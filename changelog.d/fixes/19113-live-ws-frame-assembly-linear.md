- **fix(ws):** the `/v1/ws` bridge used by `npm start` and `npm run dev` re-copied its whole input buffer on every TCP chunk, so a large frame cost quadratic CPU (about 20 s for 64 MiB) and had no size cap besides `Number.MAX_SAFE_INTEGER`. Input now goes into one buffer that grows by doubling, so a frame costs linear copying and the same few objects whether it arrives in 64 KiB reads or 1-byte reads. A frame over 16 MiB (the `/v1/responses` WebSocket limit) closes the connection with `1009` as soon as its header arrives, and a fragmented message does so once the fragment that crosses 16 MiB arrives or it passes 16384 fragments (`ws` closes that case with `1008`). An unmasked client frame now closes the connection with `1002` instead of being re-decoded with every later chunk. When an oversized or unmasked header arrives in the same read as complete frames before it, those earlier frames are dropped with the connection. The base had no size cap, so it handled them when the bad header was oversized; an unmasked header made the base drop them as well.
