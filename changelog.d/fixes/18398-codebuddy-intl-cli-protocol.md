- **fix(providers):** align the `codebuddy-intl` executor with the official CodeBuddy International CLI (`CLI/2.175.0`) instead of the IDE profile it had drifted into, so identity headers, the request body, the model catalog and rate-limit handling all describe the same request: the `X-Conversation-*` / `X-Root-Request-ID` / `X-Trace-ID` identifier families are modelled separately and kept correlated per request (a `WeakMap` on the request body replaces an instance field that leaked ids between concurrent turns on the cached executor singleton), and a retry now advances the attempt, re-parents its span and bumps `x-stainless-retry-count` instead of replaying the first attempt's identity; `GET /v3/config?repos[]=` becomes the authoritative model catalog, fetched at runtime, cached per account with a TTL and merged into the curated list at the route, so the gateway decides which models exist while the curated registry keeps the metadata it does not publish (context windows, output caps, vision/reasoning flags) and any model the gateway omits — previously the first successful fetch replaced those rows with gateway-only ones and silently dropped that metadata; and the client fingerprint is derived from the running process instead of claiming to be the captured Windows/x64 host. A `429` carrying an unlock date freezes the account until that date instead of being retried after generic backoff — via a new per-provider `trustUpstreamResetDate` registry opt-in, because the connection-cooldown profile sets `useUpstreamRetryHints` per CATEGORY (all OAuth providers share one value) and the operator's `maxCooldownMs` cap (30 min by default) would otherwise truncate a 9-hour reset. A live run against `www.codebuddy.ai` with a real account turned the assumptions into evidence and exposed the defects behind them: the dated `429` never reached the freeze at all, because the resolved OAuth profile discards upstream retry hints (`cooldownMs: 5000` for a real 9-hour reset, measured), so the account was retried minutes after the provider said it would be limited. The real capture also shows the date arrives in PROSE (`your usage will reset at 2026-10-26 10:17:44`, read as UTC), not in a structured `data.resetTime` field. The same run showed the curated lineup had drifted from `/v3/config` (`gemini-3.5-flash`, `minimax-m3` and `step-5-preview` are no longer served), so they are dropped ([#18398](https://github.com/cheaper-inference/OmniRoute/pull/18398)).
