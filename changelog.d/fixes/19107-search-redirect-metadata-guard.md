- **fix(security):** `/v1/search` checked only the first URL against the cloud-metadata guard, by name, and then let `fetch()` follow redirects on its own, so a permitted host (including a caller-supplied SearXNG `provider_options.baseUrl`) could answer `302` and land the request on `169.254.169.254`, and a DNS name that resolves to that address passed the check even without a redirect. Search providers that go through the shared provider fetch (SearXNG, Firecrawl and every other search provider except `zai-search` and `duckduckgo-free`) now follow redirects by hand (only 301, 302, 303, 307 and 308, at most five), re-run the block-metadata check on every `Location`, and on a direct connection check the resolved address at connect time for every redirect hop and for a first hop to an operator or caller base URL (built-in provider hosts keep the pooled connection). Loopback and LAN hops are still allowed, so a self-hosted SearXNG behind a redirect keeps working; Authorization, Cookie, Proxy-Authorization, x-api-key and x-subscription-token are dropped on cross-origin hops (fetch() keeps the last two; this does not), and a provider that sets `redirect: "error"` (Parallel) keeps it. Behind a proxy only the name check applies. `zai-search` talks to its MCP endpoint through its own transport and is not covered; `duckduckgo-free` calls a fixed public URL through its own public-only check and is unchanged. Under Bun, which is not a supported runtime, the connect-time guard is unavailable and fails closed: a SearXNG base URL outside the default `localhost:8888` origin, any other operator or caller base URL, and any search that follows a redirect return an error there. Executor base URL overrides fail the same way under Bun but can opt out with `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`; search has no opt-out.
