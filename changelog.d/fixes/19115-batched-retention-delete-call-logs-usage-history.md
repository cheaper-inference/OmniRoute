- **fix(db):** scheduled retention cleanup no longer removes all expired `call_logs` and `usage_history` rows in one `DELETE`, which on a large backlog blocked request handling and held the SQLite write lock for the whole run. `call_logs` now goes 10,000 rows per statement and `usage_history` one whole day per statement, with the event loop running in between so other writers can proceed (that also means new rows can land during a long cleanup; the next run picks them up against the same retention cutoff). `usage_history` is not split inside a day, so an interrupted cleanup cannot leave a partial day that the next rollup would undercount; one very large day is still a single statement. Wall-clock total can go up; the point is that each statement's write-lock hold is capped by the batch or day, not the whole backlog. Absolute timings depend on row width and machine load.
