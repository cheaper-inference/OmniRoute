- **feat(providers):** add the MiniMax Code provider — OmniRoute can now route chat completions through the managed MiniMax subscription gateway under the `minimax-code` / `mmcode` alias. The gateway path reads the local refresh token of the user's own MiniMax Code profile (`~/.minimax/auth/prod/<region>/mcode-public/auth.json`) and rewrites the auth files of that profile when the account rotates the credential, so the CLI and the local agent pick the rotated credential up on their next session; OmniRoute does not persist a separate provider credential in its connection database. The transport speaks the native tool protocol, so a request that carries client tools comes back as `tool_calls` for the client to execute, and a refusal of the gateway keeps its own status instead of being renamed into an outage of the model ([#17286](https://github.com/diegosouzapw/OmniRoute/pull/17286))
- **feat(oauth):** the MiniMax Code provider can now be signed in from the dashboard — the provider page offers the MiniMax account device-code flow (RFC 8628 + S256-PKCE), the panel shows the verification URL and the code to confirm, and the credential that comes back is written into the local MiniMax Code profile, so the CLI and the local agent pick it up on their next session; the provider itself stays a no-auth provider: the dashboard connection is the account entry, the local profile is the credential ([#17286](https://github.com/diegosouzapw/OmniRoute/pull/17286))
- **fix(sse):** refuse an oversized MiniMax Code request with a request-scoped 413 — a request that did not fit the ceiling of the managed gateway was refused with a status that the combo layer renamed into a 502, and a 502 is in the model-lockout list, so one request that was too large took the MiniMax leg out of every combo for minutes and the next request answered 503; the refusal is now a 413 marked `invalid_request_error`, which is a property of the request and never of the model ([#17286](https://github.com/diegosouzapw/OmniRoute/pull/17286))
- **fix(sse):** the MiniMax Code executor answers 499 while the instance is draining — a graceful shutdown tears the transport down under the requests that are still in flight, so the failure is evidence about our own shutdown and not about the health of the provider, but a 502 said the opposite: it is in the model-lockout list and in the provider-breaker list, and it is not exempt from the connection cooldown, so the account was written as `unavailable` with a `rateLimitedUntil` into the `provider_connections` table — a state that outlives the restart; the answer during a drain is now 499, the status an aborted caller already gets, which carries `client_disconnected` and is exempt from that cooldown ([#17286](https://github.com/diegosouzapw/OmniRoute/pull/17286))
