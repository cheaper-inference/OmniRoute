> សន្សំ 15-95% លើ context ដែលមានសិទ្ធិដោយស្វ័យប្រវត្តិ។ សម្រាប់ទិដ្ឋភាពទូទៅរហ័ស សូមមើល [ផ្នែក Compression ក្នុង README](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically)។

## ទិដ្ឋភាពទូទៅ

OmniRoute អនុវត្ត pipeline បង្ហាប់ prompt បែបម៉ូឌុល ដែលដំណើរការ **ជាមុន** មុនពេលសំណើទៅដល់ provider ខាងលើ។ នេះមានន័យថា ការសន្សំ token របស់អ្នកកើតឡើងដោយតម្លាភាព — មិនចាំបាច់ផ្លាស់ប្តូរ workflow របស់អ្នកទេ។

```
សំណើរបស់ Client
  → កម្មវិធីជ្រើសរើសយុទ្ធសាស្ត្របង្ហាប់
    → មានការកំណត់ combo ជំនួសឬ? → ប្រើការកំណត់ combo
    → ដល់កម្រិតកេះស្វ័យប្រវត្តិឬ? → ប្រើ mode ស្វ័យប្រវត្តិ
    → mode លំនាំដើមឬ? → ប្រើការកំណត់សកល
    → បិទឬ? → រំលងការបង្ហាប់
  → Mode បង្ហាប់ដែលបានជ្រើសរើស
    → បិទ: គ្មានការបង្ហាប់
    → ស្រាល: សម្អាតចន្លោះ/ទ្រង់ទ្រាយដោយសុវត្ថិភាព (~15%)
    → ស្តង់ដារ: លុបពាក្យបំពេញបែប Caveman (~30%)
    → ខ្លាំង: ធ្វើឱ្យប្រវត្តិចាស់ + សង្ខេប (~50%)
    → អតិបរមា: កាត់ចេញដោយ heuristic + សម្រួល code block (~75%)
    → RTK: ចម្រោះលទ្ធផល terminal/tool ដោយយល់ដឹងពី command (ចន្លោះ 60-90% ខាង upstream)
    → ជង់: pipeline ម៉ាស៊ីនច្រើនតាមលំដាប់ ជាធម្មតា RTK បន្ទាប់មក Caveman (ចន្លោះ 78-95% សម្រាប់ទិន្នន័យដែលមានសិទ្ធិ)
  → សំណើដែលបានបង្ហាប់ → Provider
```

## របៀបបង្ហាប់

### បិទ (Off)

មិនមានការបង្ហាប់ត្រូវបានអនុវត្តទេ។ សារទាំងអស់ឆ្លងកាត់ដោយគ្មានការផ្លាស់ប្តូរ។

### របៀប Lite (សន្សំ ~15%, ភាពយឺតយ៉ាវ <1ms)

របៀបដែលមានសុវត្ថិភាពបំផុត — គ្មានការផ្លាស់ប្តូរអត្ថន័យទាល់តែសោះ មានតែការសម្អាតទម្រង់ប៉ុណ្ណោះ៖

| បច្ចេកទេស                | ការពិពណ៌នា                                         |
| ------------------------ | -------------------------------------------------- |
| `collapseWhitespace`     | បញ្ចូលបន្ទាត់ទទេជាប់ៗគ្នា និងចន្លោះទទេនៅចុងបន្ទាត់ |
| `dedupSystemPrompt`      | លុបសារប្រព័ន្ធដែលស្ទួនគ្នាចេញ                      |
| `compressToolResults`    | បង្ហាប់លទ្ធផលឧបករណ៍/មុខងារដែលវែងអន្លាយ             |
| `removeRedundantContent` | ដកការណែនាំដែលធ្វើឡើងម្តងហើយម្តងទៀតចេញ              |
| `replaceImageUrls`       | បង្ខំ data URI រូបភាព base64 ឱ្យខ្លីជាងមុន         |

**សមរម្យបំផុតសម្រាប់:** ការប្រើប្រាស់បើកជាប់ជានិច្ច លំហូរការងារដែលសុវត្ថិភាពជាកត្តាសំខាន់។

### របៀប Standard (សន្សំ ~30%)

បានទទួលការបំផុសគំនិតពី [Caveman](https://github.com/JuliusBrussee/caveman) — លុបពាក្យបំពេញភាល់ និងឃ្លាវែងអន្លាយចេញ ខណៈពេលរក្សាអត្ថន័យ៖

- លុបពាក្យបំពេញភាល់ ("please", "I think", "basically", "actually")
- បង្រួមឃ្លាវែងអន្លាយ ("in order to" → "to", "as a result of" → "because")
- ដកការនិយាយប្រព្រឹត្តសុភាពលម្អិតចេញ ("Would you mind...", "If you could possibly...")
- ច្បាប់ regex ចំនួន 30+ ដែលបានកែសម្រួលសម្រាប់ prompt សរសេរកូដ

**សមរម្យបំផុតសម្រាប់:** លំហូរការងារសរសេរកូដប្រចាំថ្ងៃ ក្រុមដែលយកចិត្តទុកដាក់លើថ្លៃដើម។

### របៀប Aggressive (សន្សំ ~50%)

ការគ្រប់គ្រងប្រវត្តិឆ្លាតវៃសម្រាប់សម័យយូរ៖

- **ការចាស់ទុំសារ (Message Aging)** — សារចាស់ៗត្រូវបានបង្ហាប់កាន់តែច្រើនឡើងតាមពេលវេលា
- **ការបង្ហាប់លទ្ធផលឧបករណ៍** — លទ្ធផលឧបករណ៍វែងៗត្រូវបានកាត់ចុះ ឬលុបផ្នែកមួយចំនួនចេញ (បន្ទាត់ដំបូង/ចុងក្រោយ
  ការត្រងបន្ទាត់ដែលត្រូវគ្នា ការបង្រួម key របស់ JSON)
- **ការការពារភាពពេញលេញនៃរចនាសម្ព័ន្ធ** — ធានាថាគូ `tool_use` + `tool_result` នៅតែត្រឹមត្រូវ
- **ការយល់ដឹងអំពី Context Window** — គោរពដែនកំណត់ token តាមម៉ូដែលនីមួយៗ

**សមរម្យបំផុតសម្រាប់:** សម័យ debugging យូរ មូលដ្ឋានកូដធំៗ។

### របៀប Ultra (សន្សំ ~75%)

ការបង្ហាប់អតិបរមាសម្រាប់ស្ថានភាពដែល token ជាកត្តាសំខាន់៖

- **ការកាត់ចោលតាម Heuristic** — ការកាត់ token នៃអត្ថបទសាស្ត្រដោយផ្អែកលើពិន្ទុ
- **ការរក្សារចនាសម្ព័ន្ធ** — ប្លុកកូដដែលមានរបាំង (fenced) កូដ inline, URLs និងអត្តសញ្ញាណ
  ត្រូវបានដាក់ជា tombstone ហើយដាក់ត្រឡប់មកវិញដោយពាក្យដើម មិនដែលត្រូវបានកាត់ចោលឡើយ
- **ជាន់ SLM ជាជម្រើស** — ម៉ូដែលមូលដ្ឋានតូចមួយអាចកែសម្រួលការកាត់ចោល នៅពេលដែលបានកំណត់រចនាសម្ព័ន្ធ
- ឯករាជ្យពីរបៀប Aggressive: វាមិនដំណើរការការចាស់ទុំសារ ការបង្ហាប់លទ្ធផលឧបករណ៍ ឬឧបករណ៍សង្ខេប fallback ទេ
  (មានតែការបរាជ័យនៃជាន់ SLM ប៉ុណ្ណោះ ដែលអាចបញ្ជូនដំណើរការ fallback មួយតាមរយៈ
  aggressive)

**សមរម្យបំផុតសម្រាប់:** នៅពេលដែលអ្នកជួបដែនកំណត់ context ដាច់ៗគ្នា។

### របៀប RTK (ជួរ upstream 60-90%)

របៀប RTK ត្រូវបានបង្កើនប្រសិទ្ធភាពសម្រាប់លទ្ធផលឧបករណ៍ដែលវែងអន្លាយ ដែលបង្ហាញក្នុងសម័យ coding-agent៖

- រកឃើញប្រភេទពាក្យបញ្ជា/លទ្ធផល ដូចជា `git status`, `git diff`, `git log`, test runners,
  builds របស់ TypeScript/Vite/Webpack, ESLint/Biome/Prettier, npm audit/installs, Docker logs,
  លទ្ធផល infra និងលទ្ធផល shell ទូទៅ
- អនុវត្តកញ្ចប់តម្រង JSON ពី `open-sse/services/compression/engines/rtk/filters/`
- នាំចូលតម្រង RTK TOML schema v1 ពីឯកសារ `filters.toml` របស់គម្រោង ឬជាសកល ជាមួយនឹងការផ្ទៀងផ្ទាត់
  inline-test និង trust-gating សម្រាប់ឯកសារគម្រោង
- ភ្ជាប់មកជាមួយតម្រង built-in ចំនួន 56 ជាមួយគំរូ verify inline
- លុបលំដាប់គ្រប់គ្រង ANSI របារវឌ្ឍនភាព បន្ទាត់ដដែលៗ និងសំលេងរំខានដែលមិនអាចអនុវត្តសកម្មភាពបាន

## គណនាវិធីសាស្ត្រសន្សំ Upstream

OmniRoute កត់ត្រាការសន្សំពីការបង្ហាប់ដែលបានមកពីប្រភពពីរ៖ លទ្ធផលសាកល្បងសមត្ថភាពរបស់គម្រោង upstream និង
ការផ្គុំ engine ផ្ទាល់របស់ OmniRoute។

| ប្រភព   | លេខពី README របស់ upstream ដែលប្រើនៅទីនេះ                                                                                     |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Caveman | output token តិចជាង `~75%`, ការសន្សំ output ជាមធ្យម `65%` ពីការសាកល្បងសមត្ថភាព, ចន្លោះ `22-87%` និងឧបករណ៍បង្ហាប់ input `~46%` |
| RTK     | ការសន្សំ command-output `60-90%`; session គំរូ `~118,000 -> ~23,900` tokens ឬសន្សំបាន `79.7%` (`~80%`)                        |

សម្រាប់ payload របស់ tool/context ដែលត្រួតស៊ីគ្នា combo លំនាំដើមរបស់ OmniRoute ដាក់ engine បន្តគ្នា៖

```txt
RTK -> Caveman
```

ការសន្សំរួមត្រូវគុណគ្នា មិនមែនបូកគ្នាទេ៖

```txt
រួម     = 1 - (1 - ការសន្សំ RTK) * (1 - ការសន្សំ input របស់ Caveman)
មធ្យម   = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
ចន្លោះ  = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

លេខ `78-95%` នោះអនុវត្តនៅពេលដែលទាំង RTK និង Caveman អាចកាត់បន្ថយ input/context payload ដូចគ្នា។
របៀប response output របស់ Caveman គឺដាច់ដោយឡែក៖ នៅពេលបើកវា សូមប្រើការសន្សំ output ផ្ទាល់របស់ Caveman (`65%`
ជាមធ្យម, `~75%` ជាតួលេខសំខាន់, ចន្លោះ `22-87%`)។ ការសន្សំថ្លៃប្រើប្រាស់សរុបអាស្រ័យលើសមាមាត្រ prompt/output របស់អ្នក។

ផ្ញើ header សំណើ `x-omniroute-compression` ដើម្បីកំណត់ជំនួសផែនការបង្ហាប់សម្រាប់សំណើតែមួយ។
វាមានអាទិភាពខ្ពស់បំផុត — វាមានអាទិភាពលើការកំណត់ជំនួសរបស់បន្សំការកំណត់ទិស profile ដែលសកម្ម
ការចាប់ផ្តើមស្វ័យប្រវត្តិ និង Default របស់ panel។ តម្លៃមិនស្គាល់ត្រូវបានមិនអើពើ (សំណើមិនត្រូវបានបដិសេធឡើយ) ហើយ
កុងតាក់មេសកលនៅតែគ្រប់គ្រងអ្វីៗទាំងអស់៖ នៅពេលការបង្ហាប់ត្រូវបានបិទជាសកល header មិនអាច
បើកវាបានទេ។ តម្លៃ៖

| តម្លៃ         | ផលប៉ះពាល់                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `off`         | មិនមានការបង្ហាប់សម្រាប់សំណើនេះទេ។                                                                          |
| `default`     | profile Default ដែលបានមកពី panel (មិនអើពើ profile ដែលសកម្ម)។ engine ដែលបាត់បង់ទិន្នន័យត្រូវបានបិទ។         |
| `safe`        | ដូចគ្នានឹងការមិនបញ្ចូល header៖ មានតែការលុបទិន្នន័យស្ទួន និងការបង្រួមចន្លោះទទេប៉ុណ្ណោះ។                     |
| `allow-lossy` | រក្សាផែនការរបស់ operator សម្រាប់សំណើនេះ រួមទាំងសេចក្តីសង្ខេប តម្រងភាពពាក់ព័ន្ធ និងការសរសេររចនាប័ទ្មឡើងវិញ។ |
| `engine:<id>` | engine តែមួយនៅពេលបានបើក ឧ. `engine:rtk`។ នេះគឺជាការយល់ព្រមប្រើ engine នោះតាមសំណើ។                          |
| `<combo>`     | បន្សំដែលមានឈ្មោះ ដោយផ្គូផ្គងតាមឈ្មោះជាមុនសិន (មិនប្រកាន់តួអក្សរធំតូច) បន្ទាប់មកតាម id។                     |

បើគ្មាន `allow-lossy`, `engine:<id>` ឬបន្សំដែលមានឈ្មោះទេ engine ដែលបាត់បង់ទិន្នន័យនឹងមិនត្រូវបានអនុវត្តឡើយ។
សំណើនៅតែទទួលបានការលុបទិន្នន័យស្ទួនតាម session និងការបង្រួមចន្លោះទទេ នៅពេលការបង្ហាប់ត្រូវបានបើក។

ផែនការដែលបានអនុវត្តត្រូវបានឆ្លុះតបវិញនៅក្នុង header ឆ្លើយតប `X-OmniRoute-Compression: <mode>; source=<source>`
ដែល `<source>` គឺជាតម្លៃមួយក្នុងចំណោម `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` ឬ `off`។

### API

```bash
# ទទួលយកការកំណត់ការបង្ហាប់
curl http://localhost:20128/api/settings/compression

# ធ្វើបច្ចុប្បន្នភាពការកំណត់ការបង្ហាប់
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# មើលជាមុននូវ payload RTK/stacked ជាក់លាក់មួយ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# រាយបញ្ជីកញ្ចប់តម្រង RTK
curl http://localhost:20128/api/context/rtk/filters

# សាកល្បង RTK ដោយផ្ទាល់ជាមួយ metadata ពាក្យបញ្ជាជាជម្រើស
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

### ការបង្ហាប់ដែលគិតគូរអំពីឃ្លាំងសម្ងាត់

អ្នកផ្តល់សេវាមួយចំនួន (ដូចជា Anthropic ដែលមាន prompt caching) គាំទ្រ **prompt caching**
ដែលអនុញ្ញាតឱ្យពួកគេរក្សាទុកផ្នែកខ្លះនៃ prompt ក្នុងឃ្លាំងសម្ងាត់ ដើម្បីកាត់បន្ថយថ្លៃដើម និងភាពយឺតយ៉ាវ។ នៅពេល
ការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ត្រូវបានបើក ការបង្ហាប់ខ្លាំងក្លាអាចធ្វើឱ្យដំណើរការ **កាន់តែអន់**
ព្រោះវាផ្លាស់ប្តូរ token ដែលបានរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ ធ្វើឱ្យឃ្លាំងសម្ងាត់នោះលែងមានសុពលភាព។

ម៉ូឌុល `cachingAware.ts` ដោះស្រាយបញ្ហានេះដោយ **រកឃើញបរិបទនៃការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់** និង
**កែសម្រួលយុទ្ធសាស្ត្របង្ហាប់** ឱ្យសមស្រប។

#### របៀបដែលវាដំណើរការ

1. **រកឃើញបរិបទនៃការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់** — ស្កេនតួសំណើដើម្បីស្វែងរកសញ្ញាសម្គាល់ `cache_control`
2. **កំណត់អត្តសញ្ញាណអ្នកផ្តល់សេវាដែលប្រើឃ្លាំងសម្ងាត់** — ពិនិត្យថាតើអ្នកផ្តល់សេវាគោលដៅគាំទ្រការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ឬអត់
3. **កែសម្រួលយុទ្ធសាស្ត្រ** — បន្ទាប `aggressive`/`ultra` ទៅជា `standard` សម្រាប់អ្នកផ្តល់សេវាដែលប្រើឃ្លាំងសម្ងាត់
4. **រំលង system prompt** — ជាទូទៅ system prompt ត្រូវបានរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ ដូច្នេះកុំបង្ហាប់វា

អនុគមន៍ជំនួយរបស់យុទ្ធសាស្ត្រក៏ត្រឡប់ flag `deterministicOnly` មួយផងដែរ ប៉ុន្តែកម្មវិធីបង្កើតផែនការ
ប្រើប្រាស់តែយុទ្ធសាស្ត្រប៉ុណ្ណោះ — បច្ចុប្បន្ននេះ គ្មានអ្វីនៅដំណាក់កាលបន្ទាប់អាន flag នោះទេ។

#### ឧទាហរណ៍កូដ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← សញ្ញាសម្គាល់ឃ្លាំងសម្ងាត់
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ពេលណាដែលត្រូវប្រើ

ការបង្ហាប់ដែលគិតគូរអំពីឃ្លាំងសម្ងាត់គឺ **បើកជានិច្ច** — មិនចាំបាច់កំណត់រចនាសម្ព័ន្ធទេ។ វាចាប់ផ្តើមដំណើរការនៅពេលណាក៏ដោយដែល
ការបង្ហាប់ត្រូវបានបើក ហើយអ្នកផ្តល់សេវាគោលដៅគាំទ្រ prompt caching (Anthropic, OpenAI,
ជាដើម)។ សញ្ញាសម្គាល់ `cache_control` ដែលបានកំណត់ជាក់លាក់មិនត្រូវបានទាមទារទេ — គ្រាន់តែជាអ្នកផ្តល់សេវាដែលប្រើឃ្លាំងសម្ងាត់
ក៏បង្កឱ្យមានការបន្ទាបកម្រិតដែរ ហើយសញ្ញាសម្គាល់តែឯងមិនដែលបង្កឱ្យមានវាទេ (ការរកឃើញសញ្ញាសម្គាល់ផ្តល់ទិន្នន័យដល់ telemetry នៃឃ្លាំងសម្ងាត់
មិនមែនការសម្រេចចិត្តអំពីយុទ្ធសាស្ត្រទេ)។

### ការធ្វើឱ្យចាស់ជាបន្តបន្ទាប់

ការសន្ទនាវែងៗប្រមូលផ្តុំសារជាច្រើនវគ្គ ប៉ុន្តែវគ្គចាស់ៗកាន់តែមិនសូវ
ពាក់ព័ន្ធ។ ម៉ូឌុល `progressiveAging.ts` **បន្ថយកម្រិតលម្អិតរបស់សារតាមចម្ងាយវគ្គ**
(ចម្ងាយត្រូវបានវាស់ពីចុងបញ្ចប់នៃការសន្ទនា)។ ជាមួយនឹងតម្លៃលំនាំដើមដែលបានផ្តល់មក
(`verbatim: 2, light: 2, moderate: 3`)៖

- **2 វគ្គចុងក្រោយ (ចម្ងាយ ≤ 2)**៖ រក្សាទុកដូចដើមទាំងស្រុង
- **ចម្ងាយ 3**៖ ការបង្ហាប់ Caveman (ដកពាក្យបំពេញចេញ)
- **ចម្ងាយ 4+**៖ សាររបស់ assistant ត្រូវបានសង្ខេប។ សាររបស់ user ត្រូវបានកាត់ឱ្យនៅសល់តែបន្ទាត់ទីមួយ
  និងកំណត់ត្រឹម 120 តួអក្សរ។ role ផ្សេងទៀតមិនត្រូវបានប៉ះពាល់ទេ។ System prompt សារដែលបានធ្វើឱ្យចាស់
  រួចហើយ និងសារចុងក្រោយបំផុតរបស់ user តែងតែត្រូវបានរក្សាទុកដូចដើមទាំងស្រុង ដោយមិនគិតពីចម្ងាយ។
  គ្មានអ្វីត្រូវបានលុបចោលទាំងស្រុងទេ ហើយកម្រិត `light`
  មិនអាចឈានដល់បានទេជាមួយនឹងតម្លៃលំនាំដើមដែលបានផ្តល់មក (`light` ស្មើនឹង `verbatim`)។

#### ឧទាហរណ៍កូដ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 វគ្គទៀត ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // 3 វគ្គចុងក្រោយ៖ រក្សាទុកដូចដើម
  light: 8, // ចម្ងាយ <= 8៖ ការបង្ហាប់កម្រិតស្រាល
  moderate: 20, // ចម្ងាយ <= 20៖ ការបង្ហាប់ Caveman
  fullSummary: 5, // ត្រូវបានទាមទារដោយ type ប៉ុន្តែមិនត្រូវបានអានដោយកូដបែងចែកកម្រិតទេ
  // ចម្ងាយ > 20៖ សង្ខេប (assistant) / រក្សាទុកបន្ទាត់ទីមួយ (user)
});

// saved = ចំនួន token ដែលបានសន្សំ
```

#### ពេលណាដែលត្រូវប្រើ

ការធ្វើឱ្យចាស់ជាបន្តបន្ទាប់គឺ **បើកជានិច្ច** សម្រាប់របៀប `aggressive` — វាជាជំហានទី 2 នៃ
`compressAggressive()`។ របៀប Ultra មិនដំណើរការវាទេ។ វាមានប្រសិទ្ធភាពជាពិសេសសម្រាប់៖

- វគ្គសរសេរកូដដែលដំណើរការយូរ
- ការសន្ទនារយៈពេលច្រើនថ្ងៃ
- លំហូរការងារបែប agent ដែលមានការហៅឧបករណ៍ជាច្រើន

### របៀបលទ្ធផល Caveman

របៀបលទ្ធផល Caveman បន្ថែម **ការណែនាំក្នុង system prompt** ដែលស្នើឱ្យម៉ូដែលផ្តល់
លទ្ធផលខ្លីរហ័ស — កម្រិត `lite` ស្នើឱ្យផ្តល់ចម្លើយខ្លីដែលនៅតែរក្សាប្រយោគពេញលេញ កម្រិត `full`
ស្នើឱ្យវា "ឆ្លើយខ្លីៗដូចមនុស្សល្អាងឆ្លាត" ហើយកម្រិត `ultra` ស្នើឱ្យផ្តល់លទ្ធផលបែបសារទូរលេខ។
ការណែនាំគ្រាន់តែស្នើប៉ុណ្ណោះ វាមិនអាចធានាបានទេ។ សំណើទទួលបានការណែនាំទាំងនេះតាមរយៈ
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`)៖
ដំបូង `open-sse/handlers/chatCore.ts` ដោះស្រាយជម្រើសដោយប្រើ back-compat shim
(`resolveOutputStyleSelection()` នៅក្នុង
`open-sse/services/compression/outputStyles/backCompat.ts`) ដែលនៅពេល `outputStyles`
ទទេ វាផ្គូផ្គង `cavemanOutputMode` ដែលបានបើកទៅនឹងរចនាប័ទ្មលទ្ធផល `terse-prose` នៅកម្រិត
`cavemanOutputMode.intensity` (សូមមើល Back-compat ខាងក្រោម)។ ជម្រើស `outputStyles`
ដែលមិនទទេត្រូវបានប្រើតាមសភាពដើម ហើយបន្ទាប់មក `cavemanOutputMode.enabled` និង `intensity` មិនមាន
ឥទ្ធិពលទេ ខណៈដែលប៊ូតុងបិទបើក `autoClarity` របស់វានៅតែត្រូវបានអនុវត្ត។ `outputMode.ts` ផ្ទុក
អត្ថបទណែនាំ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`) ការរំលងដោយផ្អែកលើមាតិកា និង
អនុគមន៍ជំនួយកំណត់ទីតាំងដែលការចាក់បញ្ចូលប្រើ។ ឧបករណ៍ចាក់បញ្ចូល `applyCavemanOutputMode()` ផ្ទាល់របស់វា មិនមាន
អ្នកហៅប្រើក្នុង production ទេ។

#### របៀបដែលវាដំណើរការ

របៀបនេះមិនបង្ហាប់ input ទេ។ វាបន្ថែមប្លុកសេចក្តីណែនាំទៅក្នុង system prompt
(មើល របៀបដែលការបញ្ចូលដំណើរការ ខាងក្រោម) ហើយរបៀបបង្ហាប់ input ណាមួយដែលបានជ្រើសសម្រាប់ request
នៅតែដំណើរការបន្ទាប់ពីនោះ លើ body ដែលឥឡូវមានប្លុកនោះ។ មុនឃ្លាព្រំដែនរួម
ដែលគ្រប់កម្រិតបញ្ចប់ដោយវា កម្រិត `full` ជាភាសាអង់គ្លេសមានខ្លឹមសារថា៖

> "ឆ្លើយខ្លីរឹងមាំដូចមនុស្សរូងភ្នំឆ្លាត។ ដក article (a/an/the), ពាក្យបំពេញ (just/really/basically/actually/simply), ពាក្យគួរសម និងពាក្យបន្ធូរបន្ថយភាពច្បាស់លាស់។ ប្រយោគមិនពេញលេញក៏បាន។ ប្រើពាក្យមានន័យដូចគ្នាដែលខ្លី (big មិនមែន extensive, fix មិនមែន implement)។ រក្សាខ្លឹមសារបច្ចេកទេសទាំងអស់ code, errors, URLs និង identifiers ឱ្យដូចដើម។"

វាដំណើរការល្អជាពិសេសសម្រាប់៖

- ការបង្កើត code (output ខ្លីជាង = tokens តិចជាង)
- សំណួរ-ចម្លើយរហ័ស (មិនចាំបាច់មានការពន្យល់វែងឆ្ងាយ)
- ការដំណើរការជាបាច់ (បង្កើន throughput អតិបរមា)

#### ពេលណាគួរប្រើ

របៀប output បែបមនុស្សរូងភ្នំគឺត្រូវតែ **ជ្រើសបើកដោយខ្លួនឯង**។ នៅពេលបើកការបង្ហាប់ (`enabled: true` ដែលជា toggle មេ
នៅលើទំព័រ Compression Settings) សូមបើកវាដោយ `cavemanOutputMode.enabled`; `intensity`
ជ្រើស `lite`, `full` ឬ `ultra`៖

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

toggle **Output Mode** របស់ combo ការបង្ហាប់មួយ (`outputMode` និងកម្រិតក្នុង `outputModeIntensity`)
កំណត់ switch ដូចគ្នាសម្រាប់ requests ដែល combo នោះអនុវត្តទៅលើ ហើយឧបករណ៍ MCP

#### របៀបដែលការបញ្ចូលដំណើរការ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ផ្គូផ្គងជម្រើសជាមួយកាតាឡុក (id ដែលមិនស្គាល់ និងស្ទីលដែលមិនត្រូវគ្នានឹង locale ត្រូវបានដកចេញ ដោយមិនចាត់ទុកជាកំហុសឡើយ; ជម្រើសដែលផ្គូផ្គងហើយមិនទទួលបានស្ទីលណាមួយ នឹងទុក body ឱ្យនៅដដែល ហើយរំលងជា `no_styles`), ភ្ជាប់សេចក្ដីណែនាំដែលបានជ្រើសតាមលំដាប់កាតាឡុក,
បន្ថែមឃ្លាកំណត់ព្រំដែន **តែម្ដង** (រួមទាំងឃ្លាសុវត្ថិភាព `SAFETY_BOUNDARIES` ឬការបកប្រែរបស់វា នៅពេលបានជ្រើស `less-code` ឬ `ponytail`) ហើយចាប់ផ្ដើមប្លុកដោយសញ្ញាសម្គាល់ idempotency តែមួយ (`[OmniRoute Output Styles]`) ដូច្នេះការអនុវត្តម្ដងទៀតនឹងមិនធ្វើអ្វីឡើយ។ នៅពេលភាសាដែលបានកំណត់ (សូមមើលការជ្រើសរើសភាសាខាងក្រោម) មានការបកប្រែ សេចក្ដីណែនាំជាភាសាមូលដ្ឋាននឹងត្រូវបានបញ្ចូលជំនួសភាសាអង់គ្លេស។

សម្រាប់ body ដែលមាន array `messages` មិនទទេ ការត្រួតពិនិត្យ idempotency ដំណើរការមុនការរំលងផ្អែកលើខ្លឹមសារ៖ នៅពេលសញ្ញាសម្គាល់ `[OmniRoute Output Styles]` មានរួចហើយក្នុង field `system` កម្រិតកំពូល (ជា string ឬជា array នៃ content-block) ឬក្នុង system message ដែលមានខ្លឹមសារជា string នោះ body ត្រូវបានទុកឱ្យនៅដដែលជា `already_applied` ហើយមិនមានការត្រួតពិនិត្យពាក្យគន្លឹះណាមួយទេ។

## ការកំណត់ជាន់លើនៃការបង្ហាប់តាម Combo

អ្នកអាចកំណត់ជាន់លើរបៀបបង្ហាប់សកល **សម្រាប់ combo នីមួយៗ** ដើម្បីកែសម្រួលឥរិយាបថឱ្យសមស្រប

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

វាមានប្រយោជន៍សម្រាប់៖

- **Combo សរសេរកូដ**៖ ប្រើរបៀប `aggressive` សម្រាប់សម័យការងារយូរ
- **Combo សំណួរ និងចម្លើយរហ័ស**៖ ប្រើរបៀប `lite` សម្រាប់ការឆ្លើយតបរហ័ស
- **Combo ដែលប្រើឧបករណ៍ច្រើន**៖ ប្រើរបៀប `stacked` ដើម្បីសន្សំបានអតិបរមា
- **Combo សម្រាប់បរិស្ថានផលិតកម្ម**៖ កុំបើកការកំណត់ជាន់លើសម្រាប់អ្នកផ្តល់សេវាដែលប្រើឃ្លាំងសម្ងាត់ — ការកែសម្រួល
  ដែលគិតគូរពីឃ្លាំងសម្ងាត់ និងបើកជានិច្ច នឹងបន្ថយកម្រិត `aggressive`/`ultra` ទៅជា `standard` ដោយស្វ័យប្រវត្តិ
  (មិនមានរបៀប `cache-aware` ដែលអាចជ្រើសរើសបានទេ)
