## ទិដ្ឋភាពទូទៅ

OmniRoute អនុវត្ត pipeline បង្ហាប់ prompt បែបម៉ូឌុល ដែលដំណើរការ **ជាមុន** មុនពេលសំណើទៅដល់ provider ខាងលើ។ នេះមានន័យថា ការសន្សំ token របស់អ្នកកើតឡើងដោយតម្លាភាព — មិនចាំបាច់ផ្លាស់ប្តូរ workflow របស់អ្នកទេ។

```
សំណើរបស់ Client
  → កម្មវិធីជ្រើសរើសយុទ្ធសាស្ត្របង្ហាប់
    → មានការកំណត់ combo ជំនួសឬ? → ប្រើការកំណត់ combo
    → ដល់កម្រិតកេះស្វ័យប្រវត្តិឬ? → ប្រើ mode ស្វ័យប្រវត្តិ
    → mode លំនាំដើមឬ? → ប្រើការកំណត់សកល
    → បិទឬ? → រំលងការបង្ហាប់
  → Mode បង្ហាប់ដែលបានជ្រើសរើស
    → បិទ: គ្មានការបង្ហាប់
    → ស្រាល: សម្អាតចន្លោះ/ទ្រង់ទ្រាយដោយសុវត្ថិភាព (~15%)
    → ស្តង់ដារ: លុបពាក្យបំពេញបែប Caveman (~30%)
    → ខ្លាំង: ធ្វើឱ្យប្រវត្តិចាស់ + សង្ខេប (~50%)
    → អតិបរមា: កាត់ចេញដោយ heuristic + សម្រួល code block (~75%)
    → RTK: ចម្រោះលទ្ធផល terminal/tool ដោយយល់ដឹងពី command (ចន្លោះ 60-90% ខាង upstream)
    → ជង់: pipeline ម៉ាស៊ីនច្រើនតាមលំដាប់ ជាធម្មតា RTK បន្ទាប់មក Caveman (ចន្លោះ 78-95% សម្រាប់ទិន្នន័យដែលមានសិទ្ធិ)
  → សំណើដែលបានបង្ហាប់ → Provider
```

## របៀបបិទ

មិនអនុវត្តការបង្ហាប់ទេ។ សារទាំងអស់ឆ្លងកាត់ដោយមិនមានការផ្លាស់ប្តូរ។

### របៀប Lite (~សន្សំបាន 15%, ភាពយឺតយ៉ាវ <1ms)

របៀបដែលមានសុវត្ថិភាពបំផុត — សម្អាតការរៀបចំទ្រង់ទ្រាយ។ ការកាត់បន្ថយលទ្ធផលឧបករណ៍របស់វាបាត់បង់ទិន្នន័យ ដូច្នេះផ្លូវលំនាំដើម
(គ្មានការជ្រើស `allow-lossy`, `engine:lite` ឬការជ្រើសរើស named-combo) ដំណើរការ lite ជាមួយ
`compressToolResults: false`៖ លទ្ធផលឧបករណ៍មុនៗទៅដល់អ្នកផ្តល់សេវាដោយមិនមានការផ្លាស់ប្តូរ។

| បច្ចេកទេស                | ការពិពណ៌នា                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | បញ្ចូលបន្ទាត់ទទេជាប់គ្នា និងដកចន្លោះនៅខាងចុង                                                    |
| `dedupSystemPrompt`      | លុបសារប្រព័ន្ធស្ទួន                                                                             |
| `compressToolResults`    | កាត់លទ្ធផលឧបករណ៍មុនៗទៅត្រឹមកម្រិតកំណត់របស់ lite (បាត់បង់ទិន្នន័យ៖ មានតែពេលស្នើសុំជាមុនប៉ុណ្ណោះ) |
| `removeRedundantContent` | ដកសេចក្តីណែនាំដែលនិយាយដដែលៗ                                                                     |
| `replaceImageUrls`       | បង្រួមទិន្នន័យ URI រូបភាព base64                                                                |

**សមស្របសម្រាប់៖** ការប្រើប្រាស់បើកជានិច្ច និងលំហូរការងារដែលមានសារៈសំខាន់ខ្ពស់ចំពោះសុវត្ថិភាព។

### របៀប Standard (~សន្សំបាន 30%)

បានបំផុសគំនិតដោយ [Caveman](https://github.com/JuliusBrussee/caveman) — ដកពាក្យបំពេញ និងឃ្លាដែលវែងពេក ខណៈពេលរក្សាអត្ថន័យ៖

- ដកពាក្យបំពេញ ("please", "I think", "basically", "actually")
- បង្រួមឃ្លាដែលវែងពេក ("in order to" → "to", "as a result of" → "because")
- ដកការបង្ហាញភាពទន់ភ្លន់ដោយសុភាព ("Would you mind...", "If you could possibly...")
- ច្បាប់ regex ជាង 30 ដែលបានកែសម្រួលសម្រាប់ប្រូមបនៃការសរសេរកូដ

**សមស្របសម្រាប់៖** លំហូរការងារសរសេរកូដប្រចាំថ្ងៃ និងក្រុមដែលយកចិត្តទុកដាក់លើថ្លៃដើម។

### របៀប Aggressive (~សន្សំបាន 50%)

ការគ្រប់គ្រងប្រវត្តិឆ្លាតវៃសម្រាប់សម័យប្រើប្រាស់ដែលវែង៖

- **ការធ្វើឱ្យសារចាស់ទៅតាមអាយុ** — សារចាស់ៗត្រូវបានបង្រួមជាបន្តបន្ទាប់
- **ការបង្ហាប់លទ្ធផលឧបករណ៍** — លទ្ធផលឧបករណ៍វែងៗត្រូវបានកាត់ ឬលាក់ (បន្ទាត់ដំបូង/ចុងក្រោយ,
  ការត្រងតាមបន្ទាត់ដែលត្រូវគ្នា ការបង្រួមគន្លឹះ JSON)
- **ឧបករណ៍ការពារបូរណភាពរចនាសម្ព័ន្ធ** — ធានាថាគូ `tool_use` + `tool_result` នៅតែស្របគ្នា
- **ការយល់ដឹងអំពីបង្អួចបរិបទ** — គោរពដែនកំណត់ token តាមម៉ូដែលនីមួយៗ

**សមស្របសម្រាប់៖** សម័យកែបញ្ហាដែលវែង និងមូលដ្ឋានកូដធំៗ។

### របៀប Ultra (~សន្សំបាន 75%)

ការបង្ហាប់អតិបរមាសម្រាប់ស្ថានភាពដែល token មានសារៈសំខាន់ខ្លាំង៖

- **ការកាត់តាមហេយូរីស្ទិក** — កាត់ token នៃអត្ថបទពណ៌នាតាមពិន្ទុ
- **ការរក្សារចនាសម្ព័ន្ធ** — ប្លុកកូដដែលមានសញ្ញាព័ទ្ធជុំវិញ កូដក្នុងបន្ទាត់ URL និង identifier ត្រូវបានរក្សាទុកជាបណ្ដោះអាសន្ន ហើយភ្ជាប់ត្រឡប់ជាពាក្យដើម ដោយមិនដែលត្រូវបានកាត់ចេញ
- **ជម្រើសកម្រិត SLM** — ម៉ូដែលមូលដ្ឋានតូចមួយអាចកែលម្អការកាត់បាន នៅពេលកំណត់រចនាសម្ព័ន្ធ
- ឯករាជ្យពីរបៀប Aggressive៖ វាមិនដំណើរការការធ្វើឱ្យសារចាស់ទៅតាមអាយុ ការបង្ហាប់លទ្ធផលឧបករណ៍
  ឬកម្មវិធីសង្ខេបបម្រុងទុកទេ (មានតែការបរាជ័យកម្រិត SLM ប៉ុណ្ណោះដែលអាចបញ្ជូនដំណើរការបម្រុងទុកតាមរយៈ
  aggressive)

**សមស្របសម្រាប់៖** នៅពេលអ្នកជួបដែនកំណត់បរិបទម្តងហើយម្តងទៀត។

### របៀប RTK (ចន្លោះ upstream 60-90%)

របៀប RTK ត្រូវបានបង្កើនប្រសិទ្ធភាពសម្រាប់លទ្ធផលឧបករណ៍ដែលមានអត្ថបទច្រើន ដែលលេចឡើងក្នុងសម័យប្រើប្រាស់ coding-agent៖

- រកឃើញថ្នាក់ពាក្យបញ្ជា/លទ្ធផល ដូចជា `git status`, `git diff`, `git log`, អ្នកដំណើរការតេស្ត,
  ប៊ิลด์ TypeScript/Vite/Webpack, ESLint/Biome/Prettier, npm audit/installs, កំណត់ហេតុ Docker, លទ្ធផល infra
  និងលទ្ធផល shell ទូទៅ
- អនុវត្តកញ្ចប់តម្រង JSON ពី `open-sse/services/compression/engines/rtk/filters/`

## គណនាវិធីសាស្ត្រសន្សំ Upstream

OmniRoute កត់ត្រាការសន្សំពីការបង្ហាប់ដែលបានមកពីប្រភពពីរ៖ លទ្ធផលសាកល្បងសមត្ថភាពរបស់គម្រោង upstream និង
ការផ្គុំ engine ផ្ទាល់របស់ OmniRoute។

| ប្រភព   | លេខពី README របស់ upstream ដែលប្រើនៅទីនេះ                                                                                     |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Caveman | output token តិចជាង `~75%`, ការសន្សំ output ជាមធ្យម `65%` ពីការសាកល្បងសមត្ថភាព, ចន្លោះ `22-87%` និងឧបករណ៍បង្ហាប់ input `~46%` |
| RTK     | ការសន្សំ command-output `60-90%`; session គំរូ `~118,000 -> ~23,900` tokens ឬសន្សំបាន `79.7%` (`~80%`)                        |

សម្រាប់ payload របស់ tool/context ដែលត្រួតស៊ីគ្នា combo លំនាំដើមរបស់ OmniRoute ដាក់ engine បន្តគ្នា៖

```txt
RTK -> Caveman
```

ការសន្សំរួមត្រូវគុណគ្នា មិនមែនបូកគ្នាទេ៖

```txt
រួម     = 1 - (1 - ការសន្សំ RTK) * (1 - ការសន្សំ input របស់ Caveman)
មធ្យម   = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
ចន្លោះ  = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

លេខ `78-95%` នោះអនុវត្តនៅពេលដែលទាំង RTK និង Caveman អាចកាត់បន្ថយ input/context payload ដូចគ្នា។
របៀប response output របស់ Caveman គឺដាច់ដោយឡែក៖ នៅពេលបើកវា សូមប្រើការសន្សំ output ផ្ទាល់របស់ Caveman (`65%`
ជាមធ្យម, `~75%` ជាតួលេខសំខាន់, ចន្លោះ `22-87%`)។ ការសន្សំថ្លៃប្រើប្រាស់សរុបអាស្រ័យលើសមាមាត្រ prompt/output របស់អ្នក។

auto-trigger និង panel Default។ តម្លៃដែលមិនស្គាល់ត្រូវបានមិនអើពើ (សំណើមិនត្រូវបានបដិសេធទេ) ហើយ
global master switch នៅតែគ្រប់គ្រងអ្វីៗទាំងអស់៖ នៅពេលការបង្ហាប់ត្រូវបានបិទជាសកល header មិនអាច
បើកវាបានទេ។ តម្លៃ៖

| Value         | Effect                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `off`         | មិនប្រើការបង្ហាប់សម្រាប់សំណើនេះទេ។                                                               |
| `default`     | profile Default ដែលបានមកពី panel (មិនអើពើ active profile)។ ម៉ាស៊ីនដែលបាត់បង់ទិន្នន័យត្រូវបានបិទ។ |
| `safe`        | ដូចគ្នានឹងការមិនដាក់ header។                                                                     |
| `allow-lossy` | រក្សា operator plan របស់សំណើនេះ រួមទាំង summaries, relevance filters និង style rewrites។         |
| `engine:<id>` | ម៉ាស៊ីនតែមួយនៅពេលបានបើក ដូចជា `engine:rtk`។ នេះជាការជ្រើសប្រើម៉ាស៊ីននោះតាមសំណើ។                  |
| `<combo>`     | combo ដែលមានឈ្មោះ ដោយផ្គូផ្គងតាមឈ្មោះ (មិនប្រកាន់អក្សរធំតូច) ជាមុន បន្ទាប់មកតាម id។              |

បើគ្មាន `allow-lossy`, `engine:<id>` ឬ combo ដែលមានឈ្មោះទេ ម៉ាស៊ីនដែលបាត់បង់ទិន្នន័យនឹងមិនត្រូវបាន
អនុវត្តឡើយ។ នៅពេល Default, auto-trigger ឬ routing override ដែលបាត់បង់ទិន្នន័យត្រូវបានបន្ទាប
OmniRoute រក្សាទុកជំហានដែលគ្មានការបាត់បង់ដែលបានស្គាល់ ពី stacked pipeline ដែលបានកំណត់រចនាសម្ព័ន្ធ
តាមលំដាប់ដែលបានកំណត់។ វាត្រឡប់ទៅ `session-dedup → lite` វិញ លុះត្រាតែគ្មានជំហានដែលគ្មាន
ការបាត់បង់ដែលបានកំណត់រចនាសម្ព័ន្ធណាមួយនៅសល់។

ការមើលជាមុន **Effective pipeline** របស់ Settings panel បង្ហាញ at-rest plan ធម្មតា។ នៅពេល
auto-trigger អាចដំណើរការបាន ការមើលជាមុនដដែលនេះក៏បង្ហាញ conditional effective pipeline របស់វាផងដែរ
ដើម្បីឱ្យការដោះស្រាយនៅក្នុង panel និង runtime ដែលគ្មាន header រក្សាភាពស្របគ្នា។

Applied plan ត្រូវបានបញ្ជូនត្រឡប់ក្នុង response header
`X-OmniRoute-Compression: <mode>; source=<source>` ដែល `<source>` គឺមួយក្នុងចំណោម
`request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ឬ `off`។

### ការបង្ហាប់ Cache-Aware

អ្នកផ្តល់សេវាមួយចំនួន (ដូចជា Anthropic ជាមួយនឹងឃ្លាំងសម្ងាត់ភ្លាមៗ) ការគាំទ្រ** ឃ្លាំងសម្ងាត់ភ្លាមៗ** ដែលអនុញ្ញាតឱ្យពួកគេរក្សាទុកផ្នែកនៃប្រអប់បញ្ចូល ដើម្បីកាត់បន្ថយការចំណាយ និងការពន្យារពេល។ នៅពេលដែលឃ្លាំងសម្ងាត់ត្រូវបានបើក ការបង្ហាប់ដ៏ខ្លាំងក្លាអាចជាការពិត** ឈឺចាប់** ដំណើរការព្រោះវាផ្លាស់ប្តូរថូខឹនក្នុងឃ្លាំងសម្ងាត់ ធ្វើឱ្យឃ្លាំងសម្ងាត់មិនត្រឹមត្រូវ។

ម៉ូឌុល `cachingAware.ts` ដោះស្រាយវាដោយ** ការរកឃើញបរិបទឃ្លាំងសម្ងាត់** និង** ការកែតម្រូវយុទ្ធសាស្ត្របង្ហាប់** តាម។

#### របៀបដែលវាដំណើរការ

1. **រកឃើញបរិបទឃ្លាំងសម្ងាត់** — ស្កេនតួសំណើសម្រាប់សញ្ញាសម្គាល់ `cache_control`
2. **កំណត់អ្នកផ្តល់ឃ្លាំងសម្ងាត់** — ពិនិត្យមើលថាតើអ្នកផ្តល់សេវាគោលដៅគាំទ្រឃ្លាំងសម្ងាត់ឬអត់
3. **កែសម្រួលយុទ្ធសាស្ត្រ** — ទម្លាក់ចំណាត់ថ្នាក់ `aggressive`/`ultra` ទៅ `standard` សម្រាប់អ្នកផ្តល់ឃ្លាំងសម្ងាត់
4. **រំលងការជូនដំណឹងប្រព័ន្ធ** — System prompts ជាធម្មតាត្រូវបានទុកក្នុងឃ្លាំងសម្ងាត់ ដូច្នេះកុំបង្ហាប់ពួកវា

អ្នកជំនួយយុទ្ធសាស្ត្រក៏ត្រឡប់ទង់ `deterministicOnly` ដែរ ប៉ុន្តែអ្នកបង្កើតផែនការប្រើប្រាស់តែយុទ្ធសាស្ត្រ — គ្មានអ្វីនៅខាងក្រោមអានទង់ថ្ងៃនេះទេ។

#### ឧទាហរណ៍កូដ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ពេលណាត្រូវប្រើ

ការបង្ហាប់ដែលដឹងអំពីឃ្លាំងសម្ងាត់គឺ** ជានិច្ច** — មិនត្រូវការការកំណត់រចនាសម្ព័ន្ធទេ។ វាចាប់ផ្តើមនៅពេលណាដែលការបង្ហាប់បើក ហើយអ្នកផ្តល់គោលដៅគាំទ្រការបញ្ចូលឃ្លាំងសម្ងាត់ភ្លាមៗ (Anthropic, OpenAI, ល។ ); សញ្ញាសម្គាល់ `cache_control` ច្បាស់លាស់មិនត្រូវបានទាមទារ — អ្នកផ្តល់ឃ្លាំងសម្ងាត់តែម្នាក់ឯងបង្កឱ្យមានការបន្ទាបចំណាត់ថ្នាក់ ហើយសញ្ញាសម្គាល់តែម្នាក់ឯងមិនដែលធ្វើទេ (ការរកឃើញសញ្ញាសម្គាល់ផ្តល់ព័ត៌មានឃ្លាំងសម្ងាត់ មិនមែនជាការសម្រេចចិត្តយុទ្ធសាស្ត្រ) ។

OpenRouter រាប់ថាជាអ្នកផ្តល់ឃ្លាំងសម្ងាត់សម្រាប់តែម៉ូដែល `anthropic/*` ប៉ុណ្ណោះ៖ សំណើកូដ Claude រក្សាចំណុចឈប់ `cache_control` របស់ពួកគេ (ច្រើនបំផុត 4) ហើយឆ្មាំការពារបុព្វបទ ខណៈពេលដែលគ្រួសារ OpenRouter ផ្សេងទៀត (`openai/`, `google/`, `qwen/`, … ) នៅតែត្រូវបានដកចេញ និងមិនមានការការពារ។

### ភាពចាស់ជរារីកចម្រើន

ការសន្ទនាវែងៗប្រមូលផ្តុំវេនសារជាច្រើន ប៉ុន្តែវេនចាស់ៗកាន់តែមិនសូវពាក់ព័ន្ធ។ ម៉ូឌុល `progressiveAging.ts`** បង្ខូចសារដោយចម្ងាយវេន** (ចម្ងាយវាស់ពីចុងបញ្ចប់នៃការសន្ទនា) ។ ជាមួយនឹងលំនាំដើមដែលបានដឹកជញ្ជូន (`verbatim: 2, light: 2, moderate: 3`):

- **2 វេនចុងក្រោយ (ចម្ងាយ ≤ 2)** ៖ រក្សាពាក្យសំដី
- **ចម្ងាយ ៣** : ការបង្ហាប់ Caveman (ការដកយក Filler)
- **ចម្ងាយ 4 +** ៖ សារជំនួយការសង្ខេប; សាររបស់អ្នកប្រើត្រូវបានកាត់បន្ថយទៅជួរទីមួយរបស់ពួកគេ ដែលដាក់នៅ 120 តួអក្សរ។ តួនាទីផ្សេងទៀតដែលមិនប៉ះពាល់។ ការជម្រុញប្រព័ន្ធ សារដែលមានវ័យចំណាស់រួចហើយ និងសារអ្នកប្រើប្រាស់ចុងក្រោយបំផុត តែងតែរក្សាពាក្យសំដីដោយមិនគិតពីចម្ងាយ។ គ្មានអ្វីត្រូវបានទម្លាក់ចេញទេ ហើយក្រុម `light` គឺមិនអាចទៅដល់បានជាមួយនឹងលំនាំដើមដែលបានបញ្ជូនចេញ (`light` ស្មើ `verbatim`) ។

#### ឧទាហរណ៍កូដ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### ពេលណាត្រូវប្រើ

ការវិវត្តនៃភាពចាស់គឺ** ជានិច្ច** សម្រាប់ `aggressive` mode — វាគឺជាជំហានទី 2 នៃ `compressAggressive()`។ មុខងារជ្រុលមិនដំណើរការទេ។ វាមានប្រសិទ្ធភាពជាពិសេសសម្រាប់៖

- វគ្គសរសេរកូដរយៈពេលវែង
- ការសន្ទនាច្រើនថ្ងៃ
- លំហូរការងាររបស់ភ្នាក់ងារជាមួយនឹងការហៅឧបករណ៍ជាច្រើន។

### របៀបបញ្ចេញ Caveman

បន្ថែមរបៀបទិន្នផល Caveman** ការណែនាំអំពីប្រព័ន្ធ** ដែលសួរគំរូខ្លួនវាសម្រាប់ទិន្នផល terse — កម្រិត `lite` សុំចម្លើយសង្ខេបដែលរក្សាប្រយោគពេញលេញ `full` សួរវាឱ្យ "ឆ្លើយតប terse ដូចជាអ្នករូងភ្នំឆ្លាត" ហើយ `ultra` ស្នើសុំលទ្ធផលតេឡេក្រាម។ ការណែនាំគ្រាន់តែសួរពួកគេមិនអាចធានាបានទេ។ សំណើទទួលបានពួកគេតាមរយៈ `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`): `open-sse/handlers/chatCore.ts` ដំបូងដោះស្រាយការជ្រើសរើសដោយប្រើ back-compat shim (`resolveOutputStyleSelection()` in `open-sse/services/compression/outputStyles/backCompat.ts`) ដែលខណៈពេលដែល `outputStyles` គឺទទេ ផែនទី `cavemanOutputMode` ដែលបានបើកទៅរចនាប័ទ្មលទ្ធផល `terse-prose` នៅ `cavemanOutputMode.intensity` (សូមមើល Back-compat ខាងក្រោម); ការជ្រើសរើស `outputStyles` ដែលមិនទទេរត្រូវបានប្រើជាគឺ ហើយ `cavemanOutputMode.enabled` និង `intensity` បន្ទាប់មកគ្មានប្រសិទ្ធភាពទេ ខណៈដែលការបិទបើក `autoClarity` របស់វានៅតែអនុវត្ត។ `outputMode.ts` កាន់អត្ថបទណែនាំ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`) មាតិកាផ្លូវវាង និងកន្លែងជំនួយដែលចាក់ប្រើ។ ម៉ាស៊ីនចាក់ `applyCavemanOutputMode()` ផ្ទាល់របស់វាមិនមានអ្នកហៅផលិតកម្មទេ។

#### របៀបដែលវាដំណើរការ

របៀបនេះមិនបង្ហាប់ការបញ្ចូលទេ។ វាបន្ថែមប្លុកការណែនាំទៅប្រអប់បញ្ចូលប្រព័ន្ធ (សូមមើលរបៀបដែលការចាក់ដំណើរការខាងក្រោម) ហើយរបៀបបង្ហាប់បញ្ចូលណាមួយដែលបានជ្រើសរើសសម្រាប់សំណើនៅតែដំណើរការបន្ទាប់ពីនោះនៅលើតួដែលឥឡូវនេះផ្ទុកប្លុក។ មុនពេលឃ្លាព្រំដែនរួមដែលគ្រប់កម្រិតបញ្ចប់ដោយ កម្រិត `full` ភាសាអង់គ្លេសអានថា:

> "ឆ្លើយតបពាក្យពេចន៍ដូចជាមនុស្សល្អាងឆ្លាត។ ទម្លាក់អត្ថបទ (a/an/the) ធាតុបំពេញ (just/really/basically/actually/simply) ភាពរីករាយ ការទប់ស្កាត់។ បំណែក OK។ សទិសន័យខ្លីៗ (ធំមិនទូលំទូលាយ ជួសជុលមិនអនុវត្ត។ រក្សាសារធាតុបច្ចេកទេស កូដ កំហុស URLs ការកំណត់អត្តសញ្ញាណទាំងអស់។"

វាដំណើរការល្អជាពិសេសសម្រាប់៖

- ការបង្កើតកូដ (លទ្ធផល terser = ថូខឹនតិចជាងមុន)
- សំណួរ និងចម្លើយរហ័ស (មិនត្រូវការការពន្យល់លម្អិត)
- ដំណើរការបណ្តុំ (បង្កើនទិន្នផល)

#### ពេលណាត្រូវប្រើ

របៀបទិន្នផល Caveman គឺ** ជ្រើសរើសចូល** . ជាមួយនឹងការបង្ហាប់នៅលើ (`enabled: true` មេបិទបើកនៅលើទំព័រការកំណត់ការបង្ហាប់) បើកវាជាមួយ `cavemanOutputMode.enabled`; `intensity` ជ្រើសរើស `lite`, `full` ឬ `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

បន្សំនៃការបង្ហាប់** របៀបបញ្ចេញ** បិទ/បើក (`outputMode` កម្រិតក្នុង `outputModeIntensity`) កំណត់ការប្ដូរដូចគ្នាសម្រាប់សំណើដែលបន្សំអនុវត្ត ហើយឧបករណ៍ `omniroute_set_compression_engine` MCP សរសេរវាតាមរយៈអាគុយម៉ង់ `outputMode` ប៊ូលីនរបស់វា។ ការជ្រើសរើស `outputStyles` ដែលមិនទទេមានអាទិភាពលើកុងតាក់នេះ។ នៅក្នុងផ្ទាំងគ្រប់គ្រងការបើកដំណើរការ** សូរសព្ទ Terse** រចនាប័ទ្មលទ្ធផល ចាក់ប្លុកដូចគ្នា (សូមមើលរចនាប័ទ្មលទ្ធផលខាងក្រោម)។

#### របៀបដែលការចាក់ថ្នាំដំណើរការ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ដោះស្រាយការជ្រើសរើសទល់នឹងកាតាឡុក (លេខសម្គាល់ដែលមិនស្គាល់ និងរចនាប័ទ្មមិនត្រូវគ្នានឹងមូលដ្ឋានត្រូវបានទម្លាក់ មិនដែលមានបញ្ហាទេ ការជ្រើសរើសដែលដោះស្រាយដោយគ្មានរចនាប័ទ្មទុកតួមិនផ្លាស់ប្តូរ រំលងជា `no_styles`) ភ្ជាប់ការណែនាំដែលបានជ្រើសរើសក្នុងលំដាប់កាតាឡុក បន្ថែមឃ្លាព្រំដែន** ម្តង** (បូកនឹងឃ្លាសុវត្ថិភាព `SAFETY_BOUNDARIES` ឬការបកប្រែរបស់វា នៅពេលដែល `less-code` ឬ `ponytail` ត្រូវបានជ្រើសរើស) ហើយចាប់ផ្តើមប្លុកជាមួយនឹងសញ្ញាសម្គាល់ ideempotency តែមួយ (`[OmniRoute Output Styles]`) ដូច្នេះការដាក់ពាក្យម្តងទៀតគឺគ្មានជម្រើសទេ។ នៅពេលដែលភាសាដែលបានដោះស្រាយ (សូមមើលការជ្រើសរើសភាសាខាងក្រោម) មានការបកប្រែ ការណែនាំដែលបានធ្វើមូលដ្ឋានីយកម្មត្រូវបានចាក់ជំនួសឱ្យភាសាអង់គ្លេស។

នៅលើតួដែលមានអារេ `messages` ដែលមិនទទេ ការត្រួតពិនិត្យ ideempotency ដំណើរការមុននឹងការរំលងមាតិកា៖ នៅពេលដែលសញ្ញាសម្គាល់ `[OmniRoute Output Styles]` មាននៅក្នុងវាល `system` កម្រិតកំពូលរួចហើយ (ខ្សែអក្សរ ឬអារេប្លុកមាតិកា) ឬនៅក្នុងសារប្រព័ន្ធដែលមានខ្លឹមសារខ្សែអក្សរ តួមិនត្រូវបានផ្លាស់ប្តូរជា `already_applied` ហើយគ្មានការត្រួតពិនិត្យពាក្យគន្លឹះដំណើរការទេ។ បើមិនដូច្នេះទេ មាតិការំលង (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) ពិនិត្យអត្ថបទនៃសារបីចុងក្រោយ ទោះជាតួនាទីរបស់ពួកគេបែបណាក៏ដោយ ហើយរំលងរចនាប័ទ្មសម្រាប់វេនទាំងមូល នៅពេលដែលអត្ថបទនោះត្រូវគ្នានឹងពាក្យគន្លឹះសុវត្ថិភាព សកម្មភាពដែលមិនអាចត្រឡប់វិញបាន ឬការបំភ្លឺ ឬលំដាប់ដែលប្រកាន់អក្សរតូចធំ៖ `first`, `then`, `after that`, `before` `migrate`, `rollback` `delete`, `drop`, `deploy` ឬ `backup` `release` ផ្លូវវាងដំណើរការខណៈពេលដែល** ការឆ្លងកាត់ភាពច្បាស់លាស់ដោយស្វ័យប្រវត្តិ** បិទ/បើក (`cavemanOutputMode.autoClarity`, តាមលំនាំដើម) បើក។ ការបិទបើក រំលងការត្រួតពិនិត្យពាក្យគន្លឹះ។

នៅពេលដែលផ្លូវវាងអនុញ្ញាតឱ្យវេនឆ្លងកាត់ `placeSystemInstruction()` (ឯកសារដូចគ្នា) ដែលមិនដែលបង្កើត `messages[0]` ថ្មីដាក់ប្លុកនៅក្នុងទីមួយដែលវារកឃើញ:

1. សារប្រព័ន្ធឈានមុខគេដែលមានខ្លឹមសារខ្សែអក្សរ៖ ប្លុកត្រូវបានបន្ថែមបន្ទាប់ពីអត្ថបទរបស់វា។
2. វាល `system` កម្រិតកំពូល៖ ប្លុកត្រូវបានបន្ថែមបន្ទាប់ពីអត្ថបទនៃខ្សែអក្សរ ឬបន្ថែមជាប្លុកអត្ថបទថ្មីទៅអារេប្លុកមាតិកា។
3. សារប្រព័ន្ធនៅពេលក្រោយដំបូងដែលមានខ្លឹមសារខ្សែអក្សរ៖ ប្លុកត្រូវបានបន្ថែមបន្ទាប់ពីអត្ថបទរបស់វា។

3. **`shellOutput`**: output that contains an ANSI CSI sequence (`ESC[` then digits or semicolons then a letter, as in color codes) or a `$` followed by whitespace anywhere in the text loses those sequences (other escapes, such as `ESC[?25l` or an OSC window-title sequence, are kept) and keeps its last 50 lines, with consecutive repeated lines collapsed. Because this check runs before `json` and `errorMessage`, JSON or error output that contains such a `$` never reaches them while `shellOutput` is on.
4. **`json`** ៖ JSON payload ជាង 2,000 តួអក្សរដែលចាប់ផ្តើមដោយ `{` ឬ `[` (បន្ទាប់ពីដកឃ្លាជាជម្រើស) ហើយការញែកត្រូវបានសង្ខេប៖ អារេនៃធាតុច្រើនជាង 7 រក្សាធាតុ 5 ដំបូង និង 2 ចុងក្រោយរបស់វា និងចំនួនសរុបរបស់វា ហើយវត្ថុមួយរក្សាកូនសោ 20 ដំបូងរបស់វា ដោយវត្ថុដាក់គ្នា ឬអារេនីមួយៗត្រូវបានជំនួសដោយតម្លៃ `{…N keys}` របស់វា length) និងសញ្ញាសម្គាល់ `_remaining_<N>_keys` រាប់គ្រាប់ចុចដែលបានទម្លាក់ពីលើ 20 ដំបូង។ តម្លៃមាត្រដ្ឋានត្រូវបានចម្លងទាំងស្រុង ដូច្នេះវត្ថុដែលមាន 20 គ្រាប់ចុច ឬតិចជាងនេះដោយគ្មានតម្លៃដាក់គឺគ្រាន់តែចូលបន្ទាត់ឡើងវិញ — មួយដែលបានបង្រួមតូចនឹងទទួលបានតួអក្សរ ហើយនៅតែមិនផ្លាស់ប្តូរ។
5. **`errorMessage`** ៖ លទ្ធផលដែលមាននៅគ្រប់ទីកន្លែង និងក្នុងអក្សរណាមួយ `error:`, `error ` (ពាក្យដែលបន្តដោយដកឃ្លា ដូចក្នុង `no error found`) `[error]`, `exception:`, `exception `, `[exception]` ឬ `traceback` រក្សាបន្ទាត់ទីមួយរបស់វា 10 ជួរបន្ទាប់ និង 3 ចុងក្រោយដោយមានសញ្ញាសម្គាល់ `… [N frames elided] …` ជំនួសបន្ទាត់រវាងពួកវា។ សញ្ញាសម្គាល់លេចឡើងតែនៅពេលដែលច្រើនជាង 13 បន្ទាត់ដើរតាមបន្ទាត់ទីមួយ ដូច្នេះលទ្ធផលកំហុសនៃ 14 បន្ទាត់ ឬតិចជាងនេះមិនត្រូវបានកាត់បន្ថយទេ (នៅ 12 ឬ 13 បន្ទាត់ បន្ទាត់ចុងក្រោយ 3 ដដែលបានរក្សាទុករួចហើយ)។

បន្ទាប់ពីការផ្គូផ្គងយុទ្ធសាស្រ្ត សូម្បីតែមួយដែលមិនរក្សាទុកអ្វីក៏ដោយ យុទ្ធសាស្ត្រក្រោយៗទៀតមិនត្រូវបានសាកល្បងទេ។ នៅពេលដែលយុទ្ធសាស្រ្តផ្គូផ្គងមិនរក្សាទុកថូខឹនប៉ាន់ស្មាន (ប្រវែង ÷ 4 បង្គត់ឡើង) — ឧទាហរណ៍ ឯកសារដូចកូដដែលមាន 25 បន្ទាត់ ឬតិចជាងនេះ ឬអារេ JSON លើសពី 2,000 តួអក្សរដែលមាន 7 ធាតុ ឬ — តិចជាងនេះ ម៉ាស៊ីនឈ្លានពានរក្សាលទ្ធផលឧបករណ៍ដើម៖ ទាំងអ្នកហៅចូល (`compressAggressive()` និង `saved` នៅខាងក្រោម ឬ `compressAnthropicToolResultBlock()`) ត្រឡប់លទ្ធផលនៃ `compressToolResult()` នោះ។ ជំហានលទ្ធផលឧបករណ៍មិនមែនជាពាក្យចុងក្រោយទេ៖ ការសង្ខេបការត្រលប់ថយក្រោយរបស់ម៉ាស៊ីននៅតែអាចកាត់បន្ថយសារ `tool` ឬ `function` ឱ្យវែងជាង 8,192 តួអក្សរ (`maxTokensPerMessage`, 2,048, គុណ 4)។

#### ពេលណាត្រូវប្រើ

ការបង្ហាប់លទ្ធផលឧបករណ៍គឺជាជំហានទី 1 នៃម៉ាស៊ីនឈ្លានពាន (`compressAggressive()` ក្នុង `open-sse/services/compression/aggressive.ts`) ដូច្នេះវាដំណើរការក្នុងរបៀបឈ្លានពាន និងក្នុងជំហាន `aggressive` នៃបំពង់បង្ហូរជង់។ វាបង្រួមសារ OpenAI-shape `tool` និង `function` និងអត្ថបទនៅខាងក្នុងប្លុក Anthropic `tool_result` ។ យុទ្ធសាស្ត្រនីមួយៗមានកុងតាក់ផ្ទាល់ខ្លួននៅក្រោម `aggressive.toolStrategies` ទាំងអស់ដំណើរការតាមលំនាំដើម។ នៅក្នុងផ្ទាំងគ្រប់គ្រង ឧបករណ៍ប្តូរស្ថិតនៅក្នុងទំព័រ Caveman** កម្រិតខ្ពស់** មើលខណៈពេលដែលការបង្ហាប់បើក ហើយរបៀបលំនាំដើមគឺឈ្លានពាន។

### បំពង់ជង់

របៀបជង់ដំណើរការ** ម៉ាស៊ីនច្រើនតាមលំដាប់លំដោយ** — ជាធម្មតា RTK ដំបូង (60-90% ការសន្សំលើទិន្នផលឧបករណ៍) បន្ទាប់មក Caveman នៅលើអត្ថបទដែលនៅសល់ (~ 46% ការសន្សំបញ្ចូល) ។ សមាសភាព, នោះគឺជា** ជួរដែលមានសិទ្ធិ 78-95%** (សូមមើល Upstream Savings Math ខាងលើ)៖ `1 - (1 - 0.60..0.90) × (1 - 0.46)` ជាមធ្យម ≈ 89%។

#### របៀបដែលវាដំណើរការ

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### ពេលណាត្រូវប្រើ

ប្រើរបៀបជង់សម្រាប់៖

- ដំណើរការការងារធ្ងន់របស់ឧបករណ៍ (ការសរសេរកូដភ្នាក់ងារ ការស្រាវជ្រាវ)
- ដំណើរការបាច់ដែលងាយនឹងចំណាយ
- នៅពេលដែលអ្នកត្រូវការការសន្សំសញ្ញាសម្ងាត់អតិបរមា

បំពង់បង្ហូរជង់ត្រូវបានកំណត់រចនាសម្ព័ន្ធតាមរយៈការកំណត់ការបង្ហាប់ `stackedPipeline` សកល ឬតាមរយៈបន្សំការបង្ហាប់ដែលមានឈ្មោះដែលបានកំណត់ទៅបន្សំផ្លូវ (សូមមើល Per-Combo Override ខាងលើ) — មិនមែនតាមរយៈបន្សំស្វ័យប្រវត្តិ `modePack` (វាលនោះគ្រាន់តែថ្លឹងទម្ងន់ឡើងវិញនូវការជ្រើសរើសគំរូបន្សំស្វ័យប្រវត្តិ ហើយ `stacked` មិនមែនជាឈ្មោះកញ្ចប់ត្រឹមត្រូវទេ)។

## ការកំណត់ជាន់លើនៃការបង្ហាប់តាម Combo

អ្នកអាចកំណត់ជាន់លើរបៀបបង្ហាប់សកល **សម្រាប់ combo នីមួយៗ** ដើម្បីកែសម្រួលឥរិយាបថឱ្យសមស្រប
សម្រាប់ករណីប្រើប្រាស់ផ្សេងៗ៖

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

វាមានប្រយោជន៍សម្រាប់៖

- **Combo សរសេរកូដ**៖ ប្រើរបៀប `aggressive` សម្រាប់សម័យការងារយូរ
- **Combo សំណួរ និងចម្លើយរហ័ស**៖ ប្រើរបៀប `lite` សម្រាប់ការឆ្លើយតបរហ័ស
- **Combo ដែលប្រើឧបករណ៍ច្រើន**៖ ប្រើរបៀប `stacked` ដើម្បីសន្សំបានអតិបរមា
- **Combo សម្រាប់បរិស្ថានផលិតកម្ម**៖ កុំបើកការកំណត់ជាន់លើសម្រាប់អ្នកផ្តល់សេវាដែលប្រើឃ្លាំងសម្ងាត់ — ការកែសម្រួល
  ដែលគិតគូរពីឃ្លាំងសម្ងាត់ និងបើកជានិច្ច នឹងបន្ថយកម្រិត `aggressive`/`ultra` ទៅជា `standard` ដោយស្វ័យប្រវត្តិ
  (មិនមានរបៀប `cache-aware` ដែលអាចជ្រើសរើសបានទេ)
