## 1. របៀបដែលវាដំណើរការ

```
ម៉ាស៊ីនមេ (ឌិគ្រីប + ផ្ទៀងផ្ទាត់ការកំណត់រចនាសម្ព័ន្ធ, សម្របសម្រួល cursor)
  → ចាប់ផ្ដើម IPC → ដំណើរការ OS exportChild ដាច់ដោយឡែក
    → storage.sqlite សម្រាប់តែអាន → សំណួរ/ការផ្គូផ្គងកំណត់ហេតុការហៅរួម
      → ផ្ទុក artifact តាមអសមកាល → prepare()/send() របស់ទិសដៅ
        → IPC ជាបាច់ → ម៉ាស៊ីនមេរក្សាទុក cursor → IPC ack
          → បាច់បន្ទាប់; IPC done → ម៉ាស៊ីនមេកត់ត្រាជោគជ័យ
```

- **កាលវិភាគ** — ការងារ cron មួយរបស់ `JobRegistry` ឈ្មោះ `log_export` ដែលមានលំនាំដើមជា `0 * * * *` (រៀងរាល់ម៉ោង
  តាម UTC)។ វាត្រូវបានចុះឈ្មោះក្នុង `src/lib/initCloudSync.ts`; អាចកំណត់ជំនួសដោយ `OMNIROUTE_LOG_EXPORT_CRON`។
  នៅរាល់ tick វាបញ្ជូនទិន្នន័យដែលរង់ចាំទៅគ្រប់ទិសដៅដែល**បានបើក** តាមលំដាប់ម្តងមួយៗ។
- **Cursor** — `call_logs.rowid` អាំងភ្លីស៊ីតរបស់ SQLite ដែលត្រូវបានរក្សាទុកដោយឡែកសម្រាប់ទិសដៅនីមួយៗក្នុង
  `log_export_destinations.cursor_row_id`។ `timestamp` ត្រូវបានជ្រើសរើសដោយចេតនាមិនឱ្យធ្វើជា cursor ទេ៖ អ្នកហៅ
  អាចផ្ដល់តម្លៃផ្ទាល់ខ្លួន ដូច្នេះសំណើយឺតមួយអាចត្រូវបានសរសេរបន្ទាប់ពីសំណើលឿនជាងដែលបានចាប់ផ្ដើម
  នៅពេលក្រោយ ហើយ cursor ដែលផ្អែកលើ timestamp នឹងរំលងវា។
- **ការបែងចែកជាបាច់** — `batch_size` ជួរដេកក្នុងមួយសំណើ (លំនាំដើម 500), `max_rows_per_run` ជួរដេកក្នុងមួយដំណើរការ
  (លំនាំដើម 10000) ដើម្បីឱ្យទិន្នន័យកកស្ទះច្រើនត្រូវបានបញ្ជូនអស់ក្នុងរយៈពេល tick ជាច្រើន ជំនួសឱ្យការរារាំងក្នុង tick តែមួយ។
- **ការបញ្ជូន** — cursor ទៅមុខតែបន្ទាប់ពី `send()` បញ្ចប់ដោយជោគជ័យ។ បាច់ដែលបរាជ័យទុកឱ្យ
  cursor នៅទីតាំងដដែល ដូច្នេះជួរដេកដដែលត្រូវបានព្យាយាមម្ដងទៀតក្នុងការដំណើរការបន្ទាប់។ ការធានាគឺ
  យ៉ាងហោចណាស់ម្តង រួមជាមួយការលុបទិន្នន័យស្ទួននៅខាងទិសដៅ មិនមែនពិតប្រាកដម្តងគត់នោះទេ៖ BigQuery កំណត់សោឱ្យជួរដេកនីមួយៗ
  តាម id របស់កំណត់ហេតុការហៅ ដែលវាគោរពតាមមូលដ្ឋានខិតខំប្រឹងប្រែងអស់ពីសមត្ថភាពក្នុងចន្លោះពេលលុបទិន្នន័យស្ទួនរបស់វា។
- **ការការពារការត្រួតស៊ីគ្នា** — tick របស់ cron និង `POST .../run` អាចដំណើរការក្នុងពេលតែមួយ។ ទិសដៅដែល
  កំពុងបញ្ជូនទិន្នន័យរួចហើយត្រូវបានរំលង ជំនួសឱ្យការបញ្ជូនពីរដង (`skipped: true` ក្នុងលទ្ធផលដំណើរការ)
  ដូច្នេះការដំណើរការស្របគ្នាមិនអាចផ្ញើបាច់ម្ដងទៀត ឬសរសេរ cursor ថយក្រោយបានទេ។
- **ការស្ដារឡើងវិញបន្ទាប់ពីការសម្អាត** — ប្រសិនបើ `cursor_row_id` ស្ថិតលើស `MAX(rowid)` (តារាងទាំងមូលត្រូវបាន
  សម្អាត ហើយ rowid បានចាប់ផ្ដើមឡើងវិញ) កម្មវិធីដំណើរការនឹងបង្វិលត្រឡប់ទៅ 0 ជំនួសឱ្យលែងឃើញទិន្នន័យជាអចិន្ត្រៃយ៍។

### កម្មវិធីដំណើរការដាច់ដោយឡែក និងដែនកំណត់

ការដំណើរការទិសដៅនីមួយៗលើ Node ចាប់ផ្ដើមដំណើរការ OS កូនដាច់ដោយឡែកដែលមានអាយុកាលខ្លី (`child_process`
ជាមួយ IPC មិនមែន `worker_threads`)។ ការអាន body, ការញែក/បម្លែង payload JSON ជាស៊េរី, `prepare()`

មានតែការកំណត់រចនាសម្ព័ន្ធ និងសារវឌ្ឍនភាពតូចៗប៉ុណ្ណោះដែលឆ្លងកាត់ IPC; កំណត់ត្រាដែលបាននាំចេញមិនត្រឡប់ទៅ
ម៉ាស៊ីនមេឡើយ។ ការងារ cron និង route ដំណើរការភ្លាមៗរក្សាលទ្ធផលសាធារណៈ និងការការពារការត្រួតស៊ីគ្នាដដែល។

3. សរសេរ test នៅក្រោម `tests/unit/`។

នោះគឺជាការផ្លាស់ប្តូរទាំងមូល៖ ការរក្សាទុកទិន្នន័យ, cron job, ស្រទាប់ REST, ការអ៊ិនគ្រីបព័ត៌មានសម្ងាត់ និង
សំណុំបែបបទ dashboard សុទ្ធតែអាន registry។

ច្បាប់ពីរសម្រាប់គោលដៅថ្មី៖

- `send()` **ត្រូវតែ throw** នៅពេលមានការបរាជ័យមួយផ្នែក។ ការដោះស្រាយបានជោគជ័យមានន័យថា «គោលដៅមានជួរដេកទាំងនេះ» ហើយ
  cursor នឹងផ្លាស់ទីរំលងពួកវាជាអចិន្ត្រៃយ៍។
- គោលដៅដែលទទួល URL ផ្តល់ដោយអ្នកប្រើ ត្រូវតែ validate វាតាមរយៈ
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) មុនពេល fetch
  ដូចគ្នានឹងរបៀបដែល webhook ធ្វើ។ BigQuery មិនត្រូវការវាទេ៖ host របស់វាជាតម្លៃថេរ។

## 7. ការដំណើរការវា

- **Dashboard**៖ Integrations → Log export។ បន្ថែមគោលដៅមួយ ដំណើរការ **Test** ដើម្បីពិនិត្យព័ត៌មានសម្គាល់អត្តសញ្ញាណ
  ដោយមិនសរសេរជួរដេក បន្ទាប់មកបើកដំណើរការវា។
- **Backlog**៖ កាតគោលដៅនីមួយៗបង្ហាញជួរដេកដែលកំពុងរង់ចាំ និង cursor; `GET
/api/log-export/status` ត្រឡប់តួលេខដូចគ្នា រួមទាំងការដំណើរការ job 20 លើកចុងក្រោយ។
- **គោលដៅដែលបរាជ័យមួយមិនធ្វើឱ្យគោលដៅផ្សេងទៀតបរាជ័យទេ** — សេចក្តីសង្ខេបនៃការដំណើរការកត់ត្រា status តាមគោលដៅ
  នៅក្នុង `last_status` / `last_error` ហើយប្រវត្តិការដំណើរការ job រក្សាទុកលទ្ធផលសរុប។
- **ការលុបគោលដៅមួយ នឹងលុប cursor របស់វា។** ការបន្ថែមវាឡើងវិញនឹងចាប់ផ្តើមពី call log ដែលបានរក្សាទុកចាស់បំផុត
  ដែលនឹងផ្ញើជួរដេកឡើងវិញ ទោះបីជាគោលដៅអាចមានពួកវារួចហើយក៏ដោយ។ នៅលើ BigQuery `insertId` សម្រាប់ជួរដេកនីមួយៗ
  អាចដោះស្រាយករណីនោះបានតែក្នុង de-duplication window ផ្ទាល់របស់ BigQuery ប៉ុណ្ណោះ ដូច្នេះគួរជ្រើសរើសបិទដំណើរការ
  គោលដៅ ជាជាងលុបវា។
