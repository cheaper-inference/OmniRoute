ការនាំចេញកំណត់ហេតុការហៅ OmniRoute ជាបន្តបន្ទាប់ និងតាមការកើនឡើង ទៅកាន់ឃ្លាំងវិភាគខាងក្រៅ។

ផ្ទាំង Logs នៅក្នុងផ្ទាំងគ្រប់គ្រងរក្សាទុកប្រវត្តិសំណើក្នុង SQLite (`call_logs`) ដែលត្រូវបានកំណត់ដោយ
ការបង្វិល និងរយៈពេលរក្សាទុក។ ការនាំចេញកំណត់ហេតុបញ្ជូនសំណុំកំណត់ត្រាដូចគ្នានេះចេញតាមកាលវិភាគ ដើម្បីឱ្យវាអាចរក្សាទុកបានយូរជាង
មូលដ្ឋានទិន្នន័យមូលដ្ឋាន និងអាចភ្ជាប់ជាមួយទិន្នន័យផ្សេងទៀត។ BigQuery គឺជាគោលដៅដំបូង;
បំពង់ដំណើរការនេះប្រើបញ្ជីចុះឈ្មោះ ដូច្នេះអាចបន្ថែមគោលដៅផ្សេងទៀតបាន។

## 1. របៀបដំណើរការ

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **កាលវិភាគ** — ការងារ cron មួយរបស់ `JobRegistry` ឈ្មោះ `log_export` ដែលមានតម្លៃលំនាំដើម `0 * * * *` (រៀងរាល់ម៉ោង,
  UTC)។ វាត្រូវបានចុះឈ្មោះនៅក្នុង `src/lib/initCloudSync.ts`; អាចកំណត់ជំនួសដោយ `OMNIROUTE_LOG_EXPORT_CRON`។
  រាល់ពេលកាលវិភាគដំណើរការ វានាំចេញទិន្នន័យពីគោលដៅទាំងអស់ដែលបាន **បើកដំណើរការ** តាមលំដាប់លំដោយ។
- **ទស្សន៍ទ្រនិច** — `call_logs.rowid` លាក់របស់ SQLite ដែលត្រូវបានរក្សាទុកសម្រាប់គោលដៅនីមួយៗក្នុង
  `log_export_destinations.cursor_row_id`។ `timestamp` ត្រូវបានចេតនាមិនប្រើជាទស្សន៍ទ្រនិច៖ អ្នកហៅ
  អាចផ្តល់តម្លៃផ្ទាល់ខ្លួន ដូច្នេះសំណើយឺតអាចត្រូវបានសរសេរបន្ទាប់ពីសំណើលឿនជាងដែលបានចាប់ផ្តើម
  នៅពេលក្រោយ ហើយទស្សន៍ទ្រនិចតាមត្រាពេលវេលានឹងរំលងវា។
- **ការបែងចែកជាបាច់** — `batch_size` ជួរដេកក្នុងមួយសំណើ (លំនាំដើម 500), `max_rows_per_run` ជួរដេកក្នុងមួយលើកដំណើរការ
  (លំនាំដើម 10000) ដូច្នេះទិន្នន័យរង់ចាំច្រើនត្រូវបាននាំចេញក្នុងការដំណើរការតាមកាលវិភាគជាច្រើនលើក ជំនួសឱ្យការរាំងស្ទះមួយលើក។
- **ការបញ្ជូន** — ទស្សន៍ទ្រនិចទៅមុខតែបន្ទាប់ពី `send()` បញ្ចប់ដោយជោគជ័យ។ បាច់ដែលបរាជ័យទុក
  ទស្សន៍ទ្រនិចនៅទីតាំងដដែល ដូច្នេះជួរដេកដដែលនឹងត្រូវបានសាកល្បងឡើងវិញនៅលើកបន្ទាប់។ ការធានាគឺ
  យ៉ាងហោចណាស់មួយដង រួមជាមួយការលុបទិន្នន័យស្ទួននៅខាងគោលដៅ មិនមែនម្តងគត់យ៉ាងពិតប្រាកដទេ៖ BigQuery កំណត់សោឱ្យជួរដេកនីមួយៗ
  តាមលេខសម្គាល់កំណត់ហេតុការហៅ ដែលវាគោរពតាមលទ្ធភាពអតិបរមាក្នុងចន្លោះពេលលុបទិន្នន័យស្ទួនរបស់វា។
- **ការការពារការដំណើរការត្រួតគ្នា** — ការដំណើរការតាម cron និង `POST .../run` អាចកើតឡើងក្នុងពេលតែមួយ។ គោលដៅដែល
  កំពុងនាំចេញរួចហើយនឹងត្រូវបានរំលង ជំនួសឱ្យការនាំចេញពីរដង (`skipped: true` ក្នុងលទ្ធផលដំណើរការ),
  ដូច្នេះការដំណើរការស្របពេលគ្នាមិនអាចបញ្ជូនបាច់ឡើងវិញ ឬសរសេរទស្សន៍ទ្រនិចថយក្រោយបានទេ។
- **ការស្ដារឡើងវិញក្រោយការលុបសម្អាត** — ប្រសិនបើ `cursor_row_id` មានតម្លៃខ្ពស់ជាង `MAX(rowid)` (តារាងទាំងមូលត្រូវបាន
  លុបសម្អាត ហើយ rowid ចាប់ផ្តើមឡើងវិញ) កម្មវិធីដំណើរការនឹងថយទៅ 0 ជំនួសឱ្យការមិនអាចមើលឃើញទិន្នន័យជាអចិន្ត្រៃយ៍។

### កម្មវិធីដំណើរការដាច់ដោយឡែក និងដែនកំណត់

ការដំណើរការគោលដៅនីមួយៗនៅលើ Node ចាប់ផ្តើមដំណើរការកូនរបស់ប្រព័ន្ធប្រតិបត្តិការដាច់ដោយឡែក ដែលមានអាយុកាលខ្លី (`child_process`
ជាមួយ IPC មិនមែន `worker_threads` ទេ)។ ការអានតួទិន្នន័យ ការញែក/បម្លែង JSON របស់ទិន្នន័យបញ្ជូន,
`prepare()` របស់គោលដៅ និង I/O បណ្ដាញរបស់គោលដៅ សុទ្ធតែដំណើរការនៅទីនោះ មិនមែននៅលើរង្វិលជុំព្រឹត្តិការណ៍របស់ម៉ាស៊ីនមេទេ។
មានតែការកំណត់រចនាសម្ព័ន្ធ និងសារវឌ្ឍនភាពតូចៗប៉ុណ្ណោះដែលឆ្លងកាត់ IPC; កំណត់ត្រាដែលបាននាំចេញមិនត្រឡប់ទៅ
ម៉ាស៊ីនមេវិញឡើយ។ ការងារ cron និងផ្លូវ Run now រក្សាលទ្ធផលសាធារណៈ និងការការពារការដំណើរការត្រួតគ្នាដដែល។

ដំណើរការកូនបើក `DATA_DIR/storage.sqlite` ដែលម៉ាស៊ីនមេបានកំណត់ទីតាំងរួច ក្នុងរបៀបអានតែប៉ុណ្ណោះ ដោយប្រើ `node:sqlite`,
ជាមួយ `busy_timeout=5000` និង `query_only=ON`។ វាមិននាំចូល singleton របស់មូលដ្ឋានទិន្នន័យទេ ហើយមិនធ្វើ
ការផ្លាស់ប្ដូររចនាសម្ព័ន្ធ ការបម្រុងទុក ឬការធ្វើបច្ចុប្បន្នភាព SQLite ឡើយ។ ការគ្រប់គ្រងកំណត់ត្រាឯកសារធាតុដែលបាត់/ខូច (រួមទាំង
UPDATE សម្រាប់ឯកសារធាតុខូច) នៅតែមានតែក្នុងផ្លូវព័ត៌មានលម្អិតរបស់ផ្ទាំងគ្រប់គ្រងប៉ុណ្ណោះ។ ផ្លូវទាំងពីរប្រើមុខងារដោះស្រាយ
ព័ត៌មានលម្អិតសុទ្ធរួមគ្នា; ការនាំចេញប្រើការអានប្រព័ន្ធឯកសារបែបអសមកាល និងលំដាប់ដោះស្រាយដូចគ្នា គឺឯកសារធាតុ → ទិន្នន័យបង្កប់
បែបចាស់ → ឌីសបែបចាស់ → គ្មាន។ ការដំណើរការមួយថតទុក rowid បញ្ចូលអតិបរមា

`gen_ai.input.messages` / `gen_ai.output.messages` ផ្ទុក JSON នៃ request/response body ដែលបានសម្អាត ដូចដែលបានរក្សាទុកដោយ OmniRoute (ត្រូវបានធ្វើ canonicalize នៅពេលអាច parse បាន) មិនមែនជា messages array តាម semconv ដែលបានរៀបចំរូបរាងថ្មីទេ។ Bodies ដែលត្រូវបានកាត់ ឬមិនមែនជា JSON នៅតែជាអត្ថបទដើម។ នៅពេល `langfuseMapping=true`,
bodies ត្រូវបានបញ្ចេញតែជា `langfuse.observation.input` / `langfuse.observation.output` ប៉ុណ្ណោះ;
គុណលក្ខណៈ `gen_ai.*.messages` ត្រូវបានលុបចោល ដើម្បីឱ្យ body នីមួយៗត្រូវបានផ្ញើតែម្តង។ របៀបទាំងពីរទទួល `maxBodyBytes` ពី hydration path ដែលមានស្រាប់;
`omniroute.bodies_truncated=true` សម្គាល់ការកាត់ត។ មិនមាន pipeline snapshots បន្ថែម ឬការអាន artifacts ដែលមិនបានសម្អាត ត្រូវបានបន្ថែមដោយ destination នេះទេ; ការចាប់យក request-header ជាជម្រើស ប្រើ client snapshot ដែលបាន hydrate រួចដែលបានពិពណ៌នាខាងក្រោម។ ប្រើ cadence កម្រិតនាទី ដូចជា `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` នៅពេលនាំចេញ bodies ជំនួសឱ្យការប្រមូល backlog រៀងរាល់ម៉ោង។

### Request headers របស់ client ជាជម្រើស

ការចាប់យក header គឺ **បិទជាលំនាំដើម**។ កំណត់ `requestHeaderAllowlist` នៅក្នុង destination config
ហើយបើក **Export prompts and responses** (`includeBodies: true` នៅលើ destination)។
Allowlist ទទួលយកជា API array ឬ textarea ដែលមាន names បំបែកដោយបន្ទាត់ថ្មី/ក្បៀស៖

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ឈ្មោះត្រូវផ្គូផ្គងដោយមិនប្រកាន់អក្សរធំតូច និងត្រូវតែដូចគ្នាពេញលេញ លើកលែងតែ `*` មួយនៅចុងបញ្ចប់ ដែលជ្រើសរើសបុព្វបទឈ្មោះ header ដែលមិនទទេ។ `*` ដាច់ដោយឡែក, wildcard នៅកណ្ដាល និងឈ្មោះ HTTP header ដែលមិនត្រឹមត្រូវ នឹងត្រូវបដិសេធ។
មាន selector យ៉ាងច្រើន 64 ហើយ selector នីមួយៗមានឈ្មោះ/បុព្វបទប្រវែងអតិបរមា 256 បៃ ASCII។
ការកំណត់នេះដាច់ដោយឡែកពី `headers` ដែលប្រើសម្រាប់ផ្ទៀងផ្ទាត់ exporter ជាមួយ collector។

ការចាប់យកអានតែ `pipeline_client_request` ដែលត្រូវបានបំពេញពី `clientRawRequest` (ឬ `clientRequest` ចាស់) របស់ detailed pipeline ដែលបានរក្សាទុក។ វាមិនដែលត្រឡប់ទៅប្រើ request headers របស់ provider ទេ។
ការកត់ត្រា detailed pipeline ត្រូវតែបានបើកនៅពេល request ត្រូវបានកត់ត្រា។ នៅពេល `includeBodies` ត្រូវបានបិទ ឬ JSON របស់ client-snapshot បាត់ ខូច ឬត្រូវបានកាត់ខ្លី នឹងមិនបញ្ចេញ header attributes ទេ។ ការបង្កើន `maxBodyBytes` អាចជួយជៀសវាងការកាត់ snapshot នៅពេល export ប៉ុណ្ណោះ។ វាមិនអាចស្ដារព័ត៌មានលម្អិតដែលមិនបានរក្សាទុកពីដំបូងបានទេ។ Snapshot ដែលលើស 1 MiB ឬមាន header entries លើស 256 នឹងត្រូវមិនអើពើ។ ការបញ្ជូន prompt/response ដែលមានស្រាប់នៅតែដំណើរការជាមួយការចាប់យក header; allowlist មិនផ្ដល់ hydration mode សម្រាប់ headers តែប៉ុណ្ណោះទេ។

តម្លៃដែលបានជ្រើស នឹងក្លាយជា OTLP string arrays នៅ `http.request.header.<full lowercase header name>` ទោះបីជាមាន string តែមួយក៏ដោយ។ ឧទាហរណ៍ `X-OmniRoute-Meta-Team: example-team` នឹងក្លាយជា `http.request.header.x-omniroute-meta-team` ជាមួយ
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`។
បុព្វបទពេញលេញត្រូវបានរក្សាទុក៖ ទាំងនេះគឺជា headers ធម្មតា ដោយគ្មានការបកស្រាយ business field ឬការបម្លែងទៅជា `omniroute.metadata.*` / Langfuse metadata។ `langfuseMapping` មិនផ្លាស់ប្ដូរអត្ថន័យរបស់ header ទេ។ `User-Agent` ដែលបានជ្រើស និងមានតម្លៃតែមួយ ក៏កំណត់ scalar ស្តង់ដារ `user_agent.original` ផងដែរ។ សញ្ញាក្បៀសនៅក្នុងតម្លៃមួយ មិនត្រូវបានបំបែកទេ។ Case variants ត្រូវបានបញ្ចូលចូលគ្នាតាមលំដាប់ entry ដែលបានរក្សាទុក; ប្រសិនបើ variant ណាមួយមិនត្រឹមត្រូវ នោះ header ទាំងមូលនឹងមិនត្រូវបានបញ្ចូលទេ។ Attributes ត្រូវបានរៀបតាមឈ្មោះអក្សរតូច។

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-key headers, ឈ្មោះដែលមានសញ្ញាសម្គាល់ auth/token/secret/password/credential និងព័ត៌មានសម្ងាត់ខាងក្នុងរបស់ gateway តែងតែត្រូវបានដកចេញ ទោះបីបានជ្រើស ឬត្រូវបានបិទបាំងមួយផ្នែកនៅក្នុង storage ក៏ដោយ។ លំនាំ credential ដែលស្គាល់ នឹងប្រើ credential detector ដែលចែករំលែករួមគ្នា; redaction markers ត្រូវបានដកចេញ មិនត្រូវបាន export ជាតម្លៃដែលមានសុវត្ថិភាពទេ។ ទទួលយកតែ strings និង string arrays ដែលមិនទទេប៉ុណ្ណោះ; មិនធ្វើការបម្លែង numbers ឬ objects ដោយបង្ខំទេ។ ឈ្មោះមិនត្រឹមត្រូវ, prototype keys, control characters (លើកលែង horizontal tab) និង Unicode ដែលមានទម្រង់មិនត្រឹមត្រូវ នឹងត្រូវមិនអើពើ ដោយមិនធ្វើឱ្យ batch បរាជ័យ ឬបង្ហាញមាតិការបស់វានៅក្នុង errors ទេ។

Span នីមួយៗចាប់យក header បានយ៉ាងច្រើន 32, តម្លៃ 16 ក្នុងមួយ header, 4096 បៃ UTF-8 ក្នុងមួយតម្លៃ និងសរុប 16384 បៃ UTF-8 នៅទូទាំងឈ្មោះ និងតម្លៃ header ដែលបានចាប់យក។ Headers ដែលធំពេក/មិនត្រឹមត្រូវ នឹងត្រូវលុបចេញទាំងមូល មិនមែនកាត់ខ្លីទេ។ ការជ្រើសរើសគឺជាការសម្រេចចិត្តអំពីភាពឯកជនរបស់ប្រតិបត្តិករ៖ ឈ្មោះដែលមើលទៅមានសុវត្ថិភាព ក៏អាចមានទិន្នន័យផ្ទាល់ខ្លួនបានដែរ ហើយកម្រិតកំណត់/ឧបករណ៍ស្វែងរកទាំងនេះ មិនមែនជាឧបករណ៍សម្អាត PII ទូទៅទេ។

### ដែនកំណត់ការបញ្ជូន

Requests ត្រូវបានកំណត់ត្រឹម 500 spans និង 4 MiB នៃ JSON UTF-8 រួមទាំង envelope។ Span ដែលត្រូវបានអនុញ្ញាតគ្រប់មួយ ត្រូវបានពិនិត្យទំហំមុន request ដំបូងនៃ cursor batch។ ប្រសិនបើ span មួយធំជាងដែនកំណត់ នោះគ្មានផ្នែកណាមួយនៃ batch នោះត្រូវបានបញ្ជូនទេ ហើយនឹងបរាជ័យជាមួយការណែនាំឱ្យបន្ថយ `maxBodyBytes`; វាមិនត្រូវបានលុបចោលដោយស្ងាត់ៗទេ។ Preflight រក្សាទុកតែ record references និងចំនួនបៃ ដោយលុប span/JSON បណ្ដោះអាសន្ននីមួយៗ; spans ត្រូវបានបង្កើតឡើងវិញសម្រាប់ chunks ដែលមានដែនកំណត់ ជំនួសឱ្យការរក្សាទុកច្បាប់ចម្លង serialized ទីពីររបស់ batch។ HTTP 408/429/5xx, network failures និង timeouts ទទួលបានការព្យាយាមយ៉ាងច្រើនបីដង ជាមួយ exponential backoff 250/500 ms។ `Retry-After` ជាវិនាទី ឬ HTTP dates អាចពន្យារពេលរង់ចាំបានរហូតដល់ 5 វិនាទី។ Status ផ្សេងទៀតនឹងបរាជ័យភ្លាមៗ។ OTLP 2xx partial rejection ក៏បោះកំហុសដែរ ជំនួសឱ្យការទទួលស្គាល់ span ដែលបាត់បង់; acknowledgements ជា JSON ទទេ ឬត្រឹមត្រូវ ត្រូវបានទទួលយក ដោយមានដែនកំណត់ការអាន response 64 KiB។

Errors មានតែព័ត៌មានដែលជាកម្មសិទ្ធិរបស់ exporter ប៉ុណ្ណោះ៖ HTTP status, retry class, ចំនួន attempts និង sent spans ឬពាក្យថេរសម្រាប់ acknowledgement/network failure។ Collector response bodies, partial-success counts និង response headers មិនត្រូវបានចម្លងទៅក្នុង errors, logs ឬ dashboard ឡើយ។ Batch ដែលបរាជ័យ ឬត្រូវបានទទួលយកមួយផ្នែក មិនត្រូវបានទទួលស្គាល់ទេ៖ destination បង្ហាញថា Failing ជាមួយ status នោះ cursor នៅតែស្ថិតនៅ batch ចុងក្រោយដែលបានទទួលស្គាល់ ហើយការដំណើរការលើកបន្ទាប់នឹងបញ្ជូន rows ដដែលម្ដងទៀត។ Status អចិន្ត្រៃយ៍នឹងបន្តបរាជ័យ រហូតដល់ collector ឬ configuration ត្រូវបានជួសជុល។ ប្រើ logs របស់ collector ផ្ទាល់សម្រាប់ព័ត៌មានលម្អិតអំពី response។ សេចក្ដីសង្ខេប error របស់ call-log នៅតែរក្សា redaction ដាច់ដោយឡែករបស់វា។

Trace ids និង span ids គឺជា 32/16 តួអក្សរ hex ដំបូងនៃ SHA-256 លើ
`"omniroute.trace\\0" + callLogId` និង `"omniroute.span\\0" + callLogId`។ ការបញ្ជូនម្ដងទៀតមាន ids ដូចគ្នា។
នេះមិនមែនជាការធានាការកម្ចាត់ទិន្នន័យស្ទួនទេ៖ backends មួយចំនួន រួមទាំង Langfuse v4 ingestion មិនកម្ចាត់ spans ដែលមាន id ដូចគ្នាទេ។ Crash ឬ partial chunk failure អាចបញ្ជូន cursor batch ដែលមិនទាន់បានទទួលស្គាល់តែមួយនោះម្ដងទៀតបានយ៉ាងច្រើន; batch ទាំងមូលអាចត្រូវបានធ្វើស្ទួន មិនមែនតែ HTTP chunk ចុងក្រោយរបស់វាទេ។ ជ្រើសរើសទំហំ cursor batch ដោយគិតពីការប្ដូរផលប្រយោជន៍នេះ។

### ឧទាហរណ៍ Langfuse

កំណត់ fields ទាំងនេះសម្រាប់ instance Langfuse ដែល self-hosted៖

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

បង្កើតតម្លៃ Authorization នៅមូលដ្ឋាន ដោយប្រើ Base64 នៃ string តាមព្យញ្ជនៈ `public-key:secret-key`
(ឧទាហរណ៍ដោយប្រើ `Buffer.from(publicKey + ":" + secretKey).toString("base64")`)។
កុំដាក់ credentials ពិតប្រាកដនៅក្នុង logs, screenshots ឬ issues។ ការផ្គូផ្គងនឹងកំណត់
`x-langfuse-ingestion-version: 4` ដោយស្វ័យប្រវត្តិ; Authorization នៅតែត្រូវបានផ្គត់ផ្គង់នៅក្នុង `headers`។
ទាំង headers និង identity salt ដែលបានបង្កើត ប្រើយន្តការដែលមានស្រាប់សម្រាប់ encrypted secret-field និង API placeholders; `STORAGE_ENCRYPTION_KEY` គឺត្រូវការ។

ការម៉ាប់បន្ថែមប្រភេទ/ម៉ូដែលនៃការបង្កើត ព័ត៌មានលម្អិតអំពីការប្រើប្រាស់ JSON (input/output/total និង cache keys ដែលមាន) ស្នាមថត JSON input/output កម្រិត ERROR/DEFAULT សារស្ថានភាពដែលបានសម្អាត ឈ្មោះ trace លេខសម្គាល់ session បរិស្ថានជាជម្រើស និង
`langfuse.observation.metadata.<key>` ដែលអាចត្រងបាន សម្រាប់ provider, requested model, path, combo, cache
source និង status។ `langfuse.observation.completion_start_time` គឺជា ISO 8601 នៅពេលចាប់ផ្តើម + TTFT តែនៅពេលស្គាល់ TTFT និងវាស្ថិតនៅក្នុងរយៈពេលប៉ុណ្ណោះ។ មិនមាន cost attributes ត្រូវបានផ្ញើទេ។

របៀបកំណត់អត្តសញ្ញាណអនុវត្តចំពោះ `langfuse.user.id`៖

- `pseudonymous` (លំនាំដើម): HMAC-SHA256 នៃ internal id របស់ API key ដោយប្រើ salt ទំហំ 32 បៃ ដែលចៃដន្យ និងមានតែមួយសម្រាប់ destination នីមួយៗ។ Salt ត្រូវបានបង្កើតនៅពេលបង្កើត ប្រសិនបើមិនមាន ហើយត្រូវបានអ៊ិនគ្រីបជា `identitySalt` មិនដែលត្រូវបានបញ្ជូនត្រឡប់ និងត្រូវបានរក្សាទុកនៅពេលកែសម្រួល។ Raw key ids មិនដែលត្រូវបានដាក់ចូលក្នុង span attributes ទេ។ ការបង្កើតឡើងវិញ/បង្វិល salt របស់ destination នឹងផ្លាស់ប្តូរអត្តសញ្ញាណ។
- `keyName`: ឈ្មោះ API key ដែលបានកំណត់រចនា ដោយចេតនា ដើម្បីបង្ហាញ operator label នោះ។
- `none`: គ្មាន user id។ Session tags នៅតែត្រូវបាន export នៅពេលមាន; របៀបទាំងនេះមិនធ្វើឱ្យ prompt content តាមអំពើចៃដន្យ ឬ session/correlation labels ដែលផ្តល់ដោយ operator ក្លាយជាអនាមិកទេ។

### ចាប់ផ្តើមដោយមិនធ្វើ backfill

នៅពេលបង្កើតប៉ុណ្ណោះ សូមបើក **ចាប់ផ្តើមពីទីតាំងបច្ចុប្បន្ន (រំលង logs ដែលមានស្រាប់)** ឬបញ្ជូន
`startFromCurrentPosition: true` នៅកម្រិតកំពូលនៃ create API payload។ វាចាប់ផ្តើម
`cursor_row_id` ទៅជា rowid អតិបរមាបច្ចុប្បន្ននៃ call-log ដែលបានរក្សាទុក ដោយប្រើ cursor helpers ដែលមានស្រាប់ ដោយមិនចាំបាច់ធ្វើ migration។ លំនាំដើមគឺ false (cursor 0 និង retained-history backfill)។
វាមិនមែនជាការកំណត់សម្រាប់ reset cursor នៅពេល update ទេ។

ការបន្ថែម `ttftMs` ដែលបានចែករំលែក ក៏បន្ថែមជួរឈរ `ttft_ms` ដែលអាចជា null បានទៅក្នុង BigQuery mapper
និង new-table schema៖ schema test របស់វាតម្រូវឱ្យគ្រប់ canonical record field មានជួរឈរមួយ។ តារាងដែលមានស្រាប់នៅតែ export ដដែល៖ `prepare()` អាន table schema ហើយលុបចេញតែ `ttft_ms` នៅពេលជួរឈរនោះមិនមាន។ បន្ថែមជួរឈរ nullable INT64 ដើម្បីទទួលបាន TTFT
នៅការដំណើរការបន្ទាប់ ឬប្រើតារាងថ្មី។ ជួរឈរ TTFT ជាជម្រើសមិនបង្កឱ្យមាន schema update ទេ។ ជួរឈរ usage-evidence
អនុវត្តតាមលំហូរភាពឆបគ្នាតាមលក្ខខណ្ឌ និងជ្រើសរើសចូលខាងក្រោម; row fields ផ្សេងទៀតនៅតែរក្សាការត្រួតពិនិត្យ schema យ៉ាងតឹងរ៉ឹង។
