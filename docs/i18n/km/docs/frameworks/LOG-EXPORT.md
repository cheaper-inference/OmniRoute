ការនាំចេញកំណត់ហេតុការហៅ OmniRoute ជាបន្តបន្ទាប់ និងតាមការកើនឡើង ទៅកាន់ឃ្លាំងវិភាគខាងក្រៅ។

ផ្ទាំង Logs នៅក្នុងផ្ទាំងគ្រប់គ្រងរក្សាទុកប្រវត្តិសំណើក្នុង SQLite (`call_logs`) ដែលត្រូវបានកំណត់ដោយ
ការបង្វិល និងរយៈពេលរក្សាទុក។ ការនាំចេញកំណត់ហេតុបញ្ជូនសំណុំកំណត់ត្រាដូចគ្នានេះចេញតាមកាលវិភាគ ដើម្បីឱ្យវាអាចរក្សាទុកបានយូរជាង
មូលដ្ឋានទិន្នន័យមូលដ្ឋាន និងអាចភ្ជាប់ជាមួយទិន្នន័យផ្សេងទៀត។ BigQuery គឺជាគោលដៅដំបូង;
បំពង់ដំណើរការនេះប្រើបញ្ជីចុះឈ្មោះ ដូច្នេះអាចបន្ថែមគោលដៅផ្សេងទៀតបាន។

## 1. របៀបដំណើរការ

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **កាលវិភាគ** — ការងារ cron មួយរបស់ `JobRegistry` ឈ្មោះ `log_export` ដែលមានតម្លៃលំនាំដើម `0 * * * *` (រៀងរាល់ម៉ោង,
  UTC)។ វាត្រូវបានចុះឈ្មោះនៅក្នុង `src/lib/initCloudSync.ts`; អាចកំណត់ជំនួសដោយ `OMNIROUTE_LOG_EXPORT_CRON`។
  រាល់ពេលកាលវិភាគដំណើរការ វានាំចេញទិន្នន័យពីគោលដៅទាំងអស់ដែលបាន **បើកដំណើរការ** តាមលំដាប់លំដោយ។
- **ទស្សន៍ទ្រនិច** — `call_logs.rowid` លាក់របស់ SQLite ដែលត្រូវបានរក្សាទុកសម្រាប់គោលដៅនីមួយៗក្នុង
  `log_export_destinations.cursor_row_id`។ `timestamp` ត្រូវបានចេតនាមិនប្រើជាទស្សន៍ទ្រនិច៖ អ្នកហៅ
  អាចផ្តល់តម្លៃផ្ទាល់ខ្លួន ដូច្នេះសំណើយឺតអាចត្រូវបានសរសេរបន្ទាប់ពីសំណើលឿនជាងដែលបានចាប់ផ្តើម
  នៅពេលក្រោយ ហើយទស្សន៍ទ្រនិចតាមត្រាពេលវេលានឹងរំលងវា។
- **ការបែងចែកជាបាច់** — `batch_size` ជួរដេកក្នុងមួយសំណើ (លំនាំដើម 500), `max_rows_per_run` ជួរដេកក្នុងមួយលើកដំណើរការ
  (លំនាំដើម 10000) ដូច្នេះទិន្នន័យរង់ចាំច្រើនត្រូវបាននាំចេញក្នុងការដំណើរការតាមកាលវិភាគជាច្រើនលើក ជំនួសឱ្យការរាំងស្ទះមួយលើក។
- **ការបញ្ជូន** — ទស្សន៍ទ្រនិចទៅមុខតែបន្ទាប់ពី `send()` បញ្ចប់ដោយជោគជ័យ។ បាច់ដែលបរាជ័យទុក
  ទស្សន៍ទ្រនិចនៅទីតាំងដដែល ដូច្នេះជួរដេកដដែលនឹងត្រូវបានសាកល្បងឡើងវិញនៅលើកបន្ទាប់។ ការធានាគឺ
  យ៉ាងហោចណាស់មួយដង រួមជាមួយការលុបទិន្នន័យស្ទួននៅខាងគោលដៅ មិនមែនម្តងគត់យ៉ាងពិតប្រាកដទេ៖ BigQuery កំណត់សោឱ្យជួរដេកនីមួយៗ
  តាមលេខសម្គាល់កំណត់ហេតុការហៅ ដែលវាគោរពតាមលទ្ធភាពអតិបរមាក្នុងចន្លោះពេលលុបទិន្នន័យស្ទួនរបស់វា។
- **ការការពារការដំណើរការត្រួតគ្នា** — ការដំណើរការតាម cron និង `POST .../run` អាចកើតឡើងក្នុងពេលតែមួយ។ គោលដៅដែល
  កំពុងនាំចេញរួចហើយនឹងត្រូវបានរំលង ជំនួសឱ្យការនាំចេញពីរដង (`skipped: true` ក្នុងលទ្ធផលដំណើរការ),
  ដូច្នេះការដំណើរការស្របពេលគ្នាមិនអាចបញ្ជូនបាច់ឡើងវិញ ឬសរសេរទស្សន៍ទ្រនិចថយក្រោយបានទេ។
- **ការស្ដារឡើងវិញក្រោយការលុបសម្អាត** — ប្រសិនបើ `cursor_row_id` មានតម្លៃខ្ពស់ជាង `MAX(rowid)` (តារាងទាំងមូលត្រូវបាន
  លុបសម្អាត ហើយ rowid ចាប់ផ្តើមឡើងវិញ) កម្មវិធីដំណើរការនឹងថយទៅ 0 ជំនួសឱ្យការមិនអាចមើលឃើញទិន្នន័យជាអចិន្ត្រៃយ៍។

### កម្មវិធីដំណើរការដាច់ដោយឡែក និងដែនកំណត់

ការដំណើរការគោលដៅនីមួយៗនៅលើ Node ចាប់ផ្តើមដំណើរការកូនរបស់ប្រព័ន្ធប្រតិបត្តិការដាច់ដោយឡែក ដែលមានអាយុកាលខ្លី (`child_process`
ជាមួយ IPC មិនមែន `worker_threads` ទេ)។ ការអានតួទិន្នន័យ ការញែក/បម្លែង JSON របស់ទិន្នន័យបញ្ជូន,
`prepare()` របស់គោលដៅ និង I/O បណ្ដាញរបស់គោលដៅ សុទ្ធតែដំណើរការនៅទីនោះ មិនមែននៅលើរង្វិលជុំព្រឹត្តិការណ៍របស់ម៉ាស៊ីនមេទេ។
មានតែការកំណត់រចនាសម្ព័ន្ធ និងសារវឌ្ឍនភាពតូចៗប៉ុណ្ណោះដែលឆ្លងកាត់ IPC; កំណត់ត្រាដែលបាននាំចេញមិនត្រឡប់ទៅ
ម៉ាស៊ីនមេវិញឡើយ។ ការងារ cron និងផ្លូវ Run now រក្សាលទ្ធផលសាធារណៈ និងការការពារការដំណើរការត្រួតគ្នាដដែល។

ដំណើរការកូនបើក `DATA_DIR/storage.sqlite` ដែលម៉ាស៊ីនមេបានកំណត់ទីតាំងរួច ក្នុងរបៀបអានតែប៉ុណ្ណោះ ដោយប្រើ `node:sqlite`,
ជាមួយ `busy_timeout=5000` និង `query_only=ON`។ វាមិននាំចូល singleton របស់មូលដ្ឋានទិន្នន័យទេ ហើយមិនធ្វើ
ការផ្លាស់ប្ដូររចនាសម្ព័ន្ធ ការបម្រុងទុក ឬការធ្វើបច្ចុប្បន្នភាព SQLite ឡើយ។ ការគ្រប់គ្រងកំណត់ត្រាឯកសារធាតុដែលបាត់/ខូច (រួមទាំង
UPDATE សម្រាប់ឯកសារធាតុខូច) នៅតែមានតែក្នុងផ្លូវព័ត៌មានលម្អិតរបស់ផ្ទាំងគ្រប់គ្រងប៉ុណ្ណោះ។ ផ្លូវទាំងពីរប្រើមុខងារដោះស្រាយ
ព័ត៌មានលម្អិតសុទ្ធរួមគ្នា; ការនាំចេញប្រើការអានប្រព័ន្ធឯកសារបែបអសមកាល និងលំដាប់ដោះស្រាយដូចគ្នា គឺឯកសារធាតុ → ទិន្នន័យបង្កប់
បែបចាស់ → ឌីសបែបចាស់ → គ្មាន។ ការដំណើរការមួយថតទុក rowid បញ្ចូលអតិបរមា

នេះជាខ្លឹមសារសំណើណែនាំ ដូច្នេះវា **ត្រូវបានបិទតាមលំនាំដើម** ហើយត្រូវបានកំណត់ដោយចេតនាឱ្យជាជម្រើសតាមគោលដៅនីមួយៗ។

  ធ្វើឱ្យខ្លឹមសារប្រអប់បញ្ចូលណាមួយ ឬស្លាកសម័យ/ទំនាក់ទំនងដែលផ្ដល់ដោយប្រតិបត្តិករ ក្លាយជាអនាមិកទេ។

### ការចាប់ផ្ដើមដោយមិនបំពេញទិន្នន័យប្រវត្តិ

តែនៅពេលបង្កើតប៉ុណ្ណោះ សូមបើក **ចាប់ផ្ដើមពីទីតាំងបច្ចុប្បន្ន (រំលងកំណត់ហេតុដែលមានស្រាប់)** ឬបញ្ជូន
`startFromCurrentPosition: true` នៅកម្រិតកំពូលនៃទិន្នន័យសំណើ API សម្រាប់ការបង្កើត។ វាកំណត់តម្លៃដំបូងរបស់
`cursor_row_id` ទៅជា rowid អតិបរមាបច្ចុប្បន្ននៃកំណត់ហេតុការហៅដែលបានរក្សាទុក ដោយប្រើមុខងារជំនួយទស្សន៍ទ្រនិចដែលមានស្រាប់
ដោយមិនចាំបាច់ធ្វើការផ្លាស់ប្ដូររចនាសម្ព័ន្ធទិន្នន័យ។ តម្លៃលំនាំដើមគឺ false (ទស្សន៍ទ្រនិច 0 និងការបំពេញទិន្នន័យប្រវត្តិដែលបានរក្សាទុក)។
វាមិនមែនជាការកំណត់សម្រាប់កំណត់ទស្សន៍ទ្រនិចឡើងវិញនៅពេលធ្វើបច្ចុប្បន្នភាពទេ។

ការបន្ថែម `ttftMs` រួមនេះក៏បន្ថែមជួរឈរ `ttft_ms` ដែលអាចមានតម្លៃ null ទៅក្នុងឧបករណ៍ផ្គូផ្គង BigQuery
និងគ្រោងការណ៍តារាងថ្មីផងដែរ៖ ការធ្វើតេស្តគ្រោងការណ៍របស់វាតម្រូវឱ្យវាលនីមួយៗនៃកំណត់ត្រាស្តង់ដារមាន
ជួរឈរមួយ។ តារាងដែលមានស្រាប់បន្តនាំចេញដោយមិនផ្លាស់ប្ដូរ៖ `prepare()` អានគ្រោងការណ៍តារាង ហើយ
លុបចេញតែ `ttft_ms` ប៉ុណ្ណោះ នៅពេលគ្មានជួរឈរនោះ។ បន្ថែមជួរឈរ INT64 ដែលអាចមានតម្លៃ null ដើម្បីទទួលបាន TTFT
នៅពេលដំណើរការបន្ទាប់ ឬប្រើតារាងថ្មី។ មិនតម្រូវឱ្យមាន PATCH ការកែប្រែគ្រោងការណ៍ដោយស្វ័យប្រវត្តិ ឬសិទ្ធិអនុញ្ញាត
បន្ថែមទេ។ វាលផ្សេងទៀតទាំងអស់ក្នុងជួរដេកនៅតែរក្សាការត្រួតពិនិត្យគ្រោងការណ៍យ៉ាងតឹងរ៉ឹង។

## 7. ការប្រើប្រាស់វា

- **ផ្ទាំងគ្រប់គ្រង**៖ ការរួមបញ្ចូល → ការនាំចេញកំណត់ហេតុ។ បន្ថែមគោលដៅមួយ ដំណើរការ **សាកល្បង** ដើម្បីពិនិត្យព័ត៌មានផ្ទៀងផ្ទាត់អត្តសញ្ញាណ
  ដោយមិនសរសេរជួរដេក បន្ទាប់មកបើកដំណើរការវា។
- **ទិន្នន័យរង់ចាំ**៖ កាតគោលដៅនីមួយៗបង្ហាញជួរដេកដែលកំពុងរង់ចាំ និងទស្សន៍ទ្រនិច; `GET
/api/log-export/status` ត្រឡប់តួលេខដូចគ្នា រួមជាមួយការដំណើរការកិច្ចការ 20 លើកចុងក្រោយ។
- **គោលដៅដែលបរាជ័យមិនធ្វើឱ្យគោលដៅផ្សេងទៀតបរាជ័យទេ** — សេចក្តីសង្ខេបនៃការដំណើរការកត់ត្រាស្ថានភាពតាមគោលដៅនីមួយៗ
  នៅក្នុង `last_status` / `last_error` ហើយប្រវត្តិនៃការដំណើរការកិច្ចការរក្សាទុកលទ្ធផលសរុប។
- **ការលុបគោលដៅនឹងលុបទស្សន៍ទ្រនិចរបស់វា។** ការបន្ថែមវាឡើងវិញនឹងចាប់ផ្តើមពីកំណត់ហេតុការហៅចាស់បំផុតដែលនៅរក្សាទុក
  ដែលនឹងផ្ញើជួរដេកឡើងវិញ ទោះបីជាគោលដៅអាចមានជួរដេកទាំងនោះរួចហើយក៏ដោយ។ នៅលើ BigQuery,
  `insertId` របស់ជួរដេកនីមួយៗអាចទប់ស្កាត់ការស្ទួននោះបានតែក្នុងចន្លោះពេលលុបការស្ទួនរបស់ BigQuery ប៉ុណ្ណោះ ដូច្នេះគួរបិទដំណើរការ
  គោលដៅជាជាងលុបវា។
