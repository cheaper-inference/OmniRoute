### ស្ថាបត្យកម្មក្នុងមួយកថាខណ្ឌ

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) គឺជា ring buffer ក្នុងអង្គចងចាំដែលប្រើរួមគ្នា (លំនាំដើម 1000 ធាតុ និងអាចកំណត់បានតាមរយៈ `INSPECTOR_BUFFER_SIZE`)។ ប្រភពចាប់យកទាំងអស់សរសេរទិន្នន័យចូលវាតាមរយៈ `push()`។ ថ្នាក់ buffer ចាត់ថ្នាក់ធាតុនីមួយៗដោយប្រើ `kindDetector.ts` (កំណត់ថាតើវាជាសំណើ LLM ឬអត់) គណនា `contextKey` (ស្នាមម្រាមដៃ SHA-256 នៃ system prompt) ហើយផ្សាយទៅកាន់អ្នកជាវ WebSocket ទាំងអស់តាមរយៈ `globalTrafficBuffer.subscribe()`។ ផ្ទាំងគ្រប់គ្រងតភ្ជាប់តាមរយៈ `GET /api/tools/traffic-inspector/ws` ហើយទទួល snapshot នៅពេលតភ្ជាប់ បន្ទាប់មកទទួលព្រឹត្តិការណ៍ `new`/`update`/`clear`។

## §2 របៀបចាប់យក

Traffic Inspector គាំទ្រ **ប្រភពចាប់យកចំនួន 5 ក្នុងពេលដំណាលគ្នា**។ ប្រភពនីមួយៗអាចបើក ឬបិទដោយឯករាជ្យ។ វាល `source` នៅលើ `InterceptedRequest` នីមួយៗ (`src/mitm/inspector/types.ts`) គឺជាតម្លៃមួយក្នុងចំណោម `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` ឬ `"tproxy"`។

### របៀបទី 1 — AgentBridge (លំនាំដើម បើកជានិច្ច)

**ប្រភព:** កម្មវិធីដោះស្រាយ AgentBridge (`src/mitm/handlers/base.ts`)
**យន្តការ:** រាល់ការហៅ `intercept()` ក្នុង `MitmHandlerBase` នឹងហៅ `hookBufferStart()` មុនពេលបញ្ជូនបន្ត និង `hookBufferUpdate()` នៅពេលបញ្ចប់។ មិនត្រូវការការកំណត់រចនាសម្ព័ន្ធបន្ថែមឡើយ — វាដំណើរការភ្លាមៗនៅពេល AgentBridge កំពុងដំណើរការ។
**វិសាលភាព:** ភ្នាក់ងារ IDE ចំនួន 9 ដែលបានកំណត់រចនាសម្ព័ន្ធក្នុង AgentBridge
**ចំណាំ:** វាល `source` ក្នុង `InterceptedRequest` = `"agent-bridge"`

### របៀបទី 2 — ម៉ាស៊ីនផ្ទាល់ខ្លួន (ការបង្វែរទិស DNS)

**ប្រភព:** បញ្ជីម៉ាស៊ីនដែលកំណត់ដោយអ្នកប្រើប្រាស់ (តារាង `inspector_custom_hosts`)
**យន្តការ:** ការបន្ថែមម៉ាស៊ីនតាមរយៈ UI នឹងបន្ថែម `127.0.0.1 <host>` ទៅ `/etc/hosts` (ទាមទារ sudo)។ ម៉ាស៊ីនមេ MITM របស់ AgentBridge ដែលមានស្រាប់ (ច្រក 443) នឹងបង្កើតវិញ្ញាបនបត្រ SNI ជាថាមវន្តសម្រាប់ម៉ាស៊ីនថ្មី។
**វិសាលភាព:** កម្មវិធីណាមួយដែលប្រើម៉ាស៊ីនដែលបានបន្ថែម — មិនចាំបាច់ផ្លាស់ប្តូរការកំណត់រចនាសម្ព័ន្ធរបស់កម្មវិធី
**ចំណាំ:** `source` = `"custom-host"`

ឧទាហរណ៍ករណីប្រើប្រាស់៖

- ត្រួតពិនិត្យ `api.openai.com` ពីស្គ្រីប Python
- បំបាត់កំហុស `my-internal-llm.company.com`
- ចាប់យកចរាចរណ៍ពីឧបករណ៍ចល័តនៅលើបណ្តាញដូចគ្នា (តាមរយៈការក្លែងបន្លំ ARP — កម្រិតខ្ពស់)

### របៀបទី 3 — កម្មវិធីស្តាប់ HTTP_PROXY (ច្រក 8080)

**ប្រភព:** កម្មវិធីដែលប្រើអថេរបរិស្ថាន `HTTP_PROXY`/`HTTPS_PROXY`
**យន្តការ:** កម្មវិធីស្តាប់បន្ទាប់បន្សំនៅច្រក 8080 (`src/mitm/inspector/httpProxyServer.ts`) ដែលដើរតួជាប្រូកស៊ី HTTP/HTTPS ជាក់លាក់តាមស្តង់ដារ។ វាទទួលយកធ្យូនែល `CONNECT` (HTTPS) និងសំណើ HTTP ដោយផ្ទាល់។
**វិសាលភាព:** កម្មវិធីណាមួយដែលគោរពតាមបរិស្ថាន `HTTP_PROXY` — មិនត្រូវការផ្លាស់ប្តូរ DNS និងមិនត្រូវការ sudo
**ចំណាំ:** `source` = `"http-proxy"`

```bash
# ចាប់យករហ័សសម្រាប់ពាក្យបញ្ជាតែមួយ៖
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# ចាប់យកជាប់លាប់ក្នុងសម័យដំណើរការ shell មួយ៖
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**ដែនកំណត់ TLS:** HTTPS ឆ្លងកាត់ធ្យូនែល `CONNECT` ធម្មតា៖ កម្មវិធីស្តាប់បញ្ជូនតបៃដែលបានអ៊ិនគ្រីបបន្តដោយមិនកែប្រែ និងកត់ត្រាតែទិន្នន័យមេតាប៉ុណ្ណោះ (ម៉ាស៊ីន ច្រក និងពេលវេលា)។ វាមិនដែលឌិគ្រីប HTTPS ទេ ហើយមិនមានការកំណត់ណាដែលបើកការឌិគ្រីបសម្រាប់របៀបនេះឡើយ។ ដើម្បីចាប់យកខ្លឹមសារ HTTPS សូមបញ្ជូនម៉ាស៊ីនតាមរយៈរបៀបទី 1 (AgentBridge), របៀបទី 2 (ម៉ាស៊ីនផ្ទាល់ខ្លួន) ឬរបៀបទី 5 (ការឌិគ្រីប TPROXY)។

**ការប៉ះទង្គិចច្រក:** ប្រសិនបើច្រក 8080 កំពុងត្រូវបានប្រើ AgentBridge នឹងត្រឡប់ 409 ជាមួយកំហុសដែលមានរចនាសម្ព័ន្ធ។ ផ្លាស់ប្តូរច្រកតាមរយៈអថេរបរិស្ថាន `INSPECTOR_HTTP_PROXY_PORT`។

### របៀបទី 4 — ប្រូកស៊ីទូទាំងប្រព័ន្ធ (កម្រិតខ្ពស់ ត្រូវជ្រើសរើសបើក)

**ប្រភព:** ការកំណត់ប្រូកស៊ីកម្រិត OS (អនុវត្តចំពោះគ្រប់កម្មវិធីនៅលើម៉ាស៊ីន)
**យន្តការ:** ប្រើ API របស់ OS ដើម្បីបង្វែរទិសចរាចរណ៍ HTTP/HTTPS ទាំងអស់ឱ្យឆ្លងកាត់កម្មវិធីស្តាប់ HTTP_PROXY៖

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **វិសាលភាព:** គ្រប់កម្មវិធីនៅលើម៉ាស៊ីនដែលគោរពតាមការកំណត់ប្រូកស៊ីរបស់ប្រព័ន្ធ
  **ចំណាំ:** `source` = `"system-proxy"`

**យន្តការសុវត្ថិភាព:**

- កម្មវិធីកំណត់ពេលបិទដោយស្វ័យប្រវត្តិ (លំនាំដើម 30 នាទី អាចកំណត់រចនាសម្ព័ន្ធតាមរយៈ `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- ស្ថានភាពប្រូកស៊ីប្រព័ន្ធពីមុនត្រូវបានរក្សាទុកក្នុង DB និងស្ដារឡើងវិញនៅពេលត្រឡប់ការផ្លាស់ប្តូរ
- ផ្ទាំងគ្រប់គ្រងបង្ហាញសារជំរុញ "កំពុងត្រឡប់ការផ្លាស់ប្តូរប្រូកស៊ីប្រព័ន្ធ" ប្រសិនបើអ្នកប្រើប្រាស់ចាកចេញពីទំព័រខណៈពេលវាសកម្ម
- UI បង្ហាញផ្លាក `⚠ កម្រិតខ្ពស់` + ប្រអប់ធីកបញ្ជាក់យ៉ាងច្បាស់

### របៀបទី 5 — ការឌិគ្រីបថ្លារបស់ TPROXY (Linux, root, ត្រូវជ្រើសរើសបើក)

**ប្រភព:** TPROXY របស់ខឺណែល + ការកំណត់ទិសដៅផ្អែកលើគោលការណ៍ (`src/mitm/tproxy/`)
**យន្តការ:** ដាក់សញ្ញាសម្គាល់លើការតភ្ជាប់ TCP ចេញពីមូលដ្ឋានថ្មីទៅច្រកគោលដៅ (លំនាំដើម `443`) ក្នុង `mangle OUTPUT` ហើយ `ip rule` បង្វែរទិសកញ្ចប់ទិន្នន័យដែលបានសម្គាល់ទៅការបញ្ជូនក្នុងមូលដ្ឋាន ខណៈដែលគោលដៅ `TPROXY` របស់ `mangle PREROUTING` ប្រគល់កញ្ចប់ទាំងនោះទៅកម្មវិធីស្តាប់ថ្លា (**IP_TRANSPARENT**) (ច្រកលំនាំដើម `8443`)។ កម្មវិធីស្តាប់បញ្ចប់ TLS ដោយប្រើវិញ្ញាបនបត្រចុងដែលចេញ **សម្រាប់ឈ្មោះម៉ាស៊ីន SNI នីមួយៗតាមតម្រូវការ** ដោយ CA ជាថាមវន្ត ចាប់យកការផ្លាស់ប្តូរទិន្នន័យដែលបានឌិគ្រីប ហើយបញ្ជូនសំណើដែលបានអ៊ិនគ្រីបឡើងវិញទៅគោលដៅដើម។
**វិសាលភាព:** ម៉ាស៊ីនគោលដៅ **ណាមួយ** នៅលើច្រកគោលដៅ — មិនមានការក្លែងបន្លំ `/etc/hosts` មិនមានបរិស្ថាន `HTTP_PROXY` និងមិនមានការកែប្រែប្រូកស៊ីទូទាំងប្រព័ន្ធ។ ដំណើរការដែលត្រូវបានស្ទាក់ចាប់មិនចាំបាច់ផ្លាស់ប្តូរការកំណត់រចនាសម្ព័ន្ធទេ ប៉ុន្តែត្រូវតែទុកចិត្ត CA ជាថាមវន្ត។
**ចំណាំ:** `source` = `"tproxy"`

**តម្រូវការ:** សម្រាប់តែ Linux ប៉ុណ្ណោះ (**IP_TRANSPARENT** មានតែលើ Linux) សមត្ថភាព **CAP_NET_ADMIN** (root) និងកម្មវិធីបន្ថែម N-API ដើមដែលត្រូវតែសាងសង់ដោយប្រើខ្សែឧបករណ៍ C (`npm run build:native:tproxy`)។ នៅពេលមិនអាចប្រើបាន ប៊ូតុងបិទបើកនៅលើផ្ទាំងគ្រប់គ្រងនឹងត្រូវបានបិទ ដោយមានព័ត៌មានជំនួយ "ការឌិគ្រីប TPROXY តម្រូវឱ្យមាន Linux + root + កម្មវិធីបន្ថែមដើម"។ ច្បាប់ជញ្ជាំងភ្លើងត្រូវបានអនុវត្ត/ត្រឡប់ការផ្លាស់ប្តូរជាប្រតិបត្តិការ (ការគាំងមិនដែលទុកច្បាប់ `mangle` ចោលទេ) និងត្រូវបានសម្អាតនៅពេលចាប់ផ្តើមប្រព័ន្ធឡើងវិញ។ យន្តការប្រឆាំងរង្វិលជុំដែលផ្អែកលើ SO_MARK រារាំងការបញ្ជូនបន្តដែលបានអ៊ិនគ្រីបឡើងវិញរបស់ប្រូកស៊ីផ្ទាល់ពីការត្រូវបានស្ទាក់ចាប់ម្តងទៀត។

នេះជាប្រព័ន្ធរងដ៏ធំមួយដែលមានមគ្គុទ្ទេសក៍ប្រតិបត្តិករផ្ទាល់ខ្លួន — សូមមើល `docs/security/MITM-TPROXY-DECRYPT.md` (git; មិនត្រូវបានចងក្រងបញ្ចូលក្នុង `/docs`) សម្រាប់រូបមន្តជញ្ជាំងភ្លើងពេញលេញ CA ជាថាមវន្តសម្រាប់ SNI នីមួយៗ + កម្មវិធីដំឡើងឃ្លាំងទំនុកចិត្ត ផ្លូវសម្រាប់តែក្នុងមូលដ្ឋាន សេចក្ដីលម្អិតអំពីការប្រឆាំងរង្វិលជុំ និងគ្រោងការណ៍កំណត់រចនាសម្ព័ន្ធ។ ប៊ូតុងបិទបើកត្រូវបានគ្រប់គ្រងដោយ `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (ចំណាំ៖ ផ្លូវស្ថិតនៅក្រោមបុព្វបទ AgentBridge មិនមែនបុព្វបទ Traffic Inspector ទេ)។

- **អ៊ីមូជីភ្នាក់ងារ**៖ 🔵 Antigravity, 🟢 Copilot, 🟠 Kiro, 🟣 Codex, 🔷 Cursor, 🟤 Zed, 🟡 Claude Code, ⚫ Open Code, 🌐 ម៉ាស៊ីនផ្ទាល់ខ្លួន
- **របារពណ៌បរិបទ**៖ ស៊ុមខាងឆ្វេង 1px ដែលដាក់ពណ៌តាម `contextKey` (SHA-256 នៃប្រអប់បញ្ចូលប្រព័ន្ធ) — ដាក់ការសន្ទនាដែលពាក់ព័ន្ធជាក្រុមតាមរូបភាព
- **តួអត្ថបទផ្ទុកយឺត**៖ មានតែតួអត្ថបទនៃសំណើដែលបានជ្រើសប៉ុណ្ណោះត្រូវបានបង្កើតក្នុងផ្ទាំងព័ត៌មានលម្អិត (ជៀសវាងការបង្ហាញតួអត្ថបទ 1000 × 1MB)

## §4 មុខងារដែលយល់ដឹងអំពី LLM

### 4.1 កម្មវិធីកំណត់ប្រភេទ (`src/mitm/inspector/kindDetector.ts`)

ចាត់ថ្នាក់សំណើនីមួយៗជា `"llm"`, `"app"` ឬ `"unknown"` ដោយប្រើសញ្ញា 4 ប្រភេទ៖

1. **បញ្ជីម៉ាស៊ីនមេ** — ឈ្មោះម៉ាស៊ីនមេ LLM API ដែលស្គាល់ប្រហែល 18 (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot ជាដើម)
2. **លំនាំផ្លូវ** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` ជាដើម
3. **ទម្រង់តួសំណើ** — រកឃើញវាល `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **តម្រុយពី user-agent** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` នៅក្នុងខ្សែអក្សរ UA

ម៉ាស៊ីនមេផ្ទាល់ខ្លួនដែលបានបន្ថែមតាមរយៈ Mode 2 ទទួលតម្លៃ `kind` របស់ពួកវាពីការបញ្ចូលក្នុងសំណុំបែបបទ (តម្លៃលំនាំដើមគឺ `"custom"`)។

### 4.2 កម្មវិធីបញ្ចូល SSE (`src/mitm/inspector/sseMerger.ts`)

**ការអនុវត្ត clean-room ដោយឯករាជ្យ។** ការញែកព្រឹត្តិការណ៍អនុវត្តតាម
[ក្បួនដោះស្រាយព្រឹត្តិការណ៍ដែលផ្ញើពីម៉ាស៊ីនមេរបស់ WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
ខណៈដែលការស្ថាបនាឡើងវិញអនុវត្តតាមគ្រោងការណ៍ស្ទ្រីមសាធារណៈរបស់ [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) និង
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)។

ស្ថាបនាសារចុងក្រោយរបស់ជំនួយការឡើងវិញពីព្រឹត្តិការណ៍ delta SSE ដើម៖

- **Anthropic**: ប្រមូលផ្តុំ `content_block_delta` តាមលិបិក្រម; គ្រប់គ្រង `text_delta`, `input_json_delta` (ការហៅឧបករណ៍), `thinking_delta`
- **OpenAI**: ប្រមូលផ្តុំជម្រើស/ការហៅឧបករណ៍របស់ Chat Completions និងធាតុលទ្ធផលរបស់ Responses API
  តាមលិបិក្រម
- **Gemini**: ប្រមូលផ្តុំ `candidates[i].content.parts`
- **មិនស្គាល់**: ត្រឡប់ព្រឹត្តិការណ៍ដើមដូចដែលមាន

ផ្ទាំង Response បង្ហាញប៊ូតុងបិទបើក៖ **"ព្រឹត្តិការណ៍ដើម ↔ បានបញ្ចូល"**។

### 4.3 កម្មវិធីធ្វើឱ្យការសន្ទនាមានទម្រង់ស្តង់ដារ (`src/mitm/inspector/conversationNormalizer.ts`)

**ការអនុវត្ត clean-room ដោយឯករាជ្យ។** ការធ្វើឱ្យមានទម្រង់ស្តង់ដារត្រូវបានកំណត់ដោយកិច្ចសន្យា black-box
ក្នុងមូលដ្ឋាន និងគ្រោងការណ៍សារសាធារណៈរបស់ OpenAI, Anthropic និង Gemini; មិនមានការប្រើប្រាស់
កូដប្រភពនៃការអនុវត្តពី upstream ទេ។

បម្លែងទម្រង់សាររបស់ OpenAI, Anthropic និង Gemini ទៅជា `NormalizedConversation` តែមួយ មុនពេលបង្ហាញ៖

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // សារ / ខ្លឹមសារ / prompt ពីតួសំណើ
  response: NormalizedTurn[]; // ការឆ្លើយតបរបស់ជំនួយការ (បានបញ្ចូលតាមរយៈ sseMerger)
  contextKey: string | null; // ស្នាមម្រាមដៃ SHA-256 របស់ system-prompt
}
```

ប្រភេទប្លុក៖ `text`, `tool_use`, `tool_result`។ ផ្ទាំង Conversation ប្រើទម្រង់នេះដោយមិនគិតពីអ្នកផ្តល់សេវា។

### 4.4 ការដាក់ពណ៌តាម context key (`src/mitm/inspector/contextKey.ts`)

- គណនា `SHA-256` នៃ system prompt (សារ `role:system` ដំបូង ឬវាល `system` ឬ `systemInstruction` របស់ Gemini)
- ត្រឡប់បុព្វបទ hex ប្រវែង 12 តួអក្សរ (`"a3f9c2..."`)
- ផ្នែក frontend ផ្គូផ្គង key ទៅពណ៌ HSL ដែលកំណត់បានជាក់លាក់ សម្រាប់របារស៊ុមខាងឆ្វេង
- **តម្រង "បរិបទដូចគ្នា"**៖ ការចុចលើ chip `ctx #a3f` នឹងបន្ថែមតម្រង ដើម្បីបង្ហាញតែសំណើដែលមានស្នាមម្រាមដៃដូចគ្នា

វាធ្វើឱ្យងាយស្រួលសម្គាល់ដោយមើលឃើញនូវ "បុគ្គលិកលក្ខណៈ" ឬកិច្ចការផ្សេងៗ ដែលកំពុងដំណើរការក្នុងវគ្គ agent តែមួយ។

### 4.5 ការស្រង់ metadata របស់ LLM

សម្រាប់សំណើ LLM ផ្ទាំង LLM Details ស្រង់ព័ត៌មានដូចខាងក្រោម៖

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // ពីតួសំណើ ឬការឆ្លើយតប
  messages: number; // ចំនួនវេន
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true ប្រសិនបើជាការឆ្លើយតប SSE
  mappedTo: string | null; // header x-omniroute-mapped
  costEstimateUsd: number | null; // តម្លៃប៉ាន់ស្មានផ្អែកលើតម្លៃរបស់ OmniRoute
}
```

### 4.6 តម្រងសំណើកំពុងដំណើរការផ្ទាល់

វាល `status` របស់សំណើគឺ `number | "in-flight" | "error"` — ធាតុមួយត្រូវបាន
បញ្ចូលជា `"in-flight"` ភ្លាមៗនៅពេលសំណើចាប់ផ្តើម និងត្រូវបាន **ធ្វើបច្ចុប្បន្នភាពនៅទីតាំងដដែល**
នៅពេលការឆ្លើយតប (ឬកំហុស) មកដល់។ ប៊ូតុងបិទបើក **"ផ្ទាល់"** របស់របារឧបករណ៍
(`liveOnly`, i18n key `trafficInspector.liveOnly`) កំណត់ឱ្យបញ្ជីបង្ហាញតែធាតុ
ដែលមាន `status === "in-flight"` ដើម្បីឱ្យអ្នកអាចតាមដានការតភ្ជាប់ដែលបើកចំហក្នុងពេលជាក់ស្តែង។

តម្រងនេះជាលក្ខខណ្ឌវិនិច្ឆ័យសុទ្ធសាធនៅផ្នែក client ក្នុង
`src/lib/inspector/matchesTrafficFilter.ts`៖

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

ស្ថានភាពប៊ូតុងបិទបើកស្ថិតនៅក្នុង `useTrafficFilters` (hooks របស់ផ្ទាំងគ្រប់គ្រង inspector) និង
រួមបញ្ចូលជាមួយតម្រងផ្សេងទៀត (profile, host, agent, source, status, context)។

### 4.7 ការកំណត់ប្រភពដំណើរការ (Linux)

នៅលើ Linux សំណើដែលបានស្ទាក់ចាប់នីមួយៗអាចត្រូវបានកំណត់ថាមកពី **ដំណើរការមូលដ្ឋានដែលបានផ្តួចផ្តើម
វា**។ វាលជាជម្រើសពីរត្រូវបានបន្ថែមទៅ `InterceptedRequest`៖

```ts
pid?: number;          // លេខសម្គាល់ដំណើរការដែលជាប្រភព (សម្រាប់តែ Linux)
processName?: string;  // ឈ្មោះដំណើរការដែលជាប្រភព (សម្រាប់តែ Linux)
```

`src/mitm/inspector/processAttribution.ts` ផ្គូផ្គងច្រកបណ្តោះអាសន្នរបស់ _client_
នៃការតភ្ជាប់ទៅ PID + ឈ្មោះ ដោយ៖

1. អាន `/proc/net/tcp` និង `/proc/net/tcp6` ដើម្បីស្វែងរក inode របស់ socket សម្រាប់
   ច្រកនោះ (`parseProcNetTcpForInode` ដែលជាកម្មវិធីញែកសុទ្ធសាធ និងអាចសាកល្បងជាមួយ fixture)។
2. ស្កេន `/proc/<pid>/fd/` ដើម្បីរក symlink ទៅកាន់ `socket:[<inode>]`។
3. អានឈ្មោះដំណើរការពី `/proc/<pid>/comm`។

ឃ្លាំងសម្ងាត់ TTL រយៈពេល 1 វិនាទី កំណត់បន្ទុកចំណាយនៃការស្កេន procfs នៅពេលមានបន្ទុកខ្ពស់។ ការកំណត់ប្រភពនេះជា
**ការខិតខំប្រឹងប្រែងតាមលទ្ធភាព** — កំហុសណាមួយនឹងផ្តល់លទ្ធផលជា `null` ហើយមិនរារាំងការចាប់យកឡើយ។ នៅលើ
macOS/Windows មុខងារនេះត្រឡប់ `null` (stub; ការគាំទ្រ `lsof`/`GetExtendedTcpTable`
នឹងត្រូវអនុវត្តជាបន្តបន្ទាប់)។

## §5 សម័យ

### 5.1 ការថតសម័យ

1. ចុច **"● ថតសម័យ"** ក្នុងរបារឧបករណ៍ → បញ្ចូលឈ្មោះមួយ (មិនបង្ខំ)
2. ការបង្ហាញទិន្នន័យបន្តផ្ទាល់នៅតែដំណើរការធម្មតា; សូចនាករពណ៌ក្រហមលោតបង្ហាញ `◉ កំពុងថត · <ឈ្មោះ> · 00:42 · សំណើ 23`
3. ចុច **"⏹ បញ្ឈប់"** → រូបថតស្ថានភាពរបស់សម័យត្រូវបានរក្សាទុកទៅក្នុង `inspector_sessions` + `inspector_session_requests`

### 5.2 ការមើលសម័យដែលបានថត

បញ្ជីទម្លាក់ចុះ **សម័យ** ក្នុងរបារឧបករណ៍រាយសម័យដែលបានរក្សាទុក។ នៅពេលជ្រើសរើសសម័យមួយ៖

- ផ្ទុករូបថតស្ថានភាពរបស់សម័យ (ស្ថានភាពថេរ)
- បដាមួយបង្ហាញ៖ `កំពុងមើលសម័យដែលបានថត "<ឈ្មោះ>" — [ត្រឡប់ទៅទិន្នន័យបន្តផ្ទាល់]`
- ផ្ទាំងស្ថិតិអាចប្រើបានជាមួយទិន្នន័យសរុបរបស់ Recharts

### 5.3 ទម្រង់នាំចេញ

សម័យនីមួយៗអាចត្រូវបាននាំចេញជាទម្រង់៖

| ទម្រង់                     | ការប្រើប្រាស់                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------- |
| **HAR** (HTTP Archive 1.2) | អាចប្រើជាមួយ Chrome DevTools, Charles និង Fiddler — នាំចូលសម្រាប់ការវិភាគក្រៅបណ្ដាញ |
| **JSONL**                  | `InterceptedRequest` មួយក្នុងមួយបន្ទាត់ — អាចប្រើជាមួយទម្រង់ `llm-interceptor`      |

### ដែនកំណត់ដែលបានដឹង

- **របៀប proxy ទូទាំងប្រព័ន្ធ** ប៉ះពាល់ដល់កម្មវិធីទាំងអស់នៅលើម៉ាស៊ីន រួមទាំងកម្មវិធី VPN និង SSO។ ត្រូវប្រើវាជានិច្ចជាមួយកម្មវិធីកំណត់ពេលបិទដោយស្វ័យប្រវត្តិ។ កុំប្រើវានៅលើម៉ាស៊ីនដែលប្រើរួមគ្នា។
- **CONNECT tunnel HTTPS**៖ របៀបទី 3 (HTTP_PROXY) ចាប់យកតែ metadata របស់ tunnel សម្រាប់គោលដៅ HTTPS ប៉ុណ្ណោះ ហើយមិនដែលឌិគ្រីបពួកវាទេ។ នេះគឺជាការរចនាដោយចេតនា — ការឌិគ្រីបនឹងតម្រូវឱ្យ client ទាំងអស់ទុកចិត្តវិញ្ញាបនបត្រ MITM ដូច្នេះ listener រក្សា HTTPS ឱ្យនៅតែមានការអ៊ិនគ្រីបពីចុងដល់ចុង។ ប្រើ AgentBridge, Custom Hosts ឬការឌិគ្រីប TPROXY នៅពេលអ្នកត្រូវការតួទិន្នន័យ HTTPS។
- **ខ្សែអក្សរដែលបានសរសេរថេរនៅក្នុងសមាសភាគមួយចំនួន**៖ សមាសភាគ UI មួយចំនួន (F7/F8) មានខ្សែអក្សរដែលបានសរសេរថេរមួយចំនួនតូច ដែលមិនទាន់ត្រូវបានគ្របដណ្តប់ដោយសោ i18n នៅឡើយ។ ពួកវាត្រូវបានកត់ត្រាជាដែនកំណត់ដែលបានដឹងនៅក្នុងរបាយការណ៍ចន្លោះខ្វះខាត i18n; ពួកវានឹងត្រូវបានផ្ទេរនៅក្នុងវគ្គបន្ទាប់។ ខ្សែអក្សរដែលរងផលប៉ះពាល់គឺជាស្លាកតុបតែង UI ដែលមិនតម្រូវឱ្យបកប្រែសម្រាប់ការប្រើប្រាស់មុខងារនោះទេ។

1. ពិនិត្យមើលថាម៉ាស៊ីនមេនៅតែដំណើរការ៖ `GET /api/tools/traffic-inspector/capture-modes`
2. ផ្ទុកទំព័រឡើងវិញ — WebSocket នឹងភ្ជាប់ឡើងវិញ និងទទួលបានស្នាដៃចម្លងស្ថានភាពថ្មី
3. ប្រសិនបើម៉ាស៊ីនមេត្រូវបានចាប់ផ្តើមឡើងវិញ អង្គចងចាំបណ្ដោះអាសន្នក្នុងអង្គចងចាំត្រូវបានសម្អាត — ធាតុចាស់ៗបានបាត់ លុះត្រាតែសម័យមួយត្រូវបានថតទុក

### ការប៉ះទង្គិចច្រក 8080

ប្រសិនបើមុខងារ HTTP_PROXY មិនអាចចាប់ផ្តើមបាន៖

```bash
lsof -i :8080    # ស្វែងរកដំណើរការ
```

ប្ដូរច្រក៖

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### ប្រូកស៊ីប្រព័ន្ធមិនត្រូវបានត្រឡប់ទៅស្ថានភាពដើម

ប្រសិនបើ OmniRoute គាំង ខណៈដែលមុខងារប្រូកស៊ីទូទាំងប្រព័ន្ធកំពុងសកម្ម៖

**macOS៖**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME)៖**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows៖**

```cmd
netsh winhttp reset proxy
```

ផ្ទាំងគ្រប់គ្រងក៏នឹងផ្តល់ជម្រើស "ត្រឡប់ប្រូកស៊ីប្រព័ន្ធទៅស្ថានភាពដើម" នៅពេលផ្ទុកលើកក្រោយផងដែរ ប្រសិនបើវារកឃើញថាស្ថានភាព DB បង្ហាញថាប្រូកស៊ីធ្លាប់សកម្ម។

### អង្គចងចាំបណ្ដោះអាសន្នពេញ

នៅពេលអង្គចងចាំបណ្ដោះអាសន្នឈានដល់ `INSPECTOR_BUFFER_SIZE` (លំនាំដើម 1000) ធាតុថ្មីនឹងជំនួសធាតុចាស់បំផុត។ ប្រសិនបើសំណើសំខាន់ៗកំពុងបាត់បង់៖

- បង្កើន `INSPECTOR_BUFFER_SIZE` (ឧ. 5000) — ប្រើអង្គចងចាំកាន់តែច្រើន ដើម្បីរក្សាទិន្នន័យបានយូរ
- ថតសម័យមួយ ដើម្បីរក្សាទុកចន្លោះពេលពាក់ព័ន្ធទៅក្នុង DB
