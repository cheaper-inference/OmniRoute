## ហេតុអ្វីត្រូវមានកញ្ចប់ Workspace ដាច់ដោយឡែក?

`open-sse/` គឺជា **workspace ឯករាជ្យ** មួយនៅក្នុង monorepo របស់ OmniRoute ដោយសារហេតុផលជាច្រើន៖

1. **ការប្រើប្រាស់ឡើងវិញ** — `open-sse` ត្រូវបានចេញផ្សាយជា `@omniroute/open-sse` នៅលើ npm ដូច្នេះគម្រោងផ្សេងទៀតអាចប្រើវាដោយឯករាជ្យបាន
2. **ព្រំដែនច្បាស់លាស់** — ម៉ាស៊ីនស្ទ្រីមត្រូវបានផ្តាច់ចេញពីស្រទាប់ UI/DB ដែលជាក់លាក់សម្រាប់ OmniRoute
3. **ប្រសិទ្ធភាព** — ម៉ាស៊ីននេះមិនមាន dependency លើ Next.js ទេ ដែលអនុញ្ញាតឱ្យចាប់ផ្ដើមពីស្ថានភាពត្រជាក់បានលឿនជាងមុនក្នុងបរិបទ CLI/serverless
4. **ការគ្រប់គ្រងកំណែ** — `open-sse` អាចចេញកំណែតាមកាលវិភាគរបស់ខ្លួន

```json
// package.json
"workspaces": ["open-sse"]
```

   (route របស់ Next.js)        └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. បកប្រែ    │   បម្លែងទម្រង់ (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. ប្រតិបត្តិ │   កម្មវិធីប្រតិបត្តិ provider, HTTP, retry, breaker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. ស្ទ្រីម    │   ការបម្លែង SSE, backpressure

### ដំណាក់កាលទី 1៖ កំណត់ផ្លូវ (services/combo.ts)

**ចំណុចចូល**៖ `handleComboChat()` នៅក្នុង `services/combo.ts`

ដោះស្រាយសំណើទៅជា tuple ជាក់លាក់មួយ `(provider, model, account, credentials)`៖

- ស្វែងរក combo តាម ID (ឬបង្កើត combo និម្មិតសម្រាប់ model `auto/*`)
- អនុវត្តយុទ្ធសាស្ត្រកំណត់ផ្លូវ (អាទិភាព ទម្ងន់ round-robin ជាដើម)
- ច្រោះ provider ដែលមិនមានស្ថានភាពល្អចេញ (circuit breaker)
- ជ្រើសរើសគោលដៅបន្ទាប់ដែលអាចប្រើបាន

សម្រាប់ model `auto/*` ដំណាក់កាលនេះក៏៖

- ដំណើរការអាល់ហ្គរីធម៍ **ដាក់ពិន្ទុដោយផ្អែកលើកត្តា 16** (`services/autoCombo/`)
- ជ្រើសរើសគូ `provider+model` ដោយផ្អែកលើស្ថានភាព ប្រសិទ្ធភាព ថ្លៃចំណាយ latency ជាដើម

### ដំណាក់កាលទី 2៖ បកប្រែ (translator/)

ប្រសិនបើទម្រង់ប្រភព (ឧទាហរណ៍ OpenAI) ខុសពីទម្រង់គោលដៅ (ឧទាហរណ៍ Claude) សំណើនឹងត្រូវបាន **បកប្រែ**៖

- System prompt → system message
- និយមន័យឧបករណ៍ → ទម្រង់ឧបករណ៍ជាក់លាក់របស់ provider
- ប៉ារ៉ាម៉ែត្រ reasoning/thinking → តម្លៃសមមូលជាក់លាក់របស់ provider
- ធ្វើឱ្យ message role មានលក្ខណៈស្តង់ដារ (`developer` → `system` សម្រាប់ប្រព័ន្ធដែលមិនមែនជា OpenAI)

`translator/index.ts` បង្ហាញមុខងារខាងក្រោម៖

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### ដំណាក់កាលទី 3៖ ប្រតិបត្តិ (executors/)

**ចំណុចចូល**៖ `getExecutor(providerId).execute(request, options)`

provider ទាំងអស់ប្រើ `DefaultExecutor` (`executors/default.ts`) តាមរយៈ fallback របស់ factory `getExecutor()`។ កម្មវិធីប្រតិបត្តិនេះ៖

- បង្កើត URL ខ្សែខាងលើ (`buildUrl()`)
- បន្ថែម header ជាក់លាក់របស់ provider (`buildHeaders()`)
- បម្លែង request body (`transformRequest()`)
- ផ្ញើសំណើ HTTP ជាមួយ retry + exponential backoff
- ដោះស្រាយការធ្វើឱ្យ auth ស្រស់ឡើងវិញប្រសិនបើចាំបាច់ (provider ដែលប្រើ OAuth)

កម្មវិធីប្រតិបត្តិទាំងអស់ពង្រីកពី `BaseExecutor` (`executors/base.ts`, 1170 LOC) ដែលផ្ដល់នូវ៖

- តក្កវិជ្ជា retry រួម
- ការរួមបញ្ចូល proxy
- ការរួមបញ្ចូល circuit breaker
- hook សម្រាប់កត់ត្រាការប្រើប្រាស់

### ដំណាក់កាលទី 4៖ ស្ទ្រីម (utils/stream.ts)

  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);

  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;

    }

}

អ្នកផ្តល់សេវាត្រូវបានដោះស្រាយតាមរយៈ `getExecutor(providerId)` ដែលត្រឡប់អ្នកប្រតិបត្តិដែលបានកំណត់រចនាសម្ព័ន្ធ។ អ្នកផ្តល់សេវា OpenAI/Anthropic-compatible ប្រើ `DefaultExecutor` (`executors/default.ts`) ។ អាកប្បកិរិយាជាក់លាក់របស់អ្នកផ្តល់សេវា ( URL មូលដ្ឋាន បឋមកថាភាពត្រឹមត្រូវ កំណែ API ) ត្រូវបានកំណត់រចនាសម្ព័ន្ធជា `open-sse/config/providers/` ខណៈពេលដែលការបំប្លែងតួសំណើត្រូវបានគ្រប់គ្រងជា `open-sse/translator/`។

**URL ផ្ទាល់ខ្លួន** ត្រូវបានកំណត់តាមរយៈការកំណត់រចនាសម្ព័ន្ធអ្នកផ្តល់សេវា៖

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**ការផ្ទៀងផ្ទាត់ផ្ទាល់ខ្លួន** ត្រូវបានគ្រប់គ្រងតាមរយៈការកំណត់ការផ្ទៀងផ្ទាត់ភាពត្រឹមត្រូវរបស់អ្នកផ្តល់សេវា (API key, OAuth, header profiles)។

**រាងកាយសំណើផ្ទាល់ខ្លួន** ការបំប្លែង (ឧទាហរណ៍ Anthropic បំបែក `system` ពី `messages`) ត្រូវបានចុះឈ្មោះអ្នកផ្តល់សេវាក្នុង `open-sse/translator/`។

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

ដំណោះស្រាយឆ្លងកាត់ `ExecutorRegistry` (`executors/registry.ts`): រាល់ប្រតិបត្តិករឯកទេសត្រូវបានប្រកាសនៅក្នុងតារាងដែលភ្ជាប់មកជាមួយនៃ `executors/index.ts` និងចុះឈ្មោះតាមរយៈ `registerExecutor(alias, instance)` នៅពេលផ្ទុកម៉ូឌុល។ `getExecutor()` ពិគ្រោះជាមួយបញ្ជីឈ្មោះ ហើយត្រលប់ទៅ `DefaultExecutor` ដែលត្រូវបានចងចាំសម្រាប់អ្នកផ្តល់សេវាណាមួយដោយគ្មានធាតុឯកទេស។ ការគូសផែនទីប្រតិបត្តិករ → ឈ្មោះក្លែងក្លាយពេញលេញត្រូវបានកំណត់លក្ខណៈដោយការធ្វើតេស្តមាស `tests/unit/executor-map-golden.test.ts`។

## កម្មវិធីបកប្រែ

បកប្រែរវាង **ទម្រង់ 3**៖ OpenAI, Anthropic, Gemini រួមទាំង Responses API ថ្មីផងដែរ។

### ពេលដែលការបកប្រែកើតឡើង

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

ការបកប្រែទូទៅ៖

- `OpenAI → Anthropic`៖ វាល `system` ដាច់ដោយឡែក និង header `x-api-key`
- `OpenAI → Gemini`៖ ប្រើ `contents` ជំនួសឱ្យ `messages` និង `systemInstruction`
- `OpenAI → Responses API`៖ array `input` និង state `previous_response_id`

### ករណីពិសេសដែលបានដោះស្រាយ

- role `developer` → `system` សម្រាប់ប្រព័ន្ធដែលមិនមែនជា OpenAI
- role `system` → បញ្ចូលជាមួយសាររបស់អ្នកប្រើដំបូងសម្រាប់ GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` របស់ Gemini
- `tools` → ទម្រង់ឧបករណ៍ជាក់លាក់តាម provider
- ប៉ារ៉ាម៉ែត្រសម្រាប់ការគិត (o1, Claude) → សមមូលជាក់លាក់តាម provider

## MCP Server

`open-sse/mcp-server/` អនុវត្ត server សម្រាប់ **Model Context Protocol**៖

- **ឧបករណ៍ 110** (ការគ្រប់គ្រង provider, combos, memory, cache, compression, proxy, skills, gamification, plugins, Notion, Obsidian និង corpus ក្នុងមូលដ្ឋាន)
- **មធ្យោបាយបញ្ជូន 3**៖ stdio, SSE, Streamable HTTP
- **scope 33** សម្រាប់ការផ្តល់សិទ្ធិកម្រិតលម្អិត

### ការចុះបញ្ជីឧបករណ៍

ឧបករណ៍ត្រូវបានចុះបញ្ជីជាឯកសារឯករាជ្យក្នុង `open-sse/mcp-server/tools/` ដោយឯកសារនីមួយៗ export ឈ្មោះ schema, handler និង scope៖

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### មធ្យោបាយបញ្ជូន

```ts
// stdio (ការប្រើប្រាស់ CLI)
startMcpStdio(server);

// SSE (ការផ្សាយជាបន្តបន្ទាប់ផ្អែកលើ HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP ទំនើប)
startMcpStreamable(server, port);
```

### ការផ្តល់សិទ្ធិ

រាល់ការហៅឧបករណ៍ទាំងអស់ឆ្លងកាត់ការត្រួតពិនិត្យ scope (`open-sse/mcp-server/auth/`)៖

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## កម្មវិធីបំប្លែង

`open-sse/transformer/` បំប្លែងរវាងទម្រង់ **Chat Completions** និង **Responses API**។

### ហេតុអ្វីត្រូវការកម្មវិធីបំប្លែងដាច់ដោយឡែក?

Responses API គឺជាទម្រង់ថ្មីរបស់ OpenAI ដែលមាន **ការសន្ទនារក្សាទុក state** (`previous_response_id`)។ នៅពេល client ផ្ញើសំណើ Responses មក OmniRoute នឹង៖

1. បំប្លែង Responses → Chat Completions នៅខាងក្នុង
2. ផ្ញើទៅ provider (provider ណាមួយដែលគាំទ្រ Chat Completions)
3. បំប្លែង response ត្រឡប់ទៅជាទម្រង់ Responses
4. ផ្សាយ response ដែលបានបំប្លែងទៅ client ជាបន្តបន្ទាប់

កម្មវិធីបំប្លែង (`transformer/responsesTransformer.ts`) ផ្តល់ជូន៖

```ts
createResponsesApiTransformStream(): TransformStream
```

វាដោះស្រាយ៖

- event `response.output_item.added`
- event `response.output_text.delta`
- event `response.completed`
- ការផ្គូផ្គងការហៅឧបករណ៍ (`function_call` ↔ `tool_calls`)

## ការបន្ថែមសមាសភាគថ្មី

### ការបន្ថែមសេវាថ្មី

1. បង្កើត `open-sse/services/[serviceName].ts` ដែលមានការទទួលខុសត្រូវផ្តោតច្បាស់លាស់
2. Export អនុគមន៍ handler ចម្បង និង constants ណាមួយ
3. បន្ថែមការធ្វើតេស្តឯកតានៅក្នុង `tests/unit/services/[serviceName].test.mjs`
4. បញ្ចូលទៅក្នុងខ្សែដំណើរការសំណើនៅក្នុង `handlers/chatCore.ts` (ប្រសិនបើពាក់ព័ន្ធនឹងការកំណត់ផ្លូវ)
5. ធ្វើបច្ចុប្បន្នភាពតក្កវិជ្ជាកំណត់ផ្លូវនៅក្នុង `combo.ts` ប្រសិនបើសេវាប៉ះពាល់ដល់ការជ្រើសរើសគោលដៅ
6. ចងក្រងជាឯកសារនៅក្នុងឯកសារនេះ

### ការបន្ថែម Executor ថ្មី

1. បង្កើត `open-sse/executors/[provider].ts` ដែលពង្រីកពី `BaseExecutor`
2. ចុះឈ្មោះនៅក្នុង `config/providerRegistry.ts`
3. បន្ថែមទៅ factory របស់ `executors/index.ts`
4. បន្ថែមការធ្វើតេស្តឯកតាសម្រាប់ executor
5. ចងក្រងជាឯកសារនៅក្នុង `docs/architecture/ARCHITECTURE.md`

### ការបន្ថែមឧបករណ៍ MCP ថ្មី

1. បង្កើត ឬធ្វើបច្ចុប្បន្នភាព `open-sse/mcp-server/tools/[category]Tools.ts`
2. កំណត់ Zod schema សម្រាប់ inputs
3. ចុះឈ្មោះឧបករណ៍នៅក្នុង `mcp-server/index.ts`
4. បន្ថែមទៅម៉ាទ្រីសវិសាលភាពនៅក្នុង `mcp-server/auth/`
5. បន្ថែមការធ្វើតេស្តឯកតា
