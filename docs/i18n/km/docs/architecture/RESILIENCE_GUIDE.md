## 1. Circuit Breaker កម្រិត Provider

**វិសាលភាព:** ទាំងមូល provider (ឧ. `glm`, `openai`, `anthropic`)។

**គោលបំណង:** បញ្ឈប់ការផ្ញើ traffic ទៅកាន់ provider ដែលបរាជ័យជាប់ៗគ្នានៅកម្រិត upstream/service ។

**ការអនុវត្ត:**

- ថ្នាក់សំខាន់: `src/shared/utils/circuitBreaker.ts`
- ការភ្ជាប់ (wiring): `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API ស្ថានភាព: `GET /api/monitoring/health`
- API កំណត់ឡើងវិញ: `POST /api/resilience/reset`
- Wrapper: `open-sse/services/accountFallback.ts`
- តារាង DB: `domain_circuit_breakers`

**ស្ថានភាព:**

- `CLOSED` — អនុញ្ញាត traffic ធម្មតា
- `DEGRADED` — នៅតែអនុញ្ញាត traffic ប៉ុន្តែកំពុងតាមដានការបរាជ័យរបស់ provider ដែលកើនឡើង; ត្រឡប់ទៅ `CLOSED` នៅពេលមានការជោគជ័យគ្រប់គ្រាន់ នៅពេល connection test ត្រឹមត្រូវ ឬក្រោយពីការរង់ចាំ `OPEN` យូរបំផុតសម្រាប់ប្រភេទបរាជ័យចុងក្រោយ (តម្លៃ `cooldownByKind` របស់វា បើមិនមាន `resetTimeout` × `maxBackoffMultiplier` យ៉ាងតិចមួយ cooldown) ដោយគ្មានការបរាជ័យថ្មី
- `OPEN` — provider ត្រូវបានបិទជាបណ្តោះអាសន្ន; combo routing រំលងវា
- `HALF_OPEN` — reset timeout ផុតកំណត់ហើយ; អនុញ្ញាតសំណើ probe

**តម្លៃលំនាំដើមដែលកំណត់បាន (`open-sse/config/constants.ts`, បង្ហាញក្នុង Dashboard → Settings → Resilience):**

| ថ្នាក់  | ចូល DEGRADED នៅ | ចូល OPEN នៅ  | Reset timeout |
| ------- | --------------- | ------------ | ------------- |
| OAuth   | បរាជ័យ 5 ដង     | បរាជ័យ 8 ដង  | 60s           |
| API-key | បរាជ័យ 7 ដង     | បរាជ័យ 12 ដង | 30s           |
| Local   | គណនាតាម         | បរាជ័យ 2 ដង  | 15s           |

`degradationThreshold` គ្រប់គ្រងពេលដែល provider ចូល `DEGRADED`; `failureThreshold` គ្រប់គ្រងពេលដែលវា open ហើយត្រូវបានរំលង។ Profile របស់ Local provider មិនទាន់បានបង្ហាញនៅលើទំព័រការកំណត់ Resilience នៅឡើយទេ។

**កូដ trip:** តែ status កម្រិត provider `[408, 500, 502, 503, 504]` ប៉ុណ្ណោះ។ កុំ trip ចំពោះកំហុសកម្រិតគណនី (ភាគច្រើន 401/403/429 — ពួកនោះស្ថិតក្រោម cooldown ឬ lockout)។

**ការស្តារឡើងវិញបែប lazy:** នៅពេល `OPEN` ផុតកំណត់ `getStatus()`, `canExecute()`, `getRetryAfterMs()` refresh ស្ថានភាពទៅ `HALF_OPEN` ។ ការអានដដែលទាំងនេះ (និងការបរាជ័យបន្ទាប់) បន្សាប `DEGRADED` ដែល stale ឱ្យត្រឡប់ទៅ `CLOSED` វិញ។ មិនត្រូវការ background timer ទេ។

### Provider Cooldown សកលជាជម្រើស opt-in (window gate)

ស្រទាប់ទីបួន ជា **opt-in** (`PROVIDER_COOLDOWN_ENABLED`, លំនាំដើម **បិទ**) រក្សាទុកអង្គចងចាំឆ្លងសំណើ (cross-request) នៃ provider ដែលបរាជ័យ ក្នុង
`open-sse/services/providerCooldownTracker.ts` ដែលការកំណត់គោលដៅ combo (combo target resolution) យកមកពិគ្រោះ ដូច្នេះសំណើ combo ជាប់ៗគ្នាឈប់ walk ឡើងវិញលើ provider ដែលទើបតែបរាជ័យ។ ធាតុកម្រិត provider គោរពតាម window gate របស់ `PROVIDER_PROFILES`:

| Profile | trip ក្រោយពេល (`providerFailureThreshold`) | ក្នុងរយៈពេល (`providerFailureWindowMs`) | cool រយៈពេល (`providerCooldownMs`) |
| ------- | -----------------------------------------: | --------------------------------------: | ---------------------------------: |
| OAuth   |                                       `10` |                                 `15min` |                             `5min` |
| API key |                                       `15` |                                 `30min` |                            `10min` |

ក្រោម threshold នេះ provider **មិន** ត្រូវបានចាត់ទុកថាកំពុងស្ថិតក្នុង cooldown ទេ; ការជោគជ័យមួយសម្អាត window ។ ធាតុកម្រិត connection (`provider:connectionId`) រក្សា backoff អិចស្បូណង់ស្យែល `minRetryCooldownMs → maxRetryCooldownMs` ជំនួសវិញ។ ការ override:
`OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}` ។
ការការពារ regression: `tests/unit/provider-cooldown-window-gate.test.ts` ។

## 2. ការតភ្ជាប់ Cooldown

**វិសាលភាព៖** អ្នកផ្តល់សេវាតែមួយ connection/account/key.

**គោលបំណង៖** រំលងសោមិនល្អមួយ ខណៈពេលដែលការតភ្ជាប់ផ្សេងទៀតសម្រាប់អ្នកផ្តល់សេវាដូចគ្នាបន្តបម្រើ។

**ការអនុវត្ត៖**

- សម្គាល់មិនអាចប្រើបាន៖ `src/sse/services/auth.ts::markAccountUnavailable()`
- ការជ្រើសរើស៖ `getProviderCredentials*` ក្នុងឯកសារដូចគ្នា។
- Cooldown Calc: `open-sse/services/accountFallback.ts::checkFallbackError()`
- ការកំណត់៖ `src/lib/resilience/settings.ts`

**វាលក្នុងមួយការតភ្ជាប់៖**

- `rateLimitedUntil` — ត្រាពេលវេលារហូតដល់ការចុះត្រជាក់ផុតកំណត់
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — អិចស្ប៉ូណង់ស្យែល backoff counter

**ការចុះត្រជាក់លំនាំដើម៖**

- មូលដ្ឋាន OAuth : 5s
- មូលដ្ឋានគន្លឹះ API៖ 3s
- API-key 429៖ ចូលចិត្ត `Retry-After`/reset headers/parseable កំណត់អត្ថបទឡើងវិញ
- ថយក្រោយ៖ `baseCooldownMs * 2 ** failureIndex`

**ការពន្យាពេលព្យាយាមម្តងទៀតរបស់អ្នកផ្តល់សេវា។** ទំព័រលម្អិតអ្នកផ្តល់សេវាមាន ក** ព្យាយាមពន្យាពេលម្តងទៀត** ជ្រើសរើស (ស្វ័យប្រវត្តិ ១៥ វិនាទីរហូតដល់ ១ ម៉ោង) ។ វារក្សាទុក `resilienceSettings.providerQuotaOverrides[<providerId>].rateLimitCooldownSeconds` (1-21600 តាមរយៈ `PATCH /api/resilience`) ។ នៅពេលដែលកំហុសកម្រិតអត្រាមិនមានព័ត៌មានជំនួយការព្យាយាមឡើងវិញ តម្លៃនោះជំនួសការថយក្រោយដែលបានកំណត់សម្រាប់អ្នកផ្តល់សេវា ហើយកំណត់ `backoffLevel` ឡើងវិញទៅ 0 (`open-sse/services/rotationConfig.ts::overrideFor`)។ អាទិភាពសម្រាប់កំហុសដែលមានកម្រិតអត្រា ខ្ពស់បំផុតដំបូងបង្អស់៖ ការណែនាំអំពីការព្យាយាមឡើងវិញនៅលើចរន្ត បន្ទាប់មក `providerSpecificData.rotationOverrides.rateLimitResetSeconds` ក្នុងមួយការតភ្ជាប់ បន្ទាប់មកការពន្យាពេលនៃការព្យាយាមម្តងទៀតរបស់អ្នកផ្តល់សេវា បន្ទាប់មក env `OMNIROUTE_ROTATION_RATE_LIMIT_RESET_SECONDS` បន្ទាប់មកការបិទការធ្វើមាត្រដ្ឋាន។ ដកវាលដោយស្វ័យប្រវត្តិ។ វាប៉ះពាល់តែលើហេតុផលកំណត់អត្រាប៉ុណ្ណោះ មិនដែលស្ថានភាពស្ថានីយទេ។

**ឆ្មាំការពារហ្វូងសត្វ៖** ការពារការបរាជ័យក្នុងពេលដំណាលគ្នាពីការ cooldown លើសពីការពង្រីក ឬ `backoffLevel` កើនឡើងទ្វេដង។

**Concurrency-limit 429s មិនឡើងលើជណ្ដើរថយក្រោយទេ។** `429` ដែលរាងកាយរាយការណ៍ដែនកំណត់ស្របគ្នា ("សំណើស្របគ្នាច្រើនពេក", "ដែនកំណត់ស្របគ្នា", "ដែនកំណត់សំណើប៉ារ៉ាឡែល", GLM `并发数过高`) មានន័យថាគណនីមានសុខភាពល្អ ប៉ុន្តែរវល់។ `checkFallbackError()` ត្រឡប់ហេតុផល `concurrency_limited`: បរាជ័យក្នុងការតភ្ជាប់បន្ទាប់ឥឡូវនេះ ត្រជាក់វាសម្រាប់ `CONCURRENCY_LIMIT_COOLDOWN_MS` ថេរ (1s) ឬព័ត៌មានជំនួយព្យាយាមឡើងវិញ រក្សា `backoffLevel` មិនផ្លាស់ប្តូរ ហើយកំណត់ `skipProviderBreaker`។ ស្ថាប័នកូតាច្បាស់លាស់នៅតែឈ្នះ ដូច្នេះស្ថាប័នដែលត្រូវគ្នានឹងគំរូកូតានៅតែជាសាលក្រមកូតា។ ការរកឃើញ៖ `looksLikeConcurrencyLimit()` ក្នុង `src/shared/utils/classify429.ts`; សាលក្រម៖ `open-sse/services/accountFallback/concurrencyLimit429.ts`។ `classify429()` ( `FailureKind` របស់ breaker ) មិនផ្លាស់ប្តូរ ហើយនៅតែអាន `rate_limit` សម្រាប់តួទាំងនេះ។

**ស្ទ្រីមមាតិកាស្ទ្រីមមិនធ្វើឱ្យគណនីត្រជាក់ទេ។** នៅពេលដែលក្រុមឃ្លាំមើលមាតិកា (`open-sse/utils/streamHandler.ts`) បោះបង់ការផ្សាយដែលមិនបានបញ្ជូនលទ្ធផលគំរូទាន់ពេល `markAccountUnavailable()` កត់ត្រាកំហុសនៅលើការតភ្ជាប់ ប៉ុន្តែមិនបានកំណត់ការចុះត្រជាក់ទេ៖ តូបជាកម្មសិទ្ធិរបស់សំណើនោះ ដែលភាគច្រើនជាវេនហេតុផលវែងឆ្ងាយដែលមិនទាន់មានលទ្ធផលនៅឡើយ។ ប្រតិបត្តិករអាចជ្រើសរើសត្រឡប់មកវិញជាមួយ `resilienceSettings.streamStallCooldown.enabled` ( `false` លំនាំដើម) ។

**ជ្រើសរើសសញ្ញាភាពយឺតយ៉ាវសម្រាប់ការជ្រើសរើសគណនី `p2c` ។** ការប៉ុនប៉ងដែលបានបញ្ជូននីមួយៗកត់ត្រាពីពេលវេលាទៅបៃដំបូងរបស់វា និងលទ្ធផលក្នុងមួយការតភ្ជាប់ (និងសម្រាប់ការតភ្ជាប់ + គំរូ) នៅក្នុងបង្អួចរំកិលក្នុងអង្គចងចាំ៖ គំរូ 20 ចុងក្រោយក្នុងរយៈពេល 15 នាទី (`open-sse/services/connectionLatencyTracker.ts` កត់ត្រាពី `safeLogEvents()` ក្នុង `src/sse/handlers/chatHelpers.ts`) ។ នៅពេលដែល `resilienceSettings.p2cLatency.weight` លើសពី `0` (ជួរ 0-20, លំនាំដើម `0` = បិទ) `compareP2CConnections()` ក្នុង `src/sse/services/auth.ts` បន្ថែមរហូតដល់ `weight` ដល់បេក្ខជននីមួយៗនៃគូ។ ពាក់កណ្តាលនៃនោះបានមកពីភាពយឺតយ៉ាវជាសមាមាត្រទៅនឹងបេក្ខជនដែលលឿនជាងមុន (យឺតជាងពីរដងត្រូវចំណាយពេលពាក់កណ្តាលពេញ) និងពាក់កណ្តាលពីអត្រាកំហុសរំកិល។ ពាក្យនេះអនុវត្តតែនៅពេលដែលបេក្ខជនទាំងពីរមានយ៉ាងហោចណាស់ 3 គំរូ ដូច្នេះគណនីថ្មីមិនត្រូវបានពិន័យទេ ហើយពិដានរបស់វានៅតែស្ថិតនៅក្រោមការពិន័យដែលបិទដោយកូតា និងកាត់បន្ថយកូតា។ វាមិនបន្ថែមសៀគ្វីរបស់វាទេ៖ គណនីដែលបរាជ័យនៅតែត្រូវបានគ្រប់គ្រងដោយ cooldown, lockout និង breaker layers។ កំណត់វាជាមួយ `PATCH /api/resilience` `{ "p2cLatency": { "weight": 10 } }`។

**ស៊ុមហេតុផលចាប់ផ្តើមថវិកាផ្អាកមាតិកាឡើងវិញ។** គំរូហេតុផលអាចគិតបានប៉ុន្មាននាទី មុនពេលនិមិត្តសញ្ញាដែលអាចមើលឃើញដំបូងរបស់វា៖ Claude ស្ទ្រីមស៊ុម `thinking_delta` ដែលអត្ថបទនៃការគិតអាចទទេ ហើយការឆ្លើយតប API ស្ទ្រីមធាតុហេតុផលមួយបន្ទាប់ពីមួយផ្សេងទៀត។ `isReasoningProgressFrame()` (`open-sse/utils/streamReadiness.ts`) ទទួលស្គាល់ស៊ុមទាំងនេះ ហើយអ្នកឃ្លាំមើលចាប់ផ្ដើមថវិការបស់ខ្លួនម្ដងទៀតជាជាងបោះបង់វេន។ ពួកគេនៅតែមិនមែនជាគំរូលទ្ធផល ដូច្នេះវេនដែលបញ្ចប់ដោយការវែកញែកនៅតែត្រូវបានរាយការណ៍ថាទទេ ហើយវេនដែលបញ្ឈប់ការវែកញែក ហើយគ្រាន់តែបញ្ជូនចង្វាក់បេះដូងនៅតែដើរតាមអ្នកឃ្លាំមើល។

ស៊ុម `reasoningContentEvent` គោលពីររបស់Kiro ដែលមានហត្ថលេខាមិនទទេរក្សាសកម្មភាពហេតុផលនេះតាមរយៈប្រតិបត្តិករជាតំបន់ដីសណ្ត `reasoning_content` ទទេ។ ហត្ថលេខាមិនត្រូវបានបញ្ជូនបន្តទេ។ ទិន្នន័យមេតា ស៊ុមមិនពេញលេញ និងហត្ថលេខាទទេ មិនចាប់ផ្តើមថវិកាមាតិកាឡើងវិញទេ។ ការអស់ពេលស្ទ្រីមឯករាជ្យ និងការលុបចោលអតិថិជននៅតែអនុវត្ត (`open-sse/executors/kiro/reasoning.ts`) ។

**ការងើបឡើងវិញខ្ជិល៖** នៅពេលដែល `rateLimitedUntil` កន្លងផុត ការតភ្ជាប់នឹងមានសិទ្ធិម្តងទៀត។ នៅពេលប្រើដោយជោគជ័យ `clearAccountError()` សម្អាតវាលកំហុសទាំងអស់។

**វិសាលភាព៖** ការតភ្ជាប់ Claude មួយ (OAuth) ។ លក្ខណៈពិសេសទាំងពីរគឺ** ជ្រើសរើសចូលតាមការតភ្ជាប់** (កែសម្រួលការតភ្ជាប់ → Claude ផ្នែក → `lowPriorityMode` / `autoLimitReset` ក្នុង `providerSpecificData` ទាំងបិទលំនាំដើម) និងពាក្យបញ្ជា `/low-priority` និង `/limit-reset` របស់កញ្ចក់ Claude Code (កិច្ចសន្យាខ្សែដែលចាប់យកពី Claude Code 2.1.263)។

**ការអនុវត្ត៖**

- ការចាត់ថ្នាក់ការឆ្លើយតប + ម៉ាស៊ីនរបស់រដ្ឋ៖ `open-sse/services/claudeLowPriority.ts`
- កំណត់អតិថិជន status/claim ឡើងវិញ៖ `open-sse/services/claudeLimitReset.ts`
- ទំពក់ប្រតិបត្តិ (ការបញ្ចូលបឋមកថា + ការព្យាយាមគណនីដូចគ្នា): `open-sse/executors/base.ts::execute()`
- ជ្រើសរើសក្នុងការតស៊ូ៖ `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**កេះ៖** ជញ្ជាំងប្រើប្រាស់រយៈពេល 5 ម៉ោង — a `429` ដែលបឋមកថាមាន `anthropic-ratelimit-unified-status: rejected` ហើយនៅពេលដែលគណនីមានសិទ្ធិ `anthropic-ratelimit-unified-slow-offer: treatment`។ គ្មានអ្វីត្រូវបានផ្ញើនៅមុខជញ្ជាំងដំបូងនោះ 429; ការផ្ទុះ 429 ដោយគ្មានបឋមកថាបង្រួបបង្រួមឆ្លងកាត់ផ្លូវត្រជាក់ធម្មតា។

**ផ្លូវអាទិភាពទាប** (`lowPriorityMode`):

- នៅលើជញ្ជាំង 429 ប្រតិបត្តិករទទួលយកការផ្តល់ជូននេះ ហើយព្យាយាមម្តងទៀតភ្លាមៗ** ដូចគ្នា** គណនីជាមួយ `anthropic-usage-limit: slow`; ផ្លូវនេះនៅតែសកម្មរហូតដល់ `anthropic-ratelimit-unified-reset` ដែលបានប្រកាស (+ 60s grace) ហើយរាល់សំណើនៅក្នុងបង្អួចនោះមានបឋមកថា។ ការស្ទាក់ចាប់ 429 មិនដែលឈានដល់ `handleChatCore` ដូច្នេះការតភ្ជាប់គឺ** ទេ។** ដាក់ក្នុង cooldown ហើយមិនត្រូវបានបង្វិលឆ្ងាយ។
- `anthropic-ratelimit-unified-slow-status` លើការឆ្លើយតបនៅពេលក្រោយ៖ `active` / `not_needed` រក្សាផ្លូវ; `slot_busy` (429) ឬ `529` រង់ចាំ `anthropic-ratelimit-unified-slow-retry-after` របស់ម៉ាស៊ីនមេ (លំនាំដើម 20s, តោង 5–600s, ± 30% jitter) ហើយព្យាយាមម្តងទៀត ដោយកំណត់ដោយ `anthropic-ratelimit-unified-slow-max-wait` (លំនាំដើម 20 នាទី, តោង 1 នាទី–6 ម៉ោង) — ហួសពីផ្លូវបញ្ចប់ និង 10 នាទី cool-off blocks ។ ការរង់ចាំត្រូវបានបិទបន្ថែមដោយអ្វីដែលនៅសេសសល់ពីការអស់ពេលចាប់ផ្តើមចរន្តផ្ទាល់របស់សំណើ (`resolveFetchStartTimeout`, 10 នាទីតាមលំនាំដើម) ដករឹម 5 វិនាទី៖ ដោយគ្មានកំណត់នោះ ការរង់ចាំអតិបរមារយៈពេល 20 នាទីនឹងលើសពីសំណើ ហើយការគេងនឹងត្រូវបានលុបចោលពាក់កណ្តាលការរង់ចាំ ដោយប្រើ `TimeoutError` ជំនួសឱ្យ + បញ្ចប់ `max_wait` ។
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, 5h-window rollover, ឬ `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (ដែលបញ្ចប់វាជា `extra_usage` នៅលើស្ថានភាពណាមួយ ចាប់តាំងពីការបង់ប្រាក់លើសឥឡូវនេះគ្របដណ្តប់លើជញ្ជាំង) បញ្ចប់ផ្លូវ; ការឆ្លើយតបនឹងហូរទៅផ្លូវត្រជាក់ធម្មតា។ `budget_exhausted` ត្រូវបានចងចាំរហូតដល់ការកំណត់ថវិកាដែលបានប្រកាសឡើងវិញ (≤ 8 ថ្ងៃ) ។
- ការត្រួតពិនិត្យជញ្ជាំងដំណើរការបន្ទាប់ពីការព្យាយាមឡើងវិញ 400-driven ផ្ទាល់របស់អ្នកប្រតិបត្តិ (ការកែសម្រួលបរិបទ ការគៀប thinking/effort, param auto-learn) ដូច្នេះជញ្ជាំង 429 ដែលមានផ្ទៃលើការព្យាយាមម្ដងទៀតនៅតែត្រូវបានស្ទាក់ចាប់ ជំនួសឱ្យការឈានទៅដល់ផ្លូវត្រជាក់។
- រដ្ឋស្ថិតនៅក្នុងអង្គចងចាំក្នុងមួយការតភ្ជាប់ (ការចាប់ផ្តើមឡើងវិញមានតម្លៃ 429 ជញ្ជាំងបន្ថែមដើម្បីទទួលយកឡើងវិញ) ។

**កំណត់រយៈពេលកំណត់សម័យឡើងវិញ** (`autoLimitReset`, ព្យាយាមនៅពីមុខផ្លូវនៅពេលទាំងពីរនៅលើ):

- `result: reset|not_limited` → សំណើត្រូវបានព្យាយាមម្ដងទៀតក្នុងល្បឿនពេញ (មិនមានបឋមកថាយឺត) ។ `already_used` / `not_offered` memoise `next_available_at` (លំនាំដើមមួយសប្តាហ៍); ការបរាជ័យណាមួយនឹងបិទ 15 នាទី។ ការកំណត់ឡើងវិញគឺម្តងក្នុងមួយសប្តាហ៍ ហើយនៅតែរាប់ដល់ដែនកំណត់ប្រចាំសប្តាហ៍។

5. ការការពារកំណត់ឡើងវិញតាមធម្មជាតិ៖ រំលងនៅពេលដែលបង្អួចដែលមានជញ្ជាំងរយៈពេល 5 ម៉ោងកំណត់ឡើងវិញនៅក្នុង `sessionResetGuardMinutes` (90) ឬបង្អួចប្រចាំសប្តាហ៍ដែលមានជញ្ជាំងនៅក្នុង `weeklyResetGuardHours` (12) ។
6. ជាន់ប្រចាំសប្តាហ៍៖ រំលងការកំណត់ឡើងវិញរយៈពេល 5 ម៉ោង នៅពេលដែលនៅសល់ប្រចាំសប្តាហ៍គឺទាបជាង `weeklyFloorPercent` (10)។
7. របៀប `last-resort` ៖ រំលងខណៈពេលដែលគណនីក្នុងវិសាលភាពមួយផ្សេងទៀតរបស់អ្នកផ្តល់សេវាដូចគ្នាមានយ៉ាងហោចណាស់ `poolHeadroomPercent` (10) ដែលនៅសល់ក្នុងបង្អួចទាំងពីរ។ ការកេះឥណទានផុតកំណត់រំលងវា។
8. `dry-run` កត់ត្រាជួរដេកមួយហើយមិនយកអ្វីមកវិញ; `last-resort` និង `eager` ប្រោសលោះ។

ការបាត់ទិន្នន័យកូតាមិនដែលដោះសោការប្រោសលោះទេ៖ ពេលវេលាកំណត់ឡើងវិញដែលមិនស្គាល់ ឬរំលងការប្រើប្រាស់ប្រចាំសប្តាហ៍។

**កំណត់វគ្គ Claude ឡើងវិញ៖** ជាមួយនឹងមុខងារបិទ ឬបិទ `claudeSessionReset` បិទ/បើក `autoLimitReset` ក្នុងមួយគណនីសម្រេចចិត្តយ៉ាងពិតប្រាកដដូចពីមុន។ ជាមួយនឹងការបើកទាំងពីរ មុខងារជំនួសការបិទ/បើកក្នុងមួយគណនី៖ គណនីក្នុងវិសាលភាពអាចទាមទារបានលុះត្រាតែគោលការណ៍អនុញ្ញាត ហើយនៅក្នុងរបៀប `dry-run` គ្មានការទាមទារណាមួយត្រូវបានធ្វើឡើងទេ។

**សុវត្ថិភាព៖** ការងារនឹងប្តូរយកឥណទានច្រើនបំផុតក្នុងមួយធីក សម្រេចចិត្តមុនពេលចុះបញ្ជីឥណទាន (គណនីដែលរំលងមិនត្រូវបានរាយក្នុងបញ្ជី) ប្រើ idempotency keys `auto-reset:<connectionId>:<yyyy-mm-dd>:<n>` ហើយបិទគណនីមួយក្នុងរយៈពេល 1 ម៉ោងបន្ទាប់ពីការចុះបញ្ជីបរាជ័យ ឬការលោះ។ រាល់ការប្រោសលោះ ការបរាជ័យ និងការសម្រេចចិត្តស្ងួតត្រូវបានសរសេរទៅកាន់ `audit_log` (`action: "bankedReset.redeem"`, no tokens or credit ids ); មួកត្រូវបានរាប់ពីជួរទាំងនោះ ដូច្នេះពួកវាអាចរួចផុតពីការចាប់ផ្តើមឡើងវិញ។ ការប្រោសលោះដោយជោគជ័យក៏បាញ់ `provider.reset_redeemed` webhook ផងដែរ។

### ភាពស្និទ្ធស្នាលសម័យ (#7274)

**វិសាលភាព៖** សម័យម៉ាស៊ីនភ្ញៀវមួយ (ក្បាល `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session` ) ត្រូវបានខ្ទាស់ទៅការតភ្ជាប់មួយ សម្រាប់** ណាមួយ។** អ្នកផ្តល់សេវា។

**គោលបំណង៖** រក្សាភ្នាក់ងារពហុវេន (Claude Code, aider, custom agents) នៅលើគណនីដូចគ្នានៅលើសំណើ កាត់បន្ថយការបាត់បង់បរិបទឆ្លងគណនី និងការចាប់ផ្តើមត្រជាក់ម្តងទៀត 429s លើអ្នកផ្តល់សេវាដែលមានស្ថានភាពនៃវគ្គក្នុងមួយគណនី។

**ការអនុវត្ត៖**

- ដំណោះស្រាយ TTL : `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- ខ្ទាស់ selection/creation: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- ការទាញយកបឋមកថា (ទូទៅ, អ្នកផ្តល់សេវាណាមួយ): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- តារាងលេខសម្គាល់ដែលនៅជាប់៖ `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- ការកំណត់៖ `sessionAffinityTtlMs` ( TTL សកលក្នុង ms, `0` បិទ) — `src/lib/db/settings.ts`។ បានប្តូរឈ្មោះពី Codex-only `codexSessionAffinityTtlMs` ដោយការ migration `124_generic_session_affinity_ttl.sql` ដែលអនុវត្តលើ Codex TTL ដែលបានកំណត់ពីមុនណាមួយជាលំនាំដើមថ្មី។

មុនពេល #7274, `resolveSessionAffinityTtlMs()` hard-bailed to `0` សម្រាប់អ្នកផ្តល់សេវាទាំងអស់ លើកលែងតែ `codex` ដូច្នេះការកំណត់ TTL (និងបឋមកថាវគ្គ) មិនមានឥទ្ធិពលនៅកន្លែងណាផ្សេងទៀតទេ ទោះបីជាយន្តការខ្ទាស់ និងការទាញយកបឋមកថាជាអ្នកផ្តល់សេវាមិនប្រក្រតីក៏ដោយ។ ការជួសជុលបានយកចេញថាការត្រឡប់មកវិញមុនពេល; TTL ឥឡូវនេះអនុវត្តដូចគ្នាទៅនឹងអ្នកផ្តល់សេវាទាំងអស់នៅពេលដែលបានកំណត់ជាសកលខាងលើ `0`។

បឋមកថាទំនាក់ទំនងវគ្គទាំងបីមិនត្រូវបានបញ្ជូនបន្តទេ អ្នកប្រតិបត្តិ — ខាងលើបង្កើតបឋមកថាផ្ទាល់របស់ពួកគេពីដំបូងជាជាងការឆ្លងកាត់បឋមកថារបស់អតិថិជន ដូច្នេះនេះនៅតែជាលេខសម្គាល់ទំនាក់ទំនងខាងក្នុងប៉ុណ្ណោះ។

### ការជួលការតភ្ជាប់សម័យដែលបានគ្រប់គ្រងផ្តាច់មុខ

**វិសាលភាព៖** HTTP client/session ដែលគ្រប់គ្រងសកម្មមួយ ជាម្ចាស់ការតភ្ជាប់ OmniRoute ដែលមានសិទ្ធិមួយ។

**គោលបំណង៖** ផ្តល់ភាពជាម្ចាស់នៃការតភ្ជាប់ផ្តាច់មុខយូរអង្វែងសម្រាប់អតិថិជនដែលត្រូវការរបងផ្លូវពិបាកឆ្លងកាត់សំណើ។ វាខុសគ្នាពីភាពស្និទ្ធស្នាលក្នុងសម័យប្រជុំ ដែលជាចំណូលចិត្តបន្តទន់៖ ការជួលផ្តាច់មុខនៅតែបន្តមានស្ថានភាពវដ្តជីវិតនៅក្នុង SQLite បង្ខំម្ចាស់សកម្មជាសកល និងភាពឯកោនៃការតភ្ជាប់សកម្ម ហើយបដិសេធជំនាន់ដែលជាប់គាំងមុនពេលបញ្ជូនអ្នកផ្តល់សេវា។

លក្ខណៈពិសេសគឺជ្រើសរើសចូលក្នុងមួយគ្រាប់ចុច API ។ សោដែលបានគ្រប់គ្រងត្រូវតែមានវិសាលភាព `lease:exclusive` និងបញ្ជី `allowedConnections` មិនទទេច្បាស់លាស់។ ម៉ាស៊ីនភ្ញៀវ HTTP ណាមួយអាចប្រើចំណុចបញ្ចប់នៃវដ្តជីវិត។ គ្មានឈ្មោះអតិថិជន ភ្នាក់ងារអ្នកប្រើប្រាស់ អ្នកផ្តល់សេវា វិធីសាស្ត្រ OAuth ឬគំរូត្រូវបានទាមទារ។ ការជួលជាម្ចាស់ការតភ្ជាប់ មិនមែនជាគំរូទេ ដូច្នេះការផ្លាស់ប្តូរគំរូរក្សាការចង ខណៈដែលការតភ្ជាប់នៅតែមានសិទ្ធិធម្មតា។ គំរូធម្មតា កូតា សុខភាព ការចុះត្រជាក់ និងច្បាប់បញ្ជីអនុញ្ញាតនៅតែអនុញ្ញាត ហើយអាចផ្លាស់ប្តូរជំនាន់ដូចគ្នាទៅការតភ្ជាប់ដែលមានសិទ្ធិឥតគិតថ្លៃផ្សេងទៀត។

វដ្តជីវិតគឺ `POST /api/v1/session-leases` ជាមួយនឹងសកម្មភាព JSON `acquire` `renew` និង `release`។ សំណើការសន្និដ្ឋានដែលបានគ្រប់គ្រងបង្ហាញតម្លៃ `X-OmniRoute-Lease-Owner` ស្រអាប់ និង `X-OmniRoute-Lease-Generation` ពិតប្រាកដ។ ម្ចាស់ប្រើ `vlo_` អមដោយ 43 base64url តួអក្សរ; មានតែ SHA-256 hash របស់វាប៉ុណ្ណោះដែលត្រូវបានរក្សាទុក។ រាល់របងបញ្ជូនចុងក្រោយក៏ចង API key ID ដែលបានផ្ទៀងផ្ទាត់ និងការភ្ជាប់សកម្ម ID ផងដែរ។ បឋមកថាគ្រប់គ្រងការជួលត្រូវបានដកចេញពីកំណត់ហេតុ រូបថតនៃសំណើដែលបានរក្សាទុក និងបឋមកថាប្រតិបត្តិករខាងលើ។

ប្រសិនបើការបញ្ជូនបន្តធម្មតាមានបេក្ខជនដែលមានសិទ្ធិគ្រប់គ្រង ប៉ុន្តែរាល់បេក្ខជនឥតគិតថ្លៃត្រូវបានកាន់កាប់ដោយការជួលសកម្មពីបរទេស OmniRoute ត្រឡប់ HTTP `429` លេខកូដជួល-សមត្ថភាពមិនអាចប្រើបាន ស្ថានភាពរង់ចាំសម្រាប់សមត្ថភាព និង `Retry-After` ព្រំដែនដែលបានមកពីការផុតកំណត់ដែលពាក់ព័ន្ធដំបូងបំផុត។ សិទ្ធិទទេធម្មតាគឺមិនមែនជាការឈ្លោះគ្នាក្នុងការជួលនិងរក្សាការកំណត់ផ្លូវដែលមានស្រាប់របស់វាមានន័យថាកំហុស។

## 3. ការចាក់សោម៉ូដែល

**វិសាលភាព៖** បន្សំ provider + connection + model។

  connection) ហើយសម្រាប់ provider ផ្សេងទៀត គឺ `getQuotaScopedModelForProvider()`។

  អំពីកូតារបស់គណនីទេ។ មុនពេលមានច្បាប់នេះ ការឆ្លើយតបទទេមួយនៅលើ
  `codex/gpt-5.6-luna` បានដកម៉ូដែល `gpt-5*` ទាំងអស់របស់ connection នោះចេញពី
  routing រយៈពេល 2–30 នាទី (ដោយកើនឡើងជាបន្តបន្ទាប់) ខណៈដែលកូតារបស់វាមិនត្រូវបានប៉ះពាល់។
- ជម្រើស `scope` ជាក់លាក់របស់ caller តែងតែមានអាទិភាព (Antigravity បញ្ជូន `"exact"`)។

## 4. ការគ្រប់គ្រងការចែករំលែកកូតា (v3.8.36)

គណនីជាវ (GLM, MiniMax, ល) ជាញឹកញាប់ទទួលយកតែសំណើស្របគ្នា ~ 1-3 លើសពីនោះធ្វើឱ្យ 429s និង cooldowns ។ នេះគឺស្រួចស្រាវនៅក្រោម** ការចែករំលែកកូតា** (`qtSd/…`) បន្សំ ដែលគ្រាប់ចុច API ជាច្រើនចែករំលែកគណនីខាងលើមួយ។ បីស្រទាប់រក្សាគណនីរួមពីការជន់លិច។

### មូលធននីយកម្មក្នុងមួយការតភ្ជាប់ (`max_concurrent`)

ការតភ្ជាប់អ្នកផ្តល់សេវានីមួយៗអាចប្រកាសពិដាន `max_concurrent` (`provider_connections.max_concurrent` កំណត់ក្នុងម៉ូឌុលការតភ្ជាប់ / API / DB) ។ ទុកវាឱ្យនៅទទេដោយគ្មានដែនកំណត់។ នេះគឺជាកូនសោតែមួយដែលជំរុញស្រទាប់សៀរៀលខាងក្រោម — កំណត់វាទៅជារូបិយប័ណ្ណរួមពិតរបស់គណនី (ឧទាហរណ៍ GLM ~ 1, MiniMax ~ 2) ។

### មួករូបិយប័ណ្ណក្នុងមួយគំរូ (`modelConcurrency`)

ការតភ្ជាប់ក៏អាចប្រកាសអំពីពិដានស្របគ្នានៃគំរូនីមួយៗនៅក្នុងផែនទី `rateLimitOverrides` របស់វាផងដែរ៖

```json
{
  "rateLimitOverrides": {
    "maxConcurrent": 4,
    "modelConcurrency": { "glm-5": 1, "glm-4.7": 3 }
  }
}
```

កំណត់វានៅក្នុងម៉ូឌុលការតភ្ជាប់ (** ដែនកំណត់អត្រាបដិសេធ → Per-model concurrency caps** មួយ `model=cap` ក្នុងមួយជួរ) ឬតាមរយៈ `PATCH /api/providers/[id]` ដែលមានរាង JSON ដូចគ្នា។ ពាក្យគន្លឹះ៖

- **ការតភ្ជាប់ធំទូលាយធៀបនឹងម៉ូដែលជាក់លាក់៖** `maxConcurrent` នៅតែជាពិដានការតភ្ជាប់ធំទូលាយ។ នៅពេលអនុវត្តទាំងពីរ ច្រកទ្វារទាំងពីរត្រូវបានទទួលដោយអាតូមនៅក្នុងច្រកទ្វារសមាសធាតុដូចគ្នា (`global → provider → account → model`); ឥរិយាបទដែលមានប្រសិទ្ធភាពគឺជាដែនកំណត់ដែលអាចអនុវត្តបានកាន់តែតឹងរ៉ឹង។
- **ការផ្គូផ្គងគន្លឹះគំរូជាក់លាក់៖** គន្លឹះគឺជាខ្សែអក្សរគំរូដែលបានបញ្ជូនទៅកាន់ប្រតិបត្តិករបន្ទាប់ពីការកំណត់ផ្លូវដោះស្រាយ — ជាធម្មតា លេខសម្គាល់គំរូខាងលើទទេ (`glm-5`) មិនមែនជាឈ្មោះជំនួស `provider/model` ខាងអតិថិជន (`zai/glm-5` មិនផ្គូផ្គង `glm-5`) ។ តម្លៃគឺជាពិដានសំណើស្របគ្នាចំនួនវិជ្ជមាន។
- **ការតម្រង់ជួរក្នុងតំបន់ គ្មានការរកឃើញទេ៖** សំណើលើសតម្រង់ជួរក្នុងមូលដ្ឋានជាមួយនឹងអត្ថន័យ queue/timeout ដែលមានស្រាប់ (វាយបញ្ចូល `SEMAPHORE_TIMEOUT` / `SEMAPHORE_QUEUE_FULL` កំហុសចូល) ។ OmniRoute មិនបានរកឃើញ ឬសន្និដ្ឋានគោលការណ៍ខាងលើ — វាអនុវត្តពិដានពិតប្រាកដដែលប្រតិបត្តិករបានកំណត់រចនាសម្ព័ន្ធ។ ច្រកទ្វារគំរូឆ្អែត មិនដែលបិទអ្នកផ្តល់សេវា និងមិនដែលបង្កើតការចាក់សោគំរូអចិន្ត្រៃយ៍ឡើយ។ ឥរិយាបថ 429/cooldown/fallback ខាងលើនៅតែជាកំហុស backstop ។
- **ក្នុងមួយការតភ្ជាប់ វិសាលភាពនៃដំណើរការ៖** caps គឺក្នុងមួយការតភ្ជាប់មូលដ្ឋានទិន្នន័យ និងរក្សាទុកក្នុងអង្គចងចាំ ដូច្នេះការតភ្ជាប់ពីរដែលប្រើគ្រាប់ចុច API ខាងលើដូចគ្នាមិនសម្របសម្រួលជាមួយគ្នាទេ។
- **Unconfigured មានន័យថាមិនផ្លាស់ប្តូរ៖** ការលុបផែនទី (ឬទុកវាលផ្ទាំងគ្រប់គ្រងទទេ) មិនបន្ថែមច្រកទ្វារគំរូទេ។ ការកំណត់រចនាសម្ព័ន្ធឧទាហរណ៍ដោយមិនអះអាងដែនកំណត់អ្នកផ្តល់សេវាសកលណាមួយ៖

```text
glm-5=1
glm-4.7=3
```

### សៀរៀលសំណើចែករំលែកកូតា

នៅពេលដែលការចែកចាយការចែករំលែកកូតាកំណត់គោលដៅនៃការតភ្ជាប់ដែលប្រកាស `max_concurrent` វិជ្ជមាន សំណើស្របគ្នានឹងវា** គណនី** ត្រូវបានធ្វើជាសៀរៀលតាមរយៈការតភ្ជាប់មួយ semaphore (គន្លឹះ `qsconn:<connectionId>`): សំណើលើស** រង់ចាំក្នុងជួរ** ជំនួសឱ្យការជន់លិចគណនី។ វាគឺ** បរាជ័យ - បើក** — ជួរដែលឆ្អែត ឬអស់ពេលដំណើរការដោយគ្មានរន្ធដោត ជាជាងការបដិសេធសំណើដែលអាចបញ្ជូនបាន។ បិទ/បើក** ការកំណត់ → Resilience → Quota-share per-connection concurrency** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, លំនាំដើមនៅលើ) ។ បើគ្មានមួក `max_concurrent` ឥរិយាបទមិនផ្លាស់ប្តូរទេ។

> ច្រកផ្លូវចែករំលែកកូតា (`selectQuotaShareTarget`, DRR + P2C) គឺខ្លួនវាមិនបានបើក ហើយមានតែ _deprioritizes_ ការតភ្ជាប់ at-cap — ជាមួយនឹងអាងតភ្ជាប់តែមួយ វាមិនអាចកំណត់រឹងបាន ដូច្នេះ semaphore នេះគឺជាអ្វីដែលពិតជាមានទឹកជំនន់។

### ព្យាយាមម្តងទៀតដោយដឹងអំពីភាពត្រជាក់នៃបន្សំ

សម្រាប់រាល់យុទ្ធសាស្ត្របន្សំ (នៅពេលបើកដំណើរការ) សំណើដែលនឹងធ្វើឱ្យគ្រីស្តាល់ 429 សម្រាប់ការ cooldown បណ្តោះអាសន្ន SHORT រង់ចាំវាចេញ ហើយបញ្ជូនឡើងវិញជំនួសឱ្យការត្រឡប់ 429 — នេះគ្របដណ្តប់លើបង្អួច TPM/RPM ថ្នាក់ Gemini (~ 60s retry-after) លើបន្សំពហុម៉ូដែល ឧ. អត្រាការវាយលុកក្នុងកម្រិត 2. bodel ក្នុងមួយ កំណត់ដោយ `comboCooldownWait` (`enabled`, `maxWaitMs`, `maxAttempts`, `budgetMs`) ក្នុង** ការកំណត់ → ភាពធន់** . វាមិនដែលរង់ចាំ `quota_exhausted` (ចាក់សោរហូតដល់ពាក់កណ្តាលអធ្រាត្រ) ឬហេតុផល auth/not-found ។ ជាមួយនឹងការកំណត់ `comboTimeoutMs` ការរង់ចាំដែលមិនអាចបញ្ចប់មុនថ្ងៃកំណត់នោះមិនចាប់ផ្តើមទេ (#18998): បន្សំឆ្លើយតបភ្លាមៗជាមួយនឹងការឆ្លើយតបស្ថានីយរបស់វាជំនួសឱ្យ `COMBO_TIMEOUT` 504 ។

បន្សំអាចបដិសេធជាមួយ `config.comboCooldownWaitEnabled: false`។ មានតែ `false` តាមព្យញ្ជនៈប៉ុណ្ណោះដែលបិទការរង់ចាំបន្សំដែលបានចែករំលែកទាំងនេះ (ការពន្យារពេលក្រោយការបញ្ជូន និងការរង់ចាំ circuit-open/model-lock ជាមុន) និងផ្នែកបន្ថែមពេលវេលានៃការរង់ចាំថវិការបស់ពួកគេ។ បាត់ ឬ `true` រក្សាគោលការណ៍សកល។ `true` មិនអាចបើកការរង់ចាំដែលបិទជាសកលបានទេ។ `targetTimeoutMs` ច្បាស់លាស់នៅតែឈ្នះ។ ការបដិសេធនេះមិនផ្លាស់ប្តូរការរង់ចាំការបញ្ជូនជាមុនកូដកូដដើមកំណើតដាច់ដោយឡែកពីគ្នានោះទេ។

ច្រកដូចគ្នាគ្របដណ្តប់ករណីបញ្ជូនមុន (#16319): នៅពេលដែលរាល់គោលដៅនៃបន្សំមួយត្រូវបានរំលង មុនពេលការប៉ុនប៉ងណាមួយត្រូវបានធ្វើឡើង ដោយសារតែគំរូរបស់វាស្ថិតនៅក្នុងការចាក់សោរបណ្តោះអាសន្នខ្លី ផ្លូវព្យាយាមសូន្យនឹងរង់ចាំការចាក់សោរនៅក្រោមពិដានដូចគ្នា ហើយបញ្ជូនម្តងទៀត ជំនួសឱ្យការឆ្លើយ `503 ALL_TARGETS_SKIPPED` តិច។ នៅពេលដែលគ្មានការរង់ចាំត្រូវបានអនុញ្ញាត (ពិដាន ការប៉ុនប៉ង ឬថវិកាអស់ ឬមុខងារបិទ) ការឆ្លើយតបរបស់ស្ថានីយនឹងដំឡើងកំណែទៅ `429 rate_limit_error` ដែលផ្ទុក `retry_after` / `reset_at` ពីការផុតកំណត់នៃការចាក់សោបណ្តោះអាសន្នដំបូងបំផុត; កូតា ការផ្ទៀងផ្ទាត់ និងសោមិនបានរកឃើញរក្សាព័ត៌មានជំនួយតិចជាង 503។

```text
#16319 · comboCooldownWait · pre-dispatch (attempts = 0)
all targets skipped + transient model lockout:
  enabled ∧ 0 < waitMs ≤ maxWaitMs ∧ attempt < maxAttempts ∧ budgetLeftMs ≥ waitMs
    → wait → re-dispatch
  wait = false → HTTP 429 rate_limit_error
  retry_after / reset_at ← earliest transient lock expiry
quota_exhausted / auth_error / not_found / not_found_local:
  no transient hint → HTTP 503 ALL_TARGETS_SKIPPED
```

## 5. ការគ្រប់គ្រងការទទួលយកជួររងសំណើ (v3.8.49 · issue #6593)

**វិសាលភាព**: ជួររងលីមីតប្រាក់ប្រចាំអ្នកផ្គត់ផ្គង់+ការតភ្ជាប់ក្នុងស្រុក (`open-sse/services/rateLimitManager.ts`, ដែលបានគាំទ្រដោយ Bottleneck) ជាមួយជាន់មួយក្រោមម៉ាស៊ីនចំណាត់ថ្នាក់បីខាងលើ។

**`maxWaitMs` កំណត់ព្រំកំណត់ការរង; `executionMaxWaitMs` កំណត់ព្រំកំណត់ការអនុវត្ត។**  
ទាំងពីរនេះត្រូវបានបំបែកយ៉ាងច្បាស់ ហើយមួយក៏មិនផ្គត់ផ្គង់ទៅលើមួយទៀតឡើយ។

`resilienceSettings.requestQueue.maxWaitMs` គឺជា **ថវិកាការរងជួរ**: វាគ្របដណ្ដប់ការរងសម្រាប់ស្លុតអ្នកផ្គត់ផ្គង់ម្នាក់ និងបន្ទាប់មកអង្គុយនៅក្នុង QUEUED, ហើយ Timer របស់វាត្រូវបានលុបចោលភ្លាមៗនៅពេលដែលការងារចេញពី QUEUED និងចាប់ផ្តើមអនុវត្ត (`rateLimitManager.ts`, `wrappedFn`)។ ការស្នើរសុំដែលលើសពីវា មិនដែលឈានដល់ upstream ទេ។ តម្លៃលំនាំដើម 30000ms, ផ្តល់ដោយ `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS` នៅក្នុង `src/lib/resilience/settings.ts` និងត្រូវបានផ្អូញផ្អើលដោយ `tests/unit/ratelimit-admission-control-6593.test.ts`, ដូច្នេះ ការផ្លាស់ប្តូរវានឹងធ្វើឲ្យតេស្តនោះបង្ហាញជាពណ៌ក្រហម ជាជម្រើសផ្ទុយពីការធ្វើអត្ថបទនេះឲ្យក្លាយជាការមិនប្រើប្រាស់។

`resilienceSettings.requestQueue.executionMaxWaitMs` គឺជាអ្វីដែល Bottleneck ទទួលជាការបញ្ចប់ការងារ `expiration`, ដែល Timer របស់វាចាប់ផ្តើមតែបន្ទាប់ពីការបញ្ជូន។ វាជាការពារសម្រាប់ executors ដែលគ្មាន upstream timeout ផ្ទាល់ខ្លួន ហើយវាត្រូវបានលើកឡើងទៅ fetch-start timeout ផ្ទាល់ខ្លួនរបស់ executor នៅពេលវាខ្លាំងជាង ដូច្នេះវាមិនអាចផ្តាច់ការឆ្លើយតបដែលសុខភាពនៅក្នុងដំណើរការ។ តម្លៃលំនាំដើម 600000ms (10 នាទី)។

ការផ្ទុកថវិកាជួររងទៅក្នុង `expiration` គឺជាអ្វីដែលអស់កល្បជាមុន សម្រាប់ gateways មិនអាចបន្ថែមបាននៅពេលដំណើរការ — ពួកវាអាចដំណើរការបានជាក់ស្ដែងជាច្រើននាទីមុន bytes ដំបូង — ហើយវាជាការបង្ហាញរបស់ expiration ជាមួយ `code:
"RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504) ខណៈដែលថវិកាជួររងកាន់កូដ queue-timeout។ អាចការលើសកំណត់ដោយ `RATE_LIMIT_MAX_WAIT_MS` / `RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (env) ឬតាមផ្ទាំងគ្រប់គ្រង (**Settings → Resilience**)។ តម្លៃទាំងពីរត្រូវបានប៉ុនប៉ងកំណត់នៅ 1ms–24h នៅពេលនោះត្រូវបានធម្មតា។

**លំដាប់អាទិភាព សម្រាប់ទាំងពីរ**: env var ផ្តល់តែ _default_ ប៉ុណ្ណោះ។ តម្លៃដែលបានរក្សាទុកនៅក្នុង `resilienceSettings.requestQueue` (ផ្ទាំងគ្រប់គ្រង / API patch, ដែលបានទុកក្នុង `key_value`) មានអាទិភាពលើវា ហើយការកំណត់តាមការតភ្ជាប់មួយ `rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` មានអាទិភាពលើវា។ ការកំណត់ env var នៅលើ deployment ដែលស្រាប់មានតម្លៃដែលបានរក្សាទុកមិនបំលែងអ្វីទេ — សូមលុបចោលឬធ្វើបច្ចុប្បន្នភាពការកំណត់ដែលបានរក្សាទុកជាជម្រើស។

ការរស់នៅក្នុងជួររងត្រូវបានកំណត់ដោយ `maxWaitMs`; `maxQueueDepth` ខាងក្រោមកំណត់ចំនួនអ្នកអំពាវនាវដែលអាចរង់ចាំក្នុងជួរបាននៅពេលតែមួយ។

**ការស្នើរសុំបន្តរបស់រាងកាយ: ការរំកិលប្រកបដោយចំណាយពេល vs ការចាក់ចោល។**  
រាងកាយ 429 អាចបញ្ជាក់រយៈពេលរងរបស់ខ្លួន (Gemini `RetryInfo.retryDelay`, អត្ថបទ "retry after Ns"), ដែល `updateFromResponseBody` អាន។ ការរងដែលសមនឹង `maxWaitMs` នៃការតភ្ជាប់ គឺជាការរំកិលប្រកបដោយចំណាយពេល៖ limiter នឹងទទួលសម្រួលធុងរបស់វាក្នុងរយៈពេលនោះ ហើយការអំពាវនាវដែលបានដាក់ក្នុងជួរនឹងត្រូវបញ្ចូននៅពេលធុងនេះបានស្ដារឡើងវិញ។ ការរងដែលលើសពី `maxWaitMs` មិនមែនជារឿងដែលជួររងអាចរង់ចាំបានទេ — Gemini ឆ្លើយតបនឹង Quota ប្រចាំថ្ងៃដែលបានប្រើប្រាស់ exhausted ជាមួយ `retryDelay: "86399s"`។ `Retry-After` ដែលបានផ្ទេរឡើងវិញនៅលើ 429 ដែលបានសាងសង់ឡើងវិញ (#16528) បានធ្វើឲ្យ fallback engine ចាក់ចោលម៉ូដែលសម្រាប់វិនាទីនោះរួចហើយ ប៉ុន្តែក្នុងករណីលើក limiter សម្រាប់វាបង្កើតឲ្យរារាំងការអំពាវនាវណាមួយដែលឆ្លោះគន្លងឆាប់ (បន្ទាប់ពីការកំណត់សមរម្យ resilience, ឧទាហរណ៍) សម្រាប់ពេញមួយ `maxWaitMs`។ នៅពេលដែលការរងបែបនេះមកពីព័ត៌មានលម្អិតប្រភេទ Google `RetryInfo` (ដែលមានប្រភព `google_rpc_retry_info`) ហើយ limiter នៃ key បានកំណត់រួចទៅលើម៉ូដែល (សូមមើល `getLimiterKey`), 429 នេះក្លាយជាការចាក់ចោលម៉ូដែលលើការតភ្ជាប់នោះ (`lockModelForLongBodyRetry` នៅក្នុង `open-sse/services/rateLimitManager/bodyRetryPause.ts`, មានកំណត់សម្រាប់ 24h) ហើយ limiter ត្រូវបានទុកឲ្យមិនបានផ្អាក។ ការជ្រើសរើសគណនីនឹងរំលងការចាក់ចោលនេះតាមរយៈ `isModelLocked()`, ហើយ gate ជាមុនការបញ្ជូនសម្រាប់គោលដៅដែលត្រូវបានចងជាមួយការតភ្ជាប់ក៏ដូចជាការនោះផងដែរ។ នៅលើ antigravity ដែល limiter របស់វាត្រូវបានកំណត់តាមក្រុម quota, ការចាក់ចោលនឹងចាក់លើម៉ូដែលត្រឹមត្រូវ ដូចជាការចាក់លេខ quota ផ្សេងទៀតរបស់វា។ ឈ្មោះដែល client បានស្នើសុំត្រូវបានចាក់បិទផងនៅពេលដែល alias បានដោះស្រាយវាទៅម៉ូដែលនោះ ពីព្រោះការពិនិត្យនោះប្រើឈ្មោះដែលបានស្នើសុំ; វាត្រូវបានចាក់បិទដោយត្រឹមត្រូវ (`lockExactModel`), ដូច្នេះ alias ដែលឆ្លងកាត់ antigravity quota family ឬ codex scope មិនដែលចាក់បិទលើរបស់ខ្លួនឡើយ។ សេចក្តីគ្រប់គ្រងដោយអក្សរពិពណ៌, `retryDelay` ដែលមិនបានបញ្ជាក់ប្រភេទ, ឬ limiter ដែលចែករំលែកដោយការតភ្ជាប់ទាំងមូល នឹងរក្សាការផ្អាក។ នៅពេលដែល limiter របស់ផ្លូវ 429 ដែលទើបសាងសង់ឡើងវិញផ្អាក, អ្នកអំពាវនាវដែលពេលវេលាជួររងនៅសល់របស់គាត់ផុតទៅមុនការផ្អាក ត្រូវបានបដិសេធភ្លាមៗជាមួយកូដ queue-timeout (`checkLimiterPause`) ជំនួសការរងពេលនោះ; ចំណុចបញ្ចប់ដែលបានកត់ត្រាត្រូវបានដាក់ចិញ្ចើមនៅមុនការសាងសង់ឡើង limiter ដែល Bottleneck ចាប់ផ្តើមនាឡិកាស្ដារឡើងវិញ ហើយការផ្លាស់ប្តូរណាមួយក្រោយពេលក្នុងធុង (reservoir) នឹងភ្លេចវា។ (បានគ្របដណ្តប់ដោយ `tests/unit/rate-limit-long-body-retry-lockout.test.ts` និង `tests/unit/rate-limit-body-retry-pause.test.ts`)

**`maxQueueDepth` — កម្រិតទទួលការអនុម័តជាជម្រើស (ថ្មី)**  
`resilienceSettings.requestQueue.maxQueueDepth` កំណត់ចំនួនសំណើដែលអាចអង្គុយរង (មិនទាន់បានបញ្ជូន) សម្រាប់ provider+connection មួយនៅពេលតែមួយ។ នៅពេលដែលជួររងមានសំណើដល់ `maxQueueDepth` រួចហើយ, សំណើថ្មីនឹងត្រូវបានបដិសេធយ៉ាងរហ័សជាមួយកូដដែលមានព័ត៍មានប្រភេទ `code: "RATE_LIMIT_QUEUE_FULL"` **មុន**ដែលវានឹងឈានដល់ `limiter.schedule()` — ដូច្នេះការបដិសេធនេះមានថ្លៃថោក និងកើតឡើងជាមុននូវកិច្ចការបង្រ្កាប/ការប្រែសម្រួលណាមួយសម្រាប់សំណើនោះ។ តម្លៃលំនាំដើម `0` = បានបិទ, រក្សាទុកអាកប្បកិរិយាជួររងមិនមានព្រំកំណត់; តម្លៃអាចកំណត់បានពី 0–100000។ អាចផ្លាស់ប្តូរបានតាមរយៈ `RATE_LIMIT_MAX_QUEUE_DEPTH` (env) ឬ `resilienceSettings.requestQueue.maxQueueDepth` (ផ្ទាំងគ្រប់គ្រង/API patch)។

ការត្រួតពិនិត្យការទទួលយកដោយខ្លួនឯងគឺជាអនុគមន៍ស្អាត (`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`) ដូច្នេះវាអាចធ្វើតេស្តជាមួយ unit-test ដោយមិនត្រូវការប្រើប្រាស់ Bottleneck limiter ពិតៗទេ។

> RFC ដែលបានបើក #6593 ក៏បានស្នើនូវ flag `bypassCompressionOnRateLimit` ផងដែរ។ ប៉ាយឡាញ `open-sse/services/compression/` របស់ repo នេះ គឺជា prompt/context compression លើសំណើ LLM ចេញ (`chatCore.ts` ជុំវិញប្លុក `resolveCompressionSettings`/`selectCompressionStrategy`) មិនមែនជា HTTP response compression លើ 429 bodies ដែលបានបង្កើតឡើងទេ — មិនមាន code path ដែលត្រូវគ្នាសម្រាប់ bypass flag ពិតប្រាកដទេ។ ជំហាន prompt-compression នោះក៏ដំណើរការនៅ _មុន_ `withRateLimit()` ក្នុង request pipeline បច្ចុប្បន្នដែរ ដូច្នេះការរៀបចំលំដាប់ឡើងវិញដើម្បីរំលងវានៅពេល queue-full rejection គឺជាការផ្លាស់ប្តូរដាច់ដោយឡែក និងធំជាងវិសាលភាពរបស់ issue នេះ; វាត្រូវបានគេចេតនា **មិន** អនុវត្តនៅទីនេះ ហើយទុកជា follow-up ប្រសិនបើផលប្រយោជន៍នៃការសន្សំ CPU មានតម្លៃជាងហានិភ័យនៃការរៀបចំលំដាប់ឡើងវិញ។

### សំណាញ់សុវត្ថិភាពបើកដោយស្វ័យប្រវត្តិនៃ Rate-Limit និងការការពារការភ្ជាប់ (`rateLimitProtection`)

**សំណាញ់សុវត្ថិភាពបើកដោយស្វ័យប្រវត្តិ** (`resilienceSettings.requestQueue.autoEnableApiKeyProviders`, លំនាំដើម `true`):
តាមលំនាំដើម OmniRoute បើកការការពារ rate-limit queue ដោយស្វ័យប្រវត្តិសម្រាប់ការភ្ជាប់ API-key provider សកម្មទាំងអស់ (`getProviderCategory(provider) === "apikey"`)។ នេះធានាថាសំណើចូលទៅកាន់ upstream API keys ដែលងាយរងផលប៉ះពាល់ពី rate ត្រូវបានដាក់ជួរ និងគ្រប់គ្រងល្បឿនតាមរយៈ Bottleneck ជំនួសឱ្យការផ្ទុះចូលទៅក្នុងកំហុស upstream 429 ។ សំណាញ់សុវត្ថិភាពនេះអាចត្រូវបាន override តាមរយៈអថេរបរិស្ថាន `RATE_LIMIT_AUTO_ENABLE` (`false`/`0`/`off` បិទ, `true`/`1`/`on` បង្ខំបើក) ដែលមានអាទិភាពលើការកំណត់ dashboard ដែលបានរក្សាទុក (**Settings → Resilience** / `PATCH /api/resilience`)។

**អត្ថន័យនៃ `rateLimitProtection` ក្នុងមួយការភ្ជាប់:**
ការការពារ rate-limit ក្នុងមួយការភ្ជាប់ត្រូវបានតាមដានតាមរយៈ field boolean `rateLimitProtection` លើការភ្ជាប់ provider (រក្សាទុកជា `rate_limit_protection` ក្នុង SQLite):

- **បើកច្បាស់លាស់ (`rateLimitProtection === true`)**: ការការពារ rate-limit ត្រូវបានបើកយ៉ាងច្បាស់សម្រាប់ការភ្ជាប់នេះ មិនថាប្រភេទ provider ឬថាតើសំណាញ់សុវត្ថិភាព auto-enable ត្រូវបានបើកឬអត់នោះទេ។
- **បិទច្បាស់លាស់ (`rateLimitProtection === false`)**: បិទការការពារច្បាស់លាស់ ប៉ុន្តែ **មិន** ដកការភ្ជាប់ API-key សកម្មចេញពីសំណាញ់សុវត្ថិភាព auto-enable សកលទេ។ ក្នុង `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` និង `undefined` គឺសមមូលគ្នា: មានតែ `rateLimitProtection === true` ប៉ុណ្ណោះដែលត្រូវបានចាត់ទុកជា override ច្បាស់លាស់។ ប្រសិនបើ `rateLimitProtection` គឺ `false` (ឬមិនបានកំណត់) ការភ្ជាប់ API-key សកម្មនៅតែត្រូវនឹងលក្ខខណ្ឌ auto-enable ហើយនៅតែត្រូវបានការពារ rate-limit។
- **គ្មានការដកខ្លួនក្នុងមួយការភ្ជាប់**: អ្នកប្រតិបត្តិមិនអាចបង្ហាញថា "ការភ្ជាប់ API-key សកម្មតែមួយនេះត្រូវដំណើរការដោយគ្មានការការពារ rate-limit queue" ខណៈពេលដែលរក្សា auto-enable សកម្មសម្រាប់ការភ្ជាប់ផ្សេងទៀតនៅឡើយទេ។ ដើម្បីដំណើរការការភ្ជាប់ API-key ដោយគ្មាន rate-limit queues ទាំងស្រុង សំណាញ់សុវត្ថិភាពត្រូវតែបិទជាសកល (`RATE_LIMIT_AUTO_ENABLE=false` ឬ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`)។

**ផ្លូវសរសេរដែលគាំទ្រ:**

- **`POST /api/rate-limits`**: ផ្លូវសរសេរគ្រប់គ្រងដែលគាំទ្រដើម្បីប្តូរ `rateLimitProtection` សម្រាប់ការភ្ជាប់ (`{ connectionId: string, enabled: boolean }`)។ ការហៅជាមួយ `enabled: true` បើកការការពារច្បាស់លាស់; ការហៅជាមួយ `enabled: false` ដកការការពារច្បាស់លាស់ចេញ (ទោះបីជាការភ្ជាប់ API-key សកម្មនៅតែត្រូវបានគ្របដណ្តប់ក្រោមសំណាញ់សុវត្ថិភាពសកល ប្រសិនបើ auto-enable កំពុងបើកក៏ដោយ)។
- **`PUT /api/providers/[id]`**: ដោយចេតនា **មិន** ទទួល ឬប្តូរ `rateLimitProtection` (#11278)។ ការធ្វើបច្ចុប្បន្នភាព metadata ការភ្ជាប់ provider តាមរយៈ `PUT /api/providers/[id]` នឹងមិនផ្លាស់ប្តូរស្ថានភាពការពារ rate-limit ដែលបានរក្សាទុកឡើយ។

## 6. ឧបករណ៍ឃ្លាំមើលលំហូរយឺត (#9709)

ឆ្មាំ `resilienceSettings.streamRecovery.throughputWatchdog` ជាជម្រើសរកឃើញខ្សែទឹកដែលនៅតែបញ្ជូនកំណាត់ ប៉ុន្តែផលិតលទ្ធផលជំនួយនៅក្រោមអត្រាទិន្នផលដែលមានប្រយោជន៍ដែលបានកំណត់រចនាសម្ព័ន្ធ។ វាខុសពីការអស់ពេលទំនេរដោយចេតនា៖ ចង្វាក់បេះដូង និងទិន្នន័យមេតាកំណត់ឡើងវិញ ទាំងកម្មវិធីកំណត់ម៉ោង និងមិនរាប់បញ្ចូលជាដំណើរការ។ វាក៏ខុសប្លែកពីថ្ងៃផុតកំណត់នៃការព្យាយាមយ៉ាងលំបាក (#9153) ដែលនៅតែជាពិដានសុវត្ថិភាពទាំងស្រុងដោយមិនគិតពីគុណភាពទិន្នផល។

អង្គការឃ្លាំមើលតម្រូវឱ្យមានការកម្តៅសាច់ដុំ អមដោយបង្អួចរំកិលពេញលេញ មុនពេលវាអាចរំលូតកូនបាន។ វារាប់បញ្ចូលអត្ថបទ deltas ពីការបញ្ចប់ការជជែក និងការឆ្លើយតប API ព្រឹត្តិការណ៍លទ្ធផល (ប្រូកស៊ី UTF-8 byte អភិរក្ស) មិនអើពើចំពោះតែការប្រើប្រាស់ និងព្រឹត្តិការណ៍ទទេ ហើយផ្អាកការវិនិច្ឆ័យខណៈពេលដែលព្រឹត្តិការណ៍ហៅឧបករណ៍ ឬហេតុផលកំពុងហោះហើរ។ វាត្រូវបានបិទតាមលំនាំដើម ហើយអាចត្រូវបានបើកដោយប្រើ `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true` (តម្លៃ env មានតែគ្រាប់ពូជ — លំនាំដើម `resilienceSettings.streamRecovery.throughputWatchdog.enabled` boolean ដែលបានរក្សាទុក។ សូមមើលកំណត់ចំណាំ env-vs-dashboard នាំមុខនៅផ្នែកខាងលើនៃការណែនាំនេះ); បង្អួច កំដៅឡើង អត្រាអប្បបរមា និងទិន្នផលដែលអាចវាស់វែងបានអប្បបរមាត្រូវបានចងភ្ជាប់ដោយស្រទាប់ធម្មតានៃការកំណត់ភាពធន់នឹងធម្មតា។

នៅពេលបើកដំណើរការ ការបោះបង់ការឃ្លាំមើលត្រូវបានអនុវត្តចំពោះតែការប៉ុនប៉ងសកម្ម។ មុនពេលដែលអតិថិជនមើលឃើញបៃណាមួយ ផ្លូវសង្គ្រោះមុនដំបូងរបស់គណនីដូចគ្នាដែលមានស្រាប់អាចបើកការប៉ុនប៉ងឡើងវិញ។ បន្ទាប់ពីការប្តេជ្ញាចិត្ត ស្ទ្រីមមិនដែលចាក់ឡើងវិញដោយងងឹតងងល់ឡើយ។ មានតែកិច្ចសន្យាបន្តពាក់កណ្តាលស្ទ្រីមសុវត្ថិភាពដែលមានស្រាប់ប៉ុណ្ណោះដែលអាចភ្ជាប់បច្ច័យបាន។ ការបញ្ចប់ចុងក្រោយនៅតែជាការបាញ់ប្រហារតែមួយ ដូច្នេះគណនេយ្យនៃការប្រើប្រាស់ និងការចេញផ្សាយ semaphore មិនត្រូវបានចម្លងទេ។

## 7. ការកំណត់ស្ថានភាព Upstream ឡើងវិញ (កំហុស quota ដែលរាយការណ៍ខុស)

**វិសាលភាព៖** gateway upstream មួយដែលរាយការណ៍ថា quota អស់ជាបណ្ដោះអាសន្ន ប៉ុន្តែប្រើ HTTP status ខុស។

**គោលបំណង៖** កែស្ថានភាពដែលបំភាន់ មុនពេលធ្វើចំណាត់ថ្នាក់ ដើម្បីឱ្យអ្នកប្រើប្រាស់ downstream (fallback engine, combo aggregation និងការឆ្លើយតបទៅ client) មើលឃើញលក្ខណៈដែលអាច retry បានពិតប្រាកដរបស់បញ្ហាបរាជ័យ។

Gateway មួយចំនួនបង្ហាញការអស់ quota ជាបណ្ដោះអាសន្នជាមួយ HTTP
status ដែលមិនអាច retry បាន។ `agentrouter.org` ត្រឡប់ `403` (ពេលខ្លះ `400`) ជាមួយ body
ជាភាសាចិន (`用户额度不足` / `额度不足`) ជំនួសឱ្យ `429` ស្តង់ដារ។ Client ដូចជា Claude
Code ចាត់ទុក `403` ថាជាកំហុសអចិន្ត្រៃយ៍ ហើយបញ្ឈប់ session ហើយបើគ្មានការកែតម្រូវ
fallback engine នឹងចាត់ថ្នាក់វាជា `AUTH_ERROR` ជំនួសឱ្យព្រឹត្តិការណ៍ quota។

`CONTEXT_OVERFLOW_PATTERNS` ។ល។ នៅក្នុង `accountFallback.ts`) ហើយត្រឡប់ចេញ មុនពេលអាចឈានដល់សាខា `configuredRule`/`getProviderErrorRuleMatch` ដែលនៅខាងលើ។ ច្បាប់ក្នុងកាតាឡុកដែលភ្ជាប់មកជាមួយ (ឬច្បាប់ operator) ដែលមាន `status: 400` គឺមានវាក្យសម្ព័ន្ធត្រឹមត្រូវ ប៉ុន្តែនឹងមិនដំណើរការឡើយ។ បច្ចុប្បន្ននេះ គ្មានច្បាប់ដែលកំណត់គោលដៅទៅ 400 ទេ ដូច្នេះផលិតកម្មមិនរងផលប៉ះពាល់អ្វីឡើយ — ប៉ុន្តែច្បាប់ 400 នាពេលអនាគត ត្រូវកែសាខានេះជាមុន ដែលជាការផ្លាស់ប្តូរធំជាងការបន្ថែមច្បាប់មួយ (វានឹងចាត់ថ្នាក់ 400 ឡើងវិញសម្រាប់គ្រប់ provider ដែលកំពុងពឹងផ្អែកលើឥរិយាបថអារេលំនាំ) ហើយមិនស្ថិតក្នុងវិសាលភាពសម្រាប់ការបន្ថែមច្បាប់សម្រាប់ provider តែមួយទេ។

#### Egress-bucketed lock (#10880)

Provider ដែលស្ថិតនៅក្នុង `EGRESS_BUCKETED_LOCK_PROVIDERS` (ត្រកូល opencode) ត្រូវបានចាត់ទុកថាជា upstream ដែលបែងចែកតាម IP (កម្រិត free របស់ opencode បែងចែកតាម IP មិនមែនតាមគណនីទេ — មើល #9611)៖ status-429 ដែលត្រូវបានចាត់ថ្នាក់ជា
`quota_exhausted` **ឬ** `rate_limit_exceeded` នឹងដាក់ cooldown លើ connection នៃត្រកូលដែលមានក្នុង allowlist ទាំងអស់
ដែលមាន egress IP ដែលបានស្គាល់ចុងក្រោយ ផ្គូផ្គងនឹង egress IP របស់ connection ដែលបរាជ័យ មុនពេល rotation អាចសាកល្បងពួកវា
— ដើម្បីជៀសវាងការហៅ upstream ដែលត្រូវបរាជ័យជាក់ជាមិនខានចំនួន N-1 ដង (មានរូបរាងដូចគ្នានឹង #10460/#10525)។
`rate_limit_exceeded` ត្រូវបានបញ្ចូលដោយចេតនា៖ នៅលើផ្លូវ `markAccountUnavailable` ច្បាប់ជាក់លាក់របស់ opencode មិនដែលផ្គូផ្គងទេ (គ្មាន headers/body ត្រូវបានបញ្ជូនទៅ `checkFallbackError` ហើយ opencode មិនស្ថិតក្នុង `FULL_TEXT_RULE_PROVIDERS` ទេ) ដូច្នេះ 429 ដែល body របស់វាមានអត្ថបទ subscription-quota ("monthly usage limit
reached") នឹងត្រូវបានចាត់ថ្នាក់ជា `quota_exhausted` ដោយ quota-text fallback
(`buildSubscriptionQuotaFallback`, `accountFallback.ts`; cooldown 1 ម៉ោង) មុនពេលឈានដល់ច្បាប់
`status_429` — ខណៈដែល 429 ដែលគ្មាន quota-text (ការកំណត់អត្រាធម្មតា) នឹងត្រូវបានចាត់ថ្នាក់តាមច្បាប់
`status_429` ជា `rate_limit_exceeded` ហើយនៅតែដាក់ cooldown លើត្រកូល IP ដដែល។ ដែនកំណត់ដែលមានភាពសមហេតុផល៖

- **ប្រឹងប្រែងតាមដែលអាចធ្វើបាន**: lock នឹងដោះស្រាយ `egress_ip` ដែលបានស្គាល់ចុងក្រោយរបស់ connection
  ពី `proxy_logs` (បង្អួច 24h, synchronous, គ្មាន cache)។ Cache ត្រជាក់ (មិនដែល probe
  IP ចេញ) ឬគ្មាន row → connection ដែលបរាជ័យនៅតែត្រូវបានធ្វើឱ្យត្រជាក់ដោយ branch
  (កត់ត្រាដូចបច្ចុប្បន្ន) មានតែ sibling ប៉ុណ្ណោះដែលមិនត្រូវបាន lock។
- **មិនដែលជាស្ថានភាពបញ្ចប់**: cooldown គឺជាបង្អួច quota ដែលបន្តធ្វើថ្មី
  (`testStatus: "unavailable"`)។ ស្ថានភាពអចិន្ត្រៃយ៍មិនដែលត្រូវបានសន្និដ្ឋានពីសញ្ញាកម្រិត IP ទេ។ Connection ដែលមាន `disableCooling` នឹងរំលង branch ទាំងស្រុង។
- **កម្រិត lock ផ្លាស់ប្តូរសម្រាប់គ្រួសារ allowlisted**: នេះគឺជាការផ្លាស់ប្តូរ scope មិនមែនគ្រាន់តែជាការបង្កើនប្រសិទ្ធភាព sibling ទេ។ opencode គឺជា provider `passthroughModels` ដូច្នេះមុនពេល branch នេះ 429 នឹងបង្កើតការចាក់សោតាម MODEL; ឥឡូវនេះវាបង្កើត cooldown សម្រាប់ connection — រួមទាំងករណី operator ដំណើរការ connection តែមួយដែលគ្មាន sibling ទាល់តែសោះ។ នេះគឺជាកម្រិតដែលតារាងច្បាប់ opencode បានប្រកាសរួចហើយថាត្រឹមត្រូវ (`scope: "connection"`,
  `providerErrorRules.ts`) ប៉ុន្តែមិនដែលត្រូវបានគោរពរហូតមកដល់ពេលនេះ ព្រោះ opencode មិនស្ថិតក្នុង `HONORS_RULE_LOCK_SCOPE_PROVIDERS`។ Branch នឹងសរសេរ cooldown របស់ connection ដែលបរាជ័យ + `backoffLevel` ដោយខ្លួនឯង ដោយធ្វើតាម branch agentrouter ដែលមាន scope ជា connection ហើយ return — per-model block និង generic path ខាងក្រោមនឹងមិនត្រូវបានឈានដល់ទេ។
- **រួមបញ្ចូល Combo**: ដូចជា branch agentrouter ដែរ scope នេះចេតនាមិនអើពើនឹងការបន្ថយ `persistUnavailableState`/`isCombo` ដែល combo caller អនុវត្តចំពោះ 429។ ការចាក់សោតាម model មិនមែនជាទម្រង់ខ្សោយជាងនៃ scope នេះទេ វាគឺជាឯកតាខុស៖ វាមិនប្រាប់អ្វីសោះអំពី IP ដែលអស់សមត្ថភាព ដូច្នេះការបង្វិល combo នឹងបន្តខាតការហៅដែលបរាជ័យជាក់ជាមិនខានមួយដងក្នុងមួយ sibling។

  ឬស្ថិតក្នុង cooldown ដែលយូរជាងរួចហើយ នឹងមិនត្រូវបានសរសេរជំនួសឡើយ។

- **ការបង្វិល Egress IP ទាំងពីរទិស**: បង្អួចស្វែងរក (24h) ធំទូលាយជាង egress-IP cache TTL (5 min) ឆ្ងាយណាស់ ដូច្នេះ “last known IP” គឺជាប្រវត្តិ មិនមែនស្ថានភាពបច្ចុប្បន្នទេ។ ប្រសិនបើ proxy របស់ connection មួយបានបង្វិលក្នុងបង្អួចនោះ lock អាច **ខកខាន** IP ដែលចែករំលែកគ្នាពិតប្រាកដ (IP ដែលបានកត់ត្រាគឺជា IP ថ្មី ដែលមិនទាន់អស់សមត្ថភាព) — ហើយតាមសញ្ញាដូចគ្នា វាអាច **ធ្វើឱ្យ sibling ត្រជាក់** ដែលបានបង្វិលចេញពី IP ដែលអស់សមត្ថភាពរួចទៅហើយ។ ករណីទីពីរនឹងធ្វើឱ្យ sibling នោះខាតបង់ cooldown window មួយ; ទាំងពីរត្រូវបានទទួលយកជាដែនកំណត់ best-effort នៃការស្វែងរកផ្អែកលើប្រវត្តិ។
- **ថ្លៃដើម**: ការស្កេន `proxy_logs` ចំនួនពីរដែលមានព្រំដែន (ត្រងតាមបង្អួចដោយប្រើ `idx_pl_timestamp`) តែពេលមាន 429 ប៉ុណ្ណោះ។ មិនមាន index ថ្មីទេ (migration 134 YAGNI)។ បានវាស់វែងលើច្បាប់ចម្លង DB ដែលមានចរាចរណ៍ពិត និងទំហំមធ្យម; instance ដែលមាន throughput ខ្ពស់នឹងរក្សាទុក rows ច្រើនជាងតាមសមាមាត្រនៅក្នុងបង្អួចដដែល។

breaker ប្រើការស្តារឡើងវិញបែប lazy មិនមែនប្រើ background timer ទេ។ នៅពេល `OPEN` ផុតកំណត់ ការអានដូចជា `getStatus()`, `canExecute()` និង `getRetryAfterMs()` នឹង refresh ស្ថានភាពទៅជា `HALF_OPEN` ដូច្នេះ dashboard និង combo candidate builder មិនបន្តដកចេញ provider ដែលផុតកំណត់ជាអចិន្ត្រៃយ៍ទេ។

### Cooldown តំណភ្ជាប់

**វិសាលភាព**: តំណភ្ជាប់/គណនី/key របស់ provider មួយ។

**គោលបំណង**: រំលង key/គណនីដែលមានបញ្ហាមួយជាបណ្តោះអាសន្ន ខណៈដែលអនុញ្ញាតឱ្យតំណភ្ជាប់ផ្សេងទៀតសម្រាប់ provider ដដែលបន្តបម្រើសំណើ។

**ការអនុវត្ត**:

- ផ្លូវសរសេរ/ធ្វើបច្ចុប្បន្នភាព: `src/sse/services/auth.ts::markAccountUnavailable()`
- ការជ្រើសរើស/តម្រងគណនី: `src/sse/services/auth.ts::getProviderCredentials...`
- ការគណនា cooldown: `open-sse/services/accountFallback.ts::checkFallbackError()`
- ការកំណត់: `src/lib/resilience/settings.ts`

Field សំខាន់ៗលើតំណភ្ជាប់ provider:

```ts
rateLimitedUntil;
testStatus: "unavailable";
lastError;
lastErrorType;
errorCode;
backoffLevel;
```

ក្នុងអំឡុងការជ្រើសរើសគណនី តំណភ្ជាប់ត្រូវបានរំលង នៅពេល:

```ts
new Date(rateLimitedUntil).getTime() > Date.now();
```

Cooldown ក៏ជាបែប lazy ដែរ៖ នៅពេល `rateLimitedUntil` កន្លងផុតទៅហើយ តំណភ្ជាប់នឹងមានសិទ្ធិឡើងវិញ។ នៅពេលប្រើប្រាស់បានជោគជ័យ `clearAccountError()` នឹងសម្អាត `testStatus`, `rateLimitedUntil`, field កំហុស និង `backoffLevel`។

អាកប្បកិរិយា cooldown តំណភ្ជាប់លំនាំដើម:

- Cooldown មូលដ្ឋាន OAuth: `5s`។
- Cooldown មូលដ្ឋាន API-key: `3s`។
- API-key `429` គួរផ្តល់អាទិភាពលើ retry hint ពី upstream (`Retry-After`, reset header ឬអត្ថបទ reset ដែលអាច parse បាន) នៅពេលមាន។
- ការបរាជ័យដែលអាចស្តារបាន ដែលកើតឡើងដដែលៗ ប្រើ exponential backoff:

```ts
baseCooldownMs * 2 ** failureIndex;
```

ការការពារ anti-thundering-herd បង្ការការបរាជ័យ concurrent លើតំណភ្ជាប់ដដែល មិនឱ្យពង្រីក cooldown ដដែលៗ ឬបង្កើន `backoffLevel` ទ្វេដង។

ស្ថានភាព terminal មិនមែនជា cooldown ទេ។ `banned`, `expired` (ដែលក្លាយជា terminal បន្ទាប់ពីការព្យាយាមឡើងវិញដែលមានដែនកំណត់ N ដងតាមរយៈ `EXPIRED_RETRY_MAX`) និង `credits_exhausted` មានគោលបំណងឱ្យនៅមិនអាចប្រើបាន រហូតដល់ credential/ការកំណត់ផ្លាស់ប្តូរ ឬ operator កំណត់ឡើងវិញ។ កុំសរសេរជាន់ស្ថានភាព terminal ដោយស្ថានភាព cooldown បណ្តោះអាសន្ន។

### Model Lockout

**វិសាលភាព**: provider + តំណភ្ជាប់ + model។

**គោលបំណង**: ជៀសវាងការបិទតំណភ្ជាប់ទាំងមូល នៅពេលមានតែ model មួយប៉ុណ្ណោះដែលមិនអាចប្រើបាន ឬត្រូវបានកំណត់ quota សម្រាប់តំណភ្ជាប់នោះ។

ឧទាហរណ៍:

- Provider ដែលមាន quota តាម model នីមួយៗ ដែល return `429`។
- Provider ក្នុងស្រុក (local) ដែល return `404` សម្រាប់ model ដែលបាត់មួយ។
- ការបរាជ័យសិទ្ធិ mode/model ជាក់លាក់របស់ provider ដូចជា Grok mode ដែលបានជ្រើសរើស។

Model lockout ស្ថិតនៅក្នុង `open-sse/services/accountFallback.ts` ហើយអនុញ្ញាតឱ្យតំណភ្ជាប់ដដែលបន្តបម្រើ model ផ្សេងទៀត។

### ការណែនាំអំពីការ Debug

- ប្រសិនបើ key ទាំងអស់សម្រាប់ provider ត្រូវបានរំលង សូមពិនិត្យទាំងស្ថានភាព breaker របស់ provider និង `rateLimitedUntil`/`testStatus` របស់តំណភ្ជាប់នីមួយៗ។
- ប្រសិនបើ provider ហាក់ដូចជាត្រូវបានដកចេញជាអចិន្ត្រៃយ៍បន្ទាប់ពី reset window សូមពិនិត្យមើលថាតើ code កំពុងអាន `state` ដោយផ្ទាល់ ជំនួសឱ្យការប្រើ `getStatus()`/`canExecute()` ឬទេ។
- ប្រសិនបើ key របស់ provider មួយបរាជ័យ ប៉ុន្តែ key ផ្សេងទៀតគួរដំណើរការ សូមផ្តល់អាទិភាព connection cooldown ជាង provider breaker។
- ប្រសិនបើមានតែ model មួយប៉ុណ្ណោះដែលបរាជ័យ សូមផ្តល់អាទិភាព model lockout ជាង connection cooldown។
- ប្រសិនបើស្ថានភាពមួយគួរស្តារឡើងវិញដោយខ្លួនឯង វាគួរមាន timestamp/reset timeout នាពេលអនាគត និងផ្លូវអានដែល refresh ស្ថានភាពដែលផុតកំណត់។ ស្ថានភាពអចិន្ត្រៃយ៍ត្រូវការការផ្លាស់ប្តូរ credential ឬ config ដោយដៃ។
