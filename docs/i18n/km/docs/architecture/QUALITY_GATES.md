## បញ្ជី Gate និងប្រូហ្វាល់ប្រតិបត្តិការ

### ការទទួលយកបេក្ខភាព

Workflow CI និង Quality Gates នីមួយៗបញ្ចេញសេចក្ដីសម្រេចដែលមានឈ្មោះថេរ៖ `Gate / CI` និង
`Gate / Quality`។ គោលការណ៍ទទួលយកដែលមានកំណែរបស់ពួកវា រាយបញ្ជី job ខាងដើមទាំងអស់
ថាជា required ឬ advisory។ job ដែល required ហើយអាចអនុវត្តបាន ត្រូវតែជោគជ័យ៖ លទ្ធផលដែលបាត់,
ត្រូវបានលុបចោល, ត្រូវបានរំលង, កំពុងរង់ចាំ និងមិនស្គាល់ មិនអាចបញ្ជាក់ PASS បានទេ។ ការចាត់ថ្នាក់
docs-only ឬ catalog-only ដែលមានសុពលភាព អាចធ្វើឱ្យ code lane មិនអាចអនុវត្តបាន;
draft PR មិនមែនជាបេក្ខភាពដែលត្រូវបានទទួលយកទេ។ ស្លាក `hotfix` មិនលើកលែងភស្តុតាងឡើយ។

Workflow ទាំងពីរគ្របដណ្ដប់លើ PRs ដែលចូលទៅក្នុង branch main/release, push ទៅ `main`, manual dispatch
និងព្រឹត្តិការណ៍ merge-group។ Push, dispatch និង merge-group ដំណើរការជម្រើសពេញលេញ។ Push ទៅ
`release/**` មិនចាប់ផ្ដើមពួកវាទេ (2026-10-18)៖ ការផ្លាស់ប្ដូរនីមួយៗបានដំណើរការ matrix រួចហើយនៅលើ PR
របស់វា ហើយបន្សំដែលបាន merge គឺជាការងាររបស់ Release-Green (`docs/ops/RUNNER_BOX.md` → Hosted lane)។ Fork
និង merge group ប្រើ hosted runner សម្រាប់ job ដែលបើមិនដូច្នោះទេនឹងជ្រើស self-hosted
runner; ត្រូវផ្ទៀងផ្ទាត់ថាមានសមត្ថភាព hosted គ្រប់គ្រាន់ មុនពេល rollout។

បង្កាន់ដៃ JSON នីមួយៗកំណត់អត្តសញ្ញាណ SHA ដែលបាន checkout, workflow run និង attempt។
CLI បដិសេធភាពមិនត្រូវគ្នារវាង checkout/event SHA។ ការធ្វើតេស្ត Workflow ភ្ជាប់សមាជិកភាពគោលការណ៍
ទៅនឹងបញ្ជី `needs` របស់ verdict job ដើម្បីកុំឱ្យ lane ថ្មី ឬ lane ដែលបានដកចេញ បាត់ទៅដោយស្ងៀមស្ងាត់។
បង្កាន់ដៃគ្របដណ្តប់លើលំហូរការងាររបស់វាផ្ទាល់ មិនមែនការបោះពុម្ពផ្សាយ ការដាក់ឱ្យប្រើប្រាស់ ឬផ្នែកខាងក្នុង
នៃកម្មវិធីស្កេនដែលផ្តល់លទ្ធផលជាការណែនាំដែលមានស្រាប់នោះទេ។ ការកំណត់ឱ្យការត្រួតពិនិត្យដែលពាក់ព័ន្ធជាកាតព្វកិច្ចក្នុងច្បាប់សាខា
គឺជាការផ្លាស់ប្តូរផ្នែករដ្ឋបាលដាច់ដោយឡែកមួយ; ការកំណត់ការងាររបស់វាមិនការពារសាខាដោយខ្លួនឯងទេ។

`API Route Typecheck` គឺជាការត្រួតពិនិត្យលំហូរការងារឯករាជ្យមួយ ដែលស្ថិតនៅក្រៅទាំងសេចក្តីសម្រេចសរុប
និងប្រវត្តិរូបថេររបស់អ្នកសង្កេតការណ៍ពេញលេញក្នុងមូលដ្ឋាន។ សូមពិនិត្យលទ្ធផលរបស់វាដាច់ដោយឡែកសម្រាប់
កំណែដែលត្រូវពិនិត្យជាក់លាក់។ `.github/workflows/api-route-typecheck.yml` ដំណើរការលើ PR ដែលចូលទៅកាន់ `main` ឬ
`release/**` ការរុញកូដទៅកាន់ក្រុមសាខាណាមួយក្នុងចំណោមសាខាទាំងពីរ និងការចាប់ផ្តើមដោយដៃ។ វាមិនមានតម្រងផ្លូវទេ។
ការប្តូរសាខាគោលដៅរបស់ PR ស្នើសុំការត្រួតពិនិត្យថ្មីមួយ; ការកែសម្រួលតួអត្ថបទ/ចំណងជើងប្រើឈ្មោះសម្រាប់តែការសង្កេត
`Admission not requested / API Route Typecheck` ហើយមិនអាចជំនួសការត្រួតពិនិត្យការអនុញ្ញាតបានទេ។
លំហូរការងារនេះមិនប្រកាសគន្លឹះបង្កសម្រាប់ក្រុមបញ្ចូលចូលគ្នាទេ។ ការដាក់ឱ្យប្រើប្រាស់ជួររង់ចាំការបញ្ចូលចូលគ្នាណាមួយដែលទាមទារ
ការត្រួតពិនិត្យនេះ ត្រូវតែរៀបចំឱ្យវាដំណើរការសម្រាប់ព្រឹត្តិការណ៍នោះជាមុនសិន។

### សមត្ថភាពប្រតិបត្តិការ UI

CI ដំណើរការបញ្ជី UI ពេញលេញជា shard matrix `test-vitest` ចំនួនបួន ដោយ shard នីមួយៗមាន worker ច្រើនបំផុត
ពីរ និងមានកាលកំណត់ job 15 នាទីដូចដែលមានស្រាប់។ shard ទីមួយក៏ដំណើរការ
MCP/autoCombo Vitest suite ផងដែរ។ លទ្ធផល job ដែល required គ្របដណ្ដប់លើ matrix leg នីមួយៗ; ការបរាជ័យ
ឬការលុបចោល shard មួយ មិនអាចបញ្ជាក់ការទទួលយកបេក្ខភាពបានទេ។

nightly observer រក្សាទុកបង្កាន់ដៃ exact-candidate ដាច់ដោយឡែកសម្រាប់ UI shard នីមួយៗ
រួមទាំងការប្រតិបត្តិ MCP ក្នុងបង្កាន់ដៃទីមួយ។ បង្កាន់ដៃទាំងបួន, log និង
អត្តសញ្ញាណប្រតិបត្តិដែលត្រូវគ្នា សុទ្ធតែត្រូវបានទាមទារ។ `npm run test:vitest:ui` នៅ local នៅតែជ្រើស
suite ពេញលេញ; ការដំណើរការ `--shard` មួយគ្រាន់តែជាភស្តុតាងមួយផ្នែកប៉ុណ្ណោះ។

#### របាយការណ៍អំពី sibling tests ដែលត្រូវបានភ្លេច

`npm run check:forgotten-sibling-tests` ប្រើកម្មវិធីដោះស្រាយ import ដែលនៅពីក្រោយផែនទីផលប៉ះពាល់នៃតេស្តឡើងវិញ។
សម្រាប់រាល់ម៉ូឌុល production ដែលបានផ្លាស់ប្ដូរ វារាយការណ៍ខ្សែសង្វាក់ដែលមានលទ្ធផលកំណត់ជាក់លាក់
`changed module/symbol -> static consumer -> candidate sibling test` នៅពេលតេស្តដែលអាចប្រើបាន
មិនមាននៅក្នុង diff របស់ pull request។ សេចក្ដីសង្ខេប Markdown និងលទ្ធផល JSON ត្រូវបានរក្សាទុកជា
artifact នៃ workflow `forgotten-sibling-tests` សម្រាប់ការក្រិតតម្រូវ មុនពេលដាក់ឱ្យប្រើជារបាំងណាមួយ។

ការនាំចេញបន្តតាម barrel និង dynamic imports គ្រាន់តែជាការវិនិច្ឆ័យការដោះស្រាយប៉ុណ្ណោះ; ពួកវាមិនដែលបង្កើត
ការរកឃើញដែលរារាំងឡើយ។ ករណីលើកលែងដែលបានពិនិត្យរួច មាននៅក្នុង
`config/quality/forgotten-sibling-allowlist.json`។ ធាតុនីមួយៗត្រូវតែបញ្ជាក់ឈ្មោះអ្នកប្រើប្រាស់ និងតេស្តដែលអាចប្រើបាន
ផ្ដល់ហេតុផលជាក់លាក់ និងភ្ជាប់ទៅកាន់ GitHub issue ឬ pull request។ ធាតុដែលមានទម្រង់មិនត្រឹមត្រូវ
នឹងត្រូវបរាជ័យដោយសុវត្ថិភាព។ ករណីលើកលែងមិនអាចលាក់បាំងតេស្តដែលអាចប្រើបានហើយត្រូវបានលុប ឬ diff ដែលបន្ថែម `.skip`/`.todo` បានទេ;

   គ្របដណ្តប់លើវា)៖ បន្ថែមធាតុ allowlist ដោយមាន comment បញ្ជាក់ហេតុផល និង tracking issue។
