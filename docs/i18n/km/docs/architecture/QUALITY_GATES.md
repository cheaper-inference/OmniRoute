## សារពើភ័ណ្ឌច្រកទ្វារ និងទម្រង់ការប្រតិបត្តិ

### ការចុះឈ្មោះបេក្ខជន

លំហូរការងារ CI និង Quality Gates នីមួយៗបញ្ចេញនូវសាលក្រមដែលមានស្ថេរភាព៖ `Gate / CI` និង `Gate / Quality`។ គោលការណ៍ទទួលបានកំណែរបស់ពួកគេបានចុះបញ្ជីរាល់ការងារខាងលើតាមតម្រូវការ ឬការប្រឹក្សា។ ការងារដែលត្រូវការដែលអាចអនុវត្តបានត្រូវតែជោគជ័យ៖ បាត់ លុបចោល រំលង មិនទាន់សម្រេច និងលទ្ធផលមិនស្គាល់មិនអាចបង្កើត PASS បានទេ។ ការចាត់ថ្នាក់សម្រាប់តែឯកសារ ឬតែកាតាឡុកដែលមានសុពលភាពអាចធ្វើឱ្យផ្លូវកូដមិនអាចអនុវត្តបាន។ សេចក្តីព្រាងធម្មតា PR មិនមែនជាបេក្ខជនដែលទទួលយកទេ។ ស្លាក `hotfix` មិនលះបង់ភស្តុតាងទេ។

លំហូរការងារទាំងពីរគ្របដណ្តប់ PRs ចូលទៅក្នុងសាខា main/release រុញទៅ `main` ការបញ្ជូនដោយដៃ និងព្រឹត្តិការណ៍ក្រុមបញ្ចូលគ្នា។ រុញ បញ្ជូន និងបញ្ចូលក្រុម ដំណើរការការជ្រើសរើសពេញលេញ។ សេចក្តីព្រាងជួរដែលគួរឱ្យទុកចិត្ត Mergify ក៏ដំណើរការការងារ `full-code`/`full-code-e2e` ផងដែរ។ PRs ធម្មតារំលងពួកគេ។ មុនពេលបញ្ចូលគ្នាដោយដៃ ដំណើរការការបញ្ជូនពេញលេញលើបេក្ខជនពិតប្រាកដ។ ការជំរុញទៅ `release/**` មិនចាប់ផ្តើមលំហូរការងារទាំងនេះទេ។ Release-Green សង្កេតមើលមូលដ្ឋានរួមបញ្ចូលគ្នាដោយឡែកពីគ្នា (`docs/ops/RUNNER_BOX.md` → Hosted lane)។ សម និងក្រុមបញ្ចូលគ្នាប្រើអ្នករត់ដែលរៀបចំសម្រាប់ការងារដែលជ្រើសរើសអ្នករត់ដែលរៀបចំដោយខ្លួនឯង សមត្ថភាពរៀបចំគ្រប់គ្រាន់ត្រូវតែផ្ទៀងផ្ទាត់មុនពេលដាក់ឱ្យដំណើរការ។

PR ធម្មតាដំណើរការការជ្រើសរើសលឿន។ ផ្លូវ `full-code` និង `full-code-e2e` នៃគោលការណ៍ចូលរៀន (E2E, ការរួមបញ្ចូល , វត្ថុបុរាណកញ្ចប់ , ផ្សែង Electron, Bun SQLite, ប្រព័ន្ធអេកូឡូស៊ី និងអតិថិជនពិធីការ) ដំណើរការតែលើសេចក្តីព្រាងជួរបញ្ចូលគ្នា ឬដំណើរការពេញលេញប៉ុណ្ណោះ៖ `gh workflow run ci.yml --ref <branch>`។

បង្កាន់ដៃ JSON នីមួយៗកំណត់អត្តសញ្ញាណ SHA ដែលបានពិនិត្យចេញ លំហូរការងារ និងការព្យាយាម។ CLI បដិសេធការមិនស៊ីគ្នា checkout/event SHA ។ ការធ្វើតេស្តលំហូរការងារភ្ជាប់សមាជិកភាពគោលនយោបាយទៅនឹងបញ្ជី `needs` របស់ការងារសាលក្រម ដូច្នេះផ្លូវថ្មី ឬដែលត្រូវបានដកចេញមិនអាចបាត់ដោយស្ងៀមស្ងាត់បានទេ។ បង្កាន់ដៃនេះគ្របដណ្តប់លើដំណើរការការងារផ្ទាល់របស់ពួកគេ មិនមែនការបោះពុម្ព ការដាក់ឱ្យប្រើប្រាស់ ឬផ្នែកខាងក្នុងនៃម៉ាស៊ីនស្កេនផ្តល់ប្រឹក្សាដែលមានស្រាប់នោះទេ។ ការធ្វើការត្រួតពិនិត្យដែលអាចអនុវត្តបានដែលទាមទារនៅក្នុងច្បាប់សាខាគឺជាការផ្លាស់ប្តូរផ្នែករដ្ឋបាលដាច់ដោយឡែក។ ការកំណត់ការងាររបស់ពួកគេមិនបានការពារសាខាដោយខ្លួនឯងនោះទេ។

`API Route Typecheck` គឺជាការត្រួតពិនិត្យលំហូរការងារឯករាជ្យ នៅខាងក្រៅសាលក្រមសរុប និងទម្រង់ឋិតិវន្តពេញលេញរបស់អ្នកសង្កេតការណ៍ក្នុងស្រុក។ ពិនិត្យលទ្ធផលរបស់វាដាច់ដោយឡែកសម្រាប់បេក្ខជនពិតប្រាកដ។ `.github/workflows/api-route-typecheck.yml` ដំណើរការលើ PRs ចូលទៅក្នុង `main` ឬ `release/**` រុញទៅក្រុមគ្រួសារសាខាណាមួយ ការបញ្ជូនដោយដៃ និងព្រឹត្តិការណ៍ `merge_group` នៃប្រភេទ `checks_requested`។ វាមិនមានតម្រងផ្លូវទេ។ បញ្ចូលក្រុមពិនិត្យមើល `merge_group.head_sha`; ព្រឹត្តិការណ៍ផ្សេងទៀតពិនិត្យមើល `github.sha`។ ព្រឹត្តិការណ៍ទាំងអស់ប្រើការវិនិច្ឆ័យ API ដូចគ្នា និងការធ្វើតេស្តឯកតាច្រកទ្វារ។ ការកំណត់មូលដ្ឋាន PR ស្នើសុំការត្រួតពិនិត្យថ្មី; ការកែសម្រួល body/title ប្រើឈ្មោះសម្រាប់តែសង្កេត `Admission not requested / API Route Typecheck` ហើយមិនអាចជំនួសការត្រួតពិនិត្យការចូលរៀនបានទេ។

### ភស្តុតាងត្រូវបានរក្សាទុកនៅក្នុងឧបករណ៍កាត់បន្ថយការទទួលយក

`scripts/quality/validate-release-acceptance.mjs` កាត់បន្ថយផែនការដែលបានផ្គត់ផ្គង់ និងការបង្ហាញរបស់វា; វាមិនបានកំណត់ថាផែនការនេះគ្របដណ្តប់លើបំពង់បង្ហូរចេញទាំងស្រុងទេ។ របាយការណ៍របស់វាកំណត់ `releaseAcceptance: false` យ៉ាងច្បាស់លាស់ ទោះបីជាផែនការនោះជា `VERIFIED` ក៏ដោយ។ លំហូរការងារ `release-acceptance.yml` នៅតែប្រើ shadow fixtures មិនមែនជាការបង្កើតពិតប្រាកដ កញ្ចប់ ចាប់ផ្ដើម ឬបង្កាន់ដៃផ្សព្វផ្សាយទេ។

CLI តម្រូវឱ្យ `--evidence-root` ផ្ទៀងផ្ទាត់ភស្តុតាងដែលរក្សាទុក។ ឯកសារត្រូវបានដោះស្រាយជា `<evidence-root>/<artifact_id>/<member>` និងហាសជា SHA-256។ កំណត់ត្រា PASS ដោយគ្មានភ័ស្តុតាង ឯកសារបាត់ ឬផ្លាស់ប្តូរ ផ្លូវមិនមានសុវត្ថិភាព ឬតំណភ្ជាប់និមិត្តសញ្ញារារាំងការផ្ទៀងផ្ទាត់។ ឯកសារដែលបាត់គឺមិនស្មើនឹងកំណត់ហេតុជោគជ័យទទេនោះទេ។ ការត្រួតពិនិត្យ SHA/run/attempt ដែលមានស្រាប់នៅតែឯករាជ្យ៖ បៃដែលត្រូវគ្នាមិនអាចជួយសង្គ្រោះបង្កាន់ដៃដែលជាប់គាំងបានទេ។ ភាពត្រឹមត្រូវនៃឯកសារមិនមែនជាភស្តុតាងនៃភាពត្រឹមត្រូវនៃការប្រតិបត្តិឬការផ្សព្វផ្សាយវត្ថុបុរាណនោះទេ។

### DAST ប្រើប្រាស់ការស្ថាបនា CI ដែលបានផ្ទៀងផ្ទាត់

ការងារ `dast-smoke` CI ដែលត្រូវការ ហៅ `.github/workflows/dast-smoke.yml` បន្ទាប់ពី `build`។ វាធ្វើតាមការជ្រើសរើស code/draft ដូចគ្នាទៅនឹងការស្ថាបនា រួមទាំង fork ដែលគាំទ្រ PRs, release-target PRs និងក្រុមបញ្ចូលគ្នា។ បាត់ បរាជ័យ លុបចោល ឬរំលងការងារ DAST ដោយមិនបានរំពឹងទុក រារាំង `Gate / CI`។ លំហូរការងារដែលអាចប្រើឡើងវិញបានមិនមានកេះ PR/dispatch ឯករាជ្យទេ។ សុពលភាពដោយដៃប្រើការបញ្ជូនរបស់ CI ដូច្នេះការស្ថាបនា និងអ្នកប្រើប្រាស់នៅតែដំណើរការតែមួយ។

`scripts/ci/next-build-provenance.mjs` ផ្សាភ្ជាប់វត្ថុបុរាណបន្ទាប់ពេញលេញជាមួយនឹងការរំលាយ tar, repository/event/run, ការប៉ុនប៉ងរបស់អ្នកផលិត, head/base/checkout/tree, អត្តសញ្ញាណលំហូរការងារ, ឯកសារចាក់សោ, ថ្នាំងពិតប្រាកដ version/ABI, វេទិកា និងកញ្ចប់។ DAST ជ្រើសរើសវត្ថុបុរាណដែលមិនអាចផ្លាស់ប្តូរបាន ID ពី `needs.build.outputs` ទាមទារការផ្ទៀងផ្ទាត់ការទាញយកការរំលាយ និងបំបែក ZIP ដោយឯករាជ្យប្រឆាំងនឹងការរំលាយរបស់អ្នកផលិត មុនពេលទាញយកសមាជិកដែលបានអនុញ្ញាតទាំងពីររបស់ខ្លួនតាមរយៈ `scripts/ci/unpack-ci-build.py`។ ឯកសារ manifest និង tar ត្រូវតែផ្គូផ្គងលទ្ធផលរបស់អ្នកផលិតឯករាជ្យ មុនពេលដែលដើមឈើបន្ទាប់ត្រូវបានស្រង់ចេញ។ វាមិនដែលស្វែងរកការស្ថាបនាសាខាដែលជោគជ័យចុងក្រោយបង្អស់នោះទេ។ ការដំណើរការឡើងវិញដោយផ្នែកអាចប្រើការប៉ុនប៉ងរបស់អ្នកផលិតដដែលនោះឡើងវិញ នៅពេលដែល ID និងធាតុបញ្ចូលទាំងអស់នៅតែត្រូវគ្នា។ បង្កាន់ដៃកត់ត្រាការប៉ុនប៉ងទាំងពីរ។

អ្នកប្រើប្រាស់ស្នាក់នៅលើកម្មវិធីរត់ Linux ដែលរៀបចំដោយមានការអនុញ្ញាតពីឃ្លាំងសម្រាប់តែអាន និងគ្មានអាថ៌កំបាំងនៃឃ្លាំង។ វាដំឡើងកំណែ Node ពិតប្រាកដរបស់អ្នកផលិត បន្ទាប់មកប្រមូលផ្តុំ CLI ជាមួយ `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1`។ `scripts/build/standaloneInput.mjs` បដិសេធម៉ាស៊ីនបម្រើឯករាជ្យដែលបាត់មុនពេលបង្កើតការត្រឡប់ ការស្ថាបនា CLI ក្នុងស្រុកធម្មតារក្សាការថយក្រោយដែលមានស្រាប់របស់ពួកគេ។ ការត្រៀមខ្លួនរបស់ម៉ាស៊ីនមេ គ្រោងការណ៍ និង promptfoo ត្រូវតែជោគជ័យក្នុងដែនកំណត់ការងារ 25 នាទីដែលមិនផ្លាស់ប្តូរ។ បង្កាន់ដៃបញ្ជាក់បញ្ជាក់អត្តសញ្ញាណបញ្ចូល និងបៃ មិនមែនជាការស្កេន DAST ជោគជ័យទេ។ ការផុតកំណត់វត្ថុបុរាណ ការរំខានរបស់អ្នករត់ ឬម៉ាស៊ីនស្កេនដែលបរាជ័យនៅតែជាភស្តុតាងមិនពេញលេញ ឬបរាជ័យ។ វាមិនអាចក្លាយជា PASS តាមរយៈកញ្ចប់ប្រឹក្សាទេ។

### សមត្ថភាពប្រតិបត្តិUI

អ្នកសង្កេតការណ៍ពេលយប់រក្សាបង្កាន់ដៃបេក្ខជនជាក់លាក់ដាច់ដោយឡែកសម្រាប់ UI shard នីមួយៗ រួមទាំងការប្រតិបត្តិ MCP នៅក្នុងបង្កាន់ដៃដំបូង។ បង្កាន់ដៃ កំណត់ហេតុ និងអត្តសញ្ញាណប្រតិបត្តិដែលត្រូវគ្នាទាំងបួនត្រូវបានទាមទារ។ `npm run test:vitest:ui` ក្នុងស្រុកនៅតែជ្រើសរើសឈុតពេញលេញ។ ការរត់ `--shard` មួយគ្រាន់តែជាភស្តុតាងមួយផ្នែកប៉ុណ្ណោះ។

### ការប្រមូលផ្នែកគ្របដណ្តប់

គ្រឿងចក្រទាំងដប់ពីរប្រមូលការគ្របដណ្តប់ V8 កំឡុងពេលអនុវត្តការសាកល្បងដែលមានស្រាប់របស់ពួកគេ។ shard ជោគជ័យដំណើរការ `scripts/ci/compact-v8-coverage.mjs` ដើម្បីបង្ហាប់ឯកសារដើមដោយមិនបង្កើតរបាយការណ៍មធ្យមអ៊ីស្តង់ប៊ុល។ ការងារ Coverage ចុងក្រោយផ្ទៀងផ្ទាត់ការបង្ហាញទាំងដប់ពីរប្រឆាំងនឹងបេក្ខជន SHA ពេលវេលាដំណើរការ ប្រភព root និងទិន្នន័យ hash បន្ទាប់មកដំណើរការអ្នករាយការណ៍របស់ c8 និងកម្រិតនៃការគ្របដណ្តប់ដែលមានស្រាប់។ ធាតុបញ្ចូលរក្សាលំដាប់ឈ្មោះឯកសារសកលរបស់ c8 ។ ការរួមបញ្ចូលគ្នាជាមុនក្នុងមួយ shard គឺមិនមានសុវត្ថិភាពសម្រាប់ការគ្របដណ្តប់ function/block ចម្រុះ។ បំណែកដែលបាត់ ខូចទ្រង់ទ្រាយ ឬមិនត្រូវគ្នា បរាជ័យក្នុងការចូលរៀន។ បន្ទះសាកល្បងដែលបរាជ័យរក្សាការរ៉ាប់រងការវិនិច្ឆ័យឆៅដាច់ដោយឡែក។ វាមិនអាចចូលទៅក្នុងការរួមបញ្ចូលគ្នាចុងក្រោយបានទេ។

### បង្កាន់ដៃដំណើរការដំណើរការផ្នែក

ពាក្យបញ្ជា `test:unit:ci:shard` ដែលបានចែករំលែកកត់ត្រាដំណាក់កាល `primary`, `dashboard` និង `serial` តាមរយៈ `scripts/ci/unit-progress-reporter.mjs`។ របាយការណ៍តេស្តធម្មតានៅតែមាន។ បង្កាន់ដៃសម្រាប់តែទិន្នន័យមេតាដាច់ដោយឡែកមួយកត់ត្រាការចាប់ផ្តើម និងការបញ្ចប់របស់ឯកសារនីមួយៗ ហើយចង្វាក់បេះដូង 30 វិនាទីរាយបញ្ជីឯកសារដែលនៅតែសកម្ម និងពេលវេលាដែលបានកន្លងផុតទៅ។ វាកត់ត្រាតែទិន្នន័យមេតានៃការប្រតិបត្តិដែលបានអនុញ្ញាតប៉ុណ្ណោះ។ ការពិពណ៌នាការសាកល្បង លទ្ធផល តួនៃកំហុស និងបរិស្ថានពេញលេញមិនត្រូវបានដាក់ជាស៊េរីទេ។

CI រក្សាឯកសារ JSONL ជា `unit-progress-ci-<run>-<attempt>-<shard>`។ ការអស់ពេលនៃការងារអាចការពារការបង្ហោះនៅពេលក្រោយ។ ចង្វាក់បេះដូងដែលបញ្ចេញរួចហើយ នៅតែជាភស្តុតាងនៃការវិនិច្ឆ័យ។ ការបាត់ចង្វាក់បេះដូងក៏អាចឆ្លុះបញ្ចាំងពីដំណើរការរបស់អ្នករត់ដែលត្រូវបានរារាំង ឬត្រូវបានបញ្ចប់ផងដែរ។ បង្កាន់ដៃទាំងនេះរក្សាការជ្រើសរើសការធ្វើតេស្តដែលមានស្រាប់ ភាពស្របគ្នា ថ្ងៃផុតកំណត់ និងស្ថានភាពចេញ។ ពួកគេមិនមែនជាសាលក្រមបេក្ខជន-បេក្ខភាពទេ។

### បញ្ចូលជួរ

ស្លាក `queue` ផ្ញើ PR ទៅកាន់ជួររួមបញ្ចូលគ្នា (`.mergify.yml`) ។ Mergify បើក PR ព្រាងនៅលើសាខា `mergify/merge-queue/` CI ដំណើរការការជ្រើសរើសពេញលេញនៅទីនោះ ហើយ PR ដើមបញ្ចូលគ្នានៅពេលដែល `Gate / CI`, `Gate / Quality` និង `Merge integrity (changelog + generated skills)` ឆ្លងកាត់។

Mergify សរសេរសេចក្តីសង្ខេបជួររបស់វាទៅក្នុងសេចក្តីពិពណ៌នារបស់សេចក្តីព្រាង។ ព្រឹត្តិការណ៍ Body/title-only `pull_request` `edited` ប្រើក្រុមស្របគ្នាជាក់លាក់ដែលដំណើរការ ហើយមិនដំណើរការឡើងវិញនូវចំណាត់ថ្នាក់ តេស្តម៉ាទ្រីស បញ្ចូលសុចរិតភាព ឬសាលក្រមចូល។ ឈ្មោះពិនិត្យតែការសង្កេតមិនអាចជំនួស `Gate / CI` ឬ `Gate / Quality` បានទេ។ ការកែសម្រួលដែលផ្លាស់ប្តូរមូលដ្ឋានគោលដៅ ស្នើសុំសុពលភាពបេក្ខជនថ្មី។

បន្ទាប់ពីការបញ្ជាទិញ ការជំរុញមិនតែងតែស្នើសុំ PR ទេ។ ផ្តល់យោបល់ `@mergifyio queue` លើវា។

### សារពើភ័ណ្ឌស្កេនឋិតិវន្ត

បញ្ជីសារពើភណ្ឌ npm-alias កំណែ និងសមាជិកភាពស្កែនឋិតិវន្ត រស់នៅក្នុង `config/quality/gate-manifest.json`។ ដំណើរការ `npm run check:gate-manifest` ដើម្បីធ្វើសុពលភាពឈ្មោះស្គ្រីប និងពាក្យបញ្ជាពិតប្រាកដប្រឆាំងនឹង `package.json`; ការបន្ថែម ការដកយកចេញ និងការរសាត់ពាក្យបញ្ជាបរាជ័យទាំងទំពក់ក្នុងតំបន់ និងការងារផ្លាស់ប្តូរចំណាត់ថ្នាក់នៅក្នុង CI។ ឈ្មោះក្លែងក្លាយមិនមែនជាការងារលំហូរការងារទេ ឧទាហរណ៍ម៉ាទ្រីស ឬករណីសាកល្បង៖ ចំនួនទាំងនេះមិនត្រូវបង្ហាញថាអាចផ្លាស់ប្តូរបានទេ។

ប្រើ `npm run quality:scan -- --list` ឬ `npm run quality:scan:fast -- --list` ដើម្បីពិនិត្យមើលឈ្មោះក្លែងក្លាយដែលបានជ្រើសរើសដោយមិនចាំបាច់ប្រតិបត្តិពួកវា។ អ្នករត់ការហៅចំណុចបញ្ចូល npm ដូច្នេះរយៈពេលរត់របស់វា (រួមទាំង Bun ដែលកំណត់រចនាសម្ព័ន្ធ) ត្រូវបានរក្សាទុក។ Manifest កត់ត្រាឈ្មោះក្លែងក្លាយនៅខាងក្រៅទម្រង់ទាំងនោះ ដូចដែលបានហៅដាច់ដោយឡែក ហើយពាក្យបញ្ជាថែទាំត្រូវបានហាមឃាត់នៅក្នុងទម្រង់ស្កេនបានតែអានប៉ុណ្ណោះ។

ទម្រង់ទាំងនេះគ្របដណ្តប់តែការស្កេនឋិតិវន្តប៉ុណ្ណោះ។ ពួកគេមិនបញ្ជាក់ការធ្វើតេស្តផលិតផល ការគ្របដណ្តប់ ការវេចខ្ចប់ ការត្រួតពិនិត្យខាងក្រៅ ឬការទទួលយកការចេញផ្សាយពេញលេញរបស់បេក្ខជននោះទេ។ ការទទួលយកលំហូរការងារប្រើ `config/quality/admission-policy.json` និង `scripts/quality/admission-verdict.mjs` ដែលបានភ្ជាប់។ ទម្រង់អ្នកសង្កេតការចេញផ្សាយនៅដាច់ដោយឡែក។ ត្រួតពិនិត្យការត្រួតពិនិត្យ និងបង្កាន់ដៃដែលអាចអនុវត្តបានដោយឯករាជ្យ។ ពាក្យបញ្ជាឋិតិវន្តរបស់អ្នកសង្កេតការណ៍ពេញលេញត្រូវបានប្រកាសនៅក្នុង `config/quality/release-green-static-profile.json` រួមទាំង `audit:deps` ការជ្រើសរើសការធ្វើតេស្តផ្លាស់ប្តូរ និងការត្រួតពិនិត្យការបកប្រែ។ កម្មវិធីផ្ទុកសុពលភាពពាក្យបញ្ជា npm ប្រឆាំងនឹង package.json និងការប្រកាស CI/Quality គំរូ។ វាច្រានចោលការរសាត់ ជំនួសឱ្យការប្រតិបត្តិសញ្ញាសម្ងាត់សែលជាអាគុយម៉ង់។ ម៉ាស៊ីនស្កេនដែលត្រូវការទិន្នផល SKIP/INCOMPLETE មិនអាចបង្កើត PASS បានទេ។ កម្រងព័ត៌មានកត់ត្រាការមិនរាប់បញ្ចូលខាងក្រៅរបស់វា និងមិនជំនួសការគ្របដណ្តប់ដែលបានបង្ហោះ ការសាកល្បងម៉ាទ្រីស កញ្ចប់ ឬភស្តុតាងដាក់ពង្រាយ។ សារពើភណ្ឌសុភាសិតខាងក្រោមគឺជាឯកសារយោង មិនមែនជាភ័ស្តុតាងដែលថាច្រកទ្វារមួយបានដំណើរការពិតប្រាកដនោះទេ។

ស្គ្រីបរស់នៅក្រោម `scripts/check/` (ច្រកទ្វារគោលនយោបាយ) និង `scripts/quality/` (ម៉ាស៊ីន ratchet) ។ ប្រភពនៃការពិត CI គឺ `.github/workflows/ci.yml`។

### សុខភាពឯកសារមូលដ្ឋានដែលបានបោះពុម្ពផ្សាយ

`.github/workflows/i18n-base-health.yml` សង្កេតមើលសុខភាពឯកសារបន្ទាប់ពីការចុចដែលបានជ្រើសរើសទៅកាន់ `main` និង `release/v*` និងនៅលើការបញ្ជូនដោយដៃ។ តម្រងរបស់វាគ្របដណ្តប់ឯកសារ, ឫស Markdown, `llm.txt`, ការបកប្រែ state/configuration និងឧបករណ៍ i18n ដែលពាក់ព័ន្ធ។ ការងារ `Published base documentation health` តែមួយប្រើអ៊ូប៊ុនទូ និងថ្ងៃផុតកំណត់ប្រាំនាទី។ វាអនុវត្តសុពលភាពបានតែអាន និងសរសេរវិក័យប័ត្រវិនិច្ឆ័យដោយមិនមានការដំឡើងអាស្រ័យ ការបកប្រែ ឬការអនុម័តដោយរដ្ឋ។

`scripts/i18n/check-base-health.mjs` ទាមទារសូន្យប្រភព-hash, បាត់គោលដៅ, target-hash, stale-translation និង section-cache inconsistencies។ វាក៏ផ្តល់សុពលភាពដល់វិសាលភាព document/locale ស្នូលបច្ចុប្បន្ន និងការបញ្ជាក់ដែលបានកត់ត្រារបស់វា។ បរិបទមិនត្រឹមត្រូវ ការគ្របដណ្តប់មិនពេញលេញ ឬអ្នកត្រួតពិនិត្យដែលរំខានបង្កើត `INCOMPLETE`; drift ដែលបានបញ្ជាក់ផលិត `FAIL`។ ទាំងពីរត្រឡប់ស្ថានភាពចាកចេញដែលបរាជ័យ។ បង្កាន់ដៃត្រូវបានចងភ្ជាប់ទៅនឹងការចេញ SHA លំហូរការងារ ដំណើរការ និងការប៉ុនប៉ង ហើយត្រូវបានរក្សាទុកជា `i18n-base-health-<sha>-<run>-<attempt>`។

នេះជាការសង្កេតឯករាជ្យនៃមូលដ្ឋានដែលបានបោះពុម្ពផ្សាយ។ វាមិនបន្ថែមព្រឹត្តិការណ៍ PR ឬការរួមបញ្ចូលគ្នានៃក្រុម ការត្រួតពិនិត្យ PR ដែលត្រូវការ នាមក្លែងក្លាយ npm ឬសមាជិកទម្រង់ស្កែនស្កេត។ កម្មវិធីត្រួតពិនិត្យមូលដ្ឋានក៏ទប់ស្កាត់ថ្នាក់ទាំងប្រាំនៅក្នុងរបៀបដាច់ខាត។ ការរៀបចំ PR ធម្មតានៅតែដាច់ដោយឡែកពីការចូលរៀន។ ការបង្ហោះជោគជ័យមិនអាចប្រែក្លាយលទ្ធផលសុខភាពដែលបរាជ័យទៅជា PASS បានទេ។

PR ធម្មតាប្រើ `--preflight` ជាមួយនឹងរបាយការណ៍មូលដ្ឋានដែលបង្កើតដោយ `--baseline-evidence`។ វាអាចទុកប្រភពភាសាអង់គ្លេសដែលរង់ចាំតែនៅពេលដែលកំណត់ត្រាបកប្រែពេញលេញ និងបៃគោលដៅពិតប្រាកដមិនផ្លាស់ប្តូរពីមូលដ្ឋានពិតប្រាកដនោះ។ គោលដៅថ្មី ឬភាពមិនស៊ីសង្វាក់នៃផ្នែកឃ្លាំងសម្ងាត់នៅតែរារាំង ហើយភស្តុតាងមិនពេញលេញមិនអាចអនុញ្ញាតឱ្យរៀបចំបានទេ។ របាយការណ៍លាតត្រដាង `preparationPending` និង `mergeReady` ដាច់ដោយឡែកពីគ្នា៖ ការរៀបចំដោយជោគជ័យមិនធ្វើឱ្យការបកប្រែដែលមិនទាន់សម្រេចរួចរាល់ដើម្បីបញ្ចូលគ្នាទេ។ ធ្វើឱ្យកញ្ចក់ដែលរងផលប៉ះពាល់ឡើងវិញនៅក្នុងបេក្ខជនដែលបានតែងមុនពេលចូលរៀន។ បេក្ខភាពជួរដែលជឿទុកចិត្តបាន Mergify, `merge_group`, សាខាជំរុញ និងដំណើរការ CI ដោយដៃ ប្រើកម្មវិធីពិនិត្យដាច់ខាត ដោយគ្មាន `--warn` ឬការអភ័យទោសពីការបរាជ័យដែលបានទទួលមរតក។ បាត់សញ្ញាសម្គាល់គោលដៅ និងវិសាលភាពដែលកាត់បន្ថយដោយឯកសារស្នូលដែលបានកត់ត្រាដែលបានលុបមិនអាចបង្កើតសាលក្រមពេញលេញបានជោគជ័យនោះទេ។

#### របាយការណ៏ការធ្វើតេស្តបងប្អូនដែលភ្លេច

`npm run check:forgotten-sibling-tests` ដំណើរការជាជំហានប្រឹក្សារបស់ `Fast Quality Gates` ហើយប្រើឡើងវិញនូវឧបករណ៍ដោះស្រាយការនាំចូលនៅពីក្រោយផែនទីផលប៉ះពាល់សាកល្បង។ សម្រាប់រាល់ម៉ូឌុលផលិតកម្មដែលបានផ្លាស់ប្តូរ វារាយការណ៍អំពីខ្សែសង្វាក់ `changed module/symbol -> static consumer -> candidate sibling test` ដែលកំណត់នៅពេលដែលការធ្វើតេស្តបេក្ខជនអវត្តមានពីភាពខុសគ្នានៃសំណើរទាញ។ សេចក្តីសង្ខេប Markdown និងលទ្ធផល JSON ត្រូវបានរក្សាទុកជាវត្ថុបុរាណនៃលំហូរការងារ `forgotten-sibling-tests` សម្រាប់ការក្រិតតាមខ្នាត មុនពេលការបិទដំណើរការណាមួយ។

ការនាំចេញឡើងវិញនូវធុងបារ៉ែល និងការនាំចូលថាមវន្ត គឺជាដំណោះស្រាយការវិនិច្ឆ័យតែប៉ុណ្ណោះ។ ពួកគេមិនដែលបង្កើតការរកឃើញរារាំងទេ។ ករណីលើកលែងដែលបានត្រួតពិនិត្យរស់នៅក្នុង `config/quality/forgotten-sibling-allowlist.json`។ ធាតុនីមួយៗត្រូវតែដាក់ឈ្មោះការធ្វើតេស្តអតិថិជន និងបេក្ខជន ផ្តល់ហេតុផលជាក់លាក់ និងភ្ជាប់បញ្ហា GitHub ឬសំណើទាញ។ ធាតុខុសទម្រង់មិនបានបិទ។ ករណីលើកលែងមិនអាចរារាំងការធ្វើតេស្តបេក្ខជនដែលបានលុប ឬភាពខុសគ្នាដែលបន្ថែម `.skip`/`.todo` បានទេ ; ការអះអាងចុះខ្សោយ និងការបិទបាំងផ្សេងទៀតនៅតែជាកម្មសិទ្ធិរបស់ច្រក `check:test-masking` ដែលរារាំងដោយឯករាជ្យ។

#### កម្មវិធីវាយអក្សរពីរឆ្លើយខុសគ្នា

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) និង `check:build-typecheck` ចងក្រងកម្មវិធីផ្សេងគ្នានៅក្រោមជម្រើសផ្សេងគ្នា ហើយឯកសារដូចគ្នាអាចស្អាតនៅក្នុងមួយ និងពោរពេញដោយកំហុសនៅក្នុងមួយផ្សេងទៀត។

`tsconfig.build.json` កំណត់ `"strict": false` ដូច្នេះ `noImplicitAny` ត្រូវបានបិទ។ ការកំណត់រចនាសម្ព័ន្ធស្នូលចងក្រងបញ្ជីអនុញ្ញាតឯកសារចំនួន 27 ដែលមានជម្រើសតឹងរ៉ឹង ហើយធ្វើតាមក្រាហ្វនាំចូលរបស់ធាតុនីមួយៗ ដូច្នេះឯកសារដែលមិនដែលបង្ហាញក្នុងកម្មវិធីសាងសង់នៅតែត្រូវបានពិនិត្យនៅទីនោះ។

លទ្ធផលគឺសំខាន់នៅពេលវិនិច្ឆ័យថាតើឯកសារត្រូវបានវាយបញ្ចូល៖**ការធ្វើរោគវិនិច្ឆ័យសូន្យនៅក្រោម `check:build-typecheck` មិនមានន័យថាសូន្យទេ។** . ការដក `@ts-nocheck` ចេញពីឯកសារចំនួន 26 បានបង្ហាញថា 23 នៃពួកគេស្អាតនៅក្នុងកម្មវិធីសាងសង់។ ដប់ប្រាំមួយនៃអ្នកទាំងនោះបានលេចឡើងប្រហែល 120 កំហុសក្នុងការតឹងរ៉ឹង។ ពិនិត្យទាំងពីរមុនពេលហៅឯកសារស្អាត។

ការងារម៉ាទ្រីសនីមួយៗកត់ត្រាការបង្ហោះ SARIF ពិតប្រាកដរបស់ខ្លួន ID ភាសា ប្រភេទ ការរត់ និងការព្យាយាម អត្តសញ្ញាណលំហូរការងារអ្នកហៅ ព្រឹត្តិការណ៍ ref/head/base/merge SHA និងសញ្ញាគោលនយោបាយ។ ការងារដែលពឹងផ្អែកទាញយកតែបង្កាន់ដៃនៃការដំណើរការនេះ និងធ្វើឱ្យមានសុពលភាពការសង្ខេបវត្ថុបុរាណ។ វាទាមទារប្រភេទទាំងបួន ដែលជាអ្នកផលិតជោគជ័យ និងដំណើរការពេញលេញនៃការផ្ទុកឡើងពិតប្រាកដនីមួយៗ។ វាប្រើតម្រង sarif_id របស់ API មិនមែនជាការវិភាគចុងក្រោយបង្អស់ដែលបានរកឃើញនៅលើសាខានោះទេ។ ការដំណើរការឡើងវិញដោយផ្នែកអាចប្រើប្រភេទដែលទទួលបានជោគជ័យឡើងវិញពីការប៉ុនប៉ងពីមុននៃការរត់ដូចគ្នា និងបេក្ខជន ដោយរក្សាការប៉ុនប៉ងផលិត។ អ្នកផលិតបច្ចុប្បន្នដែលបរាជ័យមិនអាចប្រើឡើងវិញនូវភស្តុតាងពណ៌បៃតងពីមុនបានទេ។

សកម្មភាព CodeQL រង់ចាំដំណើរការ ប៉ុន្តែការអនុវត្តដែលបានកំណត់របស់វាអាចព្រមាន និងបន្តបន្ទាប់ពីការបរាជ័យក្នុងការអានស្ថានភាព ឬការរង់ចាំអស់កំលាំង។ ដូច្នេះការចូលរៀនផ្ទៀងផ្ទាត់ដំណើរការម្តងទៀត។ ប្រភេទដែលបាត់ ដំណើរការមិនទាន់សម្រេច ការងារដែលបរាជ័យ ឬលុបចោល អត្តសញ្ញាណជាប់គាំង ទំព័រមិនពេញលេញ ឬមិនអាចប្រើបាន APIs បង្កើត HOLD និងចេញ 2។ គ្មានការរង់ចាំថេរសម្រាប់លំហូរការងាររបស់ម៉ាស៊ីនស្កេនឯករាជ្យនៅតែមាន។ PR ដែលមិនបានស្កែនមិនអាចឆ្លងកាត់បានទេ ដោយសារសំណួរដាស់តឿនបានត្រឡប់ 0។ ចំនួនដែលបានវាស់វែងខាងលើ `metrics.codeqlAlerts.value` ចេញ 1; បន្ទាត់មូលដ្ឋានមិនត្រូវបានលើកឡើងដើម្បីស្រូបយកការជូនដំណឹងរបស់សាខាផ្សេងទៀតទេ។ [ផ្ទុកឡើងស្ថានភាព និងការវិភាគរកមើល](https://docs.github.com/en/rest/code-scanning/code-scanning) ។

## គោលការណ៍ Allowlist

រាល់ gate ដែលមិនអាចបរាជ័យដោយសារការបំពានដែលមានស្រាប់ ប្រើ allowlist ដែលបានកំណត់ថេរ
(ឧ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)។ គោលការណ៍គឺ៖

**កែតម្រូវមូលហេតុដើម; ប្រើ allowlist តែនៅពេលការបំពានមានស្រាប់ ហើយ
មិនអាចកែតម្រូវក្នុង PR ដូចគ្នាបានប៉ុណ្ណោះ។**

នៅពេលបន្ថែមធាតុមួយទៅក្នុង allowlist៖

1. ដាក់បញ្ចូល comment ដែលមានហេតុផលបញ្ជាក់។
2. យោងទៅ tracking issue (ឧ., `// #3498 — Phase 2 feature, not yet implemented`)។
3. លុបធាតុនោះនៅក្នុង PR ដូចគ្នាដែលកែតម្រូវការបំពាន — ធាតុហួសសម័យដែលលែង
   ទប់ស្កាត់ការបំពានសកម្ម គឺជាកំហុសមួយដោយខ្លួនឯង (ការអនុវត្តច្បាប់លើធាតុហួសសម័យ 6A.3 នឹង
   ធ្វើឱ្យ gate បរាជ័យលើធាតុ allowlist ដែលលែងមានការយោង នៅពេលបានអនុវត្តរួច)។

**កុំ**បន្ថែមធាតុ allowlist ដើម្បីធ្វើឱ្យការធ្វើតេស្តជោគជ័យលឿនជាងមុន។ gate ពណ៌បៃតងដែលមាន
allowlist កាន់តែធំឡើង បង្កើតតែអារម្មណ៍ក្លែងក្លាយអំពីគុណភាពប៉ុណ្ណោះ។

### នៅពេល gate បរាជ័យលើ PR របស់អ្នក

1. **អាន output របស់ gate ដោយប្រុងប្រយ័ត្ន** — វាប្រាប់អ្នកយ៉ាងច្បាស់ថា file ឬ symbol មួយណាបានបំពាន
   ច្បាប់។
2. **កែតម្រូវការបំពាន** — gate ភាគច្រើនជាការត្រួតពិនិត្យ filesystem ដែលមានលទ្ធផលកំណត់ច្បាស់ ហើយនឹងជោគជ័យភ្លាមៗ
   នៅពេល code ត្រឹមត្រូវ។
3. **ប្រសិនបើការបំពានមានស្រាប់** (មានន័យថា អ្នកមិនបានបង្កើតវាទេ ប៉ុន្តែឥឡូវនេះ gate
   គ្របដណ្តប់លើវា)៖ បន្ថែមធាតុ allowlist ដោយមាន comment បញ្ជាក់ហេតុផល និង tracking issue។
4. **ប្រសិនបើ gate ជា ratchet** (coverage, ការព្រមាន ESLint, ការស្ទួន, complexity)៖
   ការផ្លាស់ប្តូររបស់អ្នកបានធ្វើឱ្យ metric កាន់តែអាក្រក់។ កែតម្រូវបញ្ហាមូលដ្ឋាន ឬ (ក្នុងករណីកម្រ) ដំណើរការ
   `npm run quality:ratchet -- --update` ប្រសិនបើការផ្លាស់ប្តូរនោះធ្វើឡើងដោយចេតនា ហើយការធ្លាក់ចុះនៃ metric
   អាចទទួលយកបាន — ប៉ុន្តែត្រូវកត់ត្រាហេតុផលនៅក្នុងសេចក្តីពិពណ៌នា PR។
5. **gate ផ្តល់ដំបូន្មាន** (`continue-on-error: true`) គឺសម្រាប់ផ្តល់ព័ត៌មាន — វាមិនរារាំង
   ការបញ្ចូលចូលគ្នាទេ ប៉ុន្តែបង្ហាញនៅក្នុងសេចក្តីសង្ខេប CI។ ទោះយ៉ាងណាក៏ដោយ សូមកែតម្រូវវា។

**ក៏មិនទាន់បានកត់ត្រាខាងលើ** (ជាយោបល់ សញ្ញាខ្សោយ)៖ ការងារ `docs-lint` (markdownlint + Vale ដោយការងារទាំងមូលប្រើ `continue-on-error`) និង workflow scanner ដាច់ដោយឡែក `semgrep.yml` / `scorecard.yml`។ ឥឡូវ CodeQL មានការងារផលិត និងទទួលយកដែលចាំបាច់ក្រោម `Gate / CI` ដោយអនុវត្តតាមលក្ខខណ្ឌបើកដំណើរការខាងលើ។ `semgrepFindings: 0` មានក្នុង `quality-baseline.json` ប៉ុន្តែមិនបានភ្ជាប់ទៅ ratchet ដែលរារាំងក្នុង `ci.yml` ទេ — បច្ចុប្បន្ន metric នេះគ្មានការត្រួតពិនិត្យអនុវត្តដែលភ្ជាប់ជាមួយ។

### បញ្ចូលចូលគ្នា / លុបភាពស្ទួន (បែបមេកានិច ហានិភ័យទាបជាង)

បេក្ខភាពនីមួយៗត្រូវបានផ្ទៀងផ្ទាត់ទល់នឹងស្ថានភាព gate ជាក់ស្តែងនៅថ្ងៃទី 2026-06-17 (ជឿទុកចិត្ត ប៉ុន្តែត្រូវផ្ទៀងផ្ទាត់);
ការបញ្ចូលចូលគ្នាដែលមើលទៅ "ជាក់ស្តែង" មួយចំនួន បែរជាលាក់បំណុល ហើយ **មិនមែន** ជាការជំនួសដោយផ្ទាល់ដែលស្អាតនោះទេ។

- **`check:docs-sync` ដំណើរការពីរដង** — ដំណើរការដាច់ដោយឡែកនៅក្នុង job `lint` ហើយម្តងទៀតនៅខាងក្នុង `check:docs-all` (`docs-sync-strict`) និង hook មុន commit របស់ husky។ ✅ **រួចរាល់** — បានលុបការហៅដាច់ដោយឡែកក្នុង `lint`។
- **ការស្កេន CVE** — ❌ **មិនមែនជាការបញ្ចូលចូលគ្នាដែលស្អាតទេ។** `audit:deps` ទប់ស្កាត់សេចក្តីជូនដំណឹងកម្រិតធ្ងន់ធ្ងរបំផុត និងការធ្វើសវនកម្មមិនពេញលេញនៅទូទាំង lockfile ទាំងប្រាំ ខណៈពេលរាយការណ៍សេចក្តីជូនដំណឹងកម្រិតខ្ពស់ជាការព្រមានក្រោមគោលនយោបាយបច្ចុប្បន្ន; `check:vuln-ratchet` (osv) បរាជ័យតែនៅពេលមាន _ការថយក្រោយ_ ធៀបនឹង baseline ដែលបាន check in ហើយបដិសេធ measurement ដែលបាត់ នៅពេលវាត្រូវបានទាមទារ។ semantics ខុសគ្នា — ការដក `audit:deps` នឹងធ្វើឱ្យបាត់ absolute critical gate និងបង្កាន់ដៃសវនកម្ម package ឯករាជ្យ។ រក្សាទុកទាំងពីរ។
- **ការរកឃើញ cycle** — ✅ **រួចរាល់** (#15159 G-01/G-02)។ អត្ថបទចាស់នៅទីនេះបានហៅ `check:cycles` ថាជា gate "បៃតង ដែលបានជ្រើសរើសដោយប្រុងប្រយ័ត្ន" ហើយបានអះអាងថាគួររក្សាវាឱ្យនៅជាការទប់ស្កាត់ ព្រោះ `check:circular-deps` (dpdm) បានរាយការណ៍ cycle ចំនួន 91។ ភាពបៃតងនោះគឺជា **ភាពបៃតងក្លែងក្លាយ**៖ `check:cycles` បានស្កេនថតរងចំនួន 5 (450 files) ផ្គូផ្គងតែ static `import|export … from` ហើយបានទម្លាក់ specifier `@/` និង `@omniroute/open-sse/` ទាំងអស់ ដូច្នេះវាមិនអាចមើលឃើញ cycle នៃ dynamic-import + alias ដែលមានច្រើនលើសលប់ក្នុង repo បានទេ។ បានកែរួច៖ ឥឡូវ gate នេះដើរកាត់ `src` + `open-sse` (5023 files) ប្រមូល specifier ពី TypeScript AST (ដូច្នេះ `import("…")` ត្រូវបានរាប់ ខណៈ type-position `typeof import("…")` មិនត្រូវបានរាប់) ហើយ resolve `paths` របស់ tsconfig។ វារកឃើញ cycle ចំនួន **14** មិនមែន 0 ទេ។ ដោយសារ cycle ដែលមានស្រាប់ចំនួន 14 មិនអាចត្រូវបានកែសម្រួលក្នុង gate PR បាន `check:cycles` ឥឡូវនេះជា **ratchet** (`--ratchet`, ពិដាន `metrics.cycles.value = 14` ក្នុង `quality-baseline.json`, `direction: down`) — វាទប់ស្កាត់ _ការថយក្រោយ_ ណាមួយ ហើយចំនួនអាចតែថយចុះប៉ុណ្ណោះ។ CI ដំណើរការ `npm run check:cycles:ratchet`។ ការកាត់បន្ថយជាបន្តបន្ទាប់ដំណើរការជាមួយ **A-01**។ `check:circular-deps` (dpdm) នៅតែជាការណែនាំក្នុងនាមជាមតិទីពីរដែលទូលំទូលាយជាង។
- **ភាពស្មុគស្មាញ** — ✅ **រួចរាល់** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`)៖ ការដើរត្រួតពិនិត្យ ESLint មួយដង រាប់តាម ruleId ដើម្បីឱ្យ baseline cyclomatic+max-lines និង cognitive នៅតែឯករាជ្យពីគ្នា; `check:complexity` / `check:cognitive-complexity` ដាច់ដោយឡែកនៅតែរក្សាទុកសម្រាប់ `--update` ក្នុងមូលដ្ឋាន។
