## បញ្ជីសារពើភណ្ឌច្រកត្រួតពិនិត្យ និងប្រវត្តិរូបការប្រតិបត្តិ

### ការទទួលយកបេក្ខជន

workflow របស់ CI និង Quality Gates នីមួយៗបញ្ចេញសេចក្តីសម្រេចដែលមានស្ថិរភាព៖ `Gate / CI` និង
`Gate / Quality`។ គោលនយោបាយទទួលយកដែលមានកំណែរបស់ពួកវា រាយការងារដើមទាំងអស់ជា ចាំបាច់ ឬ ជាការណែនាំ។ ការងារចាំបាច់ដែលអនុវត្តត្រូវតែជោគជ័យ៖ លទ្ធផលបាត់, បោះបង់, រំលង, កំពុងរង់ចាំ និងមិនស្គាល់ មិនអាចបង្កើត PASS បានទេ។ ការចាត់ថ្នាក់ត្រឹមត្រូវថាតែឯកសារ ឬតែកាតាឡុក អាចធ្វើឱ្យផ្លូវកូដមួយមិនអនុវត្ត។
PR សេចក្តីព្រាងមិនមែនជាបេក្ខជនដែលទទួលយកបានទេ។ ស្លាក `hotfix` មិនលើកលែងភស្តុតាងទេ។

workflow ទាំងពីរគ្របដណ្តប់ PR ចូលសាខា main/release, ការ push ទៅ `main`, manual dispatch
និងព្រឹត្តិការណ៍ merge-group។ Push, dispatch និង merge-group ដំណើរការការជ្រើសរើសពេញលេញ។ ការ push ទៅ
`release/**` មិនបើកពួកវាទេ (2026-10-18)៖ ការផ្លាស់ប្តូរនីមួយៗបានដំណើរការ matrix លើ PR របស់ខ្លួនរួចហើយ
ហើយការរួមបញ្ចូលដែលបាន merge គឺជាការងាររបស់ Release-Green (`docs/ops/RUNNER_BOX.md` → Hosted lane)។ Fork
និង merge group ប្រើ hosted runner សម្រាប់ការងារដែលបើមិនដូច្នេះជ្រើស self-hosted
runner; ត្រូវផ្ទៀងផ្ទាត់សមត្ថភាព hosted ឱ្យបានគ្រប់គ្រាន់មុនពេលដាក់ឱ្យដំណើរការ។

វិក្កយបត្រ JSON នីមួយៗកំណត់ SHA ដែលបាន checkout, workflow run និង attempt។
CLI បដិសេធការមិនត្រូវគ្នានៃ SHA រវាង checkout/event។ ការធ្វើតេស្ត workflow ចងសមាជិកភាពគោលនយោបាយ
ទៅបញ្ជី `needs` របស់ការងារសេចក្តីសម្រេច ដើម្បីកុំឱ្យផ្លូវថ្មី ឬផ្លូវដែលបានដកចេញ អាចបាត់ខ្លួនដោយស្ងាត់។
វិក្កយបត្រគ្របដណ្តប់ workflow របស់ខ្លួនឯង មិនមែនការបោះពុម្ពផ្សាយ ការដាក់ឱ្យដំណើរការ ឬផ្នែកខាងក្នុង
នៃ scanner ណែនាំដែលមានស្រាប់ទេ។ ការបើកឈ្មោះត្រួតពិនិត្យទាំងពីរនៅក្នុងច្បាប់សាខា គឺជាការផ្លាស់ប្តូរ
រដ្ឋបាលដាច់ដោយឡែក; ការបន្ថែមការងារទាំងនេះមិនការពារសាខាដោយខ្លួនឯងទេ។

### បញ្ជីសារពើភណ្ឌស្កេនស្ថិតិ

បញ្ជីសារពើភណ្ឌ npm-alias ដែលមានកំណែ និងសមាជិកភាពស្កេនស្ថិតិ មាននៅក្នុង
`config/quality/gate-manifest.json`។ ដំណើរការ `npm run check:gate-manifest` ដើម្បីផ្ទៀងផ្ទាត់
ឈ្មោះ script និងពាក្យបញ្ជាពិតប្រាកដធៀបនឹង `package.json`; ការបន្ថែម, ការដកចេញ និង
ការផ្លាស់ប្តូរពាក្យបញ្ជា ធ្វើឱ្យខកខានទាំង hook មូលដ្ឋាន និងការងារចាត់ថ្នាក់ការផ្លាស់ប្តូរនៅក្នុង CI។
alias មិនមែនជាការងារ workflow, ឧទាហរណ៍ matrix ឬករណីសាកល្បងទេ៖ ចំនួនទាំងនេះមិនត្រូវបង្ហាញថា
អាចជំនួសគ្នាបានឡើយ។

ប្រើ `npm run quality:scan -- --list` ឬ `npm run quality:scan:fast -- --list`
ដើម្បីពិនិត្យ alias ដែលបានជ្រើស ដោយមិនចាំបាច់ប្រតិបត្តិពួកវា។ runner ហៅ entrypoint របស់ npm
ដូច្នេះ runtime របស់វា (រួមទាំង Bun នៅកន្លែងដែលបានកំណត់) ត្រូវបានរក្សាទុក។
manifest កត់ត្រា alias ក្រៅប្រវត្តិរូបទាំងនោះថាត្រូវបានហៅដាច់ដោយឡែក ហើយពាក្យបញ្ជាថែទាំត្រូវបានហាមឃាត់
នៅក្នុងប្រវត្តិរូបស្កេនអានតែប៉ុណ្ណោះ។

ប្រវត្តិរូបទាំងនេះគ្របដណ្តប់តែការស្កេនស្ថិតិប៉ុណ្ណោះ។ ពួកវាមិនបញ្ជាក់ការធ្វើតេស្តផលិតផល,
គម្របតេស្ត, ការវេចខ្ចប់, ការត្រួតពិនិត្យខាងក្រៅ ឬការទទួលយកការចេញផ្សាយពេញលេញរបស់បេក្ខជនទេ។
ការទទួលយក workflow ប្រើ `config/quality/admission-policy.json` និង
`scripts/quality/admission-verdict.mjs` ដែលបានភ្ជាប់។ ប្រវត្តិរូបអ្នកសង្កេតការចេញផ្សាយ (Release-observer) នៅដាច់ដោយឡែក;
ពិនិត្យការត្រួតពិនិត្យ និងវិក្កយបត្រដែលអនុវត្តរបស់ពួកវាដោយឯករាជ្យ។ បញ្ជីសារពើភណ្ឌជាអត្ថបទ
ខាងក្រោម គឺជាឯកសារយោង មិនមែនជាភស្តុតាងថាច្រកត្រួតពិនិត្យពិតជាបានដំណើរការទេ។

Script មាននៅក្រោម `scripts/check/` (ច្រកត្រួតពិនិត្យគោលនយោបាយ) និង `scripts/quality/` (ratchet engine)។
ប្រភពការពិតរបស់ CI គឺ `.github/workflows/ci.yml`។

### ផ្លូវលឿនសម្រាប់ PR ចេញផ្សាយ (`quality.yml`)

`.github/workflows/quality.yml` បំពេញបន្ថែម CI លើ PR ទៅ main/release, ការ push ទៅ `main`,
dispatch និង merge group។ PR ប្រើការត្រួតពិនិត្យលឿនដែលចម្រាញ់តាមផ្លូវ។ ការសាងសង់ស្ទួនដែលបានបិទ
ជាអចិន្ត្រៃយ៍ត្រូវបានដកចេញ; ការត្រួតពិនិត្យ build/package/boot ពិតប្រាកដនៅតែមាននៅក្នុង CI។

#### របាយការណ៍ការធ្វើតេស្ត sibling ដែលបានបំភ្លេច

`npm run check:forgotten-sibling-tests` ប្រើឡើងវិញនូវ import resolver ដែលស្ថិតនៅពីក្រោយ test-impact map។
សម្រាប់ production module ដែលបានផ្លាស់ប្តូរនីមួយៗ វារាយការណ៍ខ្សែ
`changed module/symbol -> static consumer -> candidate sibling test` ដែលមានលក្ខណៈកំណត់បានពិតប្រាកដ នៅពេលដែល candidate
test អវត្តមាននៅក្នុង pull-request diff។ សេចក្តីសង្ខេប Markdown និងលទ្ធផល JSON ត្រូវបានរក្សាទុកជា
workflow artifact ឈ្មោះ `forgotten-sibling-tests` សម្រាប់ការ calibration មុននឹងការដាក់ប្រើប្រាស់បែប blocking ណាមួយ។

Barrel re-exports និង dynamic imports គឺជា diagnostic នៃការ resolve ប៉ុណ្ណោះ; ពួកវាមិនដែលបង្កើត
finding ដែល block ទេ។ ករណីលើកលែងដែលបានពិនិត្យឡើងវិញ ស្ថិតនៅក្នុង
`config/quality/forgotten-sibling-allowlist.json`។ ធាតុនីមួយៗត្រូវតែបញ្ជាក់ឈ្មោះ consumer និង candidate
test ផ្តល់មូលហេតុជាក់លាក់ និងភ្ជាប់តំណទៅ GitHub issue ឬ pull request។ ធាតុដែលមានទម្រង់ខុស នឹង
បរាជ័យបែប fail-closed។ ករណីលើកលែងមិនអាចបិទបាំង candidate test ដែលត្រូវបានលុប ឬ diff ដែលបន្ថែម `.skip`/`.todo` បានទេ;
ការបន្ថយកម្លាំង assertion និង masking ផ្សេងទៀត នៅតែស្ថិតក្រោមការទទួលខុសត្រូវរបស់
gate `check:test-masking` ដែល block ដោយឯករាជ្យ។
