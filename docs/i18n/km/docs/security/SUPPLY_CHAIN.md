OmniRoute បោះពុម្ពផ្សាយ npm + Docker artifacts។ ច្រកទ្វារទាំងនេះផ្ដល់នូវ provenance, inventory (SBOM) និងការស្កេន CVE ដែលទាំងអស់នេះជា OSS ហើយត្រូវបានបញ្ចូលទៅក្នុងលំហូរការងារនៃការចេញផ្សាយ។ ឥរិយាបថ **ផ្ដល់ដំបូន្មានជាមុន** — ពួកគេរាយការណ៍ឥឡូវនេះ ហើយនឹងលើកកម្ពស់ទៅជាការទប់ស្កាត់បន្ទាប់ពីការចេញផ្សាយពណ៌បៃតងលើកទី១។

| ច្រកទ្វារ             | ឧបករណ៍                                         | កន្លែង                        | ទប់ស្កាត់?                      | លទ្ធផល                                       |
| --------------------- | ---------------------------------------------- | ----------------------------- | ------------------------------- | -------------------------------------------- |
| SLSA provenance (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | លុះត្រាតែការបោះពុម្ពផ្សាយបរាជ័យ | badge npmjs / `npm audit signatures`         |
| SBOM npm              | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | លុះត្រាតែការបង្កើតបរាជ័យ        | ទ្រព្យសម្បត្តិចេញផ្សាយ + artifact            |
| SBOM image            | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | ផ្ដល់ដំបូន្មាន                  | CycloneDX artifact                           |
| Trivy CVE (SARIF)     | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | ផ្ដល់ដំបូន្មាន                  | SARIF (HIGH+CRITICAL) → ផ្ទាំង Security      |
| Trivy CRITICAL gate   | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **ទប់ស្កាត់**                   | `exit-code: '1'` លើ CRITICAL ដែលអាចជួសជុលបាន |
| osv vulnCount         | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **ទប់ស្កាត់**                   | រឹតបន្តឹង `metrics.vulnCount` (ទិសដៅ:ចុះ)    |
| OpenSSF Scorecard     | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | ផ្ដល់ដំបូន្មាន                  | SARIF → Security + ផ្លាកសញ្ញា                |

CVE ratchet រូបភាពប្រើប្រាស់ **ពីរជំហាន** នៅក្នុង `docker-publish.yml`: ជំហាន SARIF (`HIGH,CRITICAL`, `exit-code: 0`) រក្សា HIGH+CRITICAL ឱ្យមើលឃើញនៅក្នុងផ្ទាំង Security ដោយមិនទប់ស្កាត់; ជំហាន _CRITICAL gate_ (`severity: CRITICAL`, `ignore-unfixed: true`, `exit-code: 1`) ធ្វើឱ្យការចេញផ្សាយបរាជ័យលើ CRITICAL CVE **ដែលមានដំណោះស្រាយដែលអាចប្រើបាន**។ `ignore-unfixed` ការពារការទប់ស្កាត់ការចេញផ្សាយសម្រាប់ base-image CVE ដែលគ្មាន upstream patch។

## ⚠️ ភាពប្រែប្រួលនៃ CVE (ច្រកត្រួតពិនិត្យ osv/Trivy ដែលមានលក្ខណៈរារាំង)

osv និង Trivy ប្រៀបធៀប dependencies ជាមួយមូលដ្ឋានទិន្នន័យ CVE ដែល**កើនឡើងជាបន្តបន្ទាប់**។ PR មួយដែល
**មិនបានប៉ះពាល់ dependencies ណាមួយ** អាចប្រែជាពណ៌ក្រហមភ្លាមៗ ដោយសារ CVE ថ្មីមួយត្រូវបាន
បង្ហាញជាសាធារណៈនៅក្នុង dependency ដែលមានស្រាប់ (osv៖ `vulnCount` ដែលបានវាស់ > baseline; Trivy៖ មាន
CRITICAL ថ្មីដែលអាចជួសជុលបាននៅក្នុង image)។ **នេះជាឥរិយាបថប្រតិបត្តិការដែលត្រូវបានរំពឹងទុករបស់ច្រកត្រួតពិនិត្យ
CVE ដែលមានលក្ខណៈរារាំង មិនមែនជាការថយចុះគុណភាពរបស់ផលិតផលទេ។**

នៅពេល osv ឬ Trivy ប្រែជាពណ៌ក្រហមដោយសារ CVE ដែលទើបត្រូវបានបង្ហាញជាសាធារណៈ ដំណោះស្រាយគឺ៖

1. **ដំឡើងកំណែ dependency ដែលរងផលប៉ះពាល់** (ជាជម្រើសដែលពេញចិត្ត) — ដំឡើងទៅកំណែដែលបានបំណះតាមរយៈ `package.json`
   `overrides` (dependencies បន្តបន្ទាប់) ឬ build image ឡើងវិញដោយប្រើ base ដែលបានបំណះ។
2. **ប្រសិនបើមិនមានការជួសជុលពី upstream៖**
   - **osv:** កំណត់ baseline ឡើងវិញសម្រាប់ `metrics.vulnCount` នៅក្នុង `config/quality/quality-baseline.json`
     (`npm run quality:ratchet -- --update` មិនគ្របដណ្ដប់ច្រកត្រួតពិនិត្យដាច់ដោយឡែកទេ — កែតម្លៃ
     ដោយដៃ ដោយប្រើ `direction:down`) ព្រមទាំងបន្ថែមកំណត់សម្គាល់អំពីហេតុផល + issue សម្រាប់តាមដាន។
   - **Trivy:** បន្ថែមធាតុមួយនៅក្នុង `.trivyignore` (CVE-ID មួយក្នុងមួយបន្ទាត់) ជាមួយ comment អំពីហេតុផល + issue សម្រាប់តាមដាន។ `ignore-unfixed: true` គ្របដណ្ដប់ CVE ដែលគ្មាន
     បំណះដោយស្វ័យប្រវត្តិរួចហើយ។

ការប្រតិបត្តិ OSV ដែលតម្រូវឱ្យមាន (`check:vuln-ratchet -- --ratchet`) នឹងបិទដោយបរាជ័យជាមួយ
`INCOMPLETE` និង exit 2 នៅពេលមិនអាចផ្ទៀងផ្ទាត់ scanner, report ឬ baseline បាន។
ការថយចុះតាមលទ្ធផលដែលបានវាស់នឹង exit 1។ ការប្រតិបត្តិបែបផ្ដល់ព័ត៌មានអាចនៅតែរាយការណ៍ `SKIP` ជាមួយ
exit 0 ដែលមិនបានបញ្ជាក់ថា dependencies បានឆ្លងកាត់ការស្កេននោះទេ។ ជំហាន Trivy ដែលមានលក្ខណៈ
រារាំងក៏តម្រូវឱ្យមានការវាស់វែងដែលបានជោគជ័យផងដែរ៖ tools ដែលមិនអាចប្រើបាន, jobs ដែលបរាជ័យ
និងការខ្វះភស្តុតាងអំពី image មិនអាចបញ្ជាក់ថា image នោះគ្មានភាពងាយរងគ្រោះបានទេ។

## ហានិភ័យនៃ dependency ដែលបានឈប់ប្រើ

root lockfile លែងរួមបញ្ចូល `extract-zip` ឬ dependency edge ទៅកាន់វាទៀតហើយ បន្ទាប់ពីបានដំឡើងកំណែ pinned promptfoo development tool។ វាបញ្ចប់ការប្រើប្រាស់ខ្សែសង្វាក់ `promptfoo` → `@openai/codex-security` → `extract-zip` ដែលពីមុនត្រូវបានទទួលយក និងតាមដានក្នុង #14482។ ការត្រួតពិនិត្យ regression នៅក្នុង `tests/unit/extract-zip-14482-exposure.test.ts` នឹងបដិសេធការដាក់បញ្ចូលវាឡើងវិញ ហើយរក្សាការហាមឃាត់លើការ import ពី production code។

ការជួសជុល dependency បច្ចុប្បន្នក៏កំណត់វិសាលភាព compatibility overrides ឱ្យប្រើតែចំពោះ MSAL client របស់ Azure identity, FTP client របស់ get-uri និង Zod dependency របស់ OpenCode v1 SDK ប៉ុណ្ណោះ។ ការទទួលបាន Azure token និងការទាញយកតាម FTP ត្រូវបានសាកល្បងដោយប្រើ controlled transports ខណៈដែល package ទាំងពីររបស់ OpenCode ដំណើរការ build និង test suite ផ្ទាល់ខ្លួន។ ចំនួន registry advisory គឺជាការវាស់វែងនៅពេលជាក់លាក់មួយ ហើយអាចផ្លាស់ប្តូរបន្ទាប់ពី lockfile ត្រូវបាន commit។
