ប្រើមគ្គុទ្ទេសក៍នេះ ដើម្បីជ្រើសរើសវដ្តអភិវឌ្ឍន៍តូចបំផុតដែលអាចទុកចិត្តបាន សម្រាប់ pull request មួយ។ វាមិន
ជំនួសឯកសារស្ថាបត្យកម្ម និងសុវត្ថិភាពជាក់លាក់តាមផ្នែកដែលបានភ្ជាប់ខាងក្រោមទេ; វាភ្ជាប់ប្រភេទ
ការផ្លាស់ប្តូរទូទៅនីមួយៗទៅនឹងកិច្ចសន្យា ការត្រួតពិនិត្យចំគោលដៅ និងវិសាលភាពគ្របដណ្តប់របស់ CI។

## ផ្លូវដែលរាល់ការផ្លាស់ប្តូរត្រូវអនុវត្តតាម

1. **ជ្រើសរើសមូលដ្ឋានមុនពេលកែសម្រួល។** ស្វែងរកសាខា `release/v*` សកម្មដែលខ្ពស់បំផុត ហើយបង្កើតសាខាពី
   ចុងរបស់វា។ កំណត់គោលដៅទៅសាខានោះ មិនមែន `main` ទេ។ ប្រសិនបើការបង្កកំណែចេញផ្សាយកំពុងសកម្ម កុំកំណត់គោលដៅទៅសាខា
   ដែលបានបង្កក; ប្រើវដ្តសកម្មបន្ទាប់ដែលបានពិពណ៌នានៅក្នុង
   [គំរូនៃការបែងចែកសាខា និងការចេញផ្សាយ](BRANCHING_MODEL.md)។
2. **កំណត់ឈ្មោះកិច្ចសន្យា។** កំណត់អត្តសញ្ញាណកាតាឡុក schema វត្ថុដែលបានបង្កើតដោយស្វ័យប្រវត្តិ API សាធារណៈ ឬចំណុចប្រទាក់អ្នកប្រើ
   ទាំងអស់ដែលការផ្លាស់ប្តូរនេះប៉ះពាល់។ តារាងខាងក្រោមផ្តល់សំណុំចាប់ផ្តើមអប្បបរមា។
3. **សរសេរ ឬធ្វើបច្ចុប្បន្នភាពតេស្តចំគោលដៅ។** ការផ្លាស់ប្តូរសម្រាប់ production ក្នុង `src/`, `open-sse/`, `electron/` ឬ
   `bin/` តម្រូវឱ្យមានតេស្តស្វ័យប្រវត្តិក្នុង PR ដូចគ្នា។ ដំណើរការឯកសារតេស្តតិចបំផុតដែលបញ្ជាក់ឥរិយាបថ
   បន្ទាប់មកដំណើរការច្រកត្រួតពិនិត្យចំគោលដៅដែលបានរាយ។
4. **អនុញ្ញាតឱ្យ CI ដំណើរការម៉ាទ្រីសទូលំទូលាយ។** ផ្នែកតេស្តឯកតាពេញលេញ Vitest យន្តការកំណត់កម្រិត coverage និង
   production build ដំណើរការលើ PR។ ដំណើរការឈុតតេស្តទូលំទូលាយនៅមូលដ្ឋាន តែនៅពេលការបរាជ័យចំគោលដៅបង្ហាញថា
   មានផលប៉ះពាល់ធំជាងនេះ ឬនៅពេលការផ្លាស់ប្តូរគ្របដណ្តប់ប្រព័ន្ធរងជាច្រើន។
5. **ផ្ទៀងផ្ទាត់ឱ្យស្របគ្នាមុនការពិនិត្យ។** ទាញយកមូលដ្ឋានសកម្ម ពិនិត្យ commit ថ្មីរបស់វា និង diff របស់អ្នកធៀបនឹង
   វា រួច rebase ឬ merge មូលដ្ឋានស្របតាមលំហូរការងាររបស់អ្នករួមចំណែក។ ដោះស្រាយការប៉ះទង្គិចឯកសារដែលបានបង្កើតដោយស្វ័យប្រវត្តិ
   និងកាតាឡុកពីប្រភពរបស់វា បង្កើតពួកវាឡើងវិញ ដំណើរការវដ្តចំគោលដៅឡើងវិញ ហើយបញ្ជាក់ថា
   PR នៅតែកំណត់គោលដៅទៅសាខាកំណែចេញផ្សាយសកម្ម។
6. **កត់ត្រាភស្តុតាង។** ក្នុងគំរូ PR រាយពាក្យបញ្ជាដែលបានដំណើរការ រាល់ឯកសារតេស្តដែលបានបន្ថែម ឬផ្លាស់ប្តូរ
   migration ឬ feature flag និងការផ្ទៀងផ្ទាត់ដែលដំណើរការតែលើ CI ណាមួយដែលនៅរង់ចាំ។

## ផ្លូវគំរូតាមប្រភេទការផ្លាស់ប្តូរ

ពាក្យបញ្ជាខាងក្រោមគឺជាការត្រួតពិនិត្យចំគោលដៅអប្បបរមា មិនមែនជាការអនុញ្ញាតឱ្យរំលងតេស្តដែលគ្របដណ្តប់ដោយផ្ទាល់លើ
ឥរិយាបថដែលអ្នកបានផ្លាស់ប្តូរទេ។

### Provider

**កិច្ចសន្យា**

- និយមន័យ Provider ក្នុង `src/shared/constants/providers/` និងការផ្គុំរបស់វាក្នុង
  `src/shared/constants/providers.ts`។
- Model និងសមត្ថភាពក្នុង `open-sse/config/providerRegistry.ts` ឬឯកសារ registry ដែលបានបំបែកចេញ។
- ការជ្រើសរើស executor/translator ការកំណត់រចនាសម្ព័ន្ធ OAuth ឬ API-key ទ្រព្យធន dashboard និងឯកសារយោង
  provider ដែលបានបង្កើតដោយស្វ័យប្រវត្តិ នៅពេលអនុវត្ត។
- ព័ត៌មានសម្ងាត់សាធារណៈត្រូវប្រើ `resolvePublicCred()`; response កំហុសត្រូវប្រើ helper កំហុសរួម
  ដែលបានសម្អាតទិន្នន័យរសើប។ សូមមើល `docs/security/PUBLIC_CREDS.md` (git; មិនត្រូវបានចងក្រងចូលក្នុង `/docs`) និង
  [ការសម្អាតទិន្នន័យរសើបពីកំហុស](../security/ERROR_SANITIZATION.md)។

**វដ្តចំគោលដៅ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # នៅពេលកាតាឡុកផ្លាស់ប្តូរ; commit diff ដែលបានបង្កើត
npm run lint
```

ត្រូវសាកល្បងរាល់ក្រុម request ដែលរងផលប៉ះពាល់ផងដែរ៖ chat, Responses, images, embeddings, audio ឬ video។
ពិនិត្យកាតាឡុកដែលបានបង្កើត និង golden diff ជាការផ្លាស់ប្តូរកិច្ចសន្យា; កុំទទួលយកពួកវាដោយមិនពិនិត្យ។

### Routing

**កិច្ចសន្យា**

- តម្លៃ strategy សាធារណៈ និង metadata របស់ UI ក្នុង `src/shared/constants/routingStrategies.ts`។
- ការបញ្ជូន និងការរៀបលំដាប់ក្រោម `open-sse/services/combo.ts` និង `open-sse/services/combo/`។
- Combo schema ការរក្សាទុក ស្ថានភាពធន់ទ្រាំ សមត្ថភាព model និងឧបករណ៍បញ្ជា API/UI។
- [ម៉ាស៊ីន Auto-Combo](../routing/AUTO-COMBO.md) និងឯកសារស្តីពីភាពធន់ទ្រាំ នៅពេលឥរិយាបថផ្លាស់ប្តូរ។

**វដ្តចំគោលដៅ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ការផ្លាស់ប្តូរ strategy ឬ dispatch
npm run check:known-symbols      # ការផ្លាស់ប្តូរការចុះឈ្មោះ strategy
npm run lint
```

ប្រើតេស្ត mocked-upstream ដែលមានលទ្ធផលកំណត់ជាក់លាក់នៅមូលដ្ឋាន។ ការធ្វើ live combo smoke test តម្រូវឱ្យមានព័ត៌មានសម្ងាត់ ហើយជា
ការធ្វើដោយដៃ មិនមែនជាជំនួសសម្រាប់ CI ទេ។

### UI / UX

**កិច្ចសន្យា**

- route/page របស់ Next.js និងព្រំដែន component រួមក្រោម `src/app/` និង

## ស្គ្រីបសម្រាប់អ្នកអភិវឌ្ឍន៍លើម៉ាស៊ីនរួម

កម្មវិធីជំនួយពីរនៅក្នុង `scripts/dev/` កំណត់លំហូរការងារមូលដ្ឋានលើ devbox ដែលមានសម័យការងារផ្សេងទៀតកំពុងដំណើរការ៖

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # ឯកសារពី merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # តែឯកសារទាំងនេះប៉ុណ្ណោះ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # worktree ដាច់ដោយឡែក ដែលមានសុវត្ថិភាពសម្រាប់ដំណើរការស្របគ្នា
```

- `typecheck-touched.sh` ពិនិត្យប្រភេទតែឯកសារ `.ts/.tsx` ដែលបានប៉ះពាល់ប៉ុណ្ណោះ តាមរយៈ
  `tsconfig.touched.tmp.json` បណ្ដោះអាសន្ន (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ក្រោម heap ទំហំ 6 GB ដូច្នេះវាជំនួស `tsc -p tsconfig.json` ដែលដំណើរការលើគម្រោងទាំងមូល
  ហើយអស់អង្គចងចាំលើម៉ាស៊ីនដែលមានបន្ទុកខ្ពស់។ វាបង្ហាញកំហុសនៅក្នុងឯកសារដែលបានប៉ះពាល់ ព្រមទាំងបន្ទាត់សង្ខេបមួយ ហើយបញ្ចប់
  ដោយ `1` សម្រាប់កំហុសនៅក្នុងឯកសារដែលបានប៉ះពាល់, `2` នៅពេលកំហុសមានតែនៅក្នុងឯកសារដែលបាន import ឬ tsc បានឈប់ដំណើរការ
  ដោយគ្មានព័ត៌មានវិនិច្ឆ័យ (សូមអាន log ដែលវាបញ្ជាក់ឈ្មោះនៅក្រោម `_artifacts/typecheck-touched/`) និង `0` នៅពេល
  គ្មានកំហុស។ tsconfig បណ្ដោះអាសន្នតែងតែត្រូវបានលុបចេញ; កុំ commit វាដាច់ខាត។
- `new-worktree.sh` រៀបលំដាប់ការដំណើរការស្របគ្នានៅលើ `<git-common-dir>/omniroute-new-worktree.lock`
  (តាមលំនាំដើម វារង់ចាំរហូតដល់ 600 s ដោយមានសារដែលអាចមើលឃើញ; ក្បាលស្គ្រីបមានឯកសារពន្យល់អំពី
  ការកំណត់ជំនួស) និងត្រឡប់
  branch ដែលវាបានបង្កើតទៅស្ថានភាពដើម នៅពេល `git worktree add` បរាជ័យមុនពេល worktree មានវត្តមាន ដូច្នេះការព្យាយាមម្ដងទៀត
  មិនតម្រូវឱ្យប្រើ `git branch -D` ដោយដៃទេ។ `node_modules` ដែលបាន hard-link និងច្បាប់ចម្លង `.husky/_` មិនត្រូវបានផ្លាស់ប្ដូរទេ។

## លំហូរ candidate មូលដ្ឋាន

ការធ្វើតេស្ត source មិនអាចបញ្ជាក់បានទេថា artifact ដែលបានវេចខ្ចប់អាចចាប់ផ្ដើមដំណើរការ៖ បញ្ជីវេចខ្ចប់, dependency ដែលបានកាត់ចេញ,
និង binary ដើម នឹងបរាជ័យតែនៅពេល tarball ត្រូវបានដំឡើង និងចាប់ផ្ដើមប៉ុណ្ណោះ។ `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) គឺជាផ្នែកមូលដ្ឋាននៃលំហូរ build-once / validate / promote ពី
RFC #8084៖ វា build candidate មួយ, validate artifact ពិតប្រាកដនោះ, promote វាដោយប្ដូរឈ្មោះ directory,
ហើយ rollback វា នៅពេល slot ដែលបាន promote បរាជ័យក្នុងការពិនិត្យសុខភាព។

```bash
npm run dev:candidate -- run --dry-run --json  # បង្ហាញផែនការ ដោយមិនផ្លាស់ប្ដូរអ្វីទាំងអស់
npm run dev:candidate -- run                   # build + validate + promote និង rollback ដោយស្វ័យប្រវត្តិ
npm run dev:candidate -- build                 # npm pack + ដំឡើងទៅក្នុង _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # ចាប់ផ្ដើមលើ port ទំនេរ, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # ប្ដូរ current និង previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # ប្រើ tarball ដែលបាន build នៅកន្លែងផ្សេងឡើងវិញ (CI)
```

- **Build តែម្ដង។** `build` វេចខ្ចប់ tree បច្ចុប្បន្ន (វាត្រូវការ `dist/server.js` ដូច្នេះត្រូវដំណើរការ
  `npm run build:release` ជាមុន) ឬចម្លង `--from-tarball` បន្ទាប់មកដំឡើង tarball ទៅក្នុង
  npm prefix ដាច់ដោយឡែក ព្រោះ tarball មិនមាន `node_modules` ទេ។ id គឺជា sha ខ្លីនៃ `HEAD`
  (`-dirty` នៅពេល tree មានការផ្លាស់ប្ដូរមូលដ្ឋាន) ឬ `tgz-<sha256>` សម្រាប់ tarball មួយ។ id ស្អាតដែល
  បាន build រួចហើយ នឹងត្រូវបានប្រើឡើងវិញជំនួសឱ្យការ build ឡើងវិញ; ផ្ដល់ `--force` ដើម្បី build វាឡើងវិញ។
- **Validate package មិនមែន source ទេ។** `validate` ចាប់ផ្ដើម CLI ដែលបានដំឡើង
  (`serve --port <free port>`) ជាមួយ `DATA_DIR=<candidate>/data` ថ្មី, secret ក្លែងក្លាយ និងដក
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` និង `INITIAL_PASSWORD` របស់ operator ចេញពី
  environment ដូច្នេះវាពិនិត្យស្ថានភាព keyless loopback នៃការដំឡើងថ្មី។ វារង់ចាំឱ្យ
  `GET /api/health` ត្រឡប់ 200, តម្រូវឱ្យ `GET /v1/models` ត្រឡប់ 200, បញ្ឈប់ក្រុម process
  ហើយកត់ត្រាលទ្ធផលនៅក្នុង `validation.json` រួមជាមួយ hash របស់ tarball។
- **Promote artifact ដដែល។** `promote` បដិសេធ candidate ដែលមិនមាន validation ជោគជ័យសម្រាប់
  hash tarball បច្ចុប្បន្នរបស់វា។ slot សកម្មតាមលំនាំដើមគឺ `_artifacts/candidate/current`; `--target <dir>`
  ជ្រើសរើស directory ផ្សេងទៀតលើ filesystem ដូចគ្នា ហើយ slot មុនរបស់វាគឺ `<dir>.previous`។
  ការប្ដូរឈ្មោះនីមួយៗមានលក្ខណៈ atomic ហើយបរាជ័យនៅពាក់កណ្ដាលដំណើរការនឹងត្រឡប់ការប្ដូរឈ្មោះដែលបានដំណើរការរួចទៅស្ថានភាពដើម។
- **Rollback។** `run` validate slot ដែលបាន promote ម្ដងទៀត ហើយប្ដូរ `current` និង `previous` ត្រឡប់វិញ នៅពេល
  ការពិនិត្យនោះបរាជ័យ។ candidate ដែលបរាជ័យក្នុង validation ដំបូង នឹងមិនត្រូវបាន promote ឡើយ។

អ្វីៗទាំងអស់ត្រូវបានសរសេរនៅក្រោម `_artifacts/candidate/` ដែល git មិនអើពើ; ការដំឡើង OmniRoute
ដែលមានស្រាប់ និង directory ទិន្នន័យរបស់វា មិនត្រូវបានប៉ះពាល់ឡើយ។ CLI ដែលបាន promote គឺ
`_artifacts/candidate/current/prefix/bin/omniroute`; ចាប់ផ្ដើមវាជាមួយ `DATA_DIR` ផ្ទាល់ខ្លួនរបស់អ្នក នៅពេលអ្នកប្រើ
វា។ លេខកូដបញ្ចប់៖ `0` ជោគជ័យ, `1` validation ឬ promotion បរាជ័យ, `2` កំហុសក្នុងការប្រើប្រាស់ ឬគ្មាន build។

## បញ្ជីត្រួតពិនិត្យការធ្វើសមកាលកម្ម

មុនពេលស្នើសុំការពិនិត្យ៖

- បញ្ជាក់ថា base របស់ PR នៅតែជាសាខា `release/v*` សកម្មដែលខ្ពស់បំផុត។
- Fetch base នោះ ហើយពិនិត្យ commit ដែលបានបញ្ចូលចាប់តាំងពីអ្នកបានបង្កើតសាខា។
- ពិនិត្យ `git diff <active-base>...HEAD` ដើម្បីរកការផ្លាស់ប្តូរដោយអចេតនា ឬការផ្លាស់ប្តូរដែលបានបង្កើតដោយស្វ័យប្រវត្តិ។
- ដោះស្រាយ conflict ក្នុង catalog និងឯកសារដែលបានបង្កើត ដោយធ្វើបច្ចុប្បន្នភាពប្រភព ហើយបង្កើត output ឡើងវិញ។
- ដំណើរការឡើងវិញនូវរាល់តេស្ត/ច្រកត្រួតពិនិត្យដែលផ្តោតជាក់លាក់ និងបានរាយក្នុងសេចក្តីពិពណ៌នា PR បន្ទាប់ពីការធ្វើសមកាលកម្ម។
- កុំបន្ធូរបន្ថយ assertion ឬលុបតេស្តដែលតម្រូវឱ្យមាន គ្រាន់តែដើម្បីឱ្យត្រូវនឹង base ដែលបានផ្លាស់ទី។
