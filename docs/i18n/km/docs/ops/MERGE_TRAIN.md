## ចុះចតនៅលើសាខាចេញផ្សាយ

ជួរ omni គ្រប់គ្រងការចុះចតចូលទៅក្នុង `release/vX.Y.Z`។ អាន `mode` កម្រិតកំពូលនៅក្នុង `config/merge-queue/config.json` នៅលើសាខាលំនាំដើមមុនពេលចុះចត PR។ សូមមើល [Omni-Queue](OMNI_QUEUE.md) ។

- **`shadow`** ដំណើរការការបញ្ជាក់ហើយទុកពេលចុះចតទៅការបញ្ចូលគ្នាដោយដៃ។ អនុវត្ត `omni-queue` ទៅ PR ដែលត្រូវបានអនុម័តនៅក្បាលចុងក្រោយរបស់វា។ ពិនិត្យមើលសិទ្ធិជាមួយ `npm run queue -- why <PR>`។ រង់ចាំសាលក្រមសម្រាប់ក្បាលនោះនៅក្នុង `npm run queue -- history --base <branch>`។ បន្តនៅលើ `would-land`។ នៅលើ `culprit-found` ឬ `would-dequeue` សង្កត់ការបញ្ចូលគ្នា ហើយជួសជុលមូលហេតុ។
- **ការលើកលែងស្រមោល។** រថភ្លើងដែលមាន CI ពណ៌បៃតងពេញលេញប្រឆាំងនឹងព័ត៌មានជំនួយមូលដ្ឋានបច្ចុប្បន្នអាចដំណើរការដោយគ្មានសាលក្រមជួរដាច់ដោយឡែក។ ការលើកលែងដូចគ្នានេះត្រូវបានអនុវត្តនៅពេលដែលក្បាល PR មានព័ត៌មានជំនួយមូលដ្ឋានបច្ចុប្បន្នរួចហើយ។
- **`live`** ប្រើស្លាក `omni-queue` ដើម្បីចាប់ផ្តើមការចុះចត។ ជួរតែម្នាក់ឯងចុះចត PR។ ទុកពាក្យបញ្ជាបញ្ចូលគ្នា ហើយរុញទៅជួរ។

រាល់ការចុះចតទាមទារការអនុញ្ញាតពីម្ចាស់ និងការត្រួតពិនិត្យដែលត្រូវការ។ អនុវត្ត `omni-queue` តែបន្ទាប់ពីម្ចាស់បានអនុញ្ញាតឱ្យចុះចត។ តម្រង់ជួរ PRs ប៉ះផ្លូវដែលបានការពារក៏ទាមទារការសម្រេចចិត្ត `protected-approved` របស់ម្ចាស់សម្រាប់ PR នោះ។

ក្បួន "ទាមទារច្រកពណ៌បៃតងនៅលើការចេញផ្សាយសកម្ម" តម្រូវឱ្យ `Gate / CI` និង `Gate / Quality` ពណ៌បៃតងនៅលើក្បាល។ កុំប្រើ `--admin` ដើម្បីឆ្លងកាត់ច្រកក្រហម។ ប្លុកបង្កកដែលបានចេញផ្សាយ បញ្ចូលទៅក្នុងសាខាដែលកក។ សូមមើល [ច្បាប់រឹង 21](HARD_RULES_DETAIL.md) ។ កុំដាក់ស្លាក បញ្ចូលចូលគ្នា ឬរុញទៅសំណើទាញដែលវគ្គផ្សេងទៀតកំពុងដំណើរការ។ សូមមើល [ច្បាប់រឹង 22](HARD_RULES_DETAIL.md) ។

## ពាក្យសុំទាញរថភ្លើង

1. ចាប់ផ្តើមសាខារថភ្លើងនៅព័ត៌មានជំនួយមូលដ្ឋាននៃការចេញផ្សាយបច្ចុប្បន្ន។ បញ្ចូលប្រធានសមាជិកដែលបានអនុម័តពិតប្រាកដដោយប្រើការបញ្ចូលគ្នា។ រក្សាប្រវត្តិនៃការប្រព្រឹត្តរបស់ពួកគេដោយជៀសវាងការបំផ្លាញនិងការបង្កើតឡើងវិញ។
2. បើកសំណើទាញមួយសម្រាប់សាខារថភ្លើង។ ធ្វើឱ្យមានសុពលភាព PR នោះជាមួយនឹង CI ពេញលេញរបស់វានៅលើព័ត៌មានជំនួយមូលដ្ឋានបច្ចុប្បន្ន។ ពិនិត្យព័ត៌មានជំនួយមូលដ្ឋាន និងក្បាលសមាជិកដែលបានអនុម័តមុនពេលចុះចត។ ផ្ទុកឡើងវិញនូវរថភ្លើង និង CI របស់វា នៅពេលដែលបេក្ខជនដែលមានសុពលភាពផ្លាស់ប្តូរ។
3. ចុះចតរថភ្លើង PR ជាមួយនឹងការប្តេជ្ញាចិត្តបញ្ចូលគ្នានៅក្រោមរបៀបជួរដែលអាចអនុវត្តបាន។ នៅក្នុងរបៀបបន្តផ្ទាល់ វិធីសាស្ត្រចុះចត `merge-ff` របស់ជួររក្សាការបញ្ចូលបញ្ចូលគ្នា។ ប្រធានសមាជិកដើមអាចទៅដល់បានពីសាខាចេញផ្សាយ។ GitHub សម្គាល់សមាជិក PRs ថាបានបញ្ចូលគ្នា ហើយការប្តេជ្ញាចិត្តរក្សាអ្នកនិពន្ធរបស់ពួកគេ។

ឧទាហរណ៍សាធារណៈគឺ [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071) ។ វារួមបញ្ចូលគ្នានូវសមាជិក 18 PRs ហើយបានចុះចតជាមួយនឹងការប្តេជ្ញាចិត្តបញ្ចូលគ្នានៅថ្ងៃទី 2026-11-24 ។

ការធ្វើសមកាលកម្មត្រឡប់មកវិញពី `main` ទៅកាន់សាខាចេញផ្សាយបន្ទាប់ក៏ឈានដល់ការប្តេជ្ញាចិត្តបញ្ចូលគ្នាផងដែរ។ ការរក្សាពូជពង្ស `main` គឺចាំបាច់សម្រាប់ការធ្វើសមកាលកម្មនៅពេលក្រោយ។ សូមមើល [Worktree Isolation](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash) ។

## អ្នកត្រួតពិនិត្យផ្លូវរថភ្លើងរួមបញ្ចូលគ្នាក្នុងស្រុក

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

អ្នកផ្តល់សុពលភាពយកក្បាលមូលដ្ឋាន និង PR ហើយបញ្ចូលគ្នានៅក្នុងមែកធាងការងារដែលអាចចោលបាន។ វាដំណើរការឈុត parity របស់វាម្តងនៅលើមែកធាងលទ្ធផល។ ការទាញយកក្បាលដែលមិនបានសម្រេច ឬបញ្ចូលការប៉ះទង្គិចនឹងច្រានចេញដែល PR ហើយស្គ្រីបបន្តជាមួយ PRs ដែលនៅសល់។

- **`--plan`** បោះពុម្ពជំហាននៃរបៀបដែលបានជ្រើសរើស ហើយចេញដោយមិនបង្កើត worktree ឬទាក់ទងពីចម្ងាយ។ ផ្សំវាជាមួយ `--fast` ដើម្បីពិនិត្យមើលផែនការរហ័ស។
- **`--fast`** ដំណើរការច្រកឋិតិវន្តទូទៅ ឯកសារ `node:test` ដែលបានផ្លាស់ប្តូរដែលបានជ្រើសរើសនៅក្រោម `tests/unit/` និង `npm run test:vitest`។ ដំណើរការការផ្ទៀងផ្ទាត់មូលដ្ឋានពេញលេញយ៉ាងហោចណាស់ម្តងក្នុងមួយថ្ងៃនៅលើព័ត៌មានជំនួយដែលបានប្រមូលនៅពេលប្រើមុខងាររហ័ស។
- **របៀបពេញ** បន្ថែមច្រកឋិតិវន្តតែមួយគត់ពេញលេញ និងដំណើរការ `npm run test:unit` និង `npm run test:vitest`។

ច្រកឋិតិវន្តដែលបរាជ័យត្រូវបានដំណើរការឡើងវិញនៅលើមូលដ្ឋានដែលមិនប៉ះ ប្រសិនបើការស៊ើបអង្កេតមូលដ្ឋានអាចរកបាន។ ស្គ្រីបរាយការណ៍ពីការបរាជ័យដែលបានទទួលមរតក ហើយបន្តនៅពេលដែលរាល់បន្ទាត់បំពានដែលបានទទួលស្គាល់ក៏លេចឡើងនៅលើមូលដ្ឋាន ហើយចំនួនសរុបមិនកើនឡើងទេ។

## លំដាប់

- **ក្នុងមួយ PR។** CI និងគុណភាពជ្រើសរើសការត្រួតពិនិត្យដោយផ្អែកលើផ្លូវដែលបានផ្លាស់ប្តូរ។ កូដ PRs ដំណើរការច្រកទ្វារគុណភាពរហ័ស និងការធ្វើតេស្តដែលរងផលប៉ះពាល់ ជាមួយនឹងការងារដាច់ដោយឡែក និង Vitest នៅក្នុង CI។
- **សម្រាប់បេក្ខជនជួរ។** CI និងគុណភាពដំណើរការទម្រង់ពេញលេញសម្រាប់បេក្ខជនដែលតែងនៅលើជួរយោងរបស់វា។
- **សម្រាប់ព័ត៌មានជំនួយចេញផ្សាយ។** Release-Green ដំណើរការច្រករឹងរហ័សនៅលើការរុញដែលត្រូវគ្នានឹងតម្រងផ្លូវរបស់វា។ ការរត់តាមកាលវិភាគចំនួនបីក្នុងមួយថ្ងៃ ប្រើការបោសសំអាតពេញលេញសម្រាប់សាខាចេញផ្សាយ។
- **ក្នុងមួយការចេញផ្សាយ។** ម៉ាទ្រីស CI ពេញលេញរួមមាន E2E shards សុពលភាពកញ្ចប់ ផ្សែង tarball boot និងការត្រួតពិនិត្យការគ្របដណ្តប់។ សូមមើល [បញ្ជីត្រួតពិនិត្យការចេញផ្សាយ](RELEASE_CHECKLIST.md) ។

## លក្ខខណ្ឌបង់ប្រាក់ជាមុនសម្រាប់ `merge-train.sh`

preflight ដំណើរការមុនពេលបង្កើត worktrees ។ ដំឡើងភាពអាស្រ័យជាមួយ `npm ci`។ បញ្ជាក់ថា `node_modules/.bin/tsc` គឺអាចប្រតិបត្តិបាន ហើយ `node_modules/node_modules` គឺអវត្តមាន។ ពិនិត្យមើលថា `node_modules/.bin/bun --version` ជោគជ័យ។

ប្រសិនបើ Bun postinstall ត្រូវបានរំលង សូមដំណើរការ `(cd node_modules/bun && node install.js)`។ ការត្រួតពិនិត្យភាពស៊ីសង្វាក់គ្នារវាងអ្នកផ្តល់សេវា និងនិមិត្តសញ្ញាដែលគេស្គាល់ប្រើ Bun។ សុពលភាពដំណើរការ `npm run check:cycles:ratchet` ជាច្រករារាំង។ ពាក្យបញ្ជា `npm run check:cycles` ឯករាជ្យគឺជាការប្រឹក្សា។
