## ការបំពេញការជជែក

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### បឋមកថាផ្ទាល់ខ្លួន

| Header                   | Direction | Description                                                                                                                                                                                                            |
| ------------------------ | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Request   | កំណត់ជា `true` ដើម្បីរំលងឃ្លាំងសម្ងាត់                                                                                                                                                                                 |
| `x-omniroute-no-memory`  | Request   | កំណត់ជា `true` ដើម្បីរំលងការបញ្ចូល memory + skills សម្រាប់សំណើនេះ (ដំណើរការដូច no-cache; ជៀសវាងការចំណាយ token/cost ក្នុងមួយការហៅ)                                                                                      |
| `X-OmniRoute-Progress`   | Request   | កំណត់ជា `true` សម្រាប់ព្រឹត្តិការណ៍វឌ្ឍនភាព                                                                                                                                                                            |
| `X-Session-Id`           | Request   | គន្លឹះសម័យជាប់លាប់សម្រាប់ការកំណត់ភាពស្អិតនៃសម័យខាងក្រៅ                                                                                                                                                                 |
| `x_session_id`           | Request   | វ៉ារ្យ៉ង់ដែលប្រើសញ្ញាគូសក្រោមក៏ត្រូវបានទទួលយកដែរ (HTTP ដោយផ្ទាល់)                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | Request   | ស្លាកសម័យ/ការសន្ទនាដែលអ្នកហៅផ្តល់ជូន (ក៏បញ្ចូលទៅក្នុង memory ផងដែរ)។ នៅពេលមាន វាត្រូវបានរក្សាទុកដូចដើមទៅ `call_logs.session_tag` សម្រាប់ការបែងចែកថ្លៃដើមតាមសម័យ (#8249) — មិនដែលបង្កើតឡើងដោយស្វ័យប្រវត្តិពេលអវត្តមានទេ |
| `Idempotency-Key`        | Request   | គន្លឹះលុបស្ទួន (បង្អួច 5s)                                                                                                                                                                                             |
| `X-Request-Id`           | Request   | គន្លឹះលុបស្ទួនជំនួស                                                                                                                                                                                                    |
| `x-omniroute-connection` | Request   | ភ្ជាប់សំណើដែលប្រើម៉ូដែលតែមួយទៅកាន់ការតភ្ជាប់ provider មួយ (គណនី) តាម id របស់វា — សូមមើល [ការភ្ជាប់គណនីតាមសំណើ](#account-pinning-per-request)                                                                           |
| `X-OmniRoute-Cache`      | Response  | `HIT` ឬ `MISS` (មិនមែនការបញ្ជូនជាបន្តបន្ទាប់)                                                                                                                                                                          |
| `X-OmniRoute-Idempotent` | Response  | `true` ប្រសិនបើបានលុបសំណើស្ទួន                                                                                                                                                                                         |
| `X-OmniRoute-Progress`   | Response  | `enabled` ប្រសិនបើបានបើកការតាមដានវឌ្ឍនភាព                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | Response  | លេខសម្គាល់សម័យមានប្រសិទ្ធភាពដែល OmniRoute បានប្រើ                                                                                                                                                                      |
| `X-OmniRoute-Request-Id` | Response  | លេខសម្គាល់សម្រាប់ភ្ជាប់ទំនាក់ទំនងសំណើ (នៅពេលស្គាល់)                                                                                                                                                                    |
| `X-OmniRoute-Version`    | Response  | កំណែ build របស់ OmniRoute (មានជានិច្ច)                                                                                                                                                                                 |
| `X-OmniRoute-Cost-Saved` | Response  | ចំនួន USD ដែលឃ្លាំងសម្ងាត់បានជៀសវាងនៅពេល HIT (មានតែ cache hits ប៉ុណ្ណោះ)                                                                                                                                               |
| `X-OmniRoute-Decision`   | Response  | ដានការកំណត់ផ្លូវ៖ `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` គឺជាយុទ្ធសាស្ត្ររួម ឬ `single` សម្រាប់សំណើដែលមិនមែនជាសំណើរួម) — មានជានិច្ចនៅក្នុងការឆ្លើយតបពេលបញ្ចប់                                   |

> ចំណាំអំពី Nginx៖ ប្រសិនបើអ្នកពឹងផ្អែកលើ header ដែលមានសញ្ញាគូសក្រោម (ឧទាហរណ៍ `x_session_id`) សូមបើក `underscores_in_headers on;`។

#### ការភ្ជាប់គណនីតាមសំណើ

នៅពេល provider មួយមានការតភ្ជាប់ជាច្រើន (គណនី ឬ key) ជាទូទៅ OmniRoute ជ្រើសរើសមួយតាមរយៈយុទ្ធសាស្ត្រជ្រើសរើសគណនីរបស់វា។ ជំនួសវិញ សំណើមួយអាចភ្ជាប់ទៅកាន់ការតភ្ជាប់ជាក់លាក់មួយដោយប្រើ header `x-omniroute-connection`៖

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **កន្លែងស្វែងរក id។** បើកទំព័រ provider នៅក្នុង dashboard
  (**Dashboard → Providers → <provider>**) ហើយចុចលើបន្ទះ id `xxxxxxxx…` នៅជួរ connection
  — វានឹងចម្លង connection id ពេញលេញ។
- **សំណើណាខ្លះគោរពវា។** សំណើ single-model (`provider/model`) នៅលើ
  `/v1/chat/completions`, `/v1/messages` និង `/v1/responses`។ Combos មិនអើពើចំពោះ header នេះទេ៖
  pin account មួយសម្រាប់ជំហាននីមួយៗក្នុង combo តាមរយៈ connection ផ្ទាល់របស់ជំហាននោះ។
- **Pin នេះមានភាពតឹងរ៉ឹង មិនមែនជាចំណូលចិត្តទេ។** ប្រព័ន្ធប្រើ pinned connection ផ្តាច់មុខ។ ប្រសិនបើមាន
  failure នៅក្នុងសំណើ វានឹងកត់ត្រា cooldown របស់ account ប៉ុន្តែ **មិន** ប្ដូរទៅ sibling account
  របស់ provider ដូចគ្នាទេ។
- **Cooldown និង quota នឹងដោះលែង pin។** ខណៈពេល pinned connection កំពុងស្ថិតក្នុង cooldown,
  quota អស់ ឬត្រូវបាន block ដោយ quota policy សំណើបន្ទាប់នឹងត្រឡប់ទៅប្រើ connections ផ្សេងទៀត
  របស់ provider ដូចគ្នានឹង traffic ដែលមិនបាន pin។
- **id ដែលមិនស្គាល់ ឬត្រូវបានបិទនឹងបរាជ័យ។** id ដែលមិនស្ថិតក្នុង active pool របស់ provider (ត្រូវបានលុប,
  បិទដំណើរការ ឬជាកម្មសិទ្ធិរបស់ provider ផ្សេង) នឹងមិនមាន account ដែលអាចប្រើបានទេ ដូច្នេះសំណើនឹង
  បរាជ័យ ជំនួសឱ្យការបញ្ជូនទៅកន្លែងផ្សេងដោយស្ងាត់ៗ។

Claude Code ផ្ញើ custom headers តាមរយៈ `ANTHROPIC_CUSTOM_HEADERS`។ ដាក់វានៅក្នុងប្លុក `env`
នៃ `~/.claude/settings.json` ឬក្នុង `.claude/settings.json` កម្រិត project ដើម្បី pin account
ផ្សេងគ្នាសម្រាប់ project នីមួយៗ៖

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ប្រភព៖ `src/sse/handlers/chat.ts` (ការអាន header), `src/sse/services/auth.ts` និង
`src/sse/services/sessionAffinityPin.ts` (ការដោះលែង pin និងការត្រួតពិនិត្យថាបាត់ពី pool)។

> **Cost telemetry headers:** ចម្លើយជោគជ័យដែលមិនមែនជា streaming ក៏មានសំណុំ cost-telemetry `X-OmniRoute-*` ផងដែរ — `X-OmniRoute-Response-Cost` (USD, ថេរ 10 ខ្ទង់ទសភាគ; `0.0000000000` សម្រាប់ free/unpriced), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` និង `X-OmniRoute-Fallback-Attempts` (មានតែនៅពេល > 0) ព្រមទាំង `X-OmniRoute-Request-Id` និង `X-OmniRoute-Version`។ វាត្រូវបានបញ្ចេញដោយ chat completions, `/v1/responses`, `/v1/messages`, **និង media endpoints** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` និង `/v1/moderations` (តម្លៃតែងតែ `0`)។ Media cost ត្រូវបានគណនាតាម modality (ក្នុងមួយរូបភាព ក្នុងមួយវិនាទី ក្នុងមួយតួអក្សរ ក្នុងមួយ search-unit) នៅពេលមាន pricing បើមិនដូច្នោះទេ វានឹងជា `0` (fail-open)។

> **Cache-hit cost semantics:** នៅពេល semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) មិនមានការហៅទៅ upstream ទេ ដូច្នេះ `X-OmniRoute-Response-Cost` គឺ `0.0000000000` (ជា **incremental** cost នៃការផ្តល់ hit)។ តម្លៃដើម/តម្លៃដែលនឹងកើតឡើង ត្រូវបានរាយការណ៍ដោយឡែកក្នុង `X-OmniRoute-Cost-Saved`។ អ្នកប្រើប្រាស់ billing គួរបូកសរុប `X-OmniRoute-Response-Cost` (hits មិនមានតម្លៃទេ); cache analytics អាចប្រមូលផ្តុំ `X-OmniRoute-Cost-Saved`។

## ការជួលសម័យ Managed ផ្តាច់មុខ

ការជួលសម័យ managed ផ្តាច់មុខ គឺជាកិច្ចសន្យាកំណត់ផ្លូវដែលជ្រើសរើសប្រើតាមចិត្ត និងមិនពាក់ព័ន្ធនឹងប្រភេទ client៖ owner សកម្មម្នាក់កាន់កាប់ការតភ្ជាប់ OmniRoute ដែលមានសិទ្ធិប្រើប្រាស់មួយ។ វាមិនជួល model មួយ មិនតម្រូវឱ្យប្រើ OAuth មិនកំណត់អត្តសញ្ញាណ client ជាក់លាក់ណាមួយ និងមិនតម្រូវឱ្យប្រើ provider ជាក់លាក់ណាមួយឡើយ។

API key ដែលប្រើសម្រាប់ផ្ទៀងផ្ទាត់ ត្រូវមាន scope `lease:exclusive` និងបញ្ជី `allowedConnections` ដែលបានកំណត់យ៉ាងច្បាស់ និងមិនទទេ។ ព្រំដែននៃការកែប្រែមូលដ្ឋានទិន្នន័យ អនុវត្តការតម្រូវឱ្យវាលទាំងពីរនេះមានរួមគ្នា នៅពេលបង្កើត key និងធ្វើបច្ចុប្បន្នភាពផ្នែកខ្លះ។

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

ការឆ្លើយតបដែលជោគជ័យសម្រាប់ acquire, renew និង release បង្ហាញ timestamps, `state` និង `generation` វិជ្ជមានពិតប្រាកដ ប៉ុន្តែមិនដែលបង្ហាញ connection ឬព័ត៌មានសម្គាល់ឡើយ។ Renew និង release ផ្តល់ generation នៅក្នុងតួ JSON៖

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Owner នៃ lease ដែលសកម្ម អាចស្នើសុំ metadata សម្រាប់បង្ហាញដែលការពារឯកជនភាពយ៉ាងច្បាស់ សម្រាប់ binding បច្ចុប្បន្នរបស់វា៖

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

សកម្មភាព status ដែលជ្រើសរើសប្រើតាមចិត្តនេះ ត្រូវបានការពារដោយ owner ដែលមិនអាចទាយបាន, managed API key ដែលបានផ្ទៀងផ្ទាត់ និង generation សកម្មពិតប្រាកដ ក្នុង transaction មូលដ្ឋានទិន្នន័យតែមួយ។ `displayName` គឺជាឈ្មោះ connection ដែលបានកំណត់រួច និងបានកាត់ចន្លោះទទេប៉ុណ្ណោះ; វាគឺ `null` នៅពេលគ្មានឈ្មោះដែលបានកំណត់ដោយសុវត្ថិភាព។ OmniRoute មិនដែលជំនួសវាដោយអ៊ីមែល ឬអត្តសញ្ញាណគណនីដែលបានបង្កើតដោយស្វ័យប្រវត្តិឡើយ។ តម្លៃ provider គឺជាស្លាកសម្រាប់បង្ហាញដែលមិនមានព័ត៌មានរសើប ហើយមិនមែនជាអត្តសញ្ញាណ provider ដែលឆបគ្នា និងបានបង្កើតដោយស្វ័យប្រវត្តិឡើយ។ Credentials, tokens, cookies, raw connection ឬ API key ids, owner hashes, fencing secrets និងទិន្នន័យកំណត់ផ្លូវខាងក្នុង ត្រូវបានដកចេញ។

ការស្វែងរកដែលប្រើ key ខុស, owner ខុស, generation ហួសសម័យ, ខ្វះ, ផុតកំណត់, បាន release និងត្រូវបាន invalidated ទាំងអស់ ត្រឡប់កំហុស `409 LEASE_FENCE_STALE` ដូចគ្នា ដោយគ្មាន metadata របស់ connection។ Client ដែលបានទទួលការឆ្លើយតបរង់ចាំសមត្ថភាព មិនមាន binding សកម្មសម្រាប់ពិនិត្យឡើយ។ នៅពេលការកំណត់ផ្លូវប្តូរ lease សកម្ម generation ដដែលនៅតែមានសុពលភាព ហើយ status ត្រឡប់ binding ថ្មីជាអាតូមិក មិនដែលត្រឡប់ binding ចាស់ឡើយ។ Client ដែលមានស្រាប់នៅតែមិនមានការផ្លាស់ប្តូរ ព្រោះការឆ្លើយតប acquire, renew, release និង waiting នៅតែរក្សារូបរាងដើមរបស់វា។

កិច្ចសន្យារបស់ server នេះ មិនផ្លាស់ប្តូរ `/status` របស់ OpenAI Codex ស្តង់ដារឡើយ។ បច្ចុប្បន្ន Codex ស្តង់ដារ រាយការណ៍ provider របស់ model និងស្ថានភាព authentication/account ដែលមានស្រាប់ ប៉ុន្តែមិនបង្ហាញ metadata គណនីរបស់ provider ផ្ទាល់ខ្លួនតាមអំពើចិត្តឡើយ; ការរួមបញ្ចូលជាមួយ client នាពេលក្រោយ ត្រូវហៅសកម្មភាពនេះ ហើយសម្រេចថាត្រូវបង្ហាញ `connection.displayName` យ៉ាងដូចម្តេច។

រាល់សំណើ inference ដែលគ្រប់គ្រងដោយ managed បន្ទាប់មក ត្រូវផ្តល់ control headers ទាំងពីរ៖

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

owner ពិតប្រាកដ, generation, connection សកម្ម និង API key ដែលបានផ្ទៀងផ្ទាត់ ត្រូវបានធ្វើ fencing ភ្លាមៗ មុនពេលព្យាយាម upstream នីមួយៗដែលបានគាំទ្រ។ ការបញ្ជូន owner និង generation ឡើងវិញជាមួយ key ផ្សេង បរាជ័យ ទោះបី key នោះអនុញ្ញាតឱ្យប្រើ connection ដូចគ្នាក៏ដោយ។ Raw owners មិនត្រូវបានរក្សាទុក, កត់ត្រា, រក្សាទុកក្នុង request snapshot ឬបញ្ជូនទៅ upstream ឡើយ។

ការប្រជែងធនធានបណ្តោះអាសន្ន ត្រឡប់ HTTP `429` ជាមួយ `Retry-After` និង៖

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ការឆ្លើយតបនេះមានន័យតែថា សំណុំ eligible ធម្មតាមិនទទេ ហើយ candidate ទំនេរគ្រប់មួយ ត្រូវបាន lease សកម្មរបស់ភាគីផ្សេងកាន់កាប់។ Model/provider ដែលមិនគាំទ្រ, policy មិនត្រូវគ្នា, cooldown, quota, health និងការបរាជ័យសិទ្ធិប្រើប្រាស់ធម្មតាផ្សេងទៀត នៅតែរក្សាការឆ្លើយតប OmniRoute ដែលមានស្រាប់។

### `x-omniroute-compression`

ការបដិសេធផែនការបង្ហាប់តាមសំណើនីមួយៗ។ មានអាទិភាពខ្ពស់បំផុត — ឈ្នះការបដិសេធ routing-combo, profile សកម្ម, auto-trigger និង Default ក្នុង panel។ តម្លៃ៖

| Value         | Effect                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------- |
| `off`         | គ្មានការបង្ហាប់សម្រាប់សំណើនេះ។                                                                    |
| `default`     | Profile Default ដែលបានមកពី panel (មិនអើពើ profile សកម្ម)។ Engines ដែលបាត់បង់ទិន្នន័យ ត្រូវបានបិទ។ |
| `safe`        | អនុវត្តតែការដកស្ទួន និងការរួមចន្លោះទទេប៉ុណ្ណោះ។                                                   |
| `allow-lossy` | រក្សាផែនការរបស់ operator សម្រាប់សំណើនេះ រួមទាំងសេចក្តីសង្ខេប និងការសរសេររចនាប័ទ្មឡើងវិញ។          |
| `engine:<id>` | Engine តែមួយនៅពេលបានបើក ដូចជា `engine:rtk`។ ជម្រើសប្រើ engine នោះតាមសំណើនីមួយៗ។                   |
| `<combo>`     | Combo ដែលមានឈ្មោះ ត្រូវផ្គូផ្គងតាមឈ្មោះ (មិនប្រកាន់អក្សរធំតូច) ជាមុន បន្ទាប់មកតាម id។             |

កំណត់សម្គាល់៖

- តម្លៃដែលមិនស្គាល់ ត្រូវបានមិនអើពើ (សំណើមិនត្រូវបានបដិសេធឡើយ); ការដោះស្រាយបន្តធ្លាក់ទៅតាមលំដាប់អាទិភាពធម្មតារបស់ operator។
- ប្រសិនបើ combo ច្រើនមានឈ្មោះដូចគ្នា សូមបញ្ជូន combo **id** ដើម្បីផ្គូផ្គងបានច្បាស់លាស់។
- Combo ដែលមានឈ្មោះ `off` ឬ `default` មិនអាចជ្រើសរើសតាមឈ្មោះបានទេ (ពាក្យគន្លឹះទាំងនេះត្រូវបានបកស្រាយជាមុន); សូមយោងទៅ combo បែបនេះតាម id របស់វា។
- master compression switch គឺជារបាំងរឹង៖ នៅពេលការបង្ហាប់ត្រូវបានបិទជាសកល header នេះមិនអាចបើកវាបានឡើយ។

ផែនការដែលបានអនុវត្ត ត្រូវបានបញ្ជូនត្រឡប់ក្នុង response header៖

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ដែល `<source>` គឺមួយក្នុងចំណោម `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ឬ `off`។

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

អ្នកផ្តល់សេវាដែលមាន៖ Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI។

លេខសម្គាល់កាតាឡុកមានទម្រង់ `provider/model` (ឧទាហរណ៍៖ `jina-ai/jina-embeddings-v5-omni-small`)។ លេខសម្គាល់ម៉ូដែល Jina ដែលមិនមានបុព្វបទ ហើយមាននៅក្នុង registry (ឧទាហរណ៍៖ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ក៏អាច resolve បានដែរ។ Jina embed/rerank/classify/segment ប្រើព័ត៌មានសម្ងាត់ `jina-ai` ពី dashboard ជាមុនសិន; `JINA_AI_API_KEY` គឺជាជម្រើសបម្រុងតែពេលគ្មាន dashboard key ប៉ុណ្ណោះ។ កាត `jina-reader` គឺសម្រាប់ Reader / `r.jina.ai` ប៉ុណ្ណោះ (`POST /v1/web/fetch`) ហើយមិនផ្តល់ embeddings ឬ rerank ឡើយ។

ម៉ូដែលក្នុង Registry ដែលប្រកាសថាគាំទ្រ multimodal ក៏ទទួលយក items ដែលមានរចនាសម្ព័ន្ធ និងមិនអាស្រ័យលើ provider បានរហូតដល់ 32 ផងដែរ។ ប្រភេទ media item មាន `text`, `image`, `audio`, `video`, និង `document`។ `source`
របស់ media គឺជា `{"type":"url","url":"https://..."}` ឬ
`{"type":"base64","data":"...","media_type":"..."}`។

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
និង alias របស់គ្រួសារ `jina-ai/jina-embeddings-v5-omni` → omni-small) ក៏ទទួលយកឯកសារ native
EmbeddingsV5Request របស់ Jina ហើយ **បញ្ជូនបន្តដោយមិនកែប្រែ** ទៅ `https://api.jina.ai/v1/embeddings`៖

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

តម្លៃ native `{ image | audio | video | pdf }` អាចជា public HTTPS URL, `data:` URI ឬ base64 ដើម។ OmniRoute មិនបម្លែង objects ទាំងនោះទៅជាខ្សែអក្សរ ឬទាញយក native image URLs ឡើយ — Jina ជាអ្នកទាញយក media សាធារណៈដោយខ្លួនឯង។ វាលបន្ថែមរបស់ Jina (`task`, `normalized`, `truncate`, `embedding_type`) ត្រូវបានបញ្ជូនបន្ត។ SKU របស់ Jina ដែលមានតែ text នៅតែបដិសេធឯកសារដែលមិនមែនជា text។

ដែនកំណត់សុវត្ថិភាព និងការបញ្ជូន៖

- Remote media URLs ត្រូវតែជា public HTTPS។ Items canonical `{type,source:url}` ត្រូវបានទាញយកនៅផ្នែក server (ធ្វើសុពលកម្ម redirect ឡើងវិញ, កំណត់ពេលអស់សុពលភាព, កំណត់ទំហំ, public DNS និងការភ្ជាប់ដែលបាន pin) ហើយបញ្ចូល inline មុនពេលហៅ provider។ Items Jina-native `{image:"https://..."}` ត្រូវបានបញ្ជូនបន្តតាមសភាពដើម បន្ទាប់ពីឆ្លងកាត់ការត្រួតពិនិត្យ public-HTTPS ដូចគ្នា; Jina ជាអ្នកទាញយក URL។
- Inline base64 media ត្រូវបានកំណត់ត្រឹម 8 MiB បន្ទាប់ពី decode ក្នុងមួយ item និង 16 MiB បន្ទាប់ពី decode សរុបក្នុងមួយ request។

ការបកប្រែទៅតាម provider (canonical items មិនដែលត្រូវបានបញ្ជូនបន្តដោយមិនកែប្រែឡើយ)៖

- ម៉ូដែល Jina multimodal៖ item កម្រិតកំពូលនីមួយៗក្លាយជាវត្ថុមួយដែលមាន key តាម modality
  (`text` / `image` / `audio` / `video` / `pdf`) ដោយប្រើ data URI សម្រាប់ media inline; vector មួយសម្រាប់
  item កម្រិតកំពូលនីមួយៗ។

### បុព្វបទ model id (`?prefix=`)

ម៉ូដែលភាគច្រើនត្រូវបានផ្សព្វផ្សាយក្រោម **បុព្វបទ provider**។ បុព្វបទដែលអ្នកទទួលបាន ត្រូវបានគ្រប់គ្រងដោយ
feature flag `MODELS_CATALOG_PREFIX_MODE` ហើយអាចបដិសេធបាន **ក្នុងមួយសំណើ** ដោយប្រើ
query parameter — មានប្រយោជន៍សម្រាប់ client ដែលចង់បានបញ្ជីស្អាត ដោយមិនបាច់ផ្លាស់ប្តូរការកំណត់
ទូទាំង server សម្រាប់អ្នកដទៃ៖

```bash
GET /v1/models?prefix=alias        # id មួយក្នុងមួយម៉ូដែល — បុព្វបទ alias ខ្លី
GET /v1/models?prefix=dual         # ទម្រង់ទាំងពីរ (លំនាំដើមរបស់ server)
GET /v1/models?prefix=canonical    # មានតែបុព្វបទ provider-id ពេញលេញ
```

### តម្រង Discovery (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ទទួលយកតម្រង discovery ដែលជ្រើសរើសប្រើ។ ប្រសិនបើគ្មានតម្រងណាមួយ ការឆ្លើយតប
មិនផ្លាស់ប្តូរទេ។ តម្រងទាំងនេះបង្រួម catalog ដែល caller មើលឃើញរួចហើយ (សិទ្ធិ API-key ត្រូវបានអនុវត្តជាមុន)
ហើយវាដំណើរការមុនការបែងចែកទំព័រតាមរចនាប័ទ្ម OpenAI `limit` / `after`៖

```bash
GET /v1/models?capability=vision&capability=tool_calling   # សមត្ថភាពដែលបានរាយទាំងអស់ត្រូវតែជា true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # catalog `type`; ជួរដែលគ្មានវា គឺ `chat`
GET /v1/models?q=sonnet&limit=10                           # ផ្គូផ្គងមិនប្រកាន់អក្សរធំតូចលើ id ឬ name
```

| ប៉ារ៉ាម៉ែត្រ  | តម្លៃ                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ចំនួនគត់មិនអវិជ្ជមាន ដែលប្រៀបធៀបជាមួយ `context_length`                                              |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | តួអក្សរ 1–200                                                                                       |

តម្លៃដែលមិនស្គាល់ ឬ `min_context` ដែលមិនមែនជាចំនួនគត់មិនអវិជ្ជមាន (ឧទាហរណ៍ `1.5`)
នឹងត្រឡប់ HTTP `400` ហើយសារនោះនឹងរាយតម្លៃត្រឹមត្រូវ។ ការអនុវត្ត៖
`src/app/api/v1/models/catalogFilters.ts`។

### បញ្ជីសម្រាំងម៉ូដែល (`POST /v1/models/query`)

`POST /v1/models/query` ត្រឡប់បញ្ជីខ្លីដែលមានលទ្ធផលកំណត់ជាក់លាក់ពីកាតាឡុកដដែល ដោយប្រើ
ការផ្ទៀងផ្ទាត់ដូចគ្នា និងការមើលឃើញតាមសោនីមួយៗដូចជា `GET /v1/models`៖

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

គ្រប់វាលទាំងអស់សុទ្ធតែជាជម្រើស។ `capabilities` និង `exclude` អាចទទួលយកអារេ ឬខ្សែអក្សរដែលបំបែកដោយសញ្ញាក្បៀស;
`max_output` ប្រៀបធៀបជាមួយ `max_output_tokens`។ លទ្ធផលត្រូវបានតម្រៀបតាម `owned_by` បន្ទាប់មកតាម `id`។
`limit` មានតម្លៃលំនាំដើមជា `20` ហើយតម្លៃលើសពី `100` នឹងត្រូវកំណត់ត្រឹម `100`។ JSON មិនត្រឹមត្រូវ វាលដែលមិនស្គាល់
ឬតម្លៃមិនត្រឹមត្រូវ នឹងត្រឡប់ HTTP `400`។

### ម៉ូដែលជជែកដែលលាក់ជាបុគ្គល

ម៉ូដែលដែលត្រូវបានសម្គាល់ថា **លាក់** នៅលើទំព័ររបស់អ្នកផ្តល់សេវា នឹងត្រូវដកចេញពីកាតាឡុក ហើយត្រូវបានបដិសេធ
ដោយ HTTP `404` / `model_not_found` នៅពេលស្នើសុំដោយផ្ទាល់។ ការត្រួតពិនិត្យនេះប្រើអ្នកផ្តល់សេវា និងម៉ូដែលដែលបានដោះស្រាយ
រួចរាល់ រួមទាំងឈ្មោះកាត់របស់អ្នកផ្តល់សេវា បុព្វបទថ្នាំងរបស់អ្នកផ្តល់សេវាដែលឆបគ្នា និងលំនាំដើមនៃការតភ្ជាប់។
Combo នឹងរំលងគោលដៅដែលលាក់ ហើយអាចប្រើ sibling ដែលអាចមើលឃើញបាន; នៅពេលគ្មានគោលដៅដែលអាចប្រតិបត្តិបាននៅសល់
វានឹងត្រឡប់កូដកំហុសដដែល។ ការបង្ហាញម៉ូដែលឡើងវិញនឹងមានប្រសិទ្ធភាពនៅសំណើបន្ទាប់។ ការកំណត់ការមើលឃើញសម្រាប់តែរូបភាព
នឹងមិនលាក់ម៉ូដែលជជែកដែលមាន ID ដូចគ្នានោះទេ។

## ការបង្កើតសំឡេង ElevenLabs

បំណែកសំឡេងដែលបាន encode ជា base64 នៅក្នុងព្រឹត្តិការណ៍ SSE។ Route ទាំងប្រាំមួយគាំទ្រ CORS preflight។

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# បែបផែនសំឡេងខ្លីមួយ។ រយៈពេល៖ 0.5 ដល់ 30 វិនាទី។
```

## Files API

ចំណុចបញ្ចប់ files ដែលអាចប្រើជាមួយ OpenAI សម្រាប់ការបញ្ចូល/បញ្ចេញជាបាច់ និងការអាប់ឡូតឯកសារតាមគោលបំណង។

| Method | Path                     | Description                                                                                                      |
| ------ | ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | អាប់ឡូតឯកសារ (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — អតិបរមា 512 MiB |
| GET    | `/v1/files`              | រាយបញ្ជីឯកសារសម្រាប់ API key ដែលបានផ្ទៀងផ្ទាត់                                                                   |

| GET    | `/v1/files/[id]/content` | បញ្ជូនខ្លឹមសារដើមរបស់ឯកសារត្រឡប់មកវិញជាស្ទ្រីម                                                                   |

**ការផ្ទៀងផ្ទាត់សិទ្ធិ:** Bearer API key — files ត្រូវបានកំណត់វិសាលភាពតាម API key នីមួយៗតាមរយៈ `getApiKeyRequestScope`។ API key មួយអាចមើល ទាញយក និងលុបតែ files របស់ខ្លួនប៉ុណ្ណោះ; សម័យ dashboard ដែលគ្មាន key អាចអាន instance ទាំងមូលបាន; file ដែលគ្មានម្ចាស់ (ការអាប់ឡូតដោយអនាមិក ឬដោយសម័យ dashboard) ត្រូវបានបដិសេធចំពោះអ្នកហៅដែលមិនមែនជាសម័យ។ `GET /v1/files` បដិសេធអ្នកហៅអនាមិក — និង key ដែលបានបង្ហាញ ប៉ុន្តែមិនអាចដោះស្រាយបាន — ដោយប្រើ `401` ទោះបី `REQUIRE_API_KEY=false` ក៏ដោយ ជំនួសឱ្យការរាយបញ្ជី files របស់ tenant ទាំងអស់ (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)។

([ការចេញវិក្កយបត្រ Firecrawl](https://docs.firecrawl.dev/billing))៖ លទ្ធផល 11 មានតម្លៃ $0.004។

`time_range` ទូទៅឥឡូវនេះត្រូវបានបញ្ជូនទៅអ្នកផ្តល់សេវាទាំងពីរ៖ Exa ទទួល `startPublishedDate` (ត្រាពេលវេលា ISO)

នឹងជំនួសកាលបរិច្ឆេទដែលបានផ្គូផ្គង។

`snippet` ទេ), `highlight_scores`, `summary`, `subpages`, `entities` និង `extras` នៅក្នុង
`provider_raw`។ លទ្ធផល Tavily រក្សាទុក `images` និង `favicon`។

`deep` ([តម្លៃ Linkup](https://docs.linkup.so/pages/documentation/development/pricing))

Exa `type: "lite"` (Exa 3.0) ទទួលយកសំណុំវាលតូចជាង ហើយបដិសេធសំណើទាំងមូល

## Web Fetch API

ស្រង់មាតិកាពី URL តាមរយៈអ្នកផ្តល់សេវា web-fetch ដែលបានកំណត់រចនាសម្ព័ន្ធ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)។

Parallel Extract (`parallel-search`, API key ដូចគ្នានឹង Parallel Search) ត្រឡប់តែ Markdown
ប៉ុណ្ណោះ — `format` ផ្សេងទៀតណាមួយនឹងទទួលបាន `400` — ហើយកំណត់មាតិកាត្រឹម 100,000 តួអក្សរ។ នៅពេលទំព័រគោលដៅខ្លួនឯងមិនអាចស្រង់បាន upstream នឹងរាយការណ៍វានៅក្នុង HTTP 200;
OmniRoute បង្ហាញវាជា `422` ជាមួយសារថេរ។

| Method | Path            | Description                                                      |
| ------ | --------------- | ---------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | ទាញយក/ស្កេន URL — body ត្រូវបានផ្ទៀងផ្ទាត់ដោយ `v1WebFetchSchema` |

**ការផ្ទៀងផ្ទាត់:** Bearer API key (`extractApiKey` + `isValidApiKey`)។ គោលការណ៍ត្រូវបានអនុវត្តតាមរយៈ `enforceApiKeyPolicy`។

**ការប្ដូរជំនួសដែលដឹងពីកូតា (#8297):** នៅពេលមិនបានផ្តល់ `provider` ជាក់លាក់ បណ្តុំ
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ត្រូវបាន
ដើរឆ្លងកាត់តាមលំដាប់អាទិភាពថេរ (fill-first) — អ្នកផ្តល់សេវាដែលកំណត់រចនាសម្ព័ន្ធរួច ប៉ុន្តែមានកម្រិតអត្រា នឹងត្រូវរំលង
ជំនួសឱ្យការបញ្ឈប់សំណើភ្លាមៗ ហើយការបរាជ័យ upstream ដែលអាចព្យាយាមម្ដងទៀត/ពាក់ព័ន្ធនឹងកូតា
(HTTP 429 ជានិច្ច; 402/403 សម្រាប់កម្រិត free tier ប្រភេទកូតារបស់ Firecrawl/Tavily/TinyFish —
មិនមែនសម្រាប់ Jina Reader ទេ ហើយមិនដែលសម្រាប់សំណើ 400 មិនត្រឹមត្រូវធម្មតាទេ) នឹងបន្តទៅកាន់
អ្នកផ្តល់សេវាដែលមានព័ត៌មានសម្ងាត់ និងមិនទាន់បានសាកល្បងបន្ទាប់ នៅពេលសំណើកំពុងដំណើរការ។ នៅពេលអ្នកផ្តល់សេវាទាំងអស់ក្នុងបណ្តុំអស់សមត្ថភាព endpoint នឹងត្រឡប់ `429` តែមួយ
(ជាមួយបឋមកថា `Retry-After`) ជំនួសឱ្យ `400` ទូទៅដូចមុន។ នៅពេលបានស្នើ `provider` ជាក់លាក់ នឹង **គ្មានការប្ដូរជំនួសដោយស្ងៀមស្ងាត់ទេ** — អ្នកផ្តល់សេវាជាក់លាក់ដែលមានកម្រិតអត្រា ឬបរាជ័យ នឹងបង្ហាញកំហុសរបស់វាផ្ទាល់ (`429` ប្រសិនបើមានកម្រិតអត្រា បើមិនដូច្នោះទេគឺស្ថានភាពពី upstream)។

## ការផ្សាយទិន្នន័យ WebSocket

```bash
GET /v1/ws?handshake=1
```

ផ្ទៀងផ្ទាត់ handshake សម្រាប់ការអាប់ក្រេដ WebSocket ហើយត្រឡប់សារឧទាហរណ៍នៃ wire protocol (`request`, `cancel`)។ WS frames ពិតប្រាកដត្រូវបានគ្រប់គ្រងដោយ WS server ដែលភ្ជាប់មកជាមួយ នៅខាងក្រៅតារាង route របស់ Next.js។

**ការផ្ទៀងផ្ទាត់:** Bearer API key ក្នុងអំឡុងពេល handshake។

### Responses API តាម WebSocket (codex ប៉ុណ្ណោះ)

```bash
# Host:port ដូចគ្នានឹង HTTP API (លំនាំដើម 20128); អាប់ក្រេដការតភ្ជាប់៖
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ឬ៖ -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Frame ដំបូង ត្រូវតែជា response.create៖
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

ប្រូកស៊ី Responses-API-over-WebSocket ត្រូវបានភ្ជាប់ **សម្រាប់ `codex` តែប៉ុណ្ណោះ** (backend របស់ ChatGPT)។ វាស្តាប់នៅលើ port ដូចគ្នានឹង API/dashboard នៅ paths `/v1/responses`,
`/responses` និង `/api/v1/responses`។ នៅលើ frame `response.create` ដំបូង វាផ្ទៀងផ្ទាត់អត្តសញ្ញាណ + រៀបចំតាមរយៈ bridge ខាងក្នុង `codex-responses-ws` ជ្រើសរើសការតភ្ជាប់ codex OAuth ហើយបញ្ជូនទិន្នន័យជាប្រឡាយទៅ `wss://chatgpt.com/backend-api/codex/responses`
តាមរយៈ transport `wreq-js`។ **ម៉ូដែលដែលមិនមែនជា codex នឹងត្រូវបដិសេធ** (`codex_ws_provider_required`)។
សម្រាប់ការកំណត់ផ្លូវតាម quota-share សូមប្រើ `model: "qtSd/<group>/codex/<model>"`។ បានអនុវត្តនៅក្នុង
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`។

**ការផ្ទៀងផ្ទាត់:** Bearer API key ក្នុងអំឡុងពេល handshake។ HTTP server ដែលភ្ជាប់មកជាមួយ (`server-ws.mjs`)
ត្រូវតែជា entrypoint សកម្ម (តាមលំនាំដើម វាគឺជាវា នៅពេល `app/server-ws.mjs` មាន)។

#### Model id៖ ប្រើ ChatGPT id ដើម (គ្មានបុព្វបទ `codex/`)

**Codex CLI** របស់ OpenAI ផ្ទៀងផ្ទាត់ឈ្មោះម៉ូដែលនៅផ្នែក client នៅពេល
`supports_websockets = true` ហើយ **បដិសេធ id ដែលមានបុព្វបទ provider** ដូចជា
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)។ ផ្ញើ id ដើម (ឧ. `gpt-5.5`)។ Bridge របស់ OmniRoute គឺសម្រាប់ codex តែប៉ុណ្ណោះ ដូច្នេះវានឹងដោះស្រាយ id ដើមឡើងវិញជាម៉ូដែល codex
(`resolveCodexWsModelInfo`) មុនពេលបញ្ជូនបន្តទៅ upstream — ទោះបីជា `gpt-5.5` ដើមនឹងត្រូវបញ្ជូនទៅ provider ផ្សេងតាម HTTP ក៏ដោយ។

#### ការកំណត់រចនាសម្ព័ន្ធ OpenAI Codex CLI

ចង្អុល Codex CLI ទៅ OmniRoute ដោយបន្ថែម provider ផ្ទាល់ខ្លួនដែលមានការគាំទ្រ WebSocket ទៅ `~/.codex/config.toml` (ប្រើ `CODEX_HOME` ដាច់ដោយឡែក ដើម្បីជៀសវាងការប៉ះពាល់ដល់ config ដែលមានស្រាប់)៖

```toml
model = "gpt-5.5"                 # id ដើម — មិនមែន "codex/gpt-5.5" ទេ
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # គ្មាន slash នៅខាងចុង; WS URL ត្រូវបានបង្កើតដោយស្វ័យប្រវត្តិ (ប្រើ https/wss នៅ production)
wire_api = "responses"                    # តម្លៃដែលគាំទ្រតែមួយគត់ចាប់ពី ខែកុម្ភៈ 2026
supports_websockets = true                # បើក transport Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # រក្សាទុក OmniRoute API key (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key (key ណាមួយ ប្រសិនបើ REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI អាប់ក្រេដ `base_url + /responses` ទៅជា WebSocket ហើយ OmniRoute បញ្ជូនបន្តវាទៅកាន់ការតភ្ជាប់ codex OAuth ដែលបានជ្រើសរើស។ បានផ្ទៀងផ្ទាត់ពីដើមដល់ចប់ជាមួយ server មូលដ្ឋាន៖ ChatGPT ត្រឡប់ `codex.rate_limits` + `response.created` ហើយផ្សាយលទ្ធផលបញ្ចប់ជាបន្តបន្ទាប់។

## ការប្រើប្រាស់សម្រាប់ self-service (`/api/usage/om-usage`)

API key ណាមួយអាចអានការប្រើប្រាស់ និងកូតា **របស់ខ្លួនឯង** បាន — មិនត្រូវការសិទ្ធិគ្រប់គ្រងទេ។ នេះជា endpoint ដែល
client (CLI, បន្ទះ OmniCopilot) ប្រើ ដើម្បីបង្ហាញការចំណាយរបស់អ្នកកាន់សោ។

```bash
# ទម្រង់អត្ថបទ (កិច្ចសន្យាប្រវត្តិសាស្ត្រ — អត្ថបទធម្មតាសម្រាប់ terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ទម្រង់មានរចនាសម្ព័ន្ធ — អ្វីដែល UI ប្រើប្រាស់
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

សោត្រូវតែបើក **`allowUsageCommand`** (បិទតាមលំនាំដើម — កម្មវិធីគ្រប់គ្រង API-key របស់ dashboard
អាចបិទ/បើកវាសម្រាប់សោនីមួយៗ)។ ប្រសិនបើមិនបើកទេ endpoint នឹងឆ្លើយតប `403`។

`?format=json` ត្រឡប់រចនាសម្ព័ន្ធដែលបែងចែកតាមប្រភេទ ដូច្នេះអ្នកហៅមិនអាន data field ពីការបដិសេធបានទេ។ នៅពេលជោគជ័យ៖

```jsonc
{
  "allowed": true,
  // មានតែនៅពេលសោបានជ្រើសរើសកម្រិតប្រើប្រាស់តាមសោ (USD ប្រចាំថ្ងៃ/សប្តាហ៍) ប៉ុណ្ណោះ៖
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // snapshot កូតារបស់ provider ដែលបានជ្រើសរើស ឬ null នៅពេលមិនទាន់មានអ្វីត្រូវបាន cache៖
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // snapshot របស់ connection ទាំងអស់ ដើម្បីឱ្យ UI អាចបង្ហាញ provider ជាច្រើននៅជាប់គ្នា៖
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

នៅពេលបដិសេធ (`401` សោមិនត្រឹមត្រូវ / `403` មិនត្រូវបានអនុញ្ញាត) route ដដែលនេះនឹងត្រឡប់
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` ដែលមានតែទទេ
(សោត្រូវបានអនុញ្ញាត ប៉ុន្តែមិនទាន់ទទួលបានទិន្នន័យ) គឺជាស្ថានភាពផ្សេងពីការបដិសេធ ហើយមានតែទម្រង់ JSON
ប៉ុណ្ណោះដែលអាចបែងចែកស្ថានភាពទាំងពីរនេះបាន។

**ការផ្ទៀងផ្ទាត់:** Bearer API key របស់អ្នកហៅផ្ទាល់ ដែលបានផ្ទៀងផ្ទាត់ដោយ `isValidApiKey` — នេះ _មិនមែនជា_
ផ្ទៃគ្រប់គ្រង (`/api/keys/…`) ទេ ដែលនៅតែការពារដោយ `requireManagementAuth`។

### ភាគរយកូតាដើម និងភាគរយដែលបានកែតម្រូវតាម cutoff

នៅពេលប្រើប្រាស់ `/api/usage/om-usage` អ្នកហៅគួរកត់សម្គាល់ពីភាពខុសគ្នារវាង
ភាគរយដែលបង្ហាញដោយ **លទ្ធផលអត្ថបទធម្មតា** និងលទ្ធផល **JSON ដែលមានរចនាសម្ព័ន្ធ**៖

| Aspect               | Plain-text format (`/api/usage/om-usage` / `@@om-usage`)                                            | JSON format (`?format=json`)                                                            |
| :------------------- | :-------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------- |
| **Output field**     | `NN% left` (ឧ. `20% left`)                                                                          | `provider.quotas` / `providers[].quotas`                                                |
| **Measurement**      | **សិទ្ធិប្រើប្រាស់ដែលនៅសល់ និងបានកែតម្រូវតាម cutoff**៖ សមត្ថភាពដែលនៅសល់លើសកម្រិត cutoff             | **កូតាដើមពី upstream**៖ ការវាស់វែងរបស់ provider ដែលមិនបានកែតម្រូវ                       |
| **Cutoff scaling**   | បានធ្វើមាត្រដ្ឋានតាម `effectiveRemainingPercent()` ដើម្បីឱ្យ reserve ដែលបានការពារបង្ហាញជា `0% left` | គ្មាន (តម្លៃ snapshot ដើមតាមដែល provider បានរាយការណ៍)                                   |
| **Threshold data**   | បានបញ្ចូលទៅក្នុងភាគរយដែលបង្ហាញ                                                                      | រក្សាទុកក្នុង `quotaWindowThresholds` តាម connection នីមួយៗ (ឬតម្លៃលំនាំដើមរបស់ server) |
| **Primary consumer** | CLI អន្តរកម្ម, សារ prompt ក្នុង terminal, ប្រតិបត្តិករមនុស្ស                                        | ការរួមបញ្ចូលតាមកម្មវិធី, dashboard, analytics, កម្មវិធីតាមដានការចេញវិក្កយបត្រ           |

#### រូបមន្តកែតម្រូវ Cutoff

OmniRoute គាំទ្រ cutoff កូតាសកម្មដែលមានលក្ខណៈ proactive ដើម្បីទប់ស្កាត់ការប្រើប្រាស់ upstream រហូតអស់
(កំណត់រចនាសម្ព័ន្ធតាម connection `quotaWindowThresholds`, លំនាំដើមរបស់ provider ឬការកំណត់ resilience សកល)។ នៅពេលកម្រិត cutoff
(ឧ. `cutoff = 25%`) សកម្មលើបង្អួចកូតា អ្នកបង្ហាញអត្ថបទនឹងគណនាសិទ្ធិប្រើប្រាស់ដែលនៅសល់ដូចតទៅ៖

- ប្រសិនបើ `remaining <= cutoff`: ត្រឡប់ `0%`។
- ប្រសិនបើ `remaining > cutoff`: returns `((remaining - cutoff) / (100 - cutoff)) * 100`។

លទ្ធផលអត្ថបទដែលបានធ្វើទ្រង់ទ្រាយ នឹងបង្គត់ទៅចំនួនគត់ដែលនៅជិតបំផុត (`Math.round(...)`)។

#### ឧទាហរណ៍សម្រាប់បង្ហាញagaduhan

ពិចារណាបង្អួចកូតារបស់អ្នកផ្តល់សេវាមួយ ដែលមាន **ការប្រើប្រាស់ដើម 60%** (ដូច្នេះ **កូតាដើមដែលនៅសល់ 40%**) និងកម្រិតកំណត់ **25% នៃកូតាដែលនៅសល់**៖

| តំណាង                         | ការគណនា                                            |  នៅសល់  |       ភាគរយប្រើប្រាស់ដែលសន្និដ្ឋាន       |
| :---------------------------- | :------------------------------------------------- | :-----: | :--------------------------------------: |
| **JSON ដើម (`?format=json`)** | សnapshot ពី upstream (`quotas[window]`)            | **40%** |                 **60%**                  |
| **ទម្រង់អត្ថបទ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (ប្រសិនបើគណនា `100 - remaining`) |

- **ហេតុអ្វីបានជាអត្ថបទបង្ហាញថានៅសល់ 20%៖** ក្នុងចំណោមកូតារូបវន្ត 40% ដែលនៅសល់លើគណនី 25% ត្រូវបានបម្រុងទុកដោយគោលការណ៍កម្រិតកាត់ផ្តាច់។ អ្នកហៅមានតែ 15% ក្នុងចំណោមទំហំដែលអាចប្រើបាន 75% ប៉ុណ្ណោះ ដែលនៅសល់ មុនពេលរ៉ោតទ័រឈប់បញ្ជូនទៅការតភ្ជាប់នេះ។ ការធ្វើមាត្រដ្ឋានធានាថា ការតភ្ជាប់នឹងបង្ហាញសញ្ញាថាអស់ (`0% left`) ពិតប្រាកដនៅពេលការបញ្ជូននឹងត្រូវបញ្ឈប់។
- **ហេតុអ្វីបានជា JSON រក្សាតម្លៃដើម៖** បន្ទុក JSON ត្រឡប់ snapshot ពិតប្រាកដរបស់អ្នកផ្តល់សេវា (`UsageSnapshot`) ដើម្បីឱ្យឧបករណ៍ខាងក្រៅអាចចូលប្រើការប្រើប្រាស់ពិតប្រាកដពី upstream និង `quotaWindowThresholds` កម្រិតការតភ្ជាប់ ដោយគ្មានការធ្វើមាត្រដ្ឋានបាត់បង់ទិន្នន័យនៅខាងម៉ាស៊ីនមេ។

#### សេចក្តីណែនាំអំពីការផ្លាស់ប្តូរសម្រាប់អ្នកប្រើប្រាស់

ប្រសិនបើការរួមបញ្ចូលខាងក្រៅ (ដូចជា plugin របស់កម្មវិធីកែសម្រួល ឬ extension របស់ភ្នាក់ងារ) ពីមុនបានទាញយកទិន្នន័យពី endpoint អត្ថបទ (`NN% left`) ហើយគណនាភាគរយប្រើប្រាស់ជា `100 - NN` នោះ ការផ្លាស់ប្តូរទៅ `?format=json` មានន័យថា៖

- ការអានតម្លៃ JSON ដើមនឹងឆ្លុះបញ្ចាំងពី **ការប្រើប្រាស់ពិតប្រាកដពី upstream** (ប្រើប្រាស់ 60% ក្នុងឧទាហរណ៍ខាងលើ)។
- ប្រសិនបើការរួមបញ្ចូលចង់រក្សាអត្ថន័យនៃចំនួនដែលអាចប្រើបានរបស់ endpoint អត្ថបទ វាអាចវាយតម្លៃរូបមន្តចំនួនដែលនៅសល់មានប្រសិទ្ធភាពនៅខាង client ដោយប្រើ `quotaWindowThresholds` សម្រាប់ការកំណត់ជំនួសកម្រិតការតភ្ជាប់។

### ផលប៉ះពាល់លើភាពយឺតយ៉ាវ

ការឆ្លើយតបដែលជា semantic cache HIT ត្រូវបានផ្ដល់ពីឃ្លាំង **ដោយមិនមាន
ការហៅទៅ upstream** ដូច្នេះ `X-OmniRoute-Response-Latency` ដែលបានរាយការណ៍
នឹងជិតសូន្យ (មិនថាភាពយឺតយ៉ាវរបស់ upstream ដើមមានប៉ុនណាក៏ដោយ)។ Client
ដែលយកចិត្តទុកដាក់លើភាពយឺតយ៉ាវ (ការធ្វើ benchmark និងការតាមដាន p50/p99)
គួរតែពិនិត្យ response header
`X-OmniRoute-Cache-Latency`៖

| តម្លៃ        | អត្ថន័យ                                                                    |
| ------------ | -------------------------------------------------------------------------- |
| `synthetic`  | ការឆ្លើយតបបានផ្ដល់ពីឃ្លាំង។ ភាពយឺតយ៉ាវមិនមែនជាពេលវេលា upstream ពិតប្រាកដទេ |
| _(អវត្តមាន)_ | ការឆ្លើយតបពីការហៅទៅ upstream ពិតប្រាកដ                                     |

### ការរំលងឃ្លាំងតាម key

API key អាចជ្រើសមិនអានពី semantic cache តាមរយៈ `cacheDefaultMode`៖

| តម្លៃ    | ឥរិយាបថ                                                   |
| -------- | --------------------------------------------------------- |
| `legacy` | ឥរិយាបថឃ្លាំងធម្មតា (លំនាំដើម)                            |
| `bypass` | រំលងការស្វែងរកក្នុងឃ្លាំងទាំងស្រុង។ ហៅទៅ upstream ជានិច្ច |

កំណត់នៅពេលបង្កើត key (`POST /api/keys`) ឬធ្វើបច្ចុប្បន្នភាព (`PATCH /api/keys/[id]`)៖

```json
{ "cacheDefaultMode": "bypass" }
```

```

```

```json
}
```

- `releaseChannel` — ឆានែល npm របស់ build ដែលកំពុងដំណើរការ៖ `nightly` សម្រាប់កំណែ `-nightly.*`,
  `next` សម្រាប់ pre-release ផ្សេងទៀត (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` សម្រាប់កំណែ stable នៃ
  major ចាស់ជាង `channels.latest`, បើមិនដូច្នោះទេគឺ `latest`។ ប្រើច្បាប់ដូចគ្នានឹង
  `scripts/release/dist-tag.mjs` ដែលជ្រើស npm dist-tag នៅពេល publish។
- `channels` — កំណែចុងក្រោយដែលបានចេញផ្សាយរបស់ dist-tag នីមួយៗ ពី `npm view omniroute dist-tags` (មានការបម្រុងទុកទៅ HTTP របស់ registry) ហើយត្រូវបានរក្សាទុកក្នុង cache ដោយប្រើ TTL 10 នាទីដូចគ្នានឹង `latest`។ `latest` មានជានិច្ច
  (បើគ្មាន នឹងប្រើវាល `latest` បន្ទាប់មក `"unavailable"`); `next`, `nightly` និង `lts` បង្ហាញ
  តែពេល dist-tag នោះមានប៉ុណ្ណោះ។ សំណើដែលមាន `Cache-Control: no-cache` នឹងធ្វើឱ្យការស្វែងរកទាំងពីរឡើងវិញ។

ម៉ូដែលឆានែល (`latest` = v3 រហូតដល់ 4.0 GA, `next` = rc, `nightly` = build ពី
`develop`, `lts` = បំណះ v3 បន្ទាប់ពី 4.0 GA) ត្រូវបានពិពណ៌នានៅក្នុង
`docs/ops/RELEASE_STRATEGY.md`។

```bash
GET /api/v1/vscode/{token}/models

POST /api/v1/vscode/{token}/api/chat
```

ឧទាហរណ៍៖

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

ចំណាំ៖

- alias ដែលមាន token ប្រើ handler ដូចគ្នានឹង `/v1/*` និង `/api/tags`; ទម្រង់ការឆ្លើយតបនៅដដែល។

- Token ដែលផ្អែកលើ URL អាចបង្ហាញនៅក្នុងកំណត់ហេតុ reverse-proxy, ប្រវត្តិកម្មវិធីរុករក និង telemetry នៅខាងក្រៅ OmniRoute។ ចាត់ទុកវាជាជម្រើសសម្រាប់ភាពឆបគ្នា មិនមែនជារបៀបផ្ទៀងផ្ទាត់លំនាំដើមទេ។

## ថវិកា

```bash
# ទទួលស្ថានភាពថវិកាសម្រាប់ API keys ទាំងអស់
```

> **ចំណាំអំពី Schema** (`setBudgetSchema`)៖ `apiKeyId` គឺចាំបាច់; យ៉ាងហោចណាស់មួយក្នុងចំណោម `dailyLimitUsd`, `weeklyLimitUsd`, ឬ `monthlyLimitUsd` ត្រូវតែធំជាងសូន្យ។ វាលស្រេចចិត្ត៖ `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`)។ ទម្រង់ចាស់ `{keyId, limit, period}` នឹងត្រឡប់ `400 Bad Request`។

## ដែនកំណត់ Token

ថវិកា **token** តាម API key នីមួយៗ (ខុសពីថវិកាផ្អែកលើ USD ខាងលើ)។ ត្រូវបានអនុវត្ត inline នៅលើផ្លូវសំណើ៖ នៅពេលការប្រើប្រាស់ក្នុង window បច្ចុប្បន្នរបស់ key ឈានដល់ដែនកំណត់ សំណើនឹងត្រូវបដិសេធដោយ `429 Too Many Requests`។ ដែនកំណត់អាចកំណត់ជាក់លាក់ទៅ `model` មួយ `provider` មួយ ឬអនុវត្តជា `global` ទូទាំង key។ នៅពេលមានដែនកំណត់ជាច្រើនត្រូវនឹងសំណើ នោះដែនកំណត់ដែលតឹងរ៉ឹងជាងគេនឹងត្រូវអនុវត្ត។

```bash
# រាយបញ្ជីដែនកំណត់ token របស់ key (រួមមានការប្រើប្រាស់ក្នុង window បច្ចុប្បន្ន)
GET /api/usage/token-limits?apiKeyId=key-123

# បង្កើត ឬធ្វើបច្ចុប្បន្នភាពដែនកំណត់ token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# លុបដែនកំណត់ token តាម id
DELETE /api/usage/token-limits?id=tl-abc
```

> **កំណត់ចំណាំអំពី Schema** (`setTokenLimitSchema`): `apiKeyId` និង `scopeType` (`model` | `provider` | `global`) គឺជាតម្លៃចាំបាច់។ `scopeValue` គឺចាំបាច់ លុះត្រាតែ `scopeType` ជា `global` (ឧ. model id សម្រាប់ scope `model` និង provider id សម្រាប់ scope `provider`)។ `tokenLimit` ត្រូវតែជាចំនួនគត់វិជ្ជមាន (បម្លែងពី string)។ ជម្រើស៖ `id` (លុបចោលដើម្បីបង្កើត និងផ្តល់តម្លៃដើម្បីធ្វើបច្ចុប្បន្នភាព), `resetInterval` (`daily` | `weekly` | `monthly`, លំនាំដើម `monthly`), `resetTime` (`HH:MM`), `enabled` (លំនាំដើម `true`)។ ការឆ្លើយតបរបស់ `GET` នឹងបន្ថែម `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` និង `nextResetAt` ទៅក្នុងដែនកំណត់នីមួយៗ។ នេះគឺជា endpoint ប្រភេទគ្រប់គ្រង (ការផ្ទៀងផ្ទាត់សិទ្ធិត្រូវបានអនុវត្តជាស្នូលដោយ authz pipeline)។

## ដំណើរការសំណើ

1. Client ផ្ញើសំណើទៅ `/v1/*`
2. Route handler ហៅ `handleChat`, `handleEmbedding`, `handleAudioTranscription` ឬ `handleImageGeneration`
3. Model ត្រូវបានដោះស្រាយ (provider/model ផ្ទាល់ ឬ alias/combo)
4. Credentials ត្រូវបានជ្រើសពី local DB ដោយមានការត្រងតាមភាពអាចប្រើបានរបស់ account
5. សម្រាប់ chat៖ `handleChatCore` ពិនិត្យ semantic/signature cache និងដោះស្រាយការកំណត់ការបង្ហាប់របស់ combo
6. ការបង្ហាប់ជាមុនដំណើរការមុនពេលបកប្រែទៅ provider នៅពេលបានបើក (`lite`, Caveman, RTK ឬ stacked)
7. Provider executor ផ្ញើសំណើ upstream
8. ការឆ្លើយតបត្រូវបានបកប្រែត្រឡប់ទៅទម្រង់របស់ client (chat) ឬត្រឡប់ដូចដើម (embeddings/images/audio)
9. Usage, compression analytics និង request logs ត្រូវបានកត់ត្រា
10. Fallback ត្រូវបានអនុវត្តនៅពេលមានកំហុស ស្របតាមច្បាប់របស់ combo

ឯកសារយោងស្ថាបត្យកម្មពេញលេញ៖ [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## ពិធីការភ្នាក់ងារ

ភារកិច្ចភ្នាក់ងារ Cloud (Claude Code, Codex Cloud, OpenHands ជាដើម) ដែលត្រូវបានប្រតិបត្តិពីចម្ងាយក្នុងនាមអ្នកប្រើប្រាស់ OmniRoute។

| Method | Path                          | Description                                                                                                                                               |
| ------ | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/agents/tasks`        | រាយបញ្ជីភារកិច្ច — អាចប្រើ `?provider=`, `?status=`, `?limit=` (1–500, លំនាំដើម 50)                                                                       |
| POST   | `/api/v1/agents/tasks`        | បង្កើតភារកិច្ច — body ត្រូវបានផ្ទៀងផ្ទាត់ដោយ `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`)។ ត្រឡប់ `201` ជាមួយស្រោមភារកិច្ច |
| DELETE | `/api/v1/agents/tasks?id=...` | លុបភារកិច្ច                                                                                                                                               |

## ភាពធន់ (ពង្រីក)

OmniRoute បង្ហាញយន្តការបរាជ័យបណ្តោះអាសន្នឯករាជ្យចំនួនបី; endpoint គ្រប់គ្រងខាងក្រោមអនុញ្ញាតឱ្យប្រតិបត្តិករអាន និងបដិសេធតម្លៃរបស់វា៖

| វិសាលភាព                     | ការផ្ទុកស្ថានភាព                                 | អាន                                       | កំណត់ឡើងវិញ / សម្អាត                                             |
| ---------------------------- | ------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------------- |
| ឧបករណ៍បំបែករបស់អ្នកផ្តល់សេវា | `domain_circuit_breakers` + ក្នុងអង្គចងចាំ       | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                     |
| រយៈពេលរង់ចាំការតភ្ជាប់       | `rateLimitedUntil` លើការតភ្ជាប់របស់អ្នកផ្តល់សេវា | `/api/rate-limits`, `/api/providers/[id]` | (បើកដំណើរការឡើងវិញដោយពន្យារ; សម្អាតតាមរយៈ PUT របស់អ្នកផ្តល់សេវា) |
| ការចាក់សោម៉ូដែល              | បញ្ជីឈ្មោះភាពមានម៉ូដែលក្នុងអង្គចងចាំ             | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                         |

`PATCH /api/resilience` ទទួលយកការបដិសេធតម្លៃរបស់ឧបករណ៍បំបែកអ្នកផ្តល់សេវា តាមរយៈ `providerBreaker.oauth` និង `providerBreaker.apikey`។ ប្រវត្តិរូបនីមួយៗគាំទ្រ `degradationThreshold`, `failureThreshold`, និង `resetTimeoutMs`; វាលដូចគ្នានេះត្រូវបានបង្ហាញនៅក្នុង ផ្ទាំងគ្រប់គ្រង → ការកំណត់ → ភាពធន់។

```bash
# សម្អាតការចាក់សោម៉ូដែលតែមួយ
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# លុបការចាក់សោទាំងអស់
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

សម្រាប់ឯកសារយោងគំនិតពេញលេញ និងតម្លៃលំនាំដើមរបស់ឧបករណ៍បំបែក៖ សូមមើល [`CLAUDE.md`](../../CLAUDE.md) → "ស្ថានភាពពេលដំណើរការនៃភាពធន់" និង [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)។

### ជួររង់ចាំកំណត់អត្រា និងបណ្តាញសុវត្ថិភាពបើកដំណើរការដោយស្វ័យប្រវត្តិ

- **ផ្លូវសរសេរដែលបានគាំទ្រ**៖ `POST /api/rate-limits` ជាមួយតួ `{"connectionId": "<id>", "enabled": true|false}` គឺជា endpoint គ្រប់គ្រងដែលបានគាំទ្រ សម្រាប់បិទ/បើកការការពារកំណត់អត្រាសម្រាប់ការតភ្ជាប់។ `PUT /api/providers/[id]` មិនកែប្រែ ឬបិទ/បើក `rateLimitProtection` ដោយចេតនា (#11278)។
- **អត្ថន័យនៃ `enabled: false`**៖ ការកំណត់ `enabled: false` នឹងដកការការពារជាក់លាក់សម្រាប់ការតភ្ជាប់ ប៉ុន្តែ **មិន** ដកការតភ្ជាប់ API-key ដែលសកម្មចេញពីបណ្តាញសុវត្ថិភាពបើកដំណើរការដោយស្វ័យប្រវត្តិសកល (`autoEnableApiKeyProviders = true`) ទេ។ នៅក្នុង `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) តម្លៃ `false` និង `undefined` មានអត្ថន័យស្មើគ្នា; ការតភ្ជាប់ API-key ដែលសកម្ម និងគ្មានការការពារជាក់លាក់ នឹងនៅតែត្រូវបានការពារក្រោមបណ្តាញសុវត្ថិភាពបើកដំណើរការដោយស្វ័យប្រវត្តិ។
- **បិទជាសកល**៖ ដើម្បីដំណើរការការតភ្ជាប់ API-key ដោយគ្មានជួររង់ចាំកំណត់អត្រា សូមបិទបណ្តាញសុវត្ថិភាពជាសកលតាមរយៈ `RATE_LIMIT_AUTO_ENABLE=false` (env) ឬ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (ការកំណត់ → ភាពធន់ / `PATCH /api/resilience`)។

## ម៉ាស៊ីនមេ A2A

OmniRoute បង្ហាញ endpoint JSON-RPC 2.0 របស់ A2A (Agent-to-Agent) ព្រមទាំង REST wrapper សម្រាប់ការត្រួតពិនិត្យ/ប្រើប្រាស់ dashboard។

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # ជាជម្រើស លុះត្រាតែបានកំណត់ OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

វិធីសាស្ត្រដែលគាំទ្រ (ទាំងអស់ត្រូវបានគ្រប់គ្រងដោយ `settings.a2aEnabled`)៖

| Method           | Description                                                    |
| ---------------- | -------------------------------------------------------------- |
| `message/send`   | ប្រតិបត្តិជំនាញសមកាលកម្ម; ត្រឡប់ `{task, artifacts, metadata}` |
| `message/stream` | ប្រតិបត្តិ SSE ជាបន្តបន្ទាប់សម្រាប់សំណុំជំនាញដូចគ្នា           |
| `tasks/get`      | ទាញយក task តាម `taskId`                                        |
| `tasks/cancel`   | បោះបង់ task តាម `taskId`                                       |

ជំនាញដែលមានស្រាប់៖ `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`។

### Agent Card

```bash
GET /.well-known/agent.json
```

ត្រឡប់កាតភ្នាក់ងារ A2A សាធារណៈ (ឈ្មោះ ការពិពណ៌នា សមត្ថភាព កាតាឡុកជំនាញ និងគ្រោងការផ្ទៀងផ្ទាត់) — ត្រូវបានរក្សាទុកក្នុង cache ជាសាធារណៈរយៈពេល 1h។ មិនត្រូវការការផ្ទៀងផ្ទាត់ទេ។

### ជំនួយ REST

| Method | Path                         | Description                                                                                                        |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/a2a/status`            | ស្ថានភាព A2A ថាតើបានបើកឬអត់ + ស្ថិតិ task + សេចក្ដីសង្ខេបកាតភ្នាក់ងារដែលបានរក្សាទុកក្នុង cache                     |
| GET    | `/api/a2a/tasks`             | រាយបញ្ជី task — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (មិនទាន់អនុវត្តជាជំនួយ REST — បង្កើតតាម JSON-RPC `message/send`)                                                   |
| GET    | `/api/a2a/tasks/[id]`        | ទាញយក task មួយ                                                                                                     |
| POST   | `/api/a2a/tasks/[id]/cancel` | បោះបង់ task                                                                                                        |

**ការផ្ទៀងផ្ទាត់:** ជំនួយ REST ដំណើរការដោយគ្មានការផ្ទៀងផ្ទាត់ការគ្រប់គ្រង (អាចអានបានតាម dashboard)។ រីឯ route JSON-RPC `/a2a` ប្រើ Bearer `OMNIROUTE_API_KEY` ប្រសិនបើបានកំណត់។

## ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ

សូមមើល [ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រង](../guides/MANAGEMENT-AUTH.md) សម្រាប់ក្រុមព័ត៌មានសម្ងាត់ទាំងបួន (សម័យ dashboard, សញ្ញាសម្គាល់ CLI មូលដ្ឋាន, Access Token `oma_live_…`, សោ API ដែលមានវិសាលភាព manage) និងភាពខុសគ្នារបស់ពួកវាពីសោ inference។

- ផ្លូវ Dashboard (`/dashboard/*`) ប្រើខូគី `auth_token`
- ការចូលប្រើពាក្យសម្ងាត់ដែលបានរក្សាទុកជាហាស; ប្រើ `INITIAL_PASSWORD` ជាជម្រើសបម្រុង
- ការបិទ/បើក `requireLogin` តាម `/api/settings/require-login`
- ផ្លូវ `/v1/*` អាចតម្រូវឱ្យមាន Bearer API key នៅពេល `REQUIRE_API_KEY=true`
- "management token" / "management-scoped API key" នៅក្នុងឯកសារយោងនេះ មានន័យថា ជាមួយក្នុងចំណោមក្រុមព័ត៌មានសម្ងាត់ក្នុងមគ្គុទ្ទេសក៍នោះ — មិនមែនជាប្រភេទសោសម្ងាត់បន្ថែមដែលមិនបានកំណត់នោះទេ

> **ការផ្លាស់ប្តូរដែលអាចបំបែកភាពឆបគ្នា (v3.8.0)** — `/api/v1/agents/tasks/*` និង endpoint គ្រប់គ្រង cooldown ឥឡូវនេះតម្រូវឱ្យមាន **ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រង** (ខូគី `auth_token` របស់ dashboard ឬ management-scoped API key)។ Client ដែលពីមុនបានហៅផ្លូវទាំងនេះដោយមិនមានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ នឹងទទួលបាន `401 Unauthorized`។ សូមមើល commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`)។
