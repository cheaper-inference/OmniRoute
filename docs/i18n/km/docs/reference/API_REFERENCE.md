## ការបំពេញការជជែក

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Header ផ្ទាល់ខ្លួន

| Header                   | ទិសដៅ      | សេចក្ដីពិពណ៌នា                                                                                                                                                                                                        |
| ------------------------ | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | សំណើ       | កំណត់ជា `true` ដើម្បីរំលងឃ្លាំងសម្ងាត់                                                                                                                                                                                |
| `x-omniroute-no-memory`  | សំណើ       | កំណត់ជា `true` ដើម្បីរំលងការបញ្ចូលអង្គចងចាំ + ជំនាញសម្រាប់សំណើនេះ (ដូចគ្នានឹងការមិនប្រើឃ្លាំងសម្ងាត់ ហើយជៀសវាងការចំណាយ token/ថ្លៃសេវាក្នុងការហៅនីមួយៗ)                                                                |
| `X-OmniRoute-Progress`   | សំណើ       | កំណត់ជា `true` សម្រាប់ព្រឹត្តិការណ៍វឌ្ឍនភាព                                                                                                                                                                           |
| `X-Session-Id`           | សំណើ       | សោសម័យអចិន្ត្រៃយ៍សម្រាប់ភាពជាប់ទាក់ទងនៃសម័យខាងក្រៅ                                                                                                                                                                    |
| `x_session_id`           | សំណើ       | ទម្រង់ដែលប្រើសញ្ញាគូសក្រោមក៏ត្រូវបានទទួលយកផងដែរ (HTTP ផ្ទាល់)                                                                                                                                                         |
| `X-OmniRoute-Session-Id` | សំណើ       | ស្លាកសម័យ/ការសន្ទនាដែលផ្តល់ដោយអ្នកហៅ (ក៏បញ្ចូលទៅក្នុងអង្គចងចាំផងដែរ)។ នៅពេលមាន វាត្រូវបានរក្សាទុកដូចដើមទៅក្នុង `call_logs.session_tag` សម្រាប់ការកំណត់ថ្លៃចំណាយតាមសម័យ (#8249) — មិនត្រូវបានបង្កើតឡើងឡើយនៅពេលអវត្តមាន |
| `Idempotency-Key`        | សំណើ       | សោលុបធាតុស្ទួន (ចន្លោះពេល 5 វិនាទី)                                                                                                                                                                                   |
| `X-Request-Id`           | សំណើ       | សោជំនួសសម្រាប់លុបធាតុស្ទួន                                                                                                                                                                                            |
| `x-omniroute-connection` | សំណើ       | ភ្ជាប់សំណើម៉ូដែលតែមួយទៅកាន់ការតភ្ជាប់របស់អ្នកផ្តល់សេវាមួយ (គណនី) តាម id របស់វា — សូមមើល [ការភ្ជាប់គណនីសម្រាប់សំណើនីមួយៗ](#account-pinning-per-request)                                                                |
| `X-OmniRoute-Cache`      | ការឆ្លើយតប | `HIT` ឬ `MISS` (មិនមែនស្ទ្រីម)                                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | ការឆ្លើយតប | `true` ប្រសិនបើត្រូវបានលុបស្ទួន                                                                                                                                                                                       |
| `X-OmniRoute-Progress`   | ការឆ្លើយតប | `enabled` ប្រសិនបើការតាមដានវឌ្ឍនភាពត្រូវបានបើក                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | ការឆ្លើយតប | ID សម័យជាក់ស្តែងដែល OmniRoute បានប្រើ                                                                                                                                                                                 |
| `X-OmniRoute-Request-Id` | ការឆ្លើយតប | id សម្រាប់ផ្គូផ្គងសំណើ (នៅពេលស្គាល់)                                                                                                                                                                                  |
| `X-OmniRoute-Version`    | ការឆ្លើយតប | កំណែ build របស់ OmniRoute (មានជានិច្ច)                                                                                                                                                                                |
| `X-OmniRoute-Cost-Saved` | ការឆ្លើយតប | ចំនួន USD ដែលឃ្លាំងសម្ងាត់បានជួយសន្សំលើ `HIT` (សម្រាប់តែ cache hit ប៉ុណ្ណោះ)                                                                                                                                          |
| `X-OmniRoute-Decision`   | ការឆ្លើយតប | ដានការកំណត់ផ្លូវ៖ `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` គឺជាយុទ្ធសាស្ត្រ combo ឬ `single` សម្រាប់សំណើដែលមិនមែនជា combo) — មានជានិច្ចនៅក្នុងការឆ្លើយតបពេលបញ្ចប់                                |

> ចំណាំអំពី Nginx៖ ប្រសិនបើអ្នកពឹងផ្អែកលើ header ដែលមានសញ្ញាគូសក្រោម (ឧទាហរណ៍ `x_session_id`) សូមបើក `underscores_in_headers on;`។

#### ការចងគណនីសម្រាប់សំណើនីមួយៗ

នៅពេល provider មួយមាន connection ច្រើន (គណនី ឬ key) ជាធម្មតា OmniRoute ជ្រើសរើសមួយ
តាមយុទ្ធសាស្ត្រជ្រើសរើសគណនីរបស់វា។ ផ្ទុយទៅវិញ សំណើមួយអាចចងទៅនឹង connection ជាក់លាក់មួយ
ដោយប្រើ header `x-omniroute-connection`៖

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **កន្លែងស្វែងរក id។** បើកទំព័រ provider ក្នុង dashboard
  (**Dashboard → Providers → <provider>**) ហើយចុច chip id `xxxxxxxx…` នៅលើជួរ connection
  — វានឹងចម្លង connection id ពេញលេញ។
- **សំណើណាខ្លះដែលគោរពវា។** សំណើម៉ូដែលតែមួយ (`provider/model`) នៅលើ
  `/v1/chat/completions`, `/v1/messages` និង `/v1/responses`។ Combo មិនអើពើ header នេះទេ៖ សូមចង
  គណនីសម្រាប់ជំហាន combo នីមួយៗ តាមរយៈ connection ផ្ទាល់របស់ជំហាននោះជំនួសវិញ។
- **ការចងនេះតឹងរ៉ឹង មិនមែនគ្រាន់តែជាចំណូលចិត្តទេ។** មានតែ connection ដែលបានចងប៉ុណ្ណោះដែលត្រូវបានប្រើ។ ការ
  បរាជ័យនៅក្នុងសំណើនឹងកត់ត្រារយៈពេល cooldown របស់គណនី ប៉ុន្តែ **មិន** ប្ដូរទៅ
  គណនីផ្សេងទៀតរបស់ provider ដូចគ្នាទេ។
- **Cooldown និង quota នឹងដោះការចងនេះ។** ខណៈពេល connection ដែលបានចងកំពុងស្ថិតក្នុង cooldown,
  អស់ quota ឬត្រូវបានទប់ស្កាត់ដោយគោលការណ៍ quota សំណើបន្ទាប់នឹងប្ដូរទៅប្រើ connection
  ផ្សេងទៀតរបស់ provider ដូចគ្នានឹង traffic ដែលមិនបានចង។
- **id ដែលមិនស្គាល់ ឬត្រូវបានបិទនឹងបរាជ័យ។** id ដែលមិនស្ថិតក្នុង pool សកម្មរបស់ provider (ត្រូវបានលុប,
  បិទដំណើរការ ឬជាកម្មសិទ្ធិរបស់ provider ផ្សេង) នឹងធ្វើឱ្យគ្មានគណនីដែលមានសិទ្ធិប្រើប្រាស់ ដូច្នេះសំណើ
  នឹងបរាជ័យ ជំនួសឱ្យការបញ្ជូនទៅកន្លែងផ្សេងដោយស្ងាត់ៗ។

Claude Code ផ្ញើ header ផ្ទាល់ខ្លួនតាមរយៈ `ANTHROPIC_CUSTOM_HEADERS`។ ដាក់វានៅក្នុង block `env`
នៃ `~/.claude/settings.json` ឬនៅក្នុង `.claude/settings.json` កម្រិត project ដើម្បីចងគណនីផ្សេងគ្នា
សម្រាប់ project នីមួយៗ៖

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },

```

ប្រភព៖ `src/sse/handlers/chat.ts` (ការអាន header), `src/sse/services/auth.ts` និង
`src/sse/services/sessionAffinityPin.ts` (ការដោះការចង និងការត្រួតពិនិត្យថាមិនមានក្នុង pool)។

> **Header ទិន្នន័យតេឡេមេទ្រីអំពីថ្លៃចំណាយ៖** response ជោគជ័យដែលមិនមែនជា streaming ក៏មានសំណុំទិន្នន័យតេឡេមេទ្រីអំពីថ្លៃចំណាយ `X-OmniRoute-*` ផងដែរ — `X-OmniRoute-Response-Cost` (USD មានទសភាគថេរ 10 ខ្ទង់; `0.0000000000` សម្រាប់ការប្រើប្រាស់ឥតគិតថ្លៃ/គ្មានតម្លៃកំណត់), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` និង `X-OmniRoute-Fallback-Attempts` (មានតែនៅពេល > 0) ព្រមទាំង `X-OmniRoute-Request-Id` និង `X-OmniRoute-Version`។ Header ទាំងនេះត្រូវបានបញ្ចេញដោយ chat completions, `/v1/responses`, `/v1/messages` និង **media endpoint ផងដែរ** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` និង `/v1/moderations` (ថ្លៃចំណាយតែងតែជា `0`)។ ថ្លៃចំណាយ media ត្រូវបានគណនាតាម modality នីមួយៗ (តាមរូបភាព តាមវិនាទី តាមតួអក្សរ តាមឯកតាស្វែងរក) នៅពេលមានព័ត៌មានតម្លៃ បើមិនដូច្នោះទេគឺ `0` (អនុញ្ញាតឱ្យបន្តដំណើរការនៅពេលបរាជ័យ)។

> **អត្ថន័យថ្លៃចំណាយពេល cache hit៖** នៅពេល semantic cache HIT (`X-OmniRoute-Cache-Hit: true`) គ្មានការហៅទៅ upstream ទេ ដូច្នេះ `X-OmniRoute-Response-Cost` គឺ `0.0000000000` (ថ្លៃចំណាយ **បន្ថែម** សម្រាប់ការផ្ដល់លទ្ធផល hit នោះ)។ ថ្លៃចំណាយដើម/ដែលនឹងត្រូវចំណាយ ត្រូវបានរាយការណ៍ដាច់ដោយឡែកក្នុង `X-OmniRoute-Cost-Saved`។ ប្រព័ន្ធប្រើប្រាស់ទិន្នន័យ billing គួរបូកសរុប `X-OmniRoute-Response-Cost` (hit មិនមានថ្លៃចំណាយទេ) ខណៈដែលការវិភាគ cache អាចបូកសរុប `X-OmniRoute-Cost-Saved`។

## ការជួលសម័យដែលបានគ្រប់គ្រងផ្តាច់មុខ

ការជួលសម័យដែលបានគ្រប់គ្រងផ្តាច់មុខ គឺជាកិច្ចសន្យាកំណត់ផ្លូវដែលអាចជ្រើសរើសប្រើ និងមិនអាស្រ័យលើកម្មវិធីអតិថិជន៖ ម្ចាស់សកម្មមួយ
កាន់កាប់ការតភ្ជាប់ OmniRoute មួយដែលមានសិទ្ធិ។ វាមិនជួលម៉ូដែល មិនទាមទារ OAuth មិនកំណត់អត្តសញ្ញាណ
កម្មវិធីអតិថិជនជាក់លាក់ណាមួយ និងមិនទាមទារអ្នកផ្តល់សេវាជាក់លាក់ណាមួយឡើយ។

API key ដែលប្រើសម្រាប់ផ្ទៀងផ្ទាត់ត្រូវតែមានវិសាលភាព `lease:exclusive` និងបញ្ជី
`allowedConnections` ដែលមិនទទេ និងបានកំណត់យ៉ាងច្បាស់។ ព្រំដែនបម្លែងទិន្នន័យក្នុងមូលដ្ឋានទិន្នន័យអនុវត្តលក្ខខណ្ឌទាំងពីររួមគ្នា នៅពេលបង្កើត key
និងធ្វើបច្ចុប្បន្នភាពដោយផ្នែក។

ការតភ្ជាប់ដែលបានកំណត់រចនាសម្ព័ន្ធ និងកាត់ដកចន្លោះជុំវិញប៉ុណ្ណោះ។ វាជា `null` នៅពេលមិនមានឈ្មោះដែលបានកំណត់រចនាសម្ព័ន្ធប្រកបដោយសុវត្ថិភាព។ OmniRoute មិនដែលជំនួសវាដោយ

### `x-omniroute-compression`

ការកំណត់ជំនួសផែនការបង្ហាប់សម្រាប់សំណើនីមួយៗ។ មានអាទិភាពខ្ពស់បំផុត — ឈ្នះលើការកំណត់ជំនួស routing-combo
profile សកម្ម auto-trigger និង Default របស់ផ្ទាំង។ តម្លៃ៖

| តម្លៃ         | ប្រសិទ្ធភាព                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| `off`         | មិនមានការបង្ហាប់សម្រាប់សំណើនេះទេ។                                                                       |
| `default`     | profile Default ដែលកំណត់ដោយផ្ទាំង (មិនអើពើ profile សកម្ម)។ ម៉ាស៊ីនបង្ហាប់ដែលបាត់បង់ទិន្នន័យត្រូវបានបិទ។ |
| `safe`        | មានតែការលុបធាតុស្ទួន និងការបង្រួមចន្លោះទទេប៉ុណ្ណោះ។                                                     |
| `allow-lossy` | រក្សាផែនការរបស់ប្រតិបត្តិករសម្រាប់សំណើនេះ រួមទាំងសេចក្តីសង្ខេប និងការសរសេររចនាប័ទ្មឡើងវិញ។              |
| `engine:<id>` | ម៉ាស៊ីនតែមួយនៅពេលបានបើក ឧ. `engine:rtk`។ ការជ្រើសរើសប្រើម៉ាស៊ីននោះសម្រាប់សំណើនីមួយៗ។                    |
| `<combo>`     | combo ដែលមានឈ្មោះ ដោយផ្គូផ្គងតាមឈ្មោះជាមុន (មិនប្រកាន់តួអក្សរធំតូច) បន្ទាប់មកតាម id។                    |

ចំណាំ៖

- តម្លៃដែលមិនស្គាល់ត្រូវបានមិនអើពើ (សំណើមិនត្រូវបានបដិសេធឡើយ)។ ការដោះស្រាយនឹងបន្តទៅតាមលំដាប់អាទិភាពធម្មតារបស់ប្រតិបត្តិករ។
- ប្រសិនបើ combo ច្រើនមានឈ្មោះដូចគ្នា សូមផ្តល់ **id** របស់ combo ដើម្បីទទួលបានការផ្គូផ្គងដែលកំណត់ច្បាស់លាស់។
- combo ដែលមានឈ្មោះជា `off` ឬ `default` មិនអាចជ្រើសរើសតាមឈ្មោះបានទេ (ពាក្យគន្លឹះទាំងនោះត្រូវបានបកស្រាយជាមុន)។ សូមយោងទៅ combo បែបនេះតាម id របស់វា។
- master compression switch គឺជារបាំងដាច់ខាត៖ នៅពេលការបង្ហាប់ត្រូវបានបិទជាសកល header នេះមិនអាចបើកវាបានទេ។

ផែនការដែលបានអនុវត្តត្រូវបានផ្ញើត្រឡប់ក្នុង response header៖

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ដែល `<source>` គឺជាតម្លៃមួយក្នុងចំណោម `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ឬ `off`។

## ការបង្កើតរូបភាព

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

អ្នកផ្តល់សេវាដែលអាចប្រើបានរួមមាន OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (មូលដ្ឋាន), ComfyUI (មូលដ្ឋាន)។

`n` ត្រឡប់រូបភាពចំនួន `n` នៅក្នុង `data[]`។ សម្រាប់អ្នកផ្តល់សេវាដែល upstream API របស់ពួកគេត្រឡប់រូបភាពមួយក្នុងមួយការហៅ
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) នឹងមានការហៅ upstream ដាច់ដោយឡែកចំនួន `n` ដោយដំណើរការក្នុងពេលតែមួយមិនលើសពី 4។ តម្លៃ

ទម្រង់ fan-out គឺ `SINGLE_IMAGE_FANOUT_FORMATS` នៅក្នុង
`open-sse/handlers/imageGeneration/fanOut.ts`។

## OCR ឯកសារ

```bash

Authorization: Bearer your-api-key

  "document": {
    "type": "document_url",
```

### លំហូរ poll របស់ Azure Document Intelligence

(`open-sse/handlers/ocr.ts`) ធ្វើ poll URL នោះរៀងរាល់មួយវិនាទី រហូតដល់ 30 ដង ហើយបរាជ័យភ្លាមៗ (មិន
បន្តធ្វើ poll) នៅពេលការឆ្លើយតប poll មិនមែនជា `ok` ឬមានស្ថានភាព `"failed"` ហើយត្រឡប់ `504` ប្រសិនបើ

### តម្លៃម៉ូដែល (`pricing`)

### តម្រងស្វែងរក (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

នឹងមិនផ្លាស់ប្តូរ។ តម្រងទាំងនេះបង្រួមកាតាឡុកដែលអ្នកហៅអាចមើលឃើញរួចហើយ (សិទ្ធិ API-key ត្រូវបានអនុវត្តមុន)

```bash
GET /v1/models?kind=embedding                              # `type` របស់កាតាឡុក; ជួរដែលគ្មានវាត្រូវបានចាត់ទុកជា `chat`
GET /v1/models?q=sonnet&limit=10                           # ផ្គូផ្គងលើ id ឬឈ្មោះ ដោយមិនប្រកាន់អក្សរធំតូច
```

### បញ្ជីសម្រាំងម៉ូដែល (`POST /v1/models/query`)

`POST /v1/models/query` ត្រឡប់បញ្ជីខ្លីដែលមានលទ្ធផលកំណត់ច្បាស់ពីកាតាឡុកដូចគ្នា ដោយមាន
ការផ្ទៀងផ្ទាត់ និងលទ្ធភាពមើលឃើញតាម key ដូចគ្នានឹង `GET /v1/models`៖

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

គ្រប់វាលទាំងអស់គឺជាជម្រើស។ `capabilities` និង `exclude` ទទួលយក array ឬ string ដែលបំបែកដោយសញ្ញាក្បៀស;
`max_output` ប្រៀបធៀបជាមួយ `max_output_tokens`។ លទ្ធផលត្រូវបានតម្រៀបតាម `owned_by` បន្ទាប់មកតាម `id`។
តម្លៃលំនាំដើមរបស់ `limit` គឺ `20` ហើយតម្លៃលើសពី `100` ត្រូវបានកំណត់ត្រឹម `100`។ JSON មិនត្រឹមត្រូវ វាលដែល
មិនស្គាល់ ឬតម្លៃមិនត្រឹមត្រូវ នឹងត្រឡប់ HTTP `400`។

### ម៉ូដែល chat ដែលត្រូវបានលាក់ដាច់ដោយឡែក

ម៉ូដែលដែលត្រូវបានសម្គាល់ថា **លាក់** នៅលើទំព័រ provider របស់វា នឹងត្រូវដកចេញពីកាតាឡុក និងត្រូវបានបដិសេធ
ដោយ HTTP `404` / `model_not_found` នៅពេលស្នើសុំដោយផ្ទាល់។ ការត្រួតពិនិត្យប្រើ provider និងម៉ូដែលដែលបាន resolve
រួមទាំង alias របស់ provider, បុព្វបទ node របស់ compatible-provider និងតម្លៃលំនាំដើមនៃ
connection។ combo មួយនឹងរំលង target ដែលត្រូវបានលាក់ ហើយអាចប្រើ target ដែលមើលឃើញផ្សេងទៀត; នៅពេលគ្មាន
target ដែលអាចប្រតិបត្តិបាននៅសល់ វានឹងត្រឡប់លេខកូដកំហុសដូចគ្នា។ ការឈប់លាក់នឹងមានប្រសិទ្ធភាពនៅសំណើ
បន្ទាប់។ ការកំណត់ជាន់លើលទ្ធភាពមើលឃើញសម្រាប់តែ image មិនលាក់ម៉ូដែល chat ដែលមាន ID ដូចគ្នាទេ។

ការកំណត់ម៉ូដែលដាច់ដោយឡែកនេះ គឺខុសពី
[បញ្ជីអនុញ្ញាត/បដិសេធការបង្ហាញម៉ូដែល](../routing/MODEL_EXPOSURE_LIST.md) ដែលច្រោះការផ្សព្វផ្សាយក្នុងកាតាឡុក

## ការបង្កើតអូឌីយ៉ូដោយ ElevenLabs

កំណត់រចនាសម្ព័ន្ធ connection របស់ provider `elevenlabs` នៅក្នុង OmniRoute ដោយប្រើ ElevenLabs API key របស់អ្នក។
Client ធ្វើ authentication ដោយប្រើ key របស់ **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gateway នឹងផ្ដល់ provider key ដែលបានរក្សាទុកជា `xi-api-key`។ កុំផ្ញើ ElevenLabs key
ជា bearer token របស់ gateway ឡើយ។

| វិធីសាស្ត្រ | Path                        | Response                                 | ប្រភេទ endpoint របស់ API key |
| ----------- | --------------------------- | ---------------------------------------- | ---------------------------- |
| POST        | `/v1/sound-generation`      | បៃអូឌីយ៉ូដើម                             | `elevenlabs`                 |
| POST        | `/v1/music`                 | បៃអូឌីយ៉ូដើម                             | `music`                      |
| POST        | `/v1/music/stream`          | បៃអូឌីយ៉ូបែប streaming                   | `music`                      |
| POST        | `/v1/music/detailed`        | អូឌីយ៉ូ multipart ដើម និងផែនការតែងនិពន្ធ | `music`                      |
| POST        | `/v1/music/detailed/stream` | metadata SSE ដើម និងបំណែកអូឌីយ៉ូ         | `music`                      |
| POST        | `/v1/music/plan`            | ផែនការតែងនិពន្ធជា JSON                   | `music`                      |

Endpoint ទាំងនេះបំពេញបន្ថែមទៅលើ route `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` និង `/v1/speech-to-text` ដែលមានស្រាប់។ Field របស់ JSON ដើម
និង query parameter ដូចជា `output_format` និង `enable_logging` ត្រូវបានរក្សាទុកដដែល។
Response របស់ `/v1/music/detailed` រក្សា multipart boundary របស់វា; សូម parse ពួកវាជា multipart។
`/v1/music/detailed/stream` ត្រឡប់ `text/event-stream` ដែលមាន metadata នៃការតែងនិពន្ធ និង
បំណែកអូឌីយ៉ូ base64 នៅក្នុង event របស់ SSE។ Route ទាំងប្រាំមួយគាំទ្រ CORS preflight។

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# បែបផែនសំឡេងខ្លីមួយ។ រយៈពេល៖ 0.5 ដល់ 30 វិនាទី។
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# រយៈពេលតន្ត្រីត្រូវបានបង្ហាញជា millisecond៖ 3000 ដល់ 600000។
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ប្រើ `/v1/music/stream` ជាមួយ JSON body ដូចគ្នា ដើម្បីបញ្ជូនអូឌីយ៉ូជាបន្តបន្ទាប់។ ការតែងនិពន្ធ
ទទួលយកតែមួយគត់ក្នុងចំណោម `prompt` ឬ `composition_plan`; `/v1/music/plan` ទាមទារ `prompt`
ហើយអាចទទួលយក `source_composition_plan` ជាជម្រើស។ Schema ដើមរក្សាទុក
field បន្ថែមរបស់ provider ដើម្បីឱ្យ version របស់ composition plan និងជម្រើស fine-tuning អាចទៅដល់ ElevenLabs។

Endpoint រួម `/v1/music/generations` ក៏ទទួលយក `elevenlabs/music_v1`,
`elevenlabs/music_v2` និង `elevenlabs/music_v2_5` ផងដែរ។ នៅពេលមាន ElevenLabs connection សកម្ម
model ទាំងនេះនឹងត្រូវបានបង្ហាញក្នុង catalog តន្ត្រី។ Endpoint នេះត្រឡប់
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`។ Field `duration` របស់វាគិតជា
វិនាទី ហើយ map ទៅ `music_length_ms`; `music_length_ms` ដែលបានកំណត់ជាក់លាក់មានអាទិភាព។
`instrumental` map ទៅ `force_instrumental` ដោយ field ដើមមានអាទិភាព។
ប្រើ streaming endpoint ដើមសម្រាប់ streaming និង composition endpoint ដើម
សម្រាប់ request ដែលផ្អែកតែលើ composition plan ប៉ុណ្ណោះ។

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

ការរឹតបន្តឹងតាម endpoint, model, budget និង connection នឹងត្រូវអនុវត្ត មុនពេលធ្វើការហៅទៅ upstream។ Route
ដើមត្រឡប់ status code និង error body របស់ upstream ដោយមិនកែប្រែ រួមទាំង `402` សម្រាប់ការរឹតបន្តឹង
plan និង `429` សម្រាប់ដែនកំណត់ quota។ Header `character-cost`, `song-id`, `request-id` និង `retry-after`
ត្រូវបានរក្សាទុកនៅពេលមាន។ សមតុល្យ credit ឥតគិតថ្លៃមិនធានាការចូលប្រើគ្រប់
music model, output format ឬ API feature ទាំងអស់ទេ៖ ElevenLabs កំណត់សិទ្ធិសម្រាប់ request នីមួយៗ។
Endpoint រួមរក្សាទុក error status code នៅក្នុង error envelope ស្តង់ដាររបស់ OmniRoute។

## Files API

### Exa និង Tavily `provider_options`

Exa និង Tavily អានវាលជាក់លាក់របស់អ្នកផ្តល់សេវាពីកាបូបដាក់ឈ្មោះ៖ `provider_options.exa` (ឬ `provider_options["exa-search"]`) និង `provider_options.tavily` (ឬ `provider_options["tavily-search"]`). មានតែសោខាងក្រោមប៉ុណ្ណោះដែលត្រូវបានបញ្ជូនបន្ត។ នីមួយៗត្រូវបានពិនិត្យទល់នឹងគ្រោងការណ៍ Zod ផ្ទាល់ខ្លួនក្នុង `open-sse/handlers/search/providerOptionsPassthrough.ts` ហើយសោដែលមានប្រភេទខុសត្រូវបានទម្លាក់។ សោណាមួយផ្សេងទៀតមិនត្រូវបានអើពើ រួមទាំង auth, base URL, `stream` និង `outputSchema`។ សោសំប៉ែតដែលប្រើដោយអ្នកផ្តល់សេវាផ្សេងទៀត (`cx`, `depth`, ... ) ដំណើរការដូចពីមុន។

| អ្នកផ្តល់សេវា | វាលកម្រិតកំពូល                                                                                                                                                                                                                                                                                                                                                            | សំបុក                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Exa           | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (បុព្វកាលផ្ទះល្វែង), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` បញ្ចូលគ្នាលើ `{ text: true, highlights: true }` លំនាំដើម |
| តាវីលី        | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                      |

វាលទូទៅតែងតែឈ្នះ៖ `query`, `max_results`, `filters` (ដែន), `country` និងប្រធានបទដែលបានមកពី `search_type`។ នៅលើ Exa, `search_type: "news"` រក្សា `category: "news"`។ Tavily ក៏ទទួលយក `search_type: "finance"` (`topic: "finance"`) ផងដែរ។

ការចំណាយលើការស្វែងរក Firecrawl ត្រូវបានកត់ត្រាក្នុងមួយប្លុកដែលបានចាប់ផ្តើមនៃលទ្ធផល 10 ដែលត្រឡប់មកវិញនៅ $0.002 (2 ក្រេឌីត) ក្នុងមួយប្លុក និងយ៉ាងហោចណាស់មួយប្លុកក្នុងមួយការហៅ ( [ការចេញវិក្កយបត្រ Firecrawl](https://docs.firecrawl.dev/billing) ): 11 លទ្ធផលមានតម្លៃ $0.004 ។

`time_range` ទូទៅឥឡូវនេះទៅដល់អ្នកផ្តល់សេវាទាំងពីរ៖ Exa ទទួលបាន `startPublishedDate` (ISO timestamp) និង Tavily ទទួលបាន `start_date` (`YYYY-MM-DD`)។ កាលបរិច្ឆេទច្បាស់លាស់នៅក្នុង `provider_options` បដិសេធការគូសផែនទី។

លទ្ធផល Exa រក្សា `id`, `highlight_scores`, `summary`, `subpages`, `entities` និង `extras` ក្នុង `provider_raw`។ លទ្ធផល Tavily រក្សា `images` និង `favicon`។

តម្លៃនៃការស្វែងរកតំណភ្ជាប់ត្រូវបានកត់ត្រានៅ $0.005 សម្រាប់ `depth` `fast` និង `standard` និង $0.05 សម្រាប់ `deep` ( [តម្លៃភ្ជាប់](https://docs.linkup.so/pages/documentation/development/pricing) ) ថាតើ `depth` មកពី `provider_options` ឬការកំណត់នៃការតភ្ជាប់។

Exa `type: "lite"` (Exa 3.0) ទទួលយកសំណុំវាលតូចជាង ហើយបដិសេធសំណើទាំងមូលនៅពេលដែលវាលផ្សេងទៀតត្រូវបានកំណត់។ សម្រាប់ lite, `additionalQueries`, `systemPrompt` និងរាល់ `contents` key លើកលែងតែ `text` និង `highlights` ត្រូវបានទម្លាក់មុនពេលហៅ។ `subpages`, `subpageTarget`, `highlights.numSentences` និង `highlights.highlightsPerUrl` ដែលបានបដិសេធមិនត្រូវបានបញ្ជូនបន្តទៀតទេ។

គណនេយ្យតម្លៃគឺជា `costPerQuery` ឈ្មោះផ្ទះល្វែង លើកលែងតែ Exa ដែលធ្វើតាមតម្លៃផ្ទាល់ខ្លួនរបស់ Exa៖ 0.007 ដុល្លារក្នុងមួយការហៅសម្រាប់ `auto` (និង `fast` កេរ្តិ៍ដំណែល) ឬ 0.004 ដុល្លារសម្រាប់ `lite` (និង `instant` កេរ្តិ៍ដំណែល) គ្របដណ្តប់លទ្ធផល 10 ។ $0.001 សម្រាប់លទ្ធផលបន្ថែមនីមួយៗ; និង $0.001 ក្នុងមួយលទ្ធផលត្រឡប់មកវិញនៅពេលដែល `contents.summary` ត្រូវបានកំណត់។ Tavily ត្រូវបានកត់ត្រាក្នុង 1 ក្រេឌីត ($0.008) សម្រាប់ `search_depth` `basic`, `fast` និង `ultra-fast`, និង 2 credits ($0.016) សម្រាប់ `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) )។ ការហៅទូរសព្ទជាមួយ `auto_parameters: true` ដែល Tavily ដំឡើងកំណែទៅកម្រិតខ្ពស់នៅតែត្រូវបានកត់ត្រាក្នុង 1 ក្រេឌីត។

## Web Fetch API

ស្រង់មាតិកាពី URL តាមរយៈអ្នកផ្តល់សេវា web-fetch ដែលបានកំណត់រចនាសម្ព័ន្ធ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)។

Parallel Extract (`parallel-search`, ប្រើ API key ដូចគ្នានឹង Parallel Search) ផ្ដល់តែ Markdown
ប៉ុណ្ណោះ — `format` ផ្សេងទៀតណាមួយនឹងទទួលបាន `400` — ហើយកំណត់មាតិកាអតិបរមាត្រឹម 100,000 តួអក្សរ។ នៅពេល
ទំព័រគោលដៅផ្ទាល់មិនអាចត្រូវបានស្រង់ចេញ អ្នកផ្តល់សេវាខាងលើរាយការណ៍វានៅក្នុង HTTP 200;
OmniRoute បង្ហាញវាជា `422` ជាមួយសារថេរមួយ។

| វិធីសាស្ត្រ | ផ្លូវ           | សេចក្ដីពិពណ៌នា                                                              |
| ----------- | --------------- | --------------------------------------------------------------------------- |
| POST        | `/v1/web/fetch` | ទាញយក/ស្រង់ទិន្នន័យពី URL — តួសំណើត្រូវបានផ្ទៀងផ្ទាត់ដោយ `v1WebFetchSchema` |

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** Bearer API key (`extractApiKey` + `isValidApiKey`)។ គោលការណ៍ត្រូវបានអនុវត្តតាមរយៈ `enforceApiKeyPolicy`។

**ការបម្រុងទុកដែលគិតគូរពីកូតា (#8297):** នៅពេលមិនមានការបញ្ជាក់ `provider` ជាក់លាក់ ក្រុម
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ត្រូវបាន
ពិនិត្យតាមលំដាប់
អាទិភាពថេរ (បំពេញមុន) — អ្នកផ្តល់សេវាដែលបានកំណត់រចនាសម្ព័ន្ធ ប៉ុន្តែត្រូវបានកម្រិតអត្រា នឹងត្រូវបានរំលង
ជំនួសឱ្យការបញ្ឈប់សំណើភ្លាមៗ ហើយកំហុសពីសេវាខាងលើដែលអាចសាកល្បងម្ដងទៀត/ពាក់ព័ន្ធនឹងកូតា
(HTTP 429 ជានិច្ច; 402/403 សម្រាប់កម្រិតឥតគិតថ្លៃបែបកូតារបស់ Firecrawl/Tavily/TinyFish —
មិនអនុវត្តចំពោះ Jina Reader ហើយមិនដែលអនុវត្តចំពោះសំណើមិនត្រឹមត្រូវ 400 ធម្មតា) នឹងបន្តទៅ
អ្នកផ្តល់សេវាបន្ទាប់ដែលមានព័ត៌មានសម្ងាត់ និងមិនទាន់បានសាកល្បង នៅពេលសំណើដំណើរការ។ នៅពេលអ្នកផ្តល់សេវាទាំងអស់ក្នុង
ក្រុមត្រូវបានប្រើអស់ endpoint នឹងត្រឡប់ `429` តែមួយ (ជាមួយ header `Retry-After`)
ជំនួសឱ្យ `400` ទូទៅដូចពីមុន។ នៅពេលមានការស្នើ `provider`
ជាក់លាក់ នឹង **មិនមាន** ការបម្រុងទុកដោយស្ងាត់ស្ងៀមទេ — អ្នកផ្តល់សេវាជាក់លាក់ដែលត្រូវបានកម្រិតអត្រា ឬបរាជ័យ
នឹងបង្ហាញកំហុសផ្ទាល់របស់វា (`429` ប្រសិនបើត្រូវបានកម្រិតអត្រា បើមិនដូច្នោះទេ គឺស្ថានភាពពីសេវាខាងលើ)។

## ការស្ទ្រីមតាម WebSocket

```bash
GET /v1/ws?handshake=1
```

ផ្ទៀងផ្ទាត់ការចាប់ដៃដំឡើងកំណែ WebSocket ហើយត្រឡប់សារឧទាហរណ៍នៃពិធីការលើខ្សែ (`request`, `cancel`)។ ស៊ុម WS ពិតប្រាកដត្រូវបានដោះស្រាយដោយម៉ាស៊ីនមេ WS ដែលបានភ្ជាប់មកជាមួយ នៅក្រៅតារាង route របស់ Next.js។

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** Bearer API key ក្នុងអំឡុងពេលចាប់ដៃ។

### Responses API តាមរយៈ WebSocket (សម្រាប់ codex ប៉ុណ្ណោះ)

```bash
# ម៉ាស៊ីនមេ:ច្រកដូចគ្នានឹង HTTP API (លំនាំដើម 20128); ដំឡើងកំណែការតភ្ជាប់៖
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ឬ៖ -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# ស៊ុមទីមួយត្រូវតែជា response.create៖
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

ប្រូកស៊ី Responses-API-over-WebSocket ត្រូវបានភ្ជាប់ **ផ្ដាច់មុខទៅកាន់ `codex`** (backend របស់ ChatGPT)។
វាស្ដាប់លើច្រកដូចគ្នានឹង API/dashboard នៅផ្លូវ `/v1/responses`,
`/responses` និង `/api/v1/responses`។ នៅស៊ុម `response.create` ដំបូង វា
ផ្ទៀងផ្ទាត់អត្តសញ្ញាណ + រៀបចំតាមរយៈ bridge `codex-responses-ws` ខាងក្នុង ជ្រើសរើស
ការតភ្ជាប់ OAuth របស់ codex ហើយបញ្ជូន tunnel ទៅ `wss://chatgpt.com/backend-api/codex/responses`
តាមរយៈ transport `wreq-js`។ **ម៉ូដែលដែលមិនមែនជា codex នឹងត្រូវបានបដិសេធ** (`codex_ws_provider_required`)។
សម្រាប់ routing ចែករំលែកកូតា សូមប្រើ `model: "qtSd/<group>/codex/<model>"`។ បានអនុវត្តនៅក្នុង
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`។

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** Bearer API key ក្នុងអំឡុងពេលចាប់ដៃ។ ម៉ាស៊ីនមេ HTTP ដែលបានភ្ជាប់មកជាមួយ (`server-ws.mjs`)
ត្រូវតែជា entrypoint ដែលកំពុងសកម្ម (ជាលំនាំដើម វាគឺដូច្នោះ នៅពេលមាន `app/server-ws.mjs`)។

#### លេខសម្គាល់ម៉ូដែល៖ ប្រើលេខសម្គាល់ ChatGPT ដើម (គ្មានបុព្វបទ `codex/`)

**Codex CLI** របស់ OpenAI ផ្ទៀងផ្ទាត់ឈ្មោះម៉ូដែលនៅផ្នែក client នៅពេល
`supports_websockets = true` ហើយ **បដិសេធលេខសម្គាល់ដែលមានបុព្វបទអ្នកផ្តល់សេវា** ដូចជា
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)។ ផ្ញើលេខសម្គាល់ **ដើម** (ឧ. `gpt-5.5`)។ bridge របស់ OmniRoute គឺ
សម្រាប់តែ codex ដូច្នេះវាដោះស្រាយលេខសម្គាល់ដើមឡើងវិញជាម៉ូដែល codex
(`resolveCodexWsModelInfo`) មុនពេលបញ្ជូន tunnel ទៅសេវាខាងលើ — ទោះបីជា
`gpt-5.5` ដើម បើមិនដូច្នោះទេ នឹងត្រូវបានបញ្ជូនទៅអ្នកផ្តល់សេវាផ្សេងតាមរយៈ HTTP ក៏ដោយ។

#### ការកំណត់រចនាសម្ព័ន្ធ OpenAI Codex CLI

តម្រង់ Codex CLI ទៅ OmniRoute ដោយបន្ថែមអ្នកផ្តល់សេវាផ្ទាល់ខ្លួនដែលគាំទ្រ WebSocket
ទៅក្នុង `~/.codex/config.toml` (ប្រើ `CODEX_HOME` ដាច់ដោយឡែក ដើម្បីជៀសវាងការប៉ះពាល់
ដល់ការកំណត់រចនាសម្ព័ន្ធដែលមានស្រាប់)៖

```toml
model = "gpt-5.5"                 # លេខសម្គាល់ដើម — មិនមែន "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # គ្មានសញ្ញា slash នៅចុង; URL របស់ WS ត្រូវបានបង្កើតចេញពីនេះ (ប្រើ https/wss ក្នុង production)
wire_api = "responses"                    # តម្លៃតែមួយគត់ដែលគាំទ្រ ចាប់តាំងពីខែកុម្ភៈ ឆ្នាំ 2026
supports_websockets = true                # បើក transport Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # ផ្ទុក API key របស់ OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API key របស់ OmniRoute (key ណាមួយ ប្រសិនបើ REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI ដំឡើងកំណែ `base_url + /responses` ទៅជា WebSocket ហើយ OmniRoute បញ្ជូន tunnel វា
ទៅការតភ្ជាប់ OAuth របស់ codex ដែលបានជ្រើសរើស។ បានផ្ទៀងផ្ទាត់ពីដើមដល់ចប់ជាមួយម៉ាស៊ីនមេ
មូលដ្ឋាន៖ ChatGPT ត្រឡប់ `codex.rate_limits` + `response.created` ហើយស្ទ្រីម
លទ្ធផលបំពេញ។

## ការប្រើប្រាស់ដោយខ្លួនឯង (`/api/usage/om-usage`)

សោ API ណាមួយក៏អាចអានការប្រើប្រាស់ និងកូតា **របស់ខ្លួនឯង** បានដែរ — មិនចាំបាច់មានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រងទេ។ នេះគឺជា endpoint ដែល
client (CLI, ផ្ទាំង OmniCopilot) ប្រើដើម្បីបង្ហាញអ្នកកាន់សោអំពីការចំណាយរបស់ពួកគេ។

```bash
# ទម្រង់អត្ថបទ (កិច្ចសន្យាប្រវត្តិសាស្ត្រ — អត្ថបទធម្មតាសម្រាប់ terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ទម្រង់មានរចនាសម្ព័ន្ធ — ជាទម្រង់ដែល UI ប្រើប្រាស់
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

សោត្រូវតែបានបើក **`allowUsageCommand`** (បិទតាមលំនាំដើម — កម្មវិធីគ្រប់គ្រងសោ API របស់ dashboard
បិទបើកវាតាមសោនីមួយៗ)។ បើគ្មានវា endpoint នឹងឆ្លើយតប `403`។

`?format=json` ត្រឡប់ទម្រង់ដែលបែងចែកប្រភេទច្បាស់លាស់ ដើម្បីឱ្យអ្នកហៅមិនអានវាលទិន្នន័យពី
ការបដិសេធឡើយ។ នៅពេលជោគជ័យ៖

```jsonc
{
  "allowed": true,
  // មានតែនៅពេលសោបានជ្រើសប្រើដែនកំណត់ការប្រើប្រាស់តាមសោ (USD ប្រចាំថ្ងៃ/ប្រចាំសប្ដាហ៍)៖
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // រូបថតចម្លងកូតារបស់ provider ដែលបានជ្រើស ឬ null នៅពេលមិនទាន់មានអ្វីត្រូវបានរក្សាទុកក្នុង cache៖
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // រូបថតចម្លងរបស់ connection ទាំងអស់ ដើម្បីឱ្យ UI អាចបង្ហាញ provider ជាច្រើននៅក្បែរគ្នា៖
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],

```

នៅពេលបដិសេធ (`401` សោមិនត្រឹមត្រូវ / `403` មិនត្រូវបានអនុញ្ញាត) route ដដែលនឹងត្រឡប់
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` ដែលមានវត្តមាន ប៉ុន្តែទទេ
(សោត្រូវបានអនុញ្ញាត ប៉ុន្តែមិនទាន់ទទួលបានទិន្នន័យ) គឺជាស្ថានភាពខុសពីការបដិសេធ ហើយមានតែទម្រង់ JSON
ប៉ុណ្ណោះដែលអាចបែងចែកស្ថានភាពទាំងនេះបាន។

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** សោ Bearer API ផ្ទាល់របស់អ្នកហៅ ដែលបានផ្ទៀងផ្ទាត់ជាមួយ `isValidApiKey` — នេះ _មិនមែន_ ជា
ផ្ទៃគ្រប់គ្រង (`/api/keys/…`) ដែលនៅតែត្រូវបានការពារដោយ `requireManagementAuth` នោះទេ។

### ភាគរយកូតាឆៅ ធៀបនឹងភាគរយដែលបានកែតម្រូវតាមកម្រិតកាត់ផ្ដាច់

នៅពេលប្រើប្រាស់ `/api/usage/om-usage` អ្នកហៅគួរកត់សម្គាល់ពីភាពខុសគ្នារវាង
ភាគរយដែលបង្ហាញដោយ **លទ្ធផលជាអត្ថបទធម្មតា** និង **លទ្ធផល JSON** ដែលមានរចនាសម្ព័ន្ធ៖

| ទិដ្ឋភាព                              | ទម្រង់អត្ថបទធម្មតា (`/api/usage/om-usage` / `@@om-usage`)                                             | ទម្រង់ JSON (`?format=json`)                                                           |
| :------------------------------------ | :---------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| **វាលលទ្ធផល**                         | `NN% left` (ឧ. `20% left`)                                                                            | `provider.quotas` / `providers[].quotas`                                               |
| **រង្វាស់**                           | **ចំនួនអនុញ្ញាតដែលអាចប្រើបាន បន្ទាប់ពីកែតម្រូវតាមកម្រិតកាត់ផ្ដាច់**៖ សមត្ថភាពនៅសល់លើសកម្រិតកាត់ផ្ដាច់ | **កូតាឆៅពី upstream**៖ រង្វាស់ provider ដែលមិនបានកែតម្រូវ                              |
| **ការធ្វើមាត្រដ្ឋានកម្រិតកាត់ផ្ដាច់** | ធ្វើមាត្រដ្ឋានតាម `effectiveRemainingPercent()` ដើម្បីឱ្យទុនបម្រុងដែលបានការពារបង្ហាញជា `0% left`      | គ្មាន (តម្លៃរូបថតចម្លងឆៅតាមដែល provider បានរាយការណ៍)                                   |
| **ទិន្នន័យកម្រិតកំណត់**               | ត្រូវបានបញ្ចូលទៅក្នុងភាគរយដែលបង្ហាញ                                                                   | រក្សាទុកក្នុង `quotaWindowThresholds` សម្រាប់ connection នីមួយៗ (ឬលំនាំដើមរបស់ server) |
| **អ្នកប្រើប្រាស់ចម្បង**               | CLI អន្តរកម្ម សារ prompt ក្នុង terminal និងប្រតិបត្តិករមនុស្ស                                         | ការរួមបញ្ចូលតាមកម្មវិធី dashboard ការវិភាគ និងឧបករណ៍តាមដានការចេញវិក្កយបត្រ             |

#### រូបមន្តកែតម្រូវកម្រិតកាត់ផ្ដាច់

OmniRoute គាំទ្រការកាត់ផ្ដាច់កូតាជាមុន ដើម្បីទប់ស្កាត់ការប្រើប្រាស់ upstream អស់ (កំណត់រចនាសម្ព័ន្ធតាម connection
`quotaWindowThresholds` លំនាំដើមរបស់ provider ឬការកំណត់ភាពធន់ជាសកល)។ នៅពេលកម្រិតកាត់ផ្ដាច់
(ឧ. `cutoff = 25%`) សកម្មលើចន្លោះកូតា កម្មវិធីបង្ហាញអត្ថបទគណនាចំនួនអនុញ្ញាតដែលនៅសល់ដូចខាងក្រោម៖

- ប្រសិនបើ `remaining <= cutoff`៖ ត្រឡប់ `0%`។
- ប្រសិនបើ `remaining > cutoff`៖ ត្រឡប់ `((remaining - cutoff) / (100 - cutoff)) * 100`។

លទ្ធផលអត្ថបទដែលបានធ្វើទ្រង់ទ្រាយបង្គត់តម្លៃនេះទៅចំនួនគត់ដែលនៅជិតបំផុត (`Math.round(...)`)។

#### ឧទាហរណ៍បង្ហាញ

ពិចារណាចន្លោះរបស់ provider ដែលមាន **ការប្រើប្រាស់ឆៅ 60%** (ដូច្នេះមាន **កូតាឆៅនៅសល់ 40%**) និងបានកំណត់រចនាសម្ព័ន្ធ
កម្រិត **កាត់ផ្ដាច់នៅពេលកូតានៅសល់ 25%**៖

| ការតំណាង                      | ការគណនា                                            |  នៅសល់  |     ការប្រើប្រាស់ដែលអាចសន្និដ្ឋានបាន     |
| :---------------------------- | :------------------------------------------------- | :-----: | :--------------------------------------: |
| **JSON ឆៅ (`?format=json`)**  | រូបថតចម្លងពី upstream (`quotas[window]`)           | **40%** |                 **60%**                  |
| **ទម្រង់អត្ថបទ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (ប្រសិនបើគណនា `100 - remaining`) |

- **មូលហេតុដែលអត្ថបទបង្ហាញថានៅសល់ 20%៖** ក្នុងចំណោមកូតាជាក់ស្ដែង 40% ដែលនៅសល់ក្នុងគណនី មាន 25% ត្រូវបានរក្សាទុកដោយ
  គោលការណ៍កាត់ផ្ដាច់។ អ្នកហៅមានចន្លោះដែលអាចប្រើបានត្រឹមតែ 15% ក្នុងចំណោម 75% ដែលនៅសល់ មុនពេល router ឈប់
  បញ្ជូនទៅ connection នេះ។ ការធ្វើមាត្រដ្ឋានធានាថា connection ផ្ដល់សញ្ញាថាកូតាបានអស់ (`0% left`) នៅពេលជាក់លាក់ដែល
  ការបញ្ជូននឹងបញ្ឈប់។
- **មូលហេតុដែល JSON រក្សាទុកតម្លៃឆៅ៖** payload JSON ត្រឡប់រូបថតចម្លងពិតប្រាកដរបស់ provider (`UsageSnapshot`)
  ដើម្បីឱ្យឧបករណ៍ខាងក្រៅអាចចូលប្រើទិន្នន័យពិតនៃការប្រើប្រាស់ upstream និង
  `quotaWindowThresholds` កម្រិត connection ដោយគ្មានការធ្វើមាត្រដ្ឋានដែលបាត់បង់ទិន្នន័យពីផ្នែក server។

#### សេចក្ដីណែនាំសម្រាប់ការផ្លាស់ប្ដូររបស់អ្នកប្រើប្រាស់

ប្រសិនបើការរួមបញ្ចូលជាមួយប្រព័ន្ធខាងក្រៅ (ដូចជា plugin សម្រាប់កម្មវិធីកែសម្រួល ឬផ្នែកបន្ថែមរបស់ agent) ពីមុនបានស្រង់យកទិន្នន័យពី
endpoint អត្ថបទ (`NN% left`) ហើយគណនាភាគរយដែលបានប្រើជា `100 - NN` នោះការផ្លាស់ប្តូរទៅ `?format=json` មានន័យថា៖

- ការអានតម្លៃ JSON ដើមនឹងបង្ហាញពី **ការប្រើប្រាស់ upstream ជាក់ស្តែង** (បានប្រើ 60% ក្នុងឧទាហរណ៍ខាងលើ)។
- ប្រសិនបើការរួមបញ្ចូលចង់រក្សាអត្ថន័យនៃកម្រិតដែលអាចប្រើបានរបស់ endpoint អត្ថបទ វាអាចវាយតម្លៃ
  រូបមន្តបរិមាណនៅសល់ជាក់ស្តែងនៅផ្នែក client ដោយប្រើ `quotaWindowThresholds` សម្រាប់ការកំណត់ជាន់លើនៅកម្រិត connection។

### ផលប៉ះពាល់លើរយៈពេលឆ្លើយតប

នៅពេលឃ្លាំងសម្ងាត់តាមន័យរកឃើញទិន្នន័យ (HIT) វានឹងផ្តល់ការឆ្លើយតបពីឃ្លាំងសម្ងាត់ **ដោយមិនមានការហៅទៅប្រភពខាងលើ
ឡើយ** ដូច្នេះ `X-OmniRoute-Response-Latency` ដែលបានរាយការណ៍គឺជិតសូន្យ
(ដោយមិនគិតពីរយៈពេលឆ្លើយតបដើមរបស់ប្រភពខាងលើ)។ កម្មវិធីអតិថិជនដែលងាយរងឥទ្ធិពលពីរយៈពេលឆ្លើយតប
(ការធ្វើតេស្តសមត្ថភាព ការត្រួតពិនិត្យ p50/p99) គួរតែពិនិត្យបឋមកថាការឆ្លើយតប
`X-OmniRoute-Cache-Latency`៖

| តម្លៃ        | អត្ថន័យ                                                                            |
| ------------ | ---------------------------------------------------------------------------------- |
| `synthetic`  | ការឆ្លើយតបត្រូវបានផ្តល់ពីឃ្លាំងសម្ងាត់; រយៈពេលនេះមិនមែនជារយៈពេលពិតរបស់ប្រភពខាងលើទេ |
| _(អវត្តមាន)_ | ការឆ្លើយតបពីការហៅពិតប្រាកដទៅប្រភពខាងលើ                                             |

### ការរំលងឃ្លាំងសម្ងាត់តាមកូនសោនីមួយៗ

កូនសោ API អាចជ្រើសរើសមិនអានពីឃ្លាំងសម្ងាត់តាមន័យតាមរយៈ `cacheDefaultMode`៖

| តម្លៃ    | ឥរិយាបថ                                                        |
| -------- | -------------------------------------------------------------- |
| `legacy` | ឥរិយាបថឃ្លាំងសម្ងាត់ធម្មតា (លំនាំដើម)                          |
| `bypass` | រំលងការស្វែងរកក្នុងឃ្លាំងសម្ងាត់ទាំងស្រុង; តែងតែហៅទៅប្រភពខាងលើ |

កំណត់នៅពេលបង្កើតកូនសោ (`POST /api/keys`) ឬធ្វើបច្ចុប្បន្នភាព (`PATCH /api/keys/[id]`)៖

```json
{ "cacheDefaultMode": "bypass" }
```

### ការរំលងតាមសំណើនីមួយៗ

សំណើណាមួយអាចរំលងឃ្លាំងសម្ងាត់បាន ដោយមិនគិតពីការកំណត់របស់កូនសោ៖

```
X-OmniRoute-No-Cache: true
```

### កំណែ និងឆានែលចេញផ្សាយ

```bash
GET /api/system/version
```

ផ្លូវគ្រប់គ្រងសម្រាប់តែ loopback ប៉ុណ្ណោះ (ការផ្ទៀងផ្ទាត់អ្នកគ្រប់គ្រង)។ ត្រឡប់កំណែដែលកំពុងដំណើរការ កំណែដែលបានបោះពុម្ពផ្សាយចុងក្រោយ និងស្ថានភាពអាប់ដេតស្វ័យប្រវត្តិ។ `releaseChannel` និង `channels` គឺជាវាលដែលបានបន្ថែម (rail 3.8.54); `channel` រក្សាអត្ថន័យដដែល — របៀបដាក់ឱ្យដំណើរការដែលកម្មវិធីអាប់ដេតរបស់ផ្ទាំងគ្រប់គ្រងប្រើ (`npm`, `source` ឬ `docker-compose`)។

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ឆានែល npm របស់ build ដែលកំពុងដំណើរការ៖ `nightly` សម្រាប់កំណែ `-nightly.*`,
  `next` សម្រាប់កំណែមុនចេញផ្សាយផ្សេងទៀត (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` សម្រាប់កំណែស្ថិរភាពដែលមានកំណែ major
  ចាស់ជាង `channels.latest` បើមិនដូច្នោះទេគឺ `latest`។ ប្រើច្បាប់ដូចគ្នានឹង
  `scripts/release/dist-tag.mjs` ដែលជ្រើសរើស npm dist-tag នៅពេលបោះពុម្ពផ្សាយ។
- `channels` — កំណែចុងក្រោយដែលបានបោះពុម្ពផ្សាយនៃ dist-tag នីមួយៗ ពី `npm view omniroute dist-tags` (មាន registry
  HTTP ជាជម្រើសបម្រុង) ដែលត្រូវបានរក្សាទុកក្នុង cache ជាមួយ TTL 10 នាទីដូចគ្នានឹង `latest`។ `latest` តែងតែមាន
  (ត្រឡប់ទៅប្រើវាល `latest` ហើយបន្ទាប់មក `"unavailable"` ជាជម្រើសបម្រុង); `next`, `nightly` និង `lts` បង្ហាញ
  តែនៅពេលដែលមាន dist-tag នោះប៉ុណ្ណោះ។ សំណើ `Cache-Control: no-cache` នឹងធ្វើឱ្យការស្វែងរកទាំងពីរស្រស់ឡើងវិញ។

ម៉ូដែលឆានែល (`latest` = v3 រហូតដល់ 4.0 GA, `next` = rc, `nightly` = build ពី `develop`,
`lts` = patch របស់ v3 បន្ទាប់ពី 4.0 GA) ត្រូវបានពិពណ៌នានៅក្នុង `docs/ops/RELEASE_STRATEGY.md`។

## ឈ្មោះជំនួស VS Code ដែលមាន Token / គ្មាន Header

ប្រើឈ្មោះជំនួសទាំងនេះ នៅពេលការរួមបញ្ចូលមួយមិនអាចបញ្ចូល header `Authorization` ហើយត្រូវការបង្កប់សោ API នៅក្នុង URL មូលដ្ឋាន។

```bash

POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# ឈ្មោះជំនួសតាមរចនាប័ទ្ម Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ឧទាហរណ៍៖

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

ចំណាំ៖

- ឈ្មោះជំនួសដែលមាន Token ប្រើ handler ដូចគ្នានឹង `/v1/*` និង `/api/tags` ឡើងវិញ ដូច្នេះទម្រង់ការឆ្លើយតបនៅតែដូចគ្នា។
- គួរប្រើ `Authorization: Bearer ...` នៅពេលណាដែល client គាំទ្រ header ផ្ទាល់ខ្លួន។
- Token ដែលមានមូលដ្ឋានលើ URL អាចបង្ហាញនៅក្នុងកំណត់ហេតុ reverse-proxy ប្រវត្តិកម្មវិធីរុករក និងទិន្នន័យតេឡេមេទ្រីនៅខាងក្រៅ OmniRoute។ ចាត់ទុកវាជាជម្រើសសម្រាប់ភាពឆបគ្នា មិនមែនជារបៀបផ្ទៀងផ្ទាត់អត្តសញ្ញាណលំនាំដើមទេ។

```bash
# ទទួលស្ថានភាពថវិកាសម្រាប់សោ API ទាំងអស់
```

## ដែនកំណត់ Token

ថវិកា **token** ក្នុងមួយ API key (ខុសពីថវិកាផ្អែកលើ USD ខាងលើ)។ ដែនកំណត់នេះត្រូវបានអនុវត្តផ្ទាល់នៅលើផ្លូវដំណើរការសំណើ៖ នៅពេលការប្រើប្រាស់ក្នុងចន្លោះពេលបច្ចុប្បន្នរបស់ key មួយឈានដល់ដែនកំណត់ សំណើនឹងត្រូវបានបដិសេធដោយ `429 Too Many Requests`។ ដែនកំណត់អាចត្រូវបានកំណត់វិសាលភាពទៅលើ `model` ជាក់លាក់មួយ, `provider` មួយ ឬអនុវត្តជា `global` លើ key ទាំងមូល។ នៅពេលដែនកំណត់ច្រើនត្រូវគ្នានឹងសំណើមួយ ដែនកំណត់ដែលតឹងរ៉ឹងបំផុតនឹងត្រូវបានយកមកអនុវត្ត។

```bash
# រាយបញ្ជីដែនកំណត់ token របស់ key មួយ (រួមទាំងការប្រើប្រាស់ក្នុងចន្លោះពេលបច្ចុប្បន្ន)
GET /api/usage/token-limits?apiKeyId=key-123

# បង្កើត ឬធ្វើបច្ចុប្បន្នភាពដែនកំណត់ token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# លុបដែនកំណត់ token តាម id
DELETE /api/usage/token-limits?id=tl-abc
```

> **កំណត់សម្គាល់អំពី Schema** (`setTokenLimitSchema`)៖ `apiKeyId` និង `scopeType` (`model` | `provider` | `global`) គឺតម្រូវឱ្យមាន។ `scopeValue` តម្រូវឱ្យមាន លុះត្រាតែ `scopeType` គឺជា `global` (ឧ. model id សម្រាប់វិសាលភាព `model` ឬ provider id សម្រាប់វិសាលភាព `provider`)។ `tokenLimit` ត្រូវតែជាចំនួនគត់វិជ្ជមាន (បំប្លែងពី string)។ ជាជម្រើស៖ `id` (មិនត្រូវបញ្ចូលដើម្បីបង្កើតថ្មី និងត្រូវផ្តល់ដើម្បីធ្វើបច្ចុប្បន្នភាព), `resetInterval` (`daily` | `weekly` | `monthly`, លំនាំដើម `monthly`), `resetTime` (`HH:MM`), `enabled` (លំនាំដើម `true`)។ ការឆ្លើយតប `GET` បន្ថែមព័ត៌មានទៅក្នុងដែនកំណត់នីមួយៗដោយមាន `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` និង `nextResetAt`។ នេះជា endpoint ប្រភេទគ្រប់គ្រង (ការផ្ទៀងផ្ទាត់សិទ្ធិត្រូវបានអនុវត្តជាកណ្ដាលដោយ authz pipeline)។

## ដំណើរការសំណើ

1. Client ផ្ញើសំណើទៅកាន់ `/v1/*`
2. Route handler ហៅ `handleChat`, `handleEmbedding`, `handleAudioTranscription` ឬ `handleImageGeneration`
3. Model ត្រូវបានកំណត់រក (provider/model ផ្ទាល់ ឬ alias/combo)
4. Credentials ត្រូវបានជ្រើសរើសពី local DB ដោយមានការច្រោះតាមភាពអាចប្រើបានរបស់ account
5. សម្រាប់ chat៖ `handleChatCore` ពិនិត្យ semantic/signature cache និងកំណត់ការកំណត់ combo compression
6. Proactive compression ដំណើរការមុន provider translation នៅពេលបានបើកប្រើ (`lite`, Caveman, RTK ឬ stacked)
7. Provider executor ផ្ញើសំណើទៅកាន់ upstream
8. Response ត្រូវបានបកប្រែត្រឡប់ទៅជា client format (chat) ឬត្រូវបានបញ្ជូនត្រឡប់តាមសភាពដើម (embeddings/images/audio)
9. Usage, compression analytics និង request logs ត្រូវបានកត់ត្រា
10. Fallback ត្រូវបានអនុវត្តនៅពេលមានកំហុស ស្របតាម combo rules

ឯកសារយោងអំពីស្ថាបត្យកម្មពេញលេញ៖ [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## ការគ្រប់គ្រង Combo

Routing combos កម្រិតខ្ពស់ជាង (ដែលបានសង្ខេបរួចហើយនៅក្រោម `/api/combos*`) ក៏អាចត្រូវបានផ្គូផ្គង 1:1 ពី model id pattern មួយផងដែរ ដែលអនុញ្ញាតឱ្យបង្វែរទិសដោយថ្លាភាពពី OpenAI-style model id ទៅកាន់ combo មួយ។

| Method | Path                             | សេចក្ដីពិពណ៌នា                                                                 |
| ------ | -------------------------------- | ------------------------------------------------------------------------------ |

## ពិធីការ Agents

កិច្ចការរបស់ cloud agent (Claude Code, Codex Cloud, OpenHands ជាដើម) ដែលត្រូវបានប្រតិបត្តិពីចម្ងាយក្នុងនាមអ្នកប្រើប្រាស់ OmniRoute។

| វិធីសាស្ត្រ | ផ្លូវ                         | សេចក្ដីពិពណ៌នា                                                                                                                                             |

| DELETE      | `/api/v1/agents/tasks?id=...` | លុបកិច្ចការមួយ                                                                                                                                             |

## ភាពធន់ (បន្ថែម)

OmniRoute ផ្តល់នូវយន្តការបរាជ័យបណ្តោះអាសន្នឯករាជ្យចំនួនបី; endpoint គ្រប់គ្រងខាងក្រោមអនុញ្ញាតឱ្យប្រតិបត្តិករអាន និងកំណត់វាឡើងវិញបាន៖

| វិសាលភាព                        | កន្លែងផ្ទុកស្ថានភាព                                | អាន                                       | កំណត់ឡើងវិញ / សម្អាត                                    |
| ------------------------------- | -------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------- |
| ឧបករណ៍ផ្តាច់សៀគ្វីរបស់អ្នកផ្តល់ | `domain_circuit_breakers` + ក្នុងអង្គចងចាំ         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                            |
| រយៈពេលរង់ចាំការតភ្ជាប់          | `rateLimitedUntil` លើការតភ្ជាប់របស់អ្នកផ្តល់       | `/api/rate-limits`, `/api/providers/[id]` | (បើកឡើងវិញនៅពេលចាំបាច់; សម្អាតតាមរយៈ PUT របស់អ្នកផ្តល់) |
| ការចាក់សោម៉ូដែល                 | បញ្ជីចុះឈ្មោះភាពអាចប្រើបានរបស់ម៉ូដែលក្នុងអង្គចងចាំ | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                |

`PATCH /api/resilience` ទទួលយកការកំណត់ជំនួសសម្រាប់ឧបករណ៍ផ្តាច់សៀគ្វីរបស់អ្នកផ្តល់នៅក្រោម `providerBreaker.oauth` និង `providerBreaker.apikey`។ Profile នីមួយៗគាំទ្រ `degradationThreshold`, `failureThreshold` និង `resetTimeoutMs`; field ដូចគ្នាទាំងនេះក៏ត្រូវបានបង្ហាញនៅក្នុង ផ្ទាំងគ្រប់គ្រង → ការកំណត់ → ភាពធន់ ផងដែរ។

```bash
# សម្អាតការចាក់សោម៉ូដែលតែមួយ
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# លុបការចាក់សោទាំងអស់
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

សម្រាប់ឯកសារយោងផ្នែកគោលគំនិតពេញលេញ និងតម្លៃលំនាំដើមរបស់ឧបករណ៍ផ្តាច់សៀគ្វី៖ សូមមើល [`CLAUDE.md`](../../CLAUDE.md) → "ស្ថានភាព Runtime នៃភាពធន់" និង [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)។

### ជួររង់ចាំកម្រិតអត្រា និងសំណាញ់សុវត្ថិភាពបើកដោយស្វ័យប្រវត្តិ

- **ផ្លូវសរសេរដែលគាំទ្រ**៖ `POST /api/rate-limits` ជាមួយ body `{"connectionId": "<id>", "enabled": true|false}` គឺជា endpoint គ្រប់គ្រងដែលគាំទ្រសម្រាប់បិទបើកការការពារកម្រិតអត្រាសម្រាប់ការតភ្ជាប់។ `PUT /api/providers/[id]` ត្រូវបានរចនាដោយចេតនាមិនឱ្យកែប្រែ ឬបិទបើក `rateLimitProtection` (#11278)។
- **អត្ថន័យនៃ `enabled: false`**៖ ការកំណត់ `enabled: false` ដកការការពារដែលបានកំណត់ជាក់លាក់សម្រាប់ការតភ្ជាប់ចេញ ប៉ុន្តែ **មិន** ដកការតភ្ជាប់ API-key ដែលសកម្មចេញពីសំណាញ់សុវត្ថិភាពបើកដោយស្វ័យប្រវត្តិសកល (`autoEnableApiKeyProviders = true`) ទេ។ នៅក្នុង `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` និង `undefined` មានន័យដូចគ្នា; ការតភ្ជាប់ API-key ដែលសកម្ម និងគ្មានការការពារដែលបានកំណត់ជាក់លាក់ នៅតែត្រូវបានការពារក្រោមសំណាញ់សុវត្ថិភាពបើកដោយស្វ័យប្រវត្តិ។
- **ការបិទជាសកល**៖ ដើម្បីដំណើរការការតភ្ជាប់ API-key ដោយគ្មានជួររង់ចាំកម្រិតអត្រា សូមបិទសំណាញ់សុវត្ថិភាពជាសកលតាមរយៈ `RATE_LIMIT_AUTO_ENABLE=false` (env) ឬ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (ការកំណត់ → ភាពធន់ / `PATCH /api/resilience`)។

## MCP Server

OmniRoute ផ្ដល់មកជាមួយ Model Context Protocol server ដែលបានបង្កប់ ដោយមាន transport ចំនួន 3 (stdio, SSE, streamable-http) និងឧបករណ៍ដែលបានកំណត់វិសាលភាព។ endpoints របស់ dashboard ខាងក្រោមអានទិន្នន័យស្ថានភាព/សវនកម្ម និងធ្វើ proxy សម្រាប់ HTTP transports។

| វិធីសាស្ត្រ | ផ្លូវ | សេចក្ដីពិពណ៌នា |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Heartbeat, transport, ស្ថានភាព online, ការហៅចុងក្រោយ, ឧបករណ៍ដែលប្រើច្រើនបំផុត និងអត្រាជោគជ័យក្នុងរយៈពេល 24 ម៉ោង |
| GET | `/api/mcp/tools` | បញ្ជីឧបករណ៍ MCP ដែលមាន `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | បើក SSE stream សម្រាប់ SSE transport (ត្រឡប់ `503` ប្រសិនបើ MCP ត្រូវបានបិទ ឬ transport មិនត្រូវគ្នា) |
| POST | `/api/mcp/sse` | ផ្ញើ JSON-RPC frame លើ SSE transport |
| GET | `/api/mcp/stream` | បើកផ្នែក SSE នៃ Streamable HTTP transport (សារដែលផ្ដួចផ្ដើមដោយ server) |
| POST | `/api/mcp/stream` | ផ្ញើ JSON-RPC frame លើ Streamable HTTP transport |
| DELETE | `/api/mcp/stream` | បញ្ចប់ Streamable HTTP session |
| GET | `/api/mcp/audit` | សាកសួរ audit log — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | ស្ថិតិសវនកម្មសរុប (ចំនួនសរុប, អត្រាជោគជ័យ, រយៈពេលមធ្យម និងឧបករណ៍ដែលប្រើច្រើនបំផុត) |

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ៖** transports `sse`/`stream` គោរពតាមផ្ទៃការផ្ទៀងផ្ទាត់អត្តសញ្ញាណជាក់លាក់របស់ MCP (Bearer API key ដែលមានវិសាលភាព `mcp`)។ routes `status`/`tools`/`audit*` អាចអានបានពី dashboard (មិនត្រូវការការផ្ទៀងផ្ទាត់អត្តសញ្ញាណបន្ថែមក្រៅពីអាចចូលទៅកាន់ dashboard host បានទេ)។

> HTTP transports ទាំងពីរត្រូវបានគ្រប់គ្រងដោយ `settings.mcpEnabled` និង `settings.mcpTransport` — transport ដែលមិនត្រូវគ្នានឹងត្រឡប់ `400` ហើយស្ថានភាព MCP ដែលត្រូវបានបិទនឹងត្រឡប់ `503`។

## ម៉ាស៊ីនមេ A2A

OmniRoute ផ្តល់ endpoint A2A (Agent-to-Agent) JSON-RPC 2.0 រួមជាមួយ REST wrapper សម្រាប់ការត្រួតពិនិត្យ/ការប្រើប្រាស់ dashboard។

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # ជាជម្រើស លុះត្រាតែ OMNIROUTE_API_KEY ត្រូវបានកំណត់
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

វិធីសាស្ត្រដែលគាំទ្រ (ទាំងអស់ត្រូវបានគ្រប់គ្រងដោយ `settings.a2aEnabled`)៖

| វិធីសាស្ត្រ      | ការពិពណ៌នា                                                        |
| ---------------- | ----------------------------------------------------------------- |
| `message/send`   | ប្រតិបត្តិជំនាញដោយសមកាលកម្ម; ត្រឡប់ `{task, artifacts, metadata}` |
| `message/stream` | ប្រតិបត្តិការ SSE ជាបន្តបន្ទាប់នៃសំណុំជំនាញដូចគ្នា                |
| `tasks/get`      | ទាញយកកិច្ចការតាម `taskId`                                         |
| `tasks/cancel`   | បោះបង់កិច្ចការតាម `taskId`                                        |

ជំនាញដែលមានស្រាប់៖ `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`។

### កាត Agent

```bash
GET /.well-known/agent.json
```

ត្រឡប់កាត agent A2A សាធារណៈ (ឈ្មោះ ការពិពណ៌នា សមត្ថភាព កាតាឡុកជំនាញ គម្រោង auth) — ត្រូវបាន cache ជាសាធារណៈរយៈពេល 1h។ មិនតម្រូវឱ្យមាន auth ទេ។

### ឧបករណ៍ជំនួយ REST

| វិធីសាស្ត្រ | Path                         | ការពិពណ៌នា                                                                                                       |
| ----------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| GET         | `/api/a2a/status`            | ស្ថានភាពបើក A2A + ស្ថិតិកិច្ចការ + សេចក្ដីសង្ខេបកាត agent ដែលបាន cache                                           |
| GET         | `/api/a2a/tasks`             | រាយកិច្ចការ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST        | `/api/a2a/tasks`             | (មិនទាន់ត្រូវបានអនុវត្តជា REST helper ទេ — បង្កើតតាម JSON-RPC `message/send`)                                    |
| GET         | `/api/a2a/tasks/[id]`        | ទាញយកកិច្ចការមួយ                                                                                                 |
| POST        | `/api/a2a/tasks/[id]/cancel` | បោះបង់កិច្ចការ                                                                                                   |

**Auth៖** ឧបករណ៍ជំនួយ REST ដំណើរការដោយមិនត្រូវការ management auth (អាចអានបានតាម dashboard); route JSON-RPC `/a2a` ប្រើ Bearer `OMNIROUTE_API_KEY` ប្រសិនបើបានកំណត់រចនាសម្ព័ន្ធ។

## ការគ្រប់គ្រង ACP (Agent Client Protocol)

ជាដំណើរការរង។ Endpoint ទាំងនេះគ្រប់គ្រងការរកឃើញភ្នាក់ងារ ACP និងការចុះឈ្មោះភ្នាក់ងារផ្ទាល់ខ្លួន។

| វិធីសាស្ត្រ | ផ្លូវ             | ការពិពណ៌នា                                                                                                                                                            |
| ----------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET         | `/api/acp/agents` | រាយបញ្ជីភ្នាក់ងារ CLI ដែលស្គាល់ទាំងអស់ (ភ្ជាប់មកជាមួយ + ផ្ទាល់ខ្លួន) ព្រមទាំងស្ថានភាពដំឡើង កំណែ និង binary                                                            |
| POST        | `/api/acp/agents` | ចុះឈ្មោះភ្នាក់ងារ ACP ផ្ទាល់ខ្លួន ឬធ្វើឱ្យ cache ស្រស់ឡើងវិញ — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` ឬ `{action: "refresh"}` |
| DELETE      | `/api/acp/agents` | លុបភ្នាក់ងារ ACP ផ្ទាល់ខ្លួន — query param: `?id=<agentId>`                                                                                                           |

**ឧទាហរណ៍ response** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** តម្រូវឱ្យមាន management session (cookie `auth_token` របស់ dashboard) ឬ API key ដែលមានវិសាលភាពសម្រាប់ការគ្រប់គ្រង។

សូមមើល [ACP Framework](../frameworks/ACP.md) សម្រាប់ព័ត៌មានលម្អិតពេញលេញ។

## ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ

សូមមើល [ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រង](../guides/MANAGEMENT-AUTH.md) សម្រាប់ព័ត៌មានអំពីអត្តសញ្ញាណបណ្ណសម្គាល់ទាំងបួនប្រភេទ (សម័យ dashboard, token របស់ CLI មូលដ្ឋាន, Access Token `oma_live_…`, API key ដែលមានវិសាលភាពគ្រប់គ្រង) និងភាពខុសគ្នារបស់ពួកវាពី inference key។

- ផ្លូវ dashboard (`/dashboard/*`) ប្រើ cookie `auth_token`
- ការចូលប្រើប្រើ hash ពាក្យសម្ងាត់ដែលបានរក្សាទុក ហើយបើវាមិនដំណើរការ នឹងប្រើ `INITIAL_PASSWORD`
- `requireLogin` អាចបើក ឬបិទបានតាមរយៈ `/api/settings/require-login`
- ផ្លូវ `/v1/*` អាចតម្រូវឱ្យមាន Bearer API key នៅពេល `REQUIRE_API_KEY=true`
- ក្នុងឯកសារយោងនេះ "management token" / "management-scoped API key" មានន័យថាជាប្រភេទមួយក្នុងចំណោមប្រភេទដែលមានក្នុងមគ្គុទ្ទេសក៍នោះ — មិនមែនជាប្រភេទ secret បន្ថែមដែលមិនបានកំណត់នោះទេ

> **ការផ្លាស់ប្ដូរដែលមិនត្រូវគ្នាជាមួយកំណែមុន (v3.8.0)** — `/api/v1/agents/tasks/*` និង endpoint សម្រាប់ការគ្រប់គ្រង cooldown ឥឡូវនេះតម្រូវឱ្យមាន **ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រង** (cookie `auth_token` របស់ dashboard ឬ API key ដែលមានវិសាលភាពគ្រប់គ្រង)។ Client ដែលពីមុនបានហៅផ្លូវទាំងនេះដោយគ្មានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ នឹងទទួលបាន `401 Unauthorized`។ សូមមើល commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`)។
