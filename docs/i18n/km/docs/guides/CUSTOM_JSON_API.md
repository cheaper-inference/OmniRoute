ថ្នាំង JSON API ផ្ទាល់ខ្លួនភ្ជាប់ចំណុចបញ្ចប់អាជីវកម្ម JSON ដែលមិននិយាយពិធីការ OpenAI ឬ Anthropic ។ OmniRoute បំពេញគំរូសំណើ JSON ផ្ញើវាទៅចំណុចបញ្ចប់ពេញលេញ URL អានការឆ្លើយតបពីផ្លូវឆ្លើយតប ហើយបញ្ជូនវាទៅអតិថិជនក្នុងទម្រង់ផ្ទាល់ខ្លួនរបស់អតិថិជន (ការបំពេញការជជែក ការឆ្លើយតប សារ...)។

វាគឺជាថ្នាំង OpenAI ដែលឆបគ្នាជាមួយ `apiType: "custom-json"`; លេខសម្គាល់របស់វាមានទម្រង់ `openai-compatible-custom-json-<suffix>`។ ទម្រង់ផ្ទាំងគ្រប់គ្រងមិនទាន់មាននៅឡើយទេ។ បង្កើត និងកែសម្រួលថ្នាំងទាំងនេះតាមរយៈថ្នាំងអ្នកផ្តល់សេវា API ខាងក្រោម។

## បង្កើតថ្នាំង

`POST /api/provider-nodes` (ការផ្ទៀងផ្ទាត់ការគ្រប់គ្រង):

```json
{
  "type": "openai-compatible",
  "apiType": "custom-json",
  "name": "Business API",
  "prefix": "biz",
  "baseUrl": "https://api.example.com/v1/answer",
  "customHeaders": { "X-Tenant": "demo" },
  "customJson": {
    "method": "POST",
    "authType": "api-key",
    "authHeader": "X-Service-Key",
    "requestTemplate": {
      "project_id": "demo-project",
      "question": "{{prompt}}",
      "history": "{{messages}}"
    },
    "responsePath": "data.answer"
  }
}
```

- `baseUrl` គឺជា** ពេញលេញ** ចំណុចបញ្ចប់ URL។ គ្មានអ្វីត្រូវបានបន្ថែម (គ្មាន `/chat/completions`, no `/models`) ហើយមិនដូចថ្នាំងដែលឆបគ្នាជាមួយ OpenAI ផ្សេងទៀតទេ វាមិនមាន URL លំនាំដើមទេ។ វាត្រូវតែជា `http(s)` ដោយគ្មានព័ត៌មានបញ្ជាក់អត្តសញ្ញាណដែលបានបង្កប់ ឬ `#fragment` ហើយវាឆ្លងកាត់ការការពារ URL ខាងក្រៅដូចគ្នានឹងថ្នាំងអ្នកផ្តល់សេវាទាំងអស់ ទាំងនៅពេលដែលថ្នាំងត្រូវបានរក្សាទុក និងរាល់ការស្នើសុំ។
- ថ្នាំងដែលផ្ញើសោតភ្ជាប់ (`authType` `bearer` ឬ `api-key` រួមទាំងលំនាំដើម) ត្រូវតែប្រើ `https://`។ `http://` ធម្មតាត្រូវបានទទួលយកសម្រាប់តែម៉ាស៊ីនរង្វិលជុំ (`localhost`, `127.0.0.0/8`, `::1`) ឬជាមួយ `authType: "none"` ដែលមិនផ្ញើសោ។ អាសយដ្ឋាន LAN ឯកជន (`10.x`, `172.16-31.x`, `192.168.x`) មិនត្រូវបានលើកលែងទេ៖ នរណាម្នាក់នៅលើបណ្តាញនោះអាចអានសោ។ ការរក្សាទុកថ្នាំងបែបនេះបរាជ័យជាមួយ `400` ហើយថ្នាំងដែលបានរក្សាទុកមុននឹងបរាជ័យក្នុងការបិទរាល់សំណើដែលមានសារដូចគ្នា មុនពេលសំណើណាមួយត្រូវបានផ្ញើ។ សម្រាប់ចំណុចបញ្ចប់ដែលចុចលើ LAN ដាក់វានៅខាងក្រោយ TLS (ឧទាហរណ៍ប្រូកស៊ីបញ្ច្រាស)។
- `customJson` ត្រូវបានផ្ទៀងផ្ទាត់ជាមួយ Zod; សោមិនស្គាល់ត្រូវបានបដិសេធ។ វាលនីមួយៗគឺស្រេចចិត្ត៖

| វាល               | តម្លៃ                               | លំនាំដើម                                               |
| ----------------- | ----------------------------------- | ------------------------------------------------------ |
| `method`          | `POST`, `PUT`, `PATCH`              | `POST`                                                 |
| `authType`        | `bearer`, `api-key`, `none`         | `bearer`                                               |
| `authHeader`      | ឈ្មោះបឋមកថាប្រើនៅពេល `api-key`      | `X-API-Key`                                            |
| `requestTemplate` | វត្ថុJSON (≤ 64 KB, ជម្រៅ ≤ 32)     | `{ "model": "{{model}}", "messages": "{{messages}}" }` |
| `responsePath`    | ផ្លូវវាល ឬ `$` សម្រាប់រាងកាយទាំងមូល | `choices[0].message.content`                           |

- អាថ៌កំបាំងស្ថិតនៅក្នុងកូនសោ API នៃការតភ្ជាប់ មិនដែលនៅក្នុងគំរូទេ។ `bearer` ផ្ញើ `Authorization: Bearer <key>`; `api-key` ផ្ញើ `<authHeader>: <key>`។ បឋមកថា auth មិនអាចជា `Host`, `Content-Type`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Authorization`, `Cookie` ឬបឋមកថា hop-by-hop ទេ។ ជាមួយ `none` ការតភ្ជាប់មិនត្រូវការសោទេ។
- បឋមកថាឋិតិវន្តបន្ថែមប្រើ `customHeaders` ធម្មតារបស់ថ្នាំង (សុពលភាពដូចគ្នានឹងថ្នាំងដែលត្រូវគ្នាផ្សេងទៀតដែរ បឋមកថាភាពត្រឹមត្រូវមិនត្រូវបានអនុញ្ញាតនៅទីនោះទេ)។

`PUT /api/provider-nodes/<id>` ទទួលយក `customJson` ដូចគ្នា ហើយសរសេរ `baseUrl` ឡើងវិញ និង config លើរាល់ការតភ្ជាប់ដែលមានស្រាប់នៃ node ។ ការលុបចោល `customJson` រក្សាការកំណត់ដែលបានរក្សាទុក។ ការប្តូរ `apiType` ទៅ `chat` ឬ `responses` យកវាចេញពី node និងការតភ្ជាប់របស់វា។

បន្ទាប់មកបន្ថែមការតភ្ជាប់ទៅថ្នាំងដូចធម្មតា (`POST /api/providers` ជាមួយ node id ) ហើយស្នើសុំ `<prefix>/<model>` ឧទាហរណ៍ `biz/assistant-v1`។ ចំណុចបញ្ចប់មិនបង្ហាញបញ្ជីគំរូ ដូច្នេះសូមបន្ថែមលេខសម្គាល់គំរូដោយដៃ។

## ស្នើសុំគំរូ

គំរូគឺ JSON ធម្មតា។ តម្លៃខ្សែអក្សរអាចមានសញ្ញាសម្គាល់ `{{placeholder}}` ; គ្មានអ្វីត្រូវបានវាយតម្លៃ ឬប្រតិបត្តិឡើយ ហើយគ្រាប់ចុចវត្ថុមិនត្រូវបានជំនួសឡើយ។

| កន្លែងដាក់           | តម្លៃ                                                                      |
| -------------------- | -------------------------------------------------------------------------- |
| `{{prompt}}`         | អត្ថបទនៃសារអ្នកប្រើប្រាស់ចុងក្រោយបំផុត (ផ្នែកអត្ថបទភ្ជាប់ជាមួយបន្ទាត់ថ្មី) |
| `{{messages}}`       | ការសន្ទនាក្នុងទម្រង់ជជែក OpenAI                                            |
| `{{model}}`          | លេខសម្គាល់ម៉ូដែលដែលបានស្នើ ដោយគ្មានបុព្វបទអ្នកផ្តល់សេវា                    |
| `{{stream}}`         | តែងតែ `false` — ចំណុចបញ្ចប់ឆ្លើយជាមួយនឹងឯកសារ JSON មួយ។                    |
| `{{request.<path>}}` | វាលនៃសំណើដែលបានបកប្រែ (OpenAI chat format)                                 |

- តម្លៃដែលពិតប្រាកដមួយកន្លែងរក្សាប្រភេទ JSON របស់វា (`"{{messages}}"` ក្លាយជាអារេ); កន្លែងដាក់នៅខាងក្នុងខ្សែអក្សរវែងជាងត្រូវបានបញ្ចូលជាអត្ថបទ។
- កន្លែងដាក់ដែលដោះស្រាយគ្មានអ្វីបរាជ័យសំណើរជាមួយ HTTP 400 ជំនួសឱ្យការផ្ញើបន្ទុកមិនពេញលេញ។
- ផ្លូវប្រើសញ្ញាចុច និងសន្ទស្សន៍លេខ (`data.items[0].text`) ។ `__proto__`, `prototype` និង `constructor` ត្រូវបានច្រានចោលក្នុងសោ និងផ្លូវ។

## ការឆ្លើយតប

តម្លៃនៅ `responsePath` ក្លាយជាការឆ្លើយតបរបស់ជំនួយការ៖ ខ្សែអក្សរឆ្លងកាត់ តម្លៃ JSON ផ្សេងទៀតត្រូវបានដាក់សៀរៀល។ វាលដែលបាត់ ឬ `null` ឬតួដែលមិនមែនជា JSON ត្រឡប់ HTTP 502 ។ ស្ថានភាពកំហុសខាងលើត្រូវបានឆ្លងកាត់។ សម្រាប់ការផ្សាយអតិថិជន OmniRoute រង់ចាំការឆ្លើយតប JSON ទាំងមូល ហើយបន្ទាប់មកបញ្ចេញវាជាកំណាត់មាតិកាមួយ បូកនឹងកំណាត់បញ្ចប់។ នេះមិនមែនជាការស្ទ្រីមនិមិត្តសញ្ញាទេ។ ការហៅឧបករណ៍ និងវាលប្រើប្រាស់មិនត្រូវបានគូសផែនទីទេ។

## មិនដែលចាក់ឡើងវិញទេ។

សំណើអាជីវកម្មអាចមានផលប៉ះពាល់ ទោះបីវាបរាជ័យក៏ដោយ។ OmniRoute ដូច្នេះផ្ញើវាម្តង៖

- គ្មានការព្យាយាមដឹកជញ្ជូនឡើងវិញ និងគ្មានការបញ្ជូនបន្តដូចខាងក្រោម;
- គ្មានការព្យាយាមម្តងទៀតលើការតភ្ជាប់ផ្សេងទៀត (គណនីត្រលប់មកវិញ) — ការបរាជ័យត្រូវបានត្រឡប់ដូចដែលនៅហើយការតភ្ជាប់មិនត្រូវបាន cooled ចុះ;
- មិនមានការត្រលប់ទៅគោលដៅបន្សំបន្ទាប់ទេ សូម្បីតែការឆ្លើយតបទទេ ឬបរាជ័យក៏ដោយ។

សំណើអតិថិជនដោយឡែកពីគ្នា និងបន្ទះបញ្ចូលគ្នាដែលហៅទូរស័ព្ទទៅម៉ូដែលជាច្រើនយ៉ាងច្បាស់លាស់ នៅតែហៅចំណុចបញ្ចប់ដោយឯករាជ្យ។

## សាកល្បងថ្នាំង

រក្សាទុកការតភ្ជាប់, ការតភ្ជាប់** សាកល្បង** ប៊ូតុង និងការត្រួតពិនិត្យសុខភាពផ្ទៃខាងក្រោយមិនដែលហៅទៅចំណុចបញ្ចប់ទេ៖ ពួកគេគ្រាន់តែបញ្ជាក់សុពលភាពនៃការកំណត់ដែលបានរក្សាទុក ហើយរាយការណ៍ថាការតភ្ជាប់មិនអាចផ្ទៀងផ្ទាត់បាន។

`POST /api/provider-nodes/validate` ជាមួយ `"apiType": "custom-json"` និងវាលថ្នាំង (`baseUrl`, `apiKey`, `customJson`, `customHeaders` ស្រេចចិត្ត និង `modelId`) ផ្ញើសំណើពិតប្រាកដមួយដោយ `ping` ជាអត្ថបទអ្នកប្រើប្រាស់ចុងក្រោយបំផុត។ វាឆ្លើយតប `{ "valid": true }` ឬស្ថានភាពខាងលើ (មិនដែលរាងកាយខាងលើ) ។

## ការផ្ទុក

ការកំណត់រចនាសម្ព័ន្ធត្រូវបានរក្សាទុកក្នុង `provider_nodes.custom_json_config_json` (migration `240_provider_node_custom_json_config.sql`) ហើយចម្លងទៅក្នុង `providerSpecificData.customJson` នៃការតភ្ជាប់នីមួយៗ។

ការអនុវត្ត៖ `open-sse/utils/customJson.ts` (សុពលភាព និងគំរូ), `open-sse/executors/customJson.ts` (ប្រតិបត្តិករ), `open-sse/services/combo/noReplayLatch.ts` និង `src/sse/handlers/chat/responsePolicies.ts` (គ្មានការចាក់ឡើងវិញ)។
