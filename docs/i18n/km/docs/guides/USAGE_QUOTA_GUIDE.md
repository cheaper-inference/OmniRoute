## ទិដ្ឋភាពទូទៅ

រាល់សំណើដែលឆ្លងកាត់ OmniRoute បង្កើត **កំណត់ត្រាការប្រើប្រាស់** មួយ ដែលកត់ត្រា៖

- **អត្តសញ្ញាណ**៖ API key, provider, model និង combo មួយណាដែលត្រូវបានប្រើ
- **ថូខឹន**៖ ថូខឹន prompt, ថូខឹន completion, ថូខឹន cached និងចំនួនសរុប
- **ថ្លៃដើម**៖ ចំនួនទឹកប្រាក់ជា USD (គណនាពីទិន្នន័យតម្លៃ)
- **ពេលវេលា**៖ latency និង timestamp ចាប់ផ្តើម/បញ្ចប់
- **ស្ថានភាព**៖ ជោគជ័យ កំហុស ត្រូវបានកម្រិតអត្រា ជាដើម។

កំណត់ត្រាទាំងនេះត្រូវបានប្រមូលផ្តុំទៅជា **ទិន្នន័យវិភាគ** រក្សាទុកជា **snapshot កូតា** និងប្រើដើម្បីអនុវត្ត **ដែនកំណត់ថវិកាសម្រាប់ key នីមួយៗ**។

```
សំណើ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ការវិភាគ   កូតា   ការគិតថ្លៃ
                 (ផ្ទាំងគ្រប់គ្រង) (អនុវត្ត) (នាំចេញ)
```

## អ្វីដែលត្រូវបានកត់ត្រា

សេវា `usage.ts` កត់ត្រា **ព្រឹត្តិការណ៍ប្រើប្រាស់** សម្រាប់សំណើនីមួយៗ៖

| វាល                | ប្រភេទ  | ប្រភព                                                                                       |
| ------------------ | ------- | ------------------------------------------------------------------------------------------- |
| `id`               | string  | UUID ដែលបង្កើតនៅពេលកត់ត្រា                                                                  |
| `apiKeyId`         | string  | សោ API ដែលបានផ្តួចផ្តើមសំណើ                                                                 |
| `provider`         | string  | ID របស់អ្នកផ្តល់សេវា (openai, anthropic ជាដើម)                                              |
| `model`            | string  | ID របស់ម៉ូដែល (gpt-5, claude-opus-4-6 ជាដើម)                                                |
| `comboId`          | string? | ID របស់ combo ប្រសិនបើបានបញ្ជូនតាម combo                                                    |
| `promptTokens`     | number  | ពីការឆ្លើយតបរបស់សេវាខាងលើ                                                                   |
| `completionTokens` | number  | ពីការឆ្លើយតបរបស់សេវាខាងលើ                                                                   |
| `cachedTokens`     | number  | ថូខឹនដែលរកឃើញក្នុងឃ្លាំងសម្ងាត់ (ការរក្សាទុក prompt ក្នុងឃ្លាំងសម្ងាត់របស់ Anthropic ជាដើម) |
| `totalTokens`      | number  | prompt + ការបំពេញ                                                                           |
| `costUsd`          | number  | គណនាពីទិន្នន័យតម្លៃ                                                                         |
| `latencyMs`        | number  | រយៈពេលសំណើពីដើមដល់ចប់                                                                       |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                                  |
| `errorClass`       | string? | ថ្នាក់កំហុស ប្រសិនបើស្ថានភាព != success                                                     |
| `timestamp`        | string  | ISO 8601 UTC                                                                                |
| `metadata`         | object  | ទិន្នន័យផ្ទាល់ខ្លួនដែលបញ្ចូលដោយកម្មវិធីជំនួយ                                                |

### ប្រភពនៃថូខឹន

ថូខឹនត្រូវបានស្រង់ចេញពីការឆ្លើយតបរបស់អ្នកផ្តល់សេវាខាងលើ ក្នុង **កម្មវិធីដោះស្រាយការឆ្លើយតប**៖

```ts
// ពី open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

សម្រាប់អ្នកផ្តល់សេវាដែលមិនបញ្ជូនទិន្នន័យប្រើប្រាស់ត្រឡប់មកវិញ (អ្នកផ្តល់សេវា web-cookie មួយចំនួន) OmniRoute **ប៉ាន់ប្រមាណ** ថូខឹនដោយប្រើក្បួនប៉ាន់ស្មាន `~4 chars per token` (សូមមើល `open-sse/services/autoCombo/pipelineRouter.ts`)។

### ថូខឹនក្នុងឃ្លាំងសម្ងាត់

OmniRoute តាមដាន `cached_tokens` ដាច់ដោយឡែកពី `prompt_tokens` ពីព្រោះ៖

- ការរក្សាទុក prompt ក្នុងឃ្លាំងសម្ងាត់របស់ Anthropic គិតថ្លៃថូខឹនក្នុងឃ្លាំងសម្ងាត់ក្នុងអត្រាទាបជាង (10% នៃអត្រាធម្មតា)
- អ្នកផ្តល់សេវាមួយចំនួនបញ្ជូន `cache_read_input_tokens` ត្រឡប់មកវិញ ដែលគួរត្រូវបានកំណត់តម្លៃខុសគ្នា
- ការវិភាគអាចបង្ហាញ **អត្រារកឃើញក្នុងឃ្លាំងសម្ងាត់** = `cached_tokens / prompt_tokens`

### ការវិនិច្ឆ័យកម្រិតនៃការសរសេរចូលឃ្លាំងសម្ងាត់

ផ្ទាំងសុខភាពឃ្លាំងសម្ងាត់ prompt នៅលើផ្ទាំងគ្រប់គ្រងការវិភាគ បែងចែកការសរសេរចូលឃ្លាំងសម្ងាត់
រយៈពេល 5 នាទី និង 1 ម៉ោង ដែលរាយការណ៍ដោយអ្នកផ្តល់សេវា។ តម្លៃ
`usage.cache_creation.ephemeral_5m_input_tokens` និង
`usage.cache_creation.ephemeral_1h_input_tokens` របស់ Anthropic ត្រូវបានរក្សាទុកក្នុងអំឡុងពេលបម្លែងទិន្នន័យប្រើប្រាស់ទាំងបែបស្ទ្រីម និង
មិនមែនស្ទ្រីម ហើយត្រូវបានរក្សាទុកជាមួយសេចក្តីសង្ខេបកំណត់ហេតុការហៅ។ ចំនួនសរុបរួម
នៃការសរសេរចូលឃ្លាំងសម្ងាត់ មិនត្រូវបានបន្ថែមទៅក្រុមទាំងនោះជាលើកទីពីរទេ។

ការហៅដែលមានតែចំនួនរាប់ការសរសេររួម រួមទាំងកំណត់ត្រាចាស់ៗ មានកម្រិត
មិនស្គាល់។ ការបែងចែកដែលមានតែផ្នែកខ្លះ រក្សាចំណែកដែលមិនទាន់កំណត់ទុកជាមិនស្គាល់; ចំនួនរាប់ដែលមិនត្រឹមត្រូវ ឬ
ផ្ទុយគ្នាត្រូវបានសម្គាល់ ជំនួសឱ្យការកំណត់ TTL ឱ្យដោយស្ងាត់ៗ។ សញ្ញាសម្គាល់
TTL នៅខាងសំណើ មិនមែនជាភស្តុតាងនៃកម្រិតដែលត្រូវបានគិតថ្លៃទេ។

ការប៉ាន់ប្រមាណថ្លៃសរសេរសមមូល API របស់ផ្ទាំងនេះ គ្របដណ្តប់តែកម្រិតដែលបានរាយការណ៍ និងមានតម្លៃប៉ុណ្ណោះ មិនមែន
សំណើទាំងមូលទេ។ សម្រាប់តម្លៃម៉ូដែល Claude/Anthropic ដើម វាប្រើអត្រា 1.25 ដងនៃ
អត្រាធាតុចូល សម្រាប់ការសរសេររយៈពេល 5 នាទី និងពីរដងនៃអត្រាធាតុចូល សម្រាប់ការសរសេររយៈពេល 1 ម៉ោង។ តម្លៃដែលខ្វះ
ត្រូវបានចាត់ទុកថាមិនមាន មិនមែនសូន្យទេ។ តម្លៃត្រូវបានកត់ទុកនៅពេលការហៅថ្មីនីមួយៗត្រូវបានកត់ត្រា;

ការប៉ាន់ប្រមាណសមមូល API ដោយមិនចាំបាច់ចំណាយចំនួននោះជាសាច់ប្រាក់ ឬកាត់ពី

| claude-opus-4-6   | $15.00      | $75.00      | $1.50              |

រូបមន្តគណនាថ្លៃចំណាយ (`src/lib/usage/costCalculator.ts`)៖

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

## ការអនុវត្តកូតា

កូតាសម្រាប់សោ API នីមួយៗត្រូវបានអនុវត្តនៅពីរកន្លែង៖

1. **កម្រិតព្រមាន** (`quotaWarnAt`)៖ ការព្រមានលើផ្ទាំងគ្រប់គ្រង នៅពេលការប្រើប្រាស់លើសកម្រិតកំណត់
2. **កម្រិតរឹង** (`quotaLimit`)៖ សំណើត្រូវបានបដិសេធជាមួយ HTTP 429 នៅពេលលើសកម្រិត

### ការកំណត់រចនាសម្ព័ន្ធ

```ts
// សម្រាប់សោ API នីមួយៗ
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — បង្ហាញការព្រមាន
  quotaLimit: 10_00,    // $10.00 — បញ្ឈប់ជាដាច់ខាត
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### លំហូរនៃការអនុវត្ត

```
សំណើ ──▶ quotaCheck()
              │
              ├── នៅក្នុងកម្រិត?  ──▶ អនុញ្ញាត
              │
              └── លើសកម្រិត?  ──▶ 429 សំណើច្រើនពេក
                                   ជាមួយបឋមកថា Retry-After
```

### រូបថតស្ថានភាពកូតា

តារាង `quotaSnapshots` រក្សាទុក **ស្ថានភាពកូតាក្នុងអតីតកាល** សម្រាប់ការវិភាគនិន្នាការ៖

| វាល | សេចក្តីពិពណ៌នា |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | សោដែលកំពុងត្រូវបានតាមដាន |
| `window` | "ថ្ងៃ" | "សប្តាហ៍" | "ខែ" |
| `used` | ចំណាយដែលបានប្រើក្នុងរយៈពេលនេះ (សេន) |
| `limit` | កម្រិតកំណត់ (សេន) |
| `resetAt` | ពេលដែលរយៈពេលត្រូវបានកំណត់ឡើងវិញ |
| `createdAt` | ពេលដែលរូបថតស្ថានភាពត្រូវបានថត |

រូបថតស្ថានភាពត្រូវបានថត **នៅរាល់សំណើ** ដែលមានចំណាយ > 0 ហើយត្រូវបានប្រើដើម្បី៖

- បង្ហាញរបារវឌ្ឍនភាពកូតានៅលើផ្ទាំងគ្រប់គ្រង
- បង្ហាញគំនូសតាងនិន្នាការកូតារយៈពេល 30 ថ្ងៃ
- បង្កការជូនដំណឹងនៅពេលការប្រើប្រាស់ជិតដល់កម្រិតកំណត់

## ការរក្សាទុក និងការសម្អាត

ទិន្នន័យការប្រើប្រាស់កើនឡើង ~1-10KB ក្នុងមួយសំណើ។ នៅពេលប្រើប្រាស់ក្នុងទ្រង់ទ្រាយធំ បរិមាណនេះអាចមានទំហំច្រើន។

### ការកំណត់ការរក្សាទុក

ការរក្សាទុកប្រវត្តិការប្រើប្រាស់ត្រូវបានកំណត់តាមរយៈការកំណត់មូលដ្ឋានទិន្នន័យនៅក្នុង UI ឬតាមរយៈ `/api/settings/database`។

តាមលំនាំដើម ប្រវត្តិការប្រើប្រាស់ត្រូវបានរក្សាទុករយៈពេល **90 ថ្ងៃ**។

### ការសម្អាត

កំណត់ត្រាចាស់ៗត្រូវបានសម្អាតដោយ `src/lib/db/cleanup.ts`៖

- ត្រូវបានដំណើរការដោយដំណើរការ cron នៅផ្ទៃខាងក្រោយ
- លុបកំណត់ត្រាចេញពី `usage_history` ដែលចាស់ជាងរយៈពេលរក្សាទុកដែលបានកំណត់ក្នុង `usageHistory`

### ការប៉ាន់ស្មានទំហំផ្ទុក

| អត្រាសំណើ         | ទំហំផ្ទុកសម្រាប់ 30 ថ្ងៃ | ទំហំផ្ទុកសម្រាប់ 90 ថ្ងៃ |
| ----------------- | ------------------------ | ------------------------ |
| 100 សំណើ/ថ្ងៃ     | ~3MB                     | ~9MB                     |
| 1,000 សំណើ/ថ្ងៃ   | ~30MB                    | ~90MB                    |
| 10,000 សំណើ/ថ្ងៃ  | ~300MB                   | ~900MB                   |
| 100,000 សំណើ/ថ្ងៃ | ~3GB                     | ~9GB                     |

សម្រាប់ចរាចរណ៍ខ្ពស់ខ្លាំង សូមពិចារណា៖

- កាត់បន្ថយរយៈពេលរក្សាទុកតាមរយៈការកំណត់មូលដ្ឋានទិន្នន័យ
- ប្រើ `aggregated_metrics` ជំនួសឱ្យកំណត់ត្រាដើម (សម្រាប់តែការវិភាគប៉ុណ្ណោះ)

## គន្លឹះបង្កើនប្រសិទ្ធភាពចំណាយ

### 1. ប្រើម៉ូដែលដែលសមស្រប

```bash
# ចម្លើយរហ័ស — ប្រើជម្រើសថោក + លឿន
curl -d '{"model":"auto/fast","messages":[...]}'

# កិច្ចការស្មុគស្មាញ — ប្រើជម្រើសគុណភាពខ្ពស់
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. បើកការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់

ការរក្សាទុក prompt ក្នុងឃ្លាំងសម្ងាត់របស់ Anthropic សន្សំបាន **90% លើបរិបទដែលប្រើដដែលៗ**៖

```ts
// ការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ដំណើរការដោយស្វ័យប្រវត្តិ — គ្រាន់តែបញ្ចូល system prompt ធំដដែល
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // នឹងត្រូវបានរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ដោយស្វ័យប្រវត្តិ
  messages: [{ role: "user", content: "..." }],
});
```

### 3. ប្រើការបង្ហាប់

ការបង្ហាប់ RTK + Caveman សន្សំបាន **15-95% លើសម័យដែលប្រើឧបករណ៍ច្រើន**៖

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. កំណត់កូតាសម្រាប់សោនីមួយៗ

កំណត់ `quotaLimit` ជានិច្ច ដើម្បីការពារការចំណាយដែលកើនឡើងដោយមិនអាចគ្រប់គ្រងបាន៖

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // កម្រិតអតិបរមា $10/ខែ
```

### 5. ពិនិត្យអ្នកប្រើប្រាស់ដែលចំណាយច្រើនបំផុត

ប្រើផ្ទាំងគ្រប់គ្រង ឬ **`/api/usage/analytics`** ដើម្បីដាក់ជាក្រុមតាមសោ API និងតម្រៀបតាមចំណាយ៖

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## ការដោះស្រាយបញ្ហា

### "ចំណាយខ្ពស់ជាងការរំពឹងទុក"

1. ពិនិត្យ **`/api/usage/analytics?groupBy=model`** — ស្វែងរកម៉ូដែលដែលមានតម្លៃខ្ពស់
2. ពិនិត្យ **`/api/usage/analytics?groupBy=apiKey`** — ស្វែងរកអ្នកប្រើប្រាស់ដែលប្រើច្រើន
3. ផ្ទៀងផ្ទាត់ថាទិន្នន័យតម្លៃមានបច្ចុប្បន្នភាព៖ `POST /api/pricing/sync`

### "បាត់កំណត់ត្រា"

- ពិនិត្យការកំណត់រយៈពេលរក្សាទុក DB នៅក្រោម ផ្ទាំងគ្រប់គ្រង → មូលដ្ឋានទិន្នន័យ → ការសម្អាត — កំណត់ត្រាចាស់ត្រូវបានលុបដោយកិច្ចការសម្អាតតាមកាលកំណត់ (`src/lib/db/cleanup.ts`)
- ពិនិត្យរកកំហុសក្នុង `src/lib/db/usage*.ts` — ការបរាជ័យក្នុងការសរសេរចូល DB ត្រូវបានកត់ត្រា ប៉ុន្តែមិនត្រូវបានបង្ហាញទេ
- ផ្ទៀងផ្ទាត់ថាសំណើពិតជាបានទៅដល់ `chatCore` — ពិនិត្យការកំណត់ផ្លូវ combo

### "កូតាមិនត្រូវបានអនុវត្ត"

- ពិនិត្យការកំណត់ `quotaLimit` របស់សោ
- ផ្ទៀងផ្ទាត់ថា `quotaWindow` ត្រូវបានកំណត់ត្រឹមត្រូវ
- ស្វែងរកកំណត់ត្រា `quotaSnapshots` — កំណត់ត្រាទាំងនេះគួរត្រូវបានបង្កើតនៅរាល់សំណើ
