### ការផ្សំ Category × Tier (`auto/<category>:<tier>`)

suffix បែប OpenRouter បំបែក **ប្រភេទផ្លូវ** (category) ចេញពី **របៀបបង្កើនប្រសិទ្ធភាពរបស់វា** (tier) ដូច្នេះអ្នកអាចផ្សំពួកវាបានដោយសេរី (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`)៖

- **Category** (ត្រងបណ្តុំ candidate តាមសមត្ថភាព)៖ `coding` · `reasoning` · `vision` · `chat` · `multimodal`។ `vision`/`multimodal` រក្សាទុក model ដែលគាំទ្រ vision; `reasoning` រក្សាទុក model សម្រាប់ reasoning/thinking។
- **Tier** (ជ្រើសរើសទម្ងន់ដាក់ពិន្ទុ / តម្រងបណ្តុំ)៖ `fast` (ដាក់ឱ្យប្រើបានរហ័ស) · `cheap` (alias `floor` ដែលសន្សំថ្លៃដើម) · `reliable` (សុខភាព circuit-breaker + ស្ថិរភាព latency) · `free` / `pro` (ត្រងបណ្តុំតាម tier របស់ model តាមរយៈ `classifyTier` — free-tier ទល់នឹង premium)។

| ឧទាហរណ៍                | ត្រូវបានដោះស្រាយទៅជា                                                  |
| ---------------------- | --------------------------------------------------------------------- |
| `auto/coding:fast`     | បណ្តុំ coding និងទម្ងន់ latency ទាប                                   |
| `auto/coding:cheap`    | បណ្តុំ coding ដែលបង្កើនប្រសិទ្ធភាពថ្លៃដើម (alias `auto/coding:floor`) |
| `auto/reasoning:pro`   | តែ model សម្រាប់ reasoning/thinking និង premium tier                  |
| `auto/vision`          | model ដែលគាំទ្រ vision (គ្មាន tier → ទម្ងន់មានតុល្យភាព)               |
| `auto/multimodal:free` | model ដែលគាំទ្រ multimodal និងមានតែ free tier                         |

`auto/<category>[:<tier>]` ដែលត្រឹមត្រូវណាមួយត្រូវបានដោះស្រាយតាមតម្រូវការ; សំណុំរងដែលបានជ្រើសរើសដោយប្រុងប្រយ័ត្នត្រូវបានបង្ហាញនៅក្នុង `/v1/models` និង dashboard (`AUTO_SUFFIX_VARIANTS` ក្នុង `open-sse/services/autoCombo/builtinCatalog.ts`)។ ការត្រងគឺ **fail-open** — ប្រសិនបើលក្ខខណ្ឌមួយមិនត្រូវនឹង model ដែលបានភ្ជាប់ណាមួយទេ បណ្តុំពេញលេញនឹងត្រូវបានប្រើ ដើម្បីកុំឱ្យការកំណត់ផ្លូវខូច។ core scorer (`combo.ts`) មិនត្រូវបានផ្លាស់ប្តូរទេ; តម្រង category/tier ត្រូវបានអនុវត្តក្នុង `buildAutoCandidates`។

> **ទិន្នន័យឆ្លាតវៃរបស់ model ជាក់ស្តែង៖** ភាពសមស្របនៃការកំណត់ផ្លូវដោយស្វ័យប្រវត្តិ ទទួលព័ត៌មានពីចំណាត់ថ្នាក់ **Arena ELO** ជាក់ស្តែង + ទិន្នន័យ tier របស់ **models.dev** នៅពេល flag `ARENA_ELO_SYNC_ENABLED` បើក (បើមិនដូច្នោះទេ នឹងត្រឡប់ទៅប្រើផែនទី fitness ថេរ)។

**របៀបប្រើ៖**

```bash
# IDE ឬឧបករណ៍ CLI ណាមួយដែលគាំទ្រទម្រង់ OpenAI
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ក្នុងកូដ/ការកំណត់រចនាសម្ព័ន្ធរបស់អ្នក កំណត់ model ទៅជា៖
model: "auto"                 # លំនាំដើមមានតុល្យភាព
model: "auto/coding"          # ល្អបំផុតសម្រាប់កិច្ចការសរសេរកូដ
model: "auto/fast"            # ជម្រើសលឿនបំផុតដែលអាចប្រើបាន
model: "auto/cheap"           # ថោកបំផុតក្នុងមួយ token
```

**អ្វីដែលកើតឡើង៖**

1. OmniRoute រកឃើញ `auto/` prefix ក្នុង `src/sse/handlers/chat.ts`
2. ស្វែងរក **ការតភ្ជាប់ provider សកម្ម** ទាំងអស់ពី database
3. ត្រងយកការតភ្ជាប់ដែលមាន credential ត្រឹមត្រូវ (API key ឬ OAuth token)
4. កំណត់ model ក្នុងមួយការតភ្ជាប់ (`connection.defaultModel` ឬ model ដំបូងរបស់ provider)
5. បង្កើត **virtual combo** ក្នុង memory (មិនត្រូវបានរក្សាទុកក្នុង DB)
6. កំណត់ផ្លូវដោយប្រើប្រវត្តិរូបទម្ងន់របស់វ៉ារ្យ៉ង់ដែលបានជ្រើសរើស + យុទ្ធសាស្ត្រ LKGP

**លក្ខណៈសម្បត្តិសំខាន់ៗ៖**

- ✅ **ដំណើរការជានិច្ច៖** មិនចាំបាច់មាន toggle មិនចាំបាច់បង្កើត combo និងមិនចាំបាច់កំណត់រចនាសម្ព័ន្ធ
- ✅ **Dynamic៖** ឆ្លុះបញ្ចាំង provider ដែលបានភ្ជាប់បច្ចុប្បន្នដោយស្វ័យប្រវត្តិ
- ✅ **ភាពជាប់លាប់នៃ session៖** LKGP ធានាថា provider ដែលជោគជ័យចុងក្រោយត្រូវបានផ្តល់អាទិភាព
- ✅ **គាំទ្រគណនីច្រើន៖** ការតភ្ជាប់ provider នីមួយៗក្លាយជា candidate ដាច់ដោយឡែក
- ✅ **មិនសរសេរទៅ DB៖** Virtual combo មានតែសម្រាប់ request ប៉ុណ្ណោះ ដោយគ្មានបន្ទុកលើសពីការរក្សាទុក

### ការគ្រប់គ្រង candidate តាម key នីមួយៗ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = suffix ដែលនៅបន្ទាប់ពី `auto/` ឬ
ពាក្យ `auto` ផ្ទាល់សម្រាប់ channel មូលដ្ឋាន) គឺជា endpoint **បានតែអាន** ដែលរាយបញ្ជី
បណ្តុំ candidate បច្ចុប្បន្នរបស់ channel `auto/*` ដោយភ្ជាប់ជាមួយស្ថានភាពអាចចូលដល់បានជាក់ស្តែង និងប្រើឡើងវិញនូវ
ការអាន resilience ដែលមានស្រាប់ (មិនដែលអាន breaker `state` ដោយផ្ទាល់ទេ)៖

## ការហៅ Custom Combo ពី Client

1. ផ្គូផ្គងឈ្មោះ combo ដូចគ្នាបេះបិទ (`model: "my-combo"`),
2. prefix `combo/<name>` (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)។

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

### `weighted` អត្ថន័យ

`weighted` គឺមួយ។**ការចាប់ឆ្នោតចៃដន្យតាមសមាមាត្រតាមសំណើ** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`) មិនមែនជាឧបករណ៍ស្មើ៖

- សំណើនីមួយៗគូរ **មួយ។** ជំហានជាមួយនឹងប្រូបាប៊ីលីតេ `weight / totalWeight`; ជំហានដែលនៅសេសសល់ត្រូវបានបញ្ជាដោយទម្ងន់ចុះក្រោមជាខ្សែសង្វាក់ថយក្រោយសម្រាប់សំណើនោះ។
- ជំហានដែលទម្ងន់គឺ `0` (ឬបាត់) គឺ**មិនដែលគូរ** ខណៈពេលដែលជំហានផ្សេងទៀតមានទម្ងន់ > 0 — វាអាចគ្រាន់តែជាការថយក្រោយបន្ទាប់ពីជំហានដែលបានគូរបរាជ័យ។ លុះត្រាតែ**ទាំងអស់។** ទម្ងន់គឺ 0 តើការជ្រើសរើសក្លាយជាឯកសណ្ឋាន។
- ជំហានដែលគោលដៅរបស់ពួកគេគឺមិនអាចប្រើបានទេ ឧបករណ៍បំលែងសៀគ្វីអ្នកផ្តល់សេវា — `OPEN` ភាពត្រជាក់នៃការតភ្ជាប់ ការចាក់សោម៉ូដែល — ត្រូវបានយកចេញពីការចាប់ឆ្នោតមុនពេលវាកើតឡើង (`open-sse/services/combo/targetResolution.ts`) ដូច្នេះជំហានដែលមានសុខភាពល្អតែមួយអាចឈ្នះរាល់សំណើ។
- `stickyWeightedLimit` (ការកំណត់រចនាសម្ព័ន្ធបន្សំ, លំនាំដើម `1` = បិទ) កំណត់ជំហានដែលបានគូរសម្រាប់ជោគជ័យជាបន្តបន្ទាប់គ្នាជាច្រើន មុនពេលគូរឡើងវិញ។

សម្រាប់ការបង្វិលដ៏តឹងរឹង ប្រើ `round-robin`; ទម្ងន់ស្មើគ្នានៅលើ `weighted` ផ្តល់ឱ្យ — ស្ថិតិមិនតឹងរឹង — សមតុល្យ។

### `round-robin` បណ្តុំស្អិត និងការពង្រីកគណនី

Round-robin ត្រូវបានដាក់ជាបាច់ មិនមែនជាការស្នើសុំតែមួយជំហានទេ៖

- `stickyRoundRobinLimit` (កំណត់រចនាសម្ព័ន្ធបន្សំ បន្ទាប់មក `comboStickyRoundRobinLimit` បន្ទាប់មក `settings.stickyRoundRobinLimit` លំនាំដើម **៣** ) រក្សាគោលដៅដូចគ្នាសម្រាប់ជោគជ័យជាប់ៗគ្នាជាច្រើន មុនពេលបង្វិល។ កំណត់ការបដិសេធបន្សំទៅ `1` សម្រាប់ការបង្វិលសំណើមួយ។ កម្មវិធីនិពន្ធបន្សំបង្ហាញពីតម្លៃដ៏មានប្រសិទ្ធភាព និងស្រទាប់ណាមួយដែលវាបានមកពី។
- `connectionAwareExpansion` (កំណត់រចនាសម្ព័ន្ធបន្សំ បន្ទាប់មកការកំណត់ លំនាំដើម **មិនពិត** ) ពង្រីកជំហានកម្រិតអ្នកផ្តល់សេវានីមួយៗទៅក្នុងគោលដៅនីមួយៗមុនពេលបង្វិល។ យុទ្ធសាស្ត្រក្រុម-B (អាទិភាព ទម្ងន់ ជុំ-រ៉ូប៊ីន ចៃដន្យ p2c ប្រើតិចបំផុត បង្កើនប្រសិទ្ធភាពតម្លៃ lkgp បំពេញដំបូង តឹងរ៉ឹងចៃដន្យ ធ្វើឱ្យប្រសើរបរិបទ ធ្វើឱ្យប្រសើរឃ្លាំងសម្ងាត់ ការបញ្ជូនបន្តបរិបទ ការលាយបញ្ចូលគ្នា បំពង់បង្ហូរប្រេង) រក្សាទិដ្ឋភាពកម្រិតអ្នកផ្តល់សេវារហូតដល់វាបើក។ កម្មវិធីនិពន្ធបន្សំបង្ហាញពីមរតក / បើក / បិទ; មរតកប្រើលំនាំដើមសកល (បិទ) ។

## រោងចក្រ Auto-Combo និម្មិត

ម៉ាស៊ីន Auto Combo មិនតម្រូវឱ្យមាន combo ដែលបានកំណត់ជាមុនទេ។ ផ្ទុយទៅវិញ `open-sse/services/autoCombo/virtualFactory.ts` បង្កើត candidate ភ្លាមៗតាមតម្រូវការ៖

1. ទាញយក `getProviderConnections({ isActive: true })` (connection ទាំងអស់ដែលបានបើកដំណើរការ)
2. ច្រោះយកតែ connection ដែលមាន credential ត្រឹមត្រូវ (API key ឬ OAuth token ដែលមិនទាន់ផុតកំណត់ តាមរយៈ `hasUsableOAuthToken()`)
3. ផ្ទៀងផ្ទាត់ជាមួយ `getProviderRegistry()` សម្រាប់ភាពអាចប្រើបាននៃ model និងតម្លៃ
4. សម្រាប់ tuple នីមួយៗ `(provider, model, connection)` បង្កើត `VirtualAutoComboCandidate`
5. ជ្រើសរើស `connection.defaultModel` (ឬ model ដំបូងរបស់ registry) ជាគោលដៅ dispatch
6. ដាក់ពិន្ទុ candidate នីមួយៗដោយប្រើ `scorePool()` ដែលមាន 16 កត្តា និងកញ្ចប់ weight របស់ variant
7. ត្រឡប់ `AutoComboConfig` ក្នុង memory ដែលទទួលបានសម្រាប់ `handleComboChat()` — មិនដែលរក្សាទុកទៅ DB ទេ

នេះមានន័យថា **ការបន្ថែម provider ថ្មីដែលបានបើក `auto/*` នឹងពង្រីក candidate pool ដោយស្វ័យប្រវត្តិ** — មិនចាំបាច់កែសម្រួល combo ដោយដៃទេ។ Virtual combo ត្រូវបានបង្កើតឡើងវិញសម្រាប់ request នីមួយៗ ដូច្នេះ connection ដែលទើបបន្ថែមថ្មី ឬទើបមានស្ថានភាពល្អឡើងវិញ នឹងត្រូវបានយកមកប្រើភ្លាមៗ។

## ការស្ដារឡើងវិញដោយស្វ័យប្រវត្តិ

- **ការដកចេញបណ្ដោះអាសន្ន**៖ ពិន្ទុ < 0.2 → ដកចេញរយៈពេល 5 នាទី (progressive backoff អតិបរមា 30 នាទី)
- **ការយល់ដឹងអំពី circuit breaker**៖ OPEN → ដកចេញដោយស្វ័យប្រវត្តិ; HALF_OPEN → request សាកល្បង
- **Incident mode**៖ >50% OPEN → បិទ exploration និងបង្កើនស្ថិរភាពឱ្យដល់អតិបរមា
- **ការស្ដារឡើងវិញក្រោយ cooldown**៖ បន្ទាប់ពីការដកចេញ request ដំបូងគឺជា "probe" ដែលមាន timeout តិចជាងមុន

## Bandit Exploration

5% នៃ request (អាចកំណត់បាន) ត្រូវបាន route ទៅ provider ចៃដន្យសម្រាប់ exploration។ វាត្រូវបានបិទនៅក្នុង incident mode។

## API

មិនមាន **endpoint `POST /api/combos/auto` ដាច់ដោយឡែកទេ** — Auto-Combo ត្រូវបានប្រើតាមពីរវិធី៖

1. **មិនត្រូវការការកំណត់រចនាសម្ព័ន្ធ (បានណែនាំ)៖** ផ្ញើសំណើ chat completion ណាមួយជាមួយ `model: "auto"` ឬ `model: "auto/<variant>"`។ virtual factory នឹងបង្កើត combo សម្រាប់សំណើនីមួយៗ — មិនត្រូវការការរក្សាទុក និងមិនត្រូវការការហៅ API ទេ។

2. **Combo ដែលបានរក្សាទុកជាមួយ `strategy: "auto"`៖** បង្កើត combo ធម្មតាតាមរយៈ `POST /api/combos` ហើយកំណត់ `strategy: "auto"` រួមជាមួយ `config.auto.weights` / `config.auto.candidatePool`។ scoring engine ដូចគ្នានឹងត្រូវបានប្រើ ហើយ combo ត្រូវបានរក្សាទុកក្នុង `combos` និងអាចប្រើឡើងវិញតាម ID។

### យុទ្ធសាស្ត្រ Auto router

Combo `strategy: "auto"` ដែលបានរក្សាទុកអាចកំណត់ `config.routerStrategy` (ឬ
`config.auto.routerStrategy` ចាស់) ទៅជាមួយក្នុងចំណោម៖

- `rules` — weighted scoring លំនាំដើម
- `score` — ជ្រើសរើស configured weighted score ដែលខ្ពស់បំផុត។ ក្នុងករណីពិន្ទុស្មើគ្នាទាំងស្រុង លំដាប់
  candidate ដែលបានកំណត់នឹងត្រូវបានរក្សាទុក ហើយ `explorationRate` ដែលមានស្រាប់នឹងយកគំរូពី ranked pool ទាំងមូល។
- `cost` / `eco` — provider ដែលមានស្ថានភាពល្អ និងតម្លៃថោកបំផុត
- `latency` / `fast` — latency p95 ទាបបំផុតជាមួយ reliability penalty
- `sla-aware` / `sla` — ផ្តល់អាទិភាពដល់ candidate ដែលបំពេញតាម latency p95, error-rate និង
  cost SLO ជាជម្រើស
- `lkgp` — provider ដែលបានដឹងថាដំណើរការល្អចុងក្រោយមុនគេ
- `nadir` — ស្នើឱ្យ decision API របស់ [Nadir](https://getnadir.com) សម្រេចថា model មួយណាក្នុង pool ដែល
  prompt ត្រូវការ។ វាជាមុខងារ opt-in និង fail-open ទៅ `rules`

### យុទ្ធសាស្ត្រ Router លម្អិត

Auto-combo engine ផ្តល់ implementation **RouterStrategy** ដែលអាចដោតបន្ថែមបានចំនួន 7 ដែល
អ្នកអាចប្តូរតាមរយៈ `config.routerStrategy` (ឬ `config.auto.routerStrategy` ចាស់)។
យុទ្ធសាស្ត្រនីមួយៗជ្រើសរើស provider មួយពី candidate pool ដោយផ្អែកលើ `RoutingContext`
(ប្រភេទ task, សញ្ញាបង្ហាញ tool/vision, ការប៉ាន់ស្មាន token, គោលការណ៍ SLA ជាជម្រើស និង
provider ដែលបានដឹងថាដំណើរការល្អចុងក្រោយជាជម្រើស)។

#### 1. `rules` (លំនាំដើម) — weighted scoring ដែលមាន 16 កត្តា

រុំជុំវិញ scoring engine ដែលមានស្រាប់។ ត្រង candidate របស់ circuit-breaker ដែលមានស្ថានភាព `OPEN`
ចេញ បន្ទាប់មកដំណើរការ `scorePool()` ជាមួយប្រភេទ task បច្ចុប្បន្ន និង `getTaskFitness()`
ដោយជ្រើសរើស provider ដែលមានពិន្ទុខ្ពស់បំផុត។

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ពេលដែលគួរប្រើ**៖ លំនាំដើម។ ប្រើនៅពេលដែលអ្នកចង់បានតុល្យភាពរវាង signal ទាំងអស់។

**Alias**៖ `rules` (គ្មាន alias)

---

#### 2. `cost` / `eco` — provider ដែលមានស្ថានភាពល្អ និងតម្លៃថោកបំផុត

តម្រៀប candidate pool តាម `costPer1MTokens` (ពីតូចទៅធំ) ហើយជ្រើសរើសតម្លៃថោកបំផុត។
ត្រង candidate ដែលមានស្ថានភាព `OPEN` ចេញជាមុន។

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ពេលដែលគួរប្រើ**៖ Workload ដែលយកចិត្តទុកដាក់លើថ្លៃចំណាយ, batch processing ឬ background job។

**Alias**៖ `cost`, `eco`

---

#### 3. `latency` / `fast` — latency p95 ទាបបំផុតជាមួយ reliability penalty

តម្រៀបតាម `p95LatencyMs + (errorRate * 1000)`។ Error-rate penalty ធានាថា
provider ដែលមិនគួរឱ្យទុកចិត្តត្រូវបានដាក់ចំណាត់ថ្នាក់ទាបជាង បើទោះបីជា latency ធម្មតារបស់ពួកវាទាបក៏ដោយ។

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ពេលដែលគួរប្រើ**៖ Workload ដែលយកចិត្តទុកដាក់លើ latency ដូចជា chat ក្នុងពេលជាក់ស្តែង, autocomplete ឬ
ជំនួយការ coding អន្តរកម្ម។

**Alias**៖ `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ការអនុលោមតាម SLO សម្រាប់ latency/error/cost

ដាក់ពិន្ទុឱ្យ candidate នីមួយៗដោយផ្អែកលើកម្រិតដែលវាបំពេញតាមគោលការណ៍ SLO ដែលបានកំណត់៖

| កត្តា           | ទម្ងន់ | រូបមន្ត                                                       |
| --------------- | ------ | ------------------------------------------------------------- |
| ពិន្ទុភាពយឺត    | 35%    | `threshold / max(value, ε)`                                   |
| ពិន្ទុកំហុស     | 35%    | `threshold / max(value, ε)`                                   |
| ពិន្ទុសុខភាព    | 15%    | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)             |
| ពិន្ទុថ្លៃចំណាយ | 10%    | `threshold / max(value, ε)` ឬតម្លៃច្រាសដែលបានធ្វើប្រក្រតីកម្ម |
| ពិន្ទុស្ថិរភាព  | 5%     | គម្លាតស្តង់ដារនៃភាពយឺតដែលបានធ្វើប្រក្រតីកម្មបញ្ច្រាស          |

នៅពេល `hardConstraints: true` បេក្ខភាពត្រូវបានតម្រៀបជាចម្បងតាម **ពិន្ទុនៃការបំពាន**
(ថាតើពួកវាលើសពី SLO ណាមួយប៉ុនណា) បន្ទាប់មកតាមពិន្ទុសមាស។ បើមិនដូច្នោះទេ វាប្រើតែ
ពិន្ទុសមាសប៉ុណ្ណោះ។

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ដាក់ពិន្ទុបេក្ខភាពនីមួយៗធៀបនឹងគោលការណ៍៖ { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**វាល SLA** (កំណត់នៅលើការកំណត់រចនាសម្ព័ន្ធ combo)៖

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ពេលដែលគួរប្រើ**៖ បន្ទុកការងារ production ដែលមានកម្រិតកំណត់តឹងរ៉ឹងលើភាពយឺត អត្រាកំហុស ឬថវិកាចំណាយ។

**ឈ្មោះហៅក្រៅ**៖ `sla-aware`, `sla`

---

#### 5. `lkgp` — អ្នកផ្តល់សេវាដែលដំណើរការល្អចុងក្រោយជាមុន

សាកល្បង **អ្នកផ្តល់សេវាដែលដំណើរការល្អចុងក្រោយ** (ប្រសិនបើបានកំណត់) ជាមុន បន្ទាប់មកត្រឡប់ទៅប្រើ
យុទ្ធសាស្ត្រ `rules`។ វាមានប្រយោជន៍សម្រាប់ការរក្សាភាពជាប់លាប់នៃសម័យ — អ្នកផ្តល់សេវាដដែលគ្រប់គ្រង
សំណើបន្តនៅក្នុងការសន្ទនា។

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // ត្រឡប់ទៅប្រើយុទ្ធសាស្ត្រ rules
    return getStrategy("rules").select(pool, context);
  }
}
```

**ពេលដែលគួរប្រើ**៖ ការសន្ទនាច្រើនវេន ដែលអ្នកចង់ឱ្យអ្នកផ្តល់សេវាដដែលគ្រប់គ្រង
សំណើបន្ត (ឧ. សម្រាប់ caching ភាពបន្តនៃបរិបទ ឬភាពស៊ីគ្នានៃតម្លៃ)។

**ឈ្មោះហៅក្រៅ**៖ `lkgp` (គ្មានឈ្មោះហៅក្រៅ)

---

#### 6. `nadir` — ជម្រើសម៉ូដែលដែលយល់ដឹងអំពី prompt តាមរយៈ Nadir

គ្រប់យុទ្ធសាស្ត្រខាងលើចាត់ចំណាត់ថ្នាក់បេក្ខភាពតាម telemetry របស់វាផ្ទាល់ ហើយគ្មានយុទ្ធសាស្ត្រណាមួយអាន
សំណើនោះទេ។ `nadir` ផ្ញើវេនចុងក្រោយរបស់អ្នកប្រើ រួមជាមួយអត្តសញ្ញាណម៉ូដែលរបស់ pool ទៅកាន់
API សម្រេចចិត្តរបស់ [Nadir](https://getnadir.com) (`POST /v1/bucket`) ហើយបញ្ជូនទៅម៉ូដែល
ដែល Nadir ជ្រើសរើសពីម៉ឺនុយនោះ (`simple` → ម៉ូដែលសមត្ថភាពគ្រប់គ្រាន់ដែលថោកបំផុត, `complex` → ម៉ូដែល
ជួរមុខ)។ ការតភ្ជាប់ដែលបម្រើម៉ូដែលនោះនៅតែត្រូវបានជ្រើសរើសដោយ `rules` ដូច្នេះកូតា
សុខភាព និងថ្លៃចំណាយនៅតែជាកត្តាសម្រេចថាគណនីណាត្រូវប្រើ។

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` និង `OMNIROUTE_NADIR_BASE_URL` គឺជាតម្លៃជំនួសពី env សម្រាប់ខ្សែអក្សរទាំងពីរ។
`baseUrl` ត្រូវការតែសម្រាប់ Nadir ដែលបង្ហោះដោយខ្លួនឯងប៉ុណ្ណោះ (អាចមាន `/v1` នៅខាងចុងបាន)។
ការហៅដោយគ្មាន key នឹងចូលទៅកាន់កម្រិតអនាមិករបស់ Nadir ដែលត្រូវបានកំណត់អត្រាតាម IP។ ជាមួយ key
([បង្កើតមួយ](https://app.getnadir.com/dashboard/api-keys)) រាល់ការសម្រេចចិត្តនឹងត្រូវបាន
កត់ត្រាទៅក្នុងផ្ទាំងគ្រប់គ្រង Nadir របស់អ្នក។ ការដំឡើង និងការផ្ទៀងផ្ទាត់ពេញលេញ៖
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/)។

អ្វីដែលត្រូវបានផ្ញើចេញ៖ អត្ថបទសារចុងក្រោយរបស់អ្នកប្រើ (16k តួអក្សរដំបូង) អត្តសញ្ញាណម៉ូដែល
បេក្ខភាព និងស្លាកឆានែល `source: "omniroute"`។ គ្មាន system prompt ប្រវត្តិ tools ឬ
headers ឡើយ។

ឥរិយាបថពេលបរាជ័យគឺ fail-open៖ timeout (លំនាំដើម 2000 ms), ការឆ្លើយតបមិនមែន 2xx, host ដែលមិនអាច
ចូលដំណើរការបាន, ការឆ្លើយតបមិនត្រឹមត្រូវ ឬជម្រើសដែលនៅក្រៅ pool នឹងត្រឡប់ទៅការសម្រេចចិត្តរបស់ `rules`
ហើយហេតុផលនឹងត្រូវដាក់បុព្វបទ `NadirStrategy: fallback (…)`។ បន្ទាប់ពីការហៅបរាជ័យ យុទ្ធសាស្ត្រ
នឹងរំលងបណ្ដាញរយៈពេល 30 s ដូច្នេះការដាច់សេវាមួយនឹងចំណាយ timeout មួយក្នុងរៀងរាល់ 30 s ជំនួសឱ្យ
មួយក្នុងមួយសំណើ។ ព្រឹត្តិការណ៍បញ្ជូនផ្លូវរាយការណ៍ `strategy: "nadir"` តែនៅពេល Nadir ពិតជាបានធ្វើ
ជម្រើសប៉ុណ្ណោះ។

**ពេលដែលគួរប្រើ**៖ ចរាចរណ៍ដែលមានកម្រិតលំបាកចម្រុះនៅលើ pool ដែលគ្របដណ្ដប់ម៉ូដែលច្រើនកម្រិត (ម៉ូដែលតូច មធ្យម
និងជួរមុខ) ដែលការប្រើម៉ូដែលជួរមុខជានិច្ចគឺជាថ្លៃចំណាយដែលអ្នកចង់កាត់បន្ថយ។

**ឈ្មោះហៅក្រៅ**៖ `nadir` (គ្មានឈ្មោះហៅក្រៅ)

### យុទ្ធសាស្ត្រ router ផ្ទាល់ខ្លួន

អ្នកអាចចុះឈ្មោះការអនុវត្ត `RouterStrategy` ផ្ទាល់ខ្លួនរបស់អ្នកតាមរយៈ API សាធារណៈ៖

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ឡូជីខលបញ្ជូនផ្លូវរបស់អ្នកនៅទីនេះ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

បន្ទាប់មកប្រើវា៖

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## សង្ខេបអំពី Auto Variants

ដោយរាប់បញ្ចូលទាំង `auto` ដាច់ដោយឡែក (លំនាំដើម) និងតម្លៃ `AutoVariant` ទាំង 6 ដែលបានប្រកាសក្នុង `autoPrefix.ts` មាន **លេខសម្គាល់ម៉ូដែលដែលអាចហៅប្រើបានចំនួន 7**៖

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ផ្ទាល់រាយតម្លៃចំនួន 6; ជម្រើសទី 7 គឺ "គ្មានវ៉ារ្យ៉ង់" — `auto` ដាច់ដោយឡែក — ដែលត្រូវបានដោះស្រាយដោយ `parseAutoPrefix()` ជា `variant: undefined`។)

## របៀបដែលកម្រិតត្រូវគ្នាជាមួយ Auto-Combo

មុខងារដាក់ពិន្ទុដែលមាន 16 កត្តា (`open-sse/services/autoCombo/scoring.ts`) ចាត់ទុកសមាជិកភាពកម្រិតជាសញ្ញាពីរ៖ `tierPriority` (0.0476) និង `tierAffinity` (0.0476)។ សូមមើល[តារាងកត្តាដាក់ពិន្ទុគោល](#how-it-works-persisted-auto-combos)ខាងលើ សម្រាប់សំណុំ `DEFAULT_WEIGHTS` ពេញលេញ — ការកំណត់ជំនួសតាមកញ្ចប់នីមួយៗ (ship-fast/cost-saver/quality-first/
offline-friendly) ត្រូវបានរាយក្នុងតារាង "ទម្រង់ទម្ងន់តាមកញ្ចប់"។

កម្រិតតែមួយមុខ **មិន**បង្ខំឱ្យកម្រិតទី 1 មកមុនទេ — ប្រសិនបើភាពយឺតយ៉ាវរបស់កម្រិតទី 1 មិនល្អ ឬតម្លៃធៀបនឹងគុណភាពមិនល្អប្រសើរ នោះកម្រិតទី 2 នឹងឈ្នះ។ ដើម្បីបង្ខំលំដាប់កម្រិត សូមប្រើយុទ្ធសាស្ត្របន្សំ `priority` ហើយរៀបចំអ្នកផ្តល់សេវាតាមកម្រិត។

ដើម្បីផ្តល់អាទិភាពខ្លាំងដល់កម្រិតទី 1 (ការជាវ) សូមបង្កើនទម្ងន់ `tierPriority`៖

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

សូមមើល [`docs/guides/TIERS.md`](../guides/TIERS.md) សម្រាប់និយមន័យកម្រិត និងការចាត់ថ្នាក់អ្នកផ្តល់សេវា។

## ការធ្វើតេស្ត និងវិសាលភាពគ្របដណ្តប់

### ម៉ាទ្រីសការសម្រេចចិត្តបញ្ជូនតាមផ្លូវបែបកំណត់ជាមុន (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` បញ្ជាក់អំពី **ការសម្រេចចិត្ត** បញ្ជូនតាមផ្លូវរបស់យុទ្ធសាស្ត្រសាធារណៈទាំង 19
ពីដើមដល់ចប់ តាមរយៈ pipeline combo ពិតប្រាកដ ដោយប្រើ upstream ក្លែងធ្វើ។
វិសាលភាពគ្របដណ្តប់រួមមាន៖

- យុទ្ធសាស្ត្រ `ROUTING_STRATEGY_VALUES` ទាំង 19 (ordered, weighted, cost, context, fusion, …)។
- `quota-share` (ខាងក្នុង) ពីដើមដល់ចប់៖ ភាពយុត្តិធម៌ DRR + ការបន្ថយអាទិភាពពេលឆ្អែត តាមរយៈ
  seam `selectQuotaShareTarget` ពិតប្រាកដ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)។
- វិសាលភាពគ្របដណ្តប់នៃការប្រគល់បន្តជាសកល `context-relay` នៅគ្រប់ចំនួនគោលដៅ។

សំណុំតេស្តនេះដំណើរការក្នុង CI (job `test:integration`) ជាមួយ `--test-concurrency=1` និង
`--test-force-exit` ដូច្នេះវាមានលទ្ធផលកំណត់ជាមុន និងមិនត្រូវការព័ត៌មានសម្ងាត់ពិតប្រាកដទេ។

### Smoke test ផ្ទាល់ដែលមានលក្ខខណ្ឌ (មិនមានក្នុង CI — providers ពិតប្រាកដ)

| ពាក្យបញ្ជា                             | អ្វីដែលវាធ្វើ                                                                                  |
| :------------------------------------- | :--------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | ការបញ្ជូនតាមផ្លូវពិតក្នុង process ជាមួយ `RUN_COMBO_LIVE=1`; ថត snapshot នៃ OmniRoute DB ផ្ទាល់ |

| `npm run test:combo:live:vps:failover` | ដូចគ្នា ប៉ុន្តែមានសេណារីយ៉ូ failover ដែលបានបង្កើតឡើងដោយចេតនា                                   |
