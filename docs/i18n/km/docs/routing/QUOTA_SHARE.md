## ទិដ្ឋភាពទូទៅ

ម៉ាស៊ីនចែករំលែកកូតា (Quota Sharing Engine) បែងចែកកូតាផ្អែកលើពេលវេលារបស់អ្នកផ្តល់សេវា (ឧ. ចន្លោះពេល 5 ម៉ោងរបស់ Codex, Kimi 1500 សំណើ/ម៉ោង) ដោយយុត្តិធម៌រវាង API key ជាច្រើនដែលប្រើការតភ្ជាប់ដូចគ្នា។

**បញ្ហាដែលវាដោះស្រាយ:** OmniRoute ធ្វើប្រូកស៊ី API key ជាច្រើនទៅកាន់គណនីអ្នកផ្តល់សេវាខាងលើដូចគ្នា។ បើគ្មានតក្កវិជ្ជាចែករំលែកទេ សំណើដ៏ច្រើនភ្លាមៗពី key A អាចប្រើកូតារបស់អ្នកផ្តល់សេវាអស់សម្រាប់ម៉ោងនោះ ដែលធ្វើឱ្យ key B និង C ត្រូវបានទប់ស្កាត់រហូតដល់ចន្លោះពេលកំណត់ឡើងវិញ។ ម៉ាស៊ីននេះទប់ស្កាត់បញ្ហានេះដោយ៖

1. តាមដានការប្រើប្រាស់រំកិលរបស់ key នីមួយៗតាមវិមាត្រ (%, សំណើ, token, $)។
2. អនុវត្តក្បួនចែករំលែកដោយយុត្តិធម៌ដែលរក្សាការប្រើប្រាស់ធនធាន៖ key មួយអាចខ្ចីពីចំណែកដែលនៅទំនេរ ខណៈពេលដែលធនធានរួមមិនទាន់ឈានដល់កម្រិតឆ្អែត។
3. អនុវត្តលទ្ធផលនៅក្នុងផ្លូវដំណើរការសំខាន់ (`chatCore.ts`) មុនពេលសំណើទៅដល់កម្មវិធីប្រតិបត្តិខាងលើ។

## ក្បួនដោះស្រាយ៖ ការចែករំលែកការងារដោយយុត្តិធម៌

បានអនុវត្តនៅក្នុង `src/lib/quota/fairShare.ts`។

### របៀប

| លក្ខខណ្ឌ                                   | របៀប        | ឥរិយាបទ                                         |
| ------------------------------------------ | ----------- | ----------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **សប្បុរស** | សោអាចខ្ចីរហូតដល់ដែនកំណត់សកល ដកការប្រើប្រាស់សរុប |
| `globalUsedPercent >= saturationThreshold` | **តឹងរ៉ឹង** | អនុវត្តការចែករំលែកដោយយុត្តិធម៌បុគ្គលយ៉ាងតឹងរ៉ឹង |

`saturationThreshold = 0.5` លំនាំដើម (env `QUOTA_SATURATION_THRESHOLD`) ។

របៀបទាំងពីរនេះពិពណ៌នាអំពីអាងមួយនៅក្នុងរបៀបខ្ចីលំនាំដើម `saturation`។ អាងនៅក្នុងរបៀប `consent` តែងតែអនុវត្តច្បាប់ដ៏តឹងរ៉ឹង ទោះបីជាកម្រិតតិត្ថិភាពក៏ដោយ។ សូមមើល [ការផ្តល់កម្ចីដែលបានយល់ព្រម (ការជ្រើសរើសចូលក្នុងមួយក្រុម)។](#consented-lending-per-pool-opt-in)

### ការសម្រេចចិត្តតាមវិមាត្រ

សម្រាប់វិមាត្រសកម្មនីមួយៗនៅក្នុងអាង ម៉ាស៊ីនគណនា៖

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

សម្រាប់វិមាត្រ `percent` `consumed` មកពីសៀវភៅគុណលក្ខណៈជំនួសវិញ (សូមមើល [ទំហំភាគរយ៖ គុណលក្ខណៈក្នុងមួយគន្លឹះ](#percent-dimensions-per-key-attribution) )។

បន្ទាប់មក៖

- **`policy = hard`** ៖ ប្រសិនបើ `consumed > fairShareAllowed` និងរបៀបគឺ → តឹងរ៉ឹង** ប្លុក** .
- **`policy = soft`** ៖ ប្រសិនបើ `consumed > fairShareAllowed` និងរបៀបគឺ → តឹងរ៉ឹង** ពិន័យ** (បន្ថយអាទិភាពក្នុងបន្សំ មិនដែលពិបាកទប់ស្កាត់)។
- **`policy = burst`** ៖ អនុញ្ញាតខណៈពេលដែល headroom សកលមាន ដោយមិនគិតពីការចែករំលែកដោយយុត្តិធម៌។

### Cap absoluto

`capValue` + `capUnit` លើការបែងចែកគឺជាពិដានរឹងដោយឯករាជ្យនៃរបៀប ឬគោលការណ៍។ វិមាត្រណាមួយដែល `consumed >= capValue` តែងតែ** ប្លុក** សំណើ។ សម្រាប់ `percent` cap, `consumed` គឺគ្រាន់តែជាផ្នែកដែលត្រូវបានកំណត់គុណលក្ខណៈគន្លឹះប៉ុណ្ណោះ។

### ការត្រួតពិនិត្យពហុវិមាត្រ

សំណើត្រូវបានរារាំងប្រសិនបើ** ណាមួយ។** វិមាត្រនៅក្នុងអាងនឹងរារាំងវា។ វិមាត្រគឺឯករាជ្យ — ការហត់នឿយ 5h% មិនប៉ះពាល់ដល់វិមាត្រ% ប្រចាំសប្តាហ៍ទេ។

### ការខ្ចីប្រាក់

នៅក្នុងរបៀបទូទៅ សោដែលការបែងចែកត្រូវបានប្រើប្រាស់តិចអាចប្រើអតិរេកពីការចែករំលែកដែលមិនបានបែងចែករបស់សោផ្សេងទៀត។ រូបមន្តគឺ៖

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ដែលជាកន្លែងដែល `consumedByOtherKeys = consumedTotal - consumedByThisKey`។ តេតូសកល (អាង `limit` សម្រាប់វិមាត្រនោះ) គឺតែងតែជាពិដានរឹង។

### ការផ្តល់កម្ចីដែលបានយល់ព្រម (ការជ្រើសរើសចូលក្នុងមួយក្រុម)

អាងនីមួយៗមានរបៀបខ្ចី។ `saturation` គឺជាលំនាំដើម ហើយរក្សាច្បាប់ខាងលើ។ នៅក្នុងរបៀប `consent` គ្រាប់ចុច `hard` ឆ្លងកាត់ចំណែករបស់វានៅក្នុងសមត្ថភាពដែលសោផ្សេងទៀតបានយល់ព្រមឱ្យខ្ចី។ អ្នកគ្រប់គ្រងកំណត់របៀបនៃអាងនីមួយៗ។ អ្នកកាន់កូនសោនីមួយៗកំណត់ការយល់ព្រមរបស់ពួកគេតាមរយៈ [ការយល់ព្រមលើការផ្តល់ប្រាក់កម្ចី](#lending-consent) ។

ការយល់ព្រមគឺជាភាគរយពី 0 ដល់ 100 និងកាលបរិច្ឆេទកំណត់ជាជម្រើសគិតជាមីលីវិនាទី។ គន្លឹះផ្តល់ប្រាក់កម្ចីនោះភាគរយនៃចំណែកទំនេររបស់វា ខណៈដែលថ្ងៃផុតកំណត់គឺនៅពេលអនាគត។

សម្រាប់វិមាត្រមួយ `L` គឺជាដែនកំណត់ដ៏មានប្រសិទ្ធភាព៖ ផែនការកំណត់ចំនួនគណនីនៅក្នុងអាង។ ច្រកទ្វារគណនាសម្រាប់សោដែលស្នើសុំ៖

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` គឺជាទម្ងន់របស់កូនសោ ឬ `100 / n` សម្រាប់រាល់គន្លឹះនៅពេលដែលគ្មានទម្ងន់លើសពី 0 ។ `lend_k` គឺជាភាគរយសកម្មរបស់សោ និង 0 នៅពេលដែលកាលបរិច្ឆេទផុតកំណត់របស់វាបានកន្លងផុតទៅហើយ។ ការយល់ព្រមផ្ទាល់ខ្លួនរបស់សោដែលស្នើសុំមិនរាប់បញ្ចូលទេ។ គ្រាប់ចុច `hard` ត្រូវបានបដិសេធនៅពេលដែលការប្រើប្រាស់របស់វាឈានដល់ចំណែករបស់វាបូក `borrowAvailable`។

សមត្ថភាពដែលមិនទាមទារការបែងចែក (100 ដកផលបូកនៃទម្ងន់) មិនអាចផ្តល់ប្រាក់កម្ចីបានទេ។ គ្មានកូនសោយល់ព្រមឱ្យខ្ចី។

**ឧទាហរណ៍។** `L` គឺ 1000 ។

| សោ  | ទម្ងន់ | ចែករំលែក | ប្រើប្រាស់ | ខ្ចី |
| --- | ------ | -------- | ---------- | ---- |
| ក   | 50     | 500      | 530        | 0%   |
| ខ   | 30     | 300      | 100        | 50%  |

- B ខ្ចី 50% នៃ idle 200 របស់វា ដែលស្មើនឹង 100 ។ C បានយក 60 ពីលើចំណែករបស់វា។ A អាចខ្ចីបាន ៤០.
- A ត្រូវបានបម្រើនៅ 530 ហើយបដិសេធនៅពេលដែលការប្រើប្រាស់របស់វាឡើងដល់ 540។
- មុនពេល C ប្រើអ្វីក៏ដោយ ជាមួយ A នៅ ឬក្រោមចំណែករបស់វា C អាចខ្ចី 100 ។
- មុនពេល C ប្រើអ្វីក៏ដោយ ដោយ A នៅ 530 C អាចខ្ចីបាន 70 ។

**ទម្ងន់សូន្យ។** គ្រាប់ចុចដែលមានទម្ងន់ 0 មានចំណែកនៃ 0។ វាត្រូវបានបម្រើតែខណៈពេលដែលការប្រើប្រាស់របស់វាទាបជាងអ្វីដែលអ្នកផ្សេងទៀតខ្ចី។ នៅពេលដែលគ្មាននរណាម្នាក់ខ្ចី វាត្រូវបានបដិសេធពីការស្នើសុំដំបូងរបស់វា។

**ថ្ងៃផុតកំណត់។** គ្មានកិច្ចការផ្ទៃខាងក្រោយផុតកំណត់ការយល់ព្រមទេ។ សំណើនីមួយៗប្រៀបធៀបថ្ងៃផុតកំណត់ជាមួយនឹងពេលវេលារបស់វា ហើយថ្ងៃផុតកំណត់ស្មើនឹងពេលវេលានោះបានកន្លងផុតទៅហើយ។ ថ្ងៃផុតកំណត់ដែលបានរក្សាទុកដែលមិនមែនជាចំនួនកំណត់ ឬហួសកាលបរិច្ឆេទធំបំផុតដែល `Date` អាចរក្សាបាន រាប់ថាបានឆ្លងកាត់។

**`soft` និង `burst`។** ការផ្តល់ប្រាក់កម្ចីមិនកំណត់ពួកគេទេ។ សោ `soft` ត្រូវបានដកអាទិភាពនៅពេលដែលការចែករំលែករបស់វា។ គ្រាប់ចុច `burst` ឆ្លងកាត់ខណៈពេលដែលអាងមានបន្ទប់។ ពិដានអាងនៅតែបដិសេធរាល់គន្លឹះទាំងអស់ នៅពេលដែលចំនួនសរុបនៃអាងឈានដល់ដែនកំណត់របស់វា។

**ការចំណាយលើផ្លូវស្នើសុំ។** អាង `saturation` អានអ្វីច្រើនជាងមុន។ នៅក្នុងក្រុម `consent` វិមាត្រដែលអាចរាប់បានអានគ្រាប់ចុចផ្សេងទៀតសម្រាប់តែគ្រាប់ចុច `hard` នៅ ឬលើសពីការចែករំលែករបស់វា ខណៈដែលកូនសោផ្សេងទៀតខ្ចី។ បន្ទាប់មកវាធ្វើឱ្យការអានមួយសម្រាប់គន្លឹះផ្សេងទៀតស្របគ្នា។ ការអានដែលបរាជ័យរាប់ជាការប្រើប្រាស់ 0 សម្រាប់សោនោះ។ វិមាត្រ `percent` បន្ថែមការអានទេ ព្រោះសៀវភៅគុណលក្ខណៈមានគ្រប់គន្លឹះ។

**ការកែសម្រួលអាង។** ការកែសម្រួលរក្សាការយល់ព្រមពីសោដែលនៅដដែល។ វារក្សាទុកសម្រាប់ការកែសម្រួលការបែងចែក ការជំនួសជាក្រុម និងការហៅ `ensure` ។ សោដែលបានដកចេញបាត់បង់ការយល់ព្រមរបស់វា ហើយសោដែលបានបន្ថែមត្រឡប់មកវិញចាប់ផ្តើមនៅ 0។ ផ្លូវអ្នកគ្រប់គ្រងត្រឡប់ការយល់ព្រមរបស់សោនីមួយៗ ហើយកុំសរសេរវា។ ការប្តូរអាងត្រឡប់ទៅ `saturation` រក្សារាល់ការយល់ព្រមដែលបានរក្សាទុក ដែលមិនមានឥទ្ធិពលនៅក្នុងរបៀបនោះ។ ការប្តូរអាងទៅ `consent` ម្តងទៀតធ្វើឱ្យការយល់ព្រមដែលបានរក្សាទុកឡើងវិញដែលកាលបរិច្ឆេទផុតកំណត់មិនបានកន្លងផុតទៅ។ អ្នកកាន់សោអាចជម្រះការយល់ព្រមដែលបានរក្សាទុកនៅក្នុងរបៀបណាមួយ។

**ការធ្វើឱ្យប្រសើរឡើង។** ប្រសិនបើជួរឈរ `lending_percent` និង `lending_until` មានរួចហើយ ការធ្វើចំណាកស្រុកបន្ថែមតែ `borrow_mode` ហើយភាគរយដែលបានរក្សាទុកនឹងនៅដដែល។ អាងនីមួយៗចាប់ផ្តើមនៅក្នុងរបៀប `saturation` ។ បើក `consent` ក្នុងមួយអាងនៅក្នុងអ្នកជំនួយការអាង។ គ្មានអ្វីត្រូវបានសន្និដ្ឋានពីតម្លៃដែលបានរក្សាទុក។

**ដែនកំណត់។**

- អ្នកអោយខ្ចីអាចស្វែងរកអាងទឹកនៅពិដានរបស់វា មុនពេលដែលវាប្រើប្រាស់ចំណែករបស់ខ្លួន។ សមត្ថភាពដែលអ្នកផ្សេងបានខ្ចីរាប់បញ្ចូលទៅនឹងចំនួនសរុបរបស់អាង។
- មូលប្បទានប័ត្រដំណើរការមុនការស្នើសុំ និងមិនរក្សាទុកអ្វីទាំងអស់។ សំណើក្នុងពេលដំណាលគ្នាអានការប្រើប្រាស់មុនពេលណាមួយត្រូវបានកត់ត្រា ដូច្នេះសមត្ថភាពផ្តល់ប្រាក់កម្ចីអាចត្រូវបានចំណាយច្រើនជាងម្តង ដោយកំណត់ដោយសំណើក្នុងការហោះហើរ។ ការត្រួតពិនិត្យចែករំលែកនៃរបៀប `saturation` មានទ្រព្យសម្បត្តិដូចគ្នា។

## កម្មវិធីរាប់ចន្លោះពេលរំកិល

ត្រូវបានអនុវត្តនៅក្នុង `src/lib/quota/sqliteQuotaStore.ts` និង `redisQuotaStore.ts`។

មាន bucket ពីរសម្រាប់ `(apiKeyId, dimensionKey)` នីមួយៗ៖

- `curr`៖ bucket បច្ចុប្បន្ន (`floor(nowMs / windowMs)`)
- `prev`៖ bucket មុន (`curr - 1`)

តម្លៃរំកិលជាក់ស្តែង៖

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ភាពជាក់លាក់**៖ ត្រឹមត្រូវប្រហែល 99%។ កំហុសមានច្រើនបំផុត 1% នៃទំហំចន្លោះពេល នៅត្រង់ព្រំដែនរវាង bucket (ជាលក្ខណៈដែលជៀសមិនរួចនៃការប៉ាន់ស្មានដោយប្រើ bucket 2)។

### ភាពដំណាលគ្នា

កម្មវិធីបញ្ជា SQLite៖ mutex ក្នុងអង្គចងចាំសម្រាប់ key `(apiKeyId | dimensionKey)` នីមួយៗ ទប់ស្កាត់ស្ថានភាពប្រណាំង read-modify-write។ លំនាំនេះដូចគ្នានឹងវិធីប្រឆាំង anti-thundering-herd របស់ `src/sse/services/auth.ts`។

កម្មវិធីបញ្ជា Redis៖ ស្គ្រីប Lua EVAL សម្រាប់ការបង្កើនតម្លៃបែប atomic — ដំណើរការជាពាក្យបញ្ជា Redis តែមួយ។

### ការប្ដូរកម្មវិធីបញ្ជា

លំដាប់នៃការជ្រើសរើសកម្មវិធីបញ្ជា៖

1. ការកំណត់ DB `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. លំនាំដើម៖ `sqlite`

#### នៅពេលដែលសៀវភៅត្រូវបានប្រើប្រាស់

បន្ទាប់ពីការអាន សៀវភៅត្រូវបានប្រើប្រាស់ លុះត្រាតែពេលវេលាកំណត់ឡើងវិញដែលបានរក្សាទុករបស់វាមិនមែនបន្ទាប់ពីម៉ោងបច្ចុប្បន្ន។ ករណីនោះកើតឡើងនៅពេលដែលការអានដែលបានធ្វើឡើងមុនពេលកំណត់ឡើងវិញ ដូចជាការបម្រើពីឃ្លាំងសម្ងាត់ត្រូវបានសង្កេតឃើញបន្ទាប់ពីវា។

បើគ្មានការអានដែលអាចប្រើបានទេ សៀវភៅដែលបានរក្សាទុកត្រូវបានប្រើតែខណៈពេលដែលវានៅតែអាចជាសៀវភៅរបស់បង្អួចបច្ចុប្បន្ន។ វាស្ថិតនៅក្នុងករណីពីរ៖

- ពេលវេលាកំណត់ឡើងវិញរបស់វាត្រូវបានដឹង និងនៅតែមាននៅខាងមុខ
- វាមិនមានពេលកំណត់ឡើងវិញទេ ហើយការអានចុងក្រោយដែលបានផ្លាស់ប្តូរវាមានរយៈពេលច្រើនបំផុត 15 នាទី។

បើមិនដូច្នេះទេគ្មានអ្វីត្រូវបានកំណត់ដូចជានៅពេលដែលគ្មានសៀវភៅ។ សៀវភៅដែលរក្សាទុកពេលវេលាកំណត់ឡើងវិញបានកន្លងផុតទៅ មិនត្រូវបានគិតប្រាក់ទេ។

#### ការអនុវត្ត

ការប្រើប្រាស់របស់សោនៅលើវិមាត្រភាគរយគឺជាផ្នែកកំណត់របស់វាបូកនឹងចំណែកនៃផ្នែកខាងក្រៅ។ ផ្នែកខាងក្រៅដំបូងប្រើសមត្ថភាពគ្មានការទាមទារបែងចែក (100 ដកផលបូកនៃទម្ងន់)។ មានតែការលើសប៉ុណ្ណោះដែលត្រូវបានចែករំលែកក្នុងចំណោមសោតាមទម្ងន់។

ការប្រើប្រាស់នោះត្រូវបានប្រៀបធៀបជាមួយនឹងការចែករំលែកដោយយុត្តិធម៌របស់គន្លឹះសម្រាប់ទំហំផ្សេងទៀត។ របៀបតឹងរឹងនៅតែចាប់ផ្តើមនៅពេលដែលសញ្ញាតិត្ថិភាពឈានដល់ `QUOTA_SATURATION_THRESHOLD` (លំនាំដើម 0.5) ។ លេខនីមួយៗត្រូវបានធ្វើមាត្រដ្ឋានដោយដែនកំណត់ដែលមានប្រសិទ្ធភាព៖ ដែនកំណត់ក្នុងមួយគណនីត្រូវនឹងចំនួនគណនីនៅក្នុងក្រុម។

មួកដាច់ខាតជាមួយ `capUnit: "percent"` រាប់តែផ្នែកដែលត្រូវបានកំណត់គុណលក្ខណៈសោ ធ្វើមាត្រដ្ឋានតាមរបៀបដូចគ្នា។ យកដែនកំណត់ក្នុងគណនី 100 និង k គណនី។ បន្ទាប់មក CAP នៃ N ត្រូវបានឈានដល់នៅពេលដែលផ្នែកនៃគន្លឹះនៃតួលេខនៃគណនីបម្រើឈានដល់ចំណុច N/k ។ គណនីនីមួយៗត្រូវបានពិនិត្យជាមួយនឹងសៀវភៅរបស់ខ្លួន។ ជាឧទាហរណ៍ ដោយមានគណនីពីរ មួកចំនួន 10 ត្រូវបានឈានដល់ 5 ពិន្ទុនៃតួលេខគណនីមួយ។

នៅពេលដែលហាងមិនអាចអានបាន គ្មានអ្វីត្រូវបានកំណត់គុណលក្ខណៈទេ ហើយរាល់សោត្រូវបានគិតថ្លៃ 0 លើវិមាត្រនោះ។ នៅពេលដែលការសរសេរសៀវភៅបរាជ័យ គុណលក្ខណៈនោះប្រើសៀវភៅដូចដែលបានអាន។ ការសរសេរនិមិត្តសញ្ញាដែលបរាជ័យទុកសញ្ញាសម្ងាត់របស់សំណើចេញពីសៀវភៅ។ គ្មានការបរាជ័យទាំងនេះរារាំងសំណើនោះទេ។

នៅក្នុងក្រុម `consent` រូបមន្តផ្តល់ប្រាក់កម្ចីប្រើការប្រើប្រាស់របស់សោនីមួយៗលើវិមាត្រភាគរយដូចដែលបានពិពណ៌នាខាងលើ។ នៅពេលដែលកូនសោផ្សេងទៀតខ្ចី សៀវភៅត្រូវបានអានម្តង ហើយសន្មតថាជាកូនសោនីមួយៗ។ បើគ្មានសៀវភៅដែលអាចប្រើបានទេ រាល់សោត្រូវគិតថ្លៃ 0។ គ្រាប់ចុចដែលមានទម្ងន់បន្ទាប់មកហុច ហើយសោដែលមានទម្ងន់ 0 ហុចបានតែនៅពេលដែលកូនសោផ្សេងទៀតខ្ចី។

## ការរួមបញ្ចូលបំពង់

### ទំពក់PRE (`open-sse/handlers/chatCore.ts`)

ដំណើរការនៅចំពោះមុខអ្នកប្រតិបត្តិចរន្ត បន្ទាប់ពីការត្រួតពិនិត្យសិទ្ធិ និងគោលការណ៍៖

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**បរាជ័យ - បើក** : ប្រសិនបើ `enforceQuotaShare` បោះ សំណើត្រូវបានអនុញ្ញាតដោយប្រើកំណត់ហេតុ `pino.warn` ។ វាការពារកំហុសម៉ាស៊ីនកូតាពីការទប់ស្កាត់ចរាចរណ៍ទាំងអស់។

**នៅពេលដែលសមត្ថភាពត្រឡប់មកវិញ។** ការបដិសេធនៅចំណែករបស់កូនសោ ឬនៅពិដានអាងបញ្ចប់ដោយប្រយោគមួយក្នុងចំណោមប្រយោគពីរ ក្នុងរបៀបខ្ចីទាំងពីរ៖

- `percent` window: `. The <window> window resets at <time>.` ពេលវេលាគឺកំណត់ឡើងវិញនូវរបាយការណ៍អ្នកផ្តល់សេវា។
- ឯកតាដែលអាចរាប់បាន៖ `. Enough <window> usage is expected to clear by <time>.` ពេលវេលាគឺជាព្រំដែនខាងលើពីបង្អួចរអិល ប្រសិនបើសោមិនផ្ញើអ្វីផ្សេង។

`<time>` គឺជា ISO 8601 ភ្លាមៗនៅក្នុង UTC។ ការបដិសេធបន្ទាប់មកអនុវត្ត `Retry-After`: វិនាទីទាំងមូលរហូតដល់ភ្លាមៗនោះបូកមួយ។ ម៉ាស៊ីនភ្ញៀវដែលរង់ចាំយូរនោះ ព្យាយាមម្តងទៀតច្រើនបំផុតមួយវិនាទីបន្ទាប់ពីភ្លាមៗ។ នៅពេលដែលមិនដឹងភ្លាមៗ ការបដិសេធមិនអនុវត្តទាំងប្រយោគ ឬបឋមកថាឡើយ។ ការបដិសេធដាច់ខាតមិនអាចអនុវត្តបានទេ។ លេខកូដសាធារណៈស្ថិតនៅ `quota_share_blocked`។

ការបដិសេធការចែករំលែកមិនប៉ះការតភ្ជាប់ដែលបានចែករំលែកទេ។ វាកំណត់មិនដំណើរការ cooldown គ្មានការចាក់សោរគំរូ និងគ្មានការបរាជ័យរបស់ឧបករណ៍បំបែកអ្នកផ្តល់សេវា ហើយសោផ្សេងទៀតនៃអាងនៅតែបន្តដំណើរការ។ នៅពេលដែលរាល់គោលដៅនៃបន្សំបដិសេធគន្លឹះសម្រាប់ការចែករំលែករបស់វា បន្សំឆ្លើយតប 429 ដោយមិនរង់ចាំ។ ចម្លើយរបស់វាមានតម្រុយដូចជា `Retry-After`។ ផ្លូវបង្កប់បញ្ចប់ការបដិសេធរបស់វាដោយប្រយោគដដែល ហើយមិនផ្ញើ `Retry-After` ទេ។

### POST hook (ការប្រើប្រាស់កំណត់ត្រា)

បន្ទាប់ពីការឆ្លើយតបដោយជោគជ័យ៖

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**កំណត់ចំណាំរសាត់** : ប្រសិនបើ `consume` បរាជ័យក្រោយការឆ្លើយតប នោះការរាប់រំកិលចុះក្រោម។ សញ្ញាតិត្ថិភាពពីអ្នកផ្តល់សេវា (ឧទាហរណ៍ `anthropic-ratelimit-unified-5h-utilization`) កែតម្រូវការប៉ាន់ស្មានជាសកលនៅលើសំណើបន្ទាប់។

### ការពិន័យទន់បន្សំ (`open-sse/services/combo.ts`)

នៅពេលដែល `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

ការពិន័យត្រូវបានអនុវត្តបន្ទាប់ពីកត្តាស៊ុតបញ្ចូលទីផ្សេងទៀត។ វាបន្ថយប្រូបាប៊ីលីតេនៃបន្សំស្វ័យប្រវត្តិនៃការជ្រើសរើសសោឆ្អែតដោយមិនចាំបាច់រារាំងវាឡើយ។

ផ្លាកសញ្ញាផ្តល់ប្រាក់កម្ចីបង្ហាញភាគរយ ហើយនៅពេលកំណត់ ថ្ងៃផុតកំណត់នៅក្នុង UTC ជាមួយនឹងតំបន់ដែលមានឈ្មោះ។ វាវិនិច្ឆ័យថ្ងៃផុតកំណត់នៅពេលរូបថតនៃការប្រើប្រាស់។ ថ្ងៃផុតកំណត់ដែលផុតកំណត់ ឬមិនអាចអានបាន បង្ហាញជា `lending expired`។

ទំព័រភ្ជាប់៖

- `usePools` — ទាញយក `GET /api/quota/pools` រៀងរាល់ 30 វិនាទី។
- `usePoolUsage` — ទាញយក `GET /api/quota/pools/[id]/usage` តាមតម្រូវការ។
- `useLocalStoragePoolMigration` — ដំណើរការម្តងនៅលើម៉ោនដើម្បីផ្ទេរទិន្នន័យ LS ចាស់។

ជំហានគន្លឹះរបស់អ្នកជំនួយការអាងមានប្រអប់ `Show usage by member to key holders` ។ វាកំណត់ជម្រើស `memberBreakdown` របស់អាង (សូមមើល [ការប្រើប្រាស់សមាជិក](#member-usage) )។ ខាងក្រោមវា អ្នកជំនួយការព្រមានថានរណាម្នាក់ដែលដឹងពីអ្វីដែលកូនសោដែលបានប្រើអាចផ្គូផ្គងរបារមួយទៅនឹងសោនោះ។ ជាមួយនឹងការគូសធីកប្រអប់ វានិយាយដូច្នេះ នៅពេលដែលជំហានមានបញ្ជីកូនសោតិចជាងបី ឬច្រើនជាង 20 ដោយសាររបារបន្ទាប់មកលាក់។ វារាប់គ្រាប់ចុចនៅក្នុងជំហាន ហើយមិនអាចប្រាប់ថាតើពួកវាមួយណាអាចធ្វើការស្នើសុំបានទេ។

- អាងមួយត្រូវបានកំណត់អត្តសញ្ញាណដោយ `ref` ដែលជាតម្លៃស្រអាប់ដែលភ្ជាប់ទៅនឹងសោហៅទូរសព្ទ។ ឈ្មោះបង្ហាញរបស់វា (`name`) ត្រូវបានរួមបញ្ចូលដូចដែលអ្នកគ្រប់គ្រងបានសរសេរវា។ `ref` គឺបានមកពីកូនសោ និងក្រុមដែលមាន API-key secret របស់ម៉ាស៊ីនបម្រើ (`API_KEY_SECRET`)។ អតិថិជនមិនត្រូវបន្តវាទេ៖ វាផ្លាស់ប្តូរប្រសិនបើការសម្ងាត់នោះត្រូវបានបង្វិល។
- គណនីត្រូវបានរាយបញ្ជីជា `Account 1`, `Account 2`, … តាមលំដាប់លំដោយ។ គ្មានលេខសម្គាល់អាង លេខសម្គាល់ការតភ្ជាប់ អ៊ីមែលគណនី ឬឈ្មោះគណនីត្រូវបានប្រគល់មកវិញទេ ហើយការឆ្លើយតបឆ្លងកាត់តាមគ្រោងការណ៍កិច្ចសន្យា ដែលទម្លាក់វាលណាមួយនៅខាងក្រៅវា។
- Countable units (`requests`, `tokens`, `usd`) are reported as the pool bucket the quota gate enforces: `limit` = plan limit × accounts in the pool, `fairShare` = weight / 100 × `limit` (equal split when every weight is 0), `consumed` = the key's own counter in the quota store, `remaining` = `fairShare` − `consumed`, floored at 0.
- `blocks.schedules` រាយបញ្ជីបង្អួចកាលវិភាគរបស់កូនសោ (`open`/`closed`, `blackout` ឬ `outside-window`, `retryAfterSeconds`, ជាន់បម្រុង និងថាតើថវិការបស់បង្អួចត្រូវបានចំណាយដែរឬទេ); `blocks.modelCaps` រាយបញ្ជីមួកប្រចាំម៉ោងក្នុងមួយម៉ូដែលជាមួយនឹងការប្រើប្រាស់។
- កូនសោនៅខាងក្រៅអាងនីមួយៗរបស់អ្នកផ្តល់សេវាទទួលបាន 200 ជាមួយ `pools: []`; `availableModels` (លេខសម្គាល់ `qtSd/` ដែលកូនសោឃើញក្នុង `/v1/models`) `expiresAt` និង `apiBaseUrl` នៅតែត្រូវបានបំពេញ។
- `apiBaseUrl` គឺ `OMNIROUTE_PUBLIC_API_BASE_URL` បន្ទាប់មក `OMNIROUTE_PUBLIC_BASE_URL` ផ្សេងទៀត `null`។ វាមិនដែលមានប្រភពដើមនៃការស្នើសុំនោះទេ។

### ការយល់ព្រមផ្តល់ប្រាក់កម្ចី

`PATCH /api/v1/me/quota/{provider}` កត់ត្រាការយល់ព្រមផ្ទាល់ខ្លួនរបស់សោហៅទូរសព្ទសម្រាប់អាងមួយ។ វាប្រើទង់ បឋមកថា និងច្បាប់អ្នកផ្តល់សេវារបស់ `GET`។ វិសាលភាព `self:usage` អនុញ្ញាតការសរសេរនេះ ទោះបីជាឈ្មោះរបស់វាអានថាបានតែអានក៏ដោយ។

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` គឺជា `ref` ដែល `GET` ត្រឡប់សម្រាប់អាងនោះ។
- `lendingPercent` គឺជាចំនួនគត់ពី 0 ដល់ 100។ តម្លៃនៃ 0 ជម្រះការយល់ព្រម និងកាលបរិច្ឆេទផុតកំណត់របស់វា។ តួដែលមាន `lendingPercent` 0 ត្រូវបានទទួលយកក្នុងរបៀបទាំងពីរ។
- `lendingUntil` គឺស្រេចចិត្ត៖ epoch milliseconds ឬ `null` ដោយគ្មានកាលកំណត់។ វាត្រូវតែមាននាពេលអនាគត និងច្រើនបំផុត 8640000000000000 ។ តម្លៃក្រោម 100000000000 អានជាវិនាទី ហើយត្រូវបានបដិសេធ។
- វិស័យផ្សេងទៀតត្រូវបានបដិសេធ។ តួដែលវែងជាង 4096 បៃត្រូវបានបដិសេធ។ ការអានឈប់ត្រឹមទំហំនោះ ដូច្នេះរាងកាយដែលវែងជាងនេះមិនត្រូវបានទុកពេញទេ។

### ការប្រើប្រាស់សមាជិក

### ស៊េរីការប្រើប្រាស់ (`GET /api/v1/me/usage`)

នៅពេលដែលសោត្រូវបានទទួលយក ទំព័រក៏បង្ហាញកាត "ដំឡើងឧបករណ៍របស់អ្នក" ដែលមានផ្ទាំងបី។ "Claude Code" ផ្តល់ឱ្យប្លុក `env` សម្រាប់ `~/.claude/settings.json`។ "សែល" ផ្តល់អថេរដូចគ្នានឹងបន្ទាត់ `export` ។ "Claude Desktop" ផ្តល់តម្លៃសម្រាប់បង្អួចការសន្និដ្ឋានភាគីទីបីរបស់វា។ ម៉ូដែលទាំងនេះគឺជាគំរូចែករំលែកកូតា ដែលគន្លឹះអាចហៅរកអ្នកផ្តល់សេវានោះ។ នៅពេលដែលមិនមានបញ្ជីបែបនេះភ្ជាប់មកជាមួយសោ នោះប្លុកនឹងបើកការរកឃើញគំរូច្រកផ្លូវជំនួសវិញ។ អាសយដ្ឋានច្រកផ្លូវគឺជាប្រភព API សាធារណៈដែលម៉ាស៊ីនមេរាយការណ៍ (`OMNIROUTE_PUBLIC_API_BASE_URL` បន្ទាប់មក `OMNIROUTE_PUBLIC_BASE_URL`) ។ នៅពេលដែលទាំងពីរមិនត្រូវបានកំណត់ កាតបង្ហាញកន្លែងដាក់ ហើយប្រាប់អ្នកកាន់ឱ្យសួរអ្នកគ្រប់គ្រង។ គន្លឹះត្រូវបានបង្ហាញជាកន្លែងដាក់។ "រួមបញ្ចូលកូនសោរបស់ខ្ញុំ" ដាក់កូនសោទាំងមូលនៅក្នុងអត្ថបទនៅលើអេក្រង់ហើយនៅក្នុងអ្វីដែលប៊ូតុងចម្លងចម្លង។ វាមានរយៈពេលរហូតដល់ប្រអប់ត្រូវបានជម្រះ សោត្រូវបានបំភ្លេច ឬជំនួស ឬទំព័រត្រូវបានទុកចោល។ កាតមិនផ្ញើសំណើ ហើយមិនផ្តល់ការទាញយកឯកសារទេ។

`PATCH` ត្រូវតែអនុវត្ត `Content-Type: application/json` ដោយគ្មានប៉ារ៉ាម៉ែត្រ ឬជាមួយ `charset=utf-8` ប៉ុណ្ណោះ។ វាត្រូវតែមាន `Content-Length` មួយពី 1 ដល់ 4096 សរសេរជាលេខធម្មតា និងគ្មាន `Transfer-Encoding`។ `PATCH` ដែលបំពានច្បាប់មួយក្នុងចំណោមច្បាប់ទាំងនេះឆ្លើយ 404 ។ ប្រវែងខុសមួយចំនួន ដូចជាការចុះហត្ថលេខា ឬពាក្យដដែលៗត្រូវបានឆ្លើយតប 400 ដោយអ្នកញែក HTTP មុនពេលពិនិត្យផ្ទាល់របស់ច្រកនេះ។ ច្រកនេះអានបៃដែលបានប្រកាស មុនពេលវាទាក់ទងច្រកមេ ហើយរង់ចាំយ៉ាងហោចណាស់ 5 វិនាទីសម្រាប់ពួកគេ។ តួអង្គដែលមិនទាន់បញ្ចប់នៅពេលនោះឆ្លើយ 404 ហើយការតភ្ជាប់របស់វាត្រូវបានបិទ។ មិនមានអ្វីទៅដល់ច្រកសំខាន់នៅក្នុងករណីនោះ ឬនៅពេលដែលម៉ាស៊ីនភ្ញៀវចាកចេញមុន។ ច្រកបញ្ជូនបន្តតាមបៃដែលបានប្រកាសយ៉ាងពិតប្រាកដ ជាមួយនឹង `Content-Length` ដូចគ្នា។ បៃបន្ទាប់ពីពួកវាត្រូវបានអានជាសំណើបន្ទាប់នៅលើការតភ្ជាប់។ ប្រូកស៊ីបញ្ច្រាស TLS នៅខាងមុខត្រូវតែបញ្ជូន `Content-Length` ហើយមិនត្រូវបំបែកតួសំណើឡើងវិញទេ។ ច្រកសំខាន់ពិនិត្យគ្រាប់ចុច API នៅក្នុងបឋមកថា `Authorization` ដូចជាសម្រាប់ `GET`។

## ការដោះស្រាយបញ្ហា

### បានកំណត់ Redis ប៉ុន្តែមិនអាចតភ្ជាប់បាន

(កត់ត្រាក្នុង log នៅកម្រិត `warn`)។

### `peek` ត្រឡប់ទិន្នន័យចាស់ / fail-open

ប្រសិនបើ `peek` បង្កើត exception នោះ `enforceQuotaShare` នឹងចាត់ទុកលទ្ធផលថា "អនុញ្ញាត"

ដើម្បីកំណត់រកមូលហេតុដើម។

### ភាពលម្អៀងនៃកម្មវិធីរាប់ការប្រើប្រាស់

ប្រសិនបើការប្រើប្រាស់ provider ជាក់ស្ដែងខុសពីកម្មវិធីរាប់ នោះគឺជាអ្វីដែលបានរំពឹងទុក —
2-bucket sliding window មានកំហុសប្រហែល 1% នៅត្រង់ព្រំដែន window ហើយ `consume`
ដំណើរការបែប fire-and-forget បន្ទាប់ពី response។ សញ្ញា saturation (`saturationSignals.ts`)
អាន utilization ពិតប្រាកដរបស់ provider ដោយមាន TTL 30 វិនាទី និងកែសម្រួល
`globalUsedPercent` ឱ្យសមស្រប។

## DB សង្ខេបគ្រោងការណ៍

តារាងចំនួនបីបន្ថែមដោយការធ្វើចំណាកស្រុក `078`, `079` និង `085`:

- `quota_pools` + `quota_allocations` — pool និយមន័យ និងការបែងចែកតាមគន្លឹះ។
- `quota_consumption` — វិល 2-bucket counters ក្នុងមួយ `(apiKeyId, dimensionKey)`។
- `provider_plans` — ផែនការអ្នកផ្តល់សៀវភៅដៃបដិសេធ (វិមាត្រ JSON ក្នុងមួយ connectionId) ។

តារាងទាំងអស់ត្រូវបានបន្ថែមតាមរយៈការធ្វើចំណាកស្រុក ideempotent `CREATE TABLE IF NOT EXISTS` ។

ការផ្តល់ប្រាក់កម្ចីដោយយល់ព្រមបន្ថែមជួរចំនួនបី៖ `quota_allocations.lending_percent` (ចំនួនគត់ លំនាំដើម 0) `quota_allocations.lending_until` (មីល្លីវិនាទី ឬ `NULL` សម្រាប់គ្មានថ្ងៃកំណត់) និង `quota_pools.borrow_mode` ( `saturation` លំនាំដើម )។ ការធ្វើចំណាកស្រុករបស់វាបន្ថែមតែជួរឈរទាំងនេះ ហើយមិនសរសេរជួរដេកដែលមានស្រាប់ទេ។

សៀវភៅគុណលក្ខណៈភាគរយបន្ថែម `quota_percent_ledger` (មួយជួរក្នុងមួយក្រុម គណនី និងបង្អួចគម្រោង) និង `quota_percent_ledger_tokens` (សញ្ញាសម្ងាត់មួយក្នុងមួយអាង គណនី និង API key) ។ `src/lib/db/quotaPercentLedger.ts` អាននិងសរសេរពួកគេ។
