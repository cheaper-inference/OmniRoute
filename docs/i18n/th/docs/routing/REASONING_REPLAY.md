OmniRoute จับภาพผู้ช่วย `reasoning_content` ที่สร้างโดยโมเดลโหมดการคิด และเล่นซ้ำอย่างโปร่งใสในคำขอแบบหลายเทิร์นเมื่อผู้ให้บริการอัปสตรีมต้องการ วิธีนี้จะกำจัดข้อผิดพลาด HTTP 400 ที่ผู้ให้บริการที่เข้มงวดเกิดขึ้นเมื่อประวัติการสนทนาของลูกค้าขาดเหตุผลของเทิร์นก่อนหน้า

## ทำไมถึงมีสิ่งนี้

ผู้ให้บริการโหมดการคิดหลายรายปฏิเสธการติดตามผล เว้นแต่ว่า** ข้อความผู้ช่วยก่อนหน้ามี `reasoning_content` ดั้งเดิมด้วย** . อัปสตรีมส่งคืน 400 พร้อมข้อความเช่น:

```
Param Incorrect: The reasoning_content in the thinking mode must be passed back to the API.
```

แต่ไคลเอนต์ทั่วไป (Cursor, Cline, Roo Code, OpenAI SDK) ดึง `reasoning_content` ออกจากประวัติที่พวกเขาเล่นซ้ำ OmniRoute กู้คืนจากแคชฝั่งเซิร์ฟเวอร์ ดังนั้นคำขอที่อัปสตรีมเห็นจึงสอดคล้องกัน ปัญหา #1628 ทำให้เกิดความคงอยู่ memory/SQLite แบบไฮบริด ดังนั้นแคชจึงรอดพ้นจากการรีสตาร์ทกระบวนการ

## สถาปัตยกรรม

```
Turn N (assistant generates):
  → response contains reasoning_content + tool_calls
  → if requiresReasoningReplay(provider, model): cacheReasoningFromAssistantMessage()
      writes (memory + DB), keyed by every tool_call.id
  → forward response to client (which may or may not retain reasoning)

Turn N+1 (client sends follow-up):
  → translator detects: requiresReasoningReplay(provider, model) === true
  → for each assistant message with tool_calls and no reasoning_content:
      lookupReasoning(toolCalls[0].id) → memory → DB
      hit  → msg.reasoning_content = cached; recordReplay()
      miss → msg.reasoning_content = "" (legacy fallback for older DeepSeek)
  → upstream sees consistent history → no 400
```

การจับภาพเกิดขึ้นใน `open-sse/handlers/chatCore.ts` (สองไซต์ ที่ไซต์การโทร `cacheReasoningFromAssistantMessage` สองแห่ง) การเล่นซ้ำเกิดขึ้นใน `open-sse/translator/index.ts` หลังจากการบังคับสคีมา แต่ก่อนที่จะส่ง

การเลี้ยวของผู้ช่วยแบบธรรมดา (ไม่ใช่การเรียกใช้เครื่องมือ) จะมีการคีย์ที่แตกต่างกัน: `buildAssistantMessageCacheKey()` ย่อยขอบเขตเซสชันบวกกับการถอดเสียงรูปแบบ OpenAI ที่เป็นมาตรฐานจนถึงเทิร์นนั้น เนื่องจาก DeepSeek ต้องการเหตุผลของ _every_ ก่อนเทิร์นเมื่อมี `tools` ปรากฏ สำหรับเป้าหมาย Responses-API (เช่น `opencode-go/deepseek-v4-flash` ที่ถูกกำหนดเส้นทางไปยัง `/responses`) ส่วนอัปสตรีมจะมี `input` ไม่ใช่ `messages` ดังนั้น `translateRequest()` (`open-sse/translator/index.ts`) จะรายงานการถอดเสียง Pivot ที่ย่อยผ่านตัวเลือกการโทรกลับ และไซต์ที่จับภาพจะย่อยการถอดเสียงเดียวกันนั้น บัตรผ่านการเล่นซ้ำของ Responses ทำงานบน OpenAI pivot สำหรับทุกรูปแบบต้นฉบับ ดังนั้นไคลเอ็นต์ข้อความ Anthropic (Claude → OpenAI → Responses) จะถูกเล่นซ้ำด้วยเช่นกัน

## พื้นที่เก็บข้อมูล — หน่วยความจำไฮบริด + SQLite

เส้นทางลัดใช้ `Map` ในหน่วยความจำ (LRU-by-creation) ที่สนับสนุนโดยตาราง SQLite สำหรับการกู้คืนข้อขัดข้องและการมองเห็นแดชบอร์ด

| ชั้น        | การนำไปปฏิบัติ                                 | วัตถุประสงค์                                     |
| ----------- | ---------------------------------------------- | ------------------------------------------------ |
| หน่วยความจำ | `Map` ใน `open-sse/services/reasoningCache.ts` | การค้นหาที่รวดเร็ว ขับไล่ที่เก่าแก่ที่สุดที่ 200 |
| DB          | ตาราง `reasoning_cache` (`src/lib/db/`)        | ยังคงมีอยู่ตลอดการรีสตาร์ท สถิติการขับเคลื่อน    |

เขียนไปทั้งคู่ อ่านคำแนะนำเกี่ยวกับหน่วยความจำก่อน จากนั้นจึงถอยกลับไปที่ DB ( การเข้าชม DB ได้รับการเลื่อนระดับกลับเข้าไปในหน่วยความจำ) ความล้มเหลว DB นั้นไม่ร้ายแรง — แคชในหน่วยความจำยังคงให้บริการเส้นทางร้อน

**ค่าเริ่มต้น:**

- TTL: `2h` (`TTL_MS = 2 * 60 * 60 * 1000`)
- รายการหน่วยความจำสูงสุด: `200` (`MAX_MEMORY_ENTRIES`)
- การขับไล่: `createdAt` ที่เก่าที่สุดก่อน

## สคีมาฐานข้อมูล

การโยกย้าย: `src/lib/db/migrations/033_create_reasoning_cache.sql`

```sql
CREATE TABLE IF NOT EXISTS reasoning_cache (
  tool_call_id   TEXT PRIMARY KEY,
  provider       TEXT NOT NULL,
  model          TEXT NOT NULL,
  reasoning      TEXT NOT NULL,
  char_count     INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL DEFAULT (datetime('now')),
  expires_at     INTEGER NOT NULL
);
```

ดัชนี: `expires_at`, `provider`, `model`, `created_at`. `expires_at` ถูกจัดเก็บเป็น Unix epoch วินาที; เลเยอร์ SELECT ทำให้ค่าข้อความเดิมเป็นปกติผ่าน `EXPIRES_AT_EPOCH_SQL`

## หมายเหตุการปฏิบัติงาน

- **การล้างข้อมูล:** `cleanupReasoningCache()` ล้างรายการหน่วยความจำที่หมดอายุและรัน `DELETE FROM reasoning_cache WHERE expires_at <= unixepoch('now')` เจ้าหน้าที่ตรวจสุขภาพโทรมาเป็นระยะๆ
- **การกู้คืนความเสียหาย:** หลังจากรีสตาร์ท หน่วยความจำจะว่างเปล่า แต่ DB ยังคงมีรายการที่ยังไม่หมดอายุ การค้นหาครั้งแรกสำหรับ `tool_call_id` ที่กำหนดคือการเข้าชม DB การค้นหาครั้งต่อไปคือการเข้าถึงหน่วยความจำ
- **ไม่มีเหตุผล ไม่มีแคช:** `cacheReasoningFromAssistantMessage` ส่งคืน `0` เมื่อข้อความผู้ช่วยไม่มีฟิลด์ `reasoning_content` / `reasoning` ดังนั้นการตอบกลับโดยไม่คิดจึงไม่มีค่าใช้จ่าย
- **การเขียนก็มีรั้วรอบขอบชิดเช่นกัน:** ไซต์การโทรทั้งสองใน `chatCore.ts` (ไม่ใช่สตรีมมิ่งและสตรีมมิ่ง) เรียก `cacheReasoningFromAssistantMessage()` เมื่อ `requiresReasoningReplay(provider, model)` คือ `true` — ซึ่งเป็นเพรดิเคตเดียวกันในการตรวจสอบด้านการอ่าน การติดตั้งที่ไม่เคยแตะต้องผู้ให้บริการเล่นซ้ำจะหยุดจ่ายเงินสำหรับการเขียน การอัปเดตดัชนี และ try/catch ในทุกคำตอบที่มีเหตุผล
- **ผู้ให้บริการที่ไม่เข้มงวด:** เมื่อ `requiresReasoningReplay` คือ `false` และรูปแบบเป้าหมายคือ OpenAI นักแปล** แถบ** ช่อง `reasoning_content` ใดๆ จากข้อความขาออก — OpenAI การแชทเสร็จสิ้นไม่ยอมรับ

## Muse ทึบแสง-เหตุผลความเป็นเจ้าของ

Muse (`muse-code`) ส่งคืนเหตุผลทึบแสงที่ผูกกับผู้โทร (`encrypted_content`) การเล่นซ้ำภายใต้บัญชีอื่นหรือข้อมูลประจำตัวที่ถูกเตือนจะล้มเหลวในอัปสตรีม ดังนั้นคำขอ OAuth ดั้งเดิมจึงใช้การเป็นเจ้าของระดับเซสชันแทนการหมุนเวียนต่อคำขอ (`src/sse/services/museSessionOwnership.ts` บังคับใช้ใน `src/sse/handlers/chat.ts`) การเชื่อมต่อคีย์ API ที่เลือกไว้อย่างชัดเจนและการกำหนดค่าเฉพาะคีย์ API จะคงเส้นทางที่มีอยู่ไว้โดยไม่มีโหมดความเป็นเจ้าของนี้

- จัดหาเซสชันที่เสถียร ID ในทุกเทิร์น: `x-omniroute-session-id`, `x-omniroute-session`, `x-session-id` หรือ `x-codex-session-id`; หรือใช้ `prompt_cache_key`, `session_id`, `conversation_id` หรือ `metadata.session_id` ในร่างกาย (ตามลำดับก่อนหน้านั้น) IDs ที่หายไปหรือว่างเปล่าจะคืนค่า 400 เมื่อมีบัญชี OAuth ดั้งเดิมสองบัญชีขึ้นไปที่ใช้งานอยู่ ด้วยบัญชี OAuth เดียว ไม่มีอะไรให้หมุนเวียนไป ดังนั้นคำขอดังกล่าวจะยกเลิกการปักหมุดการกำหนดเส้นทาง ขอบเขตรวมถึง OmniRoute API-key ID ของผู้เรียก
- เซสชันอิสระใหม่แบบหมุนเวียนข้ามบัญชี OAuth ดั้งเดิมที่ใช้งานอยู่ซึ่งได้รับอนุญาตตามนโยบายการเชื่อมต่อคีย์ API ซึ่งเรียงลำดับโดยการเชื่อมต่อ ID Round-robin ข้ามบัญชีที่อยู่ในคูลดาวน์การเชื่อมต่อ โดยมีสถานะเทอร์มินัล (`banned`, `expired`, `credits_exhausted`) หรือล็อคโมเดลสำหรับโมเดลที่ร้องขอ Muse ความล้มเหลวต้นน้ำจะบันทึกคูลดาวน์และสถานะเบรกเกอร์เช่นเดียวกับผู้ให้บริการรายอื่น การเชื่อมต่อที่บังคับอย่างชัดเจนจะข้ามการวนซ้ำสำหรับเซสชันใหม่ แต่ไม่สามารถแทนที่เจ้าของที่มีอยู่ได้
- จนกว่าเจ้าของจะตอบสนองได้สำเร็จ เซสชันที่เจ้าของไม่พร้อมใช้งานจะถูกอ้างสิทธิ์อีกครั้งในบัญชีที่ดี หลังจากการตอบกลับสำเร็จครั้งแรก เซสชันจะยังคงตรึงอยู่กับเจ้าของรายนั้นจนกว่าจะไม่มีการใช้งานเป็นเวลา 30 วัน (`MUSE_SESSION_IDLE_TTL_MS`)
- การต่อเนื่องและผลลัพธ์ของเครื่องมือทุกครั้งจะถูกตรึงไว้ที่เจ้าของเซสชัน: การเชื่อมต่อ ข้อมูลประจำตัวของบัญชี และการสร้างข้อมูลรับรองการอนุมาน ได้รับการตรวจสอบอีกครั้งก่อนที่จะพยายามอัปสตรีม รวมถึงการลองรีเฟรชข้อมูลรับรองอีกครั้ง การอ้างอิงการเรียก IDs/item และการเรียกเครื่องมือ Chat Completions การเรียก IDs จะต้องได้รับการบันทึกสำหรับเซสชันและรุ่นนั้น
- SQLite `key_value` บันทึกในเนมสเป `muse_session_ownership` (`src/lib/db/museSessionOwnership.ts`) ยังคงเป็นเจ้าของและเคอร์เซอร์หมุนตลอดการรีสตาร์ท การอ้างสิทธิ์และการตอบกลับแต่ละครั้งจะรีเฟรชการประทับกิจกรรมของเซสชัน เซสชันที่ไม่ได้ใช้งานนานกว่า `MUSE_SESSION_IDLE_TTL_MS` ที่ถูกตัดแต่ง (หมุดเจ้าของ แฟล็กแสดงผล และแฮช opaque/reference ที่บันทึกไว้) มากที่สุดหนึ่งครั้งทุกๆ 10 นาทีและอยู่ในแบทช์ที่มีขอบเขต ดังนั้นการเล่นซ้ำประวัติในภายหลังจึงล้มเหลวในการปิดในฐานะเจ้าของที่ไม่รู้จัก บันทึกประกอบด้วยการเชื่อมต่อ IDs และแฮชของข้อมูลประจำตัวบัญชี ข้อมูลรับรอง เนื้อหาที่ไม่ชัดเจน และการอ้างอิงต่อเนื่อง ไม่ใช่ความลับหรือประวัติการสนทนา ลูกค้าจะต้องเก็บรักษาและส่งประวัติทั้งหมดและเหตุผลที่คลุมเครือ
- การให้เหตุผลที่ไม่ชัดเจนหรือไม่ทราบสาเหตุ เจ้าของหายไป บัญชีเจ้าของไม่พร้อมใช้งาน หรือการเปลี่ยนแปลงรุ่นที่มีประวัติที่บันทึกไว้ล้มเหลวในการปิดด้วย 4xx/503 — ที่ชัดเจน ไม่เคยเฟลโอเวอร์ข้ามบัญชีแบบเงียบ และไม่เคยทิ้งการให้เหตุผล
- รหัสบัญชีเดียวกันที่ถูกเรียกคืนจะถูกนำมาใช้เฉพาะเมื่อเซสชันบันทึกไม่มีประวัติการเล่นซ้ำ เซสชันที่บันทึกไว้จะปิดไม่สำเร็จจนกว่าจะเริ่มใหม่
- การตอบสนองต้นทางที่ว่างเปล่า (`upstream_empty_response` / `empty_response` ไม่มีการปล่อยสัญญาณไปยังผู้โทร) จะถูกลองอีกครั้งสูงสุดสองครั้งกับเจ้าของคนเดียวกัน หลังจาก 0.5 วินาที จากนั้น 1.5 วินาที (`MUSE_EMPTY_RESPONSE_RETRY_DELAYS_MS`) หากความพยายามทั้งหมดว่างเปล่า 502 ดั้งเดิมจะถูกส่งคืนโดยไม่มีคูลดาวน์หรือเครื่องหมายเบรกเกอร์ ดังนั้นการตอบกลับที่ไม่สม่ำเสมอจะไม่ล็อคเจ้าของ
- คำขอ `muse-code` ทั้งหมดจะเลี่ยงการอ่านและเขียน semantic-cache รวมถึงการเขียนแบบสตรีมมิ่ง ดังนั้นเอาต์พุตทึบแสงที่แคชไว้จึงไม่สามารถรับเจ้าของเซสชันรายอื่นได้
