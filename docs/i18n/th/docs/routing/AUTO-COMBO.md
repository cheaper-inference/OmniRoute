## การกำหนดเส้นทางอัตโนมัติแบบ Zero-Config (คำนำหน้า `auto/` )

ไม่จำเป็นต้องสร้างคอมโบ ใช้ `auto` หรือตัวแปร `auto/` โดยตรงในไคลเอนต์ของคุณ

### ตัวอย่างด่วน

| รุ่น ID             | พฤติกรรม                                                                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`              | โมเดลผู้ให้บริการที่มีสิทธิ์ กลยุทธ์ LKGP และน้ำหนักที่สมดุล                                                                                               |
| `auto/coding`       | ตุ้มน้ำหนักคุณภาพอันดับแรกสำหรับงานเขียนโค้ด                                                                                                               |
| `auto/fast`         | มอบเวลาแฝงที่ต่ำกว่าและผู้ให้บริการที่ดี                                                                                                                   |
| `auto/cheap`        | น้ำหนักที่ประหยัดต้นทุน: ช่วยให้ราคาแค็ตตาล็อกลดลง รักษาความเหนียว LKGP ไม่ใช่การเรียงลำดับแรกสุดที่เข้มงวดที่สุด                                          |
| `auto/subscription` | โควต้ารวมแผนเท่านั้น ได้รับการยืนยันแล้ว พูลว่างส่งคืน HTTP 503 ไม่เคยมีการเรียกเก็บเงินสำรอง                                                              |
| `auto/thrifty`      | สมัครสมาชิก → keyless → ฟรี → ราคาถูก → พรีเมียม ทีละขั้น; สามารถเรียกเก็บเงินได้                                                                          |
| `auto/offline`      | เอื้ออำนวยต่อความพร้อมใช้งานของโควต้าและสุขภาพของผู้ให้บริการ (แพ็ค `offline-friendly` ); ไม่ใช่คำขอ — การอนุมานแบบออฟไลน์ยังคงส่งไปยังผู้ให้บริการระยะไกล |
| `auto/smart`        | ตุ้มน้ำหนักคุณภาพต้องมาก่อนด้วยอัตราการสำรวจ 10%                                                                                                           |
| `auto/lkgp`         | ชัดเจน LKGP โดยมีน้ำหนักเท่ากับ `auto` เริ่มต้น                                                                                                            |
| `auto/chaos`        | แผงขนานที่มีหนึ่งรุ่นต่อผู้ให้บริการ โดยค่าเริ่มต้นสูงสุดห้ารายการ โดยส่งคืนหนึ่งคำตอบ                                                                     |

รูปแบบน้ำหนักยังคงความเหนียวของ LKGP ดังนั้น `fast` และ `cheap` จึงแสดงความต้องการ แทนที่จะรับประกันเวลาแฝงหรือราคาต่ำสุดในทุกคำขอ `auto/chaos` ทำการโทรอัปสตรีมหลายครั้ง `auto/thrifty` อาจใช้กำลังการผลิตที่ต้องชำระเงิน การกลับคืนสู่โควต้าแผนจะขึ้นอยู่กับสิทธิ์ที่ต่ออายุและคูลดาวน์การเชื่อมต่อ ไม่ใช่แค่เวลารีเซ็ต ดู [การกำหนดเส้นทางการสมัครสมาชิกก่อน](./SUBSCRIPTION_LADDER.md)

### หมวดหมู่ × Tier Composition (`auto/<category>:<tier>`)

ส่วนต่อท้ายสไตล์ OpenRouter แยกจากกัน** เส้นทางแบบไหน** (หมวดหมู่) จาก** วิธีเพิ่มประสิทธิภาพ** (ระดับ) เพื่อให้คุณสามารถเขียนได้อย่างอิสระ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **หมวดหมู่** : `coding` · `reasoning` · `vision` · `chat` · `multimodal` `vision`/`multimodal` เก็บโมเดลที่มีความสามารถในการมองเห็นไว้ `reasoning` เก็บโมเดล reasoning/thinking `coding` และ `chat` ไม่ได้เพิ่มตัวกรองความสามารถ หมวดหมู่ที่ไม่ใช่การแชทจะเลือกน้ำหนักที่มีคุณภาพก่อนก่อนที่จะแทนที่ระดับใดๆ
- **ชั้น** (เลือกน้ำหนักการให้คะแนน / ตัวกรองพูล): `fast` (จัดส่งเร็ว) · `cheap` (นามแฝง `floor` ประหยัดต้นทุน) · `reliable` (เสถียรภาพของตัวตัดวงจร + latency เสถียรภาพ) · `free` / `pro` (กรองพูลตามระดับโมเดลผ่าน `classifyTier` — free-tier เทียบกับพรีเมียม) `subscription` และ `thrifty` ใช้ [บันไดการสมัครสมาชิก](./SUBSCRIPTION_LADDER.md) ตามการเชื่อมต่อ

| ตัวอย่าง               | แก้เป็น                                                             |
| ---------------------- | ------------------------------------------------------------------- |
| `auto/coding:fast`     | พูลที่มีสิทธิ์ น้ำหนักเวลาแฝงต่ำ                                    |
| `auto/coding:cheap`    | พูลที่มีสิทธิ์ น้ำหนักประหยัดต้นทุน (นามแฝง `auto/coding:floor`)    |
| `auto/reasoning:pro`   | รุ่น reasoning/thinking เท่านั้น ระดับพรีเมี่ยม                     |
| `auto/vision`          | รุ่นที่มีความสามารถในการมองเห็นพร้อมน้ำหนักที่มีคุณภาพเป็นอันดับแรก |
| `auto/multimodal:free` | โมเดลที่รองรับหลายรูปแบบ Free Tier เท่านั้น                         |

`auto/<category>[:<tier>]` ที่ถูกต้องใดๆ ได้รับการแก้ไขตามความต้องการ ชุดย่อยที่ดูแลจัดการถูกโฆษณาใน `/v1/models` และแดชบอร์ด (`AUTO_SUFFIX_VARIANTS` ใน `open-sse/services/autoCombo/builtinCatalog.ts`) การกรอง Category/tier คือ** ปิดไม่สำเร็จตามค่าเริ่มต้น** : หากไม่มีโมเดลที่เข้าเกณฑ์ คอมโบเสมือนจะมีพูลว่าง และตัวแก้ไขการแชทจะส่งคืน HTTP 503 (`src/sse/handlers/chatHelpers.ts`) ตัวกรองคือ `narrowPoolByCategoryTier` ใน `open-sse/services/autoCombo/virtualFactory.ts`

`OMNIROUTE_AUTO_FREE_FALLBACK_TO_FULL_POOL=true` คืนค่า category/tier ทางเลือกดั้งเดิมไปเป็นพูลเต็มเมื่อตัวกรองไม่ตรงกับสิ่งใด สิ่งนี้สามารถละทิ้งข้อจำกัดระดับหรือความสามารถที่ร้องขอได้ ตัวกรองตระกูลโมเดลไม่เคยใช้ทางเลือกนั้น และการกำหนดเส้นทางแบบสมัครสมาชิกเท่านั้นยังคงต้องมีความจุที่รวมแผนที่ผ่านการตรวจสอบแล้ว

> **ข้อมูลโมเดลสด:** ฟิตเนสกำหนดเส้นทางอัตโนมัติได้รับการแจ้งโดยสด** อารีน่า ELO** อันดับ +** รุ่น.dev** ข้อมูลระดับเมื่อเปิดแฟล็ก `ARENA_ELO_SYNC_ENABLED` (มิฉะนั้นจะถอยกลับไปยังแผนที่ฟิตเนสแบบคงที่)

**วิธีใช้:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # favor coding task fit
model: "auto/fast"            # favor lower latency
model: "auto/cheap"           # favor lower catalog cost
```

**จะเกิดอะไรขึ้น:**

1. OmniRoute ตรวจพบคำนำหน้า `auto/` ใน `src/sse/handlers/chat.ts`
2. สอบถามทั้งหมด** การเชื่อมต่อของผู้ให้บริการที่ใช้งานอยู่** จากฐานข้อมูล
3. ใช้ตัวกรองข้อมูลรับรอง การมองเห็นโมเดล และตัวกรองสิทธิ์
4. สร้างตัวเลือก provider/model แบบลอจิคัลจากโมเดลที่มีอยู่ โดยเก็บรายการบัญชีที่อนุญาตที่มีสิทธิ์สำหรับการจัดส่ง
5. สร้างก** คำสั่งผสมเสมือน** ในหน่วยความจำ (ไม่เก็บไว้ใน DB)
6. เส้นทางโดยใช้โปรไฟล์น้ำหนัก + LKGP กลยุทธ์ของตัวแปรที่เลือก

**คุณสมบัติที่สำคัญ:**

- ✅** เปิดตลอดเวลา:** ไม่ต้องสลับ ไม่ต้องสร้างคอมโบ ไม่ต้องกำหนดค่าใดๆ
- ✅** พลวัต:** สะท้อนถึงผู้ให้บริการที่เชื่อมต่อในปัจจุบันโดยอัตโนมัติ
- ✅** ความเหนียวของเซสชัน:** LKGP ช่วยให้มั่นใจว่าผู้ให้บริการที่ประสบความสำเร็จคนสุดท้ายจะได้รับการจัดลำดับความสำคัญ
- ✅** บัญชีหลายบัญชีทราบ:** ผู้สมัคร provider/model แบบลอจิคัลจะรักษารายการบัญชีที่อนุญาตไว้
- ✅** ไม่จำเป็นต้องบันทึกคอมโบ:** การกำหนดค่าเสมือนจะยังคงอยู่ในหน่วยความจำ เมตริกการกำหนดเส้นทางปกติและสถานะรันไทม์ยังคงสามารถคงอยู่ได้

### การควบคุมตัวเลือกต่อคีย์ (#7819 ระดับ 1 + 2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = ส่วนต่อท้ายหลัง `auto/` หรือตัวอักษร `auto` สำหรับช่องฐาน) คือ** อ่านอย่างเดียว** จุดสิ้นสุดที่แสดงรายการกลุ่มตัวเลือกปัจจุบันของช่อง `auto/*` ที่ตกแต่งด้วยความสามารถในการเข้าถึงแบบสด โดยการนำการอ่านความยืดหยุ่นที่มีอยู่กลับมาใช้ใหม่ (ไม่ใช้ตัวแบ่งดิบ `state`):

- ผู้ให้บริการ เซอร์กิตเบรกเกอร์ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- คูลดาวน์การเชื่อมต่อ — `rateLimitedUntil` / `testStatus` บนแถว `provider_connections` ที่แก้ไขแล้ว
- การล็อกโมเดล — `isModelLocked(provider, connectionId, model)`

ผู้สมัครแต่ละคนจะมีแฟล็ก `excluded` ของคีย์ API นี้ด้วย การยกเว้นจะถูกจัดเก็บต่อคีย์ API ( ตาราง `auto_candidate_overrides`, การย้ายข้อมูล `128`) — OmniRoute เป็นผู้เช่ารายเดียวที่ไม่มีตาราง `users` ดังนั้น `apiKeyId` จึงเป็นข้อมูลระบุตัวตนต่อผู้โทรที่แท้จริงที่ใกล้เคียงที่สุด — และบังคับใช้ที่โช้คพอยต์พูลผู้สมัครใน `open-sse/services/autoCombo/virtualFactory.ts` ผ่าน `filterExcludedCandidates()` ที่ทดสอบโดยหน่วยล้วนๆ (`open-sse/services/autoCombo/candidateOverrides.ts`) ไส้กรองก็คือ** เปิดไม่สำเร็จ** : apiKeyId/channel ที่ไม่ได้ตั้งค่าหรือการค้นหา DB ล้มเหลวทั้งคู่ปล่อยให้พูลไม่มีการกรอง ดังนั้นตัวดำเนินการที่ไม่มีการแทนที่ที่กำหนดค่าไว้จะเห็นการกำหนดเส้นทางไบต์ที่เหมือนกันก่อนคุณลักษณะนี้

**เลื่อนออกไปเป็นประเด็นติดตามผล:** น้ำหนักต่อผู้สมัคร + การสั่งซื้อที่ชัดเจน (ระดับ 3 — ป้อนเข้าสู่เส้นทางกลยุทธ์ weighted/priority ที่มีอยู่) และปักหมุดกลยุทธ์ `combo.ts` เฉพาะต่อช่อง `auto/*` (ระดับ 4) ดูแผน #7819 สำหรับคำถามปลายเปิดว่าการแทนที่ควรคงอยู่ต่อคีย์ API หรือกลายเป็นส่วนกลางตามโมเดลผู้เช่ารายเดียว

**เบื้องหลัง:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

## การตั้งค่าบัญชีสำหรับคอมโบอัตโนมัติที่บันทึกไว้

โปรแกรมแก้ไขอัตโนมัติอัจฉริยะเสนอทางเลือก** การตั้งค่าบัญชี** ส่วน. การเชื่อมต่อแต่ละรายการสามารถเป็นที่ต้องการ ปกติ (ค่าเริ่มต้น) สำรอง หรือไม่รวม การเชื่อมต่อหลายรายการสามารถแชร์ระดับได้ เลือกอัตโนมัติภายในระดับที่มีสิทธิ์ระดับแรก โดยคงลักษณะการทำงานของ scoring/router ไว้ตรงนั้น ความพยายามที่ล้มเหลวจะตกไปสู่บัญชีที่เป็นรูปธรรมที่เหลืออยู่ แนะนำให้ใช้ก่อนปกติก่อนสำรอง การเชื่อมต่อที่แยกออกจะไม่ถูกใช้โดยคอมโบนี้

การตั้งค่าถูกจัดเก็บเป็น `config.accountPreferences` คีย์โดยการเชื่อมต่อ ID:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

แผนที่ที่ถูกละเว้นหรือว่างเปล่าจะคงเส้นทางที่มีอยู่ไว้ การตั้งค่าไม่เปิดใช้งานการเชื่อมต่อที่ถูกปิดใช้งาน ให้สิทธิ์การเข้าถึงคีย์ API กู้คืนผู้สมัครที่ถูกบล็อกโควต้า หรือเลี่ยงการตรวจสอบงบประมาณ ความพยายามแต่ละครั้งจำกัดอยู่ที่การเชื่อมต่อที่เป็นรูปธรรม ดังนั้นบัญชีสำรองจึงไม่สามารถข้ามระดับหลังเราเตอร์คอมโบได้ ความเกี่ยวข้องของเซสชันที่มีอยู่อาจรักษาบัญชีที่มีสิทธิ์ไว้ได้ ไม่รวมบัญชีที่ผูกไว้กับเทิร์นดั้งเดิมที่หยุดซึ่งจะเปลี่ยนแทนการเปลี่ยนบัญชีอย่างเงียบ ๆ

การตั้งค่าที่กำหนดค่าไว้จะใช้เส้นทางอัตโนมัติที่รับรู้ถึงบัญชี: ทางลัดแคชบริบทที่ไม่ได้ผูกไว้ สมาร์ทไปป์ไลน์ ความโกลาหล และทางลัดเงาจะไม่ถูกส่งไป การป้องกันความเสี่ยงแบบเก็งกำไรถูกปิดใช้งานสำหรับคำขอเหล่านี้ ดังนั้นบัญชีสำรองจึงไม่สามารถแข่งขันกับบัญชีที่ต้องการได้ กลยุทธ์คอมโบอื่นๆ ไม่ตีความการตั้งค่านี้ การเปลี่ยนคอมโบออกจากอัตโนมัติจะคงการตั้งค่าที่บันทึกไว้ไว้สำหรับการสลับกลับในภายหลัง

## ชื่อคอมโบที่ตรงกับรหัสโมเดลจริง

คอมโบที่ `name` เหมือนกับรหัสโมเดลเปลือย (เช่นคอมโบชื่อ `gpt-5.5`) นั้นเป็น** รูปแบบที่ตั้งใจและสนับสนุน** ไม่ใช่ข้อบกพร่อง: เป็นกลไกสำหรับทางเลือกผู้ให้บริการสำรองต่อรุ่น ID ที่บันทึกไว้ใน [#6940](https://github.com/cheaper-inference/OmniRoute/issues/6940) เนื่องจากความละเอียดของคอมโบได้รับการตรวจสอบก่อนที่จะมีการแก้ไข bare-model-id (`getComboForModel()` ใน `src/sse/services/model.ts`) คำขอสำหรับ bare id `gpt-5.5` จึงถูกส่งผ่านเป้าหมายของคอมโบ (เช่น `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) แทนที่จะตรงไปยังผู้ให้บริการรายเดียว — สิ่งนี้จะนำคำสั่งคอมโบก่อนเขียนซ้ำซึ่งสร้างไว้สำหรับ [#3227/#3233](https://github.com/cheaper-inference/OmniRoute/issues/3227) และทดสอบการถดถอยโดย `tests/unit/responses-combo-resolution-3227.test.ts` และ `tests/unit/combo-name-codex-responses-rewrite.test.ts`

การสร้างหรือเปลี่ยนชื่อคอมโบเป็นชื่อที่เงารหัสโมเดลจริง** ไม่เคยปฏิเสธ** — การทำเช่นนั้นจะทำให้เวิร์กโฟลว์ที่บันทึกไว้นี้เสียหาย แทน (#8530) `POST /api/combos` และ `PUT /api/combos/[id]` จะแนบฟิลด์ `warning` ที่ไม่ปิดกั้นเข้ากับการตอบสนองเมื่อชื่อ (ใหม่) ขัดแย้งกับรหัสโมเดลจริง:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

เมื่อบูต `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ยังบันทึกคำเตือน `[STARTUP]` หนึ่งบรรทัดโดยแจกแจงทุกคอมโบที่มีอยู่ซึ่งปกปิดรหัสโมเดล ดังนั้นผู้ปฏิบัติงานที่โจมตีสิ่งนี้โดยไม่ได้ตั้งใจ (แทนที่จะตั้งใจต่อ #6940) จะมีสัญญาณ ผู้ช่วยการตรวจจับอาศัยอยู่ใน `src/lib/combos/modelNameCollision.ts`

## การเรียกคำสั่งผสมแบบกำหนดเองจากไคลเอนต์

คอมโบแบบถาวร (การตั้งค่า → Combos) จะใช้เฉพาะเมื่อไคลเอนต์ส่งคอมโบ** ชื่อที่แน่นอน** ในฟิลด์ `model` — ไม่มีการจับคู่ชื่อคอมโบแบบคลุมเครือหรือบางส่วน และไม่มีส่วนนำหน้า `auto/` ที่เกี่ยวข้อง ลำดับการแก้ปัญหา (`getComboForModel()` ใน `src/sse/services/model.ts`):

1. การจับคู่ชื่อคำสั่งผสมแบบตรงทั้งหมด (`model: "my-combo"`)
2. คำนำหน้า `combo/<name>` (`model: "combo/my-combo"`)
3. การแมป glob ของโมเดล → คอมโบ (`/api/model-combo-mappings`)

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ข้อผิดพลาดทั่วไปสองประการ:

- **`auto` ไม่ได้ใช้คอมโบของคุณ** `auto`/`auto/*` สร้างกลุ่มตัวเลือกการกำหนดค่าเป็นศูนย์ของตัวเองและปรึกษาเฉพาะคอมโบที่คงอยู่หากคอมโบชื่อ `auto` อย่างแท้จริง (ไม่แนะนำ) หากต้องการกำหนดเส้นทางผ่านคอมโบ ให้ส่งชื่อที่แน่นอน — ไม่ใช่ `auto`
- **`openrouter/auto` เป็นผลิตภัณฑ์ OpenRouter ที่จ่ายจริง** ("ดีที่สุดโดยอัตโนมัติ") ไม่ใช่นามแฝง OmniRoute เป็นรายการโมเดลคงที่รายการเดียวของรีจิสทรี OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) และมีการเรียกเก็บเงินแยกต่างหาก ใช้การตั้งค่า → การกำหนดเส้นทาง → ซ่อนโมเดลที่ต้องชำระเงินเพื่อแยกออกจากพูล `auto`

ดู [#7992](https://github.com/cheaper-inference/OmniRoute/issues/7992) และ [#7111](https://github.com/cheaper-inference/OmniRoute/issues/7111) สำหรับความสับสนดั้งเดิมในเอกสารนี้

## มันทำงานอย่างไร (คอมโบอัตโนมัติยังคงมีอยู่)

Auto-Combo Engine ให้คะแนนผู้สมัคร provider/model แบบไดนามิกที่ใช้** 16 ปัจจัยที่ประกาศ** (กำหนดใน `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`) น้ำหนักเริ่มต้นรวมเป็น `1.0`; น้ำหนักที่กำหนดเองจะถูกทำให้เป็นมาตรฐานใหม่โดย `normalizeScoringWeights()` ปัจจัยสามประการมีน้ำหนักเป็นศูนย์โดยค่าเริ่มต้น: `cacheAffinity`, `resetWindowAffinity` และ `reliability` โหมดแพ็กให้น้ำหนัก `reliability` เป็น `0.03` หรือ `0.04` ใน `reliability-first`; `quality` ดำเนินการ `0.03` ตามค่าเริ่มต้นและใน `quality-first` และ `0.02` ในชุดอื่น ๆ `cacheAffinity` ยังขจัดความซ้ำซ้อนของแคชพร้อมท์ที่อยู่นอกคะแนนถ่วงน้ำหนักด้วย

![Auto-Combo 16-factor scoring](../diagrams/exported/auto-combo-scoring.svg)

> ที่มา: [diagrams/auto-combo-scoring.mmd](../diagrams/auto-combo-scoring.mmd) (สร้างใหม่ผ่าน `npm run docs:render-diagrams`) ชื่อไฟล์เป็นข้อมูลทางประวัติศาสตร์ แหล่งที่มาและแผนภาพที่แสดงผลแสดงปัจจัยทั้งหมด 16 ประการที่ประกาศใน `DEFAULT_WEIGHTS`

| :-------------------- | :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `quota`               | 0.1429          | โควต้าคงเหลือ / อัตราจำกัดเฮดรูม [0..1]                                                                                                                                                                       |

| `costInv`             | 0.1429          | ผกผัน** ผสม** ราคา (อินพุต 60% + ราคาโทเค็นเอาท์พุต 40%, ปรับมาตรฐาน) — ถูกกว่า = คะแนนสูงกว่า                                                                                                                |
| `latencyInv`          | 0.1143          | เวลาแฝง p95 แบบผกผันทำให้เป็นมาตรฐานเพื่อรวม — เร็วขึ้น = คะแนนที่สูงขึ้น                                                                                                                                     |
| `taskFit`             | 0.0762          | ความเหมาะสมของประเภทงาน (การเขียนโค้ด การทบทวน การวางแผน การวิเคราะห์ การดีบัก เอกสาร)                                                                                                                        |

| `specificityMatch`    | 0.0476          | จับคู่ระหว่างความจำเพาะของคำขอ (คำใบ้ที่ชัดเจน) และระดับโมเดล                                                                                                                                                 |

| `quality`             | 0.03            | สัญญาณคุณภาพเอาต์พุตที่ขับเคลื่อนด้วยคำติชมจากตัวติดตามคุณภาพเหตุการณ์การกำหนดเส้นทาง ผู้สมัครที่ไม่มีการสังเกตการณ์จะได้รับคะแนนเป็นกลาง 0.5                                                                 |

ตัวติดตาม `quality` ในหน่วยความจำ (`open-sse/services/routing/quality.ts`) จะว่างเปล่าหลังจากการรีสตาร์ทแบบเย็น ดังนั้นผู้สมัครทุกคนจึงให้คะแนน `0.5` ที่เป็นกลางจนกว่าการสังเกตครั้งแรกจะไปถึง

> **โควต้าที่อ่านไม่ได้ (#15347)** เมื่อผู้ให้บริการมีโควต้าดึงข้อมูลแต่ส่งคืนสิ่งใดที่ไม่สามารถอ่านได้ (การดึงข้อมูลล้มเหลว ข้อมูลรับรองหายไป การใช้งานข้อความเท่านั้น หรือสแน็ปช็อตที่มีรูปแบบไม่ถูกต้องโดยไม่มี `windows` ที่แยกวิเคราะห์ได้และไม่มีจำกัด `percentUsed` รวมถึง `percentUsed: null`) ผู้สมัครจะให้คะแนน `0` บนแกน `quota` และคะแนนสุดท้ายจะถูกคูณด้วย `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`) ซึ่งเป็นรูปแบบการลงโทษแบบนุ่มนวลเช่นเดียวกับ การลงโทษสถานะการเชื่อมต่อ การอ่านการใช้งานที่ล้มเหลวถือเป็นหลักฐานเกี่ยวกับการวัดและส่งข้อมูลทางไกล ไม่ใช่ผู้ให้บริการ ดังนั้นจึงอยู่ในอันดับที่ต่ำกว่าการอ่านจริงใดๆ อย่างเคร่งครัด รวมถึงการอ่านค่า -used ที่ได้รับการยืนยัน 100% ด้วย แต่จะไม่มีการบล็อคถาวรหรือถูกไล่ออก ผู้ให้บริการที่ไม่มี cap รายงาน `unlimited: true` และให้คะแนนเป็นโควต้าเต็ม ผู้ให้บริการที่ไม่มีตัวดึงโควต้าที่ลงทะเบียนไม่มีแหล่งที่มาของการวัดและส่งข้อมูลทางไกลเลยและคงค่าเริ่มต้นไว้ที่ `100`

**รวม:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` ตามที่ประกาศไว้ใน `DEFAULT_WEIGHTS`; ตุ้มน้ำหนักที่ผู้ใช้กำหนดค่าจะถูกปรับให้เป็นมาตรฐานใหม่เป็นการแจกแจงโดย `normalizeScoringWeights()` ก่อนที่จะให้คะแนน

### การควบคุมต่อคำขอ (ส่วนหัว) — #6023 / #6024 / #6025 / #3470

คอมโบ `auto` สามารถถูกควบคุมทิศทาง **ต่อคำขอ** ผ่านส่วนหัวสามรายการได้ โดยไม่เปลี่ยนแปลงการกำหนดค่าที่จัดเก็บไว้ของคอมโบ การควบคุมเหล่านี้ใช้เฉพาะกับกลยุทธ์ `auto` และเฉพาะคำขอที่มีส่วนหัวดังกล่าวเท่านั้น; ระบบจะใช้ `modePack`/`budgetCap`/`budgetFallback` ที่บันทึกไว้ของคอมโบเมื่อไม่มีส่วนหัวนั้น

| `expiry-first`      | ใช้บัญชีที่โควต้าจะหมดอายุโดยไม่ได้ใช้ก่อน — ส่วนที่เหลือสูงสุดโดยมีกำหนดเวลาการรีเซ็ตที่ใกล้ที่สุดไปก่อน                                                                                                                                                                                                                                                                             |
| `headroom`          | เลือกเป้าหมายที่มีโควต้าเฮดรูมที่เหลืออยู่มากที่สุด                                                                                                                                                                                                                                                                                                                                   |
| `quota-weighted`    | กระจายคำขอตามความพร้อมโควต้าและปริมาณในเที่ยวบิน รักษาความสัมพันธ์ของเซสชัน                                                                                                                                                                                                                                                                                                           |
| `strict-random`     | สับไพ่ต่อคอมโบ: ทุกเป้าหมายจะถูกใช้หนึ่งครั้งก่อนที่จะสับใหม่ รอบสุดท้ายของรอบหนึ่งจะไม่เริ่มรอบถัดไป                                                                                                                                                                                                                                                                                 |
| `auto`              | ใช้การให้คะแนนคอมโบอัตโนมัติ (16 ปัจจัย) —** ที่แนะนำ**                                                                                                                                                                                                                                                                                                                               |
| `lkgp`              | Last-Known-Good Path (ปักหมุดผู้ให้บริการที่ประสบความสำเร็จคนสุดท้าย จากนั้นกลับไปสู่กฎเกณฑ์)                                                                                                                                                                                                                                                                                         |
| `context-optimized` | ลองใช้หน้าต่างบริบทที่ใหญ่ที่สุดที่รู้จักก่อน (แก้ไขขีดจำกัดความสามารถของโมเดลแล้ว)                                                                                                                                                                                                                                                                                                   |
| `cache-optimized`   | ต้องการการเชื่อมต่อที่มีสิทธิ์ที่จะเก็บคำนำหน้าพรอมต์ไว้ในแคช (`open-sse/services/combo/promptCacheAffinity.ts`, #8008)                                                                                                                                                                                                                                                               |
| `fusion` 🧬         | คลี่ออกไปยังแผงของแบบจำลองขนานกัน จากนั้นสังเคราะห์คำตอบหนึ่งคำตอบโดยกรรมการ (ดูด้านล่าง)                                                                                                                                                                                                                                                                                             |
| `pipeline`          | รันเป้าหมายตามลำดับ โดยเธรดเอาต์พุตของแต่ละขั้นตอนไปยังอินพุตของขั้นตอนถัดไป ส่งคืนเฉพาะคำตอบสุดท้ายเท่านั้น (#6396)                                                                                                                                                                                                                                                                  |
| `jev`               | รายการกำหนดลักษณะที่ผู้ใช้จัดลำดับ; TypeSafe Jev ยอมรับว่ารายการใดที่เรียกใช้สำหรับคำขอนี้ ผู้ชนะก่อน เป้าหมายที่ได้รับการยอมรับอื่นๆ จะรักษาลำดับของคุณไว้ เลือกใช้และชำระเงิน: เรียกเมื่อเปิด `COMBO_JEV_STRATEGY_ENABLED` เท่านั้น (ปิดค่าเริ่มต้น); การโทรแต่ละครั้งจะส่งข้อความที่ตัดตอนมาแบบมีขอบเขตไปที่ api.typesafe.ai กลับไปที่คำสั่งซื้อของคุณเมื่อไม่พร้อมใช้งาน (#15276) |

⭐ = ใหม่ใน v3.8.0 · 🧬 = ใหม่ใน v3.8.36

กลยุทธ์ `jev` ทำการเรียก TypeSafe แบบชำระเงินเฉพาะเมื่อเปิดใช้งาน `COMBO_JEV_STRATEGY_ENABLED` เท่านั้น คีย์ TypeSafe ที่เก็บไว้เพียงอย่างเดียวไม่สามารถเปิดใช้งานได้ เมื่อปิดแฟล็ก คอมโบจะเก็บคำสั่งของผู้ดำเนินการโดยไม่ต้องโทรออก (`open-sse/services/combo/jevAsk.ts`)

### ความหมาย `weighted`

`weighted` คือก** สุ่มจับสลากตามสัดส่วนตามคำขอ** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`) ไม่ใช่อีควอไลเซอร์:

- แต่ละคำขอดึง** หนึ่ง** ก้าวด้วยความน่าจะเป็น `weight / totalWeight`; ขั้นตอนที่เหลือจะเรียงลำดับตามน้ำหนักจากมากไปน้อยเป็นห่วงโซ่ทางเลือกสำหรับคำขอนั้น
- ขั้นที่มีน้ำหนักเป็น `0` (หรือหายไป) คือ** ไม่เคยวาด** ในขณะที่ขั้นตอนอื่นๆ มีน้ำหนัก > 0 — แต่จะสามารถใช้เป็นทางเลือกสำรองได้หลังจากที่ขั้นตอนที่วาดไว้ล้มเหลวเท่านั้น เมื่อเท่านั้น** ทั้งหมด** น้ำหนักเป็น 0 การเลือกจะสม่ำเสมอ
- ขั้นตอนที่เป้าหมายไม่พร้อมใช้งานทั้งหมด — provider เซอร์กิตเบรกเกอร์ `OPEN`, คูลดาวน์การเชื่อมต่อ, การล็อคโมเดล — จะถูกลบออกจากการดึงก่อนที่จะเกิดขึ้น (`open-sse/services/combo/targetResolution.ts`) ดังนั้นขั้นตอนเดียวที่ดีสามารถชนะทุกคำขอได้ชั่วคราว
- `stickyWeightedLimit` (การกำหนดค่าคำสั่งผสม, ค่าเริ่มต้น `1` = ปิด) จะปักหมุดขั้นตอนที่วาดไว้สำหรับความสำเร็จติดต่อกันหลายๆ ครั้งก่อนที่จะวาดใหม่

สำหรับการหมุนอย่างเข้มงวดให้ใช้ `round-robin`; น้ำหนักที่เท่ากันบน `weighted` ให้ — ทางสถิติไม่ใช่ความสมดุล — ที่เข้มงวด

### โหมดไปป์ไลน์ตัวแทน

คำสั่งผสม `pipeline` ที่มีอย่างน้อยสองรุ่นสามารถเลือกใช้การกำหนดเส้นทาง planner/executor ด้วย `config.agenticOrchestration.enabled` เป้าหมายแรกเป็นเจ้าของการวางแผนและคำตอบสุดท้าย เป้าหมายที่สองส่งเสียงการเรียกเครื่องมือแบบไคลเอ็นต์เนทีฟ OmniRoute ตรวจพบความต่อเนื่องของเครื่องมือ-ผลลัพธ์จากโปรโตคอลคำขอ ถามผู้วางแผนว่าจำเป็นต้องใช้เครื่องมือรอบอื่นหรือไม่ และทำให้ผู้ดำเนินการหรือผู้วางแผนเป็นขั้นตอนสุดท้ายที่ลูกค้าต้องเผชิญแบบไดนามิก

`config.agenticOrchestration.contextCompaction` ที่เป็นทางเลือกจะใช้งบประมาณเพย์โหลดแยกต่างหากก่อนที่จะส่งผู้วางแผนหรือผู้ดำเนินการแต่ละคน เปิดใช้งานอย่างชัดเจน:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

สิ่งเหล่านี้คืองบประมาณอักขระ JSON ที่ทำให้เป็นอนุกรมที่เลือกโดยผู้ดำเนินการ ไม่ใช่หน้าต่างบริบทโทเค็นหรือขีดจำกัดอัปสตรีมที่รับประกัน โมเดลที่แน่นอน IDs จะแทนที่ค่าเริ่มต้น เหนือเกณฑ์ขั้นต่ำ การบดอัดจะลบคำจำกัดความของเครื่องมือที่เหมือนกัน ตัดหลักฐานเครื่องมือขนาดใหญ่ออกด้วยการสรุป และลบกลุ่มประวัติเก่าที่สมบูรณ์ตามอัตราส่วนเป้าหมาย โดยยังคงรักษาคำสั่ง system/developer คำขอล่าสุดของผู้ใช้ รอบเครื่องมือสุดท้ายซึ่งรวมถึง Parallel calls/results และคำสั่งการกำหนดเส้นทางชั้นนำของ Gemini คำแนะนำระดับบนสุดและการตั้งค่าเครื่องมือจะยังคงอยู่ เครื่องหมายละเว้นบันทึกประวัติที่ถูกลบออก นี่คือการตัดแต่งตามที่กำหนด ไม่ใช่การสรุปเชิงความหมาย หากบริบทที่ปักหมุดยังเกินงบประมาณ คำขอจะส่งกลับ 413 ก่อนที่จะติดต่อโมเดล เมื่อปิดใช้การบีบอัดหรือต่ำกว่าเกณฑ์ คำขอจะผ่านโดยไม่มีการเปลี่ยนแปลง

ในการดำเนินการต่อผลลัพธ์ของเครื่องมือ OmniRoute ยังหยุดการดำเนินการเมื่อรอบที่เสร็จสมบูรณ์สองรอบติดต่อกันทำซ้ำการเรียกใช้เครื่องมือเดียวกันโดยไม่มีการเปลี่ยนแปลง หรือเมื่อทุกผลลัพธ์ที่ทำเครื่องหมายไว้อย่างชัดเจนในสองรอบติดต่อกันล้มเหลว ผลลัพธ์ที่เปลี่ยนแปลงทำให้สามารถโทรซ้ำได้ (เช่น การโพล) ตัวป้องกันจะรีเซ็ตตามคำขอของผู้ใช้ใหม่ จัดกลุ่มการโทรแบบขนานเป็นหนึ่งรอบ และรองรับ Anthropic การแชทให้เสร็จสิ้น การตอบกลับ และประวัติ Gemini ผู้วางแผนจะได้รับเหตุผลและเป็นเจ้าของคำตอบสุดท้ายแม้ว่าจะขอเครื่องมือใหม่ก็ตาม

โมเดลเพิ่มเติมหลังจากเป้าหมายที่สองได้รับคำสั่งให้สำรองข้อมูลของผู้ดำเนินการ การตอบสนอง HTTP ที่ล้มเหลวหรือข้อยกเว้นในการขนส่งจะเลื่อนไปยังตัวดำเนินการถัดไป โดยดำเนินการตัดสินใจของการวางแผนแบบเดียวกันและเครื่องมือดั้งเดิม แต่ขั้นตอนของตัวดำเนินการนั้นพร้อมต์และแก้ไขการเชื่อมต่อแล้ว การตอบสนองที่สำเร็จครั้งแรกจะถูกส่งกลับไม่เปลี่ยนแปลง รวมถึงการสตรีม SSE ด้วย ความล้มเหลวหลังจากเริ่มสตรีมสำเร็จแล้วไม่สามารถลองใหม่ได้ที่นี่ หากตัวดำเนินการทั้งหมดล้มเหลว ความล้มเหลวครั้งล่าสุดจะถูกส่งกลับ ลูกค้ายกเลิกการหยุดการจัดส่ง

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

ผู้ดำเนินการอาจส่งเสียงการโทรอิสระหลายครั้งในการตอบกลับครั้งเดียว การเรียกที่ขึ้นต่อกันจะได้รับการจัดการในรอบผลลัพธ์ของเครื่องมือไคลเอนต์ในภายหลัง โดยผู้วางแผนจะตรวจสอบทุกผลลัพธ์ `maxToolRounds` มีค่าเริ่มต้นเป็น `8` และยอมรับ `1`–`32`; เมื่อถึงจุดนั้นแล้ว ผู้วางแผนจะต้องสร้างคำตอบสุดท้ายที่ดีที่สุด การตัดสินใจของผู้วางแผนภายในจะถูกบัฟเฟอร์ ในขณะที่การตอบสนองต่อหน้าไคลเอ็นต์ที่เลือกจะคงการตั้งค่าการสตรีมดั้งเดิมไว้

### `round-robin` แบตช์เหนียวและการขยายบัญชี

Round-robin เป็นแบทช์ ไม่ใช่หนึ่งคำขอต่อขั้นตอน:

- `stickyRoundRobinLimit` (กำหนดค่าคอมโบ จากนั้น `comboStickyRoundRobinLimit` จากนั้น `settings.stickyRoundRobinLimit` เป็นค่าเริ่มต้น** 3** ) คงเป้าหมายเดิมไว้สำหรับความสำเร็จติดต่อกันหลายๆ ครั้งก่อนที่จะหมุน ตั้งค่าการแทนที่คำสั่งผสมเป็น `1` สำหรับการหมุนเวียนคำขอเดียว โปรแกรมแก้ไขคำสั่งผสมจะแสดงค่าที่มีประสิทธิภาพและมาจากเลเยอร์ใด
- `connectionAwareExpansion` (กำหนดค่าคอมโบ จากนั้นตั้งค่า เป็นค่าเริ่มต้น** เท็จ** ) ขยายแต่ละขั้นตอนระดับผู้ให้บริการเป็นเป้าหมายต่อบัญชีก่อนการหมุนเวียน กลยุทธ์ Group-B (ลำดับความสำคัญ, แบบถ่วงน้ำหนัก, แบบ Round-robin, สุ่ม, p2c, ใช้น้อยที่สุด, ปรับต้นทุนให้เหมาะสม, lkgp, เติมก่อน, สุ่มเข้มงวด, ปรับบริบทให้เหมาะสม, ปรับแคชให้เหมาะสม, ถ่ายทอดบริบท, ฟิวชั่น, ไปป์ไลน์, jev) จะเก็บมุมมองระดับผู้ให้บริการไว้จนกว่าจะเปิดใช้งาน ตัวแก้ไขคำสั่งผสมเปิดเผยการสืบทอด / เปิด / ปิด; inherit ใช้ค่าเริ่มต้นสากล (ปิด)
- การกำหนดเส้นทางท้องถิ่นพร้อมท์แคช (`promptCacheAffinityEnabled`, default** จริง** ) จัดลำดับการเชื่อมต่อที่ปักหมุดใหม่ เพื่อให้คีย์แคชที่ตรงกันยังคงอยู่ในบัญชีเดียว โดยจะมีความสำคัญเหนือกว่าการหมุนเวียนแบบวนรอบและการหมุนเวียนแบบถ่วงน้ำหนักในขั้นตอนที่ปักหมุดต่อบัญชี ปิดภายใต้การตั้งค่า → Combo defaults หากคุณต้องการการหมุนอย่างเข้มงวด ไม่มีการแทนที่ต่อคอมโบ

หากต้องการหมุนเวียนหลายบัญชีในรุ่นเดียว ให้เลือก** ขั้นตอนบัญชีแบบไดนามิกหนึ่งขั้นตอน** (ว่าง `connectionId`, ทั้งพูล) โดยมีขีดจำกัดแบบเหนียว `1` ไม่ใช่ `connectionId` s ที่ปักหมุดสามอัน ขั้นตอนที่ปักหมุดบวกความสัมพันธ์จะยุบลงในบัญชีเดียวกันแม้ในขณะที่ตัวนับ RR ก้าวหน้าไป

## กลยุทธ์ฟิวชั่น

`fusion` เป็นกลยุทธ์เดียวที่ทำ** ไม่** เลือกเป้าหมายเดียว มันแฟนพร้อมต์ออกไป** แผงทุกรุ่นขนานกัน** จากนั้นกำหนดค่าได้** โมเดลผู้พิพากษา** สังเคราะห์คำตอบสุดท้ายเพียงคำตอบเดียวจากคำตอบของแผงทั้งหมด ย้ายจากอัพสตรีม `decolua/9router` (การออกแบบฟิวชั่นของ OpenRouter); การใช้งานใน `open-sse/services/fusion.ts`

มันทำงานอย่างไร:

0. **บายพาสแบริ่งเครื่องมือ** — คำขอที่มีอาร์เรย์ `tools` ที่ไม่ว่างเปล่าโดยมี `tool_choice` ไม่ชัดเจน `"none"` ข้ามพาเนลทั้งหมด: มันกำหนดเส้นทางโดยตรงไปยังโมเดลเดียว (ผู้ตัดสินที่กำหนดค่าหรือ `panel[0]`) โดยที่ `tools`/`tool_choice` ส่งผ่านโดยไม่มีการแก้ไข สมาชิกของคณะผู้อภิปรายไม่สามารถเข้าถึงเครื่องมือได้ และคำสั่งการสังเคราะห์ของผู้พิพากษาไม่สนับสนุนการปล่อยการเรียกเครื่องมือ ดังนั้น ลูกค้า agentic/tool-calling จะได้รับการตัดสินใจในการเรียกเครื่องมือจริง แทนที่จะเป็นร้อยแก้วสังเคราะห์ (#6771)
1. **พัดออก** (คำขอที่ไม่ต้องใช้เครื่องมือเท่านั้น) — พรอมต์จะถูกส่งไปยังทุกรุ่นของพาเนลในคราวเดียว บังคับให้ไม่สตรีมโดยที่เครื่องมือถูกถอดออก (ผู้พิพากษาต้องการร้อยแก้วที่สมบูรณ์เพื่อสังเคราะห์)
2. **คอลเลกชันโควรัม-เกรซ** — ทันทีที่คำตอบ `minPanel` มาถึง ตัวจับเวลาเกรซสั้นๆ จะเริ่มต้นขึ้นสำหรับผู้พลัดหลง จากนั้นฟิวชั่นจะดำเนินต่อไปกับอะไรก็ตามที่รวบรวมได้ นี่เป็นการจำกัดการลงโทษของโมเดลที่ช้าที่สุดในเวลาติดผนัง โดยมีขอบเขตด้วยการหมดเวลาจริง
3. **การสังเคราะห์ผู้พิพากษา** คำตอบของแผง — จะไม่ระบุชื่อ (`Source 1`, `Source 2`, … — ดังนั้นผู้พิพากษาจะชั่งน้ำหนักเนื้อหา ไม่ใช่แบรนด์โมเดล) และส่งต่อให้กับผู้พิพากษา ซึ่งวิเคราะห์ฉันทามติ / ความขัดแย้ง / ความคุ้มครองบางส่วน / ข้อมูลเชิงลึกที่ไม่ซ้ำกัน / จุดบอด จากนั้นเขียน** หนึ่ง** คำตอบที่เชื่อถือได้ การเรียกผู้พิพากษาจะเก็บเครื่องมือ `stream` flag + ดั้งเดิมของไคลเอ็นต์ไว้ ดังนั้นการใช้เครื่องมือสตรีมมิ่งและดาวน์สตรีมยังคงใช้งานได้
4. **การเสื่อมสลายอย่างสง่างาม** คำตอบของแผง — 0 → `503`; ผู้รอดชีวิต 1 คน → คำตอบนั้นจะถูกส่งกลับโดยตรง (ไม่มีอะไรจะหลอมรวม) แผงรุ่นเดียวตอบโดยตรง

สมาชิกพาเนลอาจเป็นขั้นตอน `combo-ref` (`{kind: "combo-ref", comboName: "..."}`) ที่อ้างอิงถึงคอมโบอื่น — ที่จะแก้ไขเป็น** เสียงแผงกล่องดำหนึ่งเสียง** (การส่งแบบเรียกซ้ำแบบเต็มไปยังคอมโบที่อ้างอิง ไม่ใช่การกระจายออกจากเป้าหมายของคอมโบนั้น) โดยมีการป้องกัน depth/cycle แบบเดียวกันทุกกลยุทธ์การใช้คอมโบอ้างอิงคอมโบอื่น ๆ ใช้อยู่แล้ว (#6764)

### การกำหนดค่า

กำหนดค่าบน `config` blob ของคอมโบ (ไม่มีการโยกย้ายสคีมา — โดยจะใช้ตาราง `combos` ที่มีอยู่ซ้ำ):

| สนาม                                     | พิมพ์    | ค่าเริ่มต้น | วัตถุประสงค์                                                                           |
| :--------------------------------------- | :------- | :---------- | :------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | แผงรุ่นแรก  | โมเดลที่สังเคราะห์คำตอบสุดท้าย                                                         |
| `config.fusionTuning.minPanel`           | `number` | `2`         | ต้องการคำตอบที่สำเร็จก่อนที่ตัวจับเวลาผ่อนผันจะเริ่มต้น (จำกัดไว้ที่ `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`      | ต้องรอนานแค่ไหนเมื่อถึงองค์ประชุม                                                      |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`     | ฝาครอบแบบสัมบูรณ์ทำให้โมเดลที่แขวนอยู่หนึ่งตัวไม่สามารถขัดขวางคำขอได้                  |

ค่าเริ่มต้นอยู่ใน `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)

curl -X POST http://localhost:20128/api/combos \

## โรงงาน Auto-Combo แบบเสมือน

เอนจิน Auto Combo ไม่จำเป็นต้องมีคอมโบที่กำหนดไว้ล่วงหน้า แต่ `open-sse/services/autoCombo/virtualFactory.ts` จะสร้างตัวเลือกแบบทันที:

1. ดึง `getProviderConnections({ isActive: true })` (การเชื่อมต่อทั้งหมดที่เปิดใช้งาน)
2. กรองเฉพาะรายการที่มีข้อมูลรับรองถูกต้อง (API key หรือ OAuth token ที่ยังไม่หมดอายุผ่าน `hasUsableOAuthToken()`)
3. ตรวจสอบเทียบกับ `getProviderRegistry()` เพื่อดูความพร้อมใช้งานของโมเดลและราคา
4. สำหรับแต่ละทูเพิล `(provider, model, connection)` ให้สร้าง `VirtualAutoComboCandidate`
5. เลือก `connection.defaultModel` (หรือโมเดลแรกในรีจิสทรี) เป็นเป้าหมายในการส่งคำขอ
6. ให้คะแนนตัวเลือกแต่ละรายการด้วย `scorePool()` แบบ 16 ปัจจัยและชุดค่าน้ำหนักของเวอร์ชันย่อย
7. ส่งคืน `AutoComboConfig` ที่ได้ซึ่งอยู่ในหน่วยความจำให้แก่ `handleComboChat()` — โดยไม่บันทึกลง DB

ซึ่งหมายความว่า **การเพิ่มผู้ให้บริการรายใหม่ที่เปิดใช้ `auto/*` จะขยายกลุ่มตัวเลือกโดยอัตโนมัติ** — ไม่จำเป็นต้องแก้ไขคอมโบด้วยตนเอง คอมโบเสมือนจะถูกสร้างใหม่สำหรับแต่ละคำขอ ดังนั้นการเชื่อมต่อที่เพิ่งเพิ่มเข้ามาหรือเพิ่งกลับมามีสถานะปกติจะถูกนำมาใช้ทันที

## การฟื้นฟูตนเอง

- **การยกเว้นชั่วคราว**: คะแนน < 0.2 → ยกเว้นเป็นเวลา 5 นาที (เพิ่มระยะเวลาแบบต่อเนื่อง สูงสุด 30 นาที)
- **การรับรู้สถานะ circuit breaker**: OPEN → ยกเว้นโดยอัตโนมัติ; HALF_OPEN → ส่งคำขอทดสอบ
- **โหมดเหตุขัดข้อง**: OPEN >50% → ปิดการสำรวจและเน้นเสถียรภาพสูงสุด
- **การฟื้นตัวหลังคูลดาวน์**: หลังสิ้นสุดการยกเว้น คำขอแรกจะเป็น "คำขอทดสอบ" ที่ลดระยะหมดเวลา

## การสำรวจแบบ Bandit

คำขอ 5% (กำหนดค่าได้) จะถูกกำหนดเส้นทางไปยังผู้ให้บริการแบบสุ่มเพื่อการสำรวจ ฟังก์ชันนี้จะถูกปิดในโหมดเหตุขัดข้อง

## API

มี** ไม่มีจุดสิ้นสุด `POST /api/combos/auto` เฉพาะ** — Auto-Combo ถูกใช้ในสองวิธี:

1. **Zero-config (แนะนำ):** ส่งคำขอให้เสร็จสิ้นการแชทด้วย `model: "auto"` หรือ `model: "auto/<variant>"` โรงงานเสมือนสร้างคอมโบต่อคำขอ — โดยไม่ต้องคงอยู่ ไม่จำเป็นต้องเรียก API

2. **คอมโบยังคงมีอยู่ `strategy: "auto"`:** สร้างคอมโบปกติผ่าน `POST /api/combos` และตั้งค่า `strategy: "auto"` plus `config.auto.weights` / `config.auto.candidatePool` ใช้เครื่องมือให้คะแนนแบบเดียวกัน คอมโบถูกเก็บไว้ใน `combos` และนำมาใช้ซ้ำได้โดย ID

สำหรับการค้นพบ `GET /api/combos/auto` จะแสดงรายการทุกตัวแปรพร้อมกับกลุ่มตัวเลือกที่ได้รับการแก้ไขแล้ว บวกกับ `context_length` / `max_output_tokens` — MAX ทั่วหน้าต่างของพูลตัวเลือก ลูกค้า (เช่นปลั๊กอิน opencode) ต้องโฆษณาค่าเหล่านี้แทน `0`: บริบทที่เป็นศูนย์จะปิดใช้งานการบีบอัดอัตโนมัติของ opencode ทั้งหมด โดยปล่อยให้เซสชันขยายจนกว่าการล้างประวัติของเกตเวย์จะทำลายบริบท MAX ปลอดภัยในการโฆษณา เนื่องจากบริบทที่กรองล่วงหน้าแบบคอมโบอัตโนมัติจะกำหนดเส้นทางคำขอที่มีขนาดใหญ่เกินไปไปยังผู้สมัครที่มีกรอบเวลากว้าง

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### กลยุทธ์เราเตอร์อัตโนมัติ

คอมโบ `strategy: "auto"` ที่คงอยู่สามารถตั้งค่า `config.routerStrategy` (หรือแบบเดิม `config.auto.routerStrategy`) เป็นหนึ่งใน:

- `rules` — การให้คะแนนแบบถ่วงน้ำหนักเริ่มต้น
- `score` — เลือกคะแนนถ่วงน้ำหนักที่กำหนดค่าสูงสุด ความสัมพันธ์ที่แน่นอนจะรักษาลำดับของผู้สมัครที่กำหนดค่าไว้ ตัวอย่าง `explorationRate` ที่มีอยู่จากพูลอันดับเต็ม
- `cost` / `eco` — ผู้ให้บริการด้านสุขภาพที่ถูกที่สุด
- `latency` / `fast` — เวลาแฝง p95 ต่ำสุดพร้อมการลดความน่าเชื่อถือ
- `sla-aware` / `sla` — ต้องการผู้สมัครที่ตอบสนอง p95 latency อัตราข้อผิดพลาด และต้นทุนเสริม SLOs
- `lkgp` — ผู้ให้บริการที่ดีคนสุดท้ายที่รู้จักก่อน
- `nadir` — ถามการตัดสินใจของ [Nadir](https://getnadir.com) API โมเดลใดในพูลที่ต้องการทันที เลือกใช้ ไม่สามารถเปิดเป็น `rules`
- `decision` — ถามผู้ตัดสินใจที่กำหนดค่าไว้ (TypeSafe System One, การตัดสินใจของคุณเอง URL หรือหนึ่งในโมเดลของคอมโบเอง) ว่าโมเดลใดในพูลที่เหมาะกับคำขอ ด้านหลังแฟล็ก `COMBO_DECISION_ROUTER_ENABLED` ที่ปิดโดยค่าเริ่มต้น ไม่สามารถเปิดเป็น `rules` ได้

### กลยุทธ์เราเตอร์โดยละเอียด

เครื่องยนต์คอมโบอัตโนมัติทำให้สามารถเสียบปลั๊กได้ 7 อัน**RouterStrategy** การใช้งานที่คุณสามารถสลับผ่าน `config.routerStrategy` (หรือแบบเดิม `config.auto.routerStrategy`) แต่ละกลยุทธ์จะเลือกผู้ให้บริการหนึ่งรายจากกลุ่มผู้สมัคร โดยกำหนด `RoutingContext` (ประเภทงาน คำแนะนำ tool/vision การประมาณโทเค็น นโยบาย SLA ที่เป็นตัวเลือก ผู้ให้บริการที่รู้จักล่าสุดซึ่งเป็นทางเลือก)

#### 1. `rules` (ค่าเริ่มต้น) — การให้คะแนนแบบถ่วงน้ำหนัก 16 ปัจจัย

ล้อมกลไกการให้คะแนนที่มีอยู่ กรองตัวเลือกเซอร์กิตเบรกเกอร์ `OPEN` ออก จากนั้นรัน `scorePool()` ด้วยประเภทงานปัจจุบันและ `getTaskFitness()` โดยเลือกผู้ให้บริการที่ให้คะแนนสูงสุด

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**เมื่อจะใช้** : ค่าเริ่มต้น. ใช้เมื่อคุณต้องการการแลกเปลี่ยนที่สมดุลกับสัญญาณทั้งหมด

**นามแฝง** : `rules` (ไม่มีนามแฝง)

---

#### 2. `cost` / `eco` — ผู้ให้บริการด้านสุขภาพที่ถูกที่สุด

เรียงลำดับกลุ่มผู้สมัครตาม `costPer1MTokens` (จากน้อยไปมาก) และเลือกสิ่งที่ถูกที่สุด กรองตัวเลือก `OPEN` ออกก่อน

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**เมื่อจะใช้** : ปริมาณงานที่คำนึงถึงต้นทุน การประมวลผลเป็นชุด หรืองานเบื้องหลัง

**นามแฝง** : `cost`, `eco`

---

#### 3. `latency` / `fast` — เวลาแฝง p95 ต่ำสุดพร้อมการลงโทษความน่าเชื่อถือ

จัดเรียงตาม `p95LatencyMs + (errorRate * 1000)` การลงโทษอัตราข้อผิดพลาดทำให้มั่นใจได้ว่าผู้ให้บริการที่ไม่น่าเชื่อถือจะถูกจัดอันดับต่ำกว่า แม้ว่าเวลาแฝงเล็กน้อยจะต่ำก็ตาม

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**เมื่อจะใช้** : ปริมาณงานที่ไวต่อความหน่วง เช่น การแชทแบบเรียลไทม์ การเติมข้อความอัตโนมัติ หรือผู้ช่วยการเขียนโค้ดเชิงโต้ตอบ

**นามแฝง** : `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO

ให้คะแนนผู้สมัครแต่ละคนตามความเหมาะสมกับนโยบาย SLO ที่กำหนดค่าไว้:

| ปัจจัย          | น้ำหนัก | สูตร                                                        |
| --------------- | ------- | ----------------------------------------------------------- |
| คะแนนแฝง        | 35%     | `threshold / max(value, ε)`                                 |
| คะแนนข้อผิดพลาด | 35%     | `threshold / max(value, ε)`                                 |
| คะแนนสุขภาพ     | 15%     | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)           |
| คะแนนต้นทุน     | 10%     | `threshold / max(value, ε)` หรือค่าผกผันที่ทำให้เป็นมาตรฐาน |
| คะแนนความมั่นคง | 5%      | เวลาแฝงปกติผกผัน stddev                                     |

เมื่อ `hardConstraints: true` ผู้สมัครจะถูกจัดเรียงตามเป็นหลัก** คะแนนการละเมิด** (ไกลแค่ไหนที่พวกเขาเกิน SLO ใด ๆ ) จากนั้นด้วยคะแนนรวม ไม่อย่างนั้นก็เป็นเพียงคะแนนรวมเท่านั้น

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**เขตข้อมูล SLA** (ตั้งค่าในการกำหนดค่าคอมโบ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**เมื่อจะใช้** : ปริมาณงานการผลิตที่มีเวลาแฝง อัตราข้อผิดพลาด หรืองบประมาณต้นทุนที่เข้มงวด

**นามแฝง** : `sla-aware`, `sla`

#### 5. `lkgp` — ผู้ให้บริการที่ดีคนสุดท้ายที่รู้จักก่อน

พยายาม** ผู้ให้บริการที่ดีคนสุดท้ายที่รู้จัก** (หากตั้งค่าไว้) ก่อน จากนั้นจึงถอยกลับไปใช้กลยุทธ์ `rules` มีประโยชน์สำหรับความเหนียวของเซสชัน — ผู้ให้บริการรายเดียวกันจะจัดการคำขอติดตามผลในการสนทนา

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**เมื่อจะใช้** : การสนทนาหลายรอบที่คุณต้องการให้ผู้ให้บริการรายเดียวกันจัดการคำขอติดตามผล (เช่น สำหรับการแคช ความต่อเนื่องของบริบท หรือความสอดคล้องของราคา)

**นามแฝง** : `lkgp` (ไม่มีนามแฝง)

#### 6. `nadir` — ตัวเลือกรุ่นที่ทราบทันทีผ่าน Nadir

ทุกกลยุทธ์ที่กล่าวมาข้างต้นจะจัดอันดับผู้สมัครด้วยการวัดและส่งข้อมูลทางไกลของตนเอง ไม่มีใครอ่านคำขอ `nadir` ส่งเทิร์นผู้ใช้คนสุดท้ายบวกกับรหัสโมเดลของพูลไปยังการตัดสินใจของ [Nadir](https://getnadir.com) API (`POST /v1/bucket`) และเส้นทางไปยังโมเดล Nadir เลือกจากเมนูนั้น (`simple` → โมเดลที่มีความสามารถที่ถูกที่สุด `complex` → อันชายแดน) การเชื่อมต่อที่ให้บริการโมเดลนั้นยังคงถูกเลือกโดย `rules` ดังนั้นโควต้า ความสมบูรณ์ และต้นทุนจึงตัดสินใจเลือกบัญชีต่อไป

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` และ `OMNIROUTE_NADIR_BASE_URL` เป็นทางเลือกสำรองของ env สำหรับทั้งสองสตริง `baseUrl` จำเป็นสำหรับ Nadir ที่โฮสต์เองเท่านั้น (ยอมรับ `/v1` ต่อท้ายได้) การโทรแบบไม่ใช้คีย์จะเข้าสู่ระดับที่ไม่ระบุตัวตนของ Nadir ซึ่งมีอัตราจำกัดต่อ IP ด้วยคีย์ ( [สร้างหนึ่งรายการ](https://app.getnadir.com/dashboard/api-keys) ) การตัดสินใจแต่ละครั้งจะถูกบันทึกไว้ในแดชบอร์ด Nadir ของคุณ การตั้งค่าและการตรวจสอบแบบเต็ม: [getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/)

สิ่งที่อยู่ในกล่อง: ข้อความของข้อความผู้ใช้สุดท้าย (อักขระ 16,000 ตัวแรก) รหัสโมเดลที่เป็นตัวเลือก และแท็กช่อง `source: "omniroute"` ไม่มีพรอมต์ของระบบ ประวัติ เครื่องมือ หรือส่วนหัว

ลักษณะการทำงานที่ล้มเหลวเปิดไม่สำเร็จ: การหมดเวลา (ค่าเริ่มต้น 2000 ms), non-2xx, โฮสต์ที่ไม่สามารถเข้าถึงได้, การตอบสนองที่มีรูปแบบไม่ถูกต้อง หรือการเลือกภายนอกพูลจะแก้ไขการตัดสินใจ `rules` และเหตุผลคือคำนำหน้า `NadirStrategy: fallback (…)` หลังจากการเรียกที่ล้มเหลว กลยุทธ์จะข้ามเครือข่ายเป็นเวลา 30 วินาที ดังนั้นการหยุดทำงานจะมีค่าการหมดเวลาหนึ่งครั้งต่อ 30 วินาที แทนที่จะเป็นหนึ่งครั้งต่อคำขอ เหตุการณ์การกำหนดเส้นทางรายงาน `strategy: "nadir"` เฉพาะเมื่อ Nadir ตัดสินใจเลือกแล้วเท่านั้น

**เมื่อจะใช้** : การรับส่งข้อมูลที่มีความยากลำบากแบบผสมบนพูลที่ครอบคลุมระดับโมเดล (รุ่นเล็ก กลาง และชายแดน) โดยที่ต้นทุนที่คุณต้องการลดเสมอคือชายแดน

**นามแฝง** : `nadir` (ไม่มีนามแฝง)

#### 7. `decision` — ตัวตัดสินใจแบบเสียบได้จะเลือกโมเดล

`decision` ถามก** ผู้ตัดสินใจ** โมเดลใดในพูลที่เหมาะกับคำขอ จากนั้นจำกัดพูลให้แคบลงตามโมเดลนั้น และให้ `rules` เลือกการเชื่อมต่อ (โควต้า ความสมบูรณ์ และต้นทุนยังคงเลือกบัญชี) ตัวตัดสินใจถูกตั้งค่าไว้ในบล็อกการตัดสินใจของคอมโบ — `config.decision` เมื่อปุ่มหมุนของเราเตอร์อยู่ที่ด้านบนของ `config` (สิ่งที่แดชบอร์ดเขียน) หรือ `config.auto.decision` ถัดจาก `config.auto.routerStrategy`:

| `decider`     | ใครตอบ.                                                                                                                  | ความต้องการ                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| `systemone`   | TypeSafe System One (`POST https://api.typesafe.ai/v1/systemone`) โมเดลเริ่มต้น `jev-latest`                             | การเชื่อมต่อ `typesafe` หรือคีย์ env       |
| `http`        | ผู้ตัดสินใจของคุณเองที่ `baseUrl`: `wire: "systemone"` (`{baseUrl}/v1/systemone`) หรือ `"openai-chat"` (เสร็จสิ้นการแชท) | `baseUrl` + `model`; ที่สำคัญไม่จำเป็น     |
| `combo-model` | หนึ่งในโมเดลผู้ให้บริการของคุณ ที่ถูกเรียกในกระบวนการเหมือนกับผู้ตัดสินฟิวชั่น                                           | `model` เป็น `provider/model` (ไม่มีคอมโบ) |

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "decision",
    "decision": {
      "decider": "http",
      "baseUrl": "https://decider.example.com",
      "wire": "openai-chat",
      "model": "qwen-small",
      "connectionId": "<stored connection id>",
      "timeoutMs": 2000,
      "minConfidence": 0.6,
      "descriptions": { "gpt-4o-mini": "Quick drafts and short answers" }
    }
  }
}
```

ฟิลด์ (ตรวจสอบโดยสคีมาที่เข้มงวดในการบันทึกและอีกครั้งตามเวลาที่ร้องขอ):

- `decider` — `systemone`, `http` หรือ `combo-model`
- `model` — TypeSafe model, โมเดลการตัดสินใจที่ URL ของคุณ หรือ `provider/model` ของการเรียกคอมโบโมเดล (สูงสุด 200 อักขระ)
- `baseUrl` — `http` เท่านั้น: `http(s)` URL สูงสุด 500 อักขระ โดยไม่มีข้อมูลประจำตัว แบบสอบถาม หรือส่วนย่อย URL ที่ชี้ไปที่ OmniRoute นี้ (loopback + `PORT`) ถูกปฏิเสธ
- `wire` — `http` เท่านั้น: `systemone` (ค่าเริ่มต้น) หรือ `openai-chat`
- `connectionId` — การเชื่อมต่อที่เก็บไว้ซึ่งมีการใช้คีย์ (เฉพาะภายในการเชื่อมต่อที่อนุญาตของคีย์ API ที่เรียกเท่านั้น) หากไม่มีมัน `systemone` จะอ่านการเชื่อมต่อ `typesafe` และตัวตัดสินใจเครือข่ายทุกตัวจะกลับไปเป็น `OMNIROUTE_DECISION_API_KEY` ไม่มีฟิลด์ `apiKey` : คีย์จะไม่ถูกเก็บไว้ในคอมโบ
- `timeoutMs` — จำนวนเต็ม 100–5000 ค่าเริ่มต้นคือ 2000
- `minConfidence` — 0–1; คำตอบที่มีความมั่นใจต่ำจะกลับไปอยู่ที่ `rules` (ตัวตัดสินที่รายงานว่าไม่มั่นใจจะนับเป็น 0)
- `descriptions` — สูงสุด 50 รายการ (ป้อนได้สูงสุด 300 รายการ, ข้อความสูงสุด 1,000 อักขระ) ป้อนด้วยรหัสโมเดลหรือ `provider/model`; รายการที่ไม่ได้ตั้งค่าจะได้รับคำอธิบายระดับต้นทุนที่สร้างขึ้น

**ธง.** `COMBO_DECISION_ROUTER_ENABLED` (ค่าเริ่มต้น `false`) ประตูทุกผู้ตัดสินใจ ในขณะที่ปิดอยู่ คำสั่งผสม `decision` จะไม่อ่านข้อมูลประจำตัว ไม่ทำการโทร และกำหนดเส้นทางด้วย `rules`; บันทึกบอกว่า `fallback (disabled)` คีย์ที่เก็บไว้เพียงอย่างเดียวจะไม่เปิดขึ้น คอมโบที่ไม่มีบล็อคการตัดสินใจจะไม่ได้รับผลกระทบเลย

**อะไรเหลือกล่อง.** เฉพาะข้อความของข้อความผู้ใช้ล่าสุด (สูงสุด 8000 อักขระ; chat/Claude `messages` หรือ Responses `input`) และเมนูของรหัสโมเดลพร้อมคำอธิบาย ไม่ต้องแจ้งระบบ, การตอบสนอง `instructions`, เครื่องมือ, ประวัติ, ส่วนหัวหรือข้อมูลบัญชี การโทรผ่านเครือข่ายจะผ่านตัวป้องกันขาออกของผู้ให้บริการโดยไม่ต้องลองใหม่ ไม่มีการเปลี่ยนเส้นทาง และขีดจำกัดการตอบกลับอยู่ที่ 64 KB การเรียก `combo-model` ไม่ใช่การสตรีมมิ่ง ไม่ต้องใช้เครื่องมือ `temperature: 0` โดยมีงบประมาณ 256 โทเค็น การตัดสินใจที่เริ่มต้นภายในการเรียกการตัดสินใจจะถูกปฏิเสธ

**พฤติกรรมความล้มเหลว** เปิดล้มเหลว: ความล้มเหลวใด ๆ แก้ไขการตัดสินใจของ `rules` และเหตุผลอ่าน `decision(<decider>): fallback (<reason>)` โดยมี `<reason>` หนึ่งใน `disabled`, `not_configured`, `missing_credential`, `timeout`, `http_error`, `invalid_response`, `out_of_menu`, `refused`, `cooldown`, `network_error`, `recursion`, `low_confidence`, `single_option` หรือ `no_user_text` หลังจากหมดเวลา ข้อผิดพลาด HTTP หรือข้อผิดพลาดเครือข่าย จุดสิ้นสุดจะถูกข้ามไปเป็นเวลา 30 วินาที การเลือกที่สำเร็จจะอ่าน `decision(<decider>): selected <model> from <n>; confidence <c> (<rules reason>)` ไม่มีเนื้อหา URL, key, prompt หรือ upstream เข้าถึงบันทึก

ตัวสร้างคอมโบจะแสดงฟิลด์เหล่านี้เมื่อกลยุทธ์ของเราเตอร์คือ `decision` โดยมีคำอธิบายที่สร้างขึ้นเป็นตัวยึดตำแหน่งและ** ตัดสินใจทดสอบ** ปุ่มที่เรียก `POST /api/combos/decision-preview` หนึ่งครั้งด้วยการตั้งค่าที่ยังไม่ได้บันทึก (แฟล็กเดียวกัน)

**เมื่อจะใช้** : การรับส่งข้อมูลที่มีความยากแบบผสมที่คุณต้องการให้ชั้นเลือกตามคำขอโดยตัวแยกประเภทที่คุณเลือก ไม่ใช่โดย Nadir โดยเฉพาะ

**นามแฝง** : `decision` (ไม่มีนามแฝง)

### กลยุทธ์เราเตอร์แบบกำหนดเอง

คุณสามารถลงทะเบียนการใช้งาน `RouterStrategy` ของคุณเองผ่านทางสาธารณะ API:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

จากนั้นใช้มัน:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

| แชทหลายรอบ                  | `lkgp`      | ความเหนียวของเซสชัน                       |
| ความยากแบบผสม               | `nadir`     | เลือกระดับโมเดลตามพรอมต์                  |
| ลักษณนามของตัวเอง           | `decision`  | ผู้ตัดสินใจของคุณเลือกแบบจำลอง            |

ฟิลด์ที่ทราบ SLA:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## ความเหมาะสมกับงาน

โมเดลมากกว่า 30 รายการได้รับการประเมินในงาน 6 ประเภท (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) รองรับรูปแบบไวลด์การ์ด (เช่น `*-coder` → คะแนนด้านการเขียนโค้ดสูง)

## สรุปรูปแบบรถยนต์

`AutoVariant` ใน `autoPrefix.ts` ประกาศ** 7 ค่า** (`coding`, `fast`, `cheap`, `offline`, `smart`, `lkgp`, `chaos`) Together พร้อม `auto` เปล่า (จัดการโดย `parseAutoPrefix()` เป็น `variant: undefined`) และการซ้อนทับระดับแบนสองชั้น `auto/subscription` และ `auto/thrifty` (`FLAT_TIER_OVERLAY_IDS` ใน `builtinCatalog.ts`) มี** 10 รุ่นแบน IDs** : :

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`, `auto/chaos`, `auto/subscription`, `auto/thrifty`

นอกเหนือจากนั้น องค์ประกอบ `auto/<category>[:<tier>]` ตระกูลโมเดล IDs (เช่น `auto/claude-opus`) และนามแฝง `auto/best-*` / `auto/pro-*` ใน `builtinCatalog.ts` ก็ได้รับการแก้ไขเช่นกัน

## ระดับ Tier ทำงานร่วมกับ Auto-Combo อย่างไร

ฟังก์ชันการให้คะแนนแบบ 16 ปัจจัย (`open-sse/services/autoCombo/scoring.ts`) ถือว่าการเป็นสมาชิกระดับ Tier
เป็นสัญญาณสองรายการ ได้แก่ `tierPriority` (0.0476) และ `tierAffinity` (0.0476) โปรดดู
[ตารางปัจจัยการให้คะแนน](#how-it-works-persisted-auto-combos) มาตรฐานด้านบนสำหรับชุด
`DEFAULT_WEIGHTS` ทั้งหมด — ค่าที่กำหนดทับต่อแพ็ก (ship-fast/cost-saver/quality-first/
offline-friendly) แสดงอยู่ในตาราง "โปรไฟล์น้ำหนักต่อแพ็ก"

ระดับ Tier เพียงอย่างเดียว **ไม่ได้** บังคับให้ Tier 1 มาก่อน — หากเวลาแฝงของ Tier 1 ไม่ดี หรือ
ความคุ้มค่าระหว่างต้นทุนกับคุณภาพไม่เหมาะสม Tier 2 จะชนะ หากต้องการบังคับลำดับตาม Tier ให้ใช้
กลยุทธ์คอมโบ `priority` และจัดเรียงผู้ให้บริการตาม Tier

หากต้องการให้น้ำหนักแก่ Tier 1 (การสมัครสมาชิก) อย่างมาก ให้เพิ่มน้ำหนักของ `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

โปรดดู [`docs/guides/TIERS.md`](../guides/TIERS.md) สำหรับคำจำกัดความของ Tier และการจัดประเภทผู้ให้บริการ

## การทดสอบและความครอบคลุม

### เมทริกซ์การกำหนดเส้นทาง-การตัดสินใจที่กำหนด (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` พิสูจน์เส้นทาง** การตัดสินใจ** ของกลยุทธ์สาธารณะครอบคลุมตั้งแต่ต้นทางถึงปลายทางผ่านท่อส่งคำสั่งผสมจริงพร้อมต้นน้ำจำลอง ความคุ้มครองประกอบด้วย:

- 18 จาก 22 กลยุทธ์ `ROUTING_STRATEGY_VALUES` สาธารณะ (เรียงลำดับ ถ่วงน้ำหนัก ต้นทุน บริบท ฟิวชั่น …); `quota-weighted`, `cache-optimized`, `pipeline` และ `jev` ไม่ได้ใช้โดยเมทริกซ์และอาศัยการทดสอบหน่วยของตัวเอง
- `quota-share` (ภายใน) จากต้นทางถึงปลายทาง: DRR ความเป็นธรรม การลดความอิ่มตัวของสี + ผ่านตะเข็บ `selectQuotaShareTarget` จริง (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`)
- `context-relay` universal-handoff ครอบคลุมทุกจำนวนเป้าหมาย

ชุดนี้ทำงานใน CI (งาน `test:integration` ) พร้อมด้วย `--test-concurrency=1` และ `--test-force-exit` ดังนั้นจึงถูกกำหนดไว้และไม่ต้องใช้ข้อมูลประจำตัวที่ใช้งานอยู่
