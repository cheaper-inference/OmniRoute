## การกำหนดเส้นทางอัตโนมัติแบบไม่ต้องตั้งค่า (คำนำหน้า `auto/`)

> **ใหม่:** ไม่ต้องสร้างคอมโบ ใช้คำนำหน้า `auto/` ได้โดยตรงในไคลเอนต์ใดก็ได้

### ตัวอย่างด่วน

| Model ID       | ตัวแปร  | ลักษณะการทำงาน                                                                     |
| -------------- | ------- | ---------------------------------------------------------------------------------- |
| `auto`         | default | ผู้ให้บริการที่เชื่อมต่อทั้งหมด กลยุทธ์ LKGP และค่าน้ำหนักแบบสมดุล                 |
| `auto/coding`  | coding  | ค่าน้ำหนักที่ให้ความสำคัญกับคุณภาพ เหมาะสำหรับการสร้างโค้ด                         |
| `auto/fast`    | fast    | การเลือกแบบถ่วงน้ำหนักที่มีเวลาแฝงต่ำ                                              |
| `auto/cheap`   | cheap   | การกำหนดเส้นทางที่ปรับให้เหมาะกับต้นทุน (ต้นทุนต่ำสุดก่อน)                         |
| `auto/offline` | offline | ให้ความสำคัญกับผู้ให้บริการที่มีโควตาพร้อมใช้งานสูงสุด                             |
| `auto/smart`   | smart   | ให้ความสำคัญกับคุณภาพ + อัตราการสำรวจที่สูงขึ้น (10%) เพื่อค้นหาโมเดลได้ดียิ่งขึ้น |
| `auto/lkgp`    | lkgp    | LKGP แบบระบุชัดเจน (เหมือนกับ `auto` เริ่มต้น)                                     |
| `auto/chaos`   | chaos   | กระจายคำขอแบบขนาน โดยใช้หนึ่งโมเดลต่อหนึ่งผู้ให้บริการ (ไม่ใช่การแทรกความขัดข้อง)  |

### การประกอบหมวดหมู่ × ระดับ (`auto/<category>:<tier>`)

ส่วนต่อท้ายแบบ OpenRouter จะแยก **เส้นทางประเภทใด** (หมวดหมู่) ออกจาก **วิธีปรับเส้นทางให้เหมาะสม** (ระดับ) เพื่อให้คุณประกอบทั้งสองส่วนได้อย่างอิสระ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **หมวดหมู่** (กรองกลุ่มตัวเลือกตามความสามารถ): `coding` · `reasoning` · `vision` · `chat` · `multimodal` โดย `vision`/`multimodal` จะคงโมเดลที่รองรับภาพไว้ ส่วน `reasoning` จะคงโมเดลที่รองรับการให้เหตุผล/การคิดไว้
- **ระดับ** (เลือกค่าน้ำหนักการให้คะแนน/ตัวกรองกลุ่ม): `fast` (ส่งมอบรวดเร็ว) · `cheap` (นามแฝง `floor`, ประหยัดต้นทุน) · `reliable` (ความสมบูรณ์ของ circuit breaker + ความเสถียรของเวลาแฝง) · `free` / `pro` (กรองกลุ่มตามระดับโมเดลผ่าน `classifyTier` — ระดับฟรีเทียบกับพรีเมียม)

| ตัวอย่าง               | ผลลัพธ์                                                                    |
| ---------------------- | -------------------------------------------------------------------------- |
| `auto/coding:fast`     | กลุ่มสำหรับการเขียนโค้ด ค่าน้ำหนักที่เน้นเวลาแฝงต่ำ                        |
| `auto/coding:cheap`    | กลุ่มสำหรับการเขียนโค้ด ปรับให้เหมาะกับต้นทุน (นามแฝง `auto/coding:floor`) |
| `auto/reasoning:pro`   | เฉพาะโมเดลการให้เหตุผล/การคิด ระดับพรีเมียม                                |
| `auto/vision`          | โมเดลที่รองรับภาพ (ไม่มีระดับ → ค่าน้ำหนักแบบสมดุล)                        |
| `auto/multimodal:free` | โมเดลที่รองรับหลายรูปแบบ เฉพาะระดับฟรี                                     |

`auto/<category>[:<tier>]` ที่ถูกต้องทุกรูปแบบจะได้รับการแปลงเมื่อมีการร้องขอ โดยชุดย่อยที่คัดสรรไว้จะถูกประกาศใน `/v1/models` และแดชบอร์ด (`AUTO_SUFFIX_VARIANTS` ใน `open-sse/services/autoCombo/builtinCatalog.ts`) การกรองเป็นแบบ **fail-open** — หากเงื่อนไขไม่ตรงกับโมเดลที่เชื่อมต่ออยู่เลย ระบบจะใช้กลุ่มทั้งหมดเพื่อไม่ให้การกำหนดเส้นทางหยุดทำงาน ตัวให้คะแนนหลัก (`combo.ts`) ไม่มีการเปลี่ยนแปลง ส่วนตัวกรองหมวดหมู่/ระดับจะถูกใช้ใน `buildAutoCandidates`

> **ข้อมูลอัจฉริยะของโมเดลแบบสด:** ความเหมาะสมของการกำหนดเส้นทางอัตโนมัติอ้างอิงจากอันดับ **Arena ELO** แบบสด + ข้อมูลระดับจาก **models.dev** เมื่อเปิดแฟล็ก `ARENA_ELO_SYNC_ENABLED` (มิฉะนั้นจะย้อนกลับไปใช้แผนผังความเหมาะสมแบบคงที่)

**วิธีใช้งาน:**

```bash
# IDE หรือเครื่องมือ CLI ใด ๆ ที่รองรับรูปแบบ OpenAI
Base URL: http://localhost:20128/v1
API Key:  <คีย์เอนด์พอยต์ของคุณ>

# ในโค้ด/การกำหนดค่าของคุณ ให้ตั้งค่าโมเดลเป็น:
model: "auto"                 # ค่าเริ่มต้นแบบสมดุล
model: "auto/coding"          # เหมาะที่สุดสำหรับงานเขียนโค้ด
model: "auto/fast"            # ตัวเลือกที่พร้อมใช้งานและเร็วที่สุด
model: "auto/cheap"           # ราคาต่อโทเค็นต่ำที่สุด
```

**สิ่งที่เกิดขึ้น:**

1. OmniRoute ตรวจพบคำนำหน้า `auto/` ใน `src/sse/handlers/chat.ts`
2. สอบถาม **การเชื่อมต่อผู้ให้บริการที่ใช้งานอยู่** ทั้งหมดจากฐานข้อมูล
3. กรองให้เหลือเฉพาะรายการที่มีข้อมูลรับรองถูกต้อง (API key หรือ OAuth token)
4. กำหนดโมเดลต่อการเชื่อมต่อ (`connection.defaultModel` หรือโมเดลแรกของผู้ให้บริการ)
5. สร้าง **คอมโบเสมือน** ในหน่วยความจำ (ไม่จัดเก็บใน DB)
6. กำหนดเส้นทางโดยใช้โปรไฟล์ค่าน้ำหนักของตัวแปรที่เลือก + กลยุทธ์ LKGP

**คุณสมบัติสำคัญ:**

- ✅ **เปิดใช้งานตลอดเวลา:** ไม่ต้องมีตัวสลับ ไม่ต้องสร้างคอมโบ และไม่ต้องกำหนดค่า
- ✅ **ไดนามิก:** สะท้อนผู้ให้บริการที่เชื่อมต่ออยู่ในปัจจุบันโดยอัตโนมัติ
- ✅ **การยึดติดกับเซสชัน:** LKGP ทำให้ผู้ให้บริการล่าสุดที่ทำงานสำเร็จได้รับลำดับความสำคัญ
- ✅ **รองรับหลายบัญชี:** การเชื่อมต่อผู้ให้บริการแต่ละรายการจะกลายเป็นตัวเลือกแยกกัน
- ✅ **ไม่มีการเขียน DB:** คอมโบเสมือนมีอยู่เฉพาะสำหรับคำขอนั้น จึงไม่มีค่าใช้จ่ายเพิ่มเติมจากการจัดเก็บถาวร

### การควบคุมตัวเลือกต่อคีย์ (#7819, ระดับ 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = ส่วนต่อท้ายหลัง `auto/` หรือ
ค่า `auto` ตามตัวอักษรสำหรับช่องทางพื้นฐาน) เป็นเอนด์พอยต์แบบ **อ่านอย่างเดียว** ที่แสดงรายการ
กลุ่มตัวเลือกปัจจุบันของช่องทาง `auto/*` พร้อมสถานะการเข้าถึงแบบสด โดยนำข้อมูลการอ่านด้านความยืดหยุ่น
ที่มีอยู่แล้วมาใช้ซ้ำ (ไม่อ่าน `state` ดิบของ breaker):

- circuit breaker ของผู้ให้บริการ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ช่วงพักของการเชื่อมต่อ — `rateLimitedUntil` / `testStatus` ในแถว
  `provider_connections` ที่ได้รับการแปลงแล้ว
- การล็อกโมเดล — `isModelLocked(provider, connectionId, model)`

ตัวเลือกแต่ละรายการยังมีแฟล็ก `excluded` ของ API key นี้ด้วย รายการยกเว้นจะถูกจัดเก็บ
แยกตาม API key (ตาราง `auto_candidate_overrides`, migration `128`) — OmniRoute เป็น
ระบบผู้เช่ารายเดียวโดยไม่มีตาราง `users` ดังนั้น `apiKeyId` จึงเป็นข้อมูลระบุตัวตนต่อผู้เรียก
ที่มีอยู่จริงและใกล้เคียงที่สุด — และมีการบังคับใช้ที่จุดควบคุมหลักของกลุ่มตัวเลือกใน
`open-sse/services/autoCombo/virtualFactory.ts` ผ่านฟังก์ชันบริสุทธิ์ที่ผ่านการทดสอบหน่วยแล้ว
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`)
ตัวกรองเป็นแบบ **fail-open**: หากไม่ได้ตั้งค่า apiKeyId/ช่องทาง หรือการค้นหา DB ล้มเหลว
ระบบจะไม่กรองกลุ่ม ดังนั้นผู้ดูแลระบบที่ไม่ได้กำหนดรายการแทนที่ไว้จะเห็นการกำหนดเส้นทาง
ที่เหมือนเดิมทุกไบต์กับก่อนมีฟีเจอร์นี้

**เลื่อนไปดำเนินการในประเด็นติดตามผล:** น้ำหนักแยกตามตัวเลือก + การจัดลำดับอย่างชัดเจน (ระดับ 3
— เชื่อมเข้าสู่เส้นทางกลยุทธ์แบบถ่วงน้ำหนัก/ตามลำดับความสำคัญที่มีอยู่) และการตรึงกลยุทธ์
`combo.ts` ที่เฉพาะเจาะจงสำหรับแต่ละช่องทาง `auto/*` (ระดับ 4) ดูแผน #7819 สำหรับคำถามที่ยังเปิดอยู่
ว่าการแทนที่ค่าควรคงไว้แยกตาม API key หรือเปลี่ยนเป็นแบบส่วนกลาง เมื่อพิจารณาจาก
โมเดลผู้เช่ารายเดียว

**เบื้องหลังการทำงาน:**

```txt
คำขอ: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts ตรวจพบคำนำหน้า
   ↓
createVirtualAutoCombo('coding') → candidatePool จากการเชื่อมต่อที่ใช้งานอยู่
   ↓
handleComboChat (เอนจินเดียวกับคอมโบที่บันทึกถาวร)
   ↓
การให้คะแนนอัตโนมัติเลือกผู้ให้บริการ/โมเดลที่ดีที่สุดสำหรับแต่ละคำขอ
```

**ไฟล์ที่ใช้ในการติดตั้งใช้งาน:**

| ไฟล์                                                      | วัตถุประสงค์                                          |
| --------------------------------------------------------- | ----------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | ตัวแยกวิเคราะห์คำนำหน้า (`parseAutoPrefix`)           |
| `open-sse/services/autoCombo/virtualFactory.ts`           | สร้างออบเจ็กต์ `AutoComboConfig` เสมือน               |

| `src/sse/handlers/chat.ts`                                | การผสานรวม: ลัดขั้นตอนด้วยคำนำหน้าอัตโนมัติ           |
| `src/shared/constants/providers.ts`                       | รายการระบบ `SYSTEM_PROVIDERS.auto`                    |

## การตั้งค่าบัญชีสำหรับคอมโบอัตโนมัติที่บันทึกไว้

โปรแกรมแก้ไขอัตโนมัติอัจฉริยะเสนอทางเลือก** การตั้งค่าบัญชี** ส่วน. การเชื่อมต่อแต่ละรายการสามารถเป็นที่ต้องการ ปกติ (ค่าเริ่มต้น) สำรอง หรือไม่รวม การเชื่อมต่อหลายรายการสามารถแชร์ระดับได้ เลือกอัตโนมัติภายในระดับที่มีสิทธิ์ระดับแรก โดยคงลักษณะการทำงานของ scoring/router ไว้ตรงนั้น ความพยายามที่ล้มเหลวจะตกไปสู่บัญชีที่เป็นรูปธรรมที่เหลืออยู่ แนะนำให้ใช้ก่อนปกติก่อนสำรอง การเชื่อมต่อที่แยกออกจะไม่ถูกใช้โดยคอมโบนี้

การตั้งค่าถูกจัดเก็บเป็น `config.accountPreferences` คีย์โดยการเชื่อมต่อ ID:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

แผนที่ที่ถูกละเว้นหรือว่างเปล่าจะคงเส้นทางที่มีอยู่ไว้ การตั้งค่าไม่เปิดใช้งานการเชื่อมต่อที่ถูกปิดใช้งาน ให้สิทธิ์การเข้าถึงคีย์ API กู้คืนผู้สมัครที่ถูกบล็อกโควต้า หรือเลี่ยงการตรวจสอบงบประมาณ ความพยายามแต่ละครั้งจำกัดอยู่ที่การเชื่อมต่อที่เป็นรูปธรรม ดังนั้นบัญชีสำรองจึงไม่สามารถข้ามระดับหลังเราเตอร์คอมโบได้ ความเกี่ยวข้องของเซสชันที่มีอยู่อาจรักษาบัญชีที่มีสิทธิ์ไว้ได้ ไม่รวมบัญชีที่ผูกไว้กับเทิร์นดั้งเดิมที่หยุดซึ่งจะเปลี่ยนแทนการเปลี่ยนบัญชีอย่างเงียบ ๆ

การตั้งค่าที่กำหนดค่าไว้จะใช้เส้นทางอัตโนมัติที่รับรู้ถึงบัญชี: ทางลัดแคชบริบทที่ไม่ได้ผูกไว้ สมาร์ทไปป์ไลน์ ความโกลาหล และทางลัดเงาจะไม่ถูกส่งไป การป้องกันความเสี่ยงแบบเก็งกำไรถูกปิดใช้งานสำหรับคำขอเหล่านี้ ดังนั้นบัญชีสำรองจึงไม่สามารถแข่งขันกับบัญชีที่ต้องการได้ กลยุทธ์คอมโบอื่นๆ ไม่ตีความการตั้งค่านี้ การเปลี่ยนคอมโบออกจากอัตโนมัติจะคงการตั้งค่าที่บันทึกไว้ไว้สำหรับการสลับกลับในภายหลัง

## ชื่อคอมโบที่ตรงกับรหัสโมเดลจริง

คอมโบที่มี `name` เหมือนกับรหัสโมเดลเปล่าทุกประการ (เช่น คอมโบชื่อ
`gpt-5.5`) เป็น **รูปแบบที่ตั้งใจให้ใช้งานและรองรับอย่างเป็นทางการ** ไม่ใช่ข้อบกพร่อง โดยเป็น
กลไกสำหรับการสลับไปใช้ผู้ให้บริการสำรองตามรหัสโมเดลตามที่บันทึกไว้ใน
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) เนื่องจากระบบตรวจสอบการ
แก้ไขคอมโบก่อนการแก้ไขรหัสโมเดลเปล่า
(`getComboForModel()` ใน `src/sse/services/model.ts`) คำขอสำหรับรหัสเปล่า
`gpt-5.5` จึงถูกกำหนดเส้นทางผ่านเป้าหมายของคอมโบ (เช่น
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) แทนที่จะส่งตรงไปยัง
ผู้ให้บริการรายเดียว ซึ่งเป็นการนำลำดับความสำคัญแบบคอมโบก่อนการเขียนใหม่ที่สร้างขึ้นสำหรับ
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) มาใช้ซ้ำ และมี
การทดสอบการถดถอยโดย `tests/unit/responses-combo-resolution-3227.test.ts` และ
`tests/unit/combo-name-codex-responses-rewrite.test.ts`

การสร้างหรือเปลี่ยนชื่อคอมโบเป็นชื่อที่บดบังรหัสโมเดลจริงจะ
**ไม่ถูกปฏิเสธโดยเด็ดขาด** เพราะการทำเช่นนั้นจะทำให้เวิร์กโฟลว์ที่บันทึกไว้นี้ใช้งานไม่ได้ แต่
(#8530) `POST /api/combos` และ `PUT /api/combos/[id]` จะแนบฟิลด์
`warning` ที่ไม่ขัดขวางการทำงานไว้ในผลลัพธ์ตอบกลับ เมื่อชื่อ (ใหม่) ชนกับรหัส
โมเดลจริง:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

ขณะเริ่มระบบ `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) จะบันทึกคำเตือน `[STARTUP]` แบบหนึ่งบรรทัดด้วย
โดยแจกแจงคอมโบที่มีอยู่ทั้งหมดซึ่งบดบังรหัสโมเดล เพื่อให้ผู้ดูแลระบบที่
พบกรณีนี้โดยไม่ตั้งใจ (แทนที่จะตั้งใจตาม #6940) ได้รับสัญญาณแจ้งเตือน
ตัวช่วยตรวจจับอยู่ใน `src/lib/combos/modelNameCollision.ts`

## การเรียกคอมโบแบบกำหนดเองจากไคลเอนต์

คอมโบที่บันทึกไว้ (การตั้งค่า → คอมโบ) จะถูกใช้เฉพาะเมื่อไคลเอนต์ส่ง **ชื่อที่ตรงกันทุกประการ** ของคอมโบในฟิลด์ `model` เท่านั้น โดยไม่มีการจับคู่ชื่อคอมโบแบบคลุมเครือหรือบางส่วน และไม่เกี่ยวข้องกับคำนำหน้า `auto/` ลำดับการแก้ไข (`getComboForModel()` ใน `src/sse/services/model.ts`):

1. ชื่อคอมโบตรงกันทุกประการ (`model: "my-combo"`),
2. คำนำหน้า `combo/<name>` (`model: "combo/my-combo"`),
3. การแมปโมเดล→คอมโบด้วยรูปแบบ glob (`/api/model-combo-mappings`)

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ข้อผิดพลาดที่พบบ่อยสองประการ:

- **`auto` ไม่ได้ใช้คอมโบของคุณ** `auto`/`auto/*` จะสร้างกลุ่มตัวเลือกแบบไม่ต้องตั้งค่าของตัวเอง และจะตรวจสอบคอมโบที่บันทึกไว้ก็ต่อเมื่อมีคอมโบชื่อ `auto` จริง ๆ เท่านั้น (ไม่แนะนำ) หากต้องการกำหนดเส้นทางผ่านคอมโบ ให้ส่งชื่อที่ตรงกันทุกประการ ไม่ใช่ `auto`
- **`openrouter/auto` เป็นผลิตภัณฑ์ OpenRouter แบบชำระเงินจริง** ("Auto Best Available") ไม่ใช่นามแฝงของ OmniRoute โดยเป็นรายการโมเดลแบบคงที่เพียงรายการเดียวในรีจิสทรี OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) และมีการเรียกเก็บเงินแยกต่างหาก ใช้ การตั้งค่า → การกำหนดเส้นทาง → ซ่อนโมเดลแบบชำระเงิน เพื่อยกเว้นรายการนี้ออกจากกลุ่ม `auto`

ดู [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) และ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) สำหรับความสับสนเดิมที่เอกสารนี้จัดทำขึ้นเพื่ออธิบาย

## มันทำงานอย่างไร (คอมโบอัตโนมัติยังคงมีอยู่)

Auto-Combo Engine จะเลือก provider/model ที่ดีที่สุดแบบไดนามิกสำหรับแต่ละคำขอโดยใช้**ฟังก์ชั่นการให้คะแนน 16 ปัจจัย** (กำหนดใน `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`) น้ำหนักเริ่มต้นรวมเป็น `1.0`; น้ำหนักที่กำหนดเองจะถูกทำให้เป็นมาตรฐานใหม่โดย `normalizeScoringWeights()` สองในสิบหก — `cacheAffinity` และ `resetWindowAffinity` — มีน้ำหนักเริ่มต้นเป็น `0`; `reliability` บรรทุก `0` ใน `DEFAULT_WEIGHTS` แต่ `0.03` อยู่ในแพ็กทั่วไป และ `0.04` ใน `reliability-first` และ `quality` บรรทุก `0.02` ในแพ็ก (`0.03` ใน `quality-first`): ยังคงถูกคำนวณสำหรับผู้สมัครทุกคน และ `cacheAffinity` เกตการขจัดข้อมูลซ้ำซ้อนของ prompt-cache ออกไปนอกคะแนน ดังนั้นปัจจัยที่เป็นศูนย์ค่าเริ่มต้นจึงไม่โหวตตามค่าเริ่มต้น ในขณะที่แพ็กทำ

![Auto-Combo 16-factor scoring](../diagrams/exported/auto-combo-scoring.svg)

ตัวติดตาม `quality` ในหน่วยความจำ (`open-sse/services/routing/quality.ts`) จะว่างเปล่าหลังจากการรีสตาร์ทแบบเย็น ดังนั้นผู้สมัครทุกคนจึงให้คะแนน `0.5` ที่เป็นกลางจนกว่าการสังเกตครั้งแรกจะไปถึง

> **โควต้าที่อ่านไม่ได้ (#15347)** เมื่อผู้ให้บริการมีตัวดึงข้อมูลโควต้าแต่ไม่ได้ส่งคืนสิ่งใดที่อ่านได้ (การดึงข้อมูลล้มเหลว ข้อมูลรับรองหายไป การใช้งานข้อความเท่านั้น หรือสแน็ปช็อตที่มีรูปแบบไม่ถูกต้องโดยไม่มี `windows` ที่สามารถแยกวิเคราะห์ได้และไม่มี `percentUsed` ที่จำกัด รวมถึง `percentUsed: null`) ผู้สมัครจะให้คะแนน `0` บนแกน `quota` และคะแนนสุดท้ายจะถูกคูณด้วย `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`) ซึ่งเป็นรูปแบบการลงโทษแบบนุ่มนวลเช่นเดียวกับการลงโทษสถานะการเชื่อมต่อ การอ่านการใช้งานที่ล้มเหลวถือเป็นหลักฐานเกี่ยวกับการวัดและส่งข้อมูลทางไกล ไม่ใช่ผู้ให้บริการ ดังนั้นจึงอยู่ในอันดับที่ต่ำกว่าการอ่านจริงใดๆ อย่างเคร่งครัด รวมถึงการอ่าน -used 100% ที่ได้รับการยืนยันด้วย แต่จะไม่มีการบล็อคถาวรหรือถูกไล่ออก ผู้ให้บริการที่ไม่มีขีดจำกัดจะรายงาน `unlimited: true` และให้คะแนนเป็นโควต้าเต็ม ผู้ให้บริการที่ไม่มีตัวดึงโควต้าที่ลงทะเบียนไม่มีแหล่งที่มาของการวัดและส่งข้อมูลทางไกลเลยและคงค่าเริ่มต้นเป็น `100`

**รวม:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` ตามที่ประกาศใน `DEFAULT_WEIGHTS`; ตุ้มน้ำหนักที่ผู้ใช้กำหนดค่าจะถูกปรับให้เป็นมาตรฐานใหม่เป็นการแจกแจงโดย `normalizeScoringWeights()` ก่อนที่จะให้คะแนน

| `lkgp`              | Last-Known-Good Path (ปักหมุดผู้ให้บริการที่ประสบความสำเร็จคนสุดท้าย จากนั้นกลับไปสู่กฎเกณฑ์)                                                                                 |
| `context-optimized` | เลือกเป้าหมายที่เหมาะสมที่สุดกับขนาดบริบทปัจจุบัน                                                                                                                             |
| `cache-optimized`   | เรียงลำดับเป้าหมายใหม่โดยความสัมพันธ์ของแคชทันที — การเชื่อมต่อที่น่าจะเก็บคำนำหน้าแคชของคำขอนี้ไว้แล้วจะถูกลองก่อน (`open-sse/services/combo/promptCacheAffinity.ts`, #8008) |
| `fusion` 🧬         | คลี่ออกไปยังแผงของแบบจำลองขนานกัน จากนั้นสังเคราะห์คำตอบหนึ่งคำตอบโดยกรรมการ (ดูด้านล่าง)                                                                                     |
| `pipeline`          | รันเป้าหมายตามลำดับ โดยเธรดเอาต์พุตของแต่ละขั้นตอนไปยังอินพุตของขั้นตอนถัดไป ส่งคืนเฉพาะคำตอบสุดท้ายเท่านั้น (#6396)                                                          |

⭐ = ใหม่ใน v3.8.0 · 🧬 = ใหม่ใน v3.8.36

### ความหมาย `weighted`

`weighted` คือ **สุ่มจับสลากตามสัดส่วนตามคำขอ** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`) ไม่ใช่อีควอไลเซอร์:

- แต่ละคำขอดึง **หนึ่ง** ก้าวด้วยความน่าจะเป็น `weight / totalWeight`; ขั้นตอนที่เหลือจะเรียงลำดับตามน้ำหนักจากมากไปน้อยเป็นห่วงโซ่ทางเลือกสำหรับคำขอนั้น
- ขั้นที่มีน้ำหนักเป็น `0` (หรือหายไป) คือ **ไม่เคยวาด** ในขณะที่ขั้นตอนอื่นๆ มีน้ำหนัก > 0 — แต่จะสามารถใช้เป็นทางเลือกสำรองได้หลังจากที่ขั้นตอนที่ดึงออกมาล้มเหลวเท่านั้น เมื่อเท่านั้น **ทั้งหมด** น้ำหนักเป็น 0 การเลือกจะสม่ำเสมอ
- ขั้นตอนที่เป้าหมายไม่พร้อมใช้งานทั้งหมด เซอร์กิตเบรกเกอร์ผู้ให้บริการ — `OPEN` คูลดาวน์การเชื่อมต่อ การล็อคโมเดล — จะถูกลบออกจากการดึงก่อนที่จะเกิดขึ้น (`open-sse/services/combo/targetResolution.ts`) ดังนั้นขั้นตอนเดียวที่ดีสามารถชนะทุกคำขอได้ชั่วคราว
- `stickyWeightedLimit` (การกำหนดค่าคำสั่งผสม, ปิด `1` = เริ่มต้น) จะปักหมุดขั้นตอนที่วาดไว้สำหรับความสำเร็จติดต่อกันหลายๆ ครั้งก่อนที่จะวาดใหม่

สำหรับการหมุนอย่างเข้มงวด ให้ใช้ `round-robin`; น้ำหนักที่เท่ากันบน `weighted` ทำให้ — ทางสถิติไม่ใช่ความสมดุล — ที่เข้มงวด

### โหมดไปป์ไลน์ตัวแทน

คอมโบ `pipeline` ที่มีอย่างน้อยสองรุ่นสามารถเลือกใช้การกำหนดเส้นทาง planner/executor ด้วย `config.agenticOrchestration.enabled` เป้าหมายแรกเป็นเจ้าของการวางแผนและคำตอบสุดท้าย เป้าหมายที่สองส่งเสียงการเรียกเครื่องมือแบบไคลเอ็นต์เนทีฟ OmniRoute ตรวจพบความต่อเนื่องของเครื่องมือ-ผลลัพธ์จากโปรโตคอลคำขอ ถามผู้วางแผนว่าจำเป็นต้องใช้เครื่องมือรอบอื่นหรือไม่ และทำให้ผู้ดำเนินการหรือผู้วางแผนเป็นขั้นตอนสุดท้ายที่ต้องพบปะกับลูกค้าแบบไดนามิก

`config.agenticOrchestration.contextCompaction` ที่เป็นทางเลือกจะใช้งบประมาณเพย์โหลดแยกต่างหากก่อนที่จะส่งผู้วางแผนหรือผู้ดำเนินการแต่ละคน เปิดใช้งานอย่างชัดเจน:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

สิ่งเหล่านี้คืองบประมาณอักขระ JSON ตามลำดับที่เลือกโดยผู้ดำเนินการ ไม่ใช่หน้าต่างบริบทโทเค็นหรือขีดจำกัดอัปสตรีมที่รับประกัน IDs รุ่นที่แน่นอนจะแทนที่ค่าเริ่มต้น เหนือเกณฑ์ขั้นต่ำ การบดอัดจะลบคำจำกัดความของเครื่องมือที่เหมือนกัน ตัดหลักฐานเครื่องมือขนาดใหญ่ออกด้วยการสรุป และลบกลุ่มประวัติเก่าที่สมบูรณ์ตามอัตราส่วนเป้าหมาย โดยยังคงรักษาคำสั่ง system/developer คำขอล่าสุดของผู้ใช้ รอบเครื่องมือสุดท้ายซึ่งรวมถึง calls/results แบบขนาน และคำแนะนำการกำหนดเส้นทางชั้นนำของ Gemini คำแนะนำระดับบนสุดและการตั้งค่าเครื่องมือจะยังคงอยู่ เครื่องหมายละเว้นบันทึกประวัติที่ถูกลบออก นี่คือการตัดแต่งตามที่กำหนด ไม่ใช่การสรุปเชิงความหมาย หากบริบทที่ปักหมุดยังเกินงบประมาณ คำขอจะส่งกลับ 413 ก่อนที่จะติดต่อโมเดล เมื่อปิดใช้การบีบอัดหรือต่ำกว่าเกณฑ์ คำขอจะผ่านโดยไม่มีการเปลี่ยนแปลง

ในการดำเนินการต่อผลลัพธ์ของเครื่องมือ OmniRoute ยังหยุดการดำเนินการเมื่อรอบที่เสร็จสมบูรณ์สองรอบติดต่อกันทำซ้ำการเรียกเครื่องมือเดียวกันโดยไม่มีการเปลี่ยนแปลง หรือเมื่อทุกผลลัพธ์ที่ทำเครื่องหมายไว้อย่างชัดเจนในสองรอบติดต่อกันล้มเหลว ผลลัพธ์ที่เปลี่ยนแปลงทำให้สามารถโทรซ้ำได้ (เช่น การโพล) ตัวป้องกันจะรีเซ็ตตามคำขอของผู้ใช้ใหม่ จัดกลุ่มการโทรแบบขนานเป็นรอบเดียว และรองรับประวัติ Anthropic การแชทให้เสร็จสิ้น การตอบกลับ และประวัติ Gemini ผู้วางแผนจะได้รับเหตุผลและเป็นเจ้าของคำตอบสุดท้ายแม้ว่าจะขอเครื่องมือใหม่ก็ตาม

โมเดลเพิ่มเติมหลังจากเป้าหมายที่สองได้รับคำสั่งให้สำรองข้อมูลของผู้ดำเนินการ การตอบสนอง HTTP ที่ล้มเหลวหรือข้อยกเว้นในการขนส่งจะเลื่อนไปยังตัวดำเนินการถัดไป โดยดำเนินการตัดสินใจของผู้วางแผนแบบเดียวกันและเครื่องมือดั้งเดิม แต่ขั้นตอนของตัวดำเนินการนั้นพร้อมต์และแก้ไขการเชื่อมต่อแล้ว การตอบสนองที่สำเร็จครั้งแรกจะถูกส่งกลับไม่เปลี่ยนแปลง รวมถึงการสตรีม SSE ด้วย ความล้มเหลวหลังจากเริ่มสตรีมสำเร็จแล้วไม่สามารถลองใหม่ได้ที่นี่ หากตัวดำเนินการทั้งหมดล้มเหลว ความล้มเหลวครั้งล่าสุดจะถูกส่งกลับ ลูกค้ายกเลิกการหยุดการจัดส่ง

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

ผู้ดำเนินการอาจส่งเสียงการโทรอิสระหลายครั้งในการตอบกลับครั้งเดียว การเรียกที่ขึ้นต่อกันจะได้รับการจัดการในรอบผลลัพธ์ของเครื่องมือไคลเอนต์ในภายหลัง โดยผู้วางแผนจะตรวจสอบทุกผลลัพธ์ `maxToolRounds` มีค่าเริ่มต้นเป็น `8` และยอมรับ `1`–`32`; เมื่อถึงจุดนั้นแล้ว ผู้วางแผนจะต้องสร้างคำตอบสุดท้ายที่ดีที่สุด การตัดสินใจของผู้วางแผนภายในจะถูกบัฟเฟอร์ ในขณะที่การตอบสนองต่อหน้าไคลเอ็นต์ที่เลือกจะคงการตั้งค่าการสตรีมดั้งเดิมไว้

### ชุดเหนียว `round-robin` และการขยายบัญชี

Round-robin เป็นแบทช์ ไม่ใช่หนึ่งคำขอต่อขั้นตอน:

- `stickyRoundRobinLimit` (การกำหนดค่าคอมโบ จากนั้น `comboStickyRoundRobinLimit` จากนั้น `settings.stickyRoundRobinLimit` เป็นค่าเริ่มต้น **3** ) คงเป้าหมายเดิมไว้สำหรับความสำเร็จติดต่อกันหลายๆ ครั้งก่อนที่จะหมุน ตั้งค่าการแทนที่คำสั่งผสมเป็น `1` สำหรับการหมุนเวียนคำขอเดียว โปรแกรมแก้ไขคำสั่งผสมจะแสดงค่าที่มีประสิทธิภาพและมาจากเลเยอร์ใด
- `connectionAwareExpansion` (กำหนดค่าคอมโบ จากนั้นตั้งค่า เป็นค่าเริ่มต้น **เท็จ** ) ขยายแต่ละขั้นตอนระดับผู้ให้บริการเป็นเป้าหมายต่อบัญชีก่อนการหมุนเวียน กลยุทธ์ Group-B (ลำดับความสำคัญ, แบบถ่วงน้ำหนัก, แบบ Round-robin, สุ่ม, p2c, ใช้น้อยที่สุด, ปรับต้นทุนให้เหมาะสม, lkgp, เติมก่อน, สุ่มเข้มงวด, ปรับบริบทให้เหมาะสม, ปรับแคชให้เหมาะสม, ถ่ายทอดบริบท, ฟิวชั่น, ไปป์ไลน์) จะเก็บมุมมองระดับผู้ให้บริการไว้จนกว่าจะเปิดใช้งาน ตัวแก้ไขคำสั่งผสมเปิดเผยการสืบทอด / เปิด / ปิด; inherit ใช้ค่าเริ่มต้นสากล (ปิด)
- การกำหนดเส้นทางท้องถิ่นพร้อมท์แคช (`promptCacheAffinityEnabled`, default **จริง** ) จัดลำดับการเชื่อมต่อที่ปักหมุดใหม่ เพื่อให้คีย์แคชที่ตรงกันยังคงอยู่ในบัญชีเดียว โดยจะมีความสำคัญเหนือกว่าการหมุนเวียนแบบวนรอบและการหมุนเวียนแบบถ่วงน้ำหนักในขั้นตอนที่ปักหมุดต่อบัญชี ปิดภายใต้การตั้งค่าเริ่มต้น → Combo หากคุณต้องการการหมุนที่เข้มงวด ไม่มีการแทนที่ต่อคอมโบ

หากต้องการหมุนเวียนหลายบัญชีในรุ่นเดียว ให้เลือก **ขั้นตอนบัญชีแบบไดนามิกหนึ่งขั้นตอน** ( `connectionId` ว่าง ทั้งพูล) โดยมีขีดจำกัดแบบเหนียว `1` ไม่ใช่ `connectionId` ที่ปักหมุดสามตัว ขั้นตอนที่ปักหมุดบวกความสัมพันธ์จะยุบลงในบัญชีเดียวกันแม้ในขณะที่ตัวนับ RR ก้าวหน้าไป

## กลยุทธ์ฟิวชั่น

`fusion` เป็นกลยุทธ์เดียวที่ทำ **ไม่** เลือกเป้าหมายเดียว มันแฟนพร้อมต์ออกไป **แผงทุกรุ่นขนานกัน** จากนั้นกำหนดค่าได้**โมเดลผู้พิพากษา** สังเคราะห์คำตอบสุดท้ายเพียงคำตอบเดียวจากคำตอบของแผงทั้งหมด ย้ายจากอัพสตรีม `decolua/9router` (การออกแบบฟิวชั่นของ OpenRouter); การใช้งานใน `open-sse/services/fusion.ts`

มันทำงานอย่างไร:

0. **บายพาสแบริ่งเครื่องมือ** — คำขอที่มีอาร์เรย์ `tools` ที่ไม่ว่างเปล่าโดยมี `tool_choice` ไม่ได้ `"none"` อย่างชัดเจนจะข้ามพาเนลทั้งหมด: โดยกำหนดเส้นทางโดยตรงไปยังโมเดลเดียว (ผู้พิพากษาที่กำหนดค่าหรือ `panel[0]`) โดยที่ `tools`/`tool_choice` ส่งผ่านโดยไม่มีการแก้ไข สมาชิกของคณะผู้พิจารณาไม่สามารถเข้าถึงเครื่องมือได้ และคำสั่งการสังเคราะห์ของผู้พิพากษาไม่สนับสนุนการปล่อยการเรียกเครื่องมือ ดังนั้น ลูกค้า agentic/tool-calling จะได้รับการตัดสินใจในการเรียกเครื่องมือจริง แทนที่จะเป็นร้อยแก้วสังเคราะห์ (#6771)
1. **พัดออก** (คำขอที่ไม่ต้องใช้เครื่องมือเท่านั้น) — พรอมต์จะถูกส่งไปยังแผงควบคุมทุกรุ่นในคราวเดียว บังคับให้ไม่ทำการสตรีมโดยที่เครื่องมือถูกถอดออก (ผู้พิพากษาต้องการร้อยแก้วที่สมบูรณ์เพื่อสังเคราะห์)
2. **คอลเลกชันโควรัม-เกรซ** — ทันทีที่คำตอบ `minPanel` มาถึง ตัวจับเวลาผ่อนผันสั้นๆ จะเริ่มต้นขึ้นสำหรับผู้หลงทาง จากนั้นจะฟิวชั่นต่อจากสิ่งที่รวบรวมได้ นี่เป็นการจำกัดการลงโทษของโมเดลที่ช้าที่สุดในเวลาติดผนัง โดยมีขอบเขตด้วยการหมดเวลาจริง
3. **การสังเคราะห์ผู้พิพากษา** คำตอบของแผง — จะไม่ระบุชื่อ (`Source 1`, `Source 2`, … — ดังนั้นผู้พิพากษาจึงชั่งน้ำหนักเนื้อหา ไม่ใช่แบรนด์ต้นแบบ) และส่งต่อให้กับผู้พิพากษา ซึ่งจะวิเคราะห์ฉันทามติ / ความขัดแย้ง / การครอบคลุมบางส่วน / ข้อมูลเชิงลึกที่ไม่ซ้ำกัน / จุดบอด จากนั้นเขียน **หนึ่ง** คำตอบที่เชื่อถือได้ การเรียกผู้พิพากษาจะเก็บเครื่องมือ `stream` flag + ดั้งเดิมของลูกค้าไว้ ดังนั้นการใช้เครื่องมือสตรีมมิ่งและดาวน์สตรีมยังคงใช้งานได้
4. **การเสื่อมสลายอย่างสง่างาม** แผง — 0 ตอบ → `503`; → ผู้รอดชีวิต 1 คนอย่างแน่นอนซึ่งคำตอบนั้นจะถูกส่งกลับโดยตรง (ไม่มีอะไรจะหลอมรวม) แผงรุ่นเดียวตอบโดยตรง

สมาชิกแผงอาจเป็นขั้นตอน `combo-ref` (`{kind: "combo-ref", comboName: "..."}`) ที่อ้างอิงถึง — คอมโบอื่นที่จะแก้ไขเป็น **เสียงแผงกล่องดำหนึ่งเสียง** (การส่งแบบเรียกซ้ำแบบเต็มไปยังคอมโบที่อ้างอิง ไม่ใช่การกระจายออกจากเป้าหมายของคอมโบนั้น) โดยมีการป้องกัน depth/cycle แบบเดียวกันทุกกลยุทธ์การใช้การอ้างอิงคอมโบอื่น ๆ ที่ใช้อยู่แล้ว (#6764)

### การกำหนดค่า

กำหนดค่าบนบล็อบ `config` ของคอมโบ (ไม่มีการย้ายสคีมา — ใช้ตาราง `combos`
ที่มีอยู่เดิม):

| ฟิลด์                                    | ชนิด     | ค่าเริ่มต้น     | วัตถุประสงค์                                                                               |
| :--------------------------------------- | :------- | :-------------- | :----------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | โมเดลแรกในพาเนล | โมเดลที่สังเคราะห์คำตอบสุดท้าย                                                             |
| `config.fusionTuning.minPanel`           | `number` | `2`             | จำนวนคำตอบที่สำเร็จซึ่งจำเป็นก่อนเริ่มตัวจับเวลาช่วงผ่อนผัน (จำกัดไว้ที่ `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`          | ระยะเวลารอโมเดลที่ล่าช้าหลังจากครบโควรัมแล้ว                                               |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`         | ขีดจำกัดเวลาสูงสุดแบบตายตัว เพื่อไม่ให้โมเดลหนึ่งที่ค้างทำให้คำขอหยุดชะงัก                 |

ค่าเริ่มต้นอยู่ใน `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)

## โรงงาน Auto-Combo แบบเสมือน

เอนจิน Auto Combo ไม่จำเป็นต้องมีคอมโบที่กำหนดไว้ล่วงหน้า แต่ `open-sse/services/autoCombo/virtualFactory.ts` จะสร้างตัวเลือกแบบทันที:

1. ดึง `getProviderConnections({ isActive: true })` (การเชื่อมต่อทั้งหมดที่เปิดใช้งาน)
2. กรองเฉพาะรายการที่มีข้อมูลรับรองถูกต้อง (API key หรือ OAuth token ที่ยังไม่หมดอายุผ่าน `hasUsableOAuthToken()`)
3. ตรวจสอบเทียบกับ `getProviderRegistry()` เพื่อดูความพร้อมใช้งานของโมเดลและราคา
4. สำหรับแต่ละทูเพิล `(provider, model, connection)` ให้สร้าง `VirtualAutoComboCandidate`
5. เลือก `connection.defaultModel` (หรือโมเดลแรกในรีจิสทรี) เป็นเป้าหมายในการส่งคำขอ
6. ให้คะแนนตัวเลือกแต่ละรายการด้วย `scorePool()` แบบ 16 ปัจจัยและชุดค่าน้ำหนักของเวอร์ชันย่อย
7. ส่งคืน `AutoComboConfig` ที่ได้ซึ่งอยู่ในหน่วยความจำให้แก่ `handleComboChat()` — โดยไม่บันทึกลง DB

ซึ่งหมายความว่า **การเพิ่มผู้ให้บริการรายใหม่ที่เปิดใช้ `auto/*` จะขยายกลุ่มตัวเลือกโดยอัตโนมัติ** — ไม่จำเป็นต้องแก้ไขคอมโบด้วยตนเอง คอมโบเสมือนจะถูกสร้างใหม่สำหรับแต่ละคำขอ ดังนั้นการเชื่อมต่อที่เพิ่งเพิ่มเข้ามาหรือเพิ่งกลับมามีสถานะปกติจะถูกนำมาใช้ทันที

## การฟื้นฟูตนเอง

- **การยกเว้นชั่วคราว**: คะแนน < 0.2 → ยกเว้นเป็นเวลา 5 นาที (เพิ่มระยะเวลาแบบต่อเนื่อง สูงสุด 30 นาที)
- **การรับรู้สถานะ circuit breaker**: OPEN → ยกเว้นโดยอัตโนมัติ; HALF_OPEN → ส่งคำขอทดสอบ
- **โหมดเหตุขัดข้อง**: OPEN >50% → ปิดการสำรวจและเน้นเสถียรภาพสูงสุด
- **การฟื้นตัวหลังคูลดาวน์**: หลังสิ้นสุดการยกเว้น คำขอแรกจะเป็น "คำขอทดสอบ" ที่ลดระยะหมดเวลา

## การสำรวจแบบ Bandit

คำขอ 5% (กำหนดค่าได้) จะถูกกำหนดเส้นทางไปยังผู้ให้บริการแบบสุ่มเพื่อการสำรวจ ฟังก์ชันนี้จะถูกปิดในโหมดเหตุขัดข้อง

## API

**ไม่มี endpoint `POST /api/combos/auto` โดยเฉพาะ** — สามารถใช้งาน Auto-Combo ได้สองวิธี:

1. **ไม่ต้องกำหนดค่า (แนะนำ):** ส่งคำขอ chat completion ใดๆ โดยใช้ `model: "auto"` หรือ `model: "auto/<variant>"` โรงงานเสมือนจะสร้างคอมโบให้ในแต่ละคำขอ โดยไม่ต้องจัดเก็บข้อมูลถาวรหรือเรียก API เพิ่มเติม

2. **คอมโบแบบจัดเก็บถาวรด้วย `strategy: "auto"`:** สร้างคอมโบตามปกติผ่าน `POST /api/combos` แล้วตั้งค่า `strategy: "auto"` พร้อม `config.auto.weights` / `config.auto.candidatePool` ระบบจะใช้กลไกการให้คะแนนเดียวกัน คอมโบจะถูกจัดเก็บไว้ใน `combos` และสามารถนำกลับมาใช้ซ้ำด้วย ID ได้

สำหรับการค้นหา `GET /api/combos/auto` จะแสดงรายการตัวแปรทั้งหมด พร้อมพูลตัวเลือกที่ผ่านการกำหนดค่าแล้ว รวมถึง `context_length` / `max_output_tokens` ซึ่งเป็นค่า MAX จากวินโดว์ทั้งหมดในพูลตัวเลือก ไคลเอนต์ (เช่น ปลั๊กอิน opencode) ต้องประกาศค่าเหล่านี้แทน `0` เนื่องจากบริบทที่เป็นศูนย์จะปิดใช้งานการย่อบริบทอัตโนมัติของ opencode โดยสิ้นเชิง ทำให้เซสชันขยายตัวต่อไปจนกว่าการล้างประวัติของเกตเวย์จะทำลายบริบท การประกาศค่า MAX มีความปลอดภัย เนื่องจากตัวกรองบริบทเบื้องต้นของออโต้คอมโบจะกำหนดเส้นทางคำขอที่มีขนาดใหญ่เกินไปไปยังตัวเลือกที่มีวินโดว์ขนาดใหญ่

```bash
# การใช้งานแบบไม่ต้องกำหนดค่า (ไม่ต้องสร้างคอมโบ)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# คอมโบอัตโนมัติแบบจัดเก็บถาวรผ่าน endpoint คอมโบตามปกติ
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### กลยุทธ์เราเตอร์อัตโนมัติ

คอมโบแบบจัดเก็บถาวรที่ใช้ `strategy: "auto"` สามารถตั้งค่า `config.routerStrategy` (หรือค่าเดิม
`config.auto.routerStrategy`) เป็นค่าใดค่าหนึ่งต่อไปนี้:

- `rules` — การให้คะแนนแบบถ่วงน้ำหนักตามค่าเริ่มต้น
- `score` — เลือกคะแนนถ่วงน้ำหนักที่กำหนดค่าไว้ซึ่งมีค่าสูงสุด หากคะแนนเท่ากันทุกประการ จะคง
  ลำดับตัวเลือกที่กำหนดค่าไว้ ส่วน `explorationRate` ที่มีอยู่จะสุ่มตัวอย่างจากพูลที่จัดอันดับทั้งหมด
- `cost` / `eco` — ผู้ให้บริการที่พร้อมใช้งานและมีราคาถูกที่สุด
- `latency` / `fast` — เวลาแฝง p95 ต่ำที่สุด พร้อมบทลงโทษด้านความน่าเชื่อถือ
- `sla-aware` / `sla` — เลือกตัวเลือกที่เป็นไปตาม SLO ด้านเวลาแฝง p95 อัตราข้อผิดพลาด และ
  ต้นทุน (หากกำหนด)
- `lkgp` — เลือกผู้ให้บริการล่าสุดที่ทราบว่าใช้งานได้ก่อน
- `nadir` — ขอให้ API การตัดสินใจของ [Nadir](https://getnadir.com) ระบุว่า prompt ต้องการ
  โมเดลใดในพูล ต้องเลือกเปิดใช้ และหากล้มเหลวจะกลับไปใช้ `rules`

### รายละเอียดกลยุทธ์เราเตอร์

กลไกออโต้คอมโบมีการใช้งาน **RouterStrategy** แบบถอดเปลี่ยนได้ 7 แบบ ซึ่ง
คุณสามารถสลับผ่าน `config.routerStrategy` (หรือค่าเดิม `config.auto.routerStrategy`)
แต่ละกลยุทธ์จะเลือกผู้ให้บริการหนึ่งรายจากพูลตัวเลือกตาม `RoutingContext`
(ประเภทงาน คำใบ้เกี่ยวกับเครื่องมือ/ภาพ จำนวนโทเค็นโดยประมาณ นโยบาย SLA ที่กำหนดหรือไม่กำหนดก็ได้ และ
ผู้ให้บริการล่าสุดที่ทราบว่าใช้งานได้ ซึ่งกำหนดหรือไม่กำหนดก็ได้)

#### 1. `rules` (ค่าเริ่มต้น) — การให้คะแนนแบบถ่วงน้ำหนักด้วย 16 ปัจจัย

ครอบกลไกการให้คะแนนที่มีอยู่ โดยกรองตัวเลือกที่มี circuit breaker เป็นสถานะ `OPEN`
ออกก่อน จากนั้นเรียกใช้ `scorePool()` ด้วยประเภทงานปัจจุบันและ `getTaskFitness()`
แล้วเลือกผู้ให้บริการที่มีคะแนนสูงสุด

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ควรใช้เมื่อใด**: ค่าเริ่มต้น ใช้เมื่อคุณต้องการความสมดุลระหว่างสัญญาณทั้งหมด

**นามแฝง**: `rules` (ไม่มีนามแฝง)

---

#### 2. `cost` / `eco` — ผู้ให้บริการที่พร้อมใช้งานและมีราคาถูกที่สุด

จัดเรียงพูลตัวเลือกตาม `costPer1MTokens` (จากน้อยไปมาก) แล้วเลือกตัวที่ถูกที่สุด
โดยกรองตัวเลือกที่เป็น `OPEN` ออกก่อน

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ควรใช้เมื่อใด**: เวิร์กโหลดที่คำนึงถึงต้นทุน การประมวลผลแบบแบตช์ หรืองานเบื้องหลัง

**นามแฝง**: `cost`, `eco`

---

#### 3. `latency` / `fast` — เวลาแฝง p95 ต่ำที่สุด พร้อมบทลงโทษด้านความน่าเชื่อถือ

จัดเรียงตาม `p95LatencyMs + (errorRate * 1000)` บทลงโทษจากอัตราข้อผิดพลาดช่วยให้
ผู้ให้บริการที่ไม่น่าเชื่อถือถูกจัดอันดับต่ำลง แม้เวลาแฝงตามค่าที่ระบุจะต่ำก็ตาม

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ควรใช้เมื่อใด**: เวิร์กโหลดที่ไวต่อเวลาแฝง เช่น แชตแบบเรียลไทม์ การเติมข้อความอัตโนมัติ หรือ
ผู้ช่วยเขียนโค้ดแบบโต้ตอบ

**นามแฝง**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — การปฏิบัติตาม SLO ด้านเวลาแฝง/ข้อผิดพลาด/ต้นทุน

ให้คะแนนตัวเลือกแต่ละรายการตามระดับความสอดคล้องกับนโยบาย SLO ที่กำหนดค่าไว้:

| ปัจจัย             | น้ำหนัก | สูตร                                              |
| ------------------ | ------- | ------------------------------------------------- |
| คะแนนเวลาแฝง       | 35%     | `threshold / max(value, ε)`                       |
| คะแนนข้อผิดพลาด    | 35%     | `threshold / max(value, ε)`                       |
| คะแนนสถานะการทำงาน | 15%     | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| คะแนนต้นทุน        | 10%     | `threshold / max(value, ε)` หรือค่าปกติแบบผกผัน   |
| คะแนนความเสถียร    | 5%      | ส่วนเบี่ยงเบนมาตรฐานของเวลาแฝงที่ปรับค่าแบบผกผัน  |

เมื่อ `hardConstraints: true` ระบบจะเรียงตัวเลือกโดยใช้ **คะแนนการละเมิด**
(ค่าที่เกิน SLO ใดๆ) เป็นหลัก แล้วจึงเรียงตามคะแนนรวม มิฉะนั้น ระบบจะใช้
เฉพาะคะแนนรวม

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ให้คะแนนตัวเลือกแต่ละรายการเทียบกับนโยบาย: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**ฟิลด์ SLA** (กำหนดใน config ของคอมโบ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ควรใช้เมื่อใด**: เวิร์กโหลดระดับโปรดักชันที่มีข้อจำกัดด้านเวลาแฝง อัตราข้อผิดพลาด หรืองบประมาณต้นทุนอย่างเข้มงวด

**ชื่อเรียกอื่น**: `sla-aware`, `sla`

#### 5. `lkgp` — ใช้ผู้ให้บริการล่าสุดที่ทราบว่าใช้งานได้ดีก่อน

ลองใช้ **ผู้ให้บริการล่าสุดที่ทราบว่าใช้งานได้ดี** (หากกำหนดไว้) ก่อน จากนั้นจึงย้อนกลับไปใช้
กลยุทธ์ `rules` ซึ่งมีประโยชน์สำหรับการคงผู้ให้บริการเดิมตลอดเซสชัน เพื่อให้ผู้ให้บริการรายเดิมจัดการ
คำขอต่อเนื่องในการสนทนา

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // ย้อนกลับไปใช้กลยุทธ์ rules
    return getStrategy("rules").select(pool, context);
  }
}
```

**ควรใช้เมื่อใด**: การสนทนาหลายรอบที่คุณต้องการให้ผู้ให้บริการรายเดิมจัดการ
คำขอต่อเนื่อง (เช่น เพื่อการแคช ความต่อเนื่องของบริบท หรือความสม่ำเสมอของราคา)

**ชื่อเรียกอื่น**: `lkgp` (ไม่มีชื่อเรียกอื่น)

#### 6. `nadir` — การเลือกโมเดลตามพรอมต์ผ่าน Nadir

กลยุทธ์ทั้งหมดข้างต้นจัดอันดับตัวเลือกโดยอิงจากข้อมูลเทเลเมทรีของตนเอง แต่ไม่มีกลยุทธ์ใดอ่าน
คำขอ `nadir` จะส่งข้อความล่าสุดของผู้ใช้พร้อมรหัสโมเดลในพูลไปยัง
API สำหรับการตัดสินใจของ [Nadir](https://getnadir.com) (`POST /v1/bucket`) และกำหนดเส้นทางไปยังโมเดล
ที่ Nadir เลือกจากรายการดังกล่าว (`simple` → โมเดลที่รองรับและมีราคาถูกที่สุด, `complex` → โมเดล
ระดับแนวหน้า) ส่วนการเชื่อมต่อที่ให้บริการโมเดลดังกล่าวยังคงถูกเลือกโดย `rules` ดังนั้นโควตา
สถานะการทำงาน และต้นทุนจึงยังคงเป็นปัจจัยตัดสินว่าจะใช้บัญชีใด

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` และ `OMNIROUTE_NADIR_BASE_URL` เป็นค่าทดแทนจาก env สำหรับสตริงทั้งสอง
โดยจำเป็นต้องใช้ `baseUrl` เฉพาะสำหรับ Nadir ที่โฮสต์เองเท่านั้น (ระบบรองรับ `/v1` ที่ต่อท้ายมา)
การเรียกโดยไม่มีคีย์จะใช้ระดับผู้ใช้แบบไม่ระบุตัวตนของ Nadir ซึ่งมีการจำกัดอัตราต่อ IP เมื่อใช้คีย์
([สร้างคีย์](https://app.getnadir.com/dashboard/api-keys)) การตัดสินใจแต่ละครั้งจะถูก
บันทึกลงในแดชบอร์ด Nadir ของคุณ ดูขั้นตอนการตั้งค่าและการตรวจสอบทั้งหมดได้ที่:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/)

ข้อมูลที่ถูกส่งออกไป ได้แก่ ข้อความล่าสุดของผู้ใช้ (16,000 อักขระแรก) รหัสโมเดล
ของตัวเลือก และแท็กช่องทาง `source: "omniroute"` โดยจะไม่มีการส่งพรอมต์ระบบ ประวัติ เครื่องมือ หรือ
ส่วนหัว

ลักษณะการทำงานเมื่อเกิดความล้มเหลวคือ fail-open: เมื่อหมดเวลา (ค่าเริ่มต้น 2000 ms), ได้รับสถานะที่ไม่ใช่ 2xx, ไม่สามารถเข้าถึง
โฮสต์, การตอบกลับผิดรูปแบบ หรือเลือกโมเดลที่อยู่นอกพูล ระบบจะใช้การตัดสินใจจาก `rules`
และเติม `NadirStrategy: fallback (…)` ไว้ข้างหน้าเหตุผล หลังจากการเรียกล้มเหลว กลยุทธ์จะ
ข้ามการเรียกผ่านเครือข่ายเป็นเวลา 30 s ดังนั้นเมื่อบริการขัดข้อง จะเกิดการหมดเวลาเพียงหนึ่งครั้งต่อ 30 s แทนที่จะ
เกิดหนึ่งครั้งต่อคำขอ เหตุการณ์การกำหนดเส้นทางจะรายงาน `strategy: "nadir"` เฉพาะเมื่อ Nadir เป็นผู้
ตัดสินใจเลือกจริงเท่านั้น

**ควรใช้เมื่อใด**: ทราฟฟิกที่มีระดับความยากหลากหลายบนพูลซึ่งครอบคลุมโมเดลหลายระดับ (โมเดลขนาดเล็ก โมเดลระดับกลาง
และโมเดลระดับแนวหน้า) เมื่อคุณต้องการลดต้นทุนจากการใช้โมเดลระดับแนวหน้าอยู่เสมอ

**ชื่อเรียกอื่น**: `nadir` (ไม่มีชื่อเรียกอื่น)

### กลยุทธ์เราเตอร์แบบกำหนดเอง

คุณสามารถลงทะเบียนการนำ `RouterStrategy` ไปใช้งานด้วยตนเองผ่าน API สาธารณะ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ใส่ตรรกะการกำหนดเส้นทางของคุณที่นี่
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

จากนั้นใช้งานดังนี้:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## ความเหมาะสมกับงาน

โมเดลมากกว่า 30 รายการได้รับการประเมินในงาน 6 ประเภท (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) รองรับรูปแบบไวลด์การ์ด (เช่น `*-coder` → คะแนนด้านการเขียนโค้ดสูง)

## สรุป Auto Variants

เมื่อรวม `auto` แบบเปล่า (ค่าเริ่มต้น) กับค่า `AutoVariant` ทั้ง 6 ค่าที่ประกาศไว้ใน `autoPrefix.ts` จะมี **ID โมเดลที่เรียกใช้ได้ 7 รายการ**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` แจกแจงค่าไว้ 6 ค่า ส่วนตัวเลือกที่ 7 คือ "ไม่มี variant" — `auto` แบบเปล่า — ซึ่งจัดการโดย `parseAutoPrefix()` เป็น `variant: undefined`)

## ระดับ Tier ทำงานร่วมกับ Auto-Combo อย่างไร

ฟังก์ชันการให้คะแนนแบบ 16 ปัจจัย (`open-sse/services/autoCombo/scoring.ts`) ถือว่าการเป็นสมาชิกระดับ Tier
เป็นสัญญาณสองรายการ ได้แก่ `tierPriority` (0.0476) และ `tierAffinity` (0.0476) โปรดดู
[ตารางปัจจัยการให้คะแนน](#how-it-works-persisted-auto-combos) มาตรฐานด้านบนสำหรับชุด
`DEFAULT_WEIGHTS` ทั้งหมด — ค่าที่กำหนดทับต่อแพ็ก (ship-fast/cost-saver/quality-first/
offline-friendly) แสดงอยู่ในตาราง "โปรไฟล์น้ำหนักต่อแพ็ก"

ระดับ Tier เพียงอย่างเดียว **ไม่ได้** บังคับให้ Tier 1 มาก่อน — หากเวลาแฝงของ Tier 1 ไม่ดี หรือ
ความคุ้มค่าระหว่างต้นทุนกับคุณภาพไม่เหมาะสม Tier 2 จะชนะ หากต้องการบังคับลำดับตาม Tier ให้ใช้
กลยุทธ์คอมโบ `priority` และจัดเรียงผู้ให้บริการตาม Tier

หากต้องการให้น้ำหนักแก่ Tier 1 (การสมัครสมาชิก) อย่างมาก ให้เพิ่มน้ำหนักของ `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

โปรดดู [`docs/guides/TIERS.md`](../guides/TIERS.md) สำหรับคำจำกัดความของ Tier และการจัดประเภทผู้ให้บริการ

### เมทริกซ์การตัดสินใจกำหนดเส้นทางแบบกำหนดผลลัพธ์ได้ (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` พิสูจน์ **การตัดสินใจ** กำหนดเส้นทางของกลยุทธ์สาธารณะทั้ง 19 รายการแบบต้นทางถึงปลายทางผ่านไปป์ไลน์ combo จริง โดยจำลองระบบต้นทาง ความครอบคลุมประกอบด้วย:

- กลยุทธ์ `ROUTING_STRATEGY_VALUES` ทั้ง 19 รายการ (ordered, weighted, cost, context, fusion, …)
- `quota-share` (ภายใน) แบบต้นทางถึงปลายทาง: ความเป็นธรรมของ DRR + การลดลำดับความสำคัญเมื่ออิ่มตัวผ่านจุดเชื่อมต่อ `selectQuotaShareTarget` จริง (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)
- ความครอบคลุมของการส่งต่อแบบสากลสำหรับ `context-relay` ในทุกจำนวนเป้าหมาย

ชุดการทดสอบนี้ทำงานใน CI (งาน `test:integration`) โดยใช้ `--test-concurrency=1` และ `--test-force-exit` เพื่อให้ผลลัพธ์แน่นอนและไม่ต้องใช้ข้อมูลประจำตัวจริง

### การทดสอบ smoke แบบ live ที่มีเงื่อนไข (ไม่อยู่ใน CI — ผู้ให้บริการจริง)

| `npm run test:combo:live`              | การกำหนดเส้นทางจริงภายในโปรเซสด้วย `RUN_COMBO_LIVE=1`; บันทึก snapshot ของฐานข้อมูล OmniRoute ที่ใช้งานจริง |
