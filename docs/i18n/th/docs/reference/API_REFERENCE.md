## การทำให้การสนทนาเสร็จสมบูรณ์

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### ส่วนหัวที่กำหนดเอง

| Header                   | Direction | Description                                                                                                                                                                                               |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Request   | ตั้งค่าเป็น `true` เพื่อข้ามแคช                                                                                                                                                                           |
| `x-omniroute-no-memory`  | Request   | ตั้งค่าเป็น `true` เพื่อข้ามการแทรก memory + skills สำหรับคำขอนี้ (ทำงานเหมือน no-cache และหลีกเลี่ยงค่าใช้จ่ายด้านโทเค็น/ต้นทุนต่อการเรียก)                                                              |
| `X-OmniRoute-Progress`   | Request   | ตั้งค่าเป็น `true` สำหรับเหตุการณ์ความคืบหน้า                                                                                                                                                             |
| `X-Session-Id`           | Request   | คีย์เซสชันแบบคงที่สำหรับการยึดเซสชันภายนอก                                                                                                                                                                |
| `x_session_id`           | Request   | ยอมรับรูปแบบที่ใช้ขีดล่างด้วย (HTTP โดยตรง)                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | Request   | แท็กเซสชัน/การสนทนาที่ผู้เรียกกำหนดเอง (ใช้กับ memory ด้วย) เมื่อมีการระบุ ค่านี้จะถูกบันทึกตามเดิมใน `call_logs.session_tag` เพื่อจัดสรรค่าใช้จ่ายรายเซสชัน (#8249) — จะไม่สร้างขึ้นเองเมื่อไม่มีการระบุ |
| `Idempotency-Key`        | Request   | คีย์สำหรับขจัดรายการซ้ำ (ช่วงเวลา 5 วินาที)                                                                                                                                                               |
| `X-Request-Id`           | Request   | คีย์สำหรับขจัดรายการซ้ำทางเลือก                                                                                                                                                                           |
| `x-omniroute-connection` | Request   | ยึดคำขอแบบโมเดลเดียวกับการเชื่อมต่อของผู้ให้บริการหนึ่งรายการ (บัญชี) ตาม id — ดู [การยึดบัญชีต่อคำขอ](#account-pinning-per-request)                                                                      |
| `X-OmniRoute-Cache`      | Response  | `HIT` หรือ `MISS` (ไม่ใช่การสตรีม)                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | Response  | `true` หากมีการขจัดรายการซ้ำ                                                                                                                                                                              |
| `X-OmniRoute-Progress`   | Response  | `enabled` หากเปิดใช้การติดตามความคืบหน้า                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | Response  | ID เซสชันที่มีผลซึ่ง OmniRoute ใช้งาน                                                                                                                                                                     |
| `X-OmniRoute-Request-Id` | Response  | ID สำหรับเชื่อมโยงคำขอ (เมื่อทราบ)                                                                                                                                                                        |
| `X-OmniRoute-Version`    | Response  | เวอร์ชันบิลด์ของ OmniRoute (มีอยู่เสมอ)                                                                                                                                                                   |
| `X-OmniRoute-Cost-Saved` | Response  | จำนวนเงิน USD ที่แคชช่วยหลีกเลี่ยงได้เมื่อเป็น HIT (เฉพาะ cache hit)                                                                                                                                      |
| `X-OmniRoute-Decision`   | Response  | ร่องรอยการกำหนดเส้นทาง: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` คือกลยุทธ์แบบผสม หรือ `single` สำหรับคำขอที่ไม่ใช่แบบผสม) — มีอยู่เสมอในการตอบกลับเมื่อเสร็จสมบูรณ์                 |

> หมายเหตุเกี่ยวกับ Nginx: หากคุณใช้เฮดเดอร์ที่มีขีดล่าง (เช่น `x_session_id`) ให้เปิดใช้ `underscores_in_headers on;`

#### การยึดบัญชีต่อคำขอ

เมื่อผู้ให้บริการมีการเชื่อมต่อหลายรายการ (บัญชีหรือคีย์) โดยปกติ OmniRoute จะเลือกหนึ่งรายการ
ผ่านกลยุทธ์การเลือกบัญชี คำขอสามารถยึดการเชื่อมต่อเฉพาะรายการหนึ่งแทนได้
โดยใช้เฮดเดอร์ `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **ตำแหน่งที่ค้นหา id ได้** เปิดหน้าผู้ให้บริการในแดชบอร์ด
  (**Dashboard → Providers → <provider>**) แล้วคลิกชิป id `xxxxxxxx…` บนแถวการเชื่อมต่อ
  — ระบบจะคัดลอก connection id แบบเต็ม
- **คำขอใดที่รองรับค่าอ้างอิงนี้** คำขอโมเดลเดี่ยว (`provider/model`) บน
  `/v1/chat/completions`, `/v1/messages` และ `/v1/responses` ชุดคอมโบจะไม่สนใจเฮดเดอร์นี้ ให้ตรึงบัญชีต่อขั้นตอนของคอมโบผ่านการเชื่อมต่อของขั้นตอนนั้นเอง
- **การตรึงนี้เป็นข้อบังคับ ไม่ใช่เพียงการตั้งค่า предпочтительнее** ระบบจะใช้การเชื่อมต่อที่ตรึงไว้เท่านั้น หากเกิดความล้มเหลวภายในคำขอ ระบบจะบันทึกช่วงพักใช้งานของบัญชี แต่จะ **ไม่** เปลี่ยนไปใช้บัญชีพี่น้องของผู้ให้บริการรายเดียวกัน
- **ช่วงพักใช้งานและโควตาจะยกเลิกการตรึง** ขณะที่การเชื่อมต่อที่ตรึงไว้กำลังอยู่ในช่วงพักใช้งาน โควตาถูกใช้หมด หรือถูกบล็อกโดยนโยบายโควตา คำขอถัดไปจะย้อนกลับไปใช้การเชื่อมต่ออื่นของผู้ให้บริการ เช่นเดียวกับทราฟฟิกที่ไม่ได้ตรึง
- **id ที่ไม่รู้จักหรือถูกปิดใช้งานจะทำให้คำขอล้มเหลว** id ที่ไม่อยู่ในพูลที่ใช้งานอยู่ของผู้ให้บริการ (ถูกลบ ปิดใช้งาน หรือเป็นของผู้ให้บริการรายอื่น) จะไม่เหลือบัญชีที่ใช้ได้ ดังนั้นคำขอจะล้มเหลวแทนที่จะเปลี่ยนเส้นทางไปที่อื่นโดยไม่แจ้งให้ทราบ

Claude Code ส่งเฮดเดอร์แบบกำหนดเองผ่าน `ANTHROPIC_CUSTOM_HEADERS` ให้ใส่ไว้ในบล็อก `env`
ของ `~/.claude/settings.json` หรือใน `.claude/settings.json` ระดับโปรเจกต์ เพื่อจะตรึงบัญชีที่แตกต่างกันสำหรับแต่ละโปรเจกต์:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

แหล่งที่มา: `src/sse/handlers/chat.ts` (การอ่านเฮดเดอร์), `src/sse/services/auth.ts` และ
`src/sse/services/sessionAffinityPin.ts` (การยกเลิกการตรึงและการตรวจสอบว่าไม่มีอยู่ในพูล)

> **เฮดเดอร์ข้อมูลต้นทุน:** การตอบกลับที่สำเร็จแบบไม่สตรีมยังมีชุดข้อมูลต้นทุน `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, ทศนิยมคงที่ 10 ตำแหน่ง; `0.0000000000` สำหรับรายการที่ไม่มีค่าใช้จ่ายหรือไม่มีการกำหนดราคา), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` และ `X-OmniRoute-Fallback-Attempts` (เฉพาะเมื่อมีค่ามากกว่า 0) รวมถึง `X-OmniRoute-Request-Id` และ `X-OmniRoute-Version` ข้อมูลเหล่านี้ถูกส่งออกโดย chat completions, `/v1/responses`, `/v1/messages` **และมีเดียเอนด์พอยต์** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` และ `/v1/moderations` (มีต้นทุนเป็น `0` เสมอ) ต้นทุนของมีเดียจะคำนวณแยกตามประเภทข้อมูล (ต่อภาพ, ต่อวินาที, ต่อตัวอักษร, ต่อหน่วยการค้นหา) เมื่อมีข้อมูลราคา มิฉะนั้นจะเป็น `0` (ทำงานต่อได้เมื่อคำนวณต้นทุนไม่ได้)

> **ความหมายของต้นทุนเมื่อแคชถูกใช้งาน:** เมื่อเกิด semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) จะไม่มีการเรียก upstream ดังนั้น `X-OmniRoute-Response-Cost` จึงเป็น `0.0000000000` (ต้นทุน **ส่วนเพิ่ม**ของการให้บริการผลลัพธ์จากแคช) ต้นทุนเดิม/ต้นทุนที่ควรเกิดขึ้นจะรายงานแยกต่างหากใน `X-OmniRoute-Cost-Saved` ผู้บริโภคข้อมูลการเรียกเก็บเงินควรรวมค่า `X-OmniRoute-Response-Cost` (ผลลัพธ์จากแคชไม่มีต้นทุน); ระบบวิเคราะห์แคชสามารถรวมค่า `X-OmniRoute-Cost-Saved` ได้

## ลีสเซสเซสชันแบบจัดการพิเศษเฉพาะ

การให้เช่าลีสเซสเซสชันแบบจัดการพิเศษเฉพาะเป็นสัญญาการกำหนดเส้นทางแบบเลือกใช้ ซึ่งไม่ขึ้นกับไคลเอนต์: เจ้าของที่ใช้งานอยู่หนึ่งรายจะถือครองการเชื่อมต่อ OmniRoute ที่เข้าเกณฑ์หนึ่งรายการ ไม่ใช่การเช่าโมเดล ไม่จำเป็นต้องใช้ OAuth ไม่ได้ระบุไคลเอนต์ใดโดยเฉพาะ และไม่จำเป็นต้องใช้ผู้ให้บริการรายใดรายหนึ่ง

คีย์ API ที่ใช้ยืนยันตัวตนต้องมีสโคป `lease:exclusive` และมีรายการ `allowedConnections` ที่ระบุไว้อย่างชัดเจนและไม่ว่างเปล่า ขอบเขตการเปลี่ยนแปลงฐานข้อมูลจะบังคับใช้ทั้งสองฟิลด์ร่วมกันเมื่อสร้างคีย์และอัปเดตบางส่วน

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

การตอบกลับที่สำเร็จสำหรับการ acquire, renew และ release จะแสดงไทม์สแตมป์, `state` และ `generation` ที่เป็นค่าบวกและตรงกันทุกประการ แต่จะไม่เปิดเผยการเชื่อมต่อที่เลือกหรือข้อมูลรับรองใด ๆ การ renew และ release จะส่ง generation ในเนื้อหา JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

เจ้าของลีสที่ใช้งานอยู่สามารถขอข้อมูลเมตาดาต้าสำหรับการแสดงผลที่ปลอดภัยต่อความเป็นส่วนตัวของการผูกปัจจุบันได้อย่างชัดเจน:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

การดำเนินการ status แบบเลือกใช้นี้ถูกตรวจสอบการผูกด้วย owner แบบทึบแสง คีย์ API แบบจัดการที่ผ่านการยืนยันตัวตน และ generation ที่ใช้งานอยู่และตรงกันทุกประการ ภายในธุรกรรมฐานข้อมูลเดียว `displayName` จะเป็นเพียงชื่อการเชื่อมต่อที่กำหนดค่าไว้หลังตัดช่องว่างแล้วเท่านั้น และจะเป็น `null` เมื่อไม่มีชื่อที่กำหนดค่าไว้อย่างปลอดภัย OmniRoute จะไม่แทนที่ด้วยอีเมลหรือข้อมูลระบุตัวตนของบัญชีที่สร้างขึ้น ค่า provider เป็นป้ายกำกับสำหรับการแสดงผลที่ไม่อ่อนไหว และจะไม่เป็นตัวระบุผู้ให้บริการที่เข้ากันได้ซึ่งสร้างขึ้น ข้อมูลรับรอง โทเค็น คุกกี้ รหัสการเชื่อมต่อหรือคีย์ API แบบดิบ แฮชของ owner ความลับสำหรับการตรวจสอบสิทธิ์ และข้อมูลการกำหนดเส้นทางภายในจะถูกตัดออก

การค้นหาด้วยคีย์ผิด owner ผิด generation ที่ล้าสมัย ไม่พบ หมดอายุ ถูก release หรือถูกทำให้ใช้ไม่ได้ทั้งหมด จะส่งคืนข้อผิดพลาด `409 LEASE_FENCE_STALE` แบบเดียวกันโดยไม่มีข้อมูลเมตาดาต้าการเชื่อมต่อ ไคลเอนต์ที่ได้รับการตอบกลับให้รอความจุจะไม่มีการผูกที่ใช้งานอยู่ให้ตรวจสอบ เมื่อการกำหนดเส้นทางเปลี่ยนลีสที่ใช้งานอยู่ generation เดิมจะยังคงใช้งานได้ และ status จะส่งคืนการผูกใหม่แบบอะตอมิก โดยไม่ส่งคืนการผูกเดิม ไคลเอนต์ที่มีอยู่ยังคงไม่เปลี่ยนแปลง เนื่องจากการตอบกลับของ acquire, renew, release และการรอยังคงใช้รูปแบบเดิม

สัญญาของเซิร์ฟเวอร์นี้ไม่เปลี่ยนแปลง `/status` ของ OpenAI Codex มาตรฐาน ปัจจุบัน Codex มาตรฐานรายงานผู้ให้บริการโมเดลและสถานะการยืนยันตัวตน/บัญชีในตัว แต่ไม่ได้แสดงข้อมูลเมตาดาต้าบัญชีของผู้ให้บริการแบบกำหนดเองโดยพลการ การผสานรวมไคลเอนต์ในภายหลังจะต้องเรียกการดำเนินการนี้และตัดสินใจว่าจะแสดง `connection.displayName` อย่างไร

จากนั้นทุกคำขอการอนุมานที่จัดการจะส่งเฮดเดอร์ควบคุมทั้งสองรายการ:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

owner, generation, การเชื่อมต่อที่ใช้งานอยู่ และคีย์ API ที่ผ่านการยืนยันตัวตนซึ่งตรงกันทุกประการ จะถูกตรวจสอบการผูกทันทีก่อนการพยายามส่งต่อไปยัง upstream ที่รองรับแต่ละครั้ง การเล่นซ้ำ owner และ generation กับคีย์อื่นจะล้มเหลว แม้ว่าคีย์นั้นจะอนุญาตให้ใช้การเชื่อมต่อเดียวกันก็ตาม owner แบบดิบจะไม่ถูกจัดเก็บในระบบ ไม่ถูกบันทึกในล็อก ไม่ถูกเก็บไว้ในสแนปช็อตคำขอ และไม่ถูกส่งต่อไปยัง upstream

การแย่งใช้ชั่วคราวจะส่งคืน HTTP `429` พร้อม `Retry-After` และ:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

การตอบกลับนี้หมายความเพียงว่าชุดรายการที่เข้าเกณฑ์ตามปกติไม่ว่างเปล่า และตัวเลือกที่ว่างอยู่ทั้งหมดถูกถือครองโดยลีสที่ใช้งานอยู่ของเจ้าของรายอื่น โมเดล/ผู้ให้บริการที่ไม่รองรับ ความไม่ตรงกันของนโยบาย ช่วงพักการใช้งาน โควตา สถานะสุขภาพ และความล้มเหลวด้านการเข้าเกณฑ์ตามปกติอื่น ๆ ยังคงใช้การตอบกลับเดิมของ OmniRoute

### `x-omniroute-compression`

การแทนที่แผนการบีบอัดต่อคำขอ มีลำดับความสำคัญสูงสุด — มีผลเหนือการแทนที่ของ routing-combo, โปรไฟล์ที่ใช้งานอยู่, auto-trigger และ Default ของแผงควบคุม ค่า:

| ค่า           | ผลลัพธ์                                                                                            |
| ------------- | -------------------------------------------------------------------------------------------------- |
| `off`         | ไม่มีการบีบอัดสำหรับคำขอนี้                                                                        |
| `default`     | โปรไฟล์ Default ที่มาจากแผงควบคุม (ไม่สนใจโปรไฟล์ที่ใช้งานอยู่) เอ็นจินแบบสูญเสียข้อมูลจะถูกปิดไว้ |
| `safe`        | ดำเนินการเฉพาะการลบข้อมูลซ้ำและการรวมช่องว่างเท่านั้น                                              |
| `allow-lossy` | ใช้แผนของผู้ปฏิบัติงานต่อไปสำหรับคำขอนี้ รวมถึงสรุปและการเขียนรูปแบบใหม่                           |
| `engine:<id>` | เอ็นจินเดียวเมื่อเปิดใช้งาน เช่น `engine:rtk` เป็นการเลือกใช้เอ็นจินนั้นต่อคำขอ                    |
| `<combo>`     | คอมโบที่มีชื่อ โดยจับคู่ตามชื่อ (ไม่พิจารณาตัวพิมพ์เล็ก-ใหญ่) ก่อน แล้วจึงตาม id                   |

หมายเหตุ:

- ค่าที่ไม่รู้จักจะถูกละเว้น (คำขอจะไม่ถูกปฏิเสธ); การแก้ไขค่าจะดำเนินต่อไปตามลำดับความสำคัญปกติของผู้ปฏิบัติงาน
- หากมีหลายคอมโบใช้ชื่อเดียวกัน ให้ส่ง **id** ของคอมโบเพื่อให้จับคู่ได้แน่นอน
- คอมโบที่มีชื่อเป็น `off` หรือ `default` จะไม่สามารถเลือกตามชื่อได้ (คีย์เวิร์ดเหล่านี้จะถูกตีความก่อน); ให้อ้างอิงคอมโบดังกล่าวด้วย id
- สวิตช์การบีบอัดหลักเป็นประตูควบคุมแบบเข้มงวด: เมื่อปิดใช้การบีบอัดทั่วโลก เฮดเดอร์นี้จะไม่สามารถเปิดใช้งานได้

แผนที่ถูกนำไปใช้จะถูกส่งกลับในเฮดเดอร์การตอบกลับ:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

โดย `<source>` จะเป็นหนึ่งใน `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` หรือ `off`


ผู้ให้บริการที่ใช้ได้: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI

รหัสแค็ตตาล็อกอยู่ในรูปแบบ `provider/model` (ตัวอย่าง: `jina-ai/jina-embeddings-v5-omni-small`) นอกจากนี้ รหัสโมเดล Jina แบบไม่ระบุผู้ให้บริการที่ปรากฏในรีจิสทรี (เช่น `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ก็สามารถแก้ไขได้เช่นกัน โมเดลฝังเวกเตอร์/จัดอันดับ/จำแนก/แบ่งส่วนของ Jina จะใช้ข้อมูลรับรอง `jina-ai` จากแดชบอร์ดก่อน โดย `JINA_AI_API_KEY` จะเป็นทางเลือกสำรองเฉพาะเมื่อไม่มีคีย์จากแดชบอร์ดเท่านั้น การ์ด `jina-reader` ใช้สำหรับ Reader / `r.jina.ai` เท่านั้น (`POST /v1/web/fetch`) และไม่ให้บริการการฝังเวกเตอร์หรือการจัดอันดับ

โมเดลในรีจิสทรีที่ประกาศว่ารองรับหลายโมดัลยังรับรายการแบบมีโครงสร้างที่ไม่ขึ้นกับผู้ให้บริการได้สูงสุด 32 รายการ ประเภทของรายการสื่อ ได้แก่ `text`, `image`, `audio`, `video` และ `document` โดย `source` ของสื่อจะเป็น `{"type":"url","url":"https://..."}` หรือ `{"type":"base64","data":"...","media_type":"..."}`

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` และนามแฝงของตระกูล `jina-ai/jina-embeddings-v5-omni` → omni-small) ยังรับเอกสาร EmbeddingsV5Request แบบเนทีฟของ Jina และ **ส่งต่อโดยคงสภาพเดิม** ไปยัง `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ค่าเนทีฟ `{ image | audio | video | pdf }` อาจเป็น URL HTTPS สาธารณะ, URI `data:` หรือ base64 ดิบ OmniRoute จะไม่แปลงอ็อบเจ็กต์เหล่านั้นเป็นสตริงหรือดึง URL รูปภาพแบบเนทีฟ — Jina จะดึงสื่อสาธารณะด้วยตนเอง ฟิลด์ Jina เพิ่มเติม (`task`, `normalized`, `truncate`, `embedding_type`) จะถูกส่งต่อ โมเดล Jina SKU ที่รับเฉพาะข้อความยังคงปฏิเสธเอกสารที่ไม่ใช่ข้อความ

ขอบเขตด้านความปลอดภัยและการส่งข้อมูล:

- URL สื่อระยะไกลต้องเป็น HTTPS สาธารณะ รายการรูปแบบมาตรฐาน `{type,source:url}` จะถูกดึงจากฝั่งเซิร์ฟเวอร์ (ตรวจสอบการเปลี่ยนเส้นทางซ้ำ, จำกัดเวลา, จำกัดขนาด, DNS สาธารณะ, การตรึงการเชื่อมต่อ) และแทรกข้อมูลไว้ก่อนเรียกผู้ให้บริการ รายการ Jina-native `{image:"https://..."}` จะถูกส่งต่อโดยไม่เปลี่ยนแปลงหลังจากผ่านการตรวจสอบ HTTPS สาธารณะเดียวกัน โดย Jina จะเป็นผู้ดึง URL
- สื่อ base64 แบบอินไลน์จำกัดที่ 8 MiB หลังถอดรหัสต่อรายการ และ 16 MiB หลังถอดรหัสรวมทั้งคำขอ

การแปลงสำหรับผู้ให้บริการ (รายการมาตรฐานจะไม่ถูกส่งต่อโดยไม่เปลี่ยนแปลง):

- โมเดลหลายโมดัลของ Jina: แต่ละรายการระดับบนสุดจะกลายเป็นอ็อบเจ็กต์ที่มีคีย์ตามโมดัลหนึ่งรายการ (`text` / `image` / `audio` / `video` / `pdf`) โดยใช้ URI `data:` สำหรับสื่อแบบอินไลน์ และได้เวกเตอร์หนึ่งรายการต่อรายการระดับบนสุด
- ตระกูล Gemini Embedding 2: อาร์เรย์ระดับบนสุดหนึ่งชุดจะกลายเป็นคำขอ `models/{model}:embedContent` แบบเนทีฟรายการเดียว โดยมี `content.parts` (`text` หรือ `inline_data`)
- llama.cpp (`llama-cpp/<model>` หรือโมเดลใดก็ตามที่เซิร์ฟเวอร์ภายในโหลดไว้): รายการ `text` แบบมาตรฐานจะกลายเป็นสตริงธรรมดา ส่วน `image` / `audio` / `video` จะกลายเป็นอ็อบเจ็กต์ `{"content": [part]}` หนึ่งรายการต่อประเภท โดยใช้ส่วนเนื้อหาแชตของ llama-server (`image_url`, `input_audio` ที่มีรูปแบบ `wav` / `mp3` / `flac`, `input_video`) พร้อมข้อมูลแบบอินไลน์ และได้เวกเตอร์หนึ่งรายการต่อรายการระดับบนสุด เซิร์ฟเวอร์ต้องทำงานด้วย `--embedding --mmproj …`; หากไม่มีโปรเจ็กเตอร์ เซิร์ฟเวอร์จะปฏิเสธสื่อเอง ไม่รองรับ `document`
- โมเดลที่ไม่รู้จัก/ไดนามิกซึ่งไม่มีข้อมูลเมทาดาทาโมดัลอย่างชัดเจนจะปฏิเสธอินพุตแบบมีโครงสร้างด้วย HTTP 400

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

การผสมผสานโมเดล/โมดัลที่ไม่รองรับจะแสดงผลเป็น HTTP 400 แทนการบังคับแปลงรายการ คำขอแบบสตริง/โทเค็นเดิมที่มีฟิลด์ส่วนขยายที่ไม่ใช่อินพุตจะยังคงถูกส่งต่อโดยไม่เปลี่ยนแปลง

```bash
# แสดงรายการโมเดลการฝังเวกเตอร์ทั้งหมด
GET /v1/embeddings
```

## การสร้างภาพ

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ผู้ให้บริการที่รองรับ ได้แก่ OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (ภายในเครื่อง), ComfyUI (ภายในเครื่อง)

`n` จะส่งคืนภาพจำนวน `n` ภาพใน `data[]` ผู้ให้บริการที่ API ต้นทางส่งคืนภาพหนึ่งภาพต่อการเรียกหนึ่งครั้ง
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) จะมีการเรียกต้นทางแยกกัน `n` ครั้ง โดยมีการเรียกพร้อมกันได้สูงสุด 4 ครั้ง ค่า
`seed` คงที่จะถูกเพิ่มตามดัชนีการเรียก (`seed`, `seed + 1`, …) ดังนั้นภาพจะแตกต่างกันแต่ยังคงสร้างซ้ำได้
`n` จำกัดสูงสุดที่ 10 คำขอจะล้มเหลวทั้งหมดหากการเรียกครั้งใดครั้งหนึ่งล้มเหลว รายการรูปแบบที่ทำ fan-out อยู่ใน
`SINGLE_IMAGE_FANOUT_FORMATS` ที่
`open-sse/handlers/imageGeneration/fanOut.ts`

ZenMux ใช้การเชื่อมต่อคีย์ API ที่มีอยู่ซ้ำ และรองรับคำนำหน้า `zenmux/` หรือ `zm/`:

- `zenmux/openai/gpt-image-2` ใช้ OpenAI Images API ของ ZenMux ตัวเลือกต่าง ๆ ได้แก่ `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` และ `response_format`
- ผู้เผยแพร่รายอื่น เช่น `zm/meta/muse-image-1.0` ใช้ปลายทาง Vertex AI `:predict` ของ ZenMux `n` จะจับคู่กับ
  `sampleCount`, `aspect_ratio` กับ `aspectRatio` และ `image_size`
  (`1K`, `2K`, `4K`) กับ `sampleImageSize` ค่า `size` ในหน่วยพิกเซลจะระบุเพียงอัตราส่วนภาพ
  ไม่ได้รับประกันขนาดพิกเซล อัตราส่วนที่รองรับ ความละเอียด และจำนวนภาพจะแตกต่างกันไปตามโมเดล
- `zm/inclusionai/ming-image-0.1-design` จะเลือกขนาดของภาพเอง ให้ละเว้น `size`,
  `aspect_ratio` และ `image_size`; การระบุค่าเหล่านี้จะส่งคืน HTTP 400 สามารถขอรูปแบบ PNG, JPEG และ WebP
  ได้ด้วย `output_format`

การผสานการทำงานนี้รองรับการสร้างภาพจากข้อความ ไม่รองรับการแก้ไขภาพอ้างอิง ผลลัพธ์จาก Vertex
จะถูกปรับให้อยู่ในรูปแบบ `data[].b64_json`; `response_format: "url"` จะส่งคืน URL HTTPS จากต้นทาง
หรือ data URL แบบ base64 เมื่อมีเฉพาะไบต์ของภาพเท่านั้น ผลลัพธ์ที่ว่างเปล่า/ถูกกรองจะส่งคืนข้อผิดพลาด
แทนที่จะส่งคืนผลสำเร็จที่ว่างเปล่า การเข้าถึงโมเดลขึ้นอยู่กับบัญชี ZenMux ดูที่
[Vertex API ของ ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) และ
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)


## OCR เอกสาร

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` จะเลือกผู้ให้บริการ OCR ผ่านคำนำหน้า `provider/model`; รหัสโมเดลแบบไม่ระบุผู้ให้บริการ (เช่น
`mistral-ocr-latest`) จะจับคู่กับผู้ให้บริการที่ลงทะเบียนไว้ และหากละเว้น `model` จะใช้ค่าเริ่มต้นเป็น
Mistral (`mistral-ocr-latest`) ผู้ให้บริการที่ลงทะเบียนไว้ (`open-sse/config/ocrRegistry.ts`):

| รหัสผู้ให้บริการ              | รหัสโมเดล            | ค่า `model`                                                                     | หมายเหตุ                                                                                                                       |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (หรือ `mistral-ocr-latest` แบบไม่ระบุผู้ให้บริการ) | ทำงานแบบ synchronous — ส่งคืนการตอบกลับโดยตรงจากการเรียกต้นทางครั้งเดียว                                                       |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                                     | ต้นทางทำงานแบบ asynchronous (`analyze` + poll) — ดูรายละเอียดด้านล่าง                                                          |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                         | ทำงานแบบ synchronous ผ่านปลายทางพาร์ทเนอร์ `openapi/chat/completions` ของ Vertex AI — ดูรายละเอียดการยืนยันตัวตน/URL ด้านล่าง. |

ผู้ให้บริการทั้งสามรายจะตอบกลับด้วยเนื้อหาที่มีรูปแบบเดียวกับ Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### ขั้นตอนการโพลของ Azure Document Intelligence

API `analyze` ของ Azure Document Intelligence ทำงานแบบ asynchronous: คำขอเริ่มต้นจะส่งคืน
เฮดเดอร์ `Operation-Location` แทนเนื้อหา และต้องทำการโพลเพื่อรับผลลัพธ์ ตัวจัดการ
(`open-sse/handlers/ocr.ts`) จะโพล URL ดังกล่าวทุกวินาที โดยพยายามสูงสุด 30 ครั้ง หยุดทันที (ไม่
โพลต่อ) เมื่อการตอบกลับการโพลมีสถานะไม่ใช่ `ok` หรือมีสถานะ `"failed"` และส่งคืน `504` หากการดำเนินการยังคง
ทำงานอยู่หลังจากใช้จำนวนครั้งที่กำหนดครบแล้ว การตอบกลับสุดท้ายจาก Azure จะถูกปรับให้อยู่ในรูปแบบ
`pages`/`markdown` เดียวกับที่ Mistral ใช้ก่อนส่งคืนให้ผู้เรียก ดังนั้นโค้ดฝั่งไคลเอนต์จึงไม่จำเป็นต้อง
จัดการผู้ให้บริการเป็นกรณีพิเศษ

### การยืนยันตัวตนและการแก้ไขปลายทางของ Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` ใช้การยืนยันตัวตน Vertex AI แบบเดียวกับที่ OmniRoute รองรับอยู่แล้วสำหรับ
การรับส่งข้อมูลแชต/ภาพ (`open-sse/executors/vertex.ts`): คีย์ API ของการเชื่อมต่ออาจเป็นข้อมูลรับรอง
Service Account JSON (แลกเปลี่ยนเป็นโทเค็นการเข้าถึง OAuth อายุสั้นผ่านโฟลว์ JWT-bearer)
หรือเป็นโทเค็นการเข้าถึง OAuth ที่ออกให้แล้วและนำมาใช้โดยตรง URL ปลายทางต้นทางคือปลายทางพาร์ทเนอร์
ทั่วไป `openapi/chat/completions` ของ Vertex ซึ่งสร้างจากโปรเจกต์และภูมิภาคของการเชื่อมต่อ —
`providerSpecificData.project`/`providerSpecificData.region` ที่ระบุอย่างชัดเจนจะมีลำดับความสำคัญสูงสุดเสมอ;
มิฉะนั้นโปรเจกต์จะถูกอนุมานจาก `project_id` ใน Service Account JSON และภูมิภาคจะใช้ค่าเริ่มต้นเป็น
`us-central1` การแก้ไขทั้งสองอย่างเกิดขึ้นใน `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) และถูกใช้งานโดย
`src/app/api/v1/ocr/route.ts` ก่อนส่งต่อไปยัง `handleOcr`

### ราคาโมเดล (`pricing`)

รายการจะมีออบเจ็กต์ `pricing` เมื่อ OmniRoute ทราบราคาของโมเดล ราคาดังกล่าวมาจากตารางราคา
ที่ใช้สำหรับคำนวณค่าใช้จ่าย ได้แก่ ค่าเริ่มต้นในตัว, ราคาที่ซิงค์ และค่าที่เขียนทับผ่าน
`/api/pricing` ราคาเหล่านี้เป็นราคาตามรายการ ดังนั้นผู้ให้บริการแบบสมัครสมาชิกก็จะแสดงราคา
ต่อโทเค็นด้วย

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| ฟิลด์                                                           | หน่วย                      | หมายเหตุ                                                                                                                       |
| --------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD ต่อโทเค็น, สตริงทศนิยม | เข้ากันได้กับ OpenRouter และไม่ใช้รูปแบบเลขชี้กำลัง ฟิลด์แคชทั้งสองจะแสดงเฉพาะเมื่อมีราคาแคชเท่านั้น                           |
| `input`, `output`, `cached`, `cache_creation`                   | USD ต่อ 1M โทเค็น, ตัวเลข  | ฟิลด์จากแค็ตตาล็อกรุ่นก่อน ซึ่งเก็บไว้สำหรับไคลเอ็นต์เดิม `reasoning` และ `long_context` จะแสดงด้วยเมื่อแถวราคามีฟิลด์เหล่านี้ |

- **คอมโบ** จะใช้ราคาของเป้าหมายแรกที่มองเห็นได้ คอมโบ `auto/*` ในตัวจะเลือก
  เป้าหมายขณะส่งคำขอ จึงไม่มี `pricing`
- **โมเดลฟรี** จะแสดงค่า `"0"` (และ `0`) เมื่อราคาเป็นศูนย์ โมเดลที่ไม่มีแถวราคา
  จะแสดงค่า `"0"` เช่นกันเมื่อแค็ตตาล็อกระบุว่าเป็นโมเดลฟรี (`free: true`) หรือมีชื่ออยู่ใน
  แค็ตตาล็อกโมเดลฟรีในตัว
- **ไม่ทราบราคา:** รายการนั้นจะไม่มีคีย์ `pricing`
- **ผู้ให้บริการที่คิดค่าบริการตามเครดิต** (เช่น Kiro) จะเรียกเก็บค่าบริการต่อคำขอแทนที่จะคิดตามโทเค็น รายการของผู้ให้บริการเหล่านี้ยังคงมีฟิลด์ตัวเลขต่อ 1M ที่เคยมี และไม่มีฟิลด์สตริงต่อโทเค็น
- **รูปแบบย่อย** (ไอดีระดับความพยายามในการให้เหตุผล, ชื่อแทนที่ไม่ใช้การคิด, มิเรอร์สำหรับการค้นหาและเกตเวย์)
  จะคัดลอกราคาของโมเดลที่ส่งต่อไป
- ฟิลด์เหล่านี้แสดงเฉพาะอัตราพื้นฐาน ระดับบริบทขนาดยาว (ฟิลด์ตัวเลข `long_context`) และ
  ตัวคูณระดับบริการ (เช่น Codex fast หรือ flex) จะไม่เปลี่ยนแปลง `prompt` หรือ
  `completion`
- ออบเจ็กต์นี้เหมือนกันสำหรับรูปแบบการยืนยันตัวตนทุกแบบ รวมถึงคำขอรูปแบบ Anthropic
  ที่มี `x-api-key` และ `anthropic-version` (การตอบกลับยังคงเป็น `{ "object": "list",
"data": [...] }`) การนำไปใช้งาน: `src/app/api/v1/models/catalogPricing.ts`

### คำนำหน้าไอดีโมเดล (`?prefix=`)

โมเดลส่วนใหญ่จะแสดงภายใต้ **คำนำหน้าผู้ให้บริการ** คำนำหน้าที่ได้รับจะควบคุมโดย
แฟล็กฟีเจอร์ `MODELS_CATALOG_PREFIX_MODE` และสามารถเขียนทับ **ต่อคำขอ** ได้ด้วย
พารามิเตอร์ query ซึ่งมีประโยชน์สำหรับไคลเอ็นต์ที่ต้องการรายการแบบสะอาดโดยไม่เปลี่ยนแปลง
การตั้งค่าทั้งเซิร์ฟเวอร์สำหรับผู้ใช้อื่น:

```bash
GET /v1/models?prefix=alias        # หนึ่งไอดีต่อโมเดล — คำนำหน้าชื่อแทนแบบสั้น
GET /v1/models?prefix=dual         # ทั้งสองรูปแบบ (ค่าเริ่มต้นของเซิร์ฟเวอร์)
GET /v1/models?prefix=canonical    # เฉพาะคำนำหน้า provider-id แบบเต็ม
```

| โหมด        | สิ่งที่แสดง                                               | หมายเหตุ                                                                                                                                                                                |
| ----------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **และ** `claude/claude-sonnet-4-6` | **ค่าเริ่มต้น** ไอดีทั้งสองจะส่งต่อไปยังโมเดลเดียวกัน โดยเก็บไว้เพื่อให้การตั้งค่าไคลเอ็นต์ที่กำหนดรูปแบบใดรูปแบบหนึ่งไว้ตายตัว ยังคงทำงานได้ แค็ตตาล็อกจะมีขนาดเพิ่มขึ้นประมาณสองเท่า  |
| `alias`     | `cc/claude-sonnet-4-6`                                    | หนึ่งรายการต่อโมเดล ผู้ให้บริการที่ไม่มีชื่อแทนแยกต่างหากจะแสดงรายการของตนด้วย ดังนั้นจะไม่มีรายการใดสูญหาย                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                                | หนึ่งรายการต่อโมเดลภายใต้คำนำหน้า provider-id แบบเต็ม ผู้ให้บริการที่ไม่มีชื่อแทนแยกต่างหาก (เช่น `antigravity/…`, `agy/…`) จะแสดงไอดีเดียวของตนที่นี่ด้วย ดังนั้นจะไม่มีรายการใดสูญหาย |

นอกจากนี้ยังสามารถระบุมิเรอร์โหมด `dual` ได้โดยไม่ต้องใช้พารามิเตอร์ query โดยมิเรอร์นั้นจะมีฟิลด์
`parent` ที่ชี้ไปยังไอดีหลัก

ไคลเอ็นต์ที่แสดงตัวเลือกโมเดลควรส่งคำขอด้วย `?prefix=alias` — นี่คือสิ่งที่
[ส่วนขยาย OmniCopilot สำหรับ VS Code](../guides/VSCODE-COPILOT.md) ใช้

### ตัวกรองการค้นหา (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` รองรับตัวกรองการค้นหาแบบเลือกใช้ หากไม่ใช้ตัวกรองใด การตอบกลับจะไม่เปลี่ยนแปลง ตัวกรองเหล่านี้จะจำกัดแค็ตตาล็อกที่ผู้เรียกเห็นอยู่แล้ว (สิทธิ์ของ API key จะมีผลก่อน) และทำงานก่อนการแบ่งหน้าแบบ `limit` / `after` ของรูปแบบ OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ความสามารถทุกอย่างที่ระบุต้องเป็น true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` ของแค็ตตาล็อก; แถวที่ไม่มีค่าจะเป็น `chat`
GET /v1/models?q=sonnet&limit=10                           # ตรงกับ id หรือ name โดยไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่
```

| พารามิเตอร์   | ค่า                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | จำนวนเต็มที่ไม่เป็นลบ เปรียบเทียบกับ `context_length`                                               |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | อักขระ 1–200 ตัว                                                                                    |

ค่าที่ไม่รู้จัก หรือ `min_context` ที่ไม่ใช่จำนวนเต็มที่ไม่เป็นลบ (เช่น `1.5`)
จะส่งคืน HTTP `400` และข้อความจะแสดงค่าที่ถูกต้องทั้งหมด การใช้งานอยู่ที่:
`src/app/api/v1/models/catalogFilters.ts`.

### รายการโมเดลคัดสรร (`POST /v1/models/query`)

`POST /v1/models/query` จะส่งคืนรายการสั้น ๆ ที่กำหนดผลลัพธ์ได้จากแค็ตตาล็อกเดียวกัน
โดยใช้การยืนยันตัวตนและการมองเห็นตามคีย์เดียวกันกับ `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ทุกฟิลด์เป็นตัวเลือก `capabilities` และ `exclude` รับอาร์เรย์หรือสตริงที่คั่นด้วยจุลภาค
`max_output` จะเปรียบเทียบกับ `max_output_tokens` ผลลัพธ์จะเรียงตาม `owned_by` แล้วจึงตาม `id`
ค่าเริ่มต้นของ `limit` คือ `20` และค่าที่มากกว่า `100` จะถูกจำกัดไว้ที่ `100` JSON ที่ไม่ถูกต้อง
ฟิลด์ที่ไม่รู้จัก หรือค่าที่ไม่ถูกต้อง จะส่งคืน HTTP `400`

### โมเดลแชตที่ซ่อนเป็นรายโมเดล

โมเดลที่ทำเครื่องหมายว่า **ซ่อน** ในหน้าผู้ให้บริการจะไม่รวมอยู่ในแค็ตตาล็อก และจะถูกปฏิเสธ
ด้วย HTTP `404` / `model_not_found` เมื่อมีการร้องขออย่างชัดเจน การตรวจสอบจะใช้ผู้ให้บริการ
และโมเดลที่แก้ไขได้แล้ว รวมถึงชื่อแทนของผู้ให้บริการ คำนำหน้าโหนดของผู้ให้บริการที่เข้ากันได้
และค่าเริ่มต้นของการเชื่อมต่อ คอมโบจะข้ามเป้าหมายที่ซ่อนอยู่และสามารถใช้พี่น้องที่มองเห็นได้
หากไม่มีเป้าหมายที่สามารถดำเนินการได้เหลืออยู่ จะส่งคืนรหัสข้อผิดพลาดเดียวกัน การยกเลิกการซ่อน
จะมีผลในคำขอถัดไป การกำหนดการมองเห็นเฉพาะรูปภาพจะไม่ซ่อนโมเดลแชตที่มี ID เดียวกัน

การตั้งค่าโมเดลรายโมเดลนี้แยกจาก
[รายการอนุญาต/ปฏิเสธการเปิดเผยโมเดล](../routing/MODEL_EXPOSURE_LIST.md) ซึ่งใช้กรอง
การประกาศในแค็ตตาล็อกและตัวเลือกสำหรับการกำหนดเส้นทางอัตโนมัติ โดยยังคงรองรับการส่งงานที่ระบุ
อย่างชัดเจน สิทธิ์ของโมเดลตามคีย์ API ยังคงมีผลแยกจากกัน โหมดคำนำหน้าแค็ตตาล็อกเริ่มต้นยังคงเป็น
`dual`

### รุ่นโมเดลที่ไม่ใช้การคิด

สำหรับโมเดล Claude ที่รองรับการคิด `/v1/models` จะแสดงรุ่น **ไม่ใช้การคิด** เพิ่มเติมด้วย โดยมี id
ขึ้นต้นด้วย `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

การเลือก id นี้ (เช่น ในการกำหนดค่า Claude Code ที่แนบ `thinking` block เสมอ)
จะย้อนกลับไปแก้ไขเป็น `<provider>/<model>` จริง โดยระงับการให้เหตุผล — `thinking:{type:"disabled"}`
บนเส้นทาง `/v1/messages` หรือทิ้งฟิลด์ `reasoning`/`reasoning_effort` บนเส้นทาง
`/v1/chat/completions` รุ่นนี้จะแสดงเฉพาะสำหรับโมเดลตระกูล Claude ที่รองรับการคิด **และ** ยอมรับ
`disabled` เท่านั้น (ดังนั้นโมเดลที่รองรับเฉพาะแบบปรับตามบริบท ซึ่งปฏิเสธ `disabled` จะไม่รวมอยู่ด้วย)
ผู้ดูแลระบบสามารถบังคับเปิดหรือปิดรุ่นนี้แยกตามโมเดลได้ผ่าน `ModelSpec.noThinkingAlias`

## การสร้างเสียง ElevenLabs

กำหนดค่าการเชื่อมต่อผู้ให้บริการ `elevenlabs` ใน OmniRoute ด้วยคีย์ API ของ ElevenLabs
ไคลเอ็นต์จะยืนยันตัวตนด้วยคีย์ **OmniRoute** ของคุณ (`Authorization: Bearer $OMNIROUTE_API_KEY`);
เกตเวย์จะส่งคีย์ผู้ให้บริการที่จัดเก็บไว้เป็น `xi-api-key` อย่าส่งคีย์ ElevenLabs
เป็นโทเค็น bearer ของเกตเวย์

| วิธีการ | เส้นทาง                     | การตอบกลับ                                    | หมวดหมู่ endpoint ของ API key |
| ------- | --------------------------- | --------------------------------------------- | ----------------------------- |
| POST    | `/v1/sound-generation`      | ไบต์เสียงแบบ Native                           | `elevenlabs`                  |
| POST    | `/v1/music`                 | ไบต์เสียงแบบ Native                           | `music`                       |
| POST    | `/v1/music/stream`          | ไบต์เสียงแบบสตรีม                             | `music`                       |
| POST    | `/v1/music/detailed`        | เสียง multipart และแผนการเรียบเรียงแบบ Native | `music`                       |
| POST    | `/v1/music/detailed/stream` | ข้อมูลเมทาดาทา SSE และชิ้นส่วนเสียงแบบ Native | `music`                       |
| POST    | `/v1/music/plan`            | แผนการเรียบเรียงในรูปแบบ JSON                 | `music`                       |

Endpoint เหล่านี้ทำงานเสริมกับเส้นทาง `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` และ `/v1/speech-to-text` ที่มีอยู่เดิม ฟิลด์ JSON
และพารามิเตอร์ query แบบ Native เช่น `output_format` และ `enable_logging` จะถูกรักษาไว้
การตอบกลับจาก `/v1/music/detailed` จะคงขอบเขต multipart ไว้ ให้แยกวิเคราะห์เป็น multipart
`/v1/music/detailed/stream` จะส่ง `text/event-stream` พร้อมเมทาดาทาการเรียบเรียงและ
ชิ้นส่วนเสียงแบบ base64 ในอีเวนต์ SSE ทั้งหกเส้นทางรองรับ CORS preflight

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# เอฟเฟกต์เสียงสั้น ๆ ระยะเวลา: 0.5 ถึง 30 วินาที
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# ระยะเวลาของเพลงระบุเป็นมิลลิวินาที: 3000 ถึง 600000
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ใช้ `/v1/music/stream` พร้อม body JSON เดียวกันเพื่อส่งมอบเสียงแบบต่อเนื่อง
การเรียบเรียงรับค่าอย่างใดอย่างหนึ่งจาก `prompt` หรือ `composition_plan` เท่านั้น ส่วน `/v1/music/plan`
ต้องมี `prompt` และอาจรับ `source_composition_plan` ได้ สคีมาแบบ Native
จะรักษาฟิลด์เพิ่มเติมของผู้ให้บริการไว้ เพื่อให้เวอร์ชันของแผนการเรียบเรียงและตัวเลือกการปรับแต่งละเอียด
ถูกส่งต่อไปยัง ElevenLabs

Endpoint แบบรวม `/v1/music/generations` ยังรองรับ
`elevenlabs/music_v1`, `elevenlabs/music_v2` และ `elevenlabs/music_v2_5` ด้วย เมื่อมีการเชื่อมต่อ ElevenLabs
ที่ใช้งานอยู่ โมเดลเหล่านี้จะแสดงในแค็ตตาล็อกเพลง Endpoint นี้ส่งคืนค่าในรูปแบบ
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ฟิลด์ `duration` ของ endpoint นี้มีหน่วยเป็น
วินาทีและจับคู่กับ `music_length_ms`; หากระบุ `music_length_ms` อย่างชัดเจน ค่านั้นจะมีลำดับความสำคัญสูงกว่า
`instrumental` จะจับคู่กับ `force_instrumental` โดยฟิลด์แบบ Native จะมีลำดับความสำคัญสูงกว่า
ใช้ endpoint การสตรีมแบบ Native สำหรับการสตรีม และใช้ endpoint การเรียบเรียงแบบ Native
สำหรับคำขอที่ขับเคลื่อนด้วยแผนการเรียบเรียงเพียงอย่างเดียว

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

ข้อจำกัดด้าน endpoint, โมเดล, งบประมาณ และการเชื่อมต่อจะถูกบังคับใช้ก่อนการเรียก upstream เส้นทางแบบ Native
จะส่งคืนรหัสสถานะและ body ข้อผิดพลาดจาก upstream โดยไม่เปลี่ยนแปลง รวมถึง `402` สำหรับข้อจำกัดของแผน
และ `429` สำหรับขีดจำกัดโควตา ส่วนหัว `character-cost`, `song-id`, `request-id` และ `retry-after`
จะถูกรักษาไว้เมื่อมีอยู่ ยอดเครดิตฟรีไม่ได้รับประกันว่าจะเข้าถึงโมเดลเพลง รูปแบบเอาต์พุต หรือฟีเจอร์ API
ได้ทุกอย่าง โดย ElevenLabs จะเป็นผู้ตัดสินสิทธิ์สำหรับแต่ละคำขอ
Endpoint แบบรวมจะรักษารหัสสถานะข้อผิดพลาดไว้ในซองข้อผิดพลาดที่ทำให้เป็นมาตรฐานของ OmniRoute

สัญญา upstream: [เอฟเฟกต์เสียง](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[การเรียบเรียงเพลง](https://elevenlabs.io/docs/api-reference/music/compose) และ
[รายละเอียดการสตรีมเพลง](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)

สำหรับไคลเอ็นต์ที่ไม่สามารถแนบ `Authorization: Bearer ...` ได้ OmniRoute ยังรองรับคีย์ API ใน URL ผ่าน query-string ที่เข้ากันได้ (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) หรือผ่านเอนด์พอยต์เฉพาะ `/api/v1/vscode/{token}/...` ที่ระบุไว้ด้านล่าง

```bash
# จัดอันดับใหม่ (ผู้ให้บริการจากคลาวด์รีจิสทรี หรือโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI ในรูปแบบ "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina classify (ข้อมูลรับรอง Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina segmenter
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina search (s.jina.ai; นามแฝงผู้ให้บริการ: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# การกลั่นกรอง
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — ส่งคืนเนื้อหา audio/mpeg (หรือรูปแบบที่ร้องขอ)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS ต้องระบุภาษาและเสียง: `language` มีค่าเริ่มต้นเป็น "en"; หากไม่ระบุ
# เสียง หรือใช้ชื่อเสียงมาตรฐานของ OpenAI (alloy, nova, …) ระบบจะใช้ "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# การแก้ไขรูปภาพ (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# การสร้างวิดีโอ / เพลง (รหัสโมเดลที่มีคำนำหน้าผู้ให้บริการ)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **โหนดผู้ให้บริการ Rerank:** `POST /v1/rerank` จะกำหนดเส้นทางไปยังโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI
> (oMLX, vLLM, Infinity, TEI ที่อยู่หลังเกตเวย์, …) ด้วยรูปแบบ `<node-prefix>/<model>` เช่นกัน โหนดแบบลูปแบ็ก
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) จะมีสิทธิ์ใช้งานได้เสมอ เช่นเดียวกับชื่อโฮสต์ที่ผู้ดูแลระบบระบุไว้ใน
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (เช่น ชื่อบริการ Docker/Compose อย่าง
> `http://reranker:8080/v1`; โหนดเหล่านี้จะถูกเรียกโดยตรง ไม่ผ่าน `HTTP(S)_PROXY` หรือพร็อกซีที่ผูกไว้กับ
> การเชื่อมต่อ) โหนดบนโฮสต์อื่น — ไม่ว่าจะเป็นเครื่องใน LAN หรือเพียร์ Tailscale — จะมีสิทธิ์ใช้งานได้ก็ต่อเมื่อผู้ดูแลระบบเปิดใช้
> แฟล็กฟีเจอร์ `RERANK_REMOTE_PROVIDER_NODES` **และ** URL พื้นฐานของโหนดผ่านนโยบาย URL ขาออกของผู้ให้บริการ
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)
> ขั้นตอน rerank ของเอนจินหน่วยความจำจะเรียกเส้นทางนี้ผ่านลูปแบ็ก ดังนั้นกฎเดียวกันนี้จึงใช้ควบคุม
> `rerankProviderModel` ในการตั้งค่า Memory ด้วย
>
> **รูปแบบเซิร์ฟเวอร์ภายในเครื่อง:** ระบบจะเรียกโหนดที่ `<base>/v1/rerank` และเมื่อได้ 404 จะเรียกที่ `<base>/rerank`
> (Infinity, TEI) บอดีต้นทางจะมีทั้งรูปแบบการสะกดของ Cohere/OpenAI (`documents`,
> `return_documents`) และรูปแบบการสะกดของ TEI (`texts`, `return_text`) และการตอบกลับจากต้นทางจะถูก
> ทำให้เป็นมาตรฐานตามเอนเวโลปของ Cohere: อาร์เรย์เปล่าของ TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> จากเกตเวย์แบบบาง และ `{data: [...]}` ในรูปแบบ Voyage จะถูกส่งกลับไปยังไคลเอ็นต์เป็น
> `{results: [{index, relevance_score, document?}]}` โดยเรียงตามคะแนนและจำกัดจำนวนไว้ที่ `top_n`

> **การค้นพบโหนดผู้ให้บริการ:** โมเดลบนโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI จะปรากฏใน `GET /v1/models`
> ภายใต้คำนำหน้าโหนด แถวข้อมูลที่ไม่มีข้อมูลเมทาดาทาของปลายทาง (โดยทั่วไปมักพบในรายการ `/v1/models` ภายในเครื่อง)
> จะสืบทอดค่า `apiType` ของโหนด ดังนั้นโมเดลของโหนด `embeddings` จะมีค่า `type: "embedding"` และโมเดลของโหนด
> `rerank` จะมีค่า `type: "rerank"` แทนที่จะใช้ค่าเริ่มต้นเป็น chat; ค่า `supportedEndpoints` ที่ระบุอย่างชัดเจน
> ในแถวข้อมูลที่ซิงค์หรือเพิ่มด้วยตนเองจะยังมีลำดับความสำคัญสูงกว่า

## Files API

เอนด์พอยต์ไฟล์ที่เข้ากันได้กับ OpenAI สำหรับอินพุต/เอาต์พุตแบบแบตช์และการอัปโหลดไฟล์ตามวัตถุประสงค์

| Method | Path                     | Description                                                                                                    |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | อัปโหลดไฟล์ (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — สูงสุด 512 MiB |
| GET    | `/v1/files`              | แสดงรายการไฟล์สำหรับคีย์ API ที่ผ่านการยืนยันตัวตน                                                             |
| GET    | `/v1/files/[id]`         | ดึงข้อมูลเมตาของไฟล์                                                                                           |
| DELETE | `/v1/files/[id]`         | ลบไฟล์                                                                                                         |
| GET    | `/v1/files/[id]/content` | สตรีมเนื้อหาไฟล์ดิบกลับไป                                                                                      |

**การยืนยันตัวตน:** คีย์ API แบบ Bearer — ไฟล์จะถูกกำหนดขอบเขตต่อคีย์ API ผ่าน `getApiKeyRequestScope` คีย์หนึ่งจะ
เห็น ดาวน์โหลด และลบได้เฉพาะไฟล์ของตนเองเท่านั้น ส่วนเซสชันแดชบอร์ดที่ไม่มีคีย์จะอ่านได้ทั้งอินสแตนซ์ ไฟล์ที่ไม่มีเจ้าของ
(อัปโหลดแบบไม่ระบุชื่อหรืออัปโหลดจากเซสชันแดชบอร์ด) จะถูกปฏิเสธสำหรับผู้เรียกที่ไม่ใช่เซสชันทุกราย `GET /v1/files` จะปฏิเสธผู้เรียกแบบไม่ระบุชื่อ — และคีย์ที่ส่งมาแต่ไม่สามารถระบุได้ —
ด้วย `401` แม้ว่า `REQUIRE_API_KEY=false` แทนที่จะแสดงรายการไฟล์ของทุกเทนแนนต์ (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)

## Batches API

การประมวลผลแบบแบตช์ที่เข้ากันได้กับ OpenAI

| Method | Path                      | Description                                                                                                          |
| ------ | ------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | สร้างแบตช์ — เนื้อหาคำขอได้รับการตรวจสอบโดย `v1BatchCreateSchema` (`input_file_id`, `endpoint`, `completion_window`) |
| GET    | `/v1/batches`             | แสดงรายการแบตช์                                                                                                      |
| GET    | `/v1/batches/[id]`        | ดึงสถานะแบตช์และ `request_counts`                                                                                    |
| DELETE | `/v1/batches/[id]`        | ลบแบตช์ที่เสร็จสิ้น/ล้มเหลว                                                                                          |
| POST   | `/v1/batches/[id]/cancel` | ยกเลิกแบตช์ที่กำลังดำเนินการ                                                                                         |

**การยืนยันตัวตน:** คีย์ API แบบ Bearer แบตช์จะถูกกำหนดขอบเขตต่อคีย์ API ภายใต้กฎสามทางเดียวกับ
ไฟล์: ใช้ได้เฉพาะคีย์ของตนเอง เซสชันแดชบอร์ดใช้งานได้ทั้งอินสแตนซ์ ระเบียนที่ไม่มีเจ้าของจะถูกปฏิเสธสำหรับผู้เรียกที่ไม่ใช่เซสชันทุกราย
(การดึงข้อมูล การลบ การยกเลิก และการตรวจสอบ `input_file_id` ขณะสร้าง) `GET /v1/batches` จะปฏิเสธผู้เรียกแบบไม่ระบุชื่อด้วย `401` แม้ว่า `REQUIRE_API_KEY=false`

## API การค้นหา

ชั้นนามธรรมของผู้ให้บริการเว็บ/การค้นหา (Tavily, Brave, Exa, Serper และอื่น ๆ)

| Method | Path                   | Description                                                                       |
| ------ | ---------------------- | --------------------------------------------------------------------------------- |
| GET    | `/v1/search`           | แสดงรายการผู้ให้บริการการค้นหาที่กำหนดค่าไว้พร้อมความสามารถ                       |
| POST   | `/v1/search`           | เรียกใช้คำค้นหา — เนื้อหาจะถูกตรวจสอบโดย `v1SearchSchema` และรองรับการแคช/รวมคำขอ |
| GET    | `/v1/search/analytics` | สถิติผลลัพธ์/เวลาแฝง/แคชแยกตามผู้ให้บริการ                                        |

**การยืนยันตัวตน:** คีย์ API แบบ Bearer (`extractApiKey` + `isValidApiKey`) นโยบายการค้นหาจะถูกบังคับใช้ผ่าน `enforceApiKeyPolicy`

### `provider_options` ของ Exa และ Tavily

Exa และ Tavily อ่านฟิลด์เฉพาะผู้ให้บริการจากออบเจ็กต์แบบมี namespace:
`provider_options.exa` (หรือ `provider_options["exa-search"]`) และ `provider_options.tavily`
(หรือ `provider_options["tavily-search"]`) ระบบจะส่งต่อเฉพาะคีย์ด้านล่าง แต่ละคีย์จะถูก
ตรวจสอบกับ Zod schema ของตนเองใน `open-sse/handlers/search/providerOptionsPassthrough.ts`
และคีย์ที่มีชนิดข้อมูลไม่ถูกต้องจะถูกตัดออก คีย์อื่น ๆ ทั้งหมดจะถูกละเว้น รวมถึง auth, base URL,
`stream` และ `outputSchema` คีย์แบบแบนที่ผู้ให้บริการรายอื่นใช้ (`cx`, `depth`, ...) ยังคง
ทำงานเหมือนเดิม

| Provider | Top-level fields                                                                                                                                                                                                                                                                                                                                                          | Nested                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |

ค่าใช้จ่ายการค้นหาของ Firecrawl จะถูกบันทึกตามบล็อกละ 10 ผลลัพธ์ที่เริ่มต้น โดยคิดราคา $0.002 (2

`startPublishedDate` (ประทับเวลา ISO) และ Tavily จะได้รับ `start_date` (`YYYY-MM-DD`)

`deep` ([ราคา Linkup](https://docs.linkup.so/pages/documentation/development/pricing))

`contents` ยกเว้น `text` และ `highlights` จะถูกตัดออกก่อนการเรียกใช้ `subpages`,
`subpageTarget`, `highlights.numSentences` และ `highlights.highlightsPerUrl` ที่เลิกใช้แล้วจะไม่ถูก
ส่งต่ออีกต่อไป

Exa: 0.007 ดอลลาร์ต่อการเรียก `auto` (และ `fast` แบบเดิม) หรือ 0.004 ดอลลาร์สำหรับ `lite` (และ `instant` แบบเดิม) ครอบคลุม 10 ผลลัพธ์ $0.001 สำหรับผลลัพธ์เพิ่มเติมแต่ละรายการ และ 0.001 ดอลลาร์ต่อผลลัพธ์ที่ส่งคืนเมื่อตั้งค่า `contents.summary` Tavily ได้รับการบันทึกที่ 1 เครดิต ($0.008) สำหรับ `search_depth` `basic`, `fast` และ `ultra-fast` และ 2 เครดิต ($0.016) สำหรับ `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) ) การโทรด้วย `auto_parameters: true` ที่ Tavily อัปเกรดเป็นขั้นสูงจะยังคงบันทึกไว้ที่ 1 เครดิต

## Web Fetch API

แยกเนื้อหาจาก URL ผ่านผู้ให้บริการ web-fetch ที่กำหนดค่าไว้ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)

Parallel Extract (`parallel-search` ใช้ API key เดียวกับ Parallel Search) ส่งคืนเฉพาะ Markdown — `format`
อื่นใดจะส่งผลให้เกิด `400` — และจำกัดเนื้อหาไว้ที่ 100,000 อักขระ เมื่อไม่สามารถแยกหน้าเป้าหมายได้ ตัว upstream จะแจ้งข้อมูลดังกล่าวภายใน HTTP 200;
OmniRoute จะแสดงผลเป็น `422` พร้อมข้อความคงที่

| Method | Path            | Description                                                                |
| ------ | --------------- | -------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | ดึงข้อมูล/ขูดข้อมูลจาก URL — body ตรวจสอบความถูกต้องโดย `v1WebFetchSchema` |

**Auth:** Bearer API key (`extractApiKey` + `isValidApiKey`) นโยบายจะถูกบังคับใช้ผ่าน `enforceApiKeyPolicy`

**การสำรองข้อมูลที่คำนึงถึงโควตา (#8297):** เมื่อไม่ได้ระบุ `provider` อย่างชัดเจน ระบบจะไล่ตรวจ pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ตามลำดับความสำคัญที่กำหนดตายตัว (fill-first) — provider ที่มีการจำกัดอัตราแต่กำหนดค่าไว้แล้วจะถูกข้าม
แทนที่จะทำให้คำขอหยุดทำงาน และความล้มเหลวจาก upstream ที่สามารถลองใหม่ได้/เกี่ยวกับโควตา (HTTP 429 เสมอ; 402/403 สำหรับโควตารูปแบบ free tier ของ Firecrawl/Tavily/TinyFish —
ไม่รวม Jina Reader และไม่รวมคำขอ 400 ที่ไม่ถูกต้องทั่วไป) จะส่งต่อไปยัง credentialed provider ถัดไปที่ยังไม่ได้ลอง ณ เวลาที่ร้องขอ เมื่อ provider ทุกตัวใน pool ใช้งานโควตาจนหมด endpoint จะส่งคืน `429` รายการเดียว (พร้อมส่วนหัว `Retry-After`) แทน `400` ทั่วไปแบบเดิม เมื่อมีการร้องขอ `provider` อย่างชัดเจน จะ **ไม่มี** fallback แบบเงียบ — provider ที่ถูกจำกัดอัตราหรือล้มเหลวจะแสดงข้อผิดพลาดของตนเอง (`429` หากถูกจำกัดอัตรา มิฉะนั้นเป็นสถานะจาก upstream)

## การสตรีม WebSocket

```bash
GET /v1/ws?handshake=1
```

ตรวจสอบ handshake สำหรับการอัปเกรด WebSocket และส่งคืนข้อความตัวอย่างของ wire protocol (`request`, `cancel`) เฟรม WS จริงจะได้รับการจัดการโดย WS server ที่มาพร้อมชุดระบบภายนอกตารางเส้นทางของ Next.js

**Auth:** Bearer API key ระหว่าง handshake

### Responses API ผ่าน WebSocket (เฉพาะ codex)

```bash
# โฮสต์:พอร์ตเดียวกับ HTTP API (ค่าเริ่มต้น 20128); อัปเกรดการเชื่อมต่อ:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (หรือ: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# เฟรมแรก MUST be response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

พร็อกซี Responses-API-over-WebSocket เชื่อมต่อไว้ **เฉพาะกับ `codex`** (แบ็กเอนด์ ChatGPT) โดยรับฟังที่พอร์ตเดียวกับ API/dashboard ที่เส้นทาง `/v1/responses`,
`/responses` และ `/api/v1/responses` เมื่อได้รับเฟรม `response.create` แรก ระบบจะยืนยันตัวตน + เตรียมการผ่านบริดจ์ภายใน `codex-responses-ws` เลือกการเชื่อมต่อ OAuth ของ codex และทำ tunnel ไปยัง
`wss://chatgpt.com/backend-api/codex/responses` ผ่านทรานสปอร์ต `wreq-js` โมเดลที่ไม่ใช่ codex จะถูกปฏิเสธ (`codex_ws_provider_required`)
สำหรับการกำหนดเส้นทางแบบ quota-share ให้ใช้ `model: "qtSd/<group>/codex/<model>"` มีการใช้งานอยู่ใน
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`

**Auth:** Bearer API key ระหว่าง handshake bundled HTTP server (`server-ws.mjs`)
ต้องเป็น entrypoint ที่ใช้งานอยู่ (โดยค่าเริ่มต้นจะเป็นเช่นนั้นเมื่อมี `app/server-ws.mjs`)

#### Model id: ใช้ ChatGPT id แบบไม่มีคำนำหน้า (ไม่มีคำนำหน้า `codex/`)

**Codex CLI** ของ OpenAI จะตรวจสอบชื่อโมเดลฝั่งไคลเอ็นต์เมื่อ
`supports_websockets = true` และปฏิเสธ id ที่มี provider นำหน้า เช่น
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`) ให้ส่ง id แบบไม่มีคำนำหน้า (เช่น `gpt-5.5`) บริดจ์ของ OmniRoute ใช้ได้เฉพาะ codex จึงจะ resolve id แบบไม่มีคำนำหน้าใหม่เป็นโมเดล codex
(`resolveCodexWsModelInfo`) ก่อนทำ tunnel ไปยัง upstream — แม้ว่า `gpt-5.5` แบบไม่มีคำนำหน้าจะถูกกำหนดเส้นทางไปยัง provider อื่นผ่าน HTTP

#### การกำหนดค่า OpenAI Codex CLI

ชี้ Codex CLI ไปยัง OmniRoute โดยเพิ่ม custom provider ที่รองรับ WebSocket
ลงใน `~/.codex/config.toml` (ใช้ `CODEX_HOME` แยกต่างหากเพื่อหลีกเลี่ยงการแก้ไข config ที่มีอยู่):

```toml
model = "gpt-5.5"                 # id แบบไม่มีคำนำหน้า — ไม่ใช่ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ไม่มี slash ต่อท้าย; URL ของ WS จะถูกสร้างขึ้นจากค่านี้ (ใช้ https/wss ใน production)
wire_api = "responses"                    # ค่าที่รองรับเพียงค่าเดียวตั้งแต่ Feb 2026
supports_websockets = true                # เปิดใช้งานทรานสปอร์ต Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # เก็บ OmniRoute API key (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key (ใช้ key ใดก็ได้หาก REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI จะอัปเกรด `base_url + /responses` เป็น WebSocket และ OmniRoute จะทำ tunnel ไปยังการเชื่อมต่อ OAuth ของ codex ที่เลือกไว้ มีการตรวจสอบการทำงานตั้งแต่ต้นจนจบกับเซิร์ฟเวอร์ภายในเครื่อง: ChatGPT ส่งคืน `codex.rate_limits` + `response.created` และสตรีมผลลัพธ์ที่เสร็จสมบูรณ์

### การกู้คืนเซสชันโควตา (เลือกเปิดใช้)

`POST /v1/chat/completions` หรือ `POST /v1/responses` แบบไม่สตรีมที่ล้มเหลวด้วยข้อผิดพลาดโควตาขั้นสุดท้าย (`402`/`429`/`503` ซึ่ง body ระบุว่าโควตาหรือเครดิตหมดแล้ว) สามารถพักคำขอและเล่นซ้ำภายหลังแทนการส่งคืนข้อผิดพลาดได้ ผู้เรียกใช้เลือกเปิดใช้ต่อคำขอด้วยส่วนหัวสามรายการต่อไปนี้:

| Header                       | Value                                           |
| ---------------------------- | ----------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                          |
| `x-omniroute-session`        | session id, `[A-Za-z0-9._:-]{1,128}`            |
| `x-omniroute-recovery-turn`  | turn id ที่ไม่ซ้ำกันภายในเซสชัน (ใช้กฎเดียวกัน) |

เฉพาะ turn ที่มี `stream: false` ซึ่งไม่มี tools, ประวัติ tool หรือ `previous_response_id` และไม่มีการ pin `x-omniroute-connection` เท่านั้นที่มีสิทธิ์ใช้ได้ และต้องตั้งค่า `STORAGE_ENCRYPTION_KEY` ไว้ (คำขอจะถูกจัดเก็บแบบเข้ารหัสเป็นเวลาสูงสุด 24 ชั่วโมง) จากนั้น response จะเป็น `202` พร้อม `recovery.poll`; poll ด้วย `GET /v1/quota-recoveries/{id}` (`202` ขณะรอดำเนินการ, `200` พร้อม body ที่กู้คืนเมื่อเสร็จสิ้น) หรือยกเลิกด้วย `DELETE` ตั๋วจะแสดงเฉพาะ API key ที่สร้างตั๋วนั้นเท่านั้น การเล่นซ้ำที่ไม่สามารถยืนยันผลลัพธ์ได้จะสิ้นสุดที่ `needs_confirmation` แทนที่จะถูกส่งซ้ำสองครั้ง แหล่งที่มา: `src/lib/quota/quotaSessionRecovery.ts`.

## การใช้งานแบบบริการตนเอง (`/api/usage/om-usage`)

API key ใด ๆ สามารถอ่านการใช้งานและโควตาของ **ตนเอง** ได้ — ไม่ต้องใช้การตรวจสอบสิทธิ์การจัดการ นี่คือ endpoint ที่ไคลเอ็นต์ (CLI, แผง OmniCopilot) ใช้เพื่อแสดงค่าใช้จ่ายของคีย์ให้เจ้าของคีย์ทราบ

```bash
# รูปแบบข้อความ (สัญญาเดิม — ข้อความธรรมดาสำหรับเทอร์มินัล)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# รูปแบบมีโครงสร้าง — สิ่งที่ UI ใช้งาน
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

คีย์ต้องเปิดใช้ **`allowUsageCommand`** (ปิดไว้โดยค่าเริ่มต้น — ตัวจัดการ API key ของแดชบอร์ดใช้สลับค่านี้แยกตามคีย์) หากไม่ได้เปิดใช้ endpoint จะตอบกลับ `403`

`?format=json` ส่งคืนโครงสร้างที่จำแนกประเภท เพื่อให้ผู้เรียกไม่ต้องอ่านฟิลด์ข้อมูลจากการปฏิเสธ เมื่อสำเร็จ:

```jsonc
{
  "allowed": true,
  // มีเฉพาะเมื่อคีย์เลือกใช้ขีดจำกัดการใช้งานต่อคีย์ (USD รายวัน/รายสัปดาห์):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // snapshot โควตาของ provider ที่เลือก หรือเป็น null เมื่อยังไม่มีสิ่งใดถูกแคช:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // snapshot ของทุก connection เพื่อให้ UI แสดง provider หลายรายการเคียงข้างกันได้:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

เมื่อถูกปฏิเสธ (คีย์ไม่ถูกต้อง `401` / ไม่ได้รับอนุญาต `403`) route เดียวกันนี้จะส่งคืน
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` ที่มีอยู่แต่เป็นค่าว่าง
(คีย์ได้รับอนุญาต แต่ยังไม่มีข้อมูล) เป็นสถานะที่แตกต่างจากการปฏิเสธ และมีเพียงรูปแบบ JSON
เท่านั้นที่แยกแยะสถานะเหล่านี้ได้

**Auth:** Bearer API key ของผู้เรียกเอง ซึ่งตรวจสอบด้วย `isValidApiKey` — นี่ไม่ใช่
management surface (`/api/keys/…`) ซึ่งยังคงอยู่ภายใต้ `requireManagementAuth`

### เปอร์เซ็นต์โควตาดิบเทียบกับเปอร์เซ็นต์ที่ปรับตามจุดตัด

เมื่อใช้งาน `/api/usage/om-usage` ผู้เรียกควรทราบความแตกต่างระหว่างเปอร์เซ็นต์ที่แสดงโดย
**เอาต์พุตข้อความธรรมดา** และ **เอาต์พุต JSON แบบมีโครงสร้าง**:

| Aspect               | Plain-text format (`/api/usage/om-usage` / `@@om-usage`)                                         | JSON format (`?format=json`)                                                     |
| :------------------- | :----------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------- |
| **Output field**     | `NN% left` (เช่น `20% left`)                                                                     | `provider.quotas` / `providers[].quotas`                                         |
| **Measurement**      | **สิทธิ์การใช้งานที่เหลือซึ่งปรับตามจุดตัด**: ความจุที่เหลือเหนือเกณฑ์จุดตัด                     | **โควตาดิบจาก upstream**: การวัดของ provider ที่ยังไม่ได้ปรับ                    |
| **Cutoff scaling**   | ปรับสเกลผ่าน `effectiveRemainingPercent()` เพื่อให้ส่วนสำรองที่ได้รับการปกป้องแสดงเป็น `0% left` | ไม่มี (ค่า snapshot ดิบตามที่ provider รายงาน)                                   |
| **Threshold data**   | รวมอยู่ในเปอร์เซ็นต์ที่แสดง                                                                      | จัดเก็บใน `quotaWindowThresholds` ต่อ connection (หรือค่าเริ่มต้นของเซิร์ฟเวอร์) |
| **Primary consumer** | CLI แบบโต้ตอบ, พรอมต์เทอร์มินัล, ผู้ปฏิบัติงานที่เป็นมนุษย์                                      | การผสานรวมแบบโปรแกรม, แดชบอร์ด, การวิเคราะห์, ตัวติดตามการเรียกเก็บเงิน          |

#### สูตรการปรับตามจุดตัด

OmniRoute รองรับจุดตัดโควตาเชิงรุกเพื่อป้องกันโควตาจาก upstream หมด (กำหนดค่าผ่าน connection
`quotaWindowThresholds`, ค่าเริ่มต้นของ provider หรือการตั้งค่าความยืดหยุ่นทั่วโลก) เมื่อมีเกณฑ์จุดตัด
(เช่น `cutoff = 25%`) ที่ใช้งานอยู่บนช่วงเวลาโควตา ตัวแสดงผลข้อความจะคำนวณสิทธิ์ที่เหลือดังนี้:

- หาก `remaining <= cutoff`: ส่งคืน `0%`
- หาก `remaining > cutoff`: ส่งคืน `((remaining - cutoff) / (100 - cutoff)) * 100`

เอาต์พุตข้อความที่จัดรูปแบบจะปัดเศษเป็นจำนวนเต็มที่ใกล้ที่สุด (`Math.round(...)`)

#### ตัวอย่างประกอบ

พิจารณาหน้าต่างของผู้ให้บริการที่มี **การใช้งานดิบ 60%** (จึงเหลือ **โควตาดิบ 40%**) และมีการกำหนดเกณฑ์
**25% ของโควตาที่เหลือ**:

| การแสดงผล                      | การคำนวณ                                           | คงเหลือ |           การใช้งานโดยนัย            |
| :----------------------------- | :------------------------------------------------- | :-----: | :----------------------------------: |
| **JSON ดิบ (`?format=json`)**  | สแนปช็อตจากต้นทาง (`quotas[window]`)               | **40%** |               **60%**                |
| **รูปแบบข้อความ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (หากคำนวณ `100 - remaining`) |

- **เหตุผลที่ข้อความแสดงว่าคงเหลือ 20%:** จากโควตาทางกายภาพ 40% ที่เหลืออยู่ในบัญชี 25% จะถูกสงวนไว้ตาม
  นโยบาย cutoff ผู้เรียกใช้จึงเหลือพื้นที่รองรับที่ใช้งานได้เพียง 15% จากทั้งหมด 75% ก่อนที่เราเตอร์จะหยุด
  การกำหนดเส้นทางไปยังการเชื่อมต่อนี้ การปรับสเกลทำให้การเชื่อมต่อส่งสัญญาณว่าหมดลง (`0% left`) ตรงกับเวลาที่
  การกำหนดเส้นทางจะยุติลงพอดี
- **เหตุผลที่ JSON ยังคงค่าดิบไว้:** เพย์โหลด JSON จะแสดงสแนปช็อตที่แน่นอนจากผู้ให้บริการ (`UsageSnapshot`)
  เพื่อให้เครื่องมือภายนอกเข้าถึงการใช้งานจริงจากต้นทางและ `quotaWindowThresholds` ระดับการเชื่อมต่อได้
  โดยไม่มีการปรับสเกลแบบสูญเสียข้อมูลจากฝั่งเซิร์ฟเวอร์

#### คำแนะนำในการย้ายระบบสำหรับผู้ใช้

หากการผสานการทำงานภายนอก (เช่น ปลั๊กอินตัวแก้ไขหรือส่วนขยายเอเจนต์) เคยดึงข้อมูลจากปลายทางข้อความ
(`NN% left`) และคำนวณเปอร์เซ็นต์การใช้งานเป็น `100 - NN` การย้ายไปใช้ `?format=json` หมายความว่า:

- การอ่านค่าดิบจาก JSON จะแสดง **การใช้งานจริงจากต้นทาง** (ใช้งานไป 60% ในตัวอย่างข้างต้น)
- หากการผสานการทำงานต้องการคงความหมายของค่าเผื่อที่ใช้งานได้จากปลายทางข้อความไว้ ก็สามารถประเมิน
  สูตรคำนวณค่าคงเหลือที่มีผลในฝั่งไคลเอ็นต์โดยใช้ `quotaWindowThresholds` สำหรับการแทนที่ในระดับการเชื่อมต่อได้

## แคชเชิงความหมาย

```bash
# รับสถิติแคช
GET /api/cache/stats

# ล้างแคชทั้งหมด
DELETE /api/cache/stats
```

ตัวอย่างการตอบกลับ:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### ผลกระทบต่อเวลาแฝง

Semantic cache HIT จะส่งการตอบกลับจากแคช **โดยไม่เรียก upstream**
ดังนั้นค่า `X-OmniRoute-Response-Latency` ที่รายงานจะใกล้ศูนย์
(ไม่ขึ้นกับเวลาแฝงของ upstream เดิม) ไคลเอ็นต์ที่ไวต่อเวลาแฝง
(การทำเบนช์มาร์ก การตรวจสอบ p50/p99) ควรตรวจสอบเฮดเดอร์การตอบกลับ
`X-OmniRoute-Cache-Latency`:

| ค่า         | ความหมาย                                                 |
| ----------- | -------------------------------------------------------- |
| `synthetic` | การตอบกลับถูกส่งจากแคช เวลาแฝงไม่ใช่เวลาจริงของ upstream |
| _(absent)_  | การตอบกลับจากการเรียก upstream จริง                      |

### การข้ามแคชตามคีย์

คีย์ API สามารถเลือกไม่อ่านจาก semantic cache ได้ผ่าน `cacheDefaultMode`:

| ค่า      | ลักษณะการทำงาน                               |
| -------- | -------------------------------------------- |
| `legacy` | ลักษณะการทำงานของแคชตามปกติ (ค่าเริ่มต้น)    |
| `bypass` | ข้ามการค้นหาในแคชทั้งหมด เรียก upstream เสมอ |

กำหนดค่าขณะสร้างคีย์ (`POST /api/keys`) หรืออัปเดต (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### การข้ามแคชตามคำขอ

คำขอใด ๆ สามารถข้ามแคชได้โดยไม่ขึ้นกับการตั้งค่าคีย์:

```
X-OmniRoute-No-Cache: true
```

## ความเข้ากันได้ในการจัดการ CLIProxyAPI

OmniRoute ตอบสนองต่อเอนด์พอยต์การจัดการทั้งสามของ
[CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ที่แดชบอร์ดการใช้งานเรียกเพื่ออ่านขีดจำกัดการสมัครสมาชิก Claude และ Codex
(เช่น แหล่งข้อมูลขีดจำกัดการใช้งาน `cliproxy` ของ T3 Code) กำหนด URL พื้นฐานของไคลเอ็นต์ให้ชี้ไปที่
OmniRoute และใช้คีย์ API ที่มีสโคป `manage` เป็นคีย์การจัดการของไคลเอ็นต์ เส้นทางเหล่านี้
ให้บริการที่ `/v0/management/*` และ `/api/v0/management/*`

| Method | Path                         | Description                                                                                                                              |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | การเชื่อมต่อ OAuth ของ Claude และ Codex ในรูปแบบ `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }` ไม่มีโทเค็น      |
| POST   | `/v0/management/api-call`    | เนื้อหา `{ auth_index, method, url, header?, data? }` ส่งคำขอที่อนุญาตไว้หนึ่งรายการด้วยโทเค็นของบัญชี และส่งคืน `{ status_code, body }` |
| POST   | `/v0/management/reset-quota` | เนื้อหา `{ auth_index }` ล้างคูลดาวน์ของการเชื่อมต่อ การล็อกเอาต์ของโมเดล และคูลดาวน์ตามสโคปของ Codex สำหรับบัญชีหนึ่งบัญชี              |

- `auth_index` คือ ID การเชื่อมต่อของ OmniRoute ส่วน `provider` คือ `claude` หรือ `codex` (เฉพาะการเชื่อมต่อ OAuth โดยไม่นับผู้ให้บริการแบบ API key `anthropic`) สำหรับ Codex ค่า `id_token.chatgpt_account_id` คือ ID เวิร์กสเปซที่เก็บไว้ และ `plan_type` คือแผนที่เก็บไว้
- `api-call` ไม่ใช่พร็อกซีทั่วไป ยอมรับเฉพาะ `GET
https://api.anthropic.com/api/oauth/usage` ของ Claude และ `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits`, `POST .../wham/rate-limit-reset-credits/consume` ของ Codex โดยแต่ละรายการใช้ได้เฉพาะกับบัญชีของผู้ให้บริการที่ตรงกัน สิ่งอื่นจะคืน `403` โดยไม่ติดต่อระบบต้นทาง เฮดเดอร์ `Authorization` ของผู้เรียก รวมถึงตัวแทนค่า `$TOKEN$` จะถูกละเลย OmniRoute ใส่โทเค็นการเข้าถึงของการเชื่อมต่อให้ โดยรีเฟรชก่อนหากใกล้หมดอายุ และส่งต่อเฉพาะเฮดเดอร์ที่อยู่ในรายการอนุญาต (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`) หากไม่มี `Chatgpt-Account-Id` จะใช้ ID เวิร์กสเปซที่เก็บไว้เป็นค่าเริ่มต้น หากคำตอบแรกจากต้นทางคือ `401` ระบบจะรีเฟรชหนึ่งครั้งและลองใหม่เฉพาะเมื่อโทเค็นการเข้าถึงเปลี่ยนไป แต่ละครั้งที่เรียกต้นทางจะหมดเวลาหลัง 15 วินาทีและใช้พร็อกซีของการเชื่อมต่อ
- `reset-quota` ไม่เปลี่ยนสถานะสิ้นสุด (banned, expired, credits_exhausted) หากไม่รู้จัก `auth_index` จะคืน `404`

**การตรวจสอบสิทธิ์:** ต้องใช้เซสชันแดชบอร์ดหรือคีย์ API ที่มีสโคป `manage` แม้จะปิดใช้งานการเข้าสู่ระบบ
แล้วก็ตาม (เส้นทางเหล่านี้อยู่ใน `ALWAYS_PROTECTED_API_PATHS`) คีย์ที่ใช้สำหรับการอนุมานเท่านั้นจะได้รับ `403` แหล่งที่มา:
`src/lib/cliproxyCompat/managementApi.ts`.

บนโหนดผู้ให้บริการที่เข้ากันได้ เส้นทางการเขียน (`POST`, `PUT`, `PATCH`, `DELETE` และ
`/api/provider-models/validate-and-add`) จะจัดเก็บรหัสโมเดลเป็นรหัสต้นทางแบบไม่มีคำนำหน้า: รหัสที่
วางจากรายการที่มีคำนำหน้าจะถูกยุบคำนำหน้าที่ซ้อนกันทั้งหมดซึ่งเป็นคำนำหน้าของโหนดนั้นเอง และ
การตอบกลับจะแสดงรหัสที่จัดเก็บไว้ รหัสที่มีเครื่องหมายทับของผู้ให้บริการมาตรฐาน (เช่น `nvidia/nemotron-…`) จะถูก
จัดเก็บตามเดิม `/v1/models` จะไม่แสดงรหัสในรูปแบบ `<prefix>/<prefix>/<model>` ที่มีคำนำหน้าซ้อนกัน

โหนด Custom Chat Completions จะปรับการเลือกไม่ใช้เหตุผลอย่างชัดแจ้งให้เข้ากับแบ็กเอนด์ต้นทาง การทดสอบการเชื่อมต่อที่สำเร็จจะเลือกตัวควบคุม chat-template โดยอัตโนมัติสำหรับ model ID ที่ตรงกันทุกประการ ซึ่งรายการ `/models` ยืนยันค่า `owned_by` ที่รู้จัก ได้แก่ `vllm`, `sglang` หรือ `llamacpp`\
wrapper ที่เข้ากันได้กับ OpenAI แบบโปร่งใสอาจเก็บรายการโมเดลเดิมไว้ภายในออบเจ็กต์ `openai` ที่ซ้อนกัน การตรวจจับจะติดตาม envelope ดังกล่าวได้สูงสุดสามชั้น โมเดลที่ไม่มีข้อมูล ownership มีค่าที่ไม่รู้จัก หรือมี ownership ขัดแย้งกัน จะคงพฤติกรรม OpenAI ปกติไว้ การตรวจจับจะใช้คำขอ catalog ที่มีอยู่เดิม ไม่สร้าง completion token และจะถูกทำให้ใช้งานไม่ได้เมื่อ endpoint ของการเชื่อมต่อเปลี่ยนแปลง

หากต้องการกำหนดพฤติกรรมตายตัวสำหรับแบ็กเอนด์ที่ไม่เปิดเผย metadata ดังกล่าว ให้ใช้ API การอัปเดต provider บางส่วนที่มีอยู่เดิม:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ส่ง body ดังกล่าวด้วย `PUT /api/providers/<connection-id>` สำหรับการเชื่อมต่อนั้น reasoning effort ที่ระบุเป็น `none` จะถูกส่งเป็น `chat_template_kwargs.thinking=false` และ `chat_template_kwargs.enable_thinking=false` ค่าเทมเพลตแบบ native ที่ระบุอย่างชัดแจ้งจะยังคงมีผลเหนือกว่า เว้นแต่กฎ reasoning ฝั่งเซิร์ฟเวอร์จะบังคับให้ใช้ effort การตั้งค่านี้มีผลเฉพาะเมื่อการเชื่อมต่อ OpenAI-compatible แบบกำหนดเองส่ง body ของ Chat Completions เท่านั้น คำขอ Responses และ provider ปกติจะยังคงใช้รูปแบบคำขอแบบ native ของตน ตั้งค่า `reasoningControl` เป็น `openai` เพื่อบังคับให้ส่งผ่าน `reasoning_effort` แบบ OpenAI ปกติ หรือไม่ระบุค่านี้/ตั้งเป็น `null` เพื่อใช้การตรวจจับอัตโนมัติ

คำขอ classifier ของ Claude Code auto-mode จะปิด native thinking เป็นค่าเริ่มต้นเมื่อไม่มีตัวควบคุม reasoning ที่ระบุอย่างชัดแจ้ง การตรวจจับใช้เครื่องหมายระบบของ classifier ในคำขอรูปแบบ Claude ไม่ได้ใช้ชื่อโมเดลหรือขีดจำกัด completion ตัวควบคุมใน body ที่ระบุอย่างชัดแจ้ง ส่วนหัว effort/thinking ที่รองรับ กฎ routing และ effort ของโมเดลที่แก้ไขแล้ว จะยังคงมีลำดับความสำคัญเดิม ทั้งสองขั้นของ classifier ยังคงใช้ prompts, ขีดจำกัด completion, stop sequences และผลการอนุญาตจริงจาก upstream ตามเดิม โดยขั้นที่สองยังสามารถสร้าง reasoning ที่มองเห็นได้ตามที่ร้องขอเป็นข้อความปกติ

#### แหล่งที่มาของขีดจำกัดโมเดล

`GET /api/models?withLimits=1` (รวมถึง `true`; การใช้ `0`/`false` หรือไม่ระบุจะคง payload เริ่มต้นไว้เหมือนเดิม) จะเพิ่ม `contextWindow`, `maxInputTokens`, `maxOutputTokens` และออบเจ็กต์ `capsSource` ให้กับแถวโมเดลทุกแถว `capsSource` จะระบุกฎที่จัดหาขีดจำกัดแต่ละรายการ ทำให้สามารถติดตามขีดจำกัดที่ดูผิดปกติ (เช่น 128k สำหรับโมเดล 1M) กลับไปยังต้นทางได้ ค่าที่แก้ไขแล้วเป็นค่าเดียวกับที่ routing ใช้ แฟล็กนี้เพิ่มเฉพาะฟิลด์และจะไม่เปลี่ยนค่าใด ๆ ค่า `withLimits` อื่นใดจะถูกปฏิเสธด้วย `400`

| ค่า `capsSource`                             | ต้นทาง                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| `override:context`                           | การแทนที่ context-window ที่จัดเก็บถาวร (`model_context_overrides`)         |
| `override:max_input` / `override:max_output` | การแทนที่ความสามารถ `max_input_tokens` / `max_output_tokens` ที่จัดเก็บถาวร |
| `static-authoritative:<provider>/<model>`    | ตาราง context-window แบบ static ที่มีสิทธิ์อ้างอิงสูงสุด                    |
| `synced:<provider>/<model>`                  | แถวความสามารถที่ซิงค์จาก models.dev                                         |
| `registry:<provider>/<model>`                | รายการในรีจิสทรีของ provider                                                |
| `spec:<model>`                               | ข้อมูลจำเพาะโมเดลแบบ static                                                 |
| `effort-base:` prefix                        | แถวยืมมาจากโมเดลฐานของตัวแปรที่มี suffix เป็น effort                        |
| `none`                                       | ไม่มีแหล่งที่มาที่ประกาศขีดจำกัด (ค่าคือ `null`)                            |

การใช้งาน: `getResolvedModelCapabilitiesWithLimitSources()` ใน `src/lib/modelCapabilities.ts`\
และ chain ลำดับความสำคัญใน `src/lib/modelCapabilityLimits.ts`

### เวอร์ชันและช่องทางการเผยแพร่

```bash
GET /api/system/version
```

เส้นทางการจัดการที่ใช้ได้เฉพาะ loopback (ต้องมีการยืนยันตัวตนของผู้ดูแลระบบ) ส่งคืนเวอร์ชันที่กำลังทำงาน เวอร์ชันล่าสุดที่เผยแพร่ และสถานะการอัปเดตอัตโนมัติ `releaseChannel` และ `channels` เป็นฟิลด์เพิ่มเติม (rail 3.8.54); `channel` ยังคงมีความหมายเดิม — โหมดการติดตั้งที่ตัวอัปเดตของแดชบอร์ดใช้ (`npm`, `source` หรือ `docker-compose`)

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ช่องทาง npm ของบิลด์ที่กำลังทำงาน: `nightly` สำหรับเวอร์ชัน `-nightly.*`, `next` สำหรับรุ่นก่อนเผยแพร่อื่น ๆ (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` สำหรับเวอร์ชันเสถียรของ major รุ่นเก่ากว่า `channels.latest` และเป็น `latest` ในกรณีอื่น กฎเดียวกับ `scripts/release/dist-tag.mjs` ซึ่งเลือก npm dist-tag เมื่อเผยแพร่
- `channels` — เวอร์ชันล่าสุดที่เผยแพร่ของแต่ละ dist-tag จาก `npm view omniroute dist-tags` (มีการสำรองไปใช้ HTTP ของรีจิสทรี) โดยแคชด้วย TTL 10 นาทีเดียวกับ `latest` จะมี `latest` อยู่เสมอ (สำรองไปใช้ฟิลด์ `latest` จากนั้นจึงใช้ `"unavailable"`); `next`, `nightly` และ `lts` จะแสดงเฉพาะเมื่อมี dist-tag ดังกล่าวอยู่ คำขอ `Cache-Control: no-cache` จะรีเฟรชการค้นหาทั้งสองรายการ

โมเดลของช่องทาง (`latest` = v3 จนถึง GA ของ 4.0, `next` = rc, `nightly` = บิลด์จาก `develop`, `lts` = แพตช์ v3 หลัง GA ของ 4.0) อธิบายไว้ใน `docs/ops/RELEASE_STRATEGY.md`

## การถอดเสียง

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

ถอดเสียงไฟล์เสียงโดยใช้ผู้ให้บริการ STT ที่กำหนดค่าไว้ได้ ผู้ให้บริการเนทีฟจะถูกเลือกโดยเซกเมนต์แรกของพาธ (`openai/…`, `deepgram/…`) เกตเวย์ที่ส่งต่อโมเดลของผู้ให้บริการรายอื่นจะใช้ ID แบบมีคุณสมบัติกำกับ
(`openrouter/deepgram/nova-3`)

**คำขอ:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**การตอบกลับ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**ตัวอย่าง ID ของโมเดล:** `openai/whisper-1` (ต้องใช้คีย์ OpenAI),
`openrouter/deepgram/nova-3` (ต้องใช้คีย์ OpenRouter),
`deepgram/nova-3` (ต้องใช้คีย์ Deepgram เนทีฟ) คำขอ
`deepgram/nova-3` แบบไม่ระบุเกตเวย์จะ **ไม่** ใช้ OpenRouter

**รูปแบบที่รองรับ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** การถอดเสียงในโหมดไฟล์ผ่าน
WebSocket ของ Gemini Live (ต้องใช้คีย์ API ของ Gemini) ไฟล์อัปโหลดจะถูกแปลงเป็น PCM โมโน 16 kHz ด้วย `ffmpeg`
(ต้องอยู่ใน `PATH` เว้นแต่ไฟล์นั้นจะเป็น WAV แบบ PCM โมโน 16 kHz อยู่แล้ว) จากนั้นจะสตรีมไปยังเซสชันและ
ส่งคืนข้อความที่สรุปแล้วเป็น `{ "text": "..." }` ฟิลด์ฟอร์ม `language` และ `prompt` เป็นตัวเลือกและจะถูกส่งต่อไป
ขีดจำกัด: การอัปโหลดที่มีขนาดเกิน 25 MiB หรือเสียงที่ถอดรหัสแล้วมีความยาวเกิน 10 นาทีจะตอบกลับด้วย
`413`; หากการแปลงใช้เวลานานกว่า 60 วินาที ระบบจะยุติกระบวนการและตอบกลับด้วย `504` คีย์ API จะถูกส่ง
ในเฮดเดอร์ `x-goog-api-key` เท่านั้น และจะไม่ถูกส่งใน URL ของ WebSocket

## นามแฝง VS Code แบบมีโทเค็น / ไม่มีส่วนหัว

ใช้นามแฝงเหล่านี้เมื่อการผสานรวมไม่สามารถเพิ่มส่วนหัว `Authorization` และจำเป็นต้องฝังคีย์ API ไว้ใน URL ฐาน

```bash
# นามแฝงแค็ตตาล็อกสไตล์ OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# นามแฝงแชตสไตล์ OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# นามแฝงสไตล์ Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ตัวอย่าง:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

หมายเหตุ:

- นามแฝงแบบมีโทเค็นจะใช้ตัวจัดการเดียวกับ `/v1/*` และ `/api/tags`; รูปแบบการตอบกลับยังคงเหมือนเดิม
- เลือกใช้ `Authorization: Bearer ...` ทุกครั้งที่ไคลเอ็นต์รองรับส่วนหัวแบบกำหนดเอง
- โทเค็นใน URL อาจปรากฏในบันทึกของพร็อกซีแบบย้อนกลับ ประวัติเบราว์เซอร์ และข้อมูลการวัดผลนอก OmniRoute ให้ถือว่าโทเค็นเหล่านี้เป็นตัวเลือกด้านความเข้ากันได้ ไม่ใช่โหมดการตรวจสอบสิทธิ์เริ่มต้น

## งบประมาณ

```bash
# รับสถานะงบประมาณสำหรับคีย์ API ทั้งหมด
GET /api/usage/budget

# ตั้งค่าหรืออัปเดตงบประมาณ
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **หมายเหตุเกี่ยวกับสคีมา** (`setBudgetSchema`): ต้องระบุ `apiKeyId`; อย่างน้อยหนึ่งรายการจาก `dailyLimitUsd`, `weeklyLimitUsd` หรือ `monthlyLimitUsd` ต้องมีค่ามากกว่าศูนย์ ฟิลด์ที่ไม่บังคับ: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`) รูปแบบเดิม `{keyId, limit, period}` จะส่งคืน `400 Bad Request`

## ขีดจำกัดโทเค็น

งบประมาณ **โทเค็น** ต่อ API key (แตกต่างจากงบประมาณที่คิดตาม USD ด้านบน) ระบบบังคับใช้แบบ inline บนเส้นทางคำขอ: เมื่อการใช้งานในหน้าต่างปัจจุบันของคีย์ถึงขีดจำกัด คำขอจะถูกปฏิเสธด้วย `429 Too Many Requests` ขีดจำกัดสามารถกำหนดขอบเขตเฉพาะ `model` หรือ `provider` หรือใช้แบบ `global` ทั่วทั้งคีย์ได้ หากมีขีดจำกัดหลายรายการที่ตรงกับคำขอ ระบบจะใช้ขีดจำกัดที่เข้มงวดที่สุด

```bash
# แสดงขีดจำกัดโทเค็นของคีย์ (รวมการใช้งานในหน้าต่างปัจจุบัน)
GET /api/usage/token-limits?apiKeyId=key-123

# สร้างหรืออัปเดตขีดจำกัดโทเค็น
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ลบขีดจำกัดโทเค็นตาม id
DELETE /api/usage/token-limits?id=tl-abc
```

> **หมายเหตุเกี่ยวกับสคีมา** (`setTokenLimitSchema`): จำเป็นต้องระบุ `apiKeyId` และ `scopeType` (`model` | `provider` | `global`) ต้องระบุ `scopeValue` เว้นแต่ `scopeType` จะเป็น `global` (เช่น รหัสโมเดลสำหรับขอบเขต `model` หรือรหัสผู้ให้บริการสำหรับขอบเขต `provider`) `tokenLimit` ต้องเป็นจำนวนเต็มบวก (แปลงจากสตริงโดยอัตโนมัติ) ตัวเลือก: `id` (ไม่ต้องระบุเมื่อสร้าง ให้ระบุเมื่อต้องการอัปเดต), `resetInterval` (`daily` | `weekly` | `monthly`, ค่าเริ่มต้นคือ `monthly`), `resetTime` (`HH:MM`), `enabled` (ค่าเริ่มต้นคือ `true`) การตอบกลับจาก `GET` จะเพิ่มข้อมูลให้แต่ละขีดจำกัด ได้แก่ `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` และ `nextResetAt` จุดปลายทางนี้จัดอยู่ในคลาสการจัดการ (การตรวจสอบสิทธิ์ถูกบังคับใช้จากส่วนกลางโดยไปป์ไลน์ authz)

## การประมวลผลคำขอ

1. ไคลเอนต์ส่งคำขอไปยัง `/v1/*`
2. ตัวจัดการเส้นทางเรียกใช้ `handleChat`, `handleEmbedding`, `handleAudioTranscription` หรือ `handleImageGeneration`
3. ระบบแก้ไขโมเดล (ผู้ให้บริการ/โมเดลโดยตรง หรือ alias/combo)
4. ระบบเลือกข้อมูลรับรองจากฐานข้อมูลภายใน โดยกรองตามความพร้อมใช้งานของบัญชี
5. สำหรับแชต: `handleChatCore` ตรวจสอบแคชเชิงความหมาย/ลายเซ็น และแก้ไขการตั้งค่าการบีบอัดของ combo
6. ระบบบีบอัดเชิงรุกก่อนการแปลสำหรับผู้ให้บริการเมื่อเปิดใช้งาน (`lite`, Caveman, RTK หรือแบบซ้อนกัน)
7. ตัวดำเนินการของผู้ให้บริการส่งคำขอไปยัง upstream
8. ระบบแปลการตอบกลับกลับเป็นรูปแบบของไคลเอนต์ (แชต) หรือส่งกลับตามเดิม (embeddings/images/audio)
9. ระบบบันทึกการใช้งาน การวิเคราะห์การบีบอัด และบันทึกคำขอ
10. ระบบ fallback ทำงานเมื่อเกิดข้อผิดพลาดตามกฎของ combo

เอกสารอ้างอิงสถาปัตยกรรมฉบับเต็ม: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## คีย์ที่ลงทะเบียน (การจัดการอัตโนมัติ)

ใช้โดยระบบจัดการคีย์อัตโนมัติเพื่อออกและหมุนเวียนคีย์ API กับผู้ให้บริการ/บัญชีที่อยู่เบื้องหลัง พร้อมโควตารายวัน/รายชั่วโมง

| Method | Path                                  | Description                                                                                                                                                                                              |
| ------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | แสดงรายการคีย์ที่ลงทะเบียน (แสดงเฉพาะคำนำหน้าที่ปิดบังแล้ว)                                                                                                                                              |
| POST   | `/api/v1/registered-keys`             | ออกคีย์ที่ลงทะเบียนใหม่ — body: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}` โดยจะแสดงคีย์ดิบ **เพียงครั้งเดียว** และส่งคืน `429` เมื่อปฏิเสธเนื่องจากโควตา |
| GET    | `/api/v1/registered-keys/[id]`        | ดึงข้อมูลเมตาของคีย์ที่ลงทะเบียน (ไม่มีข้อมูลคีย์ดิบ)                                                                                                                                                    |
| DELETE | `/api/v1/registered-keys/[id]`        | เพิกถอนคีย์ที่ลงทะเบียน                                                                                                                                                                                  |
| POST   | `/api/v1/registered-keys/[id]/revoke` | จุดปลายทางสำหรับการเพิกถอนโดยเฉพาะ (มีผลเช่นเดียวกับ DELETE)                                                                                                                                             |

**การตรวจสอบสิทธิ์:** เซสชันการจัดการ/คีย์ API (`requireManagementAuth`) — ตัวป้องกันเดียวกับ `/api/keys`: เซสชันแดชบอร์ด โทเค็น CLI ภายในเครื่อง หรือคีย์ API ที่มีขอบเขต `manage`/`admin`; คีย์ API ที่ใช้สำหรับการอนุมานเท่านั้นจะได้รับ `403` ดูเพิ่มเติมที่ `/v1/quotas/check` และ `/v1/issues/report`

## โปรโตคอล Agents

งานของ Cloud agent (Claude Code, Codex Cloud, OpenHands ฯลฯ) ที่ดำเนินการจากระยะไกลในนามของผู้ใช้ OmniRoute

| Method | Path                          | Description                                                                                                                                             |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/agents/tasks`        | แสดงรายการงาน — เลือกกรองได้ด้วย `?provider=`, `?status=`, `?limit=` (1–500 ค่าเริ่มต้นคือ 50)                                                          |
| POST   | `/api/v1/agents/tasks`        | สร้างงาน — body จะได้รับการตรวจสอบโดย `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`) โดยจะส่งคืน `201` พร้อม task envelope |
| DELETE | `/api/v1/agents/tasks?id=...` | ลบงาน                                                                                                                                                   |
| GET    | `/api/v1/agents/tasks/[id]`   | อ่านงาน — จะรีเฟรชสถานะจาก Cloud agent ต้นทางแบบ synchronous เมื่อมีการกำหนด `external_id`                                                              |
| POST   | `/api/v1/agents/tasks/[id]`   | การดำเนินการแบบแยกประเภท: `{action: "approve"}`, `{action: "message", message}` หรือ `{action: "cancel"}`                                               |
| DELETE | `/api/v1/agents/tasks/[id]`   | ลบงานเฉพาะรายการตาม id                                                                                                                                  |

> **การยืนยันตัวตน:** ทุกเมธอดต้องใช้การยืนยันตัวตนสำหรับการจัดการ (`requireCloudAgentManagementAuth`) ก่อนหน้า v3.8.0 เส้นทางเหล่านี้ไม่มีการยืนยันตัวตน — ดู commit `588a0333` สำหรับการเปลี่ยนแปลงที่ไม่เข้ากันได้ย้อนหลัง

```bash
# สร้างงาน Claude Code cloud
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Authorization: Bearer your-management-key" \
  -H "Content-Type: application/json" \
  -d '{"providerId":"claude-code-cloud","prompt":"Fix the failing test","source":{"repo":"...","branch":"..."}}'
```

## พร็อกซีการจัดการ

พร็อกซี HTTP(S)/SOCKS ขาออกที่สามารถกำหนดให้กับ providers, accounts หรือใช้ทั่วโลกได้

| Method | Path                                         | Description                                                                                                                                        |
| ------ | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | แสดงรายการพร็อกซี (หากมี `?id=` จะส่งคืนหนึ่งรายการ; หากมี `?id=&where_used=1` จะส่งคืนกราฟการกำหนด)                                               |
| POST   | `/api/v1/management/proxies`                 | สร้างพร็อกซี — body จะได้รับการตรวจสอบโดย `createProxyRegistrySchema`                                                                              |
| PATCH  | `/api/v1/management/proxies`                 | อัปเดตพร็อกซี — body จะได้รับการตรวจสอบโดย `updateProxyRegistrySchema` (ต้องมี `id`)                                                               |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | ลบพร็อกซี (ใช้ `force=1` เพื่อยกเลิกการกำหนดทั้งหมด)                                                                                               |

| PUT    | `/api/v1/management/proxies/assignments`     | กำหนด — body จะได้รับการตรวจสอบโดย `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) โดยจะล้างแคชของ dispatcher                              |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | กำหนดเป็นกลุ่ม — body จะได้รับการตรวจสอบโดย `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`)                                          |
| GET    | `/api/v1/management/proxies/health?hours=24` | สถานะสุขภาพพร็อกซีโดยรวม (จำนวนสำเร็จ/ล้มเหลว, latency) ในช่วงเวลาที่กำหนด                                                                         |

**การยืนยันตัวตน:** ทุก route ต้องใช้ management session/API key (`requireManagementAuth`)

> คำอธิบายงานที่ระบุ `POST /api/v1/management/proxies/[id]/assignments` และ `POST /api/v1/management/proxies/[id]/health` นั้นให้บริการผ่าน route แบบ flat คือ `/assignments` และ `/health` ที่แสดงไว้ด้านบน — ใน codebase ไม่มี subroute ที่แยกตาม id

## ความยืดหยุ่น (เพิ่มเติม)

OmniRoute มีกลไกจัดการความล้มเหลวชั่วคราวที่เป็นอิสระต่อกันสามรูปแบบ โดยจุดสิ้นสุดการจัดการด้านล่างช่วยให้ผู้ปฏิบัติงานอ่านและแทนที่ค่าเหล่านี้ได้:

| ขอบเขต                    | ที่จัดเก็บสถานะ                                  | อ่าน                                      | รีเซ็ต / ล้าง                                              |
| ------------------------- | ------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------- |
| ตัวตัดวงจรของผู้ให้บริการ | `domain_circuit_breakers` + หน่วยความจำ          | `/api/monitoring/health`                  | `POST /api/resilience/reset`                               |
| ช่วงพักการเชื่อมต่อ       | `rateLimitedUntil` บนการเชื่อมต่อของผู้ให้บริการ | `/api/rate-limits`, `/api/providers/[id]` | (เปิดใช้งานอีกครั้งแบบ lazy; ล้างผ่าน PUT ของผู้ให้บริการ) |
| การล็อกโมเดล              | รีจิสทรีความพร้อมใช้งานของโมเดลในหน่วยความจำ     | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                   |

`PATCH /api/resilience` รองรับการแทนที่ค่าตัวตัดวงจรของผู้ให้บริการภายใต้ `providerBreaker.oauth` และ `providerBreaker.apikey` แต่ละโปรไฟล์รองรับ `degradationThreshold`, `failureThreshold` และ `resetTimeoutMs` โดยฟิลด์เดียวกันนี้จะแสดงใน Dashboard → Settings → Resilience

```bash
# ล้างการล็อกโมเดลรายการเดียว
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ล้างการล็อกทั้งหมด
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

สำหรับเอกสารอ้างอิงเชิงแนวคิดฉบับเต็มและค่าเริ่มต้นของตัวตัดวงจร โปรดดู [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" และ [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)

### คิวจำกัดอัตราและระบบความปลอดภัยเปิดใช้งานอัตโนมัติ

- **เส้นทางการเขียนที่รองรับ**: `POST /api/rate-limits` พร้อม body `{"connectionId": "<id>", "enabled": true|false}` คือจุดสิ้นสุดการจัดการที่รองรับสำหรับสลับการป้องกันการจำกัดอัตราของการเชื่อมต่อ `PUT /api/providers/[id]` จะไม่แก้ไขหรือสลับค่า `rateLimitProtection` โดยเจตนา (#11278)
- **ความหมายของ `enabled: false`**: การตั้งค่า `enabled: false` จะลบการป้องกันที่ระบุไว้อย่างชัดเจนสำหรับการเชื่อมต่อ แต่ **ไม่ได้** ยกเลิกการเข้าร่วมระบบความปลอดภัยเปิดใช้งานอัตโนมัติระดับโกลบอลสำหรับการเชื่อมต่อ API-key ที่ทำงานอยู่ (`autoEnableApiKeyProviders = true`) ใน `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) ค่า `false` และ `undefined` มีความหมายเทียบเท่ากัน การเชื่อมต่อ API-key ที่ทำงานอยู่และไม่มีการป้องกันที่ระบุไว้อย่างชัดเจนจะยังคงได้รับการป้องกันภายใต้ระบบความปลอดภัยเปิดใช้งานอัตโนมัติ
- **การปิดใช้งานระดับโกลบอล**: หากต้องการให้การเชื่อมต่อ API-key ทำงานโดยไม่มีคิวจำกัดอัตรา ให้ปิดระบบความปลอดภัยนี้ทั่วทั้งระบบผ่าน `RATE_LIMIT_AUTO_ENABLE=false` (env) หรือ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`)

## เซิร์ฟเวอร์ MCP

OmniRoute มาพร้อมเซิร์ฟเวอร์ Model Context Protocol ในตัว ซึ่งมีการขนส่ง 3 รูปแบบ (stdio, SSE, streamable-http) และเครื่องมือที่กำหนดขอบเขตไว้ จุดปลายทางของแดชบอร์ดด้านล่างนี้อ่านข้อมูลสถานะ/การตรวจสอบ และทำหน้าที่เป็นพร็อกซีสำหรับการขนส่งผ่าน HTTP

| Method | Path                   | Description                                                                                                                    |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/mcp/status`      | ฮาร์ตบีต, การขนส่ง, สถานะออนไลน์, การเรียกล่าสุด, เครื่องมือยอดนิยม, อัตราความสำเร็จในช่วง 24 ชั่วโมง                          |
| GET    | `/api/mcp/tools`       | รายการเครื่องมือ MCP พร้อม `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints`                           |
| GET    | `/api/mcp/sse`         | เปิดสตรีม SSE สำหรับการขนส่ง SSE (ส่งคืน `503` หาก MCP ถูกปิดใช้งานหรือการขนส่งไม่ตรงกัน)                                      |
| POST   | `/api/mcp/sse`         | ส่งเฟรม JSON-RPC ผ่านการขนส่ง SSE                                                                                              |
| GET    | `/api/mcp/stream`      | เปิดฝั่ง SSE ของการขนส่ง Streamable HTTP (ข้อความที่เซิร์ฟเวอร์เริ่มส่งเอง)                                                    |
| POST   | `/api/mcp/stream`      | ส่งเฟรม JSON-RPC ผ่านการขนส่ง Streamable HTTP                                                                                  |
| DELETE | `/api/mcp/stream`      | สิ้นสุดเซสชัน Streamable HTTP                                                                                                  |
| GET    | `/api/mcp/audit`       | ค้นหาบันทึกการตรวจสอบ — `?limit=`, `?offset=`, `?tool=`, `?success=true                                \| false`, `?apiKeyId=` |
| GET    | `/api/mcp/audit/stats` | สถิติการตรวจสอบแบบรวม (จำนวนรวม, อัตราความสำเร็จ, ระยะเวลาเฉลี่ย, เครื่องมือยอดนิยม)                                           |

**การยืนยันตัวตน:** การขนส่ง `sse`/`stream` ใช้พื้นผิวการยืนยันตัวตนเฉพาะของ MCP (Bearer API key ที่มี scope `mcp`); เส้นทาง `status`/`tools`/`audit*` สามารถอ่านได้จากแดชบอร์ด (ไม่ต้องมีการยืนยันตัวตนเพิ่มเติมนอกเหนือจากการเข้าถึงโฮสต์แดชบอร์ด)

> การขนส่งผ่าน HTTP ทั้งสองรูปแบบถูกควบคุมด้วย `settings.mcpEnabled` และ `settings.mcpTransport` — หากการขนส่งไม่ตรงกันจะส่งคืน `400` และหาก MCP ถูกปิดใช้งานจะส่งคืน `503`

## เซิร์ฟเวอร์ A2A

OmniRoute เปิดให้ใช้งานปลายทาง JSON-RPC 2.0 ของ A2A (Agent-to-Agent) พร้อมตัวห่อหุ้ม REST สำหรับการตรวจสอบ/แดชบอร์ด

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # ไม่บังคับ เว้นแต่จะตั้งค่า OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

เมธอดที่รองรับ (ทั้งหมดควบคุมด้วย `settings.a2aEnabled`):

| Method           | Description                                                       |
| ---------------- | ----------------------------------------------------------------- |
| `message/send`   | การเรียกใช้ทักษะแบบซิงโครนัส คืนค่า `{task, artifacts, metadata}` |
| `message/stream` | การเรียกใช้ทักษะชุดเดียวกันผ่าน SSE แบบสตรีม                      |
| `tasks/get`      | ดึงข้อมูลงานตาม `taskId`                                          |
| `tasks/cancel`   | ยกเลิกงานตาม `taskId`                                             |

ทักษะในตัว: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`

### การ์ดเอเจนต์

```bash
GET /.well-known/agent.json
```

ส่งคืนการ์ดเอเจนต์ A2A สาธารณะ (ชื่อ คำอธิบาย ความสามารถ แค็ตตาล็อกทักษะ รูปแบบการยืนยันตัวตน) — แคชแบบสาธารณะเป็นเวลา 1 ชั่วโมง ไม่จำเป็นต้องยืนยันตัวตน

### ตัวช่วย REST

| Method | Path                         | Description                                                                                                        |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/a2a/status`            | สถานะการเปิดใช้งาน A2A + สถิติงาน + สรุปการ์ดเอเจนต์ที่แคชไว้                                                      |
| GET    | `/api/a2a/tasks`             | แสดงรายการงาน — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (ยังไม่ได้ติดตั้งเป็นตัวช่วย REST — ให้สร้างผ่าน JSON-RPC `message/send`)                                          |
| GET    | `/api/a2a/tasks/[id]`        | ดึงข้อมูลงานหนึ่งรายการ                                                                                            |
| POST   | `/api/a2a/tasks/[id]/cancel` | ยกเลิกงาน                                                                                                          |

**การยืนยันตัวตน:** ตัวช่วย REST ทำงานโดยไม่ใช้การยืนยันตัวตนสำหรับการจัดการ (แดชบอร์ดสามารถอ่านได้); เส้นทาง JSON-RPC `/a2a` ใช้ Bearer `OMNIROUTE_API_KEY` หากมีการกำหนดค่าไว้

## การตรวจสอบสิทธิ์

ดู [การตรวจสอบสิทธิ์สำหรับการจัดการ](../guides/MANAGEMENT-AUTH.md) สำหรับตระกูลข้อมูลรับรองทั้งสี่ประเภท (เซสชันแดชบอร์ด โทเค็น CLI ในเครื่อง Access Token `oma_live_…` คีย์ API ที่กำหนดขอบเขตเป็น manage) และความแตกต่างจากคีย์สำหรับการอนุมาน

- เส้นทางแดชบอร์ด (`/dashboard/*`) ใช้คุกกี้ `auth_token`

- สามารถสลับใช้ `requireLogin` ได้ผ่าน `/api/settings/require-login`
