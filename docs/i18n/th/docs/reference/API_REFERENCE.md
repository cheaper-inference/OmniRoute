## การเติมข้อความแชตให้สมบูรณ์

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### ส่วนหัวแบบกำหนดเอง

| ส่วนหัว                  | ทิศทาง     | คำอธิบาย                                                                                                                                                                                                                        |
| ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | คำขอ       | ตั้งค่าเป็น `true` เพื่อข้ามแคช                                                                                                                                                                                                 |
| `x-omniroute-no-memory`  | คำขอ       | ตั้งค่าเป็น `true` เพื่อข้ามการแทรกหน่วยความจำและทักษะสำหรับคำขอนี้ (ทำงานสอดคล้องกับ no-cache และหลีกเลี่ยงโอเวอร์เฮดด้านโทเค็น/ค่าใช้จ่ายต่อการเรียก)                                                                         |
| `X-OmniRoute-Progress`   | คำขอ       | ตั้งค่าเป็น `true` เพื่อรับเหตุการณ์ความคืบหน้า                                                                                                                                                                                 |
| `X-Session-Id`           | คำขอ       | คีย์เซสชันแบบคงที่สำหรับการเชื่อมโยงเซสชันภายนอก                                                                                                                                                                                |
| `x_session_id`           | คำขอ       | รองรับรูปแบบที่ใช้ขีดล่างด้วยเช่นกัน (HTTP โดยตรง)                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | คำขอ       | แท็กเซสชัน/การสนทนาที่ผู้เรียกระบุ (และส่งข้อมูลให้หน่วยความจำด้วย) เมื่อมีค่านี้ ระบบจะบันทึกค่าตามที่ได้รับลงใน `call_logs.session_tag` เพื่อระบุค่าใช้จ่ายแยกตามเซสชัน (#8249) — จะไม่มีการสร้างค่านี้ขึ้นเองเมื่อไม่ได้ระบุ |
| `Idempotency-Key`        | คำขอ       | คีย์สำหรับขจัดรายการซ้ำ (ช่วงเวลา 5 วินาที)                                                                                                                                                                                     |
| `X-Request-Id`           | คำขอ       | คีย์ทางเลือกสำหรับขจัดรายการซ้ำ                                                                                                                                                                                                 |
| `x-omniroute-connection` | คำขอ       | ตรึงคำขอแบบโมเดลเดียวไว้กับการเชื่อมต่อของผู้ให้บริการ (บัญชี) หนึ่งรายการด้วย ID ของรายการนั้น — ดู[การตรึงบัญชีต่อคำขอ](#account-pinning-per-request)                                                                         |
| `X-OmniRoute-Cache`      | การตอบกลับ | `HIT` หรือ `MISS` (แบบไม่สตรีม)                                                                                                                                                                                                 |
| `X-OmniRoute-Idempotent` | การตอบกลับ | `true` หากมีการขจัดรายการซ้ำ                                                                                                                                                                                                    |
| `X-OmniRoute-Progress`   | การตอบกลับ | `enabled` หากเปิดการติดตามความคืบหน้า                                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | การตอบกลับ | ID เซสชันที่ OmniRoute ใช้งานจริง                                                                                                                                                                                               |
| `X-OmniRoute-Request-Id` | การตอบกลับ | ID สำหรับเชื่อมโยงคำขอ (เมื่อทราบค่า)                                                                                                                                                                                           |
| `X-OmniRoute-Version`    | การตอบกลับ | เวอร์ชันบิลด์ของ OmniRoute (มีอยู่เสมอ)                                                                                                                                                                                         |
| `X-OmniRoute-Cost-Saved` | การตอบกลับ | จำนวนเงิน USD ที่ประหยัดได้จากแคชเมื่อเกิด HIT (เฉพาะเมื่อแคชพบข้อมูล)                                                                                                                                                          |
| `X-OmniRoute-Decision`   | การตอบกลับ | ร่องรอยการกำหนดเส้นทาง: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` คือกลยุทธ์ของคอมโบ หรือ `single` สำหรับคำขอที่ไม่ใช่คอมโบ) — มีอยู่เสมอในการตอบกลับเมื่อดำเนินการเสร็จสิ้น                                |

> หมายเหตุเกี่ยวกับ Nginx: หากคุณใช้ส่วนหัวที่มีเครื่องหมายขีดล่าง (ตัวอย่างเช่น `x_session_id`) ให้เปิดใช้งาน `underscores_in_headers on;`

#### การตรึงบัญชีสำหรับแต่ละคำขอ

เมื่อผู้ให้บริการมีการเชื่อมต่อหลายรายการ (บัญชีหรือคีย์) โดยปกติ OmniRoute จะเลือกหนึ่งรายการ
ผ่านกลยุทธ์การเลือกบัญชี แต่คำขอสามารถตรึงการเชื่อมต่อเฉพาะรายการหนึ่งได้
ด้วยส่วนหัว `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **ตำแหน่งที่ใช้ค้นหา id** เปิดหน้าผู้ให้บริการในแดชบอร์ด
  (**Dashboard → Providers → <provider>**) แล้วคลิกชิป id `xxxxxxxx…` ในแถวการเชื่อมต่อ
  ระบบจะคัดลอก id การเชื่อมต่อแบบเต็ม
- **คำขอที่รองรับ** คำขอแบบโมเดลเดียว (`provider/model`) บน
  `/v1/chat/completions`, `/v1/messages` และ `/v1/responses` ส่วนคอมโบจะไม่ใช้ส่วนหัวนี้: ให้ตรึง
  บัญชีสำหรับแต่ละขั้นตอนของคอมโบผ่านการเชื่อมต่อของขั้นตอนนั้นแทน
- **การตรึงเป็นข้อกำหนดที่เคร่งครัด ไม่ใช่เพียงค่ากำหนดที่ต้องการ** ระบบจะใช้การเชื่อมต่อที่ตรึงไว้แต่เพียงรายการเดียว
  ความล้มเหลวภายในคำขอจะบันทึกช่วงพักการใช้งานของบัญชี แต่จะ **ไม่** สลับไปยัง
  บัญชีอื่นของผู้ให้บริการเดียวกัน
- **ช่วงพักการใช้งานและโควตาจะปลดการตรึง** ขณะที่การเชื่อมต่อที่ตรึงไว้อยู่ในช่วงพักการใช้งาน
  ใช้โควตาหมดแล้ว หรือถูกบล็อกโดยนโยบายโควตา คำขอภายหลังจะเปลี่ยนไปใช้การเชื่อมต่ออื่น
  ของผู้ให้บริการ เช่นเดียวกับทราฟฟิกที่ไม่ได้ตรึง
- **id ที่ไม่รู้จักหรือปิดใช้งานแล้วจะทำให้คำขอล้มเหลว** id ที่ไม่ได้อยู่ในพูลที่ใช้งานอยู่ของผู้ให้บริการ (ถูกลบ
  ปิดใช้งาน หรือเป็นของผู้ให้บริการรายอื่น) จะทำให้ไม่มีบัญชีที่มีสิทธิ์ใช้งาน ดังนั้นคำขอ
  จะล้มเหลวแทนที่จะถูกกำหนดเส้นทางไปยังที่อื่นโดยไม่มีการแจ้งเตือน

Claude Code ส่งส่วนหัวแบบกำหนดเองผ่าน `ANTHROPIC_CUSTOM_HEADERS` ให้ใส่ไว้ในบล็อก `env`
ของ `~/.claude/settings.json` หรือใน `.claude/settings.json` ระดับโปรเจกต์เพื่อตรึงบัญชีที่แตกต่างกัน
สำหรับแต่ละโปรเจกต์:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

แหล่งที่มา: `src/sse/handlers/chat.ts` (การอ่านส่วนหัว), `src/sse/services/auth.ts` และ
`src/sse/services/sessionAffinityPin.ts` (การปลดการตรึงและการตรวจสอบว่าไม่มีอยู่ในพูล)

> **ส่วนหัวข้อมูลเทเลเมทรีต้นทุน:** การตอบกลับที่สำเร็จแบบไม่สตรีมจะมีชุดข้อมูลเทเลเมทรีต้นทุน `X-OmniRoute-*` ด้วย — `X-OmniRoute-Response-Cost` (USD, ทศนิยมคงที่ 10 ตำแหน่ง; `0.0000000000` สำหรับรายการที่ไม่มีค่าใช้จ่าย/ไม่มีการกำหนดราคา), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` และ `X-OmniRoute-Fallback-Attempts` (เฉพาะเมื่อ > 0) รวมถึง `X-OmniRoute-Request-Id` และ `X-OmniRoute-Version` ส่วนหัวเหล่านี้จะถูกส่งโดยการเติมข้อความแชต, `/v1/responses`, `/v1/messages` **และเอนด์พอยต์สื่อ** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` และ `/v1/moderations` (มีค่าใช้จ่าย `0` เสมอ) ต้นทุนสื่อจะคำนวณตามแต่ละโมดาลิตี (ต่อภาพ ต่อวินาที ต่ออักขระ หรือต่อหน่วยการค้นหา) เมื่อมีข้อมูลราคา มิฉะนั้นจะเป็น `0` (ทำงานต่อโดยไม่หยุด)

> **ความหมายของต้นทุนเมื่อพบข้อมูลในแคช:** เมื่อพบข้อมูลในแคชเชิงความหมาย (`X-OmniRoute-Cache-Hit: true`) จะไม่มีการเรียกบริการต้นทาง ดังนั้น `X-OmniRoute-Response-Cost` จะเป็น `0.0000000000` (ต้นทุน **ส่วนเพิ่ม** ในการให้บริการจากแคช) ต้นทุนเดิม/ต้นทุนที่ควรจะเกิดขึ้นจะถูกรายงานแยกต่างหากใน `X-OmniRoute-Cost-Saved` ระบบที่ใช้ข้อมูลเพื่อการเรียกเก็บเงินควรรวมค่า `X-OmniRoute-Response-Cost` (การพบข้อมูลในแคชไม่มีค่าใช้จ่าย) ส่วนการวิเคราะห์แคชสามารถรวมค่า `X-OmniRoute-Cost-Saved` ได้

## การเช่าเซสชันแบบจัดการที่ใช้เฉพาะราย

การเช่าเซสชันแบบจัดการที่ใช้เฉพาะรายเป็นสัญญาการกำหนดเส้นทางแบบเลือกใช้และไม่ขึ้นกับไคลเอนต์ โดยเจ้าของที่ใช้งานอยู่หนึ่งราย
จะถือครองการเชื่อมต่อ OmniRoute ที่มีสิทธิ์หนึ่งรายการ สัญญานี้ไม่ได้เช่าโมเดล ไม่ต้องใช้ OAuth ไม่ระบุ
ไคลเอนต์ใดโดยเฉพาะ และไม่บังคับให้ใช้ผู้ให้บริการรายใดโดยเฉพาะ

คีย์ API ที่ใช้ยืนยันตัวตนต้องมีขอบเขต `lease:exclusive` และรายการ
`allowedConnections` ที่ระบุไว้อย่างชัดเจนและไม่ว่างเปล่า ขอบเขตการเปลี่ยนแปลงฐานข้อมูลจะบังคับใช้ทั้งสองฟิลด์ร่วมกันเมื่อสร้างคีย์
และเมื่ออัปเดตบางส่วน

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

การตอบกลับเมื่อขอสิทธิ์ ต่ออายุ และปล่อยสิทธิ์สำเร็จจะแสดงการประทับเวลา `state` และค่า
`generation` ที่เป็นจำนวนบวกอย่างถูกต้อง แต่จะไม่เปิดเผยการเชื่อมต่อที่เลือกหรือข้อมูลประจำตัว การต่ออายุและการปล่อยสิทธิ์จะส่ง
generation ในเนื้อหา JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

เจ้าของสัญญาเช่าที่ใช้งานอยู่สามารถร้องขอเมทาดาทาสำหรับการแสดงผลที่ปลอดภัยต่อความเป็นส่วนตัวสำหรับการผูกการเชื่อมต่อปัจจุบันได้อย่างชัดเจน:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

การดำเนินการสถานะแบบเลือกใช้นี้ถูกควบคุมโดยเจ้าของแบบทึบ คีย์ API แบบจัดการที่ผ่านการยืนยันตัวตน และ
generation ที่ใช้งานอยู่ซึ่งตรงกันทุกประการ ภายในธุรกรรมฐานข้อมูลเดียว `displayName` เป็นเพียงชื่อการเชื่อมต่อที่กำหนดค่าไว้
และตัดช่องว่างส่วนเกินออกแล้ว โดยจะเป็น `null` เมื่อไม่มีชื่อที่กำหนดค่าไว้อย่างปลอดภัย OmniRoute จะไม่นำ
อีเมลหรือข้อมูลระบุตัวตนของบัญชีที่สร้างขึ้นมาใช้แทน ค่าผู้ให้บริการเป็นป้ายกำกับสำหรับการแสดงผลที่ไม่ละเอียดอ่อน และจะไม่เป็น
ตัวระบุผู้ให้บริการที่เข้ากันได้ซึ่งสร้างขึ้น ข้อมูลประจำตัว โทเค็น คุกกี้ ID การเชื่อมต่อหรือคีย์ API แบบดิบ
แฮชของเจ้าของ ข้อมูลลับสำหรับการควบคุม generation และข้อมูลการกำหนดเส้นทางภายในจะไม่ถูกรวมไว้

การค้นหาด้วยคีย์ผิด เจ้าของผิด generation เก่า ข้อมูลที่ไม่มี หมดอายุ ถูกปล่อย หรือถูกทำให้ใช้งานไม่ได้
จะส่งคืนข้อผิดพลาด `409 LEASE_FENCE_STALE` แบบเดียวกันทั้งหมดโดยไม่มีเมทาดาทาการเชื่อมต่อ ไคลเอนต์ที่ได้รับการตอบกลับให้รอความจุจะไม่มีการผูกการเชื่อมต่อที่ใช้งานอยู่ให้ตรวจสอบ เมื่อการกำหนดเส้นทางเปลี่ยนสัญญาเช่าที่ใช้งานอยู่
generation เดิมจะยังคงใช้ได้ และสถานะจะส่งคืนการผูกการเชื่อมต่อใหม่แบบอะตอมมิก โดยจะไม่ส่งคืนรายการเก่า
ไคลเอนต์ที่มีอยู่จะไม่เปลี่ยนแปลง เนื่องจากการตอบกลับของการขอสิทธิ์ การต่ออายุ การปล่อยสิทธิ์ และการรอ
จะยังคงใช้โครงสร้างเดิม

สัญญาฝั่งเซิร์ฟเวอร์นี้ไม่เปลี่ยนแปลง `/status` มาตรฐานของ OpenAI Codex ปัจจุบัน Codex มาตรฐานรายงาน
ผู้ให้บริการโมเดลและสถานะการยืนยันตัวตน/บัญชีในตัว แต่ไม่แสดงเมทาดาทาบัญชีของ
ผู้ให้บริการแบบกำหนดเองใดๆ การผสานรวมกับไคลเอนต์ในอนาคตต้องเรียกใช้การดำเนินการนี้และตัดสินใจว่าจะ
แสดง `connection.displayName` อย่างไร

จากนั้นคำขออนุมานแบบจัดการทุกคำขอจะส่งเฮดเดอร์ควบคุมทั้งสองรายการ:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

เจ้าของและ generation ที่ตรงกันทุกประการ การเชื่อมต่อที่ใช้งานอยู่ และคีย์ API ที่ผ่านการยืนยันตัวตนจะถูกตรวจสอบเงื่อนไขควบคุม
ทันทีก่อนการพยายามส่งคำขอไปยังต้นทางแต่ละครั้งที่รองรับ การนำเจ้าของและ generation มาใช้ซ้ำกับคีย์อื่นจะล้มเหลว แม้ว่า
คีย์นั้นจะอนุญาตการเชื่อมต่อเดียวกันก็ตาม เจ้าของแบบดิบจะไม่ถูกจัดเก็บถาวร บันทึกในล็อก เก็บไว้ใน
สแนปช็อตคำขอ หรือส่งต่อไปยังต้นทาง

การแข่งขันใช้ทรัพยากรชั่วคราวจะส่งคืน HTTP `429` พร้อม `Retry-After` และ:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

การตอบกลับนี้หมายความเพียงว่าชุดการเชื่อมต่อที่มีสิทธิ์ตามปกติไม่ว่างเปล่า และตัวเลือกที่ว่างทุกรายการ
ถูกครอบครองโดยสัญญาเช่าที่ใช้งานอยู่ของเจ้าของรายอื่น โมเดล/ผู้ให้บริการที่ไม่รองรับ ความไม่ตรงกันของนโยบาย ช่วงพักการใช้งาน โควตา
สถานะความพร้อม และความล้มเหลวด้านสิทธิ์ตามปกติอื่นๆ จะยังคงใช้การตอบกลับ OmniRoute เดิม

### `x-omniroute-compression`

ใช้แทนแผนการบีบอัดเป็นรายคำขอ มีลำดับความสำคัญสูงสุด โดยอยู่เหนือการแทนที่ของชุดการกำหนดเส้นทาง
โปรไฟล์ที่ใช้งานอยู่ การทริกเกอร์อัตโนมัติ และค่าเริ่มต้นของแผงควบคุม ค่าได้แก่:

| ค่า           | ผลลัพธ์                                                                                               |
| ------------- | ----------------------------------------------------------------------------------------------------- |
| `off`         | ไม่มีการบีบอัดสำหรับคำขอนี้                                                                           |
| `default`     | โปรไฟล์ค่าเริ่มต้นที่ได้จากแผงควบคุม (ไม่สนใจโปรไฟล์ที่ใช้งานอยู่) กลไกแบบสูญเสียข้อมูลจะยังคงปิดอยู่ |
| `safe`        | เฉพาะการขจัดข้อมูลซ้ำและการยุบช่องว่าง                                                                |
| `allow-lossy` | ใช้แผนของผู้ดำเนินการต่อไปสำหรับคำขอนี้ รวมถึงการสรุปและการเขียนรูปแบบใหม่                            |
| `engine:<id>` | กลไกเดียวเมื่อเปิดใช้งาน เช่น `engine:rtk` เป็นการเลือกใช้กลไกนั้นเป็นรายคำขอ                         |
| `<combo>`     | ชุดผสมที่มีชื่อ โดยจับคู่ตามชื่อ (ไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่) ก่อน แล้วจึงจับคู่ตาม ID              |

หมายเหตุ:

- ค่าที่ไม่รู้จักจะถูกละเว้น (คำขอจะไม่ถูกปฏิเสธ) และการแก้ไขค่าจะใช้ลำดับความสำคัญตามปกติของผู้ดำเนินการต่อไป
- หากมีชุดผสมหลายชุดที่ใช้ชื่อเดียวกัน ให้ส่ง **id** ของชุดผสมเพื่อให้การจับคู่เป็นแบบกำหนดแน่นอน
- ไม่สามารถเลือกชุดผสมที่มีชื่อเป็น `off` หรือ `default` ด้วยชื่อได้ (ระบบจะตีความคีย์เวิร์ดเหล่านั้นก่อน) ให้อ้างอิงชุดผสมดังกล่าวด้วย ID
- สวิตช์หลักของการบีบอัดเป็นเงื่อนไขบังคับ เมื่อปิดใช้งานการบีบอัดทั่วทั้งระบบ เฮดเดอร์นี้จะไม่สามารถเปิดใช้งานได้

แผนที่นำไปใช้จะถูกส่งกลับในเฮดเดอร์การตอบกลับ:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

โดย `<source>` เป็นค่าใดค่าหนึ่งจาก `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` หรือ `off`

ผู้ให้บริการที่รองรับ: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI

รหัสในแค็ตตาล็อกอยู่ในรูปแบบ `provider/model` (ตัวอย่าง: `jina-ai/jina-embeddings-v5-omni-small`) รหัสโมเดล Jina แบบไม่มีคำนำหน้าที่ปรากฏในรีจิสทรี (ตัวอย่างเช่น `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) สามารถถูกรีโซลฟ์ได้เช่นกัน การฝัง/จัดอันดับใหม่/จำแนกประเภท/แบ่งส่วนของ Jina จะใช้ข้อมูลรับรอง `jina-ai` จากแดชบอร์ดก่อน โดยจะใช้ `JINA_AI_API_KEY` เป็นทางเลือกสำรองเฉพาะเมื่อไม่มีคีย์จากแดชบอร์ด การ์ด `jina-reader` ใช้สำหรับ Reader / `r.jina.ai` เท่านั้น (`POST /v1/web/fetch`) และจะไม่ให้บริการการฝังหรือการจัดอันดับใหม่

โมเดลในรีจิสทรีที่ระบุว่ารองรับมัลติโมดัลยังยอมรับรายการแบบมีโครงสร้างที่เป็นกลางต่อผู้ให้บริการได้สูงสุด 32 รายการ
ประเภทรายการสื่อ ได้แก่ `text`, `image`, `audio`, `video` และ `document` ส่วน `source`
ของสื่อจะเป็น `{"type":"url","url":"https://..."}` หรือ
`{"type":"base64","data":"...","media_type":"..."}`

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
และนามแฝงของตระกูล `jina-ai/jina-embeddings-v5-omni` → omni-small) ยังยอมรับเอกสาร
EmbeddingsV5Request แบบเนทีฟของ Jina และ **ส่งต่อเอกสารเหล่านั้นโดยไม่มีการแก้ไข** ไปยัง `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ค่า `{ image | audio | video | pdf }` แบบเนทีฟอาจเป็น URL HTTPS สาธารณะ, URI แบบ `data:` หรือ
base64 ดิบ OmniRoute จะไม่แปลงออบเจ็กต์เหล่านั้นเป็นสตริงหรือดึงข้อมูลจาก URL รูปภาพแบบเนทีฟ — Jina จะดึง
สื่อสาธารณะด้วยตัวเอง ฟิลด์เพิ่มเติมของ Jina (`task`, `normalized`, `truncate`, `embedding_type`) จะถูก
ส่งต่อ ส่วน SKU ของ Jina ที่รองรับเฉพาะข้อความจะยังคงปฏิเสธเอกสารที่ไม่ใช่ข้อความ

ข้อจำกัดด้านความปลอดภัยและการรับส่งข้อมูล:

- URL ของสื่อระยะไกลต้องเป็น HTTPS สาธารณะ รายการมาตรฐาน `{type,source:url}` จะถูกดึง
  ที่ฝั่งเซิร์ฟเวอร์ (ตรวจสอบการเปลี่ยนเส้นทางซ้ำ, กำหนดเวลาหมดอายุ, จำกัดขนาด, ใช้ DNS สาธารณะ และ
  ตรึงการเชื่อมต่อ) และแทรกไว้ภายในก่อนเรียกผู้ให้บริการ รายการแบบเนทีฟของ Jina `{image:"https://..."}` จะถูกส่งต่อตามเดิม
  หลังผ่านการตรวจสอบ HTTPS สาธารณะแบบเดียวกัน โดย Jina จะเป็นผู้ดึง URL
- สื่อ base64 แบบอินไลน์จำกัดขนาดหลังถอดรหัสไว้ที่ 8 MiB ต่อรายการ และ 16 MiB รวมทั้งคำขอ

การแปลงรูปแบบสำหรับผู้ให้บริการ (รายการมาตรฐานจะไม่ถูกส่งต่อโดยไม่มีการเปลี่ยนแปลง):

- โมเดลมัลติโมดัลของ Jina: รายการระดับบนสุดแต่ละรายการจะกลายเป็นออบเจ็กต์หนึ่งรายการที่มีคีย์ตามโมดาลิตี
  (`text` / `image` / `audio` / `video` / `pdf`) โดยใช้ URI แบบ data สำหรับสื่ออินไลน์ และมีหนึ่งเวกเตอร์ต่อ
  รายการระดับบนสุด
- ตระกูล Gemini Embedding 2: อาร์เรย์ระดับบนสุดหนึ่งชุดจะกลายเป็นคำขอเนทีฟ
  `models/{model}:embedContent` หนึ่งรายการพร้อม `content.parts` (`text` หรือ `inline_data`)
- llama.cpp (`llama-cpp/<model>`, โมเดลใดก็ตามที่เซิร์ฟเวอร์ภายในโหลดไว้): รายการมาตรฐาน `text`
  จะกลายเป็นสตริงธรรมดา ส่วน `image` / `audio` / `video` แต่ละรายการจะกลายเป็นออบเจ็กต์
  `{"content": [part]}` หนึ่งรายการ โดยใช้ส่วนเนื้อหาแชตของ llama-server (`image_url`,
  `input_audio` พร้อมรูปแบบ `wav` / `mp3` / `flac`, `input_video`) กับข้อมูลอินไลน์ และมีหนึ่งเวกเตอร์
  ต่อรายการระดับบนสุด เซิร์ฟเวอร์ต้องทำงานด้วย `--embedding --mmproj …`; หากไม่มีโปรเจกเตอร์
  เซิร์ฟเวอร์จะปฏิเสธสื่อเอง ไม่รองรับ `document`
- โมเดลที่ไม่รู้จัก/ไดนามิกซึ่งไม่มีเมทาดาทาโมดาลิตีอย่างชัดเจนจะปฏิเสธอินพุตแบบมีโครงสร้างด้วย HTTP 400

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

ชุดโมเดล/โมดาลิตีที่ไม่รองรับจะส่งคืน HTTP 400 แทนการบังคับแปลงรายการ ฟิลด์ส่วนขยายที่ไม่ใช่อินพุต
ในคำขอสตริง/โทเค็นแบบเดิมจะยังคงถูกส่งต่อโดยไม่มีการเปลี่ยนแปลง

```bash
# แสดงรายการโมเดลเวกเตอร์ฝังทั้งหมด
GET /v1/embeddings
```

## การสร้างรูปภาพ

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ผู้ให้บริการที่พร้อมใช้งาน ได้แก่ OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (ภายในเครื่อง), ComfyUI (ภายในเครื่อง)

`n` จะส่งคืนรูปภาพจำนวน `n` รูปใน `data[]` สำหรับผู้ให้บริการที่ upstream API ส่งคืนรูปภาพหนึ่งรูปต่อการเรียกหนึ่งครั้ง
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) ระบบจะเรียก upstream แยกกันจำนวน `n` ครั้ง โดยมีการเรียกที่กำลังดำเนินการพร้อมกันไม่เกิน 4 ครั้ง
ค่า `seed` แบบคงที่จะถูกเพิ่มตามดัชนีของการเรียก (`seed`, `seed + 1`, …) ทำให้รูปภาพแตกต่างกันแต่ยังคง
สร้างซ้ำได้อย่างสอดคล้อง ค่า `n` ถูกจำกัดไว้สูงสุดที่ 10 คำขอทั้งหมดจะล้มเหลวหากมีการเรียกใดล้มเหลว รายการ
รูปแบบ fan-out อยู่ใน `SINGLE_IMAGE_FANOUT_FORMATS` ที่
`open-sse/handlers/imageGeneration/fanOut.ts`

ZenMux ใช้การเชื่อมต่อ API key ที่มีอยู่เดิมซ้ำ และรองรับคำนำหน้า `zenmux/` หรือ `zm/`:

- `zenmux/openai/gpt-image-2` ใช้ OpenAI Images API ของ ZenMux ตัวเลือกประกอบด้วย `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` และ `response_format`
- ผู้เผยแพร่รายอื่น เช่น `zm/meta/muse-image-1.0` จะใช้ endpoint `:predict` ของ Vertex AI จาก ZenMux
  โดย `n` แมปไปยัง `sampleCount`, `aspect_ratio` ไปยัง `aspectRatio` และ `image_size`
  (`1K`, `2K`, `4K`) ไปยัง `sampleImageSize` ค่า `size` แบบพิกเซลจะระบุเพียงอัตราส่วนภาพ
  โดยไม่ได้รับประกันขนาดพิกเซล อัตราส่วน ความละเอียด และจำนวนที่รองรับจะแตกต่างกันไปตามโมเดล
- `zm/inclusionai/ming-image-0.1-design` จะเลือกขนาดของตัวเอง ให้ละเว้น `size`,
  `aspect_ratio` และ `image_size`; การระบุค่าเหล่านี้อย่างชัดเจนจะทำให้ได้รับ HTTP 400 สามารถขอรูปแบบ PNG, JPEG และ WebP
  ได้ด้วย `output_format`

การผสานรวมนี้รองรับการสร้างรูปภาพจากข้อความ ไม่รองรับการแก้ไขรูปภาพอ้างอิง เอาต์พุตจาก Vertex
จะถูกปรับให้อยู่ในรูปแบบ `data[].b64_json`; `response_format: "url"` จะส่งคืน URL แบบ HTTPS จาก upstream
หรือ URL ข้อมูลแบบ base64 เมื่อมีเพียงไบต์ของรูปภาพ เอาต์พุตที่ว่างเปล่าหรือถูกกรอง
จะส่งคืนข้อผิดพลาดแทนผลลัพธ์สำเร็จที่ว่างเปล่า การเข้าถึงโมเดลขึ้นอยู่กับบัญชี ZenMux
ดู [Vertex API ของ ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) และ
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)

```bash
# แสดงรายการโมเดลรูปภาพทั้งหมด
GET /v1/images/generations
```

## OCR เอกสาร

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` ใช้เลือกผู้ให้บริการ OCR ผ่านคำนำหน้า `provider/model`; รหัสโมเดลแบบไม่มีคำนำหน้า (เช่น
`mistral-ocr-latest`) จะถูกจับคู่กับผู้ให้บริการที่ลงทะเบียนไว้ และหากละเว้น `model` ระบบจะใช้
Mistral (`mistral-ocr-latest`) เป็นค่าเริ่มต้น ผู้ให้บริการที่ลงทะเบียนไว้ (`open-sse/config/ocrRegistry.ts`):

| รหัสผู้ให้บริการ              | รหัสโมเดล            | ค่า `model`                                                               | หมายเหตุ                                                                                                           |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (หรือ `mistral-ocr-latest` แบบไม่มีคำนำหน้า) | ทำงานแบบซิงโครนัส — ส่งคืนการตอบกลับโดยตรงจากการเรียก upstream เพียงครั้งเดียว                                     |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                               | upstream แบบอะซิงโครนัส (`analyze` + การ poll) — ดูรายละเอียดด้านล่าง                                              |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                   | ทำงานแบบซิงโครนัสผ่าน endpoint พาร์ทเนอร์ `openapi/chat/completions` ของ Vertex AI — ดูการยืนยันตัวตน/URL ด้านล่าง |

ผู้ให้บริการทั้งสามรายตอบกลับด้วย body รูปแบบเดียวกับ Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### ขั้นตอนการ poll ของ Azure Document Intelligence

API `analyze` ของ Azure Document Intelligence ทำงานแบบอะซิงโครนัส โดยคำขอเริ่มต้นจะส่งคืนเฮดเดอร์
`Operation-Location` แทน body และต้อง poll เพื่อรับผลลัพธ์ ตัว handler
(`open-sse/handlers/ocr.ts`) จะ poll URL นั้นทุกหนึ่งวินาที สูงสุด 30 ครั้ง และหยุดทันที (ไม่
poll ต่อ) เมื่อการตอบกลับจากการ poll ไม่เป็น `ok` หรือมีสถานะ `"failed"` และจะส่งคืน `504` หาก
การดำเนินการยังคงทำงานอยู่หลังจากใช้จำนวนครั้งที่อนุญาตหมดแล้ว การตอบกลับสุดท้ายจาก Azure
จะถูกปรับให้อยู่ในโครงสร้าง `pages`/`markdown` เดียวกับที่ Mistral ใช้ก่อนส่งคืนให้
ผู้เรียก ดังนั้นโค้ดฝั่งไคลเอนต์จึงไม่จำเป็นต้องจัดการผู้ให้บริการรายนี้เป็นกรณีพิเศษ

### การยืนยันตัวตนและการกำหนด endpoint ของ Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` ใช้การยืนยันตัวตน Vertex AI แบบเดียวกับที่ OmniRoute รองรับอยู่แล้วสำหรับ
ทราฟฟิกแชต/รูปภาพ (`open-sse/executors/vertex.ts`) โดย API key ของการเชื่อมต่อจะเป็นข้อมูลรับรอง
Service Account JSON (ซึ่งจะถูกแลกเป็นโทเค็นการเข้าถึง OAuth อายุสั้นผ่านขั้นตอน JWT-bearer)
หรือเป็นโทเค็นการเข้าถึง OAuth ที่ออกไว้แล้วและนำมาใช้โดยตรง URL ของ endpoint upstream คือ
endpoint พาร์ทเนอร์ `openapi/chat/completions` แบบทั่วไปของ Vertex ซึ่งสร้างขึ้นจากโปรเจกต์และ
ภูมิภาคของการเชื่อมต่อ — ค่า `providerSpecificData.project`/`providerSpecificData.region` ที่ระบุไว้อย่างชัดเจนจะมีสิทธิ์เหนือกว่าเสมอ
มิฉะนั้น โปรเจกต์จะได้มาจาก `project_id` ใน Service Account JSON และภูมิภาค
จะใช้ `us-central1` เป็นค่าเริ่มต้น การกำหนดค่าทั้งสองเกิดขึ้นใน `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) และถูกใช้งานโดย
`src/app/api/v1/ocr/route.ts` ก่อนส่งต่อไปยัง `handleOcr`

### ราคาของโมเดล (`pricing`)

รายการจะมีออบเจ็กต์ `pricing` เมื่อ OmniRoute ทราบราคาของโมเดล ราคานี้มาจากตารางราคา
ที่ใช้ในการคำนวณต้นทุน ได้แก่ ค่าเริ่มต้นในตัว ราคาที่ซิงค์ และค่าที่กำหนดทับผ่าน
`/api/pricing` ราคาเหล่านี้เป็นราคาปลีก ดังนั้นผู้ให้บริการแบบสมัครสมาชิกจึงแสดง
ราคาต่อโทเค็นด้วย

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| ฟิลด์                                                           | หน่วย                      | หมายเหตุ                                                                                                                             |
| --------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD ต่อโทเค็น, สตริงทศนิยม | เข้ากันได้กับ OpenRouter และไม่ใช้รูปแบบเลขยกกำลัง ฟิลด์แคชทั้งสองจะปรากฏเฉพาะเมื่อมีราคาสำหรับแคช                                   |
| `input`, `output`, `cached`, `cache_creation`                   | USD ต่อ 1M โทเค็น, ตัวเลข  | ฟิลด์จากแค็ตตาล็อกเวอร์ชันก่อนหน้า ซึ่งเก็บไว้สำหรับไคลเอนต์เดิม `reasoning` และ `long_context` จะปรากฏด้วยเมื่อแถวราคามีค่าเหล่านี้ |

- **คอมโบ** ใช้ราคาของเป้าหมายแรกที่มองเห็นได้ คอมโบ `auto/*` ในตัวจะเลือก
  เป้าหมายขณะประมวลผลคำขอ จึงไม่มี `pricing`
- **โมเดลฟรี** แสดง `"0"` (และ `0`) เมื่อราคาเป็นศูนย์ โมเดลที่ไม่มีแถวราคา
  จะแสดง `"0"` เช่นกันเมื่อแค็ตตาล็อกระบุว่าเป็นโมเดลฟรี (`free: true`) หรือมีรายชื่ออยู่ใน
  แค็ตตาล็อกโมเดลฟรีในตัว
- **ไม่ทราบราคา:** รายการนั้นไม่มีคีย์ `pricing`
- **ผู้ให้บริการที่คิดค่าบริการตามเครดิต** (เช่น Kiro) เรียกเก็บเงินต่อคำขอแทนที่จะคิดตามโทเค็น
  รายการของผู้ให้บริการเหล่านี้จะคงฟิลด์ตัวเลขต่อ 1M แบบเดิมไว้ และไม่มีฟิลด์สตริงต่อโทเค็น
- **ตัวแปร** (ID ระดับความพยายามในการให้เหตุผล นามแฝงแบบไม่ใช้การคิด มิเรอร์สำหรับการค้นพบและเกตเวย์)
  จะคัดลอกราคาของโมเดลที่ตัวแปรเหล่านั้นกำหนดเส้นทางไป
- ฟิลด์เหล่านี้มีเฉพาะอัตราพื้นฐานเท่านั้น ระดับบริบทแบบยาว (ฟิลด์ตัวเลข `long_context`) และ
  ตัวคูณระดับบริการ (เช่น Codex แบบ fast หรือ flex) จะไม่เปลี่ยน `prompt` หรือ
  `completion`
- ออบเจ็กต์นี้เหมือนกันสำหรับการยืนยันตัวตนทุกรูปแบบ รวมถึงคำขอในรูปแบบ Anthropic
  ที่ใช้ `x-api-key` และ `anthropic-version` (การตอบกลับยังคงเป็น `{ "object": "list",
"data": [...] }`) การใช้งาน: `src/app/api/v1/models/catalogPricing.ts`

### คำนำหน้า ID ของโมเดล (`?prefix=`)

โมเดลส่วนใหญ่จะแสดงภายใต้ **คำนำหน้าของผู้ให้บริการ** คำนำหน้าที่ได้รับจะถูกควบคุมโดย
แฟล็กฟีเจอร์ `MODELS_CATALOG_PREFIX_MODE` และสามารถกำหนดทับได้ **แยกตามคำขอ** ด้วย
พารามิเตอร์คิวรี ซึ่งมีประโยชน์สำหรับไคลเอนต์ที่ต้องการรายการที่เรียบง่ายโดยไม่ต้องเปลี่ยนการตั้งค่า
ทั่วทั้งเซิร์ฟเวอร์สำหรับผู้ใช้อื่น:

```bash
GET /v1/models?prefix=alias        # หนึ่ง ID ต่อโมเดล — คำนำหน้านามแฝงแบบสั้น
GET /v1/models?prefix=dual         # ทั้งสองรูปแบบ (ค่าเริ่มต้นของเซิร์ฟเวอร์)
GET /v1/models?prefix=canonical    # เฉพาะคำนำหน้า ID ผู้ให้บริการแบบเต็ม
```

| โหมด        | ส่งออก                                                    | หมายเหตุ                                                                                                                                                                                 |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **และ** `claude/claude-sonnet-4-6` | **ค่าเริ่มต้น** ID ทั้งสองจะกำหนดเส้นทางไปยังโมเดลเดียวกัน โดยเก็บไว้เพื่อให้การกำหนดค่าไคลเอนต์ที่ฮาร์ดโค้ดรูปแบบใดรูปแบบหนึ่งยังคงทำงานได้ ทำให้แค็ตตาล็อกมีขนาดเพิ่มขึ้นประมาณสองเท่า |
| `alias`     | `cc/claude-sonnet-4-6`                                    | หนึ่งรายการต่อโมเดล ผู้ให้บริการที่ไม่มีนามแฝงแยกต่างหากจะยังคงส่งออกรายการของตน จึงไม่มีข้อมูลใดสูญหาย                                                                                  |
| `canonical` | `claude/claude-sonnet-4-6`                                | หนึ่งรายการต่อโมเดลภายใต้คำนำหน้า ID ผู้ให้บริการแบบเต็ม ผู้ให้บริการที่ไม่มีนามแฝงแยกต่างหาก (เช่น `antigravity/…`, `agy/…`) จะส่งออก ID เดียวของตนที่นี่ด้วย จึงไม่มีข้อมูลใดสูญหาย    |

นอกจากนี้ ยังสามารถระบุมิเรอร์ในโหมด `dual` ได้โดยไม่ต้องใช้พารามิเตอร์คิวรี เนื่องจากมิเรอร์จะมีฟิลด์ `parent`
ที่ชี้ไปยัง ID หลัก

ไคลเอนต์ที่แสดงตัวเลือกโมเดลควรส่งคำขอด้วย `?prefix=alias` ซึ่งเป็นวิธีที่
[ส่วนขยาย OmniCopilot สำหรับ VS Code](../guides/VSCODE-COPILOT.md) ใช้

### ตัวกรองการค้นพบ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` รองรับตัวกรองการค้นพบแบบเลือกใช้ หากไม่ระบุตัวกรองใดเลย การตอบกลับจะ
ไม่เปลี่ยนแปลง ตัวกรองเหล่านี้จะจำกัดแค็ตตาล็อกที่ผู้เรียกมองเห็นอยู่แล้วให้แคบลง (ใช้สิทธิ์ของคีย์ API ก่อน)
และจะทำงานก่อนการแบ่งหน้าด้วย `limit` / `after` ในรูปแบบ OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ความสามารถทุกรายการที่ระบุต้องเป็นจริง
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` ของแค็ตตาล็อก; แถวที่ไม่มีค่านี้จะเป็น `chat`
GET /v1/models?q=sonnet&limit=10                           # จับคู่ ID หรือชื่อโดยไม่คำนึงถึงตัวพิมพ์เล็กและตัวพิมพ์ใหญ่
```

| พารามิเตอร์   | ค่า                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | จำนวนเต็มที่ไม่เป็นลบ ซึ่งนำไปเปรียบเทียบกับ `context_length`                                       |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 อักขระ                                                                                        |

ค่าที่ไม่รู้จัก หรือ `min_context` ที่ไม่ใช่จำนวนเต็มที่ไม่เป็นลบ (เช่น `1.5`)
จะส่งคืน HTTP `400` และข้อความจะแสดงรายการค่าที่ถูกต้อง การนำไปใช้งาน:
`src/app/api/v1/models/catalogFilters.ts`

### รายการโมเดลที่คัดเลือก (`POST /v1/models/query`)

`POST /v1/models/query` ส่งคืนรายการแบบสั้นที่ให้ผลลัพธ์คงที่จากแค็ตตาล็อกเดียวกัน โดยใช้การ
ตรวจสอบสิทธิ์และการมองเห็นต่อคีย์แบบเดียวกับ `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ทุกฟิลด์เป็นตัวเลือก `capabilities` และ `exclude` รับค่าเป็นอาร์เรย์หรือสตริงที่คั่นด้วยจุลภาค;
`max_output` จะนำไปเปรียบเทียบกับ `max_output_tokens` ผลลัพธ์จะเรียงตาม `owned_by` แล้วตามด้วย `id`
ค่าเริ่มต้นของ `limit` คือ `20` และค่าที่มากกว่า `100` จะถูกจำกัดไว้ที่ `100` JSON ที่ไม่ถูกต้อง ฟิลด์ที่ไม่รู้จัก
หรือค่าที่ไม่ถูกต้องจะส่งคืน HTTP `400`

### โมเดลแชตที่ซ่อนเป็นรายโมเดล

โมเดลที่ทำเครื่องหมายเป็น **ซ่อนอยู่** ในหน้าผู้ให้บริการจะถูกนำออกจากแค็ตตาล็อกและถูกปฏิเสธ
ด้วย HTTP `404` / `model_not_found` เมื่อมีการร้องขออย่างเจาะจง การตรวจสอบนี้ใช้ผู้ให้บริการ
และโมเดลที่ผ่านการแก้ไขค่าแล้ว รวมถึงนามแฝงของผู้ให้บริการ คำนำหน้าโหนดของผู้ให้บริการที่เข้ากันได้ และ
ค่าเริ่มต้นของการเชื่อมต่อ คอมโบจะข้ามเป้าหมายที่ซ่อนอยู่และสามารถใช้โมเดลร่วมลำดับชั้นที่มองเห็นได้; เมื่อไม่มี
เป้าหมายที่เรียกใช้งานได้เหลืออยู่ ระบบจะส่งคืนรหัสข้อผิดพลาดเดียวกัน การยกเลิกการซ่อนจะมีผลในคำขอถัดไป
การกำหนดการมองเห็นเฉพาะรูปภาพจะไม่ซ่อนโมเดลแชตที่มี ID เดียวกัน

การตั้งค่าโมเดลรายรายการนี้แยกจาก
[รายการอนุญาต/ปฏิเสธการเปิดเผยโมเดล](../routing/MODEL_EXPOSURE_LIST.md) ซึ่งกรองการแสดงโมเดลในแค็ตตาล็อก
และตัวเลือกสำหรับการกำหนดเส้นทางอัตโนมัติ โดยยังคงอนุญาตการส่งต่ออย่างเจาะจง สิทธิ์ของโมเดลสำหรับ API key
ยังคงมีผลอย่างเป็นอิสระ โหมดคำนำหน้าเริ่มต้นของแค็ตตาล็อกยังคงเป็น `dual`

### ตัวแปรโมเดลแบบไม่ใช้การคิด

สำหรับโมเดล Claude ที่รองรับการคิด `/v1/models` จะแสดงตัวแปรแบบ **ไม่ใช้การคิด** เพิ่มเติมด้วย โดย ID จะมีคำนำหน้าเป็น `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

การเลือก ID นี้ (เช่น ในการกำหนดค่า Claude Code ที่แนบบล็อก `thinking` เสมอ) จะถูกแก้ไขกลับไปเป็น `<provider>/<model>` จริงโดยระงับการใช้เหตุผล — ใช้ `thinking:{type:"disabled"}` บนเส้นทาง `/v1/messages` หรือตัดฟิลด์ `reasoning`/`reasoning_effort` ออกบนเส้นทาง `/v1/chat/completions` ตัวแปรนี้จะแสดงเฉพาะสำหรับโมเดลตระกูล Claude ที่รองรับการคิด **และ** ยอมรับ `disabled` (ดังนั้น ตัวอย่างเช่น โมเดลที่รองรับเฉพาะโหมดปรับตัวและปฏิเสธ `disabled` จะไม่ถูกรวมไว้) ผู้ดูแลระบบสามารถบังคับเปิดหรือปิดตัวแปรนี้เป็นรายโมเดลผ่าน `ModelSpec.noThinkingAlias`

## การสร้างเสียงด้วย ElevenLabs

กำหนดค่าการเชื่อมต่อผู้ให้บริการ `elevenlabs` ใน OmniRoute ด้วยคีย์ API ของ ElevenLabs
ไคลเอนต์ยืนยันตัวตนด้วยคีย์ **OmniRoute** ของตน (`Authorization: Bearer $OMNIROUTE_API_KEY`);
เกตเวย์จะส่งคีย์ผู้ให้บริการที่จัดเก็บไว้ในรูปแบบ `xi-api-key` ห้ามส่งคีย์ ElevenLabs
เป็น bearer token ของเกตเวย์

| เมธอด | พาธ                         | การตอบกลับ                                   | หมวดหมู่ปลายทางคีย์ API |
| ----- | --------------------------- | -------------------------------------------- | ----------------------- |
| POST  | `/v1/sound-generation`      | ไบต์เสียงแบบเนทีฟ                            | `elevenlabs`            |
| POST  | `/v1/music`                 | ไบต์เสียงแบบเนทีฟ                            | `music`                 |
| POST  | `/v1/music/stream`          | ไบต์เสียงแบบสตรีม                            | `music`                 |
| POST  | `/v1/music/detailed`        | เสียงแบบ multipart และแผนการประพันธ์แบบเนทีฟ | `music`                 |
| POST  | `/v1/music/detailed/stream` | ข้อมูลเมตา SSE และส่วนย่อยเสียงแบบเนทีฟ      | `music`                 |
| POST  | `/v1/music/plan`            | แผนการประพันธ์ JSON                          | `music`                 |

ปลายทางเหล่านี้เสริมเส้นทาง `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` และ `/v1/speech-to-text` ที่มีอยู่แล้ว ฟิลด์ JSON
และพารามิเตอร์คิวรีแบบเนทีฟ เช่น `output_format` และ `enable_logging` จะยังคงเดิม
การตอบกลับจาก `/v1/music/detailed` จะคงขอบเขต multipart ไว้ ให้แยกวิเคราะห์เป็น multipart
`/v1/music/detailed/stream` ส่งคืน `text/event-stream` พร้อมข้อมูลเมตาการประพันธ์และ
ส่วนย่อยเสียงแบบ base64 ในเหตุการณ์ SSE เส้นทางทั้งหกรองรับคำขอ CORS preflight

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# เอฟเฟกต์เสียงสั้น ระยะเวลา: 0.5 ถึง 30 วินาที
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# ระยะเวลาของเพลงระบุเป็นมิลลิวินาที: 3000 ถึง 600000
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ใช้ `/v1/music/stream` กับเนื้อหา JSON เดียวกันเพื่อส่งเสียงแบบทยอย การประพันธ์
ยอมรับ `prompt` หรือ `composition_plan` อย่างใดอย่างหนึ่งเท่านั้น ส่วน `/v1/music/plan` ต้องมี `prompt`
และอาจรับ `source_composition_plan` เพิ่มเติมได้ สคีมาแบบเนทีฟจะคงฟิลด์เพิ่มเติม
ของผู้ให้บริการไว้ เพื่อให้เวอร์ชันแผนการประพันธ์และตัวเลือกการปรับแต่งแบบละเอียดถูกส่งไปถึง ElevenLabs

ปลายทางรวม `/v1/music/generations` ยังยอมรับ `elevenlabs/music_v1`,
`elevenlabs/music_v2` และ `elevenlabs/music_v2_5` เมื่อมีการเชื่อมต่อ ElevenLabs ที่ใช้งานอยู่
โมเดลเหล่านี้จะแสดงในแค็ตตาล็อกเพลง ปลายทางนี้ส่งคืน
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ฟิลด์ `duration` มีหน่วยเป็น
วินาทีและแมปไปยัง `music_length_ms` โดย `music_length_ms` ที่ระบุอย่างชัดเจนจะมีลำดับความสำคัญสูงกว่า
`instrumental` แมปไปยัง `force_instrumental` โดยฟิลด์แบบเนทีฟจะมีลำดับความสำคัญสูงกว่า
ใช้ปลายทางสตรีมแบบเนทีฟสำหรับการสตรีม และใช้ปลายทางการประพันธ์แบบเนทีฟ
สำหรับคำขอที่ขับเคลื่อนด้วยแผนการประพันธ์เพียงอย่างเดียว

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

ข้อจำกัดด้านปลายทาง โมเดล งบประมาณ และการเชื่อมต่อจะถูกบังคับใช้ก่อนเรียกใช้ upstream เส้นทาง
แบบเนทีฟจะส่งคืนรหัสสถานะและเนื้อหาข้อผิดพลาดจาก upstream โดยไม่เปลี่ยนแปลง รวมถึง `402` สำหรับข้อจำกัด
ของแพ็กเกจ และ `429` สำหรับขีดจำกัดโควตา ส่วนหัว `character-cost`, `song-id`, `request-id` และ `retry-after`
จะยังคงอยู่เมื่อมีให้ใช้งาน ยอดเครดิตฟรีไม่ได้รับประกันว่าจะเข้าถึงโมเดลเพลง
รูปแบบเอาต์พุต หรือฟีเจอร์ API ทุกรายการได้ โดย ElevenLabs จะเป็นผู้พิจารณาสิทธิ์สำหรับแต่ละคำขอ
ปลายทางรวมจะคงรหัสสถานะข้อผิดพลาดไว้ในโครงสร้างข้อผิดพลาดมาตรฐานของ OmniRoute

สัญญา upstream: [เอฟเฟกต์เสียง](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[การประพันธ์เพลง](https://elevenlabs.io/docs/api-reference/music/compose) และ
[รายละเอียดเพลงแบบสตรีม](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)

เส้นทาง POST ทั้งหมดใช้รูปแบบเดียวกัน: `Bearer your-api-key` + เนื้อหา JSON ที่ตรวจสอบความถูกต้องด้วย Zod (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` ฯลฯ โปรดดู `src/shared/validation/schemas.ts`) ระบบจะส่งคืน 4xx เมื่อการตรวจสอบสคีมาล้มเหลว

สำหรับไคลเอนต์ที่ไม่สามารถแนบ `Authorization: Bearer ...` ได้ OmniRoute ยังรองรับ API key ใน URL ผ่านความเข้ากันได้ของสตริงคำค้นหา (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) หรือเอนด์พอยต์เฉพาะ `/api/v1/vscode/{token}/...` ที่อธิบายไว้ด้านล่าง

```bash
# จัดอันดับซ้ำ (ผู้ให้บริการในรีจิสทรีคลาวด์ หรือโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI ในรูปแบบ "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# จัดประเภทด้วย Jina (ข้อมูลประจำตัว Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# ตัวแบ่งส่วนของ Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# การค้นหาด้วย Jina (s.jina.ai; นามแฝงผู้ให้บริการ: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# การกลั่นกรอง
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — ส่งคืนเนื้อหา audio/mpeg (หรือรูปแบบที่ร้องขอ)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS ต้องระบุภาษาและเสียง: `language` มีค่าเริ่มต้นเป็น "en"; หากไม่ได้ระบุ
# voice หรือใช้ชื่อเสียงมาตรฐานของ OpenAI (alloy, nova, …) ระบบจะเปลี่ยนเป็น "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# การแก้ไขรูปภาพ (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# การสร้างวิดีโอ / เพลง (รหัสโมเดลที่มีคำนำหน้าผู้ให้บริการ)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **โหนดผู้ให้บริการ Rerank:** `POST /v1/rerank` จะกำหนดเส้นทางไปยังโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI ด้วย
> (oMLX, vLLM, Infinity, TEI ที่อยู่หลังเกตเวย์, …) โดยระบุที่อยู่ในรูปแบบ `<node-prefix>/<model>` โหนด
> ลูปแบ็ก (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ใช้งานได้เสมอ เช่นเดียวกับชื่อโฮสต์ที่
> ผู้ดำเนินการระบุไว้ใน `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (เช่น ชื่อบริการ Docker/Compose อย่าง
> `http://reranker:8080/v1` โดยระบบจะเรียกโหนดเหล่านี้โดยตรง และจะไม่ผ่าน `HTTP(S)_PROXY` หรือ
> พร็อกซีที่ตรึงไว้กับการเชื่อมต่อ) โหนดบนโฮสต์อื่นใด
> เช่น เครื่องใน LAN หรือเพียร์ Tailscale จะใช้งานได้เฉพาะเมื่อผู้ดำเนินการเปิดใช้แฟล็กฟีเจอร์
> `RERANK_REMOTE_PROVIDER_NODES` **และ** URL ฐานของโหนดผ่านนโยบาย URL ขาออกของผู้ให้บริการ
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)
> ขั้นตอน rerank ของกลไกหน่วยความจำจะเรียกเส้นทางนี้ผ่าน
> ลูปแบ็ก ดังนั้นกฎเดียวกันจึงใช้ควบคุม `rerankProviderModel` ในการตั้งค่าหน่วยความจำด้วย
>
> **รูปแบบเซิร์ฟเวอร์ภายในเครื่อง:** ระบบจะเรียกโหนดที่ `<base>/v1/rerank` และเมื่อได้รับ 404 จะเรียกที่ `<base>/rerank`
> (Infinity, TEI) เนื้อหาคำขอต้นทางจะมีทั้งรูปแบบการสะกดของ Cohere/OpenAI (`documents`,
> `return_documents`) และรูปแบบการสะกดของ TEI (`texts`, `return_text`) ส่วนการตอบกลับจากต้นทางจะถูก
> ปรับให้อยู่ในเอนเวโลปของ Cohere โดย TEI แบบเปลือย `[{index, score, text}]`, `{results: [{index, score}]}`
> จากเกตเวย์แบบบาง และรูปแบบ Voyage `{data: [...]}` ทั้งหมดจะถูกส่งกลับไปยังไคลเอนต์ในรูปแบบ
> `{results: [{index, relevance_score, document?}]}` โดยเรียงตามคะแนนและจำกัดจำนวนไว้ที่ `top_n`

> **การค้นหาโหนดผู้ให้บริการ:** โมเดลบนโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI จะปรากฏใน `GET /v1/models`
> ภายใต้คำนำหน้าของโหนด แถวที่ไม่มีข้อมูลเมตาของปลายทาง (โดยทั่วไปพบในรายการ `/v1/models` ภายในเครื่อง)
> จะสืบทอด `apiType` ของโหนด ดังนั้นโมเดลของโหนด `embeddings` จะเป็น `type: "embedding"` และโมเดลของ
> โหนด `rerank` จะเป็น `type: "rerank"` แทนที่จะใช้ค่าเริ่มต้นเป็นแชต ส่วน
> `supportedEndpoints` ที่ระบุไว้อย่างชัดเจนในแถวที่ซิงค์หรือเพิ่มด้วยตนเองจะยังคงมีลำดับความสำคัญเหนือกว่า

## API ไฟล์

เอนด์พอยต์ไฟล์ที่เข้ากันได้กับ OpenAI สำหรับอินพุต/เอาต์พุตแบบแบตช์และการอัปโหลดไฟล์ตามวัตถุประสงค์

| เมธอด  | พาธ                      | คำอธิบาย                                                                                                       |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | อัปโหลดไฟล์ (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — สูงสุด 512 MiB |
| GET    | `/v1/files`              | แสดงรายการไฟล์สำหรับคีย์ API ที่ผ่านการตรวจสอบสิทธิ์                                                           |
| GET    | `/v1/files/[id]`         | เรียกดูข้อมูลเมตาของไฟล์                                                                                       |
| DELETE | `/v1/files/[id]`         | ลบไฟล์                                                                                                         |
| GET    | `/v1/files/[id]/content` | สตรีมเนื้อหาไฟล์ดิบกลับไป                                                                                      |

**การตรวจสอบสิทธิ์:** คีย์ API แบบ Bearer — ไฟล์ถูกจำกัดขอบเขตแยกตามคีย์ API ผ่าน `getApiKeyRequestScope` คีย์
สามารถดู ดาวน์โหลด และลบได้เฉพาะไฟล์ของตนเอง ส่วนเซสชันแดชบอร์ดที่ไม่มีคีย์สามารถอ่านข้อมูลได้ทั้ง
อินสแตนซ์ ขณะที่ไฟล์ซึ่งไม่มีเจ้าของ (อัปโหลดแบบไม่ระบุตัวตนหรือผ่านเซสชันแดชบอร์ด) จะถูกปฏิเสธสำหรับผู้เรียกใช้ทุกคน
ที่ไม่ได้ใช้เซสชัน `GET /v1/files` จะปฏิเสธผู้เรียกใช้แบบไม่ระบุตัวตน — รวมถึงคีย์ที่ส่งมาแต่
ไม่สามารถจับคู่ได้ — ด้วย `401` แม้ว่า `REQUIRE_API_KEY=false` แทนที่จะแสดงรายการไฟล์ของ
ผู้เช่าทุกราย (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)

## API แบตช์

การประมวลผลแบบแบตช์ที่เข้ากันได้กับ OpenAI

| เมธอด  | พาธ                       | คำอธิบาย                                                                                                             |
| ------ | ------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | สร้างแบตช์ — เนื้อหาคำขอได้รับการตรวจสอบโดย `v1BatchCreateSchema` (`input_file_id`, `endpoint`, `completion_window`) |
| GET    | `/v1/batches`             | แสดงรายการแบตช์                                                                                                      |
| GET    | `/v1/batches/[id]`        | เรียกดูสถานะแบตช์ + `request_counts`                                                                                 |
| DELETE | `/v1/batches/[id]`        | ลบแบตช์ที่เสร็จสิ้น/ล้มเหลวแล้ว                                                                                      |

**การตรวจสอบสิทธิ์:** คีย์ API แบบ Bearer แบตช์ถูกจำกัดขอบเขตแยกตามคีย์ API ภายใต้กฎสามกรณีเดียวกับ

**รับรองความถูกต้อง:** ผู้ถือคีย์ API (`extractApiKey` + `isValidApiKey`) นโยบายการค้นหาบังคับใช้ผ่าน `enforceApiKeyPolicy`

### Exa และ Tavily `provider_options`

Exa และ Tavily อ่านฟิลด์เฉพาะผู้ให้บริการจากกระเป๋าเนมสเปซ: `provider_options.exa` (หรือ `provider_options["exa-search"]`) และ `provider_options.tavily` (หรือ `provider_options["tavily-search"]`) เฉพาะคีย์ด้านล่างเท่านั้นที่จะถูกส่งต่อ แต่ละรายการจะถูกตรวจสอบกับ Zod schema ของตัวเองใน `open-sse/handlers/search/providerOptionsPassthrough.ts` และคีย์ที่มีประเภทไม่ถูกต้องจะถูกละทิ้ง คีย์อื่นๆ จะถูกละเว้น รวมถึง auth, base URL, `stream` และ `outputSchema` ปุ่มแบนที่ใช้โดยผู้ให้บริการรายอื่น (`cx`, `depth`, ... ) ทำงานเหมือนเมื่อก่อน

| ผู้ให้บริการ | ฟิลด์ระดับบนสุด                                                                                                                                                                                                                                                                                                                                                           | ซ้อนกัน                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| สอบ          | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ดั้งเดิมแบน), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                                  | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` ถูกรวมเข้ากับ `{ text: true, highlights: true }` เริ่มต้น |
| ทาวิลี่      | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                       |

ช่องทั่วไปจะชนะเสมอ: `query`, `max_results`, `filters` (โดเมน), `country` และหัวข้อที่ได้มาจาก `search_type` บน Exa นั้น `search_type: "news"` จะเก็บ `category: "news"` ไว้ Tavily ยังยอมรับ `search_type: "finance"` (`topic: "finance"`)

ค่าใช้จ่ายในการค้นหา Firecrawl จะถูกบันทึกต่อบล็อกเริ่มต้นของผลลัพธ์ที่ส่งคืน 10 รายการ ที่ 0.002 ดอลลาร์ (2 เครดิต) ต่อบล็อกและอย่างน้อยหนึ่งบล็อกต่อการโทร ( [การเรียกเก็บเงินของ Firecrawl](https://docs.firecrawl.dev/billing) ): ผลลัพธ์ 11 รายการมีราคา 0.004 ดอลลาร์

ขณะนี้ `time_range` ทั่วไปเข้าถึงผู้ให้บริการทั้งสองรายแล้ว: Exa ได้รับ `startPublishedDate` (ISO timestamp) และ Tavily ได้รับ `start_date` (`YYYY-MM-DD`) วันที่ที่ชัดเจนใน `provider_options` จะแทนที่วันที่ที่แมปไว้

ผลลัพธ์ Exa เก็บ `id`, `highlight_scores`, `summary`, `subpages`, `entities` และ `extras` ใน `provider_raw` ผลลัพธ์ Tavily ให้ `images` และ `favicon`

ค่าใช้จ่ายในการค้นหาลิงก์อัปจะถูกบันทึกไว้ที่ 0.005 ดอลลาร์สำหรับ `depth` `fast` และ `standard` และ 0.05 ดอลลาร์สำหรับ `deep` ( [การกำหนดราคาลิงก์อัป](https://docs.linkup.so/pages/documentation/development/pricing) ) ไม่ว่า `depth` จะมาจาก `provider_options` หรือการตั้งค่าของการเชื่อมต่อก็ตาม

Exa `type: "lite"` (Exa 3.0) ยอมรับชุดฟิลด์ที่เล็กกว่าและปฏิเสธคำขอทั้งหมดเมื่อมีการตั้งค่าฟิลด์อื่น สำหรับ lite, `additionalQueries`, `systemPrompt` และทุกคีย์ `contents` ยกเว้น `text` และ `highlights` จะถูกละทิ้งก่อนการโทร `subpages`, `subpageTarget`, `highlights.numSentences` และ `highlights.highlightsPerUrl` ที่เลิกใช้แล้วจะไม่ถูกส่งต่ออีกต่อไป

การบัญชีต้นทุนเป็นแบบแฟลตรีจีสทรี `costPerQuery` ยกเว้น Exa ซึ่งเป็นไปตามราคาของ Exa เอง: 0.007 ดอลลาร์ต่อการเรียก `auto` (และ `fast` แบบเดิม) หรือ 0.004 ดอลลาร์สำหรับ `lite` (และ `instant` แบบเดิม) ครอบคลุม 10 ผลลัพธ์ $0.001 สำหรับผลลัพธ์เพิ่มเติมแต่ละรายการ และ 0.001 ดอลลาร์ต่อผลลัพธ์ที่ส่งคืนเมื่อตั้งค่า `contents.summary` Tavily ได้รับการบันทึกที่ 1 เครดิต ($0.008) สำหรับ `search_depth` `basic`, `fast` และ `ultra-fast` และ 2 เครดิต ($0.016) สำหรับ `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) ) การโทรด้วย `auto_parameters: true` ที่ Tavily อัปเกรดเป็นขั้นสูงจะยังคงบันทึกไว้ที่ 1 เครดิต

## Web Fetch API

แยกเนื้อหาจาก URL ผ่านผู้ให้บริการ web-fetch ที่กำหนดค่าไว้ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)

Parallel Extract (`parallel-search` ซึ่งใช้ API key เดียวกับ Parallel Search) ส่งคืนเฉพาะ
Markdown เท่านั้น — `format` อื่นใดจะได้รับสถานะ `400` — และจำกัดเนื้อหาไว้ที่ 100,000 อักขระ เมื่อ
ไม่สามารถแยกข้อมูลจากหน้าเป้าหมายได้ ระบบต้นทางจะรายงานปัญหาดังกล่าวภายใน HTTP 200;
OmniRoute จะแสดงผลเป็น `422` พร้อมข้อความคงที่

| เมธอด | พาธ             | คำอธิบาย                                                            |
| ----- | --------------- | ------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | ดึง/สแครป URL — เนื้อหา body ได้รับการตรวจสอบโดย `v1WebFetchSchema` |

**การยืนยันตัวตน:** Bearer API key (`extractApiKey` + `isValidApiKey`) บังคับใช้นโยบายผ่าน `enforceApiKeyPolicy`

**การสำรองที่คำนึงถึงโควตา (#8297):** เมื่อไม่ได้ระบุ `provider` อย่างชัดเจน ระบบจะไล่ตรวจสอบพูล
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ตาม
ลำดับความสำคัญคงที่
แบบใช้ผู้ให้บริการแรกให้เต็มก่อน — ผู้ให้บริการที่กำหนดค่าไว้แต่ถูกจำกัดอัตราจะถูกข้าม
แทนที่จะยุติคำขอทันที และความล้มเหลวจากระบบต้นทางที่ลองใหม่ได้หรือเกี่ยวข้องกับโควตา
(HTTP 429 เสมอ; 402/403 สำหรับโควตาแบบ Free Tier ของ Firecrawl/Tavily/TinyFish —
ไม่ใช้กับ Jina Reader และไม่ใช้กับคำขอไม่ถูกต้องแบบ 400 ทั่วไป) จะเปลี่ยนไปใช้
ผู้ให้บริการรายถัดไปที่ยังไม่เคยลองและมีข้อมูลรับรองในขณะประมวลผลคำขอ เมื่อผู้ให้บริการทุก
รายในพูลไม่พร้อมใช้งานแล้ว เอนด์พอยต์จะส่งคืน `429` รายการเดียว (พร้อมเฮดเดอร์ `Retry-After`)
แทน `400` แบบทั่วไปที่เคยใช้ เมื่อร้องขอ `provider` อย่างชัดเจน
จะ**ไม่มี**การสำรองโดยอัตโนมัติ — ผู้ให้บริการที่ระบุอย่างชัดเจนซึ่งถูกจำกัดอัตราหรือทำงานล้มเหลว
จะแสดงข้อผิดพลาดของตนเอง (`429` หากถูกจำกัดอัตรา มิฉะนั้นจะใช้สถานะจากระบบต้นทาง)

## การสตรีมผ่าน WebSocket

```bash
GET /v1/ws?handshake=1
```

ตรวจสอบแฮนด์เชกสำหรับการอัปเกรด WebSocket และส่งคืนข้อความตัวอย่างของโพรโทคอลผ่านสาย (`request`, `cancel`) เฟรม WS จริงได้รับการจัดการโดยเซิร์ฟเวอร์ WS ที่รวมมาให้ ซึ่งอยู่นอกตารางเส้นทางของ Next.js

**การยืนยันตัวตน:** Bearer API key ระหว่างแฮนด์เชก

### Responses API ผ่าน WebSocket (เฉพาะ codex)

```bash
# โฮสต์:พอร์ตเดียวกับ HTTP API (ค่าเริ่มต้นคือ 20128); อัปเกรดการเชื่อมต่อ:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (หรือ: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# เฟรมแรกต้องเป็น response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

พร็อกซี Responses-API-over-WebSocket เชื่อมต่อ**เฉพาะกับ `codex` เท่านั้น** (แบ็กเอนด์
ChatGPT) โดยรับฟังบนพอร์ตเดียวกับ API/แดชบอร์ดที่พาธ `/v1/responses`,
`/responses` และ `/api/v1/responses` เมื่อได้รับเฟรม `response.create` แรก ระบบจะ
ยืนยันตัวตนและเตรียมการผ่านบริดจ์ภายใน `codex-responses-ws` เลือกการเชื่อมต่อ
codex OAuth และสร้างทันเนลไปยัง `wss://chatgpt.com/backend-api/codex/responses`
ผ่านทรานสปอร์ต `wreq-js` **โมเดลที่ไม่ใช่ codex จะถูกปฏิเสธ** (`codex_ws_provider_required`)
สำหรับการกำหนดเส้นทางแบบแบ่งโควตา ให้ใช้ `model: "qtSd/<group>/codex/<model>"` ระบบนี้ถูกนำไปใช้ใน
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`

**การยืนยันตัวตน:** Bearer API key ระหว่างแฮนด์เชก เซิร์ฟเวอร์ HTTP ที่รวมมาให้ (`server-ws.mjs`)
ต้องเป็นจุดเริ่มต้นที่กำลังใช้งานอยู่ (และจะเป็นเช่นนั้นโดยค่าเริ่มต้นเมื่อมี `app/server-ws.mjs`)

#### ID โมเดล: ใช้ ID ของ ChatGPT โดยตรง (ไม่มีคำนำหน้า `codex/`)

OpenAI **Codex CLI** จะตรวจสอบชื่อโมเดลฝั่งไคลเอนต์เมื่อ
`supports_websockets = true` และ**ปฏิเสธ ID ที่มีคำนำหน้าผู้ให้บริการ** เช่น
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`) ให้ส่ง ID **โดยตรง** (เช่น `gpt-5.5`) บริดจ์ของ OmniRoute
รองรับเฉพาะ codex จึงจะแก้ไข ID โดยตรงให้เป็นโมเดล codex อีกครั้ง
(`resolveCodexWsModelInfo`) ก่อนสร้างทันเนลไปยังระบบต้นทาง — แม้ว่า
`gpt-5.5` แบบไม่มีคำนำหน้าจะถูกกำหนดเส้นทางไปยังผู้ให้บริการรายอื่นผ่าน HTTP ในกรณีปกติก็ตาม

#### การกำหนดค่า OpenAI Codex CLI

กำหนดให้ Codex CLI ชี้ไปยัง OmniRoute โดยเพิ่มผู้ให้บริการแบบกำหนดเองที่รองรับ WebSocket
ลงใน `~/.codex/config.toml` (ใช้ `CODEX_HOME` แยกต่างหากเพื่อหลีกเลี่ยงการแก้ไข
การกำหนดค่าที่มีอยู่):

```toml
model = "gpt-5.5"                 # ID โดยตรง — ไม่ใช่ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ไม่มีเครื่องหมายทับต่อท้าย; URL ของ WS จะถูกสร้างจากค่านี้ (ใช้ https/wss ในระบบใช้งานจริง)
wire_api = "responses"                    # ค่าที่รองรับเพียงค่าเดียวนับตั้งแต่เดือนกุมภาพันธ์ 2026
supports_websockets = true                # เปิดใช้งานทรานสปอร์ต Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # เก็บ API key ของ OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API key ของ OmniRoute (ใช้คีย์ใดก็ได้หาก REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI จะอัปเกรด `base_url + /responses` เป็น WebSocket และ OmniRoute จะสร้างทันเนล
ไปยังการเชื่อมต่อ codex OAuth ที่เลือกไว้ ผ่านการตรวจสอบแบบครบวงจรกับเซิร์ฟเวอร์ภายในแล้ว:
ChatGPT ส่งคืน `codex.rate_limits` + `response.created` และสตรีมผลลัพธ์จนเสร็จสมบูรณ์

## การใช้งานแบบบริการตนเอง (`/api/usage/om-usage`)

คีย์ API ใดๆ สามารถอ่านการใช้งานและโควตา**ของตนเอง**ได้ โดยไม่ต้องใช้การยืนยันตัวตนสำหรับการจัดการ นี่คือเอนด์พอยต์ที่
ไคลเอนต์ (CLI หรือแผง OmniCopilot) ใช้เพื่อแสดงค่าใช้จ่ายแก่ผู้ถือคีย์

```bash
# รูปแบบข้อความ (สัญญาการทำงานดั้งเดิม — ข้อความธรรมดาสำหรับเทอร์มินัล)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# รูปแบบมีโครงสร้าง — รูปแบบที่ UI ใช้งาน
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

คีย์ต้องเปิดใช้ **`allowUsageCommand`** (ปิดไว้ตามค่าเริ่มต้น — ตัวจัดการคีย์ API ของแดชบอร์ด
จะเปิดหรือปิดค่านี้แยกตามแต่ละคีย์) หากไม่ได้เปิดใช้ เอนด์พอยต์จะตอบกลับด้วย `403`

`?format=json` ส่งคืนโครงสร้างแบบจำแนกชนิด เพื่อให้ผู้เรียกไม่อ่านฟิลด์ข้อมูลจาก
การปฏิเสธ เมื่อสำเร็จ:

```jsonc
{
  "allowed": true,
  // มีเฉพาะเมื่อคีย์เลือกใช้ขีดจำกัดการใช้งานรายคีย์ (USD รายวัน/รายสัปดาห์):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // สแนปช็อตโควตาของผู้ให้บริการที่เลือก หรือ null เมื่อยังไม่มีข้อมูลที่แคชไว้:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // สแนปช็อตของทุกการเชื่อมต่อ เพื่อให้ UI แสดงผู้ให้บริการหลายรายเคียงข้างกันได้:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

เมื่อถูกปฏิเสธ (`401` คีย์ไม่ถูกต้อง / `403` ไม่ได้รับอนุญาต) เส้นทางเดียวกันจะส่งคืน
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` ที่มีอยู่แต่ไม่มีข้อมูล
(คีย์ได้รับอนุญาต แต่ยังไม่ได้รับข้อมูลใดๆ) เป็นสถานะที่แตกต่างจากการถูกปฏิเสธ และมีเพียงรูปแบบ JSON
เท่านั้นที่แยกแยะสถานะเหล่านี้ได้

**การยืนยันตัวตน:** คีย์ API แบบ Bearer ของผู้เรียกเอง ซึ่งตรวจสอบด้วย `isValidApiKey` — นี่_ไม่ใช่_
ส่วนการจัดการ (`/api/keys/…`) ซึ่งยังคงได้รับการป้องกันด้วย `requireManagementAuth`

### เปอร์เซ็นต์โควตาแบบดิบเทียบกับแบบปรับตามจุดตัด

เมื่อใช้งาน `/api/usage/om-usage` ผู้เรียกควรทราบความแตกต่างระหว่าง
เปอร์เซ็นต์ที่แสดงโดย**เอาต์พุตข้อความธรรมดา**กับ**เอาต์พุต JSON** ที่มีโครงสร้าง:

| ลักษณะ                   | รูปแบบข้อความธรรมดา (`/api/usage/om-usage` / `@@om-usage`)                                        | รูปแบบ JSON (`?format=json`)                                                            |
| :----------------------- | :------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------- |
| **ฟิลด์เอาต์พุต**        | `NN% left` (เช่น `20% left`)                                                                      | `provider.quotas` / `providers[].quotas`                                                |
| **การวัดค่า**            | **โควตาที่ใช้งานได้หลังปรับตามจุดตัด**: ความจุคงเหลือเหนือเกณฑ์จุดตัด                             | **โควตาดิบจากต้นทาง**: ค่าที่วัดจากผู้ให้บริการโดยไม่มีการปรับ                          |
| **การปรับสเกลตามจุดตัด** | ปรับสเกลผ่าน `effectiveRemainingPercent()` เพื่อให้ส่วนสำรองที่ได้รับการป้องกันแสดงเป็น `0% left` | ไม่มี (ค่าสแนปช็อตดิบตามที่ผู้ให้บริการรายงาน)                                          |
| **ข้อมูลเกณฑ์**          | รวมอยู่ในเปอร์เซ็นต์ที่แสดง                                                                       | จัดเก็บใน `quotaWindowThresholds` แยกตามการเชื่อมต่อ (หรือใช้ค่าเริ่มต้นของเซิร์ฟเวอร์) |
| **ผู้ใช้งานหลัก**        | CLI แบบโต้ตอบ พรอมต์เทอร์มินัล และผู้ปฏิบัติงาน                                                   | การผสานรวมเชิงโปรแกรม แดชบอร์ด การวิเคราะห์ และเครื่องมือติดตามการเรียกเก็บเงิน         |

#### สูตรการปรับตามจุดตัด

OmniRoute รองรับจุดตัดโควตาเชิงรุกเพื่อป้องกันไม่ให้โควตาต้นทางหมดลง (กำหนดค่าผ่าน
`quotaWindowThresholds` ของการเชื่อมต่อ ค่าเริ่มต้นของผู้ให้บริการ หรือการตั้งค่าความยืดหยุ่นส่วนกลาง) เมื่อเกณฑ์จุดตัด
(เช่น `cutoff = 25%`) ทำงานอยู่ในช่วงโควตา ตัวเรนเดอร์ข้อความจะคำนวณโควตาคงเหลือดังนี้:

- หาก `remaining <= cutoff`: ส่งคืน `0%`
- หาก `remaining > cutoff`: ส่งคืน `((remaining - cutoff) / (100 - cutoff)) * 100`

เอาต์พุตข้อความที่จัดรูปแบบแล้วจะปัดค่าเป็นจำนวนเต็มที่ใกล้ที่สุด (`Math.round(...)`)

#### ตัวอย่างประกอบ

พิจารณาช่วงโควตาของผู้ให้บริการที่มี**การใช้งานดิบ 60%** (จึงมี**โควตาดิบคงเหลือ 40%**) และกำหนด
เกณฑ์**จุดตัดโควตาคงเหลือ 25%** ไว้:

| รูปแบบการแสดง                  | การคำนวณ                                           | คงเหลือ |            ค่าการใช้งานโดยนัย            |
| :----------------------------- | :------------------------------------------------- | :-----: | :--------------------------------------: |
| **JSON ดิบ (`?format=json`)**  | สแนปช็อตจากต้นทาง (`quotas[window]`)               | **40%** |                 **60%**                  |
| **รูปแบบข้อความ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (หากคำนวณด้วย `100 - remaining`) |

- **เหตุใดข้อความจึงแสดงว่าเหลือ 20%:** จากโควตาจริง 40% ที่เหลืออยู่ในบัญชี มี 25% ถูกสำรองไว้โดย
  นโยบายจุดตัด ผู้เรียกจึงมีพื้นที่ใช้งานได้เหลือเพียง 15% จากทั้งหมด 75% ก่อนที่เราเตอร์จะหยุด
  กำหนดเส้นทางไปยังการเชื่อมต่อนี้ การปรับสเกลช่วยให้การเชื่อมต่อส่งสัญญาณว่าโควตาหมด (`0% left`) ในจังหวะเดียวกับที่
  การกำหนดเส้นทางหยุดลงพอดี
- **เหตุใด JSON จึงคงค่าดิบไว้:** เพย์โหลด JSON ส่งคืนสแนปช็อตจากผู้ให้บริการ (`UsageSnapshot`) ตามค่าจริง
  เพื่อให้เครื่องมือภายนอกเข้าถึงการใช้งานต้นทางตามข้อเท็จจริงและ
  `quotaWindowThresholds` ระดับการเชื่อมต่อได้ โดยไม่เกิดการสูญเสียข้อมูลจากการปรับสเกลฝั่งเซิร์ฟเวอร์

#### แนวทางการย้ายระบบสำหรับผู้ใช้งาน

หากการผสานรวมภายนอก (เช่น ปลั๊กอินของตัวแก้ไขหรือส่วนขยายเอเจนต์) ก่อนหน้านี้ดึงข้อมูลจาก
เอนด์พอยต์ข้อความ (`NN% left`) และคำนวณเปอร์เซ็นต์ที่ใช้ไปเป็น `100 - NN` การย้ายไปใช้ `?format=json` หมายความว่า:

- การอ่านค่า JSON ดิบจะแสดงถึง **การใช้งานจริงจากต้นทาง** (ใช้ไป 60% ในตัวอย่างข้างต้น)
- หากการผสานรวมต้องการคงความหมายของโควตาที่ใช้งานได้ตามเอนด์พอยต์ข้อความไว้ ก็สามารถประเมิน
  สูตรคำนวณจำนวนคงเหลือที่มีผลในฝั่งไคลเอนต์ได้โดยใช้ `quotaWindowThresholds` สำหรับการแทนที่ค่าในระดับการเชื่อมต่อ

## แคชเชิงความหมาย

```bash
# ดูสถิติแคช
GET /api/cache/stats

# ล้างแคชทั้งหมด
DELETE /api/cache/stats
```

ตัวอย่างการตอบกลับ:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### ผลกระทบต่อเวลาแฝง

เมื่อพบข้อมูลในแคชเชิงความหมาย ระบบจะส่งการตอบกลับจากแคช **โดยไม่เรียกใช้บริการต้นทาง**
ดังนั้นค่า `X-OmniRoute-Response-Latency` ที่รายงานจึงใกล้ศูนย์
(โดยไม่ขึ้นอยู่กับเวลาแฝงเดิมของบริการต้นทาง) ไคลเอนต์ที่ไวต่อเวลาแฝง
(การทดสอบประสิทธิภาพ การตรวจสอบ p50/p99) ควรตรวจสอบส่วนหัวการตอบกลับ
`X-OmniRoute-Cache-Latency`:

| ค่า         | ความหมาย                                                    |
| ----------- | ----------------------------------------------------------- |
| `synthetic` | ส่งการตอบกลับจากแคช เวลาแฝงจึงไม่ใช่เวลาจริงของบริการต้นทาง |
| _(ไม่มี)_   | การตอบกลับจากการเรียกใช้บริการต้นทางจริง                    |

### การข้ามแคชสำหรับแต่ละคีย์

คีย์ API สามารถเลือกไม่อ่านข้อมูลจากแคชเชิงความหมายได้ผ่าน `cacheDefaultMode`:

| ค่า      | ลักษณะการทำงาน                                       |
| -------- | ---------------------------------------------------- |
| `legacy` | การทำงานของแคชตามปกติ (ค่าเริ่มต้น)                  |
| `bypass` | ข้ามการค้นหาในแคชทั้งหมด และเรียกใช้บริการต้นทางเสมอ |

กำหนดค่าเมื่อสร้างคีย์ (`POST /api/keys`) หรืออัปเดต (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### การข้ามแคชสำหรับแต่ละคำขอ

คำขอใดๆ สามารถข้ามแคชได้โดยไม่ขึ้นอยู่กับการตั้งค่าของคีย์:

```
X-OmniRoute-No-Cache: true
```

สำหรับโมเดลที่ซิงค์/นำเข้า `PUT /api/provider-models` ยอมรับ `provider`, `modelId` และ
`maxOutputTokenOverride`: จำนวนเต็มบวกจะกำหนดขีดจำกัดโทเค็นเอาต์พุตด้วยตนเอง และ `null`
จะล้างค่านี้เพื่อคืนค่าเริ่มต้น `GET /api/provider-models?provider=<provider>` จะส่งคืน
ค่าเหล่านี้ใน `modelOutputOverrides` รวมถึงโมเดลที่ไม่มีแถวโมเดลแบบกำหนดเอง ค่าที่แทนที่
จะใช้ความสามารถ `max_output_tokens` ขณะรันไทม์และยังคงอยู่หลังการซิงค์โมเดลใหม่ หน้าผู้ให้บริการ
ที่เข้ากันได้กับ OpenAI มีตัวควบคุมแก้ไข/ล้างค่าแบบเดียวกัน และทำเครื่องหมายโมเดลที่รองรับการมองเห็นอย่างชัดเจน

โหนด Custom Chat Completions จะปรับการเลือกไม่ใช้การให้เหตุผลที่ระบุไว้อย่างชัดเจนให้เข้ากับแบ็กเอนด์ต้นทาง
การทดสอบการเชื่อมต่อที่สำเร็จจะเลือกตัวควบคุมเทมเพลตแชตโดยอัตโนมัติสำหรับ ID โมเดลแต่ละรายการที่ตรงกันทุกประการ
ซึ่งรายการ `/models` พิสูจน์ว่ามีค่า `owned_by` ที่รู้จัก ได้แก่ `vllm`, `sglang` หรือ `llamacpp`
แรปเปอร์ที่เข้ากันได้กับ OpenAI แบบโปร่งใสอาจเก็บรายการโมเดลดั้งเดิมไว้ภายในออบเจ็กต์
`openai` ที่ซ้อนกัน การตรวจจับจะติดตามเอนเวโลปดังกล่าวได้สูงสุดสามชั้น โมเดลที่ไม่มีข้อมูล มีข้อมูลความเป็นเจ้าของที่ไม่รู้จัก
หรือขัดแย้งกัน จะยังคงใช้ลักษณะการทำงานปกติของ OpenAI การตรวจจับจะใช้คำขอแค็ตตาล็อกที่มีอยู่ซ้ำ
ไม่สร้างโทเค็นการตอบให้สมบูรณ์ และจะถูกทำให้ใช้ไม่ได้เมื่อเอนด์พอยต์การเชื่อมต่อเปลี่ยนแปลง

หากต้องการตรึงลักษณะการทำงานสำหรับแบ็กเอนด์ที่ไม่เปิดเผยข้อมูลเมตาดังกล่าว ให้ใช้ API ที่มีอยู่
สำหรับการอัปเดตผู้ให้บริการบางส่วน:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ส่งเนื้อหานั้นด้วย `PUT /api/providers/<connection-id>` สำหรับการเชื่อมต่อนั้น ความพยายาม
ในการให้เหตุผลที่ระบุชัดเจนเป็น `none` จะถูกส่งเป็น `chat_template_kwargs.thinking=false` และ
`chat_template_kwargs.enable_thinking=false` ค่าเทมเพลตเนทีฟที่ระบุอย่างชัดเจนยังคงมีผลเหนือกว่า
เว้นแต่กฎการให้เหตุผลฝั่งเซิร์ฟเวอร์จะบังคับระดับความพยายาม การตั้งค่านี้ใช้เฉพาะเมื่อการเชื่อมต่อแบบกำหนดเอง
ที่เข้ากันได้กับ OpenAI ส่งเนื้อหา Chat Completions เท่านั้น คำขอ Responses และผู้ให้บริการทั่วไป
จะยังคงใช้รูปแบบคำขอเนทีฟของตน ตั้งค่า `reasoningControl` เป็น `openai` เพื่อบังคับให้ส่งผ่าน
`reasoning_effort` แบบปกติของ OpenAI หรือไม่ระบุ/ตั้งค่าเป็น `null` เพื่อใช้การตรวจจับอัตโนมัติ

คำขอตัวจำแนกประเภทในโหมดอัตโนมัติของ Claude Code จะตั้งค่าเริ่มต้นให้ปิดการคิดแบบเนทีฟเมื่อไม่มี
ตัวควบคุมการให้เหตุผลที่ระบุอย่างชัดเจน การตรวจจับจะใช้เครื่องหมายระบบของตัวจำแนกประเภทในคำขอรูปแบบ Claude
ไม่ใช่ชื่อโมเดลหรือขีดจำกัดการตอบให้สมบูรณ์ ตัวควบคุมในเนื้อหาที่ระบุชัดเจน เฮดเดอร์ระดับความพยายาม/การคิด
ที่รองรับ กฎการกำหนดเส้นทาง และระดับความพยายามของโมเดลที่ได้รับการกำหนดค่าแล้ว จะยังคงมีลำดับความสำคัญ
ตามเดิม ตัวจำแนกประเภททั้งสองขั้นตอนจะคงพรอมต์ ขีดจำกัดการตอบให้สมบูรณ์ ลำดับหยุด และคำตัดสินสิทธิ์จริง
จากต้นทางไว้ ขั้นตอนที่สองยังคงสามารถสร้างการให้เหตุผลที่มองเห็นได้ตามที่ร้องขอในรูปแบบข้อความปกติ

### สิทธิ์ของคีย์ API

`PATCH /api/keys/{id}` อัปเดตสิทธิ์ของคีย์ที่มีอยู่ เช่นเดียวกับทุกเส้นทาง `/api/keys*` เส้นทางนี้ต้องใช้การให้สิทธิ์เพื่อการจัดการ (ดู [การยืนยันตัวตนเพื่อการจัดการ](../guides/MANAGEMENT-AUTH.md)) ไม่ใช่คีย์สำหรับการอนุมาน ให้ส่งเฉพาะฟิลด์ที่ต้องการเปลี่ยนแปลงเท่านั้น คำขอที่ไม่มีฟิลด์เหล่านี้จะถูกปฏิเสธด้วยข้อความ `No valid fields to update` ฟิลด์ที่ยอมรับได้รับการกำหนดโดย `updateKeyPermissionsSchema` ใน `src/shared/validation/schemas/keys.ts`

| `/api/db-backups/exportAll` | GET    | ดาวน์โหลดข้อมูลสำรองทั้งหมดเป็นไฟล์เก็บถาวร .tar.gz                          |

`/api/db-backups/export`, `/api/db-backups/exportAll` และ `/api/settings/export-json` ส่งมอบ
ข้อมูลประจำตัวทั้งหมดที่จัดเก็บไว้ ดังนั้นจึงจำเป็นต้องใช้เซสชันแดชบอร์ดหรือ CLI ภายในเครื่อง (หรือปิดใช้งาน
การเข้าสู่ระบบ) คีย์ API ทุกขอบเขตและโทเค็นการเข้าถึง `oma_` จะได้รับ `403` การกู้คืนใช้ขอบเขต
เดียวกัน: `POST /api/db-backups/import` (รวมถึง `dryRun=true`), `POST /api/db-backups` (กู้คืน
ตาม id) และ `POST /api/settings/import-json` จะแทนที่ฐานข้อมูลหรือการตั้งค่าที่ใช้งานอยู่ ดังนั้นข้อมูล
ประจำตัวของเครื่องจะได้รับ `403` เช่นกัน โดย `omniroute sync import` จะส่งข้อมูลประจำตัวของ CLI ภายในเครื่อง เช่นเดียวกับ
`DELETE /api/db-backups` (ล้างข้อมูลสำรองที่จัดเก็บไว้) และ `PATCH /api/db-backups` (การตั้งค่าการเก็บรักษา:
ค่าที่บันทึกไว้จะควบคุมการล้างข้อมูลอัตโนมัติหลังการสำรองข้อมูลแต่ละครั้ง) การแสดงรายการ (`GET`) และการสร้าง
ข้อมูลสำรองด้วยตนเอง (`PUT`) ยังคงใช้การยืนยันตัวตนสำหรับการจัดการทั่วไป

### เวอร์ชันและช่องทางการเผยแพร่

```bash
GET /api/system/version
```

เส้นทางการจัดการที่เข้าถึงได้จากลูปแบ็กเท่านั้น (ต้องผ่านการยืนยันตัวตนของผู้ดูแลระบบ) ส่งคืนเวอร์ชันที่กำลังทำงาน เวอร์ชันล่าสุดที่เผยแพร่ และสถานะการอัปเดตอัตโนมัติ `releaseChannel` และ `channels` เป็นฟิลด์ที่เพิ่มเข้ามา (rail 3.8.54) ส่วน `channel` ยังคงมีความหมายเดิม — คือโหมดการปรับใช้ที่ตัวอัปเดตแดชบอร์ดใช้ (`npm`, `source` หรือ `docker-compose`)

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ช่องทาง npm ของบิลด์ที่กำลังทำงาน: `nightly` สำหรับเวอร์ชัน `-nightly.*`,
  `next` สำหรับเวอร์ชันก่อนเผยแพร่อื่นๆ (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` สำหรับเวอร์ชันเสถียรของ
  รุ่นหลักที่เก่ากว่า `channels.latest` มิฉะนั้นจะเป็น `latest` ใช้กฎเดียวกับ
  `scripts/release/dist-tag.mjs` ซึ่งเลือก npm dist-tag ในขณะเผยแพร่
- `channels` — เวอร์ชันล่าสุดที่เผยแพร่ของแต่ละ dist-tag จาก `npm view omniroute dist-tags` (ใช้
  HTTP ของรีจิสทรีเป็นทางเลือกสำรอง) โดยแคชด้วย TTL 10 นาทีเช่นเดียวกับ `latest` ค่า `latest` จะมีอยู่
  เสมอ (หากไม่มีจะใช้ฟิลด์ `latest` และจากนั้นใช้ `"unavailable"`); `next`, `nightly` และ `lts` จะปรากฏ
  เฉพาะเมื่อมี dist-tag นั้นอยู่ คำขอ `Cache-Control: no-cache` จะรีเฟรชการค้นหาทั้งสองรายการ

โมเดลช่องทาง (`latest` = v3 จนกว่า 4.0 จะพร้อมใช้งานทั่วไป, `next` = rc, `nightly` = บิลด์จาก `develop`,
`lts` = แพตช์ v3 หลังจาก 4.0 พร้อมใช้งานทั่วไป) มีคำอธิบายอยู่ใน `docs/ops/RELEASE_STRATEGY.md`

## การถอดเสียง

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

ถอดเสียงไฟล์เสียงโดยใช้ผู้ให้บริการ STT ที่กำหนดค่าไว้ รายการพาธส่วนแรก
ใช้เลือกผู้ให้บริการโดยตรง (`openai/…`, `deepgram/…`) ส่วนเกตเวย์ที่
ให้บริการโมเดลของผู้จำหน่ายรายอื่นอีกทอดหนึ่งจะใช้ ID แบบระบุคุณสมบัติครบถ้วน
(`openrouter/deepgram/nova-3`)

**คำขอ:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**การตอบกลับ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**ตัวอย่าง ID โมเดล:** `openai/whisper-1` (ต้องใช้คีย์ OpenAI),
`openrouter/deepgram/nova-3` (ต้องใช้คีย์ OpenRouter),
`deepgram/nova-3` (ต้องใช้คีย์ Deepgram โดยตรง) คำขอที่ระบุเพียง
`deepgram/nova-3` จะ **ไม่** ใช้ OpenRouter

**รูปแบบที่รองรับ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`

## นามแฝงแบบมีโทเค็นสำหรับ VS Code / แบบไม่มีส่วนหัว

ใช้นามแฝงเหล่านี้เมื่อการผสานรวมไม่สามารถแทรกส่วนหัว `Authorization` และจำเป็นต้องฝังคีย์ API ไว้ใน URL ฐาน

```bash
# นามแฝงแค็ตตาล็อกแบบ OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# นามแฝงแชตแบบ OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# นามแฝงแบบ Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ตัวอย่าง:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

หมายเหตุ:

- นามแฝงแบบมีโทเค็นใช้ตัวจัดการเดียวกับ `/v1/*` และ `/api/tags` โดยโครงสร้างการตอบกลับจะยังคงเหมือนเดิม
- ควรใช้ `Authorization: Bearer ...` เมื่อใดก็ตามที่ไคลเอนต์รองรับส่วนหัวแบบกำหนดเอง
- โทเค็นที่อยู่ใน URL อาจปรากฏในบันทึกของพร็อกซีย้อนกลับ ประวัติของเบราว์เซอร์ และข้อมูลเทเลเมทรีภายนอก OmniRoute ให้ใช้เป็นตัวเลือกเพื่อความเข้ากันได้ ไม่ใช่โหมดการตรวจสอบสิทธิ์เริ่มต้น

```bash
# รับสถานะงบประมาณสำหรับคีย์ API ทั้งหมด
GET /api/usage/budget

# กำหนดหรืออัปเดตงบประมาณ
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **หมายเหตุเกี่ยวกับสคีมา** (`setBudgetSchema`): ต้องระบุ `apiKeyId` และค่าอย่างน้อยหนึ่งค่าจาก `dailyLimitUsd`, `weeklyLimitUsd` หรือ `monthlyLimitUsd` ต้องมากกว่าศูนย์ ฟิลด์ที่ไม่บังคับ: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`) รูปแบบเดิม `{keyId, limit, period}` จะส่งคืน `400 Bad Request`

## ขีดจำกัดโทเค็น

งบประมาณ **โทเค็น** ต่อคีย์ API (แยกจากงบประมาณที่อิงตาม USD ด้านบน) ระบบบังคับใช้โดยตรงในเส้นทางการประมวลผลคำขอ: เมื่อปริมาณการใช้งานในช่วงเวลาปัจจุบันของคีย์ถึงขีดจำกัด คำขอจะถูกปฏิเสธด้วย `429 Too Many Requests` ขีดจำกัดสามารถกำหนดขอบเขตสำหรับ `model` หรือ `provider` ที่เฉพาะเจาะจง หรือใช้แบบ `global` กับทั้งคีย์ เมื่อมีขีดจำกัดหลายรายการตรงกับคำขอ ระบบจะใช้รายการที่เข้มงวดที่สุด

```bash
# แสดงขีดจำกัดโทเค็นของคีย์ (รวมการใช้งานปัจจุบันในช่วงเวลา)
GET /api/usage/token-limits?apiKeyId=key-123

# สร้างหรืออัปเดตขีดจำกัดโทเค็น
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ลบขีดจำกัดโทเค็นตาม id
DELETE /api/usage/token-limits?id=tl-abc
```

> **หมายเหตุเกี่ยวกับสคีมา** (`setTokenLimitSchema`): ต้องระบุ `apiKeyId` และ `scopeType` (`model` | `provider` | `global`) ต้องระบุ `scopeValue` เว้นแต่ `scopeType` จะเป็น `global` (เช่น id ของโมเดลสำหรับขอบเขต `model` หรือ id ของผู้ให้บริการสำหรับขอบเขต `provider`) `tokenLimit` ต้องเป็นจำนวนเต็มบวก (แปลงจากสตริงได้) ตัวเลือกที่ระบุหรือไม่ก็ได้: `id` (ไม่ต้องระบุเพื่อสร้างใหม่ หรือระบุเพื่ออัปเดต), `resetInterval` (`daily` | `weekly` | `monthly` ค่าเริ่มต้นคือ `monthly`), `resetTime` (`HH:MM`), `enabled` (ค่าเริ่มต้นคือ `true`) การตอบกลับจาก `GET` จะเพิ่มข้อมูลให้แต่ละขีดจำกัดด้วย `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` และ `nextResetAt` นี่คือปลายทางระดับการจัดการ (การตรวจสอบสิทธิ์ถูกบังคับใช้จากส่วนกลางโดยไปป์ไลน์ authz)

## การประมวลผลคำขอ

1. ไคลเอนต์ส่งคำขอไปยัง `/v1/*`
2. ตัวจัดการเส้นทางเรียก `handleChat`, `handleEmbedding`, `handleAudioTranscription` หรือ `handleImageGeneration`
3. ระบบระบุโมเดล (ผู้ให้บริการ/โมเดลโดยตรง หรือ alias/combo)
4. ระบบเลือกข้อมูลประจำตัวจากฐานข้อมูลภายใน พร้อมกรองตามความพร้อมใช้งานของบัญชี
5. สำหรับแชต: `handleChatCore` จะตรวจสอบแคชเชิงความหมาย/ลายเซ็น และระบุการตั้งค่าการบีบอัดของ combo
6. การบีบอัดเชิงรุกจะทำงานก่อนการแปลงรูปแบบสำหรับผู้ให้บริการเมื่อเปิดใช้งาน (`lite`, Caveman, RTK หรือแบบซ้อนกัน)
7. ตัวดำเนินการของผู้ให้บริการส่งคำขอไปยังระบบต้นทาง
8. ระบบแปลงการตอบกลับกลับเป็นรูปแบบของไคลเอนต์ (แชต) หรือส่งคืนตามเดิม (embeddings/images/audio)
9. ระบบบันทึกการใช้งาน การวิเคราะห์การบีบอัด และบันทึกคำขอ
10. ระบบใช้ fallback เมื่อเกิดข้อผิดพลาดตามกฎของ combo

ข้อมูลอ้างอิงสถาปัตยกรรมฉบับเต็ม: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## การจัดการ Combo

Combo สำหรับการกำหนดเส้นทางระดับสูง (สรุปไว้แล้วภายใต้ `/api/combos*`) ยังสามารถแมปแบบ 1:1 จากรูปแบบ id ของโมเดลได้ด้วย ซึ่งช่วยให้เปลี่ยนเส้นทาง id ของโมเดลรูปแบบ OpenAI ไปยัง combo ได้อย่างโปร่งใส

| เมธอด  | พาธ                              | คำอธิบาย                                                                       |
| ------ | -------------------------------- | ------------------------------------------------------------------------------ |
| GET    | `/api/model-combo-mappings`      | แสดงรายการการแมป model→combo ทั้งหมด                                           |
| POST   | `/api/model-combo-mappings`      | สร้างการแมป — เนื้อหา: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | ดึงข้อมูลการแมปรายการเดียว                                                     |
| PUT    | `/api/model-combo-mappings/[id]` | อัปเดตฟิลด์ของการแมปที่มีอยู่                                                  |
| DELETE | `/api/model-combo-mappings/[id]` | ลบการแมป                                                                       |

**การตรวจสอบสิทธิ์:** เซสชัน/คีย์ API สำหรับการจัดการ (`requireManagementAuth`)

## เว็บฮุก

การสมัครรับเว็บฮุกขาออกสำหรับเหตุการณ์ของ OmniRoute (การดำเนินการตามคำขอเสร็จสมบูรณ์ โควตาหมด การหมุนเวียนคีย์ ฯลฯ)

| เมธอด  | พาธ                       | คำอธิบาย                                                               |
| ------ | ------------------------- | ---------------------------------------------------------------------- |
| GET    | `/api/webhooks`           | แสดงรายการเว็บฮุก (ข้อมูลลับถูกปิดบังเป็น `<prefix>...`)               |
| POST   | `/api/webhooks`           | สร้างเว็บฮุก — เนื้อหา: `{url, events?: ["*"], secret?, description?}` |
| GET    | `/api/webhooks/[id]`      | ดึงข้อมูลเว็บฮุก                                                       |
| PUT    | `/api/webhooks/[id]`      | อัปเดต URL/เหตุการณ์/ข้อมูลลับ/คำอธิบาย                                |
| DELETE | `/api/webhooks/[id]`      | ลบเว็บฮุก                                                              |
| POST   | `/api/webhooks/[id]/test` | ส่งเพย์โหลดทดสอบไปยัง URL ของเว็บฮุกและส่งคืนสถานะการนำส่ง             |

**การยืนยันตัวตน:** เซสชันการจัดการ/API key (`requireManagementAuth`)

## คีย์ที่ลงทะเบียน (การจัดการอัตโนมัติ)

ใช้โดยระบบย่อยการจัดการคีย์อัตโนมัติเพื่อออกและหมุนเวียน API key กับผู้ให้บริการ/บัญชีเบื้องหลัง โดยมีโควตารายวัน/รายชั่วโมง

| เมธอด  | พาธ                                   | คำอธิบาย                                                                                                                                                                                                 |
| ------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | แสดงรายการคีย์ที่ลงทะเบียน (เฉพาะคำนำหน้าที่ถูกปิดบัง)                                                                                                                                                   |
| POST   | `/api/v1/registered-keys`             | ออกคีย์ที่ลงทะเบียนใหม่ — เนื้อหา: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}` ส่งคืนคีย์ดิบ **เพียงครั้งเดียว** ส่งคืน `429` เมื่อถูกปฏิเสธเนื่องจากโควตา |
| GET    | `/api/v1/registered-keys/[id]`        | ดึงข้อมูลเมทาดาทาของคีย์ที่ลงทะเบียน (ไม่มีข้อมูลคีย์ดิบ)                                                                                                                                                |
| DELETE | `/api/v1/registered-keys/[id]`        | เพิกถอนคีย์ที่ลงทะเบียน                                                                                                                                                                                  |
| POST   | `/api/v1/registered-keys/[id]/revoke` | เอนด์พอยต์สำหรับเพิกถอนโดยชัดแจ้ง (มีผลเช่นเดียวกับ DELETE)                                                                                                                                              |

**การยืนยันตัวตน:** เซสชันการจัดการ/API key (`requireManagementAuth`) — ใช้ตัวตรวจสอบเดียวกับ `/api/keys`: เซสชันแดชบอร์ด โทเค็น CLI ภายในเครื่อง หรือ API key ที่มีขอบเขต `manage`/`admin`; API key สำหรับการอนุมานเท่านั้นจะได้รับ `403` ดูเพิ่มเติมที่ `/v1/quotas/check` และ `/v1/issues/report`

## โปรโตคอล Agents

งานของ Cloud Agent (Claude Code, Codex Cloud, OpenHands เป็นต้น) ที่ดำเนินการจากระยะไกลในนามของผู้ใช้ OmniRoute

| เมธอด  | พาธ                           | คำอธิบาย                                                                                                                                         |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/agents/tasks`        | แสดงรายการงาน — รองรับ `?provider=`, `?status=`, `?limit=` เป็นตัวเลือก (1–500, ค่าเริ่มต้น 50)                                                  |
| POST   | `/api/v1/agents/tasks`        | สร้างงาน — เนื้อหา body ตรวจสอบด้วย `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`) ส่งคืน `201` พร้อม task envelope |
| DELETE | `/api/v1/agents/tasks?id=...` | ลบงาน                                                                                                                                            |
| GET    | `/api/v1/agents/tasks/[id]`   | อ่านงาน — รีเฟรชสถานะจาก Cloud Agent ต้นทางแบบซิงโครนัสเมื่อตั้งค่า `external_id`                                                                |
| POST   | `/api/v1/agents/tasks/[id]`   | การดำเนินการแบบจำแนก: `{action: "approve"}`, `{action: "message", message}` หรือ `{action: "cancel"}`                                            |
| DELETE | `/api/v1/agents/tasks/[id]`   | ลบงานที่ระบุตาม id                                                                                                                               |

> **การยืนยันตัวตน:** ทุกเมธอดต้องมีการยืนยันตัวตนสำหรับการจัดการ (`requireCloudAgentManagementAuth`) ก่อน v3.8.0 จุดเชื่อมต่อเหล่านี้ไม่มีการยืนยันตัวตน — ดูการเปลี่ยนแปลงที่ส่งผลให้เข้ากันไม่ได้ใน commit `588a0333`

```bash
# สร้างงาน Claude Code บนคลาวด์
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Authorization: Bearer your-management-key" \
  -H "Content-Type: application/json" \
  -d '{"providerId":"claude-code-cloud","prompt":"Fix the failing test","source":{"repo":"...","branch":"..."}}'
```

## พร็อกซีสำหรับการจัดการ

พร็อกซี HTTP(S)/SOCKS ขาออกที่สามารถกำหนดให้กับผู้ให้บริการ บัญชี หรือกำหนดแบบส่วนกลางได้

| เมธอด  | พาธ                                          | คำอธิบาย                                                                                                                                         |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/management/proxies`                 | แสดงรายการพร็อกซี (`?id=` ส่งคืนหนึ่งรายการ ส่วน `?id=&where_used=1` ส่งคืนกราฟการกำหนด)                                                         |
| POST   | `/api/v1/management/proxies`                 | สร้างพร็อกซี — เนื้อหา body ตรวจสอบด้วย `createProxyRegistrySchema`                                                                              |
| PATCH  | `/api/v1/management/proxies`                 | อัปเดตพร็อกซี — เนื้อหา body ตรวจสอบด้วย `updateProxyRegistrySchema` (ต้องมี `id`)                                                               |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | ลบพร็อกซี (ใช้ `force=1` เพื่อยกเลิกการเชื่อมโยงการกำหนด)                                                                                        |
| GET    | `/api/v1/management/proxies/assignments`     | แสดงรายการการกำหนด — กรองได้ด้วย `proxy_id`, `scope`, `scope_id`; ส่ง `resolve_connection_id=<id>` เพื่อหาพร็อกซีที่ใช้งานอยู่สำหรับการเชื่อมต่อ |
| PUT    | `/api/v1/management/proxies/assignments`     | กำหนด — เนื้อหา body ตรวจสอบด้วย `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) และล้างแคชของ dispatcher                                |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | กำหนดแบบกลุ่ม — เนื้อหา body ตรวจสอบด้วย `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`)                                           |
| GET    | `/api/v1/management/proxies/health?hours=24` | สรุปสถานะความพร้อมใช้งานของพร็อกซี (จำนวนครั้งที่สำเร็จ/ล้มเหลวและ latency) ภายในช่วงเวลาที่กำหนด                                                |

**การยืนยันตัวตน:** ทุก route ต้องมีเซสชัน/คีย์ API สำหรับการจัดการ (`requireManagementAuth`)

> `POST /api/v1/management/proxies/[id]/assignments` และ `POST /api/v1/management/proxies/[id]/health` ในคำอธิบายงานให้บริการผ่าน route แบบแบน `/assignments` และ `/health` ที่แสดงไว้ด้านบน — ไม่มี route ย่อยแยกตาม id ใน codebase

## ความยืดหยุ่นต่อความล้มเหลว (เพิ่มเติม)

OmniRoute มีกลไกจัดการความล้มเหลวชั่วคราวที่เป็นอิสระต่อกันสามแบบ โดย endpoint สำหรับการจัดการด้านล่างช่วยให้ผู้ดูแลระบบสามารถอ่านและเขียนทับค่าเหล่านี้ได้:

| ขอบเขต                   | การจัดเก็บสถานะ                                  | อ่าน                                      | รีเซ็ต / ล้าง                                          |
| ------------------------ | ------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------ |
| เบรกเกอร์ของผู้ให้บริการ | `domain_circuit_breakers` + หน่วยความจำ          | `/api/monitoring/health`                  | `POST /api/resilience/reset`                           |
| ช่วงพักการเชื่อมต่อ      | `rateLimitedUntil` บนการเชื่อมต่อของผู้ให้บริการ | `/api/rate-limits`, `/api/providers/[id]` | (เปิดใช้งานอีกครั้งเมื่อจำเป็น; ล้างผ่าน provider PUT) |
| การล็อกโมเดล             | รีจิสทรีความพร้อมใช้งานของโมเดลในหน่วยความจำ     | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`               |

`PATCH /api/resilience` รองรับการเขียนทับค่าเบรกเกอร์ของผู้ให้บริการภายใต้ `providerBreaker.oauth` และ `providerBreaker.apikey` แต่ละโปรไฟล์รองรับ `degradationThreshold`, `failureThreshold` และ `resetTimeoutMs` โดยฟิลด์เดียวกันนี้ยังมีอยู่ใน แดชบอร์ด → การตั้งค่า → ความยืดหยุ่นต่อความล้มเหลว

```bash
# ล้างการล็อกของโมเดลรายการเดียว
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ล้างการล็อกทั้งหมด
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

สำหรับเอกสารอ้างอิงเชิงแนวคิดฉบับสมบูรณ์และค่าเริ่มต้นของเบรกเกอร์ โปรดดู [`CLAUDE.md`](../../CLAUDE.md) → "สถานะรันไทม์ของความยืดหยุ่นต่อความล้มเหลว" และ [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)

### คิวจำกัดอัตราและกลไกป้องกันการเปิดใช้งานอัตโนมัติ

- **เส้นทางการเขียนที่รองรับ**: `POST /api/rate-limits` พร้อม body `{"connectionId": "<id>", "enabled": true|false}` คือ endpoint สำหรับการจัดการที่รองรับการสลับเปิดหรือปิดการป้องกันการจำกัดอัตราสำหรับการเชื่อมต่อ `PUT /api/providers/[id]` ได้รับการออกแบบโดยเจตนาไม่ให้แก้ไขหรือสลับค่า `rateLimitProtection` (#11278)
- **ความหมายของ `enabled: false`**: การตั้งค่า `enabled: false` จะนำการป้องกันที่ระบุไว้อย่างชัดเจนสำหรับการเชื่อมต่อออก แต่ **ไม่ได้** นำการเชื่อมต่อด้วยคีย์ API ที่ยังทำงานอยู่ออกจากกลไกป้องกันการเปิดใช้งานอัตโนมัติส่วนกลาง (`autoEnableApiKeyProviders = true`) ใน `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) ค่า `false` และ `undefined` มีความหมายเทียบเท่ากัน การเชื่อมต่อด้วยคีย์ API ที่ยังทำงานอยู่และไม่มีการป้องกันที่ระบุไว้อย่างชัดเจนจะยังคงได้รับการป้องกันภายใต้กลไกป้องกันการเปิดใช้งานอัตโนมัติ
- **การปิดใช้งานส่วนกลาง**: หากต้องการใช้งานการเชื่อมต่อด้วยคีย์ API โดยไม่มีคิวจำกัดอัตรา ให้ปิดใช้งานกลไกป้องกันนี้ในระดับส่วนกลางผ่าน `RATE_LIMIT_AUTO_ENABLE=false` (ตัวแปรสภาพแวดล้อม) หรือ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (การตั้งค่า → ความยืดหยุ่นต่อความล้มเหลว / `PATCH /api/resilience`)

## เซิร์ฟเวอร์ MCP

OmniRoute มาพร้อมเซิร์ฟเวอร์ Model Context Protocol แบบฝังตัว ซึ่งมี 3 ทรานสปอร์ต (stdio, SSE, streamable-http) และเครื่องมือที่มีการกำหนดขอบเขต เอนด์พอยต์แดชบอร์ดด้านล่างใช้อ่านข้อมูลสถานะ/การตรวจสอบ และทำหน้าที่เป็นพร็อกซีให้กับทรานสปอร์ต HTTP

| เมธอด | พาธ | คำอธิบาย |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ฮาร์ตบีต, ทรานสปอร์ต, สถานะออนไลน์, การเรียกใช้ล่าสุด, เครื่องมือยอดนิยม, อัตราความสำเร็จในช่วง 24 ชั่วโมง |
| GET | `/api/mcp/tools` | รายการเครื่องมือ MCP พร้อม `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | เปิดสตรีม SSE สำหรับทรานสปอร์ต SSE (คืนค่า `503` หาก MCP ถูกปิดใช้งานหรือทรานสปอร์ตไม่ตรงกัน) |
| POST | `/api/mcp/sse` | ส่งเฟรม JSON-RPC ผ่านทรานสปอร์ต SSE |
| GET | `/api/mcp/stream` | เปิดฝั่ง SSE ของทรานสปอร์ต Streamable HTTP (ข้อความที่เซิร์ฟเวอร์เป็นผู้เริ่มส่ง) |
| POST | `/api/mcp/stream` | ส่งเฟรม JSON-RPC ผ่านทรานสปอร์ต Streamable HTTP |
| DELETE | `/api/mcp/stream` | สิ้นสุดเซสชัน Streamable HTTP |
| GET | `/api/mcp/audit` | ค้นหาบันทึกการตรวจสอบ — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | สถิติการตรวจสอบแบบรวม (ยอดรวม, อัตราความสำเร็จ, ระยะเวลาเฉลี่ย, เครื่องมือยอดนิยม) |

**การยืนยันตัวตน:** ทรานสปอร์ต `sse`/`stream` ใช้กลไกการยืนยันตัวตนเฉพาะของ MCP (คีย์ API แบบ Bearer ที่มีขอบเขต `mcp`); เส้นทาง `status`/`tools`/`audit*` สามารถอ่านได้จากแดชบอร์ด (ไม่ต้องมีการยืนยันตัวตนเพิ่มเติม นอกเหนือจากการเข้าถึงโฮสต์ของแดชบอร์ด)

> ทรานสปอร์ต HTTP ทั้งสองถูกควบคุมโดย `settings.mcpEnabled` และ `settings.mcpTransport` — หากทรานสปอร์ตไม่ตรงกันจะคืนค่า `400` และหาก MCP ถูกปิดใช้งานจะคืนค่า `503`

## เซิร์ฟเวอร์ A2A

OmniRoute เปิดให้ใช้งานตำแหน่งข้อมูล JSON-RPC 2.0 แบบ A2A (Agent-to-Agent) พร้อม REST wrapper สำหรับการตรวจสอบและการใช้งานแดชบอร์ด

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # ไม่บังคับ เว้นแต่มีการตั้งค่า OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

เมธอดที่รองรับ (ทั้งหมดควบคุมโดย `settings.a2aEnabled`):

| เมธอด            | คำอธิบาย                                                      |
| ---------------- | ------------------------------------------------------------- |
| `message/send`   | เรียกใช้สกิลแบบซิงโครนัส ส่งคืน `{task, artifacts, metadata}` |
| `message/stream` | เรียกใช้สกิลชุดเดียวกันแบบสตรีมผ่าน SSE                       |
| `tasks/get`      | ดึงข้อมูลงานตาม `taskId`                                      |
| `tasks/cancel`   | ยกเลิกงานตาม `taskId`                                         |

สกิลในตัว: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`

### การ์ดเอเจนต์

```bash
GET /.well-known/agent.json
```

ส่งคืนการ์ดเอเจนต์ A2A สาธารณะ (ชื่อ คำอธิบาย ความสามารถ แค็ตตาล็อกสกิล และรูปแบบการยืนยันตัวตน) — แคชแบบสาธารณะเป็นเวลา 1 ชั่วโมง ไม่จำเป็นต้องยืนยันตัวตน

### ตัวช่วย REST

| เมธอด | พาธ                          | คำอธิบาย                                                                                                           |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET   | `/api/a2a/status`            | สถานะการเปิดใช้งาน A2A + สถิติงาน + สรุปการ์ดเอเจนต์ที่แคชไว้                                                      |
| GET   | `/api/a2a/tasks`             | แสดงรายการงาน — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (ยังไม่ได้ทำเป็นตัวช่วย REST — สร้างผ่าน JSON-RPC `message/send`)                                                  |
| GET   | `/api/a2a/tasks/[id]`        | เรียกดูงานหนึ่งรายการ                                                                                              |
| POST  | `/api/a2a/tasks/[id]/cancel` | ยกเลิกงาน                                                                                                          |

**การยืนยันตัวตน:** ตัวช่วย REST ทำงานโดยไม่ต้องใช้การยืนยันตัวตนระดับการจัดการ (แดชบอร์ดสามารถอ่านได้) ส่วนเส้นทาง JSON-RPC `/a2a` จะใช้ Bearer `OMNIROUTE_API_KEY` หากมีการกำหนดค่าไว้

## การจัดการ ACP (Agent Client Protocol)

ในฐานะโปรเซสลูก Endpoint เหล่านี้ใช้จัดการการตรวจหาเอเจนต์ ACP และการลงทะเบียนเอเจนต์แบบกำหนดเอง

| เมธอด  | พาธ               | คำอธิบาย                                                                                                                                                  |
| ------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | แสดงรายการเอเจนต์ CLI ที่รู้จักทั้งหมด (ในตัว + แบบกำหนดเอง) พร้อมสถานะการติดตั้ง เวอร์ชัน และไบนารี                                                      |
| POST   | `/api/acp/agents` | ลงทะเบียนเอเจนต์ ACP แบบกำหนดเองหรือรีเฟรชแคช — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` หรือ `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | ลบเอเจนต์ ACP แบบกำหนดเอง — query param: `?id=<agentId>`                                                                                                  |

**ตัวอย่างการตอบกลับ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**การตรวจสอบสิทธิ์:** ต้องใช้เซสชันการจัดการ (คุกกี้ `auth_token` ของแดชบอร์ด) หรือ API key ที่มีขอบเขตการจัดการ

ดูรายละเอียดทั้งหมดได้ที่ [เฟรมเวิร์ก ACP](../frameworks/ACP.md)

## การวิเคราะห์และการสังเกตการณ์

Endpoint การวิเคราะห์แบบเรียลไทม์สำหรับตรวจสอบการกำหนดเส้นทาง การบีบอัด และความหลากหลายของผู้ให้บริการ Endpoint เหล่านี้ขับเคลื่อนหน้า `/dashboard/analytics/*`

### การวิเคราะห์การกำหนดเส้นทางอัตโนมัติ

| เมธอด | พาธ                                  | คำอธิบาย                                                                                                                   |
| ----- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |

## การยืนยันตัวตน

ดู [การยืนยันตัวตนสำหรับการจัดการ](../guides/MANAGEMENT-AUTH.md) สำหรับข้อมูลรับรองทั้งสี่ประเภท
(เซสชันแดชบอร์ด, โทเค็น CLI ภายในเครื่อง, Access Token แบบ `oma_live_…`
และคีย์ API ที่มีขอบเขตสำหรับการจัดการ) รวมถึงความแตกต่างจากคีย์สำหรับการอนุมาน

- เส้นทางแดชบอร์ด (`/dashboard/*`) ใช้คุกกี้ `auth_token`
- การเข้าสู่ระบบใช้แฮชรหัสผ่านที่บันทึกไว้ โดยมี `INITIAL_PASSWORD` เป็นค่าทดแทน
- สามารถสลับเปิดหรือปิด `requireLogin` ผ่าน `/api/settings/require-login`
- เส้นทาง `/v1/*` สามารถกำหนดให้ต้องใช้คีย์ API แบบ Bearer ได้เมื่อ `REQUIRE_API_KEY=true`
- ในเอกสารอ้างอิงนี้ "โทเค็นสำหรับการจัดการ" / "คีย์ API ที่มีขอบเขตสำหรับการจัดการ" หมายถึงข้อมูลรับรองประเภทใดประเภทหนึ่งในคู่มือดังกล่าว ไม่ใช่ประเภทข้อมูลลับเพิ่มเติมที่ไม่ได้กำหนดไว้

> **การเปลี่ยนแปลงที่ไม่รองรับเวอร์ชันก่อนหน้า (v3.8.0)** — ขณะนี้ `/api/v1/agents/tasks/*` และเอ็นด์พอยต์สำหรับจัดการระยะพักต้องใช้ **การยืนยันตัวตนสำหรับการจัดการ** (คุกกี้ `auth_token` ของแดชบอร์ดหรือคีย์ API ที่มีขอบเขตสำหรับการจัดการ) ไคลเอนต์ที่ก่อนหน้านี้เรียกใช้เส้นทางเหล่านี้โดยไม่มีการยืนยันตัวตนจะได้รับ `401 Unauthorized` ดูคอมมิต `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`)
