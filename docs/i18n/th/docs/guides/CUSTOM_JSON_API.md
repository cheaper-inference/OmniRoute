โหนด JSON API แบบกำหนดเองจะเชื่อมต่อจุดสิ้นสุดธุรกิจ JSON ที่ไม่พูดโปรโตคอล OpenAI หรือ Anthropic OmniRoute กรอกเทมเพลตคำขอ JSON ส่งไปยังจุดสิ้นสุดที่สมบูรณ์ URL อ่านการตอบกลับจากพาธการตอบกลับ และส่งคืนไปยังไคลเอ็นต์ในรูปแบบของลูกค้าเอง (การแชทเสร็จสิ้น การตอบกลับ ข้อความ ...)

เป็นโหนดที่เข้ากันได้กับ OpenAI พร้อมด้วย `apiType: "custom-json"`; รหัสของมันมีรูปแบบ `openai-compatible-custom-json-<suffix>` แบบฟอร์มแดชบอร์ดยังไม่พร้อมใช้งาน สร้างและแก้ไขโหนดเหล่านี้ผ่านผู้ให้บริการโหนด API ด้านล่าง

## สร้างโหนด

`POST /api/provider-nodes` (การรับรองความถูกต้องการจัดการ):

```json
{
  "type": "openai-compatible",
  "apiType": "custom-json",
  "name": "Business API",
  "prefix": "biz",
  "baseUrl": "https://api.example.com/v1/answer",
  "customHeaders": { "X-Tenant": "demo" },
  "customJson": {
    "method": "POST",
    "authType": "api-key",
    "authHeader": "X-Service-Key",
    "requestTemplate": {
      "project_id": "demo-project",
      "question": "{{prompt}}",
      "history": "{{messages}}"
    },
    "responsePath": "data.answer"
  }
}
```

- `baseUrl` คือ** สมบูรณ์** จุดสิ้นสุด URL ไม่มีการต่อท้าย (ไม่มี `/chat/completions`, ไม่มี `/models`) และแตกต่างจากโหนดอื่นที่เข้ากันได้กับ OpenAI ตรงที่ไม่มีค่าเริ่มต้น URL ต้องเป็น `http(s)` โดยไม่มีข้อมูลประจำตัวแบบฝังหรือ `#fragment` และจะส่งผ่านตัวป้องกัน URL ขาออกเดียวกันกับทุกโหนดของผู้ให้บริการ ทั้งเมื่อโหนดถูกบันทึกและในทุกคำขอ
- โหนดที่ส่งคีย์การเชื่อมต่อ (`authType` `bearer` หรือ `api-key` รวมถึงค่าเริ่มต้น) ต้องใช้ `https://` ยอมรับ `http://` ธรรมดาสำหรับโฮสต์ลูปแบ็ค (`localhost`, `127.0.0.0/8`, `::1`) หรือด้วย `authType: "none"` ซึ่งไม่มีการส่งคีย์ ที่อยู่ LAN ส่วนตัว (`10.x`, `172.16-31.x`, `192.168.x`) ไม่ได้รับการยกเว้น: ทุกคนในเครือข่ายนั้นสามารถอ่านคีย์ได้ การบันทึกโหนดดังกล่าวล้มเหลวด้วย `400` และโหนดที่เก็บไว้ก่อนหน้านี้ล้มเหลวในการปิดทุกคำขอที่มีข้อความเดียวกัน ก่อนที่จะส่งคำขอใดๆ สำหรับจุดสิ้นสุดแบบคีย์บน LAN ให้วางไว้ด้านหลัง TLS (เช่น Reverse Proxy)
- `customJson` ได้รับการตรวจสอบด้วย Zod; คีย์ที่ไม่รู้จักถูกปฏิเสธ ทุกฟิลด์เป็นทางเลือก:

| สนาม              | ค่านิยม                               | ค่าเริ่มต้น                                            |
| ----------------- | ------------------------------------- | ------------------------------------------------------ |
| `method`          | `POST`, `PUT`, `PATCH`                | `POST`                                                 |
| `authType`        | `bearer`, `api-key`, `none`           | `bearer`                                               |
| `authHeader`      | ชื่อส่วนหัวที่ใช้เมื่อ `api-key`      | `X-API-Key`                                            |
| `requestTemplate` | วัตถุJSON (≤ 64 KB ความลึก ≤ 32)      | `{ "model": "{{model}}", "messages": "{{messages}}" }` |
| `responsePath`    | เส้นทางสนามหรือ `$` สำหรับทั้งร่างกาย | `choices[0].message.content`                           |

- ข้อมูลลับจะอยู่ในคีย์ API ของการเชื่อมต่อ ไม่เคยอยู่ในเทมเพลต `bearer` ส่ง `Authorization: Bearer <key>`; `api-key` ส่ง `<authHeader>: <key>` ส่วนหัวการตรวจสอบสิทธิ์ไม่สามารถเป็น `Host`, `Content-Type`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Authorization`, `Cookie` หรือส่วนหัวแบบ hop-by-hop ด้วย `none` การเชื่อมต่อไม่จำเป็นต้องมีคีย์
- ส่วนหัวแบบคงที่เพิ่มเติมใช้ `customHeaders` ปกติของโหนด (การตรวจสอบเช่นเดียวกับโหนดที่เข้ากันได้อื่นๆ ทั้งหมด ไม่อนุญาตให้ใช้ส่วนหัวการรับรองความถูกต้องที่นั่น)

`PUT /api/provider-nodes/<id>` ยอมรับ `customJson` เดียวกันและเขียน `baseUrl` และการกำหนดค่าใหม่ในทุกการเชื่อมต่อที่มีอยู่ของโหนด การละเว้น `customJson` จะเก็บการกำหนดค่าที่เก็บไว้ การสลับ `apiType` เป็น `chat` หรือ `responses` จะลบออกจากโหนดและการเชื่อมต่อ

จากนั้นเพิ่มการเชื่อมต่อกับโหนดตามปกติ (`POST /api/providers` พร้อม id โหนด) และร้องขอ `<prefix>/<model>` เช่น `biz/assistant-v1` จุดสิ้นสุดไม่เปิดเผยรายการโมเดล ดังนั้นให้เพิ่มรหัสโมเดลด้วยตนเอง

## ขอแบบ

เทมเพลตเป็นแบบธรรมดา JSON ค่าสตริงอาจมีเครื่องหมาย `{{placeholder}}` ไม่มีสิ่งใดถูกประเมินหรือดำเนินการ และคีย์อ็อบเจ็กต์จะไม่ถูกแทนที่

| ตัวยึดตำแหน่ง        | ค่า                                                                    |
| -------------------- | ---------------------------------------------------------------------- |
| `{{prompt}}`         | ข้อความของข้อความผู้ใช้ล่าสุด (ส่วนข้อความที่รวมด้วยการขึ้นบรรทัดใหม่) |
| `{{messages}}`       | การสนทนาในรูปแบบการแชท OpenAI                                          |
| `{{model}}`          | รหัสโมเดลที่ร้องขอ โดยไม่มีคำนำหน้าของผู้ให้บริการ                     |
| `{{stream}}`         | `false` — ปลายทางจะตอบด้วยเอกสาร JSON หนึ่งฉบับเสมอ                    |
| `{{request.<path>}}` | ช่องคำขอแปล (รูปแบบแชท OpenAI )                                        |

- ค่าที่เป็นตัวยึดตำแหน่งเดียวจะเก็บประเภท JSON ไว้ (`"{{messages}}"` กลายเป็นอาร์เรย์) พื้นที่ที่สำรองไว้ภายในสตริงที่ยาวกว่าจะถูกแทรกเป็นข้อความ
- ตัวยึดตำแหน่งที่แก้ไขเป็นไม่มีอะไรจะทำให้คำขอล้มเหลวด้วย HTTP 400 แทนที่จะส่งเพย์โหลดที่ไม่สมบูรณ์
- เส้นทางใช้สัญลักษณ์จุดและดัชนีตัวเลข (`data.items[0].text`) `__proto__`, `prototype` และ `constructor` ถูกปฏิเสธในคีย์และพาธ

## คำตอบ

ค่าที่ `responsePath` จะกลายเป็นการตอบกลับของผู้ช่วย: สตริงที่ผ่านไป ค่า JSON อื่นๆ จะถูกทำให้เป็นอนุกรม ฟิลด์ที่หายไปหรือ `null` หรือเนื้อหาที่ไม่ใช่ JSON ส่งคืน HTTP 502 สถานะข้อผิดพลาดอัปสตรีมจะถูกส่งผ่าน สำหรับการสตรีมไคลเอนต์ OmniRoute จะรอการตอบสนอง JSON ทั้งหมด จากนั้นปล่อยมันเป็นก้อนเนื้อหาเดียวบวกกับชิ้นสุดท้าย นี่ไม่ใช่การสตรีมโทเค็น ฟิลด์การเรียกใช้เครื่องมือและการใช้งานไม่ได้รับการแมป

## ไม่เคยเล่นซ้ำ

คำขอทางธุรกิจอาจมีผลข้างเคียงแม้ว่าจะล้มเหลวก็ตาม OmniRoute จึงส่งครั้งเดียว:

- ไม่ต้องลองขนส่งอีกครั้งและไม่มีการเปลี่ยนเส้นทางดังต่อไปนี้
- ไม่ต้องลองอีกครั้งในการเชื่อมต่ออื่น (การสำรองบัญชี) — ความล้มเหลวจะถูกส่งกลับตามที่เป็นอยู่ และการเชื่อมต่อไม่เย็นลง
- ไม่มีทางเลือกอื่นไปยังเป้าหมายคอมโบถัดไป แม้ว่าจะว่างเปล่าหรือตอบกลับไม่สำเร็จก็ตาม

แยกคำขอไคลเอ็นต์และแผงฟิวชั่นที่เรียกหลายรุ่นอย่างชัดเจน ยังคงเรียกใช้จุดสิ้นสุดโดยแยกจากกัน

## การทดสอบโหนด

บันทึกการเชื่อมต่อ, การเชื่อมต่อ** ทดสอบ** การตรวจสอบสภาพของปุ่มและพื้นหลังจะไม่เรียกตำแหน่งข้อมูล แต่จะตรวจสอบการกำหนดค่าที่เก็บไว้เท่านั้นและรายงานการเชื่อมต่อว่าไม่สามารถตรวจสอบได้

`POST /api/provider-nodes/validate` พร้อม `"apiType": "custom-json"` และฟิลด์โหนด (`baseUrl`, `apiKey`, `customJson`, ตัวเลือก `customHeaders` และ `modelId`) ส่งคำขอจริงหนึ่งคำขอเท่านั้น โดยมี `ping` เป็นข้อความผู้ใช้ล่าสุด มันตอบ `{ "valid": true }` หรือสถานะต้นน้ำ (ไม่ใช่เนื้อหาต้นน้ำ)

## พื้นที่จัดเก็บ

การกำหนดค่าจะถูกเก็บไว้ใน `provider_nodes.custom_json_config_json` (การโยกย้าย `240_provider_node_custom_json_config.sql`) และคัดลอกไปยัง `providerSpecificData.customJson` ของแต่ละการเชื่อมต่อ

การใช้งาน: `open-sse/utils/customJson.ts` (การตรวจสอบความถูกต้องและการสร้างเทมเพลต), `open-sse/executors/customJson.ts` (ตัวดำเนินการ), `open-sse/services/combo/noReplayLatch.ts` และ `src/sse/handlers/chat/responsePolicies.ts` (ไม่เล่นซ้ำ)
