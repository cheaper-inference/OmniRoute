> **สรุปสั้นๆ**: OmniRoute ติดตามการใช้โทเค็นของทุกคำขอ คำนวณค่าใช้จ่าย บังคับใช้โควตาต่อคีย์ API และแสดงข้อมูลวิเคราะห์ในแดชบอร์ด คู่มือนี้อธิบายว่าทั้งหมดนี้ทำงานอย่างไร

**แหล่งข้อมูล:**

- `open-sse/services/usage.ts` (~70KB) — ระบบติดตามการใช้งานหลัก
- `src/lib/usageAnalytics.ts` (~10KB) — การรวบรวมข้อมูลสำหรับแดชบอร์ด
- `src/lib/db/quotaSnapshots.ts` — ข้อมูลประวัติโควตา
- `src/lib/db/usage*.ts` — โมดูลฐานข้อมูลหลายรายการที่เกี่ยวข้องกับการใช้งาน

## ภาพรวม

ทุกคำขอที่ไหลผ่าน OmniRoute จะสร้าง **ระเบียนการใช้งาน** ซึ่งบันทึกข้อมูลต่อไปนี้:

- **ข้อมูลระบุตัวตน**: คีย์ API, ผู้ให้บริการ, โมเดล และคอมโบที่ใช้
- **โทเค็น**: โทเค็นพรอมต์ โทเค็นผลลัพธ์ โทเค็นที่แคชไว้ และจำนวนรวม
- **ค่าใช้จ่าย**: จำนวนเงิน USD (คำนวณจากข้อมูลราคา)
- **เวลา**: เวลาแฝง และเวลาประทับเริ่มต้น/สิ้นสุด
- **สถานะ**: สำเร็จ ข้อผิดพลาด ถูกจำกัดอัตรา เป็นต้น

ระเบียนเหล่านี้จะถูกรวบรวมเป็น **ข้อมูลวิเคราะห์** จัดเก็บเป็น **สแนปช็อตโควตา** และใช้บังคับใช้ **ขีดจำกัดงบประมาณต่อคีย์**

```
คำขอ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    การวิเคราะห์ โควตา การเรียกเก็บเงิน
                    (แดชบอร์ด) (บังคับใช้) (ส่งออก)
```

## ข้อมูลที่บันทึก

บริการ `usage.ts` จะบันทึก **เหตุการณ์การใช้งาน** สำหรับทุกคำขอ:

| ฟิลด์              | ชนิด    | แหล่งที่มา                                                 |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID ที่สร้างขึ้นเมื่อบันทึก                               |
| `apiKeyId`         | string  | คีย์ API ที่เริ่มต้นคำขอ                                   |
| `provider`         | string  | ID ของผู้ให้บริการ (openai, anthropic ฯลฯ)                 |
| `model`            | string  | ID ของโมเดล (gpt-5, claude-opus-4-6 ฯลฯ)                   |
| `comboId`          | string? | ID ของคอมโบ หากกำหนดเส้นทางผ่านคอมโบ                       |
| `promptTokens`     | number  | จากการตอบกลับของผู้ให้บริการต้นทาง                         |
| `completionTokens` | number  | จากการตอบกลับของผู้ให้บริการต้นทาง                         |
| `cachedTokens`     | number  | โทเค็นที่พบในแคช (การแคชพรอมป์ต์ของ Anthropic ฯลฯ)         |
| `totalTokens`      | number  | พรอมป์ต์ + ข้อความที่สร้าง                                 |
| `costUsd`          | number  | คำนวณจากข้อมูลราคา                                         |
| `latencyMs`        | number  | ระยะเวลาของคำขอตั้งแต่ต้นจนจบ                              |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | คลาสข้อผิดพลาด หากสถานะไม่ใช่ success                      |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | ข้อมูลที่กำหนดเองซึ่งปลั๊กอินแทรกเข้ามา                    |

### โทเค็นมาจากที่ใด

โทเค็นจะถูกดึงจากการตอบกลับของผู้ให้บริการต้นทางใน **ตัวจัดการการตอบกลับ**:

```ts
// จาก open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

สำหรับผู้ให้บริการที่ไม่ส่งข้อมูลการใช้งานกลับมา (ผู้ให้บริการบางรายที่ใช้คุกกี้เว็บ) OmniRoute จะ **ประมาณ** จำนวนโทเค็นด้วยเกณฑ์โดยประมาณ `~4 chars per token` (ดู `open-sse/services/autoCombo/pipelineRouter.ts`)

### โทเค็นที่แคชไว้

OmniRoute ติดตาม `cached_tokens` แยกจาก `prompt_tokens` เนื่องจาก:

- การแคชพรอมป์ต์ของ Anthropic คิดค่าบริการในอัตราที่ลดลงสำหรับโทเค็นที่แคชไว้ (10% ของอัตราปกติ)
- ผู้ให้บริการบางรายส่งค่า `cache_read_input_tokens` กลับมา ซึ่งควรคิดราคาในอัตราที่ต่างกัน
- ข้อมูลวิเคราะห์สามารถแสดง **อัตราการพบข้อมูลในแคช** = `cached_tokens / prompt_tokens`

### การวินิจฉัยระดับการเขียนแคช

แผงสถานะแคชพรอมป์ต์ในแดชบอร์ดการวิเคราะห์จะแยกการเขียนแคชแบบ
5 นาทีและ 1 ชั่วโมงที่ผู้ให้บริการรายงาน ค่า
`usage.cache_creation.ephemeral_5m_input_tokens` และ
`usage.cache_creation.ephemeral_1h_input_tokens` ของ Anthropic จะยังคงอยู่ตลอดการแปลงข้อมูลการใช้งานทั้งแบบสตรีมและ
ไม่ใช่สตรีม และจัดเก็บไว้พร้อมสรุปบันทึกการเรียกใช้งาน ยอดรวม
การเขียนแคชจะไม่ถูกนำไปบวกซ้ำในกลุ่มเหล่านั้นอีกครั้ง

การเรียกใช้งานที่มีเพียงตัวนับการเขียนรวม ซึ่งรวมถึงระเบียนเก่า จะมีระดับที่ไม่ทราบ
หากมีการแจกแจงเพียงบางส่วน ส่วนที่เหลือซึ่งยังไม่ได้จัดสรรจะยังคงเป็นระดับที่ไม่ทราบ ตัวนับที่ไม่ถูกต้องหรือ
ขัดแย้งกันจะถูกทำเครื่องหมาย แทนการกำหนด TTL ให้โดยไม่แจ้งให้ทราบ ตัวระบุ
TTL ฝั่งคำขอไม่ใช่หลักฐานยืนยันระดับที่ถูกเรียกเก็บเงิน

ค่าประมาณการเขียนเทียบเท่า API ของแผงนี้ครอบคลุมเฉพาะระดับที่มีการรายงานและมีข้อมูลราคา ไม่ใช่
คำขอทั้งหมด สำหรับราคาโมเดล Claude/Anthropic แบบเนทีฟ จะใช้อัตรา 1.25 เท่าของ
อัตราอินพุตสำหรับการเขียนแบบ 5 นาที และสองเท่าของอัตราอินพุตสำหรับการเขียนแบบ 1 ชั่วโมง หากไม่มี
ข้อมูลราคา จะแสดงว่าไม่มีข้อมูล ไม่ใช่ศูนย์ ราคาจะถูกบันทึกเมื่อมีการบันทึกการเรียกใช้งานใหม่แต่ละครั้ง
ระเบียนในอดีตจะไม่ถูกคำนวณราคาใหม่ ดังนั้น บัญชีแบบสมัครสมาชิกจึงอาจมี
ค่าประมาณเทียบเท่า API โดยไม่ได้เสียค่าใช้จ่ายเป็นเงินจริงหรือใช้โควตาการสมัครสมาชิก
ตามจำนวนนั้น การคำนวณโควตา งบประมาณ และต้นทุนตามข้อมูลจริงของผู้ให้บริการที่มีอยู่จะไม่เปลี่ยนแปลง

การวินิจฉัยเหล่านี้ใช้สรุปสถานะแคชที่มีขอบเขตจำกัดและการเก็บรักษาบันทึกการเรียกใช้งาน
ที่มีอยู่ โดยไม่เปลี่ยนค่าเริ่มต้น TTL ของคำขอ การกำหนดเส้นทาง หรือการเลือกบัญชี
การบันทึก TTL ที่ไคลเอนต์ร้องขอเทียบกับ TTL ขาออกที่มีผลจริง ณ จุดส่ง
ไปยังผู้ให้บริการจะดำเนินการในภายหลัง แผงนี้รายงานระดับตามข้อมูลการเรียกเก็บเงิน ไม่ใช่ TTL ขาออกที่มีผลจริง

การนำไปใช้: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` และ `open-sse/utils/cacheWriteUsage.ts`

## การคำนวณค่าใช้จ่าย

ค่าใช้จ่ายคำนวณจาก **ข้อมูลราคา** ที่ซิงค์จาก LiteLLM (`src/lib/pricingSync.ts`):

| โมเดล             | อินพุต $/1M | เอาต์พุต $/1M | แคช $/1M |
| ----------------- | ----------- | ------------- | -------- |
| gpt-5             | $2.50       | $10.00        | —        |
| claude-opus-4-6   | $15.00      | $75.00        | $1.50    |
| claude-sonnet-4-5 | $3.00       | $15.00        | $0.30    |
| gemini-2.5-pro    | $1.25       | $10.00        | —        |

สูตรคำนวณค่าใช้จ่าย (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **เหตุใดจึงต้องหักแคชออกจากพรอมต์?** ส่วนที่แคชไว้มีการคิดราคาแยกต่างหาก การคิดราคาอินพุตจากพรอมต์ทั้งหมดจึงทำให้คำนวณเกินจริง

### การซิงค์ราคา

ข้อมูลราคาจะซิงค์จาก LiteLLM โดยอัตโนมัติผ่านเอนด์พอยต์ `/api/pricing/sync` (ทริกเกอร์โดยงาน cron ในตัว ไม่ใช่ตัวแปรสภาพแวดล้อมที่ผู้ใช้เข้าถึงได้):

```bash
# ทริกเกอร์ด้วยตนเอง
curl -X POST http://localhost:20128/api/pricing/sync
```

สำหรับโมเดลที่ไม่มีข้อมูลราคา OmniRoute จะใช้วิธี **ประมาณค่าใช้จ่าย** ด้วยอัตราเฉลี่ยภายในแทน (อ้างอิงจากข้อมูลราคาของ LiteLLM)

## การรวมข้อมูลตามช่วงวันที่

โมดูล `usageAnalytics.ts` คำนวณข้อมูลสำหรับวิดเจ็ตบนแดชบอร์ดจากข้อมูลการใช้งานดิบ โดยรองรับช่วงเวลา 7 แบบ:

| ช่วงเวลา | กรอบเวลา                            | กรณีใช้งาน                                |
| -------- | ----------------------------------- | ----------------------------------------- |
| `1d`     | 24 ชั่วโมงที่ผ่านมา                 | ตรวจจับค่าใช้จ่ายที่พุ่งสูงเป็นรายชั่วโมง |
| `7d`     | 7 วันที่ผ่านมา                      | ทบทวนรายสัปดาห์                           |
| `30d`    | 30 วันที่ผ่านมา                     | เรียกเก็บเงินรายเดือน                     |
| `90d`    | 90 วันที่ผ่านมา                     | วิเคราะห์รายไตรมาส                        |
| `ytd`    | ตั้งแต่วันที่ 1 มกราคมของปีปัจจุบัน | ติดตามงบประมาณรายปี                       |
| `all`    | ตลอดเวลา                            | สถิติตลอดอายุการใช้งาน                    |
| `custom` | วันเริ่มต้น/สิ้นสุดที่ผู้ใช้กำหนด   | การตรวจสอบและการสืบค้นเฉพาะกิจ            |

### วิดเจ็ตบนแดชบอร์ดที่คำนวณ

สำหรับช่วงวันที่ใดก็ตาม ชั้นการวิเคราะห์จะคำนวณ:

| วิดเจ็ต                          | คำอธิบาย                                                |
| -------------------------------- | ------------------------------------------------------- |
| **การ์ดสรุป**                    | คำขอทั้งหมด ค่าใช้จ่ายรวม โทเค็นทั้งหมด อัตราความสำเร็จ |
| **แผนภูมิแนวโน้มรายวัน**         | ค่าใช้จ่าย + โทเค็นต่อวัน ซ้อนแยกตามโมเดล               |
| **แผนที่ความร้อนของกิจกรรม**     | ตารางชั่วโมงในวัน × วันในสัปดาห์ สี = จำนวนคำขอ         |
| **รายละเอียดแยกตามโมเดล**        | แผนภูมิวงกลมแสดงค่าใช้จ่ายแยกตามโมเดล                   |
| **รายละเอียดแยกตามผู้ให้บริการ** | แผนภูมิแท่งแสดงคำขอแยกตามผู้ให้บริการ                   |
| **คีย์ API อันดับสูงสุด**        | ตารางคีย์ 10 อันดับแรกตามค่าใช้จ่าย                     |
| **การวิเคราะห์ข้อผิดพลาด**       | อัตราข้อผิดพลาดตามเวลา ประเภทข้อผิดพลาดที่พบบ่อยที่สุด  |

### การเข้าถึงผ่านโปรแกรม

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // ระเบียนประวัติการใช้งาน
  "7d",                 // ช่วงเวลา: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // แมปการเชื่อมต่อผู้ให้บริการ (connectionId → ชื่อบัญชี)
  {
    startDate: "2025-01-01",  // ไม่บังคับ: สำหรับช่วง "custom"
    endDate: "2025-06-01",   // ไม่บังคับ: สำหรับช่วง "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (เซนต์)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## การบังคับใช้โควตา

โควตาต่อคีย์ API จะถูกบังคับใช้ในสองจุด:

1. **ขีดจำกัดแบบแจ้งเตือน** (`quotaWarnAt`): แสดงคำเตือนบนแดชบอร์ดเมื่อการใช้งานเกินเกณฑ์
2. **ขีดจำกัดแบบบังคับ** (`quotaLimit`): ปฏิเสธคำขอด้วย HTTP 429 เมื่อเกินขีดจำกัด

### การกำหนดค่า

```ts
// ต่อคีย์ API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — แสดงคำเตือน
  quotaLimit: 10_00,    // $10.00 — หยุดการใช้งานทันที
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### ลำดับการบังคับใช้

```
คำขอ ──▶ quotaCheck()
              │
              ├── อยู่ภายในขีดจำกัด?  ──▶ อนุญาต
              │
              └── เกินขีดจำกัด?  ──▶ 429 Too Many Requests
                                   พร้อมส่วนหัว Retry-After
```

### สแนปช็อตโควตา

ตาราง `quotaSnapshots` จัดเก็บ **สถานะโควตาในอดีต** สำหรับการวิเคราะห์แนวโน้ม:

| ฟิลด์ | คำอธิบาย |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | คีย์ที่กำลังติดตาม |
| `window` | "day" | "week" | "month" |
| `used` | ค่าใช้จ่ายที่ใช้ไปในกรอบเวลานี้ (เซนต์) |
| `limit` | ขีดจำกัด (เซนต์) |
| `resetAt` | เวลาที่กรอบเวลาเริ่มต้นใหม่ |
| `createdAt` | เวลาที่บันทึกสแนปช็อต |

สแนปช็อตจะถูกบันทึก **ทุกครั้งที่มีคำขอ** ซึ่งมีค่าใช้จ่าย > 0 และนำไปใช้เพื่อ:

- แสดงแถบความคืบหน้าของโควตาบนแดชบอร์ด
- แสดงแผนภูมิแนวโน้มโควตา 30 วัน
- ส่งการแจ้งเตือนเมื่อการใช้งานใกล้ถึงขีดจำกัด

### สืบค้นข้อมูลวิเคราะห์การใช้งาน

เข้าถึงข้อมูลการใช้งานผ่านแดชบอร์ดหรือเครื่องมือ MCP ไม่ใช่ผ่านเอนด์พอยต์ REST สำหรับส่งออกข้อมูลโดยตรง ข้อมูลวิเคราะห์ที่มีให้ใช้งาน:

- **`/api/usage/analytics`** — เมตริกการใช้งานแบบรวม (จัดกลุ่มตามโมเดล ผู้ให้บริการ หรือคีย์)
- **`/api/usage/quota`** — สถานะโควตาปัจจุบันของแต่ละคีย์ API
- **`/api/usage/history`** — บันทึกประวัติคำขอ

## การเก็บรักษาและการล้างข้อมูล

ข้อมูลการใช้งานเพิ่มขึ้นประมาณ 1-10KB ต่อคำขอ เมื่อมีการใช้งานในปริมาณมาก ข้อมูลส่วนนี้อาจมีขนาดใหญ่มาก

### การตั้งค่าการเก็บรักษาข้อมูล

กำหนดค่าการเก็บรักษาประวัติการใช้งานได้ผ่านการตั้งค่าฐานข้อมูลใน UI หรือผ่าน `/api/settings/database`

ตามค่าเริ่มต้น ประวัติการใช้งานจะถูกเก็บไว้เป็นเวลา **90 วัน**

### การล้างข้อมูล

บันทึกเก่าจะถูกล้างโดย `src/lib/db/cleanup.ts`:

- ทำงานเมื่อถูกเรียกโดยกระบวนการ cron ที่ทำงานเบื้องหลัง
- ลบบันทึกจาก `usage_history` ที่เก่ากว่าระยะเวลาเก็บรักษาที่กำหนดไว้ในการตั้งค่า `usageHistory`

### การประมาณพื้นที่จัดเก็บ

| อัตราคำขอ        | พื้นที่จัดเก็บสำหรับ 30 วัน | พื้นที่จัดเก็บสำหรับ 90 วัน |
| ---------------- | --------------------------- | --------------------------- |
| 100 คำขอ/วัน     | ~3MB                        | ~9MB                        |
| 1,000 คำขอ/วัน   | ~30MB                       | ~90MB                       |
| 10,000 คำขอ/วัน  | ~300MB                      | ~900MB                      |
| 100,000 คำขอ/วัน | ~3GB                        | ~9GB                        |

สำหรับปริมาณการใช้งานที่สูงมาก ให้พิจารณา:

- ลดระยะเวลาเก็บรักษาข้อมูลผ่านการตั้งค่าฐานข้อมูล
- ใช้ `aggregated_metrics` แทนบันทึกดิบ (สำหรับการวิเคราะห์เท่านั้น)

## เคล็ดลับการปรับต้นทุนให้เหมาะสม

### 1. ใช้โมเดลที่เหมาะสม

```bash
# คำตอบด่วน — ใช้แบบประหยัด + รวดเร็ว
curl -d '{"model":"auto/fast","messages":[...]}'

# งานซับซ้อน — ใช้แบบคุณภาพสูง
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. เปิดใช้งานการแคช

การแคชพรอมป์ต์ของ Anthropic ช่วยประหยัด **90% สำหรับบริบทที่ใช้ซ้ำ**:

```ts
// การแคชทำงานอัตโนมัติ — เพียงใส่พรอมป์ต์ระบบขนาดใหญ่ชุดเดิม
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // จะถูกแคชโดยอัตโนมัติ
  messages: [{ role: "user", content: "..." }],
});
```

### 3. ใช้การบีบอัด

การบีบอัดด้วย RTK + Caveman ช่วยประหยัด **15-95% สำหรับเซสชันที่ใช้เครื่องมือเป็นหลัก**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. กำหนดโควตาแยกตามคีย์

กำหนด `quotaLimit` เสมอเพื่อป้องกันค่าใช้จ่ายที่พุ่งสูงเกินควบคุม:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // จำกัดที่ $10/เดือน
```

### 5. ตรวจสอบผู้ใช้ที่มีค่าใช้จ่ายสูงสุด

ใช้แดชบอร์ดหรือ **`/api/usage/analytics`** เพื่อจัดกลุ่มตามคีย์ API และเรียงลำดับตามค่าใช้จ่าย:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## การแก้ไขปัญหา

### "ค่าใช้จ่ายสูงกว่าที่คาดไว้"

1. ตรวจสอบ **`/api/usage/analytics?groupBy=model`** — ค้นหาโมเดลที่มีค่าใช้จ่ายสูง
2. ตรวจสอบ **`/api/usage/analytics?groupBy=apiKey`** — ค้นหาผู้ใช้ที่ใช้งานมาก
3. ตรวจสอบว่าข้อมูลราคาเป็นปัจจุบัน: `POST /api/pricing/sync`

### "ระเบียนหายไป"

- ตรวจสอบการตั้งค่าระยะเวลาเก็บข้อมูลของฐานข้อมูลใน แดชบอร์ด → ฐานข้อมูล → ล้างข้อมูล — ระเบียนเก่าจะถูกลบโดยงานล้างข้อมูลที่ทำงานเป็นระยะ (`src/lib/db/cleanup.ts`)
- ตรวจสอบข้อผิดพลาดใน `src/lib/db/usage*.ts` — ความล้มเหลวในการเขียนฐานข้อมูลจะถูกบันทึกลงล็อก แต่จะไม่แสดงให้เห็น
- ตรวจสอบว่าคำขอไปถึง `chatCore` จริง — ตรวจสอบการกำหนดเส้นทางแบบคอมโบ

### "โควตาไม่ถูกบังคับใช้"

- ตรวจสอบการตั้งค่า `quotaLimit` ของคีย์
- ตรวจสอบว่าตั้งค่า `quotaWindow` ถูกต้อง
- ค้นหาระเบียน `quotaSnapshots` — ควรมีการสร้างระเบียนเหล่านี้ในทุกคำขอ
