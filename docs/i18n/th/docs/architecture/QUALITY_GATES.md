## เกตสินค้าคงคลังและโปรไฟล์การดำเนินการ

### การรับสมัครผู้สมัคร

เวิร์กโฟลว์ CI และ Quality Gates ต่างก็ส่งคำตัดสินที่เสถียร: `Gate / CI` และ `Gate / Quality` นโยบายการรับเข้าศึกษาตามเวอร์ชันจะระบุงานขั้นต้นทุกงานตามความจำเป็นหรือตามคำแนะนำ งานที่จำเป็นที่เกี่ยวข้องจะต้องสำเร็จ: ขาดหายไป ยกเลิก ข้าม รอดำเนินการ และผลลัพธ์ที่ไม่รู้จักไม่สามารถสร้าง PASS ได้ การจัดหมวดหมู่เอกสารเท่านั้นหรือแค็ตตาล็อกเท่านั้นที่ถูกต้องอาจทำให้ช่องโค้ดใช้ไม่ได้ ร่างธรรมดา PR ไม่ได้รับการยอมรับจากผู้สมัคร ฉลาก `hotfix` ไม่ได้ยกเว้นหลักฐาน

เวิร์กโฟลว์ทั้งสองครอบคลุม PRs ลงในสาขา main/release, พุชไปที่ `main`, การจัดส่งด้วยตนเอง และเหตุการณ์กลุ่มผสาน พุช จัดส่ง และรวมกลุ่มดำเนินการเลือกทั้งหมด ร่างคิว Mergify ที่เชื่อถือได้ยังรันงาน `full-code`/`full-code-e2e` ที่เกี่ยวข้องด้วย PRs ธรรมดาจะข้ามไป ก่อนที่จะทำการผสานด้วยตนเอง ให้ดำเนินการจัดส่งแบบเต็มกับผู้สมัครที่แน่นอน การพุชไปที่ `release/**` จะไม่เริ่มเวิร์กโฟลว์เหล่านี้ Release-Green สังเกตฐานที่ผสานแยกกัน (`docs/ops/RUNNER_BOX.md` → Hosted lane) ทางแยกและกลุ่มรวมใช้นักวิ่งที่โฮสต์สำหรับงานที่เลือกนักวิ่งที่โฮสต์เอง ต้องตรวจสอบความจุที่โฮสต์เพียงพอก่อนเปิดตัว

PR ธรรมดาจะรันการเลือกที่รวดเร็ว ช่องทาง `full-code` และ `full-code-e2e` ของนโยบายการรับเข้า (E2E, การบูรณาการ, สิ่งประดิษฐ์ของแพ็คเกจ, Electron ควัน, Bun SQLite, ระบบนิเวศและไคลเอ็นต์โปรโตคอล) ทำงานเฉพาะบน Mergify Queue Draft หรือทำงานเต็ม: `gh workflow run ci.yml --ref <branch>`

ใบเสร็จรับเงิน JSON แต่ละใบจะระบุ SHA ที่เช็คเอาท์ การรันเวิร์กโฟลว์ และความพยายาม CLI ปฏิเสธ checkout/event SHA ที่ไม่ตรงกัน การทดสอบเวิร์กโฟลว์จะผูกการเป็นสมาชิกนโยบายเข้ากับรายการ `needs` ของงานตัดสิน ดังนั้นช่องทางใหม่หรือที่ถูกลบออกจะไม่หายไปอย่างเงียบๆ ใบเสร็จรับเงินครอบคลุมขั้นตอนการทำงานของตนเอง ไม่ใช่การเผยแพร่ การปรับใช้ หรือภายในของเครื่องสแกนที่ปรึกษาที่มีอยู่ การตรวจสอบที่เกี่ยวข้องตามที่กำหนดในกฎของสาขาเป็นการเปลี่ยนแปลงด้านการดูแลระบบที่แยกต่างหาก การกำหนดงานของพวกเขาไม่ได้ปกป้องสาขาด้วยตัวมันเอง

`API Route Typecheck` เป็นการตรวจสอบเวิร์กโฟลว์ที่เป็นอิสระ นอกทั้งคำตัดสินโดยรวมและโปรไฟล์คงที่ของผู้สังเกตการณ์แบบเต็มในพื้นที่ ตรวจสอบผลลัพธ์แยกกันเพื่อหาผู้สมัครที่แน่นอน `.github/workflows/api-route-typecheck.yml` รันบน PRs ลงใน `main` หรือ `release/**` พุชไปที่ตระกูลสาขา การจัดส่งแบบแมนนวล และเหตุการณ์ `merge_group` ประเภท `checks_requested` มันไม่มีตัวกรองเส้นทาง รวมกลุ่มตรวจสอบ `merge_group.head_sha`; กิจกรรมอื่น ๆ ตรวจสอบ `github.sha`. เหตุการณ์ทั้งหมดใช้การทดสอบเกทวินิจฉัยและหน่วยเกท API เดียวกัน เป้าหมายฐาน PR ขอเช็คใหม่ การแก้ไข body/title ใช้ชื่อ `Admission not requested / API Route Typecheck` แบบสังเกตการณ์เท่านั้น และไม่สามารถแทนที่การตรวจสอบการรับเข้าได้

### หลักฐานที่เก็บไว้ในตัวลดการยอมรับ

`scripts/quality/validate-release-acceptance.mjs` ลดแผนการจัดหาและรายการแผน; ไม่ได้กำหนดว่าแผนครอบคลุมไปป์ไลน์การปล่อยที่สมบูรณ์ รายงานกำหนด `releaseAcceptance: false` ไว้อย่างชัดเจน แม้ว่าแผนนั้นจะเป็น `VERIFIED` ก็ตาม เวิร์กโฟลว์ `release-acceptance.yml` ยังคงใช้การติดตั้งเงา ไม่ใช่บิลด์จริง แพ็คเกจ บูต หรือใบเสร็จรับเงินโปรโมชัน

CLI กำหนดให้ `--evidence-root` ตรวจสอบหลักฐานที่เก็บไว้ ไฟล์ได้รับการแก้ไขเป็น `<evidence-root>/<artifact_id>/<member>` และแฮชเป็น SHA-256 บันทึก PASS ที่ไม่มีหลักฐาน ไฟล์สูญหายหรือมีการเปลี่ยนแปลง เส้นทางที่ไม่ปลอดภัย หรือลิงก์สัญลักษณ์จะป้องกันการตรวจสอบ ไฟล์ที่หายไปไม่เท่ากับบันทึกที่สำเร็จที่ว่างเปล่า การตรวจสอบ SHA/run/attempt ที่มีอยู่ยังคงเป็นอิสระ: ไบต์ที่ตรงกันไม่สามารถช่วยเหลือใบเสร็จรับเงินเก่าได้ ความสมบูรณ์ของไฟล์ไม่ใช่ข้อพิสูจน์ถึงความถูกต้องของการดำเนินการหรือการส่งเสริมสิ่งประดิษฐ์

### DAST ใช้บิลด์ CI ที่ตรวจสอบแล้ว

งาน `dast-smoke` CI ที่จำเป็นจะเรียก `.github/workflows/dast-smoke.yml` หลัง `build` โดยเป็นไปตามการเลือก code/draft แบบเดียวกับบิวด์ รวมถึง fork PRs ที่รองรับ, PRs เป้าหมายการเผยแพร่ และกลุ่มที่ผสาน งาน DAST หายไป ล้มเหลว ยกเลิกหรือข้ามโดยไม่คาดคิด `Gate / CI` เวิร์กโฟลว์ที่ใช้ซ้ำได้ไม่มีทริกเกอร์ PR/dispatch อิสระ การตรวจสอบความถูกต้องด้วยตนเองใช้การจัดส่งของ CI ดังนั้นบิลด์และคอนซูเมอร์จึงยังคงอยู่ในการดำเนินการเดียว

`scripts/ci/next-build-provenance.mjs` ผนึกส่วน Next แบบเต็มด้วย tar digest, repository/event/run, ความพยายามของผู้ผลิต, head/base/checkout/tree, ข้อมูลประจำตัวเวิร์กโฟลว์, ไฟล์ล็อค, โหนด version/ABI ที่แน่นอน, แพลตฟอร์ม และบันเดิล DAST เลือกอาร์ติแฟกต์ ID ที่ไม่เปลี่ยนรูปจาก `needs.build.outputs` ต้องมีการยืนยันไดเจสต์การดาวน์โหลด และแฮช ZIP อย่างอิสระกับไดเจสต์ของผู้ผลิตก่อนที่จะแยกสมาชิกที่อนุญาตทั้งสองรายการผ่าน `scripts/ci/unpack-ci-build.py` ไฟล์ Manifest และไฟล์ tar ต้องตรงกับเอาต์พุตของผู้ผลิตอิสระก่อนที่จะแยกแผนผัง Next มันไม่เคยค้นหาการสร้างสาขาที่ประสบความสำเร็จล่าสุด การรันซ้ำบางส่วนอาจใช้ความพยายามของผู้ผลิตคนเดิมซ้ำเมื่อ ID และอินพุตทั้งหมดยังคงตรงกัน ใบเสร็จจะบันทึกความพยายามทั้งสองครั้ง

ผู้ใช้บริการจะอยู่บน Linux runner ที่โฮสต์โดยได้รับอนุญาตจากพื้นที่เก็บข้อมูลแบบอ่านอย่างเดียวและไม่มีความลับของพื้นที่เก็บข้อมูล โดยจะติดตั้งเวอร์ชัน Node ที่แน่นอนของผู้ผลิต จากนั้นประกอบ CLI ด้วย `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` `scripts/build/standaloneInput.mjs` ปฏิเสธเซิร์ฟเวอร์แบบสแตนด์อโลนที่ขาดหายไปก่อนที่จะสร้างทางเลือกใดๆ CLI บิวด์โลคัลปกติจะคงทางเลือกที่มีอยู่ไว้ ความพร้อมของเซิร์ฟเวอร์ Schemathesis และ promptfoo จะต้องสำเร็จทั้งหมดภายในขีดจำกัดงาน 25 นาทีที่ไม่เปลี่ยนแปลง ใบเสร็จรับเงินที่มาจากพิสูจน์ตัวตนและไบต์ของอินพุต ไม่ใช่การสแกน DAST ที่ประสบความสำเร็จ สิ่งประดิษฐ์หมดอายุ การหยุดชะงักของนักวิ่ง หรือเครื่องสแกนที่ล้มเหลวยังคงมีหลักฐานที่ไม่สมบูรณ์หรือล้มเหลว มันไม่สามารถกลายเป็น PASS ผ่าน wrapper ที่ปรึกษาได้

### ความสามารถในการดำเนินการ UI

CI รันสินค้าคงคลัง UI เต็มรูปแบบโดยแบ่งเป็นส่วนย่อยเมทริกซ์ `test-vitest` สี่ส่วน โดยแต่ละส่วนมีผู้ปฏิบัติงานสูงสุดสองคนต่อส่วนย่อย และมีกำหนดเวลางาน 15 นาทีที่มีอยู่ ชาร์ดแรกยังรันชุด MCP/autoCombo Vitest อีกด้วย ผลลัพธ์ของงานที่ต้องการครอบคลุมทุกขาเมทริกซ์ ความล้มเหลวหรือการยกเลิกชิ้นส่วนหนึ่งไม่สามารถสร้างการรับผู้สมัครได้

ผู้สังเกตการณ์ทุกคืนเก็บใบเสร็จรับเงินของผู้สมัครที่แน่นอนแยกต่างหากสำหรับชิ้นส่วน UI แต่ละชิ้น รวมถึงการดำเนินการ MCP ในการรับครั้งแรก จำเป็นต้องมีใบเสร็จรับเงิน บันทึก และข้อมูลประจำตัวการดำเนินการที่ตรงกันทั้งสี่รายการ `npm run test:vitest:ui` ในพื้นที่ยังคงเลือกชุดที่สมบูรณ์ การรัน `--shard` หนึ่งครั้งเป็นเพียงหลักฐานบางส่วนเท่านั้น

### การรวบรวมความคุ้มครองหน่วย

ชาร์ดยูนิตทั้ง 12 ชิ้นรวบรวมความครอบคลุม V8 ในระหว่างการทดสอบที่มีอยู่ ชาร์ดที่ประสบความสำเร็จเรียกใช้ `scripts/ci/compact-v8-coverage.mjs` เพื่อบีบอัดไฟล์ต้นฉบับโดยไม่ต้องสร้างรายงานอิสตันบูลระดับกลาง งานความครอบคลุมขั้นสุดท้ายจะตรวจสอบรายการทั้งสิบสองรายการกับผู้สมัคร SHA, รันไทม์, รูทต้นทาง และแฮชข้อมูล จากนั้นจึงรันผู้รายงานของ c8 และเกณฑ์ความครอบคลุมที่มีอยู่ อินพุตยังคงรักษาลำดับชื่อไฟล์ทั่วโลกของ c8 การรวมล่วงหน้าต่อส่วนข้อมูลไม่ปลอดภัยสำหรับการครอบคลุม function/block แบบผสม ชิ้นส่วนที่หายไป มีรูปแบบไม่ถูกต้อง หรือเข้ากันไม่ได้ไม่ผ่านการพิจารณา ชิ้นส่วนทดสอบที่ล้มเหลวจะคงความครอบคลุมของการวินิจฉัยดิบไว้แยกกัน มันไม่สามารถเข้าสู่การรวมครั้งสุดท้ายได้

### ใบเสร็จรับเงินความคืบหน้าการดำเนินการหน่วย

คำสั่ง `test:unit:ci:shard` ที่ใช้ร่วมกันจะบันทึกเฟส `primary`, `dashboard` และ `serial` ผ่าน `scripts/ci/unit-progress-reporter.mjs` รายงานผลการทดสอบปกติยังคงมีอยู่ ใบเสร็จรับเงินเฉพาะข้อมูลเมตาที่แยกต่างหากจะบันทึกการเริ่มต้นและสิ้นสุดของแต่ละไฟล์ และการเต้นของหัวใจ 30 วินาทีจะแสดงรายการไฟล์ที่ยังคงใช้งานอยู่และเวลาที่ผ่านไป โดยจะบันทึกเฉพาะข้อมูลเมตาการดำเนินการที่อนุญาตเท่านั้น คำอธิบายการทดสอบ เอาต์พุต เนื้อหาข้อผิดพลาด และสภาพแวดล้อมทั้งหมดจะไม่ถูกทำให้เป็นอนุกรม

CI เก็บไฟล์ JSONL ไว้เป็น `unit-progress-ci-<run>-<attempt>-<shard>` การหมดเวลางานสามารถป้องกันการอัปโหลดในภายหลังได้ การเต้นของหัวใจที่ปล่อยออกมาแล้วยังคงเป็นหลักฐานการวินิจฉัย การเต้นของหัวใจที่หายไปยังอาจสะท้อนถึงกระบวนการวิ่งที่ถูกบล็อกหรือยุติลง ใบเสร็จรับเงินเหล่านี้จะรักษาการเลือกการทดสอบ ความพร้อมกัน กำหนดเวลา และสถานะการออกข้อสอบที่มีอยู่ ไม่ใช่คำตัดสินของผู้สมัครรับเข้าเรียน

### รวมคิว

ป้ายกำกับ `queue` จะส่ง PR ไปยังคิว Mergify (`.mergify.yml`) Mergify จะเปิดร่าง PR ในสาขา `mergify/merge-queue/`, CI ดำเนินการเลือกแบบเต็มที่นั่น และ PR ดั้งเดิมจะรวมเข้าด้วยกันเมื่อ `Gate / CI`, `Gate / Quality` และ `Merge integrity (changelog + generated skills)` ผ่าน

Mergify เขียนสรุปคิวลงในคำอธิบายของแบบร่าง เหตุการณ์ Body/title-only `pull_request` `edited` ใช้กลุ่มการทำงานพร้อมกันเฉพาะการรัน และไม่มีการรันการจัดประเภทซ้ำ เมทริกซ์ทดสอบ ความสมบูรณ์ของการผสาน หรือคำตัดสินการรับเข้า ชื่อการตรวจสอบเพื่อการสังเกตเท่านั้นไม่สามารถแทนที่ `Gate / CI` หรือ `Gate / Quality` ได้ การแก้ไขที่เปลี่ยนแปลงฐานเป้าหมายร้องขอการตรวจสอบผู้สมัครใหม่

หลังจากการถอนคิว การพุชจะไม่ส่ง PR ใหม่เสมอไป แสดงความคิดเห็นเกี่ยวกับ `@mergifyio queue`

### สินค้าคงคลังสแกนแบบคงที่

สินค้าคงคลัง npm-alias เวอร์ชันและการเป็นสมาชิกการสแกนแบบคงที่อยู่ใน `config/quality/gate-manifest.json` เรียกใช้ `npm run check:gate-manifest` เพื่อตรวจสอบชื่อสคริปต์และคำสั่งที่ตรงกับ `package.json` การเพิ่ม การลบ และการดริฟท์คำสั่งจะล้มเหลวทั้งงาน hook ในเครื่องและงานการจัดประเภทการเปลี่ยนแปลงใน CI นามแฝงไม่ใช่งานเวิร์กโฟลว์ อินสแตนซ์เมทริกซ์ หรือกรณีทดสอบ: จำนวนเหล่านี้ต้องไม่แสดงให้ใช้แทนกันได้

ใช้ `npm run quality:scan -- --list` หรือ `npm run quality:scan:fast -- --list` เพื่อตรวจสอบนามแฝงที่เลือกโดยไม่ต้องดำเนินการ รันเนอร์เรียกใช้จุดเข้าใช้งาน npm ดังนั้นรันไทม์ (รวมถึง Bun ที่กำหนดค่าไว้) จึงยังคงอยู่ รายการบันทึกนามแฝงภายนอกโปรไฟล์เหล่านั้นตามที่เรียกใช้แยกต่างหาก และคำสั่งการบำรุงรักษาไม่ได้รับอนุญาตในโปรไฟล์การสแกนแบบอ่านอย่างเดียว

โปรไฟล์เหล่านี้ครอบคลุมเฉพาะการสแกนแบบคงที่เท่านั้น พวกเขาไม่รับรองการทดสอบผลิตภัณฑ์ ความครอบคลุม บรรจุภัณฑ์ การตรวจสอบภายนอก หรือการยอมรับการเปิดตัวเต็มรูปแบบของผู้สมัคร การรับเข้าเวิร์กโฟลว์ใช้ `config/quality/admission-policy.json` และ `scripts/quality/admission-verdict.mjs` ที่เชื่อมโยง โปรไฟล์ผู้สังเกตการณ์การเปิดตัวยังคงแยกจากกัน ตรวจสอบเช็คและใบเสร็จรับเงินที่เกี่ยวข้องอย่างอิสระ คำสั่งคงที่ของผู้สังเกตการณ์แบบเต็มจะถูกประกาศใน `config/quality/release-green-static-profile.json` รวมถึง `audit:deps` การเลือกการทดสอบการกลายพันธุ์ และการตรวจสอบการแปล ตัวโหลดตรวจสอบคำสั่ง npm กับ package.json และการประกาศ CI/Quality แบบจำลอง มันปฏิเสธการดริฟท์แทนที่จะดำเนินการโทเค็นเชลล์เป็นอาร์กิวเมนต์ เอาต์พุต SKIP/INCOMPLETE ของสแกนเนอร์ที่จำเป็นไม่สามารถสร้าง PASS ได้ โปรไฟล์จะบันทึกข้อยกเว้นภายนอกและไม่ได้แทนที่ความครอบคลุมที่โฮสต์ เมทริกซ์ทดสอบ แพ็กเกจ หรือหลักฐานการใช้งาน รายการร้อยแก้วด้านล่างเป็นข้อมูลอ้างอิง ไม่ใช่ข้อพิสูจน์ว่าประตูวิ่งจริง

สคริปต์อยู่ภายใต้ `scripts/check/` (ประตูนโยบาย) และ `scripts/quality/` (เครื่องมือวงล้อ) แหล่งที่มาของความจริง CI คือ `.github/workflows/ci.yml`

### ความสมบูรณ์ของเอกสารฐานที่เผยแพร่

`.github/workflows/i18n-base-health.yml` สังเกตความสมบูรณ์ของเอกสารหลังจากการพุชที่เลือกไปยัง `main` และ `release/v*` และในการจัดส่งด้วยตนเอง ตัวกรองครอบคลุมเอกสารประกอบ, Root Markdown, `llm.txt`, การแปล state/configuration และเครื่องมือ i18n ที่เกี่ยวข้อง งาน `Published base documentation health` เดียวใช้ Ubuntu ที่โฮสต์และกำหนดเวลาห้านาที จะทำการตรวจสอบแบบอ่านอย่างเดียวและเขียนใบรับการวินิจฉัยโดยไม่ต้องมีการติดตั้งการขึ้นต่อกัน การแปล หรือการนำสถานะไปใช้

`scripts/i18n/check-base-health.mjs` ต้องการความไม่สอดคล้องกันของซอร์สแฮช, เป้าหมายที่หายไป, แฮชเป้าหมาย, การแปลเก่า และแคชของส่วน นอกจากนี้ยังตรวจสอบขอบเขต document/locale หลักปัจจุบันและแหล่งที่มาที่บันทึกไว้ บริบทไม่ถูกต้อง ความครอบคลุมที่ไม่สมบูรณ์ หรือตัวตรวจสอบที่ถูกขัดจังหวะทำให้เกิด `INCOMPLETE` ยืนยันดริฟท์ผลิต `FAIL` ทั้งสองส่งคืนสถานะการออกที่ล้มเหลว ใบเสร็จรับเงินเชื่อมโยงกับการชำระเงิน SHA เวิร์กโฟลว์ เรียกใช้และพยายาม และจะคงไว้เป็น `i18n-base-health-<sha>-<run>-<attempt>`

นี่เป็นข้อสังเกตที่เป็นอิสระจากฐานที่เผยแพร่ จะไม่เพิ่มเหตุการณ์ PR หรือกลุ่มผสาน การตรวจสอบ PR ที่จำเป็น นามแฝง npm หรือสมาชิกโปรไฟล์การสแกนแบบคงที่ ตัวตรวจสอบพื้นฐานยังบล็อกทั้งห้าคลาสในโหมดสัมบูรณ์ การเตรียม PR ทั่วไปยังคงแยกจากการรับเข้า การอัปโหลดที่สำเร็จไม่สามารถเปลี่ยนผลลัพธ์ด้านสุขภาพที่ล้มเหลวเป็น PASS ได้

PR ทั่วไปใช้ `--preflight` กับรายงานพื้นฐานที่สร้างโดย `--baseline-evidence` อาจทำให้ต้นฉบับภาษาอังกฤษค้างอยู่เฉพาะเมื่อบันทึกการแปลที่สมบูรณ์และไบต์เป้าหมายที่แท้จริงไม่เปลี่ยนแปลงจากฐานที่แน่นอนนั้น ความไม่สอดคล้องกันของเป้าหมายใหม่หรือแคชส่วนยังคงบล็อก และหลักฐานที่ไม่สมบูรณ์ไม่สามารถอนุมัติการเตรียมการได้ รายงานเปิดเผย `preparationPending` และ `mergeReady` แยกกัน: การเตรียมการที่ประสบความสำเร็จไม่ได้ทำให้การแปลที่รอดำเนินการพร้อมที่จะรวมเข้าด้วยกัน รีเฟรชกระจกที่ได้รับผลกระทบในตัวผู้สมัครที่ประกอบขึ้นก่อนเข้ารับการรักษา ผู้สมัครคิว Mergify ที่เชื่อถือได้ `merge_group` การพุชสาขาและการรัน CI แบบแมนนวลใช้ตัวตรวจสอบแบบสัมบูรณ์ โดยไม่มี `--warn` หรือการให้อภัยความล้มเหลวที่สืบทอดมา แฮชเป้าหมายที่หายไปและขอบเขตที่ลดลงโดยไฟล์หลักที่บันทึกไว้ที่ถูกลบไม่สามารถให้คำตัดสินที่สมบูรณ์ได้สำเร็จ

### ปล่อยเส้นทางด่วน PR (`quality.yml`)

`.github/workflows/quality.yml` เสริม CI บน main/release PRs พุชไปที่ `main` จัดส่งและรวมกลุ่ม PRs ใช้การตรวจสอบด่วนแบบกรองพาธ โครงสร้างที่ซ้ำกันที่ปิดใช้งานอย่างถาวรถูกลบออก เช็ค build/package/boot จริงจะยังคงอยู่ใน CI ชุดหน่วยและ vitest ทำงานเฉพาะใน CI (`Unit Tests (N/12)` และ `Vitest`)

| งาน                                              | ขอบเขต                                                                                                                                                                                              | การปิดกั้น          |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; เอกสารอ้างอิง API และเอกสารทั้งหมด                                                                                                                                                   | ใช่                 |
| `Fast Quality Gates`                             | รหัส PRs; การตรวจสอบแบบคงที่ การตรวจสอบประเภท การตรวจสอบประเภทแดชบอร์ด การทดสอบหน่วยที่ได้รับผลกระทบ                                                                                                | ใช่                 |
| `Forgotten sibling tests`                        | รหัส PRs; เปลี่ยนโมดูลที่ติดตามไปยังผู้บริโภคแบบคงที่และการทดสอบพี่น้องของผู้สมัคร เส้นทางบาร์เรลและการนำเข้าแบบไดนามิกได้รับการรายงานเป็นการวินิจฉัยเชิงแนะนำ โดยมีข้อยกเว้นรายการที่อนุญาตอ้างอิง | **ที่ปรึกษา**       |
| `No new ESLint warnings`                         | รหัส PRs; การ์ดป้องกันผ้าสำลีที่รับรู้ถึงการปราบปราม                                                                                                                                                | ใช่ รวมทั้งส้อมด้วย |
| `Merge integrity (changelog + generated skills)` | PRs ที่ไม่ใช่ฉบับร่าง ; บันทึกการเปลี่ยนแปลงและการซิงค์ทักษะที่สร้างขึ้น                                                                                                                            | ใช่ รวมทั้งส้อมด้วย |

#### รายงานผลการตรวจพี่น้องที่ถูกลืม

`npm run check:forgotten-sibling-tests` ทำงานเป็นขั้นตอนคำแนะนำของ `Fast Quality Gates` และนำตัวแก้ไขการนำเข้ากลับมาใช้ใหม่เบื้องหลังแมปการทดสอบผลกระทบ สำหรับทุกโมดูลการผลิตที่เปลี่ยนแปลง ระบบจะรายงานห่วงโซ่ `changed module/symbol -> static consumer -> candidate sibling test` ที่กำหนดไว้ เมื่อไม่มีการทดสอบผู้สมัครจากส่วนต่างคำขอดึง สรุป Markdown และผลลัพธ์ JSON จะถูกเก็บไว้เป็นอาร์ติแฟกต์เวิร์กโฟลว์ `forgotten-sibling-tests` สำหรับการสอบเทียบก่อนการเปิดตัวบล็อกใดๆ

การส่งออกซ้ำแบบ Barrel และการนำเข้าแบบไดนามิกเป็นเพียงการวินิจฉัยความละเอียดเท่านั้น พวกเขาไม่เคยสร้างการค้นพบที่ปิดกั้น ข้อยกเว้นที่ตรวจสอบแล้วอยู่ใน `config/quality/forgotten-sibling-allowlist.json` แต่ละรายการจะต้องตั้งชื่อการทดสอบผู้บริโภคและผู้สมัคร ให้เหตุผลเฉพาะ และเชื่อมโยงปัญหา GitHub หรือคำขอดึง รายการที่มีรูปแบบไม่ถูกต้องปิดไม่สำเร็จ ข้อยกเว้นไม่สามารถระงับการทดสอบผู้สมัครที่ถูกลบหรือส่วนต่างที่เพิ่ม `.skip`/`.todo`; การลดทอนการยืนยันและการมาสก์อื่น ๆ ยังคงเป็นของเกต `check:test-masking` ที่ปิดกั้นอย่างอิสระ

#### โปรแกรมตรวจสอบการพิมพ์สองโปรแกรมตอบต่างกัน

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) และ `check:build-typecheck` คอมไพล์โปรแกรมที่แตกต่างกันภายใต้ตัวเลือกที่แตกต่างกัน และไฟล์เดียวกันสามารถล้างได้ในไฟล์หนึ่งและเต็มไปด้วยข้อผิดพลาดในอีกไฟล์หนึ่ง

`tsconfig.build.json` ตั้งค่า `"strict": false` ดังนั้น `noImplicitAny` จึงปิดอยู่ การกำหนดค่าหลักจะรวบรวมรายการที่อนุญาต 27 ไฟล์ที่คัดสรรแล้วพร้อมตัวเลือกที่เข้มงวดกว่าและเป็นไปตามกราฟการนำเข้าของแต่ละรายการ ดังนั้นไฟล์ที่ไม่เคยปรากฏในโปรแกรมบิลด์จะยังคงถูกตรวจสอบอยู่ที่นั่น

ผลที่ตามมามีความสำคัญเมื่อตัดสินว่าไฟล์ถูกพิมพ์หรือไม่:**การวินิจฉัยเป็นศูนย์ภายใต้ `check:build-typecheck` ไม่ได้หมายความว่าเป็นศูนย์** . การแยก `@ts-nocheck` จากไฟล์ 26 ไฟล์แสดงให้เห็นว่า 23 ไฟล์นั้นสะอาดในโปรแกรมบิลด์ สิบหกรายการพบข้อผิดพลาดโดยนัยประมาณ 120 รายการในส่วนที่เข้มงวด ตรวจสอบทั้งสองอย่างก่อนที่จะเรียกไฟล์ให้สะอาด

#### `check-ui-value-drift` — ประตูการแปลเก่า

จับการถดถอย i18n อย่างหนึ่งที่ประตูอื่นๆ ไม่สามารถมองเห็นได้ในเชิงโครงสร้าง: ค่าภาษาอังกฤษจะถูกเขียนใหม่และคำแปลที่ได้มาจาก _previous_ English ยังคงอยู่ข้างหลัง ดังนั้นผู้ใช้ที่ไม่ได้ใช้ภาษาอังกฤษจึงอ่านสำเนาด้วยถ้อยคำอย่างมั่นใจ ซึ่งตอนนี้เป็นสำเนาที่ผิด

อันนี้ส่งจริง.. `oauthModal.googleOAuthWarning` ถูกเขียนใหม่เมื่อตัวช่วยเข้าสู่ระบบ Antigravity ลงจอด (#5203);**39 จาก 43 แห่ง** เก็บข้อความบอกโอเปอเรเตอร์ให้ "คัดลอก URL แบบเต็มแล้ววางไว้ด้านล่าง" — โฟลว์ที่ไม่สามารถดำเนินการได้สำหรับผู้ให้บริการรายนั้น ไม่มีใครสังเกตเห็นจนกระทั่ง #8463 เพราะ:

- `sync-ui-keys` จะทดแทนคีย์ที่เป็นเท่านั้น **ไม่มา** ไม่เคยเป็นแบบนั้น **เหม็นอับ** ;
- `check-ui-keys-coverage` นับคีย์ _presence_ ดังนั้นคะแนนการแปลเก่าจึงถือว่าครอบคลุม
- `check-translation-drift` ติดตามเอกสาร `docs/i18n/<locale>/**.md` สะท้อน — ไม่เคยอ่าน `src/i18n/messages/*.json` การบล็อกในงาน `docs-sync-strict` นับตั้งแต่การซิงค์ใหม่ในปี 2569-52: แก้ไขเอกสารหลัก → `npm run i18n:run -- --files=<doc>` (ระดับส่วน ราคาถูก)

**รับรู้ความแตกต่าง ไม่ได้รับการสนับสนุนพื้นฐาน** โดยจะเปรียบเทียบ `en.json` ที่ฐานผสานกับแผนผังการทำงาน สำหรับคีย์ทุกอันที่ค่าภาษาอังกฤษเปลี่ยนไป สถานที่ใด ๆ ที่ยังคงมีคำแปลที่ยังไม่ได้ถูกแตะต้องนั้นจะไม่เก่า นี้จงใจ **ระงับหนี้ที่มีอยู่แล้ว** ส่วนต่าง — ไม่สามารถเปิดเผยได้ว่าคำแปลที่มีมายาวนานในภาษาอังกฤษโบราณมาจากภาษาใด ดังนั้นประตูจะตัดสินเฉพาะการเปลี่ยนแปลงที่เกิดขึ้นในปัจจุบันเท่านั้น ทางเลือกอื่น (พื้นฐานแฮชต่อคีย์) จะใช้ไฟล์ที่สร้าง ~ 600 KB โดย 3 × เป็นไฟล์พื้นฐานที่ใหญ่ที่สุดที่มีอยู่ โดยจะปั่นในทุก ๆ i18n PR

สองวิธีเพื่อตอบสนองความต้องการ:

1. อัปเดตคำแปลที่ได้รับผลกระทบหรือ
2. ตั้งค่าเป็น `__MISSING__:<new english>` — รันไทม์จากนั้นให้บริการภาษาอังกฤษที่แก้ไข (`src/i18n/request.ts::deepMergeFallback`, #7258) และคิวคีย์สำหรับการแปล

ถ้าเป็นเชือก **ความหมาย** เปลี่ยนแล้วชอบ **เปลี่ยนชื่อคีย์** : คีย์ใหม่ไม่สามารถสืบทอดการแปลเก่าได้ นั่นคือรูปแบบที่ #8463 ใช้

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

value-drift และ new-key gates แบ่งปันการเปรียบเทียบที่ไม่เปลี่ยนรูปแบบจาก `scripts/i18n/resolve-ui-diff-base.mjs` ขั้นตอนการทำงานจะส่งผ่านฐาน ปลายฐาน และ SHAs ของตัวเลือกเดียวกันไปยังการตรวจสอบทั้งสอง PR/base-retarget, push และ merge-group run ใช้บริบทของเหตุการณ์ การจัดส่งสาขาผู้สมัครต้องมี PR แบบเปิดที่แน่นอนหรืออินพุต `i18n_base_sha` ที่ชัดเจน การจัดส่งหรือการสังเกตตามกำหนดเวลาของ `main` หรือ `release/vX.Y.Z` โดยไม่มีอินพุตนั้นเปรียบเทียบการคอมมิตครั้งล่าสุดกับพาเรนต์ตัวแรก ไม่ใช่การตรวจสอบหนี้การแปลที่สืบทอดมาทั้งหมด การร้องขอเฉพาะที่จำเป็นต้องมีฐานการเปรียบเทียบที่ชัดเจน เช่น คำสั่ง `BASE_REF` ด้านบน

บริบทการเปรียบเทียบที่ขาดหายไปหรือคลุมเครือ แค็ตตาล็อกที่จำเป็นที่อ่านไม่ได้หรือไม่ถูกต้อง และตัวเลือกที่เปลี่ยนแปลงจะสร้าง `INCOMPLETE` พร้อมรหัสทางออก **2** รวมถึงในโหมดเตือนด้วย แคตตาล็อกอ่านใช้ `scripts/i18n/read-ui-catalog.mjs`; ความล้มเหลวในการอ่านจะไม่ถูกแทนที่ด้วยวัตถุว่าง ทั้งฐานที่ไม่พร้อมใช้งานหรืออินพุตที่ไม่สมบูรณ์จะสร้าง PASS

## ระยะเร่งความเร็ว (2026-08-30 → v4.0 LTS): ผ่อนปรนค่าฐานทุกค่า 20%

การตัดสินใจของผู้รับผิดชอบ (2026-08-30): จนกว่าจะมีการปรับโครงสร้างเป็นโมดูลใน v4.0 ความเร็วในการส่งมอบมีความสำคัญมากกว่า
การควบคุมหนี้ทางเทคนิคให้อยู่ในระดับเดิม ค่าฐานแบบ ratchet ที่เป็น **ตัวเลข** ทุกค่าถูกผ่อนปรน 20% ในรอบเดียว
ที่ตรวจสอบย้อนหลังได้ และมีการประกาศระยะนี้ไว้ใน `config/quality/quality-baseline.json`:

```json
"_policy": { "phase": "velocity", "since": "2026-08-30", "until": "4.0.0",
             "relaxPct": 20, "requireTighten": false }
```

- `npm run quality:relax-baselines -- --pct 20 --note velocity_YYYY_MM_DD [--dry-run]` — การผ่อนปรนแบบ

  ตารางในสรุปการรัน workflow และอัปโหลดรายงาน JSON/Markdown เป็น
  `baseline-headroom-<run_id>` โดยเก็บรักษาไว้ 90 วัน แถวคำเตือนและวิกฤตจะระบุเกณฑ์
  ที่เหลือระยะไม่เกิน 10% ก่อนถึงขีดจำกัด หรือเกินขีดจำกัดไปแล้ว ให้ตรวจสอบรายงานเหล่านี้เพื่อเป็นสัญญาณเตือนล่วงหน้า
  ว่างบประมาณกำลังถูกใช้ไป และตรวจสอบหมายเหตุ `_rebaseline_*` ของเกณฑ์ที่เป็นปัญหา งานนี้จะไม่
  สร้างหรืออัปเดต issue ถาวรอีกต่อไป; #12149 เก็บรักษาประวัติรายงานก่อนหน้านี้ไว้

**โหมดโค้ดใหม่ (Clean-as-You-Code) — ตั้งแต่ 2026-08-30 เฉพาะเส้นทางด่วนของ PR**

ในเหตุการณ์ `pull_request` ไฟล์ `quality.yml` จะส่ง `--base-ref <PR base SHA>` ให้กับ `check:file-size`,
`check:complexity-ratchets` และ `check:dead-code` สำหรับ `check:complexity-ratchets` และ
`check:dead-code` เกณฑ์จะเปรียบเทียบ HEAD กับ merge-base โดย **จำกัดเฉพาะไฟล์ที่ PR
แก้ไข** (`scripts/check/newCodeMode.mjs`: merge-base จะถูกสร้างเป็นไฟล์จริงใน
`git worktree` ชั่วคราว จากนั้นรัน ESLint/knip ที่นั่นและบน HEAD แล้วหาผลต่างของจำนวนต่อไฟล์):

- **บล็อก** — PR เพิ่มการละเมิด cyclomatic/cognitive หรือ dead exports ในไฟล์ที่แก้ไข
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` ในบันทึก);
- **คำแนะนำ** — ยอดรวมทั้งหมดในระบบเทียบกับค่าฐานที่ตรึงไว้ ความคลาดเคลื่อนที่สืบทอดมาจะไม่ทำให้
  PR ที่ไม่เกี่ยวข้องล้มเหลว โดยจะมีการติดตามความคลาดเคลื่อนดังกล่าวเพื่อแก้ไขในการกระทบยอดตอนออกรุ่น และเฝ้าระวังโดย
  งาน headroom

`check:file-size` ใช้ base ref ตามเงื่อนไขของตัวเอง (`scripts/check/check-file-size.mjs`, #8522):
โดยจะตรวจสอบไฟล์ซอร์สและไฟล์ทดสอบทุกไฟล์ใน tree อ่านจำนวนบรรทัดของแต่ละไฟล์ ณ ฐานของ PR
ด้วย `git show` และทำให้ไฟล์ล้มเหลวเฉพาะเมื่อไฟล์ขยายเกินค่าที่มากกว่าระหว่างเพดานค่าฐาน
(`frozen` / `testFrozen` หรือ `cap` / `testCap` สำหรับไฟล์ที่อยู่นอกค่าฐาน) กับขนาดที่ฐาน
ดังนั้นไฟล์ที่คลาดเคลื่อนไปแล้วบนฐานจะไม่ทำให้ PR ที่ไม่เกี่ยวข้องล้มเหลว

`check:boundary:ratchet` ใช้กฎเดียวกันกับตัวเลขเพียงค่าเดียวของมัน
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): ในเหตุการณ์ PR ทั้ง fast-gate ของ
`quality.yml` และงาน lint ของ `ci.yml` จะส่งค่า SHA ฐานของ PR โดยคอมมิตฐานจะถูกวัดจากการส่งออกด้วย `git archive`
และ PR จะล้มเหลวเฉพาะเมื่อจำนวน edge ของ `open-sse → src` สูงกว่าค่าที่มากกว่าระหว่าง
`metrics.boundaryOpenSseToSrc` กับจำนวนบนฐาน ระบบจะรายงาน base drift ที่สูงกว่าเพดาน
(`base drift herdado`) แต่จะไม่ทำให้ PR ที่ไม่ได้เป็นต้นเหตุกลายเป็นสีแดง ส่วน push → main
ยังคงใช้เพดานสัมบูรณ์ และ SHA ฐานที่ไม่สามารถ resolve ได้จะย้อนกลับไปใช้เพดานดังกล่าวพร้อมคำเตือน

การรัน `workflow_dispatch`, การกวาดตรวจ release-green และงาน headroom รายคืนไม่มีฐาน PR
และยังคงใช้การเปรียบเทียบแบบสัมบูรณ์ (ทั่วทั้งระบบ) ส่วน coverage, duplication และ type-coverage
ยังคงเป็นแบบทั่วทั้งระบบในขณะนี้ (เครื่องมือของส่วนเหล่านี้ไม่สามารถสร้าง diff รายไฟล์ได้อย่างประหยัด) — และเป็นตัวเลือกสำหรับการปรับใช้แนวทางเดียวกัน

**การปิดเฟสที่ v4.0 (LTS = เข้มงวดกว่าเดิม ไม่ใช่ "กลับสู่ภาวะปกติ")**

1. บน tip ของ `release/v4.0.0` แบบล้วน: รัน `npm run quality:headroom --json` เพื่อบันทึกไว้ จากนั้นรัน
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update` และ `--update` ของ typecheck gate
   แต่ละรายการ — baseline ทุกค่าจะลดลงมาเท่ากับค่าที่วัดได้
2. ลบ `_policy` ออกจาก `quality-baseline.json` (เปิดใช้งาน `--require-tighten` และการสะสม
   รายคืนอีกครั้ง) และคืนค่า `THRESHOLD = 36` (หรือสูงกว่า) ใน `check-openapi-coverage.mjs`
3. ปรับให้เข้มงวดยิ่งกว่าค่าที่วัดได้ในจุดที่การทำ modularization ให้ผลลัพธ์: คืนค่า `cap` ของ file-size เป็น 1000
   (หรือ 800), เพิ่ม coverage floor อีก +5 และกำหนด dead exports เป็น 0 สำหรับ package ที่ทำ modularization แล้ว

## ค่าอ้างอิง Ratchet (`quality-baseline.json`)

กลไก ratchet (`scripts/quality/check-quality-ratchet.mjs`) จะอ่าน `quality-baseline.json`
และเปรียบเทียบกับ `quality-metrics.json` ที่เพิ่งรวบรวมมาใหม่ เมตริกใดก็ตามที่ถดถอย
เกินค่า epsilon จะทำให้บิลด์ล้มเหลว

เมตริกที่ติดตามอยู่ในปัจจุบัน:

| เมตริก                | ทิศทาง | ความหมาย                              |
| --------------------- | ------ | ------------------------------------- |
| `eslintWarnings`      | `down` | จำนวนคำเตือน ESLint ต้องไม่เพิ่มขึ้น  |
| `coverage.statements` | `up`   | ความครอบคลุมของ statement ต้องไม่ลดลง |
| `coverage.lines`      | `up`   | ความครอบคลุมของบรรทัดต้องไม่ลดลง      |
| `coverage.functions`  | `up`   | ความครอบคลุมของฟังก์ชันต้องไม่ลดลง    |
| `coverage.branches`   | `up`   | ความครอบคลุมของ branch ต้องไม่ลดลง    |

หากต้องการอัปเดตค่าอ้างอิงหลังจากมีการปรับปรุงจริง:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

แฟล็ก `--update` จะเขียนค่าที่วัดได้ในปัจจุบันลงใน `quality-baseline.json`
ให้ commit ไฟล์นี้พร้อมกับการเปลี่ยนแปลงที่ปรับปรุงเมตริก PR ที่ปรับปรุง
เมตริกโดยไม่อัปเดตค่าอ้างอิงจะถูกตรวจพบโดย `--require-tighten` (ระยะ 6A.5,
รอการนำไปใช้งาน)

### วงล้อ CodeQL : การรับสมัครผู้สมัครและสินค้าคงคลัง

CI เป็นเจ้าของการรับเข้า CodeQL ของผู้สมัครผ่านสายการพึ่งพาที่ชัดเจน: `codeql-scan` เรียกเมทริกซ์สี่ภาษาใน `codeql.yml` จากนั้น `codeql-admission` จะรัน `node scripts/check/check-codeql-ratchet.mjs --candidate` `Gate / CI` ต้องการผลลัพธ์ทั้งสองอย่าง คุณภาพยังคงมีการตรวจสอบตัวเลขของตัวเอง แต่จะไม่สอบถามเครื่องสแกนก่อนที่ผู้ผลิตจะเสร็จสิ้น `Gate / Quality` เพียงอย่างเดียวยังไม่สามารถรับสมัครผู้สมัครได้อย่างสมบูรณ์ CodeQL ยังคงจำเป็นสำหรับผู้สมัครที่เป็นเอกสารเท่านั้น

นโยบายใน `config/quality/codeql-admission-policy.json` เลือก Actions, C/C++, JavaScript/TypeScript และ Python, ค่าเริ่มต้นของชุดการสืบค้น, โมเดลภัยคุกคามระยะไกล และไม่มีโหมดบิวด์ preflight ของผู้ผลิตปฏิเสธบันทึกการเปิดใช้งานที่ค้างอยู่และแยกออกนอกรายการเป้าหมายที่ชัดเจน เป้าหมายปัจจุบันคือเป้าหมายหลักและการทดสอบสัญญา release/v3.8.54. จะเปรียบเทียบรายการที่จำกัดนี้และทริกเกอร์พุชการบำรุงรักษากับเวอร์ชันแพ็คเกจ รุ่นถัดไปจำเป็นต้องตรวจสอบการเริ่มต้นใช้งาน ทริกเกอร์ PR ที่เผยแพร่ในวงกว้างกว่าที่มีอยู่ของ CI จะยังคงอยู่ แต่เป้าหมายที่ไม่ได้รับการรายงานจะรายงาน HOLD ก่อนที่จะทำการแยก แทนที่จะได้รับ PASS ที่ไม่ได้วัด

งานเมทริกซ์แต่ละงานจะบันทึก SARIF ที่อัปโหลดจริง ID ภาษา หมวดหมู่ การเรียกใช้และความพยายาม ข้อมูลระบุตัวตนเวิร์กโฟลว์ของผู้เรียก เหตุการณ์ ref/head/base/merge SHA และแฮชนโยบาย งานที่ขึ้นต่อกันจะดาวน์โหลดเฉพาะใบเสร็จรับเงินของการรันนี้และตรวจสอบการแยกส่วนสิ่งประดิษฐ์ จำเป็นต้องมีทั้งสี่หมวดหมู่ ผู้ผลิตที่ประสบความสำเร็จ และการประมวลผลการอัปโหลดแต่ละครั้งเสร็จสมบูรณ์ ใช้ตัวกรอง sarif_id ของ API ไม่ใช่การวิเคราะห์ล่าสุดที่พบในสาขา การฉายซ้ำบางส่วนอาจนำหมวดหมู่ที่ประสบความสำเร็จกลับมาใช้ซ้ำจากความพยายามครั้งก่อนของการวิ่งและผู้สมัครคนเดียวกัน โดยคงความพยายามในการผลิตไว้ ผู้ผลิตปัจจุบันที่ล้มเหลวไม่สามารถใช้หลักฐานสีเขียวก่อนหน้านี้ซ้ำได้

การดำเนินการ CodeQL รอการประมวลผล แต่การใช้งานที่ปักหมุดไว้สามารถเตือนและดำเนินการต่อได้หลังจากความล้มเหลวในการอ่านสถานะหรือการรอที่หมดลง การรับเข้าจึงตรวจสอบการประมวลผลอีกครั้ง หมวดหมู่ที่ขาดหายไป, รอการประมวลผล, งานที่ล้มเหลวหรือถูกยกเลิก, ข้อมูลประจำตัวเก่า, การแบ่งหน้าไม่สมบูรณ์หรือ APIs ที่ไม่พร้อมใช้งานจะสร้าง HOLD และทางออก 2 ไม่มีการรอคงที่สำหรับเวิร์กโฟลว์สแกนเนอร์อิสระยังคงอยู่ PR ที่ไม่ได้สแกนไม่สามารถผ่านได้เนื่องจากการสอบถามการแจ้งเตือนส่งคืน 0 จำนวนที่วัดได้เหนือ `metrics.codeqlAlerts.value` จะออก 1 พื้นฐานจะไม่ถูกยกขึ้นเพื่อรองรับการแจ้งเตือนของสาขาอื่น [อัปโหลดสถานะและการค้นหาการวิเคราะห์](https://docs.github.com/en/rest/code-scanning/code-scanning)

ใบเสร็จรับเงินจะบันทึกการอัปโหลดและการวิเคราะห์ IDs หมวดหมู่ เวอร์ชันเครื่องมือ ref/SHA หมายเลขพื้นฐาน และการแจ้งเตือน จำนวน SARIF identity/result จำนวนกฎขั้นต่ำ และอินสแตนซ์การแจ้งเตือนที่แน่นอนยังคงมีผลบังคับใช้ ข้อมูลประจำตัว PR/analysis จะถูกตรวจสอบอีกครั้งก่อนที่จะยอมรับ การตรวจสอบเหล่านี้จะสร้างความครอบคลุมหมวดหมู่ที่กำหนดค่าไว้ ไม่ใช่รายการของไฟล์ต้นฉบับที่แตกออกมาทุกไฟล์ C/C++ no-build extraction ไม่รวมโค้ดที่สร้างขึ้นระหว่างการสร้างโปรเจ็กต์ การยกเว้นแหล่งที่มายังต้องมีการตรวจสอบ และการระบุแหล่งที่มาของผู้ร่วมให้ข้อมูลจำเป็นต้องมีหลักฐานฐานที่ตรงกันทุกประการที่เทียบเคียงได้

`codeql-maintenance.yml` จัดเตรียมการสแกนแบบพุชที่ใช้งานอยู่และกำหนดการรายสัปดาห์โดยไม่สร้างซ้ำกับผู้ผลิต PR/main `nightly-codeql-inventory.yml` แยกบรรทัดฐานทั่วทั้งพื้นที่เก็บข้อมูลออกจากกัน โดยมี `--strict-measurement` และความล้มเหลวเมื่อการวัดไม่พร้อมใช้งาน การข้ามอย่างสง่างามของนักสะสมมรดกในท้องถิ่นไม่ใช่การรับผู้สมัคร การกระชับยังคงเป็น `--update` ที่ชัดเจนหลังจากการนับรวมที่ต่ำกว่าที่ผ่านการตรวจสอบแล้ว

เวิร์กโฟลว์ขั้นสูงจะต้องไม่ถูกเผยแพร่ในขณะที่กำหนดค่าการตั้งค่าเริ่มต้น: GitHub ปฏิเสธชุดค่าผสมนั้น นโยบายเวอร์ชันยังคงอยู่รอดำเนินการจนกว่าการเปลี่ยนแปลงด้านการดูแลระบบที่ได้รับการตรวจสอบแล้วจะถูกอ่านกลับ ก่อนที่จะเผยแพร่ ผู้ดำเนินการจะปักหมุดพื้นที่เก็บข้อมูล head/base/tree แฮช policy/patch/rollback และสถานะการตั้งค่าที่สังเกตได้ `node scripts/quality/codeql-producer.mjs verify-admin-readback` ตรวจสอบบันทึก JSON ที่คาดหวังและตามจริงที่ให้มา นี่คือการป้องกันทางเทคนิค ไม่ใช่การอนุมัติจากผู้ปฏิบัติงานหรือทดแทนการดึงข้อมูลการอ่านกลับใหม่ โทเค็น PR ไม่เคยร้องขอการเข้าถึงระดับผู้ดูแลระบบ การเปิดตัวและการเปลี่ยนแปลงเครื่องสแกนใดๆ จำเป็นต้องมีการอ่านกลับแยกต่างหาก รวมถึงหลักฐานความเข้ากันได้ของ PR จริง ทางแยก และกลุ่มผสาน

Forks ใช้รันเนอร์ที่โฮสต์ ชำระเงินโดยไม่มีข้อมูลประจำตัวที่คงอยู่ ไม่มีโปรเจ็กต์ install/build ในโปรดิวเซอร์ และไม่มีความลับของพื้นที่เก็บข้อมูลที่สืบทอดมา GitHub รองรับการอัปโหลด SARIF สำหรับเหตุการณ์ pull_request ด้วยโทเค็นทางแยกที่ลดลง การอนุมัติการดำเนินการสนับสนุนครั้งแรกยังคงเป็นนโยบาย GitHub ห้ามใช้ pull_request_target เพื่อรันโค้ดที่ไม่น่าเชื่อถือ ยืนยันสิทธิ์โทเค็นจริง analyse_key และสภาพแวดล้อมหมวดหมู่ทั้งหมดใน Canary ที่ควบคุม ก่อนที่จะพิจารณาว่าการย้ายข้อมูลเสร็จสมบูรณ์ [กฎการอัปโหลดทางแยก](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible) [โหมดการตั้งค่าที่ขัดแย้งกัน](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows)

**การเลิกจ้างเป็นการเรียกร้องของผู้ปฏิบัติงาน (Hard Rule #14)** — จะไม่ละทิ้งการแจ้งเตือน CodeQL โดยไม่บันทึกเหตุผลทางเทคนิคไว้ในความคิดเห็นในการเลิกจ้าง: `won't fix` สำหรับข้อกำหนดโปรโตคอลอัปสตรีม, `used in tests` สำหรับฟิกซ์เจอร์ทดสอบ, `false positive` สำหรับน้ำยาฆ่าเชื้อ CodeQL ไม่สามารถมองเห็นได้ (แบบอย่าง: `docs/security/ERROR_SANITIZATION.md`)

## นโยบายการลองทดสอบซ้ำ (WS5.4, v3.8.49)

การลองซ้ำกำหนดแยกตาม runner เท่านั้น ไม่ใช่การลองซ้ำแบบครอบคลุมทั้งหมด — เพราะการลองซ้ำแบบครอบคลุมจะเปลี่ยน regression ที่เกิดขึ้นจริง
ให้กลายเป็น flake ที่มองไม่เห็น:

| Runner           | นโยบาย                                                                                                                                                 | เหตุผล                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Playwright (e2e) | `retries: 1` เฉพาะใน CI พร้อม `trace: on-first-retry`                                                                                                  | จังหวะเวลาของเบราว์เซอร์/เครือข่ายมีความไม่แน่นอนจริง การลองซ้ำหนึ่งครั้งพร้อม trace จะเปลี่ยน flake ให้เป็น artifact ที่วินิจฉัยได้ |
| Vitest           | ไม่มีการลองซ้ำแบบ global การทดสอบที่พิสูจน์แล้วว่า flaky จะได้รับการกำหนดให้ลองซ้ำอย่างชัดเจนเป็นราย test (มองเห็นได้ใน diff และได้รับการตรวจสอบใน PR) | ทำให้รายการ quarantine อยู่ใน repo และไม่คลุมเครือ                                                                                   |
| node:test (unit) | ไม่มีการลองซ้ำไม่ว่าในกรณีใด                                                                                                                           | unit test ที่ flaky คือบั๊กในการทดสอบ — ให้แก้ไข อย่าสุ่มรันใหม่                                                                     |

SLO เป้าหมายเมื่อมี telemetry ของ flake แล้ว (WS5.2/5.3): อัตรา flake ต่อการทดสอบ <1%
(เกณฑ์ "แก้ทันที") และอัตราผ่านต่อ pipeline ≥95% ค่ามาตรฐานอ้างอิงของอุตสาหกรรม —
ให้ปรับเทียบใหม่จากค่าที่เราวัดได้เอง

## การเลื่อนถอยของ Ratchet ระดับรีลีส (WS5.5, v3.8.49)

เมื่อ ratchet (ขนาดไฟล์, ความซับซ้อน, คำเตือน eslint) ถดถอยบนปลายรีลีสที่เป็น PURE
กล่าวคือ เกิดการถดถอยจากผลรวมของการ merge และไม่มี PR ใดเพียงรายการเดียวที่ทำให้เกิด
การถดถอยซ้ำได้บน branch ของตนเอง การแก้ไขนั้นเป็นหน้าที่ของ **release captain เพียงครั้งเดียวบน
release branch**: ให้เลือกการแยกโค้ด/refactor เป็นอันดับแรก และ rebaseline เฉพาะเมื่อมีรายการ
เหตุผลที่บันทึกไว้เท่านั้น ห้ามผลักภาระการเลื่อนถอยจากผลรวมไปยัง PR ของ contributor และห้าม
rebaseline แยกตาม PR (เพราะจะซ่อน regression ที่เกิดขึ้นจริง) ให้แยกแยะสาเหตุก่อน: ทำให้สถานะ
แดงเกิดซ้ำบนปลายรีลีสที่เป็น pure ใน probe worktree ก่อนสันนิษฐานว่า PR ของคุณเป็นสาเหตุ

## การเก็บสะสมการลดค่า Ratchet — ทิศทางขาลง (#8584)

ratchet เป็นระบบอัตโนมัติเพียงครึ่งเดียว และเป็นครึ่งที่ผิดเสียด้วย การ **เพิ่ม** cap คือการแก้ไข
JSON ด้วยตนเองซึ่งใช้เวลาสิบวินาที และเป็นวิธีที่เร็วที่สุดในการปลดล็อก PR ที่เป็นสีแดง
การ **ลด** cap ต้องมีผู้รัน `--update` และ commit ผลลัพธ์ — และก่อนที่จะมี job
`bank-ratchet-shrinks` ก็ไม่มี workflow ใดรันคำสั่งนี้ ผลที่วัดได้
(2026-07-25): มีไฟล์ frozen 18 ไฟล์ที่มีขนาดไม่เกิน cap 800 บรรทัดสำหรับไฟล์ใหม่อยู่แล้ว โดยกรณีที่แย่ที่สุด
อยู่ที่ 132 เท่า (`src/shared/validation/schemas.ts` มี 19 บรรทัดแต่ถือ cap ไว้ที่ 2,523);
เพดานความซับซ้อนขยับจาก `1794 → 2169` ตลอดบันทึก rebaseline ประมาณ 37 รายการ โดยลดลงเพียง
ครั้งเดียว (−1); และมีการเขียนว่า "ปรับให้เข้มงวดผ่าน `--update` ในรอบถัดไป" 31 ครั้ง แต่ทำจริง
เพียงครั้งเดียว cap ที่ยังคงอยู่หลังจากโค้ดที่ทำให้ต้องมี cap นั้นหมดไปแล้ว จะเปลี่ยนทุกการแยกส่วนโค้ด
ที่เสร็จสมบูรณ์ให้กลายเป็นโควตาการเติบโตสำหรับผู้ที่มาแก้ไขไฟล์นั้นเป็นรายถัดไปโดยไม่ส่งสัญญาณเตือน

`nightly-release-green.yml` → job **`bank-ratchet-shrinks`** ปิดวงจรดังกล่าว:

|          |                                                                                                             |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| รันเมื่อ | `schedule` (3×/วัน) + `workflow_dispatch` — ตั้งใจ **ไม่** ใช้ `push`                                       |
| วัดผล    | `release/vX.Y.Z` ที่สูงที่สุด โดยใช้การ resolve และ injection guard แบบเดียวกับ `release-green`             |
| เขียน    | `check:file-size --update` และ `check:complexity-ratchets --update` (ทั้งสองลดค่าได้อย่างเดียวตามโครงสร้าง) |
| ตรวจสอบ  | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                    |
| ส่งมอบ   | PR ที่เป็นปัจจุบันเสมอเพียงรายการเดียวไปยัง release branch — อัปเดตแบบบังคับและไม่สร้างสแปม                 |

การเก็บสะสมจะทำเป็นชุดแทนที่จะทำทุกครั้งที่ push เพราะไม่มีข้อกำหนดด้าน latency (เก็บสะสมการลดค่า
ภายใน 8 ชั่วโมงก็เพียงพอ) ขณะที่การรันทุกครั้งที่ merge จะสร้าง PR branch ใหม่ซ้ำหลายครั้ง
ระหว่างแคมเปญ merge และเสียค่าใช้จ่ายในการรัน ESLint แบบเต็มทุกครั้ง การตรวจจับยังคงทำเมื่อ
push (`release-green`); มีเพียงการเก็บสะสมเท่านั้นที่ทำเป็นชุด

### ตัวตรวจสอบความปลอดภัย

job นี้เขียนลง baseline โดยไม่มีผู้ดูแล ดังนั้น `verify-ratchet-bank.mjs` จึงเป็นสิ่งที่ทำให้
การดำเนินการดังกล่าวยอมรับได้ มันจะ diff tree หลัง `--update` กับ `HEAD` และ **ยุติ job
ก่อนที่จะมี commit ใดเกิดขึ้น** — โดยไม่เปิด PR — เว้นแต่ทุกการเปลี่ยนแปลงจะเป็นหนึ่งในรายการต่อไปนี้:

- รายการตัวเลข `frozen` / `testFrozen` ที่ถูก **ลดค่า** หรือ **ลบออก**
- `complexity-baseline.json` → `count` ถูก **ลดค่า**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ถูก **ลดค่า**

สิ่งอื่นทั้งหมดจะถือว่าล้มเหลว: การเพิ่มตัวเลข, การเพิ่มรายการ, การเปลี่ยน `cap`/`testCap` หรือ
การลบ/เขียนบันทึก `_rebaseline_*` ใหม่ (บันทึกเหล่านี้คือ audit trail ที่อธิบายว่าเหตุใดเพดานแต่ละค่า
จึงมีอยู่ และถูกจัดเก็บภายใน object `frozen` เดียวกับรายการไฟล์)
บอตที่สามารถเพิ่ม cap ได้จะแย่กว่าสถานะปัจจุบันอย่างชัดเจน ตัวป้องกัน regression:
`tests/unit/verify-ratchet-bank.test.ts`

job นี้จะไม่ push ไปยัง `release/*` — มนุษย์เป็นผู้ merge PR ดังนั้นผลการวัดที่ผิดพลาด
จึงไม่สามารถถูกรวมเข้าไปโดยไม่ได้รับการตรวจสอบได้

## นโยบาย Allowlist

ทุกเกตที่ไม่สามารถล้มเหลวจากการละเมิดที่มีอยู่ก่อนแล้วจะใช้ allowlist ที่ตรึงไว้
(เช่น `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`) โดยมีนโยบายดังนี้:

**แก้ไขสาเหตุที่แท้จริง และใช้ allowlist เฉพาะเมื่อการละเมิดนั้นมีอยู่ก่อนแล้วและ
ไม่สามารถแก้ไขได้ใน PR เดียวกัน**

เมื่อเพิ่มรายการลงใน allowlist:

1. ใส่ความคิดเห็นพร้อมเหตุผลประกอบ
2. อ้างอิงปัญหาที่ใช้ติดตาม (เช่น `// #3498 — Phase 2 feature, not yet implemented`)
3. ลบรายการนั้นใน PR เดียวกับที่แก้ไขการละเมิด — รายการที่ล้าสมัยและไม่ได้
   ระงับการละเมิดที่ยังเกิดขึ้นอยู่ถือเป็นข้อบกพร่องในตัวเอง (การบังคับใช้รายการล้าสมัยใน 6A.3 จะ
   ทำให้เกตล้มเหลวเมื่อพบรายการ allowlist ที่ไม่มีการละเมิดรองรับ หลังจากนำระบบนี้มาใช้แล้ว)

**อย่า** เพิ่มรายการ allowlist เพื่อให้การทดสอบผ่านเร็วขึ้น เกตที่เป็นสีเขียวพร้อมกับ
allowlist ที่เพิ่มขึ้นเรื่อย ๆ ทำให้เข้าใจผิดว่ามีคุณภาพดี

### เมื่อเกตล้มเหลวใน PR ของคุณ

1. **อ่านผลลัพธ์ของเกตอย่างละเอียด** — ผลลัพธ์จะบอกอย่างชัดเจนว่าไฟล์หรือสัญลักษณ์ใดละเมิด
   กฎ
2. **แก้ไขการละเมิด** — เกตส่วนใหญ่เป็นการตรวจสอบระบบไฟล์แบบให้ผลลัพธ์แน่นอน ซึ่งจะผ่านทันที
   ที่โค้ดถูกต้อง
3. **หากการละเมิดมีอยู่ก่อนแล้ว** (กล่าวคือ คุณไม่ได้เป็นผู้ทำให้เกิด แต่ตอนนี้เกต
   ครอบคลุมการละเมิดนั้น): ให้เพิ่มรายการ allowlist พร้อมความคิดเห็นที่ระบุเหตุผลและปัญหาที่ใช้ติดตาม
4. **หากเกตเป็นแบบ ratchet** (ความครอบคลุม, คำเตือน ESLint, ความซ้ำซ้อน, ความซับซ้อน):
   การเปลี่ยนแปลงของคุณทำให้เมตริกแย่ลง ให้แก้ไขปัญหาที่ต้นเหตุ หรือในกรณีที่พบได้น้อย ให้เรียกใช้
   `npm run quality:ratchet -- --update` หากการเปลี่ยนแปลงนั้นเกิดขึ้นโดยตั้งใจและยอมรับได้ที่เมตริก
   จะลดลง — แต่ต้องระบุเหตุผลไว้ในคำอธิบาย PR
5. **เกตเชิงแนะนำ** (`continue-on-error: true`) มีไว้เพื่อให้ข้อมูล — โดยจะไม่ขัดขวาง
   การผสานโค้ด แต่จะปรากฏในสรุป CI ถึงกระนั้นก็ควรแก้ไขอยู่ดี

### รวม / กำจัดความซ้ำซ้อน (เชิงกลไก, ความเสี่ยงต่ำกว่า)

รายการแต่ละรายการได้รับการตรวจสอบเทียบกับสถานะ gate ที่ใช้งานจริงเมื่อ 2026-06-17 (เชื่อใจแต่ต้องตรวจสอบ);
การรวมหลายรายการที่ดู “ชัดเจน” กลับซ่อนหนี้ทางเทคนิคไว้และ **ไม่ใช่** สิ่งที่สามารถนำมาแทนได้โดยตรงอย่างไร้ปัญหา

- **`check:docs-sync` ทำงานสองครั้ง** — แยกเดี่ยวในงาน `lint` และอีกครั้งภายใน `check:docs-all` (`docs-sync-strict`) รวมถึงใน husky pre-commit hook ✅ **เสร็จแล้ว** — นำการเรียกใช้แบบแยกเดี่ยวใน `lint` ออกแล้ว
- **การสแกน CVE** — ❌ **ไม่ใช่การรวมที่ทำได้อย่างไร้ปัญหา** `audit:deps` บล็อกคำแนะนำด้านความปลอดภัยระดับวิกฤตและการตรวจสอบที่ไม่สมบูรณ์ใน lockfile ทั้งห้าไฟล์ ขณะเดียวกันก็รายงานคำแนะนำระดับสูงเป็นคำเตือนตามนโยบายปัจจุบัน ส่วน `check:vuln-ratchet` (osv) จะล้มเหลวเฉพาะเมื่อมี _การถดถอย_ เมื่อเทียบกับ baseline ที่ commit ไว้ และปฏิเสธค่าการวัดที่หายไปเมื่อมีการกำหนดให้ต้องใช้ ทั้งสองมีความหมายต่างกัน — การยกเลิก `audit:deps` จะทำให้สูญเสีย gate ระดับวิกฤตแบบสัมบูรณ์และหลักฐานการตรวจสอบแพ็กเกจที่เป็นอิสระจากกัน ให้คงทั้งสองรายการไว้
- **การตรวจหาวงจร** — ✅ **เสร็จแล้ว** (#15159 G-01/G-02) ข้อความเดิมในส่วนนี้เรียก `check:cycles` ว่าเป็น gate ที่ “ผ่านและผ่านการคัดสรร” และให้เหตุผลว่าควรคงการบล็อกไว้ เพราะ `check:circular-deps` (dpdm) รายงานวงจร 91 รายการ สถานะผ่านนั้นเป็น **ผลผ่านลวง**: `check:cycles` สแกนไดเรกทอรีย่อย 5 แห่ง (450 ไฟล์), จับคู่เฉพาะ `import|export … from` แบบสแตติก และตัด specifier ที่เป็น `@/` และ `@omniroute/open-sse/` ทั้งหมดออก จึงไม่สามารถมองเห็นวงจร dynamic-import + alias ซึ่งเป็นส่วนใหญ่ของ repo ได้ แก้ไขแล้ว: ขณะนี้ gate จะไล่ตรวจ `src` + `open-sse` (5023 ไฟล์), รวบรวม specifier จาก TypeScript AST (ดังนั้น `import("…")` จึงถูกนับ แต่ `typeof import("…")` ในตำแหน่งของ type ไม่ถูกนับ) และ resolve `paths` ของ tsconfig โดยพบวงจร **14** รายการ ไม่ใช่ 0 เนื่องจากไม่สามารถแก้ไขวงจรเดิมที่มีอยู่แล้ว 14 รายการภายใน PR ของ gate ได้ ตอนนี้ `check:cycles` จึงเป็น **ratchet** (`--ratchet`, เพดาน `metrics.cycles.value = 14` ใน `quality-baseline.json`, `direction: down`) — โดยจะบล็อก _การถดถอย_ ใดๆ และจำนวนดังกล่าวลดลงได้เท่านั้น CI เรียกใช้ `npm run check:cycles:ratchet` การทยอยลดจำนวนจะดำเนินการร่วมกับ **A-01** ส่วน `check:circular-deps` (dpdm) ยังคงเป็นคำแนะนำในฐานะความเห็นที่สองซึ่งครอบคลุมกว่า

เช่นเดียวกับเกตพี่น้อง เกตนี้ **รับรู้ส่วนต่าง** โดยเปรียบเทียบภาษาอังกฤษ ณ merge base กับ working
tree ดังนั้นช่องว่างที่มีอยู่ก่อนแล้วจะยังคงถูกตรึงไว้ และไม่ต้องมีการย้ายข้อมูลก่อนเปิดใช้เกต

**มาร์กเกอร์ `__MISSING__:<english>` ไม่ถือว่าผ่านเกตนี้ (ตั้งแต่ 2026-09-17)** ก่อนหน้านี้มาร์กเกอร์ดังกล่าว

เกตนี้ยอมรับทุก PR ไม่มีสิ่งใดขัดขวาง PR เหล่านั้น และจากนั้นเกตตรวจสอบอัตราส่วนคำแปลจริงแบบบล็อก

#### `check-vitest-exclusions` — เกตสำหรับเทสต์ที่ถูกพักไว้

ไฟล์ที่อยู่ในรายการ `exclude` ของ `vitest.config.ts` คือเทสต์ที่ไม่ได้ทำงาน และในสายตาของผู้ที่อ่าน
โครงสร้างไฟล์ เทสต์นั้นดูเหมือนเป็นส่วนหนึ่งของความครอบคลุม มีไฟล์สะสมอยู่หลังคอมเมนต์
`// #8618 — pre-existing failure; remove this exclusion when fixed` ถึงหกสิบสองไฟล์ Issue #8618
ถูกปิดเมื่อ 2026-08-11 ขณะที่รายการที่ติดตามโดย issue นี้เพิ่มจาก 45 รายการเป็น 62 รายการ โดยแต่ละ
รายการใหม่รับช่วงคอมเมนต์ที่ชี้ไปยัง issue ที่ปิดไปแล้ว เมื่อมีการวัดผลรายการดังกล่าวทีละไฟล์ในที่สุด
(#13204) พบว่า **51 จาก 62 ไฟล์ผ่านกับ tree ปัจจุบันโดยไม่ต้องเปลี่ยนแปลง source ใดๆ**

เกตนี้กำหนดให้ทุก exclusion ที่ resolve ไปยังไฟล์จริงต้อง (a) ระบุ tracking issue และ
(b) ปรากฏใน `config/quality/vitest-exclusions.json` พร้อมสถานะที่วัดได้ เพื่อให้การเพิ่ม exclusion
เป็น diff ที่ตรวจสอบได้ในไฟล์เฉพาะ แทนที่จะเป็นเพียงอีกหนึ่งบรรทัดในอาร์เรย์ที่มี 60 รายการ เกตนี้
ตั้งใจไม่เรียกใช้เทสต์ที่ถูก exclude ซ้ำ — การทำเช่นนั้นใช้เวลาประมาณ 10 นาทีและควรอยู่ในงานที่รัน
เป็นระยะ ส่วน inventory จะบันทึกว่าแต่ละรายการถูกวัดผลครั้งล่าสุดเมื่อใด
