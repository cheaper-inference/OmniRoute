## ลงจอดบนสาขาที่วางจำหน่าย

omni-queue ควบคุมการลงจอด `release/vX.Y.Z` อ่าน `mode` ระดับบนสุดใน `config/merge-queue/config.json` บนสาขาเริ่มต้นก่อนที่จะลงจอด PR ดู [Omni-คิว](OMNI_QUEUE.md)

- **`shadow`** ดำเนินการตรวจสอบความถูกต้องและออกจากการลงจอดไปสู่การผสานด้วยตนเอง ใช้ `omni-queue` กับ PR ที่ได้รับอนุมัติที่ส่วนหัวสุดท้าย ตรวจสอบสิทธิ์ด้วย `npm run queue -- why <PR>` รอคำตัดสินสำหรับหัวนั้นใน `npm run queue -- history --base <branch>` ดำเนินการต่อใน `would-land` บน `culprit-found` หรือ `would-dequeue` ให้กดผสานค้างไว้และแก้ไขสาเหตุ
- **ข้อยกเว้นเงา** รถไฟที่มี CI สีเขียวเต็มตัดกับปลายฐานปัจจุบันสามารถดำเนินการต่อได้โดยไม่ต้องมีการพิจารณาคิวแยกต่างหาก ข้อยกเว้นเดียวกันนี้ใช้เมื่อส่วนหัว PR มีส่วนปลายฐานปัจจุบันอยู่แล้ว
- **`live`** ใช้ป้ายกำกับ `omni-queue` เพื่อเรียกการลงจอด คิวเพียงอย่างเดียวจะลงจอด PR ปล่อยให้คำสั่งผสานและพุชโดยตรงไปที่คิว

การลงจอดทุกครั้งต้องได้รับอนุญาตจากเจ้าของและการตรวจสอบที่จำเป็นที่เกี่ยวข้อง ใช้ `omni-queue` หลังจากที่เจ้าของอนุญาตให้ลงจอดแล้วเท่านั้น เส้นทางที่ได้รับการป้องกันการสัมผัส PRs ที่อยู่ในคิวยังต้องมีการตัดสินใจ `protected-approved` ของเจ้าของสำหรับ PR นั้นด้วย

ชุดกฎ "ต้องมีประตูสีเขียวในรุ่นที่ใช้งานอยู่" ต้องใช้ `Gate / CI` และ `Gate / Quality` สีเขียวบนส่วนหัว ห้ามใช้ `--admin` เพื่อเลี่ยงผ่านประตูสีแดง บล็อกการตรึงการเผยแพร่จะรวมเข้ากับสาขาที่ตรึงไว้ ดู [กฎยากข้อ 21](HARD_RULES_DETAIL.md) ห้ามติดป้ายกำกับ ผสาน หรือพุชไปยังคำขอดึงที่เซสชันอื่นกำลังทำงานอยู่ ดู [กฎยากข้อ 22](HARD_RULES_DETAIL.md)

## คำขอดึงรถไฟ

1. เริ่มสาขารถไฟที่ปลายฐานรุ่นปัจจุบัน รวมส่วนหัวของสมาชิกที่ได้รับอนุมัติทุกประการโดยใช้การคอมมิตแบบผสาน รักษาประวัติการคอมมิตโดยหลีกเลี่ยงสควอชและรีเบส
2. เปิดคำขอดึงหนึ่งรายการสำหรับสาขารถไฟ ตรวจสอบ PR ด้วย CI แบบเต็มของตัวเองบนส่วนปลายฐานปัจจุบัน ตรวจสอบปลายฐานและหัวสมาชิกที่ได้รับอนุมัติอีกครั้งก่อนลงจอด รีเฟรชรถไฟและ CI เมื่อมีการเปลี่ยนแปลงผู้สมัครที่ผ่านการตรวจสอบแล้ว
3. ลงจอดรถไฟ PR ด้วยการรวมคอมมิตภายใต้โหมดคิวที่ใช้งานได้ ในโหมดถ่ายทอดสด วิธีการลงจอด `merge-ff` ของคิวจะคงการคอมมิตการผสานไว้ ส่วนหัวของสมาชิกดั้งเดิมสามารถเข้าถึงได้จากสาขาที่วางจำหน่าย GitHub ทำเครื่องหมายสมาชิก PRs ว่าผสานแล้ว และคอมมิตยังคงรักษาผู้เขียนไว้

ตัวอย่างสาธารณะคือ [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071) มันรวมสมาชิก 18 PRs และลงจอดด้วยการรวมคอมมิตในวันที่ 24-11-2569

การซิงค์แบ็คจาก `main` ไปยังสาขารุ่นถัดไปยังเกิดขึ้นผ่านการคอมมิตแบบผสานด้วย จำเป็นต้องมีการรักษาบรรพบุรุษ `main` เพื่อการซิงค์กลับในภายหลัง ดู [การแยกเวิร์กทรี](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash)

## เครื่องมือตรวจสอบการรวมรถไฟท้องถิ่น

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

เครื่องมือตรวจสอบจะดึงข้อมูลส่วนหัวของฐานและ PR แล้วรวมเข้าด้วยกันในแผนผังงานแบบใช้แล้วทิ้ง มันจะรันชุดพาริตี้หนึ่งครั้งบนแผนผังผลลัพธ์ ข้อขัดแย้งในการดึงข้อมูลส่วนหัวหรือผสานล้มเหลวจะทำให้ PR และสคริปต์ดำเนินต่อไปด้วย PRs ที่เหลือ

- **`--plan`** พิมพ์ขั้นตอนของโหมดที่เลือกและออกโดยไม่ต้องสร้างแผนผังงานหรือติดต่อกับรีโมท รวมเข้ากับ `--fast` เพื่อตรวจสอบแผนด่วน
- **`--fast`** รันประตูคงที่ทั่วไป ไฟล์ `node:test` ที่ถูกเปลี่ยนแปลงที่เลือกไว้ภายใต้ `tests/unit/` และ `npm run test:vitest` ดำเนินการตรวจสอบภายในแบบเต็มอย่างน้อยวันละครั้งกับทิปที่สะสมเมื่อใช้โหมดเร็ว
- **โหมดเต็ม** เพิ่มประตูคงที่แบบเต็มเท่านั้นและรัน `npm run test:unit` และ `npm run test:vitest`

ประตูคงที่ที่ล้มเหลวจะถูกรันใหม่บนฐานที่ไม่ถูกแตะต้อง ถ้ามีโพรบฐานอยู่ สคริปต์รายงานความล้มเหลวที่สืบทอดมาและดำเนินต่อไปเมื่อทุกบรรทัดการละเมิดที่ได้รับการยอมรับปรากฏบนฐานด้วย และจำนวนรวมยังไม่เพิ่มขึ้น

| ออก | ความหมาย                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------- |
| `0` | พิมพ์แผนหรือทำชุดให้เสร็จ สรุปชุดแสดงรายการความล้มเหลวแบบคงที่ที่สืบทอดมาและดีดออก PRs                  |
| `1` | อาร์กิวเมนต์ไม่ถูกต้อง ไม่มีการชำระเงิน Git ล้มเหลวในการดำเนินการล่วงหน้า หรือไม่มีการขึ้น PR           |
| `2` | การตรวจสอบชุดล้มเหลวและไม่เข้าข่ายสืบทอดมา ผู้ปฏิบัติงานสามารถแบ่งแบทช์ ดีด PR ที่ละเมิดออก แล้วรันใหม่ |

บัตรผ่านในพื้นที่จะให้หลักฐานการวินิจฉัยสำหรับเอกสารของเจ้าของเท่านั้น การลงจอดแต่ละครั้งยังคงต้องได้รับอนุญาตจากเจ้าของ การตรวจสอบที่จำเป็นของตัวเอง และการตัดสินคิวเงาเมื่อมีความเหมาะสม

## การจัดระดับ

- **ต่อ PR.** CI และการตรวจสอบคุณภาพเลือกตามเส้นทางที่เปลี่ยนแปลง รหัส PRs รันเกตคุณภาพที่รวดเร็วและการทดสอบที่ได้รับผลกระทบ โดยมีหน่วยแยกและงาน Vitest ใน CI
- **ต่อผู้สมัครคิว** CI และ Quality รันโปรไฟล์แบบเต็มสำหรับผู้สมัครที่แต่งในการอ้างอิงคิว
- **ต่อเคล็ดลับการเปิดตัว** Release-Green รันฮาร์ดเกตอย่างรวดเร็วเมื่อกดที่ตรงกับตัวกรองเส้นทาง การดำเนินการตามกำหนดการสามรายการต่อวันใช้การกวาดแบบเต็มสำหรับสาขาการเผยแพร่
- **ต่อการปล่อย** เมทริกซ์ CI แบบเต็มประกอบด้วยชาร์ด E2E การตรวจสอบแพ็กเกจ ควันบูต tarball และการตรวจสอบความครอบคลุม ดู [รายการตรวจสอบการเผยแพร่](RELEASE_CHECKLIST.md)

## ข้อกำหนดเบื้องต้นในการชำระเงินใหม่สำหรับ `merge-train.sh`

preflight ทำงานก่อนที่จะสร้างแผนผังงาน ติดตั้งการพึ่งพาด้วย `npm ci` ยืนยันว่า `node_modules/.bin/tsc` นั้นสามารถเรียกใช้งานได้ และไม่มี `node_modules/node_modules` อยู่ ตรวจสอบว่า `node_modules/.bin/bun --version` สำเร็จ

หากข้ามการติดตั้ง Bun หลังการติดตั้ง ให้รัน `(cd node_modules/bun && node install.js)` ความสอดคล้องของผู้ให้บริการและการตรวจสอบสัญลักษณ์ที่รู้จักใช้ Bun เครื่องมือตรวจสอบรัน `npm run check:cycles:ratchet` เป็นประตูปิดกั้น คำสั่ง `npm run check:cycles` แบบสแตนด์อโลนเป็นคำแนะนำ
