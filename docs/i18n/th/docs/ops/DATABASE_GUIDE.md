> **สรุปสั้นๆ**: OmniRoute ใช้ **SQLite พร้อมการทำเจอร์นัลแบบ WAL** เป็นพื้นที่จัดเก็บหลัก และใช้การเข้ารหัส **AES-256-GCM** สำหรับข้อมูลสำคัญที่จัดเก็บอยู่ คู่มือนี้ครอบคลุมสคีมา การย้ายข้อมูล การสำรอง/กู้คืน และคู่มือปฏิบัติงาน

**แหล่งอ้างอิง:**

- `src/lib/db/core.ts` — singleton + SCHEMA_SQL (ตารางพื้นฐาน 17 ตาราง)
- `src/lib/db/migrationRunner.ts` — การย้ายข้อมูลแบบกำหนดเวอร์ชัน
- `src/lib/db/migrations/` — ไฟล์ SQL แบบกำหนดเวอร์ชัน 167 ไฟล์
- `src/lib/db/encryption.ts` — ฟังก์ชันช่วยสำหรับการเข้ารหัส
- `src/lib/db/backup.ts` — การส่งออก/นำเข้าข้อมูลสำรอง
- `src/lib/db/healthCheck.ts` — การวินิจฉัยสถานะระบบ

## ทำไมจึงเลือก SQLite?

OmniRoute เลือก SQLite แทน PostgreSQL/MySQL ด้วยเหตุผลหลายประการ:

| ปัจจัย               | SQLite                                    | PostgreSQL                                 |
| -------------------- | ----------------------------------------- | ------------------------------------------ |
| **การปรับใช้**       | ฝังในตัว — ไม่ต้องมีเซิร์ฟเวอร์แยกต่างหาก | ต้องตั้งค่าเซิร์ฟเวอร์                     |
| **การเข้ารหัส**      | ระดับแอปพลิเคชัน (AES-256-GCM)            | TDE ในตัว                                  |
| **ประสิทธิภาพ**      | เร็วกว่าสำหรับเวิร์กโหลดขนาดเล็ก/ปานกลาง  | เหมาะกว่าสำหรับการเขียนพร้อมกันจำนวนมหาศาล |
| **การทำงานพร้อมกัน** | โหมด WAL รองรับการอ่านพร้อมกัน            | MVCC เต็มรูปแบบ                            |
| **การสำรองข้อมูล**   | คัดลอกไฟล์เดียว                           | `pg_dump` หรือสแนปช็อตระบบไฟล์             |
| **กรณีใช้งาน**       | การติดตั้งต่อผู้ใช้, แบบฝังในตัว          | SaaS แบบหลายผู้เช่า                        |

สำหรับการปรับใช้แบบ **ผู้ใช้คนเดียว อินสแตนซ์เดียว** (กรณีใช้งานหลักของ OmniRoute) SQLite เรียบง่ายและรวดเร็วกว่า

### การทำเจอร์นัลแบบ WAL

`core.ts` เปิดฐานข้อมูลด้วย **โหมด WAL (Write-Ahead Logging)**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL รองรับ **การอ่านพร้อมกัน** ระหว่างการเขียน ซึ่งสำคัญสำหรับแดชบอร์ดที่เรียกค้นข้อมูลในขณะที่กำลังบันทึกคำขอ

ขนาดแคชเริ่มต้นคือ **65,536 KiB (64 MiB)** SQLite ตีความค่า
`cache_size` ที่เป็นค่าลบว่าเป็นขีดจำกัดบนโดยประมาณในหน่วย KiB และจัดสรรเพจตามความต้องการ
**การตั้งค่า > ระบบและพื้นที่จัดเก็บ > ขนาดแคช** รองรับค่าจำนวนเต็มตั้งแต่ **1 ถึง
1,000,000 KiB** การบันทึกการตั้งค่าจะนำค่านั้นไปใช้กับการเชื่อมต่อฐานข้อมูลที่กำลังทำงานอยู่
และ OmniRoute จะคืนค่าที่บันทึกไว้เมื่อเริ่มต้นระบบ

## ตำแหน่งฐานข้อมูล

ไฟล์ SQLite ถูกจัดเก็บไว้ที่:

| ระบบปฏิบัติการ | พาธ                                                     |
| -------------- | ------------------------------------------------------- |
| Linux          | `~/.omniroute/storage.sqlite`                           |
| macOS          | `~/.omniroute/storage.sqlite`                           |
| Windows        | `%USERPROFILE%\.omniroute\storage.sqlite`               |
| Docker         | `/app/data/storage.sqlite` (กำหนดค่าได้ผ่าน `DATA_DIR`) |

ไฟล์และไดเรกทอรีประกอบ:

- `storage.sqlite-wal` — บันทึกแบบ write-ahead
- `storage.sqlite-shm` — ไฟล์หน่วยความจำร่วม
- `call_logs/` — อาร์ติแฟกต์เพย์โหลดของคำขอ (หากเปิดใช้งาน)

**กำหนดตำแหน่งอื่น:**

```bash
DATA_DIR=/custom/path omniroute
```

### ขอบเขตของโมดูล

กฎหลักของสถาปัตยกรรมคือ: **โมดูลต้องไม่เข้าถึงตารางของกันและกันโดยตรง** หากต้องการทำงานกับข้อมูลของโมดูลอื่น ให้นำเข้าฟังก์ชันจากโมดูลนั้น

```ts
// ❌ ไม่ถูกต้อง: ใช้ SQL โดยตรงจากโมดูลอื่น
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ถูกต้อง: ใช้ฟังก์ชันจากโมดูล providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

กฎนี้บังคับใช้ผ่านการตรวจสอบโค้ด — ไม่มีการตรวจสอบแบบสแตติก แต่การละเมิดจะถูกแจ้งเตือน

## สคีมาพื้นฐาน (17 ตาราง)

`core.ts` กำหนดตารางพื้นฐาน 17 ตารางใน `SCHEMA_SQL` ตารางเหล่านี้ถูกสร้างโดยไมเกรชัน `001_initial_schema.sql` และประกอบเป็นสคีมาหลัก

| `domain_fallback_chains`   | เชนโมเดลไปยังผู้ให้บริการ                | `model`, `chain`                                                        |

| `domain_lockout_state`     | สถานะการจำกัดอัตราของโดเมน               | `identifier`, `attempts`, `locked_until`                                |

### ตารางเพิ่มเติม (เพิ่มโดยไมเกรชันภายหลัง)

ไมเกรชันถัดมาเพิ่มตารางต่าง ๆ เช่น:

## การโยกย้าย

OmniRoute ใช้** การโยกย้ายตามเวอร์ชันและแบบ idempotent** ใน `src/lib/db/migrations/` การย้ายแต่ละครั้งจะเป็นไฟล์ SQL ไฟล์เดียว รูปแบบการตั้งชื่อสองรูปแบบอยู่ร่วมกัน เวอร์ชันที่บันทึกใน `_omniroute_migrations` คือคำนำหน้าตัวเลข

### การตั้งชื่อการย้ายถิ่น

เหตุใดจึงมีการเปลี่ยนแปลง: ด้วยตัวเลขตามลำดับ PRs แบบขนานจะเลือกหมายเลขถัดไปที่เหมือนกัน และทั้งหมดจะต้องกำหนดหมายเลขใหม่ก่อนที่จะรวม การประทับเวลา UTC ทำให้แต่ละ PR มีเวอร์ชันเป็นของตัวเอง

กฎสำหรับรูปแบบการประทับเวลา (บังคับใช้โดย `npm run check:migration-numbering` แชร์กับตัวสร้างใน `scripts/check/lib/migrationNaming.mjs`):

- การประทับเวลาเป็นวันที่และเวลา UTC จริง ไม่เร็วกว่า `20261113000000` และไม่เกิน 10 นาทีในอนาคต
- คำอธิบายคือ `snake_case` ตัวพิมพ์เล็กที่ขึ้นต้นด้วยตัวอักษร (`a-z`, `0-9`, `_` เดี่ยวระหว่างคำ) สูงสุด 80 อักขระ
- ไฟล์สองไฟล์ที่มีการประทับเวลาเดียวกันถือเป็นไฟล์ที่ซ้ำกัน
- กฎไม่มีช่องว่างใช้กับซีรี่ส์เก่าเท่านั้น: ต้องมีทุกตัวเลขตั้งแต่ `001` ถึง `241` ยกเว้นช่องว่างที่รู้จัก `026`, `055` และ `121` การลบ `241` (หรือไฟล์เก่าใดๆ) ทำให้เกตล้มเหลว ไม่สามารถเพิ่ม `001` และ `241` ในรายการ `KNOWN_GAPS` ที่อนุญาตได้ ไฟล์ที่ประทับเวลาจะไม่สร้างช่องว่าง
- ทุกรายการใน `src/lib/db/migrations/` ต้องเป็นไฟล์ปกติที่มีชื่อ `.sql` ตัวพิมพ์เล็กที่ถูกต้อง ไดเร็กทอรี, symlink, ไฟล์ `.SQL` หรือ `.sql.bak`, ไฟล์ที่ซ่อนไว้ หรือชื่อที่มีช่องว่างทำให้เกตล้มเหลว เนื่องจากนักวิ่งจะข้ามมันไปอย่างเงียบๆ หรือไม่ก็พังขณะบู๊ต

**สมัครสั่งซื้อ.** ตัวรันเนอร์จะเรียงลำดับตามค่าตัวเลขของคำนำหน้า ไม่ใช่ตามข้อความ: ไฟล์ `001`–`241` เก่าก่อน จากนั้นจึงเรียงลำดับไฟล์การประทับเวลาตามลำดับการประทับเวลา จากนั้นตามด้วยไดเร็กทอรีเนมสเปซใดๆ ที่ลงทะเบียนด้วย `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (เวอร์ชันต่างๆ เช่น `ee-001`) การโยกย้ายที่รอดำเนินการคือไฟล์ใดๆ ที่เวอร์ชันไม่อยู่ใน `_omniroute_migrations` ดังนั้นการย้ายจากสาขาเก่าที่รวมเข้าด้วยกันหลังจากสาขาที่ใหม่กว่ายังคงมีผลกับฐานข้อมูลที่มีอยู่

**การประทับเวลาคือลำดับการสร้าง ไม่ใช่ลำดับการรวม** หากการโยกย้ายของคุณขึ้นอยู่กับตารางหรือคอลัมน์ที่สร้างขึ้นโดยการโยกย้ายด้วย** ใหม่กว่า** การประทับเวลา (ตัวอย่างเช่น หนึ่งรายการจาก PR อื่นที่รวมเข้าด้วยกันก่อน) ฐานข้อมูลใหม่จะเรียกใช้ฐานข้อมูลของคุณก่อนและล้มเหลว ขณะที่ PR ของคุณยังคงเปิดอยู่ ให้สร้างชื่อไฟล์ใหม่ด้วย `npm run db:new-migration` เพื่อให้มีการประทับเวลาที่ใหม่กว่า หรือทำให้เป็นอิสระ `npm run test:migrations:fresh` ใช้ทุกการโยกย้ายไปยังฐานข้อมูลว่างและจับสิ่งนี้

### การย้ายแบบรวมจะไม่ถูกลบหรือเปลี่ยนชื่อ

เมื่อไฟล์การย้ายข้อมูลอยู่ในสาขา release หรือ `main` ไฟล์นั้นจะรันบนฐานข้อมูล homolog และนักพัฒนา บนการติดตั้ง VPS และในการซิงค์ระดับองค์กร ตั้งแต่นั้นเป็นต้นมา:

- **ไม่เคยลบมัน** การติดตั้งใหม่จะสูญเสียสคีมาในขณะที่ฐานข้อมูลที่อัปเกรดจะเก็บไว้
- **ไม่เคยเปลี่ยนชื่อมัน** เวอร์ชันใน `_omniroute_migrations` จะไม่ตรงกับไฟล์อีกต่อไป ดังนั้นทุกฐานข้อมูลที่ใช้แล้วจะต้องเรียกใช้อีกครั้ง SQL ที่ไม่ใช่ idempotent จะทำซ้ำข้อมูลหรือหยุดการบูต
- **ต้องการสคีมาอื่นหรือไม่?** สร้างการโยกย้ายใหม่ด้วย `npm run db:new-migration`

การเปลี่ยนชื่อจะปลอดภัยสำหรับไฟล์ที่ยังไม่ได้รวมเท่านั้น ซึ่งเป็นกรณีที่คำแนะนำของเกตอ้างถึง แท็ก release จะไม่เปลี่ยนแปลงใดๆ ที่นี่ ทุกครั้งที่กดไปที่สาขา `release/v*` จะเผยแพร่อิมเมจ Docker `:next` และทำงานบน homolog การติดตั้ง VPS และการซิงค์ระดับองค์กร ดังนั้นการย้ายแบบผสานจึงทำงานบนฐานข้อมูลจริงก่อนที่จะมีแท็ก `vX.Y.Z` ใดๆ อยู่ ประตูล้มเหลวในการลบไฟล์ฐานทุกครั้ง ไม่ว่าจะแท็กหรือไม่ก็ตาม

- **การคืนค่าการโยกย้ายแบบรวม** `git revert` ที่ลบไฟล์จะทำให้เกตล้มเหลว เก็บไฟล์และเลิกทำสคีมาในการโยกย้ายใหม่: `npm run db:new-migration -- <description>` ด้วย `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` และอื่นๆ ฐานข้อมูลที่อัปเกรดและใหม่แล้วลงท้ายด้วยสคีมาเดียวกัน
- **การเปลี่ยนชื่อที่ยอมรับ: รายการความเข้ากันได้และเนื้อหาที่เหมือนกัน** หากไฟล์ที่ผสานต้องย้าย (เช่น ไฟล์ที่ผสานสองไฟล์แชร์การประทับเวลาและตัวรันเนอร์หยุดด้วยการชนกันของเวอร์ชัน) ให้เปลี่ยนชื่อไฟล์ในภายหลังโดยไม่ต้องแตะ SQL และเพิ่ม `{ fromVersion, fromName, toVersion, toName }` ไปที่ `RENAMED_MIGRATION_COMPATIBILITY` ใน `src/lib/db/migrationRunner/constants.ts` ฐานข้อมูลที่ใช้เวอร์ชันเก่าจะถูกย้ายแถว `_omniroute_migrations` แทนที่จะเรียกใช้ไฟล์อีกครั้ง เกตจะเตือนเกี่ยวกับการเปลี่ยนชื่อดังกล่าวและจะทำการตรวจสอบการสับเปลี่ยนเสมอ ไม่ว่าจะประทับเวลาใหม่ใดก็ตาม: การติดตั้งใหม่จะใช้ไฟล์ในตำแหน่งใหม่ ฐานข้อมูลที่อัปเกรดแล้วจะไม่ทำเช่นนั้น ดังนั้นให้เลือกการประทับเวลาใหม่ใกล้กับอันเก่า ประตูล้มเหลวในการเปลี่ยนชื่อหากเนื้อหามีการเปลี่ยนแปลง (การเปลี่ยนแปลงสคีมายังคงอยู่ในการย้ายข้อมูลครั้งใหม่) หรือหากไฟล์เป้าหมายของรายการไม่ได้อยู่ในดิสก์
- **อย่าเปลี่ยนชื่อภายในเวลาเดียวกัน** การเปลี่ยนชื่อที่เก็บการประทับเวลาและการเปลี่ยนแปลงเฉพาะคำอธิบายจะล้มเหลวในเกต โดยมีหรือไม่มีรายการ ด้วยรายการที่มี `toVersion` เท่ากับ `fromVersion` ตัวรันจะลบแถว `_omniroute_migrations` เก่าและนำไฟล์ไปใช้อีกครั้งในทุกฐานข้อมูลที่รันไฟล์นั้นแล้ว หากไม่มีรายการ runner จะติดตามเฉพาะเวอร์ชันเท่านั้น โดยจะข้ามไฟล์ในฐานข้อมูลเหล่านั้น (เนื้อหาใหม่จะไม่ทำงานที่นั่น) และบันทึกข้อผิดพลาดในการกำหนดหมายเลขใหม่ในการบู๊ตทุกครั้ง ใช้การประทับเวลาอื่นบวกกับรายการความเข้ากันได้ หรือเก็บชื่อไว้
- **เกตจะตรวจสอบว่าไฟล์ที่ถูกเปลี่ยนชื่อไม่ทำงานอีกครั้ง** สำหรับการเปลี่ยนชื่อที่ครอบคลุมแต่ละครั้ง เกตจะส่งชื่อไฟล์ใหม่ไปยังการตรวจสอบการสับเปลี่ยนด้วย `--must-not-apply` การตรวจสอบจะบูตฐานข้อมูลที่อัปเกรดแล้วด้วย real runner และหาก runner ใช้ไฟล์นั้นอีกครั้ง (เช่น เนื่องจากรายการมีเวอร์ชันหรือชื่อไม่ถูกต้อง หรือเนื่องจากตัวแยกวิเคราะห์ข้อความของเกตอ่าน `constants.ts` แตกต่างจาก TypeScript) เกตจะล้มเหลวด้วย `migration renomeada rodaria de novo` และขอให้คุณตรวจสอบเวอร์ชันและชื่อของเก่าและใหม่ของรายการ

### สิ่งที่ประตูตรวจสอบกับฐาน

ในการดึงคำขอและการรันคิวผสาน `npm run check:migration-numbering` จะเปรียบเทียบ `src/lib/db/migrations/` บนดิสก์กับไดเร็กทอรีเดียวกันบนสาขาฐาน ฐานอยู่ในลำดับนี้: `--base-latest-tag`, `--base <ref>`, ตัวแปร `MIGRATION_BASE_REF` หรือเมื่อ `GITHUB_EVENT_NAME` คือ `pull_request`, `pull_request_target` หรือ `merge_group` ซึ่งเป็นพาเรนต์แรกของคอมมิตการผสาน `merge_group.base_sha` ของเพย์โหลดเหตุการณ์ หรือ `git merge-base HEAD origin/$GITHUB_BASE_REF` ในการร้องขอการดึงหรือคิวการรวมโดยไม่มีฐานที่แก้ไขได้เกตจะล้มเหลว ภายนอก CI ที่ไม่มี `--base` จะพิมพ์ `comparação com a base: pulada (sem --base)` และข้ามกฎเหล่านี้

`--base-latest-tag` เปรียบเทียบกับแท็กรีลีสใหม่ล่าสุด (`vX.Y.Z` ตามลำดับ semver; แท็กต่อท้าย เช่น nightlies ไม่นับรวม) ที่อยู่ในประวัติของ `HEAD` โดยมีกฎเดียวกันกับ `--base` Release-Green (`scripts/quality/validate-release-green.mjs`) รันเกตด้วยวิธีนี้ เนื่องจากการรันแบบพุชและการรันตามกำหนดเวลาไม่มีฐานคำขอการดึง และการผสานสามารถลงจอดได้โดยไม่ต้องรัน CI ใหม่ เมื่อไม่มีแท็กปล่อยในประวัติศาสตร์ ประตูจะล้มเหลว เรียกใช้ `git fetch --tags` (ใน CI, `actions/checkout` พร้อม `fetch-depth: 0` จะนำแท็ก)

การตรวจสอบการสับเปลี่ยนหนึ่งครั้งจะครอบคลุมไฟล์ที่ไม่อยู่ในลำดับ ไฟล์ที่แก้ไข และไฟล์ที่เปลี่ยนชื่อรวมกัน

การตรวจสอบการสับเปลี่ยน (`scripts/check/migration-commutation.ts`) จะสร้างฐานข้อมูลชั่วคราวสองฐานข้อมูลโดยมีพาธการติดตั้งจริง:** อัพเกรดแล้ว** หนึ่ง (บูตด้วยการย้ายฐาน จากนั้นบูตอีกครั้งในไฟล์เดียวกันพร้อมกับการย้ายคำขอดึง) และ** สด** หนึ่ง (บูตหนึ่งครั้งพร้อมกับการย้ายข้อมูลของคำขอดึง) โดยจะเปรียบเทียบสคีมาผลลัพธ์: ตารางและคอลัมน์ (ไม่สนใจลำดับคอลัมน์), ข้อจำกัด UNIQUE / PRIMARY KEY และ FOREIGN KEY, ข้อความ `CREATE TABLE` ที่ทำให้เป็นมาตรฐานของแต่ละตาราง (ซึ่งครอบคลุมข้อจำกัด CHECK, การจัดเรียง, คอลัมน์ที่สร้างขึ้นและตัวเลือกตาราง), ดัชนี, ทริกเกอร์ และมุมมอง ข้อมูลแถวจะไม่ถูกเปรียบเทียบ หากตรงกัน ประตูจะพิมพ์ว่าไฟล์ไม่เป็นระเบียบแต่เดินทางและผ่านไปได้ หากต่างกัน ประตูจะล้มเหลวพร้อมกับความแตกต่างและคำแนะนำสำหรับกรณีนี้: สำหรับไฟล์ที่ไม่อยู่ในลำดับ ให้สร้างชื่อใหม่ด้วย `npm run db:new-migration` ซึ่งปลอดภัยเนื่องจากไฟล์ยังไม่ได้ถูกรวมเข้าด้วยกัน สำหรับไฟล์ฐานที่แก้ไข ให้กู้คืนเนื้อหาฐานและทำการเปลี่ยนแปลงในการโยกย้ายใหม่ สำหรับไฟล์ที่ถูกเปลี่ยนชื่อ ให้เลิกทำการเปลี่ยนชื่อหรือเลือกการประทับเวลาใหม่ที่จะสับเปลี่ยน โดยจะไม่ประทับเวลาเดียวกันกับชื่ออื่น หากการตรวจสอบไม่สามารถทำงานได้ ประตูจะล้มเหลวใน CI และจะเตือนเฉพาะในเครื่องเท่านั้น สำหรับไฟล์ฐานที่แก้ไข ฐานข้อมูลที่อัปเกรดจะถูกสร้างขึ้นด้วยเนื้อหาฐานของไฟล์นั้น และการบูตครั้งที่สองจะข้ามไปเนื่องจากมีการบันทึกเวอร์ชันไว้แล้ว สำหรับไฟล์ที่ถูกเปลี่ยนชื่อ ฐานข้อมูลที่อัปเกรดจะถูกสร้างขึ้นด้วยไฟล์ภายใต้ชื่อเก่า และการบูตครั้งที่สองจะย้ายแถว `_omniroute_migrations` ผ่านรายการความเข้ากันได้แทนที่จะรันอีกครั้ง เกตส่งชื่อใหม่ด้วย `--must-not-apply` ดังนั้นการตรวจสอบจะล้มเหลวหากการบูตครั้งที่สองมีผล หากการย้ายคำขอดึงล้มเหลวในการใช้บนพาธที่อัปเกรด นั่นคือ หลังจากการโยกย้ายฐานทุกครั้ง (ไม่ว่าจะล้มเหลวในการติดตั้งใหม่หรือไม่ก็ตาม) เกทจะรายงาน `migration do PR não aplica` และขอให้คุณแก้ไข SQL กับสคีมาปัจจุบันของฐาน หากไฟล์ขึ้นอยู่กับการย้ายคำขอดึงอื่นที่มีการประทับเวลาในภายหลัง ให้สร้างชื่อใหม่ด้วย `npm run db:new-migration`

หากต้องการรันการเปรียบเทียบเดียวกันภายในเครื่อง ให้ส่งฐานอย่างชัดเจน เช่น `npm run check:migration-numbering -- --base origin/<base-branch>` หรือ `npm run check:migration-numbering -- --base-latest-tag` เพื่อเปรียบเทียบกับรีลีสล่าสุด

### การแปลงการโยกย้าย `NNN` ของ Open PR

คำขอดึงที่เปิดก่อนที่สวิตช์อาจยังคงมีไฟล์ต่อเนื่องเช่น `242_add_widgets.sql` ตัวเลขเก่าที่อยู่เหนือ `241` ถูกปฏิเสธ ดังนั้นให้แปลงก่อนรวม:

1. **เปลี่ยนชื่อไฟล์ด้วยตัวสร้างโดยเก็บคำอธิบายไว้** เรียกใช้ `npm run db:new-migration -- <same description>` เพื่อรับชื่อใหม่ ย้าย SQL ไปที่นั่น และลบไฟล์ `NNN_` เก่า คำอธิบายจะต้องเหมือนกัน: รายการความเข้ากันได้ด้านล่างตรงกัน
2. **เพิ่มรายการความเข้ากันได้หากฐานข้อมูลถาวรเรียกใช้หมายเลขเก่า** หากฐานข้อมูลใด ๆ ที่ถูกเก็บไว้ (homolog, VPS การติดตั้งของผู้สนับสนุนเอง) รันบิลด์ของ PR ด้วยไฟล์ `NNN_` ให้เพิ่ม `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` ไปที่ `RENAMED_MIGRATION_COMPATIBILITY` ใน `src/lib/db/migrationRunner/constants.ts` นี่คือ** จำเป็นสำหรับ `237` ถึง `241`** : ช่องเหล่านั้นตอนนี้เก็บ canonical `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` และ `241_seen_models.sql` และหากไม่มีรายการฐานข้อมูลดังกล่าวจะข้ามการโยกย้ายตามรูปแบบบัญญัติตลอดไปและเรียกใช้การแปลงอีกครั้ง นอกจากนี้ยังใช้งานได้กับช่องที่ว่างอยู่ เช่น `242` เมื่อปลายทางเป็นการประทับเวลา หากมีข้อสงสัย ให้เพิ่มรายการ ตำแหน่งที่คุณเพิ่มลงในอาร์เรย์ไม่สำคัญ: เมื่อช่องเป้าหมายของรายการยังคงมีแถวที่รายการอื่นย้ายออกไป (เช่น `237` ถือแถว PR ในขณะที่แถว `usage_history_calculated_cost` เก่ารอที่จะย้ายเข้าไป `237`) นักวิ่งปล่อยให้รายการนั้นรอจนกว่าช่องจะว่าง เฉพาะข้อขัดแย้งที่แท้จริง เช่น ช่องที่ถือโดยแถวที่ไม่มีการย้ายรายการ หรือสองรายการที่สลับช่อง หยุดการบูตด้วย `Cannot reconcile ...`
3. **เก็บ SQL idempotent ไว้** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`) เนื่องจากการโยกย้ายที่แปลงแล้วอาจเป็นไปตามฐานข้อมูลที่มีสคีมาอยู่แล้ว
4. **ย้ายกรณีพิเศษที่มีคีย์เวอร์ชัน** หาก PR เพิ่มตัวพิมพ์สำหรับหมายเลขเก่าใน `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) หรือใน `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) ให้เปลี่ยนคีย์เป็นการประทับเวลาใหม่

`tests/unit/db/codex-fence-migration-rename.test.ts` เป็นตัวอย่างการทำงานของการทดสอบการย้ายข้อมูลที่ถูกเปลี่ยนชื่อ

### แบ็คพอร์ตไปยังสาขาก่อนสวิตช์

อย่าเลือกหรือแบ็คพอร์ตไฟล์ `YYYYMMDDHHMMSS_` ไปยังสาขาที่เกิดก่อนสวิตช์ (เช่น สาขา `release/v*` ที่เก่ากว่า) ตัวดำเนินการจะเรียงลำดับชื่อไฟล์เป็นข้อความ ดังนั้นไฟล์ที่มีการประทับเวลาจะทำงานระหว่าง `201_` และ `202_` บนฐานข้อมูลใหม่ และเกตแบบเก่าที่นั่นไม่เข้าใจคำนำหน้า 14 หลัก ในสาขาดังกล่าว ให้เขียนการเปลี่ยนแปลงเป็นไฟล์ `NNN_` ถัดไปของสาขานั้นเอง ซึ่งเป็นไฟล์ idempotent ดังนั้นจึงไม่ต้องดำเนินการใดๆ เมื่อเวอร์ชันที่ประทับเวลามาถึงในภายหลัง

### การโยกย้ายดำเนินไปอย่างไร

เมื่อเริ่มต้น `migrationRunner.ts`:

1. สร้างตาราง `_omniroute_migrations` หากไม่มีอยู่
2. ข้อความค้นหาสำหรับการย้ายข้อมูลที่ใช้แล้ว
3. ใช้การย้ายข้อมูลใหม่ตามลำดับ แต่ละรายการในธุรกรรม
4. บันทึกการย้ายที่ใช้แต่ละครั้งพร้อมการประทับเวลา

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### ความเป็นเอกภาพ

การย้ายถิ่นจะต้องเป็น** idempotent** — ที่รันมันสองครั้งควรเป็น no-op:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

ใช้คำสั่งย่อย `IF NOT EXISTS`, `IF EXISTS` และ `OR IGNORE` / `OR REPLACE` อย่างเสรี

### เพิ่มการโยกย้ายใหม่

1. **สร้างไฟล์ด้วยตัวสร้าง** : `npm run db:new-migration -- <description>` (เช่น `npm run db:new-migration -- add combo priority`) โดยจะเขียน `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` ด้วยเวลา UTC ปัจจุบันและส่วนหัวของความคิดเห็น เลื่อนไปข้างหน้าหนึ่งวินาทีหากประทับเวลานั้น และจะไม่เขียนทับไฟล์ อย่าเลือกหมายเลขด้วยมือ
2. **ใช้ DDL ที่ปลอดภัย** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **ทดแทนข้อมูลอย่างระมัดระวัง** : ใช้ `UPDATE ... WHERE ...` เพื่อจัดการแถวที่มีอยู่
4. **ตรวจสอบคำสั่งซื้อและการตั้งชื่อ** : `npm run test:migrations:fresh` (การย้ายทั้งหมดบนฐานข้อมูลว่าง) และ `npm run check:migration-numbering`
5. **ทดสอบกับสำเนา** : ไม่เคยดำเนินการโยกย้ายที่ยังไม่ทดสอบในการใช้งานจริง
6. **ตารางที่สร้างจากโค้ดจำเป็นต้องมีการโยกย้ายด้วย** : หากโมดูลสร้างตารางอย่างเกียจคร้าน (`CREATE TABLE IF NOT EXISTS` เก็บไว้เป็นเส้นทางการรักษาตัวเอง) การย้ายจะต้องสร้างตารางด้วย DDL เดียวกัน มิฉะนั้น การติดตั้งใหม่ทั้งหมดและการติดตั้งที่อัปเกรดแล้วจะมีสคีมาที่แตกต่างกัน ขึ้นอยู่กับว่าเส้นทางโค้ดนั้นทำงานหรือไม่ `tests/unit/db/lazy-table-migration-guard.test.ts` สแกน `src/` และ `open-sse/` และล้มเหลวบน `CREATE` แบบขี้เกียจโดยไม่มีการโยกย้าย (#20557) ตัวอย่าง: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`

ตัวอย่าง:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **การเปลี่ยนแปลงที่เข้ากันไม่ได้แบบย้อนหลัง** (เช่น การวางคอลัมน์) เป็นเรื่องยุ่งยาก OmniRoute ไม่ NOT รองรับการปรับลดรุ่น — เมื่อใช้การโยกย้าย การเปลี่ยนแปลงสคีมาจะเป็นแบบถาวร วางแผนตามนั้น

## การเข้ารหัสข้อมูลขณะจัดเก็บ

ฟิลด์ที่ละเอียดอ่อน (คีย์ API, โทเค็น OAuth, สตริงการเชื่อมต่อ) จะได้รับการเข้ารหัสขณะจัดเก็บด้วย **AES-256-GCM**

### วิธีการทำงาน

```ts
// src/lib/db/encryption.ts (ฉบับย่อ)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### ตำแหน่งที่ใช้งาน

- `provider_connections.api_key` — เข้ารหัสในระดับแอปพลิเคชัน
- `provider_connections.access_token`, `refresh_token`, `id_token` — เข้ารหัสในระดับแอปพลิเคชัน
- รายการ `key_value` ที่มี `namespace = "secrets"` — เข้ารหัสในระดับแอปพลิเคชัน
- `proxy_registry.auth` — เข้ารหัสในระดับแอปพลิเคชัน (หากมี)

### คีย์การเข้ารหัส

คีย์การเข้ารหัสจะถูกสร้างจาก **วลีรหัสผ่าน** (ตั้งค่าผ่านตัวแปรสภาพแวดล้อม `STORAGE_ENCRYPTION_KEY`) และ **salt** (จัดเก็บไว้ในฐานข้อมูล) โดยจำเป็นต้องมีทั้งสองอย่างเพื่อถอดรหัสข้อมูล

```bash
# สร้างวลีรหัสผ่านที่ปลอดภัย
openssl rand -hex 32

# ตั้งค่าใน .env
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **สำคัญอย่างยิ่ง**: การทำคีย์การเข้ารหัสสูญหายหมายถึงการสูญเสียสิทธิ์เข้าถึงข้อมูลที่เข้ารหัสทั้งหมด **สำรองคีย์แยกจากฐานข้อมูล**

### สิ่งที่ไม่ได้เข้ารหัส

เพื่อประสิทธิภาพ ข้อมูลต่อไปนี้จะถูกจัดเก็บเป็นข้อความธรรมดา:

- ชื่อที่ใช้แสดงของผู้ให้บริการ
- ข้อกำหนดโมเดล (เป็นข้อมูลสาธารณะอยู่แล้ว)
- กฎการกำหนดเส้นทาง
- บันทึกการใช้งาน (ไม่มี PII)

---

## ข้อควรระวังเกี่ยวกับการเข้ารหัส (v3.8.16+)

OmniRoute ใช้ **`migrateLegacyEncryptedString()`** เพื่อรองรับรูปแบบการเข้ารหัสสองแบบอย่างโปร่งใส:

- **แบบเดิม** (ก่อน v3.5.0): "การเข้ารหัส" ที่ใช้ XOR (ไม่ใช่การเข้ารหัสที่แท้จริง)
- **แบบปัจจุบัน**: AES-256-GCM พร้อม IV และแท็กยืนยันความถูกต้องที่เหมาะสม

ตัวช่วยย้ายข้อมูลจะตรวจจับรูปแบบเดิมและเข้ารหัสใหม่ด้วยรูปแบบใหม่เมื่ออ่านครั้งแรก ซึ่งหมายความว่าคุณสามารถอัปเกรดฐานข้อมูลเก่าได้โดยไม่สูญเสียข้อมูลประจำตัว

## แคชสำหรับการอ่าน

สำหรับข้อมูลที่มีการอ่านบ่อย (โมเดล ผู้ให้บริการ และการตั้งค่า) `readCache.ts` มี **แคชในหน่วยความจำ**:

```ts
// แคชเมื่อเริ่มต้น และทำให้ใช้ไม่ได้เมื่อมีการเขียน
const providers = await getCachedProviders(); // รวดเร็ว อยู่ในหน่วยความจำ
const fresh = await listProviders(); // ช้า เข้าถึงฐานข้อมูล
```

| เอนทิตีที่แคชไว้       | คีย์แคช        | TTL                |
| ---------------------- | -------------- | ------------------ |
| `models`               | `models:v1`    | จนกว่าจะมีการเขียน |
| `provider_connections` | `providers:v1` | จนกว่าจะมีการเขียน |
| `settings`             | `settings:v1`  | จนกว่าจะมีการเขียน |
| `combos`               | `combos:v1`    | จนกว่าจะมีการเขียน |

แคชจะถูกทำให้ใช้ไม่ได้ทุกครั้งที่มีการเขียนไปยังตารางที่เกี่ยวข้อง

## การสำรองและการกู้คืน

### การสำรองข้อมูลด้วยตนเอง

```bash
# ใช้ CLI เพื่อสร้างข้อมูลสำรองในเครื่อง
omniroute backup create --name pre-migration

# หรือผ่าน API
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

ไฟล์สำรองประกอบด้วย:

- ตารางฐานข้อมูลทั้งหมด (ทำให้เป็นอนุกรมในรูปแบบ JSON)
- อาร์ติแฟกต์บันทึกการเรียก (เข้ารหัสแบบ base64 และเลือกเปิดใช้ได้)
- การตั้งค่า + ข้อมูลลับ (เข้ารหัสแล้ว)
- การกำหนดค่าปลั๊กอิน

### การกู้คืน

```bash
# ผ่าน CLI
omniroute restore pre-migration

# ผ่าน API
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **คำเตือน**: การกู้คืนจะเขียนทับฐานข้อมูลทั้งหมด โปรดหยุดไคลเอนต์ทั้งหมดก่อน

### การสำรองข้อมูลอัตโนมัติ

```bash
# เปิดใช้การสำรองข้อมูลรายวันอัตโนมัติผ่าน CLI
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

กำหนดการจะถูกเรียกใช้ที่ฝั่งเซิร์ฟเวอร์โดยงานเบื้องหลังซึ่งทำงานทุก 30 วินาที
(ค่าเริ่มต้น) และประเมินนิพจน์ cron เทียบกับเวลาท้องถิ่นของเซิร์ฟเวอร์

| ตัวแปร                                      | ค่าเริ่มต้น | คำอธิบาย                                                                                                                   |
| ------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`     | ช่วงเวลาการทำงานในหน่วย ms (ขั้นต่ำ `5000`) ต้องสั้นกว่า 60 วินาทีเพื่อให้ทำงานภายในนาทีที่ตรงกับ cron ได้อย่างน่าเชื่อถือ |

### การสำรองข้อมูลแบบ Hot Backup ของ SQLite

สำหรับการสำรองฐานข้อมูลที่กำลังใช้งานโดยไม่มีช่วงหยุดให้บริการ:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

วิธีนี้ใช้ API สำรองข้อมูลออนไลน์ของ SQLite ซึ่งสามารถเรียกใช้ได้อย่างปลอดภัยขณะที่ OmniRoute กำลังทำงาน

## การปรับแต่งประสิทธิภาพ

### โหมด WAL

WAL ถูกเปิดใช้งานตามค่าเริ่มต้น สำหรับเวิร์กโหลดที่มีการเขียนสูง ให้พิจารณา:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute ไม่ได้ตั้งค่า `journal_size_limit` จุดตรวจสอบจะย้ายเฟรม WAL ไปยังไฟล์หลัก แต่ไฟล์ WAL จะคงขนาดที่จัดสรรไว้ที่ใหญ่ที่สุดไว้ `OMNIROUTE_WAL_GUARD_MAX_MB` guard เพียงเตือนและรัน `wal_checkpoint(RESTART)`; ไม่ใช่ขนาดสูงสุดของดิสก์

### ดัชนี

ดัชนีหลักสำหรับประสิทธิภาพ (สร้างอัตโนมัติโดยการย้ายข้อมูล):

- การค้นหาโมเดล `idx_models_provider` — โดยผู้ให้บริการ
- `idx_combo_targets_combo_id` — การขยายเป้าหมายคอมโบ
- การวิเคราะห์การใช้งาน `idx_usage_history_api_key_timestamp` —
- การติดตามโควต้า `idx_quota_snapshots_api_key_window` —
- `idx_call_logs_timestamp` — ข้อความค้นหาบันทึกการโทร

หากต้องการเพิ่มดัชนีใหม่ ให้สร้างการย้าย:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### I/O ที่แมปหน่วยความจำ

สำหรับฐานข้อมูลขนาดใหญ่มาก (> 10GB) การแมปหน่วยความจำสามารถปรับได้ผ่าน SQLite pragma:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

อินสแตนซ์ OmniRoute ที่รันระยะยาวจะได้รับประโยชน์จาก `VACUUM`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

เรียกใช้ทุกเดือนในช่วงกรอบเวลาที่มีการเข้าชมน้อย ( โหมด WAL ลดความต้องการ แต่ไม่ได้กำจัดความต้องการ)

## การตรวจสอบสถานะ

`src/lib/db/healthCheck.ts` ให้บริการ **การวินิจฉัยสถานะระดับฐานข้อมูล**:

HTTP verb ทั้งสองต้องมีการยืนยันตัวตน (มิฉะนั้นจะได้รับ `401`) `GET` ใช้สำหรับวินิจฉัยเท่านั้น ส่วน `POST` จะเรียกใช้
การตรวจสอบเดียวกันโดยเปิดใช้งาน `autoRepair`

```bash
GET  /api/db/health   # วินิจฉัย
POST /api/db/health   # วินิจฉัย + ซ่อมแซม
```

การตอบกลับคือ `DbHealthCheckResult` ที่สร้างโดย `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "งบประมาณโดเมนอ้างอิง API key ที่ไม่มีอยู่อีกต่อไป",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ฟิลด์             | ความหมาย                                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `isHealthy`       | เป็น `true` เมื่อ `issues` ว่างเปล่า โดย `driver` จะไม่มีผลต่อค่านี้                                                                                               |
| `issues[].type`   | เป็นหนึ่งในค่า `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`                                                                     |
| `repairedCount`   | จำนวนแถวที่ซ่อมแซมระหว่างการเรียกใช้ครั้งนี้ และจะเป็น `0` เสมอเมื่อ `autoRepair` เป็น false                                                                       |
| `backupCreated`   | ระบุว่ามีการสำรองข้อมูลก่อนซ่อมแซมหรือไม่                                                                                                                          |
| `checkedAt`       | การประทับเวลาแบบ ISO ที่ใช้ร่วมกันระหว่างการเรียกใช้กับหมายเหตุการซ่อมแซมที่ถูกเขียนขึ้น                                                                           |
| `driver.name`     | ไดรเวอร์ SQLite ที่ให้บริการฐานข้อมูลซึ่งถูกตรวจสอบ                                                                                                                |
| `driver.degraded` | เป็น `true` เมื่อการเขียนไม่ได้รับการสำรองลงในไฟล์ฐานข้อมูลอย่างคงทน — กรณี fallback แบบ WASM ของ `sql.js` (การคงอยู่ของข้อมูลทั้งไฟล์) หรือฐานข้อมูลในหน่วยความจำ |

เครื่องมือ MCP `omniroute_db_health_check` จะส่งคืนเพย์โหลดเดียวกัน

เรียกใช้ `PRAGMA integrity_check` เพื่อตรวจหาความเสียหาย:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ควรแสดงผล: ok
```

หากส่งคืนค่าอื่นนอกเหนือจาก `ok` ให้ **หยุดใช้ฐานข้อมูลทันที** และกู้คืนจากข้อมูลสำรอง

## การกู้คืนจากภัยพิบัติ

### สถานการณ์ที่ 1: ไฟล์ WAL สูญหาย

ไฟล์ `-wal` หายไป แต่ไฟล์ `-shm` และฐานข้อมูลหลักยังคงสมบูรณ์:

```bash
# กู้คืนโดยอัตโนมัติเมื่อเปิดครั้งถัดไป

```

หาก SQLite ไม่สามารถกู้คืนโดยอัตโนมัติได้:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### สถานการณ์ที่ 2: ไฟล์ฐานข้อมูลหลักเสียหาย

คืนค่าจากข้อมูลสำรอง:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` จะดาวน์โหลดเฉพาะไฟล์เก็บถาวร `.tar.gz` แบบเต็มจากเซิร์ฟเวอร์ที่กำลังทำงานอยู่
(`GET /api/db-backups/exportAll` โดยต้องใช้ข้อมูลประจำตัวของผู้ดำเนินการ) และจะไม่คืนค่าข้อมูลใดๆ

### สถานการณ์ที่ 3: คีย์เข้ารหัสสูญหาย

**ไม่สามารถกู้คืนได้** หากไม่มีคีย์ ฟิลด์ที่เข้ารหัสไว้จะไม่สามารถอ่านได้ ให้เพิ่มผู้ให้บริการทั้งหมดอีกครั้งด้วยข้อมูลประจำตัวใหม่

> **การลดความเสี่ยง**: สำรองคีย์เข้ารหัสแยกต่างหากเสมอ โดยควรจัดเก็บไว้ในโปรแกรมจัดการรหัสผ่านหรือ KMS

### สถานการณ์ที่ 4: ดิสก์เต็ม

SQLite จะส่งคืนข้อผิดพลาด `SQLITE_FULL` ให้เพิ่มพื้นที่ว่างบนดิสก์ จากนั้น:

```bash
# ทำ checkpoint ให้ WAL เพื่อคืนพื้นที่ว่าง
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## การแก้ไขปัญหา

### "ฐานข้อมูลถูกล็อก"

มีกระบวนการอื่นกำลังถือ write lock อยู่ ให้ดำเนินการอย่างใดอย่างหนึ่ง:

- รอให้กระบวนการอื่นทำงานเสร็จ (ตรวจสอบด้วย `lsof | grep storage.sqlite`)
- ยุติกระบวนการอื่น
- หากปัญหายังคงอยู่ ให้เริ่ม OmniRoute ใหม่

### "ข้อจำกัดของ foreign key ล้มเหลว"

โมดูลโดเมนกำลังละเมิดความสมบูรณ์ของการอ้างอิง ให้ตรวจสอบ:

- แถวที่ไม่มีข้อมูลแม่ในตารางที่ขึ้นต่อกัน
- การลบแบบต่อเนื่องที่ไม่ส่งผลต่อไปยังข้อมูลที่เกี่ยวข้อง
- การย้ายข้อมูลล่าสุดที่เปลี่ยน foreign key

เรียกใช้ `PRAGMA foreign_key_check;` เพื่อค้นหาการละเมิด

### "หน่วยความจำไม่เพียงพอ"

I/O แบบ memory-mapped ของ SQLite ใช้หน่วยความจำเกินขีดจำกัดของระบบปฏิบัติการ ให้ลดค่าผ่าน pragma ของ SQLite:

```sql
PRAGMA mmap_size = 134217728;  -- 128MB แทน 256MB
```

หรือปิดใช้งาน:

```sql
PRAGMA mmap_size = 0;
```

### "การย้ายข้อมูลล้มเหลวระหว่างดำเนินการ"

การย้ายข้อมูลทำงานภายใน transaction ดังนั้นจึงควรถูกย้อนกลับแล้ว หากไม่เป็นเช่นนั้น:

1. **หยุด OmniRoute** (ป้องกันการพยายามดำเนินการเพิ่มเติม)
2. **ตรวจสอบสถานะฐานข้อมูล** ด้วย `sqlite3`
3. **แก้ไข** การย้ายข้อมูลบางส่วนด้วยตนเอง
4. **เรียกใช้** OmniRoute อีกครั้ง (ระบบจะลองย้ายข้อมูลอีกครั้ง)

เพื่อป้องกันปัญหานี้ ให้ทดสอบการย้ายข้อมูลกับสำเนาก่อนเสมอ
