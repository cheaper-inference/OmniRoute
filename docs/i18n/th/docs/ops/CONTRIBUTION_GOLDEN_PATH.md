ใช้คู่มือนี้เพื่อเลือกวงจรการพัฒนาที่เล็กที่สุดและเชื่อถือได้สำหรับ pull request คู่มือนี้ไม่ได้
ใช้แทนเอกสารสถาปัตยกรรมและความปลอดภัยเฉพาะด้านที่ลิงก์ไว้ด้านล่าง แต่เชื่อมโยงการเปลี่ยนแปลง
แต่ละประเภทที่พบบ่อยเข้ากับสัญญา การตรวจสอบแบบเจาะจง และขอบเขตการตรวจสอบของ CI

## เส้นทางที่ทุกการเปลี่ยนแปลงต้องดำเนินตาม

1. **เลือกฐานก่อนแก้ไข** ค้นหา branch `release/v*` ที่ยังใช้งานอยู่และมีเวอร์ชันสูงสุด แล้วสร้าง branch จาก
   commit ปลายสุดของ branch นั้น กำหนดเป้าหมายเป็น branch ดังกล่าว ไม่ใช่ `main` หากกำลังอยู่ในช่วงระงับการเปลี่ยนแปลงก่อนออกรุ่น อย่ากำหนดเป้าหมายเป็น
   branch ที่ถูกระงับไว้ ให้ใช้รอบการพัฒนาถัดไปที่ยังใช้งานอยู่ตามที่อธิบายไว้ใน
   [โมเดล Branching และการออกรุ่น](BRANCHING_MODEL.md)
2. **ระบุสัญญา** ระบุ catalog, schema, artifact ที่สร้างขึ้น, public API หรืออินเทอร์เฟซผู้ใช้
   ทุกรายการที่ได้รับผลกระทบจากการเปลี่ยนแปลง ตารางด้านล่างแสดงชุดเริ่มต้นขั้นต่ำ
3. **เขียนหรืออัปเดตการทดสอบแบบเจาะจง** การเปลี่ยนแปลง production ใน `src/`, `open-sse/`, `electron/` หรือ
   `bin/` ต้องมีการทดสอบอัตโนมัติใน PR เดียวกัน เรียกใช้ไฟล์ทดสอบที่เล็กที่สุดซึ่งพิสูจน์
   พฤติกรรมนั้นได้ จากนั้นจึงเรียกใช้เกณฑ์ตรวจสอบแบบเจาะจงที่ระบุไว้
4. **ให้ CI เรียกใช้เมทริกซ์แบบครอบคลุม** unit shard ทั้งหมด, Vitest, coverage ratchet และ
   production build จะทำงานบน PR ให้เรียกใช้ชุดทดสอบแบบครอบคลุมในเครื่องเฉพาะเมื่อความล้มเหลวจากการทดสอบแบบเจาะจงบ่งชี้ว่า
   มีผลกระทบในวงกว้างขึ้น หรือเมื่อการเปลี่ยนแปลงครอบคลุมหลายระบบย่อย
5. **ปรับให้สอดคล้องก่อนขอรีวิว** Fetch ฐานที่ยังใช้งานอยู่ ตรวจสอบ commit ใหม่และ diff ของคุณเทียบกับ
   ฐานนั้น จากนั้น rebase หรือ merge ฐานตาม workflow สำหรับผู้มีส่วนร่วม แก้ conflict ของไฟล์ที่สร้างขึ้น
   และ catalog จากต้นทางของไฟล์เหล่านั้น สร้างไฟล์ใหม่ เรียกใช้วงจรแบบเจาะจงอีกครั้ง และยืนยันว่า
   PR ยังคงกำหนดเป้าหมายเป็น release branch ที่ใช้งานอยู่
6. **บันทึกหลักฐาน** ในเทมเพลต PR ให้ระบุคำสั่งที่เรียกใช้ ไฟล์ทดสอบทุกไฟล์ที่เพิ่มหรือเปลี่ยนแปลง
   migration หรือ feature flag และการตรวจสอบเฉพาะ CI ที่ยังรอดำเนินการ

## แนวทางมาตรฐานตามประเภทการเปลี่ยนแปลง

คำสั่งด้านล่างเป็นการตรวจสอบแบบเจาะจงขั้นต่ำ ไม่ใช่การอนุญาตให้ข้ามการทดสอบที่ครอบคลุม
พฤติกรรมที่คุณเปลี่ยนแปลงโดยตรง

### Provider

**สัญญา**

- นิยาม Provider ใน `src/shared/constants/providers/` และการประกอบนิยามดังกล่าวใน
  `src/shared/constants/providers.ts`
- Model และ capability ใน `open-sse/config/providerRegistry.ts` หรือไฟล์ registry ที่แยกออกมา
- การเลือก executor/translator, การกำหนดค่า OAuth หรือ API key, asset ของ dashboard และข้อมูลอ้างอิง
  provider ที่สร้างขึ้นเมื่อเกี่ยวข้อง
- Credential สาธารณะต้องใช้ `resolvePublicCred()` ส่วน response ข้อผิดพลาดต้องใช้ helper กลางสำหรับ
  การกรองข้อมูลที่ละเอียดอ่อน โปรดดู `docs/security/PUBLIC_CREDS.md` (อยู่ใน git; ไม่ถูก compile เข้า `/docs`) และ
  [การกรองข้อมูลที่ละเอียดอ่อนจากข้อผิดพลาด](../security/ERROR_SANITIZATION.md)

**วงจรแบบเจาะจง**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # เมื่อ catalog เปลี่ยนแปลง ให้ commit diff ที่สร้างขึ้น
npm run lint
```

ทดสอบ request family ที่ได้รับผลกระทบทุกประเภทด้วย ได้แก่ chat, Responses, images, embeddings, audio หรือ video
ตรวจสอบ catalog ที่สร้างขึ้นและ golden diff ในฐานะการเปลี่ยนแปลงสัญญา อย่ายอมรับโดยไม่ตรวจสอบ

### Routing

**สัญญา**

- ค่าของ strategy สาธารณะและ metadata ของ UI ใน `src/shared/constants/routingStrategies.ts`
- การ dispatch และการจัดลำดับภายใต้ `open-sse/services/combo.ts` และ `open-sse/services/combo/`
- Combo schema, persistence, สถานะ resilience, capability ของ model และส่วนควบคุม API/UI
- [กลไก Auto-Combo](../routing/AUTO-COMBO.md) และเอกสาร resilience เมื่อพฤติกรรมเปลี่ยนแปลง

**วงจรแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # การเปลี่ยนแปลง strategy หรือ dispatch
npm run check:known-symbols      # การเปลี่ยนแปลงการลงทะเบียน strategy
npm run lint
```

ใช้การทดสอบที่ mock upstream และให้ผลลัพธ์คงที่ในเครื่อง การทดสอบ smoke ของ combo แบบ live ต้องใช้ credential และดำเนินการ
ด้วยตนเอง จึงใช้แทน CI ไม่ได้

### UI / UX

**สัญญา**

- route/page ของ Next.js และขอบเขตของ component ที่ใช้ร่วมกันภายใต้ `src/app/` และ
  `src/shared/components/`
- รูปแบบ response ของ API, สถานะ loading/empty/error, พฤติกรรมสำหรับ keyboard และ screen reader,
  layout แบบ responsive, theming และการรองรับ locale เพิ่มเติม
- สตริงต้นฉบับภาษาอังกฤษสำหรับ UI ใน `src/i18n/messages/en.json` ห้าม hard-code ข้อความใหม่ที่ผู้ใช้มองเห็น

**วงจรแบบเจาะจง**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

เรียกใช้แอปสำหรับการเปลี่ยนแปลงด้านการโต้ตอบหรือภาพ และตรวจสอบทั้ง viewport แบบแคบและกว้าง CI จะเรียกใช้
production build และชุดทดสอบที่ครอบคลุมกว่า แต่พฤติกรรมด้านภาพยังคงต้องใช้ component test แบบเจาะจง, Playwright
หรือการตรวจสอบด้วยตนเองที่มีการบันทึกไว้และเหมาะสมกับการเปลี่ยนแปลง

### i18n

**สัญญา**

- `src/i18n/messages/en.json` เป็นแหล่งต้นฉบับของ UI ส่วน `config/i18n.json` เป็นแหล่งข้อมูล locale
- Catalog ของ CLI แยกอยู่ภายใต้ `bin/cli/locales/`
- รักษา placeholder และ tag ของ ICU ให้เหมือนเดิมทุกประการ ห้ามแปลชื่อผลิตภัณฑ์/provider/model,
  ชื่อ protocol และ header, คำสั่ง, identifier ของ code/JSON, URL, environment variable หรือ
  คำที่ได้รับการคุ้มครอง เช่น `OmniRoute`, `OAuth`, `MCP` และ `A2A` รายการต้นฉบับปัจจุบันคือ
  `scripts/i18n/glossary/protected-terms.json`

**วงจรแบบเจาะจง**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # เมื่อสตริง/catalog ของ CLI เปลี่ยนแปลง
npm run lint
```

นี่คือแนวทางสำหรับระบบที่มีอยู่ ไม่ใช่คำเชิญให้ขยายเครื่องมือหรือโมเดล key ของระบบ
จำกัดแพตช์ i18n ให้เฉพาะเจาะจงในระหว่างที่กำลังออกแบบระบบทดแทน ห้ามเรียกใช้คำสั่งแปล
ที่ติดต่อบริการภายนอก เว้นแต่งานนั้นกำหนดให้สร้างคำแปลอย่างชัดเจน และคุณได้ตรวจสอบ diff ที่เกิดขึ้นแล้ว

### CLI

**สัญญา**

- คำสั่งและแฟล็กสาธารณะใน `bin/cli/`, คำสั่ง API ที่สร้างขึ้น, exit code, stdout/stderr และ
  รูปแบบเอาต์พุต JSON, ลักษณะการทำงานของการกำหนดค่า/สภาพแวดล้อม และไฟล์ที่รวมอยู่ในแพ็กเกจ
- สตริงที่แสดงต่อผู้ใช้ CLI ต้องใช้เลเยอร์ i18n ของ CLI และทำให้แค็ตตาล็อก `en`/`pt-BR` สอดคล้องกัน
- รักษา Node ไว้เป็นรันไทม์ที่รองรับ และคงสัญญาของไบนารีที่เผยแพร่ไว้

**วงรอบการตรวจสอบแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # การเปลี่ยนแปลง CLI ที่สร้างขึ้น/บันเดิล
npm run check:pack-policy     # การเปลี่ยนแปลงพื้นผิวของแพ็กเกจ
npm run lint
```

ใช้คำสั่งจริงในไดเรกทอรีข้อมูลชั่วคราว เมื่อลักษณะการทำงานขึ้นอยู่กับการแยกวิเคราะห์ ไฟล์ หรือ
สถานะการออก CI จะดำเนินการตรวจสอบอาร์ติแฟกต์ของแพ็กเกจและระบบนิเวศในขอบเขตที่กว้างกว่า

### ฐานข้อมูล

**สัญญา**

- โมดูลโดเมนอยู่ภายใต้ `src/lib/db/`; ให้นำเข้าโมดูลที่ต้องการโดยตรง (เลเยอร์ re-export เดิม `localDb.ts` ถูกนำออกแล้ว)
- การย้าย SQL ที่มีหมายเลขกำกับและทำซ้ำได้อย่างปลอดภัยภายใต้ `src/lib/db/migrations/`, ความปลอดภัยของทรานแซกชัน, ลักษณะการทำงานเมื่ออัปเกรด,
  ดัชนี และผู้เรียกใช้ทุกรายที่ได้รับผลกระทบจากสคีมา
- Routes และ handlers ต้องไม่เรียกใช้ SQL ดิบโดยตรง

**วงรอบการตรวจสอบแบบเจาะจง**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

เมื่อเพิ่ม migration ให้ทดสอบทั้งกับฐานข้อมูลใหม่และการอัปเกรดจากสคีมาก่อนหน้า การทดสอบฐานข้อมูล
ต้องปิด handles และเรียก `resetDbInstance()` ระหว่างการล้างข้อมูล เรียกใช้ `npm run test:bun:db` เฉพาะเมื่อ
เส้นทางอะแดปเตอร์ Bun แบบ best-effort มีการเปลี่ยนแปลงเท่านั้น โดย Node ยังคงเป็นแหล่งอ้างอิงหลัก

### การบิลด์ / การปรับใช้

**สัญญา**

- manifests/lockfile ที่รูทและใน workspace, `scripts/build/`, การประกอบ Next.js standalone, เนื้อหาแพ็กเกจ `dist/`,
  เมทาดาทาของ Electron สำหรับแต่ละแพลตฟอร์ม, เวิร์กโฟลว์ CI และ deployment sentinels
- ช่วงเวอร์ชัน Node ที่รองรับและการใช้งาน Bun ที่อยู่ในรายการอนุญาตใน `CLAUDE.md` ต้องคงเดิม
- อาร์ติแฟกต์จากการบิลด์ต้องไม่ถูกติดตาม; ต้องปฏิบัติตามนโยบายเกี่ยวกับ dependency, license, workflow และ package

**วงรอบการตรวจสอบแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # การเปลี่ยนแปลง dependency หรือ lockfile
npm run check:pack-policy      # การเปลี่ยนแปลงพื้นผิวของแพ็กเกจที่เผยแพร่
npm run lint
```

ใช้ `npm run build` ในเครื่องเฉพาะเมื่อการเปลี่ยนแปลงส่งผลต่อการคอมไพล์ การประกอบ standalone, assets
หรือการบันเดิลรันไทม์ ใช้ `npm run build:release` เฉพาะสำหรับการตรวจสอบ release/deploy เท่านั้น การบิลด์ของ CI
เป็นสัญญาณข้ามแพลตฟอร์มขั้นสุดท้าย; การเปลี่ยนแปลง Electron ที่เฉพาะเจาะจงต่อแพลตฟอร์มต้องมีผลการบิลด์แบบเจาะจง
หรือหลักฐาน smoke test ที่ตรงกับแพลตฟอร์มนั้น

## สคริปต์สำหรับนักพัฒนาบนเครื่องที่ใช้ร่วมกัน

ตัวช่วยสองรายการใน `scripts/dev/` กำหนดลูปการทำงานภายในเครื่องบน devbox ที่มีเซสชันอื่นกำลังทำงานอยู่:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # ไฟล์จาก merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # เฉพาะไฟล์เหล่านี้เท่านั้น
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # worktree แยกอิสระ ใช้งานแบบขนานได้อย่างปลอดภัย
```

- `typecheck-touched.sh` ตรวจสอบชนิดเฉพาะไฟล์ `.ts/.tsx` ที่มีการแก้ไขผ่าน
  `tsconfig.touched.tmp.json` ชั่วคราว (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ภายใต้ heap ขนาด 6 GB จึงใช้แทน `tsc -p tsconfig.json` ทั้งโปรเจกต์
  ซึ่งทำให้เครื่องที่มีภาระงานสูงเกิด OOM สคริปต์จะแสดงข้อผิดพลาดในไฟล์ที่มีการแก้ไขพร้อมบรรทัดสรุปหนึ่งบรรทัด และจบการทำงานด้วย
  `1` เมื่อมีข้อผิดพลาดในไฟล์ที่มีการแก้ไข, `2` เมื่อข้อผิดพลาดทั้งหมดอยู่ในไฟล์ที่ import เข้ามา หรือ tsc หยุดทำงาน
  โดยไม่มีข้อมูลวินิจฉัย (ให้อ่านล็อกที่ระบุไว้ภายใต้ `_artifacts/typecheck-touched/`), และ `0` เมื่อ
  ไม่มีข้อผิดพลาด tsconfig ชั่วคราวจะถูกลบเสมอ ห้าม commit ไฟล์นี้
- `new-worktree.sh` จัดลำดับการทำงานพร้อมกันด้วย `<git-common-dir>/omniroute-new-worktree.lock`
  (โดยค่าเริ่มต้นจะรอสูงสุด 600 วินาที พร้อมแสดงข้อความให้เห็น ส่วนหัวของสคริปต์ระบุวิธี
  override ค่า) และย้อนคืน
  branch ที่สร้างไว้เมื่อ `git worktree add` ล้มเหลวก่อนที่ worktree จะถูกสร้างขึ้น ดังนั้นการลองใหม่
  จึงไม่จำเป็นต้องเรียก `git branch -D` ด้วยตนเอง `node_modules` ที่ทำ hard link และสำเนา `.husky/_` ยังคงไม่เปลี่ยนแปลง

## ลูป candidate ภายในเครื่อง

การทดสอบ source ไม่สามารถพิสูจน์ได้ว่า artifact ที่แพ็กเกจแล้วสามารถเริ่มทำงานได้จริง: รายการไฟล์สำหรับแพ็กเกจ, dependency ที่ถูกตัดออก
และ native binary จะล้มเหลวก็ต่อเมื่อติดตั้งและเริ่มใช้งาน tarball แล้วเท่านั้น `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) เป็นส่วนภายในเครื่องของขั้นตอน build-once / validate / promote จาก
RFC #8084 โดยจะ build candidate หนึ่งรายการ, validate artifact เดียวกันนั้น, promote ด้วยการ
เปลี่ยนชื่อไดเรกทอรี และ rollback เมื่อ slot ที่ promote แล้วไม่ผ่านการตรวจสอบสถานะ

```bash
npm run dev:candidate -- run --dry-run --json  # แสดงแผนโดยไม่เปลี่ยนแปลงสิ่งใด
npm run dev:candidate -- run                   # build + validate + promote และ rollback อัตโนมัติ
npm run dev:candidate -- build                 # npm pack + ติดตั้งลงใน _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # เริ่มทำงานบน port ที่ว่าง แล้วตรวจสอบ /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # สลับ current กับ previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # ใช้ tarball ที่ build จากที่อื่น (CI) ซ้ำ
```

- **Build เพียงครั้งเดียว** `build` จะ pack tree ปัจจุบัน (ต้องมี `dist/server.js` ดังนั้นให้เรียก
  `npm run build:release` ก่อน) หรือคัดลอกจาก `--from-tarball` แล้วติดตั้ง tarball ลงใน
  npm prefix ที่แยกอิสระ เนื่องจาก tarball ไม่มี `node_modules` มาด้วย id คือ sha แบบสั้นของ `HEAD`
  (`-dirty` เมื่อ tree มีการเปลี่ยนแปลงภายในเครื่อง) หรือ `tgz-<sha256>` สำหรับ tarball หาก id ที่สะอาด
  ถูก build ไว้แล้ว ระบบจะนำกลับมาใช้แทนการ build ใหม่ ส่ง `--force` เพื่อบังคับให้ build ใหม่
- **Validate แพ็กเกจ ไม่ใช่ source** `validate` จะเริ่ม CLI ที่ติดตั้งไว้
  (`serve --port <free port>`) ด้วย `DATA_DIR=<candidate>/data` ใหม่, secret ปลอม และนำ
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` และ `INITIAL_PASSWORD` ของผู้ปฏิบัติงานออกจาก
  environment เพื่อให้ตรวจสอบรูปแบบ keyless loopback ของการติดตั้งใหม่ ระบบจะรอให้
  `GET /api/health` ส่งคืน 200, กำหนดให้ `GET /v1/models` ต้องส่งคืน 200, หยุด process group
  และบันทึกผลการตัดสินลงใน `validation.json` พร้อมกับ hash ของ tarball
- **Promote artifact เดียวกัน** `promote` จะปฏิเสธ candidate ที่ไม่มีผล validation ซึ่งผ่านสำหรับ
  hash ของ tarball ปัจจุบัน slot ที่ active โดยค่าเริ่มต้นคือ `_artifacts/candidate/current`; `--target <dir>`
  ใช้เลือกไดเรกทอรีอื่นบน filesystem เดียวกัน และ slot ก่อนหน้าคือ `<dir>.previous`
  การเปลี่ยนชื่อแต่ละครั้งเป็นแบบ atomic และหากล้มเหลวระหว่างทาง ระบบจะย้อนการเปลี่ยนชื่อที่ดำเนินการไปแล้ว
- **Rollback** `run` จะ validate slot ที่ promote แล้วอีกครั้ง และสลับ `current` กับ `previous` กลับคืนเมื่อ
  การตรวจสอบนั้นล้มเหลว candidate ที่ไม่ผ่าน validation ครั้งแรกจะไม่ถูก promote

ทุกอย่างจะถูกเขียนไว้ภายใต้ `_artifacts/candidate/` ซึ่งถูก gitignore ไว้ การติดตั้ง OmniRoute
ที่มีอยู่และ data directory ของการติดตั้งนั้นจะไม่ถูกแตะต้อง CLI ที่ promote แล้วอยู่ที่
`_artifacts/candidate/current/prefix/bin/omniroute`; เมื่อใช้งาน ให้เริ่ม CLI นี้ด้วย `DATA_DIR` ของคุณเอง
รหัสออกจากโปรแกรม: `0` หมายถึงสำเร็จ, `1` หมายถึง validation หรือ promotion ล้มเหลว, `2` หมายถึงข้อผิดพลาดในการใช้งานหรือไม่มี build

## ลูปภายในเครื่องเทียบกับ CI

| เรียกใช้ภายในเครื่องสำหรับแต่ละแพตช์                                             | CI ให้สัญญาณในภาพกว้าง                                                      |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| การทดสอบพฤติกรรมโดยตรงและเกตตามหมวดหมู่ข้างต้น                                   | ชุดการทดสอบยูนิตเต็มรูปแบบที่แบ่งเป็นชาร์ดและการทดสอบแบบอนุกรม              |
| `npm run lint`                                                                   | ชุดทดสอบ Vitest และกลไกปรับเกณฑ์ความครอบคลุม/คุณภาพให้เข้มขึ้น              |
| ตรวจสอบชนิดหรือบิลด์เฉพาะเมื่อสัญญาที่ได้รับผลกระทบกำหนดให้ทำ                    | บิลด์สำหรับโปรดักชัน รวมถึงเกตด้านความปลอดภัย เอกสาร การพึ่งพา และนโยบาย PR |
| ตรวจสอบการโต้ตอบด้วยตนเอง/แบบสดเฉพาะเมื่อระบบอัตโนมัติไม่สามารถยืนยันพฤติกรรมได้ | การตรวจสอบการผสานรวมข้ามงานและแพลตฟอร์มที่กำหนดค่าโดยเวิร์กโฟลว์            |

ลูปแบบเจาะจงที่ผ่านทั้งหมดเป็นหลักฐานเกี่ยวกับสัญญาที่เปลี่ยนแปลง ไม่ใช่ข้อพิสูจน์ว่าการตรวจสอบ CI
ที่ไม่เกี่ยวข้องจะผ่าน ในทางกลับกัน อย่าทำให้การแก้ไขทุกครั้งภายในเครื่องต้องรอเมทริกซ์ทั้งหมดของรีโพซิทอรี

## รายการตรวจสอบการปรับให้สอดคล้องกัน

ก่อนขอรับการรีวิว:

- ยืนยันว่าเบสของ PR ยังคงเป็นสาขา `release/v*` ที่ใช้งานอยู่และมีเวอร์ชันสูงสุด
- ดึงข้อมูลเบสนั้นและตรวจสอบคอมมิตที่ผสานเข้ามาหลังจากที่คุณสร้างสาขา
- ตรวจสอบ `git diff <active-base>...HEAD` เพื่อหาการเปลี่ยนแปลงที่ไม่ตั้งใจหรือเกิดจากการสร้างอัตโนมัติ
- แก้ไขข้อขัดแย้งของแค็ตตาล็อกและเอกสารที่สร้างอัตโนมัติด้วยการอัปเดตต้นทางและสร้างเอาต์พุตใหม่
- เรียกใช้การทดสอบ/เกตแบบเจาะจงทุกรายการที่ระบุไว้ในคำอธิบาย PR อีกครั้งหลังจากปรับให้สอดคล้องกัน
- ห้ามลดความเข้มงวดของการยืนยันผลหรือตัดการทดสอบที่จำเป็นออกเพียงเพื่อให้ตรงกับเบสที่เปลี่ยนไป

สำหรับกฎการระงับการเปลี่ยนแปลงก่อนรีลีสและการเปลี่ยนเป้าหมาย โปรดดู
