## ภาพรวม

OmniRoute ใช้ไปป์ไลน์การบีบอัดพรอมต์แบบโมดูลาร์ที่ทำงาน **เชิงรุก** ก่อนที่คำขอจะไปถึงผู้ให้บริการต้นทาง ซึ่งหมายความว่าคุณจะประหยัดโทเค็นได้อย่างโปร่งใส โดยไม่จำเป็นต้องเปลี่ยนแปลงเวิร์กโฟลว์

```
คำขอจากไคลเอนต์
  → ตัวเลือกกลยุทธ์การบีบอัด
    → มีการตั้งค่าทับด้วยคอมโบหรือไม่? → ใช้การตั้งค่าคอมโบ
    → ถึงเกณฑ์ทริกเกอร์อัตโนมัติหรือไม่? → ใช้โหมดอัตโนมัติ
    → มีโหมดเริ่มต้นหรือไม่? → ใช้การตั้งค่าส่วนกลาง
    → ปิดอยู่หรือไม่? → ข้ามการบีบอัด
  → โหมดการบีบอัดที่เลือก
    → Off: ไม่มีการบีบอัด
    → Lite: ล้างช่องว่าง/การจัดรูปแบบอย่างปลอดภัย (~15%)
    → Standard: ลบคำฟุ่มเฟือยแบบภาษามนุษย์ถ้ำ (~30%)
    → Aggressive: ลดทอนประวัติเก่า + สรุปเนื้อหา (~50%)
    → Ultra: ตัดทอนด้วยฮิวริสติก + ลดขนาดบล็อกโค้ด (~75%)
    → RTK: กรองเอาต์พุตจากเทอร์มินัล/เครื่องมือโดยพิจารณาคำสั่ง (ช่วงต้นทาง 60-90%)
    → Stacked: ไปป์ไลน์หลายเอนจินตามลำดับ โดยทั่วไปใช้ RTK แล้วตามด้วย Caveman (ช่วงที่เข้าเกณฑ์ 78-95%)
  → คำขอที่บีบอัดแล้ว → ผู้ให้บริการ
```

## โหมดการบีบอัด

### ปิด

ไม่มีการบีบอัด ใช้ข้อความทั้งหมดโดยไม่เปลี่ยนแปลง

### โหมด Lite (ประหยัดประมาณ 15%, ความหน่วง <1ms)

โหมดที่ปลอดภัยที่สุด — ทำความสะอาดการจัดรูปแบบ ผลลัพธ์จากเครื่องมือจะถูกตัดทอนแบบสูญเสียข้อมูล ดังนั้นเส้นทางเริ่มต้น
(ไม่มี `allow-lossy`, `engine:lite` หรือการเลือกใช้ชุดชื่อแบบระบุเอง) จะรัน Lite โดยมี
`compressToolResults: false`: ผลลัพธ์จากเครื่องมือก่อนหน้าจะถูกส่งไปยังผู้ให้บริการโดยไม่เปลี่ยนแปลง

| เทคนิค                   | คำอธิบาย                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | รวมบรรทัดว่างที่ต่อเนื่องกันและช่องว่างท้ายบรรทัด                                                                   |
| `dedupSystemPrompt`      | ลบข้อความระบบที่ซ้ำกัน                                                                                              |
| `compressToolResults`    | ตัดทอนผลลัพธ์จากเครื่องมือก่อนหน้าให้ไม่เกินขีดจำกัดของ Lite (สูญเสียข้อมูล: ใช้ได้เฉพาะเมื่อมีการเลือกใช้ผ่านคำขอ) |
| `removeRedundantContent` | ลบคำสั่งที่ซ้ำซ้อน                                                                                                  |
| `replaceImageUrls`       | ย่อข้อมูล URI ของรูปภาพแบบ base64                                                                                   |

**เหมาะสำหรับ:** การใช้งานที่เปิดไว้เสมอ เวิร์กโฟลว์ที่ต้องการความปลอดภัยสูง

### โหมด Standard (ประหยัดประมาณ 30%)

ได้รับแรงบันดาลใจจาก [Caveman](https://github.com/JuliusBrussee/caveman) — ลบคำเติมและถ้อยคำที่เยิ่นเย้อโดยยังคงความหมายเดิม:

- ลบคำเติม ("please", "I think", "basically", "actually")
- ย่อวลีที่เยิ่นเย้อ ("in order to" → "to", "as a result of" → "because")
- ลบถ้อยคำสุภาพที่แสดงความไม่มั่นใจ ("Would you mind...", "If you could possibly...")
- มีกฎ regex มากกว่า 30 รายการที่ปรับแต่งสำหรับพรอมต์การเขียนโค้ด

**เหมาะสำหรับ:** เวิร์กโฟลว์การเขียนโค้ดประจำวัน ทีมที่คำนึงถึงต้นทุน

### โหมด Aggressive (ประหยัดประมาณ 50%)

การจัดการประวัติอัจฉริยะสำหรับเซสชันที่ยาวนาน:

- **การจัดอายุข้อความ** — ข้อความเก่าจะถูกบีบอัดเพิ่มขึ้นเป็นลำดับ
- **การบีบอัดผลลัพธ์จากเครื่องมือ** — ตัดทอนหรือละเว้นผลลัพธ์จากเครื่องมือที่ยาว (บรรทัดแรก/ท้าย
  การกรองตามบรรทัดที่ตรงกัน การย่อคีย์ JSON)
- **ตัวป้องกันความสมบูรณ์ของโครงสร้าง** — ตรวจสอบให้คู่ `tool_use` + `tool_result` ยังคงสอดคล้องกัน
- **การตระหนักถึงหน้าต่างบริบท** — เคารพขีดจำกัดโทเค็นต่อโมเดล

**เหมาะสำหรับ:** เซสชันการดีบักที่ยาวนาน โค้ดเบสขนาดใหญ่

### โหมด Ultra (ประหยัดประมาณ 75%)

การบีบอัดสูงสุดสำหรับสถานการณ์ที่โทเค็นมีจำกัด:

- **การตัดทอนตามฮิวริสติก** — ตัดทอนโทเค็นของข้อความร้อยแก้วตามคะแนน
- **การรักษาโครงสร้าง** — บล็อกโค้ดที่ครอบด้วยเครื่องหมาย แท็กโค้ดแบบอินไลน์ URL และตัวระบุจะถูกเก็บเป็นข้อมูลอ้างอิงชั่วคราวและนำกลับมาต่อใหม่โดยคงรูปแบบเดิม ไม่ถูกตัดทอน
- **ระดับ SLM ที่เป็นตัวเลือก** — โมเดลภายในเครื่องขนาดเล็กสามารถปรับปรุงการตัดทอนได้เมื่อกำหนดค่าไว้
- ทำงานแยกจากโหมด Aggressive: จะไม่ทำการจัดอายุข้อความ การบีบอัดผลลัพธ์จากเครื่องมือ
  หรือตัวสรุปสำรอง (เฉพาะความล้มเหลวของระดับ SLM เท่านั้นที่อาจเปลี่ยนเส้นทางให้การประมวลผลสำรองผ่าน Aggressive)

**เหมาะสำหรับ:** เมื่อพบข้อจำกัดของบริบทซ้ำ ๆ

### โหมด RTK (ช่วงต้นทาง 60-90%)

โหมด RTK ได้รับการปรับให้เหมาะกับผลลัพธ์จากเครื่องมือที่มีความยาวและปรากฏในเซสชันของเอเจนต์การเขียนโค้ด:

- ตรวจจับคลาสคำสั่ง/ผลลัพธ์ เช่น `git status`, `git diff`, `git log`, ตัวรันทดสอบ,
  การบิลด์ TypeScript/Vite/Webpack, ESLint/Biome/Prettier, การตรวจสอบ/ติดตั้ง npm, บันทึก Docker, ผลลัพธ์โครงสร้างพื้นฐาน และผลลัพธ์ shell ทั่วไป
- ใช้ชุดตัวกรอง JSON จาก `open-sse/services/compression/engines/rtk/filters/`
- นำเข้าตัวกรองสคีมา TOML v1 ของ RTK จากไฟล์ `filters.toml` ระดับโปรเจกต์หรือส่วนกลาง พร้อมการตรวจสอบ inline-test และการควบคุมความน่าเชื่อถือสำหรับไฟล์ระดับโปรเจกต์
- มีตัวกรองในตัว 56 รายการพร้อมตัวอย่างการตรวจสอบแบบอินไลน์
- ลำดับอักขระควบคุม ANSI แถบความคืบหน้า บรรทัดที่ซ้ำกัน และข้อมูลรบกวนที่ไม่สามารถนำไปปฏิบัติได้จะถูกลบออก
- รักษาความล้มเหลว ข้อผิดพลาด คำเตือน ไฟล์ที่เปลี่ยนแปลง สรุปผล และส่วนท้ายของผลลัพธ์ที่ยาว
- รองรับตัวกรองระดับโปรเจกต์ที่ควบคุมด้วยความน่าเชื่อถือ ตัวกรองส่วนกลาง และการกู้คืนผลลัพธ์ดิบที่ถูกปกปิดข้อมูลตามตัวเลือก

**เหมาะสำหรับ:** เซสชันของเอเจนต์ที่ใช้ shell, build, test, git, grep และทรานสคริปต์ผลลัพธ์จากไฟล์

### โหมด Stacked (ช่วงที่ใช้ได้ 78-95%)

โหมด Stacked จะรันเอ็นจินการบีบอัดหลายตัวตามลำดับที่กำหนดแน่นอน ไปป์ไลน์เริ่มต้นคือ:

```txt
RTK -> Caveman
```

ลำดับนี้ทำให้ผลลัพธ์จากเทอร์มินัล/เครื่องมือกระชับก่อน จากนั้นจึงใช้การย่อเชิงความหมายของ Caveman
กับพรอมต์ภาษาธรรมชาติที่เหลือ ไปป์ไลน์แบบ Stacked สามารถกำหนดค่าทั่วโลกหรือผ่านชุดการบีบอัด
ที่กำหนดให้กับชุดการกำหนดเส้นทาง

**เหมาะสำหรับ:** บริบทแบบผสมที่มีบันทึกเครื่องมือขนาดใหญ่ รวมกับคำสั่งจากมนุษย์หรือสรุปจากผู้ช่วย

## คณิตศาสตร์การประหยัดจากต้นน้ำ

OmniRoute บันทึกข้อมูลการประหยัดจากการบีบอัดโดยอ้างอิงจากสองแหล่ง ได้แก่ เกณฑ์มาตรฐานของโปรเจกต์ต้นน้ำและ
การประกอบเอนจินของ OmniRoute เอง

| แหล่งที่มา | ตัวเลขจาก README ต้นน้ำที่ใช้ในที่นี้                                                                                 |
| ---------- | --------------------------------------------------------------------------------------------------------------------- |
| Caveman    | โทเค็นเอาต์พุตลดลง `~75%`, ประหยัดเอาต์พุตเฉลี่ยจากเกณฑ์มาตรฐาน `65%`, ช่วง `22-87%` และเครื่องมือบีบอัดอินพุต `~46%` |
| RTK        | ประหยัดเอาต์พุตคำสั่ง `60-90%`; เซสชันตัวอย่าง `~118,000 -> ~23,900` โทเค็น หรือประหยัด `79.7%` (`~80%`)              |

สำหรับเพย์โหลดของเครื่องมือ/บริบทที่ทับซ้อนกัน คอมโบเริ่มต้นของ OmniRoute จะซ้อนเอนจินดังนี้:

```txt
RTK -> Caveman
```

การประหยัดรวมคำนวณแบบคูณ ไม่ใช่แบบบวก:

```txt
รวม    = 1 - (1 - การประหยัดของ RTK) * (1 - การประหยัดอินพุตของ Caveman)
ค่าเฉลี่ย = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
ช่วง    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ตัวเลข `78-95%` นี้ใช้ได้เมื่อทั้ง RTK และ Caveman สามารถลดเพย์โหลดอินพุต/บริบทเดียวกันได้
โหมดเอาต์พุตการตอบกลับของ Caveman เป็นส่วนแยกต่างหาก: เมื่อเปิดใช้งาน ให้ใช้ค่าการประหยัดเอาต์พุตของ Caveman เอง (`65%`
โดยเฉลี่ย, ตัวเลขพาดหัว `~75%`, ช่วง `22-87%`) การประหยัดค่าใช้จ่ายทั้งหมดขึ้นอยู่กับสัดส่วนพรอมต์/เอาต์พุตของคุณ

### ความหมายที่แท้จริงของ "เข้าเกณฑ์"

ช่วงพาดหัว 15-95% เป็นตัวเลขจริง แต่ใช้ได้เฉพาะกับเนื้อหาที่ **ซ้ำซ้อนหรือเยิ่นเย้อ** เท่านั้น — เช่น บรรทัดข้อผิดพลาดที่เกิดซ้ำ
บันทึกการบิลด์ที่แสดงคำเตือนเดิมซ้ำจำนวนมาก หรือดัมป์จาก `grep`/การอ่านไฟล์ที่มีขนาดใหญ่เกินไป ตัวเลขนี้
**ไม่ได้** หมายความว่าทุกคำขอจะประหยัดได้มากขนาดนั้น

ผ่านการตรวจสอบเชิงประจักษ์แล้ว (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): การรันแบบ
`stacked` (RTK + Caveman) กับบล็อก `tool_result` รูปแบบ Anthropic ที่มีบรรทัดข้อผิดพลาดเหมือนกัน 300 บรรทัด
ให้ผลลัพธ์เป็น **ประหยัดโทเค็น 95.93% / ประหยัดอักขระ 96.26%** — อยู่ในช่วงที่ประกาศไว้อย่างชัดเจน
แต่เมื่อใช้ไปป์ไลน์เดียวกันกับเอาต์พุตเครื่องมือปกติที่ไม่ซ้ำซ้อน (รายการผลลัพธ์ `grep` ที่สะอาด
การอ่านไฟล์สั้น ๆ หรือข้อความสนทนาทั่วไป) ระบบจะให้ผลเป็น **การประหยัดเกือบศูนย์** อย่างถูกต้อง เนื่องจาก
ไม่มีสิ่งซ้ำซ้อนให้ลบ และ `validateCompression()` (`validation.ts`) จะไม่ยอมส่ง
ข้อความที่เขียนใหม่ซึ่งทำให้บล็อกโค้ด, URL, หัวข้อ, เวอร์ชัน หรือตัวระบุค่าคงที่แบบตัวพิมพ์ใหญ่ทั้งหมดสูญหายหรือเปลี่ยนแปลงไป

นี่เป็นพฤติกรรมที่คาดไว้และปลอดภัย ไม่ใช่ข้อบกพร่อง: เซสชันการเขียนโค้ดที่ส่วนใหญ่อ่าน/ค้นหาไฟล์ที่สะอาดด้วย `grep` จะ
ประหยัดโดยรวมได้ไม่มากนัก แม้เปิดใช้งานการบีบอัดอย่างเต็มที่แล้ว ขณะที่เซสชันที่พบลูปล้มเหลว
หรือลินเตอร์ที่สร้างข้อความจำนวนมากจะประหยัดได้เต็มช่วง 78-95% สำหรับทราฟฟิกส่วนนั้น อย่าใช้เปอร์เซ็นต์
การประหยัดรวมที่ต่ำจากเซสชันเดียวเป็นหลักฐานว่าการบีบอัดถูกกำหนดค่าผิด — ให้ตรวจสอบก่อนว่า
เอาต์พุตเครื่องมือต้นทางมีความซ้ำซ้อนจริงหรือไม่

## การกำหนดค่า

### แดชบอร์ด

ไปที่ `Dashboard → Context & Cache`:

- **Caveman** — การเลือกโหมด ชุดภาษา การแสดงตัวอย่าง และค่าเริ่มต้นส่วนกลาง
- **RTK** — การแสดงตัวอย่างตัวกรองคำสั่ง การตั้งค่าความปลอดภัยของ RTK และแค็ตตาล็อกตัวกรอง
- **Compression Combos** — ไปป์ไลน์เอนจินที่มีชื่อ ซึ่งกำหนดให้กับชุดการกำหนดเส้นทาง
- **Auto-Trigger Threshold** — เริ่มใช้การบีบอัดโดยอัตโนมัติเมื่อจำนวนโทเค็นเกินค่าขีดจำกัด

### การแทนที่ต่อชุด

ใน `Dashboard → Context & Cache → Compression Combos` ให้กำหนดชุดการบีบอัดให้กับชุดการกำหนดเส้นทาง:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

วิธีนี้ช่วยให้คุณใช้การบีบอัดแบบซ้อนกันกับผู้ให้บริการระดับฟรี/การเขียนโค้ด ขณะที่ยังคงใช้โหมด lite กับการสมัครสมาชิกแบบชำระเงิน

การกำหนด "Per-Combo Override" นี้เป็นการควบคุมคนละส่วนกับการแทนที่ **โหมดการบีบอัดของชุดการกำหนดเส้นทาง** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — สคีมาของฟิลด์นี้ยังรองรับ `rtk`, `stacked` และ `omniglyph` ด้วย) — การแทนที่ดังกล่าวจะไม่เลือกไปป์ไลน์ compression-combo ที่มีชื่อ แต่จะกำหนดเฉพาะฟิลด์ `compressionMode` ที่ `resolveCompressionPlan` ใช้ตรวจสอบเท่านั้น โดยสามารถตั้งค่าได้ทั้งบนการ์ดชุดการกำหนดเส้นทาง (`Dashboard → Combos`) หรือ ตั้งแต่ #6760 เป็นต้นมา สามารถตั้งค่าต่อชุดการกำหนดเส้นทางได้ในรายการ "Assign to routing" ที่ `Dashboard → Context & Cache → Compression Combos` ถัดจากช่องทำเครื่องหมายการกำหนดไปป์ไลน์ที่อธิบายไว้ด้านบน ทั้งสองตำแหน่งจะบันทึกข้อมูลผ่านเอนด์พอยต์ `PUT /api/combos/{id}` เดียวกัน

### การแทนที่ต่อคำขอ

ส่งเฮดเดอร์คำขอ `x-omniroute-compression` เพื่อแทนที่แผนการบีบอัดสำหรับคำขอเดียว โดยมีลำดับความสำคัญสูงสุด — มีผลเหนือการแทนที่ชุดการกำหนดเส้นทาง โปรไฟล์ที่ใช้งานอยู่ การเริ่มทำงานอัตโนมัติ และค่าเริ่มต้นของแผง Unknown values จะถูกละเว้น (คำขอจะไม่ถูกปฏิเสธ) และสวิตช์หลักส่วนกลางยังคงควบคุมทุกอย่าง: เมื่อปิดการบีบอัดไว้ทั่วโลก เฮดเดอร์นี้จะไม่สามารถเปิดใช้งานได้ ค่าที่รองรับมีดังนี้:

| ค่า           | ผลลัพธ์                                                                                        |
| ------------- | ---------------------------------------------------------------------------------------------- |
| `off`         | ไม่มีการบีบอัดสำหรับคำขอนี้                                                                    |
| `default`     | โปรไฟล์ Default ที่มาจากแผง (ไม่สนใจโปรไฟล์ที่ใช้งานอยู่) เอนจินแบบสูญเสียข้อมูลจะยังคงปิดอยู่ |
| `safe`        | เหมือนกับการไม่ส่งเฮดเดอร์                                                                     |
| `allow-lossy` | คงแผนของตัวดำเนินการสำหรับคำขอนี้ไว้ รวมถึงสรุป ตัวกรองความเกี่ยวข้อง และการเขียนรูปแบบใหม่    |
| `engine:<id>` | เอนจินเดียวเมื่อเปิดใช้งานแล้ว เช่น `engine:rtk` นี่คือการเลือกใช้เอนจินดังกล่าวต่อคำขอ        |
| `<combo>`     | ชุดที่มีชื่อ โดยจับคู่ตามชื่อ (ไม่พิจารณาตัวพิมพ์เล็ก-ใหญ่) ก่อน จากนั้นจึงจับคู่ตาม id        |

หากไม่มี `allow-lossy`, `engine:<id>` หรือชุดที่มีชื่อ ระบบจะไม่นำเอนจินแบบสูญเสียข้อมูลมาใช้ เมื่อ Default, การเริ่มทำงานอัตโนมัติ หรือการแทนที่เส้นทางแบบสูญเสียข้อมูลถูกลดระดับ OmniRoute จะคงขั้นตอนแบบไม่สูญเสียข้อมูลที่รู้จักจากไปป์ไลน์แบบซ้อนกันที่กำหนดค่าไว้ โดยเรียงตามลำดับที่กำหนดค่าไว้ ระบบจะย้อนกลับไปใช้ `session-dedup → lite` เฉพาะเมื่อไม่มีขั้นตอนแบบไม่สูญเสียข้อมูลที่กำหนดค่าไว้เหลืออยู่เท่านั้น

ตัวอย่าง **Effective pipeline** ของแผง Settings จะแสดงแผนปกติขณะไม่มีการร้องขอ เมื่อสามารถเรียกใช้การเริ่มทำงานอัตโนมัติได้ ตัวอย่างเดียวกันนี้จะแสดงไปป์ไลน์ที่มีผลแบบมีเงื่อนไขด้วย เพื่อให้การแก้ไขค่าของแผงและการแก้ไขค่าขณะรันไทม์โดยไม่มีเฮดเดอร์สอดคล้องกัน

แผนที่นำไปใช้จะถูกส่งกลับในเฮดเดอร์การตอบกลับ `X-OmniRoute-Compression: <mode>; source=<source>` โดย `<source>` จะเป็นค่าใดค่าหนึ่งใน `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` หรือ `off`

### API

```bash
# รับการตั้งค่าการบีบอัด
curl http://localhost:20128/api/settings/compression

# อัปเดตการตั้งค่าการบีบอัด
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# แสดงตัวอย่างเพย์โหลด RTK/stacked ที่ระบุ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# แสดงรายการชุดตัวกรอง RTK
curl http://localhost:20128/api/context/rtk/filters

# ทดสอบ RTK โดยตรงพร้อมข้อมูลเมทาดาทาของคำสั่งที่เป็นตัวเลือก
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## ระบบการบีบอัดขั้นสูง

นอกเหนือจากโหมด 7 โหมดที่อธิบายไว้ข้างต้น (แหล่งที่มายังยอมรับโหมด `codex-responses` และ `omniglyph` ซึ่งคู่มือนี้ไม่ครอบคลุม) ส่วนด้านล่างจะครอบคลุมถึงคุณสมบัติที่ทำงานภายในหรือควบคู่ไปกับโหมดเหล่านั้น: Tool Result Compression และ Progressive Aging เป็นขั้นตอนที่ 1 และ 2 ของเอ็นจิ้นเชิงรุก (โหมด Aggressive และขั้นตอน `aggressive` ของไปป์ไลน์แบบซ้อนกัน) Stacked Pipeline คือวิธีการทำงานของโหมด Stacked, Cache-Aware Compression ปรับลด `aggressive` และ `ultra` เป็น `standard` สำหรับผู้ให้บริการแคชในขณะที่เปิดการบีบอัด และ Caveman Output Mode และ Output Styles เป็นคำสั่งที่ระบบเลือกใช้ ซึ่งปิดไว้ตามค่าเริ่มต้น ซึ่งจะกำหนดรูปร่างเอาต์พุตของโมเดลแทนที่จะบีบอัดคำขอ

### การบีบอัดแคช Aware

ผู้ให้บริการบางราย (เช่น Anthropic พร้อมการแคชทันที) รองรับ** แคชทันที** ซึ่งช่วยให้พวกเขาแคชบางส่วนของข้อความแจ้งเพื่อลดต้นทุนและเวลาแฝงได้ เมื่อเปิดใช้งานการแคช การบีบอัดเชิงรุกสามารถทำได้จริง** เจ็บ** ประสิทธิภาพการทำงานเนื่องจากจะเปลี่ยนโทเค็นที่แคชไว้ ทำให้แคชใช้ไม่ได้

โมดูล `cachingAware.ts` แก้ปัญหานี้โดย** การตรวจจับบริบทการแคช** และ** การปรับกลยุทธ์การบีบอัด** ตามนั้น

#### มันทำงานอย่างไร

1. **ตรวจหาบริบทการแคช** — สแกนเนื้อหาคำขอเพื่อหาเครื่องหมาย `cache_control`
2. **ระบุผู้ให้บริการแคช** — ตรวจสอบว่าผู้ให้บริการเป้าหมายรองรับการแคชหรือไม่
3. **ปรับกลยุทธ์** — ปรับลดรุ่น `aggressive`/`ultra` เป็น `standard` สำหรับผู้ให้บริการแคช
4. **ข้ามข้อความแจ้งของระบบ** พรอมต์ของระบบ — มักจะถูกแคชไว้ ดังนั้นอย่าบีบอัดพรอมต์เหล่านั้น

ตัวช่วยกลยุทธ์ยังส่งคืนแฟล็ก `deterministicOnly` ด้วย แต่ตัวสร้างแผนใช้เฉพาะกลยุทธ์ — โดยที่ดาวน์สตรีมจะไม่อ่านแฟล็กในวันนี้

#### ตัวอย่างรหัส

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### เมื่อจะใช้

การบีบอัดแบบรับรู้แคชคือ** เปิดอยู่เสมอ** — ไม่จำเป็นต้องกำหนดค่าใดๆ มันจะเริ่มทำงานทุกครั้งที่เปิดการบีบอัดและผู้ให้บริการเป้าหมายรองรับการแคชทันที (Anthropic, OpenAI ฯลฯ ); ไม่จำเป็นต้องมีเครื่องหมาย `cache_control` ที่ชัดเจน — ผู้ให้บริการแคชเพียงอย่างเดียวจะทริกเกอร์การลดระดับ และเครื่องหมายเพียงอย่างเดียวจะไม่ทำ (การตรวจจับเครื่องหมายจะฟีดแคช telemetry ไม่ใช่การตัดสินใจด้านกลยุทธ์)

OpenRouter นับเป็นผู้ให้บริการแคชสำหรับรุ่น `anthropic/*` เท่านั้น: คำขอรหัส Claude จะเก็บเบรกพอยต์ `cache_control` ไว้ (สูงสุด 4 ตัว) และตัวป้องกันจะปกป้องคำนำหน้า ในขณะที่ตระกูล OpenRouter อื่นๆ ทุกตระกูล (`openai/`, `google/`, `qwen/`, …) ยังคงถูกปลดเปลื้องและไม่มีการป้องกัน

### การแก่ชราแบบก้าวหน้า

การสนทนาที่ยาวนานจะสะสมข้อความจำนวนมาก แต่การสนทนาที่เก่ากว่าจะมีความเกี่ยวข้องน้อยลง โมดูล `progressiveAging.ts`** ลดระดับข้อความตามระยะทางเลี้ยว** (ระยะทางวัดจากท้ายบทสนทนา) ด้วยค่าเริ่มต้นที่จัดส่ง (`verbatim: 2, light: 2, moderate: 3`):

- **2 เทิร์นสุดท้าย (ระยะ ≤ 2)** : เก็บไว้เป็นคำต่อคำ
- **ระยะทาง 3** : การบีบอัด Caveman (การกำจัดฟิลเลอร์)
- **ระยะทาง 4 +** : สรุปข้อความผู้ช่วย; ข้อความของผู้ใช้ลดลงเหลือบรรทัดแรก โดยมีความยาวสูงสุด 120 อักขระ บทบาทอื่น ๆ ไม่ได้ถูกแตะต้อง ข้อความแจ้งของระบบ ข้อความที่เก่าแล้ว และข้อความของผู้ใช้ล่าสุดจะถูกเก็บไว้แบบคำต่อคำเสมอโดยไม่คำนึงถึงระยะห่าง ไม่มีสิ่งใดถูกทิ้งทันทีและไม่สามารถเข้าถึงแบนด์ `light` ด้วยค่าเริ่มต้นที่จัดส่ง (`light` เท่ากับ `verbatim`)

#### ตัวอย่างรหัส

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### เมื่อจะใช้

วัยที่ก้าวหน้าก็คือ** เปิดอยู่เสมอ** สำหรับโหมด `aggressive` — มันคือขั้นตอนที่ 2 ของ `compressAggressive()` โหมด Ultra ไม่ทำงาน มีประสิทธิภาพโดยเฉพาะอย่างยิ่งสำหรับ:

- เซสชันการเขียนโค้ดที่ยาวนาน
- การสนทนาหลายวัน
- เวิร์กโฟลว์ตัวแทนที่มีการเรียกใช้เครื่องมือมากมาย

### โหมดเอาท์พุตมนุษย์ถ้ำ

เพิ่มโหมดเอาท์พุตมนุษย์ถ้ำ** คำแนะนำของระบบ** ที่ถามโมเดลเองสำหรับเอาต์พุตสั้น ๆ — ระดับ `lite` ถามหาคำตอบที่กระชับซึ่งเก็บประโยคเต็ม `full` ขอให้ "ตอบสั้น ๆ เหมือนมนุษย์ถ้ำที่ฉลาด" และ `ultra` ถามเอาท์พุททางโทรเลข คำแนะนำเพียงถามเท่านั้น พวกเขาไม่สามารถรับประกันได้ คำขอจะได้รับผ่าน `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`): อันดับแรก `open-sse/handlers/chatCore.ts` จะแก้ไขการเลือกด้วย back-compat shim (`resolveOutputStyleSelection()` ใน `open-sse/services/compression/outputStyles/backCompat.ts`) ซึ่งในขณะที่ `outputStyles` ว่างเปล่า ให้จับคู่ `cavemanOutputMode` ที่เปิดใช้งานกับรูปแบบเอาต์พุต `terse-prose` ที่ `cavemanOutputMode.intensity` (ดู Back-compat ด้านล่าง) การเลือก `outputStyles` ที่ไม่ว่างเปล่าจะถูกใช้ตามที่เป็นอยู่ จากนั้น `cavemanOutputMode.enabled` และ `intensity` จะไม่มีผลใดๆ ในขณะที่การสลับ `autoClarity` ยังคงใช้อยู่ `outputMode.ts` เก็บข้อความคำสั่ง (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`) การเลี่ยงเนื้อหา และผู้ช่วยจัดตำแหน่งที่การฉีดใช้ หัวฉีด `applyCavemanOutputMode()` ของตัวเองไม่มีผู้เรียกการผลิต

#### มันทำงานอย่างไร

โหมดนี้ไม่บีบอัดอินพุต โดยจะเพิ่มบล็อกคำสั่งให้กับพรอมต์ของระบบ (ดูวิธีการทำงานของการฉีดด้านล่าง) และโหมดการบีบอัดอินพุตใดๆ ที่เลือกไว้สำหรับคำขอจะยังคงทำงานหลังจากนั้น บนเนื้อหาที่ขณะนี้บล็อกอยู่ นำหน้าประโยคขอบเขตที่ใช้ร่วมกันที่ทุกระดับลงท้ายด้วย ระดับ `full` ภาษาอังกฤษจะอ่านว่า:

> "ตอบสั้น ๆ เหมือนมนุษย์ถ้ำที่ฉลาด วางบทความ (a/an/the) ฟิลเลอร์ (just/really/basically/actually/simply) รื่นรมย์ ป้องกันความเสี่ยง แฟรกเมนต์ OK คำพ้องความหมายสั้น ๆ (ใหญ่ ไม่ครอบคลุม แก้ไขไม่ได้นำไปใช้) เก็บเนื้อหาทางเทคนิค รหัส ข้อผิดพลาด URLs ตัวระบุให้ถูกต้องทั้งหมด "

สิ่งนี้ใช้ได้ผลดีเป็นพิเศษสำหรับ:

- การสร้างโค้ด (เอาต์พุต terser = โทเค็นน้อยลง)
- ถามตอบด่วน (ไม่จำเป็นต้องอธิบายให้ละเอียด)
- การประมวลผลเป็นชุด (เพิ่มปริมาณงานสูงสุด)

#### เมื่อจะใช้

โหมดเอาท์พุตมนุษย์ถ้ำคือ** เลือกใช้** . เมื่อเปิดการบีบอัด (`enabled: true` ตัวสลับหลักในหน้าการตั้งค่าการบีบอัด) ให้เปิดด้วย `cavemanOutputMode.enabled`; `intensity` เลือก `lite`, `full` หรือ `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

คอมโบการบีบอัด** โหมดเอาท์พุต** toggle (`outputMode`, ระดับเป็น `outputModeIntensity`) ตั้งค่าสวิตช์เดียวกันสำหรับคำขอที่คอมโบใช้ และเครื่องมือ `omniroute_set_compression_engine` MCP เขียนมันผ่านอาร์กิวเมนต์ `outputMode` บูลีน การเลือก `outputStyles` ที่ไม่ว่างเปล่าจะมีความสำคัญเหนือกว่าสวิตช์นี้ ในแดชบอร์ดเปิดใช้งาน** ร้อยแก้วสั้น ๆ** รูปแบบเอาต์พุตจะแทรกบล็อกเดียวกัน (ดูรูปแบบเอาต์พุตด้านล่าง)

### รูปแบบผลงาน (แค็ตตาล็อก)

| เตอร์เซ CJK (文言)                 | `terse-cjk`     | คำตอบ `full`/`ultra` ในภาษาจีนคลาสสิก (文言); `lite` จะถามเฉพาะคำตอบสั้นๆ เท่านั้น โดยไม่มีคำที่สื่อความหมาย คำสุภาพ หรือคำเสริมแต่ง                                                                                                                        | zh (locale-gated ดูด้านล่าง)                   |

ทุกสไตล์มีระดับความเข้มข้นสามระดับ — `lite`, `full`, `ultra` — และทุกระดับจะลงท้ายด้วย shared boundaries clause (`SHARED_BOUNDARIES` ใน `outputMode.ts`) ซึ่งจะเก็บบล็อกโค้ด เส้นทางไฟล์ คำสั่ง ข้อผิดพลาด และ URLs ที่แน่นอน ข้อความระดับ `terse-prose` และ `terse-cjk` จะเพิ่มตัวระบุให้กับรายการนั้น

`terse-cjk` เป็น locale-gated ถึง `zh` ในสองแห่ง หน้าการตั้งค่าการบีบอัดจะแสดงแถวเฉพาะเมื่อภาษา UI ของแดชบอร์ดเป็นภาษาจีน (`zh-CN` หรือ `zh-TW`) และ `applyOutputStyles()` แทรกเฉพาะเมื่อภาษาที่แก้ไขแล้วของคำขอ (ดูการเลือกภาษาด้านล่าง) คือ `zh` การซ่อนแถวไม่ได้ล้างการเลือก `terse-cjk` ที่บันทึกไว้: การตั้งค่า API ยอมรับรหัสสไตล์ใดๆ และการบันทึกสไตล์อื่นๆ บนเพจจะยังคงอยู่ ณ เวลาร้องขอ การตรวจสอบภาษา `applyOutputStyles()` เป็นประตูโลแคลเดียวเท่านั้น

#### การฉีดทำงานอย่างไร

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) แก้ไขการเลือกกับแค็ตตาล็อก (id ที่ไม่รู้จักและสไตล์ที่ไม่ตรงกันของโลแคลจะถูกละทิ้ง ไม่มีข้อผิดพลาด การเลือกที่แก้ไขเป็นไม่มีสไตล์จะทำให้เนื้อหาไม่เปลี่ยนแปลง ข้ามเป็น `no_styles`) เชื่อมต่อคำสั่งที่เลือกตามลำดับแค็ตตาล็อก ผนวกส่วนคำสั่งขอบเขต** ครั้งหนึ่ง** (รวมถึงส่วนคำสั่งความปลอดภัย `SAFETY_BOUNDARIES` หรือการแปล เมื่อเลือก `less-code` หรือ `ponytail` ) และเริ่มต้นบล็อกด้วยเครื่องหมาย idempotency เดียว (`[OmniRoute Output Styles]`) ดังนั้นการนำกลับมาใช้ใหม่จึงไม่ต้องดำเนินการ เมื่อภาษาที่ได้รับการแก้ปัญหา (ดูการเลือกภาษาด้านล่าง) มีการแปล คำสั่งที่แปลเป็นภาษาท้องถิ่นจะถูกแทรกเข้าไปแทนภาษาอังกฤษ

บนเนื้อหาที่มีอาร์เรย์ `messages` ที่ไม่ว่างเปล่า การตรวจสอบ idempotency จะทำงานก่อนที่จะข้ามเนื้อหา: เมื่อเครื่องหมาย `[OmniRoute Output Styles]` อยู่ในฟิลด์ `system` ระดับบนสุดแล้ว (สตริงหรืออาร์เรย์บล็อกเนื้อหา) หรือในข้อความระบบที่มีเนื้อหาเป็นสตริง เนื้อความจะไม่เปลี่ยนแปลงเป็น `already_applied` และไม่มีการเรียกใช้การตรวจสอบคำหลัก มิฉะนั้น การข้ามเนื้อหา (`shouldBypassCavemanOutputMode()` ใน `open-sse/services/compression/outputMode.ts`) จะตรวจสอบข้อความของสามข้อความล่าสุด ไม่ว่าบทบาทจะเป็นอย่างไร และข้ามสไตล์ตลอดทั้งเทิร์นเมื่อข้อความนั้นตรงกับคีย์เวิร์ดด้านความปลอดภัย การดำเนินการที่ไม่สามารถย้อนกลับได้ หรือการชี้แจง หรือลำดับที่ละเอียดอ่อนตามลำดับ: `first`, `then`, `after that`, `before`, `rollback` หรือ `backup` ตามด้วยอักขระไม่เกิน 240 ตัวโดย `delete` `drop`, `migrate`, `deploy` หรือ `release` ทางเลี่ยงวิ่งในขณะที่** บายพาสความคมชัดอัตโนมัติ** สลับ (`cavemanOutputMode.autoClarity` เปิดโดยค่าเริ่มต้น) เปิดอยู่; การปิดสวิตช์จะข้ามการตรวจสอบคำหลัก

เมื่อบายพาสปล่อยให้เลี้ยวผ่านไป `placeSystemInstruction()` (ไฟล์เดียวกัน) ซึ่งไม่เคยสร้าง `messages[0]` ใหม่ ให้วางบล็อกไว้ที่ตัวแรกที่พบ:

1. ข้อความระบบนำหน้าที่มีเนื้อหาเป็นสตริง: บล็อกจะถูกต่อท้ายข้อความ
2. ฟิลด์ `system` ระดับบนสุด: บล็อกจะถูกต่อท้ายข้อความของสตริง หรือเพิ่มเป็นบล็อกข้อความใหม่ในอาร์เรย์บล็อกเนื้อหา
3. ข้อความระบบข้อความแรกในภายหลังที่มีเนื้อหาเป็นสตริง: บล็อกจะถูกต่อท้ายข้อความ
4. ไม่มีข้อใดที่กล่าวมาข้างต้น: บล็อกจะเข้าสู่ข้อความระบบใหม่ที่ส่วนท้ายของ `messages`

บนเนื้อความที่ไม่มีอาร์เรย์ `messages` (หรืออาร์เรย์ว่าง) จะไม่มีการเรียกใช้การเลี่ยงเนื้อหาและฟิลด์ `system` ระดับบนสุดจะไม่ได้รับการพิจารณา บล็อกจะถูกต่อท้ายข้อความของฟิลด์สตริง `instructions` เว้นแต่ว่าฟิลด์นั้นมีเครื่องหมาย `[OmniRoute Output Styles]` อยู่แล้ว ซึ่งในกรณีนี้เนื้อหาจะไม่เปลี่ยนแปลงเป็น `already_applied` เมื่อเนื้อหาไม่มีฟิลด์สตริง `instructions` แต่มี `input` (สตริงหรืออาร์เรย์) บล็อกจะกลายเป็น `instructions` แทนที่ค่าที่ไม่ใช่สตริงที่ฟิลด์นั้นเก็บไว้ เนื้อความที่ไม่มีฟิลด์สตริง `instructions` หรือสตริงหรืออาร์เรย์ `input` จะไม่มีการเปลี่ยนแปลงและข้ามเป็น `no_messages`

#### วิธีการเปิดใช้งาน

ในแดชบอร์ด:** บริบทการบีบอัด การตั้งค่าการบีบอัด →** (`/dashboard/context/settings`) ส่วนสไตล์เอาต์พุต: หนึ่งแถวต่อสไตล์พร้อมสลับ on/off และตัวเลือกระดับ สไตล์ที่ฉีดในขณะที่เปิดการบีบอัด (ตัวสลับหลักของหน้า `enabled`) ที่** บายพาสความคมชัดอัตโนมัติ** สลับเปิดอยู่** มนุษย์ถ้ำ** หน้า (`/dashboard/context/caveman`) ในนั้น** โหมดเอาท์พุต** การ์ด. โดยทางโปรแกรม การกำหนดค่าการบีบอัดจะยังคงเลือกเป็น:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ความเข้ากันได้แบบย้อนกลับ: ในขณะที่ `outputStyles` ว่างเปล่า การตั้งค่า `cavemanOutputMode.enabled` แบบเดิมจะแมปกับ `terse-prose` ที่ `cavemanOutputMode.intensity` จากนั้นบล็อกจะเริ่มต้นด้วยเครื่องหมาย `[OmniRoute Output Styles]` โดยที่ `applyCavemanOutputMode()` injector แบบเดิมเขียน `[OmniRoute Caveman Output Mode]` ด้านล่างเครื่องหมาย ข้อความตรงกับการแทรกแบบดั้งเดิมใน en, pt-BR, es, de, fr, it, ru, id และ vi; ใน ja และ zh จะมีช่องว่างเพิ่มหนึ่งช่องก่อนส่วนคำสั่งขอบเขต `terse-prose` แปลเป็น pt-BR, es, de, fr, it, ru, zh, ja, id และ vi ดังนั้นคำขอที่มีภาษาที่แก้ไขแล้วคือ `hu` จะได้รับข้อความภาษาอังกฤษที่ injector แบบเดิมใช้ภาษาฮังการี

การเลือกภาษารูปแบบเอาต์พุต (`resolveOutputStyleLanguage()` ใน `outputStyles/apply.ts`): เมื่อเปิด `languageConfig.enabled` `autoDetect` จะสุ่มตัวอย่างข้อความผู้ใช้ล่าสุดในอาร์เรย์ `messages` ของคำขอที่มีข้อความ (เนื้อหาสตริงหรือ `text` ของส่วนเนื้อหา) และเรียกใช้ตัวตรวจจับของ Caveman engine (`detectCompressionLanguage()`) อยู่ เครื่องมือตรวจสอบจะส่งคืน `zh` สำหรับข้อความที่มีอักขระ Han และไม่มี kana มิฉะนั้นจะส่งกลับค่าใดก็ตามของ `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` และ `id` มีคำใบ้ที่ตรงกันมากที่สุด และ `en` เมื่อไม่มีข้อความที่ตรงกับ — ข้อความจะไม่สามารถจำแนกประเภทได้รับภาษาอังกฤษ ไม่เคย `defaultLanguage` และไม่เคยตรวจพบ `vi` แม้ว่าสไตล์จะจัดส่งข้อความ `vi` เนื้อหาการตอบสนอง API จะผลัดกันเป็น `input` ซึ่งไม่ได้สุ่มตัวอย่าง ดังนั้นจึงได้ `defaultLanguage` ตามด้วยภาษาอังกฤษ เมื่อไม่มีข้อความผู้ใช้ใน `messages` มีข้อความ หรือปิด `autoDetect` จะใช้ `defaultLanguage` ตามด้วยภาษาอังกฤษ เมื่อปิด `languageConfig.enabled` ภาษาจะเป็นภาษาอังกฤษ — เว้นแต่ว่าคำสั่งผสมการบีบอัดจะใช้กับคำขอ (คำสั่งผสมที่กำหนดให้กับคำสั่งผสมการกำหนดเส้นทางของคำขอ หรือคำสั่งผสมการบีบอัดเริ่มต้น chatCore จะถอยกลับไปสำหรับไปป์ไลน์แบบสแต็กในตัว): การใช้คำสั่งผสมจะเปิด `languageConfig.enabled` สำหรับคำขอนั้น และตั้งค่า `defaultLanguage` จากชุดภาษาของคำสั่งผสม (ค่าที่บันทึกไว้หากเป็นหนึ่งในแพ็กของคอมโบ มิฉะนั้นจะเป็นแพ็กแรกของคอมโบ ซึ่งมีค่าเริ่มต้นเป็น `en`) ในขณะที่ `autoDetect` ที่บันทึกไว้ (เปิดโดยค่าเริ่มต้น) ยังคงมีผลอยู่ เอ็นจิ้นอินพุต Caveman เลือกภาษาของชุดกฎที่แตกต่างกัน — ต่อส่วนของข้อความ และปิดการตรวจจับอัตโนมัติ `enabledPacks`

เมทริกซ์ภาษา × ของสไตล์ถูกปักหมุดโดย `tests/unit/compression/output-styles-i18n-matrix.test.ts`: ทุกสไตล์แคตตาล็อกจำเป็นต้องมีรายการในการทดสอบ `BASELINE_LANGUAGES`; สไตล์ที่ไม่ใช่ locale-gated จะต้องจัดส่งการแปล pt-BR ( `terse-cjk` ที่ locale-gated ได้รับการยกเว้นจากกฎนี้) เว้นแต่จะมีการระบุไว้ใน `KNOWN_ENGLISH_ONLY` ซึ่งอาจเก็บเฉพาะสไตล์ที่ไม่มีการแปลเลย — สไตล์ที่อยู่ในรายการที่มีการแปลใด ๆ ไม่ผ่านการทดสอบ และสไตล์ไม่ผ่านการทดสอบเมื่อสูญเสียภาษาที่อยู่ในรายการ `BASELINE_LANGUAGES` หากต้องการเพิ่มสไตล์ โปรดดูที่ [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)

### การบีบอัดผลลัพธ์ของเครื่องมือ

`compressToolResult()` ใน `open-sse/services/compression/toolResultCompressor.ts` บีบอัดข้อความผลลัพธ์ของเครื่องมือด้วย** 5 กลยุทธ์** . โดยจะลองใช้ตามลำดับนี้ และกลยุทธ์ที่เปิดใช้งานครั้งแรกซึ่งมีการตรวจสอบตรงกับเนื้อหาจะตัดสินผลลัพธ์:

1. **`fileContent`** : เนื้อหาตั้งแต่ 3 บรรทัดขึ้นไปโดยละเว้นการเยื้องนำหน้าอย่างน้อยหนึ่งบรรทัด เริ่มต้นด้วย `import `, `export `, `function `, `class `, `const `, `let `, `var ` หรือ `return ` (คีย์เวิร์ดบวกช่องว่าง) หรือด้วย `if`, `for` หรือ `while` ตามด้วย `(` หรือ ` (` เก็บ 20 ตัวแรกและ 5 ตัวสุดท้ายไว้ เส้นที่มีเครื่องหมายกลบตรงกลาง
2. **`grepSearch`** : เนื้อหาที่มีรูปแบบอย่างน้อยหนึ่งบรรทัด `<path>:<digits>:` โดยที่ข้อความก่อนโคลอนแรกไม่มีช่องว่าง จะเก็บเฉพาะบรรทัดเหล่านั้น สูงสุด 30 บรรทัด ตามด้วยจำนวนรายการที่ตรงกันเพิ่มเติมและรายการไฟล์ที่ตรงกัน ทุกบรรทัดอื่น ๆ จะถูกละทิ้ง บรรทัดดังกล่าวเพียงบรรทัดเดียวก็เพียงพอที่จะกระตุ้นกลยุทธ์ ดังนั้นบรรทัดบันทึกที่เริ่มต้นด้วยการประทับเวลา เช่น `12:30:45` ก็นับเช่นกัน
3. **`shellOutput`** : เอาต์พุตที่มีลำดับ ANSI CSI (`ESC[` ตามด้วยตัวเลขหรืออัฒภาคตามด้วยตัวอักษร เช่นเดียวกับในรหัสสี) หรือ `$` ตามด้วยช่องว่างที่ใดก็ได้ในข้อความ จะทำให้ลำดับเหล่านั้นหายไป (การหลีกเลี่ยงอื่นๆ เช่น `ESC[?25l` หรือลำดับชื่อหน้าต่าง OSC จะถูกเก็บไว้) และเก็บ 50 บรรทัดสุดท้ายไว้ โดยที่บรรทัดที่ซ้ำกันติดต่อกันจะยุบลง เนื่องจากการตรวจสอบนี้ทำงานก่อน `json` และ `errorMessage`, JSON หรือเอาต์พุตข้อผิดพลาดที่มี `$` ดังกล่าวไม่เคยเข้าถึงในขณะที่ `shellOutput` เปิดอยู่
4. **`json`** : เพย์โหลด JSON มากกว่า 2,000 อักขระที่ขึ้นต้นด้วย `{` หรือ `[` (หลังจากช่องว่างเผื่อเลือก) และสรุปการแยกวิเคราะห์: อาร์เรย์ที่มีมากกว่า 7 รายการจะเก็บ 5 รายการแรกและ 2 รายการสุดท้ายและจำนวนทั้งหมดไว้ และออบเจ็กต์จะเก็บ 20 คีย์แรกไว้ โดยแต่ละออบเจ็กต์ที่ซ้อนกันหรือค่าอาร์เรย์จะถูกแทนที่ด้วยตัวยึด `{…N keys}` (สำหรับอาร์เรย์ N คือความยาวของคีย์) และเครื่องหมาย `_remaining_<N>_keys` ที่นับคีย์ที่ปล่อยผ่านคีย์แรก 20. ค่าสเกลาร์จะถูกคัดลอกทั้งหมด ดังนั้นออบเจ็กต์ที่มี 20 คีย์หรือน้อยกว่าที่ไม่มีค่าที่ซ้อนกันจะถูกเยื้องใหม่เพียง — ส่วนค่าที่ย่อเล็กสุดจะได้รับอักขระและไม่มีการเปลี่ยนแปลง
5. **`errorMessage`** : เอาต์พุตที่มีทุกที่และในกรณีตัวอักษรใดๆ `error:`, `error ` (คำที่ตามด้วยช่องว่าง เช่นเดียวกับใน `no error found`), `[error]`, `exception:`, `exception `, `[exception]` หรือ `traceback` จะเก็บบรรทัดแรกไว้ 10 บรรทัดถัดไปและ 3 บรรทัดสุดท้าย โดยมีเครื่องหมาย `… [N frames elided] …` แทนที่บรรทัดที่อยู่ระหว่างบรรทัดเหล่านั้น เครื่องหมายจะปรากฏเฉพาะเมื่อมีมากกว่า 13 บรรทัดต่อจากบรรทัดแรก ดังนั้นข้อผิดพลาดที่ส่งออกไป 14 บรรทัดหรือน้อยกว่าจะไม่ถูกทำให้สั้นลง (ที่ 12 หรือ 13 บรรทัด บรรทัดที่ซ้ำกัน 3 บรรทัดสุดท้ายจะเก็บไว้แล้ว)

หลังจากที่กลยุทธ์ตรงกัน แม้แต่กลยุทธ์ที่ไม่ช่วยอะไรเลย กลยุทธ์ในภายหลังก็จะไม่ลองใช้ เมื่อกลยุทธ์การจับคู่ไม่ได้บันทึกโทเค็นโดยประมาณ (ความยาว ÷ 4 ปัดเศษขึ้น) — เช่น ไฟล์คล้ายโค้ดที่มี 25 บรรทัดหรือน้อยกว่า หรืออาร์เรย์ JSON มากกว่า 2,000 อักขระ โดยมี 7 รายการหรือน้อยกว่า — เอ็นจิ้นเชิงรุกจะคงผลลัพธ์ของเครื่องมือดั้งเดิมไว้: ทั้งผู้เรียก (`compressAggressive()` และ `compressAnthropicToolResultBlock()`) คงต้นฉบับไว้เมื่อ `saved` เป็น 0 หรือต่ำกว่า ในขณะที่ `compressToolResult()` เองยังคงส่งคืนผลลัพธ์นั้น ผลลัพธ์ของกลยุทธ์ ขั้นตอนผลลัพธ์ของเครื่องมือไม่ใช่คำสุดท้าย: ตัวสรุปทางเลือกของกลไกยังคงสามารถย่อข้อความ `tool` หรือ `function` ที่ยาวกว่า 8,192 อักขระ (`maxTokensPerMessage`, 2,048, คูณ 4)

#### เมื่อจะใช้

การบีบอัดผลลัพธ์ของเครื่องมือคือขั้นตอนที่ 1 ของเอ็นจิ้นเชิงรุก (`compressAggressive()` ใน `open-sse/services/compression/aggressive.ts`) ดังนั้นจึงรันในโหมด Aggressive และในขั้นตอน `aggressive` ของไปป์ไลน์แบบสแต็ก มันบีบอัดข้อความ `tool` และ `function` รูปร่าง OpenAI และข้อความภายในบล็อก Anthropic `tool_result` แต่ละกลยุทธ์มีสวิตช์ของตัวเองภายใต้ `aggressive.toolStrategies` ซึ่งทั้งหมดจะเปิดตามค่าเริ่มต้น ในแดชบอร์ด สวิตช์จะอยู่ในหน้า Caveman** ขั้นสูง** ดูขณะเปิดการบีบอัดและโหมดเริ่มต้นคือแบบก้าวร้าว

### ท่อซ้อนกัน

โหมดสแต็กทำงาน** เครื่องยนต์หลายเครื่องตามลำดับ** — โดยปกติ RTK ก่อน (ประหยัด 60-90% สำหรับเอาท์พุตเครื่องมือ) จากนั้น Caveman กับข้อความที่เหลือ (ประหยัดอินพุต ~ 46%) ประกอบนั่นคือ** ช่วงที่มีสิทธิ์ 78-95%** (ดูคณิตศาสตร์การออมขั้นต้นด้านบน): `1 - (1 - 0.60..0.90) × (1 - 0.46)` เฉลี่ย ≈ 89%

#### มันทำงานอย่างไร

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### เมื่อจะใช้

ใช้โหมดสแต็กสำหรับ:

- ขั้นตอนการทำงานที่ต้องใช้เครื่องมือจำนวนมาก (การเข้ารหัสแบบเอเจนต์ การวิจัย)
- การประมวลผลแบบแบตช์ที่คำนึงถึงต้นทุน
- เมื่อคุณต้องการประหยัดโทเค็นสูงสุด

ไปป์ไลน์แบบสแต็กได้รับการกำหนดค่าผ่านการตั้งค่าการบีบอัด `stackedPipeline` ส่วนกลาง หรือผ่านคอมโบการบีบอัดที่ระบุชื่อซึ่งกำหนดให้กับคอมโบการกำหนดเส้นทาง (ดูการแทนที่ Per-Combo ด้านบน) — ไม่ใช่ผ่านคอมโบอัตโนมัติ `modePack` (ฟิลด์นั้นจะมีน้ำหนักซ้ำเฉพาะการเลือกโมเดลคอมโบอัตโนมัติเท่านั้น และ `stacked` ไม่ใช่ชื่อแพ็กที่ถูกต้อง)

## การกำหนดค่าทับสำหรับชุดคอมโบการบีบอัด

คุณสามารถกำหนดโหมดการบีบอัดส่วนกลางทับ **เป็นรายคอมโบ** เพื่อปรับแต่งลักษณะการทำงาน
ให้เหมาะสมกับกรณีการใช้งานต่างๆ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

สิ่งนี้มีประโยชน์สำหรับ:

- **คอมโบการเขียนโค้ด**: ใช้โหมด `aggressive` สำหรับเซสชันที่ยาวนาน
- **คอมโบถาม-ตอบแบบรวดเร็ว**: ใช้โหมด `lite` เพื่อการตอบกลับที่รวดเร็ว
- **คอมโบที่ใช้เครื่องมือจำนวนมาก**: ใช้โหมด `stacked` เพื่อประหยัดสูงสุด
- **คอมโบสำหรับระบบใช้งานจริง**: ปิดการกำหนดค่าทับไว้สำหรับผู้ให้บริการที่รองรับการแคช — การปรับค่า
  โดยคำนึงถึงแคชซึ่งเปิดใช้งานอยู่เสมอ จะลดระดับ `aggressive`/`ultra` เป็น `standard` โดยอัตโนมัติ
  (ไม่มีโหมด `cache-aware` ที่สามารถเลือกได้)
