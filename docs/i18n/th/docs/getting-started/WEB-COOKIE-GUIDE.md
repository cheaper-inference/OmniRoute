ผู้ให้บริการ Web Cookie ช่วยให้ OmniRoute สามารถใช้บริการ AI ผ่านเซสชันเบราว์เซอร์ที่คุณใช้งานอยู่ แทนการใช้ API key ซึ่งมีประโยชน์เมื่อคุณสามารถเข้าถึงบริการผ่านเว็บไซต์อยู่แล้ว และต้องการให้ OmniRoute ใช้เซสชันที่ผ่านการยืนยันตัวตนเดียวกัน

ผู้ให้บริการ Web Cookie แตกต่างจากผู้ให้บริการที่ใช้ API key ตรงที่ใช้ข้อมูลรับรองที่เบราว์เซอร์ของคุณส่งไปยังเว็บไซต์เพื่อยืนยันตัวตน

# ก่อนเริ่มต้น

> **สำคัญ:** คัดลอกข้อมูลรับรองจาก **คำขอเครือข่ายที่กำลังใช้งานอยู่** เสมอ และ **อย่า** คัดลอกจากพื้นที่จัดเก็บคุกกี้ของเบราว์เซอร์

ปัญหาการยืนยันตัวตนจำนวนมากเกิดจากการคัดลอกคุกกี้จากตำแหน่งที่ไม่ถูกต้อง

## อย่าคัดลอกจากพื้นที่จัดเก็บคุกกี้

เบราว์เซอร์ส่วนใหญ่แสดงคุกกี้ที่จัดเก็บไว้ผ่าน:

```
DevTools
→ Application (หรือ Storage)
→ Cookies
```

แม้ว่าคุกกี้เหล่านี้จะดูถูกต้อง แต่อาจมีลักษณะดังนี้:

- ล้าสมัย
- ไม่ครบถ้วน
- ไม่มีคุกกี้ที่ส่งเฉพาะเมื่อมีคำขอที่ผ่านการยืนยันตัวตน

การใช้ค่าเหล่านี้อาจทำให้การยืนยันตัวตนล้มเหลว แม้ว่าค่าดังกล่าวจะดูเหมือนถูกต้องก็ตาม

## คัดลอกจากคำขอที่กำลังใช้งานอยู่

ให้ใช้คุกกี้จากคำขอที่สำเร็จแทน:

```
DevTools
→ Network
→ รีเฟรชหน้า
→ เปิดคำขอแชทหรือการสนทนา
→ Request Headers
→ Cookie
```

ส่วนหัวคำขอ `Cookie` มีข้อมูลการยืนยันตัวตนที่ถูกต้องตรงกับข้อมูลที่เบราว์เซอร์ของคุณใช้สำเร็จ

สำหรับผู้ให้บริการ Web Cookie ส่วนใหญ่ ค่านี้คือค่าที่ควรวางลงใน OmniRoute

# การตั้งค่าทั่วไป

กระบวนการตั้งค่าจะเหมือนกันสำหรับผู้ให้บริการ Web Cookie ส่วนใหญ่

1. ลงชื่อเข้าใช้เว็บไซต์ของผู้ให้บริการ
2. เปิด Developer Tools ของเบราว์เซอร์
3. เปิดแท็บ **Network**
4. รีเฟรชหน้า
5. เปิดคำขอแชทหรือการสนทนาที่ผ่านการยืนยันตัวตน
6. คัดลอกข้อมูลรับรองการยืนยันตัวตนที่จำเป็น
7. เปิด OmniRoute
8. ไปที่ **Providers → Add Provider**
9. เลือกผู้ให้บริการ Web Cookie ของคุณ
10. วางข้อมูลรับรอง
11. คลิก **Test Connection**
12. บันทึกผู้ให้บริการ

ข้อมูลรับรองที่จำเป็นจะแตกต่างกันไปตามผู้ให้บริการ

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) เป็นแพลตฟอร์มแชตสำหรับผู้ใช้งานทั่วไปที่ใช้งานได้ฟรีโดยไม่ต้องสมัครบัญชี โดยระบบจะสร้างเซสชันแบบไม่ระบุตัวตนเมื่อเข้าชมครั้งแรก และคงเซสชันไว้ผ่านคุกกี้สามรายการ ได้แก่ `uid`, `si_usr_id` และ `si_ses_id` OmniRoute ทำหน้าที่พร็อกซีเอนด์พอยต์ `/api/dispatch` เดียวกันผ่านรหัสโมเดลเดียว (`notrack-c` โดยมีชื่อแทนว่า `ntw`)

### ขั้นตอนการเชื่อมต่อ

1. เปิด [notrack.ai](https://notrack.ai) ในเบราว์เซอร์ และปล่อยให้ระบบตั้งค่าคุกกี้ของเซสชันแบบไม่ระบุตัวตน
2. เปิด **เครื่องมือสำหรับนักพัฒนา → เครือข่าย** รีเฟรชหน้า แล้วคลิกคำขอ `/api` รายการใดก็ได้
3. ใน **ส่วนหัวของคำขอ** ให้คัดลอกค่าทั้งหมดของส่วนหัว `Cookie`
4. ใน OmniRoute ให้ไปที่ **ผู้ให้บริการ → เพิ่มผู้ให้บริการ → NoTrack Web (ฟรี)**
5. วางสตริงคุกกี้ลงในฟิลด์ `apiKey` แล้วกด **บันทึก**

OmniRoute จะแยก `uid`, `si_usr_id` และ `si_ses_id` ออกจากสตริงที่วาง แล้วสร้างส่วนหัว `Cookie` ใหม่ที่เรียบร้อยโดยมีเฉพาะคู่ค่าเหล่านั้น รวมถึง `nt_session` (โทเค็น `ntk_…` ที่กำหนดไว้สำหรับบัญชีที่เข้าสู่ระบบ) หากมีอยู่ หากค่าใดค่าหนึ่งในสามรายการขาดหายไป ระบบจะส่งต่อสตริงดิบที่วางไว้โดยไม่เปลี่ยนแปลง เพื่อให้ผู้ดูแลระบบสามารถทดลองใช้รูปแบบอื่นได้

### รหัสโมเดล

| รหัสโมเดล   | ชื่อที่แสดง | หมายเหตุ                                            |
| ----------- | ----------- | --------------------------------------------------- |
| `notrack-c` | NoTrack C   | ค่าเริ่มต้น — โมเดลการส่งต่อคำขอต้นทาง `C`          |
| `C`         | NoTrack C   | ชื่อแทนของ `notrack-c` (รหัสการส่งต่อคำขอต้นทางดิบ) |
| `notrack`   | NoTrack C   | ชื่อแทนของ `notrack-c`                              |
| `ntw`       | NoTrack C   | ชื่อแทนแบบสั้นของ `notrack-c`                       |

รหัสโมเดลทั้งสี่รายการจะเชื่อมโยงไปยังโมเดลการส่งต่อคำขอต้นทางเดียวกัน (`C`)

### ตัวเลือกของคำขอ

ตัวดำเนินการรองรับฟิลด์ทางเลือกต่อไปนี้ในเนื้อหาคำขอ:

| ฟิลด์ในเนื้อหา        | ค่าเริ่มต้น | วัตถุประสงค์                                                        |
| --------------------- | ----------- | ------------------------------------------------------------------- |
| `notrack_mode`        | `usual`     | โหมดการส่งต่อคำขอ (สตริงรูปแบบอิสระ โดยระบบต้นทางรองรับ `usual`, …) |
| `notrack_max_turns`   | `6`         | จำนวนรอบการทำงานภายในที่ระบบต้นทางอาจใช้ก่อนตอบกลับ                 |
| `notrack_chat_id`     | `null`      | ดำเนินแชตต้นทางที่มีอยู่ต่อ (ไม่ต้องระบุหากต้องการเริ่มแชตใหม่)     |
| `notrack_attachments` | `[]`        | อาร์เรย์ตัวอธิบายไฟล์แนบของระบบต้นทางที่ส่งผ่านโดยตรง               |
| `notrack_regenerate`  | `false`     | ตั้งเป็น `true` เพื่อขอให้สร้างคำตอบใหม่สำหรับรอบก่อนหน้า           |

### ความสามารถ

- การสร้างคำตอบแชตแบบ **สตรีมและไม่สตรีม**
- **การเรียกใช้เครื่องมือ** — กำหนด `tools: [...]` ในคำขอ ตัวดำเนินการจะจัดรูปแบบข้อมูลเหล่านั้นเป็นสัญญาเอนเวโลปสำหรับการเรียกใช้เครื่องมือ และแปลงการตอบกลับของโมเดลกลับเป็น `tool_calls` ของ OpenAI
- **`response_format`** — รองรับ `json_object` และ `json_schema` ตัวดำเนินการจะแยกออบเจ็กต์ JSON แรกจากคำตอบของโมเดล แล้วแปลงเป็นสตริงก่อนส่งกลับ
- **คำใบ้การให้เหตุผล** — ตัวดำเนินการจะส่งเดลตา `reasoning` เมื่อระบบต้นทางส่งเหตุการณ์ `thinking`

### ข้อจำกัด

- ระบบต้นทางบังคับใช้โควตาการใช้งานแบบไม่ระบุตัวตน เมื่อถึงขีดจำกัด ตัวดำเนินการจะแสดงข้อผิดพลาด 429 พร้อมข้อความที่เข้าใจง่าย
- รหัสโมเดลทั้งหมดจะถูกเชื่อมโยงไปยังโมเดลการส่งต่อคำขอต้นทางเดียวกัน โดยไม่สามารถสลับแยกตามแต่ละโมเดลได้
- ตัวดำเนินการจะไม่เรียกเอนด์พอยต์ `/api/chats` ของระบบต้นทาง ดังนั้นประวัติแชต / เซสชันจะไม่ได้รับการจัดการโดยอัตโนมัติ ใช้ `notrack_chat_id` เพื่อดำเนินแชตต้นทางที่มีอยู่ต่อ

# สิ่งที่ผู้ให้บริการ Web Cookie ทำได้และทำไม่ได้

ผู้ให้บริการ Web Cookie นำอินเทอร์เฟซแชตของเว็บไซต์กลับมาใช้ใหม่ โดย **ไม่ได้** มีความสามารถเทียบเท่ากับ API อย่างเป็นทางการ

## รองรับ

- ยืนยันตัวตนโดยใช้เซสชันเบราว์เซอร์ที่มีอยู่
- เข้าถึงโมเดลที่พร้อมใช้งานผ่านบัญชีของคุณ
- สตรีมการตอบกลับของแชต
- ไม่ต้องใช้ API key

## ไม่รองรับ

- การเรียกใช้ฟังก์ชัน
- การเรียกใช้เครื่องมือ
- การแก้ไขไฟล์โดยอัตโนมัติ
- เวิร์กโฟลว์ IDE แบบเอเจนต์
- ฟีเจอร์ที่ใช้ได้เฉพาะ API

ลักษณะการทำงานนี้เป็นไปตามที่คาดไว้และ **ไม่ใช่** บั๊ก

หากคุณต้องการเรียกใช้เครื่องมือ แก้ไขไฟล์โดยอัตโนมัติ หรือใช้เวิร์กโฟลว์เอเจนต์อื่นๆ ให้ใช้ **ผู้ให้บริการแบบ API key** แทนผู้ให้บริการแบบ Web Cookie

---

# ข้อควรทราบเกี่ยวกับการตรวจสอบความถูกต้อง

การ **Test Connection** หรือการตรวจสอบคุกกี้สำเร็จ เป็นเพียงการยืนยันว่าข้อมูลรับรองที่ให้มาดูเหมือนจะอยู่ในรูปแบบที่ถูกต้อง

จนกว่า Issue #7857 จะได้รับการแก้ไข การตรวจสอบความถูกต้องที่สำเร็จ **ไม่ได้รับประกัน** ว่าผู้ให้บริการจะสามารถยืนยันตัวตนได้สำเร็จ

หากการยืนยันตัวตนยังคงล้มเหลว ให้ตรวจสอบว่าคุณคัดลอกข้อมูลรับรองจากคำขอเครือข่ายที่กำลังใช้งานอยู่ ไม่ใช่จากพื้นที่จัดเก็บคุกกี้ของเบราว์เซอร์

---

# การแก้ไขปัญหา

## การยืนยันตัวตนล้มเหลว

ตรวจสอบว่าคัดลอกข้อมูลรับรองมาจาก:

```
Network
→ Request Headers
→ Cookie
```

และ **ไม่ใช่** จาก:

```
Application
→ Cookies
```

---

## คุกกี้ใช้ได้ในเบราว์เซอร์ แต่ใช้ไม่ได้ใน OmniRoute

ผู้ให้บริการบางรายมีคุกกี้ที่จะถูกส่งเฉพาะระหว่างคำขอที่ผ่านการยืนยันตัวตนแล้วเท่านั้น

คัดลอกข้อมูลรับรองอีกครั้งจากคำขอเครือข่ายใหม่ หลังจากเปิดการสนทนาได้สำเร็จแล้ว

---

## เซสชันหมดอายุ

ผู้ให้บริการแบบ Web Cookie ใช้เซสชันเบราว์เซอร์ที่มีอยู่ของคุณ

หากเซสชันเบราว์เซอร์หมดอายุหรือคุณออกจากระบบ คุณต้องคัดลอกข้อมูลรับรองชุดใหม่ หากต้องการให้การต่ออายุคุกกี้สำหรับผู้ให้บริการเว็บที่รองรับเป็นไปโดยอัตโนมัติ โปรดดูเครื่องมือเสริม [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md)

---

## Test Connection ผ่าน แต่คำขอล้มเหลว

จนกว่า Issue #7857 จะได้รับการแก้ไข การผ่านการตรวจสอบความถูกต้องไม่ได้รับประกันว่าคำขอยืนยันตัวตนจะสำเร็จ

คัดลอกข้อมูลรับรองอีกครั้งจากคำขอใหม่ที่ผ่านการยืนยันตัวตนแล้ว ก่อนดำเนินการแก้ไขปัญหาเพิ่มเติม

## ChatGPT Web ล้มเหลวพร้อมข้อความ "Unsupported ChatGPT integrity dependency"

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

ข้อมูลรับรองไม่มีปัญหา — ข้อผิดพลาดนั้นมาจากบริดจ์ ไม่ใช่จากเซสชัน chatgpt.com กำหนดรหัสโมดูลใหม่ในแต่ละการปรับใช้ และก่อนหน้านี้บริดจ์จะตรึงรหัสของตัวช่วย Sentinel ที่บริดจ์สร้างขึ้น ดังนั้นเมื่อมีการสร้าง chatgpt.com รุ่นใหม่ซึ่งเปลี่ยนชื่อตัวช่วย ทุกคำขอจึงใช้งานไม่ได้ แม้ว่าคุกกี้จะยังคงใช้ได้ การอนุญาตการเชื่อมต่อใหม่ไม่สามารถแก้ไขปัญหานี้ได้

บิลด์ที่ค้นหาโมดูลผ่านรันไทม์ของหน้าเว็บเองจะไม่ตรึงรหัสใดๆ และไม่พบปัญหานี้ หากคุณพบข้อผิดพลาดดังกล่าว ให้อัปเกรด OmniRoute แล้วเรียกใช้การตรวจสอบการเชื่อมต่ออีกครั้ง

# ตัวอย่างผู้ให้บริการ

สำหรับคำแนะนำแบบทีละขั้นตอนที่ครบถ้วนสำหรับผู้ให้บริการรายใดรายหนึ่ง โปรดดู:

- **Claude Web** — `docs/providers/CLAUDE_WEB.md`

คู่มือ Claude Web แสดงขั้นตอนการตั้งค่าทั้งหมดสำหรับผู้ให้บริการแบบ Web Cookie และใช้เป็นตัวอย่างอ้างอิง

---

# แนวทางปฏิบัติที่ดีที่สุด

- คัดลอกข้อมูลรับรองจากคำขอใหม่ที่ผ่านการยืนยันตัวตนแล้ว
- หลีกเลี่ยงการนำคุกกี้เก่ากลับมาใช้
- รักษาเซสชันเบราว์เซอร์ให้ทำงานอยู่เสมอขณะใช้ผู้ให้บริการแบบ Web Cookie
- จัดการคุกกี้ที่คัดลอกมาเสมือนเป็นข้อมูลรับรองที่ละเอียดอ่อน
- ใช้ผู้ให้บริการแบบ API key เมื่อคุณต้องการเรียกใช้ฟังก์ชันหรือใช้เวิร์กโฟลว์เอเจนต์
