การส่งออกบันทึกการเรียกของ OmniRoute ไปยังคลังข้อมูลวิเคราะห์ภายนอกอย่างต่อเนื่องและเป็นส่วนเพิ่ม

แท็บแดชบอร์ด Logs เก็บประวัติคำขอไว้ใน SQLite (`call_logs`) ซึ่งมีขอบเขตจำกัดด้วย
การหมุนเวียนและระยะเวลาการเก็บรักษา การส่งออกบันทึกจะส่งชุดระเบียนเดียวกันออกไปตามกำหนดเวลา เพื่อให้ข้อมูลมีอายุยาวนานกว่า
ฐานข้อมูลภายในเครื่องและสามารถนำไปรวมกับข้อมูลอื่นได้ BigQuery เป็นปลายทางแรก ส่วน
ไปป์ไลน์เป็นรีจิสทรี ดังนั้นจึงสามารถเพิ่มปลายทางอื่นได้

## 1. วิธีการทำงาน

```
เซิร์ฟเวอร์ (ถอดรหัส + ตรวจสอบความถูกต้องของการกำหนดค่า, ปรับ cursor ให้สอดคล้อง)
  → เริ่ม IPC → โปรเซส exportChild ของระบบปฏิบัติการที่แยกออกมา
    → storage.sqlite แบบอ่านอย่างเดียว → การสืบค้น/แมป call-log ที่ใช้ร่วมกัน
      → เติมข้อมูลอาร์ติแฟกต์แบบอะซิงโครนัส → prepare()/send() ของปลายทาง
        → IPC แบบแบตช์ → เซิร์ฟเวอร์บันทึก cursor → IPC ตอบรับ
          → แบตช์ถัดไป; IPC แจ้งเสร็จสิ้น → เซิร์ฟเวอร์บันทึกความสำเร็จ
```

- **กำหนดการ** — งาน cron ของ `JobRegistry` หนึ่งงานชื่อ `log_export` ซึ่งมีค่าเริ่มต้นเป็น
  `0 * * * *` (ทุกชั่วโมง, UTC) ลงทะเบียนใน `src/lib/initCloudSync.ts`; สามารถแทนที่ได้ด้วย
  `OMNIROUTE_LOG_EXPORT_CRON` ในแต่ละรอบ ระบบจะระบายข้อมูลไปยังปลายทางที่ **เปิดใช้งาน**
  ทุกแห่งตามลำดับ
- **Cursor** — ใช้ `call_logs.rowid` โดยปริยายของ SQLite และบันทึกแยกสำหรับแต่ละปลายทางใน
  `log_export_destinations.cursor_row_id` จงใจไม่ใช้ `timestamp` เป็น cursor เนื่องจากผู้เรียก
  อาจระบุค่าของตนเองได้ ดังนั้นคำขอที่ทำงานช้าอาจถูกเขียนหลังคำขอที่ทำงานเร็วกว่าแต่เริ่มต้น
  ภายหลัง และ cursor แบบ timestamp จะข้ามรายการนั้น
- **การแบ่งแบตช์** — ส่ง `batch_size` แถวต่อคำขอ (ค่าเริ่มต้น 500) และไม่เกิน
  `max_rows_per_run` แถวต่อการทำงานหนึ่งรอบ (ค่าเริ่มต้น 10000) เพื่อให้ข้อมูลค้างจำนวนมาก
  ถูกระบายตลอดหลายรอบ แทนที่จะขัดขวางการทำงานในรอบเดียว
- **การส่งมอบ** — cursor จะเลื่อนไปข้างหน้าหลังจาก `send()` สำเร็จแล้วเท่านั้น แบตช์ที่ล้มเหลว
  จะปล่อย cursor ไว้ที่เดิม เพื่อให้ลองส่งแถวเดิมอีกครั้งในการทำงานรอบถัดไป การรับประกันเป็นแบบ
  อย่างน้อยหนึ่งครั้งร่วมกับการขจัดข้อมูลซ้ำที่ฝั่งปลายทาง ไม่ใช่ exactly-once อย่างแท้จริง:
  BigQuery กำหนดคีย์แต่ละแถวด้วย id ของ call-log ซึ่งจะนำไปใช้แบบ best-effort ภายในช่วงเวลา
  การขจัดข้อมูลซ้ำของ BigQuery เอง
- **ตัวป้องกันการทำงานซ้อนกัน** — รอบ cron และ `POST .../run` อาจเริ่มพร้อมกัน ปลายทางที่
  กำลังระบายข้อมูลอยู่แล้วจะถูกข้ามแทนที่จะระบายซ้ำสองครั้ง (`skipped: true` ในผลลัพธ์ของ
  การทำงาน) ดังนั้นการทำงานพร้อมกันจึงไม่สามารถส่งแบตช์ซ้ำหรือเขียน cursor ย้อนกลับได้
- **การกู้คืนหลังการล้างข้อมูล** — หาก `cursor_row_id` มีค่ามากกว่า `MAX(rowid)` (ตารางทั้งหมด
  ถูกล้างและ rowid เริ่มต้นใหม่) runner จะย้อนกลับไปที่ 0 แทนที่จะมองไม่เห็นข้อมูลอย่างถาวร

### Runner แบบแยกส่วนและขีดจำกัด

การทำงานของแต่ละปลายทางบน Node จะเริ่มโปรเซสลูกของระบบปฏิบัติการที่แยกออกมาและมีอายุสั้น
(`child_process` พร้อม IPC ไม่ใช่ `worker_threads`) การอ่านเนื้อหา การแยกวิเคราะห์/ซีเรียลไลซ์
payload JSON, `prepare()` ของปลายทาง และ I/O เครือข่ายของปลายทาง ล้วนทำงานในโปรเซสนั้น
ไม่ใช่บน event loop ของเซิร์ฟเวอร์ มีเพียงการกำหนดค่าและข้อความความคืบหน้าขนาดเล็กที่ส่งผ่าน
IPC; ระเบียนที่ส่งออกจะไม่ย้อนกลับมายังเซิร์ฟเวอร์ งาน cron และ route เรียกใช้ทันทีจะยังคงใช้
ผลลัพธ์สาธารณะและตัวป้องกันการทำงานซ้อนกันแบบเดิม

โปรเซสลูกจะเปิด `DATA_DIR/storage.sqlite` ที่เซิร์ฟเวอร์ resolve แล้วในโหมดอ่านอย่างเดียวโดยใช้
`node:sqlite` พร้อม `busy_timeout=5000` และ `query_only=ON` โดยจะไม่นำเข้า DB singleton
และไม่ดำเนินการ migration, backup หรืออัปเดต SQLite การติดตามอาร์ติแฟกต์ที่สูญหาย/เสียหาย
(รวมถึง UPDATE สำหรับอาร์ติแฟกต์ที่เสียหาย) จะยังคงอยู่เฉพาะในเส้นทางรายละเอียดของแดชบอร์ด
ทั้งสองเส้นทางใช้ตัว resolve รายละเอียดแบบ pure ร่วมกัน; การส่งออกใช้การอ่านระบบไฟล์แบบ
อะซิงโครนัสและลำดับการ resolve เดียวกันคือ อาร์ติแฟกต์ → inline แบบเดิม → ดิสก์แบบเดิม →
ไม่มีข้อมูล การทำงานหนึ่งรอบจะบันทึก snapshot ของ rowid การแทรกสูงสุดเมื่อโปรเซสลูกเปิด
reader; ข้อมูลที่แทรกภายหลังจะรอจนถึงรอบถัดไป นี่เป็นขอบเขตการแทรก ไม่ใช่ transaction
SQLite ที่มีอายุยาวนาน: writer และ checkpoint ของ WAL ยังคงทำงานได้อย่างอิสระระหว่างรอ
เครือข่าย การอัปเดต/ลบแถวที่มีอยู่จะไม่ถูกตรึงด้วยขอบเขตนี้

หลังจากแต่ละแบตช์ได้รับการยอมรับ โปรเซสลูกจะรอการตอบรับ เซิร์ฟเวอร์จะบันทึก cursor ด้วย
`advanceLogExportCursor` ก่อน แล้วจึงส่ง `ack`; แบตช์ถัดไปจะไม่เริ่มทำงานก่อนหน้านั้น
ความล้มเหลวในการส่ง โปรเซสล่ม หรือหมดเวลา จะบันทึกเป็นความล้มเหลวโดยไม่เลื่อน cursor ของ
แบตช์นั้น แบตช์ที่ได้รับการตอบรับก่อนหน้านี้จะยังคงถูก commit; มีเพียงแบตช์ที่ยังไม่ได้รับ
การตอบรับไม่เกินหนึ่งแบตช์เท่านั้นที่อาจถูกส่งซ้ำ ระบบจะบันทึกความสำเร็จหลังจากได้รับ `done`
และโปรเซสลูกจบการทำงานอย่างสมบูรณ์เท่านั้น เมื่อเกิดความล้มเหลว ระบบจะยุติโปรเซสลูกด้วย
SIGTERM และยกระดับเป็น SIGKILL หลังจาก 500 ms จากนั้น runner จะรอจนกว่าโปรเซสจะปิดลง

| ตัวแปรสภาพแวดล้อม                             | ค่าเริ่มต้น | วัตถุประสงค์                         |
| --------------------------------------------- | ----------- | ------------------------------------ |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000      | ขีดจำกัดเวลาจริงต่อปลายทาง           |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024        | ขีดจำกัด old-space ของ V8 ในหน่วย MB |

ค่าที่ไม่ถูกต้อง/ไม่เป็นจำนวนบวก/ไม่เป็นจำนวนเต็มจะใช้ค่าเริ่มต้น การตั้งค่า heap ไม่ใช่ขีดจำกัด
RSS ทั้งหมด; แบตช์ที่มีขนาดใหญ่มากยังคงอาจใช้หน่วยความจำของโปรเซสลูกจนหมดและทำให้การทำงาน
ล้มเหลวได้อย่างปลอดภัย ค่าเริ่มต้น 1024 MB จะเผื่อพื้นที่สำหรับแบตช์เริ่มต้น 500 แถวที่มี
อาร์ติแฟกต์ขนาด 512 KiB และเปิดใช้งานเนื้อหา รวมถึงการซีเรียลไลซ์ JSON แบบแบ่งเป็นส่วนตาม
จำนวนไบต์ของ BigQuery แต่ไม่ได้ทำให้แบตช์เนื้อหาขนาด 10000 แถวปลอดภัย การใช้ heap ของ V8
จนหมดจะบันทึกความล้มเหลวพร้อมแนวทางแก้ไข: ลดขนาดแบตช์หรือเพิ่ม
`OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; cursor จะยังคงอยู่ที่แบตช์ล่าสุดที่ได้รับ
การตอบรับ เนื้อหา inline/ดิสก์แบบเก่าไม่อยู่ภายใต้ขีดจำกัดอาร์ติแฟกต์สมัยใหม่ ผู้ดูแลระบบต้อง
จัดสรร RSS แยกต่างหาก โดยเฉพาะภายใน container ที่มีการจำกัดหน่วยความจำ

โปรเซสลูกจะรับช่วงต่อเฉพาะ `DATA_DIR` ที่ resolve แล้ว, `NODE_ENV`, `TZ` ที่ระบุอย่างชัดเจน
(สำหรับการ resolve เวลาท้องถิ่นของชื่อไฟล์แบบเดิม), `ELECTRON_RUN_AS_NODE` หากมีอยู่ และ
อินพุตขาออกต่อไปนี้:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (รวมถึงรูปแบบตัวพิมพ์เล็ก),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`
dispatcher ส่วนกลางของ Undici จะใช้การ resolve proxy จากสภาพแวดล้อมแบบ pure และกฎการ
ข้าม proxy สำหรับโฮสต์ภายในร่วมกับเซิร์ฟเวอร์ รวมถึง `NO_PROXY`; โดยจะไม่นำเข้า
`proxyFetch.ts` หรือ DB/feature flag ของไฟล์ดังกล่าว ข้อมูลรับรองของ proxy จะถูกปกปิดจาก
เอาต์พุตที่ส่งต่อและข้อผิดพลาดที่บันทึกไว้ ข้อมูลรับรองของปลายทางจะเดินทางผ่านข้อความ IPC
เริ่มต้นหนึ่งข้อความเท่านั้น โดยไม่ผ่าน argv หรือสภาพแวดล้อม; การส่งต่อเอาต์พุต/ข้อผิดพลาด
จะมีคำนำหน้าและผ่านการล้างข้อมูล มีเพียง `ExperimentalWarning` เท่านั้นที่ถูกปิดใช้งานใน
อาร์กิวเมนต์การเรียกโปรเซสลูก เพื่อหลีกเลี่ยงการแสดงคำเตือน SQLite ของ Node ซ้ำในทุกการทำงาน
ของ cron; คำเตือนประเภทอื่นจะยังคงมองเห็นได้

โมดูลปลายทางต้องสามารถนำเข้าได้โดยไม่ต้องพึ่งพา Next.js หรือการอ้างอิงที่ใช้ได้เฉพาะฝั่งเซิร์ฟเวอร์ การใช้งาน
BigQuery ที่มีอยู่เป็นไปตามข้อกำหนดนี้แล้ว แคชโทเค็นการเข้าถึงจะคงอยู่เฉพาะตลอดการทำงานของโปรเซสลูก
แต่ละครั้ง ไม่ได้คงอยู่ข้ามการทำงาน Node คือรันไทม์ที่รองรับ (`package.json` engines) แต่ส่วนการติดตั้ง Bun
ใน README และ `Dockerfile.bun` ยังระบุเส้นทางความเข้ากันได้สำหรับการใช้งานจริงโดยใช้
`bun:sqlite` (`src/lib/db/core.ts` / อะแดปเตอร์) ดังนั้นภายใต้ Bun การส่งออกจะยังคงใช้เส้นทาง
ภายในโปรเซสแบบเดิมและแสดงคำเตือนหนึ่งครั้งว่า ไม่สามารถใช้การแยก heap/timeout ของโปรเซสลูกได้ โปรดใช้
Node เพื่อแยก event loop และ OOM ส่วน Bun ไม่ได้ถูกถือว่าใช้เฉพาะสำหรับการพัฒนาในที่นี้

เมื่อเปิดใช้งาน `includeBodies` ควรเลือกความถี่ระดับนาที เช่น
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` แทนการสะสมเพย์โหลดค้างไว้เป็นรายชั่วโมง
ขีดจำกัดแบตช์และแถวยังคงจำกัดการทำงานแต่ละครั้ง การเริ่มต้นโปรเซสมีต้นทุนต่อปลายทางต่อการทำงานหนึ่งครั้ง
นี่คือการยอมแลกต้นทุนเริ่มต้นเพียงเล็กน้อยเพื่อแยก event loop ของเซิร์ฟเวอร์ ไม่ใช่เพื่อลดการใช้ CPU โดยรวม

### เพย์โหลด (พรอมต์และคำตอบ)

โดยค่าเริ่มต้น การส่งออกจะมีเฉพาะฟิลด์สรุปที่หน้า **รายการ** ของ Logs แสดง การเปิด
**ส่งออกพรอมต์และคำตอบ** (`includeBodies`) จะส่งข้อมูลที่แผง **รายละเอียด**
ของ Logs แสดงสำหรับแต่ละคำขอเพิ่มเติมด้วย:

| ฟิลด์                            | ข้อมูลที่จัดเก็บ                                         |
| -------------------------------- | -------------------------------------------------------- |
| `request_body` / `response_body` | เพย์โหลดของคำขอตามที่แดชบอร์ดแสดงผล                      |
| `pipeline_route_decision`        | เป้าหมายและโมเดลที่เราเตอร์เลือก                         |
| `pipeline_client_request`        | คำขอดิบตามที่ไคลเอนต์ส่งมาทุกประการ                      |
| `pipeline_openai_request`        | หลังจากแปลงเป็นรูปแบบ OpenAI ภายในแล้ว                   |
| `pipeline_provider_request`      | ข้อมูลที่ส่งไปยังต้นทางจริงในรูปแบบภาษาของผู้ให้บริการ   |
| `pipeline_provider_response`     | การตอบกลับดิบจากต้นทาง                                   |
| `pipeline_client_response`       | ข้อมูลที่ส่งกลับไปยังผู้เรียก                            |
| `pipeline_error`                 | รายละเอียดข้อผิดพลาดระดับไปป์ไลน์สำหรับคำขอที่ล้มเหลว    |
| `bodies_truncated`               | เป็นจริงเมื่อฟิลด์ใดก็ตามข้างต้นมีขนาดถึง `maxBodyBytes` |

นี่คือเนื้อหาพรอมต์ จึง **ปิดไว้โดยค่าเริ่มต้น** และตั้งใจให้เลือกแยกสำหรับแต่ละปลายทาง
ข้อมูลที่ส่งออกคือสิ่งที่แดชบอร์ดแสดง เนื่องจากการส่งออกและ `getCallLogById` ใช้กระบวนการดึง
รายละเอียดร่วมกัน: เพย์โหลดได้รับการลบข้อมูลระบุตัวบุคคล (PII) และปกปิดข้อมูลลับแล้ว
เมื่อมีการเขียนข้อมูล และคำขอที่ใช้คีย์ API แบบ `noLog` จะไม่จัดเก็บเพย์โหลดใดๆ เลย
ดังนั้นจึงไม่มีข้อมูลให้ส่งออก

เพย์โหลดจะถูกอ่านแยกทีละแถวจากอาร์ติแฟกต์ในระบบไฟล์ ดังนั้นกระบวนการเติมข้อมูลจึงทำงาน
เฉพาะกับปลายทางที่ร้องขอเท่านั้น หากอาร์ติแฟกต์สูญหายหรือเสียหาย ระบบจะส่งออกข้อมูลสรุป
พร้อมเพย์โหลดที่เป็น null แทนที่จะทำให้ทั้งแบตช์ล้มเหลวและเคอร์เซอร์ค้างอยู่

`maxBodyBytes` (ค่าเริ่มต้น 262144) จำกัดขนาดของแต่ละฟิลด์ เพย์โหลดที่ยาวกว่านี้จะถูก
**ตัดทอนแทนที่จะทิ้ง** — พรอมต์ที่ถูกตัดยังคงตอบคำถามว่า "มีการถามอะไร" ได้ — และแถวจะถูกทำเครื่องหมายด้วย
`bodies_truncated` ระบบจะไม่ส่งออกเดลตาที่สตรีมมาทีละส่วน โดยคำตอบที่ประกอบเสร็จแล้วมีอยู่ใน
`pipeline_provider_response` และ `pipeline_client_response` อยู่แล้ว

## 3. REST API

ทุกเส้นทางผ่านการยืนยันตัวตนสำหรับการจัดการ (`requireManagementAuth`) ระบบจะไม่ส่งคืนข้อมูลลับ:
ข้อมูลลับที่จัดเก็บไว้จะถูกส่งกลับเป็นค่าตรงตัว `__stored__` และการส่งค่านี้กลับมาในการอัปเดต
จะคงข้อมูลรับรองที่จัดเก็บไว้เดิม

การสร้างหรืออัปเดตปลายทางที่ชนิดของปลายทางระบุว่ามีข้อมูลลับ **จำเป็นต้องมี
`STORAGE_ENCRYPTION_KEY`** หากไม่มี `encrypt()` จะส่งค่าผ่านโดยไม่มีการแจ้งเตือน ดังนั้นระบบจึง
ปฏิเสธการเขียนด้วยสถานะ 400 แทนที่จะบันทึกข้อมูลรับรองลงใน SQLite เป็นข้อความธรรมดา (ใช้การป้องกันแบบเดียวกับ
เว็บฮุก Telegram)

| เมธอด    | พาธ                                      | วัตถุประสงค์                                                  |
| -------- | ---------------------------------------- | ------------------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | ชนิดของปลายทาง + รายการฟิลด์การกำหนดค่าของแต่ละชนิด           |
| `GET`    | `/api/log-export/destinations`           | แสดงรายการปลายทาง (ปกปิดข้อมูลลับ)                            |
| `POST`   | `/api/log-export/destinations`           | สร้างปลายทาง                                                  |
| `GET`    | `/api/log-export/destinations/{id}`      | อ่านข้อมูลหนึ่งรายการ                                         |
| `PUT`    | `/api/log-export/destinations/{id}`      | อัปเดตชื่อ / สถานะเปิดใช้งาน / การกำหนดค่า / การจัดชุดข้อมูล  |
| `DELETE` | `/api/log-export/destinations/{id}`      | ลบ                                                            |

ตัวอธิบายฟิลด์ที่ส่งกลับมา ดังนั้นปลายทางใหม่จึงไม่ต้องแก้ไข UI

## 4. ปลายทาง BigQuery

คีย์การกำหนดค่า (`type: "bigquery"`):

| คีย์                 | หมายเหตุ                                                       |
| -------------------- | -------------------------------------------------------------- |
| `projectId`          | โปรเจกต์ GCP ที่มีชุดข้อมูลอยู่                                |
| `datasetId`          | `[A-Za-z0-9_]+`                                                |
| `tableId`            | `[A-Za-z0-9_]+`                                                |
| `location`           | ใช้เฉพาะเมื่อต้องสร้างชุดข้อมูล (ค่าเริ่มต้น `EU`)             |
| `serviceAccountJson` | คีย์บัญชีบริการ ข้อมูลลับ: เข้ารหัสขณะจัดเก็บและไม่ส่งคืน      |
| `autoCreate`         | สร้างชุดข้อมูลและตารางในการส่งออกครั้งแรก (ค่าเริ่มต้น `true`) |

บัญชีบริการต้องมีสิทธิ์ `bigquery.tables.updateData` บนตารางเป้าหมาย รวมถึง
`bigquery.datasets.create` / `bigquery.tables.create` เมื่อเปิด `autoCreate`

ชุดข้อมูลที่กำหนดค่าไว้เป็นหน่วยของ **เคอร์เซอร์** ไม่ใช่หน่วย HTTP: `send()` จะแบ่งชุดข้อมูลออกเป็นการเรียก insertAll
ครั้งละไม่เกิน 500 แถว ดังนั้น `batch_size` ขนาดใหญ่จึงไม่ทำให้เกินขีดจำกัดคำขอ 10 MB ของ BigQuery
สถานะชั่วคราว (408/429/500/502/503/504) จะถูกลองใหม่สูงสุดสามครั้งด้วยการหน่วงเวลาแบบเอ็กซ์โพเนนเชียล
โดยใช้ insertIds เดิมซ้ำ ส่วนข้อผิดพลาดด้านการยืนยันตัวตนและสคีมาจะ throw ตั้งแต่ครั้งแรก แทนที่จะ
ใช้รอบการทำงานไปโดยเปล่าประโยชน์

ตารางที่เพิ่งสร้างเมื่อไม่กี่วินาทีก่อนยังไม่ปรากฏต่อเอนด์พอยต์สตรีมมิง ซึ่งจะตอบกลับ
404 เป็นเวลาสองสามวินาที ระบบจะลองใหม่เมื่อได้รับ 404 แต่ **เฉพาะเมื่อการทำงานรอบนี้เป็นผู้สร้างตาราง** เท่านั้น —
ตารางที่ไม่มีอยู่จริงจะยังคงล้มเหลวทันที โปรดทราบว่าการสร้างตารางใหม่โดยใช้ชื่อที่เพิ่งถูกลบไป
จะทำให้ BigQuery ปฏิเสธการแทรกข้อมูลแบบสตรีมมิงเป็นเวลาหลายนาที ซึ่งเป็นคุณสมบัติของการลบแล้วสร้างใหม่
ดังนั้นควรใช้ชื่อตารางใหม่แทนการลบแล้วเพิ่มตารางเดิมกลับเข้ามา

**ความล้มเหลวบางส่วนจะมาในรูปแบบ HTTP 200 พร้อม `insertErrors[]` ที่ไม่ว่างเปล่า** ระบบจะถือว่า
นี่เป็นความล้มเหลวและ throw ซึ่งจะหยุดไม่ให้เคอร์เซอร์เลื่อนผ่านแถวที่ BigQuery ไม่เคย
ยอมรับ โดย `tests/unit/log-export-bigquery.test.ts` จะตรึงพฤติกรรมนี้ไว้

การรับส่งข้อมูลใช้ REST โดยตรง — assertion แบบ RS256 ที่ลงนามด้วยตนเองจะถูกแลกเป็นโทเค็นการเข้าถึงที่
`https://oauth2.googleapis.com/token` จากนั้นแถวข้อมูลจะถูกส่งไปยัง `tabledata.insertAll` ไม่มีการดึง
Google SDK เข้ามาใช้ โทเค็นการเข้าถึงจะถูกแคชภายในโปรเซสแยกตามคู่ (บัญชีบริการ, ขอบเขต)

ตารางที่สร้างขึ้นจะมีหนึ่งคอลัมน์ต่อหนึ่งฟิลด์ในแท็บ Logs รวมถึง `exported_at` และถูกจัดวางให้เหมาะกับ
รูปแบบการคิวรีบันทึกการเรียกใช้งานจริง:

- **แบ่งพาร์ทิชันรายวันตาม `timestamp`** ดังนั้นคิวรีที่จำกัดขอบเขตด้วยวันที่จะสแกนเฉพาะวันเหล่านั้น
- **คลัสเตอร์ตาม `api_key_name`, `provider`, `model`, `status`** (ตามลำดับนี้) ดังนั้นการกรองตาม
  ผู้ที่เรียกใช้ ปลายทางที่ส่งไป หรือสถานะว่าล้มเหลวหรือไม่ จะช่วยตัดบล็อกภายในแต่ละพาร์ทิชันออก BigQuery
  อนุญาตคอลัมน์คลัสเตอร์ได้สูงสุดสี่คอลัมน์และลำดับมีความสำคัญ: การกรองเฉพาะ `api_key_name`
  ช่วยตัดบล็อกได้ แต่การกรองเฉพาะ `status` ทำไม่ได้
- **การเก็บรักษาพาร์ทิชันแบบเลือกได้** ผ่าน `partitionExpirationDays` (0 หมายถึงเก็บทุกอย่างไว้) ซึ่งจะถูกนำไปใช้
  เมื่อสร้างตาราง

การตั้งค่าทั้งสองมีผลในขณะสร้าง ตารางที่มีอยู่แล้วจะคงรูปแบบเดิมไว้ ดังนั้น
หากต้องการใช้การตั้งค่าเหล่านี้ ให้กำหนดปลายทางไปยัง id ของตารางใหม่

`tests/unit/log-export-bigquery.test.ts` ตรวจสอบว่า mapper และสคีมาของตารางสอดคล้องกันอยู่เสมอ
ดังนั้นคอลัมน์ call-log ใหม่จะไม่ถูกละทิ้งโดยไม่มีการแจ้งเตือนระหว่างการส่งออก

แบตช์จะถูกแบ่งเป็นส่วนย่อยตาม **ทั้ง** จำนวนแถวและจำนวนไบต์หลังการแปลงเป็นข้อมูลแบบลำดับ จำนวนแถวเพียงอย่างเดียวนั้นไม่เพียงพอ
เมื่อมีการส่งออก payload: 500 แถวที่มี prompt อาจมีขนาดหลายสิบเมกะไบต์ และ insertAll
จะปฏิเสธคำขอที่มีขนาดเกิน 10 MB แต่ละส่วนย่อยจะสิ้นสุดเมื่อครบ 500 แถวหรือมีขนาดถึง 9 MB แล้วแต่ว่าเงื่อนไขใดจะเกิดขึ้นก่อน

## 5. ปลายทางเทรซ OTLP/HTTP

การกำหนดค่าใช้ `type: "otlp-http"` นี่คือการส่งออกบันทึกการเรียกใช้ที่จัดเก็บไว้ตามกำหนดเวลา
โดยใช้เคอร์เซอร์ ไม่ใช่ปลายทางรับเหตุการณ์การกำหนดเส้นทางแบบสดที่ทำงานตามความพยายามที่ดีที่สุดใน
`open-sse/services/routing/otel.ts` โดยจะไม่อ่านหรือเปลี่ยนตัวแปรสภาพแวดล้อม
ตัวจับเวลา หรือบัฟเฟอร์ของปลายทางรับนั้น การเปิดใช้งานทั้งสองอย่างอาจสร้าง span สองประเภทที่เป็นอิสระต่อกัน;
ใช้ขอบเขต instrumentation `omniroute.log-export` เพื่อแยกแยะ span ของบันทึกการเรียกใช้เหล่านี้

| คีย์                     | ค่าเริ่มต้น / วัตถุประสงค์                                                        |
| ------------------------ | --------------------------------------------------------------------------------- |
| `endpoint`               | ต้องระบุ URL เทรซ HTTP(S) แบบเต็ม; จะไม่มีการต่อท้ายด้วย `/v1/traces`             |
| `headers`                | บรรทัด `Name: value` หรือออบเจ็กต์ JSON ของสตริงที่ระบุได้ตามต้องการ; เข้ารหัสไว้ |
| `requestHeaderAllowlist` | ว่าง (ปิด); ชื่อ/คำนำหน้าของเฮดเดอร์ไคลเอนต์ที่จะบันทึกเป็นแอตทริบิวต์ของ span    |
| `serviceName`            | `omniroute`; ทรัพยากร `service.name`                                              |
| `langfuseMapping`        | `false`; เพิ่มแอตทริบิวต์ generation/session/user ของ Langfuse                    |
| `identity`               | `pseudonymous`, `keyName` หรือ `none`                                             |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                           |
| `timeoutMs`              | `30000` ต่อความพยายามส่ง HTTP แต่ละครั้ง                                          |
| `environment`            | ไม่ได้ตั้งค่า; `langfuse.environment` ที่ระบุได้ตามต้องการ                        |

แดชบอร์ดทั่วไปจะแสดงฟิลด์เหล่านี้ `paths` รับอาร์เรย์ผ่าน API หรือพื้นที่ข้อความ
ที่มีพาธตรงตามที่ระบุ คั่นด้วยการขึ้นบรรทัดใหม่/จุลภาค พาธ embeddings, rerank และพาธอื่นๆ
จะถูกข้าม เว้นแต่จะอนุญาตไว้อย่างชัดเจน แถวที่ถูกข้ามยังคงทำให้เคอร์เซอร์เลื่อนไปข้างหน้า; ตัวนับ
`exported`/`exportedTotal` ของตัวรันที่มีอยู่นับแถวต้นทางที่ประมวลผลแล้ว รวมถึงแถวที่ถูกกรองออก
ไม่ใช่ span ที่ยอมรับ การกรองทำในโปรเซสลูก โดยไม่เปลี่ยนข้อตกลง IPC/เคอร์เซอร์
ของโปรเซสนั้น

การตรวจสอบ URL ใช้ตัวช่วย `parseAndValidateNonMetadataUrl` ที่ไม่ต้องใช้ฐานข้อมูลจาก
`src/shared/network/outboundUrlGuard.ts`: นโยบาย `block-metadata` ซึ่งมี
การตรวจสอบเมทาดาทา/โพรโทคอล/ข้อมูลรับรองที่ฝังอยู่โดยไม่มีเงื่อนไขเหมือนกับตัวตรวจสอบ webhook
ที่เปิดให้ใช้ URL ส่วนตัว แต่จงใจอนุญาตปลายทาง localhost/LAN โดยไม่ต้องใช้แฟล็กฟีเจอร์ส่วนกลางเพื่อแทนที่ข้อจำกัด
จึงรองรับปลายทาง Langfuse, Phoenix, Tempo และ Collector
ที่โฮสต์เอง รวมถึงปลายทาง HTTP ส่วนตัว โฮสต์เมทาดาทาของคลาวด์จะถูกบล็อกเสมอ
ระบบไม่ติดตามการเปลี่ยนเส้นทาง ดังนั้น collector จึงไม่สามารถเปลี่ยนเส้นทางข้อมูลรับรองไปยังโฮสต์อื่นได้
เช่นเดียวกับตัวป้องกัน URL แบบตรวจข้อความที่มีอยู่ ระบบนี้ไม่ได้ตรึงผลการแปลงชื่อ DNS; ให้กำหนดค่าเฉพาะ
โฮสต์ที่ผู้ดูแลควบคุมเท่านั้น ควรเลือกใช้ HTTPS เมื่อปลายทางไม่ได้อยู่บนเครือข่ายที่เชื่อถือได้

### เพย์โหลดและการส่ง

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) ส่ง
span แบบ CLIENT หนึ่งรายการต่อแถวที่อนุญาต โดยตั้งชื่อตามพาธคำขอที่ตรงกันทุกตัวอักษร การตั้งชื่อตามพาธช่วยแยกแยะ
Chat Completions, Responses และ Messages โดยไม่ฝังข้อมูลโมเดลหรือข้อมูลระบุตัวตนไว้ใน
ชื่อ span แอตทริบิวต์ของทรัพยากรประกอบด้วย `service.name` และ `service.version` ของแพ็กเกจ

ตัวบันทึกความพยายามแชทปกติ (`open-sse/handlers/chatCore/attemptLogging.ts`) เขียน
`duration = Date.now() - startTime` เมื่อเสร็จสิ้นและไม่ได้ระบุเวลาประทับ;
`saveCallLogOperation` ใน `src/lib/usage/callLogs.ts` กำหนดค่าเวลาประทับเริ่มต้นเป็นเวลาเขียน
(เวลาที่เสร็จสิ้น) ดังนั้นการส่งออกจึงตั้งเวลาสิ้นสุด = เวลาประทับของแถว และเวลาเริ่มต้น = เวลาสิ้นสุด − ระยะเวลา
(มิลลิวินาที แปลงเป็นนาโนวินาทีแบบฐานสิบ) เวลาประทับย้อนหลังที่ผู้เรียกระบุ
จะถูกเก็บไว้เป็นเวลาสิ้นสุดเช่นกัน; ไม่มีตัวแยกแยะเวลาเริ่มต้น/เวลาที่เสร็จสิ้นในแต่ละแถว
ระยะเวลาที่เป็น null จะกลายเป็นศูนย์ เวลาประทับที่ไม่ถูกต้อง/ไม่มีอยู่จะทำให้แบตช์ล้มเหลว แทนที่จะสร้าง
span ที่ให้ผลไม่แน่นอน `ttftMs` เป็น null ได้และแมปไปยัง `omniroute.ttft_ms`

แอตทริบิวต์ประกอบด้วย `gen_ai.operation.name="chat"`, ผู้ให้บริการ, โมเดลที่ร้องขอ/ตอบกลับ,
โทเค็นอินพุต/เอาต์พุต, โทเค็นการอ่านแคช/การสร้างแคช/การให้เหตุผลที่ระบุได้ตามต้องการ, สถานะ HTTP,
combo, แหล่งที่มาของแคช, แท็กเซสชัน และรหัสสหสัมพันธ์ ค่า OTLP ที่เป็นจำนวนเต็มและเวลาประทับ
เป็นสตริงฐานสิบ; สตริง บูลีน และจำนวนที่มีเศษส่วนใช้รูปแบบค่า OTLP
ดั้งเดิมของแต่ละชนิด span ที่เกิดข้อผิดพลาดมีสถานะ ERROR และข้อความสถานะที่ผ่านการล้างข้อมูลแล้ว ระเบียนมาตรฐาน
ไม่มี URL โฮสต์ต้นทาง จึงละเว้น `server.address` แทนที่จะระบุ
collector เป็นเซิร์ฟเวอร์โมเดลอย่างไม่ถูกต้อง ไม่มีการส่งออกค่าใช้จ่าย

เฉพาะ `includeBodies=true` เท่านั้นที่จะโหลดเนื้อหามาเติม เมื่อ `langfuseMapping=false`,
`gen_ai.input.messages` / `gen_ai.output.messages` จะมี JSON ของเนื้อหาคำขอ/การตอบกลับที่ผ่านการล้างข้อมูล
ตามที่ OmniRoute จัดเก็บไว้ (ปรับเป็นรูปแบบมาตรฐานเมื่อแยกวิเคราะห์ได้) ไม่ใช่อาร์เรย์
messages ตาม semconv ที่จัดโครงสร้างใหม่ เนื้อหาที่ถูกตัด/ไม่ใช่ JSON จะยังคงเป็นข้อความดิบ เมื่อ `langfuseMapping=true`,
เนื้อหาจะถูกส่งออกเป็น `langfuse.observation.input` / `langfuse.observation.output` เท่านั้น;
แอตทริบิวต์ `gen_ai.*.messages` จะถูกละเว้นเพื่อให้ส่งเนื้อหาแต่ละรายการเพียงครั้งเดียว ทั้งสองโหมด
สืบทอด `maxBodyBytes` จากกระบวนการโหลดข้อมูลมาเติมที่มีอยู่;
`omniroute.bodies_truncated=true` ระบุว่ามีการตัดเนื้อหา
ปลายทางนี้ไม่ได้เพิ่มสแนปช็อตของไปป์ไลน์หรือการอ่านอาร์ติแฟกต์ที่ยังไม่ผ่านการล้างข้อมูล;
การบันทึกเฮดเดอร์คำขอแบบเลือกเปิดใช้จะใช้สแนปช็อตไคลเอนต์ที่โหลดข้อมูลมาเติมแล้วตามที่อธิบายด้านล่าง
ใช้ความถี่ระดับนาที เช่น `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` เมื่อส่งออก
เนื้อหา แทนที่จะปล่อยให้มีงานค้างสะสมเป็นรายชั่วโมง

### เฮดเดอร์คำขอของไคลเอนต์แบบเลือกเปิดใช้

การบันทึกเฮดเดอร์ **ปิดอยู่โดยค่าเริ่มต้น** ตั้งค่า `requestHeaderAllowlist` ในการกำหนดค่าปลายทาง
และเปิดใช้งาน **ส่งออกพรอมต์และการตอบกลับ** (`includeBodies: true` ที่ปลายทาง)
รายการอนุญาตรับอาร์เรย์ผ่าน API หรือพื้นที่ข้อความที่มีชื่อคั่นด้วยการขึ้นบรรทัดใหม่/จุลภาค:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ชื่อจะจับคู่แบบตรงกันทุกตัวอักษรโดยไม่แยกตัวพิมพ์เล็กและใหญ่ เว้นแต่จะใช้ `*` เพียงตัวเดียวที่ท้ายชื่อเพื่อเลือก
คำนำหน้าชื่อส่วนหัวที่ไม่ว่าง ระบบจะปฏิเสธ `*` ที่อยู่เดี่ยว ๆ ไวลด์การ์ดที่แทรกอยู่ภายใน และชื่อส่วนหัว HTTP ที่ไม่ถูกต้อง
มีตัวเลือกได้สูงสุด 64 รายการ โดยแต่ละรายการมีชื่อ/คำนำหน้ายาวไม่เกิน 256 ไบต์ ASCII
การตั้งค่านี้แยกจาก `headers` ซึ่งใช้ยืนยันตัวตนของตัวส่งออกกับตัวรวบรวม

การเก็บข้อมูลจะอ่านเฉพาะ `pipeline_client_request` ซึ่งเติมข้อมูลจาก
`clientRawRequest` (หรือ `clientRequest` แบบเดิม) ของไปป์ไลน์แบบละเอียดที่บันทึกไว้ โดยจะไม่ใช้ส่วนหัวคำขอของผู้ให้บริการเป็นข้อมูลสำรอง
ต้องเปิดใช้งานการบันทึกไปป์ไลน์แบบละเอียดไว้ขณะบันทึกคำขอนั้น หาก
ปิดใช้งาน `includeBodies` หรือ JSON สแนปช็อตของไคลเอนต์ขาดหาย เสียหาย หรือถูกตัดทอน ระบบจะไม่ส่งออก
แอตทริบิวต์ส่วนหัว การเพิ่ม `maxBodyBytes` อาจช่วยหลีกเลี่ยงการตัดทอนสแนปช็อตขณะส่งออกได้
แต่ไม่สามารถกู้คืนรายละเอียดที่ไม่เคยบันทึกไว้ ระบบจะละเว้นสแนปช็อตที่มีขนาดเกิน 1 MiB หรือมี
รายการส่วนหัวมากกว่า 256 รายการ การส่งออกพรอมป์ต์/คำตอบที่มีอยู่จะยังคงเปิดใช้งานควบคู่กับ
การเก็บส่วนหัว รายการที่อนุญาตไม่ได้จัดเตรียมโหมดโหลดข้อมูลเฉพาะส่วนหัว

ค่าที่เลือกจะกลายเป็นอาร์เรย์สตริง OTLP ของ `http.request.header.<full lowercase header name>`
แม้จะมีสตริงเพียงค่าเดียว ตัวอย่างเช่น `X-OmniRoute-Meta-Team: example-team` จะกลายเป็น
`http.request.header.x-omniroute-meta-team` โดยมีค่า
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`
คำนำหน้าแบบเต็มจะยังคงอยู่ เนื่องจากส่วนหัวเหล่านี้เป็นส่วนหัวทั่วไป จึงไม่มีการแยกวิเคราะห์ฟิลด์ทางธุรกิจหรือ
การแปลงเป็นเมทาดาทาของ `omniroute.metadata.*` / Langfuse `langfuseMapping` ไม่เปลี่ยนความหมาย
ของส่วนหัว `User-Agent` ที่เลือกและมีค่าเดียวจะกำหนดค่าสเกลาร์มาตรฐาน
`user_agent.original` ด้วย เครื่องหมายจุลภาคภายในค่าเดียวจะไม่ถูกใช้แยกค่า ชื่อที่ต่างกันเฉพาะตัวพิมพ์เล็กและใหญ่จะถูกรวมตามลำดับ
รายการที่บันทึกไว้ หากรูปแบบใดไม่ถูกต้อง ระบบจะละเว้นส่วนหัวนั้นทั้งหมด แอตทริบิวต์จะเรียงตามชื่อที่เป็นตัวพิมพ์เล็ก

Authorization, Proxy-Authorization, Cookie, Set-Cookie, ส่วนหัวคีย์ API, ชื่อที่มี
คำบ่งชี้ auth/token/secret/password/credential และข้อมูลรับรองภายในเกตเวย์จะถูก
ยกเว้นเสมอ แม้จะถูกเลือกหรือถูกปกปิดบางส่วนในที่จัดเก็บ รูปแบบข้อมูลรับรองที่รู้จักจะใช้
ตัวตรวจจับข้อมูลรับรองร่วมกัน เครื่องหมายปกปิดข้อมูลจะถูกละเว้น ไม่ใช่ส่งออกเป็นค่าที่ปลอดภัย
ระบบยอมรับเฉพาะสตริงและอาร์เรย์สตริงที่ไม่ว่าง โดยจะไม่แปลงตัวเลขหรือออบเจ็กต์ให้เป็นสตริง
ชื่อที่ไม่ถูกต้อง คีย์โพรโทไทป์ อักขระควบคุม (ยกเว้นแท็บแนวนอน) และ Unicode ที่มีรูปแบบไม่ถูกต้อง
จะถูกละเว้นโดยไม่ทำให้ชุดข้อมูลล้มเหลวหรือแสดงเนื้อหาเหล่านั้นในข้อผิดพลาด

แต่ละสแปนจะเก็บส่วนหัวได้สูงสุด 32 รายการ ส่วนหัวละ 16 ค่า ค่าละ 4096 ไบต์ UTF-8
และรวมชื่อกับค่าของส่วนหัวที่เก็บทั้งหมดไม่เกิน 16384 ไบต์ UTF-8 ส่วนหัวที่ใหญ่เกินไปหรือไม่ถูกต้อง
จะถูกละเว้นทั้งรายการ ไม่ใช่ตัดทอน การเลือกเป็นการตัดสินใจด้านความเป็นส่วนตัวของผู้ดูแลระบบ ชื่อที่ดูปลอดภัย
อาจยังมีข้อมูลส่วนบุคคล และข้อจำกัด/ตัวตรวจจับเหล่านี้ไม่ใช่เครื่องมือล้างข้อมูลระบุตัวบุคคล (PII) สำหรับใช้งานทั่วไป

### ขีดจำกัดการส่งข้อมูล

คำขอถูกจำกัดไว้ที่ 500 สแปนและ JSON แบบ UTF-8 ขนาด 4 MiB ซึ่งรวมส่วนห่อหุ้มแล้ว
ทุกสแปนที่อนุญาตจะถูกตรวจสอบขนาดก่อนส่งคำขอแรกของชุดข้อมูลเคอร์เซอร์ หากสแปนใด
มีขนาดเกินขีดจำกัด ระบบจะไม่ส่งส่วนใดของชุดข้อมูลนั้นและจะล้มเหลวพร้อมคำแนะนำให้ลด
`maxBodyBytes` โดยจะไม่ทิ้งสแปนนั้นอย่างเงียบ ๆ การตรวจสอบล่วงหน้าจะเก็บเฉพาะการอ้างอิงระเบียนและ
จำนวนไบต์ โดยทิ้งสแปน/JSON ชั่วคราวแต่ละรายการ แล้วสร้างสแปนใหม่สำหรับกลุ่มย่อยที่จำกัดขนาด
แทนการเก็บสำเนาที่แปลงเป็นรูปแบบอนุกรมแล้วของชุดข้อมูลไว้อีกชุด HTTP 408/429/5xx ความล้มเหลวของเครือข่าย และการหมดเวลาจะได้รับการลองสูงสุด
สามครั้ง โดยเว้นระยะแบบทวีคูณที่ 250/500 ms ค่า `Retry-After` ที่เป็นวินาทีหรือวันที่ HTTP
สามารถขยายเวลารอได้สูงสุด 5 วินาที สถานะอื่นจะล้มเหลวทันที การปฏิเสธบางส่วนของ OTLP 2xx จะทำให้เกิดข้อผิดพลาดเช่นกัน แทนที่จะ
ยืนยันการรับสแปนที่สูญหาย ระบบยอมรับการยืนยันที่ว่างเปล่าหรือเป็น JSON ที่ถูกต้อง โดย
จำกัดการอ่านคำตอบไว้ที่ 64 KiB

ข้อผิดพลาดจะมีเฉพาะข้อเท็จจริงที่ตัวส่งออกเป็นผู้กำหนด ได้แก่ สถานะ HTTP ประเภทการลองใหม่ จำนวนครั้งที่ลอง และจำนวน
สแปนที่ส่ง หรือข้อความตายตัวเกี่ยวกับความล้มเหลวของการยืนยัน/เครือข่าย เนื้อหาคำตอบของตัวรวบรวม
จำนวนรายการที่สำเร็จบางส่วน และส่วนหัวคำตอบจะไม่ถูกคัดลอกไปยังข้อผิดพลาด บันทึก หรือ
แดชบอร์ด ชุดข้อมูลที่ล้มเหลวหรือได้รับการยอมรับเพียงบางส่วนจะไม่ได้รับการยืนยัน โดยปลายทางจะแสดง
สถานะล้มเหลวพร้อมสถานะนั้น เคอร์เซอร์จะคงอยู่ที่ชุดข้อมูลล่าสุดที่ได้รับการยืนยัน และการทำงานครั้งถัดไป
จะส่งแถวเดิมซ้ำ สถานะถาวรจะยังคงล้มเหลวจนกว่าตัวรวบรวมหรือการกำหนดค่า
จะได้รับการแก้ไข ใช้บันทึกของตัวรวบรวมเองเพื่อดูรายละเอียดคำตอบ สรุปข้อผิดพลาดในบันทึกการเรียก
ยังคงใช้การปกปิดข้อมูลแยกต่างหาก
`prepare()` ไม่จัดเตรียมสิ่งใด การทดสอบจะส่ง POST ที่มีเนื้อหา `{"resourceSpans":[]}` เท่านั้น และรายงาน
สถานะ HTTP โดยไม่เขียนสแปนของบันทึกการเรียก

รหัสเทรซและรหัสสแปนคือเลขฐานสิบหก 32/16 หลักแรกของ SHA-256 ที่คำนวณจาก
`"omniroute.trace\0" + callLogId` และ `"omniroute.span\0" + callLogId` การส่งซ้ำจะใช้
รหัสเดิม นี่ไม่ใช่การรับประกันว่าจะกำจัดข้อมูลซ้ำ ระบบแบ็กเอนด์บางระบบ รวมถึงการรับข้อมูลของ Langfuse
v4 ไม่กำจัดสแปนที่มีรหัสเดียวกันออกเมื่อซ้ำกัน การขัดข้องหรือความล้มเหลวของกลุ่มย่อยบางส่วนอาจ
ทำให้ส่งซ้ำได้สูงสุดหนึ่งชุดข้อมูลเคอร์เซอร์ที่ยังไม่ได้รับการยืนยัน โดยทั้งชุดข้อมูลนั้นอาจซ้ำกัน
ไม่ใช่เฉพาะกลุ่มย่อย HTTP สุดท้าย โปรดเลือกขนาดชุดข้อมูลเคอร์เซอร์โดยคำนึงถึงข้อแลกเปลี่ยนนี้

### ตัวอย่าง Langfuse

กำหนดค่าฟิลด์เหล่านี้สำหรับอินสแตนซ์ Langfuse ที่โฮสต์เอง:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

สร้างค่า Authorization ภายในเครื่องโดยเข้ารหัสสตริง `public-key:secret-key` ตามตัวอักษรเป็น Base64
(ตัวอย่างเช่นใช้ `Buffer.from(publicKey + ":" + secretKey).toString("base64")`)
อย่าวางข้อมูลรับรองจริงลงในบันทึก ภาพหน้าจอ หรือรายงานปัญหา การแมปจะกำหนด
`x-langfuse-ingestion-version: 4` โดยอัตโนมัติ ส่วน Authorization ยังคงระบุใน `headers`
ทั้งส่วนหัวและค่า salt ของข้อมูลระบุตัวตนที่สร้างขึ้นจะใช้กลไกฟิลด์ลับที่เข้ารหัส
และตัวแทนค่า API ที่มีอยู่ โดยจำเป็นต้องมี `STORAGE_ENCRYPTION_KEY`

การแมปจะเพิ่มประเภท/โมเดลการสร้าง รายละเอียดการใช้งานในรูปแบบ JSON (อินพุต/เอาต์พุต/ยอดรวม และคีย์แคช
ที่มีอยู่), สแนปช็อตอินพุต/เอาต์พุตในรูปแบบ JSON, ระดับ ERROR/DEFAULT, ข้อความสถานะที่ผ่านการล้างข้อมูล,
ชื่อ trace, ID เซสชัน, สภาพแวดล้อมซึ่งระบุหรือไม่ก็ได้ และ
`langfuse.observation.metadata.<key>` ที่ใช้กรองตามผู้ให้บริการ โมเดลที่ร้องขอ พาธ คอมโบ แหล่งที่มาของแคช
และสถานะได้ `langfuse.observation.completion_start_time` เป็นเวลาในรูปแบบ ISO 8601 ที่
เวลาเริ่มต้น + TTFT เฉพาะเมื่อทราบค่า TTFT และค่านั้นอยู่ภายในระยะเวลาเท่านั้น ไม่มีการส่งแอตทริบิวต์ค่าใช้จ่าย

โหมดข้อมูลระบุตัวตนใช้กับ `langfuse.user.id`:

- `pseudonymous` (ค่าเริ่มต้น): ค่า HMAC-SHA256 ของ ID ภายในของคีย์ API โดยใช้ salt แบบสุ่ม
  ขนาด 32 ไบต์ที่แยกเฉพาะแต่ละปลายทาง หากยังไม่มี salt ระบบจะสร้างขึ้นเมื่อสร้างปลายทาง เข้ารหัส
  เป็น `identitySalt` ไม่ส่งกลับเด็ดขาด และเก็บไว้เมื่อมีการแก้ไข ระบบจะไม่ใส่ ID คีย์ดิบ
  ลงในแอตทริบิวต์ของ span การสร้าง salt ของปลายทางใหม่หรือหมุนเวียน salt จะทำให้ข้อมูลระบุตัวตนเปลี่ยนไป
- `keyName`: ชื่อคีย์ API ที่กำหนดค่าไว้ โดยตั้งใจเปิดเผยป้ายกำกับที่ผู้ดูแลระบบตั้งไว้
- `none`: ไม่มี ID ผู้ใช้ แต่ยังคงส่งออกแท็กเซสชันเมื่อมีอยู่ โหมดเหล่านี้ไม่ได้
  ทำให้เนื้อหาพรอมป์ต์ใด ๆ หรือป้ายกำกับเซสชัน/การเชื่อมโยงที่ผู้ดูแลระบบระบุเป็นข้อมูลนิรนาม

### เริ่มต้นโดยไม่เติมข้อมูลย้อนหลัง

เฉพาะขณะสร้าง ให้เปิดใช้งาน **เริ่มจากตำแหน่งปัจจุบัน (ข้ามบันทึกที่มีอยู่)** หรือส่ง
`startFromCurrentPosition: true` ที่ระดับบนสุดของเพย์โหลด API สำหรับการสร้าง การตั้งค่านี้จะกำหนดค่าเริ่มต้น
ของ `cursor_row_id` เป็น rowid สูงสุดในปัจจุบันของบันทึกการเรียกที่ยังเก็บรักษาอยู่ โดยใช้ฟังก์ชันช่วยจัดการเคอร์เซอร์ที่มีอยู่
โดยไม่ต้องย้ายข้อมูล ค่าเริ่มต้นคือ false (เคอร์เซอร์ 0 และเติมข้อมูลย้อนหลังจากประวัติที่ยังเก็บรักษาอยู่)
การตั้งค่านี้ไม่ใช่การตั้งค่ารีเซ็ตเคอร์เซอร์ขณะอัปเดต

การเพิ่ม `ttftMs` ที่ใช้ร่วมกันยังเพิ่มคอลัมน์ `ttft_ms` ที่อนุญาตให้เป็น null ในตัวแมป BigQuery
และสคีมาสำหรับตารางใหม่ด้วย: การทดสอบสคีมากำหนดให้ทุกฟิลด์ของระเบียนมาตรฐานต้องมี
คอลัมน์รองรับ ตารางที่มีอยู่ยังคงส่งออกได้โดยไม่มีการเปลี่ยนแปลง: `prepare()` จะอ่านสคีมาของตารางและ
ละเว้นเฉพาะ `ttft_ms` เมื่อไม่มีคอลัมน์นั้น เพิ่มคอลัมน์ INT64 ที่อนุญาตให้เป็น null เพื่อรับค่า TTFT
ในการรันครั้งถัดไป หรือใช้ตารางใหม่ ไม่จำเป็นต้องใช้ PATCH การปรับเปลี่ยนสคีมาอัตโนมัติ หรือสิทธิ์เพิ่มเติม
ฟิลด์อื่น ๆ ทั้งหมดของแถวยังคงผ่านการตรวจสอบสคีมาอย่างเข้มงวด

## 6. การเพิ่มปลายทาง

1. สร้าง `src/lib/logExport/destinations/<name>.ts` ซึ่งส่งออก `LogExportDestinationType`:
   โดยมี `configSchema` ของ Zod, อาร์เรย์ตัวอธิบาย `fields` สำหรับ UI, `secretFields` และ
   `createClient(config)` ที่คืนค่า `test()` / `prepare()` / `send(records)`
2. เพิ่มรายการดังกล่าวลงในอาร์เรย์ `DESTINATIONS` ใน `src/lib/logExport/registry.ts`
3. เขียนการทดสอบไว้ภายใต้ `tests/unit/`

การเปลี่ยนแปลงมีเพียงเท่านี้: ส่วนการจัดเก็บข้อมูล งาน cron เลเยอร์ REST การเข้ารหัสข้อมูลลับ และ
แบบฟอร์มแดชบอร์ด ล้วนอ้างอิงรีจิสทรี

กฎสองข้อสำหรับปลายทางใหม่:

- `send()` **ต้อง throw** เมื่อเกิดความล้มเหลวบางส่วน การ resolve หมายความว่า "ปลายทางมีแถวเหล่านี้แล้ว"
  และเคอร์เซอร์จะเลื่อนผ่านแถวเหล่านั้นอย่างถาวร
- ปลายทางที่รับ URL จากผู้ใช้ต้องตรวจสอบ URL ผ่าน
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) ก่อนทำการ fetch
  เช่นเดียวกับที่ webhook ทำ ส่วน BigQuery ไม่จำเป็นต้องทำเช่นนี้ เนื่องจากโฮสต์ของ BigQuery เป็นค่าคงที่

## 7. การใช้งาน

- **แดชบอร์ด**: Integrations → Log export เพิ่มปลายทาง เรียกใช้ **Test** เพื่อตรวจสอบข้อมูลประจำตัว
  โดยไม่เขียนแถวข้อมูล จากนั้นเปิดใช้งานปลายทาง
- **งานค้าง**: การ์ดของแต่ละปลายทางจะแสดงแถวที่รอดำเนินการและเคอร์เซอร์ ส่วน `GET
/api/log-export/status` จะส่งคืนตัวเลขเดียวกันพร้อมกับประวัติการทำงาน 20 ครั้งล่าสุด
- **ปลายทางหนึ่งที่ล้มเหลวจะไม่ทำให้ปลายทางอื่นล้มเหลว** — สรุปการทำงานจะบันทึกสถานะของแต่ละปลายทาง
  ไว้ใน `last_status` / `last_error` และประวัติการทำงานจะเก็บผลรวมโดยรวมไว้
- **การลบปลายทางจะลบเคอร์เซอร์ของปลายทางนั้นด้วย** การเพิ่มปลายทางนั้นกลับเข้ามาใหม่จะเริ่มจาก
  บันทึกการเรียกที่เก่าที่สุดซึ่งยังคงเก็บรักษาไว้ ทำให้มีการส่งแถวที่ปลายทางอาจมีอยู่แล้วซ้ำอีกครั้ง
  สำหรับ BigQuery ค่า `insertId` ของแต่ละแถวจะจัดการข้อมูลซ้ำได้เฉพาะภายในช่วงเวลาการขจัดข้อมูลซ้ำ
  ของ BigQuery เองเท่านั้น ดังนั้นควรปิดใช้งานปลายทางแทนการลบ
