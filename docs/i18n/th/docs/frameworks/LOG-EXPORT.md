ส่งออกบันทึกการเรียก OmniRoute ไปยังแหล่งจัดเก็บข้อมูลวิเคราะห์ภายนอกอย่างต่อเนื่อง โดยส่งออกเฉพาะรายการที่เพิ่มขึ้น

แท็บ Logs ในแดชบอร์ดเก็บประวัติคำขอไว้ใน SQLite (`call_logs`) ซึ่งมีขอบเขตจำกัดตาม
การหมุนเวียนและระยะเวลาเก็บรักษา การส่งออกบันทึกจะส่งชุดระเบียนเดียวกันออกไปตามกำหนดเวลา เพื่อให้เก็บไว้ได้นานกว่า
ฐานข้อมูลภายในเครื่องและนำไปเชื่อมกับข้อมูลอื่นได้ BigQuery เป็นปลายทางแรก โดย
ไปป์ไลน์ใช้รูปแบบรีจิสทรี จึงสามารถเพิ่มปลายทางอื่นได้โดยไม่ต้องเปลี่ยนโครงสร้างเดิม

## 1. วิธีการทำงาน

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **กำหนดเวลา** — งาน cron ของ `JobRegistry` หนึ่งงานชื่อ `log_export` มีค่าเริ่มต้นเป็น `0 * * * *` (ทุกชั่วโมง,
  UTC) ลงทะเบียนไว้ใน `src/lib/initCloudSync.ts` และสามารถกำหนดทับด้วย `OMNIROUTE_LOG_EXPORT_CRON`
  การทำงานแต่ละรอบจะส่งข้อมูลที่ค้างอยู่ไปยังทุกปลายทางที่**เปิดใช้งาน**ตามลำดับ
- **เคอร์เซอร์** — ใช้ `call_logs.rowid` โดยนัยของ SQLite และบันทึกแยกตามปลายทางไว้ใน
  `log_export_destinations.cursor_row_id` โดยตั้งใจไม่ใช้ `timestamp` เป็นเคอร์เซอร์: ผู้เรียก
  อาจระบุค่าเองได้ ดังนั้นคำขอที่ช้าอาจถูกเขียนหลังคำขอที่เร็วกว่าแต่เริ่มทีหลัง
  และเคอร์เซอร์ที่ใช้เวลาประทับจะข้ามระเบียนนั้นไป
- **การแบ่งชุด** — ส่ง `batch_size` แถวต่อคำขอ (ค่าเริ่มต้น 500) และ `max_rows_per_run` แถวต่อการทำงานหนึ่งครั้ง
  (ค่าเริ่มต้น 10000) เพื่อให้ทยอยส่งข้อมูลค้างจำนวนมากในหลายรอบ แทนที่จะกีดขวางการทำงานรอบเดียว
- **การส่งมอบ** — เคอร์เซอร์จะเลื่อนไปข้างหน้าหลังจาก `send()` สำเร็จแล้วเท่านั้น หากชุดข้อมูลล้มเหลว
  เคอร์เซอร์จะคงอยู่ที่เดิม จึงมีการลองส่งแถวเดิมอีกครั้งในการทำงานรอบถัดไป การรับประกันคือ
  ส่งอย่างน้อยหนึ่งครั้งร่วมกับการกำจัดข้อมูลซ้ำฝั่งปลายทาง ไม่ใช่ส่งครั้งเดียวอย่างแท้จริง: BigQuery ใช้
  ID ของบันทึกการเรียกเป็นคีย์ของแต่ละแถว โดยพยายามกำจัดข้อมูลซ้ำตามคีย์นี้ภายในช่วงเวลาการกำจัดข้อมูลซ้ำของตนเอง
- **การป้องกันการทำงานซ้อนกัน** — รอบ cron และ `POST .../run` อาจเริ่มทำงานพร้อมกันได้ ปลายทาง
  ที่กำลังส่งข้อมูลค้างอยู่จะถูกข้ามแทนการส่งซ้ำสองรอบ (`skipped: true` ในผลการทำงาน)
  ดังนั้นการทำงานพร้อมกันจึงไม่สามารถส่งชุดข้อมูลซ้ำหรือเขียนเคอร์เซอร์ย้อนกลับได้
- **การกู้คืนหลังล้างข้อมูล** — หาก `cursor_row_id` มีค่าสูงกว่า `MAX(rowid)` (มีการล้างทั้งตาราง
  และเริ่ม rowid ใหม่) ตัวรันจะย้อนกลับไปที่ 0 แทนที่จะมองไม่เห็นข้อมูลใหม่อย่างถาวร

### ตัวรันแบบแยกและขีดจำกัด

การทำงานของแต่ละปลายทางบน Node จะเริ่มโพรเซสลูกของระบบปฏิบัติการที่แยกต่างหากและมีอายุสั้น (`child_process`
ที่ใช้ IPC ไม่ใช่ `worker_threads`) การอ่านเนื้อหา การแยกวิเคราะห์/ซีเรียลไลซ์ JSON ของเพย์โหลด
`prepare()` ของปลายทาง และ I/O เครือข่ายของปลายทางทั้งหมดทำงานในโพรเซสนั้น ไม่ใช่บน event loop ของเซิร์ฟเวอร์
มีเพียงการกำหนดค่าและข้อความรายงานความคืบหน้าขนาดเล็กเท่านั้นที่ส่งผ่าน IPC ระเบียนที่ส่งออกจะไม่ถูกส่งกลับไปยัง
เซิร์ฟเวอร์ งาน cron และเส้นทาง Run now ยังคงผลลัพธ์สาธารณะและการป้องกันการทำงานซ้อนกันไว้เหมือนเดิม

โพรเซสลูกเปิด `DATA_DIR/storage.sqlite` ตามพาธที่เซิร์ฟเวอร์ระบุไว้ในโหมดอ่านอย่างเดียวโดยใช้ `node:sqlite`
พร้อม `busy_timeout=5000` และ `query_only=ON` โดยไม่อิมพอร์ต DB singleton และไม่ทำ
การย้ายโครงสร้างข้อมูล การสำรองข้อมูล หรือการอัปเดต SQLite การจัดการข้อมูลกำกับอาร์ติแฟกต์ที่หายไป/เสียหาย (รวมถึง
คำสั่ง UPDATE สำหรับอาร์ติแฟกต์ที่เสียหาย) ยังคงอยู่เฉพาะในเส้นทางรายละเอียดของแดชบอร์ด ทั้งสองเส้นทางใช้
ตัวแก้ไขรายละเอียดแบบ pure ร่วมกัน การส่งออกใช้การอ่านระบบไฟล์แบบอะซิงโครนัสและลำดับการค้นหาเดียวกันคือ อาร์ติแฟกต์ → ข้อมูลแบบเก่า
ที่ฝังในระเบียน → ข้อมูลแบบเก่าบนดิสก์ → ไม่มีข้อมูล การทำงานแต่ละครั้งจะบันทึกค่าสูงสุดของ rowid สำหรับการแทรก
เมื่อโพรเซสลูกเปิดตัวอ่าน ข้อมูลที่แทรกภายหลังจะรอการทำงานรอบถัดไป นี่คือขอบเขต
การแทรกข้อมูล ไม่ใช่ธุรกรรม SQLite ที่เปิดค้างไว้นาน: ตัวเขียน WAL และเช็กพอยต์ยังทำงานได้ตามปกติระหว่าง
รอเครือข่าย ขอบเขตนี้ไม่ได้ตรึงการอัปเดต/การลบแถวที่มีอยู่แล้ว

หลังจากแต่ละชุดข้อมูลได้รับการยอมรับ โพรเซสลูกจะรอการตอบรับ เซิร์ฟเวอร์จะบันทึก
เคอร์เซอร์ด้วย `advanceLogExportCursor` ก่อน จากนั้นจึงส่ง `ack` โดยจะไม่เริ่มชุดถัดไปก่อนขั้นตอนนี้
การส่งล้มเหลว การขัดข้อง หรือการหมดเวลาจะบันทึกความล้มเหลวโดยไม่เลื่อนเคอร์เซอร์ของชุดนั้น ชุดข้อมูลที่
ได้รับการตอบรับแล้วจะยังคงถูกบันทึกไว้ มีเพียงชุดเดียวที่ยังไม่ได้รับการตอบรับเท่านั้นที่อาจถูกส่งซ้ำ
ระบบจะบันทึกความสำเร็จหลังจากได้รับ `done` และโพรเซสลูกจบการทำงานตามปกติเท่านั้น เมื่อเกิดความล้มเหลวจะยุติโพรเซสลูก
ด้วย SIGTERM และเพิ่มระดับเป็น SIGKILL หลังจาก 500 ms โดยตัวรันจะรอจนโพรเซสปิด

| ตัวแปรสภาพแวดล้อม                             | ค่าเริ่มต้น | วัตถุประสงค์                                   |
| --------------------------------------------- | ----------- | ---------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000      | ขีดจำกัดเวลาจริงต่อปลายทาง                     |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024        | ขีดจำกัด old-space ของ V8 ในโพรเซสลูก หน่วย MB |

ค่าที่ไม่ถูกต้อง/ไม่เป็นบวก/ไม่ใช่จำนวนเต็มจะใช้ค่าเริ่มต้น การตั้งค่าฮีปไม่ใช่ขีดจำกัด
RSS ทั้งหมด ชุดข้อมูลที่ใหญ่มากยังอาจใช้หน่วยความจำของโพรเซสลูกจนหมดและทำให้การทำงานล้มเหลวอย่างปลอดภัยได้
ค่าเริ่มต้น 1024 MB เผื่อพื้นที่ไว้สำหรับชุดข้อมูลเริ่มต้น 500 แถวที่มีอาร์ติแฟกต์ขนาด 512 KiB และ
เปิดใช้งานเนื้อหา รวมถึงการซีเรียลไลซ์ JSON แบบแบ่งตามจำนวนไบต์ของ BigQuery แต่ไม่ได้ทำให้
ชุดข้อมูล 10000 แถวที่มีเนื้อหาปลอดภัยต่อการใช้งาน เมื่อฮีป V8 หมด ระบบจะบันทึกความล้มเหลวพร้อมแนวทางแก้ไข: ลดขนาด
ชุดข้อมูลหรือเพิ่ม `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` โดยเคอร์เซอร์จะคงอยู่ที่ชุดล่าสุด
ที่ได้รับการตอบรับ เนื้อหาเก่าที่ฝังในระเบียน/อยู่บนดิสก์ไม่ได้อยู่ภายใต้ขีดจำกัดอาร์ติแฟกต์แบบใหม่
ผู้ดูแลระบบต้องจัดสรรงบประมาณ RSS แยกต่างหาก โดยเฉพาะภายในคอนเทนเนอร์ที่จำกัดหน่วยความจำ

โปรเซสลูกจะรับสืบทอดเฉพาะ `DATA_DIR` ที่ระบุค่าแล้ว, `NODE_ENV`, `TZ` ที่กำหนดไว้อย่างชัดเจน (การตีความเวลาท้องถิ่น
จากชื่อไฟล์แบบเดิม), `ELECTRON_RUN_AS_NODE` หากมี และค่าอินพุตสำหรับการเชื่อมต่อขาออกต่อไปนี้:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (รวมถึงรูปแบบตัวพิมพ์เล็ก),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`
ตัวกระจายคำขอ Undici ส่วนกลางใช้กลไกการกำหนดพร็อกซีจากสภาพแวดล้อมเพียงอย่างเดียวและกฎการข้ามพร็อกซีสำหรับโฮสต์ภายใน
ร่วมกับเซิร์ฟเวอร์ รวมถึง `NO_PROXY`; โดยไม่ได้นำเข้า `proxyFetch.ts` หรือแฟล็ก DB/ฟีเจอร์ของไฟล์ดังกล่าว
ข้อมูลรับรองพร็อกซีจะถูกปกปิดจากเอาต์พุตที่ส่งต่อและข้อผิดพลาดที่บันทึกไว้ ข้อมูลรับรองของปลายทาง
จะถูกส่งผ่านข้อความ IPC สำหรับเริ่มต้นเพียงข้อความเดียวเท่านั้น ไม่ผ่าน argv หรือสภาพแวดล้อม; เอาต์พุต/ข้อผิดพลาดที่ส่งต่อจะ
มีคำนำหน้าและผ่านการกรองข้อมูลที่ละเอียดอ่อน อาร์กิวเมนต์ exec ของโปรเซสลูกจะปิดใช้เฉพาะ `ExperimentalWarning` เพื่อหลีกเลี่ยง
การแสดงคำเตือน SQLite ของ Node ซ้ำทุกครั้งที่ cron ทำงาน; คำเตือนประเภทอื่นยังคงแสดงตามปกติ

โมดูลปลายทางต้องนำเข้าได้โดยไม่พึ่งพา Next.js/ส่วนที่ใช้ได้เฉพาะเซิร์ฟเวอร์ การใช้งาน
BigQuery ที่มีอยู่เป็นไปตามข้อกำหนดนี้แล้ว แคชโทเค็นการเข้าถึงจะคงอยู่เฉพาะช่วงที่โปรเซสลูก
ทำงานเท่านั้น ไม่คงอยู่ข้ามการทำงานแต่ละครั้ง Node คือรันไทม์ที่รองรับ (engines ใน `package.json`) แต่ส่วนการติดตั้ง Bun ใน README
และ `Dockerfile.bun` ยังระบุแนวทางที่เข้ากันได้สำหรับใช้งานจริงผ่าน
`bun:sqlite` (`src/lib/db/core.ts` / อะแดปเตอร์) ด้วย ดังนั้นเมื่อใช้ Bun การส่งออกจะยังคงใช้
แนวทางเดิมที่ทำงานภายในโปรเซส และแสดงคำเตือนครั้งเดียวว่า: ไม่สามารถแยกฮีป/การหมดเวลาของโปรเซสลูกได้ ให้ใช้
Node เพื่อแยกผลกระทบต่อ event loop และภาวะหน่วยความจำไม่เพียงพอ (OOM); ในที่นี้ไม่ได้ถือว่า Bun ใช้สำหรับการพัฒนาเท่านั้น

เมื่อเปิดใช้ `includeBodies` ควรกำหนดรอบการทำงานในระดับนาที เช่น
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` แทนการสะสมเพย์โหลดค้างไว้รายชั่วโมง
ขีดจำกัดแบตช์และจำนวนแถวยังคงจำกัดปริมาณงานแต่ละครั้ง การเริ่มโปรเซสมีต้นทุนต่อปลายทางต่อการทำงานแต่ละครั้ง;
นี่คือการแลกต้นทุนการเริ่มต้นเล็กน้อยกับการแยกผลกระทบต่อ event loop ของเซิร์ฟเวอร์ ไม่ใช่การลดการใช้ CPU โดยรวม

### เพย์โหลด (พรอมป์ต์และคำตอบ)

โดยค่าเริ่มต้น การส่งออกจะมีเฉพาะฟิลด์สรุปที่แสดงใน**รายการ**บันทึก การเปิด
**ส่งออกพรอมป์ต์และคำตอบ** (`includeBodies`) จะส่งข้อมูลที่แสดงในบานหน้าต่าง**รายละเอียด**
ของบันทึกสำหรับแต่ละการเรียกเพิ่มด้วย:

| ฟิลด์                            | ข้อมูลที่เก็บ                                               |
| -------------------------------- | ----------------------------------------------------------- |
| `request_body` / `response_body` | เพย์โหลดของการเรียกตามที่แดชบอร์ดแสดง                       |
| `pipeline_route_decision`        | เป้าหมายและโมเดลที่เราเตอร์เลือก                            |
| `pipeline_client_request`        | คำขอดิบตรงตามที่ไคลเอนต์ส่งมา                               |
| `pipeline_openai_request`        | ข้อมูลหลังแปลงเป็นรูปแบบ OpenAI ภายใน                       |
| `pipeline_provider_request`      | ข้อมูลที่ส่งไปยังระบบต้นทางจริงในรูปแบบเฉพาะของผู้ให้บริการ |
| `pipeline_provider_response`     | คำตอบดิบจากระบบต้นทาง                                       |
| `pipeline_client_response`       | ข้อมูลที่ส่งกลับให้ผู้เรียก                                 |
| `pipeline_error`                 | รายละเอียดข้อผิดพลาดระดับไปป์ไลน์สำหรับการเรียกที่ล้มเหลว   |
| `bodies_truncated`               | เป็นจริงเมื่อฟิลด์ใดก็ตามข้างต้นถึงขีดจำกัด `maxBodyBytes`  |

ข้อมูลนี้เป็นเนื้อหาพรอมป์ต์ จึง**ปิดไว้โดยค่าเริ่มต้น** และตั้งใจให้เลือกเปิดแยกตามปลายทาง
ข้อมูลที่ส่งออกคือข้อมูลเดียวกับที่แดชบอร์ดแสดง เนื่องจากการส่งออกและ `getCallLogById` ใช้กลไก
การดึงรายละเอียดร่วมกัน: เพย์โหลด
ผ่านการกรองข้อมูลส่วนบุคคลที่ระบุตัวตนได้ (PII) และปกปิดข้อมูลลับแล้วเมื่อบันทึก และการเรียกที่ใช้
คีย์ API แบบ `noLog` จะไม่เก็บเพย์โหลดใด ๆ จึงไม่มีข้อมูลให้ส่งออก

เพย์โหลดจะถูกอ่านทีละแถวจากอาร์ติแฟกต์ในระบบไฟล์ ดังนั้นการโหลดข้อมูลประกอบจึงทำเฉพาะกับปลายทาง
ที่ร้องขอเท่านั้น หากอาร์ติแฟกต์หายไปหรือเสียหาย ระบบจะส่งออกข้อมูลสรุปพร้อมเพย์โหลดเป็น null แทน
การทำให้ทั้งแบตช์ล้มเหลวและเคอร์เซอร์ค้างอยู่

`maxBodyBytes` (ค่าเริ่มต้น 262144) จำกัดขนาดของแต่ละฟิลด์ เพย์โหลดที่ยาวกว่าจะถูก**ตัดให้สั้นลงแทนที่จะ
ทิ้งไป** — พรอมป์ต์ที่ถูกตัดยังคงบอกได้ว่า "ถามอะไรไป" — และแถวนั้นจะถูกทำเครื่องหมายด้วย
`bodies_truncated` จะไม่ส่งออกข้อมูลส่วนต่างที่สตรีมมาทีละชังก์; คำตอบที่ประกอบเสร็จแล้ว
อยู่ใน `pipeline_provider_response` และ `pipeline_client_response` อยู่แล้ว

## 3. REST API

ทุกเส้นทางต้องผ่านการยืนยันตัวตนสำหรับการจัดการ (`requireManagementAuth`) ข้อมูลลับจะไม่ถูกส่งกลับ:
ข้อมูลลับที่จัดเก็บไว้จะถูกส่งกลับเป็นค่าตามตัวอักษร `__stored__` และการส่งค่านั้นกลับมาเมื่ออัปเดต
จะคงข้อมูลรับรองที่จัดเก็บไว้

การสร้างหรืออัปเดตปลายทางที่ประเภทของปลายทางระบุว่ามีข้อมูลลับ **จำเป็นต้องมี
`STORAGE_ENCRYPTION_KEY`** หากไม่มีค่านี้ `encrypt()` จะส่งข้อมูลผ่านโดยไม่เข้ารหัสและไม่แจ้งเตือน ดังนั้นการเขียนข้อมูลจึง
ถูกปฏิเสธด้วยสถานะ 400 แทนที่จะบันทึกข้อมูลรับรองลงใน SQLite เป็นข้อความธรรมดา (เป็นมาตรการป้องกันเดียวกับที่
webhook ของ Telegram ใช้)

| เมธอด    | เส้นทาง                                  | วัตถุประสงค์                                                              |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | ประเภทปลายทาง + รายการฟิลด์การกำหนดค่าของแต่ละประเภท                      |
| `GET`    | `/api/log-export/destinations`           | แสดงรายการปลายทาง (ปกปิดข้อมูลลับ)                                        |
| `POST`   | `/api/log-export/destinations`           | สร้างปลายทาง                                                              |
| `GET`    | `/api/log-export/destinations/{id}`      | อ่านข้อมูลปลายทางหนึ่งรายการ                                              |
| `PUT`    | `/api/log-export/destinations/{id}`      | อัปเดตชื่อ / สถานะเปิดใช้งาน / การกำหนดค่า / การแบ่งเป็นชุด               |
| `DELETE` | `/api/log-export/destinations/{id}`      | ลบ                                                                        |
| `POST`   | `/api/log-export/destinations/{id}/test` | ทดสอบข้อมูลรับรองโดยไม่เขียนข้อมูลใด ๆ                                    |
| `POST`   | `/api/log-export/destinations/{id}/run`  | ส่งข้อมูลค้างทั้งหมดทันที โดยใช้เส้นทางการทำงานเดียวกับการรันตามกำหนดเวลา |
| `GET`    | `/api/log-export/status`                 | สถานะ Cron, การรันล่าสุด, ข้อมูลค้างของแต่ละปลายทาง                       |

`GET /api/log-export/types` ทำให้ UI รองรับปลายทางได้ทุกประเภท: ฟอร์มบนแดชบอร์ดถูกสร้างจาก
คำอธิบายฟิลด์ที่ส่งกลับมา จึงไม่จำเป็นต้องเปลี่ยน UI เมื่อเพิ่มปลายทางใหม่

## 4. ปลายทาง BigQuery

คีย์การกำหนดค่า (`type: "bigquery"`):

| Key                  | Notes                                                                                                            |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `projectId`          | โปรเจ็กต์ GCP ที่มีชุดข้อมูล                                                                                     |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                                  |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                                  |
| `location`           | ใช้เฉพาะเมื่อจำเป็นต้องสร้างชุดข้อมูล (ค่าเริ่มต้นคือ `EU`)                                                      |
| `serviceAccountJson` | คีย์บัญชีบริการ ความลับ: เข้ารหัสขณะจัดเก็บและไม่ส่งคืน                                                          |
| `autoCreate`         | สร้างชุดข้อมูล/ตารางที่หายไป และเพิ่มคอลัมน์หลักฐานการใช้งานที่เป็น nullable ตามเงื่อนไข (ค่าเริ่มต้นคือ `true`) |

บัญชีบริการต้องมี `bigquery.tables.updateData` ในตารางเป้าหมาย รวมถึง
`bigquery.datasets.create` / `bigquery.tables.create` เมื่อเปิดใช้ `autoCreate`
การอัปเดตตารางที่มีอยู่เพื่อเพิ่มฟิลด์หลักฐานการใช้งานที่เป็น nullable สองฟิลด์ยังต้องมี
`bigquery.tables.update` ด้วย หากไม่มีสิทธิ์ใดสิทธิ์หนึ่ง การส่งออกจะล้มเหลวโดยไม่เลื่อนเคอร์เซอร์

แบตช์ที่กำหนดค่าไว้เป็นหน่วย **เคอร์เซอร์** ไม่ใช่หน่วย HTTP: `send()` จะแบ่งเป็นการเรียก insertAll
ครั้งละไม่เกิน 500 แถว ดังนั้น `batch_size` ขนาดใหญ่จึงไม่ทำให้เกินขีดจำกัดคำขอ 10 MB ของ BigQuery
สถานะชั่วคราว (408/429/500/502/503/504) จะลองใหม่สูงสุดสามครั้งด้วย exponential
backoff โดยใช้ insertIds เดิม ส่วนความล้มเหลวด้านการยืนยันตัวตนและสคีมาจะโยนข้อผิดพลาดตั้งแต่ครั้งแรก
แทนที่จะใช้การทำงานของรอบนั้นจนหมด

ตารางที่เพิ่งสร้างอาจยังไม่ปรากฏให้ปลายทางสตรีมมิงเห็น และจะตอบกลับ 404 เป็นเวลาสองสามวินาที
ระบบจะลองใหม่สำหรับ 404 นี้ แต่ **เฉพาะเมื่อรอบการทำงานนี้เป็นผู้สร้างตารางเท่านั้น** —
หากตารางหายไปจริงจะล้มเหลวทันที โปรดทราบว่าการสร้างตารางใหม่ด้วยชื่อเดิมหลังจากเพิ่งลบตารางนั้น
จะทำให้ BigQuery ปฏิเสธการแทรกข้อมูลแบบสตรีมมิงเป็นเวลาหลายนาที นี่เป็นคุณสมบัติของการลบแล้วสร้างใหม่
ดังนั้นควรใช้ชื่อตารางใหม่แทนการลบแล้วเพิ่มตารางเดิมกลับมา

**ความล้มเหลวบางส่วนจะมาถึงในรูปแบบ HTTP 200 พร้อม `insertErrors[]` ที่ไม่ว่าง** ระบบจะถือว่าเป็น
ความล้มเหลวและโยนข้อผิดพลาด ซึ่งเป็นสิ่งที่หยุดไม่ให้เคอร์เซอร์เลื่อนไปเลยแถวที่ BigQuery ไม่เคยรับข้อมูล
โดย `tests/unit/log-export-bigquery.test.ts` จะยืนยันพฤติกรรมนี้

การขนส่งใช้ REST โดยตรง — assertion แบบ RS256 ที่ลงชื่อด้วยใบรับรองที่ออกเองจะถูกแลกเปลี่ยนเป็น access token ที่
`https://oauth2.googleapis.com/token` จากนั้นแถวต่าง ๆ จะถูกส่งไปยัง `tabledata.insertAll` โดยจะไม่มีการดึง
Google SDK เข้ามา access token จะถูกแคชภายในโปรเซสแยกตาม (บัญชีบริการ, scope)

ตารางที่สร้างขึ้นจะมีหนึ่งคอลัมน์ต่อหนึ่งฟิลด์จากแท็บ Logs รวมถึง `exported_at` และจัดวางให้เหมาะกับ
รูปแบบการค้นหาบันทึกการเรียกใช้งานจริง:

- **แบ่งพาร์ติชันตามวันด้วย `timestamp`** ดังนั้นคำค้นหาที่จำกัดด้วยวันที่จะสแกนเฉพาะวันเหล่านั้น
- **จัดกลุ่มคลัสเตอร์ด้วย `api_key_name`, `provider`, `model`, `status`** (ตามลำดับนี้) ดังนั้นการกรองตาม
  ผู้เรียกใช้งาน ปลายทาง หรือสถานะความล้มเหลวจะตัดบล็อกภายในแต่ละพาร์ติชันออกได้ BigQuery อนุญาตคอลัมน์
  สำหรับการจัดคลัสเตอร์ได้สูงสุดสี่คอลัมน์ และลำดับมีความสำคัญ: การกรองด้วย `api_key_name` เพียงอย่างเดียว
  จะตัดบล็อกได้ แต่การกรองด้วย `status` เพียงอย่างเดียวจะทำไม่ได้
- **การเก็บรักษาพาร์ติชันแบบเลือกได้** ผ่าน `partitionExpirationDays` (ค่า 0 จะเก็บทุกอย่าง) โดยจะมีผล
  เมื่อสร้างตาราง

การตั้งค่าทั้งสองรายการมีผลขณะสร้างเท่านั้น ตารางที่มีอยู่แล้วจะคงรูปแบบเดิมไว้ ดังนั้นให้ชี้ปลายทางไปยัง

## 5. ปลายทาง traces ของ OTLP/HTTP

การกำหนดค่าใช้ `type: "otlp-http"` นี่คือการส่งออก call log ที่บันทึกไว้ตามกำหนดเวลาและมีเคอร์เซอร์รองรับ ไม่ใช่ sink สำหรับ routing-event แบบเรียลไทม์ที่พยายามส่งให้ดีที่สุดใน
`open-sse/services/routing/otel.ts` โดยจะไม่อ่านหรือเปลี่ยนแปลงตัวแปรสภาพแวดล้อม ตัวจับเวลา หรือบัฟเฟอร์ของ sink ดังกล่าว การเปิดใช้ทั้งสองแบบอาจทำให้เกิด spans อิสระสองประเภท
ให้ใช้ instrumentation scope `omniroute.log-export` เพื่อแยกความแตกต่างของ call-log spans เหล่านี้

### Payload และการส่งข้อมูล

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) จะส่งหนึ่ง
CLIENT span ต่อแถวที่อนุญาต โดยตั้งชื่อจาก request path ที่ตรงกันทุกประการ การตั้งชื่อ path
ช่วยแยก Chat Completions, Responses และ Messages ออกจากกัน โดยไม่ฝังข้อมูลโมเดลหรือข้อมูลระบุตัวตน
ไว้ในชื่อ span แอตทริบิวต์ของ resource ประกอบด้วย `service.name` และ `service.version` ของแพ็กเกจ

ตัวบันทึกความพยายามของแชตตามปกติ (`open-sse/handlers/chatCore/attemptLogging.ts`) จะเขียน
`duration = Date.now() - startTime` เมื่อเสร็จสิ้น และไม่ได้ระบุ timestamp;
`saveCallLogOperation` ใน `src/lib/usage/callLogs.ts` จะตั้งค่า timestamp เริ่มต้นเป็นเวลาที่เขียน
(เวลาที่เสร็จสิ้น) ดังนั้นการส่งออกจะกำหนด end = timestamp ของแถว และ start = end − duration
(มิลลิวินาที ซึ่งแปลงเป็น decimal nanoseconds) timestamp ในอดีตที่ผู้เรียกระบุจะยังคงถูกเก็บไว้
เป็นเวลา end เช่นเดียวกัน ไม่มีตัวแยก start/completion ต่อแถว duration ที่เป็น null จะถูกเปลี่ยนเป็นศูนย์
timestamp ที่ไม่ถูกต้องหรือขาดหายจะทำให้ batch ล้มเหลว แทนที่จะสร้าง spans ที่ไม่เป็นดีเทอร์มินิสติก
`ttftMs` เป็น nullable และจะถูกแมปไปยัง `omniroute.ttft_ms`

แอตทริบิวต์ประกอบด้วย `gen_ai.operation.name="chat"`, provider, requested/response model,
input/output tokens, cache-read/cache-creation/reasoning tokens ที่เป็นตัวเลือก, HTTP status,
combo, cache source, session tag และ correlation id ค่า OTLP แบบจำนวนเต็มและ timestamp จะเป็น
สตริงทศนิยม ส่วนสตริง บูลีน และตัวเลขเศษส่วนจะใช้รูปแบบค่า OTLP แบบ native ของตนเอง
Error spans จะมีสถานะ ERROR และข้อความสถานะที่ผ่านการทำให้ปลอดภัยแล้ว canonical record
ไม่มี URL โฮสต์ upstream ดังนั้นจึงละเว้น `server.address` แทนที่จะระบุ collector อย่างไม่ถูกต้อง
ว่าเป็น model server จะไม่มีการส่งออก cost

เฉพาะ `includeBodies=true` เท่านั้นที่จะ hydrate เนื้อหา เมื่อใช้ `langfuseMapping=false`,
`gen_ai.input.messages` / `gen_ai.output.messages` จะมี JSON ของ body คำขอ/คำตอบที่ผ่านการทำให้ปลอดภัย
ตามที่ OmniRoute จัดเก็บไว้ (ทำให้เป็นรูปแบบ canonical เมื่อสามารถ parse ได้) ไม่ใช่อาร์เรย์ messages
ของ semconv ที่จัดรูปแบบใหม่ body ที่ถูกตัดหรือไม่ใช่ JSON จะยังคงเป็นข้อความดิบ เมื่อใช้
`langfuseMapping=true`, body จะถูกส่งออกเฉพาะใน `langfuse.observation.input` /
`langfuse.observation.output`; แอตทริบิวต์ `gen_ai.*.messages` จะถูกละเว้นเพื่อให้ส่ง body
แต่ละรายการเพียงครั้งเดียว ทั้งสองโหมดสืบทอด `maxBodyBytes` จากเส้นทาง hydration ที่มีอยู่;
`omniroute.bodies_truncated=true` จะระบุว่ามีการตัดข้อมูล
ปลายทางนี้จะไม่เพิ่ม snapshot ของ pipeline หรือการอ่าน artifact ที่ยังไม่ผ่านการทำให้ปลอดภัย
การเก็บส่วนหัวคำขอที่เป็นตัวเลือกจะใช้ snapshot ของไคลเอ็นต์ที่ hydrate แล้วซึ่งอธิบายไว้ด้านล่าง
ให้ใช้ความถี่ระดับนาที เช่น `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` เมื่อส่งออก
bodies แทนการสะสม backlog รายชั่วโมง

### ส่วนหัวคำขอของไคลเอ็นต์ที่เป็นตัวเลือก

การเก็บส่วนหัวจะ **ปิดใช้งานตามค่าเริ่มต้น** ตั้งค่า `requestHeaderAllowlist` ในการกำหนดค่าปลายทาง
และเปิดใช้ **Export prompts and responses** (`includeBodies: true` ในปลายทาง)
allowlist รับอาร์เรย์ API หรือ textarea ที่มีชื่อคั่นด้วยบรรทัดใหม่/จุลภาค:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ชื่อจะจับคู่โดยไม่คำนึงถึงตัวพิมพ์เล็กและใหญ่และต้องตรงกันทุกประการ เว้นแต่ `*` เดี่ยวที่อยู่ท้ายสุดจะเลือกคำนำหน้าชื่อส่วนหัวที่ไม่ว่างเปล่า `*` เดี่ยว, wildcard ที่ฝังอยู่ และชื่อส่วนหัว HTTP ที่ไม่ถูกต้องจะถูกปฏิเสธ  
มี selector ได้ไม่เกิน 64 รายการ โดยแต่ละรายการมีชื่อ/คำนำหน้าได้ไม่เกิน 256 ไบต์ ASCII  
การตั้งค่านี้แยกจาก `headers` ซึ่งใช้ยืนยันตัวตนของ exporter กับ collector

การดักจับจะอ่านเฉพาะ `pipeline_client_request` ซึ่งมาจาก `clientRawRequest` (หรือ `clientRequest` แบบเก่า) ของ pipeline แบบละเอียดที่บันทึกไว้เท่านั้น และจะไม่ย้อนกลับไปใช้ส่วนหัวคำขอของ provider การบันทึก pipeline แบบละเอียดต้องเปิดใช้งานอยู่ขณะที่บันทึกคำขอ หากปิดใช้ `includeBodies` หรือ JSON ของ client snapshot หายไป เสียหาย หรือถูกตัด จะไม่มีการส่งออกแอตทริบิวต์ส่วนหัว การเพิ่ม `maxBodyBytes` อาจช่วยหลีกเลี่ยงการถูกตัดของ snapshot ขณะส่งออกได้ แต่ไม่สามารถกู้คืนรายละเอียดที่ไม่ได้บันทึกไว้ตั้งแต่แรกได้ snapshot ที่มีขนาดเกิน 1 MiB หรือมีรายการส่วนหัวมากกว่า 256 รายการจะถูกละเว้น การส่งออก prompt/response ที่มีอยู่จะยังคงเปิดใช้งานควบคู่กับการดักจับส่วนหัว allowlist นี้ไม่ได้จัดเตรียมโหมด hydration ที่มีเฉพาะส่วนหัว

ค่าที่เลือกจะกลายเป็นอาร์เรย์สตริง OTLP ที่ชื่อ `http.request.header.<full lowercase header name>` แม้จะมีสตริงเดียวก็ตาม ตัวอย่างเช่น `X-OmniRoute-Meta-Team: example-team` จะกลายเป็น `http.request.header.x-omniroute-meta-team` พร้อมกับ `{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`  
คำนำหน้าแบบเต็มจะยังคงอยู่: ค่าเหล่านี้เป็นส่วนหัวทั่วไป โดยไม่มีการแยกวิเคราะห์ฟิลด์ทางธุรกิจหรือการแปลงเป็น `omniroute.metadata.*` / Langfuse metadata `langfuseMapping` ไม่เปลี่ยนความหมายของส่วนหัว `User-Agent` ที่เลือกและมีค่าเดียวจะตั้งค่า scalar มาตรฐาน `user_agent.original` ด้วย เครื่องหมายจุลภาคภายในค่าเดียวจะไม่ถูกแยก การเปลี่ยนรูปแบบตัวพิมพ์จะถูกรวมตามลำดับรายการที่บันทึกไว้ หากรูปแบบใดรูปแบบหนึ่งไม่ถูกต้อง ส่วนหัวนั้นทั้งรายการจะถูกละเว้น แอตทริบิวต์จะเรียงตามชื่อที่เป็นตัวพิมพ์เล็ก

Authorization, Proxy-Authorization, Cookie, Set-Cookie, ส่วนหัว API-key, ชื่อที่มีตัวบ่งชี้ auth/token/secret/password/credential และข้อมูลรับรองภายในของ gateway จะถูกแยกออกเสมอ แม้จะถูกเลือกหรือถูกปกปิดบางส่วนในพื้นที่จัดเก็บก็ตาม รูปแบบข้อมูลรับรองที่รู้จักจะใช้ตัวตรวจจับข้อมูลรับรองร่วมกัน เครื่องหมายการลบข้อมูลจะถูกละเว้น ไม่ใช่ส่งออกเป็นค่าที่ปลอดภัย ยอมรับเฉพาะสตริงและอาร์เรย์สตริงที่ไม่ว่างเปล่าเท่านั้น จะไม่มีการแปลงตัวเลขหรืออ็อบเจ็กต์โดยอัตโนมัติ ชื่อที่ไม่ถูกต้อง คีย์ prototype อักขระควบคุม (ยกเว้นแท็บแนวนอน) และ Unicode ที่มีรูปแบบไม่ถูกต้องจะถูกละเว้นโดยไม่ทำให้ batch ล้มเหลวหรือสะท้อนเนื้อหาดังกล่าวในข้อผิดพลาด

แต่ละ span จะจับส่วนหัวได้ไม่เกิน 32 รายการ ค่าไม่เกิน 16 ค่าต่อส่วนหัว แต่ละค่าไม่เกิน 4096 ไบต์ UTF-8 และรวมชื่อกับค่าของส่วนหัวที่จับได้ทั้งหมดไม่เกิน 16384 ไบต์ UTF-8 ส่วนหัวที่มีขนาดเกินกำหนดหรือไม่ถูกต้องจะถูกละเว้นทั้งรายการ ไม่ใช่ตัดบางส่วน การเลือกเป็นการตัดสินใจด้านความเป็นส่วนตัวของผู้ปฏิบัติงาน: ชื่อที่ดูปลอดภัยอาจยังมีข้อมูลส่วนบุคคลได้ และขอบเขต/ตัวตรวจจับเหล่านี้ไม่ใช่เครื่องมือขัดข้อมูล PII ทั่วไป

### ขีดจำกัดการส่ง

คำขอถูกจำกัดไว้ที่ 500 span และ JSON UTF-8 ขนาด 4 MiB โดยรวม envelope ด้วย ทุก span ที่ได้รับอนุญาตจะถูกตรวจสอบขนาดก่อนคำขอแรกของ cursor batch หาก span แต่ละรายการมีขนาดเกินขีดจำกัด จะไม่มีการส่งส่วนใดของ batch นั้น และจะล้มเหลวพร้อมคำแนะนำให้ลด `maxBodyBytes` ไม่ใช่ถูกละทิ้งอย่างเงียบ ๆ preflight จะเก็บไว้เฉพาะการอ้างอิง record และจำนวนไบต์ โดยทิ้ง span/JSON ชั่วคราวแต่ละรายการ และจะสร้าง span ขึ้นใหม่สำหรับ chunk ที่มีขนาดอยู่ภายในขีดจำกัด แทนการเก็บสำเนา batch ที่ serialize แล้วอีกชุดหนึ่ง HTTP 408/429/5xx, ความล้มเหลวของเครือข่าย และ timeout จะลองใหม่ได้ไม่เกินสามครั้ง โดยใช้ exponential backoff ที่ 250/500 มิลลิวินาที `Retry-After` ที่ระบุเป็นวินาทีหรือวันที่ HTTP สามารถขยายเวลาหน่วงได้สูงสุด 5 วินาที สถานะอื่น ๆ จะล้มเหลวทันที การปฏิเสธบางส่วนของ OTLP 2xx ก็จะทำให้เกิดข้อผิดพลาดแทนการยืนยัน span ที่สูญหาย การตอบรับที่เป็น JSON ว่างหรือถูกต้องจะได้รับการยอมรับ โดยจำกัดการอ่านการตอบกลับไว้ที่ 64 KiB

ข้อผิดพลาดจะมีเฉพาะข้อเท็จจริงที่ exporter เป็นเจ้าของ ได้แก่ สถานะ HTTP, คลาสการลองใหม่, จำนวนครั้งที่พยายาม และจำนวน span ที่ส่ง หรือข้อความคงที่เกี่ยวกับการตอบรับ/เครือข่าย เนื้อหาการตอบกลับของ collector, จำนวนที่สำเร็จบางส่วน และส่วนหัวการตอบกลับจะไม่ถูกคัดลอกไปไว้ในข้อผิดพลาด log หรือแดชบอร์ด batch ที่ล้มเหลวหรือได้รับการยอมรับเพียงบางส่วนจะไม่ถูกยืนยัน: ปลายทางจะแสดงสถานะ Failing พร้อมสถานะดังกล่าว cursor จะคงอยู่ที่ batch ล่าสุดที่ได้รับการยืนยัน และการทำงานครั้งถัดไปจะส่งแถวเดิมอีกครั้ง สถานะถาวรจะยังคงล้มเหลวจนกว่าจะแก้ไข collector หรือการตั้งค่า ให้ใช้ log ของ collector เองเพื่อดูรายละเอียดการตอบกลับ สรุปข้อผิดพลาดใน call-log ยังคงมีการลบข้อมูลแยกต่างหาก  
`prepare()` จะไม่จัดเตรียมสิ่งใด Test จะโพสต์ `{"resourceSpans":[]}` อย่างตรงไปตรงมา และรายงานสถานะ HTTP โดยไม่เขียน span ของ call-log

Trace id และ span id คือเลขฐานสิบหก 32/16 ตัวแรกของ SHA-256 ที่คำนวณจาก `"omniroute.trace\\0" + callLogId` และ `"omniroute.span\\0" + callLogId` การส่งซ้ำจะใช้ id เดิม การทำเช่นนี้ไม่ใช่การรับประกันการขจัดข้อมูลซ้ำ: backend บางประเภท รวมถึงการรับข้อมูลของ Langfuse v4 จะไม่ขจัด span ที่มี id เดียวกัน ความล้มเหลวจากการหยุดทำงานหรือจาก chunk บางส่วนอาจทำให้ส่ง cursor batch ที่ยังไม่ได้รับการยืนยันซ้ำได้ไม่เกินหนึ่ง batch ทั้ง batch นั้นอาจถูกทำซ้ำ ไม่ใช่เฉพาะ HTTP chunk ล่าสุดเท่านั้น ควรเลือกขนาด cursor batch โดยคำนึงถึงข้อแลกเปลี่ยนนี้

### ตัวอย่าง Langfuse

กำหนดค่าฟิลด์เหล่านี้สำหรับอินสแตนซ์ Langfuse แบบ self-hosted:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

สร้างค่า Authorization ภายในเครื่องเป็น Base64 ของสตริง `public-key:secret-key` ตามตัวอักษร (เช่นใช้ `Buffer.from(publicKey + ":" + secretKey).toString("base64")`)  
อย่าวางข้อมูลรับรองจริงลงใน log ภาพหน้าจอ หรือ issue การแมปจะตั้งค่า `x-langfuse-ingestion-version: 4` โดยอัตโนมัติ ส่วน Authorization ยังคงต้องระบุใน `headers`  
ทั้งส่วนหัวและ salt ของ identity ที่สร้างขึ้นจะใช้กลไกฟิลด์ secret ที่เข้ารหัสและ API placeholder ที่มีอยู่ ต้องใช้ `STORAGE_ENCRYPTION_KEY`

การแมปจะเพิ่มประเภท/โมเดลของการสร้าง รายละเอียดการใช้งาน JSON (อินพุต/เอาต์พุต/ทั้งหมด และคีย์แคชที่พร้อมใช้งาน) สแนปช็อตอินพุต/เอาต์พุต JSON ระดับ ERROR/DEFAULT ข้อความสถานะที่ผ่านการทำความสะอาด ชื่อเทรซ รหัสเซสชัน สภาพแวดล้อมเพิ่มเติมที่เป็นตัวเลือก และ
`langfuse.observation.metadata.<key>` ที่สามารถใช้กรองได้สำหรับผู้ให้บริการ โมเดลที่ร้องขอ พาธ คอมโบ แหล่งที่มาของแคช และสถานะ `langfuse.observation.completion_start_time` จะเป็น ISO 8601 ณ เวลาเริ่มต้น + TTFT เฉพาะเมื่อทราบค่า TTFT และค่าอยู่ภายในระยะเวลาเท่านั้น จะไม่มีการส่งแอตทริบิวต์ต้นทุน

โหมดข้อมูลระบุตัวตนมีผลกับ `langfuse.user.id`:

- `pseudonymous` (ค่าเริ่มต้น): HMAC-SHA256 ของรหัสภายในของคีย์ API ด้วย salt ขนาด 32 ไบต์แบบสุ่มต่อปลายทาง Salt จะถูกสร้างเมื่อสร้าง หากยังไม่มี เข้ารหัสเป็น `identitySalt` จะไม่ถูกส่งกลับ และจะคงเดิมระหว่างการแก้ไข จะไม่มีการใส่รหัสคีย์ดิบลงในแอตทริบิวต์ของสแปน การสร้าง/หมุนเวียน salt ของปลายทางใหม่จะทำให้ข้อมูลระบุตัวตนเปลี่ยนไป
- `keyName`: ชื่อคีย์ API ที่กำหนดค่าไว้ ซึ่งจงใจเปิดเผยป้ายกำกับของผู้ดูแลระบบ
- `none`: ไม่มีรหัสผู้ใช้ แท็กเซสชันจะยังถูกส่งออกเมื่อมีอยู่ โหมดเหล่านี้ไม่ได้ทำให้เนื้อหาพรอมต์ที่กำหนดเองหรือป้ายกำกับเซสชัน/สหสัมพันธ์ที่ผู้ดูแลระบบระบุเป็นนิรนาม

### เริ่มต้นโดยไม่ทำ backfill

เฉพาะตอนสร้างเท่านั้น ให้เปิดใช้งาน **เริ่มจากตำแหน่งปัจจุบัน (ข้ามบันทึกที่มีอยู่)** หรือส่ง
`startFromCurrentPosition: true` ที่ระดับบนสุดของเพย์โหลด create API ระบบจะกำหนดค่าเริ่มต้นให้
`cursor_row_id` เป็นค่า rowid สูงสุดปัจจุบันของแถวบันทึกการเรียกที่ยังเก็บรักษาไว้ โดยใช้ตัวช่วยเคอร์เซอร์ที่มีอยู่ โดยไม่ต้องทำ migration ค่าเริ่มต้นคือ false (เคอร์เซอร์ 0 และทำ backfill ประวัติที่เก็บรักษาไว้)
การตั้งค่านี้ไม่ใช่การรีเซ็ตเคอร์เซอร์ขณะอัปเดต

การเพิ่ม `ttftMs` ที่ใช้ร่วมกันยังเพิ่มคอลัมน์ `ttft_ms` ที่เป็น nullable ให้กับตัวแมป BigQuery
และสคีมาของตารางใหม่ด้วย: การทดสอบสคีมาต้องการให้ทุกฟิลด์ของเรคอร์ดมาตรฐานมีคอลัมน์รองรับ ตารางที่มีอยู่จะยังส่งออกโดยไม่เปลี่ยนแปลง: `prepare()` จะอ่านสคีมาของตารางและละเว้นเฉพาะ `ttft_ms` เมื่อไม่มีคอลัมน์ดังกล่าว เพิ่มคอลัมน์ INT64 ที่เป็น nullable เพื่อรับค่า TTFT ในการทำงานครั้งถัดไป หรือใช้ตารางใหม่ คอลัมน์ TTFT ที่เป็นตัวเลือกจะไม่ทริกเกอร์การอัปเดตสคีมา คอลัมน์หลักฐานการใช้งานจะทำตามโฟลว์ความเข้ากันได้แบบมีเงื่อนไขและเลือกเปิดใช้งานตามด้านล่าง ส่วนฟิลด์แถวอื่น ๆ จะยังคงตรวจสอบสคีมาอย่างเข้มงวด

## 6. การเพิ่มปลายทาง

1. สร้าง `src/lib/logExport/destinations/<name>.ts` ที่ส่งออก `LogExportDestinationType`:
   โดยมี Zod `configSchema`, อาร์เรย์ตัวอธิบาย `fields` สำหรับ UI, `secretFields` และ
   `createClient(config)` ที่คืนค่า `test()` / `prepare()` / `send(records)`
2. เพิ่มลงในอาร์เรย์ `DESTINATIONS` ใน `src/lib/logExport/registry.ts`
3. เขียนการทดสอบไว้ใน `tests/unit/`

การเปลี่ยนแปลงทั้งหมดมีเพียงเท่านี้: การจัดเก็บข้อมูลถาวร, งาน cron, ชั้น REST, การเข้ารหัสข้อมูลลับ และ
แบบฟอร์มบนแดชบอร์ดล้วนอ่านข้อมูลจากรีจิสทรี

กฎสองข้อสำหรับปลายทางใหม่:

- `send()` **ต้องโยนข้อผิดพลาด** เมื่อเกิดความล้มเหลวบางส่วน การทำงานสำเร็จหมายถึง "ปลายทางมีแถวเหล่านี้แล้ว"
  และเคอร์เซอร์จะเลื่อนผ่านแถวเหล่านั้นไปอย่างถาวร
- ปลายทางที่รับ URL จากผู้ใช้ต้องตรวจสอบความถูกต้องผ่าน
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) ก่อนดึงข้อมูล
  เช่นเดียวกับเว็บฮุก BigQuery ไม่จำเป็นต้องทำเช่นนี้ เพราะโฮสต์ของ BigQuery เป็นค่าคงที่

## 7. การใช้งาน

- **แดชบอร์ด**: การผสานการทำงาน → การส่งออกบันทึก เพิ่มปลายทาง เรียกใช้ **Test** เพื่อตรวจสอบข้อมูลรับรอง
  โดยไม่เขียนแถว จากนั้นเปิดใช้งาน
- **รายการค้างดำเนินการ**: การ์ดปลายทางแต่ละรายการจะแสดงแถวที่รอดำเนินการและเคอร์เซอร์ ส่วน `GET
/api/log-export/status` จะแสดงตัวเลขเดียวกันพร้อมประวัติการทำงาน 20 รายการล่าสุด
- **ปลายทางที่ล้มเหลวจะไม่ทำให้ปลายทางอื่นล้มเหลว** — สรุปการทำงานจะบันทึกสถานะรายปลายทางไว้ใน
  `last_status` / `last_error` และประวัติการทำงานจะเก็บสถานะรวม
- **การลบปลายทางจะลบเคอร์เซอร์ของปลายทางนั้นด้วย** การเพิ่มปลายทางกลับมาใหม่จะเริ่มจาก
  บันทึกการเรียกใช้ที่เก่าที่สุดซึ่งยังเก็บรักษาไว้ ซึ่งจะส่งแถวที่ปลายทางอาจมีอยู่แล้วซ้ำอีกครั้ง สำหรับ BigQuery ค่า
  `insertId` ต่อแถวจะช่วยจัดการกรณีนี้ได้เฉพาะภายในช่วงเวลาการกำจัดข้อมูลซ้ำของ BigQuery เอง ดังนั้นควรปิดใช้งาน
  ปลายทางแทนการลบ

### ความเข้ากันได้ของสคีมาหลักฐานการใช้งาน

ตาราง BigQuery ใหม่จะมี `usage_evidence` ที่เป็นค่าว่างได้ (STRING ที่มี JSON) และ
`usage_estimated` (BOOL) เมื่อเปิดใช้ `autoCreate` ตารางที่มีอยู่แล้วจะได้รับเฉพาะคอลัมน์ที่เป็นค่าว่างได้เหล่านี้ซึ่งขาดหายไป
ตัวส่งออกจะคงสคีมาเดิมทั้งหมด รวมถึงข้อมูลเมตาของฟิลด์ และส่งคำขอ PATCH แบบมีเงื่อนไขโดยใช้ etag ที่ส่งกลับมา
การเปลี่ยนแปลงสคีมาพร้อมกันจะทำให้การส่งออกล้มเหลวแทนที่จะเขียนทับ และการทำงานครั้งถัดไปจะอ่านตารางอีกครั้ง

เมื่อปิดใช้ `autoCreate` ให้เพิ่มคอลัมน์เหล่านี้ด้วยตนเองก่อนส่งออกระเบียนที่มีหลักฐานการใช้งาน
หากไม่มีข้อมูลเมตาของสคีมา/etag หรือการอัปเดตล้มเหลว การแทรกข้อมูลที่มีหลักฐานก็จะไม่เกิดขึ้นด้วย เคอร์เซอร์การส่งออกจะไม่เลื่อนไปข้างหน้าเมื่อเกิดความล้มเหลวนั้น และหลักฐานจะไม่ถูกละทิ้งโดยไม่มีการแจ้งเตือน การเก็บรักษาบันทึกภายในเครื่องยังคงมีผลขณะที่การส่งออกถูกระงับ ดังนั้นให้แก้ไขความล้มเหลวก่อนที่แถวต้นทางที่ยังเก็บรักษาไว้จะหมดอายุ
