## เหตุใดจึงต้องมีแพ็กเกจ Workspace แยกต่างหาก?

`open-sse/` เป็น **workspace แบบสแตนด์อโลน** ใน monorepo ของ OmniRoute ด้วยเหตุผลหลายประการ:

1. **นำกลับมาใช้ใหม่ได้** — `open-sse` เผยแพร่เป็น `@omniroute/open-sse` บน npm ดังนั้นโปรเจกต์อื่นจึงสามารถใช้งานได้อย่างอิสระ
2. **ขอบเขตที่ชัดเจน** — เอนจินสตรีมมิงแยกออกจากเลเยอร์ UI/DB ที่เจาะจงสำหรับ OmniRoute
3. **ประสิทธิภาพ** — เอนจินไม่มี dependency ของ Next.js ทำให้เริ่มต้นแบบ cold start ได้เร็วขึ้นในบริบทของ CLI/serverless
4. **การกำหนดเวอร์ชัน** — `open-sse` สามารถออกรุ่นตามรอบของตนเองได้

```json
// package.json
"workspaces": ["open-sse"]
```

## ไปป์ไลน์คำขอ

คำขอ LLM ทุกคำขอไหลผ่าน **ไปป์ไลน์ 5 ขั้นตอน**:

```
                              ┌──────────────┐
   คำขอ HTTP                  │  1. กำหนดเส้นทาง │   การแก้ไข combo, การเลือกโมเดล
   (เส้นทาง Next.js)          └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. แปล      │   การแปลงรูปแบบ (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. ดำเนินการ │   ตัวดำเนินการของผู้ให้บริการ, HTTP, การลองใหม่, เบรกเกอร์
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. สตรีม    │   การแปลง SSE, backpressure
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. บันทึก   │   การติดตามการใช้งาน, บันทึกการเรียก, การจำแนกข้อผิดพลาด
                              └──────┬───────┘
                                     │
                                     ▼
                              การตอบกลับ HTTP (SSE หรือ JSON)
```

### ขั้นตอนที่ 1: กำหนดเส้นทาง (services/combo.ts)

**จุดเริ่มต้น**: `handleComboChat()` ใน `services/combo.ts`

แก้ไขคำขอให้เป็นทูเพิล `(provider, model, account, credentials)` ที่เป็นรูปธรรม:

- ค้นหา combo ตาม ID (หรือสร้าง combo เสมือนสำหรับโมเดล `auto/*`)
- ใช้กลยุทธ์การกำหนดเส้นทาง (ลำดับความสำคัญ แบบถ่วงน้ำหนัก round-robin เป็นต้น)
- กรองผู้ให้บริการที่ไม่พร้อมใช้งานออก (circuit breaker)
- เลือกเป้าหมายถัดไปที่ใช้งานได้

สำหรับโมเดล `auto/*` ขั้นตอนนี้ยังดำเนินการดังต่อไปนี้:

- เรียกใช้อัลกอริทึม **การให้คะแนน 16 ปัจจัย** (`services/autoCombo/`)
- เลือกคู่ `provider+model` ตามสถานะการทำงาน ต้นทุน เวลาแฝง เป็นต้น

### ขั้นตอนที่ 2: แปล (translator/)

หากรูปแบบต้นทาง (เช่น OpenAI) แตกต่างจากรูปแบบเป้าหมาย (เช่น Claude) คำขอจะถูก **แปล**:

- พรอมต์ระบบ → ข้อความระบบ
- นิยามเครื่องมือ → รูปแบบเครื่องมือเฉพาะของผู้ให้บริการ
- พารามิเตอร์การให้เหตุผล/การคิด → ค่าที่เทียบเท่าเฉพาะของผู้ให้บริการ
- การปรับบทบาทข้อความให้เป็นมาตรฐาน (`developer` → `system` สำหรับระบบที่ไม่ใช่ OpenAI)

`translator/index.ts` เปิดเผย:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### ขั้นตอนที่ 3: ดำเนินการ (executors/)

**จุดเริ่มต้น**: `getExecutor(providerId).execute(request, options)`

ผู้ให้บริการทั้งหมดใช้ `DefaultExecutor` (`executors/default.ts`) ผ่านกลไก fallback ของแฟกทอรี `getExecutor()` ตัวดำเนินการจะ:

- สร้าง URL ต้นทาง (`buildUrl()`)
- เพิ่มส่วนหัวเฉพาะของผู้ให้บริการ (`buildHeaders()`)
- แปลงเนื้อหาคำขอ (`transformRequest()`)
- ส่งคำขอ HTTP พร้อมการลองใหม่ + exponential backoff
- จัดการการรีเฟรชการยืนยันตัวตนหากจำเป็น (ผู้ให้บริการ OAuth)

ตัวดำเนินการทั้งหมดสืบทอดจาก `BaseExecutor` (`executors/base.ts`, 1170 LOC) ซึ่งมีความสามารถดังต่อไปนี้:

- ตรรกะการลองใหม่ที่ใช้ร่วมกัน
- การผสานรวมพร็อกซี
- การผสานรวม circuit breaker
- hook สำหรับบันทึกการใช้งาน

### ขั้นตอนที่ 4: สตรีม (utils/stream.ts)

สำหรับการตอบกลับแบบสตรีม ตัวดำเนินการจะคืนค่า **ReadableStream** ตัวจัดการจะ:

- ส่งผ่านตัวแปลง SSE (`createSSETransformStreamWithLogger`)
- ใช้ heartbeat ping เพื่อตรวจหาการเชื่อมต่อที่ขาดหาย
- จัดการการตัดการเชื่อมต่อของไคลเอนต์อย่างเหมาะสม (`pipeWithDisconnect`)
- แปลง SSE → JSON สำหรับไคลเอนต์ที่ไม่ใช้สตรีม

สำหรับการตอบกลับที่ไม่ใช่แบบสตรีม ตัวดำเนินการจะคืนค่าออบเจ็กต์ JSON ที่ผ่านการพาร์สแล้ว ซึ่งจะถูกส่งต่อโดยไม่มีการเปลี่ยนแปลง

### ขั้นตอนที่ 5: บันทึก (services/usage.ts)

หลังจากได้รับการตอบกลับ (ไม่ว่าจะสำเร็จหรือล้มเหลว) ระบบจะบันทึกข้อมูลการใช้งาน:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` จากการตอบกลับ
- `cost_usd` ที่คำนวณจากข้อมูลราคา
- `latency_ms`, `status`, `error_class` หากล้มเหลว
- จัดเก็บถาวรในตาราง `usage_history`

อาร์ติแฟกต์ของบันทึกการเรียกใช้ (หากเปิดใช้งาน) จะถูกเขียนไปยัง `${DATA_DIR}/call_logs/`

## เจาะลึกไฟล์สำคัญ

### chatCore.ts (5977 บรรทัด)

ที่** ตัวจัดการคำขอหลัก** . แม้จะมีขนาด แต่ก็มีโครงสร้างที่ชัดเจน:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

แม้ว่าจะเป็นงานใหญ่งานหนึ่ง แต่ก็จัดเป็น** ส่วนที่แสดงความคิดเห็น** ที่แมปกับไปป์ไลน์ 5 ขั้นตอน

### combo.ts (4456 LOC)

ที่** เครื่องยนต์กำหนดเส้นทาง** ที่แก้ไขคอมโบตามเป้าหมายที่ได้รับคำสั่ง

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

| ------------------- | ------------------------------------------------------------------------------------ |

| `weighted`          | ความน่าจะเป็นโดยน้ำหนักต่อเป้าหมาย                                                   |
| `round-robin`       | วนผ่านเป้าหมายตามลำดับ                                                               |
| `context-relay`     | ถ่ายทอดบริบทข้ามเป้าหมาย                                                             |
| `fill-first`        | เติมโควต้าก่อนย้ายไปหน้าถัดไป                                                        |
| `p2c`               | พลังของสองทางเลือก                                                                   |
| `random`            | เครื่องแบบสุ่ม                                                                       |
| `least-used`        | เลือกอันที่มีการใช้งานล่าสุดน้อยที่สุด                                               |
| `cost-optimized`    | เป้าหมายสุขภาพที่ถูกที่สุดก่อน                                                       |

### base.ts (1170 LOC)

ที่** ผู้ดำเนินการที่เป็นนามธรรม** ที่ทุกคลาสของตัวดำเนินการขยาย (โดยตรงหรือผ่าน `DefaultExecutor` และคลาสย่อยอื่น ๆ ) ประกอบด้วย:

- `buildUrl()` — การสร้าง URL เริ่มต้น (คลาสย่อยแทนที่สำหรับแบบกำหนดเอง)

- `transformRequest()` — พาสทรูตามค่าเริ่มต้น
- `execute()` — ลูป HTTP หลักที่มี retry/backoff/breaker

```ts

export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

````
## ผู้ดำเนินการ (150 โมดูล)

ส่วนใหญ่หนึ่งไฟล์ต่อผู้ให้บริการ คลาสตัวดำเนินการทั้งหมดขยาย `BaseExecutor` และแทนที่สิ่งที่แตกต่าง โมดูลอื่นๆ เป็นตัวช่วยต่อผู้ให้บริการ (สกีมาเครื่องมือ, อะแดปเตอร์ fetch/TTS, ตัวจัดการมุม)

### รูปแบบทั่วไป

ผู้ให้บริการได้รับการแก้ไขผ่าน `getExecutor(providerId)` ซึ่งจะส่งคืนตัวดำเนินการที่กำหนดค่าไว้ ผู้ให้บริการ OpenAI/Anthropic-compatible ใช้ `DefaultExecutor` (`executors/default.ts`) พฤติกรรมเฉพาะของผู้ให้บริการ (ฐาน URL, ส่วนหัวการตรวจสอบสิทธิ์, เวอร์ชัน API ) ได้รับการกำหนดค่าใน `open-sse/config/providers/` ในขณะที่การเปลี่ยนแปลงเนื้อหาคำขอได้รับการจัดการใน `open-sse/translator/`

**URL แบบกำหนดเอง** ถูกตั้งค่าผ่านการกำหนดค่าของผู้ให้บริการ:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**การรับรองความถูกต้องที่กำหนดเอง** ได้รับการจัดการผ่านการกำหนดค่าการตรวจสอบสิทธิ์ของรีจิสทรีของผู้ให้บริการ (คีย์API, OAuth, โปรไฟล์ส่วนหัว)

**เนื้อหาคำขอที่กำหนดเอง** การแปลง (เช่น Anthropic แยก `system` จาก `messages`) ได้รับการลงทะเบียนต่อผู้ให้บริการใน `open-sse/translator/`

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

ความละเอียดต้องผ่าน `ExecutorRegistry` (`executors/registry.ts`): ตัวดำเนินการพิเศษทุกตัวจะถูกประกาศในตารางในตัวของ `executors/index.ts` และลงทะเบียนผ่าน `registerExecutor(alias, instance)` เมื่อโหลดโมดูล `getExecutor()` จะปรึกษากับรีจิสทรีและกลับไปใช้ `DefaultExecutor` ที่บันทึกไว้สำหรับผู้ให้บริการใดๆ ที่ไม่มีรายการพิเศษ การแมปตัวเรียกทำงาน → นามแฝงแบบเต็มมีลักษณะเฉพาะด้วยการทดสอบทองคำ `tests/unit/executor-map-golden.test.ts`

## ตัวแปล

แปลระหว่าง **3 รูปแบบ** ได้แก่ OpenAI, Anthropic, Gemini รวมถึง Responses API ใหม่

### การแปลเกิดขึ้นเมื่อใด

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

การแปลที่พบบ่อย:

- `OpenAI → Anthropic`: แยกฟิลด์ `system` และใช้ส่วนหัว `x-api-key`
- `OpenAI → Gemini`: ใช้ `contents` แทน `messages` และใช้ `systemInstruction`
- `OpenAI → Responses API`: ใช้อาร์เรย์ `input` และสถานะ `previous_response_id`

### กรณีพิเศษที่รองรับ

- บทบาท `developer` → `system` สำหรับผู้ให้บริการที่ไม่ใช่ OpenAI
- บทบาท `system` → ผสานเข้ากับข้อความแรกของผู้ใช้สำหรับ GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` ของ Gemini
- `tools` → รูปแบบเครื่องมือเฉพาะของผู้ให้บริการ
- พารามิเตอร์การคิด (o1, Claude) → ค่าเทียบเท่าเฉพาะของผู้ให้บริการ

## เซิร์ฟเวอร์ MCP

`open-sse/mcp-server/` ใช้งานเซิร์ฟเวอร์ **Model Context Protocol**:

- **110 เครื่องมือ** (การจัดการผู้ให้บริการ, คอมโบ, หน่วยความจำ, แคช, การบีบอัด, พร็อกซี, ทักษะ, เกมมิฟิเคชัน, ปลั๊กอิน, Notion, Obsidian, คลังข้อมูลภายในเครื่อง)
- **3 ทรานสปอร์ต**: stdio, SSE, Streamable HTTP
- **33 ขอบเขตสิทธิ์** สำหรับการให้สิทธิ์แบบละเอียด

### การลงทะเบียนเครื่องมือ

เครื่องมือจะถูกลงทะเบียนเป็นไฟล์แยกใน `open-sse/mcp-server/tools/` โดยแต่ละไฟล์จะส่งออกชื่อ สคีมา ตัวจัดการ และขอบเขตสิทธิ์:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "รับสแนปช็อตสถานะความพร้อมของระบบ",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### ทรานสปอร์ต

```ts
// stdio (การใช้งานผ่าน CLI)
startMcpStdio(server);

// SSE (การสตรีมผ่าน HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP สมัยใหม่)
startMcpStreamable(server, port);
```

### การให้สิทธิ์

การเรียกใช้เครื่องมือทุกครั้งจะผ่านการตรวจสอบขอบเขตสิทธิ์ (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("ขอบเขตสิทธิ์ไม่เพียงพอ");
}
```

## ตัวแปลงรูปแบบ

`open-sse/transformer/` แปลงระหว่างรูปแบบ **Chat Completions** และ **Responses API**

### เหตุใดจึงต้องมีตัวแปลงแยกต่างหาก?

Responses API เป็นรูปแบบใหม่ของ OpenAI ที่มี **การสนทนาแบบเก็บสถานะ** (`previous_response_id`) เมื่อไคลเอนต์ส่งคำขอ Responses ทาง OmniRoute จะ:

1. แปลง Responses → Chat Completions ภายในระบบ
2. ส่งไปยังผู้ให้บริการ (ผู้ให้บริการใดก็ได้ที่รองรับ Chat Completions)
3. แปลงการตอบกลับกลับเป็นรูปแบบ Responses
4. สตรีมการตอบกลับที่แปลงแล้วไปยังไคลเอนต์

ตัวแปลง (`transformer/responsesTransformer.ts`) มีรายการต่อไปนี้:

```ts
createResponsesApiTransformStream(): TransformStream
```

ซึ่งรองรับ:

- เหตุการณ์ `response.output_item.added`
- เหตุการณ์ `response.output_text.delta`
- เหตุการณ์ `response.completed`
- การแมปการเรียกใช้เครื่องมือ (`function_call` ↔ `tool_calls`)

## รูปแบบที่ไม่ควรใช้

❌ **การเรียกฐานข้อมูลแบบซิงโครนัสใน `combo.ts`** — คำนวณล่วงหน้าและแคช
❌ **ตรรกะการลองใหม่ในตัวจัดการ** — ใช้ `retry()` จากบริการความยืดหยุ่น
❌ **การเข้าถึงการกำหนดค่าผู้ให้บริการโดยตรง** — ใช้ getter ของ `providerRegistry`
❌ **เชนสำรองที่ฮาร์ดโค้ดไว้** — กำหนดใน `modelFamilyFallback.ts`
❌ **การแก้ไขสถานะข้ามคำขอที่ทำงานพร้อมกัน** — ใช้เฉพาะบริบทที่มีขอบเขตระดับคำขอ

## การเพิ่มคอมโพเนนต์ใหม่

### การเพิ่มบริการใหม่

1. สร้าง `open-sse/services/[serviceName].ts` โดยมีหน้าที่เฉพาะเจาะจง
2. ส่งออกฟังก์ชันตัวจัดการหลักและค่าคงที่ต่าง ๆ
3. เพิ่มการทดสอบหน่วยใน `tests/unit/services/[serviceName].test.mjs`
4. ผสานรวมเข้ากับไปป์ไลน์คำขอใน `handlers/chatCore.ts` (หากเกี่ยวข้องกับการกำหนดเส้นทาง)
5. อัปเดตตรรกะการกำหนดเส้นทางใน `combo.ts` หากบริการมีผลต่อการเลือกเป้าหมาย
6. จัดทำเอกสารในไฟล์นี้

### การเพิ่มตัวดำเนินการใหม่

1. สร้าง `open-sse/executors/[provider].ts` โดยสืบทอดจาก `BaseExecutor`
2. ลงทะเบียนใน `config/providerRegistry.ts`
3. เพิ่มลงใน factory ของ `executors/index.ts`
4. เพิ่มการทดสอบหน่วยสำหรับตัวดำเนินการ
5. จัดทำเอกสารใน `docs/architecture/ARCHITECTURE.md`

### การเพิ่มเครื่องมือ MCP ใหม่

1. สร้างหรืออัปเดต `open-sse/mcp-server/tools/[category]Tools.ts`
2. กำหนดสคีมา Zod สำหรับอินพุต
3. ลงทะเบียนเครื่องมือใน `mcp-server/index.ts`
4. เพิ่มลงในเมทริกซ์ขอบเขตใน `mcp-server/auth/`
5. เพิ่มการทดสอบหน่วย
