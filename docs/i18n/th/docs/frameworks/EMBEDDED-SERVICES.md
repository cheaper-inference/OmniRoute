ทั้งแปดปฏิบัติตามรูปแบบการกำกับดูแลเดียวกัน:

- OmniRoute ติดตั้งภายใต้ `DATA_DIR/services/{name}/` (แยกจาก OmniRoute ของตัวเอง `package.json`)
- OmniRoute วางไข่และติดตามพวกมันเป็นกระบวนการลูก
- OmniRoute ฉีดคีย์ API ชั่วคราวลงในสภาพแวดล้อมของเด็กและหมุนโดยไม่มีการหยุดทำงาน (ถ้ามี)
- เส้นทางการจัดการทั้งหมด (`/api/services/*`) คือ**LOCAL_ONLY** — เข้าถึงได้จากลูปแบ็คเท่านั้น (กฎยาก #17)

### แกนพร็อกซีที่มีการจัดการ

ฟิลด์โฮสต์พร็อกซีแบบกำหนดเองยังยอมรับลิงก์ต้นทาง V2Ray อีกด้วย เลือก** กล่องร้องเพลง** หรือ** เอ็กซ์เรย์** อย่างชัดเจน จากนั้นคลิกบันทึก การพิมพ์จะไม่ดาวน์โหลดหรือเริ่มแกนหลัก บันทึกจะตรวจสอบไฟล์เก็บถาวรรีลีสอย่างเป็นทางการ ตรวจสอบการกำหนดค่าดั้งเดิม เริ่มฟังโลคัลโฮสต์ SOCKS ที่แตกต่างกัน จากนั้นจึงเขียนเฉพาะการมอบหมายรีจิสทรีพร็อกซี การเปิดใช้งานที่ล้มเหลวจะคืนค่าการกำหนดค่าและกระบวนการที่ได้รับการจัดการก่อนหน้านี้ จำเป็นต้องมี `STORAGE_ENCRYPTION_KEY` ; ลิงก์แหล่งที่มาถูกเข้ารหัส

ไฟล์ที่ได้รับการจัดการอยู่ภายใต้ `DATA_DIR/services/managed-proxy/` แยกจาก TPROXY มีหนึ่งกระบวนการที่เป็นเจ้าของต่อคอร์ที่เลือก โดยมี Listener สูงสุด 100 คน ไม่มีการเปลี่ยนแปลงการเริ่มต้นอัตโนมัติหรือค่าเริ่มต้นของเส้นทางทั่วโลก Successful Save จะจดจำการเปิดใช้งานสำหรับคอร์ที่ได้รับการจัดการนี้เท่านั้น การเริ่มต้นแอปพลิเคชันจะกู้คืนแกนที่บันทึกไว้ที่เปิดใช้งานโดยใช้ไบนารีที่ตรวจสอบแล้ว โดยไม่ต้องดาวน์โหลดเวลาบูต Explicit Stop ล้างค่าสถานะการเปิดใช้งานนั้น ไบนารีที่หายไปหรือเสียหายจำเป็นต้องบันทึกแหล่งที่มาอีกครั้ง การลบรีจิสทรีจะลบแหล่งที่มาและผู้ฟังในเครื่อง การแก้ไขจุดสิ้นสุดแบบธรรมดาจะถูกปฏิเสธสำหรับแถวที่ได้รับการจัดการ ดังนั้นแหล่งข้อมูลที่บันทึกไว้จึงไม่สามารถเบี่ยงเบนไปจาก Listener ที่กำหนดเส้นทางได้อย่างเงียบๆ

| รูปแบบแหล่งที่มา                      | กล่องร้องเพลง                                                     | เอ็กซ์เรย์                                                        |
| ------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| VLESS, VMess, โทรจัน, Shadowsocks URI | รองรับการแปลง                                                     | รองรับการแปลง                                                     |
| Hysteria2/hy2, TUIC, AnyTLS URI       | รองรับการแปลง                                                     | ถูกปฏิเสธ; ใช้แกนที่เข้ากันได้                                    |
| TCP/raw, WebSocket, gRPC, HTTPUpgrade | รองรับ VLESS/VMess/Trojan                                         | รองรับ VLESS/VMess/Trojan                                         |
| การขนส่ง XHTTP URI                    | ถูกปฏิเสธ                                                         | รองรับการแปลง                                                     |
| JSON ออกดั้งเดิม                      | พร็อกซีที่อนุญาตของคอร์ที่เลือก protocols/options ตรวจสอบแบบเนทีฟ | พร็อกซีที่อนุญาตของคอร์ที่เลือก protocols/options ตรวจสอบแบบเนทีฟ |

ตัวเลือกการโยงที่ไม่รู้จัก แฟล็ก TLS ที่ไม่ปลอดภัย ปลั๊กอินภายนอก ตัวเลือกพาธไฟล์ในเครื่อง และชุดค่าผสมที่ไม่รองรับจะถูกปฏิเสธ แทนที่จะละทิ้งอย่างเงียบๆ ออบเจ็กต์ดั้งเดิมเป็นคำจำกัดความขาออก ไม่ใช่การกำหนดค่าแบบคอร์ทั้งหมด ไม่ยอมรับขาออก control/direct/bypass WireGuard บน sing-box 1.14 ใช้จุดปลาย ดังนั้นจึงไม่ได้รับการยอมรับว่าเป็นขาออกดั้งเดิม นี่ไม่ใช่ตัวแปลงทุกรูปแบบ SSR, ลิงก์ whole-base64 Shadowsocks แบบเดิม, วัตถุ Clash ตามอำเภอใจ และรูปแบบการขนส่งที่ขาดหายไปจากตาราง จำเป็นต้องมีรูปแบบแหล่งที่มาที่รองรับแยกต่างหาก

`/api/services/managed-proxy` ได้รับการตรวจสอบสิทธิ์และวนกลับเท่านั้น: GET แสดงรายการข้อมูลเมตาที่แก้ไข, POST บันทึก `{core,name,sourceLink,id?,assignment?}`, PATCH ยอมรับ `{core,action:"start"|"stop"}` ต้องมีไปป์ไลน์เพียร์สแตมป์ที่เชื่อถือได้ของโฮสต์ การวินิจฉัยเนทิฟคอร์จะถูกระงับเนื่องจากสามารถมีข้อมูลประจำตัวได้ เหตุการณ์วงจรการใช้งานใช้ตัวบันทึกไฟล์แอปพลิเคชันที่มีโครงสร้างที่มีอยู่โดยไม่มีลิงก์ต้นทางหรือเพย์โหลดอัปสตรีม แนบเฉพาะบันทึกแอปพลิเคชันที่ผ่านการฆ่าเชื้อแล้วเพื่อรับการสนับสนุน เวอร์ชันอย่างเป็นทางการถูกปักหมุดไว้ที่ sing-box 1.14.3 และ Xray 26.3.27 พร้อมด้วย release-asset SHA-256 manifests; การอัปเดตในอนาคตจำเป็นต้องเปลี่ยนเวอร์ชันและไดเจสต์ที่ตรวจสอบแล้วทั้งหมดพร้อมกัน

## 2. สถาปัตยกรรม — 4 ชั้น

## 3. เครื่องสถานะวงจรชีวิต

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
         การตรวจสอบสุขภาพสำเร็จ   │         ขัดข้อง / SIGTERM    │
                               ┌────▼─────┐  (ออกภายใน 5 วินาที) │
                               │ running  │──── ขัดข้อง ─────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

สถานะจะถูกจัดเก็บในตาราง `version_manager` ของฐานข้อมูล (คอลัมน์ `status`) และทำสำเนา
ไว้ในสถานะในหน่วยความจำของ `ServiceSupervisor` สถานะในหน่วยความจำเป็นแหล่งข้อมูลหลักสำหรับ
กระบวนการที่กำลังทำงาน ส่วนสถานะในฐานข้อมูลเป็นข้อมูลสำรองแบบถาวรเมื่อบูต

### การเปลี่ยนสถานะ

| จาก             | เหตุการณ์                             | ไปยัง                         |
| --------------- | ------------------------------------- | ----------------------------- |
| `not_installed` | `install()` สำเร็จ                    | `stopped`                     |
| `stopped`       | มีการเรียก `start()`                  | `starting`                    |
| `starting`      | การตรวจสอบสุขภาพส่งคืน 200            | `running`                     |
| `starting`      | กระบวนการออกก่อนมีสถานะพร้อมใช้งาน    | `error`                       |
| `running`       | มีการเรียก `stop()`                   | `stopping` → `stopped`        |
| `running`       | กระบวนการออกโดยไม่คาดคิด (< 5 วินาที) | `error` (ขัดข้องอย่างรวดเร็ว) |
| `running`       | กระบวนการออกโดยไม่คาดคิด (> 5 วินาที) | `error`                       |
| `error`         | มีการเรียก `start()`                  | `starting`                    |
| สถานะใดๆ        | `stop()` ขณะอยู่ในสถานะ `stopping`    | ไม่ดำเนินการใดๆ               |

### ล็อกการดำเนินการ

`ServiceSupervisor` จัดลำดับการดำเนินการของวงจรชีวิตผ่านล็อกการดำเนินการแบบ async
(`withLock()`) การเรียก `start()` พร้อมกันบน supervisor เดียวกันจะทำให้เกิดการ spawn
เพียงหนึ่งครั้งเท่านั้น ผู้เรียกรายที่สองจะรอและส่งคืนสถานะที่มีอยู่ ซึ่งช่วยป้องกัน
race condition เช่น เมื่อการเริ่มต้นอัตโนมัติและปุ่มใน UI ถูกเรียกใช้พร้อมกัน

## 4. การอ้างอิง API

ทุกเส้นทางภายใต้ `/api/services/` คือ**LOCAL_ONLY** (เฉพาะลูปแบ็ค กฎยาก #17) คำขอแบบไม่มีลูปแบ็คจะได้รับ `403 LOCAL_ONLY` โดยไม่คำนึงถึงโทเค็นการตรวจสอบสิทธิ์

### 4.1 9 จุดสิ้นสุดเราเตอร์ (11 เส้นทาง)

#### `POST /api/services/9router/install`

ติดตั้ง 9Router จาก npm สร้าง `DATA_DIR/services/9router/` ด้วย `package.json` และ `node_modules/` ของตัวเอง ไม่ขัดแย้งกับ deps ของ OmniRoute

**ขอร่างกาย** (ไม่บังคับทั้งหมด):

```json
{ "version": "latest" }
```

| สนาม      | พิมพ์    | ค่าเริ่มต้น | คำอธิบาย                                  |
| --------- | -------- | ----------- | ----------------------------------------- |
| `version` | `string` | `"latest"`  | แท็กเวอร์ชัน npm หรือ semver ที่จะติดตั้ง |

**คำตอบ:**

| สถานะ | คำอธิบาย                                                          |
| ----- | ----------------------------------------------------------------- |
| `200` | `{ ok: true, installedVersion: "x.y.z", path: "..." }`            |
| `400` | เนื้อความคำขอไม่ถูกต้อง (การตรวจสอบ Zod ล้มเหลว)                  |
| `409` | ติดตั้งเรียบร้อยแล้ว (ล็อคไว้)                                    |
| `500` | การติดตั้ง npm ล้มเหลว — ดู `message` สำหรับข้อผิดพลาดที่เป็นมิตร |

**หมายเหตุ:** ใช้ `execFile('npm', [...])` — ไม่มีเชลล์ ไม่มีการแก้ไข (กฎยาก #13) ข้อผิดพลาด EACCES จะแสดงเป็นข้อความที่เป็นมิตร

#### `POST /api/services/9router/start`

| `200` | วัตถุ`ServiceStatus` (ดูสคีมาด้านล่าง)                       |
| `409` | 9ไม่ได้ติดตั้งเราเตอร์ (`status: "not_installed"`)           |
| `503` | การเริ่มต้นล้มเหลว (ข้อผิดพลาดของกระบวนการ — ดู `lastError`) |

**สคีมา ServiceStatus :**

```json
{
  "tool": "9router",
  "state": "running",
  "pid": 12345,
  "port": 20130,
  "health": "healthy",

```

**เนื้อหาคำขอ:** ไม่มี

**คำตอบ:**

| สถานะ | คำอธิบาย                            |
| ----- | ----------------------------------- |
| `200` | `ServiceStatus` (สถานะ: "หยุดแล้ว") |

### จุดสิ้นสุด 4.2 CLIProxyAPI (10 เส้นทาง)

CLIProxyAPI มีรูปร่างจุดสิ้นสุดเช่นเดียวกับ 9Router ลบ `rotate-key` บวก `accounts`, `provider-expose` และ `auto-restart-adopted` ตอนนี้ได้รับคีย์ data-plane API เฉพาะที่ฉีดเมื่อวางไข่ (`needsApiKey: true` ใน `bootstrap.ts` ใช้สำหรับการซิงค์โมเดล); `status` มีฟิลด์น้อยลง

| วิธี   | เส้นทาง                             | คำอธิบาย                             |
| ------ | ----------------------------------- | ------------------------------------ |
| `POST` | `/api/services/cliproxy/install`    | ติดตั้ง CLIProxyAPI จาก npm          |
| `POST` | `/api/services/cliproxy/start`      | เริ่ม CLIProxyAPI                    |
| `POST` | `/api/services/cliproxy/stop`       | หยุด CLIProxyAPI                     |
| `POST` | `/api/services/cliproxy/restart`    | รีสตาร์ท CLIProxyAPI                 |
| `POST` | `/api/services/cliproxy/update`     | อัปเดตเป็นเวอร์ชันที่ใหม่กว่า        |
| `GET`  | `/api/services/cliproxy/status`     | สถานะ + DB สด (ไม่มี `apiKeyMasked`) |
| `POST` | `/api/services/cliproxy/auto-start` | สลับการเริ่มต้นอัตโนมัติ             |

### 4.9 Reverse proxy (ฝังแดชบอร์ด 9Router)

แดชบอร์ดฝัง 9Router web UI ภายใน iframe ผ่านพร็อกซีย้อนกลับภายในที่:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

พร็อกซีนี้:

- ส่งต่อคำขอไปที่ `http://127.0.0.1:{port}/{path}` (เฉพาะลูปแบ็ค)
- ตัดส่วนหัว `cookie` และ `authorization` ที่เข้ามา (ไม่มีการรั่วไหลของเซสชัน OmniRoute )
- แทรก `Authorization: Bearer {apiKey}` สำหรับการตรวจสอบสิทธิ์ 9Router
- ตัด `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` จากการตอบกลับ
- เขียนการตอบสนอง HTML ใหม่เพื่อฉีด `<base href>` และทำให้เส้นทางสัมบูรณ์เป็นมาตรฐาน (`/foo` → `/dashboard/.../embed/foo`)

การอัพเกรด WebSocket สำหรับแดชบอร์ดแบบฝังได้รับการจัดการโดยเซิร์ฟเวอร์ที่แสดงร่วมบนพอร์ตเฉพาะ (ดู `src/lib/services/embedWsProxy.ts`)

**ความปลอดภัย:** เส้นทางพร็อกซีที่ฝังไว้จะถูกจัดประเภทภายใต้ `LOCAL_ONLY_API_PREFIXES` และสามารถเข้าถึงได้จากลูปแบ็คเท่านั้น ผู้โจมตีที่ได้รับ JWT ผ่านอุโมงค์ Cloudflare/Ngrok ไม่สามารถพร็อกซีในบริการที่ฝังตัวได้

## 5. ความปลอดภัย

### การบังคับใช้ LOCAL_ONLY (กฎตายตัว #17)

เส้นทางทั้งหมดภายใต้ `/api/services/` และ `/dashboard/providers/services/*/embed/` ถูก
จัดประเภทเป็น LOCAL_ONLY ใน `src/server/authz/routeGuard.ts` การตรวจสอบ loopback
จะทำงานโดยไม่มีเงื่อนไขก่อนเข้าสู่สาขาการยืนยันตัวตนใดๆ:

```
คำขอมาถึง
  → isLocalOnlyPath(path)?
      → ไม่ใช่ loopback → 403 LOCAL_ONLY (เสมอ ก่อนตรวจสอบการยืนยันตัวตน)
      → เป็น loopback  → ดำเนินการต่อไปยังการยืนยันตัวตนตามปกติ
```

การดำเนินการนี้ป้องกันไม่ให้ JWT ที่รั่วไหล (เช่น ผ่าน tunnel) เรียกใช้ `npm install` หรือ
สร้างโปรเซส โปรดดูเมทริกซ์ระดับทั้งหมดที่ `docs/security/ROUTE_GUARD_TIERS.md`

### การแทรก API key

9Router และ Mux ต้องใช้ API key/bearer token สำหรับ HTTP endpoint ของตนเอง
OmniRoute:

1. สร้างคีย์ผ่าน `crypto.randomBytes(32).toString("base64url")` โดยมี
   คำนำหน้าเฉพาะบริการ (`nr_` สำหรับ 9Router, `mx_` สำหรับ Mux)
2. เข้ารหัสคีย์ขณะจัดเก็บด้วย AES-256-GCM (cipher เดียวกับที่ใช้สำหรับข้อมูลรับรองของ provider)
3. ถอดรหัสและแทรกคีย์เป็น environment variable ขณะสร้างโปรเซส —
   `NINEROUTER_API_KEY` สำหรับ 9Router, `MUX_SERVER_AUTH_TOKEN` สำหรับ Mux (ไม่ใช้เป็น
   flag ของ CLI เพื่อไม่ให้ token ปรากฏใน `ps`/รายการโปรเซส)
4. ไม่ส่งคืนคีย์แบบ plaintext ใน HTTP response ใดๆ

CLIProxyAPI จะได้รับคีย์เฉพาะสำหรับ data plane ซึ่งถูกแทรกขณะสร้างโปรเซส
(`needsApiKey: true` — ใช้สำหรับซิงค์โมเดลกับ adapter)

### การป้องกัน SSRF

reverse HTTP proxy (`/dashboard/.../embed/[...path]`) ถูกกำหนดแบบตายตัวให้ส่งต่อ
ไปยัง `http://127.0.0.1:{port}` เท่านั้น โดยจะไม่ติดตาม redirect ไปยัง
ปลายทางที่ไม่ใช่ loopback ไลบรารี `ssrf-req-filter` ใช้เพื่อปฏิเสธ upstream URL ใดๆ ที่
resolve ไปยังตำแหน่งนอกช่วง loopback

### ความปลอดภัยของ shell (กฎตายตัว #13)

`npm install` ถูกเรียกใช้ผ่าน `execFile('npm', ['install', pkg, '--prefix', dir])` —
ไม่มี template literal, ไม่มี shell และไม่มีการแทรก path ภายนอกลงในสตริงคำสั่ง
ค่าขณะ runtime (port, API key) จะถูกส่งผ่านออบเจ็กต์ `env` ของ child

### การคัดกรองข้อผิดพลาด (กฎตายตัว #12)

error response ทั้งหมดจาก `/api/services/*` จะผ่าน `buildErrorBody()` หรือ
`sanitizeErrorMessage()` โดยจะไม่มีการส่งคืน `err.stack` และ `err.message` แบบดิบ
ไปยังผู้เรียกโดยตรง

## 6. การเพิ่มบริการแบบฝังตัวใหม่

ทำตาม 8 ขั้นตอนต่อไปนี้ โปรดอ่าน implementation ที่มีอยู่ใน `src/lib/services/installers/`
และ `src/app/api/services/` เพื่อใช้เป็นแหล่งอ้างอิงมาตรฐาน

### ขั้นตอนที่ 1 — สร้าง installer

สร้าง `src/lib/services/installers/{name}.ts` โดยใช้ `ninerouter.ts` เป็นต้นแบบ:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // เลือก port ที่ว่าง

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }

export async function getLatestVersion(): Promise<string | null> { ... }
```

ใช้ `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` จาก `installers/utils.ts`
— ห้ามใช้ `execSync` หรือการแทรกค่าผ่าน shell

### ขั้นตอนที่ 2 — ลงทะเบียนใน bootstrap

เพิ่ม `ServiceEntry` ลงในอาร์เรย์ `SERVICES` ใน `src/lib/services/bootstrap.ts`:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // ใช้ false หากไม่จำเป็นต้องมี API key
}
```

ขยาย `buildSpawnArgsFactory()` ให้รองรับ `cfg.tool === "myservice"`

#### สัญญา provider-plugin แบบเสียบเปลี่ยนได้ (ระยะที่ 1, #7333)

`src/lib/services/providerPlugins/` เพิ่มสัญญา `ServiceProviderPlugin` ซึ่ง
รวมฟิลด์ `ServiceEntry` จาก `bootstrap.ts` ของ backend และฟิลด์เทมเพลต manifest จาก
`serviceBackends.ts` ไว้ในออบเจ็กต์เดียว แทนที่จะนิยามโครงสร้างของ backend เดียวกัน
แยกกันอยู่ในสองไฟล์ที่ไม่เกี่ยวข้องกัน ณ ขณะที่เขียนนี้ **มีเพียง `9router` เท่านั้นที่
ย้ายแล้ว** — `bootstrap.ts` สร้างรายการใน `SERVICES[]` จาก
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`)
และจะ throw startup error หาก plugin หายไป ส่วน `cliproxy`, `mux` และ `bifrost`
ยังคงใช้ literal แบบ inline ใน `SERVICES[]` ที่มีอยู่เดิมโดยไม่มีการเปลี่ยนแปลง

`open-sse/config/providerPluginManifest.ts` ยังได้รับ helper แบบเพิ่มเติม
`createServiceBackendManifestEntry(pluginId, template)` ซึ่งสร้าง
`ProviderPluginManifestEntry` ที่มีรูปแบบถูกต้องจากรายการ `SERVICE_BACKEND_MANIFEST_TEMPLATE` —
ขณะนี้ helper ดังกล่าว **ยังไม่ได้** เชื่อมต่อเข้ากับเส้นทางคำขอที่ใช้งานจริงใดๆ (ทั้ง
`generateProviderPluginManifestFromRegistry()` และ `/v1/providers/[provider]/models`);
ส่วนนี้ยังคงเป็นงานติดตามผลหลังจากพิสูจน์สัญญานี้กับ backend รายที่สองแล้ว

งานที่เลื่อนไปยัง PR ติดตามผลและติดตามภายใต้ issue #7333 ได้แก่ การย้าย `cliproxyapi` ผ่าน
registry เดียวกัน, การทำให้ `mux`/`bifrost` เป็นรูปแบบทั่วไปใน union ของ
`ServiceBackendPluginId`, การรวมกรณีพิเศษของ executor routing
(`open-sse/executors/index.ts`, `open-sse/handlers/chatCore/executorProxy.ts`)
เข้าไว้ในสัญญา plugin และการเชื่อมต่อ `createServiceBackendManifestEntry()` เข้ากับ
เส้นทางโค้ด manifest/models ที่ใช้งานจริง

## 7. การแก้ไขปัญหา

### บริการไม่เริ่มทำงาน

**อาการ:** ปุ่มเริ่มทำงานส่งคืน 503 และสถานะยังคงเป็น `"error"` หรือ `"starting"`

**รายการตรวจสอบ:**

1. ตรวจสอบ `GET /api/services/{name}/logs` (หรือแผง Logs ในแดชบอร์ด) มองหา
   บรรทัดอย่างเช่น `Error: ENOENT`, `address already in use` หรือ `Cannot find module`
2. ตรวจสอบว่า `npm` อยู่ใน PATH: เรียกใช้ `which npm` จากบัญชีผู้ใช้เดียวกับที่ใช้เรียกใช้ OmniRoute
3. ตรวจสอบว่าบริการได้รับการติดตั้งแล้ว: ตรวจสอบ `GET /api/services/{name}/status` เพื่อดู
   `installedVersion` หากเป็น `null` ให้เรียกใช้การติดตั้งก่อน
4. ตรวจสอบว่า `DATA_DIR/services/{name}/node_modules/` มีอยู่และไม่ใช่ไดเรกทอรีว่าง
5. ตรวจสอบฟิลด์ `lastError` ในการตอบกลับสถานะเพื่อดูเหตุผลการออกจากโปรแกรมที่ผ่านการกรองข้อมูลสำคัญแล้ว

---

### การเริ่มต้นแบบ Cold Start ใช้เวลานาน (> 10 วินาทีกว่าจะถึงสถานะ `running`)

**อาการ:** สถานะยังคงเป็น `"starting"` เป็นเวลานานก่อนจะเปลี่ยนเป็น `"running"` หรือ `"error"`

**คำอธิบาย:** การเริ่มต้นแบบ Cold Start ของ 9Router รวมถึงการนำเข้าลำดับชั้นการพึ่งพาขนาดใหญ่ (โมดูล DNS,
tunnel และ MITM) ช่วงเวลาตรวจสอบสถานะเริ่มต้นคือ 2 วินาที โดยพยายาม 3 ครั้งก่อนที่
supervisor จะประกาศว่าหมดเวลา (แต่ยังคงตรวจสอบต่อไป)

**วิธีแก้ไข:** `healthIntervalMs` และระยะหมดเวลาของ `waitForHealthy`
(`healthIntervalMs * 3`) สามารถกำหนดค่าได้ใน `bootstrap.ts` สำหรับบริการที่ใช้เวลา
เริ่มต้นนานกว่านั้น ให้เพิ่ม `healthIntervalMs` เป็น 5000 และ `stopTimeoutMs` เป็น 30 000

---

### พอร์ตชนกัน (`EADDRINUSE`)

**อาการ:** บันทึกแสดง `address already in use :::20130`

**สาเหตุ:**

- มีกระบวนการอื่นกำลังใช้พอร์ต 20130 อยู่แล้ว
- กระบวนการ 9Router ก่อนหน้านี้หยุดทำงานไม่สมบูรณ์ (PID ซอมบี้)

**วิธีแก้ไข:**

1. เปลี่ยนพอร์ตเริ่มต้นผ่านตัวแปรสภาพแวดล้อม `NINEROUTER_PORT` ใน `.env`
2. ค้นหาและหยุดกระบวนการที่ขัดแย้งกัน: `lsof -ti :20130 | xargs kill -9`
3. สามารถกำหนดค่าพอร์ตแยกตามบริการได้ใน `bootstrap.ts` ผ่านฟิลด์ `port`

**หมายเหตุ:** 9Router ใช้พอร์ต 20130 เป็นค่าเริ่มต้นโดยเฉพาะเพื่อหลีกเลี่ยงการชนกับ
พอร์ตเริ่มต้น 20128 ของ OmniRoute

---

### สิทธิ์ถูกปฏิเสธ (EACCES) ระหว่างการติดตั้ง

**อาการ:** การติดตั้งส่งคืน 500 และบันทึกแสดง `EACCES` หรือ `permission denied`

**สาเหตุ:**

- กระบวนการ OmniRoute ไม่มีสิทธิ์เขียนไปยัง `DATA_DIR` หรือไดเรกทอรีแม่
- ทำงานภายใน Docker แบบ rootless โดยไม่มีสิทธิ์เขียนไปยังวอลุ่มที่แมปไว้

**วิธีแก้ไข:**

1. ตรวจสอบ `DATA_DIR` (ค่าเริ่มต้น: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. ตรวจสอบให้แน่ใจว่าผู้ใช้ของกระบวนการ OmniRoute เป็นเจ้าของไดเรกทอรี: `chown -R $USER ~/.omniroute/`
3. ใน Docker ให้ตรวจสอบว่าการเมานต์วอลุ่มมีสิทธิ์ที่ถูกต้องสำหรับผู้ใช้ในคอนเทนเนอร์

### การอัปเดตล้มเหลว (`npm install` หมดเวลาหรือเกิดข้อผิดพลาดของเครือข่าย)

**อาการ:** การอัปเดตส่งคืน 500 พร้อม `InstallError` และบันทึกแสดงว่าการเชื่อมต่อเครือข่ายหมดเวลา

**รายการตรวจสอบ:**

1. ยืนยันว่าเข้าถึงรีจิสทรี npm ได้: `npm ping`
2. ตรวจสอบพร็อกซีขององค์กร: `npm config get proxy`, `npm config get https-proxy`
3. ลองติดตั้งด้วยตนเอง: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`
4. หากอยู่หลังเครือข่ายแบบ air-gap ให้ดาวน์โหลด tarball ล่วงหน้าและใช้ `npm install /path/to/tarball.tgz`

### บริการแสดงสถานะ `"error"` ทันทีหลังเริ่มทำงาน (หยุดทำงานอย่างรวดเร็ว)

**อาการ:** สถานะเปลี่ยนจาก `"starting"` เป็น `"error"` ภายในเวลาไม่ถึง 5 วินาที
`lastError` แสดง `"Fast crash (exited with code 1)"`

**รายการตรวจสอบ:**

1. อ่านส่วนท้ายของบันทึกฉบับเต็ม: `GET /api/services/{name}/logs?tail=500`
2. สาเหตุทั่วไป: ไม่มีตัวแปรสภาพแวดล้อมที่บริการต้องใช้
3. สำหรับ 9Router: ตรวจสอบว่า `NINEROUTER_DISABLE_MITM=true` และ
   `NINEROUTER_DISABLE_TUNNEL=true` อยู่ในสภาพแวดล้อมที่ส่งผ่านเมื่อสร้างกระบวนการ (ดู
   `installers/ninerouter.ts` `resolveSpawnArgs`)

## 8. คำถามที่พบบ่อย

**ถาม: ฉันสามารถเปิดเผย endpoint ของบริการแบบฝังตัวให้ไคลเอนต์ที่ไม่ใช่ loopback เข้าถึงได้หรือไม่**

ไม่ได้ ระดับ LOCAL_ONLY ถูกกำหนดไว้โดยเจตนา (กฎตายตัวข้อ #17) Route ที่สามารถเรียกใช้
`npm install` หรือสร้างโปรเซส `node` ต้องไม่สามารถเข้าถึงได้จากทราฟฟิกที่ไม่ใช่ loopback
เพราะมิฉะนั้น JWT ที่รั่วไหลผ่าน tunnel (Cloudflare, Ngrok, Tailscale) จะทำให้
สามารถสร้างโปรเซสใดๆ ก็ได้ ไม่มีข้อยกเว้นให้ปิดใช้ข้อจำกัดนี้สำหรับ
`/api/services/` ซึ่งต่างจาก `/api/mcp/` ตรงที่ถูกยกเว้นออกจากรายการ bypass
ของ manage-scope ดู `docs/security/ROUTE_GUARD_TIERS.md`

---

**ถาม: 9Router และ CLIProxyAPI จะพร้อมใช้งานในการนำขึ้นใช้งานจริง/ระบบคลาวด์หรือไม่**

พร้อมใช้งาน ทั้งสองบริการใช้โมเดลที่เน้นการทำงานภายในเครื่องเป็นหลักเช่นเดียวกับ OmniRoute โดยทำงาน
บนเครื่องเดียวกันและสื่อสารกันผ่าน loopback ในที่นี้ "ระบบใช้งานจริง" หมายถึง VPS
หรือเซิร์ฟเวอร์ภายในเครื่องที่ติดตั้งใช้งาน OmniRoute ไม่ใช่ผู้ให้บริการคลาวด์ระยะไกล

---

**ถาม: ฉันจะดีบัก supervisor ได้อย่างไร**

1. ติดตามสตรีมล็อก SSE: `curl -N http://localhost:20128/api/services/9router/logs`
2. ตรวจสอบล็อกแบบมีโครงสร้างในเอาต์พุต pino ของ OmniRoute โดยกรองตาม namespace
   `service:supervisor`
3. ตรวจสอบแถวใน DB: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`
4. ใช้ `GET /api/services/9router/status` เพื่อดูสถานะปัจจุบันแบบสด, PID, สถานะสุขภาพ
   และ `lastError` ได้ในคำขอเดียว

---

**ถาม: supervisor แสดง `health: "degraded"` หรือ `health: "unknown"` แต่ state เป็น `"running"` นี่เป็นปัญหาหรือไม่**

`"degraded"` หมายความว่าการตรวจสอบสุขภาพได้รับการตอบกลับที่ไม่ใช่ 200 ส่วน `"unknown"` หมายความว่ายังไม่มี
การตรวจสอบใดเสร็จสิ้น (เกิด race กับการ poll ครั้งแรก) ทั้งสองสถานะเป็นเพียงชั่วคราวระหว่างการเริ่มต้นระบบ
หากสถานะสุขภาพยังคงเป็น `"degraded"` นานกว่า `healthIntervalMs * 3` ms หลังจาก
`"running"` แสดงว่าบริการแบบฝังตัวกำลังทำงานอยู่ แต่ HTTP API ไม่ตอบสนอง ให้ตรวจสอบ
ว่าพอร์ตในผลตอบกลับสถานะถูกต้องหรือไม่ และบริการกำลังรับฟังอยู่บนพอร์ตนั้นจริงหรือไม่

---

**ถาม: ฉันสามารถเปลี่ยน API key ของ 9Router โดยไม่ต้องรีสตาร์ตทั้งหมดได้หรือไม่**

ไม่ได้ API key จะถูกส่งให้ 9Router ผ่าน environment variable ขณะสร้างโปรเซส
ไม่สามารถเปลี่ยน environment variable ในโปรเซสที่กำลังทำงานอยู่ได้ `POST .../rotate-key`
จะหยุดและรีสตาร์ตบริการโดยอัตโนมัติเพื่อนำคีย์ใหม่ไปใช้ การหมุนเวียนคีย์
จะมีผลภายในระยะเวลา `stopTimeoutMs` ของบริการ (ค่าเริ่มต้น 15 s) บวกกับเวลา
เริ่มต้นระบบของบริการ

---

**ถาม: ขีดจำกัดของ ring buffer คือเท่าใด และจะเกิดอะไรขึ้นเมื่อเต็ม**

แต่ละบริการมี ring buffer เฉพาะขนาด 5 MB เมื่อบัฟเฟอร์เต็ม
บรรทัดล็อกที่เก่าที่สุดจะถูกนำออกเพื่อเพิ่มพื้นที่ให้บรรทัดใหม่ Event `snapshot` ของ SSE จะส่งคืน
บรรทัดล่าสุดภายในขีดจำกัด `tail` ล็อกจะไม่ถูกบันทึกลงดิสก์ เว้นแต่
จะกำหนด `logsBufferPath` ไว้ในแถวของ DB
