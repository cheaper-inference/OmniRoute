> **แหล่งข้อมูลหลัก:** `src/lib/plugins/` (`marketplace.ts`, `manager.ts`, `manifest.ts`,
> `scanner.ts`, `loader.ts`), `src/app/api/plugins/` และ
> `src/app/(dashboard)/dashboard/plugins/`
> **อัปเดตล่าสุด:** 2026-06-28 — v3.8.40

OmniRoute มาพร้อมระบบปลั๊กอินแบบ WordPress ปลั๊กอินแต่ละตัวเป็นไดเรกทอรีที่แยกเป็นอิสระ
โดยแต่ละไดเรกทอรีมีไฟล์แมนิเฟสต์ `plugin.json` และไฟล์เริ่มต้น ซึ่งเชื่อมต่อ
เข้ากับไปป์ไลน์คำขอ (`onRequest` / `onResponse` / `onError`) และ
เหตุการณ์วงจรชีวิต (`onInstall` / `onActivate` / `onDeactivate` / `onUninstall`)

**ตลาดปลั๊กอิน** เป็นเลเยอร์สำหรับการค้นหาและสำรวจที่อยู่บนระบบดังกล่าว
โดยนำเสนอแค็ตตาล็อกปลั๊กอินที่สามารถเรียกดูและติดตั้งได้ ตามค่าเริ่มต้น แค็ตตาล็อกจะเป็น
รีจิสทรีเริ่มต้นขนาดเล็กที่มีมาให้ในตัว ผู้ดูแลระบบสามารถกำหนดให้ใช้ URL ของรีจิสทรีระยะไกล
แบบกำหนดเองได้ ซึ่งในกรณีนี้ การดึงข้อมูลจะได้รับการป้องกันอย่างเข้มงวดด้วยตัวป้องกัน SSRF
ที่ตรวจสอบ DNS (ดู[ความปลอดภัย](#security))

ทุกเส้นทางของปลั๊กอินเป็นแบบ **เข้าถึงได้จากลูปแบ็กเท่านั้น** (ระดับ 1 — `LOCAL_ONLY`):
ปลั๊กอินจะโหลดและเรียกใช้โค้ดในโปรเซสลูก ดังนั้นเส้นทางเหล่านี้จึงไม่สามารถเข้าถึงได้
จากต้นทางที่ไม่ใช่ลูปแบ็ก ไม่ว่าการยืนยันตัวตนจะเป็นอย่างไรก็ตาม ดู
[`docs/security/ROUTE_GUARD_TIERS.md`](../security/ROUTE_GUARD_TIERS.md)

## มันเหมาะกับ Together อย่างไร

```
Dashboard (/dashboard/plugins)
  ├─ "Installed" tab  → GET /api/plugins            (listPlugins)
  │                     POST /api/plugins/scan      (pluginManager.scan)
  │                     POST /api/plugins/{name}/activate|deactivate
  │                     DELETE /api/plugins/{name}   (uninstall)
  └─ "Marketplace" tab → GET /api/plugins/marketplace
                          → listMarketplacePlugins()
                            ├─ no custom URL → built-in SEED_REGISTRY
                            └─ custom URL → isSafeMarketplaceUrl() SSRF guard
                                          → safeOutboundFetch(guard:"public-only")
```

- **เลเยอร์รีจิสทรี** — `src/lib/plugins/marketplace.ts`: แสดงรายการ / ค้นหาแค็ตตาล็อก โดยถอยกลับไปที่รีจิสตรีเริ่มต้นหากเกิดความล้มเหลวใดๆ
- **ชั้นวงจรชีวิต** — `src/lib/plugins/manager.ts` (`pluginManager` singleton): ติดตั้ง, อัปเกรด, เปิดใช้งาน, ปิดใช้งาน, ถอนการติดตั้ง, สแกน, โหลดเริ่มต้น
- **ปรากฏชั้น** — `src/lib/plugins/manifest.ts`: Zod schema + เป็นค่าเริ่มต้นสำหรับ `plugin.json`
- **เครื่องสแกน** — `src/lib/plugins/scanner.ts`: ค้นหาปลั๊กอินบนดิสก์ภายใต้ไดเร็กทอรีปลั๊กอิน
- **รถตักดิน** — `src/lib/plugins/loader.ts`: วางไข่แต่ละปลั๊กอินในกระบวนการย่อย Node.js ที่แยกจากกัน และโบรกเกอร์จะเรียกผ่าน IPC ลูกไม่ใช่แซนด์บ็อกซ์ (ดู "การแยกการดำเนินการปลั๊กอิน" ด้านล่าง)

## แค็ตตาล็อกตลาดปลั๊กอิน

`listMarketplacePlugins()` (`src/lib/plugins/marketplace.ts`) ส่งคืนรายการออบเจ็กต์
`MarketplaceEntry`:

| ฟิลด์         | ชนิด     | หมายเหตุ                                                |
| ------------- | -------- | ------------------------------------------------------- |
| `name`        | string   | ชื่อปลั๊กอินแบบ kebab-case                              |
| `version`     | string   | semver                                                  |
| `description` | string   | ข้อมูลสรุปสั้น ๆ                                        |
| `author`      | string   | ผู้เขียน / องค์กร                                       |
| `license`     | string   | รหัสสัญญาอนุญาตแบบ SPDX                                 |
| `downloadUrl` | string   | URL สำหรับดาวน์โหลดซอร์ส (อาจว่างเปล่า)                 |
| `repository`  | string?  | URL ของรีโพซิทอรีซึ่งระบุหรือไม่ก็ได้                   |
| `tags`        | string[] | แท็กสำหรับค้นหา/กรอง                                    |
| `downloads`   | number   | จำนวนการดาวน์โหลด                                       |
| `rating`      | number   | 0–5                                                     |
| `verified`    | boolean  | ระบุว่ารายการได้รับการทำเครื่องหมายว่ายืนยันแล้วหรือไม่ |
| `lastUpdated` | string   | สตริงวันที่ในรูปแบบคล้าย ISO                            |

เมื่อไม่ได้กำหนด URL ของรีจิสทรีแบบกำหนดเอง แค็ตตาล็อกจะใช้
`SEED_REGISTRY` ที่มีมาให้ในตัว (ปัจจุบันประกอบด้วย `request-logger`, `rate-limiter`,
`cost-tracker` และ `theme-manager`) รีจิสทรีเริ่มต้นพร้อมใช้งานเสมอ หากรีจิสทรีระยะไกล
ที่กำหนดค่าไว้ไม่สามารถเข้าถึงได้ ส่งคืนสถานะที่ไม่ใช่ `200` หรือส่งคืนเนื้อหา
ที่ระบบไม่รู้จัก `listMarketplacePlugins()` จะบันทึกคำเตือนและกลับไปใช้รายการเริ่มต้น

> หมายเหตุ: **แค็ตตาล็อก** ตลาดปลั๊กอิน (เรียกดู/ค้นหา) เชื่อมต่อการทำงานครบถ้วนตั้งแต่ต้นจนจบแล้ว แต่
> การ**ติดตั้ง**จากแค็ตตาล็อกด้วยคลิกเดียวยังไม่ได้รับการพัฒนา ปุ่ม "ติดตั้ง"
> บนรายการในตลาดปลั๊กอินของแดชบอร์ดจะแสดงข้อความว่า "เร็ว ๆ นี้" ในขณะนี้
> การติดตั้งปัจจุบันดำเนินการผ่านโฟลว์การติดตั้งจากพาธภายในเครื่อง
> (`POST /api/plugins`) และการค้นหาบนดิสก์ (`POST /api/plugins/scan`)

## REST API

จุดสิ้นสุดทั้งหมดต้องมีการตรวจสอบสิทธิ์การจัดการ (`requireManagementAuth`)** และ** เป็น — `/api/plugins` และ `/api/plugins/` เท่านั้นที่แสดงอยู่ใน `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`)

| จุดสิ้นสุด                         | วิธี   | คำอธิบาย                                                   |
| ---------------------------------- | ------ | ---------------------------------------------------------- |
| `/api/plugins`                     | GET    | แสดงรายการปลั๊กอินที่ติดตั้ง (ตัวกรอง `?status=` เสริม)    |
| `/api/plugins`                     | POST   | ติดตั้งปลั๊กอินจากไดเร็กทอรีแหล่งที่มาของปลั๊กอิน          |
| `/api/plugins/scan`                | POST   | สแกนไดเร็กทอรีปลั๊กอินและลงทะเบียนปลั๊กอินใหม่             |
| `/api/plugins/marketplace`         | GET    | แสดงรายการแคตตาล็อกตลาด                                    |
| `/api/plugins/marketplace/install` | POST   | ติดตั้งปลั๊กอิน Marketplace ตามชื่อ                        |
| `/api/plugins/[name]`              | GET    | รับรายละเอียดปลั๊กอินที่ติดตั้ง                            |
| `/api/plugins/[name]`              | DELETE | ถอนการติดตั้งปลั๊กอิน                                      |
| `/api/plugins/[name]/activate`     | POST   | เปิดใช้งาน (โหลดตะขอลงทะเบียน + )                          |
| `/api/plugins/[name]/deactivate`   | POST   | ปิดการใช้งาน (ยิง `onDeactivate` ยกเลิกการลงทะเบียน hooks) |
| `/api/plugins/[name]/config`       | GET    | รับปลั๊กอิน config + config schema                         |
| `/api/plugins/[name]/config`       | PUT    | อัปเดตการกำหนดค่าปลั๊กอิน (ตรวจสอบกับสคีมา)                |

ตัวกรอง `GET /api/plugins` `status` ยอมรับหนึ่งใน `installed` / `active` / `inactive` / `error` ค่าที่ไม่ถูกต้องส่งคืน `400`

### แสดงรายการปลั๊กอินที่ติดตั้ง

```bash
curl http://localhost:20128/api/plugins \
  -H "Cookie: auth_token=..."
```

### ติดตั้งจากเส้นทางท้องถิ่น

```bash
curl -X POST http://localhost:20128/api/plugins \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{ "path": "/absolute/path/to/my-plugin" }'
```

`path` จะต้องเป็น** แน่นอน** เส้นทางไปยังไดเร็กทอรี** ภายในไดเรกทอรีแหล่งที่มาของปลั๊กอิน** : `plugin-sources` ถัดจากรูทปลั๊กอิน ดังนั้น `~/.omniroute/plugin-sources/` เป็นค่าเริ่มต้น หรือ `<parent of OMNIROUTE_PLUGINS_DIR>/plugin-sources/` เมื่อตั้งค่าตัวแปรนั้น (`getPluginSourcesDir()` ใน `src/lib/plugins/installSource.ts`) คัดลอกหรือโคลนปลั๊กอินที่นั่นก่อน การติดตั้งถูกปฏิเสธด้วย `400` เมื่อพาธมี `..` หรือไบต์ว่าง อยู่นอกไดเร็กทอรีนั้น แก้ไขภายนอกไดเร็กทอรีผ่าน symlink มี symlink ซึ่งเป้าหมายอยู่ภายนอก หรือเมื่อไม่มีไดเร็กทอรี ไดเร็กทอรีต้นทางต้องมี `plugin.json` ที่ถูกต้อง (หรือเป็นพาเรนต์ของไดเร็กทอรี) เมื่อประสบความสำเร็จ การตอบสนองจะเป็น `201` พร้อมกับแถวปลั๊กอินที่ติดตั้งไว้

ไม่เหมือนกับเส้นทางปลั๊กอินอื่นๆ เส้นทางนี้ต้องใช้ข้อมูลรับรองการจัดการ (เซสชันแดชบอร์ดหรือคีย์ API ที่มีขอบเขตการจัดการ) แม้ว่าการเข้าสู่ระบบจะถูกปิดใช้งาน (`requireLogin=false`): การติดตั้งโค้ดจะไม่เป็นการกระทำที่ไม่เปิดเผยตัวตน เช่นเดียวกับ `POST /api/plugins/marketplace/install` (body `{ "name": "<plugin>" }`)

### เรียกดูตลาด

```bash
curl http://localhost:20128/api/plugins/marketplace \
  -H "Cookie: auth_token=..."
```

### อัปเดตการกำหนดค่าปลั๊กอิน

```bash
curl -X PUT http://localhost:20128/api/plugins/my-plugin/config \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{ "config": { "level": "debug", "maxItems": 100 } }'
```

`PUT .../config` ตรวจสอบเนื้อหากับ `configSchema` ของปลั๊กอิน (ประกาศในรายการ) ด้วย `validatePluginConfig()` จาก `src/lib/plugins/manifest.ts`: ทุกคีย์จะต้องประกาศในสคีมา ค่าจะต้องตรงกับประเภทที่ประกาศ ฟิลด์ `number` ให้เกียรติ `min`/`max` และฟิลด์ `select` จะต้องตรงกับ `enum` ที่ประกาศ การละเมิดใดๆ จะส่งคืน `400` และไม่มีสิ่งใดถูกเก็บไว้ ปลั๊กอินที่ประกาศว่าไม่มี `configSchema` ไม่มีคีย์ที่กำหนดค่าได้ ดังนั้นคำขอจึงถูกปฏิเสธด้วย `400` ("ปลั๊กอินไม่ได้ประกาศคีย์ที่กำหนดค่าได้ใดๆ")

## การกำหนดค่า

### ไดเรกทอรีปลั๊กอิน

ปลั๊กอินอยู่ภายใต้ไดเรกทอรีข้อมูลของ OmniRoute:

```
~/.omniroute/plugins/<plugin-name>/
  ├─ plugin.json
  └─ index.js          # (หรือไฟล์ใดก็ตามที่ manifest.main ชี้ไป)
```

`getDefaultPluginDir()` (`src/lib/plugins/scanner.ts`) จะกำหนดไดเรกทอรีดังกล่าวตาม
สามขั้นตอน:

1. **`OMNIROUTE_PLUGINS_DIR`** เมื่อมีการตั้งค่า — ใช้ค่าตามที่ระบุโดยตรง ไม่ว่า `HOME` จะเป็นค่าใด นี่คือ
   ตัวเลือกที่กำหนดอย่างชัดเจนสำหรับ Docker/K8s ซึ่งโครงสร้างปลั๊กอินจะถูก bind mount ไว้ที่พาธ
   ซึ่งโดยปกติไม่เกี่ยวข้องกับไดเรกทอรี home ของคอนเทนเนอร์ (#11827)
2. `<home>/.omniroute/plugins` โดย `<home>` มาจากตัวแปรสภาพแวดล้อม `HOME` / `USERPROFILE`
3. `/tmp/.omniroute/plugins` เมื่อโปรเซสไม่ได้ export ค่า home ใดๆ เลย

ไดเรกทอรีที่กำหนดได้จะถูกบันทึกใน log หนึ่งครั้งเมื่อเริ่มต้นระบบในชื่อ `scanner.dir_resolved` โดยระบุ
อินพุตที่ถูกเลือก (`OMNIROUTE_PLUGINS_DIR`, `home` หรือ `no-home-fallback`) — ดังนั้น image
ที่ไปใช้ขั้นตอนที่ 3 โดยไม่มีการแจ้งเตือนจะแสดงข้อมูลดังกล่าว แทนที่จะรายงานเพียงว่ารายการปลั๊กอินว่างเปล่า
`POST /api/plugins/scan` จะค้นหาไดเรกทอรีย่อยทั้งหมดในตำแหน่งนั้นซึ่งมี
`plugin.json` ที่ถูกต้องและลงทะเบียนไดเรกทอรีเหล่านั้น ไดเรกทอรีเดียวกันนี้ยังเป็น root ที่
`pluginManager.install()` ใช้คัดลอกปลั๊กอินเข้าไป ดังนั้นการ override จะย้ายทั้งตำแหน่งการค้นหาและ
การติดตั้งไปด้วยกัน

> **`OMNIROUTE_PLUGINS_DIR` ไม่ใช่ `OMNIROUTE_PLUGIN_PATH`** ตัวแปรหลังจะถูกอ่านเฉพาะโดย
> ตัวโหลด command-plugin ของ CLI (`bin/cli/plugins.mjs`) เพื่อค้นหาแพ็กเกจ npm `omniroute-cmd-*`
> ที่เพิ่มคำสั่งย่อยให้กับ `omniroute` — ตัวแปรนี้ไม่มีผลต่อ runtime scanner

## ความปลอดภัย

### เส้นทางระดับ — loopback เท่านั้น

ปลั๊กอินรันโค้ดในกระบวนการลูกที่เกิด ดังนั้นพื้นผิว `/api/plugins` ทั้งหมดจึงถูกจัดประเภทเป็น `LOCAL_ONLY` (ระดับ 1) การบังคับใช้แบบวนกลับทำงานโดยไม่มีเงื่อนไข** ก่อน** การตรวจสอบการรับรองความถูกต้อง ดังนั้นโทเค็นการจัดการที่รั่วไหลไปถึงกล่องเหนืออุโมงค์ยังคงไม่สามารถติดตั้ง เปิดใช้งาน หรือถอนการติดตั้งปลั๊กอินได้ ดู [`docs/security/ROUTE_GUARD_TIERS.md`](../security/ROUTE_GUARD_TIERS.md) และ Hard Rules #15 / #17

### ยาม SSRF รีจิสทรีของ Marketplace

URL รีจิสทรีแบบกำหนดเองคือการกำหนดค่าที่มีอิทธิพลต่อผู้โจมตี ดังนั้นก่อนที่จะดึงข้อมูล `listMarketplacePlugins()` จะรันผ่านสองชั้น:

1. **`isSafeMarketplaceUrl(url)`** (`src/lib/plugins/marketplace.ts`):
   - ปฏิเสธสิ่งใดก็ตามที่ไม่ใช่ `http:` / `https:`
   - ปฏิเสธโฮสต์ private/loopback/link-local/ULA ตามตัวอักษร (IPv4** และ** IPv6 รวมถึง IPv4-mapped) ผ่าน canonical `isPrivateHost` (`src/shared/network/outboundUrlGuard.ts`)
   - แก้ไข** ทั้งคู่** `A` และ `AAAA` จะบันทึกและปฏิเสธ if** ใดๆ** ที่อยู่ที่ได้รับการแก้ไขคือ — ส่วนตัวที่ปิดชื่อโฮสต์สาธารณะ → บายพาส IP ส่วนตัว
   - **ปิดไม่สำเร็จ** : ความล้มเหลวในการแก้ไข DNS จะปฏิเสธ URL
2. **`safeOutboundFetch(url, { guard: "public-only", timeoutMs: 5000 })`** (`src/shared/network/safeOutboundFetch.ts`): ใช้ URL guard แบบสาธารณะเท่านั้นอีกครั้งในเวลาดึงข้อมูลและ** บล็อกการเปลี่ยนเส้นทาง** (ไม่มี → สาธารณะ `30x` pivot ส่วนตัว)

URL ที่ล้มเหลวในเลเยอร์ใดเลเยอร์หนึ่งจะไม่ยกเลิกคำขอ — ตลาดจะถอยกลับไปยังรีจิสทรีเริ่มต้นในตัวและบันทึกคำเตือน

> การป้องกันนี้ได้รับการเสริมความแข็งแกร่งใน PR #3774 โดยเฉพาะเพื่อแก้ไข A + AAAA และใช้ `isPrivateHost` แบบบัญญัติแทนการตรวจสอบ IPv4-only

### การแยกการดำเนินการปลั๊กอิน

> **ปลั๊กอินจะไม่ถูกแซนด์บ็อกซ์ตามค่าเริ่มต้น** ลูกเป็นกระบวนการ Node.js ทั่วไปที่ทำงานในฐานะผู้ใช้ OmniRoute โดยไม่มีบริบท VM และไม่มีแฟล็กการอนุญาต Node.js ดังนั้นโค้ดปลั๊กอินจึงสามารถอ่านและเขียนไฟล์ใดๆ ที่ผู้ใช้สามารถดำเนินการได้ รันโปรแกรม และเข้าถึงเครือข่าย `requires.permissions` ตัดสินใจเท่านั้นว่าตัวแปรสภาพแวดล้อมใดที่เด็กจะได้รับ สิทธิ์อื่น ๆ จะไม่ถูกบังคับใช้ การตั้งค่าสถานะคุณลักษณะ `PLUGIN_PERMISSION_MODEL_ENABLED` ที่เลือกใช้ (ปิดโดยค่าเริ่มต้น) จะเรียกใช้แต่ละปลั๊กอินภายใต้รูปแบบการอนุญาต Node.js ที่สร้างขึ้นจากการอนุญาตเหล่านั้น ยกเว้น `network` ซึ่ง Node.js ไม่สามารถจำกัดได้ (ดู [`PLUGIN_SDK.md`](./PLUGIN_SDK.md#%E0%B8%A3%E0%B8%B0%E0%B8%9A%E0%B8%9A%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%AD%E0%B8%99%E0%B8%B8%E0%B8%8D%E0%B8%B2%E0%B8%95) ) ติดตั้งปลั๊กอินที่คุณเชื่อถือเท่านั้น ขอบเขตกระบวนการด้านล่างประกอบด้วยข้อขัดข้องและแฮงค์ มันไม่ใช่ขอบเขตความปลอดภัย

- **การแยกกระบวนการ** — `loadPlugin()` (`src/lib/plugins/loader.ts`) วางไข่แต่ละปลั๊กอินในกระบวนการลูก Node.js แยกกันและสื่อสารผ่าน IPC การโทรแบบ Hook มีการหมดเวลาโดยมีการยกระดับ `SIGTERM` → `SIGKILL`
- **รายการที่อนุญาตของ Env** — ลูกจะได้รับเฉพาะชุดตัวแปรสภาพแวดล้อมที่อนุญาตเท่านั้น ชุดที่กว้างขึ้นจะได้รับก็ต่อเมื่อรายการร้องขอสิทธิ์ `env`
- **ติดตั้งการกักเก็บแหล่งที่มา** — `POST /api/plugins` อ่านจากไดเรกทอรีแหล่งที่มาของปลั๊กอินเท่านั้น (ดู "ติดตั้งจากเส้นทางในเครื่อง"): เส้นทางถูกกำหนดให้เป็นมาตรฐานด้วย `realpath` ต้องอยู่ภายในไดเรกทอรีนั้นอย่างเคร่งครัด และแผนผังต้นทางที่มี symlink ที่หลบหนีจะถูกปฏิเสธก่อนที่จะคัดลอกสิ่งใดๆ
- **การควบคุมเส้นทาง** — install/upgrade/uninstall ยืนยันว่าไดเร็กทอรีปลั๊กอินและ `manifest.main` แก้ไขได้** ภายใน** รูทปลั๊กอินที่ได้รับการจัดการก่อนที่จะคัดลอกหรือลบแบบเรียกซ้ำ (ป้องกันเส้นทาง DB ที่ถูกดัดแปลงและ `../` traversal ใน `manifest.main`) การเปิดใช้งานแก้ไข symlink ผ่าน `realpath` และปฏิเสธที่จะโหลดจุดเริ่มต้นที่หนีจากไดเร็กทอรีปลั๊กอิน
- **พินความสมบูรณ์เสริม** — รายการอาจประกาศฟิลด์ `integrity` (`sha256-<base64>`, SRI format) เมื่อมีอยู่ ตัวโหลดจะตรวจสอบแฮชของไฟล์รายการ ณ เวลาโหลด และปฏิเสธที่จะเปิดใช้งานเมื่อไม่ตรงกัน เป็นการเลือกใช้การตรวจจับการงัดแงะ** ไม่** ขอบเขตความปลอดภัย: ไม่จำกัดสิ่งที่ปลั๊กอินที่โหลดสามารถทำได้
- **ไม่มีข้อมูลรับรองไคลเอ็นต์ใน hooks** — บริบทที่ส่งผ่านไปยัง `onRequest`, `onResponse` และ `onError` มีส่วนหัว `authorization`, `x-api-key`, `proxy-authorization` และ `cookie` ถูกลบออก และบันทึกคีย์ API ไม่มีค่าคีย์ (`redactPluginContext()` ใน `src/lib/plugins/hooks.ts`)

## ลำดับวงจรชีวิต

```
install (POST /api/plugins, path)
  → สแกน/ตรวจสอบ manifest → คัดลอกไปยัง staging → ยืนยันว่า main อยู่ภายในไดเรกทอรี
  → เปลี่ยนชื่อแบบ atomic ไปยัง ~/.omniroute/plugins/<name> → เพิ่มแถวในฐานข้อมูล
  → เรียกใช้ onInstall → หาก enabledByDefault: activate

activate (POST /api/plugins/{name}/activate)
  → ตรวจสอบการอยู่ภายในขอบเขตด้วย realpath → loadPlugin() (สร้าง child process)
  → ลงทะเบียน hooks ที่ประกาศไว้ → status = "active" → เรียกใช้ onActivate

deactivate (POST /api/plugins/{name}/deactivate)
  → เรียกใช้ onDeactivate (ก่อนยกเลิกการลงทะเบียน) → ยกเลิกการลงทะเบียน hooks
  → ปิด child process → status = "inactive"

uninstall (DELETE /api/plugins/{name})
  → deactivate หาก active → เรียกใช้ onUninstall
  → ลบไดเรกทอรีปลั๊กอินแบบ recursive โดยตรวจสอบขอบเขต → ลบแถวในฐานข้อมูล
```

การเรียกใช้ `install` ซ้ำกับไดเรกทอรีที่มีเวอร์ชันใน manifest **ใหม่กว่าอย่างเคร่งครัด**
เมื่อเทียบกับเวอร์ชันที่ติดตั้งไว้ จะอัปเกรดโดยอัตโนมัติ (ติดตั้งใหม่ทั้งหมด โดยรีเซ็ต config
เป็นค่าเริ่มต้น) เวอร์ชันที่เท่ากันหรือเก่ากว่าจะถูกปฏิเสธ

เมตริก/การวิเคราะห์ของปลั๊กอินจะถูกติดตามในตารางเพิ่มเติม
(`090_plugin_metrics.sql`, `091_plugin_analytics.sql`)

## แดชบอร์ด

หน้าแดชบอร์ดที่ `/dashboard/plugins` (`src/app/(dashboard)/dashboard/plugins/page.tsx`) มีสองแท็บ:

- **ติดตั้งแล้ว** — แสดงรายการปลั๊กอินที่ติดตั้งพร้อมกับ hooks ที่ประกาศไว้ การสลับ activate/deactivate ปุ่มถอนการติดตั้ง และการดำเนินการ "สแกนหาปลั๊กอิน" (`POST /api/plugins/scan`)
- **ตลาด** — แสดงแค็ตตาล็อกจาก `GET /api/plugins/marketplace` พร้อมฟิลด์เพื่อตั้งค่ารีจิสทรีที่กำหนดเอง URL

หน้านี้จะแสดงคำเตือนเสมอว่าปลั๊กอินทำงานด้วยสิทธิ์เต็มของกระบวนการ OmniRoute

หน้าการกำหนดค่าต่อปลั๊กอินอยู่ที่ `/dashboard/plugins/[name]/config` (`src/app/(dashboard)/dashboard/plugins/[name]/config/page.tsx`)
