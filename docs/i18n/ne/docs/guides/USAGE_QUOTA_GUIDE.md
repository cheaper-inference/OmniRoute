> **संक्षेपमा**: OmniRoute ले प्रत्येक अनुरोधको टोकन प्रयोग ट्र्याक गर्छ, लागत गणना गर्छ, प्रत्येक API कुञ्जीको कोटा लागू गर्छ, र ड्यासबोर्डमा विश्लेषण देखाउँछ। यो गाइडले यी सबै कसरी काम गर्छन् भनेर व्याख्या गर्छ।

**स्रोतहरू:**

- `open-sse/services/usage.ts` (~70KB) — मुख्य प्रयोग ट्र्याकिङ
- `src/lib/usageAnalytics.ts` (~10KB) — ड्यासबोर्डका लागि एकत्रीकरण
- `src/lib/db/quotaSnapshots.ts` — ऐतिहासिक कोटा डेटा
- `src/lib/db/usage*.ts` — प्रयोगसँग सम्बन्धित विभिन्न DB मोड्युलहरू

## अवलोकन

OmniRoute मार्फत प्रवाहित हुने प्रत्येक अनुरोधले एउटा **प्रयोग रेकर्ड** उत्पन्न गर्छ, जसले निम्न कुराहरू समेट्छ:

- **पहिचान**: कुन API कुञ्जी, प्रदायक, मोडेल, कम्बो
- **टोकनहरू**: प्रम्प्ट टोकनहरू, कम्प्लिसन टोकनहरू, क्यास गरिएका टोकनहरू, कुल
- **लागत**: USD रकम (मूल्य निर्धारण डेटाबाट गणना गरिएको)
- **समय**: विलम्बता, सुरु/अन्त्यका टाइमस्ट्याम्पहरू
- **स्थिति**: सफल, त्रुटि, दर-सीमित, आदि।

यी रेकर्डहरूलाई **विश्लेषण** मा एकत्रित गरिन्छ, **कोटा स्न्यापसटहरू** का रूपमा स्थायी रूपमा भण्डारण गरिन्छ, र **प्रत्येक कुञ्जीका बजेट सीमाहरू** लागू गर्न प्रयोग गरिन्छ।

```
अनुरोध ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    विश्लेषण    कोटा    बिलिङ
                    (ड्यासबोर्ड) (लागू)  (निर्यात)
```

## के रेकर्ड गरिन्छ

`usage.ts` सेवाले हरेक अनुरोधका लागि एउटा **प्रयोग घटना** सङ्कलन गर्छ:

| फिल्ड              | प्रकार  | स्रोत                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | रेकर्ड गर्दा उत्पन्न गरिएको UUID                           |
| `apiKeyId`         | string  | अनुरोध सुरु गर्ने API कुञ्जी                               |
| `provider`         | string  | प्रदायक ID (openai, anthropic, आदि)                        |
| `model`            | string  | मोडेल ID (gpt-5, claude-opus-4-6, आदि)                     |
| `comboId`          | string? | कम्बोमार्फत राउट गरिएको भए कम्बो ID                        |
| `promptTokens`     | number  | अपस्ट्रिम प्रतिक्रियाबाट                                   |
| `completionTokens` | number  | अपस्ट्रिम प्रतिक्रियाबाट                                   |
| `cachedTokens`     | number  | क्यास हिट टोकनहरू (Anthropic प्रम्प्ट क्यासिङ, आदि)        |
| `totalTokens`      | number  | प्रम्प्ट + पूर्णता                                         |
| `costUsd`          | number  | मूल्य निर्धारण डेटाबाट गणना गरिएको                         |
| `latencyMs`        | number  | अनुरोधको सुरुदेखि अन्त्यसम्मको अवधि                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | स्थिति != success भए त्रुटि वर्ग                           |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | प्लगइनद्वारा थपिएको अनुकूलित डेटा                          |

### टोकनहरू कहाँबाट आउँछन्

टोकनहरू **प्रतिक्रिया ह्यान्डलर** मा अपस्ट्रिम प्रदायकको प्रतिक्रियाबाट निकालिन्छन्:

```ts
// open-sse/handlers/chatCore.ts बाट
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

प्रयोग विवरण नफर्काउने प्रदायकहरूका लागि (केही वेब-कुकी प्रदायकहरू), OmniRoute ले `~4 chars per token` अनुमान विधि प्रयोग गरेर टोकनहरूको **अनुमान** गर्छ (`open-sse/services/autoCombo/pipelineRouter.ts` हेर्नुहोस्)।

### क्यास गरिएका टोकनहरू

OmniRoute ले `cached_tokens` लाई `prompt_tokens` बाट छुट्टै ट्र्याक गर्छ किनभने:

- Anthropic प्रम्प्ट क्यासिङले क्यास गरिएका टोकनहरूका लागि कम दरमा शुल्क लिन्छ (सामान्य दरको 10%)
- केही प्रदायकहरूले `cache_read_input_tokens` फर्काउँछन्, जसको मूल्य फरक तरिकाले निर्धारण गर्नुपर्छ
- विश्लेषणले **क्यास हिट दर** = `cached_tokens / prompt_tokens` देखाउन सक्छ

### क्यास-लेखन तहको निदान

विश्लेषण ड्यासबोर्डको प्रम्प्ट-क्यास स्वास्थ्य प्यानलले प्रदायकले रिपोर्ट गरेका
5-मिनेट र 1-घण्टाका क्यास लेखनहरू छुट्याउँछ। Anthropic का
`usage.cache_creation.ephemeral_5m_input_tokens` र
`usage.cache_creation.ephemeral_1h_input_tokens` लाई स्ट्रिमिङ र
गैर-स्ट्रिमिङ प्रयोग विवरण रूपान्तरणका क्रममा कायम राखिन्छ र कल-लग सारांशहरूसँग भण्डारण गरिन्छ। संयुक्त
क्यास-लेखन कुललाई ती समूहहरूमा दोस्रो पटक थपिँदैन।

पुराना रेकर्डहरूसहित, संयुक्त लेखन काउन्टर मात्र भएका कलहरूको तह अज्ञात
हुन्छ। आंशिक विभाजनमा नछुट्याइएको बाँकी अंश अज्ञात नै रहन्छ; अमान्य वा
बाझिएका काउन्टरहरूलाई चुपचाप TTL तोक्नुको सट्टा चिन्ह लगाइन्छ। अनुरोधतर्फका
TTL चिह्नहरू बिल लगाइएको तहको प्रमाण होइनन्।

प्यानलको API-समतुल्य लेखन अनुमानले रिपोर्ट गरिएका, मूल्य तोकिएका तहहरू मात्र समेट्छ,
सम्पूर्ण अनुरोधलाई होइन। नेटिभ Claude/Anthropic मोडेलको मूल्य निर्धारणका लागि यसले
5-मिनेटका लेखनहरूमा इनपुट दरको 1.25 गुणा र 1-घण्टाका लेखनहरूमा इनपुट दरको दोब्बर प्रयोग गर्छ। मूल्य निर्धारण
नभएको अवस्थामा त्यो अनुपलब्ध हुन्छ, शून्य होइन। प्रत्येक नयाँ कल लग गर्दा मूल्यहरू सङ्कलन गरिन्छन्;
पुराना रेकर्डहरूको मूल्य पुनः निर्धारण गरिँदैन। त्यसैले सदस्यता खाताहरूमा
त्यो रकम नगद खर्च वा सदस्यता कोटामा नलागीकनै API-समतुल्य
अनुमान हुन सक्छ। विद्यमान कोटा, बजेट र प्रदायकको ठ्याक्कै लागतका गणनाहरू अपरिवर्तित छन्।

यी निदानहरूले विद्यमान सीमित क्यास-स्वास्थ्य सारांश र कल-लग
प्रतिधारण प्रयोग गर्छन्। यिनले अनुरोधका पूर्वनिर्धारित TTL, राउटिङ वा खाता चयन परिवर्तन गर्दैनन्।
प्रदायकलाई पठाउने सीमाबिन्दुमा क्लाइन्टले अनुरोध गरेको TTL र प्रभावकारी बहिर्गमन TTL सङ्कलन गर्ने काम
पछि सारिएको छ; यो प्यानलले प्राप्ति विवरणका तहहरू रिपोर्ट गर्छ, प्रभावकारी बहिर्गमन TTL होइन।

कार्यान्वयन: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, र `open-sse/utils/cacheWriteUsage.ts`।

## लागत गणना

लागतहरू LiteLLM बाट सिंक गरिएको **मूल्य निर्धारण डेटा** (`src/lib/pricingSync.ts`) बाट गणना गरिन्छ:

| मोडेल             | इनपुट $/1M | आउटपुट $/1M | क्यास गरिएको $/1M |
| ----------------- | ---------- | ----------- | ----------------- |
| gpt-5             | $2.50      | $10.00      | —                 |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50             |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30             |
| gemini-2.5-pro    | $1.25      | $10.00      | —                 |

लागत सूत्र (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **प्रम्प्टबाट क्यास गरिएको भाग किन घटाइन्छ?** क्यास गरिएको भागको मूल्य छुट्टै निर्धारण गरिन्छ; सम्पूर्ण प्रम्प्टमा इनपुट मूल्य लगाउँदा लागत बढी गणना हुन्छ।

### मूल्य निर्धारण सिंक

मूल्य निर्धारण डेटा `/api/pricing/sync` एन्डपोइन्टमार्फत LiteLLM बाट स्वतः सिंक हुन्छ (यो बिल्ट-इन cron कार्यद्वारा ट्रिगर हुन्छ, प्रयोगकर्ताले प्रयोग गर्ने env var द्वारा होइन):

```bash
# म्यानुअल रूपमा ट्रिगर गर्नुहोस्
curl -X POST http://localhost:20128/api/pricing/sync
```

मूल्य निर्धारण डेटा नभएका मोडेलहरूका लागि, OmniRoute ले आन्तरिक औसत दरहरू (LiteLLM को मूल्य निर्धारण डेटाबाट लिइएको) प्रयोग गरेर **लागत अनुमान** गर्छ।

## मिति दायरा एकत्रीकरण

`usageAnalytics.ts` मोड्युलले कच्चा उपयोग डेटाबाट ड्यासबोर्ड विजेटहरू गणना गर्छ। यसले 7 समय दायराहरू समर्थन गर्छ:

| दायरा    | अवधि                             | प्रयोगको अवस्था                          |
| -------- | -------------------------------- | ---------------------------------------- |
| `1d`     | पछिल्ला 24 घण्टा                 | घण्टागत लागतमा अचानक वृद्धि पत्ता लगाउने |
| `7d`     | पछिल्ला 7 दिन                    | साप्ताहिक समीक्षा                        |
| `30d`    | पछिल्ला 30 दिन                   | मासिक बिलिङ                              |
| `90d`    | पछिल्ला 90 दिन                   | त्रैमासिक विश्लेषण                       |
| `ytd`    | चालु वर्षको जनवरी 1 देखि         | वार्षिक बजेट अनुगमन                      |
| `all`    | सम्पूर्ण अवधि                    | सम्पूर्ण अवधिका तथ्याङ्क                 |
| `custom` | प्रयोगकर्ताले तोकेको सुरु/अन्त्य | लेखापरीक्षण, तदर्थ क्वेरीहरू             |

### गणना गरिने ड्यासबोर्ड विजेटहरू

कुनै पनि मिति दायराका लागि, एनालिटिक्स तहले निम्न गणना गर्छ:

| विजेट                     | विवरण                                                  |
| ------------------------- | ------------------------------------------------------ |
| **सारांश कार्डहरू**       | कुल अनुरोधहरू, कुल लागत, कुल टोकनहरू, सफलता दर         |
| **दैनिक प्रवृत्ति चार्ट** | प्रतिदिन लागत + टोकनहरू, मोडेलअनुसार तहबद्ध            |
| **गतिविधि हिटम्याप**      | दिनको घण्टा × हप्ताको दिनको ग्रिड, रङ = अनुरोध सङ्ख्या |
| **मोडेलअनुसार विवरण**     | मोडेलअनुसार लागतको पाई चार्ट                           |
| **प्रदायकअनुसार विवरण**   | प्रदायकअनुसार अनुरोधहरूको बार चार्ट                    |
| **शीर्ष API कुञ्जीहरू**   | लागतअनुसार शीर्ष 10 कुञ्जीहरूको तालिका                 |
| **त्रुटि विश्लेषण**       | समयअनुसार त्रुटि दर, प्रमुख त्रुटि वर्गहरू             |

### प्रोग्राममार्फत पहुँच

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // उपयोग इतिहासका रेकर्डहरू
  "7d",                 // समय दायरा: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // प्रदायक जडान नक्सा (connectionId → खाताको नाम)
  {
    startDate: "2025-01-01",  // ऐच्छिक: "custom" दायराका लागि
    endDate: "2025-06-01",   // ऐच्छिक: "custom" दायराका लागि
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (सेन्ट)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## कोटा लागू गर्ने प्रक्रिया

प्रत्येक API कुञ्जीको कोटा दुई ठाउँमा लागू गरिन्छ:

1. **नरम सीमा** (`quotaWarnAt`): उपयोगले तोकिएको सीमा नाघ्दा ड्यासबोर्डमा चेतावनी
2. **कडा सीमा** (`quotaLimit`): सीमा नाघ्दा HTTP 429 सहित अनुरोध अस्वीकार गरिन्छ

### कन्फिगरेसन

```ts
// प्रत्येक API कुञ्जीका लागि
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — चेतावनी देखाउनुहोस्
  quotaLimit: 10_00,    // $10.00 — पूर्ण रोक
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### लागू गर्ने प्रवाह

```
अनुरोध ──▶ quotaCheck()
              │
              ├── सीमाभित्र छ?  ──▶ अनुमति दिनुहोस्
              │
              └── सीमा नाघ्यो?  ──▶ 429 अत्यधिक अनुरोधहरू
                                   Retry-After हेडरसहित
```

### कोटा स्न्यापसटहरू

`quotaSnapshots` तालिकाले प्रवृत्ति विश्लेषणका लागि **कोटाको ऐतिहासिक अवस्था** भण्डारण गर्छ:

| फिल्ड | विवरण |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | अनुगमन गरिँदै गरेको कुञ्जी |
| `window` | "दिन" | "हप्ता" | "महिना" |
| `used` | यस अवधिमा प्रयोग भएको लागत (सेन्ट) |
| `limit` | सीमा (सेन्ट) |
| `resetAt` | अवधि रिसेट हुने समय |
| `createdAt` | स्न्यापसट लिइएको समय |

लागत > 0 हुने **हरेक अनुरोधमा** स्न्यापसट लिइन्छ, र तिनलाई निम्न कार्यमा प्रयोग गरिन्छ:

- ड्यासबोर्डमा कोटा प्रगति पट्टी देखाउन
- 30-दिने कोटा प्रवृत्ति चार्टहरू देखाउन
- उपयोग सीमाको नजिक पुग्दा सतर्कता सक्रिय गर्न

## अवधारण र सरसफाइ

प्रत्येक अनुरोधसँगै प्रयोगसम्बन्धी डेटा ~1-10KB ले बढ्छ। ठूलो परिमाणमा यो उल्लेखनीय हुन सक्छ।

### अवधारण सेटिङहरू

प्रयोग इतिहासको अवधारण UI मा रहेको डेटाबेस सेटिङहरू वा `/api/settings/database` मार्फत कन्फिगर गरिन्छ।

पूर्वनिर्धारित रूपमा, प्रयोग इतिहास **90 दिन** सम्म राखिन्छ।

### सरसफाइ

पुराना अभिलेखहरू `src/lib/db/cleanup.ts` द्वारा हटाइन्छन्:

- पृष्ठभूमिमा चल्ने cron प्रक्रियाद्वारा सुरु गरिन्छ
- `usage_history` बाट कन्फिगर गरिएको `usageHistory` अवधारण सेटिङभन्दा पुराना अभिलेखहरू मेटाउँछ

### भण्डारण अनुमान

| अनुरोध दर          | 30-दिने भण्डारण | 90-दिने भण्डारण |
| ------------------ | --------------- | --------------- |
| 100 अनुरोध/दिन     | ~3MB            | ~9MB            |
| 1,000 अनुरोध/दिन   | ~30MB           | ~90MB           |
| 10,000 अनुरोध/दिन  | ~300MB          | ~900MB          |
| 100,000 अनुरोध/दिन | ~3GB            | ~9GB            |

अत्यधिक ट्राफिकका लागि, यी विकल्पहरू विचार गर्नुहोस्:

- डेटाबेस सेटिङहरूमार्फत अवधारण अवधि घटाउने
- कच्चा अभिलेखहरूको सट्टा `aggregated_metrics` प्रयोग गर्ने (विश्लेषणका लागि मात्र)

### 1. उपयुक्त मोडेल प्रयोग गर्नुहोस्

Anthropic प्रम्प्ट क्यासिङले **दोहोरिने सन्दर्भमा 90% बचत गर्छ**:

```ts
// क्यासिङ स्वतः हुन्छ — उही ठूलो सिस्टम प्रम्प्ट समावेश गर्नुहोस्
const response = await openai.chat({
  model: "claude-sonnet-4-5",
```

RTK + Caveman कम्प्रेसनले **धेरै टुल प्रयोग हुने सत्रहरूमा 15-95% बचत गर्छ**:

```ts
const config = {
  compression: {
    engine: "rtk",

  },
};
```

अनियन्त्रित खर्च रोक्न सधैँ `quotaLimit` तोक्नुहोस्:


API कीअनुसार समूहबद्ध गर्न र लागतअनुसार क्रमबद्ध गर्न ड्यासबोर्ड वा **`/api/usage/analytics`** प्रयोग गर्नुहोस्:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## समस्या निवारण

### "लागत अपेक्षाभन्दा बढी छ"

1. **`/api/usage/analytics?groupBy=model`** जाँच गर्नुहोस् — महँगो मोडेल पत्ता लगाउनुहोस्
2. **`/api/usage/analytics?groupBy=apiKey`** जाँच गर्नुहोस् — धेरै खपत गर्ने पत्ता लगाउनुहोस्
3. मूल्यसम्बन्धी डेटा अद्यावधिक छ भनी पुष्टि गर्नुहोस्: `POST /api/pricing/sync`

### "रेकर्डहरू हराइरहेका छन्"

- ड्यासबोर्ड → डाटाबेस → सफाइ अन्तर्गत DB डेटा राख्ने अवधिका सेटिङहरू जाँच गर्नुहोस् — आवधिक सफाइ कार्यले पुराना रेकर्डहरू मेटाउँछ (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts` मा त्रुटिहरू जाँच गर्नुहोस् — DB मा लेख्न असफल भएका घटनाहरू लग गरिन्छन् तर देखाइँदैनन्
- अनुरोध वास्तवमै `chatCore` मा पुगेको छ भनी पुष्टि गर्नुहोस् — कम्बो राउटिङ जाँच गर्नुहोस्

### "कोटा लागू भइरहेको छैन"

- कीको `quotaLimit` सेटिङ जाँच गर्नुहोस्
- `quotaWindow` सही रूपमा सेट गरिएको छ भनी पुष्टि गर्नुहोस्
- `quotaSnapshots` रेकर्डहरू खोज्नुहोस् — ती प्रत्येक अनुरोधमा सिर्जना हुनुपर्छ
