> **TL;DR**: OmniRoute ले आफ्नो प्राथमिक भण्डारका रूपमा **WAL journaling सहितको SQLite** प्रयोग गर्छ, र संवेदनशील फिल्डहरूका लागि स्थिर अवस्थामा **AES-256-GCM** इन्क्रिप्सन प्रयोग गर्छ। यस गाइडले स्किमा, माइग्रेसन, ब्याकअप/रिकभरी, र सञ्चालनसम्बन्धी रनबुकहरू समेट्छ।

**स्रोतहरू:**

- `src/lib/db/core.ts` — singleton + SCHEMA_SQL (17 आधारभूत तालिकाहरू)
- `src/lib/db/migrationRunner.ts` — संस्करणयुक्त माइग्रेसनहरू
- `src/lib/db/migrations/` — 167 संस्करणयुक्त SQL फाइलहरू
- `src/lib/db/encryption.ts` — इन्क्रिप्सन सहायकहरू
- `src/lib/db/backup.ts` — ब्याकअप निर्यात/आयात
- `src/lib/db/healthCheck.ts` — स्वास्थ्य निदान

## SQLite किन?

OmniRoute ले PostgreSQL/MySQL को सट्टा SQLite रोज्नुका धेरै कारणहरू छन्:

| पक्ष              | SQLite                                | PostgreSQL                         |
| ----------------- | ------------------------------------- | ---------------------------------- |
| **डिप्लोयमेन्ट**  | एम्बेडेड — छुट्टै सर्भर आवश्यक पर्दैन | सर्भर सेटअप आवश्यक पर्छ            |
| **इन्क्रिप्सन**   | एप्लिकेसन-स्तर (AES-256-GCM)          | बिल्ट-इन TDE                       |
| **कार्यसम्पादन**  | साना/मध्यम कार्यभारका लागि छिटो       | अत्यधिक समवर्ती लेखनका लागि राम्रो |
| **समवर्तिता**     | WAL मोडले समवर्ती पठन सम्भव बनाउँछ    | पूर्ण MVCC                         |
| **ब्याकअप**       | एकल-फाइल प्रतिलिपि                    | `pg_dump` वा फाइलसिस्टम स्न्यापसट  |
| **प्रयोग अवस्था** | प्रति-प्रयोगकर्ता स्थापना, एम्बेडेड   | बहु-टेनेन्ट SaaS                   |

**एकल-प्रयोगकर्ता, एकल-इन्स्ट्यान्स** डिप्लोयमेन्टहरूका लागि (OmniRoute को प्राथमिक प्रयोग अवस्था), SQLite अझ सरल र छिटो छ।

### WAL जर्नलिङ

`core.ts` ले डेटाबेसलाई **WAL (Write-Ahead Logging) मोड** मा खोल्छ:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL ले लेखन भइरहेका बेला **समवर्ती पठन** सम्भव बनाउँछ — अनुरोधहरू रेकर्ड भइरहेका बेला क्वेरी गर्ने ड्यासबोर्डका लागि यो महत्त्वपूर्ण छ।

पूर्वनिर्धारित क्यास आकार **65,536 KiB (64 MiB)** हो। SQLite ले ऋणात्मक
`cache_size` लाई KiB मा अनुमानित अधिकतम सीमाका रूपमा व्याख्या गर्छ र आवश्यकताअनुसार पृष्ठहरू आवंटन गर्छ।
**सेटिङहरू > प्रणाली र भण्डारण > क्यास आकार** ले **1 देखि
1,000,000 KiB** सम्मका पूर्णाङ्क मानहरू स्वीकार गर्छ; सेटिङ सेभ गर्दा त्यो चालु डेटाबेस जडानमा लागू हुन्छ,
र OmniRoute ले स्टार्टअपमा कायम गरिएको मान पुनर्स्थापना गर्छ।

## डेटाबेसको स्थान

SQLite फाइल यहाँ भण्डारण हुन्छ:

| OS      | पथ                                                                |
| ------- | ----------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                     |
| macOS   | `~/.omniroute/storage.sqlite`                                     |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                         |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` मार्फत कन्फिगर गर्न सकिने) |

सहायक फाइलहरू:

- `storage.sqlite-wal` — अग्रिम-लेखन लग
- `storage.sqlite-shm` — साझा मेमोरी फाइल
- `call_logs/` — अनुरोध पेलोड आर्टिफ्याक्टहरू (सक्षम पारिएको भए)

**स्थान ओभरराइड गर्नुहोस्:**

```bash
DATA_DIR=/custom/path omniroute
```

### मोड्युल सीमाहरू

एउटा मुख्य आर्किटेक्चरल नियम: **मोड्युलहरूले एकअर्काका तालिकाहरूमा प्रत्यक्ष पहुँच गर्दैनन्**। अर्को मोड्युलको डेटासँग काम गर्न, उक्त मोड्युलबाट प्रकार्य आयात गर्नुहोस्।

```ts
// ❌ गलत: अर्को मोड्युलबाट प्रत्यक्ष SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ सही: providers मोड्युलको प्रकार्य प्रयोग गर्नुहोस्
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

यो नियम कोड समीक्षामार्फत लागू गरिन्छ — कुनै स्थिर जाँच छैन, तर उल्लङ्घनहरू चिन्हित गरिन्छ।

~30+ तालिकाहरूको पूर्ण सूची `src/lib/db/migrations/` मा छ।

किन परिवर्तन: क्रमिक संख्याहरूको साथ, समानान्तर PRs उही अर्को नम्बर छान्यो र एक बाहेक सबैलाई मर्ज गर्नु अघि पुन: नम्बर गर्नुपर्‍यो। एक UTC टाइमस्ट्याम्पले प्रत्येक PR यसको आफ्नै संस्करण दिन्छ।

टाइमस्ट्याम्प ढाँचाका लागि नियमहरू ( `npm run check:migration-numbering` द्वारा लागू गरिएको, `scripts/check/lib/migrationNaming.mjs` मा जेनेरेटरसँग साझेदारी गरिएको):

- टाइमस्ट्याम्प वास्तविक UTC मिति र समय हो, `20261113000000` भन्दा पहिले होइन र भविष्यमा 10 मिनेट भन्दा बढी होइन।
- वर्णन लोअरकेस `snake_case` अक्षर (`a-z`, `0-9`, शब्दहरू बीचको एकल `_` ) बाट सुरु हुने हो, बढीमा 80 वर्णहरू।
- एउटै टाइमस्ट्याम्प भएका दुई फाइलहरू नक्कल हुन्।
- नो-ग्याप नियम पुरानो श्रृङ्खलाहरूमा मात्र लागू हुन्छ: `001` देखि `241` सम्मको प्रत्येक नम्बर अवस्थित हुनुपर्छ, ज्ञात अंतरहरू `026`, `055` र `121` बाहेक। `241` (वा कुनै पुरानो फाइल) मेटाउँदा गेट असफल हुन्छ। `001` र `241` `KNOWN_GAPS` अनुमति सूचीमा कहिल्यै थप्न सकिँदैन। टाइमस्ट्याम्प गरिएका फाइलहरूले कहिले पनि ग्याप बनाउँदैनन्।
- `src/lib/db/migrations/` मा प्रत्येक प्रविष्टि वैध लोअरकेस `.sql` नामको साथ नियमित फाइल हुनुपर्छ। डाइरेक्टरी, सिमलिङ्क, `.SQL` वा `.sql.bak` फाइल, लुकेको फाइल वा स्पेस भएको नामले गेट फेल गर्छ, किनभने रनरले चुपचाप छोड्छ वा बुटमा क्र्यास हुन्छ।

**अर्डर लागू गर्नुहोस्।** धावक उपसर्गको संख्यात्मक मान अनुसार क्रमबद्ध गर्दछ, पाठ द्वारा होइन: पुरानो `001`–`241` फाइलहरू पहिले, त्यसपछि टाइमस्ट्याम्प क्रममा टाइमस्ट्याम्प गरिएका फाइलहरू, त्यसपछि `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ( `ee-001` जस्ता संस्करणहरू) सँग दर्ता गरिएका कुनै पनि नेमस्पेस गरिएका डाइरेक्टरीहरू। पेन्डिङ माइग्रेसन भनेको कुनै पनि फाइल हो जसको संस्करण `_omniroute_migrations` मा छैन, त्यसैले पुरानो शाखाबाट माइग्रेसन जुन नयाँ पछि मर्ज हुन्छ त्यो अझै अवस्थित डाटाबेसमा लागू हुन्छ।

**टाइमस्ट्याम्प सिर्जना क्रम हो, मर्ज क्रम होइन।** यदि तपाईको माइग्रेसन तालिका वा स्तम्भमा निर्भर छ भने a माइग्रेसनद्वारा सिर्जना गरिएको** नयाँ** टाइमस्ट्याम्प (उदाहरणका लागि, पहिले मर्ज भएको अर्को PR बाट), एउटा नयाँ डाटाबेसले तपाइँको पहिले चलाउँछ र असफल हुन्छ। जब तपाइँको PR अझै खुला छ, `npm run db:new-migration` को साथ फाइल नाम पुन: उत्पन्न गर्नुहोस् ताकि यसले नयाँ टाइमस्ट्याम्प प्राप्त गर्दछ, वा यसलाई स्वतन्त्र बनाउनुहोस्। `npm run test:migrations:fresh` प्रत्येक माइग्रेसनलाई खाली डाटाबेसमा लागू गर्छ र यसलाई समात्छ।

### मर्ज गरिएको माइग्रेसन कहिल्यै मेटिने वा पुन: नामकरण हुँदैन

एक पटक माइग्रेसन फाइल रिलिज शाखा वा `main` मा भएपछि, यो पहिले नै homolog र विकासकर्ता डेटाबेसहरूमा, VPS स्थापनाहरूमा र इन्टरप्राइज सिंकमा चलेको छ। तब देखि:

- **यसलाई कहिल्यै नमेट्नुहोस्।** अपग्रेड गरिएका डाटाबेसहरूले यसलाई राख्दा ताजा स्थापनाहरूले यसको स्कीमा गुमाउनेछ।
- **यसलाई कहिल्यै पुन: नामाकरण नगर्नुहोस्।** `_omniroute_migrations` मा भएको संस्करण अब फाइलसँग मेल खाँदैन, त्यसैले यसलाई पहिले नै लागू गरेको प्रत्येक डाटाबेसले यसलाई फेरि चलाउनेछ। Non-idempotent SQL ले डाटा डुप्लिकेट गर्छ वा बुट रोक्छ।
- **फरक योजना चाहिन्छ?** `npm run db:new-migration` सँग नयाँ माइग्रेसन सिर्जना गर्नुहोस्।

पुन: नामाकरण केवल एक फाइलको लागि सुरक्षित छ जुन अहिलेसम्म मर्ज गरिएको छैन, जुन गेटको संकेतले सन्दर्भ गर्दछ। रिलीज ट्यागले यहाँ केहि परिवर्तन गर्दैन: `release/v*` शाखामा प्रत्येक धक्काले Docker `:next` छवि प्रकाशित गर्दछ र homolog, VPS स्थापनाहरू र इन्टरप्राइज सिंकमा चल्छ, त्यसैले कुनै पनि `vX.Y.Z` ट्याग अवस्थित हुनु अघि वास्तविक डाटाबेसमा मर्ज गरिएको माइग्रेसन चलेको छ। गेटले आधार फाइलको प्रत्येक हटाउन असफल हुन्छ, ट्याग गरिएको वा छैन।

- **मर्ज गरिएको माइग्रेसनलाई उल्टाउँदै।** फाइल मेटाउने `git revert` गेट असफल हुन्छ। फाइल राख्नुहोस् र यसको स्किमालाई नयाँ माइग्रेसनमा पूर्ववत गर्नुहोस्: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` र यस्तै अन्य। अपग्रेड गरिएका र ताजा डाटाबेसहरू त्यसपछि एउटै स्कीमासँग समाप्त हुन्छन्।
- **एउटा स्वीकृत नाम परिवर्तन: एक अनुकूलता प्रविष्टि र समान सामग्री।** यदि मर्ज गरिएको फाइल सार्नैपर्छ (उदाहरणका लागि, दुई मर्ज गरिएका फाइलहरूले टाइमस्ट्याम्प साझा गर्छन् र रनरले संस्करणको टक्करमा रोक्छ), यसको SQL छोईकनै पछिको नाम परिवर्तन गर्नुहोस् र `src/lib/db/migrationRunner/constants.ts` मा `{ fromVersion, fromName, toVersion, toName }` लाई `RENAMED_MIGRATION_COMPATIBILITY` मा थप्नुहोस्। पुरानो संस्करण लागू गर्ने डाटाबेसहरूले फाइल पुन: चलाउनुको सट्टा तिनीहरूको `_omniroute_migrations` पङ्क्ति सारियो। गेटले यस्तो नाम परिवर्तनको बारेमा चेतावनी दिन्छ र सधैं यसमा कम्युटेशन जाँच चलाउँछ, जुनसुकै नयाँ टाइमस्ट्याम्प: ताजा स्थापनाहरूले फाइललाई यसको नयाँ स्थानमा लागू गर्दछ, अपग्रेड गरिएका डाटाबेसहरूले गर्दैनन्, त्यसैले पुरानोको नजिक नयाँ टाइमस्ट्याम्प छान्नुहोस्। यदि सामग्री परिवर्तन भयो भने गेटले नाम परिवर्तन गर्न असफल हुन्छ (स्कीमा परिवर्तन अझै नयाँ माइग्रेसनमा जान्छ), वा यदि प्रविष्टिको लक्ष्य फाइल डिस्कमा छैन।
- **एउटै टाइमस्ट्याम्प भित्र कहिल्यै पुन: नामाकरण नगर्नुहोस्।** टाइमस्ट्याम्प राख्ने र केवल विवरण परिवर्तन गर्ने नाम परिवर्तनले प्रवेशको साथ वा बिना गेट असफल हुन्छ। एउटा प्रविष्टिको साथ जसको `toVersion` यसको `fromVersion` बराबर हुन्छ, धावकले पुरानो `_omniroute_migrations` पङ्क्ति मेटाउँछ र फाइललाई पहिले नै चलाएको प्रत्येक डाटाबेसमा पुन: लागू गर्दछ। कुनै प्रविष्टि बिना, धावकले संस्करण मात्र ट्र्याक गर्दछ: यसले ती डाटाबेसहरूमा फाइल छोड्छ (नयाँ सामग्री त्यहाँ कहिल्यै चल्दैन) र प्रत्येक बुटमा पुन: नम्बर त्रुटि लगाउँछ। अर्को टाइमस्ट्याम्प र एक अनुकूलता प्रविष्टि प्रयोग गर्नुहोस्, वा नाम राख्नुहोस्।
- **गेटले जाँच गर्दछ कि पुन: नामकरण गरिएको फाइल फेरि चल्दैन।** प्रत्येक कभर गरिएको नाम परिवर्तनको लागि, गेटले नयाँ फाइल नाम `--must-not-apply` सँग कम्युटेशन जाँचमा पास गर्दछ। चेकले अपग्रेड गरिएको डाटाबेसलाई वास्तविक धावकसँग बुट गर्छ, र यदि धावकले त्यो फाइल फेरि लागू गर्छ (उदाहरणका लागि, प्रविष्टिमा गलत संस्करण वा नाम भएको कारणले, वा गेटको पाठ पार्सरले TypeScript बाट फरक रूपमा `constants.ts` पढेको कारणले), गेट `migration renomeada rodaria de novo` सँग असफल हुन्छ र तपाईंलाई प्रविष्टिको पुरानो र नयाँ संस्करणहरू र नामहरू जाँच गर्न सोध्छ।

### गेटले आधार विरुद्ध के जाँच गर्दछ

पुल अनुरोध र मर्ज-क्यु रनमा, `npm run check:migration-numbering` डिस्कमा `src/lib/db/migrations/` आधार शाखामा रहेको एउटै डाइरेक्टरीसँग तुलना गर्छ। आधार यस क्रममा छ: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` चर, वा, जब `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` वा `merge_group` हुन्छ, मर्ज कमिटको पहिलो अभिभावक, घटना पेलोडको `merge_group.base_sha`, वा `git merge-base HEAD origin/$GITHUB_BASE_REF`। कुनै समाधान गर्न मिल्ने आधार बिना पुल अनुरोध वा मर्ज-क्युमा गेट असफल हुन्छ। CI बिना `--base` बाहिर यसले `comparação com a base: pulada (sem --base)` छाप्छ र यी नियमहरू छोड्छ।

`--base-latest-tag` सबैभन्दा नयाँ रिलीज ट्याग (semver क्रममा`vX.Y.Z` ; नाइटलीज जस्ता प्रत्यय ट्यागहरू गणना गर्दैन) सँग तुलना गर्दछ जुन `HEAD` को इतिहासमा छ, `--base` जस्तै समान नियमहरूसँग। रिलीज-ग्रीन (`scripts/quality/validate-release-green.mjs`) ले यसरी गेट चलाउँछ, किनकि पुश र निर्धारित रनहरूमा कुनै पुल अनुरोध आधार छैन र एक मर्जले नयाँ CI रन बिना ल्यान्ड गर्न सक्छ। इतिहासमा कुनै रिलीज ट्याग बिना गेट असफल हुन्छ; `git fetch --tags` चलाउनुहोस् ( CI मा, `actions/checkout` सँग `fetch-depth: 0` ले ट्यागहरू ल्याउँछ)।

कम्युटेशन चेकको एक रनले आउट-अफ-अर्डर, सम्पादन गरिएका र पुन: नामकरण गरिएका फाइलहरू सँगै समावेश गर्दछ।

कम्युटेशन चेक (`scripts/check/migration-commutation.ts`) ले वास्तविक स्थापना मार्गको साथ दुई अस्थायी डाटाबेसहरू निर्माण गर्दछ: एक** अपग्रेड गरियो** एउटा (आधार माइग्रेसनसँग बुट गर्नुहोस्, त्यसपछि पुल अनुरोधको माइग्रेसनको साथ एउटै फाइलमा फेरि बुट गर्नुहोस्) र एक** ताजा** एउटा (पुल अनुरोधको माइग्रेसनसँग एउटा बुट)। यसले परिणाम स्वरूप स्कीमाहरू तुलना गर्दछ: तालिकाहरू र स्तम्भहरू (स्तम्भ क्रमलाई बेवास्ता गर्दै), UNIQUE / PRIMARY KEY र FOREIGN KEY अवरोधहरू, प्रत्येक तालिकाको सामान्यीकृत `CREATE TABLE` पाठ (जसले CHECK अवरोधहरू, कोलेसनहरू, उत्पन्न स्तम्भहरू र अनुक्रमणिका विकल्पहरू समावेश गर्दछ), तालिका विकल्पहरू। पङ्क्ति डेटा तुलना गरिएको छैन। यदि तिनीहरू मेल खान्छ भने, गेटले प्रिन्ट गर्दछ कि फाइल व्यवस्थित छैन तर कम्युट, र पास हुन्छ। यदि तिनीहरू फरक छन् भने, गेट भिन्नता र केसको लागि संकेतको साथ असफल हुन्छ: अर्डर-अर्डर फाइलको लागि, यसको नाम `npm run db:new-migration` सँग पुन: उत्पन्न गर्नुहोस्, जुन सुरक्षित छ किनभने फाइल अझै मर्ज गरिएको छैन; सम्पादन गरिएको आधार फाइलको लागि, आधार सामग्री पुनर्स्थापना गर्नुहोस् र परिवर्तनलाई नयाँ माइग्रेसनमा राख्नुहोस्; पुन: नामकरण गरिएको फाइलको लागि, पुन: नामाकरण पूर्ववत गर्नुहोस् वा अर्को नयाँ टाइमस्ट्याम्प छान्नुहोस् जहाँ यो कम्युट हुन्छ, अर्को नामको साथ एउटै टाइमस्ट्याम्प कहिल्यै नगर्नुहोस्। यदि चेक आफै चलाउन सक्दैन भने, गेट CI मा असफल हुन्छ र स्थानीय रूपमा मात्र चेतावनी दिन्छ। सम्पादन गरिएको आधार फाइलको लागि, अपग्रेड गरिएको डाटाबेस त्यो फाइलको आधार सामग्रीसँग बनाइन्छ, र दोस्रो बुटले यसलाई छोड्छ किनभने यसको संस्करण पहिले नै रेकर्ड गरिएको छ। पुन: नामाकरण गरिएको फाइलको लागि, अपग्रेड गरिएको डाटाबेस यसको पुरानो नाम अन्तर्गत फाइलसँग बनाइएको छ, र दोस्रो बुटले यसलाई पुन: चलाउनको सट्टा अनुकूलता प्रविष्टि मार्फत यसको `_omniroute_migrations` पङ्क्ति सार्दछ; गेटले नयाँ नाम `--must-not-apply` सँग पास गर्छ, त्यसैले दोस्रो बुटले यसलाई लागू गरेमा जाँच असफल हुन्छ। यदि पुल अनुरोध माइग्रेसन अपग्रेड गरिएको मार्गमा लागू हुन असफल भयो भने, अर्थात् प्रत्येक आधार माइग्रेसन पछि (यसले नयाँ स्थापना गर्दा पनि असफल हुन्छ वा होइन), गेटले `migration do PR não aplica` रिपोर्ट गर्छ र आधारको हालको स्कीमा विरुद्ध SQL लाई ठीक गर्न सोध्छ; यदि फाइल पछिको टाइमस्ट्याम्पको साथ अर्को पुल अनुरोध माइग्रेसनमा निर्भर छ भने, यसको नाम `npm run db:new-migration` सँग पुन: उत्पन्न गर्नुहोस्।

स्थानीय रूपमा समान तुलना चलाउन, आधार स्पष्ट रूपमा पास गर्नुहोस्, उदाहरणका लागि `npm run check:migration-numbering -- --base origin/<base-branch>`, वा `npm run check:migration-numbering -- --base-latest-tag` पछिल्लो रिलीजसँग तुलना गर्न।

### खुला PR को `NNN` माइग्रेसन रूपान्तरण गर्दै

स्विच अघि खोलिएको पुल अनुरोधले अझै पनि `242_add_widgets.sql` जस्तै क्रमिक फाइल बोक्न सक्छ। `241` माथिका पुराना नम्बरहरू अस्वीकार गरिएका छन्, त्यसैले मर्ज गर्नु अघि यसलाई रूपान्तरण गर्नुहोस्:

1. **जेनेरेटरको साथ फाइलको नाम परिवर्तन गर्नुहोस्, विवरण राख्दै।** नयाँ नाम प्राप्त गर्न `npm run db:new-migration -- <same description>` चलाउनुहोस्, यसमा SQL सार्नुहोस्, र पुरानो `NNN_` फाइल मेटाउनुहोस्। विवरण उस्तै हुनुपर्छ: तलको अनुकूलता प्रविष्टि यसमा मेल खान्छ।
2. **यदि निरन्तर डाटाबेसले पुरानो नम्बर चलायो भने अनुकूलता प्रविष्टि थप्नुहोस्।** यदि राखिएको कुनै डाटाबेस (homolog, a VPS, योगदानकर्ताको आफ्नै स्थापना) ले `NNN_` फाइलसँग PR को निर्माण चलाएको छ भने, `src/lib/db/migrationRunner/constants.ts` मा `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` `RENAMED_MIGRATION_COMPATIBILITY` । यो हो** `237` देखि `241` को लागि आवश्यक छ** : ती स्लटहरूले अब क्यानोनिकल `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` र `241_seen_models.sql` राख्छन्, र प्रविष्टि बिना नै यस्तो डाटाबेसले क्यानोनिकल माइग्रेसनलाई सदाको लागि छोड्छ र रूपान्तरितलाई फेरि चलाउँछ। यसले एउटा स्लटको लागि पनि काम गर्छ जुन खाली रहन्छ, जस्तै `242`, जब गन्तव्य टाइमस्ट्याम्प हुन्छ। शंका हुँदा, प्रविष्टि थप्नुहोस्। तपाईँले array मा कहाँ थप्नुहुन्छ भन्ने कुराले फरक पार्दैन: जब प्रविष्टिको लक्ष्य स्लटले अझै पङ्क्ति राख्छ कि अर्को प्रविष्टि टाढा जान्छ (उदाहरणका लागि `237` PR पङ्क्ति समातेको छ जबकि पुरानो `usage_history_calculated_cost` पङ्क्तिले `237` मा सार्न पर्खिरहेको छ), धावकले त्यो प्रविष्टिलाई स्लट खाली नभएसम्म पर्खन अनुमति दिन्छ। केवल एक वास्तविक द्वन्द्व, जस्तै पङ्क्तिमा राखिएको स्लट नो एन्ट्री चाल, वा स्लटहरू स्वैप गर्ने दुई प्रविष्टिहरू, `Cannot reconcile ...` सँग बुट रोक्छ।
3. **SQL लाई अशक्त राख्नुहोस्** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), किनभने रूपान्तरित माइग्रेसनले डाटाबेसलाई भेट्न सक्छ जहाँ यसको योजना पहिले नै अवस्थित छ।
4. **संस्करण-कुञ्जी विशेष केसहरू सार्नुहोस्।** यदि PR `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) वा `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) मा पुरानो नम्बरको लागि केस थपेको छ भने, नयाँ टाइमस्ट्याम्पमा कुञ्जी परिवर्तन गर्नुहोस्।

`tests/unit/db/codex-fence-migration-rename.test.ts` पुन: नामाकरण गरिएको माइग्रेसनको लागि परीक्षणको काम गर्ने उदाहरण हो।

### स्विच अघि शाखाहरूमा ब्याकपोर्टहरू

`YYYYMMDDHHMMSS_` फाइललाई स्विच भन्दा पहिलेको शाखामा चेरी-पिक वा ब्याकपोर्ट नगर्नुहोस् (उदाहरणका लागि पुरानो `release/v*` शाखा)। त्यहाँ धावकले फाइल नामहरूलाई पाठको रूपमा क्रमबद्ध गर्दछ, त्यसैले टाइमस्ट्याम्प गरिएको फाइल `201_` र `202_` बीचमा नयाँ डाटाबेसमा चल्नेछ, र त्यहाँको पुरानो गेटले 14-अङ्कको उपसर्गहरू बुझ्दैन। यस्तो शाखामा, त्यो शाखाको आफ्नै अर्को `NNN_` फाइल, idempotent को रूपमा परिवर्तन लेख्नुहोस्, त्यसैले टाइमस्ट्याम्प गरिएको संस्करण पछि आइपुग्दा यो नो-अप हो।

### कसरी माइग्रेसन चल्छ

स्टार्टअपमा, `migrationRunner.ts`:

1. यदि अवस्थित छैन भने `_omniroute_migrations` तालिका सिर्जना गर्दछ
2. पहिले नै लागू गरिएको माइग्रेसनका लागि प्रश्नहरू
3. कुनै पनि नयाँ माइग्रेसनहरू क्रमबद्ध रूपमा लागू गर्दछ, प्रत्येक लेनदेनमा
4. टाइमस्ट्याम्पको साथ प्रत्येक लागू माइग्रेसन रेकर्ड गर्दछ

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### इडम्पोटेन्सी

माइग्रेसन हुनु पर्छ** अशक्त** — तिनीहरूलाई दुई पटक चलाउनु नो-अप हुनुपर्छ:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, र `OR IGNORE` / `OR REPLACE` खण्डहरू उदारतापूर्वक प्रयोग गर्नुहोस्।

### नयाँ माइग्रेसन थप्दै

1. **जेनरेटरको साथ फाइल सिर्जना गर्नुहोस्** : `npm run db:new-migration -- <description>` (उदाहरणका लागि `npm run db:new-migration -- add combo priority`)। यसले वर्तमान UTC समय र टिप्पणी हेडरको साथ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` लेख्छ, यदि त्यो टाइमस्ट्याम्प लिइयो भने एक सेकेन्ड अगाडि बढ्छ, र फाइललाई कहिल्यै ओभरराइट गर्दैन। हातले नम्बर नछोड्नुहोस्।
2. **सुरक्षित DDL प्रयोग गर्नुहोस्** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **सावधानीपूर्वक डेटा ब्याकफिल गर्नुहोस्** : अवस्थित पङ्क्तिहरू ह्यान्डल गर्न `UPDATE ... WHERE ...` प्रयोग गर्नुहोस्
4. **अर्डर र नामकरण जाँच गर्नुहोस्** : `npm run test:migrations:fresh` (खाली डाटाबेसमा सबै माइग्रेसनहरू) र `npm run check:migration-numbering`
5. **प्रतिलिपिमा परीक्षण गर्नुहोस्** : उत्पादनमा परीक्षण नगरिएको माइग्रेसन कहिल्यै नचलाउनुहोस्
6. **कोडबाट सिर्जना गरिएको तालिकालाई पनि माइग्रेसन चाहिन्छ** : यदि मोड्युलले पनि तालिकालाई अल्छी रूपमा सिर्जना गर्दछ (`CREATE TABLE IF NOT EXISTS`, आत्म-निको मार्गको रूपमा राखिएको छ), माइग्रेसनले समान DDL सँग सिर्जना गर्नुपर्छ। अन्यथा क्लिन इन्स्टल र अपग्रेड गरिएको इन्स्टल बिभिन्न स्कीमाहरूसँग समाप्त हुन्छ, त्यो कोड पथ चलेको छ कि छैन भन्ने आधारमा। `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` र `open-sse/` स्क्यान गर्छ र माइग्रेसन बिना अल्छी `CREATE` मा असफल हुन्छ (#20557)। उदाहरण: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`।

उदाहरण:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **पछाडि - असंगत परिवर्तनहरू** (जस्तै, स्तम्भहरू छोड्ने) कठिन छन्। एक पटक माइग्रेसन लागू भएपछि OmniRoute ले NOT डाउनग्रेड — लाई समर्थन गर्छ, स्किमा परिवर्तन स्थायी हुन्छ। सोही अनुसार योजना बनाउनुहोस्।

## स्थिर अवस्थामा इन्क्रिप्सन

संवेदनशील फिल्डहरू (API कुञ्जीहरू, OAuth टोकनहरू, कनेक्सन स्ट्रिङहरू) स्थिर अवस्थामा **AES-256-GCM** प्रयोग गरेर इन्क्रिप्ट गरिन्छन्।

### यसले कसरी काम गर्छ

```ts
// src/lib/db/encryption.ts (सरलीकृत)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### यो कहाँ प्रयोग हुन्छ

- `provider_connections.api_key` — एप्लिकेसन तहमा इन्क्रिप्ट गरिएको
- `provider_connections.access_token`, `refresh_token`, `id_token` — एप्लिकेसन तहमा इन्क्रिप्ट गरिएको
- `namespace = "secrets"` भएका `key_value` प्रविष्टिहरू — एप्लिकेसन तहमा इन्क्रिप्ट गरिएको
- `proxy_registry.auth` — एप्लिकेसन तहमा इन्क्रिप्ट गरिएको (उपस्थित भएमा)

### इन्क्रिप्सन कुञ्जी

इन्क्रिप्सन कुञ्जी एउटा **पासफ्रेज** (`STORAGE_ENCRYPTION_KEY` env var मार्फत सेट गरिएको) र एउटा **साल्ट** (DB मा भण्डारण गरिएको) बाट व्युत्पन्न गरिन्छ। डेटा डिक्रिप्ट गर्न दुवै आवश्यक हुन्छन्।

```bash
# सुरक्षित पासफ्रेज उत्पन्न गर्नुहोस्
openssl rand -hex 32

# .env मा सेट गर्नुहोस्
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **अत्यन्त महत्त्वपूर्ण**: इन्क्रिप्सन कुञ्जी हराउनुको अर्थ सबै इन्क्रिप्ट गरिएको डेटामाथिको पहुँच गुमाउनु हो। **कुञ्जीलाई डेटाबेसबाट अलग्गै ब्याकअप गर्नुहोस्**।

### के इन्क्रिप्ट गरिएको छैन

कार्यसम्पादनसम्बन्धी कारणहरूले गर्दा, निम्न कुराहरू प्लेनटेक्स्टमा भण्डारण गरिन्छन्:

- प्रदायकका प्रदर्शन नामहरू
- मोडेल परिभाषाहरू (पहिल्यै सार्वजनिक)
- राउटिङ नियमहरू
- प्रयोग अभिलेखहरू (कुनै PII छैन)

## इन्क्रिप्सनसम्बन्धी सावधानीहरू (v3.8.16+)

OmniRoute ले दुईवटा इन्क्रिप्सन योजनालाई पारदर्शी रूपमा व्यवस्थापन गर्न **`migrateLegacyEncryptedString()`** प्रयोग गर्छ:

- **पुरानो** (v3.5.0 भन्दा अघिको): XOR-आधारित "इन्क्रिप्सन" (वास्तविक क्रिप्टोग्राफी होइन)
- **हालको**: उचित IV र प्रमाणीकरण ट्यागसहितको AES-256-GCM

माइग्रेसन सहायकले पुरानो ढाँचा पत्ता लगाउँछ र पहिलो पटक पढ्दा नयाँ योजनाद्वारा पुनः इन्क्रिप्ट गर्छ। यसको अर्थ तपाईंले क्रेडेन्सियलहरू नगुमाई पुरानो डेटाबेस अपग्रेड गर्न सक्नुहुन्छ।

## रिड क्यास

बारम्बार पढिने डेटा (मोडेलहरू, प्रदायकहरू, सेटिङहरू) का लागि, `readCache.ts` ले **इन-मेमोरी क्यास** प्रदान गर्छ:

```ts
// स्टार्टअपमा क्यास गरिन्छ, लेख्दा अमान्य बनाइन्छ
```

| ---------------------- | -------------- | ---------- |

| `settings`             | `settings:v1`  | लेख्दासम्म |
| `combos`               | `combos:v1`    | लेख्दासम्म |

सम्बन्धित तालिकामा प्रत्येक पटक लेख्दा क्यास अमान्य बनाइन्छ।

यसले SQLite को अनलाइन ब्याकअप API प्रयोग गर्छ — OmniRoute चलिरहेको बेला सञ्चालन गर्न सुरक्षित छ।

## प्रदर्शन ट्युनिङ

### WAL मोड

WAL पूर्वनिर्धारित रूपमा सक्षम छ। उच्च-लेखन कार्यभारहरूको लागि, विचार गर्नुहोस्:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute ले `journal_size_limit` सेट गर्दैन। चेकपोइन्टले WAL फ्रेमहरूलाई मुख्य फाइलमा सार्छ, तर WAL फाइलले यसको सबैभन्दा ठूलो आवंटित साइज राख्छ। `OMNIROUTE_WAL_GUARD_MAX_MB` गार्डले मात्र चेतावनी दिन्छ र `wal_checkpoint(RESTART)` चलाउँछ; यो डिस्क साइज टोपी होइन।

### अनुक्रमणिकाहरू

कार्यसम्पादनका लागि प्रमुख अनुक्रमणिकाहरू (माइग्रेसनद्वारा स्वत: सिर्जना गरिएको):

- प्रदायक द्वारा`idx_models_provider` — मोडेल लुकअप
- `idx_combo_targets_combo_id` — कम्बो लक्ष्य विस्तार
- `idx_usage_history_api_key_timestamp` — उपयोग विश्लेषण
- `idx_quota_snapshots_api_key_window` — कोटा ट्र्याकिङ
- `idx_call_logs_timestamp` — कल लग प्रश्नहरू

नयाँ अनुक्रमणिका थप्न, माइग्रेसन सिर्जना गर्नुहोस्:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### मेमोरी-म्याप गरिएको I/O

धेरै ठूला डाटाबेसहरूको लागि (> 10GB), मेमोरी म्यापिङ SQLite pragma मार्फत समायोजन गर्न सकिन्छ:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### कम्प्याक्शन

लामो समयदेखि चलिरहेको OmniRoute उदाहरणहरू कहिलेकाहीं `VACUUM` बाट लाभ उठाउँछन्:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

कम ट्राफिक विन्डोको समयमा मासिक चलाउनुहोस्। (WAL मोडले आवश्यकता घटाउँछ, तर यसलाई हटाउँदैन।)

## स्वास्थ्य जाँच

`src/lib/db/healthCheck.ts` ले **DB-स्तरीय स्वास्थ्य निदान** प्रदान गर्छ:

दुवै क्रियाका लागि प्रमाणीकरण आवश्यक हुन्छ (अन्यथा `401`)। `GET` ले निदान मात्र गर्छ; `POST` ले
`autoRepair` सक्षम गरेर उही जाँच चलाउँछ।

```bash
GET  /api/db/health   # निदान गर्नुहोस्
POST /api/db/health   # निदान + मर्मत गर्नुहोस्
```

प्रतिक्रिया `runDbHealthCheck()` द्वारा उत्पादित `DbHealthCheckResult` हो
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Domain budgets referenced API keys that no longer exist.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| फिल्ड             | अर्थ                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `issues` खाली हुँदा `true`। `driver` ले यसलाई कहिल्यै प्रभावित गर्दैन।                                                                 |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` मध्ये एउटा।                                            |
| `repairedCount`   | यो रनका क्रममा मर्मत गरिएका पङ्क्तिहरू; `autoRepair` false हुँदा सधैँ `0`।                                                             |
| `backupCreated`   | मर्मत गर्नुअघि ब्याकअप लिइएको थियो कि थिएन।                                                                                            |
| `checkedAt`       | रन र त्यसले लेख्ने कुनै पनि मर्मत नोटद्वारा साझा गरिएको ISO टाइमस्ट्याम्प।                                                             |
| `driver.name`     | जाँच गरिएको डेटाबेस उपलब्ध गराउने SQLite ड्राइभर।                                                                                      |
| `driver.degraded` | लेखनहरू डेटाबेस फाइलद्वारा स्थायी रूपमा ब्याकअप नहुँदा `true` — `sql.js` WASM fallback (सम्पूर्ण-फाइल स्थायित्व) वा इन-मेमोरी डेटाबेस। |

उही पेलोड `omniroute_db_health_check` MCP उपकरणद्वारा फर्काइन्छ।

करप्सन पत्ता लगाउन `PRAGMA integrity_check` चलाउनुहोस्:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# यसले प्रिन्ट गर्नुपर्छ: ok
```

यदि यसले `ok` बाहेक अरू केही फर्काउँछ भने, **डेटाबेस प्रयोग गर्न तुरुन्तै बन्द गर्नुहोस्** र ब्याकअपबाट पुनर्स्थापना गर्नुहोस्।

## विपद् पुनःप्राप्ति

### परिदृश्य 1: WAL फाइल हरायो

`-wal` फाइल हराएको छ तर `-shm` र मुख्य DB अक्षुण्ण छन्:

```bash
# अर्को पटक खोल्दा स्वचालित रूपमा पुनःप्राप्त हुन्छ
omniroute
```

यदि SQLite ले स्वतः पुनःप्राप्त गर्न सकेन भने:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### परिदृश्य 2: मुख्य DB फाइल बिग्रियो

ब्याकअपबाट पुनर्स्थापना गर्नुहोस्:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` ले चलिरहेको सर्भरबाट पूर्ण `.tar.gz` अभिलेख मात्र डाउनलोड गर्छ
(`GET /api/db-backups/exportAll`, अपरेटरको प्रमाण आवश्यक); यसले कुनै पनि कुरा पुनर्स्थापना गर्दैन।

### परिदृश्य 3: इन्क्रिप्सन कुञ्जी हरायो

कुञ्जीविना **पुनःप्राप्ति सम्भव छैन**। इन्क्रिप्ट गरिएका फिल्डहरू पढ्न सकिँदैनन्। नयाँ प्रमाणहरू प्रयोग गरेर सबै प्रदायकहरू म्यानुअल रूपमा पुनः थप्नुहोस्।

> **न्यूनीकरण**: इन्क्रिप्सन कुञ्जीलाई सधैँ छुट्टै ब्याकअप गर्नुहोस्, सम्भव भएसम्म पासवर्ड म्यानेजर वा KMS मा।

### परिदृश्य 4: डिस्क भरियो

SQLite ले `SQLITE_FULL` त्रुटिहरू फर्काउनेछ। डिस्कमा ठाउँ खाली गर्नुहोस्, त्यसपछि:

```bash
# ठाउँ खाली गर्न WAL लाई चेकपोइन्ट गर्नुहोस्
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

### तालिका निरीक्षण गर्नुहोस्

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### सबै तालिकाका पङ्क्तिहरू गणना गर्नुहोस्

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### सबै डेटा रिसेट (मेटाउनुहोस्) गर्नुहोस्

```bash
# पहिले OmniRoute रोक्नुहोस्
omniroute stop

# DB फाइल मेटाउनुहोस्
rm ~/.omniroute/storage.sqlite*

# पुनः सुरु गर्नुहोस् (खाली DB पुनः सिर्जना हुनेछ)
omniroute
```

**छनोटात्मक** रिसेटका लागि (प्रदायकहरू राख्ने, प्रयोगसम्बन्धी डेटा मेटाउने):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### एउटा तालिका निर्यात गर्नुहोस्

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## समस्या निवारण

### "डेटाबेस लक गरिएको छ"

अर्को प्रक्रियाले लेखन लक समातिरहेको छ। निम्नमध्ये कुनै एक गर्नुहोस्:

- अर्को प्रक्रिया समाप्त नभएसम्म पर्खनुहोस् (`lsof | grep storage.sqlite` जाँच गर्नुहोस्)
- अर्को प्रक्रिया बन्द गर्नुहोस्
- समस्या जारी रहेमा OmniRoute पुनः सुरु गर्नुहोस्

### "फरेन की अवरोध असफल भयो"

एउटा डोमेन मोड्युलले सन्दर्भ अखण्डता उल्लङ्घन गरिरहेको छ। निम्न जाँच गर्नुहोस्:

- निर्भर तालिकाहरूमा मूल पङ्क्तिसँग सम्बन्ध नभएका पङ्क्तिहरू
- प्रसारित नभएका क्यास्केडिङ मेटाइहरू
- फरेन की परिवर्तन गरेको हालैको माइग्रेसन

उल्लङ्घनहरू फेला पार्न `PRAGMA foreign_key_check;` चलाउनुहोस्।

### "मेमोरी सकियो"

SQLite को मेमोरी-म्याप गरिएको I/O ले OS को सीमा नाघिरहेको छ। SQLite pragma मार्फत घटाउनुहोस्:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB को सट्टा 128MB
```

वा निष्क्रिय गर्नुहोस्:

```sql
PRAGMA mmap_size = 0;
```

### "माइग्रेसन बीचमै असफल भयो"

माइग्रेसन ट्रान्ज्याक्सनभित्र चलेको थियो, त्यसैले यो रोलब्याक भएको हुनुपर्छ। नभएको भए:

1. **OmniRoute रोक्नुहोस्** (थप प्रयासहरू रोक्न)
2. `sqlite3` प्रयोग गरेर **DB को अवस्था जाँच गर्नुहोस्**
3. आंशिक माइग्रेसनलाई **म्यानुअल रूपमा सच्याउनुहोस्**
4. OmniRoute **पुनः चलाउनुहोस्** (माइग्रेसन पुनः प्रयास गरिनेछ)

यसलाई रोक्न, माइग्रेसनहरूलाई सधैं पहिले प्रतिलिपिमा परीक्षण गर्नुहोस्।
