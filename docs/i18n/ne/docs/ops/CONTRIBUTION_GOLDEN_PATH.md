पुल अनुरोधका लागि सबैभन्दा सानो भरपर्दो विकास चक्र छनोट गर्न यो मार्गदर्शिका प्रयोग गर्नुहोस्। यसले
तल लिङ्क गरिएका क्षेत्र-विशिष्ट आर्किटेक्चर र सुरक्षा कागजातहरूलाई प्रतिस्थापन गर्दैन; यसले प्रत्येक सामान्य
परिवर्तन प्रकारलाई त्यसका अनुबन्धहरू, केन्द्रित जाँचहरू, र CI कभरेजसँग जोड्छ।

## प्रत्येक परिवर्तनले पछ्याउने मार्ग

1. **सम्पादन गर्नुअघि आधार छनोट गर्नुहोस्।** सबैभन्दा माथिल्लो सक्रिय `release/v*` शाखा फेला पार्नुहोस् र
   त्यसको शीर्षबाट शाखा बनाउनुहोस्। `main` होइन, त्यही शाखालाई लक्ष्य बनाउनुहोस्। यदि रिलिज फ्रिज सक्रिय छ भने, फ्रिज गरिएको
   शाखालाई लक्ष्य नबनाउनुहोस्; [शाखाकरण र रिलिज मोडेल](BRANCHING_MODEL.md) मा वर्णन गरिएको
   अर्को सक्रिय चक्र प्रयोग गर्नुहोस्।
2. **अनुबन्धहरू उल्लेख गर्नुहोस्।** परिवर्तनले असर गर्ने प्रत्येक क्याटलग, स्किमा, उत्पन्न गरिएको आर्टिफ्याक्ट, सार्वजनिक API, वा प्रयोगकर्ता
   इन्टरफेस पहिचान गर्नुहोस्। तलको तालिकाले न्यूनतम प्रारम्भिक सेट दिन्छ।
3. **केन्द्रित परीक्षणहरू लेख्नुहोस् वा अद्यावधिक गर्नुहोस्।** `src/`, `open-sse/`, `electron/`, वा
   `bin/` मा गरिएका उत्पादन परिवर्तनहरूका लागि सोही PR मा स्वचालित परीक्षण आवश्यक हुन्छ। व्यवहार प्रमाणित गर्ने सबैभन्दा साना
   परीक्षण फाइलहरू चलाउनुहोस्, त्यसपछि सूचीबद्ध केन्द्रित गेटहरू चलाउनुहोस्।
4. **CI लाई विस्तृत म्याट्रिक्स चलाउन दिनुहोस्।** पूर्ण युनिट शार्डहरू, Vitest, कभरेज र्याचेट, र
   उत्पादन बिल्ड PR मा चल्छन्। केन्द्रित असफलताले व्यापक प्रभाव सङ्केत गर्दा वा परिवर्तनले धेरै उपप्रणालीहरू
   समेट्दा मात्र स्थानीय रूपमा विस्तृत सुइट चलाउनुहोस्।
5. **समीक्षाअघि समायोजन गर्नुहोस्।** सक्रिय आधार फेच गर्नुहोस्, त्यसका नयाँ कमिटहरू र त्यससँग तुलना गरिएको आफ्नो डिफ निरीक्षण
   गर्नुहोस्, त्यसपछि योगदानकर्ता कार्यप्रवाहअनुसार आधारलाई रिबेस वा मर्ज गर्नुहोस्। उत्पन्न गरिएका फाइल
   र क्याटलगका द्वन्द्वहरू तिनको स्रोतबाट समाधान गर्नुहोस्, तिनलाई पुनः उत्पन्न गर्नुहोस्, केन्द्रित चक्र फेरि चलाउनुहोस्, र
   PR ले अझै पनि सक्रिय रिलिज शाखालाई नै लक्ष्य गरेको पुष्टि गर्नुहोस्।
6. **प्रमाण अभिलेख गर्नुहोस्।** PR टेम्प्लेटमा चलाइएका कमान्डहरू, थपिएका वा परिवर्तन गरिएका प्रत्येक परीक्षण फाइल,
   माइग्रेसन वा फिचर फ्ल्यागहरू, र अझै बाँकी रहेका कुनै पनि CI-मात्र प्रमाणीकरण सूचीबद्ध गर्नुहोस्।

## परिवर्तन प्रकारअनुसारका आदर्श मार्गहरू

तलका कमान्डहरू न्यूनतम केन्द्रित जाँचहरू हुन्; तपाईंले परिवर्तन गरेको व्यवहारलाई प्रत्यक्ष रूपमा समेट्ने परीक्षण
छोड्ने अनुमति होइनन्।

### प्रदायक

**अनुबन्धहरू**

- `src/shared/constants/providers/` मा रहेको प्रदायक परिभाषा र
  `src/shared/constants/providers.ts` मा त्यसको संयोजन।
- `open-sse/config/providerRegistry.ts` वा त्यसबाट निकालिएका रजिस्ट्री फाइलहरूमा रहेका मोडेल र क्षमताहरू।
- लागू हुँदा एक्जिक्युटर/ट्रान्सलेटर छनोट, OAuth वा API-key कन्फिगरेसन, ड्यासबोर्ड एसेटहरू, र उत्पन्न गरिएको
  प्रदायक सन्दर्भ।
- सार्वजनिक क्रेडेन्सियलहरूले `resolvePublicCred()` प्रयोग गर्नुपर्छ; त्रुटि प्रतिक्रियाहरूले साझा स्यानिटाइज्ड
  त्रुटि हेल्परहरू प्रयोग गर्नुपर्छ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` मा कम्पाइल नगरिएको) र
  [त्रुटि स्यानिटाइजेसन](../security/ERROR_SANITIZATION.md) हेर्नुहोस्।

**केन्द्रित चक्र**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # क्याटलग परिवर्तन हुँदा; उत्पन्न गरिएको डिफ कमिट गर्नुहोस्
npm run lint
```

प्रभावित प्रत्येक अनुरोध परिवार पनि परीक्षण गर्नुहोस्: च्याट, Responses, इमेज, एम्बेडिङ, अडियो, वा भिडियो।
उत्पन्न गरिएका क्याटलग र गोल्डेन डिफहरूलाई अनुबन्ध परिवर्तनका रूपमा समीक्षा गर्नुहोस्; तिनलाई आँखा चिम्लेर स्वीकार नगर्नुहोस्।

### राउटिङ

**अनुबन्धहरू**

- `src/shared/constants/routingStrategies.ts` मा रहेका सार्वजनिक रणनीति मानहरू र UI मेटाडेटा।
- `open-sse/services/combo.ts` र `open-sse/services/combo/` अन्तर्गतको डिस्प्याच र क्रम निर्धारण।
- कम्बो स्किमाहरू, पर्सिस्टेन्स, रिजिलिएन्स अवस्था, मोडेल क्षमताहरू, र API/UI नियन्त्रणहरू।
- व्यवहार परिवर्तन हुँदा [Auto-Combo इन्जिन](../routing/AUTO-COMBO.md) र रिजिलिएन्ससम्बन्धी कागजात।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # रणनीति वा डिस्प्याच परिवर्तनहरू
npm run check:known-symbols      # रणनीति दर्ता परिवर्तनहरू
npm run lint
```

स्थानीय रूपमा निर्धारणात्मक नक्कली-अपस्ट्रिम परीक्षणहरू प्रयोग गर्नुहोस्। प्रत्यक्ष कम्बो स्मोक परीक्षणहरूका लागि क्रेडेन्सियल आवश्यक हुन्छन् र ती
म्यानुअल हुन्, CI का विकल्प होइनन्।

### UI / UX

**अनुबन्धहरू**

- `src/app/` र `src/shared/components/` अन्तर्गतका Next.js रुट/पेज र साझा कम्पोनेन्ट सीमाहरू।
- API प्रतिक्रिया संरचनाहरू, लोडिङ/खाली/त्रुटि अवस्थाहरू, किबोर्ड र स्क्रिन-रिडर व्यवहार,
  रेस्पोन्सिभ लेआउट, थिमिङ, र लोकेल विस्तार।
- `src/i18n/messages/en.json` मा रहेका अङ्ग्रेजी UI स्रोत स्ट्रिङहरू; प्रयोगकर्ताले देख्ने नयाँ पाठ हार्ड-कोड नगर्नुहोस्।

**केन्द्रित चक्र**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

अन्तरक्रिया वा दृश्य परिवर्तनहरूका लागि एप चलाउनुहोस् र साँघुरा तथा फराकिला दुवै भ्युपोर्ट जाँच गर्नुहोस्। CI ले
उत्पादन बिल्ड र विस्तृत सुइटहरू चलाउँछ; दृश्य व्यवहारका लागि अझै पनि परिवर्तनअनुकूल केन्द्रित कम्पोनेन्ट, Playwright,
वा अभिलेखित म्यानुअल जाँच आवश्यक हुन्छ।

### i18n

**अनुबन्धहरू**

- `src/i18n/messages/en.json` UI स्रोत हो; `config/i18n.json` लोकेल स्रोत हो।
- CLI क्याटलगहरू `bin/cli/locales/` अन्तर्गत छुट्टै रहन्छन्।
- ICU प्लेसहोल्डर र ट्यागहरू ठ्याक्कै जोगाउनुहोस्। उत्पादन/प्रदायक/मोडेलका नाम,
  प्रोटोकल र हेडरका नाम, कमान्डहरू, कोड/JSON आइडेन्टिफायरहरू, URLs, वातावरण चरहरू, वा
  `OmniRoute`, `OAuth`, `MCP`, र `A2A` जस्ता संरक्षित पदहरू अनुवाद नगर्नुहोस्। हालको स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` हो।

**केन्द्रित चक्र**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI स्ट्रिङ/क्याटलगहरू परिवर्तन हुँदा
npm run lint
```

यो विद्यमान प्रणालीका लागि मार्गदर्शन हो, यसको टुलिङ वा की मोडेल विस्तार गर्ने निमन्त्रणा होइन।
प्रतिस्थापन प्रणाली डिजाइन भइरहँदा i18n प्याचहरू सटिक र सीमित राख्नुहोस्। कार्यले उत्पन्न गरिएका अनुवादहरू स्पष्ट रूपमा आवश्यक नबनाएसम्म र
तपाईंले परिणामस्वरूप आएको डिफ समीक्षा नगरेसम्म बाह्य सेवाहरू कल गर्ने अनुवाद कमान्डहरू नचलाउनुहोस्।

### CLI

**अनुबन्धहरू**

- `bin/cli/` का सार्वजनिक कमाण्ड र फ्ल्यागहरू, उत्पन्न गरिएका API कमाण्डहरू, exit code हरू, stdout/stderr र
  JSON आउटपुटका संरचनाहरू, config/environment व्यवहार, र प्याकेज गरिएका फाइलहरू।
- CLI का प्रयोगकर्तामुखी स्ट्रिङहरूले CLI i18n तह प्रयोग गर्नुपर्छ र `en`/`pt-BR` क्याटलगहरू समक्रमित राख्नुपर्छ।
- Node लाई समर्थित runtime का रूपमा र प्रकाशित binary contract लाई कायम राख्नुहोस्।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # उत्पन्न गरिएको/बन्डल गरिएको CLI परिवर्तनहरू
npm run check:pack-policy     # प्याकेज-सतह परिवर्तनहरू
npm run lint
```

व्यवहार parsing, फाइलहरू, वा exit status मा निर्भर हुँदा अस्थायी data directory मा ठ्याक्कै सोही कमाण्ड प्रयोग गर्नुहोस्।
CI ले अझ व्यापक package artifact र ecosystem जाँचहरू गर्छ।

### Database

**अनुबन्धहरू**

- `src/lib/db/` अन्तर्गतका domain module हरू; निश्चित module हरू सिधै import गर्नुहोस् (पुरानो `localDb.ts` re-export तह हटाइएको थियो)।
- `src/lib/db/migrations/` अन्तर्गतका क्रमाङ्कित, idempotent SQL migration हरू, transaction सुरक्षा, upgrade
  व्यवहार, index हरू, र schema बाट प्रभावित प्रत्येक caller।
- Route र handler हरूले कहिल्यै raw SQL सिधै जारी गर्दैनन्।

**केन्द्रित चक्र**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration थप्दा नयाँ database र अघिल्लो schema बाट गरिने upgrade दुवै परीक्षण गर्नुहोस्। Database परीक्षणहरूले
handle हरू बन्द गर्नुपर्छ र cleanup का क्रममा `resetDbInstance()` कल गर्नुपर्छ। best-effort Bun adapter path परिवर्तन हुँदा मात्र
`npm run test:bun:db` चलाउनुहोस्; Node नै आधिकारिक रहन्छ।

### Build / deploy

**अनुबन्धहरू**

- Root र workspace manifest/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  प्याकेज सामग्री, Electron platform metadata, CI workflow हरू, र deployment sentinel हरू।
- समर्थित Node range हरू र `CLAUDE.md` मा allow-list गरिएको Bun प्रयोग अक्षुण्ण रहनुपर्छ।
- Build artifact हरू untracked रहन्छन्; dependency, license, workflow, र package नीति लागू हुन्छन्।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency वा lockfile परिवर्तनहरू
npm run check:pack-policy      # प्रकाशित प्याकेज सतहका परिवर्तनहरू
npm run lint
```

परिवर्तनले compilation, standalone assembly, asset हरू, वा runtime bundling लाई असर गर्दा मात्र स्थानीय रूपमा `npm run build` प्रयोग गर्नुहोस्।
release/deploy प्रमाणीकरणका लागि मात्र `npm run build:release` प्रयोग गर्नुहोस्। CI को build नै अन्तिम cross-platform सङ्केत हो;
platform-specific Electron परिवर्तनहरूलाई सम्बन्धित केन्द्रित build वा smoke प्रमाण आवश्यक पर्छ।

## साझा मेसिनका लागि विकासकर्ता स्क्रिप्टहरू

अन्य सत्रहरू सक्रिय रहेको devbox मा स्थानीय लूपका लागि दुई `scripts/dev/` सहायकहरूले प्रक्रिया परिभाषित गर्छन्:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD का फाइलहरू
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ठ्याक्कै यी फाइलहरू
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # अलग गरिएको worktree, समानान्तर रूपमा सुरक्षित
```

- `typecheck-touched.sh` ले 6 GB heap अन्तर्गत अस्थायी
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) मार्फत परिवर्तन गरिएका `.ts/.tsx` फाइलहरू मात्र typecheck गर्छ, त्यसैले यसले व्यस्त मेसिनमा OOM हुने परियोजनाभरिको `tsc -p tsconfig.json`
  लाई प्रतिस्थापन गर्छ। यसले परिवर्तन गरिएका फाइलहरूका त्रुटिहरूका साथै एउटा सारांश पङ्क्ति प्रिन्ट गर्छ र
  परिवर्तन गरिएका फाइलहरूमा त्रुटि भए `1`, त्रुटिहरू आयात गरिएका फाइलहरूमा मात्र भए वा tsc
  diagnostics नदिई बन्द भए `2` (यसले `_artifacts/typecheck-touched/` अन्तर्गत उल्लेख गरेको लग पढ्नुहोस्), र
  त्रुटिरहित भए `0` सहित बाहिरिन्छ। अस्थायी tsconfig सधैँ हटाइन्छ; यसलाई कहिल्यै commit नगर्नुहोस्।
- `new-worktree.sh` ले `<git-common-dir>/omniroute-new-worktree.lock` मा एकसाथ चलाइएका रनहरूलाई क्रमबद्ध गर्छ
  (पूर्वनिर्धारित रूपमा दृश्य सन्देशसहित 600 s सम्म प्रतीक्षा गर्छ; स्क्रिप्टको header मा
  override बारे दस्तावेज गरिएको छ) र worktree अस्तित्वमा आउनुअघि `git worktree add` असफल हुँदा यसले सिर्जना गरेको branch लाई
  rollback गर्छ, त्यसैले पुनः प्रयास गर्न म्यानुअल `git branch -D` आवश्यक पर्दैन। hard-linked `node_modules` र `.husky/_` प्रतिलिपि अपरिवर्तित रहन्छन्।

## स्थानीय candidate लूप

स्रोत परीक्षणहरूले प्याकेज गरिएको artifact सुरु हुन्छ भनेर प्रमाणित गर्न सक्दैनन्: packaging सूचीहरू, prune गरिएका dependencies,
र native binaries केवल tarball स्थापना गरेर सुरु गरेपछि मात्र असफल हुन्छन्। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 को एकपटक build गर्ने / validate गर्ने / promote गर्ने प्रवाहको स्थानीय पक्ष हो:
यसले एउटा candidate build गर्छ, त्यही artifact validate गर्छ, directory rename मार्फत त्यसलाई promote गर्छ,
र promote गरिएको slot को health check असफल हुँदा rollback गर्छ।

```bash
npm run dev:candidate -- run --dry-run --json  # योजना प्रिन्ट गर्ने, केही पनि परिवर्तन नगर्ने
npm run dev:candidate -- run                   # build + validate + promote, स्वचालित rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ मा स्थापना
npm run dev:candidate -- validate --id <id>    # खाली port मा सुरु गर्ने, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current र previous साट्ने
npm run dev:candidate -- run --from-tarball <file.tgz>  # अन्यत्र (CI) build गरिएको tarball पुनः प्रयोग गर्ने
```

- **एकपटक build गर्नुहोस्।** `build` ले हालको tree pack गर्छ (यसलाई `dist/server.js` चाहिन्छ, त्यसैले पहिले
  `npm run build:release` चलाउनुहोस्) वा `--from-tarball` प्रतिलिपि गर्छ, त्यसपछि tarball लाई
  अलग गरिएको npm prefix मा स्थापना गर्छ, किनकि tarball मा `node_modules` हुँदैन। id छोटो `HEAD`
  sha (tree मा स्थानीय परिवर्तनहरू हुँदा `-dirty`) वा tarball का लागि `tgz-<sha256>` हुन्छ। पहिले नै build गरिएको सफा id लाई पुनः build गर्नुको सट्टा पुनः प्रयोग गरिन्छ; पुनः build गर्न `--force` दिनुहोस्।
- **स्रोत होइन, प्याकेज validate गर्नुहोस्।** `validate` ले नयाँ `DATA_DIR=<candidate>/data`, नक्कली secrets, र
  environment बाट हटाइएका operator का `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` र `INITIAL_PASSWORD`
  सहित स्थापित CLI (`serve --port <free port>`) सुरु गर्छ, जसले गर्दा यसले नयाँ स्थापनाको keyless loopback अवस्थिति जाँच गर्छ। यसले
  `GET /api/health` ले 200 फर्काउन्जेल प्रतीक्षा गर्छ, `GET /v1/models` ले 200 फर्काउनै पर्ने बनाउँछ, process group रोक्छ,
  र tarball hash सहितको नतिजा `validation.json` मा अभिलेख गर्छ।
- **त्यही artifact promote गर्नुहोस्।** हालको tarball hash का लागि सफल validation नभएको candidate लाई `promote` ले अस्वीकार गर्छ।
  पूर्वनिर्धारित सक्रिय slot `_artifacts/candidate/current` हो; `--target <dir>`
  ले उही filesystem मा अर्को directory चयन गर्छ, र यसको अघिल्लो slot `<dir>.previous` हुन्छ।
  प्रत्येक rename atomic हुन्छ, र प्रक्रियाको बीचमा असफल भए पहिले नै चलेका rename हरू उल्टाइन्छन्।
- **Rollback गर्नुहोस्।** `run` ले promote गरिएको slot फेरि validate गर्छ र
  त्यो जाँच असफल हुँदा `current` र `previous` लाई पुनः साट्छ। पहिलो validation मै असफल भएको candidate कहिल्यै promote हुँदैन।

सबै कुरा gitignored `_artifacts/candidate/` अन्तर्गत लेखिन्छ; विद्यमान OmniRoute
स्थापना र त्यसको data directory लाई कहिल्यै छोइँदैन। promote गरिएको CLI
`_artifacts/candidate/current/prefix/bin/omniroute` हो; प्रयोग गर्दा यसलाई आफ्नै `DATA_DIR` सहित सुरु गर्नुहोस्।
Exit codes: सफलताका लागि `0`, validation वा promotion असफल भए `1`, usage error वा build नभए `2`।

## स्थानीय लूप बनाम CI

| प्रत्येक प्याचका लागि स्थानीय रूपमा चलाउनुहोस्                                 | CI ले व्यापक संकेत प्रदान गर्छ                                      |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| माथिका प्रत्यक्ष व्यवहार परीक्षणहरू र श्रेणी गेटहरू                            | शार्ड गरिएको पूर्ण युनिट सुइट र क्रमिक परीक्षणहरू                   |
| `npm run lint`                                                                 | Vitest सुइटहरू र कभरेज/गुणस्तर र्याचेटहरू                           |
| प्रभावित कन्ट्र्याक्टले आवश्यक ठहर्याउँदा मात्र टाइपचेक वा बिल्ड               | उत्पादन बिल्ड, सुरक्षा, दस्तावेज, निर्भरता र PR-नीति गेटहरू         |
| स्वचालनले व्यवहार प्रमाणित गर्न नसक्दा मात्र म्यानुअल अन्तरक्रिया/लाइभ जाँचहरू | वर्कफ्लोद्वारा कन्फिगर गरिएका क्रस-जबसँग एकीकरण र प्लेटफर्म जाँचहरू |

सफल केन्द्रित लूप परिवर्तन गरिएको कन्ट्र्याक्टबारेको प्रमाण हो, असम्बन्धित CI जाँचहरू
उत्तीर्ण हुनेछन् भन्ने प्रमाण होइन। त्यसैगरी, प्रत्येक स्थानीय सम्पादनलाई पूर्ण रिपोजिटरी म्याट्रिक्सका लागि प्रतीक्षा नगराउनुहोस्।

## सामञ्जस्य जाँचसूची

समीक्षा अनुरोध गर्नुअघि:

- PR को आधार अझै पनि सबैभन्दा उच्च सक्रिय `release/v*` शाखा हो भनी पुष्टि गर्नुहोस्।
- उक्त आधार फेच गर्नुहोस् र तपाईंले शाखा बनाएयता समावेश भएका कमिटहरू समीक्षा गर्नुहोस्।
- अनपेक्षित वा उत्पन्न फेरबदलका लागि `git diff <active-base>...HEAD` समीक्षा गर्नुहोस्।
- स्रोत अद्यावधिक गरेर र आउटपुट पुनः उत्पन्न गरेर क्याटलग तथा उत्पन्न-दस्तावेजका द्वन्द्वहरू समाधान गर्नुहोस्।
- सामञ्जस्यपछि PR विवरणमा सूचीबद्ध प्रत्येक केन्द्रित परीक्षण/गेट पुनः चलाउनुहोस्।
- सरेको आधारसँग मिलाउनका लागि मात्र एसर्शनहरू कहिल्यै कमजोर नबनाउनुहोस् वा आवश्यक परीक्षणहरू नहटाउनुहोस्।

रिलिज-फ्रिज र पुनःलक्ष्यीकरण नियमहरूका लागि,
[शाखीकरण र रिलिज मोडेल](BRANCHING_MODEL.md) प्रयोग गर्नुहोस्। पूर्ण CI सूचीका लागि,
[गुणस्तर गेट सन्दर्भ](../architecture/QUALITY_GATES.md) प्रयोग गर्नुहोस्।
