OmniRoute तीनवटा समर्पित ड्यासबोर्ड पृष्ठहरूमा विभाजित CLI उपकरणका तीन श्रेणीसँग एकीकृत हुन्छ:

| पृष्ठ          | रुट                     | अवधारणा                                                                                        | सङ्ख्या              |
| -------------- | ----------------------- | ---------------------------------------------------------------------------------------------- | -------------------- |
| **CLI Code's** | `/dashboard/cli-code`   | तपाईंले OmniRoute तर्फ निर्देशित गर्ने कोडिङ उपकरणहरू (क्लाइन्ट → CLI → OmniRoute → प्रदायक)   | 26                   |
| **CLI Agents** | `/dashboard/cli-agents` | तपाईंले OmniRoute तर्फ निर्देशित गर्ने स्वायत्त एजेन्टहरू (उही प्रवाह, अझ व्यापक कार्यक्षेत्र) | 10                   |
| **ACP Agents** | `/dashboard/acp-agents` | OmniRoute ले stdio/ACP मार्फत ब्याकएन्डका रूपमा सुरु गर्ने CLI हरू (उल्टो प्रवाह)              | रजिस्ट्री हेर्नुहोस् |

## यसले कसरी काम गर्छ

```
CLI Code's / CLI Agents (उपभोग प्रवाह):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (सबै OmniRoute तर्फ निर्देशित हुन्छन्)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute ले सही प्रदायकतर्फ रुट गर्छ)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (उल्टो रूपमा सुरु हुने प्रवाह):
    क्लाइन्ट अनुरोध → OmniRoute → stdio/ACP मार्फत CLI सुरु गर्छ → प्रतिक्रिया
```

**फाइदाहरू:**

- सबै उपकरण व्यवस्थापन गर्न एउटै API कुञ्जी
- ड्यासबोर्डमा सबै CLI हरूको लागत ट्र्याकिङ
- प्रत्येक उपकरण पुनः कन्फिगर नगरी मोडेल परिवर्तन
- स्थानीय रूपमा र रिमोट सर्भरहरूमा काम गर्छ (VPS, Docker, Akamai, Cloudflare Tunnel)

## `setup-*` मार्फत स्वतः कन्फिगर गर्नुहोस्

तपाईंले प्रत्येक उपकरणको कन्फिगरेसन हातैले लेख्नुपर्दैन। OmniRoute ले समर्थित प्रत्येक CLI का लागि एउटा `setup-*`
आदेश उपलब्ध गराउँछ, जसले चलिरहेको OmniRoute (स्थानीय वा रिमोट) बाट **प्रत्यक्ष** मोडेल क्याटलग पढ्छ
र तपाईंको मेसिनमा उपकरणको आफ्नै कन्फिगरेसन लेख्छ:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
```

प्रत्येकले `--remote <url> --api-key <key>` (रिमोट OmniRoute विरुद्ध स्थानीय उपकरण कन्फिगर गर्न),
`--dry-run` (नलेखी पूर्वावलोकन गर्न), र `--port` स्वीकार गर्छ। मोडेल स्वतः-पत्ता लगाउने सुविधा नभएका
उपकरणहरू (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive) ले `--model <id>` (र अन्तर्क्रियारहित
रनहरूका लागि `--yes`) लिन्छन्। `setup-5dive` नै `$HOME` अन्तर्गत नलेख्ने एकमात्र रेसिपी हो:
यसले फ्लीट होस्टमा root-स्वामित्व भएको प्रमाणीकरण प्रोफाइल लेखेर 5dive एजेन्ट फ्लीट कन्फिगर गर्छ,
त्यसैले यो `sudo` मार्फत पुनः कार्यान्वयन हुन्छ र यसको आफ्नै रिमोट मोड हुँदैन। सही env इन्जेक्ट गरेर
र कुनै पनि कन्फिगरेसन नलेखी CLI सुरु गर्न, सामान्य
`omniroute run <target>` लन्चर प्रयोग गर्नुहोस् (claude, codex, aider, goose, opencode, qwen,
gemini — लक्ष्यहरू र उपनामहरू `bin/cli/cli-manifest.mjs` बाट आउँछन्); पुराना प्रति-उपकरण
लन्चरहरू `omniroute launch` (Claude Code) र `omniroute launch-codex`
(Codex) अझै उपलब्ध छन्। Gemini CLI लन्च-मात्र हो: यो `omniroute run`
को लक्ष्य हो तर यसमा `setup-*`/`configure` रेसिपी छैन।

> **पूर्ण सन्दर्भ:** मुख्य तालिका — प्रत्येक आदेशले के लेख्छ, प्रत्येक फ्ल्याग,
> स्थानीय बनाम रिमोट, र कुन उपकरणलाई `/v1` प्रत्यय चाहिन्छ — यहाँ उपलब्ध छ:
> **[CLI एकीकरणहरू](../guides/CLI-INTEGRATIONS.md)**।

### यी आदेशहरू कन्टेनरभित्र चलाउँदा

OmniRoute कन्टेनरभित्र कार्यान्वयन गरिएको `setup-*` आदेशले कन्टेनरकै home मा लेख्छ,
जुन कुनै पनि होस्ट CLI ले पढ्दैन र कन्टेनरसँगै हराउँछ। OmniRoute ले यो अवस्था पत्ता लगाउँछ र
लेख्नुको सट्टा निर्देशनहरूसहित `2` मा निस्कन्छ। अगाडि बढ्ने दुईवटा समर्थित तरिकाहरू छन् —
होस्टमा CLI स्थापना गरेर कन्टेनरसँग `omniroute connect` गर्नुहोस्, वा कन्फिग डाइरेक्टरीहरू
bind-mount गरेर `CLI_CONFIG_HOME` सेट गर्नुहोस् (compose को `host` प्रोफाइल)। कन्टेनरकै
CLI हरू कन्फिगर गर्नु वास्तवमै तपाईंको उद्देश्य हो भने, प्रत्येक `setup-*` आदेशका साथै
`omniroute configure` र `omniroute config set` ले
`--allow-container-write` स्वीकार गर्छन्; सर्भरका लागि `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true`
ले पनि त्यही काम गर्छ। हेर्नुहोस्:
[Docker मार्गदर्शिका → होस्ट CLI उपकरणहरू कन्फिगर गर्ने](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker)।

ड्यासबोर्डको **apply endpoint** (`POST /api/cli-tools/apply`) ले पनि उही सुरक्षा नियम लागू गर्छ:
कन्टेनरमा, लक्ष्य होस्टबाट bind-mount गरिएको छैन भने लेख्ने अनुरोधले **`422`** सहित
`containerEphemeralTarget: true`, सुरक्षित त्रुटि पाठ र — होस्ट रेसिपी भएका उपकरणहरूका लागि
(claude, codex, opencode, cline, kilo, continue) — होस्टमा चलाउनुपर्ने `hostSetupCommand`
(जस्तै `omniroute setup-opencode`) फर्काउँछ; केही पनि लेखिँदैन। `dryRun: true` ले कन्टेनर
मोडमा पनि काम गरिरहन्छ र डिस्कलाई नछोई संवेदनशील विवरण हटाइएको पूर्वावलोकन + लक्ष्य पथ
फर्काउँछ। पूर्वावलोकन सामग्री प्रतिलिपि वा आयात गर्न मिल्ने प्रमाणपत्र-युक्त कन्फिगरेसन होइन।
मूल उपकरण/base URL/API key/model इनपुटहरू प्रयोग गरेर होस्टमा apply गर्नुहोस्, वा उल्लेख गरिएको
होस्ट-साइड setup आदेश प्रयोग गर्नुहोस्। पूर्वावलोकन header र अनुरोध contract का लागि
[CLI कन्फिगरेसन सुरक्षा](../security/CLI-CONFIGURATION.md) हेर्नुहोस्। यो व्यवहार
जानाजानी राखिएको हो र
`tests/unit/api/cli-tools/apply-container-guard.test.ts` द्वारा regression विरुद्ध सुरक्षित गरिएको छ —
guard हटाएर `422` लाई कहिल्यै "ठीक" नगर्नुहोस्।

## सत्यको आधिकारिक स्रोत

एकीकृत क्याटलग `src/shared/constants/cliTools.ts` मा `CLI_TOOLS: Record<string, CliCatalogEntry>` का रूपमा अवस्थित छ।

प्रत्येक प्रविष्टिमा यी फिल्डहरू छन् (`src/shared/schemas/cliCatalog.ts` मा परिभाषित):

| फिल्ड                                           | प्रकार                                                       | विवरण                                                   |
| ----------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| `category`                                      | `"code" \| "agent"`                                          | उपकरण कुन पृष्ठमा देखिन्छ                               |
| `vendor`                                        | `string`                                                     | उपकरणको उत्पत्ति ("Anthropic", "OSS (P. Gauthier)")     |
| `acpSpawnable`                                  | `boolean`                                                    | ACP Agent का रूपमा पनि प्रयोगयोग्य (ब्याज देखाइन्छ)     |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | अनुकूलन एन्डपोइन्ट समर्थन स्तर। `"none"` = MITM ब्याकलग |
| `configType`                                    | `"env" \| "custom" \| "guide" \| "custom-builder" \| "mitm"` | कन्फिगरेसन संयन्त्र                                     |
| `id`, `name`, `color`, `description`, `docsUrl` | मानक                                                         | मुख्य प्रदर्शन फिल्डहरू                                 |

`baseUrlSupport: "none"` भएका प्रविष्टिहरू ड्यासबोर्ड पृष्ठहरूमा **देखाइँदैनन्** — तिनीहरू योजना 11 का लागि MITM ब्याकलगमा दर्ता गरिएका छन् (`_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md` हेर्नुहोस्)।

### क्षमता तहहरू (क्याटलगबद्ध × पत्ता लगाउन सकिने × कन्फिगर गर्न सकिने × चलाउन सकिने)

क्याटलगमा समावेश गरिएको प्रत्येक उपकरण पत्ता लगाउन, कन्फिगर गर्न वा चलाउन सकिने हुँदैन। प्रत्येक तहको एउटा
घोषणात्मक स्रोत हुन्छ, र ड्रिफ्ट परीक्षणले तिनीहरूलाई समक्रमित राख्छ:

| तह                     | अर्थ                                                                  | यहाँ घोषणा गरिएको                                                |
| ---------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **क्याटलगबद्ध**        | ड्यासबोर्ड क्याटलगमा देखिन्छ (नाम, विक्रेता, कागजात, कन्फिग प्रकार)   | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                 |
| **पत्ता लगाउन सकिने**  | बाइनरी/कन्फिग पहिचान, स्वास्थ्य जाँच, कन्फिग पथहरू                    | `src/shared/services/cliRuntime.ts` (`CLI_TOOLS` रनटाइम क्याटलग) |
| **कन्फिगर गर्न सकिने** | `omniroute configure <cli>` द्वारा समर्थित (सेटअप विधि उपलब्ध छ)      | `bin/cli/cli-manifest.mjs` (`configure: true`)                   |
| **चलाउन सकिने**        | `omniroute run <target>` द्वारा समर्थित (env/args इन्जेक्सन परिभाषित) | `bin/cli/cli-manifest.mjs` (`run: true`)                         |

`bin/cli/cli-manifest.mjs` CLI कमाण्ड
सतहहरूका लागि आधिकारिक एक्जिक्युटेबल म्यानिफेस्ट हो: `run`, `configure` र शेल-कम्प्लिसन जेनेरेटरहरू सबैले आफ्ना
लक्ष्य सूचीहरू, एलियास रिजोल्युसन (उदाहरणका लागि `kilocode`/`kilo-code`/`kilo_cli` → `kilo`)
र `--model` फ्ल्यागको जडान यसैबाट प्राप्त गर्छन्। ड्रिफ्ट गार्ड
`tests/unit/cli/cli-manifest-drift.test.ts` ले म्यानिफेस्ट, रनटाइम
क्याटलग, UI क्याटलग र प्रत्येक उपभोक्ता सतह समक्रमित रहेको सुनिश्चित गर्छ — अन्य सतहहरूमा नथपी
कुनै एक सतहमा मात्र थपिएको लक्ष्य चुपचाप ड्रिफ्ट हुनुको सट्टा परीक्षण सुइट असफल गराउँछ।

## 1. CLI Code को सूची (27 उपकरण)

## 5. ब्याच पहिचान API

सबै उपकरणको पहिचान एउटै एन्डपोइन्टमार्फत एकत्रित गरिन्छ:

**`GET /api/cli-tools/all-statuses`**

- प्रमाणीकरण: `requireCliToolsAuth(request)` (अन्य `/api/cli-tools/` रुटहरूकै जस्तो)
- फिर्ता गर्छ: `Record<toolId, ToolBatchStatus>` (प्रकार: `src/shared/types/cliBatchStatus.ts`)
- रणनीति: सबै उपकरणमाथि `Promise.all`, प्रत्येक उपकरणका लागि 5s समयसीमा
- क्यास: कन्फिगरेसन फाइलको `mtime` द्वारा अनुक्रमित इन-मेमोरी LRU। mtime परिवर्तन हुँदा क्यास अमान्य हुन्छ। सर्भर पुनः सुरु हुँदा रिसेट हुन्छ।

प्रत्येक उपकरणको प्रतिक्रिया संरचना:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // सफा गरिएको, स्ट्याक ट्रेसहरू छैनन्
}
```

VS Code Insiders लाई अनुकूलित एन्डपोइन्ट मोडेलहरूका लागि कन्फिगर गरिएको छ र तपाईं OmniRoute लाई अनुकूलित हेडर फिल्डविना चलाउन चाहनुहुन्छ भने यो प्रयोग गर्नुहोस्।

**सिफारिस गरिएको स्थान:**

- Linux: `~/.config/Code - Insiders/User/chatLanguageModels.json`
- Windows: `%APPDATA%/Code - Insiders/User/chatLanguageModels.json`

**टोकनयुक्त OmniRoute उपनाम प्रयोग गर्ने उदाहरण:**

```json
[
  {
    "vendor": "customendpoint",
    "id": "auto",
    "name": "OmniRoute Auto",
    "family": "gpt-4",
    "version": "1.0.0",
    "url": "http://localhost:20128/api/v1/vscode/sk-your-omniroute-key/chat/completions",
    "modelsUrl": "http://localhost:20128/api/v1/vscode/sk-your-omniroute-key/models",
    "requestFormat": "openai-chat-completions",
    "contextWindow": 256000,
    "maxOutputTokens": 32768,
    "auth": {
      "type": "none"
    }
  }
]
```

**टिप्पणीहरू:**

- `sk-your-omniroute-key` लाई OmniRoute मा सिर्जना गरिएको API कुञ्जीले प्रतिस्थापन गर्नुहोस्।
- `url` फिल्डले `/api/v1/vscode/{token}/chat/completions` लाई सङ्केत गर्नुपर्छ।
- `modelsUrl` फिल्डले `/api/v1/vscode/{token}/models` लाई सङ्केत गर्नुपर्छ।
- क्लाइन्टले अनुकूलन हेडरहरू समर्थन गर्दा सामान्य `/v1` + Bearer हेडर प्रवाहलाई प्राथमिकता दिनुहोस्।
- URL मा समावेश गरिएका टोकनहरू अनुकूलता प्रयोजनका वैकल्पिक उपाय हुन् र ती सम्पादक लगहरू वा प्रोक्सी इतिहासमा देखिन सक्छन्।

## 10. आन्तरिक OmniRoute CLI

`omniroute` बाइनरीले सर्भरको जीवनचक्र, सेटअप, निदान र प्रदायक व्यवस्थापनका लागि आदेशहरू प्रदान गर्छ। प्रवेश बिन्दु: `bin/omniroute.mjs`।

```bash
omniroute                              # सर्भर सुरु गर्नुहोस् (पूर्वनिर्धारित पोर्ट 20128)
omniroute setup                        # अन्तरक्रियात्मक सेटअप विजार्ड
omniroute doctor                       # कन्फिगरेसन, DB, पोर्ट, रनटाइम जाँच गर्नुहोस्
omniroute providers list               # कन्फिगर गरिएका प्रदायक जडानहरू
omniroute providers test-all           # प्रत्येक सक्रिय जडान परीक्षण गर्नुहोस्
omniroute reset-password               # प्रशासकको पासवर्ड रिसेट गर्नुहोस्
omniroute logs                         # अनुरोध लगहरू स्ट्रिम गर्नुहोस्
omniroute health                       # विस्तृत स्वास्थ्य स्थिति (ब्रेकरहरू, क्यास, मेमोरी)
omniroute --version                    # संस्करण देखाउनुहोस्
omniroute --help                       # सबै आदेशहरू देखाउनुहोस्
```

### सेटअप र प्रारम्भीकरण

```bash
omniroute setup                        # अन्तरक्रियात्मक सेटअप विजार्ड
omniroute setup --non-interactive      # CI/स्वचालन मोड (env vars + flags पढ्छ)
omniroute setup --password '<value>'   # प्रशासकको पासवर्ड सिधै सेट गर्नुहोस्
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # एउटै चरणमा प्रदायक थप्नुहोस् र परीक्षण गर्नुहोस्
```

गैर-अन्तरक्रियात्मक सेटअपका लागि पहिचान गरिने वातावरणीय चरहरू:

| चर                  | उद्देश्य                                                             |
| ------------------- | -------------------------------------------------------------------- |
| `OMNIROUTE_API_KEY` | प्रदायक API कुञ्जी (Commander `.env()` मार्फत `--api-key` सँग आबद्ध) |
| `DATA_DIR`          | OmniRoute डेटा डाइरेक्टरी अधिलेखन गर्नुहोस्                          |

अन्य सबै गैर-अन्तरक्रियात्मक इनपुटहरू वातावरणीय चरका रूपमा नभई फ्ल्यागका रूपमा पठाइन्छन्:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(माथिका `omniroute setup` विकल्पहरू हेर्नुहोस्)।

### निदान

```bash
omniroute doctor                       # कन्फिगरेसन, DB, पोर्ट, रनटाइम, मेमोरी र जीवन्तता जाँच गर्नुहोस्
omniroute doctor --json                # मेसिनले पढ्न सक्ने JSON
omniroute doctor --no-liveness         # HTTP स्वास्थ्य परीक्षण छोड्नुहोस्
omniroute doctor --host 0.0.0.0        # जीवन्तता होस्ट अधिलेखन गर्नुहोस्
omniroute doctor --liveness-url <url>  # पूर्ण स्वास्थ्य अन्त्यबिन्दु URL अधिलेखन गर्नुहोस्
```

doctor ले यी जाँचहरू चलाउँछ: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory`, र `Server liveness`। कुनै पनि जाँच `fail` भएमा यो गैर-शून्य कोडसहित बन्द हुन्छ।

### प्रदायक व्यवस्थापन

```bash
omniroute providers available                       # OmniRoute प्रदायक सूची
omniroute providers available --search openai       # id/name/alias/category का आधारमा सूची फिल्टर गर्नुहोस्
omniroute providers available --category api-key    # श्रेणीअनुसार फिल्टर गर्नुहोस् (api-key, oauth, free, ...)
omniroute providers available --json                # मेसिनले पढ्न सक्ने JSON

omniroute providers list                            # कन्फिगर गरिएका प्रदायक जडानहरू
omniroute providers list --json

omniroute providers test <id|name>                  # एउटा कन्फिगर गरिएको जडान परीक्षण गर्नुहोस्
omniroute providers test-all                        # प्रत्येक सक्रिय जडान परीक्षण गर्नुहोस्
omniroute providers validate                        # स्थानीय-मात्र संरचनात्मक प्रमाणीकरण
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # विद्यमान OAuth प्रवाह
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` API-प्राथमिक हुन् र त्यसैले सक्रिय स्थानीय वा
रिमोट सन्दर्भविरुद्ध काम गर्छन्। प्रमाणपत्र इनपुटका लागि
`--credential-stdin` वा `--credential-env` प्रयोग गर्नुपर्छ; `--dry-run --json` ले
लुकाइएको उपस्थिति/स्वरूप मात्र रिपोर्ट गर्छ। `providers available` ले OmniRoute सूची पढ्छ;
`providers list/test/test-all/validate` ले आफ्नो स्थानीय SQLite व्यवहार कायम राख्छन् र
सर्भर चलिरहेको हुनु आवश्यक पर्दैन।

अनुकूलन गरिएको OpenAI-सङ्गत वा Anthropic-सङ्गत नोडका लागि, `omniroute nodes add` ले
फिर्ता गरेको नोड ID मा `omniroute keys add "$NODE_ID" --stdin` प्रयोग गरेर प्रमाणपत्रहरू संलग्न गर्नुहोस्।
यसका लागि सक्रिय सन्दर्भमा चलिरहेको सर्भर र व्यवस्थापन प्रमाणीकरण आवश्यक हुन्छ।
CLI ले `POST /api/providers` प्रयोग गर्छ, जसले नोड प्रमाणीकरण गर्छ र यसको अन्त्यबिन्दु
सेटिङहरू जडानमा प्रतिलिपि गर्छ। नोड नभएको, प्राधिकरण असफल भएको वा सर्भर अनुपलब्ध भएको
अवस्थामा स्थानीय वैकल्पिक प्रमाणपत्र सिर्जना नगरी त्रुटि फर्काइन्छ।

`nodes add --base-url` ले नोडको अन्त्यबिन्दु सेट गर्छ; यो `OMNIROUTE_BASE_URL` मा रहेको
सर्भर ठेगानाभन्दा फरक हुन्छ। OpenAPI फाइलहरूका लागि,
`omniroute openapi dump --format json --out ./openapi.json` प्रयोग गर्नुहोस्; विश्वव्यापी `--output`
ले CLI प्रदर्शन ढाँचा चयन गर्छ, गन्तव्य फाइलनाम होइन।

### पुनर्प्राप्ति र रिसेट

```bash
omniroute reset-password                # प्रशासकको पासवर्ड रिसेट गर्नुहोस् (यो पनि: omniroute-reset-password)
omniroute reset-encrypted-columns       # इन्क्रिप्टेड प्रमाणपत्र रिसेटका लागि चेतावनी + dry-run देखाउनुहोस्
omniroute reset-encrypted-columns --force  # SQLite मा इन्क्रिप्टेड प्रमाणपत्रहरू वास्तवमै null बनाउनुहोस्
```

### प्रमाणपत्र निर्यात (⚠ सावधानीपूर्वक सम्हाल्नुहोस्)

```bash
omniroute auth export                                 # चेतावनी + पुष्टिकरण चरण देखाउनुहोस् — DB पहुँच हुँदैन
omniroute auth export --force                          # सबै जडानका डिक्रिप्ट गरिएका प्रमाणपत्रहरू JSON का रूपमा stdout मा निर्यात गर्नुहोस्
omniroute auth export --force --id <id>                 # मेल खाने जडान मात्र निर्यात गर्नुहोस्
omniroute auth export --force --format env               # OMNIROUTE_<PROVIDER>_<FIELD>=<value> पङ्क्तिहरू उत्सर्जन गर्नुहोस्
omniroute auth export --force --out creds.json           # फाइलमा लेख्नुहोस् (0600 अनुमतिसहित सिर्जना गरिन्छ)
```

`auth export` **स्थानीय-मात्र** हो (प्रत्यक्ष SQLite पठन, कुनै HTTP रुट होइन) र यसले जानाजानी
**सादा पाठ** `apiKey`/`accessToken`/`refreshToken`/`idToken` मानहरू प्रिन्ट/लेखन गर्छ — यो सुविधा हो,
बग होइन। `--force` बिना डेटाबेसबाट केही पनि पढिँदैन र केही पनि डिक्रिप्ट गरिँदैन। कुनै पनि सादा पाठ
उत्सर्जन हुनुअघि stderr मा चेतावनी ब्यानर सधैं प्रिन्ट हुन्छ। `STORAGE_ENCRYPTION_KEY` सेट गरिएको
हुनुपर्छ। डिक्रिप्ट गर्न असफल हुने फिल्ड (पुरानो कुञ्जी, दूषित सिफरटेक्स्ट) लाई सम्पूर्ण निर्यात
रद्द गर्नु वा अन्तर्निहित त्रुटि चुहाउनुको सट्टा `<field>DecryptFailed: true` का रूपमा रिपोर्ट गरिन्छ।

अन्यथा उल्लेख नगरिएको अवस्थामा, यी कमान्डहरूले चलिरहेको OmniRoute सर्भर मान्छन्:

omniroute env show | get <k> | set <k> <v>  # वातावरण चरहरू निरीक्षण / सेट गर्नुहोस् (अस्थायी)

omniroute test                         # प्रदायक कनेक्टिभिटी स्मोक परीक्षण
omniroute update                       # अद्यावधिकहरू जाँच गर्नुहोस्
omniroute completion                   # शेल कम्प्लिसन उत्पन्न गर्नुहोस्

## OmniRoute CLI मार्फत inference-key नीति व्यवस्थापन गर्नुहोस्

अवस्थित inference key लाई यसको ID द्वारा निरीक्षण वा अद्यावधिक गर्न प्रमाणीकरण गरिएको व्यवस्थापन कन्टेक्स्ट प्रयोग गर्नुहोस् ([रिमोट मोड](../guides/REMOTE-MODE.md) हेर्नुहोस्):

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted`, `--model-access-mode all` को उपनाम हो। अद्यावधिकले
मोडेल allowlist खाली गर्छ। यसले scopes, connection rules, blocked models, rate limits
र cost limits सुरक्षित राख्छ, त्यसैले ती अन्य नियन्त्रणहरूले अझै पनि अनुरोध अस्वीकार गर्न सक्छन्। स्पष्ट रूपमा दिइएको
`--allowed-models ""` ले पनि `all` चयन गर्छ; अनुमति दिइएका मोडेलहरू नभएको restricted key कायम राख्न
यसलाई `--model-access-mode restricted` सँग संयोजन गर्नुहोस्।
खाली नभएको अल्पविरामद्वारा छुट्याइएको सूचीले स्पष्ट रूपमा अन्यथा निर्दिष्ट नगरिएसम्म `restricted` चयन गर्छ।
खाली नभएको allowlist सँग विरोधाभासी `all` दिइएमा अनुरोध पठाउनुअघि नै अस्वीकार गरिन्छ।

`--rate-limit 30` ले प्रतिमिनेट अनुरोधहरूको सीमा सेट गर्छ र अन्य समय
अवधिका नियमहरू सुरक्षित राख्छ। `--max-cost 5` ले साप्ताहिक सीमा परिवर्तन नगरी दैनिक USD सीमा सक्षम गर्छ;
`--max-cost 0` ले दैनिक सीमा हटाउँछ र विद्यमान usage-limit toggle
तथा साप्ताहिक सीमा सुरक्षित राख्छ। नदिइएका नीति फिल्डहरू अपरिवर्तित रहन्छन्। दर परिवर्तन गर्दा पहिले
हालको नीति पढिन्छ; एउटै key को rate-limit array मा एकै समयमा सम्पादन नगर्नुहोस्।

नीति आदेशहरूले प्रमाणीकरण गरिएको `GET`/`PATCH /api/keys/{id}` प्रयोग गर्छन् र सक्रिय
कन्टेक्स्ट तथा ग्लोबल `--api-key` विकल्पलाई मान्छन्। JSON आउटपुटमा भण्डारण गरिएको key
वा त्यसको मास्क गरिएको रूप बिना नीति फिल्डहरू मात्र हुन्छन्। inference-only credential ले
व्यवस्थापन परिवर्तनहरूलाई अधिकार दिन सक्दैन। 401/403 आएमा व्यवस्थापन
credential र कन्टेक्स्ट जाँच गर्नुपर्छ; यसले स्थानीय CLI-token वा salt विफलता प्रमाणित गर्दैन।
छुट्टै स्थानीय प्रमाणीकरण सम्झौताका लागि [CLI टोकन](../security/CLI_TOKEN.md) हेर्नुहोस्।
