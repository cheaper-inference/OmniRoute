> **सत्यको स्रोत:** `src/lib/db/reasoningCache.ts`, `open-sse/services/reasoningCache.ts`** पछिल्लो अपडेट:** 2026-06-28 — v3.8.40

OmniRoute विचार-मोड मोडेलहरूद्वारा उत्पादित सहायक `reasoning_content` क्याप्चर गर्छ र अपस्ट्रीम प्रदायकलाई आवश्यक पर्दा बहु-टर्न अनुरोधहरूमा पारदर्शी रूपमा पुन: प्ले गर्छ। यसले HTTP 400 त्रुटिहरूलाई हटाउँछ जुन कडा प्रदायकहरूले ग्राहकको वार्तालाप इतिहासमा अघिल्लो पालोको तर्क हराइरहेको बेला उठाउँछन्।

## किन यो अवस्थित छ

धेरै सोच-मोड प्रदायकहरूले फलो-अप पालो अस्वीकार नगरेसम्म** अघिल्लो सहायक सन्देशमा मूल `reasoning_content` समावेश छ** । अपस्ट्रीमले 400 फिर्ता गर्छ जस्तै सन्देशहरू:

```
Param Incorrect: The reasoning_content in the thinking mode must be passed back to the API.
```

तर सामान्य ग्राहकहरू (Cursor, Cline, Roo Code, OpenAI SDK) तिनीहरूले पुन: प्ले गर्ने इतिहासबाट `reasoning_content` स्ट्रिप गर्छन्। OmniRoute यसलाई सर्भर-साइड क्यासबाट पुनर्स्थापना गर्दछ त्यसैले अपस्ट्रीमले देखेको अनुरोध अनुरूप छ। मुद्दा #1628 ले हाइब्रिड memory/SQLite दृढता प्रस्तुत गर्‍यो त्यसैले क्यास जीवित रहन्छ प्रक्रिया पुन: सुरु हुन्छ।

## वास्तुकला

```
Turn N (assistant generates):
  → response contains reasoning_content + tool_calls
  → if requiresReasoningReplay(provider, model): cacheReasoningFromAssistantMessage()
      writes (memory + DB), one entry per tool_call.id within the request scope
  → forward response to client (which may or may not retain reasoning)

Turn N+1 (client sends follow-up):
  → translator detects: requiresReasoningReplay(provider, model) === true
  → for each assistant message with tool_calls and no reasoning_content:
      lookupReasoning(buildToolCallCacheKey(scope, toolCalls[0].id)) → memory → DB
      hit  → msg.reasoning_content = cached; recordReplay()
      miss → msg.reasoning_content = "" (legacy fallback for older DeepSeek)
  → upstream sees consistent history → no 400
```

क्याप्चर `open-sse/handlers/chatCore.ts` मा हुन्छ (दुई साइटहरू, दुई `cacheReasoningFromAssistantMessage` कल साइटहरूमा)। रिप्ले स्किमा जबरजस्ती पछि तर प्रेषण अघि `open-sse/translator/index.ts` मा हुन्छ।

उपकरण-कल प्रविष्टिहरू `buildToolCallCacheKey()` अन्तर्गत भण्डारण गरिन्छ, अनुरोध दायरा र उपकरण कल आईडीको डाइजेस्ट, त्यसैले अर्को API कुञ्जी वा सत्रले प्रयोग गरेको समान आईडीले प्रविष्टि चयन गर्दैन। दायरा `buildReasoningCacheScope()` बाट आउँछ: API कुञ्जी आईडी, र अनुरोधमा एक हुँदा सत्र कुञ्जी। त्यसैले `tool_call_id` स्तम्भ र ड्यासबोर्डले ती प्रविष्टिहरूको लागि यो डाइजेस्ट देखाउँछ।

सादा (गैर-उपकरण-कल) सहायक पालोहरू फरक रूपमा कुञ्जी गरिएका छन्: `buildAssistantMessageCacheKey()` सत्र स्कोप र सामान्यीकृत OpenAI-ढाँचा ट्रान्सक्रिप्टलाई त्यो पालोसम्म पचाउँछ, किनभने DeepSeek लाई _every_ अघिल्लो पालो `tools` उपस्थित भएपछि तर्क आवश्यक हुन्छ। प्रतिक्रियाहरू-एपीआई लक्ष्यहरूका लागि (उदाहरणका लागि `opencode-go/deepseek-v4-flash`, `/responses` मा रूट गरिएको) अपस्ट्रिम बडीले `input` बोक्छ, `messages` होइन, त्यसैले `translateRequest()` (`open-sse/translator/index.ts`) ले कलब्याक विकल्प मार्फत पचाइएको पिभोट ट्रान्सक्रिप्ट रिपोर्ट गर्छ र क्याप्चर साइटहरूले त्यही ट्रान्सक्रिप्ट पचाउँछन्। प्रतिक्रियाहरू रिप्ले पास प्रत्येक स्रोत ढाँचाको लागि OpenAI पिभोटमा चल्छ, त्यसैले Anthropic सन्देश ग्राहकहरू (Claude → OpenAI → प्रतिक्रियाहरू) पनि पुन: प्ले हुन्छन्।

## भण्डारण — हाइब्रिड मेमोरी + SQLite

तातो मार्गले क्र्यास रिकभरी र ड्यासबोर्ड दृश्यताका लागि SQLite तालिकाद्वारा समर्थित इन-मेमोरी `Map` (LRU-by-create) प्रयोग गर्दछ।

| तह     | कार्यान्वयन                                   | उद्देश्य                                     |
| ------ | --------------------------------------------- | -------------------------------------------- |
| मेमोरी | `open-sse/services/reasoningCache.ts` मा`Map` | द्रुत लुकअपहरू, 200 मा सबैभन्दा पुरानो बेदखल |
| DB     | `reasoning_cache` तालिका (`src/lib/db/`)      | रिस्टार्टहरू, ड्राइभ तथ्याङ्कहरूमा रहन्छ     |

दुबैमा लेखिन्छ । पहिले मेमोरी कन्सल्ट गर्नुहोस्, त्यसपछि DB मा फर्कनुहोस् (DB हिटहरू मेमोरीमा फिर्ता प्रवर्द्धन गरिन्छ)। DB विफलताहरू गैर-घातक — हुन् इन-मेमोरी क्यासले तातो मार्ग सेवा गर्न जारी राख्छ।

**पूर्वनिर्धारित:**

- TTL: `2h` (`TTL_MS = 2 * 60 * 60 * 1000`)
- अधिकतम मेमोरी प्रविष्टिहरू: `200` (`MAX_MEMORY_ENTRIES`)
- निष्कासन: सबैभन्दा पुरानो `createdAt` पहिले

## डाटाबेस योजना

माइग्रेसन: `src/lib/db/migrations/033_create_reasoning_cache.sql`

```sql
CREATE TABLE IF NOT EXISTS reasoning_cache (
  tool_call_id   TEXT PRIMARY KEY,
  provider       TEXT NOT NULL,
  model          TEXT NOT NULL,
  reasoning      TEXT NOT NULL,
  char_count     INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL DEFAULT (datetime('now')),
  expires_at     INTEGER NOT NULL
);
```

अनुक्रमणिकाहरू: `expires_at`, `provider`, `model`, `created_at`। `expires_at` युनिक्स युग सेकेन्डको रूपमा भण्डारण गरिएको छ; SELECT तहले `EXPIRES_AT_EPOCH_SQL` मार्फत लिगेसी पाठ मानहरूलाई सामान्य बनाउँछ।

## परिचालन नोटहरू

- **सरसफाई:** `cleanupReasoningCache()` म्याद सकिएको मेमोरी प्रविष्टिहरू सफा गर्छ र `DELETE FROM reasoning_cache WHERE expires_at <= unixepoch('now')` चलाउँछ। स्वास्थ्य-जाँच कर्मचारीहरूले यसलाई आवधिक रूपमा कल गर्छन्।
- **क्र्यास रिकभरी:** पुन: सुरु गरेपछि, मेमोरी खाली छ तर DB अझै पनि अप्रमाणित प्रविष्टिहरू राख्छ। दिइएको `tool_call_id` को लागि पहिलो लुकअप DB हिट हो; पछि लुकअपहरू मेमोरी हिटहरू हुन्।
- **कुनै तर्क छैन, कुनै क्यास छैन:** `cacheReasoningFromAssistantMessage` `0` फिर्ता गर्छ जब सहायक सन्देशमा कुनै `reasoning_content` / `reasoning` फिल्ड छैन, त्यसैले गैर-सोच प्रतिक्रियाहरूको लागि केही खर्च हुँदैन।
- **लेख्नुहोस् पनि गेट गरिएको छ:** `chatCore.ts` (गैर-स्ट्रिमिङ र स्ट्रिमिङ) मा दुबै कल साइटहरूले `cacheReasoningFromAssistantMessage()` मात्र कल गर्दछ जब `requiresReasoningReplay(provider, model)` `true` — हो भने पढ्ने साइड जाँचहरूको भविष्यवाणी गर्दछ। पुन: प्ले प्रदायकलाई कहिल्यै नछुने स्थापनाहरूले लेखन, अनुक्रमणिका अपडेट, र try/catch प्रत्येक तर्क-असर प्रतिक्रियामा भुक्तान गर्न रोक्छन्।
- **गैर-कडा प्रदायकहरू:** जब `requiresReasoningReplay` `false` हुन्छ र लक्षित ढाँचा OpenAI हुन्छ, अनुवादक** स्ट्रिप्स** बहिर्गमन सन्देशहरूबाट कुनै पनि `reasoning_content` फिल्ड — OpenAI च्याट पूराहरूले यसलाई स्वीकार गर्दैन।

## म्यूज अपारदर्शी-तर्क स्वामित्व

Muse (`muse-code`) ले कलर-बाउन्ड अपारदर्शी तर्क (`encrypted_content`) फर्काउँछ। यसलाई फरक खाता अन्तर्गत पुन: प्ले गर्दा वा रिमिन्ट गरिएको प्रमाणहरू अपस्ट्रीम असफल हुन्छ, त्यसैले नेटिभ OAuth अनुरोधहरूले प्रति-अनुरोध रोटेशनको सट्टा सत्र-स्तर स्वामित्व प्रयोग गर्दछ (`src/sse/services/museSessionOwnership.ts`, `src/sse/handlers/chat.ts` मा लागू गरिएको)। स्पष्ट रूपमा चयन गरिएको API-कुञ्जी जडानहरू र API-कुञ्जी-मात्र कन्फिगरेसनहरूले यो स्वामित्व मोड बिना तिनीहरूको अवस्थित राउटिङ कायम राख्छन्।

- प्रत्येक मोडमा स्थिर सत्र ID आपूर्ति गर्नुहोस्: `x-omniroute-session-id`, `x-omniroute-session`, `x-session-id`, वा `x-codex-session-id`; वैकल्पिक रूपमा शरीरमा `prompt_cache_key`, `session_id`, `conversation_id`, वा `metadata.session_id` प्रयोग गर्नुहोस् (त्यो अग्रक्रममा)। दुई वा बढी नेटिभ OAuth खाताहरू सक्रिय हुँदा छुटेको वा खाली IDs फिर्ता 400; एकल OAuth खातामा घुमाउनको लागि केहि छैन, त्यसैले यस्तो अनुरोध अनपिन राउटिंग राख्छ। दायराले कलरको OmniRoute API-key ID समावेश गर्दछ।
- एपीआई-कुञ्जी जडान नीति द्वारा अनुमति दिइएको सक्रिय नेटिभ OAuth खाताहरूमा ताजा स्वतन्त्र सत्रहरू राउन्ड-रोबिन, जडान ID द्वारा क्रमबद्ध। राउन्ड-रोबिनले टर्मिनल स्थिति (`banned`, `expired`, `credits_exhausted`), वा अनुरोध गरिएको मोडेलको लागि मोडेल-लक भएको जडान कूलडाउनमा खाताहरू छोड्छ; म्यूज अपस्ट्रीम विफलताहरूले अन्य प्रदायकहरू जस्तै कूलडाउन र ब्रेकर अवस्था रेकर्ड गर्दछ। स्पष्ट रूपमा जबरजस्ती जडानले नयाँ सत्रको लागि राउन्ड-रोबिनलाई बाइपास गर्छ तर अवस्थित मालिकलाई ओभरराइड गर्न सक्दैन।
- मालिकले सफल प्रतिक्रिया नदिएसम्म, मालिक अनुपलब्ध भएको सत्रलाई स्वस्थ खातामा पुन: दावी गरिन्छ। पहिलो सफल प्रतिक्रिया पछि, सत्र 30 दिन (`MUSE_SESSION_IDLE_TTL_MS`) को लागि निष्क्रिय नभएसम्म त्यो मालिकमा पिन रहन्छ।
- प्रत्येक निरन्तरता र उपकरण-परिणाम पालो सत्र मालिकमा पिन रहन्छ: जडान, खाता पहिचान, र अनुमान-प्रमाणपत्र उत्पादन, क्रेडेन्सियल-रिफ्रेस पुन: प्रयासहरू सहित अपस्ट्रीम प्रयासहरू अघि फेरि जाँच गरियो। प्रतिक्रियाहरू कल IDs/item सन्दर्भहरू र च्याट पूरा गर्ने उपकरण-कल IDs त्यो सत्र र पुस्ताको लागि रेकर्ड गरिएको हुनुपर्छ।
- SQLite `key_value` रेकर्डहरू `muse_session_ownership` नेमस्पेस (`src/lib/db/museSessionOwnership.ts`) मा कायम रहन्छ स्वामित्व र रोटेशन कर्सर पुन: सुरु हुन्छ। प्रत्येक दावी र प्रस्तुत प्रतिक्रियाले सत्रको गतिविधि स्ट्याम्प ताजा गर्दछ; `MUSE_SESSION_IDLE_TTL_MS` भन्दा लामो सत्र निष्क्रिय छ (मालिकको पिन, सेवा गरिएको झण्डा र रेकर्ड गरिएको opaque/reference ह्यासहरू), प्रत्येक 10 मिनेटमा एक पटक र बाउन्ड ब्याचहरूमा, त्यसैले यसको इतिहासको पछिको पुन: प्ले अज्ञात मालिकको रूपमा बन्द हुन्छ। रेकर्डहरूमा जडान IDs र खाता पहिचानको ह्यासहरू, प्रमाणहरू, अपारदर्शी सामग्री, र निरन्तरता सन्दर्भहरू समावेश छन्, गोप्य वा कुराकानी इतिहास होइन। ग्राहकहरूले आफ्नो पूर्ण इतिहास र अपारदर्शी तर्कहरू राखेर पठाउनु पर्छ।
- अज्ञात वा विदेशी अपारदर्शी तर्क, एक हराएको मालिक, एक अनुपलब्ध मालिक खाता, वा रेकर्ड गरिएको इतिहासको साथ एक पुस्ता परिवर्तन एक स्पष्ट 4xx/503 — कहिल्यै मौन क्रस-खाता असफलता संग बन्द असफल हुन्छ र तर्क कहिल्यै छोड्दैन।
- सत्रले पुन: खेल्न मिल्ने इतिहास रेकर्ड नगरेमा मात्र सम्झाइएको समान खाता कुञ्जी अपनाइन्छ; रेकर्ड गरिएका सत्रहरू ताजा सुरु नभएसम्म बन्द बन्द रहन्छन्।
- एक खाली अपस्ट्रीम प्रतिक्रिया (`upstream_empty_response` / `empty_response`, कलरमा उत्सर्जित केहि पनि छैन) एउटै मालिकमा बढीमा दुई पटक पुन: प्रयास गरिन्छ, 0.5 s पछि 1.5 s (`MUSE_EMPTY_RESPONSE_RETRY_DELAYS_MS`)। यदि सबै प्रयासहरू खाली छन् भने, मूल 502 कूलडाउन वा ब्रेकर मार्किङ बिना फर्काइन्छ, त्यसैले फ्ल्याकी जवाफले मालिकलाई कहिल्यै बन्द गर्दैन।
- सबै `muse-code` अनुरोधहरूले स्ट्रिमिङ राइटहरू सहित सिमान्टिक-क्यास पढ्ने र लेख्नेहरूलाई बाइपास गर्दछ, त्यसैले क्यास गरिएको अपारदर्शी आउटपुटले फरक सत्र मालिक प्राप्त गर्न सक्दैन।
