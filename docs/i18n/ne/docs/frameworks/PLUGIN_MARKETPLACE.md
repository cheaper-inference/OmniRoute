> **आधिकारिक स्रोत:** `src/lib/plugins/` (`marketplace.ts`, `manager.ts`, `manifest.ts`,
> `scanner.ts`, `loader.ts`), `src/app/api/plugins/`, र
> `src/app/(dashboard)/dashboard/plugins/`
> **अन्तिम अद्यावधिक:** 2026-06-28 — v3.8.40

OmniRoute सँग WordPress-जस्तो प्लगइन प्रणाली समावेश छ। प्लगइनहरू आफैंमा पूर्ण
डाइरेक्टरीहरू हुन् — प्रत्येकमा एउटा `plugin.json` म्यानिफेस्ट र एउटा प्रवेश फाइल हुन्छ — जसले
अनुरोध पाइपलाइन (`onRequest` / `onResponse` / `onError`) र
जीवनचक्र घटनाहरू (`onInstall` / `onActivate` / `onDeactivate` / `onUninstall`) मा हुक गर्छन्।

**प्लगइन मार्केटप्लेस** उक्त प्रणालीमाथिको खोज तह हो। यसले स्थापना गर्न सकिने
प्लगइनहरूको ब्राउज गर्न मिल्ने क्याटलग उपलब्ध गराउँछ। पूर्वनिर्धारित रूपमा क्याटलग एउटा
सानो अन्तर्निर्मित प्रारम्भिक रजिस्ट्री हो; सञ्चालकले यसलाई अनुकूलित रिमोट
रजिस्ट्री URL तर्फ निर्देशित गर्न सक्छन्, जसको हकमा फेचलाई DNS-रिजोल्भिङ SSRF गार्डद्वारा
सुरक्षित बनाइन्छ ([सुरक्षा](#security) हेर्नुहोस्)।

प्रत्येक प्लगइन रुट **लुपब्याकमा मात्र सीमित** छ (Tier 1 — `LOCAL_ONLY`): प्लगइनहरूले
चाइल्ड प्रोसेसहरूमा कोड लोड र कार्यान्वयन गर्ने भएकाले, प्रमाणीकरण जे भए पनि
गैर-लुपब्याक मूलबाट यी रुटहरू पहुँचयोग्य हुँदैनन्।
[`docs/security/ROUTE_GUARD_TIERS.md`](../security/ROUTE_GUARD_TIERS.md) हेर्नुहोस्।

## यो कसरी Together फिट हुन्छ

```
Dashboard (/dashboard/plugins)
  ├─ "Installed" tab  → GET /api/plugins            (listPlugins)
  │                     POST /api/plugins/scan      (pluginManager.scan)
  │                     POST /api/plugins/{name}/activate|deactivate
  │                     DELETE /api/plugins/{name}   (uninstall)
  └─ "Marketplace" tab → GET /api/plugins/marketplace
                          → listMarketplacePlugins()
                            ├─ no custom URL → built-in SEED_REGISTRY
                            └─ custom URL → isSafeMarketplaceUrl() SSRF guard
                                          → safeOutboundFetch(guard:"public-only")
```

- **रजिस्ट्री तह** — `src/lib/plugins/marketplace.ts`: कुनै पनि असफलतामा बीज रजिस्ट्रीमा फर्केर, सूचीहरू / सूचीहरू खोज्नुहोस्।
- **जीवनचक्र तह** — `src/lib/plugins/manager.ts` (`pluginManager` सिंगलटन): स्थापना गर्नुहोस्, अपग्रेड गर्नुहोस्, सक्रिय गर्नुहोस्, निष्क्रिय गर्नुहोस्, स्थापना रद्द गर्नुहोस्, स्क्यान गर्नुहोस्, स्टार्टअप लोड गर्नुहोस्।
- **प्रकट तह** — `src/lib/plugins/manifest.ts`: `plugin.json` को लागि Zod स्कीमा + पूर्वनिर्धारित।
- **स्क्यानर** — `src/lib/plugins/scanner.ts`: प्लगइन डाइरेक्टरी अन्तर्गत डिस्कमा प्लगइनहरू पत्ता लगाउँदछ।
- **लोडर** — `src/lib/plugins/loader.ts`: प्रत्येक प्लगइनलाई छुट्टै Node.js चाइल्ड प्रक्रियामा स्प्यान गर्दछ र दलालहरूले IPC मा कलहरू हुक गर्दछ। बच्चा स्यान्डबक्स होइन (तल "प्लगइन कार्यान्वयन अलगाव" हेर्नुहोस्)।

## मार्केटप्लेस क्याटलग

`listMarketplacePlugins()` (`src/lib/plugins/marketplace.ts`) ले
`MarketplaceEntry` वस्तुहरूको सूची फर्काउँछ:

| फिल्ड         | प्रकार   | टिप्पणी                                      |
| ------------- | -------- | -------------------------------------------- |
| `name`        | string   | kebab-case प्लगइन नाम                        |
| `version`     | string   | semver                                       |
| `description` | string   | छोटो सारांश                                  |
| `author`      | string   | लेखक / संस्था                                |
| `license`     | string   | SPDX-शैलीको इजाजतपत्र id                     |
| `downloadUrl` | string   | स्रोत डाउनलोड URL (खाली हुन सक्छ)            |
| `repository`  | string?  | वैकल्पिक रिपोजिटरी URL                       |
| `tags`        | string[] | खोज/फिल्टर ट्यागहरू                          |
| `downloads`   | number   | डाउनलोड सङ्ख्या                              |
| `rating`      | number   | 0–5                                          |
| `verified`    | boolean  | प्रविष्टिलाई प्रमाणित चिन्ह लगाइएको छ कि छैन |
| `lastUpdated` | string   | ISO-जस्तो मिति स्ट्रिङ                       |

कुनै अनुकूलित रजिस्ट्री URL कन्फिगर नगरिएको अवस्थामा, क्याटलग अन्तर्निर्मित
`SEED_REGISTRY` हुन्छ (हाल `request-logger`, `rate-limiter`, `cost-tracker`, र
`theme-manager`)। प्रारम्भिक रजिस्ट्री सधैं उपलब्ध हुन्छ — यदि कन्फिगर गरिएको रिमोट
रजिस्ट्री पहुँचयोग्य छैन, गैर-`200` स्थिति फर्काउँछ, वा पहिचान गर्न नसकिने
बडी फर्काउँछ भने, `listMarketplacePlugins()` ले चेतावनी लग गर्छ र प्रारम्भिक सूची प्रयोग गर्छ।

> टिप्पणी: मार्केटप्लेस **क्याटलग** (ब्राउज/खोज) सुरुदेखि अन्त्यसम्म जडान गरिएको छ, तर
> क्याटलगबाट एक-क्लिक मार्केटप्लेस **स्थापना** अझै कार्यान्वयन गरिएको छैन —
> मार्केटप्लेस प्रविष्टिमा रहेको ड्यासबोर्डको "स्थापना गर्नुहोस्" बटनले हाल
> "चाँडै आउँदैछ" सूचना देखाउँछ। अहिले स्थापना स्थानीय-पाथ स्थापना
> प्रवाह (`POST /api/plugins`) र डिस्कमा आधारित खोज (`POST /api/plugins/scan`) मार्फत हुन्छ।

## REST API

सबै अन्तिम बिन्दुहरूलाई व्यवस्थापन प्रमाणीकरण आवश्यक छ (`requireManagementAuth`)** र** लुपब्याक-मात्र — `/api/plugins` र `/api/plugins/` `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`) मा सूचीबद्ध छन्।

| अन्तिम बिन्दु                      | विधि   | विवरण                                                                  |
| ---------------------------------- | ------ | ---------------------------------------------------------------------- |
| `/api/plugins`                     | GET    | स्थापित प्लगइनहरू सूचीबद्ध गर्नुहोस् (वैकल्पिक `?status=` फिल्टर)      |
| `/api/plugins`                     | POST   | प्लगइन स्रोत डाइरेक्टरीबाट प्लगइन स्थापना गर्नुहोस्                    |
| `/api/plugins/scan`                | POST   | प्लगइन डाइरेक्टरी स्क्यान गर्नुहोस् र नयाँ प्लगइनहरू दर्ता गर्नुहोस्   |
| `/api/plugins/marketplace`         | GET    | बजार सूची सूची प्रविष्टिहरू                                            |
| `/api/plugins/marketplace/install` | POST   | नामद्वारा मार्केटप्लेस प्लगइन स्थापना गर्नुहोस्                        |
| `/api/plugins/[name]`              | GET    | स्थापित प्लगइन विवरण प्राप्त गर्नुहोस्                                 |
| `/api/plugins/[name]`              | DELETE | प्लगइन अनइन्स्टल गर्नुहोस्                                             |
| `/api/plugins/[name]/activate`     | POST   | सक्रिय गर्नुहोस् ( + दर्ता हुकहरू लोड गर्नुहोस्)                       |
| `/api/plugins/[name]/deactivate`   | POST   | निष्क्रिय गर्नुहोस् (फायर `onDeactivate`, दर्ता हुकहरू रद्द गर्नुहोस्) |
| `/api/plugins/[name]/config`       | GET    | प्लगइन कन्फिगरेसन + कन्फिगरेसन स्कीमा प्राप्त गर्नुहोस्                |
| `/api/plugins/[name]/config`       | PUT    | प्लगइन कन्फिगरेसन अपडेट गर्नुहोस् (स्कीमा विरुद्ध मान्य)               |

`GET /api/plugins` `status` फिल्टरले `installed` / `active` / `inactive` / `error` मध्ये एक स्वीकार गर्दछ। अवैध मानले `400` फर्काउँछ।

### स्थापित प्लगइनहरू सूचीबद्ध गर्नुहोस्

```bash
curl http://localhost:20128/api/plugins \
  -H "Cookie: auth_token=..."
```

### स्थानीय मार्गबाट स्थापना गर्नुहोस्

```bash
curl -X POST http://localhost:20128/api/plugins \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{ "path": "/absolute/path/to/my-plugin" }'
```

`path` हुनुपर्छ** निरपेक्ष** डाइरेक्टरीमा जाने बाटो** प्लगइन स्रोत निर्देशिका भित्र** : प्लगइन रूटको छेउमा `plugin-sources`, त्यसैले पूर्वनिर्धारित रूपमा `~/.omniroute/plugin-sources/`, वा `<parent of OMNIROUTE_PLUGINS_DIR>/plugin-sources/` जब त्यो चर सेट हुन्छ (`getPluginSourcesDir()` मा `src/lib/plugins/installSource.ts`)। त्यहाँ पहिले प्लगइन प्रतिलिपि वा क्लोन गर्नुहोस्। जब पथमा `..` वा नल बाइट हुन्छ, त्यो डाइरेक्टरी बाहिर हुन्छ, symlink मार्फत यसको बाहिर समाधान हुन्छ, symlink समावेश हुन्छ जसको लक्ष्य बाहिर हुन्छ, वा डाइरेक्टरी अवस्थित हुँदैन भने `400` सँग इन्स्टल गर्न अस्वीकार गरिन्छ। स्रोत डाइरेक्टरीमा मान्य `plugin.json` हुनु पर्छ (वा एकको अभिभावक हुनुहोस्)। सफलता मा प्रतिक्रिया स्थापित प्लगइन पङ्क्ति संग `201` छ।

अन्य प्लगइन मार्गहरू जस्तो नभई, लगइन असक्षम हुँदा पनि यसलाई व्यवस्थापन प्रमाण (ड्यासबोर्ड सत्र वा व्यवस्थापन-स्कोप गरिएको API कुञ्जी) आवश्यक पर्दछ (`requireLogin=false`): स्थापना कोड कहिल्यै बेनामी कार्य होइन। त्यही कुरा `POST /api/plugins/marketplace/install` (body `{ "name": "<plugin>" }`) मा लागू हुन्छ।

### बजार ब्राउज गर्नुहोस्

```bash
curl http://localhost:20128/api/plugins/marketplace \
  -H "Cookie: auth_token=..."
```

### प्लगइन कन्फिगरेसन अपडेट गर्नुहोस्

```bash
curl -X PUT http://localhost:20128/api/plugins/my-plugin/config \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{ "config": { "level": "debug", "maxItems": 100 } }'
```

`PUT .../config` `src/lib/plugins/manifest.ts` बाट `validatePluginConfig()` सँग प्लगइनको `configSchema` (म्यानिफेस्टमा घोषणा गरिएको) विरुद्ध शरीरलाई प्रमाणित गर्छ : प्रत्येक कुञ्जी स्किमामा घोषित गरिनुपर्छ, मानहरू घोषित प्रकारसँग मेल खानुपर्छ, `number` क्षेत्रहरू सम्मान `min`/`max`, र `select` क्षेत्रहरू घोषित `enum` सँग मेल खानुपर्छ। कुनै पनि उल्लङ्घनले `400` फर्काउँछ र केहि पनि भण्डार गरिएको छैन। कुनै `configSchema` घोषणा गर्ने प्लगइनमा कन्फिगर योग्य कुञ्जीहरू छैनन्, त्यसैले अनुरोधलाई `400` सँग अस्वीकार गरिएको छ ("प्लगइनले कुनै पनि कन्फिगर योग्य कुञ्जीहरू घोषणा गर्दैन")।

## कन्फिगरेसन

### Plugin directory

Plugins OmniRoute data directory अन्तर्गत रहन्छन्:

```
~/.omniroute/plugins/<plugin-name>/
  ├─ plugin.json
  └─ index.js          # (वा manifest.main ले देखाएको जुनसुकै फाइल)
```

`getDefaultPluginDir()` (`src/lib/plugins/scanner.ts`) ले उक्त directory लाई
तीन चरणमा निर्धारण गर्छ:

1. **`OMNIROUTE_PLUGINS_DIR`**, सेट गरिएको अवस्थामा — `HOME` को मान जे भए पनि, जस्ताको तस्तै प्रयोग गरिन्छ। यो
   Docker/K8s का लागि स्पष्ट नियन्त्रण हो, जहाँ plugin tree सामान्यतया container को home directory सँग
   कुनै सम्बन्ध नभएको path मा bind-mount गरिएको हुन्छ (#11827)।
2. `<home>/.omniroute/plugins`, जहाँ `<home>` `HOME` / `USERPROFILE`
   environment variables बाट आउँछ।
3. `/tmp/.omniroute/plugins`, जब process ले कुनै home नै export गर्दैन।

निर्धारित directory लाई startup मा एकपटक `scanner.dir_resolved` का रूपमा log गरिन्छ, जसमा
प्रयोग भएको input (`OMNIROUTE_PLUGINS_DIR`, `home`, वा `no-home-fallback`) उल्लेख हुन्छ — त्यसैले कुनै image
चुपचाप चरण 3 मा पुगेमा, खाली plugin list मात्र रिपोर्ट गर्नुको सट्टा त्यसबारे बताउँछ।
`POST /api/plugins/scan` ले त्यहाँका मान्य `plugin.json` भएका सबै subdirectory पत्ता लगाएर
दर्ता गर्छ; यही directory `pluginManager.install()` ले plugins प्रतिलिपि गर्ने root पनि हो,
त्यसैले override गर्दा discovery र installation दुवै सँगसँगै सर्छन्।

> **`OMNIROUTE_PLUGINS_DIR`, `OMNIROUTE_PLUGIN_PATH` होइन।** पछिल्लो मानलाई
> CLI command-plugin loader (`bin/cli/plugins.mjs`) ले मात्र `omniroute-cmd-*` npm
> packages खोज्नका लागि पढ्छ, जसले `omniroute` subcommands थप्छन् — यहाँ वर्णन गरिएको runtime scanner मा
> यसको कुनै प्रभाव हुँदैन। त्यस पक्षका लागि [PLUGINS.md](./PLUGINS.md) हेर्नुहोस्।

### अनुकूल marketplace registry URL

Marketplace catalog को स्रोत `pluginMarketplaceUrl` setting बाट पढिन्छ
(`src/lib/plugins/marketplace.ts` ले `settings.pluginMarketplaceUrl` पढ्छ)। यसलाई
`http(s)` URL मा सेट गर्दा, `listMarketplacePlugins()` ले उक्त URL fetch गर्छ र
entries को top-level JSON array वा `plugins` array भएको object मध्ये कुनै एक स्वीकार गर्छ;
string `name` नभएका entries हटाइन्छन्। सेट नगरिएको अवस्थामा (वा fetch
SSRF guard मा असफल भएमा / खराब response फर्काएमा), built-in seed registry
प्रयोग गरिन्छ।

Dashboard को "Marketplace" tab ले यो URL का लागि field उपलब्ध गराउँछ (`GET /api/settings`
बाट फिर्ता पढिन्छ)।

> कार्यान्वयनसम्बन्धी टिप्पणी: dashboard को "Save" action ले
> `pluginMarketplaceUrl` लाई `PATCH /api/settings` मा पठाउँछ। यो लेखिँदाको समयमा यो
> key `updateSettingsSchema`
> (`src/shared/validation/settingsSchemas.ts`) मा घोषणा गरिएको छैन, त्यसैले यसमा निर्भर हुनुअघि आफ्नो
> release मा persistence प्रमाणित गर्नुहोस् — settings store मा key उपस्थित भएपछि **read**
> path (`getSettings()` → `listMarketplacePlugins()`) ले त्यसलाई प्रयोग गर्छ।

## सुरक्षा

### रुट टियर — लुपब्याक मात्र

प्लगइनहरूले जन्मेको बाल प्रक्रियाहरूमा कोड कार्यान्वयन गर्दछ, त्यसैले सम्पूर्ण `/api/plugins` सतहलाई `LOCAL_ONLY` (Tier 1) वर्गीकृत गरिएको छ। लूपब्याक प्रवर्तन बिना शर्त चल्छ** अघि** कुनै पनि प्रमाणीकरण जाँच, त्यसैले सुरुङमा बक्समा पुग्ने एउटा लीक व्यवस्थापन टोकनले अझै पनि प्लगइन स्थापना, सक्रिय वा स्थापना रद्द गर्न सक्दैन। [`docs/security/ROUTE_GUARD_TIERS.md`](../security/ROUTE_GUARD_TIERS.md) र कडा नियमहरू #15 / #17 हेर्नुहोस्।

### बजार रजिस्ट्री SSRF गार्ड

अनुकूलन रजिस्ट्री URL आक्रमणकर्ता-प्रभावकारी कन्फिगरेसन हो, त्यसैले यसलाई ल्याउनु अघि `listMarketplacePlugins()` यसलाई दुई तहहरू मार्फत चलाउँछ:

1. **`isSafeMarketplaceUrl(url)`** (`src/lib/plugins/marketplace.ts`):
   - `http:` / `https:` नभएको कुनै पनि कुरालाई अस्वीकार गर्दछ।
   - शाब्दिक private/loopback/link-local/ULA होस्टहरू अस्वीकार गर्दछ (IPv4** र** IPv6, IPv4-mapped सहित ) क्यानोनिकल `isPrivateHost` (`src/shared/network/outboundUrlGuard.ts`) मार्फत।
   - समाधान गर्छ** दुबै** `A` र `AAAA` रेकर्ड गर्दछ र यदि अस्वीकार गर्दछ** कुनै पनि** समाधान गरिएको ठेगाना निजी — हो सार्वजनिक-होस्टनाम → निजी-आईपी बाइपास बन्द गर्दै।
   - **असफल बन्द** : DNS रिजोल्युसन विफलताले URL लाई अस्वीकार गर्दछ।
2. **`safeOutboundFetch(url, { guard: "public-only", timeoutMs: 5000 })`** (`src/shared/network/safeOutboundFetch.ts`): सार्वजनिक मात्र URL गार्ड ल्याउने समयमा र** अवरुद्ध पुनर्निर्देशन** (कुनै सार्वजनिक → निजी `30x` पिभोट छैन)।

कुनै पनि तहमा असफल भएको URL ले अनुरोधलाई रद्द गर्दैन — बजार चुपचाप बिल्ट-इन बीज रजिस्ट्रीमा फर्कन्छ र चेतावनी लगाउँछ।

> यो गार्ड PR #3774 मा विशेष गरी A + AAAA समाधान गर्न र IPv4-only चेकको सट्टा क्यानोनिकल `isPrivateHost` प्रयोग गर्न कडा बनाइएको थियो।

### प्लगइन कार्यान्वयन अलगाव

> **प्लगइनहरू पूर्वनिर्धारित रूपमा स्यान्डबक्स गरिएका छैनन्।** बच्चा OmniRoute प्रयोगकर्ताको रूपमा चलिरहेको एक सामान्य Node.js प्रक्रिया हो, कुनै VM सन्दर्भ र कुनै Node.js अनुमति झण्डाहरू बिना, त्यसैले प्लगइन कोडले प्रयोगकर्ताले गर्न सक्ने कुनै पनि फाइल पढ्न र लेख्न सक्छ, प्रोग्रामहरू चलाउन र नेटवर्कमा पुग्न सक्छ। `requires.permissions` मात्र निर्णय गर्छ कि बच्चाले कुन परिवेश चरहरू प्राप्त गर्छ। अन्य अनुमतिहरू लागू छैनन्। अप्ट-इन `PLUGIN_PERMISSION_MODEL_ENABLED` सुविधा झण्डा (पूर्वनिर्धारित रूपमा बन्द) ले प्रत्येक प्लगइनलाई ती अनुमतिहरूबाट निर्मित Node.js अनुमति मोडेल अन्तर्गत चलाउँछ, `network` बाहेक, जुन Node.js प्रतिबन्ध लगाउन सक्दैन (हेर्नुहोस् [`PLUGIN_SDK.md`](./PLUGIN_SDK.md#permission-system) )। तपाईंले विश्वास गर्ने प्लगइनहरू मात्र स्थापना गर्नुहोस्। तलको प्रक्रिया सीमाले क्र्यास र ह्याङ्गहरू समावेश गर्दछ; यो सुरक्षा सीमा होइन।

- **प्रक्रिया अलगाव** — `loadPlugin()` (`src/lib/plugins/loader.ts`) ले प्रत्येक प्लगइनलाई छुट्टै Node.js चाइल्ड प्रक्रियामा स्प्यान गर्छ र IPC मा सञ्चार गर्छ। हुक कलहरूमा `SIGTERM` → `SIGKILL` एस्केलेसनसँग टाइमआउट हुन्छ।
- **Env अनुमति सूची** — बच्चाले वातावरणीय चरहरूको केवल एक स्वीकृत सेट प्राप्त गर्दछ; फराकिलो सेट तब मात्र दिइन्छ जब manifest ले `env` अनुमति अनुरोध गर्दछ।
- **स्रोत कन्टेनमेन्ट स्थापना गर्नुहोस्** — `POST /api/plugins` प्लगइन स्रोत डाइरेक्टरीबाट मात्र पढ्छ ("स्थानीय मार्गबाट स्थापना गर्नुहोस्" हेर्नुहोस्): पथ `realpath` सँग क्यानोनिकलाइज गरिएको छ, त्यो डाइरेक्टरी भित्र कडाइका साथ रहनु पर्छ, र कुनै पनि कुरा प्रतिलिपि गर्नु अघि यो भाग्ने सिमलिङ्क बोक्ने स्रोत रूखलाई अस्वीकार गरिन्छ।
- **मार्ग नियन्त्रण** — install/upgrade/uninstall जोड दिन्छ कि प्लगइन डाइरेक्टरी र `manifest.main` समाधान** भित्र** कुनै पनि प्रतिलिपि वा पुनरावर्ती मेटाउनु अघि व्यवस्थित प्लगइन रूट (छेड़छाड गरिएको DB पथहरू र `manifest.main` मा `../` ट्राभर्सल विरुद्ध गार्डहरू)। सक्रियताले `realpath` मार्फत सिमलिङ्कहरू समाधान गर्छ र प्लगइन डाइरेक्टरीबाट भाग्ने प्रविष्टि बिन्दु लोड गर्न अस्वीकार गर्दछ।
- **वैकल्पिक अखंडता पिन** — a manifest ले `integrity` (`sha256-<base64>`, SRI ढाँचा) क्षेत्र घोषणा गर्न सक्छ। उपस्थित हुँदा, लोडरले लोड समयमा प्रविष्टि फाइल ह्यास प्रमाणित गर्छ र बेमेलमा सक्रिय गर्न अस्वीकार गर्दछ। यो छेडछाड पत्ता लगाउन अप्ट-इन हो,** होइन** सुरक्षा सीमा: यसले लोड गरिएको प्लगइनले के गर्न सक्छ भनेर सीमित गर्दैन।
- **हुकहरूमा कुनै ग्राहक प्रमाणहरू छैनन्** — सन्दर्भ `onRequest`, `onResponse` र `onError` मा `authorization`, `x-api-key`, `proxy-authorization` र `cookie` हेडरहरू हटाइएको छ, र API कुञ्जी रेकर्डले कुनै कुञ्जी मान राख्दैन ( `src/lib/plugins/hooks.ts` मा`redactPluginContext()` )।

## जीवनचक्र प्रवाह

```
install (POST /api/plugins, पथ)
  → manifest स्क्यान/प्रमाणीकरण → staging मा प्रतिलिपि → main डाइरेक्टरीभित्र रहेको सुनिश्चित
  → ~/.omniroute/plugins/<name> मा परमाणविक पुनःनामकरण → DB पङ्क्ति थप्ने
  → onInstall चलाउने → enabledByDefault भएमा: activate

activate (POST /api/plugins/{name}/activate)
  → realpath सीमाभित्र रहेको जाँच → loadPlugin() (चाइल्ड प्रक्रिया सुरु गर्ने)
  → घोषित hooks दर्ता गर्ने → status = "active" → onActivate चलाउने

deactivate (POST /api/plugins/{name}/deactivate)
  → onDeactivate चलाउने (दर्ता हटाउनुअघि) → hooks को दर्ता हटाउने
  → चाइल्ड प्रक्रिया अन्त्य गर्ने → status = "inactive"

uninstall (DELETE /api/plugins/{name})
  → सक्रिय भएमा deactivate → onUninstall चलाउने
  → सीमाभित्र रहेको जाँचसहित plugin डाइरेक्टरी पुनरावर्ती रूपमा मेटाउने → DB पङ्क्ति मेटाउने
```

स्थापित संस्करणभन्दा manifest संस्करण **कडाइका साथ नयाँ** भएको डाइरेक्टरीमा
`install` पुनः चलाउँदा स्वतः स्तरोन्नति हुन्छ (सफा पुनःस्थापना; config पूर्वनिर्धारित
मानहरूमा रिसेट हुन्छ)। उही वा पुरानो संस्करण अस्वीकृत हुन्छ।

`/dashboard/plugins` (`src/app/(dashboard)/dashboard/plugins/page.tsx`) मा ड्यासबोर्ड पृष्ठले दुई ट्याबहरू प्रदान गर्दछ:

- **स्थापना गरियो** — तिनीहरूको घोषित हुकहरू, एक activate/deactivate टगल, एक अनइन्स्टल बटन, र "प्लगइनहरूको लागि स्क्यान" कार्य (`POST /api/plugins/scan`) सँग स्थापित प्लगइनहरू सूचीबद्ध गर्दछ।
- **बजार** — कस्टम रजिस्ट्री URL सेट गर्न फिल्डको साथ `GET /api/plugins/marketplace` बाट क्याटलग देखाउँछ।

पृष्ठले सधैं चेतावनी देखाउँछ कि प्लगइनहरू OmniRoute प्रक्रियाको पूर्ण विशेषाधिकारहरूसँग चल्छन्।

प्रति-प्लगइन कन्फिगरेसन पृष्ठ `/dashboard/plugins/[name]/config` (`src/app/(dashboard)/dashboard/plugins/[name]/config/page.tsx`) मा रहन्छ।
