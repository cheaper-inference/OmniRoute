सबै आठ एउटै पर्यवेक्षक मोडेल पछ्याउनुहोस्:

- OmniRoute तिनीहरूलाई `DATA_DIR/services/{name}/` अन्तर्गत स्थापना गर्दछ ( OmniRoute को आफ्नै `package.json` बाट अलग गरिएको)
- OmniRoute तिनीहरूलाई बाल प्रक्रियाको रूपमा जन्माउँछ र निगरानी गर्दछ
- OmniRoute बच्चाको वातावरणमा अल्पकालिक API कुञ्जी इन्जेक्ट गर्छ र डाउनटाइम बिना नै घुमाउँछ (जहाँ लागू हुन्छ)
- सबै व्यवस्थापन मार्गहरू (`/api/services/*`) छन्**LOCAL_ONLY** — लुपब्याकबाट मात्र पहुँचयोग्य (हार्ड नियम #17)

## 2. वास्तुकला — 4 तहहरू

```
┌────────────────────────────────────────────────────────────────────┐
│  Layer 1 — UI                                                      │
│  /dashboard/providers/services  (tabs: CLIProxyAPI | 9Router | Mux)│
│  Logs live (SSE), Start/Stop/Restart/Update, Settings, Install     │
│                                                                    │
│  src/app/(dashboard)/dashboard/providers/services/                 │
│    ├── page.tsx               Shell + tab routing by ?tab=         │
│    ├── tabs/                  CliproxyServiceTab, NinerouterServiceTab,│
│    │                          MuxServiceTab                        │
│    └── components/            ServiceStatusCard, ServiceLifecycleButtons,│
│                               ServiceLogsPanel, ApiKeyCard, ...    │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ HTTP (Next.js fetch)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 2 — API (LOCAL_ONLY — loopback only)                        │
│                                                                    │
│  /api/services/9router/{install|start|stop|restart|update|         │
│                          rotate-key|status|auto-start|logs}        │
│  /api/services/cliproxy/{install|start|stop|restart|update|        │
│                           status|auto-start|logs}                  │
│  /api/services/mux/{install|start|stop|restart|update|             │
│                      status|auto-start|logs}                       │
│  /dashboard/providers/services/9router/embed/[...path]             │
│    (reverse HTTP + WebSocket proxy → 9Router upstream)             │
│                                                                    │
│  Gate: LOCAL_ONLY_API_PREFIXES includes "/api/services/" and       │
│        "/dashboard/providers/services/*/embed/"                    │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ in-process calls
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 3 — ServiceSupervisor (src/lib/services/)                   │
│                                                                    │
│  ServiceSupervisor.ts   Generic supervisor (child_process.spawn)   │
│    ├── install:    execFile('npm', ['install', pkg, '--prefix'])    │
│    ├── start:      spawn(node, [entrypoint], {env, cwd})           │
│    ├── api_key:    crypto.randomBytes(32) → env NINEROUTER_API_KEY  │
│    ├── port:       20130 for 9Router (configurable)                │
│    ├── logs:       stdio ring buffer 5 MB → SSE events             │
│    ├── health:     HTTP GET /health every 2–5 s, lazy recovery     │
│    └── lifecycle:  SIGTERM 15 s → SIGKILL                          │
│                                                                    │
│  registry.ts        getSupervisor(name) / registerSupervisor()     │
│  bootstrap.ts       Bootstraps all SERVICES[] at process start     │
│  apiKey.ts          getOrCreateApiKey(), generateServiceApiKey()   │
│  modelSync.ts       Periodic GET /v1/models → service_models table │
│  ringBuffer.ts      Circular log buffer (5 MB per service)         │
│  healthCheck.ts     Polling HTTP health probe                      │
│  installers/        ninerouter.ts, cliproxy.ts, mux.ts, openwa.ts  │
│                      (installer adapters)                          │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ OpenAI-compatible HTTP (loopback)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 4 — Provider / Routing                                      │
│                                                                    │
│  open-sse/executors/ninerouter.ts                                  │
│    Re-looks up port and API key per-request (no caching).          │
│    Strips "9router/" prefix from model id before proxying.         │
│    Returns 503 service_not_running if supervisor not in "running". │
│                                                                    │
│  src/shared/constants/providers.ts                                 │
│    Entry for "9router": isEmbeddedService: true                    │
│                                                                    │
│  open-sse/config/providerRegistry.ts                               │
│    Models stored as "9router/{sub}/{model}" (prefixed).            │
│    Synced every 5 min by modelSync.ts.                             │
│                                                                    │
│  Mux is lifecycle-managed ONLY (Layers 1-3) — it is an agent-       │
│  orchestration daemon, not an LLM proxy, so it has no Layer 4      │
│  executor/provider entry and is never a routing target.            │
└────────────────────────────────────────────────────────────────────┘
```

## 3. जीवनचक्र अवस्था मेसिन

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
             स्वास्थ्य जाँच सफल    │         क्र्यास / SIGTERM   │
                               ┌────▼─────┐  (5s भित्र बन्द)    │
                               │ running  │──── क्र्यास ─────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

अवस्थाहरू `version_manager` DB तालिकाको (`status` स्तम्भ) मा भण्डारण गरिन्छन् र
`ServiceSupervisor` को इन-मेमोरी अवस्थामा प्रतिबिम्बित गरिन्छन्। चलिरहेको
प्रक्रियाका लागि इन-मेमोरी अवस्था आधिकारिक हुन्छ; बुट हुँदा DB अवस्था टिकाउ
फल्ब्याक हो।

### अवस्था सङ्क्रमणहरू

| बाट             | घटना                                           | मा                      |
| --------------- | ---------------------------------------------- | ----------------------- |
| `not_installed` | `install()` सफल हुन्छ                          | `stopped`               |
| `stopped`       | `start()` कल गरिन्छ                            | `starting`              |
| `starting`      | स्वास्थ्य जाँचले 200 फर्काउँछ                  | `running`               |
| `starting`      | स्वस्थ हुनुअघि प्रक्रिया बन्द हुन्छ            | `error`                 |
| `running`       | `stop()` कल गरिन्छ                             | `stopping` → `stopped`  |
| `running`       | प्रक्रिया अप्रत्याशित रूपमा बन्द हुन्छ (< 5 s) | `error` (द्रुत क्र्यास) |
| `running`       | प्रक्रिया अप्रत्याशित रूपमा बन्द हुन्छ (> 5 s) | `error`                 |
| `error`         | `start()` कल गरिन्छ                            | `starting`              |
| कुनै पनि        | `stopping` हुँदा `stop()`                      | कुनै कार्य हुँदैन       |

### सञ्चालन लक

`ServiceSupervisor` ले async सञ्चालन लक (`withLock()`) मार्फत जीवनचक्र सञ्चालनहरूलाई
क्रमबद्ध गर्छ। एउटै सुपरभाइजरमा एकसाथ गरिएका `start()` कलहरूले ठ्याक्कै एउटा
प्रक्रिया मात्र सुरु गर्छन्; दोस्रो कल गर्ने पक्षले प्रतीक्षा गर्छ र विद्यमान अवस्था
फर्काउँछ। यसले, उदाहरणका लागि, स्वतः-सुरुवात र UI बटन एकैसाथ सक्रिय हुँदा उत्पन्न
हुने रेस अवस्थाहरू रोक्छ।

## 4. API सन्दर्भ

`/api/services/` अन्तर्गत सबै मार्गहरू छन्**LOCAL_ONLY** (लुपब्याक मात्र, कडा नियम #17)। गैर-लूपब्याक अनुरोधहरूले प्रमाणिकरण टोकनको पर्वाह नगरी `403 LOCAL_ONLY` प्राप्त गर्दछ।

### ४.१ ९ राउटर अन्तिम बिन्दुहरू (११ मार्गहरू)

#### `POST /api/services/9router/install`

npm बाट 9 राउटर स्थापना गर्नुहोस्। यसको आफ्नै `package.json` र `node_modules/` संग `DATA_DIR/services/9router/` सिर्जना गर्दछ। OmniRoute को आफ्नै deps संग विवाद गर्दैन।

**शरीर अनुरोध गर्नुहोस्** (सबै वैकल्पिक):

```json
{ "version": "latest" }
```

| क्षेत्र   | टाइप गर्नुहोस् | पूर्वनिर्धारित | विवरण                                    |
| --------- | -------------- | -------------- | ---------------------------------------- |
| `version` | `string`       | `"latest"`     | npm संस्करण ट्याग वा Semver स्थापना गर्न |

**प्रतिक्रियाहरू:**

| स्थिति | विवरण                                                            |
| ------ | ---------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`           |
| `400`  | अमान्य अनुरोध मुख्य भाग (Zod प्रमाणीकरण विफलता)                  |
| `409`  | पहिले नै स्थापना गर्दै (लक राखिएको)                              |
| `500`  | npm स्थापना असफल भयो — अनुकूल त्रुटिको लागि `message` हेर्नुहोस् |

**नोट:** `execFile('npm', [...])` — no shell, no interpolation (हार्ड नियम #13) प्रयोग गर्दछ। EACCES त्रुटिहरू मैत्री सन्देशहरूको रूपमा देखा पर्छन्।

| स्थिति | विवरण                                                      |
| ------ | ---------------------------------------------------------- |
| `200`  | `ServiceStatus` वस्तु (तल स्कीमा हेर्नुहोस्)               |
| `409`  | 9 राउटर स्थापना गरिएको छैन (`status: "not_installed"`)     |

| `POST` | `/api/services/openwa/update`     | नयाँ संस्करणमा अद्यावधिक गर्नुहोस्                         |
| `GET`  | `/api/services/openwa/status`     | लाइभ + DB स्थिति                                           |

| `GET`  | `/api/services/openwa/logs`       | SSE लग टेल (साझा `[name]/logs` गतिशील मार्ग मार्फत)        |

**API कुञ्जी:** `WA_KEY` — ओपन-वाको जेनेरिक `WA_*` -prefixed env ओभरराइडको रूपमा इन्जेक्ट गरिएकोले यसलाई `--key`/`-k` CLI विकल्प (`dist/cli/setup.js::envArgs()`, स्थापित 4.76.0 प्याकेज विरुद्ध प्रमाणित) मा नक्सा बनाउँछ। `generateServiceApiKey()` द्वारा उत्पन्न गर्दा उपसर्ग `ow_` । open-wa ले `key`/`api_key` HTTP हेडरबाट कुञ्जी फिर्ता पढ्छ ( `Authorization: Bearer` होइन); `/api-docs*` चेकबाट स्पष्ट रूपमा छुट दिइएको छ (`setupAuthenticationLayer` मा `dist/cli/server.js`), त्यसैले स्वास्थ्य जाँचलाई कुनै प्रमाणीकरण हेडर आवश्यक पर्दैन।

**जोडा बनाउँदै:** open-wa अनौपचारिक छ र WhatsApp — सँग असंबद्ध छ र जडान गरिएको नम्बरले WhatsApp को आफ्नै स्वचालन पत्ता लगाउन प्रतिबन्ध जोखिम बोक्छ। पहिलो सुरुमा, पेरिङ QR कोड stdout मा छापिएको छ र अवस्थित Logs panel/SSE स्ट्रिम — मार्फत देखा परेको छ त्यहाँ यस एकीकरणमा अझै कुनै समर्पित QR-छवि अन्तिम बिन्दु छैन।

### ४.९ रिभर्स प्रोक्सी (९ राउटर ड्यासबोर्ड इम्बेड)

ड्यासबोर्डले 9 राउटर वेब UI लाई iframe भित्र आन्तरिक रिभर्स प्रोक्सी मार्फत इम्बेड गर्दछ:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

यो प्रोक्सी:

- `http://127.0.0.1:{port}/{path}` मा अनुरोध फर्वार्ड गर्नुहोस् (लुपब्याक मात्र)
- स्ट्रिप इनकमिङ `cookie` र `authorization` हेडरहरू ( OmniRoute सत्रको कुनै चुहावट छैन)
- 9 राउटर प्रमाणीकरणको लागि `Authorization: Bearer {apiKey}` इन्जेक्ट गर्दछ
- स्ट्रिपहरू `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` प्रतिक्रियाबाट
- `<base href>` इन्जेक्सन गर्न र निरपेक्ष मार्गहरू सामान्य बनाउन HTML प्रतिक्रियाहरू पुन: लेख्छ (`/foo` → `/dashboard/.../embed/foo`)

एम्बेडेड ड्यासबोर्डका लागिWebSocket अपग्रेडहरू एक समर्पित पोर्टमा साथी सर्भरद्वारा ह्यान्डल गरिन्छ ( `src/lib/services/embedWsProxy.ts` हेर्नुहोस्)।

**सुरक्षा:** इम्बेड प्रोक्सी मार्गहरू `LOCAL_ONLY_API_PREFIXES` अन्तर्गत वर्गीकृत छन् र लुपब्याकबाट मात्र पुग्न सकिन्छ। Cloudflare/Ngrok सुरुङ मार्फत JWT प्राप्त गर्ने आक्रमणकारीले इम्बेडेड सेवाहरूमा प्रोक्सी गर्न सक्दैन।

## 5. सुरक्षा

### LOCAL_ONLY कार्यान्वयन (कडा नियम #17)

`/api/services/` र `/dashboard/providers/services/*/embed/` अन्तर्गतका सबै रुटहरूलाई
`src/server/authz/routeGuard.ts` मा LOCAL_ONLY का रूपमा वर्गीकृत गरिएको छ। लुपब्याक जाँच
कुनै पनि प्रमाणीकरण शाखाभन्दा अगाडि सधैं चल्छ:

```
अनुरोध आइपुग्छ
  → isLocalOnlyPath(path)?
      → गैर-लुपब्याक → 403 LOCAL_ONLY (सधैं, प्रमाणीकरण जाँचअघि)
      → लुपब्याक     → सामान्य प्रमाणीकरणमा अगाडि बढ्छ
```

यसले चुहिएको JWT (उदाहरणका लागि, टनेलमार्फत) ले `npm install` वा
प्रक्रिया सुरु गर्नबाट रोक्छ। पूर्ण तह म्याट्रिक्सका लागि
`docs/security/ROUTE_GUARD_TIERS.md` हेर्नुहोस्।

### API कुञ्जी इन्जेक्सन

9Router र Mux लाई तिनका आफ्नै HTTP एन्डपोइन्टहरूका लागि API कुञ्जी/बियरर टोकन आवश्यक हुन्छ।
OmniRoute ले:

1. सेवाविशेष प्रिफिक्स (`nr_` 9Router का लागि, `mx_` Mux का लागि) सहित
   `crypto.randomBytes(32).toString("base64url")` मार्फत कुञ्जी उत्पन्न गर्छ।
2. AES-256-GCM प्रयोग गरेर यसलाई भण्डारण अवस्थामा इन्क्रिप्ट गर्छ (प्रदायक क्रेडेन्सियलका लागि प्रयोग हुने उही साइफर)।
3. स्पन गर्ने समयमा यसलाई डिक्रिप्ट गरेर वातावरण चरका रूपमा इन्जेक्ट गर्छ —
   9Router का लागि `NINEROUTER_API_KEY`, Mux का लागि `MUX_SERVER_AUTH_TOKEN` (कहिल्यै CLI
   फ्ल्यागका रूपमा होइन, त्यसैले टोकन `ps`/प्रक्रिया सूचीहरूमा कहिल्यै देखिँदैन)।
4. कुनै पनि HTTP प्रतिक्रियामा प्लेनटेक्स्ट कुञ्जी कहिल्यै फिर्ता गर्दैन।

CLIProxyAPI ले स्पन गर्दा इन्जेक्ट गरिएको समर्पित डेटा-प्लेन कुञ्जी प्राप्त गर्छ
(`needsApiKey: true` — एडाप्टरविरुद्ध मोडेल सिङ्कका लागि प्रयोग गरिन्छ)।

### SSRF प्रतिरक्षा

रिभर्स HTTP प्रोक्सी (`/dashboard/.../embed/[...path]`) लाई
`http://127.0.0.1:{port}` मा मात्र फर्वार्ड गर्न हार्डकोड गरिएको छ। यसले गैर-लुपब्याक
गन्तव्यतर्फका रिडाइरेक्टहरू कहिल्यै पछ्याउँदैन। लुपब्याक दायराबाहिर रिजोल्भ हुने कुनै पनि
अपस्ट्रिम URL अस्वीकार गर्न `ssrf-req-filter` लाइब्रेरी प्रयोग गरिन्छ।

### शेल सुरक्षा (कडा नियम #13)

`npm install` लाई `execFile('npm', ['install', pkg, '--prefix', dir])` मार्फत आह्वान गरिन्छ —
कुनै टेम्प्लेट लिटरल, शेल, वा बाह्य पाथलाई कमान्ड स्ट्रिङमा इन्टरपोलेसन गरिँदैन।
रनटाइम मानहरू (पोर्टहरू, API कुञ्जीहरू) चाइल्डको `env` अब्जेक्टमार्फत पठाइन्छन्।

### त्रुटि स्यानिटाइजेसन (कडा नियम #12)

`/api/services/*` बाट आउने सबै त्रुटि प्रतिक्रियाहरू `buildErrorBody()` वा
`sanitizeErrorMessage()` मार्फत जान्छन्। कच्चा `err.stack` र `err.message` कलरलाई
जस्ताको तस्तै कहिल्यै फिर्ता गरिँदैनन्।

## 6. नयाँ एम्बेडेड सेवा थप्ने

यी 8 चरणहरू पालना गर्नुहोस्। आधिकारिक सन्दर्भका रूपमा `src/lib/services/installers/`
र `src/app/api/services/` मा रहेका विद्यमान कार्यान्वयनहरू पढ्नुहोस्।

### चरण 1 — इन्स्टलर सिर्जना गर्ने

`ninerouter.ts` को ढाँचामा `src/lib/services/installers/{name}.ts` सिर्जना गर्नुहोस्:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // खाली पोर्ट छान्नुहोस्

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

`installers/utils.ts` बाट `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` प्रयोग गर्नुहोस्
— `execSync` वा शेल इन्टरपोलेसन कहिल्यै प्रयोग नगर्नुहोस्।

### चरण 2 — बुटस्ट्र्यापमा दर्ता गर्ने

`src/lib/services/bootstrap.ts` को `SERVICES` एरेमा एउटा `ServiceEntry` थप्नुहोस्:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // API कुञ्जी आवश्यक नभए false
}
```

`cfg.tool === "myservice"` ह्यान्डल गर्न `buildSpawnArgsFactory()` विस्तार गर्नुहोस्।

#### प्लग गर्न मिल्ने प्रदायक-प्लगइन कन्ट्र्याक्ट (चरण 1, #7333)

`src/lib/services/providerPlugins/` ले एउटा `ServiceProviderPlugin` कन्ट्र्याक्ट प्रस्तुत गर्छ,
जसले एउटै ब्याकएन्डको स्वरूपलाई दुई असम्बन्धित फाइलमा छुट्टाछुट्टै व्यक्त गर्नुको सट्टा
ब्याकएन्डको `bootstrap.ts` का `ServiceEntry` फिल्डहरू र `serviceBackends.ts` का
म्यानिफेस्ट-टेम्प्लेट फिल्डहरूलाई एउटै अब्जेक्टमा प्याकेज गर्छ। यो लेखिँदासम्म **`9router` मात्र
माइग्रेट गरिएको छ** — `bootstrap.ts` ले आफ्नो `SERVICES[]` प्रविष्टि
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`) बाट
निकाल्छ र प्लगइन कहिल्यै हराएमा स्टार्टअप त्रुटि फ्याँक्छ। `cliproxy`, `mux`, र `bifrost`
कुनै परिवर्तनबिना पहिलेदेखिका इनलाइन `SERVICES[]` लिटरलमै रहन्छन्।

`open-sse/config/providerPluginManifest.ts` मा पनि राम्रोसँग संरचित
`ProviderPluginManifestEntry` लाई `SERVICE_BACKEND_MANIFEST_TEMPLATE` प्रविष्टिबाट बनाउने
थपात्मक `createServiceBackendManifestEntry(pluginId, template)` हेल्पर थपिएको छ — यसलाई
अझै कुनै लाइभ अनुरोध पाथमा जोडिएको **छैन** (`generateProviderPluginManifestFromRegistry()`
वा `/v1/providers/[provider]/models` कुनैमा पनि होइन); दोस्रो ब्याकएन्डका लागि कन्ट्र्याक्ट
प्रमाणित भएपछि यो फलो-अपका रूपमा बाँकी रहन्छ।

समस्या #7333 अन्तर्गत ट्र्याक गरिएका फलो-अप PR हरूका लागि स्थगित कार्यहरू: उही रजिस्ट्रीमार्फत
`cliproxyapi` माइग्रेट गर्ने, `mux`/`bifrost` लाई `ServiceBackendPluginId` युनियनमा
सामान्यीकरण गर्ने, एक्जिक्युटर-राउटिङको विशेष-केसिङ (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) लाई प्लगइन कन्ट्र्याक्टमा समेट्ने, र
`createServiceBackendManifestEntry()` लाई लाइभ म्यानिफेस्ट/मोडेल कोड पाथमा जोड्ने।

## 7. समस्या समाधान

### सेवा सुरु हुँदैन

**लक्षणहरू:** Start बटनले 503 फर्काउँछ, अवस्था `"error"` वा `"starting"` मै रहन्छ।

**जाँचसूची:**

1. `GET /api/services/{name}/logs` (वा ड्यासबोर्डको Logs प्यानल) जाँच गर्नुहोस्। `Error: ENOENT`, `address already in use`, वा `Cannot find module` जस्ता पङ्क्तिहरू खोज्नुहोस्।
2. `npm` PATH मा छ भनी पुष्टि गर्नुहोस्: OmniRoute चलाउने सोही प्रयोगकर्ता खाताबाट `which npm` चलाउनुहोस्।
3. सेवा इन्स्टल गरिएको छ भनी पुष्टि गर्नुहोस्: `installedVersion` का लागि `GET /api/services/{name}/status` जाँच गर्नुहोस्। यदि यो `null` छ भने, पहिले इन्स्टल चलाउनुहोस्।
4. `DATA_DIR/services/{name}/node_modules/` अवस्थित र खाली नभएको जाँच गर्नुहोस्।
5. सुरक्षित बनाइएको बाहिरिने कारणका लागि स्थिति प्रतिक्रियाको `lastError` फिल्ड जाँच गर्नुहोस्।

---

### कोल्ड स्टार्ट ढिलो छ (`running` मा पुग्न > 10 s)

**लक्षणहरू:** `"running"` वा `"error"` मा जानुअघि अवस्था लामो समयसम्म `"starting"` मै रहन्छ।

**व्याख्या:** 9Router को कोल्ड स्टार्टमा ठूला निर्भरता ट्रीहरू (DNS, टनेल, MITM मोड्युलहरू) आयात गर्ने कार्य समावेश हुन्छ। पूर्वनिर्धारित स्वास्थ्य जाँच अन्तराल 2 s हो र सुपरभाइजरले टाइमआउट घोषणा गर्नुअघि 3 पटक प्रयास गर्छ (तर पोलिङ जारी राख्छ)।

**समाधान:** `healthIntervalMs` र `waitForHealthy` टाइमआउट (`healthIntervalMs * 3`) लाई `bootstrap.ts` मा कन्फिगर गर्न सकिन्छ। सुरु हुन बढी समय लाग्ने सेवाहरूका लागि `healthIntervalMs` लाई 5000 र `stopTimeoutMs` लाई 30 000 मा बढाउनुहोस्।

---

### पोर्ट टकराव (`EADDRINUSE`)

**लक्षणहरू:** लगहरूले `address already in use :::20130` देखाउँछन्।

**कारणहरू:**

- अर्को प्रक्रियाले पहिले नै पोर्ट 20130 प्रयोग गरिरहेको छ।
- अघिल्लो 9Router प्रक्रिया पूर्ण रूपमा रोकिएको थिएन (जोम्बी PID)।

**समाधान:**

1. `.env` मा रहेको `NINEROUTER_PORT` वातावरण चरमार्फत पूर्वनिर्धारित पोर्ट परिवर्तन गर्नुहोस्।
2. टकराव गर्ने प्रक्रिया फेला पारेर अन्त्य गर्नुहोस्: `lsof -ti :20130 | xargs kill -9`।
3. `bootstrap.ts` मा रहेको `port` फिल्डमार्फत प्रत्येक सेवाका लागि पोर्ट कन्फिगर गर्न सकिन्छ।

**नोट:** OmniRoute को पूर्वनिर्धारित पोर्ट 20128 सँग टकराव हुन नदिन 9Router ले विशेष रूपमा पोर्ट 20130 पूर्वनिर्धारित रूपमा प्रयोग गर्छ।

---

### इन्स्टल गर्दा अनुमति अस्वीकृत (EACCES)

**लक्षणहरू:** इन्स्टलले 500 फर्काउँछ, लगहरूले `EACCES` वा `permission denied` देखाउँछन्।

**कारणहरू:**

- `DATA_DIR` वा यसको मूल डाइरेक्टरीमा OmniRoute प्रक्रियाले लेख्न सक्दैन।
- म्याप गरिएको भोल्युममा लेख्ने पहुँचबिना रुटलेस Docker भित्र चलिरहेको छ।

**समाधान:**

1. `DATA_DIR` (पूर्वनिर्धारित: `~/.omniroute/`) जाँच गर्नुहोस्: `ls -la ~/.omniroute/`
2. OmniRoute प्रक्रिया चलाउने प्रयोगकर्ता उक्त डाइरेक्टरीको मालिक भएको सुनिश्चित गर्नुहोस्: `chown -R $USER ~/.omniroute/`
3. Docker मा, भोल्युम माउन्टसँग कन्टेनर प्रयोगकर्ताका लागि सही अनुमतिहरू भएको सुनिश्चित गर्नुहोस्।

---

### अपडेट असफल हुन्छ (`npm install` टाइमआउट वा नेटवर्क त्रुटि)

**लक्षणहरू:** अपडेटले `InstallError` सहित 500 फर्काउँछ, लगहरूले नेटवर्क टाइमआउट देखाउँछन्।

**जाँचसूची:**

1. npm रजिस्ट्रीमा पहुँच छ भनी पुष्टि गर्नुहोस्: `npm ping`।
2. कर्पोरेट प्रोक्सी जाँच गर्नुहोस्: `npm config get proxy`, `npm config get https-proxy`।
3. इन्स्टल म्यानुअल रूपमा प्रयास गर्नुहोस्: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`।
4. एयर-ग्याप पछाडि भएमा, टारबल पहिले नै डाउनलोड गर्नुहोस् र `npm install /path/to/tarball.tgz` प्रयोग गर्नुहोस्।

---

### सुरु गरेलगत्तै सेवाले `"error"` अवस्था देखाउँछ (द्रुत क्र्यास)

**लक्षणहरू:** अवस्था 5 सेकेन्डभन्दा कम समयमा `"starting"` बाट `"error"` मा परिवर्तन हुन्छ। `lastError` ले `"Fast crash (exited with code 1)"` देखाउँछ।

**जाँचसूची:**

1. पूरा लग टेल पढ्नुहोस्: `GET /api/services/{name}/logs?tail=500`।
2. सामान्य कारण: सेवाले अपेक्षा गरेका वातावरण चरहरू छुटेका छन्।
3. 9Router का लागि: `NINEROUTER_DISABLE_MITM=true` र `NINEROUTER_DISABLE_TUNNEL=true` स्पन गर्दा पास गरिएको env मा छन् भनी पुष्टि गर्नुहोस् (`installers/ninerouter.ts` को `resolveSpawnArgs` हेर्नुहोस्)।

## 8. प्रायः सोधिने प्रश्नहरू

**प्रश्न: के म अन्तर्निहित सेवाका एन्डपोइन्टहरू गैर-लुपब्याक क्लाइन्टहरूका लागि खुला गर्न सक्छु?**

सक्नुहुन्न। LOCAL_ONLY तह जानाजानी राखिएको हो (कडा नियम #17)। `npm install` चलाउन वा `node` प्रक्रियाहरू सुरु गर्न सक्ने रुटहरू गैर-लुपब्याक ट्राफिकबाट पहुँचयोग्य हुनु हुँदैन, किनभने अन्यथा टनेल (Cloudflare, Ngrok, Tailscale) मार्फत चुहिएको JWT ले जथाभावी प्रक्रियाहरू सुरु गर्न अनुमति दिनेछ। `/api/services/` का लागि यो प्रतिबन्ध हटाउने कुनै अपवाद छैन—`/api/mcp/` को विपरीत, यसलाई manage-scope बाइपास सूचीबाट हटाइएको छ। `docs/security/ROUTE_GUARD_TIERS.md` हेर्नुहोस्।

---

**प्रश्न: के 9Router र CLIProxyAPI उत्पादन/क्लाउड डिप्लोयमेन्टहरूमा उपलब्ध हुनेछन्?**

हुनेछन्। दुवै सेवाले OmniRoute स्वयंले जस्तै local-first मोडेल पालना गर्छन्। तिनीहरू एउटै मेसिनमा चल्छन् र लुपब्याकमार्फत सञ्चार गर्छन्। यहाँ "उत्पादन" भन्नाले OmniRoute डिप्लोय गरिएको VPS वा स्थानीय सर्भर बुझिन्छ, टाढाको क्लाउड प्रदायक होइन।

---

**प्रश्न: म सुपरभाइजरलाई कसरी डिबग गर्न सक्छु?**

1. SSE लग स्ट्रिमलाई निरन्तर हेर्नुहोस्: `curl -N http://localhost:20128/api/services/9router/logs`।
2. OmniRoute को pino आउटपुटमा `service:supervisor` नेमस्पेसद्वारा फिल्टर गरिएका संरचित लगहरू जाँच गर्नुहोस्।
3. DB पङ्क्ति निरीक्षण गर्नुहोस्: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`।
4. हालको प्रत्यक्ष अवस्था, PID, स्वास्थ्य र `lastError` एउटै कलमा हेर्न `GET /api/services/9router/status` प्रयोग गर्नुहोस्।

---

**प्रश्न: सुपरभाइजरले `health: "degraded"` वा `health: "unknown"` देखाउँछ तर अवस्था `"running"` छ। के यो समस्या हो?**

`"degraded"` को अर्थ स्वास्थ्य प्रोबले गैर-200 प्रतिक्रिया फर्काएको हो। `"unknown"` को अर्थ अहिलेसम्म कुनै प्रोब पूरा भएको छैन (पहिलो पोलसँगको रेस) भन्ने हो। स्टार्टअपका बेला दुवै अस्थायी हुन्छन्। `"running"` भएपछि `healthIntervalMs * 3` ms भन्दा बढी समयसम्म स्वास्थ्य `"degraded"` नै रहिरहेमा, अन्तर्निहित सेवा चलिरहेको छ तर यसको HTTP API ले प्रतिक्रिया दिइरहेको छैन। स्थिति प्रतिक्रियामा पोर्ट सही छ कि छैन र सेवाले वास्तवमै उक्त पोर्टमा सुनिरहेको छ कि छैन जाँच गर्नुहोस्।

---

**प्रश्न: के म पूर्ण रिस्टार्ट नगरी 9Router API कुञ्जी परिवर्तन गर्न सक्छु?**

सक्नुहुन्न। API कुञ्जी स्पन गर्ने समयमा वातावरण चरमार्फत 9Router लाई पठाइन्छ। चलिरहेको प्रक्रियामा वातावरण चरहरू परिवर्तन गर्न सकिँदैन। `POST .../rotate-key` ले नयाँ कुञ्जी लागू गर्न सेवा स्वतः रोक्छ र पुनः सुरु गर्छ। कुञ्जी रोटेसन सेवाको `stopTimeoutMs` (पूर्वनिर्धारित 15 s) र यसको स्टार्टअप समयभित्र प्रभावकारी हुन्छ।

**प्रश्न: रिङ बफरको सीमा कति हो र यो भरिएपछि के हुन्छ?**

प्रत्येक सेवासँग समर्पित 5 MB रिङ बफर हुन्छ। बफर भरिएपछि नयाँ लग लाइनहरूका लागि ठाउँ बनाउन सबैभन्दा पुराना लग लाइनहरू हटाइन्छन्। SSE `snapshot` घटनाले `tail` सीमाभित्रका सबैभन्दा नयाँ लाइनहरू फर्काउँछ। DB पङ्क्तिमा `logsBufferPath` सेट नगरिएसम्म लगहरू डिस्कमा स्थायी रूपमा भण्डारण गरिँदैनन्।
