AgentBridge je MITM (Man-in-the-Middle) proxy OmniRoute, které zachytává provoz HTTPS z AI agentů v IDE a přesměrovává jej přes jednotný směrovací modul OmniRoute. Podporuje **10 agentů v IDE** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code a Trae (ve fázi zkoumání) — díky čemuž je OmniRoute MITM proxy s nejširší podporou AI asistentů pro programování na trhu.

**Umístění v řídicím panelu:** `/dashboard/tools/agent-bridge`
**Skupina v postranním panelu:** Nástroje (za Cloud Agents)
**Viz také:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — monitorování veškerého zachyceného provozu v reálném čase; `docs/security/MITM-TPROXY-DECRYPT.md` (git; není zahrnut do `/docs`) — režim transparentního dešifrování a zachytávání pomocí Linux TPROXY, řízený trasou `/api/tools/agent-bridge/tproxy`.

## §1 Přehled

### Co je AgentBridge?

Když agent IDE (např. GitHub Copilot, Cursor, Claude Code) provede volání API, připojí se přímo k upstreamovému poskytovateli AI (OpenAI, Anthropic atd.). AgentBridge toto připojení transparentně zachytí na úrovni TLS — bez nutnosti jakékoli změny konfigurace agenta — a přepíše požadavek tak, aby procházel přes OmniRoute.

To znamená, že můžete:

- **Přesměrovat libovolného agenta na jakéhokoli poskytovatele**: Copilot komunikuje s OpenAI? Přesměrujte ho na Anthropic Claude, Gemini nebo na kteréhokoli z 376 poskytovatelů OmniRoute.
- **Používat mapování modelů**: `gemini-3-flash` → `claude-sonnet-4.7` transparentně na úrovni handleru.
- **Sledovat veškerou komunikaci agentů**: každý zachycený požadavek je publikován do [Traffic Inspectoru](./TRAFFIC_INSPECTOR.md).
- **Využívat odolnost OmniRoute**: combo směrování, circuit breakery, fallbacky a sledování nákladů fungují i pro provoz IDE agentů.

## §2 Architektura

### 2.1 Přehled komponent

```
Agent IDE (VS Code / Cursor / atd.)
    │  HTTPS (port 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← přesměrování DNS
    │
    ▼
src/mitm/server.cjs  (port 443, podřízený proces CJS)
    │  překládá cíl podle SNI z hlavičky Host
    │  generuje certifikát TLS pro každé SNI podepsaný CA AgentBridge
    ├── Shoda se seznamem výjimek? → přímý přenos TCP (bez dešifrování)
    ├── Shoda s cílem? → fetch → směrovač OmniRoute (port 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() v těle/hlavičkách požadavku
    │               ├── TrafficBuffer.push() — publikuje do Inspektoru provozu
    │               └── fetchRouter() → /v1/chat/completions
    └── Bez shody? → přímý přenos TCP (bez dešifrování)
```

### 2.2 Server MITM (`src/mitm/server.cjs`)

Jádro serveru MITM běží jako podřízený proces Node.js CJS (aby nebylo nutné přepisovat existující kódovou základnu CJS). Provádí následující:

- Naslouchá na portu 443 (vyžaduje oprávnění nebo `authbind`/`setcap`)
- Přijímá tunely CONNECT z operačního systému (prostřednictvím přesměrování DNS v `/etc/hosts`)
- Generuje certifikáty TLS pro jednotlivá SNI podepsané CA AgentBridge (`DATA_DIR/mitm/ca.crt`)
- Překládá cílového agenta podle hlavičky Host prostřednictvím registru `targets/index.ts`
- Předává požadavky vrstvě obslužných rutin v TypeScriptu přes HTTP na `http://127.0.0.1:20128`

`TARGET_HOSTS` se načítá z `DATA_DIR/mitm/targets.json` (soubor při spuštění zapisuje `targets/index.ts`), což umožňuje dynamické aktualizace bez restartování serveru CJS.

> **Model kořenové CA (#6684).** Výše uvedený popis certifikátů pro jednotlivá SNI podepsaných CA
> představuje trvalý model kořenové CA přidaný v #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, který znovu využívá kryptografii CA/koncových certifikátů již
> ověřenou pro TPROXY v `src/mitm/tproxy/dynamicCert.ts`) — nahrazuje
> starší jediný statický koncový certifikát podepsaný sám sebou (`src/mitm/cert/generate.ts`, stále
> omezený pouze na hostitele antigravity), který indikuje pouhá dvojice `server.crt`/`server.key`
> na disku. **Chování při migraci**: nová instalace (bez předchozího
> `server.crt`) získá model kořenové CA automaticky; instalace, která již
> důvěřovala starému statickému koncovému certifikátu, jej používá i nadále, dokud provozovatel nenastaví
> `MITM_ROOT_CA_ENABLED=true` a nerestartuje bridge (`src/mitm/cert/migration.ts`
> je čistá rozhodovací funkce — důvěryhodná MITM CA, která může podepsat koncový certifikát pro
> **libovolného** hostitele, je výrazně mocnější než starý koncový certifikát s pevně danými SAN, takže
> k přepnutí u instalace, která mu již důvěřuje, nikdy nedojde bez upozornění). Certifikát CA se instaluje
> do stejného umístění `omniroute-mitm.crt` v úložišti důvěryhodných certifikátů, které používal starý koncový certifikát
> (`cert/install.ts::installCaCert`) — není potřeba čistit dvojí důvěryhodnost.

### 2.3 Základ obslužných rutin (`src/mitm/handlers/base.ts`)

Všechny obslužné rutiny agentů rozšiřují `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Chráněné pomocné funkce: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Každá obslužná rutina před předáním požadavku proxy volá `hookBufferStart()` a po dokončení volá `hookBufferUpdate()`. Tyto funkce vkládají položky `InterceptedRequest` do `globalTrafficBuffer` (viz [Inspektor provozu](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Registr cílů (`src/mitm/targets/`)

Každý agent má deklarativní cílový soubor:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Registr (`targets/index.ts`) exportuje `ALL_TARGETS` a při spuštění generuje `DATA_DIR/mitm/targets.json`.

### 2.5 Přímý přenos a seznam výjimek (`src/mitm/passthrough.ts`)

**Seznam výjimek** (kontroluje se jako první a má přednost před shodou s cílem):

- Výchozí vzory: hostitelé bank, `.gov.`, poskytovatelé OAuth/SSO (Okta, Auth0) atd.
- Uživatelské vzory: uložené v databázové tabulce `agent_bridge_bypass`
- Hostitelé ve výjimkách obdrží transparentní tunel TCP — TLS se **nikdy nedešifruje**

**Výchozí přímý přenos** (žádná shoda s cílem a žádná shoda se seznamem výjimek):

- Také obdrží tunel TCP — spojení nejsou nikdy přerušena
- Zabraňuje tomu, aby AgentBridge narušoval obecný systémový provoz HTTPS

Priorita směrování:

```
seznam výjimek → shoda s cílem → přímý přenos
```

### 2.6 Certifikát nadřazené CA (`src/mitm/upstreamTrust.ts`)

Pro firemní síťová prostředí s vlastní CA:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Pokud je tato proměnná nastavena, nakonfiguruje globální dispatcher knihovny `undici` s dodatečným certifikátem CA, což umožní AgentBridge přistupovat k nadřazeným poskytovatelům prostřednictvím firemních proxy ukončujících TLS.

### 2.7 Maskování tajných údajů (`src/mitm/maskSecrets.ts`)

Nezávislý skener vytvořený metodou clean-room se aplikuje na těla požadavků a hlavičky s přihlašovacími údaji
**předtím**, než vstoupí do vyrovnávací paměti Inspektoru provozu nebo jakéhokoli protokolu. Provádí jediný lineární průchod:

- Tokeny s předponou `sk-` / `ak-` / `pk-` (ve stylu OpenAI/Anthropic)
- Přihlašovací údaje RFC 6750 `Authorization: Bearer <token>`, přičemž celý token má přednost
- Obecné dlouhé neprůhledné tokeny (≥40 znaků), včetně forem s tečkami a odsazením

`sanitizeHeaders()` převádí zachované názvy na malá písmena, deterministicky spojuje hodnoty polí, odstraňuje
sdílený seznam zakázaných hlaviček mezi jednotlivými uzly/rámců (včetně ověřování proxy), zcela rediguje `cookie` a
`set-cookie` a předává hodnoty přihlašovacích údajů skeneru.

## §3 Nastavení

### 3.1 Spuštění/zastavení serveru MITM

Použijte kartu serveru AgentBridge na adrese `/dashboard/tools/agent-bridge`:

| Akce                         | Popis                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spustit server               | Spustí `src/mitm/server.cjs` na portu 443. V modelu kořenové CA při prvním spuštění vytvoří `ca.crt` a nastaví aktivní certifikát jako důvěryhodný, pokud je k dispozici heslo pro sudo                                                                                                                                                                                                                                    |
| Zastavit server              | Korektně ukončí podřízený proces                                                                                                                                                                                                                                                                                                                                                                                           |
| Restartovat server           | Zastavení + spuštění (načte změny cílů a nově vygenerovaný certifikát)                                                                                                                                                                                                                                                                                                                                                     |
| Důvěřovat certifikátu        | Nainstaluje aktivní certifikát do systémového úložiště důvěryhodných certifikátů: `DATA_DIR/mitm/ca.crt` v modelu kořenové CA, `DATA_DIR/mitm/server.crt` u starší instalace s koncovým certifikátem                                                                                                                                                                                                                       |
| Stáhnout certifikát          | Stáhne aktivní certifikát pro ruční instalaci (`omniroute-mitm-ca.crt` = `ca.crt`, nebo `omniroute-mitm.crt` = `server.crt` u starší instalace s koncovým certifikátem)                                                                                                                                                                                                                                                    |
| Znovu vygenerovat certifikát | Nikdy nemění model certifikátu. Starší instalace s koncovým certifikátem: vystaví nový `server.crt`/`server.key` (aby jej server začal používat, restartujte jej). Model kořenové CA: obmění `ca.crt`/`ca.key`; operace je odmítnuta, pokud server běží. Nejprve se zruší důvěryhodnost staré důvěryhodné CA (vyžaduje heslo pro sudo), jinak se obměna přeruší. Klienti poté musí nové CA znovu nastavit jako důvěryhodné |

### 3.2 Nastavení důvěryhodnosti certifikátu

Než budou IDE přijímat připojení MITM, musí operační systém považovat certifikát CA služby AgentBridge za důvěryhodný.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Klíčenka):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Případně použijte tlačítko „Důvěřovat certifikátu“ na řídicím panelu (spustí příslušný příkaz pro váš operační systém a v případě potřeby zobrazí výzvu k zadání hesla pro sudo).

#### IDE založená na Electronu ignorují systémové úložiště důvěryhodných certifikátů (`NODE_EXTRA_CA_CERTS`)

Některá IDE — zejména **Antigravity IDE** a další aplikace odvozené od Electronu / VS Code — obsahují
vlastní běhové prostředí Node.js, které pro odchozí požadavky `fetch`/HTTPS **nepoužívá systémové
úložiště důvěryhodných certifikátů**. Nastavení CA jako důvěryhodné na úrovni OS/NSS postačuje pro nativní
**backend** IDE (např. jazykový server v Go, který používá systémový balíček CA), ale **frontend Electronu**
bude při TLS stále selhávat — projeví se to tak, že aplikace uživatele _odhlásí_ nebo zobrazí
_"chybu připojení"_, přestože protokol MITM ukazuje, že zaváděcí volání backendu vracejí `200`. Jsou
nutné dva kroky a oba jsou důležité:

1. Explicitně nasměrujte běhové prostředí na CA:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Spusťte IDE z tohoto shellu.** Spuštění pomocí ikony na ploše / Docku / nabídky Start
   **nepřevezme** exportované proměnné shellu a `~/.config/environment.d/*.conf` se projeví až po
   novém grafickém přihlášení. Nejprve IDE úplně ukončete — kvůli zámku jediné instance Electronu
   druhé spuštění pouze aktivuje existující proces a nové prostředí bude ignorováno.

Výše uvedený krok s nastavením důvěryhodnosti na úrovni OS + NSS je nadále nezbytný (síťová vrstva
Chromia používaná některými ověřovacími procesy čte uživatelské úložiště NSS a má vlastní statická
připnutí pro `*.googleapis.com`, která lokálně důvěryhodná CA přepíše). `NODE_EXTRA_CA_CERTS` navíc
pokrývá cestu Node `fetch`.

### 3.3 Směrování DNS

Pro každého agenta, jehož komunikaci chcete zachytávat, se musí jeho hostitelé API překládat na `127.0.0.1`. AgentBridge automaticky spravuje záznamy v `/etc/hosts`, když v průvodci nastavením přepnete DNS pro daného agenta.

Příklad záznamů v `/etc/hosts` pro GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Mapování modelů

Pomocí tabulky mapování modelů na kartě každého agenta definujte mapování zdroj → cíl:

| Zdrojový model (nativní pro agenta) | Cílový model (OmniRoute) |
| ----------------------------------- | ------------------------ |
| `gpt-4o`                            | `claude-sonnet-4.7`      |
| `*` (zástupný znak)                 | `claude-haiku-4.7`       |

Zástupný znak `*` namapuje jakýkoli nerozpoznaný model na zadaný cíl. Nastavení je uloženo v tabulce `agent_bridge_mappings`.

> **Tip — zjistěte skutečná ID modelů agenta.** IDE může odesílat názvy modelů, které se liší od
> popisků v jeho uživatelském rozhraní a mění se mezi hlavními verzemi. Například **Antigravity 2** odesílá
> `gemini-3.1-pro-low`, `gemini-pro-agent` a `gemini-3.1-flash-lite` — nikoli
> `gemini-2.5-pro` uváděný ve starší dokumentaci. Odešlete jeden chat bez odpovídajícího mapování: MITM
> zaznamená přesnou příchozí hodnotu `model:` a požadavek propustí dál. Namapujte tuto doslovnou hodnotu a
> další požadavek bude zachycen a směrován na váš cílový model.

### 3.5 Upozornění na rizika

AgentBridge zachytává přihlašovací údaje (tokeny OAuth, klíče API), které IDE používá k ověřování u upstream poskytovatelů. Před protokolováním jsou **maskovány** (viz §2.7), ale vrstva MITM nástroje OmniRoute je může zobrazit. Při první aktivaci každého agenta se zobrazí modální okno s upozorněním na rizika, které lze zavřít.

### 3.6 Údržba a diagnostika

Řídicí panel obsahuje kartu **Údržba a diagnostika** (`AgentBridgeMaintenanceCard`, v `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`), která zpřístupňuje provozní trasy MITM, jež dříve neměly uživatelské rozhraní. Její podtitulek zní: _„Otestujte kanál zachytávání, odstraňte zbytkový stav systému a přeneste své nastavení mezi počítači.“_ Klientské pomocné funkce karty se nacházejí v `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Tlačítko                   | Trasa                                  | Co dělá                                                                                                                                                                                                                            |
| -------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Diagnostikovat**         | `GET /api/tools/agent-bridge/diagnose` | Spustí samočinný test kanálu zachytávání a zobrazí zprávu pro každou kontrolu (✓/✗ + doporučení k nápravě).                                                                                                                        |
| **Opravit**                | `POST /api/tools/agent-bridge/repair`  | Vrátí zpět osiřelý systémový stav MITM (podvržené záznamy DNS, kořenovou CA, systémový proxy server), který zůstal po pádu nebo signálu SIGKILL. Operace je idempotentní — pokud je stav čistý, oznámí „Není co opravovat“.        |
| **Odebrat CA**             | `DELETE /api/tools/agent-bridge/cert`  | Zruší důvěru a odebere kořenovou CA MITM z úložiště důvěryhodných certifikátů operačního systému (explicitně a idempotentně). Zobrazuje se pouze tehdy, když je CA aktuálně důvěryhodná; vyžaduje vložené potvrzení „Odebrat CA?“. |
| **Exportovat konfiguraci** | `GET /api/tools/agent-bridge/config`   | Stáhne přenositelnou konfiguraci ve formátu JSON (viz §3.7).                                                                                                                                                                       |
| **Importovat konfiguraci** | `POST /api/tools/agent-bridge/config`  | Nahraje dříve exportovanou konfiguraci ve formátu JSON (viz §3.7).                                                                                                                                                                 |

Každá karta agenta má také vlastní tlačítko **Obnovit výchozí nastavení** (`POST
/api/tools/agent-bridge/agents/{id}/reset`) — možnost vrátit změny jedním kliknutím pro konkrétního agenta, která zruší podvržení pouze
hostitelů tohoto agenta, vymaže jeho uložená mapování modelů a resetuje jeho stav `dns_enabled`/`setup_completed`,
takže po úplném restartování bude IDE opět komunikovat se skutečným upstreamem. Tato akce **neovlivní**
sdílený server MITM ani kořenovou CA (ostatní agenti na nich mohou stále záviset) — ty zůstávají dostupné
prostřednictvím karty serveru a výše uvedené akce **Odebrat CA**. V systému Windows se také podle možností spustí
`ipconfig /flushdns`, protože klient DNS systému Windows ukládá položky souboru hosts do mezipaměti a jinak
právě odebrané podvržení nezahodí.

**Diagnostické kontroly** (`summarizeDiagnostics()` v `src/mitm/inspector/diagnostics.ts`). Trasa spustí pro každou kontrolu sondu s vedlejšími účinky a předá booleovské hodnoty čisté sumarizační funkci; vrátí se jeden verdikt `healthy` spolu s doporučením pro každé selhání:

| Název kontroly     | Co ověřuje                                                                          | Doporučení při selhání                                                                                                                                             |
| ------------------ | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `server-running`   | Proces serveru MITM je aktivní                                                      | „Server MITM není spuštěn. Spusťte jej na kartě AgentBridge.“                                                                                                      |
| `server-reachable` | Server MITM přijímá připojení na svém portu (sonda TCP)                             | „Server MITM nepřijímá připojení na svém portu. Zkontrolujte, zda je port volný a zda máte oprávnění jej navázat.“                                                 |
| `cert-exists`      | Certifikát MITM byl vygenerován na disku                                            | „Dosud nebyl vygenerován žádný certifikát MITM. Vygenerujte jej na kartě AgentBridge.“                                                                             |
| `cert-trusted`     | Kořenová CA MITM se nachází v úložišti důvěryhodných certifikátů operačního systému | „Operační systém nedůvěřuje kořenové CA MITM, takže zachytávání TLS selže. Nastavte certifikát jako důvěryhodný na kartě AgentBridge.“                             |
| `dns-configured`   | Cílové názvy hostitelů jsou podvrženy v `/etc/hosts`                                | „Cílové názvy hostitelů nejsou v /etc/hosts podvrženy, takže provoz se k proxy serveru nikdy nedostane. Povolte DNS pro agenty, jejichž provoz chcete zachytávat.“ |

**Banner osiřelého stavu:** když stránka zjistí stav, který zůstal po pádu (podvržení DNS / CA / systémový proxy server), karta zobrazí žlutý banner — _„Předchozí relace zanechala v systému stav (podvržení DNS, CA nebo systémový proxy server). Spusťte Opravit, abyste jej odstranili.“_ — a zvýrazní tlačítko **Opravit**. `Repair` je obdobou příznaku `--cleanup` nástroje ProxyBridge na aplikační vrstvě (deleguje na `repairMitm()` v `src/mitm/manager.ts`).

> Kořenová CA pro MITM zůstává nainstalovaná i po zastavení/spuštění, aby se zabránilo
> opakovaným výzvám k zadání hesla pro sudo (stejné chování jako u mitmproxy/Charles), takže její odebrání je explicitní
> akcí **Odebrat CA**, nikoli něčím, co se provede automaticky při zastavení.

### 3.7 Přenosný import/export konfigurace

AgentBridge dokáže serializovat stav **nastavitelný operátorem** do verzovaného objektu JSON, aby bylo možné stejné nastavení replikovat na více počítačích. Serializátor je `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) a je validován pomocí `AgentBridgeConfigSchema`.

Export obsahuje přesně tři části (vestavěné výchozí hodnoty se záměrně **NEEXPORTUJÍ**, takže při importu nikdy nedochází k jejich duplikování ani ke konfliktům s nimi):

| Pole             | Zdroj                                                            | Poznámky                                                                    |
| ---------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `bypassPatterns` | uživatelsky definované vzory pro obejití (`agent_bridge_bypass`) | výchozí vzory pro banky, státní správu a Okta jsou vyloučeny                |
| `customHosts`    | vlastní hostitelé Traffic Inspectoru (`inspector_custom_hosts`)  | každý: `{ host, kind: "llm"\|"app"\|"custom", label? }`                     |
| `agentMappings`  | mapování modelů pro jednotlivé agenty (`agent_bridge_mappings`)  | `{ [agentId]: [{ source, target }] }` pro každého agenta, který má mapování |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Chování při importu** (`POST /api/tools/agent-bridge/config`): vzory pro obejití a mapování jednotlivých agentů se **zcela nahradí**; vlastní hostitelé se přidávají **idempotentně** (`INSERT OR IGNORE`). Odpověď uvádí, kolik položek každého typu bylo použito:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Co konfigurace **NEOBSAHUJE**: stav spuštění serveru, cesty k certifikátům, stav DNS jednotlivých agentů, cestu k nadřazené CA a nastavení TPROXY — jde o stav hostitele/běhového prostředí, nikoli o přenosné předvolby.

## §5 Zabezpečení

### Použitá pevná pravidla

| Pravidlo                           | Použití                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`     | Všechny chyby obslužných rutin jsou před odpovědí nebo zápisem do vyrovnávací paměti očištěny             |
| **#13** Předávání prostředí shellu | Úpravy `/etc/hosts` používají volbu `env` — bez řetězcové interpolace cest                                |

### Seznam výjimek pro citlivé hostitele

Seznam výjimek zajišťuje, že finanční instituce, poskytovatelé OAuth/SSO a další citliví hostitelé nejsou **nikdy dešifrováni**. Jejich provoz TLS prochází jako transparentní tunel TCP — OmniRoute nikdy nevidí data v otevřené podobě.

Výchozí vzory výjimek zahrnují:

- `*.bank.*`, `*.gov.*` (finance/státní správa)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identita)
- `*.apple.com`, `*.icloud.com` (systémové služby Apple)

Vzory výjimek přidané uživatelem jsou uloženy v tabulce `agent_bridge_bypass` a mají přednost před vším ostatním.

### Maskování tajných údajů

Používá se `maskSecrets()` ze souboru `src/mitm/maskSecrets.ts`:

- Na každé tělo požadavku před voláním `TrafficBuffer.push()`
- Na každou hlavičku před protokolováním nebo vysíláním

Vzory: tokeny s předponou `sk-`/`ak-`/`pk-`, tokeny `Bearer` a obecné tokeny o délce ≥40 znaků.

### Certifikát nadřazené CA

Když je nastavena proměnná `AGENTBRIDGE_UPSTREAM_CA_CERT`, soubor se načte při spuštění. Pokud cesta existuje, ale soubor nelze přečíst, AgentBridge zaznamená srozumitelnou chybu a odmítne se spustit (zabrání tím tichým selháním TLS v podnikových prostředích).

### Známá omezení

- **Port 443 vyžaduje oprávnění**: V Linuxu potřebuje AgentBridge na binárním souboru Node nastavit `setcap 'cap_net_bind_service=+ep'` nebo musí být spuštěn prostřednictvím `authbind`. Průvodce nastavením zobrazuje pokyny specifické pro daný operační systém.
- **Je vyžadován restart IDE**: Po přesměrování DNS je nutné IDE restartovat, aby se nové překládání hostitele projevilo.
- **Pevně zakódované tokeny OAuth**: Někteří agenti (Kiro, Antigravity) ukládají obnovovací tokeny OAuth lokálně. Pro AgentBridge jsou transparentní — v každém požadavku vidí token Bearer, který je před protokolováním maskován.
- **Frontendové aplikace Electron vyžadují `NODE_EXTRA_CA_CERTS`**: IDE, jejichž frontend běží v přibaleném běhovém prostředí Node/Electron, ignorují úložiště důvěryhodných certifikátů operačního systému/NSS a musí být spuštěna ze shellu s nastavenou proměnnou `NODE_EXTRA_CA_CERTS` (viz §3.2). Příznak chybějícího nastavení: backend IDE se ověří (MITM zobrazuje odpovědi `200`), ale uživatelské rozhraní zůstává odhlášené.
- **Více instalací stejného IDE je na sobě nezávislých**: systémová instalace (např. `/usr/share/antigravity/antigravity`) a uživatelská lokální instalace „Full“ (např. `~/AntigravityIDE_Full/antigravity-ide`) jsou samostatné procesy s vlastními běhovými prostředími — každý z nich musí být znovu spuštěn s vloženou CA. Před opětovným spuštěním určete podle cesty k binárnímu souboru, který z nich je spuštěný.
- **Identitu určuje systémová výzva agenta, nikoli směrovaný model**: když přemapujete model agenta na jiného poskytovatele, odpověď se stále hlásí k nativní identitě agenta (např. Antigravity odpoví „Používám Gemini“), protože ji IDE vkládá do systémové výzvy. Skutečný backend ověřte v `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), nikoli dotazem modelu na jeho identitu.

## §6 Řešení problémů

### Konflikt na portu 443

Pokud již na portu 443 naslouchá jiný proces (webový server, VPN apod.):

```bash
lsof -i :443          # vyhledání procesu
sudo fuser -k 443/tcp  # vynucené ukončení (používejte opatrně)
```

Případně v nastavení AgentBridge nakonfigurujte neprivilegovaný port a nastavte pravidla přesměrování `iptables` / `pf`.

### Certifikát není důvěryhodný

Pokud IDE po spuštění AgentBridge zobrazuje chyby TLS:

1. Ověřte, že byl certifikát nainstalován: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) nebo `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Některé aplikace používají vlastní úložiště důvěryhodných certifikátů (Firefox, Chrome v Linuxu). Spusťte znovu „Trust Cert“ a zkontrolujte úložiště certifikátů specifické pro NSS/Firefox.
3. Po nastavení důvěryhodnosti IDE restartujte — probíhající relace TLS používají původní stav důvěryhodnosti.

### IDE je odhlášené / zobrazuje „chybu připojení“ navzdory důvěryhodné CA

Příznak: po přesměrování DNS a nastavení důvěryhodnosti CA se IDE založené na Electronu (např. Antigravity)
otevře **odhlášené** nebo zobrazí chybu ověřování/připojení, přestože protokol MITM ukazuje, že
inicializační volání (`loadCodeAssist`, `fetchAvailableModels`, …) vracejí `200`.

Příčina: **přibalené běhové prostředí Node/Electron v IDE ignoruje systémové úložiště důvěryhodných certifikátů**. Nativní
backend (jazykový server v Go) důvěřuje systémové CA a ověří se, ale frontend Electron
nikoli — uživatelské rozhraní se proto domnívá, že je offline.

Řešení (oba kroky): exportujte `NODE_EXTRA_CA_CERTS=<ca.crt>` **a znovu spusťte IDE z tohoto
shellu**, nikoli pomocí ikony na ploše. Nejprve IDE zcela ukončete — zámek jediné instance Electronu způsobí,
že druhé spuštění pouze přepne pozornost na existující proces a nové prostředí se ignoruje. Viz §3.2.
To odpovídá otevřenému hlášení v upstream projektu, podle kterého samostatný agent přes MITM funguje, ale varianta
IDE ve stejném prostředí selhává.

### Změny DNS se neprojevily

Zkontrolujte, zda byl aktualizován soubor `/etc/hosts`:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Vyprázdněte mezipaměť DNS:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE nebylo rozpoznáno

Automatická detekce používá běžná umístění instalace. Pokud se detekce nezdaří, ale IDE je nainstalováno:

- Zkontrolujte, zda se binární soubor IDE nenachází v nestandardním umístění
- Průvodce nastavením bude i nadále fungovat — selhání detekce pouze znamená, že odznak nezobrazí cestu k instalaci

### Chyby obslužné rutiny (načtení z upstream serveru selže)

Pokud AgentBridge zachytává požadavky, ale všechny selhávají:

1. Ověřte, že je na `/dashboard/providers` připojen alespoň jeden poskytovatel
2. Zkontrolujte protokoly serveru OmniRoute: `APP_LOG_LEVEL=debug` v `.env`
3. Ověřte, že `OMNIROUTE_BASE_URL` odkazuje na správný koncový bod směrovače (výchozí: `http://127.0.0.1:20128`)

## §8 Plán vývoje

### Průzkum Trae

Trae je relativně nový AI asistent pro programování. Před implementací handleru:

1. Identifikujte binární soubor/rozšíření v tržištích VS Code / JetBrains nebo samostatnou aplikaci
2. Zachyťte provoz pomocí mitmproxy, abyste zjistili hostitele API a strukturu endpointů
3. Určete mechanismus autentizace
4. Na základě smluvních podmínek a zjistitelnosti API rozhodněte, zda pokračovat

Dokud nebude průzkum dokončen, karta Trae na řídicím panelu zobrazuje odznak „Probíhá průzkum“ s odkazem „Nahlásit životaschopnost“. Zástupný handler v `src/mitm/handlers/trae.ts` vyvolá strukturovanou chybu `Dosud neimplementováno`.

### Agenti v backlogu (vyžadován MITM — bez podpory vlastní základní adresy URL)

Následující nástroje ve svých aktuálních verzích nepodporují vlastní základní adresy URL, takže MITM je jedinou možností zachytávání. Posouzení životaschopnosti zatím nebylo dokončeno:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — oddělené od Kiro IDE)
- **Cowork** (desktopová aplikace Anthropic)

Poznámka: GitHub Copilot CLI ≥v1.0.19 podporuje `COPILOT_PROVIDER_BASE_URL` — pro tento nástroj použijte místo MITM přímou konfiguraci.
