Pomocí tohoto průvodce zvolte nejmenší spolehlivý vývojový cyklus pro pull request. Nenahrazuje
níže odkazované dokumenty o architektuře a zabezpečení konkrétních oblastí; propojuje každý běžný
typ změny s jeho kontrakty, cílenými kontrolami a pokrytím v CI.

## Postup, kterým prochází každá změna

1. **Před úpravami zvolte základní větev.** Najděte nejvyšší aktivní větev `release/v*` a vytvořte
   větev z její špičky. Cílovou větví musí být tato větev, nikoli `main`. Pokud probíhá zmrazení
   vydání, necílujte na zmrazenou větev; použijte další aktivní cyklus popsaný v dokumentu
   [Model větvení a vydávání](BRANCHING_MODEL.md).
2. **Pojmenujte kontrakty.** Určete každý katalog, schéma, generovaný artefakt, veřejné API nebo
   uživatelské rozhraní, kterého se změna týká. Níže uvedená tabulka uvádí minimální výchozí sadu.
3. **Napište nebo aktualizujte cílené testy.** Změny produkčního kódu v `src/`, `open-sse/`, `electron/`
   nebo `bin/` vyžadují automatizovaný test ve stejném PR. Spusťte nejmenší sadu testovacích souborů,
   která dané chování prokáže, a poté uvedené cílené kontroly.
4. **Širokou matici nechte spustit v CI.** V PR se spustí všechny části jednotkových testů, Vitest,
   kontrola pokrytí a produkční sestavení. Širokou sadu spouštějte lokálně pouze tehdy, když cílené
   selhání naznačuje širší dopad nebo když změna zasahuje několik subsystémů.
5. **Před kontrolou změny sesynchronizujte.** Načtěte aktivní základní větev, zkontrolujte její nové
   commity a rozdíl svých změn vůči ní a poté podle pracovního postupu přispěvatele proveďte rebase
   nebo sloučení základní větve. Konflikty v generovaných souborech a katalozích vyřešte v jejich
   zdroji, znovu je vygenerujte, opakujte cílený cyklus a ověřte, že PR stále cílí na aktivní větev
   vydání.
6. **Zaznamenejte důkazy.** V šabloně PR uveďte spuštěné příkazy, všechny přidané nebo změněné
   testovací soubory, migrace či příznaky funkcí a veškeré validace čekající pouze na CI.

## Zlaté stezky podle typu změny

Níže uvedené příkazy představují minimální cílené kontroly, nikoli oprávnění k přeskočení testu, který přímo pokrývá chování, které jste změnili.

### Poskytovatel

**Smlouvy**

- Definice poskytovatele v `src/shared/constants/providers/` a jeho složení v `src/shared/constants/providers.ts`.
- Modely a možnosti v `open-sse/config/providerRegistry.ts` nebo jeho extrahovaných souborech registru.
- výběr Executor/translator, konfigurace klíče OAuth nebo API a aktiva řídicího panelu. Nekomprimujte regenerované diagramy `docs/reference/PROVIDER_REFERENCE.md` nebo README : aktualizace vydání je přepíše (`check:pr-derived-paths` selže s funkcí PR, která je přenáší).
- Veřejné přihlašovací údaje musí používat `resolvePublicCred()`; chybové odpovědi musí používat sdílené sanitované pomocníky při chybách. Viz `docs/security/PUBLIC_CREDS.md` (git; není zkompilován do `/docs`) a [Error Sanitization](../security/ERROR_SANITIZATION.md).

**Zaměřená smyčka**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # preview the generated reference; do not commit it
npm run lint
```

Otestujte také všechny dotčené skupiny požadavků: chat, odpovědi, obrázky, vložení, zvuk nebo video. Zkontrolujte vygenerovaný katalog a zlaté diffy při změnách smlouvy; nepřijímejte je slepě.

### Směrování

**Smlouvy**

- Hodnoty veřejné strategie a metadata UI v `src/shared/constants/routingStrategies.ts`.
- Odeslání a objednání pod `open-sse/services/combo.ts` a `open-sse/services/combo/`.
- Kombinovaná schémata, persistence, stav odolnosti, schopnosti modelu a ovládací prvky API/UI.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) a dokumentace odolnosti při změně chování.

**Zaměřená smyčka**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy or dispatch changes
npm run check:known-symbols      # strategy registration changes
npm run lint
```

Lokálně použijte deterministické simulované upstream testy. Živé kombinované kouře vyžadují přihlašovací údaje a jsou manuální, nikoli náhražky CI.

### UI / UX

**Smlouvy**

- Next.js route/page a sdílené hranice komponent pod `src/app/` a `src/shared/components/`.
- tvary odezvy API, stavy loading/empty/error, chování klávesnice a čtečky obrazovky, responzivní rozvržení, tématika a rozšíření národního prostředí.
- anglické zdrojové řetězce UI v `src/i18n/messages/en.json`; nekódujte novou kopii pro uživatele.

**Zaměřená smyčka**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Spusťte aplikaci pro interakci nebo vizuální změny a zkontrolujte úzké i široké výřezy. CI provozuje produkční sestavení a širší sady; vizuální chování stále vyžaduje cílenou komponentu, Playwright nebo zdokumentovanou ruční kontrolu vhodnou pro změnu.

### i18n

**Smlouvy**

- `src/i18n/messages/en.json` je zdroj UI ; `config/i18n.json` je zdroj národního prostředí.
- katalogy CLI žijí samostatně pod `bin/cli/locales/`.
- Přesně zachovejte zástupné symboly a značky ICU. Nepřekládejte názvy product/provider/model, názvy protokolů a hlaviček, příkazy, identifikátory code/JSON, URLs, proměnné prostředí nebo chráněné výrazy jako `OmniRoute`, `OAuth`, `MCP` a `A2A`. Aktuální zdrojový seznam je `scripts/i18n/glossary/protected-terms.json`.

Prvek PR upravuje pouze `src/i18n/messages/en.json` (CLI: `bin/cli/locales/en.json`); ostatní lokality jsou dokončeny jednou za vydání aktualizací vydání nebo vlnou překladu (`docs/guides/I18N.md` → "Pouze funkce PRs dotyk `en.json` "). `npm run check:pr-derived-paths` selže funkci PR, která upravuje jiný katalog lokalit.

**Zaměřená smyčka**

```bash
npm run i18n:check-ui-coverage
npm run check:ui-icu
node scripts/i18n/check-key-completeness.mjs --mode=pr      # what CI runs on your PR
node scripts/i18n/check-ui-value-drift.mjs --mode=pr
node scripts/check/check-cli-i18n.mjs --mode=pr              # when CLI strings change
npm run i18n:check-glossary
npm run lint
```

Bez `--mode=pr` tyto brány běží v režimu uvolnění lokálně a hlásí každý klíč přidaný nebo přepsaný v `en.json`; to je práce na obnovení vydání, ne vaše PR.

Toto je návod pro stávající systém, nikoli výzva k rozšíření jeho nástrojů nebo modelu klíče. Během navrhování náhradního systému nechte náplasti i18n chirurgické. Nespouštějte překladové příkazy, které volají externí služby, pokud úloha výslovně nevyžaduje vygenerované překlady a pokud jste nezkontrolovali výsledný rozdíl.

### CLI

**Smlouvy**

- Veřejné příkazy a příznaky v `bin/cli/`, generované příkazy API, ukončovací kódy, výstupní tvary stdout/stderr a JSON, chování config/environment a zabalené soubory.
- Uživatelské řetězce CLI musí používat vrstvu CLI i18n ( klíče `t()`, které existují v `bin/cli/locales/en.json`). Prvek PR upravuje pouze `en.json`; `pt-BR` a ostatní lokality jsou dokončeny při vydání.
- Zachovat Node jako podporované běhové prostředí a publikovanou binární smlouvu.

**Zaměřená smyčka**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
node scripts/check/check-cli-i18n.mjs --mode=pr
npm run build:cli             # generated/bundled CLI changes
npm run check:pack-policy     # package-surface changes
npm run lint
```

Použijte přesný příkaz v dočasném datovém adresáři, když chování závisí na analýze, souborech nebo stavu ukončení. CI provádí širší kontroly artefaktů balíčku a ekosystému.

### Databáze

**Smlouvy**

- Doménové moduly pod `src/lib/db/`; import konkrétních modulů přímo (stará vrstva reexportu `localDb.ts` byla odstraněna).
- Číslované, idempotentní migrace SQL pod `src/lib/db/migrations/`, bezpečnost transakcí, chování při upgradu, indexy a každý volající ovlivněný schématem.
- Trasy a handlery nikdy nevydávají surovou SQL přímo.

**Zaměřená smyčka**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Při přidávání migrace otestujte jak novou databázi, tak upgrade z předchozího schématu. Testy databáze musí během čištění zavřít úchyty a volat `resetDbInstance()`. Spusťte `npm run test:bun:db` pouze tehdy, když se změní cesta adaptéru Bun s nejlepším úsilím; Uzel zůstává autoritativní.

### Sestavení / nasazení

**Smlouvy**

- Kořenový a pracovní prostor manifests/lockfile, `scripts/build/`, samostatné sestavení Next.js, obsah balíčku `dist/`, metadata platformy Electron, pracovní postupy CI a hlídače nasazení.
- Podporované rozsahy uzlů a použití Bun uvedené v seznamu povolených v `CLAUDE.md` musí zůstat nedotčené.
- Artefakty sestavení zůstávají nesledované; platí zásady závislosti, licence, pracovního postupu a balíčků.

**Zaměřená smyčka**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency or lockfile changes
npm run check:pack-policy      # published package surface changes
npm run lint
```

Použijte `npm run build` lokálně pouze v případě, že změna ovlivní kompilaci, samostatné sestavení, aktiva nebo runtime svazování. `npm run build:release` používejte pouze pro ověření release/deploy. sestavení CI je konečným signálem napříč platformami; Změny Electron specifické pro platformu vyžadují odpovídající důkazy o sestavení nebo kouři.

## Vývojářské skripty pro sdílený stroj

Dva pomocné skripty v `scripts/dev/` zajišťují lokální pracovní cyklus na vývojovém stroji, kde jsou aktivní i další relace:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # soubory z merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # přesně tyto soubory
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # izolovaný worktree, bezpečný pro paralelní práci
```

- `typecheck-touched.sh` provádí typovou kontrolu pouze změněných souborů `.ts/.tsx` prostřednictvím dočasného
  souboru `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) s limitem haldy 6 GB, takže nahrazuje celoprojektový příkaz `tsc -p tsconfig.json`,
  který na vytíženém stroji končí kvůli nedostatku paměti. Vypíše chyby ve změněných souborech a jeden souhrnný řádek a skončí
  s kódem `1` při chybách ve změněných souborech, `2`, pokud jsou chyby pouze v importovaných souborech nebo tsc skončil
  bez diagnostiky (přečtěte si uvedený protokol v `_artifacts/typecheck-touched/`), a `0`, pokud
  nejsou žádné chyby. Dočasný tsconfig je vždy odstraněn; nikdy jej necommitujte.
- `new-worktree.sh` serializuje souběžná spuštění pomocí `<git-common-dir>/omniroute-new-worktree.lock`
  (ve výchozím nastavení čeká až 600 s a zobrazuje přitom viditelnou zprávu; hlavička skriptu popisuje
  způsob změny tohoto nastavení) a vrátí zpět
  jím vytvořenou větev, pokud `git worktree add` selže před vytvořením worktree, takže opakovaný pokus
  nevyžaduje ruční `git branch -D`. Pevně odkazovaný adresář `node_modules` a kopie `.husky/_` zůstávají beze změny.

## Lokální cyklus kandidátního sestavení

Testy zdrojového kódu nemohou prokázat, že se zabalený artefakt spustí: seznamy souborů balíčku, pročištěné závislosti
a nativní binární soubory selžou až po instalaci a spuštění tarballu. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) je lokální část postupu jediné sestavení / ověření / nasazení z
RFC #8084: sestaví jednoho kandidáta, ověří přesně tento artefakt, nasadí jej přejmenováním adresářů
a vrátí jej zpět, pokud nasazený slot neprojde kontrolou stavu.

```bash
npm run dev:candidate -- run --dry-run --json  # vypíše plán, nic nezmění
npm run dev:candidate -- run                   # sestavení + ověření + nasazení, automatický návrat zpět
npm run dev:candidate -- build                 # npm pack + instalace do _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # spuštění na volném portu, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # prohodí current a previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # znovu použije tarball sestavený jinde (CI)
```

- **Sestavte pouze jednou.** `build` zabalí aktuální strom (vyžaduje `dist/server.js`, proto nejprve spusťte
  `npm run build:release`) nebo zkopíruje `--from-tarball` a poté nainstaluje tarball do
  izolovaného prefixu npm, protože tarball neobsahuje `node_modules`. Id je zkrácený sha aktuálního `HEAD`
  (`-dirty`, pokud strom obsahuje lokální změny), nebo `tgz-<sha256>` pro tarball. Již sestavené čisté id
  se namísto opětovného sestavení použije znovu; pro nové sestavení použijte `--force`.
- **Ověřujte balíček, nikoli zdrojový kód.** `validate` spustí nainstalované CLI
  (`serve --port <free port>`) s novým `DATA_DIR=<candidate>/data`, falešnými tajnými údaji a proměnnými
  operátora `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` a `INITIAL_PASSWORD` odstraněnými z
  prostředí, čímž ověří chování nové instalace bez klíče na rozhraní loopback. Čeká, až
  `GET /api/health` vrátí 200, vyžaduje, aby `GET /v1/models` vrátilo 200, zastaví skupinu procesů
  a zaznamená výsledek společně s hashem tarballu do `validation.json`.
- **Nasaďte stejný artefakt.** `promote` odmítne kandidáta bez úspěšného ověření jeho
  aktuálního hashe tarballu. Výchozí aktivní slot je `_artifacts/candidate/current`; `--target <dir>`
  vybere jiný adresář na stejném souborovém systému a jeho předchozí slot bude `<dir>.previous`.
  Každé přejmenování je atomické a případné selhání v průběhu obrátí již provedená přejmenování.
- **Vraťte nasazení zpět.** `run` znovu ověří nasazený slot a při selhání této kontroly prohodí
  `current` a `previous` zpět. Kandidát, který neprojde prvním ověřením, není nikdy nasazen.

Vše se zapisuje do adresáře `_artifacts/candidate/`, který git ignoruje; existující instalace OmniRoute
ani její datový adresář nejsou nikdy změněny. Nasazené CLI se nachází v
`_artifacts/candidate/current/prefix/bin/omniroute`; při jeho používání jej spusťte s vlastním `DATA_DIR`.
Návratové kódy: `0` úspěch, `1` neúspěšné ověření nebo nasazení, `2` chyba použití nebo chybějící sestavení.

## Lokální smyčka versus CI

| Spouštět lokálně pro každou úpravu                                                     | CI poskytuje širší zpětnou vazbu                                                         |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Přímé testy chování a výše uvedené kontroly kategorií                                  | Plná sada jednotkových testů rozdělená do shardů a sériové testy                         |
| `npm run lint`                                                                         | Sady Vitest a postupně zpřísňované požadavky na pokrytí a kvalitu                        |
| Kontrola typů nebo sestavení pouze tehdy, když to vyžaduje dotčený kontrakt            | Produkční sestavení a kontroly zabezpečení, dokumentace, závislostí a zásad pro PR       |
| Ruční interakce / živé kontroly pouze tehdy, když automatizace nedokáže chování ověřit | Mezistupňové integrační kontroly a kontroly platforem nakonfigurované pracovním postupem |

Úspěšná cílená smyčka dokládá stav změněného kontraktu, ale není důkazem, že projdou
nesouvisející kontroly CI. Zároveň nenechávejte každou lokální úpravu čekat na dokončení celé
matice repozitáře.

## Kontrolní seznam pro sesouladění

Před požádáním o kontrolu:

- Ověřte, že základem PR je stále nejvyšší aktivní větev `release/v*`.
- Načtěte tuto základní větev a zkontrolujte commity, které do ní byly začleněny od vytvoření vaší větve.
- Pomocí `git diff <active-base>...HEAD` zkontrolujte neúmyslné nebo generované změny.
- Konflikty v katalozích a generovaných dokumentech vyřešte aktualizací zdroje a opětovným vygenerováním výstupu.
- Po sesouladění znovu spusťte všechny cílené testy a kontroly uvedené v popisu PR.
- Nikdy neoslabujte aserce ani nevynechávejte povinné testy jen proto, abyste se přizpůsobili posunuté základní větvi.

Pravidla pro zmrazení vydání a změnu cílové větve naleznete v dokumentu
[Model větvení a vydávání](BRANCHING_MODEL.md). Úplný přehled kontrol CI naleznete v dokumentu
[Referenční přehled kontrol kvality](../architecture/QUALITY_GATES.md).
