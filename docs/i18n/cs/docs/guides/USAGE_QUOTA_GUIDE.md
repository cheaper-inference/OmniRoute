> **TL;DR**: OmniRoute sleduje využití tokenů u každého požadavku, vypočítává náklady, vynucuje kvóty pro jednotlivé API klíče a zobrazuje analytická data na řídicím panelu. Tato příručka vysvětluje, jak vše funguje.

**Zdroje:**

- `open-sse/services/usage.ts` (~70KB) — hlavní sledování využití
- `src/lib/usageAnalytics.ts` (~10KB) — agregace pro řídicí panel
- `src/lib/db/quotaSnapshots.ts` — historická data kvót
- `src/lib/db/usage*.ts` — několik databázových modulů souvisejících s využitím

## Přehled

Každý požadavek, který prochází přes OmniRoute, generuje **záznam o využití**, který zachycuje:

- **Identitu**: který API klíč, poskytovatel, model a kombinace
- **Tokeny**: tokeny promptu, tokeny dokončení, tokeny z mezipaměti a celkový počet
- **Náklady**: částku v USD (vypočítanou z cenových údajů)
- **Časování**: latenci a časová razítka začátku/konce
- **Stav**: úspěch, chyba, omezení rychlosti atd.

Tyto záznamy se agregují do **analytických dat**, ukládají se jako **snímky kvót** a používají se k vynucování **rozpočtových limitů pro jednotlivé klíče**.

```
Požadavek ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    analytika  kvóta   účtování
                    (panel)     (vynucení) (export)
```

## Co se zaznamenává

Služba `usage.ts` zachycuje **událost využití** pro každý požadavek:

| Pole               | Typ     | Zdroj                                                            |
| ------------------ | ------- | ---------------------------------------------------------------- |
| `id`               | string  | UUID vygenerované při záznamu                                    |
| `apiKeyId`         | string  | Klíč API, který inicioval požadavek                              |
| `provider`         | string  | ID poskytovatele (openai, anthropic atd.)                        |
| `model`            | string  | ID modelu (gpt-5, claude-opus-4-6 atd.)                          |
| `comboId`          | string? | ID kombinace, pokud je požadavek směrován přes kombinaci         |
| `promptTokens`     | number  | Z odpovědi nadřazeného poskytovatele                             |
| `completionTokens` | number  | Z odpovědi nadřazeného poskytovatele                             |
| `cachedTokens`     | number  | Tokeny nalezené v mezipaměti (ukládání promptů u Anthropic atd.) |
| `totalTokens`      | number  | prompt + dokončení                                               |
| `costUsd`          | number  | Vypočteno z cenových údajů                                       |
| `latencyMs`        | number  | Celková doba zpracování požadavku                                |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`       |
| `errorClass`       | string? | Třída chyby, pokud stav není success                             |
| `timestamp`        | string  | ISO 8601 UTC                                                     |
| `metadata`         | object  | Vlastní data vložená pluginem                                    |

### Odkud pocházejí tokeny

Tokeny se získávají z odpovědi nadřazeného poskytovatele v **obslužné rutině odpovědi**:

```ts
// Z open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

U poskytovatelů, kteří nevracejí údaje o využití (někteří poskytovatelé využívající webové cookies), OmniRoute počet tokenů **odhaduje** pomocí heuristiky `~4 chars per token` (viz `open-sse/services/autoCombo/pipelineRouter.ts`).

### Tokeny v mezipaměti

OmniRoute sleduje `cached_tokens` odděleně od `prompt_tokens`, protože:

- Anthropic účtuje za tokeny promptu uložené v mezipaměti sníženou sazbu (10 % běžné sazby)
- Někteří poskytovatelé vracejí `cache_read_input_tokens`, které by měly být oceněny jinak
- Analytika může zobrazit **míru zásahů mezipaměti** = `cached_tokens / prompt_tokens`

### Diagnostika úrovní zápisu do mezipaměti

Panel stavu mezipaměti promptů na analytickém přehledu rozlišuje poskytovatelem hlášené
zápisy do mezipaměti na 5 minut a 1 hodinu. Hodnoty Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` a
`usage.cache_creation.ephemeral_1h_input_tokens` se zachovávají při převodu údajů o využití ve streamovaném i
nestreamovaném režimu a ukládají se se souhrny protokolů volání. Souhrnný
počet zápisů do mezipaměti se k těmto kategoriím nepřičítá podruhé.

Volání pouze se souhrnným čítačem zápisů, včetně starších záznamů, mají neznámou
úroveň. U částečného rozpisu zůstává nepřiřazený zbytek neznámý; neplatné nebo
konfliktní čítače se označují, místo aby jim byla bez upozornění přiřazena hodnota TTL. Značky
TTL na straně požadavku nejsou důkazem účtované úrovně.

Odhad zápisů odpovídající cenám API na tomto panelu zahrnuje pouze hlášené úrovně se známou cenou, nikoli
celý požadavek. U nativních cen modelů Claude/Anthropic používá 1,25násobek
vstupní sazby pro zápisy na 5 minut a dvojnásobek vstupní sazby pro zápisy na 1 hodinu. Chybějící
cena znamená nedostupnou hodnotu, nikoli nulu. Ceny se zaznamenávají při protokolování každého nového volání;
historické záznamy se nepřeceňují. Účty s předplatným proto mohou mít
odhad odpovídající cenám API, aniž by tato částka představovala skutečný finanční výdaj nebo čerpání
kvóty předplatného. Stávající výpočty kvót, rozpočtů a nákladů přesně podle poskytovatele zůstávají beze změny.

Tato diagnostika využívá stávající kapacitně omezený souhrn stavu mezipaměti a uchovávání
protokolů volání. Nemění výchozí hodnoty TTL požadavků, směrování ani výběr účtu.
Zachycování TTL požadovaného klientem oproti skutečnému odchozímu TTL v okamžiku
odeslání poskytovateli je odloženo; tento panel uvádí úrovně podle údajů z vyúčtování, nikoli skutečné odchozí TTL.

Implementace: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` a `open-sse/utils/cacheWriteUsage.ts`.

## Výpočet nákladů

Náklady se počítají z **cenových dat** synchronizovaných z LiteLLM (`src/lib/pricingSync.ts`):

| Model             | Vstup $/1M | Výstup $/1M | Mezipaměť $/1M |
| ----------------- | ---------- | ----------- | -------------- |
| gpt-5             | $2.50      | $10.00      | —              |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50          |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30          |
| gemini-2.5-pro    | $1.25      | $10.00      | —              |

Vzorec pro výpočet nákladů (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Proč se tokeny z mezipaměti odečítají od tokenů promptu?** Část z mezipaměti je účtována samostatně; účtování vstupní ceny za celý prompt by vedlo k započítání příliš vysoké částky.

### Synchronizace cen

Cenová data se automaticky synchronizují z LiteLLM prostřednictvím koncového bodu `/api/pricing/sync` (spouští jej vestavěná úloha cron, nikoli uživatelská proměnná prostředí):

```bash
# Ruční spuštění
curl -X POST http://localhost:20128/api/pricing/sync
```

U modelů bez cenových dat OmniRoute přejde na **odhad nákladů** pomocí interních průměrných sazeb (získaných z cenových dat LiteLLM).

## Agregace podle časového rozsahu

Modul `usageAnalytics.ts` vypočítává widgety přehledu z nezpracovaných dat o využití. Podporuje 7 časových rozsahů:

| Rozsah   | Období                                | Případ použití                        |
| -------- | ------------------------------------- | ------------------------------------- |
| `1d`     | Posledních 24 hodin                   | Detekce hodinových špiček v nákladech |
| `7d`     | Posledních 7 dní                      | Týdenní kontrola                      |
| `30d`    | Posledních 30 dní                     | Měsíční fakturace                     |
| `90d`    | Posledních 90 dní                     | Čtvrtletní analýza                    |
| `ytd`    | Od 1. ledna aktuálního roku           | Sledování ročního rozpočtu            |
| `all`    | Celé období                           | Statistiky za celou dobu              |
| `custom` | Uživatelem definovaný začátek a konec | Audity, dotazy ad hoc                 |

### Vypočítávané widgety přehledu

Pro libovolný časový rozsah analytická vrstva vypočítává:

| Widget                            | Popis                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------- |
| **Souhrnné karty**                | Celkový počet požadavků, celkové náklady, celkový počet tokenů, míra úspěšnosti |
| **Graf denního vývoje**           | Náklady a tokeny za den, skládané podle modelu                                  |
| **Teplotní mapa aktivity**        | Mřížka hodina dne × den v týdnu, barva = počet požadavků                        |
| **Rozdělení podle modelu**        | Výsečový graf nákladů podle modelu                                              |
| **Rozdělení podle poskytovatele** | Sloupcový graf požadavků podle poskytovatele                                    |
| **Nejvýznamnější klíče API**      | Tabulka 10 klíčů s nejvyššími náklady                                           |
| **Analýza chyb**                  | Míra chybovosti v čase, nejčastější třídy chyb                                  |

### Programový přístup

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // záznamy historie využití
  "7d",                 // časový rozsah: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // mapa připojení poskytovatelů (connectionId → název účtu)
  {
    startDate: "2025-01-01",  // volitelné: pro rozsah "custom"
    endDate: "2025-06-01",   // volitelné: pro rozsah "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (centy)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Vynucování kvót

Kvóta pro jednotlivé klíče API se vynucuje na dvou místech:

1. **Měkký limit** (`quotaWarnAt`): upozornění v přehledu, když využití překročí prahovou hodnotu
2. **Tvrdý limit** (`quotaLimit`): při překročení je požadavek odmítnut se stavem HTTP 429

### Konfigurace

```ts
// Pro jednotlivý klíč API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — zobrazit upozornění
  quotaLimit: 10_00,    // $10.00 — úplné zastavení
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Průběh vynucování

```
Požadavek ──▶ quotaCheck()
              │
              ├── V rámci limitu?  ──▶ povolit
              │
              └── Nad limitem?  ──▶ 429 Too Many Requests
                                   s hlavičkou Retry-After
```

### Snímky kvót

Tabulka `quotaSnapshots` ukládá **historický stav kvót** pro analýzu trendů:

| Pole | Popis |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Sledovaný klíč |
| `window` | "day" | "week" | "month" |
| `used` | Náklady za toto období (centy) |
| `limit` | Limit (centy) |
| `resetAt` | Kdy se období obnoví |
| `createdAt` | Kdy byl snímek pořízen |

Snímky se pořizují **při každém požadavku**, jehož náklady jsou > 0, a slouží k těmto účelům:

- Vykreslení ukazatele čerpání kvóty v přehledu
- Zobrazení grafů vývoje kvót za 30 dní
- Spouštění upozornění, když se využití blíží limitu

### Dotazování na analytiku využití

K datům o využití se přistupuje prostřednictvím řídicího panelu nebo nástrojů MCP, nikoli přímo přes exportní endpointy REST. Dostupná analytika:

## Uchovávání a čištění dat

Objem dat o využití roste přibližně o 1–10 KB na požadavek. Při velkém provozu to může být významné.

### Nastavení doby uchovávání

Doba uchovávání historie využití se nastavuje v Nastavení databáze v uživatelském rozhraní nebo prostřednictvím `/api/settings/database`.

Ve výchozím nastavení se historie využití uchovává po dobu **90 dnů**.

### Čištění

Staré záznamy odstraňuje `src/lib/db/cleanup.ts`:

- Spouští se procesem cron na pozadí
- Odstraňuje záznamy z `usage_history` starší než doba uchovávání nakonfigurovaná v nastavení `usageHistory`

### Odhad potřebného úložiště

| Počet požadavků       | Úložiště na 30 dnů | Úložiště na 90 dnů |
| --------------------- | ------------------ | ------------------ |
| 100 požadavků/den     | ~3MB               | ~9MB               |
| 1 000 požadavků/den   | ~30MB              | ~90MB              |
| 10 000 požadavků/den  | ~300MB             | ~900MB             |
| 100 000 požadavků/den | ~3GB               | ~9GB               |

Při velmi vysokém provozu zvažte:

- Zkrácení doby uchovávání v Nastavení databáze
- Použití `aggregated_metrics` místo nezpracovaných záznamů (pouze pro analytiku)

## Tipy pro optimalizaci nákladů

### 1. Používejte vhodný model

```bash
# Rychlá odpověď — použijte levný a rychlý model
curl -d '{"model":"auto/fast","messages":[...]}'

# Složitý úkol — použijte kvalitní model
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Povolte ukládání do mezipaměti

Ukládání promptů do mezipaměti od Anthropic šetří **90 % nákladů na opakovaný kontext**:

```ts
// Ukládání do mezipaměti je automatické — stačí zahrnout stejný rozsáhlý systémový prompt
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Automaticky se uloží do mezipaměti
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Používejte kompresi

Komprese RTK + Caveman šetří **15–95 % nákladů v relacích s intenzivním využitím nástrojů**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Nastavte kvóty pro jednotlivé klíče

Vždy nastavte `quotaLimit`, abyste zabránili nekontrolovanému růstu nákladů:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Limit 10 $ měsíčně
```

### 5. Prověřujte největší spotřebitele

Pomocí ovládacího panelu nebo **`/api/usage/analytics`** seskupte údaje podle klíče API a seřaďte je podle nákladů:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Řešení problémů

### „Náklady jsou vyšší, než se očekávalo“

1. Zkontrolujte **`/api/usage/analytics?groupBy=model`** — najděte nákladný model
2. Zkontrolujte **`/api/usage/analytics?groupBy=apiKey`** — najděte největšího spotřebitele
3. Ověřte aktuálnost cenových údajů: `POST /api/pricing/sync`

### „Chybějící záznamy“

- Zkontrolujte nastavení uchovávání dat v databázi v části Ovládací panel → Databáze → Čištění — staré záznamy odstraňuje pravidelná úloha čištění (`src/lib/db/cleanup.ts`)
- Zkontrolujte chyby v `src/lib/db/usage*.ts` — selhání zápisu do databáze se zaznamenávají do protokolu, ale nezobrazují se uživateli
- Ověřte, že požadavek skutečně dorazil do `chatCore` — zkontrolujte směrování kombinací

### „Kvóta se nevynucuje“

- Zkontrolujte nastavení `quotaLimit` daného klíče
- Ověřte, že je `quotaWindow` správně nastaveno
- Vyhledejte záznamy `quotaSnapshots` — měly by se vytvářet při každém požadavku
