## Přehled

Všechny trasy API pro správu OmniRoute jsou zařazeny do jedné ze tří úrovní
ochrany. Klasifikace je statická, je definována v `src/server/authz/routeGuard.ts`
a vyhodnocuje se před spuštěním jakékoli jiné větve ověřování.

## Úrovně

### Úroveň 1 — LOCAL_ONLY

**Vynuceno pomocí:** `isLocalOnlyPath(path)` → kontrola hostitele loopbacku  
**Obejití:** Ve výchozím nastavení žádné. Úzce vymezená výjimka pro cesty v
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, pokud požadavek obsahuje platný
API klíč s rozsahem `manage` (viz [Výjimka pro rozsah manage](#manage-scope-carve-out)).

Tyto trasy spouštějí podřízené procesy nebo vykonávají kód za běhu. Jejich
zpřístupnění provozu mimo loopback by útočníkovi, který získal platný JWT (např.
prostřednictvím tunelu Cloudflared/Ngrok), umožnilo spouštět procesy — známou
třídu zranitelností CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Co je GHSA-fhh6-4qxv-rpqj (třída útoku):** server pro správu/agenta
zpřístupňuje koncový bod, který spouští podproces (`npm install`, `node`, prohlížeč,
proxy, `git`, `tar`, …). Pokud je tento koncový bod dostupný mimo hostitele — protože
provozovatel umístil OmniRoute za tunel nginx/Cloudflare/Tailscale a došlo k úniku
JWT nebo bylo nesprávně nakonfigurováno ověřování — útočník změní „volání API“ na
„spuštění příkazu na hostiteli“ (vzdálené spuštění kódu). OmniRoute tomu zabraňuje
tím, že na každé trase schopné spouštět procesy **bezpodmínečně vynucuje kontrolu
hostitele loopbacku ještě před jakoukoli kontrolou ověřování**: uniklý token se
ani přes tunel ke spuštění procesu nedostane.

**Úplná sada LOCAL_ONLY.** Autoritativním zdrojem jsou
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` v
`src/server/authz/routeGuard.ts`; níže uvedená tabulka odráží aktuální stav.
Kontrola `check-route-guard-membership` prochází každý soubor `route.ts` pod
prefixy umožňujícími spouštění procesů a způsobí selhání CI, pokud některý z nich
není klasifikován jako pouze lokální.

#### Výjimka pro rozsah správy

K podmnožině cest LOCAL_ONLY LZE přistupovat také mimo rozhraní loopback, právě
když požadavek obsahuje `Authorization: Bearer <api-key>`, jehož
metadata zahrnují rozsah `manage` (nebo `admin`). Výjimka je explicitně
povolena pro jednotlivé cesty prostřednictvím `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, takže
výchozím nastavením každé nové cesty LOCAL_ONLY zůstává striktní omezení na loopback. Neověřené
požadavky a požadavky s klíči bez oprávnění ke správě jsou nadále odmítány odpovědí
`403 LOCAL_ONLY`.

V současnosti je jediným prefixem, pro který lze výjimku použít, `/api/mcp/`. `/api/cli-tools/runtime/` a
`/api/services/` jsou záměrně vyloučeny, protože mohou spouštět libovolné
podprocesy (`npm install`, `node`), což je přesně třída CVE, které má
úroveň LOCAL_ONLY zabránit.

**#7895 — úzký rozsah `mcp:connect`:** výjimka pro `/api/mcp/` TAKÉ přijímá
klíč Bearer s úzkým rozsahem `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), který se ověřuje pomocí
`hasMcpConnectOrManageScope()` v `src/server/authz/policies/management.ts`.
Toto oprávnění je omezeno POUZE na `/api/mcp/` — `mcp:connect` neposkytuje žádná oprávnění pro žádnou jinou
trasu správy (včetně všech ostatních prefixů s výjimkou LOCAL_ONLY, pokud by někdy
byly přidány) a je záměrně vyloučeno z
`MANAGEMENT_API_KEY_SCOPES`. Klíč s rozsahem `manage`/`admin` nadále
projde touto výjimkou přesně jako dříve; `mcp:connect` je alternativou s nižšími oprávněními
pro vzdálené volající používající pouze MCP, kteří by neměli potřebovat široký přístup ke správě.

| Požadavek                                                | Cesta                      | Výsledek                  |
| -------------------------------------------------------- | -------------------------- | ------------------------- |
| Mimo loopback, bez Bearer                                | `/api/mcp/*`               | 403 LOCAL_ONLY            |
| Mimo loopback, Bearer s rozsahem `manage`                | `/api/mcp/*`               | Povolit                   |
| Mimo loopback, Bearer s rozsahem `mcp:connect`           | `/api/mcp/*`               | Povolit                   |
| Mimo loopback, Bearer bez rozsahu `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY            |
| Mimo loopback, Bearer s rozsahem `mcp:connect`           | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY            |
| Mimo loopback, Bearer s rozsahem `manage`                | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY            |
| Loopback, s libovolným/žádným Bearer                     | libovolná cesta LOCAL_ONLY | Povolit (kontrola prošla) |

#### Pokyny pro provozovatele a auditování

Pokud provozujete OmniRoute za reverzním proxy serverem nebo tunelem (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), kontrola loopback nadále chrání výše uvedené trasy,
které mohou spouštět procesy — požadavek, jehož adresa klienta není loopback, je odmítnut odpovědí
`403 LOCAL_ONLY` **před spuštěním ověřování**, takže uniklý JWT nemůže spustit proces. Provozovateli
nadále zůstávají dvě povinnosti:

- **„Neopravujte“ chybu 403 podvržením IP adresy klienta jako loopback.** Nastavení
  `X-Forwarded-For: 127.0.0.1` nebo proxy, která přepisuje zdrojovou adresu na
  loopback, znovu zpřístupní přesně tu třídu RCE, kterou tato úroveň blokuje. Přes
  proxy zpřístupněte dashboard/API — nikdy ne trasy schopné spouštět procesy.
- **Udržujte obcházení pomocí oprávnění manage minimální.** Ochranu lze obejít pouze pro `/api/mcp/`,
  a to pouze pomocí API klíče s oprávněním `manage`. Položky `SPAWN_CAPABLE_PREFIXES` nelze nikdy
  přidat do seznamu výjimek — schéma zod je odmítne a
  `isLocalOnlyBypassableByManageScope` je zakáže za běhu (vícevrstvá ochrana),
  což je to, co dashboard označuje jako „nelze povolit obejití“. Stejný
  seznam zákazů obsahuje také několik tras LOCAL_ONLY, které sice nespouštějí procesy, ale rovněž
  nesmí být nikdy vzdáleně dostupné — `/api/oauth/kiro/auto-import` (čte lokální
  soubory přihlašovacích údajů Kiro na hostiteli), `/api/discovery/` a `/api/issue-agent/`. Zavaděč
  snímku běhového prostředí také takové položky odstraní z uloženého řádku nastavení a
  starší import JSON (`/api/settings/import-json`) klíče pro obcházení ochrany nikdy nezapisuje.
  Každá položka `LOCAL_ONLY_API_PREFIXES` musí být buď v seznamu zákazů, nebo
  posouzena jako způsobilá k obejití (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Trasy
  schopné spouštět procesy s dynamickými segmenty a statickými cestami pod `/api/providers/`
  (např. `/login`, `/refresh-cursor`) pokrývá doprovodná dvojice založená na regulárních výrazech
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` v
  `src/shared/constants/spawnCapablePrefixes.ts`, nikoli ploché pole
  `SPAWN_CAPABLE_PREFIXES` — ploché pole by je zachytilo pouze tehdy, pokud by pokrývalo
  celý prefix `/api/providers/`, což by příliš rozšířilo omezení stromu tras,
  který vzdálené dashboardy legitimně používají ke CRUD operacím s poskytovateli.

**Auditování přístupu** — chcete-li ověřit, že se k těmto trasám nic mimo hostitele nedostává:

- Otevřete **Inventář autorizací** na `/dashboard/settings/security`: zobrazuje
  aktuální seznam prefixů LOCAL_ONLY, prefixy, u kterých lze ochranu obejít, a sadu
  tras schopných spouštět procesy určenou při kompilaci („nelze povolit obejití“).
- Prohledejte logy reverzní proxy / přístupové logy a vyhledejte výše uvedené prefixy
  spárované s klientskou adresou, která není loopback. Jakýkoli takový požadavek, který vrátil `200`
  namísto `403 LOCAL_ONLY`, znamená, že proxy maskuje skutečnou IP adresu klienta — opravte proxy.
- Záznam `403 LOCAL_ONLY` v logách OmniRoute pro jednu z těchto cest znamená, že ochrana
  funguje správně, nikoli chybu, kterou je třeba potlačit.

#### Vzdáleně dostupné trasy s kontrolní bránou v místě volání

Některé trasy musí zůstat dostupné ze vzdáleného dashboardu, ale pro místní volající
spouštějí kontrolu na straně hostitele (`which <binary>`, `<binary> --version`, `tailscale status --json`).
Pro `GET` nejsou LOCAL_ONLY; obslužná rutina místo toho načte důvěryhodné vyhodnocení protistrany
pomocí `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) a kontrolu spustí
pouze pro volající typu `loopback` / `lan`. Volající typu `remote` obdrží stejnou strukturu odpovědi sestavenou
ze zdrojů, které nespouštějí procesy (trvalý stav, nastavení, kontroly souborového systému), označenou `probed: false`.

| Trasa                                                            | Kontrola přeskočená pro vzdálené volající                                         |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | Kontrola běhového prostředí CLI (`allowLocalRuntimeProbe`) a záložní spuštění CLI |
| `GET /api/headroom/status`                                       | `which headroom` a kontroly pythonu pomocí `--version`                            |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`                 |
| `GET /api/tunnels/cloudflared` (výjimka z LOCAL_ONLY pro GET)    | Vyhledání `which cloudflared` v PATH                                              |

Nová trasa pro čtení, která kontroluje hostitele, používá stejný vzor, nebo je přímo
klasifikována jako LOCAL_ONLY.

### Úroveň 2 — ALWAYS_PROTECTED

**Vynucováno pomocí:** `isAlwaysProtectedPath(path)` → přeskočení obejití přes `requireLogin=false`
**Obejití:** Žádné, když `requireLogin=false`; JWT je vyžadován vždy

Tyto trasy provádějí destruktivní nebo nevratné operace. Jejich povolení v instalaci
„bez hesla“ by znamenalo, že kdokoli ve stejné síti LAN může vymazat databázi nebo ukončit
serverový proces.

| Cesta                                     | Důvod                                                                            |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Ukončí serverový proces                                                          |
| `/api/settings/database`                  | Export, import a vymazání databáze                                               |
| `/api/db-backups`                         | Přístup k úplnému archivu zálohy databáze                                        |
| `/api/settings/export-json`               | Exportuje celý objekt nastavení (vč. tajných údajů)                              |
| `/api/settings/import-json`               | Nahradí celý objekt nastavení                                                    |
| `/api/providers/health-autopilot/actions` | Provádí nápravné akce autopilota                                                 |
| `/api/settings/obsidian`                  | Vydává opakovaně použitelné přihlašovací údaje WebDAV pro libovolný kořen vaultu |
| `/api/relay/tokens`                       | Mints, lists, edits and revokes relay tokens                                     |

**Odpověď při porušení:** `401 Authentication required`

`/api/settings/obsidian` pokrývá svou podřízenou cestu `/webdav`: `POST` nasměruje souborovou službu WebDAV —
obsluhovanou vlastní vrstvou Node před Next.js, mimo tento řetězec zpracování — na kořen zvolený volajícím
a vrátí nově vydané přihlašovací údaje Basic, `DELETE` je obmění a nadřazený požadavek `POST` uloží
token REST API služby Obsidian. GHSA-62vw pouze skryla odhalení hesla prostřednictvím `GET`; jeho vydávání
stále zůstávalo na úrovni, která při selhání povolovala přístup (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` navíc
odmítne vault, který je datovým adresářem, nachází se v něm nebo jej obsahuje.

#### Export přihlašovacích údajů je určen pouze pro operátory

Výše uvedená úroveň pouze rozhoduje, zda je vyžadován _nějaký_ přihlašovací údaj. Trasy, které stahují
uložené přihlašovací údaje, provádějí v obslužné rutině druhou kontrolu: `GET /api/settings/export-json` (dešifrovaná
připojení k poskytovatelům a nezpracované klíče API), `GET /api/db-backups/export` (soubor SQLite) a
`GET /api/db-backups/exportAll` (úplný archiv) volají `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). Tato funkce přijímá relaci řídicího panelu, lokální subjekt CLI nebo
instanci s vypnutým přihlašováním a vrací odpověď `403` pro klíče API libovolného rozsahu (včetně `manage`
a `admin`) a pro přístupové tokeny `oma_`. Vydávání synchronizačních tokenů (`POST /api/sync/tokens`) používá
stejnou pomocnou funkci a navíc důvěryhodný token interní služby přes zpětnou smyčku.

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### Inicializační zavedení po nové instalaci je dostupné pouze přes zpětnou smyčku — podle skutečného protějšku, nikoli podle `Host`

Pokud není nakonfigurováno žádné heslo pro správu (ani `INITIAL_PASSWORD`), funkce `isAuthRequired()` v
`src/shared/utils/apiAuth.ts` ponechá anonymní inicializační zavedení přístupné **pouze protějškům na zpětné smyčce**.
Zpětná smyčka se určuje z důvěryhodných signálů protějšku v tomto pořadí: tokenem označený skutečný protějšek TCP
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, který vidí zásady), rozhodnutí vlastního kanálu
`AUTHZ_HEADER_PEER_LOCALITY` (které vidí obslužné rutiny tras a kterému se důvěřuje pouze tehdy, když je nastaven
`OMNIROUTE_PEER_STAMP_TOKEN`) nebo skutečný protějšek soketu u přímých volajících. `Host` /
`nextUrl.hostname` se nikdy nekontrolují a první nastavení hesla
(`POST /api/settings/require-login`) podléhá stejnému omezení, namísto aby bylo přístupné každému
síťovému protějšku (GHSA-7pq4-8pvv-rx7r). `managementPolicy` explicitně předává své vlastní rozhodnutí
`peerContext`, takže o něm nikdy nerozhodují hlavičky PŮVODNÍHO požadavku (před jejich odebráním).

### Úroveň 3 — SPRÁVA (výchozí)

Všechny ostatní trasy pro správu. Ověření je vyžadováno, pokud není nakonfigurováno
`requireLogin=false`. Tokeny CLI mohou tyto trasy ověřovat (zpětná smyčka + platný HMAC).

## Pořadí vyhodnocování

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → pokračovat
     → non-loopback, Bearer s rozsahem manage
        AND isLocalOnlyBypassableByManageScope   → povolit (management_key)
     → jinak                                     → zamítnout 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → povolit (system)
  3. hasValidCliToken(headers)?
     → povolit (cli) [loopback + kontrola HMAC pomocí timingSafeEqual]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → povolit (dashboard_session)
     → Bearer s rozsahem manage na cestě bez možnosti obejití?
        → povolit (management_key)
     → zamítnout 401/403
  5. requireLogin=false?
     → povolit (anonymous)
```

Větev s rozsahem manage v kroku 1 je jedinou autentizovanou cestou, která může splnit
požadavky trasy LOCAL_ONLY; režim selhání autentizačního backendu vrací 503 (nikoli 403), takže
expirovaná DB se tiše nepřepne na „zamítnout“.

## Přidání nové trasy umožňující spouštění

1. Přidejte prefix cesty do `LOCAL_ONLY_API_PREFIXES` v
   `src/server/authz/routeGuard.ts`
2. Přidejte test do `tests/unit/authz/routeGuard.test.ts`, který ověří, že
   `isLocalOnlyPath()` vrací pro nový prefix hodnotu true
3. **Tento krok nikdy nevynechávejte** — viz Pevné pravidlo č. 15 v `CLAUDE.md`
4. Rozhodněte: patří tato trasa TAKÉ do `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Výchozí odpověď je **ne**. Povolte ji pouze tehdy, když je bezpečné trasu zpřístupnit
   držiteli rozsahu manage (tj. NESPOUŠTÍ libovolný uživatelem řízený kód).

## Přidání cesty, kterou lze obejít pomocí rozsahu manage

1. Ověřte, že trasa nespouští kód ani příkazy dodané uživatelem. Pokud je
   spouští, zastavte se — tato výjimka není správným nástrojem.
2. Přidejte prefix do `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` v
   `src/server/authz/routeGuard.ts`
3. Přidejte pokrytí do `tests/unit/authz/management-policy.test.ts` pro všechny čtyři
   podoby požadavku: bez Bearer (403), Bearer s rozsahem manage (povolit), Bearer bez rozsahu manage
   (403) a regresní test pro každý prefix, který ověří, že `/api/cli-tools/runtime/*` zůstává
   omezeno výhradně na loopback i s Bearer s rozsahem manage.

## Dokumentování úrovní zabezpečení v OpenAPI

Při přidávání nové trasy do `docs/openapi.yaml` použijte odpovídající
rozšíření dodavatele, pokud je trasa klasifikována souborem `routeGuard.ts`:

| Klasifikace v routeGuard.ts              | Anotace YAML               | Vynucení                                                |
| ---------------------------------------- | -------------------------- | ------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                | `x-loopback-only: true`    | Bezpodmínečně blokováno mimo loopback                   |
| `ALWAYS_PROTECTED_API_PATHS`             | `x-always-protected: true` | Autentizace je vyžadována i při `requireLogin=false`    |
| Interní trasa admin/debug                | `x-internal: true`         | Ve výchozím nastavení skryto v /dashboard/api-endpoints |
| Žádná (veřejná / standardní autentizace) | (anotace není potřeba)     | Standardní přístup řízený pomocí `requireLogin`         |

### Validace

Konzistenci mezi anotacemi YAML a `routeGuard.ts` vynucují dva skripty:

- `scripts/check/check-openapi-coverage.mjs` — selže, pokud je pokrytí < 99 %
- `scripts/check/check-openapi-security-tiers.mjs` — selže, pokud se anotace `x-loopback-only` nebo
  `x-always-protected` liší od konstant definovaných při kompilaci

Oba skripty se spouštějí v pre-commit hooku a v CI.

### Pravidlo pro falešně pozitivní nálezy

Pokud je `x-always-protected` nebo `x-loopback-only` uvedeno u trasy, která NENÍ v
konstantě v `routeGuard.ts`, skript kontroly pokrytí selže. Správným řešením je vždy sjednotit
YAML s tím, co `routeGuard.ts` skutečně vynucuje — nikoli přidávat trasy do `routeGuard.ts`,
aniž by byla zároveň implementována logika jejich vynucení.
