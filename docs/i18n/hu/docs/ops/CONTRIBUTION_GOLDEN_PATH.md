Használja ezt az útmutatót, hogy kiválassza a legkisebb megbízható fejlesztési ciklust egy pull requesthez. Ez nem
helyettesíti az alább hivatkozott, területspecifikus architekturális és biztonsági dokumentumokat; minden gyakori
módosítástípust összekapcsol a hozzá tartozó szerződésekkel, célzott ellenőrzésekkel és CI-lefedettséggel.

## Az útvonal, amelyet minden módosítás követ

1. **Szerkesztés előtt válassza ki az alapágat.** Keresse meg a legmagasabb verziójú aktív `release/v*` ágat, és annak
   csúcsából hozzon létre új ágat. Ezt az ágat célozza meg, ne a `main` ágat. Ha kiadási befagyasztás van érvényben, ne a befagyasztott
   ágat célozza; használja a
   [Branching & Release Model](BRANCHING_MODEL.md) dokumentumban leírt következő aktív ciklust.
2. **Nevezze meg a szerződéseket.** Azonosítson minden katalógust, sémát, generált összetevőt, nyilvános API-t vagy felhasználói
   felületet, amelyet a módosítás érint. Az alábbi táblázat megadja a minimális kiindulási készletet.
3. **Írjon vagy frissítsen célzott teszteket.** A `src/`, `open-sse/`, `electron/` vagy
   `bin/` alatti éles kód módosításaihoz ugyanabban a PR-ben automatizált teszt szükséges. Futtassa a legkisebb tesztfájlkészletet, amely igazolja
   a működést, majd a felsorolt célzott ellenőrzéseket.
4. **A széles körű mátrixot futtassa a CI.** A teljes egységteszt-szegmensek, a Vitest, a lefedettségi küszöb és az
   éles build a PR-en fut. Széles körű tesztcsomagot helyben csak akkor futtasson, ha egy célzott hiba
   szélesebb körű hatásra utal, vagy ha a módosítás több alrendszert érint.
5. **A felülvizsgálat előtt egyeztesse a módosításokat.** Kérje le az aktív alapágat, vizsgálja meg annak új commitjait és az ahhoz viszonyított
   saját diffjét, majd a közreműködői munkafolyamatnak megfelelően végezzen rebase-t, vagy merge-ölje az alapágat. A generált fájlokkal
   és katalógusokkal kapcsolatos ütközéseket a forrásuknál oldja fel, generálja újra őket, futtassa újra a célzott ciklust, és erősítse meg, hogy a
   PR továbbra is az aktív kiadási ágat célozza.
6. **Rögzítse a bizonyítékokat.** A PR-sablonban sorolja fel a futtatott parancsokat, minden hozzáadott vagy módosított tesztfájlt,
   a migrációkat vagy funkciójelzőket, valamint minden még függőben lévő, csak CI-ben végrehajtható ellenőrzést.

## Bevált eljárások módosítástípusonként

Az alábbi parancsok a minimális célzott ellenőrzések; nem jelentenek engedélyt az Ön által módosított
működést közvetlenül lefedő teszt kihagyására.

### Szolgáltató

**Szerződések**

- A szolgáltató definíciója a `src/shared/constants/providers/` alatt, valamint annak összeállítása a
  `src/shared/constants/providers.ts` fájlban.
- Modellek és képességek az `open-sse/config/providerRegistry.ts` fájlban vagy annak különálló rendszerleíró fájljaiban.
- Végrehajtó-/fordítóválasztás, OAuth- vagy API-kulcs-konfiguráció, vezérlőpulti elemek és adott esetben a generált
  szolgáltatói referencia.
- A nyilvános hitelesítő adatoknak a `resolvePublicCred()` függvényt kell használniuk; a hibaválaszoknak a megosztott, megtisztított
  hibakezelő segédfüggvényeket kell használniuk. Lásd: `docs/security/PUBLIC_CREDS.md` (git; nincs beépítve a `/docs` könyvtárba) és
  [Hibák megtisztítása](../security/ERROR_SANITIZATION.md).

**Célzott ciklus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # amikor a katalógus módosul; commitolja a generált diffet
npm run lint
```

Teszteljen minden érintett kéréstípust is: chat, Responses, képek, beágyazások, hang vagy videó.
A generált katalógus- és golden diffeket szerződésmódosításként vizsgálja felül; ne fogadja el őket vakon.

### Útválasztás

**Szerződések**

- Nyilvános stratégiaértékek és felhasználóifelület-metaadatok a `src/shared/constants/routingStrategies.ts` fájlban.
- Elosztás és sorrendezés az `open-sse/services/combo.ts` fájlban és az `open-sse/services/combo/` alatt.
- Combo-sémák, perzisztencia, rezilienciaállapot, modellképességek, valamint API-/felhasználóifelület-vezérlők.
- Az [Auto-Combo Engine](../routing/AUTO-COMBO.md) és a rezilienciadokumentáció, amikor a működés módosul.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # stratégia- vagy elosztásmódosítások
npm run check:known-symbols      # a stratégia regisztrációjának módosításai
npm run lint
```

Helyben determinisztikus, mockolt upstreamet használó teszteket alkalmazzon. Az élő combo füsttesztek hitelesítő adatokat igényelnek, és
manuálisak; nem helyettesítik a CI-t.

### UI / UX

**Szerződések**

- Next.js-útvonalak/-oldalak és megosztott komponenshatárok a `src/app/` és
  `src/shared/components/` alatt.
- API-válaszformák, betöltési/üres/hibaállapotok, billentyűzetes és képernyőolvasós működés,
  reszponzív elrendezés, témakezelés és területi beállítások bővítése.
- Angol felhasználóifelület-forrásszövegek a `src/i18n/messages/en.json` fájlban; ne kódoljon közvetlenül új, felhasználóknak szóló szöveget.

**Célzott ciklus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interakciós vagy vizuális módosítások esetén futtassa az alkalmazást, és ellenőrizze keskeny és széles nézetablakban egyaránt. A CI futtatja az
éles buildet és a szélesebb körű tesztcsomagokat; a vizuális működéshez továbbra is szükség van a módosításnak megfelelő célzott komponens- vagy Playwright-tesztre,
illetve dokumentált manuális ellenőrzésre.

### i18n

**Szerződések**

- A `src/i18n/messages/en.json` a felhasználói felület forrása; a `config/i18n.json` a területi beállítások forrása.
- A CLI-katalógusok külön, a `bin/cli/locales/` alatt találhatók.
- Az ICU-helyőrzőket és -címkéket pontosan őrizze meg. Ne fordítsa le a termék-/szolgáltató-/modellneveket,
  a protokoll- és fejlécneveket, a parancsokat, a kód-/JSON-azonosítókat, az URL-eket, a környezeti változókat vagy
  az olyan védett kifejezéseket, mint az `OmniRoute`, `OAuth`, `MCP` és `A2A`. Az aktuális forráslista:
  `scripts/i18n/glossary/protected-terms.json`.

**Célzott ciklus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # amikor a CLI-szövegek/-katalógusok módosulnak
npm run lint
```

Ez a meglévő rendszerhez nyújt útmutatást, nem pedig felhívás az eszközkészlet vagy a kulcsmodell bővítésére.
Amíg a helyettesítő rendszert tervezik, az i18n-javításokat tartsa célzottnak és minimálisnak. Ne futtasson külső szolgáltatásokat
hívó fordítási parancsokat, kivéve, ha a feladat kifejezetten generált fordításokat igényel, és Ön
áttekintette az így létrejött diffet.

### CLI

**Szerződések**

- Nyilvános parancsok és kapcsolók a `bin/cli/` könyvtárban, generált API-parancsok, kilépési kódok, stdout/stderr és
  JSON-kimeneti struktúrák, konfigurációs/környezeti viselkedés, valamint a csomagolt fájlok.
- A CLI felhasználóknak szánt szövegeinek a CLI i18n rétegét kell használniuk, az `en`/`pt-BR` katalógusokat pedig szinkronban kell tartani.
- Őrizd meg a Node-ot támogatott futtatókörnyezetként, valamint a közzétett bináris szerződést.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generált/csomagolt CLI-módosítások
npm run check:pack-policy     # a csomag publikus felületének módosításai
npm run lint
```

Ha a viselkedés az értelmezéstől, fájloktól vagy a kilépési állapottól függ, használd a pontos parancsot egy ideiglenes adatkönyvtárban. A CI végzi el a csomagtermékek és az ökoszisztéma átfogóbb ellenőrzéseit.

### Adatbázis

**Szerződések**

- Tartománymodulok a `src/lib/db/` alatt; közvetlenül az adott modulokat importáld (a régi `localDb.ts` újraexportálási réteg el lett távolítva).
- Számozott, idempotens SQL-migrációk a `src/lib/db/migrations/` alatt, tranzakcióbiztonság, frissítési
  viselkedés, indexek, valamint a séma által érintett összes hívó.
- Az útvonalak és kezelők soha nem hajtanak végre közvetlenül nyers SQL-t.

**Célzott ciklus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migráció hozzáadásakor tesztelj új adatbázissal és az előző sémáról történő frissítéssel is. Az adatbázisteszteknek a takarítás során le kell zárniuk a leírókat, és meg kell hívniuk a `resetDbInstance()` függvényt. Az `npm run test:bun:db` parancsot csak akkor futtasd, ha a legjobb szándék szerint támogatott Bun-adapter útvonala változik; továbbra is a Node a mérvadó.

### Build / telepítés

**Szerződések**

- Gyökér- és munkaterületi manifestek/zárolási fájl, `scripts/build/`, Next.js önálló összeállítás, a `dist/`
  csomag tartalma, Electron-platformmetaadatok, CI-munkafolyamatok és telepítési jelzők.
- A támogatott Node-verziótartományoknak és a Bun `CLAUDE.md` fájlban engedélyezési listán szereplő használatának változatlanul meg kell maradnia.
- A buildtermékek nem kerülhetnek verziókövetés alá; a függőségi, licencelési, munkafolyamat- és csomagszabályzatok érvényesek.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # függőség- vagy zárolásifájl-módosítások
npm run check:pack-policy      # a közzétett csomag felületének módosításai
npm run lint
```

Az `npm run build` parancsot helyben csak akkor használd, ha a módosítás érinti a fordítást, az önálló összeállítást, az erőforrásokat vagy a futásidejű csomagolást. Az `npm run build:release` parancsot csak kiadási/telepítési ellenőrzéshez használd. A CI buildje a végső, platformokon átívelő visszajelzés; a platformspecifikus Electron-módosításokhoz a megfelelő célzott build vagy füstteszt bizonyítéka szükséges.

## Fejlesztői szkriptek megosztott géphez

Két `scripts/dev/` segéd valósítja meg a helyi munkafolyamatot olyan fejlesztői gépen, ahol más munkamenetek is aktívak:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # fájlok a merge-base(HEAD, base)..HEAD tartományból
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # pontosan ezek a fájlok
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # elkülönített worktree, párhuzamosan is biztonságos
```

- A `typecheck-touched.sh` csak a módosított `.ts/.tsx` fájlokon végez típusellenőrzést egy ideiglenes
  `tsconfig.touched.tmp.json` használatával (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`), 6 GB-os heap mellett, így kiváltja a teljes projektre kiterjedő `tsc -p tsconfig.json`
  parancsot, amely egy terhelt gépen memóriahiány miatt leáll. Kiírja a módosított fájlok hibáit és egy összegző sort, majd
  `1` kilépési kóddal áll le, ha a módosított fájlokban vannak hibák; `2` kóddal, ha csak az importált fájlokban vannak hibák, vagy a tsc
  diagnosztika nélkül leállt (olvassa el az `_artifacts/typecheck-touched/` alatt megnevezett naplót); és `0` kóddal, ha
  nincs hiba. Az ideiglenes tsconfig mindig törlődik; soha ne commitolja.
- A `new-worktree.sh` sorosítja az egyidejű futtatásokat a `<git-common-dir>/omniroute-new-worktree.lock`
  zárolással (alapértelmezés szerint legfeljebb 600 másodpercig vár, látható üzenettel; a szkript fejléce dokumentálja a
  felülbírálási lehetőséget), és visszagörgeti
  az általa létrehozott branchet, ha a `git worktree add` még a worktree létrejötte előtt meghiúsul, így az újrapróbálkozáshoz
  nincs szükség kézi `git branch -D` parancsra. A hard linkelt `node_modules` és a `.husky/_` másolata változatlan marad.

## Helyi candidate-munkafolyamat

A forrástesztek nem tudják bizonyítani, hogy a csomagolt artifact elindul: a csomagolási listák, a ritkított függőségek
és a natív binárisok hibái csak a tarball telepítése és elindítása után jelentkeznek. Az `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) az RFC #8084 szerinti egyszeri buildelés / validálás / előléptetés folyamat
helyi oldala: létrehoz egy candidate-et, pontosan ezt az artifactot validálja, könyvtár-átnevezésekkel
előlépteti, és visszagörgeti, ha az előléptetett slot állapotellenőrzése meghiúsul.

```bash
npm run dev:candidate -- run --dry-run --json  # a terv kiírása módosítás nélkül
npm run dev:candidate -- run                   # buildelés + validálás + előléptetés, automatikus visszagörgetés
npm run dev:candidate -- build                 # npm pack + telepítés az _artifacts/candidate/<id>/ könyvtárba
npm run dev:candidate -- validate --id <id>    # indítás egy szabad porton, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # a current és a previous felcserélése
npm run dev:candidate -- run --from-tarball <file.tgz>  # máshol (CI-ben) létrehozott tarball újrafelhasználása
```

- **Egyszer buildelje.** A `build` becsomagolja az aktuális fát (ehhez szükséges a `dist/server.js`, ezért előbb futtassa az
  `npm run build:release` parancsot), vagy bemásolja a `--from-tarball` által megadott fájlt, majd egy
  elkülönített npm prefixbe telepíti a tarballt, mert a tarball nem tartalmaz `node_modules` könyvtárat. Az id a rövid `HEAD`
  sha (`-dirty` utótaggal, ha a fában helyi módosítások vannak), tarball esetén pedig `tgz-<sha256>`. A már
  buildelt, tiszta id újrafelhasználásra kerül az újbóli buildelés helyett; az újbóli buildeléshez adja meg a `--force` kapcsolót.
- **A csomagot validálja, ne a forrást.** A `validate` elindítja a telepített CLI-t
  (`serve --port <free port>`) egy friss `DATA_DIR=<candidate>/data` könyvtárral és hamis titkos értékekkel, miközben az
  operátor `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` és `INITIAL_PASSWORD` változóit eltávolítja a
  környezetből, így egy friss telepítés kulcs nélküli loopback-beállítását ellenőrzi. Megvárja, hogy a
  `GET /api/health` 200-as választ adjon, megköveteli, hogy a `GET /v1/models` is 200-as választ adjon, leállítja a folyamatcsoportot,
  és az eredményt a tarball hashével együtt a `validation.json` fájlban rögzíti.
- **Ugyanazt az artifactot léptesse elő.** A `promote` elutasítja az olyan candidate-et, amelynek
  aktuális tarball-hashéhez nem tartozik sikeres validálás. Az alapértelmezett aktív slot az `_artifacts/candidate/current`; a `--target <dir>`
  egy másik, ugyanazon a fájlrendszeren található könyvtárat választ ki, amelynek előző slotja `<dir>.previous`.
  Minden átnevezés atomi, és a folyamat közbeni hiba visszafordítja a már végrehajtott átnevezéseket.
- **Görgesse vissza.** A `run` ismét validálja az előléptetett slotot, és visszacseréli a `current` és a `previous` slotot, ha
  ez az ellenőrzés meghiúsul. Az első validáláson megbukó candidate soha nem kerül előléptetésre.

Minden a git által figyelmen kívül hagyott `_artifacts/candidate/` alatt jön létre; a meglévő OmniRoute-
telepítés és annak adatkönyvtára soha nem módosul. Az előléptetett CLI elérési útja:
`_artifacts/candidate/current/prefix/bin/omniroute`; használatakor saját `DATA_DIR` értékével indítsa el.
Kilépési kódok: `0` siker, `1` sikertelen validálás vagy előléptetés, `2` használati hiba vagy hiányzó build.

## Helyi ciklus kontra CI

| Futtatás helyben minden javításcsomaghoz                                                               | A CI biztosítja az átfogó visszajelzést                                           |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| A fenti közvetlen viselkedési tesztek és kategóriakapuk                                                | Részekre osztott teljes egységtesztcsomag és soros tesztek                        |
| `npm run lint`                                                                                         | Vitest tesztcsomagok és lefedettségi/minőségi szigorítások                        |
| Típusellenőrzés vagy buildelés csak akkor, ha az érintett szerződés megköveteli                        | Éles build, biztonsági, dokumentációs, függőségi és PR-szabályzati kapuk          |
| Manuális interakciós/élő ellenőrzések csak akkor, ha az automatizálás nem képes igazolni a viselkedést | A munkafolyamat által konfigurált feladatközi integrációs és platformellenőrzések |

A sikeres, célzott helyi ciklus bizonyítékot szolgáltat a módosított szerződésről, de nem igazolja, hogy a kapcsolódó változtatásoktól független CI-ellenőrzések
sikeresek lesznek. Ugyanakkor ne várakoztasson minden helyi módosítást a teljes repozitóriummátrix lefutására.

## Egyeztetési ellenőrzőlista

Felülvizsgálat kérése előtt:

- Győződjön meg arról, hogy a PR alapága továbbra is a legmagasabb aktív `release/v*` ág.
- Kérje le ezt az alapágat, és tekintse át az elágazás óta bekerült commitokat.
- Tekintse át a `git diff <active-base>...HEAD` kimenetét a véletlen vagy generált módosítások kiszűréséhez.
- A katalógus- és generáltdokumentum-ütközéseket a forrás frissítésével és a kimenet újbóli generálásával oldja fel.
- Az egyeztetés után futtasson újra minden, a PR leírásában felsorolt célzott tesztet/kaput.
- Soha ne gyengítse az elvárásokat, és ne hagyjon el kötelező teszteket pusztán azért, hogy igazodjon egy módosult alapághoz.

A kiadásbefagyasztási és újracélzási szabályokért tekintse meg az
[Elágazási és kiadási modellt](BRANCHING_MODEL.md). A CI-ellenőrzések teljes jegyzékéért tekintse meg a
[Minőségi kapuk referenciáját](../architecture/QUALITY_GATES.md).
