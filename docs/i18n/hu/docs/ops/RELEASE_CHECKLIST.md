## npm Trusted Publishing (alapértelmezett a 3.8.51-es verzió óta) — kérésre, közvetlenül tartalékként

`npm-publish.yml` keresztül publikálja** npm Trusted Publishing (OIDC)** alapértelmezés szerint: a `stage-npm` job (github-hosted) kicseréli GitHub id-tokenjét egy rövid élettartamú npm hitelesítő adatra az adott futáshoz. — nincs hosszú életű npm token a lerakattitkokban, nincs 2FA prompt, származás csatolva. Ez a bypass npm szankció most, amikor a 2FA-t kihagyó tokeneket visszavonják; visszaállítja a projekt teljesen automatikus folyamatát a v3.8.48-ig, miközben megtartja a WS1.3 garanciát (a kiszivárgott token nem tud egyedül közzétenni — nincs token).

**Egyszeri beállítás (tulajdonos):** npmjs.com → csomag `omniroute` → Beállítások → _Trusted Publisher_ → GitHub: tulajdonos `diegosouzapw`, repo `OmniRoute`, munkafolyamat `npm-publish.yml` (környezet: nincs). Amíg ez nem létezik, az automatikus lépés meghiúsul `ENEEDAUTH`: re-dispatch `publish_mode=staged` (lent) vagy `direct` segítségével.

### Szakaszos közzététel (kérésre — `publish_mode=staged`)

Az npm-publish munkafolyamat már nem tesz közzé közvetlenül: elindítja a csomagolt tarballt (`check:pack-boot`), majd futtatja `npm stage publish` — parancsot, a pontos bájtok a rendszerleíró adatbázisban vannak parkolva,** nem telepíthető** amíg a tulajdonos jóváhagyja. Az emberi 2FA-kapu a bizonyíték AFTER jára mozdult, nem előtte.

**A tulajdonosi folyamat a munkafolyamat után zöldre vált:**

1. `npm stage list omniroute` — keresse meg a szakaszazonosítót (a munkafolyamat-összefoglalóban is kinyomtatva).
2. Ellenőrizze a szakaszos bájtokat (ajánlott): `npm stage download <id>`, majd telepítse a letöltött tarballt egy ideiglenes előtagba, és indítsa el (`npm run check:pack-boot` automatizálja ugyanazt a csomagot → install → boot verdict CI ben).
3. `npm stage approve <id>` — a 2FA prompt IS a közzététel. `npm stage reject <id>` eldobja.
4. Közzététel utáni hálózat: a közzététel utáni ellenőrző (a v3.8.49-es terv WS1.4-je) telepíti a közzétett verziót a nyilvános nyilvántartásból egy tiszta tárolóba, és elindítja azt.

**Vészhelyzeti tartalék:** `workflow_dispatch` `publish_mode=direct` vel visszaállítja az örökölt azonnali `npm publish` (csak akkor használja, ha maga a staging rosszul működik; jegyezze fel, miért).

**Egyszeri keményítés (tulajdonos, npmjs.com):** állítsa be a Trusted Publishert `omniroute` hoz csak szakaszos módban, így a kiszivárgott, hosszú élettartamú token nem `npm publish` közvetlenül bárhonnan, — CI csak színpadképes; csak a tulajdonos 2FA kiadásai.

**Törött műtárgy-játékkönyv (változatlan):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` mint alapértelmezett reflex (perc, megfordítható); `npm unpublish` csak a 72h/no-dependents ablakon belül, és soha nem az első lépésként. Docker: soha ne írjon át verziócímkét. — rollback `latest` az utolsó jó kivonathoz irányítja.

**Docker Hub `latest` (minden stabil SemVer közzétételhez szükséges):** a `docker-publish` munkafolyamatnak címkéznie kell** mindkét** `X.Y.Z` és ha `should-promote-latest.sh` egyetért, ez a legmagasabb stabil SemVer, `:latest` a** ugyanaz az emésztés** . A feladat elvégzése után: A Hub `latest` kivonat megegyezik az új SemVer kivonattal, és `last_updated` áthelyezve. Ne hagyja `:latest` egy régebbi builden, miközben a kiadási megjegyzések csak a git-en létező javításokról beszélnek. Gyorsindítások összeállítása használja `:latest`; GitOps folyamatosan rögzítenie kell `X.Y.Z`. Lásd [Docker kiadási csatornák](../guides/DOCKER_GUIDE.md#release-channels) és #10317.

**Docker Hub szervezeti adattár (`cheaperinference/omniroute`):** Docker Hub nem tud áthelyezni egy adattárat a névterek között, ezért `diegosouzapw/omniroute` megőrzi lehívási előzményeit és minden kiadást, a `docker-publish` `mirror-org-dockerhub` feladata pedig minden egyes kiadott verziót (és előléptetéskor `:latest` ) átmásolja a `ghcr.io/cheaper-inference/omniroute` ból a szervezeti lerakatba. Szüksége van a `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` titkaira; nélkülük a feladat zöld marad, a "Docker Hub org mirror kihagyva" figyelmeztetéssel, és a többi registry normálisan publikál. A kiadott verzió későbbi közzétételéhez futtassa** Műveletek → Docker kép tükrözése a Docker Hub org-hoz → Munkafolyamat futtatása** `version=X.Y.Z` vel (és `promote_latest` a legmagasabb stabil verziónál): a meglévő képeket másolja, nincs újraépítés.

## Gyorsított hotfix-folyamat (`hotfix` címke)

A `hotfix` címkével ellátott PR kihagyja a nagy CI-mátrixot (9 részre osztott E2E, lefedettségi küszöbkövetés,
quality-gate, quality-extended), és megtartja a gyors, nagy jelértékű ellenőrzéseket: build,
egységteszt-részek, integrációs tesztek, vitest, lint/típusellenőrzés, docs-sync, `check:pack-artifact`,
valamint a tarball indulási füsttesztje (`check:pack-boot`). Cél: zöld eredmény ≤15 perc alatt a ~33 perc helyett.

**Belépési szabályzat — mind a négy feltétel kötelező (a Chromium/VS Code/Node vészhelyzeti folyamatai alapján):**

1. **Súlyosság**: a produkciós rendszer nem működik — egy közzétett artefaktum induláskor összeomlik / egy
   biztonsági javításról van szó / a kiadás minden felhasználója érintett. A „fontos” nem jelenti azt, hogy „nem működik”.
2. **Jogosultság**: kizárólag a repository tulajdonosa alkalmazhatja a `hotfix` címkét. A címke MAGA
   a jóváhagyás — kampány-PR esetén soha nem alkalmazható saját hatáskörben.
3. **Bizonyíték**: a PR törzse hivatkozik az előző, teljesen zöld nagy futtatásra (arra a tesztcsomagra, amelyet
   a kihagyott feladatok újra ellenőriznének), valamint a javítás saját, előbb sikertelen, majd sikeres tesztjére.
4. **Hatókör**: kizárólag cherry-pick — a minimális javítás, refaktorálás és kapcsolódó mellékes módosítások nélkül.

A kihagyott lefedettségi/küszöbkövetési felületet a release ágon következő teljes futtatás
újra ellenőrzi (folyamatosan zöld release) — a folyamat csak a VÁRAKOZÁST hagyja ki, az ellenőrzést soha.
A csak teszteket érintő módosítások (minden fájl a `tests/` alatt, egy sem a `tests/e2e/` alatt)
automatikusan, címke nélkül is kihagyják az E2E-mátrixot.

```
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

NOT futtassa `npm run build` majd egy külön `npm run build:cli` — telepítéséhez használja `npm run build:release` amely egy paranccsal tiszta + sentinel újraépítést végez.

- Mindig adj hozzá vagy frissíts teszteket, amikor a `src/`, `open-sse/`, `electron/` vagy `bin/` könyvtárban lévő éles kódot módosítod

## Automatizált szinkronizálási ellenőrzés

PR megnyitása előtt futtasd helyben a dokumentáció szinkronizálási ellenőrzését:

```bash
npm run check:docs-sync
```

A CI ezt az ellenőrzést a `.github/workflows/ci.yml` fájlban is futtatja (lintelési feladat).
