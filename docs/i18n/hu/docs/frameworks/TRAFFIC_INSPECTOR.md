A Traffic Inspector az OmniRoute beépített HTTPS-forgalom-hibakeresője — egy Charles Proxy / mitmweb / HTTP Toolkit jellegű eszköz, amely **LLM-tudatos** és **ügynöktudatos**. A `/dashboard/tools/traffic-inspector` útvonalon érhető el, és legfeljebb 5 egyidejű rögzítési forrás élő forgalmát fogadja.

**Irányítópult helye:** `/dashboard/tools/traffic-inspector`
**Oldalsáv csoportja:** Eszközök (az AgentBridge után)
**Lásd még:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — az AgentBridge az 1. rögzítési mód.

### Az architektúra egy bekezdésben

A `TrafficBuffer` (`src/mitm/inspector/buffer.ts`) egy megosztott, memóriában tárolt körkörös puffer (alapértelmezés szerint 1000 bejegyzéssel, amely az `INSPECTOR_BUFFER_SIZE` használatával konfigurálható). Minden rögzítési forrás a `push()` használatával ír bele. A puffer minden bejegyzést a `kindDetector.ts` segítségével osztályoz (megállapítja, hogy LLM-kérésről van-e szó), kiszámít egy `contextKey` értéket (a rendszerprompt SHA-256-ujjlenyomatát), majd a `globalTrafficBuffer.subscribe()` használatával továbbítja az adatokat az összes WebSocket-előfizetőnek. Az irányítópult a `GET /api/tools/traffic-inspector/ws` végponton keresztül csatlakozik, csatlakozáskor pillanatképet kap, amelyet `new`/`update`/`clear` események követnek.

## §2 Rögzítési módok

A Traffic Inspector **5 egyidejű rögzítési forrást** támogat. Mindegyik egymástól függetlenül kapcsolható be és ki. Minden `InterceptedRequest` (`src/mitm/inspector/types.ts`) `source` mezője az `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` vagy `"tproxy"` értékek egyikét tartalmazza.

### 1. mód — AgentBridge (alapértelmezett, mindig bekapcsolva)

**Forrás:** AgentBridge-kezelők (`src/mitm/handlers/base.ts`)
**Működés:** A `MitmHandlerBase` minden `intercept()` hívása meghívja a `hookBufferStart()` függvényt a továbbítás előtt, majd a `hookBufferUpdate()` függvényt a befejezéskor. Nem igényel további konfigurációt — az AgentBridge elindulásakor azonnal működik.
**Hatókör:** Az AgentBridge-ben konfigurált 9 IDE-ügynök
**Megjegyzés:** Az `InterceptedRequest` `source` mezője = `"agent-bridge"`

### 2. mód — Egyéni gazdagépek (DNS-átirányítás)

**Forrás:** Felhasználó által meghatározott gazdagéplista (`inspector_custom_hosts` tábla)
**Működés:** Egy gazdagép felhasználói felületen keresztüli hozzáadásakor a rendszer beírja a `127.0.0.1 <host>` sort az `/etc/hosts` fájlba (sudo szükséges). A meglévő AgentBridge MITM-kiszolgáló (443-as port) dinamikusan létrehoz egy SNI-tanúsítványt az új gazdagéphez.
**Hatókör:** Bármely, a hozzáadott gazdagépet használó alkalmazás — nincs szükség az alkalmazás konfigurációjának módosítására
**Megjegyzés:** `source` = `"custom-host"`

Példák felhasználási esetekre:

- Az `api.openai.com` figyelése Python-szkriptekből
- A `my-internal-llm.company.com` hibakeresése
- Az ugyanazon a hálózaton lévő mobileszközök forgalmának rögzítése (ARP-hamisítással — haladó)

### 3. mód — HTTP_PROXY-figyelő (8080-as port)

**Forrás:** A `HTTP_PROXY`/`HTTPS_PROXY` környezeti változókat használó alkalmazások
**Működés:** Egy másodlagos, a 8080-as porton figyelő szolgáltatás (`src/mitm/inspector/httpProxyServer.ts`), amely szabványos explicit HTTP/HTTPS-proxyként működik. Fogad `CONNECT` alagutakat (HTTPS) és közvetlen HTTP-kéréseket.
**Hatókör:** Bármely alkalmazás, amely figyelembe veszi a `HTTP_PROXY` környezeti változót — nincs szükség DNS-módosításra vagy sudo használatára
**Megjegyzés:** `source` = `"http-proxy"`

```bash
# Egyetlen parancs gyors rögzítése:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Folyamatos rögzítés egy parancsértelmező-munkamenetben:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS-korlátozás:** A HTTPS egy egyszerű `CONNECT` alagúton halad keresztül: a figyelő változtatás nélkül továbbítja a titkosított bájtokat, és csak metaadatokat rögzít (gazdagép, port, időzítés). Soha nem fejti vissza a HTTPS-t, és ehhez a módhoz nincs olyan beállítás, amely bekapcsolná a visszafejtést. A HTTPS-törzsek rögzítéséhez irányítsa a gazdagépet az 1. módon (AgentBridge), a 2. módon (Egyéni gazdagépek) vagy az 5. módon (TPROXY-visszafejtés) keresztül.

**Portütközés:** Ha a 8080-as port használatban van, az AgentBridge strukturált hibával kísért 409-es választ ad vissza. A port az `INSPECTOR_HTTP_PROXY_PORT` környezeti változóval módosítható.

### 4. mód — Rendszerszintű proxy (haladó, külön bekapcsolható)

**Forrás:** Operációsrendszer-szintű proxybeállítások (a gép összes alkalmazására érvényes)
**Működés:** Operációsrendszer-API-k segítségével az összes HTTP/HTTPS-forgalmat a HTTP_PROXY-figyelőn keresztül irányítja át:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Hatókör:** A gép minden olyan alkalmazása, amely figyelembe veszi a rendszer proxybeállításait
  **Megjegyzés:** `source` = `"system-proxy"`

**Biztonsági mechanizmusok:**

- Automatikus kikapcsolási időzítő (alapértelmezés szerint 30 perc, az `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES` változóval konfigurálható)
- A rendszer korábbi proxyállapota az adatbázisba kerül, és visszaállításkor helyreáll
- Ha a felhasználó aktív állapotban elnavigál, az irányítópulton megjelenik a „Rendszerproxy visszaállítása” üzenet
- A felhasználói felületen megjelenik a `⚠ Haladó` jelvény és egy kifejezett megerősítő jelölőnégyzet

### 5. mód — TPROXY transzparens visszafejtés (Linux, root, külön bekapcsolható)

**Forrás:** Kernel TPROXY + házirend-alapú útválasztás (`src/mitm/tproxy/`)
**Működés:** A célportra (alapértelmezés szerint `443`) irányuló új helyi kimenő TCP-kapcsolatokat megjelöli a `mangle OUTPUT` láncban, egy `ip rule` átirányítja a megjelölt csomagokat helyi kézbesítésre, majd a `mangle PREROUTING` `TPROXY` célja átadja őket egy transzparens (**IP_TRANSPARENT**) figyelőnek (alapértelmezett portja `8443`). A figyelő a TLS-kapcsolatot egy dinamikus hitelesítésszolgáltató által **igény szerint, SNI-gazdagépnevenként** kiadott végtanúsítvánnyal végződteti, rögzíti a visszafejtett adatcserét, majd újratitkosítva továbbítja a kérést az eredeti célhoz.
**Hatókör:** **Tetszőleges** célgazdagépek a célporton — nincs `/etc/hosts`-hamisítás, nincs `HTTP_PROXY` környezeti változó, és nem módosítja a rendszerszintű proxyt. Az elfogott folyamat nem igényel konfigurációmódosítást, de meg kell bíznia a dinamikus hitelesítésszolgáltatóban.
**Megjegyzés:** `source` = `"tproxy"`

**Követelmények:** Kizárólag Linux (**IP_TRANSPARENT** csak Linuxon érhető el), **CAP_NET_ADMIN** képesség (root), valamint egy natív N-API-kiegészítő, amelyet C-eszközlánccal kell lefordítani (`npm run build:native:tproxy`). Ha ezek nem érhetők el, az irányítópult kapcsolója le van tiltva, és a következő elemleírás jelenik meg: „A TPROXY-visszafejtéshez Linux + root + a natív kiegészítő szükséges”. A tűzfalszabályok alkalmazása és visszaállítása tranzakciós módon történik (egy összeomlás soha nem hagy hátra `mangle` szabályt), újraindításkor pedig törlődnek. Egy SO_MARK-alapú hurokellenes mechanizmus megakadályozza, hogy a proxy saját, újratitkosított továbbított forgalmát ismét elfogja a rendszer.

Ez egy jelentős alrendszer, amely saját, külön üzemeltetői útmutatóval rendelkezik — a teljes tűzfalreceptet, az SNI-nként dinamikus hitelesítésszolgáltatót és megbízhatóságitár-telepítőt, a csak helyi útvonalat, a hurokellenes megoldás részleteit és a konfigurációs sémát lásd a `docs/security/MITM-TPROXY-DECRYPT.md` fájlban (git; nincs beépítve a `/docs` könyvtárba). A kapcsolót a `GET / POST / DELETE /api/tools/agent-bridge/tproxy` vezérli (megjegyzés: az útvonal az AgentBridge előtag alatt található, nem a Traffic Inspector előtagja alatt).

### 3.2 Kéréslista (bal oldali panel)

- **Virtualizált** (`useVirtualList` + `ResizeObserver`): 1000 elemet is képes lefagyás nélkül kezelni
- **Automatikus görgetés**, amely egy kapcsolóval szüneteltethető a vizsgálat idejére
- **Színkódolt állapot**: zöld (2xx), sárga (3xx), piros (4xx/5xx), szürke (folyamatban)
- **Ügynökhangulatjelek**: 🔵 Antigravity, 🟢 Copilot, 🟠 Kiro, 🟣 Codex, 🔷 Cursor, 🟤 Zed, 🟡 Claude Code, ⚫ Open Code, 🌐 egyéni gazdagép
- **Környezetet jelző színsáv**: 1 képpont széles, a `contextKey` alapján színezett bal oldali szegély (a rendszerprompt SHA-256-kivonata) — vizuálisan csoportosítja a kapcsolódó beszélgetéseket
- **Lusta törzsbetöltés**: csak a kijelölt kérés törzse materializálódik a részletező lapokon (így elkerülhető 1000 × 1 MB-os törzs megjelenítése)

## §4 LLM-tudatos funkciók

### 4.1 Típusfelismerő (`src/mitm/inspector/kindDetector.ts`)

Minden kérést `"llm"`, `"app"` vagy `"unknown"` típusúnak minősít 4 jel alapján:

1. **Hosztregiszter** — ~18 ismert LLM API-hosztnév (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot stb.)
2. **Útvonalminták** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` stb.
3. **Törzs szerkezete** — felismeri a `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` mezőket
4. **User-agent jelzések** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` az UA-karakterláncban

A 2. módban hozzáadott egyéni hosztok a `kind` értéküket az űrlap mezőjéből öröklik (alapértelmezés szerint `"custom"`).

### 4.2 SSE-egyesítő (`src/mitm/inspector/sseMerger.ts`)

**Független, tiszta szobás implementáció.** Az események elemzése a
[WHATWG kiszolgáló által küldött események algoritmusát](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)
követi, míg a rekonstrukció a nyilvános [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) és
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
streamelési sémáit követi.

A nyers SSE-deltaeseményekből rekonstruálja az asszisztens végső üzenetét:

- **Anthropic**: index szerint összegzi a `content_block_delta` elemeket; kezeli a `text_delta`, `input_json_delta` (eszközhívások), `thinking_delta` típusokat
- **OpenAI**: index szerint összegzi a Chat Completions választásait/eszközhívásait és a Responses API kimeneti elemeit
- **Gemini**: összegzi a `candidates[i].content.parts` elemeit
- **Ismeretlen**: változatlanul adja vissza a nyers eseményeket

A Válasz lap egy kapcsolót jelenít meg: **„Nyers események ↔ Egyesített”**.

### 4.3 Beszélgetésnormalizáló (`src/mitm/inspector/conversationNormalizer.ts`)

**Független, tiszta szobás implementáció.** A normalizálást helyi feketedobozos
szerződések, valamint az OpenAI, az Anthropic és a Gemini nyilvános üzenetsémái határozzák meg; nem használ külső
implementációból származó forráskódot.

Az OpenAI, az Anthropic és a Gemini üzenetformátumait a megjelenítés előtt egyetlen `NormalizedConversation` formátummá alakítja:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // üzenetek / tartalmak / prompt a kérés törzséből
  response: NormalizedTurn[]; // asszisztensi válasz (az sseMerger által egyesítve)
  contextKey: string | null; // a rendszerprompt SHA-256-ujjlenyomata
}
```

Blokktípusok: `text`, `tool_use`, `tool_result`. A Beszélgetés lap szolgáltatótól függetlenül ezt a struktúrát használja.

### 4.4 Kontextuskulcs színezése (`src/mitm/inspector/contextKey.ts`)

- Kiszámítja a rendszerprompt `SHA-256`-kivonatát (az első `role:system` üzenet, a `system` mező vagy a Gemini `systemInstruction` alapján)
- Egy 12 karakteres hexadecimális előtagot ad vissza (`"a3f9c2..."`)
- A frontend a kulcsot egy determinisztikus HSL-színhez rendeli a bal oldali szegélysávhoz
- **„Azonos kontextus” szűrő**: a `ctx #a3f` címkére kattintva hozzáad egy szűrőt, amely csak az azonos ujjlenyomattal rendelkező kéréseket jeleníti meg

Ez megkönnyíti az ugyanazon ügynökmenetben futó különböző „személyiségek” vagy feladatok vizuális megkülönböztetését.

### 4.5 LLM-metaadatok kinyerése

LLM-kérések esetén az LLM részletei lap a következőket nyeri ki:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // a kérés törzséből vagy a válaszból
  messages: number; // fordulók száma
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true, ha SSE-válasz
  mappedTo: string | null; // x-omniroute-mapped fejléc
  costEstimateUsd: number | null; // az OmniRoute díjszabásán alapuló becsült költség
}
```

### 4.6 Élő, folyamatban lévő kérések szűrője

A kérés `status` mezője `number | "in-flight" | "error"` típusú — a bejegyzés
`"in-flight"` értékkel kerül be azonnal a kérés indulásakor, majd **helyben frissül**,
amikor megérkezik a válasz (vagy a hiba). Az eszköztár **„Élő”** kapcsolója
(`liveOnly`, i18n-kulcs: `trafficInspector.liveOnly`) azokra a bejegyzésekre
korlátozza a listát, amelyeknél `status === "in-flight"`, így valós időben figyelhetők a nyitott kapcsolatok.

A szűrő egy tiszta, kliensoldali predikátum a
`src/lib/inspector/matchesTrafficFilter.ts` fájlban:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

A kapcsoló állapota a `useTrafficFilters` elemben található (az ellenőrző irányítópult hookjai), és
a többi szűrővel (profil, hoszt, ügynök, forrás, állapot, kontextus) együtt érvényesül.

### 4.7 Folyamat-hozzárendelés (Linux)

Linux rendszeren minden elfogott kérés hozzárendelhető az azt **kezdeményező helyi
folyamathoz**. Két opcionális mező kerül az `InterceptedRequest` típusba:

```ts
pid?: number;          // a kezdeményező folyamat azonosítója (csak Linux)
processName?: string;  // a kezdeményező folyamat neve (csak Linux)
```

A `src/mitm/inspector/processAttribution.ts` a kapcsolat _kliensoldali_
ideiglenes portját a következő módon rendeli hozzá egy PID-hez és névhez:

1. Beolvassa a `/proc/net/tcp` és `/proc/net/tcp6` fájlokat, hogy megkeresse a
   porthoz tartozó socket inode-ot (`parseProcNetTcpForInode`, egy tiszta, fixture-ökkel tesztelhető elemző).
2. Átvizsgálja a `/proc/<pid>/fd/` könyvtárat a `socket:[<inode>]` célra mutató szimbolikus hivatkozásért.
3. Beolvassa a folyamat nevét a `/proc/<pid>/comm` fájlból.

Egy 1 másodperces TTL-gyorsítótár terhelés alatt korlátozza a procfs átvizsgálásának költségét. A hozzárendelés
**legjobb igyekezet szerinti** — bármilyen hiba esetén `null` értéket ad vissza, és soha nem blokkolja a rögzítést.
macOS/Windows rendszeren a függvény `null` értéket ad vissza (helykitöltő; az `lsof`/`GetExtendedTcpTable`
támogatása egy későbbi feladat).

## §6 Biztonság

A Traffic Inspector megjeleníti az **összes elfogott HTTPS-forgalmat**, beleértve az engedélyezési fejléceket és a kérés törzsét is. A következő védelmi mechanizmusok vannak érvényben:

| Védelmi mechanizmus                             | Részletek                                                                                                                                                                                                              |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                                  | Minden útvonal és a WebSocket-végpont kizárólag loopback kapcsolaton érhető el (ezt a `routeGuard.ts` még a hitelesítés előtt kikényszeríti)                                                                           |
| **Titkok maszkolása**                           | A lineáris `maskSecret()` vizsgáló kitakarja az RFC 6750 szerinti Bearer hitelesítő adatokat, a szolgáltatói előtaggal ellátott kulcsokat és a hosszú, átlátszatlan tokeneket a `TrafficBuffer.push()` meghívása előtt |
| **Törzsméret korlátozása**                      | Az `INSPECTOR_MAX_BODY_KB` értéknél (alapértelmezés szerint 1024 KB) nagyobb törzsek csonkolva lesznek, és megjelenik a `"(teljesítménybeli okokból csonkolva)"` értesítés                                             |
| **Fejlécek tisztítása**                         | A nevek kisbetűssé alakulnak; a keretezési, ugrásonkénti és proxyhitelesítési fejlécek el lesznek távolítva; a sütik teljesen ki lesznek takarva; a hitelesítőadat-értékek kezelését a `maskSecret()` végzi            |
| **CSP**                                         | A Traffic Inspector oldalain szigorú Content Security Policy akadályozza meg a befecskendezett választörzseken keresztüli XSS-támadásokat                                                                              |
| **Alapértelmezés szerint nincs tartós tárolás** | A `TrafficBuffer` memóriában tárolódik, és a kiszolgáló újraindításakor elveszik. A munkamenetek csak kifejezett rögzítés esetén lesznek tartósan tárolva                                                              |

### Alkalmazott kötelező szabályok

| Szabály                           | Alkalmazás                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | A Traffic Inspector útvonalairól érkező összes HTTP-hibaválasz megtisztításra kerül     |
| **#15 + #17** `isLocalOnlyPath()` | Az `/api/tools/traffic-inspector/` LOCAL_ONLY + SPAWN_CAPABLE (rendszerproxy-parancsok) |

### Ismert korlátozások

- A **rendszerszintű proxymód** a gépen futó összes alkalmazásra hatással van, beleértve a VPN-klienseket és az SSO-t is. Mindig automatikus kikapcsolási időzítővel használja. Megosztott gépeken ne használja.
- **CONNECT-alagutas HTTPS**: A 3. mód (HTTP_PROXY) HTTPS-célok esetén csak az alagút metaadatait rögzíti, és soha nem fejti vissza a titkosításukat. Ez szándékos működés — a visszafejtéshez minden kliensnek megbízhatónak kellene tekintenie egy MITM-tanúsítványt, ezért a figyelő végpontok között titkosítva tartja a HTTPS-forgalmat. Ha szüksége van a HTTPS-törzsekre, használja az AgentBridge, a Custom Hosts vagy a TPROXY decrypt megoldást.
- **Egyes komponensekbe beégetett karakterláncok**: Néhány felhasználói felületi komponens (F7/F8) kis számú, beégetett karakterláncot tartalmaz, amelyeket még nem fednek le i18n-kulcsok. Ezek ismert korlátozásként szerepelnek az i18n-hiányossági jelentésben; áttelepítésük egy későbbi körben történik meg. Az érintett karakterláncok a felhasználói felület olyan dekoratív címkéi, amelyek funkcionális használatához nincs szükség fordításra.

## §7 Hibaelhárítás

### WebSocket-kapcsolat megszakadása

Ha az élő naplóban a „Kapcsolat megszakadt” üzenet jelenik meg:

1. Ellenőrizze, hogy a kiszolgáló még fut-e: `GET /api/tools/traffic-inspector/capture-modes`
2. Töltse újra az oldalt — a WebSocket újracsatlakozik, és friss pillanatképet kap
3. Ha a kiszolgálót újraindították, a memóriában tárolt puffer törlődött — a régi bejegyzések elvesztek, kivéve, ha munkamenetben rögzítették őket

### Ütközés a 8080-as porton

Ha a HTTP_PROXY mód nem indul el:

```bash
lsof -i :8080    # a folyamat megkeresése
```

Módosítsa a portot:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### A rendszerproxy nem lett visszaállítva

Ha az OmniRoute összeomlik, miközben a rendszerszintű proxy mód aktív:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

A vezérlőpult a következő betöltéskor felajánlja a „Rendszerproxy visszaállítása” lehetőséget is, ha az adatbázis állapota alapján azt észleli, hogy a proxy aktív volt.

### Megtelt puffer

Amikor a puffer eléri az `INSPECTOR_BUFFER_SIZE` értékét (alapértelmezés szerint 1000), az új bejegyzések kiszorítják a legrégebbieket. Ha fontos kérések vesznek el:

- Növelje az `INSPECTOR_BUFFER_SIZE` értékét (például 5000-re) — ez több memóriát használ a hosszabb megőrzés érdekében
- Rögzítsen egy munkamenetet, hogy a releváns időszak adatai megmaradjanak az adatbázisban
