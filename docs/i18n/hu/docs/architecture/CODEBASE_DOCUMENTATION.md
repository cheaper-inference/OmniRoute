## 1. Technológiai stack

| Terület               | Választás                                                                                                                         |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Webes keretrendszer   | **Next.js 16** (App Router, önálló kimenet, globális middleware nélkül)                                                           |
| Nyelv                 | **TypeScript 6.0+** — cél: `ES2022`, `module: esnext`, `moduleResolution: bundler`, `strict: false`                               |
| Futtatókörnyezet      | **Node.js** `>=22.22.2 <23` vagy `>=24.0.0 <27` (az `engines` + `SUPPORTED_NODE_RANGE` kényszeríti ki)                            |
| Adatbázis             | **SQLite** a `better-sqlite3` használatával (singleton, WAL-naplózás)                                                             |
| Asztali alkalmazás    | **Electron 41** + `electron-builder` 26.10 (külön munkaterület az `electron/` könyvtárban)                                        |
| Tesztek               | **Node natív tesztfuttató** (egység-/integrációs), **Vitest** (MCP, autoCombo, gyorsítótár), **Playwright** (e2e + protocols-e2e) |
| Buildelés             | Önálló Next.js-kimenet a `scripts/build/build-next-isolated.mjs` használatával                                                    |
| Lint/formázás         | ESLint flat konfiguráció + Prettier (`lint-staged` Husky pre-commit hookkal)                                                      |
| Modulrendszer         | Mindenhol ESM (`"type": "module"`)                                                                                                |
| Irányítópult felülete | **Tailwind CSS 4** + a repóban tárolt **Keak CI UI Kit** (`packages/ui-kit`), Lucide ikonok — lásd: `DESIGN_SYSTEM.md`            |
| Munkaterületek        | npm-munkaterületek — `open-sse`, `packages/browser-pool`, `packages/ui-kit`                                                       |

Útvonalálnevek (`tsconfig.json`):

- `@/*` → `src/*`
- `@omniroute/open-sse` → `open-sse/index.ts`
- `@omniroute/open-sse/*` → `open-sse/*`
- `@omniroute/ui-kit` → `packages/ui-kit/src`, `@omniroute/ui-kit/*` → `packages/ui-kit/src/*`

Alapértelmezett HTTP-port: **`20128`** (az API és az irányítópult ugyanazt a folyamatot használja). Az adatkönyvtárat
a `DATA_DIR` környezeti változó határozza meg, alapértelmezett értéke `~/.omniroute/`.

### 3.1 `src/app/` — App Router

Az App Router megjeleníti a műszerfal UI és public/management HTTP API is. Van** nincs globális köztes szoftver** — elfogás útvonalonként történik.

Legfelső szintű szegmensek `src/app/` alatt:

| Útvonal                                                                       | Cél                                                 |
| ----------------------------------------------------------------------------- | --------------------------------------------------- |
| `api/`                                                                        | Minden HTTP API útvonal (lásd lent a bontást)       |
| `a2a/`                                                                        | A2A JSON-RPC 2.0 végpont (`POST /a2a`)              |
| `.well-known/agent.json/`                                                     | A2A Agent Card felfedezési dokumentum               |
| `(dashboard)/`                                                                | Irányítópult UI (útvonalcsoport, URL előtag nélkül) |

## 10. Hogyan járulhatsz hozzá

### Új szolgáltató hozzáadása

1. Regisztráld a `src/shared/constants/providers.ts` fájlban (betöltéskor Zod-validáció történik).
2. Ha egyéni logika szükséges, adj hozzá egy végrehajtót az `open-sse/executors/` könyvtárban
   (a `BaseExecutor` kiterjesztésével).
3. Ha nem az OpenAI-formátumot használja, adj hozzá egy fordítót az `open-sse/translator/` könyvtárban.
4. OAuth-alapú szolgáltató esetén adj hozzá konfigurációt a `src/lib/oauth/providers/` és
   a `src/lib/oauth/services/` könyvtárban.
5. Regisztráld a modelleket az `open-sse/config/providerRegistry.ts` fájlban (vagy a formátumspecifikus
   regisztrációs fájlban az `open-sse/config/` alatt).
6. Írj teszteket a `tests/unit/` könyvtárban.

### Új API-útvonal hozzáadása

1. Hozd létre a `src/app/api/your-route/route.ts` fájlt.
2. Kövesd ezt a mintát: CORS → a törzs Zod-validációja → hitelesítés → delegálás a kezelőnek.
3. Új kérésstruktúra esetén add hozzá a Zod-sémát a `src/shared/validation/schemas.ts` fájlban.
4. Ha csak felügyeleti célú: add hozzá az elérési utat a `src/shared/constants/publicApiRoutes.ts`
   fájlhoz (a nyilvános API-felület tiltólistája).
5. Adj hozzá teszteket a `tests/unit/` könyvtárban.
6. Frissítsd a `docs/reference/API_REFERENCE.md` és a `docs/openapi.yaml` fájlt.

### Új DB-modul hozzáadása

1. Hozd létre a `src/lib/db/yourModule.ts` fájlt, és importáld a `getDbInstance()` függvényt a `./core.ts` fájlból.
2. Exportáld a domainedhez tartozó CRUD-függvényeket.
3. Új táblák esetén adj hozzá egy migrációt a `src/lib/db/migrations/` könyvtárban, szekvenciális
   sorszámozással, idempotens és tranzakciós módon.
4. Az importálók közvetlen importokat használnak az `@/lib/db/yourModule` modulból (nincs gyűjtőmodul — a régi `localDb.ts` újraexportálási réteget eltávolítottuk).
5. Adj hozzá teszteket a `tests/unit/` könyvtárban.

### Új MCP-eszköz hozzáadása

1. Add hozzá az eszköz definícióját az `open-sse/mcp-server/tools/` könyvtárban (vagy bővítsd az
   `open-sse/mcp-server/schemas/tools.ts` fájlt).
2. Rendeld hozzá a megfelelő hatókör(öke)t a `src/shared/constants/mcpScopes.ts` fájlban.
3. Regisztráld az eszközt az `open-sse/mcp-server/server.ts` fájlban.
4. Adj hozzá teszteket az `open-sse/mcp-server/__tests__/` könyvtárban.
5. Frissítsd az [MCP-SERVER.md](../frameworks/MCP-SERVER.md) fájlt.

### Új A2A-képesség hozzáadása

Lásd: [A2A-SERVER.md § Új képesség hozzáadása](../frameworks/A2A-SERVER.md). A képességek a
`src/lib/a2a/skills/` könyvtárban találhatók, és az A2A-feladatkezelőn keresztül vannak regisztrálva.

## 11. Konvenciók

- **Kódstílus**: 2 szóközös behúzás, dupla idézőjelek, 100 karakteres sorhossz, pontosvesszők,
  `es5` záróvesszők — a Prettier kényszeríti ki a `lint-staged` segítségével.
- **Importok**: külső → belső (`@/`, `@omniroute/open-sse`) → relatív.
- **Elnevezés**: fájloknál `camelCase` vagy `kebab-case`, komponenseknél `PascalCase`,
  konstansoknál `UPPER_SNAKE`.
- **ESLint**: `no-eval`, `no-implied-eval`, `no-new-func` = `error` mindenhol;
  `no-explicit-any` = `warn` az `open-sse/` és a `tests/` könyvtárban, máshol `error`.
- **TypeScript**: `strict: false` (örökölt beállítás). A modulok közötti határokon részesítsd előnyben az explicit típusokat
  a típuskövetkeztetéssel szemben.
- **Adatbázis**: soha ne írj nyers SQL-t útvonalakba vagy kezelőkbe — mindig a
  `src/lib/db/` moduljait használd. Soha ne importálj gyűjtőmodulból — közvetlenül az egyes `src/lib/db/*` modulokat használd.
- **DB-entitások tipizálása (#3512)**: egy DB-tábla sorstruktúráját író vagy olvasó függvény
  egy elnevezett TS-interfészt fogadjon/adjon vissza, amely 1:1 arányban tükrözi az adott tábla
  oszlopait, ne pedig `any` típust vagy a hívás helyén megadott névtelen beágyazott típust. Helyezd
  az interfészt a függvény mellé (például `export interface UsageEntry` a
  `src/lib/usage/usageHistory.ts` fájlban, a `saveRequestUsage` fölött), az egyes
  mezők maradjanak opcionálisak/null értékűek, ha a különböző írók fokozatosan töltik fel a sort,
  és részesítsd előnyben az `unknown` típust az `any` típussal szemben, ha egy mező struktúrája
  hívónként változik (ezt dokumentáld a mezőnél, például a `UsageEntry.tokens`
  a szolgáltató nyers használati struktúráját és a normalizált struktúrát is
  elfogadja). Ha egy fájl `any`-előfordulásainak száma így eléri a nullát, add hozzá a
  `check:any-budget:t11` engedélyezési listájához (`scripts/check/check-t11-any-budget.mjs`,
  `maxAny: 0`), hogy ne történhessen visszalépés. Ez egy első részletre vonatkozó konvenció — a
  névtelen `any` típusok átfogó eltávolítása iteratívan történik a kódbázis többi részében.
- **Hibák**: használj try/catch blokkot konkrét hibatípusokkal, és naplózz pino-kontextussal. Az SSE-adatfolyamokban
  soha ne nyeld el csendben a hibákat; a tisztításhoz használj megszakítási jeleket.
- **Biztonság**: soha ne használj `eval()` / `new Function()` / közvetett eval funkciót. Minden
  bemenetet validálj Zoddal. A hitelesítő adatokat titkosítva tárold (AES-256-GCM). Tartsd
  összhangban a `src/shared/constants/upstreamHeaders.ts` tiltólistáját a
  tisztítási/validációs réteggel.
- **Commitok**: Conventional Commits — `feat(scope): subject`. Engedélyezett hatókörök:
  `db`, `sse`, `oauth`, `dashboard`, `api`, `cli`, `docker`, `ci`, `mcp`,
  `a2a`, `memory`, `skills`.
- **Ágak**: előtagok: `feat/`, `fix/`, `refactor/`, `docs/`, `test/`,
  `chore/`. Soha ne commitolj közvetlenül a `main` ágba.
- **Husky**: a pre-commit futtatja a `lint-staged` + `check:docs-sync` +
  `check:any-budget:t11` feladatokat; a pre-push futtatja a `check:any-budget:t11` + `check:tracked-artifacts` feladatokat (gyors ellenőrzőkapuk; a `test:unit` nincs köztük).
