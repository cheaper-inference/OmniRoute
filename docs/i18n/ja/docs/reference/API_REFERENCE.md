## チャット補完

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### カスタムヘッダー

| ヘッダー                 | 方向       | 説明                                                                                                                                                                                                                 |
| ------------------------ | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | リクエスト | キャッシュをバイパスするには`true`に設定します                                                                                                                                                                       |
| `x-omniroute-no-memory`  | リクエスト | このリクエストでメモリとスキルの挿入をスキップするには`true`に設定します（キャッシュ無効化と同様で、呼び出しごとのトークン／コストのオーバーヘッドを回避します）                                                     |
| `X-OmniRoute-Progress`   | リクエスト | 進捗イベントを有効にするには`true`に設定します                                                                                                                                                                       |
| `X-Session-Id`           | リクエスト | 外部セッションアフィニティ用の固定セッションキー                                                                                                                                                                     |
| `x_session_id`           | リクエスト | アンダースコア形式も使用可能です（直接HTTP）                                                                                                                                                                         |
| `X-OmniRoute-Session-Id` | リクエスト | 呼び出し元が指定するセッション／会話タグ（メモリにも渡されます）。指定された場合、セッションごとのコスト配賦のために、そのまま`call_logs.session_tag`へ永続化されます（#8249）。指定されていない場合は生成されません |
| `Idempotency-Key`        | リクエスト | 重複排除キー（5秒間のウィンドウ）                                                                                                                                                                                    |
| `X-Request-Id`           | リクエスト | 代替の重複排除キー                                                                                                                                                                                                   |
| `x-omniroute-connection` | リクエスト | 単一モデルのリクエストを、IDで指定した1つのプロバイダー接続（アカウント）に固定します — [リクエストごとのアカウント固定](#account-pinning-per-request)を参照してください                                             |
| `X-OmniRoute-Cache`      | レスポンス | `HIT`または`MISS`（非ストリーミング）                                                                                                                                                                                |
| `X-OmniRoute-Idempotent` | レスポンス | 重複排除された場合は`true`                                                                                                                                                                                           |
| `X-OmniRoute-Progress`   | レスポンス | 進捗追跡が有効な場合は`enabled`                                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | レスポンス | OmniRouteが使用した有効なセッションID                                                                                                                                                                                |
| `X-OmniRoute-Request-Id` | レスポンス | リクエスト相関ID（判明している場合）                                                                                                                                                                                 |
| `X-OmniRoute-Version`    | レスポンス | OmniRouteのビルドバージョン（常に存在）                                                                                                                                                                              |
| `X-OmniRoute-Cost-Saved` | レスポンス | キャッシュヒットによって回避されたコスト（USD、キャッシュヒット時のみ）                                                                                                                                              |
| `X-OmniRoute-Decision`   | レスポンス | ルーティングトレース：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>`はコンボ戦略、コンボ以外のリクエストでは`single`）— 完了レスポンスには常に存在します                                              |

> Nginx に関する注意: アンダースコアを含むヘッダー（例: `x_session_id`）を使用する場合は、`underscores_in_headers on;` を有効にしてください。

#### リクエストごとのアカウント固定

プロバイダーに複数の接続（アカウントまたはキー）がある場合、OmniRoute は通常、アカウント選択戦略に従って
そのうちの1つを選択します。代わりに、`x-omniroute-connection` ヘッダーを使用して、リクエストを
特定の1つの接続に固定できます。

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **ID の確認場所。** ダッシュボードでプロバイダーページ
  （**ダッシュボード → プロバイダー → <provider>**）を開き、接続行の `xxxxxxxx…` ID チップをクリックすると、
  完全な接続 ID がコピーされます。
- **このヘッダーが適用されるリクエスト。** `/v1/chat/completions`、`/v1/messages`、`/v1/responses` に対する
  単一モデルリクエスト（`provider/model`）。コンボではこのヘッダーは無視されます。代わりに、
  各コンボステップ独自の接続を使用して、ステップごとにアカウントを固定してください。
- **固定は優先指定ではなく、厳密な指定です。** 固定された接続のみが使用されます。リクエスト内で
  障害が発生すると、そのアカウントのクールダウンは記録されますが、同じプロバイダーの
  別アカウントへは**切り替わりません**。
- **クールダウンとクォータにより固定は解除されます。** 固定された接続がクールダウン中、
  クォータ枯渇状態、またはクォータポリシーによってブロックされている間、後続のリクエストは、
  固定されていないトラフィックとまったく同様に、そのプロバイダーの他の接続へフォールバックします。
- **不明または無効な ID は失敗します。** プロバイダーのアクティブプールに存在しない ID（削除済み、
  無効化済み、または別のプロバイダーに属するもの）では適格なアカウントがなくなるため、
  リクエストは暗黙的に別の接続へルーティングされるのではなく、失敗します。

Claude Code は、`ANTHROPIC_CUSTOM_HEADERS` を介してカスタムヘッダーを送信します。これを
`~/.claude/settings.json` の `env` ブロックに設定するか、プロジェクトごとに異なるアカウントへ固定する場合は、
プロジェクトレベルの `.claude/settings.json` に設定してください。

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

出典: `src/sse/handlers/chat.ts`（ヘッダーの読み取り）、`src/sse/services/auth.ts` および
`src/sse/services/sessionAffinityPin.ts`（固定の解除と、プール内に存在しないことの確認）。

> **コストテレメトリヘッダー:** 非ストリーミングの成功レスポンスには、`X-OmniRoute-*` コストテレメトリ一式も含まれます。具体的には、`X-OmniRoute-Response-Cost`（USD、小数点以下10桁固定。無料または価格未設定の場合は `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit`、`X-OmniRoute-Fallback-Attempts`（> 0 の場合のみ）、さらに `X-OmniRoute-Request-Id` と `X-OmniRoute-Version` です。これらは、チャット補完、`/v1/responses`、`/v1/messages`、**およびメディアエンドポイント**（`/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations`、`/v1/moderations`（コストは常に `0`））によって出力されます。価格情報が利用可能な場合、メディアのコストはモダリティごと（画像単位、秒単位、文字単位、検索単位）に計算され、それ以外の場合は `0`（フェイルオープン）になります。

> **キャッシュヒット時のコストの意味:** セマンティックキャッシュのヒット時（`X-OmniRoute-Cache-Hit: true`）はアップストリーム呼び出しが行われないため、`X-OmniRoute-Response-Cost` は `0.0000000000`（ヒットを処理するための**増分**コスト）になります。元のコスト、またはキャッシュがなければ発生していたコストは、`X-OmniRoute-Cost-Saved` で別途報告されます。課金処理では `X-OmniRoute-Response-Cost` を合計してください（ヒットにはコストがかかりません）。キャッシュ分析では `X-OmniRoute-Cost-Saved` を集計できます。

## 排他的マネージドセッションリース

排他的マネージドセッションリースは、オプトイン方式のクライアント非依存ルーティング契約です。1つのアクティブな所有者が、条件を満たす1つの OmniRoute 接続を保持します。モデルをリースするものではなく、OAuth を要求せず、特定のクライアントを識別せず、特定のプロバイダーも要求しません。

認証に使用する API キーには、スコープ `lease:exclusive` と、明示的かつ空でない `allowedConnections` リストが必要です。データベースのミューテーション境界では、キーの作成時と部分更新時に、これら両方のフィールドがまとめて適用されます。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

取得、更新、解放に成功したレスポンスでは、タイムスタンプ、`state`、および正確な正の `generation` が公開されますが、選択された接続や認証情報は公開されません。更新と解放では、JSON 本文で世代を指定します。

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

アクティブなリース所有者は、現在のバインディングについて、プライバシーに配慮した表示用メタデータを明示的に要求できます。

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

このオプトインのステータスアクションは、不透明な所有者、認証済みのマネージド API キー、および正確なアクティブ世代によって、1つのデータベーストランザクション内でフェンシングされます。`displayName` は、設定済みの接続名をトリミングしたものに限られ、安全な設定名が存在しない場合は `null` になります。OmniRoute がメールアドレスや生成されたアカウント ID で代用することはありません。プロバイダー値は機密性のない表示ラベルであり、生成された互換プロバイダー識別子になることはありません。認証情報、トークン、Cookie、生の接続 ID または API キー ID、所有者ハッシュ、フェンシングシークレット、および内部ルーティングデータは除外されます。

誤ったキー、誤った所有者、古い世代、欠落、期限切れ、解放済み、および無効化済みのルックアップはすべて、接続メタデータを含まない同一の `409 LEASE_FENCE_STALE` エラーを返します。容量待機レスポンスを受け取ったクライアントには、検査できるアクティブなバインディングがありません。ルーティングによってアクティブなリースが切り替えられた場合、同じ世代が引き続き有効であり、ステータスは古いバインディングではなく新しいバインディングをアトミックに返します。取得、更新、解放、および待機レスポンスは従来の形式を維持するため、既存のクライアントへの変更はありません。

このサーバー契約は、標準の OpenAI Codex `/status` を変更しません。現在、標準の Codex はモデルプロバイダーと組み込みの認証／アカウント状態を報告しますが、任意のカスタムプロバイダーのアカウントメタデータは表示しません。将来のクライアント統合では、このアクションを呼び出し、`connection.displayName` の表示方法を決定する必要があります。

その後、マネージド推論リクエストでは毎回、次の両方の制御ヘッダーを指定します。

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

所有者、世代、アクティブな接続、および認証済み API キーが完全に一致することは、サポート対象の各アップストリーム試行の直前にフェンシングによって検証されます。別のキーが同じ接続を許可している場合でも、そのキーで所有者と世代を再利用すると失敗します。生の所有者情報は、永続化、ログ記録、リクエストスナップショットへの保持、またはアップストリームへの転送が行われません。

一時的な競合が発生すると、HTTP `429` と `Retry-After` に加えて、次のレスポンスが返されます。

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

このレスポンスは、通常の適格セットが空ではなく、空き状態の候補がすべて他の所有者のアクティブなリースによって保持されていたことだけを意味します。サポートされていないモデル／プロバイダー、ポリシーの不一致、クールダウン、クォータ、正常性、およびその他の通常の適格性エラーについては、既存の OmniRoute レスポンスが維持されます。

### `x-omniroute-compression`

リクエスト単位で圧縮プランをオーバーライドします。優先順位は最上位であり、ルーティングコンボのオーバーライド、アクティブプロファイル、自動トリガー、およびパネルのデフォルトよりも優先されます。値は次のとおりです。

| 値            | 効果                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `off`         | このリクエストでは圧縮しません。                                                                                         |
| `default`     | パネルから導出されたデフォルトプロファイルです（アクティブプロファイルは無視されます）。非可逆エンジンは無効のままです。 |
| `safe`        | 重複排除と空白の折りたたみのみを行います。                                                                               |
| `allow-lossy` | 要約やスタイルの書き換えを含め、このリクエストに対するオペレーターのプランを維持します。                                 |
| `engine:<id>` | 有効な場合に単一のエンジンを使用します（例: `engine:rtk`）。そのエンジンに対するリクエスト単位のオプトインです。         |
| `<combo>`     | 名前付きコンボです。最初に名前（大文字と小文字を区別しない）、次に ID で照合されます。                                   |

注:

- 不明な値は無視され（リクエストが拒否されることはありません）、通常のオペレーター優先順位による解決へフォールスルーします。
- 複数のコンボが同じ名前を共有している場合、決定的な照合を行うにはコンボの **ID** を渡してください。
- 名前が `off` または `default` のコンボは、名前では選択できません（これらのキーワードが先に解釈されます）。そのようなコンボは ID で参照してください。
- 圧縮のマスタースイッチは強制的なゲートです。圧縮がグローバルで無効になっている場合、このヘッダーで有効にすることはできません。

適用されたプランは、レスポンスヘッダーにエコーバックされます。

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ここで `<source>` は、`request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default`、または `off` のいずれかです。

## 埋め込み

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

利用可能なプロバイダー: Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

カタログ ID は `provider/model` 形式です（例: `jina-ai/jina-embeddings-v5-omni-small`）。レジストリに存在する、プロバイダー名を含まない Jina モデル ID（例: `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）も解決されます。Jina の埋め込み／リランキング／分類／セグメンテーションでは、まずダッシュボードの `jina-ai` 認証情報が使用されます。`JINA_AI_API_KEY` は、ダッシュボードキーが存在しない場合にのみフォールバックとして使用されます。`jina-reader` カードは Reader / `r.jina.ai` 専用（`POST /v1/web/fetch`）であり、埋め込みやリランキングには使用されません。

マルチモーダル対応を明示しているレジストリモデルは、プロバイダーに依存しない構造化
項目を最大 32 個まで受け付けます。メディア項目のタイプは `text`、`image`、`audio`、`video`、`document` です。メディアの `source`
には、`{"type":"url","url":"https://..."}` または
`{"type":"base64","data":"...","media_type":"..."}` を指定します。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`、
およびファミリーエイリアス `jina-ai/jina-embeddings-v5-omni` → omni-small）は、Jina ネイティブの
EmbeddingsV5Request ドキュメントも受け付け、`https://api.jina.ai/v1/embeddings` に**そのまま転送します**。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ネイティブの `{ image | audio | video | pdf }` 値には、公開 HTTPS URL、`data:` URI、または未加工の
base64 を指定できます。OmniRoute はこれらのオブジェクトを文字列化せず、ネイティブの画像 URL も取得しません。公開メディアは
Jina 自身が取得します。追加の Jina フィールド（`task`、`normalized`、`truncate`、`embedding_type`）も
転送されます。テキスト専用の Jina SKU は、引き続きテキスト以外のドキュメントを拒否します。

セキュリティおよび転送に関する制限:

- リモートメディア URL は、公開 HTTPS である必要があります。標準形式の `{type,source:url}` 項目は
  サーバー側で取得され（リダイレクトの再検証、タイムアウト、サイズ制限、公開 DNS、接続のピン留め）、
  プロバイダー呼び出しの前にインライン化されます。Jina ネイティブの `{image:"https://..."}` 項目は、
  同じ公開 HTTPS チェックの後、そのまま転送されます。URL は Jina が取得します。
- インライン base64 メディアは、デコード後のサイズが項目ごとに 8 MiB、リクエスト全体で 16 MiB に制限されます。

プロバイダー向け変換（標準形式の項目が変更されずに転送されることはありません）:

- Jina マルチモーダルモデル: 各トップレベル項目は、インラインメディアにデータ URI を使用する、
  モダリティをキーとした単一のオブジェクト（`text` / `image` / `audio` / `video` / `pdf`）になります。
  トップレベル項目ごとに 1 つのベクトルが生成されます。
- Gemini Embedding 2 ファミリー: 1 つのトップレベル配列は、`content.parts`（`text` または `inline_data`）を含む
  単一のネイティブ `models/{model}:embedContent` リクエストになります。
- llama.cpp（`llama-cpp/<model>`、ローカルサーバーが読み込んだ任意のモデル）: 標準形式の `text` 項目は
  プレーン文字列になり、`image` / `audio` / `video` はそれぞれ 1 つの
  `{"content": [part]}` オブジェクトになります。インラインデータを含む llama-server のチャットコンテンツパーツ
  （`image_url`、形式が `wav` / `mp3` / `flac` の `input_audio`、`input_video`）を使用し、
  トップレベル項目ごとに 1 つのベクトルが生成されます。サーバーは `--embedding --mmproj …` を指定して
  実行する必要があります。プロジェクターがない場合、サーバー自身がメディアを拒否します。`document` はサポートされていません。
- 明示的なモダリティメタデータを持たない不明なモデル／動的モデルは、構造化入力を HTTP 400 で拒否します。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

サポートされていないモデルとモダリティの組み合わせでは、項目を強制変換せず HTTP 400 を返します。従来の文字列／トークンリクエストに含まれる
入力以外の拡張フィールドは、引き続き変更されずにそのまま渡されます。

```bash
# すべての埋め込みモデルを一覧表示
GET /v1/embeddings
```

## 画像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

利用可能なプロバイダーには、OpenAI (GPT Image 2)、xAI (Grok Image)、Together AI (FLUX)、Fireworks AI、Nebius (FLUX)、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（ローカル）、ComfyUI（ローカル）が含まれます。

`n` は、`data[]` 内に `n` 個の画像を返します。アップストリーム API が呼び出しごとに 1 つの画像を返すプロバイダー
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI）では、`n` 回の個別アップストリーム呼び出しが行われ、同時実行数は最大 4 です。
固定の `seed` は呼び出しインデックスに応じてオフセットされるため（`seed`、`seed + 1`、…）、画像は異なりつつも
再現可能な状態が保たれます。`n` の上限は 10 です。いずれかの呼び出しが失敗すると、リクエスト全体が失敗します。
ファンアウト形式の一覧は、
`open-sse/handlers/imageGeneration/fanOut.ts` の `SINGLE_IMAGE_FANOUT_FORMATS` にあります。

ZenMux は既存の API キー接続を再利用し、`zenmux/` または `zm/` プレフィックスを受け付けます。

- `zenmux/openai/gpt-image-2` は、ZenMux の OpenAI Images API を使用します。オプションには `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background`、`response_format` があります。
- `zm/meta/muse-image-1.0` などのその他のパブリッシャーは、ZenMux の Vertex AI `:predict`
  エンドポイントを使用します。`n` は `sampleCount`、`aspect_ratio` は `aspectRatio`、`image_size`
  （`1K`、`2K`、`4K`）は `sampleImageSize` にマッピングされます。ピクセル単位の `size` はアスペクト比のみを指定し、
  ピクセル寸法は保証されません。サポートされる比率、解像度、生成数はモデルによって異なります。
- `zm/inclusionai/ming-image-0.1-design` は、独自に寸法を選択します。`size`、
  `aspect_ratio`、`image_size` は省略してください。明示的に値を指定すると HTTP 400 が返されます。PNG、JPEG、WebP
  は `output_format` で指定できます。

この統合は、参照画像の編集ではなく、テキストからの画像生成をサポートします。Vertex
の出力は `data[].b64_json` に正規化されます。`response_format: "url"` は、アップストリームの
HTTPS URL、または画像バイトのみが利用可能な場合は base64 データ URL を返します。空またはフィルタリング済みの出力では、
空の成功レスポンスではなくエラーが返されます。モデルへのアクセス可否は ZenMux アカウントによって異なります。
[ZenMux の Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) および
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) を参照してください。

```bash
# すべての画像モデルを一覧表示
GET /v1/images/generations
```

## ドキュメント OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` は、`provider/model` プレフィックスを使用して OCR プロバイダーを選択します。プレフィックスのないモデル ID（例：
`mistral-ocr-latest`）は登録済みプロバイダーに解決され、`model` を省略すると
Mistral（`mistral-ocr-latest`）がデフォルトになります。登録済みプロバイダー（`open-sse/config/ocrRegistry.ts`）：

| プロバイダー ID               | モデル ID            | `model` の値                                                                    | 備考                                                                                                                           |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（またはプレフィックスなしの `mistral-ocr-latest`） | 同期処理 — 単一のアップストリーム呼び出しからレスポンスが直接返されます。                                                      |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                                     | 非同期アップストリーム（`analyze` + ポーリング）— 以下を参照してください。                                                     |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                         | Vertex AI の `openapi/chat/completions` パートナーエンドポイント経由の同期処理 — 認証と URL については以下を参照してください。 |

3 つのプロバイダーはすべて、同じ Mistral 形式のボディで応答します。

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence のポーリングフロー

Azure Document Intelligence の `analyze` API は非同期です。最初のリクエストではボディの代わりに
`Operation-Location` ヘッダーが返されるため、結果をポーリングする必要があります。ハンドラー
（`open-sse/handlers/ocr.ts`）は、その URL を 1 秒ごとに最大 30 回ポーリングします。`ok` ではないポーリングレスポンスまたは
`"failed"` ステータスを受け取ると即座に失敗し（ポーリングを継続せず）、試行回数の上限に達した後も
処理が実行中の場合は `504` を返します。最終的な Azure レスポンスは、呼び出し元に返される前に、
Mistral で使用されるものと同じ `pages`/`markdown` 形式へ正規化されるため、クライアントコードで
プロバイダーごとの特別な処理を行う必要はありません。

### Vertex AI DeepSeek OCR の認証とエンドポイント解決

`vertex-deepseek-ocr` は、チャットおよび画像トラフィック向けに OmniRoute がすでにサポートしているものと同じ
Vertex AI 認証（`open-sse/executors/vertex.ts`）を再利用します。接続の API キーには、
Service Account JSON 認証情報（JWT-bearer フローを介して有効期間の短い OAuth アクセストークンに交換される）、
またはすでに発行済みの OAuth アクセストークンをそのまま使用できます。アップストリームエンドポイント URL は Vertex の
汎用 `openapi/chat/completions` パートナーエンドポイントであり、接続のプロジェクトとリージョンから構築されます。
明示的な `providerSpecificData.project`/`providerSpecificData.region` が常に優先されます。
それ以外の場合、プロジェクトは Service Account JSON の `project_id` から取得され、リージョンの
デフォルトは `us-central1` です。どちらの解決処理も `open-sse/handlers/ocr.ts`
（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`）で行われ、
`handleOcr` にディスパッチする前に `src/app/api/v1/ocr/route.ts` によって使用されます。

### モデル価格（`pricing`）

OmniRouteがモデルの価格を把握している場合、エントリには`pricing`オブジェクトが含まれます。価格は、
コスト計算で使用される価格表（組み込みのデフォルト、同期された価格、および
`/api/pricing`を通じて設定されたオーバーライド）から取得されます。これらは定価であるため、サブスクリプションプロバイダーにも
トークン単位の価格が表示されます。

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| フィールド                                                      | 単位                            | 注記                                                                                                                                                |
| --------------------------------------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | トークンあたりのUSD、10進文字列 | OpenRouter互換で、指数表記にはなりません。2つのキャッシュフィールドは、キャッシュ価格が存在する場合にのみ表示されます。                             |
| `input`, `output`, `cached`, `cache_creation`                   | 100万トークンあたりのUSD、数値  | 以前のカタログバージョンのフィールドで、既存クライアント向けに維持されています。価格行に値がある場合は、`reasoning`と`long_context`も表示されます。 |

- **コンボ**には、最初に表示されるターゲットの価格が設定されます。組み込みの`auto/*`コンボは
  リクエスト時にターゲットを選択するため、`pricing`はありません。
- **無料モデル**は、価格がゼロの場合に`"0"`（および`0`）を表示します。価格行がないモデルでも、
  カタログで無料とマークされている場合（`free: true`）、または組み込みの無料モデル
  カタログに含まれている場合は`"0"`を表示します。
- **価格不明:** エントリには`pricing`キーがありません。
- **クレジット従量制プロバイダー**（Kiroなど）は、トークン単位ではなくリクエスト単位で課金します。その
  エントリでは以前からの100万トークンあたりの数値フィールドが維持され、トークン単位の文字列フィールドは含まれません。
- **バリアント**（reasoning-effort ID、no-thinkingエイリアス、ディスカバリーおよびゲートウェイのミラー）は、
  ルーティング先モデルの価格をコピーします。
- 各フィールドには基本料金のみが含まれます。ロングコンテキスト階層（数値の`long_context`フィールド）および
  サービス階層の乗数（Codex fastやflexなど）によって`prompt`や
  `completion`が変わることはありません。
- このオブジェクトは、`x-api-key`と`anthropic-version`を使用するAnthropic形式の
  リクエストを含め、すべての認証方式で同一です（レスポンスは`{ "object": "list",
"data": [...] }`のままです）。実装: `src/app/api/v1/models/catalogPricing.ts`。

### モデルIDのプレフィックス（`?prefix=`）

ほとんどのモデルは**プロバイダープレフィックス**付きで公開されます。使用されるプレフィックスは
`MODELS_CATALOG_PREFIX_MODE`機能フラグによって制御され、クエリパラメーターで**リクエストごとに**
オーバーライドできます。これは、すべてのユーザーに対するサーバー全体の設定を変更せずに、
整理されたリストを必要とするクライアントに便利です。

```bash
GET /v1/models?prefix=alias        # モデルごとに1つのID — 短いエイリアスプレフィックス
GET /v1/models?prefix=dual         # 両方の形式（サーバーのデフォルト）
GET /v1/models?prefix=canonical    # 完全なプロバイダーIDプレフィックスのみ
```

| モード      | 出力                                                         | 注記                                                                                                                                                                                         |
| ----------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **および** `claude/claude-sonnet-4-6` | **デフォルト。** 両方のIDは同じモデルにルーティングされます。いずれかの形式をハードコードしたクライアント設定が引き続き機能するよう維持されています。カタログのサイズはおよそ2倍になります。 |
| `alias`     | `cc/claude-sonnet-4-6`                                       | モデルごとに1つのエントリ。個別のエイリアスがないプロバイダーもエントリを出力するため、何も失われません。                                                                                    |
| `canonical` | `claude/claude-sonnet-4-6`                                   | 完全なプロバイダーIDプレフィックスの下にモデルごとに1つのエントリ。個別のエイリアスがないプロバイダー（例: `antigravity/…`、`agy/…`）も、ここでは単一のIDを出力するため、何も失われません。  |

`dual`モードのミラーは、クエリパラメーターがなくても識別できます。プライマリIDを指す`parent`
フィールドが含まれます。

モデル選択画面を表示するクライアントは`?prefix=alias`をリクエストする必要があります。これは
[OmniCopilot VS Code拡張機能](../guides/VSCODE-COPILOT.md)で採用されている方式です。

### ディスカバリーフィルター（`?capability=`、`?min_context=`、`?kind=`、`?q=`）

`GET /v1/models`は、オプトインのディスカバリーフィルターを受け付けます。いずれも指定しない場合、
レスポンスは変わりません。呼び出し元がすでに参照可能なカタログを絞り込み（APIキーの権限が先に適用されます）、
OpenAI形式の`limit` / `after`ページングより前に実行されます。

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 列挙されたすべての機能がtrueである必要があります
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # カタログの`type`。これがない行は`chat`です
GET /v1/models?q=sonnet&limit=10                           # IDまたは名前に対する大文字と小文字を区別しない一致
```

| パラメーター  | 値                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | 0 以上の整数。`context_length` と比較されます                                                       |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1～200 文字                                                                                         |

不明な値、または 0 以上の整数ではない `min_context`（例: `1.5`）を指定すると、
HTTP `400` が返され、メッセージに有効な値の一覧が示されます。実装:
`src/app/api/v1/models/catalogFilters.ts`。

### モデル候補リスト（`POST /v1/models/query`）

`POST /v1/models/query` は、`GET /v1/models` と同じカタログから、同じ認証およびキーごとの可視性に基づいて、
短い決定的なリストを返します。

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

すべてのフィールドは省略可能です。`capabilities` と `exclude` には配列またはカンマ区切りの文字列を指定できます。
`max_output` は `max_output_tokens` と比較されます。結果は `owned_by`、次に `id` の順でソートされます。
`limit` のデフォルトは `20` で、`100` を超える値は `100` に制限されます。無効な JSON、不明な
フィールド、または無効な値を指定すると HTTP `400` が返されます。

### 個別に非表示にされたチャットモデル

プロバイダーページで **非表示** に設定されたモデルはカタログから除外され、明示的にリクエストされた場合は
HTTP `404` / `model_not_found` で拒否されます。このチェックでは、プロバイダーエイリアス、互換プロバイダーのノードプレフィックス、
および接続のデフォルトを含め、解決済みのプロバイダーとモデルが使用されます。コンボは非表示のターゲットをスキップし、
表示されている同系列のモデルを使用できます。実行可能なターゲットが残っていない場合は、同じエラーコードを返します。
非表示を解除すると、次のリクエストから反映されます。画像専用の可視性オーバーライドによって、同じ ID のチャットモデルが
非表示になることはありません。

このモデルごとの設定は、[モデル公開の許可／拒否リスト](../routing/MODEL_EXPOSURE_LIST.md)とは別のものです。
これらのリストは、明示的なディスパッチを維持しながら、カタログへの掲載と自動ルーティングの候補をフィルタリングします。
API キーのモデル権限も、引き続き独立して適用されます。デフォルトのカタログプレフィックスモードは `dual` のままです。

### 思考なしモデルバリアント

思考機能に対応する Claude モデルについては、`/v1/models` で ID の先頭に `claude-3-omniroute-no-thinking/` が付いた **思考なし** バリアントも公開されます。

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

この ID を選択すると（たとえば、常に `thinking` ブロックを付加する Claude Code の設定内で指定すると）、推論を抑制した状態で実際の `<provider>/<model>` に解決されます。つまり、`/v1/messages` パスでは `thinking:{type:"disabled"}` が指定され、`/v1/chat/completions` パスでは `reasoning`/`reasoning_effort` フィールドが除去されます。このバリアントは、思考機能に対応し、**かつ** `disabled` を受け付ける Claude ファミリーのモデルに対してのみ掲載されます（したがって、`disabled` を拒否する適応型専用モデルなどは除外されます）。運用者は、`ModelSpec.noThinkingAlias` を使用して、モデルごとにこのバリアントを強制的に有効または無効にできます。

## ElevenLabs オーディオ生成

ElevenLabs API キーを使用して、OmniRoute に `elevenlabs` プロバイダー接続を設定します。
クライアントは自身の **OmniRoute** キー（`Authorization: Bearer $OMNIROUTE_API_KEY`）で認証します。ゲートウェイは、保存されているプロバイダーキーを `xi-api-key` として送信します。ElevenLabs キーをゲートウェイの Bearer トークンとして送信しないでください。

| メソッド | パス                        | レスポンス                                               | API キーのエンドポイントカテゴリー |
| -------- | --------------------------- | -------------------------------------------------------- | ---------------------------------- |
| POST     | `/v1/sound-generation`      | ネイティブオーディオバイト                               | `elevenlabs`                       |
| POST     | `/v1/music`                 | ネイティブオーディオバイト                               | `music`                            |
| POST     | `/v1/music/stream`          | ストリーミングオーディオバイト                           | `music`                            |
| POST     | `/v1/music/detailed`        | ネイティブのマルチパート形式のオーディオおよび構成プラン | `music`                            |
| POST     | `/v1/music/detailed/stream` | ネイティブ SSE メタデータおよびオーディオチャンク        | `music`                            |
| POST     | `/v1/music/plan`            | JSON 構成プラン                                          | `music`                            |

これらのエンドポイントは、既存の `/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/voices`、`/v1/text-to-speech/{voiceId}`、および `/v1/speech-to-text` ルートを補完します。`output_format` や `enable_logging` などのネイティブ JSON フィールドとクエリパラメーターは保持されます。
`/v1/music/detailed` のレスポンスではマルチパート境界が保持されるため、マルチパートとして解析してください。
`/v1/music/detailed/stream` は、構成メタデータと base64 オーディオチャンクを SSE イベントとして含む `text/event-stream` を返します。6 つすべてのルートが CORS プリフライトをサポートします。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 短い効果音。長さ：0.5～30 秒。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 音楽の長さはミリ秒単位で指定します：3000～600000。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

オーディオを段階的に配信するには、同じ JSON ボディで `/v1/music/stream` を使用します。構成では `prompt` または `composition_plan` のいずれか一方のみを指定できます。`/v1/music/plan` では `prompt` が必須で、必要に応じて `source_composition_plan` も指定できます。ネイティブスキーマでは追加のプロバイダーフィールドが保持されるため、構成プランのバージョンや微調整オプションが ElevenLabs に渡されます。

統合 `/v1/music/generations` エンドポイントも、`elevenlabs/music_v1`、`elevenlabs/music_v2`、および `elevenlabs/music_v2_5` を受け付けます。有効な ElevenLabs 接続がある場合、これらのモデルは音楽カタログに表示されます。このエンドポイントは `{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` を返します。このエンドポイントの `duration` フィールドは秒単位であり、`music_length_ms` にマッピングされます。`music_length_ms` が明示的に指定されている場合は、そちらが優先されます。
`instrumental` は `force_instrumental` にマッピングされ、ネイティブフィールドが優先されます。
ストリーミングにはネイティブのストリーミングエンドポイントを使用し、構成プランのみを使用するリクエストにはネイティブの構成エンドポイントを使用してください。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

アップストリーム呼び出しの前に、エンドポイント、モデル、予算、および接続に関する制限が適用されます。ネイティブルートは、プラン制限を示す `402` やクォータ上限を示す `429` を含め、アップストリームのステータスコードとエラーボディを変更せずに返します。`character-cost`、`song-id`、`request-id`、および `retry-after` ヘッダーは、存在する場合に保持されます。無料クレジット残高があっても、すべての音楽モデル、出力形式、または API 機能へのアクセスが保証されるわけではありません。各リクエストの利用資格は ElevenLabs が決定します。
統合エンドポイントでは、OmniRoute の正規化されたエラーエンベロープ内にエラーステータスコードが保持されます。

アップストリームのコントラクト：[効果音](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音楽構成](https://elevenlabs.io/docs/api-reference/music/compose)、および
[ストリーミング音楽の詳細](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。


> **リランキングプロバイダーノード:** `POST /v1/rerank` は、`<node-prefix>/<model>` として指定された
> OpenAI 互換プロバイダーノード（oMLX、vLLM、Infinity、ゲートウェイ背後の TEI など）にもルーティングされます。
> ループバックノード（`localhost`、`127.0.0.1`、`172.16.0.0/12`）は常に利用対象となり、オペレーターが
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` に指定したホスト名も対象になります（例:
> `http://reranker:8080/v1` のような Docker/Compose サービス名。これらは直接呼び出され、
> `HTTP(S)_PROXY` や接続に固定されたプロキシを経由することはありません）。それ以外の
> ホスト上のノード（LAN 内のマシンや Tailscale ピアなど）は、オペレーターが
> `RERANK_REMOTE_PROVIDER_NODES` 機能フラグを有効にし、かつノードのベース URL がプロバイダーの
> アウトバウンド URL ポリシー（`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）を
> 満たす場合にのみ利用できます。メモリエンジンのリランキング処理は、このルートを
> ループバック経由で呼び出すため、Memory 設定の `rerankProviderModel` にも同じルールが適用されます。
>
> **ローカルサーバーの形式:** ノードは `<base>/v1/rerank` で呼び出され、404 の場合は
> `<base>/rerank`（Infinity、TEI）で呼び出されます。アップストリームのボディには、
> Cohere/OpenAI 形式（`documents`、`return_documents`）と TEI 形式（`texts`、`return_text`）の両方が含まれ、
> アップストリームのレスポンスは Cohere エンベロープに正規化されます。TEI の単純な
> `[{index, score, text}]`、薄いゲートウェイから返される `{results: [{index, score}]}`、
> および Voyage 形式の `{data: [...]}` はすべて、スコア順に並べられ、`top_n` を上限として、
> `{results: [{index, relevance_score, document?}]}` の形式でクライアントに返されます。

> **プロバイダーノードの検出:** OpenAI 互換プロバイダーノード上のモデルは、ノードのプレフィックス配下で
> `GET /v1/models` に表示されます。エンドポイントのメタデータを持たない行（ローカルの
> `/v1/models` 一覧では一般的）はノードの `apiType` を継承するため、`embeddings` ノードのモデルは
> デフォルトでチャットになる代わりに `type: "embedding"` となり、`rerank` ノードのモデルは
> `type: "rerank"` となります。同期された行または手動で追加された行に明示的な
> `supportedEndpoints` がある場合は、引き続きそちらが優先されます。

### 専用プロバイダールート

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

プロバイダーのプレフィックスがない場合は、自動的に追加されます。一致しないモデルに対しては `400` が返されます。

## API検索

Web/searchプロバイダーの抽象化 (Tavily、Brave、Exa、Serper など)。

| 方法 | パス                   | 説明                                                                                                    |
| ---- | ---------------------- | ------------------------------------------------------------------------------------------------------- |
| GET  | `/v1/search`           | 構成された検索プロバイダーの+機能をリストする                                                           |
| POST | `/v1/search`           | 検索クエリを実行します。 —本体は`v1SearchSchema`によって検証され、 caching/coalescingをサポートします。 |
| GET  | `/v1/search/analytics` | プロバイダーごとのhit/latency/cache統計                                                                 |

**認証:**ベアラーAPIキー (`extractApiKey` + `isValidApiKey`)。検索ポリシーは`enforceApiKeyPolicy`経由で適用されます。

### エクサとタヴィリー`provider_options`

Exa と Tavily は、名前空間バッグからプロバイダー固有のフィールドを読み取ります: `provider_options.exa` (または`provider_options["exa-search"]`) および`provider_options.tavily` (または`provider_options["tavily-search"]`)。以下のキーのみが転送されます。それぞれが`open-sse/handlers/search/providerOptionsPassthrough.ts`内の独自のZodスキーマに対してチェックされ、間違ったタイプのキーは削除されます。 auth、base URL、 `stream` 、 `outputSchema`などの他のキーは無視されます。他のプロバイダー (`cx`、 `depth`) で使用されるフラット キーは以前と同様に機能します。

| プロバイダー | 最上位フィールド                                                                                                                                                                                                                                                                                                                                                          | 入れ子になった                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| エクサ       | `type`、 `category`、 `userLocation`、 `moderation`、 `additionalQueries`、 `objective`、 `systemPrompt`、 `compliance` (フラット プリミティブ)、 `startPublishedDate`、 `endPublishedDate`                                                                                                                                                                               | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}`デフォルトの`{ text: true, highlights: true }`上にマージされました |
| タヴィリー   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                               |

汎用フィールドが常に優先されます: `query`、 `max_results`、 `filters` (ドメイン)、 `country` 、および`search_type`から派生したトピック。 Exa では、 `search_type: "news"` `category: "news"`を保持します。 Tavily は`search_type: "finance"` (`topic: "finance"`) も受け入れます。

Firecrawl の検索コストは、返された 10 件の結果の開始ブロックごとに記録され、1 ブロックあたり 0.002 ドル (2 クレジット)、呼び出しごとに少なくとも 1 ブロック ( [Firecrawl の請求](https://docs.firecrawl.dev/billing)): 11 件の結果の費用は 0.004 ドルです。

汎用`time_range`両方のプロバイダーに到達するようになりました。Exa は`startPublishedDate` (ISOタイムスタンプ) を取得し、Tavily は`start_date` (`YYYY-MM-DD`) を取得します。 `provider_options`内の明示的な日付は、マップされた日付をオーバーライドします。

Exa の結果は、 `id`、 `highlight_scores`、 `summary`、 `subpages`、 `entities`および`extras`を`provider_raw`に保持します。 Tavily の結果は`images`と`favicon`を維持します。

リンクアップ検索コストは、 `depth` `provider_options`からのものか接続の設定からのものかに関係なく、 `depth` `fast`および`standard`については 0.005 ドル、 `deep`については 0.05 ドル ([リンクアップ価格設定](https://docs.linkup.so/pages/documentation/development/pricing)) で記録されます。

Exa `type: "lite"` (Exa 3.0) は、より小さいフィールドのセットを受け入れ、他のフィールドが設定されている場合はリクエスト全体を拒否します。 lite の場合、 `additionalQueries`、 `systemPrompt` 、および`text`と`highlights`を除くすべての`contents`キーは呼び出し前に削除されます。非推奨の`subpages`、 `subpageTarget`、 `highlights.numSentences`および`highlights.highlightsPerUrl`は転送されなくなりました。

原価計算はフラット レジストリ`costPerQuery`です。ただし Exa は Exa 独自の価格設定に従います。 `auto` (および従来の`fast`) の場合は呼び出しごとに 0.007 ドル、 `lite` (および従来の`instant`) の場合は 0.004 ドルで、10 件の結果がカバーされます。その後の結果ごとに 0.001 ドル。 `contents.summary`が設定されている場合は、返された結果ごとに $0.001 がかかります。 Tavily は、 `search_depth` `basic`、 `fast`および`ultra-fast`の場合は 1 クレジット ($0.008)、 `advanced` ( [Tavily APIクレジット](https://docs.tavily.com/documentation/api-credits)) の場合は 2 クレジット ($0.016) で記録されます。 Tavily がアドバンストにアップグレードした`auto_parameters: true`との通話は、引き続き 1 クレジットで記録されます。

## Web Fetch API

設定済みの Web Fetch プロバイダー（Firecrawl、Jina Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）を使用して、URL からコンテンツを抽出します。

Parallel Extract（`parallel-search`、Parallel Search と同じ API キー）は Markdown のみを返します。それ以外の `format` は `400` となり、コンテンツは 100,000 文字に制限されます。対象ページ自体を抽出できない場合、アップストリームは HTTP 200 内でその旨を報告します。OmniRoute はこれを固定メッセージ付きの `422` として返します。

| メソッド | パス            | 説明                                                                      |
| -------- | --------------- | ------------------------------------------------------------------------- |
| POST     | `/v1/web/fetch` | URL を取得／スクレイピング — リクエストボディは `v1WebFetchSchema` で検証 |

**認証:** Bearer API キー（`extractApiKey` + `isValidApiKey`）。ポリシーは `enforceApiKeyPolicy` によって適用されます。

**クォータを考慮したフォールバック（#8297）:** 明示的な `provider` が指定されていない場合、プール
（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`）を固定の
優先順位（先着充当方式）で
順に処理します。レート制限中ではあるものの設定済みのプロバイダーは、リクエストを即座に終了させるのではなくスキップされます。また、再試行可能なアップストリーム障害またはクォータ障害
（HTTP 429 は常に対象。Firecrawl/Tavily/TinyFish のクォータ方式の無料枠では 402/403 も対象。ただし
Jina Reader は対象外で、単純な 400 不正リクエストも対象外）は、リクエスト時に、まだ試行していない認証情報設定済みの
次のプロバイダーへフォールスルーします。プール内のすべてのプロバイダーを使い果たした場合、
エンドポイントは従来の汎用的な `400` ではなく、単一の `429`（`Retry-After`
ヘッダー付き）を返します。明示的な `provider` が要求された場合、
暗黙的なフォールバックは**行われません**。レート制限中または障害が発生している明示指定プロバイダーは、
自身のエラー（レート制限中の場合は `429`、それ以外の場合はアップストリームの
ステータス）をそのまま返します。

## WebSocket ストリーミング

```bash
GET /v1/ws?handshake=1
```

WebSocket アップグレードのハンドシェイクを検証し、ワイヤープロトコルのメッセージ例（`request`、`cancel`）を返します。実際の WS フレームは、Next.js のルートテーブル外にある同梱の WS サーバーによって処理されます。

**認証:** ハンドシェイク時の Bearer API キー。

### WebSocket 経由の Responses API（codex のみ）

```bash
# HTTP API と同じ host:port（デフォルトは 20128）を使用し、接続をアップグレードします:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （または: -H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 最初のフレームは response.create でなければなりません:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses API over WebSocket プロキシは、**`codex` のみに接続されます**（ChatGPT
バックエンド）。このプロキシは、API／ダッシュボードと同じポートのパス `/v1/responses`、
`/responses`、および `/api/v1/responses` でリッスンします。最初の `response.create` フレームで、
内部の `codex-responses-ws` ブリッジを介して認証と準備を行い、codex OAuth 接続を
選択し、`wreq-js` トランスポートを介して `wss://chatgpt.com/backend-api/codex/responses`
へトンネリングします。**codex 以外のモデルは拒否されます**（`codex_ws_provider_required`）。
クォータ共有ルーティングには `model: "qtSd/<group>/codex/<model>"` を使用してください。実装は
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`
にあります。

**認証:** ハンドシェイク時の Bearer API キー。同梱の HTTP サーバー（`server-ws.mjs`）が
有効なエントリーポイントである必要があります（`app/server-ws.mjs` が存在する場合、デフォルトでそうなります）。

#### モデル ID: ChatGPT のベア ID を使用（`codex/` プレフィックスなし）

OpenAI **Codex CLI** は、`supports_websockets = true` の場合にクライアント側でモデル名を検証し、
`codex/gpt-5.5` のような**プロバイダープレフィックス付き ID を拒否します**
（`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`）。
**ベア** ID（例: `gpt-5.5`）を送信してください。OmniRoute のブリッジは
codex 専用であるため、アップストリームへトンネリングする前に、ベア ID を codex モデルとして
再解決します（`resolveCodexWsModelInfo`）。これは、ベア
`gpt-5.5` が HTTP 経由では本来、別のプロバイダーへルーティングされる場合でも同様です。

#### OpenAI Codex CLI の設定

WebSocket をサポートするカスタムプロバイダーを `~/.codex/config.toml` に追加し、
Codex CLI の接続先を OmniRoute に設定します（既存の設定に影響を与えないよう、別の `CODEX_HOME` を使用してください）。

```toml
model = "gpt-5.5"                 # ベア ID — "codex/gpt-5.5" ではありません
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 末尾のスラッシュは不要です。WS URL はここから導出されます（本番環境では https/wss を使用してください）
wire_api = "responses"                    # 2026 年 2 月以降、サポートされる唯一の値です
supports_websockets = true                # Responses-over-WS トランスポートを有効にします
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API キー（Bearer）を保持します
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API キー（REQUIRE_API_KEY=false の場合は任意のキー）
codex exec "Responda apenas: PONG"
```

CLI は `base_url + /responses` を WebSocket にアップグレードし、OmniRoute は選択された
codex OAuth 接続へトンネリングします。ローカル
サーバーに対するエンドツーエンド検証済みです。ChatGPT は `codex.rate_limits` + `response.created` を返し、補完を
ストリーミングします。

## セルフサービスでの使用状況確認（`/api/usage/om-usage`）

どの API キーでも、管理者認証なしで**自身の**使用状況とクォータを確認できます。これは、
クライアント（CLI、OmniCopilot パネル）がキーホルダーに利用料金を表示するために使用するエンドポイントです。

```bash
# テキスト形式（従来からの仕様 — ターミナル向けのプレーンテキスト）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 構造化形式 — UI が使用する形式
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

キーでは **`allowUsageCommand`** が有効になっている必要があります（デフォルトでは無効です。ダッシュボードの API キー
マネージャーでキーごとに切り替えられます）。有効でない場合、エンドポイントは `403` を返します。

`?format=json` は判別可能な構造を返すため、呼び出し元が拒否レスポンスから誤ってデータフィールドを読み取ることはありません。
成功時:

```jsonc
{
  "allowed": true,
  // キーでキー単位の使用上限（日次／週次、USD）が有効になっている場合にのみ存在します:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 選択されたプロバイダーのクォータスナップショット。まだ何もキャッシュされていない場合は null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // UI で複数のプロバイダーを並べて表示できるようにする、全接続のスナップショット:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

拒否時（`401` は無効なキー／`403` は許可されていない場合）、同じルートは
`{ "allowed": false, "error": { "message": "…" } }` を返します。`personal`／`provider` が存在するものの空である状態
（キーは許可されているが、まだ情報が取得されていない状態）は拒否とは異なり、この違いを判別できるのは JSON 形式
のみです。

**認証:** 呼び出し元自身の Bearer API キー。`isValidApiKey` で検証されます。これは
管理インターフェース（`/api/keys/…`）ではありません。管理インターフェースは引き続き `requireManagementAuth` によって保護されます。

### 未調整のクォータ割合とカットオフ調整済みのクォータ割合

`/api/usage/om-usage` を利用する場合、呼び出し元は**プレーンテキスト出力**と構造化された
**JSON 出力**で示される割合の違いに注意する必要があります。

| 項目                       | プレーンテキスト形式（`/api/usage/om-usage` / `@@om-usage`）                                | JSON 形式（`?format=json`）                                              |
| :------------------------- | :------------------------------------------------------------------------------------------ | :----------------------------------------------------------------------- |
| **出力フィールド**         | `NN% left`（例: `20% left`）                                                                | `provider.quotas` / `providers[].quotas`                                 |
| **測定値**                 | **カットオフ調整済みの使用可能枠**: カットオフしきい値を超える残り容量                      | **未調整の上流クォータ**: プロバイダーによる未調整の測定値               |
| **カットオフスケーリング** | 保護された予備枠が `0% left` と表示されるよう、`effectiveRemainingPercent()` でスケーリング | なし（プロバイダーから報告された未加工のスナップショット値）             |
| **しきい値データ**         | 表示される割合に反映                                                                        | 接続ごとの `quotaWindowThresholds`（またはサーバーのデフォルト値）に保存 |
| **主な利用者**             | 対話型 CLI、ターミナルプロンプト、人間のオペレーター                                        | プログラムによる連携、ダッシュボード、分析、課金トラッカー               |

#### カットオフ調整の計算式

OmniRoute は、上流のクォータ枯渇を防止するため、予防的なクォータカットオフをサポートしています（接続の
`quotaWindowThresholds`、プロバイダーのデフォルト値、またはグローバルなレジリエンス設定で構成します）。クォータウィンドウでカットオフしきい値
（例: `cutoff = 25%`）が有効な場合、テキストレンダラーは残りの使用可能枠を次のように計算します。

- `remaining <= cutoff` の場合: `0%` を返します。
- `remaining > cutoff` の場合: `((remaining - cutoff) / (100 - cutoff)) * 100` を返します。

整形されたテキスト出力では、最も近い整数に丸められます（`Math.round(...)`）。

#### 具体例

**未調整の使用率が 60%**（したがって**未調整の残りクォータは 40%**）で、設定された
**残りクォータのカットオフしきい値が 25%** のプロバイダーウィンドウを考えます。

| 表現                                | 計算                                               |  残り   |                推定使用済み                 |
| :---------------------------------- | :------------------------------------------------- | :-----: | :-----------------------------------------: |
| **未調整の JSON（`?format=json`）** | 上流スナップショット（`quotas[window]`）           | **40%** |                   **60%**                   |
| **テキスト形式（`NN% left`）**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%**（`100 - remaining` で計算する場合） |

- **テキストに残り 20% と表示される理由:** アカウントに物理的に残っている 40% のクォータのうち、25% は
  カットオフポリシーによって予約されています。ルーターがこの接続へのルーティングを停止するまでに、呼び出し元が使用できる残りの余裕は、
  使用可能な 75% のうち 15% のみです。スケーリングにより、ルーティングが停止する正確な時点で、
  接続が枯渇状態（`0% left`）を示すようになります。
- **JSON が未調整の値を維持する理由:** JSON ペイロードはプロバイダーの正確なスナップショット（`UsageSnapshot`）を返すため、
  外部ツールは、サーバー側で情報が失われるスケーリングを適用されることなく、信頼できる上流の使用状況と接続レベルの
  `quotaWindowThresholds` にアクセスできます。

#### 利用側の移行ガイダンス

外部インテグレーション（エディタープラグインやエージェント拡張機能など）が以前にテキスト
エンドポイント（`NN% left`）をスクレイピングし、使用済みの割合を `100 - NN` として計算していた場合、`?format=json` への移行により、次のようになります。

- 生の JSON 値を読み取ると、**実際のアップストリーム消費量**（上記の例では 60% 使用済み）が反映されます。
- インテグレーションがテキストエンドポイントの使用可能枠のセマンティクスを維持する場合は、
  接続レベルのオーバーライドに `quotaWindowThresholds` を使用して、クライアント側で有効な残量の計算式を評価できます。

## セマンティックキャッシュ

```bash
# キャッシュ統計を取得
GET /api/cache/stats

# すべてのキャッシュをクリア
DELETE /api/cache/stats
```

レスポンス例:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### レイテンシへの影響

セマンティックキャッシュがヒットした場合、レスポンスはキャッシュから返され、**アップストリーム
呼び出しは行われない**ため、報告される `X-OmniRoute-Response-Latency` はほぼゼロになります
（元のアップストリームレイテンシには関係ありません）。レイテンシに敏感なクライアント
（ベンチマーク、p50/p99 モニタリング）は、
`X-OmniRoute-Cache-Latency` レスポンスヘッダーを確認する必要があります:

| 値          | 意味                                                                                   |
| ----------- | -------------------------------------------------------------------------------------- |
| `synthetic` | キャッシュから返されたレスポンス。レイテンシは実際のアップストリーム時間ではありません |
| _(なし)_    | 実際のアップストリーム呼び出しからのレスポンス                                         |

### キー単位のキャッシュバイパス

API キーでは、`cacheDefaultMode` を使用してセマンティックキャッシュの読み取りを無効にできます:

| 値       | 動作                                                             |
| -------- | ---------------------------------------------------------------- |
| `legacy` | 通常のキャッシュ動作（デフォルト）                               |
| `bypass` | キャッシュ検索を完全にスキップし、常にアップストリームへアクセス |

キーの作成時（`POST /api/keys`）または更新時（`PATCH /api/keys/[id]`）に設定します:

```json
{ "cacheDefaultMode": "bypass" }
```

### リクエスト単位のバイパス

キー設定に関係なく、任意のリクエストでキャッシュをバイパスできます:

```
X-OmniRoute-No-Cache: true
```

同期またはインポートされたモデルの場合、`PUT /api/provider-models` は `provider`、`modelId`、および
`maxOutputTokenOverride` を受け付けます。正の整数を指定すると出力トークンの上限が手動で設定され、`null`
を指定するとその設定が解除されてデフォルトに戻ります。`GET /api/provider-models?provider=<provider>` は、
カスタムモデルの行がないモデルも含め、これらの値を `modelOutputOverrides` で返します。このオーバーライドは
ランタイムの `max_output_tokens` 機能を使用し、モデルを再同期しても維持されます。OpenAI 互換
プロバイダーページには同じ編集および解除コントロールがあり、明示的にビジョンをサポートするモデルにはマークが付きます。

カスタム Chat Completions ノードは、明示的な推論のオプトアウトをアップストリームバックエンドに適合させます。
接続テストが成功すると、`/models` のエントリで認識済みの `owned_by` 値（`vllm`、`sglang`、または `llamacpp`）
が確認された各モデル ID に対して、チャットテンプレートコントロールが自動的に選択されます。
透過的な OpenAI 互換ラッパーでは、元のモデルエントリがネストされた `openai` オブジェクト内に保持される場合があります。
検出では、このようなエンベロープを最大3階層まで追跡します。所有者情報が欠落している、不明である、または
競合しているモデルでは、通常の OpenAI の動作が維持されます。検出では既存のカタログリクエストを再利用し、
補完トークンは生成されません。また、接続エンドポイントが変更されると検出結果は無効になります。

このメタデータを公開しないバックエンドで動作を固定するには、既存の部分的な
プロバイダー更新 API を使用します。

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

この本文を `PUT /api/providers/<connection-id>` で送信します。その接続では、明示的な
推論強度 `none` は `chat_template_kwargs.thinking=false` および
`chat_template_kwargs.enable_thinking=false` として送信されます。サーバー側の推論ルールによって
推論強度が強制されない限り、明示的なネイティブテンプレート値が優先されます。この設定は、カスタムの
OpenAI 互換接続が Chat Completions の本文を送信する場合にのみ適用されます。Responses リクエストと通常の
プロバイダーでは、ネイティブのリクエスト形式が維持されます。通常の OpenAI の
`reasoning_effort` パススルーを強制するには `reasoningControl` を `openai` に設定し、自動検出を使用するには
省略するか `null` に設定します。

Claude Code の自動モード分類器リクエストでは、明示的な推論コントロールが含まれていない場合、
ネイティブ thinking がデフォルトで無効になります。検出には、モデル名や補完上限ではなく、Claude 形式の
リクエストに含まれる分類器のシステムマーカーが使用されます。明示的な本文コントロール、サポートされている
effort/thinking ヘッダー、ルーティングルール、および解決済みのモデル推論強度は、既存の優先順位を維持します。
分類器の両ステージでは、プロンプト、補完上限、停止シーケンス、および実際のアップストリーム権限判定が維持されます。
第2ステージでは、要求された可視の推論を通常のテキストとして引き続き生成できます。

### バージョンとリリースチャネル

```bash
GET /api/system/version
```

ループバック専用の管理ルート（管理者認証）。実行中のバージョン、最新の
公開済みバージョン、および自動更新の状態を返します。`releaseChannel` と `channels` は追加
フィールドです（rail 3.8.54）。`channel` の意味は変わらず、ダッシュボードのアップデーターが
使用するデプロイモード（`npm`、`source`、または `docker-compose`）を示します。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 実行中のビルドの npm チャネル: `-nightly.*` バージョンの場合は `nightly`、
  その他のプレリリース（`-rc.*`、`-beta.*`、`-alpha.*`）の場合は `next`、`channels.latest` より
  古いメジャーの安定版の場合は `lts`、それ以外は `latest`。公開時に npm dist-tag を選択する
  `scripts/release/dist-tag.mjs` と同じルールです。
- `channels` — `npm view omniroute dist-tags`（レジストリ HTTP フォールバック）から取得した
  各 dist-tag の公開済み最新バージョンで、`latest` と同じ 10 分間の TTL でキャッシュされます。
  `latest` は常に存在します（`latest` フィールドにフォールバックし、さらに `"unavailable"` に
  フォールバックします）。`next`、`nightly`、`lts` は、その dist-tag が存在する場合にのみ
  表示されます。`Cache-Control: no-cache` リクエストを使用すると、両方の検索結果が更新されます。

チャネルモデル（`latest` = 4.0 GA までは v3、`next` = rc、`nightly` = `develop` ビルド、
`lts` = 4.0 GA 後の v3 パッチ）については、`docs/ops/RELEASE_STRATEGY.md` を参照してください。

## トークン制限

API キーごとの **トークン** 予算（上記の USD ベースの予算とは別）。リクエスト処理経路内で適用され、キーの現在のウィンドウ使用量が上限に達すると、リクエストは `429 Too Many Requests` で拒否されます。制限は、特定の `model`、`provider`、またはキー全体に対して `global` に設定できます。複数の制限がリクエストに一致する場合は、最も厳しい制限が優先されます。

```bash
# キーのトークン制限を一覧表示（現在のウィンドウ使用量を含む）
GET /api/usage/token-limits?apiKeyId=key-123

# トークン制限を作成または更新
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ID を指定してトークン制限を削除
DELETE /api/usage/token-limits?id=tl-abc
```

> **スキーマに関する注意事項**（`setTokenLimitSchema`）：`apiKeyId` と `scopeType`（`model` | `provider` | `global`）は必須です。`scopeType` が `global` でない限り、`scopeValue` は必須です（例：`model` スコープではモデル ID、`provider` スコープではプロバイダー ID）。`tokenLimit` は正の整数である必要があります（文字列から強制変換されます）。任意項目：`id`（作成時は省略し、更新時は指定）、`resetInterval`（`daily` | `weekly` | `monthly`、デフォルトは `monthly`）、`resetTime`（`HH:MM`）、`enabled`（デフォルトは `true`）。`GET` レスポンスでは、各制限に `tokensUsed`、`remaining`、`windowStart`、`periodStartAt`、`nextResetAt` が追加されます。これは管理クラスのエンドポイントです（認証は authz パイプラインによって一元的に適用されます）。

## リクエスト処理

1. クライアントが `/v1/*` にリクエストを送信
2. ルートハンドラーが `handleChat`、`handleEmbedding`、`handleAudioTranscription`、または `handleImageGeneration` を呼び出す
3. モデルを解決（プロバイダー/モデルの直接指定、またはエイリアス/コンボ）
4. アカウントの可用性フィルタリングを使用してローカル DB から認証情報を選択
5. チャットの場合：`handleChatCore` がセマンティック/シグネチャキャッシュを確認し、コンボの圧縮設定を解決
6. 有効な場合、プロバイダー形式への変換前にプロアクティブ圧縮を実行（`lite`、Caveman、RTK、またはスタック）
7. プロバイダーエグゼキューターがアップストリームリクエストを送信
8. レスポンスをクライアント形式に変換（チャット）するか、そのまま返却（埋め込み/画像/音声）
9. 使用量、圧縮分析、リクエストログを記録
10. エラー発生時はコンボルールに従ってフォールバックを適用

アーキテクチャの完全なリファレンス：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## レジリエンス（拡張）

OmniRoute は、独立した3つの一時的障害メカニズムを提供しています。以下の管理エンドポイントを使用して、オペレーターはそれらの状態を確認および上書きできます。

| スコープ               | 状態の保存先                          | 読み取り                                  | リセット / クリア                             |
| ---------------------- | ------------------------------------- | ----------------------------------------- | --------------------------------------------- |
| プロバイダーブレーカー | `domain_circuit_breakers` + メモリ内  | `/api/monitoring/health`                  | `POST /api/resilience/reset`                  |
| 接続クールダウン       | プロバイダー接続の `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | （遅延再有効化。プロバイダーの PUT でクリア） |
| モデルロックアウト     | メモリ内のモデル可用性レジストリ      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`      |

`PATCH /api/resilience` は、`providerBreaker.oauth` および `providerBreaker.apikey` 配下でプロバイダーブレーカーのオーバーライドを受け付けます。各プロファイルは `degradationThreshold`、`failureThreshold`、`resetTimeoutMs` をサポートしており、同じフィールドがダッシュボード → 設定 → レジリエンスにも表示されます。

```bash
# 単一モデルのロックアウトをクリア
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# すべてのロックアウトを消去
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

完全な概念リファレンスとブレーカーのデフォルト値については、[`CLAUDE.md`](../../CLAUDE.md) → 「レジリエンスのランタイム状態」および [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) を参照してください。

### レート制限キューと自動有効化セーフティネット

- **サポートされる書き込みパス**: ボディに `{"connectionId": "<id>", "enabled": true|false}` を指定する `POST /api/rate-limits` は、接続のレート制限保護を切り替えるためにサポートされている管理エンドポイントです。`PUT /api/providers/[id]` は意図的に `rateLimitProtection` を変更または反転しません（#11278）。
- **`enabled: false` のセマンティクス**: `enabled: false` を設定すると、接続に対する明示的な保護は解除されますが、アクティブな API キー接続をグローバルな自動有効化セーフティネット（`autoEnableApiKeyProviders = true`）の対象外には**しません**。`reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）では、`false` と `undefined` は同等です。明示的な保護が設定されていないアクティブな API キー接続も、自動有効化セーフティネットによって引き続き保護されます。
- **グローバル無効化**: レート制限キューなしで API キー接続を実行するには、`RATE_LIMIT_AUTO_ENABLE=false`（環境変数）または `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（設定 → レジリエンス / `PATCH /api/resilience`）を使用して、セーフティネットをグローバルに無効化します。

## MCP サーバー

OmniRoute には、3 つのトランスポート（stdio、SSE、streamable-http）とスコープ設定されたツールを備えた Model Context Protocol サーバーが組み込まれています。以下のダッシュボードエンドポイントは、ステータス／監査データを読み取り、HTTP トランスポートをプロキシします。

| メソッド | パス | 説明 |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ハートビート、トランスポート、オンライン状態、最終呼び出し、上位ツール、24 時間の成功率 |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` を含む MCP ツールの一覧 |
| GET | `/api/mcp/sse` | SSE トランスポート用の SSE ストリームを開く（MCP が無効、またはトランスポートが一致しない場合は `503` を返す） |
| POST | `/api/mcp/sse` | SSE トランスポートで JSON-RPC フレームを送信 |
| GET | `/api/mcp/stream` | Streamable HTTP トランスポートの SSE 側を開く（サーバー起点のメッセージ） |
| POST | `/api/mcp/stream` | Streamable HTTP トランスポートで JSON-RPC フレームを送信 |

## A2Aサーバー

OmniRouteは、A2A（Agent-to-Agent）JSON-RPC 2.0エンドポイントに加えて、検査およびダッシュボード用途のRESTラッパーを公開します。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEYが設定されていない限り省略可能
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

サポートされているメソッド（すべて`settings.a2aEnabled`によって制御されます）：

| メソッド         | 説明                                                    |
| ---------------- | ------------------------------------------------------- |
| `message/send`   | スキルを同期実行し、`{task, artifacts, metadata}`を返す |
| `message/stream` | 同じスキルセットをストリーミングSSEで実行               |
| `tasks/get`      | `taskId`でタスクを取得                                  |
| `tasks/cancel`   | `taskId`でタスクをキャンセル                            |

組み込みスキル：`smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### エージェントカード

```bash
GET /.well-known/agent.json
```

公開A2Aエージェントカード（名前、説明、機能、スキルカタログ、認証方式）を返します。公開キャッシュの有効期間は1時間です。認証は不要です。

### RESTヘルパー

| メソッド | パス                         | 説明                                                                                                             |
| -------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/a2a/status`            | A2Aの有効状態、タスク統計、キャッシュ済みエージェントカードの概要                                                |
| GET      | `/api/a2a/tasks`             | タスク一覧 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST     | `/api/a2a/tasks`             | （RESTヘルパーとしては未実装 — JSON-RPCの`message/send`で作成）                                                  |
| GET      | `/api/a2a/tasks/[id]`        | 単一のタスクを取得                                                                                               |
| POST     | `/api/a2a/tasks/[id]/cancel` | タスクをキャンセル                                                                                               |

**認証：** RESTヘルパーは管理認証なしで動作します（ダッシュボードから読み取り可能）。JSON-RPCの`/a2a`ルートでは、設定されている場合にBearer `OMNIROUTE_API_KEY`を使用します。

## 認証

4 種類の認証情報（ダッシュボードセッション、ローカル CLI トークン、`oma_live_…` アクセストークン、管理スコープの API キー）と、それらが推論キーとどのように異なるかについては、[管理認証](../guides/MANAGEMENT-AUTH.md)を参照してください。

- ダッシュボードルート（`/dashboard/*`）では `auth_token` Cookie を使用します
- ログインでは保存済みのパスワードハッシュを使用し、使用できない場合は `INITIAL_PASSWORD` にフォールバックします
- `requireLogin` は `/api/settings/require-login` で切り替え可能です
- `REQUIRE_API_KEY=true` の場合、`/v1/*` ルートでは必要に応じて Bearer API キーが要求されます
- このリファレンスにおける「管理トークン」または「管理スコープの API キー」とは、そのガイドに記載されている認証情報ファミリーのいずれかを指し、未定義の追加シークレット種別を意味するものではありません

> **破壊的変更（v3.8.0）** — `/api/v1/agents/tasks/*` およびクールダウン管理エンドポイントでは、**管理認証**（ダッシュボードの `auth_token` Cookie または管理スコープの API キー）が必須になりました。これまで認証なしでこれらのルートを呼び出していたクライアントには、`401 Unauthorized` が返されます。コミット `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）を参照してください。
