## チャット補完

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### カスタムヘッダー

| Header                   | Direction  | Description                                                                                                                                                                                               |
| ------------------------ | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | リクエスト | キャッシュをバイパスするには `true` に設定                                                                                                                                                                |
| `x-omniroute-no-memory`  | リクエスト | このリクエストでメモリとスキルの注入をスキップするには `true` に設定（no-cache をミラーリングし、呼び出しごとのトークン／コストのオーバーヘッドを回避）                                                   |
| `X-OmniRoute-Progress`   | リクエスト | 進行状況イベントを有効にするには `true` に設定                                                                                                                                                            |
| `X-Session-Id`           | リクエスト | 外部セッションアフィニティ用のスティッキーセッションキー                                                                                                                                                  |
| `x_session_id`           | リクエスト | アンダースコア形式も受け付け（直接 HTTP）                                                                                                                                                                 |
| `X-OmniRoute-Session-Id` | リクエスト | 呼び出し元が指定するセッション／会話タグ（メモリにも供給）。存在する場合は、セッションごとのコスト帰属（#8249）のため `call_logs.session_tag` にそのまま永続化される — 存在しない場合は決して生成されない |
| `Idempotency-Key`        | リクエスト | 重複排除キー（5 秒間）                                                                                                                                                                                    |
| `X-Request-Id`           | リクエスト | 代替の重複排除キー                                                                                                                                                                                        |
| `x-omniroute-connection` | リクエスト | 単一モデルのリクエストを ID で 1 つのプロバイダー接続（アカウント）に固定 — [リクエストごとのアカウント固定](#account-pinning-per-request)を参照                                                          |
| `X-OmniRoute-Cache`      | レスポンス | `HIT` または `MISS`（非ストリーミング）                                                                                                                                                                   |
| `X-OmniRoute-Idempotent` | レスポンス | 重複排除された場合は `true`                                                                                                                                                                               |
| `X-OmniRoute-Progress`   | レスポンス | 進行状況の追跡が有効な場合は `enabled`                                                                                                                                                                    |
| `X-OmniRoute-Session-Id` | レスポンス | OmniRoute が使用した実効セッション ID                                                                                                                                                                     |
| `X-OmniRoute-Request-Id` | レスポンス | リクエストの相関 ID（判明している場合）                                                                                                                                                                   |
| `X-OmniRoute-Version`    | レスポンス | OmniRoute のビルドバージョン（常に存在）                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | レスポンス | HIT 時にキャッシュによって回避された USD 額（キャッシュヒット時のみ）                                                                                                                                     |
| `X-OmniRoute-Decision`   | レスポンス | ルーティングトレース: `strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` はコンボ戦略、またはコンボ以外のリクエストでは `single`） — 完了レスポンスには常に存在                                |

> Nginx に関する注意: アンダースコア付きヘッダー（例: `x_session_id`）に依存する場合は、`underscores_in_headers on;` を有効にしてください。

#### リクエストごとのアカウント固定

プロバイダーに複数の接続（アカウントまたはキー）がある場合、OmniRoute は通常、アカウント選択戦略を通じて 1 つを選択します。リクエストでは、代わりに `x-omniroute-connection` ヘッダーを使用して特定の接続 1 つに固定できます。

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **ID の確認方法。** ダッシュボードでプロバイダーページ
  （**Dashboard → Providers → <provider>**）を開き、接続行にある `xxxxxxxx…` ID チップをクリックします。
  完全な接続 ID がコピーされます。
- **どのリクエストで有効か。** `/v1/chat/completions`、`/v1/messages`、`/v1/responses` に対する単一モデルリクエスト（`provider/model`）。コンボではヘッダーが無視されます。代わりに、各コンボステップの接続を通じて、ステップごとにアカウントを固定してください。
- **固定は優先設定ではなく、厳密な指定です。** 固定された接続だけが排他的に使用されます。リクエスト内で障害が発生すると、そのアカウントのクールダウンが記録されますが、同じプロバイダーの別アカウントへは切り替わりません。
- **クールダウンとクォータによって固定が解除されます。** 固定された接続がクールダウン中、クォータを使い切っている、またはクォータポリシーによってブロックされている場合、後続のリクエストは、固定されていないトラフィックとまったく同じように、プロバイダーの他の接続へフォールバックします。
- **不明または無効な ID は失敗します。** プロバイダーのアクティブプールに存在しない ID（削除済み、無効化済み、または別のプロバイダーに属する ID）では利用可能なアカウントがなくなるため、リクエストは別の場所へ暗黙的にルーティングされず、失敗します。

Claude Code は `ANTHROPIC_CUSTOM_HEADERS` を通じてカスタムヘッダーを送信します。`~/.claude/settings.json` の `env` ブロックに設定するか、プロジェクトごとに異なるアカウントを固定する場合は、プロジェクトレベルの `.claude/settings.json` に設定してください。

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ソース: `src/sse/handlers/chat.ts`（ヘッダーの読み取り）、`src/sse/services/auth.ts` および
`src/sse/services/sessionAffinityPin.ts`（固定の解除とプールからの欠落チェック）。

> **コストテレメトリヘッダー:** ストリーミングではない成功レスポンスには、`X-OmniRoute-*` コストテレメトリセットも含まれます — `X-OmniRoute-Response-Cost`（USD、小数点以下 10 桁固定。無料または価格未設定の場合は `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit`、`X-OmniRoute-Fallback-Attempts`（0 より大きい場合のみ）、さらに `X-OmniRoute-Request-Id` と `X-OmniRoute-Version` です。これらはチャット補完、`/v1/responses`、`/v1/messages`、**およびメディアエンドポイント** — `/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations`、`/v1/moderations` — から出力されます（常にコストは `0`）。メディアのコストは、価格が利用可能な場合、モダリティごと（画像ごと、秒ごと、文字ごと、検索単位ごと）に計算され、それ以外の場合は `0` になります（fail-open）。

> **キャッシュヒット時のコストの意味:** セマンティックキャッシュが HIT（`X-OmniRoute-Cache-Hit: true`）した場合、アップストリームへの呼び出しは行われないため、`X-OmniRoute-Response-Cost` は `0.0000000000` になります（ヒットを提供するための**増分**コスト）。元のコスト／発生していたはずのコストは、`X-OmniRoute-Cost-Saved` で別途報告されます。課金処理では `X-OmniRoute-Response-Cost`（ヒットのコストはゼロ）を合計し、キャッシュ分析では `X-OmniRoute-Cost-Saved` を集計できます。

## 排他的マネージドセッションリース

排他的マネージドセッションリースは、オプトイン方式でクライアントに依存しないルーティング契約です。1つのアクティブな所有者が、利用資格のある1つの OmniRoute 接続を保持します。モデルをリースするものではなく、OAuth を必要とせず、特定のクライアントを識別せず、特定のプロバイダーも必要としません。

認証に使用する API キーには `lease:exclusive` スコープがあり、明示的な空でない
`allowedConnections` リストが必要です。データベースの変更境界では、キーの作成時と部分更新時に、両方のフィールドが必ず同時に指定されることを強制します。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

取得、更新、解放に成功したレスポンスでは、タイムスタンプ、`state`、正確な正の
`generation` が公開されますが、選択された接続や認証情報は決して公開されません。更新と解放では、JSON ボディに generation を指定します。

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

アクティブなリース所有者は、現在のバインディングについて、プライバシーに配慮した表示メタデータを明示的に要求できます。

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

このオプトイン方式の status アクションは、不透明な owner、認証済みのマネージド API キー、正確なアクティブ generation によってフェンスされ、1つのデータベーストランザクション内で処理されます。`displayName` は設定された接続名をトリミングしたものに限られ、安全な設定名が存在しない場合は `null` になります。OmniRoute がメールアドレスや生成されたアカウント ID を代わりに使用することはありません。provider の値は機密情報ではない表示ラベルであり、生成された互換プロバイダー ID ではありません。認証情報、トークン、Cookie、生の接続 ID や API キー ID、owner ハッシュ、フェンシングシークレット、内部ルーティングデータは除外されます。

誤ったキー、誤った owner、古い generation、存在しない、期限切れ、解放済み、無効化済みのルックアップは、すべて接続メタデータを含まない同一の `409 LEASE_FENCE_STALE` エラーを返します。キャパシティ待機レスポンスを受け取ったクライアントには、調査できるアクティブなバインディングがありません。ルーティングによってアクティブなリースが遷移した場合も、同じ generation が有効なまま維持され、status は新しいバインディングをアトミックに返します。古いバインディングが返されることはありません。取得、更新、解放、待機レスポンスは従来の形式を維持するため、既存のクライアントに変更はありません。

このサーバー契約によって、標準の OpenAI Codex `/status` が変更されることはありません。標準の Codex は現在、モデルプロバイダーと組み込みの認証／アカウント状態を報告しますが、任意のカスタムプロバイダーアカウントメタデータを表示することはありません。後続のクライアント統合では、このアクションを呼び出し、`connection.displayName` の表示方法を決定する必要があります。

その後、すべてのマネージド推論リクエストで、両方の制御ヘッダーを指定します。

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

正確な owner、generation、アクティブな接続、認証済み API キーは、サポート対象の各アップストリーム試行の直前にフェンスされます。owner と generation を別のキーで再利用した場合、そのキーが同じ接続を許可していても失敗します。生の owner が永続化、ログ出力、リクエストスナップショットへの保持、アップストリームへの転送されることはありません。

一時的な競合では、`Retry-After` と次のレスポンスを伴う HTTP `429` が返されます。

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

このレスポンスは、通常の利用資格のある集合が空ではなく、空いているすべての候補が別のアクティブなリースによって保持されていることだけを意味します。サポートされていないモデル／プロバイダー、ポリシー不一致、クールダウン、クォータ、ヘルス、その他の通常の利用資格エラーでは、既存の OmniRoute レスポンスが引き続き返されます。

### `x-omniroute-compression`

リクエストごとに圧縮プランを上書きします。最も高い優先順位を持ち、ルーティングコンボの上書き、アクティブなプロファイル、自動トリガー、パネルの Default より優先されます。値：

| 値            | 効果                                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | このリクエストでは圧縮しません。                                                                                      |
| `default`     | パネルから導出された Default プロファイル（アクティブなプロファイルは無視します）。ロッシーエンジンはオフのままです。 |
| `safe`        | 重複排除と空白の折りたたみのみ。                                                                                      |
| `allow-lossy` | サマリーやスタイルの書き換えを含め、このリクエストではオペレータープランを維持します。                                |
| `engine:<id>` | 有効化されている単一のエンジン。例：`engine:rtk`。そのエンジンをリクエスト単位でオプトインします。                    |
| `<combo>`     | 名前付きコンボ。まず名前（大文字と小文字を区別しない）で照合し、次に ID で照合します。                                |

注：

- 不明な値は無視されます（リクエストが拒否されることはありません）。解決処理は通常のオペレーター優先順位にフォールスルーします。
- 複数のコンボが同じ名前を共有している場合は、決定的に照合するためにコンボ **id** を指定します。
- 名前が `off` または `default` のコンボは、名前で選択できません（これらのキーワードが先に解釈されます）。そのようなコンボは ID で参照してください。
- 圧縮のマスタースイッチはハードゲートです。圧縮がグローバルに無効化されている場合、このヘッダーで有効化することはできません。

適用されたプランは、レスポンスヘッダーにエコーされます。

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ここで `<source>` は `request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default`、`off` のいずれかです。

## 埋め込み

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

利用可能なプロバイダー: Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

カタログ ID は `provider/model` 形式です（例: `jina-ai/jina-embeddings-v5-omni-small`）。レジストリに登録されている Jina のモデル ID（例: `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）は、単独でも解決されます。Jina の embed/rerank/classify/segment は、まずダッシュボードの `jina-ai` 認証情報を使用します。`JINA_AI_API_KEY` は、ダッシュボードキーが存在しない場合にのみフォールバックとして使用されます。`jina-reader` カードは Reader / `r.jina.ai` 専用（`POST /v1/web/fetch`）であり、埋め込みや rerank には使用されません。

マルチモーダル対応を宣言しているレジストリモデルは、プロバイダーに依存しない構造化アイテムを最大 32 個まで受け付けます。メディアアイテムの型は `text`、`image`、`audio`、`video`、`document` です。メディアの `source` は `{"type":"url","url":"https://..."}` または `{"type":"base64","data":"...","media_type":"..."}` のいずれかです。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`、およびファミリーエイリアス `jina-ai/jina-embeddings-v5-omni` → omni-small）は、Jina ネイティブの EmbeddingsV5Request ドキュメントも受け付け、`https://api.jina.ai/v1/embeddings` に**そのまま転送**します。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ネイティブの `{ image | audio | video | pdf }` の値には、公開 HTTPS URL、`data:` URI、または生の base64 を指定できます。OmniRoute はこれらのオブジェクトを文字列化せず、ネイティブの画像 URL も取得しません。Jina が公開メディアを自ら取得します。追加の Jina フィールド（`task`、`normalized`、`truncate`、`embedding_type`）は転送されます。テキスト専用の Jina SKU は、テキスト以外のドキュメントを引き続き拒否します。

セキュリティおよび転送に関する制限:

- リモートメディア URL は公開 HTTPS である必要があります。標準の `{type,source:url}` アイテムはサーバー側で取得され（リダイレクトの再検証、タイムアウト、サイズ制限、パブリック DNS、接続の固定を実施）、プロバイダー呼び出しの前にインライン化されます。Jina ネイティブの `{image:"https://..."}` アイテムは、同じ公開 HTTPS チェック後にそのまま転送されます。URL の取得は Jina が行います。
- インライン base64 メディアは、アイテムごとにデコード後 8 MiB、リクエスト全体でデコード後 16 MiB に制限されます。

プロバイダー変換（標準アイテムが変更されずに転送されることはありません）:

- Jina マルチモーダルモデル: トップレベルの各アイテムは、データ URI を使用したモダリティキー付きオブジェクト（`text` / `image` / `audio` / `video` / `pdf`）になります。トップレベルの各アイテムにつき 1 つのベクトルが生成されます。
- Gemini Embedding 2 ファミリー: 1 つのトップレベル配列が、`content.parts`（`text` または `inline_data`）を含む単一のネイティブ `models/{model}:embedContent` リクエストになります。
- llama.cpp（`llama-cpp/<model>`、ローカルサーバーが読み込んだ任意のモデル）: 標準の `text` アイテムはプレーンな文字列になり、`image` / `audio` / `video` はそれぞれ 1 つの `{"content": [part]}` オブジェクトになります。これらには、インラインデータを使用する llama-server のチャットコンテンツパーツ（`image_url`、形式 `wav` / `mp3` / `flac` の `input_audio`、`input_video`）が使用されます。トップレベルの各アイテムにつき 1 つのベクトルが生成されます。`document` はサポートされません。サーバーは `--embedding --mmproj …` を指定して実行する必要があります。プロジェクターがない場合、メディアはサーバー自体によって拒否されます。
- 明示的なモダリティメタデータを持たない未知のモデルまたは動的モデルは、構造化入力を HTTP 400 で拒否します。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

サポートされていないモデルとモダリティの組み合わせは、アイテムを強制的に変換せず、HTTP 400 を返します。従来の文字列/トークンリクエストに含まれる入力以外の拡張フィールドは、引き続き変更されずに通過します。

```bash
# すべての埋め込みモデルを一覧表示
GET /v1/embeddings
```

## 画像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

利用可能なプロバイダーには、OpenAI（GPT Image 2）、xAI（Grok Image）、Together AI（FLUX）、Fireworks AI、Nebius（FLUX）、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（ローカル）、ComfyUI（ローカル）が含まれます。

`n` は `data[]` に `n` 個の画像を返します。上流 API が 1 回の呼び出しにつき 1 つの画像を返すプロバイダー
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI）では、上流への呼び出しを `n` 回個別に行い、同時実行数は最大 4 です。
固定された `seed` は呼び出しインデックス（`seed`、`seed + 1`、…）によってオフセットされるため、画像は異なりますが再現性は維持されます。
`n` の上限は 10 です。いずれかの呼び出しが失敗すると、リクエスト全体が失敗します。ファンアウト形式の一覧は
`open-sse/handlers/imageGeneration/fanOut.ts` の `SINGLE_IMAGE_FANOUT_FORMATS` です。

ZenMux は既存の API キー接続を再利用し、`zenmux/` または `zm/` プレフィックスを受け付けます。

- `zenmux/openai/gpt-image-2` は ZenMux の OpenAI Images API を使用します。オプションには `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background`、`response_format` が含まれます。
- `zm/meta/muse-image-1.0` などの他のパブリッシャーは、ZenMux の Vertex AI `:predict`
  エンドポイントを使用します。`n` は `sampleCount` に、`aspect_ratio` は `aspectRatio` に、
  `image_size`（`1K`、`2K`、`4K`）は `sampleImageSize` にマッピングされます。ピクセル単位の `size` は
  アスペクト比のみを指定し、ピクセル寸法が保証されるわけではありません。サポートされる比率、解像度、個数はモデルによって異なります。
- `zm/inclusionai/ming-image-0.1-design` は独自に寸法を選択します。`size`、`aspect_ratio`、`image_size` は省略してください。
  明示的に値を指定すると HTTP 400 が返されます。`output_format` で PNG、JPEG、WebP をリクエストできます。

この統合はテキストから画像を生成する機能をサポートしており、参照画像の編集には対応していません。Vertex の出力は
`data[].b64_json` に正規化されます。`response_format: "url"` は、上流の HTTPS URL、または画像バイトのみが利用可能な場合は
base64 データ URL を返します。空の出力やフィルタリングされた出力の場合は、空の成功レスポンスではなくエラーを返します。
モデルへのアクセスは ZenMux アカウントによって異なります。[ZenMux の Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) および
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) を参照してください。

```bash
# すべての画像モデルを一覧表示
GET /v1/images/generations
```

## ドキュメント OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` は `provider/model` プレフィックスを使用して OCR プロバイダーを選択します。プレフィックスのないモデル ID（例:
`mistral-ocr-latest`）は登録済みのプロバイダーに解決され、省略した `model` はデフォルトで
Mistral（`mistral-ocr-latest`）になります。登録済みのプロバイダー（`open-sse/config/ocrRegistry.ts`）:

| プロバイダー ID               | モデル ID            | `model` の値                                                                    | 備考                                                                                                                         |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（またはプレフィックスのない `mistral-ocr-latest`） | 同期処理 — 単一の上流呼び出しからレスポンスが直接返されます。                                                                |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                                     | 上流では非同期処理（`analyze` + ポーリング） — 詳細は以下を参照してください。                                                |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                         | Vertex AI の `openapi/chat/completions` パートナーエンドポイント経由の同期処理 — 認証と URL の詳細は以下を参照してください。 |

3 つのプロバイダーはすべて、同じ Mistral 形式の本文で応答します。

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence のポーリングフロー

Azure Document Intelligence の `analyze` API は非同期です。初回リクエストは本文の代わりに
`Operation-Location` ヘッダーを返し、結果をポーリングする必要があります。ハンドラー
（`open-sse/handlers/ocr.ts`）は、最大 30 回の試行にわたって 1 秒ごとにその URL をポーリングします。
`ok` でないポーリングレスポンスまたは `"failed"` ステータスの場合は、ポーリングを継続せず直ちに失敗します。
試行回数の上限に達した時点でも処理が実行中の場合は `504` を返します。最終的な Azure のレスポンスは、
呼び出し元に返す前に、Mistral で使用されるものと同じ `pages`/`markdown` 形式に正規化されます。
そのため、クライアントコードでプロバイダーごとの特別な処理を行う必要はありません。

### Vertex AI DeepSeek OCR の認証とエンドポイント解決

`vertex-deepseek-ocr` は、OmniRoute がチャットおよび画像トラフィックですでにサポートしているものと同じ Vertex AI 認証
（`open-sse/executors/vertex.ts`）を再利用します。接続の API キーは、サービスアカウント JSON 認証情報
（JWT ベアラーフローを介して短期間有効な OAuth アクセストークンと交換）または、そのまま使用される既発行の OAuth アクセストークンのいずれかです。
上流エンドポイント URL は、接続のプロジェクトとリージョンから構築される Vertex の汎用
`openapi/chat/completions` パートナーエンドポイントです。明示的な
`providerSpecificData.project`/`providerSpecificData.region` が常に優先され、それ以外の場合は、プロジェクトはサービスアカウント JSON の
`project_id` から導出され、リージョンは `us-central1` がデフォルトになります。どちらの解決も
`open-sse/handlers/ocr.ts`（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`）で行われ、
`src/app/api/v1/ocr/route.ts` が `handleOcr` にディスパッチする前に使用します。

### モデル価格（`pricing`）

OmniRoute がモデルの価格を把握している場合、エントリには `pricing` オブジェクトが含まれます。価格は、コスト計算で使用される価格表（組み込みのデフォルト、同期された価格、`/api/pricing` で設定された上書き）から取得されます。これらは表示価格であるため、サブスクリプションプロバイダーにもトークン単位の価格が表示されます。

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| フィールド                                                      | 単位                                | 注記                                                                                                                                                     |
| --------------------------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | トークンあたりの USD、10 進数文字列 | OpenRouter 互換で、指数表記は使用しません。2 つのキャッシュフィールドは、キャッシュ価格が存在する場合にのみ表示されます。                                |
| `input`, `output`, `cached`, `cache_creation`                   | 100 万トークンあたりの USD、数値    | 以前のカタログバージョンのフィールドで、既存のクライアント向けに維持されています。価格行に含まれる場合は、`reasoning` と `long_context` も表示されます。 |

- **コンボ**には、最初に表示されるターゲットの価格が設定されます。組み込みの `auto/*` コンボはリクエスト時にターゲットを選択するため、`pricing` はありません。
- **無料モデル**は、価格がゼロの場合 `"0"`（および `0`）を表示します。価格行がないモデルでも、カタログが無料（`free: true`）とマークしているか、組み込みの無料モデルカタログに掲載されている場合は `"0"` を表示します。
- **価格不明:** エントリに `pricing` キーはありません。
- **クレジット従量制のプロバイダー**（Kiro など）は、トークン単位ではなくリクエスト単位で課金します。これらのエントリには、以前から存在する 100 万トークンあたりの数値フィールドが残され、トークン単位の文字列フィールドはありません。
- **バリアント**（推論エフォート ID、思考なしのエイリアス、検出用およびゲートウェイ用ミラー）は、ルーティング先モデルの価格をコピーします。
- フィールドには基本料金のみが含まれます。長文コンテキストのティア（数値の `long_context` フィールド）やサービスティアの乗数（Codex の fast や flex など）によって、`prompt` や `completion` が変わることはありません。
- このオブジェクトは、`x-api-key` と `anthropic-version` を使用する Anthropic 形式のリクエストを含め、すべての認証方式で同一です（レスポンスは `{ "object": "list", "data": [...] }` のままです）。実装: `src/app/api/v1/models/catalogPricing.ts`。

### モデル ID のプレフィックス（`?prefix=`）

ほとんどのモデルは、**プロバイダープレフィックス**付きで公開されます。使用されるプレフィックスは `MODELS_CATALOG_PREFIX_MODE` 機能フラグによって制御されますが、クエリパラメーターで **リクエストごとに**上書きできます。これは、サーバー全体の設定を他のユーザー向けに変更せず、クリーンな一覧を取得したいクライアントに便利です。

```bash
GET /v1/models?prefix=alias        # モデルごとに 1 つの ID — 短いエイリアスプレフィックス
GET /v1/models?prefix=dual         # 両方の形式（サーバーのデフォルト）
GET /v1/models?prefix=canonical    # 完全なプロバイダー ID プレフィックスのみ
```

| モード      | 出力                                                         | 注記                                                                                                                                                                                              |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **および** `claude/claude-sonnet-4-6` | **デフォルト。** 両方の ID が同じモデルにルーティングされます。どちらかの形式をハードコードしたクライアント設定が引き続き機能するように維持されています。カタログの規模はおよそ 2 倍になります。  |
| `alias`     | `cc/claude-sonnet-4-6`                                       | モデルごとに 1 エントリ。個別のエイリアスを持たないプロバイダーもエントリを出力するため、何も失われません。                                                                                       |
| `canonical` | `claude/claude-sonnet-4-6`                                   | 完全なプロバイダー ID プレフィックスの下に、モデルごとに 1 エントリ。個別のエイリアスを持たないプロバイダー（例: `antigravity/…`、`agy/…`）も、ここで単一の ID を出力するため、何も失われません。 |

`dual` モードのミラーは、クエリパラメーターがなくても、プライマリ ID を指す `parent` フィールドによって識別できます。

モデルピッカーを表示するクライアントは `?prefix=alias` をリクエストしてください。これは [OmniCopilot VS Code 拡張機能](../guides/VSCODE-COPILOT.md)で使用されています。

### 検出フィルター（`?capability=`, `?min_context=`, `?kind=`, `?q=`）

`GET /v1/models` は、オプトイン方式の検出フィルターを受け付けます。これらを指定しない場合、レスポンスは変わりません。フィルターは、呼び出し元がすでに参照できるカタログ（API キーの権限が先に適用されます）を絞り込み、OpenAI 形式の `limit` / `after` ページングより前に実行されます。

```bash
GET /v1/models?capability=vision&capability=tool_calling   # リストされたすべての機能が true である必要があります
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # カタログの `type`。指定がない行は `chat`
GET /v1/models?q=sonnet&limit=10                           # ID または名前に対する大文字と小文字を区別しない検索
```

| パラメーター  | 値                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | `context_length` と比較される 0 以上の整数                                                          |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1～200 文字                                                                                         |

未知の値、または 0 以上の整数ではない `min_context`（例: `1.5`）の場合は、
HTTP `400` が返され、メッセージに有効な値が一覧表示されます。実装:
`src/app/api/v1/models/catalogFilters.ts`。

### モデルのショートリスト（`POST /v1/models/query`）

`POST /v1/models/query` は、`GET /v1/models` と同じカタログから、同じ認証およびキーごとの
可視性を適用して、短く決定論的なリストを返します。

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

すべてのフィールドはオプションです。`capabilities` と `exclude` には、配列またはカンマ区切り文字列を
指定できます。`max_output` は `max_output_tokens` と比較されます。結果は `owned_by`、次に `id`
の順でソートされます。`limit` のデフォルト値は `20` で、`100` を超える値は `100` に
上限設定されます。無効な JSON、未知のフィールド、または無効な値の場合は HTTP `400` が返されます。

### 個別に非表示にされたチャットモデル

プロバイダーページで **非表示** とマークされたモデルはカタログから除外され、明示的にリクエストされた場合は
HTTP `404` / `model_not_found` で拒否されます。このチェックでは、プロバイダーのエイリアス、
互換プロバイダーのノードプレフィックス、接続のデフォルト値を含め、解決済みのプロバイダーとモデルが使用されます。
コンボは非表示のターゲットをスキップして、表示されている兄弟モデルを使用できます。実行可能なターゲットが
残っていない場合は、同じエラーコードが返されます。非表示を解除すると、次のリクエストから反映されます。
画像専用の可視性オーバーライドによって、同じ ID のチャットモデルが非表示になることはありません。

この個別モデル設定は、
[モデル公開の許可/拒否リスト](../routing/MODEL_EXPOSURE_LIST.md) とは別のものです。後者は、
明示的なディスパッチを維持したまま、カタログへの掲載と自動ルーティング候補をフィルタリングします。
API キーのモデル権限は引き続き独立して適用されます。デフォルトのカタログプレフィックスモードは引き続き
`dual` です。

### 思考なしモデルのバリアント

思考機能に対応する Claude モデルでは、`/v1/models` に、ID が
`claude-3-omniroute-no-thinking/` で始まる**思考なし**バリアントも掲載されます。

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

この ID を選択すると（たとえば、常に `thinking` ブロックを付加する Claude Code 設定で）、
実際の `<provider>/<model>` に解決され、推論が抑制されます。`/v1/messages` パスでは
`thinking:{type:"disabled"}` が設定され、`/v1/chat/completions` パスでは `reasoning` /
`reasoning_effort` フィールドが削除されます。このバリアントは、思考機能に対応し、かつ
`disabled` を受け入れる Claude ファミリーのモデルにのみ一覧表示されます。そのため、たとえば
`disabled` を拒否する適応型のみのモデルは除外されます。オペレーターは
`ModelSpec.noThinkingAlias` により、モデルごとにこのバリアントを強制的に有効化または無効化できます。

## ElevenLabs オーディオ生成

ElevenLabs API キーを使用して、OmniRoute に `elevenlabs` プロバイダー接続を設定します。
クライアントは **OmniRoute** キー（`Authorization: Bearer $OMNIROUTE_API_KEY`）で認証します。
ゲートウェイは保存済みのプロバイダーキーを `xi-api-key` として提供します。ElevenLabs キーをゲートウェイの bearer トークンとして送信しないでください。

| メソッド | パス                        | レスポンス                                        | API キーエンドポイントカテゴリ |
| -------- | --------------------------- | ------------------------------------------------- | ------------------------------ |
| POST     | `/v1/sound-generation`      | ネイティブオーディオバイト                        | `elevenlabs`                   |
| POST     | `/v1/music`                 | ネイティブオーディオバイト                        | `music`                        |
| POST     | `/v1/music/stream`          | ストリーミングオーディオバイト                    | `music`                        |
| POST     | `/v1/music/detailed`        | ネイティブマルチパートオーディオおよび作曲プラン  | `music`                        |
| POST     | `/v1/music/detailed/stream` | ネイティブ SSE メタデータおよびオーディオチャンク | `music`                        |
| POST     | `/v1/music/plan`            | JSON 作曲プラン                                   | `music`                        |

これらのエンドポイントは、既存の `/v1/audio/speech`、`/v1/audio/transcriptions`、
`/v1/voices`、`/v1/text-to-speech/{voiceId}`、`/v1/speech-to-text` ルートを補完します。ネイティブ JSON フィールドと
`output_format` や `enable_logging` などのクエリパラメーターは保持されます。
`/v1/music/detailed` のレスポンスはマルチパート境界を保持します。マルチパートとして解析してください。
`/v1/music/detailed/stream` は、作曲メタデータと Base64 オーディオチャンクを SSE イベントで含む
`text/event-stream` を返します。6 つのルートすべてが CORS プリフライトをサポートします。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 短い効果音。長さ: 0.5～30 秒。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 音楽の長さはミリ秒で指定します: 3000～600000。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

増分オーディオ配信には、同じ JSON ボディで `/v1/music/stream` を使用します。作曲では
`prompt` または `composition_plan` のいずれか一方だけを指定できます。`/v1/music/plan` には `prompt`
が必須で、`source_composition_plan` を任意で指定できます。ネイティブスキーマは追加の
プロバイダーフィールドを保持するため、作曲プランのバージョンや微調整オプションを ElevenLabs に渡せます。

統合 `/v1/music/generations` エンドポイントは、
`elevenlabs/music_v1`、`elevenlabs/music_v2`、`elevenlabs/music_v2_5` も受け付けます。ElevenLabs 接続がアクティブな場合、
これらのモデルは音楽カタログで公開されます。このエンドポイントは
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` を返します。その `duration` フィールドは
秒単位で、`music_length_ms` にマッピングされます。明示的な `music_length_ms` が優先されます。
`instrumental` は `force_instrumental` にマッピングされ、ネイティブフィールドが優先されます。
ストリーミングにはネイティブストリーミングエンドポイントを使用し、作曲プランだけで駆動されるリクエストには
ネイティブ作曲エンドポイントを使用してください。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

エンドポイント、モデル、予算、接続に関する制限は、アップストリームへの呼び出し前に適用されます。ネイティブルートは、
`402`（プラン制限）や `429`（クォータ上限）を含め、アップストリームのステータスコードとエラーボディを変更せずに返します。
`character-cost`、`song-id`、`request-id`、`retry-after` ヘッダーは、存在する場合に保持されます。無料クレジット残高があっても、
すべての音楽モデル、出力形式、API 機能へのアクセスが保証されるわけではありません。各リクエストの利用資格は ElevenLabs が決定します。
統合エンドポイントは、OmniRoute の正規化されたエラーエンベロープ内でエラーステータスコードを保持します。

アップストリームの仕様: [効果音](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音楽の作曲](https://elevenlabs.io/docs/api-reference/music/compose)、および
[ストリーミング音楽の詳細](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。

```bash
# 再ランキング（クラウドレジストリプロバイダー、または "<prefix>/<model>" 形式のOpenAI互換プロバイダーノード）
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina search（s.jina.ai。プロバイダーエイリアス：jina-search、jina-ai、jina）
POST /v1/search      { "query": "...", "provider": "jina-search" }

# モデレーション
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg（または要求された形式）の本文を返却
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTSでは言語と音声が必要です。`language` のデフォルトは "en" です。指定がない
# voice、またはOpenAIの標準音声名（alloy、nova、…）が指定された場合は "Adrian" になります

POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **再ランクプロバイダーノード:** `POST /v1/rerank` は、`<node-prefix>/<model>` として指定された OpenAI 互換プロバイダーノード（oMLX、vLLM、Infinity、ゲートウェイ配下の TEI など）にもルーティングされます。ループバックノード（`localhost`、`127.0.0.1`、`172.16.0.0/12`）は常に利用可能であり、オペレーターが `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` に列挙したホスト名も利用可能です（例: `http://reranker:8080/v1` のような Docker/Compose サービス名。これらは常に直接呼び出され、`HTTP(S)_PROXY` や接続に固定されたプロキシを経由しません）。その他のホスト上にあるノード（LAN 上のマシンや Tailscale ピア）は、オペレーターが `RERANK_REMOTE_PROVIDER_NODES` 機能フラグを有効にし、かつノードのベース URL がプロバイダーの外向き URL ポリシー（`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）を通過した場合にのみ利用可能です。メモリエンジンの再ランク処理はループバック経由でこのルートを呼び出すため、Memory 設定の `rerankProviderModel` にも同じルールが適用されます。
>
> **ローカルサーバーの形式:** ノードは `<base>/v1/rerank` で呼び出され、404 の場合は `<base>/rerank` で呼び出されます（Infinity、TEI）。上流へのリクエストボディには Cohere/OpenAI の表記（`documents`、`return_documents`）と TEI の表記（`texts`、`return_text`）の両方が含まれ、上流レスポンスは Cohere のエンベロープに正規化されます。TEI の単純な `[{index, score, text}]`、シンプルなゲートウェイからの `{results: [{index, score}]}`、Voyage 形式の `{data: [...]}` はすべて、スコア順にソートされ、`top_n` 件に制限された `{results: [{index, relevance_score, document?}]}` としてクライアントに返されます。

> **プロバイダーノードの検出:** OpenAI 互換プロバイダーノード上のモデルは、ノードプレフィックス配下の `GET /v1/models` に表示されます。エンドポイントメタデータを持たない行（ローカルの `/v1/models` 一覧に典型的なもの）は、ノードの `apiType` を継承します。そのため、`embeddings` ノードのモデルはデフォルトでチャットになるのではなく `type: "embedding"` となり、`rerank` ノードのモデルは `type: "rerank"` となります。同期または手動で追加された行に明示的な `supportedEndpoints` がある場合は、引き続きそちらが優先されます。

### 専用プロバイダールート

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

プロバイダープレフィックスがない場合は自動的に追加されます。モデルが一致しない場合は `400` が返されます。

### Exa と Tavily の `provider_options`

Exa と Tavily は、名前空間付きのバッグからプロバイダー固有のフィールドを読み取ります:
`provider_options.exa`（または `provider_options["exa-search"]`）および `provider_options.tavily`
（または `provider_options["tavily-search"]`）。以下のキーのみが転送されます。それぞれ
`open-sse/handlers/search/providerOptionsPassthrough.ts` の独自の Zod スキーマに対して
検証され、型が正しくないキーは削除されます。認証、ベース URL、`stream`、
`outputSchema` を含むその他のキーはすべて無視されます。他のプロバイダーで使用される
フラットなキー（`cx`、`depth` など）は、これまでどおり機能します。

| プロバイダー | トップレベルフィールド                                                                                                                                                                                                                                                                                                                                                    | ネストされたフィールド                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa          | `type`、`category`、`userLocation`、`moderation`、`additionalQueries`、`objective`、`systemPrompt`、`compliance`（フラットなプリミティブ）、`startPublishedDate`、`endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}`。デフォルトの `{ text: true, highlights: true }` にマージされます |
| Tavily       | `search_depth`、`chunks_per_source`、`time_range`、`start_date`、`end_date`、`include_published_date`、`filter_by_published_date`、`include_answer`、`include_raw_content`、`include_images`、`include_image_descriptions`、`include_favicon`、`include_domains_mode`、`language`、`filter_by_language`、`auto_parameters`、`exact_match`、`include_usage`、`safe_search` | —                                                                                                                                               |

汎用フィールドは常に優先されます: `query`、`max_results`、`filters`（ドメイン）、
`country`、および `search_type` から導出されるトピックです。Exa では、
`search_type: "news"` により `category: "news"` が維持されます。
Tavily は `search_type: "finance"`（`topic: "finance"`）にも対応しています。

Firecrawl の検索コストは、返された結果 10 件ごとの開始済みブロック単位で記録されます。
1 ブロックあたり $0.002（2 クレジット）で、呼び出しごとに最低 1 ブロックが課金されます
（[Firecrawl の請求](https://docs.firecrawl.dev/billing)）: 11 件の結果では $0.004 です。

汎用の `time_range` は現在、両方のプロバイダーに渡されます: Exa には
`startPublishedDate`（ISO タイムスタンプ）として、Tavily には `start_date`
（`YYYY-MM-DD`）として渡されます。`provider_options` に明示的な日付がある場合は、
マッピングされた日付より優先されます。

Exa の結果では、`id`、`highlights`（`snippet` に使用される最初の 1 件だけでなく、
すべてのハイライト）、`highlight_scores`、`summary`、`subpages`、`entities`、
`extras` が `provider_raw` に保持されます。Tavily の結果では `images` と `favicon` が
保持されます。

Linkup の検索コストは、`depth` が `fast` および `standard` の場合は $0.005、
`deep` の場合は $0.05 として記録されます（[Linkup の料金](https://docs.linkup.so/pages/documentation/development/pricing)）。
`depth` が `provider_options` から指定された場合でも、接続の設定から指定された場合でも同じです。

Exa の `type: "lite"`（Exa 3.0）は、より少ないフィールドの組み合わせに対応しており、
他のフィールドが 1 つでも設定されているとリクエスト全体を拒否します。lite の場合、
`additionalQueries`、`systemPrompt`、および `text` と `highlights` 以外のすべての
`contents` キーは呼び出し前に削除されます。非推奨の `subpages`、
`subpageTarget`、`highlights.numSentences`、`highlights.highlightsPerUrl` は
今後転送されません。

コスト計算は、Exa を除き、固定のレジストリ `costPerQuery` に基づきます。Exa は
独自の料金体系に従います: `auto`（および従来の `fast`）は呼び出し 1 回あたり $0.007、
`lite`（および従来の `instant`）は $0.004 で、10 件の結果を含みます。追加の結果には
1 件あたり $0.001 がかかり、`contents.summary` が設定されている場合は返された結果
1 件あたり $0.001 がかかります。Tavily は、`search_depth` が `basic`、`fast`、
`ultra-fast` の場合は 1 クレジット（$0.008）、`advanced` の場合は 2 クレジット
（$0.016）として記録されます（[Tavily API クレジット](https://docs.tavily.com/documentation/api-credits)）。
`auto_parameters: true` を指定した呼び出しで Tavily が `advanced` にアップグレード
した場合も、1 クレジットとして記録されます。

## Web Fetch API

設定済みの Web Fetch プロバイダー（Firecrawl、Jina
Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）を介して、URL からコンテンツを抽出します。

Parallel Extract（`parallel-search`、Parallel Search と同じ API キー）は Markdown
のみを返します — その他の `format` は `400` になります — また、コンテンツは 100,000 文字に制限されます。対象ページ自体を抽出できない場合、アップストリームはそれを HTTP 200 内で報告しますが、OmniRoute は固定メッセージとともに `422` として返します。

| Method | Path            | Description                                                          |
| ------ | --------------- | -------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL を取得／スクレイピング — `v1WebFetchSchema` によってボディを検証 |

**認証:** Bearer API キー（`extractApiKey` + `isValidApiKey`）。ポリシーは `enforceApiKeyPolicy` によって適用されます。

**クォータ対応フォールバック (#8297):** 明示的な `provider` が指定されていない場合、プール
（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`）は
固定された
優先順位（fill-first）で走査されます — レート制限されているものの設定済みのプロバイダーは、リクエストをそこで打ち切るのではなくスキップされます。また、再試行可能な／クォータ超過のアップストリームエラー（HTTP 429 は常に、Firecrawl／Tavily／TinyFish のクォータ形式の無料ティアでは 402/403 — Jina Reader では対象外で、通常の 400 不正リクエストでは決して対象外）は、リクエスト時点でまだ試行されていない認証済みプロバイダーへフォールスルーします。プール内のすべてのプロバイダーを使い切った場合、エンドポイントは以前の汎用的な `400` の代わりに、`Retry-After` ヘッダー付きの単一の `429` を返します。明示的な `provider` が要求された場合、サイレントフォールバックは行われません — レート制限または障害が発生した明示的なプロバイダー自身のエラー（レート制限時は `429`、それ以外はアップストリームのステータス）が返されます。

## WebSocket ストリーミング

```bash
GET /v1/ws?handshake=1
```

WebSocket アップグレードハンドシェイクを検証し、ワイヤープロトコルのサンプルメッセージ（`request`、`cancel`）を返します。実際の WS フレームは、Next.js のルートテーブル外にある同梱の WS サーバーによって処理されます。

**認証:** ハンドシェイク時の Bearer API キー。

### WebSocket 経由の Responses API（codex のみ）

```bash
# HTTP API と同じ host:port（デフォルトは 20128）；接続をアップグレード：
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （または：-H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 最初のフレームは必ず response.create にする：
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses API over WebSocket プロキシは **`codex`（ChatGPT バックエンド）専用**に接続されています。API／ダッシュボードと同じポートで、パス `/v1/responses`、`/responses`、`/api/v1/responses` をリッスンします。最初の `response.create` フレームで、内部の `codex-responses-ws` ブリッジを介して認証と準備を行い、codex OAuth 接続を選択して、`wreq-js` トランスポート経由で `wss://chatgpt.com/backend-api/codex/responses` にトンネルします。**codex 以外のモデルは拒否されます**（`codex_ws_provider_required`）。クォータ共有ルーティングには、`model: "qtSd/<group>/codex/<model>"` を使用します。`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` に実装されています。

**認証:** ハンドシェイク時の Bearer API キー。同梱の HTTP サーバー（`server-ws.mjs`）がアクティブなエントリーポイントである必要があります（`app/server-ws.mjs` が存在する場合、デフォルトでそうなります）。

#### モデル ID：ベアの ChatGPT ID を使用（`codex/` プレフィックスなし）

OpenAI **Codex CLI** は、`supports_websockets = true` の場合にクライアント側でモデル名を検証し、`codex/gpt-5.5` のようなプロバイダー接頭辞付き ID を拒否します（`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`）。ベアの ID（例：`gpt-5.5`）を送信してください。OmniRoute のブリッジは codex 専用のため、HTTP 経由では別のプロバイダーにルーティングされるはずのベアの `gpt-5.5` であっても、トンネリング前に codex モデルとして再解決します（`resolveCodexWsModelInfo`）。

#### OpenAI Codex CLI の設定

既存の設定に影響を与えないよう、別の `CODEX_HOME` を使用し、WebSocket サポート付きのカスタムプロバイダーを `~/.codex/config.toml` に追加して、Codex CLI を OmniRoute に向けます。

```toml
model = "gpt-5.5"                 # ベア ID — "codex/gpt-5.5" ではない
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 末尾にスラッシュを付けない；WS URL はここから導出される（本番環境では https/wss を使用）
wire_api = "responses"                    # 2026 年 2 月以降、サポートされる値はこれのみ
supports_websockets = true                # Responses-over-WS トランスポートを有効化
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API キー（Bearer）を保持
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API キー（REQUIRE_API_KEY=false の場合は任意のキー）
codex exec "Responda apenas: PONG"
```

CLI は `base_url + /responses` を WebSocket にアップグレードし、OmniRoute はそれを選択された codex OAuth 接続へトンネルします。ローカルサーバーに対してエンドツーエンドで検証済みです。ChatGPT は `codex.rate_limits` + `response.created` を返し、補完をストリーミングします。

| Method | Path                | Description                                                                               |
| ------ | ------------------- | ----------------------------------------------------------------------------------------- |

### クォータセッションの復旧（オプトイン）

非ストリーミングの `POST /v1/chat/completions` または `POST /v1/responses` が、終端クォータエラー（本文がクォータまたはクレジットの枯渇を示す `402`/`429`/`503`）で失敗した場合、エラーを返す代わりに保留して後で再実行できます。呼び出し元は、以下の 3 つのヘッダーを使用してリクエストごとにオプトインします。

| Header                       | Value                                       |
| ---------------------------- | ------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                      |
| `x-omniroute-session`        | セッション ID、`[A-Za-z0-9._:-]{1,128}`     |
| `x-omniroute-recovery-turn`  | セッション内で一意のターン ID（同じルール） |

`stream: false` で、ツール、ツール履歴、`previous_response_id` がなく、`x-omniroute-connection` による固定もないターンのみが対象となります。また、`STORAGE_ENCRYPTION_KEY` が設定されている必要があります（リクエストは最大 24 時間、暗号化して保存されます）。その後、レスポンスは `202` と `recovery.poll` になります。`GET /v1/quota-recoveries/{id}` をポーリングすると（保留中は `202`、完了時は復旧した本文とともに `200`）、または `DELETE` でキャンセルできます。チケットを参照できるのは、作成した API キーのみです。結果が不確実な再実行は、二重送信を避けるため `needs_confirmation` で終了します。ソース: `src/lib/quota/quotaSessionRecovery.ts`。

## セルフサービスの使用状況（`/api/usage/om-usage`）

任意の API キーで、**自身の**使用状況とクォータを読み取れます。管理者認証は不要です。これは、クライアント（CLI、OmniCopilot パネル）がキー所有者に使用額を表示するために使用するエンドポイントです。

```bash
# テキスト形式（従来の契約 — ターミナル向けのプレーンテキスト）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 構造化形式 — UI が消費する形式
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

キーでは **`allowUsageCommand`** が有効になっている必要があります（デフォルトでは無効 — ダッシュボードの API キーマネージャーでキーごとに切り替えます）。無効の場合、エンドポイントは `403` を返します。

`?format=json` は判別可能な形式を返すため、呼び出し元が拒否レスポンスからデータフィールドを読み取ることはありません。成功時:

```jsonc
{
  "allowed": true,
  // キーがキーごとの使用制限（日次/月次 USD）をオプトインした場合のみ存在します:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 選択されたプロバイダーのクォータスナップショット。まだキャッシュされていない場合は null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // 各接続のスナップショット。UI は複数のプロバイダーを横並びで表示できます:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

拒否時（無効なキーによる `401` / 許可されていない場合の `403`）も同じルートが
`{ "allowed": false, "error": { "message": "…" } }` を返します。`personal`/`provider` が存在するものの空である状態（キーは許可されているが、まだ取得できる情報がない）は拒否とは異なる状態であり、これらを区別できるのは JSON 形式のみです。

**認証:** 呼び出し元自身の Bearer API キーを `isValidApiKey` で検証します。これは管理サーフェス（`/api/keys/…`）ではなく、管理サーフェスは引き続き `requireManagementAuth` の背後にあります。

### 生のクォータ割合とカットオフ調整済みクォータ割合

`/api/usage/om-usage` を利用する際、呼び出し元は、**プレーンテキスト出力**と構造化された **JSON 出力**で示される割合の違いに注意する必要があります。

| Aspect               | Plain-text format (`/api/usage/om-usage` / `@@om-usage`)                                          | JSON format (`?format=json`)                                                 |
| :------------------- | :------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------- |
| **Output field**     | `NN% left`（例: `20% left`）                                                                      | `provider.quotas` / `providers[].quotas`                                     |
| **Measurement**      | **カットオフ調整済みの使用可能量**: カットオフしきい値を超えて残っている容量                      | **上流の生クォータ**: 調整されていないプロバイダーの測定値                   |
| **Cutoff scaling**   | `effectiveRemainingPercent()` により、保護された予備容量が `0% left` と表示されるようスケーリング | なし（プロバイダーが報告した生のスナップショット値）                         |
| **Threshold data**   | 表示される割合に組み込まれる                                                                      | 接続ごとの `quotaWindowThresholds`（またはサーバーのデフォルト）に保存される |
| **Primary consumer** | 対話型 CLI、ターミナルプロンプト、人間のオペレーター                                              | プログラムによる統合、ダッシュボード、分析、課金トラッカー                   |

#### カットオフ調整の計算式

OmniRoute は、上流での枯渇を防ぐために、事前対応型のクォータカットオフをサポートしています（接続の `quotaWindowThresholds`、プロバイダーのデフォルト、またはグローバルのレジリエンス設定で構成）。クォータウィンドウでカットオフしきい値（例: `cutoff = 25%`）が有効な場合、テキストレンダラーは残りの使用可能量を次のように計算します。

- `remaining <= cutoff` の場合: `0%` を返します。
- `remaining > cutoff` の場合: `((remaining - cutoff) / (100 - cutoff)) * 100` を返します。

整形されたテキスト出力では、これを最も近い整数に丸めます（`Math.round(...)`）。

#### 具体例

プロバイダーウィンドウが**生の使用率 60%**（したがって**生の残りクォータ 40%**）で、設定された
**残りクォータのカットオフ**しきい値が **25%** の場合：

| 表現                            | 計算                                                   |  残り   |                 推定使用率                  |
| :------------------------------ | :----------------------------------------------------- | :-----: | :-----------------------------------------: |
| **生の JSON（`?format=json`）** | アップストリームのスナップショット（`quotas[window]`） | **40%** |                   **60%**                   |
| **テキスト形式（`NN% left`）**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100`     | **20%** | **80%**（`100 - remaining` を計算する場合） |

- **テキストに 20% left と表示される理由：** アカウント上で物理的に残っているクォータ 40% のうち、25% は
  カットオフポリシーによって予約されています。ルーターがこの接続へのルーティングを停止するまでに、呼び出し元が利用できる残りのヘッドルームは、使用可能な 75% のうち 15% だけです。スケーリングにより、ルーティングが停止するタイミングと、接続が枯渇（`0% left`）を示すタイミングが正確に一致します。
- **JSON が生の値を保持する理由：** JSON ペイロードは正確なプロバイダーのスナップショット（`UsageSnapshot`）を返すため、外部ツールは、サーバー側での情報損失を伴うスケーリングなしに、アップストリームの実際の使用率と接続レベルの `quotaWindowThresholds` にアクセスできます。

#### 利用者の移行ガイダンス

外部統合（エディタープラグインやエージェント拡張機能など）が以前、テキストエンドポイント（`NN% left`）をスクレイピングし、使用率を `100 - NN` として計算していた場合、`?format=json` への移行により次のようになります。

- 生の JSON 値を読み取ることで、**実際のアップストリーム消費量**（上記の例では使用率 60%）が反映されます。
- 統合側でテキストエンドポイントの利用可能量のセマンティクスを維持したい場合は、接続レベルのオーバーライドに `quotaWindowThresholds` を使用して、実効残量の計算式をクライアント側で評価できます。

## セマンティックキャッシュ

```bash
# キャッシュ統計を取得
GET /api/cache/stats

# すべてのキャッシュをクリア
DELETE /api/cache/stats
```

レスポンス例:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,

  }

```

### レイテンシーへの影響

セマンティックキャッシュの HIT は、**アップストリームへの呼び出しなし**でキャッシュからレスポンスを返すため、報告される `X-OmniRoute-Response-Latency` は、元のアップストリームのレイテンシーに関係なく、ほぼゼロになります。レイテンシーに敏感なクライアント（ベンチマーク、p50/p99 の監視）は、レスポンスヘッダー `X-OmniRoute-Cache-Latency` を確認してください。

| Value       | Meaning                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------- |
| `synthetic` | レスポンスはキャッシュから返されます。レイテンシーは実際のアップストリーム時間ではありません |
| _(なし)_    | 実際のアップストリーム呼び出しからのレスポンス                                               |

### キー単位のキャッシュバイパス

API キーでは、`cacheDefaultMode` を使用してセマンティックキャッシュの読み取りをオプトアウトできます。

| Value    | Behavior                                                         |
| -------- | ---------------------------------------------------------------- |
| `legacy` | 通常のキャッシュ動作（デフォルト）                               |
| `bypass` | キャッシュ検索を完全にスキップし、常にアップストリームにアクセス |

キーの作成（`POST /api/keys`）または更新（`PATCH /api/keys/[id]`）時に設定します。

```json
{ "cacheDefaultMode": "bypass" }
```

### リクエスト単位のバイパス

キーの設定に関係なく、任意のリクエストでキャッシュをバイパスできます。

```
X-OmniRoute-No-Cache: true
```

## CLIProxyAPI 管理互換性

OmniRoute は、使用状況ダッシュボードが Claude および Codex のサブスクリプション上限を読み取るために呼び出す、3 つの [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) 管理エンドポイント（たとえば T3 Code の `cliproxy` 使用量ソース）に応答します。クライアントのベース URL を OmniRoute に設定し、管理キーとして `manage` スコープを持つ API キーを使用してください。ルートは `/v0/management/*` および `/api/v0/management/*` で提供されます。

| Method | Path                         | Description                                                                                                                                                           |
| ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }` 形式の Claude および Codex OAuth 接続。トークンは含まれません                                  |
| POST   | `/v0/management/api-call`    | 本文 `{ auth_index, method, url, header?, data? }`。アカウントのトークンを使用して、許可リストに登録されたリクエストを 1 件送信し、`{ status_code, body }` を返します |
| POST   | `/v0/management/reset-quota` | 本文 `{ auth_index }`。1 つのアカウントの接続クールダウン、モデルロックアウト、Codex のスコープごとのクールダウンをクリアします                                       |

- `auth_index` は OmniRoute の接続 ID です。`provider` は `claude` または `codex` です（OAuth 接続のみ。`anthropic` API キープロバイダーは一覧に含まれません）。Codex の場合、`id_token.chatgpt_account_id` は保存されたワークスペース ID、`plan_type` は保存されたプランです。
- `api-call` は汎用プロキシではありません。Claude の `GET
https://api.anthropic.com/api/oauth/usage` および Codex の `GET
https://chatgpt.com/backend-api/wham/usage`、`GET .../wham/rate-limit-reset-credits`、`POST .../wham/rate-limit-reset-credits/consume` のみを受け付け、それぞれ対応するプロバイダーのアカウントに対してのみ実行します。それ以外はアップストリームに接続せずに `403` を返します。呼び出し元の `Authorization` ヘッダー（`$TOKEN$` プレースホルダーを含む）は無視されます。OmniRoute は接続のアクセストークンを注入し、有効期限が近い場合は先に更新し、許可リストに登録されたヘッダー（`anthropic-beta`、`OpenAI-Beta`、`Originator`、`Chatgpt-Account-Id`、`Accept`、`Content-Type`）のみを転送します。`Chatgpt-Account-Id` がない場合は、保存されたワークスペース ID がデフォルトになります。リクエストは 15 秒後にタイムアウトし、接続のプロキシを使用します。
- `reset-quota` は終端状態（banned、expired、credits_exhausted）をそのままにします。不明な `auth_index` は `404` を返します。

**認証:** ログインが無効になっている場合でも、ダッシュボードセッションまたは `manage` スコープの API キーが必要です（パスは `ALWAYS_PROTECTED_API_PATHS` に含まれています）。推論専用キーでは `403` が返されます。ソース: `src/lib/cliproxyCompat/managementApi.ts`。

同期／インポートされたモデルでは、`PUT /api/provider-models` は `provider`、`modelId`、`maxOutputTokenOverride` を受け付けます。正の整数を設定すると手動の出力トークン上限になり、`null` にすると解除されてデフォルトに戻ります。`GET /api/provider-models?provider=<provider>` は、カスタムモデルの行がないモデルも含め、これらの値を `modelOutputOverrides` で返します。このオーバーライドはランタイムの `max_output_tokens` 機能を使用し、モデルの再同期後も維持されます。OpenAI 互換プロバイダーのページでも同じ編集／解除操作を行え、明示的にビジョンサポートがあるモデルにはその旨が表示されます。

互換性のあるプロバイダーノードでは、書き込みパス（`POST`、`PUT`、`PATCH`、`DELETE` および `/api/provider-models/validate-and-add`）によって、モデル ID がプレーンな上流 ID として保存されます。プレフィックス付きの一覧から貼り付けられた ID は、ノード自身のプレフィックスが先頭に連続している場合、それらがまとめて 1 つに整理され、レスポンスでは保存された ID が返されます。正規プロバイダーのスラッシュ付き ID（例：`nvidia/nemotron-…`）はそのまま保存されます。`/v1/models` が、`<prefix>/<prefix>/<model>` のようにプレフィックスが重複した ID を出力することはありません。

カスタム Chat Completions ノードは、明示的な reasoning オプトアウトを上流バックエンド向けに適合させます。
接続テストが成功すると、`/models` のエントリによって `owned_by` の値が `vllm`、`sglang`、または
`llamacpp` のいずれかであることが確認された各モデル ID に対して、チャットテンプレートの制御が自動的に
選択されます。透過的な OpenAI 互換ラッパーは、元のモデルエントリをネストされた
`openai` オブジェクト内に保持している場合があります。検出では、このようなエンベロープを最大 3 層まで
追跡します。所有者情報が欠落している、未知である、または競合しているモデルでは、通常の OpenAI の動作が
維持されます。検出では既存のカタログリクエストを再利用し、completion トークンは生成されません。また、
接続エンドポイントが変更されると無効化されます。

このメタデータを公開しないバックエンドで動作を固定するには、既存の部分プロバイダー更新 API を使用します。

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

この本文を `PUT /api/providers/<connection-id>` とともに送信します。その接続では、明示的な
reasoning effort の `none` は `chat_template_kwargs.thinking=false` および
`chat_template_kwargs.enable_thinking=false` として送信されます。サーバー側の reasoning ルールが
effort を強制しない限り、明示的なネイティブテンプレート値が優先されます。この設定は、カスタム
OpenAI 互換接続が Chat Completions 本文をディスパッチする場合にのみ適用されます。Responses リクエストと
通常のプロバイダーでは、ネイティブのリクエスト形式が維持されます。通常の OpenAI の
`reasoning_effort` パススルーを強制するには `reasoningControl` を `openai` に設定し、自動検出を使用するには
省略するか `null` に設定します。

Claude Code の自動モード分類器リクエストでは、明示的な reasoning 制御が含まれていない場合、ネイティブの
thinking はデフォルトで無効になります。検出では、モデル名や completion の上限ではなく、Claude 形式の
リクエストに含まれる分類器のシステムマーカーを使用します。明示的な本文制御、サポートされている
effort/thinking ヘッダー、ルーティングルール、解決済みモデル effort では、既存の優先順位が維持されます。
どちらの分類器ステージでも、プロンプト、completion の上限、停止シーケンス、実際の上流権限判定は維持されます。
第 2 ステージでは、要求した表示用 reasoning が通常のテキストとして生成される場合もあります。

| `override:context`                           | 永続化されたコンテキストウィンドウの上書き（`model_context_overrides`） |

| `effort-base:` prefix                        | effort サフィックス付きバリアントのベースモデルから借用した行           |
| `none`                                       | 制限を宣言するソースがない（値は `null`）                               |

### バージョンとリリースチャンネル

```bash
GET /api/system/version
```

ループバック専用の管理ルート（管理者認証）。実行中のバージョン、公開済みの最新バージョン、自動更新の状態を返します。`releaseChannel` と `channels` は追加フィールド（rail 3.8.54）です。`channel` の意味は変わらず、ダッシュボードのアップデーターが使用するデプロイモード（`npm`、`source`、`docker-compose`）を示します。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 実行中のビルドの npm チャンネル: `-nightly.*` バージョンの場合は `nightly`、その他のプレリリース（`-rc.*`、`-beta.*`、`-alpha.*`）の場合は `next`、`channels.latest` より前のメジャーバージョンの安定版の場合は `lts`、それ以外の場合は `latest`。公開時に npm の dist-tag を選択する `scripts/release/dist-tag.mjs` と同じルールです。
- `channels` — 各 dist-tag の公開済みヘッド。`npm view omniroute dist-tags`（レジストリ HTTP フォールバック）から取得され、`latest` と同じ 10 分間の TTL でキャッシュされます。`latest` は常に存在します（`latest` フィールドにフォールバックし、それもない場合は `"unavailable"`）。`next`、`nightly`、`lts` は、その dist-tag が存在する場合にのみ表示されます。`Cache-Control: no-cache` リクエストを行うと、両方の参照が更新されます。

チャンネルモデル（4.0 GA までは `latest` = v3、`next` = rc、`nightly` = `develop` ビルド、4.0 GA 後の v3 パッチは `lts`）については、`docs/ops/RELEASE_STRATEGY.md` で説明しています。

```json
}
```

**モデル ID の例:** `openai/whisper-1`（OpenAI キーが必要）、
`openrouter/deepgram/nova-3`（OpenRouter キーが必要）、
`deepgram/nova-3`（ネイティブの Deepgram キーが必要）。単独の
`deepgram/nova-3` リクエストでは OpenRouter は使用されません。

**サポートされている形式:** `mp3`、`wav`、`m4a`、`flac`、`ogg`、`webm`。

**Gemini Live（`gemini/gemini-3.5-transcribe-live`）:** Gemini Live
WebSocket 経由でファイルモードの文字起こしを行います（Gemini API キーが必要）。アップロードされたファイルは
`ffmpeg`（ファイルがすでに 16 kHz モノラル PCM WAV である場合を除き、`PATH` に存在している必要があります）を使用して
16 kHz モノラル PCM に変換され、セッションにストリーミングされた後、確定したテキストが `{ "text": "..." }` として返されます。オプションの `language` および `prompt` フォームフィールドは転送されます。
制限事項: 25 MiB を超えるアップロード、またはデコード後の音声が 10 分を超える場合は
`413` が返されます。変換に 60 秒を超えて実行時間がかかった場合は強制終了され、`504` が返されます。API キーは
`x-goog-api-key` ヘッダーでのみ送信され、WebSocket URL に含まれることはありません。

## トークン制限

API キーごとの **トークン** 予算（上記の USD ベースの予算とは別）。リクエストパス上でインラインに適用されます。キーの現在のウィンドウ使用量が上限に達すると、リクエストは `429 Too Many Requests` で拒否されます。制限は特定の `model`、`provider` にスコープすることも、キー全体に `global` に適用することもできます。1 つのリクエストに複数の制限が一致する場合は、最も厳しい制限が適用されます。

```bash
# キーのトークン制限を一覧表示（現在のウィンドウ使用量を含む）
GET /api/usage/token-limits?apiKeyId=key-123

# トークン制限を作成または更新
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ID でトークン制限を削除
DELETE /api/usage/token-limits?id=tl-abc
```

> **スキーマに関する注意** (`setTokenLimitSchema`): `apiKeyId` と `scopeType` (`model` | `provider` | `global`) は必須です。`scopeType` が `global` でない場合は `scopeValue` が必須です（`model` スコープの場合はモデル ID、`provider` スコープの場合はプロバイダー ID など）。`tokenLimit` は正の整数である必要があります（文字列から変換されます）。オプション: `id`（作成時は省略し、更新時に指定）、`resetInterval`（`daily` | `weekly` | `monthly`、デフォルトは `monthly`）、`resetTime`（`HH:MM`）、`enabled`（デフォルトは `true`）。`GET` のレスポンスでは、各制限に `tokensUsed`、`remaining`、`windowStart`、`periodStartAt`、`nextResetAt` が追加されます。これは管理クラスのエンドポイントです（認証は authz パイプラインによって中央で適用されます）。

## リクエスト処理

1. クライアントが `/v1/*` にリクエストを送信
2. ルートハンドラーが `handleChat`、`handleEmbedding`、`handleAudioTranscription`、または `handleImageGeneration` を呼び出す
3. モデルを解決（直接のプロバイダー/モデル、またはエイリアス/コンボ）
4. アカウントの利用可能性によるフィルタリングを行い、ローカル DB から認証情報を選択
5. チャットの場合: `handleChatCore` がセマンティック/シグネチャキャッシュを確認し、コンボの圧縮設定を解決
6. 有効な場合、プロバイダーへの変換前にプロアクティブ圧縮を実行（`lite`、Caveman、RTK、またはスタック）
7. プロバイダーエグゼキューターがアップストリームリクエストを送信
8. レスポンスをクライアント形式に変換して返す（チャット）、またはそのまま返す（埋め込み/画像/音声）
9. 使用量、圧縮分析、リクエストログを記録
10. コンボのルールに従い、エラー発生時にフォールバックを適用

アーキテクチャの完全なリファレンス: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 耐障害性（拡張）

OmniRoute は、独立した 3 つの一時的障害メカニズムを提供します。以下の管理エンドポイントを使用して、それらの状態を読み取ったり、上書きしたりできます。

| スコープ               | 状態の保存先                          | 読み取り                                  | リセット / クリア                                             |
| ---------------------- | ------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| プロバイダーブレーカー | `domain_circuit_breakers` + メモリ内  | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                  |
| 接続クールダウン       | プロバイダー接続の `rateLimitedUntil` | `/api/rate-limits`、`/api/providers/[id]` | （遅延して再有効化されます。プロバイダーの PUT でクリア可能） |
| モデルロックアウト     | メモリ内のモデル可用性レジストリ      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                      |

`PATCH /api/resilience` は、`providerBreaker.oauth` および `providerBreaker.apikey` の下でプロバイダーブレーカーの上書きを受け付けます。各プロファイルでは `degradationThreshold`、`failureThreshold`、`resetTimeoutMs` を設定できます。同じフィールドは、ダッシュボード → 設定 → 耐障害性にも表示されます。

```bash
# 1 つのモデルロックアウトをクリア
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# すべてのロックアウトを消去
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

概念の完全なリファレンスとブレーカーのデフォルト値については、[`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" および [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) を参照してください。

### レート制限キューと自動有効化セーフティネット

- **サポートされている書き込みパス**: 本文 `{"connectionId": "<id>", "enabled": true|false}` の `POST /api/rate-limits` は、接続のレート制限保護を切り替えるためにサポートされている管理エンドポイントです。`PUT /api/providers/[id]` は意図的に `rateLimitProtection` を変更または切り替えません（#11278）。
- **`enabled: false` の意味**: `enabled: false` を設定すると、その接続に対する明示的な保護は解除されますが、アクティブな API キー接続がグローバルな自動有効化セーフティネット（`autoEnableApiKeyProviders = true`）の対象外になるわけではありません。`reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）では、`false` と `undefined` は同等です。明示的な保護が設定されていないアクティブな API キー接続は、自動有効化セーフティネットによって引き続き保護されます。
- **グローバルな無効化**: レート制限キューなしで API キー接続を実行するには、`RATE_LIMIT_AUTO_ENABLE=false`（環境変数）または `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（設定 → 耐障害性 / `PATCH /api/resilience`）によって、セーフティネットをグローバルに無効化します。

## MCP サーバー

OmniRoute には、3 つのトランスポート（stdio、SSE、streamable-http）とスコープ付きツールを備えた、組み込みの Model Context Protocol サーバーが付属しています。以下のダッシュボードエンドポイントでは、ステータス/監査データを読み取り、HTTP トランスポートをプロキシします。

| メソッド | パス | 説明 |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ハートビート、トランスポート、オンライン状態、最終呼び出し、上位ツール、24 時間の成功率 |
| GET | `/api/mcp/tools` | `name`、`description`、`scopes`、`phase`、`auditLevel`、`sourceEndpoints` を含む MCP ツールの一覧 |
| GET | `/api/mcp/sse` | SSE トランスポート用の SSE ストリームを開く（MCP が無効、またはトランスポートが一致しない場合は `503` を返す） |
| POST | `/api/mcp/sse` | SSE トランスポート上で JSON-RPC フレームを送信 |
| GET | `/api/mcp/stream` | Streamable HTTP トランスポートの SSE 側を開く（サーバー起点のメッセージ） |
| POST | `/api/mcp/stream` | Streamable HTTP トランスポート上で JSON-RPC フレームを送信 |
| DELETE | `/api/mcp/stream` | Streamable HTTP セッションを終了 |
| GET | `/api/mcp/audit` | 監査ログをクエリ — `?limit=`、`?offset=`、`?tool=`、`?success=true                                | false`、`?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | 監査統計の集計（合計、成功率、平均所要時間、上位ツール） |

**認証:** `sse`/`stream` トランスポートでは MCP 固有の認証インターフェース（`mcp` スコープを持つ Bearer API キー）が使用されます。`status`/`tools`/`audit*` ルートはダッシュボードから読み取り可能です（ダッシュボードホストへのアクセス以外に追加の認証は必要ありません）。

> どちらの HTTP トランスポートも `settings.mcpEnabled` と `settings.mcpTransport` によって制御されます — トランスポートが一致しない場合は `400`、MCP が無効な場合は `503` を返します。

## A2A サーバー

OmniRoute は、検査およびダッシュボード用途向けに、A2A（Agent-to-Agent）JSON-RPC 2.0 エンドポイントと REST ラッパーを公開します。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY が設定されている場合を除き任意
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

サポートされているメソッド（すべて `settings.a2aEnabled` によって制御されます）:

| メソッド         | 説明                                                         |
| ---------------- | ------------------------------------------------------------ |
| `message/send`   | 同期的なスキル実行。`{task, artifacts, metadata}` を返します |
| `message/stream` | 同じスキルセットをストリーミング SSE で実行します            |
| `tasks/get`      | `taskId` でタスクを取得します                                |
| `tasks/cancel`   | `taskId` でタスクをキャンセルします                          |

組み込みスキル: `smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### エージェントカード

```bash
GET /.well-known/agent.json
```

公開 A2A エージェントカード（名前、説明、機能、スキルカタログ、認証方式）を返します。公開キャッシュの有効期間は 1 時間です。認証は必要ありません。

### REST ヘルパー

| メソッド | パス                         | 説明                                                                                                             |
| -------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/a2a/status`            | A2A の有効状態、タスク統計、キャッシュされたエージェントカードの概要                                             |
| GET      | `/api/a2a/tasks`             | タスク一覧 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST     | `/api/a2a/tasks`             | （REST ヘルパーとしては未実装 — JSON-RPC `message/send` で作成）                                                 |
| GET      | `/api/a2a/tasks/[id]`        | 1 件のタスクを取得                                                                                               |
| POST     | `/api/a2a/tasks/[id]/cancel` | タスクをキャンセル                                                                                               |

**認証:** REST ヘルパーは管理用認証なしで実行されます（ダッシュボードから読み取り可能）。JSON-RPC の `/a2a` ルートでは、設定されている場合、Bearer `OMNIROUTE_API_KEY` が使用されます。

## 認証

4 種類の認証情報ファミリー（ダッシュボードセッション、ローカル CLI トークン、`oma_live_…` アクセストークン、manage スコープの API キー）と、それらが推論キーとどのように異なるかについては、[管理認証](../guides/MANAGEMENT-AUTH.md)を参照してください。

- ダッシュボードのルート（`/dashboard/*`）では `auth_token` Cookie を使用します
- ログインでは保存されたパスワードハッシュを使用し、フォールバックとして `INITIAL_PASSWORD` を使用します
- `requireLogin` は `/api/settings/require-login` で切り替えられます
- `/v1/*` ルートでは、`REQUIRE_API_KEY=true` の場合に Bearer API キーが必要になります
- このリファレンスにおける「管理トークン」/「管理スコープの API キー」は、上記ガイドにあるいずれかの認証情報ファミリーを指します。未定義の追加のシークレット種別を意味するものではありません

> **破壊的変更（v3.8.0）** — `/api/v1/agents/tasks/*` とクールダウン管理エンドポイントでは、管理認証（ダッシュボードの `auth_token` Cookie または管理スコープの API キー）が必要になりました。以前これらのルートを未認証で呼び出していたクライアントは、`401 Unauthorized` を受け取ります。詳しくはコミット `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）を参照してください。
