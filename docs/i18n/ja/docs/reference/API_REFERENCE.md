## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### カスタムヘッダー

| ヘッダー                 | 方向       | 説明                                                                                                                                                                                                       |
| ------------------------ | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | リクエスト | キャッシュをバイパスするには `true` に設定                                                                                                                                                                 |
| `x-omniroute-no-memory`  | リクエスト | このリクエストでメモリとスキルの注入をスキップするには `true` に設定（キャッシュ無効化と同様に動作し、呼び出しごとのトークンおよびコストのオーバーヘッドを回避）                                           |
| `X-OmniRoute-Progress`   | リクエスト | 進捗イベントを有効にするには `true` に設定                                                                                                                                                                 |
| `X-Session-Id`           | リクエスト | 外部セッションアフィニティ用のスティッキーセッションキー                                                                                                                                                   |
| `x_session_id`           | リクエスト | アンダースコア形式も使用可能（直接 HTTP）                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | リクエスト | 呼び出し元が指定するセッション／会話タグ（メモリにも渡される）。指定された場合、セッションごとのコスト配賦のために、そのまま `call_logs.session_tag` に永続化される（#8249）— 指定がない場合は生成されない |
| `Idempotency-Key`        | リクエスト | 重複排除キー（5秒間のウィンドウ）                                                                                                                                                                          |
| `X-Request-Id`           | リクエスト | 代替の重複排除キー                                                                                                                                                                                         |
| `x-omniroute-connection` | リクエスト | 単一モデルのリクエストを、ID で指定した1つのプロバイダー接続（アカウント）に固定 — [リクエストごとのアカウント固定](#account-pinning-per-request)を参照                                                    |
| `X-OmniRoute-Cache`      | レスポンス | `HIT` または `MISS`（非ストリーミング）                                                                                                                                                                    |
| `X-OmniRoute-Idempotent` | レスポンス | 重複排除された場合は `true`                                                                                                                                                                                |
| `X-OmniRoute-Progress`   | レスポンス | 進捗追跡が有効な場合は `enabled`                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | レスポンス | OmniRoute が使用した実効セッション ID                                                                                                                                                                      |
| `X-OmniRoute-Request-Id` | レスポンス | リクエスト相関 ID（判明している場合）                                                                                                                                                                      |
| `X-OmniRoute-Version`    | レスポンス | OmniRoute のビルドバージョン（常に含まれる）                                                                                                                                                               |
| `X-OmniRoute-Cost-Saved` | レスポンス | HIT によってキャッシュが削減した金額（USD、キャッシュヒット時のみ）                                                                                                                                        |
| `X-OmniRoute-Decision`   | レスポンス | ルーティングトレース：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` は組み合わせ戦略。組み合わせではないリクエストの場合は `single`）— 完了レスポンスには常に含まれる                      |

> Nginx に関する注意：アンダースコアを含むヘッダー（例：`x_session_id`）を使用する場合は、`underscores_in_headers on;` を有効にしてください。

#### リクエストごとのアカウント固定

プロバイダーに複数の接続（アカウントまたはキー）がある場合、通常 OmniRoute は
アカウント選択戦略を使用してそのうちの1つを選択します。代わりに、リクエストで
`x-omniroute-connection` ヘッダーを使用して特定の接続を1つ固定できます：

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id の確認場所。** ダッシュボードでプロバイダーページ
  （**Dashboard → Providers → <provider>**）を開き、接続行にある `xxxxxxxx…` の id チップをクリックすると、
  完全な接続 id がコピーされます。
- **対象となるリクエスト。** `/v1/chat/completions`、`/v1/messages`、
  `/v1/responses` に対する単一モデルリクエスト（`provider/model`）が対象です。コンボではこのヘッダーは無視されます。
  代わりに、各ステップ独自の接続を通じて、コンボのステップごとにアカウントを固定してください。
- **固定は優先設定ではなく厳格に適用されます。** 固定された接続のみが使用されます。リクエスト内で
  障害が発生すると、そのアカウントのクールダウンは記録されますが、同じプロバイダーの
  別アカウントへローテーションされることは**ありません**。
- **クールダウンとクォータにより固定が解除されます。** 固定された接続がクールダウン中、
  クォータ超過、またはクォータポリシーによってブロックされている間、後続のリクエストは、固定されていないトラフィックと
  まったく同様に、プロバイダーの他の接続へフォールバックします。
- **不明または無効な id は失敗します。** プロバイダーのアクティブプールに存在しない id（削除済み、
  無効化済み、または別のプロバイダーに属するもの）では、利用可能なアカウントがなくなるため、リクエストは
  暗黙的に別の接続へルーティングされることなく失敗します。

Claude Code は `ANTHROPIC_CUSTOM_HEADERS` を通じてカスタムヘッダーを送信します。プロジェクトごとに異なる
アカウントへ固定するには、`~/.claude/settings.json` の `env` ブロック、またはプロジェクトレベルの
`.claude/settings.json` に設定してください。

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

出典：`src/sse/handlers/chat.ts`（ヘッダーの読み取り）、`src/sse/services/auth.ts` および
`src/sse/services/sessionAffinityPin.ts`（固定の解除とプール内に存在しないことの確認）。

> **コストテレメトリヘッダー：** 非ストリーミングの成功レスポンスには、`X-OmniRoute-*` コストテレメトリ一式も含まれます。具体的には、`X-OmniRoute-Response-Cost`（USD、小数点以下10桁固定。無料または価格未設定の場合は `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit`、`X-OmniRoute-Fallback-Attempts`（> 0 の場合のみ）、および `X-OmniRoute-Request-Id` と `X-OmniRoute-Version` です。これらは、チャット補完、`/v1/responses`、`/v1/messages`、**およびメディアエンドポイント**（`/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations`、`/v1/moderations`〔コストは常に `0`〕）から出力されます。価格情報が利用可能な場合、メディアコストはモダリティごと（画像単位、秒単位、文字単位、検索ユニット単位）に計算され、それ以外の場合は `0` になります（フェイルオープン）。

> **キャッシュヒット時のコストセマンティクス：** セマンティックキャッシュの HIT（`X-OmniRoute-Cache-Hit: true`）ではアップストリーム呼び出しが行われないため、`X-OmniRoute-Response-Cost` は `0.0000000000`（ヒットを処理するための**増分**コスト）になります。元のコスト、またはキャッシュがなければ発生していたコストは、`X-OmniRoute-Cost-Saved` で個別に報告されます。課金処理では `X-OmniRoute-Response-Cost` を合計してください（ヒットのコストはゼロです）。キャッシュ分析では `X-OmniRoute-Cost-Saved` を集計できます。

## 排他的マネージドセッションリース

排他的マネージドセッションリースは、オプトインのクライアントに依存しないルーティング契約です。1つのアクティブな所有者が、1つの適格なOmniRoute接続を保持します。これはモデルをリースしたり、OAuthを要求したり、特定のクライアントを識別したり、特定のプロバイダーを要求したりするものではありません。

認証するAPIキーには、`lease:exclusive`スコープと、明示的な空でない`allowedConnections`リストが必要です。データベースの変更境界は、キーの作成時および部分的な更新時に、両方のフィールドを同時に強制します。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

取得、更新、解放が成功した応答では、タイムスタンプ、`state`、および正確な正の`generation`が公開されますが、選択された接続や資格情報は決して公開されません。更新と解放は、JSONボディで世代を提供します。

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

アクティブなリース所有者は、現在のバインディングについてプライバシー保護された表示メタデータを明示的に要求できます。

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

このオプトインのステータスアクションは、不透明な所有者、認証されたマネージドAPIキー、および正確なアクティブな世代によって、1つのデータベーストランザクション内で保護されます。`displayName`は、トリミングされた設定済み接続名にすぎません。安全な設定済み名が存在しない場合は`null`になります。OmniRouteは、メールアドレスや生成されたアカウントIDを代用することはありません。プロバイダー値は機密性のない表示ラベルであり、生成された互換プロバイダー識別子ではありません。資格情報、トークン、Cookie、生の接続またはAPIキーID、所有者ハッシュ、フェンシングシークレット、および内部ルーティングデータは除外されます。

誤ったキー、誤った所有者、古い世代、欠落、期限切れ、解放済み、無効化されたルックアップはすべて、接続メタデータなしで同じ`409 LEASE_FENCE_STALE`エラーを返します。容量待機応答を受け取ったクライアントは、検査するアクティブなバインディングを持っていません。ルーティングがアクティブなリースを移行する際、同じ世代は有効なままであり、ステータスは新しいバインディングをアトミックに返し、古いものは決して返しません。取得、更新、解放、および待機中の応答は以前の形式を保持するため、既存のクライアントは変更されません。

このサーバー契約は、既存のOpenAI Codexの`/status`を変更しません。既存のCodexは現在、そのモデルプロバイダーと組み込みの認証/アカウント状態を報告しますが、任意のカスタムプロバイダーアカウントメタデータをレンダリングしません。後のクライアント統合でこのアクションを呼び出し、`connection.displayName`をどのように表示するかを決定する必要があります。

その後、すべてのマネージド推論リクエストは両方の制御ヘッダーを提供します。

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

正確な所有者、世代、アクティブな接続、および認証されたAPIキーは、サポートされている各アップストリーム試行の直前に保護されます。同じ接続を許可するキーであっても、別のキーで所有者と世代をリプレイすると失敗します。生の所有者は、永続化、ログ記録、リクエストスナップショットへの保持、またはアップストリームへの転送はされません。

一時的な競合は、`Retry-After`とともにHTTP `429`を返します。

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

この応答は、通常の適格なセットが空ではなく、すべての空き候補が外部のアクティブなリースによって保持されていたことを意味するだけです。サポートされていないモデル/プロバイダー、ポリシーの不一致、クールダウン、クォータ、ヘルス、およびその他の通常の適格性失敗は、既存のOmniRoute応答を保持します。

### `x-omniroute-compression`

リクエストごとの圧縮プランのオーバーライド。最高の優先順位を持ち、ルーティングコンボのオーバーライド、アクティブなプロファイル、自動トリガー、およびパネルのデフォルトよりも優先されます。値：

| 値            | 効果                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| `off`         | このリクエストでは圧縮を行いません。                                                                           |
| `default`     | パネル由来のデフォルトプロファイル（アクティブなプロファイルは無視されます）。非可逆エンジンはオフのままです。 |
| `safe`        | 重複排除と空白の折りたたみのみ。                                                                               |
| `allow-lossy` | 要約やスタイルの書き換えを含む、このリクエストのオペレータープランを維持します。                               |
| `engine:<id>` | 有効な場合、単一のエンジン（例：`engine:rtk`）。そのエンジンに対するリクエストごとのオプトイン。               |
| `<combo>`     | 名前付きコンボ。まず名前（大文字小文字を区別しない）で、次にIDで一致させます。                                 |

注記：

- 不明な値は無視されます（リクエストが拒否されることはありません）。解決は通常のオペレーターの優先順位に従って行われます。
- 複数のコンボが同じ名前を共有する場合、決定的な一致を得るにはコンボの**ID**を渡してください。
- `off`または`default`という名前のコンボは、名前で選択できません（これらのキーワードが最初に解釈されるため）。そのようなコンボはIDで参照してください。
- マスター圧縮スイッチは厳格なゲートです。圧縮がグローバルに無効になっている場合、このヘッダーで圧縮を有効にすることはできません。

適用されたプランは、応答ヘッダーでエコーバックされます。

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ここで`<source>`は、`request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default`、または`off`のいずれかです。

## 埋め込み

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

利用可能なプロバイダー: Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

カタログ ID は `provider/model` 形式です（例: `jina-ai/jina-embeddings-v5-omni-small`）。レジストリに存在する、プロバイダー名を含まない Jina モデル ID（例: `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）も解決されます。Jina の embed/rerank/classify/segment では、まずダッシュボードの `jina-ai` 認証情報が使用されます。`JINA_AI_API_KEY` は、ダッシュボードキーが存在しない場合にのみフォールバックとして使用されます。`jina-reader` カードは Reader / `r.jina.ai` 専用（`POST /v1/web/fetch`）であり、埋め込みやリランキングには使用されません。

マルチモーダル対応を明示しているレジストリモデルでは、プロバイダーに依存しない構造化項目を最大 32 件まで受け付けます。メディア項目のタイプは `text`、`image`、`audio`、`video`、`document` です。各メディアの `source` は、`{"type":"url","url":"https://..."}` または
`{"type":"base64","data":"...","media_type":"..."}` のいずれかです。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`、
およびファミリーエイリアス `jina-ai/jina-embeddings-v5-omni` → omni-small）は、Jina ネイティブの
EmbeddingsV5Request ドキュメントも受け付け、`https://api.jina.ai/v1/embeddings` に**そのまま転送します**。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

ネイティブの `{ image | audio | video | pdf }` 値には、公開 HTTPS URL、`data:` URI、または未加工の
base64 を指定できます。OmniRoute は、それらのオブジェクトを文字列化したり、ネイティブ画像 URL を取得したりしません。公開メディアは Jina 自身が取得します。追加の Jina フィールド（`task`、`normalized`、`truncate`、`embedding_type`）も転送されます。テキスト専用の Jina SKU では、テキスト以外のドキュメントは引き続き拒否されます。

セキュリティおよび転送上の制限:

- リモートメディア URL は公開 HTTPS である必要があります。標準形式の `{type,source:url}` 項目は、サーバー側で取得され（リダイレクトの再検証、タイムアウト、サイズ制限、公開 DNS、接続先の固定を適用）、プロバイダー呼び出しの前にインライン化されます。Jina ネイティブの `{image:"https://..."}` 項目は、同じ公開 HTTPS チェックの後にそのまま転送され、Jina が URL を取得します。
- インライン base64 メディアは、デコード後のサイズで項目ごとに 8 MiB、リクエスト全体で 16 MiB に制限されます。

プロバイダー向け変換（標準形式の項目が変更されずに転送されることはありません）:

- Jina マルチモーダルモデル: 最上位の各項目は、インラインメディアにデータ URI を使用した、モダリティをキーとする 1 つのオブジェクト（`text` / `image` / `audio` / `video` / `pdf`）になります。最上位項目ごとに 1 つのベクトルが生成されます。
- Gemini Embedding 2 ファミリー: 1 つの最上位配列が、`content.parts`（`text` または `inline_data`）を持つ単一のネイティブ `models/{model}:embedContent` リクエストになります。
- llama.cpp（`llama-cpp/<model>`、ローカルサーバーに読み込まれた任意のモデル）: 標準形式の `text` 項目はプレーン文字列になり、`image` / `audio` / `video` はそれぞれ 1 つの `{"content": [part]}` オブジェクトになります。インラインデータを使用し、llama-server のチャットコンテンツパーツ（`image_url`、形式が `wav` / `mp3` / `flac` の `input_audio`、`input_video`）に変換されます。最上位項目ごとに 1 つのベクトルが生成されます。サーバーは `--embedding --mmproj …` を指定して実行する必要があります。プロジェクターがない場合、サーバー自身がメディアを拒否します。`document` はサポートされていません。
- 明示的なモダリティメタデータがない不明または動的なモデルは、構造化入力を HTTP 400 で拒否します。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

サポートされていないモデルとモダリティの組み合わせでは、項目を強制変換せずに HTTP 400 が返されます。従来の文字列またはトークンリクエストに含まれる、入力以外の拡張フィールドは、引き続き変更されずにそのまま渡されます。

```bash
# すべての埋め込みモデルを一覧表示
GET /v1/embeddings
```

## 画像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "山々に沈む美しい夕日",
  "size": "1024x1024"
}
```

利用可能なプロバイダーには、OpenAI (GPT Image 2)、xAI (Grok Image)、Together AI (FLUX)、Fireworks AI、Nebius (FLUX)、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（ローカル）、ComfyUI（ローカル）が含まれます。

`n` を指定すると、`data[]` に `n` 枚の画像が返されます。アップストリーム API が呼び出しごとに 1 枚の画像を返すプロバイダー
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI）では、アップストリームへの呼び出しが `n` 回個別に実行され、同時実行数は最大 4 です。
固定の `seed` は呼び出しインデックスに応じてオフセットされるため（`seed`、`seed + 1`、…）、画像はそれぞれ異なりますが、
再現性は維持されます。`n` の上限は 10 です。いずれかの呼び出しが失敗した場合、リクエスト全体が失敗します。ファンアウト形式の一覧は、
`open-sse/handlers/imageGeneration/fanOut.ts` の `SINGLE_IMAGE_FANOUT_FORMATS` にあります。

ZenMux は既存の API キー接続を再利用し、`zenmux/` または `zm/` プレフィックスを受け付けます。

- `zenmux/openai/gpt-image-2` は ZenMux の OpenAI Images API を使用します。オプションには `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background`、`response_format` が含まれます。
- `zm/meta/muse-image-1.0` などの他のパブリッシャーは、ZenMux の Vertex AI `:predict`
  エンドポイントを使用します。`n` は `sampleCount` に、`aspect_ratio` は `aspectRatio` に、`image_size`
  （`1K`、`2K`、`4K`）は `sampleImageSize` にマッピングされます。ピクセル単位の `size` はアスペクト比のみを指定し、
  ピクセル寸法を保証するものではありません。サポートされる比率、解像度、枚数はモデルによって異なります。
- `zm/inclusionai/ming-image-0.1-design` は独自に寸法を決定します。`size`、
  `aspect_ratio`、`image_size` は省略してください。明示的な値を指定すると HTTP 400 が返されます。`output_format` を使用して、
  PNG、JPEG、WebP をリクエストできます。

この統合はテキストからの画像生成をサポートしますが、参照画像の編集はサポートしません。Vertex の
出力は `data[].b64_json` に正規化されます。`response_format: "url"` を指定すると、アップストリームの
HTTPS URL、または画像バイトのみが利用可能な場合は base64 データ URL が返されます。空またはフィルタリングされた出力の場合、
空の成功レスポンスではなくエラーが返されます。モデルへのアクセス可否は ZenMux アカウントによって異なります。
[ZenMux の Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) および
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) を参照してください。

```bash
# すべての画像モデルを一覧表示
GET /v1/images/generations
```

## ドキュメントOCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` は、`provider/model` プレフィックスを使用してOCRプロバイダーを選択します。プロバイダーを含まないモデルID（例:
`mistral-ocr-latest`）は登録済みのプロバイダーに解決され、`model` を省略した場合はデフォルトで
Mistral（`mistral-ocr-latest`）が使用されます。登録済みプロバイダー（`open-sse/config/ocrRegistry.ts`）:

| プロバイダーID                | モデルID             | `model` の値                                                | 備考                                                                                                                   |
| ----------------------------- | -------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（または `mistral-ocr-latest`） | 同期式 — 単一のアップストリーム呼び出しからレスポンスが直接返されます。                                                |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                 | 非同期アップストリーム（`analyze` + ポーリング）— 以下を参照してください。                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                     | Vertex AIの`openapi/chat/completions`パートナーエンドポイント経由の同期式 — 認証/URLについては以下を参照してください。 |

3つのプロバイダーはすべて、同じMistral形式の本文で応答します:

```json
{
  "pages": [{ "index": 0, "markdown": "# 抽出されたテキスト..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligenceのポーリングフロー

Azure Document Intelligenceの`analyze` APIは非同期です。最初のリクエストでは本文の代わりに
`Operation-Location`ヘッダーが返されるため、結果をポーリングする必要があります。ハンドラー
（`open-sse/handlers/ocr.ts`）は、そのURLを1秒ごとに最大30回ポーリングします。ポーリングレスポンスが`ok`でない場合、またはステータスが`"failed"`の場合は即座に失敗し（ポーリングを
継続せず）、試行回数の上限に達した後も処理が実行中の場合は`504`を返します。Azureの最終レスポンスは、
呼び出し元へ返される前に、Mistralで使用されるものと同じ`pages`/`markdown`形式へ正規化されるため、
クライアントコードでプロバイダーごとの特別な処理を行う必要はありません。

### Vertex AI DeepSeek OCRの認証とエンドポイント解決

`vertex-deepseek-ocr`は、OmniRouteがチャット/画像トラフィック向けにすでにサポートしているものと同じ
Vertex AI認証（`open-sse/executors/vertex.ts`）を再利用します。接続のAPIキーには、
Service Account JSON認証情報（JWTベアラーフローを介して短期間有効なOAuthアクセストークンと交換される）、
または発行済みのOAuthアクセストークンをそのまま使用できます。アップストリームエンドポイントURLは、
接続のプロジェクトとリージョンから構築される、Vertexの汎用`openapi/chat/completions`パートナーエンドポイントです。
明示的な`providerSpecificData.project`/`providerSpecificData.region`が常に優先されます。
それ以外の場合、プロジェクトはService Account JSONの`project_id`から取得され、リージョンのデフォルトは
`us-central1`です。どちらの解決も`open-sse/handlers/ocr.ts`
（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`）で行われ、
`handleOcr`へ処理を渡す前に`src/app/api/v1/ocr/route.ts`によって使用されます。

### モデル ID のプレフィックス（`?prefix=`）

ほとんどのモデルは、**プロバイダープレフィックス**付きで公開されます。どのプレフィックスが使用されるかは、`MODELS_CATALOG_PREFIX_MODE` 機能フラグによって制御されます。また、クエリパラメーターを使用して**リクエストごと**に上書きできます。これは、他のすべてのユーザーに適用されるサーバー全体の設定を変更せずに、整理された一覧を取得したいクライアントに便利です。

```bash
GET /v1/models?prefix=alias        # モデルごとに 1 つの ID — 短いエイリアスプレフィックス
GET /v1/models?prefix=dual         # 両方の形式（サーバーのデフォルト）
GET /v1/models?prefix=canonical    # 完全なプロバイダー ID プレフィックスのみ
```

| モード      | 出力                                                         | 備考                                                                                                                                                                                                          |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **および** `claude/claude-sonnet-4-6` | **デフォルト。** 両方の ID が同じモデルにルーティングされます。どちらかの形式をハードコードしたクライアント設定が引き続き機能するよう維持されています。カタログのサイズはおおよそ 2 倍になります。            |
| `alias`     | `cc/claude-sonnet-4-6`                                       | モデルごとに 1 エントリです。個別のエイリアスを持たないプロバイダーも引き続きエントリを出力するため、失われるものはありません。                                                                               |
| `canonical` | `claude/claude-sonnet-4-6`                                   | 完全なプロバイダー ID プレフィックス配下で、モデルごとに 1 エントリです。個別のエイリアスを持たないプロバイダー（例：`antigravity/…`、`agy/…`）も、ここで単一の ID を出力するため、失われるものはありません。 |

`dual` モードのミラーは、クエリパラメーターがなくても識別できます。プライマリ ID を指す `parent` フィールドを持っています。

モデルピッカーを表示するクライアントは、`?prefix=alias` をリクエストする必要があります。[OmniCopilot VS Code 拡張機能](../guides/VSCODE-COPILOT.md)もこの方法を使用しています。

### 検出フィルター（`?capability=`、`?min_context=`、`?kind=`、`?q=`）

`GET /v1/models` は、オプトインの検出フィルターを受け付けます。これらを指定しない場合、レスポンスは変更されません。フィルターは、呼び出し元にすでに表示されているカタログを絞り込み（API キーの権限が先に適用されます）、OpenAI 形式の `limit` / `after` ページングより前に実行されます。

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 一覧に指定したすべての機能が true である必要があります
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # カタログの `type`。指定のない行は `chat` です
GET /v1/models?q=sonnet&limit=10                           # ID または名前に対する、大文字と小文字を区別しない一致
```

| パラメーター  | 値                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | 非負整数。`context_length` と比較されます                                                           |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1～200 文字                                                                                         |

不明な値、または非負整数ではない `min_context`（例：`1.5`）を指定すると、HTTP `400` が返され、メッセージに有効な値の一覧が示されます。実装：
`src/app/api/v1/models/catalogFilters.ts`。

### モデルのショートリスト（`POST /v1/models/query`）

`POST /v1/models/query` は、`GET /v1/models` と同じカタログから、同じ認証およびキーごとの可視性を適用した、短く決定論的な一覧を返します。

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

すべてのフィールドは任意です。`capabilities` と `exclude` には、配列またはカンマ区切りの文字列を指定できます。`max_output` は `max_output_tokens` と比較されます。結果は `owned_by`、次に `id` の順でソートされます。`limit` のデフォルトは `20` で、`100` を超える値は `100` に制限されます。無効な JSON、不明なフィールド、または無効な値を指定すると、HTTP `400` が返されます。

### 個別に非表示にされたチャットモデル

プロバイダーページで **Hidden** とマークされたモデルはカタログから除外され、明示的にリクエストされた場合は HTTP `404` / `model_not_found` で拒否されます。このチェックでは、解決済みのプロバイダーとモデルが使用され、プロバイダーエイリアス、互換プロバイダーのノードプレフィックス、および接続のデフォルト設定も考慮されます。コンボは非表示のターゲットをスキップし、表示されている同系列のモデルを使用できます。実行可能なターゲットが残っていない場合は、同じエラーコードが返されます。非表示を解除すると、次のリクエストから有効になります。画像専用の可視性オーバーライドによって、同じ ID を持つチャットモデルが非表示になることはありません。

この個別モデル設定は、[モデル公開の許可／拒否リスト](../routing/MODEL_EXPOSURE_LIST.md)とは別のものです。後者は、明示的なディスパッチを維持しつつ、カタログでの公開と自動ルーティングの候補をフィルタリングします。API キーのモデル権限も引き続き独立して適用されます。デフォルトのカタログプレフィックスモードは `dual` のままです。

### thinking なしのモデルバリアント

thinking 対応の Claude モデルについては、`/v1/models` で、ID の先頭に `claude-3-omniroute-no-thinking/` が付いた **thinking なし**のバリアントも公開されます。

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

この id を選択すると（例: 常に `thinking` ブロックを付加する Claude Code の設定内）、推論を抑制した実際の `<provider>/<model>` に解決されます。具体的には、`/v1/messages` パスでは `thinking:{type:"disabled"}` が設定され、`/v1/chat/completions` パスでは `reasoning`/`reasoning_effort` フィールドが削除されます。このバリアントは、thinking をサポートし、かつ `disabled` を受け付ける Claude ファミリーのモデルにのみ表示されます（そのため、たとえば `disabled` を拒否する adaptive 専用モデルは除外されます）。オペレーターは、`ModelSpec.noThinkingAlias` を使用して、モデルごとにこのバリアントを強制的に有効または無効にできます。

すべてのPOSTルートは同じ形式に従います。`Bearer your-api-key`と、Zodで検証されたJSONボディ（`v1RerankSchema`、`v1ModerationSchema`、`v1AudioSpeechSchema`など。`src/shared/validation/schemas.ts`を参照）です。スキーマ検証に失敗した場合は4xxが返されます。

`Authorization: Bearer ...`を付与できないクライアント向けに、OmniRouteでは、クエリ文字列による互換方式（`?token=...`、`?apiKey=...`、`?api_key=...`、`?key=...`）または以下に記載する専用の`/api/v1/vscode/{token}/...`エンドポイントを通じて、URL内のAPIキーも受け付けます。

```bash
# リランキング（クラウドレジストリプロバイダー、または"<prefix>/<model>"形式のOpenAI互換プロバイダーノード）
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina分類（Foundation API認証情報）
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jinaセグメンター
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina検索（s.jina.ai、プロバイダーエイリアス：jina-search、jina-ai、jina）
POST /v1/search      { "query": "...", "provider": "jina-search" }

# モデレーション
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg（または指定された形式）のボディを返す
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTSには言語と音声が必要。`language`のデフォルトは"en"。音声が指定されていない場合、
# またはOpenAIの標準音声名（alloy、nova、…）が指定された場合は"Adrian"になる
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# 画像編集（multipart）
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# 動画／音楽生成（プロバイダーのプレフィックス付きモデルID）
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **リランキングプロバイダーノード:** `POST /v1/rerank` は、`<node-prefix>/<model>` として指定される OpenAI 互換プロバイダーノード
> （oMLX、vLLM、Infinity、ゲートウェイ配下の TEI など）にもルーティングされます。ループバック
> ノード（`localhost`、`127.0.0.1`、`172.16.0.0/12`）は常に対象となり、オペレーターが
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` に列挙したホスト名（たとえば
> `http://reranker:8080/v1` のような Docker/Compose サービス名）も対象となります。これらは直接呼び出され、
> `HTTP(S)_PROXY` や接続に固定されたプロキシを経由することはありません。その他の
> ホスト上のノード（LAN 内のマシンや Tailscale ピア）が対象となるのは、オペレーターが
> `RERANK_REMOTE_PROVIDER_NODES` 機能フラグを有効にし、**かつ**ノードのベース URL がプロバイダーの
> アウトバウンド URL ポリシー（`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）を満たす場合のみです。
> メモリエンジンのリランキングステップはループバック経由でこのルートを呼び出すため、
> Memory 設定の `rerankProviderModel` にも同じルールが適用されます。
>
> **ローカルサーバーの形式:** ノードは `<base>/v1/rerank` で呼び出され、404 の場合は `<base>/rerank`
> （Infinity、TEI）で呼び出されます。アップストリームのボディには、Cohere/OpenAI 形式のフィールド名（`documents`、
> `return_documents`）と TEI 形式のフィールド名（`texts`、`return_text`）の両方が含まれ、アップストリームのレスポンスは
> Cohere のエンベロープ形式に正規化されます。TEI のベア形式 `[{index, score, text}]`、簡易ゲートウェイからの
> `{results: [{index, score}]}`、および Voyage 形式の `{data: [...]}` は、すべて
> `{results: [{index, relevance_score, document?}]}` としてクライアントに返され、スコア順にソートされたうえで `top_n` 件に制限されます。

> **プロバイダーノードの検出:** OpenAI 互換プロバイダーノード上のモデルは、ノードプレフィックス付きで `GET /v1/models`
> に表示されます。エンドポイントメタデータを持たない行（ローカルの `/v1/models` リストでは一般的）は、
> ノードの `apiType` を継承します。そのため、`embeddings` ノードのモデルは `type: "embedding"`、`rerank`
> ノードのモデルは `type: "rerank"` となり、デフォルトで chat にはなりません。同期された行または手動で追加された行に
> 明示的な `supportedEndpoints` がある場合は、引き続きそちらが優先されます。

### Exa と Tavily の `provider_options`

Exa と Tavily は、名前空間付きのオプションバッグからプロバイダー固有のフィールドを読み取ります。
Exa は `provider_options.exa`（または `provider_options["exa-search"]`）、Tavily は `provider_options.tavily`
（または `provider_options["tavily-search"]`）を使用します。以下のキーのみが転送されます。各キーは
`open-sse/handlers/search/providerOptionsPassthrough.ts` 内の独自の Zod スキーマに照らして
検証され、型が正しくないキーは破棄されます。認証、ベース URL、`stream`、`outputSchema` を含む、
その他のキーはすべて無視されます。他のプロバイダーで使用されるフラットなキー（`cx`、`depth`、...）は、
従来どおり機能します。

| プロバイダー | トップレベルフィールド                                                                                                                                                                                                                                                                                                                                                    | ネスト                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa          | `type`、`category`、`userLocation`、`moderation`、`additionalQueries`、`objective`、`systemPrompt`、`compliance`（フラットなプリミティブ）、`startPublishedDate`、`endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` はデフォルトの `{ text: true, highlights: true }` にマージされます |
| Tavily       | `search_depth`、`chunks_per_source`、`time_range`、`start_date`、`end_date`、`include_published_date`、`filter_by_published_date`、`include_answer`、`include_raw_content`、`include_images`、`include_image_descriptions`、`include_favicon`、`include_domains_mode`、`language`、`filter_by_language`、`auto_parameters`、`exact_match`、`include_usage`、`safe_search` | —                                                                                                                                                                         |

汎用フィールドが常に優先されます。対象は `query`、`max_results`、`filters`（ドメイン）、`country`、
および `search_type` から導出されるトピックです。Exa では、`search_type: "news"` の場合、
`category: "news"` が維持されます。Tavily は `search_type: "finance"`（`topic: "finance"`）も受け付けます。

汎用の `time_range` は、両方のプロバイダーに渡されるようになりました。Exa には
`startPublishedDate`（ISO タイムスタンプ）、Tavily には `start_date`（`YYYY-MM-DD`）として渡されます。
`provider_options` で日付を明示的に指定した場合は、マッピングされた値よりも優先されます。

Exa の結果では、`id`、`highlight_scores`、`summary`、`subpages`、`entities`、`extras` が
`provider_raw` に保持されます。Tavily の結果では、`images` と `favicon` が保持されます。

コスト計算では、引き続きフラットなレジストリ `costPerQuery` が使用されます。Tavily の
`search_depth: "advanced"` は、1 回の呼び出しあたりのクレジット消費が多くなりますが、その差は
`usage.search_cost_usd` には反映されません。

## Web Fetch API

設定済みの Web Fetch プロバイダー（Firecrawl、Jina
Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）を介して URL からコンテンツを抽出します。

Parallel Extract（`parallel-search`、Parallel Search と同じ API キー）は Markdown
のみを返します。それ以外の `format` はすべて `400` となり、コンテンツは 100,000 文字に制限されます。対象ページ自体を抽出できない場合、アップストリームは HTTP 200 内でその旨を報告します。
OmniRoute はこれを固定メッセージ付きの `422` として返します。

| メソッド | パス            | 説明                                                          |
| -------- | --------------- | ------------------------------------------------------------- |
| POST     | `/v1/web/fetch` | URL を取得／スクレイピング — 本文は `v1WebFetchSchema` で検証 |

**認証:** Bearer API キー（`extractApiKey` + `isValidApiKey`）。ポリシーは `enforceApiKeyPolicy` によって適用されます。

**クォータ対応フォールバック（#8297）:** 明示的な `provider` が指定されていない場合、プール
（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`）は固定された
優先順位（先詰め方式）で走査されます。レート制限中ではあるものの設定済みのプロバイダーは、
リクエストを即座に終了させる代わりにスキップされます。また、リトライ可能な障害またはクォータに起因するアップストリーム障害
（HTTP 429 は常に対象。402/403 は Firecrawl/Tavily/TinyFish のクォータ方式の無料枠で対象 —
Jina Reader では対象外。また、通常の 400 不正リクエストは一切対象外）は、リクエスト時に認証情報が設定された
未試行の次のプロバイダーへフォールスルーします。プール内のすべてのプロバイダーを使い果たした場合、
エンドポイントは従来の汎用的な `400` の代わりに、単一の `429`（`Retry-After`
ヘッダー付き）を返します。明示的な `provider` が指定された場合、暗黙的なフォールバックは
**行われません**。レート制限中または障害が発生している明示指定プロバイダーは、そのプロバイダー自身のエラー
（レート制限の場合は `429`、それ以外の場合はアップストリームのステータス）をそのまま返します。

## WebSocketストリーミング

```bash
GET /v1/ws?handshake=1
```

WebSocketアップグレードのハンドシェイクを検証し、ワイヤープロトコルのメッセージ例（`request`、`cancel`）を返します。実際のWSフレームは、Next.jsのルートテーブル外にある同梱のWSサーバーによって処理されます。

**認証:** ハンドシェイク時のBearer APIキー。

### WebSocket経由のResponses API（codexのみ）

```bash
# HTTP APIと同じhost:port（デフォルトは20128）を使用し、接続をアップグレードします:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （または: -H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 最初のフレームは必ずresponse.createでなければなりません:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocketプロキシは、**`codex` 専用**（ChatGPT
バックエンド）として接続されています。API/ダッシュボードと同じポートで、パス `/v1/responses`、
`/responses`、`/api/v1/responses` をリッスンします。最初の `response.create` フレームで、
内部の `codex-responses-ws` ブリッジを介して認証と準備を行い、codex OAuth接続を
選択し、`wreq-js` トランスポート経由で `wss://chatgpt.com/backend-api/codex/responses`
へトンネリングします。**codex以外のモデルは拒否されます**（`codex_ws_provider_required`）。
クォータ共有ルーティングには `model: "qtSd/<group>/codex/<model>"` を使用してください。実装は
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` にあります。

**認証:** ハンドシェイク時のBearer APIキー。同梱のHTTPサーバー（`server-ws.mjs`）が
有効なエントリーポイントである必要があります（`app/server-ws.mjs` が存在する場合、デフォルトで有効です）。

#### モデルID: `codex/` プレフィックスなしのChatGPT IDを使用

OpenAI **Codex CLI** は、`supports_websockets = true` の場合に
クライアント側でモデル名を検証し、`codex/gpt-5.5` のような
**プロバイダープレフィックス付きIDを拒否します**（`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`）。**プレフィックスなし**のID（例: `gpt-5.5`）を送信してください。OmniRouteのブリッジは
codex専用であるため、アップストリームへトンネリングする前に、プレフィックスなしのIDをcodexモデルとして
再解決します（`resolveCodexWsModelInfo`）。これは、プレフィックスなしの
`gpt-5.5` がHTTP経由では本来別のプロバイダーにルーティングされる場合でも同様です。

#### OpenAI Codex CLIの設定

WebSocketをサポートするカスタムプロバイダーを `~/.codex/config.toml` に追加して、
Codex CLIの接続先をOmniRouteに設定します（既存の設定に影響を与えないよう、別の `CODEX_HOME` を使用してください）。

```toml
model = "gpt-5.5"                 # プレフィックスなしのID — "codex/gpt-5.5"ではありません
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 末尾にスラッシュを付けません。WS URLはここから導出されます（本番環境ではhttps/wssを使用してください）
wire_api = "responses"                    # 2026年2月以降でサポートされる唯一の値
supports_websockets = true                # Responses-over-WSトランスポートを有効にします
env_key = "OMNIROUTE_API_KEY"             # OmniRoute APIキー（Bearer）を保持します
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute APIキー（REQUIRE_API_KEY=falseの場合は任意のキー）
codex exec "Responda apenas: PONG"
```

CLIは `base_url + /responses` をWebSocketへアップグレードし、OmniRouteは選択された
codex OAuth接続へトンネリングします。ローカル
サーバーに対してエンドツーエンドで検証済みです。ChatGPTは `codex.rate_limits` + `response.created` を返し、完了結果を
ストリーミングします。

## セルフサービス利用状況（`/api/usage/om-usage`）

どの API キーでも、管理者認証なしで**自身の**利用状況とクォータを確認できます。これは、クライアント（CLI、OmniCopilot パネル）がキーホルダーに利用金額を表示するために使用するエンドポイントです。

```bash
# テキスト形式（従来の仕様 — ターミナル向けプレーンテキスト）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 構造化形式 — UI が利用する形式
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

キーでは **`allowUsageCommand`** が有効になっている必要があります（デフォルトでは無効です。ダッシュボードの API キーマネージャーでキーごとに切り替えます）。有効になっていない場合、エンドポイントは `403` を返します。

`?format=json` は判別可能な構造を返すため、呼び出し元が拒否レスポンスからデータフィールドを読み取ることはありません。成功時：

```jsonc
{
  "allowed": true,
  // キーでキー単位の利用上限（日次／週次の USD）が有効になっている場合にのみ存在：
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 選択されたプロバイダーのクォータスナップショット。まだ何もキャッシュされていない場合は null：
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // UI で複数のプロバイダーを並べて表示できるようにする、すべての接続のスナップショット：
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

拒否時（`401`：無効なキー／`403`：許可されていない場合）、同じルートは `{ "allowed": false, "error": { "message": "…" } }` を返します。`personal`／`provider` が存在するものの空である状態（キーは許可されているが、まだ情報を取得できていない状態）は拒否とは異なり、この違いを判別できるのは JSON 形式のみです。

**認証：** 呼び出し元自身の Bearer API キーを `isValidApiKey` で検証します。これは、`requireManagementAuth` によって保護されている管理インターフェース（`/api/keys/…`）ではありません。

### 生のクォータ割合とカットオフ調整済みクォータ割合

`/api/usage/om-usage` を利用する際、呼び出し元は**プレーンテキスト出力**と構造化された **JSON 出力**に表示される割合の違いに注意する必要があります。

| 項目               | プレーンテキスト形式（`/api/usage/om-usage`／`@@om-usage`）                               | JSON 形式（`?format=json`）                                            |
| :----------------- | :---------------------------------------------------------------------------------------- | :--------------------------------------------------------------------- |
| **出力フィールド** | `NN% left`（例：`20% left`）                                                              | `provider.quotas`／`providers[].quotas`                                |
| **測定値**         | **カットオフ調整済みの使用可能枠**：カットオフしきい値を上回る残容量                      | **生のアップストリームクォータ**：調整されていないプロバイダー測定値   |
| **カットオフ調整** | `effectiveRemainingPercent()` によりスケーリングされ、保護された予備枠は `0% left` と表示 | なし（プロバイダーから報告された生のスナップショット値）               |
| **しきい値データ** | 表示される割合に反映                                                                      | 接続ごとの `quotaWindowThresholds`（またはサーバーのデフォルト）に保存 |
| **主な利用者**     | 対話型 CLI、ターミナルプロンプト、人間のオペレーター                                      | プログラムによる連携、ダッシュボード、分析、課金トラッカー             |

#### カットオフ調整の計算式

OmniRoute は、アップストリームの枯渇を防ぐための予防的なクォータカットオフをサポートしています（接続の `quotaWindowThresholds`、プロバイダーのデフォルト、またはグローバルなレジリエンス設定で構成します）。クォータ期間にカットオフしきい値（例：`cutoff = 25%`）が設定されている場合、テキストレンダラーは残りの利用可能枠を次のように計算します。

- `remaining <= cutoff` の場合：`0%` を返します。
- `remaining > cutoff` の場合：`((remaining - cutoff) / (100 - cutoff)) * 100` を返します。

フォーマットされたテキスト出力では、これを最も近い整数に丸めます（`Math.round(...)`）。

#### 具体例

あるプロバイダーの期間について、**生の使用率が 60%**（したがって、**生の残りクォータは 40%**）であり、**残りクォータのカットオフしきい値が 25%** に設定されているとします。

| 表現                            | 計算                                                   |  残り   |                 推定使用率                  |
| :------------------------------ | :----------------------------------------------------- | :-----: | :-----------------------------------------: |
| **生の JSON（`?format=json`）** | アップストリームのスナップショット（`quotas[window]`） | **40%** |                   **60%**                   |
| **テキスト形式（`NN% left`）**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100`     | **20%** | **80%**（`100 - remaining` で計算した場合） |

- **テキストで残り 20% と表示される理由：** アカウントに物理的に残っている 40% のクォータのうち、25% はカットオフポリシーによって予約されています。ルーターがこの接続へのルーティングを停止するまでに呼び出し元が利用できる余裕は、使用可能な 75% のうち 15% しか残っていません。スケーリングにより、ルーティングが停止する時点で接続が正確に枯渇状態（`0% left`）を示すようになります。
- **JSON が生の値を保持する理由：** JSON ペイロードはプロバイダーの正確なスナップショット（`UsageSnapshot`）を返すため、外部ツールは、サーバー側の非可逆なスケーリングを介さずに、アップストリームの実際の利用状況と接続レベルの `quotaWindowThresholds` にアクセスできます。

#### 利用側の移行ガイダンス

外部連携（エディタープラグインやエージェント拡張機能など）が以前、テキストエンドポイント（`NN% left`）をスクレイピングし、使用率を `100 - NN` として計算していた場合、`?format=json` への移行には次の点が伴います。

- 生の JSON 値を読み取ると、**実際のアップストリーム消費量**（上記の例では使用率 60%）が反映されます。
- 連携側でテキストエンドポイントの使用可能枠のセマンティクスを維持する場合は、接続レベルのオーバーライドに `quotaWindowThresholds` を使用して、実効残量の計算式をクライアント側で評価できます。

## セマンティックキャッシュ

```bash
# キャッシュ統計を取得
GET /api/cache/stats

# すべてのキャッシュをクリア
DELETE /api/cache/stats
```

レスポンス例:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### レイテンシへの影響

セマンティックキャッシュが HIT した場合、**アップストリーム呼び出しなしで**
キャッシュからレスポンスが返されるため、報告される `X-OmniRoute-Response-Latency` は
（元のアップストリームレイテンシに関係なく）ほぼゼロになります。レイテンシを重視するクライアント
（ベンチマーク、p50/p99 モニタリング）は、`X-OmniRoute-Cache-Latency`
レスポンスヘッダーを確認する必要があります。

| 値          | 意味                                                                                   |
| ----------- | -------------------------------------------------------------------------------------- |
| `synthetic` | キャッシュから返されたレスポンス。レイテンシは実際のアップストリーム時間ではありません |
| _(なし)_    | 実際のアップストリーム呼び出しからのレスポンス                                         |

### キー単位のキャッシュバイパス

API キーでは、`cacheDefaultMode` を使用してセマンティックキャッシュの読み取りを無効にできます。

| 値       | 動作                                                                 |
| -------- | -------------------------------------------------------------------- |
| `legacy` | 通常のキャッシュ動作（デフォルト）                                   |
| `bypass` | キャッシュ検索を完全にスキップし、常にアップストリームを呼び出します |

キーの作成時（`POST /api/keys`）に設定するか、更新時（`PATCH /api/keys/[id]`）に変更します。

```json
{ "cacheDefaultMode": "bypass" }
```

### リクエスト単位のバイパス

キーの設定に関係なく、任意のリクエストでキャッシュをバイパスできます。

```
X-OmniRoute-No-Cache: true
```

OpenAI 互換プロバイダーのページでは、同じ編集／クリアコントロールが提供され、明示的なビジョン
サポートを持つモデルがマークされます。

カスタム Chat Completions ノードは、明示的な推論オプトアウトをアップストリームバックエンドに
適応させます。接続テストが成功すると、`/models` エントリが認識された `owned_by` 値
（`vllm`、`sglang`、または `llamacpp`）を示す完全一致のモデル ID ごとに、チャットテンプレート
コントロールが自動的に選択されます。透過的な OpenAI 互換ラッパーは、ネストされた `openai`
オブジェクト内に元のモデルエントリを保持する場合があります。検出は最大 3 層のそのような
エンベロープをたどります。所有情報が欠落している、不明、または競合しているモデルは、通常の
OpenAI の動作を維持します。検出は既存のカタログリクエストを再利用し、補完トークンを生成せず、
接続エンドポイントが変更されると無効化されます。

そのメタデータを公開しないバックエンドに対して動作を固定するには、既存のプロバイダー部分更新
API を使用します：

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

そのボディを `PUT /api/providers/<connection-id>` で送信してください。その接続では、`none` という明示的な推論エフォートは `chat_template_kwargs.thinking=false` および `chat_template_kwargs.enable_thinking=false` として送信されます。サーバー側の推論ルールがエフォートを強制しない限り、明示的なネイティブテンプレート値が優先されます。この設定は、カスタムの OpenAI 互換接続が Chat Completions ボディをディスパッチする場合にのみ適用されます。Responses リクエストおよび通常のプロバイダーは、ネイティブのリクエスト形式を維持します。`reasoningControl` を `openai` に設定すると通常の OpenAI `reasoning_effort` のパススルーが強制され、省略するか `null` に設定すると自動検出が使用されます。

Claude Code のオートモード分類器リクエストは、明示的な推論コントロールが含まれていない場合、ネイティブの thinking をデフォルトで無効にします。検出には、モデル名や completion 上限ではなく、Claude 形式リクエスト内の分類器のシステムマーカーが使用されます。明示的なボディコントロール、サポートされる effort/thinking ヘッダー、ルーティングルール、および解決されたモデルのエフォートは、既存の優先順位を維持します。両方の分類器ステージは、プロンプト、completion 上限、停止シーケンス、および実際のアップストリームの権限判定を保持します。第 2 ステージは、要求された可視の推論を通常のテキストとして引き続き生成できます。

### バージョンとリリースチャンネル

```bash
GET /api/system/version
```

ループバック専用の管理ルート(管理者認証)。実行中のバージョン、公開されている最新バージョン、自動更新のステータスを返します。`releaseChannel` と `channels` は追加フィールドです(rail 3.8.54)。`channel` は従来の意味を維持します — ダッシュボードアップデーターが使用するデプロイモード(`npm`、`source` または `docker-compose`)です。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 実行中のビルドの npm チャンネル:`-nightly.*` バージョンの場合は `nightly`、その他のプレリリース(`-rc.*`、`-beta.*`、`-alpha.*`)の場合は `next`、`channels.latest` より古いメジャーバージョンの安定版の場合は `lts`、それ以外の場合は `latest` です。公開時に npm dist-tag を決定する `scripts/release/dist-tag.mjs` と同じルールです。
- `channels` — 各 dist-tag の公開されている最新版。`npm view omniroute dist-tags`(レジストリ HTTP フォールバック)から取得され、`latest` と同じ 10 分間の TTL でキャッシュされます。`latest` は常に存在します(`latest` フィールドにフォールバックし、それでも取得できない場合は `"unavailable"` になります)。`next`、`nightly`、`lts` はその dist-tag が存在する場合にのみ表示されます。`Cache-Control: no-cache` リクエストを送信すると、両方のルックアップが更新されます。

チャンネルモデル(`latest` = 4.0 GA までの v3、`next` = rc、`nightly` = `develop` ビルド、`lts` = 4.0 GA 後の v3 パッチ)については、`docs/ops/RELEASE_STRATEGY.md` に記載されています。

## トークン制限

API キーごとの **トークン** 予算（上記の USD ベースの予算とは別）。リクエストパス上でインラインに適用されます。キーの現在のウィンドウ使用量が上限に達すると、リクエストは `429 Too Many Requests` で拒否されます。制限は、特定の `model`、`provider` にスコープ設定することも、キー全体に `global` に適用することもできます。複数の制限がリクエストに一致する場合は、最も厳しい制限が優先されます。

```bash
# キーのトークン制限を一覧表示（現在のウィンドウ使用量を含む）
GET /api/usage/token-limits?apiKeyId=key-123

# トークン制限を作成または更新
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ID を指定してトークン制限を削除
DELETE /api/usage/token-limits?id=tl-abc
```

> **スキーマに関する注記**（`setTokenLimitSchema`）：`apiKeyId` と `scopeType`（`model` | `provider` | `global`）は必須です。`scopeType` が `global` でない限り、`scopeValue` は必須です（例：`model` スコープではモデル ID、`provider` スコープではプロバイダー ID）。`tokenLimit` は正の整数である必要があります（文字列から変換されます）。任意項目：`id`（作成時は省略し、更新時は指定）、`resetInterval`（`daily` | `weekly` | `monthly`、デフォルトは `monthly`）、`resetTime`（`HH:MM`）、`enabled`（デフォルトは `true`）。`GET` レスポンスでは、各制限に `tokensUsed`、`remaining`、`windowStart`、`periodStartAt`、`nextResetAt` が追加されます。これは管理クラスのエンドポイントです（認証は authz パイプラインによって一元的に適用されます）。

## リクエスト処理

1. クライアントが `/v1/*` にリクエストを送信
2. ルートハンドラーが `handleChat`、`handleEmbedding`、`handleAudioTranscription`、または `handleImageGeneration` を呼び出す
3. モデルを解決（プロバイダー/モデルの直接指定、またはエイリアス/コンボ）
4. アカウントの可用性をフィルタリングし、ローカル DB から認証情報を選択
5. チャットの場合：`handleChatCore` がセマンティック/シグネチャキャッシュを確認し、コンボの圧縮設定を解決
6. 有効な場合、プロバイダー向け変換の前にプロアクティブ圧縮を実行（`lite`、Caveman、RTK、またはそれらのスタック）
7. プロバイダーエグゼキューターがアップストリームリクエストを送信
8. レスポンスをクライアント形式に再変換（チャット）するか、そのまま返却（埋め込み/画像/音声）
9. 使用量、圧縮分析、リクエストログを記録
10. エラー発生時、コンボルールに従ってフォールバックを適用

アーキテクチャの完全なリファレンス：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 耐障害性(拡張)

OmniRoute は 3 つの独立した一時障害メカニズムを公開しています。以下の管理エンドポイントにより、オペレーターはそれらの状態を読み取り、上書きできます。

| スコープ               | 状態の保存場所                         | 読み取り                                  | リセット / クリア                             |
| ---------------------- | -------------------------------------- | ----------------------------------------- | --------------------------------------------- |
| プロバイダーブレーカー | `domain_circuit_breakers` + インメモリ | `/api/monitoring/health`                  | `POST /api/resilience/reset`                  |
| 接続のクールダウン     | プロバイダー接続の `rateLimitedUntil`  | `/api/rate-limits`, `/api/providers/[id]` | (遅延的に再有効化。プロバイダー PUT でクリア) |
| モデルのロックアウト   | インメモリのモデル可用性レジストリ     | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`      |

`PATCH /api/resilience` は、`providerBreaker.oauth` および `providerBreaker.apikey` の下でプロバイダーブレーカーの上書きを受け付けます。各プロファイルは `degradationThreshold`、`failureThreshold`、`resetTimeoutMs` をサポートしており、同じフィールドは Dashboard → Settings → Resilience にも公開されています。

```bash
# 単一のモデルロックアウトをクリア
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# すべてのロックアウトを消去
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

完全な概念リファレンスとブレーカーのデフォルト値については、[`CLAUDE.md`](../../CLAUDE.md) の「Resilience Runtime State」および [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) を参照してください。

### レート制限キューと自動有効化のセーフティネット

- **サポートされる書き込みパス**: 接続のレート制限保護を切り替える、サポートされる管理エンドポイントは、ボディ `{"connectionId": "<id>", "enabled": true|false}` を指定する `POST /api/rate-limits` です。`PUT /api/providers/[id]` は意図的に `rateLimitProtection` を変更・反転しません (#11278)。
- **`enabled: false` のセマンティクス**: `enabled: false` を設定すると接続の明示的な保護は解除されますが、アクティブな API キー接続がグローバルな自動有効化セーフティネット (`autoEnableApiKeyProviders = true`) から**除外されるわけではありません**。`reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) では、`false` と `undefined` は同等です。明示的な保護のないアクティブな API キー接続は、自動有効化セーフティネットの下で保護されたままになります。
- **グローバルな無効化**: API キー接続をレート制限キューなしで実行するには、`RATE_LIMIT_AUTO_ENABLE=false` (環境変数) または `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) でセーフティネットをグローバルに無効化します。

## MCP サーバー

OmniRoute には、3 つのトランスポート（stdio、SSE、streamable-http）とスコープ付きツールを備えた Model Context Protocol サーバーが組み込まれています。以下のダッシュボードエンドポイントは、ステータス／監査データを読み取り、HTTP トランスポートをプロキシします。

| メソッド | パス | 説明 |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ハートビート、トランスポート、オンライン状態、最終呼び出し、上位ツール、24 時間の成功率 |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` を含む MCP ツール一覧 |
| GET | `/api/mcp/sse` | SSE トランスポート用の SSE ストリームを開く（MCP が無効、またはトランスポートが一致しない場合は `503` を返す） |
| POST | `/api/mcp/sse` | SSE トランスポートで JSON-RPC フレームを送信 |
| GET | `/api/mcp/stream` | Streamable HTTP トランスポートの SSE 側を開く（サーバー起点のメッセージ） |
| POST | `/api/mcp/stream` | Streamable HTTP トランスポートで JSON-RPC フレームを送信 |
| DELETE | `/api/mcp/stream` | Streamable HTTP セッションを終了 |
| GET | `/api/mcp/audit` | 監査ログを照会 — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | 監査統計を集計（合計、成功率、平均所要時間、上位ツール） |

**認証:** `sse`／`stream` トランスポートは MCP 固有の認証方式（`mcp` スコープを持つ Bearer API キー）に従います。`status`／`tools`／`audit*` ルートはダッシュボードから読み取り可能です（ダッシュボードホストへのアクセスに必要な認証以外に、追加の認証は不要です）。

> どちらの HTTP トランスポートも `settings.mcpEnabled` と `settings.mcpTransport` によって制御されます。トランスポートが一致しない場合は `400`、MCP が無効な場合は `503` が返されます。

## A2A サーバー

OmniRoute は、A2A（Agent-to-Agent）JSON-RPC 2.0 エンドポイントに加え、確認やダッシュボードで使用するための REST ラッパーを公開します。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY が設定されていない場合は省略可能
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

サポートされるメソッド（すべて `settings.a2aEnabled` によって制御されます）：

| メソッド         | 説明                                                         |
| ---------------- | ------------------------------------------------------------ |
| `message/send`   | スキルを同期実行し、`{task, artifacts, metadata}` を返します |
| `message/stream` | 同じスキルセットをストリーミング SSE で実行します            |
| `tasks/get`      | `taskId` を指定してタスクを取得します                        |
| `tasks/cancel`   | `taskId` を指定してタスクをキャンセルします                  |

組み込みスキル：`smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### エージェントカード

```bash
GET /.well-known/agent.json
```

公開 A2A エージェントカード（名前、説明、機能、スキルカタログ、認証スキーム）を返します。公開キャッシュの有効期間は 1 時間です。認証は不要です。

### REST ヘルパー

| メソッド | パス                         | 説明                                                                                                             |
| -------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/a2a/status`            | A2A の有効状態、タスク統計、キャッシュされたエージェントカードの概要                                             |
| GET      | `/api/a2a/tasks`             | タスク一覧 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST     | `/api/a2a/tasks`             | （REST ヘルパーとしては未実装 — JSON-RPC の `message/send` を使用して作成）                                      |
| GET      | `/api/a2a/tasks/[id]`        | 1 件のタスクを取得                                                                                               |
| POST     | `/api/a2a/tasks/[id]/cancel` | タスクをキャンセル                                                                                               |

**認証：** REST ヘルパーは管理認証なしで動作し、ダッシュボードから参照できます。JSON-RPC の `/a2a` ルートは、設定されている場合に Bearer `OMNIROUTE_API_KEY` を使用します。

## 認証

4つの認証情報ファミリー（ダッシュボードセッション、ローカルCLIトークン、`oma_live_…` Access Token、管理スコープ付きAPIキー）と、推論キーとの違いについては、[管理認証](../guides/MANAGEMENT-AUTH.md)を参照してください。

- ダッシュボードルート（`/dashboard/*`）では、`auth_token` Cookieを使用します
- ログインでは保存済みのパスワードハッシュを使用し、利用できない場合は`INITIAL_PASSWORD`にフォールバックします
- `requireLogin`は`/api/settings/require-login`経由で切り替えられます
- `REQUIRE_API_KEY=true`の場合、`/v1/*`ルートではBearer APIキーが必要になることがあります
- このリファレンスにおける「管理トークン」/「管理スコープ付きAPIキー」は、上記ガイドに記載されているファミリーのいずれかを意味し、未定義の追加シークレット種別を指すものではありません

> **破壊的変更（v3.8.0）** — `/api/v1/agents/tasks/*`およびクールダウン管理エンドポイントでは、**管理認証**（ダッシュボードの`auth_token` Cookieまたは管理スコープ付きAPIキー）が必須になりました。以前、認証なしでこれらのルートを呼び出していたクライアントは、`401 Unauthorized`を受け取ります。コミット`588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）を参照してください。
