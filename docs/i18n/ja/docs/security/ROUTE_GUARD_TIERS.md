## 概要

OmniRoute のすべての管理 API ルートは、3 つの保護階層のいずれかに分類されます。分類は静的で、`src/server/authz/routeGuard.ts` で定義されており、他の認証分岐が実行される前に評価されます。

## ティア

### ティア 1 — LOCAL_ONLY

**適用方法:** `isLocalOnlyPath(path)` → ループバックホストのチェック  
**バイパス:** デフォルトではなし。リクエストに `manage` スコープを持つ有効な API キーが含まれる場合に限り、`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 内のパスに対する限定的な例外があります（[manage スコープの例外](#manage-scope-carve-out)を参照）。

これらのルートは、子プロセスを起動するか、ランタイムコードを実行します。これらを非ループバックトラフィックに公開すると、有効な JWT を取得した攻撃者（たとえば Cloudflared/Ngrok トンネル経由）がプロセスの起動を引き起こせるようになります。これは既知の CVE クラスです（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj とは何か（攻撃クラス）:** 管理/エージェントサーバーが、サブプロセス（`npm install`、`node`、ブラウザー、プロキシ、`git`、`tar` など）を起動するエンドポイントを公開します。オペレーターが OmniRoute を nginx/Cloudflare/Tailscale トンネルの背後に配置し、JWT が漏洩した、または認証が誤って構成されていたために、そのエンドポイントへホスト外部から到達できる場合、攻撃者は「API を呼び出す」ことを「ホスト上でコマンドを実行する」こと（リモートコード実行）に変えられます。OmniRoute は、プロセスを起動できるすべてのルートに対して、**あらゆる認証チェックよりも前に、ループバックホストのチェックを無条件で適用する**ことで、これを防ぎます。トンネル経由でトークンが漏洩しても、プロセス起動処理には到達できません。

**LOCAL_ONLY の完全なセット。** 正式な情報源は、`src/server/authz/routeGuard.ts` 内の `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` です。以下の表は現在の状態を反映しています。`check-route-guard-membership` ゲートは、プロセス起動が可能なプレフィックス配下にあるすべての `route.ts` を列挙し、いずれかがローカル限定として分類されていない場合は CI を失敗させます。

**違反時のレスポンス：** `403 LOCAL_ONLY`

#### 管理スコープの例外

LOCAL_ONLY パスの一部は、リクエストに `Authorization: Bearer <api-key>` が含まれ、そのメタデータに `manage` スコープ（または `admin`）が含まれている場合に限り、非ループバックからもアクセスできます。この例外は `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` を介してパスごとに明示的に制御されるため、新しい LOCAL_ONLY パスのデフォルトは引き続き厳格なループバック限定となります。未認証のリクエスト、および管理スコープを持たないキーによるリクエストは、引き続き `403 LOCAL_ONLY` で拒否されます。

現在、例外適用可能なプレフィックスは `/api/mcp/` のみです。`/api/cli-tools/runtime/` と `/api/services/` は、任意のサブプロセス（`npm install`、`node`）を起動できるため、意図的に除外されています。これはまさに LOCAL_ONLY 層が防止するために存在する CVE の種類です。

**#7895 — `mcp:connect` の限定スコープ：** `/api/mcp/` の例外では、限定的な `mcp:connect` スコープ（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`）を保持する Bearer キーも受け入れます。これは `src/server/authz/policies/management.ts` の `hasMcpConnectOrManageScope()` によって確認されます。このスコープは `/api/mcp/` のみに限定されます。`mcp:connect` は、その他の管理ルート（将来追加される可能性がある他のすべての LOCAL_ONLY 例外プレフィックスを含む）に対して一切の権限を付与せず、`MANAGEMENT_API_KEY_SCOPES` から意図的に除外されています。`manage`/`admin` を保持するキーは従来どおりこの例外を通過します。`mcp:connect` は、広範な管理アクセスを必要としないリモートの MCP 専用呼び出し元向けの、より権限の低い代替手段です。

| リクエスト                                               | パス                       | 結果                 |
| -------------------------------------------------------- | -------------------------- | -------------------- |
| 非ループバック、Bearer なし                              | `/api/mcp/*`               | 403 LOCAL_ONLY       |
| 非ループバック、`manage` スコープを持つ Bearer           | `/api/mcp/*`               | 許可                 |
| 非ループバック、`mcp:connect` スコープを持つ Bearer      | `/api/mcp/*`               | 許可                 |
| 非ループバック、`manage`/`mcp:connect` を持たない Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY       |
| 非ループバック、`mcp:connect` スコープを持つ Bearer      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY       |
| 非ループバック、`manage` スコープを持つ Bearer           | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY       |
| ループバック、Bearer の有無を問わない                    | 任意の LOCAL_ONLY          | 許可（ゲートを通過） |

#### オペレーター向けガイダンスと監査

OmniRoute をリバースプロキシまたはトンネル（nginx、Caddy、Cloudflare Tunnel、Tailscale、Ngrok）の背後で実行する場合でも、ループバックチェックによって上記の起動可能なルートは保護されます。クライアントアドレスが非ループバックであるリクエストは、**認証が実行される前に** `403 LOCAL_ONLY` で拒否されるため、漏洩した JWT でも起動処理には到達できません。オペレーターには、次の 2 つの責任が残ります：

- **403 を「修正」するために、クライアント IP をループバックとして偽装しないでください。**
  `X-Forwarded-For: 127.0.0.1` を設定したり、送信元アドレスをループバックに
  書き換えるプロキシを使用したりすると、この層で防いでいる RCE クラスの脆弱性が
  そのまま再び有効になります。プロキシ経由で公開するのは
  ダッシュボード/API に限り、プロセス起動可能なルートは決して公開しないでください。
- **`manage` スコープによるバイパスは最小限に保ってください。** バイパス可能なのは
  `/api/mcp/` のみであり、かつ `manage` スコープの API キーを使用した場合に限られます。
  `SPAWN_CAPABLE_PREFIXES` をバイパスリストに追加することは一切できません。zod スキーマが
  それらを拒否し、実行時にも `isLocalOnlyBypassableByManageScope` が拒否します
  （多層防御）。ダッシュボード上の「バイパス可能にできない」とは、このことを意味します。
  同じ拒否リストには、プロセスを起動しないものの、リモートから決して到達可能にしては
  ならない LOCAL_ONLY ルートもいくつか含まれています。具体的には、
  `/api/oauth/kiro/auto-import`（ホストローカルの Kiro 認証情報ファイルを読み取る）、
  `/api/discovery/`、および `/api/issue-agent/` です。実行時のスナップショットローダーも、
  保存済み設定行からこのようなエントリを除外し、従来の JSON インポート
  （`/api/settings/import-json`）もバイパスキーを書き込みません。
  すべての `LOCAL_ONLY_API_PREFIXES` エントリは、拒否リストに含まれるか、
  バイパス対象として適格であることをレビュー済みでなければなりません
  （`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`）。`/api/providers/` 配下にある、
  動的セグメントおよび静的パスのプロセス起動可能なルート（例: `/login`、
  `/refresh-cursor`）は、フラットな `SPAWN_CAPABLE_PREFIXES` 配列ではなく、
  `src/shared/constants/spawnCapablePrefixes.ts` 内の正規表現ベースの
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` によってカバーされます。
  フラットな配列でこれらを捕捉するには `/api/providers/` プレフィックス全体を
  対象にする必要があり、リモートダッシュボードがプロバイダーの CRUD に正当に使用する
  ルートツリーまで過剰に制限してしまうためです。

**アクセスの監査** — ホスト外からこれらのルートにアクセスされていないことを確認するには:

- `/dashboard/settings/security` の **認可インベントリ**を開いてください。現在有効な
  LOCAL_ONLY プレフィックスのリスト、バイパス可能なプレフィックス、およびコンパイル時に
  定義されたプロセス起動可能（「バイパス可能にできない」）セットが表示されます。
- リバースプロキシ/アクセスログで、上記プレフィックスと非ループバックのクライアント
  アドレスの組み合わせを grep してください。そのようなアクセスが
  `403 LOCAL_ONLY` ではなく `200` を返している場合、プロキシが実際のクライアント IP を
  隠しています。プロキシを修正してください。
- OmniRoute のログで、これらのパスのいずれかに対する `403 LOCAL_ONLY` が記録されている
  場合、それはガードが意図どおりに機能していることを示しており、抑制すべきエラーでは
  ありません。

#### 呼び出し元チェックゲートを備えた、リモートから到達可能なルート

一部のルートは、リモートダッシュボードから到達可能な状態を維持しつつ、ローカルの
呼び出し元に対してホスト側のプローブ（`which <binary>`、`<binary> --version`、
`tailscale status --json`）を実行する必要があります。これらは `GET` に対して
LOCAL_ONLY ではありません。代わりに、ハンドラーが `getRequestPeerLocality()`
（`src/shared/utils/apiAuth.ts`）を使用して信頼済みピアの判定結果を読み取り、
`loopback` / `lan` の呼び出し元に対してのみプローブを実行します。`remote` の
呼び出し元には、プロセスを起動しないソース（永続化された状態、設定、fs チェック）から
構築した同じ形式のレスポンスが返され、`probed: false` として示されます。

| ルート                                                           | リモートの呼び出し元に対してスキップされるプローブ                                        |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI ランタイムプローブ（`allowLocalRuntimeProbe`）および CLI フォールバックのプロセス起動 |
| `GET /api/headroom/status`                                       | `which headroom` および python の `--version` プローブ                                    |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`、`tailscale status/funnel --json`、`which brew`                         |
| `GET /api/tunnels/cloudflared`（LOCAL_ONLY から除外された GET）  | `which cloudflared` による PATH 検索                                                      |

ホストをプローブする新しい読み取りルートは、同じパターンに従うか、最初から
LOCAL_ONLY に分類します。

### Tier 2 — ALWAYS_PROTECTED

**適用方法:** `isAlwaysProtectedPath(path)` → `requireLogin=false` によるバイパスをスキップ  
**バイパス:** `requireLogin=false` の場合でも不可。JWT が常に必須

これらのルートは破壊的、または元に戻せない操作を実行します。「パスワードなし」の
インストール環境でこれらを許可すると、同じ LAN 上の誰もがデータベースを消去したり、
サーバープロセスを強制終了したりできることになります。

| パス                                      | 理由                                                          |
| ----------------------------------------- | ------------------------------------------------------------- |
| `/api/shutdown`                           | サーバープロセスを終了する                                    |
| `/api/settings/database`                  | データベースのエクスポート、インポート、消去                  |
| `/api/db-backups`                         | データベースの完全バックアップアーカイブへのアクセス          |
| `/api/settings/export-json`               | 設定 BLOB 全体（シークレットを含む）をエクスポートする        |
| `/api/settings/import-json`               | 設定 BLOB 全体を置き換える                                    |
| `/api/providers/health-autopilot/actions` | 自動修復アクションを実行する                                  |
| `/api/settings/obsidian`                  | 任意の vault ルート用に再利用可能な WebDAV 認証情報を発行する |
| `/api/relay/tokens`                       | Mints, lists, edits and revokes relay tokens                  |

**違反時のレスポンス:** `401 Authentication required`

`/api/settings/obsidian` は、その子パス `/webdav` も対象とします。`POST` は、
このパイプラインの外側で Next.js より先にカスタム Node レイヤーによって提供される
WebDAV ファイルサービスに、呼び出し元が選択したルートを設定し、新しく発行した
Basic 認証情報をレスポンスに含めます。`DELETE` はその認証情報をローテーションし、
親ルートの `POST` は Obsidian REST API トークンを保存します。GHSA-62vw が
隠したのは `GET` によるパスワードの露出だけであり、認証情報の発行自体は依然として
フェイルオープン層にありました（GHSA-7pq4-8pvv-rx7r）。
`enableObsidianVaultSync()` はさらに、データディレクトリそのもの、データディレクトリ内、
またはデータディレクトリを内包する vault を拒否します。

#### 認証情報のエクスポートはオペレーター専用

上記の階層では、_何らかの_認証情報が必要かどうかだけを決定します。保存済みの認証情報をダウンロードするルートでは、ハンドラー内でさらに2段階目のチェックが行われます。`GET /api/settings/export-json`（復号されたプロバイダー接続情報と未加工の API キー）、`GET /api/db-backups/export`（SQLite ファイル）、および `GET /api/db-backups/exportAll`（完全なアーカイブ）は、`requireOperatorCredential()`（`src/lib/api/operatorCredential.ts`）を呼び出します。これは、ダッシュボードセッション、ローカル CLI サブジェクト、またはログインが無効化されているインスタンスを受け入れますが、あらゆるスコープ（`manage` および `admin` を含む）の API キーと、`oma_` アクセストークンに対しては `403` を返します。同期トークンの発行（`POST /api/sync/tokens`）では、同じヘルパーに加えて、信頼されたループバック内部サービストークンを使用します。

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### 新規インストール時のブートストラップはループバック限定 — `Host` ではなく実際のピアに基づく

管理パスワードが設定されておらず（かつ `INITIAL_PASSWORD` もない）場合、`src/shared/utils/apiAuth.ts` の `isAuthRequired()` は、匿名ブートストラップを**ループバックピアに対してのみ**開放したままにします。ループバックかどうかは、信頼されたピアシグナルから次の優先順で判定されます。トークンによって記録された実際の TCP ピア（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`、ポリシーから見える情報）、パイプライン自身の `AUTHZ_HEADER_PEER_LOCALITY` 判定結果（ルートハンドラーから見える情報で、`OMNIROUTE_PEER_STAMP_TOKEN` が設定されている間のみ信頼される）、または直接呼び出すクライアントの場合は実際のソケットピアです。`Host` / `nextUrl.hostname` は一切参照されません。また、最初のパスワード設定（`POST /api/settings/require-login`）にも同じ制約が適用され、すべてのネットワークピアに開放されることはありません（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` は自身の `peerContext` 判定結果を明示的に下流へ渡すため、ORIGINAL（除去処理前）リクエストのヘッダーによって判定されることはありません。

### Tier 3 — MANAGEMENT（デフォルト）

その他すべての管理ルートです。`requireLogin=false` が設定されていない限り、認証が必要です。CLI トークンは、これらのルートを認証できます（ループバック + 有効な HMAC）。

## 評価順序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ループバック                                  → 次へ進む
     → 非ループバック、manage スコープの Bearer
        かつ isLocalOnlyBypassableByManageScope      → 許可 (management_key)
     → それ以外                                      → 拒否 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 許可 (system)
  3. hasValidCliToken(headers)?
     → 許可 (cli) [ループバック + timingSafeEqual による HMAC チェック]
  4. isAlwaysProtectedPath(path) または requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 許可 (dashboard_session)
     → バイパス不可のパスで manage スコープの Bearer?
        → 許可 (management_key)
     → 拒否 401/403
  5. requireLogin=false?
     → 許可 (anonymous)
```

ステップ 1 の manage スコープ分岐は、LOCAL_ONLY ルートの条件を満たせる唯一の認証済み経路です。認証バックエンドで障害が発生した場合は 403 ではなく 503 を返すため、期限切れの DB によって暗黙的に「拒否」へダウングレードされることはありません。

## 新しい spawn 対応ルートの追加

1. `src/server/authz/routeGuard.ts` の `LOCAL_ONLY_API_PREFIXES` にパスプレフィックスを追加する
2. `tests/unit/authz/routeGuard.test.ts` に、新しいプレフィックスに対して `isLocalOnlyPath()` が true を返すことを確認するテストを追加する
3. **この手順は絶対に省略しないでください** — `CLAUDE.md` のハードルール #15 を参照してください
4. 判断する：このルートは `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` にも含めるべきか？
   デフォルトの回答は **いいえ** です。manage スコープ保持者に公開しても安全なルート（すなわち、ユーザーが制御できる任意のコードを spawn しないルート）に限って明示的に追加してください。

## OpenAPI でのセキュリティティアの文書化

`docs/openapi.yaml` に新しいルートを追加する際、そのルートが `routeGuard.ts` によって分類されている場合は、対応するベンダー拡張を適用してください。

| routeGuard.ts の分類         | YAML アノテーション        | 適用される制約                                       |
| ---------------------------- | -------------------------- | ---------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 非ループバックからのアクセスを無条件でブロック       |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false` の場合でも認証が必要            |
| 内部管理/debug ルート        | `x-internal: true`         | デフォルトで /dashboard/api-endpoints に表示されない |
| なし（公開 / 標準認証）      | （アノテーション不要）     | 標準の `requireLogin` によって制御されるアクセス     |

### 検証

2 つのスクリプトにより、YAML アノテーションと `routeGuard.ts` の整合性が強制されます。

- `scripts/check/check-openapi-coverage.mjs` — カバレッジが 99% 未満の場合に失敗
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` または
  `x-always-protected` のアノテーションがコンパイル時定数と一致しない場合に失敗

両方のスクリプトは、pre-commit フックおよび CI で実行されます。

### 誤検出に関するルール

`routeGuard.ts` の定数に含まれていないルートに `x-always-protected` または `x-loopback-only` が付与されている場合、カバレッジスクリプトは失敗します。修正方法は常に、YAML を `routeGuard.ts` が実際に適用している内容に合わせることです。適用ロジックも実装せずにルートを `routeGuard.ts` へ追加してはいけません。
