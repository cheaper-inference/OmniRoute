ガードレールは、OmniRoute とアップストリームプロバイダーとの境界で、安全性、ポリシー、
コンテンツ変換を強制します。各ガードレールは、リクエストペイロード（`preCall`）と
アップストリームレスポンス（`postCall`）を検査できます（オプションで拒否、変換、
注釈付けも可能）。

このシステムは**フェイルオープン**です：ガードレールが実行中に例外をスローしても、
レジストリはエラーを記録し、リクエストを失敗させるのではなく次のガードレールに
進みます。ブロッキングは明示的な判断（`block: true`）であり、決して偶発的に
起こるものではありません。唯一の例外はアボートされたリクエストです：呼び出し元の
`signal` がアボートされた場合、例外をスローしたガードレールはスキップされるのではなく、
フック実行を拒否します。

フックはすべてのルートやすべてのレスポンスで実行されるわけでは**ありません**。
ガードレールをセキュリティ制御として信頼する前に、
[カバレッジと制限](#coverage-and-limits)をお読みください。

## 組み込みガードレール

レジストリは、インポート時に優先度順で6つのガードレールを自動的に読み込みます
（`registry.ts` → `registerDefaultGuardrails()` を参照）:

| 優先度 | 名前                | ステージ       | ファイル              |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

優先度の数値が小さいものから**先に**実行されます。

### Vision Bridge (`visionBridge.ts`) — モダリティブリッジ PR-1

GLM 5.3 ベースモデルおよび `glm-5.3-{low,high,max}` には、
`supportsVision:false` のレジストリ／仕様メタデータが明示されています。GLM 5.3 Flash バリアントは
引き続きネイティブのビジョンモデルです。Claude Code の `/v1/messages` ルートは、
Claude から OpenAI への変換**前**に共有の `handleChat` pre-call ガードレールチェーンに入ります。
そのため、ネストされた `Read` ツール結果の画像は、変換によって OpenAI の `image_url` コンテンツに
展開される前に、説明または処理される必要があります (#17069)。

**ビジョン非対応モデル**を対象とする画像を含むリクエストをインターセプトし、リクエスト全体を
ビジョン対応モデルへ再ルーティングするか、設定可能なビジョンモデルによって生成されたテキスト説明で
画像部分を置き換えてから上流呼び出しを行います。これにより、テキスト専用プロバイダーでも
マルチモーダルペイロードを透過的に処理できます。

フロー:

1. 対象モデルがすでにビジョンをサポートしている場合はスキップします
   （強制ブリッジリスト `isVisionBridgeForcedModel` に含まれる場合を除く）。
2. `extractImageParts(messages)`（`visionBridgeHelpers.ts`）を使用して画像部分を抽出します。
   この処理は、コンボ互換性フィルターと共有される唯一の信頼できる情報源である
   `open-sse/utils/mediaParts.ts` の**統合メディア検出器** `detectMediaParts()` に委譲されます。
   抽出対象は、`replaceImageParts` が再度差し込める形状（extract↔replace コントラクト）の
   allowlist に含まれるものに限定されます。対象は OpenAI の `image_url`、Anthropic の
   base64 `source.type:"base64"`、Anthropic URL の `source.type:"url"`、および Responses API の
   `input_image` です。Claude Code の `tool_result.content` および Responses のツール出力内に
   ネストされた一致画像も抽出され、元のパスで置き換えられます。インジケーターのみの形状は
   コンボフィルター用の素材であり、抽出されません。
   見つからない場合はスキップします。
3. `resolveVisionBridgeRuntimeSettings()`（`src/shared/constants/modalityBridgeDefaults.ts`）を使用して
   実行時設定を解決します。新しい `modalityBridge*` 設定キーが優先され、従来の
   `visionBridge*` キーは**1サイクルのフォールバック**（ロールバック期間）として引き続き使用できます。
   ブリッジが無効な場合は、メディアの走査を行う前にスキップします。
4. モードセレクター（`modalityBridgeVisionMode`、下表を参照）が、再ルーティングと説明のどちらを
   行うかを決定します。再ルーティングでは、`model` のみを差し替えた `modifiedPayload` と、
   `{ rerouted, fromModel, toModel, imagesKept }` のメタ情報を返します。
5. 説明パスでは、画像数を `maxImages` で制限し、タスクを考慮したプロンプトを組み立て、
   説明キャッシュを参照し、ビジョンモデルを**並列**（`Promise.allSettled`）で呼び出して、
   画像の位置に `[Image N]: <description>` というテキスト部分を挿入します。説明に失敗した場合は
   `null` が返されます。ターゲットが不明またはビジョン対応の場合は元の画像が保持されますが
   (#4012)、**ビジョン非対応であることが確認された直接ターゲット**またはビジョンプロバイダーが
   0個のコンボの場合は、説明されなかった画像ごとに明示的な
   `(unavailable — no vision-capable provider connected)` テキストスタブが生成されます。
   これには部分的な失敗や、説明呼び出し数の上限を超えた画像も含まれます (#17069)。
   既存の、すべての説明が失敗した場合のコンボ説明フォールバックも引き続き使用されます (#8430)。
6. `modifiedPayload` とメタ情報（`imagesProcessed`、`descriptions`、`processingTimeMs`、
   `visionModel`）を返します。

#### モードセレクター (`modalityBridgeVisionMode`)

| モード     | デフォルト | 動作                                                                                                                                                                                                                                                                                                       |
| ---------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | 従来のヒューリスティックをそのまま使用します (#6640/#7204)。コンボ以外のモデル／`auto/` モデルは、元のモデルに使用可能な認証情報がすでにある場合（その場合は説明）を除き、最適なビジョンモデルへ再ルーティングされます。コンボターゲットでは常に説明を行います。                                           |
| `describe` |            | 常に説明を行います。再ルーティングブロックは完全にスキップされ、ユーザーが選択したモデルが常に応答します。                                                                                                                                                                                                 |
| `reroute`  |            | 再ルーティングを強制します。認証済みモデルを維持するためのガードはバイパスされます。ただし、再ルーティング**先**の認証情報ガードは引き続き適用されます。使用可能なビジョンターゲットがない場合、ブリッジは説明を行ったり、テキスト専用ターゲットに元の画像を送信したりせず、明確なエラーでブロックします。 |

強制モードは自動ヒューリスティックの実行**前**に短絡します。`auto` の動作は PR-1 前の
ガードレールとバイト単位で同一です。

#### APIキーのスコープ (`visionBridgeKeyScope.ts`)

呼び出し元の API キーで `allowedConnections`、クォータプール
(`allowedQuotas`)、またはモデル (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) が制限されている場合、ブリッジはそのキーが使用を許可されている再ルート用モデルと説明用モデルのみを、そのキーが使用を許可されている接続上で選択します。説明呼び出しは常に `x-omniroute-self-loop-key-id` ヘッダー付きで OmniRoute のセルフループを経由するため、受信側のチャットリクエストで、そのキーの接続ポリシーとモデルポリシーが再度適用されます。`enforceApiKeyPolicy()` は、そのヘッダーをセルフループの bearer と組み合わせた場合にのみ認識するため、アクセスを狭めることしかできず、解決できない ID は拒否されます。

キーでビジョンモデルの使用が一切許可されていない場合、**テキストのみであることが確認されたターゲット**は、画像リクエストをローカルで明確な HTTP 400 とともに拒否し、対応できない上流サービスへ画像バイトを転送しません (#17069)。ビジョン機能が不明またはネイティブであるターゲットでは、説明パスは従来の fail-open 動作 (meta `{ skipped: true, reason: "no_permitted_vision_model" }`) を維持します。キーなしのリクエスト、およびこれらの制限がないキーは、これまでとまったく同じように動作します。

#### タスク対応の説明プロンプト (`modalityBridgeVisionTaskAware`)

デフォルトは **`true`** です。`composeVisionPrompt()` (`visionBridgeHelpers.ts`) は、**最後のユーザーメッセージ**のテキスト（500 文字に切り詰め）を基本説明プロンプトに追加し、ユーザーが実際に求めた内容に説明の焦点を合わせ（codex-vision-proxy パターン）、ビジョンモデルに表示されているテキストの転記を求めます。フラグが無効の場合、またはユーザーテキストがない場合は、基本プロンプトが変更されずに使用されます。

説明セルフループ独自の OpenAI 互換リクエスト (`visionBridgeHelpers.ts` 内の
`callVisionModelSingle()`) は、すべての呼び出し元およびプロバイダーに対して無条件に `image_url.detail: "high"` を要求します。クライアントからのシグナルによる制御はありません。このプロンプトが求めるテキスト転記タスクでは、低詳細度のサンプリングにより OCR の精度が低下するため、元の受信リクエストで使用された詳細度にかかわらず、説明呼び出し自体は常に高詳細度を要求します。これは内部の説明リクエスト本文にのみ影響し、OmniRoute が呼び出し元自身の `image_url.detail` をプライマリリクエストで転送する方法は変更しません。そのデフォルトは別途、検出された OpenCode クライアントに対してのみ、`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) で適用されます。説明セルフループの Anthropic ワイヤーフォーマット分岐には `detail` フィールドがなく、いずれのデフォルトの影響も受けません。

#### 説明出力の上限 (`modalityBridgeVisionMaxChars`)

| キー                           | デフォルト | 範囲                 |
| ------------------------------ | ---------- | -------------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` または 100–50000 |

`0`（デフォルト）は **上限なし** を意味します。`callVisionModel()` が返す説明は変更されずにそのまま渡され、既存の動作が維持されます。100～50000 の範囲の値を指定すると、説明は `…` サフィックス付きで切り詰められてから、`[Image N]: <description>` として再度組み込まれます
(`src/lib/guardrails/visionBridge.ts` の `VisionBridgeGuardrail.preCall()`)。下流モデルが完全な転記結果を必要とする詳細な OCR タスクではこの値を大きくし、会話的なビジョンモデルでのトークン使用量を制限するには小さくします。ダッシュボードのフィールドは Vision タブの Advanced パネルにあります
(`ModalityBridgeVisionTab.tsx` の `modality-bridge-max-chars`)。1～99 の値は 100 の下限まで切り上げられますが、明示的な `0` はそのまま維持されます。`0` はそれ自体が有効な Zod 値であり
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)、単に「未設定」のデフォルトというわけではありません。

#### 説明キャッシュ (`modalityBridge/bridgeCache.ts`)

説明出力用のメモリ内 LRU + TTL キャッシュで、プロセス全体で共有されます。
キーは、長さプレフィックスによるフレーミング（フィールド境界の衝突なし）を使用した
`sha256(imageRef + composedPrompt + configuredBridgeModel)` です。モデルの構成要素には、実際に応答したモデルではなく、**設定された**ブリッジモデルが使用されます。`callVisionModel` は内部でフォールバックする可能性があり、試行ごとにキーを作成するとキャッシュが分断されるためです。失敗した説明はキャッシュされません。設定：

| キー                            | デフォルト | 範囲    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### リモート画像の正規化（セルフループによる説明/base64 取得）

ブリッジが**リモート**画像自体を取得する場合、Anthropic の説明セルフコールと claude ワイヤーフォーマットの base64 変換
(`ensureBase64ImagesForClaudeWire`) は、どちらも `visionBridgeHelpers.ts` の
`fetchRemoteImageAsDataUri()` を介して行われ、結果の data URI はビジョンモデルのリクエストに埋め込まれる前に `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) を通されます。大きすぎる画像は、**2048px の長辺**まで縮小されます（OpenAI/Anthropic がすでにサーバー側で適用しているリサイズ上限と同じ）。これにより、ビジョンモデルが見る内容を変更せずに、アップロードのバイト数とレイテンシーを削減できます。リサイズには `sharp` を使用し、動的 import で読み込まれます。ネイティブバイナリの読み込みに失敗するプラットフォームでも、`normalizeDataUri()` が**決して例外をスローせず**、元のバイト列をそのまま通過させるため、説明/base64 変換パスは常に動作し続けます。画像以外のバイト（取得結果がデコード可能な画像でなかった場合）も変更されずにそのまま通過します。この正規化の対象は、ブリッジが自身のセルフコール用に取得する画像に限定されます。オプトインのみの変更原則（Hard Rule #20）に従い、呼び出し元の未加工のパススルーペイロードには決して適用されません。

#### 設定スキーマ + 移行

新しい `modalityBridge*` キーは、`updateSettingsSchema`
（`src/shared/validation/settingsSchemas.ts`）で Zod による検証が行われます。
対象は `modalityBridgeVisionEnabled`、
`modalityBridgeVisionMode`、`modalityBridgeVisionModel`、
`modalityBridgeVisionTaskAware`、`modalityBridgeVisionPrompt`、
`modalityBridgeVisionTimeout`、`modalityBridgeVisionMaxImages`、
`modalityBridgeVisionMaxChars`、`modalityBridgeCache*` の 3 キー、
および Audio Bridge で使用される `modalityBridgeAudio*` グループです。
マイグレーション `141_modality_bridge_settings.sql` は、既存の
`visionBridge*` の値を対応する新しいキーにコピーします（冪等であり、
オペレーターが設定した `modalityBridge*` の値を上書きしません）。レガシー
キーは、1 リリースサイクルの間、読み取り時のフォールバックとして引き続き
受け付けられます。

#### 透明性ヘッダー + 統計

変換内容を説明するレスポンスには、
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
が付与されます（`modalityBridge/bridgeStats.ts` の
`buildModalityBridgeHeader()` で構築され、
`src/sse/handlers/chatHelpers.ts` の `withModalityBridgeHeader()` で付与されます）。
再ルーティングされたリクエストにはヘッダーは付与されません — ペイロードは
変更されておらず、モデルの入れ替えはレスポンス本文の `model` フィールドですでに
確認できるためです。

`GET /api/modality-bridge/stats`（管理者認証。`GET /api/settings` と同じ
ティア）は、`vision`、`audio`、`video` のモダリティごとのメモリ内カウンター
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` を返します。
`averageLatencyMs` の分母にはすべての試行ではなく `latencySamples` が使用されます。
タイミング情報のない操作で、0 ミリ秒のサンプルが捏造されることはありません。
`bridged` は、後方互換性のため、成功した変換のエイリアスとして引き続き使用されます。
失敗した試行ではインクリメントされません。
カウンターは設計上、プロセスの再起動時にリセットされます
（会計ではなくテレメトリです）。

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

音声を含むチャットリクエストのうち、音声入力を受け付けることが既知ではない
ターゲットに到達する前のものをインターセプトします。チャットリクエストを
再ルーティングすることはありません。音声パートは既存の OpenAI 互換マルチパート
エンドポイントを通じて文字起こしされ、選択されたチャットモデルはテキストの
トランスクリプトで処理を続行します。

フロー:

1. `getResolvedModelCapabilities()` を通じて `supportsAudio` を解決します。明示的なプロバイダーレジストリメタデータを最優先し、次に静的モデルメタデータ、最後に同期された `modalities_input` を使用します。入力リストが宣言されていて `audio` が含まれていない場合は `false` となり、機能を示す情報が残っていない場合は `null` となります。`false` と `null` のどちらも保守的なブリッジを有効にし、`true` の場合はこれを回避します。
2. `modalityBridgeAudio*` 設定を解決し、共有の `detectMediaParts()` 検出器を通じて、すべてのメッセージから分離可能なトップレベルの音声パーツを抽出します。サポートされるワイヤ形式は、OpenAI の `input_audio`、`audio_url`、および `source.media_type: "audio/*"` です。ネストされた音声はルーティング用に検出されますが、分離パスでは削除されません。処理量は `modalityBridgeAudioMaxClips` によって制限され、それ以降のパーツは変更されません。
3. 設定された `provider/model` を使用するか、`selectAudioBridgeModel()` に `AUDIO_TRANSCRIPTION_PROVIDERS` を安定したカタログ順で走査させ、利用可能なアクティブプロバイダー認証情報を持つ最初のモデルを選択します。
4. `callAudioTranscription()` は、base64／data URI 形式の音声をマルチパートの `file` に変換するか、DNS ピンニングと 25 MB の上限を備えたパブリック専用アウトバウンドガードを通じてリモートの `audio_url` をダウンロードします。その後、ファイルと選択されたモデルをローカルの `/v1/audio/transcriptions` セルフループに POST します。認証には `resolveSelfLoopBearer()` を使用します。既存の文字起こしルートが通常の認証情報検索、クールダウン／レート制限処理、プロバイダーディスパッチを実行します。
5. 成功した呼び出しでは、パーツを `[Audio N]: <transcript>` に置き換えます。呼び出しは `Promise.allSettled` で実行され、個々の失敗時には元の音声パーツが保持されます（#4012 の契約）。すべての呼び出しに失敗し、対象が `supportsAudio === false` であることが確認されている場合、パーツは
   `[Audio N]: (unavailable — no STT provider connected)`（#8430 の契約）になります。不明な対象（`null`）では、すべて失敗した結果も変更されません。テキストのみの対象であることが確認され、使用可能な STT 認証情報がない場合は、ネットワーク呼び出しを行わずに同じ明示的なスタブが設定されます。

成功した文字起こしでは、プロセス全体で共有される Modality Bridge の LRU／TTL キャッシュを使用します。キーは音声参照、安定した `audio-transcription` 操作ラベル、選択された STT モデルを組み合わせたものです。失敗はキャッシュされません。音声の試行により、共有される `bridged`、`cacheHits`、`failures`、`lastUsedAt` カウンターが更新されます。変換されたレスポンスには
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` が付与されます。変更されていないリクエストには Audio Bridge セグメントは付与されません。

ランタイム設定は DB に保存され、Zod による検証が行われます。

| Key                           | Default | Range          |
| ----------------------------- | ------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —              |
| `modalityBridgeAudioModel`    | `""`    | Auto or STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10           |

共有キャッシュは引き続き、`modalityBridgeCacheEnabled`、
`modalityBridgeCacheTtlMinutes`、`modalityBridgeCacheMaxEntries` によって制御されます。

### ビデオブリッジ（`videoBridge.ts`、`videoBridgePipeline.ts`）

ネイティブのビデオサポートが既知でない対象が呼び出される前に、Chat Completions の `messages` と Responses API の `input` に含まれるトップレベルのビデオパーツをインターセプトします。サポートされる形式は、`input_video`、`video_url`、`video_source`、HTTPS URL、`data:video/*;base64,...` データ URI です。テキスト内の単純なファイル名はビデオとして扱いません。

`VideoBridgeGuardrail.preCall`（`videoBridge.ts`）は、リクエストの走査、機能／ポリシーチェック、リクエスト単位の集約、レスポンスペイロードを担います。ビデオごとの処理（取得、全体結果キャッシュ、呼び出し元が宣言した音声文字起こしを融合したフレームシーケンスの説明、試行単位のメトリクス／中止／クリーンアップ）は、`videoBridgePipeline.ts` の `processVideoPart` 内に隠蔽されています。これは `preCall` のループ内でビデオパーツごとに 1 回呼び出されます。このモジュールでは、明示的なポート境界である `VideoMediaBrokerPort`（バイトの取得とサンプリングされたフレームの抽出）、`VideoAudioTranscriptionPort`（呼び出し元が宣言した音声文字起こしとサンプリングされたキャプションの融合）、`VideoDrilldownPort`（従来の raw-store 形式）も定義します。プロダクションの STT とフレーム保持は、`createVideoSttAdapter` と `createVideoDrilldownAdapter` を通じて説明ポートの周囲に構成されます。後者は共有された不透明ハンドルのライフサイクルを使用します。

パブリックな `/v1` リクエストパスがサブプロセスをインポートまたは呼び出すことはありません。リモートビデオは 50 MiB の上限の下でダウンロードされます。インライン base64 ビデオには、モデル／メッセージ／フレーミングのエンベロープを、50 MiB のパブリック JSON リクエスト受け入れ上限内に収められるよう、ビデオごとに保守的な 36 MiB のデコード済み上限が設定されます。インライン長とデコード済みサイズの推定値は、割り当ての前に検査されます。初期リモート URL とすべてのリダイレクトでは HTTPS が必須であり、DNS ピンニングを備えた既存のパブリック専用アウトバウンドガードが使用されます。その後、バイト列は正確な内部 `POST /api/modality-bridge/video/extract` ブローカー境界を通過します。このルートは `LOCAL_ONLY` と `SPAWN_CAPABLE` の両方であり、プロセス単位で認証された信頼済みループバックリクエストのみを受け付け、URL、ファイルシステムパス、実行可能ファイル、引数リストは一切受け付けません。API の本文サイズパイプラインとハンドラーのインクリメンタル本文リーダーは、それぞれ独立して 50 MiB のブローカー入力上限を適用します。境界付きキューは一度に 1 件の抽出を実行し、4 件の保留ジョブを許可し、保留中の入力を 100 MiB に制限します。

ブローカー内では、`ffprobe` が非公開のローカルファイルを読み取ります。固定の形式許可リストでは、プレイリスト形式とマニフェスト形式が除外されています。許可された MOV 系コンテナでは、外部 MOV データ参照はデフォルトで無効のままであり、固定コマンドもそれらを有効化しません。`ffprobe` と `ffmpeg` は、いずれも `file` のみを許可するプロトコルホワイトリスト、1 スレッド、固定された引数配列、シェルなしで動作し、実行ファイルは `PATH` から解決されます。付加画像のカバーストリームは再生可能な候補になりません。再生可能なすべてのストリームは制限を満たす必要があり、明示的なデフォルトストリームが優先された後、決定論的に最小インデックスのストリームへフォールバックします。動画は 600 秒、各寸法 8,192 ピクセル、ソースピクセル数 33,554,432 に制限されます。FFmpeg は 1～16 枚の中間点 JPEG フレームをサンプリングし、入力がそれより小さい場合に拡大することなく、長辺を最大 1,024 ピクセルまで縮小します。また、URL を受け取ることはありません。サンプリングはデフォルトで `uniform` です。オプションの `scene_aware` ポリシーと実験的な `segment_aware` ポリシーは、検証済みのローカルストリームに対して、追加の固定 FFmpeg パスを 1 回実行し、制限された `showinfo` シーンタイムスタンプを選択します。検出器の失敗、タイムアウト、不正な出力、または候補集合が空の場合は、決定論的に同じ均等な中間点へフォールバックします。セグメント認識モードでは、検証済みのシーン区間に比例して中間点サンプルを割り当てます。セグメント認識に関する証拠とフォールバック動作については、以下で詳しく説明します。ハードな 16 フレーム上限は、すべてのポリシーで選択後に適用されます。シーン認識リクエストのフレーム予算が 1 枚しかない場合、アクティブな動画全体またはフォーカスウィンドウの均等な中間点を使用し、`policyEffective: uniform` を報告します。選択されたシーンフレーム 1 枚だけでは、時間軸の両端を同時に保持できないためです。呼び出し元は、有限のフォーカスウィンドウ（`start`/`end` 秒）を任意で指定できます。境界値はメディアの長さにクランプされ、逆順または有限でないウィンドウは拒否されます。すべてのサンプリングポリシーは、正規化された区間内でのみ実行されます。生成されたウィンドウは、サンプリングメタデータと、信頼できない説明のプレフィックスに含められるため、下流のモデルは、フォーカスされた抜粋とタイムライン全体を区別できます。

意味的なキャプションのフォーカスは、独立した明示的な設定です。デフォルトの `full` 分析モードでは、既存のフレームプロンプトが維持され、リクエストテキストがキャプションモデルに転送されることはありません。`focused` モードでは、ブリッジは同じ Chat または Responses コンテナから、ユーザーが作成した最新の空でない `text`/`input_text` のみを読み取り、NFC に正規化し、制御文字と空白をまとめ、500 Unicode コードポイントに制限します。結果が空の場合は、正確な `full` プロンプトにフォールバックします。使用可能なヒントは、専用の信頼できないユーザーコンテキストブロック内に JSON としてシリアライズされ、観測可能な詳細の優先順位付けにのみ使用できます。メディア内で視覚または聴覚的に確認できる指示に従わないようにする別個の警告を上書きすることはできません。テキストによるフォーカスが `start`/`end` を推測したり、時間サンプラーを変更したりすることはありません。

#### FU-07 構造的セグメント証拠

`segment_aware` は、検証済みのローカル動画ストリームに対して、制限付きの事前分析パスを 1 回実行します。固定フィルターチェーンは、まず幅を最大 320 ピクセルに縮小し、シーン変更と静止区間を検出した後、1 秒あたり 1 フレームで、ぼけ、平均輝度、空間情報および時間情報をサンプリングします。このパスは、構造サンプル 600 件、FFmpeg/フィルターの 1 スレッド、同じ `file` のみを許可するプロトコルおよびコンテナの許可リスト、プロセス出力 1 MiB の上限、さらにブローカー共有の中止／期限内で最大 30 秒に制限されます。リクエストからコマンド、フィルター、パス、URL を受け入れることはありません。

構造値は決定論的なサンプリング証拠であり、動画の意味的な理解ではありません。これらから、被写体、動作、キャプション、音声、ユーザーの意図を推測することはありません。シーン境界と静止境界がセグメントを形成し、静止範囲、ぼけ、露出、空間的詳細、時間的変化は、既存の 1～16 フレーム予算の割り当て方法にのみ影響します。完全に静止したセグメントは 1 フレームに制限され、静止していないセグメントが残りの予算を競合します。境界の数がフレーム数を上回る場合でも、タイムライン全体の均等なカバレッジは維持されるため、急速な初期カットによって長い後半セグメントが隠れることはありません。静止境界の 1 秒の分析解像度内にあるシーン境界は統合されます。

フィルターの欠落、不正または空の証拠、検出器エラー、あるいは制限付き事前分析のタイムアウトが発生した場合は、正確な均等中間点ポリシーへフェイルオープンします。呼び出し元による中止またはブローカーの期限到達ではフェイルオープンしません。実行中のサブプロセスを終了し、その後のフレーム抽出を防止し、非公開の一時ツリーを `finally` で削除します。

`scripts/perf/video-bridge-fu07-eval.ts` は、重複排除後のキャプション呼び出し削減、密な動きに対する予算割り当て、ぼけ／露出／SI-TI の証拠、長い末尾を伴う急速なカット、緩やかなフェードによる誤検出のために、決定論的な実 FFmpeg フィクスチャを生成します。事前分析のウォール時間を記録し、`/usr/bin/time` が利用可能な場合は、子プロセスの CPU 使用時間とピーク RSS も記録します。その品質チェックは構造的オラクルにのみ基づきます。このハーネスには承認済みのエンドポイントも固定された判定者もないため、実際のキャプションモデルの品質は引き続き `HOLD` です。`--caption-cost-per-call-usd` に明示的な正の 1 呼び出しあたりの見積もりが指定されない限り、金銭的な削減効果も `HOLD` のままです。このスクリプトがいずれかの結果を捏造することはありません。

各フレームの上限は 4 MiB、すべての生フレームの合計上限は 23 MiB、シリアライズされたブローカー応答の上限は 32 MiB です。専用の一時ディレクトリは `finally` で削除されます。OmniRoute は FFmpeg をバンドルせず、カスタム実行可能ファイルパスも受け付けません。キャプション生成の前に、ブリッジは保守的な視覚的重複排除処理を適用します。各 JPEG を 16×16 のグレースケールバッファに縮小し、直前に保持されたフレームとのみ比較します。要求されたキャプション数が 1 フレームを超える場合、抽出処理はその要求数の最大 2 倍、かつ 16 フレーム以下に制限された候補プールを提供します。要求された上限は重複排除後にのみ適用され、上限が 2 以上の場合、最終的な間引きでは最初と最後に選択された候補が保持されます。バージョン管理された
`grayscale-16x16-mean-cells-v2` ポリシーでは、平均輝度差と、正規化された差分が 0.05 以上であるサムネイルセルの割合のうち、大きい方を使用します。重複のしきい値は定数 0.04 であり、実行時設定として公開するのではなく、予測可能性を重視して選択されています。この二次的な
高コントラスト信号により、平均値のみの比較では見落とされる可能性がある小さな動きや表示テキストの変化も保持できます。比較処理またはデコーダーでエラーが発生した場合はフェイルオープンし、網羅性を維持します。出力メタデータでは、抽出された候補、正常に使用されたフレーム、削除された視覚的重複を分離して記録します。

明示的にマークされた動画パートでは、タイムスタンプ付きコンタクトシートを要求できます。ブリッジは最大 4 列、16 フレームの JPEG グリッドを構築します。512 ピクセルの各セルには、コントラストの高い下部帯に元のタイムスタンプが焼き付けられます。同じタイムスタンプは、下流での関連付けと監査のためにテキストメタデータにも残されます。完全な JPEG のサイズ上限は 32 MiB です。`sharp` がグリッドをデコードまたは合成できない場合、ブリッジは個別の JPEG フレームにフォールバックします。クライアントによる中断は、シート処理を通じて伝播します。

プロモーションの証拠は、合成構成マイクロベンチマークとは意図的に分離されています。`scripts/perf/video-bridge-contact-sheet-eval.ts` は、実際の OpenAI 互換ビジョンモデル向けに、スキーマバージョン管理された A/B ハーネスを定義します。プロバイダーが報告するトークン数、シート合成を含むエンドツーエンドの実時間レイテンシ、モデル呼び出し回数、マニフェストで定義された事実の保持率を測定します。生のモデル応答はレポートに書き込まず、SHA-256 ダイジェストと一致した事実 ID のみを保持します。ハーネスは、`--execute-real` が渡され、`--model`、`OMNIROUTE_BASE_URL`、`OMNIROUTE_API_KEY` が設定されている場合を除き、ネットワークアクセスや有料モデル呼び出しを行いません。明示的な実行を行わない場合、機械可読な判定は `HOLD` のままです。合成ペイロードや呼び出し回数の測定だけでは、プロモーションの証拠にはなりません。

分離された `scripts/perf/video-bridge-promotion-eval.ts` は、FU-07 または FU-09 の観測結果を消費します。プロモーションへの採用には、8 種類すべての合成シナリオに加えてサニタイズ済みの実クリップ、各ロールおよびケースについて少なくとも 3 回の測定済み反復、宣言された 10 個すべてのメトリクス、固定されたメディア／プロンプト／期待される事実／設定のダイジェスト、一意の観測 ID、検証済みのシード付き A/B 順序が必要です。実行レシートは、コーパスのダイジェスト、正確な候補 SHA、モデルリビジョンをひも付けます。CPU が 30 秒を超える、ピーク RSS が 512 MiB を超える、または事前分析が 30 秒を超える場合を含め、測定値が欠落しているか無効であれば `HOLD` のままです。これらは証拠採用時の上限であり、新たな実行時 RSS 強制保証ではありません。

FU-07 では、品質保持率 98% 以上、p95 レイテンシがベースラインの 1.2 倍以下であることに加え、平均キャプション呼び出し回数が同等である場合のケース均衡平均再現率が絶対値で 0.05 改善するか、重複排除後の平均キャプション呼び出し回数が少なくとも 10% 減少することのいずれかが必要です。FU-09 では、品質 0.85 以上、保持率 95%、レイテンシの中央値 20% 削減、トークン数 10% 削減が必要です。重要な事実の喪失、インジェクションへの準拠不備、または使用状況の欠落がある場合、プロモーションは行えません。1 回の実行だけでプロモーションすることはできません。`--previous-report` により、同一のポリシー、モデルリビジョン、候補、コーパスについて、相互に異なり重複せず、連続して適格となった 2 回の実行を確認します。サンプリング実験でコンタクトシート実験を確認することはできません。

収集器は応答をメモリ上で採点し、`responseDigest` とメトリクスおよび観測の関連付けを保存しますが、応答テキストは決して保存しません。コンシューマーは従来形式の生の観測結果も読み取りますが、そのテキストをレポートにコピーすることは決してありません。各観測について、`responseDigest` または `rawResponseText` のいずれか一方だけが受け付けられます。バージョン管理された許可リストは空のままで、変更不可能な `hold` をデフォルトとします。適格なエントリには、その証拠参照、ポリシー、モデルリビジョン、正確な候補 SHA、マニフェストダイジェスト、2 つの異なる実行 ID が必要です。コンテキストが競合する場合は拒否されます。これらのメタデータは監査契約であり、参照先ファイルに真正な測定値が含まれていることの証明ではありません。エントリを追加する前に、実際のレシートを確認してください。管理統計エンドポイントと Video ダッシュボードは、保守的な準備状況を公開します。設定されたモデルエイリアスだけでは、そのリビジョンや実行中の候補 SHA を確定できないため、現在のダッシュボードは別の実行コンテキストから適格性を再利用せず、`HOLD` を報告します。明示的な実験的選択はプロモーションとは分離されたままであり、デフォルトが自動的に変更されることはありません。

呼び出し元は、整列済みテキストをすでに保持している場合、サポート対象の動画
part に任意の `transcript.cues` 配列を付加できます。各 cue には `text`、プローブされた再生時間内に収まる有限の `start`/`end` 区間、および許可リストに含まれる
`source`（`client`、`embedded`、または `audio-bridge`）を指定する必要があります。`confidence` のデフォルト値は
`1` で、`0` から `1` の範囲内でなければなりません。完全に重複する cue は統合されます。
OmniRoute はこのメタデータから文字起こしを開始することはありません。検証済みの cue は、source、confidence、区間とともに記述された結果へコピーされ、フレームキャプションと並ぶ信頼できない観測としてレンダリングされます。無効なテキスト、範囲外のテキスト、または来歴のないテキストは、キャプションストリームに混在させず拒否されます。リクエスト本文の両方の transcript チャネルでは、指定された来歴を `client` に正規化します。自己申告された `embedded` または `audio-bridge` ラベルも同様です。信頼済みラベルを割り当てられるのは、コード専用の `trustedSource` 引数を通じたサーバー所有のアダプターだけです。リクエスト JSON フィールドからその引数に到達することはできません。Transcript テキストは、その来歴にかかわらず信頼できないメディア由来のコンテンツであり、認可を決定するために使用してはなりません。

高度な呼び出し元は、同じ動画に対して `audioTranscript` トラックを指定することもできます。これはクライアントが提供したテキストとして扱われ、サーバーによる文字起こしの証明ではありません。融合処理の接合部では、視覚観測と音声観測を単一の期限および中止シグナルの下で実行し、共通のタイムライン上に並べ、完全に重複する項目を統合し、片方だけが成功した場合は部分的な結果を報告します。無効な `audioTranscript` は、動画全体を失敗させるのではなく、部分的な結果へ劣化します。つまり、視覚的な説明は保持され、音声ブランチにはサニタイズ済みの失敗コードが記録されます。ブランチごとの可用性、部分結果フラグ、サニタイズ済みの失敗コードは、記述された結果、ガードレールメタデータ（`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`）、結果キャッシュのメタデータ、およびブリッジ融合カウンターに保持されます。デフォルトの Video Bridge パスでは音声テキスト化を呼び出したり、2 つ目のメディアコピーをダウンロードしたりしません。その明示的なトラックがない場合、動画専用のままです。

**Transcript の保持（#12150 P1）。** これは Video Bridge（それ自体がオプトイン）が transcript cue をレンダリングするたびに自動的に適用されます。別個の保持フラグはありません。リクエストが transcript cue（呼び出し元が宣言した
`transcript` または融合された `audioTranscript`）を 1 つでもレンダリングすると、ガードレールは `videoBridgeObserved` を設定し、動画説明のレダクション済みシャドウを生成します。これは、すべての cue の自由テキスト本文を
`[redacted-video-transcript]` に置き換えた同一のレンダリングであり、文字列を組み立てる前に構造化された cue フィールドを置換して構築されます（フラット化されたテキストを解析することは決してないため、`]` を含む本文、たとえば
`[inaudible]`/`[music]` のような敵対的または通常の本文を含め、cue の内容が残存することはありません）。永続化される呼び出しログのリクエスト本文では、各動画由来のテキスト part がそのレダクション済みシャドウに置き換えられ、内容の等価性によって照合されます。`fullText` アンカーは、完成した pre-call ガードレールペイロードから再読み込みされるため、後続のチェーンガードレール（優先度 10/95 の PII および認証情報マスカー）が説明テキストをインプレースで書き換えた後や、システムプロンプト／ハンドオフ／メモリの注入によってメッセージ配列の形状が変わった後でも、照合は成功します。上流のモデルに送信される本文は変更されません。観測されたリクエストでは永続的な Memory も生成されません（リクエスト由来とレスポンス由来の両方の抽出がスキップされます）。そのため、モデル自身の返信が transcript テキストを Memory に反映することもありません。

**Raw video フィールド（#12430）。** ブリッジが有効で、ネイティブ動画サポートが不明または存在しない場合、定義済みの `transcript`/`audioTranscript` フィールドも、説明の失敗後や `maxVideos` の上限到達後であっても `videoBridgeObserved` を有効化します。`null` と空文字列は対象となりますが、フィールドが存在しない場合や動画以外のメタデータは対象となりません。保持されるコピーではこれらのフィールドがレダクションされるか、リクエスト自体が省略され、キャッシュ／Memory はバイパスされます。

これらのフォールバックパスでは、呼び出し元の有効な cue は、標準外のプロバイダーフィールドではなく、サポート対象の
`text`/`input_text` part になります。リクエストで指定された両方のトラックは、信頼できない `client` 観測として扱われ、動画が説明されておらず、タイムスタンプがメディアに対して検証されていないことを明示する警告が付加されます。既存の 256 cue／合計 64 KiB の予算および cue ごとの予算は、2 つのトラック全体に対してまとめて適用されます。タイムスタンプは、ブローカーの 600 秒上限および指定されたフォーカスウィンドウ内に収まらなければなりません。無効なトラックは任意のテキストとして転送されず破棄されます。合計予算を超えない限り、有効なもう一方のトラックは引き続き使用できます。null／空のフィールドはテキストを追加しません。このフォールバックによってメディアの取得や文字起こしが追加されることはありません。Transcript 拡張フィールドは、フォールバック動画キャリアとその
`video_url`/`source` オブジェクトから削除されます。OpenAI ワイヤーの許可リストは厳格なままです。未知のネイティブ動画キャリアは引き続き利用可能で、既知のテキスト専用ターゲットは安全なマーカーを保持します。構造化されたレダクション済みシャドウによって、追加された transcript テキストが保護されます。一方、呼び出し元が所有する元のリクエストは変更されません。ネイティブサポート対象のターゲットと無効化されたブリッジでは、既存のバイパス動作が維持されます。

追加で保持されるコピーにも、同じ観測済みリクエストシグナルが使用されます。raw の pre-guardrail クライアントリクエストスナップショット、メモリ内の保留中リクエスト、早期に拒否されたリクエストのログでは、動画 part 内の transcript フィールドが構造的に置き換えられます。パイプライン段階およびコンテキストハンドオフによって合成された文字列プロンプトは、永続化されるリクエスト本文のシンクでレダクションされます。永続化される `video_content_removed` マーカーにより、`previous_response_id` による継続はフェイルクローズし、意図的に破棄されたテキストを再構築しないようにします。観測されたリクエストで、ログ記録前に part ごとのレダクション済みシャドウが失われた場合、または後続のリクエスト変更後に複数ある動画シャドウのうち 1 つでも照合に失敗した場合、部分的にレダクションされた transcript を保持する代わりに、保持されるリクエスト本文全体が省略されます。

観測対象のリクエストでは、モデルの応答が構造化されたキュー境界なしにトランスクリプトの任意の部分を引用する可能性があります。そのため、永続化されるコールログの `responseBody` は省略マーカーに置き換えられます。詳細なパイプライン成果物（上流側やクライアント側の本文、ストリームチャンクを含む可能性があります）は保持されません。セマンティックキャッシュ、冪等性キャッシュ、推論リプレイキャッシュでは、そのリクエストに対する読み取りと書き込みがバイパスされます。プロバイダーへのリクエストとクライアントに表示されるレスポンスは変更されません。詳細な成果物が省略される場合、一時バッファー内の初期キープアライブバイトは排出されます。Kiro の不正な EventStream 警告では、ペイロードのバイト数のみが報告され、内容や JSON パーサーの生のエラーは報告されません。
これは、無関係なプロバイダーまたはプラグインの診断情報がすべて監査済みであることを意味するものではありません。より広範な保持先の点検は #11658 で追跡されています。

内部の `/api/modality-bridge/video/drilldown` ライフサイクルは、独立したループバック／トークン認証済みのキャッシュ基盤です。すべての操作には、正規の不透明なプリンシパル ID も必要です。本番の呼び出し元を有効にする前に、認証済みテナントからその ID を導出し、クライアントが選択した値を決して転送しないようにする必要があります。キャッシュキーは、そのプリンシパルを正規のセッション ID および動画参照 ID にバインドし、それらの SHA-256 から導出したキーのみを保存します。読み取りと削除のスコープは、いずれも同じプリンシパルに限定されます。キャッシュはエントリごとに導出済み JPEG フレームを最大 16 個保存し、10 分後に期限切れにし、制限付きの `start`／`end` 読み取りまたは明示的なセッション削除をサポートします。

各プリンシパルには、16 エントリおよび正規 JPEG データ 64 MiB の上限が設定されます。これらの上限は、グローバルな 64 エントリ／256 MiB の上限とは独立しています。プリンシパルのクォータが逼迫した場合は、グローバル LRU 追い出しが検討される前に、そのプリンシパルの最も長く未使用のエントリだけが追い出されます。期限切れのエントリは、キャッシュのアクティビティ時にプリンシパル単位とグローバルの両方の使用量管理から除去されます。一方、キャンセルや検証失敗によって部分的な置換がコミットされることはありません。

キャッシュは、正規形式でない Base64、過剰なパディング、JPEG 以外のメディア、不正または切り詰められた JPEG、および制限付きの完全画像 `sharp` デコード中に警告が発生する JPEG を拒否します。受け入れた各画像は正規 JPEG として再エンコードされ、幅と高さは呼び出し元のフィールドを信頼せず、デコードしたバイトから導出されます。また、末尾にあるポリグロットバイトは保持せず破棄します。両方のクォータに課金されるのは、制限付きの正規圧縮バッファーのみです。JSON ワイヤー上の上限には、32 MiB のデコード済み入力上限に対する Base64 のオーバーヘッドが含まれます。保存される各導出情報には、検証済みの JPEG 形式／解像度、サンプリングポリシー、導出バージョン、作成時刻、サーバーが計算したコンテンツハッシュ、ハッシュ化された親参照、および信頼された呼び出し元の親コンテンツハッシュが記録されます。キャンセルは、非同期のデコード／ハッシュフェーズ間、およびアトミックなキャッシュコミット前に確認されます。

本番のプロデューサーは、追加の動画ダウンロード／抽出を行わず、正常に視覚分析を完了した後にのみ、すでに導出済みのブローカーフレームを再利用します。オペレーター設定 `modalityBridgeVideoDrilldownEnabled=true`、パートごとの厳密な `drilldown: true`、および認証済み API キーレコード ID が必要です。クライアントが宣言したプリンシパル／セッション値によって所有権が確立されることはありません。3 つの条件がすべて満たされない場合、追加フレームのハッシュ化、リサイズ、保持は行いません。保持に失敗しても、利用可能な視覚レスポンスは維持されます。同意済みのリクエストでは動画全体の結果キャッシュをバイパスするため、キャッシュされた結果がハンドルを再生することはありません。

成功した JSON および SSE レスポンスでは、制限付きの `x-omniroute-video-drilldown` ヘッダーに最大 4 個の不透明なハンドルが公開されます。認証済みのブラウザーオリジンは、CORS オリジンポリシーを広げることなく、そのヘッダーを読み取れます。新しいハンドルは `v1.<32-byte random base64url
token>` を使用し、レジストリにはその SHA-256 ハッシュのみが保持されます。読み取り側／ヘッダーパーサーは、レガシー形式の 64 桁 16 進トークンも受け付けます。認証済みの公開コンシューマーは
`GET /api/v1/video-bridge/drilldown?handle=...` であり、`modalityBridgeVideoDrilldownRemoteEnabled=true` によって個別にゲートされます。明示的に永続化された false は、レガシーの `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` 環境フォールバックが有効な場合でもアクセスを無効にします。本番の保持には、同様にレガシーの
`OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` フォールバックがあります。いずれのフォールバックもデフォルトでは無効です。

コンシューマーは認証済みキーから所有権を導出し、キーのポリシーを適用します。GET と DELETE は、`/v1` および `/api/v1` エイリアスを含め、いずれも `video` エンドポイントカテゴリに属します。空でないエンドポイント許可リストを持つキーには `video` が含まれている必要があります。制限のないキーは引き続き互換性を保ちます。コンシューマーは、未知のハンドル、期限切れのハンドル、別のキーが所有するハンドルに対して同じ 404 を返します。`variant=preview|standard|detail`（JPEG の最大寸法は 320／640／1280、拡大は行いません）、`limit=1..8`（またはレガシーの `frames` エイリアス。両方は指定できません）、0 始まりの `page`、および任意の `start`／`end` フォーカス秒を受け付けます。重複するクエリキーと、前後が逆転したフォーカスウィンドウは拒否されます。返される各バリアントには、実際のコンテンツのハッシュと実際の解像度メタデータが含まれ、保持されたソースにリンクされます。バリアントは追加の保持コピーとして保存されず、読み取り時に導出されます。JSON レスポンスは Base64／エンベロープを含めて 32 MiB に制限されます。ページが大きすぎる場合は 413 を返し、クライアントはフレーム数を減らしてリクエストする必要があります。読み取りでは各リサイズの前後でキャンセルを確認し、返却前にハンドルの有効性を再確認します。所有者による `DELETE` は冪等です。削除または TTL の期限切れにより、保持されたソースと使用量管理が解放されます。

共有ストアはプロセスローカルです。再起動するとハンドルは期限切れになり、独立した OmniRoute プロセス間で移転することはできません。管理統計には、有効な保持／リモートポリシーと、保持中のエントリ数／バイト数の集計のみが公開されます。メディア、参照、プリンシパル ID、ハンドルが公開されることはありません。Video 設定パネルにはこれらの値が表示され、両方の同意スイッチを永続化できます。この実装ドキュメントは、実際のデプロイまたは昇格の証拠ではありません。実モデルによる受け入れは別途追跡されています。

フレームは、設定された Video モデルで順番にキャプション化されます。空の
Video オーバーライドは Vision 設定を継承します。両方が空の場合は、Vision
自動ルーターが実効的なビジョン対応モデルを選択します。キャプション化に成功すると、
元のパートは安定した `[Video description:` プレフィックスで置き換えられます。このプレフィックスは、
テキストが信頼できないメディア由来の観測結果であることも示し、メディア内で見つかった指示に
従わないよう下流のモデルに伝えます。フレームキャプションのキャッシュキーには JPEG
バイト、プロンプト、タイムスタンプ、実効モデルが含まれます。キャッシュされるのは、
キャプション化に成功した場合のみです。キャッシュエントリには実際に成功した生成元モデルが
保持され、フォールバックモデルも含まれます。異なるフレームが異なるモデルで生成された場合、
ブリッジは `mixed` を報告します。キャッシュヒット時には、その生成元の識別情報が再利用され、
要求されたルーティング計画のラベルに付け替えられることはありません。ビデオ全体の結果キャッシュは、
出力を変更するすべての入力（プロンプト、実効モデル、サンプリングポリシー、フレーム数、
セマンティック分析モード、正規化されたフォーカスヒントの SHA-256 フィンガープリント、
フォーカスウィンドウ、`transcript`、`audioTranscript`、コンタクトシートフラグ）をキーにします。
したがって、これらのいずれかの次元を変更するとキャッシュミスとなり、古い結果が再利用されることは
ありません。ビジュアル重複排除ポリシーのバージョン、しきい値、候補フレーム数の上限も結果キャッシュの
キーとメタデータに明示的に含まれます。そのため、ポリシーが変更された場合に古いビデオ全体の説明が
再利用されることはありません。結果キャッシュ v4 のメタデータにはモードとフィンガープリントが保持され、
生のユーザータスクは保持されません。ガードレールのメタデータには要求された分析モードと実効的な分析
モードの両方が記録されます。使用可能なユーザーテキストを伴わない要求 `focused` モードは、実効的には
`full` として報告されます。

ガードレールは、サポートされているすべてのビデオパートを抽出しますが、
`modalityBridgeVideoMaxVideos` を超えて説明することはありません。
`supportsVideo === false` であることが確認された対象では、失敗したビデオおよび上限を超えたビデオは
明示的な安全テキストマーカーに変換されるため、生のビデオが残ることはありません。機能が不明な場合、
これらのパートはビデオキャリアを保持します。フォールバックのトランスクリプトがある場合は、上記の
上限付きテキスト変換に従います。`supportsVideo === true` の対象ではブリッジをバイパスします。
クライアントリクエストの中止シグナルは、ダウンロード、ブローカーキュー、サブプロセス、キャプション呼び出し
を通じて伝播します。中止された場合はビデオ間で処理を停止し、生のメディアに対してフェイルオープンすることは
ありません。

ランタイム設定は DB に保存され、Zod で検証されます。

| Key                                 | Default     | Range / behavior                                                                                            |
| ----------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | オプションのランタイム、オプトイン                                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` は汎用キャプションを保持し、`focused` は上限付きで信頼できない最新ユーザーコンテキストを使用         |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge モデルを継承                                                                                  |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                        |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`、`scene_aware`、または比例配分の `segment_aware`。検出に失敗した場合は `uniform` にフォールバック |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                         |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                              |

永続化された従来の Video タイムアウト値が 120 秒を超える場合は、
ブローカーの期限まで短縮されます。新しい設定書き込みでこの上限を超える値を指定した場合は拒否されます。
`GET /api/modality-bridge/video/runtime` は、認証またはランタイムプロービングの前に、信頼できるスタンプ付き
ループバックのローカリティを必要とし、その後に管理認証を要求します。返すのは `available`、
サニタイズされた FFmpeg/ffprobe バージョン、およびランタイムが使用できない場合の固定理由のみです。
内部抽出エンドポイントは公開アップロード API ではありません。キューが飽和している場合は
`503` と `Retry-After` を返し、呼び出し元が切断した場合は `499` を返し、固定されたブローカー期限に
達した場合は `504` を返します。変換されたレスポンスは、Vision または Audio のセグメントを削除せずに、
中央の `x-omniroute-modality-bridge` ヘッダーへ
`video->text;model=<visionModel>;parts=<videos>` を追加します。

### PII マスカー（`piiMasker.ts`）

**両方**のステージで実行されます。

- **`preCall`** はペイロードをクローンし、`system`、`messages`、`input`、および
  `prompt`（プレーンな文字列アイテムを含む）を走査し、文字列の `content`/`text` フィールドに
  `@/shared/utils/inputSanitizer` の `processPII()` を適用します。`PII_REDACTION_ENABLED=true` の場合、
  検出された PII は送信ペイロード内で墨消しされます。これは `INPUT_SANITIZER_MODE` とは独立しています
  （`INPUT_SANITIZER_MODE` はプロンプトインジェクションポリシーのみを制御します）。墨消しが無効な場合、
  呼び出しでは検出数を記録しますが、コンテンツは書き換えません。
- **`postCall`** はレスポンスをディープクローンし、`sanitizePIIResponse()` と
  Responses API 形状のマスカー（`maskResponsesOutput` — `output_text` および
  `output[].content[].text` を対象）を実行します。墨消しが発生した場合は、変更されたレスポンスが
  元のレスポンスを置き換えます。

ガードレールはブロックを行わず、注釈（`meta.detections`、`meta.redacted`）を付与するか、書き換えるだけです。

**可逆ボールト（`PII_REVERSIBLE_VAULT_ENABLED`、デフォルトは `false`）。**  
`PII_REDACTION_ENABLED` と `PII_REVERSIBLE_VAULT_ENABLED` の両方が有効な場合（DB オーバーライド >
環境変数 > デフォルト、リクエストごとに 1 回読み取り）、`handleChat` はクライアントリクエストごとに 1 つのボールト
（`src/lib/pii/requestTokenVaultScope.ts`）を開き、それを `GuardrailContext.tokenVault` として pre-call
パスに渡します。マスカーは、組み込みルール、検証済み（GDPR/POPIA）ルール、カスタムルールのいずれでも、
`[EMAIL_REDACTED]` の代わりに `<<PII_EMAIL_QWERTYUI_1>>` のような代替トークンを書き込みます。ノンスは
リクエストごとにランダムな大文字 8 文字で、同じ値にはリクエスト内で同じトークンが割り当てられます。トークンを
発行するのはマスカーだけです。プロンプトインジェクションガードと `/api/guardrails/test` はボールトなしで実行され、
プレースホルダーを保持します。

- プロバイダー、すべてのコンボの各処理、リトライ、フュージョンパネルの各メンバー、フュージョンジャッジには、トークンだけが表示されます。トークンは、`handleChat` から出る 2xx レスポンスで 1 回だけ復元されます。SSE をパースした後はフィールドごとに復元され（イベント間で分割されたトークンも解決され、ツール呼び出しの引数は JSON エスケープされます）、JSON ボディではフィールドごとに復元され、`Content-Length` が再計算されます。コンテンツ、推論テキスト、ツール呼び出しの引数が復元されます。エラーボディ（4xx/5xx）ではトークンが保持されます。
- 失敗の内容が外部に漏れることはありません。発行に失敗した場合、またはボールトが値を拒否した場合（エントリ数 1000 件、値ごとに 256 文字、合計 64 KB）、代わりにプレースホルダーが書き込まれます。ボールトが解決できないトークンや、復元に失敗したトークンはリテラルのままになり、ログには件数だけが記録されます。ボールトにはタイマーもグローバル状態もなく、レスポンスストリームの終了、キャンセル、エラー時にクリアされます。
- リクエストでトークンが発行された場合、メモリ抽出、べき等性保存、両方のセマンティックキャッシュへの書き込みはスキップされます。後続のリクエストではそれらのトークンを解決できないためです。コールログではプロバイダーへのリクエストとレスポンスにトークンが含まれますが、ログに記録されるクライアントリクエストボディは、通常のマスキングと同様に、クライアントから受け取った生の入力のままです。
- トークンはリクエストごとにランダムなノンスを使用するため、プロンプトプレフィックスはターンごとに変化します。プロバイダー側のプロンプトキャッシュはマスキングされたターンではヒットせず、後続のターン（たとえば `previous_response_id` 経由）で返されたトークンは古いリクエストに属するため、リテラルのままになります。

#### タイプごとの選択、カスタムパターン、検出カウンター

**ダッシュボード → 設定 → セキュリティ → PII マスキング**で、_何を_マスキングするかを選択します。
ここでマスキング自体を切り替えるわけではありません。マスキングは引き続き
`PII_REDACTION_ENABLED`（リクエスト）と `PII_RESPONSE_SANITIZATION`（レスポンス + SSE）で制御され、
どちらもデフォルトでは無効です。

- **タイプごとの選択** — 組み込み ID は `src/shared/constants/piiTypes.ts`（`PII_BUILTIN_TYPES`）に一覧されています。未設定の場合はすべてのタイプが対象です（この設定が存在する前の動作）。リクエストエンジンの `ssn_us` パターンは `ssn` にマッピングされます。テンプレート（Minimal、Standard、Financial、Brazilian、USA、GDPR、POPIA、Full）は UI のチェックボックスを埋めるだけです。
- **GDPR および POPIA の識別子** — EU および南アフリカの個人識別子を対象とする 12 個の組み込み ID です（下表）。それらの正規表現、バリデーター、管轄区域タグは 1 つのテーブル `src/shared/utils/piiPatterns.ts` に定義されており、レスポンスサニタイザー（`src/lib/piiSanitizer.ts`）とリクエストマスカー（`src/shared/utils/inputSanitizer.ts`）の両方が使用します。バリデーターが受け入れた場合にのみマッチがレダクトされ、数字だけの単純な並びでは不十分です。これらの ID が存在する前に範囲を絞った選択を保存したオペレーターは、新しい ID にチェックを付けるまで、以前の動作を維持します。
- **カスタムパターン** — 最大 20 個の正規表現またはワイルドカードパターン（`*` = 空白以外の最大 64 文字、`?` = 1 文字）を指定できます。マッチした部分は `[CUSTOM_REDACTED]` になります。すべてのパターンは `compilePiiCustomPattern()`（`src/shared/utils/piiCustomPatterns.ts`）を通過します。最大 500 文字、フラグは `g i m s u` に限定され、コンパイル可能で、`safe-regex`（壊滅的なバックトラッキング）に合格し、空文字列またはレダクションプレースホルダーにマッチしてはなりません。失敗するパターンは保存時とテスト時に拒否され、保存済みの行が失敗する場合は、コンパイルされずに実行時にスキップされます。カスタムパターンはマスキングが有効な間だけ実行されます。
- **検出カウンター** — タイプごとの件数（マッチした値は一切含まない）をメモリ上に保持し、再起動時にリセットします（`src/lib/pii/piiDetectionStats.ts`）。マスキングが有効な間だけ増加します。

設定は `key_value` テーブル（名前空間 `pii_settings`、`src/lib/db/piiSettings.ts`）に保存され、1 秒間のキャッシュを介して読み取られます。API は次のとおりです。

| メソッド | パス                     | 目的                                                                      |
| -------- | ------------------------ | ------------------------------------------------------------------------- |
| `GET`    | `/api/settings/pii`      | フラグの状態、`enabledTypes`、`customPatterns`、検出カウンター            |
| `PUT`    | `/api/settings/pii`      | `enabledTypes`（`null` = すべて）および／または `customPatterns` を置換   |
| `POST`   | `/api/settings/pii/test` | 最大 8 KB のサンプルに対して 1 つのパターンをドライランし、何も保存しない |

3 つのエンドポイントはいずれも管理認証を必要とし、Zod（`src/shared/validation/schemas/piiSettings.ts`）で
ボディを検証します。ログインが無効（`requireLogin=false`）の場合、`GET` とテストエンドポイントは公開されますが、
`PUT` には引き続き、ダッシュボードセッション、`manage` スコープの API キー、書き込みスコープ以上を持つ
`oma_` アクセストークン、またはループバックから送信された CLI トークンか内部サービス用トークンが必要です。

#### GDPR（EU）および POPIA（南アフリカ）の識別子

| Id                  | Identifier                | Validation                                                                           |
| ------------------- | ------------------------- | ------------------------------------------------------------------------------------ |
| `iban`              | IBAN                      | 既知の国、その国の正確な長さ、ISO 13616 MOD-97-10                                    |
| `eu_vat`            | EU VAT番号                | 既知の加盟国プレフィックスと、その国の番号形式（VIES照会なし）                       |
| `es_dni_nie`        | スペイン DNI / NIE        | 管理文字（値 mod 23）；NIEは`X/Y/Z` + 7桁                                            |
| `it_codice_fiscale` | イタリア Codice Fiscale   | 奇数・偶数位置のテーブルに基づく管理文字                                             |
| `pl_pesel`          | ポーランド PESEL          | 加重チェックサムと、実在する生年月日のエンコード                                     |
| `nl_bsn`            | オランダ BSN              | 11検証（重み9..2、-1）                                                               |
| `de_steuer_id`      | ドイツ Steuer-ID          | ISO 7064 Mod 11,10、および数字構造のルール（先頭0は禁止）                            |
| `se_personnummer`   | スウェーデン personnummer | 最後の10桁に対するLuhnと、妥当な生年月日（10桁または12桁）                           |
| `za_id`             | 南アフリカ ID番号         | 全13桁に対するLuhn、有効な誕生月日、市民権の数字が0または1                           |
| `za_phone`          | 南アフリカの電話番号      | `+27` / `27` プレフィックス、またはスペースかハイフンで記述された国内の`0..`形式     |
| `za_vat`            | 南アフリカ VAT番号        | `4`で始まる10桁、かつ直前48文字以内に **VAT** / **BTW** があること                   |
| `za_tax_ref`        | 南アフリカの税務照会番号  | `0`〜`3`で始まる10桁、Luhn、**および**直前48文字以内に **tax** / **SARS** があること |

数字のみの形式は注文番号、ビルド番号、タイムスタンプと衝突するため、最も弱いもの（`za_vat`、`za_tax_ref`）にはキーワードによる手掛かりが必要であり、10桁の`0..`形式の数字だけでは南アフリカの電話番号として扱われません。スペース区切りのIBAN（`GB29 NWBK ...`）は一致しません。ストリーミング経路では、手掛かりは現在のチャンク内だけで検索されます。IDは汎用電話番号パターンより前に配置されているため、検証済みの識別子は独自のプレースホルダー（`[IBAN_REDACTED]`、`[NL_BSN_REDACTED]`、...）を保持します。`gdpr`および`popia`テンプレートは、それぞれEUおよび南アフリカのIDを選択します。マスキング自体は引き続きオプトイン（ハードルール #20）であり、ここでの変更によって機能フラグのデフォルトが変わることはありません。

### プロンプトインジェクション（`promptInjection.ts`）

ユーザーが提供したコンテンツ内の敵対的な構造を検出し、設定されたポリシーを適用します。動作は環境変数とコンストラクターのオプションによって制御されます。

| Setting          | Env var                                                                                               | Default | Effect                                                                                                                                                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 有効             | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false`の場合、ガードレールは即時終了します。                                                                                                                                                                            |
| モード           | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | インジェクションポリシー：`block`、`warn`、または`log`。(`redact`は後方互換性のために受け付けられますが、インジェクションテキストは除去しません。リクエストのPII書き換えは`PII_REDACTION_ENABLED`によって制御されます。) |
| ブロックしきい値 | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ブロックに必要な最低重大度。デフォルトではMediumは監視のみです。                                                                                                                                                         |

**モードの優先順位**（`getMode`）：呼び出し元の`options.mode` →
`INJECTION_GUARD_MODE` **DB機能フラグの上書き**（ダッシュボード → 設定 →
機能フラグ）→ `INJECTION_GUARD_MODE`環境変数 → `INPUT_SANITIZER_MODE`環境変数 →
`warn`。したがって、ダッシュボードの上書きは環境変数より優先され、機能
フラグUIによって実行中のガードをライブで制御できます（再起動不要）。DBの
読み取りはフェイルセーフです。エラーが発生した場合、ガードは環境変数ベースの
動作にフォールバックし、上書きが設定されていない場合の動作は環境変数のみの
解決と同一です。

検出ソース：

1. `@/shared/utils/inputSanitizer`の`sanitizeRequest()`（パイプライン内の他の箇所でも使用される共通検出セット）。
2. 組み込みの`DEFAULT_GUARD_PATTERNS`（現在は`system_override_inline`と
   `markdown_system_block`で、どちらも重大度は`high`）。
3. コンストラクターのオプションで渡される任意の`customPatterns`（文字列、正規表現、
   または`{ name, pattern, severity }`レコード）。

`mode === "block"`かつ少なくとも1つの検出が重大度しきい値を満たす場合、
`preCall`は`{ block: true, message: "Request rejected:
suspicious content detected" }`を返します。`warn`/`log`モードではガードレールが
ログを記録しますが、呼び出しは許可します。共有ヘルパーの
`evaluatePromptInjection()`もエクスポートされており、レジストリを経由せずに
プロンプトを評価する必要がある呼び出し元が利用できます。

**スキャン範囲 (v3.8.20):** 検出器は結合されたプロンプトテキストの
**最初の 16 KB** のみを検査します — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 バイト) は
`src/shared/utils/inputSanitizer.ts` にあります。`detectInjection()` と
`evaluatePromptInjection()` はどちらもパターンループを実行する前に
`slice(0, MAX_INJECTION_SCAN_BYTES)` を実行します。インジェクション指示は入力の上部付近に置かれるため、
これにより検出能力を弱めることなく、数百 KB のペイロードに対する正規表現の CPU/GC 負荷を抑えられます（#3932、#4041 を参照）。

### 認証情報マスカー (`credentialMasker.ts`)

両方のステージで実行され、デフォルトチェーンの最後（優先度 `95`）に位置します。送信ペイロード（メッセージ内容、ツール呼び出しの引数、ツール結果）**および**プロバイダーのレスポンスから、既知の API キー / シークレットトークンのパターンを秘匿化します。これにより、プロンプトに貼り付けられた認証情報（またはツール結果によってエコーバックされた認証情報）が上流プロバイダーやクライアントに漏洩することを防ぎます。

- **オプトインのみ**で、PII の秘匿化と同じ規則（ハードルール #20 に隣接）です。`settings.credentialRedactionEnabled === true` **または**
  `CREDENTIAL_REDACTION_ENABLED=true` の場合を除き無効です。無効時はガードレールは何もしません —
  ブロックも書き換えも行いません。
- `redactCredentials()` はペイロード / レスポンスツリー全体を（プロトタイプ汚染に安全で、
  `WeakSet` によって循環参照にも対応した `walkValue()` を通じて）走査し、一致した箇所を
  `[REDACTED:<type>]` プレースホルダーに置き換えます。変更されたブランチのみをコピーします。
- `CREDENTIAL_PATTERNS` は、LLM プロバイダーのキー（OpenAI、OpenAI-proj、
  Anthropic、Google、Hugging Face、Replicate）、VCS/SaaS トークン（GitHub、Slack、
  Linear、Notion、npm、Postman、Discord）、決済キー（Stripe、Square）、クラウドキー
  （AWS アクセスキー、Twilio、SendGrid、Mailgun）、秘密鍵 / JWT、
  認証情報を含む接続文字列（`mongodb://user:pass@...` など）、および汎用的な
  `Authorization`/`x-api-key`/`api-key`/`apikey` ヘッダー値パターンを対象とします。
  ヘッダー形式のキー（`authorization`、`x-api-key`、`api-key`、`apikey`）は構造的に
  （値のみを）秘匿化し、`Bearer `/`Basic ` のようなスキーム接頭辞は保持します。汎用的な
  テキスト正規表現は使用しません。
- ガードレールは決してブロックせず、書き換え（`modifiedPayload` /
  `modifiedResponse`）と注釈付け（`meta.credentialsRedacted`、`meta.count`）のみを行います。

回帰ガード: `tests/unit/credential-masker-guardrail.test.ts`。

## 基本コントラクト（`base.ts`）

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true の場合はチェーンを短絡する
  message?: string; // ブロック時に表示される
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // preCall が返し、リクエストを書き換える
  modifiedResponse?: TValue; // postCall が返し、レスポンスを書き換える
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ガードレールは、`void`、`{}`、または `{ block: false }` のいずれかを返すことで「変更なし」を示します。`modifiedPayload`/`modifiedResponse` を返すと、チェーンを通じて下流のガードレールに流れる値が置き換えられます。
`signal?: AbortSignal` は呼び出し元のライフサイクルをガードレールへ伝えます。リクエストの中断（abort）は、意図的なフェイルオープンの例外です。メディアブリッジは処理を停止し、生のメディアをサポートしないことがわかっているターゲットに復元することなく、クリーンアップを行います。

## レジストリ（`registry.ts`）

シングルトンの `guardrailRegistry` は以下を公開します：

- `register(guardrail)` — ガードレールを追加し（正規化された名前で置き換え）、`priority` の昇順で再ソートします。
- `clear()` / `list()` — 管理用ヘルパー。
- `runPreCallHooks(payload, context)` — アクティブなガードレールを反復処理し、ペイロードを `modifiedPayload` を通じて受け渡し、最初の `block: true` で停止します。
- `runPostCallHooks(response, context)` — レスポンス側で同じフローを実行します。
- `resetGuardrailsForTests({ registerDefaults })` — 状態をクリアし、オプションでデフォルトを再登録して、テストをクリーンに分離します。

両方のランナーは `{ blocked, payload|response, results, guardrail?, message? }` を返します。ここで `results` は `GuardrailExecutionResult` レコードの配列で、ガードレールごとの `blocked`、`skipped`、`modified`、`error`、`meta` フィールドを含み、トレースに役立ちます。

### リクエストごとのガードレールの無効化

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` は、現在のリクエストでスキップすべきガードレール名の重複排除済みリストを集約します。チャネルは 5 つあり、次の順序で読み取られ、1 つのリストにマージされます（重複排除では最初の出現が優先されます）：

1. `apiKeyInfo.disabledGuardrails`
2. リクエストボディの `disabledGuardrails`（トップレベル）
3. リクエストボディの `metadata.disabledGuardrails`（`metadata` がオブジェクトの場合のみ）
4. ヘッダー `x-omniroute-disabled-guardrails`
5. レガシーヘッダー `x-disabled-guardrails`

5 つのチャネルすべてがマージされ、2 つのヘッダーも含まれます。`x-omniroute-disabled-guardrails` と `x-disabled-guardrails` の両方を送信すると、それらのリストの和集合がスキップされ、空の新しいヘッダーがレガシーヘッダーを隠すことはなくなりました
（[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)、
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) で修正）。

値は文字列の配列またはカンマ区切りの文字列で指定できます。名前はトリミングされ、小文字の kebab-case に正規化され（`pii_masker` → `pii-masker`）、空のエントリは破棄されます。結果は `context.disabledGuardrails` を通じてレジストリに渡され、一致するガードレールはスキップされます（`results` では `skipped: true`）。

無効化リストは**レジストリ**にのみ影響します。プロンプトインジェクションの `block` モードは必須の境界です。インジェクションガードミドルウェア
（`src/middleware/promptInjectionGuard.ts`）は、呼び出し元が制御できる無効化リストなしで `evaluatePromptInjection()` を呼び出します（以前行っていたデッドな
`resolveDisabledGuardrails({ body })` 呼び出しは
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934) で削除されました）。そのため、`prompt-injection` を無効化したリクエストでも、`block` モードでは依然として拒否されます。これは意図的な設計です。無効化チャネルは呼び出し元が制御するもの（リクエストボディ、メタデータ、ヘッダー）であり、呼び出し元がオペレーターが設定したセキュリティコントロールを無効にできてはなりません
（[#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)）。[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) のヘッダー和集合は、どのレジストリガードレールがスキップされるかを変更するだけであり、クライアントがミドルウェアをバイパスできるようにはなりません。キー単位およびグループ単位の必須ガードレールポリシーは、v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417) で追跡されています。
[対象範囲と制限](#coverage-and-limits)を参照してください。

## 実行順序

`src/sse/handlers/chat.ts` および
`open-sse/handlers/chatCore.ts` を通過する各リクエスト（[対象範囲と制限](#coverage-and-limits) に記載されている chat ファミリーのルート）では、次の処理が行われます。

1. `resolveDisabledGuardrails(...)` が API キー、ボディ、ヘッダーからスキップリストを構築します。
2. `guardrailRegistry.runPreCallHooks(body, ctx)` が、優先度の昇順でガードレールを実行します。
   - 無効化されたガードレールは `skipped` として記録されます。
   - 各ガードレールの `preCall` は、`modifiedPayload` を通じてペイロードを書き換えることができます。
   - 最初に `block: true` になった時点でチェーンを短絡し、ハンドラーはガードレールによる拒否レスポンスを返します。
3. （書き換えられている可能性のある）ペイロードが、コンボルーティングおよび上流へのディスパッチに渡されます。
4. **非ストリーミングのみ:** レスポンスの組み立て後、`guardrailRegistry.runPostCallHooks(...)` が同じチェーンをレスポンスに対して実行します。この時点で `block: true` になった場合、上流のレスポンスは破棄され、HTTP 400 が返されます。ストリーミングレスポンスでは、このステップは完全にスキップされます。
5. **可逆ボールトのみ:** リクエストでトークンが発行された場合、`handleChat` は、ポストコールフックおよびストリーミング PII 変換の後に返す 2xx レスポンス上でトークンを復元します。これにより、`PII_RESPONSE_SANITIZATION` が認識するのはトークンとモデルが生成した PII であり、復元された元の値ではありません。

例外をスローしたガードレールは `error: <message>` として記録され、`logger.warn` を通じてログに出力されます。ただしチェーンは継続します。これは意図的なフェイルオープン設計です。

## カバレッジと制限

ガードレールレジストリはチャットパイプラインにのみ組み込まれています。これらの制限は
`tests/unit/guardrail-pipeline-wiring-characterization.test.ts` と
`tests/unit/guardrail-pipeline-characterization.test.ts` によって固定されています。動作を変更する場合は、これらのテストを意図的に更新してください。

### フックの実行箇所

| フック / 制御                                  | 実行対象                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `runPreCallHooks`                              | `handleChat`（`src/sse/handlers/chat.ts`）によって処理されるリクエスト：`/v1/chat/completions`、`/v1/completions`、`/v1/messages`、`/v1/responses`（および `/v1/responses/*`）、`/v1/relay/chat/completions`、`/v1/providers/{provider}/chat/completions`、`/v1/api/chat`、`/v1/antigravity`、`/v1beta/models/*`、Telegram チャットプロキシ。また、ダッシュボードのテストエンドポイント `/api/guardrails/test`。呼び出し前のブロックは HTTP 400 を返します。 |
| `runPostCallHooks`                             | **非ストリーミング**のチャットレスポンスのみ（`open-sse/handlers/chatCore/nonStreamingResponse.ts`）。ストリーミングレスポンスがここに到達することはありません。                                                                                                                                                                                                                                                                                             |
| ストリーミング PII                             | `createPiiSseTransform`（`src/lib/streamingPiiTransform.ts`）。`PII_RESPONSE_SANITIZATION` が有効な場合に `streamingPipeline.ts` でパイプされます。これはガードレールではないため、無効化用の経路の影響を受けません。                                                                                                                                                                                                                                        |
| 可逆 PII ボールト                              | `PII_REDACTION_ENABLED` と `PII_REVERSIBLE_VAULT_ENABLED` が有効な場合に限り、`handleChat` によって処理されるリクエスト。トークンは呼び出し前の `pii-masker` によって発行され、`handleChat` の終了時に復元されます（`src/lib/pii/requestTokenVaultScope.ts`）。リクエストに対して `pii-masker` を無効にすると、何も発行されません。                                                                                                                          |
| インジェクションガードミドルウェア（レガシー） | チャット系を含む、プロンプトを受け取るすべての `/v1` ルート（[ルートのカバレッジ](#injection-guard-route-coverage--red-team-phase-8--block-d) を参照）。プロンプトインジェクションのみ。                                                                                                                                                                                                                                                                     |

### 対象外

- **メディア、埋め込み、データの各ルート**（`/v1/images/*`、`/v1/embeddings`、
  `/v1/audio/*`、`/v1/videos/generations`、`/v1/music/generations`、
  `/v1/rerank`、`/v1/search`、`/v1/moderations`）はレジストリに到達しません。PII
  マスキング、認証情報のマスキング、モダリティブリッジはこれらのルートでは実行されません。実行される唯一のチェックは、レガシーのインジェクションガードミドルウェアです。
- **ストリーミングレスポンス**には、呼び出し後のガードレールは適用されません。`pii-masker` や
  `credential-masker` による呼び出し後の処理も、呼び出し後のブロックもありません。適用されるのは、ストリーミング PII
  トランスフォームのみです（`PII_RESPONSE_SANITIZATION` が有効な場合）。ストリーミングレスポンスでエコーバックされた認証情報は、リダクトされません。
- **無効化用の経路とミドルウェアの関係（意図された仕様）：** ミドルウェアは、呼び出し元が制御する無効化リストを渡さず、独自に `evaluatePromptInjection()` を呼び出してプロンプトインジェクションを評価します。`block` モードは、呼び出し元が制御する無効化では回避できない必須の境界であり、チャット系ルートでも同様です
  （[#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)）。`prompt-injection` を無効にすると、レジストリのガードレールのみがスキップされます。

### 呼び出し後の処理前にレスポンスを参照するもの

非ストリーミング経路の順序は、メモリ抽出 → 組み込みツールの実行 → 呼び出し後のガードレール → 呼び出し後のブロック終了 → セマンティックキャッシュへの保存です。

- **メモリ抽出**と**ツール実行**は、呼び出し後のガードレールによってレスポンスが書き換えられたりブロックされたりする前のレスポンスを参照します。
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) 以降、`PII_RESPONSE_SANITIZATION` が有効な場合、メモリ抽出では抽出したテキストを `sanitizePII` に通します（ストリーミングと非ストリーミングの両方）。ただし、後から呼び出し後の処理でブロックされるレスポンスも、メモリとツールにはすでに提供されています。
- **セマンティックキャッシュ**は呼び出し後の処理の後にレスポンスを保存するため、書き換え後のレスポンスが保存され、ブロックされたレスポンスがキャッシュされることはありません。キャッシュエントリは API キーごとにキー付けされます。

## 設定

組み込みのガードレールによって読み取られる環境変数:

| 変数                                  | 使用箇所                   | 効果                                                                                                                          |
| ------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | 検出を完全に無効にするには `false` に設定します。                                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | インジェクションポリシー: `warn`、`block`、または `log`。従来の値 `redact` ではインジェクションテキストは書き換えられません。 |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | インジェクションガードのモード。DB の機能フラグでもあり、環境変数を上書きします（DB > ENV）。                                 |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` で拒否する最小重大度: `high`（デフォルト）、`medium`、または `low`。                                             |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` の従来の別名。                                                                              |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` の場合、リクエスト内の PII が秘匿化されます（インジェクションモードとは独立）。                                        |
| `PII_REVERSIBLE_VAULT_ENABLED`        | `pii-masker`, `handleChat` | `PII_REDACTION_ENABLED` と併用すると、復元可能なトークンを発行し、2xx レスポンスで復元します。                                |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (下流)        | レスポンス側のマスカーの動作を制御します。                                                                                    |

Modality Bridge のガードレールは、環境変数ではなく DB ベースの設定ストア
（`getSettings()`）から実行時設定を読み取ります。Vision の主要キーは
`modalityBridgeVisionEnabled`、`modalityBridgeVisionMode`、
`modalityBridgeVisionModel`、`modalityBridgeVisionTaskAware`、
`modalityBridgeVisionPrompt`、`modalityBridgeVisionTimeout`、
`modalityBridgeVisionMaxImages`、`modalityBridgeVisionMaxChars`、
`modalityBridgeCacheEnabled`、`modalityBridgeCacheTtlMinutes`、および
`modalityBridgeCacheMaxEntries` です。従来の
`visionBridge*` キーは、文書化された 1 サイクル限りの読み取りフォールバックとしてのみ受け付けられます。ダッシュボードへの書き込みでは主要キーが使用されます。デフォルト値とフォールバックの解決処理は
`src/shared/constants/modalityBridgeDefaults.ts` にあり、従来の定数は
`src/shared/constants/visionBridgeDefaults.ts` に保持されています。

Audio では、`modalityBridgeAudioEnabled`、`modalityBridgeAudioModel`、
`modalityBridgeAudioTimeout`、`modalityBridgeAudioMaxClips` と、共有の
`modalityBridgeCache*` 設定が使用されます。これらのキーは Modality Bridge スキーマの導入時に追加されたため、Audio には従来のキーへのフォールバックはありません。

Video では、`modalityBridgeVideoEnabled`、`modalityBridgeVideoAnalysisMode`、
`modalityBridgeVideoModel`、
`modalityBridgeVideoFrameCount`、`modalityBridgeVideoSamplingPolicy`、
`modalityBridgeVideoMaxVideos`、および
`modalityBridgeVideoTimeout` と、共有の `modalityBridgeCache*` 設定が使用されます。
FFmpeg/ffprobe は運用上任意の依存関係であり、フレームのキャプション生成によってレイテンシーとモデルコストが増加するため、デフォルトでは無効になっています。

## カスタムガードレール

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

手順:

1. `BaseGuardrail` を継承した `src/lib/guardrails/myGuardrail.ts` を作成する。
2. `preCall` および/または `postCall` を実装する。
3. インポート時に登録する(`registerDefaultGuardrails` からプッシュする)か、
   実行時に `guardrailRegistry.register(...)` を呼び出す — レジストリは
   正規化された名前が同じ既存のガードレールを置き換える。
4. `tests/unit/` 配下にテストを追加する(既存の例:
   `tests/unit/guardrails-registry.test.ts`、
   `tests/unit/prompt-injection-guard.test.ts`、
   `tests/unit/guardrails/visionBridge.test.ts`)。

## テスト

テスト間では `resetGuardrailsForTests()` を使用して、既知の状態から開始する。
`{ registerDefaults: false }` を渡すと空のレジストリから開始し、
テスト対象のガードレールのみを登録できる。Vision Bridge は依存性注入
(`deps.getSettings`、`deps.callVisionModel`)を受け付ける。Audio Bridge は
設定、機能、STT モデル選択、認証情報チェック、文字起こしに関する
同等のシームを公開している。そのため、テストは DB や

## インジェクションガードのルートカバレッジとレッドチーム(フェーズ 8 · ブロック D)

インジェクションガード(`createInjectionGuard` / `withInjectionGuard`)は、
ユーザープロンプトを受け付けるすべてのルートをカバーする。`INJECTION_GUARD_MODE`
を尊重する(デフォルトの `warn` = ログのみ;`block` = HTTP 400 `SECURITY_001` を返す)。

| タイプ         | ルート                                                                                                                                               | デフォルトモード |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| テキスト(既存) | `/v1/chat/completions`、`/v1/completions`、`/v1/relay/chat/completions`                                                                              | warn             |
| 生成系         | `/v1/messages`、`/v1/responses`、`/v1/images/generations`、`/v1/images/edits`、`/v1/videos/generations`、`/v1/music/generations`、`/v1/audio/speech` | warn             |
| データ         | `/v1/embeddings`、`/v1/rerank`、`/v1/search`、`/v1/moderations`                                                                                      | warn             |

テキスト抽出(`extractMessageContents`)は `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` をカバーする。

**レッドチーム(ナイトリー、`nightly-llm-security.yml`):** promptfoo は
`INJECTION_GUARD_MODE=block` で各ルートが OWASP-LLM コーパスをブロックすることを検証し、
garak はプローブを実行する(シークレットがない場合はスキップ)。
`moderations` は一貫性のために含まれている。ブロックモードは必須の境界である:
`evaluatePromptInjection()` はミドルウェアが渡すリクエストごとの無効化リストを
無視するため、`disabledGuardrails` によってルートがブロックモードから免除されることは
**ない**([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413))。

ナイトリーワークフロー(`.github/workflows/nightly-llm-security.yml`、cron + 手動
ディスパッチ)には 2 つのジョブがある:

- **`promptfoo-guard`(ブロッキング)** — `INJECTION_GUARD_MODE=block` で
  `promptfoo eval -c promptfooconfig.yaml` を実行する。各攻撃的ケース
  (例:「ignore all previous instructions…」(以前の指示をすべて無視せよ)、
  DAN スタイルのジェイルブレイク)は、レスポンスが `error.code === "SECURITY_001"` を
  含むこと、すなわちガードが実際にリクエストを拒否したことをアサートする。
- **`garak`(アドバイザリ)** — ローカルの OmniRoute インスタンス
  (`http://localhost:20128/v1`)に対して garak `--probes promptinject,dan,leakreplay`
  を実行する。プロバイダーシークレット(`PROMPTFOO_PROVIDER_KEY`)でゲートされ、
  正常にスキップされ、`|| true` が付与されているため、CI を失敗させずにレポートする。

ガードヘルパー(`createInjectionGuard` / `withInjectionGuard`)のカバレッジは、
プロンプトを受け取るすべての `/v1` ルートに及ぶ。プロンプトテキストは
`src/shared/utils/inputSanitizer.ts` 内の `extractMessageContents()` によって
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` から抽出される。
