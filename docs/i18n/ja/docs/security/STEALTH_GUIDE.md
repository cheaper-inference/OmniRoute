OmniRoute は、非公式クライアントを能動的にフィンガープリントするエッジ（TLS JA3/JA4、ヘッダー順序、JSON ボディ形状、整合性トークン）を持つプロバイダーと統合します。このページでは、OmniRoute が公開するステルス機能の対象領域と、それらの実装場所について説明します。

## 法的および倫理的な注意事項

ステルス機能は、OmniRoute がユーザー所有の公式アカウント（Claude Code CLI、Codex、Antigravity、Cursor など）と OmniRoute の統合 API の間の互換レイヤーとして機能できるようにするためのものです。これらは、不正検知の回避、認証情報の共有、またはプロバイダーの利用規約への違反を目的としたものでは**ありません**。メンテナーは、アカウント作成時に同意したアップストリームの利用規約を運用者が遵守することを求めています。

## TLS フィンガープリンティングレイヤー

### `open-sse/utils/tlsClient.ts` — wreq-js（Chrome 124）

永続的な `wreq-js` セッションは、アカウントスコープと解決済みプロキシごとに遅延作成されます。
プロセス全体の `TlsClient` は、Cloudflare の背後にあるアップストリーム向けに **macOS 上の Chrome 124** を偽装するセッションを最大 128 個プールします。
ネイティブランタイムが利用できない場合、`TlsClient.fetch()` はフェイルクローズします。呼び出し元は、このラッパーの外部でフォールバックを明示的に選択できます。

- セッションプロファイル: `browser: "chrome_124", os: "macos"`
- プロキシ解決（優先順）: `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY`（小文字も対象）
- タイムアウト: `TLS_CLIENT_TIMEOUT_MS`（`FETCH_TIMEOUT_MS` から継承、デフォルトは 600000）
- `wreq-js` の Response は fetch 互換です（`headers`、`text()`、`json()`、`clone()`、`body`）。
- 最初のバイトのウォッチドッグ（`open-sse/utils/tlsFirstByteWatchdog.ts`、#12656）: `TlsClient.fetch()` は
  アップストリームのヘッダーが到着するとすぐに解決されるため、`TLS_CLIENT_TIMEOUT_MS` だけでは、
  最初のバイトをまったく返さないボディを制限できません。`guardTlsFirstByte()` はボディの最初の `read()` と
  `TLS_FIRST_BYTE_WATCHDOG_MS`（デフォルトは `10000`、`0` で無効化）を競合させます。正常なボディには
  影響しませんが、停止したボディでは wreq リーダーをキャンセルし、`proxyFetch` の既存の
  TLS フォールバックロジックが直接／プロキシディスパッチャーへフォールスルーできるようにします（たとえば、
  ボディを持つ POST のようなリプレイセーフでないリクエストは、暗黙的に再試行される代わりに引き続き例外をスローします）。

### Web Cookie プロバイダートランスポート — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` は、以下の 5 つの専用
Web Cookie トランスポートで共有されるアダプターです。各軽量プロバイダーラッパーがブラウザー／OS プロファイルを選択します。このアダプターは、
`open-sse/utils/tlsClient.ts` 内の単一の wreq ランタイムローダーとトランスポートプールを使用し、
プロファイル + OS + 解決済みプロキシをキーとします。一方、すべてのリクエストは `cookieMode: "ephemeral"` を使用します。そのため、
アカウントとリクエストはトランスポートレベルの接続を共有しますが、wreq セッションや Cookie jar は一切共有しません。

| プロバイダー | プロファイル  | エミュレートする OS | ストリーム EOF ポリシー                   |
| ------------ | ------------- | ------------------- | ----------------------------------------- |
| Claude       | `chrome_146`  | Linux               | `[DONE]` を含める                         |
| Perplexity   | `firefox_151` | macOS               | `event: end_of_stream` を含める           |
| Grok         | `chrome_146`  | Linux               | `[DONE]` を除外                           |
| Notion       | `chrome_146`  | Windows             | `[DONE]` を含める                         |
| LMArena      | `chrome_146`  | Windows             | センチネルなし。ネイティブ EOF でクローズ |

- ストリーミングはネイティブレスポンスの `ReadableStream` を直接消費します。一時ファイルやサイドカーは
  作成されません。
- ストリームを公開する前に、先頭から最大 256 バイトが検査されます。SSE プロバイダーは SSE ではない
  エラーをバッファリングします。Grok/LMArena は Cloudflare チャレンジを `403` に、HTML インタースティシャルを `502` にマッピングします。
- ネイティブリクエストのタイムアウトは、引き続き絶対的な JS ハードデッドラインでラップされます。ハングが発生すると、
  影響を受けたプロファイル／OS／プロキシのトランスポートのみが無効化されて閉じられ、次のリクエスト時に再作成されます。
- プロキシ解決の優先順位は、呼び出しごとの `proxyUrl` → リクエストスコープのアカウント／ダッシュボードコンテキスト →
  `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY`（小文字のバリアントを含む）です。解決エラーは、
  直接接続が漏洩するのを防ぐためフェイルクローズします。LMArena は意図的に `arena.ai` に対して解決します。
- `byteResponse` は、UTF-8 の破損なしで Content-Type が指定された `data:` URL を返します。
- エラーは、`TlsClientUnavailableError`（パッケージ／アドオンが利用不可）、`TlsClientHangError`
  （デッドライン超過）、および 128 個に制限されたプロファイル／OS／プロキシスロットがすべて使用中またはクローズ中の場合の
  `WreqTransportCapacityError`（共有セッション容量エラーコード）です。

上記の汎用 `TlsClient` セッションは、ブラウザーにより維持される永続的な Cookie 状態専用のままです。
両方のパスは、キャッシュされた単一の wreq モジュールローダーとプロセスライフサイクルフックを再利用しますが、Cookie の有効期間が
意図的に異なるため、それぞれのプールは分離されたままです。

これらのプロファイルは固定されたパッケージでサポートされていますが、実際の WAF による受け入れ可否は、
ローカルのコントラクトテストとは無関係に変化する可能性があります。アップストリームブラウザーとの同等性を主張する前に、
明示的に許可された実アカウントを使用してフィンガープリントの変更を検証してください。

## Claude Code ステルスバンドル

`cliCompatMode` が有効な場合、OmniRoute は送信する Claude リクエストを変形し、`claude-cli` のトラフィックと見分けがつかないようにします。以下の 3 つのモジュールが連携します。

### `claudeCodeFingerprint.ts`

課金ヘッダーに埋め込まれる 3 文字の `cc_version` フィンガープリントを計算します。

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"`（ハードコード済み。公式クライアントと一致）
- 入力: 最初のユーザーメッセージ本文のインデックス 4、7、20 にある文字 + バージョン文字列
- 出力: 3 文字の 16 進数プレフィックス

### `claudeCodeCCH.ts`（クライアントコンテンツハッシュ）

公式 Claude Code CLI が Bun/Zig を介して計算する、サーバー側の整合性チェックです。OmniRoute はこれを `xxhash-wasm` で再実装しています。

1. `cch=00000;` プレースホルダーを使用して本文をシリアライズ
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. 5 文字になるようゼロ埋めした小文字の 16 進数
4. `cch=00000;` を計算済みトークンに置換

定数:

- シード: `0x6e52736ac806831e`
- パターン: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

「機密性の高い」クライアント名の最初の文字の後に Unicode の**ゼロ幅接合子**（`U+200D`）を挿入し、上流のフィルターが grep できないようにします。デフォルトの単語リスト:

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

適用対象: `system` ブロック、すべての `messages[].content`、および `tools[].description` / `tools[].function.description`。オペレーターは `setSensitiveWords()` を使用して上書きできます。

### `claudeCodeCompatible.ts` — `anthropic-compatible-cc-*` プロバイダー

「本物の Claude Code」トラフィックのみを受け入れるサードパーティー製 Anthropic リレー向け:

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.280 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- デフォルトでは `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"`
- 接続ごとの「Enable redact-thinking beta」トグルは、CC Compatible の上流が編集済み思考ストリームを明示的に必要とする場合に、`redact-thinking-2026-02-12` を追加します
- 接続ごとの「Enable summarized thinking display」トグルは `providerSpecificData.requestDefaults.summarizeThinking` を保存し、表示モードがまだ設定されていない CC Compatible の思考リクエストに `display: "summarized"` を追加します
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"`（Opus/Sonnet 4.x ファミリー）
- デフォルトパス: `/v1/messages?beta=true`

同じバンドル内の関連モジュール:

- `claudeCodeConstraints.ts` — temperature + cache-control のルール
- `claudeCodeToolRemapper.ts` — ツール名の再マッピング
- `claudeCodeExtraRemap.ts` — 追加のペイロード正規化

## Antigravityステルス

Antigravityリクエストは、呼び出し元のテキストをバイト単位で保持します。 OmniRoute 、 IDEクライアントを模倣するためにプロンプトまたはrename/injectツールにゼロ幅文字を挿入しません。

### `antigravityHeaderScrub.ts`

転送前にステンレスSDKマーカー (`x-stainless-lang`、 `x-stainless-package-version`、 `x-stainless-os`、 `x-stainless-arch`、 `x-stainless-runtime`、 `x-stainless-runtime-version`、 `x-stainless-timeout`、 `x-stainless-retry-count`、 `x-stainless-helper-method`) を除去します。

### ⚠️リスク: `ANTIGRAVITY_CREDITS=always` (アカウント禁止ホット スポット)

`ANTIGRAVITY_CREDITS=always` ( `open-sse/executors/antigravity.ts`によって消費される) ルート**毎**Googleの無料枠クォータによって処理を制御するのではなく、 Antigravity AIクレジット超過 (有料のGoogleクレジット) を介してリクエストします。これは機能として文書化されていますが、**最も一般的な ToS 違反レポート**—複数のGoogle Ultra アカウントは、 `=always`で数時間実行した後、 `403 / "service disabled for ToS violation" / insufficient_quota`で禁止されました。

アップストリームの強制がオンになっています**Google側**、 OmniRoute阻止できるものは何もありません。環境変数名と既存のドキュメントを見ると、ノブを安全に切り替えることができるように思えます。そうではありません。

**これが無料枠のみの使用よりも積極的に不正行為の検出を行う理由:**

- 単一のGoogleアカウントでの継続的な自動支出は、無料枠のヒットクォータ アンド ストップとは異なるフラグを立てます。
- クレジット超過にはレートの上限がないため、設定を誤ったクライアントは数分で数百のUSDを使い果たし、API キーの再販またはボット トラフィックのように見える可能性があります。
- 複数のOmniRouteユーザーが同じ外部IPから並行して超過クレジットに達すると、信号が複雑になります。

**推奨姿勢：**

1. オペレータが有料クレジットとアカウント強制のリスクを明示的に受け入れる場合を除き、デフォルトの`ANTIGRAVITY_CREDITS=off`維持します。 `retry`最初に通常のリクエストを送信し、適格なクォータ 429 の後に最大 1 回クレジットを注入します。 `always`最初のリクエストでクレジットを挿入します。
2. **自動コンボを介してプロバイダー間で負荷を分散します。** (`model: "auto"`または`kr/glm/etc` -combo) 単一のAntigravityアカウントを飽和させる代わりに。
3. **接続ごとのRPM制限を設定する**Antigravityプロバイダーの編集ページ (ダッシュボード→プロバイダー→ Antigravity →接続→レート制限)。 30 ～ 60 RPMが、継続的な使用に対する防御可能な上限です。
4. **安定したオペレータ制御の上流ネットワーキングを使用する**また、無関係なユーザーやワークロード間で 1 つのアカウントを共有することは避けてください。
5. **禁止されている場合**: Google送信した正確な`quota_exceeded` / `service disabled`応答本文を使用して、 `support.google.com` → 「 Workspace/Accountアクセスを復元」経由でアピールします。復元は保証されません。

環境リファレンスには、各クレジット モードのアカウントと支出への影響が文書化されています。

#### `=always`: Antigravity OAuthルーティング全般だけではありません

停止はクレジット超過に限定されません。 2026 年 11 月のレポート (#19223、 #19266) では、 `antigravity`および`agy` (Antigravity CLI) プロバイダーを介したルーティング中に一時停止されたいくつかのGoogleアカウントについて説明しています。

```
403: This service has been disabled in this account for violation of Terms of Service.
Please submit an appeal to continue using this product.
```

どちらのプロバイダーも、 Antigravity製品OAuthセッションで認証します。これは、接続が追加される前に、ダッシュボードのリスク通知 (「このプロバイダーは、 proxy/router使用が許可されていない公式製品session/OAuth使用しています」) で警告される場合です。上記の推奨事項のいずれも、その使用を許可するものではありません。 1 つのアカウントが運ぶトラフィック量を減らすだけです。

**Geminiモデル用の承認されたAPIインターフェイス。** Google 、 APIsを介してGeminiへのプログラムによるアクセスを提供します。 OmniRouteこれを通常の API キー プロバイダーとしてサポートします。

| プロバイダーID | ダッシュボード名           | 資格情報                                                                                 |
| -------------- | -------------------------- | ---------------------------------------------------------------------------------------- |
| `gemini`       | Gemini (Google AIスタジオ) | Google AI Studio のGemini APIキー (無料利用枠あり)                                       |
| `vertex`       | 頂点AI                     | サービス アカウントJSON、 OAuthアクセス トークン、または Vertex Express APIキー (Gemini) |

これらのプロバイダーは、 Antigravity製品セッションとは異なり、 APIアクセスに資格情報Google発行を使用します。これらは、すべての使用法を準拠させたり、施行のリスクを排除したりするものではありません。それぞれの使用法には独自の条件が適用され、運用者はその使用条件を確認する必要があります。たとえば、 [Gemini API追加利用規約で](https://ai.google.dev/gemini-api/terms)は、 APIクライアントが欧州経済領域、スイス、または英国のユーザーに利用可能になっている場合、有料サービスのみが許可されており、無料サービスに送信されたコンテンツはGoogleの製品を改善するために使用される場合があります。 Vertex AI 、代わりにGoogle Cloud 規約 ([サービス固有の規約](https://cloud.google.com/terms/service-terms)) に該当します。価格と割り当ては、 Antigravityサブスクリプションではなく、 API条件に従います。

上記のAntigravity一時停止を回避したい事業者は、その使用がプロバイダーの条件に適合していることを確認した後、 `antigravity` / `agy`の代わりにこれらのプロバイダーのいずれかを介してGeminiトラフィックをルーティングする必要があります。

タッチポイント:

- `open-sse/executors/antigravity.ts` —は`process.env.ANTIGRAVITY_CREDITS`を読み取ります
- `src/lib/oauth/providers/antigravity.ts` —資格情報の配管
- 元のインシデント レポート: ディスカッション[#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## CLI フィンガープリントレジストリ — `open-sse/config/cliFingerprints.ts`

公式 CLI の mitmproxy トレースから取得した、**厳密な**ヘッダー順序と JSON ボディフィールド順序を固定するプロバイダー別テーブルです。現在登録済み: `codex`、`claude`。さらに、`antigravity` と `github` については `providerHeaderProfiles.ts` にランタイムから導出されるプロファイルがあります。

```ts
interface CliFingerprint {
  headerOrder: string[]; // 大文字と小文字を区別
  bodyFieldOrder: string[]; // トップレベルの JSON キー
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

環境変数を使用してプロバイダーごとに切り替えます（下記参照）。無効にすると、ヘッダーとボディキーは Node/JSON が生成した順序のままになるため、簡単にフィンガープリントされます。

## MITM プロキシ（Antigravity、Linux/macOS/Windows）

バイナリを `OPENAI_BASE_URL` でリダイレクトできない CLI のために、OmniRoute はローカルで TLS を終端するプロキシを実行します。エンドポイントは `src/app/api/cli-tools/antigravity-mitm/` 配下にあります。

| メソッド | エンドポイント                          | 用途                                                 |
| -------- | --------------------------------------- | ---------------------------------------------------- |
| GET      | `/api/cli-tools/antigravity-mitm`       | ステータス — running、pid、dnsConfigured、certExists |
| POST     | `/api/cli-tools/antigravity-mitm`       | MITM を開始（`apiKey` + `sudoPassword` が必要）      |
| DELETE   | `/api/cli-tools/antigravity-mitm`       | MITM を停止                                          |
| GET      | `/api/cli-tools/antigravity-mitm/alias` | モデルエイリアスを一覧表示                           |
| PUT      | `/api/cli-tools/antigravity-mitm/alias` | ツールのモデルエイリアスを保存                       |

インターセプト対象ホスト: **`daily-cloudcode-pa.googleapis.com`**（Antigravity のアップストリーム）。

### 開始シーケンス（`src/mitm/manager.ts::startMitm`）

1. `selfsigned` を使用して自己署名証明書を生成（RSA-2048、SHA-256、1年）— `cert/generate.ts`
2. 証明書をシステムの信頼ストアにインストール — `cert/install.ts`
3. hosts エントリ `127.0.0.1 daily-cloudcode-pa.googleapis.com` を追加 — `dns/dnsConfig.ts`
4. `ROUTER_API_KEY` + `MITM_LOCAL_PORT`（デフォルトは `443`）を指定して `src/mitm/server.cjs` を起動
5. PID を `<DATA_DIR>/mitm/.mitm.pid` に永続化

### Linux の動的な信頼ストア検出 — `cert/install.ts`

`getLinuxCertConfig()` は優先順位リストを走査し、最初に存在するディレクトリを選択します。

| ディストリビューションファミリー | ディレクトリ                                | 更新コマンド             |
| -------------------------------- | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu                  | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro         | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS           | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                         | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

証明書ファイル名: `omniroute-mitm.crt`。`getCertFingerprint()` を使用してフィンガープリントを照合します（DER の SHA-1）。

さらに、`certutil` が利用可能な場合、`updateNssDatabases()` はユーザーごとの NSS DB に証明書をインストールします: `~/.pki/nssdb`、`~/snap/chromium/.../nssdb`、すべての Firefox プロファイル（snap を含む）。ニックネームは **`OmniRoute MITM Root CA`** です。

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** 管理者権限の PowerShell → `certutil -addstore Root`

### 認証

すべての MITM エンドポイントには管理認証（`requireCliToolsAuth`）が必要です。sudo パスワードはモジュールスコープ内にキャッシュされ（`globalThis` には決して保存されません）、`stopMitm()` の実行時に消去されます。

## 受信ヘッダーのサニタイズ

OmniRoute は転送前に受信クライアントヘッダーを除去するため、Cursor から到着したリクエストの `User-Agent: Cursor/X.Y.Z` が Claude のアップストリームに漏れることはありません。拒否リストについては `src/shared/constants/upstreamHeaders.ts` を参照してください。このリストは Zod スキーマおよびユニットテストと常に同期されています。

## プロバイダーの変更時にフィンガープリントを更新する方法

1. `mitmproxy` を使用して公式 CLI のトラフィックをキャプチャする（TLS インターセプト + ダンプ）
2. JA3/JA4 と実際のヘッダー順序を抽出する
3. 該当する `CLI_FINGERPRINTS[...]` エントリを更新する
4. `.env.example` 内の対応する `*_USER_AGENT` のデフォルトを更新する
5. TLS ハンドシェイク自体が変更された場合は、該当するプロバイダーラッパーまたは wreq-js の `browser:` オプションを更新する
6. プロバイダー固有の TLS テストを実行し、稼働中のプロバイダーに対して手動カナリアテストを行う
7. パッチリリースとして公開し、`CHANGELOG.md` に記録する
