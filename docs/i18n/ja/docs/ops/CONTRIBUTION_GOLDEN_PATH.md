このガイドを使用して、プルリクエストに対する信頼性の高い最小限の開発ループを選択してください。これは、
以下にリンクされている領域固有のアーキテクチャおよびセキュリティドキュメントに代わるものではありません。一般的な
変更タイプごとに、そのコントラクト、重点チェック、CI カバレッジを関連付けるものです。

## すべての変更がたどる手順

1. **編集前にベースを選択します。** アクティブな `release/v*` ブランチのうち最上位のものを見つけ、その先端から
   ブランチを作成します。`main` ではなく、そのブランチをターゲットにしてください。リリースフリーズ中の場合は、フリーズされた
   ブランチをターゲットにせず、
   [ブランチおよびリリースモデル](BRANCHING_MODEL.md)に記載された次のアクティブなサイクルを使用してください。
2. **コントラクトを明示します。** 変更が影響するすべてのカタログ、スキーマ、生成済み成果物、公開 API、またはユーザー
   インターフェースを特定します。以下の表に、開始時に最低限確認すべきものを示します。
3. **重点テストを作成または更新します。** `src/`、`open-sse/`、`electron/`、または
   `bin/` の本番コードを変更する場合は、同じ PR に自動テストが必要です。動作を証明する最小限のテストファイルを
   実行してから、記載されている重点ゲートを実行します。
4. **広範なマトリクスは CI に任せます。** 完全なユニットシャード、Vitest、カバレッジラチェット、および
   本番ビルドは PR 上で実行されます。重点テストの失敗から影響範囲が広いと判明した場合、または変更が複数の
   サブシステムにまたがる場合にのみ、ローカルで広範なスイートを実行してください。
5. **レビュー前に整合させます。** アクティブなベースをフェッチし、その新しいコミットと、それに対する自分の差分を
   確認してから、コントリビューターワークフローに従ってベースをリベースまたはマージします。生成済みファイルと
   カタログの競合は、そのソース側で解決して再生成し、重点ループを再実行したうえで、PR が引き続きアクティブな
   リリースブランチをターゲットにしていることを確認します。
6. **証跡を記録します。** PR テンプレートに、実行したコマンド、追加または変更したすべてのテストファイル、
   マイグレーションまたはフィーチャーフラグ、および未完了の CI 専用検証を記載します。

## 変更タイプ別のゴールデンパス

以下のコマンドは最低限の重点チェックであり、変更した動作を直接カバーするテストを省略してよいという意味では
ありません。

### プロバイダー

**コントラクト**

- `src/shared/constants/providers/` 内のプロバイダー定義と、
  `src/shared/constants/providers.ts` でのその合成。
- `open-sse/config/providerRegistry.ts` またはそこから分離されたレジストリファイル内のモデルと機能。
- 該当する場合は、エグゼキューター／トランスレーターの選択、OAuth または API キー設定、ダッシュボードアセット、および生成済み
  プロバイダーリファレンス。
- 公開認証情報には `resolvePublicCred()` を使用する必要があります。エラーレスポンスには共有のサニタイズ済み
  エラーヘルパーを使用する必要があります。`docs/security/PUBLIC_CREDS.md`（git 内に存在し、`/docs` にはコンパイルされません）および
  [エラーのサニタイズ](../security/ERROR_SANITIZATION.md)を参照してください。

**重点ループ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # カタログを変更した場合。生成された差分をコミットする
npm run lint
```

影響を受けるすべてのリクエストファミリー（チャット、Responses、画像、埋め込み、音声、動画）もテストしてください。
生成されたカタログとゴールデン差分はコントラクト変更としてレビューし、無条件に受け入れないでください。

### ルーティング

**コントラクト**

- `src/shared/constants/routingStrategies.ts` 内の公開ストラテジー値と UI メタデータ。
- `open-sse/services/combo.ts` および `open-sse/services/combo/` 配下のディスパッチと順序付け。
- Combo スキーマ、永続化、レジリエンス状態、モデル機能、および API／UI コントロール。
- 動作を変更する場合は、[Auto-Combo エンジン](../routing/AUTO-COMBO.md)およびレジリエンスに関するドキュメント。

**重点ループ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ストラテジーまたはディスパッチの変更
npm run check:known-symbols      # ストラテジー登録の変更
npm run lint
```

ローカルでは、モック化したアップストリームを使った決定論的テストを使用してください。ライブ Combo スモークテストには認証情報が必要であり、
手動で実施するもので、CI の代わりにはなりません。

### UI / UX

**コントラクト**

- `src/app/` および `src/shared/components/` 配下の Next.js ルート／ページと共有コンポーネントの境界。
- API レスポンス形式、読み込み／空／エラー状態、キーボードおよびスクリーンリーダーの動作、
  レスポンシブレイアウト、テーマ、ロケール展開。
- `src/i18n/messages/en.json` 内の英語 UI ソース文字列。ユーザー向けの新しい文言をハードコードしないでください。

**重点ループ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

インタラクションまたは視覚的な変更ではアプリを実行し、狭いビューポートと広いビューポートの両方を確認してください。CI では
本番ビルドとより広範なスイートが実行されますが、視覚的な動作については、変更に適した重点コンポーネントテスト、Playwright、
または文書化された手動チェックが引き続き必要です。

### i18n

**コントラクト**

- `src/i18n/messages/en.json` は UI のソースであり、`config/i18n.json` はロケールのソースです。
- CLI カタログは `bin/cli/locales/` 配下に別途配置されています。
- ICU プレースホルダーとタグは正確に保持してください。製品名／プロバイダー名／モデル名、
  プロトコル名とヘッダー名、コマンド、コード／JSON 識別子、URL、環境変数、または
  `OmniRoute`、`OAuth`、`MCP`、`A2A` などの保護用語は翻訳しないでください。現在のソースリストは
  `scripts/i18n/glossary/protected-terms.json` です。

**重点ループ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI の文字列／カタログを変更した場合
npm run lint
```

これは既存システム向けのガイダンスであり、そのツール群やキーモデルの拡張を促すものではありません。
代替システムが設計されている間、i18n のパッチは必要最小限にしてください。タスクで生成翻訳が明示的に必要とされ、
かつ生成された差分をレビューできる場合を除き、外部サービスを呼び出す翻訳コマンドを実行しないでください。

### CLI

**コントラクト**

- `bin/cli/` 内の公開コマンドとフラグ、生成された API コマンド、終了コード、stdout/stderr および
  JSON 出力形式、設定/環境の動作、パッケージに含まれるファイル。
- CLI のユーザー向け文字列には CLI の i18n レイヤーを使用し、`en`/`pt-BR` カタログの整合性を維持する必要があります。
- Node をサポート対象のランタイムとして維持し、公開済みバイナリの契約を保持してください。

**重点確認ループ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 生成/バンドルされた CLI の変更
npm run check:pack-policy     # パッケージ公開範囲の変更
npm run lint
```

動作が解析、ファイル、または終了ステータスに依存する場合は、一時データディレクトリ内で正確なコマンドを使用してください。
CI では、より広範なパッケージ成果物とエコシステムのチェックが実行されます。

### データベース

**契約**

- `src/lib/db/` 配下のドメインモジュール。特定のモジュールを直接インポートしてください（旧 `localDb.ts` 再エクスポートレイヤーは削除済みです）。
- `src/lib/db/migrations/` 配下の番号付きで冪等な SQL マイグレーション、トランザクションの安全性、アップグレード時の
  動作、インデックス、およびスキーマの影響を受けるすべての呼び出し元。
- ルートとハンドラーから生の SQL を直接発行してはいけません。

**重点確認ループ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

マイグレーションを追加する際は、新規データベースと以前のスキーマからのアップグレードの両方をテストしてください。データベーステストでは、
クリーンアップ中にハンドルを閉じ、`resetDbInstance()` を呼び出す必要があります。ベストエフォートの Bun アダプターパスが変更された場合に限り
`npm run test:bun:db` を実行してください。引き続き Node を正式な基準とします。

### ビルド / デプロイ

**契約**

- ルートおよびワークスペースのマニフェスト/ロックファイル、`scripts/build/`、Next.js のスタンドアロンアセンブリ、`dist/`
  パッケージの内容、Electron のプラットフォームメタデータ、CI ワークフロー、およびデプロイ用センチネル。
- サポート対象の Node バージョン範囲と、`CLAUDE.md` で許可リストに登録された Bun の使用を維持する必要があります。
- ビルド成果物は追跡対象外のままとし、依存関係、ライセンス、ワークフロー、およびパッケージのポリシーが適用されます。

**重点確認ループ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 依存関係またはロックファイルの変更
npm run check:pack-policy      # 公開パッケージ範囲の変更
npm run lint
```

変更がコンパイル、スタンドアロンアセンブリ、アセット、またはランタイムバンドルに影響する場合に限り、ローカルで `npm run build` を使用してください。
`npm run build:release` は、リリース/デプロイの検証にのみ使用してください。CI のビルドが
最終的なクロスプラットフォーム判定となります。プラットフォーム固有の Electron の変更には、対応する重点ビルドまたはスモークテストの証跡が必要です。

## 共有マシン向け開発者用スクリプト

2 つの `scripts/dev/` ヘルパーは、他のセッションも稼働している devbox 上でのローカルな開発ループを実装しています。

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD のファイル
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # 指定したファイルのみ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # 分離された worktree。並列実行しても安全
```

- `typecheck-touched.sh` は、一時的な `tsconfig.touched.tmp.json`（`extends ./tsconfig.json`、`types: ["node"]`、`noEmit`、`incremental: false`）を使用し、6 GB のヒープで変更された `.ts/.tsx` ファイルのみを型チェックします。そのため、負荷の高いマシンで OOM になるプロジェクト全体の `tsc -p tsconfig.json` の代わりに使用できます。変更されたファイル内のエラーと 1 行のサマリーを出力し、変更されたファイルにエラーがある場合は `1`、エラーがインポート先のファイルにのみ存在する場合、または診断情報を出力せずに tsc が終了した場合は `2`（表示された `_artifacts/typecheck-touched/` 配下のログを確認してください）、問題がない場合は `0` で終了します。一時 tsconfig は必ず削除されます。コミットしないでください。
- `new-worktree.sh` は、`<git-common-dir>/omniroute-new-worktree.lock` を使用して同時実行を直列化します（デフォルトでは最大 600 秒待機し、その間はメッセージを表示します。変更方法はスクリプトのヘッダーに記載されています）。また、worktree が作成される前に `git worktree add` が失敗した場合は、作成したブランチをロールバックするため、再試行前に手動で `git branch -D` を実行する必要はありません。ハードリンクされた `node_modules` と `.husky/_` のコピーに変更はありません。

## ローカル候補版ループ

ソーステストだけでは、パッケージ化された成果物が起動することを証明できません。パッケージング対象の一覧、削減された依存関係、ネイティブバイナリに関する問題は、tarball をインストールして起動した時点で初めて判明します。`npm run dev:candidate`（`scripts/dev/candidate.mjs`）は、RFC #8084 の「一度ビルド / 検証 / 昇格」フローをローカルで実行するためのものです。候補版を一度ビルドし、その正確な成果物を検証し、ディレクトリ名の変更によって昇格させ、昇格先スロットのヘルスチェックが失敗した場合はロールバックします。

```bash
npm run dev:candidate -- run --dry-run --json  # 計画を出力し、何も変更しない
npm run dev:candidate -- run                   # ビルド + 検証 + 昇格、自動ロールバック
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ へのインストール
npm run dev:candidate -- validate --id <id>    # 空いているポートで起動し、/api/health + /v1/models を確認
npm run dev:candidate -- promote --id <id>     # <id> → current、current → previous
npm run dev:candidate -- rollback              # current と previous を入れ替える
npm run dev:candidate -- run --from-tarball <file.tgz>  # 別の場所（CI）でビルドした tarball を再利用
```

- **一度だけビルドします。** `build` は現在のツリーをパッケージ化するか（`dist/server.js` が必要なため、先に `npm run build:release` を実行してください）、`--from-tarball` で指定されたファイルをコピーし、その後 tarball を分離された npm prefix にインストールします。これは tarball に `node_modules` が含まれていないためです。id は短縮された `HEAD` sha（ツリーにローカルな変更がある場合は `-dirty` 付き）、tarball の場合は `tgz-<sha256>` です。すでにビルド済みのクリーンな id は、再ビルドせずに再利用されます。再ビルドするには `--force` を指定してください。
- **ソースではなくパッケージを検証します。** `validate` は、インストールされた CLI（`serve --port <free port>`）を、新しい `DATA_DIR=<candidate>/data`、ダミーのシークレット、および環境からオペレーターの `OMNIROUTE_API_KEY`、`STORAGE_ENCRYPTION_KEY`、`INITIAL_PASSWORD` を除外した状態で起動し、新規インストール時のキーなしループバック構成を確認します。`GET /api/health` が 200 を返すまで待機し、`GET /v1/models` が 200 を返すことを必須条件として、プロセスグループを停止し、判定結果を tarball のハッシュとともに `validation.json` に記録します。
- **同じ成果物を昇格させます。** `promote` は、現在の tarball ハッシュに対する検証に合格していない候補版の昇格を拒否します。デフォルトのアクティブスロットは `_artifacts/candidate/current` です。`--target <dir>` を指定すると同じファイルシステム上の別のディレクトリが選択され、その previous スロットは `<dir>.previous` になります。各名前変更はアトミックに行われ、途中で失敗した場合は、それまでに実行済みの名前変更を元に戻します。
- **ロールバックします。** `run` は昇格後のスロットを再度検証し、そのチェックが失敗した場合は `current` と `previous` を元に戻します。最初の検証に失敗した候補版が昇格されることはありません。

すべてのファイルは gitignore 対象の `_artifacts/candidate/` 配下に書き込まれます。既存の OmniRoute インストールとそのデータディレクトリには一切触れません。昇格された CLI は `_artifacts/candidate/current/prefix/bin/omniroute` にあります。使用する際は、独自の `DATA_DIR` を指定して起動してください。終了コード：成功は `0`、検証または昇格の失敗は `1`、使用方法の誤りまたはビルドの欠落は `2` です。

## ローカルループと CI の比較

| 各パッチでローカル実行する項目                                         | CI が提供する広範なシグナル                                            |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 上記の直接的な動作テストとカテゴリゲート                               | シャーディングされた完全なユニットテストスイートとシリアルテスト       |
| `npm run lint`                                                         | Vitest スイートとカバレッジ／品質のラチェット                          |
| 影響を受けるコントラクトで必要な場合にのみ型チェックまたはビルドを実行 | 本番ビルド、セキュリティ、ドキュメント、依存関係、PR ポリシーのゲート  |
| 自動化で動作を検証できない場合にのみ手動操作／ライブチェックを実行     | ワークフローで構成されたジョブ間統合チェックとプラットフォームチェック |

対象を絞ったローカルループが成功することは、変更されたコントラクトに関する根拠にはなりますが、無関係な CI チェックが
成功することの証明にはなりません。一方で、ローカルで編集するたびにリポジトリ全体のマトリクスの完了を待つ必要もありません。

## 調整チェックリスト

レビューを依頼する前に、以下を確認してください。

- PR のベースが、引き続きアクティブな `release/v*` ブランチのうち最上位であることを確認する。
- そのベースをフェッチし、ブランチ作成後に追加されたコミットを確認する。
- `git diff <active-base>...HEAD` を確認し、意図しない変更や生成物による差分がないかを確認する。
- カタログおよび生成ドキュメントの競合は、ソースを更新して出力を再生成することで解決する。
- 調整後、PR の説明に記載した対象テスト／ゲートをすべて再実行する。
- 移動したベースに合わせるためだけに、アサーションを弱めたり、必須テストを削除したりしない。

[ブランチおよびリリースモデル](BRANCHING_MODEL.md)を参照してください。CI の完全な一覧については、
[品質ゲートリファレンス](../architecture/QUALITY_GATES.md)を参照してください。
