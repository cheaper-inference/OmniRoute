このドキュメントでは、OmniRoute を Fly.io に実際にデプロイする手順について、以下のシナリオを説明します。

- 現在のプロジェクトを初めて Fly.io にデプロイする
- 以降のコード更新を公開する
- 新しいプロジェクトで同じデプロイワークフローを使用する

このガイドは、現在のプロジェクトで動作確認済みの設定に基づいています。アプリケーション名は `omniroute` です。

---

## 1. デプロイの目標

- プラットフォーム: Fly.io
- デプロイ方法: ローカルの `flyctl` から直接公開
- ランタイム: リポジトリ内の既存の `Dockerfile` と `fly.toml` を使用
- データの永続化: `/data` にマウントされた Fly Volume
- アクセス URL: `https://omniroute.fly.dev/`

---

## 2. 現在のプロジェクトの主要設定

現在のリポジトリにある `fly.toml` に、以下の主要項目が含まれていることを確認済みです。

```toml
app = 'omniroute'
primary_region = 'sin'

[[mounts]]
  source = 'data'
  destination = '/data'

[processes]
  app = 'node run-standalone.mjs'

[http_service]
  internal_port = 20128

[env]
  TZ = "Asia/Shanghai"
  HOST = "0.0.0.0"
  HOSTNAME = "0.0.0.0"
  BIND = "0.0.0.0"
```

注意事項:

- `app = 'omniroute'` は、デプロイ対象となる Fly アプリケーションを指定します
- `destination = '/data'` は、永続ボリュームのマウント先ディレクトリを指定します
- このプロジェクトでは `DATA_DIR=/data` を設定する必要があります。設定しない場合、データベースとキーはコンテナの一時ディレクトリに書き込まれます

## 3. 前提条件

### 3.1 Fly CLI のインストール

Windows PowerShell:

```powershell
pwsh -Command "iwr https://fly.io/install.ps1 -useb | iex"
```

環境によってインストールスクリプトが失敗する場合は、`flyctl` バイナリを手動でダウンロードし、`PATH` に追加することもできます。

### 3.2 Fly アカウントへのログイン

```powershell
flyctl auth login
```

### 3.3 ログイン状態の確認

```powershell
flyctl auth whoami
flyctl version
```

## 4. 現在のプロジェクトを初めてデプロイする

### 4.1 コードをクローンしてディレクトリに移動する

```powershell
git clone https://github.com/diegosouzapw/OmniRoute.git
cd OmniRoute
```

### 4.2 アプリケーション名を確認する

`fly.toml` を開き、以下の行を確認します。

```toml
app = 'omniroute'
```

独自の新しいアプリケーションにデプロイする場合は、グローバルに一意な名前へ変更できます。例:

```toml
app = 'omniroute-yourname'
```

注意:

- コンソールに表示されるアプリケーションが、`fly.toml` の `app` の値と一致していることを確認してください
- 以前に `oroute` など別の名前を使用していた場合は、`omniroute` と混同しないでください

### 4.3 アプリケーションを作成する

アプリケーションがまだ存在しない場合:

```powershell
flyctl apps create omniroute
```

アプリケーション名を変更した場合は、`omniroute` を選択した名前に置き換えてください。

### 4.4 初回デプロイ

```powershell
flyctl deploy
```

## 5. 必須パラメータ

このプロジェクトでは、Fly.io で少なくとも次のパラメーターを構成することをお勧めします。

### 5.1 検証済みパラメータ

これらのパラメータは、現在の`omniroute`アプリケーションの実際のデプロイメントで使用されています。

- `API_KEY_SECRET`
- `DATA_DIR`
- `JWT_SECRET`
- `MACHINE_ID_SALT`
- `NEXT_PUBLIC_BASE_URL`
- `OMNIROUTE_WS_BRIDGE_SECRET` ( WebSocketブリッジ認証に使用される本番環境の—で必要)
- `STORAGE_ENCRYPTION_KEY`

### 5.2 `INITIAL_PASSWORD`について

The current project does not set `INITIAL_PASSWORD` because this deployment does not require it.

設定されていない場合:

- 最初の訪問時にオンボーディング ウィザードでダッシュボードのパスワードを作成します。パスワード手順を完了します。これをスキップすると、ダッシュボードへのログインがオフになり、アプリURLにアクセスできるすべてのユーザーがダッシュボードを利用できるようになります。
- Fly のプロキシは非ループバック アドレスからアプリに到達するため、パスワードを送信すると、ウィザードはワンタイム ブートストラップ トークンを要求します。その時点でアプリはそのトークンをログに出力します: `flyctl logs --no-tail -a omniroute | Select-String BOOTSTRAP`。その行がログからスクロールアウトされている場合は、アプリを再起動し、ウィザードを再度実行して新しいトークンを出力します。

代わりにパスワードを無人で設定するには、最初のダッシュボードにアクセスする前にパスワードを追加します (パスワードが保存されると、 `INITIAL_PASSWORD`は無視されます)。

- `INITIAL_PASSWORD`

## 6. 推奨パラメータ

### 6.1 シークレットの設定

Fly Secrets には、以下の変数を設定することを推奨します。

| 変数                         | 推奨度           | 説明                                             |
| ---------------------------- | ---------------- | ------------------------------------------------ |
| `API_KEY_SECRET`             | 必須             | API キーの生成と検証に使用                       |
| `JWT_SECRET`                 | 必須             | ログインセッションと JWT 署名に使用              |
| `OMNIROUTE_WS_BRIDGE_SECRET` | 本番環境では必須 | WebSocket ブリッジの認証シークレット             |
| `STORAGE_ENCRYPTION_KEY`     | 強く推奨         | 保存されている機密性の高い接続情報を暗号化       |
| `MACHINE_ID_SALT`            | 推奨             | 安定したマシン識別子を生成                       |
| `INITIAL_PASSWORD`           | 任意             | 初回デプロイ時の初期バックエンドパスワードを設定 |
| OAuth/API の非公開認証情報   | 必要に応じて     | 外部プラットフォームの認証設定                   |

### 6.2 現在のプロジェクトの推奨値

| 変数                   | 推奨値                      |
| ---------------------- | --------------------------- |
| `DATA_DIR`             | `/data`                     |
| `NEXT_PUBLIC_BASE_URL` | `https://omniroute.fly.dev` |

注意事項:

- `DATA_DIR=/data` は非常に重要であり、Fly Volume のマウントポイントと一致している必要があります
- `NEXT_PUBLIC_BASE_URL` は、スケジューラー、フロントエンドのコールバック、および同様の用途で使用されます

### 6.3 OAuth コールバック URL の設定

Fly.io へのデプロイで OAuth ベースのプロバイダー（例: Antigravity、Gemini、Cursor）を有効にする必要がある場合は、以下の 2 点を確認してください。

1. **`NEXT_PUBLIC_BASE_URL` を公開 HTTPS ドメインに設定する**

   ```powershell
   flyctl secrets set NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev -a omniroute
   ```

   カスタムドメインを使用している場合は、対応するドメイン（例: `https://omniroute.yourdomain.com`）に置き換えてください。

2. **プロバイダーのコンソールでコールバック URL を設定する**

   すべての OAuth プロバイダーは、単一のコールバックパス `/callback` を共有します。プロバイダーごとのコールバックルートはありません。

   ```text
   <NEXT_PUBLIC_BASE_URL>/callback
   ```

   たとえば、Gemini、Antigravity、Cursor、GitLab Duo のいずれでも、以下を使用します。
   - `https://omniroute.fly.dev/callback`

   `NEXT_PUBLIC_BASE_URL` がプロバイダーに登録されたコールバック URL と一致しない場合、OAuth フローはブラウザのリダイレクト手順で失敗します。

## 7. 1 コマンドでのシークレット設定

以下のコマンドは、安全なランダム値を生成し、現在のプロジェクトに必要なすべてのパラメータを 1 回の操作で Fly Secrets に書き込みます。

注意事項:

- `INITIAL_PASSWORD` は含まれません
- 現在のプロジェクト `omniroute` を対象としています

```powershell
$apiKeySecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$jwtSecret = [Convert]::ToHexString((1..64 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$machineIdSalt = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$storageKey = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$wsBridgeSecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()

flyctl secrets set `
  API_KEY_SECRET=$apiKeySecret `
  JWT_SECRET=$jwtSecret `
  MACHINE_ID_SALT=$machineIdSalt `
  STORAGE_ENCRYPTION_KEY=$storageKey `
  OMNIROUTE_WS_BRIDGE_SECRET=$wsBridgeSecret `
  DATA_DIR=/data `
  NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev `
  -a omniroute
```

Linux / macOS では、`openssl rand -hex 32` も使用できます。

```bash
flyctl secrets set OMNIROUTE_WS_BRIDGE_SECRET=$(openssl rand -hex 32) -a omniroute
```

注意事項:

- `OMNIROUTE_WS_BRIDGE_SECRET` は本番環境では必須です。設定されていない場合、WebSocket ブリッジのハンドシェイクが失敗します

初期パスワードも設定する場合:

```powershell
flyctl secrets set INITIAL_PASSWORD=your-strong-password -a omniroute
```

## 9. その後のアップデートとリリース

コードを更新した後のリリース プロセスは簡単です。

```powershell
git pull
flyctl deploy
```

コードを変更せずにパラメータのみを更新する必要がある場合は、次のようにします。

```powershell
flyctl secrets set KEY=value -a omniroute
```

Fly はマシンのローリング アップデートを自動的に実行します。

### 9.1 フォークの`fly.toml`を保持しながら上流リポジトリの更新を追跡する

現在のリポジトリがフォークであり、上流の`https://github.com/cheaper-inference/OmniRoute`から更新を同期したい場合は、以下のワークフローに従います。

まず、リモコンを確認します。

```powershell
git remote -v
```

少なくとも次のものが表示されるはずです。

- `origin`自分のフォークを指している
- `upstream`元のリポジトリを指します

`upstream`が構成されていない場合は、追加します。

```powershell
git remote add upstream https://github.com/cheaper-inference/OmniRoute.git
```

アップストリームと同期する前に、最新のコミットとタグをフェッチします。

```powershell
git fetch upstream --tags
```

現在のバージョンとアップストリームのタグを確認します。

```powershell
git describe --tags --always
git show --no-patch --oneline v3.4.7
```

> 注: 現在のプロジェクトのバージョンは`v3.8.0`です。以下の`v3.4.7`参照は、歴史的な例としてのみ保持されています。実際のリリースの場合は、 `:latest`または現在のバージョン タグ (例: `:v3.8.0`) を使用します。

フォークの`fly.toml`強制的に保持しながら、最新のアップストリーム`main`をマージする場合は、次のワークフローに従います。

```powershell
git merge upstream/main
git checkout HEAD~1 -- fly.toml
git add -- fly.toml
git commit -m "chore(deploy): keep fork fly.toml"
git push origin main
```

注:

- `git merge upstream/main`元のリポジトリから最新のコードを同期します
- `git checkout HEAD~1 -- fly.toml`マージ前からフォーク自身の`fly.toml`を復元します。
- アップストリームが`fly.toml`変更しなかった場合、このステップでは違いは生じません。
- アップストリームが`fly.toml`変更した場合、この手順により、Fly アプリケーション名、ボリューム マウント、リージョン、およびその他のフォーク固有のデプロイメント構成が上書きされないことが保証されます。

特定のリリース タグ (例: `v3.4.7`) に合わせたい場合は、まずそのタグが既に`upstream/main`に含まれていることを確認します。

```powershell
git merge-base --is-ancestor v3.4.7 upstream/main
```

正常に返されたということは、 `upstream/main`そのバージョンがすでに含まれていることを意味します。 `upstream/main`をマージするだけです。

### 9.2 アップストリーム同期後の標準リリース シーケンス

元のリポジトリと同期した後、次の推奨リリース順序に従ってください。

1. `git fetch upstream --tags`
2. `git merge upstream/main`
3. フォークの`fly.toml`を復元する
4. `git push origin main`
5. `flyctl deploy`
6. `flyctl status -a omniroute`
7. `flyctl logs --no-tail -a omniroute`

これは、現在のプロジェクトを`v3.4.7`にアップグレードするときに使用される実際のワークフローです (この例では過去のバージョンを参照しています。現在の実際のバージョンは`v3.8.0`です)。

try {

## 11. 成功を示す指標

デプロイが成功すると、ログには次のような内容が表示されます。

```text
[bootstrap] Secrets persisted to: /data/server.env
[DB] SQLite database ready: /data/storage.sqlite
```

次の2点が重要です。

- `/data/server.env` は、実行時のシークレットが永続ボリュームに書き込まれていることを示します
- `/data/storage.sqlite` は、データベースが永続ボリュームに書き込まれていることを示します

代わりに `/app/data/...` が表示される場合は、`DATA_DIR` の設定に誤りがあるため、直ちに修正する必要があります。

## 12. 一般的な問題

### 12.1 `Secrets`ページが空です

通常、次の 2 つの理由が考えられます。

- まだ`flyctl secrets set`を実行していません
- 別のアプリケーションを表示しています (例: `omniroute`ではなく`oroute` )

### 12.2 `flyctl deploy`レポート`app not found`

まずアプリケーションを作成します。

```powershell
flyctl apps create omniroute
```

### 12.3 `fly.toml`解析が失敗する

次のことを確認してください。

- コメント文字化けの有無
- TOML引用とインデントが正しいかどうか

### 12.4 データが永続化されない

次の両方を確認します。

- `fly.toml` `destination = '/data'`が含まれます
- `DATA_DIR`は`/data`に設定されます

### 12.5 `INITIAL_PASSWORD`なしで実行できますか?

はい。 `INITIAL_PASSWORD`設定されていない場合、最初の訪問時にオンボーディング ウィザードでダッシュボードのパスワードを作成します (セクション 5.2 では、ワンタイム ブートストラップ トークンとパスワードの手順について説明します)。

---

## 13. 新しいプロジェクトでの再利用

このドキュメントに従って新しいプロジェクトをデプロイする場合は、次の項目のみを変更する必要があります。

1. `fly.toml` の `app` の値を変更する
2. `NEXT_PUBLIC_BASE_URL` を変更する
3. `DATA_DIR=/data` はそのまま維持する
4. `API_KEY_SECRET`、`JWT_SECRET`、`MACHINE_ID_SALT`、`STORAGE_ENCRYPTION_KEY` を再生成する
5. 初回デプロイ後、ログが `/data` に書き込まれていることを確認する

以前のプロジェクトのキーを再利用しないでください。

## 14. 現在のプロジェクト向け最小リリースチェックリスト

以降のリリースで最もよく使用するコマンドは次のとおりです。

```powershell
flyctl auth whoami
flyctl status -a omniroute
flyctl secrets list -a omniroute
flyctl deploy
flyctl logs --no-tail -a omniroute
```

通常のリリースでは、中心となるコマンドは次の1つだけです。

```powershell
flyctl deploy
```

新しい環境への初回デプロイでは、主な手順は次のとおりです。

1. `flyctl auth login`
2. `flyctl apps create omniroute`
3. `flyctl secrets set ... -a omniroute`
4. `flyctl deploy`
5. `flyctl logs --no-tail -a omniroute`
