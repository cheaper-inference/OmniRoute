Web Cookie プロバイダーを使用すると、API キーの代わりに既存のブラウザーセッションを通じて、OmniRoute から AI サービスを利用できます。Web サイト経由ですでにサービスへアクセスでき、同じ認証済みセッションを OmniRoute でも使用したい場合に便利です。

API キープロバイダーとは異なり、Web Cookie プロバイダーは、ブラウザーから Web サイトに送信される認証情報を使用して認証します。

---

# はじめる前に

> **重要:** 認証情報は必ずブラウザーの Cookie ストレージではなく、**実際に行われたネットワークリクエスト**からコピーしてください。

認証に関する問題の多くは、誤った場所から Cookie をコピーすることで発生します。

## Cookie ストレージからコピーしないでください

ほとんどのブラウザーでは、保存されている Cookie を次の場所で確認できます。

```
DevTools
→ Application（または Storage）
→ Cookies
```

これらの Cookie は正しいように見えても、次のような可能性があります。

- 古くなっている
- 不完全である
- 認証済みリクエストでのみ送信される Cookie が含まれていない

これらの値を使用すると、有効に見える場合でも認証に失敗する可能性があります。

## 実際に行われたリクエストからコピーする

代わりに、成功したリクエストの Cookie を使用してください。

```
DevTools
→ Network
→ ページを更新
→ チャットまたは会話のリクエストを開く
→ Request Headers
→ Cookie
```

`Cookie` リクエストヘッダーには、ブラウザーが正常に使用した正確な認証情報が含まれています。

ほとんどの Web Cookie プロバイダーでは、この値を OmniRoute に貼り付けます。

---

# 一般的なセットアップ

セットアップ手順は、ほとんどの Web Cookie プロバイダーで共通です。

1. プロバイダーの Web サイトにサインインします。
2. ブラウザーの開発者ツールを開きます。
3. **Network** タブを開きます。
4. ページを更新します。
5. 認証済みのチャットまたは会話のリクエストを開きます。
6. 必要な認証情報をコピーします。
7. OmniRoute を開きます。
8. **Providers → Add Provider** に移動します。
9. 使用する Web Cookie プロバイダーを選択します。
10. 認証情報を貼り付けます。
11. **Test Connection** をクリックします。
12. プロバイダーを保存します。

必要な認証情報はプロバイダーによって異なります。

---

# プロバイダーの認証情報形式

認証情報の保存方法は Web サイトごとに異なります。Cookie のみを必要とするものもあれば、追加のヘッダーやトークンを必要とするものもあります。

| プロバイダー                    | 認証情報の形式                   | プロバイダーガイド               |
| ------------------------------- | -------------------------------- | -------------------------------- |
| Claude Web                      | 完全な Cookie リクエストヘッダー | `docs/providers/CLAUDE_WEB.md`   |
| ChatGPT Web (Codex)             | 完全な Cookie ヘッダー           | `docs/providers/CHATGPT_WEB.md`  |
| Gemini Web                      | _(要確認)_                       |                                  |
| Copilot Web                     | _(要確認)_                       | `docs/providers/COPILOT-M365.md` |
| Microsoft 365 Copilot (BizChat) | WS access_token + chathubPath    | `docs/providers/COPILOT-M365.md` |
| Grok Web                        | _(要確認)_                       |                                  |
| ...                             | ...                              | ...                              |

> 新しい Web Cookie プロバイダーが追加された場合や、既存プロバイダーの認証要件が変更された場合は、この表を更新してください。

## NoTrack (notrack-web)

NoTrack（[notrack.ai](https://notrack.ai)）は、登録不要で無料の一般ユーザー向けチャットプラットフォームです。初回訪問時に匿名でセッションが作成され、`uid`、`si_usr_id`、`si_ses_id` の3つのCookieによって維持されます。OmniRouteは、単一のモデルID（`notrack-c`、エイリアスは `ntw`）を通じて、同じ `/api/dispatch` エンドポイントをプロキシします。

### 接続手順

1. ブラウザーで [notrack.ai](https://notrack.ai) を開き、匿名セッションCookieが設定されるまで待ちます。
2. **開発者ツール → ネットワーク**を開き、ページを更新して、いずれかの `/api` リクエストをクリックします。
3. **リクエストヘッダー**で、`Cookie` ヘッダーの値全体をコピーします。
4. OmniRouteで、**プロバイダー → プロバイダーを追加 → NoTrack Web（無料）**に移動します。
5. Cookie文字列を `apiKey` フィールドに貼り付けて、**保存**します。

OmniRouteは、貼り付けられた文字列から `uid`、`si_usr_id`、`si_ses_id` を抽出し、それらのペアのみを含むクリーンな `Cookie` ヘッダーを再構築します。さらに、ログイン済みアカウントに設定される `nt_session`（`ntk_…` トークン）が存在する場合は、それも追加されます。3つのうちいずれかが欠けている場合は、運用担当者が別の形式を試せるように、貼り付けられた未加工の文字列が変更されずに転送されます。

### モデルID

| モデルID    | 表示名    | 注記                                                                     |
| ----------- | --------- | ------------------------------------------------------------------------ |
| `notrack-c` | NoTrack C | デフォルト — アップストリームのディスパッチモデル `C`。                  |
| `C`         | NoTrack C | `notrack-c` のエイリアス（アップストリームの未加工ディスパッチコード）。 |
| `notrack`   | NoTrack C | `notrack-c` のエイリアス。                                               |
| `ntw`       | NoTrack C | `notrack-c` の短縮エイリアス。                                           |

4つのモデルIDはすべて、同じアップストリームのディスパッチモデル（`C`）に対応します。

### リクエストオプション

実行機構は、リクエスト本文で次のオプションフィールドを受け付けます。

| 本文フィールド        | デフォルト | 用途                                                                                  |
| --------------------- | ---------- | ------------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`    | ディスパッチモード（自由形式の文字列。アップストリームは `usual` などを受け付けます） |
| `notrack_max_turns`   | `6`        | 回答前にアップストリームが実行できる内部ターン数。                                    |
| `notrack_chat_id`     | `null`     | 既存のアップストリームチャットを再開します（新しいチャットでは省略します）。          |
| `notrack_attachments` | `[]`       | アップストリームの添付ファイル記述子の配列をそのまま渡します。                        |
| `notrack_regenerate`  | `false`    | 前のターンに対する回答の再生成を要求するには、`true` に設定します。                   |

### 機能

- **ストリーミングおよび非ストリーミング**のチャット補完。
- **ツール呼び出し** — リクエストに `tools: [...]` を設定します。実行機構はこれらをツール呼び出しエンベロープの規約にシリアライズし、モデルの応答を解析してOpenAIの `tool_calls` に戻します。
- **`response_format`** — `json_object` と `json_schema` がサポートされています。実行機構はモデルの応答から最初のJSONオブジェクトを抽出し、文字列化してから返します。
- **推論ヒント** — アップストリームが `thinking` イベントを送信すると、実行機構は `reasoning` デルタを出力します。

### 制限事項

- アップストリームでは匿名利用のクォータが適用されます。上限に達すると、実行機構は分かりやすいメッセージとともに429を返します。
- すべてのモデルIDは同じアップストリームのディスパッチモデルに解決され、モデルごとの切り替えはありません。
- 実行機構はアップストリームの `/api/chats` エンドポイントを呼び出さないため、チャット履歴やセッションは自動管理されません。既存のアップストリームチャットを再開するには、`notrack_chat_id` を使用してください。

# Web Cookieプロバイダーでできることとできないこと

Web Cookieプロバイダーは、Webサイトのチャットインターフェースを再利用します。公式APIと同じ機能を提供するものでは**ありません**。

## サポート対象

- 既存のブラウザーセッションを使用した認証
- アカウントで利用可能なモデルへのアクセス
- チャット応答のストリーミング
- API キー不要

## サポート対象外

- 関数呼び出し
- ツール呼び出し
- ファイルの自動編集
- エージェント型 IDE ワークフロー
- API 専用機能

これは想定された動作であり、**バグではありません**。

ツールの実行、ファイルの自動編集、またはその他のエージェントワークフローが必要な場合は、Web Cookie プロバイダーではなく、**API キープロバイダー**を使用してください。

# 検証に関する注意事項

**Test Connection** または Cookie の検証が成功しても、提供された認証情報が想定された形式であることが確認されるだけです。

Issue #7857 が解決されるまでは、検証に成功しても、プロバイダーの認証が成功することは**保証されません**。

それでも認証に失敗する場合は、ブラウザーの Cookie ストレージではなく、実際のネットワークリクエストから認証情報をコピーしたことを確認してください。

---

# トラブルシューティング

## 認証に失敗する

認証情報が次の場所からコピーされたことを確認してください。

```
Network
→ Request Headers
→ Cookie
```

次の場所からはコピー**しないでください**。

```
Application
→ Cookies
```

---

## ブラウザーでは Cookie が機能するが OmniRoute では機能しない

プロバイダーによっては、認証済みリクエスト時にのみ送信される Cookie が含まれています。

会話を正常に開いた後、新しいネットワークリクエストから認証情報を再度コピーしてください。

---

## セッションの有効期限切れ

Web Cookie プロバイダーは、既存のブラウザーセッションを使用します。

ブラウザーセッションの有効期限が切れた場合、またはサインアウトした場合は、新しい認証情報一式をコピーする必要があります。サポートされている Web プロバイダーの Cookie 更新を自動化するには、コンパニオンツールの [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md) を参照してください。

---

## Test Connection は成功するがリクエストに失敗する

Issue #7857 が解決されるまでは、検証に成功しても、認証リクエストが成功することは保証されません。

さらにトラブルシューティングを進める前に、新しい認証済みリクエストから認証情報を再度コピーしてください。

---

## ChatGPT Web で "Unsupported ChatGPT integrity dependency" エラーが発生する

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

認証情報に問題はありません。このエラーはセッションではなくブリッジに起因します。chatgpt.com はデプロイごとにモジュール ID を割り当てますが、ブリッジはインスタンス化する Sentinel ヘルパーの ID を固定していたため、ヘルパー名が変更される chatgpt.com の再ビルドが行われると、Cookie が有効なままでもすべてのターンが機能しなくなっていました。接続を再認証しても解決できません。

ページ独自のランタイムを通じてモジュールを解決するビルドでは、ID が固定されないため、この問題は発生しません。このエラーが表示された場合は、OmniRoute をアップグレードし、接続チェックを再実行してください。

# ベストプラクティス

- 新しい認証済みリクエストから認証情報をコピーしてください。
- 古い Cookie の再利用は避けてください。
- Web Cookie プロバイダーの使用中は、ブラウザーセッションをアクティブな状態に保ってください。
- コピーした Cookie は機密性の高い認証情報として扱ってください。
- 関数呼び出しやエージェントワークフローが必要な場合は、API キープロバイダーを使用してください。
