## 概要

クォータ共有エンジンは、同じ接続を共有する複数のAPIキー間で、プロバイダーの時間ベースのクォータ（例: Codexの
5時間ウィンドウ、Kimiの1500 req/h）を公平に分配します。

**解決する問題:** OmniRouteは、同じアップストリームのプロバイダーアカウントに対して多数のAPIキーをプロキシします。
共有ロジックがなければ、キーAからの突発的なリクエストによって、その時間帯のプロバイダークォータが使い果たされ、
ウィンドウがリセットされるまでキーBとCがブロックされる可能性があります。
このエンジンは、次の方法でこれを防ぎます。

1. 各キーのディメンション別（%、リクエスト数、トークン数、$）ローリング消費量を追跡します。
2. ワークコンサービングな公平配分アルゴリズムを適用します。グローバルプールが飽和していない間、キーは
   アイドル状態の割り当て分から借用できます。
3. リクエストがアップストリームエグゼキューターに到達する前に、ホットパス（`chatCore.ts`）で
   結果を適用します。

## アルゴリズム: フェアシェア作業量節約

`src/lib/quota/fairShare.ts`で実装されます。

### モード

| 状態                                       | モード     | 行動                                                                 |
| ------------------------------------------ | ---------- | -------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **寛大**   | キーはグローバル制限から消費された合計を差し引いた値まで借用できます |
| `globalUsedPercent >= saturationThreshold` | **厳しい** | 個人の公平な配分を厳格に実施する                                     |

デフォルトの`saturationThreshold = 0.5` (環境`QUOTA_SATURATION_THRESHOLD`)。

これら 2 つのモードは、デフォルトの借用モード`saturation`でのプールを記述します。 `consent`モードのプールは、飽和度に関係なく、常に厳密なルールを適用します。[同意された融資 (プールごとのオプトイン)](#consented-lending-per-pool-opt-in)を参照してください。

### 次元ごとの決定

プール内のアクティブなディメンションごとに、エンジンは以下を計算します。

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent`ディメンションの場合、 `consumed`代わりにアトリビューション ブックから取得されます ( [「パーセント ディメンション: キーごとのアトリビューション](#percent-dimensions-per-key-attribution)」を参照)。

それから：

- **`policy = hard`** : `consumed > fairShareAllowed`およびモードが strict →の場合**ブロック**。
- **`policy = soft`** : `consumed > fairShareAllowed`およびモードが strict →の場合**罰する**(コンボの優先順位を下げます。決してハードブロックしないでください)。
- **`policy = burst`** : フェアシェアに関係なく、グローバルヘッドルームが存在する間は許可します。

### 絶対キャップ

割り当ての`capValue` + `capUnit`は、モードやポリシーに依存しないハードシーリングです。 `consumed >= capValue`常に存在する任意の次元**ブロック**リクエスト。 `percent`キャップの場合、 `consumed`キーに帰属する部分のみです。

### 多次元チェック

次の場合、リクエストはブロックされます。**どれでも**プール内の次元がそれをブロックします。ディメンションは独立しています— 5 時間 % の消耗はウィークリー% ディメンションに影響しません。

### 借りる

寛大モードでは、割り当てが過少に消費されているキーは、他のキーの未割り当てシェアからの余剰を使用できます。式は次のとおりです。

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ここで、 `consumedByOtherKeys = consumedTotal - consumedByThisKey`。 teto グローバル (そのディメンションのプール`limit` ) は常にハード天井です。

### 同意された融資 (プールごとのオプトイン)

各プールには借用モードがあります。 `saturation`がデフォルトであり、上記のルールが維持されます。 `consent`モードでは、 `hard`キーは、他のキーが貸与に同意した容量内でのみそのシェアを渡します。管理者は各プールのモードを設定します。各キーホルダーは、[貸出同意](#lending-consent)を通じて独自の同意を設定します。

同意は 0 ～ 100 の割合で表され、オプションでエポックミリ秒単位の期限を指定できます。キーは、期限が将来に迫っている間、そのアイドル状態のシェアのその割合を貸し出します。

1 つのディメンションでは、 `L`が有効な制限です。つまり、プランの制限にプール内のアカウントを掛けたものです。ゲートは、要求元のキーに対して以下を計算します。

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k`はキーの重み、または 0 を超える重みがない場合はすべてのキーの`100 / n`です。 `lend_k`はキーのアクティブな割合であり、期限が過ぎると 0 になります。要求しているキー自身の同意は考慮されません。 `hard`キーは、その消費量がそのシェアに`borrowAvailable`を加えた値に達すると拒否されます。

割り当て要求のない容量 (100 から重みの合計を引いたもの) は貸与できません。鍵を貸すことに同意した人はいませんでした。

**例。** `L`は1000です。

| 鍵  | 重さ | 共有 | 消費された | 貸します |
| --- | ---- | ---- | ---------- | -------- |
| あ  | 50   | 500  | 530        | 0%       |
| B   | 30   | 300  | 100        | 50%      |
| C   | 0    | 0    | 60         | 0%       |

- B は遊休資産 200 の 50% (つまり 100) を貸し出します。C はすでにそのシェアを 60 上回っています。 Aは40を借りることができます。
- A は 530 で提供され、消費が 540 に達すると拒否されます。
- C が何かを使用する前は、A がそのシェア以下であれば、C は 100 を借りることができました。
- C が何かを使用する前、A が 530 の場合、C は 70 を借りることができました。

**重量ゼロ。**重み 0 のキーのシェアは 0 です。キーの使用量が他のキーの貸し出し量を下回っている場合にのみ提供されます。誰も貸してくれない場合は、最初の要求から拒否されます。

**締め切り。**バックグラウンド タスクで同意が期限切れになることはありません。各リクエストは期限とそれ自体の時間を比較し、その時間に等しい期限が経過しています。保存された期限が有限数でない場合、または`Date`保持できる最大の日付を過ぎている場合は、期限を過ぎたものとしてカウントされます。

**`soft`と`burst`。**融資はそれらを制限しません。 `soft`キーは、そのシェアを超えると優先順位が下がります。 `burst`キーは、プールに余裕がある間に渡されます。プールの合計が制限に達すると、プールの天井はすべてのキーを拒否します。

**リクエストパスのコスト。** `saturation`プールは以前と同様に何も読み取りません。 `consent`プールでは、可算ディメンションは、別のキーが貸与されている間、そのシェア以上の`hard`キーに対してのみ他のキーを読み取ります。次に、他のキーごとに 1 つの読み取りを並行して行います。読み取りに失敗した場合、そのキーの消費量は 0 としてカウントされます。アトリビューション ブックがすべてのキーを保持しているため、 `percent`ディメンションでは読み取りが追加されません。

**プールを編集しています。**編集では、キーの同意が維持されます。これは、割り当ての編集、グループ全体の置換、および`ensure`コールにも当てはまります。削除されたキーは同意を失い、再度追加されたキーは 0 から始まります。管理ルートは各キーの同意を返し、決して書き込みません。プールを`saturation`に戻すと、保存されているすべての同意が保持されますが、そのモードでは効果がありません。プールを再度`consent`に切り替えると、期限が過ぎていない保存されている同意が再アクティブ化されます。キー所有者は、どちらのモードでも保存された同意をクリアできます。

**アップグレード中。**列`lending_percent`および`lending_until`すでに存在する場合、移行では`borrow_mode`のみが追加され、保存されたパーセンテージはそのまま残ります。すべてのプールは`saturation`モードで開始します。プール ウィザードでプールごとに`consent`オンにします。保存された値からは何も推測されません。

**制限。**

- 貸し手は、自分のシェアを使用する前に、プールの上限を見つけることができます。他の人が借りた容量は、プールの合計にカウントされます。
- チェックはリクエストの前に実行され、何も予約されません。同時リクエストは消費量が記録される前に読み取られるため、実行中のリクエストに制限されて、貸し出された容量が複数回消費される可能性があります。 `saturation`モードの共有チェックにも同じ特性があります。

## スライディングウィンドウカウンター

`src/lib/quota/sqliteQuotaStore.ts` および `redisQuotaStore.ts` に実装されています。

`(apiKeyId, dimensionKey)` ごとに2つのバケットがあります。

- `curr`: 現在のバケット（`floor(nowMs / windowMs)`）
- `prev`: 直前のバケット（`curr - 1`）

実効ローリング値:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**精度**: 約99%の精度です。誤差は、バケット間の境界においてウィンドウサイズの最大1%です
（2バケット近似に固有の誤差）。

### 同時実行制御

SQLiteドライバー: `(apiKeyId | dimensionKey)` キーごとのインメモリミューテックスにより、
読み取り・変更・書き込みの競合を防止します。このパターンは、`src/sse/services/auth.ts` のアンチ・サンダリングハード対策を踏襲しています。

Redisドライバー: アトミックなインクリメントにはLua EVALスクリプトを使用します。単一のRedisコマンドとして実行されます。

## ドライバー

### SQLite（デフォルト、インストール不要）

- テーブル: `quota_consumption`（マイグレーション `073_quota_pools.sql` / `074_quota_consumption.sql` を参照）。
- 単一インスタンスのデプロイに最適です。
- すべての永続化データは、既存の OmniRoute SQLite DB（`DATA_DIR/storage.sqlite`）に保存されます。

### Redis（任意、複数インスタンス）

- `ioredis` npm パッケージが必要です。
- カウンターは Redis に保存されます。メタデータ（プール／割り当て）は引き続き SQLite に保存されます。
- カウンターを共有する必要がある複数レプリカのデプロイに最適です。

### ドライバーの切り替え

設定 UI（`/dashboard/settings` → Quota Store）または環境変数を使用します。

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB 設定は環境変数より優先されます。`driver=redis` であっても URL が指定されていない場合、または
`ioredis` がインストールされていない場合、ファクトリーは SQLite にフォールバックし、警告をログに記録します。

ドライバーの選択順序:

1. DB 設定 `quotaStore.driver`
2. 環境変数 `QUOTA_STORE_DRIVER`
3. デフォルト: `sqlite`

## 多次元

プールには複数のディメンションを含めることができます。各次元は独立しています。

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**例: Codexプラン**(5h% +毎週%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

リクエストは、許可されるすべてのディメンションを満たしている必要があります。

### パーセント ディメンション: キーごとのアトリビューション

パーセント プランでは、アカウントおよびプラン ウィンドウごとに 1 つの使用量の数値がレポートされます。プロバイダーは、 APIキーごとにカウンターを提供しません。

この数字をキー間で分割するために、各プールはアカウントおよびプランウィンドウごとにアトリビューションブックを保持します。 `src/lib/quota/percentLedger.ts`本のルールを保持します。 `src/lib/quota/percentAttribution.ts` 、本を執行機関が使用する番号に変換します。結果は、各キーがルーティングするトークンから構築された推定値です。

#### 本を動かす読書

ブックは、要求されたプラン ウィンドウのプロバイダー独自の図に基づいてのみ移動します。これらの接続は次の 1 つを報告します。

| プロバイダー           | 計画ウィンドウ |
| ---------------------- | -------------- |
| Claude、 OAuth接続経由 | `5h`, `weekly` |
| Codex                  | `5h`, `weekly` |

これらは読み取り値としてカウントされません。

- プロバイダクライアントが古いものとしてマークする応答
- プロバイダーがその割合を報告しなかったClaudeウィンドウ
- 別のウィンドウの数値、または複数のウィンドウにわたる最悪のケース
- レート制限ヘッダーのフォールバック
- 読み取りに失敗しました

APIキーを持つClaudeを含む他のプロバイダーにはブックがありません。この変更前と同様に、各キーのパーセント ディメンションに対して 0 が課金されます。

読み取りは、飽和信号の 30 秒キャッシュを共有します。 Claude読み取り値は、その時間がわかっている場合、その数値が応答ヘッダーで観察されたとき、または使用エンドポイントから読み取られたときによって日付が付けられます。他の読み取り値は、そのキャッシュ エントリが構築されたときの日付が付けられます。

#### 本が保管しているもの

記録された各リクエストは、そのトークンをプール、アカウント、キーごとのカウンターに 1 回追加します。カウンターは増えるばかりです。この本には次の 3 つのことが書かれています。

- ベースライン: 本を開いたとき、または窓が最後に回転したときの図
- 最後に適用された図
- キーごとに、その瞬間のトークンカウンター、そのマークと呼ばれる

このブックは、施行または使用ルートが帰属を計算するときに更新されます。書き込みはリビジョン番号に基づいて比較および設定されます。新規読み取り時に 1 回の再試行を失うライター。

#### キーの部分の計算方法

各キーの部分は、本が読み取られるときに計算されます。マーク以降に各キーがルーティングされたトークンに比例して、ベースラインがキー間で分割されてからの数値の増加。

Together、これらのトークンは、 `QUOTA_PERCENT_MIN_TOKENS_PER_POINT`トークン (デフォルトは 1,000) ごとに図の最大 1 点を説明します。彼らが説明していない成長は外部的なものです。ベースラインも外部です。

たとえば、本は 0 で開きます。キー A は 900,000 トークンをルーティングし、キー B は 100,000 トークンをルーティングします。 60 点の場合、A のパートは 54 点、B のパートは 6 点になります。

キーのマークの下にあるカウンターが再起動され、完全にカウントされます。ウィンドウの中央でプールに参加するキーなど、マークのないキーは、そのすべてのトークンをカウントします。数字がトークンより遅れるとエラーが発生しますが、次の読み取り時にはエラーが解消されます。溜まらないんです。

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT`はすべての属性で読み取られます。少なくとも 1 の有限数ではない値は 1,000 に戻ります。

#### 読書が本をどう変えるか

最初に一致するルールが適用されます。

1. **まだ本がありません:**読むことで本が開きます。その数値がベースラインであり、すべてのカウンターがマークされます。
2. **古い読書:**最後に適用されたものより前の日付の読み取り値は無視されます。リセット時間が保存された値よりも 30 分以上早い測定値も同様です。
3. **新しいプロバイダー ウィンドウ:**リセット時間は、保存した本をめくってから 30 分以上後です。この数値がベースラインとなり、すべてのカウンターが再度マークされます。カウンターのないキーはブックから離れます。
4. **終了したウィンドウ:**保存されたリセット時間が読み取りデータ時間以降でない場合は、ウィンドウが終了したことを意味します。その姿が何であれ、読むことで本は変わります。
5. **上の数字:**最後の数字だけが動きます。ベースラインとマークは残ります。
6. **同じ図:**図、ベースライン、マークは残ります。この本に足りないリセット時間だけが書かれています。
7. **下図：**下の数値がそのまま適用されることはありません。 3つのことが成立する場合にのみ本をめくります。最後に適用された測定値より少なくとも 2 分新しい値です。窓が開いているのと同じだということは何もありません。 1ポイント以上下がっています。

ウィンドウは、3 つのものが成立する場合、同じ開いたウィンドウとしてカウントされます。両方のリセット時間は既知です。お互いの距離は 30 分以内です。保存されているものはまだ読み取りの先です。そのウィンドウ内の下の図は何も変わりません。

リセット時刻は、それを伝送する読み取り値のデータ時刻よりも進んでいる間のみ保存されます。より高い数値は、その読み取り値が使用可能な場合は読み取り値のリセット時間を保存し、それ以外の場合は保存された値を保持します。等しい数字は、本に何もない場合にのみ、その読書のリセット時間を記録します。それ以外は何も変わりません。本をめくらない下位の数字はリセット時間を記録しません。

#### 本を使用するとき

読書後、保存されているリセット時刻が現在時刻を過ぎていない限り、本は使用されます。このケースは、キャッシュから提供された読み取りなど、リセットの直前に取得された読み取りが、リセット直後に観察された場合に発生します。

使用可能な読み取り値がない場合、保存されたブックは、現在のウィンドウのブックである間のみ使用されます。これは次の 2 つの場合に当てはまります。

- リセット時間はわかっていますが、まだ先です
- リセット時間はなく、それを変更した最後の読み取り値は最長 15 分前です

それ以外の場合は、本がない場合と同様に、何も帰属されません。保存されたリセット時間が経過した本は、課金されません。

#### 執行

パーセント ディメンションでのキーの消費量は、その属性部分に外部部分のシェアを加えたものです。外部部分は最初に、割り当てなしの容量要求 (100 から重みの合計を引いたもの) を使用します。超過分だけが重みによってキー間で共有されます。

その消費量は、他の次元と同様に、キーの公平なシェアと比較されます。 Strict モードは、飽和信号が`QUOTA_SATURATION_THRESHOLD` (デフォルト 0.5) に達すると開始されます。すべての数値は、有効な制限 (アカウントごとの制限とプール内のアカウント数の積) によって調整されます。

`capUnit: "percent"`を使用した絶対キャップは、同じ方法でスケーリングされた、キーに起因する部分のみをカウントします。アカウントごとの制限を 100 および k アカウントとします。サービス提供アカウントの数値のキーの部分がN/kポイントに達すると、N の上限に達します。各アカウントは独自の帳簿と照合されます。たとえば、2 つのアカウントの場合、1 つのアカウントの数値の 5 ポイントで上限の 10 に達します。

ストアを読み取れない場合は、何も属性が付けられず、そのディメンションではすべてのキーに 0 がチャージされます。ブックの書き込みが失敗した場合、その属性は読み取られたとおりにブックを使用します。トークンの書き込みが失敗すると、そのリクエストのトークンがブックから除外されます。これらの障害によってリクエストがブロックされることはありません。

`consent`プールでは、融資式は、前述のようにパーセント ディメンションで各キーの消費を使用します。別のキーが貸し出される場合、本は 1 回読み取られ、すべてのキーに割り当てられます。使用可能なブックがない場合、すべてのキーは 0 に請求されます。その後、重み付きのキーが渡され、重み 0 のキーは、別のキーが貸し出される場合にのみ渡されます。

#### 利用経路

`GET /api/quota/pools/{id}/usage`同じ関数を通じて同じ数値を報告します。パーセント ディメンションには、 `accounts`のプール接続ごとに 1 つのエントリがあります。そのトップレベルの`consumedTotal`および`perKey` 、最初のエントリをミラーリングします。

ルートは現在の読み取り値にも適用するため、リクエストに応じて本を進めることができます。使用可能な読み取り値がない場合、または下位の数値が適用されない場合、 `internal + external` `consumedTotal`と異なる場合があります。

#### 保管と保持

どちらのクォータ ストアも帳簿を保持します。 SQLiteでは、データベースの自動クリーンアップが有効になっている場合、60 日間更新されなかった行が削除されます。 Redisでは、プール接続のブックとカウンターが 1 つのキーを共有します。最後のトークンの書き込みまたはブックの変更から 60 日後に期限切れになります。変更しないブックは書き換えられないため、カットオフは最長の計画ウィンドウより上に設定されます。使用履歴を手動でリセットすると、 SQLite上のブックもクリアされます (制限事項を参照)。

#### 制限事項

- ベースライン以降のアカウント数値のすべての増加は、それ以降にルーティングされた各キーのトークンによって分割されます。その成長がいつ起こったかは問題ではありません。
- したがって、 OmniRoute外部で行われた使用は、トークンが許可する範囲内でキーに課金されます。これには、キーがウィンドウに最初に要求する前、ブックがすでに開かれていたときに行われた使用も含まれます。
- たとえば、キールートがない場合、外部使用によりアカウントが 60 ポイント上昇します。その後、キーは 30,000 個のトークンをルーティングし、その数字は 60.6 に達します。
- その使用前に本が開かれていた場合、鍵の部分は 30 ポイントです。また、重さ 25 の 4 つのキーを備えた 7.65 の外部使用も可能です。
- その使用後に本を開いた場合、60 ポイントが基準となります。キーの部分は 0.6 ポイントで、外部使用量が 15 個あります。
- リクエストまたは使用ルートへの訪問により、本が開きます。したがって、そのような使用法がベースラインとしてカウントされるかどうかは、書籍がいつ開かれたかによって決まります。
- デフォルトの下限では、屋外での使用中に 60,000 個のトークンをルーティングするキーは、アカウントの 60 ポイントを引き上げ、60 ポイントすべてを独自の部分として取得します。
- 下限が50,000なので、自身の部分は1.2ポイントです。残りの 58.8 は外部で使用され、外部での使用と同様に重量によって課金されます。
- `QUOTA_PERCENT_MIN_TOKENS_PER_POINT`プランの 1 ポイントのコストに近い値に設定します。外部使用には、プールの外部のキーからの同じアカウント上のトラフィックが含まれます。
- パーセントの上限はすべてのモードに適用されます。アカウントが飽和しきい値をはるかに下回っている間は、キャップ付きキーは拒否される可能性があります。
- 窓口の早い段階で屋外使用の10ポイントと12ポイントのキャップを取ります。 20,000 トークンをルーティングするキーは、アカウントの 12.4% という数字で拒否されます。
- 分割額はトークン量による推定値です。リクエストは、プロンプト トークンと完了トークンとしてカウントされます。キャッシュ割引やモデル価格によってもこの数は変わりません。
- ステータス 200 で終了しないリクエストはトークンを記録しません。例としては、クライアントが切断したストリームや、使用量が消費された後のアップストリーム エラーなどがあります。
- このようなリクエストによって引き起こされた使用量は、トークンが許可する範囲内で、トークンを記録したキーに課金されます。残りは外部です。後戻りはしません。トークンの使用状況を報告しない応答では、トークンも記録されません。
- 進行中のリクエストの使用状況は、リクエスト全体の別のアクティブなキーの部分に表示されることがあります。リクエストがステータス 200 で終了した場合にのみ前に戻ります。
- 本を開いたときにすでにアカウントにある使用量は、外部としてカウントされます。これには、アップグレード、新しいプール、新しいアカウントが含まれます。最初の読み取りの前に新しいウィンドウで使用した場合も、外部としてカウントされます。
- 各キーは、その使用量のウェイト シェアから始まり、その後、容量の割り当て要求がありません。 1 つのアカウントが 85%、重み 20 の 5 つのキーがある場合、それぞれの 20 個のうち 17 個が使用された状態で開始されます。
- 複数のアカウントが含まれるプールでは、サービス アカウントの数値が合計予算に適用されます。これは本書でも変わっていない。
- プロバイダーが開いていると報告するウィンドウ内の下の図は適用されません。 30 分以上遡ったリセット時刻は古い測定値として扱われます。
- どちらの場合も、本は保存されたリセット時間が経過するまでその状態を保持します。その後、本を読んでめくるまで料金はかかりません。
- 解決策は、手動による使用履歴のリセット (`POST /api/settings/purge-usage-history`) です。 SQLiteデータベース内のアトリビューション ブックとそのトークン カウンタをクリアします。
- `all`期間はすべての本とカウンターをクリアします。短い期間では、まずその期間内に書かれていない書籍が消去されます。次に、その中に書き込まれていないカウンターをクリアしますが、ブックが残っていないプール接続に対してのみクリアされます。保管されている本は、カウンターに対して各キーにマークを付けたままです。
- フィギュアが移動していないブックは書き換えられないため、より短い期間で現在のウィンドウのブックをクリアすることもできます。次に読むと、現在の図で新しいブックが開きます。
- リセットでは、 Redisクォータ ストアには影響しません。そこでは、ブックはその期間で終了するか、最後の書き込みから 60 日後に期限切れになります。
- プロバイダーがリセット時間を送信しない場合、2 つの測定値間の古い数値をリセットして再充填するウィンドウは、より高い数値のように見えます。この本では古いベースラインとマークが維持されます。
- 測定値はローカル時計によって日付が付けられます。プロバイダーよりも早く実行されたり、情報源がリセット時間を少し早めに報告したりすると、本はその差を早期に明らかにする可能性があります。
- その短いスパンでの増加は、その中でルーティングされるトークンによって分割されます。次のウィンドウの最初の読み取りにより修正されます。めくられた本がリセット時間を保持していない場合、その修正には、最後に適用された読み取り値より少なくとも 2 分新しい、より低い数値が必要です。
- Redis共有するインスタンスは、日付の読み取り値を独自のクロックで保存するため、それらのクロックを同期させてください。クロックが遅れているインスタンスの読み取り値は古く見えるため、無視されます。
- 保存されたリセット時間が経過しても使用可能な読み取り値が到着しない場合、読み取り値が返されるまでキーごとのパーセント シェアとパーセント キャップは適用されません。リセット時間を設定しないと、本を変更した最後の読書から 15 分後に開始されます。
- Redisストアでは、60 日間アイドル状態だった書籍は、作家の小切手から書き込みまでの間に期限切れになる場合があります。その後、有効な状態である 1 より上のリビジョンで再作成されます。

## パイプラインの統合

### PREフック (`open-sse/handlers/chatCore.ts`)

認証とポリシーのチェックの後、上流のエグゼキューターの前に実行されます。

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**フェールオープン**: `enforceQuotaShare`がスローした場合、リクエストは`pino.warn`ログで許可されます。これにより、クォータ エンジンのバグによってすべてのトラフィックがブロックされるのを防ぎます。

**容量が戻ったとき。**キーのシェアまたはプールの上限での拒否は、どちらの借用モードでも、次の 2 つの文のいずれかで終了します。

- `percent`ウィンドウ: `. The <window> window resets at <time>.`時刻はプロバイダーが報告するリセット時間です。
- 可算単位: `. Enough <window> usage is expected to clear by <time>.`キーが他に何も送信しない場合、時間はスライディング ウィンドウの上限です。

`<time>` 、 UTCのISO 8601 インスタントです。拒否には`Retry-After`が含まれます。つまり、その瞬間までの秒数に 1 を加えたものです。それだけの時間待機したクライアントは、その瞬間から最大 1 秒後に再試行します。瞬間が不明な場合、拒否には文もヘッダーも含まれません。絶対的な上限の拒否にはどちらも含まれません。公開コードは`quota_share_blocked`ままです。

共有を拒否しても、共有接続には影響しません。クールダウン、モデルのロック、プロバイダー ブレーカーの障害は設定されず、プールの他のキーは引き続き提供されます。コンボのすべてのターゲットがそのシェアのキーを拒否した場合、コンボは待たずに 429 を返します。その答えには`Retry-After`としてヒントが含まれています。 embeddings パスは同じ文で拒否を終了し、 `Retry-After`を送信しません。

### POSTフック (レコード消費)

正常に応答した後:

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**ドリフトノート**: `consume`応答後に失敗した場合、ローリング カウンタはアンダーカウントします。プロバイダー (例: `anthropic-ratelimit-unified-5h-utilization`) からの飽和信号により、次のリクエストのグローバル推定値が修正されます。

### コンボソフトペナルティ (`open-sse/services/combo.ts`)

`decision.deprioritize === true`場合:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

ペナルティは、他のすべての得点要素の後に適用されます。飽和したキーをハードブロックせずに選択するオートコンボの確率を下げます。

## セルフサービス クォータAPI (オプトイン)

`GET /api/v1/me/quota/{provider}` ( `/v1/me/quota/{provider}`でも提供されます) を使用すると、 APIキーホルダーは、自分のキーを使用して、共有サブスクリプションのどの程度が自分のものであるか、何がブロックしているかを読み取ることができます。ルートは`src/server/selfService/quotaHandler.ts`上の薄いシェルです。ビューは`src/lib/quota/selfView.ts`によって構築され、その応答コントラクトは`src/shared/schemas/selfQuota.ts` ( `docs/openapi.yaml`の`SelfQuotaView` ) です。

### 有効化と認証

- 機能フラグ`QUOTA_SELF_PANEL`、デフォルト`false`。オフの間、ルートに到達するリクエストは 404 を取得します。 `REQUIRE_API_KEY=true`を使用すると、クライアントAPIポリシーは、フラグが何であれ、ルートが実行される前に欠落または無効なキーを 401 で拒否します。キーを持たないがサインインしているダッシュボード セッションのリクエストはそのポリシーを渡し、ルート独自の回答を取得します。このフラグは、他のすべてのフラグと同様に解決されます (ダッシュボードまたはRESTオーバーライド、次に同じ名前の環境変数)。 [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md)参照してください。
- 各プールの表示名と各スケジュールのラベルは、管理者が書き込んだとおりにプールのキーホルダーに返されます。フラグをオンにする前に、それらのキーホルダーが読み取れるかどうかを確認してください。
- キーはヘッダーからのみ読み取られます: `Authorization: Bearer <key>`または`x-api-key: <key>`。両方が送信された場合は、最初に検証されたものが使用されます。クエリ文字列内のキーまたは Cookie は無視されます。サーバーの環境キーが拒否されました (401)。
- キーには`self:usage`スコープ (それなしの場合は 403) が必要です。
- プロバイダー セグメントはトリミングされ、小文字にされ、 `^[a-z0-9][a-z0-9._-]{0,63}$` (それ以外の場合は 400) に対してチェックされ、プロバイダー レジストリを通じて解決されるため、 `cc`などのエイリアスが`claude`プールを読み取ります。 `claude`と`anthropic`同じプールを読み取ります。

### それぞれの可視性が示すもの

| 可視性           | 必要                                                                                    | フィールド                                                                                                                                                                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 自己のシェア     | `self:usage`                                                                            | `pools[]` (参照、名前、プロバイダー、ポリシー、重み、キャップ)、 `dimensions[].yourShare`、 `accounts[]`を使用する`yourShare` ( `attributed`および`external`を使用しない`percent`ウィンドウ上)、 `blocks`、 `availableModels`、 `expiresAt`、 `apiBaseUrl`                     |
| アカウントレベル | `self:usage` + `self:account-quota`、およびキーの`sharedQuotaProviders`内のプロバイダー | `percent`ウィンドウの`yourShare`に`dimensions[].total`、 `accounts[].dimensions[].account`および`accounts[].modelWindows`、 `attributed`および`external`を追加し、メンバーの使用状況をオンにしてプールに`members`追加します ( [「メンバーの使用状況」を](#member-usage)参照)。 |

- `sharedQuotaProviders`はキーごとの設定 (`PUT /api/keys/[id]/self-service`): デフォルトの`null`、キーが到達するすべてのプロバイダーを意味します。 `[]` 「なし」を意味します。各プールの`accountVisible` 、どの可視性が適用されるかを示します。
- アカウント バーとモデル ウィンドウは、キーが使用する接続を持つアカウントに対してのみ表示されます。キーに許可された接続のリストがある場合、キーの外部にあるアカウントは、 `account`または`modelWindows`なしで`Account N`エントリを保持します。 `/v1/me/status`の場合と同様、空のリストは制限がないことを意味します。プールの合計 (`dimensions[].total`) はそのリストには依存しません。
- `self:usage`のみで示された 2 つの数字は、他のキーの使用から得られます。スケジュール バジェットの`exhausted`そのスケジュール内のすべてのキーの消費を反映します。重みがすべてゼロであるプールでは、キーの`weight`は`100 / number of members`です。どちらもキーに適用される強制です。
- プールは、呼び出しキーにバインドされた不透明な値である`ref`によってのみ識別されます。表示名 (`name`) は、管理者が作成したものとして含まれています。 `ref`は、サーバーの API キー シークレット (`API_KEY_SECRET`) を含むキーとプールから派生します。クライアントはそれを永続化してはなりません。シークレットがローテーションされると変更されます。
- アカウントは、プール順に`Account 1`、 `Account 2`、…としてリストされます。プール ID、接続 ID、アカウントの電子メール、またはアカウント名は返されず、応答はコントラクト スキーマを通過するため、スキーマ外のフィールドは削除されます。
- カウント可能なユニット (`requests`、 `tokens`、 `usd`) は、クォータ ゲートが適用するプール バケットとして報告されます。 `limit` =プール内のプラン制限×アカウント、 `fairShare` =重み / 100 × `limit` (すべての重みが 0 の場合に均等に分割)、 `consumed` =クォータ ストア内のキー自体のカウンタ、 `remaining` = `fairShare` − `consumed`、0 で下限されます。
- `blocks.schedules` 、キーのスケジュール ウィンドウ (`open`/`closed`、 `blackout`または`outside-window`、 `retryAfterSeconds`、予約フロア、およびウィンドウの予算が使用されているかどうか) をリストします。 `blocks.modelCaps` 、モデルごとの時間当たりの消費量の上限をリストします。
- プロバイダーのすべてのプールの外にあるキーは、 `pools: []`で 200 を取得します。 `availableModels` (キーが`/v1/models`内で認識する`qtSd/` ID)、 `expiresAt` 、および`apiBaseUrl`はまだ埋められています。
- `apiBaseUrl`は`OMNIROUTE_PUBLIC_API_BASE_URL`、次に`OMNIROUTE_PUBLIC_BASE_URL`、それ以外の場合は`null`。これはリクエスト自体の発信元ではありません。

### `status`と`reason`

| `status`      | 意味                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`          | 現在の読書量。                                                                                                                                                                                                                                                                                                                                                                         |
| `stale`       | キャッシュされたアカウントの読み取りが古いとマークされているか、読み取りされてからリセット時間が経過しているアカウント。番号は保存されます。リセット時間が経過した 1 つのモデル ウィンドウは、 `modelWindows`グループ`stale`全体をマークします。 `percent`ウィンドウのキー自身のシェアの場合: 本は、それを確認するためにゲートのキャッシュを読み取るアカウントなしで読み取られました。 |
| `unavailable` | 読書はありません。番号は`null`であり、 `0`ではありません。 `reason`はその理由をこう語る。                                                                                                                                                                                                                                                                                              |

| `reason`                          | いつ                                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `store_unavailable`               | クォータ ストアを読み取ることができなかったか、属性ブックを読み取ることができません。                                                     |
| `percent_attribution_unavailable` | `percent`ウィンドウのキー自体のシェア: そのアカウントおよびウィンドウの帰属ブックがまだ存在しないか、ブックにキーがリストされていません。 |
| `percent_window_ended`            | キー自体の`percent`ウィンドウの共有: ブックは終了したプラン ウィンドウに属します。                                                        |
| `account_not_used_by_key`         | キー自体の`percent`ウィンドウの共有: アカウントの接続は、キーで許可されている接続の範囲外にあります。その本は読まれていません。           |
| `window_not_reported`             | プロバイダー制限キャッシュには、そのプラン ウィンドウの読み取り値がありません。                                                           |
| `connection_lookup_failed`        | アカウントの接続を読み取ることができませんでした。                                                                                        |
| `not_supported`                   | OmniRouteアカウントのプロバイダーの使用制限を読み取ることができません。                                                                   |
| `fetch_failed`                    | キャッシュされた読み取り値が使用できず、プロバイダー制限の更新に失敗しました。                                                            |
| `not_available`                   | 測定値に使用期間がないか、アカウントに測定値がまったくありません。                                                                        |

クォータ ストアを読み取れない場合、 `blocks`のストアバック フィールド (スケジュール バジェットの`exhausted`、モデル キャップの`consumed`および`reached`) も`null`になります。

### 貸出承諾

`PATCH /api/v1/me/quota/{provider}` 、1 つのプールに対する呼び出し側キー自身の同意を記録します。 `GET`のフラグ、ヘッダー、プロバイダー ルールを使用します。名前は読み取り専用ですが、 `self:usage`スコープはこの 1 つの書き込みを許可します。

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool`は、 `GET`がそのプールに対して返す`ref`です。
- `lendingPercent`は 0 ～ 100 の整数です。値 0 は同意とその期限をクリアします。 `lendingPercent` 0 のボディはどちらのモードでも受け入れられます。
- `lendingUntil`はオプションです。エポックミリ秒、または期限なしの場合は`null` 。将来の値であり、最大でも 8640000000000000 である必要があります。100000000000 未満の値は秒として読み取られ、拒否されます。
- それ以外のフィールドは拒否されます。 4096 バイトを超えるボディは拒否されます。読み取りはそのサイズで停止するため、長い本体が完全に保持されることはありません。

チェックはこの表の順序で実行されます。すべての拒否では、固定メッセージを含む標準エラー本文が使用されます。これらのチェックのいずれかが拒否された場合は、何も書き込まれません。

| 状態 | メッセージ                                                                                         | いつ                                                             |
| ---- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 404  | `Not found`                                                                                        | `QUOTA_SELF_PANEL`フラグがオフになっています。                   |
| 401  | `Valid API key required`                                                                           | キーが見つからないか無効であるか、サーバーの環境キーです。       |
| 403  | `API key lacks the self:usage scope`                                                               | キーに`self:usage`がありません。                                 |
| 400  | `Invalid provider`                                                                                 | プロバイダーセグメントが無効です。                               |
| 429  | `Too many lending changes. Retry later.`                                                           | キーが制限を超えました。答えには`Retry-After`が含まれます。      |
| 400  | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | 本体がJSONではないか、長すぎるか、スキーマと一致しません。       |
| 400  | `lendingUntil must be a Unix time in milliseconds`                                                 | 期限は秒単位で表示されます。                                     |
| 400  | `lendingUntil must be in the future`                                                               | 締め切りはリクエスト時間またはそれ以前です。                     |
| 404  | `Pool not found`                                                                                   | `ref` 、このプロバイダーのこのキーのプールに名前を付けません。   |
| 403  | `Lending is not enabled for this pool`                                                             | プールは`saturation`モードで、 `lendingPercent`は 0 より上です。 |
| 500  | `Failed to build quota view`                                                                       | その他の失敗。その原因はサーバーに記録されています。             |

制限は、キーごとに 60 秒あたり 20 リクエストです。プロバイダーのチェックに合格したすべてのリクエストは、後で拒否されたリクエストや何も変更されなかったリクエストであってもカウントされます。キーのリクエスト レート制限とは別に、独自のカウンターがあります。

保存された同意を変更するリクエストは、1 つの`quota.pool.lending.updated`監査レコードを書き込みます。キーに古い値と新しい値を付けて名前を付けます。同じ本体が 2 回送信され、1 回の書き込みと 1 回の監査が行われました。書き込み後に構築された完全な`GET`ビューでは、答えは 200 です。

`GET`ビューは、融資を次のように報告します。

- 各プールには、 `borrowMode` (`saturation`または`consent`) と、キー独自の`lendingPercent`および`lendingUntil`が含まれます。
- `lendingActive`は`consent`プール内でのみ`true`であり、パーセンテージが 0 を超えており、期限に達していません。
- `consent`プールでは、可算な各`dimensions[].yourShare` `borrowAvailable`を保持します。これは、他のキーによって貸し出され、そのキーが現在そのシェアを超えて使用できるものです。
- `borrowAvailable`ゲートの公式を使用します。キーがその共有下にある間も、キーを 1 つおきに読み取ります。 `hard`キーの場合、他のキーおよび可算次元ごとに 1 回の追加読み取りが並行して行われます。
- `borrowAvailable` 、 `soft`または`burst`キーの場合は`null` 、読み取りが失敗した場合は`null`です。
- `borrowAvailable`は、他のすべてのキーをまとめた 1 つの数字です。 2 つのキーのプールでは、もう一方のキー自体の数字になります。
- `borrowAvailable` 、 `percent` Windows または`accounts[]`ではまだ報告されていません。
- `saturation`プールでは、ビューは`lendingActive: false`を使用して保存された同意を報告しますが、 `borrowAvailable`使用しません。

### エラー

このルートのすべての応答には、成功またはエラーにかかわらず、 `Cache-Control: no-store`が含まれます。ルートの実行前に発生した拒否には、クライアントのAPIポリシーの 401 やIPフィルターの 403 などの拒否は含まれません。ルートのエラーでは、次の固定メッセージを含む標準エラー本文が使用されます: 400 (無効なプロバイダー)、401 (欠落または無効なキー)、403 (欠落`self:usage`)、404 (フラグ オフ)、および 500 (`Failed to build quota view`）。 500 は、キー検索自体を含む、リクエストがルートに到達した後のあらゆる障害をカバーします。その原因はサーバーに記録され、返されません。 `PATCH`のエラーは、 [「貸出の同意」](#lending-consent)にリストされています。

### 制限事項

- `remaining`は、キーの公平なシェアのうち、使用されていない部分です。保証はありません。プールに余裕がある間は、キーを超えて提供することもできます。プールの合計が`limit`に達すると、それ自体の`remaining`何であれ、プールのすべてのキーが拒否され、 `self:account-quota`のないキーはその合計を確認できません。
- `remaining` 、割り当ての絶対`cap`を考慮しません。キャップのユニットのウィンドウ内でのキー自体の消費がキャップの値に達すると、執行はキーを拒否します。
- アカウント レベルのバーはプロバイダー制限キャッシュから取得され、適用の決定に数分遅れる可能性があります。リセット時間が経過した読み取り値は`stale`として報告されます。
- モデルごとのウィンドウ (`modelWindows`) は、現在プラン ウィンドウ マッピングを持つプロバイダーClaudeおよびCodexについてのみ報告されます。他のプロバイダーの場合、アカウント データが表示されるときに`modelWindows`引き続き存在し、空の`windows`リストが表示されます。
- `percent`ウィンドウにおけるキー自体のシェアは推定値です。これは帰属ブックに基づいており、上記の「パーセント ディメンション: キーごとの帰属」にリストされているすべての制限が適用されます。
- `consumed`は、公平なシェアと比較される施行数です。正確には、 `attributed`と`external`を足したものです。 `attributed`は、本がルーティングするトークンのキーを与える部分です。 `external`は、アカウントの使用のうち、プールのキーでは考慮されないキーの部分です。
- どちらの部分も、プールの`accountVisible`が true の場合にのみ送信されます。つまり、キーに`self:account-quota`があり、プロバイダーがその`sharedQuotaProviders`にあります。これを持たないキーは、同じ`status`と`reason`持つ`consumed`のみを取得します。
- 両方の部分とその自重を使用して、所有者はプールのキーに課金されるプールの外での使用を計算できます。アカウントスコープを持つ所有者には、アカウントの合計がすでに表示されています。
- ウィンドウ内で何もルーティングされていないキーでも、属性部分が 0 であるため、 `consumed`から外部チャージを読み取ることができます。
- たとえば、本は 0 で開き、キー A と B の重みはそれぞれ 50 です。キー A は 900,000 トークンをルーティングし、キー B は 100,000 トークンをルーティングします。その後、アカウントは制限 100 の 60% に達します。その後、 `attributed`はキー A で 54、キー B で 6、 `external`両方とも 0 になります。
- ビューはブックを読み取りますが、その状態を書き込むことはありません。本を開くことはありませんし、プロバイダーに読書を要求することもありません。 Redisストアでは、ゲートの読み取りと同様に、読み取りによって、置き換えられたリビジョン フィールドがバックグラウンドで削除されます。
- ゲートのキャッシュがアカウントの読み取り値を保持している間のみ、共有は`ok`になります。これがない場合は`stale`となるため、最近のリクエストがないプールでは古い可能性があると表示されます。
- リクエストがプールを通過するまで、共有は利用できません。このリクエストにより帳簿が開き、その時点のアカウントの数値がプール外での使用としてカウントされます。
- 複数のアカウントを含むプールでは、各アカウント エントリはそのアカウント独自の帳簿と 1 つのアカウントの制限を使用します。執行はアカウント数に応じて両側で調整されるため、比率は同じになります。
- モデルごとのウィンドウにはキーの共有はありません。この本にはモデルごとのデータは保存されていません。
- スケジュールの予約フロアはビューによって評価されません。リクエストが`schedule-reserve`という理由で拒否されている間、スケジュールは`open`として表示されることがあります。
- 同じキーの 2 つのプールが接続を共有する場合、適用によりそのうちの 1 つが適用され、ビューには両方がリストされます。
- 失敗したキー試行にはアドレスごとの制限はありません。リバース プロキシの背後では、呼び出し元は 1 つのアドレスを共有できるため (転送されたクライアント アドレスが信頼できるかどうかによって異なります)、ロックアウトによってすべてのキー所有者へのルートが拒否される可能性があります。 `REQUIRE_API_KEY=true`使用すると、無効なキーはルートの実行前にクライアントのAPIポリシーによって拒否され、このルートの代わりにそのポリシーの 401 本文が使用されます。

### 会員利用

管理者は、キー所有者に、ウィンドウの使用がプールのメンバー間でどのように分割されるかを確認できるようにすることができます。オプションはプールの`memberBreakdown`で、デフォルトではオフです。これは、プール ウィザードまたは`PATCH /api/quota/pools/{id}`で設定されます。 `GET /api/quota/pools`と`GET /api/quota/pools/{id}`それを報告します。

ビューのディメンションは、次のすべてが満たされる場合にのみ`members`を持ちます。

- プールのオプションがオンになっています
- プールには最大 20 個の割り当てられたキーがあり、そのうちの少なくとも 3 つはリクエストを行うことができます: アクティブ、取り消されていない、禁止されていない、有効期限が切れていない
- プールの`accountVisible`は true です。キーには`self:account-quota`があり、プロバイダーはその`sharedQuotaProviders`内にあります。
- `percent`ウィンドウでは、アカウントの接続はキーが使用できるものです
- そのウィンドウのキー自体の共有が読み取られました: その`status`は`unavailable`ではありません

それ以外の場合、 `members`は存在しません。決して空のリストではありません。

- 各スライスは`{ slot, consumed, isYou }`です。応答スキーマは、スライス上の他のプロパティと 20 を超えるスライスのリストを拒否します。スライスはスロット順にリストされます。
- リクエストを実行できなくなったキーを含め、割り当てられたキーごとに 1 つのスライスがあります。役に立たないメンバーは実質ゼロを示します。
- スロット 1 は常に要求キーであり、 `isYou`が true です。他のスロット番号は、キー付きハッシュのランクです。これは`API_KEY_SECRET`でキー付けされており、プール、要求キー、およびメンバーをカバーします。
- そのため、ホルダー間で番号が一致しません。 1 人のホルダーの場合、訪問後も同じままです。これらは、キーがプールに参加またはプールから離れるとき、またはそのシークレットがローテーションされるときに変更される可能性があります。
- 可算ウィンドウでは、スライスはクォータ ストア内のメンバーのカウンターであり、それ自身の`consumed`と同じカウンターです。
- `percent`ウィンドウでは、スライスは、キー自身のシェアとして読み取られた同じブックからのメンバーの`attributed`部分です。プールの外で行われた使用がスライスに分割されることはありません。その電荷は重量によって分割されるため、それを運ぶスライスには重量が表示されます。
- 各ビューは、他のメンバーおよび可算ウィンドウごとに 1 つの値を並行して読み取ります。 `percent`ウィンドウでは、スライスの読み取りコストは、シェア自身の書籍の読み取りを超えるものはありません。 1 つの値を読み取れない場合、そのウィンドウには`members`がなく、キー自体の共有が残ります。
- オプションと使用可能なキーの数は、アカウント データを参照できるキーに対してのみ、プールごとに 1 回読み取られます。オプションまたは使用可能なキー数の読み取りに失敗すると、そのプールのバーがオフになります。サーバーは警告をログに記録し、ビューの残りの部分が構築されます。

バーには名前も ID もありません。彼らは今でもキーホルダーに他のメンバーについて次のように語っています。

- ホルダーは引き続き、値によってスライスを照合できます。
- 安定した番号付けにより、所有者は長期間にわたって 1 人のメンバーを追跡できます。
- スライスの数は、プールに割り当てられているキーの数を示します。
- 3 つのキーのプールでは、1 つのキーが何を使用したかを知っている人は、最後に使用されたキーが何かを知ることができます。
- プールが使用可能なキー 3 つを下回ると、バーが消えます。以前に撮影したビューには、各メンバーが使用したものがまだ表示されています。
- 可算ウィンドウでは、プールの合計からスライスを差し引いた値から、割り当てられなくなったキーの使用状況が示されることがあります。
- あるアカウントではゼロを表示し、別のアカウントでは使用しているメンバーは、どのメンバーがどのアカウントを使用しているかを示すことができます。
- `hard`ポリシーを使用した可算プールでは、メンバーの公平な割合で成長が停止したスライスは、そのメンバーの重みを示します。

### 使用法シリーズ (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` ( `/v1/me/usage`でも提供されます) は、呼び出し元のキー自体のリクエストの使用量とコストを返します。合計、 UTC日ごと、日ごと、モデルごと、モデルごと、プロバイダーごとに 1 つのエントリです。フラグ、認証ルール、 `self:usage`スコープ、 `Cache-Control: no-store` 、および上記のクォータ ルートのエラー動作を共有します。キーは`range`の前にチェックされます。エラーは 400 (`Invalid range`)、401、403、404、および 500 (`Failed to build usage`) です。

- `range`は、 `1d`、 `7d`、 `30d` (デフォルト) または`90d`のいずれかです。他の値、空の値、または繰り返されるパラメータは 400 です。通話のコストを制限するために、セットは`90d`で停止します。このビューは生の使用履歴のみを読み取り、キーを持たない毎日の概要は読み取りません。
- 行は呼び出し元のキーの ID によって選択されます。キー名の列が一致することはなく、キー ID なしで記録された行はカウントされません。
- シリーズを構築すると、ウィンドウ内のキーの行に対して 5 つのグループ化されたクエリが実行されます。構築されたシリーズはキーおよび範囲ごとに 60 秒間再利用され、再利用された呼び出しは何も実行されません。その`generatedAt`その年齢を表しています。
- シリーズが構築されるとウィンドウは終了します。クロック スキューなどによって後でスタンプされた行はカウントされません。
- `coverage.retentionDays`は、オペレーターの生の使用履歴保持設定 (データベース設定の`retention.usageHistory` ) です。 `coverage.truncatedByRetention` 、要求された範囲がその設定よりも長い場合に true になります。 2 つの数値を比較しますが、実際に行が欠落しているかどうかはチェックしません。
- プロバイダーは、キー自体のリクエストに対して記録されたものとして返されます。 Model は最後の`/`の後に記録された名前であり、行はそれによってグループ化されます。すべてのターゲットが拒否されたコンボ リクエストは、プロバイダーとしてのルーティング ラベル (コンボ名、 `auto`または`combo`) とクライアントが送信したモデル文字列とともに記録されます。オープン サーキット ブレーカー、モデルのクールダウン、クォータ パーク スキップなどによってその他の拒否されたリクエストは、ターゲット プロバイダーとモデルを保持します。
- 応答には、カウントとコストに加えて、平均レイテンシ、成功率、最初と最後のリクエストの時間が含まれます。
- `byModel` 、リクエストが最も多かった 50 のプロバイダーとモデルのペアをリストします。ペアが増えると、そのエントリの合計は`summary`に達せず、 `summary.uniqueModels`記録されたすべてのモデルのスペルをカウントします。この場合、 `byModelTruncated`は true となり、ペアがカットの両側にあるモデルは部分的な合計を示します。
- 2 つのコストが報告されます。 `costUsd`は、使用状況分析で示される請求コストです。 Claudeコード プランなどの定額サブスクリプション プロバイダーは、そこで $0 としてカウントされます。 `listPriceUsd` 、サブスクリプションを含む定価での使用料金と同じです。モデルに価格行がないリクエストは、保存されているコスト (プロバイダーが報告したコスト、またはリクエストの記録時に計算されたコスト) をカウントします。どちらも含まれないリクエストのみが 0 とカウントされ、マーカーがないため、合計が部分的になる可能性があります。
- 応答コントラクトは`src/shared/schemas/selfUsage.ts` (`SelfUsageSeries`では`docs/openapi.yaml`) です。

### セルフサービスページ

`QUOTA_SELF_PANEL`がオンの場合、 `/quota/{provider}`は公開ページになります。キー所有者はそこにAPIキーを入力し、プロバイダーのそのキーのプールを確認します。各プールには、プール ウィンドウごとに 1 枚のカードが表示され、全員がプールを使用し、キーが独自に共有されます。プールの各アカウントには、アカウントの使用法とキーの共有が指定された独自のカードがあります。アカウントの使用は、キーがアカウント データを参照できる場合にのみ表示されます。このページには、各アカウントのモデルごとの制限とキー自体の使用法もリストされています。現在スケジュールによってキーがブロックされている場合、通知が表示されます。カードには、キーのモデルごとのすべての上限がその使用とともにリストされ、到達した上限がマークされます。 `{provider}`はプロバイダー ID またはそのエイリアス (`/quota/claude`、 `/quota/cc`) です。不明なプロバイダー、およびフラグがオフの間のすべての`/quota/*`パスは 404 と応答します。カスタム OpenAI または Anthropic 互換ノード上のプールにはページがありません。 API依然としてそれらに答えます。

このページにはセッションがありません。キーは`GET /api/v1/me/quota/{provider}`、 `PATCH /api/v1/me/quota/{provider}`および`GET /api/v1/me/usage`の`Authorization`ヘッダーでのみ送信され、 URLでは送信されません。サーバーが受け入れるキーは、タブの`sessionStorage`に保持されます。 「このデバイスに記憶する」を選択すると、代わりに`localStorage`に保持され、「キーを忘れる」を選択すると、両方から削除されます。サーバーが拒否したキーはストレージから削除されます。

`consent`モードのプールには、貸出カードが表示されます。そこで、キーの所有者は、貸与するキーのアイドル シェアの 0 から 100 までの整数の割合を設定します。また、所有者は同意の継続期間を選択します: オフになるまで、1 時間、8 時間、24 時間、7 日間、または 30 日間。期間は保存した瞬間からカウントされます。期限が有効である間、所有者は代わりに期限を保持することができます。保存する前にその期限が過ぎた場合、カードは何も送信せず、別の選択肢を求めます。 0% の場合、期限は送信されません。カードには、保存されている期限とそのタイムゾーンが表示されます。期限を過ぎた同意は終了済みとして表示されます。

`hard`キーの場合、カードにはプール ウィンドウごとに、そのキーに現在他のどのキーが貸し出されているかもリストされます。各行は、他のすべてのキーを合わせた 1 つの数字です。 2 つのキーのプールでは、もう一方のキー自体の数字になります。ビューがレポートしない数値は、ゼロではなく、利用不可として読み取られます。 `soft`または`burst`キーの場合、カードには数値が適用されないことが示されています。

キーに 0 を超えるパーセンテージが格納されている`saturation`モードのプールは、引き出しのみを示します。保存されているパーセンテージはそこには影響しないと言われています。その「引き出し」ボタンは期限なしで 0 を送信します。 0 が格納されている`saturation`モードのプールには、貸出カードが表示されません。保存後、返されたビューで不要になったカードは、ページのビューが再び変更されるまでメッセージとともに残ります。

所有者が保存または引き出しを押すまでは何も保存されません。各押下で 1 つの`PATCH /api/v1/me/quota/{provider}`リクエストが送信され、最初の押下が保留されている間、2 回目の押下では何も送信されません。ボディには、ビュー、パーセンテージ、および期限からのプールの不透明な`ref`が含まれます。答えは、再構築されたクォータ ビューであり、2 回目の読み取りなしでページに表示されます。 2 つの保存が重なると、ページは最後の回答の後にクォータを 1 回読み取ります。このページはブラウザのストレージに同意を保存しません。

拒否された変更については、 HTTPステータスから選択されたテキストによってカード上に説明されます。エラー本体が読み込まれません。 401 は、キーが受け入れられなかったことを示し、クォータをリロードします。 403 はプールが貸出変更を受け付けていないことを示し、404 はプールがなくなったことを示します。どちらも、クォータをリロードするボタンを提供します。 400 または別の 4xx の回答は、所有者にパーセンテージと期限を確認するよう求めます。 A 429 は、答えが得られるまで`Retry-After`秒間待つようホルダーに要求します。 5xx の応答、408、またはネットワーク障害は、変更が保存されなかった可能性があることを示し、入力された値は保持されます。契約外の回答はクォータをリロードします。保存に失敗しても、キー自体は削除されません。拒否された後のリロード時には、拒否された読み取りの場合と同様に、ページはキーを削除します。

キーが受け入れられると、ページには 3 つのタブのある「ツールのセットアップ」カードも表示されます。 「Claudeコード」は、 `~/.claude/settings.json`の`env`ブロックを提供します。 「Shell」は`export`行と同じ変数を与えます。 「Claude Desktop」は、サードパーティの推論ウィンドウの値を提供します。モデルは、キーがそのプロバイダーに対して呼び出す可能性のあるクォータ共有モデルです。そのようなリストがキーに付属していない場合、ブロックは代わりにゲートウェイ モデルの検出をオンにします。ゲートウェイ アドレスは、サーバーが報告するパブリックAPIオリジンです (`OMNIROUTE_PUBLIC_API_BASE_URL`、次に`OMNIROUTE_PUBLIC_BASE_URL`)。どちらも設定されていない場合、カードにはプレースホルダーが表示され、管理者に問い合わせるようホルダーに指示されます。キーはプレースホルダーとして表示されます。 「私のキーを含める」では、キー全体が画面上のテキストとコピーボタンでコピーされる内容に配置されます。この状態は、ボックスが空になるか、キーが忘れられるか交換されるか、ページが離れるまで続きます。このカードはリクエストを送信せず、ファイルのダウンロードも提供しません。

APIマーク`stale`を読み取ると、古い可能性があることが示されます。 `unavailable`をマークする読み取り値は、その理由とともに表示されますが、ゼロになることはありません。

パーセンテージ プランでは、 APIレポートするときにページにキー自体のシェアが描画されます。この数字は推定値であると述べ、その 2 つの部分に名前を付けています。モデルごとの制限にはアカウントのみが表示されます。

ウィンドウに`members`が含まれる場合、そのカードには、メンバーごとに 1 つのセグメントをスロット順に含むバーも表示されます。質問しているキーのセグメントはアクセントカラーを使用します。他のセグメントでは、テーマのチャートの色が循環します。テキスト凡例にはすべてのセグメントとその値がリストされるため、色には何も依存しません。セグメントには`You`または`Member N`ラベルが付けられます。N はスロットです。

### ページ専用のポート

`QUOTA_PANEL_PORT` 、セルフサービス ページのみを提供する 2 番目のリスナーを開きます。変数が設定されていない限りオフになります。 `QUOTA_PANEL_HOST`はバインド アドレスで、デフォルトは`127.0.0.1`です。

リスナーはこれらのパスをメイン ポートに中継し、他のすべてのパスに対して 404 を応答します。

| パス                                                                     | サービスします                         |
| ------------------------------------------------------------------------ | -------------------------------------- |
| `/quota/{provider}`                                                      | ページ                                 |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | ページが読み取るクォータ ビュー        |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | ページが読む使用法シリーズ             |
| `/_next/static/`                                                         | ビルドのスクリプト、スタイル、フォント |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | アイコン                               |

`GET` and `HEAD` are relayed without a body. One request with a body is also relayed: a `PATCH` of the quota view path, which the page sends to save a lending choice. Any other method answers 404, except a CONNECT request, whose connection is closed with no answer. Any other request that declares a body answers 404 and its connection is closed. Upgrade requests are refused and their connection is closed. A path with a dot segment or a fragment marker is refused, as on the API port. So is a request target with a character outside printable ASCII. A raw control character in the target is answered 400 by the HTTP parser, before this port's own check. Request headers that the framework reserves for its own use are not relayed: names that begin with `x-middleware-`, `x-invoke-`, `x-nextjs-`, `x-now-` or `x-next-`, and the names `x-matched-path` and `next-resume`. The request is relayed without them. The dashboard, the login page, the management API and the inference routes cannot be reached through this port.

`PATCH` 、パラメータなし、または`charset=utf-8`のみを指定して`Content-Type: application/json`を運ぶ必要があります。 1 ～ 4096 の 1 つの`Content-Length`単純な数字として記述し、 `Transfer-Encoding`持たない必要があります。これらのルールのいずれかに違反する`PATCH` 404 と応答します。署名されたものや反復されたものなど、一部の不正な長さは、このポート自体のチェックの前にHTTPパーサーによって 400 と応答されます。ポートはメイン ポートに接続する前に宣言されたバイトを読み取り、最大 5 秒間待機します。それまでに完了していない本体は 404 に応答し、その接続は閉じられます。その場合、またはクライアントが最初に離れるときは、メイン ポートには何も到達しません。ポートは、同じ`Content-Length`を使用して、宣言されたバイトを正確に中継します。それ以降のバイトは、接続上の次のリクエストとして読み取られます。前面のTLSリバース プロキシは`Content-Length`転送する必要があり、リクエスト本文を再チャンクしてはなりません。メインポートは、 `GET`と同様に、 `Authorization`ヘッダー内のAPIキーをチェックします。

404本体は`{"error":"not_found","message":"Not found."}`です。失敗したリレーは、 `detail`フィールドなしで 502 (`api_bridge_unavailable`) または 504 (`api_bridge_timeout`) を応答します。

リスナーは`QUOTA_SELF_PANEL`を読み取らず、ページをオンにしません。フラグがオフの間、ページとそのAPIメイン ポートで 404 に応答し、リスナーはその応答を中継します。

開発サーバー (`next dev`) では、ページはこのポートを介して対話型になりません。開発用ホットリロード ソケットはアップグレード要求ですが、ポートはそれを拒否します。開発中はメイン ポートを使用します。

ポートはプレーンHTTPを提供し、ページはAPIキーを送信します。デフォルトのバインド アドレスを保持し、その前にTLSを含むリバース プロキシを配置します。ループバック以外のバインド アドレスは、次の通知をログに記録します。

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

転送ヘッダーを送信しないループバック ピアは、メイン ポート上でローカルとしてカウントされます。したがって、同じホスト上のプロキシは`X-Forwarded-For`送信する必要があります。プライベート アドレス上のプロキシは、 `OMNIROUTE_TRUST_PROXY=private` (または`lan`) を使用するヘッダーに対してのみ信頼されます。他のピアは接続のアドレスによって報告され、送信された転送ヘッダーはドロップされます。

リスナーは一度に最大 256 の接続を保持します。クライアントは、リクエスト ヘッダーを送信するのに 10 秒、リクエスト全体を送信するのに 30 秒の時間が与えられます。アイドル状態のキープアライブ接続は、約 5 秒後に終了します。 60 秒間アクティビティがなかった接続は閉じられます。これらの値は固定されています。前面のリバース プロキシにも接続とレートの制限を設定します。前面のリバース プロキシは、アイドル状態のアップストリーム接続を 5 秒未満維持するか、再利用しないようにする必要があります。メイン ポートへのリレーでは、 APIポート (`API_BRIDGE_*`) のアップストリーム タイムアウトが使用されます。

リスナーは、 `API_PORT`が設定されていない場合にも開始されます。 `QUOTA_PANEL_PORT` 、1 ～ 65535 のポートであり、数字のみで記述される必要があります。ダッシュボード ポートやAPIポートとは異なる必要があります。ライブWebSocketサーバーが稼働している間は、 `LIVE_WS_PORT` (デフォルトは 20132) とも異なっている必要があります。他の値を指定すると何も開かず、警告がログに記録されます。拒否された値に関する警告では変数に名前が付けられ、その値は繰り返されません。すでに使用されているポートは何も開かず、次の警告がログに記録されます。

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH`設定されている場合、リスナーはそのプレフィックスの下にある上記のすべてのパスを期待します。ビルド時と実行時に同じ`OMNIROUTE_BASE_PATH`使用します。先頭にスラッシュを付け、末尾にスラッシュを付けずに記述します (例: `/omniroute`。 `/`や`/omniroute/`などの別の形式は、ビルドではこれらの形式を受け入れますが、警告とともにポートをオフのままにします。最初のセグメントがアプリケーション ルート名であるベース パスも同様です: `api`、 `v1`、 `v1beta`、 `_next`、 `quota`、 `dashboard`、 `docs`、 `login`、 `codex`、 `responses`、 `anthropic`、 `openai`、 `v0`または`connect`。

制限事項:

- 末尾にスラッシュが付いた`/quota/{provider}/` 、このポートで 404 を応答します。
- Service Worker と Web アプリ マニフェストはこのポートでは提供されません。
- ダッシュボードで設定されたカスタム ファビコンは、このポートには表示されません。
- アプリケーションがベース パスで実行されている場合、アイコンは表示されません。
- ポートは単純なHTTP/1.1.を話します
- 失敗したバインドは、プロセスが再起動されるまで再試行されません。
- リスナーには、クライアント アドレスごとの接続またはレート制限はありません。
- コンテナーのセットアップについては、このセクションでは説明しません。

## トラブルシューティング

### Redis が設定されているが接続できない

`ioredis` がインストールされていること（`npm ls ioredis`）と、`QUOTA_STORE_REDIS_URL`
に到達可能であることを確認してください。接続に失敗した場合、ファクトリは SQLite にフォールバックします（
`warn` レベルでログに記録されます）。

### `peek` が古いデータを返す / フェイルオープンになる

`peek` が例外をスローした場合、`enforceQuotaShare` は結果を「許可」として扱います（フェイルオープン）。
根本原因を特定するには、`pino` ログの `quota:enforce` および `quota:factory` エントリを
確認してください。

### 消費カウンターのずれ

実際のプロバイダー使用量がカウンターと異なる場合でも、これは想定された動作です。
2バケットのスライディングウィンドウでは、ウィンドウ境界で約1%の誤差が発生し、`consume` は
レスポンス後に非同期で実行されます。飽和シグナル（`saturationSignals.ts`）は
30秒の TTL で実際のプロバイダー使用率を読み取り、それに応じて `globalUsedPercent`
を調整します。

### プールのバーンレートに「データなし」と表示される

`computeBurnRate` には、少なくとも2つの履歴サンプルが必要です。以前に
`consume` が呼び出されていない新しいプールでは、`tokensPerSecond: 0` および `timeToExhaustionMs: null` と表示されます。

## localStorage からの移行

`/dashboard/costs/quota-share` の初回読み込み時に、フック `useLocalStoragePoolMigration`
は以下を確認します。

1. `localStorage.getItem("omniroute:quota-share:pools")` が空でないこと。
2. `GET /api/quota/pools` が `[]` を返すこと（DB が空であること）。

両方が true の場合、各レガシープールを一括で `POST /api/quota/pools` に送信し、
その後 localStorage のキーを削除します。この移行は冪等です。条件 2 によって
再移行が防止されます。

## 内部ストラテジーの分類

`quota-share` は**内部専用**のルーティングストラテジーです（
`src/shared/constants/routingStrategies.ts` 内の `INTERNAL_ROUTING_STRATEGY_VALUES`）。
システムによって生成された `qtSd/` プールコンボでのみ使用され、UI または API で
ユーザーが選択可能なオプションとして表示されないよう、意図的に
`ROUTING_STRATEGY_VALUES` から除外されています。

## DBスキーマの概要

移行によって追加された 3 つのテーブル`078`、 `079` 、および`085`:

- `quota_pools` + `quota_allocations` —プール定義とキーごとの割り当て。
- `quota_consumption` — `(apiKeyId, dimensionKey)`に 2 バケット カウンターをローリングします。
- `provider_plans` —手動プロバイダー プラン オーバーライド ( connectionIdごとのディメンションJSON )。

すべてのテーブルはべき等な`CREATE TABLE IF NOT EXISTS`移行によって追加されました。

同意されたレンディングでは、 `quota_allocations.lending_percent` (整数、デフォルトは 0)、 `quota_allocations.lending_until` (エポックミリ秒、または期限なしの場合は`NULL` )、および`quota_pools.borrow_mode` (デフォルトは`saturation`) の 3 つの列が追加されます。その移行では、これらの列が追加されるだけで、既存の行は書き込まれません。

パーセント アトリビューション ブックでは、 `quota_percent_ledger` (プール、アカウント、プラン ウィンドウごとに 1 行) と`quota_percent_ledger_tokens` (プール、アカウント、およびAPIキーごとに 1 つのトークン カウンター) が追加されます。 `src/lib/db/quotaPercentLedger.ts`それらを読み書きします。
