## 🎯 ユースケース

### ケース 1: 「Claude Pro のサブスクリプションを契約している」

**問題:** クォータを使い切れないまま期限切れになり、コーディング作業が多いときにはレート制限に達する

```
組み合わせ: "maximize-claude"
  1. cc/claude-opus-4-7        （サブスクリプションを最大限に活用）
  2. glm/glm-4.7               （クォータ切れ時の低コストなバックアップ）
  3. if/qwen3.8-max-preview       （緊急時の無料フォールバック）

月額費用: $20（サブスクリプション）+ 約$5（バックアップ）= 合計$25
対して、$20のみで制限に達する場合 = ストレス
```

### ケース 2: 「コストをゼロにしたい」

**問題:** サブスクリプションを契約する余裕はないが、信頼性の高い AI コーディングが必要

```
組み合わせ: "zero-cost"
  1. if/kimi-k2.7-code          （無料アクセスとして掲載。レート制限が適用される場合あり）
  2. kr/qwen3-coder-next        （Kiro の無料フォールバック）

月額費用: $0
品質: ワークロードに対するモデル、制限、プライバシー、SLA を確認してください
```

### ケース 3: 「中断なしで 24時間365日コーディングしたい」

**問題:** 締め切りがあり、ダウンタイムは許容できない

```
組み合わせ: "always-on"
  1. cc/claude-opus-4-7        （最高品質）
  2. cx/gpt-5.5                （2つ目のサブスクリプション）
  3. glm/glm-4.7               （低コストで毎日リセット）
  4. minimax/MiniMax-M2.1      （最安で5時間ごとにリセット）
  5. if/deepseek-v4-flash       （無料アクセスとして掲載。レート制限が適用される場合あり）

結果: 5層のフォールバックにより耐障害性が向上しますが、上流サービスの可用性は保証されません
月額費用: $20～200（サブスクリプション）+ $10～20（バックアップ）
```

### ケース 4: 「OpenClaw で無料の AI を使いたい」

**問題:** メッセージングアプリで完全無料の AI アシスタントが必要

```
組み合わせ: "openclaw-free"
  1. if/qwen3.8-max-preview     （無料アクセスとして掲載。レート制限が適用される場合あり）
  2. if/deepseek-v4-flash       （無料アクセスとして掲載。レート制限が適用される場合あり）
  3. if/kimi-k2.7-code          （無料アクセスとして掲載。レート制限が適用される場合あり）

月額費用: $0
アクセス方法: WhatsApp、Telegram、Slack、Discord、iMessage、Signal...
```

## 📖 プロバイダーのセットアップ

CSV または JSON ファイルから API キー接続を一括追加するには、**ダッシュボード → プロバイダー → ファイルからインポート**を使用します。列は位置によって決まります（`provider,name,apiKey,baseUrl,priority`）。`provider` は、管理対象プロバイダーまたは互換性のあるノードとして既に存在している必要があります。[CSV または JSON ファイルからプロバイダーをインポートする](../providers/CSV-IMPORT.md)を参照してください。

### 🔐 サブスクリプションプロバイダー

#### Claude Code（Pro/Max）

```bash
ダッシュボード → プロバイダー → Claude Code に接続
→ OAuth ログイン → トークンの自動更新
→ 5時間および週間クォータの追跡

モデル:
  cc/claude-opus-4-7
  cc/claude-sonnet-4-6
  cc/claude-haiku-4-5-20251001
```

**ヒント:** 複雑なタスクには Opus、速度を重視する場合は Sonnet を使用してください。OmniRoute はモデルごとにクォータを追跡します！

OmniRoute ホストにブラウザーがありませんか？Claude Code にログインしている任意の環境で `claude setup-token` を実行し、1年間有効なトークンを **Setup Token** タブに貼り付けてください。[セットアップトークンを使用する Claude Code](../providers/CLAUDE_CODE_SETUP_TOKEN.md)を参照してください。

Claude および Claude Code 互換ルートでは、Opus および Sonnet モデルの `max` 思考強度が維持されます。Haiku モデルは `max` 強度レベルを受け付けないため、OmniRoute はそのリクエストをアップストリームに送信する前に、高い思考バジェットへダウングレードします。

#### OpenAI Codex（Plus/Pro）

```bash
ダッシュボード → プロバイダー → Codex に接続
→ OAuth ログイン（ポート 1455）
→ 5時間ごとおよび週間リセット

モデル:
  cx/gpt-5.5
  cx/gpt-5.4
  cx/gpt-5.3-codex
  cx/gpt-5.3-codex-spark
```

#### GitHub Copilot

```bash
ダッシュボード → プロバイダー → GitHub に接続
→ GitHub 経由の OAuth
→ 毎月リセット（毎月1日）

モデル:
  gh/gpt-5.5
  gh/gpt-5.4
  gh/claude-sonnet-4.6
  gh/claude-opus-4.7
  gh/gemini-3.1-pro-preview
```

### 💰 低価格プロバイダー

#### GLM-4.7（毎日リセット、$0.6/1M）

1. 登録: [Zhipu AI](https://open.bigmodel.cn)
2. Coding Plan から API キーを取得
3. ダッシュボード → API キーを追加: プロバイダー: `glm`、API キー: `your-key`

**使用方法:** `glm/glm-4.7` — **ヒント:** Coding Plan では、7分の1のコストで3倍のクォータを利用できます！毎日午前10時にリセットされます。

#### MiniMax M2.1（5時間ごとにリセット、$0.20/1M）

1. 登録: [MiniMax](https://www.minimax.io)
2. API キーを取得 → ダッシュボード → API キーを追加

**使用方法:** `minimax/MiniMax-M2.1` — **ヒント:** 長いコンテキスト（100万トークン）向けの最安オプションです！

#### Kimi K2（月額 $9 の定額制）

1. サブスクライブ: [Moonshot AI](https://platform.kimi.ai?aff=omniroute)
2. API キーを取得 → ダッシュボード → API キーを追加

**使用方法:** `kimi/kimi-k2.5` — **ヒント:** 1,000万トークンを月額固定 $9 で利用でき、実質コストは $0.90/1M です！

#### Baidu Qianfan / ERNIE

1. 登録: [Baidu AI Cloud Qianfan](https://cloud.baidu.com/product/wenxinworkshop)
2. Qianfan API キーを作成 → ダッシュボード → API キーを追加: プロバイダー: `qianfan`

**使用方法:** `qianfan/ernie-5.1`、`qianfan/ernie-x1.1`、またはその他の Qianfan OpenAI 互換モデル ID。

### 🆓 無料プロバイダー

認証不要の無料プロバイダーには、そのプロバイダーページの **認証不要** の横にスイッチがあります。オフにすると、そのプロバイダーが無効になり、プロバイダーの設定済みビューおよびコンパクトビューから削除され、そのモデルも `/v1/models` から削除されます。

#### Qoder（無料モデル9種）

```bash
ダッシュボード → Qoder に接続 → OAuth ログイン → アクセスには現在のプロバイダー制限が適用されます

モデル: if/qwen3.8-max-preview, if/qwen3.7-max, if/qwen3.7-plus, if/kimi-k3, if/kimi-k2.7-code, if/glm-5.2, if/deepseek-v4-pro, if/deepseek-v4-flash, if/minimax-m3
```

#### Kiro（Claude を無料で利用）

```bash
ダッシュボード → Kiro に接続 → AWS Builder ID または Google/GitHub → 月間約50クレジット

モデル: kr/claude-sonnet-4.5, kr/claude-haiku-4.5
```

## 🎨 コンボ

**Dashboard → Combos** で各カードのハンドルをドラッグすると、コンボカードを直接並べ替えられます。順序は SQLite に保存され、再読み込み時に復元されます。

### 例 1: サブスクリプションを最大活用 → 安価なバックアップ

```
Dashboard → Combos → Create New

名前: premium-coding
モデル:
  1. cc/claude-opus-4-7 (サブスクリプションのプライマリ)
  2. glm/glm-4.7 (安価なバックアップ、$0.6/1M)
  3. minimax/MiniMax-M2.7 (最も安価なフォールバック、$0.3/1M)
```

## 🚀 デプロイ

### グローバル npm インストール（推奨）

```bash
npm install -g omniroute

# 設定ディレクトリを作成
mkdir -p ~/.omniroute

# .env ファイルを作成（.env.example を参照）
cp .env.example ~/.omniroute/.env

# サーバーを起動
omniroute
# またはカスタムポートを指定:
omniroute --port 3000
```

CLI は `~/.omniroute/.env` または `./.env` から `.env` を自動的に読み込みます。

### トレイモード

OmniRoute をシステムトレイで起動します:

```bash
omniroute serve --tray
```

このコマンドは、サーバーとトレイの準備が完了すると終了します。

サーバーはターミナルなしで動作を継続します。

トレイモードは macOS、Windows、およびグラフィカルな Linux セッションをサポートします。トレイモードではダッシュボードは自動的に開きません。

トレイメニューから次の操作を実行できます:

- ダッシュボードを開く。
- `/dashboard/logs` を開く。
- 自動起動の設定を変更する。
- OmniRoute を停止する。

`--tray` を次のオプションと併用しないでください:

- `--daemon`
- `--log`
- `--no-recovery`

これらのモードでは、異なるプロセス所有方式が必要です。

次回のマシンへのログイン時に起動するよう有効化します:

```bash
omniroute autostart enable
```

自動起動では、macOS、Windows、およびグラフィカルな Linux セッションでトレイモードが使用されます。ヘッドレス Linux では、既存の systemd ユーザーサービスが使用されます。

ログイン時の起動を無効化します:

```bash
omniroute autostart disable
```

### アンインストール

OmniRoute が不要になった場合、クリーンに削除するための簡単なスクリプトを 2 つ用意しています:

| コマンド                 | 操作                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------- |
| `npm run uninstall`      | システムアプリを削除しますが、`~/.omniroute` 内の**データベースと設定は保持します**。 |
| `npm run uninstall:full` | アプリを削除し、さらに**すべての設定、キー、データベースを完全に消去します**。        |

> 注: これらのコマンドを実行するには、OmniRoute プロジェクトフォルダー（クローンした場合）に移動してから実行してください。または、グローバルにインストールした場合は、`npm uninstall -g omniroute` を実行するだけです。

```bash

	NODE_ENV=development npm ci --ignore-scripts

	rm -rf .next/standalone/node_modules/@img

	for _mod in pino-abstract-transport split2 process-warning; do

do_check() {

}
```

## 🧩 高度な機能

### カスタムモデル

アプリの更新を待たずに、任意のモデル ID を任意のプロバイダーに追加できます:

```bash
# API 経由
curl -X POST http://localhost:20128/api/provider-models \
  -H "Content-Type: application/json" \
  -d '{"provider": "openai", "modelId": "gpt-5.2", "modelName": "GPT-5.2"}'

# 一覧取得: curl http://localhost:20128/api/provider-models?provider=openai
# 削除: curl -X DELETE "http://localhost:20128/api/provider-models?provider=openai&model=gpt-5.2"
```

またはダッシュボードを使用: **Providers → [Provider] → Custom Models**。

注意事項:

- OpenRouter および OpenAI/Anthropic 互換プロバイダーは、**Available Models** からのみ管理されます。手動追加、インポート、自動同期はすべて同じ利用可能モデルリストに登録されるため、これらのプロバイダーには個別の Custom Models セクションはありません。
- **Custom Models** セクションは、管理された利用可能モデルのインポートを公開していないプロバイダー向けです。

### カスタム OpenAI 互換プロバイダー

OpenAI API を話すゲートウェイ（セルフホストプロキシ、vLLM、サードパーティアグリゲーター）であれば、
独自のプロバイダーノードとして追加できます:

1. **Providers → Add OpenAI Compatible**。
2. **Name**: ノードの表示ラベル。
3. **Prefix**: ルーティング名。クライアントは `<prefix>/<model>` としてモデルを呼び出すため、
   プレフィックスが `mygw` のノードは `mygw/gpt-4o-mini` を提供します。必須。文字制限はありません。
4. **API Type**: ゲートウェイが提供するエンドポイントファミリー（Chat Completions、Responses、
   Embeddings、オーディオ、画像）。
5. **Base URL**: `/v1` を含むまでの API ルート（例:
   `https://gateway.example.com/v1`）であり、`/chat/completions` までの完全なパスではありません。
   非標準のパスを持つゲートウェイは、**Advanced Settings**（チャットパス、モデルパス）で設定します。
6. **API Key (for Check)** フィールドは接続のテストのみを行います。ノードを作成した後、
   それを開き、**Add Connection** を使用してリクエストが使用するキーを保存します。

ノードには `openai-compatible-<apiType>-<uuid>` 形式の内部 ID が付与されます。これを入力する
必要はありません。プレフィックスが公開名です。

#### 予約済みプレフィックス

プレフィックスには、組み込みプロバイダーの ID またはエイリアス（例: `openai`、`cf`）、および
廃止されたプロバイダーの ID は使用できません。モデルリゾルバーはカスタムノードより先に組み込みの
ID とエイリアスをチェックするため、これらのプレフィックスを使用するノードはトラフィックを
受け取ることがありません。`<prefix>/model` は組み込みプロバイダーにルーティングされるか、
そのプロバイダーが廃止されている場合はフェイルクローズします。このようなプレフィックスで
ノードを作成または編集すると、次のように拒否されます:

```text
prefix: "<prefix>" is a reserved provider prefix — choose a different prefix (reserved ids/aliases cannot be used for custom nodes because requests like <prefix>/model route to a built-in provider or fail closed when retired)
```

一意のプレフィックス（`mygw`、`acme-proxy` など）を選択してください。カスタムノードへのリクエストが、
組み込みプロバイダーまたはその認証情報を指名するエラーで失敗する場合は、ノードのプレフィックスが
予約済みかどうかを確認してください。このルールが存在する前に保存されたノードは引き続き保存されて
いますが、そのプレフィックスは組み込みプロバイダーにルーティングされます。ノードを編集して
新しいプレフィックスを付けてください。

#### 接続ごとのゲートウェイオプション

これらのキーは接続の `providerSpecificData` に設定します（例:
`PUT /api/providers/{id}` 経由）:

- `toolNameMaxLength`（整数、1–1024）— 長いツール名を拒否するゲートウェイを持つ
  OpenAI チャット形式互換接続向け。長い名前は短いエイリアスとして送信され、
  レスポンスで復元されます。
- `quotaEndpoint` — ゲートウェイのクォータ/クレジットエンドポイント。ダッシュボードの
  クォータストリップとクォータ対応ルーティングで読み取られます。OpenAI 互換および
  Anthropic 互換の両方の接続で動作します。完全な形式は
  `open-sse/services/usage/openaiCompatible.ts` に記載されています。

```json
{
  "toolNameMaxLength": 64,
  "quotaEndpoint": {
    "url": "https://gateway.example.com/key/info",
    "auth": "bearer",
    "quotas": {
      "budget": { "used": "$.info.spend", "total": "$.info.max_budget", "currency": "USD" }
    }
  }
}
```

### OmniRoute ピアのチェーン接続

別の OmniRoute ゲートウェイを **Custom OpenAI-compatible** プロバイダーとして追加できます。
ピアの `/v1` ベース URL と、そのピアが発行した専用の最小権限 API キーを使用してください。

相互またはマルチホップチェーンの場合は、すべてのゲートウェイでオプトインのループガードを
有効にしてください:

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

明示的に許可リストに登録されたピア URL に送信されたリクエストのみが
`X-OmniRoute-Peer-Trace` ヘッダーを受け取ります。ゲートウェイは、重複したインスタンス ID
または枯渇したホップバジェットを HTTP `508 Loop Detected` で拒否します。通常のアップストリーム
プロバイダーはピアメタデータを受け取りません。

ピアチェーンはデータベースレプリケーションやホストフェイルオーバーではありません。各ゲートウェイは
独立した SQLite の状態、キャッシュ、レートカウンター、セッションを保持します。アクティブ/パッシブ
またはアクティブ/アクティブの可用性には、ヘルスチェック付きリバースプロキシまたはクライアント
フェイルオーバーを使用し、1 つの SQLite データベースを複数の実行中の OmniRoute インスタンスに
マウントしないでください。

### Cloudflare Quick Tunnel

- Docker およびその他のセルフホスト環境では、**Dashboard → Endpoints** で利用可能
- 現在の OpenAI 互換 `/v1` エンドポイントに転送する一時的な `https://*.trycloudflare.com` URL を作成します
- 初回の有効化時には必要な場合のみ `cloudflared` をインストールし、以降の再起動では同じ管理バイナリを再利用します
- Quick Tunnel は OmniRoute またはコンテナの再起動後に自動復元されません。必要に応じてダッシュボードから再有効化してください
- トンネル URL は一時的なもので、トンネルを停止/開始するたびに変わります
- 管理対象の Quick Tunnel は、制約のあるコンテナで煩雑な QUIC UDP バッファ警告を避けるため、デフォルトで HTTP/2 トランスポートを使用します
- 管理対象のトランスポート選択を上書きしたい場合は、`CLOUDFLARED_PROTOCOL=quic` または `auto` を設定してください
- 管理対象のダウンロードではなく、プリインストールされた `cloudflared` バイナリを使用したい場合は、`CLOUDFLARED_BIN` を設定してください
- Cloudflare Quick Tunnel、Tailscale Funnel、ngrok Tunnel の各パネルは、**Settings → Appearance** で表示/非表示を切り替えられます。パネルを非表示にしても、実行中のトンネルは停止しません。

### LLM ゲートウェイインテリジェンス（フェーズ 9）

- **セマンティックキャッシュ** — 非ストリーミングかつ temperature=0 のレスポンスを自動キャッシュします（`X-OmniRoute-No-Cache: true` でバイパス可能）
- **リクエストの冪等性** — `Idempotency-Key` または `X-Request-Id` ヘッダーにより、5 秒以内のリクエストを重複排除します
- **進捗トラッキング** — `X-OmniRoute-Progress: true` ヘッダーでオプトインすると、SSE の `event: progress` イベントを受け取れます

### ルーティング戦略

**Dashboard → Settings → Routing** で設定します。ダッシュボードでは最もよく使われる 6 つの戦略を公開しています。コンボとオートルーターは内部的により広いセットをサポートしています。

**ダッシュボードに表示される戦略（アカウントレベルのルーティング）:**

| 戦略                           | 説明                                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| **Fill First**                 | 優先順位順にアカウントを使用します — プライマリアカウントが利用不可になるまですべてのリクエストを処理します  |
| **Round Robin**                | 設定可能なスティッキー制限（デフォルト: アカウントあたり 3 コール）で全アカウントを巡回します                |
| **P2C (Power of Two Choices)** | ランダムに 2 つのアカウントを選び、より健全な方へルーティングします — ヘルス状態を考慮しつつ負荷を分散します |
| **Random**                     | Fisher-Yates シャッフルを使用して、リクエストごとにアカウントをランダムに選択します                          |
| **Least Used**                 | `lastUsedAt` タイムスタンプが最も古いアカウントへルーティングし、トラフィックを均等に分散します              |
| **Cost Optimized**             | priority 値が最も低いアカウントへルーティングし、最も低コストのプロバイダーに最適化します                    |

**高度なコンボおよび自動戦略**（コンボごと、または `auto/*` プレフィックスで設定可能 — [AUTO-COMBO.md](../routing/AUTO-COMBO.md) を参照）:

- `priority` — 厳密な順序。ラウンドロビンは行いません
- `weighted` — モデルごとの重みに比例してトラフィックを分割します
- `fill-first` — 制限に達するまで最初のモデルを使い切ります
- `round-robin` / `strict-random` / `random`
- `p2c`（Power of Two Choices）
- `least-used` および `cost-optimized`
- `auto` — すべての候補に対してスコア駆動で選択します
- `lkgp`（Last Known Good Provider）— 最後に成功したプロバイダーに固定し、その後ルールにフォールバックします
- `context-optimized` — 空きコンテキストウィンドウが最も大きいモデルを選択します
- `context-relay` — フォローアップターン用に長コンテキストモデルを連鎖させます

### レジリエンスとサーキットブレーカー

**Dashboard → Settings → Resilience** から設定します。

OmniRouteは、5つのコンポーネントでプロバイダーレベルのレジリエンスを実装しています:

1. **Request Queue & Pacing** — システムレベルのリクエストシェイピング:
   - **Requests Per Minute (RPM)** — アカウントあたりの1分間の最大リクエスト数
   - **Min Time Between Requests** — リクエスト間の最小間隔(ミリ秒)
   - **Max Concurrent Requests** — アカウントあたりの最大同時リクエスト数

2. **Connection Cooldown** — リトライ可能な失敗の後、単一接続に適用される認証タイプごとの設定:
   - **Base Cooldown** — リトライ可能なアップストリーム障害に対するデフォルトのクールダウン期間
   - **Use Upstream Retry Hints** — 提供されている場合、権威ある `Retry-After` やリセットヒントを尊重します
   - **Max Backoff Steps** — 繰り返しの失敗に対する指数バックオフの最大レベル

3. **Provider Circuit Breaker** — エンドツーエンドのプロバイダー障害を追跡し、設定された警告しきい値でプロバイダーを degraded(低下)としてマークし、設定された障害しきい値に達するとブレーカーを開きます:
   - **Degradation Threshold** — `DEGRADED` 状態に入るまでの連続プロバイダー障害回数
   - **Failure Threshold** — `OPEN` 状態に入るまでの連続プロバイダー障害回数
   - **Reset Timeout** — プロバイダーが再度テストされるまでの時間枠
   - **CLOSED**(正常) — リクエストが正常に流れます
   - **DEGRADED** — 障害の増加が追跡されている間もリクエストは流れ続けます
   - **OPEN** — 繰り返しの障害の後、プロバイダーが一時的にブロックされます
   - **HALF_OPEN** — プロバイダーが回復したかどうかをテスト中

   接続スコープの `429` レート制限は **Connection Cooldown** に留まり、プロバイダーブレーカーにはカウントされません。

   プロバイダーブレーカーのランタイム状態は **Dashboard → Health** にのみ表示されます。

4. **Wait For Cooldown** — すべての候補接続がすでにクールダウン中の場合、OmniRouteは最も早く終了するクールダウンを待機し、同じクライアントリクエストを自動的にリトライできます。

5. **Rate Limit Auto-Detection** — アップストリームプロバイダーが明示的な待機期間を返す場合、この設定が有効であれば、それらのヒントがローカルの接続クールダウンを上書きします。

**プロのヒント:** 障害発生後は **Health** ページを使用して、稼働中のプロバイダーブレーカーを検査・リセットしてください。Resilienceページは設定の変更のみを行います。

### データベースのエクスポート / インポート

**Dashboard → Settings → System & Storage** でデータベースバックアップを管理します。

| アクション               | 説明                                                                                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Export Database**      | 現在のSQLiteデータベースを `.sqlite` ファイルとしてダウンロードします                                                                                                            |

- マシン間でOmniRouteを移行する
- 災害復旧用の外部バックアップを作成する

### コンボの負荷分散戦略

**ダッシュボード → コンボ → 作成/編集 → 戦略** でコンボごとの負荷分散を設定します。

| 戦略               | 説明                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- |
| **Round-Robin**    | モデルを順番にローテーションします                                                 |
| **Priority**       | 常に最初のモデルを試行し、エラー時のみフォールバックします                         |
| **Random**         | リクエストごとにコンボからランダムにモデルを選択します                             |
| **Weighted**       | モデルごとに割り当てられた重みに基づいて比例的にルーティングします                 |
| **Least-Used**     | 直近のリクエスト数が最も少ないモデルにルーティングします（コンボメトリクスを使用） |
| **Cost-Optimized** | 利用可能な最も安価なモデルにルーティングします（料金テーブルを使用）               |

グローバルなコンボのデフォルトは **ダッシュボード → 設定 → ルーティング → コンボのデフォルト** で設定できます。
コンボターゲットのタイムアウトは、デフォルトでは現在のリクエストタイムアウトを継承します。ターゲットごとの
短い制限でより速いフォールバックをトリガーしたい場合のみ、コンボのデフォルトまたは個別のコンボで
**ターゲットタイムアウト（秒）** を使用してください。

ゼロレイテンシーのコンボ最適化はオプトインです。**ゼロレイテンシー最適化** を無効のままにすると、
これらのレイテンシー機能がフォールバックターゲットと競合したり、TTFT 履歴に基づいてターゲットを
スキップしたり、フォールバックリクエストを圧縮したりするのを防げます。有効にすると、設定されたヘッジング、
予測 TTFT スキップ、プロアクティブなフォールバック圧縮が、ルーティング/リクエストの忠実性と引き換えに
テールレイテンシーを低減します。

上流プロバイダーが厳密な `max_tokens` / `maxOutputTokens` 制限を要求する場合は、**推論トークンバッファ（Reasoning token buffer）** を無効にしてください。有効になっている場合、コンボルーティングは既知の出力上限を持つモデルにのみ推論モデルのヘッドルームを追加し、安全なバッファ値がその上限を超えてしまう場合はクライアントのトークン制限を変更しません。クライアントの制限がすでに既知の上限を超えている場合、OmniRoute は上流リクエストを送信する前にその上限までクランプします。

## 🤖 自動ルーティング（設定不要）

OmniRoute には、接続されたすべてのプロバイダーから各リクエストに最適なモデルを選択する、**スコア駆動型の自動ルーター**が搭載されています。管理が必要なコンボはありません。`auto/*` プレフィックスのいずれかを指定してリクエストを送信するだけで、OmniRoute がその場で仮想コンボを構築し、レイテンシ、コスト、成功率、コンテキスト適合度、タスクに対するモデルの適性、直近の失敗、クォータ、サーキットブレーカーの状態に基づいて候補をスコアリングします。

| プレフィックス | 最適化対象                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| `auto`         | バランスの取れたデフォルト（レイテンシ × コスト × 成功率）                                           |
| `auto/coding`  | コーディングタスク：Claude、GPT-5、GLM、Kimi、Qwen Coder、DeepSeek のコーディングモデルを優先        |
| `auto/cheap`   | 最低の $/token。レイテンシの増加を許容                                                               |
| `auto/fast`    | 最低レイテンシ。コストは無視                                                                         |
| `auto/offline` | ローカル専用プロバイダー（Ollama、vLLM、llama.cpp）。エアギャップ環境に有用                          |
| `auto/smart`   | 推論品質を最優先（Opus、GPT-5 xhigh、R1、GLM 5.1 reasoning）                                         |
| `auto/lkgp`    | 「最後に正常動作したプロバイダー」— 最後に成功したプロバイダーに固定し、その後ルールへフォールバック |

例：

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer $OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto/coding",
    "messages": [{ "role": "user", "content": "この Python 関数をリファクタリングしてください" }],
    "stream": true
  }'
```

自動ルーターの詳細については、[AUTO-COMBO.md](../routing/AUTO-COMBO.md) を参照してください。スコアリングの重みの調整方法、プロバイダーをブラックリストに登録する方法、**ダッシュボード → Auto Combo** でルーティング判断を確認する方法などが記載されています。

## 🔌 MCP と A2A の統合

OmniRoute は、**MCP サーバー**（Model Context Protocol）であると同時に、**A2A サーバー**（Agent-to-Agent JSON-RPC 2.0）でもあります。MCP 互換の IDE またはエージェントホストから OmniRoute のツールを直接呼び出せます。追加のラッパーは必要ありません。

### MCP トランスポート

- **SSE**：`http://localhost:20128/api/mcp/sse`
- **ストリーム対応 HTTP**：`http://localhost:20128/api/mcp/stream`
- **stdio**：`omniroute --mcp`（stdio を使用する IDE プラグイン向け）

### Claude Desktop への接続

macOS では `~/Library/Application Support/Claude/claude_desktop_config.json` を、Windows/Linux では対応するファイルを編集します：

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### Cursor / Continue / VS Code MCP への接続

SSE URL `http://localhost:20128/api/mcp/sse` と、**ダッシュボード → API Keys** で生成した Bearer API キーを使用します。

### スコープ

MCP では現在、名前付きスコープが 32 個定義されています。各 Bearer キーは特定のスコープのみに制限できます。正式なスコープとツールの一覧については [MCP-SERVER.md](../frameworks/MCP-SERVER.md) を、JSON-RPC スキーマについては [A2A-SERVER.md](../frameworks/A2A-SERVER.md) を参照してください。

## 💾 メモリシステム

OmniRoute は、ハイブリッド検索を使用して**長期的な会話メモリ**を永続化します。

## 🔔 Webhook

## 💻 内部 CLI

OmniRoute には、セットアップ、診断、ランタイム制御用の内部 CLI（`omniroute …`）が付属しています。これは、サードパーティー製 CLI（Claude Code、Cursor、Codex、Cline など）が OmniRoute と通信できるように設定する、ダッシュボードの「CLI ツール」ページとは**別のものです**。

```bash
omniroute setup                    # 対話形式のウィザード（パスワード、プロバイダー、コンボ）
omniroute setup --non-interactive  # CI 向け
omniroute doctor                   # ヘルス診断（データディレクトリ、DB、プロバイダー、ポート）
omniroute providers available      # サポートされているプロバイダーを一覧表示
omniroute providers list           # 設定済みの接続を一覧表示
omniroute providers test <id>      # プロバイダー接続をリアルタイムでテスト
omniroute combos list              # コンボを一覧表示
omniroute combos switch <name>     # デフォルトのコンボを設定
omniroute models                   # 利用可能なモデルを一覧表示（--json、--search）
omniroute keys add | list | remove # ターミナルから API キーを管理
omniroute backup                   # 設定と DB のスナップショットを作成
omniroute restore [<timestamp>]    # スナップショットから復元
omniroute health                   # 詳細なヘルス情報（ブレーカー、キャッシュ、メモリ）
omniroute quota                    # プロバイダーのクォータ使用量
omniroute mcp status               # MCP サーバーのステータス
omniroute a2a status               # A2A サーバーのステータス
omniroute tunnel list|create|stop  # Cloudflare/Tailscale/ngrok トンネル
omniroute reset-password           # 管理者パスワードをリセット
omniroute --mcp                    # stdio 経由で MCP サーバーを起動
omniroute --port 3000              # カスタムポートでサーバーを起動
```

ヒント: `omniroute doctor --json` を監視ツールと組み合わせることで、プロバイダー接続に問題がある場合にアラートを発行できます。

## 🖥️ デスクトップアプリケーション（Electron）

OmniRoute は、Windows、macOS、Linux 向けのネイティブデスクトップアプリケーションとして利用できます。

### インストール

```bash
# electron ディレクトリから実行:
cd electron
npm install

# 開発モード（実行中の Next.js 開発サーバーに接続）:
npm run dev

# 本番モード（スタンドアロンビルドを使用）:
npm start
```

### インストーラーのビルド

```bash
cd electron
npm run build          # 現在のプラットフォーム
npm run build:win      # Windows（.exe NSIS）
npm run build:mac      # macOS（.dmg ユニバーサル）
npm run build:linux    # Linux（.AppImage）
```

出力先 → `electron/dist-electron/`

### 主な機能

| 機能                               | 説明                                                           |
| ---------------------------------- | -------------------------------------------------------------- |
| **サーバーの準備状態**             | ウィンドウを表示する前にサーバーをポーリング（空白画面を防止） |
| **システムトレイ**                 | トレイへの最小化、ポート変更、トレイメニューからの終了         |
| **ポート管理**                     | トレイからサーバーポートを変更（サーバーを自動再起動）         |
| **コンテンツセキュリティポリシー** | セッションヘッダーによる制限的な CSP                           |
| **単一インスタンス**               | 一度に実行できるアプリインスタンスは 1 つのみ                  |
| **オフラインモード**               | 同梱の Next.js サーバーはインターネット接続なしで動作          |

### 環境変数

| 変数                  | デフォルト | 説明                                 |
| --------------------- | ---------- | ------------------------------------ |
| `OMNIROUTE_PORT`      | `20128`    | サーバーポート                       |
| `OMNIROUTE_MEMORY_MB` | `512`      | Node.js のヒープ上限（64～16384 MB） |
