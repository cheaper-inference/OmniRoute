> **要約**: OmniRoute はすべてのリクエストのトークン使用量を追跡し、コストを計算し、API キーごとのクォータを適用して、ダッシュボードに分析結果を表示します。このガイドでは、その仕組み全体を説明します。

**ソース:**

- `open-sse/services/usage.ts`（約70KB）— 使用量追跡のメイン処理
- `src/lib/usageAnalytics.ts`（約10KB）— ダッシュボード向けの集計
- `src/lib/db/quotaSnapshots.ts` — クォータの履歴データ
- `src/lib/db/usage*.ts` — 使用量に関連する複数の DB モジュール

## 概要

OmniRoute を経由するすべてのリクエストについて、次の情報を記録する**使用量レコード**が生成されます。

- **識別情報**: API キー、プロバイダー、モデル、コンボ
- **トークン**: プロンプトトークン、完了トークン、キャッシュ済みトークン、合計
- **コスト**: USD 金額（料金データから計算）
- **タイミング**: レイテンシ、開始／終了タイムスタンプ
- **ステータス**: 成功、エラー、レート制限、その他

これらのレコードは**分析データ**に集計され、**クォータスナップショット**として永続化され、**キーごとの予算上限**を適用するために使用されます。

```
リクエスト ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                      │
                              ┌───────┼───────┐
                              ▼       ▼       ▼
                            分析   クォータ  請求
                     （ダッシュボード）（適用）（エクスポート）
```

## 記録される内容

`usage.ts` サービスは、リクエストごとに**使用量イベント**を記録します。

| フィールド         | 型      | 取得元                                                               |
| ------------------ | ------- | -------------------------------------------------------------------- |
| `id`               | string  | 記録時に生成される UUID                                              |
| `apiKeyId`         | string  | リクエストを開始した API キー                                        |
| `provider`         | string  | プロバイダー ID（openai、anthropic など）                            |
| `model`            | string  | モデル ID（gpt-5、claude-opus-4-6 など）                             |
| `comboId`          | string? | コンボ経由でルーティングされた場合のコンボ ID                        |
| `promptTokens`     | number  | 上流レスポンスから取得                                               |
| `completionTokens` | number  | 上流レスポンスから取得                                               |
| `cachedTokens`     | number  | キャッシュヒットしたトークン（Anthropic のプロンプトキャッシュなど） |
| `totalTokens`      | number  | プロンプト + 補完                                                    |
| `costUsd`          | number  | 料金データから算出                                                   |
| `latencyMs`        | number  | リクエストのエンドツーエンド所要時間                                 |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`           |
| `errorClass`       | string? | ステータスが success 以外の場合のエラークラス                        |
| `timestamp`        | string  | ISO 8601 UTC                                                         |
| `metadata`         | object  | プラグインが挿入するカスタムデータ                                   |

### トークン数の取得元

トークン数は、**レスポンスハンドラー**で上流プロバイダーのレスポンスから抽出されます。

```ts
// open-sse/handlers/chatCore.ts より
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

使用量を返さないプロバイダー（一部の Web Cookie プロバイダー）については、OmniRoute は `~4 chars per token` という経験則を使ってトークン数を**推定**します（`open-sse/services/autoCombo/pipelineRouter.ts` を参照）。

### キャッシュ済みトークン

OmniRoute は、次の理由から `cached_tokens` を `prompt_tokens` とは別に追跡します。

- Anthropic のプロンプトキャッシュでは、キャッシュ済みトークンに割引料金（通常の 10%）が適用されます
- 一部のプロバイダーは、異なる料金を適用すべき `cache_read_input_tokens` を返します
- 分析では、**キャッシュヒット率** = `cached_tokens / prompt_tokens` を表示できます

### キャッシュ書き込み階層の診断

分析ダッシュボードのプロンプトキャッシュ健全性パネルは、プロバイダーが報告する
5 分間と 1 時間のキャッシュ書き込みを区別します。Anthropic の
`usage.cache_creation.ephemeral_5m_input_tokens` と
`usage.cache_creation.ephemeral_1h_input_tokens` は、ストリーミングおよび
非ストリーミングの使用量変換を通じて保持され、呼び出しログのサマリーとともに保存されます。合算された
キャッシュ書き込み総数が、これらの区分に重複して加算されることはありません。

古いレコードを含め、合算された書き込みカウンターしかない呼び出しの階層は不明とされます。
内訳が一部しかない場合、未割り当ての残りは不明のまま保持されます。無効なカウンターや
矛盾するカウンターには、黙って TTL を割り当てるのではなく、フラグが付けられます。リクエスト側の
TTL マーカーは、課金対象の階層を示す根拠にはなりません。

このパネルの API 換算の書き込み見積もりは、報告済みで料金が設定されている階層のみを対象とし、
リクエスト全体を対象とするものではありません。ネイティブの Claude/Anthropic モデルの料金では、
5 分間の書き込みには入力単価の 1.25 倍、1 時間の書き込みには入力単価の 2 倍を使用します。料金が
欠けている場合はゼロではなく、利用不可として扱われます。料金は新しい呼び出しが記録されるたびに取得され、
過去のレコードの料金は再計算されません。そのため、サブスクリプションアカウントでは、
API 換算の見積もりが表示されても、その金額が実際の支出やサブスクリプションの
クォータ消費として発生するとは限りません。既存のクォータ、予算、およびプロバイダーの正確な料金に基づくコスト計算は変更されません。

これらの診断では、既存の範囲が制限されたキャッシュ健全性サマリーと呼び出しログの
保持機能を使用します。リクエストのデフォルト TTL、ルーティング、アカウント選択は変更しません。
プロバイダーへの送信境界で、クライアントが要求した TTL と実際の送信 TTL を
記録する対応は見送られています。このパネルは、実際の送信 TTL ではなく、受領した使用量情報の階層を報告します。

実装: `src/lib/usage/cacheWriteEstimate.ts`、
`src/lib/usage/cacheHealth.ts`、および `open-sse/utils/cacheWriteUsage.ts`。

## コスト計算

コストは、LiteLLM から同期された**料金データ**（`src/lib/pricingSync.ts`）に基づいて計算されます。

| モデル            | 入力 $/1M | 出力 $/1M | キャッシュ $/1M |
| ----------------- | --------- | --------- | --------------- |
| gpt-5             | $2.50     | $10.00    | —               |
| claude-opus-4-6   | $15.00    | $75.00    | $1.50           |
| claude-sonnet-4-5 | $3.00     | $15.00    | $0.30           |
| gemini-2.5-pro    | $1.25     | $10.00    | —               |

コスト計算式（`src/lib/usage/costCalculator.ts`）：

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **プロンプトからキャッシュ分を差し引く理由は？** キャッシュされた部分には別の料金が適用されるため、プロンプト全体に入力料金を課すと重複して計上されます。

### 料金同期

料金データは、`/api/pricing/sync` エンドポイントを介して LiteLLM から自動同期されます（ユーザー向けの環境変数ではなく、組み込みの cron タスクによって実行されます）。

```bash
# 手動実行
curl -X POST http://localhost:20128/api/pricing/sync
```

料金データが存在しないモデルについては、OmniRoute は内部の平均料金（LiteLLM の料金データを基に算出）を使用した**コスト推定**にフォールバックします。

## 日付範囲の集計

`usageAnalytics.ts` モジュールは、生の使用量データからダッシュボードウィジェットを算出します。7 つの期間に対応しています。

| 期間     | 対象期間                     | 用途                       |
| -------- | ---------------------------- | -------------------------- |
| `1d`     | 直近 24 時間                 | 時間単位のコスト急増の検出 |
| `7d`     | 直近 7 日間                  | 週次レビュー               |
| `30d`    | 直近 30 日間                 | 月次請求                   |
| `90d`    | 直近 90 日間                 | 四半期分析                 |
| `ytd`    | 今年の 1 月 1 日以降         | 年間予算の追跡             |
| `all`    | 全期間                       | 累計統計                   |
| `custom` | ユーザー定義の開始日と終了日 | 監査、アドホッククエリ     |

### 算出されるダッシュボードウィジェット

どの日付範囲でも、分析レイヤーは以下を算出します。

| ウィジェット                   | 説明                                                      |
| ------------------------------ | --------------------------------------------------------- |
| **サマリーカード**             | 総リクエスト数、総コスト、総トークン数、成功率            |
| **日次推移チャート**           | モデル別に積み上げ表示した 1 日あたりのコストとトークン数 |
| **アクティビティヒートマップ** | 時間帯 × 曜日のグリッド、色 = リクエスト数                |
| **モデル別内訳**               | モデル別コストの円グラフ                                  |
| **プロバイダー別内訳**         | プロバイダー別リクエスト数の棒グラフ                      |
| **上位 API キー**              | コスト上位 10 キーの表                                    |
| **エラー分析**                 | エラー率の経時変化、主なエラークラス                      |

### プログラムからのアクセス

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // 使用履歴レコード
  "7d",                 // 期間: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // プロバイダー接続マップ (connectionId → アカウント名)
  {
    startDate: "2025-01-01",  // 任意: "custom" 期間用
    endDate: "2025-06-01",   // 任意: "custom" 期間用
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (セント)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## クォータの適用

API キーごとのクォータは、次の 2 か所で適用されます。

1. **ソフトリミット** (`quotaWarnAt`): 使用量がしきい値を超えるとダッシュボードに警告を表示
2. **ハードリミット** (`quotaLimit`): 超過すると HTTP 429 でリクエストを拒否

### 設定

```ts
// API キーごと
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — 警告を表示
  quotaLimit: 10_00,    // $10.00 — 強制停止
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### 適用フロー

```
リクエスト ──▶ quotaCheck()
              │
              ├── 上限内?  ──▶ 許可
              │
              └── 上限超過?  ──▶ 429 Too Many Requests
                                   Retry-After ヘッダー付き
```

### クォータのスナップショット

`quotaSnapshots` テーブルは、傾向分析のために**過去のクォータ状態**を保存します。

| フィールド | 説明 |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | 追跡対象のキー |
| `window` | "day" | "week" | "month" |
| `used` | この期間内に使用したコスト (セント) |
| `limit` | 上限 (セント) |
| `resetAt` | 期間がリセットされる日時 |
| `createdAt` | スナップショットが取得された日時 |

スナップショットは、コストが 0 を超える**すべてのリクエストで**取得され、次の目的に使用されます。

- ダッシュボードにクォータの進捗バーを表示
- 30 日間のクォータ推移チャートを表示
- 使用量が上限に近づいたときにアラートを発報

## 保持とクリーンアップ

使用状況データは、リクエストごとに約 1～10KB 増加します。大規模な運用では、これがかなりの量になる可能性があります。

### 保持設定

使用状況履歴の保持期間は、UI のデータベース設定、または `/api/settings/database` 経由で設定します。

デフォルトでは、使用状況履歴は **90 日間**保持されます。

### クリーンアップ

古いレコードは `src/lib/db/cleanup.ts` によってクリーンアップされます:

- バックグラウンドの cron プロセスによって実行されます
- `usage_history` から、設定された `usageHistory` の保持期間を超えたレコードを削除します

### ストレージ容量の見積もり

| リクエスト頻度        | 30 日間のストレージ容量 | 90 日間のストレージ容量 |
| --------------------- | ----------------------- | ----------------------- |
| 100 リクエスト/日     | 約3MB                   | 約9MB                   |
| 1,000 リクエスト/日   | 約30MB                  | 約90MB                  |
| 10,000 リクエスト/日  | 約300MB                 | 約900MB                 |
| 100,000 リクエスト/日 | 約3GB                   | 約9GB                   |

トラフィックが非常に多い場合は、次の対応を検討してください:

- データベース設定で保持期間を短縮する
- 生のレコードの代わりに `aggregated_metrics` を使用する（分析用途のみ）

## コスト最適化のヒント

### 1. 適切なモデルを使う

```bash
# 素早い回答 — 安価で高速なモデルを使用
curl -d '{"model":"auto/fast","messages":[...]}'

# 複雑なタスク — 品質重視のモデルを使用
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. キャッシュを有効にする

Anthropicのプロンプトキャッシュは、**繰り返し使用するコンテキストのコストを90%削減**します：

```ts
// キャッシュは自動で行われます — 同じ大きなシステムプロンプトを含めるだけです
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // 自動的にキャッシュされます
  messages: [{ role: "user", content: "..." }],
});
```

### 3. 圧縮を使う

RTK + Caveman圧縮は、**ツールを多用するセッションのコストを15-95%削減**します：

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. キーごとのクォータを設定する

コストの暴走を防ぐため、必ず`quotaLimit`を設定してください：

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // 月額上限10ドル
```

### 5. 使用量の多い利用元を監査する

ダッシュボードまたは**`/api/usage/analytics`**を使い、APIキーごとにグループ化してコスト順に並べ替えます：

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## トラブルシューティング

### 「コストが予想より高い」

1. **`/api/usage/analytics?groupBy=model`**を確認 — コストの高いモデルを特定します
2. **`/api/usage/analytics?groupBy=apiKey`**を確認 — 使用量の多い利用元を特定します
3. 料金データが最新であることを確認：`POST /api/pricing/sync`

### 「レコードが見つからない」

- ダッシュボード → データベース → クリーンアップでDBの保持設定を確認してください — 古いレコードは定期クリーンアップタスク（`src/lib/db/cleanup.ts`）によって削除されます
- `src/lib/db/usage*.ts`でエラーを確認してください — DBへの書き込み失敗はログに記録されますが、表には表示されません
- リクエストが実際に`chatCore`に到達したことを確認してください — コンボルーティングを確認します

### 「クォータが適用されない」

- キーの`quotaLimit`設定を確認してください
- `quotaWindow`が正しく設定されていることを確認してください
- `quotaSnapshots`レコードを探してください — リクエストごとに作成されるはずです
