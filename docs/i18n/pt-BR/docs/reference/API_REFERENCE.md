## Conclusões de Chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

| ------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `x-omniroute-no-memory`  | Solicitação | Defina como `true` para ignorar a injeção de memória + habilidades nesta solicitação (espelha no-cache; evita a sobrecarga de tokens/custo por chamada)                                                                           |
| `X-OmniRoute-Progress`   | Solicitação | Defina como `true` para eventos de progresso                                                                                                                                                                                      |
| `X-Session-Id`           | Solicitação | Chave de sessão persistente para afinidade de sessão externa                                                                                                                                                                      |
| `x_session_id`           | Solicitação | A variante com sublinhado também é aceita (HTTP direto)                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | Solicitação | Tag de sessão/conversa fornecida pelo chamador (também alimenta a memória). Quando presente, é persistida literalmente em `call_logs.session_tag` para atribuição de custos por sessão (#8249) — nunca sintetizada quando ausente |
| `Idempotency-Key`        | Solicitação | Chave de deduplicação (janela de 5s)                                                                                                                                                                                              |

| `x-omniroute-connection` | Solicitação | Fixa uma solicitação de modelo único a uma conexão de provedor (conta) por seu ID — consulte [Fixação de conta por solicitação](#account-pinning-per-request)                                                                     |
| `X-OmniRoute-Cache`      | Resposta    | `HIT` ou `MISS` (sem streaming)                                                                                                                                                                                                   |

#### Fixação de conta por solicitação

Quando um provedor tem várias conexões (contas ou chaves), o OmniRoute normalmente escolhe uma
por meio de sua estratégia de seleção de contas. Em vez disso, uma solicitação pode fixar uma conexão específica
com o cabeçalho `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Onde encontrar o id.** Abra a página do provedor no dashboard
  (**Dashboard → Providers → <provider>**) e clique no chip de id `xxxxxxxx…` em uma linha de
  conexão — isso copia o id completo da conexão.
- **Quais solicitações o respeitam.** Solicitações de modelo único (`provider/model`) em
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. As combinações ignoram o cabeçalho:
  fixe uma conta por etapa da combinação usando a própria conexão da etapa.
- **A fixação é estrita, não uma preferência.** A conexão fixada é usada exclusivamente. Uma
  falha durante a solicitação registra o cooldown da conta, mas **não** alterna para uma conta
  irmã do mesmo provedor.
- **Cooldown e cota liberam a fixação.** Enquanto a conexão fixada estiver em cooldown,
  com a cota esgotada ou bloqueada por uma política de cota, as solicitações posteriores recorrem
  às outras conexões do provedor, exatamente como o tráfego não fixado.
- **Ids desconhecidos ou desativados falham.** Um id que não esteja no pool ativo do provedor
  (excluído, desativado ou pertencente a outro provedor) não deixa nenhuma conta elegível, portanto
  a solicitação falha em vez de ser roteada silenciosamente para outro local.

O Claude Code envia cabeçalhos personalizados por meio de `ANTHROPIC_CUSTOM_HEADERS`. Coloque-o no bloco
`env` de `~/.claude/settings.json` ou em um `.claude/settings.json` no nível do projeto para fixar uma
conta diferente por projeto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fonte: `src/sse/handlers/chat.ts` (leitura do cabeçalho), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (liberação da fixação e verificação de ausência no pool).

> **Cabeçalhos de telemetria de custo:** as respostas de sucesso sem streaming também carregam o conjunto de telemetria de custo `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 casas decimais fixas; `0.0000000000` para conteúdo gratuito/sem preço), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (somente quando > 0), além de `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Eles são emitidos por chat completions, `/v1/responses`, `/v1/messages` **e pelos endpoints de mídia** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (sempre com custo `0`). O custo de mídia é calculado por modalidade (por imagem, por segundo, por caractere, por unidade de pesquisa) quando houver informações de preço disponíveis; caso contrário, é `0` (fail-open).

> **Semântica do custo de acerto de cache:** em um HIT do cache semântico (`X-OmniRoute-Cache-Hit: true`), nenhuma chamada upstream é feita, portanto `X-OmniRoute-Response-Cost` é `0.0000000000` (o custo **incremental** de atender ao acerto). O custo original/que teria sido cobrado é informado separadamente em `X-OmniRoute-Cost-Saved`. Os consumidores de cobrança devem somar `X-OmniRoute-Response-Cost` (acertos não têm custo); as análises de cache podem agregar `X-OmniRoute-Cost-Saved`.

## Concessões Exclusivas de Sessão Gerenciada

A concessão exclusiva de sessão gerenciada é um contrato de roteamento opcional e neutro em relação ao cliente: um único proprietário ativo mantém uma conexão OmniRoute elegível. Ela não concede um modelo, não exige OAuth, não identifica um cliente específico nem exige um provedor específico.

A chave de API de autenticação deve ter o escopo `lease:exclusive` e uma lista `allowedConnections` explícita e não vazia. O limite de mutação do banco de dados impõe ambos os campos em conjunto na criação da chave e nas atualizações parciais.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

As respostas bem-sucedidas de aquisição, renovação e liberação expõem carimbos de data e hora, `state` e o `generation` positivo exato, mas nunca a conexão selecionada nem as credenciais. A renovação e a liberação fornecem o `generation` no corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Um proprietário de concessão ativo pode solicitar explicitamente metadados de exibição seguros para privacidade referentes à sua vinculação atual:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Essa ação de status opcional é protegida pelo proprietário opaco, pela chave de API gerenciada autenticada e pelo `generation` ativo exato em uma única transação do banco de dados. `displayName` é apenas o nome de conexão configurado e sem espaços nas extremidades; ele é `null` quando não existe um nome configurado seguro. O OmniRoute nunca substitui esse valor por um e-mail ou por uma identidade de conta gerada. O valor de `provider` é um rótulo de exibição não sensível e nunca um identificador de provedor compatível gerado. Credenciais, tokens, cookies, ids brutos de conexão ou de chave de API, hashes de proprietários, segredos de proteção e dados internos de roteamento são excluídos.

Consultas com chave incorreta, proprietário incorreto, geração obsoleta, inexistente, expirada, liberada ou invalidada retornam todas o mesmo erro `409 LEASE_FENCE_STALE`, sem metadados de conexão. Um cliente que recebeu a resposta de espera por capacidade não tem uma vinculação ativa para consultar. Quando o roteamento faz a transição de uma concessão ativa, o mesmo `generation` permanece válido e o status retorna atomicamente a nova vinculação, nunca a antiga. Os clientes existentes permanecem inalterados porque as respostas de aquisição, renovação, liberação e espera mantêm seus formatos anteriores.

Esse contrato do servidor não altera o `/status` padrão do OpenAI Codex. Atualmente, o Codex padrão informa seu provedor de modelo e o estado integrado de autenticação/conta, mas não renderiza metadados arbitrários de conta de provedores personalizados; uma integração futura do cliente deverá chamar essa ação e decidir como exibir `connection.displayName`.

Cada solicitação de inferência gerenciada então fornece ambos os cabeçalhos de controle:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

O proprietário exato, o `generation`, a conexão ativa e a chave de API autenticada são protegidos imediatamente antes de cada tentativa upstream compatível. Reutilizar o proprietário e o `generation` com outra chave falha mesmo quando essa chave permite a mesma conexão. Os proprietários brutos não são persistidos, registrados em logs, mantidos no instantâneo da solicitação nem encaminhados ao upstream.

A contenção temporária retorna HTTP `429` com `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Essa resposta significa apenas que o conjunto elegível comum não estava vazio e que todo candidato livre estava mantido por uma concessão ativa de terceiros. Modelos/provedores incompatíveis, incompatibilidade de política, período de espera, cota, integridade e outras falhas comuns de elegibilidade mantêm suas respostas existentes do OmniRoute.

### `x-omniroute-compression`

Substituição por solicitação do plano de compressão. Tem a precedência mais alta — supera a substituição da combinação de roteamento, o perfil ativo, o acionamento automático e o padrão do painel. Valores:

| Value         | Effect                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `off`         | Sem compressão para esta solicitação.                                                                                        |
| `default`     | O perfil padrão derivado do painel (ignora o perfil ativo). Os mecanismos com perdas permanecem desativados.                 |
| `safe`        | Apenas deduplicação e compactação de espaços em branco.                                                                      |
| `allow-lossy` | Mantém o plano do operador para esta solicitação, incluindo resumos e reescritas de estilo.                                  |
| `engine:<id>` | Um único mecanismo quando habilitado, por exemplo, `engine:rtk`. Ativação explícita por solicitação para esse mecanismo.     |
| `<combo>`     | Uma combinação nomeada, correspondida primeiro pelo nome (sem diferenciação entre maiúsculas e minúsculas) e depois pelo id. |

Observações:

- Valores desconhecidos são ignorados (a solicitação nunca é rejeitada); a resolução segue para a precedência normal do operador.
- Se várias combinações compartilharem um nome, passe o **id** da combinação para obter uma correspondência determinística.
- Uma combinação cujo nome seja `off` ou `default` não pode ser selecionada pelo nome (essas palavras-chave são interpretadas primeiro); referencie essa combinação pelo id.
- A chave mestre de compressão é um bloqueio rígido: quando a compressão está desabilitada globalmente, este cabeçalho não pode habilitá-la.

O plano aplicado é retornado no cabeçalho de resposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

onde `<source>` é um de `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ou `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Provedores disponíveis: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Os IDs de catálogo seguem o formato `provider/model` (exemplo: `jina-ai/jina-embeddings-v5-omni-small`). IDs de modelos Jina sem provedor que aparecem no registro (por exemplo, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) também são resolvidos. Os modelos de incorporação, reranking, classificação e segmentação da Jina usam primeiro as credenciais `jina-ai` do dashboard; `JINA_AI_API_KEY` é usado como fallback somente quando não existe uma chave no dashboard. O card `jina-reader` é exclusivo do Reader / `r.jina.ai` (`POST /v1/web/fetch`) e nunca fornece incorporações ou reranking.

Os modelos do registro que anunciam suporte multimodal também aceitam até 32 itens estruturados independentes do provedor. Os tipos de item de mídia são `text`, `image`, `audio`, `video` e `document`. A `source` da mídia pode ser `{"type":"url","url":"https://..."}` ou
`{"type":"base64","data":"...","media_type":"..."}`.

O Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
e o alias de família `jina-ai/jina-embeddings-v5-omni` → omni-small) também aceita a documentação nativa de EmbeddingsV5Request da Jina e a **encaminha intacta** para `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Os valores nativos `{ image | audio | video | pdf }` podem ser uma URL HTTPS pública, um URI `data:` ou
base64 bruto. O OmniRoute não converte esses objetos em strings nem busca URLs de imagens nativas — a Jina recupera a mídia pública por conta própria. Campos adicionais da Jina (`task`, `normalized`, `truncate`, `embedding_type`) são encaminhados. Os SKUs da Jina exclusivos para texto ainda rejeitam documentos que não sejam de texto.

Limites de segurança e transporte:

- As URLs de mídia remota devem ser HTTPS públicas. Os itens canônicos `{type,source:url}` são buscados
  no servidor (revalidação de redirecionamentos, tempo limite, limites de tamanho, DNS público, fixação de conexão) e incorporados antes da chamada ao provedor. Os itens nativos da Jina `{image:"https://..."}` são encaminhados como estão após a mesma verificação de HTTPS público; a Jina busca a URL.
- A mídia base64 incorporada é limitada a 8 MiB decodificados por item e 16 MiB decodificados por solicitação.

Tradução para os provedores (os itens canônicos nunca são encaminhados inalterados):

- Modelos multimodais da Jina: cada item de nível superior se torna um objeto com uma chave de modalidade
  (`text` / `image` / `audio` / `video` / `pdf`), usando URIs de dados para mídia incorporada; um vetor por
  item de nível superior.
- Família Gemini Embedding 2: um único array de nível superior se torna uma única solicitação nativa
  `models/{model}:embedContent` com `content.parts` (`text` ou `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualquer modelo carregado pelo servidor local): os itens canônicos `text`
  se tornam strings simples, e `image` / `audio` / `video` se tornam, cada um, um objeto
  `{"content": [part]}`, usando as partes de conteúdo de chat do llama-server (`image_url`,
  `input_audio` com formato `wav` / `mp3` / `flac`, `input_video`) com dados incorporados; um vetor
  por item de nível superior. O servidor deve ser executado com `--embedding --mmproj …`; sem um projetor, ele rejeita a própria mídia. `document` não é compatível.
- Modelos desconhecidos/dinâmicos sem metadados explícitos de modalidade rejeitam entradas estruturadas com HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Combinações de modelo/modalidade sem suporte retornam HTTP 400 em vez de converter o item. Campos de extensão que não sejam de entrada em solicitações legadas de string/token continuam sendo encaminhados sem alterações.

```bash
# Listar todos os modelos de incorporação
GET /v1/embeddings
```

## Geração de imagens

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Os provedores disponíveis incluem OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local), ComfyUI (local).

`n` retorna `n` imagens em `data[]`. Provedores cuja API upstream retorna uma imagem por chamada
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) fazem `n` chamadas upstream separadas, com no máximo 4 em
execução simultânea. Um `seed` fixo é incrementado pelo índice da chamada (`seed`, `seed + 1`, …),
fazendo com que as imagens sejam diferentes, mas permaneçam reproduzíveis. `n` é limitado a 10. A
solicitação falha como um todo se qualquer chamada falhar. A lista de formatos com fan-out está em
`SINGLE_IMAGE_FANOUT_FORMATS`, em
`open-sse/handlers/imageGeneration/fanOut.ts`.

O ZenMux reutiliza a conexão existente com a chave de API e aceita os prefixos `zenmux/` ou `zm/`:

- `zenmux/openai/gpt-image-2` usa a API de imagens da OpenAI do ZenMux. As opções incluem `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Outros publishers, como `zm/meta/muse-image-1.0`, usam o endpoint `:predict` do Vertex AI do
  ZenMux. `n` é mapeado para `sampleCount`, `aspect_ratio` para `aspectRatio` e `image_size`
  (`1K`, `2K`, `4K`) para `sampleImageSize`. Um `size` em pixels fornece apenas uma proporção de
  aspecto, sem garantir as dimensões em pixels. As proporções, resoluções e quantidades
  compatíveis variam de acordo com o modelo.
- `zm/inclusionai/ming-image-0.1-design` escolhe suas próprias dimensões. Omita `size`,
  `aspect_ratio` e `image_size`; valores explícitos retornam HTTP 400. PNG, JPEG e WebP
  podem ser solicitados com `output_format`.

Essa integração é compatível com a geração de texto para imagem, não com a edição de imagens de referência. A
saída do Vertex é normalizada para `data[].b64_json`; `response_format: "url"` retorna uma URL
upstream HTTPS ou uma URL de dados base64 quando apenas os bytes da imagem estão disponíveis. Saídas
vazias/filtradas retornam um erro em vez de uma resposta de sucesso vazia. O acesso aos modelos depende da
conta do ZenMux. Consulte a [API Vertex do ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) e a
[API de imagens da OpenAI](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Listar todos os modelos de imagem
GET /v1/images/generations
```

## OCR de documentos

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleciona o provedor de OCR por meio de um prefixo `provider/model`; um id de modelo sem
prefixo (por exemplo, `mistral-ocr-latest`) é resolvido para seu provedor registrado, e um `model`
omitido usa o Mistral por padrão (`mistral-ocr-latest`). Provedores registrados
(`open-sse/config/ocrRegistry.ts`):

| ID do provedor                | ID do modelo         | Valor de `model`                                       | Observações                                                                                                                       |
| ----------------------------- | -------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (ou `mistral-ocr-latest`) | Síncrono — a resposta é retornada diretamente da única chamada upstream.                                                          |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`            | Upstream assíncrono (`analyze` + poll) — veja abaixo.                                                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                | Síncrono, por meio do endpoint parceiro `openapi/chat/completions` do Vertex AI — veja abaixo informações sobre autenticação/URL. |

Os três provedores respondem no mesmo corpo no formato do Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxo de polling do Azure Document Intelligence

A API `analyze` do Azure Document Intelligence é assíncrona: a solicitação inicial retorna um
cabeçalho `Operation-Location` em vez de um corpo, e o resultado deve ser consultado por polling. O handler
(`open-sse/handlers/ocr.ts`) consulta essa URL a cada segundo por até 30 tentativas, falha rapidamente (não
continua consultando) quando a resposta de polling não é `ok` ou quando o status é `"failed"`, e retorna
`504` se a operação ainda estiver em execução após o esgotamento do limite de tentativas. A resposta final
do Azure é normalizada para o mesmo formato `pages`/`markdown` usado pelo Mistral antes de ser retornada ao
chamador, portanto o código cliente não precisa tratar o provedor de maneira especial.

### Autenticação e resolução do endpoint do Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` reutiliza a mesma autenticação do Vertex AI que o OmniRoute já oferece para
tráfego de chat/imagem (`open-sse/executors/vertex.ts`): a chave de API da conexão é uma credencial JSON de
Service Account (trocada por um token de acesso OAuth de curta duração por meio do fluxo JWT-bearer) ou um
token de acesso OAuth já emitido, usado como está. A URL do endpoint upstream é o endpoint parceiro
genérico `openapi/chat/completions` do Vertex, construído a partir do projeto e da região da conexão —
um `providerSpecificData.project`/`providerSpecificData.region` explícito sempre tem prioridade; caso
contrário, o projeto é derivado de `project_id` do JSON da Service Account e a região usa `us-central1`
por padrão. Ambas as resoluções ocorrem em `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e são consumidas por
`src/app/api/v1/ocr/route.ts` antes do despacho para `handleOcr`.

## Listar modelos

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Retorna todos os modelos de chat, embedding e imagem + combinações no formato da OpenAI
```

### Preços dos modelos (`pricing`)

Uma entrada contém um objeto `pricing` quando o OmniRoute conhece o preço do modelo. O preço vem
da tabela de preços usada pela contabilização de custos: padrões integrados, preços sincronizados e
substituições definidas por meio de `/api/pricing`. Esses são preços de lista, portanto os provedores
de assinatura também exibem um preço por token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Campos                                                          | Unidade                       | Observações                                                                                                                                                   |
| --------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD por token, string decimal | Compatível com o OpenRouter, nunca em notação exponencial. Os dois campos de cache aparecem somente quando há um preço de cache.                              |
| `input`, `output`, `cached`, `cache_creation`                   | USD por 1M tokens, número     | Campos de versões anteriores do catálogo, mantidos para clientes existentes. `reasoning` e `long_context` também aparecem quando a linha de preços os contém. |

- **Combinações** carregam o preço do primeiro destino visível. As combinações `auto/*` integradas escolhem um
  destino no momento da solicitação, portanto não têm `pricing`.
- **Modelos gratuitos** exibem `"0"` (e `0`) quando o preço é zero. Um modelo sem uma linha de preços
  também exibe `"0"` quando o catálogo o marca como gratuito (`free: true`) ou quando ele está listado
  no catálogo integrado de modelos gratuitos.
- **Preço desconhecido:** a entrada não possui a chave `pricing`.
- **Provedores medidos por créditos** (como o Kiro) cobram por solicitação, e não por token. Suas
  entradas mantêm os campos numéricos por 1M que já tinham e não possuem campos de string por token.
- **Variantes** (ids de esforço de raciocínio, aliases sem pensamento, espelhos de descoberta e gateway)
  copiam o preço do modelo para o qual roteiam.
- Os campos contêm apenas as tarifas básicas. Os níveis de contexto longo (o campo numérico
  `long_context`) e os multiplicadores de nível de serviço (por exemplo, Codex fast ou flex) não alteram
  `prompt` ou `completion`.
- O objeto é o mesmo para todos os estilos de autenticação, incluindo uma solicitação no estilo Anthropic
  com `x-api-key` e `anthropic-version` (a resposta permanece `{ "object": "list",
"data": [...] }`). Implementação: `src/app/api/v1/models/catalogPricing.ts`.

### Prefixos de id dos modelos (`?prefix=`)

A maioria dos modelos é anunciada com um **prefixo de provedor**. O prefixo obtido é controlado pela
flag de recurso `MODELS_CATALOG_PREFIX_MODE` e pode ser substituído **por solicitação** com um
parâmetro de consulta — útil para um cliente que deseja uma lista limpa sem alterar a configuração
abrangente do servidor para todos os demais:

```bash
GET /v1/models?prefix=alias        # um id por modelo — o prefixo de alias curto
GET /v1/models?prefix=dual         # ambas as formas (padrão do servidor)
GET /v1/models?prefix=canonical    # somente o prefixo completo de id do provedor
```

| Modo        | Emite                                                   | Observações                                                                                                                                                                                          |
| ----------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **e** `claude/claude-sonnet-4-6` | **Padrão.** Ambos os ids roteiam para o mesmo modelo; mantidos para que as configurações de cliente que codificaram qualquer uma das formas continuem funcionando. Aproximadamente dobra o catálogo. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Uma entrada por modelo. Provedores sem um alias distinto ainda emitem sua entrada, portanto nada é perdido.                                                                                          |
| `canonical` | `claude/claude-sonnet-4-6`                              | Uma entrada por modelo sob o prefixo completo de id do provedor. Provedores sem um alias distinto (por exemplo, `antigravity/…`, `agy/…`) também emitem seu id único aqui, portanto nada é perdido.  |

Um espelho no modo `dual` também pode ser reconhecido sem o parâmetro de consulta: ele contém um campo `parent`
apontando para o id principal.

Clientes que exibem um seletor de modelos devem solicitar `?prefix=alias` — é isso que a
[extensão OmniCopilot para VS Code](../guides/VSCODE-COPILOT.md) faz.

### Filtros de descoberta (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` aceita filtros de descoberta opcionais. Sem nenhum deles, a resposta permanece
inalterada. Eles restringem o catálogo que o chamador já visualiza (as permissões da chave de API são
aplicadas primeiro) e são executados antes da paginação `limit` / `after` no estilo OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # todas as capacidades listadas devem ser verdadeiras
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` do catálogo; as linhas sem um são `chat`
GET /v1/models?q=sonnet&limit=10                           # correspondência que não diferencia maiúsculas de minúsculas no id ou no nome
```

| Parâmetro     | Valores                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | inteiro não negativo, comparado com `context_length`                                                |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caracteres                                                                                    |

Um valor desconhecido ou um `min_context` que não seja um inteiro não negativo (por exemplo, `1.5`)
retorna HTTP `400`, e a mensagem lista os valores válidos. Implementação:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista resumida de modelos (`POST /v1/models/query`)

`POST /v1/models/query` retorna uma lista curta e determinística do mesmo catálogo, com a mesma
autenticação e visibilidade por chave de `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Todos os campos são opcionais. `capabilities` e `exclude` aceitam um array ou uma string separada por vírgulas;
`max_output` é comparado com `max_output_tokens`. Os resultados são ordenados por `owned_by` e, em seguida, por `id`.
`limit` tem como padrão `20`, e valores acima de `100` são limitados a `100`. JSON inválido, um
campo desconhecido ou um valor inválido retorna HTTP `400`.

### Modelos de chat ocultos individualmente

Um modelo marcado como **Oculto** na página de seu provedor é excluído do catálogo e rejeitado
com HTTP `404` / `model_not_found` quando solicitado explicitamente. A verificação usa o provedor e o modelo resolvidos,
incluindo aliases de provedores, prefixos de nós de provedores compatíveis e padrões de conexão. Uma combinação
ignora destinos ocultos e pode usar um irmão visível; quando nenhum destino executável permanece, retorna o mesmo
código de erro. A remoção da ocultação entra em vigor na próxima solicitação. Substituições de visibilidade exclusivas
para imagens não ocultam o modelo de chat com o mesmo ID.

Essa configuração de modelo individual é separada das
[listas de permissão/bloqueio de exposição de modelos](../routing/MODEL_EXPOSURE_LIST.md), que filtram
a divulgação no catálogo e os candidatos ao roteamento automático, mantendo o despacho explícito. As permissões de
modelos por chave de API continuam a ser aplicadas de forma independente. O modo de prefixo padrão do catálogo permanece
`dual`.

### Variantes de modelos sem raciocínio

Para modelos Claude compatíveis com raciocínio, `/v1/models` também anuncia uma variante **sem raciocínio**, cujo id é prefixado com `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Selecionar esse id (por exemplo, em uma configuração do Claude Code que sempre anexa um bloco `thinking`)
resolve novamente para o `<provider>/<model>` real, com o raciocínio suprimido — `thinking:{type:"disabled"}` no caminho
`/v1/messages`, ou os campos `reasoning`/`reasoning_effort` removidos no caminho
`/v1/chat/completions`. A variante só é listada para modelos da família Claude que oferecem suporte a raciocínio **e**
respeitam `disabled` (portanto, por exemplo, modelos somente adaptativos que rejeitam `disabled` são excluídos).
Os operadores podem forçar a ativação ou desativação da variante por modelo usando `ModelSpec.noThinkingAlias`.

## Geração de áudio do ElevenLabs

Configure uma conexão de provedor `elevenlabs` no OmniRoute com sua chave de API do ElevenLabs.
Os clientes se autenticam com a chave do **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
o gateway fornece a chave de provedor armazenada como `xi-api-key`. Nunca envie uma chave do ElevenLabs
como token bearer do gateway.

| Método | Caminho                     | Resposta                                     | Categoria do endpoint da chave de API |
| ------ | --------------------------- | -------------------------------------------- | ------------------------------------- |
| POST   | `/v1/sound-generation`      | Bytes de áudio nativos                       | `elevenlabs`                          |
| POST   | `/v1/music`                 | Bytes de áudio nativos                       | `music`                               |
| POST   | `/v1/music/stream`          | Bytes de áudio em streaming                  | `music`                               |
| POST   | `/v1/music/detailed`        | Áudio multipart nativo e plano de composição | `music`                               |
| POST   | `/v1/music/detailed/stream` | Metadados SSE nativos e blocos de áudio      | `music`                               |
| POST   | `/v1/music/plan`            | Plano de composição JSON                     | `music`                               |

Esses endpoints complementam as rotas existentes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` e `/v1/speech-to-text`. Os campos JSON nativos
e parâmetros de consulta, como `output_format` e `enable_logging`, são preservados.
As respostas de `/v1/music/detailed` mantêm seus limites multipart; analise-as como multipart.
`/v1/music/detailed/stream` retorna `text/event-stream` com metadados de composição e
blocos de áudio codificados em base64 nos eventos SSE. Todas as seis rotas oferecem suporte ao preflight do CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Um efeito sonoro curto. Duração: de 0,5 a 30 segundos.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# A duração da música é expressa em milissegundos: de 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Use `/v1/music/stream` com o mesmo corpo JSON para entrega incremental de áudio. A composição
aceita exatamente um entre `prompt` ou `composition_plan`; `/v1/music/plan` exige `prompt`
e aceita opcionalmente `source_composition_plan`. Os esquemas nativos preservam campos adicionais
do provedor para que versões do plano de composição e opções de ajuste fino cheguem ao ElevenLabs.

O endpoint unificado `/v1/music/generations` também aceita
`elevenlabs/music_v1`, `elevenlabs/music_v2` e `elevenlabs/music_v2_5`. Com uma conexão ativa
do ElevenLabs, esses modelos são expostos pelo catálogo de música. Esse endpoint retorna
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Seu campo `duration` é expresso em
segundos e mapeia para `music_length_ms`; um `music_length_ms` explícito tem precedência.
`instrumental` mapeia para `force_instrumental`, com o campo nativo tendo precedência.
Use os endpoints nativos de streaming para streaming e o endpoint nativo de composição
para solicitações orientadas exclusivamente por um plano de composição.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

As restrições de endpoint, modelo, orçamento e conexão são aplicadas antes de uma chamada upstream. As rotas
nativas retornam os códigos de status e os corpos de erro do upstream inalterados, incluindo `402`
para uma restrição do plano e `429` para um limite de cota. Os cabeçalhos `character-cost`, `song-id`, `request-id` e `retry-after`
são preservados quando presentes. Um saldo de créditos gratuito não garante acesso a todos os
modelos de música, formatos de saída ou recursos da API: o ElevenLabs decide a permissão para cada solicitação.
O endpoint unificado preserva os códigos de status de erro no envelope de erro normalizado do OmniRoute.

Contratos upstream: [efeitos sonoros](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composição musical](https://elevenlabs.io/docs/api-reference/music/compose) e
[detalhes de música em streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Nós de provedores de reranking:** `POST /v1/rerank` também roteia para nós de provedores compatíveis com OpenAI
> (oMLX, vLLM, Infinity, TEI atrás de um gateway, …) endereçados como `<node-prefix>/<model>`. Nós de loopback
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) são sempre elegíveis, assim como os nomes de host
> listados pelo operador em `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (por exemplo, um nome de serviço do Docker/Compose, como
> `http://reranker:8080/v1`; eles são chamados diretamente, nunca por meio de `HTTP(S)_PROXY` ou do proxy fixado de uma
> conexão). Nós em qualquer outro
> host — uma máquina na LAN ou um peer do Tailscale — são elegíveis somente quando o operador habilita o
> sinalizador de recurso `RERANK_REMOTE_PROVIDER_NODES` **e** a URL base do nó passa pela política de URLs de saída do provedor
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> A etapa de reranking do mecanismo de memória chama essa rota por
> loopback, portanto a mesma regra rege `rerankProviderModel` nas configurações de Memória.
>
> **Formatos de servidores locais:** o nó é chamado em `<base>/v1/rerank` e, em caso de 404, em `<base>/rerank`
> (Infinity, TEI). O corpo enviado ao upstream contém ambas as grafias do Cohere/OpenAI (`documents`,
> `return_documents`) e do TEI (`texts`, `return_text`), e a resposta do upstream é
> normalizada para o envelope do Cohere: o `[{index, score, text}]` simples do TEI, `{results: [{index, score}]}`
> de gateways intermediários e `{data: [...]}` no estilo Voyage retornam ao cliente como
> `{results: [{index, relevance_score, document?}]}`, classificados por pontuação e limitados a `top_n`.

> **Descoberta de nós de provedores:** os modelos em um nó de provedor compatível com OpenAI aparecem em `GET /v1/models`
> sob o prefixo do nó. As linhas que não contêm metadados de endpoint (típico das listagens locais de `/v1/models`)
> herdam o `apiType` do nó, portanto os modelos de um nó de `embeddings` têm `type: "embedding"` e os
> modelos de um nó de `rerank` têm `type: "rerank"`, em vez de assumirem chat por padrão; um
> `supportedEndpoints` explícito em uma linha sincronizada ou adicionada manualmente ainda tem precedência.

### `provider_options` do Exa e do Tavily

O Exa e o Tavily leem campos específicos do provedor de um contêiner com namespace:
`provider_options.exa` (ou `provider_options["exa-search"]`) e `provider_options.tavily`
(ou `provider_options["tavily-search"]`). Somente as chaves abaixo são encaminhadas. Cada uma é
validada em relação ao próprio esquema Zod em
`open-sse/handlers/search/providerOptionsPassthrough.ts`, e uma chave com o tipo incorreto é
descartada. Qualquer outra chave é ignorada, incluindo autenticação, URL base,
`stream` e `outputSchema`. As chaves simples usadas por outros provedores (`cx`, `depth`, ...) continuam funcionando como antes.

| Provedor | Campos de nível superior                                                                                                                                                                                                                                                                                                                                                  | Aninhado                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitivos simples), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                           | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` mesclado sobre o padrão `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                        |

Os campos genéricos sempre têm prioridade: `query`, `max_results`, `filters` (domínios), `country` e o
tópico derivado de `search_type`. No Exa, `search_type: "news"` mantém `category: "news"`.
O Tavily também aceita `search_type: "finance"` (`topic: "finance"`).

O custo da pesquisa do Firecrawl é registrado por bloco iniciado de 10 resultados retornados, a US$ 0,002 (2
créditos) por bloco, com pelo menos um bloco por chamada
([cobrança do Firecrawl](https://docs.firecrawl.dev/billing)): 11 resultados custam US$ 0,004.

O `time_range` genérico agora chega aos dois provedores: o Exa recebe `startPublishedDate` (carimbo de data/hora ISO)
e o Tavily recebe `start_date` (`YYYY-MM-DD`). Uma data explícita em `provider_options`
substitui a data mapeada.

Os resultados do Exa mantêm `id`, `highlights` (todos os destaques, não apenas o primeiro usado como
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` e `extras` em
`provider_raw`. Os resultados do Tavily mantêm `images` e `favicon`.

O custo da pesquisa do Linkup é registrado como US$ 0,005 para `depth` `fast` e `standard` e US$ 0,05 para
`deep` ([preços do Linkup](https://docs.linkup.so/pages/documentation/development/pricing)),
independentemente de `depth` vir de `provider_options` ou das configurações da conexão.

O Exa `type: "lite"` (Exa 3.0) aceita um conjunto menor de campos e rejeita toda a solicitação
quando qualquer outro campo é definido. Para o lite, `additionalQueries`, `systemPrompt` e todas as
chaves de `contents`, exceto `text` e `highlights`, são descartadas antes da chamada. Os campos obsoletos
`subpages`, `subpageTarget`, `highlights.numSentences` e `highlights.highlightsPerUrl` não são mais
encaminhados.

A contabilização de custos usa o registro simples `costPerQuery`, exceto para o Exa, que segue os
próprios preços do Exa: US$ 0,007 por chamada para `auto` (e o legado `fast`) ou US$ 0,004 para
`lite` (e o legado `instant`), cobrindo 10 resultados; US$ 0,001 para cada resultado adicional; e US$ 0,001 por
resultado retornado quando `contents.summary` é definido. O Tavily é registrado como 1 crédito (US$ 0,008) para
`search_depth` `basic`, `fast` e `ultra-fast`, e 2 créditos (US$ 0,016) para `advanced`
([créditos da API do Tavily](https://docs.tavily.com/documentation/api-credits)). Uma chamada com
`auto_parameters: true` que faz o Tavily mudar para advanced ainda é registrada como 1 crédito.

## API de Busca na Web

Extraia conteúdo de uma URL por meio de um provedor de busca na web configurado (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

O Parallel Extract (`parallel-search`, mesma chave de API usada pelo Parallel Search) retorna apenas Markdown — qualquer outro `format` resulta em um `400` — e limita o conteúdo a 100.000 caracteres. Quando a própria página de destino não pode ser extraída, o upstream informa isso dentro de um HTTP 200; o OmniRoute expõe essa situação como um `422` com uma mensagem fixa.

| Método | Caminho         | Descrição                                                    |
| ------ | --------------- | ------------------------------------------------------------ |
| POST   | `/v1/web/fetch` | Busca/extrai uma URL — corpo validado por `v1WebFetchSchema` |

**Autenticação:** chave de API Bearer (`extractApiKey` + `isValidApiKey`). A política é aplicada por meio de `enforceApiKeyPolicy`.

**Fallback consciente da cota (#8297):** quando nenhum `provider` explícito é informado, o pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) é percorrido em ordem de prioridade fixa (fill-first) — um provedor limitado por taxa, mas configurado, é ignorado em vez de interromper a solicitação, e uma falha upstream que pode ser repetida/relacionada à cota (HTTP 429 sempre; 402/403 para as cotas de níveis gratuitos do tipo cota do Firecrawl/Tavily/TinyFish —
não para o Jina Reader e nunca para uma solicitação 400 inválida simples) passa para a próxima credencial de provedor ainda não tentada no momento da solicitação. Quando todos os provedores do pool se esgotam, o endpoint retorna um único `429` (com um cabeçalho `Retry-After`) em vez do `400` genérico anterior. Quando um `provider` explícito é solicitado, **não há fallback silencioso** — um provedor explícito limitado por taxa ou com falha expõe seu próprio erro (`429` se estiver limitado por taxa; caso contrário, o status do upstream).

## Streaming via WebSocket

```bash
GET /v1/ws?handshake=1
```

Valida um handshake de upgrade do WebSocket e retorna as mensagens de exemplo do protocolo de transmissão (`request`, `cancel`). Os frames WS reais são tratados pelo servidor WS incluído, fora da tabela de rotas do Next.js.

**Autenticação:** chave de API Bearer durante o handshake.

### API de Responses via WebSocket (somente codex)

```bash
# Mesmo host:porta da API HTTP (padrão 20128); atualize a conexão:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ou: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# O primeiro frame DEVE ser response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Um proxy da API Responses via WebSocket está conectado **exclusivamente ao `codex`** (backend do ChatGPT). Ele escuta na mesma porta que a API/dashboard, nos caminhos `/v1/responses`,
`/responses` e `/api/v1/responses`. No primeiro frame `response.create`, ele autentica e prepara por meio da ponte interna `codex-responses-ws`, seleciona uma conexão OAuth do codex e cria um túnel para `wss://chatgpt.com/backend-api/codex/responses` por meio do transporte `wreq-js`. **Modelos que não são codex são rejeitados** (`codex_ws_provider_required`).
Para o roteamento de compartilhamento de cota, use `model: "qtSd/<group>/codex/<model>"`. Implementado em
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticação:** chave de API Bearer durante o handshake. O servidor HTTP incluído (`server-ws.mjs`)
deve ser o ponto de entrada ativo (por padrão, ele é usado quando `app/server-ws.mjs` existe).

#### ID do modelo: use o ID simples do ChatGPT (sem o prefixo `codex/`)

A **CLI do OpenAI Codex** valida o nome do modelo no lado do cliente quando
`supports_websockets = true` e **rejeita IDs com prefixo de provedor** como
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Envie o ID **simples** (por exemplo, `gpt-5.5`). A ponte do OmniRoute funciona somente com codex, portanto resolve novamente um ID simples como um modelo codex
(`resolveCodexWsModelInfo`) antes de criar o túnel upstream — embora um `gpt-5.5` simples normalmente fosse roteado para outro provedor via HTTP.

#### Configurando a CLI do OpenAI Codex

Aponte a CLI do Codex para o OmniRoute adicionando um provedor personalizado com suporte a WebSocket em `~/.codex/config.toml` (use um `CODEX_HOME` separado para evitar alterar uma configuração existente):

```toml
model = "gpt-5.5"                 # ID simples — NÃO "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # sem barra final; a URL WS é derivada (use https/wss em produção)
wire_api = "responses"                    # único valor compatível desde fevereiro de 2026
supports_websockets = true                # habilita o transporte Responses via WS
env_key = "OMNIROUTE_API_KEY"             # contém a chave de API do OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # uma chave de API do OmniRoute (qualquer chave se REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

A CLI transforma `base_url + /responses` em um WebSocket, e o OmniRoute cria um túnel até a conexão OAuth do codex selecionada. Validado de ponta a ponta no servidor local: o ChatGPT retorna `codex.rate_limits` + `response.created` e transmite a conclusão.

### Recuperação de sessão de cota (opcional)

Uma solicitação `POST /v1/chat/completions` ou `POST /v1/responses` sem streaming que falhe com um
erro terminal de cota (`402`/`429`/`503` cujo corpo informe que a cota ou os créditos estão esgotados)
pode ser armazenada e reproduzida posteriormente em vez de retornar o erro. O chamador opta por isso por
solicitação com três cabeçalhos:

| Cabeçalho                    | Valor                                                |
| ---------------------------- | ---------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                               |
| `x-omniroute-session`        | id da sessão, `[A-Za-z0-9._:-]{1,128}`               |
| `x-omniroute-recovery-turn`  | id do turno exclusivo dentro da sessão (mesma regra) |

Apenas turnos com `stream: false`, sem ferramentas, histórico de ferramentas ou
`previous_response_id`, e sem um pin de `x-omniroute-connection`, são elegíveis, e
`STORAGE_ENCRYPTION_KEY` deve estar definido (a solicitação é armazenada criptografada por até 24 h). A
resposta será então `202` com `recovery.poll`; consulte
`GET /v1/quota-recoveries/{id}` (`202` enquanto estiver pendente, `200` com o
corpo recuperado quando concluído) ou cancele com `DELETE`. Os tickets ficam visíveis apenas para a chave
de API que os criou. Uma reprodução cujo resultado seja incerto termina em `needs_confirmation`, em vez
de ser enviada duas vezes. Fonte: `src/lib/quota/quotaSessionRecovery.ts`.

## Uso de autoatendimento (`/api/usage/om-usage`)

Qualquer chave de API pode ler seu **próprio** uso e suas cotas — sem autenticação de gerenciamento. Este é o endpoint que um
cliente (CLI, o painel do OmniCopilot) usa para mostrar ao titular da chave seus gastos.

```bash
# Formato de texto (o contrato histórico — texto simples para um terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato estruturado — o que uma interface de usuário consome
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

A chave deve ter **`allowUsageCommand`** habilitado (desabilitado por padrão — o gerenciador de chaves
de API do painel alterna essa opção por chave). Sem essa opção, o endpoint responde com `403`.

`?format=json` retorna uma estrutura discriminada para que um chamador nunca leia um campo de dados de uma
recusa. Em caso de sucesso:

```jsonc
{
  "allowed": true,
  // presente somente quando a chave optou por limites de uso por chave (USD diário/semanal):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // instantâneo da cota do provedor selecionado, ou nulo quando nada estiver armazenado em cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // instantâneo de cada conexão, para que uma interface possa renderizar vários provedores lado a lado:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Em caso de recusa (chave `401` inválida / não permitido `403`), a mesma rota retorna
`{ "allowed": false, "error": { "message": "…" } }` — um `personal`/`provider`
presente, mas vazio (chave permitida, nada descoberto ainda), é um estado diferente de uma recusa, e
somente o formato JSON faz essa distinção.

**Autenticação:** a própria chave de API Bearer do chamador, validada com `isValidApiKey` — esta **não** é a
superfície de gerenciamento (`/api/keys/…`), que continua protegida por `requireManagementAuth`.

### Percentuais de cota brutos versus ajustados pelo limite

Ao consumir `/api/usage/om-usage`, os chamadores devem observar a distinção entre os
percentuais apresentados pela **saída em texto simples** e pela saída estruturada em **JSON**:

| Aspecto                     | Formato de texto simples (`/api/usage/om-usage` / `@@om-usage`)                                       | Formato JSON (`?format=json`)                                                   |
| :-------------------------- | :---------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------ |
| **Campo de saída**          | `NN% left` (por exemplo, `20% left`)                                                                  | `provider.quotas` / `providers[].quotas`                                        |
| **Medição**                 | **Proporção utilizável ajustada pelo limite**: capacidade restante acima do limite de corte           | **Cota bruta do upstream**: medição do provedor sem ajustes                     |
| **Escalonamento do limite** | Escalonada via `effectiveRemainingPercent()` para que a reserva protegida seja exibida como `0% left` | Nenhum (valores brutos do instantâneo conforme informados pelo provedor)        |
| **Dados do limite**         | Incorporados ao percentual exibido                                                                    | Armazenados em `quotaWindowThresholds` por conexão (ou nos padrões do servidor) |
| **Consumidor principal**    | CLIs interativas, prompts de terminal, operadores humanos                                             | Integrações programáticas, painéis, análises, rastreadores de faturamento       |

#### Fórmula do ajuste pelo limite

O OmniRoute oferece limites proativos de cota para evitar o esgotamento no upstream (configurados por meio de
`quotaWindowThresholds` da conexão, padrões do provedor ou configurações globais de resiliência). Quando um
limite de corte (por exemplo, `cutoff = 25%`) está ativo em uma janela de cota, o renderizador de texto
calcula a proporção restante permitida da seguinte forma:

- Se `remaining <= cutoff`: retorna `0%`.
- Se `remaining > cutoff`: retorna `((remaining - cutoff) / (100 - cutoff)) * 100`.

A saída de texto formatada arredonda esse valor para o inteiro mais próximo (`Math.round(...)`).

#### Exemplo ilustrativo

Considere uma janela do provedor com **60% de uso bruto** (portanto, **40% de cota bruta restante**) e um limite configurado de **25% de cota restante**:

| Representação                     | Cálculo                                            | Restante |                 Uso implícito                 |
| :-------------------------------- | :------------------------------------------------- | :------: | :-------------------------------------------: |
| **JSON bruto (`?format=json`)**   | Instantâneo do upstream (`quotas[window]`)         | **40%**  |                    **60%**                    |
| **Formato de texto (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (se calculado como `100 - remaining`) |

- **Por que o texto mostra 20% restante:** Dos 40% de cota física restantes na conta, 25% são reservados pela
  política de limite. O chamador tem apenas 15% dos 75% de margem utilizável restantes antes que o roteador pare de
  direcionar tráfego para esta conexão. O dimensionamento garante que a conexão sinalize esgotamento (`0% left`) exatamente quando
  o roteamento for interrompido.
- **Por que o JSON preserva os valores brutos:** A carga útil JSON retorna o instantâneo exato do provedor (`UsageSnapshot`),
  para que ferramentas externas tenham acesso à utilização real do upstream e aos
  `quotaWindowThresholds` no nível da conexão, sem dimensionamento com perda no lado do servidor.

#### Orientação para migração de consumidores

Se uma integração externa (como um plugin de editor ou uma extensão de agente) anteriormente analisava o endpoint de texto
(`NN% left`) e calculava a porcentagem usada como `100 - NN`, migrar para `?format=json` significa:

- Ler os valores brutos do JSON refletirá o **consumo real do upstream** (60% usado no exemplo acima).
- Se a integração desejar preservar a semântica de permissão utilizável do endpoint de texto, ela poderá avaliar
  a fórmula de restante efetivo no lado do cliente usando `quotaWindowThresholds` para substituições no nível da conexão.

## Cache semântico

```bash
# Obter estatísticas do cache
GET /api/cache/stats

# Limpar todos os caches
DELETE /api/cache/stats
```

Exemplo de resposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impacto na latência

Um HIT do cache semântico fornece a resposta diretamente do cache **sem uma
chamada upstream**, portanto o `X-OmniRoute-Response-Latency` reportado é
próximo de zero (independentemente da latência upstream original). Clientes
sensíveis à latência (benchmarking, monitoramento de p50/p99) devem verificar o
cabeçalho de resposta `X-OmniRoute-Cache-Latency`:

| Valor       | Significado                                                           |
| ----------- | --------------------------------------------------------------------- |
| `synthetic` | Resposta fornecida pelo cache; a latência não é o tempo upstream real |
| _(absent)_  | Resposta de uma chamada upstream real                                 |

### Ignorar o cache por chave

As chaves de API podem optar por não realizar leituras do cache semântico por
meio de `cacheDefaultMode`:

| Valor    | Comportamento                                                   |
| -------- | --------------------------------------------------------------- |
| `legacy` | Comportamento normal do cache (padrão)                          |
| `bypass` | Ignora completamente a busca no cache; sempre acessa o upstream |

Defina durante a criação da chave (`POST /api/keys`) ou na atualização
(`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Ignorar o cache por requisição

Qualquer requisição pode ignorar o cache, independentemente das configurações
da chave:

```
X-OmniRoute-No-Cache: true
```

## Compatibilidade de gerenciamento com CLIProxyAPI

O OmniRoute responde aos três endpoints de gerenciamento do
[CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) que os painéis de uso
chamam para ler os limites de assinatura do Claude e do Codex (por exemplo, a
fonte de limite de uso `cliproxy` do T3 Code). Aponte a URL base do cliente para
o OmniRoute e use uma chave de API com o escopo `manage` como chave de
gerenciamento. As rotas são disponibilizadas em `/v0/management/*` e em
`/api/v0/management/*`.

| Método | Caminho                      | Descrição                                                                                                                                     |
| ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Conexões OAuth do Claude e do Codex como `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Nenhum token                 |
| POST   | `/v0/management/api-call`    | Corpo `{ auth_index, method, url, header?, data? }`. Envia uma requisição permitida com o token da conta e retorna `{ status_code, body }`    |
| POST   | `/v0/management/reset-quota` | Corpo `{ auth_index }`. Limpa o período de espera da conexão, os bloqueios de modelo e os períodos de espera por escopo do Codex de uma conta |

- `auth_index` é o ID da conexão do OmniRoute. `provider` é `claude` ou `codex` (somente
  conexões OAuth; o provedor de chave de API `anthropic` não é listado). Para o Codex,
  `id_token.chatgpt_account_id` é o ID de workspace armazenado e `plan_type` é o plano
  armazenado.
- `api-call` não é um proxy genérico. Ele aceita somente Claude `GET
https://api.anthropic.com/api/oauth/usage` e Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` e
  `POST .../wham/rate-limit-reset-credits/consume`, cada um somente para uma conta do
  provedor correspondente. Qualquer outra opção retorna `403` sem entrar em contato com o
  upstream. O cabeçalho `Authorization` do chamador (incluindo o marcador `$TOKEN$`) é
  ignorado: o OmniRoute injeta o token de acesso da conexão, atualizando-o primeiro quando
  está próximo de expirar, e encaminha somente os cabeçalhos permitidos (`anthropic-beta`;
  `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`). A ausência de
  `Chatgpt-Account-Id` usa como padrão o ID de workspace armazenado. As requisições expiram
  após 15 segundos e usam o proxy da conexão.
- `reset-quota` deixa os estados terminais (`banned`, `expired`, `credits_exhausted`) inalterados. Um
  `auth_index` desconhecido retorna `404`.

**Autenticação:** sessão do painel ou uma chave de API com escopo `manage`, obrigatória
mesmo quando o login está desabilitado (os caminhos estão em
`ALWAYS_PROTECTED_API_PATHS`). Chaves que permitem apenas inferência recebem `403`. Fonte:
`src/lib/cliproxyCompat/managementApi.ts`.

Para modelos sincronizados/importados, `PUT /api/provider-models` aceita `provider`, `modelId` e
`maxOutputTokenOverride`: um inteiro positivo define o limite manual de tokens de saída, e `null`
o remove para restaurar o padrão. `GET /api/provider-models?provider=<provider>` retorna esses
valores em `modelOutputOverrides`, incluindo modelos sem uma linha de modelo personalizado. A substituição
usa o recurso de runtime `max_output_tokens` e persiste após uma nova sincronização do modelo. A
página do provedor compatível com OpenAI oferece os mesmos controles de edição/remoção e marca os modelos com suporte explícito à visão.

Em um nó de provedor compatível, os caminhos de gravação (`POST`, `PUT`, `PATCH`, `DELETE` e
`/api/provider-models/validate-and-add`) armazenam o id do modelo como o id upstream sem prefixo: um id
colado de uma listagem com prefixo tem qualquer sequência inicial de prefixos do próprio nó compactada, e
as respostas repetem o id armazenado. Os ids com barras dos provedores canônicos (por exemplo, `nvidia/nemotron-…`) são
armazenados literalmente. `/v1/models` nunca emite um id empilhado no formato `<prefix>/<prefix>/<model>`.

Os nós personalizados de Chat Completions adaptam as desativações explícitas de raciocínio ao back-end upstream. Um teste de conexão bem-sucedido seleciona automaticamente os controles de modelo de chat para cada ID de modelo exato cuja entrada em `/models` comprove um valor reconhecido de `owned_by`: `vllm`, `sglang` ou `llamacpp`.
Wrappers transparentes compatíveis com OpenAI podem preservar a entrada de modelo original dentro de um objeto `openai` aninhado; a detecção percorre até três desses envelopes. Modelos com propriedade de propriedade ausente, desconhecida ou conflitante mantêm o comportamento comum da OpenAI. A detecção reutiliza a solicitação de catálogo existente, não gera tokens de conclusão e é invalidada quando o endpoint de conexão é alterado.

Para fixar o comportamento de um back-end que não expõe esses metadados, use a API existente de atualização parcial do provedor:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envie esse corpo com `PUT /api/providers/<connection-id>`. Nessa conexão, um esforço de raciocínio explícito de `none` é enviado como `chat_template_kwargs.thinking=false` e
`chat_template_kwargs.enable_thinking=false`. Os valores explícitos do modelo nativo permanecem autoritativos, a menos que uma regra de raciocínio no servidor force um esforço. A configuração se aplica somente quando uma conexão personalizada compatível com OpenAI despacha um corpo de Chat Completions; solicitações de Responses e provedores comuns mantêm seu formato de solicitação nativo. Defina `reasoningControl` como `openai` para forçar a passagem comum de `reasoning_effort` da OpenAI ou omita-o/defina-o como `null` para usar a detecção automática.

As solicitações do classificador do modo automático do Claude Code mantêm o pensamento nativo desabilitado por padrão quando não contêm controles de raciocínio explícitos. A detecção usa o marcador de sistema do classificador em solicitações no formato Claude, não nomes de modelos nem limites de conclusão. Controles explícitos no corpo, cabeçalhos de esforço/pensamento compatíveis, regras de roteamento e o esforço de modelo resolvido mantêm sua prioridade existente. Ambos os estágios do classificador preservam seus prompts, limites de conclusão, sequências de parada e veredictos reais de permissão do upstream; o segundo estágio ainda pode produzir o raciocínio visível solicitado como texto comum.

#### Proveniência dos limites do modelo

`GET /api/models?withLimits=1` (também `true`; `0`/`false` ou sua omissão mantém o
payload padrão inalterado) adiciona `contextWindow`, `maxInputTokens`, `maxOutputTokens` e um objeto `capsSource` a cada linha de modelo. `capsSource` identifica a regra que forneceu cada limite, para que um limite surpreendente (por exemplo, 128k em um modelo de 1M) possa ser rastreado até sua origem. Os valores resolvidos são os mesmos usados pelo roteamento; o sinalizador apenas adiciona campos e nunca altera um valor. Qualquer outro valor de `withLimits` é rejeitado com `400`.

| Valor de `capsSource`                        | Origem                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------ |
| `override:context`                           | Substituição persistida da janela de contexto (`model_context_overrides`)      |
| `override:max_input` / `override:max_output` | Substituição persistida da capacidade `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Tabela estática autoritativa de janelas de contexto                            |
| `synced:<provider>/<model>`                  | Linha de capacidade sincronizada de models.dev                                 |
| `registry:<provider>/<model>`                | Entrada do registro do provedor                                                |
| `spec:<model>`                               | Especificação estática do modelo                                               |
| Prefixo `effort-base:`                       | Linha emprestada do modelo-base de uma variante com sufixo de esforço          |
| `none`                                       | Nenhuma fonte declara o limite (o valor é `null`)                              |

Implementação: `getResolvedModelCapabilitiesWithLimitSources()` em `src/lib/modelCapabilities.ts`
e as cadeias de precedência em `src/lib/modelCapabilityLimits.ts`.

### Versão e canal de lançamento

```bash
GET /api/system/version
```

Rota de gerenciamento exclusiva para loopback (autenticação de administrador). Retorna a versão em execução, a versão mais recente
publicada e o status da atualização automática. `releaseChannel` e `channels` são
campos aditivos (linha 3.8.54); `channel` mantém seu significado — o modo de implantação que o atualizador do dashboard
usa (`npm`, `source` ou `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal npm da build em execução: `nightly` para versões `-nightly.*`,
  `next` para outras pré-lançamentos (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para uma versão estável de uma
  versão principal mais antiga que `channels.latest`; caso contrário, `latest`. As mesmas regras de
  `scripts/release/dist-tag.mjs`, que escolhe a dist-tag do npm no momento da publicação.
- `channels` — versão mais recente publicada de cada dist-tag, de `npm view omniroute dist-tags` (fallback HTTP do registro), armazenada em cache com o mesmo TTL de 10 minutos que `latest`. `latest` está sempre presente
  (usa o campo `latest` como fallback e, depois, `"unavailable"`); `next`, `nightly` e `lts` aparecem
  somente quando essa dist-tag existe. Uma solicitação com `Cache-Control: no-cache` atualiza ambas as consultas.

O modelo de canais (`latest` = v3 até a versão 4.0 GA, `next` = rc, `nightly` = builds de `develop`,
`lts` = patches da v3 após a versão 4.0 GA) é descrito em `docs/ops/RELEASE_STRATEGY.md`.

## Transcrição de áudio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transcreva arquivos de áudio usando qualquer provedor STT configurado. O primeiro
segmento do caminho seleciona o provedor nativo (`openai/…`, `deepgram/…`). Gateways que
reexportam o modelo de outro fornecedor usam um ID qualificado
(`openrouter/deepgram/nova-3`).

**Solicitação:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Resposta:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**IDs de modelo de exemplo:** `openai/whisper-1` (requer uma chave da OpenAI),
`openrouter/deepgram/nova-3` (requer uma chave da OpenRouter),
`deepgram/nova-3` (requer uma chave nativa da Deepgram). Uma solicitação simples para
`deepgram/nova-3` **não** usa a OpenRouter.

**Formatos compatíveis:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Aliases tokenizados do VS Code / sem cabeçalho

Use estes aliases quando uma integração não puder inserir um cabeçalho `Authorization` e precisar que a chave da API seja incorporada à URL base.

```bash

GET /api/v1/vscode/{token}/models

# Aliases de chat no estilo OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Aliases no estilo Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Exemplo:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models

  -H "Content-Type: application/json" \

```

Observações:

- Os aliases tokenizados reutilizam os mesmos handlers de `/v1/*` e `/api/tags`; os formatos das respostas permanecem idênticos.
- Prefira `Authorization: Bearer ...` sempre que o cliente for compatível com cabeçalhos personalizados.
- Os tokens baseados em URL podem aparecer nos logs de proxy reverso, no histórico do navegador e na telemetria fora do OmniRoute. Trate-os como uma opção de compatibilidade, não como o modo de autenticação padrão.

```bash
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **Observações sobre o esquema** (`setBudgetSchema`): `apiKeyId` é obrigatório; pelo menos um de `dailyLimitUsd`, `weeklyLimitUsd` ou `monthlyLimitUsd` deve ser maior que zero. Campos opcionais: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). O formato legado `{keyId, limit, period}` retorna `400 Bad Request`.

## Limites de tokens

Orçamentos de **tokens** por chave de API (distintos do orçamento baseado em USD acima). Aplicados inline no caminho da requisição: quando o uso da janela atual de uma chave atinge o limite, as requisições são rejeitadas com `429 Too Many Requests`. Os limites podem ter escopo definido para um `model` específico, um `provider` ou ser aplicados `global`mente à chave; quando vários limites correspondem a uma requisição, o mais restritivo vence.

```bash
# Listar os limites de tokens de uma chave (inclui o uso da janela em tempo real)
GET /api/usage/token-limits?apiKeyId=key-123

# Criar ou atualizar um limite de tokens
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Excluir um limite de tokens por id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Observações sobre o esquema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) são obrigatórios. `scopeValue` é obrigatório, a menos que `scopeType` seja `global` (por exemplo, um id de modelo para o escopo `model` ou um id de provedor para o escopo `provider`). `tokenLimit` deve ser um número inteiro positivo (convertido a partir de uma string). Opcional: `id` (omita para criar, informe para atualizar), `resetInterval` (`daily` | `weekly` | `monthly`, padrão `monthly`), `resetTime` (`HH:MM`), `enabled` (padrão `true`). As respostas de `GET` enriquecem cada limite com `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Este é um endpoint de classe de gerenciamento (a autenticação é aplicada centralmente pelo pipeline de autorização).

## Processamento de requisições

1. O cliente envia uma requisição para `/v1/*`
2. O manipulador de rota chama `handleChat`, `handleEmbedding`, `handleAudioTranscription` ou `handleImageGeneration`
3. O modelo é resolvido (provedor/modelo direto ou alias/combo)
4. As credenciais são selecionadas do banco de dados local com filtragem de disponibilidade de contas
5. Para chat: `handleChatCore` verifica o cache semântico/de assinaturas e resolve as configurações de compressão do combo
6. A compressão proativa é executada antes da tradução para o provedor quando habilitada (`lite`, Caveman, RTK ou empilhada)
7. O executor do provedor envia a requisição upstream
8. A resposta é traduzida de volta para o formato do cliente (chat) ou retornada como está (embeddings/imagens/áudio)
9. O uso, as análises de compressão e os logs de requisições são registrados
10. O fallback é aplicado em caso de erros de acordo com as regras do combo

Referência completa da arquitetura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resiliência (estendida)

O OmniRoute expõe três mecanismos independentes de falha temporária; os endpoints de gerenciamento abaixo permitem que os operadores os leiam e sobrescrevam:

| Escopo                       | Armazenamento do estado                           | Leitura                                   | Redefinir / limpar                                     |
| ---------------------------- | ------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------ |
| Disjuntor do provedor        | `domain_circuit_breakers` + memória               | `/api/monitoring/health`                  | `POST /api/resilience/reset`                           |
| Período de espera da conexão | `rateLimitedUntil` nas conexões do provedor       | `/api/rate-limits`, `/api/providers/[id]` | (reativado de forma lenta; limpar via PUT do provedor) |
| Bloqueio do modelo           | Registro de disponibilidade de modelos em memória | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`               |

`PATCH /api/resilience` aceita substituições do disjuntor do provedor em `providerBreaker.oauth` e `providerBreaker.apikey`. Cada perfil é compatível com `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; os mesmos campos são expostos em Painel → Configurações → Resiliência.

```bash
# Limpar o bloqueio de um único modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Remover todos os bloqueios
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Para obter a referência conceitual completa e os padrões do disjuntor, consulte [`CLAUDE.md`](../../CLAUDE.md) → "Estado de execução da resiliência" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Fila de limitação de taxa e rede de segurança de ativação automática

- **Caminho de gravação compatível**: `POST /api/rate-limits` com o corpo `{"connectionId": "<id>", "enabled": true|false}` é o endpoint de gerenciamento compatível para alternar a proteção contra limitação de taxa de uma conexão. `PUT /api/providers/[id]` deliberadamente não modifica nem alterna `rateLimitProtection` (#11278).
- **Semântica de `enabled: false`**: definir `enabled: false` remove a proteção explícita da conexão, mas **não** exclui uma conexão ativa com chave de API da rede de segurança global de ativação automática (`autoEnableApiKeyProviders = true`). Em `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` são equivalentes; as conexões ativas com chave de API sem proteção explícita permanecem protegidas pela rede de segurança de ativação automática.
- **Desativação global**: para executar conexões com chave de API sem filas de limitação de taxa, desative globalmente a rede de segurança por meio de `RATE_LIMIT_AUTO_ENABLE=false` (env) ou `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Configurações → Resiliência / `PATCH /api/resilience`).

### Análise de roteamento automático

| Método | Caminho                              | Descrição                                                                                                                                       |
| ------ | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/analytics/auto-routing`        | Estatísticas agregadas de roteamento automático: total de chamadas, distribuição de estratégias, distribuição por nível e principais provedores |
| GET    | `/api/analytics/auto-routing?days=7` | Estatísticas por janela de tempo (padrão: 24 h)                                                                                                 |

**Exemplo de resposta**:

```json
{
  "window": "24h",
  "totalCalls": 1234,
  "strategyBreakdown": {
    "rules": 800,
    "cost": 200,
    "latency": 150,
    "sla-aware": 50,
    "lkgp": 34
  },
  "tierBreakdown": {
    "ultra": 100,
    "pro": 500,
    "standard": 400,
    "free": 234
  },
  "topProviders": [
    { "provider": "openai", "calls": 500, "avgLatencyMs": 850 },
    { "provider": "anthropic", "calls": 300, "avgLatencyMs": 1200 }
  ]
}
```

### Rastreamento da diversidade de provedores

| Método | Caminho                    | Descrição                                                                                                                         |
| ------ | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/analytics/diversity` | Rastreamento de diversidade com base na entropia de Shannon: evita pontos únicos de falha medindo a distribuição entre provedores |

**Exemplo de resposta**:

```json
{
  "window": "24h",
  "shannonEntropy": 2.45,
  "maxEntropy": 3.17,
  "diversityRatio": 0.77,
  "providerUsage": {
    "openai": 0.4,
    "anthropic": 0.25,
    "google": 0.2,
    "kiro": 0.15
  },
  "warnings": ["OpenAI accounts for 40% of traffic — consider diversifying"]
}
```

**Autenticação:** requer uma sessão de gerenciamento ou uma chave de API com
escopo de gerenciamento.

## Autenticação

Consulte [Autenticação de gerenciamento](../guides/MANAGEMENT-AUTH.md) para conhecer as quatro
famílias de credenciais (sessão do dashboard, token local da CLI, token de acesso `oma_live_…`, chave de API com escopo de gerenciamento) e como elas diferem das chaves de inferência.

- As rotas do dashboard (`/dashboard/*`) usam o cookie `auth_token`
- O login usa o hash de senha salvo; como fallback, usa `INITIAL_PASSWORD`
- O toggle `requireLogin` pode ser configurado por `/api/settings/require-login`
- As rotas `/v1/*` opcionalmente exigem uma chave de API Bearer quando `REQUIRE_API_KEY=true`
- "token de gerenciamento" / "chave de API com escopo de gerenciamento" nesta referência significa uma das famílias descritas nesse guia — não um tipo adicional de segredo indefinido

> **Alteração incompatível (v3.8.0)** — `/api/v1/agents/tasks/*` e os endpoints de gerenciamento de cooldown agora exigem **autenticação de gerenciamento** (cookie `auth_token` do dashboard ou uma chave de API com escopo de gerenciamento). Os clientes que anteriormente chamavam essas rotas sem autenticação receberão `401 Unauthorized`. Consulte o commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
