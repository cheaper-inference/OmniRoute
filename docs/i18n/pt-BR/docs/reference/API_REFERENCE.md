## Conclusões de chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Cabeçalhos personalizados

| Cabeçalho                | Direção    | Descrição                                                                                                                                                                                                                           |
| ------------------------ | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Requisição | Defina como `true` para ignorar o cache                                                                                                                                                                                             |
| `x-omniroute-no-memory`  | Requisição | Defina como `true` para ignorar a injeção de memória + habilidades nesta requisição (reflete no-cache; evita a sobrecarga de tokens/custo por chamada)                                                                              |
| `X-OmniRoute-Progress`   | Requisição | Defina como `true` para receber eventos de progresso                                                                                                                                                                                |
| `X-Session-Id`           | Requisição | Chave de sessão persistente para afinidade de sessão externa                                                                                                                                                                        |
| `x_session_id`           | Requisição | A variante com sublinhado também é aceita (HTTP direto)                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | Requisição | Tag de sessão/conversa fornecida pelo chamador (também alimenta a memória). Quando presente, é persistida literalmente em `call_logs.session_tag` para atribuição de custos por sessão (#8249) — nunca é sintetizada quando ausente |
| `Idempotency-Key`        | Requisição | Chave de desduplicação (janela de 5s)                                                                                                                                                                                               |
| `X-Request-Id`           | Requisição | Chave de desduplicação alternativa                                                                                                                                                                                                  |
| `x-omniroute-connection` | Requisição | Fixa uma requisição de modelo único a uma conexão de provedor (conta) pelo respectivo id — consulte [Fixação de conta por requisição](#account-pinning-per-request)                                                                 |
| `X-OmniRoute-Cache`      | Resposta   | `HIT` ou `MISS` (sem streaming)                                                                                                                                                                                                     |
| `X-OmniRoute-Idempotent` | Resposta   | `true` se desduplicada                                                                                                                                                                                                              |
| `X-OmniRoute-Progress`   | Resposta   | `enabled` se o acompanhamento de progresso estiver ativado                                                                                                                                                                          |
| `X-OmniRoute-Session-Id` | Resposta   | ID efetivo da sessão usado pelo OmniRoute                                                                                                                                                                                           |
| `X-OmniRoute-Request-Id` | Resposta   | ID de correlação da requisição (quando conhecido)                                                                                                                                                                                   |
| `X-OmniRoute-Version`    | Resposta   | Versão da build do OmniRoute (sempre presente)                                                                                                                                                                                      |
| `X-OmniRoute-Cost-Saved` | Resposta   | Valor em USD que o cache evitou em um HIT (somente acertos de cache)                                                                                                                                                                |
| `X-OmniRoute-Decision`   | Resposta   | Rastreamento de roteamento: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` é a estratégia do combo ou `single` para uma requisição sem combo) — sempre presente nas respostas de conclusão                           |

> Observação sobre o Nginx: se você depende de cabeçalhos com sublinhados (por exemplo, `x_session_id`), habilite `underscores_in_headers on;`.

#### Fixação de conta por solicitação

Quando um provedor tem várias conexões (contas ou chaves), o OmniRoute normalmente escolhe uma
por meio de sua estratégia de seleção de contas. Como alternativa, uma solicitação pode fixar
uma conexão específica com o cabeçalho `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Onde encontrar o ID.** Abra a página do provedor no painel
  (**Painel → Provedores → <provider>**) e clique no chip de ID `xxxxxxxx…` em uma linha de
  conexão — isso copia o ID completo da conexão.
- **Quais solicitações o respeitam.** Solicitações de modelo único (`provider/model`) em
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. As combinações ignoram o cabeçalho:
  fixe uma conta por etapa da combinação por meio da própria conexão da etapa.
- **A fixação é estrita, não uma preferência.** A conexão fixada é usada exclusivamente. Uma
  falha durante a solicitação registra o período de espera da conta, mas **não** alterna para
  outra conta do mesmo provedor.
- **O período de espera e a cota liberam a fixação.** Enquanto a conexão fixada estiver em
  período de espera, com a cota esgotada ou bloqueada por uma política de cotas, solicitações
  posteriores recorrerão às outras conexões do provedor, exatamente como o tráfego não fixado.
- **IDs desconhecidos ou desabilitados causam falha.** Um ID que não esteja no pool ativo do
  provedor (excluído, desativado ou pertencente a outro provedor) não deixa nenhuma conta
  qualificada, portanto a solicitação falha em vez de ser silenciosamente roteada para outro lugar.

O Claude Code envia cabeçalhos personalizados por meio de `ANTHROPIC_CUSTOM_HEADERS`. Coloque-o no
bloco `env` de `~/.claude/settings.json` ou em um `.claude/settings.json` no nível do projeto para
fixar uma conta diferente por projeto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fonte: `src/sse/handlers/chat.ts` (leitura do cabeçalho), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (liberação da fixação e verificação de ausência no pool).

> **Cabeçalhos de telemetria de custos:** as respostas bem-sucedidas sem streaming também incluem o conjunto de telemetria de custos `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, com 10 casas decimais fixas; `0.0000000000` quando gratuito/sem preço), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (somente quando > 0), além de `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Eles são emitidos por conclusões de chat, `/v1/responses`, `/v1/messages` **e pelos endpoints de mídia** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (sempre com custo `0`). O custo de mídia é calculado por modalidade (por imagem, por segundo, por caractere, por unidade de pesquisa) quando os preços estão disponíveis; caso contrário, é `0` (fail-open).

> **Semântica de custo em acertos de cache:** em um ACERTO no cache semântico (`X-OmniRoute-Cache-Hit: true`), nenhuma chamada upstream é feita, portanto `X-OmniRoute-Response-Cost` é `0.0000000000` (o custo **incremental** de servir o acerto). O custo original/que teria ocorrido é informado separadamente em `X-OmniRoute-Cost-Saved`. Os consumidores de dados de cobrança devem somar `X-OmniRoute-Response-Cost` (acertos não custam nada); as análises de cache podem agregar `X-OmniRoute-Cost-Saved`.

## Leases exclusivas de sessões gerenciadas

A lease exclusiva de sessão gerenciada é um contrato de roteamento opcional e neutro em relação ao cliente: um proprietário ativo
mantém uma conexão OmniRoute elegível. Ela não concede um modelo, não exige OAuth, não identifica um
cliente específico nem exige um provedor específico.

A chave de API usada na autenticação deve ter o escopo `lease:exclusive` e uma lista
`allowedConnections` explícita e não vazia. O limite de mutação do banco de dados exige os dois campos em conjunto durante a
criação da chave e em atualizações parciais.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

As respostas bem-sucedidas de aquisição, renovação e liberação expõem timestamps, `state` e o valor positivo exato de
`generation`, mas nunca a conexão selecionada ou as credenciais. A renovação e a liberação fornecem a
geração no corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

O proprietário de uma lease ativa pode solicitar explicitamente metadados de exibição seguros para a privacidade referentes à sua vinculação atual:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Essa ação opcional de status é protegida, em uma única transação de banco de dados, pelo proprietário opaco, pela chave de API gerenciada autenticada e pela
geração ativa exata. `displayName` contém somente o nome configurado da
conexão após a remoção de espaços em branco nas extremidades; seu valor é `null` quando não existe um nome configurado seguro. O OmniRoute nunca o substitui por um
e-mail ou por uma identidade de conta gerada. O valor do provedor é um rótulo de exibição não sensível e nunca
um identificador gerado de provedor compatível. Credenciais, tokens, cookies, IDs brutos de conexão ou de chave de
API, hashes de proprietário, segredos de fencing e dados internos de roteamento são excluídos.

Consultas com chave incorreta, proprietário incorreto, geração obsoleta, lease ausente, expirada, liberada ou invalidada
retornam todas o mesmo erro `409 LEASE_FENCE_STALE`, sem metadados da conexão. Um cliente que recebeu a resposta de espera por capacidade não tem uma vinculação ativa para consultar. Quando o roteamento faz a transição de uma lease ativa,
a mesma geração permanece válida, e o status retorna atomicamente a nova vinculação, nunca a antiga.
Os clientes existentes permanecem inalterados porque as respostas de aquisição, renovação, liberação e espera mantêm
seus formatos anteriores.

Esse contrato do servidor não altera o `/status` padrão do OpenAI Codex. Atualmente, o Codex padrão informa seu
provedor de modelo e o estado interno de autenticação/conta, mas não renderiza metadados arbitrários de
contas de provedores personalizados; uma integração futura do cliente deverá chamar essa ação e decidir como
exibir `connection.displayName`.

Cada solicitação de inferência gerenciada fornece, então, ambos os cabeçalhos de controle:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

O proprietário exato, a geração, a conexão ativa e a chave de API autenticada são submetidos à verificação de fencing imediatamente
antes de cada tentativa upstream compatível. Reutilizar o proprietário e a geração com outra chave falha mesmo
quando essa chave permite a mesma conexão. Os proprietários brutos não são persistidos, registrados em logs, mantidos no
snapshot da solicitação nem encaminhados ao upstream.

A contenção temporária retorna HTTP `429` com `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Essa resposta significa apenas que o conjunto comum de conexões elegíveis não estava vazio e que todos os candidatos livres estavam
mantidos por uma lease ativa de outro proprietário. Modelos/provedores não compatíveis, incompatibilidade de política, cooldown, cota,
integridade e outras falhas comuns de elegibilidade mantêm suas respostas existentes do OmniRoute.

### `x-omniroute-compression`

Substituição do plano de compressão por solicitação. Tem a maior precedência — prevalece sobre a substituição do combo de
roteamento, o perfil ativo, o acionamento automático e o Padrão do painel. Valores:

| Valor         | Efeito                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| `off`         | Sem compressão para esta solicitação.                                                                           |
| `default`     | O perfil Padrão derivado do painel (ignora o perfil ativo). Mecanismos com perdas permanecem desativados.       |
| `safe`        | Somente desduplicação e compactação de espaços em branco.                                                       |
| `allow-lossy` | Mantém o plano do operador para esta solicitação, incluindo resumos e reescritas de estilo.                     |
| `engine:<id>` | Um único mecanismo, quando habilitado; por exemplo, `engine:rtk`. Adesão por solicitação para esse mecanismo.   |
| `<combo>`     | Um combo nomeado, correspondido primeiro pelo nome (sem diferenciar maiúsculas de minúsculas) e depois pelo ID. |

Observações:

- Valores desconhecidos são ignorados (a solicitação nunca é rejeitada); a resolução prossegue para a precedência normal do operador.
- Se vários combos tiverem o mesmo nome, forneça o **id** do combo para obter uma correspondência determinística.
- Um combo cujo nome seja `off` ou `default` não pode ser selecionado pelo nome (essas palavras-chave são interpretadas primeiro); faça referência a esse combo por seu ID.
- O seletor mestre de compressão é uma barreira rígida: quando a compressão está desabilitada globalmente, esse cabeçalho não pode habilitá-la.

O plano aplicado é retornado no cabeçalho da resposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

em que `<source>` é um dos seguintes valores: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ou `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Provedores disponíveis: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Os IDs do catálogo seguem o formato `provider/model` (exemplo: `jina-ai/jina-embeddings-v5-omni-small`). IDs simples de modelos Jina que aparecem no registro (por exemplo, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) também são resolvidos. As operações embed/rerank/classify/segment da Jina usam primeiro as credenciais `jina-ai` do painel; `JINA_AI_API_KEY` é usada como alternativa somente quando não há uma chave no painel. O cartão `jina-reader` destina-se apenas ao Reader / `r.jina.ai` (`POST /v1/web/fetch`) e nunca fornece embeddings nem rerank.

Os modelos do registro que anunciam suporte multimodal também aceitam até 32 itens estruturados
independentes do provedor. Os tipos de item de mídia são `text`, `image`, `audio`, `video` e `document`. O `source`
da mídia é `{"type":"url","url":"https://..."}` ou
`{"type":"base64","data":"...","media_type":"..."}`.

O Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
e o alias da família `jina-ai/jina-embeddings-v5-omni` → omni-small) também aceita os documentos nativos
EmbeddingsV5Request da Jina e **os encaminha intactos** para `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Os valores nativos `{ image | audio | video | pdf }` podem ser uma URL HTTPS pública, um URI `data:` ou dados
base64 brutos. O OmniRoute não converte esses objetos em strings nem busca URLs de imagens nativas — a Jina recupera
a mídia pública por conta própria. Campos adicionais da Jina (`task`, `normalized`, `truncate`, `embedding_type`) são
encaminhados. SKUs da Jina exclusivos para texto ainda rejeitam documentos que não sejam de texto.

Limites de segurança e transporte:

- URLs de mídia remota devem usar HTTPS público. Itens canônicos `{type,source:url}` são buscados
  no lado do servidor (revalidação de redirecionamentos, tempo limite, limites de tamanho, DNS público e
  fixação de conexão) e incorporados antes da chamada ao provedor. Itens nativos da Jina `{image:"https://..."}` são encaminhados como estão
  após a mesma verificação de HTTPS público; a Jina busca a URL.
- Mídias base64 inline são limitadas a 8 MiB decodificados por item e 16 MiB decodificados em toda a solicitação.

Tradução para provedores (itens canônicos nunca são encaminhados sem alterações):

- Modelos multimodais da Jina: cada item de nível superior torna-se um objeto com chave de modalidade
  (`text` / `image` / `audio` / `video` / `pdf`), usando URIs de dados para mídia inline; um vetor por
  item de nível superior.
- Família Gemini Embedding 2: um array de nível superior torna-se uma única solicitação nativa
  `models/{model}:embedContent` com `content.parts` (`text` ou `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualquer modelo carregado pelo servidor local): itens canônicos `text`
  tornam-se strings simples, e `image` / `audio` / `video` tornam-se, cada um, um objeto
  `{"content": [part]}`, usando as partes de conteúdo de chat do llama-server (`image_url`,
  `input_audio` com formato `wav` / `mp3` / `flac`, `input_video`) com dados inline; um vetor
  por item de nível superior. O servidor deve ser executado com `--embedding --mmproj …`; sem um projetor, ele
  próprio rejeita a mídia. `document` não é compatível.
- Modelos desconhecidos/dinâmicos sem metadados explícitos de modalidade rejeitam entradas estruturadas com HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Combinações de modelo/modalidade não compatíveis retornam HTTP 400 em vez de converter o item. Campos de extensão
que não sejam de entrada em solicitações legadas de strings/tokens continuam sendo repassados sem alterações.

```bash
# Listar todos os modelos de embedding
GET /v1/embeddings
```

## Geração de imagens

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Os provedores disponíveis incluem OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local) e ComfyUI (local).

`n` retorna `n` imagens em `data[]`. Os provedores cuja API upstream retorna uma imagem por chamada
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) recebem `n` chamadas upstream separadas, com no máximo 4 em andamento. Um
`seed` fixo é incrementado pelo índice da chamada (`seed`, `seed + 1`, …), para que as imagens sejam diferentes, mas permaneçam
reproduzíveis. `n` é limitado a 10. A solicitação falha por completo se qualquer chamada falhar. A lista
de formatos com fan-out é `SINGLE_IMAGE_FANOUT_FORMATS` em
`open-sse/handlers/imageGeneration/fanOut.ts`.

O ZenMux reutiliza a conexão de chave de API existente e aceita os prefixos `zenmux/` ou `zm/`:

- `zenmux/openai/gpt-image-2` usa a API OpenAI Images do ZenMux. As opções incluem `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Outros publicadores, como `zm/meta/muse-image-1.0`, usam o endpoint `:predict` do Vertex AI
  do ZenMux. `n` é mapeado para `sampleCount`, `aspect_ratio` para `aspectRatio` e `image_size`
  (`1K`, `2K`, `4K`) para `sampleImageSize`. Um `size` em pixels fornece apenas uma proporção,
  não dimensões garantidas em pixels. As proporções, resoluções e quantidades compatíveis variam de acordo com o modelo.
- `zm/inclusionai/ming-image-0.1-design` escolhe suas próprias dimensões. Omita `size`,
  `aspect_ratio` e `image_size`; valores explícitos retornam HTTP 400. PNG, JPEG e WebP
  podem ser solicitados com `output_format`.

Esta integração oferece geração de texto para imagem, não edição de imagens de referência. A saída do Vertex
é normalizada para `data[].b64_json`; `response_format: "url"` retorna uma URL HTTPS upstream
ou uma URL de dados base64 quando apenas os bytes da imagem estão disponíveis. Saídas vazias/filtradas
retornam um erro em vez de um sucesso vazio. O acesso aos modelos depende da conta do ZenMux.
Consulte a [API Vertex do ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) e a
[API OpenAI Images](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Listar todos os modelos de imagem
GET /v1/images/generations
```

## OCR de documentos

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleciona o provedor de OCR por meio de um prefixo `provider/model`; um id de modelo sem prefixo (por exemplo,
`mistral-ocr-latest`) é resolvido para seu provedor registrado, e um `model` omitido usa por padrão
o Mistral (`mistral-ocr-latest`). Provedores registrados (`open-sse/config/ocrRegistry.ts`):

| ID do provedor                | ID do modelo         | Valor de `model`                                              | Observações                                                                                                              |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (ou apenas `mistral-ocr-latest`) | Síncrono — a resposta é retornada diretamente pela única chamada upstream.                                               |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | Upstream assíncrono (`analyze` + polling) — veja abaixo.                                                                 |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | Síncrono, por meio do endpoint de parceiro `openapi/chat/completions` do Vertex AI — veja abaixo sobre autenticação/URL. |

Todos os três provedores respondem com o mesmo corpo no formato do Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxo de polling do Azure Document Intelligence

A API `analyze` do Azure Document Intelligence é assíncrona: a solicitação inicial retorna um
cabeçalho `Operation-Location` em vez de um corpo, e o resultado precisa ser consultado periodicamente. O handler
(`open-sse/handlers/ocr.ts`) consulta essa URL a cada segundo por até 30 tentativas, falha imediatamente (não
continua o polling) em uma resposta de polling que não seja `ok` ou em um status `"failed"`, e retorna `504` se a
operação ainda estiver em andamento após o limite de tentativas ser esgotado. A resposta final do Azure é
normalizada para o mesmo formato `pages`/`markdown` usado pelo Mistral antes de ser retornada ao
chamador, portanto o código cliente não precisa tratar o provedor de forma especial.

### Autenticação e resolução de endpoint do Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` reutiliza a mesma autenticação do Vertex AI que o OmniRoute já oferece para
tráfego de chat/imagem (`open-sse/executors/vertex.ts`): a chave de API da conexão é uma
credencial JSON de Service Account (trocada por um token de acesso OAuth de curta duração por meio do fluxo
JWT bearer) ou um token de acesso OAuth já emitido, usado como está. A URL do endpoint upstream é o
endpoint genérico de parceiro `openapi/chat/completions` do Vertex, criado com base no projeto e na
região da conexão — um `providerSpecificData.project`/`providerSpecificData.region` explícito sempre prevalece;
caso contrário, o projeto é derivado do `project_id` do JSON da Service Account, e o padrão da região
é `us-central1`. Ambas as resoluções ocorrem em `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e são consumidas por
`src/app/api/v1/ocr/route.ts` antes do encaminhamento para `handleOcr`.

## Listar modelos

```bash
GET /v1/models
Authorization: Bearer sua-chave-de-api

→ Retorna todos os modelos de chat, embedding e imagem + combos no formato OpenAI
```

### Preços dos modelos (`pricing`)

Uma entrada contém um objeto `pricing` quando o OmniRoute conhece o preço do modelo. O preço vem
da tabela de preços usada pela contabilização de custos: valores padrão integrados, preços sincronizados e
substituições definidas por meio de `/api/pricing`. Esses são preços de tabela, portanto, provedores de assinatura também
exibem um preço por token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Campos                                                          | Unidade                            | Observações                                                                                                                                                   |
| --------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD por token, string decimal      | Compatível com OpenRouter, nunca em notação exponencial. Os dois campos de cache aparecem apenas quando há um preço de cache.                                 |
| `input`, `output`, `cached`, `cache_creation`                   | USD por 1 milhão de tokens, número | Campos de versões anteriores do catálogo, mantidos para clientes existentes. `reasoning` e `long_context` também aparecem quando a linha de preços os contém. |

- **Combos** contêm o preço do primeiro destino visível. Combos `auto/*` integrados escolhem um
  destino no momento da requisição, portanto, não têm `pricing`.
- **Modelos gratuitos** exibem `"0"` (e `0`) quando seu preço é zero. Um modelo sem uma linha de preços
  também exibe `"0"` quando o catálogo o marca como gratuito (`free: true`) ou quando o catálogo
  integrado de modelos gratuitos o inclui.
- **Preço desconhecido:** a entrada não contém a chave `pricing`.
- **Provedores medidos por créditos** (como o Kiro) cobram por requisição, em vez de por token. Suas
  entradas mantêm os campos numéricos por 1 milhão que já tinham e não contêm campos de string por token.
- **Variantes** (IDs de esforço de raciocínio, aliases sem raciocínio, espelhos de descoberta e de gateway)
  copiam o preço do modelo para o qual roteiam.
- Os campos contêm apenas as tarifas base. Faixas de contexto longo (o campo numérico `long_context`) e
  multiplicadores de nível de serviço (por exemplo, Codex fast ou flex) não alteram `prompt` nem
  `completion`.
- O objeto é o mesmo para todos os estilos de autenticação, incluindo uma requisição no estilo Anthropic
  com `x-api-key` e `anthropic-version` (a resposta permanece `{ "object": "list",
"data": [...] }`). Implementação: `src/app/api/v1/models/catalogPricing.ts`.

### Prefixos de ID de modelo (`?prefix=`)

A maioria dos modelos é anunciada sob um **prefixo de provedor**. O prefixo recebido é controlado pelo
sinalizador de recurso `MODELS_CATALOG_PREFIX_MODE` e pode ser substituído **por requisição** com um
parâmetro de consulta — útil para um cliente que deseja uma lista limpa sem alterar a configuração
do servidor inteiro para todos os outros:

```bash
GET /v1/models?prefix=alias        # um ID por modelo — o prefixo curto do alias
GET /v1/models?prefix=dual         # ambas as formas (padrão do servidor)
GET /v1/models?prefix=canonical    # apenas o prefixo completo do ID do provedor
```

| Modo        | Emite                                                   | Observações                                                                                                                                                                                          |
| ----------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **e** `claude/claude-sonnet-4-6` | **Padrão.** Ambos os IDs roteiam para o mesmo modelo; mantido para que as configurações de clientes que codificaram uma das formas continuem funcionando. Praticamente duplica o catálogo.           |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Uma entrada por modelo. Provedores sem um alias distinto ainda emitem sua entrada, portanto, nada é perdido.                                                                                         |
| `canonical` | `claude/claude-sonnet-4-6`                              | Uma entrada por modelo sob o prefixo completo do ID do provedor. Provedores sem um alias distinto (por exemplo, `antigravity/…`, `agy/…`) também emitem seu único ID aqui, portanto, nada é perdido. |

Um espelho no modo `dual` também pode ser reconhecido sem o parâmetro de consulta: ele contém um campo `parent`
que aponta para o ID principal.

Clientes que renderizam um seletor de modelos devem solicitar `?prefix=alias` — é isso que a
[extensão OmniCopilot para VS Code](../guides/VSCODE-COPILOT.md) faz.

### Filtros de descoberta (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` aceita filtros de descoberta opcionais. Sem nenhum deles, a resposta permanece
inalterada. Eles restringem o catálogo que o chamador já pode ver (as permissões da chave de API são aplicadas primeiro)
e são executados antes da paginação `limit` / `after` no estilo OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # todas as capacidades listadas devem ser verdadeiras
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` do catálogo; linhas sem um valor são `chat`
GET /v1/models?q=sonnet&limit=10                           # correspondência sem diferenciar maiúsculas de minúsculas no ID ou nome
```

| Parâmetro     | Valores                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | inteiro não negativo, comparado com `context_length`                                                |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caracteres                                                                                    |

Um valor desconhecido, ou um `min_context` que não seja um inteiro não negativo (por exemplo, `1.5`),
retorna HTTP `400`, e a mensagem lista os valores válidos. Implementação:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista reduzida de modelos (`POST /v1/models/query`)

`POST /v1/models/query` retorna uma lista curta e determinística do mesmo catálogo, com a mesma
autenticação e visibilidade por chave que `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Todos os campos são opcionais. `capabilities` e `exclude` aceitam um array ou uma string separada por vírgulas;
`max_output` é comparado com `max_output_tokens`. Os resultados são ordenados por `owned_by` e, em seguida, por `id`.
O valor padrão de `limit` é `20`, e valores acima de `100` são limitados a `100`. JSON inválido, um campo
desconhecido ou um valor inválido retorna HTTP `400`.

### Modelos de chat ocultados individualmente

Um modelo marcado como **Oculto** na página do provedor é excluído do catálogo e rejeitado
com HTTP `404` / `model_not_found` quando solicitado explicitamente. A verificação usa o
provedor e o modelo resolvidos, incluindo aliases de provedores, prefixos de nó de provedores
compatíveis e padrões de conexão. Uma combinação ignora destinos ocultos e pode usar outro
destino visível; quando nenhum destino executável permanece, ela retorna o mesmo código de erro.
A remoção da ocultação entra em vigor na próxima solicitação. Substituições de visibilidade
exclusivas para imagens não ocultam o modelo de chat com o mesmo ID.

Essa configuração individual de modelo é separada das
[listas de permissão/bloqueio de exposição de modelos](../routing/MODEL_EXPOSURE_LIST.md), que filtram
a exibição no catálogo e os candidatos ao roteamento automático, mantendo o despacho explícito. As permissões
de modelo por chave de API continuam sendo aplicadas de forma independente. O modo padrão de prefixo do catálogo
permanece `dual`.

### Variantes de modelo sem raciocínio

Para modelos Claude com capacidade de raciocínio, `/v1/models` também anuncia uma variante **sem raciocínio**, cujo ID recebe o prefixo `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Selecionar esse ID (por exemplo, em uma configuração do Claude Code que sempre anexa um bloco `thinking`) resolve de volta para o `<provider>/<model>` real com o raciocínio suprimido — `thinking:{type:"disabled"}` no caminho `/v1/messages`, ou com os campos `reasoning`/`reasoning_effort` removidos no caminho `/v1/chat/completions`. A variante só é listada para modelos da família Claude que oferecem suporte a raciocínio **e** respeitam `disabled` (portanto, por exemplo, modelos exclusivamente adaptativos que rejeitam `disabled` são excluídos). Os operadores podem forçar a ativação ou desativação da variante por modelo por meio de `ModelSpec.noThinkingAlias`.

## Geração de áudio do ElevenLabs

Configure uma conexão de provedor `elevenlabs` no OmniRoute com sua chave de API do ElevenLabs.
Os clientes se autenticam com sua chave do **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
o gateway fornece a chave armazenada do provedor como `xi-api-key`. Nunca envie uma chave do ElevenLabs
como o token bearer do gateway.

| Método | Caminho                     | Resposta                                     | Categoria de endpoint da chave de API |
| ------ | --------------------------- | -------------------------------------------- | ------------------------------------- |
| POST   | `/v1/sound-generation`      | Bytes de áudio nativos                       | `elevenlabs`                          |
| POST   | `/v1/music`                 | Bytes de áudio nativos                       | `music`                               |
| POST   | `/v1/music/stream`          | Bytes de áudio por streaming                 | `music`                               |
| POST   | `/v1/music/detailed`        | Áudio multipart nativo e plano de composição | `music`                               |
| POST   | `/v1/music/detailed/stream` | Metadados SSE nativos e blocos de áudio      | `music`                               |
| POST   | `/v1/music/plan`            | Plano de composição em JSON                  | `music`                               |

Esses endpoints complementam as rotas existentes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` e `/v1/speech-to-text`. Os campos JSON nativos
e os parâmetros de consulta, como `output_format` e `enable_logging`, são preservados.
As respostas de `/v1/music/detailed` mantêm seus limites multipart; interprete-as como multipart.
`/v1/music/detailed/stream` retorna `text/event-stream` com metadados de composição e
blocos de áudio em base64 nos eventos SSE. Todas as seis rotas são compatíveis com preflight de CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Um efeito sonoro curto. Duração: de 0,5 a 30 segundos.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# A duração da música é expressa em milissegundos: de 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Use `/v1/music/stream` com o mesmo corpo JSON para entrega incremental de áudio. A composição
aceita exatamente um entre `prompt` ou `composition_plan`; `/v1/music/plan` exige `prompt`
e aceita opcionalmente `source_composition_plan`. Os esquemas nativos preservam campos adicionais
do provedor para que versões do plano de composição e opções de ajuste fino cheguem ao ElevenLabs.

O endpoint unificado `/v1/music/generations` também aceita `elevenlabs/music_v1`,
`elevenlabs/music_v2` e `elevenlabs/music_v2_5`. Com uma conexão ativa do ElevenLabs,
esses modelos são disponibilizados pelo catálogo de músicas. Esse endpoint retorna
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Seu campo `duration` é expresso em
segundos e é mapeado para `music_length_ms`; um `music_length_ms` explícito tem precedência.
`instrumental` é mapeado para `force_instrumental`, com o campo nativo tendo precedência.
Use os endpoints de streaming nativos para streaming e o endpoint de composição nativo
para solicitações orientadas apenas por um plano de composição.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

As restrições de endpoint, modelo, orçamento e conexão são aplicadas antes de uma chamada ao serviço upstream. As
rotas nativas retornam os códigos de status e os corpos de erro do serviço upstream sem alterações, incluindo `402` para uma
restrição de plano e `429` para um limite de cota. Os cabeçalhos `character-cost`, `song-id`, `request-id` e `retry-after`
são preservados quando presentes. Um saldo de créditos gratuitos não garante acesso a todos os
modelos de música, formatos de saída ou recursos da API: o ElevenLabs determina a autorização para cada solicitação.
O endpoint unificado preserva os códigos de status de erro no envelope de erro normalizado do OmniRoute.

Contratos upstream: [efeitos sonoros](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composição musical](https://elevenlabs.io/docs/api-reference/music/compose) e
[detalhes de música por streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Nós de provedor de reclassificação:** `POST /v1/rerank` também é roteado para nós de provedores compatíveis com OpenAI
> (oMLX, vLLM, Infinity, TEI atrás de um gateway, …) endereçados como `<node-prefix>/<model>`. Nós de
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) são sempre elegíveis, assim como os nomes de host que o
> operador lista em `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (por exemplo, um nome de serviço do Docker/Compose,
> como `http://reranker:8080/v1`; eles são chamados diretamente, nunca por meio de `HTTP(S)_PROXY` ou do
> proxy fixado de uma conexão). Nós em qualquer outro
> host — uma máquina na LAN ou um par do Tailscale — são elegíveis somente quando o operador habilita a
> flag de recurso `RERANK_REMOTE_PROVIDER_NODES` **e** a URL base do nó passa pela política de URLs
> de saída do provedor (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> A etapa de reclassificação do mecanismo de memória chama essa rota por
> loopback; portanto, a mesma regra controla `rerankProviderModel` nas configurações de Memória.
>
> **Formatos de servidores locais:** o nó é chamado em `<base>/v1/rerank` e, em caso de 404, em `<base>/rerank`
> (Infinity, TEI). O corpo enviado ao upstream inclui tanto a nomenclatura do Cohere/OpenAI (`documents`,
> `return_documents`) quanto a nomenclatura do TEI (`texts`, `return_text`), e a resposta do upstream é
> normalizada para o envelope do Cohere: o array simples do TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> de gateways leves e `{data: [...]}` no estilo do Voyage são todos retornados ao cliente como
> `{results: [{index, relevance_score, document?}]}`, ordenados por pontuação e limitados a `top_n`.

> **Descoberta de nós de provedor:** os modelos em um nó de provedor compatível com OpenAI aparecem em `GET /v1/models`
> sob o prefixo do nó. As linhas que não contêm metadados de endpoint (comum em listagens locais de `/v1/models`)
> herdam o `apiType` do nó; portanto, os modelos de um nó `embeddings` têm `type: "embedding"` e os modelos de um
> nó `rerank` têm `type: "rerank"` em vez de usarem chat como padrão; um
> `supportedEndpoints` explícito em uma linha sincronizada ou adicionada manualmente ainda tem precedência.

## Procurar API

abstração do provedor Web/search (Tavily, Brave, Exa, Serper, etc.).

| Método | Caminho                | Descrição                                                                                         |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------- |
| GET    | `/v1/search`           | Listar recursos + dos provedores de pesquisa configurados                                         |
| POST   | `/v1/search`           | Execute uma consulta de pesquisa — body validada por `v1SearchSchema`, suporta caching/coalescing |
| GET    | `/v1/search/analytics` | Estatísticas hit/latency/cache por provedor                                                       |

### Exa e Tavily `provider_options`

Exa e Tavily leem campos específicos do provedor de um pacote com namespace: `provider_options.exa` (ou `provider_options["exa-search"]`) e `provider_options.tavily` (ou `provider_options["tavily-search"]`). Somente as chaves abaixo são encaminhadas. Cada um é verificado em relação ao seu próprio esquema Zod em `open-sse/handlers/search/providerOptionsPassthrough.ts` e uma chave com o tipo errado é descartada. Qualquer outra chave é ignorada, incluindo auth, base URL, `stream` e `outputSchema`. As chaves simples usadas por outros provedores (`cx`, `depth`, ...) funcionam como antes.

| Provedor | Campos de nível superior                                                                                                                                                                                                                                                                                                                                                  | Aninhado                                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitivas planas), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` mesclado com o `{ text: true, highlights: true }` padrão |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                      |

Vencem sempre os campos genéricos: `query`, `max_results`, `filters` (domínios), `country` e o tópico derivado de `search_type`. No Exa, `search_type: "news"` mantém `category: "news"`. Tavily também aceita `search_type: "finance"` (`topic: "finance"`).

O custo da pesquisa Firecrawl é registrado por bloco iniciado de 10 resultados retornados, em US$ 0,002 (2 créditos) por bloco e pelo menos um bloco por chamada ( [faturamento Firecrawl](https://docs.firecrawl.dev/billing) ): 11 resultados custam US$ 0,004.

O `time_range` genérico agora alcança ambos os provedores: Exa obtém `startPublishedDate` (ISO timestamp) e Tavily obtém `start_date` (`YYYY-MM-DD`). Uma data explícita em `provider_options` substitui a data mapeada.

Os resultados do Exa mantêm `id`, `highlight_scores`, `summary`, `subpages`, `entities` e `extras` em `provider_raw`. Os resultados Tavily mantêm `images` e `favicon`.

O custo da pesquisa de linkup é registrado em US$ 0,005 para `depth` `fast` e `standard` e US$ 0,05 para `deep` ( [preço de linkup](https://docs.linkup.so/pages/documentation/development/pricing) ), independentemente de `depth` vir `provider_options` ou das configurações da conexão.

Exa `type: "lite"` (Exa 3.0) aceita um conjunto menor de campos e rejeita toda a solicitação quando qualquer outro campo é definido. Para Lite, `additionalQueries`, `systemPrompt` e todas as teclas `contents` exceto `text` e `highlights` são descartadas antes da chamada. Os obsoletos `subpages`, `subpageTarget`, `highlights.numSentences` e `highlights.highlightsPerUrl` não são mais encaminhados.

A contabilidade de custos é o registro simples `costPerQuery`, exceto para Exa, que segue o próprio preço do Exa: US$ 0,007 por chamada para `auto` (e o legado `fast`) ou US$ 0,004 para `lite` (e o legado `instant`), cobrindo 10 resultados; US$ 0,001 para cada resultado adicional; e US$ 0,001 por resultado retornado quando `contents.summary` estiver definido. Tavily é registrado em 1 crédito ($ 0,008) para `search_depth` `basic`, `fast` e `ultra-fast`, e 2 créditos ($ 0,016) para `advanced` ( [créditos Tavily API](https://docs.tavily.com/documentation/api-credits) ). Uma chamada com `auto_parameters: true` que Tavily atualiza para avançado ainda é registrada com 1 crédito.

## API de Busca Web

Extraia conteúdo de uma URL por meio de um provedor de busca web configurado (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

O Parallel Extract (`parallel-search`, mesma chave de API do Parallel Search) retorna apenas
Markdown — qualquer outro `format` resulta em um `400` — e limita o conteúdo a 100.000 caracteres. Quando
a própria página de destino não pode ser extraída, o serviço upstream informa isso em uma resposta HTTP 200;
o OmniRoute expõe essa situação como um `422` com uma mensagem fixa.

| Método | Caminho         | Descrição                                                    |
| ------ | --------------- | ------------------------------------------------------------ |
| POST   | `/v1/web/fetch` | Busca/extrai uma URL — corpo validado por `v1WebFetchSchema` |

**Autenticação:** chave de API Bearer (`extractApiKey` + `isValidApiKey`). Política aplicada por meio de `enforceApiKeyPolicy`.

**Fallback sensível à cota (#8297):** quando nenhum `provider` explícito é fornecido, o pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) é
percorrido em ordem fixa
de prioridade (preenchimento prioritário) — um provedor configurado, mas limitado por taxa, é ignorado
em vez de interromper imediatamente a solicitação, e uma falha upstream recuperável/de cota
(HTTP 429 sempre; 402/403 para planos gratuitos com restrições de cota do Firecrawl/Tavily/TinyFish —
não para o Jina Reader e nunca para uma simples solicitação inválida 400) faz com que a solicitação prossiga
para o próximo provedor ainda não testado que tenha credenciais, durante a própria solicitação. Quando todos os provedores do
pool estão esgotados, o endpoint retorna um único `429` (com um cabeçalho `Retry-After`)
em vez do antigo `400` genérico. Quando um `provider` explícito é
solicitado, **não há** fallback silencioso — um provedor explícito limitado por taxa ou com falha
expõe seu próprio erro (`429` se estiver limitado por taxa; caso contrário, o status
upstream).

## Streaming via WebSocket

```bash
GET /v1/ws?handshake=1
```

Valida um handshake de upgrade para WebSocket e retorna as mensagens de exemplo do protocolo de comunicação (`request`, `cancel`). Os frames WS reais são tratados pelo servidor WS incluído, fora da tabela de rotas do Next.js.

**Autenticação:** chave de API Bearer durante o handshake.

### Responses API via WebSocket (somente codex)

```bash
# Mesmo host:porta da API HTTP (padrão 20128); faça o upgrade da conexão:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ou: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# O primeiro frame DEVE ser response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Um proxy de Responses API via WebSocket está conectado **exclusivamente ao `codex`** (backend do ChatGPT). Ele escuta na mesma porta da API/do painel nos caminhos `/v1/responses`,
`/responses` e `/api/v1/responses`. No primeiro frame `response.create`, ele
autentica + prepara por meio da ponte interna `codex-responses-ws`, seleciona uma
conexão OAuth do codex e estabelece um túnel para `wss://chatgpt.com/backend-api/codex/responses`
por meio do transporte `wreq-js`. **Modelos que não sejam codex são rejeitados** (`codex_ws_provider_required`).
Para roteamento com compartilhamento de cota, use `model: "qtSd/<group>/codex/<model>"`. Implementado em
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticação:** chave de API Bearer durante o handshake. O servidor HTTP incluído (`server-ws.mjs`)
deve ser o ponto de entrada ativo (e é, por padrão, quando `app/server-ws.mjs` existe).

#### ID do modelo: use o ID puro do ChatGPT (sem o prefixo `codex/`)

A **CLI Codex** da OpenAI valida o nome do modelo no lado do cliente quando
`supports_websockets = true` e **rejeita IDs prefixados com o provedor**, como
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Envie o ID **puro** (por exemplo, `gpt-5.5`). A ponte do OmniRoute funciona
somente com codex, portanto resolve novamente um ID puro como um modelo codex
(`resolveCodexWsModelInfo`) antes de estabelecer o túnel upstream — embora um
`gpt-5.5` puro fosse, de outra forma, roteado para outro provedor via HTTP.

#### Configuração da CLI Codex da OpenAI

Direcione a CLI Codex para o OmniRoute adicionando um provedor personalizado com suporte a WebSocket
em `~/.codex/config.toml` (use um `CODEX_HOME` separado para evitar alterar
uma configuração existente):

```toml
model = "gpt-5.5"                 # ID puro — NÃO "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # sem barra final; a URL WS é derivada (use https/wss em produção)
wire_api = "responses"                    # único valor compatível desde fevereiro de 2026
supports_websockets = true                # habilita o transporte Responses via WS
env_key = "OMNIROUTE_API_KEY"             # contém a chave de API do OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # uma chave de API do OmniRoute (qualquer chave se REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

A CLI faz o upgrade de `base_url + /responses` para um WebSocket, e o OmniRoute estabelece um túnel
para a conexão OAuth do codex selecionada. Validado de ponta a ponta com o servidor
local: o ChatGPT retorna `codex.rate_limits` + `response.created` e transmite a
conclusão via streaming.

## Uso por autoatendimento (`/api/usage/om-usage`)

Qualquer chave de API pode consultar **seu próprio** uso e suas cotas — sem autenticação de gerenciamento. Esse é o endpoint que um
cliente (CLI, o painel do OmniCopilot) usa para mostrar os gastos ao titular de uma chave.

```bash
# Formato de texto (o contrato histórico — texto simples para um terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato estruturado — o que uma interface de usuário consome
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

A chave deve ter **`allowUsageCommand`** habilitado (desabilitado por padrão — o gerenciador de chaves de API
do painel alterna essa opção por chave). Sem isso, o endpoint responde com `403`.

`?format=json` retorna uma estrutura discriminada para que um chamador nunca tente ler um campo de dados de uma
recusa. Em caso de sucesso:

```jsonc
{
  "allowed": true,
  // presente somente quando a chave optou por limites de uso por chave (USD diário/semanal):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // o snapshot de cota do provedor selecionado ou null quando ainda não há dados em cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // o snapshot de cada conexão, para que uma interface possa renderizar vários provedores lado a lado:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Em caso de recusa (`401` chave inválida / `403` não permitido), a mesma rota retorna
`{ "allowed": false, "error": { "message": "…" } }` — um `personal`/`provider` presente, porém vazio
(chave permitida, mas ainda sem dados obtidos), representa um estado diferente de uma recusa, e somente o formato JSON
faz essa distinção.

**Autenticação:** a própria chave de API Bearer do chamador, validada com `isValidApiKey` — esta _não_ é a
interface de gerenciamento (`/api/keys/…`), que permanece protegida por `requireManagementAuth`.

### Percentuais de Cota Brutos vs. Ajustados pelo Limite de Corte

Ao consumir `/api/usage/om-usage`, os chamadores devem observar a diferença entre os
percentuais apresentados pela **saída em texto simples** e pela **saída JSON** estruturada:

| Aspecto                              | Formato de texto simples (`/api/usage/om-usage` / `@@om-usage`)                                               | Formato JSON (`?format=json`)                                                   |
| :----------------------------------- | :------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------ |
| **Campo de saída**                   | `NN% left` (por exemplo, `20% left`)                                                                          | `provider.quotas` / `providers[].quotas`                                        |
| **Medição**                          | **Disponibilidade utilizável ajustada pelo limite de corte**: capacidade restante acima do limite de corte    | **Cota upstream bruta**: medição não ajustada do provedor                       |
| **Escalonamento do limite de corte** | Escalonado por meio de `effectiveRemainingPercent()` para que a reserva protegida seja exibida como `0% left` | Nenhum (valores brutos do snapshot conforme informados pelo provedor)           |
| **Dados do limite**                  | Incorporados ao percentual exibido                                                                            | Armazenados em `quotaWindowThresholds` por conexão (ou nos padrões do servidor) |
| **Consumidor principal**             | CLIs interativas, prompts de terminal, operadores humanos                                                     | Integrações programáticas, painéis, análises e rastreadores de cobrança         |

#### A Fórmula de Ajuste do Limite de Corte

O OmniRoute oferece suporte a limites de corte proativos de cota para evitar o esgotamento upstream (configurados por meio de
`quotaWindowThresholds` da conexão, padrões do provedor ou configurações globais de resiliência). Quando um limite de corte
(por exemplo, `cutoff = 25%`) está ativo em uma janela de cota, o renderizador de texto calcula a disponibilidade restante da seguinte forma:

- Se `remaining <= cutoff`: retorna `0%`.
- Se `remaining > cutoff`: retorna `((remaining - cutoff) / (100 - cutoff)) * 100`.

A saída de texto formatada arredonda esse valor para o inteiro mais próximo (`Math.round(...)`).

#### Exemplo Ilustrativo

Considere uma janela de provedor com **60% de uso bruto** (portanto, **40% de cota bruta restante**) e um
limite de corte configurado de **25% da cota restante**:

| Representação                     | Cálculo                                            | Restante |              Uso Implícito              |
| :-------------------------------- | :------------------------------------------------- | :------: | :-------------------------------------: |
| **JSON bruto (`?format=json`)**   | Snapshot upstream (`quotas[window]`)               | **40%**  |                 **60%**                 |
| **Formato de texto (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (ao calcular `100 - remaining`) |

- **Por que o texto mostra 20% restantes:** dos 40% de cota física restantes na conta, 25% são reservados pela
  política de limite de corte. O chamador tem apenas 15% dos 75% de margem utilizável restantes antes que o roteador pare de
  rotear para essa conexão. O escalonamento garante que a conexão sinalize esgotamento (`0% left`) exatamente quando
  o roteamento for interrompido.
- **Por que o JSON preserva os valores brutos:** o payload JSON retorna o snapshot exato do provedor (`UsageSnapshot`)
  para que ferramentas externas tenham acesso à utilização upstream real e aos
  `quotaWindowThresholds` no nível da conexão, sem escalonamento com perda realizado pelo servidor.

#### Orientações para Migração de Consumidores

Se uma integração externa (como um plugin de editor ou uma extensão de agente) extraía anteriormente o endpoint
de texto (`NN% left`) e calculava a porcentagem usada como `100 - NN`, migrar para `?format=json` significa:

- A leitura dos valores JSON brutos refletirá o **consumo real upstream** (60% usado no exemplo acima).
- Se a integração quiser preservar a semântica de cota disponível do endpoint de texto, ela poderá avaliar
  no lado do cliente a fórmula de saldo restante efetivo usando `quotaWindowThresholds` para substituições no nível da conexão.

## Cache semântico

```bash
# Obter estatísticas do cache
GET /api/cache/stats

# Limpar todos os caches
DELETE /api/cache/stats
```

Exemplo de resposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impacto na latência

Um HIT no cache semântico fornece a resposta a partir do cache **sem uma chamada
ao upstream**, portanto, o valor informado de `X-OmniRoute-Response-Latency` é próximo de zero
(independentemente da latência upstream original). Clientes sensíveis à latência
(benchmarking, monitoramento de p50/p99) devem verificar o cabeçalho de resposta
`X-OmniRoute-Cache-Latency`:

| Valor       | Significado                                                              |
| ----------- | ------------------------------------------------------------------------ |
| `synthetic` | Resposta fornecida pelo cache; a latência não é o tempo real do upstream |
| _(ausente)_ | Resposta proveniente de uma chamada real ao upstream                     |

### Desvio do cache por chave

As chaves de API podem optar por não realizar leituras do cache semântico por meio de `cacheDefaultMode`:

| Valor    | Comportamento                                                      |
| -------- | ------------------------------------------------------------------ |
| `legacy` | Comportamento normal do cache (padrão)                             |
| `bypass` | Ignora completamente a consulta ao cache; sempre acessa o upstream |

Defina na criação da chave (`POST /api/keys`) ou na atualização (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Desvio por solicitação

Qualquer solicitação pode ignorar o cache, independentemente das configurações da chave:

```
X-OmniRoute-No-Cache: true
```

Para modelos sincronizados/importados, `PUT /api/provider-models` aceita `provider`, `modelId` e
`maxOutputTokenOverride`: um inteiro positivo define o limite manual de tokens de saída, enquanto `null`
o remove para restaurar o padrão. `GET /api/provider-models?provider=<provider>` retorna esses
valores em `modelOutputOverrides`, incluindo modelos sem uma linha de modelo personalizado. A substituição
usa o recurso de tempo de execução `max_output_tokens` e persiste após uma nova sincronização do modelo. A página do
provedor compatível com OpenAI oferece os mesmos controles de edição/remoção e marca modelos com suporte explícito a visão.

Nós personalizados de Chat Completions adaptam desativações explícitas de raciocínio ao backend upstream. Um
teste de conexão bem-sucedido seleciona automaticamente os controles de modelo de chat para cada ID exato de modelo
cuja entrada em `/models` comprove um valor reconhecido de `owned_by`: `vllm`, `sglang` ou `llamacpp`.
Wrappers transparentes compatíveis com OpenAI podem preservar a entrada original do modelo dentro de um objeto
`openai` aninhado; a detecção percorre até três desses envelopes. Modelos com propriedade ausente, desconhecida ou
conflitante mantêm o comportamento comum do OpenAI. A detecção reutiliza a solicitação de catálogo existente,
não gera tokens de conclusão e é invalidada quando o endpoint de conexão é alterado.

Para fixar o comportamento de um backend que não expõe esses metadados, use a API existente de atualização
parcial do provedor:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envie esse corpo com `PUT /api/providers/<connection-id>`. Nessa conexão, um esforço explícito
de raciocínio definido como `none` é enviado como `chat_template_kwargs.thinking=false` e
`chat_template_kwargs.enable_thinking=false`. Valores nativos explícitos do modelo permanecem autoritativos,
a menos que uma regra de raciocínio no lado do servidor force um esforço. A configuração se aplica somente quando uma conexão
personalizada compatível com OpenAI envia um corpo de Chat Completions; solicitações de Responses e provedores
comuns mantêm o formato nativo de suas solicitações. Defina `reasoningControl` como `openai` para forçar o repasse comum
de `reasoning_effort` do OpenAI, ou omita-o/defina-o como `null` para usar a detecção automática.

As solicitações do classificador do modo automático do Claude Code desabilitam por padrão o pensamento nativo quando
não contêm controles explícitos de raciocínio. A detecção usa o marcador de sistema do classificador em solicitações no
formato Claude, não nomes de modelos nem limites de conclusão. Controles explícitos no corpo, cabeçalhos compatíveis de
esforço/pensamento, regras de roteamento e o esforço resolvido do modelo mantêm suas prioridades existentes. Ambos os
estágios do classificador preservam seus prompts, limites de conclusão, sequências de parada e veredictos reais de
permissão do upstream; o segundo estágio ainda pode produzir o raciocínio visível solicitado como texto comum.

### Versão e canal de lançamento

```bash
GET /api/system/version
```

Rota de gerenciamento restrita ao loopback (autenticação de administrador). Retorna a versão em execução, a versão publicada mais recente e o status da atualização automática. `releaseChannel` e `channels` são campos adicionais (linha 3.8.54); `channel` mantém seu significado — o modo de implantação usado pelo atualizador do painel (`npm`, `source` ou `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal npm da compilação em execução: `nightly` para versões `-nightly.*`,
  `next` para outras versões de pré-lançamento (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para uma versão estável de uma
  versão principal anterior à de `channels.latest`; caso contrário, `latest`. Segue as mesmas regras de
  `scripts/release/dist-tag.mjs`, que seleciona a dist-tag do npm no momento da publicação.
- `channels` — versão mais recente publicada de cada dist-tag, obtida de `npm view omniroute dist-tags` (com fallback
  para HTTP do registro), armazenada em cache com o mesmo TTL de 10 minutos de `latest`. `latest` está sempre presente
  (usa como fallback o campo `latest` e, depois, `"unavailable"`); `next`, `nightly` e `lts` aparecem
  somente quando a dist-tag correspondente existe. Uma solicitação com `Cache-Control: no-cache` atualiza ambas as consultas.

O modelo de canais (`latest` = v3 até a disponibilidade geral da 4.0, `next` = rc, `nightly` = compilações de `develop`,
`lts` = correções da v3 após a disponibilidade geral da 4.0) está descrito em `docs/ops/RELEASE_STRATEGY.md`.

## Limites de tokens

Orçamentos de **tokens** por chave de API (distintos do Orçamento baseado em USD acima). Aplicados diretamente no fluxo da solicitação: quando o uso da janela atual de uma chave atinge seu limite, as solicitações são rejeitadas com `429 Too Many Requests`. Os limites podem ter como escopo um `model` específico, um `provider` ou ser aplicados de forma `global` em toda a chave; quando vários limites correspondem a uma solicitação, o mais restritivo prevalece.

```bash
# Lista os limites de tokens de uma chave (inclui o uso atual da janela)
GET /api/usage/token-limits?apiKeyId=key-123

# Cria ou atualiza um limite de tokens
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Exclui um limite de tokens por ID
DELETE /api/usage/token-limits?id=tl-abc
```

> **Observações sobre o esquema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) são obrigatórios. `scopeValue` é obrigatório, a menos que `scopeType` seja `global` (por exemplo, um ID de modelo para o escopo `model` ou um ID de provedor para o escopo `provider`). `tokenLimit` deve ser um número inteiro positivo (convertido a partir de uma string). Opcionais: `id` (omita para criar, forneça para atualizar), `resetInterval` (`daily` | `weekly` | `monthly`, padrão `monthly`), `resetTime` (`HH:MM`), `enabled` (padrão `true`). As respostas de `GET` enriquecem cada limite com `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Este é um endpoint da classe de gerenciamento (a autenticação é aplicada centralmente pelo pipeline de autorização).

## Processamento de solicitações

1. O cliente envia uma solicitação para `/v1/*`
2. O manipulador da rota chama `handleChat`, `handleEmbedding`, `handleAudioTranscription` ou `handleImageGeneration`
3. O modelo é resolvido (provedor/modelo direto ou alias/combo)
4. As credenciais são selecionadas no banco de dados local com filtragem pela disponibilidade da conta
5. Para chat: `handleChatCore` verifica o cache semântico/de assinatura e resolve as configurações de compressão do combo
6. A compressão proativa é executada antes da tradução do provedor quando habilitada (`lite`, Caveman, RTK ou empilhada)
7. O executor do provedor envia a solicitação ao serviço upstream
8. A resposta é convertida novamente para o formato do cliente (chat) ou retornada como está (embeddings/imagens/áudio)
9. O uso, as análises de compressão e os logs de solicitações são registrados
10. O fallback é aplicado em caso de erros, de acordo com as regras do combo

Referência completa da arquitetura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resiliência (estendida)

O OmniRoute disponibiliza três mecanismos independentes para falhas temporárias; os endpoints de gerenciamento abaixo permitem que os operadores consultem e substituam suas configurações:

| Escopo                | Armazenamento de estado                           | Consulta                                  | Redefinição / limpeza                                    |
| --------------------- | ------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------- |
| Disjuntor do provedor | `domain_circuit_breakers` + memória               | `/api/monitoring/health`                  | `POST /api/resilience/reset`                             |
| Espera de conexão     | `rateLimitedUntil` nas conexões do provedor       | `/api/rate-limits`, `/api/providers/[id]` | (reativa de forma preguiçosa; limpe via PUT do provedor) |
| Bloqueio de modelo    | Registro de disponibilidade de modelos em memória | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                 |

`PATCH /api/resilience` aceita substituições do disjuntor do provedor em `providerBreaker.oauth` e `providerBreaker.apikey`. Cada perfil oferece suporte a `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; os mesmos campos estão disponíveis em Painel → Configurações → Resiliência.

```bash
# Limpar o bloqueio de um único modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Limpar todos os bloqueios
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Para obter a referência conceitual completa e os valores padrão dos disjuntores, consulte [`CLAUDE.md`](../../CLAUDE.md) → "Estado de resiliência em tempo de execução" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Fila de limite de taxa e mecanismo de segurança de ativação automática

- **Caminho de gravação compatível**: `POST /api/rate-limits` com o corpo `{"connectionId": "<id>", "enabled": true|false}` é o endpoint de gerenciamento compatível para ativar ou desativar a proteção contra limite de taxa de uma conexão. `PUT /api/providers/[id]` deliberadamente não modifica nem alterna `rateLimitProtection` (#11278).
- **Semântica de `enabled: false`**: Definir `enabled: false` remove a proteção explícita da conexão, mas **não** exclui uma conexão de chave de API ativa do mecanismo global de segurança de ativação automática (`autoEnableApiKeyProviders = true`). Em `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` são equivalentes; conexões de chave de API ativas sem proteção explícita permanecem protegidas pelo mecanismo de segurança de ativação automática.
- **Desativação global**: Para executar conexões de chave de API sem filas de limite de taxa, desative globalmente o mecanismo de segurança usando `RATE_LIMIT_AUTO_ENABLE=false` (variável de ambiente) ou `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Configurações → Resiliência / `PATCH /api/resilience`).

## Servidor MCP

O OmniRoute inclui um servidor Model Context Protocol integrado com 3 transportes (stdio, SSE, streamable-http) e ferramentas com escopo definido. Os endpoints do painel abaixo leem dados de status/auditoria e fazem proxy dos transportes HTTP.

| Método | Caminho | Descrição |

| POST | `/api/mcp/sse` | Envia um quadro JSON-RPC pelo transporte SSE |
| GET | `/api/mcp/stream` | Abre o lado SSE do transporte Streamable HTTP (mensagens iniciadas pelo servidor) |
| POST | `/api/mcp/stream` | Envia um quadro JSON-RPC pelo transporte Streamable HTTP |
| DELETE | `/api/mcp/stream` | Encerra uma sessão Streamable HTTP |

## Servidor A2A

O OmniRoute expõe um endpoint A2A (Agente para Agente) JSON-RPC 2.0, além de um wrapper REST para uso em inspeção/painéis.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opcional, a menos que OMNIROUTE_API_KEY esteja definida
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Métodos compatíveis (todos condicionados a `settings.a2aEnabled`):

| Método           | Descrição                                                              |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Execução síncrona da habilidade; retorna `{task, artifacts, metadata}` |
| `message/stream` | Execução por streaming via SSE do mesmo conjunto de habilidades        |
| `tasks/get`      | Busca uma tarefa por `taskId`                                          |
| `tasks/cancel`   | Cancela uma tarefa por `taskId`                                        |

Habilidades integradas: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Cartão do agente

```bash
GET /.well-known/agent.json
```

Retorna o cartão público do agente A2A (nome, descrição, recursos, catálogo de habilidades, esquema de autenticação) — armazenado em cache público por 1h. Nenhuma autenticação é necessária.

### Auxiliares REST

| Método | Caminho                      | Descrição                                                                                                          |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/a2a/status`            | A2A habilitado + estatísticas de tarefas + resumo do cartão do agente em cache                                     |
| GET    | `/api/a2a/tasks`             | Lista tarefas — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Não implementado como auxiliar REST — crie via JSON-RPC `message/send`)                                           |
| GET    | `/api/a2a/tasks/[id]`        | Recupera uma tarefa                                                                                                |
| POST   | `/api/a2a/tasks/[id]/cancel` | Cancela uma tarefa                                                                                                 |

**Autenticação:** os auxiliares REST são executados sem autenticação de gerenciamento (podem ser lidos pelo painel); a rota JSON-RPC `/a2a` usa o Bearer `OMNIROUTE_API_KEY`, se configurado.

## Autenticação

Consulte [Autenticação de gerenciamento](../guides/MANAGEMENT-AUTH.md) para conhecer as quatro famílias de credenciais (sessão do dashboard, token da CLI local, token de acesso `oma_live_…`, chave de API com escopo de gerenciamento) e entender como elas diferem das chaves de inferência.

- As rotas do dashboard (`/dashboard/*`) usam o cookie `auth_token`
- O login usa o hash de senha salvo, com fallback para `INITIAL_PASSWORD`
- `requireLogin` pode ser alternado por meio de `/api/settings/require-login`
- As rotas `/v1/*` podem exigir opcionalmente uma chave de API Bearer quando `REQUIRE_API_KEY=true`
- Nesta referência, "token de gerenciamento" / "chave de API com escopo de gerenciamento" refere-se a uma das famílias descritas nesse guia — não a um tipo de segredo adicional não definido

> **Alteração incompatível (v3.8.0)** — `/api/v1/agents/tasks/*` e os endpoints de gerenciamento de cooldown agora exigem **autenticação de gerenciamento** (cookie `auth_token` do dashboard ou uma chave de API com escopo de gerenciamento). Os clientes que anteriormente chamavam essas rotas sem autenticação receberão `401 Unauthorized`. Consulte o commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
