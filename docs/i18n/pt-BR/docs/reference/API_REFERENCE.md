## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

| `x-omniroute-no-memory`  | Requisição | Defina como `true` para ignorar a injeção de memória + habilidades nesta requisição (espelha o comportamento de no-cache; evita a sobrecarga de tokens/custo por chamada)                                                          |

| `X-Session-Id`           | Requisição | Chave de sessão persistente para afinidade de sessão externa                                                                                                                                                                       |
| `x_session_id`           | Requisição | A variante com sublinhado também é aceita (HTTP direto)                                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | Requisição | Tag de sessão/conversa fornecida pelo chamador (também alimenta a memória). Quando presente, é persistida literalmente em `call_logs.session_tag` para atribuição de custo por sessão (#8249) — nunca é sintetizada quando ausente |

#### Fixação de conta por requisição

Quando um provedor tem várias conexões (contas ou chaves), o OmniRoute normalmente escolhe uma
por meio de sua estratégia de seleção de conta. Em vez disso, uma requisição pode fixar uma conexão
específica com o cabeçalho `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Onde encontrar o ID.** Abra a página do provedor no painel
  (**Painel → Provedores → <provider>**) e clique no chip de ID `xxxxxxxx…` em uma linha de
  conexão — isso copia o ID completo da conexão.
- **Quais solicitações o respeitam.** Solicitações de modelo único (`provider/model`) em
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. Combos ignoram o cabeçalho: fixe
  uma conta por etapa do combo por meio da própria conexão da etapa.
- **A fixação é estrita, não uma preferência.** A conexão fixada é usada exclusivamente. Uma
  falha durante a solicitação registra o cooldown da conta, mas **não** alterna para outra
  conta do mesmo provedor.
- **Cooldown e cota liberam a fixação.** Enquanto a conexão fixada estiver em cooldown,
  com a cota esgotada ou bloqueada por uma política de cota, as solicitações posteriores
  recorrem às outras conexões do provedor, exatamente como o tráfego não fixado.
- **IDs desconhecidos ou desabilitados falham.** Um ID que não esteja no pool ativo do provedor
  (excluído, desativado ou pertencente a outro provedor) não deixa nenhuma conta elegível,
  portanto a solicitação falha em vez de ser silenciosamente roteada para outro destino.

O Claude Code envia cabeçalhos personalizados por meio de `ANTHROPIC_CUSTOM_HEADERS`. Coloque-o no bloco `env`
de `~/.claude/settings.json` ou em um `.claude/settings.json` no nível do projeto para fixar uma conta
diferente por projeto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fonte: `src/sse/handlers/chat.ts` (leitura do cabeçalho), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (liberação da fixação e verificação de ausência no pool).

> **Cabeçalhos de telemetria de custos:** respostas bem-sucedidas sem streaming também incluem o conjunto de telemetria de custos `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 casas decimais fixas; `0.0000000000` para serviços gratuitos/sem preço), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (somente quando > 0), além de `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Eles são emitidos por conclusões de chat, `/v1/responses`, `/v1/messages` **e pelos endpoints de mídia** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (sempre com custo `0`). O custo de mídia é calculado por modalidade (por imagem, por segundo, por caractere, por unidade de pesquisa) quando os preços estão disponíveis; caso contrário, é `0` (fail-open).

> **Semântica de custo para acertos de cache:** em um ACERTO do cache semântico (`X-OmniRoute-Cache-Hit: true`), nenhuma chamada upstream é feita, portanto `X-OmniRoute-Response-Cost` é `0.0000000000` (o custo **incremental** de servir o acerto). O custo original/que teria sido cobrado é informado separadamente em `X-OmniRoute-Cost-Saved`. Consumidores de faturamento devem somar `X-OmniRoute-Response-Cost` (acertos não custam nada); análises de cache podem agregar `X-OmniRoute-Cost-Saved`.

## Concessões de Sessão Gerenciadas Exclusivas

O aluguel de sessão gerenciada exclusiva é um contrato de roteamento opcional e neutro para o cliente: um proprietário ativo detém uma conexão OmniRoute elegível. Ele não aluga um modelo, não exige OAuth, não identifica um cliente específico e não exige um provedor específico.

A chave de API de autenticação deve ter o escopo `lease:exclusive` e uma lista `allowedConnections` explícita e não vazia. O limite de mutação do banco de dados impõe ambos os campos juntos na criação da chave e em atualizações parciais.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Respostas bem-sucedidas de aquisição, renovação e liberação expõem carimbos de data/hora, `state` e a `generation` positiva exata, mas nunca a conexão ou credenciais selecionadas. A renovação e a liberação fornecem a geração no corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Um proprietário de concessão ativo pode solicitar explicitamente metadados de exibição seguros para a privacidade de sua vinculação atual:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Esta ação de status opcional é protegida pelo proprietário opaco, pela chave de API gerenciada autenticada e pela geração ativa exata em uma única transação de banco de dados. `displayName` é apenas o nome da conexão configurada e truncado; é `null` quando não existe um nome configurado seguro. O OmniRoute nunca substitui um e-mail ou uma identidade de conta gerada. O valor do provedor é um rótulo de exibição não sensível e nunca um identificador de provedor compatível gerado. Credenciais, tokens, cookies, IDs de conexão bruta ou de chave de API, hashes de proprietário, segredos de proteção e dados de roteamento internos são excluídos.

Consultas com chave errada, proprietário errado, geração obsoleta, ausentes, expiradas, liberadas e invalidadas retornam o mesmo erro `409 LEASE_FENCE_STALE` sem metadados de conexão. Um cliente que recebeu a resposta de espera de capacidade não tem nenhuma vinculação ativa para inspecionar. Quando o roteamento transiciona uma concessão ativa, a mesma geração permanece válida e o status retorna atomicamente a nova vinculação, nunca a antiga. Os clientes existentes permanecem inalterados porque as respostas de aquisição, renovação, liberação e espera mantêm suas formas anteriores.

Este contrato de servidor não altera o `/status` padrão do OpenAI Codex. O Codex padrão atualmente relata seu provedor de modelo e o estado de autenticação/conta integrado, mas não renderiza metadados arbitrários de conta de provedor personalizado; uma integração de cliente posterior deve chamar esta ação e decidir como exibir `connection.displayName`.

Cada solicitação de inferência gerenciada fornece então ambos os cabeçalhos de controle:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

O proprietário exato, a geração, a conexão ativa e a chave de API autenticada são protegidos imediatamente antes de cada tentativa upstream suportada. Repetir proprietário e geração com outra chave falha mesmo quando essa chave permite a mesma conexão. Proprietários brutos não são persistidos, registrados, retidos no snapshot da solicitação ou encaminhados upstream.

A contenção temporária retorna HTTP `429` com `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Esta resposta significa apenas que o conjunto elegível comum não estava vazio e que cada candidato livre estava sendo mantido por uma concessão ativa estrangeira. Modelos/provedores não suportados, incompatibilidade de política, tempo de espera (cooldown), cota, saúde e outras falhas comuns de elegibilidade mantêm suas respostas OmniRoute existentes.

### `x-omniroute-compression`

Sobrescrita por solicitação do plano de compressão. Precedência mais alta — supera a sobrescrita do combo de roteamento, o perfil ativo, o gatilho automático e o Padrão do painel. Valores:

| Valor         | Efeito                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | Nenhuma compressão para esta solicitação.                                                                         |
| `default`     | O perfil Padrão derivado do painel (ignora o perfil ativo). Motores com perda são desativados.                    |
| `safe`        | Apenas deduplicação e dobramento de espaços em branco.                                                            |
| `allow-lossy` | Mantém o plano do operador para esta solicitação, incluindo resumos e reescritas de estilo.                       |
| `engine:<id>` | Um único motor quando ativado, por exemplo, `engine:rtk`. Ativação opcional por solicitação para esse motor.      |
| `<combo>`     | Um combo nomeado, correspondido primeiro pelo nome (sem distinção entre maiúsculas e minúsculas), depois pelo ID. |

Observações:

- Valores desconhecidos são ignorados (a solicitação nunca é rejeitada); a resolução segue a precedência normal do operador.
- Se vários combos compartilharem um nome, passe o **ID** do combo para uma correspondência determinística.
- Um combo cujo nome é `off` ou `default` não pode ser selecionado pelo nome (essas palavras-chave são interpretadas primeiro); referencie tal combo pelo seu ID.
- O interruptor mestre de compressão é um portão rígido: quando a compressão é desativada globalmente, este cabeçalho não pode ativá-la.

O plano aplicado é retornado no cabeçalho da resposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

onde `<source>` é um de `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, ou `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer sua-chave-de-api
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "A comida estava deliciosa"
}
```

Provedores disponíveis: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Os IDs do catálogo seguem o formato `provider/model` (exemplo: `jina-ai/jina-embeddings-v5-omni-small`). IDs de modelos Jina sem o provedor que aparecem no registro (por exemplo, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) também são resolvidos. As operações embed/rerank/classify/segment da Jina usam primeiro as credenciais `jina-ai` do painel; `JINA_AI_API_KEY` é usada como alternativa somente quando não existe uma chave no painel. O cartão `jina-reader` destina-se apenas ao Reader / `r.jina.ai` (`POST /v1/web/fetch`) e nunca fornece embeddings ou rerank.

Os modelos do registro que anunciam suporte multimodal também aceitam até 32 itens estruturados
independentes de provedor. Os tipos de item de mídia são `text`, `image`, `audio`, `video` e `document`. O `source`
da mídia é `{"type":"url","url":"https://..."}` ou
`{"type":"base64","data":"...","media_type":"..."}`.

O Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
e o alias de família `jina-ai/jina-embeddings-v5-omni` → omni-small) também aceita documentos
EmbeddingsV5Request nativos da Jina e **os encaminha intactos** para `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "uma bicicleta vermelha" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "legenda" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

Os valores nativos `{ image | audio | video | pdf }` podem ser uma URL HTTPS pública, um URI `data:` ou base64
bruto. O OmniRoute não converte esses objetos em strings nem busca URLs de imagens nativas — a própria Jina recupera
as mídias públicas. Campos adicionais da Jina (`task`, `normalized`, `truncate`, `embedding_type`) são
encaminhados. SKUs da Jina exclusivos para texto ainda rejeitam documentos que não sejam de texto.

Limites de segurança e transporte:

- URLs de mídia remota devem usar HTTPS público. Itens canônicos `{type,source:url}` são buscados
  no servidor (revalidação de redirecionamentos, tempo limite, limites de tamanho, DNS público, fixação de conexão) e
  incorporados antes da chamada ao provedor. Itens nativos da Jina `{image:"https://..."}` são encaminhados como estão
  após a mesma verificação de HTTPS público; a Jina busca a URL.
- A mídia base64 inline é limitada a 8 MiB decodificados por item e 16 MiB decodificados em toda a solicitação.

Tradução para o provedor (itens canônicos nunca são encaminhados sem alterações):

- Modelos multimodais da Jina: cada item de nível superior torna-se um objeto com uma chave de modalidade
  (`text` / `image` / `audio` / `video` / `pdf`), usando URIs de dados para mídia inline; um vetor por
  item de nível superior.
- Família Gemini Embedding 2: um array de nível superior torna-se uma única solicitação nativa
  `models/{model}:embedContent` com `content.parts` (`text` ou `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualquer modelo carregado pelo servidor local): itens canônicos `text`
  tornam-se strings simples, e `image` / `audio` / `video` tornam-se, cada um, um objeto
  `{"content": [part]}`, usando as partes de conteúdo de chat do llama-server (`image_url`,
  `input_audio` com o formato `wav` / `mp3` / `flac`, `input_video`) com dados inline; um vetor
  por item de nível superior. O servidor deve ser executado com `--embedding --mmproj …`; sem um projetor, ele
  próprio rejeita mídias. `document` não é compatível.
- Modelos desconhecidos/dinâmicos sem metadados explícitos de modalidade rejeitam entradas estruturadas com HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "Uma bicicleta vermelha" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Combinações incompatíveis de modelo/modalidade retornam HTTP 400 em vez de converter o item. Campos de extensão
que não são de entrada em solicitações legadas de strings/tokens continuam sendo repassados sem alterações.

```bash
# Listar todos os modelos de embedding
GET /v1/embeddings
```

## Geração de imagens

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Os provedores disponíveis incluem OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local), ComfyUI (local).

`n` retorna `n` imagens em `data[]`. Para provedores cuja API upstream retorna uma imagem por chamada
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), são feitas `n` chamadas upstream separadas, com no máximo 4 em execução simultânea. Um
`seed` fixo é incrementado de acordo com o índice da chamada (`seed`, `seed + 1`, …), para que as imagens sejam diferentes, mas permaneçam
reproduzíveis. `n` é limitado a 10. A solicitação inteira falha se qualquer chamada falhar. A lista
de formatos com fan-out é `SINGLE_IMAGE_FANOUT_FORMATS` em
`open-sse/handlers/imageGeneration/fanOut.ts`.

O ZenMux reutiliza a conexão existente por chave de API e aceita os prefixos `zenmux/` ou `zm/`:

- `zenmux/openai/gpt-image-2` usa a API de imagens da OpenAI do ZenMux. As opções incluem `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Outros publicadores, como `zm/meta/muse-image-1.0`, usam o endpoint `:predict`
  do Vertex AI do ZenMux. `n` é mapeado para `sampleCount`, `aspect_ratio` para `aspectRatio` e `image_size`
  (`1K`, `2K`, `4K`) para `sampleImageSize`. Um `size` em pixels fornece apenas uma proporção,
  não dimensões garantidas em pixels. As proporções, resoluções e quantidades compatíveis variam de acordo com o modelo.
- `zm/inclusionai/ming-image-0.1-design` escolhe suas próprias dimensões. Omita `size`,
  `aspect_ratio` e `image_size`; valores explícitos retornam HTTP 400. PNG, JPEG e WebP
  podem ser solicitados com `output_format`.

Esta integração oferece suporte à geração de texto para imagem, mas não à edição com imagem de referência. A saída do Vertex
é normalizada para `data[].b64_json`; `response_format: "url"` retorna uma URL HTTPS upstream
ou uma URL de dados em base64 quando apenas os bytes da imagem estão disponíveis. Saídas vazias/filtradas
retornam um erro em vez de uma resposta de sucesso vazia. O acesso aos modelos depende da conta do ZenMux.
Consulte a [API Vertex do ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) e a
[API de imagens da OpenAI](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Listar todos os modelos de imagem
GET /v1/images/generations
```

## OCR de documentos

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleciona o provedor de OCR por meio de um prefixo `provider/model`; um ID de modelo sem prefixo (por exemplo,
`mistral-ocr-latest`) é resolvido para seu provedor registrado, e, quando `model` é omitido, o padrão é
Mistral (`mistral-ocr-latest`). Provedores registrados (`open-sse/config/ocrRegistry.ts`):

| ID do provedor                | ID do modelo         | Valor de `model`                                              | Observações                                                                                                              |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (ou apenas `mistral-ocr-latest`) | Síncrono — a resposta é retornada diretamente da única chamada ao serviço upstream.                                      |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | Upstream assíncrono (`analyze` + sondagem) — veja abaixo.                                                                |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | Síncrono, por meio do endpoint de parceiro `openapi/chat/completions` do Vertex AI — veja abaixo sobre autenticação/URL. |

Todos os três provedores respondem com o mesmo corpo no formato do Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxo de sondagem do Azure Document Intelligence

A API `analyze` do Azure Document Intelligence é assíncrona: a solicitação inicial retorna um
cabeçalho `Operation-Location` em vez de um corpo, e o resultado deve ser consultado periodicamente. O manipulador
(`open-sse/handlers/ocr.ts`) consulta essa URL a cada segundo por até 30 tentativas, falha imediatamente (sem
continuar a sondagem) em caso de uma resposta de sondagem que não seja `ok` ou de um status `"failed"`, e retorna `504` se a
operação ainda estiver em execução após o esgotamento do limite de tentativas. A resposta final do Azure é
normalizada para o mesmo formato `pages`/`markdown` usado pelo Mistral antes de ser retornada ao
chamador, portanto o código do cliente não precisa tratar o provedor como um caso especial.

### Autenticação e resolução de endpoint do Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` reutiliza a mesma autenticação do Vertex AI que o OmniRoute já oferece para
tráfego de chat/imagens (`open-sse/executors/vertex.ts`): a chave de API da conexão é uma
credencial JSON de Service Account (trocada por um token de acesso OAuth de curta duração por meio do fluxo JWT bearer)
ou um token de acesso OAuth já emitido, usado sem alterações. A URL do endpoint upstream é o
endpoint genérico de parceiro `openapi/chat/completions` do Vertex, construído com base no projeto e na
região da conexão — valores explícitos de `providerSpecificData.project`/`providerSpecificData.region` sempre têm prioridade;
caso contrário, o projeto é derivado do `project_id` no JSON da Service Account, e o padrão da região
é `us-central1`. Ambas as resoluções ocorrem em `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e são utilizadas por
`src/app/api/v1/ocr/route.ts` antes do encaminhamento para `handleOcr`.

## Listar modelos

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Retorna todos os modelos de chat, embeddings e imagens + combos no formato da OpenAI
```

### Prefixos de ID de modelo (`?prefix=`)

A maioria dos modelos é anunciada sob um **prefixo de provedor**. O prefixo recebido é controlado pela
feature flag `MODELS_CATALOG_PREFIX_MODE` e pode ser substituído **por requisição** com um
parâmetro de consulta — útil para um cliente que deseja uma lista limpa sem alterar a configuração
do servidor para todos os demais:

```bash
GET /v1/models?prefix=alias        # um ID por modelo — o prefixo de alias curto
GET /v1/models?prefix=dual         # ambas as formas (padrão do servidor)
GET /v1/models?prefix=canonical    # somente o prefixo completo do ID do provedor
```

| Modo        | Emite                                                   | Observações                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **e** `claude/claude-sonnet-4-6` | **Padrão.** Ambos os IDs direcionam para o mesmo modelo; mantidos para que configurações de clientes que codificaram qualquer uma das formas continuem funcionando. Aproximadamente duplica o catálogo. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Uma entrada por modelo. Provedores sem um alias distinto ainda emitem sua entrada, portanto nada é perdido.                                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                              | Uma entrada por modelo sob o prefixo completo do ID do provedor. Provedores sem um alias distinto (por exemplo, `antigravity/…`, `agy/…`) também emitem seu único ID aqui, portanto nada é perdido.     |

Um espelho no modo `dual` também pode ser reconhecido sem o parâmetro de consulta: ele contém um campo `parent`
que aponta para o ID principal.

Clientes que renderizam um seletor de modelos devem solicitar `?prefix=alias` — é isso que a
[extensão OmniCopilot para VS Code](../guides/VSCODE-COPILOT.md) faz.

### Filtros de descoberta (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` aceita filtros de descoberta opcionais. Sem qualquer um deles, a resposta permanece
inalterada. Eles restringem o catálogo que o chamador já pode ver (as permissões da chave de API são aplicadas primeiro)
e são executados antes da paginação `limit` / `after` no estilo da OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # todas as capacidades listadas devem ser verdadeiras
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` do catálogo; linhas sem um valor são `chat`
GET /v1/models?q=sonnet&limit=10                           # correspondência sem diferenciar maiúsculas e minúsculas no ID ou nome
```

| Parâmetro     | Valores                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | inteiro não negativo, comparado com `context_length`                                                |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | de 1 a 200 caracteres                                                                               |

Um valor desconhecido ou um `min_context` que não seja um inteiro não negativo (por exemplo, `1.5`)
retorna HTTP `400`, e a mensagem lista os valores válidos. Implementação:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista reduzida de modelos (`POST /v1/models/query`)

`POST /v1/models/query` retorna uma lista curta e determinística do mesmo catálogo, com a mesma
autenticação e visibilidade por chave que `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Todos os campos são opcionais. `capabilities` e `exclude` aceitam um array ou uma string separada por vírgulas;
`max_output` é comparado com `max_output_tokens`. Os resultados são ordenados por `owned_by` e depois por `id`.
O valor padrão de `limit` é `20`, e valores acima de `100` são limitados a `100`. JSON inválido, um campo
desconhecido ou um valor inválido retorna HTTP `400`.

### Modelos de chat ocultos individualmente

Um modelo marcado como **Oculto** na página do provedor é excluído do catálogo e rejeitado
com HTTP `404` / `model_not_found` quando solicitado explicitamente. A verificação usa o provedor
e o modelo resolvidos, incluindo aliases de provedor, prefixos de nó de provedor compatível e
padrões de conexão. Um combo ignora destinos ocultos e pode usar um semelhante visível; quando
nenhum destino executável permanece, ele retorna o mesmo código de erro. Tornar o modelo visível
entra em vigor na próxima requisição. Substituições de visibilidade exclusivas para imagens não ocultam
o modelo de chat com o mesmo ID.

Essa configuração individual de modelo é separada das
[listas de permissão/bloqueio de exposição de modelos](../routing/MODEL_EXPOSURE_LIST.md), que filtram o
anúncio no catálogo e os candidatos ao roteamento automático, enquanto mantêm o despacho explícito. As permissões
de modelo da chave de API continuam sendo aplicadas de forma independente. O modo padrão de prefixo do catálogo continua sendo `dual`.

### Variantes de modelo sem raciocínio

Para modelos Claude compatíveis com raciocínio, `/v1/models` também anuncia uma variante **sem raciocínio**, cujo ID possui o prefixo `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Selecionar esse id (por exemplo, em uma configuração do Claude Code que sempre anexa um bloco `thinking`) faz com que ele seja resolvido novamente para o `<provider>/<model>` real com o raciocínio suprimido — `thinking:{type:"disabled"}` no caminho `/v1/messages`, ou com os campos `reasoning`/`reasoning_effort` removidos no caminho `/v1/chat/completions`. A variante é listada apenas para modelos da família Claude que oferecem suporte a raciocínio **e** respeitam `disabled` (portanto, por exemplo, modelos exclusivamente adaptativos que rejeitam `disabled` são excluídos). Os operadores podem ativar ou desativar a variante por modelo por meio de `ModelSpec.noThinkingAlias`.

> **Nós de provedores de rerank:** `POST /v1/rerank` também é roteado para nós de provedores compatíveis com a OpenAI
> (oMLX, vLLM, Infinity, TEI atrás de um gateway, …) endereçados como `<node-prefix>/<model>`. Nós de
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) são sempre elegíveis, assim como os nomes de host que o
> operador lista em `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (por exemplo, um nome de serviço do Docker/Compose,
> como `http://reranker:8080/v1`; eles são chamados diretamente, nunca por meio de `HTTP(S)_PROXY` ou do
> proxy fixado de uma conexão). Nós em qualquer outro
> host — uma máquina na LAN ou um par do Tailscale — são elegíveis somente quando o operador habilita a
> flag de recurso `RERANK_REMOTE_PROVIDER_NODES` **e** a URL base do nó é aprovada pela política de URLs
> de saída do provedor (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> A etapa de rerank do mecanismo de memória chama essa rota por
> loopback, portanto a mesma regra controla `rerankProviderModel` nas configurações de Memória.
>
> **Formatos de servidores locais:** o nó é chamado em `<base>/v1/rerank` e, em caso de 404, em `<base>/rerank`
> (Infinity, TEI). O corpo enviado ao upstream contém tanto a nomenclatura do Cohere/OpenAI (`documents`,
> `return_documents`) quanto a nomenclatura do TEI (`texts`, `return_text`), e a resposta do upstream é
> normalizada para o envelope do Cohere: a resposta simples do TEI `[{index, score, text}]`, a resposta
> `{results: [{index, score}]}` de gateways leves e a resposta no estilo do Voyage `{data: [...]}` são todas
> retornadas ao cliente como `{results: [{index, relevance_score, document?}]}`, ordenadas por pontuação e limitadas a `top_n`.

> **Descoberta de nós de provedores:** os modelos em um nó de provedor compatível com a OpenAI aparecem em `GET /v1/models`
> sob o prefixo do nó. As linhas que não contêm metadados de endpoint (típico de listagens locais de `/v1/models`)
> herdam o `apiType` do nó, de modo que os modelos de um nó de `embeddings` tenham `type: "embedding"` e os
> modelos de um nó de `rerank` tenham `type: "rerank"`, em vez de usarem chat como padrão; um
> `supportedEndpoints` explícito em uma linha sincronizada ou adicionada manualmente ainda tem precedência.

### `provider_options` da Exa e da Tavily

A Exa e a Tavily leem campos específicos do provedor em um objeto com namespace:
`provider_options.exa` (ou `provider_options["exa-search"]`) e `provider_options.tavily`
(ou `provider_options["tavily-search"]`). Somente as chaves abaixo são encaminhadas. Cada uma é
verificada em relação ao seu próprio esquema Zod em `open-sse/handlers/search/providerOptionsPassthrough.ts`,
e uma chave com o tipo incorreto é descartada. Qualquer outra chave é ignorada, incluindo autenticação, URL base,
`stream` e `outputSchema`. As chaves de nível superior usadas por outros provedores (`cx`, `depth`, ...) continuam funcionando
como antes.

| Provedor | Campos de nível superior                                                                                                                                                                                                                                                                                                                                                  | Aninhados                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitivos de nível superior), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                 | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` mesclado sobre o padrão `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                 |

Os campos genéricos sempre prevalecem: `query`, `max_results`, `filters` (domínios), `country` e o
tópico derivado de `search_type`. Na Exa, `search_type: "news"` mantém `category: "news"`.
A Tavily também aceita `search_type: "finance"` (`topic: "finance"`).

O campo genérico `time_range` agora chega a ambos os provedores: a Exa recebe `startPublishedDate` (carimbo de data e hora
ISO) e a Tavily recebe `start_date` (`YYYY-MM-DD`). Uma data explícita em `provider_options`
sobrescreve a data mapeada.

Os resultados da Exa mantêm `id`, `highlight_scores`, `summary`, `subpages`, `entities` e `extras` em
`provider_raw`. Os resultados da Tavily mantêm `images` e `favicon`.

A contabilização de custos continua sendo o registro de nível superior `costPerQuery`. A Tavily cobra
mais créditos por chamada para `search_depth: "advanced"`, e essa diferença não é refletida em
`usage.search_cost_usd`.

## API Web Fetch

Extraia conteúdo de uma URL por meio de um provedor de web-fetch configurado (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

O Parallel Extract (`parallel-search`, mesma chave de API do Parallel Search) retorna apenas Markdown
— qualquer outro `format` resulta em um `400` — e limita o conteúdo a 100.000 caracteres. Quando
a própria página de destino não pode ser extraída, o serviço upstream informa isso em um HTTP 200;
o OmniRoute expõe esse caso como um `422` com uma mensagem fixa.

| Método | Caminho         | Descrição                                                    |
| ------ | --------------- | ------------------------------------------------------------ |
| POST   | `/v1/web/fetch` | Busca/extrai uma URL — corpo validado por `v1WebFetchSchema` |

**Autenticação:** chave de API Bearer (`extractApiKey` + `isValidApiKey`). Política aplicada por meio de `enforceApiKeyPolicy`.

**Fallback com reconhecimento de cota (#8297):** quando nenhum `provider` explícito é fornecido, o pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) é
percorrido em uma ordem fixa
de prioridade (preenchimento prioritário) — um provedor configurado, mas com limite de requisições atingido, é ignorado
em vez de interromper imediatamente a requisição, e uma falha upstream recuperável/de cota
(HTTP 429 sempre; 402/403 para níveis gratuitos com restrições de cota do Firecrawl/Tavily/TinyFish —
não para o Jina Reader e nunca para uma requisição inválida simples com status 400) passa para o
próximo provedor ainda não testado com credenciais disponíveis no momento da requisição. Quando todos os provedores do
pool estão esgotados, o endpoint retorna um único `429` (com um cabeçalho `Retry-After`)
em vez do `400` genérico anterior. Quando um `provider` explícito é
solicitado, **não** há fallback silencioso — um provedor explícito com limite de requisições atingido ou com falha
expõe seu próprio erro (`429` se estiver com limite de requisições atingido; caso contrário, o status
upstream).

## Streaming via WebSocket

```bash
GET /v1/ws?handshake=1
```

Valida um handshake de upgrade para WebSocket e retorna as mensagens de exemplo do protocolo de comunicação (`request`, `cancel`). Os frames WS reais são tratados pelo servidor WS incluído, fora da tabela de rotas do Next.js.

**Autenticação:** chave de API Bearer durante o handshake.

### API Responses via WebSocket (somente codex)

```bash
# Mesmo host:porta da API HTTP (padrão 20128); faça o upgrade da conexão:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ou: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# O primeiro frame DEVE ser response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Um proxy da API Responses via WebSocket está conectado **exclusivamente ao `codex`** (backend do ChatGPT). Ele escuta na mesma porta que a API/o painel nos caminhos `/v1/responses`,
`/responses` e `/api/v1/responses`. No primeiro frame `response.create`, ele
autentica e prepara por meio da ponte interna `codex-responses-ws`, seleciona uma
conexão OAuth do codex e cria um túnel para `wss://chatgpt.com/backend-api/codex/responses`
por meio do transporte `wreq-js`. **Modelos que não sejam codex são rejeitados** (`codex_ws_provider_required`).
Para roteamento por compartilhamento de cota, use `model: "qtSd/<group>/codex/<model>"`. Implementado em
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticação:** chave de API Bearer durante o handshake. O servidor HTTP incluído (`server-ws.mjs`)
deve ser o ponto de entrada ativo (e é, por padrão, quando `app/server-ws.mjs` existe).

#### ID do modelo: use o ID simples do ChatGPT (sem o prefixo `codex/`)

A **Codex CLI** da OpenAI valida o nome do modelo no lado do cliente quando
`supports_websockets = true` e **rejeita IDs com prefixo de provedor**, como
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Envie o ID **simples** (por exemplo, `gpt-5.5`). A ponte do OmniRoute é
exclusiva para codex, portanto, antes de criar o túnel para o serviço upstream, ela resolve novamente um ID simples como um modelo codex
(`resolveCodexWsModelInfo`) — embora um
`gpt-5.5` simples fosse, de outra forma, roteado para outro provedor via HTTP.

#### Configuração da Codex CLI da OpenAI

Direcione a Codex CLI para o OmniRoute adicionando um provedor personalizado com suporte a WebSocket
ao `~/.codex/config.toml` (use um `CODEX_HOME` separado para evitar alterar
uma configuração existente):

```toml
model = "gpt-5.5"                 # ID simples — NÃO "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # sem barra final; a URL do WS é derivada (use https/wss em produção)
wire_api = "responses"                    # único valor compatível desde fevereiro de 2026
supports_websockets = true                # habilita o transporte Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # contém a chave de API do OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # uma chave de API do OmniRoute (qualquer chave se REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

A CLI faz o upgrade de `base_url + /responses` para um WebSocket, e o OmniRoute cria um túnel
até a conexão OAuth do codex selecionada. Validado de ponta a ponta com o servidor
local: o ChatGPT retorna `codex.rate_limits` + `response.created` e transmite a
conclusão em streaming.

## Uso por autoatendimento (`/api/usage/om-usage`)

Qualquer chave de API pode consultar **seu próprio** uso e suas cotas — sem autenticação de gerenciamento. Este é o endpoint que um
cliente (CLI, o painel OmniCopilot) usa para mostrar ao titular de uma chave seus gastos.

```bash
# Formato de texto (o contrato histórico — texto simples para um terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato estruturado — o que uma interface de usuário consome
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

A chave deve ter **`allowUsageCommand`** habilitado (desabilitado por padrão — o gerenciador de chaves de API
do painel alterna essa opção individualmente para cada chave). Sem isso, o endpoint responde com `403`.

`?format=json` retorna uma estrutura discriminada para que um chamador nunca leia um campo de dados em uma
recusa. Em caso de sucesso:

```jsonc
{
  "allowed": true,
  // presente somente quando a chave habilitou limites de uso por chave (USD diário/semanal):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // o instantâneo da cota do provedor selecionado, ou null quando nada foi armazenado em cache ainda:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // o instantâneo de cada conexão, para que uma interface possa renderizar vários provedores lado a lado:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Em caso de recusa (`401` por chave inválida / `403` por falta de permissão), a mesma rota retorna
`{ "allowed": false, "error": { "message": "…" } }` — um `personal`/`provider` presente, porém vazio
(chave permitida, mas nenhuma informação obtida ainda), é um estado diferente de uma recusa, e somente o formato JSON
os diferencia.

**Autenticação:** a própria chave de API Bearer do chamador, validada com `isValidApiKey` — esta _não_ é a
interface de gerenciamento (`/api/keys/…`), que permanece protegida por `requireManagementAuth`.

### Percentuais de cota brutos vs. ajustados pelo limite de corte

Ao consumir `/api/usage/om-usage`, os chamadores devem observar a diferença entre os
percentuais apresentados pela **saída em texto simples** e pela **saída JSON** estruturada:

| Aspecto                              | Formato de texto simples (`/api/usage/om-usage` / `@@om-usage`)                                               | Formato JSON (`?format=json`)                                               |
| :----------------------------------- | :------------------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------------- |
| **Campo de saída**                   | `NN% left` (por exemplo, `20% left`)                                                                          | `provider.quotas` / `providers[].quotas`                                    |
| **Medição**                          | **Disponibilidade utilizável ajustada pelo limite de corte**: capacidade restante acima do limite de corte    | **Cota bruta do upstream**: medição não ajustada do provedor                |
| **Escalonamento do limite de corte** | Escalonado por meio de `effectiveRemainingPercent()` para que a reserva protegida seja exibida como `0% left` | Nenhum (valores brutos do instantâneo, conforme informados pelo provedor)   |
| **Dados de limite**                  | Incorporados ao percentual exibido                                                                            | Armazenados em `quotaWindowThresholds` por conexão (ou padrões do servidor) |
| **Consumidor principal**             | CLIs interativas, prompts de terminal, operadores humanos                                                     | Integrações programáticas, painéis, análises, rastreadores de faturamento   |

#### A fórmula de ajuste do limite de corte

O OmniRoute oferece suporte a limites de corte proativos de cota para evitar o esgotamento do upstream (configurados por meio de
`quotaWindowThresholds` da conexão, padrões do provedor ou configurações globais de resiliência). Quando um limite de corte
(por exemplo, `cutoff = 25%`) está ativo em uma janela de cota, o renderizador de texto calcula a disponibilidade restante da seguinte forma:

- Se `remaining <= cutoff`: retorna `0%`.
- Se `remaining > cutoff`: retorna `((remaining - cutoff) / (100 - cutoff)) * 100`.

A saída de texto formatada arredonda esse valor para o inteiro mais próximo (`Math.round(...)`).

#### Exemplo ilustrativo

Considere uma janela de provedor com **60% de uso bruto** (portanto, **40% de cota bruta restante**) e um limite configurado
de **25% de corte da cota restante**:

| Representação                     | Cálculo                                            | Restante |                 Uso implícito                 |
| :-------------------------------- | :------------------------------------------------- | :------: | :-------------------------------------------: |
| **JSON bruto (`?format=json`)**   | Instantâneo do upstream (`quotas[window]`)         | **40%**  |                    **60%**                    |
| **Formato de texto (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (se calculado como `100 - remaining`) |

- **Por que o texto mostra 20% restantes:** Dos 40% de cota física restantes na conta, 25% são reservados pela
  política de limite de corte. O chamador possui apenas 15% dos 75% de margem utilizável restantes antes que o roteador deixe
  de encaminhar para essa conexão. O escalonamento garante que a conexão sinalize esgotamento (`0% left`) exatamente quando
  o roteamento for interrompido.
- **Por que o JSON preserva os valores brutos:** A carga JSON retorna o instantâneo exato do provedor (`UsageSnapshot`)
  para que ferramentas externas tenham acesso à utilização real do upstream e a
  `quotaWindowThresholds` no nível da conexão, sem escalonamento com perda realizado pelo servidor.

#### Orientações para migração de consumidores

Se uma integração externa (como um plugin de editor ou uma extensão de agente) analisava anteriormente o endpoint
de texto (`NN% left`) e calculava o percentual usado como `100 - NN`, a migração para `?format=json` significa que:

- A leitura dos valores JSON brutos refletirá o **consumo real do upstream** (60% usados no exemplo acima).
- Se a integração desejar preservar a semântica de disponibilidade utilizável do endpoint de texto, ela poderá calcular
  a fórmula de restante efetivo no lado do cliente usando `quotaWindowThresholds` para substituições no nível da conexão.

## Cache semântico

```bash
# Obter estatísticas do cache
GET /api/cache/stats

# Limpar todos os caches
DELETE /api/cache/stats
```

Exemplo de resposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impacto na latência

Um ACERTO no cache semântico fornece a resposta a partir do cache **sem uma chamada
ao serviço upstream**, portanto, o `X-OmniRoute-Response-Latency` informado é próximo de zero
(independentemente da latência original do serviço upstream). Clientes sensíveis à latência
(benchmarking, monitoramento de p50/p99) devem verificar o cabeçalho de resposta
`X-OmniRoute-Cache-Latency`:

| Valor       | Significado                                                                    |
| ----------- | ------------------------------------------------------------------------------ |
| `synthetic` | Resposta fornecida pelo cache; a latência não representa o tempo real upstream |
| _(ausente)_ | Resposta proveniente de uma chamada real ao serviço upstream                   |

### Desvio do cache por chave

As chaves de API podem optar por não realizar leituras do cache semântico por meio de `cacheDefaultMode`:

| Valor    | Comportamento                                                    |
| -------- | ---------------------------------------------------------------- |
| `legacy` | Comportamento normal do cache (padrão)                           |
| `bypass` | Ignora completamente a consulta ao cache; sempre acessa upstream |

Defina durante a criação da chave (`POST /api/keys`) ou na atualização (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Desvio por solicitação

Qualquer solicitação pode ignorar o cache, independentemente das configurações da chave:

```
X-OmniRoute-No-Cache: true
```

Para modelos sincronizados/importados, `PUT /api/provider-models` aceita `provider`, `modelId` e
`maxOutputTokenOverride`: um inteiro positivo define o limite manual de tokens de saída, e `null`
o limpa para restaurar o padrão. `GET /api/provider-models?provider=<provider>` retorna esses
valores em `modelOutputOverrides`, incluindo modelos sem uma linha de modelo personalizado. A
substituição usa a capacidade de tempo de execução `max_output_tokens` e sobrevive a uma
ressincronização de modelo. A página de provedor compatível com OpenAI oferece os mesmos controles
de edição/limpeza e marca os modelos com suporte explícito a visão.

Nós personalizados de Chat Completions adaptam os opt-outs explícitos de raciocínio ao backend
upstream. Um teste de conexão bem-sucedido seleciona automaticamente os controles de chat-template
para cada ID de modelo exato cuja entrada `/models` comprove um valor `owned_by` reconhecido:
`vllm`, `sglang` ou `llamacpp`. Wrappers transparentes compatíveis com OpenAI podem preservar a
entrada de modelo original dentro de um objeto `openai` aninhado; a detecção segue até três desses
envelopes. Modelos com propriedade ausente, desconhecida ou conflitante mantêm o comportamento
OpenAI comum. A detecção reutiliza a requisição de catálogo existente, não gera tokens de conclusão
e é invalidada quando o endpoint de conexão muda.

Para fixar o comportamento de um backend que não expõe esses metadados, use a API existente de
atualização parcial de provedor:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envie esse corpo com `PUT /api/providers/<connection-id>`. Nessa conexão, um esforço de
raciocínio explícito `none` é enviado como `chat_template_kwargs.thinking=false` e
`chat_template_kwargs.enable_thinking=false`. Os valores nativos explícitos do template permanecem
autoritativos, a menos que uma regra de raciocínio no lado do servidor force um esforço. A configuração
se aplica somente quando uma conexão personalizada compatível com OpenAI despacha um corpo de Chat
Completions; requisições Responses e provedores comuns mantêm seu formato de requisição nativo.
Defina `reasoningControl` como `openai` para forçar o repasse direto do `reasoning_effort` comum da
OpenAI, ou omita-o/defina-o como `null` para usar a detecção automática.

As requisições do classificador do modo automático do Claude Code definem o pensamento nativo como
desabilitado por padrão quando não contêm controles de raciocínio explícitos. A detecção usa o
marcador de sistema do classificador em requisições no formato Claude, e não nomes de modelos ou
limites de conclusão. Controles explícitos no corpo, cabeçalhos de esforço/pensamento suportados,
regras de roteamento e o esforço resolvido do modelo mantêm sua prioridade existente. Ambos os
estágios do classificador retêm seus prompts, limites de conclusão, sequências de parada e vereditos
reais de permissão do upstream; o segundo estágio ainda pode produzir o raciocínio visível solicitado
como texto comum.

### Versão e Canal de Release

```bash
GET /api/system/version
```

Rota de gerenciamento restrita a loopback (autenticação de administrador). Retorna a versão em execução, a versão mais recente publicada e o status da atualização automática. `releaseChannel` e `channels` são campos aditivos (rail 3.8.54); `channel` mantém seu significado — o modo de implantação que o atualizador do dashboard utiliza (`npm`, `source` ou `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal npm do build em execução: `nightly` para versões `-nightly.*`,
  `next` para outros pré-lançamentos (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para uma versão estável de uma
  major mais antiga que `channels.latest`, caso contrário `latest`. Mesmas regras de
  `scripts/release/dist-tag.mjs`, que escolhe a dist-tag do npm no momento da publicação.
- `channels` — head publicado de cada dist-tag, obtido de `npm view omniroute dist-tags` (fallback
  HTTP do registry), armazenado em cache com o mesmo TTL de 10 minutos de `latest`. `latest` está sempre
  presente (recorre ao campo `latest` e, depois, a `"unavailable"`); `next`, `nightly` e `lts` aparecem
  apenas quando essa dist-tag existe. Uma requisição com `Cache-Control: no-cache` atualiza ambas as consultas.

O modelo de canais (`latest` = v3 até o GA da 4.0, `next` = rc, `nightly` = builds de `develop`,
`lts` = patches da v3 após o GA da 4.0) está descrito em `docs/ops/RELEASE_STRATEGY.md`.

## Limites de tokens

Orçamentos de **tokens** por chave de API (distintos do Orçamento baseado em USD acima). Aplicados diretamente no caminho da solicitação: quando o uso de uma chave na janela atual atinge seu limite, as solicitações são rejeitadas com `429 Too Many Requests`. Os limites podem ter como escopo um `model` específico, um `provider` ou ser aplicados `global`mente à chave; quando vários limites correspondem a uma solicitação, o mais restritivo prevalece.

```bash
# Lista os limites de tokens de uma chave (inclui o uso da janela em tempo real)
GET /api/usage/token-limits?apiKeyId=key-123

# Cria ou atualiza um limite de tokens
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Exclui um limite de tokens pelo id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Observações sobre o esquema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) são obrigatórios. `scopeValue` é obrigatório, exceto quando `scopeType` é `global` (por exemplo, um id de modelo para o escopo `model` ou um id de provedor para o escopo `provider`). `tokenLimit` deve ser um número inteiro positivo (convertido a partir de uma string). Opcionais: `id` (omita para criar, forneça para atualizar), `resetInterval` (`daily` | `weekly` | `monthly`, padrão `monthly`), `resetTime` (`HH:MM`), `enabled` (padrão `true`). As respostas de `GET` enriquecem cada limite com `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Este é um endpoint da classe de gerenciamento (a autenticação é aplicada centralmente pelo pipeline de autorização).

## Processamento de solicitações

1. O cliente envia uma solicitação para `/v1/*`
2. O manipulador da rota chama `handleChat`, `handleEmbedding`, `handleAudioTranscription` ou `handleImageGeneration`
3. O modelo é resolvido (provedor/modelo direto ou alias/combo)
4. As credenciais são selecionadas do banco de dados local com filtragem pela disponibilidade da conta
5. Para chat: `handleChatCore` verifica o cache semântico/de assinatura e resolve as configurações de compactação do combo
6. A compactação proativa é executada antes da tradução para o provedor quando habilitada (`lite`, Caveman, RTK ou empilhada)
7. O executor do provedor envia a solicitação ao serviço upstream
8. A resposta é traduzida de volta para o formato do cliente (chat) ou retornada como está (embeddings/imagens/áudio)
9. O uso, as análises de compactação e os logs de solicitações são registrados
10. O fallback é aplicado em caso de erros, de acordo com as regras do combo

Referência completa da arquitetura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resiliência (estendida)

O OmniRoute expõe três mecanismos independentes de falha temporária; os endpoints de gerenciamento abaixo permitem que operadores os leiam e substituam:

| Escopo              | Armazenamento de estado                           | Leitura                                   | Redefinir / limpar                                  |
| ------------------- | ------------------------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| Breaker de provedor | `domain_circuit_breakers` + em memória            | `/api/monitoring/health`                  | `POST /api/resilience/reset`                        |
| Cooldown de conexão | `rateLimitedUntil` em conexões de provedor        | `/api/rate-limits`, `/api/providers/[id]` | (reabilita sob demanda; limpar via PUT do provedor) |
| Bloqueio de modelo  | Registro em memória de disponibilidade de modelos | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`            |

`PATCH /api/resilience` aceita substituições de breaker de provedor em `providerBreaker.oauth` e `providerBreaker.apikey`. Cada perfil suporta `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; os mesmos campos são expostos em Dashboard → Configurações → Resiliência.

```bash
# Limpar um único bloqueio de modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Remover todos os bloqueios
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Referência conceitual completa e valores padrão do breaker: consulte [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Fila de Rate-Limit e Rede de Segurança de Auto-Ativação

- **Caminho de escrita suportado**: `POST /api/rate-limits` com corpo `{"connectionId": "<id>", "enabled": true|false}` é o endpoint de gerenciamento suportado para alternar a proteção de rate-limit de uma conexão. `PUT /api/providers/[id]` deliberadamente não modifica nem inverte `rateLimitProtection` (#11278).
- **Semântica de `enabled: false`**: Definir `enabled: false` remove a proteção explícita da conexão, mas **não** exclui uma conexão ativa de chave de API da rede de segurança global de auto-ativação (`autoEnableApiKeyProviders = true`). Em `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` são equivalentes; conexões ativas de chave de API sem proteção explícita permanecem protegidas pela rede de segurança de auto-ativação.
- **Desativação global**: Para executar conexões de chave de API sem filas de rate-limit, desative a rede de segurança globalmente via `RATE_LIMIT_AUTO_ENABLE=false` (env) ou `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Configurações → Resiliência / `PATCH /api/resilience`).

## Servidor MCP

O OmniRoute inclui um servidor Model Context Protocol integrado com 3 transportes (stdio, SSE, streamable-http) e ferramentas com escopo definido. Os endpoints do painel abaixo leem dados de status/auditoria e fazem proxy dos transportes HTTP.

| Método | Caminho | Descrição |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Heartbeat, transporte, estado online, última chamada, principais ferramentas, taxa de sucesso em 24 horas |
| GET | `/api/mcp/tools` | Lista de ferramentas MCP com `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Abre um fluxo SSE para o transporte SSE (retorna `503` se o MCP estiver desabilitado ou houver incompatibilidade de transporte) |
| POST | `/api/mcp/sse` | Envia um quadro JSON-RPC no transporte SSE |
| GET | `/api/mcp/stream` | Abre o lado SSE do transporte Streamable HTTP (mensagens iniciadas pelo servidor) |
| POST | `/api/mcp/stream` | Envia um quadro JSON-RPC no transporte Streamable HTTP |
| DELETE | `/api/mcp/stream` | Encerra uma sessão Streamable HTTP |
| GET | `/api/mcp/audit` | Consulta o log de auditoria — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Estatísticas agregadas de auditoria (totais, taxa de sucesso, duração média, principais ferramentas) |

**Autenticação:** os transportes `sse`/`stream` respeitam a interface de autenticação específica do MCP (chave de API Bearer com escopo `mcp`); as rotas `status`/`tools`/`audit*` podem ser lidas pelo painel (nenhuma autenticação adicional é necessária além de acessar o host do painel).

> Ambos os transportes HTTP são controlados por `settings.mcpEnabled` e `settings.mcpTransport` — uma incompatibilidade de transporte retorna `400`, e um estado de MCP desabilitado retorna `503`.

## Servidor A2A

O OmniRoute expõe um endpoint A2A (Agent-to-Agent) JSON-RPC 2.0, além de um wrapper REST para uso em inspeção/painel.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opcional, a menos que OMNIROUTE_API_KEY esteja definida
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Métodos compatíveis (todos condicionados a `settings.a2aEnabled`):

| Método           | Descrição                                                              |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Execução síncrona de habilidade; retorna `{task, artifacts, metadata}` |
| `message/stream` | Execução via streaming SSE do mesmo conjunto de habilidades            |
| `tasks/get`      | Busca uma tarefa por `taskId`                                          |
| `tasks/cancel`   | Cancela uma tarefa por `taskId`                                        |

Habilidades integradas: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Cartão do agente

```bash
GET /.well-known/agent.json
```

Retorna o cartão público do agente A2A (nome, descrição, recursos, catálogo de habilidades, esquema de autenticação) — armazenado em cache público por 1h. Nenhuma autenticação é necessária.

### Auxiliares REST

| Método | Caminho                      | Descrição                                                                                                          |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/a2a/status`            | A2A habilitado + estatísticas de tarefas + resumo do cartão do agente armazenado em cache                          |
| GET    | `/api/a2a/tasks`             | Lista tarefas — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Não implementado como auxiliar REST — crie via JSON-RPC `message/send`)                                           |
| GET    | `/api/a2a/tasks/[id]`        | Recupera uma tarefa                                                                                                |
| POST   | `/api/a2a/tasks/[id]/cancel` | Cancela uma tarefa                                                                                                 |

**Autenticação:** os auxiliares REST são executados sem autenticação de gerenciamento (podem ser lidos pelo painel); a rota JSON-RPC `/a2a` usa o Bearer `OMNIROUTE_API_KEY`, caso esteja configurado.

## Autenticação

Consulte [Autenticação de gerenciamento](../guides/MANAGEMENT-AUTH.md) para conhecer as quatro famílias de credenciais (sessão do dashboard, token da CLI local, Token de Acesso `oma_live_…`, chave de API com escopo de gerenciamento) e como elas diferem das chaves de inferência.

- As rotas do dashboard (`/dashboard/*`) usam o cookie `auth_token`
- O login usa o hash de senha salvo; em caso de falha, usa `INITIAL_PASSWORD`
- `requireLogin` pode ser alternado por meio de `/api/settings/require-login`
- As rotas `/v1/*` podem exigir opcionalmente uma chave de API Bearer quando `REQUIRE_API_KEY=true`
- Nesta referência, "token de gerenciamento" / "chave de API com escopo de gerenciamento" significa uma das famílias descritas nesse guia — não um tipo adicional indefinido de segredo

> **Alteração incompatível (v3.8.0)** — `/api/v1/agents/tasks/*` e os endpoints de gerenciamento de cooldown agora exigem **autenticação de gerenciamento** (cookie `auth_token` do dashboard ou uma chave de API com escopo de gerenciamento). Os clientes que anteriormente chamavam essas rotas sem autenticação receberão `401 Unauthorized`. Consulte o commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
