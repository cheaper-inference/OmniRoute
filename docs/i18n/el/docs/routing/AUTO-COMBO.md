## Αυτόματη δρομολόγηση χωρίς ρυθμίσεις (πρόθεμα `auto/`)

> **ΝΕΟ:** Δεν απαιτείται δημιουργία συνδυασμού. Χρησιμοποιήστε απευθείας το πρόθεμα `auto/` σε οποιονδήποτε client.

### Γρήγορα παραδείγματα

| Αναγνωριστικό μοντέλου | Παραλλαγή     | Συμπεριφορά                                                                                       |
| ---------------------- | ------------- | ------------------------------------------------------------------------------------------------- |
| `auto`                 | προεπιλεγμένη | Όλοι οι συνδεδεμένοι πάροχοι, στρατηγική LKGP, ισορροπημένα βάρη                                  |
| `auto/coding`          | coding        | Βάρη με προτεραιότητα στην ποιότητα, κατάλληλα για δημιουργία κώδικα                              |
| `auto/fast`            | fast          | Σταθμισμένη επιλογή χαμηλής καθυστέρησης                                                          |
| `auto/cheap`           | cheap         | Δρομολόγηση βελτιστοποιημένη ως προς το κόστος (πρώτα το χαμηλότερο κόστος)                       |
| `auto/offline`         | offline       | Προτιμά παρόχους με τη μεγαλύτερη διαθεσιμότητα ορίου χρήσης                                      |
| `auto/smart`           | smart         | Προτεραιότητα στην ποιότητα + υψηλότερο ποσοστό εξερεύνησης (10%) για καλύτερη ανακάλυψη μοντέλων |
| `auto/lkgp`            | lkgp          | Ρητή χρήση LKGP (ίδιο με το προεπιλεγμένο `auto`)                                                 |
| `auto/chaos`           | chaos         | Παράλληλη διασπορά, ένα μοντέλο ανά πάροχο (όχι εισαγωγή σφαλμάτων)                               |

### Σύνθεση κατηγορίας × βαθμίδας (`auto/<category>:<tier>`)

Τα επιθήματα τύπου OpenRouter διαχωρίζουν **το είδος της διαδρομής** (κατηγορία) από **τον τρόπο βελτιστοποίησής της** (βαθμίδα), ώστε να μπορείτε να τα συνθέτετε ελεύθερα (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Κατηγορίες** (φιλτράρουν τη δεξαμενή υποψηφίων βάσει δυνατοτήτων): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. Τα `vision`/`multimodal` διατηρούν μοντέλα με δυνατότητες όρασης, ενώ το `reasoning` διατηρεί μοντέλα συλλογισμού/σκέψης.
- **Βαθμίδες** (επιλέγουν τα βάρη βαθμολόγησης / το φίλτρο της δεξαμενής): `fast` (ταχεία παράδοση) · `cheap` (ψευδώνυμο `floor`, εξοικονόμηση κόστους) · `reliable` (κατάσταση circuit breaker + σταθερότητα καθυστέρησης) · `free` / `pro` (φιλτράρουν τη δεξαμενή βάσει βαθμίδας μοντέλου μέσω του `classifyTier` — δωρεάν βαθμίδα έναντι premium).

| Παράδειγμα             | Επιλύεται σε                                                            |
| ---------------------- | ----------------------------------------------------------------------- |
| `auto/coding:fast`     | δεξαμενή coding, βάρη χαμηλής καθυστέρησης                              |
| `auto/coding:cheap`    | δεξαμενή coding, βελτιστοποίηση κόστους (ψευδώνυμο `auto/coding:floor`) |
| `auto/reasoning:pro`   | μόνο μοντέλα συλλογισμού/σκέψης, βαθμίδα premium                        |
| `auto/vision`          | μοντέλα με δυνατότητες όρασης (χωρίς βαθμίδα → ισορροπημένα βάρη)       |
| `auto/multimodal:free` | μοντέλα με πολυτροπικές δυνατότητες, μόνο δωρεάν βαθμίδα                |

Κάθε έγκυρο `auto/<category>[:<tier>]` επιλύεται κατ’ απαίτηση· ένα επιμελημένο υποσύνολο δημοσιεύεται στο `/v1/models` και στον πίνακα ελέγχου (`AUTO_SUFFIX_VARIANTS` στο `open-sse/services/autoCombo/builtinCatalog.ts`). Το φιλτράρισμα είναι **fail-open** — αν ένας περιορισμός δεν αντιστοιχεί σε κανένα συνδεδεμένο μοντέλο, χρησιμοποιείται ολόκληρη η δεξαμενή, ώστε η δρομολόγηση να μη διακόπτεται ποτέ. Ο βασικός μηχανισμός βαθμολόγησης (`combo.ts`) παραμένει αμετάβλητος· το φίλτρο κατηγορίας/βαθμίδας εφαρμόζεται στο `buildAutoCandidates`.

> **Ζωντανή ευφυΐα μοντέλων:** η καταλληλότητα της αυτόματης δρομολόγησης ενημερώνεται από τις ζωντανές κατατάξεις **Arena ELO** + τα δεδομένα βαθμίδων του **models.dev**, όταν είναι ενεργοποιημένη η σημαία `ARENA_ELO_SYNC_ENABLED` (διαφορετικά χρησιμοποιείται ως εναλλακτική ο στατικός χάρτης καταλληλότητας).

**Τρόπος χρήσης:**

```bash
# Οποιοδήποτε IDE ή εργαλείο CLI που υποστηρίζει τη μορφή OpenAI
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# Στον κώδικα/στις ρυθμίσεις σας, ορίστε το μοντέλο ως:
model: "auto"                 # ισορροπημένη προεπιλογή
model: "auto/coding"          # καλύτερο για εργασίες προγραμματισμού
model: "auto/fast"            # ταχύτερο διαθέσιμο
model: "auto/cheap"           # φθηνότερο ανά token
```

**Τι συμβαίνει:**

1. Το OmniRoute εντοπίζει το πρόθεμα `auto/` στο `src/sse/handlers/chat.ts`
2. Αναζητά όλες τις **ενεργές συνδέσεις παρόχων** από τη βάση δεδομένων
3. Φιλτράρει όσες διαθέτουν έγκυρα διαπιστευτήρια (κλειδί API ή token OAuth)
4. Προσδιορίζει το μοντέλο ανά σύνδεση (`connection.defaultModel` ή το πρώτο μοντέλο του παρόχου)
5. Δημιουργεί έναν **εικονικό συνδυασμό** στη μνήμη (δεν αποθηκεύεται στη βάση δεδομένων)
6. Εκτελεί τη δρομολόγηση χρησιμοποιώντας το προφίλ βαρών της επιλεγμένης παραλλαγής + τη στρατηγική LKGP

**Βασικές ιδιότητες:**

- ✅ **Πάντα ενεργό:** Δεν απαιτείται διακόπτης, δημιουργία συνδυασμού ή ρύθμιση
- ✅ **Δυναμικό:** Αντικατοπτρίζει αυτόματα τους τρέχοντες συνδεδεμένους παρόχους
- ✅ **Συνέπεια συνεδρίας:** Το LKGP διασφαλίζει ότι δίνεται προτεραιότητα στον τελευταίο επιτυχημένο πάροχο
- ✅ **Υποστήριξη πολλαπλών λογαριασμών:** Κάθε σύνδεση παρόχου γίνεται ξεχωριστός υποψήφιος
- ✅ **Χωρίς εγγραφές στη βάση δεδομένων:** Ο εικονικός συνδυασμός υπάρχει μόνο για το αίτημα, χωρίς καμία επιβάρυνση μόνιμης αποθήκευσης

### Έλεγχος υποψηφίων ανά κλειδί (#7819, Επίπεδο 1+2)

Το `GET /v1/auto-combo/{channel}/candidates` (`{channel}` = το επίθημα μετά το `auto/` ή
η κυριολεκτική τιμή `auto` για το βασικό κανάλι) είναι ένα endpoint **μόνο για ανάγνωση**, το οποίο παραθέτει την
τρέχουσα δεξαμενή υποψηφίων ενός καναλιού `auto/*`, εμπλουτισμένη με δεδομένα ζωντανής προσβασιμότητας, επαναχρησιμοποιώντας
τις υπάρχουσες αναγνώσεις ανθεκτικότητας (ποτέ την ανεπεξέργαστη `state` του breaker):

- circuit breaker παρόχου — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- περίοδος αναμονής σύνδεσης — `rateLimitedUntil` / `testStatus` στην επιλυμένη εγγραφή
  `provider_connections`
- αποκλεισμός μοντέλου — `isModelLocked(provider, connectionId, model)`

Κάθε υποψήφιος περιλαμβάνει επίσης τη σημαία `excluded` αυτού του κλειδιού API. Οι εξαιρέσεις αποθηκεύονται
ανά κλειδί API (πίνακας `auto_candidate_overrides`, migration `128`) — το OmniRoute είναι
single-tenant χωρίς πίνακα `users`, επομένως το `apiKeyId` είναι η πλησιέστερη πραγματική ταυτότητα
ανά καλούντα — και επιβάλλονται στο κρίσιμο σημείο ελέγχου της δεξαμενής υποψηφίων στο
`open-sse/services/autoCombo/virtualFactory.ts` μέσω της αμιγούς και καλυμμένης από unit tests
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Το φίλτρο είναι **fail-open**: ένα μη ορισμένο apiKeyId/channel ή μια αποτυχία αναζήτησης στη βάση δεδομένων
αφήνουν τη δεξαμενή αφιλτράριστη, ώστε ένας διαχειριστής χωρίς διαμορφωμένες παρακάμψεις να βλέπει δρομολόγηση
πανομοιότυπη σε επίπεδο byte με εκείνη πριν από αυτήν τη λειτουργία.

**Μετατέθηκε σε επόμενο ζήτημα:** βάρη ανά υποψήφιο + ρητή σειρά προτεραιότητας (Επίπεδο 3
— τροφοδοτεί τις υπάρχουσες διαδρομές στρατηγικής στάθμισης/προτεραιότητας) και καρφίτσωμα μιας συγκεκριμένης
στρατηγικής `combo.ts` ανά κανάλι `auto/*` (Επίπεδο 4). Δείτε το σχέδιο #7819 για το ανοιχτό
ερώτημα σχετικά με το αν οι παρακάμψεις θα πρέπει να παραμείνουν ανά κλειδί API ή να γίνουν καθολικές, δεδομένου του
μοντέλου ενός μισθωτή.

**Στο παρασκήνιο:**

```txt
Αίτημα: { model: "auto/coding" }
   ↓
Το src/sse/handlers/chat.ts εντοπίζει το πρόθεμα
   ↓
createVirtualAutoCombo('coding') → candidatePool από ενεργές συνδέσεις
   ↓
handleComboChat (ίδια μηχανή με τους αποθηκευμένους συνδυασμούς)
   ↓
Η αυτόματη βαθμολόγηση επιλέγει τον καλύτερο πάροχο/μοντέλο ανά αίτημα
```

**Αρχεία υλοποίησης:**

| Αρχείο                                                    | Σκοπός                                               |
| --------------------------------------------------------- | ---------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Αναλυτής προθέματος (`parseAutoPrefix`)              |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Δημιουργεί εικονικά αντικείμενα `AutoComboConfig`    |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Άγκιστρο δοκιμών για προσομοίωση του μητρώου παρόχων |
| `src/sse/handlers/chat.ts`                                | Ενσωμάτωση: παράκαμψη για το πρόθεμα auto            |
| `src/shared/constants/providers.ts`                       | Καταχώριση συστήματος `SYSTEM_PROVIDERS.auto`        |

## Προτιμήσεις λογαριασμού για αποθηκευμένους αυτόματους συνδυασμούς

Το Intelligent Auto editor προσφέρει ένα προαιρετικό** Προτιμήσεις λογαριασμού** τμήμα. Κάθε σύνδεση μπορεί να είναι Preferred, Normal (η προεπιλογή), Reserve ή Excluded. Πολλές συνδέσεις μπορούν να μοιράζονται ένα επίπεδο. Αυτόματη επιλογή εντός της πρώτης κατάλληλης βαθμίδας, διατηρώντας τη συμπεριφορά scoring/router εκεί. αποτυχημένες προσπάθειες εμπίπτουν στους υπόλοιπους συγκεκριμένους λογαριασμούς, που προτιμώνται πριν από την κανονική πριν από την κράτηση. Οι εξαιρούμενες συνδέσεις δεν χρησιμοποιούνται ποτέ από αυτόν τον συνδυασμό.

Η ρύθμιση αποθηκεύεται ως `config.accountPreferences`, πληκτρολογημένη από τη σύνδεση ID:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

Ένας παραλειπόμενος ή κενός χάρτης διατηρεί την υπάρχουσα δρομολόγηση. Οι προτιμήσεις δεν ενεργοποιούν τις απενεργοποιημένες συνδέσεις, δεν εκχωρούν πρόσβαση σε κλειδί API, δεν επαναφέρουν υποψηφίους που έχουν αποκλειστεί βάσει ορίων ή παρακάμπτουν τους ελέγχους προϋπολογισμού. Κάθε προσπάθεια περιορίζεται στη συγκεκριμένη σύνδεσή της, επομένως η επιστροφή λογαριασμού δεν μπορεί να μεταπηδήσει σε επίπεδα πίσω από τον δρομολογητή συνδυασμού. Η υπάρχουσα συνάφεια συνεδρίας μπορεί να διατηρήσει έναν κατάλληλο λογαριασμό. Η εξαίρεση του λογαριασμού που είναι δεσμευμένος σε μια εγγενή στροφή σταματά αυτή τη σειρά αντί να αλλάζει σιωπηλά τους λογαριασμούς.

Οι διαμορφωμένες προτιμήσεις χρησιμοποιούν την αυτόματη διαδρομή με επίγνωση λογαριασμού: οι μη δεσμευμένες συντομεύσεις cache περιβάλλοντος, smart-pipeline, χάος και σκιώδεις συντομεύσεις δεν αποστέλλονται. Η κερδοσκοπική αντιστάθμιση είναι απενεργοποιημένη για αυτά τα αιτήματα, επομένως οι αποθεματικοί λογαριασμοί δεν μπορούν να ανταγωνιστούν τους προτιμώμενους λογαριασμούς. Άλλες συνδυαστικές στρατηγικές δεν ερμηνεύουν αυτήν τη ρύθμιση. Η αλλαγή ενός συνδυασμού από το Auto διατηρεί τις αποθηκευμένες προτιμήσεις για μεταγενέστερη εναλλαγή.

## Ονόματα Combo που Ταιριάζουν με Πραγματικό Model Id

Ένα combo του οποίου το `name` είναι πανομοιότυπο με ένα απλό model id (π.χ. ένα combo με όνομα
`gpt-5.5`) είναι ένα **σκόπιμο, υποστηριζόμενο μοτίβο**, όχι σφάλμα: αποτελεί τον
μηχανισμό για ανάκαμψη (fallback) παρόχου ανά model id, όπως τεκμηριώνεται στο
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Επειδή η
επίλυση combo ελέγχεται πριν από την επίλυση απλού model id
(`getComboForModel()` στο `src/sse/services/model.ts`), ένα αίτημα για το απλό
id `gpt-5.5` δρομολογείται μέσω των στόχων του combo (π.χ.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) αντί για απευθείας σε
έναν μόνο πάροχο — αυτό επαναχρησιμοποιεί την προτεραιότητα combo-πριν-από-επανεγγραφή που δημιουργήθηκε για το
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) και ελέγχεται
με παλινδρομικά τεστ από τα `tests/unit/responses-combo-resolution-3227.test.ts` και
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Η δημιουργία ή μετονομασία ενός combo σε όνομα που σκιάζει ένα πραγματικό model id
**δεν απορρίπτεται ποτέ** — κάτι τέτοιο θα έσπαγε αυτήν την τεκμηριωμένη ροή εργασίας. Αντ' αυτού
(#8530), τα `POST /api/combos` και `PUT /api/combos/[id]` επισυνάπτουν ένα μη αποκλειστικό
πεδίο `warning` στην απόκριση όταν το (νέο) όνομα συγκρούεται με ένα πραγματικό
model id:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Κατά την εκκίνηση, η `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) καταγράφει επίσης μια μονόγραμμη προειδοποίηση `[STARTUP]`
που απαριθμεί κάθε υπάρχον combo που σκιάζει ένα model id, ώστε οι διαχειριστές που
το συναντούν κατά λάθος (αντί σκόπιμα, σύμφωνα με το #6940) να έχουν ένα σήμα.
Το βοηθητικό εργαλείο εντοπισμού βρίσκεται στο `src/lib/combos/modelNameCollision.ts`.

## Κλήση Προσαρμοσμένου Combo από Πελάτη

Τα αποθηκευμένα combo (Ρυθμίσεις → Combos) χρησιμοποιούνται μόνο όταν ο πελάτης αποστέλλει το **ακριβές όνομα** του combo στο πεδίο `model` — δεν υπάρχει ασαφής ή μερική αντιστοίχιση του ονόματος combo, ούτε εμπλέκεται πρόθεμα `auto/`. Σειρά επίλυσης (`getComboForModel()` στο `src/sse/services/model.ts`):

1. ακριβής αντιστοίχιση ονόματος combo (`model: "my-combo"`),
2. πρόθεμα `combo/<name>` (`model: "combo/my-combo"`),
3. αντιστοιχίσεις glob model→combo (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Δύο συνηθισμένες παγίδες:

- **Το `auto` δεν χρησιμοποιεί τα combo σας.** Το `auto`/`auto/*` δημιουργεί τη δική του δεξαμενή υποψηφίων χωρίς ρύθμιση και συμβουλεύεται αποθηκευμένα combo μόνο αν ένα combo έχει κυριολεκτικά το όνομα `auto` (δεν συνιστάται). Για να δρομολογήσετε μέσω ενός combo, αποστείλετε το ακριβές όνομά του — όχι `auto`.
- **Το `openrouter/auto` είναι ένα πραγματικό επί πληρωμή προϊόν OpenRouter** («Auto Best Available»), όχι ένα ψευδώνυμο OmniRoute. Αποτελεί την ενιαία στατική καταχώριση μοντέλου του μητρώου OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) και χρεώνεται ξεχωριστά. Χρησιμοποιήστε Ρυθμίσεις → Δρομολόγηση → Απόκρυψη επί πληρωμή μοντέλων για να το εξαιρέσετε από τις δεξαμενές `auto`.

Δείτε τα [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) και [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) για την αρχική σύγχυση που τεκμηριώνει αυτό το κείμενο.

## Πώς λειτουργεί (Μόνιμοι αυτόματες συνδυασμοί)

Το Auto-Combo Engine επιλέγει δυναμικά το καλύτερο provider/model για κάθε αίτημα χρησιμοποιώντας ένα** Συνάρτηση βαθμολόγησης 16 παραγόντων** (ορίζεται στο `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Το προεπιλεγμένο άθροισμα βαρών σε `1.0`; Τα προσαρμοσμένα βάρη κανονικοποιούνται εκ νέου από `normalizeScoringWeights()`. Δύο από τα δεκαέξι — `cacheAffinity` και `resetWindowAffinity` — έχουν προεπιλεγμένο βάρος `0`. `reliability` μεταφέρει `0` σε `DEFAULT_WEIGHTS` αλλά `0.03` σε γενικά πακέτα και `0.04` σε `reliability-first` και `quality` μεταφέρει `0.02` σε πακέτα (`0.03` σε `quality-first`): εξακολουθούν να υπολογίζονται για κάθε υποψήφιο και `cacheAffinity` πύλες προτρέπει την αφαίρεση της προσωρινής μνήμης εκτός της βαθμολογίας, επομένως τα μηδενικά προεπιλεγμένα πακέτα απλώς δεν ψηφίζουν από προεπιλογή.

> **Μη αναγνώσιμο όριο (#15347).** Όταν ένας πάροχος έχει μια ανάκτηση ορίου αλλά δεν επιστρέφει τίποτα αναγνώσιμο (αποτυχία λήψης, ελλείποντα διαπιστευτήρια, χρήση μόνο μηνύματος ή στιγμιότυπο με λανθασμένη μορφή χωρίς αναλύσιμο `windows` και χωρίς πεπερασμένο `percentUsed`, συμπεριλαμβανομένου `percentUsed: null`), ο υποψήφιος βαθμολογεί `0` στον άξονα `quota` και η τελική του βαθμολογία πολλαπλασιάζεται επί `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR`, `autoStrategy.ts`). μοτίβο ήπιας ποινής ως ποινή κατάστασης σύνδεσης. Μια αποτυχημένη ανάγνωση χρήσης είναι απόδειξη για την τηλεμετρία, όχι για τον πάροχο, επομένως κατατάσσεται αυστηρά κάτω από οποιαδήποτε πραγματική ένδειξη, συμπεριλαμβανομένης μιας επιβεβαιωμένης 100%-used, αλλά ποτέ δεν αποκλείεται ή αποβάλλεται. Ένας πάροχος χωρίς ανώτατο όριο αναφέρει `unlimited: true` και βαθμολογείται ως πλήρες όριο. ένας πάροχος χωρίς καταχωρημένη ανάκτηση ορίου δεν έχει καθόλου πηγή τηλεμετρίας και διατηρεί την προεπιλογή του `100`.

**Ποσό:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` όπως δηλώνεται στο `DEFAULT_WEIGHTS`; Τα βάρη που έχουν ρυθμιστεί από τον χρήστη επανακανονικοποιούνται σε κατανομή κατά `normalizeScoringWeights()` πριν από τη βαθμολόγηση.

"cheapest") ορίζει τη μόνιμη πολιτική· η κεφαλίδα την παρακάμπτει για ένα μόνο αίτημα.

### σημασιολογία `weighted`

`weighted` είναι α** αναλογική τυχαία κλήρωση ανά αίτημα** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), όχι ισοσταθμιστής:

- Κάθε αίτημα κληρώνει** ένας** βήμα με πιθανότητα `weight / totalWeight`; Τα υπόλοιπα βήματα ταξινομούνται με φθίνουσα βαρύτητα ως εναλλακτική αλυσίδα για αυτό το αίτημα.
- Ένα βήμα του οποίου το βάρος είναι `0` (ή λείπει) είναι** ποτέ τραβηγμένο** ενώ οποιοδήποτε άλλο βήμα έχει βάρος > 0 — μπορεί να χρησιμεύσει ως εναλλακτική λύση μόνο μετά την αποτυχία του σχεδιασμένου βήματος. Μόνο όταν** όλοι** τα βάρη είναι 0 η επιλογή γίνεται ομοιόμορφη.
- Τα βήματα των οποίων οι στόχοι δεν είναι όλοι διαθέσιμοι διακόπτης κυκλώματος παρόχου — `OPEN`, ψύξη σύνδεσης, κλείδωμα μοντέλου — καταργούνται από την κλήρωση πριν γίνει (`open-sse/services/combo/targetResolution.ts`), έτσι ώστε ένα μόνο υγιές βήμα να μπορεί να κερδίσει προσωρινά κάθε αίτημα.
- `stickyWeightedLimit` (συνδυαστική διαμόρφωση, προεπιλεγμένη `1` = απενεργοποιημένη) καρφιτσώνει το βήμα που σχεδιάστηκε για τόσες πολλές διαδοχικές επιτυχίες πριν από την εκ νέου σχεδίαση.

Για αυστηρή εναλλαγή χρησιμοποιήστε `round-robin`; ίσα βάρη στο `weighted` δίνουν στατιστική — όχι αυστηρή ισορροπία —.

### Λειτουργία πρακτορείου αγωγού

Ένας συνδυασμός `pipeline` με τουλάχιστον δύο μοντέλα μπορεί να επιλέξει τη δρομολόγηση planner/executor με `config.agenticOrchestration.enabled`. Ο πρώτος στόχος έχει τον προγραμματισμό και τις τελικές απαντήσεις. ο δεύτερος στόχος εκπέμπει κλήσεις εργαλείων εγγενούς πελάτη. OmniRoute ανιχνεύει τις συνεχίσεις των αποτελεσμάτων εργαλείου από το πρωτόκολλο αιτήματος, ρωτά τον σχεδιαστή εάν χρειάζεται άλλος γύρος εργαλείων και καθιστά δυναμικά είτε τον εκτελεστή είτε τον προγραμματιστή το τελικό βήμα που αντιμετωπίζει ο πελάτης.

Το προαιρετικό `config.agenticOrchestration.contextCompaction` εφαρμόζει ξεχωριστό προϋπολογισμό ωφέλιμου φορτίου πριν από κάθε αποστολή σχεδιαστή ή εκτελεστή. Ενεργοποιήστε το ρητά:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

Πρόκειται για σειριακούς προϋπολογισμούς χαρακτήρων JSON που επιλέγονται από τον χειριστή, όχι παράθυρα περιβάλλοντος συμβολικού ή εγγυημένα όρια ανάντη. Το ακριβές μοντέλο IDs παρακάμπτει την προεπιλογή. Πάνω από το όριο, η συμπύκνωση καταργεί τους ίδιους ορισμούς εργαλείων, περικόπτει μεγάλα στοιχεία εργαλείων με μια σύνοψη και αφαιρεί παλιές ομάδες πλήρους ιστορικού προς την αναλογία στόχο. Διατηρεί οδηγίες system/developer, το πιο πρόσφατο αίτημα χρήστη, τον τελευταίο γύρο εργαλείων συμπεριλαμβανομένου του παράλληλου calls/results και την κύρια οδηγία δρομολόγησης του Gemini. Οι οδηγίες ανώτατου επιπέδου και οι ρυθμίσεις εργαλείου διατηρούνται. Ένας δείκτης παράλειψης καταγράφει το καταργημένο ιστορικό. πρόκειται για ντετερμινιστική περικοπή, όχι για σημασιολογική περίληψη. Εάν το καρφιτσωμένο περιβάλλον εξακολουθεί να υπερβαίνει τον προϋπολογισμό, το αίτημα επιστρέφει 413 πριν επικοινωνήσει με το μοντέλο. Όταν η συμπίεση είναι απενεργοποιημένη ή κάτω από το όριο, το αίτημα περνά αμετάβλητο.

Στις συνέχειες αποτελεσμάτων εργαλείου, OmniRoute σταματά επίσης την εκτέλεση όταν δύο διαδοχικοί ολοκληρωμένοι γύροι επαναλαμβάνουν τις ίδιες κλήσεις εργαλείου με αμετάβλητα αποτελέσματα ή όταν κάθε ρητά επισημασμένο αποτέλεσμα σε δύο διαδοχικούς γύρους απέτυχε. Τα αλλαγμένα αποτελέσματα επιτρέπουν επαναλαμβανόμενες κλήσεις (για παράδειγμα, ψηφοφορία). Ο φύλακας κάνει επαναφορά μετά από αίτημα νέου χρήστη, ομαδοποιεί παράλληλες κλήσεις σε έναν γύρο και υποστηρίζει Anthropic, Ολοκληρώσεις συνομιλιών, Απαντήσεις και ιστορικά Gemini. Ο υπεύθυνος σχεδιασμού λαμβάνει την αιτία και έχει την τελική απάντηση ακόμα κι αν ζητήσει έναν άλλο γύρο εργαλείων.

Πρόσθετα μοντέλα μετά τον δεύτερο στόχο παραγγέλλονται αντίγραφα ασφαλείας του εκτελεστή. Μια αποτυχημένη απόκριση HTTP ή εξαίρεση μεταφοράς προχωρά στον επόμενο εκτελεστή, φέρνοντας την ίδια απόφαση σχεδιαστή και εγγενή εργαλεία, αλλά η άμεση και επιλυμένη σύνδεση του ίδιου του εκτελεστή. Η πρώτη επιτυχημένη απόκριση επιστρέφεται αμετάβλητη, συμπεριλαμβανομένης της ροής SSE. Οι αποτυχίες μετά την επιτυχή έναρξη μιας ροής δεν μπορούν να επαναληφθούν εδώ. Εάν αποτύχουν όλοι οι εκτελεστές, επιστρέφεται η τελευταία αποτυχία. Ο πελάτης ματαιώνει τη διακοπή αποστολής.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Ο εκτελεστής μπορεί να εκπέμψει πολλαπλές ανεξάρτητες κλήσεις σε μία απόκριση. Οι εξαρτημένες κλήσεις αντιμετωπίζονται σε μεταγενέστερες στροφές αποτελεσμάτων εργαλείων πελάτη, με τον υπεύθυνο σχεδιασμού να εξετάζει κάθε αποτέλεσμα. `maxToolRounds` ορίζει ως προεπιλογή `8` και δέχεται `1`–`32`; Μόλις επιτευχθεί, ο σχεδιαστής πρέπει να παράγει την καλύτερη διαθέσιμη τελική απάντηση. Οι εσωτερικές αποφάσεις του σχεδιαστή αποθηκεύονται στην προσωρινή μνήμη, ενώ η επιλεγμένη απόκριση που αντιμετωπίζει ο πελάτης διατηρεί την αρχική προτίμηση ροής.

### `round-robin` sticky batch και επέκταση λογαριασμού

Το Round Robin ολοκληρώνεται και όχι ένα αίτημα ανά βήμα:

- `stickyRoundRobinLimit` (combo config, μετά `comboStickyRoundRobinLimit`, μετά `settings.stickyRoundRobinLimit`, προεπιλογή** 3** ) διατηρεί τον ίδιο στόχο για τόσες διαδοχικές επιτυχίες πριν από την εναλλαγή. Ορίστε την σύνθετη παράκαμψη σε `1` για περιστροφή με ένα αίτημα. Ο σύνθετος επεξεργαστής εμφανίζει την αποτελεσματική τιμή και από ποιο επίπεδο προήλθε.
- `connectionAwareExpansion` (combo config, μετά ρυθμίσεις, προεπιλογή** ψευδής** ) επεκτείνει κάθε βήμα σε επίπεδο παρόχου σε στόχους ανά λογαριασμό πριν από την εναλλαγή. Οι στρατηγικές ομάδας Β (προτεραιότητα, σταθμισμένη, στρογγυλή, τυχαία, p2c, λιγότερο χρησιμοποιούμενη, βελτιστοποιημένη ως προς το κόστος, lkgp, συμπλήρωση πρώτα, αυστηρά τυχαία, βελτιστοποιημένη για το περιβάλλον, βελτιστοποιημένη προσωρινή μνήμη, αναμετάδοση περιβάλλοντος, σύντηξη, διοχέτευση, jev) διατηρούν μια προβολή σε επίπεδο παρόχου μέχρι να ενεργοποιηθεί. Ο σύνθετος επεξεργαστής εκθέτει το inherit / on / off. το inherit χρησιμοποιεί την καθολική προεπιλογή (off).
- Δρομολόγηση τοποθεσίας προσωρινής μνήμης προτροπής (`promptCacheAffinityEnabled`, προεπιλογή** αληθής** ) αναδιατάσσει τις καρφιτσωμένες συνδέσεις, ώστε τα κλειδιά της προσωρινής μνήμης που ταιριάζουν να παραμένουν σε έναν λογαριασμό. Έχει προτεραιότητα έναντι της κυκλικής περιστροφής και της σταθμισμένης εναλλαγής στα καρφιτσωμένα βήματα ανά λογαριασμό. Απενεργοποιήστε το στις Ρυθμίσεις → Προεπιλογές Combo εάν χρειάζεστε αυστηρή εναλλαγή. Δεν υπάρχει παράκαμψη ανά σύνθετο.

Για εναλλαγή πολλών λογαριασμών σε ένα μοντέλο, προτιμήστε** ένα βήμα δυναμικού λογαριασμού** (άδειο `connectionId`, ολόκληρη πισίνα) με κολλώδες όριο `1`, όχι τρία καρφιτσωμένα `connectionId` s. Τα καρφιτσωμένα βήματα και η συνάφεια συμπτύσσονται στον ίδιο λογαριασμό ακόμα και όταν ο μετρητής RR προχωρά.

## Στρατηγική Fusion

Το `fusion` είναι η μοναδική στρατηγική που **δεν** επιλέγει έναν μόνο στόχο. Διανέμει το prompt
σε **κάθε μοντέλο του πάνελ παράλληλα**, και στη συνέχεια ένα ρυθμιζόμενο **μοντέλο-κριτής** συνθέτει
μία τελική απάντηση από όλες τις απαντήσεις του πάνελ. Μεταφέρθηκε από το upstream `decolua/9router`
(σχεδιασμός Fusion του OpenRouter)· υλοποίηση στο `open-sse/services/fusion.ts`.

Πώς λειτουργεί:

0. **Παράκαμψη εργαλείων** — ένα αίτημα που φέρει μη κενό πίνακα `tools` με
   `tool_choice` που δεν είναι ρητά `"none"` παρακάμπτει εντελώς το πάνελ: δρομολογείται απευθείας σε
   ένα μοναδικό μοντέλο (το ρυθμισμένο κριτής, ή `panel[0]`) με `tools`/`tool_choice`
   που περνούν αναλλοίωτα. Τα μέλη του πάνελ δεν έχουν πρόσβαση σε εργαλεία και η
   οδηγία σύνθεσης του κριτή αποθαρρύνει την εκπομπή κλήσεων εργαλείων, οπότε οι
   agentic/tool-calling πελάτες λαμβάνουν πραγματική απόφαση κλήσης εργαλείου αντί
   για συντεθειμένο κείμενο (#6771).
1. **Fan-out** (μόνο για αιτήματα χωρίς εργαλεία) — το prompt αποστέλλεται σε κάθε μοντέλο
   του πάνελ ταυτόχρονα, αναγκαστικά χωρίς streaming και χωρίς εργαλεία (ο κριτής χρειάζεται
   πλήρες κείμενο για να συνθέσει).
2. **Συλλογή με χάρη απαρτίας** — μόλις φτάσουν `minPanel` απαντήσεις, ξεκινά ένας σύντομος
   χρονοδιακόπτης χάριτος για τους αργούς, και στη συνέχεια η fusion προχωρά με όσα
   έχουν συλλεχθεί. Αυτό περιορίζει την επίπτωση του πιο αργού μοντέλου στον χρόνο
   τοίχου, με ένα απόλυτο χρονικό όριο ως ανώτατο φράγμα.
3. **Σύνθεση κριτή** — οι απαντήσεις του πάνελ ανωνυμοποιούνται (`Source 1`, `Source 2`, … — ώστε
   ο κριτής να σταθμίζει το περιεχόμενο, όχι το brand του μοντέλου) και παραδίδονται στον
   κριτή, ο οποίος αναλύει συναίνεση / αντιφάσεις / μερική κάλυψη / μοναδικές
   επισημάνσεις / τυφλά σημεία, και στη συνέχεια γράφει **μία** αυθεντική απάντηση. Η
   κλήση του κριτή διατηρεί το αρχικό `stream` flag του πελάτη + εργαλεία, οπότε το
   streaming και η χρήση εργαλείων downstream εξακολουθούν να λειτουργούν.
4. **Ομαλή υποβάθμιση** — 0 απαντήσεις πάνελ → `503`· ακριβώς 1 επιζώσα απάντηση → επιστρέφεται
   απευθείας (τίποτα να συντεθεί)· ένα πάνελ μονού μοντέλου απαντά απευθείας.

Ένα μέλος του πάνελ μπορεί επίσης να είναι ένα βήμα `combo-ref` (`{kind: "combo-ref", comboName: "..."}`) που
αναφέρεται σε άλλο combo — επιλύεται ως **μία αδιαφανής φωνή πάνελ** (μια πλήρης αναδρομική
αποστολή στο αναφερόμενο combo, όχι fan-out των ίδιων στόχων του combo), με την ίδια
προστασία βάθους/κύκλου που χρησιμοποιεί κάθε άλλη στρατηγική που καταναλώνει combo-ref (#6764).

### Ρύθμιση παραμέτρων

Ρυθμίζεται στο blob `config` του combo (χωρίς μετανάστευση σχήματος — επαναχρησιμοποιεί τον
υπάρχοντα πίνακα `combos`):

| Πεδίο                                    | Τύπος    | Προεπιλογή          | Σκοπός                                                                                                           |
| :--------------------------------------- | :------- | :------------------ | :--------------------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | πρώτο μοντέλο πάνελ | Μοντέλο που συνθέτει την τελική απάντηση                                                                         |
| `config.fusionTuning.minPanel`           | `number` | `2`                 | Επιτυχείς απαντήσεις που απαιτούνται πριν ξεκινήσει ο χρονοδιακόπτης χάριτος (περιορισμένο στο `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`              | Πόση ώρα να περιμένει τους αργούς μόλις επιτευχθεί η απαρτία                                                     |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`             | Απόλυτο ανώτατο όριο ώστε ένα κολλημένο μοντέλο να μην μπλοκάρει το αίτημα                                       |

Οι προεπιλογές βρίσκονται στο `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`).

### Παράδειγμα

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

Στη συνέχεια καλέστε το όπως οποιοδήποτε combo: `{"model":"fusion-panel","messages":[...]}`.

## Εικονικό Εργοστάσιο Αυτόματου Συνδυασμού

Η μηχανή Auto Combo δεν απαιτεί προκαθορισμένους συνδυασμούς. Αντίθετα, το `open-sse/services/autoCombo/virtualFactory.ts` δημιουργεί υποψήφιους εν κινήσει:

1. Ανακτά `getProviderConnections({ isActive: true })` (όλες οι ενεργοποιημένες συνδέσεις)
2. Φιλτράρει σε αυτές με έγκυρα διαπιστευτήρια (κλειδί API ή μη-ληγμένο OAuth token μέσω `hasUsableOAuthToken()`)
3. Διασταυρώνει με `getProviderRegistry()` για διαθεσιμότητα μοντέλων + τιμολόγηση
4. Για κάθε πλειάδα `(provider, model, connection)`, κατασκευάζει ένα `VirtualAutoComboCandidate`
5. Επιλέγει `connection.defaultModel` (ή το πρώτο μοντέλο του μητρώου) ως στόχο αποστολής
6. Βαθμολογεί κάθε υποψήφιο χρησιμοποιώντας τη 16-παραγοντική `scorePool()` και το πακέτο βαρών της παραλλαγής
7. Επιστρέφει το προκύπτον `AutoComboConfig` στη μνήμη για το `handleComboChat()` — δεν αποθηκεύεται ποτέ στη βάση δεδομένων

Αυτό σημαίνει ότι **η προσθήκη νέου παρόχου με ενεργοποιημένο `auto/*` επεκτείνει αυτόματα το σύνολο υποψηφίων** — δεν χρειάζεται χειροκίνητη επεξεργασία συνδυασμών. Ο εικονικός συνδυασμός ανακατασκευάζεται ανά αίτημα, οπότε οι νέες ή πρόσφατα υγιείς συνδέσεις εντοπίζονται αμέσως.

## Αυτο-Επαναφορά

- **Προσωρινός αποκλεισμός**: Βαθμολογία < 0.2 → αποκλεισμός για 5 λεπτά (προοδευτική καθυστέρηση, μέγ. 30 λεπτά)
- **Αναγνώριση ασφαλιστήρου κυκλώματος**: OPEN → αυτόματος αποκλεισμός· HALF_OPEN → αιτήματα ανίχνευσης
- **Λειτουργία συμβάντος**: >50% OPEN → απενεργοποίηση εξερεύνησης, μεγιστοποίηση σταθερότητας
- **Ανάκαμψη μετά αποκλεισμό**: Μετά τον αποκλεισμό, το πρώτο αίτημα είναι «ανίχνευση» με μειωμένο χρονικό όριο

## Εξερεύνηση Bandit

Το 5% των αιτημάτων (ρυθμιζόμενο) δρομολογείται σε τυχαίους παρόχους για εξερεύνηση. Απενεργοποιείται σε λειτουργία συμβάντος.

## API

**Δεν υπάρχει αποκλειστικό endpoint `POST /api/combos/auto`** — το Auto-Combo χρησιμοποιείται με δύο τρόπους:

1. **Μηδενική διαμόρφωση (συνιστάται):** Στείλτε οποιοδήποτε αίτημα ολοκλήρωσης συνομιλίας με `model: "auto"` ή `model: "auto/<variant>"`. Το εικονικό factory δημιουργεί το combo για κάθε αίτημα — δεν απαιτείται αποθήκευση ούτε κλήσεις API.

2. **Αποθηκευμένο combo με `strategy: "auto"`:** Δημιουργήστε ένα κανονικό combo μέσω του `POST /api/combos` και ορίστε `strategy: "auto"`, μαζί με τα `config.auto.weights` / `config.auto.candidatePool`. Χρησιμοποιείται η ίδια μηχανή βαθμολόγησης· το combo αποθηκεύεται στο `combos` και μπορεί να επαναχρησιμοποιηθεί μέσω ID.

Για ανακάλυψη, το `GET /api/combos/auto` παραθέτει κάθε παραλλαγή με το επιλυμένο σύνολο υποψηφίων της, καθώς και τα `context_length` / `max_output_tokens` — τη ΜΕΓΙΣΤΗ τιμή μεταξύ των παραθύρων του συνόλου υποψηφίων. Οι clients (π.χ. το plugin opencode) πρέπει να γνωστοποιούν αυτές τις τιμές αντί για `0`: ένα μηδενικό context απενεργοποιεί πλήρως την αυτόματη συμπύκνωση του opencode, επιτρέποντας στις συνεδρίες να αυξάνονται μέχρι η εκκαθάριση ιστορικού του gateway να καταστρέψει το context. Η γνωστοποίηση της ΜΕΓΙΣΤΗΣ τιμής είναι ασφαλής, επειδή το προφίλτρο context του auto-combo δρομολογεί τα υπερμεγέθη αιτήματα σε υποψηφίους με μεγάλο παράθυρο.

```bash
# Χρήση με μηδενική διαμόρφωση (χωρίς δημιουργία combo)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Αποθηκευμένο auto combo μέσω του κανονικού endpoint combos
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Στρατηγικές αυτόματου router

Τα αποθηκευμένα combos με `strategy: "auto"` μπορούν να ορίσουν το `config.routerStrategy` (ή το παλαιότερο
`config.auto.routerStrategy`) σε μία από τις εξής τιμές:

- `rules` — προεπιλεγμένη σταθμισμένη βαθμολόγηση
- `score` — επιλέγει την υψηλότερη διαμορφωμένη σταθμισμένη βαθμολογία. Σε απόλυτες ισοβαθμίες διατηρείται η διαμορφωμένη
  σειρά των υποψηφίων· το υπάρχον `explorationRate` πραγματοποιεί δειγματοληψία από ολόκληρο το ταξινομημένο σύνολο.
- `cost` / `eco` — ο οικονομικότερος υγιής provider
- `latency` / `fast` — η χαμηλότερη καθυστέρηση p95 με ποινή αξιοπιστίας
- `sla-aware` / `sla` — προτιμά υποψηφίους που ικανοποιούν τα SLO καθυστέρησης p95, ποσοστού σφαλμάτων και, προαιρετικά,
  κόστους
- `lkgp` — πρώτα ο τελευταίος γνωστός καλός provider
- `nadir` — ζητά από το API αποφάσεων του [Nadir](https://getnadir.com) να προσδιορίσει ποιο μοντέλο από το σύνολο χρειάζεται το
  prompt· απαιτεί ρητή ενεργοποίηση και, σε περίπτωση αποτυχίας, επιστρέφει ανοιχτά στο `rules`

### Αναλυτικά οι στρατηγικές router

Η μηχανή auto-combo παρέχει 7 εναλλάξιμες υλοποιήσεις **RouterStrategy**, τις οποίες
μπορείτε να αλλάξετε μέσω του `config.routerStrategy` (ή του παλαιότερου `config.auto.routerStrategy`).
Κάθε στρατηγική επιλέγει έναν provider από το σύνολο υποψηφίων, βάσει ενός `RoutingContext`
(τύπος εργασίας, ενδείξεις εργαλείων/όρασης, εκτίμηση token, προαιρετική πολιτική SLA, προαιρετικός
τελευταίος γνωστός καλός provider).

#### 1. `rules` (προεπιλογή) — σταθμισμένη βαθμολόγηση 16 παραγόντων

Περιβάλλει την υπάρχουσα μηχανή βαθμολόγησης. Φιλτράρει τους υποψηφίους με circuit breaker σε κατάσταση `OPEN`
και έπειτα εκτελεί το `scorePool()` με τον τρέχοντα τύπο εργασίας και το `getTaskFitness()`,
επιλέγοντας τον provider με την υψηλότερη βαθμολογία.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Πότε να χρησιμοποιείται**: Προεπιλογή. Χρησιμοποιήστε τη όταν θέλετε μια ισορροπημένη αντιστάθμιση μεταξύ όλων των σημάτων.

**Ψευδώνυμο**: `rules` (χωρίς ψευδώνυμο)

---

#### 2. `cost` / `eco` — ο οικονομικότερος υγιής provider

Ταξινομεί το σύνολο υποψηφίων βάσει του `costPer1MTokens` (σε αύξουσα σειρά) και επιλέγει τον οικονομικότερο.
Αρχικά φιλτράρει τους υποψηφίους με κατάσταση `OPEN`.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Πότε να χρησιμοποιείται**: Φόρτοι εργασίας ευαίσθητοι στο κόστος, μαζική επεξεργασία ή εργασίες παρασκηνίου.

**Ψευδώνυμα**: `cost`, `eco`

---

#### 3. `latency` / `fast` — η χαμηλότερη καθυστέρηση p95 με ποινή αξιοπιστίας

Ταξινομεί βάσει του `p95LatencyMs + (errorRate * 1000)`. Η ποινή ποσοστού σφαλμάτων διασφαλίζει ότι
οι αναξιόπιστοι providers κατατάσσονται χαμηλότερα, ακόμη και αν η ονομαστική καθυστέρησή τους είναι χαμηλή.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Πότε να χρησιμοποιείται**: Φόρτοι εργασίας ευαίσθητοι στην καθυστέρηση, όπως συνομιλία σε πραγματικό χρόνο, αυτόματη συμπλήρωση ή
διαδραστικοί βοηθοί προγραμματισμού.

**Ψευδώνυμα**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — συμμόρφωση με SLO καθυστέρησης/σφαλμάτων/κόστους

Βαθμολογεί κάθε υποψήφιο βάσει του πόσο καλά ικανοποιεί τη διαμορφωμένη πολιτική SLO:

| Παράγοντας              | Βαρύτητα | Τύπος                                                    |
| ----------------------- | -------- | -------------------------------------------------------- |
| Βαθμολογία καθυστέρησης | 35%      | `threshold / max(value, ε)`                              |
| Βαθμολογία σφαλμάτων    | 35%      | `threshold / max(value, ε)`                              |
| Βαθμολογία υγείας       | 15%      | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)        |
| Βαθμολογία κόστους      | 10%      | `threshold / max(value, ε)` ή αντίστροφη κανονικοποίηση  |
| Βαθμολογία σταθερότητας | 5%       | αντίστροφα κανονικοποιημένη τυπική απόκλιση καθυστέρησης |

Όταν `hardConstraints: true`, οι υποψήφιοι ταξινομούνται πρωτίστως βάσει της **βαθμολογίας παραβίασης**
(κατά πόσο υπερβαίνουν οποιοδήποτε SLO) και, στη συνέχεια, βάσει της σύνθετης βαθμολογίας. Διαφορετικά,
χρησιμοποιείται μόνο η σύνθετη βαθμολογία.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... βαθμολογεί κάθε υποψήφιο σε σχέση με την πολιτική: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**Πεδία SLA** (ορίζονται στη διαμόρφωση του combo):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Πότε να χρησιμοποιείται**: Φόρτοι εργασίας παραγωγής με αυστηρά όρια καθυστέρησης, ποσοστού σφαλμάτων ή κόστους.

**Ψευδώνυμα**: `sla-aware`, `sla`

---

#### 5. `lkgp` — πρώτα ο τελευταίος γνωστός καλός πάροχος

Δοκιμάζει πρώτα τον **τελευταίο γνωστό καλό πάροχο** (εφόσον έχει οριστεί) και, στη συνέχεια, χρησιμοποιεί ως εναλλακτική
τη στρατηγική `rules`. Χρήσιμο για τη διατήρηση της συνέπειας μιας συνεδρίας — ο ίδιος πάροχος διαχειρίζεται
τα επακόλουθα αιτήματα σε μια συνομιλία.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Εναλλακτική χρήση της στρατηγικής rules
    return getStrategy("rules").select(pool, context);
  }
}
```

**Πότε να χρησιμοποιείται**: Συνομιλίες πολλαπλών γύρων, όπου θέλετε ο ίδιος πάροχος να διαχειρίζεται
τα επακόλουθα αιτήματα (π.χ. για προσωρινή αποθήκευση, συνέχεια περιεχομένου ή συνέπεια τιμολόγησης).

**Ψευδώνυμο**: `lkgp` (χωρίς ψευδώνυμο)

---

#### 6. `nadir` — επιλογή μοντέλου με επίγνωση του prompt μέσω του Nadir

Κάθε παραπάνω στρατηγική κατατάσσει τους υποψηφίους βάσει των δικών της δεδομένων τηλεμετρίας· καμία δεν διαβάζει
το αίτημα. Η `nadir` στέλνει την τελευταία σειρά του χρήστη μαζί με τα αναγνωριστικά μοντέλων του pool στο
API αποφάσεων του [Nadir](https://getnadir.com) (`POST /v1/bucket`) και δρομολογεί το αίτημα στο μοντέλο
που επιλέγει το Nadir από αυτό το μενού (`simple` → το φθηνότερο κατάλληλο μοντέλο, `complex` → το
κορυφαίο μοντέλο). Η σύνδεση που εξυπηρετεί αυτό το μοντέλο εξακολουθεί να επιλέγεται από τη στρατηγική `rules`, ώστε τα όρια χρήσης,
η υγεία και το κόστος να συνεχίζουν να καθορίζουν ποιος λογαριασμός θα χρησιμοποιηθεί.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

Τα `OMNIROUTE_NADIR_API_KEY` και `OMNIROUTE_NADIR_BASE_URL` χρησιμοποιούνται ως εναλλακτικές μεταβλητές περιβάλλοντος για τις δύο
συμβολοσειρές. Το `baseUrl` απαιτείται μόνο για ένα αυτοφιλοξενούμενο Nadir (ένα τελικό `/v1` γίνεται αποδεκτό).
Οι κλήσεις χωρίς κλειδί καταλήγουν στο ανώνυμο επίπεδο του Nadir, στο οποίο εφαρμόζεται περιορισμός ρυθμού ανά IP. Με ένα κλειδί
([δημιουργήστε ένα](https://app.getnadir.com/dashboard/api-keys)), κάθε απόφαση
καταγράφεται στον πίνακα ελέγχου του Nadir. Πλήρης ρύθμιση και επαλήθευση:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/).

Τι αποστέλλεται εκτός συστήματος: το κείμενο του τελευταίου μηνύματος του χρήστη (οι πρώτοι 16k χαρακτήρες), τα αναγνωριστικά των υποψήφιων
μοντέλων και μια ετικέτα καναλιού `source: "omniroute"`. Δεν αποστέλλονται prompt συστήματος, ιστορικό, εργαλεία ή
κεφαλίδες.

Η συμπεριφορά σε περίπτωση αποτυχίας είναι fail-open: ένα χρονικό όριο (προεπιλογή 2000 ms), μια απόκριση εκτός 2xx, ένας μη προσβάσιμος
κεντρικός υπολογιστής, μια λανθασμένη απόκριση ή μια επιλογή εκτός του pool οδηγεί στην απόφαση της στρατηγικής `rules`
και ο λόγος αποκτά το πρόθεμα `NadirStrategy: fallback (…)`. Μετά από μια αποτυχημένη κλήση, η
στρατηγική παραλείπει το δίκτυο για 30 s, ώστε μια διακοπή λειτουργίας να κοστίζει ένα χρονικό όριο ανά 30 s αντί για
ένα ανά αίτημα. Τα συμβάντα δρομολόγησης αναφέρουν `strategy: "nadir"` μόνο όταν το Nadir έχει πράγματι λάβει
την απόφαση.

**Πότε να χρησιμοποιείται**: Κίνηση μεικτής δυσκολίας σε ένα pool που καλύπτει διαφορετικές βαθμίδες μοντέλων (ένα μικρό, ένα μεσαίο
και ένα κορυφαίο μοντέλο), όταν θέλετε να μειώσετε το κόστος της αποκλειστικής χρήσης του κορυφαίου μοντέλου.

**Ψευδώνυμο**: `nadir` (χωρίς ψευδώνυμο)

### Προσαρμοσμένες στρατηγικές δρομολογητή

Μπορείτε να καταχωρίσετε τη δική σας υλοποίηση του `RouterStrategy` μέσω του δημόσιου API:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Η προσαρμοσμένη λογική δρομολόγησής σας εδώ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

Στη συνέχεια, χρησιμοποιήστε την:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## Ανακεφαλαίωση Αυτόματων Παραλλαγών

Συμπεριλαμβανομένου του απλού `auto` (προεπιλογή) και των 6 τιμών `AutoVariant` που δηλώνονται στο `autoPrefix.ts`, υπάρχουν **7 επικαλέσιμα αναγνωριστικά μοντέλων**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(Το `AutoVariant` απαριθμεί 6 τιμές· η 7η επιλογή είναι «χωρίς παραλλαγή» — απλό `auto` — που χειρίζεται από το `parseAutoPrefix()` ως `variant: undefined`.)

## Πώς εντάσσονται τα tiers στο Auto-Combo

Η συνάρτηση βαθμολόγησης 16 παραγόντων (`open-sse/services/autoCombo/scoring.ts`) αντιμετωπίζει τη συμμετοχή σε tier ως δύο σήματα: `tierPriority` (0.0476) και `tierAffinity` (0.0476). Δείτε τον κανονικό [πίνακα παραγόντων βαθμολόγησης](#how-it-works-persisted-auto-combos) παραπάνω για το πλήρες σύνολο `DEFAULT_WEIGHTS` — οι παρακάμψεις ανά πακέτο (ship-fast/cost-saver/quality-first/
offline-friendly) παρατίθενται στον πίνακα «Προφίλ βαρών ανά πακέτο».

Το tier από μόνο του **δεν** επιβάλλει να προηγείται το Tier 1 — εάν η καθυστέρηση του Tier 1 είναι υψηλή ή η σχέση κόστους προς ποιότητα δεν είναι βέλτιστη, υπερισχύει το Tier 2. Για να επιβάλετε τη σειρά των tiers, χρησιμοποιήστε τη στρατηγική combo `priority` και ταξινομήστε τους παρόχους ανά tier.

Για να ευνοήσετε έντονα το Tier 1 (συνδρομή), αυξήστε το βάρος `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Δείτε το [`docs/guides/TIERS.md`](../guides/TIERS.md) για τους ορισμούς των tiers και την ταξινόμηση των παρόχων.

## Δοκιμές & Κάλυψη

### Ντετερμινιστικός πίνακας δρομολόγησης-απόφασης (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` αποδεικνύει τη δρομολόγηση** απόφαση** και των 21 δημόσιων στρατηγικών από άκρο σε άκρο μέσω του πραγματικού συνδυαστικού αγωγού με μια κοροϊδευμένη ανάντη. Η κάλυψη περιλαμβάνει:

- Και οι 21 στρατηγικές `ROUTING_STRATEGY_VALUES` (παραγγελία, στάθμιση, κόστος, πλαίσιο, σύντηξη,…).
- `quota-share` (εσωτερική) από άκρο σε άκρο: DRR δικαιοσύνη + κατά προτεραιότητα κορεσμού μέσω της πραγματικής ραφής `selectQuotaShareTarget` (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`).
- Καθολική κάλυψη `context-relay` -handoff σε κάθε μέτρηση στόχου.

Αυτή η σουίτα εκτελείται σε CI (εργασία `test:integration` ) με `--test-concurrency=1` και `--test-force-exit`, επομένως είναι ντετερμινιστική και δεν απαιτεί ζωντανά διαπιστευτήρια.

### Περιφραγμένος ζωντανός καπνός (NOT σε πραγματικούς παρόχους CI — )

| Εντολή                                 | Τι κάνει                                                                                  |
| :------------------------------------- | :---------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Πραγματική δρομολόγηση σε εξέλιξη με `RUN_COMBO_LIVE=1`; στιγμιότυπα ζωντανά OmniRoute DB |
| `npm run test:combo:live:vps`          | Κλήσεις HTTP σε ζωντανό διακομιστή OmniRoute (σύνολο `COMBO_LIVE_BASE_URL`)               |
| `npm run test:combo:live:vps:failover` | Το ίδιο, με σκόπιμα σενάρια failover                                                      |

Αυτές οι δοκιμές καπνού εξασκούν την πραγματική διαδρομή καλωδίων (combo → provider → completion). Αποκλείονται σκόπιμα από CI επειδή απαιτούν ζωντανά διαπιστευτήρια και πρόσβαση VPS.
