Το παρόν έγγραφο αποτελεί την επίσημη αναφορά για όλες τις πύλες ποιότητας CI στο OmniRoute.
Περιγράφει κάθε πύλη, τι επικυρώνει, σε ποια εργασία CI εκτελείται, αν χρησιμοποιεί
γραμμή βάσης ratchet ή πολιτική επιτυχίας/αποτυχίας, καθώς και αν εμποδίζει το build ή είναι συμβουλευτική.

Για μια σύντομη σύνοψη και την πολιτική της λίστας επιτρεπόμενων, ανατρέξτε στην ενότητα "Πύλες ποιότητας και ratchets"
στο `AGENTS.md`. Για την κριτική αξιολόγηση, την ταξινόμηση ωριμότητας και το ανεξάρτητο από εργαλεία
σχέδιο αναπαραγωγής του ίδιου συστήματος, ανατρέξτε στο
[Εγχειρίδιο Πυλών Ποιότητας](../ops/QUALITY_GATE_PLAYBOOK.md).

## Προφίλ απογραφής και εκτέλεσης πύλης

### Είσοδος υποψηφίου

Οι ροές εργασίας CI και Quality Gates εκπέμπουν η καθεμία μια σταθερή ετυμηγορία: `Gate / CI` και `Gate / Quality`. Η τροποποιημένη πολιτική εισδοχής τους απαριθμεί κάθε εργασία ανάντη ως απαιτούμενη ή συμβουλευτική. Μια απαιτούμενη εργασία που ισχύει πρέπει να είναι επιτυχής: τα αποτελέσματα που λείπουν, ακυρώνονται, παραλείπονται, εκκρεμούν και άγνωστα αποτελέσματα δεν μπορούν να δημιουργήσουν PASS. Μια έγκυρη ταξινόμηση μόνο για έγγραφα ή μόνο για κατάλογο μπορεί να καταστήσει μη εφαρμόσιμη μια λωρίδα κωδικών. ένα συνηθισμένο σχέδιο PR δεν είναι αποδεκτός υποψήφιος. Μια ετικέτα `hotfix` δεν παραιτείται από στοιχεία.

Και οι δύο ροές εργασίας καλύπτουν PRs σε κλάδους main/release, προωθήσεις σε `main`, μη αυτόματη αποστολή και συμβάντα συγχώνευσης. Push, αποστολή και συγχώνευση-ομαδοποίηση εκτελέστε την πλήρη επιλογή. Ένα αξιόπιστο προσχέδιο ουράς Mergify εκτελεί επίσης ισχύουσες εργασίες `full-code`/`full-code-e2e`. τα συνηθισμένα PRs παραλείψτε τα. Πριν από μια μη αυτόματη συγχώνευση, εκτελέστε μια πλήρη αποστολή στον ακριβή υποψήφιο. Οι ωθήσεις στο `release/**` δεν ξεκινούν αυτές τις ροές εργασίας. Το Release-Green παρατηρεί τη συγχωνευμένη βάση ξεχωριστά (`docs/ops/RUNNER_BOX.md` → Hosted lane). Τα forks και οι ομάδες συγχώνευσης χρησιμοποιούν φιλοξενούμενους δρομείς για εργασίες που διαφορετικά επιλέγουν αυτο-φιλοξενούμενους δρομείς. πρέπει να επαληθευτεί επαρκής χωρητικότητα φιλοξενίας πριν από την κυκλοφορία.

Ένα συνηθισμένο PR εκτελεί τη γρήγορη επιλογή. Οι λωρίδες `full-code` και `full-code-e2e` της πολιτικής αποδοχής (E2E, ενσωμάτωση, τεχνούργημα πακέτου, καπνός Electron, Bun SQLite, πελάτες οικοσυστήματος και πρωτοκόλλου) εκτελούνται μόνο σε πρόχειρο ουράς Mergify ή σε πλήρη εκτέλεση: `gh workflow run ci.yml --ref <branch>`.

Κάθε απόδειξη JSON προσδιορίζει την αποπληρωμή SHA, τη ροή εργασίας και την προσπάθεια. Το CLI απορρίπτει μια αναντιστοιχία checkout/event SHA. Οι δοκιμές ροής εργασιών συνδέουν τη συνδρομή πολιτικής στη λίστα `needs` της εργασίας ετυμηγορίας, έτσι ώστε μια νέα ή καταργημένη λωρίδα να μην μπορεί να εξαφανιστεί σιωπηλά. Οι αποδείξεις καλύπτουν τη δική τους ροή εργασίας, όχι τη δημοσίευση, την ανάπτυξη ή τα εσωτερικά στοιχεία ενός υπάρχοντος συμβουλευτικού σαρωτή. Η διενέργεια των εφαρμοστέων ελέγχων που απαιτούνται στους κανόνες του υποκαταστήματος είναι μια ξεχωριστή διοικητική αλλαγή. ο καθορισμός των εργασιών τους δεν προστατεύει από μόνος του έναν κλάδο.

`API Route Typecheck` είναι ένας ανεξάρτητος έλεγχος ροής εργασίας, εκτός τόσο των συγκεντρωτικών ετυμηγοριών όσο και του στατικού προφίλ του τοπικού πλήρους παρατηρητή. Επιθεωρήστε το αποτέλεσμά του ξεχωριστά για τον ακριβή υποψήφιο. `.github/workflows/api-route-typecheck.yml` εκτελείται σε PRs σε `main` ή `release/**`, ωθεί σε συμβάντα είτε σε οικογένεια υποκαταστημάτων είτε σε μη αυτόματη αποστολή και σε συμβάντα `merge_group` τύπου `checks_requested`. Δεν έχει φίλτρο διαδρομής. Ομάδες συγχώνευσης ελέγξτε `merge_group.head_sha`; άλλες εκδηλώσεις ρίξτε μια ματιά στο `github.sha`. Όλα τα συμβάντα χρησιμοποιούν τις ίδιες δοκιμές διαγνωστικής πύλης και μονάδας πύλης API. Οι επαναστόχοι βάσης PR ζητούν νέο έλεγχο. Οι επεξεργασίες body/title χρησιμοποιούν το όνομα μόνο για παρατήρηση `Admission not requested / API Route Typecheck` και δεν μπορούν να αντικαταστήσουν τον έλεγχο αποδοχής.

### Διατηρούνται αποδεικτικά στοιχεία στον μειωτήρα αποδοχής

`scripts/quality/validate-release-acceptance.mjs` μειώνει ένα παρεχόμενο σχέδιο και τις εκδηλώσεις του. δεν αποδεικνύει ότι το σχέδιο καλύπτει ολόκληρο τον αγωγό απελευθέρωσης. Οι αναφορές του ορίζουν ρητά `releaseAcceptance: false`, ακόμη και όταν αυτό το σχέδιο είναι `VERIFIED`. Η ροή εργασιών `release-acceptance.yml` εξακολουθεί να χρησιμοποιεί σκιώδεις συσκευές, όχι πραγματικές αποδείξεις κατασκευής, πακέτου, εκκίνησης ή προώθησης.

Το CLI απαιτεί από `--evidence-root` να επαληθεύει τα διατηρούμενα αποδεικτικά στοιχεία. Τα αρχεία επιλύονται ως `<evidence-root>/<artifact_id>/<member>` και κατακερματίζονται ως SHA-256. Μια εγγραφή PASS χωρίς στοιχεία, ένα αρχείο που λείπει ή έχει αλλάξει, μια μη ασφαλής διαδρομή ή ένας συμβολικός σύνδεσμος εμποδίζει την επαλήθευση. Τα αρχεία που λείπουν δεν ισοδυναμούν με άδεια επιτυχημένα αρχεία καταγραφής. Οι υπάρχοντες έλεγχοι SHA/run/attempt παραμένουν ανεξάρτητοι: τα αντίστοιχα byte δεν μπορούν να διασώσουν μια μπαγιάτικη απόδειξη. Η ακεραιότητα του αρχείου δεν αποτελεί απόδειξη αυθεντικότητας εκτέλεσης ή προώθησης τεχνουργημάτων.

### DAST καταναλώνει την επαληθευμένη έκδοση CI

Η απαιτούμενη εργασία `dast-smoke` CI καλεί `.github/workflows/dast-smoke.yml` μετά `build`. Ακολουθεί την ίδια επιλογή code/draft με το build, συμπεριλαμβανομένων των υποστηριζόμενων fork PRs, PRs απελευθέρωσης-στόχου και των ομάδων συγχώνευσης. Μια εργασία DAST που λείπει, απέτυχε, ακυρώθηκε ή παραλείφθηκε απροσδόκητα αποκλείει `Gate / CI`. Η επαναχρησιμοποιήσιμη ροή εργασίας δεν έχει ανεξάρτητη σκανδάλη PR/dispatch. Η μη αυτόματη επικύρωση χρησιμοποιεί την αποστολή του CI, ώστε η κατασκευή και ο καταναλωτής να παραμένουν σε μία εκτέλεση.

`scripts/ci/next-build-provenance.mjs` σφραγίζει το πλήρες Επόμενο τεχνούργημα με την ανασκόπηση πίσσας, repository/event/run, την προσπάθεια παραγωγού, head/base/checkout/tree, τις ταυτότητες ροής εργασιών, το αρχείο κλειδώματος, το ακριβές Node version/ABI, την πλατφόρμα και το bundler. DAST επιλέγει το αμετάβλητο τεχνούργημα ID από `needs.build.outputs`, απαιτεί επαλήθευση σύνοψης λήψης και κατακερματίζει ανεξάρτητα το ZIP έναντι της σύνοψης του παραγωγού πριν εξαγάγει τα δύο επιτρεπόμενα μέλη του μέσω `scripts/ci/unpack-ci-build.py`. Το αρχείο δήλωσης και πίσσας πρέπει επίσης να ταιριάζουν με τα αποτελέσματα ανεξάρτητου παραγωγού προτού εξαχθεί το δέντρο Επόμενο. Δεν αναζητά ποτέ την τελευταία επιτυχημένη κατασκευή υποκαταστήματος. Μια μερική επανάληψη μπορεί να επαναχρησιμοποιήσει την ίδια προσπάθεια παραγωγού όταν το ID και όλες οι είσοδοι εξακολουθούν να ταιριάζουν. η απόδειξη καταγράφει και τις δύο προσπάθειες.

Ο καταναλωτής παραμένει σε έναν φιλοξενούμενο Linux runner με άδεια αποθήκευσης μόνο για ανάγνωση και χωρίς μυστικά αποθετηρίου. Εγκαθιστά την ακριβή έκδοση Node του παραγωγού και στη συνέχεια συναρμολογεί το CLI με `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1`. `scripts/build/standaloneInput.mjs` απορρίπτει έναν αυτόνομο διακομιστή που λείπει πριν από οποιαδήποτε εναλλακτική έκδοση. Οι κανονικές τοπικές εκδόσεις CLI διατηρούν το υπάρχον εναλλακτικό τους. Η ετοιμότητα διακομιστή, το Schemathesis και το promptfoo πρέπει όλα να επιτύχουν εντός του αμετάβλητου ορίου εργασίας των 25 λεπτών. Μια απόδειξη προέλευσης αποδεικνύει την ταυτότητα εισόδου και τα byte, όχι μια επιτυχημένη σάρωση DAST. Η λήξη του τεχνουργήματος, η διακοπή λειτουργίας ή ο αποτυχημένος σαρωτής παραμένει ελλιπής ή αποτυχημένη απόδειξη. δεν μπορεί να γίνει PASS μέσω συμβουλευτικού περιτυλίγματος.

### Δυνατότητα εκτέλεσης UI

CI εκτελεί το πλήρες απόθεμα UI ως τέσσερα θραύσματα μήτρας `test-vitest`, το καθένα με το πολύ δύο εργαζόμενους ανά θραύσμα και την υπάρχουσα προθεσμία εργασίας 15 λεπτών. Το πρώτο θραύσμα εκτελεί επίσης τη σουίτα MCP/autoCombo Vitest. Το απαιτούμενο αποτέλεσμα εργασίας καλύπτει κάθε σκέλος μήτρας. Η αποτυχία ή η ακύρωση ενός θραύσματος δεν μπορεί να θεμελιώσει την αποδοχή του υποψηφίου.

Ο νυχτερινός παρατηρητής διατηρεί μια ξεχωριστή απόδειξη ακριβούς υποψηφίου για κάθε θραύσμα UI, συμπεριλαμβανομένης της εκτέλεσης MCP στην πρώτη απόδειξη. Απαιτούνται και οι τέσσερις αποδείξεις, τα αρχεία καταγραφής και οι αντίστοιχες ταυτότητες εκτέλεσης. Η τοπική `npm run test:vitest:ui` εξακολουθεί να επιλέγει την πλήρη σουίτα. μια εκτέλεση `--shard` είναι μόνο μερική απόδειξη.

### Συλλογή κάλυψης μονάδας

Τα δώδεκα θραύσματα μονάδας συλλέγουν κάλυψη V8 κατά τη διάρκεια της υπάρχουσας εκτέλεσης της δοκιμής τους. Ένα επιτυχημένο θραύσμα εκτελεί `scripts/ci/compact-v8-coverage.mjs` για να συμπιέσει τα αρχικά αρχεία χωρίς να δημιουργήσει μια ενδιάμεση αναφορά Istanbul. Η τελική εργασία Κάλυψη επαληθεύει και τις δώδεκα εκδηλώσεις έναντι του υποψήφιου SHA, χρόνου εκτέλεσης, ρίζας πηγής και κατακερματισμών δεδομένων και, στη συνέχεια, εκτελεί τους ανταποκριτές του c8 και τα υπάρχοντα όρια κάλυψης. Οι είσοδοι διατηρούν την καθολική σειρά ονομάτων αρχείου του c8. Η προ-συγχώνευση ανά θραύσμα δεν είναι ασφαλής για μικτή κάλυψη function/block. Τα θραύσματα που λείπουν, έχουν κακή μορφή ή είναι ασύμβατα δεν γίνονται δεκτά. Τα αποτυχημένα θραύσματα δοκιμής διατηρούν την ακατέργαστη διαγνωστική κάλυψη χωριστά. δεν μπορεί να εισέλθει στην τελική συγχώνευση.

### Αποδείξεις προόδου εκτέλεσης μονάδας

Η κοινή εντολή `test:unit:ci:shard` καταγράφει τις φάσεις `primary`, `dashboard` και `serial` μέσω `scripts/ci/unit-progress-reporter.mjs`. Η κανονική αναφορά δοκιμής παραμένει διαθέσιμη. Μια ξεχωριστή απόδειξη μόνο για μεταδεδομένα καταγράφει την έναρξη και την ολοκλήρωση κάθε αρχείου και ένας καρδιακός παλμός 30 δευτερολέπτων αναφέρει τα αρχεία που είναι ακόμα ενεργά και τον χρόνο που έχει παρέλθει. Καταγράφει μόνο τα επιτρεπόμενα μεταδεδομένα εκτέλεσης. Οι περιγραφές δοκιμής, τα αποτελέσματα, τα σώματα σφαλμάτων και το πλήρες περιβάλλον δεν είναι σειριακά.

CI διατηρεί τα αρχεία JSONL ως `unit-progress-ci-<run>-<attempt>-<shard>`. Ένα χρονικό όριο εργασίας μπορεί να αποτρέψει την μεταγενέστερη μεταφόρτωση. οι καρδιακοί παλμοί που έχουν ήδη εκπεμπθεί παραμένουν διαγνωστικά στοιχεία. Οι καρδιακοί παλμοί που λείπουν μπορεί επίσης να αντικατοπτρίζουν μια μπλοκαρισμένη ή τερματισμένη διαδικασία δρομέα. Αυτές οι αποδείξεις διατηρούν την υπάρχουσα επιλογή δοκιμής, τη συγχρονικότητα, τις προθεσμίες και την κατάσταση εξόδου. δεν είναι ετυμηγορίες αποδοχής υποψηφίων.

### Ουρά συγχώνευσης

Η ετικέτα `queue` στέλνει ένα PR στην ουρά Mergify (`.mergify.yml`). Το Mergify ανοίγει ένα πρόχειρο PR σε έναν κλάδο `mergify/merge-queue/`, CI εκτελεί την πλήρη επιλογή εκεί και το αρχικό PR συγχωνεύεται όταν περάσουν `Gate / CI`, `Gate / Quality` και `Merge integrity (changelog + generated skills)`.

Το Mergify γράφει τη σύνοψη της ουράς στην περιγραφή του προχείρου. Τα συμβάντα Body/title-only `pull_request` `edited` χρησιμοποιούν μια ομάδα ταυτόχρονης εκτέλεσης και δεν επαναλαμβάνουν την ταξινόμηση, τους πίνακες δοκιμής, την ακεραιότητα συγχώνευσης ή την ετυμηγορία αποδοχής. Τα ονόματα ελέγχου μόνο για παρατήρηση δεν μπορούν να αντικαταστήσουν `Gate / CI` ή `Gate / Quality`. Μια τροποποίηση που αλλάζει τη βάση προορισμού ζητά νέα επικύρωση υποψηφίου.

Μετά από μια αναμονή, μια ώθηση δεν επαναφέρει πάντα το PR. Σχολιάστε `@mergifyio queue`.

### Απόθεμα στατικής σάρωσης

Το εκδομένο απόθεμα npm-alias και η συνδρομή στατικής σάρωσης ζωντανά στο `config/quality/gate-manifest.json`. Εκτελέστε `npm run check:gate-manifest` για να επικυρώσετε ονόματα σεναρίων και ακριβείς εντολές έναντι `package.json`. οι προσθήκες, οι αφαιρέσεις και η μετατόπιση εντολών αποτυγχάνουν τόσο στο τοπικό άγκιστρο όσο και στις εργασίες αλλαγής-ταξινόμησης στο CI. Ένα ψευδώνυμο δεν είναι εργασία ροής εργασίας, παράδειγμα μήτρας ή δοκιμαστική περίπτωση: αυτές οι μετρήσεις δεν πρέπει να παρουσιάζονται ως εναλλάξιμες.

Χρησιμοποιήστε `npm run quality:scan -- --list` ή `npm run quality:scan:fast -- --list` για να επιθεωρήσετε τα επιλεγμένα ψευδώνυμα χωρίς να τα εκτελέσετε. Ο δρομέας καλεί το σημείο εισόδου npm, επομένως ο χρόνος εκτέλεσης του (συμπεριλαμβανομένου Bun όπου έχει ρυθμιστεί) διατηρείται. Το μανιφέστο καταγράφει ψευδώνυμα εκτός αυτών των προφίλ όπως καλούνται χωριστά και οι εντολές συντήρησης απαγορεύονται σε προφίλ σάρωσης μόνο για ανάγνωση.

Αυτά τα προφίλ καλύπτουν μόνο τη στατική σάρωση. Δεν πιστοποιούν τις δοκιμές προϊόντων, την κάλυψη, τη συσκευασία, τους εξωτερικούς ελέγχους ή την πλήρη αποδοχή του υποψηφίου. Η εισαγωγή ροής εργασιών χρησιμοποιεί τα συνδεδεμένα `config/quality/admission-policy.json` και `scripts/quality/admission-verdict.mjs`. Τα προφίλ παρατηρητών απελευθέρωσης παραμένουν ξεχωριστά. επιθεωρούν ανεξάρτητα τις ισχύουσες επιταγές και αποδείξεις τους. Οι πλήρεις στατικές εντολές του παρατηρητή δηλώνονται στο `config/quality/release-green-static-profile.json`, συμπεριλαμβανομένου `audit:deps`, της επιλογής δοκιμής μετάλλαξης και των ελέγχων μετάφρασης. Ο φορτωτής επικυρώνει εντολές npm έναντι package.json και μοντελοποιημένων δηλώσεων CI/Quality. απορρίπτει το drift αντί να εκτελεί κουπόνια φλοιού ως ορίσματα. Η απαιτούμενη έξοδος SKIP/INCOMPLETE σαρωτή δεν μπορεί να καθορίσει PASS. Το προφίλ καταγράφει τις εξωτερικές του εξαιρέσεις και δεν αντικαθιστά την φιλοξενούμενη κάλυψη, τους πίνακες δοκιμών, το πακέτο ή τα στοιχεία ανάπτυξης. Το απόθεμα πεζογραφίας παρακάτω αποτελεί αναφορά, όχι απόδειξη ότι όντως έτρεξε μια πύλη.

Τα σενάρια ζουν κάτω από `scripts/check/` (policy gates) και `scripts/quality/` (καστάνια). Η πηγή αλήθειας του CI είναι `.github/workflows/ci.yml`.

### Υγεία τεκμηρίωσης δημοσιευμένης βάσης

`.github/workflows/i18n-base-health.yml` παρατηρεί την υγεία της τεκμηρίωσης μετά από επιλεγμένες ωθήσεις σε `main` και `release/v*` και κατά τη μη αυτόματη αποστολή. Τα φίλτρα του καλύπτουν την τεκμηρίωση, το root Markdown, `llm.txt`, τη μετάφραση state/configuration και τα σχετικά εργαλεία i18n. Η μεμονωμένη εργασία `Published base documentation health` χρησιμοποιεί φιλοξενούμενο Ubuntu και προθεσμία πέντε λεπτών. Εκτελεί επικύρωση μόνο για ανάγνωση και γράφει μια διαγνωστική απόδειξη χωρίς εγκατάσταση εξάρτησης, μετάφραση ή έγκριση κατάστασης.

`scripts/i18n/check-base-health.mjs` απαιτεί μηδενικές ασυνέπειες προέλευσης-κατακερματισμού, στόχου που λείπει, κατακερματισμού στόχου, παλαιωμένης μετάφρασης και προσωρινής μνήμης ενοτήτων. Επικυρώνει επίσης το τρέχον εύρος του πυρήνα document/locale και την καταγεγραμμένη προέλευσή του. Μη έγκυρο περιβάλλον, ατελής κάλυψη ή διακοπτόμενος ελεγκτής παράγει `INCOMPLETE`. Το επιβεβαιωμένο drift παράγει `FAIL`. Και οι δύο επιστρέφουν μια κατάσταση αποτυχίας εξόδου. Η απόδειξη δεσμεύεται για την πληρωμή SHA, τη ροή εργασιών, την εκτέλεση και την προσπάθεια και διατηρείται ως `i18n-base-health-<sha>-<run>-<attempt>`.

Αυτή είναι μια ανεξάρτητη παρατήρηση της δημοσιευμένης βάσης. Δεν προσθέτει ένα PR ή ένα συμβάν ομάδας συγχώνευσης, έναν απαιτούμενο έλεγχο PR, ένα ψευδώνυμο npm ή ένα μέλος προφίλ στατικής σάρωσης. Το υποκείμενο πούλι μπλοκάρει επίσης και τις πέντε κατηγορίες σε απόλυτη λειτουργία. Η συνηθισμένη προετοιμασία PR παραμένει ξεχωριστή από την εισαγωγή. Μια επιτυχημένη μεταφόρτωση δεν μπορεί να μετατρέψει ένα αποτυχημένο αποτέλεσμα υγείας σε PASS.

Ένα συνηθισμένο PR χρησιμοποιεί `--preflight` με μια αναφορά βάσης που δημιουργείται από `--baseline-evidence`. Μπορεί να αφήσει μια αγγλική πηγή σε εκκρεμότητα μόνο όταν η πλήρης εγγραφή μετάφρασης και τα πραγματικά byte-στόχοι παραμένουν αμετάβλητα από αυτήν ακριβώς τη βάση. Οι νέοι στόχοι ή οι ασυνέπειες της προσωρινής μνήμης ενότητας εξακολουθούν να μπλοκάρουν και τα ελλιπή στοιχεία δεν μπορούν να επιτρέψουν την προετοιμασία. Η αναφορά εκθέτει `preparationPending` και `mergeReady` ξεχωριστά: η επιτυχής προετοιμασία δεν καθιστά τις εκκρεμείς μεταφράσεις έτοιμες για συγχώνευση. Ανανεώστε τους επηρεασμένους καθρέφτες στον σύνθετο υποψήφιο πριν από την εισαγωγή. Η αξιόπιστη υποψήφια ουρά Mergify, `merge_group`, οι ωθήσεις διακλάδωσης και οι μη αυτόματες εκτελέσεις CI χρησιμοποιούν τον απόλυτο έλεγχο, χωρίς `--warn` ή συγχώρεση κληρονομικής αποτυχίας. Τα κατακερματισμένα στόχων που λείπουν και το εύρος μειώνεται από τα διαγραμμένα εγγεγραμμένα βασικά αρχεία δεν μπορούν να παράγουν μια επιτυχημένη απόλυτη ετυμηγορία.

### Απελευθερώστε τη γρήγορη διαδρομή PR (`quality.yml`)

`.github/workflows/quality.yml` συμπληρώνει CI στο main/release PRs, ωθεί σε `main`, αποστέλλει και συγχωνεύει ομάδες. PRs χρησιμοποιεί γρήγορους ελέγχους με φιλτράρισμα διαδρομής. Η μόνιμα απενεργοποιημένη διπλότυπη έκδοση καταργήθηκε. οι πραγματικοί έλεγχοι build/package/boot παραμένουν στο CI. Η σουίτα μονάδας και το βιτέστ τρέχουν μόνο σε CI (`Unit Tests (N/12)` και `Vitest`).

#### Αναφορά δοκιμών ξεχασμένων αδελφών

`npm run check:forgotten-sibling-tests` εκτελείται ως συμβουλευτικό βήμα του `Fast Quality Gates` και επαναχρησιμοποιεί τον επιλύτη εισαγωγής πίσω από τον χάρτη δοκιμής αντίκτυπου. Για κάθε αλλαγμένη μονάδα παραγωγής, αναφέρει ντετερμινιστικές αλυσίδες `changed module/symbol -> static consumer -> candidate sibling test` όταν η υποψήφια δοκιμή απουσιάζει από τη διαφορά αιτήματος έλξης. Η σύνοψη Markdown και το αποτέλεσμα JSON διατηρούνται ως το τεχνούργημα ροής εργασίας `forgotten-sibling-tests` για βαθμονόμηση πριν από οποιαδήποτε κυκλοφορία αποκλεισμού.

Οι επανεξαγωγές βαρελιού και οι δυναμικές εισαγωγές αποτελούν μόνο διαγνωστικά ανάλυσης. δεν δημιουργούν ποτέ ένα αποκλειστικό εύρημα. Εξαιρέσεις που εξετάστηκαν ζωντανά στο `config/quality/forgotten-sibling-allowlist.json`. Κάθε καταχώριση πρέπει να ονομάζει το τεστ καταναλωτή και υποψηφίου, να δίνει μια συγκεκριμένη αιτιολογία και να συνδέει ένα ζήτημα GitHub ή αίτημα έλξης. Οι καταχωρήσεις με κακή μορφή αποτυγχάνουν να κλείσουν. Οι εξαιρέσεις δεν μπορούν να καταστείλουν μια διαγραμμένη δοκιμασία υποψηφίου ή μια διαφορά που προσθέτει `.skip`/`.todo`. Η αποδυνάμωση του ισχυρισμού και άλλες καλύψεις παραμένουν στην ιδιοκτησία της πύλης `check:test-masking` που μπλοκάρει ανεξάρτητα.

#### Δύο προγράμματα ελέγχου τύπου απαντούν διαφορετικά

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) και `check:build-typecheck` μεταγλωττίζουν διαφορετικά προγράμματα κάτω από διαφορετικές επιλογές και το ίδιο αρχείο μπορεί να είναι καθαρό στο ένα και γεμάτο λάθη στο άλλο.

`tsconfig.build.json` θέτει `"strict": false`, άρα `noImplicitAny` είναι απενεργοποιημένο. Η βασική διαμόρφωση συντάσσει μια επιμελημένη λίστα επιτρεπόμενων αρχείων 27 με αυστηρότερες επιλογές και ακολουθεί το γράφημα εισαγωγής κάθε καταχώρισης, έτσι ώστε τα αρχεία που δεν εμφανίζονται ποτέ στο πρόγραμμα δημιουργίας εξακολουθούν να ελέγχονται εκεί.

Η συνέπεια είναι σημαντική όταν κρίνουμε εάν ένα αρχείο πληκτρολογείται:**μηδενικά διαγνωστικά στο `check:build-typecheck` δεν σημαίνει μηδέν** . Η απογύμνωση `@ts-nocheck` από 26 αρχεία έδειξε ότι 23 από αυτά ήταν καθαρά στο πρόγραμμα δημιουργίας. Δεκαέξι από αυτά εμφανίστηκαν περίπου 120 σιωπηρά - τυχόν σφάλματα στο αυστηρό. Ελέγξτε και τα δύο πριν καλέσετε ένα αρχείο καθαρό.

#### `check-ui-value-drift` — μπαγιάτικη-μεταφραστική πύλη

Πιάνει τη μία παλινδρόμηση i18n που οι άλλες πύλες δομικά δεν μπορούν να δουν: μια αγγλική τιμή ξαναγράφεται και οι μεταφράσεις που προέρχονται από τα _προηγούμενα_ αγγλικά παραμένουν πίσω, έτσι οι μη Άγγλοι χρήστες συνεχίζουν να διαβάζουν αντίγραφο με σιγουριά, τώρα λάθος.

Αυτό στάλθηκε πραγματικά. `oauthModal.googleOAuthWarning` γράφτηκε ξανά όταν προσγειώθηκε ο βοηθός σύνδεσης Antigravity (#5203).**39 από 43 τοποθεσίες** διατήρησε κείμενο λέγοντας στους χειριστές να "αντιγράψουν το πλήρες URL και να το επικολλήσουν παρακάτω" — μια ροή που δεν μπορεί να ολοκληρωθεί για αυτόν τον πάροχο. Πέρασε απαρατήρητο μέχρι #8463 γιατί:

- `sync-ui-keys` συμπληρώνει μόνο κλειδιά που είναι **απών** , ποτέ αυτά που είναι **μπαγιάτικος** ;
- `check-ui-keys-coverage` μετράει το κλειδί _παρουσία_, επομένως μια μπαγιάτικη μετάφραση βαθμολογείται ως καλυμμένη.
- `check-translation-drift` παρακολουθεί την τεκμηρίωση `docs/i18n/<locale>/**.md` αντικατοπτρίζει — και δεν διαβάζει ποτέ `src/i18n/messages/*.json`. Αποκλεισμός εργασίας `docs-sync-strict` από τον επανασυγχρονισμό 2026-09: επεξεργαστείτε ένα βασικό έγγραφο → `npm run i18n:run -- --files=<doc>` (σε επίπεδο ενότητας, φθηνό).

**Με επίγνωση των διαφορών, όχι με βάση τη γραμμή βάσης.** Συγκρίνει `en.json` στη βάση συγχώνευσης με το δέντρο εργασίας. Για κάθε κλειδί του οποίου η τιμή στα αγγλικά άλλαξε, κάθε τοπική γλώσσα που εξακολουθεί να διατηρεί μια ανέγγιχτη μετάφραση είναι μπαγιάτικη. Αυτό σκόπιμα **παγώνει το προϋπάρχον χρέος** Μια διαφορά — δεν μπορεί να αποκαλύψει από ποια παλιά αγγλικά προήλθε μια μακροχρόνια μετάφραση, επομένως η πύλη κρίνει μόνο τι αγγίζει η τρέχουσα αλλαγή. Η εναλλακτική λύση (μια βασική γραμμή κατακερματισμού ανά κλειδί) θα κόστιζε ένα αρχείο που δημιουργείται ~ 600 KB, 3 × τη μεγαλύτερη υπάρχουσα γραμμή βάσης, που αναδεύεται σε κάθε i18n PR.

Δύο τρόποι για να το ικανοποιήσεις:

1. ενημερώστε τις επηρεαζόμενες μεταφράσεις ή
2. ορίστε τα σε `__MISSING__:<new english>` — το χρόνο εκτέλεσης και, στη συνέχεια, εξυπηρετεί τα διορθωμένα αγγλικά (`src/i18n/request.ts::deepMergeFallback`, #7258) και τις βασικές ουρές για μετάφραση.

Αν η χορδή είναι **έννοια** άλλαξε, προτιμώ **μετονομασία του κλειδιού** : ένα νέο κλειδί δεν μπορεί να κληρονομήσει μια παλιά μετάφραση. Αυτό είναι το μοτίβο που χρησιμοποιεί #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Η μετατόπιση αξίας και οι πύλες νέων κλειδιών μοιράζονται μια αμετάβλητη σύγκριση από `scripts/i18n/resolve-ui-diff-base.mjs`. Η ροή εργασίας μεταβιβάζει την ίδια βάση, βάση-άκρο και υποψήφιο SHAs και στους δύο ελέγχους. Οι εκτελέσεις PR/base-retarget, push και συγχώνευσης ομάδας χρησιμοποιούν το πλαίσιο συμβάντων τους. Η αποστολή ενός υποψηφίου κλάδου απαιτεί το ακριβές ανοιχτό PR ή τη ρητή είσοδο `i18n_base_sha`. Η αποστολή ή η προγραμματισμένη παρατήρηση του `main` ή `release/vX.Y.Z` χωρίς αυτήν την είσοδο συγκρίνει την τελευταία δέσμευση με τον πρώτο γονέα. δεν είναι έλεγχος όλων των κληρονομικών χρεών μετάφρασης. Η τοπική επίκληση απαιτεί μια ρητή βάση σύγκρισης, για παράδειγμα την παραπάνω εντολή `BASE_REF`.

Λείπει ή διφορούμενο πλαίσιο σύγκρισης, ένας μη αναγνώσιμος ή μη έγκυρος απαιτούμενος κατάλογος και ένας αλλαγμένος υποψήφιος παράγει `INCOMPLETE` με κωδικό εξόδου **2** , συμπεριλαμβανομένης της λειτουργίας προειδοποίησης. Η ανάγνωση του καταλόγου χρησιμοποιεί `scripts/i18n/read-ui-catalog.mjs`. οι αποτυχίες ανάγνωσης δεν αντικαθίστανται με κενά αντικείμενα. Ούτε μια μη διαθέσιμη βάση ούτε η ελλιπής είσοδος καθιερώνουν PASS.

**Εργαλεία**

- `npm run quality:relax-baselines -- --pct 20 --note velocity_YYYY_MM_DD [--dry-run]` — η
  εφάπαξ χαλάρωση (`scripts/quality/relax-baselines.mjs`)· αρνείται να εκτελεστεί δύο φορές με την
  ίδια σημείωση.
- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` —
  μετρά κάθε αριθμητική πύλη με τον ίδιο τρόπο που το κάνει το CI και εμφανίζει το εναπομένον περιθώριο ανά πύλη
  (`scripts/quality/baseline-headroom.mjs`). Η νυχτερινή εργασία `baseline-headroom` δημοσιεύει
  τον πίνακα στη σύνοψη εκτέλεσης της ροής εργασίας και μεταφορτώνει την αναφορά JSON/Markdown ως
  `baseline-headroom-<run_id>`, η οποία διατηρείται για 90 ημέρες. Οι γραμμές προειδοποίησης και κρίσιμης κατάστασης επισημαίνουν πύλες
  που βρίσκονται εντός του 10% του ανώτατου ορίου τους ή το έχουν ήδη υπερβεί. Εξετάζετε αυτές τις αναφορές ως έγκαιρη προειδοποίηση
  για την κατανάλωση των προϋπολογισμών· ελέγχετε τις σημειώσεις `_rebaseline_*` της προβληματικής πύλης. Η εργασία δεν
  δημιουργεί ούτε ενημερώνει πλέον μόνιμο ζήτημα· το #12149 διατηρεί το παλαιότερο ιστορικό αναφορών.

**Λειτουργία νέου κώδικα (Clean-as-You-Code) — από 2026-08-30, μόνο για τη γρήγορη διαδρομή PR**

Σε συμβάντα `pull_request`, το `quality.yml` μεταβιβάζει το `--base-ref <PR base SHA>` στα `check:file-size`,
`check:complexity-ratchets` και `check:dead-code`. Για τα `check:complexity-ratchets` και
`check:dead-code`, η πύλη συγκρίνει το HEAD με τη βάση συγχώνευσης **περιορισμένη στα αρχεία που
τροποποίησε το PR** (`scripts/check/newCodeMode.mjs`: η βάση συγχώνευσης υλοποιείται σε ένα προσωρινό
`git worktree`, τα ESLint/knip εκτελούνται εκεί και στο HEAD και υπολογίζονται οι διαφορές των καταμετρήσεων ανά αρχείο):

- **αποκλεισμός** — το PR πρόσθεσε παραβιάσεις κυκλωματικής/γνωστικής πολυπλοκότητας ή ανενεργές εξαγωγές στα αρχεία που τροποποίησε
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` στο αρχείο καταγραφής)·
- **συμβουλευτικό** — το συνολικό καθολικό μέγεθος έναντι της παγωμένης γραμμής βάσης. Η κληρονομημένη απόκλιση δεν επισημαίνει ποτέ με κόκκινο ένα
  αθώο PR· η απόκλιση παρακολουθείται για διόρθωση κατά τη συμφωνία της έκδοσης και εποπτεύεται από την
  εργασία headroom.

Το `check:file-size` χρησιμοποιεί την αναφορά βάσης με τους δικούς του όρους (`scripts/check/check-file-size.mjs`, #8522):
ελέγχει κάθε αρχείο πηγαίου κώδικα και δοκιμών στο δέντρο, διαβάζει το πλήθος γραμμών του καθενός στη βάση του PR
με το `git show` και αποτυγχάνει ένα αρχείο μόνο όταν αυτό αυξάνεται πέρα από το μεγαλύτερο μεταξύ του ανώτατου ορίου της γραμμής βάσης του
(`frozen` / `testFrozen` ή `cap` / `testCap` για αρχείο εκτός της γραμμής βάσης) και του μεγέθους βάσης του.
Επομένως, ένα αρχείο που είχε ήδη αποκλίνει στη βάση δεν προκαλεί ποτέ αποτυχία σε ένα άσχετο PR.

Το `check:boundary:ratchet` εφαρμόζει τον ίδιο κανόνα στον μοναδικό αριθμό του
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): στα συμβάντα PR, τόσο τα γρήγορα gates του
`quality.yml` όσο και το lint job του `ci.yml` περνούν το βασικό SHA του PR, το βασικό commit
μετριέται από export μέσω `git archive` και το PR αποτυγχάνει μόνο όταν το πλήθος των ακμών
`open-sse → src` υπερβαίνει τη μεγαλύτερη τιμή μεταξύ του `metrics.boundaryOpenSseToSrc` και του πλήθους
στη βάση. Η απόκλιση της βάσης πάνω από το ανώτατο όριο αναφέρεται (`base drift herdado`), αλλά δεν προκαλεί
ποτέ την αποτυχία ενός αθώου PR· το push → main διατηρεί το απόλυτο ανώτατο όριο, ενώ ένα βασικό SHA που δεν
μπορεί να επιλυθεί επιστρέφει σε αυτό με μια προειδοποίηση.

Οι εκτελέσεις `workflow_dispatch`, η σάρωση release-green και το νυχτερινό job headroom δεν έχουν βάση PR
και διατηρούν την απόλυτη (καθολική) σύγκριση. Η κάλυψη, η επανάληψη κώδικα και η κάλυψη τύπων παραμένουν προς
το παρόν καθολικές (τα εργαλεία τους δεν παράγουν οικονομικά diff ανά αρχείο) — είναι υποψήφιες για την ίδια αντιμετώπιση.

**Κλείσιμο της φάσης στην v4.0 (LTS = αυστηρότερο από πριν, όχι «επιστροφή στην κανονικότητα»)**

1. Στο καθαρό tip του `release/v4.0.0`: `npm run quality:headroom --json` για καταγραφή και, στη συνέχεια,
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, καθώς και το
   `--update` κάθε gate ελέγχου τύπων — κάθε baseline μειώνεται στη μετρημένη τιμή.
2. Διαγράψτε το `_policy` από το `quality-baseline.json` (ενεργοποιεί ξανά το `--require-tighten` και το νυχτερινό
   banking) και επαναφέρετε το `THRESHOLD = 36` (ή υψηλότερο) στο `check-openapi-coverage.mjs`.
3. Αυστηροποιήστε τα όρια πέρα από τις μετρημένες τιμές όπου η αρθρωτή αναδιοργάνωση απέδωσε: επαναφέρετε το `cap`
   μεγέθους αρχείου στα 1000 (ή 800), αυξήστε τα κατώτατα όρια κάλυψης κατά 5 και ορίστε τα νεκρά exports σε 0
   για τα πακέτα που αναδιοργανώθηκαν αρθρωτά.

## Βασική γραμμή καστάνιας (`quality-baseline.json`)

Ο μηχανισμός καστάνιας (`scripts/quality/check-quality-ratchet.mjs`) διαβάζει το `quality-baseline.json`
και το συγκρίνει με το `quality-metrics.json` που μόλις συλλέχθηκε. Οποιαδήποτε μετρική υποχωρεί
πέρα από το έψιλόν της προκαλεί αποτυχία της μεταγλώττισης.

Τρέχουσες μετρικές που παρακολουθούνται:

| Μετρική               | Κατεύθυνση | Σημασία                                                  |

| `coverage.lines`      | `up`       | Η κάλυψη γραμμών δεν πρέπει να μειώνεται                 |
| `coverage.functions`  | `up`       | Η κάλυψη συναρτήσεων δεν πρέπει να μειώνεται             |
| `coverage.branches`   | `up`       | Η κάλυψη διακλαδώσεων δεν πρέπει να μειώνεται            |

Για να ενημερώσετε τη βασική γραμμή μετά από μια πραγματική βελτίωση:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

Η σημαία `--update` γράφει τις τρέχουσες μετρημένες τιμές στο `quality-baseline.json`.
Κάντε commit αυτό το αρχείο μαζί με την αλλαγή που βελτίωσε τη μετρική. Ένα PR που βελτιώνει μια
μετρική χωρίς να ενημερώνει τη βασική γραμμή θα εντοπιστεί από το `--require-tighten` (Φάση 6A.5,
σε αναμονή υλοποίησης).

### CodeQL καστάνια: απογραφή αποδοχής υποψηφίων και αποθετηρίου

CI κατέχει την υποψήφια αποδοχή CodeQL μέσω μιας ρητής αλυσίδας εξάρτησης: `codeql-scan` καλεί τον πίνακα τεσσάρων γλωσσών στο `codeql.yml` και, στη συνέχεια, `codeql-admission` εκτελεί `node scripts/check/check-codeql-ratchet.mjs --candidate`. `Gate / CI` απαιτεί και τα δύο αποτελέσματα. Η ποιότητα διατηρεί τους δικούς της αριθμητικούς ελέγχους, αλλά δεν ρωτά τον σαρωτή πριν τελειώσει ο παραγωγός. `Gate / Quality` από μόνο του δεν είναι πλήρης αποδοχή υποψηφίου. CodeQL παραμένει υποχρεωτικό σε υποψήφιους μόνο για έγγραφα.

Η πολιτική στο `config/quality/codeql-admission-policy.json` επιλέγει Ενέργειες, C/C++, JavaScript/TypeScript και Python, προεπιλογή της σουίτας ερωτημάτων, μοντέλο απομακρυσμένης απειλής και λειτουργία κατασκευής καμία. Η προκαταρκτική πτήση του παραγωγού απορρίπτει μια εκκρεμή εγγραφή ενεργοποίησης και διακλαδίζεται έξω από τη ρητή λίστα στόχων. Οι τρέχοντες στόχοι είναι κύριοι και οι δοκιμές συμβάσεων release/v3.8.54. συγκρίνουν αυτήν την πεπερασμένη λίστα και την ενεργοποίηση ώθησης συντήρησης με την έκδοση πακέτου. η επόμενη έκδοση χρειάζεται έλεγχο ενσωμάτωσης. Η υπάρχουσα σκανδάλη PR ευρύτερης απελευθέρωσης του CI διατηρείται, αλλά ένας μη ενσωματωμένος στόχος αναφέρει HOLD πριν από την εξαγωγή αντί να αποκτήσει ένα μη μετρημένο PASS.

Κάθε εργασία μήτρας καταγράφει την πραγματική μεταφόρτωση SARIF ID, τη γλώσσα, την κατηγορία, την εκτέλεση και την προσπάθεια, την ταυτότητα ροής εργασίας καλούντος, το συμβάν ref/head/base/merge SHA και τον κατακερματισμό πολιτικής. Η εξαρτημένη εργασία κατεβάζει μόνο τις αποδείξεις αυτής της εκτέλεσης και επικυρώνει αναλύσεις τεχνουργημάτων. Απαιτεί και τις τέσσερις κατηγορίες, επιτυχημένο παραγωγό και ολοκληρωμένη επεξεργασία κάθε ακριβούς μεταφόρτωσης. Χρησιμοποιεί το φίλτρο sarif_id του API, όχι την πιο πρόσφατη ανάλυση που βρέθηκε σε ένα υποκατάστημα. Οι μερικές επαναλήψεις μπορούν να επαναχρησιμοποιήσουν επιτυχημένες κατηγορίες από μια προηγούμενη προσπάθεια της ίδιας σειράς και υποψηφίου, διατηρώντας την προσπάθεια παραγωγής. ένας αποτυχημένος τρέχων παραγωγός δεν μπορεί να επαναχρησιμοποιήσει προηγούμενα πράσινα στοιχεία.

Η ενέργεια CodeQL περιμένει για επεξεργασία, αλλά η καρφιτσωμένη εφαρμογή της μπορεί να προειδοποιήσει και να συνεχίσει μετά από αποτυχία ανάγνωσης κατάστασης ή εξαντλημένη αναμονή. Επομένως, η είσοδος επαληθεύει ξανά την επεξεργασία. Κατηγορίες που λείπουν, επεξεργασία σε εκκρεμότητα, αποτυχημένες ή ακυρωμένες εργασίες, μπαγιάτικη ταυτότητα, ελλιπής σελιδοποίηση ή μη διαθέσιμο APIs παράγουν HOLD και έξοδος 2. Δεν παραμένει σταθερή αναμονή για μια ανεξάρτητη ροή εργασίας σαρωτή. Ένα μη σαρωμένο PR δεν μπορεί να περάσει επειδή ένα ερώτημα ειδοποίησης επέστρεψε 0. Μια μετρημένη μέτρηση πάνω από `metrics.codeqlAlerts.value` εξέρχεται από το 1. η γραμμή βάσης δεν αυξάνεται για να απορροφήσει τις ειδοποιήσεις άλλου κλάδου. [Κατάσταση μεταφόρτωσης και αναζήτηση ανάλυσης](https://docs.github.com/en/rest/code-scanning/code-scanning).

Η απόδειξη καταγράφει τη μεταφόρτωση και την ανάλυση IDs, κατηγορίες, εκδόσεις εργαλείου, ref/SHA, βασική γραμμή και αριθμούς ειδοποίησης. Η μέτρηση SARIF, identity/result ελάχιστες μετρήσεις κανόνων και οι ακριβείς περιπτώσεις ειδοποίησης παραμένουν υποχρεωτικές. Οι ταυτότητες PR/analysis ελέγχονται ξανά πριν την αποδοχή. Αυτοί οι έλεγχοι δημιουργούν ρυθμισμένη κάλυψη κατηγορίας, όχι ένα απόθεμα κάθε εξαγόμενου αρχείου προέλευσης. Η εξαγωγή χωρίς δόμηση C/C++ δεν περιλαμβάνει κώδικα που δημιουργήθηκε κατά τη διάρκεια μιας κατασκευής έργου. Οι εξαιρέσεις πηγών εξακολουθούν να χρειάζονται έλεγχο και η απόδοση συνεισφέρων χρειάζεται συγκρίσιμα στοιχεία ακριβούς βάσης.

`codeql-maintenance.yml` παρέχει σαρώσεις push ενεργής απελευθέρωσης και το εβδομαδιαίο πρόγραμμα χωρίς να αντιγράφει τους παραγωγούς PR/main. `nightly-codeql-inventory.yml` διατηρεί τη γραμμή βάσης σε όλο το χώρο αποθήκευσης ξεχωριστή, με `--strict-measurement` και αποτυχία όταν η μέτρηση δεν είναι διαθέσιμη. Η χαριτωμένη παράκαμψη του τοπικού παλαιού συλλέκτη δεν αποτελεί αποδοχή υποψηφίου. Η σύσφιξη παραμένει ένα ρητό `--update` μετά από έναν επαληθευμένο χαμηλότερο παγκόσμιο αριθμό.

Η ροή εργασίας για προχωρημένους δεν πρέπει να δημοσιευθεί ενώ έχει ρυθμιστεί η προεπιλεγμένη ρύθμιση: GitHub απορρίπτει αυτόν τον συνδυασμό. Η εκδομένη πολιτική του παραμένει σε εκκρεμότητα έως ότου αναγνωσθεί η ελεγμένη διοικητική μετάβαση. Πριν από τη δημοσίευση, ένας χειριστής καρφιτσώνει το χώρο αποθήκευσης, τους κατακερματισμούς head/base/tree, policy/patch/rollback και την παρατηρούμενη κατάσταση εγκατάστασης. `node scripts/quality/codeql-producer.mjs verify-admin-readback` ελέγχει τις παρεχόμενες αναμενόμενες και πραγματικές εγγραφές JSON. Πρόκειται για τεχνική προστασία, όχι έγκριση χειριστή ή αντικατάσταση για τη λήψη νέων αναγνώσεων. Το διακριτικό PR δεν ζητά ποτέ πρόσβαση διαχείρισης. Η διάθεση και οποιαδήποτε αλλαγή σαρωτή απαιτούν ξεχωριστή ανάγνωση συν τα πραγματικά αποδεικτικά συμβατότητας PR, διχάλας και συγχώνευσης ομάδων.

Τα Forks χρησιμοποιούν φιλοξενούμενους δρομείς, ταμείο χωρίς συνεχή διαπιστευτήρια, κανένα έργο install/build στον παραγωγό και κανένα κληρονομημένο αποθετήριο μυστικών. GitHub υποστηρίζει τη μεταφόρτωση SARIF για το συμβάν pull_request με το διακριτικό μειωμένης διχάλας. Η έγκριση εκτέλεσης συνεισφοράς για πρώτη φορά παραμένει πολιτική GitHub. Μην χρησιμοποιείτε ποτέ το pull_request_target για την εκτέλεση μη αξιόπιστου κώδικα. Επιβεβαιώστε τις πραγματικές άδειες token, το Analytics_key και όλα τα περιβάλλοντα κατηγορίας στο ελεγχόμενο καναρίνι πριν θεωρήσετε ότι η μετεγκατάσταση έχει ολοκληρωθεί. [Διαχωρίστε τους κανόνες μεταφόρτωσης](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible), [αντικρουόμενες λειτουργίες ρύθμισης](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows).

**Οι απολύσεις είναι κλήση του χειριστή (Hard Rule #14)** — δεν απορρίπτει ποτέ μια ειδοποίηση CodeQL χωρίς να καταγράφει την τεχνική αιτιολόγηση στο σχόλιο απόρριψης: `won't fix` για απαίτηση ανοδικού πρωτοκόλλου, `used in tests` για εξάρτημα δοκιμής, `false positive` για απολυμαντικό CodeQL δεν μπορεί να δει (προηγούμενο: `docs/security/ERROR_SANITIZATION.md`).

## Απόκλιση του ratchet σε επίπεδο release (WS5.5, v3.8.49)

Όταν ένα ratchet (μέγεθος αρχείου, πολυπλοκότητα, προειδοποιήσεις eslint) παρουσιάζει παλινδρόμηση στο ΚΑΘΑΡΟ tip του release
— δηλαδή ο ΣΥΝΔΥΑΣΜΟΣ των merges προκάλεσε την παλινδρόμηση και κανένα μεμονωμένο PR δεν την αναπαράγει
στο δικό του branch — η διόρθωση ανήκει στον **release captain, μία φορά, στο
release branch**: προτιμήστε εξαγωγή/refactor· επανακαθορίστε το baseline μόνο με την τεκμηριωμένη
καταχώριση αιτιολόγησης. Μην επιρρίπτετε ποτέ την απόκλιση του συνδυασμού σε PR κάποιου contributor και μην
επανακαθορίζετε ποτέ το baseline ανά PR (αυτό αποκρύπτει πραγματικές παλινδρομήσεις). Πρώτα κάντε τη διάκριση: αναπαραγάγετε
την αποτυχία στο καθαρό tip μέσα σε ένα probe worktree, προτού υποθέσετε ότι την προκάλεσε το PR σας.

## Αποθήκευση των μειώσεων του ratchet — η καθοδική κατεύθυνση (#8584)

Το ratchet είναι αυτοματοποιημένο μόνο κατά το ήμισυ, και μάλιστα στο λάθος μισό. Η **αύξηση** ενός ορίου είναι μια
χειροκίνητη επεξεργασία JSON που διαρκεί δέκα δευτερόλεπτα και αποτελεί τον ταχύτερο τρόπο για να ξεμπλοκάρει ένα αποτυχημένο PR.
Η **μείωση** ενός ορίου απαιτεί από κάποιον να εκτελέσει το `--update` και να κάνει commit το αποτέλεσμα — και μέχρι
να προστεθεί το job `bank-ratchet-shrinks`, κανένα workflow δεν το εκτελούσε. Η μετρημένη συνέπεια
(2026-07-25): 18 παγωμένα αρχεία βρίσκονται ήδη στο όριο των 800 γραμμών για νέα αρχεία ή κάτω από αυτό, με τη χειρότερη
περίπτωση στο 132× (`src/shared/validation/schemas.ts`, 19 γραμμές με όριο 2,523)· το
ανώτατο όριο πολυπλοκότητας μετακινήθηκε από `1794 → 2169` μέσα από ~37 σημειώσεις επανακαθορισμού baseline, με ακριβώς μία
μείωση (−1)· και η φράση «σύσφιξη μέσω `--update` στον επόμενο κύκλο» γράφτηκε 31 φορές και
τηρήθηκε μία φορά. Ένα όριο που επιβιώνει περισσότερο από τον κώδικα που το δικαιολόγησε μετατρέπει σιωπηρά κάθε ολοκληρωμένη
αποσύνθεση σε περιθώριο ανάπτυξης για όποιον επεξεργαστεί το αρχείο στη συνέχεια.

Το `nightly-release-green.yml` → job **`bank-ratchet-shrinks`** κλείνει αυτόν τον κύκλο:

|               |                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| Εκτελείται σε | `schedule` (3×/ημέρα) + `workflow_dispatch` — σκόπιμα **όχι** σε `push`                                             |
| Μετρά         | το υψηλότερο `release/vX.Y.Z`, με την ίδια επίλυση + προστασία από injection όπως το `release-green`                |
| Γράφει        | `check:file-size --update` και `check:complexity-ratchets --update` (και τα δύο μόνο προς μείωση εκ κατασκευής)     |
| Επαληθεύει    | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                            |
| Παραδίδει     | ένα μοναδικό, πάντα ενημερωμένο PR προς το release branch — ενημερώνεται αναγκαστικά, χωρίς ποτέ να δημιουργεί spam |

Η αποθήκευση γίνεται σε παρτίδες αντί ανά push, επειδή δεν έχει απαίτηση χαμηλού latency (μια μείωση που
αποθηκεύεται εντός 8 ωρών είναι αποδεκτή), ενώ μια εκτέλεση ανά merge θα ανακατασκεύαζε επανειλημμένα το PR branch
κατά τη διάρκεια εκστρατειών συγχωνεύσεων και θα επιβάρυνε κάθε φορά το κόστος μιας πλήρους σάρωσης ESLint. Η ανίχνευση παραμένει στο
push (`release-green`)· μόνο η αποθήκευση γίνεται σε παρτίδες.

### Ο επαληθευτής ασφάλειας

Το job γράφει στα baselines χωρίς επίβλεψη, επομένως το `verify-ratchet-bank.mjs` είναι αυτό που καθιστά
αποδεκτή αυτή τη διαδικασία. Συγκρίνει μέσω diff το δέντρο μετά το `--update` με το `HEAD` και **διακόπτει το job
προτού υπάρξει οποιοδήποτε commit** — χωρίς να ανοίξει PR — εκτός εάν κάθε αλλαγή είναι μία από τις εξής:

- μια αριθμητική καταχώριση `frozen` / `testFrozen` που **μειώθηκε** ή **αφαιρέθηκε**
- `complexity-baseline.json` → `count` που **μειώθηκε**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` που **μειώθηκε**

Οτιδήποτε άλλο αποτυγχάνει: αύξηση ενός αριθμού, προσθήκη καταχώρισης, αλλαγή των `cap`/`testCap` ή
διαγραφή/επανεγγραφή μιας σημείωσης `_rebaseline_*` (αυτές οι σημειώσεις αποτελούν το ίχνος ελέγχου που εξηγεί γιατί υπάρχει κάθε
ανώτατο όριο και αποθηκεύονται μέσα στο ίδιο αντικείμενο `frozen` με τις καταχωρίσεις αρχείων).
Ένα bot που θα μπορούσε να αυξήσει ένα όριο θα ήταν σαφώς χειρότερο από την υφιστάμενη κατάσταση. Προστασία από
παλινδρόμηση: `tests/unit/verify-ratchet-bank.test.ts`.

Το job δεν κάνει ποτέ push στο `release/*` — ένας άνθρωπος συγχωνεύει το PR, ώστε μια λανθασμένη μέτρηση
να μην μπορεί να ενσωματωθεί χωρίς έλεγχο.

## Πολιτική λίστας επιτρεπόμενων

Κάθε πύλη που δεν μπορεί να αποτύχει λόγω προϋπαρχουσών παραβιάσεων χρησιμοποιεί μια παγιωμένη λίστα επιτρεπόμενων
(π.χ. `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). Η πολιτική είναι:

**Διορθώστε τη βασική αιτία· χρησιμοποιήστε τη λίστα επιτρεπόμενων μόνο όταν η παραβίαση προϋπάρχει και
δεν μπορεί να διορθωθεί στο ίδιο PR.**

Όταν προσθέτετε μια καταχώριση σε λίστα επιτρεπόμενων:

1. Συμπεριλάβετε ένα σχόλιο με την αιτιολόγηση.
2. Αναφέρετε το σχετικό ζήτημα παρακολούθησης (π.χ. `// #3498 — Phase 2 feature, not yet implemented`).
3. Αφαιρέστε την καταχώριση στο ίδιο PR που διορθώνει την παραβίαση — μια παρωχημένη καταχώριση που δεν
   καταστέλλει πλέον μια ενεργή παραβίαση αποτελεί και η ίδια ελάττωμα (ο έλεγχος παρωχημένης επιβολής 6A.3 θα
   προκαλεί αποτυχία της πύλης για μια ορφανή καταχώριση λίστας επιτρεπόμενων μόλις υλοποιηθεί).

**Μην** προσθέτετε καταχωρίσεις στη λίστα επιτρεπόμενων για να περάσουν οι δοκιμές γρηγορότερα. Μια επιτυχής πύλη με μια διαρκώς αυξανόμενη
λίστα επιτρεπόμενων δημιουργεί μια ψευδή αίσθηση ποιότητας.

### Όταν μια πύλη αποτυγχάνει στο PR σας

1. **Διαβάστε προσεκτικά την έξοδο της πύλης** — σας υποδεικνύει ακριβώς ποιο αρχείο ή σύμβολο παραβίασε
   τον κανόνα.
2. **Διορθώστε την παραβίαση** — οι περισσότερες πύλες είναι ντετερμινιστικοί έλεγχοι του συστήματος αρχείων που ολοκληρώνονται επιτυχώς μόλις
   ο κώδικας διορθωθεί.
3. **Εάν η παραβίαση προϋπάρχει** (δηλαδή δεν την εισαγάγατε εσείς, αλλά πλέον καλύπτεται
   από την πύλη): προσθέστε μια καταχώριση στη λίστα επιτρεπόμενων με σχόλιο αιτιολόγησης και σχετικό ζήτημα παρακολούθησης.
4. **Εάν η πύλη λειτουργεί ως καστάνια** (κάλυψη, προειδοποιήσεις ESLint, διπλότυπος κώδικας, πολυπλοκότητα):
   η αλλαγή σας επιδείνωσε τη μέτρηση. Διορθώστε το υποκείμενο πρόβλημα ή (σπανίως) εκτελέστε
   `npm run quality:ratchet -- --update` εάν η αλλαγή είναι σκόπιμη και η υποβάθμιση της μέτρησης
   είναι αποδεκτή — αλλά τεκμηριώστε τον λόγο στην περιγραφή του PR.
5. **Συμβουλευτικές πύλες** (`continue-on-error: true`) παρέχουν πληροφορίες — δεν εμποδίζουν
   τη συγχώνευση, αλλά εμφανίζονται στη σύνοψη CI. Διορθώστε τες ούτως ή άλλως.

## Προσθήκη νέου ελέγχου

1. Δημιουργήστε το `scripts/check/check-<name>.mjs` (ή `.ts`). Οι έλεγχοι πολιτικής τερματίζονται με 0/1.
   Οι έλεγχοι τύπου ratchet εκπέμπουν μια μετρική στο `quality-metrics.json` μέσω του `collect-metrics.mjs`.
2. Προσθέστε το `"check:<name>": "node scripts/check/check-<name>.mjs"` στο `package.json` και
   συγχρονίστε το ψευδώνυμο και την ακριβή εντολή του στο `config/quality/gate-manifest.json`.

## Σχετική τεκμηρίωση

- Εφοδιαστική αλυσίδα (προέλευση, SBOM, Trivy, Scorecard): [`docs/security/SUPPLY_CHAIN.md`](../security/SUPPLY_CHAIN.md)

#### `check-key-completeness` — πύλη ισοτιμίας συνόλου κλειδιών

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, εργασία `i18n-ui-coverage`).
Συγκρίνει το σύνολο των τερματικών κλειδιών κάθε `src/i18n/messages/<locale>.json` με το `en.json` και αποτυγχάνει
για κάθε απόν ή επιπλέον τερματικό κλειδί, ανεξάρτητα από το πότε προστέθηκε το κλειδί. Τα σύμβολα κράτησης θέσης
`__MISSING__:` υπολογίζονται ως παρόντα (το περιεχόμενό τους αφορά την πύλη αναλογίας). Είναι το απόλυτο συμπλήρωμα
των δύο πυλών που βασίζονται σε diff/ποσοστό: το `check-ui-keys-coverage` επιβάλλει κατώτατο όριο 80 % ανά
locale (43 απόντα κλειδιά σε σύνολο ~13.000 εξακολουθούν να δίνουν 99,7 %) και το `check-new-key-coverage` αξιολογεί
μόνο τα κλειδιά που ένα PR προσθέτει στο `en.json`. Μια παρτίδα locale δημιουργείται από το `en.json` της ημέρας
κατά την οποία δημιουργείται ο κλάδος της και μεταφράζεται επί ημέρες, ενώ η βάση συνεχίζει να προσθέτει κλειδιά· το PR
της παρτίδας δεν προσθέτει το ίδιο κανένα κλειδί, οπότε και οι δύο συγγενικές πύλες παρέμειναν σιωπηλές όταν η παρτίδα 1
(#13044) ενσωματώθηκε με έλλειψη 43 κλειδιών σε εννέα locale και η παρτίδα 2 (#13660) με έλλειψη 10 κλειδιών σε οκτώ
(2026-09-15). Διορθώστε μια αποτυχία με
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`· ένα επιπλέον (`extra`) τερματικό κλειδί
σημαίνει ότι η πηγή το αφαίρεσε — διαγράψτε το από το locale. Το `--warn` αναφέρει το πρόβλημα χωρίς να προκαλεί αποτυχία.
Το `--catalog=cli` εκτελεί την ίδια σύγκριση στο `bin/cli/locales` (`npm run i18n:check-keys:cli`)·
και τα δύο βήματα βρίσκονται στην εργασία `i18n-ui-coverage`.

#### `check-new-key-coverage` — πύλη i18n νέων κλειδιών

Συγγενική πύλη του `check-ui-value-drift`. Εκείνη εντοπίζει μια αγγλική τιμή που **ξαναγράφηκε**
ενώ οι μεταφράσεις της έμειναν πίσω· αυτή εντοπίζει ένα αγγλικό κλειδί που **προστέθηκε**
ενώ ορισμένα locale δεν το έλαβαν ποτέ.

Το `check-ui-keys-coverage` δεν μπορεί να εντοπίσει αυτήν την κατηγορία: επιβάλλει ένα ποσοστιαίο κατώτατο όριο ανά locale και
έντεκα απόντα κλειδιά σε σύνολο ~13.000 αφήνουν την κάλυψη στο 99,9%. Ένα ποσοστό ανά γλώσσα δεν μπορεί
να εκφράσει ότι «αυτή η λειτουργία κυκλοφόρησε αμετάφραστη» — μια ολόκληρη λειτουργία μπορεί να προστεθεί σε ένα νέο locale χωρίς
καθόλου κείμενο και ο αριθμός να μη μετακινηθεί ποτέ.

Το περιστατικό που κωδικοποιεί: η Φάση 3 του Orchestration Canvas μετέφρασε τα έντεκα κλειδιά της στα
42 locale που υπήρχαν τότε. Ώρες αργότερα, η παρτίδα γλωσσών της ΕΕ (#13044) αύξησε τα locale του αποθετηρίου
σε 51 και τα εννέα νέα (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) δεν
τα έλαβαν ποτέ. Το `deepMergeFallback` αντικαθιστά ένα απόν κλειδί με τα αγγλικά, επομένως η μορφή της αστοχίας ήταν
ένα αμετάφραστο περιβάλλον εργασίας χρήστη αντί για ένα κενό περιβάλλον εργασίας χρήστη — πραγματική και εκ σχεδιασμού σιωπηλή.

Όπως και η συγγενική της πύλη, λαμβάνει υπόψη το **diff**, συγκρίνοντας τα αγγλικά στη βάση συγχώνευσης με το λειτουργικό
δέντρο, ώστε τα προϋπάρχοντα κενά να παραμένουν παγωμένα και να μην απαιτείται μετάπτωση για την ενεργοποίηση της πύλης.

**Ένας δείκτης `__MISSING__:<english>` δεν την ικανοποιεί (από 2026-09-17).** Προηγουμένως αποτελούσε την
τεκμηριωμένη αναβολή — κατά την εκτέλεση χρησιμοποιούνται εφεδρικά τα σωστά αγγλικά — έως ότου οκτώ PR λειτουργιών στις
2026-09-16 πρόσθεσαν 61 κλειδιά και έβαλαν τον δείκτη και στα 65 locale αντί να τα μεταφράσουν: αυτή
η πύλη τα αποδέχθηκε όλα, τίποτα δεν εμπόδισε τα PR και η πύλη αναλογίας πραγματικών μεταφράσεων που προκαλεί αποκλεισμό
απέτυχε κατόπιν στην κορυφή της έκδοσης για όλους (pt-BR 3,2 % > 2,5 % + 0,5). Ένας δείκτης πλέον αξιολογείται
ως απούσα μετάφραση. Διορθώστε μια αποτυχία με
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` ή
όλα τα locale παράλληλα με `npm run i18n:translate-new-keys` (`scripts/i18n/translate-new-keys.sh`,
ασφαλές σε αποσυνδεδεμένη εκτέλεση, αρνείται να ξεκινήσει χωρίς τις μεταβλητές περιβάλλοντος `OMNIROUTE_TRANSLATION_*`). Ένα κλειδί που πρέπει να παραμείνει
στα αγγλικά (ένα δεσμευμένο όνομα προϊόντος/μηχανής/σημαίας) ανήκει στο `scripts/i18n/untranslatable-keys.json`,
ποτέ πίσω από έναν δείκτη. Το `vi` απαγορεύει πλήρως τους δείκτες (`tests/unit/i18n-vi-completeness.test.ts`).

#### `check-vitest-exclusions` — πύλη σταθμευμένων δοκιμών

Ένα αρχείο στη λίστα `exclude` του `vitest.config.ts` είναι μια δοκιμή που δεν εκτελείται, αλλά μοιάζει
με κάλυψη σε όποιον διαβάζει το δέντρο. Εξήντα δύο αρχεία συσσωρεύτηκαν πίσω από το σχόλιο
`// #8618 — pre-existing failure; remove this exclusion when fixed`. Το ζήτημα #8618 έκλεισε στις
2026-08-11, ενώ η λίστα που παρακολουθούσε αυξήθηκε από 45 καταχωρίσεις σε 62, με καθεμία από τις νέες να κληρονομεί ένα σχόλιο
που παρέπεμπε σε ένα ανενεργό ζήτημα. Όταν η λίστα τελικά μετρήθηκε αρχείο προς αρχείο (#13204), **51 από τα 62
περνούσαν στο τρέχον δέντρο χωρίς καμία αλλαγή στον πηγαίο κώδικα**.

Η πύλη απαιτεί κάθε εξαίρεση που αντιστοιχεί σε πραγματικό αρχείο (α) να κατονομάζει ένα ζήτημα παρακολούθησης και
(β) να εμφανίζεται στο `config/quality/vitest-exclusions.json` με τη μετρημένη κατάστασή της, ώστε η προσθήκη μιας εξαίρεσης να αποτελεί
ένα diff που μπορεί να αναθεωρηθεί σε ειδικό αρχείο, αντί για μία ακόμη γραμμή σε έναν πίνακα 60 καταχωρίσεων. Σκόπιμα
δεν επανεκτελεί τις εξαιρούμενες δοκιμές — αυτό κοστίζει ~10 λεπτά και ανήκει σε μια περιοδική εργασία· η
καταγραφή αποθηκεύει το πότε μετρήθηκε τελευταία φορά καθεμία.
