## Ολοκληρώσεις συνομιλίας

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Προσαρμοσμένες κεφαλίδες

| Κεφαλίδα                 | Κατεύθυνση | Περιγραφή                                                                                                                                                                                                                                   |
| ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Αίτημα     | Ορίστε την σε `true` για παράκαμψη της κρυφής μνήμης                                                                                                                                                                                        |
| `x-omniroute-no-memory`  | Αίτημα     | Ορίστε την σε `true` για παράλειψη της εισαγωγής μνήμης + δεξιοτήτων για αυτό το αίτημα (αντικατοπτρίζει τη μη χρήση κρυφής μνήμης και αποφεύγει την επιβάρυνση διακριτικών/κόστους ανά κλήση)                                              |
| `X-OmniRoute-Progress`   | Αίτημα     | Ορίστε την σε `true` για συμβάντα προόδου                                                                                                                                                                                                   |
| `X-Session-Id`           | Αίτημα     | Σταθερό κλειδί συνεδρίας για συσχέτιση εξωτερικής συνεδρίας                                                                                                                                                                                 |
| `x_session_id`           | Αίτημα     | Γίνεται επίσης αποδεκτή η παραλλαγή με κάτω παύλα (απευθείας HTTP)                                                                                                                                                                          |
| `X-OmniRoute-Session-Id` | Αίτημα     | Ετικέτα συνεδρίας/συνομιλίας που παρέχεται από τον καλούντα (τροφοδοτεί επίσης τη μνήμη). Όταν υπάρχει, αποθηκεύεται αυτούσια στο `call_logs.session_tag` για απόδοση κόστους ανά συνεδρία (#8249) — δεν δημιουργείται ποτέ όταν απουσιάζει |
| `Idempotency-Key`        | Αίτημα     | Κλειδί αποδιπλοποίησης (παράθυρο 5s)                                                                                                                                                                                                        |
| `X-Request-Id`           | Αίτημα     | Εναλλακτικό κλειδί αποδιπλοποίησης                                                                                                                                                                                                          |
| `x-omniroute-connection` | Αίτημα     | Καρφιτσώνει ένα αίτημα ενός μοντέλου σε μία σύνδεση παρόχου (λογαριασμό) βάσει του id της — δείτε [Καρφίτσωμα λογαριασμού ανά αίτημα](#account-pinning-per-request)                                                                         |
| `X-OmniRoute-Cache`      | Απόκριση   | `HIT` ή `MISS` (χωρίς ροή)                                                                                                                                                                                                                  |
| `X-OmniRoute-Idempotent` | Απόκριση   | `true` εάν έγινε αποδιπλοποίηση                                                                                                                                                                                                             |
| `X-OmniRoute-Progress`   | Απόκριση   | `enabled` εάν είναι ενεργοποιημένη η παρακολούθηση προόδου                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | Απόκριση   | Το πραγματικό ID συνεδρίας που χρησιμοποιείται από το OmniRoute                                                                                                                                                                             |
| `X-OmniRoute-Request-Id` | Απόκριση   | ID συσχέτισης αιτήματος (όταν είναι γνωστό)                                                                                                                                                                                                 |
| `X-OmniRoute-Version`    | Απόκριση   | Έκδοση build του OmniRoute (υπάρχει πάντα)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | Απόκριση   | Ποσό σε USD που εξοικονομήθηκε από την κρυφή μνήμη σε ένα HIT (μόνο για επιτυχίες κρυφής μνήμης)                                                                                                                                            |
| `X-OmniRoute-Decision`   | Απόκριση   | Ίχνος δρομολόγησης: `strategy=<name>; provider=<alias>; latency_ms=<n>` (το `<name>` είναι η συνδυαστική στρατηγική ή `single` για αίτημα χωρίς συνδυασμό) — υπάρχει πάντα στις αποκρίσεις ολοκλήρωσης                                      |

> Σημείωση για το Nginx: εάν βασίζεστε σε κεφαλίδες με κάτω παύλες (για παράδειγμα `x_session_id`), ενεργοποιήστε το `underscores_in_headers on;`.

#### Καρφίτσωμα λογαριασμού ανά αίτημα

Όταν ένας πάροχος έχει πολλές συνδέσεις (λογαριασμούς ή κλειδιά), το OmniRoute συνήθως επιλέγει μία
μέσω της στρατηγικής επιλογής λογαριασμού. Αντ' αυτού, ένα αίτημα μπορεί να καρφιτσώσει μία συγκεκριμένη σύνδεση
με την κεφαλίδα `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Πού θα βρείτε το id.** Ανοίξτε τη σελίδα του παρόχου στον πίνακα ελέγχου
  (**Πίνακας ελέγχου → Πάροχοι → <provider>**) και κάντε κλικ στο chip του id `xxxxxxxx…` σε μια
  γραμμή σύνδεσης — αντιγράφει ολόκληρο το id της σύνδεσης.
- **Ποια αιτήματα το λαμβάνουν υπόψη.** Αιτήματα ενός μοντέλου (`provider/model`) στα
  `/v1/chat/completions`, `/v1/messages` και `/v1/responses`. Οι συνδυασμοί αγνοούν την κεφαλίδα:
  καρφιτσώστε έναν λογαριασμό ανά βήμα του συνδυασμού μέσω της σύνδεσης του ίδιου του βήματος.
- **Το καρφίτσωμα είναι αυστηρό, όχι απλή προτίμηση.** Χρησιμοποιείται αποκλειστικά η
  καρφιτσωμένη σύνδεση. Μια αποτυχία εντός του αιτήματος καταγράφει την περίοδο αναμονής του
  λογαριασμού, αλλά **δεν** μεταβαίνει σε συγγενικό λογαριασμό του ίδιου παρόχου.
- **Η περίοδος αναμονής και το όριο χρήσης αποδεσμεύουν το καρφίτσωμα.** Όσο η καρφιτσωμένη
  σύνδεση βρίσκεται σε περίοδο αναμονής, έχει εξαντλήσει το όριο χρήσης της ή έχει αποκλειστεί από
  μια πολιτική ορίων χρήσης, τα επόμενα αιτήματα καταφεύγουν στις άλλες συνδέσεις του παρόχου,
  ακριβώς όπως η μη καρφιτσωμένη κίνηση.
- **Άγνωστα ή απενεργοποιημένα ids προκαλούν αποτυχία.** Ένα id που δεν βρίσκεται στην ενεργή
  δεξαμενή του παρόχου (έχει διαγραφεί, απενεργοποιηθεί ή ανήκει σε άλλον πάροχο) δεν αφήνει κανέναν
  επιλέξιμο λογαριασμό, οπότε το αίτημα αποτυγχάνει αντί να δρομολογηθεί σιωπηρά αλλού.

Το Claude Code στέλνει προσαρμοσμένες κεφαλίδες μέσω του `ANTHROPIC_CUSTOM_HEADERS`. Τοποθετήστε το
στο μπλοκ `env` του `~/.claude/settings.json` ή σε ένα `.claude/settings.json` σε επίπεδο έργου,
ώστε να καρφιτσώσετε διαφορετικό λογαριασμό ανά έργο:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Πηγή: `src/sse/handlers/chat.ts` (ανάγνωση κεφαλίδας), `src/sse/services/auth.ts` και
`src/sse/services/sessionAffinityPin.ts` (αποδέσμευση καρφιτσώματος και έλεγχος απουσίας από τη δεξαμενή).

> **Κεφαλίδες τηλεμετρίας κόστους:** οι επιτυχείς αποκρίσεις χωρίς ροή περιλαμβάνουν επίσης το σύνολο τηλεμετρίας κόστους `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, σταθερά 10 δεκαδικά ψηφία· `0.0000000000` για δωρεάν/χωρίς τιμολόγηση), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` και `X-OmniRoute-Fallback-Attempts` (μόνο όταν > 0), καθώς και `X-OmniRoute-Request-Id` και `X-OmniRoute-Version`. Αυτές εκπέμπονται από τις ολοκληρώσεις συνομιλίας, τα `/v1/responses`, `/v1/messages`, **καθώς και τα τελικά σημεία πολυμέσων** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` και `/v1/moderations` (πάντα με κόστος `0`). Το κόστος πολυμέσων υπολογίζεται ανά τροπικότητα (ανά εικόνα, ανά δευτερόλεπτο, ανά χαρακτήρα, ανά μονάδα αναζήτησης) όταν υπάρχει διαθέσιμη τιμολόγηση, διαφορετικά είναι `0` (fail-open).

> **Σημασιολογία κόστους για cache hit:** σε ένα HIT της σημασιολογικής cache (`X-OmniRoute-Cache-Hit: true`) δεν πραγματοποιείται κλήση προς ανάντη υπηρεσία, επομένως το `X-OmniRoute-Response-Cost` είναι `0.0000000000` (το **πρόσθετο** κόστος εξυπηρέτησης του hit). Το αρχικό/υποθετικό κόστος αναφέρεται ξεχωριστά στο `X-OmniRoute-Cost-Saved`. Οι καταναλωτές δεδομένων χρέωσης θα πρέπει να αθροίζουν το `X-OmniRoute-Response-Cost` (τα hits δεν κοστίζουν τίποτα), ενώ τα αναλυτικά στοιχεία της cache μπορούν να συγκεντρώνουν το `X-OmniRoute-Cost-Saved`.

## Αποκλειστικές μισθώσεις διαχειριζόμενων συνεδριών

Η αποκλειστική μίσθωση διαχειριζόμενων συνεδριών είναι μια προαιρετική, ανεξάρτητη από τον πελάτη σύμβαση δρομολόγησης: ένας ενεργός κάτοχος
δεσμεύει μία επιλέξιμη σύνδεση OmniRoute. Δεν μισθώνει κάποιο μοντέλο, δεν απαιτεί OAuth, δεν προσδιορίζει
συγκεκριμένο πελάτη και δεν απαιτεί συγκεκριμένο πάροχο.

Το API key που χρησιμοποιείται για τον έλεγχο ταυτότητας πρέπει να διαθέτει το scope `lease:exclusive` και μια ρητή, μη κενή
λίστα `allowedConnections`. Το όριο μεταβολής της βάσης δεδομένων επιβάλλει την ταυτόχρονη παρουσία και των δύο πεδίων κατά τη
δημιουργία κλειδιού και τις μερικές ενημερώσεις.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Οι επιτυχείς αποκρίσεις απόκτησης, ανανέωσης και αποδέσμευσης εκθέτουν χρονικές σημάνσεις, το `state` και την ακριβή θετική
`generation`, αλλά ποτέ την επιλεγμένη σύνδεση ή τα διαπιστευτήρια. Η ανανέωση και η αποδέσμευση παρέχουν τη
γενιά στο σώμα JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Ένας ενεργός κάτοχος μίσθωσης μπορεί να ζητήσει ρητά μεταδεδομένα εμφάνισης που προστατεύουν το απόρρητο για την τρέχουσα δέσμευσή του:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Αυτή η προαιρετική ενέργεια κατάστασης περιφράσσεται από τον αδιαφανή κάτοχο, το διαχειριζόμενο API key με επαληθευμένη ταυτότητα και την ακριβή
ενεργή γενιά σε μία συναλλαγή βάσης δεδομένων. Το `displayName` είναι μόνο το διαμορφωμένο όνομα
σύνδεσης με αφαιρεμένα τα περιττά κενά· είναι `null` όταν δεν υπάρχει ασφαλές διαμορφωμένο όνομα. Το OmniRoute δεν υποκαθιστά ποτέ ένα
email ή μια δημιουργημένη ταυτότητα λογαριασμού. Η τιμή παρόχου είναι μια μη ευαίσθητη ετικέτα εμφάνισης και ποτέ
ένα δημιουργημένο αναγνωριστικό συμβατού παρόχου. Εξαιρούνται τα διαπιστευτήρια, τα token, τα cookie, τα ανεπεξέργαστα αναγνωριστικά σύνδεσης ή
API key, τα hash κατόχων, τα μυστικά περίφραξης και τα εσωτερικά δεδομένα δρομολόγησης.

Οι αναζητήσεις με λάθος κλειδί, λάθος κάτοχο, παρωχημένη γενιά, καθώς και οι ελλιπείς, ληγμένες, αποδεσμευμένες και ακυρωμένες αναζητήσεις,
επιστρέφουν όλες το ίδιο σφάλμα `409 LEASE_FENCE_STALE` χωρίς μεταδεδομένα σύνδεσης. Ένας πελάτης που έλαβε την απόκριση αναμονής χωρητικότητας δεν έχει ενεργή δέσμευση προς επιθεώρηση. Όταν η δρομολόγηση μεταφέρει μια ενεργή μίσθωση,
η ίδια γενιά παραμένει έγκυρη και η κατάσταση επιστρέφει ατομικά τη νέα δέσμευση, ποτέ την παλιά.
Οι υφιστάμενοι πελάτες παραμένουν αμετάβλητοι, επειδή οι αποκρίσεις απόκτησης, ανανέωσης, αποδέσμευσης και αναμονής διατηρούν
τις προηγούμενες δομές τους.

Αυτή η σύμβαση διακομιστή δεν αλλάζει το τυπικό `/status` του OpenAI Codex. Το τυπικό Codex αναφέρει επί του παρόντος τον
πάροχο μοντέλου του και την ενσωματωμένη κατάσταση ελέγχου ταυτότητας/λογαριασμού, αλλά δεν εμφανίζει αυθαίρετα προσαρμοσμένα
μεταδεδομένα λογαριασμού παρόχου· μια μελλοντική ενσωμάτωση πελάτη πρέπει να καλέσει αυτή την ενέργεια και να αποφασίσει πώς θα
εμφανίσει το `connection.displayName`.

Κάθε διαχειριζόμενο αίτημα συμπερασμού παρέχει έπειτα και τις δύο κεφαλίδες ελέγχου:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Ο ακριβής κάτοχος, η γενιά, η ενεργή σύνδεση και το API key με επαληθευμένη ταυτότητα περιφράσσονται αμέσως
πριν από κάθε υποστηριζόμενη προσπάθεια προς τα ανάντη. Η επανάληψη χρήσης του κατόχου και της γενιάς με άλλο κλειδί αποτυγχάνει, ακόμη
και όταν το συγκεκριμένο κλειδί επιτρέπει την ίδια σύνδεση. Οι ανεπεξέργαστες τιμές κατόχου δεν αποθηκεύονται μόνιμα, δεν καταγράφονται, δεν διατηρούνται στο
στιγμιότυπο του αιτήματος και δεν προωθούνται προς τα ανάντη.

Η προσωρινή διεκδίκηση πόρων επιστρέφει HTTP `429` με `Retry-After` και:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Αυτή η απόκριση σημαίνει μόνο ότι το κανονικό σύνολο επιλέξιμων συνδέσεων δεν ήταν κενό και κάθε ελεύθερος υποψήφιος
δεσμευόταν από ξένη ενεργή μίσθωση. Τα μη υποστηριζόμενα μοντέλα/οι μη υποστηριζόμενοι πάροχοι, η ασυμφωνία πολιτικής, η περίοδος αναμονής, το όριο χρήσης,
η εύρυθμη λειτουργία και άλλες συνήθεις αποτυχίες επιλεξιμότητας διατηρούν τις υπάρχουσες αποκρίσεις OmniRoute.

### `x-omniroute-compression`

Παράκαμψη του πλάνου συμπίεσης ανά αίτημα. Έχει την υψηλότερη προτεραιότητα — υπερισχύει της παράκαμψης συνδυασμού δρομολόγησης,
του ενεργού προφίλ, της αυτόματης ενεργοποίησης και της προεπιλογής του πίνακα. Τιμές:

| Τιμή          | Αποτέλεσμα                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | Καμία συμπίεση για αυτό το αίτημα.                                                                                                       |
| `default`     | Το προεπιλεγμένο προφίλ που προκύπτει από τον πίνακα (αγνοεί το ενεργό προφίλ). Οι μη αντιστρεπτές μηχανές παραμένουν απενεργοποιημένες. |
| `safe`        | Μόνο αποδιπλοποίηση και σύμπτυξη κενών διαστημάτων.                                                                                      |
| `allow-lossy` | Διατήρηση του πλάνου του διαχειριστή για αυτό το αίτημα, συμπεριλαμβανομένων περιλήψεων και αναδιατυπώσεων ύφους.                        |
| `engine:<id>` | Μία μεμονωμένη μηχανή όταν είναι ενεργοποιημένη, π.χ. `engine:rtk`. Προαιρετική ενεργοποίηση ανά αίτημα για αυτή τη μηχανή.              |
| `<combo>`     | Ένας επώνυμος συνδυασμός, με αντιστοίχιση πρώτα βάσει ονόματος (χωρίς διάκριση πεζών-κεφαλαίων) και έπειτα βάσει id.                     |

Σημειώσεις:

- Οι άγνωστες τιμές αγνοούνται (το αίτημα δεν απορρίπτεται ποτέ)· η επίλυση συνεχίζει σύμφωνα με την κανονική σειρά προτεραιότητας του διαχειριστή.
- Αν πολλοί συνδυασμοί έχουν το ίδιο όνομα, περάστε το **id** του συνδυασμού για ντετερμινιστική αντιστοίχιση.
- Ένας συνδυασμός του οποίου το όνομα είναι `off` ή `default` δεν μπορεί να επιλεγεί βάσει ονόματος (αυτές οι λέξεις-κλειδιά ερμηνεύονται πρώτες)· αναφερθείτε σε έναν τέτοιο συνδυασμό μέσω του id του.
- Ο κύριος διακόπτης συμπίεσης αποτελεί απόλυτη δικλείδα: όταν η συμπίεση είναι απενεργοποιημένη καθολικά, αυτή η κεφαλίδα δεν μπορεί να την ενεργοποιήσει.

Το εφαρμοζόμενο πλάνο επιστρέφεται στην κεφαλίδα απόκρισης:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

όπου το `<source>` είναι ένα από τα `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ή `off`.

## Ενσωματώσεις

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Διαθέσιμοι πάροχοι: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Τα αναγνωριστικά καταλόγου έχουν τη μορφή `provider/model` (παράδειγμα: `jina-ai/jina-embeddings-v5-omni-small`). Επιλύονται επίσης τα απλά αναγνωριστικά μοντέλων Jina που εμφανίζονται στο μητρώο (για παράδειγμα `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`). Οι λειτουργίες embed/rerank/classify/segment της Jina χρησιμοποιούν πρώτα τα διαπιστευτήρια `jina-ai` του πίνακα ελέγχου· το `JINA_AI_API_KEY` χρησιμοποιείται ως εναλλακτική μόνο όταν δεν υπάρχει κλειδί στον πίνακα ελέγχου. Η κάρτα `jina-reader` προορίζεται μόνο για το Reader / `r.jina.ai` (`POST /v1/web/fetch`) και δεν παρέχει ποτέ ενσωματώσεις ή ανακατάταξη.

Τα μοντέλα του μητρώου που δηλώνουν υποστήριξη πολλαπλών τρόπων λειτουργίας δέχονται επίσης έως και 32 δομημένα
στοιχεία ανεξάρτητα από τον πάροχο. Οι τύποι στοιχείων πολυμέσων είναι `text`, `image`, `audio`, `video` και `document`. Το `source`
των πολυμέσων είναι είτε `{"type":"url","url":"https://..."}` είτε
`{"type":"base64","data":"...","media_type":"..."}`.

Το Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
και το ψευδώνυμο οικογένειας `jina-ai/jina-embeddings-v5-omni` → omni-small) δέχεται επίσης τα εγγενή
έγγραφα EmbeddingsV5Request της Jina και **τα προωθεί αυτούσια** στο `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

Οι εγγενείς τιμές `{ image | audio | video | pdf }` μπορούν να είναι ένα δημόσιο URL HTTPS, ένα URI `data:` ή ακατέργαστα
δεδομένα base64. Το OmniRoute δεν μετατρέπει αυτά τα αντικείμενα σε συμβολοσειρές ούτε ανακτά εγγενή URL εικόνων — η Jina ανακτά
η ίδια τα δημόσια πολυμέσα. Τα πρόσθετα πεδία της Jina (`task`, `normalized`, `truncate`, `embedding_type`)
προωθούνται. Τα SKU της Jina που υποστηρίζουν μόνο κείμενο εξακολουθούν να απορρίπτουν έγγραφα που δεν είναι κείμενο.

Όρια ασφάλειας και μεταφοράς:

- Τα απομακρυσμένα URL πολυμέσων πρέπει να είναι δημόσια HTTPS. Τα κανονικοποιημένα στοιχεία `{type,source:url}` ανακτώνται
  από την πλευρά του διακομιστή (εκ νέου επικύρωση ανακατευθύνσεων, χρονικό όριο, όρια μεγέθους, δημόσιο DNS, καρφίτσωμα σύνδεσης) και
  ενσωματώνονται πριν από την κλήση στον πάροχο. Τα εγγενή στοιχεία Jina `{image:"https://..."}` προωθούνται ως έχουν
  μετά τον ίδιο έλεγχο δημόσιου HTTPS· η Jina ανακτά το URL.
- Τα ενσωματωμένα πολυμέσα base64 περιορίζονται σε 8 MiB αποκωδικοποιημένων δεδομένων ανά στοιχείο και 16 MiB αποκωδικοποιημένων δεδομένων συνολικά για το αίτημα.

Μετάφραση προς τον πάροχο (τα κανονικοποιημένα στοιχεία δεν προωθούνται ποτέ χωρίς μετατροπή):

- Πολυτροπικά μοντέλα Jina: κάθε στοιχείο ανώτατου επιπέδου μετατρέπεται σε ένα αντικείμενο με κλειδί τρόπου λειτουργίας
  (`text` / `image` / `audio` / `video` / `pdf`), χρησιμοποιώντας URI δεδομένων για ενσωματωμένα πολυμέσα· ένα διάνυσμα ανά
  στοιχείο ανώτατου επιπέδου.
- Οικογένεια Gemini Embedding 2: ένας πίνακας ανώτατου επιπέδου μετατρέπεται σε ένα μοναδικό εγγενές
  αίτημα `models/{model}:embedContent` με `content.parts` (`text` ή `inline_data`).
- llama.cpp (`llama-cpp/<model>`, οποιοδήποτε μοντέλο έχει φορτώσει ο τοπικός διακομιστής): τα κανονικοποιημένα στοιχεία `text`
  μετατρέπονται σε απλές συμβολοσειρές, ενώ τα `image` / `audio` / `video` μετατρέπονται το καθένα σε ένα
  αντικείμενο `{"content": [part]}`, χρησιμοποιώντας τα τμήματα περιεχομένου συνομιλίας του llama-server (`image_url`,
  `input_audio` με μορφή `wav` / `mp3` / `flac`, `input_video`) με ενσωματωμένα δεδομένα· ένα διάνυσμα
  ανά στοιχείο ανώτατου επιπέδου. Ο διακομιστής πρέπει να εκτελείται με `--embedding --mmproj …`· χωρίς προβολέα,
  απορρίπτει ο ίδιος τα πολυμέσα. Το `document` δεν υποστηρίζεται.
- Άγνωστα/δυναμικά μοντέλα χωρίς ρητά μεταδεδομένα τρόπου λειτουργίας απορρίπτουν τη δομημένη είσοδο με HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Οι μη υποστηριζόμενοι συνδυασμοί μοντέλου/τρόπου λειτουργίας επιστρέφουν HTTP 400 αντί να εξαναγκάζουν τη μετατροπή του στοιχείου. Τα πεδία επέκτασης που δεν αφορούν την είσοδο
σε παλαιότερα αιτήματα συμβολοσειρών/token εξακολουθούν να διαβιβάζονται χωρίς αλλαγές.

```bash
# Παράθεση όλων των μοντέλων ενσωματώσεων
GET /v1/embeddings
```

## Δημιουργία εικόνων

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "Ένα όμορφο ηλιοβασίλεμα πάνω από βουνά",
  "size": "1024x1024"
}
```

Οι διαθέσιμοι πάροχοι περιλαμβάνουν τους OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (τοπικό), ComfyUI (τοπικό).

Το `n` επιστρέφει `n` εικόνες στο `data[]`. Για παρόχους των οποίων το upstream API επιστρέφει μία εικόνα ανά κλήση
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), πραγματοποιούνται `n` ξεχωριστές upstream κλήσεις, με έως 4 ταυτόχρονα εκτελούμενες. Ένα
σταθερό `seed` μετατοπίζεται βάσει του δείκτη κλήσης (`seed`, `seed + 1`, …), ώστε οι εικόνες να διαφέρουν αλλά να παραμένουν
αναπαραγώγιμες. Το `n` περιορίζεται σε 10. Το αίτημα αποτυγχάνει συνολικά αν αποτύχει οποιαδήποτε κλήση. Η λίστα
των μορφών fan-out είναι η `SINGLE_IMAGE_FANOUT_FORMATS` στο
`open-sse/handlers/imageGeneration/fanOut.ts`.

Το ZenMux επαναχρησιμοποιεί την υπάρχουσα σύνδεση κλειδιού API και δέχεται τα προθέματα `zenmux/` ή `zm/`:

- Το `zenmux/openai/gpt-image-2` χρησιμοποιεί το OpenAI Images API του ZenMux. Οι επιλογές περιλαμβάνουν τα `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` και `response_format`.
- Άλλοι εκδότες, όπως το `zm/meta/muse-image-1.0`, χρησιμοποιούν το endpoint `:predict` του Vertex AI μέσω του ZenMux.
  Το `n` αντιστοιχίζεται στο `sampleCount`, το `aspect_ratio` στο `aspectRatio` και το `image_size`
  (`1K`, `2K`, `4K`) στο `sampleImageSize`. Μια τιμή `size` σε pixel παρέχει μόνο μια αναλογία διαστάσεων,
  όχι εγγυημένες διαστάσεις σε pixel. Οι υποστηριζόμενες αναλογίες, αναλύσεις και πλήθη διαφέρουν ανά μοντέλο.
- Το `zm/inclusionai/ming-image-0.1-design` επιλέγει τις δικές του διαστάσεις. Παραλείψτε τα `size`,
  `aspect_ratio` και `image_size`· οι ρητές τιμές επιστρέφουν HTTP 400. Μπορούν να ζητηθούν PNG, JPEG και WebP
  με το `output_format`.

Αυτή η ενσωμάτωση υποστηρίζει δημιουργία εικόνας από κείμενο, όχι επεξεργασία εικόνας αναφοράς. Η έξοδος του Vertex
κανονικοποιείται σε `data[].b64_json`· το `response_format: "url"` επιστρέφει ένα upstream
HTTPS URL ή ένα URL δεδομένων base64 όταν είναι διαθέσιμα μόνο τα byte της εικόνας. Οι κενές/φιλτραρισμένες έξοδοι
επιστρέφουν σφάλμα αντί για κενή επιτυχή απόκριση. Η πρόσβαση στα μοντέλα εξαρτάται από τον λογαριασμό ZenMux.
Δείτε το [Vertex API του ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) και το
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Εμφάνιση όλων των μοντέλων εικόνας
GET /v1/images/generations
```

Το `model` επιλέγει τον πάροχο OCR μέσω ενός προθέματος `provider/model`· ένα απλό αναγνωριστικό μοντέλου (π.χ. `mistral-ocr-latest`) επιλύεται στον καταχωρημένο πάροχό του, και αν το `model` παραλειφθεί, προεπιλέγεται το Mistral (`mistral-ocr-latest`). Καταχωρημένοι πάροχοι (`open-sse/config/ocrRegistry.ts`):

| Αναγνωριστικό παρόχου         | Αναγνωριστικό μοντέλου | Τιμή `model`                                               | Σημειώσεις                                                                                                    |
| ----------------------------- | ---------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest`   | `mistral/mistral-ocr-latest` (ή απλό `mistral-ocr-latest`) | Σύγχρονο — η απόκριση επιστρέφεται απευθείας από την ενιαία κλήση upstream.                                   |
| `azure-document-intelligence` | `prebuilt-read`        | `azure-document-intelligence/prebuilt-read`                | Ασύγχρονο upstream (`analyze` + polling) — δείτε παρακάτω.                                                    |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`    | `vertex-deepseek-ocr/deepseek-ocr-maas`                    | Σύγχρονο, μέσω του endpoint συνεργάτη `openapi/chat/completions` του Vertex AI — δείτε παρακάτω για auth/URL. |

Και οι τρεις πάροχοι αποκρίνονται με το ίδιο σώμα σε μορφή Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Ροή polling του Azure Document Intelligence

Το `analyze` API του Azure Document Intelligence είναι ασύγχρονο: το αρχικό αίτημα επιστρέφει μια κεφαλίδα `Operation-Location` αντί για σώμα απόκρισης, και το αποτέλεσμα πρέπει να ανακτηθεί μέσω polling. Ο χειριστής (`open-sse/handlers/ocr.ts`) εκτελεί polling σε αυτό το URL κάθε δευτερόλεπτο για έως 30 προσπάθειες, αποτυγχάνει αμέσως (σταματά το polling) σε μη-`ok` απόκριση polling ή κατάσταση `"failed"`, και επιστρέφει `504` αν η λειτουργία εξακολουθεί να εκτελείται μετά την εξάντληση του προϋπολογισμού προσπαθειών. Η τελική απόκριση Azure κανονικοποιείται στο ίδιο σχήμα `pages`/`markdown` που χρησιμοποιεί το Mistral πριν επιστραφεί στον καλούντα, οπότε ο κώδικας του πελάτη δεν χρειάζεται να χειριστεί τον πάροχο ως ειδική περίπτωση.

### Επίλυση auth και endpoint του Vertex AI DeepSeek OCR

Το `vertex-deepseek-ocr` επαναχρησιμοποιεί την ίδια αυθεντικοποίηση Vertex AI που υποστηρίζει ήδη το OmniRoute για κίνηση chat/εικόνας (`open-sse/executors/vertex.ts`): το κλειδί API της σύνδεσης είναι είτε διαπιστευτήριο JSON Λογαριασμού Υπηρεσίας (που ανταλλάσσεται για ένα βραχύβιο OAuth access token μέσω της ροής JWT-bearer) είτε ένα ήδη εκδοθέν OAuth access token που χρησιμοποιείται ως έχει. Η URL του upstream endpoint είναι το γενικό endpoint συνεργάτη `openapi/chat/completions` του Vertex, που δημιουργείται από το project και την περιοχή της σύνδεσης — ένα ρητό `providerSpecificData.project`/`providerSpecificData.region` υπερισχύει πάντα· διαφορετικά, το project προέρχεται από το `project_id` του JSON Λογαριασμού Υπηρεσίας και η περιοχή προεπιλέγεται σε `us-central1`. Και οι δύο επιλύσεις πραγματοποιούνται στο `open-sse/handlers/ocr.ts` (`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), και καταναλώνονται από το `src/app/api/v1/ocr/route.ts` πριν από την αποστολή στο `handleOcr`.

### Προθέματα αναγνωριστικών μοντέλων (`?prefix=`)

Τα περισσότερα μοντέλα δημοσιεύονται με ένα **πρόθεμα παρόχου**. Το πρόθεμα που λαμβάνετε ελέγχεται από τη
σημαία λειτουργίας `MODELS_CATALOG_PREFIX_MODE` και μπορεί να παρακαμφθεί **ανά αίτημα** με μια
παράμετρο ερωτήματος — χρήσιμο για έναν πελάτη που θέλει μια καθαρή λίστα χωρίς να αλλάξει τη ρύθμιση
σε επίπεδο διακομιστή για όλους τους υπόλοιπους:

```bash
GET /v1/models?prefix=alias        # ένα αναγνωριστικό ανά μοντέλο — το σύντομο πρόθεμα ψευδωνύμου
GET /v1/models?prefix=dual         # και οι δύο μορφές (προεπιλογή διακομιστή)
GET /v1/models?prefix=canonical    # μόνο το πλήρες πρόθεμα αναγνωριστικού παρόχου
```

| Λειτουργία  | Εκπέμπει                                                  | Σημειώσεις                                                                                                                                                                                                                        |
| ----------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **και** `claude/claude-sonnet-4-6` | **Προεπιλογή.** Και τα δύο αναγνωριστικά δρομολογούνται στο ίδιο μοντέλο· διατηρούνται ώστε οι ρυθμίσεις πελατών που έχουν κωδικοποιήσει μόνιμα οποιαδήποτε μορφή να συνεχίσουν να λειτουργούν. Διπλασιάζει περίπου τον κατάλογο. |
| `alias`     | `cc/claude-sonnet-4-6`                                    | Μία καταχώριση ανά μοντέλο. Οι πάροχοι χωρίς διακριτό ψευδώνυμο εξακολουθούν να εκπέμπουν την καταχώρισή τους, επομένως δεν χάνεται τίποτα.                                                                                       |
| `canonical` | `claude/claude-sonnet-4-6`                                | Μία καταχώριση ανά μοντέλο με το πλήρες πρόθεμα αναγνωριστικού παρόχου. Οι πάροχοι χωρίς διακριτό ψευδώνυμο (π.χ. `antigravity/…`, `agy/…`) εκπέμπουν και εδώ το μοναδικό αναγνωριστικό τους, επομένως δεν χάνεται τίποτα.        |

Ένα είδωλο σε λειτουργία `dual` μπορεί επίσης να αναγνωριστεί χωρίς την παράμετρο ερωτήματος: περιέχει ένα πεδίο `parent`
που παραπέμπει στο κύριο αναγνωριστικό.

Οι πελάτες που εμφανίζουν επιλογέα μοντέλου θα πρέπει να ζητούν `?prefix=alias` — αυτό κάνει η
[επέκταση OmniCopilot για VS Code](../guides/VSCODE-COPILOT.md).

### Φίλτρα ανακάλυψης (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

Το `GET /v1/models` δέχεται προαιρετικά φίλτρα ανακάλυψης. Χωρίς κανένα από αυτά, η απόκριση παραμένει
αμετάβλητη. Περιορίζουν τον κατάλογο που ήδη βλέπει ο καλών (τα δικαιώματα κλειδιού API εφαρμόζονται πρώτα)
και εκτελούνται πριν από τη σελιδοποίηση τύπου OpenAI με `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # κάθε αναφερόμενη δυνατότητα πρέπει να είναι αληθής
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` καταλόγου· οι γραμμές χωρίς αυτό θεωρούνται `chat`
GET /v1/models?q=sonnet&limit=10                           # αντιστοίχιση χωρίς διάκριση πεζών-κεφαλαίων στο αναγνωριστικό ή το όνομα
```

| Παράμετρος    | Τιμές                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | μη αρνητικός ακέραιος, συγκρίνεται με το `context_length`                                           |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 χαρακτήρες                                                                                    |

Μια άγνωστη τιμή ή ένα `min_context` που δεν είναι μη αρνητικός ακέραιος (για παράδειγμα `1.5`)
επιστρέφει HTTP `400` και το μήνυμα παραθέτει τις έγκυρες τιμές. Υλοποίηση:
`src/app/api/v1/models/catalogFilters.ts`.

### Σύντομη λίστα μοντέλων (`POST /v1/models/query`)

Το `POST /v1/models/query` επιστρέφει μια σύντομη, ντετερμινιστική λίστα από τον ίδιο κατάλογο, με τον ίδιο
έλεγχο ταυτότητας και την ίδια ορατότητα ανά κλειδί όπως το `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Κάθε πεδίο είναι προαιρετικό. Τα `capabilities` και `exclude` δέχονται έναν πίνακα ή μια συμβολοσειρά διαχωρισμένη με κόμματα·
το `max_output` συγκρίνεται με το `max_output_tokens`. Τα αποτελέσματα ταξινομούνται πρώτα κατά `owned_by` και έπειτα κατά `id`.
Η προεπιλογή του `limit` είναι `20` και οι τιμές άνω του `100` περιορίζονται στο `100`. Μη έγκυρο JSON, ένα άγνωστο
πεδίο ή μια μη έγκυρη τιμή επιστρέφει HTTP `400`.

### Μεμονωμένα κρυφά μοντέλα συνομιλίας

Ένα μοντέλο που έχει επισημανθεί ως **Κρυφό** στη σελίδα του παρόχου του εξαιρείται από τον κατάλογο και απορρίπτεται
με HTTP `404` / `model_not_found` όταν ζητείται ρητά. Ο έλεγχος χρησιμοποιεί τον επιλυμένο
πάροχο και το μοντέλο, συμπεριλαμβανομένων των ψευδωνύμων παρόχου, των προθεμάτων κόμβων συμβατών παρόχων και
των προεπιλογών σύνδεσης. Ένας συνδυασμός παραλείπει τους κρυφούς στόχους και μπορεί να χρησιμοποιήσει ένα ορατό συγγενικό μοντέλο· όταν δεν
απομένει εκτελέσιμος στόχος, επιστρέφει τον ίδιο κωδικό σφάλματος. Η κατάργηση της απόκρυψης τίθεται σε ισχύ στο επόμενο
αίτημα. Οι παρακάμψεις ορατότητας αποκλειστικά για εικόνες δεν αποκρύπτουν το μοντέλο συνομιλίας με το ίδιο αναγνωριστικό.

Αυτή η μεμονωμένη ρύθμιση μοντέλου είναι ξεχωριστή από τις
[λίστες επιτρεπόμενων/αποκλεισμένων μοντέλων](../routing/MODEL_EXPOSURE_LIST.md), οι οποίες φιλτράρουν τη
δημοσίευση του καταλόγου και τους υποψήφιους για αυτόματη δρομολόγηση, διατηρώντας παράλληλα τη ρητή αποστολή. Τα δικαιώματα μοντέλων
ανά κλειδί API εξακολουθούν να εφαρμόζονται ανεξάρτητα. Η προεπιλεγμένη λειτουργία προθέματος καταλόγου παραμένει `dual`.

### Παραλλαγές μοντέλων χωρίς συλλογισμό

Για τα μοντέλα Claude με δυνατότητα συλλογισμού, το `/v1/models` δημοσιεύει επίσης μια παραλλαγή **χωρίς συλλογισμό**, της οποίας το αναγνωριστικό έχει ως πρόθεμα το `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Η επιλογή αυτού του id (π.χ. σε μια διαμόρφωση του Claude Code που επισυνάπτει πάντα ένα μπλοκ `thinking`) αντιστοιχίζεται ξανά στο πραγματικό `<provider>/<model>` με απενεργοποιημένο τον συλλογισμό — `thinking:{type:"disabled"}` στη διαδρομή `/v1/messages` ή με παράλειψη των πεδίων `reasoning`/`reasoning_effort` στη διαδρομή `/v1/chat/completions`. Η παραλλαγή εμφανίζεται μόνο για μοντέλα της οικογένειας Claude που υποστηρίζουν το thinking **και** τηρούν την τιμή `disabled` (επομένως, π.χ. εξαιρούνται μοντέλα που υποστηρίζουν αποκλειστικά προσαρμοστική λειτουργία και απορρίπτουν την τιμή `disabled`). Οι διαχειριστές μπορούν να ενεργοποιήσουν ή να απενεργοποιήσουν αναγκαστικά την παραλλαγή ανά μοντέλο μέσω του `ModelSpec.noThinkingAlias`.

```bash
POST /v1/segment     { "content": "...", "return_chunks": true }

# Αναζήτηση Jina (s.jina.ai· ψευδώνυμα παρόχου: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Έλεγχοι εποπτείας περιεχομένου
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — επιστρέφει σώμα audio/mpeg (ή της ζητούμενης μορφής)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Το Soniox TTS απαιτεί γλώσσα και φωνή: η `language` έχει ως προεπιλογή την τιμή "en"· μια απούσα
# φωνή ή ένα όνομα βασικής φωνής του OpenAI (alloy, nova, …) μετατρέπεται σε "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Επεξεργασία εικόνας (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Κόμβοι παρόχων ανακατάταξης:** Το `POST /v1/rerank` δρομολογείται επίσης σε κόμβους παρόχων συμβατούς με το OpenAI
> (oMLX, vLLM, Infinity, TEI πίσω από μια πύλη, …), οι οποίοι προσδιορίζονται ως `<node-prefix>/<model>`. Οι κόμβοι
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) είναι πάντα επιλέξιμοι, όπως και τα ονόματα κεντρικών υπολογιστών που
> ο διαχειριστής παραθέτει στο `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (π.χ. ένα όνομα υπηρεσίας Docker/Compose όπως
> το `http://reranker:8080/v1`· αυτοί καλούνται απευθείας, ποτέ μέσω του `HTTP(S)_PROXY` ή του
> καρφιτσωμένου διακομιστή μεσολάβησης μιας σύνδεσης). Οι κόμβοι σε οποιονδήποτε άλλο
> κεντρικό υπολογιστή —ένα μηχάνημα LAN ή έναν ομότιμο κόμβο Tailscale— είναι επιλέξιμοι μόνο όταν ο διαχειριστής ενεργοποιεί τη
> σημαία δυνατότητας `RERANK_REMOTE_PROVIDER_NODES` **και** το βασικό URL του κόμβου πληροί την πολιτική
> εξερχόμενων URL του παρόχου (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Το βήμα ανακατάταξης της μηχανής μνήμης καλεί αυτή τη διαδρομή μέσω
> loopback, επομένως ο ίδιος κανόνας διέπει το `rerankProviderModel` στις ρυθμίσεις Μνήμης.
>
> **Μορφές τοπικών διακομιστών:** ο κόμβος καλείται στο `<base>/v1/rerank` και, σε περίπτωση 404, στο `<base>/rerank`
> (Infinity, TEI). Το σώμα του αιτήματος προς τον upstream διακομιστή περιλαμβάνει τόσο την ορθογραφία Cohere/OpenAI (`documents`,
> `return_documents`) όσο και την ορθογραφία TEI (`texts`, `return_text`), ενώ η απόκριση του upstream διακομιστή
> κανονικοποιείται στο περίβλημα Cohere: η γυμνή μορφή `[{index, score, text}]` του TEI, η μορφή `{results: [{index, score}]}`
> από ελαφριές πύλες και η μορφή τύπου Voyage `{data: [...]}` επιστρέφονται όλες στον πελάτη ως
> `{results: [{index, relevance_score, document?}]}`, ταξινομημένες κατά βαθμολογία και περιορισμένες στο `top_n`.
>
> **Εντοπισμός κόμβων παρόχων:** τα μοντέλα σε έναν κόμβο παρόχου συμβατό με το OpenAI εμφανίζονται στο `GET /v1/models`
> κάτω από το πρόθεμα του κόμβου. Οι γραμμές που δεν περιέχουν μεταδεδομένα τελικού σημείου (όπως συμβαίνει συνήθως στις τοπικές καταχωρίσεις `/v1/models`)
> κληρονομούν το `apiType` του κόμβου, επομένως τα μοντέλα ενός κόμβου `embeddings` έχουν `type: "embedding"` και τα
> μοντέλα ενός κόμβου `rerank` έχουν `type: "rerank"` αντί να προεπιλέγονται ως συνομιλία· ένα ρητό
> `supportedEndpoints` σε μια συγχρονισμένη ή μη αυτόματα προστεθειμένη γραμμή εξακολουθεί να υπερισχύει.

### Exa και Tavily `provider_options`

Τα Exa και Tavily διαβάζουν πεδία ειδικά για τον πάροχο από έναν χώρο ονομάτων:
`provider_options.exa` (ή `provider_options["exa-search"]`) και `provider_options.tavily`
(ή `provider_options["tavily-search"]`). Μόνο τα παρακάτω κλειδιά προωθούνται. Καθένα
ελέγχεται βάσει του δικού του σχήματος Zod στο `open-sse/handlers/search/providerOptionsPassthrough.ts`,
και ένα κλειδί λανθασμένου τύπου απορρίπτεται. Κάθε άλλο κλειδί αγνοείται, συμπεριλαμβανομένων των στοιχείων ελέγχου ταυτότητας, του βασικού URL,
των `stream` και `outputSchema`. Τα επίπεδα κλειδιά που χρησιμοποιούνται από άλλους παρόχους (`cx`, `depth`, ...) λειτουργούν
όπως και προηγουμένως.

| Πάροχος | Πεδία ανώτατου επιπέδου                                                                                                                                                                                                                                                                                                                                                   | Ένθετα                                                                                                                                                                          |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (επίπεδες πρωτογενείς τιμές), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                   | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` συγχωνεύονται πάνω από την προεπιλογή `{ text: true, highlights: true }` |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                               |

Τα γενικά πεδία έχουν πάντα προτεραιότητα: `query`, `max_results`, `filters` (τομείς), `country` και το
θέμα που προκύπτει από το `search_type`. Στο Exa, το `search_type: "news"` διατηρεί το `category: "news"`.
Το Tavily δέχεται επίσης `search_type: "finance"` (`topic: "finance"`).

Το γενικό `time_range` μεταβιβάζεται πλέον και στους δύο παρόχους: το Exa λαμβάνει `startPublishedDate` (χρονική
σήμανση ISO) και το Tavily λαμβάνει `start_date` (`YYYY-MM-DD`). Μια ρητή ημερομηνία στο `provider_options`
υπερισχύει της αντιστοιχισμένης.

Τα αποτελέσματα του Exa διατηρούν τα `id`, `highlight_scores`, `summary`, `subpages`, `entities` και `extras` στο
`provider_raw`. Τα αποτελέσματα του Tavily διατηρούν τα `images` και `favicon`.

Η λογιστική κόστους εξακολουθεί να χρησιμοποιεί το επίπεδο μητρώο `costPerQuery`. Το Tavily χρεώνει
το `search_depth: "advanced"` με περισσότερες μονάδες ανά κλήση και αυτή η διαφορά δεν αποτυπώνεται στο
`usage.search_cost_usd`.

## Web Fetch API

Εξαγάγετε περιεχόμενο από ένα URL μέσω ενός διαμορφωμένου παρόχου web-fetch (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Το Parallel Extract (`parallel-search`, ίδιο κλειδί API με το Parallel Search) επιστρέφει μόνο Markdown
— οποιοδήποτε άλλο `format` οδηγεί σε `400` — και περιορίζει το περιεχόμενο στους 100.000 χαρακτήρες. Όταν
η ίδια η σελίδα-στόχος δεν μπορεί να εξαχθεί, η upstream υπηρεσία το αναφέρει μέσα σε HTTP 200·
το OmniRoute το εμφανίζει ως `422` με σταθερό μήνυμα.

| Μέθοδος | Διαδρομή        | Περιγραφή                                                                 |
| ------- | --------------- | ------------------------------------------------------------------------- |
| POST    | `/v1/web/fetch` | Ανάκτηση/σάρωση ενός URL — το σώμα επικυρώνεται από το `v1WebFetchSchema` |

**Έλεγχος ταυτότητας:** Κλειδί API τύπου Bearer (`extractApiKey` + `isValidApiKey`). Η πολιτική επιβάλλεται μέσω του `enforceApiKeyPolicy`.

**Εναλλακτική μετάβαση με επίγνωση ορίων χρήσης (#8297):** όταν δεν παρέχεται ρητά `provider`, η δεξαμενή
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)
διατρέχεται με σταθερή
σειρά προτεραιότητας (fill-first) — ένας διαμορφωμένος πάροχος που υπόκειται σε περιορισμό ρυθμού παρακάμπτεται
αντί να τερματίζεται πρόωρα το αίτημα, ενώ μια επαναλήψιμη αποτυχία upstream ή αποτυχία λόγω ορίου χρήσης
(HTTP 429 πάντοτε· 402/403 για δωρεάν επίπεδα τύπου ορίου χρήσης των Firecrawl/Tavily/TinyFish —
όχι για το Jina Reader και ποτέ για ένα απλό εσφαλμένο αίτημα 400) οδηγεί στον
επόμενο μη δοκιμασμένο πάροχο με διαθέσιμα διαπιστευτήρια κατά τον χρόνο του αιτήματος. Όταν εξαντληθούν όλοι οι πάροχοι στη
δεξαμενή, το endpoint επιστρέφει ένα μόνο `429` (με κεφαλίδα `Retry-After`)
αντί για το προηγούμενο γενικό `400`. Όταν ζητείται ρητά ένα `provider`,
**δεν** πραγματοποιείται σιωπηρή εναλλακτική μετάβαση — ένας ρητά καθορισμένος πάροχος που υπόκειται σε περιορισμό ρυθμού ή αποτυγχάνει
εμφανίζει το δικό του σφάλμα (`429` εάν υπόκειται σε περιορισμό ρυθμού, διαφορετικά την upstream
κατάσταση).

## Ροή WebSocket

```bash
GET /v1/ws?handshake=1
```

Επικυρώνει μια χειραψία αναβάθμισης WebSocket και επιστρέφει τα παραδείγματα μηνυμάτων πρωτοκόλλου wire (`request`, `cancel`). Τα πραγματικά WS frames διαχειρίζεται ο ενσωματωμένος WS server εκτός του πίνακα διαδρομών Next.js.

**Έλεγχος ταυτότητας:** Bearer API key κατά τη χειραψία.

### Responses API μέσω WebSocket (μόνο codex)

```bash
# Ίδιος host:port με το HTTP API (προεπιλογή 20128)· αναβάθμιση της σύνδεσης:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ή: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Το πρώτο frame ΠΡΕΠΕΙ να είναι response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Ένας διακομιστής μεσολάβησης Responses-API-over-WebSocket είναι συνδεδεμένος **αποκλειστικά στο `codex`** (backend
ChatGPT). Ακούει στην ίδια θύρα με το API/dashboard στις διαδρομές `/v1/responses`,
`/responses` και `/api/v1/responses`. Στο πρώτο frame `response.create` εκτελεί
έλεγχο ταυτότητας + προετοιμασία μέσω της εσωτερικής γέφυρας `codex-responses-ws`, επιλέγει μια
σύνδεση codex OAuth και δρομολογεί σε `wss://chatgpt.com/backend-api/codex/responses`
μέσω της μεταφοράς `wreq-js`. **Τα μοντέλα που δεν είναι codex απορρίπτονται** (`codex_ws_provider_required`).
Για δρομολόγηση με κοινή χρήση ορίου χρησιμοποιήστε `model: "qtSd/<group>/codex/<model>"`. Υλοποιείται στα
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Έλεγχος ταυτότητας:** Bearer API key κατά τη χειραψία. Ο ενσωματωμένος HTTP server (`server-ws.mjs`)
πρέπει να είναι το ενεργό σημείο εισόδου (είναι, από προεπιλογή, όταν υπάρχει το `app/server-ws.mjs`).

#### Αναγνωριστικό μοντέλου: χρησιμοποιήστε το ανεπεξέργαστο αναγνωριστικό ChatGPT (χωρίς πρόθεμα `codex/`)

Το **Codex CLI** της OpenAI επικυρώνει το όνομα μοντέλου από την πλευρά του πελάτη όταν
`supports_websockets = true` και **απορρίπτει αναγνωριστικά με πρόθεμα παρόχου** όπως
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Στείλτε το **ανεπεξέργαστο** αναγνωριστικό (π.χ. `gpt-5.5`). Η γέφυρα του OmniRoute είναι
αποκλειστικά codex, οπότε επαναλύει ένα ανεπεξέργαστο αναγνωριστικό ως μοντέλο codex
(`resolveCodexWsModelInfo`) πριν τη δρομολόγηση upstream — ακόμα και αν ένα ανεπεξέργαστο
`gpt-5.5` θα δρομολογούταν διαφορετικά σε άλλον πάροχο μέσω HTTP.

#### Ρύθμιση του OpenAI Codex CLI

Κατευθύνετε το Codex CLI στο OmniRoute προσθέτοντας έναν προσαρμοσμένο πάροχο με υποστήριξη WebSocket
στο `~/.codex/config.toml` (χρησιμοποιήστε ξεχωριστό `CODEX_HOME` για να αποφύγετε την τροποποίηση
υπάρχουσας ρύθμισης):

```toml
model = "gpt-5.5"                 # ανεπεξέργαστο αναγνωριστικό — ΟΧΙ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # χωρίς τελεία κάθετο· το URL του WS προκύπτει αυτόματα (χρησιμοποιήστε https/wss στην παραγωγή)
wire_api = "responses"                    # η μόνη υποστηριζόμενη τιμή από τον Φεβρουάριο 2026
supports_websockets = true                # ενεργοποιεί τη μεταφορά Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # περιέχει το API key του OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ένα API key του OmniRoute (οποιοδήποτε key αν REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

Το CLI αναβαθμίζει το `base_url + /responses` σε WebSocket και το OmniRoute το δρομολογεί
στην επιλεγμένη σύνδεση codex OAuth. Επικυρώθηκε από άκρο σε άκρο έναντι του τοπικού
server: το ChatGPT επιστρέφει `codex.rate_limits` + `response.created` και μεταδίδει
ροή την ολοκλήρωση.

## Χρήση αυτοεξυπηρέτησης (`/api/usage/om-usage`)

Οποιοδήποτε κλειδί API μπορεί να διαβάσει **τη δική του** χρήση και τα δικά του όρια — χωρίς εξουσιοδότηση διαχείρισης. Αυτό είναι το endpoint που χρησιμοποιεί ένας
πελάτης (CLI, ο πίνακας OmniCopilot) για να εμφανίσει σε έναν κάτοχο κλειδιού τις δαπάνες του.

```bash
# Μορφή κειμένου (η ιστορική σύμβαση — απλό κείμενο για τερματικό)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Δομημένη μορφή — αυτή που καταναλώνει ένα UI
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Το κλειδί πρέπει να έχει ενεργοποιημένο το **`allowUsageCommand`** (είναι απενεργοποιημένο από προεπιλογή — ο διαχειριστής κλειδιών API του πίνακα ελέγχου
το εναλλάσσει ανά κλειδί). Χωρίς αυτό, το endpoint απαντά με `403`.

Το `?format=json` επιστρέφει μια διακριτή δομή, ώστε ο καλών να μην επιχειρεί ποτέ να διαβάσει ένα πεδίο δεδομένων από μια
άρνηση. Σε περίπτωση επιτυχίας:

```jsonc
{
  "allowed": true,
  // υπάρχει μόνο όταν το κλειδί έχει επιλέξει όρια χρήσης ανά κλειδί (ημερήσια/εβδομαδιαία USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // το στιγμιότυπο ορίου του επιλεγμένου παρόχου ή null όταν δεν υπάρχει ακόμη τίποτα στην κρυφή μνήμη:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // το στιγμιότυπο κάθε σύνδεσης, ώστε ένα UI να μπορεί να αποδώσει πολλούς παρόχους δίπλα-δίπλα:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Σε περίπτωση άρνησης (`401` λανθασμένο κλειδί / `403` δεν επιτρέπεται), η ίδια διαδρομή επιστρέφει
`{ "allowed": false, "error": { "message": "…" } }` — ένα `personal`/`provider` που υπάρχει αλλά είναι κενό
(το κλειδί επιτρέπεται, αλλά δεν έχει συλλεχθεί ακόμη καμία πληροφορία) αποτελεί διαφορετική κατάσταση από μια άρνηση και μόνο η μορφή JSON
τις διακρίνει.

**Έλεγχος ταυτότητας:** το ίδιο το κλειδί API Bearer του καλούντος, επικυρωμένο με `isValidApiKey` — αυτό _δεν_ είναι η
επιφάνεια διαχείρισης (`/api/keys/…`), η οποία παραμένει προστατευμένη από το `requireManagementAuth`.

### Ανεπεξέργαστα έναντι προσαρμοσμένων βάσει ορίου ποσοστών ποσόστωσης

Κατά την κατανάλωση του `/api/usage/om-usage`, οι καλούντες θα πρέπει να λαμβάνουν υπόψη τη διάκριση μεταξύ των
ποσοστών που παρουσιάζονται στην **έξοδο απλού κειμένου** και στη δομημένη **έξοδο JSON**:

| Πτυχή                  | Μορφή απλού κειμένου (`/api/usage/om-usage` / `@@om-usage`)                                                    | Μορφή JSON (`?format=json`)                                                                            |
| :--------------------- | :------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| **Πεδίο εξόδου**       | `NN% left` (π.χ. `20% left`)                                                                                   | `provider.quotas` / `providers[].quotas`                                                               |
| **Μέτρηση**            | **Χρησιμοποιήσιμο όριο προσαρμοσμένο βάσει cutoff**: υπολειπόμενη χωρητικότητα πάνω από το όριο cutoff         | **Ανεπεξέργαστη upstream ποσόστωση**: μη προσαρμοσμένη μέτρηση του παρόχου                             |
| **Κλιμάκωση cutoff**   | Κλιμακώνεται μέσω του `effectiveRemainingPercent()`, ώστε το προστατευμένο απόθεμα να εμφανίζεται ως `0% left` | Καμία (ανεπεξέργαστες τιμές στιγμιοτύπου όπως αναφέρονται από τον πάροχο)                              |
| **Δεδομένα ορίου**     | Ενσωματώνονται στο εμφανιζόμενο ποσοστό                                                                        | Αποθηκεύονται στο `quotaWindowThresholds` ανά σύνδεση (ή στις προεπιλογές του διακομιστή)              |
| **Κύριος καταναλωτής** | Διαδραστικά CLI, προτροπές τερματικού, ανθρώπινοι χειριστές                                                    | Προγραμματιστικές ενσωματώσεις, πίνακες ελέγχου, αναλυτικά στοιχεία, συστήματα παρακολούθησης χρεώσεων |

#### Ο τύπος προσαρμογής cutoff

Το OmniRoute υποστηρίζει προληπτικά cutoff ποσόστωσης για την αποτροπή της εξάντλησης upstream πόρων (διαμορφώνονται μέσω των
`quotaWindowThresholds` της σύνδεσης, των προεπιλογών του παρόχου ή των καθολικών ρυθμίσεων ανθεκτικότητας). Όταν ένα όριο cutoff
(π.χ. `cutoff = 25%`) είναι ενεργό σε ένα παράθυρο ποσόστωσης, η απόδοση κειμένου υπολογίζει το υπολειπόμενο όριο ως εξής:

- Αν `remaining <= cutoff`: επιστρέφει `0%`.
- Αν `remaining > cutoff`: επιστρέφει `((remaining - cutoff) / (100 - cutoff)) * 100`.

Η μορφοποιημένη έξοδος κειμένου το στρογγυλοποιεί στον πλησιέστερο ακέραιο (`Math.round(...)`).

#### Επεξηγηματικό παράδειγμα

Εξετάστε ένα παράθυρο παρόχου με **60% ανεπεξέργαστη χρήση** (άρα **40% ανεπεξέργαστη υπολειπόμενη ποσόστωση**) και ένα διαμορφωμένο
όριο cutoff **25% υπολειπόμενης ποσόστωσης**:

| Αναπαράσταση                            | Υπολογισμός                                        | Υπολειπόμενο |              Συνεπαγόμενη χρήση               |
| :-------------------------------------- | :------------------------------------------------- | :----------: | :-------------------------------------------: |
| **Ανεπεξέργαστο JSON (`?format=json`)** | Upstream στιγμιότυπο (`quotas[window]`)            |   **40%**    |                    **60%**                    |
| **Μορφή κειμένου (`NN% left`)**         | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |   **20%**    | **80%** (αν υπολογιστεί ως `100 - remaining`) |

- **Γιατί το κείμενο εμφανίζει 20% υπολειπόμενο:** Από το 40% της φυσικής ποσόστωσης που απομένει στον λογαριασμό, το 25% δεσμεύεται από την
  πολιτική cutoff. Ο καλών διαθέτει μόνο 15% από το 75% του χρησιμοποιήσιμου περιθωρίου που απομένει προτού ο δρομολογητής σταματήσει
  να δρομολογεί προς αυτήν τη σύνδεση. Η κλιμάκωση διασφαλίζει ότι η σύνδεση σηματοδοτεί εξάντληση (`0% left`) ακριβώς όταν
  θα διακοπεί η δρομολόγηση.
- **Γιατί το JSON διατηρεί τις ανεπεξέργαστες τιμές:** Το ωφέλιμο φορτίο JSON επιστρέφει το ακριβές στιγμιότυπο παρόχου (`UsageSnapshot`),
  ώστε τα εξωτερικά εργαλεία να έχουν πρόσβαση στην πραγματική upstream χρήση και στα `quotaWindowThresholds`
  σε επίπεδο σύνδεσης, χωρίς απωλεστική κλιμάκωση από την πλευρά του διακομιστή.

#### Οδηγίες μετάβασης για καταναλωτές

Εάν μια εξωτερική ενσωμάτωση (όπως ένα plugin επεξεργαστή ή μια επέκταση πράκτορα) προηγουμένως εξήγαγε δεδομένα από το endpoint κειμένου
(`NN% left`) και υπολόγιζε το ποσοστό χρήσης ως `100 - NN`, η μετάβαση στο `?format=json` σημαίνει ότι:

- Η ανάγνωση των ανεπεξέργαστων τιμών JSON θα αντικατοπτρίζει την **πραγματική upstream κατανάλωση** (60% χρησιμοποιημένο στο παραπάνω παράδειγμα).
- Αν η ενσωμάτωση επιθυμεί να διατηρήσει τη σημασιολογία χρησιμοποιήσιμου ορίου του endpoint κειμένου, μπορεί να υπολογίσει
  τον τύπο του ενεργού υπολοίπου στην πλευρά του πελάτη, χρησιμοποιώντας το `quotaWindowThresholds` για παρακάμψεις σε επίπεδο σύνδεσης.

```json
{
  "semanticCache": {

  },
  "idempotency": {
    "activeKeys": 3,

  }
```

### Επίπτωση στην καθυστέρηση

Μια ΕΠΙΤΥΧΊΑ σημασιολογικής κρυφής μνήμης εξυπηρετεί την απόκριση από την κρυφή μνήμη **χωρίς κλήση upstream**, οπότε η αναφερόμενη `X-OmniRoute-Response-Latency` είναι σχεδόν μηδενική
(ανεξαρτήτως της αρχικής καθυστέρησης upstream). Οι clients που είναι ευαίσθητοι στην καθυστέρηση
(benchmarking, παρακολούθηση p50/p99) θα πρέπει να ελέγχουν την
κεφαλίδα απόκρισης `X-OmniRoute-Cache-Latency`:

| Τιμή        | Σημασία                                                                                       |
| ----------- | --------------------------------------------------------------------------------------------- |
| `synthetic` | Η απόκριση εξυπηρετήθηκε από κρυφή μνήμη· η καθυστέρηση δεν είναι πραγματικός χρόνος upstream |
| _(απούσα)_  | Απόκριση από πραγματική κλήση upstream                                                        |

### Παράκαμψη κρυφής μνήμης ανά κλειδί

Τα API keys μπορούν να εξαιρεθούν από τις αναγνώσεις σημασιολογικής κρυφής μνήμης μέσω του `cacheDefaultMode`:

| Τιμή     | Συμπεριφορά                                                 |
| -------- | ----------------------------------------------------------- |
| `legacy` | Κανονική συμπεριφορά κρυφής μνήμης (προεπιλογή)             |
| `bypass` | Παράλειψη αναζήτησης στην κρυφή μνήμη· πάντα κλήση upstream |

Ορίζεται κατά τη δημιουργία κλειδιού (`POST /api/keys`) ή ενημέρωση (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Παράκαμψη ανά αίτημα

Οποιοδήποτε αίτημα μπορεί να παρακάμψει την κρυφή μνήμη ανεξαρτήτως ρυθμίσεων κλειδιού:

```
X-OmniRoute-No-Cache: true
```

Για συγχρονισμένα/εισαγόμενα μοντέλα, το `PUT /api/provider-models` δέχεται `provider`, `modelId` και
`maxOutputTokenOverride`: ένας θετικός ακέραιος ορίζει το χειροκίνητο όριο tokens εξόδου και το `null`
το καθαρίζει για να επαναφέρει την προεπιλογή. Το `GET /api/provider-models?provider=<provider>` επιστρέφει
αυτές τις τιμές στο `modelOutputOverrides`, συμπεριλαμβανομένων μοντέλων χωρίς γραμμή προσαρμοσμένου
μοντέλου. Η παράκαμψη χρησιμοποιεί τη δυνατότητα χρόνου εκτέλεσης `max_output_tokens` και διατηρείται
μετά από εκ νέου συγχρονισμό μοντέλου. Η σελίδα παρόχου συμβατού με OpenAI προσφέρει τα ίδια στοιχεία
ελέγχου επεξεργασίας/εκκαθάρισης και επισημαίνει μοντέλα με ρητή υποστήριξη όρασης.

Οι προσαρμοσμένοι κόμβοι Chat Completions προσαρμόζουν τις ρητές εξαιρέσεις συλλογισμού στο ανάντη
backend. Μια επιτυχής δοκιμή σύνδεσης επιλέγει αυτόματα στοιχεία ελέγχου προτύπου συνομιλίας για κάθε
ακριβές αναγνωριστικό μοντέλου του οποίου η καταχώρηση `/models` αποδεικνύει μια αναγνωρισμένη τιμή
`owned_by`: `vllm`, `sglang` ή `llamacpp`. Τα διαφανή wrappers συμβατά με OpenAI μπορεί να διατηρούν
την αρχική καταχώρηση μοντέλου μέσα σε ένα ένθετο αντικείμενο `openai`· η ανίχνευση ακολουθεί έως και
τρία τέτοια περιβλήματα. Τα μοντέλα με ελλιπή, άγνωστη ή αντικρουόμενη ιδιοκτησία διατηρούν τη συνήθη
συμπεριφορά OpenAI. Η ανίχνευση επαναχρησιμοποιεί το υπάρχον αίτημα καταλόγου, δεν παράγει tokens
ολοκλήρωσης και ακυρώνεται όταν αλλάζει το τελικό σημείο σύνδεσης.

Για να καθορίσετε τη συμπεριφορά για ένα backend που δεν εκθέτει αυτά τα μεταδεδομένα,
χρησιμοποιήστε το υπάρχον API μερικής ενημέρωσης παρόχου:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Στείλτε αυτό το σώμα με `PUT /api/providers/<connection-id>`. Σε αυτή τη σύνδεση, μια ρητή
προσπάθεια συλλογισμού `none` αποστέλλεται ως `chat_template_kwargs.thinking=false` και
`chat_template_kwargs.enable_thinking=false`. Οι ρητές εγγενείς τιμές προτύπου παραμένουν καθοριστικές,
εκτός εάν ένας κανόνας συλλογισμού από την πλευρά του διακομιστή επιβάλει μια προσπάθεια. Η ρύθμιση ισχύει μόνο όταν μια προσαρμοσμένη
σύνδεση συμβατή με OpenAI αποστέλλει σώμα Chat Completions· τα αιτήματα Responses και οι συνήθεις
πάροχοι διατηρούν την εγγενή μορφή αιτήματός τους. Ορίστε το `reasoningControl` σε `openai` για να επιβάλετε απλή διαβίβαση του OpenAI
`reasoning_effort`, ή παραλείψτε το/ορίστε το σε `null` για να χρησιμοποιήσετε αυτόματη ανίχνευση.

Τα αιτήματα του ταξινομητή αυτόματης λειτουργίας του Claude Code ορίζουν από προεπιλογή την εγγενή σκέψη ως απενεργοποιημένη όταν δεν περιέχουν
ρητά στοιχεία ελέγχου συλλογισμού. Η ανίχνευση χρησιμοποιεί τον δείκτη συστήματος του ταξινομητή σε αιτήματα μορφής Claude,
όχι ονόματα μοντέλων ή όρια ολοκλήρωσης. Τα ρητά στοιχεία ελέγχου σώματος, οι υποστηριζόμενες κεφαλίδες
effort/thinking, οι κανόνες δρομολόγησης και η επιλυθείσα προσπάθεια μοντέλου διατηρούν την υπάρχουσα προτεραιότητά τους. Και τα δύο
στάδια του ταξινομητή διατηρούν τις προτροπές, τα όρια ολοκλήρωσης, τις ακολουθίες διακοπής και τις πραγματικές αποφάσεις αδειών
upstream· το δεύτερο στάδιο μπορεί ακόμη να παράγει τον ζητούμενο ορατό συλλογισμό του ως απλό κείμενο.

### Έκδοση και Κανάλι Έκδοσης

```bash
GET /api/system/version
```

Διαδρομή διαχείρισης μόνο για loopback (έλεγχος ταυτότητας διαχειριστή). Επιστρέφει την τρέχουσα έκδοση, την πιο πρόσφατη δημοσιευμένη έκδοση και την κατάσταση αυτόματης ενημέρωσης. Τα `releaseChannel` και `channels` είναι επαυξητικά πεδία (rail 3.8.54)· το `channel` διατηρεί τη σημασία του — η λειτουργία ανάπτυξης που χρησιμοποιεί ο ενημερωτής του πίνακα ελέγχου (`npm`, `source` ή `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — κανάλι npm του τρέχοντος build: `nightly` για εκδόσεις `-nightly.*`,
  `next` για άλλες προ-εκδόσεις (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` για μια σταθερή έκδοση
  παλαιότερης κύριας γραμμής από το `channels.latest`, διαφορετικά `latest`. Ίδιοι κανόνες με
  το `scripts/release/dist-tag.mjs`, το οποίο επιλέγει το npm dist-tag κατά τη στιγμή της δημοσίευσης.
- `channels` — δημοσιευμένη κορυφή κάθε dist-tag, από το `npm view omniroute dist-tags` (εναλλακτική
  μέσω HTTP του registry), με προσωρινή αποθήκευση με το ίδιο TTL 10 λεπτών όπως το `latest`. Το `latest`
  υπάρχει πάντα (υποχωρεί στο πεδίο `latest`, έπειτα στο `"unavailable"`)· τα `next`, `nightly` και `lts`
  εμφανίζονται μόνο όταν υπάρχει το αντίστοιχο dist-tag. Ένα αίτημα `Cache-Control: no-cache` ανανεώνει
  και τις δύο αναζητήσεις.

Το μοντέλο καναλιών (`latest` = v3 έως την 4.0 GA, `next` = rc, `nightly` = builds του `develop`,
`lts` = διορθώσεις της v3 μετά την 4.0 GA) περιγράφεται στο `docs/ops/RELEASE_STRATEGY.md`.

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Μεταγράψτε αρχεία ήχου χρησιμοποιώντας οποιονδήποτε διαμορφωμένο πάροχο STT. Το πρώτο τμήμα της διαδρομής επιλέγει τον εγγενή πάροχο (`openai/…`, `deepgram/…`). Τα gateways που επανεξάγουν το μοντέλο άλλου προμηθευτή χρησιμοποιούν ένα αναγνωριστικό με προσδιορισμό (`openrouter/deepgram/nova-3`).

**Αίτημα:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Απόκριση:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Παραδείγματα αναγνωριστικών μοντέλου:** `openai/whisper-1` (απαιτεί κλειδί OpenAI), `openrouter/deepgram/nova-3` (απαιτεί κλειδί OpenRouter), `deepgram/nova-3` (απαιτεί εγγενές κλειδί Deepgram). Ένα απλό αίτημα `deepgram/nova-3` **δεν** χρησιμοποιεί το OpenRouter.

**Υποστηριζόμενες μορφές:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Ψευδώνυμα Tokenized VS Code / Χωρίς Επικεφαλίδα

Χρησιμοποιήστε αυτά τα ψευδώνυμα όταν μια ενσωμάτωση δεν μπορεί να εισάγει μια επικεφαλίδα `Authorization` και χρειάζεται το κλειδί API ενσωματωμένο στη βασική διεύθυνση URL.

```bash
# Ψευδώνυμο καταλόγου τύπου OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Ψευδώνυμα συνομιλίας τύπου OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ψευδώνυμα τύπου Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Παράδειγμα:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Σημειώσεις:

- Τα tokenized ψευδώνυμα επαναχρησιμοποιούν τους ίδιους χειριστές με τα `/v1/*` και `/api/tags`· τα σχήματα απόκρισης παραμένουν πανομοιότυπα.
- Προτιμήστε το `Authorization: Bearer ...` όποτε ο πελάτης υποστηρίζει προσαρμοσμένες επικεφαλίδες.
- Τα διακριτικά βάσει URL ενδέχεται να εμφανίζονται σε αρχεία καταγραφής reverse-proxy, ιστορικό προγράμματος περιήγησης και τηλεμετρία εκτός του OmniRoute. Αντιμετωπίστε τα ως επιλογή συμβατότητας και όχι ως προεπιλεγμένη λειτουργία ελέγχου ταυτότητας.

## Προϋπολογισμός

```bash
# Λήψη κατάστασης προϋπολογισμού για όλα τα κλειδιά API
GET /api/usage/budget

# Ορισμός ή ενημέρωση προϋπολογισμού

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **Σημειώσεις σχήματος** (`setBudgetSchema`): Το `apiKeyId` είναι υποχρεωτικό· τουλάχιστον ένα από τα `dailyLimitUsd`, `weeklyLimitUsd` ή `monthlyLimitUsd` πρέπει να είναι μεγαλύτερο από μηδέν. Προαιρετικά πεδία: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Το παλαιό σχήμα `{keyId, limit, period}` επιστρέφει `400 Bad Request`.

## Όρια Token

Προϋπολογισμοί **token** ανά κλειδί API (διαφορετικοί από τον παραπάνω προϋπολογισμό σε USD). Επιβάλλονται ενσωματωμένα στη διαδρομή αιτήματος: όταν η χρήση του τρέχοντος παραθύρου ενός κλειδιού φτάσει το όριό του, τα αιτήματα απορρίπτονται με `429 Too Many Requests`. Τα όρια μπορούν να εφαρμοστούν σε συγκεκριμένο `model`, σε `provider`, ή `global`α σε ολόκληρο το κλειδί· όταν πολλά όρια ταιριάζουν σε ένα αίτημα, ισχύει το πιο περιοριστικό.

```bash
# Λίστα ορίων token ενός κλειδιού (περιλαμβάνει την τρέχουσα χρήση παραθύρου)
GET /api/usage/token-limits?apiKeyId=key-123

# Δημιουργία ή ενημέρωση ορίου token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Διαγραφή ορίου token με βάση το id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Σημειώσεις σχήματος** (`setTokenLimitSchema`): Τα `apiKeyId` και `scopeType` (`model` | `provider` | `global`) είναι υποχρεωτικά. Το `scopeValue` είναι υποχρεωτικό εκτός αν το `scopeType` είναι `global` (π.χ. ένα model id για το εύρος `model`, ένα provider id για το εύρος `provider`). Το `tokenLimit` πρέπει να είναι θετικός ακέραιος (μετατρέπεται αυτόματα από string). Προαιρετικά: `id` (παράλειψη για δημιουργία, παροχή για ενημέρωση), `resetInterval` (`daily` | `weekly` | `monthly`, προεπιλογή `monthly`), `resetTime` (`HH:MM`), `enabled` (προεπιλογή `true`). Οι αποκρίσεις `GET` εμπλουτίζουν κάθε όριο με `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` και `nextResetAt`. Πρόκειται για endpoint διαχείρισης (η αυθεντικοποίηση επιβάλλεται κεντρικά από το pipeline authz).

## Επεξεργασία Αιτήματος

1. Ο client αποστέλλει αίτημα στο `/v1/*`
2. Ο handler διαδρομής καλεί `handleChat`, `handleEmbedding`, `handleAudioTranscription` ή `handleImageGeneration`
3. Το μοντέλο επιλύεται (απευθείας provider/model ή alias/combo)
4. Τα διαπιστευτήρια επιλέγονται από την τοπική βάση δεδομένων με φιλτράρισμα διαθεσιμότητας λογαριασμού
5. Για chat: το `handleChatCore` ελέγχει τη σημασιολογική/υπογραφής κρυφή μνήμη και επιλύει τις ρυθμίσεις συμπίεσης combo
6. Η προληπτική συμπίεση εκτελείται πριν τη μετάφραση provider όταν είναι ενεργοποιημένη (`lite`, Caveman, RTK ή σε στοίβα)
7. Ο εκτελεστής provider αποστέλλει το upstream αίτημα
8. Η απόκριση μεταφράζεται πίσω στη μορφή client (chat) ή επιστρέφεται αυτούσια (embeddings/images/audio)
9. Καταγράφονται η χρήση, τα αναλυτικά συμπίεσης και τα αρχεία καταγραφής αιτημάτων
10. Το fallback εφαρμόζεται σε σφάλματα σύμφωνα με τους κανόνες combo

Πλήρης αναφορά αρχιτεκτονικής: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Ανθεκτικότητα (εκτεταμένη)

Το OmniRoute εκθέτει τρεις ανεξάρτητους μηχανισμούς προσωρινών αστοχιών· τα παρακάτω endpoints διαχείρισης επιτρέπουν στους χειριστές να τους διαβάζουν και να τους παρακάμπτουν:

| Εύρος                | Αποθήκευση κατάστασης                     | Ανάγνωση                                  | Επαναφορά / εκκαθάριση                                   |
| -------------------- | ----------------------------------------- | ----------------------------------------- | -------------------------------------------------------- |
| Breaker παρόχου      | `domain_circuit_breakers` + στη μνήμη     | `/api/monitoring/health`                  | `POST /api/resilience/reset`                             |
| Αναμονή σύνδεσης     | `rateLimitedUntil` στις συνδέσεις παρόχων | `/api/rate-limits`, `/api/providers/[id]` | (επανενεργοποιείται οκνηρά· εκκαθάριση μέσω PUT παρόχου) |
| Αποκλεισμός μοντέλου | Μητρώο διαθεσιμότητας μοντέλων στη μνήμη  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                 |

Το `PATCH /api/resilience` δέχεται παρακάμψεις breaker παρόχου κάτω από τα `providerBreaker.oauth` και `providerBreaker.apikey`. Κάθε προφίλ υποστηρίζει `degradationThreshold`, `failureThreshold` και `resetTimeoutMs`· τα ίδια πεδία εκτίθενται στο Πίνακας ελέγχου → Ρυθμίσεις → Ανθεκτικότητα.

```bash
# Εκκαθάριση ενός μεμονωμένου αποκλεισμού μοντέλου
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Διαγραφή όλων των αποκλεισμών
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Πλήρης εννοιολογική αναφορά και προεπιλογές breaker: δείτε [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" και [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Ουρά Rate-Limit & Δίχτυ Ασφαλείας Αυτόματης Ενεργοποίησης

- **Υποστηριζόμενη διαδρομή εγγραφής**: Το `POST /api/rate-limits` με σώμα `{"connectionId": "<id>", "enabled": true|false}` είναι το υποστηριζόμενο endpoint διαχείρισης για την εναλλαγή της προστασίας rate-limit μιας σύνδεσης. Το `PUT /api/providers/[id]` σκόπιμα δεν τροποποιεί ούτε αντιστρέφει το `rateLimitProtection` (#11278).
- **Σημασιολογία του `enabled: false`**: Η ρύθμιση `enabled: false` αφαιρεί τη ρητή προστασία για τη σύνδεση, αλλά **δεν** εξαιρεί μια ενεργή σύνδεση API-key από το καθολικό δίχτυ ασφαλείας αυτόματης ενεργοποίησης (`autoEnableApiKeyProviders = true`). Στην `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), τα `false` και `undefined` είναι ισοδύναμα· οι ενεργές συνδέσεις API-key χωρίς ρητή προστασία παραμένουν προστατευμένες υπό το δίχτυ ασφαλείας αυτόματης ενεργοποίησης.
- **Καθολική απενεργοποίηση**: Για να εκτελείτε συνδέσεις API-key χωρίς ουρές rate-limit, απενεργοποιήστε το δίχτυ ασφαλείας καθολικά μέσω `RATE_LIMIT_AUTO_ENABLE=false` (μεταβλητή περιβάλλοντος) ή `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Ρυθμίσεις → Ανθεκτικότητα / `PATCH /api/resilience`).

## MCP Server

Το OmniRoute διαθέτει ενσωματωμένο διακομιστή Model Context Protocol με 3 μεταφορές (stdio, SSE, streamable-http) και εργαλεία περιορισμένης εμβέλειας. Τα παρακάτω endpoints του πίνακα ελέγχου διαβάζουν δεδομένα κατάστασης/ελέγχου και δρομολογούν διαμέσου των μεταφορών HTTP.

| Μέθοδος | Διαδρομή | Περιγραφή |
| ------- | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Παλμός, μεταφορά, κατάσταση σύνδεσης, τελευταία κλήση, κορυφαία εργαλεία, ποσοστό επιτυχίας 24ώρου |
| GET | `/api/mcp/tools` | Λίστα εργαλείων MCP με `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Άνοιγμα ροής SSE για τη μεταφορά SSE (επιστρέφει `503` εάν το MCP είναι απενεργοποιημένο ή υπάρχει αναντιστοιχία μεταφοράς) |
| POST | `/api/mcp/sse` | Αποστολή πλαισίου JSON-RPC μέσω της μεταφοράς SSE |
| GET | `/api/mcp/stream` | Άνοιγμα της πλευράς SSE της μεταφοράς Streamable HTTP (μηνύματα που εκκινούνται από τον διακομιστή) |
| POST | `/api/mcp/stream` | Αποστολή πλαισίου JSON-RPC μέσω της μεταφοράς Streamable HTTP |
| DELETE | `/api/mcp/stream` | Τερματισμός συνεδρίας Streamable HTTP |
| GET | `/api/mcp/audit` | Αναζήτηση στο αρχείο καταγραφής ελέγχου — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Συγκεντρωτικά στατιστικά ελέγχου (σύνολα, ποσοστό επιτυχίας, μέση διάρκεια, κορυφαία εργαλεία) |

**Αυθεντικοποίηση:** οι μεταφορές `sse`/`stream` τηρούν την επιφάνεια αυθεντικοποίησης ειδικά για το MCP (κλειδί API τύπου Bearer με εμβέλεια `mcp`)· οι διαδρομές `status`/`tools`/`audit*` είναι αναγνώσιμες από τον πίνακα ελέγχου (δεν απαιτείται πρόσθετη αυθεντικοποίηση πέραν της πρόσβασης στον κεντρικό υπολογιστή του πίνακα ελέγχου).

> Και οι δύο μεταφορές HTTP ελέγχονται από τις παραμέτρους `settings.mcpEnabled` και `settings.mcpTransport` — αναντιστοιχία μεταφοράς επιστρέφει `400`, ενώ απενεργοποιημένη κατάσταση MCP επιστρέφει `503`.

## A2A Server

Το OmniRoute παρέχει ένα A2A (Agent-to-Agent) JSON-RPC 2.0 endpoint καθώς και ένα REST wrapper για επιθεώρηση/χρήση από το dashboard.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # προαιρετικό εκτός αν το OMNIROUTE_API_KEY είναι ορισμένο
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Υποστηριζόμενες μέθοδοι (όλες ελεγχόμενες από το `settings.a2aEnabled`):

| Μέθοδος          | Περιγραφή                                                         |
| ---------------- | ----------------------------------------------------------------- |
| `message/send`   | Σύγχρονη εκτέλεση skill· επιστρέφει `{task, artifacts, metadata}` |
| `message/stream` | Streaming SSE εκτέλεση του ίδιου συνόλου skill                    |
| `tasks/get`      | Ανάκτηση εργασίας βάσει `taskId`                                  |
| `tasks/cancel`   | Ακύρωση εργασίας βάσει `taskId`                                   |

Ενσωματωμένα skills: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agent Card

```bash
GET /.well-known/agent.json
```

Επιστρέφει το δημόσιο A2A agent card (όνομα, περιγραφή, δυνατότητες, κατάλογος skill, σχήμα αυθεντικοποίησης) — αποθηκεύεται δημόσια στην cache για 1 ώρα. Δεν απαιτείται αυθεντικοποίηση.

### REST βοηθητικά endpoints

| Μέθοδος | Διαδρομή                     | Περιγραφή                                                                                                           |
| ------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET     | `/api/a2a/status`            | Κατάσταση ενεργοποίησης A2A + στατιστικά εργασιών + σύνοψη agent card από cache                                     |
| GET     | `/api/a2a/tasks`             | Λίστα εργασιών — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST    | `/api/a2a/tasks`             | (Δεν υλοποιείται ως REST helper — δημιουργία μέσω JSON-RPC `message/send`)                                          |
| GET     | `/api/a2a/tasks/[id]`        | Ανάκτηση μίας εργασίας                                                                                              |
| POST    | `/api/a2a/tasks/[id]/cancel` | Ακύρωση εργασίας                                                                                                    |

**Αυθεντικοποίηση:** τα REST βοηθητικά endpoints λειτουργούν χωρίς αυθεντικοποίηση διαχείρισης (ανάγνωση από dashboard)· η διαδρομή JSON-RPC `/a2a` χρησιμοποιεί Bearer `OMNIROUTE_API_KEY` εφόσον έχει ρυθμιστεί.

## Αυθεντικοποίηση

Δείτε [Αυθεντικοποίηση Διαχείρισης](../guides/MANAGEMENT-AUTH.md) για τις τέσσερις
οικογένειες διαπιστευτηρίων (συνεδρία dashboard, τοπικό CLI token, `oma_live_…` Access
Token, API key με εύρος manage) και τον τρόπο που διαφέρουν από τα κλειδιά inference.

- Οι διαδρομές Dashboard (`/dashboard/*`) χρησιμοποιούν cookie `auth_token`
- Η σύνδεση χρησιμοποιεί αποθηκευμένο hash κωδικού πρόσβασης· εναλλακτικά το `INITIAL_PASSWORD`
- Το `requireLogin` εναλλάσσεται μέσω `/api/settings/require-login`
- Οι διαδρομές `/v1/*` απαιτούν προαιρετικά Bearer API key όταν `REQUIRE_API_KEY=true`
- Ο όρος «management token» / «management-scoped API key» σε αυτή την αναφορά σημαίνει μία από τις οικογένειες που περιγράφονται στον οδηγό — όχι κάποιον απροσδιόριστο επιπλέον τύπο μυστικού

> **Αλλαγή που διακόπτει συμβατότητα (v3.8.0)** — Τα `/api/v1/agents/tasks/*` και τα endpoints διαχείρισης cooldown απαιτούν πλέον **auth διαχείρισης** (cookie `auth_token` dashboard ή API key με εύρος management). Οι πελάτες που καλούσαν προηγουμένως αυτές τις διαδρομές χωρίς αυθεντικοποίηση θα λαμβάνουν `401 Unauthorized`. Δείτε commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
