Το αυτοφιλοξενούμενο pool εκτελείται στο μηχάνημα **.113** (`tomni-proxmox-113`). Από τις 2026-10-18, κάθε
runner του OmniRoute έχει **έναν ρόλο**, μία ετικέτα και έναν προϋπολογισμό μνήμης/CPU προσαρμοσμένο στις μετρημένες
απαιτήσεις του φόρτου εργασίας του. Η υποδοχή Turbopack λαμβάνει τους πόρους που χρειάζεται το build· οι υπόλοιπες υποδοχές διαστασιολογούνται σύμφωνα με τις
μετρημένες μέγιστες τιμές τους. Το μηχάνημα υπερδεσμεύει πόρους μόνο όταν ένα build Turbopack συμπίπτει με ένα build webpack
του Release-Green και μια εργασία lint· το swap του host (16 GB) απορροφά αυτή την επιβάρυνση και, επειδή τα Builds των pull request εκτελούνται
σε φιλοξενούμενους runners, η υποδοχή Turbopack παραμένει αδρανής τις περισσότερες φορές:

| runner               | ετικέτα              | ρόλος                                                                                                                                                 | `MemoryHigh` / `MemoryMax` | `CPUQuota`   |
| -------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | ------------ |
| `omniroute-113-5`    | `omni-build`         | Builds Turbopack: `ci.yml` `Build` (μόνο push/dispatch), Docker amd64, `npm-publish`, `nightly-v4-build`, `preview-artifact`, το νυχτερινό build a11y | 56 GB / 60 GB (swap 0)     | 1600 %       |
| `omniroute-113-6`    | `omni-release`       | Release-Green (`release-green` + `main-green`), build webpack                                                                                         | 20 GB / 24 GB (swap 4 GB)  | 800 %        |
| `omniroute-113-2`    | `omni-light`         | νυχτερινές εργασίες (Schemathesis, promptfoo, garak, k6) και `quality.yml` `lint-guard`                                                               | 12 GB / 16 GB (swap 4 GB)  | 600 %        |
| `omniroute-113`      | `omni-light`         | ίδιο pool με το παραπάνω                                                                                                                              | 8 GB / 12 GB               | 400 %        |
| OmniHeuris, OmniMind | (τα αποθετήριά τους) | μόνο Dependabot (μέγιστη τιμή 155 MB έκαστο, 2026-10-18)                                                                                              | 4 GB / 6 GB                | 200 % έκαστο |

Τα όρια βρίσκονται στο `/etc/systemd/system/actions.runner.<…>.service.d/override.conf` κάθε μονάδας
(οι προηγούμενες τιμές διατηρούνται ως `override.conf.bak-20261018`) και εφαρμόστηκαν ενώ το σύστημα βρισκόταν σε λειτουργία με
`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` — χωρίς επανεκκίνηση, επομένως δεν
επηρεάστηκε καμία εργασία που εκτελούνταν. Οι ετικέτες αλλάζουν μέσω του API των runners (`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`), επίσης ενώ το σύστημα βρίσκεται σε λειτουργία.

## Εγκατάσταση του προγράμματος καθαρισμού (μία φορά, στο μηχάνημα)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): κάθε 30 λεπτά, καταγραφή στο /var/log/runner-janitor.log
*/30 * * * * MAX_ACTIVE_RUNNERS=8 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

Το `lsof` είναι απαραίτητο: το πρόγραμμα καθαρισμού επιβεβαιώνει ότι μια διαδρομή είναι ανενεργή μέσω ενός στιγμιότυπου των ανοιχτών
αρχείων πριν την αφαιρέσει και, χωρίς αυτό το εργαλείο, δεν αφαιρεί τίποτα και το αναφέρει
(exit 1). Δοκιμάστε πρώτα κάθε αλλαγή με `--dry-run` — εμφανίζει ακριβώς τι θα έκανε
χωρίς να τροποποιήσει τίποτα.

Τι κάνει σε κάθε εκτέλεση: καθαρίζει τα δικά μας υπολείμματα (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) μετά από **3 ώρες στο tmpfs** και 24 ώρες στο
`_work/_temp` του δίσκου· τερματίζει ένα `next-build` παλαιότερο από 75 λεπτά (καμία εργασία δεν εκτελείται τόσο πολύ — στις
2026-08-27 μία εκτελούνταν επί 70 λεπτά αφότου το GitHub είχε δηλώσει την εργασία της χαμένη)· διαγράφει αντίγραφα εργασίας παλαιότερα των 48 ωρών
από runners των οποίων η μονάδα είναι **σταματημένη**· ειδοποιεί όταν η χρήση δίσκου είναι ≥ 85 %, το PSI μνήμης
`full/avg60` είναι ≥ 10 % και οι listeners είναι περισσότεροι από το `MAX_ACTIVE_RUNNERS` (με
ανάλυση σε omniroute/λοιπούς). Exit 1 = απαιτείται προσοχή· διαβάστε το αρχείο καταγραφής.

Ο κανόνας των 75 λεπτών δεν εντοπίζει ένα build του οποίου την εργασία το GitHub έχει ήδη εγκαταλείψει. Όταν το
`Runner.Listener` δεν μπορεί να ανανεώσει την εργασία του, το `_diag/Runner_*.log` εμφανίζει
`POST request to …/renewjob timed out after 100 seconds`, το API αναφέρει την εργασία ως `completed`
(αποτυχία) περίπου δέκα λεπτά μετά την τελευταία επιτυχημένη ανανέωση και το `next-build` συνεχίζει να εκτελείται
χωρίς συνδεδεμένη εργασία (2026-10-18: το Build του #17066 σημειώθηκε ως αποτυχημένο στις 19:43 και το build του εξακολουθούσε
να δεσμεύει 40 GB πέντε λεπτά αργότερα). Επιβεβαιώστε το ref στο νεότερο `_diag/Worker_*.log` και έπειτα
στείλτε SIGTERM μόνο στο δέντρο διεργασιών του build βάσει PID — `next-build`, `npm run build`, `build-next-isolated.mjs` και
στις διεργασίες worker του `_work`. Μην πειράζετε ποτέ τα `Runner.Listener`, `RunnerService.js` ή `Runner.Worker`: το
worker αναφέρει την εργασία ως ακυρωμένη και το listener επανέρχεται online από μόνο του.

## Μονάδες runner: KillMode

Η προεπιλεγμένη ρύθμιση `KillMode=process` του runner αφήνει τα `Runner.Worker → npm → next-build`
ενεργά όταν μια μονάδα σταματά ή επανεκκινείται — ένα ορφανό build συνεχίζει να καταναλώνει RAM και
CPU χωρίς συνδεδεμένη εργασία. Κάθε μονάδα OmniRoute διαθέτει ένα drop-in
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
με `KillMode=mixed`: SIGTERM πρώτα στο listener και έπειτα SIGKILL σε ολόκληρο το cgroup κατά το
`TimeoutStop`. Ενεργοποιείται στην επόμενη επανεκκίνηση της μονάδας — επανεκκινείτε **έναν runner κάθε
φορά, μόνο όταν είναι ανενεργός**, με τον έλεγχο αδράνειας και την επανεκκίνηση στην ίδια εντολή.

## Κανόνες λειτουργίας

- **Μία μεταγλώττιση Turbopack κάθε φορά — επιβάλλεται μέσω ετικέτας.** Κάθε εργασία που εκτελεί ένα πλήρες
  `next build` με Turbopack στοχεύει το `[self-hosted, omni-build]`, και μόνο το **`omniroute-113-5`** φέρει αυτήν
  την ετικέτα: `ci.yml` `Build`, `npm-publish.yml` `publish`, `nightly-v4-build`, `preview-artifact`,
  η νυχτερινή μεταγλώττιση a11y (#16853) και το **amd64** του `docker-publish.yml` (webpack μέσα στο BuildKit —
  το Turbopack κατέρρευσε εκεί, εκτέλεση 33253576569). Το σκέλος arm64 του Docker παραμένει στο `ubuntu-24.04-arm`.
  Το amd64 του `docker-publish` μοιράζεται την ομάδα ταυτοχρονισμού `heavy-build-main` με το `Build` του `ci.yml`
  (`cancel-in-progress: false`). Το Docker Engine πρέπει να βρίσκεται στο `omniroute-113-5`. Μια δεύτερη θέση Turbopack
  δεν χωρά στα 78 GB (2 × 33–37 GB συν τα υπόλοιπα φορτία του μηχανήματος)· μια δεύτερη θέση είναι ασφαλής μόνο για
  μεταγλωττίσεις webpack.
- **Οι μεταγλωττίσεις αιτημάτων ενσωμάτωσης εκτελούνται σε φιλοξενούμενους runners (2026-10-18).** Το `Build` του `ci.yml` φτάνει στο `omni-build` μόνο για
  `push` και `workflow_dispatch`· κάθε `Build` για `pull_request` (από το ίδιο αποθετήριο ή από fork) και `merge_group`
  εκτελείται στο `ubuntu-latest` με webpack. Όταν κάθε PR από το ίδιο αποθετήριο δρομολογούνταν στη θέση, μια μεταγλώττιση Turbopack
  την καταλάμβανε για 29–58 λεπτά, 18 μεταγλωττίσεις περίμεναν στην ουρά έως και 18 ώρες, και η μεταγλώττιση push της ίδιας
  της γραμμής έκδοσης έλαβε τη θέση μία φορά σε 40 εργασίες. Στον φιλοξενούμενο runner, η ίδια μεταγλώττιση PR διαρκεί 8–12 λεπτά παράλληλα με τις άλλες
  εργασίες του PR. Το Turbopack, δηλαδή ο bundler που διανέμει το `npm-publish`, συνεχίζει να δοκιμάζεται στη γραμμή έκδοσης από τη
  νυχτερινή μεταγλώττιση a11y του προεπιλεγμένου κλάδου (04:41 UTC), από κάθε μεταγλώττιση push ή dispatch που
  φτάνει στη θέση και από το ίδιο το `npm-publish`. Το `tests/unit/build/heavy-build-queue.test.ts`
  κατοχυρώνει την πύλη τεσσάρων συνθηκών.
- **Μην ορίζετε ποτέ τη θέση Turbopack κάτω από τις μετρημένες ανάγκες της.** Στις 2026-10-18 στις 18:06 η θέση
  μειώθηκε από 56G/60G σε 40G/44G, ώστε να δημιουργηθεί χώρος για το `omni-release`. Η φάση μεταγλώττισης παρέμεινε στο
  `MemoryHigh` καθ’ όλη τη διάρκεια της εκτέλεσης (memory PSI `full` 30–43 %), και το `Runner.Listener`, το οποίο
  μοιράζεται το cgroup, δεν μπορούσε να ανανεώσει την εργασία του. Τα 56G/60G του ιδιοκτήτη από τις 2026-10-17 επαναφέρθηκαν την
  ίδια ημέρα. Κάτω από αυτήν την τιμή η μεταγλώττιση δεν αποτυγχάνει· οδηγείται σε υπερβολικό thrashing και η εργασία χάνεται.
- **Το Release-Green έχει τη δική του θέση (2026-10-18).** Μέχρι τότε, και οι δύο επικυρώσεις Release-Green εκτελούνταν
  στο `omni-build`: σε κάθε push (~10/ώρα, 97 από τις 100 εκτελέσεις push ακυρώθηκαν ενώ βρίσκονταν σε εξέλιξη μέσα σε μία ημέρα)
  και σε τρεις πλήρεις σαρώσεις διάρκειας ~2 ωρών την ημέρα (η σάρωση των 05:29 περίμενε 6 ώρες για τη θέση) — η μοναδική θέση
  μεταγλώττισης είχε υπερκαλυφθεί πολλές φορές και οι μεταγλωττίσεις PR από το ίδιο αποθετήριο περίμεναν επί ώρες.
  Τα `release-green` και `main-green` στοχεύουν πλέον το `omni-release` (μόνο το `omniroute-113-6`) με
  `OMNIROUTE_USE_TURBOPACK=0`, και μια εκτέλεση που έχει ξεκινήσει δεν ακυρώνεται πλέον από ένα νεότερο push (η
  εκκρεμής θέση εξακολουθεί να συμπτύσσει την καταιγίδα αιτημάτων). Το `tests/unit/build/runner-capacity-routing.test.ts`
  κατοχυρώνει τη δρομολόγηση, τη μετάβαση σε webpack και το ότι τίποτα στο `omni-release` δεν μεταγλωττίζεται με Turbopack.
- **Ελαφριά ομάδα: `omni-light`.** Τα `omniroute-113` και `omniroute-113-2` εκτελούν τις νυχτερινές εργασίες που χρειάζονται
  ένα `next build` μόνο για το backend (~5–6 GB· webpack), καθώς και το `lint-guard` του `quality.yml`. Το `omniroute-113`
  είχε `MemoryHigh=4G` έως τις 2026-10-18 — η μεταγλώττιση promptfoo προχωρούσε με ανακτήσεις μνήμης επί 54 λεπτά
  εκεί· τα 8 GB εξαλείφουν τον περιορισμό απόδοσης.
- **Λιγότεροι listeners, σκόπιμα.** Τέσσερις μονάδες OmniRoute απενεργοποιήθηκαν στις 2026-08-29 — κάθε επιπλέον
  listener είναι ένας ακόμη ένοικος για τον παραπάνω προϋπολογισμό μνήμης. Το ανώτατο όριο του janitor είναι 8 (`MAX_ACTIVE_RUNNERS=8` στο cron): μετρά
  κάθε `Runner.Listener` στο μηχάνημα, ενώ τα OmniHeuris + OmniMind προσθέτουν δύο στα δικά μας πέντε.
- **Οι εργασίες Unit και Vitest παραμένουν σε φιλοξενούμενους runners.** Το `ci.yml` στέλνει τα unit shards και την εργασία Vitest στο
  `[self-hosted, omni-ci]` μόνο όταν η μεταβλητή αποθετηρίου `vars.USE_VPS_TEST_RUNNER` είναι
  `true`, και τότε μόνο για εκτελέσεις `pull_request` από το ίδιο αποθετήριο· τα forks, το `merge_group` και τα push
  παραμένουν στο `ubuntu-latest` (`tests/unit/vps-runner-variable-scope.test.ts`). Η μεταβλητή είναι
  `false`. Στις 2026-10-28 τρεις listeners `omni-ci` με 4 πυρήνες χρειάστηκαν 250–270 s για το `npm ci` και κάθε
  unit shard έφτασε το όριο εργασίας των 30 λεπτών, έναντι ~634 s για ένα φιλοξενούμενο shard, με το φορτίο του μηχανήματος
  στο 17–24. Οι listeners διαγράφηκαν. Μην ενεργοποιήσετε ξανά τη μεταβλητή χωρίς listeners διαστασιολογημένους για
  ένα unit shard.
- **Μην καθαρίζετε ποτέ τα `/tmp` ή `_work` χειροκίνητα όσο οποιοσδήποτε runner είναι απασχολημένος.** Ένας
  έλεγχος και κατόπιν διαγραφή με χρονικό κενό μεταξύ των δύο είχε ως αποτέλεσμα μια ενεργή εργασία Build να χάσει τον κατάλογο
  `_work` της στις 2026-08-27. Ο janitor πραγματοποιεί τον έλεγχο και την αφαίρεση σε ένα βήμα·
  αφήστε τον να το κάνει.
- Η διακοπή ενός runner εν μέσω εργασίας ακυρώνει την εργασία (παρατηρήθηκε σε πραγματικές συνθήκες): εκτελέστε `systemctl stop` μόνο
  όταν ο listener του δεν έχει θυγατρική διεργασία `Runner.Worker` — και κάντε το με μία εντολή.
- Τα workflows δεν πρέπει να αποθηκεύουν artefacts στο `/tmp` (βρίσκεται στη RAM). Πραγματοποιήστε τη λήψη στο
  `$RUNNER_TEMP` (στον δίσκο, ανά runner) — το artefact `next-build` των 1.3 GB χρειάστηκε 27–32
  λεπτά για να αποθηκευτεί στο tmpfs και 2 λεπτά για να μεταφορτωθεί από τον δίσκο.
- Το VPS `.15` προορίζεται μόνο για homologation — δεν εκτελεί ποτέ CI runners.

## Φιλοξενούμενος δίαυλος (runners που φιλοξενούνται στο GitHub)

Το αποθετήριο ανήκει στον οργανισμό `cheaper-inference`, στο πρόγραμμα **Team**: **60
ταυτόχρονες φιλοξενούμενες εργασίες**, κοινόχρηστες από κάθε αποθετήριο του οργανισμού, κάθε έλεγχο PR,
κάθε workflow που ενεργοποιείται από push και την προεπιλεγμένη ρύθμιση του CodeQL. Τα παρακάτω στοιχεία μετρήθηκαν στο
πρόγραμμα **Pro** (40 ταυτόχρονες φιλοξενούμενες εργασίες). Μετρήθηκε στις 2026-10-18 κατά τη διάρκεια μιας
εκστρατείας συγχωνεύσεων (~10 συγχωνεύσεις/ώρα στο `release/v3.8.52`): δημιουργήθηκαν **2.500 εκτελέσεις workflow μέσα σε
24 ώρες**, 44 push στον κλάδο μέσα σε 6 ώρες, **106 φιλοξενούμενες εργασίες σε αναμονή**, ενώ οι έλεγχοι PR περίμεναν για
ώρες και τα PR συγχωνεύονταν χωρίς αυτούς. Εννέα workflow ενεργοποιούνταν σε κάθε push προς τον κλάδο:

Το `tests/unit/build/push-storm-diet.test.ts` κατοχυρώνει την ενεργοποίηση μέσω push μόνο για το `main` των `ci.yml` και
`quality.yml`. Παρενέργεια: το Codecov δεν λαμβάνει πλέον μεταφόρτωση βάσης ανά push έκδοσης (το
βήμα είναι ενημερωτικό και χρησιμοποιεί `continue-on-error`)· η πύλη κάλυψης εντός του αποθετηρίου και το σχόλιο στο PR
δεν επηρεάζονται.

**Η επιπλέον αυτοφιλοξενούμενη χωρητικότητα δεν διορθώνει την ουρά φιλοξενούμενων εργασιών.** Το devbox
(`devbox-vm-06-dev002`, 24 vCPU / 54 GB) θα μπορούσε να φιλοξενήσει έναν runner, αλλά οι συνεδρίες των agent διατηρούν ήδη
το φορτίο του στο 20–26, το container του agent δεν διαθέτει δαίμονα Docker και ο κορεσμένος δίαυλος είναι
ο φιλοξενούμενος. Το μηχάνημα `.113` είχε 71 GB ελεύθερα και φορτίο 5–8 την ίδια στιγμή· ο περιορισμός του
είναι ο παραπάνω προϋπολογισμός μνήμης ανά listener (ανώτατο όριο 6 listeners), όχι η CPU. Οι εναπομείναντες μοχλοί
αφορούν τις διαδικασίες: ενσωματώστε τα PR της εκστρατείας μέσω της ουράς του Mergify (`label=queue`, τα batches μοιράζονται
μία εκτέλεση CI `merge_group` αντί για μία εκτέλεση ανά PR συν μία ανά push), περιορίστε τις γλώσσες της
προεπιλεγμένης ρύθμισης του CodeQL και φιλτράρετε το `release-acceptance.yml` βάσει των αρχείων που διαβάζει.
