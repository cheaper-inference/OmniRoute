> **Εν συντομία**: Το OmniRoute χρησιμοποιεί το **SQLite με καταγραφή WAL** ως κύριο χώρο αποθήκευσης, με κρυπτογράφηση **AES-256-GCM** για ευαίσθητα πεδία σε κατάσταση αδράνειας. Αυτός ο οδηγός καλύπτει το σχήμα, τις μετεγκαταστάσεις, τη δημιουργία αντιγράφων ασφαλείας/ανάκτηση και τα επιχειρησιακά εγχειρίδια.

**Πηγές:**

- `src/lib/db/core.ts` — singleton + SCHEMA_SQL (17 βασικοί πίνακες)
- `src/lib/db/migrationRunner.ts` — μετεγκαταστάσεις με εκδόσεις
- `src/lib/db/migrations/` — 167 αρχεία SQL με εκδόσεις
- `src/lib/db/encryption.ts` — βοηθητικές συναρτήσεις κρυπτογράφησης
- `src/lib/db/backup.ts` — εξαγωγή/εισαγωγή αντιγράφων ασφαλείας
- `src/lib/db/healthCheck.ts` — διαγνωστικοί έλεγχοι εύρυθμης λειτουργίας

## Γιατί SQLite;

Το OmniRoute επέλεξε το SQLite αντί για PostgreSQL/MySQL για διάφορους λόγους:

| Παράγοντας              | SQLite                                            | PostgreSQL                                      |
| ----------------------- | ------------------------------------------------- | ----------------------------------------------- |
| **Ανάπτυξη**            | Ενσωματωμένο — χωρίς ξεχωριστό διακομιστή         | Απαιτεί ρύθμιση διακομιστή                      |
| **Κρυπτογράφηση**       | Σε επίπεδο εφαρμογής (AES-256-GCM)                | Ενσωματωμένο TDE                                |
| **Απόδοση**             | Ταχύτερο για μικρούς/μεσαίους φόρτους εργασίας    | Καλύτερο για τεράστιο όγκο ταυτόχρονων εγγραφών |
| **Ταυτοχρονισμός**      | Η λειτουργία WAL επιτρέπει ταυτόχρονες αναγνώσεις | Πλήρες MVCC                                     |
| **Αντίγραφα ασφαλείας** | Αντιγραφή ενός αρχείου                            | `pg_dump` ή στιγμιότυπο συστήματος αρχείων      |
| **Περίπτωση χρήσης**    | Εγκατάσταση ανά χρήστη, ενσωματωμένο              | SaaS πολλαπλών μισθωτών                         |

Για αναπτύξεις **ενός χρήστη και μίας παρουσίας** (η κύρια περίπτωση χρήσης του OmniRoute), το SQLite είναι απλούστερο και ταχύτερο.

### Καταγραφή WAL

Το `core.ts` ανοίγει τη βάση δεδομένων σε **λειτουργία WAL (Write-Ahead Logging)**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

Το WAL επιτρέπει **ταυτόχρονες αναγνώσεις** κατά τη διάρκεια εγγραφών — κάτι σημαντικό για τον πίνακα ελέγχου, ο οποίος εκτελεί ερωτήματα ενώ καταγράφονται αιτήματα.

Το προεπιλεγμένο μέγεθος κρυφής μνήμης είναι **65.536 KiB (64 MiB)**. Το SQLite ερμηνεύει ένα αρνητικό
`cache_size` ως κατά προσέγγιση ανώτατο όριο σε KiB και εκχωρεί σελίδες κατ’ απαίτηση.
Η επιλογή **Ρυθμίσεις > Σύστημα & Αποθήκευση > Μέγεθος κρυφής μνήμης** δέχεται ακέραιες τιμές από **1 έως
1.000.000 KiB**· η αποθήκευση της ρύθμισης την εφαρμόζει στην ενεργή σύνδεση της βάσης δεδομένων,
και το OmniRoute επαναφέρει τη διατηρημένη τιμή κατά την εκκίνηση.

## Θέση βάσης δεδομένων

Το αρχείο SQLite αποθηκεύεται στη θέση:

| Λειτουργικό σύστημα | Διαδρομή                                                      |
| ------------------- | ------------------------------------------------------------- |
| Linux               | `~/.omniroute/storage.sqlite`                                 |
| macOS               | `~/.omniroute/storage.sqlite`                                 |
| Windows             | `%USERPROFILE%\.omniroute\storage.sqlite`                     |
| Docker              | `/app/data/storage.sqlite` (διαμορφώσιμο μέσω του `DATA_DIR`) |

Συνοδευτικά αρχεία:

- `storage.sqlite-wal` — αρχείο καταγραφής προεγγραφής
- `storage.sqlite-shm` — αρχείο κοινόχρηστης μνήμης
- `call_logs/` — τεχνουργήματα ωφέλιμου φορτίου αιτημάτων (εάν είναι ενεργοποιημένα)

**Παράκαμψη της θέσης:**

```bash
DATA_DIR=/custom/path omniroute
```

### Όρια Μονάδων

Ένας βασικός αρχιτεκτονικός κανόνας: **οι μονάδες δεν προσπελαύνουν απευθείας τους πίνακες άλλων μονάδων**. Για να εργαστείτε με τα δεδομένα άλλης μονάδας, εισαγάγετε τη συνάρτηση από εκείνη τη μονάδα.

```ts
// ❌ ΛΑΘΟΣ: απευθείας SQL από άλλη μονάδα
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ΣΩΣΤΟ: χρησιμοποιήστε τη συνάρτηση της μονάδας providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

Αυτός ο κανόνας επιβάλλεται μέσω της ανασκόπησης κώδικα — δεν υπάρχει στατικός έλεγχος, αλλά οι παραβιάσεις επισημαίνονται.

## Μεταναστεύσεις

χρήσεις OmniRoute** εκδόσεις, ανίκανες μεταναστεύσεις** στο `src/lib/db/migrations/`. Κάθε μετεγκατάσταση είναι ένα μόνο αρχείο SQL. Συνυπάρχουν δύο μορφές ονομασίας. η έκδοση που καταγράφεται στο `_omniroute_migrations` είναι το αριθμητικό πρόθεμα.

### Ονομασία μετανάστευσης

| Σχήμα και διάταξις βιβλίου                       | Παράδειγμα                           | Χρησιμοποιείται για                                                                                                                                                                           |
| ------------------------------------------------ | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (ακριβώς 3 ψηφία)          | `241_seen_models.sql`                | Η παλιά σειρά `001`–`241`. Παγώθηκε όταν προσγειώθηκε η μορφή της χρονικής σφραγίδας (`240` και `241` συγχωνεύτηκαν ακριβώς πριν από αυτήν): κανένα νέο αρχείο δεν λαμβάνει διαδοχικό αριθμό. |
| `YYYYMMDDHHMMSS_description.sql` (14 ψηφία, UTC) | `20261113120000_add_usage_index.sql` | Κάθε μετανάστευση που δημιουργήθηκε από το 2026-11-13 και μετά.                                                                                                                               |

Γιατί η αλλαγή: με τους διαδοχικούς αριθμούς, ο παράλληλος PRs επέλεξε τον ίδιο επόμενο αριθμό και όλοι εκτός από έναν έπρεπε να επαναριθμήσουν πριν από τη συγχώνευση. Μια χρονική σήμανση UTC δίνει σε κάθε PR τη δική του έκδοση.

Κανόνες για τη μορφή χρονικής σήμανσης (επιβάλλεται από `npm run check:migration-numbering`, κοινόχρηστος με τη γεννήτρια στο `scripts/check/lib/migrationNaming.mjs`):

- Η χρονική σήμανση είναι μια πραγματική ημερομηνία και ώρα UTC, όχι νωρίτερα από `20261113000000` και όχι περισσότερο από 10 λεπτά στο μέλλον.
- Η περιγραφή είναι πεζά `snake_case` που ξεκινά με ένα γράμμα (`a-z`, `0-9`, μοναδικό `_` μεταξύ των λέξεων), το πολύ 80 χαρακτήρες.
- Δύο αρχεία με την ίδια χρονική σήμανση είναι διπλότυπα.
- Ο κανόνας μη κενού ισχύει μόνο για την παλιά σειρά: κάθε αριθμός από `001` έως `241` πρέπει να υπάρχει, εκτός από τα γνωστά κενά `026`, `055` και `121`. Η διαγραφή `241` (ή οποιουδήποτε παλιού αρχείου) αποτυγχάνει στην πύλη. `001` και `241` δεν μπορούν ποτέ να προστεθούν στη λίστα επιτρεπόμενων `KNOWN_GAPS`. Τα αρχεία με χρονική σήμανση δεν δημιουργούν ποτέ κενό.
- Κάθε καταχώρηση στο `src/lib/db/migrations/` πρέπει να είναι ένα κανονικό αρχείο με έγκυρο πεζό όνομα `.sql`. Ένας κατάλογος, ένας συμβολικός σύνδεσμος, ένα αρχείο `.SQL` ή `.sql.bak`, ένα κρυφό αρχείο ή ένα όνομα με κενό αποτυγχάνει στην πύλη, επειδή ο δρομέας θα το παρακάμψει σιωπηλά ή θα κολλούσε κατά την εκκίνηση.

**Εφαρμογή παραγγελίας.** Το πρόγραμμα εκτέλεσης ταξινομεί με βάση την αριθμητική τιμή του προθέματος και όχι με βάση το κείμενο: πρώτα τα παλιά αρχεία `001`–`241`, μετά τα αρχεία με χρονική σήμανση με σειρά χρονικής σήμανσης και, στη συνέχεια, τυχόν κατάλογοι με χώρο ονομάτων που έχουν καταχωριστεί με `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (εκδόσεις όπως `ee-001`). Μια εκκρεμή μετεγκατάσταση είναι κάθε αρχείο του οποίου η έκδοση δεν είναι σε `_omniroute_migrations`, επομένως μια μετεγκατάσταση από έναν παλαιότερο κλάδο που συγχωνεύεται μετά από έναν νεότερο εξακολουθεί να ισχύει στις υπάρχουσες βάσεις δεδομένων.

**Η χρονική σήμανση είναι σειρά δημιουργίας, όχι σειρά συγχώνευσης.** Εάν η μετεγκατάστασή σας εξαρτάται από έναν πίνακα ή στήλη που δημιουργήθηκε από μια μετεγκατάσταση με α** νεότερο** timestamp (για παράδειγμα, ένα από ένα άλλο PR που συγχωνεύτηκε πρώτο), μια νέα βάση δεδομένων θα εκτελούσε πρώτα τη δική σας και θα αποτύγχανε. Ενώ PR σας είναι ακόμα ανοιχτό, δημιουργήστε ξανά το όνομα του αρχείου με `npm run db:new-migration` ώστε να αποκτήσει μια νεότερη χρονική σήμανση ή κάντε το ανεξάρτητο. `npm run test:migrations:fresh` εφαρμόζει κάθε μετεγκατάσταση σε μια κενή βάση δεδομένων και το πιάνει.

### Μια συγχωνευμένη μετεγκατάσταση δεν διαγράφεται και δεν μετονομάζεται ποτέ

Μόλις ένα αρχείο μετεγκατάστασης βρίσκεται σε έναν κλάδο έκδοσης ή `main`, έχει ήδη εκτελεστεί σε βάσεις δεδομένων ομολόγων και προγραμματιστών, σε εγκαταστάσεις VPS και στον συγχρονισμό Enterprise. Από εκεί και πέρα:

- **Μην το διαγράψετε ποτέ.** Οι νέες εγκαταστάσεις θα χάσουν το σχήμα τους ενώ οι αναβαθμισμένες βάσεις δεδομένων το διατηρούν.
- **Ποτέ μην το μετονομάσετε.** Η έκδοση στο `_omniroute_migrations` δεν θα ταιριάζει πλέον με ένα αρχείο, επομένως κάθε βάση δεδομένων που την είχε ήδη εφαρμόσει θα την εκτελούσε ξανά. Στη συνέχεια, το μη idempotent SQL αντιγράφει δεδομένα ή σταματά την εκκίνηση.
- **Χρειάζεστε διαφορετικό σχήμα;** Δημιουργήστε μια νέα μετανάστευση με `npm run db:new-migration`.

Η μετονομασία είναι ασφαλής μόνο για ένα αρχείο που δεν έχει συγχωνευθεί ακόμα, στην περίπτωση που αναφέρονται οι συμβουλές της πύλης. Μια ετικέτα κυκλοφορίας δεν αλλάζει τίποτα εδώ: κάθε ώθηση σε έναν κλάδο `release/v*` δημοσιεύει την εικόνα Docker `:next` και εκτελείται σε ομόλογο, εγκαταστάσεις VPS και συγχρονισμό Enterprise, επομένως μια συγχωνευμένη μετεγκατάσταση έχει εκτελεστεί σε πραγματικές βάσεις δεδομένων πριν από την ύπαρξη οποιασδήποτε ετικέτας `vX.Y.Z`. Η πύλη αποτυγχάνει σε κάθε αφαίρεση ενός αρχείου βάσης, με ετικέτα ή όχι.

- **Επαναφορά συγχωνευμένης μετεγκατάστασης.** Ένα `git revert` που διαγράφει το αρχείο αποτυγχάνει στην πύλη. Διατηρήστε το αρχείο και αναιρέστε το σχήμα του σε μια νέα μετεγκατάσταση: `npm run db:new-migration -- <description>`, με `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` και ούτω καθεξής. Στη συνέχεια, οι αναβαθμισμένες και νέες βάσεις δεδομένων τελειώνουν με το ίδιο σχήμα.
- **Το ένα αποδεκτό μετονομασία: καταχώρηση συμβατότητας και πανομοιότυπο περιεχόμενο.** Εάν ένα συγχωνευμένο αρχείο πρέπει να μετακινηθεί (για παράδειγμα, δύο συγχωνευμένα αρχεία μοιράζονται μια χρονική σήμανση και ο runner σταματά με μια σύγκρουση έκδοσης), μετονομάστε το τελευταίο χωρίς να αγγίξετε SQL του και προσθέστε `{ fromVersion, fromName, toVersion, toName }` στο `RENAMED_MIGRATION_COMPATIBILITY` στο `src/lib/db/migrationRunner/constants.ts`. Οι βάσεις δεδομένων που εφάρμοσαν την παλιά έκδοση μετακινούν τη σειρά `_omniroute_migrations` αντί να εκτελούν ξανά το αρχείο. Η πύλη προειδοποιεί για μια τέτοια μετονομασία και εκτελεί πάντα τον έλεγχο εναλλαγής σε αυτήν, όποια κι αν είναι η νέα χρονική σήμανση: οι νέες εγκαταστάσεις εφαρμόζουν το αρχείο στη νέα του θέση, οι αναβαθμισμένες βάσεις δεδομένων όχι, επομένως επιλέξτε μια νέα χρονική σήμανση κοντά στην παλιά. Η πύλη αποτυγχάνει στη μετονομασία εάν το περιεχόμενο αλλάξει (μια αλλαγή σχήματος εξακολουθεί να γίνεται σε μια νέα μετεγκατάσταση) ή εάν το αρχείο προορισμού της καταχώρισης δεν βρίσκεται στο δίσκο.
- **Ποτέ μην μετονομάζετε μέσα στην ίδια χρονική σήμανση.** Μια μετονομασία που διατηρεί τη χρονική σήμανση και αλλάζει μόνο την περιγραφή αποτυγχάνει στην πύλη, με ή χωρίς καταχώρηση. Με μια καταχώρηση της οποίας `toVersion` ισούται με το `fromVersion`, ο runner διαγράφει την παλιά σειρά `_omniroute_migrations` και εφαρμόζει ξανά το αρχείο σε κάθε βάση δεδομένων που το εκτελούσε ήδη. Χωρίς καταχώρηση, ο δρομέας παρακολουθεί μόνο την έκδοση: παρακάμπτει το αρχείο σε αυτές τις βάσεις δεδομένων (το νέο περιεχόμενο δεν εκτελείται ποτέ εκεί) και καταγράφει ένα σφάλμα επαναρίθμησης σε κάθε εκκίνηση. Χρησιμοποιήστε μια άλλη χρονική σήμανση συν μια καταχώριση συμβατότητας ή διατηρήστε το όνομα.
- **Η πύλη ελέγχει ότι το αρχείο που μετονομάστηκε δεν εκτελείται ξανά.** Για κάθε καλυμμένη μετονομασία, η πύλη μεταβιβάζει το νέο όνομα αρχείου στον έλεγχο εναλλαγής με `--must-not-apply`. Ο έλεγχος εκκινεί την αναβαθμισμένη βάση δεδομένων με τον πραγματικό runner και εάν ο runner εφαρμόσει ξανά αυτό το αρχείο (για παράδειγμα, επειδή η καταχώριση έχει λάθος έκδοση ή όνομα ή επειδή ο αναλυτής κειμένου της πύλης διαβάζει `constants.ts` διαφορετικά από TypeScript), η πύλη αποτυγχάνει με το `migration renomeada rodaria de novo` και σας ζητά να ελέγξετε τις παλιές και νέες εκδόσεις και ονόματα της καταχώρισης.

### Τι ελέγχει η πύλη έναντι της βάσης

Σε εκτέλεση αιτήματος έλξης και ουράς συγχώνευσης, `npm run check:migration-numbering` συγκρίνει `src/lib/db/migrations/` στο δίσκο με τον ίδιο κατάλογο στον κλάδο βάσης. Η βάση είναι, με αυτή τη σειρά: `--base-latest-tag`, `--base <ref>`, η μεταβλητή `MIGRATION_BASE_REF` ή, όταν `GITHUB_EVENT_NAME` είναι `pull_request`, `pull_request_target` ή `merge_group`, ο πρώτος γονέας της δέσμευσης συγχώνευσης, το `merge_group.base_sha` του ωφέλιμου φορτίου συμβάντος ή `git merge-base HEAD origin/$GITHUB_BASE_REF`. Σε ένα αίτημα έλξης ή εκτέλεση ουράς συγχώνευσης χωρίς επιλύσιμη βάση, η πύλη αποτυγχάνει. Εκτός CI χωρίς `--base` εκτυπώνει `comparação com a base: pulada (sem --base)` και παρακάμπτει αυτούς τους κανόνες.

`--base-latest-tag` συγκρίνεται με την πιο πρόσφατη ετικέτα κυκλοφορίας (`vX.Y.Z` σε σειρά semver, οι ετικέτες με επίθημα όπως οι βραδινές βραδιές δεν υπολογίζονται) που βρίσκεται στην ιστορία του `HEAD`, με τους ίδιους κανόνες με `--base`. Το Release-Green (`scripts/quality/validate-release-green.mjs`) εκτελεί την πύλη με αυτόν τον τρόπο, επειδή οι εκτελέσεις push και προγραμματισμένες δεν έχουν βάση αιτημάτων έλξης και μια συγχώνευση μπορεί να προσγειωθεί χωρίς νέα εκτέλεση CI. Χωρίς ετικέτα κυκλοφορίας στο ιστορικό, η πύλη αποτυγχάνει. τρέξτε `git fetch --tags` (στο CI, `actions/checkout` με `fetch-depth: 0` φέρνει τις ετικέτες).

Ο έλεγχος αντικατάστασης (`scripts/check/migration-commutation.ts`) δημιουργεί δύο προσωρινές βάσεις δεδομένων με την πραγματική διαδρομή εγκατάστασης: an** αναβαθμίστηκε** ένα (εκκίνηση με τις βασικές μετεγκαταστάσεις, μετά εκκίνηση ξανά στο ίδιο αρχείο με τις μετεγκαταστάσεις του αιτήματος έλξης) και ένα** φρέσκο** ένα (μία εκκίνηση με τις μετεγκαταστάσεις του αιτήματος έλξης). Συγκρίνει τα σχήματα που προκύπτουν: πίνακες και στήλες (αγνοώντας τη σειρά στηλών), περιορισμούς UNIQUE / PRIMARY KEY και FOREIGN KEY, το κανονικοποιημένο κείμενο `CREATE TABLE` κάθε πίνακα (που καλύπτει περιορισμούς CHECK, συλλογές, δημιουργημένες στήλες και επιλογές πίνακα), ευρετήρια, κανόνες ετικέτας και προβολές. Τα δεδομένα σειρών δεν συγκρίνονται. Εάν ταιριάζουν, η πύλη εκτυπώνει ότι το αρχείο είναι εκτός λειτουργίας αλλά μετακινείται και περνά. Εάν διαφέρουν, η πύλη αποτυγχάνει με τη διαφορά και μια υπόδειξη για την υπόθεση: για ένα αρχείο εκτός σειράς, δημιουργήστε ξανά το όνομά του με `npm run db:new-migration`, το οποίο είναι ασφαλές επειδή το αρχείο δεν έχει συγχωνευθεί ακόμα. για ένα επεξεργασμένο αρχείο βάσης, επαναφέρετε το βασικό περιεχόμενο και βάλτε την αλλαγή σε μια νέα μετεγκατάσταση. για ένα μετονομασμένο αρχείο, αναιρέστε τη μετονομασία ή επιλέξτε άλλη νέα χρονική σήμανση όπου μετακινείται, ποτέ την ίδια χρονική σήμανση με άλλο όνομα. Εάν ο ίδιος ο έλεγχος δεν μπορεί να εκτελεστεί, η πύλη αποτυγχάνει στο CI και προειδοποιεί μόνο τοπικά. Για ένα επεξεργασμένο αρχείο βάσης, η αναβαθμισμένη βάση δεδομένων δημιουργείται με το περιεχόμενο της βάσης αυτού του αρχείου και η δεύτερη εκκίνηση το παραλείπει επειδή η έκδοσή του έχει ήδη εγγραφεί. Για ένα μετονομασμένο αρχείο, η αναβαθμισμένη βάση δεδομένων δημιουργείται με το αρχείο με το παλιό του όνομα και η δεύτερη εκκίνηση μετακινεί τη γραμμή `_omniroute_migrations` μέσα από την καταχώριση συμβατότητας αντί να την εκτελεί ξανά. η πύλη περνάει το νέο όνομα με `--must-not-apply`, οπότε ο έλεγχος αποτυγχάνει εάν το εφαρμόσει η δεύτερη εκκίνηση. Εάν μια μετεγκατάσταση αιτήματος έλξης αποτύχει να εφαρμοστεί στην αναβαθμισμένη διαδρομή, δηλαδή μετά από κάθε μετεγκατάσταση βάσης (είτε αποτυγχάνει επίσης σε μια νέα εγκατάσταση είτε όχι), η πύλη αναφέρει `migration do PR não aplica` και σας ζητά να διορθώσετε το SQL στο τρέχον σχήμα της βάσης. εάν το αρχείο εξαρτάται από μια άλλη μετεγκατάσταση αιτήματος έλξης με μεταγενέστερη χρονική σήμανση, δημιουργήστε ξανά το όνομά του με `npm run db:new-migration`.

Για να εκτελέσετε την ίδια σύγκριση τοπικά, περάστε ρητά τη βάση, για παράδειγμα `npm run check:migration-numbering -- --base origin/<base-branch>`, ή `npm run check:migration-numbering -- --base-latest-tag` για σύγκριση με την πιο πρόσφατη έκδοση.

### Μετατροπή ενός Open PR's `NNN` Migration

Ένα αίτημα έλξης που ανοίγει πριν από το διακόπτη μπορεί να εξακολουθεί να περιέχει ένα διαδοχικό αρχείο όπως `242_add_widgets.sql`. Οι παλιοί αριθμοί πάνω από `241` απορρίπτονται, επομένως μετατρέψτε τον πριν από τη συγχώνευση:

1. **Μετονομάστε το αρχείο με τη γεννήτρια, διατηρώντας την περιγραφή.** Εκτελέστε `npm run db:new-migration -- <same description>` για να λάβετε το νέο όνομα, μετακινήστε το SQL σε αυτό και διαγράψτε το παλιό αρχείο `NNN_`. Η περιγραφή πρέπει να παραμένει πανομοιότυπη: η παρακάτω καταχώριση συμβατότητας ταιριάζει σε αυτήν.
2. **Προσθέστε μια καταχώρηση συμβατότητας εάν μια μόνιμη βάση δεδομένων εκτελούσε τον παλιό αριθμό.** Εάν οποιαδήποτε βάση δεδομένων που διατηρείται (ομόλογα, VPS, εγκατάσταση του ίδιου του συντελεστή) εκτέλεσε μια κατασκευή του PR με το αρχείο `NNN_`, προσθέστε `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` στο `RENAMED_MIGRATION_COMPATIBILITY` στο `src/lib/db/migrationRunner/constants.ts`. Αυτό είναι** απαιτείται για `237` σε `241`** : αυτές οι υποδοχές κρατούν τώρα τα κανονικά `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` και `241_seen_models.sql` και χωρίς την καταχώρηση μια τέτοια βάση δεδομένων παρακάμπτει την κανονική μετεγκατάσταση για πάντα και εκτελεί ξανά τη μετατροπή. Λειτουργεί επίσης για μια υποδοχή που παραμένει κενή, όπως `242`, όταν ο προορισμός είναι μια χρονική σήμανση. Σε περίπτωση αμφιβολίας, προσθέστε την καταχώριση. Το πού θα το προσθέσετε στον πίνακα δεν έχει σημασία: όταν η υποδοχή στόχου μιας καταχώρισης εξακολουθεί να κρατά μια σειρά που μια άλλη καταχώριση απομακρύνεται (για παράδειγμα `237` κρατά μια σειρά PR ενώ μια παλαιότερη σειρά `usage_history_calculated_cost` περιμένει να μετακινηθεί σε `237`), ο δρομέας αφήνει αυτήν την καταχώριση να περιμένει έως ότου η υποδοχή είναι ελεύθερη. Μόνο μια πραγματική σύγκρουση, όπως μια υποδοχή που συγκρατείται από μια σειρά δεν κινείται η είσοδος ή δύο καταχωρήσεις που ανταλλάσσουν υποδοχές, σταματά την εκκίνηση με `Cannot reconcile ...`.
3. **Κρατήστε το SQL ανίκανο** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), επειδή η μετεγκατάσταση που έχει μετατραπεί μπορεί να συναντήσει μια βάση δεδομένων όπου υπάρχει ήδη το σχήμα της.
4. **Μετακινήστε ειδικές θήκες με κλειδί έκδοσης.** Εάν το PR πρόσθεσε μια περίπτωση για τον παλιό του αριθμό σε `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) ή σε `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`), αλλάξτε το κλειδί στη νέα χρονική σήμανση.

`tests/unit/db/codex-fence-migration-rename.test.ts` είναι ένα λειτουργικό παράδειγμα μιας δοκιμής για μια μετονομασμένη μετεγκατάσταση.

### Backports σε υποκαταστήματα πριν από το διακόπτη

Ποτέ μην κάνετε cherry-pick ή backport ένα αρχείο `YYYYMMDDHHMMSS_` σε ένα υποκατάστημα που προηγείται του switch (για παράδειγμα, ένα παλαιότερο υποκατάστημα `release/v*` ). Το πρόγραμμα εκτέλεσης ταξινομεί τα ονόματα αρχείων ως κείμενο, έτσι ένα αρχείο με χρονική σήμανση θα εκτελείται μεταξύ `201_` και `202_` σε μια νέα βάση δεδομένων και η παλιά πύλη εκεί δεν κατανοεί προθέματα 14 ψηφίων. Σε έναν τέτοιο κλάδο, γράψτε την αλλαγή ως το επόμενο αρχείο `NNN_` του ίδιου του κλάδου, idempotent, ώστε να μην λειτουργεί όταν η έκδοση με χρονική σήμανση φτάσει αργότερα.

### Πώς εκτελούνται οι μεταναστεύσεις

Κατά την εκκίνηση, `migrationRunner.ts`:

1. Δημιουργεί πίνακα `_omniroute_migrations` αν δεν υπάρχει
2. Ερωτήματα για ήδη εφαρμοσμένες μετεγκαταστάσεις
3. Εφαρμόζει τυχόν νέες μετεγκαταστάσεις κατά σειρά, καθεμία σε μια συναλλαγή
4. Καταγράφει κάθε εφαρμοσμένη μετεγκατάσταση με χρονική σήμανση

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### Ανικανότητα

Οι μεταναστεύσεις πρέπει να είναι** ανίκανος** — που τα εκτελεί δύο φορές θα πρέπει να είναι μη ενεργό:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

Χρησιμοποιήστε ελεύθερα τις ρήτρες `IF NOT EXISTS`, `IF EXISTS` και `OR IGNORE` / `OR REPLACE`.

### Προσθήκη νέας μετανάστευσης

1. **Δημιουργήστε το αρχείο με τη γεννήτρια** : `npm run db:new-migration -- <description>` (για παράδειγμα `npm run db:new-migration -- add combo priority`). Γράφει `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` με την τρέχουσα ώρα UTC και μια κεφαλίδα σχολίου, μετακινείται ένα δευτερόλεπτο προς τα εμπρός εάν ληφθεί αυτή η χρονική σήμανση και δεν αντικαθιστά ποτέ ένα αρχείο. Μην επιλέγετε έναν αριθμό με το χέρι.
2. **Χρησιμοποιήστε ασφαλή DDL** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **Συμπληρώστε τα δεδομένα προσεκτικά** : χρησιμοποιήστε `UPDATE ... WHERE ...` για να χειριστείτε υπάρχουσες σειρές
4. **Ελέγξτε τη σειρά και την ονομασία** : `npm run test:migrations:fresh` (όλες οι μετεγκαταστάσεις σε μια κενή βάση δεδομένων) και `npm run check:migration-numbering`
5. **Δοκιμή σε αντίγραφο** : μην εκτελείτε ποτέ μη δοκιμασμένες μεταναστεύσεις στην παραγωγή
6. **Ένας πίνακας που δημιουργήθηκε από κώδικα χρειάζεται επίσης μια μετεγκατάσταση** : εάν μια λειτουργική μονάδα δημιουργεί επίσης νωχελικά τον πίνακα (`CREATE TABLE IF NOT EXISTS`, που διατηρείται ως μονοπάτι αυτοθεραπείας), μια μετανάστευση πρέπει να το δημιουργήσει με το ίδιο DDL. Διαφορετικά, μια καθαρή εγκατάσταση και μια αναβαθμισμένη εγκατάσταση καταλήγουν σε διαφορετικά σχήματα, ανάλογα με το αν εκτελείται αυτή η διαδρομή κώδικα. `tests/unit/db/lazy-table-migration-guard.test.ts` σαρώνει `src/` και `open-sse/` και αποτυγχάνει σε ένα τεμπέλικο `CREATE` χωρίς μετεγκατάσταση (#20557). Παράδειγμα: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

Παράδειγμα:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **Αλλαγές μη συμβατές προς τα πίσω** (π.χ. η απόθεση στηλών) είναι δύσκολη. NOT OmniRoute υποστηρίζει την υποβάθμιση — όταν εφαρμοστεί μια μετεγκατάσταση, η αλλαγή σχήματος είναι μόνιμη. Σχεδιάστε ανάλογα.

## Κρυπτογράφηση Αποθηκευμένων Δεδομένων

Τα ευαίσθητα πεδία (κλειδιά API, διακριτικά OAuth, συμβολοσειρές σύνδεσης) κρυπτογραφούνται κατά την αποθήκευση με χρήση **AES-256-GCM**.

### Τρόπος Λειτουργίας

```ts
// src/lib/db/encryption.ts (απλοποιημένο)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### Πού Χρησιμοποιείται

- `provider_connections.api_key` — κρυπτογραφείται σε επίπεδο εφαρμογής
- `provider_connections.access_token`, `refresh_token`, `id_token` — κρυπτογραφούνται σε επίπεδο εφαρμογής
- Καταχωρίσεις `key_value` με `namespace = "secrets"` — κρυπτογραφούνται σε επίπεδο εφαρμογής
- `proxy_registry.auth` — κρυπτογραφείται σε επίπεδο εφαρμογής (εάν υπάρχει)

### Κλειδί Κρυπτογράφησης

Το κλειδί κρυπτογράφησης παράγεται από μια **φράση πρόσβασης** (ορίζεται μέσω της μεταβλητής περιβάλλοντος `STORAGE_ENCRYPTION_KEY`) και ένα **salt** (αποθηκεύεται στη βάση δεδομένων). Και τα δύο απαιτούνται για την αποκρυπτογράφηση των δεδομένων.

```bash
# Δημιουργήστε μια ασφαλή φράση πρόσβασης
openssl rand -hex 32

# Ορίστε τη στο .env
STORAGE_ENCRYPTION_KEY=<το-κλειδί-σας>
```

> **Κρίσιμο**: Η απώλεια του κλειδιού κρυπτογράφησης συνεπάγεται την απώλεια πρόσβασης σε όλα τα κρυπτογραφημένα δεδομένα. **Δημιουργήστε αντίγραφο ασφαλείας του κλειδιού ξεχωριστά από τη βάση δεδομένων**.

### Τι ΔΕΝ Κρυπτογραφείται

Για λόγους απόδοσης, τα ακόλουθα αποθηκεύονται ως απλό κείμενο:

- Εμφανιζόμενα ονόματα παρόχων
- Ορισμοί μοντέλων (είναι ήδη δημόσιοι)
- Κανόνες δρομολόγησης
- Εγγραφές χρήσης (χωρίς προσωπικά ταυτοποιήσιμες πληροφορίες)

## Επισημάνσεις κρυπτογράφησης (v3.8.16+)

Το OmniRoute χρησιμοποιεί τη **`migrateLegacyEncryptedString()`** για να διαχειρίζεται με διαφανή τρόπο δύο σχήματα κρυπτογράφησης:

- **Παλαιού τύπου** (πριν από την v3.5.0): «κρυπτογράφηση» βασισμένη σε XOR (όχι πραγματική κρυπτογραφία)
- **Τρέχον**: AES-256-GCM με κατάλληλο IV και ετικέτα αυθεντικοποίησης

Ο βοηθός μετεγκατάστασης εντοπίζει την παλαιού τύπου μορφή και επανακρυπτογραφεί με το νέο σχήμα κατά την πρώτη ανάγνωση. Αυτό σημαίνει ότι μπορείτε να αναβαθμίσετε μια παλιά βάση δεδομένων χωρίς να χάσετε διαπιστευτήρια.

## Performance Tuning

### Λειτουργία WAL

WAL είναι ενεργοποιημένο από προεπιλογή. Για μεγάλο φόρτο εργασίας, σκεφτείτε:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute δεν θέτει `journal_size_limit`. Ένα σημείο ελέγχου μετακινεί τα πλαίσια WAL στο κύριο αρχείο, αλλά το αρχείο WAL διατηρεί το μεγαλύτερο εκχωρημένο μέγεθός του. Ο φρουρός `OMNIROUTE_WAL_GUARD_MAX_MB` προειδοποιεί μόνο και εκτελεί `wal_checkpoint(RESTART)`. δεν είναι καπάκι μεγέθους δίσκου.

### Ευρετήρια

Βασικοί δείκτες απόδοσης (δημιουργούνται αυτόματα από μετεγκαταστάσεις):

- Αναζητήσεις μοντέλων `idx_models_provider` — ανά πάροχο
- Επέκταση σύνθετου στόχου `idx_combo_targets_combo_id` —
- Αναλύσεις χρήσης `idx_usage_history_api_key_timestamp` —
- παρακολούθηση ποσοστώσεων `idx_quota_snapshots_api_key_window` —
- ερωτήματα αρχείου καταγραφής κλήσεων `idx_call_logs_timestamp` —

Για να προσθέσετε ένα νέο ευρετήριο, δημιουργήστε μια μετεγκατάσταση:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### Χαρτογράφηση μνήμης I/O

Για πολύ μεγάλες βάσεις δεδομένων (> 10 GB), η αντιστοίχιση μνήμης μπορεί να προσαρμοστεί μέσω SQLite pragma:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### Συμπύκνωση

Οι μακροχρόνιες περιπτώσεις OmniRoute επωφελούνται από το περιστασιακό `VACUUM`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

Εκτελείται κάθε μήνα σε παράθυρα χαμηλής κυκλοφορίας. (Η λειτουργία WAL μειώνει την ανάγκη, αλλά δεν την εξαλείφει.)

## Έλεγχος εύρυθμης λειτουργίας

Το `src/lib/db/healthCheck.ts` παρέχει **διαγνωστικά εύρυθμης λειτουργίας σε επίπεδο βάσης δεδομένων**:

Και τα δύο ρήματα απαιτούν έλεγχο ταυτότητας (διαφορετικά επιστρέφεται `401`). Το `GET` εκτελεί μόνο διάγνωση, ενώ το `POST` εκτελεί τον
ίδιο έλεγχο με ενεργοποιημένο το `autoRepair`.

```bash
GET  /api/db/health   # διάγνωση
POST /api/db/health   # διάγνωση + επιδιόρθωση
```

Η απόκριση είναι το `DbHealthCheckResult` που παράγεται από το `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Οι προϋπολογισμοί τομέων αναφέρονταν σε κλειδιά API που δεν υπάρχουν πλέον.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| Πεδίο             | Σημασία                                                                                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | Είναι `true` όταν το `issues` είναι κενό. Το `driver` δεν το επηρεάζει ποτέ.                                                                                                                            |
| `issues[].type`   | Μία από τις τιμές `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`.                                                                                                      |
| `repairedCount`   | Γραμμές που επιδιορθώθηκαν κατά την τρέχουσα εκτέλεση· είναι πάντα `0` όταν το `autoRepair` είναι false.                                                                                                |
| `backupCreated`   | Εάν δημιουργήθηκε αντίγραφο ασφαλείας πριν από την επιδιόρθωση.                                                                                                                                         |
| `checkedAt`       | Χρονική σήμανση ISO που είναι κοινή για την εκτέλεση και για οποιαδήποτε σημείωση επιδιόρθωσης εγγράφεται από αυτήν.                                                                                    |
| `driver.name`     | Πρόγραμμα οδήγησης SQLite που εξυπηρετεί την ελεγχόμενη βάση δεδομένων.                                                                                                                                 |
| `driver.degraded` | Είναι `true` όταν οι εγγραφές δεν υποστηρίζονται με ανθεκτικό τρόπο από το αρχείο της βάσης δεδομένων — η εφεδρική λύση WASM `sql.js` (διατήρηση ολόκληρου του αρχείου) ή μια βάση δεδομένων στη μνήμη. |

Το ίδιο ωφέλιμο φορτίο επιστρέφεται από το εργαλείο MCP `omniroute_db_health_check`.

Εκτελέστε το `PRAGMA integrity_check` για να εντοπίσετε αλλοίωση:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# Θα πρέπει να εμφανίσει: ok
```

Εάν επιστρέψει οτιδήποτε άλλο εκτός από `ok`, **σταματήστε αμέσως να χρησιμοποιείτε τη βάση δεδομένων** και πραγματοποιήστε επαναφορά από αντίγραφο ασφαλείας.

(`GET /api/db-backups/exportAll`, απαιτούνται διαπιστευτήρια χειριστή)· δεν επαναφέρει τίποτα.

### Σενάριο 3: Απώλεια Κλειδιού Κρυπτογράφησης

**Δεν είναι δυνατή η ανάκτηση** χωρίς το κλειδί. Τα κρυπτογραφημένα πεδία δεν είναι αναγνώσιμα. Προσθέστε ξανά όλους τους παρόχους χειροκίνητα με νέα διαπιστευτήρια.

> **Μετριασμός κινδύνου**: Δημιουργείτε πάντα ξεχωριστό αντίγραφο ασφαλείας του κλειδιού κρυπτογράφησης, ιδανικά σε έναν διαχειριστή κωδικών πρόσβασης ή σε KMS.

### Σενάριο 4: Πλήρης Δίσκος

Το SQLite θα επιστρέψει σφάλματα `SQLITE_FULL`. Ελευθερώστε χώρο στον δίσκο και, στη συνέχεια:

```bash
# Εκτέλεση checkpoint στο WAL για την απελευθέρωση χώρου
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## Αντιμετώπιση Προβλημάτων

### "Η βάση δεδομένων είναι κλειδωμένη"

Μια άλλη διεργασία διατηρεί ένα κλείδωμα εγγραφής. Μπορείτε είτε:

- Να περιμένετε να ολοκληρωθεί η άλλη διεργασία (ελέγξτε με `lsof | grep storage.sqlite`)
- Να τερματίσετε την άλλη διεργασία
- Εάν το πρόβλημα επιμένει, να επανεκκινήσετε το OmniRoute

### "Ο περιορισμός ξένου κλειδιού απέτυχε"

Μια λειτουργική μονάδα τομέα παραβιάζει την αναφορική ακεραιότητα. Ελέγξτε για:

- Ορφανές γραμμές σε εξαρτώμενους πίνακες
- Διαδοχικές διαγραφές που δεν μεταδόθηκαν
- Πρόσφατη μετεγκατάσταση που άλλαξε ένα ξένο κλειδί

Εκτελέστε `PRAGMA foreign_key_check;` για να εντοπίσετε παραβιάσεις.

### "Ανεπάρκεια μνήμης"

Η λειτουργία εισόδου/εξόδου με αντιστοίχιση μνήμης του SQLite υπερβαίνει το όριο του λειτουργικού συστήματος. Μειώστε το μέσω pragma του SQLite:

```sql
PRAGMA mmap_size = 134217728;  -- 128MB αντί για 256MB
```

Ή απενεργοποιήστε το:

```sql
PRAGMA mmap_size = 0;
```

### "Η μετεγκατάσταση απέτυχε στα μισά της διαδικασίας"

Η μετεγκατάσταση εκτελέστηκε μέσα σε μια συναλλαγή, επομένως οι αλλαγές θα πρέπει να έχουν αναιρεθεί. Εάν όχι:

1. **Διακόψτε το OmniRoute** (αποτρέψτε περαιτέρω προσπάθειες)
2. **Ελέγξτε την κατάσταση της βάσης δεδομένων** με `sqlite3`
3. **Διορθώστε χειροκίνητα** τη μερική μετεγκατάσταση
4. **Εκτελέστε ξανά** το OmniRoute (η μετεγκατάσταση θα επιχειρηθεί ξανά)

Για να το αποτρέψετε, δοκιμάζετε πάντα πρώτα τις μετεγκαταστάσεις σε ένα αντίγραφο.
