Χρησιμοποιήστε αυτόν τον οδηγό για να επιλέξετε τον μικρότερο αξιόπιστο κύκλο ανάπτυξης για ένα pull request. Δεν
αντικαθιστά τα έγγραφα αρχιτεκτονικής και ασφάλειας ανά περιοχή που συνδέονται παρακάτω· συνδέει κάθε συνηθισμένο
τύπο αλλαγής με τις συμβάσεις του, τους στοχευμένους ελέγχους και την κάλυψη CI.

## Η διαδρομή που ακολουθεί κάθε αλλαγή

1. **Επιλέξτε τη βάση πριν από την επεξεργασία.** Βρείτε τον υψηλότερο ενεργό κλάδο `release/v*` και δημιουργήστε κλάδο από
   την κορυφή του. Στοχεύστε αυτόν τον κλάδο, όχι το `main`. Αν είναι ενεργό ένα πάγωμα έκδοσης, μη στοχεύσετε τον παγωμένο
   κλάδο· χρησιμοποιήστε τον επόμενο ενεργό κύκλο που περιγράφεται στο
   [Μοντέλο διακλάδωσης και εκδόσεων](BRANCHING_MODEL.md).
2. **Κατονομάστε τις συμβάσεις.** Προσδιορίστε κάθε κατάλογο, σχήμα, παραγόμενο τεχνούργημα, δημόσιο API ή διεπαφή
   χρήστη που επηρεάζει η αλλαγή. Ο παρακάτω πίνακας παρέχει το ελάχιστο αρχικό σύνολο.
3. **Γράψτε ή ενημερώστε στοχευμένες δοκιμές.** Οι αλλαγές παραγωγής στα `src/`, `open-sse/`, `electron/` ή
   `bin/` απαιτούν μια αυτοματοποιημένη δοκιμή στο ίδιο PR. Εκτελέστε τα μικρότερα αρχεία δοκιμών που αποδεικνύουν τη
   συμπεριφορά και, στη συνέχεια, τους αναφερόμενους στοχευμένους ελέγχους.
4. **Αφήστε το CI να εκτελέσει τον ευρύ πίνακα δοκιμών.** Τα πλήρη τμήματα δοκιμών μονάδας, το Vitest, ο μηχανισμός σταδιακής αύξησης της κάλυψης και
   το build παραγωγής εκτελούνται στο PR. Εκτελέστε μια ευρεία σουίτα τοπικά μόνο όταν μια στοχευμένη αποτυχία υποδεικνύει
   ευρύτερο αντίκτυπο ή όταν η αλλαγή εκτείνεται σε πολλά υποσυστήματα.
5. **Κάντε συγχρονισμό πριν από την ανασκόπηση.** Ανακτήστε την ενεργή βάση, επιθεωρήστε τα νέα commit της και τις διαφορές σας σε σχέση
   με αυτήν και, στη συνέχεια, κάντε rebase ή merge της βάσης σύμφωνα με τη ροή εργασίας των συνεισφερόντων. Επιλύστε τις συγκρούσεις σε παραγόμενα αρχεία
   και καταλόγους από την πηγή τους, δημιουργήστε τα ξανά, επανεκτελέστε τον στοχευμένο κύκλο και επιβεβαιώστε ότι το
   PR εξακολουθεί να στοχεύει τον ενεργό κλάδο έκδοσης.
6. **Καταγράψτε τα αποδεικτικά στοιχεία.** Στο πρότυπο του PR, παραθέστε τις εντολές που εκτελέστηκαν, κάθε αρχείο δοκιμών που προστέθηκε ή άλλαξε,
   τις μεταβιβάσεις ή τα feature flags, καθώς και οποιαδήποτε επικύρωση που εκτελείται μόνο στο CI και εξακολουθεί να εκκρεμεί.

## Προτεινόμενες διαδρομές ανά τύπο αλλαγής

Οι παρακάτω εντολές είναι οι ελάχιστοι στοχευμένοι έλεγχοι και όχι άδεια για παράλειψη μιας δοκιμής που καλύπτει άμεσα τη
συμπεριφορά που αλλάξατε.

### Πάροχος

**Συμβάσεις**

- Ορισμός παρόχου στο `src/shared/constants/providers/` και η σύνθεσή του στο
  `src/shared/constants/providers.ts`.
- Μοντέλα και δυνατότητες στο `open-sse/config/providerRegistry.ts` ή στα αρχεία registry που έχουν εξαχθεί από αυτό.
- Επιλογή executor/translator, διαμόρφωση OAuth ή API key, στοιχεία του dashboard και παραγόμενη
  αναφορά παρόχου, όπου εφαρμόζεται.
- Τα δημόσια διαπιστευτήρια πρέπει να χρησιμοποιούν `resolvePublicCred()`· οι αποκρίσεις σφαλμάτων πρέπει να χρησιμοποιούν τους κοινόχρηστους βοηθούς
  καθαρισμού σφαλμάτων. Δείτε τα `docs/security/PUBLIC_CREDS.md` (git· δεν μεταγλωττίζεται στο `/docs`) και
  [Καθαρισμός σφαλμάτων](../security/ERROR_SANITIZATION.md).

**Στοχευμένος κύκλος**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # όταν αλλάζει ο κατάλογος· κάντε commit τις παραγόμενες διαφορές
npm run lint
```

Δοκιμάστε επίσης κάθε οικογένεια αιτημάτων που επηρεάζεται: chat, Responses, εικόνες, embeddings, ήχος ή βίντεο.
Εξετάστε τις παραγόμενες διαφορές καταλόγων και golden ως αλλαγές συμβάσεων· μην τις αποδέχεστε χωρίς έλεγχο.

### Δρομολόγηση

**Συμβάσεις**

- Δημόσιες τιμές στρατηγικής και μεταδεδομένα UI στο `src/shared/constants/routingStrategies.ts`.
- Αποστολή και σειρά εκτέλεσης στο `open-sse/services/combo.ts` και στο `open-sse/services/combo/`.
- Σχήματα combo, διατήρηση δεδομένων, κατάσταση ανθεκτικότητας, δυνατότητες μοντέλων και στοιχεία ελέγχου API/UI.
- [Μηχανή Auto-Combo](../routing/AUTO-COMBO.md) και τεκμηρίωση ανθεκτικότητας όταν αλλάζει η συμπεριφορά.

**Στοχευμένος κύκλος**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # αλλαγές στρατηγικής ή αποστολής
npm run check:known-symbols      # αλλαγές καταχώρισης στρατηγικής
npm run lint
```

Χρησιμοποιήστε τοπικά ντετερμινιστικές δοκιμές με προσομοιωμένο upstream. Οι live συνοπτικές δοκιμές combo απαιτούν διαπιστευτήρια και είναι
χειροκίνητες, όχι υποκατάστατα του CI.

### UI / UX

**Συμβάσεις**

- Διαδρομή/σελίδα Next.js και όρια κοινόχρηστων component στα `src/app/` και
  `src/shared/components/`.
- Σχήματα απόκρισης API, καταστάσεις φόρτωσης/κενού/σφάλματος, συμπεριφορά πληκτρολογίου και αναγνώστη οθόνης,
  responsive διάταξη, θέματα και επέκταση locale.
- Αγγλικά πηγαία κείμενα UI στο `src/i18n/messages/en.json`· μην ενσωματώνετε απευθείας νέο κείμενο που απευθύνεται στον χρήστη.

**Στοχευμένος κύκλος**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Εκτελέστε την εφαρμογή για αλλαγές αλληλεπίδρασης ή εμφάνισης και ελέγξτε τόσο στενά όσο και πλατιά viewport. Το CI εκτελεί το
build παραγωγής και τις ευρύτερες σουίτες· η οπτική συμπεριφορά εξακολουθεί να χρειάζεται ένα στοχευμένο component, Playwright
ή τεκμηριωμένο χειροκίνητο έλεγχο κατάλληλο για την αλλαγή.

### i18n

**Συμβάσεις**

- Το `src/i18n/messages/en.json` είναι η πηγή του UI· το `config/i18n.json` είναι η πηγή των locale.
- Οι κατάλογοι CLI βρίσκονται ξεχωριστά στο `bin/cli/locales/`.
- Διατηρήστε τα placeholder και τα tag ICU ακριβώς όπως είναι. Μη μεταφράζετε ονόματα προϊόντων/παρόχων/μοντέλων,
  ονόματα πρωτοκόλλων και header, εντολές, αναγνωριστικά κώδικα/JSON, URL, μεταβλητές περιβάλλοντος ή
  προστατευμένους όρους όπως `OmniRoute`, `OAuth`, `MCP` και `A2A`. Η τρέχουσα λίστα πηγής είναι το
  `scripts/i18n/glossary/protected-terms.json`.

**Στοχευμένος κύκλος**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # όταν αλλάζουν κείμενα/κατάλογοι CLI
npm run lint
```

Αυτές είναι οδηγίες για το υπάρχον σύστημα και όχι πρόσκληση για επέκταση των εργαλείων ή του μοντέλου κλειδιών του.
Διατηρήστε τις διορθώσεις i18n περιορισμένες και ακριβείς όσο σχεδιάζεται το σύστημα αντικατάστασης. Μην εκτελείτε εντολές μετάφρασης
που καλούν εξωτερικές υπηρεσίες, εκτός αν η εργασία απαιτεί ρητά παραγόμενες μεταφράσεις και
έχετε εξετάσει τις διαφορές που προκύπτουν.

### CLI

**Συμβάσεις**

- Δημόσιες εντολές και flags στο `bin/cli/`, δημιουργημένες εντολές API, κωδικοί εξόδου, stdout/stderr και
  δομές εξόδου JSON, συμπεριφορά ρυθμίσεων/περιβάλλοντος και αρχεία που περιλαμβάνονται στο πακέτο.
- Τα μηνύματα του CLI που απευθύνονται στον χρήστη πρέπει να χρησιμοποιούν το επίπεδο i18n του CLI και να διατηρούν συγχρονισμένους τους καταλόγους `en`/`pt-BR`.
- Διατηρήστε το Node ως το υποστηριζόμενο περιβάλλον εκτέλεσης και τη δημόσια σύμβαση του δημοσιευμένου εκτελέσιμου αρχείου.

**Εστιασμένος κύκλος**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # αλλαγές στο δημιουργημένο/πακεταρισμένο CLI
npm run check:pack-policy     # αλλαγές στη δημόσια επιφάνεια του πακέτου
npm run lint
```

Χρησιμοποιήστε την ακριβή εντολή σε έναν προσωρινό κατάλογο δεδομένων όταν η συμπεριφορά εξαρτάται από την ανάλυση, τα αρχεία ή την
κατάσταση εξόδου. Το CI εκτελεί τους ευρύτερους ελέγχους τεχνουργημάτων πακέτου και οικοσυστήματος.

### Βάση δεδομένων

**Συμβάσεις**

- Θεματικές μονάδες στο `src/lib/db/`· εισάγετε απευθείας συγκεκριμένες μονάδες (το παλιό επίπεδο επανεξαγωγής `localDb.ts` αφαιρέθηκε).
- Αριθμημένες, ιδιοδύναμες μετεγκαταστάσεις SQL στο `src/lib/db/migrations/`, ασφάλεια συναλλαγών, συμπεριφορά
  αναβάθμισης, ευρετήρια και κάθε καλών που επηρεάζεται από το σχήμα.
- Οι διαδρομές και οι χειριστές δεν εκτελούν ποτέ απευθείας ανεπεξέργαστη SQL.

**Εστιασμένος κύκλος**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Όταν προσθέτετε μια μετεγκατάσταση, δοκιμάστε τόσο μια νέα βάση δεδομένων όσο και την αναβάθμιση από το προηγούμενο σχήμα. Οι δοκιμές βάσης δεδομένων
πρέπει να κλείνουν τους ανοικτούς πόρους και να καλούν τη `resetDbInstance()` κατά την εκκαθάριση. Εκτελέστε το `npm run test:bun:db` μόνο όταν
αλλάζει η διαδρομή του προσαρμογέα Bun βέλτιστης προσπάθειας· το Node παραμένει η επίσημη αναφορά.

### Δόμηση / ανάπτυξη

**Συμβάσεις**

- Δηλώσεις/αρχείο κλειδώματος ρίζας και χώρων εργασίας, `scripts/build/`, αυτόνομη συναρμολόγηση του Next.js, περιεχόμενα πακέτου `dist/`,
  μεταδεδομένα πλατφόρμας Electron, ροές εργασίας CI και δείκτες ανάπτυξης.
- Τα υποστηριζόμενα εύρη Node και η εγκεκριμένη χρήση του Bun στο `CLAUDE.md` πρέπει να παραμένουν ανέπαφα.
- Τα τεχνουργήματα δόμησης παραμένουν εκτός παρακολούθησης· ισχύουν οι πολιτικές εξαρτήσεων, αδειών, ροών εργασίας και πακέτων.

**Εστιασμένος κύκλος**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # αλλαγές εξαρτήσεων ή αρχείου κλειδώματος
npm run check:pack-policy      # αλλαγές στη δημοσιευμένη επιφάνεια του πακέτου
npm run lint
```

Χρησιμοποιήστε το `npm run build` τοπικά μόνο όταν η αλλαγή επηρεάζει τη μεταγλώττιση, την αυτόνομη συναρμολόγηση, τους πόρους
ή την πακετοποίηση χρόνου εκτέλεσης. Χρησιμοποιήστε το `npm run build:release` μόνο για επικύρωση έκδοσης/ανάπτυξης. Η δόμηση του CI αποτελεί
το τελικό σήμα μεταξύ πλατφορμών· οι αλλαγές του Electron που αφορούν συγκεκριμένη πλατφόρμα χρειάζονται την αντίστοιχη εστιασμένη δόμηση
ή τεκμήρια δοκιμής καπνού.

## Scripts προγραμματιστή για κοινόχρηστο μηχάνημα

Δύο βοηθητικά εργαλεία στο `scripts/dev/` υλοποιούν τον τοπικό κύκλο εργασίας σε ένα devbox όπου είναι ενεργές και άλλες συνεδρίες:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # αρχεία από merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ακριβώς αυτά τα αρχεία
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # απομονωμένο worktree, ασφαλές για παράλληλη χρήση
```

- Το `typecheck-touched.sh` εκτελεί έλεγχο τύπων μόνο στα τροποποιημένα αρχεία `.ts/.tsx` μέσω ενός προσωρινού
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) με heap 6 GB, επομένως αντικαθιστά το `tsc -p tsconfig.json` για ολόκληρο το έργο,
  το οποίο προκαλεί OOM σε ένα επιβαρυμένο μηχάνημα. Εκτυπώνει τα σφάλματα στα τροποποιημένα αρχεία μαζί με μία γραμμή σύνοψης και τερματίζει με
  `1` για σφάλματα στα τροποποιημένα αρχεία, `2` όταν τα μόνα σφάλματα βρίσκονται σε εισαγόμενα αρχεία ή όταν το tsc τερματίστηκε
  χωρίς διαγνωστικά (διαβάστε το αρχείο καταγραφής που αναφέρει στο `_artifacts/typecheck-touched/`) και `0` όταν
  δεν υπάρχουν σφάλματα. Το προσωρινό tsconfig αφαιρείται πάντα· μην κάνετε ποτέ commit ένα τέτοιο αρχείο.
- Το `new-worktree.sh` εκτελεί σειριακά τις ταυτόχρονες εκτελέσεις μέσω του `<git-common-dir>/omniroute-new-worktree.lock`
  (περιμένει έως και 600 s από προεπιλογή, εμφανίζοντας σχετικό μήνυμα· η κεφαλίδα του script τεκμηριώνει την
  παράκαμψη) και αναιρεί
  τη δημιουργία του branch όταν το `git worktree add` αποτύχει πριν δημιουργηθεί το worktree, ώστε μια νέα προσπάθεια
  να μη χρειάζεται χειροκίνητο `git branch -D`. Τα hard-linked `node_modules` και το αντίγραφο του `.husky/_` παραμένουν αμετάβλητα.

## Τοπικός κύκλος candidate

Τα source tests δεν μπορούν να αποδείξουν ότι το πακεταρισμένο artifact εκκινείται: οι λίστες πακεταρίσματος, οι αφαιρεμένες εξαρτήσεις
και τα native binaries αποτυγχάνουν μόνο όταν εγκατασταθεί και εκκινηθεί το tarball. Το `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) είναι η τοπική πλευρά της ροής build-once / validate / promote από το
RFC #8084: δημιουργεί ένα candidate, επικυρώνει ακριβώς αυτό το artifact, το προωθεί μέσω
μετονομασιών καταλόγων και το επαναφέρει όταν το προωθημένο slot αποτύχει στον έλεγχο εύρυθμης λειτουργίας.

```bash
npm run dev:candidate -- run --dry-run --json  # εμφάνιση του πλάνου, χωρίς καμία αλλαγή
npm run dev:candidate -- run                   # build + validate + promote, αυτόματο rollback
npm run dev:candidate -- build                 # npm pack + εγκατάσταση στο _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # εκκίνηση σε ελεύθερη θύρα, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # εναλλαγή current και previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # επαναχρησιμοποίηση tarball που δημιουργήθηκε αλλού (CI)
```

- **Build μία φορά.** Το `build` πακετάρει το τρέχον δέντρο (χρειάζεται το `dist/server.js`, οπότε εκτελέστε πρώτα
  `npm run build:release`) ή αντιγράφει το `--from-tarball` και κατόπιν εγκαθιστά το tarball σε ένα
  απομονωμένο npm prefix, επειδή το tarball δεν περιλαμβάνει `node_modules`. Το id είναι το σύντομο sha του `HEAD`
  (`-dirty` όταν το δέντρο έχει τοπικές αλλαγές) ή `tgz-<sha256>` για ένα tarball. Ένα καθαρό id που
  έχει ήδη δημιουργηθεί επαναχρησιμοποιείται αντί να δημιουργηθεί ξανά· περάστε `--force` για να το δημιουργήσετε εκ νέου.
- **Επικυρώστε το πακέτο, όχι τον πηγαίο κώδικα.** Το `validate` εκκινεί το εγκατεστημένο CLI
  (`serve --port <free port>`) με νέο `DATA_DIR=<candidate>/data`, ψεύτικα secrets, και αφαιρεί από το
  περιβάλλον τα `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` και `INITIAL_PASSWORD` του διαχειριστή,
  ώστε να ελέγξει τη συμπεριφορά keyless loopback μιας νέας εγκατάστασης. Περιμένει μέχρι το
  `GET /api/health` να επιστρέψει 200, απαιτεί το `GET /v1/models` να επιστρέψει 200, διακόπτει την ομάδα διεργασιών
  και καταγράφει την ετυμηγορία στο `validation.json` μαζί με το hash του tarball.
- **Προωθήστε το ίδιο artifact.** Το `promote` απορρίπτει ένα candidate χωρίς επιτυχή επικύρωση για το
  τρέχον hash του tarball του. Το προεπιλεγμένο ενεργό slot είναι το `_artifacts/candidate/current`· το `--target <dir>`
  επιλέγει άλλον κατάλογο στο ίδιο filesystem και το προηγούμενο slot του είναι το `<dir>.previous`.
  Κάθε μετονομασία είναι ατομική και μια αποτυχία κατά τη διάρκεια της διαδικασίας αντιστρέφει τις μετονομασίες που έχουν ήδη εκτελεστεί.
- **Επαναφορά.** Το `run` επικυρώνει ξανά το προωθημένο slot και επαναφέρει τα `current` και `previous` όταν
  αποτύχει αυτός ο έλεγχος. Ένα candidate που αποτυγχάνει στην πρώτη επικύρωση δεν προωθείται ποτέ.

Όλα εγγράφονται στον gitignored κατάλογο `_artifacts/candidate/`· μια υπάρχουσα εγκατάσταση του OmniRoute
και ο κατάλογος δεδομένων της δεν τροποποιούνται ποτέ. Το προωθημένο CLI είναι το
`_artifacts/candidate/current/prefix/bin/omniroute`· εκκινήστε το με το δικό σας `DATA_DIR` όταν το χρησιμοποιείτε.
Κωδικοί εξόδου: `0` επιτυχία, `1` αποτυχημένη επικύρωση ή προώθηση, `2` σφάλμα χρήσης ή build που λείπει.

## Τοπικός βρόχος έναντι CI

| Εκτέλεση τοπικά για κάθε διόρθωση                                                                            | Το CI παρέχει το ευρύ σήμα                                                          |
| ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Άμεσες δοκιμές συμπεριφοράς και οι παραπάνω πύλες κατηγοριών                                                 | Κατανεμημένη πλήρης σουίτα δοκιμών μονάδας και σειριακές δοκιμές                    |
| `npm run lint`                                                                                               | Σουίτες Vitest και σταδιακά αυστηρότερα όρια κάλυψης/ποιότητας                      |
| Έλεγχος τύπων ή build μόνο όταν το απαιτεί το επηρεαζόμενο συμβόλαιο                                         | Build παραγωγής, ασφάλεια, τεκμηρίωση, εξαρτήσεις και πύλες πολιτικής PR            |
| Χειροκίνητη αλληλεπίδραση/ζωντανοί έλεγχοι μόνο όταν ο αυτοματισμός δεν μπορεί να επαληθεύσει τη συμπεριφορά | Έλεγχοι ενσωμάτωσης μεταξύ εργασιών και πλατφορμών, ρυθμισμένοι από τη ροή εργασίας |

Ένας επιτυχής εστιασμένος βρόχος αποτελεί ένδειξη για το τροποποιημένο συμβόλαιο, όχι απόδειξη ότι θα
περάσουν άσχετοι έλεγχοι CI. Αντίστροφα, μην αναγκάζετε κάθε τοπική επεξεργασία να περιμένει την πλήρη μήτρα του αποθετηρίου.

## Λίστα ελέγχου συμφιλίωσης

Πριν ζητήσετε αναθεώρηση:

- Επιβεβαιώστε ότι η βάση του PR εξακολουθεί να είναι ο υψηλότερος ενεργός κλάδος `release/v*`.
- Ανακτήστε αυτήν τη βάση και εξετάστε τα commits που ενσωματώθηκαν από τότε που δημιουργήσατε τον κλάδο σας.
- Εξετάστε το `git diff <active-base>...HEAD` για ακούσιες αλλαγές ή αλλαγές σε παραγόμενο περιεχόμενο.
- Επιλύστε διενέξεις σε καταλόγους και παραγόμενα έγγραφα ενημερώνοντας την πηγή και δημιουργώντας εκ νέου το αποτέλεσμα.
- Εκτελέστε ξανά κάθε εστιασμένη δοκιμή/πύλη που αναφέρεται στην περιγραφή του PR μετά τη συμφιλίωση.
- Μην αποδυναμώνετε ποτέ τους ισχυρισμούς και μην παραλείπετε απαιτούμενες δοκιμές μόνο και μόνο για να ευθυγραμμιστείτε με μια βάση που μετακινήθηκε.

Για τους κανόνες παγώματος κυκλοφορίας και αλλαγής στόχευσης, χρησιμοποιήστε το
[Μοντέλο διακλάδωσης και κυκλοφοριών](BRANCHING_MODEL.md). Για την πλήρη απογραφή του CI, χρησιμοποιήστε την
[Αναφορά πυλών ποιότητας](../architecture/QUALITY_GATES.md).
