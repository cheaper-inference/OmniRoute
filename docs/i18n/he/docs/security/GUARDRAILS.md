> **מקור האמת:** `src/lib/guardrails/`
> **עודכן לאחרונה:** 2026-10-17 — v3.8.52 (נוסף [כיסוי ומגבלות](#coverage-and-limits):
> אילו נתיבים ומסלולי תגובה ההוקים מגיעים אליהם, כותרות ההשבתה הממוזגות (#16412), מצב חסימת
> הזרקה כגבול מחייב (#16413), ומה רואה תגובה לפני post-call)

Guardrails אוכפים בטיחות, מדיניות וטרנספורמציות תוכן בגבול שבין
OmniRoute לספקי upstream. כל guardrail יכול לבדוק (ובאופן אופציונלי
לדחות, להמיר או להוסיף הערות על) מטעני בקשות (`preCall`) ותגובות
מספקי upstream (`postCall`).

המערכת היא **fail-open**: אם guardrail זורק שגיאה במהלך הביצוע, הרג'יסטרי
מתעד את השגיאה וממשיך ל-guardrail הבא במקום להכשיל את הבקשה. חסימה היא
החלטה מפורשת (`block: true`), לעולם לא תאונה.
היוצא מן הכלל היחיד הוא בקשה שבוטלה: כאשר ה-`signal` של הקורא מבוטל,
guardrail שזורק שגיאה דוחה את ריצת ה-hook במקום לדלג.

ההוקים **לא** רצים בכל נתיב או על כל תגובה. קראו
[כיסוי ומגבלות](#coverage-and-limits) לפני הסתמכות על guardrail כבקרת
אבטחה.

### גשר ראייה (`visionBridge.ts`) — PR-1 של גשר המודאליות

למודל הבסיסי GLM 5.3 ול־`glm-5.3-{low,high,max}` קיימת במפורש
מטא־דאטה של רישום/מפרט `supportsVision:false`. גרסאות GLM 5.3 Flash
נותרות מודלים בעלי ראייה טבעית. הנתיב `/v1/messages` של Claude Code נכנס
לשרשרת מעקות ההגנה המשותפת של `handleChat` לפני התרגום מ־Claude ל־OpenAI;
יש לתאר או לטפל בתמונות של תוצאות כלי `Read` המקוננות לפני שהתרגום הזה
מעלה אותן לתוכן `image_url` של OpenAI (#17069).

מיירט בקשות המכילות תמונות המיועדות למודלים **ללא ראייה**, ובמקום זאת
מנתב מחדש את הבקשה כולה למודל בעל יכולת ראייה או מחליף את חלקי התמונה
בתיאורי טקסט שהופקו על ידי מודל ראייה שניתן להגדיר, לפני הקריאה לספק
החיצוני. כך ספקים מבוססי טקסט בלבד יכולים לטפל בשקיפות במטענים
מולטי־מודאליים.

זרימה:

1. דילוג אם מודל היעד כבר תומך בראייה (אלא אם הוא מופיע ברשימת הגישור הכפוי `isVisionBridgeForcedModel`).
2. חילוץ חלקי תמונה באמצעות `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), שמאציל את העבודה ל־**מזהה המדיה המאוחד**
   `detectMediaParts()` בתוך `open-sse/utils/mediaParts.ts` — מקור האמת
   היחיד המשותף למסנן התאימות המשולב. החילוץ מוגבל לרשימת הצורות
   ש־`replaceImageParts` יכול לשלב בחזרה (חוזה החילוץ↔ההחלפה): `image_url`
   של OpenAI, `source.type:"base64"` של Anthropic, כתובת URL של Anthropic
   `source.type:"url"`, ו־`input_image` של Responses API. תמונות תואמות
   המקוננות בתוך `tool_result.content` של Claude Code ופלטי כלים של Responses
   מחולצות ומוחלפות גם הן בנתיבים המקוריים שלהן; צורות המצביעות בלבד הן
   חומר למסנן המשולב ואינן מחולצות.
   דילוג אם לא נמצאו תמונות.
3. פתרון תצורת זמן הריצה באמצעות `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): מפתחות ההגדרות החדשים
   `modalityBridge*` גוברים; מפתחות `visionBridge*` מדור קודם נשארים
   **חלופה למחזור אחד** (חלון חזרה לאחור). דילוג לפני מעבר על מדיה כלשהי
   כאשר הגשר מושבת.
4. בורר המצבים (`modalityBridgeVisionMode`, ראו את הטבלה להלן) מחליט בין
   ניתוב מחדש לתיאור. ניתוב מחדש מחזיר `modifiedPayload` שבו הוחלף רק
   `model`, וכן מטא־נתונים `{ rerouted, fromModel, toModel, imagesKept }`.
5. נתיב התיאור: הגבלת מספר התמונות ל־`maxImages`, הרכבת הנחיה מודעת־משימה,
   בדיקת מטמון התיאורים, קריאה למודל הראייה **במקביל**
   (`Promise.allSettled`), והזרקת חלקי טקסט `[Image N]: <description>` במקום
   המתאים להם. תיאור שנכשל מחזיר `null`: התמונה הגולמית נשמרת עבור יעדים
   לא ידועים/בעלי יכולת ראייה (#4012), אך יעד ישיר מאומת של טקסט בלבד
   או שילוב ללא ראייה מקבלים במפורש מציין טקסט
   `(unavailable — no vision-capable provider connected)` עבור כל תמונה
   שלא תוארה, כולל כשלונות חלקיים ותמונות שמעבר למגבלת קריאות התיאור
   (#17069). חלופת תיאור השילוב הקיימת במקרה שבו כל התיאורים נכשלו
   נשארת במקומה (#8430).
6. החזרת `modifiedPayload` ומטא־נתונים (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### בורר המצבים (`modalityBridgeVisionMode`)

| מצב        | ברירת מחדל | התנהגות                                                                                                                                                                                                                  |
| ---------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔          | היוריסטיקה מדור קודם, ללא שינוי (#6640/#7204): מודלים שאינם שילוביים/מודלי `auto/` מנותבים מחדש למודל הראייה הטוב ביותר, אלא אם למודל המקורי כבר קיימות הרשאות שימושיות (ואז מתבצע תיאור); יעדי שילוב תמיד מקבלים תיאור. |
| `describe` |            | תמיד מתאר — בלוק הניתוב מחדש נעקף לחלוטין; המודל שהמשתמש בחר תמיד מספק את התשובה.                                                                                                                                        |
| `reroute`  |            | כפיית ניתוב מחדש: מעקף של בדיקת המודל בעל ההרשאות. בדיקת ההרשאות של **יעד** הניתוב מחדש עדיין חלה — כאשר לא קיים יעד ראייה שמיש, הגשר חוסם עם שגיאה ברורה במקום לתאר או לשלוח תמונות גולמיות ליעד טקסט בלבד.             |

מצבים כפויים מקצרים את הדרך לפני הפעלת היוריסטיקה האוטומטית; ההתנהגות של
`auto` זהה ברמת הבתים להתנהגות מעקה ההגנה שלפני PR-1.

#### תחום מפתח ה־API (`visionBridgeKeyScope.ts`)

כאשר מפתח ה-API של המתקשר מגביל את `allowedConnections`, את מאגרי המכסות
(`allowedQuotas`) או את המודלים (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), הגשר בוחר רק
מודלי ניתוב מחדש ותיאור שבהם המפתח רשאי להשתמש, ורק בחיבורים שבהם המפתח רשאי
להשתמש. לאחר מכן קריאת התיאור עוברת תמיד דרך הלולאה העצמית של OmniRoute עם
הכותרת `x-omniroute-self-loop-key-id`, כך שבקשת הצ'אט המקבלת אוכפת שוב את
מדיניות החיבור והמודל של אותו מפתח. `enforceApiKeyPolicy()` מכבדת את הכותרת הזו
רק יחד עם אסימון הנשיאה של הלולאה העצמית, ולכן היא יכולה רק לצמצם גישה, ומזהה
שלא ניתן לפתור נדחה.

אם שום מודל ראייה אינו מורשה עבור המפתח, **יעד מאומת לטקסט בלבד** דוחה את
בקשת התמונה באופן מקומי עם HTTP 400 ברור, במקום להעביר בתים של תמונה לשרת
עורפי שאינו מסוגל לטפל בהם (#17069). עבור יעדים בעלי יכולת ראייה לא ידועה או
ילידית, נתיב התיאור שומר על התנהגות ה-fail-open הקודמת שלו (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
בקשות ללא מפתח, ומפתחות ללא מגבלות אלה, מתנהגות בדיוק כפי שהתנהגו קודם.

#### הנחיית תיאור מודעת למשימה (`modalityBridgeVisionTaskAware`)

ברירת המחדל היא **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`)
מצרפת את הטקסט של **הודעת המשתמש האחרונה** (מקוצרת ל-500 תווים) להנחיית
התיאור הבסיסית, ומכוונת את התיאור למה שהמשתמש ביקש בפועל (תבנית
codex-vision-proxy), וכן מבקשת ממודל הראייה לתמלל טקסט גלוי. כאשר הדגל כבוי —
או כשאין טקסט משתמש — נעשה שימוש בהנחיה הבסיסית ללא שינוי.

בקשת OpenAI-compatible של הלולאה העצמית של התיאור
(`callVisionModelSingle()` ב-`visionBridgeHelpers.ts`) מבקשת תמיד
`image_url.detail: "high"` — ללא תנאי, עבור כל מתקשר/ספק, וללא תלות באות
כלשהו מהלקוח. דגימה ברמת פירוט נמוכה פוגעת בדיוק ה-OCR עבור משימת תמלול
הטקסט שהנחיה זו מבקשת, ולכן קריאת התיאור עצמה מבקשת תמיד רמת פירוט גבוהה,
ללא קשר לרמת הפירוט שבה השתמשה הבקשה הנכנסת המקורית. הדבר משפיע רק על גוף
בקשת התיאור הפנימית; הוא אינו משנה את האופן שבו OmniRoute מעביר את
`image_url.detail` של המתקשר בבקשה הראשית — ברירת המחדל הזו מוחלת בנפרד, ורק
עבור לקוחות OpenCode שזוהו, בתוך
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). לענף
פורמט התקשורת של Anthropic בלולאה העצמית של התיאור אין שדה `detail`, והוא אינו
מושפע מאף אחת מברירות המחדל.

#### הגבלת פלט התיאור (`modalityBridgeVisionMaxChars`)

| מפתח                           | ברירת מחדל | טווח             |
| ------------------------------ | ---------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` או 100–50000 |

`0` (ברירת המחדל) פירושו **ללא הגבלה** — התיאור המוחזר על ידי
`callVisionModel()` מועבר ללא שינוי, תוך שמירה על ההתנהגות הקיימת. כל ערך
בטווח 100–50000 מקצר את התיאור עם סיומת `…` לפני שהוא משולב מחדש בתור
`[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` בתוך `src/lib/guardrails/visionBridge.ts`).
הגדילו ערך זה עבור משימות OCR עתירות פרטים שבהן המודל במורד הזרם זקוק לתמלול
המלא; הקטינו אותו כדי להגביל את צריכת האסימונים במודלי ראייה מילוליים.
שדה לוח הבקרה נמצא בחלונית Advanced של לשונית Vision
(`modality-bridge-max-chars` בתוך `ModalityBridgeVisionTab.tsx`) ומגביל כל
ערך בין 1 ל-99 כלפי מעלה לרצפה של 100, תוך השארת `0` מפורש ללא שינוי — `0`
הוא ערך Zod תקף בפני עצמו
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ולא רק
ברירת המחדל של "לא מוגדר".

#### מטמון התיאור (`modalityBridge/bridgeCache.ts`)

מטמון LRU + TTL בזיכרון עבור פלטי תיאור, המשותף לכל התהליך.
המפתח = `sha256(imageRef + composedPrompt + configuredBridgeModel)` עם מסגור
באמצעות קידומות אורך (ללא התנגשויות בגבולות שדות). רכיב המודל הוא מודל הגשר
**שהוגדר**, ולא המודל שסיפק בפועל את התשובה —
`callVisionModel` עשויה לבצע נסיגה פנימית, ויצירת מפתח לפי כל ניסיון הייתה
מפצלת את המטמון. תיאורים שנכשלו לעולם אינם נשמרים במטמון. הגדרות:

| מפתח                            | ברירת מחדל | טווח    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### נרמול תמונות מרוחקות (תיאור בלולאה העצמית/שליפה כ-base64)

כאשר הגשר שולף בעצמו תמונה **מרוחקת** — קריאת התיאור העצמית של Anthropic והמרת
ה-base64 בפורמט התקשורת של claude
(`ensureBase64ImagesForClaudeWire`), שתיהן באמצעות
`fetchRemoteImageAsDataUri()` בתוך `visionBridgeHelpers.ts` — ה-URI של הנתונים
המופק מועבר דרך `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) לפני שהוא משובץ בבקשת מודל הראייה.
תמונות גדולות מדי מוקטנות כך שהקצה הארוך יהיה **2048px** (בהתאם למגבלת
הגודל שכבר מוחלת בצד השרת של OpenAI/Anthropic), וכך מצטמצמים נפח ההעלאה וזמן
ההשהיה בלי לשנות את מה שמודל הראייה רואה. שינוי הגודל משתמש ב-`sharp`,
שנטען באמצעות ייבוא דינמי: בפלטפורמה שבה הקובץ הבינארי המקורי שלו אינו נטען
בהצלחה, `normalizeDataUri()` **לעולם אינה זורקת** — היא חוזרת להעביר את הבתים
המקוריים ללא שינוי, כך שנתיב התיאור/ההמרה ל-base64 ממשיך תמיד לפעול. בתים
שאינם תמונה (שליפה שלא החזירה תמונה שניתנת לפענוח) מועברים גם הם ללא שינוי.
נרמול זה חל רק על תמונות שהגשר שולף עבור הקריאה העצמית שלו — הוא לעולם אינו
מוחל על מטען ה-passthrough הגולמי של המתקשר, בהתאם לעקרון השינוי
בהצטרפות מפורשת בלבד (Hard Rule #20).

#### סכמת הגדרות + הגירה

המפתחות החדשים `modalityBridge*` עוברים אימות באמצעות Zod בתוך `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, שלישיית המפתחות `modalityBridgeCache*`, וקבוצת
`modalityBridgeAudio*` המשמשת את Audio Bridge. המיגרציה
`141_modality_bridge_settings.sql` מעתיקה ערכי `visionBridge*` מדור קודם למפתחות
החדשים התואמים (אידמפוטנטית, ולעולם אינה מחליפה ערך `modalityBridge*` שהוגדר
על ידי מפעיל); המפתחות מדור קודם עדיין מתקבלים כחלופה לקריאה במשך מחזור גרסה
אחד.

#### כותרת שקיפות + סטטיסטיקות

תגובות שעברו תיאור כוללות
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(נבנה על ידי `buildModalityBridgeHeader()` בתוך `modalityBridge/bridgeStats.ts`,
ומוטבע באמצעות `withModalityBridgeHeader()` בתוך `src/sse/handlers/chatHelpers.ts`).
בקשות שנותבו מחדש אינן מקבלות כותרת — גוף המטען לא השתנה, והחלפת המודל כבר
גלויה בשדה `model` של גוף התגובה.

`GET /api/modality-bridge/stats` (אימות ניהולי, באותה רמת הרשאה כמו
`GET /api/settings`) מחזיר את המונים הזמניים בזיכרון לפי סוג מדיה
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` עבור `vision`, `audio` ו-`video`.
`averageLatencyMs` משתמש ב-`latencySamples` כמכנה, ולא בכל הניסיונות; פעולה ללא
מדידת זמן אינה ממציאה דגימה של אפס מילישניות. `bridged` נותר כינוי תואם לאחור
להמרות מוצלחות; ניסיונות שנכשלו אינם מגדילים אותו.
המונים מתאפסים בעת הפעלה מחדש של התהליך, בכוונה
(טלמטריה, לא הנהלת חשבונות).

#### תצורת לוח המחוונים

הדף הייעודי בלוח המחוונים הוא
`/dashboard/settings/modality-bridge`. הלשוניות `Vision`, `Audio` ו-`Video`,
שניתן לפנות אליהן באמצעות כתובת URL, משמרות את פרמטרי השאילתה בעת החלפה של
ערך `tab`. הלשונית Vision חושפת הפעלה, מצב, בחירת מודל (כולל ברירת המחדל
האוטומטית), הנחיות התלויות במשימה, מגבלות מתקדמות של פסק הזמן/מספר התמונות/
אורך התיאור/מטמון, מונים בזמן ריצה ובקשת דוגמה מוגנת. גם הלשונית Audio פעילה:
היא חושפת הפעלה, בורר מודלים המיועד ל-STT בלבד עם Auto, מגבלות פסק זמן/אורך
קטע מרבי, מוני שמע ובדיקת דוגמה של `input_audio`. הלשונית Video פונקציונלית:
היא מדווחת על מצב זמן הריצה של FFmpeg/ffprobe — אחד מארבעה מצבי ממשק משתמש
מפורשים (`unknown` בזמן שהבדיקה מתבצעת או כאשר לא ניתן היה להשלים אותה,
`restricted` במארח לוח מחוונים שאינו loopback, כאשר הבדיקה מדולגת בצד הלקוח,
`unavailable` לאחר שהבדיקה הסתיימה ואישרה שהרכיב חסר, או `available` עם גרסאות
FFmpeg/ffprobe) — משמרת מגבלות הפעלה/מודל/פריימים/וידאו/פסק זמן, מסננת את בורר
המודלים כך שיכלול רק מודלים בעלי יכולות ראייה וחושפת מוני וידאו.

כרטיס Vision Bridge הקודם תחת הגדרות AI הוא קישור תאימות לדף החדש; הוא כבר
אינו מנהל עותק נוסף של הטופס. גם Media Providers מקשר תהליכי Image-to-Text
ו-Speech-to-Text ללשוניות Modality Bridge המתאימות, מבלי להסיר את סביבת
הניסוי הקיימת של Speech-to-Text.

**עקיפת קבלה עבור לולאה עצמית:** כאשר קריאת התיאור מנותבת דרך לולאת
`/v1` העצמית של OmniRoute (מודל ספק שאינו סטנדרטי), בקשת המשנה שולחת
`x-omniroute-admission-bypass: internal` ומאומתת באמצעות פרטי הכניסה שנפתרו
עבור הלולאה העצמית — סמן `sk_omniroute` המקומי במצב מקומי, או מפתח הסביבה
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` שהוגדר על ידי המפעיל (#1350), כך שגם
פריסות שבהן `REQUIRE_API_KEY=true` יוכלו עדיין להריץ את קריאת התיאור. העקיפה
מכובדת רק עבור פרטי הכניסה המדויקים האלה, ולכן לקוחות חיצוניים אינם יכולים
להשתמש בכותרת כדי לדלג על הקבלה.

ברירות המחדל מדור קודם נמצאות ב-`src/shared/constants/visionBridgeDefaults.ts`;
ברירות המחדל החדשות של מצב/תלות במשימה/מטמון ופותר ההגדרות נמצאים ב-
`src/shared/constants/modalityBridgeDefaults.ts`. מנגנון ההגנה חושף אפשרות
בנאי `deps`, כדי שבדיקות יוכלו להזריק מימושים מדומים של `getSettings` ושל
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

מיירט בקשות צ'אט המכילות שמע לפני שהן מגיעות ליעד שאינו ידוע כתומך בקלט שמע.
הוא לעולם אינו מנתב מחדש את בקשת הצ'אט: חלקי השמע מתומללים דרך נקודת הקצה
הקיימת, התואמת ל-OpenAI, עבור multipart, ומודל הצ'אט שנבחר ממשיך עם תמלילי טקסט.

תהליך:

1. פתרו את `supportsAudio` באמצעות `getResolvedModelCapabilities()`. מטא־נתונים מפורשים של רישום הספק גוברים תחילה, לאחר מכן מטא־נתונים סטטיים של המודל, ולבסוף
   `modalities_input` המסונכרן. רשימת קלט מוצהרת ללא `audio` היא `false`; כאשר לא נותרת ראיה ליכולת, הערך הוא `null`. גם `false` וגם `null` מפעילים את הגשר השמרני, ואילו `true` עוקף אותו.
2. פתרו את הגדרות `modalityBridgeAudio*` וחלצו חלקי שמע עליונים הניתנים לשילוב מכל הודעה באמצעות המזהה המשותף `detectMediaParts()`. צורות התעבורה הנתמכות הן `input_audio` ו־`audio_url` של OpenAI, וכן `source.media_type: "audio/*"`. שמע מקונן מזוהה לצורך ניתוב, אך אינו מוסר בנתיב השילוב. העבודה מוגבלת באמצעות `modalityBridgeAudioMaxClips`; החלקים המאוחרים יותר נותרים ללא שינוי.
3. כבדו הגדרה של `provider/model`, או אפשרו ל־`selectAudioBridgeModel()` לעבור על `AUDIO_TRANSCRIPTION_PROVIDERS` לפי סדר הקטלוג היציב ולבחור את המודל הראשון שספק פעיל עבורו מחזיק בפרטי התחברות שמישים.
4. `callAudioTranscription()` ממיר שמע בקידוד base64 או ב־data URI לקובץ multipart בשם `file`, או מוריד `audio_url` מרוחק באמצעות מנגנון הגנת היציאה הציבורית בלבד, עם הצמדת DNS והגבלה של 25 MB. לאחר מכן הוא שולח POST לקובץ ולמודל שנבחר דרך לולאת העצמי המקומית `/v1/audio/transcriptions`, כשהוא מאומת באמצעות `resolveSelfLoopBearer()`. נתיב התמלול הקיים מבצע חיפוש רגיל של פרטי התחברות, טיפול בתקופות צינון ובהגבלת קצב, ושיגור לספק.
5. קריאות שהצליחו מחליפות את החלקים שלהן ב־`[Audio N]: <transcript>`. הקריאות מופעלות באמצעות `Promise.allSettled`: כישלון יחיד משמר את חלק השמע המקורי (#4012 contract). אם כל הקריאות נכשלות והוכח שליעד יש `supportsAudio === false`, החלקים הופכים ל־
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 contract). עבור יעד לא ידוע (`null`), תוצאה שבה כולן נכשלו נותרת ללא שינוי. יעד שהוכח שהוא תומך בטקסט בלבד, ללא פרטי התחברות שמישים של STT, מקבל את אותו קבוע מפורש בלי לבצע קריאת רשת.

תמלולים שהצליחו משתמשים במטמון LRU/TTL של Modality Bridge, המשותף לכל התהליך. המפתח משלב את הפניה לשמע, את תווית הפעולה היציבה
`audio-transcription`, ואת מודל ה־STT שנבחר; כישלונות לעולם אינם נשמרים במטמון. ניסיונות שמע מעדכנים את המונים המשותפים `bridged`, `cacheHits`, `failures` ו־`lastUsedAt`.
תגובות שעברו שינוי כוללות
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; בקשות שלא השתנו אינן מקבלות מקטע Audio Bridge.

הגדרות זמן הריצה נשמרות במסד הנתונים ונבדקות באמצעות Zod:

| מפתח                          | ברירת מחדל | טווח           |
| ----------------------------- | ---------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —              |
| `modalityBridgeAudioModel`    | `""`       | Auto או STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10           |

המטמון המשותף עדיין נשלט באמצעות
`modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` ו־`modalityBridgeCacheMaxEntries`.

### גשר וידאו (`videoBridge.ts`, `videoBridgePipeline.ts`)

מיירט חלקי וידאו עליונים ב־Chat Completions `messages` וב־Responses
API `input`, לפני קריאה ליעד שאין לגביו תמיכה טבעית ידועה בווידאו.
הצורות הנתמכות הן `input_video`, `video_url`, `video_source`, כתובות HTTPS,
ו־data URI מסוג `data:video/*;base64,...`. שמות קבצים רגילים בתוך טקסט אינם נחשבים לווידאו.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) אחראי על מעבר על הבקשה, בדיקת היכולת והמדיניות, צבירה לכל בקשה, ומטען התגובה.
העבודה לכל סרטון — רכישה, מטמון התוצאה המלאה, תיאור רצף פריימים
(המאחד כל תמלול שמע שהוצהר על ידי הקורא), ומדדים, ביטול וניקוי לכל ניסיון — מוסתרת מאחורי `processVideoPart` בתוך `videoBridgePipeline.ts`, הנקרא פעם אחת לכל חלק וידאו בתוך הלולאה של `preCall`.
מודול זה מגדיר גם את גבולות היציאה המפורשים `VideoMediaBrokerPort`
(רכישת בתים וחילוץ פריימים נדגמים), `VideoAudioTranscriptionPort` (מיזוג תמלול שמע שהוצהר על ידי הקורא עם הכיתובים שנדגמו), ו־`VideoDrilldownPort` (גבול ההתמדה של פירוט הפריימים; עדיין אינו מחובר ל־`processVideoPart` — כיום רק הנתיב הנפרד `/api/modality-bridge/video/drilldown` כותב רשומות פירוט).

נתיב הבקשות הציבורי `/v1` לעולם אינו מייבא או מפעיל תהליך משנה. סרטונים מרוחקים מורדים תחת הגבלה של 50 MiB; לסרטוני base64 מוטבעים קיימת הגבלה שמרנית של 36 MiB לאחר פענוח לכל סרטון, כדי שמעטפת המודל/ההודעות/המסגור תישאר בתוך מגבלת הקבלה של בקשת JSON ציבורית בגודל 50 MiB. אומדני האורך והגודל לאחר פענוח של תוכן מוטבע נבדקים לפני הקצאה. HTTPS נדרש בכתובת המרוחקת הראשונית ובכל הפניה, באמצעות מנגנון הגנת היציאה הציבורית הקיים עם הצמדת DNS. לאחר מכן הבתים עוברים דרך גבול הברוקר הפנימי המדויק
`POST /api/modality-bridge/video/extract`. נתיב זה הוא גם `LOCAL_ONLY` וגם `SPAWN_CAPABLE`, מקבל רק בקשה מאומתת לכל תהליך ומהימנה דרך loopback, ולעולם אינו מקבל כתובת URL, נתיב במערכת הקבצים, קובץ הרצה או רשימת ארגומנטים. צינור גודל גוף ה־API וקורא הגוף המצטבר של המטפל אוכפים כל אחד באופן בלתי תלוי מגבלה של 50 MiB על קלט הברוקר. התור המוגבל שלו מריץ חילוץ אחד בכל פעם, מאפשר ארבע משימות ממתינות, ומגביל את הקלט הממתין ל־100 MiB.

בתוך ה־broker, `ffprobe` קורא קובץ מקומי פרטי; רשימת ההיתרים של הפורמטים
הקבועה אינה כוללת פורמטים של רשימות השמעה ומניפסטים. עבור מכלים ממשפחת MOV
המותרים, הפניות נתונים חיצוניות של MOV נותרות מושבתות כברירת מחדל, והפקודה
הקבועה אינה מפעילה אותן. גם `ffprobe` וגם `ffmpeg` משתמשים ברשימת היתרים של
פרוטוקול `file` בלבד, ב־thread אחד, במערכי ארגומנטים קבועים, ללא shell,
ובקובצי הפעלה שנפתרים מתוך `PATH`. זרמי תמונת־עטיפה המצורפים אינם מועמדים
הניתנים לניגון. כל הזרמים הניתנים לניגון חייבים לעמוד במגבלות, וזרם ברירת מחדל
מפורש מועדף לפני חלופת ברירת המחדל הדטרמיניסטית בעלת האינדקס הנמוך ביותר.
סרטונים מוגבלים ל־600 שניות, ל־8,192 פיקסלים בכל ממד, ול־33,554,432 פיקסלי
מקור. FFmpeg דוגם 1–16 פריימי JPEG בנקודות אמצע, מקטין את הצלע הארוכה לכל
היותר ל־1,024 פיקסלים בלי להגדיל קלטים קטנים יותר, ולעולם אינו מקבל URL.
הדגימה היא `uniform` כברירת מחדל. המדיניות האופציונלית `scene_aware` והמדיניות
הניסיונית `segment_aware` מבצעות מעבר FFmpeg קבוע נוסף על הזרם המקומי שכבר
עבר אימות, בוחרות חותמות זמן מוגבלות של סצנות באמצעות `showinfo`, וחוזרות
באופן דטרמיניסטי לאותן נקודות אמצע אחידות במקרה של כשל בגלאי, חריגה ממגבלת
זמן, פלט פגום או קבוצת מועמדים ריקה. מצב `segment_aware` מקצה דגימות אמצע
באופן יחסי למרווחי הסצנות שאומתו; הראיות וההתנהגות במקרה של חזרה לאחור של
`segment_aware` מפורטות להלן. מגבלת 16 הפריימים הקשיחה מוחלת לאחר הבחירה
בכל מדיניות. כאשר לבקשת `scene_aware` יש תקציב של פריים אחד בלבד, היא משתמשת
בנקודת האמצע האחידה של חלון הסרטון המלא או חלון המיקוד הפעיל ומדווחת
`policyEffective: uniform`: פריים סצנה יחיד שנבחר לא יכול לשמר את שני הקצוות
הזמניים. קורא יכול לספק באופן אופציונלי חלון מיקוד סופי (`start`/`end`
בשניות); הגבולות נחתכים למשך המדיה, חלונות הפוכים או שאינם סופיים נדחים, וכל
מדיניות הדגימה מתבצעת רק בתוך המרווח המנורמל. החלון שנוצר נכלל במטא־נתוני
הדגימה ובקידומת התיאור הלא־מהימנה, כדי שמודלים במורד הזרם יוכלו להבחין בין
קטע ממוקד לבין ציר הזמן המלא.

מיקוד כיתוב סמנטי הוא הגדרה נפרדת ומפורשת. מצב הניתוח `full` כברירת מחדל
משמר את הנחיית הפריימים הקיימת ולעולם אינו מעביר את טקסט הבקשה למודל הכיתובים.
במצב `focused`, הגשר קורא רק את `text`/`input_text` האחרון שאינו ריק ונכתב
על־ידי המשתמש, מאותו מכל Chat או Responses, מנרמל אותו ל־NFC, מכווץ תווי
בקרה ורווחים, ומגביל אותו ל־500 נקודות קוד של Unicode. תוצאה ריקה חוזרת
להנחיית `full` המדויקת. רמז שמיש מסודר כ־JSON בבלוק ייעודי של הקשר משתמש
לא־מהימן, ויכול לכל היותר לתעדף פרטים ניתנים לתצפית; הוא אינו יכול לעקוף את
האזהרה הנפרדת מפני ביצוע הוראות הנראות או הנשמעות במדיה. מיקוד טקסטואלי לעולם
אינו מסיק `start`/`end` ואינו משנה את הדוגם הזמני.

#### ראיות מבניות של מקטעים FU-07

`segment_aware` משתמש במעבר ניתוח מקדים מוגבל אחד על זרם הווידאו המקומי שכבר
עבר אימות. שרשרת המסננים הקבועה מקטינה תחילה לרוחב של 320 פיקסלים לכל היותר,
מזהה שינויי סצנה ומרווחים קפואים, ולאחר מכן דוגמת בקצב של פריים אחד לשנייה
לצורך טשטוש, בהירות ממוצעת ומידע מרחבי/זמני. המעבר מוגבל ל־600 דגימות
מבניות, ל־thread אחד של FFmpeg/מסננים, לאותן רשימות היתרים של פרוטוקול
`file` ומכלים, למגבלת פלט תהליך של 1 MiB, ולכל היותר ל־30 שניות בתוך
הביטול/דדליין המשותף של ה־broker. הוא לעולם אינו מקבל מהבקשה פקודה, מסנן,
נתיב או URL.

הערכים המבניים הם ראיות של דגימה דטרמיניסטית, ולא הבנה סמנטית של וידאו. הם
אינם מסיקים נושאים, פעולות, כיתובים, דיבור או כוונת משתמש. גבולות סצנות
וקפיאה יוצרים מקטעים; כיסוי קפוא, טשטוש, חשיפה, פרטים מרחביים ושינוי זמני
משפיעים רק על אופן חלוקת תקציב 1–16 הפריימים הקיים. מקטע קפוא לחלוטין מוגבל
לפריים אחד, בעוד שמקטעים שאינם קפואים מתחרים על התקציב הנותר. כאשר מספר
הגבולות גדול ממספר הפריימים, נשמר כיסוי אחיד של ציר הזמן, כך שחיתוכים
מהירים בתחילת הסרטון לא יוכלו להסתיר מקטע ארוך בסופו. גבולות סצנה הנמצאים
בתוך רזולוציית הניתוח של שנייה אחת מגבול קפיאה מאוחדים.

מסננים חסרים, ראיות פגומות/ריקות, שגיאת גלאי או חריגה ממגבלת הזמן של הניתוח
המקדים והמוגבל נכשלים באופן פתוח למדיניות נקודות האמצע האחידות המדויקת. ביטול
של קורא או דדליין של ה־broker אינם נכשלים באופן פתוח: הם מסיימים את תהליך
המשנה הפעיל, מונעים חילוץ פריימים מאוחר יותר, ועץ הקבצים הזמני הפרטי מוסר
ב־`finally`.

`scripts/perf/video-bridge-fu07-eval.ts` יוצר fixtures דטרמיניסטיים אמיתיים
של FFmpeg עבור חיסכון בקריאות כיתוב לאחר הסרת כפילויות, הקצאת תקציב לתנועה
צפופה, ראיות טשטוש/חשיפה/SI-TI, חיתוכים מהירים עם זנב ארוך, וחיוביים שגויים
של עמעום הדרגתי. הוא מתעד את זמן הקיר של הניתוח המקדים, ובמקרים שבהם
`/usr/bin/time` זמין — את זמן ה־CPU של תהליך-הבן ואת RSS המרבי. בדיקות האיכות
שלו הן אורקלים מבניים בלבד. איכות מודל הכיתובים האמיתית נותרת `HOLD`, משום
שלרתמה זו אין נקודת קצה מורשית או שופט קפוא. גם החיסכון הכספי נותר `HOLD`,
אלא אם `--caption-cost-per-call-usd` מספק אומדן מפורש וחיובי לעלות לקריאה;
הסקריפט לעולם אינו ממציא אף אחת מהתוצאות.

כל פריים מוגבל ל־4 MiB, כל הפריימים הגולמיים יחד מוגבלים ל־23 MiB, ותגובת ה־broker שעברה סריאליזציה מוגבלת ל־32 MiB. ספרייה זמנית פרטית מוסרת ב־`finally`. OmniRoute אינה כוללת את FFmpeg ואינה מקבלת נתיב מותאם אישית לקובץ ההפעלה. לפני יצירת הכתוביות, הגשר מפעיל מעבר שמרני להסרת כפילויות חזותיות: כל JPEG מוקטן למאגר גווני אפור בגודל 16×16 ומושווה רק לפריים האחרון שנשמר. כאשר תקציב הכתוביות המבוקש גדול מפריים אחד, החילוץ מספק מאגר מועמדים מוגבל של עד פי שניים מהתקציב, ולעולם לא יותר מ־16 פריימים. התקרה המבוקשת מוחלת רק לאחר הסרת הכפילויות, כאשר המועמד הראשון והאחרון שנבחרו נשמרים במהלך הדילול הסופי אם התקציב הוא לפחות שניים. המדיניות המתומללת בגרסה
`grayscale-16x16-mean-cells-v2` משתמשת בערך הגדול יותר מבין הפרש הבהירות הממוצעת לבין היחס של תאי התמונות הממוזערות שההפרש המנורמל שלהם הוא לפחות 0.05. סף הכפילות הוא הקבוע 0.04, שנבחר לצורך יכולת חיזוי ולא נחשף כהגדרה בזמן ריצה. אות הניגודיות הגבוהה המשני הזה משמר תנועה קטנה ושינויים בטקסט גלוי שהשוואה המבוססת רק על ממוצע עלולה להסתיר. שגיאות השוואה או פענוח גורמות לפתיחה בטוחה של המעבר ושומרות על הכיסוי. מטא־נתוני הפלט מפרידים בין מועמדים שחולצו, פריימים שנעשה בהם שימוש בהצלחה, וכפילויות חזותיות שהוסרו.

חלק וידאו שסומן במפורש יכול לבקש גיליון תמונות ממוזערות עם חותמות זמן. הגשר בונה רשת JPEG של עד 4 עמודות ועד 16 פריימים. בכל תא בגודל 512 פיקסלים מוטבעת חותמת הזמן של המקור ברצועה תחתונה בעלת ניגודיות גבוהה, בעוד שאותן חותמות זמן נשארות גם במטא־נתונים הטקסטואליים לצורך שיוך וביקורת בהמשך. ה־JPEG המלא עדיין מוגבל ל־32 MiB. אם `sharp` אינו יכול לפענח או להרכיב את הרשת, הגשר חוזר לפריימי ה־JPEG הבודדים; ביטול מצד הלקוח עדיין מועבר דרך פעולת גיליון התמונות.

ראיות לקידום מופרדות במכוון ממיקרו־benchmark של הרכבה סינתטית. `scripts/perf/video-bridge-contact-sheet-eval.ts` מגדיר רתמת A/B עם גרסת סכימה עבור מודלי ראייה אמיתיים התואמים ל־OpenAI. היא מודדת אסימונים המדווחים על ידי הספק, השהיית קצה־לקצה (כולל הרכבת גיליון התמונות), מספר קריאות למודל ושימור עובדות שהוגדרו במניפסט. תגובות המודל הגולמיות אינן נכתבות לדוח; נשמרים רק תקצירי SHA-256 ומזהי עובדות תואמות. הרתמה אינה מבצעת קריאת רשת או קריאה למודל בתשלום אלא אם `--execute-real` הועבר ו־`--model`, `OMNIROUTE_BASE_URL` ו־`OMNIROUTE_API_KEY` מוגדרים. ללא הרצה אמיתית מפורשת זו, פסק הדין הקריא־למכונה שלה נשאר `HOLD`; מדידות סינתטיות של מטען ומספר קריאות לבדן אינן ראיות לקידום.

קוראים יכולים לצרף מערך אופציונלי בשם `transcript.cues` לחלק וידאו נתמך כאשר כבר מצוי בידיהם טקסט מסונכרן. כל רמז חייב לכלול `text`, מרווח `start`/`end` סופי בתוך משך הווידאו שנבדק, ו־`source` מרשימה מאושרת (`client`, `embedded` או `audio-bridge`); הערך של `confidence` הוא `1` כברירת מחדל והוא חייב להישאר בין `0` ל־`1`. רמזים זהים לחלוטין מאוחדים. OmniRoute לעולם אינה מתחילה תמלול ממטא־נתונים אלה: רמזים שעברו אימות מועתקים לתוצאה המתוארת יחד עם המקור, רמת הביטחון והמרווח, ומוצגים כתצפיות לא מהימנות לצד כתוביות הפריימים. טקסט לא תקין, מחוץ לטווח או נטול מקור נדחה במקום להתערבב בזרם הכתוביות. שני ערוצי התמלול בגוף הבקשה מנרמלים מקור שסופק ל־`client`, כולל תוויות `embedded` או `audio-bridge` שהוצהרו בעצמן. רק מתאם בבעלות השרת יכול להקצות את התוויות המהימנות הללו באמצעות הארגומנט `trustedSource` הקיים בקוד בלבד; שדה JSON בבקשה אינו יכול להגיע לארגומנט זה. טקסט התמלול נשאר תוכן לא מהימן שמקורו במדיה, ללא קשר למקורו, ולעולם אסור לו לקבוע הרשאות.

קורא מתקדם יכול לספק רצועת `audioTranscript` עבור אותו וידאו; היא מטופלת כטקסט שסופק על ידי הלקוח, ולא כהוכחה לתמלול שבוצע בשרת. נקודת החיבור של המיזוג מריצה תצפיות חזותיות ושמע תחת מועד אחרון ואות ביטול אחד, מסדרת אותן על ציר זמן משותף, מאחדת כפילויות זהות ומדווחת על תוצאה חלקית כאשר רק צד אחד מצליח. `audioTranscript` לא תקין מדרדר לתוצאה חלקית זו — התיאור החזותי נשמר וענף השמע מתעד קוד כשל שעבר חיטוי — במקום להכשיל את הווידאו כולו. הזמינות לכל ענף, הדגל המציין תוצאה חלקית וקודי הכשל שעברו חיטוי נשמרים בתוצאה המתוארת, במטא־נתוני אמצעי ההגנה (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), במטא־נתוני מטמון התוצאה ובמוני המיזוג של הגשר. נתיב ברירת המחדל של Video Bridge אינו מפעיל המרה מדיבור לטקסט או מוריד עותק מדיה נוסף; ללא רצועה מפורשת זו, הוא נשאר במצב וידאו בלבד.

**שימור תמליל (#12150 P1).** הדבר חל באופן אוטומטי בכל פעם שה־
Video Bridge (שהפעלתו היא opt-in) מרנדר קיו של תמליל — אין דגל שימור נפרד.
כאשר בקשה מרנדרת קיו כלשהו של תמליל (קיו `transcript` שהמפעיל הצהיר עליו או
`audioTranscript` ממוזג), מנגנון ההגנה מסמן אותה
`videoBridgeObserved` ומפיק צל של תיאור הווידאו לאחר השחרה —
רינדור זהה שבו גוף הטקסט החופשי של כל קיו מוחלף ב־
`[redacted-video-transcript]`, באמצעות החלפת שדה הקיו המובנה לפני הרכבת המחרוזת
(לעולם לא באמצעות ניתוח הטקסט השטוח, כך ששום תוכן של קיו — זדוני או רגיל,
לרבות גופים המכילים `]` כגון `[inaudible]`/`[music]` — לא יכול לשרוד). גוף
הבקשה ביומן השיחה הנשמר מחליף כל חלק טקסט שנגזר מהווידאו בצל המושחר הזה,
בהתאמה לפי שוויון תוכן; העוגן `fullText` נקרא מחדש ממטען מנגנון ההגנה שהושלם
לפני הקריאה, כך שההתאמה עדיין מצליחה לאחר שמנגנוני הגנה מאוחרים יותר בשרשרת
(משחיתי ה־PII והאישורים, בעדיפויות 10/95) כותבים מחדש את טקסט התיאור במקום,
ולאחר שהזרקת הנחיית המערכת/העברת הטיפול/הזיכרון משנה את מערך ההודעות. גוף
הבקשה שנשלח במעלה הזרם למודל אינו משתנה. בקשה שנצפתה גם אינה מאכלסת
Memory בר־קיימא (החילוץ הנגזר הן מהבקשה והן מהתגובה מדולג), כך שתשובת המודל
עצמה אינה יכולה להדהד טקסט של תמליל אל Memory.

**שדות וידאו גולמיים (#12430).** כאשר הגשר מופעל ותמיכת וידאו מקורית אינה
ידועה או חסרה, שדות `transcript`/`audioTranscript` מוגדרים מפעילים גם הם את
`videoBridgeObserved`, אפילו לאחר כשל בתיאור או לאחר הגעה למגבלת
`maxVideos`. `null` ומחרוזות ריקות נחשבים; שדות חסרים ומטא־נתונים שאינם של
וידאו אינם נחשבים. עותקים נשמרים משחירים את השדות האלה או משמיטים את הבקשה,
והמטמונים/Memory עוקפים את התהליך.

במסלולי fallback אלה, קיואים תקפים של המפעיל הופכים לחלקי
`text`/`input_text` נתמכים במקום לשדות ספק שאינם סטנדרטיים. שני פסי התמלול
שסופקו בבקשה נשארים תצפיות `client` שאינן מהימנות, עם אזהרה מפורשת שהווידאו
לא תואר ושחותמות הזמן לא אומתו מול המדיה. תקציבי 256 קיואים/64 KiB הכוללים
והנפרדים לקיו הקיימים חלים יחד על שני הפסים; חותמות הזמן חייבות להתאים לתקרת
600 השניות של המתווך ולכל חלון מיקוד שסופק. פסים לא תקפים מושלכים ואינם
מועברים כטקסט שרירותי; עדיין ניתן להשתמש באח תקף, אלא אם התקציב המשולב שלהם
חורג מהמגבלה. שדות null/ריקים אינם מוסיפים טקסט. ה־fallback הזה אינו מוסיף
שליפת מדיה או תמלול. שדות ההרחבה של התמליל מוסרים ממוביל הווידאו של ה־fallback
ומאובייקטי `video_url`/`source` שלו. רשימת ההיתרים של התעבורה מול OpenAI
נותרת מחמירה; מובילי וידאו מקוריים שאינם מוכרים עדיין זמינים, ויעדים מוכרים
שהם טקסט בלבד שומרים על סמנים בטוחים. צללי השחרה מובנים מגינים על טקסט
התמליל שנוסף, בעוד שהבקשה המקורית שבבעלות המפעיל נותרת ללא שינוי. יעדים
הנתמכים באופן מקורי וגשרים מושבתים שומרים על התנהגות העקיפה הקיימת שלהם.

עותקים נשמרים נוספים משתמשים באותו אות של בקשה שנצפתה. תמונת המצב הגולמית
של בקשת הלקוח שלפני מנגנון ההגנה, הבקשה הממתינה בזיכרון, ויומן הבקשה שנדחתה
בשלב מוקדם מחליפים מבנית את שדות התמליל בחלקי הווידאו; הנחיות מחרוזת שנוצרו
בשלבי הצינור ובהעברת ההקשר מושחרות בנקודת הקליטה של גוף הבקשה הנשמר. הסמן
הנשמר `video_content_removed` גורם להמשך `previous_response_id` להיכשל
בסגירה בטוחה במקום לשחזר טקסט שהושלך בכוונה. אם בקשה שנצפתה מאבדת את צל
השחרת החלק שלה לפני הרישום, או אפילו אם אחד מכמה צללי וידאו אינו מצליח
להתאים לאחר שינויים מאוחרים בבקשה, גוף הבקשה הנשמר מושמט לחלוטין במקום
לשמור תמליל שהושחר חלקית.

עבור בקשה שנצפתה, תגובת מודל עשויה לצטט כל חלק מהתמליל ללא גבול קיו מובנה.
לכן `responseBody` של יומן השיחה הנשמר מוחלף בסמן השמטה; תוצר הצינור המפורט
(שיכול לכלול גופי upstream/לקוח ונתחי זרם) אינו נשמר. מטמוני סמנטיקה,
אידמפוטנטיות ושחזור חשיבה עוקפים קריאות וכתיבות עבור בקשה זו. בקשת הספק
והתגובה הנראית ללקוח נותרות ללא שינוי. בתים מוקדמים של keepalive נוקזים
מהחוצץ הזמני כאשר התוצר המפורט מושמט. האזהרה של Kiro על EventStream פגום
מדווחת רק על ספירת בתי המטען, ולעולם לא על תוכנם או על השגיאה הגולמית של
מנתח ה־JSON.
הדבר אינו טוען שכל אבחון בלתי קשור של ספק/תוסף עבר ביקורת; הסריקה הרחבה יותר
של יעדי השימור מתועדת ב־#11658.

מחזור החיים הפנימי `/api/modality-bridge/video/drilldown` הוא תשתית מטמון
נפרדת, המאומתת באמצעות loopback/token. כל פעולה דורשת גם מזהה עיקרון אטום
קנוני. לפני שמפעיל בסביבת production מופעל, עליו לגזור את המזהה הזה מהדייר
המאומת, ולעולם אסור לו להעביר ערך שנבחר על ידי הלקוח. מפתחות המטמון קושרים
את העיקרון למזהי session והפניות וידאו קנוניים, מאחסנים רק את המפתחות שנגזרו
מ־SHA-256, ומגבילים הן קריאות והן מחיקה לאותו עיקרון. המטמון מאחסן לכל היותר
16 פריימים נגזרי JPEG בכל רשומה, פג תוקפם לאחר עשר דקות, ותומך בקריאות
`start`/`end` מוגבלות או במחיקה מפורשת של session.

כל עיקרון מוגבל ל־16 רשומות ול־64 MiB של נתוני JPEG קנוניים. מגבלות אלה
נפרדות מתקרת 64 הרשומות/256 MiB הגלובלית: לחץ על מכסת עיקרון מפנה רק את
הרשומות שהיו בשימוש לאחרונה בתדירות הנמוכה ביותר של אותו עיקרון, לפני שנבחנת
פינוי LRU גלובלי. רשומות שפג תוקפן נסרקות הן מהחשבונאות של העיקרון והן
מהחשבונאות הגלובלית בעת פעילות במטמון, בעוד שביטול ואימות שנכשל אינם מקבעים
החלפה חלקית.

המטמון דוחה Base64 שאינו קנוני, ריפוד עודף, מדיה שאינה JPEG, קובצי JPEG פגומים או קטועים, וקובצי JPEG שמפיקים אזהרה במהלך פענוח `sharp` מלא ומוגבל של התמונה. הוא מקודד מחדש כל תמונה שהתקבלה כ-JPEG קנוני, מפיק את הרוחב והגובה מהבתים שפוענחו במקום לסמוך על שדות שסופקו על ידי הקורא, ומשליך בתים פוליגלוטיים שנותרו בסוף במקום לשמור אותם. רק המאגר הדחוס הקנוני והמוגבל מחויב בשתי המכסות. מגבלת ה-wire של JSON כוללת את תקורת Base64 עבור תקרת קלט מפוענח של 32 MiB. כל נגזרת שנשמרת מתעדת את פורמט ה-JPEG והרזולוציה שאומתו, את מדיניות הדגימה, את גרסת הנגזרת, את זמן היצירה, את גיבוב התוכן שחושב בשרת, ואת ההפניה ההאשית להורה יחד עם גיבוב תוכן ההורה של הקורא המהימן. ביטול נבדק בין שלבי הפענוח/הגיבוב האסינכרוניים ולפני ה-commit האטומי למטמון.

שלב זה עדיין אינו מחבר יצרן בסביבת ייצור לנתיב, ואינו מספק בחירת וריאנטים ברזולוציות מרובות. לכן נתיב הבקשה של Transparent Video Bridge אינו כרוך בעבודה נוספת, בעוד שגזירת principal הקשורה ל-tenant ומחזור החיים המלא של FU-08 ברזולוציות מרובות נותרו עבודת המשך מפורשת, ולא יתועדו כהתנהגות שהושלמה.

פריימים מקבלים כיתובים ברצף באמצעות מודל ה-Video שהוגדר. דריסת Video ריקה יורשת את הגדרת Vision; אם שתיהן ריקות, הנתב האוטומטי של Vision בוחר את המודל האפקטיבי שמסוגל לעבד חזותית. כיתובים מוצלחים מחליפים את החלק המקורי בקידומת יציבה `[Video description:` שמסמנת גם את הטקסט כתצפית לא מהימנה שמקורה במדיה, ומורה למודלים במורד הזרם שלא לציית להוראות שנמצאות במדיה. מפתחות המטמון של כיתובי פריימים כוללים את בתֵי ה-JPEG, את ההנחיה, את חותמת הזמן ואת המודל האפקטיבי; רק כיתובים מוצלחים נשמרים במטמון. רשומות המטמון שומרות את מודל היצרן המוצלח בפועל, כולל מודל חלופי; הגשר מדווח `mixed` כאשר פריימים שונים הופקו על ידי מודלים שונים. פגיעה במטמון משתמשת מחדש בזהות היצרן במקום לתייג אותה מחדש כתוכנית הניתוב המבוקשת. מטמון התוצאות של הסרטון כולו משתמש כמפתח בכל קלט שמשנה את הפלט — ההנחיה, המודל האפקטיבי, מדיניות הדגימה, מספר הפריימים, מצב הניתוח הסמנטי, טביעת האצבע SHA-256 של רמז המיקוד המנורמל, חלון המיקוד, `transcript`,‏ `audioTranscript`, ודגל גיליון הקשר — כך ששינוי בכל אחד מהממדים האלה גורם להחטאת מטמון, ולעולם לא לשימוש חוזר בנתונים מיושנים. גרסת מדיניות מניעת הכפילויות החזותית, הסף ומספר פריימי המועמד המוגבל מפורשים גם הם במפתח ובמטא-נתונים של מטמון התוצאות; לכן שינוי מדיניות אינו יכול לעשות שימוש חוזר בתיאור מיושן של סרטון שלם. מטא-נתוני מטמון התוצאות v4 שומרים את המצב ואת טביעת האצבע, ולעולם לא את משימת המשתמש הגולמית. מטא-נתוני אמצעי ההגנה מדווחים הן על מצב הניתוח המבוקש והן על המצב האפקטיבי; מצב `focused` מבוקש ללא טקסט שמיש מהמשתמש מדווח כ-`full` בפועל.

אמצעי ההגנה מחלץ כל חלק וידאו נתמך, אך מתאר לא יותר מ-`modalityBridgeVideoMaxVideos`. עבור יעד שהוכח כי `supportsVideo === false`, סרטונים שנכשלו או חרגו מהמגבלה הופכים לסמני טקסט בטוחים מפורשים, כך שלא יישאר וידאו גולמי. כאשר היכולת אינה ידועה, חלקים אלה שומרים על נשא הווידאו שלהם; כל תמלול חלופי עוקב אחר המרת הטקסט המוגבלת שתוארה לעיל. יעדים שבהם `supportsVideo === true` עוקפים את הגשר. אות ביטול בקשת הלקוח מועבר דרך ההורדה, תור הברוקר, תהליכי המשנה וקריאות הכיתוב; ביטולים עוצרים בין סרטונים ולעולם אינם מאפשרים מעבר כשל-פתוח למדיה גולמית.

הגדרות זמן הריצה נשענות על DB ומאומתות באמצעות Zod:

| מפתח                                | ברירת מחדל  | טווח / התנהגות                                                                         |
| ----------------------------------- | ----------- | -------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | זמן ריצה אופציונלי, הפעלה בהסכמה מפורשת                                                |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` משמר כיתובים כלליים; `focused` משתמש בהקשר מוגבל ולא מהימן של המשתמש האחרון     |
| `modalityBridgeVideoModel`          | `""`        | יורש את מודל Vision Bridge                                                             |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                   |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`,‏ `scene_aware`, או `segment_aware` פרופורציונלי; כשל בגלאי חוזר ל-`uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                    |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 אלפיות שנייה                                                               |

ערכי זמן קצובים של Video שנשמרו מדור קודם מעל 120 שניות נחתכים למועד האחרון של הברוקר; כתיבות הגדרות חדשות מעל מגבלה זו נדחות.
`GET /api/modality-bridge/video/runtime` דורש מקומיות loopback מהימנה וחתומה לפני אימות או בדיקת זמן הריצה, ולאחר מכן דורש אימות ניהולי. הוא מחזיר רק `available`, גרסאות FFmpeg/ffprobe שעברו ניקוי, וסיבה קבועה כאשר זמן הריצה אינו זמין. נקודת הקצה הפנימית לחילוץ אינה API ציבורי להעלאת קבצים: רוויה של התור מחזירה `503` יחד עם `Retry-After`, התנתקות של הקורא מחזירה `499`, ומועד הברוקר הקבוע מחזיר `504`. תגובות שעברו המרה מוסיפות
`video->text;model=<visionModel>;parts=<videos>` לכותרת המרכזית
`x-omniroute-modality-bridge` מבלי להסיר מקטעי Vision או Audio.

### ממסך PII (`piiMasker.ts`)

פועל בשני השלבים.

- **`preCall`** משכפל את המטען, עובר על `system`, ‏`messages`, ‏`input` ו־
  `prompt` (כולל פריטי מחרוזת פשוטים), ומחיל את `processPII()` (מ־
  `@/shared/utils/inputSanitizer`) על שדות `content`/`text` שהם מחרוזות. כאשר
  `PII_REDACTION_ENABLED=true`, מידע אישי שזוהה מושחר במטען היוצא. פעולה זו
  אינה תלויה ב־`INPUT_SANITIZER_MODE` (ששולטת רק במדיניות הזרקת ההנחיות).
  כאשר ההשחרה כבויה, הקריאה מתעדת את מוני הזיהויים מבלי לשכתב את התוכן.
- **`postCall`** משכפל לעומק את התגובה, מפעיל את
  `sanitizePIIResponse()` וכן את ממסך מבנה ה־Responses API
  (`maskResponsesOutput` — מכסה את `output_text` ואת
  `output[].content[].text`). אם מתבצעת השחרה כלשהי, התגובה ששונתה מחליפה את
  המקורית.

אמצעי ההגנה לעולם אינו חוסם; הוא רק מוסיף הערות (`meta.detections`,
`meta.redacted`) או משכתב.

#### בחירה לפי סוג, תבניות מותאמות אישית ומוני זיהויים

**לוח מחוונים → הגדרות → אבטחה → מיסוך PII** בוחר _מה_ יושחר. הוא
אינו מפעיל את ההשחרה: היא עדיין נשלטת על ידי `PII_REDACTION_ENABLED` (בקשה)
ועל ידי `PII_RESPONSE_SANITIZATION` (תגובה + SSE), ושניהם כבויים כברירת מחדל.

- **בחירה לפי סוג** — המזהים המובנים מפורטים ב־
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). ערך שלא הוגדר
  פירושו כל הסוגים (ההתנהגות שהייתה לפני שהגדרה זו נוספה). תבנית
  `ssn_us` של מנוע הבקשות ממופה ל־`ssn`. תבניות (Minimal, Standard, Financial,
  Brazilian, USA, GDPR, POPIA, Full) רק מסמנות את תיבות הסימון בממשק המשתמש.
- **מזהי GDPR ו־POPIA** — שנים־עשר מזהים מובנים המכסים מזהים אישיים
  אירופיים ודרום־אפריקאיים (הטבלה להלן). הביטויים הרגולריים, המאמתים ותגי
  תחום השיפוט שלהם נמצאים בטבלה אחת,
  `src/shared/utils/piiPatterns.ts`, שבה משתמשים גם מטהר התגובות
  (`src/lib/piiSanitizer.ts`) וגם ממסך הבקשות
  (`src/shared/utils/inputSanitizer.ts`). התאמה מושחרת רק כאשר המאמת מאשר
  אותה; רצף ספרות חשוף לעולם אינו מספיק. מפעיל ששמר בחירה מצומצמת לפני
  שהמזהים האלה היו קיימים ישמור על ההתנהגות שהייתה לו, עד שהמזהים החדשים
  יסומנו.
- **תבניות מותאמות אישית** — עד 20 תבניות רגולריות או תבניות wildcard
  (`*` = עד 64 תווים שאינם רווחים, `?` = תו אחד). התאמות הופכות ל־`[CUSTOM_REDACTED]`.
  כל תבנית עוברת דרך `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): לכל היותר 500 תווים, הדגלים
  מוגבלים ל־`g i m s u`, התבנית חייבת להתקמפל, לעבור את
  `safe-regex` (החזרה לאחור הרסנית), ואסור לה להתאים למחרוזת ריקה או למציין
  מיקום של השחרה. תבנית שנכשלת נדחית בעת השמירה ובעת הבדיקה, ושורה שמורה
  שנכשלת מדולגת בזמן הריצה במקום לעבור הידור. תבניות מותאמות אישית פועלות רק
  כאשר המיסוך מופעל.
- **מוני זיהויים** — ספירות לפי סוג (לעולם לא הערכים שנמצאו), נשמרות בזיכרון
  ומתאפסות בעת הפעלה מחדש (`src/lib/pii/piiDetectionStats.ts`). הן גדלות
  רק כאשר המיסוך מופעל.

ההגדרות נשמרות בטבלת `key_value` (במרחב השמות `pii_settings`,
`src/lib/db/piiSettings.ts`) ונקראות דרך מטמון של שנייה אחת. API:

| שיטה   | נתיב                     | מטרה                                                               |
| ------ | ------------------------ | ------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | מצב הדגל, `enabledTypes`, `customPatterns`, מוני זיהויים           |
| `PUT`  | `/api/settings/pii`      | החלפת `enabledTypes` (`null` = הכול) ו/או `customPatterns`         |

אופציונלי (כלל קשיח מס' #20): שום דבר כאן אינו משנה ברירת מחדל של דגל תכונה.

### הזרקת פרומפט (`promptInjection.ts`)

מזהה מבנים יריביים בתוכן שסופק על ידי המשתמש ואוכף את המדיניות שהוגדרה.
ההתנהגות נשלטת על ידי משתני סביבה ואפשרויות הבנאי:

| הגדרה    | משתנה סביבה                                                                                           | ברירת מחדל | השפעה                                                                                                                                                                   |
| -------- | ----------------------------------------------------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| מופעל    | `INPUT_SANITIZER_ENABLED`                                                                             | `true`     | כאשר הערך הוא `false`, מנגנון ההגנה מפסיק מיד.                                                                                                                          |
| מצב      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`     | מדיניות הזרקה: `block`, `warn`, או `log`. (`redact` מתקבל לצורך תאימות לאחור, אך **אינו** מסיר את טקסט ההזרקה; שכתוב PII של הבקשה נשלט על ידי `PII_REDACTION_ENABLED`.) |
| סף חסימה | אפשרות `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (כינוי `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | חומרה מינימלית הנדרשת לחסימה. ברירת המחדל מתייחסת לחומרה בינונית כתצפית בלבד.                                                                                           |

**קדימות מצבים** (`getMode`): `options.mode` של הקורא →
`INJECTION_GUARD_MODE` **עקיפת דגל תכונה במסד הנתונים** (לוח הבקרה → הגדרות →
דגלי תכונות) → משתנה הסביבה `INJECTION_GUARD_MODE` → משתנה הסביבה
`INPUT_SANITIZER_MODE` → `warn`. לכן עקיפה מלוח הבקרה גוברת על משתני הסביבה,
וממשק דגלי התכונות שולט במנגנון ההגנה הפעיל בזמן אמת (ללא הפעלה מחדש).
הקריאה ממסד הנתונים בטוחה במקרה של כשל: אם היא נכשלת, מנגנון ההגנה חוזר
להתנהגות המבוססת על משתני הסביבה, וכאשר לא מוגדרת עקיפה, ההתנהגות זהה
לפתרון המבוסס על משתני סביבה בלבד.

מקורות הזיהוי:

1. `sanitizeRequest()` מתוך `@/shared/utils/inputSanitizer` (מערך המזהים
   המשותף שבו נעשה שימוש במקומות אחרים בצינור העיבוד).
2. `DEFAULT_GUARD_PATTERNS` המובנות (נכון לעכשיו `system_override_inline` ו-
   `markdown_system_block`, שתיהן בחומרה `high`).
3. `customPatterns` אופציונליות המועברות דרך אפשרויות הבנאי (מחרוזות, ביטויים
   רגולריים, או רשומות `{ name, pattern, severity }`).

כאשר `mode === "block"` ולפחות זיהוי אחד עומד בסף החומרה,
`preCall` מחזירה `{ block: true, message: "Request rejected:
suspicious content detected" }`. במצבי `warn`/`log` מנגנון ההגנה מתעד
אך מאפשר את הקריאה. פונקציית העזר המשותפת `evaluatePromptInjection()` מיוצאת
גם היא עבור קוראים שצריכים להעריך פרומפטים מבלי לעבור דרך הרישום.

**גבול הסריקה (v3.8.20):** המזהה בודק רק את **16 ה-KB הראשונים** של
טקסט הפרומפט המאוחד — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16,384 בתים)
ב-`src/shared/utils/inputSanitizer.ts`. גם `detectInjection()` וגם
`evaluatePromptInjection()` מבצעות `slice(0, MAX_INJECTION_SCAN_BYTES)` לפני
הרצת לולאת התבניות. הנחיות הזרקה נמצאות בדרך כלל בסמוך לחלק העליון של הקלט,
ולכן הגבלה זו מצמצמת את צריכת ה-CPU וה-GC של ביטויים רגולריים במטענים בגודל
מאות KB, מבלי להחליש את הזיהוי (ראו #3932, #4041).

### ממסך פרטי גישה (`credentialMasker.ts`)

פועל בשני השלבים, אחרון בשרשרת ברירת המחדל (עדיפות `95`). מסיר
דפוסים מוכרים של מפתחות API / אסימוני סוד מהמטען היוצא (תוכן הודעות,
ארגומנטים של קריאות לכלים ותוצאות כלים) **וגם** מתגובת הספק, כך שפרטי גישה
שהודבקו בפרומפט (או הוחזרו על ידי תוצאת כלי) לא ידלפו לספק במעלה הזרם או
בחזרה ללקוח.

- **מופעל רק באופן אופציונלי**, לפי אותה מוסכמה של הסרת PII (בסמוך לכלל
  קשיח מס' #20): מושבת אלא אם `settings.credentialRedactionEnabled === true`
  **או** `CREDENTIAL_REDACTION_ENABLED=true`. כאשר הוא מושבת, מנגנון ההגנה
  אינו עושה דבר — הוא לעולם אינו חוסם ולעולם אינו משנה את התוכן.
- `redactCredentials()` עוברת על עץ המטען/התגובה המלא (`walkValue()`),
  באופן בטוח מפני זיהום אבטיפוס ובטוח מפני מעגלים באמצעות `WeakSet`, ומחליפה
  התאמות במציין מיקום `[REDACTED:<type>]`, תוך שכפול רק של הענפים שהשתנו בפועל.
- `CREDENTIAL_PATTERNS` מכסה מפתחות של ספקי LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), אסימוני VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), מפתחות תשלום (Stripe, Square),
  מפתחות ענן (מפתח גישה של AWS, Twilio, SendGrid, Mailgun), מפתחות פרטיים /
  JWTs, מחרוזות חיבור המכילות פרטי גישה (`mongodb://user:pass@...` וכו'),
  ותבנית כללית של ערכי כותרות `Authorization`/`x-api-key`/`api-key`/`apikey`.
  מפתחות במבנה של כותרות (`authorization`, `x-api-key`, `api-key`,
  `apikey`) מוסרים באופן מבני (הערך בלבד, תוך שמירה על קידומת הסכמה כמו
  `Bearer `/`Basic `), ולא באמצעות ביטוי הטקסט הגנרי.
- מנגנון ההגנה לעולם אינו חוסם; הוא רק משנה את התוכן
  (`modifiedPayload` / `modifiedResponse`) ומוסיף הערות
  (`meta.credentialsRedacted`, `meta.count`).

מנגנון הגנה מפני רגרסיות: `tests/unit/credential-masker-guardrail.test.ts`.

## חוזה הבסיס (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true מקצר את השרשרת
  message?: string; // מוצג בעת חסימה
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // מוחזר על ידי preCall כדי לשכתב את הבקשה
  modifiedResponse?: TValue; // מוחזר על ידי postCall כדי לשכתב את התגובה
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

מנגנון הגנה מסמן "אין שינוי" על ידי החזרת `void`, `{}`, או
`{ block: false }`. החזרת `modifiedPayload`/`modifiedResponse` מחליפה
את הערך הזורם דרך השרשרת עבור מנגנוני ההגנה שבהמשך.
`signal?: AbortSignal` מעביר את מחזור החיים של הקורא לתוך מנגנוני ההגנה. ביטול בקשה הוא חריגת ה-fail-open המכוונת: גשרי מדיה מפסיקים את העבודה ומנקים מבלי לשחזר מדיה גולמית ליעד שידוע שאינו תומך בה.

## המרשם (`registry.ts`)

הסינגלטון `guardrailRegistry` חושף:

- `register(guardrail)` — מוסיף (או מחליף לפי שם מנורמל) מנגנון הגנה
  וממיין מחדש לפי `priority` עולה.
- `clear()` / `list()` — פונקציות עזר ניהוליות.
- `runPreCallHooks(payload, context)` — עובר על מנגנוני ההגנה הפעילים, מעביר את
  ה-payload דרך `modifiedPayload`, ועוצר ב-`block: true` הראשון.
- `runPostCallHooks(response, context)` — אותה זרימה בצד התגובה.
- `resetGuardrailsForTests({ registerDefaults })` — מנקה את המצב ואופציונלית
  רושם מחדש את ברירות המחדל לצורך בידוד נקי של בדיקות.

שני ה-runners מחזירים `{ blocked, payload|response, results, guardrail?, message? }`
כאשר `results` הוא מערך של רשומות `GuardrailExecutionResult` הכוללות
שדות `blocked`, `skipped`, `modified`, `error` ו-`meta` לכל מנגנון הגנה,
שימושיים למעקב.

### השבתת מנגנוני הגנה לפי בקשה

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` מקבצת
רשימה מנוקת-כפילויות של שמות מנגנוני הגנה שיש לדלג עליהם בבקשה
הנוכחית. קיימים חמישה ערוצים, הנקראים בסדר זה וממוזגים לרשימה אחת
(המופע הראשון מנצח בעת ניקוי הכפילויות):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` בגוף הבקשה (רמה עליונה)
3. `metadata.disabledGuardrails` בגוף הבקשה (רק כאשר `metadata` הוא אובייקט)
4. כותרת `x-omniroute-disabled-guardrails`
5. כותרת מדור קודם `x-disabled-guardrails`

כל חמשת הערוצים ממוזגים, כולל שתי הכותרות: שליחת
`x-omniroute-disabled-guardrails` ו-`x-disabled-guardrails` יחד מדלגת על איחוד
הרשימות שלהן, וכותרת מודרנית ריקה כבר לא מסתירה את זו מדור הקודם
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), תוקן ב-
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

הערכים יכולים להיות מערכים של מחרוזות או מחרוזת מופרדת בפסיקים; השמות נחתכים
ומנורמלים ל-kebab-case באותיות קטנות (`pii_masker` → `pii-masker`), וערכים
ריקים נזרקים. התוצאה מועברת דרך `context.disabledGuardrails`
למרשם, שמדלג על מנגנוני הגנה תואמים (`skipped: true` ב-`results`).

רשימת ההשבתה משפיעה רק על **המרשם**. מצב `block` של הזרקת פרומפטים
הוא גבול חובה: ה-middleware של injection-guard
(`src/middleware/promptInjectionGuard.ts`) קורא ל-`evaluatePromptInjection()`
ללא רשימת השבתה הנשלטת על ידי הקורא (קריאת ה-`resolveDisabledGuardrails({ body })`
המתה שבעבר בוצעה הוסרה ב-
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), כך שבקשה
שמשביתה את `prompt-injection` עדיין נדחית במצב `block`. זהו תכנון
מכוון. ערוצי ההשבתה נשלטים על ידי הקורא (גוף הבקשה,
metadata, כותרות), ואסור שקורא יוכל לכבות מנגנון אבטחה
שהמפעיל הגדיר
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). איחוד
הכותרות מ-[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
משנה רק אילו מנגנוני הגנה של המרשם מדולגים; הוא לא מאפשר ללקוח
לעקוף את ה-middleware. מדיניות מנגנוני הגנה חובה לפי מפתח ולפי קבוצה
נעקבת ב-RFC של v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
ראו [כיסוי ומגבלות](#coverage-and-limits).

## סדר הביצוע

עבור כל בקשה הזורמת דרך `src/sse/handlers/chat.ts` ו-`open-sse/handlers/chatCore.ts` (נתיבי משפחת הצ'אט הרשומים תחת [כיסוי ומגבלות](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` בונה את רשימת הדילוגים מתוך מפתח ה-API, גוף הבקשה והכותרות.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` מריץ את ה-guardrails בסדר עדיפות עולה:
   - guardrails מושבתים נרשמים כ-`skipped`.
   - ה-`preCall` של כל guardrail רשאי לשכתב את ה-payload באמצעות `modifiedPayload`.
   - ה-`block: true` הראשון מנתק את השרשרת (short-circuit) וה-handler מחזיר תגובת דחייה של guardrail.
3. ה-payload (שאולי שוכתב) זורם לתוך ניתוב ה-combo והשיגור ל-upstream.
4. **עבור non-streaming בלבד:** לאחר שהתגובה מורכבת, `guardrailRegistry.runPostCallHooks(...)` מריץ את אותה שרשרת על התגובה. `block: true` כאן משמיט את תגובת ה-upstream ומחזיר HTTP 400. תגובות מוזרמות (streamed) מדלגות על שלב זה לחלוטין.

guardrails שזורקים שגיאה נרשמים עם `error: <message>` ונכתבים ביומן דרך `logger.warn`, אך השרשרת ממשיכה — fail-open מתוך תכנון.

## כיסוי ומגבלות

רישום ה-guardrails מחובר לצינור (pipeline) הצ'אט בלבד. מגבלות אלו מוצמדות על ידי `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` ו-`tests/unit/guardrail-pipeline-characterization.test.ts`; עדכנו את הבדיקות הללו באופן מכוון כאשר ההתנהגות משתנה.

### היכן ה-hooks רצים

| Hook / בקרה                               | רץ על                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runPreCallHooks`                         | בקשות המטופלות על ידי `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (וגם `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*`, ופרוקסי הצ'אט של Telegram. כמו כן נקודת הקצה לבדיקה של הדשבורד `/api/guardrails/test`. חסימת pre-call מחזירה HTTP 400. |
| `runPostCallHooks`                        | תגובות צ'אט מסוג **non-streaming** בלבד (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). תגובות מוזרמות לעולם אינן מגיעות אליו.                                                                                                                                                                                                                                                                                        |
| PII בסטרימינג                             | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`), מחובר בצינור ב-`streamingPipeline.ts` כאשר `PII_RESPONSE_SANITIZATION` פעיל. זה אינו guardrail, ולכן ערוצי ההשבתה אינם משפיעים עליו.                                                                                                                                                                                                                            |
| middleware של injection-guard (מדור קודם) | כל נתיב `/v1` הנושא prompt, כולל משפחת הצ'אט (ראו [כיסוי נתיבים](#injection-guard-route-coverage--red-team-phase-8--block-d)). הזרקת prompt בלבד.                                                                                                                                                                                                                                                                             |

### מה לא מכוסה

- **נתיבי מדיה, embeddings ונתונים** (`/v1/images/*`, `/v1/embeddings`, `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/rerank`, `/v1/search`, `/v1/moderations`) לעולם אינם מגיעים לרישום. לא רצים שם מיסוך PII, מיסוך אישורים (credentials) או גשר מודאליות. הבדיקה היחידה שלהם היא ה-middleware הישן של injection-guard.
- **תגובות מוזרמות** אינן מקבלות guardrails של post-call: אין `pii-masker` או `credential-masker` של post-call, ואין חסימת post-call. רק טרנספורם ה-PII של הסטרימינג חל (כאשר `PII_RESPONSE_SANITIZATION` פעיל). אישור (credential) המוחזר בתגובה מוזרמת אינו מטושטש.
- **ערוצי השבתה מול ה-middleware (מתוך תכנון):** ה-middleware מעריך הזרקת prompt בקריאה משלו ל-`evaluatePromptInjection()`, מבלי להעביר רשימת השבתות הנשלטת על ידי המתקשר. מצב `block` הוא גבול חובה שהשבתות הנשלטות על ידי המתקשר אינן יכולות לעקוף, כולל בנתיבי משפחת הצ'אט ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). השבתת `prompt-injection` רק מדלגת על ה-guardrail של הרישום.

### מה רואה תגובה לפני ה-post-call

בנתיב ה-non-streaming הסדר הוא: חילוץ זיכרון → ביצוע כלים מובנים → guardrails של post-call → יציאת חסימת post-call → אחסון במטמון סמנטי (semantic-cache).

- **חילוץ זיכרון** ו**הרצת כלים** רואים את התגובה לפני שמנגנוני ההגנה שלאחר הקריאה (post-call) יכולים לשכתב או לחסום אותה. החל מ-[#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), חילוץ הזיכרון מעביר את הטקסט שחולץ דרך `sanitizePII` כאשר `PII_RESPONSE_SANITIZATION` מופעל (הן בסטרימינג והן במצב לא-סטרימינג), אבל תגובה שמנגנוני ה-post-call חוסמים מאוחר יותר עדיין כבר הוצעה לזיכרון ולכלים.
- **המטמון הסמנטי** מאחסן את התגובה לאחר ה-post-call, כך שהוא מאחסן את התגובה המשוכתבת, ותגובה חסומה לעולם אינה נשמרת במטמון. רשומות המטמון ממופות לפי מפתח API.

## תצורה

משתני סביבה הנקראים על ידי מנגנוני ההגנה המובנים:

| משתנה                                 | בשימוש על ידי            | השפעה                                                                                   |
| ------------------------------------- | ------------------------ | --------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`       | הגדירו `false` כדי להשבית את הזיהוי לחלוטין.                                            |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`       | מדיניות הזרקה: `warn`, `block`, או `log`. הערך הישן `redact` אינו משכתב את טקסט ההזרקה. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`       | מצב עבור שומר ההזרקה; גם דגל תכונה ב־DB ש**עוקף** את משתני הסביבה (DB > ENV).           |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`       | רמת החומרה המינימלית ש־`MODE=block` דוחה: `high` (ברירת מחדל), `medium`, או `low`.      |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`       | כינוי legacy עבור `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`             | כאשר `true`, PII בבקשה מושחר (ללא תלות במצב ההזרקה).                                    |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (מורד הזרם) | שולט בהתנהגות ה־masker בצד התגובה.                                                      |

מנגנוני ההגנה של Modality Bridge קוראים את תצורת זמן הריצה ממאגר ההגדרות
המגובה ב־DB (`getSettings()`), ולא ממשתני סביבה. המפתחות הראשיים של Vision
הם `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` ו־
`modalityBridgeCacheMaxEntries`. מפתחות ה־legacy מסוג
`visionBridge*` מתקבלים רק כ־fallback קריאה למחזור אחד כמתועד;
כתיבות מהדשבורד משתמשות במפתחות הראשיים. ברירות המחדל וה־resolver של ה־fallback
נמצאים ב־`src/shared/constants/modalityBridgeDefaults.ts`, וקבועי ה־legacy
נשמרים ב־`src/shared/constants/visionBridgeDefaults.ts`.

Audio משתמש ב־`modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` ו־`modalityBridgeAudioMaxClips`, בתוספת הגדרות
ה־`modalityBridgeCache*` המשותפות. ל־Audio אין fallback למפתחות legacy מכיוון
שמפתחות אלה הוצגו יחד עם סכמת Modality Bridge.

Video משתמש ב־`modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` ו־
`modalityBridgeVideoTimeout`, בתוספת הגדרות ה־`modalityBridgeCache*` המשותפות.
הוא מושבת כברירת מחדל מכיוון ש־FFmpeg/ffprobe הם תלויות תפעוליות
אופציונליות וכיתוב פריימים מוסיף השהייה ועלות מודל.

## מגני בטיחות מותאמים אישית

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

שלבים:

1. צרו את `src/lib/guardrails/myGuardrail.ts` בהרחבת `BaseGuardrail`.
2. ממשו את `preCall` ו/או `postCall`.
3. רשמו בזמן הייבוא (push מתוך `registerDefaultGuardrails`) או
   קראו ל-`guardrailRegistry.register(...)` בזמן ריצה — הרישום מחליף
   כל מגן קודם בעל אותו שם מנורמל.
4. הוסיפו בדיקות תחת `tests/unit/` (דוגמאות קיימות:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## בדיקות

השתמשו ב-`resetGuardrailsForTests()` בין בדיקות כדי להתחיל ממצב ידוע.
העבירו `{ registerDefaults: false }` כדי להתחיל עם רישום ריק ולרשום רק
את מגני הבטיחות שבבדיקה. Vision Bridge מקבל הזרקת תלויות
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge חושף את נקודות
התפר המקבילות עבור הגדרות, יכולות, בחירת מודל STT, בדיקות אישורים
ותמלול. לכן הבדיקות יכולות לתרגל את שני הזרמים ללא גישה למסד נתונים
או לרשת.

## כיסוי הנתיבים של מגן ההזרקה ורד-טים (שלב 8 · בלוק D)

מגן ההזרקה (`createInjectionGuard` / `withInjectionGuard`) מכסה את כל הנתיבים
שמקבלים פרומפטים של משתמשים. הוא פועל לפי `INJECTION_GUARD_MODE` (ברירת מחדל `warn` = רישום בלבד;
`block` = מחזיר HTTP 400 `SECURITY_001`).

| סוג         | נתיבים                                                                                                                                               | מצב ברירת מחדל |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| טקסט (קיים) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| גנרטיבי     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| נתונים      | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

חילוץ הטקסט (`extractMessageContents`) מכסה את `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**רד-טים (לילי, `nightly-llm-security.yml`):** promptfoo מאמת שכל נתיב חוסם
את קורפוס ה-OWASP-LLM תחת `INJECTION_GUARD_MODE=block`; garak מריץ probes (מדלג ללא secret).
`moderations` נכלל לשם עקביות. מצב block הוא גבול מחייב: `evaluatePromptInjection()`
מתעלם מרשימת ההשבתה לבקשה-בודדת שה-middleware מעביר לו, כך ש-`disabledGuardrails`
**אינו** פוטר נתיב ממנו ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

לתהליך העבודה הלילי (`.github/workflows/nightly-llm-security.yml`, cron + הפעלה
ידנית) שתי עבודות (jobs):

- **`promptfoo-guard` (חוסם)** — מריץ `promptfoo eval -c promptfooconfig.yaml`
  עם `INJECTION_GUARD_MODE=block`. כל מקרה עוין (למשל "ignore all
  previous instructions…", פריצות-עקיפה בסגנון DAN) מוודא שהתגובה נושאת
  `error.code === "SECURITY_001"`, כלומר שהמגן אכן דחה את הבקשה.
- **`garak` (מייעץ)** — מריץ garak `--probes promptinject,dan,leakreplay`
  כנגד מופע מקומי של OmniRoute (`http://localhost:20128/v1`). מותנה
  ב-secret של הספק (`PROMPTFOO_PROVIDER_KEY`); מדלג באלגנטיות ומסומן בסיומת
  `|| true`, כך שהוא מדווח מבלי להפיל את ה-CI.

כיסוי פונקציית העזר של המגן (`createInjectionGuard` / `withInjectionGuard`)
משתרע על כל נתיב `/v1` הנושא פרומפט; טקסט הפרומפט נשלף מתוך
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
באמצעות `extractMessageContents()` ב-`src/shared/utils/inputSanitizer.ts`.
