## השלמות צ'אט

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### כותרות מותאמות אישית

| כותרת                    | כיוון | תיאור                                                                                                                                                                         |
| ------------------------ | ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | בקשה  | יש להגדיר ל-`true` כדי לעקוף את המטמון                                                                                                                                        |
| `x-omniroute-no-memory`  | בקשה  | יש להגדיר ל-`true` כדי לדלג על הזרקת זיכרון ומיומנויות עבור בקשה זו (מקביל לאי-שימוש במטמון; מונע את תקורת האסימונים/העלות לכל קריאה)                                         |
| `X-OmniRoute-Progress`   | בקשה  | יש להגדיר ל-`true` עבור אירועי התקדמות                                                                                                                                        |
| `X-Session-Id`           | בקשה  | מפתח סשן דביק עבור שיוך סשן חיצוני                                                                                                                                            |
| `x_session_id`           | בקשה  | מתקבלת גם הגרסה עם קו תחתון (HTTP ישיר)                                                                                                                                       |
| `X-OmniRoute-Session-Id` | בקשה  | תג סשן/שיחה שסופק על ידי הקורא (ומוזן גם לזיכרון). כאשר הוא קיים, הוא נשמר כלשונו ב-`call_logs.session_tag` לצורך שיוך עלויות לפי סשן (#8249) — ולעולם אינו נוצר כאשר הוא חסר |
| `Idempotency-Key`        | בקשה  | מפתח למניעת כפילויות (חלון של 5 שניות)                                                                                                                                        |
| `X-Request-Id`           | בקשה  | מפתח חלופי למניעת כפילויות                                                                                                                                                    |
| `x-omniroute-connection` | בקשה  | הצמדת בקשה למודל יחיד לחיבור ספק (חשבון) אחד לפי המזהה שלו — ראו [הצמדת חשבון לפי בקשה](#account-pinning-per-request)                                                         |
| `X-OmniRoute-Cache`      | תגובה | `HIT` או `MISS` (ללא הזרמה)                                                                                                                                                   |
| `X-OmniRoute-Idempotent` | תגובה | `true` אם נמנעה כפילות                                                                                                                                                        |
| `X-OmniRoute-Progress`   | תגובה | `enabled` אם מעקב ההתקדמות מופעל                                                                                                                                              |
| `X-OmniRoute-Session-Id` | תגובה | מזהה הסשן בפועל שבו OmniRoute משתמש                                                                                                                                           |
| `X-OmniRoute-Request-Id` | תגובה | מזהה מתאם של הבקשה (כאשר הוא ידוע)                                                                                                                                            |
| `X-OmniRoute-Version`    | תגובה | גרסת ה-Build של OmniRoute (קיימת תמיד)                                                                                                                                        |
| `X-OmniRoute-Cost-Saved` | תגובה | הסכום בדולר ארה"ב שהמטמון חסך במקרה של `HIT` (פגיעות מטמון בלבד)                                                                                                              |
| `X-OmniRoute-Decision`   | תגובה | עקבת ניתוב: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` היא אסטרטגיית השילוב, או `single` עבור בקשה שאינה שילוב) — קיימת תמיד בתגובות השלמה                 |

> הערת Nginx: אם אתם מסתמכים על כותרות עם קווים תחתונים (לדוגמה `x_session_id`), הפעילו את `underscores_in_headers on;`.

#### הצמדת חשבון לכל בקשה

כאשר לספק יש כמה חיבורים (חשבונות או מפתחות), OmniRoute בדרך כלל בוחר אחד
באמצעות אסטרטגיית בחירת החשבון שלו. במקום זאת, בקשה יכולה להיצמד לחיבור מסוים אחד
באמצעות הכותרת `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **היכן למצוא את המזהה.** פתחו את דף הספק בלוח הבקרה
  (**לוח בקרה → ספקים → <provider>**) ולחצו על תג המזהה `xxxxxxxx…` בשורת חיבור —
  פעולה זו מעתיקה את מזהה החיבור המלא.
- **אילו בקשות מכבדות אותו.** בקשות למודל יחיד (`provider/model`) בנקודות הקצה
  `/v1/chat/completions`, `/v1/messages` ו-`/v1/responses`. שילובים מתעלמים מהכותרת: הצמידו
  חשבון לכל שלב בשילוב באמצעות החיבור של השלב עצמו.
- **ההצמדה קשיחה, ולא רק העדפה.** נעשה שימוש בלעדי בחיבור המוצמד. כשל
  בתוך הבקשה מתעד את תקופת ההמתנה של החשבון, אך **אינו** עובר לחשבון
  מקביל של אותו ספק.
- **תקופת המתנה ומכסה משחררות את ההצמדה.** בזמן שהחיבור המוצמד נמצא בתקופת המתנה,
  מיצה את המכסה או נחסם על ידי מדיניות מכסה, בקשות מאוחרות יותר עוברות לחיבורים
  האחרים של הספק, בדיוק כמו תעבורה ללא הצמדה.
- **מזהים לא מוכרים או מושבתים גורמים לכשל.** מזהה שאינו נמצא במאגר הפעיל של הספק (נמחק,
  הושבת או שייך לספק אחר) אינו משאיר חשבון כשיר, ולכן הבקשה
  נכשלת במקום להיות מנותבת בשקט למקום אחר.

Claude Code שולח כותרות מותאמות אישית באמצעות `ANTHROPIC_CUSTOM_HEADERS`. הוסיפו אותו לבלוק `env`
של `~/.claude/settings.json`, או לקובץ `.claude/settings.json` ברמת הפרויקט כדי להצמיד חשבון שונה
לכל פרויקט:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

מקור: `src/sse/handlers/chat.ts` (קריאת הכותרת), `src/sse/services/auth.ts` ו-
`src/sse/services/sessionAffinityPin.ts` (שחרור ההצמדה והבדיקה אם החיבור חסר מהמאגר).

> **כותרות טלמטריית עלויות:** תגובות הצלחה שאינן מוזרמות כוללות גם את ערכת טלמטריית העלויות `X-OmniRoute-*` —‏ `X-OmniRoute-Response-Cost` (בדולר ארה״ב, 10 ספרות קבועות אחרי הנקודה העשרונית; `0.0000000000` עבור שימוש חינמי או ללא תמחור), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`,‏ `X-OmniRoute-Model`,‏ `X-OmniRoute-Provider`,‏ `X-OmniRoute-Latency-Ms`,‏ `X-OmniRoute-Cache-Hit` ו-`X-OmniRoute-Fallback-Attempts` (רק כאשר > 0), וכן `X-OmniRoute-Request-Id` ו-`X-OmniRoute-Version`. כותרות אלה מופקות על ידי השלמות צ׳אט, `/v1/responses`,‏ `/v1/messages`, **וגם נקודות הקצה למדיה** —‏ `/v1/embeddings`,‏ `/v1/images/generations`,‏ `/v1/audio/speech`,‏ `/v1/audio/transcriptions`,‏ `/v1/rerank`,‏ `/v1/videos/generations`,‏ `/v1/music/generations` ו-`/v1/moderations` (העלות תמיד `0`). עלות המדיה מחושבת לפי סוג המדיה (לכל תמונה, לכל שנייה, לכל תו, לכל יחידת חיפוש) כאשר תמחור זמין; אחרת, העלות היא `0` (מעבר פתוח במקרה של כשל).

> **סמנטיקת עלות של פגיעה במטמון:** בפגיעה במטמון הסמנטי (`X-OmniRoute-Cache-Hit: true`) לא מתבצעת קריאה לספק במעלה הזרם, ולכן `X-OmniRoute-Response-Cost` הוא `0.0000000000` (העלות **המצטברת** של אספקת הפגיעה). העלות המקורית או העלות שהייתה צפויה מדווחת בנפרד ב-`X-OmniRoute-Cost-Saved`. צרכני נתוני חיוב צריכים לסכם את `X-OmniRoute-Response-Cost` (פגיעות אינן עולות דבר); ניתוחי מטמון יכולים לצבור את `X-OmniRoute-Cost-Saved`.

## חכירות בלעדיות של הפעלות מנוהלות

חכירה בלעדית של הפעלה מנוהלת היא חוזה ניתוב אופציונלי ובלתי תלוי בלקוח: בעלים פעיל אחד
מחזיק בחיבור OmniRoute כשיר אחד. היא אינה מחכירה מודל, אינה דורשת OAuth, אינה מזהה
לקוח מסוים ואינה דורשת ספק מסוים.

מפתח ה-API המשמש לאימות חייב לכלול את ההרשאה `lease:exclusive` ורשימת
`allowedConnections` מפורשת שאינה ריקה. גבול השינוי במסד הנתונים אוכף את שני השדות יחד בעת
יצירת מפתח ובעדכונים חלקיים.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

תגובות מוצלחות לרכישה, לחידוש ולשחרור חושפות חותמות זמן, `state` ואת ערך
`generation` החיובי המדויק, אך לעולם לא את החיבור שנבחר או את פרטי הגישה. בחידוש ובשחרור,
הדור מסופק בגוף ה-JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

בעלים של חכירה פעילה יכול לבקש במפורש מטא-נתונים לתצוגה השומרים על הפרטיות עבור השיוך הנוכחי שלו:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

פעולת סטטוס אופציונלית זו מוגנת באמצעות גידור לפי הבעלים האטום, מפתח ה-API המנוהל והמאומת, והדור
הפעיל המדויק, במסגרת טרנזקציה אחת במסד הנתונים. `displayName` הוא רק שם החיבור המוגדר לאחר
הסרת רווחים מיותרים; ערכו הוא `null` כאשר לא קיים שם מוגדר ובטוח. OmniRoute לעולם אינו מחליף אותו
בכתובת דוא"ל או בזהות חשבון שנוצרה. ערך הספק הוא תווית תצוגה שאינה רגישה ולעולם אינו
מזהה שנוצר עבור ספק תואם. פרטי גישה, אסימונים, קובצי Cookie, מזהים גולמיים של חיבורים או מפתחות
API, גיבובי בעלים, סודות גידור ונתוני ניתוב פנימיים אינם נכללים.

חיפושים עם מפתח שגוי, בעלים שגוי, דור מיושן, נתונים חסרים, חכירה שפג תוקפה, חכירה ששוחררה או חכירה שבוטלה
מחזירים כולם את אותה שגיאת `409 LEASE_FENCE_STALE` ללא מטא-נתונים של החיבור. ללקוח שקיבל תגובת המתנה לקיבולת אין שיוך פעיל שניתן לבדוק. כאשר הניתוב מעביר חכירה פעילה,
אותו דור נשאר תקף והסטטוס מחזיר באופן אטומי את השיוך החדש, ולעולם לא את הישן.
לקוחות קיימים נותרים ללא שינוי, משום שתגובות הרכישה, החידוש, השחרור וההמתנה שומרות
על המבנה הקודם שלהן.

חוזה שרת זה אינו משנה את `/status` של OpenAI Codex הסטנדרטי. Codex הסטנדרטי מדווח כעת על
ספק המודל שלו ועל מצב האימות/החשבון המובנה, אך אינו מציג מטא-נתוני חשבון שרירותיים של
ספק מותאם אישית; שילוב עתידי בצד הלקוח חייב לקרוא לפעולה זו ולהחליט כיצד
להציג את `connection.displayName`.

לאחר מכן, כל בקשת הסקה מנוהלת מספקת את שתי כותרות הבקרה:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

הבעלים המדויק, הדור, החיבור הפעיל ומפתח ה-API המאומת מוגנים באמצעות גידור מיד
לפני כל ניסיון נתמך מול שירות במעלה הזרם. הפעלה חוזרת של הבעלים והדור עם מפתח אחר נכשלת גם
כאשר מפתח זה מתיר את אותו חיבור. הבעלים הגולמיים אינם נשמרים, נרשמים ביומן, נשמרים
בתמונת המצב של הבקשה או מועברים לשירות במעלה הזרם.

התנגשות זמנית מחזירה HTTP `429` עם `Retry-After` ועם:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

תגובה זו מציינת רק שקבוצת החיבורים הכשירים הרגילה לא הייתה ריקה ושכל מועמד פנוי
הוחזק בידי חכירה פעילה זרה. מודלים/ספקים שאינם נתמכים, אי-התאמה למדיניות, תקופת צינון, מכסה,
תקינות וכשלי כשירות רגילים אחרים ממשיכים להחזיר את תגובות OmniRoute הקיימות שלהם.

### `x-omniroute-compression`

דריסה של תוכנית הדחיסה לפי בקשה. הקדימות הגבוהה ביותר — גוברת על דריסת שילוב
הניתוב, הפרופיל הפעיל, ההפעלה האוטומטית וברירת המחדל של הלוח. ערכים:

| ערך           | השפעה                                                                                   |
| ------------- | --------------------------------------------------------------------------------------- |
| `off`         | ללא דחיסה עבור בקשה זו.                                                                 |
| `default`     | פרופיל ברירת המחדל הנגזר מהלוח (מתעלם מהפרופיל הפעיל). מנועים מאבדי מידע נשארים כבויים. |
| `safe`        | מניעת כפילויות וצמצום רווחים בלבד.                                                      |
| `allow-lossy` | שמירת תוכנית המפעיל עבור בקשה זו, כולל סיכומים ושכתובי סגנון.                           |
| `engine:<id>` | מנוע יחיד, כאשר הוא מופעל, לדוגמה `engine:rtk`. הצטרפות לפי בקשה עבור מנוע זה.          |
| `<combo>`     | שילוב בעל שם, המותאם תחילה לפי שם (ללא תלות ברישיות) ולאחר מכן לפי מזהה.                |

הערות:

- המערכת מתעלמת מערכים לא מוכרים (הבקשה לעולם אינה נדחית); הפתרון ממשיך לפי סדר הקדימויות הרגיל של המפעיל.
- אם כמה שילובים חולקים שם, העבירו את **המזהה** של השילוב לצורך התאמה דטרמיניסטית.
- לא ניתן לבחור לפי שם שילוב ששמו `off` או `default` (מילות מפתח אלה מפורשות תחילה); יש להפנות לשילוב כזה לפי המזהה שלו.
- מתג הדחיסה הראשי הוא שער קשיח: כאשר הדחיסה מושבתת באופן גלובלי, כותרת זו אינה יכולה להפעיל אותה.

התוכנית שהוחלה מוחזרת בכותרת התגובה:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

כאשר `<source>` הוא אחד מבין `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` או `off`.

## הטמעות

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ספקים זמינים: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

מזהי הקטלוג הם בתבנית `provider/model` (לדוגמה: `jina-ai/jina-embeddings-v5-omni-small`). גם מזהי מודלים של Jina ללא שם הספק, המופיעים במרשם (לדוגמה `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), ניתנים לפענוח. פעולות ההטמעה/דירוג מחדש/סיווג/פילוח של Jina משתמשות תחילה בפרטי הכניסה `jina-ai` מלוח הבקרה; `JINA_AI_API_KEY` משמש כחלופה רק כאשר לא קיים מפתח בלוח הבקרה. הכרטיס `jina-reader` מיועד רק ל-Reader / `r.jina.ai` ‏(`POST /v1/web/fetch`), ולעולם אינו מספק הטמעות או דירוג מחדש.

מודלים במרשם שמצהירים על תמיכה מולטימודלית מקבלים גם עד 32 פריטים מובנים שאינם תלויים בספק.
סוגי פריטי המדיה הם `text`, `image`, `audio`, `video` ו-`document`. שדה המדיה `source`
שלהם הוא `{"type":"url","url":"https://..."}` או
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni ‏(`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
וכן הכינוי המשפחתי `jina-ai/jina-embeddings-v5-omni` → omni-small) מקבל גם מסמכי
EmbeddingsV5Request מקוריים של Jina ו**מעביר אותם בשלמותם** אל `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ערכי `{ image | audio | video | pdf }` מקוריים יכולים להיות כתובת URL ציבורית מסוג HTTPS, כתובת URI מסוג `data:`, או
base64 גולמי. OmniRoute אינו ממיר אובייקטים אלה למחרוזות ואינו מאחזר כתובות URL מקוריות של תמונות — Jina מאחזר
את המדיה הציבורית בעצמו. שדות נוספים של Jina‏ (`task`, `normalized`, `truncate`, `embedding_type`)
מועברים הלאה. מק"טים של Jina המיועדים לטקסט בלבד עדיין דוחים מסמכים שאינם טקסט.

מגבלות אבטחה ותעבורה:

- כתובות URL מרוחקות של מדיה חייבות להיות כתובות HTTPS ציבוריות. פריטים קנוניים מסוג `{type,source:url}` מאוחזרים
  בצד השרת (אימות מחדש של הפניות, מגבלת זמן, מגבלות גודל, DNS ציבורי והצמדת חיבור) ומוטמעים
  לפני הקריאה לספק. פריטים מקוריים של Jina מסוג `{image:"https://..."}` מועברים כפי שהם
  לאחר אותה בדיקת HTTPS ציבורי; Jina מאחזר את כתובת ה-URL.
- מדיה מוטמעת בקידוד base64 מוגבלת ל-8 MiB מפוענחים לכל פריט ול-16 MiB מפוענחים בכל הבקשה.

תרגום עבור ספקים (פריטים קנוניים לעולם אינם מועברים ללא שינוי):

- מודלים מולטימודליים של Jina: כל פריט ברמה העליונה הופך לאובייקט אחד עם מפתח לפי סוג הקלט
  (`text` / `image` / `audio` / `video` / `pdf`), תוך שימוש בכתובות URI מסוג data עבור מדיה מוטמעת; וקטור אחד לכל
  פריט ברמה העליונה.
- משפחת Gemini Embedding 2: מערך אחד ברמה העליונה הופך לבקשת
  `models/{model}:embedContent` מקורית יחידה עם `content.parts` ‏(`text` או `inline_data`).
- llama.cpp ‏(`llama-cpp/<model>`, כל מודל שהשרת המקומי טען): פריטי `text` קנוניים
  הופכים למחרוזות רגילות, ו-`image` / `audio` / `video` הופכים כל אחד לאובייקט
  `{"content": [part]}` יחיד, תוך שימוש בחלקי תוכן הצ'אט של llama-server ‏(`image_url`,
  ‏`input_audio` עם הפורמט `wav` / `mp3` / `flac`, וכן `input_video`) עם נתונים מוטמעים; וקטור אחד
  לכל פריט ברמה העליונה. השרת חייב לפעול עם `--embedding --mmproj …`; ללא מקרן הוא
  דוחה את המדיה בעצמו. `document` אינו נתמך.
- מודלים לא מוכרים/דינמיים ללא מטא-נתונים מפורשים של סוגי קלט דוחים קלט מובנה עם HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

שילובים לא נתמכים של מודל וסוג קלט מחזירים HTTP 400 במקום לכפות המרה של הפריט. שדות הרחבה שאינם שדות קלט
בבקשות מחרוזת/אסימון מדור קודם ממשיכים לעבור ללא שינוי.

```bash
# הצגת כל מודלי ההטמעה
GET /v1/embeddings
```

## יצירת תמונות

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

הספקים הזמינים כוללים את OpenAI (GPT Image 2),‏ xAI (Grok Image),‏ Together AI (FLUX),‏ Fireworks AI,‏ Nebius (FLUX),‏ Hyperbolic,‏ NanoBanana,‏ **OpenRouter**,‏ **ZenMux**,‏ SD WebUI (מקומי),‏ ComfyUI (מקומי).

`n` מחזיר `n` תמונות בתוך `data[]`. עבור ספקים שממשק ה-API שלהם במעלה הזרם מחזיר תמונה אחת בכל קריאה
(Black Forest Labs,‏ Stability AI,‏ Leonardo,‏ Ideogram,‏ Haiper,‏ Hyperbolic,‏ Magnific/Freepik,
NVIDIA NIM,‏ Cloudflare Workers AI), מתבצעות `n` קריאות נפרדות במעלה הזרם, עם לכל היותר 4 קריאות פעילות במקביל. ערך
`seed` קבוע מוזז לפי אינדקס הקריאה (`seed`,‏ `seed + 1`, …), כך שהתמונות שונות אך נשארות
ניתנות לשחזור. הערך `n` מוגבל ל-10. הבקשה כולה נכשלת אם אחת מהקריאות נכשלת. רשימת
הפורמטים לביצוע fan-out נמצאת ב-`SINGLE_IMAGE_FANOUT_FORMATS` בקובץ
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux עושה שימוש חוזר בחיבור הקיים של מפתח ה-API ומקבל קידומות `zenmux/` או `zm/`:

- `zenmux/openai/gpt-image-2` משתמש ב-OpenAI Images API של ZenMux. האפשרויות כוללות את `size`,
  `quality`,‏ `n`,‏ `output_format`,‏ `output_compression`,‏ `background` ו-`response_format`.
- מפרסמים אחרים, כגון `zm/meta/muse-image-1.0`, משתמשים בנקודת הקצה `:predict`
  של Vertex AI ב-ZenMux. הערך `n` ממופה אל `sampleCount`,‏ `aspect_ratio` אל `aspectRatio`, ו-`image_size`
  (`1K`,‏ `2K`,‏ `4K`) אל `sampleImageSize`. ערך `size` בפיקסלים מספק יחס גובה-רוחב בלבד,
  ולא ממדי פיקסלים מובטחים. היחסים, הרזולוציות והכמויות הנתמכים משתנים בהתאם למודל.
- `zm/inclusionai/ming-image-0.1-design` בוחר את הממדים בעצמו. יש להשמיט את `size`,
  `aspect_ratio` ו-`image_size`; ערכים מפורשים מחזירים HTTP 400. ניתן לבקש PNG,‏ JPEG ו-WebP
  באמצעות `output_format`.

שילוב זה תומך ביצירת תמונות מטקסט, ולא בעריכת תמונות עזר. הפלט של Vertex
מנורמל אל `data[].b64_json`;‏ `response_format: "url"` מחזיר כתובת URL מסוג HTTPS ממעלה הזרם
או כתובת URL של נתוני base64 כאשר זמינים רק בתים של תמונה. פלטים ריקים או מסוננים
מחזירים שגיאה במקום הצלחה ריקה. הגישה למודלים תלויה בחשבון ZenMux.
ראו [Vertex API של ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) ו-
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# הצגת כל מודלי התמונות
GET /v1/images/generations
```

## OCR למסמכים

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` בוחר את ספק ה-OCR באמצעות קידומת `provider/model`; מזהה מודל ללא קידומת (למשל
`mistral-ocr-latest`) נפתר לספק הרשום שלו, ואם `model` מושמט, ברירת המחדל היא
Mistral‏ (`mistral-ocr-latest`). ספקים רשומים (`open-sse/config/ocrRegistry.ts`):

| מזהה ספק                      | מזהה מודל            | ערך `model`                                                       | הערות                                                                                                        |
| ----------------------------- | -------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (או `mistral-ocr-latest` ללא קידומת) | סינכרוני — התגובה מוחזרת ישירות מהקריאה היחידה במעלה הזרם.                                                   |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                       | אסינכרוני במעלה הזרם (`analyze` + תשאול) — ראו להלן.                                                         |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                           | סינכרוני, דרך נקודת הקצה לשותפים `openapi/chat/completions` של Vertex AI — לפרטי אימות וכתובת URL, ראו להלן. |

כל שלושת הספקים מגיבים בגוף בעל אותו מבנה כמו Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### תהליך התשאול של Azure Document Intelligence

ממשק ה-API‏ `analyze` של Azure Document Intelligence הוא אסינכרוני: הבקשה הראשונית מחזירה
כותרת `Operation-Location` במקום גוף, ויש לתשאל כדי לקבל את התוצאה. המטפל
(`open-sse/handlers/ocr.ts`) מתשאל את כתובת ה-URL הזאת בכל שנייה, עד 30 ניסיונות, נכשל מיד (ואינו
ממשיך לתשאל) במקרה של תגובת תשאול שאינה `ok` או מצב `"failed"`, ומחזיר `504` אם
הפעולה עדיין פועלת לאחר שמכסת הניסיונות מוצתה. התגובה הסופית של Azure
מנורמלת לאותו מבנה `pages`/`markdown` שבו משתמש Mistral לפני שהיא מוחזרת
למתקשר, כך שקוד הלקוח אינו צריך לטפל בספק כמקרה מיוחד.

### אימות ופתרון נקודת קצה עבור Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` עושה שימוש חוזר באותו אימות Vertex AI שבו OmniRoute כבר תומך עבור
תעבורת צ'אט ותמונות (`open-sse/executors/vertex.ts`): מפתח ה-API של החיבור הוא אישור
Service Account בפורמט JSON (שמוחלף באסימון גישה קצר-טווח מסוג OAuth באמצעות תהליך JWT-bearer)
או אסימון גישה מסוג OAuth שכבר הונפק ונעשה בו שימוש כפי שהוא. כתובת ה-URL של נקודת הקצה במעלה הזרם היא
נקודת הקצה הכללית לשותפים `openapi/chat/completions` של Vertex, שנבנית מהפרויקט ומהאזור
של החיבור — ערך מפורש של `providerSpecificData.project`/`providerSpecificData.region` תמיד גובר;
אחרת, הפרויקט נגזר מהערך `project_id` ב-JSON של ה-Service Account והאזור
מקבל כברירת מחדל את `us-central1`. שני הפתרונות מתבצעים ב-`open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`,‏ `resolveVertexOcrBaseUrl`) ונצרכים על ידי
`src/app/api/v1/ocr/route.ts` לפני ההעברה אל `handleOcr`.

GET /v1/models

→ מחזיר את כל מודלי הצ'אט, ההטמעות והתמונות + שילובים בפורמט OpenAI

### מחירי מודלים (`pricing`)

רשומה מכילה אובייקט `pricing` כאשר OmniRoute יודע מהו מחיר המודל. המחיר מגיע
מטבלת התמחור המשמשת לחישוב עלויות: ברירות מחדל מובנות, מחירים מסונכרנים
ודריסות שהוגדרו באמצעות `/api/pricing`. אלה מחירי מחירון, ולכן גם ספקי מנויים
מציגים מחיר לטוקן.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| שדות                                                            | יחידה                            | הערות                                                                                                                          |
| --------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | דולר ארה"ב לטוקן, מחרוזת עשרונית | תואם OpenRouter, לעולם לא בסימון מעריכי. שני שדות המטמון מופיעים רק כאשר קיים מחיר למטמון.                                     |
| `input`, `output`, `cached`, `cache_creation`                   | דולר ארה"ב למיליון טוקנים, מספר  | שדות מגרסאות קודמות של הקטלוג, שנשמרו עבור לקוחות קיימים. גם `reasoning` ו-`long_context` מופיעים כאשר שורת התמחור כוללת אותם. |

- **שילובים** מקבלים את המחיר של היעד הגלוי הראשון שלהם. שילובי `auto/*` מובנים בוחרים
  יעד בזמן הבקשה, ולכן אין להם `pricing`.
- **מודלים חינמיים** מציגים `"0"` (וגם `0`) כאשר מחירם אפס. מודל ללא שורת תמחור
  מציג גם הוא `"0"` כאשר הקטלוג מסמן אותו כחינמי (`free: true`) או כאשר קטלוג
  המודלים החינמיים המובנה כולל אותו.
- **מחיר לא ידוע:** לרשומה אין מפתח `pricing`.
- **ספקים הנמדדים לפי נקודות זכות** (כגון Kiro) מחייבים לפי בקשה ולא לפי טוקן. הרשומות
  שלהם שומרות את השדות המספריים למיליון שהיו להן קודם, ואינן כוללות שדות מחרוזת לטוקן.
- **וריאנטים** (מזהי רמת מאמץ להסקה, כינויים ללא חשיבה, ושיקופי גילוי ושער)
  מעתיקים את המחיר של המודל שאליו הם מנתבים.
- השדות מכילים תעריפי בסיס בלבד. מדרגות הקשר ארוך (השדה המספרי `long_context`) ומכפילי
  רמת שירות (לדוגמה Codex מהיר או גמיש) אינם משנים את `prompt` או את
  `completion`.
- האובייקט זהה בכל סגנונות האימות, כולל בקשה בסגנון Anthropic עם
  `x-api-key` ו-`anthropic-version` (התגובה נשארת `{ "object": "list",
"data": [...] }`). מימוש: `src/app/api/v1/models/catalogPricing.ts`.

### קידומות מזהי מודלים (`?prefix=`)

רוב המודלים מוצגים תחת **קידומת ספק**. הקידומת שתקבל נשלטת באמצעות
דגל התכונה `MODELS_CATALOG_PREFIX_MODE`, וניתן לדרוס אותה **לכל בקשה בנפרד** באמצעות
פרמטר שאילתה — שימושי עבור לקוח שרוצה רשימה נקייה מבלי לשנות את ההגדרה הכללית
בשרת עבור כל השאר:

```bash
GET /v1/models?prefix=alias        # מזהה אחד לכל מודל — קידומת הכינוי הקצרה
GET /v1/models?prefix=dual         # שתי הצורות (ברירת המחדל של השרת)
GET /v1/models?prefix=canonical    # רק הקידומת המלאה של מזהה הספק
```

| מצב         | פלט                                                       | הערות                                                                                                                                                                |
| ----------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **וגם** `claude/claude-sonnet-4-6` | **ברירת המחדל.** שני המזהים מנתבים לאותו מודל; נשמרו כדי שתצורות לקוח שבהן אחת מהצורות מקודדת באופן קשיח ימשיכו לפעול. מכפיל בקירוב את גודל הקטלוג.                  |
| `alias`     | `cc/claude-sonnet-4-6`                                    | רשומה אחת לכל מודל. ספקים ללא כינוי נפרד עדיין מפיקים את הרשומה שלהם, כך שדבר אינו הולך לאיבוד.                                                                      |
| `canonical` | `claude/claude-sonnet-4-6`                                | רשומה אחת לכל מודל תחת הקידומת המלאה של מזהה הספק. ספקים ללא כינוי נפרד (למשל `antigravity/…`, `agy/…`) מפיקים גם כאן את המזהה היחיד שלהם, כך שדבר אינו הולך לאיבוד. |

ניתן לזהות שיקוף במצב `dual` גם ללא פרמטר השאילתה: הוא מכיל שדה `parent`
המצביע על המזהה הראשי.

לקוחות המציגים בורר מודלים צריכים לבקש `?prefix=alias` — כך פועלת
[הרחבת OmniCopilot עבור VS Code](../guides/VSCODE-COPILOT.md).

### מסנני גילוי (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` מקבל מסנני גילוי אופציונליים. ללא אף אחד מהם, התגובה
אינה משתנה. הם מצמצמים את הקטלוג שהמתקשר כבר רואה (הרשאות מפתח API מוחלות תחילה),
והם פועלים לפני הדפדוף בסגנון OpenAI באמצעות `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # כל יכולת שמופיעה חייבת להיות true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # שדה `type` בקטלוג; שורות ללא שדה כזה הן `chat`
GET /v1/models?q=sonnet&limit=10                           # התאמה שאינה תלוית רישיות לפי מזהה או שם
```

| פרמטר         | ערכים                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | מספר שלם שאינו שלילי, המושווה ל־`context_length`                                                    |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 תווים                                                                                         |

ערך לא מוכר, או `min_context` שאינו מספר שלם שאינו שלילי (לדוגמה `1.5`),
מחזירים HTTP `400`, וההודעה מפרטת את הערכים התקינים. מימוש:
`src/app/api/v1/models/catalogFilters.ts`.

### רשימת מודלים מצומצמת (`POST /v1/models/query`)

`POST /v1/models/query` מחזיר רשימה קצרה ודטרמיניסטית מאותו קטלוג, עם אותם
אימות והרשאות נראות לכל מפתח כמו `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

כל שדה הוא אופציונלי. `capabilities` ו־`exclude` מקבלים מערך או מחרוזת מופרדת בפסיקים;
`max_output` מושווה ל־`max_output_tokens`. התוצאות ממוינות לפי `owned_by`, ולאחר מכן לפי `id`.
ערך ברירת המחדל של `limit` הוא `20`, וערכים מעל `100` מוגבלים ל־`100`. JSON לא תקין, שדה
לא מוכר או ערך לא תקין מחזירים HTTP `400`.

### מודלי צ׳אט מוסתרים בנפרד

מודל המסומן כ־**מוסתר** בדף הספק שלו אינו נכלל בקטלוג, ובקשה מפורשת עבורו נדחית
עם HTTP `404` / `model_not_found`. הבדיקה משתמשת בספק ובמודל שנקבעו, לרבות כינויים
של ספקים, תחיליות צמתים של ספקים תואמים וברירות מחדל של חיבורים. שילוב מדלג על יעדים
מוסתרים ויכול להשתמש ביעד חלופי גלוי; כאשר לא נותר יעד שניתן להריץ, מוחזר אותו קוד שגיאה.
ביטול ההסתרה נכנס לתוקף בבקשה הבאה. הגדרות נראות עוקפות לתמונות בלבד אינן מסתירות
את מודל הצ׳אט בעל אותו מזהה.

הגדרת מודל נפרדת זו אינה קשורה ל־
[רשימות ההרשאה/חסימה לחשיפת מודלים](../routing/MODEL_EXPOSURE_LIST.md), שמסננות את
הצגת הקטלוג ואת המועמדים לניתוב אוטומטי, תוך שמירה על ניתוב מפורש. הרשאות מודלים
של מפתחות API ממשיכות לחול באופן עצמאי. מצב תחילית הקטלוג המוגדר כברירת מחדל נשאר `dual`.

### וריאציות מודל ללא חשיבה

עבור מודלי Claude התומכים בחשיבה, `/v1/models` מפרסם גם וריאציית **ללא חשיבה**, שהמזהה שלה מתחיל ב־`claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

בחירת מזהה זה (לדוגמה, בתצורת Claude Code שתמיד מצרפת בלוק `thinking`) חוזרת אל `<provider>/<model>` האמיתי תוך דיכוי ההסקה — `thinking:{type:"disabled"}` בנתיב `/v1/messages`, או הסרת השדות `reasoning`/`reasoning_effort` בנתיב `/v1/chat/completions`. הווריאציה מופיעה רק עבור מודלים ממשפחת Claude שתומכים בחשיבה **וגם** מכבדים `disabled` (כך שלדוגמה, מודלים אדפטיביים בלבד שדוחים `disabled` אינם נכללים). מפעילים יכולים לאלץ את הפעלת הווריאציה או את השבתתה עבור כל מודל באמצעות `ModelSpec.noThinkingAlias`.

## יצירת אודיו באמצעות ElevenLabs

הגדירו ב-OmniRoute חיבור לספק `elevenlabs` באמצעות מפתח ה-API שלכם ב-ElevenLabs.
לקוחות מבצעים אימות באמצעות מפתח **OmniRoute** שלהם (`Authorization: Bearer $OMNIROUTE_API_KEY`);
השער מספק את מפתח הספק השמור בתור `xi-api-key`. לעולם אל תשלחו מפתח ElevenLabs
בתור אסימון ה-bearer של השער.

| שיטה | נתיב                        | תגובה                                  | קטגוריית נקודת הקצה של מפתח ה-API |
| ---- | --------------------------- | -------------------------------------- | --------------------------------- |
| POST | `/v1/sound-generation`      | בתים של אודיו מקורי                    | `elevenlabs`                      |
| POST | `/v1/music`                 | בתים של אודיו מקורי                    | `music`                           |
| POST | `/v1/music/stream`          | בתים של אודיו מוזרם                    | `music`                           |
| POST | `/v1/music/detailed`        | אודיו multipart מקורי ותוכנית הלחנה    | `music`                           |
| POST | `/v1/music/detailed/stream` | מטא-נתונים מקוריים של SSE ומקטעי אודיו | `music`                           |
| POST | `/v1/music/plan`            | תוכנית הלחנה בפורמט JSON               | `music`                           |

נקודות קצה אלה משלימות את הנתיבים הקיימים `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` ו-`/v1/speech-to-text`. שדות JSON מקוריים
ופרמטרי שאילתה כגון `output_format` ו-`enable_logging` נשמרים.
התגובות של `/v1/music/detailed` שומרות על גבולות ה-multipart שלהן; יש לנתח אותן כ-multipart.
`/v1/music/detailed/stream` מחזיר `text/event-stream` עם מטא-נתונים של ההלחנה
ומקטעי אודיו בקידוד base64 באירועי SSE. כל ששת הנתיבים תומכים בבקשות קדם של CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# אפקט צליל קצר. משך: 0.5 עד 30 שניות.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# משך המוזיקה מבוטא באלפיות השנייה: 3000 עד 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

השתמשו ב-`/v1/music/stream` עם אותו גוף JSON לצורך מסירה הדרגתית של האודיו. ההלחנה
מקבלת בדיוק אחד מבין `prompt` או `composition_plan`; הנתיב `/v1/music/plan` דורש `prompt`
ומקבל באופן אופציונלי את `source_composition_plan`. הסכמות המקוריות משמרות שדות ספק
נוספים, כדי שגרסאות של תוכניות הלחנה ואפשרויות כוונון עדין יגיעו ל-ElevenLabs.

נקודת הקצה המאוחדת `/v1/music/generations` מקבלת גם את `elevenlabs/music_v1`,
`elevenlabs/music_v2` ואת `elevenlabs/music_v2_5`. כאשר קיים חיבור פעיל ל-ElevenLabs,
מודלים אלה מוצגים בקטלוג המוזיקה. נקודת קצה זו מחזירה
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. השדה `duration` שלה נמדד
בשניות וממופה אל `music_length_ms`; ערך מפורש של `music_length_ms` מקבל קדימות.
`instrumental` ממופה אל `force_instrumental`, כאשר השדה המקורי מקבל קדימות.
השתמשו בנקודות הקצה המקוריות להזרמה לצורך הזרמה, ובנקודת הקצה המקורית להלחנה
עבור בקשות שמונעות רק באמצעות תוכנית הלחנה.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

הגבלות של נקודת קצה, מודל, תקציב וחיבור חלות לפני קריאה לשירות המקור. נתיבים מקוריים
מחזירים את קודי הסטטוס ואת גופי השגיאות משירות המקור ללא שינוי, כולל `402` עבור הגבלה
של תוכנית ו-`429` עבור מגבלת מכסה. הכותרות `character-cost`, `song-id`, `request-id` ו-`retry-after`
נשמרות כאשר הן קיימות. יתרת זיכויים חינמית אינה מבטיחה גישה לכל
מודל מוזיקה, פורמט פלט או תכונת API: ElevenLabs קובעת את הזכאות לכל בקשה.
נקודת הקצה המאוחדת משמרת קודי סטטוס של שגיאות במעטפת השגיאות המנורמלת של OmniRoute.

חוזי שירות המקור: [אפקטים קוליים](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[הלחנת מוזיקה](https://elevenlabs.io/docs/api-reference/music/compose) ו-
[פרטי מוזיקה מוזרמת](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **צומתי ספק לדירוג מחדש:** `POST /v1/rerank` מנתב גם לצומתי ספק תואמי OpenAI
> (oMLX, vLLM, Infinity, TEI מאחורי שער, …) שהכתובת שלהם היא `<node-prefix>/<model>`. צומתי
> לולאה חוזרת (`localhost`, `127.0.0.1`, `172.16.0.0/12`) תמיד כשירים, וכך גם שמות מארחים
> שהמפעיל מגדיר ב-`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (למשל שם שירות של Docker/Compose כגון
> `http://reranker:8080/v1`; הפנייה אליהם מתבצעת ישירות, לעולם לא דרך `HTTP(S)_PROXY` או דרך
> פרוקסי מקובע של חיבור). צמתים בכל מארח אחר
> — מחשב ברשת LAN או עמית Tailscale — כשירים רק כאשר המפעיל מפעיל את דגל התכונה
> `RERANK_REMOTE_PROVIDER_NODES` **וגם** כתובת ה-URL הבסיסית של הצומת עוברת את מדיניות כתובות
> ה-URL היוצאות של הספק (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> שלב הדירוג מחדש של מנוע הזיכרון קורא לנתיב זה דרך
> לולאה חוזרת, ולכן אותו כלל חל על `rerankProviderModel` בהגדרות הזיכרון.
>
> **תצורות שרת מקומי:** הקריאה לצומת מתבצעת ב-`<base>/v1/rerank`, ובמקרה של 404, ב-`<base>/rerank`
> (Infinity, TEI). גוף הבקשה למעלה הזרם כולל הן את האיות של Cohere/OpenAI (`documents`,
> `return_documents`) והן את האיות של TEI (`texts`, `return_text`), ותגובת השרת במעלה הזרם
> מנורמלת למעטפת Cohere: המערך החשוף של TEI, ‏`[{index, score, text}]`, המבנה `{results: [{index, score}]}`
> משערים רזים, והמבנה בסגנון Voyage ‏`{data: [...]}` — כולם מוחזרים ללקוח בתור
> `{results: [{index, relevance_score, document?}]}`, ממוינים לפי ציון ומוגבלים ל-`top_n`.

> **גילוי צומתי ספק:** מודלים בצומת ספק תואם OpenAI מופיעים ב-`GET /v1/models`
> תחת קידומת הצומת. רשומות שאינן כוללות מטא-נתונים של נקודת קצה (כמקובל ברשימות `/v1/models` מקומיות)
> יורשות את ה-`apiType` של הצומת, כך שהמודלים של צומת `embeddings` הם `type: "embedding"` והמודלים
> של צומת `rerank` הם `type: "rerank"` במקום שברירת המחדל שלהם תהיה צ'אט; ערך מפורש של
> `supportedEndpoints` ברשומה מסונכרנת או שנוספה ידנית עדיין מקבל קדימות.

### אקסה וטבילי `provider_options`

Exa ו-Tavily קוראים שדות ספציפיים לספק מתוך תיק עם רווחי שם: `provider_options.exa` (או `provider_options["exa-search"]`) ו- `provider_options.tavily` (או `provider_options["tavily-search"]`). רק המפתחות למטה מועברים. כל אחד מהם נבדק מול סכימת Zod משלו ב- `open-sse/handlers/search/providerOptionsPassthrough.ts`, ומפתח עם הסוג הלא נכון נשמט. מתעלמים מכל מפתח אחר, כולל auth, base URL, `stream` ו- `outputSchema`. המקשים השטוחים שבהם משתמשים ספקים אחרים (`cx`, `depth`, ...) עובדים כמו קודם.

| ספק   | שדות ברמה העליונה                                                                                                                                                                                                                                                                                                                                                         | מקונן                                                                                                                                 |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Exa   | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (פרימיטיבים שטוחים), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` התמזג על ברירת המחדל `{ text: true, highlights: true }` |
| טבילי | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                     |

השדות הגנריים תמיד מנצחים: `query`, `max_results`, `filters` (דומיינים), `country` והנושא הנגזר מ- `search_type`. ב-Exa, `search_type: "news"` שומר על `category: "news"`. טבילי מקבל גם `search_type: "finance"` (`topic: "finance"`).

עלות החיפוש של Firecrawl נרשמת לכל בלוק התחיל של 10 תוצאות שהוחזרו, ב-$0.002 (2 זיכויים) לחסימה ולפחות חסימה אחת לשיחה ( [חיוב Firecrawl](https://docs.firecrawl.dev/billing) ): 11 תוצאות עולות $0.004.

ה- `time_range` הגנרי מגיע כעת לשני הספקים: Exa מקבל `startPublishedDate` (חותמת זמן ISO ) ו-Tavily מקבל `start_date` (`YYYY-MM-DD`). תאריך מפורש ב- `provider_options` עוקף את המופה.

תוצאות Exa שומרות על `id`, `highlight_scores`, `summary`, `subpages`, `entities` ו- `extras` ב- `provider_raw`. תוצאות טובות לשמור על `images` ו- `favicon`.

עלות חיפוש קישור נרשמת ב-$0.005 עבור `depth` `fast` ו- `standard` ו-$0.05 עבור `deep` ( [מחיר Linkup](https://docs.linkup.so/pages/documentation/development/pricing) ), בין אם `depth` מגיע מ- `provider_options` או מהגדרות החיבור.

Exa `type: "lite"` (Exa 3.0) מקבל קבוצה קטנה יותר של שדות ודוחה את כל הבקשה כאשר כל שדה אחר מוגדר. עבור lite, `additionalQueries`, `systemPrompt` וכל מקש `contents` מלבד `text` ו- `highlights` נשמטים לפני השיחה. `subpages`, `subpageTarget`, `highlights.numSentences` ו- `highlights.highlightsPerUrl` לא מועברים עוד.

חשבונאות עלויות היא הרישום השטוח `costPerQuery`, למעט Exa, העוקב אחר התמחור של Exa עצמו: $0.007 לקריאה עבור `auto` (וה- `fast` מדור קודם) או $0.004 עבור `lite` (וה- `instant` מדור קודם), המכסה 10 תוצאות; $0.001 עבור כל תוצאה נוספת; ו-$0.001 לתוצאה שהוחזרה כאשר `contents.summary` מוגדר. Tavily נרשם ב-1 זיכוי ($0.008) עבור `search_depth` `basic`, `fast` ו- `ultra-fast`, ו-2 קרדיטים ($0.016) עבור `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) ). שיחה עם `auto_parameters: true` שתווילי משדרגת למתקדמים עדיין מוקלטת ב-1 זיכוי.

## Web Fetch API

חילוץ תוכן מכתובת URL באמצעות ספק web-fetch מוגדר (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, אותו מפתח API כמו Parallel Search) מחזיר Markdown
בלבד — כל `format` אחר גורר שגיאת `400` — ומגביל את התוכן ל-100,000 תווים. כאשר
לא ניתן לחלץ את דף היעד עצמו, שירות המקור מדווח על כך בתוך HTTP 200;
OmniRoute מציג זאת כשגיאת `422` עם הודעה קבועה.

| שיטה | נתיב            | תיאור                                                              |
| ---- | --------------- | ------------------------------------------------------------------ |
| POST | `/v1/web/fetch` | אחזור/גירוד כתובת URL — גוף הבקשה מאומת באמצעות `v1WebFetchSchema` |

**אימות:** מפתח API מסוג Bearer (`extractApiKey` + `isValidApiKey`). המדיניות נאכפת באמצעות `enforceApiKeyPolicy`.

**מעבר אוטומטי מודע למכסה (#8297):** כאשר לא מצוין `provider` מפורש, המאגר
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) נסרק בסדר
עדיפויות קבוע (מילוי-ראשון) — מדלגים על ספק מוגדר שהוגבל בקצב
במקום להפסיק מיד את הבקשה, וכשל ניתן לניסיון חוזר/הקשור למכסה אצל שירות המקור
(HTTP 429 תמיד; 402/403 עבור שכבות חינמיות מבוססות-מכסה של Firecrawl/Tavily/TinyFish —
לא עבור Jina Reader, ולעולם לא עבור בקשה שגויה רגילה מסוג 400) גורם למעבר
לספק הבא שטרם נוסה ושיש עבורו פרטי גישה בזמן הבקשה. כאשר כל ספקי
המאגר מוצו, נקודת הקצה מחזירה `429` יחיד (עם כותרת `Retry-After`)
במקום שגיאת `400` הכללית הקודמת. כאשר מתבקש `provider`
מפורש, **אין** מעבר אוטומטי שקט — ספק מפורש שהוגבל בקצב או שנכשל
מציג את השגיאה שלו (`429` אם הוגבל בקצב, אחרת סטטוס
שירות המקור).

## הזרמה באמצעות WebSocket

### Responses API באמצעות WebSocket (עבור codex בלבד)

```bash
# אותו מארח ואותה יציאה כמו HTTP API (ברירת המחדל היא 20128); שדרגו את החיבור:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (או: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# המסגרת הראשונה חייבת להיות response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

מתווך Responses-API-over-WebSocket מחובר **באופן בלעדי אל `codex`** (קצה אחורי של ChatGPT).
הוא מאזין באותה יציאה כמו ה-API/לוח הבקרה בנתיבים `/v1/responses`,
`/responses` ו-`/api/v1/responses`. במסגרת `response.create` הראשונה הוא
מבצע אימות והכנה באמצעות גשר `codex-responses-ws` הפנימי, בוחר
חיבור OAuth של codex ומעביר את התעבורה אל `wss://chatgpt.com/backend-api/codex/responses`
באמצעות תעבורת `wreq-js`. **מודלים שאינם codex נדחים** (`codex_ws_provider_required`).
לניתוב שיתוף מכסה, השתמשו ב-`model: "qtSd/<group>/codex/<model>"`. המימוש נמצא ב-
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**אימות:** מפתח API מסוג Bearer במהלך לחיצת היד. שרת ה-HTTP המצורף (`server-ws.mjs`)
חייב להיות נקודת הכניסה הפעילה (וכברירת מחדל הוא אכן כזה, כאשר `app/server-ws.mjs` קיים).

#### מזהה מודל: השתמשו במזהה ChatGPT הגולמי (ללא הקידומת `codex/`)

ה-**Codex CLI** של OpenAI מאמת את שם המודל בצד הלקוח כאשר
`supports_websockets = true` ו**דוחה מזהים עם קידומת ספק** כגון
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). שלחו את המזהה **הגולמי** (לדוגמה, `gpt-5.5`). הגשר של OmniRoute
מיועד ל-codex בלבד, ולכן הוא פותר מחדש מזהה גולמי כמודל codex
(`resolveCodexWsModelInfo`) לפני העברת התעבורה לשירות המקור — אף שמזהה גולמי
`gpt-5.5` היה מנותב אחרת לספק אחר באמצעות HTTP.

#### הגדרת OpenAI Codex CLI

הפנו את Codex CLI אל OmniRoute על ידי הוספת ספק מותאם אישית עם תמיכה
ב-WebSocket אל `~/.codex/config.toml` (השתמשו ב-`CODEX_HOME` נפרד כדי להימנע משינוי
תצורה קיימת):

```toml
model = "gpt-5.5"                 # מזהה גולמי — לא "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ללא לוכסן מסיים; כתובת ה-WS נגזרת מכאן (השתמשו ב-https/wss בסביבת ייצור)
wire_api = "responses"                    # הערך הנתמך היחיד מאז פברואר 2026
supports_websockets = true                # מפעיל תעבורת Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # מכיל את מפתח ה-API של OmniRoute‏ (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # מפתח API של OmniRoute‏ (כל מפתח אם REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

ה-CLI משדרג את `base_url + /responses` ל-WebSocket, ו-OmniRoute מעביר את התעבורה
לחיבור OAuth של codex שנבחר. התהליך אומת מקצה לקצה מול השרת המקומי:
ChatGPT מחזיר `codex.rate_limits` + `response.created` ומזרים את
ההשלמה.

## שימוש בשירות עצמי (`/api/usage/om-usage`)

כל מפתח API יכול לקרוא את נתוני השימוש והמכסות **שלו עצמו** — ללא אימות ניהולי. זוהי נקודת הקצה שבה
לקוח (CLI, הפאנל של OmniCopilot) משתמש כדי להציג לבעל המפתח את ההוצאות שלו.

```bash
# תצורת טקסט (החוזה ההיסטורי — טקסט פשוט למסוף)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# תצורה מובנית — מה שממשק משתמש צורך
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

במפתח חייבת להיות מופעלת האפשרות **`allowUsageCommand`** (כבויה כברירת מחדל — מנהל מפתחות ה-API
בלוח הבקרה מפעיל או משבית אותה לכל מפתח). בלעדיה, נקודת הקצה מחזירה `403`.

הפרמטר `?format=json` מחזיר מבנה מבחין, כך שקורא לעולם אינו קורא שדה נתונים מתוך
סירוב. במקרה של הצלחה:

```jsonc
{
  "allowed": true,
  // קיים רק כאשר המפתח הצטרף למגבלות שימוש לפי מפתח (יומיות/שבועיות בדולר ארה"ב):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // תמונת מצב של מכסת הספק שנבחר, או null כאשר דבר עדיין אינו שמור במטמון:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // תמונות המצב של כל החיבורים, כדי שממשק משתמש יוכל להציג כמה ספקים זה לצד זה:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

במקרה של סירוב (`401` מפתח שגוי / `403` אין הרשאה), אותו נתיב מחזיר
`{ "allowed": false, "error": { "message": "…" } }` — מצב שבו `personal`/`provider` קיימים אך ריקים
(המפתח מורשה, אך עדיין לא התקבל מידע) שונה מסירוב, ורק תצורת ה-JSON
מבחינה ביניהם.

**אימות:** מפתח ה-API מסוג Bearer של הקורא עצמו, המאומת באמצעות `isValidApiKey` — זהו _לא_
ממשק הניהול (`/api/keys/…`), שנותר מוגן באמצעות `requireManagementAuth`.

### אחוזי מכסה גולמיים לעומת אחוזים מותאמי סף

בעת צריכת `/api/usage/om-usage`, על הקוראים לשים לב להבדל בין
האחוזים המוצגים ב**פלט הטקסט הפשוט** לבין **פלט ה-JSON** המובנה:

| היבט           | תצורת טקסט פשוט (`/api/usage/om-usage` / `@@om-usage`)                           | תצורת JSON‏ (`?format=json`)                                         |
| :------------- | :------------------------------------------------------------------------------- | :------------------------------------------------------------------- |
| **שדה פלט**    | `NN% left` (למשל, `20% left`)                                                    | `provider.quotas` / `providers[].quotas`                             |
| **מדידה**      | **הקצאה זמינה מותאמת לסף**: הקיבולת שנותרה מעל סף הקיטוע                         | **מכסת ספק גולמית**: מדידת הספק ללא התאמות                           |
| **התאמת הסף**  | מותאמת באמצעות `effectiveRemainingPercent()` כך שהרזרבה המוגנת מוצגת כ-`0% left` | ללא (ערכי תמונת מצב גולמיים כפי שדווחו על ידי הספק)                  |
| **נתוני סף**   | משולבים באחוז המוצג                                                              | נשמרים ב-`quotaWindowThresholds` לכל חיבור (או כברירות מחדל של השרת) |
| **צרכן עיקרי** | ממשקי CLI אינטראקטיביים, הנחיות מסוף, מפעילים אנושיים                            | אינטגרציות תכנותיות, לוחות בקרה, ניתוח נתונים, עוקבי חיוב            |

#### נוסחת התאמת הסף

OmniRoute תומך בספי קיטוע יזומים של מכסות כדי למנוע מיצוי של משאבי הספק (מוגדרים באמצעות
`quotaWindowThresholds` של החיבור, ברירות המחדל של הספק או הגדרות החוסן הגלובליות). כאשר סף קיטוע
(למשל, `cutoff = 25%`) פעיל בחלון מכסה, מעבד הטקסט מחשב את ההקצאה שנותרה כך:

- אם `remaining <= cutoff`: מוחזר `0%`.
- אם `remaining > cutoff`: מוחזר `((remaining - cutoff) / (100 - cutoff)) * 100`.

פלט הטקסט המעוצב מעגל זאת למספר השלם הקרוב ביותר (`Math.round(...)`).

#### דוגמה להמחשה

נניח חלון ספק עם **60% שימוש גולמי** (ולפיכך **40% מכסה גולמית שנותרה**) ועם סף מוגדר של
**25% קיטוע מהמכסה שנותרה**:

| ייצוג                           | חישוב                                              |  נותרו  |            שימוש משתמע             |
| :------------------------------ | :------------------------------------------------- | :-----: | :--------------------------------: |
| **JSON גולמי (`?format=json`)** | תמונת מצב מהספק (`quotas[window]`)                 | **40%** |              **60%**               |
| **תצורת טקסט (`NN% left`)**     | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (בחישוב `100 - remaining`) |

- **מדוע הטקסט מציג 20% שנותרו:** מתוך 40% מהמכסה הפיזית שנותרה בחשבון, 25% שמורים על ידי
  מדיניות הסף. לקורא נותרו רק 15% מתוך מרווח שמיש של 75% לפני שהנתב מפסיק
  לנתב לחיבור זה. ההתאמה מבטיחה שהחיבור יסמן מיצוי (`0% left`) בדיוק כאשר
  הניתוב ייפסק.
- **מדוע JSON שומר על הערכים הגולמיים:** מטען ה-JSON מחזיר את תמונת המצב המדויקת של הספק (`UsageSnapshot`)
  כדי שלכלים חיצוניים תהיה גישה לנתוני המקור המדויקים של ניצולת הספק ול-`quotaWindowThresholds`
  ברמת החיבור, ללא התאמה מאבדת מידע בצד השרת.

#### הנחיות להעברת צרכנים

אם אינטגרציה חיצונית (כגון תוסף לעורך או הרחבת סוכן) חילצה בעבר את הנתונים מנקודת הקצה
הטקסטואלית (`NN% left`) וחישבה את אחוז השימוש בתור `100 - NN`, המעבר אל `?format=json` משמעו:

- קריאת ערכי JSON גולמיים תשקף את **הצריכה בפועל במעלה הזרם** (60% שימוש בדוגמה שלעיל).
- אם האינטגרציה מעוניינת לשמר את סמנטיקת המכסה הזמינה של נקודת הקצה הטקסטואלית, היא יכולה לחשב
  בצד הלקוח את נוסחת היתרה האפקטיבית באמצעות `quotaWindowThresholds` לצורך דריסות ברמת החיבור.

### השפעה על זמן ההשהיה

פגיעה במטמון הסמנטי (HIT) מספקת את התגובה מהמטמון **ללא קריאה לשירות
במעלה הזרם**, ולכן הערך המדווח של `X-OmniRoute-Response-Latency` קרוב לאפס
(ללא תלות בזמן ההשהיה המקורי במעלה הזרם). לקוחות הרגישים לזמן השהיה
(מדידות ביצועים, ניטור p50/p99) צריכים לבדוק את כותרת התגובה
`X-OmniRoute-Cache-Latency`:

| ערך         | משמעות                                                     |
| ----------- | ---------------------------------------------------------- |
| `synthetic` | התגובה סופקה מהמטמון; זמן ההשהיה אינו זמן אמיתי במעלה הזרם |
| _(חסר)_     | תגובה מקריאה אמיתית לשירות במעלה הזרם                      |

### עקיפת מטמון לפי מפתח

מפתחות API יכולים לוותר על קריאות מהמטמון הסמנטי באמצעות `cacheDefaultMode`:

| ערך      | התנהגות                                            |
| -------- | -------------------------------------------------- |
| `legacy` | התנהגות מטמון רגילה (ברירת המחדל)                  |
| `bypass` | דילוג מוחלט על חיפוש במטמון; פנייה תמיד במעלה הזרם |

הגדירו בעת יצירת המפתח (`POST /api/keys`) או בעת עדכון (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### עקיפה לפי בקשה

כל בקשה יכולה לעקוף את המטמון ללא תלות בהגדרות המפתח:

```
X-OmniRoute-No-Cache: true
```

עבור מודלים שסונכרנו/יובאו, `PUT /api/provider-models` מקבל את `provider`, את `modelId` ואת
`maxOutputTokenOverride`: מספר שלם חיובי מגדיר את מגבלת אסימוני הפלט הידנית, ו-`null`
מנקה אותה כדי לשחזר את ברירת המחדל. `GET /api/provider-models?provider=<provider>` מחזיר ערכים אלה
בתוך `modelOutputOverrides`, כולל מודלים ללא רשומת מודל מותאם אישית. הדריסה
משתמשת ביכולת זמן הריצה `max_output_tokens` ונשמרת גם לאחר סנכרון מחדש של מודל. דף הספק
התואם ל-OpenAI מציע את אותם פקדי עריכה/ניקוי ומסמן מודלים בעלי תמיכה מפורשת בראייה.

צומתי Chat Completions מותאמים אישית מתאימים ביטולי הסקה מפורשים למערכת הקצה במעלה הזרם. בדיקת
חיבור מוצלחת בוחרת אוטומטית פקדי תבנית צ'אט עבור כל מזהה מודל מדויק
שהרשומה שלו ב-`/models` מוכיחה ערך `owned_by` מוכר: `vllm`, `sglang` או `llamacpp`.
מעטפות שקופות התואמות ל-OpenAI עשויות לשמר את רשומת המודל המקורית בתוך אובייקט
`openai` מקונן; הזיהוי עוקב אחר עד שלוש מעטפות כאלה. מודלים עם בעלות חסרה, לא מוכרת או
סותרת שומרים על התנהגות OpenAI רגילה. הזיהוי משתמש מחדש בבקשת הקטלוג הקיימת,
אינו מייצר אסימוני השלמה, ותוקפו מבוטל כאשר נקודת הקצה של החיבור משתנה.

כדי לקבע את ההתנהגות עבור מערכת קצה שאינה חושפת מטא-נתונים אלה, השתמשו ב-API הקיים לעדכון
חלקי של ספק:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

שלחו גוף זה באמצעות `PUT /api/providers/<connection-id>`. בחיבור זה, מאמץ
הסקה מפורש של `none` נשלח בתור `chat_template_kwargs.thinking=false` וגם
`chat_template_kwargs.enable_thinking=false`. ערכי תבנית מקוריים מפורשים נשארים בעלי הסמכות
אלא אם כלל הסקה בצד השרת כופה רמת מאמץ. ההגדרה חלה רק כאשר חיבור מותאם אישית
התואם ל-OpenAI שולח גוף של Chat Completions; בקשות Responses וספקים רגילים
שומרים על מבנה הבקשה המקורי שלהם. הגדירו את `reasoningControl` ל-`openai` כדי לאלץ העברה רגילה של
`reasoning_effort` אל OpenAI, או השמיטו אותו/הגדירו אותו ל-`null` כדי להשתמש בזיהוי אוטומטי.

בקשות המסווג של Claude Code במצב אוטומטי מגדירות כברירת מחדל את ההסקה המקורית כמושבתת כאשר הן
אינן מכילות פקדי הסקה מפורשים. הזיהוי משתמש בסמן המערכת של המסווג בבקשות
בפורמט Claude, ולא בשמות מודלים או במגבלות השלמה. פקדים מפורשים בגוף הבקשה, כותרות
מאמץ/הסקה נתמכות, כללי ניתוב ומאמץ מודל שכבר הוכרע שומרים על העדיפות הקיימת שלהם. שני שלבי
המסווג שומרים על ההנחיות, מגבלות ההשלמה, רצפי העצירה והכרעות ההרשאה האמיתיות
שלהם ממערכת הקצה במעלה הזרם; השלב השני עדיין יכול להפיק את ההסקה הגלויה שהתבקשה כטקסט רגיל.

### גרסה וערוץ הפצה

```bash
GET /api/system/version
```

נתיב ניהול המוגבל ל-loopback בלבד (אימות מנהל מערכת). מחזיר את הגרסה הפועלת, את הגרסה האחרונה
שפורסמה ואת מצב העדכון האוטומטי. `releaseChannel` ו-`channels` הם שדות שנוספו
במסלול 3.8.54; המשמעות של `channel` נשארת ללא שינוי — מצב הפריסה שבו משתמש מעדכן לוח הבקרה
(`npm`, `source` או `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ערוץ ה-npm של גרסת ה-build הפועלת: `nightly` עבור גרסאות `-nightly.*`,
  `next` עבור גרסאות קדם-הפצה אחרות (`-rc.*`, `-beta.*`, `-alpha.*`),‏ `lts` עבור גרסה יציבה של
  גרסה ראשית ישנה יותר מזו שב-`channels.latest`, ובכל מקרה אחר `latest`. אותם כללים כמו
  ב-`scripts/release/dist-tag.mjs`, שבוחר את ה-dist-tag של npm בזמן הפרסום.
- `channels` — הגרסה העדכנית שפורסמה בכל dist-tag, מתוך `npm view omniroute dist-tags` (עם
  גיבוי באמצעות HTTP של הרישום), שנשמרת במטמון עם אותו TTL של 10 דקות כמו `latest`. הערך `latest` קיים תמיד
  (עם חזרה לערך שבשדה `latest`, ולאחר מכן ל-`"unavailable"`); הערכים `next`,‏ `nightly` ו-`lts` מופיעים
  רק כאשר ה-dist-tag המתאים קיים. בקשה עם `Cache-Control: no-cache` מרעננת את שתי הבדיקות.

מודל הערוצים (`latest` = v3 עד ההשקה הכללית של 4.0,‏ `next` = rc,‏ `nightly` = גרסאות build של `develop`,
‏`lts` = תיקוני v3 לאחר ההשקה הכללית של 4.0) מתואר ב-`docs/ops/RELEASE_STRATEGY.md`.

## כינויים עם אסימון עבור VS Code / כינויים ללא כותרת

השתמשו בכינויים אלה כאשר אינטגרציה אינה יכולה להוסיף כותרת `Authorization` וזקוקה למפתח ה-API כשהוא מוטמע בכתובת ה-URL הבסיסית.

```bash
# כינוי קטלוג בסגנון OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# כינויי צ'אט בסגנון OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# כינויים בסגנון Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

דוגמה:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

הערות:

- הכינויים הכוללים אסימון משתמשים מחדש באותם מטפלים כמו `/v1/*` ו-`/api/tags`; מבני התגובות נשארים זהים.
- העדיפו את `Authorization: Bearer ...` בכל פעם שהלקוח תומך בכותרות מותאמות אישית.
- אסימונים המבוססים על כתובות URL עשויים להופיע ביומני רישום של פרוקסי הפוך, בהיסטוריית הדפדפן ובטלמטריה מחוץ ל-OmniRoute. התייחסו אליהם כאפשרות תאימות, ולא כמצב האימות המוגדר כברירת מחדל.

## מגבלות טוקנים

מכסות **טוקנים** לכל מפתח API (בנפרד מהתקציב המבוסס על USD לעיל). האכיפה מתבצעת כחלק מנתיב הבקשה: כאשר השימוש של מפתח בחלון הנוכחי מגיע למגבלה שלו, בקשות נדחות עם `429 Too Many Requests`. ניתן להחיל מגבלות על `model` מסוים, על `provider`, או באופן `global`י על פני המפתח כולו; כאשר כמה מגבלות תואמות לבקשה, המגבלה המחמירה ביותר גוברת.

```bash
# הצגת מגבלות הטוקנים של מפתח (כולל השימוש הנוכחי בחלון)
GET /api/usage/token-limits?apiKeyId=key-123

# יצירה או עדכון של מגבלת טוקנים
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# מחיקת מגבלת טוקנים לפי מזהה
DELETE /api/usage/token-limits?id=tl-abc
```

> **הערות לגבי הסכמה** (`setTokenLimitSchema`): השדות `apiKeyId` ו-`scopeType`‏ (`model` | `provider` | `global`) נדרשים. השדה `scopeValue` נדרש, אלא אם `scopeType` הוא `global` (לדוגמה, מזהה מודל עבור תחום `model`, או מזהה ספק עבור תחום `provider`). השדה `tokenLimit` חייב להיות מספר שלם חיובי (עם המרה ממחרוזת). אופציונלי: `id` (יש להשמיט כדי ליצור ולספק כדי לעדכן), `resetInterval`‏ (`daily` | `weekly` | `monthly`, ברירת המחדל היא `monthly`),‏ `resetTime`‏ (`HH:MM`),‏ `enabled` (ברירת המחדל היא `true`). תגובות `GET` מעשירות כל מגבלה בשדות `tokensUsed`,‏ `remaining`,‏ `windowStart`,‏ `periodStartAt` ו-`nextResetAt`. זוהי נקודת קצה מסוג ניהול (האימות נאכף באופן מרכזי על ידי תהליך ההרשאה).

## עיבוד בקשות

1. הלקוח שולח בקשה אל `/v1/*`
2. מטפל הנתיב קורא ל-`handleChat`,‏ `handleEmbedding`,‏ `handleAudioTranscription` או `handleImageGeneration`
3. המודל מזוהה (ספק/מודל ישיר או כינוי/שילוב)
4. פרטי ההזדהות נבחרים ממסד הנתונים המקומי, תוך סינון לפי זמינות החשבון
5. עבור צ'אט: `handleChatCore` בודק את מטמון הסמנטיקה/החתימות ומכריע את הגדרות הדחיסה של השילוב
6. דחיסה יזומה מתבצעת לפני התרגום לספק כאשר היא מופעלת (`lite`,‏ Caveman,‏ RTK או שילוב שכבות)
7. מנגנון הביצוע של הספק שולח את הבקשה לשירות במעלה הזרם
8. התגובה מתורגמת חזרה לפורמט הלקוח (צ'אט), או מוחזרת כפי שהיא (הטמעות/תמונות/שמע)
9. נתוני שימוש, ניתוחי דחיסה ויומני בקשות נרשמים
10. במקרה של שגיאות, מנגנון הגיבוי מופעל בהתאם לכללי השילוב

הפניה לארכיטקטורה המלאה: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## עמידות (מורחב)

OmniRoute חושף שלושה מנגנונים בלתי תלויים לטיפול בכשלים זמניים; נקודות הקצה לניהול שלהלן מאפשרות למפעילים לקרוא ולעקוף את הגדרותיהם:

| תחום         | אחסון מצב                           | קריאה                                     | איפוס / ניקוי                                        |
| ------------ | ----------------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| מפסק ספק     | `domain_circuit_breakers` + בזיכרון | `/api/monitoring/health`                  | `POST /api/resilience/reset`                         |
| השהיית חיבור | `rateLimitedUntil` בחיבורי ספקים    | `/api/rate-limits`, `/api/providers/[id]` | (מופעל מחדש באופן עצל; ניתן לניקוי באמצעות PUT לספק) |
| נעילת מודל   | מרשם זמינות מודלים בזיכרון          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`             |

`PATCH /api/resilience` מקבל עקיפות למפסקי ספקים תחת `providerBreaker.oauth` ו-`providerBreaker.apikey`. כל פרופיל תומך ב-`degradationThreshold`, ב-`failureThreshold` וב-`resetTimeoutMs`; אותם שדות זמינים גם בלוח הבקרה ← הגדרות ← עמידות.

```bash
# ניקוי נעילה של מודל יחיד
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# מחיקת כל הנעילות
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

לעיון מלא במושגים ובערכי ברירת המחדל של המפסקים: ראו [`CLAUDE.md`](../../CLAUDE.md) ← "מצב זמן הריצה של העמידות" וכן [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### תור הגבלת קצב ורשת ביטחון להפעלה אוטומטית

- **נתיב הכתיבה הנתמך**: `POST /api/rate-limits` עם גוף `{"connectionId": "<id>", "enabled": true|false}` הוא נקודת הקצה הנתמכת לניהול הפעלה או השבתה של הגנת הגבלת קצב עבור חיבור. `PUT /api/providers/[id]` אינו משנה או הופך בכוונה את `rateLimitProtection` (#11278).
- **המשמעות של `enabled: false`**: הגדרת `enabled: false` מסירה את ההגנה המפורשת מהחיבור, אך **אינה** מוציאה חיבור פעיל המשתמש במפתח API מרשת הביטחון הגלובלית להפעלה אוטומטית (`autoEnableApiKeyProviders = true`). בתוך `reconcileEnabledConnections` ‏(`open-sse/services/rateLimitManager.ts`), הערכים `false` ו-`undefined` שקולים; חיבורים פעילים המשתמשים במפתח API וללא הגנה מפורשת נותרים מוגנים במסגרת רשת הביטחון להפעלה אוטומטית.
- **השבתה גלובלית**: כדי להפעיל חיבורים המשתמשים במפתח API ללא תורי הגבלת קצב, השביתו את רשת הביטחון באופן גלובלי באמצעות `RATE_LIMIT_AUTO_ENABLE=false` (משתנה סביבה) או `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (הגדרות ← עמידות / `PATCH /api/resilience`).

## שרת MCP

OmniRoute כולל שרת Model Context Protocol מובנה עם 3 תעבורות (stdio, SSE, streamable-http) וכלים בעלי טווחי הרשאה מוגדרים. נקודות הקצה של לוח הבקרה שלהלן קוראות נתוני מצב/ביקורת ומשמשות כמתווך עבור תעבורות ה-HTTP.

| שיטה | נתיב | תיאור |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |

| GET | `/api/mcp/stream` | פתיחת צד ה-SSE של תעבורת Streamable HTTP (הודעות ביוזמת השרת) |

**אימות:** תעבורות `sse`/`stream` מכבדות את ממשק האימות הייעודי של MCP (מפתח API מסוג Bearer עם טווח `mcp`); הנתיבים `status`/`tools`/`audit*` ניתנים לקריאה מלוח הבקרה (לא נדרש אימות נוסף מעבר ליכולת להגיע למארח לוח הבקרה).

> שתי תעבורות ה-HTTP מותנות ב-`settings.mcpEnabled` וב-`settings.mcpTransport` — אי־התאמה בתעבורה מחזירה `400`, ומצב שבו MCP מושבת מחזיר `503`.

## שרת A2A

OmniRoute חושף נקודת קצה מסוג A2A (סוכן-לסוכן) בתקן JSON-RPC 2.0, וכן מעטפת REST לצורכי בדיקה ולוח בקרה.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # אופציונלי, אלא אם OMNIROUTE_API_KEY מוגדר
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

שיטות נתמכות (כולן תלויות בהפעלת `settings.a2aEnabled`):

| שיטה             | תיאור                                                            |
| ---------------- | ---------------------------------------------------------------- |
| `message/send`   | הפעלה סינכרונית של מיומנות; מחזירה `{task, artifacts, metadata}` |
| `message/stream` | הפעלת SSE בזרימה של אותה קבוצת מיומנויות                         |
| `tasks/get`      | אחזור משימה לפי `taskId`                                         |
| `tasks/cancel`   | ביטול משימה לפי `taskId`                                         |

מיומנויות מובנות: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### כרטיס סוכן

```bash
GET /.well-known/agent.json
```

מחזיר את כרטיס סוכן ה-A2A הציבורי (שם, תיאור, יכולות, קטלוג מיומנויות, סכמת אימות) — נשמר במטמון ציבורי למשך שעה. לא נדרש אימות.

### מסייעי REST

| שיטה | נתיב                         | תיאור                                                                                                                  |
| ---- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/a2a/status`            | מצב הפעלת A2A + נתוני משימות + תקציר כרטיס הסוכן השמור במטמון                                                          |
| GET  | `/api/a2a/tasks`             | הצגת רשימת משימות — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST | `/api/a2a/tasks`             | (לא ממומש כמסייע REST — יש ליצור באמצעות JSON-RPC‏ `message/send`)                                                     |
| GET  | `/api/a2a/tasks/[id]`        | אחזור משימה אחת                                                                                                        |
| POST | `/api/a2a/tasks/[id]/cancel` | ביטול משימה                                                                                                            |

**אימות:** מסייעי REST פועלים ללא אימות ניהולי (ניתנים לקריאה מלוח הבקרה); הנתיב `/a2a` של JSON-RPC משתמש ב-Bearer‏ `OMNIROUTE_API_KEY` אם הוא מוגדר.

## אימות

ראו [אימות לניהול](../guides/MANAGEMENT-AUTH.md) למידע על ארבע משפחות
פרטי האימות (הפעלת לוח המחוונים, אסימון CLI מקומי, אסימון גישה מסוג `oma_live_…`,
מפתח API בהיקף ניהול) ועל ההבדלים ביניהן לבין מפתחות הסקה.

- נתיבי לוח המחוונים (`/dashboard/*`) משתמשים בקובץ Cookie מסוג `auth_token`
- ההתחברות משתמשת בגיבוב הסיסמה השמור; עם חזרה ל-`INITIAL_PASSWORD` במקרה הצורך
- ניתן להפעיל או להשבית את `requireLogin` דרך `/api/settings/require-login`
- נתיבי `/v1/*` דורשים באופן אופציונלי מפתח API מסוג Bearer כאשר `REQUIRE_API_KEY=true`
- „אסימון ניהול” / „מפתח API בהיקף ניהול” במסמך עזר זה פירושם אחת מהמשפחות שבמדריך זה — ולא סוג נוסף ובלתי מוגדר של סוד

> **שינוי שובר תאימות (v3.8.0)** — הנתיבים `/api/v1/agents/tasks/*` ונקודות הקצה לניהול תקופת הצינון דורשים כעת **אימות לניהול** (קובץ Cookie מסוג `auth_token` של לוח המחוונים או מפתח API בהיקף ניהול). לקוחות שקראו בעבר לנתיבים אלה ללא אימות יקבלו `401 Unauthorized`. ראו את ה-commit ‏`588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
