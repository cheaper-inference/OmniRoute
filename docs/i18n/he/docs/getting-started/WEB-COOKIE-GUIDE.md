ספקי Web Cookie מאפשרים ל-OmniRoute להשתמש בשירות AI דרך הפעלת הדפדפן הקיימת שלכם במקום באמצעות מפתח API. הם שימושיים כאשר כבר יש לכם גישה לשירות דרך אתר האינטרנט שלו וברצונכם ש-OmniRoute ישתמש באותה הפעלה מאומתת.

בניגוד לספקים המשתמשים במפתח API, ספקי Web Cookie מבצעים אימות באמצעות פרטי הזיהוי שהדפדפן שלכם שולח לאתר.

---

# לפני שמתחילים

> **חשוב:** העתיקו תמיד את פרטי האימות מתוך **בקשת רשת פעילה**, **ולא** מאחסון קובצי ה-Cookie של הדפדפן.

בעיות אימות רבות נגרמות מהעתקת קובצי Cookie מהמקום הלא נכון.

## אין להעתיק מאחסון קובצי ה-Cookie

רוב הדפדפנים מציגים את קובצי ה-Cookie המאוחסנים דרך:

```
כלי פיתוח
→ יישום (או אחסון)
→ קובצי Cookie
```

אף שקובצי Cookie אלה נראים תקינים, הם עשויים להיות:

- מיושנים
- חלקיים
- חסרים בהם קובצי Cookie שנשלחים רק בבקשות מאומתות

שימוש בערכים אלה עלול לגרום לכשלי אימות, גם אם הם נראים תקינים.

## העתיקו מבקשה פעילה

במקום זאת, השתמשו בקובצי ה-Cookie מתוך בקשה שהושלמה בהצלחה:

```
כלי פיתוח
→ רשת
→ רענון הדף
→ פתיחת בקשת צ'אט או שיחה
→ כותרות הבקשה
→ Cookie
```

כותרת הבקשה `Cookie` מכילה את פרטי האימות המדויקים שבהם הדפדפן שלכם השתמש בהצלחה.

עבור רוב ספקי Web Cookie, זהו הערך שיש להדביק ב-OmniRoute.

# הגדרה כללית

תהליך ההגדרה זהה עבור רוב ספקי Web Cookie.

1. היכנסו לאתר של הספק.
2. פתחו את כלי הפיתוח של הדפדפן.
3. פתחו את הכרטיסייה **רשת**.
4. רעננו את הדף.
5. פתחו בקשת צ'אט או שיחה מאומתת.
6. העתיקו את פרטי האימות הנדרשים.
7. פתחו את OmniRoute.
8. עברו אל **ספקים → הוספת ספק**.
9. בחרו את ספק ה-Web Cookie שלכם.
10. הדביקו את פרטי האימות.
11. לחצו על **בדיקת החיבור**.
12. שמרו את הספק.

פרטי האימות המדויקים הנדרשים תלויים בספק.

> עדכנו טבלה זו כאשר נוספים ספקי Web Cookie חדשים או כאשר ספקים קיימים משנים את דרישות האימות שלהם.

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) היא פלטפורמת צ'אט חינמית לצרכנים, שאינה דורשת הרשמה — ההפעלה נוצרת באופן אנונימי בביקור הראשון ונשמרת באמצעות שלוש עוגיות: `uid`,‏ `si_usr_id` ו-`si_ses_id`. ‏OmniRoute מעביר דרך שרת מתווך את אותה נקודת קצה `/api/dispatch` באמצעות מזהה מודל יחיד (`notrack-c`, כינוי `ntw`).

### שלבי ההתחברות

1. פתחו את [notrack.ai](https://notrack.ai) בדפדפן ואפשרו את הגדרת עוגיית ההפעלה האנונימית.
2. פתחו את **כלי הפיתוח ← רשת**, רעננו את הדף ולחצו על בקשה כלשהי אל `/api`.
3. תחת **כותרות הבקשה**, העתיקו את הערך המלא של הכותרת `Cookie`.
4. ב-OmniRoute, עברו אל **ספקים ← הוספת ספק ← NoTrack Web (חינם)**.
5. הדביקו את מחרוזת העוגיות בשדה `apiKey` ולחצו על **שמירה**.

OmniRoute מחלץ את `uid`,‏ `si_usr_id` ו-`si_ses_id` מהמחרוזת שהודבקה ובונה מחדש כותרת `Cookie` נקייה המכילה רק את הצמדים האלה — ובנוסף את `nt_session` (האסימון `ntk_…` שמוגדר עבור חשבונות מחוברים), כאשר הוא קיים. אם אחד מהשלושה חסר, המחרוזת הגולמית שהודבקה מועברת ללא שינוי, כדי שמפעילים יוכלו להתנסות במבנים חלופיים.

### מזהי מודלים

| מזהה מודל   | שם תצוגה  | הערות                                                  |
| ----------- | --------- | ------------------------------------------------------ |
| `notrack-c` | NoTrack C | ברירת המחדל — מודל הניתוב במעלה הזרם `C`.              |
| `C`         | NoTrack C | כינוי עבור `notrack-c` (קוד הניתוב הגולמי במעלה הזרם). |
| `notrack`   | NoTrack C | כינוי עבור `notrack-c`.                                |
| `ntw`       | NoTrack C | כינוי מקוצר עבור `notrack-c`.                          |

כל ארבעת מזהי המודלים ממופים לאותו מודל ניתוב במעלה הזרם (`C`).

### אפשרויות בקשה

המבצע מקבל את השדות האופציונליים הבאים בגוף הבקשה:

| שדה בגוף              | ברירת מחדל | מטרה                                                               |
| --------------------- | ---------- | ------------------------------------------------------------------ |
| `notrack_mode`        | `usual`    | מצב ניתוב (מחרוזת חופשית; השירות במעלה הזרם מקבל `usual`, …)       |
| `notrack_max_turns`   | `6`        | מספר הסבבים הפנימיים שהשירות במעלה הזרם רשאי לבצע לפני מתן תשובה.  |
| `notrack_chat_id`     | `null`     | המשך צ'אט קיים במעלה הזרם (יש להשמיט עבור צ'אט חדש).               |
| `notrack_attachments` | `[]`       | מערך שמועבר כפי שהוא ובו מתארי קבצים מצורפים של השירות במעלה הזרם. |
| `notrack_regenerate`  | `false`    | הגדירו `true` כדי לבקש תשובה שנוצרה מחדש עבור הסבב הקודם.          |

### יכולות

- השלמות צ'אט **בהזרמה וללא הזרמה**.
- **קריאה לכלים** — הגדירו `tools: [...]` בבקשה; המבצע מסריאל אותם בהתאם לחוזה מעטפת לקריאה לכלים ומפענח את תשובות המודל בחזרה אל `tool_calls` של OpenAI.
- **`response_format`** — קיימת תמיכה ב-`json_object` וב-`json_schema`. המבצע מחלץ את אובייקט ה-JSON הראשון מתשובת המודל, ממיר אותו למחרוזת ומחזיר אותו.
- **רמז הנמקה** — המבצע פולט עדכון `reasoning` כאשר השירות במעלה הזרם שולח אירוע `thinking`.

### מגבלות

- השירות במעלה הזרם אוכף מכסות שימוש אנונימיות — כאשר חורגים מהן, המבצע מחזיר שגיאת 429 עם הודעה ידידותית.
- כל מזהי המודלים מתורגמים לאותו מודל ניתוב במעלה הזרם; אין אפשרות להחליף מודל בנפרד.
- המבצע אינו קורא לנקודת הקצה `/api/chats` של השירות במעלה הזרם, ולכן היסטוריית הצ'אט וההפעלות אינן מנוהלות אוטומטית. השתמשו ב-`notrack_chat_id` כדי להמשיך צ'אט קיים במעלה הזרם.

# מה ספקי עוגיות אינטרנט יכולים ואינם יכולים לעשות

ספקי עוגיות אינטרנט משתמשים מחדש בממשק הצ'אט של אתר אינטרנט. הם **אינם** מספקים את אותן יכולות כמו ממשקי API רשמיים.

## נתמך

- אימות באמצעות הפעלת הדפדפן הקיימת שלכם
- גישה למודלים הזמינים דרך החשבון שלכם
- הזרמת תגובות צ'אט
- אין צורך במפתח API

## לא נתמך

- קריאה לפונקציות
- קריאה לכלים
- עריכה אוטומטית של קבצים
- תהליכי עבודה סוכניתיים בסביבת פיתוח משולבת
- תכונות הזמינות דרך API בלבד

זוהי התנהגות צפויה וזו **אינה** תקלה.

אם אתם זקוקים להפעלת כלים, לעריכה אוטומטית של קבצים או לתהליכי עבודה סוכניתיים אחרים, השתמשו ב**ספק עם מפתח API** במקום בספק Web Cookie.

# הסתייגות בנוגע לאימות

הצלחה ב**בדיקת החיבור** או באימות קובצי ה-cookie רק מוודאת שפרטי הגישה שסופקו נראים כאילו הם בתבנית הצפויה.

עד לפתרון Issue #7857, אימות מוצלח **אינו מבטיח** שהספק יצליח לבצע אימות.

אם האימות עדיין נכשל, ודאו שהעתקתם את פרטי הגישה מבקשת רשת פעילה ולא מאחסון קובצי ה-cookie של הדפדפן.

---

# פתרון בעיות

## האימות נכשל

ודאו שפרטי הגישה הועתקו מתוך:

```
Network
→ Request Headers
→ Cookie
```

ו**לא** מתוך:

```
Application
→ Cookies
```

---

## קובץ ה-cookie פועל בדפדפן אך לא ב-OmniRoute

ספקים מסוימים כוללים קובצי cookie שנשלחים רק במהלך בקשות מאומתות.

העתיקו מחדש את פרטי הגישה מבקשת רשת חדשה לאחר שפתחתם שיחה בהצלחה.

---

## תוקף ההפעלה פג

ספקי Web Cookie משתמשים בהפעלת הדפדפן הקיימת שלכם.

אם תוקף הפעלת הדפדפן שלכם פג או שאתם מתנתקים מהחשבון, עליכם להעתיק קבוצה חדשה של פרטי גישה. כדי להפוך את חידוש קובצי ה-cookie לאוטומטי עבור ספקי אינטרנט נתמכים, עיינו בכלי הנלווה [תוסף סנכרון הפעלת הדפדפן](../guides/SESSION-SYNC-EXTENSION.md).

---

## בדיקת החיבור מצליחה אך הבקשות נכשלות

עד לפתרון Issue #7857, מעבר מוצלח של האימות אינו מבטיח שבקשת האימות תצליח.

העתיקו מחדש את פרטי הגישה מבקשה מאומתת חדשה לפני שתמשיכו בפתרון הבעיה.

---

## ChatGPT Web נכשל עם "Unsupported ChatGPT integrity dependency"

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

פרטי הגישה תקינים — השגיאה הזו מגיעה מהגשר, לא מההפעלה. chatgpt.com מקצה את
מזהי המודולים שלו בכל פריסה, והגשר נהג לקבע את מזהה מסייע ה-Sentinel שהוא יוצר, ולכן
בנייה מחדש של chatgpt.com ששינתה את שם המסייע גרמה לכשל בכל פנייה, אף שקובץ ה-cookie נשאר תקף. אישור מחדש
של החיבור אינו יכול לתקן זאת.

גרסאות build שפותרות את המודול באמצעות סביבת זמן הריצה של הדף עצמו אינן מקבעות מזהה ואינן נתקלות בבעיה הזו. אם אתם רואים את
השגיאה, שדרגו את OmniRoute והפעילו מחדש את בדיקת החיבור.

המדריך של Claude Web מדגים את תהליך ההגדרה המלא עבור ספק Web Cookie ומשמש כמימוש הייחוס.

---

# שיטות עבודה מומלצות

- העתיקו פרטי גישה מבקשה מאומתת חדשה.
- הימנעו משימוש חוזר בקובצי cookie ישנים.
- השאירו את הפעלת הדפדפן שלכם פעילה בזמן השימוש בספקי Web Cookie.
- התייחסו לקובצי cookie שהועתקו כאל פרטי גישה רגישים.
- השתמשו בספקים עם מפתח API כאשר אתם זקוקים לקריאה לפונקציות או לתהליכי עבודה סוכניתיים.
