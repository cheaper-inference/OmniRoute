השתמשו במדריך זה כדי לבחור את לולאת הפיתוח המצומצמת והאמינה ביותר עבור בקשת משיכה. הוא אינו
מחליף את מסמכי הארכיטקטורה והאבטחה הייעודיים לתחום המקושרים להלן; הוא מחבר כל סוג שינוי נפוץ
לחוזים שלו, לבדיקות הממוקדות ולכיסוי ה-CI.

## המסלול שכל שינוי עובר

1. **בחרו את ענף הבסיס לפני העריכה.** מצאו את ענף `release/v*` הפעיל הגבוה ביותר וצרו ענף
   מהקצה שלו. הגדירו ענף זה כיעד, ולא את `main`. אם הקפאת גרסה פעילה, אל תגדירו את הענף המוקפא
   כיעד; השתמשו במחזור הפעיל הבא המתואר ב
   [מודל ההסתעפות והגרסאות](BRANCHING_MODEL.md).
2. **ציינו את החוזים.** זהו כל קטלוג, סכמה, תוצר שנוצר אוטומטית, API ציבורי או ממשק
   משתמש שהשינוי משפיע עליו. הטבלה שלהלן מציגה את ערכת הפתיחה המינימלית.
3. **כתבו או עדכנו בדיקות ממוקדות.** שינויי ייצור ב-`src/`, ב-`open-sse/`, ב-`electron/` או
   ב-`bin/` מחייבים בדיקה אוטומטית באותה בקשת משיכה. הריצו את קובצי הבדיקה המצומצמים ביותר
   שמוכיחים את ההתנהגות, ולאחר מכן את שערי הבדיקה הממוקדים המפורטים.
4. **אפשרו ל-CI להריץ את המטריצה הרחבה.** כל מקטעי בדיקות היחידה, Vitest, סף הכיסוי המצטבר
   ובניית הייצור המלאה מופעלים בבקשת המשיכה. הריצו חבילת בדיקות רחבה באופן מקומי רק כאשר כשל
   ממוקד מצביע על השפעה רחבה יותר או כאשר השינוי משתרע על פני כמה תתי-מערכות.
5. **בצעו התאמה לפני הסקירה.** משכו את ענף הבסיס הפעיל, בדקו את הקומיטים החדשים שלו ואת ההבדלים
   שלכם מולו, ולאחר מכן בצעו rebase או מיזוג של הבסיס בהתאם לתהליך העבודה של התורמים. פתרו התנגשויות
   בקבצים שנוצרו אוטומטית ובקטלוגים מתוך המקור שלהם, צרו אותם מחדש, הריצו שוב את הלולאה הממוקדת וודאו
   שבקשת המשיכה עדיין מכוונת לענף הגרסה הפעיל.
6. **תעדו ראיות.** בתבנית בקשת המשיכה, רשמו את הפקודות שהורצו, כל קובץ בדיקה שנוסף או השתנה,
   מיגרציות או דגלי תכונה, וכל אימות שעדיין ממתין להרצה ב-CI בלבד.

## מסלולים מומלצים לפי סוג שינוי

הפקודות שלהלן הן בדיקות ממוקדות מינימליות, ולא הרשאה לדלג על בדיקה שמכסה ישירות את
ההתנהגות ששיניתם.

### ספק

**חוזים**

- הגדרת הספק ב-`src/shared/constants/providers/` והשילוב שלה בתוך
  `src/shared/constants/providers.ts`.
- מודלים ויכולות ב-`open-sse/config/providerRegistry.ts` או בקובצי הרישום שחולצו ממנו.
- בחירת המבצע/המתרגם, תצורת OAuth או מפתח API, נכסי לוח המחוונים והפניית הספק שנוצרת
  אוטומטית, כאשר הדבר רלוונטי.
- פרטי גישה ציבוריים חייבים להשתמש ב-`resolvePublicCred()`; תגובות שגיאה חייבות להשתמש במסייעי
  ניקוי השגיאות המשותפים. ראו `docs/security/PUBLIC_CREDS.md` (ב-git; אינו נכלל בהידור אל `/docs`) וכן
  [ניקוי שגיאות](../security/ERROR_SANITIZATION.md).

**לולאה ממוקדת**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # כאשר הקטלוג משתנה; בצעו commit להבדל שנוצר
npm run lint
```

בדקו גם כל משפחת בקשות שהושפעה: צ'אט, Responses, תמונות, embeddings, שמע או וידאו.
התייחסו להבדלים בקטלוגים שנוצרו ובקובצי הזהב כשינויים בחוזה; אל תקבלו אותם באופן עיוור.

### ניתוב

**חוזים**

- ערכי אסטרטגיה ציבוריים ומטא-נתוני ממשק משתמש ב-`src/shared/constants/routingStrategies.ts`.
- שיגור וסידור תחת `open-sse/services/combo.ts` וב-`open-sse/services/combo/`.
- סכמות Combo, התמדה, מצב עמידות, יכולות מודלים ובקרות API/ממשק משתמש.
- [מנוע Auto-Combo](../routing/AUTO-COMBO.md) ותיעוד העמידות כאשר ההתנהגות משתנה.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # שינויי אסטרטגיה או שיגור
npm run check:known-symbols      # שינויים ברישום אסטרטגיה
npm run lint
```

השתמשו באופן מקומי בבדיקות דטרמיניסטיות עם שירותי upstream מדומים. בדיקות עשן חיות של Combo דורשות פרטי גישה והן
ידניות, ולא תחליף ל-CI.

### ממשק משתמש / חוויית משתמש

**חוזים**

- נתיב/עמוד של Next.js וגבולות רכיבים משותפים תחת `src/app/` וב-
  `src/shared/components/`.
- מבני תגובות API, מצבי טעינה/ריק/שגיאה, התנהגות מקלדת וקורא מסך,
  פריסה רספונסיבית, ערכות נושא והרחבת אזורים.
- מחרוזות המקור באנגלית של ממשק המשתמש ב-`src/i18n/messages/en.json`; אל תקודדו טקסט חדש המוצג למשתמש באופן קשיח.

**לולאה ממוקדת**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

הריצו את היישום עבור שינויי אינטראקציה או תצוגה ובדקו תצוגות צרות ורחבות כאחת. CI מריץ את
בניית הייצור ואת חבילות הבדיקות הרחבות יותר; התנהגות חזותית עדיין דורשת בדיקת רכיב ממוקדת, Playwright,
או בדיקה ידנית מתועדת המתאימה לשינוי.

### i18n

**חוזים**

- `src/i18n/messages/en.json` הוא מקור ממשק המשתמש; `config/i18n.json` הוא מקור האזורים.
- קטלוגי CLI נמצאים בנפרד תחת `bin/cli/locales/`.
- שמרו במדויק על מצייני המיקום והתגים של ICU. אל תתרגמו שמות של מוצרים/ספקים/מודלים,
  שמות פרוטוקולים וכותרות, פקודות, מזהי קוד/JSON, כתובות URL, משתני סביבה או
  מונחים מוגנים כגון `OmniRoute`, `OAuth`, `MCP` ו-`A2A`. רשימת המקור הנוכחית נמצאת ב-
  `scripts/i18n/glossary/protected-terms.json`.

**לולאה ממוקדת**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # כאשר מחרוזות/קטלוגים של CLI משתנים
npm run lint
```

זוהי הנחיה עבור המערכת הקיימת, ולא הזמנה להרחיב את כלי העבודה או את מודל המפתחות שלה.
שמרו על תיקוני i18n נקודתיים בזמן שהמערכת החלופית נמצאת בתכנון. אל תריצו פקודות תרגום
שקוראות לשירותים חיצוניים, אלא אם המשימה דורשת במפורש תרגומים שנוצרו אוטומטית
ובדקתם את ההבדל שהתקבל.

### CLI

**חוזים**

- פקודות ודגלים ציבוריים ב-`bin/cli/`, פקודות API שנוצרו, קודי יציאה, stdout/stderr וכן
  מבני פלט JSON, התנהגות תצורה/סביבה וקבצים הנכללים בחבילה.
- מחרוזות CLI המוצגות למשתמש חייבות להשתמש בשכבת ה-i18n של ה-CLI ולשמור על התאמה בין הקטלוגים `en`/`pt-BR`.
- יש לשמר את Node כסביבת הריצה הנתמכת ואת חוזה קובץ ההרצה שפורסם.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # שינויים ב-CLI שנוצר/נארז
npm run check:pack-policy     # שינויים בממשק החבילה
npm run lint
```

השתמשו בפקודה המדויקת בספריית נתונים זמנית כאשר ההתנהגות תלויה בניתוח, בקבצים או בסטטוס
היציאה. CI מבצע את הבדיקות המקיפות יותר של ארטיפקט החבילה ושל המערכת האקולוגית.

### מסד נתונים

**חוזים**

- מודולי תחום תחת `src/lib/db/`; יש לייבא מודולים ספציפיים ישירות (שכבת הייצוא מחדש הישנה `localDb.ts` הוסרה).
- מיגרציות SQL ממוספרות ואידמפוטנטיות תחת `src/lib/db/migrations/`, בטיחות טרנזקציות, התנהגות
  שדרוג, אינדקסים וכל קורא המושפע מהסכמה.
- נתיבים ומטפלים לעולם אינם מריצים SQL גולמי ישירות.

**לולאה ממוקדת**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

בעת הוספת מיגרציה, יש לבדוק גם מסד נתונים חדש וגם שדרוג מהסכמה הקודמת. בדיקות מסד נתונים
חייבות לסגור נקודות אחיזה ולקרוא ל-`resetDbInstance()` במהלך הניקוי. יש להריץ את `npm run test:bun:db` רק כאשר
נתיב מתאם Bun, הפועל במתכונת מיטבית, משתנה; Node נשאר הסמכות הקובעת.

### בנייה / פריסה

**חוזים**

- מניפסטים/קובץ נעילה בשורש ובסביבות העבודה, `scripts/build/`, הרכבה עצמאית של Next.js, תוכני החבילה
  `dist/`, מטא-נתונים תלויי פלטפורמה של Electron, תהליכי עבודה של CI וסמני פריסה.
- טווחי Node הנתמכים והשימוש המאושר ב-Bun ב-`CLAUDE.md` חייבים להישאר ללא שינוי.
- ארטיפקטי בנייה אינם נשמרים במעקב; חלות מדיניות תלויות, רישיונות, תהליכי עבודה וחבילות.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # שינויים בתלויות או בקובץ הנעילה
npm run check:pack-policy      # שינויים בממשק החבילה שפורסמה
npm run lint
```

השתמשו ב-`npm run build` באופן מקומי רק כאשר השינוי משפיע על הידור, הרכבה עצמאית, נכסים
או אריזה עבור סביבת הריצה. השתמשו ב-`npm run build:release` רק לצורך אימות גרסה/פריסה. הבנייה של CI היא
האות הסופי חוצה-הפלטפורמות; שינויים תלויי פלטפורמה ב-Electron דורשים בנייה ממוקדת תואמת
או ראיות מבדיקת עשן.

## סקריפטים למפתחים עבור מכונה משותפת

שני כלי העזר ב-`scripts/dev/` מגדירים את לולאת העבודה המקומית ב-devbox שבו פעילות הפעלות נוספות:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # קבצים מתוך merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # הקבצים האלה בדיוק
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # worktree מבודד, בטוח לעבודה במקביל
```

- `typecheck-touched.sh` מבצע בדיקת טיפוסים רק לקובצי `.ts/.tsx` שנגעו בהם, באמצעות
  `tsconfig.touched.tmp.json` זמני (`extends ./tsconfig.json`,‏ `types: ["node"]`,‏ `noEmit`,
  `incremental: false`) תחת heap של 6 GB, ולכן הוא מחליף את `tsc -p tsconfig.json` הכלל-פרויקטלי
  שגורם ל-OOM במכונה עמוסה. הוא מדפיס את השגיאות בקבצים שנגעו בהם יחד עם שורת סיכום אחת, ומסיים עם
  `1` עבור שגיאות בקבצים שנגעו בהם, `2` כאשר השגיאות היחידות הן בקבצים שיובאו או כאשר tsc קרס
  ללא אבחון (קראו את הלוג ששמו מצוין תחת `_artifacts/typecheck-touched/`), ו-`0` כאשר
  הכול תקין. קובץ ה-tsconfig הזמני תמיד נמחק; לעולם אל תבצעו לו commit.
- `new-worktree.sh` מסדר הרצות מקבילות באופן טורי באמצעות `<git-common-dir>/omniroute-new-worktree.lock`
  (ממתין עד 600 שניות כברירת מחדל, עם הודעה גלויה; כותרת הסקריפט מתעדת כיצד
  לעקוף זאת) ומבטל
  את הענף שיצר כאשר `git worktree add` נכשל לפני שה-worktree קיים, כך שניסיון חוזר
  אינו דורש `git branch -D` ידני. `node_modules` המקושר בקישור קשיח והעותק של `.husky/_` נותרים ללא שינוי.

## לולאת מועמד מקומית

בדיקות קוד המקור אינן יכולות להוכיח שהתוצר הארוז עולה: רשימות אריזה, תלויות שעברו pruning,
וקבצים בינאריים מקוריים נכשלים רק לאחר שה-tarball מותקן ומופעל. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) הוא הצד המקומי של תהליך הבנייה-פעם-אחת / אימות / קידום מתוך
RFC #8084: הוא בונה מועמד אחד, מאמת את התוצר המדויק הזה, מקדם אותו באמצעות שינוי שמות
של תיקיות ומבטל את הקידום כאשר משבצת היעד נכשלת בבדיקת התקינות שלה.

```bash
npm run dev:candidate -- run --dry-run --json  # הדפסת התוכנית ללא ביצוע שינויים
npm run dev:candidate -- run                   # בנייה + אימות + קידום, עם ביטול אוטומטי
npm run dev:candidate -- build                 # npm pack + התקנה אל _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # הפעלה בפורט פנוי, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> ← current, current ← previous
npm run dev:candidate -- rollback              # החלפת current ו-previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # שימוש חוזר ב-tarball שנבנה במקום אחר (CI)
```

- **בנייה פעם אחת.** `build` אורז את העץ הנוכחי (הוא זקוק ל-`dist/server.js`, לכן הריצו תחילה
  `npm run build:release`) או מעתיק את `--from-tarball`, ולאחר מכן מתקין את ה-tarball בתוך
  prefix מבודד של npm, משום שה-tarball אינו מכיל `node_modules`. המזהה הוא ה-sha המקוצר של `HEAD`
  (`-dirty` כאשר יש בעץ שינויים מקומיים) או `tgz-<sha256>` עבור tarball. מזהה נקי
  שכבר נבנה משמש מחדש במקום להיבנות שוב; העבירו `--force` כדי לבנות אותו מחדש.
- **אמתו את החבילה, לא את קוד המקור.** `validate` מפעיל את ה-CLI המותקן
  (`serve --port <free port>`) עם `DATA_DIR=<candidate>/data` חדש, סודות מזויפים, וכאשר
  `OMNIROUTE_API_KEY`,‏ `STORAGE_ENCRYPTION_KEY` ו-`INITIAL_PASSWORD` של המפעיל הוסרו
  מהסביבה, כדי לבדוק את מצב ה-loopback ללא מפתח של התקנה חדשה. הוא ממתין עד ש-
  `GET /api/health` יחזיר 200, דורש ש-`GET /v1/models` יחזיר 200, עוצר את קבוצת התהליכים,
  ומתעד את ההכרעה ב-`validation.json` יחד עם ה-hash של ה-tarball.
- **קדמו את אותו התוצר.** `promote` מסרב לקדם מועמד ללא אימות מוצלח עבור
  ה-hash הנוכחי של ה-tarball שלו. המשבצת הפעילה המוגדרת כברירת מחדל היא `_artifacts/candidate/current`;‏ `--target <dir>`
  בוחר תיקייה אחרת באותה מערכת קבצים, והמשבצת הקודמת שלה היא `<dir>.previous`.
  כל שינוי שם הוא אטומי, וכשל באמצע התהליך הופך את שינויי השם שכבר בוצעו.
- **ביטול.** `run` מאמת שוב את המשבצת שקודמה ומחליף בחזרה בין `current` ל-`previous` כאשר
  בדיקה זו נכשלת. מועמד שנכשל באימות הראשון לעולם אינו מקודם.

הכול נכתב תחת `_artifacts/candidate/` שמתעלמים ממנו ב-git; התקנת OmniRoute קיימת
ותיקיית הנתונים שלה לעולם אינן משתנות. ה-CLI שקודם נמצא ב-
`_artifacts/candidate/current/prefix/bin/omniroute`; הפעילו אותו עם `DATA_DIR` משלכם כאשר אתם משתמשים
בו. קודי יציאה: `0` להצלחה, `1` לאימות או קידום שנכשלו, `2` לשגיאת שימוש או לבנייה חסרה.

## לולאה מקומית לעומת CI

| להריץ מקומית עבור כל תיקון                                                  | CI מספק תמונת מצב רחבה                                             |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| בדיקות התנהגות ישירות ושערי הקטגוריות שלעיל                                 | חבילת בדיקות יחידה מלאה המחולקת למקטעים ובדיקות סדרתיות            |
| `npm run lint`                                                              | חבילות בדיקות של Vitest ומנגנוני החמרה לכיסוי/איכות                |
| בדיקת טיפוסים או בנייה רק כאשר החוזה המושפע מחייב זאת                       | בניית ייצור, אבטחה, תיעוד, תלויות ושערי מדיניות PR                 |
| אינטראקציה ידנית/בדיקות חיות רק כאשר אוטומציה אינה יכולה להוכיח את ההתנהגות | בדיקות אינטגרציה בין משימות ובדיקות פלטפורמה שהוגדרו בתהליך העבודה |

לולאה ממוקדת ירוקה היא ראיה לגבי החוזה שהשתנה, ולא הוכחה לכך שבדיקות CI שאינן קשורות
יעברו. מנגד, אין להמתין עם כל עריכה מקומית עד להשלמת מטריצת המאגר המלאה.

## רשימת תיוג להתאמה

לפני בקשת סקירה:

- ודאו שבסיס ה-PR הוא עדיין ענף `release/v*` הפעיל הגבוה ביותר.
- משכו את הבסיס הזה ובדקו את הקומיטים שנוספו מאז שיצרתם את הענף.
- בדקו את `git diff <active-base>...HEAD` לאיתור שינויים מקריים או שינויים שנוצרו אוטומטית.
- פתרו התנגשויות בקטלוג ובמסמכים שנוצרו אוטומטית באמצעות עדכון המקור ויצירה מחדש של הפלט.
- הריצו מחדש כל בדיקה/שער ממוקדים המפורטים בתיאור ה-PR לאחר ההתאמה.
- לעולם אל תחלישו טענות בדיקה ואל תסירו בדיקות נדרשות רק כדי להתאים לבסיס שהשתנה.

לכללי הקפאת גרסה ושינוי יעד, השתמשו ב-[מודל ההסתעפות והשחרור](BRANCHING_MODEL.md). לרשימת ה-CI המלאה, השתמשו ב-[מסמך העזר לשערי איכות](../architecture/QUALITY_GATES.md).
