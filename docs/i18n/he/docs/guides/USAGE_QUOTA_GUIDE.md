> **בקצרה**: OmniRoute עוקב אחר צריכת הטוקנים של כל בקשה, מחשב עלויות, אוכף מכסות לפי מפתח API ומציג נתוני ניתוח בלוח הבקרה. מדריך זה מסביר כיצד הכול פועל.

**מקורות:**

- `open-sse/services/usage.ts` (~70KB) — מעקב השימוש העיקרי
- `src/lib/usageAnalytics.ts` (~10KB) — צבירה עבור לוח הבקרה
- `src/lib/db/quotaSnapshots.ts` — נתוני מכסות היסטוריים
- `src/lib/db/usage*.ts` — מספר מודולי מסד נתונים הקשורים לשימוש

## סקירה כללית

כל בקשה שעוברת דרך OmniRoute יוצרת **רשומת שימוש** שמתעדת:

- **זהות**: איזה מפתח API, ספק, מודל ושילוב
- **טוקנים**: טוקנים של ההנחיה, טוקנים של ההשלמה, טוקנים מהמטמון וסך הכול
- **עלות**: סכום בדולרים אמריקאיים (מחושב מנתוני התמחור)
- **תזמון**: השהיה וחותמות זמן של התחלה/סיום
- **סטטוס**: הצלחה, שגיאה, הגבלת קצב וכו׳

רשומות אלה נצברות לכדי **נתוני ניתוח**, נשמרות כ**תמונות מצב של מכסות** ומשמשות לאכיפת **מגבלות תקציב לפי מפתח**.

```
בקשה ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ניתוחים    מכסה    חיוב
                 (לוח הבקרה) (אכיפה)  (ייצוא)
```

## מה מתועד

השירות `usage.ts` מתעד **אירוע שימוש** לכל בקשה:

| שדה                | סוג     | מקור                                                         |
| ------------------ | ------- | ------------------------------------------------------------ |
| `id`               | מחרוזת  | UUID שנוצר בעת התיעוד                                        |
| `apiKeyId`         | מחרוזת  | מפתח ה-API שיזם את הבקשה                                     |
| `provider`         | מחרוזת  | מזהה ספק (openai, anthropic וכו')                            |
| `model`            | מחרוזת  | מזהה מודל (gpt-5, claude-opus-4-6 וכו')                      |
| `comboId`          | מחרוזת? | מזהה שילוב אם הבקשה נותבה דרך שילוב                          |
| `promptTokens`     | מספר    | מתוך תגובת הספק במעלה הזרם                                   |
| `completionTokens` | מספר    | מתוך תגובת הספק במעלה הזרם                                   |
| `cachedTokens`     | מספר    | טוקנים שנמצאו במטמון (שמירת הנחיות במטמון של Anthropic וכו') |
| `totalTokens`      | מספר    | הנחיה + השלמה                                                |
| `costUsd`          | מספר    | מחושב מתוך נתוני התמחור                                      |
| `latencyMs`        | מספר    | משך הבקשה מקצה לקצה                                          |
| `status`           | מנייה   | `success`, `error`, `rate_limited`, `timeout`, `cancelled`   |
| `errorClass`       | מחרוזת? | מחלקת השגיאה אם הסטטוס אינו הצלחה                            |
| `timestamp`        | מחרוזת  | ISO 8601 UTC                                                 |
| `metadata`         | אובייקט | נתונים מותאמים אישית שמוזרקים על ידי תוסף                    |

### מהיכן מגיעים הטוקנים

הטוקנים מחולצים מתגובת הספק במעלה הזרם בתוך **מטפל התגובה**:

```ts
// מתוך open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

עבור ספקים שאינם מחזירים נתוני שימוש (חלק מהספקים המבוססים על עוגיות דפדפן), OmniRoute **מעריך** את מספר הטוקנים באמצעות היוריסטיקת `~4 chars per token` (ראו `open-sse/services/autoCombo/pipelineRouter.ts`).

### טוקנים במטמון

OmniRoute עוקב אחר `cached_tokens` בנפרד מ-`prompt_tokens` משום ש:

- שמירת ההנחיות במטמון של Anthropic מחויבת בתעריף מופחת עבור טוקנים במטמון (10% מהתעריף הרגיל)
- ספקים מסוימים מחזירים `cache_read_input_tokens` שיש לתמחר באופן שונה
- ניתוח הנתונים יכול להציג את **שיעור הפגיעות במטמון** = `cached_tokens / prompt_tokens`

### אבחון דרגות כתיבה למטמון

לוח תקינות מטמון ההנחיות בלוח הבקרה של ניתוח הנתונים מבחין בין כתיבות למטמון
ל-5 דקות ולשעה, כפי שדווחו על ידי הספק. השדות של Anthropic,
`usage.cache_creation.ephemeral_5m_input_tokens` ו-
`usage.cache_creation.ephemeral_1h_input_tokens`, נשמרים במהלך המרת נתוני השימוש בהזרמה
וללא הזרמה, ומאוחסנים עם סיכומי יומן הקריאות. סך הכתיבות המשולב
למטמון אינו מתווסף לקטגוריות האלה פעם נוספת.

לקריאות שיש בהן רק מונה כתיבות משולב, כולל רשומות ישנות יותר, יש דרגה
לא ידועה. בפירוט חלקי, היתרה שלא שויכה נותרת לא ידועה; מונים לא תקינים או
סותרים מסומנים במקום שיוקצה להם TTL באופן שקט. סמני
TTL בצד הבקשה אינם ראיה לדרגת חיוב.

אומדן הכתיבה המקביל ל-API בלוח מכסה רק דרגות שדווחו ותומחרו, ולא
את הבקשה כולה. עבור התמחור המקורי של מודלי Claude/Anthropic, הוא משתמש בתעריף
הקלט כפול 1.25 לכתיבות ל-5 דקות, ובתעריף הקלט כפול שניים לכתיבות לשעה. תמחור
חסר נחשב לא זמין, ולא אפס. המחירים נשמרים כאשר כל קריאה חדשה מתועדת;
רשומות היסטוריות אינן מתומחרות מחדש. לכן, לחשבונות מנוי עשוי להיות
אומדן מקביל ל-API מבלי שסכום זה יחויב כהוצאה כספית או ינוכה ממכסת
המנוי. חישובי המכסה, התקציב והעלות המדויקת לפי הספק נותרים ללא שינוי.

נתוני האבחון האלה משתמשים בסיכום תקינות המטמון הקיים, המוגבל בהיקפו, ובמדיניות השמירה
של יומן הקריאות. הם אינם משנים את ברירות המחדל של TTL לבקשות, את הניתוב או את בחירת החשבון.
תיעוד ה-TTL שביקש הלקוח לעומת ה-TTL האפקטיבי היוצא בנקודת השליחה
לספק נדחה לשלב מאוחר יותר; לוח זה מדווח על דרגות כפי שהן מופיעות באסמכתאות החיוב, ולא על ה-TTL האפקטיבי היוצא.

מימוש: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` ו-`open-sse/utils/cacheWriteUsage.ts`.

## חישוב עלויות

העלויות מחושבות מתוך **נתוני תמחור** המסונכרנים מ-LiteLLM (`src/lib/pricingSync.ts`):

| מודל              | קלט $/1M | פלט $/1M | מטמון $/1M |
| ----------------- | -------- | -------- | ---------- |
| gpt-5             | $2.50    | $10.00   | —          |
| claude-opus-4-6   | $15.00   | $75.00   | $1.50      |
| claude-sonnet-4-5 | $3.00    | $15.00   | $0.30      |
| gemini-2.5-pro    | $1.25    | $10.00   | —          |

נוסחת העלות (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **מדוע מחסירים את האסימונים שבמטמון מאסימוני הקלט?** החלק שבמטמון מתומחר בנפרד; חיוב במחיר הקלט עבור הקלט כולו יוביל לספירה עודפת.

### סנכרון תמחור

נתוני התמחור מסונכרנים אוטומטית מ-LiteLLM דרך נקודת הקצה `/api/pricing/sync` (מופעלת על ידי משימת cron המובנית, ולא על ידי משתנה סביבה חשוף למשתמש):

```bash
# הפעלה ידנית
curl -X POST http://localhost:20128/api/pricing/sync
```

עבור מודלים שאין להם נתוני תמחור, OmniRoute חוזר ל-**הערכת העלות** באמצעות תעריפים ממוצעים פנימיים (שמקורם בנתוני התמחור של LiteLLM).

## צבירה לפי טווח תאריכים

המודול `usageAnalytics.ts` מחשב וידג'טים בלוח הבקרה מתוך נתוני שימוש גולמיים. הוא תומך ב-7 טווחי זמן:

| טווח     | חלון זמן                     | מקרה שימוש                   |
| -------- | ---------------------------- | ---------------------------- |
| `1d`     | 24 השעות האחרונות            | זיהוי זינוקים שעתיים בעלויות |
| `7d`     | 7 הימים האחרונים             | סקירה שבועית                 |
| `30d`    | 30 הימים האחרונים            | חיוב חודשי                   |
| `90d`    | 90 הימים האחרונים            | ניתוח רבעוני                 |
| `ytd`    | מאז 1 בינואר של השנה הנוכחית | מעקב אחר התקציב השנתי        |
| `all`    | כל התקופה                    | סטטיסטיקות לכל התקופה        |
| `custom` | התחלה וסיום בהגדרת המשתמש    | ביקורות, שאילתות אד-הוק      |

### וידג'טים המחושבים ללוח הבקרה

לכל טווח תאריכים, שכבת הניתוח מחשבת:

| וידג'ט                 | תיאור                                              |
| ---------------------- | -------------------------------------------------- |
| **כרטיסי סיכום**       | סך הבקשות, העלות הכוללת, סך הטוקנים, שיעור ההצלחה  |
| **תרשים מגמה יומי**    | עלות + טוקנים ליום, בערימה לפי מודל                |
| **מפת חום של פעילות**  | רשת של שעה ביום × יום בשבוע, צבע = מספר הבקשות     |
| **פילוח לפי מודל**     | תרשים עוגה של העלות לפי מודל                       |
| **פילוח לפי ספק**      | תרשים עמודות של הבקשות לפי ספק                     |
| **מפתחות API מובילים** | טבלה של 10 המפתחות המובילים לפי עלות               |
| **ניתוח שגיאות**       | שיעור השגיאות לאורך זמן, קטגוריות השגיאות המובילות |

### גישה תכנותית

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // רשומות היסטוריית שימוש
  "7d",                 // טווח זמן: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // מפת חיבורי ספקים (connectionId → שם החשבון)
  {
    startDate: "2025-01-01",  // אופציונלי: עבור הטווח "custom"
    endDate: "2025-06-01",   // אופציונלי: עבור הטווח "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (סנטים)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## אכיפת מכסות

המכסה לכל מפתח API נאכפת בשני מקומות:

1. **מגבלה רכה** (`quotaWarnAt`): אזהרה בלוח הבקרה כאשר השימוש חורג מהסף
2. **מגבלה קשיחה** (`quotaLimit`): הבקשה נדחית עם HTTP 429 בעת חריגה

### תצורה

```ts
// לכל מפתח API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — הצגת אזהרה
  quotaLimit: 10_00,    // $10.00 — עצירה מוחלטת
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### תהליך האכיפה

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### תמונות מצב של מכסות

הטבלה `quotaSnapshots` שומרת **מצב היסטורי של מכסות** לצורך ניתוח מגמות:

| שדה | תיאור |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | המפתח שבמעקב |
| `window` | "day" | "week" | "month" |
| `used` | העלות שנוצלה בחלון זמן זה (בסנטים) |
| `limit` | המגבלה (בסנטים) |
| `resetAt` | מועד איפוס חלון הזמן |
| `createdAt` | מועד יצירת תמונת המצב |

תמונות מצב נוצרות **בכל בקשה** שעלותה > 0, ומשמשות כדי:

- להציג את סרגל התקדמות המכסה בלוח הבקרה
- להציג תרשימי מגמה של המכסה לאורך 30 יום
- להפעיל התראות כאשר השימוש מתקרב למגבלה

### שאילתות לניתוח נתוני שימוש

הגישה לנתוני השימוש מתבצעת דרך לוח הבקרה או כלי MCP, ולא דרך נקודות קצה ישירות לייצוא ב-REST. הנתונים האנליטיים הזמינים:

- **`/api/usage/analytics`** — מדדי שימוש מצטברים (קיבוץ לפי מודל, ספק, מפתח)
- **`/api/usage/quota`** — מצב המכסה הנוכחי לכל מפתח API
- **`/api/usage/history`** — יומני היסטוריית בקשות

## שמירת נתונים וניקוי

נפח נתוני השימוש גדל בכ-1–10KB לכל בקשה. בהיקפים גדולים, נפח זה עשוי להיות משמעותי.

### הגדרות שמירת נתונים

שמירת היסטוריית השימוש מוגדרת דרך הגדרות מסד הנתונים בממשק המשתמש או דרך `/api/settings/database`.

כברירת מחדל, היסטוריית השימוש נשמרת למשך **90 ימים**.

### ניקוי

רשומות ישנות מנוקות באמצעות `src/lib/db/cleanup.ts`:

- מופעל על ידי תהליך cron ברקע
- מוחק רשומות מתוך `usage_history` שגילן חורג מתקופת השמירה שהוגדרה בהגדרה `usageHistory`

### הערכת נפח אחסון

| קצב בקשות          | אחסון ל-30 יום | אחסון ל-90 יום |
| ------------------ | -------------- | -------------- |
| 100 בקשות ביום     | ~3MB           | ~9MB           |
| 1,000 בקשות ביום   | ~30MB          | ~90MB          |
| 10,000 בקשות ביום  | ~300MB         | ~900MB         |
| 100,000 בקשות ביום | ~3GB           | ~9GB           |

בתעבורה גבוהה מאוד, כדאי לשקול:

- קיצור תקופת השמירה דרך הגדרות מסד הנתונים
- שימוש ב-`aggregated_metrics` במקום ברשומות גולמיות (לניתוח נתונים בלבד)

## טיפים לאופטימיזציית עלויות

### 1. השתמשו במודל המתאים

```bash
# תשובה מהירה — השתמשו באפשרות זולה ומהירה
curl -d '{"model":"auto/fast","messages":[...]}'

# משימה מורכבת — השתמשו באפשרות איכותית
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. הפעילו שמירה במטמון

שמירת הנחיות במטמון של Anthropic חוסכת **90% בעלויות של הקשר חוזר**:

```ts
// השמירה במטמון אוטומטית — פשוט כללו את אותה הנחיית מערכת ארוכה
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // יישמר במטמון באופן אוטומטי
  messages: [{ role: "user", content: "..." }],
});
```

### 3. השתמשו בדחיסה

דחיסת RTK + Caveman חוסכת **15-95% בעלויות של סשנים עתירי שימוש בכלים**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. הגדירו מכסות לכל מפתח

הגדירו תמיד `quotaLimit` כדי למנוע עלויות בלתי מבוקרות:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // תקרה של $10 לחודש
```

### 5. בדקו את הצרכנים המובילים

השתמשו בלוח הבקרה או ב־**`/api/usage/analytics`** כדי לקבץ לפי מפתח API ולמיין לפי עלות:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## פתרון בעיות

### "העלות גבוהה מהצפוי"

1. בדקו את **`/api/usage/analytics?groupBy=model`** — אתרו את המודל היקר
2. בדקו את **`/api/usage/analytics?groupBy=apiKey`** — אתרו את הצרכן הכבד
3. ודאו שנתוני התמחור מעודכנים: `POST /api/pricing/sync`

### "רשומות חסרות"

- בדקו את הגדרות שימור הנתונים במסד הנתונים תחת לוח הבקרה → מסד נתונים → ניקוי — רשומות ישנות נמחקות על ידי משימת הניקוי התקופתית (`src/lib/db/cleanup.ts`)
- בדקו אם יש שגיאות ב־`src/lib/db/usage*.ts` — כשלים בכתיבה למסד הנתונים נרשמים ביומן אך אינם מוצגים
- ודאו שהבקשה אכן הגיעה אל `chatCore` — בדקו את ניתוב השילובים

### "המכסה אינה נאכפת"

- בדקו את הגדרת `quotaLimit` של המפתח
- ודאו ש־`quotaWindow` מוגדר כראוי
- חפשו רשומות `quotaSnapshots` — הן אמורות להיווצר בכל בקשה
