## Hoàn tất trò chuyện

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Header tùy chỉnh

| Header                   | Hướng    | Mô tả                                                                                                                                                                                                                   |
| ------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Yêu cầu  | Đặt thành `true` để bỏ qua bộ nhớ đệm                                                                                                                                                                                   |
| `x-omniroute-no-memory`  | Yêu cầu  | Đặt thành `true` để bỏ qua việc chèn bộ nhớ + kỹ năng cho yêu cầu này (tương tự no-cache; tránh chi phí token/chi phí cho mỗi lệnh gọi)                                                                                 |
| `X-OmniRoute-Progress`   | Yêu cầu  | Đặt thành `true` để nhận các sự kiện tiến trình                                                                                                                                                                         |
| `X-Session-Id`           | Yêu cầu  | Khóa phiên cố định cho tính liên kết phiên bên ngoài                                                                                                                                                                    |
| `x_session_id`           | Yêu cầu  | Biến thể dùng dấu gạch dưới cũng được chấp nhận (HTTP trực tiếp)                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | Yêu cầu  | Thẻ phiên/cuộc hội thoại do bên gọi cung cấp (cũng được đưa vào bộ nhớ). Khi có, giá trị được lưu nguyên văn vào `call_logs.session_tag` để phân bổ chi phí theo phiên (#8249) — không bao giờ được tự tạo khi không có |
| `Idempotency-Key`        | Yêu cầu  | Khóa khử trùng lặp (cửa sổ 5 giây)                                                                                                                                                                                      |
| `X-Request-Id`           | Yêu cầu  | Khóa khử trùng lặp thay thế                                                                                                                                                                                             |
| `x-omniroute-connection` | Yêu cầu  | Ghim một yêu cầu mô hình đơn vào một kết nối (tài khoản) của nhà cung cấp theo id — xem [Ghim tài khoản cho từng yêu cầu](#account-pinning-per-request)                                                                 |
| `X-OmniRoute-Cache`      | Phản hồi | `HIT` hoặc `MISS` (không truyền phát)                                                                                                                                                                                   |
| `X-OmniRoute-Idempotent` | Phản hồi | `true` nếu đã được khử trùng lặp                                                                                                                                                                                        |
| `X-OmniRoute-Progress`   | Phản hồi | `enabled` nếu tính năng theo dõi tiến trình đang bật                                                                                                                                                                    |
| `X-OmniRoute-Session-Id` | Phản hồi | ID phiên hiệu lực được OmniRoute sử dụng                                                                                                                                                                                |
| `X-OmniRoute-Request-Id` | Phản hồi | id tương quan của yêu cầu (khi xác định được)                                                                                                                                                                           |
| `X-OmniRoute-Version`    | Phản hồi | Phiên bản bản dựng OmniRoute (luôn có)                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | Phản hồi | Số USD tiết kiệm được nhờ bộ nhớ đệm khi có HIT (chỉ áp dụng cho lượt truy cập bộ nhớ đệm)                                                                                                                              |
| `X-OmniRoute-Decision`   | Phản hồi | Dấu vết định tuyến: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` là chiến lược tổ hợp hoặc `single` đối với yêu cầu không phải tổ hợp) — luôn có trong các phản hồi hoàn tất                           |

> Lưu ý về Nginx: nếu bạn sử dụng các header có dấu gạch dưới (ví dụ `x_session_id`), hãy bật `underscores_in_headers on;`.

#### Ghim tài khoản cho từng yêu cầu

Khi một nhà cung cấp có nhiều kết nối (tài khoản hoặc khóa), OmniRoute thường chọn một kết nối
thông qua chiến lược lựa chọn tài khoản. Thay vào đó, một yêu cầu có thể ghim một kết nối cụ thể
bằng header `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Nơi tìm id.** Mở trang nhà cung cấp trong bảng điều khiển
  (**Dashboard → Providers → <provider>**) và nhấp vào chip id `xxxxxxxx…` trên một hàng kết nối
  — thao tác này sẽ sao chép id đầy đủ của kết nối.
- **Những yêu cầu áp dụng cơ chế này.** Các yêu cầu dùng một mô hình (`provider/model`) trên
  `/v1/chat/completions`, `/v1/messages` và `/v1/responses`. Combo bỏ qua header này: thay vào đó,
  hãy ghim một tài khoản cho từng bước của combo thông qua kết nối riêng của bước đó.
- **Việc ghim là bắt buộc, không phải là ưu tiên.** Kết nối được ghim sẽ được sử dụng độc quyền.
  Lỗi xảy ra trong yêu cầu sẽ ghi nhận thời gian chờ của tài khoản nhưng **không** chuyển sang
  tài khoản khác thuộc cùng nhà cung cấp.
- **Thời gian chờ và hạn ngạch sẽ hủy ghim.** Trong khi kết nối được ghim đang trong thời gian chờ,
  đã hết hạn ngạch hoặc bị chính sách hạn ngạch chặn, các yêu cầu sau đó sẽ chuyển sang những kết nối
  khác của nhà cung cấp, hoàn toàn giống như lưu lượng không được ghim.
- **Các id không xác định hoặc đã bị vô hiệu hóa sẽ gây lỗi.** Một id không nằm trong nhóm kết nối
  đang hoạt động của nhà cung cấp (đã bị xóa, vô hiệu hóa hoặc thuộc về nhà cung cấp khác) sẽ khiến
  không còn tài khoản đủ điều kiện, vì vậy yêu cầu sẽ thất bại thay vì âm thầm được định tuyến sang nơi khác.

Claude Code gửi các header tùy chỉnh thông qua `ANTHROPIC_CUSTOM_HEADERS`. Hãy đặt biến này trong khối `env`
của `~/.claude/settings.json`, hoặc trong `.claude/settings.json` ở cấp dự án để ghim một tài khoản khác
cho từng dự án:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Nguồn: `src/sse/handlers/chat.ts` (đọc header), `src/sse/services/auth.ts` và
`src/sse/services/sessionAffinityPin.ts` (hủy ghim và kiểm tra trường hợp không có trong nhóm).

> **Các header đo lường chi phí:** các phản hồi thành công không truyền trực tuyến cũng chứa bộ dữ liệu đo lường chi phí `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, cố định 10 chữ số thập phân; `0.0000000000` đối với nội dung miễn phí/chưa được định giá), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` và `X-OmniRoute-Fallback-Attempts` (chỉ khi > 0), cùng với `X-OmniRoute-Request-Id` và `X-OmniRoute-Version`. Các header này được trả về bởi API hoàn thành trò chuyện, `/v1/responses`, `/v1/messages`, **cũng như các endpoint phương tiện** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` và `/v1/moderations` (chi phí luôn là `0`). Chi phí phương tiện được tính theo từng phương thức (mỗi hình ảnh, mỗi giây, mỗi ký tự, mỗi đơn vị tìm kiếm) khi có dữ liệu định giá; nếu không, chi phí là `0` (cho phép tiếp tục khi lỗi).

> **Ngữ nghĩa chi phí khi khớp bộ nhớ đệm:** khi HIT bộ nhớ đệm ngữ nghĩa (`X-OmniRoute-Cache-Hit: true`), không có lệnh gọi nào đến dịch vụ thượng nguồn, vì vậy `X-OmniRoute-Response-Cost` là `0.0000000000` (chi phí **gia tăng** để phục vụ kết quả khớp). Chi phí ban đầu/lẽ ra phát sinh được báo cáo riêng trong `X-OmniRoute-Cost-Saved`. Các hệ thống sử dụng dữ liệu thanh toán nên tính tổng `X-OmniRoute-Response-Cost` (kết quả khớp không phát sinh chi phí); các hệ thống phân tích bộ nhớ đệm có thể tổng hợp `X-OmniRoute-Cost-Saved`.

## Quyền thuê phiên được quản lý độc quyền

Quyền thuê phiên được quản lý độc quyền là một hợp đồng định tuyến có chủ đích tham gia và không phụ thuộc vào ứng dụng khách: một chủ sở hữu đang hoạt động nắm giữ một kết nối OmniRoute đủ điều kiện. Cơ chế này không cho thuê mô hình, không yêu cầu OAuth, không xác định một ứng dụng khách cụ thể và cũng không yêu cầu một nhà cung cấp cụ thể.

Khóa API dùng để xác thực phải có phạm vi `lease:exclusive` và danh sách `allowedConnections` tường minh, không rỗng. Ranh giới thao tác thay đổi cơ sở dữ liệu buộc cả hai trường phải đồng thời hợp lệ khi tạo khóa và khi cập nhật một phần.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Các phản hồi nhận, gia hạn và giải phóng thành công cung cấp dấu thời gian, `state` và giá trị `generation` dương chính xác, nhưng không bao giờ tiết lộ kết nối hoặc thông tin xác thực đã chọn. Thao tác gia hạn và giải phóng cung cấp thế hệ trong phần thân JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Chủ sở hữu quyền thuê đang hoạt động có thể yêu cầu rõ ràng siêu dữ liệu hiển thị an toàn về quyền riêng tư cho liên kết hiện tại của mình:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Thao tác trạng thái có chủ đích tham gia này được bảo vệ bằng chủ sở hữu bất minh, khóa API được quản lý đã xác thực và thế hệ đang hoạt động chính xác trong một giao dịch cơ sở dữ liệu duy nhất. `displayName` chỉ là tên kết nối đã cấu hình sau khi loại bỏ khoảng trắng thừa; giá trị này là `null` khi không tồn tại tên đã cấu hình an toàn. OmniRoute không bao giờ thay thế bằng email hoặc danh tính tài khoản được tạo. Giá trị nhà cung cấp là một nhãn hiển thị không nhạy cảm và không bao giờ là mã định danh nhà cung cấp tương thích được tạo. Thông tin xác thực, token, cookie, mã định danh thô của kết nối hoặc khóa API, giá trị băm của chủ sở hữu, bí mật phân rào và dữ liệu định tuyến nội bộ đều bị loại trừ.

Các truy vấn dùng sai khóa, sai chủ sở hữu, thế hệ cũ, quyền thuê bị thiếu, hết hạn, đã giải phóng hoặc bị vô hiệu hóa đều trả về cùng lỗi `409 LEASE_FENCE_STALE` mà không kèm siêu dữ liệu kết nối. Ứng dụng khách đã nhận phản hồi chờ dung lượng không có liên kết đang hoạt động để kiểm tra. Khi quá trình định tuyến chuyển đổi một quyền thuê đang hoạt động, cùng một thế hệ vẫn còn hiệu lực và trạng thái sẽ trả về liên kết mới một cách nguyên tử, không bao giờ trả về liên kết cũ. Các ứng dụng khách hiện có không bị ảnh hưởng vì phản hồi nhận, gia hạn, giải phóng và chờ vẫn giữ nguyên cấu trúc trước đây.

Hợp đồng máy chủ này không thay đổi `/status` tiêu chuẩn của OpenAI Codex. Codex tiêu chuẩn hiện báo cáo nhà cung cấp mô hình cùng trạng thái xác thực/tài khoản tích hợp sẵn, nhưng không hiển thị siêu dữ liệu tài khoản tùy chỉnh của nhà cung cấp bất kỳ; một tích hợp ứng dụng khách trong tương lai phải gọi thao tác này và quyết định cách hiển thị `connection.displayName`.

Sau đó, mỗi yêu cầu suy luận được quản lý đều cung cấp cả hai tiêu đề điều khiển:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Chủ sở hữu chính xác, thế hệ, kết nối đang hoạt động và khóa API đã xác thực được kiểm tra phân rào ngay trước mỗi lần thử gửi đến thượng nguồn được hỗ trợ. Việc phát lại chủ sở hữu và thế hệ bằng một khóa khác sẽ thất bại ngay cả khi khóa đó cho phép cùng một kết nối. Chủ sở hữu thô không được lưu trữ lâu dài, ghi nhật ký, giữ lại trong ảnh chụp nhanh của yêu cầu hoặc chuyển tiếp đến thượng nguồn.

Tranh chấp tạm thời trả về HTTP `429` kèm theo `Retry-After` và:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Phản hồi này chỉ có nghĩa là tập hợp đủ điều kiện thông thường không rỗng và mọi ứng viên còn trống đều đang được một quyền thuê đang hoạt động của chủ sở hữu khác nắm giữ. Các mô hình/nhà cung cấp không được hỗ trợ, chính sách không khớp, thời gian chờ, hạn ngạch, tình trạng hoạt động và các lỗi đủ điều kiện thông thường khác vẫn giữ nguyên phản hồi OmniRoute hiện có.

### `x-omniroute-compression`

Ghi đè kế hoạch nén theo từng yêu cầu. Có mức ưu tiên cao nhất — cao hơn cấu hình ghi đè của tổ hợp định tuyến, hồ sơ đang hoạt động, điều kiện kích hoạt tự động và cấu hình Mặc định trên bảng điều khiển. Các giá trị:

| Giá trị       | Hiệu lực                                                                                                   |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `off`         | Không nén yêu cầu này.                                                                                     |
| `default`     | Hồ sơ Mặc định lấy từ bảng điều khiển (bỏ qua hồ sơ đang hoạt động). Các công cụ nén mất dữ liệu bị tắt.   |
| `safe`        | Chỉ khử trùng lặp và thu gọn khoảng trắng.                                                                 |
| `allow-lossy` | Giữ nguyên kế hoạch của người vận hành cho yêu cầu này, bao gồm tóm tắt và viết lại phong cách.            |
| `engine:<id>` | Một công cụ duy nhất khi được bật, ví dụ: `engine:rtk`. Cho phép sử dụng công cụ đó theo từng yêu cầu.     |
| `<combo>`     | Một tổ hợp có tên, được đối sánh trước tiên theo tên (không phân biệt chữ hoa chữ thường), sau đó theo mã. |

Lưu ý:

- Các giá trị không xác định sẽ bị bỏ qua (yêu cầu không bao giờ bị từ chối); quá trình phân giải sẽ chuyển sang thứ tự ưu tiên thông thường của người vận hành.
- Nếu nhiều tổ hợp dùng chung một tên, hãy truyền **id** của tổ hợp để có kết quả đối sánh xác định.
- Không thể chọn theo tên một tổ hợp có tên là `off` hoặc `default` (các từ khóa này được diễn giải trước); hãy tham chiếu tổ hợp đó bằng mã của nó.
- Công tắc nén chính là một cổng kiểm soát bắt buộc: khi tính năng nén bị vô hiệu hóa trên toàn hệ thống, tiêu đề này không thể bật tính năng đó.

Kế hoạch được áp dụng được phản hồi lại trong tiêu đề phản hồi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

trong đó `<source>` là một trong các giá trị `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` hoặc `off`.

## Vector nhúng

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Các nhà cung cấp khả dụng: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

ID danh mục có dạng `provider/model` (ví dụ: `jina-ai/jina-embeddings-v5-omni-small`). Các ID mô hình Jina không có tiền tố nhà cung cấp xuất hiện trong registry (ví dụ: `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) cũng được phân giải. Các thao tác nhúng/xếp hạng lại/phân loại/phân đoạn của Jina trước tiên sử dụng thông tin xác thực `jina-ai` từ bảng điều khiển; `JINA_AI_API_KEY` chỉ là phương án dự phòng khi không có khóa nào trên bảng điều khiển. Thẻ `jina-reader` chỉ dành cho Reader / `r.jina.ai` (`POST /v1/web/fetch`) và không bao giờ phục vụ thao tác nhúng hoặc xếp hạng lại.

Các mô hình trong registry công bố hỗ trợ đa phương thức cũng chấp nhận tối đa 32 mục có cấu trúc trung lập với nhà cung cấp.
Các loại mục phương tiện là `text`, `image`, `audio`, `video` và `document`. `source` của phương tiện
có dạng `{"type":"url","url":"https://..."}` hoặc
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
và bí danh họ `jina-ai/jina-embeddings-v5-omni` → omni-small) cũng chấp nhận các tài liệu
EmbeddingsV5Request gốc của Jina và **chuyển tiếp nguyên vẹn** chúng đến `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Các giá trị `{ image | audio | video | pdf }` gốc có thể là URL HTTPS công khai, URI `data:` hoặc dữ liệu
base64 thô. OmniRoute không chuyển các đối tượng đó thành chuỗi hoặc tải các URL hình ảnh gốc — Jina tự truy xuất
phương tiện công khai. Các trường Jina bổ sung (`task`, `normalized`, `truncate`, `embedding_type`) được
chuyển tiếp. Các SKU Jina chỉ hỗ trợ văn bản vẫn từ chối tài liệu không phải văn bản.

Các giới hạn về bảo mật và truyền tải:

- URL phương tiện từ xa phải là HTTPS công khai. Các mục `{type,source:url}` chuẩn tắc được tải
  ở phía máy chủ (xác thực lại chuyển hướng, thời gian chờ, giới hạn kích thước, DNS công khai, ghim kết nối) và
  được nhúng nội tuyến trước khi gọi nhà cung cấp. Các mục `{image:"https://..."}` gốc của Jina được chuyển tiếp nguyên trạng
  sau cùng bước kiểm tra HTTPS công khai; Jina tải URL.
- Phương tiện base64 nội tuyến bị giới hạn ở 8 MiB dữ liệu đã giải mã cho mỗi mục và 16 MiB dữ liệu đã giải mã cho toàn bộ yêu cầu.

Chuyển đổi theo nhà cung cấp (các mục chuẩn tắc không bao giờ được chuyển tiếp nguyên trạng):

- Các mô hình đa phương thức Jina: mỗi mục cấp cao nhất trở thành một đối tượng có khóa theo phương thức
  (`text` / `image` / `audio` / `video` / `pdf`), sử dụng URI dữ liệu cho phương tiện nội tuyến; một vector cho mỗi
  mục cấp cao nhất.
- Họ Gemini Embedding 2: một mảng cấp cao nhất trở thành một yêu cầu
  `models/{model}:embedContent` gốc duy nhất với `content.parts` (`text` hoặc `inline_data`).
- llama.cpp (`llama-cpp/<model>`, bất kỳ mô hình nào được máy chủ cục bộ tải): các mục `text` chuẩn tắc
  trở thành chuỗi thuần túy, còn `image` / `audio` / `video` trở thành một đối tượng
  `{"content": [part]}` cho mỗi mục, sử dụng các phần nội dung trò chuyện của llama-server (`image_url`,
  `input_audio` với định dạng `wav` / `mp3` / `flac`, `input_video`) cùng dữ liệu nội tuyến; một vector
  cho mỗi mục cấp cao nhất. Máy chủ phải chạy với `--embedding --mmproj …`; nếu không có bộ chiếu, chính máy chủ
  sẽ từ chối phương tiện. `document` không được hỗ trợ.
- Các mô hình không xác định/động không có siêu dữ liệu phương thức rõ ràng sẽ từ chối đầu vào có cấu trúc bằng HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Các tổ hợp mô hình/phương thức không được hỗ trợ trả về HTTP 400 thay vì ép kiểu mục. Các trường mở rộng không thuộc đầu vào
trên những yêu cầu chuỗi/token cũ tiếp tục được chuyển tiếp mà không thay đổi.

```bash
# Liệt kê tất cả mô hình nhúng
GET /v1/embeddings
```

## Tạo hình ảnh

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Các nhà cung cấp khả dụng bao gồm OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (cục bộ), ComfyUI (cục bộ).

`n` trả về `n` hình ảnh trong `data[]`. Các nhà cung cấp có API thượng nguồn trả về một hình ảnh cho mỗi lần gọi
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) sẽ nhận `n` lệnh gọi thượng nguồn riêng biệt, với tối đa 4 lệnh gọi đồng thời. Một
`seed` cố định được tăng theo chỉ số lệnh gọi (`seed`, `seed + 1`, …), vì vậy các hình ảnh sẽ khác nhau nhưng vẫn
có thể tái tạo. `n` được giới hạn ở mức 10. Toàn bộ yêu cầu sẽ thất bại nếu bất kỳ lệnh gọi nào thất bại. Danh sách
các định dạng fan-out là `SINGLE_IMAGE_FANOUT_FORMATS` trong
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux sử dụng lại kết nối khóa API hiện có và chấp nhận các tiền tố `zenmux/` hoặc `zm/`:

- `zenmux/openai/gpt-image-2` sử dụng OpenAI Images API của ZenMux. Các tùy chọn bao gồm `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` và `response_format`.
- Các nhà phát hành khác, chẳng hạn như `zm/meta/muse-image-1.0`, sử dụng endpoint `:predict`
  của Vertex AI trên ZenMux. `n` ánh xạ tới `sampleCount`, `aspect_ratio` tới `aspectRatio`, và `image_size`
  (`1K`, `2K`, `4K`) tới `sampleImageSize`. Giá trị `size` theo pixel chỉ cung cấp tỷ lệ khung hình,
  không đảm bảo kích thước pixel. Các tỷ lệ, độ phân giải và số lượng được hỗ trợ khác nhau tùy theo mô hình.
- `zm/inclusionai/ming-image-0.1-design` tự chọn kích thước. Hãy bỏ qua `size`,
  `aspect_ratio` và `image_size`; các giá trị được chỉ định rõ ràng sẽ trả về HTTP 400. Có thể yêu cầu PNG, JPEG và WebP
  bằng `output_format`.

Tích hợp này hỗ trợ tạo hình ảnh từ văn bản, không hỗ trợ chỉnh sửa hình ảnh tham chiếu. Đầu ra Vertex
được chuẩn hóa thành `data[].b64_json`; `response_format: "url"` trả về một URL HTTPS thượng nguồn
hoặc một URL dữ liệu base64 khi chỉ có dữ liệu byte của hình ảnh. Đầu ra trống/bị lọc
sẽ trả về lỗi thay vì một phản hồi thành công nhưng trống. Quyền truy cập mô hình phụ thuộc vào tài khoản ZenMux.
Xem [Vertex API của ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) và
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Liệt kê tất cả các mô hình hình ảnh
GET /v1/images/generations
```

## OCR tài liệu

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` chọn nhà cung cấp OCR thông qua tiền tố `provider/model`; một ID mô hình không có tiền tố (ví dụ:
`mistral-ocr-latest`) được phân giải thành nhà cung cấp đã đăng ký tương ứng, và khi bỏ qua `model`, hệ thống sẽ mặc định dùng
Mistral (`mistral-ocr-latest`). Các nhà cung cấp đã đăng ký (`open-sse/config/ocrRegistry.ts`):

| ID nhà cung cấp               | ID mô hình           | Giá trị `model`                                              | Ghi chú                                                                                                                     |
| ----------------------------- | -------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (hoặc chỉ `mistral-ocr-latest`) | Đồng bộ — phản hồi được trả về trực tiếp từ lệnh gọi thượng nguồn duy nhất.                                                 |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                  | Thượng nguồn bất đồng bộ (`analyze` + thăm dò) — xem bên dưới.                                                              |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                      | Đồng bộ, thông qua endpoint đối tác `openapi/chat/completions` của Vertex AI — xem bên dưới để biết thông tin xác thực/URL. |

Cả ba nhà cung cấp đều phản hồi bằng cùng một nội dung có cấu trúc theo Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Luồng thăm dò Azure Document Intelligence

API `analyze` của Azure Document Intelligence hoạt động bất đồng bộ: yêu cầu ban đầu trả về một
header `Operation-Location` thay vì nội dung phản hồi, và kết quả phải được thăm dò. Trình xử lý
(`open-sse/handlers/ocr.ts`) thăm dò URL đó mỗi giây, tối đa 30 lần thử; thất bại ngay lập tức (không
tiếp tục thăm dò) khi phản hồi thăm dò không phải `ok` hoặc có trạng thái `"failed"`, và trả về `504` nếu
tác vụ vẫn đang chạy sau khi đã dùng hết số lần thử. Phản hồi Azure cuối cùng được
chuẩn hóa thành cùng cấu trúc `pages`/`markdown` mà Mistral sử dụng trước khi được trả về cho
bên gọi, vì vậy mã phía máy khách không cần xử lý riêng theo từng nhà cung cấp.

### Xác thực và phân giải endpoint cho Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` sử dụng lại cơ chế xác thực Vertex AI mà OmniRoute đã hỗ trợ cho
lưu lượng trò chuyện/hình ảnh (`open-sse/executors/vertex.ts`): khóa API của kết nối là thông tin xác thực
Service Account JSON (được trao đổi lấy mã truy cập OAuth có thời hạn ngắn thông qua luồng JWT-bearer)
hoặc một mã truy cập OAuth đã được cấp sẵn và được sử dụng nguyên trạng. URL endpoint thượng nguồn là
endpoint đối tác `openapi/chat/completions` chung của Vertex, được tạo từ dự án và
khu vực của kết nối — giá trị `providerSpecificData.project`/`providerSpecificData.region` được chỉ định rõ ràng luôn được ưu tiên;
nếu không, dự án được lấy từ `project_id` trong Service Account JSON và khu vực
mặc định là `us-central1`. Cả hai thao tác phân giải đều diễn ra trong `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) và được
`src/app/api/v1/ocr/route.ts` sử dụng trước khi chuyển tiếp tới `handleOcr`.

## Danh sách mô hình

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Trả về tất cả mô hình chat, embedding và hình ảnh + các combo theo định dạng OpenAI
```

### Giá mô hình (`pricing`)

Một mục sẽ chứa đối tượng `pricing` khi OmniRoute biết giá của mô hình. Giá này lấy từ
bảng giá được hệ thống hạch toán chi phí sử dụng: các giá trị mặc định tích hợp sẵn, giá đã đồng bộ và
các giá ghi đè được đặt thông qua `/api/pricing`. Đây là giá niêm yết, vì vậy các nhà cung cấp theo gói đăng ký cũng
hiển thị giá trên mỗi token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Trường                                                          | Đơn vị                              | Ghi chú                                                                                                                                                               |
| --------------------------------------------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD trên mỗi token, chuỗi thập phân | Tương thích với OpenRouter, không bao giờ sử dụng ký hiệu số mũ. Hai trường bộ nhớ đệm chỉ xuất hiện khi có giá bộ nhớ đệm.                                           |
| `input`, `output`, `cached`, `cache_creation`                   | USD trên mỗi 1 triệu token, số      | Các trường từ những phiên bản danh mục trước đây, được giữ lại cho các máy khách hiện có. `reasoning` và `long_context` cũng xuất hiện khi hàng giá có các trường đó. |

- **Các combo** mang giá của đích hiển thị đầu tiên. Các combo `auto/*` tích hợp sẵn chọn một
  đích tại thời điểm yêu cầu, vì vậy chúng không có `pricing`.
- **Các mô hình miễn phí** hiển thị `"0"` (và `0`) khi giá bằng không. Một mô hình không có hàng giá
  cũng hiển thị `"0"` khi danh mục đánh dấu mô hình đó là miễn phí (`free: true`) hoặc danh mục mô hình miễn phí
  tích hợp sẵn có liệt kê mô hình đó.
- **Không xác định được giá:** mục này không có khóa `pricing`.
- **Các nhà cung cấp tính phí theo tín dụng** (chẳng hạn như Kiro) tính phí theo từng yêu cầu thay vì theo từng token. Các
  mục của họ giữ lại các trường số trên mỗi 1 triệu token đã có trước đây và không chứa trường chuỗi giá trên mỗi token.
- **Các biến thể** (ID mức độ suy luận, bí danh không suy luận, bản sao khám phá và gateway)
  sao chép giá của mô hình mà chúng định tuyến đến.
- Các trường chỉ chứa mức giá cơ sở. Các bậc ngữ cảnh dài (trường số `long_context`) và
  hệ số nhân theo cấp dịch vụ (ví dụ Codex fast hoặc flex) không thay đổi `prompt` hay
  `completion`.
- Đối tượng này giống nhau đối với mọi kiểu xác thực, bao gồm cả yêu cầu theo kiểu Anthropic
  với `x-api-key` và `anthropic-version` (phản hồi vẫn là `{ "object": "list",
"data": [...] }`). Phần triển khai: `src/app/api/v1/models/catalogPricing.ts`.

### Tiền tố ID mô hình (`?prefix=`)

Hầu hết các mô hình được công bố dưới một **tiền tố nhà cung cấp**. Tiền tố bạn nhận được do
cờ tính năng `MODELS_CATALOG_PREFIX_MODE` kiểm soát và có thể được ghi đè **theo từng yêu cầu** bằng một
tham số truy vấn — hữu ích cho máy khách muốn có danh sách gọn gàng mà không thay đổi cài đặt
trên toàn máy chủ cho tất cả người dùng khác:

```bash
GET /v1/models?prefix=alias        # một ID cho mỗi mô hình — tiền tố bí danh ngắn
GET /v1/models?prefix=dual         # cả hai dạng (mặc định của máy chủ)
GET /v1/models?prefix=canonical    # chỉ tiền tố ID đầy đủ của nhà cung cấp
```

| Chế độ      | Giá trị được phát ra                                     | Ghi chú                                                                                                                                                                                                             |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **và** `claude/claude-sonnet-4-6` | **Mặc định.** Cả hai ID đều định tuyến đến cùng một mô hình; được giữ lại để các cấu hình máy khách đã mã hóa cứng một trong hai dạng vẫn tiếp tục hoạt động. Số lượng mục trong danh mục tăng gần gấp đôi.         |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Một mục cho mỗi mô hình. Các nhà cung cấp không có bí danh riêng biệt vẫn phát ra mục của họ, vì vậy không có gì bị mất.                                                                                            |
| `canonical` | `claude/claude-sonnet-4-6`                               | Một mục cho mỗi mô hình dưới tiền tố ID đầy đủ của nhà cung cấp. Các nhà cung cấp không có bí danh riêng biệt (ví dụ: `antigravity/…`, `agy/…`) cũng phát ra ID duy nhất của họ tại đây, vì vậy không có gì bị mất. |

Một bản sao ở chế độ `dual` cũng có thể được nhận biết mà không cần tham số truy vấn: nó chứa trường `parent`
trỏ đến ID chính.

Các máy khách hiển thị trình chọn mô hình nên yêu cầu `?prefix=alias` — đây là cách
[tiện ích mở rộng OmniCopilot dành cho VS Code](../guides/VSCODE-COPILOT.md) hoạt động.

### Bộ lọc khám phá (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` chấp nhận các bộ lọc khám phá tùy chọn. Nếu không sử dụng bộ lọc nào, phản hồi sẽ
không thay đổi. Chúng thu hẹp danh mục mà bên gọi đã có thể xem (quyền của khóa API được áp dụng trước),
và được thực thi trước cơ chế phân trang `limit` / `after` theo kiểu OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # mọi khả năng được liệt kê đều phải là true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` trong danh mục; các hàng không có trường này là `chat`
GET /v1/models?q=sonnet&limit=10                           # đối sánh không phân biệt chữ hoa chữ thường trên ID hoặc tên
```

| Tham số       | Giá trị                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | số nguyên không âm, được so sánh với `context_length`                                               |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 ký tự                                                                                         |

Giá trị không xác định hoặc `min_context` không phải là số nguyên không âm (ví dụ `1.5`)
sẽ trả về HTTP `400`, đồng thời thông báo sẽ liệt kê các giá trị hợp lệ. Phần triển khai:
`src/app/api/v1/models/catalogFilters.ts`.

### Danh sách rút gọn mô hình (`POST /v1/models/query`)

`POST /v1/models/query` trả về một danh sách ngắn, có tính xác định từ cùng danh mục, với cùng
cơ chế xác thực và phạm vi hiển thị theo từng khóa như `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Mọi trường đều là tùy chọn. `capabilities` và `exclude` chấp nhận một mảng hoặc một chuỗi được phân tách bằng dấu phẩy;
`max_output` được so sánh với `max_output_tokens`. Kết quả được sắp xếp theo `owned_by`, sau đó theo `id`.
`limit` mặc định là `20` và các giá trị lớn hơn `100` bị giới hạn ở `100`. JSON không hợp lệ, trường không xác định
hoặc giá trị không hợp lệ sẽ trả về HTTP `400`.

### Các mô hình trò chuyện bị ẩn riêng lẻ

Một mô hình được đánh dấu **Ẩn** trên trang nhà cung cấp của mô hình đó sẽ bị loại khỏi danh mục và bị từ chối
với HTTP `404` / `model_not_found` khi được yêu cầu rõ ràng. Quá trình kiểm tra sử dụng nhà cung cấp
và mô hình đã được phân giải, bao gồm bí danh nhà cung cấp, tiền tố nút của nhà cung cấp tương thích và
giá trị mặc định của kết nối. Một tổ hợp sẽ bỏ qua các đích bị ẩn và có thể sử dụng một mô hình cùng nhóm đang hiển thị; khi không còn
đích nào có thể thực thi, tổ hợp sẽ trả về cùng mã lỗi. Việc bỏ ẩn có hiệu lực ở yêu cầu tiếp theo.
Các thiết lập ghi đè về khả năng hiển thị chỉ dành cho hình ảnh không ẩn mô hình trò chuyện có cùng ID.

Thiết lập riêng cho từng mô hình này tách biệt với
[danh sách cho phép/từ chối hiển thị mô hình](../routing/MODEL_EXPOSURE_LIST.md), vốn lọc việc
hiển thị trong danh mục và các ứng viên định tuyến tự động nhưng vẫn giữ lại khả năng điều phối rõ ràng. Quyền mô hình
của khóa API tiếp tục được áp dụng độc lập. Chế độ tiền tố danh mục mặc định vẫn là `dual`.

### Các biến thể mô hình không suy luận

Đối với các mô hình Claude có khả năng suy luận, `/v1/models` cũng hiển thị một biến thể **không suy luận** có id được thêm tiền tố `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Việc chọn id này (ví dụ trong cấu hình Claude Code luôn đính kèm một khối `thinking`) sẽ phân giải ngược về `<provider>/<model>` thực với khả năng suy luận bị vô hiệu hóa — `thinking:{type:"disabled"}` trên đường dẫn `/v1/messages`, hoặc các trường `reasoning`/`reasoning_effort` bị loại bỏ trên đường dẫn `/v1/chat/completions`. Biến thể này chỉ được liệt kê cho các mô hình thuộc họ Claude có hỗ trợ suy luận **và** chấp nhận `disabled` (do đó, ví dụ, các mô hình chỉ hỗ trợ chế độ thích ứng và từ chối `disabled` sẽ bị loại trừ). Người vận hành có thể buộc bật hoặc tắt biến thể này theo từng mô hình thông qua `ModelSpec.noThinkingAlias`.

## Tạo âm thanh bằng ElevenLabs

Cấu hình một kết nối nhà cung cấp `elevenlabs` trong OmniRoute bằng khóa API ElevenLabs của bạn.
Ứng dụng khách xác thực bằng khóa **OmniRoute** của chúng (`Authorization: Bearer $OMNIROUTE_API_KEY`);
cổng cung cấp khóa nhà cung cấp đã lưu dưới dạng `xi-api-key`. Tuyệt đối không gửi khóa ElevenLabs
làm bearer token của cổng.

| Phương thức | Đường dẫn                   | Phản hồi                                    | Danh mục điểm cuối của khóa API |
| ----------- | --------------------------- | ------------------------------------------- | ------------------------------- |
| POST        | `/v1/sound-generation`      | Dữ liệu byte âm thanh gốc                   | `elevenlabs`                    |
| POST        | `/v1/music`                 | Dữ liệu byte âm thanh gốc                   | `music`                         |
| POST        | `/v1/music/stream`          | Dữ liệu byte âm thanh dạng luồng            | `music`                         |
| POST        | `/v1/music/detailed`        | Âm thanh multipart gốc và kế hoạch sáng tác | `music`                         |
| POST        | `/v1/music/detailed/stream` | Siêu dữ liệu SSE gốc và các khối âm thanh   | `music`                         |
| POST        | `/v1/music/plan`            | Kế hoạch sáng tác dạng JSON                 | `music`                         |

Các điểm cuối này bổ sung cho những tuyến `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` và `/v1/speech-to-text` hiện có. Các trường JSON gốc
và tham số truy vấn như `output_format` và `enable_logging` được giữ nguyên.
Phản hồi từ `/v1/music/detailed` giữ lại các ranh giới multipart; hãy phân tích chúng dưới dạng multipart.
`/v1/music/detailed/stream` trả về `text/event-stream` cùng siêu dữ liệu sáng tác và
các khối âm thanh base64 trong sự kiện SSE. Cả sáu tuyến đều hỗ trợ yêu cầu kiểm tra trước CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Một hiệu ứng âm thanh ngắn. Thời lượng: từ 0,5 đến 30 giây.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Thời lượng nhạc được biểu thị bằng mili giây: từ 3000 đến 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Sử dụng `/v1/music/stream` với cùng phần thân JSON để phân phối âm thanh tăng dần. Yêu cầu sáng tác
chỉ chấp nhận một trong hai trường `prompt` hoặc `composition_plan`; `/v1/music/plan` yêu cầu `prompt`
và có thể chấp nhận `source_composition_plan`. Các schema gốc duy trì những trường bổ sung của
nhà cung cấp để các phiên bản kế hoạch sáng tác và tùy chọn tinh chỉnh được chuyển đến ElevenLabs.

Điểm cuối hợp nhất `/v1/music/generations` cũng chấp nhận `elevenlabs/music_v1`,
`elevenlabs/music_v2` và `elevenlabs/music_v2_5`. Khi có kết nối ElevenLabs đang hoạt động,
các mô hình này sẽ xuất hiện trong danh mục nhạc. Điểm cuối này trả về
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Trường `duration` sử dụng đơn vị
giây và được ánh xạ tới `music_length_ms`; giá trị `music_length_ms` được chỉ định rõ ràng sẽ được ưu tiên.
`instrumental` được ánh xạ tới `force_instrumental`, trong đó trường gốc được ưu tiên.
Sử dụng các điểm cuối truyền phát gốc để truyền phát và điểm cuối sáng tác gốc
cho các yêu cầu chỉ được điều khiển bởi kế hoạch sáng tác.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Các giới hạn về điểm cuối, mô hình, ngân sách và kết nối được áp dụng trước khi thực hiện lệnh gọi ngược dòng. Các
tuyến gốc trả về nguyên trạng mã trạng thái và phần thân lỗi từ dịch vụ ngược dòng, bao gồm `402` cho giới hạn
gói dịch vụ và `429` cho giới hạn hạn ngạch. Các tiêu đề `character-cost`, `song-id`, `request-id` và `retry-after`
được giữ nguyên khi có. Số dư tín dụng miễn phí không đảm bảo quyền truy cập vào mọi
mô hình nhạc, định dạng đầu ra hoặc tính năng API: ElevenLabs quyết định quyền sử dụng cho từng yêu cầu.
Điểm cuối hợp nhất giữ nguyên mã trạng thái lỗi trong lớp bao lỗi đã chuẩn hóa của OmniRoute.

Hợp đồng ngược dòng: [hiệu ứng âm thanh](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[sáng tác nhạc](https://elevenlabs.io/docs/api-reference/music/compose) và
[chi tiết nhạc truyền phát](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Các nút nhà cung cấp tái xếp hạng:** `POST /v1/rerank` cũng định tuyến đến các nút nhà cung cấp tương thích với OpenAI
> (oMLX, vLLM, Infinity, TEI phía sau một gateway, …) được định địa chỉ theo dạng `<node-prefix>/<model>`. Các nút
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) luôn đủ điều kiện, cũng như các tên máy chủ mà
> người vận hành liệt kê trong `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (ví dụ: tên dịch vụ Docker/Compose như
> `http://reranker:8080/v1`; các nút này được gọi trực tiếp, không bao giờ thông qua `HTTP(S)_PROXY` hoặc
> proxy cố định của một kết nối). Các nút trên bất kỳ
> máy chủ nào khác — một máy trong mạng LAN hoặc peer Tailscale — chỉ đủ điều kiện khi người vận hành bật
> cờ tính năng `RERANK_REMOTE_PROVIDER_NODES` **và** URL cơ sở của nút vượt qua chính sách URL gửi đi của nhà cung cấp
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Bước tái xếp hạng của công cụ bộ nhớ gọi tuyến này qua
> loopback, vì vậy quy tắc tương tự chi phối `rerankProviderModel` trong phần cài đặt Bộ nhớ.
>
> **Các dạng máy chủ cục bộ:** nút được gọi tại `<base>/v1/rerank` và, khi nhận được 404, tại `<base>/rerank`
> (Infinity, TEI). Nội dung gửi lên thượng nguồn mang cả cách đặt tên của Cohere/OpenAI (`documents`,
> `return_documents`) lẫn cách đặt tên của TEI (`texts`, `return_text`), và phản hồi thượng nguồn được
> chuẩn hóa thành cấu trúc bao ngoài của Cohere: mảng thuần của TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> từ các gateway mỏng và `{data: [...]}` theo kiểu Voyage đều được trả về cho máy khách dưới dạng
> `{results: [{index, relevance_score, document?}]}`, được sắp xếp theo điểm số và giới hạn ở `top_n`.

> **Khám phá nút nhà cung cấp:** các mô hình trên một nút nhà cung cấp tương thích với OpenAI xuất hiện trong `GET /v1/models`
> dưới tiền tố của nút. Các hàng không có siêu dữ liệu endpoint (điển hình đối với danh sách `/v1/models` cục bộ)
> kế thừa `apiType` của nút, vì vậy các mô hình của một nút `embeddings` có `type: "embedding"` và các
> mô hình của một nút `rerank` có `type: "rerank"` thay vì mặc định là trò chuyện; một
> `supportedEndpoints` được chỉ định rõ ràng trên hàng đã đồng bộ hoặc được thêm thủ công vẫn được ưu tiên.

## Tìm kiếm API

sự trừu tượng của nhà cung cấp Web/search (Tavily, Brave, Exa, Serper, v.v.).

| Phương pháp | Con đường              | Sự miêu tả                                                                                      |
| ----------- | ---------------------- | ----------------------------------------------------------------------------------------------- |
| GET         | `/v1/search`           | Liệt kê các khả năng + của nhà cung cấp dịch vụ tìm kiếm được định cấu hình                     |
| POST        | `/v1/search`           | Chạy truy vấn tìm kiếm nội dung — được xác thực bởi `v1SearchSchema`, hỗ trợ caching/coalescing |
| GET         | `/v1/search/analytics` | Số liệu thống kê hit/latency/cache của mỗi nhà cung cấp                                         |

**Xác thực:** Khóa API mang (`extractApiKey` + `isValidApiKey`). Chính sách tìm kiếm được thực thi thông qua `enforceApiKeyPolicy`.

### Exa và Tavily `provider_options`

Exa và Tavily đọc các trường dành riêng cho nhà cung cấp từ một túi được đặt tên: `provider_options.exa` (hoặc `provider_options["exa-search"]`) và `provider_options.tavily` (hoặc `provider_options["tavily-search"]`). Chỉ các phím bên dưới được chuyển tiếp. Mỗi cái được kiểm tra dựa trên lược đồ Zod của chính nó trong `open-sse/handlers/search/providerOptionsPassthrough.ts` và một khóa có loại sai sẽ bị loại bỏ. Bất kỳ khóa nào khác đều bị bỏ qua, bao gồm auth, base URL, `stream` và `outputSchema`. Các phím phẳng được các nhà cung cấp khác sử dụng (`cx`, `depth`, ...) vẫn hoạt động như trước.

| nhà cung cấp | Các trường cấp cao nhất                                                                                                                                                                                                                                                                                                                                                   | Lồng nhau                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa          | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (nguyên thủy phẳng), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` được hợp nhất trên `{ text: true, highlights: true }` mặc định |
| Tavily       | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                            |

Các trường chung luôn thắng: `query`, `max_results`, `filters` (tên miền), `country` và chủ đề bắt nguồn từ `search_type`. Trên Exa, `search_type: "news"` giữ `category: "news"`. Tavily cũng chấp nhận `search_type: "finance"` (`topic: "finance"`).

Chi phí tìm kiếm Firecrawl được ghi lại cho mỗi khối bắt đầu gồm 10 kết quả được trả về, ở mức 0,002 USD (2 tín dụng) một khối và ít nhất một khối cho mỗi cuộc gọi ( [Thanh toán Firecrawl](https://docs.firecrawl.dev/billing) ): 11 kết quả có giá 0,004 USD.

`time_range` chung hiện đến tay cả hai nhà cung cấp: Exa nhận được `startPublishedDate` (ISO dấu thời gian) và Tavily nhận được `start_date` (`YYYY-MM-DD`). Ngày rõ ràng trong `provider_options` sẽ ghi đè ngày được ánh xạ.

Kết quả Exa giữ `id`, `highlight_scores`, `summary`, `subpages`, `entities` và `extras` trong `provider_raw`. Kết quả rõ ràng giữ `images` và `favicon`.

Chi phí tìm kiếm liên kết được ghi nhận ở mức 0,005 USD cho `depth` `fast` và `standard` và 0,05 USD cho `deep` ( [Giá liên kết](https://docs.linkup.so/pages/documentation/development/pricing) ), cho dù `depth` đến từ `provider_options` hay cài đặt của kết nối.

Exa `type: "lite"` (Exa 3.0) chấp nhận một nhóm trường nhỏ hơn và từ chối toàn bộ yêu cầu khi bất kỳ trường nào khác được đặt. Đối với lite, `additionalQueries`, `systemPrompt` và mọi khóa `contents` ngoại trừ `text` và `highlights` đều bị loại bỏ trước cuộc gọi. `subpages`, `subpageTarget`, `highlights.numSentences` và `highlights.highlightsPerUrl` không được dùng nữa không còn được chuyển tiếp nữa.

Kế toán chi phí là sổ đăng ký cố định `costPerQuery`, ngoại trừ Exa, tuân theo giá riêng của Exa: 0,007 USD mỗi lệnh gọi cho `auto` (và `fast` cũ) hoặc 0,004 USD cho `lite` (và `instant` cũ), bao gồm 10 kết quả; 0,001 USD cho mỗi kết quả tiếp theo; và 0,001 USD cho mỗi kết quả trả về khi `contents.summary` được đặt. Tavily được ghi ở mức 1 tín dụng ($0,008) cho `search_depth` `basic`, `fast` và `ultra-fast` và 2 tín dụng ($0,016) cho `advanced` ( [tín dụng Tavily API](https://docs.tavily.com/documentation/api-credits) ). Cuộc gọi với `auto_parameters: true` mà Tavily nâng cấp lên nâng cao vẫn được ghi ở mức 1 tín dụng.

## Web Fetch API

Trích xuất nội dung từ một URL thông qua nhà cung cấp web-fetch đã cấu hình (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, sử dụng cùng API key với Parallel Search) chỉ trả về Markdown
— mọi `format` khác đều dẫn đến lỗi `400` — và giới hạn nội dung ở 100.000 ký tự. Khi
không thể trích xuất chính trang đích, dịch vụ thượng nguồn báo lỗi đó bên trong phản hồi HTTP 200;
OmniRoute biểu thị trường hợp này bằng lỗi `422` với một thông báo cố định.

| Phương thức | Đường dẫn       | Mô tả                                                                  |
| ----------- | --------------- | ---------------------------------------------------------------------- |
| POST        | `/v1/web/fetch` | Tìm nạp/quét một URL — phần thân được xác thực bằng `v1WebFetchSchema` |

**Xác thực:** Bearer API key (`extractApiKey` + `isValidApiKey`). Chính sách được thực thi thông qua `enforceApiKeyPolicy`.

**Chuyển dự phòng có tính đến hạn ngạch (#8297):** khi không chỉ định rõ `provider`, nhóm
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) được
duyệt theo thứ tự ưu tiên
cố định (ưu tiên lấp đầy) — một nhà cung cấp đã cấu hình nhưng bị giới hạn tốc độ sẽ được bỏ qua
thay vì chấm dứt ngay yêu cầu, và lỗi thượng nguồn có thể thử lại/liên quan đến hạn ngạch
(HTTP 429 trong mọi trường hợp; 402/403 đối với các gói miễn phí có kiểu hạn ngạch của Firecrawl/Tavily/TinyFish —
không áp dụng cho Jina Reader và không bao giờ áp dụng cho yêu cầu lỗi 400 thông thường) sẽ chuyển sang
nhà cung cấp tiếp theo có thông tin xác thực và chưa được thử tại thời điểm gửi yêu cầu. Khi mọi nhà cung cấp trong
nhóm đều đã cạn kiệt, endpoint trả về một lỗi `429` duy nhất (kèm header `Retry-After`)
thay vì lỗi `400` chung chung trước đây. Khi một `provider` cụ thể được
yêu cầu, sẽ **không có** chuyển dự phòng ngầm — nhà cung cấp được chỉ định rõ nếu bị giới hạn tốc độ hoặc gặp lỗi
sẽ trả về chính lỗi của nhà cung cấp đó (`429` nếu bị giới hạn tốc độ, nếu không thì là trạng thái
thượng nguồn).

## Truyền phát WebSocket

```bash
GET /v1/ws?handshake=1
```

Xác thực quá trình bắt tay nâng cấp WebSocket và trả về các thông báo ví dụ của giao thức truyền dẫn (`request`, `cancel`). Các frame WS thực tế được xử lý bởi máy chủ WS đi kèm, bên ngoài bảng định tuyến của Next.js.

**Xác thực:** Bearer API key trong quá trình bắt tay.

### Responses API qua WebSocket (chỉ codex)

```bash
# Cùng host:port với HTTP API (mặc định là 20128); nâng cấp kết nối:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (hoặc: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Frame đầu tiên PHẢI là response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Proxy Responses-API-qua-WebSocket được kết nối **chỉ với `codex`** (backend ChatGPT).
Proxy này lắng nghe trên cùng cổng với API/dashboard tại các đường dẫn `/v1/responses`,
`/responses` và `/api/v1/responses`. Khi nhận frame `response.create` đầu tiên, proxy
xác thực + chuẩn bị thông qua cầu nối nội bộ `codex-responses-ws`, chọn một
kết nối OAuth codex và tạo đường hầm tới `wss://chatgpt.com/backend-api/codex/responses`
thông qua cơ chế truyền tải `wreq-js`. **Các model không phải codex sẽ bị từ chối** (`codex_ws_provider_required`).
Để định tuyến chia sẻ hạn ngạch, hãy sử dụng `model: "qtSd/<group>/codex/<model>"`. Được triển khai trong
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Xác thực:** Bearer API key trong quá trình bắt tay. Máy chủ HTTP đi kèm (`server-ws.mjs`)
phải là entrypoint đang hoạt động (theo mặc định là như vậy khi `app/server-ws.mjs` tồn tại).

#### ID model: sử dụng ID ChatGPT nguyên bản (không có tiền tố `codex/`)

**Codex CLI** của OpenAI xác thực tên model ở phía client khi
`supports_websockets = true` và **từ chối các ID có tiền tố nhà cung cấp** như
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Hãy gửi ID **nguyên bản** (ví dụ: `gpt-5.5`). Cầu nối của OmniRoute
chỉ dành cho codex, vì vậy nó phân giải lại một ID nguyên bản thành model codex
(`resolveCodexWsModelInfo`) trước khi tạo đường hầm tới thượng nguồn — mặc dù một ID nguyên bản
`gpt-5.5` lẽ ra sẽ được định tuyến đến nhà cung cấp khác qua HTTP.

#### Cấu hình OpenAI Codex CLI

Trỏ Codex CLI đến OmniRoute bằng cách thêm một nhà cung cấp tùy chỉnh có hỗ trợ WebSocket
vào `~/.codex/config.toml` (sử dụng một `CODEX_HOME` riêng để tránh thay đổi
cấu hình hiện có):

```toml
model = "gpt-5.5"                 # ID nguyên bản — KHÔNG PHẢI "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # không có dấu gạch chéo ở cuối; URL WS được suy ra (sử dụng https/wss trong môi trường production)
wire_api = "responses"                    # giá trị duy nhất được hỗ trợ kể từ tháng 2 năm 2026
supports_websockets = true                # bật cơ chế truyền tải Responses-qua-WS
env_key = "OMNIROUTE_API_KEY"             # chứa OmniRoute API key (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # một OmniRoute API key (bất kỳ key nào nếu REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI nâng cấp `base_url + /responses` thành WebSocket và OmniRoute tạo đường hầm cho kết nối đó
tới kết nối OAuth codex đã chọn. Đã được xác thực đầu cuối với máy chủ
cục bộ: ChatGPT trả về `codex.rate_limits` + `response.created` và truyền phát
phần hoàn thành.

## Sử dụng tự phục vụ (`/api/usage/om-usage`)

Bất kỳ khóa API nào cũng có thể đọc mức sử dụng và hạn ngạch **của chính khóa đó** — không cần xác thực quản trị. Đây là endpoint mà
client (CLI, bảng điều khiển OmniCopilot) sử dụng để hiển thị cho chủ sở hữu khóa số tiền họ đã chi tiêu.

```bash
# Dạng văn bản (giao thức lịch sử — văn bản thuần túy dành cho terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Dạng có cấu trúc — dạng mà UI sử dụng
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Khóa phải bật **`allowUsageCommand`** (mặc định là tắt — trình quản lý khóa API của dashboard
bật hoặc tắt tùy theo từng khóa). Nếu không bật, endpoint sẽ trả về `403`.

`?format=json` trả về một cấu trúc phân biệt để bên gọi không bao giờ đọc trường dữ liệu từ một
phản hồi từ chối. Khi thành công:

```jsonc
{
  "allowed": true,
  // chỉ xuất hiện khi khóa đã chọn sử dụng giới hạn mức dùng theo từng khóa (USD hằng ngày/hằng tuần):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ảnh chụp nhanh hạn ngạch của nhà cung cấp đã chọn, hoặc null khi chưa có dữ liệu nào được lưu vào bộ nhớ đệm:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // ảnh chụp nhanh của mọi kết nối để UI có thể hiển thị nhiều nhà cung cấp cạnh nhau:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Khi bị từ chối (`401` khóa không hợp lệ / `403` không được phép), cùng route đó trả về
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` có mặt nhưng trống
(khóa được phép, nhưng chưa thu thập được dữ liệu nào) là trạng thái khác với bị từ chối và chỉ dạng JSON
mới phân biệt được chúng.

**Xác thực:** khóa API Bearer của chính bên gọi, được xác thực bằng `isValidApiKey` — đây _không phải_ là
bề mặt quản trị (`/api/keys/…`), vốn vẫn được bảo vệ bởi `requireManagementAuth`.

### Phần trăm hạn ngạch thô so với phần trăm đã điều chỉnh theo ngưỡng cắt

Khi sử dụng `/api/usage/om-usage`, bên gọi nên lưu ý sự khác biệt giữa các tỷ lệ phần trăm
được trình bày trong **đầu ra văn bản thuần túy** và **đầu ra JSON** có cấu trúc:

| Khía cạnh                   | Định dạng văn bản thuần túy (`/api/usage/om-usage` / `@@om-usage`)                                       | Định dạng JSON (`?format=json`)                                                      |
| :-------------------------- | :------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------- |
| **Trường đầu ra**           | `NN% left` (ví dụ: `20% left`)                                                                           | `provider.quotas` / `providers[].quotas`                                             |
| **Phép đo**                 | **Hạn mức khả dụng đã điều chỉnh theo ngưỡng cắt**: dung lượng còn lại trên ngưỡng cắt                   | **Hạn ngạch thô từ thượng nguồn**: phép đo chưa điều chỉnh của nhà cung cấp          |
| **Điều chỉnh ngưỡng cắt**   | Được điều chỉnh theo tỷ lệ qua `effectiveRemainingPercent()` để phần dự trữ bảo vệ hiển thị là `0% left` | Không có (các giá trị ảnh chụp nhanh thô do nhà cung cấp báo cáo)                    |
| **Dữ liệu ngưỡng**          | Được tích hợp vào tỷ lệ phần trăm hiển thị                                                               | Được lưu trong `quotaWindowThresholds` theo từng kết nối (hoặc mặc định của máy chủ) |
| **Đối tượng sử dụng chính** | CLI tương tác, lời nhắc terminal, người vận hành                                                         | Tích hợp lập trình, dashboard, phân tích, trình theo dõi thanh toán                  |

#### Công thức điều chỉnh ngưỡng cắt

OmniRoute hỗ trợ ngưỡng cắt hạn ngạch chủ động để ngăn cạn kiệt tài nguyên thượng nguồn (được cấu hình qua
`quotaWindowThresholds` của kết nối, giá trị mặc định của nhà cung cấp hoặc cài đặt khả năng phục hồi toàn cục). Khi một ngưỡng cắt
(ví dụ: `cutoff = 25%`) đang hoạt động trên một cửa sổ hạn ngạch, trình kết xuất văn bản sẽ tính hạn mức còn lại như sau:

- Nếu `remaining <= cutoff`: trả về `0%`.
- Nếu `remaining > cutoff`: trả về `((remaining - cutoff) / (100 - cutoff)) * 100`.

Đầu ra văn bản đã định dạng làm tròn giá trị này đến số nguyên gần nhất (`Math.round(...)`).

#### Ví dụ minh họa

Hãy xem xét một cửa sổ nhà cung cấp có **60% mức sử dụng thô** (do đó **còn lại 40% hạn ngạch thô**) và một
ngưỡng **cắt khi hạn ngạch còn lại ở mức 25%** đã được cấu hình:

| Biểu diễn                          | Phép tính                                          | Còn lại |            Mức đã dùng suy ra             |
| :--------------------------------- | :------------------------------------------------- | :-----: | :---------------------------------------: |
| **JSON thô (`?format=json`)**      | Ảnh chụp nhanh từ thượng nguồn (`quotas[window]`)  | **40%** |                  **60%**                  |
| **Định dạng văn bản (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (nếu tính bằng `100 - remaining`) |

- **Tại sao văn bản hiển thị còn lại 20%:** Trong số 40% hạn ngạch vật lý còn lại trên tài khoản, 25% được dành riêng theo
  chính sách ngưỡng cắt. Bên gọi chỉ còn 15% trong tổng biên độ khả dụng 75% trước khi router ngừng
  định tuyến đến kết nối này. Việc điều chỉnh theo tỷ lệ đảm bảo kết nối báo hiệu cạn kiệt (`0% left`) chính xác vào thời điểm
  quá trình định tuyến dừng lại.
- **Tại sao JSON giữ nguyên các giá trị thô:** Payload JSON trả về ảnh chụp nhanh chính xác từ nhà cung cấp (`UsageSnapshot`)
  để các công cụ bên ngoài có thể truy cập dữ liệu sử dụng thực tế từ thượng nguồn và
  `quotaWindowThresholds` ở cấp kết nối mà không bị điều chỉnh làm mất dữ liệu ở phía máy chủ.

#### Hướng dẫn chuyển đổi cho bên sử dụng

Nếu một tích hợp bên ngoài (chẳng hạn như plugin trình soạn thảo hoặc phần mở rộng tác nhân) trước đây đã thu thập dữ liệu từ điểm cuối
văn bản (`NN% left`) và tính tỷ lệ phần trăm đã sử dụng là `100 - NN`, thì việc chuyển sang `?format=json` có nghĩa là:

- Việc đọc các giá trị JSON thô sẽ phản ánh **mức tiêu thụ thực tế từ nguồn thượng nguồn** (đã sử dụng 60% trong ví dụ trên).
- Nếu tích hợp muốn duy trì ngữ nghĩa về hạn mức khả dụng của điểm cuối văn bản, nó có thể đánh giá
  công thức lượng còn lại hiệu dụng ở phía máy khách bằng cách sử dụng `quotaWindowThresholds` cho các giá trị ghi đè ở cấp độ kết nối.

(bất kể độ trễ thượng nguồn ban đầu). Các máy khách nhạy cảm với độ trễ
(đo điểm chuẩn, giám sát p50/p99) nên kiểm tra tiêu đề phản hồi
`X-OmniRoute-Cache-Latency`:

| Giá trị      | Ý nghĩa                                                                                |
| ------------ | -------------------------------------------------------------------------------------- |
| `synthetic`  | Phản hồi được cung cấp từ bộ nhớ đệm; độ trễ không phải thời gian thượng nguồn thực tế |
| _(không có)_ | Phản hồi từ lệnh gọi thượng nguồn thực tế                                              |

### Bỏ qua bộ nhớ đệm theo từng khóa

Các khóa API có thể chọn không đọc bộ nhớ đệm ngữ nghĩa thông qua `cacheDefaultMode`:

| Giá trị  | Hành vi                                                         |
| -------- | --------------------------------------------------------------- |
| `legacy` | Hành vi bộ nhớ đệm thông thường (mặc định)                      |
| `bypass` | Bỏ qua hoàn toàn việc tra cứu bộ nhớ đệm; luôn gọi thượng nguồn |

Thiết lập khi tạo khóa (`POST /api/keys`) hoặc cập nhật (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Bỏ qua theo từng yêu cầu

Bất kỳ yêu cầu nào cũng có thể bỏ qua bộ nhớ đệm, bất kể cài đặt của khóa:

```
X-OmniRoute-No-Cache: true
```

Đối với các mô hình đã đồng bộ/nhập, `PUT /api/provider-models` chấp nhận `provider`, `modelId` và
`maxOutputTokenOverride`: một số nguyên dương sẽ đặt giới hạn token đầu ra thủ công, còn `null`
sẽ xóa giới hạn đó để khôi phục giá trị mặc định. `GET /api/provider-models?provider=<provider>` trả về
các giá trị này trong `modelOutputOverrides`, bao gồm cả các mô hình không có hàng mô hình tùy chỉnh. Giá trị ghi đè
sử dụng khả năng `max_output_tokens` khi chạy và vẫn được duy trì sau khi mô hình được đồng bộ lại. Trang nhà cung cấp
tương thích với OpenAI cung cấp cùng các điều khiển chỉnh sửa/xóa và đánh dấu các mô hình hỗ trợ thị giác một cách rõ ràng.

Các nút Chat Completions tùy chỉnh điều chỉnh yêu cầu từ chối suy luận rõ ràng cho phù hợp với backend thượng nguồn. Một
lần kiểm tra kết nối thành công sẽ tự động chọn các điều khiển mẫu trò chuyện cho từng ID mô hình chính xác
mà mục `/models` chứng minh có giá trị `owned_by` được nhận dạng: `vllm`, `sglang` hoặc `llamacpp`.
Các wrapper tương thích với OpenAI có tính trong suốt có thể giữ nguyên mục mô hình gốc bên trong một đối tượng
`openai` lồng nhau; quá trình phát hiện sẽ đi qua tối đa ba lớp bao như vậy. Các mô hình có thông tin quyền sở hữu bị thiếu,
không xác định hoặc xung đột sẽ giữ nguyên hành vi OpenAI thông thường. Quá trình phát hiện tái sử dụng yêu cầu danh mục hiện có,
không tạo ra token hoàn thành nào và bị vô hiệu hóa khi endpoint kết nối thay đổi.

Để cố định hành vi cho một backend không cung cấp metadata đó, hãy sử dụng API cập nhật một phần
nhà cung cấp hiện có:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Gửi phần thân đó bằng `PUT /api/providers/<connection-id>`. Trên kết nối đó, mức độ
suy luận rõ ràng là `none` được gửi dưới dạng `chat_template_kwargs.thinking=false` và
`chat_template_kwargs.enable_thinking=false`. Các giá trị mẫu gốc được chỉ định rõ ràng vẫn có thẩm quyền
trừ khi một quy tắc suy luận phía máy chủ buộc áp dụng một mức độ. Cài đặt này chỉ áp dụng khi một kết nối
tùy chỉnh tương thích với OpenAI gửi phần thân Chat Completions; các yêu cầu Responses và nhà cung cấp
thông thường vẫn giữ nguyên cấu trúc yêu cầu gốc. Đặt `reasoningControl` thành `openai` để buộc truyền trực tiếp
`reasoning_effort` thông thường của OpenAI, hoặc bỏ qua/đặt thành `null` để sử dụng tính năng phát hiện tự động.

Các yêu cầu của trình phân loại ở chế độ tự động của Claude Code mặc định tắt khả năng suy nghĩ gốc khi chúng
không chứa điều khiển suy luận rõ ràng. Quá trình phát hiện sử dụng dấu hiệu hệ thống của trình phân loại trong các yêu cầu
định dạng Claude, không dùng tên mô hình hoặc giới hạn hoàn thành. Các điều khiển phần thân rõ ràng, header mức độ/suy nghĩ
được hỗ trợ, quy tắc định tuyến và mức độ của mô hình đã phân giải vẫn giữ nguyên thứ tự ưu tiên hiện có. Cả hai giai đoạn
phân loại đều giữ lại prompt, giới hạn hoàn thành, chuỗi dừng và phán quyết quyền thực tế từ thượng nguồn;
giai đoạn thứ hai vẫn có thể tạo phần suy luận hiển thị được yêu cầu dưới dạng văn bản thông thường.

### Phiên bản và Kênh phát hành

```bash
GET /api/system/version
```

Tuyến quản lý chỉ dành cho loopback (xác thực quản trị viên). Trả về phiên bản đang chạy, phiên bản
được phát hành mới nhất và trạng thái tự động cập nhật. `releaseChannel` và `channels` là các trường
được bổ sung (nhánh 3.8.54); `channel` giữ nguyên ý nghĩa — chế độ triển khai mà trình cập nhật của bảng điều khiển
sử dụng (`npm`, `source` hoặc `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — kênh npm của bản dựng đang chạy: `nightly` cho các phiên bản `-nightly.*`,
  `next` cho các bản phát hành trước khác (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` cho phiên bản ổn định thuộc
  phiên bản chính cũ hơn `channels.latest`, nếu không thì là `latest`. Áp dụng cùng các quy tắc như
  `scripts/release/dist-tag.mjs`, tập lệnh chọn npm dist-tag tại thời điểm phát hành.
- `channels` — phiên bản mới nhất đã phát hành của mỗi dist-tag, lấy từ `npm view omniroute dist-tags` (với phương án
  dự phòng qua HTTP của registry), được lưu vào bộ nhớ đệm với TTL 10 phút giống như `latest`. `latest` luôn hiện diện
  (dự phòng về trường `latest`, sau đó là `"unavailable"`); `next`, `nightly` và `lts` chỉ xuất hiện
  khi dist-tag tương ứng tồn tại. Một yêu cầu `Cache-Control: no-cache` sẽ làm mới cả hai lượt tra cứu.

Mô hình kênh (`latest` = v3 cho đến khi 4.0 GA, `next` = rc, `nightly` = các bản dựng `develop`,
`lts` = các bản vá v3 sau 4.0 GA) được mô tả trong `docs/ops/RELEASE_STRATEGY.md`.

Sử dụng các bí danh này khi một tích hợp không thể chèn header `Authorization` và cần nhúng khóa API vào URL cơ sở.

```bash
# Bí danh danh mục theo kiểu OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Bí danh trò chuyện theo kiểu OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Bí danh theo kiểu Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Ví dụ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Lưu ý:

- Các bí danh có token tái sử dụng cùng các trình xử lý như `/v1/*` và `/api/tags`; cấu trúc phản hồi vẫn giữ nguyên.
- Ưu tiên sử dụng `Authorization: Bearer ...` bất cứ khi nào máy khách hỗ trợ header tùy chỉnh.
- Token dựa trên URL có thể xuất hiện trong nhật ký reverse proxy, lịch sử trình duyệt và dữ liệu đo từ xa bên ngoài OmniRoute. Hãy xem chúng là một tùy chọn tương thích, không phải chế độ xác thực mặc định.

## Giới hạn Token

Ngân sách **token** cho từng khóa API (khác với Ngân sách dựa trên USD ở trên). Được thực thi trực tiếp trên luồng xử lý yêu cầu: khi mức sử dụng trong cửa sổ hiện tại của một khóa đạt đến giới hạn, các yêu cầu sẽ bị từ chối với `429 Too Many Requests`. Giới hạn có thể được áp dụng cho một `model` cụ thể, một `provider`, hoặc áp dụng `global` trên toàn bộ khóa; khi nhiều giới hạn khớp với một yêu cầu, giới hạn nghiêm ngặt nhất sẽ được áp dụng.

```bash
# Liệt kê các giới hạn token của một khóa (bao gồm mức sử dụng hiện tại trong cửa sổ)
GET /api/usage/token-limits?apiKeyId=key-123

# Tạo hoặc cập nhật giới hạn token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Xóa giới hạn token theo id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Ghi chú về schema** (`setTokenLimitSchema`): `apiKeyId` và `scopeType` (`model` | `provider` | `global`) là bắt buộc. `scopeValue` là bắt buộc trừ khi `scopeType` là `global` (ví dụ: id mô hình cho phạm vi `model`, id nhà cung cấp cho phạm vi `provider`). `tokenLimit` phải là một số nguyên dương (được ép kiểu từ chuỗi). Tùy chọn: `id` (bỏ qua để tạo mới, cung cấp để cập nhật), `resetInterval` (`daily` | `weekly` | `monthly`, mặc định là `monthly`), `resetTime` (`HH:MM`), `enabled` (mặc định là `true`). Phản hồi `GET` bổ sung cho mỗi giới hạn các trường `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` và `nextResetAt`. Đây là endpoint thuộc nhóm quản lý (xác thực được thực thi tập trung bởi quy trình authz).

## Xử lý Yêu cầu

1. Máy khách gửi yêu cầu đến `/v1/*`
2. Trình xử lý route gọi `handleChat`, `handleEmbedding`, `handleAudioTranscription` hoặc `handleImageGeneration`
3. Mô hình được phân giải (nhà cung cấp/mô hình trực tiếp hoặc bí danh/combo)
4. Thông tin xác thực được chọn từ DB cục bộ, có lọc theo tính khả dụng của tài khoản
5. Đối với chat: `handleChatCore` kiểm tra bộ nhớ đệm ngữ nghĩa/chữ ký và phân giải các thiết lập nén của combo
6. Quá trình nén chủ động chạy trước bước chuyển đổi cho nhà cung cấp khi được bật (`lite`, Caveman, RTK hoặc kết hợp nhiều phương thức)
7. Bộ thực thi của nhà cung cấp gửi yêu cầu ngược dòng
8. Phản hồi được chuyển đổi trở lại định dạng của máy khách (chat) hoặc được trả về nguyên trạng (embeddings/hình ảnh/âm thanh)
9. Dữ liệu sử dụng, phân tích nén và nhật ký yêu cầu được ghi lại
10. Cơ chế dự phòng được áp dụng khi xảy ra lỗi theo các quy tắc của combo

Tài liệu tham khảo kiến trúc đầy đủ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Khả năng phục hồi (mở rộng)

OmniRoute cung cấp ba cơ chế xử lý lỗi tạm thời độc lập; các endpoint quản lý bên dưới cho phép người vận hành đọc và ghi đè chúng:

| Phạm vi                   | Nơi lưu trữ trạng thái                           | Đọc                                       | Đặt lại / xóa                                     |
| ------------------------- | ------------------------------------------------ | ----------------------------------------- | ------------------------------------------------- |
| Bộ ngắt mạch nhà cung cấp | `domain_circuit_breakers` + trong bộ nhớ         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                      |
| Thời gian chờ kết nối     | `rateLimitedUntil` trên các kết nối nhà cung cấp | `/api/rate-limits`, `/api/providers/[id]` | (được bật lại trì hoãn; xóa qua PUT nhà cung cấp) |
| Khóa mô hình              | Registry tính khả dụng của mô hình trong bộ nhớ  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`          |

`PATCH /api/resilience` chấp nhận các giá trị ghi đè cho bộ ngắt mạch nhà cung cấp trong `providerBreaker.oauth` và `providerBreaker.apikey`. Mỗi hồ sơ hỗ trợ `degradationThreshold`, `failureThreshold` và `resetTimeoutMs`; các trường tương tự cũng được hiển thị trong Bảng điều khiển → Cài đặt → Khả năng phục hồi.

```bash
# Xóa trạng thái khóa của một mô hình
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Xóa mọi trạng thái khóa
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Để xem tài liệu tham khảo đầy đủ về khái niệm và các giá trị mặc định của bộ ngắt mạch, hãy xem [`CLAUDE.md`](../../CLAUDE.md) → "Trạng thái thời gian chạy của khả năng phục hồi" và [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Hàng đợi giới hạn tốc độ & Cơ chế bảo vệ tự động bật

- **Đường dẫn ghi được hỗ trợ**: `POST /api/rate-limits` với phần thân `{"connectionId": "<id>", "enabled": true|false}` là endpoint quản lý được hỗ trợ để bật/tắt cơ chế bảo vệ giới hạn tốc độ cho một kết nối. `PUT /api/providers/[id]` được thiết kế để không sửa đổi hoặc đảo trạng thái `rateLimitProtection` (#11278).
- **Ngữ nghĩa của `enabled: false`**: Việc đặt `enabled: false` sẽ loại bỏ cơ chế bảo vệ tường minh cho kết nối, nhưng **không** loại trừ một kết nối khóa API đang hoạt động khỏi cơ chế bảo vệ tự động bật toàn cục (`autoEnableApiKeyProviders = true`). Trong `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` và `undefined` là tương đương; các kết nối khóa API đang hoạt động không có cơ chế bảo vệ tường minh vẫn được bảo vệ theo cơ chế bảo vệ tự động bật.
- **Tắt toàn cục**: Để chạy các kết nối khóa API mà không sử dụng hàng đợi giới hạn tốc độ, hãy tắt cơ chế bảo vệ trên toàn cục qua `RATE_LIMIT_AUTO_ENABLE=false` (biến môi trường) hoặc `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Cài đặt → Khả năng phục hồi / `PATCH /api/resilience`).

## Máy chủ MCP

| Phương thức | Đường dẫn | Mô tả |

| GET | `/api/mcp/audit` | Truy vấn nhật ký kiểm tra — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Thống kê kiểm tra tổng hợp (tổng số, tỷ lệ thành công, thời lượng trung bình, các công cụ hàng đầu) |

**Xác thực:** các phương thức truyền tải `sse`/`stream` tuân theo cơ chế xác thực dành riêng cho MCP (khóa API Bearer với phạm vi `mcp`); các route `status`/`tools`/`audit*` có thể được đọc từ dashboard (không yêu cầu xác thực bổ sung ngoài quyền truy cập máy chủ dashboard).

> Cả hai phương thức truyền tải HTTP đều được kiểm soát bởi `settings.mcpEnabled` và `settings.mcpTransport` — phương thức truyền tải không khớp sẽ trả về `400`, trạng thái MCP bị vô hiệu hóa sẽ trả về `503`.

## Máy chủ A2A

OmniRoute cung cấp một điểm cuối A2A (Agent-to-Agent) JSON-RPC 2.0 cùng với một lớp bọc REST phục vụ việc kiểm tra/sử dụng bảng điều khiển.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # tùy chọn trừ khi OMNIROUTE_API_KEY được thiết lập
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Các phương thức được hỗ trợ (tất cả đều phụ thuộc vào `settings.a2aEnabled`):

| Phương thức      | Mô tả                                                          |
| ---------------- | -------------------------------------------------------------- |
| `message/send`   | Thực thi kỹ năng đồng bộ; trả về `{task, artifacts, metadata}` |
| `message/stream` | Thực thi SSE dạng luồng cho cùng một tập hợp kỹ năng           |
| `tasks/get`      | Truy xuất một tác vụ theo `taskId`                             |
| `tasks/cancel`   | Hủy một tác vụ theo `taskId`                                   |

Các kỹ năng tích hợp sẵn: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Thẻ tác nhân

```bash
GET /.well-known/agent.json
```

Trả về thẻ tác nhân A2A công khai (tên, mô tả, các khả năng, danh mục kỹ năng, cơ chế xác thực) — được lưu vào bộ nhớ đệm công khai trong 1 giờ. Không yêu cầu xác thực.

### Các trình trợ giúp REST

| Phương thức | Đường dẫn                    | Mô tả                                                                                                               |
| ----------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET         | `/api/a2a/status`            | Trạng thái bật A2A + số liệu thống kê tác vụ + bản tóm tắt thẻ tác nhân đã lưu vào bộ nhớ đệm                       |
| GET         | `/api/a2a/tasks`             | Liệt kê tác vụ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST        | `/api/a2a/tasks`             | (Chưa được triển khai dưới dạng trình trợ giúp REST — tạo qua JSON-RPC `message/send`)                              |
| GET         | `/api/a2a/tasks/[id]`        | Truy xuất một tác vụ                                                                                                |
| POST        | `/api/a2a/tasks/[id]/cancel` | Hủy một tác vụ                                                                                                      |

**Xác thực:** các trình trợ giúp REST chạy mà không cần xác thực quản lý (bảng điều khiển có thể đọc); tuyến JSON-RPC `/a2a` sử dụng Bearer `OMNIROUTE_API_KEY` nếu được cấu hình.

## Định tuyến bóng

## Cơ chế bảo vệ

Kiểm tra các cơ chế bảo vệ khi chạy (phát hiện PII, phát hiện chèn prompt, kết nối thị giác). Các cơ chế bảo vệ chạy trên mọi yêu cầu; có thể chọn không áp dụng cho từng lệnh gọi thông qua header yêu cầu `x-omniroute-disabled-guardrails` — không có giao diện bật/tắt được lưu cố định.

| Phương thức | Đường dẫn              | Mô tả                                                                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET         | `/api/guardrails`      | Liệt kê các cơ chế bảo vệ đã đăng ký và trạng thái của chúng (tên / trạng thái bật / mức ưu tiên)                  |
| POST        | `/api/guardrails/test` | Chạy thử quy trình tiền xử lý lệnh gọi trên dữ liệu đầu vào mẫu — nội dung yêu cầu: `{input, disabledGuardrails?}` |

## Xác thực

Xem [Xác thực quản lý](../guides/MANAGEMENT-AUTH.md) để biết bốn nhóm
thông tin xác thực (phiên bảng điều khiển, token CLI cục bộ, Access
Token `oma_live_…`, khóa API có phạm vi quản lý) và điểm khác biệt của chúng so với khóa suy luận.

- Các tuyến bảng điều khiển (`/dashboard/*`) sử dụng cookie `auth_token`
- Quá trình đăng nhập sử dụng mã băm mật khẩu đã lưu; dự phòng bằng `INITIAL_PASSWORD`
- Có thể bật/tắt `requireLogin` qua `/api/settings/require-login`
- Các tuyến `/v1/*` có thể yêu cầu khóa API Bearer khi `REQUIRE_API_KEY=true`
- Trong tài liệu tham khảo này, "token quản lý" / "khóa API có phạm vi quản lý" có nghĩa là một trong các nhóm được nêu trong hướng dẫn đó — không phải một loại bí mật bổ sung chưa được định nghĩa

> **Thay đổi không tương thích (v3.8.0)** — `/api/v1/agents/tasks/*` và các điểm cuối quản lý thời gian chờ hiện yêu cầu **xác thực quản lý** (cookie `auth_token` của bảng điều khiển hoặc khóa API có phạm vi quản lý). Các máy khách trước đây gọi những tuyến này mà không xác thực sẽ nhận được `401 Unauthorized`. Xem commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
