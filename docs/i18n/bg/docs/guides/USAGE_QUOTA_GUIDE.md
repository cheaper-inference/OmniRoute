> **Накратко**: OmniRoute проследява използването на токени за всяка заявка, изчислява разходите, налага квота за всеки API ключ и показва аналитични данни в таблото за управление. Това ръководство обяснява как работи всичко.

**Източници:**

- `open-sse/services/usage.ts` (~70KB) — основно проследяване на използването
- `src/lib/usageAnalytics.ts` (~10KB) — агрегиране за таблото за управление
- `src/lib/db/quotaSnapshots.ts` — исторически данни за квотите
- `src/lib/db/usage*.ts` — множество модули на базата данни, свързани с използването

## Общ преглед

Всяка заявка, която преминава през OmniRoute, генерира **запис за използването**, който съдържа:

- **Идентичност**: кой API ключ, доставчик, модел и комбинация са използвани
- **Токени**: токени на подканата, токени на отговора, кеширани токени, общ брой
- **Разходи**: сума в USD (изчислена от ценовите данни)
- **Времеви показатели**: латентност, времеви маркери за начало/край
- **Състояние**: успех, грешка, ограничена честота и др.

```
Заявка ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    анализи    квота   таксуване
                    (табло)  (налагане) (експорт)
```

## Какво се записва

Услугата `usage.ts` регистрира **събитие за потребление** за всяка заявка:

| Поле               | Тип     | Източник                                                                     |
| ------------------ | ------- | ---------------------------------------------------------------------------- |
| `id`               | string  | UUID, генериран при запис                                                    |
| `apiKeyId`         | string  | API ключът, с който е инициирана заявката                                    |
| `provider`         | string  | Идентификатор на доставчика (openai, anthropic и др.)                        |
| `model`            | string  | Идентификатор на модела (gpt-5, claude-opus-4-6 и др.)                       |
| `comboId`          | string? | Идентификатор на комбинацията, ако заявката е маршрутизирана през комбинация |
| `promptTokens`     | number  | От отговора на доставчика                                                    |
| `completionTokens` | number  | От отговора на доставчика                                                    |
| `cachedTokens`     | number  | Токени, намерени в кеша (кеширане на подкани при Anthropic и др.)            |
| `totalTokens`      | number  | Подкана + отговор                                                            |
| `costUsd`          | number  | Изчислена от данните за ценообразуване                                       |
| `latencyMs`        | number  | Продължителност на заявката от край до край                                  |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                   |
| `errorClass`       | string? | Клас на грешката, ако състоянието не е success                               |
| `timestamp`        | string  | ISO 8601 UTC                                                                 |
| `metadata`         | object  | Персонализирани данни, добавени от плъгин                                    |

### Откъде идват токените

Токените се извличат от отговора на доставчика в **обработчика на отговори**:

```ts
// От open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

За доставчици, които не връщат данни за потреблението (някои доставчици, използващи уеб бисквитки), OmniRoute **оценява** броя на токените чрез евристиката `~4 chars per token` (вижте `open-sse/services/autoCombo/pipelineRouter.ts`).

### Кеширани токени

OmniRoute проследява `cached_tokens` отделно от `prompt_tokens`, защото:

- Кеширането на подкани при Anthropic таксува кешираните токени по намалена тарифа (10% от стандартната)
- Някои доставчици връщат `cache_read_input_tokens`, за които трябва да се прилага различна цена
- Анализите могат да показват **процента на попаденията в кеша** = `cached_tokens / prompt_tokens`

### Диагностика на тарифните нива за запис в кеша

Панелът за състоянието на кеша за подкани в таблото за анализи разграничава отчетените от доставчика
записи в кеша с продължителност 5 минути и 1 час. Полетата на Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` и
`usage.cache_creation.ephemeral_1h_input_tokens` се запазват при преобразуването на данните за потреблението както при поточни, така и при
непоточни отговори и се съхраняват с обобщенията на журналите на извикванията. Общият
брой записи в кеша не се добавя повторно към тези категории.

Извикванията само с общ брояч за записите, включително по-старите записи, имат неизвестно
тарифно ниво. При частична разбивка неразпределеният остатък остава неизвестен; невалидните или
противоречивите броячи се маркират, вместо мълчаливо да им се присвоява TTL. Маркерите за TTL в заявката
не са доказателство за таксувано тарифно ниво.

Оценката на разходите за запис в панела, еквивалентна на API таксуването, обхваща само отчетените тарифни нива с известна цена, а не
цялата заявка. При собственото ценообразуване на моделите Claude/Anthropic тя използва 1.25 пъти
тарифата за входни токени за записи с продължителност 5 минути и два пъти тарифата за входни токени за записи с продължителност 1 час. Липсващата
цена се счита за недостъпна, а не за нулева. Цените се записват при регистрирането на всяко ново извикване;
историческите записи не се преизчисляват по нови цени. Следователно акаунтите с абонамент могат да имат
оценка, еквивалентна на API таксуването, без тази сума да се начислява като паричен разход или да се приспада от абонаментната
квота. Съществуващите изчисления за квоти, бюджети и точни разходи според доставчика остават непроменени.

Тази диагностика използва съществуващото обобщение на състоянието на кеша с ограничен обхват и правилата за съхранение на журналите
на извикванията. Тя не променя стойностите по подразбиране за TTL на заявките, маршрутизирането или избора на акаунт.
Записването на заявения от клиента TTL спрямо действителния изходящ TTL в момента на изпращане
към доставчика е отложено; този панел отчита тарифните нива според отчетеното от доставчика потребление, а не действителния изходящ TTL.

Реализация: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` и `open-sse/utils/cacheWriteUsage.ts`.

## Изчисляване на разходите

Разходите се изчисляват от **ценови данни**, синхронизирани от LiteLLM (`src/lib/pricingSync.ts`):

| Модел             | Вход $/1M | Изход $/1M | Кеширани $/1M |
| ----------------- | --------- | ---------- | ------------- |
| gpt-5             | $2.50     | $10.00     | —             |
| claude-opus-4-6   | $15.00    | $75.00     | $1.50         |
| claude-sonnet-4-5 | $3.00     | $15.00     | $0.30         |
| gemini-2.5-pro    | $1.25     | $10.00     | —             |

Формулата за разходите (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Защо кешираните токени се изваждат от токените на подканата?** Кешираната част се таксува отделно; прилагането на входната цена към цялата подкана би довело до завишено отчитане.

### Синхронизиране на цените

Ценовите данни се синхронизират автоматично от LiteLLM чрез крайната точка `/api/pricing/sync` (задейства се от вградената cron задача, а не от достъпна за потребителя променлива на средата):

```bash
# Ръчно задействане
curl -X POST http://localhost:20128/api/pricing/sync
```

За модели без ценови данни OmniRoute преминава към **приблизително изчисляване на разходите** чрез вътрешни средни тарифи (извлечени от ценовите данни на LiteLLM).

## Агрегиране по периоди

Модулът `usageAnalytics.ts` изчислява уиджетите на таблото въз основа на необработени данни за използването. Поддържа 7 времеви периода:

| Период   | Времеви прозорец                    | Приложение                                |
| -------- | ----------------------------------- | ----------------------------------------- |
| `1d`     | Последните 24 часа                  | Откриване на почасови скокове в разходите |
| `7d`     | Последните 7 дни                    | Седмичен преглед                          |
| `30d`    | Последните 30 дни                   | Месечно фактуриране                       |
| `90d`    | Последните 90 дни                   | Тримесечен анализ                         |
| `ytd`    | От 1 януари на текущата година      | Проследяване на годишния бюджет           |
| `all`    | За цялото време                     | Статистика за целия период                |
| `custom` | Зададени от потребителя начало/край | Одити, заявки при необходимост            |

### Изчислявани уиджети на таблото

За всеки период аналитичният слой изчислява:

| Уиджет                            | Описание                                                               |
| --------------------------------- | ---------------------------------------------------------------------- |
| **Обобщаващи карти**              | Общ брой заявки, общи разходи, общ брой токени, процент на успеваемост |
| **Графика на дневните тенденции** | Разходи + токени на ден, натрупани по модели                           |
| **Топлинна карта на активността** | Решетка час от денонощието × ден от седмицата, цвят = брой заявки      |
| **Разбивка по модели**            | Кръгова диаграма на разходите по модели                                |
| **Разбивка по доставчици**        | Стълбовидна диаграма на заявките по доставчици                         |
| **Водещи API ключове**            | Таблица с 10-те ключа с най-високи разходи                             |
| **Анализ на грешките**            | Честота на грешките във времето, най-чести класове грешки              |

### Програмен достъп

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // записи от историята на използването
  "7d",                 // времеви период: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // карта на връзките с доставчици (connectionId → име на акаунт)
  {
    startDate: "2025-01-01",  // незадължително: за периода "custom"
    endDate: "2025-06-01",   // незадължително: за периода "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (центове)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Прилагане на квоти

Квотата за всеки API ключ се прилага на две места:

1. **Мек лимит** (`quotaWarnAt`): предупреждение на таблото, когато използването надвиши прага
2. **Твърд лимит** (`quotaLimit`): заявката се отхвърля с HTTP 429 при превишаване

### Конфигурация

```ts
// За всеки API ключ
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — показване на предупреждение
  quotaLimit: 10_00,    // $10.00 — принудително спиране
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Последователност на прилагане

```
Заявка ──▶ quotaCheck()
              │
              ├── В рамките на лимита?  ──▶ разрешаване
              │
              └── Над лимита?  ──▶ 429 Too Many Requests
                                   с хедър Retry-After
```

### Моментни снимки на квотите

Таблицата `quotaSnapshots` съхранява **историческото състояние на квотите** за анализ на тенденциите:

| Поле | Описание |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Проследяваният ключ |
| `window` | "day" | "week" | "month" |
| `used` | Разходи за този времеви прозорец (центове) |
| `limit` | Лимитът (центове) |
| `resetAt` | Кога се нулира времевият прозорец |
| `createdAt` | Кога е направена моментната снимка |

Моментни снимки се правят **при всяка заявка** с разходи > 0 и се използват за:

- Визуализиране на лентата за напредък на квотата в таблото
- Показване на графики за тенденциите на квотите за 30 дни
- Задействане на известия, когато използването се приближава до лимита

### Заявки за аналитични данни за използването

Данните за използването са достъпни чрез таблото за управление или MCP инструментите, а не чрез директни REST крайни точки за експортиране. Налични аналитични данни:

- **`/api/usage/analytics`** — обобщени показатели за използването (групиране по модел, доставчик, ключ)
- **`/api/usage/quota`** — текущо състояние на квотата за всеки API ключ
- **`/api/usage/history`** — журнали с историята на заявките

## MCP инструменти

Два MCP инструмента предоставят на агентите достъп до данните за използването (вижте `open-sse/mcp-server/tools/`):

| Инструмент              | Описание                                               |
| ----------------------- | ------------------------------------------------------ |
| `omniroute_cost_report` | Генерира отчет за разходите по ключове за даден период |
| `omniroute_check_quota` | Връща текущото състояние на квотата за API ключ        |

Примерно извикване от агент:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## Съхранение и почистване

Обемът на данните за използването нараства с ~1-10KB на заявка. При голям мащаб това може да е значително.

### Настройки за съхранение

Периодът на съхранение на историята на използването се конфигурира чрез настройките на базата данни в потребителския интерфейс или чрез `/api/settings/database`.

По подразбиране историята на използването се съхранява за **90 дни**.

### Почистване

Старите записи се почистват от `src/lib/db/cleanup.ts`:

- Задейства се от фоновия cron процес
- Изтрива записи от `usage_history`, по-стари от периода на съхранение, зададен в настройката `usageHistory`

### Оценка на необходимото дисково пространство

| Честота на заявките | Съхранение за 30 дни | Съхранение за 90 дни |
| ------------------- | -------------------- | -------------------- |
| 100 заявки/ден      | ~3MB                 | ~9MB                 |
| 1,000 заявки/ден    | ~30MB                | ~90MB                |
| 10,000 заявки/ден   | ~300MB               | ~900MB               |
| 100,000 заявки/ден  | ~3GB                 | ~9GB                 |

При много голям трафик обмислете:

- Намаляване на периода на съхранение чрез настройките на базата данни
- Използване на `aggregated_metrics` вместо необработени записи (само за анализи)

## Съвети за оптимизиране на разходите

### 1. Използвайте подходящия модел

```bash
# Бърз отговор — използвайте евтин и бърз модел
curl -d '{"model":"auto/fast","messages":[...]}'

# Сложна задача — използвайте качествен модел
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Активирайте кеширането

Кеширането на подкани на Anthropic спестява **90% при повтарящ се контекст**:

```ts
// Кеширането е автоматично — просто включете същата дълга системна подкана
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Ще се кешира автоматично
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Използвайте компресия

Компресията с RTK + Caveman спестява **15-95% при сесии с интензивно използване на инструменти**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Задавайте квоти за всеки ключ

Винаги задавайте `quotaLimit`, за да предотвратите неконтролируеми разходи:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Лимит от $10/месец
```

### 5. Проверявайте най-големите потребители

Използвайте таблото за управление или **`/api/usage/analytics`**, за да групирате по API ключ и да сортирате по разходи:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Отстраняване на проблеми

### „Разходите са по-високи от очакваното“

1. Проверете **`/api/usage/analytics?groupBy=model`** — намерете скъпия модел
2. Проверете **`/api/usage/analytics?groupBy=apiKey`** — намерете потребителя с голямо потребление
3. Уверете се, че данните за цените са актуални: `POST /api/pricing/sync`

### „Липсващи записи“

- Проверете настройките за съхранение на данни в базата данни в Табло за управление → База данни → Почистване — старите записи се изтриват от периодичната задача за почистване (`src/lib/db/cleanup.ts`)
- Проверете за грешки в `src/lib/db/usage*.ts` — неуспешните записи в базата данни се регистрират в журналите, но не се показват
- Уверете се, че заявката действително е достигнала до `chatCore` — проверете комбинираното маршрутизиране

### „Квотата не се прилага“

- Проверете настройката `quotaLimit` на ключа
- Уверете се, че `quotaWindow` е зададена правилно
- Потърсете записи `quotaSnapshots` — те трябва да се създават при всяка заявка
