OmniRoute публикува npm + Docker артефакти. Тези гейтове осигуряват произход,
инвентаризация (SBOM) и сканиране за CVE, всички с отворен код (OSS), интегрирани в работните потоци за издаване.
**Първо консултативен** подход — те докладват сега, преминават към блокиране след първото успешно издание.

| Гейт                | Инструмент                                     | Къде                          | Блокира ли?                        | Изход                                        |
| :------------------ | :--------------------------------------------- | :---------------------------- | :--------------------------------- | :------------------------------------------- |
| SLSA произход (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | само ако публикуването е неуспешно | badge npmjs / `npm audit signatures`         |
| SBOM npm            | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | само ако генерирането е неуспешно  | Release asset + artifact                     |
| SBOM образ          | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | консултативно                      | CycloneDX artifact                           |
| Trivy CVE (SARIF)   | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | консултативно                      | SARIF (HIGH+CRITICAL) → Security tab         |
| Trivy CRITICAL гейт | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **блокиращо**                      | `exit-code: '1'` on fixable CRITICAL         |
| osv vulnCount       | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **блокиращо**                      | регулира `metrics.vulnCount` (посока:надолу) |
| OpenSSF Scorecard   | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | консултативно                      | SARIF → Security + badge                     |

CVE механизмът за регулиране на образа използва **две стъпки** във `docker-publish.yml`: SARIF стъпката
(`HIGH,CRITICAL`, `exit-code: 0`) поддържа HIGH+CRITICAL видими в раздела за сигурност, без да блокира;
стъпката _CRITICAL гейт_ (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) проваля изданието при CRITICAL CVE **с налично решение**. `ignore-unfixed`
предотвратява блокирането на изданието за CVE на базов образ без пач отгоре.

## ⚠️ Вариации при CVE (блокиращи проверки на osv/Trivy)

osv и Trivy сравняват зависимостите с бази данни за CVE, които **непрекъснато нарастват**. PR, който **не променя никакви зависимости**, може внезапно да стане неуспешен, защото е оповестена нова CVE в съществуваща зависимост (osv: измереният `vulnCount` > базовата стойност; Trivy: нова поправима уязвимост с ниво CRITICAL в образа). **Това е ОЧАКВАНО оперативно поведение на блокираща проверка за CVE, а не регресия на продукта.**

Когато osv или Trivy станат неуспешни поради новооповестена CVE, решението е:

1. **Актуализирайте засегнатата зависимост** (предпочитано) — надстройте до коригираната версия чрез `package.json` `overrides` (за транзитивни зависимости) или изградете образа отново върху коригирана базова версия.
2. **Ако няма налична корекция от доставчика:**
   - **osv:** задайте нова базова стойност за `metrics.vulnCount` в `config/quality/quality-baseline.json` (`npm run quality:ratchet -- --update` не обхваща специализираните проверки — редактирайте стойността ръчно, `direction:down`) с бележка за обосновка + задача за проследяване.
   - **Trivy:** добавете запис в `.trivyignore` (по един CVE-ID на ред) с коментар за обосновка + задача за проследяване. `ignore-unfixed: true` вече автоматично обхваща CVE без налични корекции.

Задължителните изпълнения на OSV (`check:vuln-ratchet -- --ratchet`) завършват с отказ, статус `INCOMPLETE` и изходен код 2, когато скенерът, отчетът или базовата стойност не могат да бъдат валидирани. Измерена регресия води до изходен код 1. Препоръчителното изпълнение все пак може да отчете `SKIP` с изходен код 0, което не потвърждава, че зависимостите са преминали сканирането. Блокиращата стъпка на Trivy също изисква успешно измерване: недостъпни инструменти, неуспешни задачи и липсващи доказателства за образа не могат да удостоверят, че образът е чист.

## Риск от изведена от употреба зависимост

Основният lockfile вече не включва `extract-zip` или връзка на зависимост към него след
надграждането на фиксираната версия на инструмента за разработка promptfoo. С това се премахва приетата по-рано
верига `promptfoo` → `@openai/codex-security` → `extract-zip`, проследявана в #14482.
Проверките за регресии в `tests/unit/extract-zip-14482-exposure.test.ts` отхвърлят повторното ѝ
въвеждане и запазват забраната за импортиране от продукционен код.

Текущата корекция на зависимостите също ограничава заместванията за съвместимост до
MSAL клиента на Azure identity, FTP клиента на get-uri и Zod зависимостта на OpenCode v1 SDK. Получаването
на Azure токени и извличането чрез FTP се тестват с контролирани транспортни механизми; и двата OpenCode
пакета изпълняват собствените си компилационни и тестови набори. Броят на предупрежденията в регистъра представлява
измерване към определен момент и може да се промени след commit на lockfile файла.
