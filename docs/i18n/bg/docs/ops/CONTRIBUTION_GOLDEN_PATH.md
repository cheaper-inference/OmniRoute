Използвайте това ръководство, за да изберете най-малкия надежден цикъл за разработка за дадена pull request заявка. То не
заменя свързаните по-долу архитектурни документи и документите за сигурност за конкретните области; то свързва всеки често срещан
тип промяна с неговите договори, целеви проверки и CI покритие.

## Пътят, който следва всяка промяна

1. **Изберете базовия клон, преди да редактирате.** Намерете най-високия активен клон `release/v*` и създайте клон от
   последния му commit. Насочете заявката към този клон, а не към `main`. Ако има активно замразяване на издание, не насочвайте заявката към замразения
   клон; използвайте следващия активен цикъл, описан в
   [Модел за разклоняване и издания](BRANCHING_MODEL.md).
2. **Назовете договорите.** Идентифицирайте всеки каталог, схема, генериран артефакт, публичен API или потребителски
   интерфейс, който промяната засяга. Таблицата по-долу посочва минималния начален набор.
3. **Напишете или актуализирайте целевите тестове.** Промените в продукционния код в `src/`, `open-sse/`, `electron/` или
   `bin/` изискват автоматизиран тест в същата PR заявка. Изпълнете най-малкия набор от тестови файлове, който доказва
   поведението, а след това и изброените целеви проверки.
4. **Оставете CI да изпълни широката матрица.** Пълните сегменти от модулни тестове, Vitest, прагът за покритие и
   продукционната компилация се изпълняват за PR заявката. Изпълнявайте широк набор от тестове локално само когато целева грешка сочи към
   по-широко въздействие или когато промяната обхваща няколко подсистеми.
5. **Синхронизирайте преди преглед.** Изтеглете активния базов клон, прегледайте новите му commit-и и разликите на вашия клон спрямо
   него, след което направете rebase или merge на базовия клон според работния процес за участници. Разрешете конфликтите в генерирани файлове
   и каталози от техния източник, генерирайте ги отново, изпълнете повторно целевия цикъл и потвърдете, че
   PR заявката все още е насочена към активния клон за изданието.
6. **Запишете доказателствата.** В шаблона за PR заявката посочете изпълнените команди, всеки добавен или променен тестов файл,
   миграциите или feature flags и всички проверки, които все още предстои да бъдат изпълнени само в CI.

## Препоръчителни пътища по тип промяна

Командите по-долу са минимални целеви проверки, а не разрешение да пропуснете тест, който директно покрива
поведението, което сте променили.

### Доставчик

**Договори**

- Дефиницията на доставчика в `src/shared/constants/providers/` и композицията ѝ в
  `src/shared/constants/providers.ts`.
- Моделите и възможностите в `open-sse/config/providerRegistry.ts` или в отделените от него файлове на регистъра.
- Изборът на изпълнител/транслатор, конфигурацията на OAuth или API ключ, ресурсите на таблото за управление и генерираната
  справочна документация за доставчика, когато е приложимо.
- Публичните идентификационни данни трябва да използват `resolvePublicCred()`; отговорите с грешки трябва да използват споделените помощни функции
  за премахване на чувствителна информация. Вижте `docs/security/PUBLIC_CREDS.md` (git; не се компилира в `/docs`) и
  [Премахване на чувствителна информация от грешки](../security/ERROR_SANITIZATION.md).

**Целеви цикъл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # когато каталогът се промени; commit-нете генерираната разлика
npm run lint
```

Тествайте също всяка засегната група заявки: чат, Responses, изображения, embeddings, аудио или видео.
Преглеждайте разликите в генерираните каталози и golden файлове като промени в договорите; не ги приемайте безкритично.

### Маршрутизиране

**Договори**

- Публичните стойности на стратегиите и метаданните за потребителския интерфейс в `src/shared/constants/routingStrategies.ts`.
- Разпределянето и подреждането в `open-sse/services/combo.ts` и `open-sse/services/combo/`.
- Combo схемите, персистентността, състоянието на устойчивост, възможностите на моделите и контролите в API/потребителския интерфейс.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) и документацията за устойчивостта, когато поведението се променя.

**Целеви цикъл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # промени в стратегията или разпределянето
npm run check:known-symbols      # промени в регистрирането на стратегии
npm run lint
```

Използвайте локално детерминистични тестове с имитиран upstream. Live combo smoke тестовете изискват идентификационни данни и са
ръчни, а не заместители на CI.

### Потребителски интерфейс / UX

**Договори**

- Маршрутът/страницата на Next.js и границите на споделените компоненти в `src/app/` и
  `src/shared/components/`.
- Форматите на API отговорите, състоянията за зареждане/липса на съдържание/грешка, поведението с клавиатура и екранен четец,
  адаптивното оформление, темите и разширяването на локализациите.
- Английските изходни низове за потребителския интерфейс в `src/i18n/messages/en.json`; не задавайте директно нов текст, видим за потребителите.

**Целеви цикъл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Стартирайте приложението при промени във взаимодействието или визуалното представяне и проверете както тесни, така и широки изгледи. CI изпълнява
продукционната компилация и по-широките набори от тестове; визуалното поведение все пак се нуждае от целеви компонентен тест, Playwright тест
или документирана ръчна проверка, подходяща за промяната.

### i18n

**Договори**

- `src/i18n/messages/en.json` е източникът за потребителския интерфейс; `config/i18n.json` е източникът за локализациите.
- CLI каталозите се намират отделно в `bin/cli/locales/`.
- Запазвайте ICU placeholders и таговете точно. Не превеждайте имена на продукти/доставчици/модели,
  имена на протоколи и заглавки, команди, идентификатори в код/JSON, URL адреси, променливи на средата или
  защитени термини като `OmniRoute`, `OAuth`, `MCP` и `A2A`. Текущият списък с източници е
  `scripts/i18n/glossary/protected-terms.json`.

**Целеви цикъл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # когато CLI низовете/каталозите се променят
npm run lint
```

Това са насоки за съществуващата система, а не покана за разширяване на нейните инструменти или модел на ключовете.
Поддържайте i18n промените прецизни и ограничени, докато се проектира заместващата система. Не изпълнявайте команди за превод,
които извикват външни услуги, освен ако задачата изрично не изисква генерирани преводи и
не сте прегледали получената разлика.

### CLI

**Договори**

- Публични команди и флагове в `bin/cli/`, генерирани API команди, кодове за изход, stdout/stderr и
  структури на JSON изхода, поведение на конфигурацията/средата и файлове, включени в пакета.
- Низовете на CLI, видими за потребителите, трябва да използват i18n слоя на CLI, а каталозите `en`/`pt-BR` трябва да останат синхронизирани.
- Запазете Node като поддържана среда за изпълнение и договора на публикувания двоичен файл.

**Фокусиран цикъл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # промени в генерирания/пакетирания CLI
npm run check:pack-policy     # промени в публичната повърхност на пакета
npm run lint
```

Използвайте точната команда във временна директория за данни, когато поведението зависи от синтактичен анализ, файлове или код за
изход. CI извършва по-широките проверки на артефактите на пакета и екосистемата.

### База данни

**Договори**

- Модули на домейни в `src/lib/db/`; импортирайте конкретните модули директно (старият слой за реекспортиране `localDb.ts` беше премахнат).
- Номерирани, идемпотентни SQL миграции в `src/lib/db/migrations/`, безопасност на транзакциите, поведение при
  надграждане, индекси и всеки извикващ код, засегнат от схемата.
- Маршрутите и обработчиците никога не изпълняват директно необработен SQL.

**Фокусиран цикъл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

При добавяне на миграция тествайте както с нова база данни, така и с надграждане от предходната схема. Тестовете на базата данни
трябва да затварят манипулаторите и да извикват `resetDbInstance()` по време на почистването. Изпълнявайте `npm run test:bun:db` само когато
се променя пътят на експерименталния Bun адаптер; Node остава водещият стандарт.

### Изграждане / внедряване

**Договори**

- Основни манифести и манифести на работните пространства/заключващ файл, `scripts/build/`, самостоятелно сглобяване на Next.js, съдържание на пакета `dist/`,
  платформени метаданни на Electron, CI работни процеси и контролни маркери за внедряване.
- Поддържаните диапазони на Node и разрешената употреба на Bun в `CLAUDE.md` трябва да останат непроменени.
- Артефактите от изграждането остават непроследявани; прилагат се правилата за зависимости, лицензи, работни процеси и пакети.

**Фокусиран цикъл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # промени в зависимостите или заключващия файл
npm run check:pack-policy      # промени в публичната повърхност на публикувания пакет
npm run lint
```

Използвайте `npm run build` локално само когато промяната засяга компилацията, самостоятелното сглобяване, ресурсите
или пакетирането за средата за изпълнение. Използвайте `npm run build:release` само за валидиране на издание/внедряване. Изграждането в CI е
окончателният междуплатформен сигнал; специфичните за дадена платформа промени в Electron изискват съответстващо фокусирано изграждане
или доказателство от базов тест.

## Скриптове за разработчици за споделена машина

Два помощни скрипта в `scripts/dev/` реализират локалния цикъл на devbox, където са активни и други сесии:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # файлове от merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # точно тези файлове
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # изолирано работно дърво, безопасно при паралелна работа
```

- `typecheck-touched.sh` проверява типовете само на променените `.ts/.tsx` файлове чрез временен
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) с 6 GB heap, така че заменя обхващащия целия проект `tsc -p tsconfig.json`,
  който изчерпва паметта на натоварена машина. Той извежда грешките в променените файлове плюс един обобщаващ ред и завършва
  с код `1` при грешки в променените файлове, `2`, когато единствените грешки са в импортирани файлове или tsc е прекратен
  без диагностика (прочетете посочения от него журнал в `_artifacts/typecheck-touched/`), и `0`, когато
  няма грешки. Временният tsconfig винаги се премахва; никога не го commit-вайте.
- `new-worktree.sh` сериализира едновременните изпълнения чрез `<git-common-dir>/omniroute-new-worktree.lock`
  (по подразбиране изчаква до 600 s и показва видимо съобщение; заглавната част на скрипта описва
  как стойността може да бъде заменена) и отменя
  създадения от него клон, когато `git worktree add` се провали, преди работното дърво да е създадено, така че повторният опит
  не изисква ръчно изпълнение на `git branch -D`. Твърдо свързаният `node_modules` и копието на `.husky/_` остават непроменени.

## Локален цикъл за кандидат

Тестовете на изходния код не могат да докажат, че пакетираният артефакт се стартира: списъците за пакетиране, орязаните зависимости
и собствените двоични файлове се провалят едва след като tarball файлът бъде инсталиран и стартиран. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) е локалната страна на процеса еднократно изграждане / валидиране / повишаване от
RFC #8084: той изгражда един кандидат, валидира точно този артефакт, повишава го чрез преименуване на директории
и го връща назад, когато повишеният слот не премине проверката си за изправност.

```bash
npm run dev:candidate -- run --dry-run --json  # извеждане на плана без никакви промени
npm run dev:candidate -- run                   # изграждане + валидиране + повишаване, автоматично връщане назад
npm run dev:candidate -- build                 # npm pack + инсталиране в _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # стартиране на свободен порт, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # размяна на current и previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # повторно използване на tarball, изграден другаде (CI)
```

- **Изграждане само веднъж.** `build` пакетира текущото дърво (изисква `dist/server.js`, затова първо изпълнете
  `npm run build:release`) или копира `--from-tarball`, след което инсталира tarball файла в
  изолиран npm префикс, защото tarball файлът не съдържа `node_modules`. Идентификаторът е краткият sha на `HEAD`
  (`-dirty`, когато дървото има локални промени) или `tgz-<sha256>` за tarball файл. Вече изграден чист идентификатор
  се използва повторно, вместо да бъде изграден наново; подайте `--force`, за да го изградите повторно.
- **Валидиране на пакета, а не на изходния код.** `validate` стартира инсталирания CLI
  (`serve --port <free port>`) с нов `DATA_DIR=<candidate>/data`, фиктивни тайни и премахнати от
  средата `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` и `INITIAL_PASSWORD` на оператора,
  така че да провери поведението при loopback без ключове на нова инсталация. Той изчаква
  `GET /api/health` да върне 200, изисква `GET /v1/models` да върне 200, спира групата процеси
  и записва резултата във `validation.json` заедно с хеша на tarball файла.
- **Повишаване на същия артефакт.** `promote` отказва кандидат без успешно валидиране за
  хеша на текущия му tarball файл. Активният слот по подразбиране е `_artifacts/candidate/current`; `--target <dir>`
  избира друга директория в същата файлова система, а предишният ѝ слот е `<dir>.previous`.
  Всяко преименуване е атомарно, а при грешка по време на процеса вече извършените преименувания се обръщат.
- **Връщане назад.** `run` валидира отново повишения слот и разменя обратно `current` и `previous`, когато
  тази проверка е неуспешна. Кандидат, който не премине първото валидиране, никога не се повишава.

Всичко се записва в игнорираната от git директория `_artifacts/candidate/`; съществуваща инсталация на OmniRoute
и нейната директория с данни никога не се променят. Повишеният CLI е
`_artifacts/candidate/current/prefix/bin/omniroute`; когато го използвате, стартирайте го със собствен `DATA_DIR`.
Кодове за изход: `0` при успех, `1` при неуспешно валидиране или повишаване, `2` при грешка в употребата или липсваща компилация.

## Локален цикъл спрямо CI

| Изпълнявайте локално за всяка промяна                                                                  | CI предоставя по-широкия сигнал                                                                 |
| ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Директни тестове на поведението и проверки по категории, описани по-горе                               | Разпределен пълен набор от модулни тестове и последователни тестове                             |
| `npm run lint`                                                                                         | Набори от тестове на Vitest и прагове за покритие/качество                                      |
| Проверка на типовете или компилация само когато засегнатият договор го изисква                         | Продукционна компилация, проверки за сигурност, документация, зависимости и политики за PR      |
| Ръчни интерактивни проверки/проверки на живо само когато автоматизацията не може да докаже поведението | Междузадачни интеграционни проверки и проверки на платформата, конфигурирани от работния процес |

Успешният фокусиран цикъл е доказателство за променения договор, а не гаранция, че несвързаните CI проверки
ще преминат успешно. И обратно, не карайте всяка локална редакция да чака пълната матрица на хранилището.

## Контролен списък за синхронизиране

Преди да заявите преглед:

- Потвърдете, че базовият клон на PR все още е най-високият активен клон `release/v*`.
- Извлечете този базов клон и прегледайте комитите, добавени след създаването на вашия клон.
- Прегледайте `git diff <active-base>...HEAD` за неволни или генерирани промени.
- Разрешете конфликтите в каталога и генерираните документи, като актуализирате източника и генерирате изхода отново.
- Изпълнете отново всеки фокусиран тест/проверка, посочен в описанието на PR, след синхронизирането.
- Никога не отслабвайте твърденията и не премахвайте задължителни тестове само за да ги приведете в съответствие с преместена база.

За правилата за замразяване на изданието и пренасочване използвайте
[Модел за разклоняване и издания](BRANCHING_MODEL.md). За пълния списък на CI проверките използвайте
[Справочник за проверките за качество](../architecture/QUALITY_GATES.md).
