> **Накратко**: OmniRoute се предоставя с вграден мониторинг на изправността, автопилот за доставчиците, проследяване на квотите и механизми за наблюдаемост. Това ръководство обхваща таблото за управление, известията и отстраняването на неизправности.

**Източници:**

- `src/lib/monitoring/observability.ts` — моментна снимка на наблюдаемостта
- `src/lib/monitoring/comboHealthAutopilot.ts` — автопилот за изправността на комбинациите
- `src/lib/monitoring/providerHealthAutopilot.ts` — автопилот за доставчиците
- `src/lib/monitoring/providerHealthMatrix.ts` — матрица на изправността на доставчиците
- `src/lib/localHealthCheck.ts` — локална проверка на изправността
- `src/lib/tokenHealthCheck.ts` — изправност при обновяването на токени
- `src/lib/proxyHealth.ts` — кеш за изправността на проксито (разгледан в PROXY_GUIDE.md)

## Общ преглед

OmniRoute има **3 нива на мониторинг**:

```
┌──────────────────────────────────────────────────────────────┐
│  Ниво 1: Изправност на системата (на ниво сървър)             │
│  ├─ localHealthCheck.ts — БД, портове, нативни зависимости    │
│  ├─ db/healthCheck.ts — цялост, FK, осиротели артефакти       │
│  └─ Табло: /dashboard/health                                  │
├──────────────────────────────────────────────────────────────┤
│  Ниво 2: Изправност на доставчиците (устойчивост по доставчик) │
│  ├─ providerHealthAutopilot.ts — прекъсвач, изчаквания         │
│  ├─ providerHealthMatrix.ts — оценки по доставчик/модел       │
│  └─ Табло: /dashboard/providers                               │
├──────────────────────────────────────────────────────────────┤
│  Ниво 3: Наблюдаемост в реално време (моментни снимки)         │
│  ├─ observability.ts — прекъсвачи, сесии, квота                │
│  ├─ tokenHealthCheck.ts — обновяване на OAuth токени           │
│  └─ MCP инструменти: omniroute_get_health, omniroute_get_session_snapshot │
└──────────────────────────────────────────────────────────────┘
```

## Страници на таблото за управление

### `/dashboard/health` (Изправност на системата)

Главното табло за изправността показва:

| Раздел                        | Какво показва                                         |
| ----------------------------- | ----------------------------------------------------- |
| **Състояние на сървъра**      | Време на работа, версия, порт, активни връзки         |
| **База данни**                | Връзка, цялост, размер на WAL, скорошни миграции      |
| **Обобщение на доставчиците** | Брой активни, брой изправни, брой отворени прекъсвачи |
| **Монитори на квотите**       | Активни сесии, известявани, изчерпани                 |
| **Скорошни грешки**           | Последните 10 грешки със стекови трасировки           |
| **Използване на ресурси**     | Памет, CPU, индикатор за натоварване на heap паметта  |

### `/dashboard/providers` (Изправност на доставчиците)

Табло за всеки доставчик:

| Колона     | Описание                                           |
| ---------- | -------------------------------------------------- |
| Доставчик  | ID на доставчика + показвано име                   |
| Изправност | Зелено/жълто/червено състояние                     |
| Прекъсвач  | Отворено/затворено/полуотворено състояние          |
| Връзки     | Брой връзки, последно обновяване                   |
| Модели     | Налични модели, изправност за всеки модел          |
| Разходи    | Разходи за днес, тенденция за 7 дни                |
| Грешки     | Брой грешки за последните 24 ч., водещ клас грешки |

Щракнете върху доставчик, за да видите:

- Скорошни заявки с разбивка на латентността
- Оценки за изправността на всяка връзка
- Блокирания за всеки модел
- Препоръки от автопилота

### `/dashboard/quota` (Проследяване на квотите)

За всеки API ключ:

- Текущо използване спрямо лимита (лента за напредъка)
- Тенденция на квотата (30-дневна диаграма)
- Час на следващото нулиране
- Хронология на известията

### `/dashboard/combos` (Изправност на комбинациите)

За всяка комбинация:

- Стратегия + цели
- Изправност на всяка цел
- Скорошни събития за преминаване към резервна цел
- Процент на успеваемост (24 ч., 7 дни, 30 дни)

## Здравна проверка API

OmniRoute излага** две** HTTP здравни повърхности. Те не са взаимозаменяеми за оркестрантите.

| Пътека                       | Цел                                                                                 | Тегло                                        | Използвайте за                                                                          |
| ---------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------- |
| `GET /healthz`               | Жизнен цикъл liveness/readiness (`ok` / `starting` / `stopping`)                    | Тривиален (само флаг за фаза)                | Kubernetes** готовност** ; мека** жизненост** ако трябва да използвате HTTP             |
| `GET /api/monitoring/health` | Обобщение на доставчика на задълбочена система + (DB, купчина, брой на каталога, …) | Тежък (синхронизиране DB /мониторинг работа) | Табла за управление, дълбоки проверки на blackbox, вградена проверка на здравето Docker |

> **Забележка:** Матрицата за изправност на доставчика, проблемите с автопилота, мониторите на квотите, здравето на токена и подробностите за латентността извън `/api/monitoring/health` са достъпни чрез**MCP инструмент** `observability_snapshot` или** таблото за управление** страници — няма специални REST маршрути за тях.

И двата маршрута се движат по** същият цикъл на събитие на възел** като обработка на заявки. Свързан с процесора път (голяма работа `GET /v1/models` каталог, компресиране на дълъг контекст/броене на токени) може да забави** всички** HTTP манипулатори, включително `/healthz`. Зает цикъл на събитие ≠ процес е мъртъв. Предпочитам оправянето на прасето; настройката на сондата само намалява фалшивите убийства.

### Лека сонда оркестратор

```bash
GET /healthz
# or HEAD /healthz
```

- **200** + тяло `ok` когато фазата на жизнения цикъл на сървъра е готова
- **503** + `starting` / `stopping` по време на стартиране или изключване
- Внедряване: `src/app/healthz/route.ts` (без DB ping)

#### `credentialHealth`: сонда-кеш срещу SQLite `test_status`

`GET /api/monitoring/health` → `credentialHealth` е** датчик за сонда-кеш в паметта** , а не дъмп на `provider_connections.test_status` на живо. След #12532 пътят на заявката чете само `getCachedCredentialHealthSummary()` ; фоновите проби опресняват кеша извън цикъла на събитията.

| Слой                            | Къде                                                                  | Какво означава                                                                                                                                                                                                           |
| ------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Сонда-кеш габарит               | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | Последните резултати от проверката за изправност на идентификационни данни все още се съхраняват в паметта на процеса. `source` винаги е `probe-cache`.                                                                  |
| Подробности за неуспешна връзка | `credentialHealth.failedConnections`                                  | Настояще** само когато `failed > 0`** . Ограничен списък от кеш редове с `status=error` (`connectionId`, `status`, дезинфекциран `lastError` / `lastErrorType`). `failedOmitted` се задава, когато списъкът е ограничен. |
| SQLite лепкав статус            | `credentialHealth.staleDbNonOkCount`                                  | Брой на** активен** (`is_active=1`) редове за свързване, чийто персистиран `test_status` е известно, че не е добре (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).                    |

Двата слоя могат да не са съгласни нарочно:

- Измерете `failed=0` докато `staleDbNonOkCount>0` — SQLite все още има лепкав `test_status` (например `expired` или `credits_exhausted`), че последната моментна снимка на кеша на сондата не се брои като `status=error`.
- Измерете `failed>0` докато SQLite изглежда здрав — скорошна сонда е неуспешна и е кеширана; редът DB не е актуализиран или по-късно е изчистен.

Не предупреждавайте само на `provider_connections.test_status` когато изтривате тази крайна точка. Използвайте `failed` + `failedConnections` за неизправности на сондата на живо и `staleDbNonOkCount`, когато имате нужда от постоянно преброяване на постоянно състояние.

### Препоръки за сонда на Kubernetes

OmniRoute е a** процес с единичен възел** (един цикъл на събитие). Stock Docker `HEALTHCHECK` е насочен към лекия `/healthz`. `/api/monitoring/health` е** твърде тежък** за интервали на жизненост kubelet.

| Сонда              | Препоръчителна цел                                                                        | Бележки                                                                                                                                                                                                                                                                                                                                                             |
| ------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Стартиране**     | HTTP `GET /healthz` с дълъг `failureThreshold` (или голям `startPeriod`)                  | Миграцията на студен старт + SQLite може да надхвърли няколко секунди                                                                                                                                                                                                                                                                                               |
| **Готовност**      | HTTP `GET /healthz`                                                                       | Жизнен цикъл `ok` / `starting` / `stopping` (200 срещу 503). Все още клапва, ако цикълът е блокиран от процесора. А** 200 за няколко секунди не е здравословно** (#10303) — това означава, че цикълът на събитието е бил прекъснат преди да се изпълни 3-байтовият манипулатор                                                                                      |
| **Жизненост**      | HTTP `GET /livez`,** или TCP** на главния сервизен порт (`PORT`, `20128` по подразбиране) | `/livez` е активен само процес (винаги 200, ако манипулаторът работи). Той все още споделя цикъла на събитията — busy ≠ dead и не открива липсата на цикъл на събития (#10303) по-добре от TCP. Предпочитам**TCP** ако HTTP сондите изтекат при catalog/compression натоварване; направи** не** убийте шушулката при къси сергии за цикъл на събития така или иначе |
| **Дълбоко здраве** | `GET /api/monitoring/health` от външен инструмент за проверка                             | Не е за kubelet `livenessProbe` / tight `readinessProbe`                                                                                                                                                                                                                                                                                                            |

Примерна форма (коригирайте праговете към вашия студен старт и натоварване на компресия):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Under event-loop stall HTTP /livez can still time out. TCP is the
  # conservative alternative:
  # tcpSocket:
  #   port: http
```

**недей** точка kubelet** жизненост** в `/api/monitoring/health`. Този път върши реална работа DB/monitoring и ще даде фалшиво положителен резултат при натоварване.

Свързани: [#10052](https://github.com/cheaper-inference/OmniRoute/issues/10052) (сонди, докато цикълът на събитията е зает), [#9685](https://github.com/cheaper-inference/OmniRoute/issues/9685) / [#10055](https://github.com/cheaper-inference/OmniRoute/pull/10055) (свиня за ценообразуване по каталог), [#10117](https://github.com/cheaper-inference/OmniRoute/issues/10117) (свиня за броене на символи за компресиране).

### systemd watchdog (замразен цикъл на събития)

На systemd хост, OmniRoute казва на мениджъра на услугите, когато е готов и продължава да го пингва, така че сървър, чийто цикъл на събития е блокирал, се убива и рестартира, вместо да остане и да мълчи. Пинговете идват от собствения цикъл на събитията на сървъра: когато блокира, те спират и systemd рестартира услугата, след като `WatchdogSec` изтече без такъв.

[`omniroute autostart enable`](../../bin/cli/tray/autostart.mjs) вече записва потребителска единица с това. Единица, която напишете сами (по подразбиране `Type=simple`), не получава куче-пазач, така че добавете тези редове към нейната `[Service]` секция:

```ini
[Service]
Type=notify
NotifyAccess=all
WatchdogSec=180
TimeoutStartSec=300
```

Генерираната единица задава `Restart=on-failure`, така че добавете и този ред — без него пазачът само убива блокираната услуга, вместо да я рестартира.

- `Type=notify`: услугата се "стартира", когато сървърът изпрати `READY=1`, а не когато процесът се разклонява. `TimeoutStartSec` ограничава бавен старт.
- `NotifyAccess=all`: пинговете се изпращат от процеса на сървъра, който е дъщерен на надзорника `omniroute serve`.
- `WatchdogSec`: пинговете излизат на всеки 60 секунди, така че използвайте** 120 или повече** . По-малките стойности биха рестартирали здрав сървър.
- Стартирайте `omniroute serve` на преден план. `--daemon` отделя сървъра от cgroup на модула и ръкостискането за уведомяване никога не завършва.

Проверете дали е активен след рестартиране:

```bash
systemctl --user show omniroute -p WatchdogUSec -p WatchdogTimestamp
```

`WatchdogUSec` показва конфигурираното забавяне и `WatchdogTimestamp` се придвижва напред всяка минута. Рестартиране, причинено от кучето-пазач, се записва като `Result=watchdog`. За да изключите ping-овете, като запазите устройството така, както е, задайте `OMNIROUTE_DISABLE_SD_NOTIFY=1`; без `NOTIFY_SOCKET` (терминал, Docker, Electron, Windows) нищо не се изпраща.

Кучето-пазач проверява само дали цикълът на събития продължава да работи. Сървър, който е бавен, но все още работи, не се рестартира.

### Незадължителна работа по пътя на заявката (памет, умения, опресняване на токени)

Извличане на памет, инжектиране на умения и опресняване на OAuth токени споделят** цикъл на събитие на главния възел** със `/healthz`. Те са функции за превключване на таблото (`memoryEnabled`, `skillsEnabled`), а не работен пул. Вижте [Environment — event-loop cost](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349).

### Здраве на доставчика

### Подробности за доставчика

## Автопилот за състоянието на доставчиците

Модулът `providerHealthAutopilot.ts` е **система за самовъзстановяване**, която:

1. Открива проблеми с доставчиците (отворена верига, периоди на изчакване, блокирания, предупреждения за квоти)
2. Генерира **препоръчителни действия** за отстраняването им
3. По избор **изпълнява автоматично** действия с нисък риск

### Видове откривани проблеми

| Вид проблем                  | Сериозност     | Примерно условие                                    |
| ---------------------------- | -------------- | --------------------------------------------------- |
| `provider_circuit_open`      | критична       | Прекъсвачът е отворен след 5 неуспешни опита        |
| `provider_circuit_half_open` | предупреждение | Прекъсвачът тества възстановяването                 |
| `connection_cooldown`        | предупреждение | Връзката е в период на изчакване след 429           |
| `stale_connection_error`     | предупреждение | Последното опресняване е неуспешно преди 30+ минути |
| `terminal_connection_error`  | критична       | OAuth е отменен, ключът е невалиден                 |
| `inactive_connection`        | информация     | Връзката е деактивирана в настройките               |
| `model_lockout`              | предупреждение | Конкретен модел е поставен под карантина            |
| `quota_monitor_warning`      | предупреждение | Използвани са 80%+ от квотата                       |

### Видове генерирани действия

| Действие                       | Риск   | Описание                                      |
| ------------------------------ | ------ | --------------------------------------------- |
| `clear_provider_breaker`       | среден | Нулиране на прекъсвача до затворено състояние |
| `clear_connection_cooldown`    | нисък  | Премахване на периода на изчакване от връзка  |
| `clear_stale_connection_error` | нисък  | Изчистване на флага за остаряла грешка        |
| `clear_model_lockout`          | нисък  | Повторно активиране на карантиниран модел     |
| `reactivate_connection`        | среден | Повторно активиране на деактивирана връзка    |
| `deactivate_connection`        | висок  | Деактивиране на проблемна връзка              |

### API

> **Няма REST крайна точка.** Проблемите, открити от автопилота, са достъпни чрез MCP инструмента `observability_snapshot` или таблото за управление. Автопилотът работи вътрешно; поведението му се конфигурира чрез базата данни с настройки (полето `autopilotMode` за всяка връзка), а не чрез променливи на средата — `grep -rn` за променлива на средата за режима на автопилота не връща нито едно съвпадение.

### Режим на автопилота

По подразбиране автопилотът работи в **ръчен режим** — той открива проблеми и генерира препоръчителни действия, но не ги прилага автоматично. Действията могат да бъдат приложени чрез таблото за управление.

## Автопилот за състоянието на комбинациите

`comboHealthAutopilot.ts` е **специфичният за комбинации** еквивалент на автопилота за доставчици. Той:

- Открива неизправни комбинации
- Препоръчва пренареждане на целите
- Предлага деактивиране на неработещи цели
- Автоматично премахва неработещи цели след N неуспешни опита

### Примери за проблеми с комбинации

```
Комбинация "always-on" (стратегия по приоритет)
├─ Цел 1: openai/gpt-5 (изправна)
├─ Цел 2: anthropic/claude-opus-4-6 (⚠️ моделът е блокиран до 14:00)
└─ Цел 3: kiro/claude-sonnet-4-5 (изправна)

Препоръчително действие: Пренареждане — преместете kiro над anthropic, докато блокирането изтече
```

## Монитори за квоти

`observability.ts` предоставя **монитори за квоти за всяка сесия** за доставчици с абонамент (Claude Code, Codex, GitHub Copilot):

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### Значения на състоянията

| Състояние   | Кога                              | Действие в потребителския интерфейс            |
| ----------- | --------------------------------- | ---------------------------------------------- |
| `starting`  | Извършва се първоначална проверка | Индикатор за зареждане                         |
| `idle`      | Няма скорошна активност           | Скрито от таблото за управление                |
| `healthy`   | Остават > 50% от квотата          | Зелена точка                                   |
| `warning`   | Остават < 50% от квотата          | Жълто предупреждение                           |
| `exhausted` | Квота = 0%                        | Червен блок, насочване към следващия доставчик |
| `error`     | Проверката е неуспешна            | Червена точка, скорошен повторен опит          |

### API

> **Няма REST крайна точка.** Данните от мониторите за квоти са достъпни чрез MCP инструмента `observability_snapshot` или таблото за управление.

## Проверка на състоянието на токените

OAuth доставчиците (Claude Code, GitHub Copilot, Cursor) се нуждаят от **периодично опресняване на токените**. `src/lib/tokenHealthCheck.ts` изпълнява фонов планировчик:

- **Цикъл на обхождане**: на всеки 60 секунди (обхождане в `TICK_MS = 60 * 1000` на `src/lib/tokenHealthCheck.ts:30`)
- **Интервал за проверка на състоянието на всяка връзка**: по подразбиране 60 минути (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`); конфигурира се чрез базата данни с настройки
- **Превантивно опресняване при 401**: обработва се от прихващача за съответната връзка

### Състояние на токените

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### Конфигурация

Конфигурацията за проверка на състоянието на токените се управлява вътрешно от `tokenHealthCheck.ts`.

### Състояние на токените

## Отстраняване на неизправности

### „Доставчикът се показва като работещ, но заявките са неуспешни“

1. Проверете **проблемите с автопилота** — възможно е даден модел да е блокиран
2. Прегледайте **скорошните грешки** за конкретния клас грешка
3. Опитайте **теста на връзката** в картата на доставчика
4. Проверете дали доставчикът няма **ограничение на честотата от външната услуга** (не се вижда локално)

### „Квотата се показва като налична, но виждам грешки 429“

- 429 означава, че според доставчика сте изчерпали квотата си
- Проследяването на квотата от OmniRoute може да е **неактуално** — достоверните данни са при доставчика
- Данните за квотата се опресняват автоматично чрез вътрешния монитор за квоти

### „Комбинацията е неуспешна, но всички цели изглеждат работещи“

- Проверете таблото за **състоянието на комбинациите** за проблеми с подредбата на целите
- Прегледайте **събитията за преминаване към резервен вариант** — възможно е комбинацията да изчерпва вариантите твърде бързо
- Проверете дали **стратегията** съответства на случая ви на употреба (приоритетна спрямо циклична спрямо автоматична)

### „Проверката на състоянието на базата данни е неуспешна“

- Изпълнете `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- Ако резултатът е „ok“ — фалшива тревога, проверката на състоянието е прекалено строга
- Ако резултатът е друг — **спрете OmniRoute** и следвайте [ръководството за възстановяване след бедствие](./DATABASE_GUIDE.md#disaster-recovery)

### „Натоварването на heap паметта е критично“

```bash
# Проверка на текущата heap памет
node -e "console.log(process.memoryUsage())"

# Задействане на ръчно събиране на отпадъци (ако е зададено --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# Намаляване на едновременните заявки (задава се от страницата Settings на таблото, а не чрез променлива на средата)
# Няма променлива на средата `MAX_CONCURRENT_REQUESTS` — конфигурирайте това в Settings → Concurrency.
```
