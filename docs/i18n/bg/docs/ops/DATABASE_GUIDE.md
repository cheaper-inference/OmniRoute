> **Накратко**: OmniRoute използва **SQLite с WAL журнал** като основно хранилище и **AES-256-GCM** криптиране на съхранените чувствителни полета. Това ръководство обхваща схемата, миграциите, архивирането/възстановяването и оперативните процедури.

**Източници:**

- `src/lib/db/core.ts` — единичен екземпляр + SCHEMA_SQL (17 основни таблици)
- `src/lib/db/migrationRunner.ts` — версионирани миграции
- `src/lib/db/migrations/` — 167 версионирани SQL файла
- `src/lib/db/encryption.ts` — помощни функции за криптиране
- `src/lib/db/backup.ts` — експортиране/импортиране на архиви
- `src/lib/db/healthCheck.ts` — диагностика на изправността

## Защо SQLite?

OmniRoute избра SQLite вместо PostgreSQL/MySQL по няколко причини:

| Фактор               | SQLite                                     | PostgreSQL                                         |
| -------------------- | ------------------------------------------ | -------------------------------------------------- |
| **Внедряване**       | Вградена — без отделен сървър              | Изисква настройване на сървър                      |
| **Криптиране**       | На ниво приложение (AES-256-GCM)           | Вградено TDE                                       |
| **Производителност** | По-бърза при малки/средни натоварвания     | По-добра при огромен брой едновременни записи      |
| **Паралелност**      | WAL режимът позволява едновременни четения | Пълна MVCC                                         |
| **Архивиране**       | Копиране на един файл                      | `pg_dump` или моментна снимка на файловата система |
| **Приложение**       | Инсталация за отделен потребител, вградена | SaaS с множество клиенти                           |

За внедрявания с **един потребител и един екземпляр** (основният случай на употреба на OmniRoute) SQLite е по-проста и по-бърза.

### WAL журнал

`core.ts` отваря базата данни в режим **WAL (Write-Ahead Logging)**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL позволява **едновременни четения** по време на запис — важно за таблото за управление, което изпълнява заявки, докато се записват заявки.

Размерът на кеша по подразбиране е **65 536 KiB (64 MiB)**. SQLite интерпретира отрицателна стойност за
`cache_size` като приблизителна горна граница в KiB и заделя страници при необходимост.
**Настройки > Система и съхранение > Размер на кеша** приема цели стойности от **1 до
1 000 000 KiB**; запазването на настройката я прилага към активната връзка с базата данни,
а OmniRoute възстановява съхранената стойност при стартиране.

## Местоположение на базата данни

SQLite файлът се съхранява на:

| ОС      | Път                                                        |
| ------- | ---------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                              |
| macOS   | `~/.omniroute/storage.sqlite`                              |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                  |
| Docker  | `/app/data/storage.sqlite` (конфигурируем чрез `DATA_DIR`) |

Съпътстващи файлове:

- `storage.sqlite-wal` — журнал за предварителен запис
- `storage.sqlite-shm` — файл за споделена памет
- `call_logs/` — артефакти от съдържанието на заявките (ако е активирано)

**Промяна на местоположението:**

```bash
DATA_DIR=/custom/path omniroute
```

Базата данни на OmniRoute има **110 TypeScript модула от най-високо ниво** в `src/lib/db/`. Всеки модул по домейн:

- Притежава една или повече конкретни таблици
- Експортира типизирани CRUD функции
- Никога не взаимодейства с таблиците на друг модул
- Използва `getDbInstance()` от `core.ts` за достъп до базата данни

### Граници между модулите

Основно архитектурно правило: **модулите не осъществяват директен достъп до таблиците на други модули**. За да работите с данните на друг модул, импортирайте функцията от съответния модул.

```ts
// ❌ ГРЕШНО: директен SQL от друг модул
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ПРАВИЛНО: използвайте функцията на модула providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

Това правило се налага чрез преглед на кода — няма статична проверка, но нарушенията се отбелязват.

## миграции

OmniRoute използва** версионни, идемпотентни миграции** в `src/lib/db/migrations/`. Всяка миграция е един SQL файл. Съществуват два формата за именуване; версията, записана в `_omniroute_migrations` е цифровият префикс.

### Наименуване на миграция

| Форматиране                                      | Пример                               | Използва се за                                                                                                                                                                   |
| ------------------------------------------------ | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (точно 3 цифри)            | `241_seen_models.sql`                | Старата серия `001`–`241`. Замразен, когато форматът на времевия печат се приземи (`240` и `241` бяха обединени точно преди него): нито един нов файл не получава пореден номер. |
| `YYYYMMDDHHMMSS_description.sql` (14 цифри, UTC) | `20261113120000_add_usage_index.sql` | Всяка миграция, създадена от 2026-11-13 нататък.                                                                                                                                 |

Защо промяната: с последователни номера паралелният PRs избра същия следващ номер и всички освен един трябваше да се преномерират преди сливането. Времевият печат UTC дава на всеки PR собствена версия.

Правила за формата на клеймото за време (приложени от `npm run check:migration-numbering`, споделени с генератора в `scripts/check/lib/migrationNaming.mjs`):

- Часовото клеймо е реална UTC дата и час, не по-рано от `20261113000000` и не повече от 10 минути в бъдещето.
- Описанието е с малка буква `snake_case` започваща с буква (`a-z`, `0-9`, единична `_` между думите), най-много 80 знака.
- Два файла с едно и също времево клеймо са дубликат.
- Правилото за липса на пропуски се прилага само за старите серии: всяко число от `001` до `241` трябва да съществува, с изключение на известните пропуски `026`, `055` и `121`. Изтриването на `241` (или всеки стар файл) се проваля. `001` и `241` никога не могат да бъдат добавени към списъка с разрешени `KNOWN_GAPS`. Файловете с клеймо за време никога не създават празнина.
- Всеки запис в `src/lib/db/migrations/` трябва да бъде обикновен файл с валидно `.sql` име с малки букви. Директория, символна връзка, `.SQL` или `.sql.bak` файл, скрит файл или име с интервал не успяват да преминат портала, защото бегачът ще го пропусне тихо или ще се срине при зареждане.

**Приложете поръчка.** Бегачът сортира по числовата стойност на префикса, а не по текст: първо старите `001`–`241` файлове, след това файловете с клеймо за време в реда на клеймото, след това всички директории с пространство от имена, регистрирани с `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (версии като `ee-001`). Предстояща миграция е всеки файл, чиято версия не е в `_omniroute_migrations`, така че миграция от по-стар клон, който се слива след по-нов, все още се прилага към съществуващи бази данни.

**Времето е редът на създаване, а не редът на сливане.** Ако вашата миграция зависи от таблица или колона, създадена от миграция с a** по-нова** timestamp (например един от друг PR, който се е слял първи), нова база данни ще стартира първо вашата и ще се провали. Докато вашият PR все още е отворен, регенерирайте името на файла с `npm run db:new-migration` така че да получи по-ново времево клеймо, или го направете независимо. `npm run test:migrations:fresh` прилага всяка миграция към празна база данни и улавя това.

### Обединената миграция никога не се изтрива или преименува

След като даден файл за миграция е в клон на версията или `main`, той вече се изпълнява в хомологични бази данни и бази данни на разработчици, при инсталации на VPS и в Enterprise sync. Оттам нататък:

- **Никога не го изтривайте.** Пресните инсталации биха загубили схемата си, докато надстроените бази данни я запазват.
- **Никога не го преименувайте.** Версията в `_omniroute_migrations` вече няма да съответства на файл, така че всяка база данни, която вече я е приложила, ще я стартира отново. След това неидемпотентният SQL дублира данни или спира зареждането.
- **Нуждаете се от различна схема?** Създайте нова миграция с `npm run db:new-migration`.

Преименуването е безопасно само за файл, който все още не е обединен, какъвто е случаят, за който се отнасят съветите на портала. Етикетът за освобождаване не променя нищо тук: всяко натискане към клон `release/v*` публикува Docker `:next` изображението и работи на homolog, VPS инсталации и Enterprise синхронизиране, така че обединената миграция е извършена на реални бази данни, преди да съществува `vX.Y.Z` таг. Гейтът се проваля при всяко премахване на базов файл, маркиран или не.

- **Връщане на обединена миграция.** `git revert`, която изтрива файла, не успява да изпълни портата. Запазете файла и отменете неговата схема при нова миграция: `npm run db:new-migration -- <description>`, с `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` и т.н. След това надстроените и свежи бази данни завършват със същата схема.
- **Приетото преименуване: запис за съвместимост и идентично съдържание.** Ако обединен файл трябва да се премести (например два обединени файла споделят клеймо за време и изпълнението спира със сблъсък на версия), преименувайте по-късния, без да докосвате неговия SQL и добавете `{ fromVersion, fromName, toVersion, toName }` към `RENAMED_MIGRATION_COMPATIBILITY` в `src/lib/db/migrationRunner/constants.ts`. Базите данни, които прилагат старата версия, преместват своя `_omniroute_migrations` ред, вместо да изпълняват файла отново. Порталът предупреждава за такова преименуване и винаги изпълнява проверката на комутацията върху него, независимо от новото времево клеймо: новите инсталации прилагат файла на новата му позиция, надстроените бази данни не, така че изберете ново времево клеймо близо до старото. Портата не успява да преименува, ако съдържанието е променено (промяната на схемата все още влиза в нова миграция) или ако целевият файл на записа не е на диска.
- **Никога не преименувайте в рамките на едно и също времево клеймо.** Преименуване, което запазва клеймото за време и променя само описанието, не пропуска портала, със или без запис. С запис, чийто `toVersion` е равен на неговия `fromVersion`, програмата за изпълнение изтрива стария `_omniroute_migrations` ред и прилага файла отново към всяка база данни, която вече го е изпълнявала. Без запис програмата за изпълнение проследява само версията: тя пропуска файла в тези бази данни (новото съдържание никога не се изпълнява там) и регистрира грешка при преномериране при всяко зареждане. Използвайте друго времево клеймо плюс запис за съвместимост или запазете името.
- **Порталът проверява дали преименувания файл не се изпълнява отново.** За всяко покрито преименуване порталът предава новото име на файл към проверката на комутацията с `--must-not-apply`. Проверката зарежда надстроената база данни с истинския бегач и ако бегачът приложи този файл отново (например защото записът има грешна версия или име, или защото текстовият анализатор на портала чете `constants.ts` различно от TypeScript), порталът се проваля с `migration renomeada rodaria de novo` и ви моли да проверите старите и новите версии и имена на записа.

### Какво Gate проверява спрямо базата

При изпълнение на заявка за изтегляне и опашка за сливане, `npm run check:migration-numbering` сравнява `src/lib/db/migrations/` на диск със същата директория в основния клон. Базата е в този ред: `--base-latest-tag`, `--base <ref>`, променливата `MIGRATION_BASE_REF` или, когато `GITHUB_EVENT_NAME` е `pull_request`, `pull_request_target` или `merge_group`, първият родител на ангажимента за сливане, `merge_group.base_sha` на полезния товар на събитието или `git merge-base HEAD origin/$GITHUB_BASE_REF`. При заявка за изтегляне или изпълнение на опашка за сливане без разрешима база, портата се проваля. Извън CI без `--base` отпечатва `comparação com a base: pulada (sem --base)` и пропуска тези правила.

`--base-latest-tag` сравнява с най-новия етикет за издание (`vX.Y.Z` в ред на semver; суфиксирани тагове като nightlies не се броят), който е в историята на `HEAD`, със същите правила като `--base`. Release-Green (`scripts/quality/validate-release-green.mjs`) изпълнява портала по този начин, тъй като push и планираните изпълнения нямат база за заявка за изтегляне и сливането може да се приземи без ново изпълнение CI. Без етикет за освобождаване в хронологията портата се проваля; стартирайте `git fetch --tags` (в CI, `actions/checkout` с `fetch-depth: 0` носи етикетите).

Едно изпълнение на проверката за комутация обхваща заедно неправилните, редактираните и преименуваните файлове.

Проверката на комутацията (`scripts/check/migration-commutation.ts`) изгражда две временни бази данни с реалния път на инсталиране:** обновен** едно (стартиране с базовите миграции, след това стартиране отново на същия файл с миграциите на заявката за изтегляне) и** свежи** едно (едно зареждане с миграции на заявката за изтегляне). Той сравнява получените схеми: таблици и колони (пренебрегвайки реда на колоните), UNIQUE / PRIMARY KEY и FOREIGN KEY ограничения, нормализирания `CREATE TABLE` текст на всяка таблица (който обхваща CHECK ограничения, съпоставки, генерирани колони и опции за таблици), индекси, тригери и изгледи. Данните за ред не се сравняват. Ако те съвпадат, порталът отпечатва, че файлът не е в ред, но се движи и преминава. Ако се различават, порталът се проваля с разликата и подсказка за случая: за файл извън реда, генерирайте повторно името му с `npm run db:new-migration`, което е безопасно, защото файлът все още не е обединен; за редактиран основен файл, възстановете основното съдържание и поставете промяната в нова миграция; за преименуван файл, отменете преименуването или изберете друго ново времево клеймо, където се движи, никога същото времево клеймо с друго име. Ако самата проверка не може да се изпълни, порталът се проваля в CI и предупреждава само локално. За редактиран основен файл, надстроената база данни се изгражда със съдържанието на базата на този файл и второто зареждане го пропуска, защото версията му вече е записана. За преименуван файл, надстроената база данни се изгражда с файла под старото му име и второто зареждане премества неговия `_omniroute_migrations` ред през записа за съвместимост, вместо да го стартира отново; порталът предава новото име с `--must-not-apply`, така че проверката е неуспешна, ако второто зареждане го приложи. Ако миграция на заявка за изтегляне не успее да се приложи по надстроения път, т.е. след всяка базова миграция (независимо дали е неуспешна и при нова инсталация), порталът отчита `migration do PR não aplica` и ви моли да коригирате SQL спрямо текущата схема на базата; ако файлът зависи от друга миграция на заявка за изтегляне с по-късно времево клеймо, регенерирайте името му с `npm run db:new-migration`.

За да изпълните същото сравнение локално, предайте базата изрично, например `npm run check:migration-numbering -- --base origin/<base-branch>` или `npm run check:migration-numbering -- --base-latest-tag` за сравнение с най-новата версия.

### Конвертиране на миграция на `NNN` на Open PR

Заявка за изтегляне, отворена преди превключвателя, все още може да носи последователен файл като `242_add_widgets.sql`. Старите числа над `241` се отхвърлят, така че ги преобразувайте преди сливането:

1. **Преименувайте файла с генератора, като запазите описанието.** Стартирайте `npm run db:new-migration -- <same description>`, за да получите новото име, преместете SQL в него и изтрийте стария `NNN_` файл. Описанието трябва да остане идентично: записът за съвместимост по-долу съвпада с него.
2. **Добавете запис за съвместимост, ако постоянна база данни изпълнява стария номер.** Ако някоя база данни, която се съхранява (хомолог, VPS, собствена инсталация на сътрудник) стартира компилация на PR с `NNN_` файла, добавете `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` към `RENAMED_MIGRATION_COMPATIBILITY` в `src/lib/db/migrationRunner/constants.ts`. Това е** необходимо за `237` до `241`** : тези слотове сега съдържат каноничните `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` и `241_seen_models.sql` и без запис такава база данни пропуска каноничната миграция завинаги и изпълнява преобразуваната отново. Работи и за слот, който остава празен, като например `242`, когато дестинацията е клеймо за време. Когато се съмнявате, добавете записа. Където ще го добавите в масива няма значение: когато целевият слот на запис все още съдържа ред, който друг запис премества (например `237` държи PR ред, докато по-стар `usage_history_calculated_cost` ред чака да се премести в `237`), бегачът оставя този запис да изчака, докато слотът се освободи. Само истински конфликт, като например слот, задържан от ред без влизане, или два записа, които разменят слотовете, спира зареждането с `Cannot reconcile ...`.
3. **Поддържайте SQL идемпотентен** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), защото преобразуваната миграция може да срещне база данни, където нейната схема вече съществува.
4. **Преместване на специални случаи с ключ за версия.** Ако PR добави регистър за стария си номер в `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) или в `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`), променете ключа на новия времеви печат.

`tests/unit/db/codex-fence-migration-rename.test.ts` е работещ пример за тест за преименувана миграция.

### Backports към клонове преди превключването

Никога не избирайте или пренасяйте обратно `YYYYMMDDHHMMSS_` файл към клон, който предшества превключването (например по-стар `release/v*` клон). Изпълнителят там сортира имената на файловете като текст, така че файл с клеймо за време ще се изпълнява между `201_` и `202_` в нова база данни, а старият портал там не разбира 14-цифрени префикси. В такъв клон запишете промяната като собствения следващ `NNN_` файл на този клон, идемпотентен, така че да е без операция, когато версията с клеймо за време пристигне по-късно.

### Как протичат миграциите

При стартиране `migrationRunner.ts`:

1. Създава `_omniroute_migrations` таблица, ако не съществува
2. Заявки за вече приложени миграции
3. Прилага всички нови миграции по ред, всяка в транзакция
4. Записва всяка приложена миграция с клеймо за време

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### Идемпотентност

Миграциите трябва да бъдат** идемпотентен** — да ги изпълнява два пъти трябва да е без операция:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

Използвайте `IF NOT EXISTS`, `IF EXISTS` и `OR IGNORE` / `OR REPLACE` клаузи щедро.

### Добавяне на нова миграция

1. **Създайте файла с генератора** : `npm run db:new-migration -- <description>` (например `npm run db:new-migration -- add combo priority`). Той записва `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` с текущото UTC време и заглавка на коментар, премества се с една секунда напред, ако този времеви печат е взет, и никога не презаписва файл. Не избирайте число на ръка.
2. **Използвайте безопасен DDL** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **Запълнете внимателно данните** : използвайте `UPDATE ... WHERE ...` за обработка на съществуващи редове
4. **Проверете реда и именуването** : `npm run test:migrations:fresh` (всички миграции върху празна база данни) и `npm run check:migration-numbering`
5. **Тест върху копие** : никога не изпълнявайте нетествани миграции в продукцията

Пример:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **Обратно несъвместими промени** (напр. изпускане на колони) са трудни. OmniRoute поддържа ли NOT понижаване на —, след като се приложи миграция, промяната на схемата е постоянна. Планирайте съответно.

## Криптиране на съхраняваните данни

Чувствителните полета (API ключове, OAuth токени, низове за свързване) се съхраняват криптирани чрез **AES-256-GCM**.

### Как работи

```ts
// src/lib/db/encryption.ts (опростено)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### Къде се използва

- `provider_connections.api_key` — криптирано на ниво приложение
- `provider_connections.access_token`, `refresh_token`, `id_token` — криптирани на ниво приложение
- Записите в `key_value` с `namespace = "secrets"` — криптирани на ниво приложение
- `proxy_registry.auth` — криптирано на ниво приложение (ако е налично)

### Ключ за криптиране

Ключът за криптиране се извлича от **парола** (зададена чрез променливата на средата `STORAGE_ENCRYPTION_KEY`) и **salt** (съхраняван в базата данни). И двете са необходими за декриптиране на данните.

```bash
# Генериране на защитена парола
openssl rand -hex 32

# Задаване в .env
STORAGE_ENCRYPTION_KEY=<вашият-ключ>
```

> **Критично важно**: Загубата на ключа за криптиране означава загуба на достъп до всички криптирани данни. **Архивирайте ключа отделно от базата данни**.

### Какво НЕ се криптира

От съображения за производителност следните данни се съхраняват като обикновен текст:

- Показвани имена на доставчиците
- Дефиниции на модели (вече публични)
- Правила за маршрутизиране
- Записи за използването (без лични данни)

## Особености при шифроването (v3.8.16+)

OmniRoute използва **`migrateLegacyEncryptedString()`**, за да обработва прозрачно две схеми за шифроване:

- **Остаряла** (преди v3.5.0): базирано на XOR „шифроване“ (не е истинска криптография)
- **Текуща**: AES-256-GCM с подходящ IV и таг за удостоверяване

Помощната функция за миграция открива остарелия формат и при първото прочитане шифрова повторно данните с новата схема. Това означава, че можете да надстроите стара база данни, без да загубите идентификационните данни.

## Архивиране и възстановяване

### Ръчно архивиране

```bash
# Използвайте CLI, за да създадете локално резервно копие
omniroute backup create --name pre-migration

# Или чрез API
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

Файлът на резервното копие включва:

- Всички таблици на БД (сериализирани в JSON)
- Артефакти от регистъра на извикванията (кодирани с base64, незадължително)
- Настройки + тайни данни (шифровани)
- Конфигурация на приставките

### Възстановяване

```bash
# Чрез CLI
omniroute restore pre-migration

# Чрез API
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **Предупреждение**: Възстановяването презаписва цялата БД. Първо спрете всички клиенти.

### Автоматизирани резервни копия

```bash
# Активирайте автоматизирани ежедневни резервни копия чрез CLI
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

Графикът се изпълнява от страна на сървъра чрез фонова задача, която се задейства на всеки 30 секунди
(по подразбиране) и проверява cron израза спрямо локалното време на сървъра.

| Променлива                                  | По подразбиране | Описание                                                                                                                     |
| ------------------------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`         | Интервал на задействане в ms (мин. `5000`). Трябва да е по-кратък от 60 s, за да попадне надеждно в съвпадащата cron минута. |

### Горещо архивиране на SQLite

За архивиране без прекъсване на работеща БД:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

Това използва API на SQLite за онлайн архивиране — безопасно е да се изпълнява, докато OmniRoute работи.

## Настройка на производителността

### WAL режим

WAL е активиран по подразбиране. За големи работни натоварвания при запис помислете за:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute не задава `journal_size_limit`. Контролна точка премества WAL рамки в основния файл, но WAL файлът запазва най-големия си разпределен размер. Защитата на `OMNIROUTE_WAL_GUARD_MAX_MB` само предупреждава и изпълнява `wal_checkpoint(RESTART)`; това не е ограничение за размера на диска.

### Индекси

Ключови индекси за ефективност (автоматично създадени от миграции):

- `idx_models_provider` — търсене на модели по доставчик
- `idx_combo_targets_combo_id` — комбинирано целево разширение
- `idx_usage_history_api_key_timestamp` — анализ на използването
- `idx_quota_snapshots_api_key_window` — проследяване на квоти
- `idx_call_logs_timestamp` — заявки за регистър на повикванията

За да добавите нов индекс, създайте миграция:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### Карта на паметта I/O

За много големи бази данни (> 10GB), картографирането на паметта може да се коригира чрез SQLite pragma:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### Уплътняване

Дълго работещите OmniRoute екземпляри се възползват от случаен `VACUUM`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

Изпълнявайте месечно по време на прозорци с нисък трафик. (режимът WAL намалява нуждата, но не я премахва.)

## Проверка на изправността

`src/lib/db/healthCheck.ts` предоставя **диагностика на изправността на ниво база данни**:

И двата метода изискват удостоверяване (в противен случай се връща `401`). `GET` извършва само диагностика; `POST` изпълнява
същата проверка с активиран `autoRepair`.

```bash
GET  /api/db/health   # диагностика
POST /api/db/health   # диагностика + поправка
```

Отговорът е `DbHealthCheckResult`, генериран от `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Бюджетите на домейните препращаха към API ключове, които вече не съществуват.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| Поле              | Значение                                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `isHealthy`       | `true`, когато `issues` е празно. `driver` никога не му влияе.                                                                                                                 |
| `issues[].type`   | Една от стойностите `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`.                                                                           |
| `repairedCount`   | Редове, поправени по време на това изпълнение; винаги е `0`, когато `autoRepair` е false.                                                                                      |
| `backupCreated`   | Дали е създадено резервно копие преди поправката.                                                                                                                              |
| `checkedAt`       | Времеви печат във формат ISO, общ за изпълнението и за всяка записана от него бележка за поправка.                                                                             |
| `driver.name`     | Драйверът за SQLite, обслужващ проверяваната база данни.                                                                                                                       |
| `driver.degraded` | `true`, когато записите не се съхраняват устойчиво във файла на базата данни — резервният WASM вариант `sql.js` (устойчиво съхранение на целия файл) или база данни в паметта. |

Същите данни се връщат от MCP инструмента `omniroute_db_health_check`.

Изпълнете `PRAGMA integrity_check`, за да откриете повреда:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# Трябва да изведе: ok
```

Ако върне нещо различно от `ok`, **незабавно спрете да използвате базата данни** и я възстановете от резервно копие.

## Възстановяване след авария

### Сценарий 1: Загубен WAL файл

Файлът `-wal` липсва, но `-shm` и основната база данни са непокътнати:

```bash
# Възстановява се автоматично при следващото отваряне
omniroute
```

Ако SQLite не може да се възстанови автоматично:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### Сценарий 2: Повреден файл на основната база данни

Възстановете от резервно копие:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` само изтегля пълен `.tar.gz` архив от работещ сървър
(`GET /api/db-backups/exportAll`, изискват се идентификационни данни на оператор); командата не възстановява нищо.

### Сценарий 3: Загубен ключ за криптиране

**Възстановяването е невъзможно** без ключа. Криптираните полета не могат да бъдат прочетени. Добавете отново ръчно всички доставчици с нови идентификационни данни.

> **Превантивна мярка**: Винаги архивирайте ключа за криптиране отделно, за предпочитане в мениджър на пароли или KMS.

### Сценарий 4: Пълен диск

SQLite ще върне грешки `SQLITE_FULL`. Освободете дисково пространство, след което изпълнете:

```bash
# Създаване на контролна точка на WAL за освобождаване на място
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## Отстраняване на неизправности

### „Базата данни е заключена“

Друг процес държи заключване за запис. Можете да:

- Изчакате другият процес да приключи (проверете с `lsof | grep storage.sqlite`)
- Прекратите другия процес
- Ако проблемът продължава, рестартирайте OmniRoute

### „Ограничението на външен ключ е нарушено“

Модул на домейна нарушава референтната цялост. Проверете за:

- Осиротели редове в зависимите таблици
- Каскадни изтривания, които не са се разпространили
- Скорошна миграция, която е променила външен ключ

Изпълнете `PRAGMA foreign_key_check;`, за да откриете нарушенията.

### „Недостатъчно памет“

Картографираният в паметта вход/изход на SQLite надвишава ограничението на операционната система. Намалете го чрез pragma на SQLite:

```sql
PRAGMA mmap_size = 134217728;  -- 128MB вместо 256MB
```

Или го деактивирайте:

```sql
PRAGMA mmap_size = 0;
```

### „Миграцията е неуспешна по средата“

Миграцията е изпълнена в транзакция, така че би трябвало да е била отменена. Ако това не е станало:

1. **Спрете OmniRoute** (за да предотвратите допълнителни опити)
2. **Проверете състоянието на БД** със `sqlite3`
3. **Поправете ръчно** частичната миграция
4. **Стартирайте отново** OmniRoute (миграцията ще бъде повторена)

За да предотвратите това, винаги първо тествайте миграциите върху копие.
