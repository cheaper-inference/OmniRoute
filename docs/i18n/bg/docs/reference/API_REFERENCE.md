Основна справка за API на OmniRoute. Тя обхваща публичния интерфейс `/v1` и най-често използваните крайни точки за управление; машинночетимият [`docs/openapi.yaml`](../openapi.yaml) и дървото на маршрутите в `src/app/api/` са изчерпателните източници.

За специализираната матрица на възможностите на съвместимия с OpenAI протокол и доставчици вижте
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md).

Всяко внедряване предоставя собствено копие на спецификацията на адрес `/openapi.yaml`, генерирано от `docs/openapi.yaml` по време на компилацията. То съдържа версията на компилацията и относителен URL адрес на сървъра (`./`), така че заявките да остават на хоста, от който е предоставен документът. Инструмент, който импортира изтегления файл, няма такъв хост и изисква базовият URL адрес да бъде зададен ръчно.

## Чат завършвания

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

#### Фиксиране на акаунт за заявка

Когато доставчикът има няколко връзки (акаунти или ключове), OmniRoute обикновено избира една
чрез своята стратегия за избор на акаунт. Вместо това заявката може да фиксира конкретна връзка
чрез заглавката `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Къде да намерите id.** Отворете страницата на доставчика в таблото
  (**Dashboard → Providers → <provider>**) и щракнете върху чипа с id `xxxxxxxx…` на реда за връзката — това копира пълния id на връзката.
- **Кои заявки го използват.** Заявки към единичен модел (`provider/model`) към
  `/v1/chat/completions`, `/v1/messages` и `/v1/responses`. Комбинациите игнорират заглавката: фиксирайте акаунт за всяка стъпка на комбинацията чрез собствената връзка на стъпката.
- **Фиксирането е строго, а не предпочитание.** Фиксираната връзка се използва изключително. Неуспешна операция в рамките на заявката записва cooldown за акаунта, но **не** преминава към съседен акаунт на същия доставчик.
- **Cooldown и квотата освобождават фиксирането.** Докато фиксираната връзка е в cooldown,
  квотата е изчерпана или връзката е блокирана от политика за квоти, следващите заявки преминават към другите връзки на доставчика, точно както заявките без фиксиране.
- **Непознати или деактивирани id водят до грешка.** Id, който не е в активния пул на доставчика (изтрит, деактивиран или принадлежащ към друг доставчик), не оставя допустим акаунт, така че заявката се проваля, вместо незабелязано да бъде насочена другаде.

Claude Code изпраща персонализирани заглавки чрез `ANTHROPIC_CUSTOM_HEADERS`. Поставете го в блока
`env` на `~/.claude/settings.json` или във файл `.claude/settings.json` на ниво проект, за да фиксирате различен акаунт за всеки проект:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Източник: `src/sse/handlers/chat.ts` (прочитане на заглавката), `src/sse/services/auth.ts` и
`src/sse/services/sessionAffinityPin.ts` (освобождаване на фиксирането и проверка за липсващ елемент в пула).

> **Заглавки за телеметрия на разходите:** отговорите за успешни заявки без streaming също съдържат набора `X-OmniRoute-*` за телеметрия на разходите — `X-OmniRoute-Response-Cost` (USD, фиксирани 10 десетични знака; `0.0000000000` за безплатни/без зададена цена), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` и `X-OmniRoute-Fallback-Attempts` (само когато е > 0), както и `X-OmniRoute-Request-Id` и `X-OmniRoute-Version`. Те се генерират от chat completions, `/v1/responses`, `/v1/messages` **и крайните точки за медия** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` и `/v1/moderations` (винаги с разход `0`). Разходът за медия се изчислява според типа медия (на изображение, на секунда, на символ, на единица за търсене), когато има налична информация за ценообразуването, в противен случай е `0` (fail-open).

> **Семантика на разходите при попадение в кеша:** при HIT на семантичния кеш (`X-OmniRoute-Cache-Hit: true`) не се извършва upstream извикване, така че `X-OmniRoute-Response-Cost` е `0.0000000000` (това е **добавъчният** разход за обслужване на попадението). Оригиналният/предполагаемият разход се отчита отделно в `X-OmniRoute-Cost-Saved`. Потребителите на данни за таксуване трябва да сумират `X-OmniRoute-Response-Cost` (попаденията не струват нищо); анализите на кеша могат да агрегират `X-OmniRoute-Cost-Saved`.

## Ексклузивен лизинг на управлявани сесии

Ексклузивният лизинг на управлявани сесии е договор за маршрутизиране, активиран по избор и независим от клиента: един активен собственик държи една допустима връзка към OmniRoute. Той не отдава модел под лизинг, не изисква OAuth, не идентифицира конкретен клиент и не изисква конкретен доставчик.

API ключът за удостоверяване трябва да има обхват `lease:exclusive` и изричен непразен списък
`allowedConnections`. Границата на мутацията в базата данни налага и двете полета заедно при
създаване на ключ и частични актуализации.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успешните отговори при придобиване, подновяване и освобождаване показват времеви отметки, `state` и
точното положително `generation`, но никога не показват избраната връзка или идентификационни данни. При подновяване и освобождаване `generation` се подава в JSON тялото:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Активният собственик на лиза може изрично да поиска безопасни за поверителността метаданни за показване на текущото си обвързване:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Това действие за включване по избор е защитено от непрозрачния собственик, удостоверения
управляван API ключ и точното активно поколение в рамките на една транзакция в базата данни. `displayName` е само отрязаното име на конфигурираната връзка; то е `null`, когато не съществува безопасно конфигурирано име. OmniRoute никога не замества това име с имейл или генерирана идентичност на акаунт. Стойността на доставчика е нечувствителен етикет за показване и никога не е генериран идентификатор на съвместим доставчик. Идентификационни данни, токени, бисквитки, необработени идентификатори на връзки или API ключове, хешове на собственици, тайни за ограждане и вътрешни данни за маршрутизиране са изключени.

Погрешен ключ, погрешен собственик, остаряло поколение, липсващи, изтекли, освободени и
инвалидирани търсения връщат една и съща грешка `409 LEASE_FENCE_STALE` без метаданни за връзката. Клиент, получил отговор за изчакване на капацитет, няма активно обвързване, което да инспектира. Когато маршрутизирането промени активен лиз, същото поколение остава валидно и статусът атомарно връща новото обвързване, никога старото. Съществуващите клиенти остават непроменени, защото отговорите при придобиване, подновяване, освобождаване и изчакване запазват предишните си форми.

Този договор на сървъра не променя стандартния OpenAI Codex `/status`. Понастоящем стандартният Codex отчита своя доставчик на модела и вграденото състояние на удостоверяване/акаунт, но не визуализира произволни метаданни за акаунта на персонализиран доставчик; по-късна клиентска интеграция трябва да извика това действие и да реши как да показва `connection.displayName`.

Всяка управлявана заявка за извеждане след това подава и двете контролни заглавки:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точните собственик, поколение, активна връзка и удостоверен API ключ се проверяват непосредствено
преди всеки поддържан опит към upstream. Повторното използване на собственик и поколение с друг ключ се проваля, дори когато този ключ разрешава същата връзка. Необработените собственици не се съхраняват, записват в журнал, запазват в моментната снимка на заявката или препращат към upstream.

Временната конкуренция връща HTTP `429` с `Retry-After` и:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Този отговор означава само, че обичайният допустим набор не е бил празен и всяка свободна кандидат-връзка е била задържана от чужд активен лиз. Неподдържаните модели/доставчици, несъответствието с политиката, периодът на охлаждане, квотата, състоянието и други обичайни причини за недопустимост запазват съществуващите си отговори на OmniRoute.

### `x-omniroute-compression`

Замяна на плана за компресиране за отделна заявка. С най-висок приоритет — има предимство пред замяната на комбинацията за маршрутизиране, активния профил, автоматичното задействане и Default в панела. Стойности:

| Стойност      | Ефект                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------ |
| `off`         | Без компресиране за тази заявка.                                                                             |
| `default`     | Профилът Default, извлечен от панела (игнорира активния профил). Загубните енджини остават изключени.        |
| `safe`        | Само премахване на дубликати и обединяване на интервали.                                                     |
| `allow-lossy` | Запазва операторския план за тази заявка, включително обобщения и пренаписвания на стила.                    |
| `engine:<id>` | Един енджин, когато е активиран, например `engine:rtk`. Включване по избор на този енджин за отделна заявка. |
| `<combo>`     | Именувана комбинация, съпоставена първо по име (без значение от регистъра), след това по id.                 |

Бележки:

- Непознатите стойности се игнорират (заявката никога не се отхвърля); разрешаването преминава към нормалния приоритет на оператора.
- Ако няколко комбинации споделят едно име, подайте **id** на комбинацията за детерминирано съвпадение.
- Комбинация, чието име е `off` или `default`, не може да бъде избрана по име (тези ключови думи се интерпретират първи); посочете такава комбинация чрез нейното id.
- Главният превключвател за компресиране е строго ограничаващ: когато компресирането е глобално изключено, това заглавие не може да го включи.

Приложеният план се връща в заглавката на отговора:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

където `<source>` е едно от `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Ембединг вектори

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Налични доставчици: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Идентификаторите в каталога са във формат `provider/model` (пример: `jina-ai/jina-embeddings-v5-omni-small`). Неукрасени идентификатори на модели на Jina, които присъстват в регистъра (например `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), също се разрешават. Jina embed/rerank/classify/segment първо използват идентификационните данни `jina-ai` от таблото; `JINA_AI_API_KEY` е резервен вариант само когато няма ключ от таблото. Картата `jina-reader` е предназначена само за Reader / `r.jina.ai` (`POST /v1/web/fetch`) и никога не предоставя embeddings или rerank.

Моделите от регистъра, които обявяват поддръжка на мултимодалност, приемат и до 32 структурирани елемента, независими от доставчика. Типовете медийни елементи са `text`, `image`, `audio`, `video` и `document`. Техният `source` е или `{"type":"url","url":"https://..."}`, или
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
и фамилният псевдоним `jina-ai/jina-embeddings-v5-omni` → omni-small) приема и собствената
документация за EmbeddingsV5Request на Jina и ги **препраща непроменени** към `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Собствените стойности `{ image | audio | video | pdf }` могат да бъдат публичен HTTPS URL, `data:` URI или необработен
base64. OmniRoute не преобразува тези обекти в низове и не извлича собствени URL адреси на изображения — Jina извлича
публичните медии самостоятелно. Допълнителните полета на Jina (`task`, `normalized`, `truncate`, `embedding_type`) се
препращат. Jina SKU, предназначени само за текст, продължават да отхвърлят документи, които не са текстови.

Ограничения за сигурност и пренос:

- URL адресите към отдалечени медии трябва да са публични HTTPS адреси. Каноничните елементи `{type,source:url}` се извличат
  от страна на сървъра (повторна проверка на пренасочванията, ограничение на времето, ограничения на размера, публичен DNS, фиксиране на връзката) и се вграждат преди извикването към доставчика. Собствените за Jina елементи `{image:"https://..."}` се препращат както са след същата проверка за публичен HTTPS; Jina извлича URL адреса.
- Вградените base64 медии са ограничени до 8 MiB декодирани данни на елемент и 16 MiB декодирани данни за цялата заявка.

Превод към доставчика (каноничните елементи никога не се препращат непроменени):

- Мултимодални модели на Jina: всеки елемент от най-горното ниво се превръща в един обект, чийто ключ е съответният тип
  (`text` / `image` / `audio` / `video` / `pdf`), като за вградените медии се използват URI адреси за данни; по един вектор за
  всеки елемент от най-горното ниво.
- Фамилията Gemini Embedding 2: един масив от най-горното ниво се превръща в една собствена заявка
  `models/{model}:embedContent` с `content.parts` (`text` или `inline_data`).
- llama.cpp (`llama-cpp/<model>`, всеки модел, зареден от локалния сървър): каноничните елементи `text`
  се превръщат в обикновени низове, а `image` / `audio` / `video` се превръщат във всеки по един обект
  `{"content": [part]}`, като се използват частите за съдържание на chat на llama-server (`image_url`,
  `input_audio` с формат `wav` / `mp3` / `flac`, `input_video`) с вградени данни; по един вектор за всеки елемент от
  най-горното ниво. Сървърът трябва да работи с `--embedding --mmproj …`; без проектор той сам отхвърля медията. `document` не се поддържа.
- Неизвестните/динамичните модели без изрични метаданни за модалност отхвърлят структурирани входни данни с HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Неподдържаните комбинации от модел/модалност връщат HTTP 400, вместо да преобразуват елемента. Полетата за разширение, които не са входни, при заявки от стария формат със низове/токени продължават да се препращат непроменени.

```bash
# Изброяване на всички модели за embeddings
GET /v1/embeddings
```

## Генериране на изображения

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Наличните доставчици включват OpenAI (GPT Изображение 2), xAI (Grok Изображение), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana,**OpenRouter** ,**ZenMux** , SD WebUI (локален), ComfyUI (локален).

`n` връща `n` изображения в `data[]`. Доставчиците, чийто API нагоре връща едно изображение на повикване (Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik, NVIDIA NIM, Cloudflare Workers AI), получават `n` отделни повиквания нагоре, най-много 4 в полет. Фиксираният `seed` се компенсира от индекса на повикване (`seed`, `seed + 1`, …), така че изображенията се различават, но остават възпроизводими. `n` е ограничен до 10. Заявката е неуспешна като цяло, ако някое извикване е неуспешно. Списъкът с разклонени формати е `SINGLE_IMAGE_FANOUT_FORMATS` в `open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux използва повторно съществуващата връзка с API ключ и приема `zenmux/` или `zm/` префикси:

- `zenmux/openai/gpt-image-2` използва ZenMux изображенията на OpenAI API. Опциите включват `size`, `quality`, `n`, `output_format`, `output_compression`, `background` и `response_format`.
- Други издатели, като `zm/meta/muse-image-1.0`, използват крайната точка Vertex AI `:predict` на ZenMux. `n` се преобразува в `sampleCount`, `aspect_ratio` в `aspectRatio` и `image_size` (`1K`, `2K`, `4K`) в `sampleImageSize`. Пикселът `size` предоставя само съотношение на страните, а не гарантирани размери на пикселите. Поддържаните съотношения, разделителни способности и броя варират според модела.
- `zm/inclusionai/ming-image-0.1-design` избира свои собствени размери. Пропуснете `size`, `aspect_ratio` и `image_size`; изричните стойности връщат HTTP 400. PNG, JPEG и WebP могат да бъдат поискани с `output_format`.

Тази интеграция поддържа генериране на текст към изображение, а не редактиране на референтно изображение. Изходът на Vertex се нормализира към `data[].b64_json`; `response_format: "url"` връща upstream HTTPS URL или base64 данни URL когато са налични само байтове за изображение. Empty/filtered изходите връщат грешка, а не празен успех. Достъпът до модела зависи от ZenMux акаунта. Вижте [ZenMux's Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) и [OpenAI Изображения API](https://docs.zenmux.ai/api/openai/generate-an-image).

Връзка за влизане Microsoft 365 Copilot обслужва `copilot-m365-web/m365-copilot-image` чрез вградения инструмент за изображения Copilot: едно Copilot завъртане на изображение (`n` 1–4), `size` управлява само ориентацията и изображенията се връщат вградени (`b64_json` или данни URL за `response_format: "url"`). Вижте [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# List all image models
GET /v1/images/generations
```

## OCR на документи

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` избира OCR доставчика чрез префикс `provider/model`; самостоятелен идентификатор на модел (напр.
`mistral-ocr-latest`) се насочва към регистрирания му доставчик, а ако `model` е пропуснат, по подразбиране се използва
Mistral (`mistral-ocr-latest`). Регистрирани доставчици (`open-sse/config/ocrRegistry.ts`):

| Идентификатор на доставчика   | Идентификатор на модела | Стойност на `model`                                                   | Бележки                                                                                                              |
| ----------------------------- | ----------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest`    | `mistral/mistral-ocr-latest` (или самостоятелно `mistral-ocr-latest`) | Синхронен — отговорът се връща директно от единственото upstream извикване.                                          |
| `azure-document-intelligence` | `prebuilt-read`         | `azure-document-intelligence/prebuilt-read`                           | Асинхронен upstream (`analyze` + poll) — вижте по-долу.                                                              |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`     | `vertex-deepseek-ocr/deepseek-ocr-maas`                               | Синхронен, чрез партньорския endpoint `openapi/chat/completions` на Vertex AI — вижте по-долу за удостоверяване/URL. |

И трите доставчика отговарят с тяло в същия формат като Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процес на изчакване при Azure Document Intelligence

API на Azure Document Intelligence за `analyze` е асинхронен: първоначалната заявка връща
заглавка `Operation-Location` вместо тяло, а резултатът трябва да бъде извлечен чрез периодични заявки. Обработчикът
(`open-sse/handlers/ocr.ts`) изпраща заявка към този URL всяка секунда за до 30 опита, прекратява незабавно (не
продължава да изпраща заявки) при отговор от извикването за проверка, който не е `ok`, или при статус `"failed"`, и връща `504`, ако
операцията все още се изпълнява след изчерпване на бюджета от опити. Крайният отговор от Azure се
нормализира до същата форма с `pages`/`markdown`, използвана от Mistral, преди да бъде върнат на
извикващия, така че клиентският код не трябва да обработва доставчика по специален начин.

### Удостоверяване и разрешаване на endpoint за Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` използва повторно същото удостоверяване на Vertex AI, което OmniRoute вече поддържа за
трафик към чат/изображения (`open-sse/executors/vertex.ts`): API ключът на връзката е или
идентификационни данни на Service Account във формат JSON (обменени за краткоживеещ OAuth access token чрез потока
JWT-bearer), или вече издаден OAuth access token, който се използва както е. URL адресът на upstream endpoint-а е общият
партньорски endpoint `openapi/chat/completions` на Vertex, изграден от проекта и региона на връзката — изричните
`providerSpecificData.project`/`providerSpecificData.region` винаги имат предимство;
в противен случай проектът се извлича от `project_id` в JSON данните на Service Account, а регионът по подразбиране е
`us-central1`. И двете разрешавания се извършват в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), а резултатите им се използват от
`src/app/api/v1/ocr/route.ts` преди изпращане към `handleOcr`.

### Цени на моделите (`pricing`)

Един запис съдържа обект `pricing`, когато OmniRoute знае цената на модела. Цената идва
от таблицата с цени, която се използва за отчитане на разходите: вградени стойности по
подразбиране, синхронизирани цени и замествания, зададени чрез `/api/pricing`. Това са
каталожни цени, така че при доставчиците с абонамент също се показва цена на токен.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Полета                                                          | Единица                     | Бележки                                                                                                                                                   |
| --------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD на токен, десетичен низ | Съвместими с OpenRouter, никога в експоненциална нотация. Двете полета за кеш се появяват само когато има цена за кеширане.                               |
| `input`, `output`, `cached`, `cache_creation`                   | USD на 1 млн. токена, число | Полета от по-ранни версии на каталога, запазени за съществуващи клиенти. `reasoning` и `long_context` също се появяват, когато редът с цената ги съдържа. |

- **Комбинациите** съдържат цената на първата си видима цел. Вградените комбинации `auto/*`
  избират цел по време на заявката, затова нямат `pricing`.
- **Безплатните модели** показват `"0"` (и `0`), когато цената им е нула. Модел без ред с
  цена също показва `"0"`, когато каталогът го обозначава като безплатен (`free: true`) или
  вграденият каталог на безплатните модели го съдържа.
- **Неизвестна цена:** записът няма ключ `pricing`.
- **Доставчиците с таксуване според кредитите** (като Kiro) таксуват на заявка, а не на токен.
  Техните записи запазват наличните преди числови полета на 1 млн. токена и не съдържат
  низови полета за цена на токен.
- **Вариантите** (идентификатори за усилие при разсъждение, псевдоними без мислене, огледални
  записи за откриване и шлюзове) копират цената на модела, към който насочват.
- Полетата съдържат само базови ставки. Нивата за дълъг контекст (числовото поле
  `long_context`) и множителите за ниво на услугата (например Codex fast или flex) не
  променят `prompt` или `completion`.
- Обектът е един и същ за всеки стил на удостоверяване, включително заявка в стил Anthropic
  с `x-api-key` и `anthropic-version` (отговорът остава `{ "object": "list",
"data": [...] }`). Реализация: `src/app/api/v1/models/catalogPricing.ts`.

### Префикси на идентификаторите на моделите (`?prefix=`)

Повечето модели се рекламират под **префикс на доставчика**. Кой префикс ще получите се
управлява от feature флага `MODELS_CATALOG_PREFIX_MODE` и може да бъде заменен **за всяка
заявка** чрез параметър на заявката — полезно е за клиент, който иска чист списък, без да
променя общосървърната настройка за всички останали:

```bash
GET /v1/models?prefix=alias        # един идентификатор на модел — префиксът на краткия псевдоним
GET /v1/models?prefix=dual         # двете форми (подразбирана настройка на сървъра)
GET /v1/models?prefix=canonical    # само пълният префикс на идентификатора на доставчика
```

| Режим       | Извежда                                                 | Бележки                                                                                                                                                                                                                           |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **и** `claude/claude-sonnet-4-6` | **По подразбиране.** И двата идентификатора насочват към един и същ модел; запазени са, за да продължат да работят конфигурациите на клиенти, в които е зададена твърдо някоя от двете форми. Каталогът приблизително се удвоява. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Един запис на модел. Доставчиците без отделен псевдоним също извеждат своя запис, така че нищо не се губи.                                                                                                                        |
| `canonical` | `claude/claude-sonnet-4-6`                              | Един запис на модел под пълния префикс на идентификатора на доставчика. Доставчиците без отделен псевдоним (напр. `antigravity/…`, `agy/…`) също извеждат своя единичен идентификатор тук, така че нищо не се губи.               |

Огледалният запис в режим `dual` може да бъде разпознат и без параметъра на заявката: той
съдържа поле `parent`, сочещо към основния идентификатор.

Клиентите, които визуализират инструмент за избор на модел, трябва да заявят
`?prefix=alias` — това прави [разширението OmniCopilot за VS Code](../guides/VSCODE-COPILOT.md).

### Филтри за откриване (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` приема допълнителни филтри за откриване. Без нито един от тях отговорът е
непроменен. Те ограничават каталога, който извикващият вече вижда (правата на API ключа се
прилагат първо), и се изпълняват преди странирането в стил OpenAI чрез `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # всяка посочена възможност трябва да е true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` в каталога; редовете без такъв са `chat`
GET /v1/models?q=sonnet&limit=10                           # съвпадение без значение от регистъра по id или name
```

| Параметър     | Стойности                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | неотрицателно цяло число, сравнено с `context_length`                                               |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 знака                                                                                         |

Непозната стойност или `min_context`, който не е неотрицателно цяло число (например `1.5`),
връща HTTP `400`, а съобщението изброява валидните стойности. Реализация:
`src/app/api/v1/models/catalogFilters.ts`.

### Кратък списък с модели (`POST /v1/models/query`)

`POST /v1/models/query` връща кратък, детерминиран списък от същия каталог със същото
удостоверяване и видимост за всеки ключ като `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Всички полета са незадължителни. `capabilities` и `exclude` приемат масив или низ,
разделен със запетаи; `max_output` се сравнява с `max_output_tokens`. Резултатите се сортират
по `owned_by`, след това по `id`. `limit` по подразбиране е `20`, а стойностите над `100` се
ограничават до `100`. Невалиден JSON, непознато поле или невалидна стойност връща HTTP `400`.

### Индивидуално скрити chat модели

Модел, маркиран като **Скрит** на страницата на своя доставчик, се изключва от каталога и
при изрично заявяване се отхвърля с HTTP `404` / `model_not_found`. Проверката използва
разрешения доставчик и модел, включително псевдонимите на доставчици, префиксите на възлите
на съвместимите доставчици и настройките по подразбиране на връзката. Комбинация пропуска
скритите цели и може да използва видим близък модел; когато не остане изпълнима цел, тя
връща същия код на грешка. Премахването на скриването влиза в сила при следващата заявка.
Заместителите на видимостта само за изображения не скриват chat модела със същия ID.

Тази индивидуална настройка на модела е отделна от
[списъците с разрешени/забранени модели за показване](../routing/MODEL_EXPOSURE_LIST.md), които
филтрират рекламата на каталога и кандидатите за автоматично маршрутизиране, като същевременно
запазват изричното разпределяне. Разрешенията за модели на API ключа продължават да се прилагат
независимо. Режимът на префикса на каталога по подразбиране остава `dual`.

### Варианти на моделите без мислене

За моделите Claude, поддържащи мислене, `/v1/models` също обявява вариант **без мислене**,
чийто id е с префикс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Избирането на този id (например в конфигурация на Claude Code, която винаги добавя блок
`thinking`) разрешава обратно към реалния `<provider>/<model>` с потиснато разсъждение —
`thinking:{type:"disabled"}` по пътя `/v1/messages` или с премахнати полета
`reasoning`/`reasoning_effort` по пътя `/v1/chat/completions`. Вариантът се изброява само за
модели от семейството Claude, които поддържат мислене **и** приемат `disabled` (така например
моделите само с адаптивен режим, които отхвърлят `disabled`, се изключват). Операторите могат
да включат или изключат варианта за всеки модел чрез `ModelSpec.noThinkingAlias`.

## Генериране на аудио с ElevenLabs

Конфигурирайте връзка с доставчика `elevenlabs` в OmniRoute с вашия API ключ за ElevenLabs.
Клиентите се удостоверяват с техния ключ за **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюзът подава съхранения ключ на доставчика като `xi-api-key`. Никога не изпращайте ключ за ElevenLabs
като bearer токен на шлюза.

| Метод | Път                         | Отговор                                        | Категория на крайната точка за API ключ |
| ----- | --------------------------- | ---------------------------------------------- | --------------------------------------- |
| POST  | `/v1/sound-generation`      | Собствени аудио байтове                        | `elevenlabs`                            |
| POST  | `/v1/music`                 | Собствени аудио байтове                        | `music`                                 |
| POST  | `/v1/music/stream`          | Потокови аудио байтове                         | `music`                                 |
| POST  | `/v1/music/detailed`        | Собствено multipart аудио и композиционен план | `music`                                 |
| POST  | `/v1/music/detailed/stream` | Собствени SSE метаданни и аудио фрагменти      | `music`                                 |
| POST  | `/v1/music/plan`            | JSON композиционен план                        | `music`                                 |

Тези крайни точки допълват съществуващите маршрути `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` и `/v1/speech-to-text`. Собствените JSON полета
и параметри на заявката, като `output_format` и `enable_logging`, се запазват.
Отговорите на `/v1/music/detailed` запазват своите multipart граници; анализирайте ги като multipart.
`/v1/music/detailed/stream` връща `text/event-stream` с метаданни за композицията и
base64 аудио фрагменти в SSE събития. И шестте маршрута поддържат CORS preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Кратък звуков ефект. Продължителност: 0.5 до 30 секунди.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Продължителността на музиката се задава в милисекунди: 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Използвайте `/v1/music/stream` със същото JSON тяло за постепенно предаване на аудио. Композицията
приема точно едно от `prompt` или `composition_plan`; `/v1/music/plan` изисква `prompt`
и по избор приема `source_composition_plan`. Собствените схеми запазват допълнителни
полета на доставчика, така че версиите на композиционния план и опциите за фина настройка
да достигат до ElevenLabs.

Унифицираната крайна точка `/v1/music/generations` също приема
`elevenlabs/music_v1`, `elevenlabs/music_v2` и `elevenlabs/music_v2_5`. При активна връзка с ElevenLabs
тези модели се предоставят в музикалния каталог. Тази крайна точка връща
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Полето `duration` е в
секунди и се преобразува към `music_length_ms`; изрично зададеното `music_length_ms` има предимство.
`instrumental` се преобразува към `force_instrumental`, като собственото поле има предимство.
Използвайте собствените потокови крайни точки за поточно предаване и собствената крайна точка за композиция
при заявки, управлявани единствено от композиционен план.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ограниченията за крайната точка, модела, бюджета и връзката се прилагат преди извикване към upstream.
Собствените маршрути връщат статус кодовете и телата на грешките от upstream без промяна, включително
`402` за ограничение на плана и `429` за ограничение на квотата. Заглавките `character-cost`, `song-id`, `request-id` и `retry-after`
се запазват, когато са налични. Наличният безплатен кредитен баланс не гарантира достъп до всеки
музикален модел, изходен формат или API функция: ElevenLabs определя правата за достъп за всяка заявка.
Унифицираната крайна точка запазва статус кодовете на грешките в нормализирания плик за грешки на OmniRoute.

Договори с upstream: [звукови ефекти](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[музикална композиция](https://elevenlabs.io/docs/api-reference/music/compose) и
[подробности за потокова музика](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

За клиенти, които не могат да добавят `Authorization: Bearer ...`, OmniRoute приема API ключове и в URL чрез съвместимост с query string (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) или чрез специалните крайни точки `/api/v1/vscode/{token}/...`, описани по-долу.

```bash
# Повторно класиране (доставчик от облачния регистър или възел на доставчик, съвместим с OpenAI, като "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Класифициране с Jina (идентификационни данни за Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Сегментатор на Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Търсене с Jina (s.jina.ai; псевдоними на доставчика: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Модериране
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — връща тяло audio/mpeg (или заявения формат)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS изисква език и глас: `language` по подразбиране е "en"; липсващ
# глас или стандартно име на глас на OpenAI (alloy, nova, …) се преобразува в "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Редактиране на изображение (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генериране на видео / музика (идентификатор на модел с префикс на доставчика)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Пренасочване на възли на доставчици:** `POST /v1/rerank` също маршрутизира към съвместими с OpenAI възли на доставчици
> (oMLX, vLLM, Infinity, TEI зад gateway, …), адресирани като `<node-prefix>/<model>`. Loopback
> възлите (`localhost`, `127.0.0.1`, `172.16.0.0/12`) винаги са допустими, както и имената на хостове,
> посочени от оператора в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (например име на Docker/Compose услуга,
> като `http://reranker:8080/v1`; те се извикват директно, никога чрез `HTTP(S)_PROXY` или чрез фиксирания proxy на дадена
> връзка). Възли на всеки друг хост — LAN машина или Tailscale peer — са допустими само когато операторът активира
> feature flag-а `RERANK_REMOTE_PROVIDER_NODES` **и** базовият URL на възела преминава политиката за изходящи URL адреси на доставчици
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Стъпката за rerank на memory engine извиква този маршрут чрез loopback, така че същото правило важи за
> `rerankProviderModel` в настройките на Memory.
>
> **Форми на локалния сървър:** възелът се извиква на `<base>/v1/rerank`, а при 404 — на `<base>/rerank`
> (Infinity, TEI). Тялото към upstream съдържа и двата варианта на изписване — Cohere/OpenAI (`documents`,
> `return_documents`) и TEI (`texts`, `return_text`), а отговорът от upstream се нормализира до envelope-а на Cohere:
> необработеният масив на TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> от опростени gateway-и и подобният на Voyage `{data: [...]}` се връщат към клиента като
> `{results: [{index, relevance_score, document?}]}`, сортирани по score и ограничени до `top_n`.

> **Откриване на възли на доставчици:** моделите на съвместим с OpenAI възел на доставчик се показват в `GET /v1/models`
> под префикса на възела. Редовете без метаданни за endpoint (типично за локални списъци `/v1/models`)
> наследяват неговия `apiType`, така че моделите на възел `embeddings` са с
> `type: "embedding"`, а моделите на възел `rerank` са с `type: "rerank"`, вместо по подразбиране да се считат за chat;
> изрично зададеното `supportedEndpoints` в синхронизиран или ръчно добавен ред все пак има предимство.

## Търсете API

абстракция на доставчик Web/search (Tavily, Brave, Exa, Serper и др.).

| Метод | Пътека                 | Описание                                                                                        |
| ----- | ---------------------- | ----------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | Избройте конфигурирани доставчици на търсене + възможности                                      |
| POST  | `/v1/search`           | Изпълнете заявка за търсене — тяло, валидирано от `v1SearchSchema`, поддържа caching/coalescing |
| GET   | `/v1/search/analytics` | hit/latency/cache статистика за всеки доставчик                                                 |

**Удостоверяване:** Носител API ключ (`extractApiKey` + `isValidApiKey`). Политика за търсене, наложена чрез `enforceApiKeyPolicy`.

**Автоматичен избор:** без `provider`, най-евтиният доставчик с конфигурирана връзка работи първи, а следващият най-евтин е файлоувърът. Безплатни доставчици от последна инстанция (`duckduckgo-free`) се използват само когато нищо друго не е конфигурирано. Самостоятелно хостван SearXNG се счита за конфигуриран, след като връзката му съхрани реален `baseUrl` (а не каталожния `http://localhost:8888/search` по подразбиране): след това той се класира като $0 доставчик пред ключовите, като най-евтиният ключов доставчик е преходен, включително когато SearXNG отговаря на 400, 401, 403 или 404. `baseUrl` който не е валиден `http(s)` URL или който сочи към адресът на облачни метаданни не се брои. SearXNG връзка, която съхранява токен, се класира по този начин само пред `https://` или loopback `http://`. Над отдалечен обикновен `http://` никога не е преход при срив и остава последна мярка, използвана само когато не е конфигуриран друг доставчик или когато е поискано по име, така че изпраща токена в чист текст в тези два случая.

### `provider_options` за Exa и Tavily

Exa и Tavily прочитат специфичните за доставчика полета от именувана колекция:
`provider_options.exa` (или `provider_options["exa-search"]`) и `provider_options.tavily`
(или `provider_options["tavily-search"]`). Само посочените по-долу ключове се предават нататък. Всеки от тях се
проверява спрямо собствена Zod схема в `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ с неправилен тип се премахва. Всеки друг ключ се игнорира, включително удостоверяване, базов URL,
`stream` и `outputSchema`. Плоските ключове, използвани от други доставчици (`cx`, `depth`, ...), работят както досега.

| Доставчик | Полета от най-високо ниво                                                                                                                                                                                                                                                                                                                                                 | Вложени                                                                                                                                     |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоски примитиви), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` се сливат с подразбираното `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                           |

Общите полета винаги имат предимство: `query`, `max_results`, `filters` (домейни), `country` и темата,
изведена от `search_type`. При Exa `search_type: "news"` запазва `category: "news"`.
Tavily също приема `search_type: "finance"` (`topic: "finance"`).

Разходът за търсене във Firecrawl се отчита за всеки започнат блок от 10 върнати резултата на цена от $0.002 (2
кредита) за блок и минимум един блок за извикване
([таксуване на Firecrawl](https://docs.firecrawl.dev/billing)): 11 резултата струват $0.004.

Общият `time_range` вече достига и до двата доставчика: Exa получава `startPublishedDate` (ISO клеймо за време),
а Tavily получава `start_date` (`YYYY-MM-DD`). Изрично зададена дата в `provider_options`
заменя преобразуваната дата.

Резултатите от Exa запазват `id`, `highlights` (всеки highlight, а не само първия, използван като
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` и `extras` в
`provider_raw`. Резултатите от Tavily запазват `images` и `favicon`.

Разходът за търсене в Linkup се отчита като $0.005 при `depth` `fast` и `standard` и като $0.05 при
`deep` ([цени на Linkup](https://docs.linkup.so/pages/documentation/development/pricing)),
независимо дали `depth` идва от `provider_options` или от настройките на връзката.

Exa `type: "lite"` (Exa 3.0) приема по-малък набор от полета и отхвърля цялата заявка, когато е зададено друго поле.
При lite `additionalQueries`, `systemPrompt` и всеки ключ в `contents`, с изключение на `text` и `highlights`, се премахват преди извикването. Отхвърлените
`subpages`, `subpageTarget`, `highlights.numSentences` и `highlights.highlightsPerUrl` вече не се предават.

Exa: $0,007 на повикване за `auto` (и наследеното `fast`) или $0,004 за `lite` (и наследеното `instant`), покриващи 10 резултата; $0,001 за всеки следващ резултат; и $0,001 за върнат резултат, когато е зададен `contents.summary`. Tavily се записва на 1 кредит ($0,008) за `search_depth` `basic`, `fast` и `ultra-fast` и 2 кредита ($0,016) за `advanced` ( [Tavily API кредити](https://docs.tavily.com/documentation/api-credits) ). Обаждане с `auto_parameters: true`, което Tavily надгражда до напреднал, все още се записва на 1 кредит.

## API за извличане от уеб

Извличайте съдържание от URL чрез конфигуриран доставчик за извличане от уеб (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, със същия API ключ като Parallel Search) връща само Markdown — всеки друг
`format` води до `400` — и ограничава съдържанието до 100 000 знака. Когато самата целева страница не може да бъде извлечена, upstream услугата съобщава това в HTTP 200;
OmniRoute го представя като `422` с фиксирано съобщение.

| Метод | Път             | Описание                                                         |
| ----- | --------------- | ---------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Извлича/обработва URL — тялото се валидира от `v1WebFetchSchema` |

**Удостоверяване:** Bearer API ключ (`extractApiKey` + `isValidApiKey`). Политиката се прилага чрез `enforceApiKeyPolicy`.

**Резервен вариант, съобразен с квотата (#8297):** когато не е зададен изричен `provider`, пулът
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) се
обхожда във фиксиран
ред на приоритет (fill-first) — доставчик, конфигуриран, но ограничен по честота, се пропуска,
вместо заявката да бъде прекратена веднага, а неуспешна upstream заявка, която може да бъде повторена/е свързана с квота
(HTTP 429 винаги; 402/403 за безплатни нива на Firecrawl/Tavily/TinyFish със стил на квота —
но не и за Jina Reader, и никога за обикновена 400 грешка при невалидна заявка) преминава към
следващия неизпробван удостоверен доставчик по време на заявката. Когато всеки доставчик в
пула е изчерпан, крайната точка връща единен `429` (с хедър `Retry-After`), вместо предишния общ `400`. Когато е заявен изричен `provider`, няма тих резервен вариант — ограничен по честота или неуспешен изричен доставчик показва собствената си грешка (`429` при ограничение по честота, иначе upstream статуса).

## Поточно предаване чрез WebSocket

```bash
GET /v1/ws?handshake=1
```

Валидира handshake за надграждане до WebSocket и връща примерните съобщения на протокола по кабела (`request`, `cancel`). Действителните WS рамки се обработват от включения WS сървър извън таблицата с маршрути на Next.js.

**Удостоверяване:** Bearer API ключ по време на handshake.

### Responses API чрез WebSocket (само codex)

```bash
# Същият host:port като HTTP API (по подразбиране 20128); надградете връзката:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (или: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Първата рамка ЗАДЪЛЖИТЕЛНО трябва да бъде response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Прокси за Responses-API-over-WebSocket е свързан **изключително с `codex`** (backend на ChatGPT). Той слуша на същия порт като API/dashboard по пътищата `/v1/responses`,
`/responses` и `/api/v1/responses`. При първата рамка `response.create` той се удостоверява и подготвя чрез вътрешния мост `codex-responses-ws`, избира OAuth връзка за codex и тунелира към
`wss://chatgpt.com/backend-api/codex/responses` чрез транспорта `wreq-js`. **Модели, различни от codex, се отхвърлят** (`codex_ws_provider_required`).
За маршрутизиране чрез споделяне на квота използвайте `model: "qtSd/<group>/codex/<model>"`. Реализирано е в
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Удостоверяване:** Bearer API ключ по време на handshake. Включеният HTTP сървър (`server-ws.mjs`)
трябва да бъде активната входна точка (по подразбиране е така, когато съществува `app/server-ws.mjs`).

#### Идентификатор на модела: използвайте базовия ChatGPT идентификатор (без префикс `codex/`)

OpenAI **Codex CLI** валидира името на модела от страна на клиента, когато
`supports_websockets = true`, и **отхвърля идентификатори с префикс на доставчик**, като
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Изпращайте **базовия** идентификатор (например `gpt-5.5`). Мостът на OmniRoute е само за codex, затова той разрешава отново базовия идентификатор като модел на codex
(`resolveCodexWsModelInfo`) преди тунелирането upstream — въпреки че базовият `gpt-5.5` иначе би бил маршрутизиран към друг доставчик чрез HTTP.

#### Конфигуриране на OpenAI Codex CLI

Насочете Codex CLI към OmniRoute, като добавите персонализиран доставчик с поддръжка на WebSocket в
`~/.codex/config.toml` (използвайте отделен `CODEX_HOME`, за да не променяте съществуваща конфигурация):

```toml
model = "gpt-5.5"                 # базов идентификатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без наклонена черта накрая; WS URL се извежда (използвайте https/wss в продукция)
wire_api = "responses"                    # единствената поддържана стойност от февруари 2026 г.
supports_websockets = true                # активира транспорта Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # съдържа API ключа на OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API ключ на OmniRoute (всеки ключ, ако REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI надгражда `base_url + /responses` до WebSocket, а OmniRoute тунелира връзката
към избраната OAuth връзка за codex. Валидирано от край до край спрямо локалния
сървър: ChatGPT връща `codex.rate_limits` + `response.created` и предава завършването поточно.

## Докладване на квоти и проблеми

| Метод | Пътека              | Описание                                                                                        |
| ----- | ------------------- | ----------------------------------------------------------------------------------------------- |
| GET   | `/v1/quotas/check`  | Предварително потвърдете квотата за `provider` + `accountId` преди да издадете регистриран ключ |
| POST  | `/v1/issues/report` | Докладвайте за неуспешно издаване на quota/key на GitHub (изисква `GITHUB_ISSUES_REPO` + токен) |

**Удостоверяване:** `/v1/quotas/check` приема API ключ на носител (`isAuthenticated`). `/v1/issues/report` е само за управление (`requireManagementAuth`), като `/api/v1/registered-keys`: сесия на таблото за управление, локален CLI токен или API ключ с `manage`/`admin` обхват; API ключовете само за извод получават `403`.

### Възстановяване на сесията при изчерпана квота (незадължително)

Непотоков `POST /v1/chat/completions` или `POST /v1/responses`, който завърши с
терминална грешка за квота (`402`/`429`/`503`, чието тяло указва, че квотата или кредитите са изчерпани),
може да бъде задържан и изпълнен повторно по-късно, вместо да върне грешката. Извикващият активира
тази възможност за всяка заявка чрез следните заглавки:

| Заглавка                     | Стойност                                                              |
| ---------------------------- | --------------------------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                                                |
| `x-omniroute-session`        | идентификатор на сесията, `[A-Za-z0-9._:-]{1,128}`                    |
| `x-omniroute-recovery-turn`  | идентификатор на хода, уникален в рамките на сесията (същото правило) |

Допустими са само ходове с `stream: false`, без инструменти, история на инструментите или
`previous_response_id`, както и без фиксиране чрез `x-omniroute-connection`, а
`STORAGE_ENCRYPTION_KEY` трябва да е зададен (заявката се съхранява криптирано за до 24 часа).
След това отговорът е `202` с `recovery.poll`; проверявайте чрез
`GET /v1/quota-recoveries/{id}` (`202`, докато е в изчакване, `200` с възстановеното тяло при
завършване) или отменете чрез `DELETE`. Билетите са видими само за API ключа, който ги е създал.
Повторно изпълнение с неясен резултат завършва със състояние `needs_confirmation`, вместо да бъде
изпратено два пъти. Източник: `src/lib/quota/quotaSessionRecovery.ts`.

## Използване на самообслужване (`/api/usage/om-usage`)

Всеки API ключ може да чете **своя собствена** използване и квоти — без удостоверение за управление. Това е крайната точка, която клиентът (CLI, OmniCopilot панелът) използва, за да покаже на притежател на ключ своите разходи.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Ключът трябва да има **`allowUsageCommand`** активирано (изключено по подразбиране — мениджърът на API ключове на таблото за управление го превключва за всеки ключ). Без него крайната точка отговаря `403`.

`?format=json` връща дискриминирана форма, така че повикващият никога не чете поле с данни от отказ. При успех:

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При отказ (`401` лош ключ / `403` не е позволено) същият маршрут връща `{ "allowed": false, "error": { "message": "…" } }` — присъстващ, но празен `personal`/`provider` (разрешен ключ, все още нищо не е научено) е различно състояние от отказ и само формата JSON ги отличава.

**Удостоверяване:** собственият API ключ на носителя на повикващия, валидиран с `isValidApiKey` — това _не_ е повърхността за управление (`/api/keys/…`), която остава зад `requireManagementAuth`.

### Проценти на квотата в суров вид спрямо коригирани спрямо прага

При използване на `/api/usage/om-usage` извикващите трябва да отбележат разликата между
процентите, представени от **обикновения текстов изход**, и тези от структурирания **JSON изход**:

| Аспект                      | Текстов формат (`/api/usage/om-usage` / `@@om-usage`)                                                  | JSON формат (`?format=json`)                                                                                    |
| :-------------------------- | :----------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------- |
| **Поле в изхода**           | `NN% left` (напр. `20% left`)                                                                          | `provider.quotas` / `providers[].quotas`                                                                        |
| **Измерване**               | **Използваема квота, коригирана спрямо прага**: оставащият капацитет над прага за прекъсване           | **Сурова квота от upstream**: неизменено измерване от доставчика                                                |
| **Мащабиране спрямо прага** | Мащабира се чрез `effectiveRemainingPercent()`, така че защитеният резерв да се показва като `0% left` | Няма (суровите стойности от моментната снимка, както са докладвани от доставчика)                               |
| **Данни за прага**          | Включени в показвания процент                                                                          | Съхраняват се в `quotaWindowThresholds` за всяка връзка (или се използват сървърните стойности по подразбиране) |
| **Основен потребител**      | Интерактивни CLI инструменти, терминални подкани, оператори                                            | Програмни интеграции, табла, анализи, проследяване на фактуриране                                               |

#### Формула за корекция спрямо прага

OmniRoute поддържа проактивни прагове за прекъсване на квотата, за да предотврати изчерпването от upstream
(конфигурирани чрез `quotaWindowThresholds` на връзката, стойности по подразбиране за доставчика
или глобални настройки за устойчивост). Когато прагът за прекъсване (напр. `cutoff = 25%`) е активен
за прозорец на квотата, визуализаторът на текста изчислява оставащата квота така:

- Ако `remaining <= cutoff`: връща `0%`.
- Ако `remaining > cutoff`: връща `((remaining - cutoff) / (100 - cutoff)) * 100`.

Форматираният текстов изход закръгля стойността до най-близкото цяло число (`Math.round(...)`).

#### Илюстративен пример

Разгледайте прозорец на доставчик с **60% необработено използване** (следователно **40% необработена оставаща квота**) и конфигуриран праг за прекратяване при **25% оставаща квота**:

| Представяне                           | Изчисление                                         | Оставащо |          Използвано по подразбиране          |
| :------------------------------------ | :------------------------------------------------- | :------: | :------------------------------------------: |
| **Необработен JSON (`?format=json`)** | Снимка от upstream (`quotas[window]`)              | **40%**  |                   **60%**                    |
| **Текстов формат (`NN% left`)**       | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (ако се изчислява `100 - remaining`) |

- **Защо текстът показва 20% оставащи:** От физически оставащите 40% квота в акаунта 25% са запазени от
  политиката за прекратяване. Извикващият разполага само с 15% от 75% използваем резерв, преди маршрутизаторът
  да спре да насочва заявки към тази връзка. Мащабирането гарантира, че връзката сигнализира изчерпване
  (`0% left`) точно когато маршрутизирането бъде преустановено.
- **Защо JSON запазва необработените стойности:** Полезният товар на JSON връща точната снимка от доставчика (`UsageSnapshot`),
  така че външните инструменти да имат достъп до действителното използване от upstream и до
  `quotaWindowThresholds` на ниво връзка, без сървърно мащабиране със загуба на информация.

#### Насоки за миграция за потребителите

Ако външна интеграция (например плъгин за редактор или разширение за агент) преди е извличала данни от текстовия
endpoint (`NN% left`) и е изчислявала процента на използване като `100 - NN`, мигрирането към `?format=json` означава:

- Четенето на необработените JSON стойности ще отразява **действителното потребление от upstream** (60% използвани в горния пример).
- Ако интеграцията иска да запази семантиката на използваемата квота от текстовия endpoint, тя може да изчисли
  ефективната формула за оставащото количество от страната на клиента, като използва `quotaWindowThresholds` за
  заместванията на ниво връзка.

## Семантичен кеш

```bash
# Получаване на статистика за кеша
GET /api/cache/stats

# Изчистване на всички кешове
DELETE /api/cache/stats
```

Примерен отговор:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Влияние върху латентността

Попадение в семантичния кеш обслужва отговора от кеша **без извикване към upstream**, така че отчетената `X-OmniRoute-Response-Latency` е близо до нула
(независимо от първоначалната латентност на upstream). Клиентите, чувствителни към латентността
(бенчмаркинг, наблюдение на p50/p99), трябва да проверяват заглавката на отговора
`X-OmniRoute-Cache-Latency`:

| Стойност    | Значение                                                                   |
| ----------- | -------------------------------------------------------------------------- |
| `synthetic` | Отговорът е обслужен от кеша; латентността не е реалното време на upstream |
| _(absent)_  | Отговор от реално извикване към upstream                                   |

### Заобикаляне на кеша за отделен ключ

API ключовете могат да се откажат от четенето от семантичния кеш чрез `cacheDefaultMode`:

| Стойност | Поведение                                          |
| -------- | -------------------------------------------------- |
| `legacy` | Нормално поведение на кеша (по подразбиране)       |
| `bypass` | Пропуска търсенето в кеша; винаги извиква upstream |

Задава се при създаване на ключ (`POST /api/keys`) или при актуализиране (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Заобикаляне на кеша за отделна заявка

Всяка заявка може да заобиколи кеша независимо от настройките на ключа:

```
X-OmniRoute-No-Cache: true
```

## Съвместимост с управлението на CLIProxyAPI

OmniRoute отговаря на трите крайни точки за управление на [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI),
които таблата за използване извикват, за да прочетат ограниченията на абонаментите за Claude и Codex
(например източника за ограничения на използването `cliproxy` в T3 Code). Задайте базовия URL адрес на клиента към
OmniRoute и използвайте API ключ с обхват `manage` като ключ за управление. Маршрутите се обслужват на `/v0/management/*` и на `/api/v0/management/*`.

| Метод | Път                          | Описание                                                                                                                                                    |
| ----- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/v0/management/auth-files`  | OAuth връзки за Claude и Codex като `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Без токени                                      |
| POST  | `/v0/management/api-call`    | Тяло `{ auth_index, method, url, header?, data? }`. Изпраща една заявка от списъка с разрешени заявки с токена на акаунта и връща `{ status_code, body }`   |
| POST  | `/v0/management/reset-quota` | Тяло `{ auth_index }`. Изчиства временното блокиране на връзката, блокирането на модели и временното блокиране на Codex за отделните обхвати на един акаунт |

- `auth_index` е идентификаторът на връзката в OmniRoute. `provider` е `claude` или `codex` (само OAuth връзки; доставчикът с API ключ `anthropic` не се изброява). За Codex `id_token.chatgpt_account_id` е съхраненият идентификатор на работното пространство, а `plan_type` е съхраненият план.
- `api-call` не е общо прокси. Приема само Claude `GET
https://api.anthropic.com/api/oauth/usage` и Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` и `POST .../wham/rate-limit-reset-credits/consume`, всяка само за акаунт на съответния доставчик. Всичко останало връща `403`, без да се свързва с upstream. Хедърът `Authorization` на извикващия (включително заместителят `$TOKEN$`) се игнорира: OmniRoute поставя токена за достъп на връзката, като първо го обновява, ако наближава изтичане, и препраща само разрешените хедъри (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`). При липсващ `Chatgpt-Account-Id` се използва съхраненият идентификатор на работното пространство. Ако първият upstream отговор е `401`, се извършва едно обновяване и нов опит само ако токенът за достъп се промени. Всеки upstream опит има таймаут 15 секунди и използва проксито на връзката.
- `reset-quota` оставя крайните състояния (banned, expired, credits_exhausted) непроменени. Непознат `auth_index` връща `404`.

**Удостоверяване:** сесия на таблото или API ключ с обхват `manage`, което е задължително дори когато входът е забранен
(пътищата са в `ALWAYS_PROTECTED_API_PATHS`). Ключовете само за inference получават `403`. Източник:
`src/lib/cliproxyCompat/managementApi.ts`.

За синхронизираните/импортираните модели `PUT /api/provider-models` приема `provider`, `modelId` и
`maxOutputTokenOverride`: положително цяло число задава ръчно ограничение на изходните токени, а `null`
го изчиства, за да се възстанови стойността по подразбиране. `GET /api/provider-models?provider=<provider>` връща тези стойности в `modelOutputOverrides`, включително модели без ред за персонализиран модел. Замяната използва възможността на средата за изпълнение `max_output_tokens` и се запазва при повторна синхронизация на модела. Страницата на доставчика, съвместим с OpenAI, предлага същите контроли за редактиране/изчистване и обозначава моделите с изрична поддръжка на vision.

При съвместим възел на доставчик пътищата за запис (`POST`, `PUT`, `PATCH`, `DELETE` и
`/api/provider-models/validate-and-add`) съхраняват идентификатора на модела като базов идентификатор от upstream: идентификатор, поставен от списък с префикс, има всички начални повтарящи се префикси на самия възел, обединени, а отговорите връщат съхранения идентификатор. Идентификаторите със наклонена черта на каноничните доставчици (например `nvidia/nemotron-…`) се съхраняват без промяна. `/v1/models` никога не извежда идентификатор от вида `<prefix>/<prefix>/<model>`.

Персонализираните възли за Chat Completions адаптират изричните откази от разсъждение към upstream бекенда. При успешен тест на връзката автоматично се избират контроли на chat template за всеки точно съвпадащ идентификатор на модел, чийто запис в `/models` потвърждава разпозната стойност на `owned_by`: `vllm`, `sglang` или `llamacpp`. Прозрачните OpenAI-съвместими обвивки могат да запазят оригиналния запис на модела във вложен обект `openai`; откриването следва до три такива обвивки. За модели с липсваща, неизвестна или противоречива информация за собствеността се запазва стандартното поведение на OpenAI. Откриването използва повторно съществуващата заявка към каталога, не генерира токени за завършване и се анулира при промяна на крайната точка за връзка.

За да фиксирате поведението за бекенд, който не предоставя тези метаданни, използвайте съществуващия API за частично обновяване на доставчик:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Изпратете това тяло с `PUT /api/providers/<connection-id>`. При тази връзка изрично зададеното усилие за разсъждение `none` се изпраща като `chat_template_kwargs.thinking=false` и `chat_template_kwargs.enable_thinking=false`. Изрично зададените стойности на native template остават определящи, освен ако правило за разсъждение от страна на сървъра не наложи усилие. Настройката се прилага само когато персонализирана OpenAI-съвместима връзка изпраща тяло на Chat Completions; заявките към Responses и стандартните доставчици запазват естествената си форма на заявка. Задайте `reasoningControl` на `openai`, за да наложите стандартно предаване на OpenAI `reasoning_effort`, или го пропуснете/задайте на `null`, за да използвате автоматично откриване.

Заявките на класификатора за автоматичен режим на Claude Code по подразбиране деактивират native thinking, когато не съдържат изрични контроли за разсъждение. Откриването използва системния маркер на класификатора в заявки във формат Claude, а не имената на моделите или ограниченията за завършване. Изричните контроли в тялото, поддържаните заглавки за усилие/thinking, правилата за маршрутизиране и разрешеното усилие на модела запазват съществуващия си приоритет. И двата етапа на класификатора запазват своите подсказки, ограничения за завършване, стоп последователности и реални решения за разрешение от upstream; вторият етап все още може да генерира заявеното от него видимо разсъждение като обикновен текст.

#### Произход на ограниченията на модела

`GET /api/models?withLimits=1` (също и `true`; `0`/`false` или пропускането му запазва полезния товар по подразбиране без промяна) добавя `contextWindow`, `maxInputTokens`, `maxOutputTokens` и обект `capsSource` към всеки ред на модел. `capsSource` посочва правилото, предоставило всяко ограничение, така че неочаквано ограничение (например 128k за модел с 1M) да може да бъде проследено до произхода му. Разрешените стойности са същите, които използва маршрутизирането; флагът само добавя полета и никога не променя стойност. Всяка друга стойност на `withLimits` се отхвърля с `400`.

| Стойност на `capsSource`                     | Произход                                                                      |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| `override:context`                           | Запазено заместване на контекстния прозорец (`model_context_overrides`)       |
| `override:max_input` / `override:max_output` | Запазено заместване на възможностите `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Статична авторитетна таблица на контекстните прозорци                         |
| `synced:<provider>/<model>`                  | Синхронизиран ред с възможности от models.dev                                 |
| `registry:<provider>/<model>`                | Запис в регистъра на доставчика                                               |
| `spec:<model>`                               | Статична спецификация на модела                                               |
| `effort-base:` prefix                        | Ред, заимстван от базовия модел на вариант със суфикс за усилие               |
| `none`                                       | Нито един източник не декларира ограничението (стойността е `null`)           |

Имплементация: `getResolvedModelCapabilitiesWithLimitSources()` в `src/lib/modelCapabilities.ts` и веригите на приоритет в `src/lib/modelCapabilityLimits.ts`.

### Детайлиране на видео рамка

`GET /api/v1/video-bridge/drilldown` чете непрозрачен манипулатор, обвързан с клиента, върнат в `x-omniroute-video-drilldown` след изрично одобрена заявка за Video Bridge. И reads, и `DELETE` винаги изискват валиден API ключ и независимо `modalityBridgeVideoDrilldownRemoteEnabled` разрешение на оператора. Задържането на производството допълнително изисква `modalityBridgeVideoDrilldownEnabled` и строг `drilldown: true` за част. Ако ключът има непразен списък с разрешени крайни точки, той трябва да включва `video` както за GET, така и DELETE, независимо дали повикващият използва `/v1` или `/api/v1`.

GET заявка: задължително `handle`; незадължителен `variant` (`preview`, `standard`, `detail`), `limit` (1–8; наследеният `frames` се приема, но не може да се комбинира с `limit`), `page` на база нула и `start`/`end` секунди. Когато са предоставени и двете граници на фокуса, `end` трябва да е по-голямо от `start`. Duplicate/unknown ключовете за заявка са отхвърлени. Успешните отговори съдържат `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` и незадължително `focusWindow`; no-store JSON е ограничен до 32 MiB, включително Base64. Прекомерният изход връща 413; поискайте по-малко кадри.

`DELETE /api/v1/video-bridge/drilldown?handle=...` връща `{ "removed": 0|1 }`. Неизвестен, с изтекъл срок на годност и с кръстосан ключ GETs са неразличими 404 отговора; cross-key DELETE не може да премахне записа на собственика. Деактивираният достъп връща 403, missing/invalid удостоверяване 401, невалидни заявки 400, анулиране 499 и временни грешки 503. Дръжките са локални за процеса, изтичат след десет минути и не преживяват рестартиране. Новите манипулатори използват `v1.` плюс 32-байтов произволен Base64URL токен; запазват се само хешове на токени. Наследените 64-hex токени остават синтактично четими за съвместимост. Вижте [предпазните парапети на Video Bridge](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) за подробности за съгласието, квотите и извличането на варианти.

### Версия и канал за издания

```bash
GET /api/system/version
```

Маршрут за управление, достъпен само през loopback (с администраторско удостоверяване). Връща текущата версия, последната публикувана версия и състоянието на автоматичните актуализации. `releaseChannel` и `channels` са допълнителни полета (релиз 3.8.54); `channel` запазва значението си — режимът на внедряване, който използва актуализаторът на таблото (`npm`, `source` или `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm каналът на текущата компилация: `nightly` за версии `-nightly.*`, `next` за други предварителни версии (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` за стабилна версия на по-стар major в сравнение с `channels.latest`, а във всички останали случаи — `latest`. Същите правила като в `scripts/release/dist-tag.mjs`, който избира npm dist-tag при публикуване.
- `channels` — публикуваната последна версия на всеки dist-tag, от `npm view omniroute dist-tags` (с HTTP резервен вариант към registry), кеширана със същия 10-минутен TTL като `latest`. `latest` винаги присъства (с резервен вариант към полето `latest`, след това към `"unavailable"`); `next`, `nightly` и `lts` се показват само когато съответният dist-tag съществува. Заявка с `Cache-Control: no-cache` обновява и двете справки.

Моделът на каналите (`latest` = v3 до общата наличност на 4.0, `next` = rc, `nightly` = компилации от `develop`, `lts` = корекции за v3 след общата наличност на 4.0) е описан в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрипция на аудио

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибирайте аудиофайлове с помощта на всеки конфигуриран STT доставчик. Първият сегмент от пътя избира нативния доставчик (`openai/…`, `deepgram/…`). Шлюзовете, които преекспортират модел на друг доставчик, използват квалифициран идентификатор
(`openrouter/deepgram/nova-3`).

**Заявка:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Отговор:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Примерни идентификатори на модели:** `openai/whisper-1` (изисква ключ за OpenAI),
`openrouter/deepgram/nova-3` (изисква ключ за OpenRouter),
`deepgram/nova-3` (изисква нативен ключ за Deepgram). Заявка с
`deepgram/nova-3` без префикс не използва OpenRouter.

**Поддържани формати:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** транскрипция във файлов режим през Gemini Live
WebSocket (изисква API ключ за Gemini). Каченият файл се преобразува в моно PCM с честота 16 kHz с помощта на `ffmpeg`
(`ffmpeg` трябва да е в `PATH`, освен ако файлът вече не е WAV файл с моно PCM и честота 16 kHz), предава се към сесията и
финализираният текст се връща като `{ "text": "..." }`. Незадължителните полета на формуляра `language` и `prompt`
се препращат. Ограничения: качвания над 25 MiB или декодирано аудио с продължителност над 10 минути връщат
`413`; преобразуване, което продължава повече от 60 s, се прекратява и връща `504`. API ключът се изпраща
само в заглавката `x-goog-api-key`, никога в URL адреса на WebSocket.

Използвайте тези псевдоними, когато дадена интеграция не може да добави заглавка `Authorization` и трябва да вгради API ключа в базовия URL адрес.

```bash
# Псевдоним за каталог в стил OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Псевдоними за чат в стил OpenAI
POST /api/v1/vscode/{token}/chat/completions

# Псевдоними в стил Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Пример:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Бележки:

- Токенизираните псевдоними използват същите обработващи функции като `/v1/*` и `/api/tags`; формите на отговора остават идентични.
- Предпочитайте `Authorization: Bearer ...`, когато клиентът поддържа персонализирани заглавки.
- Токените, базирани на URL адреси, може да се появят в журналите на обратния прокси, историята на браузъра и телеметрията извън OmniRoute. Разглеждайте ги като опция за съвместимост, а не като стандартен режим на удостоверяване.

## Ограничения на токените

**Бюджетите** за **токени** на API ключ (различни от посочения по-горе бюджет, базиран на USD). Прилагат се вградени в пътя на заявката: когато използването в текущия прозорец за даден ключ достигне лимита му, заявките се отхвърлят с `429 Too Many Requests`. Ограниченията могат да бъдат зададени за конкретен `model`, `provider` или да се прилагат `global` за целия ключ; когато към дадена заявка съвпадат няколко ограничения, се прилага най-строгото.

```bash
# Извеждане на ограниченията за токени на даден ключ (включва използването в текущия прозорец)
GET /api/usage/token-limits?apiKeyId=key-123

# Създаване или актуализиране на ограничение за токени
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Изтриване на ограничение за токени по идентификатор
DELETE /api/usage/token-limits?id=tl-abc
```

> **Бележки за схемата** (`setTokenLimitSchema`): `apiKeyId` и `scopeType` (`model` | `provider` | `global`) са задължителни. `scopeValue` е задължително, освен когато `scopeType` е `global` (например идентификатор на модел за обхват `model` или идентификатор на доставчик за обхват `provider`). `tokenLimit` трябва да бъде положително цяло число (преобразува се от низ). По избор: `id` (пропуснете при създаване, подайте при актуализиране), `resetInterval` (`daily` | `weekly` | `monthly`, по подразбиране `monthly`), `resetTime` (`HH:MM`), `enabled` (по подразбиране `true`). Отговорите от `GET` обогатяват всяко ограничение с `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` и `nextResetAt`. Това е крайна точка от управленски клас (автентикацията се прилага централизирано от конвейера за оторизация).

## Обработка на заявките

1. Клиентът изпраща заявка към `/v1/*`
2. Обработчикът на маршрута извиква `handleChat`, `handleEmbedding`, `handleAudioTranscription` или `handleImageGeneration`
3. Моделът се разрешава (директен доставчик/модел или псевдоним/комбинация)
4. Идентификационните данни се избират от локалната DB с филтриране според наличността на акаунта
5. За чат: `handleChatCore` проверява семантичния/сигнатурния кеш и разрешава настройките за компресиране на комбинацията
6. Проактивното компресиране се изпълнява преди превода към доставчика, когато е разрешено (`lite`, Caveman, RTK или подредени)
7. Изпълнителят на доставчика изпраща заявка нагоре по веригата
8. Отговорът се превежда обратно във формата на клиента (чат) или се връща както е (вграждания/изображения/аудио)
9. Записват се използването, аналитичните данни за компресирането и регистрационните записи на заявките
10. При грешки се прилага резервен вариант според правилата за комбинацията

Пълна справка за архитектурата: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Устойчивост (разширено)

OmniRoute предоставя три независими механизма за временни откази; крайните точки за управление по-долу позволяват на операторите да ги прочитат и заменят:

| Обхват                        | Съхранение на състоянието                      | Четене                                    | Нулиране / изчистване                                            |
| ----------------------------- | ---------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| Прекъсвач на доставчик        | `domain_circuit_breakers` + памет              | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                     |
| Период на охлаждане на връзка | `rateLimitedUntil` във връзките към доставчици | `/api/rate-limits`, `/api/providers/[id]` | (разрешава отново мързеливо; изчистване чрез PUT към доставчика) |
| Блокиране на модел            | Регистър на наличността на моделите в паметта  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                         |

`PATCH /api/resilience` приема замествания на прекъсвача на доставчик чрез `providerBreaker.oauth` и `providerBreaker.apikey`. Всеки профил поддържа `degradationThreshold`, `failureThreshold` и `resetTimeoutMs`; същите полета са налични в Табло → Настройки → Устойчивост.

```bash
# Изчистване на блокирането на един модел
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Изчистване на всички блокирания
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Пълната концептуална справка и стойностите по подразбиране на прекъсвача са описани в [`CLAUDE.md`](../../CLAUDE.md) → „Състояние на средата за изпълнение на устойчивостта“ и [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Опашка за ограничаване на честотата и предпазен механизъм за автоматично активиране

- **Поддържан път за запис**: `POST /api/rate-limits` с тяло `{"connectionId": "<id>", "enabled": true|false}` е поддържаната крайна точка за управление, чрез която се превключва защитата от ограничаване на честотата за дадена връзка. `PUT /api/providers/[id]` умишлено не променя и не превключва `rateLimitProtection` (#11278).
- **Семантика на `enabled: false`**: Задаването на `enabled: false` премахва изричната защита за връзката, но **не изключва** активна връзка с API ключ от глобалния предпазен механизъм за автоматично активиране (`autoEnableApiKeyProviders = true`). В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) `false` и `undefined` са еквивалентни; активните връзки с API ключ без изрична защита остават защитени от предпазния механизъм за автоматично активиране.
- **Глобално деактивиране**: За да използвате връзки с API ключ без опашки за ограничаване на честотата, деактивирайте глобално предпазния механизъм чрез `RATE_LIMIT_AUTO_ENABLE=false` (env) или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Настройки → Устойчивост / `PATCH /api/resilience`).

## A2A сървър

OmniRoute предоставя A2A (Agent-to-Agent) JSON-RPC 2.0 крайна точка, както и REST обвивка за инспекция и използване от таблото.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # незадължително, освен ако не е зададено OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Поддържани методи (всички са активни само при `settings.a2aEnabled`):

| Метод            | Описание                                                            |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Синхронно изпълнение на умение; връща `{task, artifacts, metadata}` |
| `message/stream` | Поточно SSE изпълнение на същия набор от умения                     |
| `tasks/get`      | Извличане на задача по `taskId`                                     |
| `tasks/cancel`   | Отмяна на задача по `taskId`                                        |

Вградени умения: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Карта на агента

```bash
GET /.well-known/agent.json
```

Връща публичната A2A карта на агента (име, описание, възможности, каталог на уменията, схема за удостоверяване) — публично кеширана за 1 час. Не се изисква удостоверяване.

### REST помощни крайни точки

| Метод | Път                          | Описание                                                                                                                  |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Състояние на A2A + статистика за задачите + обобщение на кешираната карта на агента                                       |
| GET   | `/api/a2a/tasks`             | Изброяване на задачи — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не е реализирано като REST помощна крайна точка — създавайте чрез JSON-RPC `message/send`)                               |
| GET   | `/api/a2a/tasks/[id]`        | Извличане на една задача                                                                                                  |
| POST  | `/api/a2a/tasks/[id]/cancel` | Отмяна на задача                                                                                                          |

**Удостоверяване:** REST помощните крайни точки работят без удостоверяване за управление (достъпни за преглед от таблото); JSON-RPC маршрутът `/a2a` използва Bearer `OMNIROUTE_API_KEY`, ако е конфигуриран.

| Метод  | Път               | Описание                                                                                                                                                         |

## Удостоверяване

Вижте [Удостоверяване на управлението](../guides/MANAGEMENT-AUTH.md) за четирите
семейства идентификационни данни (сесия на таблото, локален CLI токен, токен за достъп `oma_live_…`, API ключ с обхват manage) и по какво се различават от ключовете за инференция.

- Маршрутите на таблото (`/dashboard/*`) използват бисквитката `auth_token`
- Входът използва хеш на запазената парола; резервният вариант е `INITIAL_PASSWORD`
- Превключвателят `requireLogin` може да се променя чрез `/api/settings/require-login`
- Маршрутите `/v1/*` могат по избор да изискват Bearer API ключ, когато `REQUIRE_API_KEY=true`
- „management token“ / „management-scoped API key“ в тази справка означава един от семействата в това ръководство — не неопределен допълнителен тип секрет

> **Несъвместима промяна (v3.8.0)** — `/api/v1/agents/tasks/*` и крайните точки за управление на периода на изчакване вече изискват **удостоверяване на управлението** (бисквитка на таблото `auth_token` или API ключ с обхват manage). Клиентите, които преди са извиквали тези маршрути без удостоверяване, ще получат `401 Unauthorized`. Вижте commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
