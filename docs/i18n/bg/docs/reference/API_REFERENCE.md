## Завършвания на чат

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Персонализирани заглавки

| Заглавка                 | Посока  | Описание                                                                                                                                                                                                                              |
| ------------------------ | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Заявка  | Задайте на `true`, за да заобиколите кеша                                                                                                                                                                                             |
| `x-omniroute-no-memory`  | Заявка  | Задайте на `true`, за да пропуснете добавянето на памет и умения за тази заявка (аналогично на липсата на кеш; избягва допълнителния разход на токени/средства за всяко извикване)                                                    |
| `X-OmniRoute-Progress`   | Заявка  | Задайте на `true` за събития за напредъка                                                                                                                                                                                             |
| `X-Session-Id`           | Заявка  | Постоянен ключ на сесията за външно обвързване със сесия                                                                                                                                                                              |
| `x_session_id`           | Заявка  | Приема се и вариантът с долна черта (директен HTTP)                                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | Заявка  | Предоставен от извикващата страна етикет на сесията/разговора (използва се и от паметта). Когато е наличен, се запазва дословно в `call_logs.session_tag` за отчитане на разходите по сесии (#8249) — никога не се генерира при липса |
| `Idempotency-Key`        | Заявка  | Ключ за премахване на дубликати (прозорец от 5 сек.)                                                                                                                                                                                  |
| `X-Request-Id`           | Заявка  | Алтернативен ключ за премахване на дубликати                                                                                                                                                                                          |
| `x-omniroute-connection` | Заявка  | Прикрепя заявка за единичен модел към една връзка с доставчик (акаунт) според нейния идентификатор — вижте [Прикрепяне към акаунт за всяка заявка](#account-pinning-per-request)                                                      |
| `X-OmniRoute-Cache`      | Отговор | `HIT` или `MISS` (без поточно предаване)                                                                                                                                                                                              |
| `X-OmniRoute-Idempotent` | Отговор | `true`, ако дубликатът е премахнат                                                                                                                                                                                                    |
| `X-OmniRoute-Progress`   | Отговор | `enabled`, ако проследяването на напредъка е включено                                                                                                                                                                                 |
| `X-OmniRoute-Session-Id` | Отговор | Ефективният идентификатор на сесията, използван от OmniRoute                                                                                                                                                                          |
| `X-OmniRoute-Request-Id` | Отговор | Идентификатор за корелация на заявката (когато е известен)                                                                                                                                                                            |
| `X-OmniRoute-Version`    | Отговор | Версия на компилацията на OmniRoute (винаги присъства)                                                                                                                                                                                |
| `X-OmniRoute-Cost-Saved` | Отговор | Сумата в USD, спестена от кеша при `HIT` (само при попадения в кеша)                                                                                                                                                                  |
| `X-OmniRoute-Decision`   | Отговор | Данни за маршрутизирането: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` е стратегията на комбинацията или `single` за заявка без комбинация) — винаги присъства в отговорите при завършване                          |

> Бележка за Nginx: ако разчитате на заглавки с долни черти (например `x_session_id`), активирайте `underscores_in_headers on;`.

#### Фиксиране на акаунт за всяка заявка

Когато даден доставчик има няколко връзки (акаунти или ключове), OmniRoute обикновено избира една
чрез своята стратегия за избор на акаунт. Вместо това заявката може да фиксира конкретна връзка
чрез заглавката `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Къде да намерите идентификатора.** Отворете страницата на доставчика в таблото за управление
  (**Табло за управление → Доставчици → <доставчик>**) и щракнете върху елемента с идентификатор `xxxxxxxx…` в реда на връзката
  — така пълният идентификатор на връзката се копира.
- **Кои заявки го спазват.** Заявките с един модел (`provider/model`) към
  `/v1/chat/completions`, `/v1/messages` и `/v1/responses`. Комбинациите игнорират заглавката: фиксирайте
  акаунт за всяка стъпка от комбинацията чрез собствената връзка на стъпката.
- **Фиксирането е строго, а не предпочитание.** Използва се единствено фиксираната връзка. При
  грешка в рамките на заявката се регистрира периодът на изчакване на акаунта, но **не** се преминава към
  друг акаунт на същия доставчик.
- **Периодът на изчакване и квотата освобождават фиксирането.** Докато фиксираната връзка е в период на изчакване,
  с изчерпана квота или блокирана от политика за квоти, следващите заявки преминават към другите връзки на доставчика
  точно както трафикът без фиксиране.
- **Неизвестните или деактивираните идентификатори водят до грешка.** Идентификатор, който не е в активния пул на доставчика (изтрит,
  деактивиран или принадлежащ на друг доставчик), не оставя допустим акаунт, затова заявката
  е неуспешна, вместо безшумно да бъде насочена другаде.

Claude Code изпраща персонализирани заглавки чрез `ANTHROPIC_CUSTOM_HEADERS`. Поставете го в блока `env`
на `~/.claude/settings.json` или във `.claude/settings.json` на ниво проект, за да фиксирате различен
акаунт за всеки проект:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Източник: `src/sse/handlers/chat.ts` (прочитане на заглавката), `src/sse/services/auth.ts` и
`src/sse/services/sessionAffinityPin.ts` (освобождаване на фиксирането и проверка за липса в пула).

> **Заглавки за телеметрия на разходите:** успешните отговори без поточно предаване съдържат и набора `X-OmniRoute-*` за телеметрия на разходите — `X-OmniRoute-Response-Cost` (USD, точно 10 знака след десетичната запетая; `0.0000000000` за безплатни/неостойностени заявки), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` и `X-OmniRoute-Fallback-Attempts` (само когато > 0), както и `X-OmniRoute-Request-Id` и `X-OmniRoute-Version`. Те се подават от завършванията на чат, `/v1/responses`, `/v1/messages`, **както и от крайните точки за медийни данни** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` и `/v1/moderations` (винаги с разход `0`). Разходът за медийни данни се изчислява според модалността (за изображение, за секунда, за знак, за единица търсене), когато има налични цени; в противен случай е `0` (работата продължава при грешка).

> **Семантика на разходите при попадение в кеша:** при ПОПАДЕНИЕ в семантичния кеш (`X-OmniRoute-Cache-Hit: true`) не се извършва заявка към системата нагоре по веригата, затова `X-OmniRoute-Response-Cost` е `0.0000000000` (**допълнителният** разход за обслужване на попадението). Първоначалният разход/разходът, който би възникнал, се отчита отделно в `X-OmniRoute-Cost-Saved`. Системите за фактуриране трябва да сумират `X-OmniRoute-Response-Cost` (попаденията не струват нищо); анализите на кеша могат да агрегират `X-OmniRoute-Cost-Saved`.

## Ексклузивни управлявани лизинги на сесии

Ексклузивният управляван лизинг на сесии е незадължителен, независим от клиента договор за маршрутизиране: един активен собственик
държи една допустима връзка с OmniRoute. Той не отдава под лизинг модел, не изисква OAuth, не идентифицира
конкретен клиент и не изисква конкретен доставчик.

Удостоверяващият API ключ трябва да има обхват `lease:exclusive` и изричен непразен
списък `allowedConnections`. Границата за мутации в базата данни налага двете полета заедно при
създаване на ключ и частични актуализации.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успешните отговори за придобиване, подновяване и освобождаване предоставят времеви маркери, `state` и точната положителна
`generation`, но никога избраната връзка или идентификационните данни. При подновяване и освобождаване
поколението се подава в JSON тялото:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Собственикът на активен лизинг може изрично да поиска безопасни за поверителността метаданни за показване за текущото си обвързване:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Това незадължително действие за статус се ограничава от непрозрачния идентификатор на собственика, удостоверения управляван API ключ и точното
активно поколение в рамките на една транзакция с базата данни. `displayName` е само конфигурираното име на
връзката с премахнати водещи и завършващи интервали; то е `null`, когато не съществува безопасно конфигурирано име. OmniRoute никога не го заменя с
имейл адрес или генерирана самоличност на акаунт. Стойността за доставчика е нечувствителен етикет за показване и никога
не е генериран идентификатор на съвместим доставчик. Идентификационните данни, токените, бисквитките, необработените идентификатори на връзки или API
ключове, хешовете на собственици, секретите за защитно ограничаване и вътрешните данни за маршрутизиране са изключени.

Заявките с грешен ключ, грешен собственик, остаряло поколение, липсващ, изтекъл, освободен или анулиран лизинг
връщат една и съща грешка `409 LEASE_FENCE_STALE` без метаданни за връзката. Клиент, получил отговор за изчакване на капацитет, няма активно обвързване, което да провери. Когато маршрутизирането прехвърли активен лизинг,
същото поколение остава валидно и статусът атомарно връща новото обвързване, никога старото.
Съществуващите клиенти остават непроменени, тъй като отговорите за придобиване, подновяване, освобождаване и изчакване запазват
предишните си структури.

Този сървърен договор не променя стандартния `/status` на OpenAI Codex. Понастоящем стандартният Codex отчита своя
доставчик на модели и вграденото състояние на удостоверяване/акаунт, но не визуализира произволни персонализирани
метаданни за акаунти на доставчици; бъдеща клиентска интеграция трябва да извика това действие и да реши как да
покаже `connection.displayName`.

След това всяка управлявана заявка за инференция предоставя и двете контролни заглавки:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точният собственик, поколението, активната връзка и удостовереният API ключ се проверяват чрез защитно ограничение непосредствено
преди всеки поддържан опит към доставчик. Повторното използване на собственик и поколение с друг ключ е неуспешно дори
когато този ключ разрешава същата връзка. Необработените идентификатори на собствениците не се съхраняват трайно, не се записват в журналите, не се запазват в
моментната снимка на заявката и не се препращат към доставчика.

Временната конкуренция за ресурс връща HTTP `429` с `Retry-After` и:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Този отговор означава единствено, че обичайният набор от допустими връзки не е бил празен и всеки свободен кандидат е бил
зает от чужд активен лизинг. Неподдържаните модели/доставчици, несъответствията с правилата, периодите на изчакване, квотите,
състоянието на услугата и други обичайни неуспехи при проверка на допустимостта запазват съществуващите си отговори от OmniRoute.

### `x-omniroute-compression`

Замяна на плана за компресиране за отделна заявка. Има най-висок приоритет — надделява над замяната чрез комбинация за маршрутизиране,
активния профил, автоматичното задействане и настройката по подразбиране от панела. Стойности:

| Стойност      | Ефект                                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| `off`         | Без компресиране за тази заявка.                                                                                     |
| `default`     | Изведеният от панела профил по подразбиране (игнорира активния профил). Компресирането със загуби остава изключено.  |
| `safe`        | Само премахване на дубликати и нормализиране на празните пространства.                                               |
| `allow-lossy` | Запазва плана на оператора за тази заявка, включително обобщенията и пренаписването на стила.                        |
| `engine:<id>` | Единичен механизъм, когато е активиран, напр. `engine:rtk`. Изрично включване на този механизъм за отделната заявка. |
| `<combo>`     | Именувана комбинация, съпоставяна първо по име (без значение от регистъра), а след това по идентификатор.            |

Бележки:

- Непознатите стойности се игнорират (заявката никога не се отхвърля); определянето продължава според обичайния приоритет на оператора.
- Ако няколко комбинации споделят едно и също име, подайте **идентификатора** на комбинацията за детерминирано съвпадение.
- Комбинация с име `off` или `default` не може да бъде избрана по име (тези ключови думи се интерпретират първо); посочете такава комбинация чрез нейния идентификатор.
- Главният превключвател за компресиране е твърдо ограничение: когато компресирането е изключено глобално, тази заглавка не може да го активира.

Приложеният план се връща в заглавката на отговора:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

където `<source>` е една от стойностите `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Вграждания

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Налични доставчици: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Идентификаторите в каталога са във формат `provider/model` (пример: `jina-ai/jina-embeddings-v5-omni-small`). Самостоятелните идентификатори на модели на Jina, които присъстват в регистъра (например `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), също се разпознават. Операциите за вграждане, преранжиране, класифициране и сегментиране на Jina първо използват идентификационните данни `jina-ai` от таблото за управление; `JINA_AI_API_KEY` се използва като резервен вариант само когато няма ключ в таблото за управление. Картата `jina-reader` е само за Reader / `r.jina.ai` (`POST /v1/web/fetch`) и никога не обслужва заявки за вграждания или преранжиране.

Моделите в регистъра, които обявяват поддръжка на множество модалности, приемат и до 32 структурирани елемента, независими от доставчика.
Типовете мултимедийни елементи са `text`, `image`, `audio`, `video` и `document`. Техният медиен `source`
е или `{"type":"url","url":"https://..."}`, или
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
и фамилният псевдоним `jina-ai/jina-embeddings-v5-omni` → omni-small) приема също нативните за Jina
документи EmbeddingsV5Request и **ги препраща непроменени** към `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Нативните стойности `{ image | audio | video | pdf }` могат да бъдат публичен HTTPS URL адрес, `data:` URI или необработен
base64. OmniRoute не преобразува тези обекти в низове и не извлича нативните URL адреси на изображения — Jina извлича
публичните медийни ресурси самостоятелно. Допълнителните полета на Jina (`task`, `normalized`, `truncate`, `embedding_type`) се
препращат. SKU на Jina, предназначени само за текст, продължават да отхвърлят нетекстови документи.

Ограничения за сигурност и пренос:

- Отдалечените URL адреси на медийни ресурси трябва да бъдат публични и да използват HTTPS. Каноничните елементи `{type,source:url}` се извличат
  от страна на сървъра (повторна проверка при пренасочване, ограничение на времето, ограничения на размера, публичен DNS, фиксиране на връзката) и
  се вграждат преди извикването на доставчика. Нативните за Jina елементи `{image:"https://..."}` се препращат непроменени
  след същата проверка за публичен HTTPS адрес; Jina извлича URL адреса.
- Вградените base64 медийни данни са ограничени до 8 MiB декодирани данни на елемент и 16 MiB декодирани данни общо за заявката.

Преобразуване за доставчика (каноничните елементи никога не се препращат непроменени):

- Мултимодални модели на Jina: всеки елемент от най-високо ниво се превръща в един обект с ключ за съответната модалност
  (`text` / `image` / `audio` / `video` / `pdf`), като за вградените медийни данни се използват URI адреси за данни; по един вектор за
  всеки елемент от най-високо ниво.
- Фамилията Gemini Embedding 2: един масив от най-високо ниво се превръща в една нативна заявка
  `models/{model}:embedContent` с `content.parts` (`text` или `inline_data`).
- llama.cpp (`llama-cpp/<model>`, всеки модел, зареден от локалния сървър): каноничните елементи `text`
  се превръщат в обикновени низове, а `image` / `audio` / `video` се превръщат поотделно в
  обект `{"content": [part]}`, като се използват частите за чат съдържание на llama-server (`image_url`,
  `input_audio` с формат `wav` / `mp3` / `flac`, `input_video`) с вградени данни; по един вектор
  за всеки елемент от най-високо ниво. Сървърът трябва да работи с `--embedding --mmproj …`; без проектор той
  сам отхвърля медийните данни. `document` не се поддържа.
- Неизвестни/динамични модели без изрични метаданни за модалност отхвърлят структурирания вход с HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Неподдържаните комбинации от модел и модалност връщат HTTP 400, вместо да преобразуват принудително елемента. Разширителните
полета извън входните данни в наследени заявки с низове/токени продължават да се предават непроменени.

```bash
# Извеждане на всички модели за вграждания
GET /v1/embeddings
```

## Генериране на изображения

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Наличните доставчици включват OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локално), ComfyUI (локално).

`n` връща `n` изображения в `data[]`. За доставчиците, чийто външен API връща по едно изображение на извикване
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), се извършват `n` отделни външни извиквания, като най-много 4 се изпълняват едновременно. Фиксирана
стойност на `seed` се измества с индекса на извикването (`seed`, `seed + 1`, …), така че изображенията да са различни, но да останат
възпроизводими. `n` е ограничено до 10. Заявката се счита за неуспешна изцяло, ако някое извикване е неуспешно. Списъкът
с формати за паралелно извикване е `SINGLE_IMAGE_FANOUT_FORMATS` в
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux използва повторно съществуващата връзка с API ключ и приема префиксите `zenmux/` или `zm/`:

- `zenmux/openai/gpt-image-2` използва OpenAI Images API на ZenMux. Опциите включват `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` и `response_format`.
- Други издатели, като `zm/meta/muse-image-1.0`, използват крайната точка `:predict`
  на Vertex AI от ZenMux. `n` се съпоставя със `sampleCount`, `aspect_ratio` — с `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — със `sampleImageSize`. Стойност на `size` в пиксели задава само съотношение на страните,
  а не гарантирани размери в пиксели. Поддържаните съотношения, разделителни способности и брой изображения се различават според модела.
- `zm/inclusionai/ming-image-0.1-design` избира собствени размери. Пропуснете `size`,
  `aspect_ratio` и `image_size`; изрично зададени стойности връщат HTTP 400. PNG, JPEG и WebP
  могат да бъдат заявени чрез `output_format`.

Тази интеграция поддържа генериране на изображения от текст, но не и редактиране чрез референтно изображение. Резултатът от Vertex
се нормализира до `data[].b64_json`; `response_format: "url"` връща външен
HTTPS URL или URL с base64 данни, когато са налични само байтовете на изображението. Празните/филтрираните резултати
връщат грешка вместо празен успешен отговор. Достъпът до моделите зависи от акаунта в ZenMux.
Вижте [Vertex API на ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) и
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Извеждане на всички модели за изображения
GET /v1/images/generations
```

## OCR на документи

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` избира доставчика на OCR чрез префикс `provider/model`; идентификатор на модел без префикс (напр.
`mistral-ocr-latest`) се свързва с регистрирания му доставчик, а при пропуснато поле `model` по подразбиране се използва
Mistral (`mistral-ocr-latest`). Регистрирани доставчици (`open-sse/config/ocrRegistry.ts`):

| Идентификатор на доставчика   | Идентификатор на модела | Стойност на `model`                                          | Бележки                                                                                                                            |
| ----------------------------- | ----------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest`    | `mistral/mistral-ocr-latest` (или само `mistral-ocr-latest`) | Синхронно — отговорът се връща директно от единичното външно извикване.                                                            |
| `azure-document-intelligence` | `prebuilt-read`         | `azure-document-intelligence/prebuilt-read`                  | Асинхронно от външната услуга (`analyze` + периодична проверка) — вижте по-долу.                                                   |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`     | `vertex-deepseek-ocr/deepseek-ocr-maas`                      | Синхронно, чрез партньорската крайна точка `openapi/chat/completions` на Vertex AI — вижте по-долу за удостоверяването/URL адреса. |

И трите доставчика отговарят с еднакво тяло във формата на Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Поток за периодична проверка на Azure Document Intelligence

API `analyze` на Azure Document Intelligence е асинхронен: първоначалната заявка връща заглавка
`Operation-Location` вместо тяло и резултатът трябва да бъде проверяван периодично. Обработчикът
(`open-sse/handlers/ocr.ts`) проверява този URL адрес всяка секунда в рамките на до 30 опита, прекратява незабавно (без
да продължава проверките) при отговор от проверката, който не е `ok`, или при състояние `"failed"`, и връща `504`, ако
операцията все още се изпълнява след изчерпване на разрешения брой опити. Окончателният отговор от Azure се
нормализира до същия формат `pages`/`markdown`, използван от Mistral, преди да бъде върнат на
извикващата страна, така че клиентският код не трябва да обработва доставчика по специален начин.

### Удостоверяване и определяне на крайната точка за Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` използва повторно същото удостоверяване във Vertex AI, което OmniRoute вече поддържа за
трафик за чат/изображения (`open-sse/executors/vertex.ts`): API ключът на връзката е или
идентификационни данни във формат Service Account JSON (обменяни за краткотраен OAuth токен за достъп чрез JWT-bearer
потока), или вече издаден OAuth токен за достъп, който се използва директно. URL адресът на външната крайна точка е общата партньорска
крайна точка `openapi/chat/completions` на Vertex, изградена от проекта и региона на връзката
— изрично зададени `providerSpecificData.project`/`providerSpecificData.region` винаги имат предимство;
в противен случай проектът се извлича от `project_id` в Service Account JSON, а регионът
по подразбиране е `us-central1`. И двете стойности се определят в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) и се използват от
`src/app/api/v1/ocr/route.ts`, преди заявката да бъде предадена към `handleOcr`.

### Цени на моделите (`pricing`)

Даден запис съдържа обект `pricing`, когато OmniRoute знае цената на модела. Цената идва
от ценовата таблица, използвана за отчитане на разходите: вградени стойности по подразбиране, синхронизирани цени и
замествания, зададени чрез `/api/pricing`. Това са каталожни цени, така че доставчиците с абонамент също
показват цена на токен.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Полета                                                          | Единица                     | Бележки                                                                                                                                                   |
| --------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD на токен, десетичен низ | Съвместими с OpenRouter, никога не са в експоненциален запис. Двете полета за кеш се показват само когато има цена за кеширане.                           |
| `input`, `output`, `cached`, `cache_creation`                   | USD на 1 млн. токена, число | Полета от по-ранни версии на каталога, запазени за съществуващите клиенти. `reasoning` и `long_context` също се показват, когато ценовият ред ги съдържа. |

- **Комбинациите** съдържат цената на първата си видима цел. Вградените комбинации `auto/*` избират
  цел при изпълнение на заявката, затова нямат `pricing`.
- **Безплатните модели** показват `"0"` (и `0`), когато цената им е нула. Модел без ценови ред
  също показва `"0"`, когато каталогът го отбелязва като безплатен (`free: true`) или вграденият каталог
  с безплатни модели го съдържа.
- **Неизвестна цена:** записът няма ключ `pricing`.
- **Доставчиците с таксуване чрез кредити** (като Kiro) таксуват на заявка, а не на токен. Техните
  записи запазват числовите полета за 1 млн. токена, които са имали преди, и не съдържат низови полета за цена на токен.
- **Вариантите** (идентификатори за степен на разсъждение, псевдоними без разсъждение, огледални модели за откриване и шлюзове)
  копират цената на модела, към който маршрутизират.
- Полетата съдържат само базовите тарифи. Нивата за дълъг контекст (числовото поле `long_context`) и
  множителите за ниво на услугата (например Codex fast или flex) не променят `prompt` или
  `completion`.
- Обектът е един и същ за всеки стил на удостоверяване, включително заявка в стил Anthropic
  с `x-api-key` и `anthropic-version` (отговорът остава `{ "object": "list",
"data": [...] }`). Реализация: `src/app/api/v1/models/catalogPricing.ts`.

### Префикси на идентификаторите на модели (`?prefix=`)

Повечето модели се обявяват с **префикс на доставчика**. Кой префикс ще получите се определя от
флага за функционалност `MODELS_CATALOG_PREFIX_MODE` и може да бъде заменен **за всяка отделна заявка** чрез
параметър на заявката — полезно за клиент, който иска изчистен списък, без да променя общата за сървъра
настройка за всички останали:

```bash
GET /v1/models?prefix=alias        # по един идентификатор за модел — краткият префикс на псевдонима
GET /v1/models?prefix=dual         # и двете форми (стойност по подразбиране на сървъра)
GET /v1/models?prefix=canonical    # само пълният префикс с идентификатор на доставчика
```

| Режим       | Извежда                                                 | Бележки                                                                                                                                                                                                                       |
| ----------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **и** `claude/claude-sonnet-4-6` | **По подразбиране.** И двата идентификатора маршрутизират към един и същ модел; запазени са, за да продължат да работят клиентските конфигурации, в които някоя от формите е твърдо кодирана. Приблизително удвоява каталога. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | По един запис за модел. Доставчиците без отделен псевдоним все пак извеждат своя запис, така че нищо не се губи.                                                                                                              |
| `canonical` | `claude/claude-sonnet-4-6`                              | По един запис за модел с пълния префикс с идентификатор на доставчика. Доставчиците без отделен псевдоним (напр. `antigravity/…`, `agy/…`) също извеждат тук единствения си идентификатор, така че нищо не се губи.           |

Огледален модел в режим `dual` може да бъде разпознат и без параметъра на заявката: той съдържа поле `parent`,
което сочи към основния идентификатор.

Клиентите, които визуализират избор на модел, трябва да заявят `?prefix=alias` — това прави
[разширението OmniCopilot за VS Code](../guides/VSCODE-COPILOT.md).

### Филтри за откриване (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` приема незадължителни филтри за откриване. Без нито един от тях отговорът остава
непроменен. Те стесняват каталога, който заявителят вече вижда (първо се прилагат разрешенията на API ключа),
и се изпълняват преди страницирането в стил OpenAI чрез `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # всяка посочена възможност трябва да е активна
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` в каталога; редовете без такъв са `chat`
GET /v1/models?q=sonnet&limit=10                           # съвпадение без отчитане на регистъра в идентификатора или името
```

| Параметър     | Стойности                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | неотрицателно цяло число, сравнявано с `context_length`                                             |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 знака                                                                                         |

Неизвестна стойност или `min_context`, което не е неотрицателно цяло число (например `1.5`),
връща HTTP `400`, а съобщението изброява валидните стойности. Имплементация:
`src/app/api/v1/models/catalogFilters.ts`.

### Кратък списък с модели (`POST /v1/models/query`)

`POST /v1/models/query` връща кратък, детерминистичен списък от същия каталог, със същото
удостоверяване и видимост за отделните ключове като `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Всяко поле е незадължително. `capabilities` и `exclude` приемат масив или низ със стойности, разделени със запетаи;
`max_output` се сравнява с `max_output_tokens`. Резултатите се сортират първо по `owned_by`, след това по `id`.
Стойността по подразбиране на `limit` е `20`, а стойностите над `100` се ограничават до `100`. Невалиден JSON, неизвестно
поле или невалидна стойност връща HTTP `400`.

### Индивидуално скрити чат модели

Модел, маркиран като **Скрит** на страницата на доставчика си, се изключва от каталога и заявката
се отхвърля с HTTP `404` / `model_not_found`, когато моделът е указан изрично. Проверката използва определения
доставчик и модел, включително псевдонимите на доставчици, префиксите на възли за съвместими доставчици и
настройките по подразбиране на връзката. Комбинацията пропуска скритите цели и може да използва видима алтернатива; когато не
остане изпълнима цел, тя връща същия код за грешка. Премахването на скриването влиза в сила при следващата
заявка. Замените на видимостта само за изображения не скриват чат модела със същия идентификатор.

Тази индивидуална настройка на модела е отделна от
[списъците за разрешаване/забраняване на показването на модели](../routing/MODEL_EXPOSURE_LIST.md), които филтрират
моделите, показвани в каталога, и кандидатите за автоматично маршрутизиране, като запазват изричното насочване. Разрешенията за модели
на API ключовете продължават да се прилагат независимо. Режимът по подразбиране за префикси в каталога остава `dual`.

### Варианти на модели без мисловен процес

За моделите Claude с възможност за мисловен процес `/v1/models` също показва вариант **без мисловен процес**, чийто идентификатор има префикс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Избирането на този идентификатор (например в конфигурация на Claude Code, която винаги добавя блок `thinking`) се преобразува обратно към действителния `<provider>/<model>` с потиснато разсъждение — `thinking:{type:"disabled"}` при пътя `/v1/messages` или с премахнати полета `reasoning`/`reasoning_effort` при пътя `/v1/chat/completions`. Вариантът се показва само за модели от семейството Claude, които поддържат мисловен процес **и** зачитат `disabled` (така например моделите само с адаптивен режим, които отхвърлят `disabled`, са изключени). Операторите могат принудително да включат или изключат варианта за всеки модел чрез `ModelSpec.noThinkingAlias`.

## Генериране на аудио с ElevenLabs

Конфигурирайте връзка с доставчик `elevenlabs` в OmniRoute чрез своя API ключ за ElevenLabs.
Клиентите се удостоверяват със своя ключ за **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюзът предоставя съхранения ключ за доставчика като `xi-api-key`. Никога не изпращайте ключ за ElevenLabs
като bearer токен към шлюза.

| Метод | Път                         | Отговор                                      | Категория на крайната точка за API ключа |
| ----- | --------------------------- | -------------------------------------------- | ---------------------------------------- |
| POST  | `/v1/sound-generation`      | Нативни аудиобайтове                         | `elevenlabs`                             |
| POST  | `/v1/music`                 | Нативни аудиобайтове                         | `music`                                  |
| POST  | `/v1/music/stream`          | Поточно предавани аудиобайтове               | `music`                                  |
| POST  | `/v1/music/detailed`        | Нативно multipart аудио и план за композиция | `music`                                  |
| POST  | `/v1/music/detailed/stream` | Нативни SSE метаданни и аудиофрагменти       | `music`                                  |
| POST  | `/v1/music/plan`            | JSON план за композиция                      | `music`                                  |

Тези крайни точки допълват съществуващите маршрути `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` и `/v1/speech-to-text`. Нативните JSON полета
и параметрите на заявката, като `output_format` и `enable_logging`, се запазват.
Отговорите от `/v1/music/detailed` запазват своите multipart граници; обработвайте ги като multipart.
`/v1/music/detailed/stream` връща `text/event-stream` с метаданни за композицията и
base64 аудиофрагменти в SSE събития. И шестте маршрута поддържат предварителни CORS заявки.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Кратък звуков ефект. Продължителност: от 0,5 до 30 секунди.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Продължителността на музиката се задава в милисекунди: от 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Използвайте `/v1/music/stream` със същото JSON тяло за поетапно предаване на аудио. Композицията
приема точно едно от `prompt` или `composition_plan`; `/v1/music/plan` изисква `prompt`
и по избор приема `source_composition_plan`. Нативните схеми запазват допълнителните
полета на доставчика, така че версиите на плановете за композиция и опциите за фина настройка да достигат до ElevenLabs.

Унифицираната крайна точка `/v1/music/generations` също приема `elevenlabs/music_v1`,
`elevenlabs/music_v2` и `elevenlabs/music_v2_5`. При активна връзка с ElevenLabs
тези модели се предоставят чрез музикалния каталог. Тази крайна точка връща
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Полето ѝ `duration` е в
секунди и се преобразува в `music_length_ms`; изрично зададеното `music_length_ms` е с предимство.
`instrumental` се преобразува във `force_instrumental`, като нативното поле е с предимство.
Използвайте нативните крайни точки за поточно предаване и нативната крайна точка за композиция
за заявки, управлявани единствено от план за композиция.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ограниченията за крайна точка, модел, бюджет и връзка се прилагат преди извикване към външната услуга. Нативните
маршрути връщат кодовете за състояние и телата на грешките от външната услуга без промяна, включително `402` при
ограничение на абонаментния план и `429` при достигане на лимита на квотата. Заглавките `character-cost`, `song-id`, `request-id` и `retry-after`
се запазват, когато присъстват. Наличието на безплатен кредитен баланс не гарантира достъп до всеки
музикален модел, изходен формат или API функционалност: ElevenLabs определя правата за достъп за всяка заявка.
Унифицираната крайна точка запазва кодовете за състояние при грешка в нормализираната обвивка за грешки на OmniRoute.

Договори на външната услуга: [звукови ефекти](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[музикална композиция](https://elevenlabs.io/docs/api-reference/music/compose) и
[подробности за поточно предаване на музика](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

# Търсене с Jina (s.jina.ai; псевдоними на доставчика: jina-search, jina-ai, jina)

# Модериране
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — връща тяло във формат audio/mpeg (или заявения формат)

# Soniox TTS изисква език и глас: стойността по подразбиране на `language` е "en"; липсващ
# глас или име на стандартен глас на OpenAI (alloy, nova, …) се заменя с "Adrian"

# Редактиране на изображение (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }

> **Възли на доставчици за преранжиране:** `POST /v1/rerank` също насочва заявките към съвместими с OpenAI възли на доставчици
> (oMLX, vLLM, Infinity, TEI зад шлюз, …), адресирани като `<node-prefix>/<model>`. Възлите с обратна връзка
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) са винаги допустими, както и имената на хостове, които
> операторът посочва в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (напр. име на услуга в Docker/Compose,
> като `http://reranker:8080/v1`; те се извикват директно, никога чрез `HTTP(S)_PROXY` или
> фиксираното прокси на дадена връзка). Възлите на всеки друг
> хост — машина в LAN или партньорски възел в Tailscale — са допустими само когато операторът активира
> флага за функционалност `RERANK_REMOTE_PROVIDER_NODES` **и** базовият URL адрес на възела отговаря на
> правилата за изходящи URL адреси на доставчика (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Стъпката за преранжиране на механизма за памет извиква този маршрут чрез
> обратна връзка, така че същото правило управлява `rerankProviderModel` в настройките за паметта.
>
> **Формати на локалните сървъри:** възелът се извиква на `<base>/v1/rerank`, а при 404 — на `<base>/rerank`
> (Infinity, TEI). Тялото на заявката към сървъра нагоре по веригата съдържа както наименованията на Cohere/OpenAI (`documents`,
> `return_documents`), така и тези на TEI (`texts`, `return_text`), а отговорът от сървъра нагоре по веригата се
> нормализира до обвивката на Cohere: директният масив на TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> от опростени шлюзове и форматът на Voyage `{data: [...]}` се връщат към клиента като
> `{results: [{index, relevance_score, document?}]}`, сортирани по оценка и ограничени до `top_n`.

> **Откриване на възли на доставчици:** моделите на съвместим с OpenAI възел на доставчик се показват в `GET /v1/models`
> под префикса на възела. Редовете без метаданни за крайна точка (типично за локални списъци от `/v1/models`)
> наследяват `apiType` на възела, така че моделите на възел за `embeddings` са с `type: "embedding"`, а моделите
> на възел за `rerank` са с `type: "rerank"`, вместо по подразбиране да се приемат за чат модели; изрично зададеното
> `supportedEndpoints` в синхронизиран или ръчно добавен ред продължава да има предимство.

### `provider_options` за Exa и Tavily

Exa и Tavily четат специфични за доставчика полета от обособено пространство от имена:
`provider_options.exa` (или `provider_options["exa-search"]`) и `provider_options.tavily`
(или `provider_options["tavily-search"]`). Препращат се само ключовете по-долу. Всеки от тях се
проверява спрямо собствената си Zod схема в `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ с грешен тип се премахва. Всеки друг ключ се игнорира, включително тези за удостоверяване, базов URL,
`stream` и `outputSchema`. Плоските ключове, използвани от други доставчици (`cx`, `depth`, ...), работят
както преди.

| Доставчик | Полета от най-горно ниво                                                                                                                                                                                                                                                                                                                                                  | Вложени                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоски примитивни стойности), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                  | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}`, обединени върху стойността по подразбиране `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                                     |

Общите полета винаги са с предимство: `query`, `max_results`, `filters` (домейни), `country` и
темата, извлечена от `search_type`. При Exa `search_type: "news"` запазва `category: "news"`.
Tavily приема също `search_type: "finance"` (`topic: "finance"`).

Общото поле `time_range` вече достига и до двата доставчика: Exa получава `startPublishedDate` (ISO
времеви маркер), а Tavily получава `start_date` (`YYYY-MM-DD`). Изрично зададена дата в `provider_options`
има предимство пред съпоставената стойност.

Резултатите от Exa запазват `id`, `highlight_scores`, `summary`, `subpages`, `entities` и `extras` в
`provider_raw`. Резултатите от Tavily запазват `images` и `favicon`.

Отчитането на разходите продължава да използва плоския регистър `costPerQuery`. Tavily таксува
`search_depth: "advanced"` с повече кредити на извикване и тази разлика не е отразена в
`usage.search_cost_usd`.

## API за извличане на уеб съдържание

Извлича съдържание от URL чрез конфигуриран доставчик за извличане на уеб съдържание (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, същият API ключ като за Parallel Search) връща само Markdown
— всеки друг `format` води до `400` — и ограничава съдържанието до 100 000 знака. Когато
самата целева страница не може да бъде извлечена, услугата нагоре по веригата съобщава това в HTTP 200;
OmniRoute го представя като `422` с фиксирано съобщение.

| Метод | Път             | Описание                                                              |
| ----- | --------------- | --------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Извличане/обхождане на URL — тялото се валидира от `v1WebFetchSchema` |

**Удостоверяване:** Bearer API ключ (`extractApiKey` + `isValidApiKey`). Политиката се прилага чрез `enforceApiKeyPolicy`.

**Резервен избор, съобразен с квотата (#8297):** когато не е зададен изрично `provider`, пулът
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) се
обхожда във фиксиран
ред на приоритет (запълване на първия) — конфигуриран доставчик с ограничена честота на заявките се пропуска,
вместо заявката да бъде прекратена незабавно, а повторим отказ/изчерпана квота на услуга нагоре по веригата
(HTTP 429 винаги; 402/403 за безплатните нива с квотен модел на Firecrawl/Tavily/TinyFish —
не и за Jina Reader и никога при обикновена невалидна заявка 400) води до преминаване към
следващия неизпробван доставчик с налични идентификационни данни по време на заявката. Когато всички доставчици в
пула са изчерпани, крайната точка връща един отговор `429` (със заглавка `Retry-After`),
вместо предишния общ отговор `400`. Когато изрично е заявен `provider`, **няма**
неявен резервен избор — изрично избран доставчик с ограничена честота или с грешка
връща собствената си грешка (`429`, ако честотата е ограничена, в противен случай състоянието
от услугата нагоре по веригата).

## Поточно предаване чрез WebSocket

```bash
GET /v1/ws?handshake=1
```

Валидира заявка за надграждане до WebSocket и връща примерните съобщения на протокола по мрежата (`request`, `cancel`). Действителните WS кадри се обработват от включения WS сървър извън таблицата с маршрути на Next.js.

**Удостоверяване:** Bearer API ключ по време на ръкостискането.

### Responses API през WebSocket (само за codex)

```bash
# Същият хост:порт като HTTP API (по подразбиране 20128); надградете връзката:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (или: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Първият кадър ТРЯБВА да бъде response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Прокси за Responses API през WebSocket е свързано **изключително с `codex`** (бекенд на ChatGPT).
То слуша на същия порт като API/таблото за управление по пътищата `/v1/responses`,
`/responses` и `/api/v1/responses`. При първия кадър `response.create` то
удостоверява + подготвя чрез вътрешния мост `codex-responses-ws`, избира
codex OAuth връзка и създава тунел към `wss://chatgpt.com/backend-api/codex/responses`
чрез транспорта `wreq-js`. **Модели, различни от codex, се отхвърлят** (`codex_ws_provider_required`).
За маршрутизиране със споделяне на квота използвайте `model: "qtSd/<group>/codex/<model>"`. Реализирано е в
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Удостоверяване:** Bearer API ключ по време на ръкостискането. Включеният HTTP сървър (`server-ws.mjs`)
трябва да бъде активната входна точка (по подразбиране е така, когато съществува `app/server-ws.mjs`).

#### Идентификатор на модела: използвайте самостоятелния ChatGPT идентификатор (без префикс `codex/`)

**Codex CLI** на OpenAI валидира името на модела от страна на клиента, когато
`supports_websockets = true`, и **отхвърля идентификатори с префикс на доставчик** като
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Изпращайте **самостоятелния** идентификатор (напр. `gpt-5.5`). Мостът на OmniRoute е
само за codex, затова преди тунелирането към услугата нагоре по веригата той отново разрешава самостоятелния идентификатор като codex модел
(`resolveCodexWsModelInfo`) — въпреки че самостоятелен
`gpt-5.5` иначе би бил маршрутизиран към друг доставчик през HTTP.

#### Конфигуриране на OpenAI Codex CLI

Насочете Codex CLI към OmniRoute, като добавите персонализиран доставчик с поддръжка на WebSocket
в `~/.codex/config.toml` (използвайте отделен `CODEX_HOME`, за да не променяте
съществуваща конфигурация):

```toml
model = "gpt-5.5"                 # самостоятелен идентификатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без завършваща наклонена черта; WS URL адресът се извежда оттук (използвайте https/wss в продукционна среда)
wire_api = "responses"                    # единствената поддържана стойност от февруари 2026 г.
supports_websockets = true                # активира транспорта Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # съдържа API ключа за OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API ключ за OmniRoute (произволен ключ, ако REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI надгражда `base_url + /responses` до WebSocket, а OmniRoute го тунелира
към избраната codex OAuth връзка. Валидирано от край до край спрямо локалния
сървър: ChatGPT връща `codex.rate_limits` + `response.created` и предава поточно
завършения отговор.

## Самостоятелна проверка на потреблението (`/api/usage/om-usage`)

Всеки API ключ може да чете **собственото си** потребление и квоти — без удостоверяване за управление. Това е крайната точка, която
клиентът (CLI, панелът OmniCopilot) използва, за да покаже на притежателя на ключ неговите разходи.

```bash
# Текстов формат (историческият договор — обикновен текст за терминал)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Структуриран формат — използван от потребителски интерфейс
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

За ключа трябва да е активирано **`allowUsageCommand`** (по подразбиране е изключено — мениджърът на API ключове
в таблото го превключва поотделно за всеки ключ). Без него крайната точка връща `403`.

`?format=json` връща дискриминирана структура, така че извикващата страна никога да не прочете поле с данни от
отказ. При успех:

```jsonc
{
  "allowed": true,
  // присъства само когато за ключа са активирани лимити за потребление по ключ (дневни/седмични в USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // моментната снимка на квотата за избрания доставчик или null, когато все още няма кеширани данни:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // моментната снимка на всяка връзка, така че потребителският интерфейс да може да визуализира няколко доставчика един до друг:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При отказ (`401` невалиден ключ / `403` липса на разрешение) същият маршрут връща
`{ "allowed": false, "error": { "message": "…" } }` — наличен, но празен `personal`/`provider`
(ключът е разрешен, но все още няма получени данни) е различно състояние от отказ и само JSON форматът
ги разграничава.

**Удостоверяване:** собственият Bearer API ключ на извикващата страна, валидиран чрез `isValidApiKey` — това _не е_
интерфейсът за управление (`/api/keys/…`), който остава защитен от `requireManagementAuth`.

### Необработени спрямо коригирани спрямо прага проценти на квотата

При използване на `/api/usage/om-usage` извикващите страни трябва да имат предвид разликата между
процентите, представени в **обикновения текстов изход**, и структурирания **JSON изход**:

| Аспект                  | Формат с обикновен текст (`/api/usage/om-usage` / `@@om-usage`)                                        | JSON формат (`?format=json`)                                                             |
| :---------------------- | :----------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------- |
| **Изходно поле**        | `NN% left` (напр. `20% left`)                                                                          | `provider.quotas` / `providers[].quotas`                                                 |
| **Измерване**           | **Използваем лимит, коригиран спрямо прага**: оставащ капацитет над прага за прекъсване                | **Необработена квота от доставчика**: некоригирано измерване от доставчика               |
| **Мащабиране по прага** | Мащабира се чрез `effectiveRemainingPercent()`, така че защитеният резерв да се показва като `0% left` | Няма (необработени стойности от моментната снимка, отчетени от доставчика)               |
| **Данни за праговете**  | Включени са в показвания процент                                                                       | Съхраняват се в `quotaWindowThresholds` за всяка връзка (или по подразбиране на сървъра) |
| **Основен потребител**  | Интерактивни CLI инструменти, подкани в терминала, оператори                                           | Програмни интеграции, табла, анализи, системи за проследяване на таксуването             |

#### Формулата за корекция спрямо прага

OmniRoute поддържа проактивни прагове за прекъсване на квотата с цел предотвратяване на изчерпването ѝ при доставчика (конфигурирани чрез
`quotaWindowThresholds` на връзката, настройките по подразбиране на доставчика или глобалните настройки за устойчивост). Когато праг за прекъсване
(напр. `cutoff = 25%`) е активен за прозорец на квотата, текстовият визуализатор изчислява оставащия лимит по следния начин:

- Ако `remaining <= cutoff`: връща `0%`.
- Ако `remaining > cutoff`: връща `((remaining - cutoff) / (100 - cutoff)) * 100`.

Форматираният текстов изход закръгля това до най-близкото цяло число (`Math.round(...)`).

#### Илюстративен пример

Да разгледаме прозорец на доставчик с **60% необработено потребление** (следователно **40% необработена оставаща квота**) и конфигуриран
праг за прекъсване при **25% оставаща квота**:

| Представяне                           | Изчисление                                         | Оставащи |          Подразбиращо се използване          |
| :------------------------------------ | :------------------------------------------------- | :------: | :------------------------------------------: |
| **Необработен JSON (`?format=json`)** | Моментна снимка от доставчика (`quotas[window]`)   | **40%**  |                   **60%**                    |
| **Текстов формат (`NN% left`)**       | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (ако се изчислява `100 - remaining`) |

- **Защо текстът показва 20% оставащи:** От физически оставащите 40% квота в акаунта 25% са запазени от
  политиката за прекъсване. Извикващата страна разполага само с 15% от общо 75% използваем оставащ резерв, преди маршрутизаторът да спре
  да насочва заявки към тази връзка. Мащабирането гарантира, че връзката сигнализира изчерпване (`0% left`) точно когато
  маршрутизирането бъде преустановено.
- **Защо JSON запазва необработените стойности:** JSON полезният товар връща точната моментна снимка от доставчика (`UsageSnapshot`),
  така че външните инструменти да имат достъп до достоверното потребление при доставчика и
  `quotaWindowThresholds` на ниво връзка без загуба на информация от мащабиране на сървъра.

#### Насоки за миграция на потребителите

Ако външна интеграция (като плъгин за редактор или разширение на агент) преди е извличала данни от текстовата
крайна точка (`NN% left`) и е изчислявала използвания процент като `100 - NN`, преминаването към `?format=json` означава:

- Прочитането на необработените JSON стойности ще отразява **действителното потребление нагоре по веригата** (60% използвани в примера по-горе).
- Ако интеграцията желае да запази семантиката за използваемия оставащ лимит на текстовата крайна точка, тя може да изчисли
  ефективната формула за оставащия лимит от страна на клиента, като използва `quotaWindowThresholds` за замествания на ниво връзка.

## Семантичен кеш

```bash
# Получаване на статистика за кеша
GET /api/cache/stats

# Изчистване на всички кешове
DELETE /api/cache/stats
```

Примерен отговор:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Влияние върху латентността

При ПОПАДЕНИЕ в семантичния кеш отговорът се предоставя от кеша **без заявка
към доставчика**, така че отчетената стойност на `X-OmniRoute-Response-Latency` е почти нулева
(независимо от първоначалната латентност на доставчика). Клиентите, чувствителни към
латентността (сравнителни тестове, наблюдение на p50/p99), трябва да проверяват
HTTP заглавката на отговора `X-OmniRoute-Cache-Latency`:

| Стойност    | Значение                                                                        |
| ----------- | ------------------------------------------------------------------------------- |
| `synthetic` | Отговорът е предоставен от кеша; латентността не е реалното време на доставчика |
| _(липсва)_  | Отговор от реална заявка към доставчика                                         |

### Заобикаляне на кеша за отделен ключ

API ключовете могат да изключат четенето от семантичния кеш чрез `cacheDefaultMode`:

| Стойност | Поведение                                                      |
| -------- | -------------------------------------------------------------- |
| `legacy` | Нормално поведение на кеша (по подразбиране)                   |
| `bypass` | Напълно пропуска проверката на кеша; винаги заявява доставчика |

Задава се при създаване на ключ (`POST /api/keys`) или при актуализиране (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Заобикаляне за отделна заявка

Всяка заявка може да заобиколи кеша независимо от настройките на ключа:

```
X-OmniRoute-No-Cache: true
```

За синхронизирани/импортирани модели `PUT /api/provider-models` приема `provider`, `modelId` и
`maxOutputTokenOverride`: положително цяло число задава ръчно ограничение за изходните токени, а `null`
го премахва, за да възстанови стойността по подразбиране. `GET /api/provider-models?provider=<provider>` връща тези
стойности в `modelOutputOverrides`, включително за модели без запис за персонализиран модел. Заместването
използва възможността `max_output_tokens` по време на изпълнение и се запазва при повторно синхронизиране на модела. Страницата на
съвместимия с OpenAI доставчик предлага същите контроли за редактиране/изчистване и обозначава моделите с изрично поддържане на визуални данни.

Персонализираните възли за Chat Completions адаптират изричното изключване на разсъжденията към сървъра нагоре по веригата. При
успешен тест на връзката автоматично се избират контроли за шаблона за чат за всеки точен идентификатор на модел,
чийто запис в `/models` доказва разпозната стойност на `owned_by`: `vllm`, `sglang` или `llamacpp`.
Прозрачните обвивки, съвместими с OpenAI, могат да запазят оригиналния запис на модела във вложен
обект `openai`; откриването проследява до три такива обвивки. Моделите с липсваща, неизвестна или
противоречива собственост запазват обичайното поведение на OpenAI. Откриването използва повторно съществуващата заявка към каталога,
не генерира токени за завършване и се анулира, когато крайната точка на връзката се промени.

За да фиксирате поведението за сървър, който не предоставя тези метаданни, използвайте съществуващия API за частично
актуализиране на доставчика:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Изпратете това тяло чрез `PUT /api/providers/<connection-id>`. За тази връзка изрично зададеното
усилие за разсъждение `none` се изпраща като `chat_template_kwargs.thinking=false` и
`chat_template_kwargs.enable_thinking=false`. Изричните собствени стойности на шаблона остават водещи,
освен ако правило за разсъждение от страна на сървъра не налага определено усилие. Настройката се прилага само когато персонализирана
връзка, съвместима с OpenAI, изпраща тяло на Chat Completions; заявките към Responses и обикновените
доставчици запазват собствената си структура на заявките. Задайте `reasoningControl` на `openai`, за да наложите обичайното за OpenAI
директно предаване на `reasoning_effort`, или го пропуснете/задайте на `null`, за да използвате автоматично откриване.

Заявките на класификатора в автоматичния режим на Claude Code по подразбиране изключват собственото разсъждение, когато
не съдържат изрични контроли за разсъждение. Откриването използва системния маркер на класификатора в заявки
във формат Claude, а не имена на модели или ограничения за завършване. Изричните контроли в тялото, поддържаните заглавки за усилие/разсъждение,
правилата за маршрутизиране и определеното усилие на модела запазват съществуващия си приоритет. И двата етапа на класификатора
запазват своите подкани, ограничения за завършване, последователности за спиране и реални решения за разрешения от сървъра
нагоре по веригата; вторият етап все още може да генерира поисканото видимо разсъждение като обикновен текст.

### Разрешения за API ключове

`PATCH /api/keys/{id}` актуализира разрешенията на съществуващ ключ. Подобно на всеки маршрут `/api/keys*`, той изисква оторизация за управление (вижте [Удостоверяване за управление](../guides/MANAGEMENT-AUTH.md)), а не ключ за инференция. Изпращайте само полетата, които искате да промените; заявка без нито едно от тях се отхвърля с `No valid fields to update`. Приеманите полета са дефинирани от `updateKeyPermissionsSchema` в `src/shared/validation/schemas/keys.ts`.

| Поле                                        | Тип                                                                     | Бележки                                                                                                                                |
| ------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                                      | низ, 1–200 знака                                                        |                                                                                                                                        |
| `isActive`                                  | булева стойност                                                         |                                                                                                                                        |
| `isBanned`                                  | булева стойност                                                         |                                                                                                                                        |
| `expiresAt`                                 | дата и час по ISO 8601 или `null`                                       | `null` изчиства срока на валидност                                                                                                     |
| `modelAccessMode`                           | `all` \| `restricted`                                                   | `allowedModels` трябва да е празен, когато режимът е `all`                                                                             |
| `allowedModels`, `blockedModels`            | масив от низове, до 1000                                                |                                                                                                                                        |
| `allowedCombos`                             | масив от низове, до 500                                                 | Ограничава кои комбинации може да извиква ключът; директните модели се управляват от `modelAccessMode` / `allowedModels`               |
| `connectionAccessMode`                      | `all` \| `restricted`                                                   | `allowedConnections` не трябва да е празен при `restricted` и трябва да е празен при `all`                                             |

### Версия и канал за издания

```bash
GET /api/system/version
```

Маршрут за управление, достъпен само през loopback (удостоверяване на администратор). Връща изпълняваната версия, най-новата
публикувана версия и състоянието на автоматичното обновяване. `releaseChannel` и `channels` са допълнителни
полета (линия 3.8.54); `channel` запазва значението си — режимът на внедряване, който програмата за обновяване на таблото
използва (`npm`, `source` или `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm каналът на изпълняваната компилация: `nightly` за версии `-nightly.*`,
  `next` за други предварителни издания (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` за стабилна версия от
  по-стара основна версия от `channels.latest`, а във всички останали случаи — `latest`. Използва същите правила като
  `scripts/release/dist-tag.mjs`, който избира npm dist-tag при публикуване.
- `channels` — най-новата публикувана версия за всеки dist-tag, получена от `npm view omniroute dist-tags` (с резервно
  извличане чрез HTTP от регистъра), кеширана със същия TTL от 10 минути като `latest`. `latest` винаги присъства
  (при невъзможност се използва полето `latest`, а след това `"unavailable"`); `next`, `nightly` и `lts` се показват
  само когато съответният dist-tag съществува. Заявка с `Cache-Control: no-cache` обновява и двете справки.

Моделът на каналите (`latest` = v3 до общата наличност на 4.0, `next` = rc, `nightly` = компилации от `develop`,
`lts` = корекции за v3 след общата наличност на 4.0) е описан в `docs/ops/RELEASE_STRATEGY.md`.

## Аудиотранскрипция

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибирайте аудиофайлове чрез всеки конфигуриран STT доставчик. Първият сегмент от пътя избира собствения доставчик (`openai/…`, `deepgram/…`). Шлюзовете, които предоставят повторно модел на друг доставчик, използват квалифициран идентификатор (`openrouter/deepgram/nova-3`).

**Заявка:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Отговор:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Примерни идентификатори на модели:** `openai/whisper-1` (изисква ключ за OpenAI),
`openrouter/deepgram/nova-3` (изисква ключ за OpenRouter),

## Ограничения на токените

Бюджети за **токени** за всеки API ключ (различни от базирания на USD бюджет по-горе). Прилагат се директно по пътя на заявката: когато използването на ключа в текущия прозорец достигне неговото ограничение, заявките се отхвърлят с `429 Too Many Requests`. Ограниченията могат да бъдат обвързани с конкретен `model`, `provider` или да бъдат прилагани глобално (`global`) за целия ключ; когато няколко ограничения съответстват на дадена заявка, се прилага най-строгото.

```bash
# Извеждане на ограниченията за токени на даден ключ (включва текущото използване в прозореца)
GET /api/usage/token-limits?apiKeyId=key-123

# Създаване или актуализиране на ограничение за токени
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Изтриване на ограничение за токени по идентификатор
DELETE /api/usage/token-limits?id=tl-abc
```

> **Бележки за схемата** (`setTokenLimitSchema`): `apiKeyId` и `scopeType` (`model` | `provider` | `global`) са задължителни. `scopeValue` е задължително, освен ако `scopeType` е `global` (напр. идентификатор на модел за обхват `model`, идентификатор на доставчик за обхват `provider`). `tokenLimit` трябва да бъде положително цяло число (преобразува се от низ). Незадължителни: `id` (пропуснете го при създаване, подайте го при актуализиране), `resetInterval` (`daily` | `weekly` | `monthly`, по подразбиране `monthly`), `resetTime` (`HH:MM`), `enabled` (по подразбиране `true`). Отговорите на `GET` допълват всяко ограничение с `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` и `nextResetAt`. Това е крайна точка от управленски клас (удостоверяването се прилага централизирано от конвейера за оторизация).

## Обработка на заявки

1. Клиентът изпраща заявка към `/v1/*`
2. Манипулаторът на маршрута извиква `handleChat`, `handleEmbedding`, `handleAudioTranscription` или `handleImageGeneration`
3. Моделът се определя (директен доставчик/модел или псевдоним/комбинация)
4. Идентификационните данни се избират от локалната БД с филтриране според наличността на акаунта
5. За чат: `handleChatCore` проверява семантичния кеш/кеша за сигнатури и определя настройките за компресиране на комбинацията
6. Проактивното компресиране се изпълнява преди преобразуването за доставчика, когато е активирано (`lite`, Caveman, RTK или съчетание от тях)
7. Изпълнителят за доставчика изпраща заявката към външната услуга
8. Отговорът се преобразува обратно към клиентския формат (чат) или се връща непроменен (векторни представяния/изображения/аудио)
9. Използването, анализите за компресирането и регистрационните записи на заявките се записват
10. При грешки се прилага резервен вариант съгласно правилата на комбинацията

Пълно описание на архитектурата: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Устойчивост (разширено)

OmniRoute предоставя три независими механизма за временни неизправности; посочените по-долу крайни точки за управление позволяват на операторите да преглеждат и заменят настройките им:

| Обхват                 | Съхранение на състоянието                      | Преглед                                   | Нулиране / изчистване                                             |
| ---------------------- | ---------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| Прекъсвач на доставчик | `domain_circuit_breakers` + в паметта          | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                      |
| Изчакване на връзка    | `rateLimitedUntil` във връзките към доставчици | `/api/rate-limits`, `/api/providers/[id]` | (активира се отново отложено; изчиства се чрез PUT на доставчика) |
| Блокиране на модел     | Регистър в паметта за достъпност на моделите   | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                          |

`PATCH /api/resilience` приема заместващи настройки за прекъсвачите на доставчици в `providerBreaker.oauth` и `providerBreaker.apikey`. Всеки профил поддържа `degradationThreshold`, `failureThreshold` и `resetTimeoutMs`; същите полета са налични в Табло → Настройки → Устойчивост.

```bash
# Изчистване на блокирането на един модел
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Изчистване на всички блокирания
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

За пълно концептуално описание и стойностите по подразбиране на прекъсвачите вижте [`CLAUDE.md`](../../CLAUDE.md) → „Resilience Runtime State“ и [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Опашка при ограничаване на честотата и предпазен механизъм за автоматично активиране

- **Поддържан начин за запис**: `POST /api/rate-limits` с тяло `{"connectionId": "<id>", "enabled": true|false}` е поддържаната крайна точка за управление на включването и изключването на защитата от ограничаване на честотата за дадена връзка. `PUT /api/providers/[id]` умишлено не променя и не превключва `rateLimitProtection` (#11278).
- **Семантика на `enabled: false`**: Задаването на `enabled: false` премахва изричната защита за връзката, но **не** изключва активна връзка с API ключ от глобалния предпазен механизъм за автоматично активиране (`autoEnableApiKeyProviders = true`). В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) `false` и `undefined` са еквивалентни; активните връзки с API ключ без изрично зададена защита остават защитени от предпазния механизъм за автоматично активиране.
- **Глобално деактивиране**: За да използвате връзки с API ключ без опашки при ограничаване на честотата, деактивирайте глобално предпазния механизъм чрез `RATE_LIMIT_AUTO_ENABLE=false` (променлива на средата) или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Настройки → Устойчивост / `PATCH /api/resilience`).

## MCP сървър

OmniRoute включва вграден сървър за Model Context Protocol с 3 транспорта (stdio, SSE, streamable-http) и инструменти с определен обхват. Крайните точки на таблото по-долу четат данни за състоянието/одита и проксират HTTP транспортите.

| Метод | Път | Описание |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Сигнал за активност, транспорт, онлайн състояние, последно извикване, най-използвани инструменти, процент на успешните операции за 24 часа |
| GET | `/api/mcp/tools` | Списък с MCP инструменти с `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Отваряне на SSE поток за SSE транспорта (връща `503`, ако MCP е деактивиран или транспортът не съвпада) |
| POST | `/api/mcp/sse` | Изпращане на JSON-RPC рамка през SSE транспорта |
| GET | `/api/mcp/stream` | Отваряне на SSE страната на транспорта Streamable HTTP (инициирани от сървъра съобщения) |
| POST | `/api/mcp/stream` | Изпращане на JSON-RPC рамка през транспорта Streamable HTTP |
| DELETE | `/api/mcp/stream` | Прекратяване на сесия на Streamable HTTP |
| GET | `/api/mcp/audit` | Заявка към одитния дневник — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Обобщена одитна статистика (общ брой, процент на успех, средна продължителност, най-използвани инструменти) |

**Удостоверяване:** транспортите `sse`/`stream` използват специфичния за MCP механизъм за удостоверяване (Bearer API ключ с обхват `mcp`); маршрутите `status`/`tools`/`audit*` са достъпни за четене от таблото (не се изисква допълнително удостоверяване освен достъп до хоста на таблото).

> И двата HTTP транспорта се управляват от `settings.mcpEnabled` и `settings.mcpTransport` — несъответствие на транспорта връща `400`, а деактивирано състояние на MCP връща `503`.

## A2A сървър

OmniRoute предоставя A2A (Agent-to-Agent) крайна точка за JSON-RPC 2.0, както и REST обвивка за проверка и използване от таблото за управление.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # незадължително, освен ако е зададена OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Поддържани методи (всички зависят от `settings.a2aEnabled`):

| Метод            | Описание                                                            |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Синхронно изпълнение на умение; връща `{task, artifacts, metadata}` |
| `message/stream` | Поточно SSE изпълнение на същия набор от умения                     |
| `tasks/get`      | Извличане на задача по `taskId`                                     |
| `tasks/cancel`   | Отмяна на задача по `taskId`                                        |

Вградени умения: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Карта на агента

```bash
GET /.well-known/agent.json
```

Връща публичната A2A карта на агента (име, описание, възможности, каталог с умения, схема за удостоверяване) — публично кеширана за 1h. Не се изисква удостоверяване.

### REST помощни интерфейси

| Метод | Път                          | Описание                                                                                                               |
| ----- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Състояние на A2A + статистика за задачите + обобщение на кешираната карта на агента                                    |
| GET   | `/api/a2a/tasks`             | Списък със задачи — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не е реализиран като REST помощен интерфейс — създавайте чрез JSON-RPC `message/send`)                                |
| GET   | `/api/a2a/tasks/[id]`        | Извличане на една задача                                                                                               |
| POST  | `/api/a2a/tasks/[id]/cancel` | Отмяна на задача                                                                                                       |

**Удостоверяване:** REST помощните интерфейси работят без административно удостоверяване (достъпни са за четене от таблото за управление); JSON-RPC маршрутът `/a2a` използва Bearer `OMNIROUTE_API_KEY`, ако е конфигуриран.

## Приставки

Управлявайте приставките на OmniRoute (разширения от трети страни).

| Метод  | Път                                | Описание                                     |
| ------ | ---------------------------------- | -------------------------------------------- |
| GET    | `/api/plugins`                     | Изброяване на инсталираните приставки        |
| POST   | `/api/plugins/marketplace/install` | Инсталиране на приставка от пазара           |
| DELETE | `/api/plugins/[name]`              | Деинсталиране на приставка                   |
| POST   | `/api/plugins/[name]/activate`     | Активиране на приставка                      |
| POST   | `/api/plugins/[name]/deactivate`   | Деактивиране на приставка                    |
| GET    | `/api/plugins/[name]/config`       | Получаване на конфигурацията на приставка    |
| PUT    | `/api/plugins/[name]/config`       | Актуализиране на конфигурацията на приставка |

**Удостоверяване:** Изисква сесия за управление.

Вижте [Рамка за приставки](../frameworks/PLUGIN_SDK.md) за пълни подробности.

## Паралелно маршрутизиране

Паралелното / A-B сравнение на доставчици **не е самостоятелен REST интерфейс** — то се конфигурира чрез комбинирано маршрутизиране (вижте [Автоматично комбиниране](../routing/AUTO-COMBO.md)). Метриките за сравнение за всяка комбинация се предоставят чрез `GET /api/combos/metrics`.

## Защитни механизми

Проверявайте защитните механизми по време на изпълнение (откриване на лични данни, откриване на инжектиране в подкани, свързване с визуални модели). Защитните механизми се изпълняват при всяка заявка; изключването за отделно извикване става чрез заглавката на заявката `x-omniroute-disabled-guardrails` — няма постоянен интерфейс за активиране/деактивиране.

| Метод | Път                    | Описание                                                                                                          |
| ----- | ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/guardrails`      | Изброяване на регистрираните защитни механизми и тяхното състояние (име / активиран / приоритет)                  |
| POST  | `/api/guardrails/test` | Пробно изпълнение на конвейера преди извикване върху примерни входни данни — тяло: `{input, disabledGuardrails?}` |

**Удостоверяване:** Изисква сесия за управление.

Вижте [Сигурност > Защитни механизми](../security/GUARDRAILS.md) за пълни подробности.

## Удостоверяване

Вижте [Удостоверяване за управление](../guides/MANAGEMENT-AUTH.md) за четирите групи идентификационни данни (сесия на таблото за управление, локален CLI токен, `oma_live_…` токен за достъп, API ключ с обхват за управление) и по какво се различават от ключовете за изпълнение на заявки.

- Маршрутите на таблото за управление (`/dashboard/*`) използват бисквитката `auth_token`
- При влизане се използва запазеният хеш на паролата; резервният вариант е `INITIAL_PASSWORD`
- `requireLogin` може да се включва или изключва чрез `/api/settings/require-login`
- Маршрутите `/v1/*` по избор изискват Bearer API ключ, когато `REQUIRE_API_KEY=true`
- „токен за управление“ / „API ключ с обхват за управление“ в тази справка означава една от групите в посоченото ръководство — не недефиниран допълнителен тип тайна

> **Несъвместима промяна (v3.8.0)** — `/api/v1/agents/tasks/*` и крайните точки за управление на периода на изчакване вече изискват **удостоверяване за управление** (бисквитката `auth_token` на таблото за управление или API ключ с обхват за управление). Клиентите, които преди са извиквали тези маршрути без удостоверяване, ще получат `401 Unauthorized`. Вижте commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
