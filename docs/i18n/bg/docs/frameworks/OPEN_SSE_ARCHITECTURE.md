> **Накратко**: `open-sse/` е основният стрийминг механизъм, който обслужва всяка LLM заявка в OmniRoute. Той съдържа ~1 400 файла, реализиращи конвейера за заявки, изпълнителите, услугите, MCP сървъра и слоя за преобразуване. Това ръководство обяснява как отделните компоненти работят заедно.

**Изходен код:** `open-sse/` (пакет в работното пространство, ~1 440 `.ts` файла без тестовете)

## Защо отделен пакет в работното пространство?

`open-sse/` е **самостоятелно работно пространство** в монорепото на OmniRoute поради няколко причини:

1. **Повторна употреба** — `open-sse` се публикува като `@omniroute/open-sse` в npm, така че други проекти могат да го използват независимо
2. **Ясни граници** — стрийминг механизмът е отделен от специфичния за OmniRoute слой за потребителски интерфейс/база данни
3. **Производителност** — механизмът няма зависимости от Next.js, което позволява по-бързо студено стартиране в CLI/сървърлес среди
4. **Версиониране** — `open-sse` може да публикува версии по собствен график

```json
// package.json
"workspaces": ["open-sse"]
```

## Конвейерът за заявки

Всяка LLM заявка преминава през **5-етапен конвейер**:

```
                              ┌───────────────┐
   HTTP заявка                 │  1. МАРШРУТ   │   разрешаване на комбинация, избор на модел
   (Next.js маршрут)           └──────┬────────┘
                                     │
                                     ▼
                              ┌───────────────┐
                              │  2. ПРЕВОД    │   преобразуване на формат (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬────────┘
                                     │
                                     ▼
                              ┌───────────────┐
                              │  3. ИЗПЪЛНЕНИЕ│   изпълнител на доставчика, HTTP, повторен опит, прекъсвач
                              └──────┬────────┘
                                     │
                                     ▼
                              ┌───────────────┐
                              │  4. ПОТОК     │   SSE преобразуване, обратен натиск
                              └──────┬────────┘
                                     │
                                     ▼
                              ┌───────────────┐
                              │  5. ЗАПИС     │   проследяване на употребата, дневник на извикванията, класификация на грешките
                              └──────┬────────┘
                                     │
                                     ▼
                              HTTP отговор (SSE или JSON)
```

### Етап 1: Маршрутизиране (services/combo.ts)

**Входна точка**: `handleComboChat()` в `services/combo.ts`

Свързва заявката с конкретен кортеж `(provider, model, account, credentials)`:

- Намира комбинацията по ID (или създава виртуална комбинация за модели `auto/*`)
- Прилага стратегията за маршрутизиране (приоритетна, претеглена, циклична и др.)
- Филтрира неизправните доставчици (прекъсвач на веригата)
- Избира следващата подходяща цел

За модели `auto/*` този етап също:

- Изпълнява алгоритъма за **оценяване по 16 фактора** (`services/autoCombo/`)
- Избира двойка `provider+model` въз основа на изправност, цена, латентност и др.

### Етап 2: Преобразуване (translator/)

Ако изходният формат (напр. OpenAI) се различава от целевия формат (напр. Claude), заявката се **преобразува**:

- Системна подкана → системно съобщение
- Дефиниции на инструменти → специфичен за доставчика формат на инструментите
- Параметри за разсъждение/мисловен процес → специфични за доставчика еквиваленти
- Нормализиране на ролите в съобщенията (`developer` → `system` за системи, различни от OpenAI)

`translator/index.ts` предоставя:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Етап 3: Изпълнение (executors/)

**Входна точка**: `getExecutor(providerId).execute(request, options)`

Всички доставчици използват `DefaultExecutor` (`executors/default.ts`) чрез резервния механизъм на фабриката `getExecutor()`. Изпълнителят:

- Създава URL адреса към услугата нагоре по веригата (`buildUrl()`)
- Добавя специфични за доставчика заглавки (`buildHeaders()`)
- Преобразува тялото на заявката (`transformRequest()`)
- Изпраща HTTP заявката с повторни опити и експоненциално изчакване
- Обработва опресняването на удостоверяването при необходимост (за OAuth доставчици)

Всички изпълнители разширяват `BaseExecutor` (`executors/base.ts`, 1170 реда код), който предоставя:

- Обща логика за повторни опити
- Интеграция с прокси сървъри
- Интеграция с прекъсвач на веригата
- Механизми за записване на употребата

### Етап 4: Поточно предаване (utils/stream.ts)

За поточни отговори изпълнителят връща **ReadableStream**. Обработчикът:

- Прекарва потока през SSE преобразуване (`createSSETransformStreamWithLogger`)
- Прилага периодични сигнали за проверка с цел откриване на прекъснати връзки
- Обработва коректно прекъсването на връзката от клиента (`pipeWithDisconnect`)
- Преобразува SSE → JSON за клиенти без поддръжка на поточно предаване

За отговори без поточно предаване изпълнителят връща анализиран JSON обект, който се предава без промени.

### Етап 5: Записване (services/usage.ts)

След отговора (успешен или неуспешен) се записват данни за използването:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` от отговора
- `cost_usd`, изчислена въз основа на ценовите данни
- `latency_ms`, `status`, `error_class` при неуспех
- Данните се съхраняват в таблицата `usage_history`

Артефактите от регистрите на извикванията (ако са активирани) се записват в `${DATA_DIR}/call_logs/`.

## Дълбоко гмуркане на ключови файлове

### chatCore.ts (5977 реда)

The** главен манипулатор на заявки** . Въпреки размера си, той има ясна структура:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

Въпреки че е една огромна функция, тя е организирана в** коментирани секции** които се съпоставят с 5-степенния тръбопровод.

### combo.ts (4456 LOC)

The** двигател за маршрутизиране** който разрешава комбо до подредени цели.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Поддържа** 22 стратегии за маршрутизиране** (вижте `src/shared/constants/routingStrategies.ts`):

### base.ts (1170 LOC)

The** абстрактен изпълнител** че всеки изпълнителен клас се разширява (директно или чрез `DefaultExecutor` и други подкласове). Той съдържа:

- `buildUrl()` — URL конструкция по подразбиране (подкласовете отменят за потребителски)
- `buildHeaders()` — заглавки по подразбиране (auth, content-type)
- `transformRequest()` — преминаване по подразбиране
- `execute()` — главният HTTP цикъл със retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

Специфичното за доставчика поведение (заглавки за удостоверяване, базов URL, заглавки на версия) се конфигурира чрез регистъра на доставчика, а не чрез отделни класове изпълнители.

Най-често по един файл на доставчик. Всички класове изпълнители разширяват `BaseExecutor` и отменят това, което се различава; другите модули са помощници за всеки доставчик (схеми на инструменти, fetch/TTS адаптери, манипулатори на quirk).

### Често срещани модели

Доставчиците се разрешават чрез `getExecutor(providerId)`, който връща конфигурирания изпълнител. OpenAI/Anthropic-compatible доставчиците използват `DefaultExecutor` (`executors/default.ts`). Специфично за доставчика поведение (основен URL, заглавки за удостоверяване, версия API ) се конфигурира в `open-sse/config/providers/`, докато трансформациите на тялото на заявката се обработват в `open-sse/translator/`.

**Персонализиран URL** се задава чрез конфигурация на доставчика:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Персонализирано удостоверяване** се обработва чрез конфигурацията за удостоверяване на регистъра на доставчика (API ключ, OAuth, профили на заглавки).

**Персонализирано тяло на заявката** трансформации (напр. Anthropic, разделяща `system` от `messages`) се регистрират за всеки доставчик в `open-sse/translator/`.

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Резолюцията минава през `ExecutorRegistry` (`executors/registry.ts`): всеки специализиран изпълнител се декларира във вградената таблица на `executors/index.ts` и се регистрира чрез `registerExecutor(alias, instance)` при зареждане на модула; `getExecutor()` се консултира с регистъра и се връща към мемоизиран `DefaultExecutor` за всеки доставчик без специализиран запис. Пълното съпоставяне на изпълнителя на псевдоним → се характеризира със златния тест `tests/unit/executor-map-golden.test.ts`.

## Преобразуватели

Преобразуват между **3 формата**: OpenAI, Anthropic, Gemini, както и новия Responses API.

### Кога се извършва преобразуването

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Често срещани преобразувания:

- `OpenAI → Anthropic`: отделно поле `system`, заглавка `x-api-key`
- `OpenAI → Gemini`: `contents` вместо `messages`, `systemInstruction`
- `OpenAI → Responses API`: масив `input`, състояние `previous_response_id`

### Обработвани гранични случаи

- Роля `developer` → `system` за формати, различни от OpenAI
- Роля `system` → обединява се с първото потребителско съобщение за GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` на Gemini
- `tools` → специфичен за доставчика формат на инструментите
- Параметри за мисловен процес (o1, Claude) → специфични за доставчика еквиваленти

## MCP сървър

`open-sse/mcp-server/` реализира сървъра за **Model Context Protocol**:

- **110 инструмента** (управление на доставчици, комбинации, памет, кеш, компресиране, прокси, умения, геймификация, приставки, Notion, Obsidian, локален корпус)
- **3 транспорта**: stdio, SSE, Streamable HTTP
- **33 обхвата** за детайлно управление на оторизацията

### Регистриране на инструменти

Инструментите се регистрират като самостоятелни файлове в `open-sse/mcp-server/tools/`, като всеки експортира име, схема, обработчик и обхват:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Получаване на моментна снимка на състоянието на системата",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Транспорти

```ts
// stdio (използване чрез CLI)
startMcpStdio(server);

// SSE (поточно предаване чрез HTTP)
startMcpSse(server, port);

// Streamable HTTP (съвременен MCP)
startMcpStreamable(server, port);
```

### Оторизация

Всяко извикване на инструмент преминава през проверки на обхвата (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Недостатъчен обхват");
}
```

## Трансформатори

`open-sse/transformer/` преобразува между форматите **Chat Completions** и **Responses API**.

### Защо е необходим отделен трансформатор?

Responses API е новият формат на OpenAI с **разговори със състояние** (`previous_response_id`). Когато клиент изпрати заявка във формат Responses, OmniRoute:

1. Вътрешно преобразува Responses → Chat Completions
2. Изпраща заявката до доставчика (който и да е доставчик, поддържащ Chat Completions)
3. Преобразува отговора обратно във формат Responses
4. Предава поточно преобразувания отговор към клиента

Трансформаторът (`transformer/responsesTransformer.ts`) предоставя:

```ts
createResponsesApiTransformStream(): TransformStream
```

Той обработва:

- Събития `response.output_item.added`
- Събития `response.output_text.delta`
- Събитие `response.completed`
- Съпоставяне на извикванията на инструменти (`function_call` ↔ `tool_calls`)

## Конфигурация

`open-sse/config/` държи конфигурационния слой:

| Файл                          | Цел                                                     |
| ----------------------------- | ------------------------------------------------------- |
| `providerRegistry.ts`         | Регистър на модела за чат над каталога с 394 доставчици |
| `providerModels.ts`           | Псевдоними на модели, съпоставяне на формати            |
| `constants.ts`                | Изчаквания, ограничения, кодове за състояние            |
| `defaultThinkingSignature.ts` | Подпис за мислене Claude по подразбиране                |
| `modelStrip.ts` (в услуги)    | Отстраняване на полета за всеки доставчик               |

### Схема на регистъра на доставчика

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod валидирането при зареждане на модул гарантира, че всички конфигурации на доставчика са валидни.

Маршрутизиращият механизъм има строги ограничения за производителността:

| Операция                                                 | Целева стойност | Измерване                       |
| -------------------------------------------------------- | --------------- | ------------------------------- |
| Разрешаване на комбинация                                | <10ms           | За 50 цели                      |
| Проверка на ограничението на честотата                   | <1ms            | In-memory token bucket          |
| Резервен избор в рамките на семейство от модели          | <5ms            | Кеширани дефиниции на семейства |
| Насочване на заявка                                      | <2ms            | Критичен път                    |
| **Без блокиращ I/O в критичния път на маршрутизирането** | —               | Изцяло асинхронно               |

## Антипатерни

❌ **Синхронни извиквания към БД в `combo.ts`** — изчислявайте предварително и кеширайте
❌ **Логика за повторни опити в обработчиците** — използвайте `retry()` от услугата за устойчивост
❌ **Директен достъп до конфигурацията на доставчика** — използвайте getter методите на `providerRegistry`
❌ **Твърдо кодирани вериги за резервен избор** — дефинирайте ги в `modelFamilyFallback.ts`
❌ **Промени на състоянието между паралелни заявки** — използвайте само контекст с обхват на заявката

## Добавяне на нов компонент

### Добавяне на нова услуга

1. Създайте `open-sse/services/[serviceName].ts` с ясно фокусирана отговорност
2. Експортирайте основната функция за обработка и всички константи
3. Добавете модулни тестове в `tests/unit/services/[serviceName].test.mjs`
4. Интегрирайте в конвейера за обработка на заявки в `handlers/chatCore.ts` (ако е свързано с маршрутизирането)
5. Актуализирайте логиката за маршрутизиране в `combo.ts`, ако услугата влияе върху избора на цел
6. Документирайте в този файл

### Добавяне на нов изпълнител

1. Създайте `open-sse/executors/[provider].ts`, който разширява `BaseExecutor`
2. Регистрирайте го в `config/providerRegistry.ts`
3. Добавете го към фабриката в `executors/index.ts`
4. Добавете модулни тестове за изпълнителя
5. Документирайте в `docs/architecture/ARCHITECTURE.md`

### Добавяне на нов MCP инструмент

1. Създайте или актуализирайте `open-sse/mcp-server/tools/[category]Tools.ts`
2. Дефинирайте Zod схема за входните данни
3. Регистрирайте инструмента в `mcp-server/index.ts`
4. Добавете го към матрицата на обхватите в `mcp-server/auth/`
5. Добавете модулни тестове
