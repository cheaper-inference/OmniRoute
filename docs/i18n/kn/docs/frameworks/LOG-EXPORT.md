OmniRoute ಕರೆ ಲಾಗ್‌ಗಳನ್ನು ಬಾಹ್ಯ ವಿಶ್ಲೇಷಣಾ ಸಂಗ್ರಹಕ್ಕೆ ನಿರಂತರವಾಗಿ, ಹಂತಹಂತವಾಗಿ ರಫ್ತು ಮಾಡುವುದು.

ಲಾಗ್‌ಗಳ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಟ್ಯಾಬ್ ವಿನಂತಿಗಳ ಇತಿಹಾಸವನ್ನು SQLite (`call_logs`) ನಲ್ಲಿ ಉಳಿಸುತ್ತದೆ; ಇದು
ರೊಟೇಶನ್ ಮತ್ತು ಧಾರಣೆಯ ಮಿತಿಗಳಿಗೆ ಒಳಪಟ್ಟಿರುತ್ತದೆ. ಲಾಗ್ ರಫ್ತು ಅದೇ ದಾಖಲೆಗಳ ಗುಂಪನ್ನು ನಿಗದಿತ ವೇಳಾಪಟ್ಟಿಯಂತೆ ಹೊರಗೆ ಕಳುಹಿಸುತ್ತದೆ, ಇದರಿಂದ ಅದು
ಸ್ಥಳೀಯ ಡೇಟಾಬೇಸ್‌ಗಿಂತ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯಬಹುದು ಮತ್ತು ಇತರ ಡೇಟಾದೊಂದಿಗೆ ಜೋಡಿಸಬಹುದು. BigQuery ಮೊದಲ ಗಮ್ಯಸ್ಥಾನವಾಗಿದೆ;
ಪೈಪ್‌ಲೈನ್ ಒಂದು ರಿಜಿಸ್ಟ್ರಿಯಾಗಿರುವುದರಿಂದ, ಮತ್ತಷ್ಟು ಗಮ್ಯಸ್ಥಾನಗಳನ್ನು ಹೆಚ್ಚುವರಿಯಾಗಿ ಸೇರಿಸಬಹುದು.

## 1. ಇದು ಹೇಗೆ ಕೆಲಸ ಮಾಡುತ್ತದೆ

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **ವೇಳಾಪಟ್ಟಿ** — one `JobRegistry` cron job, `log_export`, `0 * * * *` ಗೆ ಡೀಫಾಲ್ಟ್ ಆಗಿದೆ (ಗಂಟೆಗೆ, UTC). `src/lib/initCloudSync.ts` ನಲ್ಲಿ ನೋಂದಾಯಿಸಲಾಗಿದೆ; `OMNIROUTE_LOG_EXPORT_CRON` ನೊಂದಿಗೆ ಅತಿಕ್ರಮಿಸಬಹುದಾದ. ಪ್ರತಿ ಟಿಕ್ ಪ್ರತಿ ಬರಿದಾಗುತ್ತದೆ** ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ** ಗಮ್ಯಸ್ಥಾನ, ಅನುಕ್ರಮವಾಗಿ.
- **Cursor** — SQLite ಯ ಸೂಚ್ಯ `call_logs.rowid`, `log_export_destinations.cursor_row_id` ನಲ್ಲಿ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಮುಂದುವರಿಯುತ್ತದೆ. `timestamp` ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಕರ್ಸರ್ ಅಲ್ಲ: ಕರೆ ಮಾಡುವವರು ತಮ್ಮದೇ ಆದ ಮೌಲ್ಯವನ್ನು ಪೂರೈಸಬಹುದು, ಆದ್ದರಿಂದ ನಂತರ ಪ್ರಾರಂಭವಾದ ವೇಗದ ನಂತರ ನಿಧಾನ ವಿನಂತಿಯನ್ನು ಬರೆಯಬಹುದು ಮತ್ತು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಕರ್ಸರ್ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.
- **ಬ್ಯಾಚಿಂಗ್** ಪ್ರತಿ ವಿನಂತಿಗೆ — `batch_size` ಸಾಲುಗಳು (ಡೀಫಾಲ್ಟ್ 500), ಪ್ರತಿ ರನ್ಗೆ `max_rows_per_run` ಸಾಲುಗಳು (ಡೀಫಾಲ್ಟ್ 10000) ಆದ್ದರಿಂದ ದೊಡ್ಡ ಬ್ಯಾಕ್ಲಾಗ್ ಒಂದನ್ನು ನಿರ್ಬಂಧಿಸುವ ಬದಲು ಹಲವಾರು ಉಣ್ಣಿಗಳ ಮೇಲೆ ಹರಿಯುತ್ತದೆ.
- **ವಿತರಣೆ** — `send()` ಪರಿಹರಿಸಿದ ನಂತರವೇ ಕರ್ಸರ್ ಮುನ್ನಡೆಯುತ್ತದೆ. ವಿಫಲವಾದ ಬ್ಯಾಚ್ ಕರ್ಸರ್ ಅನ್ನು ಅಲ್ಲಿಯೇ ಬಿಡುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದೇ ಸಾಲುಗಳನ್ನು ಮುಂದಿನ ಓಟದಲ್ಲಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ. ಗ್ಯಾರಂಟಿಯು ಕನಿಷ್ಠ-ಒಮ್ಮೆ-ಕನಿಷ್ಠ-ಒಮ್ಮೆ ಗಮ್ಯಸ್ಥಾನ-ಭಾಗದ ಡಿ-ಡಪ್ಲಿಕೇಶನ್ ಆಗಿದೆ, ನಿಖರವಾಗಿ-ಒಮ್ಮೆ ನಿಜವಲ್ಲ: BigQuery ಪ್ರತಿ ಸಾಲನ್ನು ಕರೆ-ಲಾಗ್ ಐಡಿ ಮೂಲಕ ಕೀಲಿ ಮಾಡುತ್ತದೆ, ಇದು ತನ್ನದೇ ಆದ ಡೆಡಪ್ ವಿಂಡೋದಲ್ಲಿ ಉತ್ತಮ-ಪ್ರಯತ್ನದ ಆಧಾರದ ಮೇಲೆ ಗೌರವಿಸುತ್ತದೆ.
- **ಅತಿಕ್ರಮಣ ಸಿಬ್ಬಂದಿ** — ಕ್ರಾನ್ ಟಿಕ್ ಮತ್ತು `POST .../run` ಒಟ್ಟಿಗೆ ಬೆಂಕಿಯಿಡಬಹುದು. ಈಗಾಗಲೇ ಬರಿದಾಗುತ್ತಿರುವ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಎರಡು ಬಾರಿ ಬರಿದಾಗಿಸುವ ಬದಲು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ ( ರನ್ ಫಲಿತಾಂಶದಲ್ಲಿ`skipped: true` ), ಆದ್ದರಿಂದ ಏಕಕಾಲೀನ ರನ್ ಬ್ಯಾಚ್ ಅನ್ನು ಮರು-ಕಳುಹಿಸಲು ಅಥವಾ ಕರ್ಸರ್ ಅನ್ನು ಹಿಂದಕ್ಕೆ ಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ.
- **ಶುದ್ಧೀಕರಣ ಚೇತರಿಕೆ** — `cursor_row_id` `MAX(rowid)` ಮೇಲೆ ಕೊನೆಗೊಂಡರೆ (ಇಡೀ ಟೇಬಲ್ ಅನ್ನು ಶುದ್ಧೀಕರಿಸಲಾಗಿದೆ ಮತ್ತು rowids ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಲಾಗಿದೆ), ರನ್ನರ್ ಶಾಶ್ವತವಾಗಿ ಕುರುಡಾಗುವ ಬದಲು 0 ಗೆ ಹಿಂತಿರುಗುತ್ತಾನೆ.

### ಪ್ರತ್ಯೇಕವಾದ ಓಟಗಾರ ಮತ್ತು ಮಿತಿಗಳು

ನೋಡ್ನಲ್ಲಿ ಚಾಲನೆಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು ಗಮ್ಯಸ್ಥಾನವು ಪ್ರತ್ಯೇಕವಾದ, ಅಲ್ಪಾವಧಿಯ OS ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ (`child_process` ಜೊತೆಗೆ IPC, `worker_threads` ಅಲ್ಲ). ದೇಹವನ್ನು ಓದುತ್ತದೆ, ಪೇಲೋಡ್ JSON parsing/serialization, ಗಮ್ಯಸ್ಥಾನ `prepare()` ಮತ್ತು ಗಮ್ಯಸ್ಥಾನ ನೆಟ್ವರ್ಕ್ I/O ಎಲ್ಲವೂ ಅಲ್ಲಿ ರನ್ ಆಗುತ್ತವೆ, ಸರ್ವರ್ನ ಈವೆಂಟ್ ಲೂಪ್ನಲ್ಲಿ ಅಲ್ಲ. ಸಂರಚನೆ ಮತ್ತು ಸಣ್ಣ ಪ್ರಗತಿ ಸಂದೇಶಗಳು ಮಾತ್ರ IPC ದಾಟುತ್ತವೆ; ರಫ್ತು ಮಾಡಿದ ದಾಖಲೆಗಳು ಸರ್ವರ್ಗೆ ಹಿಂತಿರುಗುವುದಿಲ್ಲ. ಕ್ರಾನ್ ಜಾಬ್ ಮತ್ತು ರನ್ ನೌ ಮಾರ್ಗವು ಅದೇ ಸಾರ್ವಜನಿಕ ಫಲಿತಾಂಶವನ್ನು ಇರಿಸುತ್ತದೆ ಮತ್ತು ಕಾವಲುಗಾರನನ್ನು ಅತಿಕ್ರಮಿಸುತ್ತದೆ.

ಮಗುವು `node:sqlite`, `busy_timeout=5000` ಮತ್ತು `query_only=ON` ನೊಂದಿಗೆ ಸರ್ವರ್ನ ಪರಿಹರಿಸಿದ `DATA_DIR/storage.sqlite` ಓದಲು-ಮಾತ್ರವನ್ನು ತೆರೆಯುತ್ತದೆ. ಇದು ಯಾವುದೇ DB ಸಿಂಗಲ್ಟನ್ ಅನ್ನು ಆಮದು ಮಾಡಿಕೊಳ್ಳುವುದಿಲ್ಲ ಮತ್ತು ಯಾವುದೇ ವಲಸೆಗಳು, ಬ್ಯಾಕ್ಅಪ್ಗಳು ಅಥವಾ SQLite ನವೀಕರಣಗಳನ್ನು ನಿರ್ವಹಿಸುವುದಿಲ್ಲ. Missing/corrupt ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಬುಕ್ಕೀಪಿಂಗ್ (ಭ್ರಷ್ಟ-ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ UPDATE ಸೇರಿದಂತೆ) ಡ್ಯಾಶ್ಬೋರ್ಡ್ ವಿವರ ಮಾರ್ಗದಲ್ಲಿ ಮಾತ್ರ ಉಳಿದಿದೆ. ಎರಡೂ ಮಾರ್ಗಗಳು ಶುದ್ಧ ವಿವರ ಪರಿಹಾರಕವನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ; ರಫ್ತು ಅಸಮಕಾಲಿಕ ಫೈಲ್ಸಿಸ್ಟಮ್ ರೀಡ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು ಅದೇ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ → ಲೆಗಸಿ ಇನ್ಲೈನ್ → ಲೆಗಸಿ ಡಿಸ್ಕ್ → ಯಾವುದೇ ರೆಸಲ್ಯೂಶನ್ ಆರ್ಡರ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಮಗು ತನ್ನ ರೀಡರ್ ಅನ್ನು ತೆರೆದಾಗ ಒಂದು ರನ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಳು ಗರಿಷ್ಠ ಅಳವಡಿಕೆ ರೋವಿಡ್; ನಂತರದ ಒಳಸೇರಿಸುವಿಕೆಗಳು ಮುಂದಿನ ಓಟಕ್ಕಾಗಿ ಕಾಯಿರಿ. ಇದು ಅಳವಡಿಕೆಯ ಗಡಿಯಾಗಿದೆ, ದೀರ್ಘಾವಧಿಯ SQLite ವಹಿವಾಟು ಅಲ್ಲ: ನೆಟ್ವರ್ಕ್ ಕಾಯುವ ಸಮಯದಲ್ಲಿ WAL ರೈಟರ್ಗಳು ಮತ್ತು ಚೆಕ್ಪಾಯಿಂಟ್ಗಳು ಮುಕ್ತವಾಗಿರುತ್ತವೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಾಲುಗಳ Updates/deletions ಅನ್ನು ಈ ಗಡಿಯಿಂದ ಫ್ರೀಜ್ ಮಾಡಲಾಗಿಲ್ಲ.

ಪ್ರತಿ ಸ್ವೀಕರಿಸಿದ ಬ್ಯಾಚ್ ನಂತರ, ಮಗು ಸ್ವೀಕೃತಿಗಾಗಿ ಕಾಯುತ್ತದೆ. ಸರ್ವರ್ ಮೊದಲು ಕರ್ಸರ್ ಅನ್ನು `advanceLogExportCursor` ನೊಂದಿಗೆ ಮುಂದುವರಿಸುತ್ತದೆ, ನಂತರ `ack` ಕಳುಹಿಸುತ್ತದೆ; ಅದರ ಮೊದಲು ಮುಂದಿನ ಬ್ಯಾಚ್ ಪ್ರಾರಂಭವಾಗುವುದಿಲ್ಲ. ಒಂದು ಕಳುಹಿಸುವಿಕೆ ವೈಫಲ್ಯ, ಕ್ರ್ಯಾಶ್ ಅಥವಾ ಸಮಯ ಮೀರುವಿಕೆಯು ಆ ಬ್ಯಾಚ್ ಅನ್ನು ಮುಂದುವರಿಸದೆ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಹಿಂದೆ ಒಪ್ಪಿಕೊಂಡ ಬ್ಯಾಚ್ಗಳು ಬದ್ಧವಾಗಿರುತ್ತವೆ; ಹೆಚ್ಚೆಂದರೆ ಒಂದು ಅಂಗೀಕರಿಸದ ಬ್ಯಾಚ್ ಅನ್ನು ಮರು-ಕಳುಹಿಸಬಹುದು. `done` ಮತ್ತು ಕ್ಲೀನ್ ಚೈಲ್ಡ್ ನಿರ್ಗಮನದ ನಂತರ ಮಾತ್ರ ಯಶಸ್ಸನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ. ವೈಫಲ್ಯಗಳು ಮಗುವನ್ನು SIGTERM ನೊಂದಿಗೆ ಕೊನೆಗೊಳಿಸುತ್ತವೆ, 500 ms ನಂತರ SIGKILL ಗೆ ಉಲ್ಬಣಗೊಳ್ಳುತ್ತವೆ ಮತ್ತು ಓಟಗಾರನು ಪ್ರಕ್ರಿಯೆಯ ಮುಚ್ಚುವಿಕೆಗಾಗಿ ಕಾಯುತ್ತಾನೆ.

| ಪರಿಸರ ವೇರಿಯಬಲ್                                | ಡೀಫಾಲ್ಟ್ | ಉದ್ದೇಶ                             |
| --------------------------------------------- | -------- | ---------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000   | ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ ಗೋಡೆ ಗಡಿಯಾರದ ಮಿತಿ |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024     | MB ನಲ್ಲಿ ಚೈಲ್ಡ್ V8 ಹಳೆಯ ಜಾಗದ ಮಿತಿ  |

Invalid/non-positive/non-integer ಮೌಲ್ಯಗಳು ಡೀಫಾಲ್ಟ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ. ರಾಶಿ ಸೆಟ್ಟಿಂಗ್ ಒಟ್ಟು RSS ಮಿತಿಯಲ್ಲ; ದೊಡ್ಡ ಬ್ಯಾಚ್ಗಳು ಇನ್ನೂ ಮಗುವಿನ ಸ್ಮರಣೆಯನ್ನು ನಿಷ್ಕಾಸಗೊಳಿಸಬಹುದು ಮತ್ತು ಸುರಕ್ಷಿತವಾಗಿ ಓಟವನ್ನು ವಿಫಲಗೊಳಿಸಬಹುದು. 1024 MB ಡೀಫಾಲ್ಟ್ 512 KiB ಕಲಾಕೃತಿಗಳ ಡೀಫಾಲ್ಟ್ 500-ಸಾಲು ಬ್ಯಾಚ್ಗೆ ಹೆಡ್ರೂಮ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ, ಇದರಲ್ಲಿ BigQuery ನ ಬೈಟ್-ಚಂಕ್ಡ್ JSON ಧಾರಾವಾಹಿ ಸೇರಿದಂತೆ ದೇಹಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ. ಇದು 10000-ಸಾಲಿನ ದೇಹಗಳ ಬ್ಯಾಚ್ ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿಸುವುದಿಲ್ಲ. V8 ರಾಶಿಯ ನಿಶ್ಯಕ್ತಿಯು ಕಾರ್ಯಸಾಧ್ಯವಾದ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ: ಕಡಿಮೆ ಬ್ಯಾಚ್ ಗಾತ್ರ ಅಥವಾ ಹೆಚ್ಚಿಸಿ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; ಕರ್ಸರ್ ಕೊನೆಯ ಅಂಗೀಕೃತ ಬ್ಯಾಚ್ನಲ್ಲಿ ಇರುತ್ತದೆ. ಐತಿಹಾಸಿಕ inline/disk ದೇಹಗಳನ್ನು ಆಧುನಿಕ ಕಲಾಕೃತಿ ಕ್ಯಾಪ್ನಿಂದ ಮುಚ್ಚಲಾಗಿಲ್ಲ. ನಿರ್ವಾಹಕರು ಪ್ರತ್ಯೇಕವಾಗಿ RSS ಬಜೆಟ್ ಮಾಡಬೇಕು, ವಿಶೇಷವಾಗಿ ಮೆಮೊರಿ-ಸೀಮಿತ ಕಂಟೈನರ್ಗಳ ಒಳಗೆ.

ಮಗುವು ಪರಿಹರಿಸಿದ `DATA_DIR`, `NODE_ENV`, ಸ್ಪಷ್ಟ `TZ` (ಪರಂಪರೆ ಫೈಲ್ ಹೆಸರು ಸ್ಥಳೀಯ-ಸಮಯದ ರೆಸಲ್ಯೂಶನ್), `ELECTRON_RUN_AS_NODE` ಇದ್ದಾಗ ಮತ್ತು ಕೆಳಗಿನ ಹೊರಹೋಗುವ ಒಳಹರಿವುಗಳನ್ನು ಮಾತ್ರ ಪಡೆದುಕೊಳ್ಳುತ್ತದೆ: `HTTP_PROXY` `SSL_CERT_DIR` `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (ಮತ್ತು ಅವುಗಳ ಸಣ್ಣ ಅಕ್ಷರಗಳು), `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS` `SSL_CERT_FILE` ಜಾಗತಿಕ Undici ರವಾನೆದಾರರು ಸರ್ವರ್ನ ಶುದ್ಧ ಪರಿಸರ-ಪ್ರಾಕ್ಸಿ ರೆಸಲ್ಯೂಶನ್ ಮತ್ತು `NO_PROXY` ಸೇರಿದಂತೆ ಸ್ಥಳೀಯ-ಹೋಸ್ಟ್ ಬೈಪಾಸ್ ನಿಯಮಗಳನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತಾರೆ; ಇದು `proxyFetch.ts` ಅಥವಾ ಅದರ DB/feature ಧ್ವಜಗಳನ್ನು ಆಮದು ಮಾಡಿಕೊಳ್ಳುವುದಿಲ್ಲ. ಫಾರ್ವರ್ಡ್ ಮಾಡಿದ ಔಟ್ಪುಟ್ ಮತ್ತು ರೆಕಾರ್ಡ್ ಮಾಡಿದ ದೋಷಗಳಿಂದ ಪ್ರಾಕ್ಸಿ ರುಜುವಾತುಗಳನ್ನು ಮರುಸಂಗ್ರಹಿಸಲಾಗಿದೆ. ಗಮ್ಯಸ್ಥಾನದ ರುಜುವಾತುಗಳು ಒಂದು ಪ್ರಾರಂಭದ IPC ಸಂದೇಶದಲ್ಲಿ ಮಾತ್ರ ಪ್ರಯಾಣಿಸುತ್ತವೆ, ಎಂದಿಗೂ argv ಅಥವಾ ಪರಿಸರವಲ್ಲ; output/error ಫಾರ್ವರ್ಡ್ ಮಾಡುವಿಕೆಯನ್ನು ಪೂರ್ವಪ್ರತ್ಯಯ ಮತ್ತು ಶುಚಿಗೊಳಿಸಲಾಗಿದೆ. ಪ್ರತಿ ಕ್ರಾನ್ ರನ್ಗೆ ಎಚ್ಚರಿಕೆ ನೀಡುವ ನೋಡ್ನ SQLite ಪುನರಾವರ್ತಿಸುವುದನ್ನು ತಪ್ಪಿಸಲು ಚೈಲ್ಡ್ ಎಕ್ಸಿಕ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳಲ್ಲಿ `ExperimentalWarning` ಮಾತ್ರ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ; ಇತರ ಎಚ್ಚರಿಕೆ ಪ್ರಕಾರಗಳು ಗೋಚರಿಸುತ್ತವೆ.

ಗಮ್ಯಸ್ಥಾನ ಮಾಡ್ಯೂಲ್ಗಳು Next.js/server-only ಅವಲಂಬನೆಗಳಿಲ್ಲದೆ ಆಮದು ಮಾಡಿಕೊಳ್ಳಬೇಕು. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ BigQuery ಅನುಷ್ಠಾನವು ಈಗಾಗಲೇ ಆ ಒಪ್ಪಂದವನ್ನು ಪೂರೈಸುತ್ತದೆ. ಪ್ರವೇಶ-ಟೋಕನ್ ಕ್ಯಾಶ್ಗಳು ಚೈಲ್ಡ್ ರನ್ಗೆ ಮಾತ್ರ ಇರುತ್ತದೆ, ರನ್ಗಳಾದ್ಯಂತ ಅಲ್ಲ. ನೋಡ್ ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ಆಗಿದೆ (`package.json` ಎಂಜಿನ್ಗಳು). ಉತ್ತಮ ಪ್ರಯತ್ನ, ಬೆಂಬಲವಿಲ್ಲದ Bun ಹೊಂದಾಣಿಕೆ ಮಾರ್ಗವು ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ (`bun:sqlite` ನಲ್ಲಿ `src/lib/db/core.ts` / ಅಡಾಪ್ಟರ್ಗಳು, ಮತ್ತು `Dockerfile.bun`), ಆದ್ದರಿಂದ ರಫ್ತುಗಳು ಅದರ ಅಡಿಯಲ್ಲಿ ಮುರಿಯಬಾರದು. Bun ಅಡಿಯಲ್ಲಿ, ರಫ್ತುಗಳು ಹಿಂದಿನ ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿನ ಮಾರ್ಗವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ ಮತ್ತು ಒಂದು-ಬಾರಿ ಎಚ್ಚರಿಕೆಯನ್ನು ಹೊರಸೂಸುತ್ತವೆ: ಚೈಲ್ಡ್ heap/timeout ಪ್ರತ್ಯೇಕತೆಯು ಲಭ್ಯವಿಲ್ಲ. ಈವೆಂಟ್-ಲೂಪ್ ಮತ್ತು OOM ಪ್ರತ್ಯೇಕತೆಗಾಗಿ ನೋಡ್ ಅನ್ನು ಬಳಸಿ.

`includeBodies` ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಗಂಟೆಯ ಪೇಲೋಡ್ ಬ್ಯಾಕ್ಲಾಗ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುವುದಕ್ಕಿಂತ ಹೆಚ್ಚಾಗಿ `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ ನಿಮಿಷ-ಮಟ್ಟದ ಕ್ಯಾಡೆನ್ಸ್ ಅನ್ನು ಆದ್ಯತೆ ನೀಡಿ. ಬ್ಯಾಚ್ ಮತ್ತು ಸಾಲು ಮಿತಿಗಳು ಇನ್ನೂ ಪ್ರತಿ ರನ್ ಅನ್ನು ಬಂಧಿಸುತ್ತವೆ. ಪ್ರತಿ ಓಟಕ್ಕೆ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭವನ್ನು ಪಾವತಿಸಲಾಗುತ್ತದೆ; ಇದು ಸರ್ವರ್ ಈವೆಂಟ್-ಲೂಪ್ ಪ್ರತ್ಯೇಕತೆಗಾಗಿ ಸಣ್ಣ ಆರಂಭಿಕ ವೆಚ್ಚವನ್ನು ವ್ಯಾಪಾರ ಮಾಡುತ್ತದೆ, ಒಟ್ಟು CPU ಬಳಕೆಯನ್ನು ಕಡಿಮೆ ಮಾಡುವುದಿಲ್ಲ.

### ಪೇಲೋಡ್ಗಳು (ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳು)

ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ರಫ್ತು ಲಾಗ್ಗಳ ಸಾರಾಂಶ ಕ್ಷೇತ್ರಗಳನ್ನು ಮಾತ್ರ ಒಯ್ಯುತ್ತದೆ** ಪಟ್ಟಿ** ತೋರಿಸುತ್ತದೆ. ಆನ್ ಆಗುತ್ತಿದೆ** ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ರಫ್ತು ಮಾಡಿ** (`includeBodies`) ಹೆಚ್ಚುವರಿಯಾಗಿ ಲಾಗ್ಗಳನ್ನು ರವಾನಿಸುತ್ತದೆ** ವಿವರ** ಪ್ರತಿ ಕರೆಗೆ ಫಲಕ ತೋರಿಸುತ್ತದೆ:

| ಕ್ಷೇತ್ರ                          | ಅದು ಏನು ಹೊಂದಿದೆ                                             |
| -------------------------------- | ----------------------------------------------------------- |
| `request_body` / `response_body` | ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಅವುಗಳನ್ನು ರೆಂಡರ್ ಮಾಡಿದಂತೆ ಕರೆ ಪೇಲೋಡ್ ಆಗುತ್ತದೆ  |
| `pipeline_route_decision`        | ರೂಟರ್ ಯಾವ ಗುರಿ ಮತ್ತು ಮಾದರಿಯನ್ನು ಆರಿಸಿದೆ                     |
| `pipeline_client_request`        | ಕ್ಲೈಂಟ್ ಕಳುಹಿಸಿದಂತೆಯೇ ಕಚ್ಚಾ ವಿನಂತಿ                          |
| `pipeline_openai_request`        | ಆಂತರಿಕ OpenAI ಆಕಾರಕ್ಕೆ ಅನುವಾದದ ನಂತರ                         |
| `pipeline_provider_request`      | ಪೂರೈಕೆದಾರರ ಉಪಭಾಷೆಯಲ್ಲಿ ವಾಸ್ತವವಾಗಿ ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ಕಳುಹಿಸಿದಂತೆ |
| `pipeline_provider_response`     | ಕಚ್ಚಾ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆ                               |
| `pipeline_client_response`       | ಕರೆ ಮಾಡಿದವನಿಗೆ ಹಿಂತಿರುಗಿ ಏನು ನೀಡಲಾಯಿತು                      |
| `pipeline_error`                 | ವಿಫಲ ಕರೆಗಾಗಿ ಪೈಪ್ಲೈನ್ ಮಟ್ಟದ ದೋಷ ವಿವರ                        |
| `bodies_truncated`               | ಮೇಲಿನ ಯಾವುದೇ ಕ್ಷೇತ್ರವು `maxBodyBytes` ಹೊಡೆದಾಗ ನಿಜ           |

ಇದು ಪ್ರಾಂಪ್ಟ್ ವಿಷಯವಾಗಿದೆ, ಆದ್ದರಿಂದ ಇದು** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಆಫ್** ಮತ್ತು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತಿ-ಗಮ್ಯಸ್ಥಾನದ ಆಯ್ಕೆ. ರಫ್ತು ಮತ್ತು `getCallLogById` ಹಂಚಿಕೆಯ ವಿವರ ರೆಸಲ್ಯೂಶನ್ ಯಾವ ಹಡಗುಗಳನ್ನು ತೋರಿಸುತ್ತದೆ: ಪೇಲೋಡ್ಗಳು ಈಗಾಗಲೇ PII-ಸ್ಯಾನಿಟೈಸ್ ಆಗಿವೆ ಮತ್ತು ಅವುಗಳನ್ನು ಬರೆದಾಗ ರಹಸ್ಯ-ಪರಿಷ್ಕರಣೆ ಮಾಡಲಾಗಿದೆ, ಮತ್ತು `noLog` API ಕೀಲಿಯೊಂದಿಗೆ ಮಾಡಿದ ಕರೆಯು ಯಾವುದೇ ಪೇಲೋಡ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ರಫ್ತು ಮಾಡಲು ಏನೂ ಇಲ್ಲ.

ಫೈಲ್ಸಿಸ್ಟಮ್ ಕಲಾಕೃತಿಯಿಂದ ಪ್ರತಿ ಸಾಲಿಗೆ ಪೇಲೋಡ್ಗಳನ್ನು ಓದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಜಲಸಂಚಯನವು ಅದನ್ನು ಕೇಳಿದ ಸ್ಥಳಗಳಿಗೆ ಮಾತ್ರ ಚಲಿಸುತ್ತದೆ. ಕಾಣೆಯಾದ ಅಥವಾ ಭ್ರಷ್ಟವಾದ ಕಲಾಕೃತಿಯು ಅದರ ಸಾರಾಂಶವನ್ನು ಶೂನ್ಯ ಪೇಲೋಡ್ಗಳೊಂದಿಗೆ ರಫ್ತು ಮಾಡುತ್ತದೆ ಬದಲಿಗೆ ಬ್ಯಾಚ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಕರ್ಸರ್ ಅನ್ನು ಸ್ಟ್ರ್ಯಾಂಡ್ ಮಾಡುತ್ತದೆ.

`maxBodyBytes` (ಡೀಫಾಲ್ಟ್ 262144) ಪ್ರತಿ ಕ್ಷೇತ್ರವನ್ನು ಕ್ಯಾಪ್ ಮಾಡುತ್ತದೆ. ಉದ್ದವಾದ ಪೇಲೋಡ್ಗಳು** ಕೈಬಿಡುವ ಬದಲು ಮೊಟಕುಗೊಳಿಸಲಾಗಿದೆ** — ಕ್ಲಿಪ್ ಮಾಡಿದ ಪ್ರಾಂಪ್ಟ್ ಇನ್ನೂ "ಏನು ಕೇಳಲಾಗಿದೆ" ಎಂದು ಉತ್ತರಿಸುತ್ತದೆ — ಮತ್ತು ಸಾಲನ್ನು `bodies_truncated` ನೊಂದಿಗೆ ಫ್ಲ್ಯಾಗ್ ಮಾಡಲಾಗಿದೆ. ಸ್ಟ್ರೀಮ್ ಮಾಡಿದ ಚಂಕ್-ಬೈ-ಚಂಕ್ ಡೆಲ್ಟಾಗಳನ್ನು ರಫ್ತು ಮಾಡಲಾಗುವುದಿಲ್ಲ; ಜೋಡಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆಯು ಈಗಾಗಲೇ `pipeline_provider_response` ಮತ್ತು `pipeline_client_response` ನಲ್ಲಿದೆ.

## 3. REST API

ಎಲ್ಲಾ ಮಾರ್ಗಗಳಿಗೂ ನಿರ್ವಹಣಾ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ (`requireManagementAuth`). ರಹಸ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ:
ಸಂಗ್ರಹಿಸಿದ ರಹಸ್ಯವನ್ನು ಅಕ್ಷರಶಃ `__stored__` ಎಂಬ ಮೌಲ್ಯವಾಗಿ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ನವೀಕರಣದ ಸಮಯದಲ್ಲಿ ಆ ಮೌಲ್ಯವನ್ನು ಮರಳಿ ಕಳುಹಿಸಿದರೆ
ಸಂಗ್ರಹಿಸಿದ ದೃಢೀಕರಣ ಮಾಹಿತಿಯನ್ನು ಹಾಗೆಯೇ ಉಳಿಸಲಾಗುತ್ತದೆ.

ರಹಸ್ಯವನ್ನು ಘೋಷಿಸುವ ಪ್ರಕಾರದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ರಚಿಸಲು ಅಥವಾ ನವೀಕರಿಸಲು **`STORAGE_ENCRYPTION_KEY`
ಅಗತ್ಯವಿದೆ**. ಅದು ಇಲ್ಲದಿದ್ದರೆ `encrypt()` ಯಾವುದೇ ಬದಲಾವಣೆ ಮಾಡದೆ ಮೌನವಾಗಿ ದತ್ತಾಂಶವನ್ನು ಮುಂದಕ್ಕೆ ಕಳುಹಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ದೃಢೀಕರಣ ಮಾಹಿತಿಯನ್ನು
SQLite ನಲ್ಲಿ ಸರಳ ಪಠ್ಯವಾಗಿ ಸಂಗ್ರಹಿಸುವ ಬದಲು ಬರವಣಿಗೆಯನ್ನು 400 ಪ್ರತಿಕ್ರಿಯೆಯೊಂದಿಗೆ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ (Telegram webhook

## 4. BigQuery ಗಮ್ಯಸ್ಥಾನ

ಸಂರಚನಾ ಕೀಗಳು (`type: "bigquery"`):

| Key                  | Notes                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------- |
| `projectId`          | ಡೇಟಾಸೆಟ್ ಹೊಂದಿರುವ GCP ಪ್ರಾಜೆಕ್ಟ್                                                                        |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                         |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                         |
| `location`           | ಡೇಟಾಸೆಟ್ ರಚಿಸಬೇಕಾದಾಗ ಮಾತ್ರ ಬಳಸಲಾಗುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `EU`)                                                 |
| `serviceAccountJson` | ಸರ್ವಿಸ್-ಅಕೌಂಟ್ ಕೀ. ರಹಸ್ಯ: ವಿಶ್ರಾಂತಿ ಸ್ಥಿತಿಯಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ, ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ  |
| `autoCreate`         | ಕಾಣೆಯಾದ ಡೇಟಾಸೆಟ್/ಟೇಬಲ್ ರಚಿಸಿ; nullable ಬಳಕೆ-ಸಾಕ್ಷ್ಯ ಕಾಲಮ್ಗಳನ್ನು ಷರತ್ತುಬದ್ಧವಾಗಿ ಸೇರಿಸಿ (ಡೀಫಾಲ್ಟ್ `true`) |

ಸರ್ವಿಸ್ ಅಕೌಂಟ್ಗೆ ಗುರಿ ಟೇಬಲ್ನಲ್ಲಿ `bigquery.tables.updateData` ಅನುಮತಿ ಬೇಕಾಗುತ್ತದೆ, ಹಾಗೆಯೇ
`autoCreate` ಸಕ್ರಿಯವಾಗಿರುವಾಗ `bigquery.datasets.create` / `bigquery.tables.create` ಅನುಮತಿಗಳೂ ಬೇಕಾಗುತ್ತವೆ.
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್ಗೆ ಎರಡು nullable ಬಳಕೆ-ಸಾಕ್ಷ್ಯ ಫೀಲ್ಡ್ಗಳನ್ನು ಸೇರಿಸಲು
`bigquery.tables.update` ಕೂಡ ಅಗತ್ಯವಿದೆ. ಅಗತ್ಯವಿರುವ ಯಾವುದೇ ಅನುಮತಿ ಇಲ್ಲದಿದ್ದರೆ, ಅದರ ಕರ್ಸರ್ ಅನ್ನು ಮುಂದಕ್ಕೆ
ಸರಿಸದೆ ರಫ್ತು ವಿಫಲವಾಗುತ್ತದೆ.

ಸಂರಚಿಸಲಾದ ಬ್ಯಾಚ್ ಒಂದು **ಕರ್ಸರ್** ಘಟಕವಾಗಿದೆ, HTTP ಘಟಕವಲ್ಲ: `send()` ಅದನ್ನು ಗರಿಷ್ಠ 500 ಸಾಲುಗಳ
insertAll ಕರೆಗಳಾಗಿ ವಿಭಜಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ದೊಡ್ಡ `batch_size` BigQueryಯ 10 MB ವಿನಂತಿ ಮಿತಿಯನ್ನು ಮೀರುವುದಿಲ್ಲ.
ತಾತ್ಕಾಲಿಕ ಸ್ಥಿತಿಗಳಿಗೆ (408/429/500/502/503/504) ಅದೇ insertIds ಅನ್ನು ಮರುಬಳಸಿ, ಎಕ್ಸ್ಪೋನೆನ್ಶಿಯಲ್
ಬ್ಯಾಕ್ಆಫ್ನೊಂದಿಗೆ ಗರಿಷ್ಠ ಮೂರು ಬಾರಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ; ಪ್ರಮಾಣೀಕರಣ ಮತ್ತು ಸ್ಕೀಮಾ ವೈಫಲ್ಯಗಳು ಮೊದಲ ಪ್ರಯತ್ನದಲ್ಲೇ
ಎಸೆದುಬಿಡುತ್ತವೆ, ಹೀಗಾಗಿ ರನ್ನ ಪ್ರಯತ್ನಗಳನ್ನು ಅನಗತ್ಯವಾಗಿ ಬಳಸುವುದಿಲ್ಲ.

ಕೆಲವೇ ಕ್ಷಣಗಳ ಹಿಂದೆ ರಚಿಸಲಾದ ಟೇಬಲ್ ಸ್ಟ್ರೀಮಿಂಗ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಇನ್ನೂ ಗೋಚರಿಸದೇ ಇರಬಹುದು; ಅದು
ಕೆಲವು ಸೆಕೆಂಡುಗಳ ಕಾಲ 404 ನೀಡುತ್ತದೆ. ಆ 404 ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ, ಆದರೆ **ಈ ರನ್ ಟೇಬಲ್ ಅನ್ನು
ರಚಿಸಿದ್ದಾಗ ಮಾತ್ರ** — ನಿಜವಾಗಿಯೂ ಕಾಣೆಯಾದ ಟೇಬಲ್ ತಕ್ಷಣವೇ ವಿಫಲವಾಗುತ್ತದೆ. ಇತ್ತೀಚೆಗೆ ಅಳಿಸಲಾದ ಟೇಬಲ್ನ
ಹೆಸರಿನಡಿಯಲ್ಲಿ ಅದನ್ನು ಮರುರಚಿಸಿದಾಗ BigQuery ಹಲವು ನಿಮಿಷಗಳ ಕಾಲ ಸ್ಟ್ರೀಮಿಂಗ್ ಇನ್ಸರ್ಟ್ಗಳನ್ನು ನಿರಾಕರಿಸಬಹುದು.
ಇದು ಅಳಿಸಿ-ಮರುರಚಿಸುವಿಕೆಯ ಸ್ವಭಾವವೇ ಆಗಿರುವುದರಿಂದ, ಟೇಬಲ್ ಅನ್ನು ತೆಗೆದುಹಾಕಿ ಮತ್ತೆ ಸೇರಿಸುವ ಬದಲು ಹೊಸ ಟೇಬಲ್
ಹೆಸರನ್ನು ಬಳಸುವುದು ಉತ್ತಮ.

**ಭಾಗಶಃ ವೈಫಲ್ಯವು ಖಾಲಿಯಲ್ಲದ `insertErrors[]` ಜೊತೆಗೆ HTTP 200 ಆಗಿ ಬರುತ್ತದೆ.** ಇದನ್ನು
ವೈಫಲ್ಯವೆಂದು ಪರಿಗಣಿಸಿ ಎಸೆಯಲಾಗುತ್ತದೆ; ಇದರಿಂದ BigQuery ಸ್ವೀಕರಿಸದ ಸಾಲುಗಳನ್ನು ದಾಟಿ ಕರ್ಸರ್ ಮುಂದೆ ಸಾಗುವುದನ್ನು
ತಡೆಯಲಾಗುತ್ತದೆ; `tests/unit/log-export-bigquery.test.ts` ಈ ವರ್ತನೆಯನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ.

ಸಾರಿಗೆ ಸರಳ REST ಆಗಿದೆ — ಸ್ವಯಂ-ಸಹಿ ಮಾಡಲಾದ RS256 ಅಸರ್ಷನ್ ಅನ್ನು
`https://oauth2.googleapis.com/token` ನಲ್ಲಿ ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗಾಗಿ ವಿನಿಮಯ ಮಾಡಲಾಗುತ್ತದೆ, ನಂತರ ಸಾಲುಗಳನ್ನು
`tabledata.insertAll` ಗೆ ಕಳುಹಿಸಲಾಗುತ್ತದೆ. ಯಾವುದೇ Google SDK ಅನ್ನು ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ. ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗಳನ್ನು
ಪ್ರಕ್ರಿಯೆಯೊಳಗೆ ಪ್ರತಿ (ಸರ್ವಿಸ್ ಅಕೌಂಟ್, ಸ್ಕೋಪ್) ಆಧಾರದಲ್ಲಿ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ.

ರಚಿಸಲಾದ ಟೇಬಲ್ Logs-ಟ್ಯಾಬ್ನ ಪ್ರತಿಯೊಂದು ಫೀಲ್ಡ್ಗೆ ಒಂದು ಕಾಲಮ್ ಜೊತೆಗೆ `exported_at` ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ,
ಮತ್ತು ಕಾಲ್ ಲಾಗ್ಗಳನ್ನು ವಾಸ್ತವವಾಗಿ ಹೇಗೆ ಪ್ರಶ್ನಿಸಲಾಗುತ್ತದೆ ಎಂಬುದಕ್ಕೆ ಅನುಗುಣವಾಗಿ ವಿನ್ಯಾಸಗೊಳಿಸಲಾಗುತ್ತದೆ:

- **`timestamp` ಆಧಾರಿತ ದಿನ-ವಿಭಜನೆ**, ಆದ್ದರಿಂದ ದಿನಾಂಕದಿಂದ ಮಾತ್ರ ಸೀಮಿತಗೊಳಿಸಿದ ಪ್ರಶ್ನೆಯು ಆ ದಿನಗಳನ್ನಷ್ಟೇ ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತದೆ.
- **`api_key_name`, `provider`, `model`, `status` ಮೂಲಕ ಕ್ಲಸ್ಟರ್ ಮಾಡಲಾಗಿದೆ** (ಈ ಕ್ರಮದಲ್ಲೇ), ಆದ್ದರಿಂದ ಅದನ್ನು
  ಯಾರು ನಡೆಸಿದರು, ಅದು ಎಲ್ಲಿಗೆ ಹೋಯಿತು ಅಥವಾ ಅದು ವಿಫಲವಾಯಿತೇ ಎಂಬುದರ ಆಧಾರದ ಮೇಲಿನ ಫಿಲ್ಟರಿಂಗ್ ಪ್ರತಿ
  ಪಾರ್ಟಿಷನ್ನೊಳಗಿನ ಬ್ಲಾಕ್ಗಳನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ. BigQuery ಗರಿಷ್ಠ ನಾಲ್ಕು ಕ್ಲಸ್ಟರಿಂಗ್ ಕಾಲಮ್ಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ
  ಮತ್ತು ಕ್ರಮವು ಮುಖ್ಯವಾಗಿದೆ: `api_key_name` ಮೇಲಿನ ಫಿಲ್ಟರ್ ಮಾತ್ರ ಬ್ಲಾಕ್ಗಳನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ,
  `status` ಮೇಲಿನ ಫಿಲ್ಟರ್ ಮಾತ್ರ ಕಡಿಮೆ ಮಾಡುವುದಿಲ್ಲ.
- `partitionExpirationDays` ಮೂಲಕ **ಐಚ್ಛಿಕ ಪಾರ್ಟಿಷನ್ ಉಳಿಕೆ** (0 ಎಲ್ಲವನ್ನೂ ಉಳಿಸುತ್ತದೆ), ಟೇಬಲ್
  ರಚಿಸಿದಾಗ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.

ಎರಡೂ ಸೆಟ್ಟಿಂಗ್ಗಳು ರಚನೆಯ ಸಮಯದಲ್ಲೇ ಅನ್ವಯಿಸುತ್ತವೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್ ಈಗಾಗಲೇ ಹೊಂದಿರುವ ವಿನ್ಯಾಸವನ್ನೇ
ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ ಇವುಗಳನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳಲು ಬಯಸಿದರೆ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಹೊಸ ಟೇಬಲ್ ಐಡಿಗೆ ಸೂಚಿಸಿ.

`tests/unit/log-export-bigquery.test.ts` ಮ್ಯಾಪರ್ ಮತ್ತು ಟೇಬಲ್ ಸ್ಕೀಮಾ ಪರಸ್ಪರ ಸಮಕಾಲಿಕವಾಗಿರುವುದನ್ನು
ಖಚಿತಪಡಿಸುತ್ತದೆ, ಹೀಗಾಗಿ ಹೊಸ ಕಾಲ್-ಲಾಗ್ ಕಾಲಮ್ ಹೊರಗೆ ಹೋಗುವ ಮಾರ್ಗದಲ್ಲಿ ಮೌನವಾಗಿ ಕೈಬಿಡಲಾಗುವುದಿಲ್ಲ.

ಬ್ಯಾಚ್ಗಳನ್ನು **ಸಾಲುಗಳ ಸಂಖ್ಯೆಯ ಜೊತೆಗೆ ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಬೈಟ್ಗಳ ಆಧಾರದಲ್ಲಿಯೂ** ವಿಭಜಿಸಲಾಗುತ್ತದೆ. ಪೇಲೋಡ್ಗಳನ್ನು
ರಫ್ತು ಮಾಡಿದ ನಂತರ ಸಾಲುಗಳ ಸಂಖ್ಯೆಯಷ್ಟೇ ಸಾಕಾಗುವುದಿಲ್ಲ: ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಹೊಂದಿರುವ 500 ಸಾಲುಗಳು ಹತ್ತಾರು
ಮೆಗಾಬೈಟ್ಗಳಷ್ಟು ಇರಬಹುದು, ಮತ್ತು 10 MB ಗಿಂತ ಹೆಚ್ಚಿನ ವಿನಂತಿಯನ್ನು insertAll ನಿರಾಕರಿಸುತ್ತದೆ. ಯಾವುದು ಮೊದಲು
ಬರುತ್ತದೆಯೋ ಅದರ ಆಧಾರದ ಮೇಲೆ 500 ಸಾಲುಗಳಲ್ಲಿ ಅಥವಾ 9 MB ಯಲ್ಲಿ ಚಂಕ್ಗಳು ಮುಚ್ಚುತ್ತವೆ.

## 5. OTLP/HTTP ಟ್ರೇಸ್ಗಳ ಗಮ್ಯಸ್ಥಾನ

ಕಾನ್ಫಿಗರೇಶನ್ `type: "otlp-http"` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಇದು ಉಳಿಸಲಾದ ಕಾಲ್ ಲಾಗ್ಗಳ ನಿಗದಿತ, ಕರ್ಸರ್-ಆಧಾರಿತ ರಫ್ತು ಆಗಿದ್ದು,
`open-sse/services/routing/otel.ts` ನಲ್ಲಿರುವ ಉತ್ತಮ-ಪ್ರಯತ್ನದ ಲೈವ್ ರೌಟಿಂಗ್-ಈವೆಂಟ್ ಸಿಂಕ್ ಅಲ್ಲ. ಇದು ಆ ಸಿಂಕ್ನ ಪರಿಸರ
ವೇರಿಯಬಲ್ಗಳು, ಟೈಮರ್ಗಳು ಅಥವಾ ಬಫರ್ಗಳನ್ನು ಓದುವುದಿಲ್ಲ ಅಥವಾ ಬದಲಾಯಿಸುವುದಿಲ್ಲ. ಎರಡನ್ನೂ ಸಕ್ರಿಯಗೊಳಿಸಿದರೆ ಸ್ವತಂತ್ರವಾದ
ಎರಡು ವಿಧದ spans ಉತ್ಪತ್ತಿಯಾಗಬಹುದು; ಈ call-log spans ಅನ್ನು ಪ್ರತ್ಯೇಕಿಸಲು `omniroute.log-export` ಇನ್ಸ್ಟ್ರುಮೆಂಟೇಶನ್ ಸ್ಕೋಪ್ ಅನ್ನು ಬಳಸಿ.

| Key                      | Default / ಉದ್ದೇಶ                                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| `endpoint`               | ಅಗತ್ಯವಿರುವ ಸಂಪೂರ್ಣ HTTP(S) ಟ್ರೇಸ್ URL; ಯಾವುದೇ `/v1/traces` suffix ಅನ್ನು ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ |
| `headers`                | ಐಚ್ಛಿಕ `Name: value` ಸಾಲುಗಳು ಅಥವಾ stringsನ JSON object; ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗಿದೆ            |
| `requestHeaderAllowlist` | ಖಾಲಿ (ಆಫ್); span attributes ಆಗಿ ಸೆರೆಹಿಡಿಯಬೇಕಾದ client header ಹೆಸರುಗಳು/ಪೂರ್ವಪ್ರತ್ಯಯಗಳು    |
| `serviceName`            | `omniroute`; resource `service.name`                                                     |
| `langfuseMapping`        | `false`; Langfuse generation/session/user attributes ಅನ್ನು ಸೇರಿಸುತ್ತದೆ                   |
| `identity`               | `pseudonymous`, `keyName`, ಅಥವಾ `none`                                                   |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                  |
| `timeoutMs`              | ಪ್ರತಿ HTTP ಪ್ರಯತ್ನಕ್ಕೆ `30000`                                                           |
| `environment`            | ಹೊಂದಿಸಲಾಗಿಲ್ಲ; ಐಚ್ಛಿಕ `langfuse.environment`                                             |

ಸಾಮಾನ್ಯ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಈ ಕ್ಷೇತ್ರಗಳನ್ನು ರೆಂಡರ್ ಮಾಡುತ್ತದೆ. `paths` API array ಅಥವಾ newline/commas ಮೂಲಕ ಬೇರ್ಪಡಿಸಿದ
ನಿಖರ paths ಹೊಂದಿರುವ textarea ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ. Embeddings, rerank ಮತ್ತು ಇತರ paths ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಅನುಮತಿಸದ
ಹೊರತು skip ಮಾಡಲಾಗುತ್ತದೆ. Skip ಮಾಡಿದ rows ಕೂಡ cursor ಅನ್ನು ಮುಂದಕ್ಕೆ ಸಾಗಿಸುತ್ತವೆ; ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ runnerನ
`exported`/`exportedTotal` counters ಸ್ವೀಕರಿಸಿದ spans ಬದಲಿಗೆ filter ಮಾಡಿದ rows ಸೇರಿದಂತೆ ಪ್ರಕ್ರಿಯೆಗೊಳಿಸಿದ source rows
ಅನ್ನು ಎಣಿಸುತ್ತವೆ. Filtering ಅನ್ನು child ನಲ್ಲಿ ಮಾಡಲಾಗುತ್ತದೆ; ಅದರ IPC/cursor contract ಬದಲಾಗುವುದಿಲ್ಲ.

URL validation `src/shared/network/outboundUrlGuard.ts` ನಲ್ಲಿರುವ DB-free `parseAndValidateNonMetadataUrl` helper ಅನ್ನು
ಬಳಸುತ್ತದೆ: `block-metadata` policy. ಇದು private URLs ಅನ್ನು opt in ಮಾಡಿಕೊಂಡಿರುವ webhook validatorನಂತೆಯೇ
unconditional metadata/protocol/embedded-credential checks ಅನ್ನು ಹೊಂದಿದೆ, ಆದರೆ global feature-flag override ಇಲ್ಲದೆಯೇ
localhost/LAN targets ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಅನುಮತಿಸುತ್ತದೆ. ಇದರಿಂದ private HTTP endpoints ಸೇರಿದಂತೆ self-hosted
Langfuse, Phoenix, Tempo ಮತ್ತು Collector endpoints ಅನ್ನು ಬಳಸಬಹುದು. Cloud-metadata hosts ಅನ್ನು ಯಾವಾಗಲೂ block ಮಾಡಲಾಗುತ್ತದೆ.
Redirects ಅನ್ನು follow ಮಾಡಲಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ collector credentials ಅನ್ನು ಬೇರೆ host ಗೆ redirect ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ.
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ lexical URL guardನಂತೆ, ಇದು DNS resolution ಅನ್ನು pin ಮಾಡುವುದಿಲ್ಲ; operator-ನಿಯಂತ್ರಿತ hosts ಅನ್ನು ಮಾತ್ರ
configure ಮಾಡಿ. Endpoint trusted network ನಲ್ಲಿ ಇಲ್ಲದಿದ್ದಾಗ HTTPS ಗೆ ಆದ್ಯತೆ ನೀಡಿ.

### Payload ಮತ್ತು delivery

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) ಅನುಮತಿಸಲಾದ ಪ್ರತಿ row ಗೆ ಒಂದು
CLIENT span ಅನ್ನು ಕೊಂಡೊಯ್ಯುತ್ತದೆ; ಅದರ ಹೆಸರನ್ನು ನಿಖರ request path ಆಧರಿಸಿ ಇಡಲಾಗುತ್ತದೆ. Path naming ಮೂಲಕ span ಹೆಸರಿನಲ್ಲಿ
model ಅಥವಾ identity data ಅನ್ನು embed ಮಾಡದೆಯೇ Chat Completions, Responses ಮತ್ತು Messages ಅನ್ನು ಪ್ರತ್ಯೇಕಿಸಲಾಗುತ್ತದೆ.
Resource attributes ನಲ್ಲಿ `service.name` ಮತ್ತು package ನ `service.version` ಸೇರಿವೆ.

ಸಾಮಾನ್ಯ chat attempt logger (`open-sse/handlers/chatCore/attemptLogging.ts`) completion ಸಮಯದಲ್ಲಿ
`duration = Date.now() - startTime` ಅನ್ನು ಬರೆಯುತ್ತದೆ ಮತ್ತು timestamp ಅನ್ನು ಒದಗಿಸುವುದಿಲ್ಲ;
`src/lib/usage/callLogs.ts` ನಲ್ಲಿರುವ `saveCallLogOperation` timestamp ಅನ್ನು write (completion) ಸಮಯಕ್ಕೆ default ಮಾಡುತ್ತದೆ.
ಆದ್ದರಿಂದ export ನಲ್ಲಿ end = row timestamp ಮತ್ತು start = end − duration
(milliseconds, decimal nanoseconds ಗೆ ಪರಿವರ್ತಿಸಲಾಗಿದೆ) ಆಗಿರುತ್ತದೆ. Caller ಒದಗಿಸಿದ historical timestamps ಕೂಡ end time
ಆಗಿ ಉಳಿಯುತ್ತವೆ; ಪ್ರತಿ row ಗೆ start/completion discriminator ಇರುವುದಿಲ್ಲ.
Null duration ಶೂನ್ಯವಾಗುತ್ತದೆ. Invalid/missing timestamps batch ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತವೆ ಮತ್ತು
non-deterministic spans ಅನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ. `ttftMs` nullable ಆಗಿದ್ದು `omniroute.ttft_ms` ಗೆ map ಆಗುತ್ತದೆ.

Attributes ನಲ್ಲಿ `gen_ai.operation.name="chat"`, provider, requested/response model,
input/output tokens, optional cache-read/cache-creation/reasoning tokens, HTTP status,
combo, cache source, session tag ಮತ್ತು correlation id ಸೇರಿವೆ. Integer OTLP values ಮತ್ತು timestamps ಗಳು decimal strings;
strings, booleans ಮತ್ತು fractional numbers ತಮ್ಮ native OTLP value variants ಅನ್ನು ಬಳಸುತ್ತವೆ. Error spans ERROR status
ಮತ್ತು sanitized status message ಅನ್ನು ಹೊಂದಿರುತ್ತವೆ. Canonical record ನಲ್ಲಿ upstream host URL ಇಲ್ಲ, ಆದ್ದರಿಂದ
collector ಅನ್ನು model server ಎಂದು ತಪ್ಪಾಗಿ ಗುರುತಿಸುವ ಬದಲು `server.address` ಅನ್ನು omit ಮಾಡಲಾಗುತ್ತದೆ. Cost ಅನ್ನು export ಮಾಡಲಾಗುವುದಿಲ್ಲ.

`includeBodies=true` ಇದ್ದಾಗ ಮಾತ್ರ content hydrate ಮಾಡಲಾಗುತ್ತದೆ. `langfuseMapping=false` ಇದ್ದಾಗ,
`gen_ai.input.messages` / `gen_ai.output.messages` attributes ನಲ್ಲಿ OmniRoute ಸಂಗ್ರಹಿಸಿದ sanitized request/response
body JSON ಇರುತ್ತದೆ (parse ಮಾಡಬಹುದಾದಾಗ canonicalized ಮಾಡಲಾಗುತ್ತದೆ); ಇದನ್ನು ಮರು-ರೂಪಿಸಿದ semconv messages array ಆಗಿ
ಪರಿವರ್ತಿಸಲಾಗುವುದಿಲ್ಲ. Clipped/non-JSON bodies raw text ಆಗಿಯೇ ಉಳಿಯುತ್ತವೆ. `langfuseMapping=true` ಇದ್ದಾಗ,
bodies ಅನ್ನು `langfuse.observation.input` / `langfuse.observation.output` ಆಗಿ ಮಾತ್ರ emit ಮಾಡಲಾಗುತ್ತದೆ;
ಪ್ರತಿ body ಒಮ್ಮೆ ಮಾತ್ರ ಕಳುಹಿಸಲಾಗುವಂತೆ `gen_ai.*.messages` attributes ಅನ್ನು omit ಮಾಡಲಾಗುತ್ತದೆ. ಎರಡೂ modes ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
hydration path ನಿಂದ `maxBodyBytes` ಅನ್ನು inherit ಮಾಡುತ್ತವೆ;
clipping ಅನ್ನು `omniroute.bodies_truncated=true` ಸೂಚಿಸುತ್ತದೆ.
ಈ destination ಮೂಲಕ ಯಾವುದೇ ಹೆಚ್ಚುವರಿ pipeline snapshots ಅಥವಾ unsanitized artifact reads ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ;
ಐಚ್ಛಿಕ request-header capture ಕೆಳಗೆ ವಿವರಿಸಿರುವ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ hydrated client snapshot ಅನ್ನು ಬಳಸುತ್ತದೆ.
Bodies ಅನ್ನು export ಮಾಡುವಾಗ hourly backlog ಸಂಗ್ರಹಿಸುವ ಬದಲು
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ minute-level cadence ಅನ್ನು ಬಳಸಿ.

### ಐಚ್ಛಿಕ client request headers

Header capture **default ಆಗಿ off ಆಗಿರುತ್ತದೆ**. Destination config ನಲ್ಲಿ `requestHeaderAllowlist` ಅನ್ನು ಹೊಂದಿಸಿ
ಮತ್ತು **Export prompts and responses** ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ (destination ನಲ್ಲಿ `includeBodies: true`).
Allowlist API array ಅಥವಾ newline/comma-separated names ಹೊಂದಿರುವ textarea ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ಹೆಸರುಗಳು ಕೇಸ್-ಇನ್ಸೆನ್ಸಿಟಿವ್ ಆಗಿ ಮತ್ತು ನಿಖರವಾಗಿ ಹೊಂದಿಕೆಯಾಗುತ್ತವೆ; ಆದರೆ ಒಂದೇ ಅಂತಿಮ `*` ಇದ್ದರೆ ಅದು ಖಾಲಿಯಲ್ಲದ
ಹೆಡರ್-ಹೆಸರು ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ. ಬರಿಯ `*`, ಮಧ್ಯದಲ್ಲಿರುವ ವೈಲ್ಡ್ಕಾರ್ಡ್ಗಳು ಮತ್ತು ಅಮಾನ್ಯ HTTP ಹೆಡರ್ ಹೆಸರುಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.
ಗರಿಷ್ಠ 64 ಆಯ್ಕೆದಾರಗಳಿರಬಹುದು; ಪ್ರತಿಯೊಂದರ ಹೆಸರು/ಪೂರ್ವಪ್ರತ್ಯಯವು ಗರಿಷ್ಠ 256 ASCII ಬೈಟ್ಗಳಾಗಿರಬಹುದು.
ಈ ಸೆಟ್ಟಿಂಗ್ `headers` ನಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿದೆ; `headers` exporter ಅನ್ನು collector ಗೆ ದೃಢೀಕರಿಸುತ್ತದೆ.

Capture ಕೇವಲ `pipeline_client_request` ನಿಂದ ಓದುತ್ತದೆ; ಇದು ಉಳಿಸಲಾದ ವಿವರವಾದ pipeline ನ
`clientRawRequest` (ಅಥವಾ ಹಳೆಯ `clientRequest`) ನಿಂದ ತುಂಬಲ್ಪಡುತ್ತದೆ. ಇದು provider request headers ಗೆ ಎಂದಿಗೂ fallback ಆಗುವುದಿಲ್ಲ.
ವಿನಂತಿಯನ್ನು ದಾಖಲಿಸುವಾಗ ವಿವರವಾದ pipeline logging ಸಕ್ರಿಯವಾಗಿರಬೇಕು. `includeBodies` ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದರೆ, ಅಥವಾ client-snapshot JSON
ಕಾಣೆಯಾಗಿದ್ದರೆ, ಹಾನಿಗೊಂಡಿದ್ದರೆ ಅಥವಾ ಕತ್ತರಿಸಲ್ಪಟ್ಟಿದ್ದರೆ, ಯಾವುದೇ ಹೆಡರ್ ಗುಣಲಕ್ಷಣಗಳನ್ನು ಹೊರಸೂಸಲಾಗುವುದಿಲ್ಲ. `maxBodyBytes` ಅನ್ನು ಹೆಚ್ಚಿಸುವುದರಿಂದ
export-time snapshot clipping ತಪ್ಪಿಸಬಹುದು; ಆದರೆ ಎಂದಿಗೂ ಉಳಿಸದ ವಿವರವನ್ನು ಮರುಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. 1 MiB ಗಿಂತ ದೊಡ್ಡದಾದ ಅಥವಾ
256 ಕ್ಕಿಂತ ಹೆಚ್ಚು ಹೆಡರ್ ಎಂಟ್ರಿಗಳನ್ನು ಹೊಂದಿರುವ snapshot ಅನ್ನು ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ. ಈಗಿರುವ prompt/response export
header capture ಜೊತೆಯಲ್ಲಿಯೇ ಸಕ್ರಿಯವಾಗಿರುತ್ತದೆ; allowlist headers-only hydration mode ಒದಗಿಸುವುದಿಲ್ಲ.

ಆಯ್ಕೆಮಾಡಿದ ಮೌಲ್ಯಗಳು OTLP string arrays ಆಗಿ `http.request.header.<full lowercase header name>` ಆಗುತ್ತವೆ,
ಒಂದೇ string ಇದ್ದರೂ ಸಹ. ಉದಾಹರಣೆಗೆ, `X-OmniRoute-Meta-Team: example-team` ಎಂಬುದು
`http.request.header.x-omniroute-meta-team` ಆಗಿ, ಕೆಳಗಿನಂತೆ ಪರಿಣಮಿಸುತ್ತದೆ:
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
ಸಂಪೂರ್ಣ prefix ಅನ್ನು ಉಳಿಸಲಾಗುತ್ತದೆ: ಇವು ಸಾಮಾನ್ಯ headers ಆಗಿದ್ದು, business-field parsing ಅಥವಾ
`omniroute.metadata.*` / Langfuse metadata conversion ನಡೆಯುವುದಿಲ್ಲ. `langfuseMapping` header semantics ಅನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ.
ಆಯ್ಕೆಮಾಡಿದ single-valued `User-Agent` standard scalar `user_agent.original` ಅನ್ನೂ ಹೊಂದಿಸುತ್ತದೆ.
ಒಂದು value ಒಳಗಿನ commas ಅನ್ನು ವಿಭಜಿಸಲಾಗುವುದಿಲ್ಲ. ಕೇಸ್ ರೂಪಾಂತರಗಳು saved entry order ನಲ್ಲಿ merge ಆಗುತ್ತವೆ; ಯಾವುದೇ ಅಮಾನ್ಯ variant ಇದ್ದರೆ
ಆ ಸಂಪೂರ್ಣ header ಅನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. Attributes ಅನ್ನು lowercase name ಕ್ರಮದಲ್ಲಿ ಜೋಡಿಸಲಾಗುತ್ತದೆ.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-key headers, auth/token/secret/password/credential markers ಹೊಂದಿರುವ
ಹೆಸರುಗಳು ಮತ್ತು internal gateway credentials ಅನ್ನು ಆಯ್ಕೆಮಾಡಿದ್ದರೂ ಅಥವಾ storage ನಲ್ಲಿ ಭಾಗಶಃ mask ಮಾಡಿದ್ದರೂ ಯಾವಾಗಲೂ ಹೊರಗಿಡಲಾಗುತ್ತದೆ.
ತಿಳಿದಿರುವ credential patterns ಹಂಚಿಕೆಯ credential detector ಅನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತವೆ; redaction markers ಅನ್ನು ಸುರಕ್ಷಿತ values ಆಗಿ export ಮಾಡದೆ ಕೈಬಿಡಲಾಗುತ್ತದೆ.
Strings ಮತ್ತು ಖಾಲಿಯಲ್ಲದ string arrays ಮಾತ್ರ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; numbers ಅಥವಾ objects ಅನ್ನು coerce ಮಾಡಲಾಗುವುದಿಲ್ಲ.
ಅಮಾನ್ಯ ಹೆಸರುಗಳು, prototype keys, control characters (horizontal tab ಹೊರತುಪಡಿಸಿ) ಮತ್ತು malformed Unicode ಅನ್ನು batch ವಿಫಲಗೊಳಿಸದೆ
ಅಥವಾ ಅವುಗಳ ವಿಷಯವನ್ನು errors ನಲ್ಲಿ ಪ್ರತಿಬಿಂಬಿಸದೆ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ.

ಪ್ರತಿ span ಗರಿಷ್ಠ 32 headers, ಪ್ರತಿ header ಗೆ 16 values, ಪ್ರತಿ value ಗೆ 4096 UTF-8 bytes,
ಮತ್ತು captured header names ಮತ್ತು valuesಗಳಾದ್ಯಂತ ಒಟ್ಟು 16384 UTF-8 bytes ಅನ್ನು ಹೊಂದಿರಬಹುದು. ಗಾತ್ರ ಮೀರಿದ/ಅಮಾನ್ಯ headers ಅನ್ನು
ಸಂಪೂರ್ಣವಾಗಿ ಕೈಬಿಡಲಾಗುತ್ತದೆ; ಅವುಗಳನ್ನು ಕತ್ತರಿಸಲಾಗುವುದಿಲ್ಲ. Selection ಒಂದು operator privacy decision ಆಗಿದೆ: ಸುರಕ್ಷಿತವಾಗಿ ಕಾಣುವ
ಹೆಸರುಗಳಲ್ಲಿಯೂ ವೈಯಕ್ತಿಕ data ಇರಬಹುದು, ಮತ್ತು ಈ ಮಿತಿಗಳು/detectors ಸಾಮಾನ್ಯ PII scrubber ಅಲ್ಲ.

### ವಿತರಣೆ ಮಿತಿಗಳು

Requests ಅನ್ನು 500 spans ಮತ್ತು 4 MiB UTF-8 JSON ಗೆ ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ; ಇದರಲ್ಲಿ envelope ಕೂಡ ಸೇರಿದೆ.
ಪ್ರತಿ allowed span ಅನ್ನು cursor batch ನ ಮೊದಲ request ಕಳುಹಿಸುವ ಮೊದಲು size-check ಮಾಡಲಾಗುತ್ತದೆ. ಮಿತಿಗಿಂತ ದೊಡ್ಡದಾದ ವೈಯಕ್ತಿಕ
span batch ನ ಯಾವುದೇ ಭಾಗವನ್ನು ಕಳುಹಿಸದೆ, `maxBodyBytes` ಕಡಿಮೆ ಮಾಡುವ ಸೂಚನೆಯೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; ಅದನ್ನು ಮೌನವಾಗಿ ಕೈಬಿಡಲಾಗುವುದಿಲ್ಲ.
Preflight ಕೇವಲ record references ಮತ್ತು byte counts ಅನ್ನು ಉಳಿಸಿಕೊಂಡು, ಪ್ರತಿ temporary span/JSON ಅನ್ನು discard ಮಾಡುತ್ತದೆ;
batch ನ ಎರಡನೇ serialized copy ಅನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳದೆ bounded chunks ಗಾಗಿ spans ಅನ್ನು ಮರುನಿರ್ಮಿಸಲಾಗುತ್ತದೆ. HTTP 408/429/5xx, network failures ಮತ್ತು timeouts ಗೆ ಗರಿಷ್ಠ
ಮೂರು attempts ಸಿಗುತ್ತವೆ; 250/500 ms exponential backoff ಬಳಸಲಾಗುತ್ತದೆ. `Retry-After` seconds ಅಥವಾ HTTP dates
delay ಅನ್ನು 5 seconds ವರೆಗೆ ವಿಸ್ತರಿಸಬಹುದು. ಇತರ statuses ತಕ್ಷಣವೇ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ. OTLP 2xx partial rejection ಕೂಡ
lost span ಅನ್ನು acknowledge ಮಾಡುವ ಬದಲು throw ಮಾಡುತ್ತದೆ; empty ಅಥವಾ valid JSON acknowledgements ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ, ಜೊತೆಗೆ
64 KiB response-read cap ಇರುತ್ತದೆ.

Errors ನಲ್ಲಿ exporter-owned facts ಮಾತ್ರ ಇರುತ್ತವೆ: HTTP status, retry class, attempts ಮತ್ತು sent span
counts, ಅಥವಾ fixed acknowledgement/network failure wording. Collector response bodies,
partial-success counts ಮತ್ತು response headers ಅನ್ನು errors, logs ಅಥವಾ dashboard ಗೆ ಎಂದಿಗೂ ನಕಲಿಸಲಾಗುವುದಿಲ್ಲ.
ವಿಫಲವಾದ ಅಥವಾ ಭಾಗಶಃ ಸ್ವೀಕರಿಸಲಾದ batch acknowledge ಆಗುವುದಿಲ್ಲ: destination ಆ status ಜೊತೆಗೆ
Failing ಎಂದು ತೋರಿಸುತ್ತದೆ, cursor ಕೊನೆಯ acknowledged batch ನಲ್ಲೇ ಉಳಿಯುತ್ತದೆ ಮತ್ತು ಮುಂದಿನ run
ಅದೇ rows ಅನ್ನು ಮರುಕಳುಹಿಸುತ್ತದೆ. Permanent statuses collector ಅಥವಾ configuration ಸರಿಯಾಗುವವರೆಗೆ fail ಆಗುತ್ತಲೇ ಇರುತ್ತವೆ.
Response details ಗಾಗಿ collector ನ ಸ್ವಂತ logs ಬಳಸಿ. Call-log error summaries ತಮ್ಮ ಪ್ರತ್ಯೇಕ redaction ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.
`prepare()` ಯಾವುದನ್ನೂ provision ಮಾಡುವುದಿಲ್ಲ; Test ನಿಖರವಾಗಿ `{"resourceSpans":[]}` ಅನ್ನು post ಮಾಡುತ್ತದೆ ಮತ್ತು call-log spans ಬರೆಯದೆ
HTTP status ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

Trace ids ಮತ್ತು span ids ಗಳು
`"omniroute.trace\\0" + callLogId` ಮತ್ತು `"omniroute.span\\0" + callLogId` ಮೇಲಿನ SHA-256 ನ ಮೊದಲ 32/16 hex digits ಆಗಿರುತ್ತವೆ.
Re-sends ಒಂದೇ ids ಅನ್ನು ಹೊಂದಿರುತ್ತವೆ. ಇದು deduplication guarantee ಅಲ್ಲ: Langfuse
v4 ingestion ಸೇರಿದಂತೆ ಕೆಲವು backends ಒಂದೇ-id spans ಅನ್ನು deduplicate ಮಾಡುವುದಿಲ್ಲ. Crash ಅಥವಾ partial chunk failure ಆದಾಗ
ಗರಿಷ್ಠ ಒಂದು unacknowledged cursor batch ಅನ್ನು ಮರುಕಳುಹಿಸಬಹುದು; ಕೊನೆಯ HTTP chunk ಮಾತ್ರವಲ್ಲ, ಆ ಸಂಪೂರ್ಣ
batch duplicate ಆಗಬಹುದು. ಈ tradeoff ಅನ್ನು ಗಮನದಲ್ಲಿಟ್ಟುಕೊಂಡು cursor batch size ಆಯ್ಕೆಮಾಡಿ.

### Langfuse ಉದಾಹರಣೆ

Self-hosted Langfuse instance ಗಾಗಿ ಈ fields ಅನ್ನು configure ಮಾಡಿ:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Authorization value ಅನ್ನು ಸ್ಥಳೀಯವಾಗಿ literal `public-key:secret-key`
string ನ Base64 ಆಗಿ ನಿರ್ಮಿಸಿ (ಉದಾಹರಣೆಗೆ `Buffer.from(publicKey + ":" + secretKey).toString("base64")` ಮೂಲಕ).
ನೈಜ credentials ಅನ್ನು logs, screenshots ಅಥವಾ issues ಗೆ paste ಮಾಡಬೇಡಿ. Mapping ಸ್ವಯಂಚಾಲಿತವಾಗಿ
`x-langfuse-ingestion-version: 4` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ; Authorization ಅನ್ನು ಇನ್ನೂ `headers` ನಲ್ಲಿ ಒದಗಿಸಬೇಕು.
Headers ಮತ್ತು generated identity salt ಎರಡೂ ಈಗಿರುವ encrypted secret-field mechanism ಮತ್ತು API placeholders ಅನ್ನು ಬಳಸುತ್ತವೆ;
`STORAGE_ENCRYPTION_KEY` ಅಗತ್ಯವಿದೆ.

ಮ್ಯಾಪಿಂಗ್ನಲ್ಲಿ generation type/model, JSON ಬಳಕೆಯ ವಿವರಗಳು (input/output/total ಮತ್ತು ಲಭ್ಯವಿರುವ
cache keys), JSON input/output snapshots, ERROR/DEFAULT ಮಟ್ಟ, sanitized status message,
trace name, session id, ಐಚ್ಛಿಕ environment ಮತ್ತು provider, requested model, path, combo, cache
source ಹಾಗೂ statusಗಾಗಿ filter ಮಾಡಬಹುದಾದ
`langfuse.observation.metadata.<key>` ಅನ್ನು ಸೇರಿಸಲಾಗುತ್ತದೆ. `langfuse.observation.completion_start_time` ಎಂಬುದು
ISO 8601 ಸ್ವರೂಪದಲ್ಲಿ start + TTFT ಆಗಿರುತ್ತದೆ, ಆದರೆ TTFT ತಿಳಿದಿದ್ದು duration ಒಳಗಿದ್ದಾಗ ಮಾತ್ರ.
ಯಾವುದೇ cost attributes ಕಳುಹಿಸಲಾಗುವುದಿಲ್ಲ.

`langfuse.user.id` ಗೆ identity modes ಅನ್ವಯಿಸುತ್ತವೆ:

- `pseudonymous` (ಡೀಫಾಲ್ಟ್): ಪ್ರತಿ destinationಗೆ random 32-byte salt ಬಳಸಿ API keyನ internal idನ HMAC-SHA256. Salt ಇಲ್ಲದಿದ್ದರೆ creation ಸಮಯದಲ್ಲಿ ರಚಿಸಲಾಗುತ್ತದೆ, `identitySalt` ಆಗಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ, ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು edits ಸಮಯದಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ. Raw key ids ಅನ್ನು span attributesನಲ್ಲಿ ಎಂದಿಗೂ ಇರಿಸಲಾಗುವುದಿಲ್ಲ. Destinationನ salt ಅನ್ನು ಮರುರಚಿಸುವುದು/ತಿರುಗಿಸುವುದು identities ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
- `keyName`: ಸಂರಚಿಸಲಾದ API key name, ಆ operator label ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.
- `none`: ಯಾವುದೇ user id ಇಲ್ಲ. Session tags ಇದ್ದಾಗ ಅವುಗಳನ್ನು ಇನ್ನೂ export ಮಾಡಲಾಗುತ್ತದೆ; ಈ modes ಅನಿಯಂತ್ರಿತ prompt content ಅಥವಾ operator ಒದಗಿಸಿದ session/correlation labels ಅನ್ನು anonymize ಮಾಡುವುದಿಲ್ಲ.

### Backfill ಇಲ್ಲದೆ ಪ್ರಾರಂಭಿಸುವುದು

Creation ಸಮಯದಲ್ಲಿ ಮಾತ್ರ **ಪ್ರಸ್ತುತ ಸ್ಥಾನದಿಂದ ಪ್ರಾರಂಭಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ logs ಅನ್ನು skip ಮಾಡಿ)** ಅನ್ನು enable ಮಾಡಿ ಅಥವಾ create API payloadನ top levelನಲ್ಲಿ
`startFromCurrentPosition: true` ಅನ್ನು pass ಮಾಡಿ. ಇದು migration ಇಲ್ಲದೆ, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ cursor helpers ಬಳಸಿ
`cursor_row_id` ಅನ್ನು ಪ್ರಸ್ತುತ ಗರಿಷ್ಠವಾಗಿ ಉಳಿಸಿಕೊಂಡಿರುವ call-log rowidಗೆ initialize ಮಾಡುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ false ಆಗಿದೆ (cursor 0 ಮತ್ತು retained-history backfill).
ಇದು update ಸಮಯದಲ್ಲಿ cursor reset ಮಾಡುವ setting ಅಲ್ಲ.

ಹಂಚಿಕೆಯ `ttftMs` addition BigQuery mapper ಮತ್ತು new-table schemaಗೆ nullable `ttft_ms` column ಅನ್ನು ಕೂಡ ಸೇರಿಸುತ್ತದೆ: canonical recordನ ಪ್ರತಿಯೊಂದು fieldಗೂ ಒಂದು column ಇರಬೇಕು ಎಂದು ಅದರ schema test ಅಗತ್ಯಪಡಿಸುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ tables ಬದಲಾಗದೆ export ಆಗುತ್ತವೆ: `prepare()` table schema ಅನ್ನು ಓದಿ, ಆ column ಇಲ್ಲದಿದ್ದಾಗ ಮಾತ್ರ `ttft_ms` ಅನ್ನು omit ಮಾಡುತ್ತದೆ. ಮುಂದಿನ runನಲ್ಲಿ TTFT ಪಡೆಯಲು nullable INT64 column ಅನ್ನು ಸೇರಿಸಿ ಅಥವಾ new table ಬಳಸಿ. ಐಚ್ಛಿಕ TTFT column schema update ಅನ್ನು trigger ಮಾಡುವುದಿಲ್ಲ. Usage-evidence columns ಕೆಳಗಿನ conditional, opt-in compatibility flow ಅನ್ನು ಅನುಸರಿಸುತ್ತವೆ; ಇತರ row fields strict schema checking ಅನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ.

## 6. ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸುವುದು

1. `LogExportDestinationType` ಅನ್ನು ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡುವ `src/lib/logExport/destinations/<name>.ts` ಅನ್ನು ರಚಿಸಿ:
   ಒಂದು Zod `configSchema`, UI ಗಾಗಿ `fields` ವಿವರಣಾ ಅರೇ, `secretFields`, ಮತ್ತು
   `test()` / `prepare()` / `send(records)` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವ `createClient(config)`.
2. ಅದನ್ನು `src/lib/logExport/registry.ts` ನಲ್ಲಿರುವ `DESTINATIONS` ಅರೇಗೆ ಸೇರಿಸಿ.
3. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ.

ಇಷ್ಟೇ ಸಂಪೂರ್ಣ ಬದಲಾವಣೆ: ಶಾಶ್ವತ ಸಂಗ್ರಹಣೆ, cron ಕೆಲಸ, REST ಪದರ, ರಹಸ್ಯಗಳ ಎನ್‌ಕ್ರಿಪ್ಶನ್ ಮತ್ತು
ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಫಾರ್ಮ್ ಎಲ್ಲವೂ ರಿಜಿಸ್ಟ್ರಿಯನ್ನು ಓದುತ್ತವೆ.

ಹೊಸ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಎರಡು ನಿಯಮಗಳು:

- ಭಾಗಶಃ ವೈಫಲ್ಯವಾದಾಗ `send()` **ಕಡ್ಡಾಯವಾಗಿ ದೋಷವನ್ನು ಎಸೆಯಬೇಕು**. ಯಶಸ್ವಿಯಾಗಿ ಪೂರ್ಣಗೊಳ್ಳುವುದರ ಅರ್ಥ "ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ ಈ ಸಾಲುಗಳಿವೆ",
  ಮತ್ತು ಕರ್ಸರ್ ಅವುಗಳನ್ನು ಶಾಶ್ವತವಾಗಿ ದಾಟಿ ಮುಂದೆ ಸಾಗುತ್ತದೆ.
- ಬಳಕೆದಾರರು ಒದಗಿಸಿದ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವ ಗಮ್ಯಸ್ಥಾನವು, ಅದರಿಂದ ಡೇಟಾ ಪಡೆಯುವ ಮೊದಲು,
  ವೆಬ್‌ಹುಕ್‌ಗಳು ಮಾಡುವಂತೆಯೇ `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`)
  ಮೂಲಕ ಅದನ್ನು ಮೌಲ್ಯೀಕರಿಸಬೇಕು. BigQuery ಗೆ ಇದು ಅಗತ್ಯವಿಲ್ಲ: ಅದರ ಹೋಸ್ಟ್‌ಗಳು ಸ್ಥಿರವಾಗಿವೆ.

## 7. ಅದನ್ನು ನಿರ್ವಹಿಸುವುದು

- **ಡ್ಯಾಶ್ಬೋರ್ಡ್**: Integrations → Log export. ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸಿ, ರುಜುವಾತುಗಳನ್ನು ಪರಿಶೀಲಿಸಲು ಯಾವುದೇ ಸಾಲುಗಳನ್ನು ಬರೆಯದೆ **ಪರೀಕ್ಷೆ** ನಡೆಸಿ,
  ನಂತರ ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ.
- **ಬ್ಯಾಕ್ಲಾಗ್**: ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನ ಕಾರ್ಡ್ ಬಾಕಿ ಇರುವ ಸಾಲುಗಳು ಮತ್ತು ಕರ್ಸರ್ ಅನ್ನು ತೋರಿಸುತ್ತದೆ; `GET
/api/log-export/status` ಅದೇ ಅಂಕಿಅಂಶಗಳ ಜೊತೆಗೆ ಕೊನೆಯ 20 ಕೆಲಸದ ರನ್ಗಳನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
- **ವಿಫಲಗೊಳ್ಳುವ ಗಮ್ಯಸ್ಥಾನವು ಇತರ ಗಮ್ಯಸ್ಥಾನಗಳನ್ನು ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ** — ರನ್ ಸಾರಾಂಶವು ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ
  ಸ್ಥಿತಿಯನ್ನು `last_status` / `last_error` ನಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು ಕೆಲಸದ ರನ್ ಇತಿಹಾಸವು ಒಟ್ಟು ಸ್ಥಿತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.
- **ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸಿದರೆ ಅದರ ಕರ್ಸರ್ ಅಳಿಸಲಾಗುತ್ತದೆ.** ಅದನ್ನು ಮರುಸೇರಿಸಿದಾಗ ಉಳಿಸಿಕೊಂಡಿರುವ
  ಅತ್ಯಂತ ಹಳೆಯ ಕರೆ ಲಾಗ್ನಿಂದ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ; ಇದರಿಂದ ಗಮ್ಯಸ್ಥಾನವು ಈಗಾಗಲೇ ಹೊಂದಿರಬಹುದಾದ ಸಾಲುಗಳನ್ನು
  ಮರುಕಳುಹಿಸಲಾಗುತ್ತದೆ. BigQuery ನಲ್ಲಿ ಪ್ರತಿ ಸಾಲಿನ `insertId` ಇದನ್ನು BigQuery ಯ ಸ್ವಂತ
  ನಕಲು-ತಡೆಹಿಡಿಯುವ ಅವಧಿಯೊಳಗೆ ಮಾತ್ರ ನಿರ್ವಹಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸುವುದಕ್ಕಿಂತ
  ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದಕ್ಕೆ ಆದ್ಯತೆ ನೀಡಿ.

### ಬಳಕೆ-ಸಾಕ್ಷ್ಯ ಸ್ಕೀಮಾ ಹೊಂದಾಣಿಕೆ

ಹೊಸ BigQuery ಟೇಬಲ್ಗಳು nullable `usage_evidence` (JSON ಹೊಂದಿರುವ STRING) ಮತ್ತು
`usage_estimated` (BOOL) ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತವೆ. `autoCreate` ಸಕ್ರಿಯವಾಗಿದ್ದರೆ, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಟೇಬಲ್ಗೆ ಈ ಕಾಣೆಯಾಗಿರುವ nullable ಕಾಲಮ್ಗಳನ್ನು ಮಾತ್ರ ಸೇರಿಸಬಹುದು. ರಫ್ತುದಾರವು ಕ್ಷೇತ್ರದ ಮೆಟಾಡೇಟಾವನ್ನು
ಒಳಗೊಂಡಂತೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಂಪೂರ್ಣ ಸ್ಕೀಮಾವನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ ಮತ್ತು ಹಿಂತಿರುಗಿಸಲಾದ etag ಬಳಸಿ
ಷರತ್ತುಬದ್ಧ PATCH ಅನ್ನು ಸಲ್ಲಿಸುತ್ತದೆ. ಸಮಕಾಲೀನ ಸ್ಕೀಮಾ ಬದಲಾವಣೆಯು ಅದನ್ನು ಮೇಲ್ಬರೆಯುವ ಬದಲು ರಫ್ತನ್ನು
ವಿಫಲಗೊಳಿಸುತ್ತದೆ; ಮುಂದಿನ ರನ್ ಟೇಬಲ್ ಅನ್ನು ಮತ್ತೆ ಓದುತ್ತದೆ.

`autoCreate` ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದರೆ, ಬಳಕೆ-ಸಾಕ್ಷ್ಯ ಹೊಂದಿರುವ ದಾಖಲೆಗಳನ್ನು ರಫ್ತು ಮಾಡುವ ಮೊದಲು ಈ
ಕಾಲಮ್ಗಳನ್ನು ನೀವೇ ಸೇರಿಸಿ. ಕಾಣೆಯಾಗಿರುವ ಸ್ಕೀಮಾ/etag ಮೆಟಾಡೇಟಾ ಅಥವಾ ವಿಫಲವಾದ ನವೀಕರಣವು
ಸಾಕ್ಷ್ಯ ಹೊಂದಿರುವ ಇನ್ಸರ್ಟ್ಗಳನ್ನೂ ತಡೆಯುತ್ತದೆ. ಆ ವಿಫಲತೆಯ ಸಂದರ್ಭದಲ್ಲಿ ರಫ್ತು ಕರ್ಸರ್ ಮುಂದುವರಿಯುವುದಿಲ್ಲ
ಮತ್ತು ಸಾಕ್ಷ್ಯವನ್ನು ಎಂದಿಗೂ ಮೌನವಾಗಿ ಕೈಬಿಡಲಾಗುವುದಿಲ್ಲ. ರಫ್ತು ತಡೆಹಿಡಿದಿರುವಾಗಲೂ ಸ್ಥಳೀಯ ಲಾಗ್
ಉಳಿಸಿಕೆ ಅನ್ವಯಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಉಳಿಸಿಕೊಂಡಿರುವ ಮೂಲ ಸಾಲುಗಳ ಅವಧಿ ಮುಗಿಯುವ ಮೊದಲು ವಿಫಲತೆಯನ್ನು
ಪರಿಹರಿಸಿ.
