OmniRoute ಕರೆ ಲಾಗ್ಗಳನ್ನು ಬಾಹ್ಯ ಅನಾಲಿಟಿಕ್ಸ್ ಸ್ಟೋರ್ಗೆ ನಿರಂತರವಾಗಿ, ಇನ್ಕ್ರಿಮೆಂಟಲ್ ಆಗಿ ರಫ್ತು ಮಾಡುವುದು.

Logs ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಟ್ಯಾಬ್ ವಿನಂತಿ ಇತಿಹಾಸವನ್ನು SQLite (`call_logs`) ನಲ್ಲಿ ಇರಿಸುತ್ತದೆ; ಇದು
ರೊಟೇಶನ್ ಮತ್ತು ರಿಟೆನ್ಶನ್ನಿಂದ ಮಿತಿಗೊಳಿಸಲ್ಪಟ್ಟಿದೆ. ಲಾಗ್ ರಫ್ತು ಅದೇ ದಾಖಲೆಗಳ ಸಮೂಹವನ್ನು ವೇಳಾಪಟ್ಟಿಯಂತೆ ಹೊರಗೆ ಕಳುಹಿಸುತ್ತದೆ, ಇದರಿಂದ ಅವು
ಸ್ಥಳೀಯ ಡೇಟಾಬೇಸ್ಗಿಂತ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯಬಹುದು ಮತ್ತು ಇತರ ಡೇಟಾದೊಂದಿಗೆ ಜೋಡಿಸಬಹುದು. BigQuery ಮೊದಲ ಗಮ್ಯಸ್ಥಾನವಾಗಿದೆ;
ಪೈಪ್ಲೈನ್ ಒಂದು ರಿಜಿಸ್ಟ್ರಿಯಾಗಿರುವುದರಿಂದ, ಹೆಚ್ಚಿನ ಗಮ್ಯಸ್ಥಾನಗಳನ್ನು ಹೆಚ್ಚುವರಿಯಾಗಿ ಸೇರಿಸಬಹುದು.

## 1. ಇದು ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ

```
ಸರ್ವರ್ (config ಅನ್ನು ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿ + ಮೌಲ್ಯೀಕರಿಸಿ, cursor ಅನ್ನು ಸಮನ್ವಯಗೊಳಿಸಿ)
  → IPC ಪ್ರಾರಂಭಿಸಿ → ಪ್ರತ್ಯೇಕಿಸಲಾದ exportChild OS process
    → ಓದಲು-ಮಾತ್ರವಾದ storage.sqlite → ಹಂಚಿಕೆಯ call-log query/mapping
      → ಅಸಿಂಕ್ರೋನಸ್ artifact hydration → destination prepare()/send()
        → batch IPC → ಸರ್ವರ್ cursor ಅನ್ನು ಉಳಿಸುತ್ತದೆ → ack IPC
          → ಮುಂದಿನ batch; done IPC → ಸರ್ವರ್ ಯಶಸ್ಸನ್ನು ದಾಖಲಿಸುತ್ತದೆ
```

- **ವೇಳಾಪಟ್ಟಿ** — ಒಂದು `JobRegistry` cron job, `log_export`, ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ `0 * * * *` (ಪ್ರತಿ ಗಂಟೆಗೆ,
  UTC). `src/lib/initCloudSync.ts` ನಲ್ಲಿ ನೋಂದಾಯಿಸಲಾಗಿದೆ; `OMNIROUTE_LOG_EXPORT_CRON` ಮೂಲಕ ಬದಲಾಯಿಸಬಹುದು.
  ಪ್ರತಿ tick ಪ್ರತಿಯೊಂದು **ಸಕ್ರಿಯಗೊಳಿಸಲಾದ** destination ಅನ್ನು ಅನುಕ್ರಮವಾಗಿ ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರಕ್ರಿಯೆಗೊಳಿಸುತ್ತದೆ.
- **Cursor** — SQLite ನ ಅಪ್ರತ್ಯಕ್ಷ `call_logs.rowid`, ಪ್ರತಿ destination ಗಾಗಿ
  `log_export_destinations.cursor_row_id` ನಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ. `timestamp` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ cursor ಆಗಿ ಬಳಸಲಾಗುವುದಿಲ್ಲ:
  ಕರೆ ಮಾಡುವವರು ತಮ್ಮದೇ ಮೌಲ್ಯವನ್ನು ಒದಗಿಸಬಹುದು; ಆದ್ದರಿಂದ ನಿಧಾನವಾದ request, ನಂತರ ಪ್ರಾರಂಭವಾದ ವೇಗವಾದ
  request ಗಿಂತ ತಡವಾಗಿ ಬರೆಯಲ್ಪಡಬಹುದು ಮತ್ತು timestamp cursor ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.
- **Batching** — ಪ್ರತಿ request ಗೆ `batch_size` ಸಾಲುಗಳು (ಪೂರ್ವನಿಯೋಜಿತ 500), ಪ್ರತಿ run ಗೆ
  `max_rows_per_run` ಸಾಲುಗಳು (ಪೂರ್ವನಿಯೋಜಿತ 10000); ಇದರಿಂದ ದೊಡ್ಡ backlog ಒಂದೇ run ಅನ್ನು ನಿರ್ಬಂಧಿಸುವ ಬದಲು
  ಹಲವಾರು tick ಗಳಲ್ಲಿ ಖಾಲಿಯಾಗುತ್ತದೆ.
- **Delivery** — `send()` ಪೂರ್ಣಗೊಂಡ ನಂತರವೇ cursor ಮುಂದುವರಿಯುತ್ತದೆ. ವಿಫಲವಾದ batch,
  cursor ಅನ್ನು ಇದ್ದಲ್ಲಿಯೇ ಉಳಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಅದೇ ಸಾಲುಗಳನ್ನು ಮುಂದಿನ run ನಲ್ಲಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ. ಭರವಸೆಯು
  ಕನಿಷ್ಠ-ಒಮ್ಮೆ ವಿತರಣೆ ಮತ್ತು destination ಕಡೆಯ ನಕಲು-ನಿವಾರಣೆಯದ್ದಾಗಿದೆ, ನಿಜವಾದ ನಿಖರವಾಗಿ-ಒಮ್ಮೆ ವಿತರಣೆಯದ್ದಲ್ಲ: BigQuery ಪ್ರತಿ
  ಸಾಲಿಗೆ call-log id ಅನ್ನು key ಆಗಿ ಬಳಸುತ್ತದೆ ಮತ್ತು ತನ್ನದೇ dedup window ಒಳಗೆ ಅದನ್ನು ಸಾಧ್ಯವಾದಷ್ಟು ಉತ್ತಮ ರೀತಿಯಲ್ಲಿ
  ಪಾಲಿಸುತ್ತದೆ.
- **ಅತಿಕ್ರಮಣ ತಡೆ** — cron tick ಮತ್ತು `POST .../run` ಒಂದೇ ಸಮಯದಲ್ಲಿ ಕಾರ್ಯಗತಗೊಳ್ಳಬಹುದು. ಈಗಾಗಲೇ
  ಪ್ರಕ್ರಿಯೆಗೊಳ್ಳುತ್ತಿರುವ destination ಅನ್ನು ಎರಡು ಬಾರಿ ಪ್ರಕ್ರಿಯೆಗೊಳಿಸುವ ಬದಲು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ (run ಫಲಿತಾಂಶದಲ್ಲಿ `skipped: true`);
  ಹೀಗಾಗಿ ಸಮಕಾಲೀನ run ಒಂದು batch ಅನ್ನು ಮರುಕಳುಹಿಸಲು ಅಥವಾ cursor ಅನ್ನು ಹಿಂದಕ್ಕೆ ಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ.
- **Purge ಮರುಪಡೆಯುವಿಕೆ** — `cursor_row_id`, `MAX(rowid)` ಗಿಂತ ಮೇಲಕ್ಕೆ ಹೋದರೆ (ಇಡೀ table ಅನ್ನು
  purge ಮಾಡಿ rowid ಗಳು ಮರುಪ್ರಾರಂಭವಾಗಿದ್ದರೆ), runner ಶಾಶ್ವತವಾಗಿ ಹೊಸ ಸಾಲುಗಳನ್ನು ಕಾಣದೆ ಹೋಗುವ ಬದಲು 0 ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ.

### ಪ್ರತ್ಯೇಕಿಸಲಾದ runner ಮತ್ತು ಮಿತಿಗಳು

Node ನಲ್ಲಿನ ಪ್ರತಿಯೊಂದು destination run ಪ್ರತ್ಯೇಕವಾದ, ಅಲ್ಪಕಾಲೀನ OS child process ಅನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ (`child_process`
ಅನ್ನು IPC ಜೊತೆಗೆ ಬಳಸುತ್ತದೆ, `worker_threads` ಅಲ್ಲ). Body ಓದುವಿಕೆ, payload JSON parsing/serialization, destination
`prepare()` ಮತ್ತು destination network I/O ಎಲ್ಲವೂ ಅಲ್ಲಿಯೇ ನಡೆಯುತ್ತವೆ, ಸರ್ವರ್ನ event loop ನಲ್ಲಿ ಅಲ್ಲ.
IPC ಮೂಲಕ configuration ಮತ್ತು ಸಣ್ಣ progress message ಗಳು ಮಾತ್ರ ಸಾಗುತ್ತವೆ; export ಮಾಡಿದ record ಗಳು ಎಂದಿಗೂ
ಸರ್ವರ್ಗೆ ಮರಳುವುದಿಲ್ಲ. cron job ಮತ್ತು Run now route ಅದೇ public result ಮತ್ತು overlap guard ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

Child, ಸರ್ವರ್ ಪರಿಹರಿಸಿದ `DATA_DIR/storage.sqlite` ಅನ್ನು `node:sqlite` ಬಳಸಿ ಓದಲು-ಮಾತ್ರವಾಗಿ ತೆರೆಯುತ್ತದೆ,
`busy_timeout=5000` ಮತ್ತು `query_only=ON` ಜೊತೆಗೆ. ಇದು ಯಾವುದೇ DB singleton ಅನ್ನು import ಮಾಡುವುದಿಲ್ಲ ಮತ್ತು
migrations, backups ಅಥವಾ SQLite updates ಅನ್ನು ನಿರ್ವಹಿಸುವುದಿಲ್ಲ. ಕಾಣೆಯಾದ/ದೋಷಪೂರಿತ artifact bookkeeping (ದೋಷಪೂರಿತ-artifact
UPDATE ಸೇರಿದಂತೆ) dashboard detail path ನಲ್ಲಿ ಮಾತ್ರ ಉಳಿಯುತ್ತದೆ. ಎರಡೂ path ಗಳು ಶುದ್ಧ
detail resolver ಅನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ; export ಅಸಿಂಕ್ರೋನಸ್ filesystem read ಗಳನ್ನು ಮತ್ತು ಅದೇ artifact → legacy
inline → legacy disk → none ಪರಿಹಾರ ಕ್ರಮವನ್ನು ಬಳಸುತ್ತದೆ. Child ತನ್ನ reader ಅನ್ನು ತೆರೆಯುವಾಗ run ಗರಿಷ್ಠ insertion rowid ನ
snapshot ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ; ನಂತರದ insert ಗಳು ಮುಂದಿನ run ಗಾಗಿ ಕಾಯುತ್ತವೆ. ಇದು insertion
boundary ಆಗಿದೆಯೇ ಹೊರತು ದೀರ್ಘಕಾಲ ಇರುವ SQLite transaction ಅಲ್ಲ: network wait ಗಳ ಸಮಯದಲ್ಲಿ WAL writer ಗಳು ಮತ್ತು
checkpoint ಗಳು ಮುಕ್ತವಾಗಿ ಮುಂದುವರಿಯಬಹುದು. ಈಗಾಗಲೇ ಇರುವ ಸಾಲುಗಳ update/delete ಗಳು ಈ boundary ಯಿಂದ ಸ್ಥಗಿತಗೊಳ್ಳುವುದಿಲ್ಲ.

ಸ್ವೀಕರಿಸಲಾದ ಪ್ರತಿ batch ನಂತರ, child acknowledgement ಗಾಗಿ ಕಾಯುತ್ತದೆ. ಸರ್ವರ್ ಮೊದಲು
`advanceLogExportCursor` ಮೂಲಕ cursor ಅನ್ನು ಉಳಿಸಿ, ನಂತರ `ack` ಕಳುಹಿಸುತ್ತದೆ; ಅದಕ್ಕಿಂತ ಮೊದಲು ಮುಂದಿನ batch ಪ್ರಾರಂಭವಾಗುವುದಿಲ್ಲ.
ಕಳುಹಿಸುವಿಕೆ ವಿಫಲವಾದರೆ, crash ಆದರೆ ಅಥವಾ timeout ಆದರೆ, ಆ batch ಅನ್ನು ಮುಂದುವರಿಸದೆ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ. ಈ ಹಿಂದೆ
acknowledge ಮಾಡಲಾದ batch ಗಳು commit ಆಗಿಯೇ ಉಳಿಯುತ್ತವೆ; acknowledge ಮಾಡದ ಹೆಚ್ಚೆಂದರೆ ಒಂದೇ batch ಅನ್ನು ಮರುಕಳುಹಿಸಬಹುದು.
`done` ಬಂದ ನಂತರ ಮತ್ತು child ದೋಷವಿಲ್ಲದೆ exit ಆದ ಬಳಿಕ ಮಾತ್ರ ಯಶಸ್ಸನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ. ವೈಫಲ್ಯಗಳು child ಅನ್ನು
SIGTERM ಮೂಲಕ ಕೊನೆಗೊಳಿಸುತ್ತವೆ, 500 ms ನಂತರ SIGKILL ಗೆ ಹೆಚ್ಚಿಸುತ್ತವೆ, ಮತ್ತು runner process ಮುಚ್ಚುವವರೆಗೆ ಕಾಯುತ್ತದೆ.

| ಪರಿಸರ ಚರಾಂಶ                                   | ಪೂರ್ವನಿಯೋಜಿತ | ಉದ್ದೇಶ                               |
| --------------------------------------------- | ------------ | ------------------------------------ |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | ಪ್ರತಿ destination ಗೆ wall-clock ಮಿತಿ |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | Child V8 old-space ಮಿತಿ, MB ಯಲ್ಲಿ    |

ಅಮಾನ್ಯ/ಧನಾತ್ಮಕವಲ್ಲದ/ಪೂರ್ಣಾಂಕವಲ್ಲದ ಮೌಲ್ಯಗಳು ಪೂರ್ವನಿಯೋಜಿತ ಮೌಲ್ಯಗಳನ್ನು ಬಳಸುತ್ತವೆ. Heap setting ಒಟ್ಟು
RSS ಮಿತಿಯಲ್ಲ; ಬಹಳ ದೊಡ್ಡ batch ಗಳು ಇನ್ನೂ child memory ಅನ್ನು ಖಾಲಿಮಾಡಿ run ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲಗೊಳಿಸಬಹುದು.
1024 MB ಪೂರ್ವನಿಯೋಜಿತ ಮೌಲ್ಯವು bodies ಸಕ್ರಿಯವಾಗಿರುವ 512 KiB artifact ಗಳ ಪೂರ್ವನಿಯೋಜಿತ 500-ಸಾಲಿನ batch ಗೆ,
BigQuery ಯ byte-chunked JSON serialization ಸೇರಿದಂತೆ, ಸಾಕಷ್ಟು ಹೆಚ್ಚುವರಿ ಸ್ಥಳವನ್ನು ಬಿಡುತ್ತದೆ. ಇದು
10000-ಸಾಲಿನ bodies batch ಅನ್ನು ಸುರಕ್ಷಿತಗೊಳಿಸುವುದಿಲ್ಲ. V8 heap ಖಾಲಿಯಾಗುವುದು ಕ್ರಮ ಕೈಗೊಳ್ಳಬಹುದಾದ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ: batch
size ಅನ್ನು ಕಡಿಮೆ ಮಾಡಿ ಅಥವಾ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` ಅನ್ನು ಹೆಚ್ಚಿಸಿ; cursor ಕೊನೆಯದಾಗಿ
acknowledge ಮಾಡಲಾದ batch ನಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ. ಐತಿಹಾಸಿಕ inline/disk body ಗಳು ಆಧುನಿಕ artifact cap ವ್ಯಾಪ್ತಿಗೆ ಬರುವುದಿಲ್ಲ.
ವಿಶೇಷವಾಗಿ memory ಮಿತಿಯಿರುವ container ಗಳಲ್ಲಿ, operator ಗಳು RSS ಗಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಸಾಮರ್ಥ್ಯ ಯೋಜಿಸಬೇಕು.

Child, ಪರಿಹರಿಸಲಾದ `DATA_DIR`, `NODE_ENV`, ಸ್ಪಷ್ಟವಾದ `TZ` (legacy filename
local-time resolution), ಇದ್ದಾಗ `ELECTRON_RUN_AS_NODE`, ಮತ್ತು ಕೆಳಗಿನ outbound input ಗಳನ್ನು ಮಾತ್ರ inherit ಮಾಡುತ್ತದೆ:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (ಮತ್ತು ಅವುಗಳ lowercase ರೂಪಗಳು),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
Global Undici dispatcher, ಸರ್ವರ್ನ ಶುದ್ಧ environment-proxy resolution ಮತ್ತು local-host
bypass ನಿಯಮಗಳನ್ನು, `NO_PROXY` ಸೇರಿದಂತೆ, ಹಂಚಿಕೊಳ್ಳುತ್ತದೆ; ಅದು `proxyFetch.ts` ಅಥವಾ ಅದರ DB/feature flag ಗಳನ್ನು import ಮಾಡುವುದಿಲ್ಲ.
ಮುಂದಕ್ಕೆ ಕಳುಹಿಸಲಾದ output ಮತ್ತು ದಾಖಲಿಸಲಾದ error ಗಳಿಂದ proxy credential ಗಳನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ. Destination credential ಗಳು
ಒಂದೇ start IPC message ನಲ್ಲಿ ಮಾತ್ರ ಸಾಗುತ್ತವೆ, argv ಅಥವಾ environment ನಲ್ಲಿ ಎಂದಿಗೂ ಅಲ್ಲ; output/error forwarding ಗೆ
prefix ಸೇರಿಸಿ sanitize ಮಾಡಲಾಗುತ್ತದೆ. ಪ್ರತಿ cron run ನಲ್ಲಿ Node ನ SQLite warning ಮರುಕಳಿಸುವುದನ್ನು ತಪ್ಪಿಸಲು
child exec argument ಗಳಲ್ಲಿ `ExperimentalWarning` ಅನ್ನು ಮಾತ್ರ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗುತ್ತದೆ; ಇತರ warning type ಗಳು ಗೋಚರವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.

ಗಮ್ಯಸ್ಥಾನ ಮಾಡ್ಯೂಲ್ಗಳು Next.js/ಸರ್ವರ್ಗೆ-ಮಾತ್ರ ಸೀಮಿತವಾದ ಅವಲಂಬನೆಗಳಿಲ್ಲದೆ ಆಮದು ಮಾಡಬಹುದಾಗಿರಬೇಕು. ಈಗಿರುವ
BigQuery ಅನುಷ್ಠಾನವು ಈಗಾಗಲೇ ಆ ಒಪ್ಪಂದವನ್ನು ಪೂರೈಸುತ್ತದೆ. ಪ್ರವೇಶ-ಟೋಕನ್ ಕ್ಯಾಶ್ಗಳು ಉಪ ಪ್ರಕ್ರಿಯೆಯ
ಚಾಲನೆಯವರೆಗೆ ಮಾತ್ರ ಇರುತ್ತವೆ, ಚಾಲನೆಗಳ ನಡುವೆ ಅಲ್ಲ. Node ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ಆಗಿದೆ (`package.json` engines), ಆದರೆ READMEಯ Bun
ಸ್ಥಾಪನಾ ವಿಭಾಗ ಮತ್ತು `Dockerfile.bun` ಸಹ `bun:sqlite` (`src/lib/db/core.ts` / ಅಡಾಪ್ಟರ್ಗಳು) ಬಳಸುವ
ಉತ್ಪಾದನಾ ಹೊಂದಾಣಿಕೆಯ ಮಾರ್ಗವನ್ನು ಒದಗಿಸುತ್ತವೆ. ಆದ್ದರಿಂದ Bun ಅಡಿಯಲ್ಲಿ, ರಫ್ತುಗಳು ಹಿಂದಿನ
ಪ್ರಕ್ರಿಯೆಯೊಳಗಿನ ಮಾರ್ಗವನ್ನೇ ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ ಮತ್ತು ಒಂದು-ಬಾರಿಯ ಎಚ್ಚರಿಕೆಯನ್ನು ನೀಡುತ್ತವೆ: ಉಪ ಪ್ರಕ್ರಿಯೆಯ ಹೀಪ್/ಕಾಲಮಿತಿ ಪ್ರತ್ಯೇಕಿಸುವಿಕೆ ಲಭ್ಯವಿಲ್ಲ.
ಈವೆಂಟ್-ಲೂಪ್ ಮತ್ತು OOM ಪ್ರತ್ಯೇಕಿಸುವಿಕೆಗಾಗಿ Node ಬಳಸಿ; ಇಲ್ಲಿ Bun ಅನ್ನು ಅಭಿವೃದ್ಧಿಗೆ-ಮಾತ್ರ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`includeBodies` ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಗಂಟೆಗೊಮ್ಮೆ ಪೇಲೋಡ್ಗಳ ಬ್ಯಾಕ್ಲಾಗ್ ಸಂಗ್ರಹಿಸುವುದಕ್ಕಿಂತ
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ ನಿಮಿಷ-ಮಟ್ಟದ ವೇಳಾಪಟ್ಟಿಗೆ ಆದ್ಯತೆ ನೀಡಿ.
ಬ್ಯಾಚ್ ಮತ್ತು ಸಾಲಿನ ಮಿತಿಗಳು ಇನ್ನೂ ಪ್ರತಿಯೊಂದು ಚಾಲನೆಯನ್ನೂ ನಿಯಂತ್ರಿಸುತ್ತವೆ. ಪ್ರತಿ ಚಾಲನೆಯಲ್ಲಿ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೂ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವ ವೆಚ್ಚ ಉಂಟಾಗುತ್ತದೆ;
ಇದು ಸಣ್ಣ ಪ್ರಾರಂಭಿಕ ವೆಚ್ಚವನ್ನು ಸರ್ವರ್ ಈವೆಂಟ್-ಲೂಪ್ ಪ್ರತ್ಯೇಕಿಸುವಿಕೆಗಾಗಿ ವಿನಿಮಯ ಮಾಡಿಕೊಳ್ಳುತ್ತದೆ, ಒಟ್ಟು CPU ಬಳಕೆಯನ್ನು ಕಡಿಮೆ ಮಾಡಲು ಅಲ್ಲ.

### ಪೇಲೋಡ್ಗಳು (ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳು)

ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ, ರಫ್ತು Logs **ಪಟ್ಟಿ** ತೋರಿಸುವ ಸಾರಾಂಶ ಕ್ಷೇತ್ರಗಳನ್ನು ಮಾತ್ರ ಒಳಗೊಂಡಿರುತ್ತದೆ.
**ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ರಫ್ತುಮಾಡಿ** (`includeBodies`) ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿದರೆ, ಪ್ರತಿಯೊಂದು ಕರೆಗೆ Logs **ವಿವರ**
ಫಲಕವು ತೋರಿಸುವ ಮಾಹಿತಿಯನ್ನೂ ಹೆಚ್ಚುವರಿಯಾಗಿ ಕಳುಹಿಸಲಾಗುತ್ತದೆ:

| ಕ್ಷೇತ್ರ                          | ಅದು ಒಳಗೊಂಡಿರುವುದು                                          |
| -------------------------------- | ---------------------------------------------------------- |
| `request_body` / `response_body` | ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪ್ರದರ್ಶಿಸುವ ರೀತಿಯಲ್ಲಿರುವ ಕರೆ ಪೇಲೋಡ್ಗಳು        |
| `pipeline_route_decision`        | ರೂಟರ್ ಆಯ್ಕೆಮಾಡಿದ ಗುರಿ ಮತ್ತು ಮಾದರಿ                          |
| `pipeline_client_request`        | ಕ್ಲೈಂಟ್ ಕಳುಹಿಸಿದಂತೆಯೇ ಇರುವ ಮೂಲ ವಿನಂತಿ                      |
| `pipeline_openai_request`        | ಆಂತರಿಕ OpenAI ಸ್ವರೂಪಕ್ಕೆ ಪರಿವರ್ತಿಸಿದ ನಂತರದ ರೂಪ             |
| `pipeline_provider_request`      | ಪೂರೈಕೆದಾರರ ಉಪಭಾಷೆಯಲ್ಲಿ, ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ನಿಜವಾಗಿ ಕಳುಹಿಸಿದ ರೂಪ |
| `pipeline_provider_response`     | ಮೂಲ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆ                                |
| `pipeline_client_response`       | ಕರೆ ಮಾಡಿದವರಿಗೆ ಹಿಂತಿರುಗಿಸಿದ ಮಾಹಿತಿ                         |
| `pipeline_error`                 | ವಿಫಲವಾದ ಕರೆಗೆ ಪೈಪ್ಲೈನ್-ಮಟ್ಟದ ದೋಷದ ವಿವರ                     |
| `bodies_truncated`               | ಮೇಲಿನ ಯಾವುದೇ ಕ್ಷೇತ್ರವು `maxBodyBytes` ತಲುಪಿದಾಗ ಸರಿ         |

ಇದು ಪ್ರಾಂಪ್ಟ್ ವಿಷಯವಾಗಿರುವುದರಿಂದ, ಇದು **ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ** ಮತ್ತು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತಿ-ಗಮ್ಯಸ್ಥಾನದ ಆಯ್ಕೆಯಾಗಿದೆ.
ಕಳುಹಿಸಲಾಗುವುದು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ತೋರಿಸುವುದನ್ನೇ, ಏಕೆಂದರೆ ರಫ್ತು ಮತ್ತು `getCallLogById` ಒಂದೇ ವಿವರ
ರೆಸಲ್ಯೂಶನ್ ಅನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ: ಪೇಲೋಡ್ಗಳನ್ನು
ಬರೆಯುವಾಗಲೇ ಅವುಗಳ PII ಅನ್ನು ಶುದ್ಧೀಕರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ರಹಸ್ಯಗಳನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ; ಜೊತೆಗೆ,
`noLog` API ಕೀಲಿಯಿಂದ ಮಾಡಿದ ಕರೆಯು ಯಾವುದೇ ಪೇಲೋಡ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ರಫ್ತುಮಾಡಲು ಏನೂ ಇರುವುದಿಲ್ಲ.

ಪೇಲೋಡ್ಗಳನ್ನು ಪ್ರತಿ ಸಾಲಿಗೆ ಫೈಲ್ಸಿಸ್ಟಮ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ನಿಂದ ಓದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದನ್ನು ಕೇಳಿದ ಗಮ್ಯಸ್ಥಾನಗಳಿಗೆ ಮಾತ್ರ
ಹೈಡ್ರೇಶನ್ ನಡೆಯುತ್ತದೆ. ಕಾಣೆಯಾದ ಅಥವಾ ಹಾಳಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್, ಬ್ಯಾಚ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸಿ ಕರ್ಸರ್ ಅನ್ನು
ಅಲ್ಲಿಯೇ ಸಿಲುಕಿಸುವ ಬದಲು, ಶೂನ್ಯ ಪೇಲೋಡ್ಗಳೊಂದಿಗೆ ಅದರ ಸಾರಾಂಶವನ್ನು ರಫ್ತುಮಾಡುತ್ತದೆ.

`maxBodyBytes` (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ 262144) ಪ್ರತಿಯೊಂದು ಕ್ಷೇತ್ರಕ್ಕೂ ಗರಿಷ್ಠ ಮಿತಿಯನ್ನು ವಿಧಿಸುತ್ತದೆ. ಉದ್ದವಾದ ಪೇಲೋಡ್ಗಳನ್ನು **ತೆಗೆದುಹಾಕುವ ಬದಲು
ಮೊಟಕುಗೊಳಿಸಲಾಗುತ್ತದೆ** — ಮೊಟಕುಗೊಳಿಸಿದ ಪ್ರಾಂಪ್ಟ್ ಇನ್ನೂ "ಏನು ಕೇಳಲಾಗಿತ್ತು" ಎಂಬುದಕ್ಕೆ ಉತ್ತರಿಸುತ್ತದೆ — ಮತ್ತು ಸಾಲನ್ನು
`bodies_truncated` ಮೂಲಕ ಗುರುತಿಸಲಾಗುತ್ತದೆ. ತುಂಡು-ತುಂಡಾಗಿ ಸ್ಟ್ರೀಮ್ ಮಾಡಿದ ಡೆಲ್ಟಾಗಳನ್ನು ರಫ್ತುಮಾಡಲಾಗುವುದಿಲ್ಲ; ಸಂಯೋಜಿತ ಪ್ರತಿಕ್ರಿಯೆ ಈಗಾಗಲೇ
`pipeline_provider_response` ಮತ್ತು `pipeline_client_response` ನಲ್ಲಿ ಇರುತ್ತದೆ.

## 3. REST API

ಎಲ್ಲಾ ರೂಟ್ಗಳು ನಿರ್ವಹಣಾ ದೃಢೀಕರಣವನ್ನು (`requireManagementAuth`) ಹೊಂದಿವೆ. ರಹಸ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ:
ಸಂಗ್ರಹಿಸಲಾದ ರಹಸ್ಯವು ಅಕ್ಷರಶಃ `__stored__` ಆಗಿ ಮರಳುತ್ತದೆ ಮತ್ತು ಅಪ್ಡೇಟ್ ಮಾಡುವಾಗ ಆ ಮೌಲ್ಯವನ್ನೇ ಹಿಂದಕ್ಕೆ ಕಳುಹಿಸಿದರೆ
ಸಂಗ್ರಹಿಸಲಾದ ರುಜುವಾತು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತದೆ.

ರಹಸ್ಯವನ್ನು ಘೋಷಿಸುವ ಪ್ರಕಾರದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ರಚಿಸಲು ಅಥವಾ ಅಪ್ಡೇಟ್ ಮಾಡಲು **`STORAGE_ENCRYPTION_KEY`
ಅಗತ್ಯವಿದೆ**. ಅದು ಇಲ್ಲದಿದ್ದರೆ `encrypt()` ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಇನ್ಪುಟ್ ಅನ್ನು ಹಾಗೆಯೇ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ರುಜುವಾತನ್ನು
SQLite ನಲ್ಲಿ ಸರಳ ಪಠ್ಯವಾಗಿ ಇರಿಸುವ ಬದಲು ಬರೆಯುವಿಕೆಯನ್ನು 400 ದೋಷದೊಂದಿಗೆ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ (Telegram ವೆಬ್ಹುಕ್
ಅನ್ವಯಿಸುವ ಅದೇ ರಕ್ಷಣೆ).

| ವಿಧಾನ    | ಪಥ                                       | ಉದ್ದೇಶ                                               |
| -------- | ---------------------------------------- | ---------------------------------------------------- |

| `GET`    | `/api/log-export/destinations/{id}`      | ಒಂದನ್ನು ಓದುವುದು                                      |
| `PUT`    | `/api/log-export/destinations/{id}`      | ಹೆಸರು / ಸಕ್ರಿಯತೆ / ಕಾನ್ಫಿಗ್ / ಬ್ಯಾಚಿಂಗ್ ಅಪ್ಡೇಟ್      |

## 4. BigQuery ಗಮ್ಯಸ್ಥಾನ

ಕಾನ್ಫಿಗ್ ಕೀಗಳು (`type: "bigquery"`):

| ಕೀ                   | ಟಿಪ್ಪಣಿಗಳು                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `projectId`          | ಡೇಟಾಸೆಟ್ ಅನ್ನು ಹೊಂದಿರುವ GCP ಪ್ರಾಜೆಕ್ಟ್                                                           |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                  |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                  |
| `location`           | ಡೇಟಾಸೆಟ್ ರಚಿಸಬೇಕಾದಾಗ ಮಾತ್ರ ಬಳಸಲಾಗುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `EU`)                                          |
| `serviceAccountJson` | ಸರ್ವಿಸ್-ಅಕೌಂಟ್ ಕೀ. ರಹಸ್ಯ: ಸಂಗ್ರಹಿತ ಸ್ಥಿತಿಯಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಆಗಿರುತ್ತದೆ, ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸುವುದಿಲ್ಲ |
| `autoCreate`         | ಮೊದಲ ಎಕ್ಸ್ಪೋರ್ಟ್ನಲ್ಲಿ ಡೇಟಾಸೆಟ್ ಮತ್ತು ಟೇಬಲ್ ರಚಿಸಿ (ಡೀಫಾಲ್ಟ್ `true`)                               |

ಸರ್ವಿಸ್ ಅಕೌಂಟ್ಗೆ ಗುರಿ ಟೇಬಲ್ನಲ್ಲಿ `bigquery.tables.updateData` ಅಗತ್ಯವಿದೆ, ಜೊತೆಗೆ
`autoCreate` ಸಕ್ರಿಯವಾಗಿರುವಾಗ `bigquery.datasets.create` / `bigquery.tables.create` ಅಗತ್ಯವಿವೆ.

ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಬ್ಯಾಚ್ ಒಂದು **ಕರ್ಸರ್** ಘಟಕವೇ ಹೊರತು HTTP ಘಟಕವಲ್ಲ: `send()` ಅದನ್ನು ಗರಿಷ್ಠ 500 ಸಾಲುಗಳ
insertAll ಕರೆಗಳಾಗಿ ವಿಭಜಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ದೊಡ್ಡ `batch_size` BigQuery ನ 10 MB ವಿನಂತಿ ಮಿತಿಯನ್ನು ಮೀರಿಸುವುದಿಲ್ಲ.
ತಾತ್ಕಾಲಿಕ ಸ್ಥಿತಿಗಳಲ್ಲಿ (408/429/500/502/503/504), ಅದೇ insertIds ಅನ್ನು ಮರುಬಳಸುತ್ತಾ ಎಕ್ಸ್ಪೊನೆನ್ಶಿಯಲ್
ಬ್ಯಾಕ್ಆಫ್ನೊಂದಿಗೆ ಗರಿಷ್ಠ ಮೂರು ಬಾರಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ; ದೃಢೀಕರಣ ಮತ್ತು ಸ್ಕೀಮಾ ವೈಫಲ್ಯಗಳು ರನ್ ಅನ್ನು
ವ್ಯರ್ಥಗೊಳಿಸುವ ಬದಲು ಮೊದಲ ಪ್ರಯತ್ನದಲ್ಲೇ ದೋಷವನ್ನು ಎಸೆಯುತ್ತವೆ.

ಕೆಲವೇ ಕ್ಷಣಗಳ ಹಿಂದೆ ರಚಿಸಲಾದ ಟೇಬಲ್ ಇನ್ನೂ ಸ್ಟ್ರೀಮಿಂಗ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಗೋಚರಿಸುವುದಿಲ್ಲ ಮತ್ತು ಅದು
ಕೆಲವು ಸೆಕೆಂಡುಗಳವರೆಗೆ 404 ಎಂದು ಉತ್ತರಿಸುತ್ತದೆ. ಆ 404 ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ, ಆದರೆ **ಈ ರನ್ ಟೇಬಲ್ ಅನ್ನು
ರಚಿಸಿದ್ದರೆ ಮಾತ್ರ** — ನಿಜವಾಗಿಯೂ ಕಾಣೆಯಾಗಿರುವ ಟೇಬಲ್ ತಕ್ಷಣವೇ ವಿಫಲವಾಗುತ್ತದೆ. ಇತ್ತೀಚೆಗೆ ಅಳಿಸಲಾದ ಹೆಸರಿನ
ಅಡಿಯಲ್ಲೇ ಟೇಬಲ್ ಅನ್ನು ಮರುರಚಿಸಿದರೆ, BigQuery ಹಲವು ನಿಮಿಷಗಳವರೆಗೆ ಸ್ಟ್ರೀಮಿಂಗ್ ಇನ್ಸರ್ಟ್ಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ
ಎಂಬುದನ್ನು ಗಮನಿಸಿ; ಇದು ಅಳಿಸಿ-ನಂತರ-ಮರುರಚಿಸುವಿಕೆಯ ಗುಣಲಕ್ಷಣವಾಗಿದೆ, ಆದ್ದರಿಂದ ಟೇಬಲ್ ಅನ್ನು ಕೈಬಿಟ್ಟು ಮತ್ತೆ
ಸೇರಿಸುವ ಬದಲು ಹೊಸ ಟೇಬಲ್ ಹೆಸರನ್ನು ಬಳಸುವುದು ಉತ್ತಮ.

**ಭಾಗಶಃ ವೈಫಲ್ಯವು ಖಾಲಿಯಲ್ಲದ `insertErrors[]` ಜೊತೆಗೆ HTTP 200 ಆಗಿ ಬರುತ್ತದೆ.** ಅದನ್ನು ವೈಫಲ್ಯವೆಂದು
ಪರಿಗಣಿಸಿ ದೋಷವನ್ನು ಎಸೆಯಲಾಗುತ್ತದೆ; ಇದರಿಂದ BigQuery ಎಂದಿಗೂ ಸ್ವೀಕರಿಸದ ಸಾಲುಗಳನ್ನು ಮೀರಿ ಕರ್ಸರ್ ಮುಂದುವರಿಯುವುದನ್ನು
ತಡೆಯಲಾಗುತ್ತದೆ; `tests/unit/log-export-bigquery.test.ts` ಈ ವರ್ತನೆಯನ್ನು ಸ್ಥಿರಪಡಿಸುತ್ತದೆ.

ಟ್ರಾನ್ಸ್ಪೋರ್ಟ್ ಸರಳ REST ಆಗಿದೆ — ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ RS256 ಅಸರ್ಷನ್ ಅನ್ನು
`https://oauth2.googleapis.com/token` ನಲ್ಲಿ ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗೆ ವಿನಿಮಯ ಮಾಡಲಾಗುತ್ತದೆ, ನಂತರ ಸಾಲುಗಳು
`tabledata.insertAll` ಗೆ ಹೋಗುತ್ತವೆ. ಯಾವುದೇ Google SDK ಅನ್ನು ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ. ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗಳನ್ನು
ಪ್ರತಿ (ಸರ್ವಿಸ್ ಅಕೌಂಟ್, ಸ್ಕೋಪ್) ಗೆ ಪ್ರಕ್ರಿಯೆಯೊಳಗೆ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ.

ರಚಿಸಲಾದ ಟೇಬಲ್ನಲ್ಲಿ Logs-ಟ್ಯಾಬ್ನ ಪ್ರತಿ ಫೀಲ್ಡ್ಗೆ ಒಂದೊಂದು ಕಾಲಮ್ ಜೊತೆಗೆ `exported_at` ಇರುತ್ತದೆ ಮತ್ತು
ಕಾಲ್ ಲಾಗ್ಗಳನ್ನು ವಾಸ್ತವವಾಗಿ ಹೇಗೆ ಕ್ವೆರಿ ಮಾಡಲಾಗುತ್ತದೆ ಎಂಬುದಕ್ಕೆ ಅನುಗುಣವಾಗಿ ಅದನ್ನು ವಿನ್ಯಾಸಗೊಳಿಸಲಾಗಿದೆ:

- **`timestamp` ಆಧಾರಿತ ದಿನ-ವಿಭಜನೆ**, ಆದ್ದರಿಂದ ದಿನಾಂಕದಿಂದ ಮಿತಿಗೊಳಿಸಲಾದ ಕ್ವೆರಿ ಆ ದಿನಗಳನ್ನು ಮಾತ್ರ ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತದೆ.
- **`api_key_name`, `provider`, `model`, `status` ಆಧಾರಿತ ಕ್ಲಸ್ಟರಿಂಗ್** (ಅದೇ ಕ್ರಮದಲ್ಲಿ), ಆದ್ದರಿಂದ
  ಅದನ್ನು ಯಾರು ಚಲಾಯಿಸಿದರು, ಅದು ಎಲ್ಲಿಗೆ ಹೋಯಿತು ಅಥವಾ ಅದು ವಿಫಲವಾಗಿದೆಯೇ ಎಂಬುದರ ಆಧಾರದ ಮೇಲೆ ಫಿಲ್ಟರ್ ಮಾಡುವುದರಿಂದ
  ಪ್ರತಿ ಪಾರ್ಟಿಷನ್ನೊಳಗಿನ ಬ್ಲಾಕ್ಗಳು ಕಡಿತಗೊಳ್ಳುತ್ತವೆ. BigQuery ಗರಿಷ್ಠ ನಾಲ್ಕು ಕ್ಲಸ್ಟರಿಂಗ್ ಕಾಲಮ್ಗಳನ್ನು
  ಅನುಮತಿಸುತ್ತದೆ ಮತ್ತು ಕ್ರಮವು ಮುಖ್ಯವಾಗಿದೆ: `api_key_name` ಮೇಲೆ ಮಾತ್ರ ಇರುವ ಫಿಲ್ಟರ್ ಬ್ಲಾಕ್ಗಳನ್ನು ಕಡಿತಗೊಳಿಸುತ್ತದೆ,
  ಆದರೆ `status` ಮೇಲೆ ಮಾತ್ರ ಇರುವ ಫಿಲ್ಟರ್ ಹಾಗೆ ಮಾಡುವುದಿಲ್ಲ.
- **`partitionExpirationDays` ಮೂಲಕ ಐಚ್ಛಿಕ ಪಾರ್ಟಿಷನ್ ಉಳಿಕೆ** (0 ಎಲ್ಲವನ್ನೂ ಉಳಿಸುತ್ತದೆ), ಟೇಬಲ್
  ರಚಿಸುವಾಗ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.

ಎರಡೂ ಸೆಟ್ಟಿಂಗ್ಗಳು ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಅನ್ವಯಿಸುತ್ತವೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್ ತನ್ನಲ್ಲಿರುವ ವಿನ್ಯಾಸವನ್ನೇ ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ
ಅವುಗಳನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳಲು ಬಯಸಿದರೆ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಹೊಸ ಟೇಬಲ್ ID ಕಡೆಗೆ ನಿರ್ದೇಶಿಸಿ.

`tests/unit/log-export-bigquery.test.ts` ಮ್ಯಾಪರ್ ಮತ್ತು ಟೇಬಲ್ ಸ್ಕೀಮಾ ಒಂದಕ್ಕೊಂದು
ಹೊಂದಿಕೊಂಡೇ ಇರುವುದನ್ನು ದೃಢಪಡಿಸುತ್ತದೆ, ಹೀಗಾಗಿ ಹೊಸ ಕಾಲ್-ಲಾಗ್ ಕಾಲಮ್ ರಫ್ತಾಗುವಾಗ ಸದ್ದಿಲ್ಲದೆ ಕೈಬಿಡಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಬ್ಯಾಚ್ಗಳನ್ನು ಸಾಲುಗಳ ಸಂಖ್ಯೆ ಮತ್ತು ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಬೈಟ್ಗಳು **ಎರಡರ** ಆಧಾರದಲ್ಲಿಯೂ ಚಂಕ್ಗಳಾಗಿ ವಿಭಜಿಸಲಾಗುತ್ತದೆ. ಪೇಲೋಡ್ಗಳನ್ನು ರಫ್ತು ಮಾಡುವಾಗ
ಸಾಲುಗಳ ಸಂಖ್ಯೆ ಮಾತ್ರ ಸಾಕಾಗುವುದಿಲ್ಲ: ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಹೊಂದಿರುವ 500 ಸಾಲುಗಳು ಹತ್ತಾರು ಮೆಗಾಬೈಟ್ಗಳಷ್ಟಾಗಬಹುದು ಮತ್ತು 10 MB ಮೀರಿದ ವಿನಂತಿಯನ್ನು insertAll
ತಿರಸ್ಕರಿಸುತ್ತದೆ. 500 ಸಾಲುಗಳು ಅಥವಾ 9 MB—ಇವುಗಳಲ್ಲಿ ಯಾವುದು ಮೊದಲು ತಲುಪುತ್ತದೆಯೋ ಆಗ ಚಂಕ್ಗಳನ್ನು ಮುಚ್ಚಲಾಗುತ್ತದೆ.

## 5. OTLP/HTTP ಟ್ರೇಸ್‌ಗಳ ಗಮ್ಯಸ್ಥಾನ

ಕಾನ್ಫಿಗರೇಶನ್ `type: "otlp-http"` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಇದು ಸಂಗ್ರಹಿತ ಕರೆ ಲಾಗ್‌ಗಳ ನಿಗದಿತ, ಕರ್ಸರ್-ಆಧಾರಿತ
ರಫ್ತು; ಇದು `open-sse/services/routing/otel.ts` ನಲ್ಲಿರುವ ಸಾಧ್ಯವಾದಷ್ಟು ಉತ್ತಮ ಪ್ರಯತ್ನದ ಲೈವ್ ರೂಟಿಂಗ್-ಈವೆಂಟ್ ಸಿಂಕ್ ಅಲ್ಲ.
ಇದು ಆ ಸಿಂಕ್‌ನ ಪರಿಸರ ಚರಗಳು, ಟೈಮರ್‌ಗಳು ಅಥವಾ ಬಫರ್‌ಗಳನ್ನು ಓದುವುದಿಲ್ಲ ಅಥವಾ ಬದಲಾಯಿಸುವುದಿಲ್ಲ.
ಎರಡನ್ನೂ ಸಕ್ರಿಯಗೊಳಿಸಿದರೆ ಎರಡು ಸ್ವತಂತ್ರ ಬಗೆಯ ಸ್ಪ್ಯಾನ್‌ಗಳು ಉತ್ಪತ್ತಿಯಾಗಬಹುದು;
ಈ ಕರೆ-ಲಾಗ್ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಗುರುತಿಸಲು `omniroute.log-export` ಇನ್‌ಸ್ಟ್ರುಮೆಂಟೇಶನ್ ವ್ಯಾಪ್ತಿಯನ್ನು ಬಳಸಿ.

| ಕೀ                       | ಡೀಫಾಲ್ಟ್ / ಉದ್ದೇಶ                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| `endpoint`               | ಪೂರ್ಣ HTTP(S) ಟ್ರೇಸ್‌ಗಳ URL ಅಗತ್ಯ; `/v1/traces` ಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ                  |
| `headers`                | ಐಚ್ಛಿಕ `Name: value` ಸಾಲುಗಳು ಅಥವಾ ಸ್ಟ್ರಿಂಗ್‌ಗಳ JSON ಆಬ್ಜೆಕ್ಟ್; ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ       |
| `requestHeaderAllowlist` | ಖಾಲಿ (ನಿಷ್ಕ್ರಿಯ); ಸ್ಪ್ಯಾನ್ ಗುಣಲಕ್ಷಣಗಳಾಗಿ ಸೆರೆಹಿಡಿಯಬೇಕಾದ ಕ್ಲೈಂಟ್ ಹೆಡರ್ ಹೆಸರುಗಳು/ಪೂರ್ವಪ್ರತ್ಯಯಗಳು |
| `serviceName`            | `omniroute`; ಸಂಪನ್ಮೂಲ `service.name`                                                           |
| `langfuseMapping`        | `false`; Langfuse ಜನರೇಶನ್/ಸೆಷನ್/ಬಳಕೆದಾರ ಗುಣಲಕ್ಷಣಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ                             |
| `identity`               | `pseudonymous`, `keyName`, ಅಥವಾ `none`                                                         |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                        |
| `timeoutMs`              | ಪ್ರತಿ HTTP ಪ್ರಯತ್ನಕ್ಕೆ `30000`                                                                 |
| `environment`            | ಹೊಂದಿಸಿಲ್ಲ; ಐಚ್ಛಿಕ `langfuse.environment`                                                      |

ಸಾಮಾನ್ಯ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಈ ಕ್ಷೇತ್ರಗಳನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ. `paths` ಒಂದು API ಅರೇ ಅಥವಾ ಹೊಸಸಾಲುಗಳು/ಅಲ್ಪವಿರಾಮಗಳಿಂದ
ಬೇರ್ಪಡಿಸಲಾದ ನಿಖರ ಪಥಗಳಿರುವ ಪಠ್ಯಪ್ರದೇಶವನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ. ಸ್ಪಷ್ಟವಾಗಿ ಅನುಮತಿಸದಿದ್ದರೆ ಎಂಬೆಡಿಂಗ್‌ಗಳು, ರೀರ್ಯಾಂಕ್ ಮತ್ತು ಇತರ ಪಥಗಳನ್ನು
ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ. ಬಿಟ್ಟುಬಿಟ್ಟ ಸಾಲುಗಳೂ ಕರ್ಸರ್ ಅನ್ನು ಮುಂದಕ್ಕೆ ಸಾಗಿಸುತ್ತವೆ; ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ರನ್ನರ್‌ನ `exported`/`exportedTotal` ಎಣಿಕೆಗಳು ಸ್ವೀಕರಿಸಿದ ಸ್ಪ್ಯಾನ್‌ಗಳ ಬದಲು, ಫಿಲ್ಟರ್ ಮಾಡಿದ ಸಾಲುಗಳನ್ನೂ ಒಳಗೊಂಡಂತೆ
ಪ್ರಕ್ರಿಯೆಗೊಳಿಸಿದ ಮೂಲ ಸಾಲುಗಳನ್ನು ಎಣಿಸುತ್ತವೆ. ಅದರ IPC/ಕರ್ಸರ್ ಒಪ್ಪಂದವನ್ನು ಬದಲಾಯಿಸದೆ,
ಚೈಲ್ಡ್‌ನಲ್ಲಿ ಫಿಲ್ಟರಿಂಗ್ ಮಾಡಲಾಗುತ್ತದೆ.

URL ಪರಿಶೀಲನೆಯು `src/shared/network/outboundUrlGuard.ts` ನಲ್ಲಿರುವ DB-ರಹಿತ
`parseAndValidateNonMetadataUrl` ಸಹಾಯಕವನ್ನು ಬಳಸುತ್ತದೆ: `block-metadata` ನೀತಿ. ಖಾಸಗಿ URLಗಳನ್ನು ಅನುಮತಿಸಿರುವ
ವೆಬ್‌ಹುಕ್ ಪರಿಶೀಲಕದಲ್ಲಿರುವಂತೆಯೇ ಷರತ್ತುರಹಿತ ಮೆಟಾಡೇಟಾ/ಪ್ರೋಟೋಕಾಲ್/ಅಂತರ್ಗತ-ರುಜುವಾತು ಪರಿಶೀಲನೆಗಳು ಇದರಲ್ಲಿವೆ,
ಆದರೆ ಜಾಗತಿಕ ಫೀಚರ್-ಫ್ಲ್ಯಾಗ್ ಓವರ್‌ರೈಡ್ ಇಲ್ಲದೆಯೇ localhost/LAN ಗುರಿಗಳನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
ಅನುಮತಿಸುತ್ತದೆ. ಇದು ಖಾಸಗಿ HTTP ಎಂಡ್‌ಪಾಯಿಂಟ್‌ಗಳು ಸೇರಿದಂತೆ ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ Langfuse, Phoenix, Tempo ಮತ್ತು Collector
ಎಂಡ್‌ಪಾಯಿಂಟ್‌ಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ. ಕ್ಲೌಡ್-ಮೆಟಾಡೇಟಾ ಹೋಸ್ಟ್‌ಗಳನ್ನು ಯಾವಾಗಲೂ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ.
ಮರುನಿರ್ದೇಶನಗಳನ್ನು ಅನುಸರಿಸಲಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಕಲೆಕ್ಟರ್ ರುಜುವಾತುಗಳನ್ನು ಬೇರೆ ಹೋಸ್ಟ್‌ಗೆ ಮರುನಿರ್ದೇಶಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಪದರೂಪ-ಆಧಾರಿತ URL ಗಾರ್ಡ್‌ನಂತೆಯೇ, ಇದು DNS ರೆಸಲ್ಯೂಶನ್ ಅನ್ನು ಸ್ಥಿರಗೊಳಿಸುವುದಿಲ್ಲ; ಆಪರೇಟರ್ ನಿಯಂತ್ರಣದಲ್ಲಿರುವ
ಹೋಸ್ಟ್‌ಗಳನ್ನು ಮಾತ್ರ ಕಾನ್ಫಿಗರ್ ಮಾಡಿ. ಎಂಡ್‌ಪಾಯಿಂಟ್ ವಿಶ್ವಾಸಾರ್ಹ ನೆಟ್‌ವರ್ಕ್‌ನಲ್ಲಿ ಇಲ್ಲದಿದ್ದಾಗಲೆಲ್ಲ HTTPS ಗೆ ಆದ್ಯತೆ ನೀಡಿ.

### ಪೇಲೋಡ್ ಮತ್ತು ವಿತರಣೆ

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) ಪ್ರತಿ ಅನುಮತಿಸಲಾದ
ಸಾಲಿಗೆ ಒಂದು CLIENT ಸ್ಪ್ಯಾನ್ ಅನ್ನು ಹೊತ್ತೊಯ್ಯುತ್ತದೆ; ಅದರ ನಿಖರ ವಿನಂತಿ ಪಥವೇ ಅದರ ಹೆಸರಾಗಿರುತ್ತದೆ. ಪಥದ ಆಧಾರದ ಹೆಸರಿಸುವಿಕೆಯು
ಸ್ಪ್ಯಾನ್ ಹೆಸರಿನಲ್ಲಿ ಮಾಡೆಲ್ ಅಥವಾ ಗುರುತಿನ ಡೇಟಾವನ್ನು ಸೇರಿಸದೆ Chat Completions, Responses ಮತ್ತು Messages ಅನ್ನು
ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ. ಸಂಪನ್ಮೂಲ ಗುಣಲಕ್ಷಣಗಳಲ್ಲಿ `service.name` ಮತ್ತು ಪ್ಯಾಕೇಜ್‌ನ `service.version` ಸೇರಿವೆ.

ಸಾಮಾನ್ಯ ಚಾಟ್ ಪ್ರಯತ್ನ ಲಾಗರ್ (`open-sse/handlers/chatCore/attemptLogging.ts`) ಪೂರ್ಣಗೊಂಡಾಗ
`duration = Date.now() - startTime` ಅನ್ನು ಬರೆಯುತ್ತದೆ ಮತ್ತು ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಒದಗಿಸುವುದಿಲ್ಲ;
`src/lib/usage/callLogs.ts` ನಲ್ಲಿರುವ `saveCallLogOperation` ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಡೀಫಾಲ್ಟ್ ಆಗಿ ಬರೆಯುವ
(ಪೂರ್ಣಗೊಳ್ಳುವ) ಸಮಯಕ್ಕೆ ಹೊಂದಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ರಫ್ತು ಅಂತ್ಯ = ಸಾಲಿನ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಮತ್ತು ಆರಂಭ = ಅಂತ್ಯ − ಅವಧಿ ಎಂದು ಹೊಂದಿಸುತ್ತದೆ
(ಮಿಲಿಸೆಕೆಂಡ್‌ಗಳನ್ನು ದಶಮಾಂಶ ನ್ಯಾನೊಸೆಕೆಂಡ್‌ಗಳಿಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ). ಕರೆ ಮಾಡುವವರು ಒದಗಿಸಿದ ಹಿಂದಿನ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳನ್ನೂ
ಅಂತ್ಯದ ಸಮಯವಾಗಿ ಉಳಿಸಲಾಗುತ್ತದೆ; ಪ್ರತಿ ಸಾಲಿಗೆ ಆರಂಭ/ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಯನ್ನು ಪ್ರತ್ಯೇಕಿಸುವ ಸೂಚಕವಿಲ್ಲ.
null ಅವಧಿಯು ಶೂನ್ಯವಾಗುತ್ತದೆ. ಅಮಾನ್ಯ/ಕಾಣೆಯಾದ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳು ಅನಿರ್ಧಾರಿತ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಸೃಷ್ಟಿಸುವ ಬದಲು
ಬ್ಯಾಚ್ ವಿಫಲಗೊಳ್ಳುವಂತೆ ಮಾಡುತ್ತವೆ. `ttftMs` null ಆಗಿರಬಹುದು ಮತ್ತು ಅದು `omniroute.ttft_ms` ಗೆ ಮ್ಯಾಪ್ ಆಗುತ್ತದೆ.

ಗುಣಲಕ್ಷಣಗಳಲ್ಲಿ `gen_ai.operation.name="chat"`, ಪೂರೈಕೆದಾರ, ವಿನಂತಿಸಿದ/ಪ್ರತಿಕ್ರಿಯೆಯ ಮಾಡೆಲ್,
ಇನ್‌ಪುಟ್/ಔಟ್‌ಪುಟ್ ಟೋಕನ್‌ಗಳು, ಐಚ್ಛಿಕ ಕ್ಯಾಶ್-ಓದು/ಕ್ಯಾಶ್-ರಚನೆ/ತಾರ್ಕಿಕ ಟೋಕನ್‌ಗಳು, HTTP ಸ್ಥಿತಿ,
ಕಾಂಬೊ, ಕ್ಯಾಶ್ ಮೂಲ, ಸೆಷನ್ ಟ್ಯಾಗ್ ಮತ್ತು ಸಹಸಂಬಂಧ ಐಡಿ ಸೇರಿವೆ. ಪೂರ್ಣಾಂಕ OTLP ಮೌಲ್ಯಗಳು ಮತ್ತು ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳು
ದಶಮಾಂಶ ಸ್ಟ್ರಿಂಗ್‌ಗಳಾಗಿರುತ್ತವೆ; ಸ್ಟ್ರಿಂಗ್‌ಗಳು, ಬೂಲಿಯನ್‌ಗಳು ಮತ್ತು ಭಿನ್ನರಾಶಿ ಸಂಖ್ಯೆಗಳು ಅವುಗಳ ಸ್ಥಳೀಯ OTLP ಮೌಲ್ಯ
ರೂಪಾಂತರಗಳನ್ನು ಬಳಸುತ್ತವೆ. ದೋಷ ಸ್ಪ್ಯಾನ್‌ಗಳು ERROR ಸ್ಥಿತಿ ಮತ್ತು ಶುದ್ಧೀಕರಿಸಿದ ಸ್ಥಿತಿ ಸಂದೇಶವನ್ನು ಹೊಂದಿರುತ್ತವೆ. ಪ್ರಮಾಣಿತ
ದಾಖಲೆಯಲ್ಲಿ ಅಪ್‌ಸ್ಟ್ರೀಮ್ ಹೋಸ್ಟ್ URL ಇಲ್ಲ, ಆದ್ದರಿಂದ ಕಲೆಕ್ಟರ್ ಅನ್ನು ಮಾಡೆಲ್ ಸರ್ವರ್ ಎಂದು ತಪ್ಪಾಗಿ
ಗುರುತಿಸುವ ಬದಲು `server.address` ಅನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ವೆಚ್ಚವನ್ನು ರಫ್ತು ಮಾಡಲಾಗುವುದಿಲ್ಲ.

`includeBodies=true` ಮಾತ್ರ ವಿಷಯವನ್ನು ಲೋಡ್ ಮಾಡುತ್ತದೆ. `langfuseMapping=false` ಇದ್ದಾಗ,
`gen_ai.input.messages` / `gen_ai.output.messages` ಮರುರೂಪಿಸಿದ semconv ಸಂದೇಶಗಳ ಅರೇ ಬದಲಾಗಿ,
OmniRoute ಸಂಗ್ರಹಿಸಿದಂತೆ ಶುದ್ಧೀಕರಿಸಿದ ವಿನಂತಿ/ಪ್ರತಿಕ್ರಿಯೆ ಬಾಡಿ JSON ಅನ್ನು ಹೊತ್ತೊಯ್ಯುತ್ತವೆ
(ಪಾರ್ಸ್ ಮಾಡಬಹುದಾದಾಗ ಪ್ರಮಾಣಿತ ರೂಪಕ್ಕೆ ತರಲಾಗುತ್ತದೆ). ಕಡಿತಗೊಳಿಸಿದ/JSON ಅಲ್ಲದ ಬಾಡಿಗಳು ಕಚ್ಚಾ ಪಠ್ಯವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ. `langfuseMapping=true` ಇದ್ದಾಗ,
ಬಾಡಿಗಳನ್ನು `langfuse.observation.input` / `langfuse.observation.output` ಆಗಿ ಮಾತ್ರ ಹೊರಹಾಕಲಾಗುತ್ತದೆ;
ಪ್ರತಿ ಬಾಡಿಯನ್ನು ಒಮ್ಮೆ ಮಾತ್ರ ಕಳುಹಿಸುವಂತೆ `gen_ai.*.messages` ಗುಣಲಕ್ಷಣಗಳನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ಎರಡೂ ಮೋಡ್‌ಗಳು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ವಿಷಯ-ಲೋಡಿಂಗ್ ಪಥದಿಂದ `maxBodyBytes` ಅನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯುತ್ತವೆ;
`omniroute.bodies_truncated=true` ಕಡಿತಗೊಳಿಸುವಿಕೆಯನ್ನು ಸೂಚಿಸುತ್ತದೆ.
ಈ ಗಮ್ಯಸ್ಥಾನವು ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಪೈಪ್‌ಲೈನ್ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್‌ಗಳು ಅಥವಾ ಶುದ್ಧೀಕರಿಸದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಓದುಗಳನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ;
ಐಚ್ಛಿಕ ವಿನಂತಿ-ಹೆಡರ್ ಸೆರೆಹಿಡಿಯುವಿಕೆಯು ಕೆಳಗೆ ವಿವರಿಸಿದ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲೋಡ್ ಮಾಡಿದ ಕ್ಲೈಂಟ್ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ಅನ್ನು ಬಳಸುತ್ತದೆ.
ಬಾಡಿಗಳನ್ನು ರಫ್ತು ಮಾಡುವಾಗ ಗಂಟೆಗೊಮ್ಮೆ ಬಾಕಿ ಕೆಲಸವನ್ನು ಸಂಗ್ರಹಿಸುವ ಬದಲು,
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ ನಿಮಿಷ-ಮಟ್ಟದ ಆವರ್ತನವನ್ನು ಬಳಸಿ.

### ಐಚ್ಛಿಕ ಕ್ಲೈಂಟ್ ವಿನಂತಿ ಹೆಡರ್‌ಗಳು

ಹೆಡರ್ ಸೆರೆಹಿಡಿಯುವಿಕೆಯು **ಡೀಫಾಲ್ಟ್ ಆಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ**. ಗಮ್ಯಸ್ಥಾನದ ಕಾನ್ಫಿಗರೇಶನ್‌ನಲ್ಲಿ `requestHeaderAllowlist` ಅನ್ನು ಹೊಂದಿಸಿ
ಮತ್ತು **ಪ್ರಾಂಪ್ಟ್‌ಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ರಫ್ತು ಮಾಡಿ** ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ (ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ `includeBodies: true`).
ಅನುಮತಿ ಪಟ್ಟಿಯು API ಅರೇ ಅಥವಾ ಹೊಸಸಾಲು/ಅಲ್ಪವಿರಾಮದಿಂದ ಬೇರ್ಪಡಿಸಿದ ಹೆಸರುಗಳಿರುವ ಪಠ್ಯಪ್ರದೇಶವನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ಒಂದು ಕೊನೆಯ `*` ಖಾಲಿಯಲ್ಲದ ಹೆಡರ್-ಹೆಸರಿನ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಆಯ್ಕೆಮಾಡುವ ಸಂದರ್ಭವನ್ನು ಹೊರತುಪಡಿಸಿ, ಹೆಸರುಗಳು ದೊಡ್ಡಕ್ಷರ-ಚಿಕ್ಕಕ್ಷರ ಭೇದವಿಲ್ಲದೆ ಮತ್ತು ನಿಖರವಾಗಿ ಹೊಂದಿಕೆಯಾಗುತ್ತವೆ.
ಕೇವಲ `*`, ಮಧ್ಯದಲ್ಲಿ ಬರುವ ವೈಲ್ಡ್‌ಕಾರ್ಡ್‌ಗಳು ಮತ್ತು ಅಮಾನ್ಯ HTTP ಹೆಡರ್ ಹೆಸರುಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.
ಗರಿಷ್ಠ 64 ಆಯ್ಕೆಕಾರಕಗಳಿರಬಹುದು; ಪ್ರತಿಯೊಂದರ ಹೆಸರು/ಪೂರ್ವಪ್ರತ್ಯಯವು ಗರಿಷ್ಠ 256 ASCII ಬೈಟ್‌ಗಳಾಗಿರಬಹುದು.
ಈ ಸೆಟ್ಟಿಂಗ್ `headers` ನಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿದೆ; `headers` ಎಕ್ಸ್‌ಪೋರ್ಟರ್ ಅನ್ನು ಕಲೆಕ್ಟರ್‌ಗೆ ದೃಢೀಕರಿಸುತ್ತದೆ.

ಕ್ಯಾಪ್ಚರ್ ಕೇವಲ `pipeline_client_request` ಅನ್ನು ಓದುತ್ತದೆ; ಇದನ್ನು ಉಳಿಸಿದ ವಿವರವಾದ ಪೈಪ್‌ಲೈನ್‌ನ
`clientRawRequest` ನಿಂದ (ಅಥವಾ ಹಳೆಯ `clientRequest` ನಿಂದ) ತುಂಬಲಾಗುತ್ತದೆ. ಇದು ಎಂದಿಗೂ ಪೂರೈಕೆದಾರರ ವಿನಂತಿ ಹೆಡರ್‌ಗಳನ್ನು ಪರ್ಯಾಯವಾಗಿ ಬಳಸುವುದಿಲ್ಲ.
ವಿನಂತಿಯನ್ನು ದಾಖಲಿಸಿದಾಗ ವಿವರವಾದ ಪೈಪ್‌ಲೈನ್ ಲಾಗಿಂಗ್ ಸಕ್ರಿಯವಾಗಿರಬೇಕು.
`includeBodies` ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದರೆ, ಅಥವಾ ಕ್ಲೈಂಟ್-ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ JSON ಇಲ್ಲದಿದ್ದರೆ, ಹಾಳಾಗಿದ್ದರೆ ಅಥವಾ ಮೊಟಕುಗೊಂಡಿದ್ದರೆ, ಯಾವುದೇ ಹೆಡರ್
ಗುಣಲಕ್ಷಣಗಳನ್ನು ಹೊರಹಾಕಲಾಗುವುದಿಲ್ಲ. `maxBodyBytes` ಹೆಚ್ಚಿಸುವುದರಿಂದ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ಮೊಟಕುಗೊಳ್ಳುವುದನ್ನು ತಪ್ಪಿಸಬಹುದು;
ಆದರೆ ಎಂದಿಗೂ ಉಳಿಸದ ವಿವರಗಳನ್ನು ಅದು ಮರುಸ್ಥಾಪಿಸಲಾರದು. 1 MiB ಗಿಂತ ದೊಡ್ಡದಾದ ಅಥವಾ
256 ಕ್ಕಿಂತ ಹೆಚ್ಚು ಹೆಡರ್ ನಮೂದುಗಳನ್ನು ಹೊಂದಿರುವ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ಅನ್ನು ಕಡೆಗಣಿಸಲಾಗುತ್ತದೆ. ಹೆಡರ್ ಕ್ಯಾಪ್ಚರ್ ಜೊತೆಗೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಪ್ರಾಂಪ್ಟ್/ಪ್ರತಿಕ್ರಿಯೆ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಸಕ್ರಿಯವಾಗಿಯೇ ಇರುತ್ತದೆ;
ಅನುಮತಿ ಪಟ್ಟಿಯು ಹೆಡರ್‌ಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತವಾದ ಹೈಡ್ರೇಶನ್ ಮೋಡ್ ಅನ್ನು ಒದಗಿಸುವುದಿಲ್ಲ.

ಆಯ್ಕೆಮಾಡಿದ ಮೌಲ್ಯಗಳು `http.request.header.<full lowercase header name>` OTLP ಸ್ಟ್ರಿಂಗ್ ಅರೇಗಳಾಗುತ್ತವೆ,
ಒಂದೇ ಸ್ಟ್ರಿಂಗ್ ಇದ್ದರೂ ಸಹ. ಉದಾಹರಣೆಗೆ, `X-OmniRoute-Meta-Team: example-team` ಎಂಬುದು
`http.request.header.x-omniroute-meta-team` ಆಗುತ್ತದೆ, ಜೊತೆಗೆ
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}` ಇರುತ್ತದೆ.
ಪೂರ್ಣ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ: ಇವು ಸಾಮಾನ್ಯ ಹೆಡರ್‌ಗಳಾಗಿವೆ; ಯಾವುದೇ ವ್ಯವಹಾರ-ಕ್ಷೇತ್ರ ಪಾರ್ಸಿಂಗ್ ಅಥವಾ
`omniroute.metadata.*` / Langfuse ಮೆಟಾಡೇಟಾ ಪರಿವರ್ತನೆ ಇರುವುದಿಲ್ಲ. `langfuseMapping` ಹೆಡರ್‌ಗಳ
ಅರ್ಥವ್ಯವಸ್ಥೆಯನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ. ಆಯ್ಕೆಮಾಡಿದ ಏಕ-ಮೌಲ್ಯದ `User-Agent` ಪ್ರಮಾಣಿತ ಸ್ಕೇಲರ್
`user_agent.original` ಅನ್ನೂ ಹೊಂದಿಸುತ್ತದೆ. ಒಂದೇ ಮೌಲ್ಯದೊಳಗಿನ ಅಲ್ಪವಿರಾಮಗಳ ಆಧಾರದಲ್ಲಿ ವಿಭಜಿಸಲಾಗುವುದಿಲ್ಲ. ದೊಡ್ಡಕ್ಷರ-ಚಿಕ್ಕಕ್ಷರ ರೂಪಾಂತರಗಳು ಉಳಿಸಿದ
ನಮೂದುಗಳ ಕ್ರಮದಲ್ಲಿ ವಿಲೀನಗೊಳ್ಳುತ್ತವೆ; ಯಾವುದೇ ಅಮಾನ್ಯ ರೂಪಾಂತರವಿದ್ದರೆ ಆ ಸಂಪೂರ್ಣ ಹೆಡರ್ ಅನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ಗುಣಲಕ್ಷಣಗಳನ್ನು ಚಿಕ್ಕಕ್ಷರದ ಹೆಸರಿನ ಕ್ರಮದಲ್ಲಿ ಜೋಡಿಸಲಾಗುತ್ತದೆ.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-ಕೀ ಹೆಡರ್‌ಗಳು, auth/token/secret/password/credential
ಗುರುತುಗಳನ್ನು ಹೊಂದಿರುವ ಹೆಸರುಗಳು ಮತ್ತು ಆಂತರಿಕ ಗೇಟ್‌ವೇ ಪ್ರವೇಶ ರುಜುವಾತುಗಳನ್ನು ಯಾವಾಗಲೂ
ಹೊರಗಿಡಲಾಗುತ್ತದೆ; ಆಯ್ಕೆಮಾಡಿದ್ದರೂ ಅಥವಾ ಸಂಗ್ರಹಣೆಯಲ್ಲಿ ಭಾಗಶಃ ಮರೆಮಾಚಿದ್ದರೂ ಸಹ. ತಿಳಿದಿರುವ ಪ್ರವೇಶ ರುಜುವಾತು ಮಾದರಿಗಳು
ಹಂಚಿಕೆಯ ಪ್ರವೇಶ ರುಜುವಾತು ಪತ್ತೆಕಾರಕವನ್ನು ಮರುಬಳಸುತ್ತವೆ; ಮರೆಮಾಚುವಿಕೆಯ ಗುರುತುಗಳನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ, ಸುರಕ್ಷಿತ ಮೌಲ್ಯಗಳೆಂದು ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ.
ಸ್ಟ್ರಿಂಗ್‌ಗಳು ಮತ್ತು ಖಾಲಿಯಲ್ಲದ ಸ್ಟ್ರಿಂಗ್ ಅರೇಗಳನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; ಸಂಖ್ಯೆಗಳು ಅಥವಾ ಆಬ್ಜೆಕ್ಟ್‌ಗಳನ್ನು ಪರಿವರ್ತಿಸಲಾಗುವುದಿಲ್ಲ.
ಅಮಾನ್ಯ ಹೆಸರುಗಳು, ಪ್ರೋಟೋಟೈಪ್ ಕೀಗಳು, ನಿಯಂತ್ರಣ ಅಕ್ಷರಗಳು (ಅಡ್ಡ ಟ್ಯಾಬ್ ಹೊರತುಪಡಿಸಿ) ಮತ್ತು ತಪ್ಪಾಗಿ ರೂಪುಗೊಂಡ Unicode ಅನ್ನು
ಬ್ಯಾಚ್ ವಿಫಲಗೊಳಿಸದೆ ಅಥವಾ ಅವುಗಳ ವಿಷಯವನ್ನು ದೋಷಗಳಲ್ಲಿ ಪ್ರತಿಬಿಂಬಿಸದೆ ಕಡೆಗಣಿಸಲಾಗುತ್ತದೆ.

ಪ್ರತಿ ಸ್ಪ್ಯಾನ್ ಗರಿಷ್ಠ 32 ಹೆಡರ್‌ಗಳನ್ನು, ಪ್ರತಿ ಹೆಡರ್‌ಗೆ 16 ಮೌಲ್ಯಗಳನ್ನು, ಪ್ರತಿ ಮೌಲ್ಯಕ್ಕೆ 4096 UTF-8 ಬೈಟ್‌ಗಳನ್ನು,
ಮತ್ತು ಕ್ಯಾಪ್ಚರ್ ಮಾಡಿದ ಹೆಡರ್ ಹೆಸರುಗಳು ಹಾಗೂ ಮೌಲ್ಯಗಳಾದ್ಯಂತ ಒಟ್ಟು 16384 UTF-8 ಬೈಟ್‌ಗಳನ್ನು ಕ್ಯಾಪ್ಚರ್ ಮಾಡುತ್ತದೆ. ಮಿತಿಮೀರಿದ/ಅಮಾನ್ಯ ಹೆಡರ್‌ಗಳನ್ನು
ಸಂಪೂರ್ಣವಾಗಿ ಕೈಬಿಡಲಾಗುತ್ತದೆ, ಮೊಟಕುಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ. ಆಯ್ಕೆಯು ನಿರ್ವಾಹಕರ ಗೌಪ್ಯತಾ ನಿರ್ಧಾರವಾಗಿದೆ: ಸುರಕ್ಷಿತವಾಗಿ ಕಾಣುವ ಹೆಸರುಗಳೂ
ವೈಯಕ್ತಿಕ ಡೇಟಾವನ್ನು ಹೊಂದಿರಬಹುದು, ಮತ್ತು ಈ ಮಿತಿಗಳು/ಪತ್ತೆಕಾರಕಗಳು ಸಾಮಾನ್ಯ PII ಶುದ್ಧೀಕರಣ ಸಾಧನವಲ್ಲ.

### ವಿತರಣೆಯ ಮಿತಿಗಳು

ವಿನಂತಿಗಳನ್ನು 500 ಸ್ಪ್ಯಾನ್‌ಗಳು ಮತ್ತು ಎನ್‌ವೆಲಪ್ ಸೇರಿದಂತೆ 4 MiB UTF-8 JSON ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ.
ಕರ್ಸರ್ ಬ್ಯಾಚ್‌ನ ಮೊದಲ ವಿನಂತಿಗೂ ಮೊದಲು ಅನುಮತಿಸಲಾದ ಪ್ರತಿ ಸ್ಪ್ಯಾನ್‌ನ ಗಾತ್ರವನ್ನು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಪ್ರತ್ಯೇಕ
ಸ್ಪ್ಯಾನ್ ಮಿತಿಗಿಂತ ದೊಡ್ಡದಾಗಿದ್ದರೆ, ಆ ಬ್ಯಾಚ್‌ನ ಯಾವುದೇ ಭಾಗವನ್ನು ಕಳುಹಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು
`maxBodyBytes` ಕಡಿಮೆ ಮಾಡುವ ಮಾರ್ಗದರ್ಶನದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; ಅದನ್ನು ಮೌನವಾಗಿ ಕೈಬಿಡಲಾಗುವುದಿಲ್ಲ. ಪೂರ್ವಪರಿಶೀಲನೆಯು ದಾಖಲೆ ಉಲ್ಲೇಖಗಳು ಮತ್ತು
ಬೈಟ್ ಎಣಿಕೆಗಳನ್ನು ಮಾತ್ರ ಉಳಿಸಿಕೊಂಡು, ಪ್ರತಿ ತಾತ್ಕಾಲಿಕ ಸ್ಪ್ಯಾನ್/JSON ಅನ್ನು ತ್ಯಜಿಸುತ್ತದೆ; ಬ್ಯಾಚ್‌ನ ಎರಡನೇ ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಪ್ರತಿಯನ್ನು
ಇಟ್ಟುಕೊಳ್ಳುವ ಬದಲು, ಸೀಮಿತ ಗಾತ್ರದ ಚಂಕ್‌ಗಳಿಗಾಗಿ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಮರುನಿರ್ಮಿಸಲಾಗುತ್ತದೆ. HTTP 408/429/5xx, ನೆಟ್‌ವರ್ಕ್ ವೈಫಲ್ಯಗಳು ಮತ್ತು ಸಮಯಮೀರಿಕೆಗಳಿಗೆ ಗರಿಷ್ಠ
ಮೂರು ಪ್ರಯತ್ನಗಳನ್ನು ಮಾಡಲಾಗುತ್ತದೆ, 250/500 ms ಘಾತೀಯ ಹಿಂಜರಿಕೆ ವಿಳಂಬದೊಂದಿಗೆ. `Retry-After` ಸೆಕೆಂಡುಗಳು ಅಥವಾ HTTP ದಿನಾಂಕಗಳು
ವಿಳಂಬವನ್ನು 5 ಸೆಕೆಂಡುಗಳವರೆಗೆ ವಿಸ್ತರಿಸಬಹುದು. ಇತರ ಸ್ಥಿತಿಗಳು ತಕ್ಷಣ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ. OTLP 2xx ಭಾಗಶಃ ತಿರಸ್ಕಾರವೂ ಕಳೆದುಹೋದ ಸ್ಪ್ಯಾನ್ ಅನ್ನು
ಸ್ವೀಕರಿಸಲಾಗಿದೆ ಎಂದು ದೃಢೀಕರಿಸುವ ಬದಲು ದೋಷವನ್ನು ಎಸೆಯುತ್ತದೆ; ಖಾಲಿ ಅಥವಾ ಮಾನ್ಯ JSON ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣಗಳನ್ನು ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ,
ಪ್ರತಿಕ್ರಿಯೆ ಓದುವಿಕೆಗೆ 64 KiB ಮಿತಿಯೊಂದಿಗೆ.

ದೋಷಗಳು ಎಕ್ಸ್‌ಪೋರ್ಟರ್‌ಗೆ ಸೇರಿದ ಸಂಗತಿಗಳನ್ನು ಮಾತ್ರ ಒಳಗೊಂಡಿರುತ್ತವೆ: HTTP ಸ್ಥಿತಿ, ಮರುಪ್ರಯತ್ನ ವರ್ಗ, ಪ್ರಯತ್ನಗಳು ಮತ್ತು ಕಳುಹಿಸಿದ ಸ್ಪ್ಯಾನ್
ಎಣಿಕೆಗಳು, ಅಥವಾ ನಿಗದಿತ ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣ/ನೆಟ್‌ವರ್ಕ್ ವೈಫಲ್ಯದ ಪಠ್ಯ. ಕಲೆಕ್ಟರ್ ಪ್ರತಿಕ್ರಿಯೆಯ ಬಾಡಿಗಳು,
ಭಾಗಶಃ ಯಶಸ್ಸಿನ ಎಣಿಕೆಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಹೆಡರ್‌ಗಳನ್ನು ದೋಷಗಳು, ಲಾಗ್‌ಗಳು ಅಥವಾ
ಡ್ಯಾಶ್‌ಬೋರ್ಡ್‌ಗೆ ಎಂದಿಗೂ ನಕಲಿಸಲಾಗುವುದಿಲ್ಲ. ವಿಫಲವಾದ ಅಥವಾ ಭಾಗಶಃ ಸ್ವೀಕರಿಸಲಾದ ಬ್ಯಾಚ್‌ಗೆ ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣ ನೀಡಲಾಗುವುದಿಲ್ಲ: ಗಮ್ಯಸ್ಥಾನವು
ಆ ಸ್ಥಿತಿಯೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತಿದೆ ಎಂದು ತೋರಿಸುತ್ತದೆ, ಕರ್ಸರ್ ಕೊನೆಯದಾಗಿ ದೃಢೀಕರಿಸಲಾದ ಬ್ಯಾಚ್‌ನಲ್ಲೇ ಉಳಿಯುತ್ತದೆ, ಮತ್ತು ಮುಂದಿನ ಚಾಲನೆಯು
ಅದೇ ಸಾಲುಗಳನ್ನು ಮತ್ತೆ ಕಳುಹಿಸುತ್ತದೆ. ಕಲೆಕ್ಟರ್ ಅಥವಾ ಸಂರಚನೆಯನ್ನು ಸರಿಪಡಿಸುವವರೆಗೆ ಶಾಶ್ವತ ಸ್ಥಿತಿಗಳು ವಿಫಲಗೊಳ್ಳುತ್ತಲೇ ಇರುತ್ತವೆ.
ಪ್ರತಿಕ್ರಿಯೆ ವಿವರಗಳಿಗಾಗಿ ಕಲೆಕ್ಟರ್‌ನ ಸ್ವಂತ ಲಾಗ್‌ಗಳನ್ನು ಬಳಸಿ. ಕಾಲ್-ಲಾಗ್ ದೋಷ ಸಾರಾಂಶಗಳು
ತಮ್ಮ ಪ್ರತ್ಯೇಕ ಮರೆಮಾಚುವಿಕೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.
`prepare()` ಯಾವುದನ್ನೂ ಸಿದ್ಧಪಡಿಸುವುದಿಲ್ಲ; ಪರೀಕ್ಷೆಯು ನಿಖರವಾಗಿ `{"resourceSpans":[]}` ಅನ್ನು ಪೋಸ್ಟ್ ಮಾಡಿ,
ಕಾಲ್-ಲಾಗ್ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಬರೆಯದೆ HTTP ಸ್ಥಿತಿಯನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

ಟ್ರೇಸ್ ಐಡಿಗಳು ಮತ್ತು ಸ್ಪ್ಯಾನ್ ಐಡಿಗಳು ಕ್ರಮವಾಗಿ
`"omniroute.trace\0" + callLogId` ಮತ್ತು `"omniroute.span\0" + callLogId` ಮೇಲಿನ SHA-256 ನ ಮೊದಲ 32/16 ಹೆಕ್ಸ್ ಅಂಕೆಗಳಾಗಿವೆ. ಮರುಕಳುಹಿಸುವಿಕೆಗಳು
ಒಂದೇ ರೀತಿಯ ಐಡಿಗಳನ್ನು ಹೊಂದಿರುತ್ತವೆ. ಇದು ನಕಲು ನಿವಾರಣೆಯ ಖಾತರಿಯಲ್ಲ: Langfuse
v4 ಇಂಜೆಶನ್ ಸೇರಿದಂತೆ ಕೆಲವು ಬ್ಯಾಕ್‌ಎಂಡ್‌ಗಳು ಒಂದೇ ಐಡಿಯ ಸ್ಪ್ಯಾನ್‌ಗಳ ನಕಲುಗಳನ್ನು ನಿವಾರಿಸುವುದಿಲ್ಲ. ಕ್ರ್ಯಾಶ್ ಅಥವಾ ಭಾಗಶಃ ಚಂಕ್ ವೈಫಲ್ಯವು
ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣ ಪಡೆಯದ ಒಂದೇ ಕರ್ಸರ್ ಬ್ಯಾಚ್ ಅನ್ನು ಗರಿಷ್ಠವಾಗಿ ಮರುಕಳುಹಿಸಬಹುದು; ಆ ಸಂಪೂರ್ಣ ಬ್ಯಾಚ್ ನಕಲಾಗಬಹುದು,
ಅದರ ಕೊನೆಯ HTTP ಚಂಕ್ ಮಾತ್ರವಲ್ಲ. ಈ ಹೊಂದಾಣಿಕೆಯನ್ನು ಮನಸ್ಸಿನಲ್ಲಿಟ್ಟುಕೊಂಡು ಕರ್ಸರ್ ಬ್ಯಾಚ್ ಗಾತ್ರವನ್ನು ಆಯ್ಕೆಮಾಡಿ.

### Langfuse ಉದಾಹರಣೆ

ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ Langfuse ಇನ್‌ಸ್ಟನ್ಸ್‌ಗಾಗಿ ಈ ಕ್ಷೇತ್ರಗಳನ್ನು ಸಂರಚಿಸಿ:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

ನಿಖರವಾದ `public-key:secret-key` ಸ್ಟ್ರಿಂಗ್‌ನ Base64 ರೂಪವಾಗಿ Authorization ಮೌಲ್ಯವನ್ನು ಸ್ಥಳೀಯವಾಗಿ ರಚಿಸಿ
(ಉದಾಹರಣೆಗೆ `Buffer.from(publicKey + ":" + secretKey).toString("base64")` ಬಳಸಿ).
ನಿಜವಾದ ಪ್ರವೇಶ ರುಜುವಾತುಗಳನ್ನು ಲಾಗ್‌ಗಳು, ಸ್ಕ್ರೀನ್‌ಶಾಟ್‌ಗಳು ಅಥವಾ ಇಶ್ಯೂಗಳಲ್ಲಿ ಅಂಟಿಸಬೇಡಿ. ಮ್ಯಾಪಿಂಗ್ ಸ್ವಯಂಚಾಲಿತವಾಗಿ
`x-langfuse-ingestion-version: 4` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ; Authorization ಅನ್ನು ಇನ್ನೂ `headers` ನಲ್ಲಿ ಒದಗಿಸಲಾಗುತ್ತದೆ.
ಹೆಡರ್‌ಗಳು ಮತ್ತು ರಚಿಸಲಾದ ಗುರುತಿನ ಸಾಲ್ಟ್ ಎರಡೂ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ರಹಸ್ಯ-ಕ್ಷೇತ್ರ
ಕಾರ್ಯವಿಧಾನ ಮತ್ತು API ಪ್ಲೇಸ್‌ಹೋಲ್ಡರ್‌ಗಳನ್ನು ಬಳಸುತ್ತವೆ; `STORAGE_ENCRYPTION_KEY` ಅಗತ್ಯವಾಗಿದೆ.

ಮ್ಯಾಪಿಂಗ್‌ನಲ್ಲಿ ಜನರೇಷನ್ ಪ್ರಕಾರ/ಮಾದರಿ, JSON ಬಳಕೆಯ ವಿವರಗಳು (ಇನ್‌ಪುಟ್/ಔಟ್‌ಪುಟ್/ಒಟ್ಟು ಮತ್ತು ಲಭ್ಯವಿರುವ
ಕ್ಯಾಶ್ ಕೀಗಳು), JSON ಇನ್‌ಪುಟ್/ಔಟ್‌ಪುಟ್ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್‌ಗಳು, ERROR/DEFAULT ಮಟ್ಟ, ಶುದ್ಧೀಕರಿಸಿದ ಸ್ಥಿತಿ ಸಂದೇಶ,
ಟ್ರೇಸ್ ಹೆಸರು, ಸೆಷನ್ ಐಡಿ, ಐಚ್ಛಿಕ ಪರಿಸರ ಮತ್ತು ಪ್ರೊವೈಡರ್, ವಿನಂತಿಸಿದ ಮಾದರಿ, ಪಾಥ್, ಕಾಂಬೊ, ಕ್ಯಾಶ್
ಮೂಲ ಮತ್ತು ಸ್ಥಿತಿಗಾಗಿ ಫಿಲ್ಟರ್ ಮಾಡಬಹುದಾದ
`langfuse.observation.metadata.<key>` ಸೇರಿಸಲಾಗುತ್ತದೆ. TTFT ತಿಳಿದಿದ್ದು, ಅದು ಅವಧಿಯೊಳಗೆ ಇದ್ದಾಗ ಮಾತ್ರ
`langfuse.observation.completion_start_time` ಅನ್ನು ಪ್ರಾರಂಭ + TTFT ಸಮಯಕ್ಕೆ ISO 8601 ಸ್ವರೂಪದಲ್ಲಿ ಹೊಂದಿಸಲಾಗುತ್ತದೆ. ಯಾವುದೇ ವೆಚ್ಚದ ಗುಣಲಕ್ಷಣಗಳನ್ನು ಕಳುಹಿಸಲಾಗುವುದಿಲ್ಲ.

ಗುರುತಿನ ವಿಧಾನಗಳು `langfuse.user.id` ಗೆ ಅನ್ವಯಿಸುತ್ತವೆ:

- `pseudonymous` (ಡೀಫಾಲ್ಟ್): ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಯಾದೃಚ್ಛಿಕವಾದ
  32-ಬೈಟ್ ಸಾಲ್ಟ್ ಬಳಸಿ API ಕೀಯ ಆಂತರಿಕ ಐಡಿಯ HMAC-SHA256. ಸಾಲ್ಟ್ ಇಲ್ಲದಿದ್ದರೆ ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಅದನ್ನು ಉತ್ಪಾದಿಸಿ,
  `identitySalt` ಆಗಿ ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ; ಅದನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು ಸಂಪಾದನೆಗಳ ಸಮಯದಲ್ಲಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. ಮೂಲ ಕೀ ಐಡಿಗಳನ್ನು ಎಂದಿಗೂ
  ಸ್ಪ್ಯಾನ್ ಗುಣಲಕ್ಷಣಗಳಲ್ಲಿ ಇರಿಸಲಾಗುವುದಿಲ್ಲ. ಗಮ್ಯಸ್ಥಾನದ ಸಾಲ್ಟ್ ಅನ್ನು ಮರುರಚಿಸುವುದು/ರೊಟೇಟ್ ಮಾಡುವುದು ಗುರುತುಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
- `keyName`: ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ API ಕೀ ಹೆಸರು; ಇದು ಆ ಆಪರೇಟರ್ ಲೇಬಲ್ ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.
- `none`: ಬಳಕೆದಾರ ಐಡಿ ಇಲ್ಲ. ಸೆಷನ್ ಟ್ಯಾಗ್‌ಗಳು ಇದ್ದಾಗ ಅವುಗಳನ್ನು ಇನ್ನೂ ರಫ್ತು ಮಾಡಲಾಗುತ್ತದೆ; ಈ ವಿಧಾನಗಳು
  ಯಾವುದೇ ಪ್ರಾಂಪ್ಟ್ ವಿಷಯವನ್ನು ಅಥವಾ ಆಪರೇಟರ್ ಒದಗಿಸಿದ ಸೆಷನ್/ಸಹಸಂಬಂಧ ಲೇಬಲ್‌ಗಳನ್ನು ಅನಾಮಧೇಯಗೊಳಿಸುವುದಿಲ್ಲ.

### ಬ್ಯಾಕ್‌ಫಿಲ್ ಇಲ್ಲದೆ ಪ್ರಾರಂಭಿಸುವುದು

ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಮಾತ್ರ, **ಪ್ರಸ್ತುತ ಸ್ಥಾನದಿಂದ ಪ್ರಾರಂಭಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲಾಗ್‌ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಿ)** ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ ಅಥವಾ
ರಚನೆಯ API ಪೇಲೋಡ್‌ನ ಮೇಲಿನ ಹಂತದಲ್ಲಿ `startFromCurrentPosition: true` ಅನ್ನು ನೀಡಿ. ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕರ್ಸರ್
ಸಹಾಯಕಗಳನ್ನು ಬಳಸಿ, ಯಾವುದೇ ಮೈಗ್ರೇಷನ್ ಇಲ್ಲದೆ, `cursor_row_id` ಅನ್ನು ಪ್ರಸ್ತುತ ಉಳಿಸಿಕೊಂಡಿರುವ ಕಾಲ್-ಲಾಗ್‌ನ ಗರಿಷ್ಠ rowid ಗೆ
ಆರಂಭಿಸುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ false ಆಗಿರುತ್ತದೆ (ಕರ್ಸರ್ 0 ಮತ್ತು ಉಳಿಸಿಕೊಂಡಿರುವ ಇತಿಹಾಸದ ಬ್ಯಾಕ್‌ಫಿಲ್).
ಇದು ನವೀಕರಣದ ಸಮಯದಲ್ಲಿ ಕರ್ಸರ್ ಮರುಹೊಂದಿಸುವ ಸೆಟ್ಟಿಂಗ್ ಅಲ್ಲ.

ಹಂಚಿಕೆಯ `ttftMs` ಸೇರ್ಪಡೆಯು BigQuery ಮ್ಯಾಪರ್
ಮತ್ತು ಹೊಸ-ಟೇಬಲ್ ಸ್ಕೀಮಾಗೆ nullable `ttft_ms` ಕಾಲಮ್ ಅನ್ನೂ ಸೇರಿಸುತ್ತದೆ: ಅದರ ಸ್ಕೀಮಾ ಪರೀಕ್ಷೆಯು ಪ್ರತಿ ಕ್ಯಾನಾನಿಕಲ್ ರೆಕಾರ್ಡ್ ಫೀಲ್ಡ್‌ಗೆ
ಒಂದು ಕಾಲಮ್ ಇರಬೇಕೆಂದು ನಿರೀಕ್ಷಿಸುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್‌ಗಳು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ರಫ್ತು ಮಾಡುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ: `prepare()` ಟೇಬಲ್ ಸ್ಕೀಮಾವನ್ನು ಓದುತ್ತದೆ ಮತ್ತು
ಆ ಕಾಲಮ್ ಇಲ್ಲದಿದ್ದಾಗ `ttft_ms` ಅನ್ನು ಮಾತ್ರ ಹೊರಗಿಡುತ್ತದೆ. ಮುಂದಿನ ಚಾಲನೆಯಲ್ಲಿ TTFT ಪಡೆಯಲು nullable INT64 ಕಾಲಮ್ ಅನ್ನು ಸೇರಿಸಿ,
ಅಥವಾ ಹೊಸ ಟೇಬಲ್ ಬಳಸಿ. ಯಾವುದೇ PATCH, ಸ್ವಯಂಚಾಲಿತ ಸ್ಕೀಮಾ ಬದಲಾವಣೆ ಅಥವಾ ಹೆಚ್ಚುವರಿ
ಅನುಮತಿಗಳು ಅಗತ್ಯವಿಲ್ಲ; ಇತರ ಎಲ್ಲಾ ಸಾಲಿನ ಫೀಲ್ಡ್‌ಗಳು ಕಟ್ಟುನಿಟ್ಟಾದ ಸ್ಕೀಮಾ ಪರಿಶೀಲನೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

## 6. ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸುವುದು

1. `LogExportDestinationType` ಅನ್ನು export ಮಾಡುವ `src/lib/logExport/destinations/<name>.ts` ಅನ್ನು ರಚಿಸಿ:
   UI ಗಾಗಿ Zod `configSchema`, `fields` ವಿವರಣಾ array, `secretFields`, ಮತ್ತು
   `test()` / `prepare()` / `send(records)` ಅನ್ನು ಹಿಂದಿರುಗಿಸುವ `createClient(config)`.
2. ಅದನ್ನು `src/lib/logExport/registry.ts` ನಲ್ಲಿರುವ `DESTINATIONS` array ಗೆ ಸೇರಿಸಿ.
3. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ.

ಬದಲಾವಣೆ ಇಷ್ಟೇ: persistence, cron job, REST layer, secret encryption ಮತ್ತು
dashboard form ಎಲ್ಲವೂ registry ಅನ್ನು ಓದುತ್ತವೆ.

ಹೊಸ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಎರಡು ನಿಯಮಗಳು:

- ಭಾಗಶಃ ವೈಫಲ್ಯ ಸಂಭವಿಸಿದಾಗ `send()` **throw ಮಾಡಲೇಬೇಕು**. resolve ಆಗುವುದು ಎಂದರೆ "ಗಮ್ಯಸ್ಥಾನವು ಈ rows ಅನ್ನು ಹೊಂದಿದೆ"
  ಎಂದರ್ಥ, ಮತ್ತು cursor ಅವುಗಳನ್ನು ಶಾಶ್ವತವಾಗಿ ದಾಟಿ ಮುಂದೆ ಸಾಗುತ್ತದೆ.
- ಬಳಕೆದಾರರು ಒದಗಿಸಿದ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವ ಗಮ್ಯಸ್ಥಾನವು fetch ಮಾಡುವ ಮೊದಲು,
  webhooks ಮಾಡುವಂತೆಯೇ, `parseAndValidateWebhookUrl`
  (`src/shared/network/outboundUrlGuardPolicy.ts`) ಮೂಲಕ ಅದನ್ನು validate ಮಾಡಬೇಕು. BigQuery ಗೆ ಇದರ ಅಗತ್ಯವಿಲ್ಲ:
  ಅದರ hosts ಸ್ಥಿರಾಂಕಗಳಾಗಿವೆ.

## 7. ಇದನ್ನು ಕಾರ್ಯಾಚರಿಸುವುದು

- **Dashboard**: Integrations → Log export. ಒಂದು ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸಿ, rows ಅನ್ನು ಬರೆಯದೆಯೇ credentials ಅನ್ನು
  ಪರಿಶೀಲಿಸಲು **Test** ಅನ್ನು ಚಲಾಯಿಸಿ, ನಂತರ ಅದನ್ನು enable ಮಾಡಿ.
- **Backlog**: ಪ್ರತಿಯೊಂದು ಗಮ್ಯಸ್ಥಾನದ card ಬಾಕಿ ಇರುವ rows ಮತ್ತು cursor ಅನ್ನು ತೋರಿಸುತ್ತದೆ; `GET
/api/log-export/status` ಅದೇ ಅಂಕಿಅಂಶಗಳ ಜೊತೆಗೆ ಕೊನೆಯ 20 job runs ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
- **ಒಂದು ಗಮ್ಯಸ್ಥಾನದ ವೈಫಲ್ಯವು ಇತರವುಗಳನ್ನು ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ** — run summary ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ
  status ಅನ್ನು `last_status` / `last_error` ನಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು job run history ಒಟ್ಟು ಫಲಿತಾಂಶವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.
- **ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸುವುದರಿಂದ ಅದರ cursor ಕೂಡ ಅಳಿಸಲ್ಪಡುತ್ತದೆ.** ಅದನ್ನು ಮರುಸೇರಿಸಿದಾಗ, ಉಳಿಸಿಕೊಂಡಿರುವ ಅತ್ಯಂತ ಹಳೆಯ
  call log ನಿಂದ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ; ಇದರಿಂದ ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ ಈಗಾಗಲೇ ಇರಬಹುದಾದ rows ಮತ್ತೆ ಕಳುಹಿಸಲ್ಪಡುತ್ತವೆ. BigQuery ನಲ್ಲಿ ಪ್ರತಿ row ಗೆ ಇರುವ
  `insertId`, BigQuery ನ ಸ್ವಂತ de-duplication window ಒಳಗೆ ಮಾತ್ರ ಇದನ್ನು ನಿಭಾಯಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸುವುದಕ್ಕಿಂತ
  disable ಮಾಡುವುದಕ್ಕೆ ಆದ್ಯತೆ ನೀಡಿ.
