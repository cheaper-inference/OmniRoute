OmniRoute ಕರೆ ಲಾಗ್‌ಗಳನ್ನು ಬಾಹ್ಯ ವಿಶ್ಲೇಷಣಾ ಸಂಗ್ರಹಕ್ಕೆ ನಿರಂತರವಾಗಿ, ಹಂತಹಂತವಾಗಿ ರಫ್ತು ಮಾಡುವುದು.

ಲಾಗ್‌ಗಳ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಟ್ಯಾಬ್ ವಿನಂತಿಗಳ ಇತಿಹಾಸವನ್ನು SQLite (`call_logs`) ನಲ್ಲಿ ಉಳಿಸುತ್ತದೆ; ಇದು
ರೊಟೇಶನ್ ಮತ್ತು ಧಾರಣೆಯ ಮಿತಿಗಳಿಗೆ ಒಳಪಟ್ಟಿರುತ್ತದೆ. ಲಾಗ್ ರಫ್ತು ಅದೇ ದಾಖಲೆಗಳ ಗುಂಪನ್ನು ನಿಗದಿತ ವೇಳಾಪಟ್ಟಿಯಂತೆ ಹೊರಗೆ ಕಳುಹಿಸುತ್ತದೆ, ಇದರಿಂದ ಅದು
ಸ್ಥಳೀಯ ಡೇಟಾಬೇಸ್‌ಗಿಂತ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯಬಹುದು ಮತ್ತು ಇತರ ಡೇಟಾದೊಂದಿಗೆ ಜೋಡಿಸಬಹುದು. BigQuery ಮೊದಲ ಗಮ್ಯಸ್ಥಾನವಾಗಿದೆ;
ಪೈಪ್‌ಲೈನ್ ಒಂದು ರಿಜಿಸ್ಟ್ರಿಯಾಗಿರುವುದರಿಂದ, ಮತ್ತಷ್ಟು ಗಮ್ಯಸ್ಥಾನಗಳನ್ನು ಹೆಚ್ಚುವರಿಯಾಗಿ ಸೇರಿಸಬಹುದು.

## 1. ಇದು ಹೇಗೆ ಕೆಲಸ ಮಾಡುತ್ತದೆ

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **ವೇಳಾಪಟ್ಟಿ** — ಒಂದು `JobRegistry` cron ಕಾರ್ಯ, `log_export`, ಇದರ ಡೀಫಾಲ್ಟ್ `0 * * * *` (ಪ್ರತಿ ಗಂಟೆ,
  UTC). ಇದನ್ನು `src/lib/initCloudSync.ts` ನಲ್ಲಿ ನೋಂದಾಯಿಸಲಾಗಿದೆ; `OMNIROUTE_LOG_EXPORT_CRON` ಮೂಲಕ ಬದಲಾಯಿಸಬಹುದು.
  ಪ್ರತಿ ಆವರ್ತನವು **ಸಕ್ರಿಯಗೊಳಿಸಲಾದ** ಪ್ರತಿಯೊಂದು ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿರುವ ಬಾಕಿ ದಾಖಲೆಗಳನ್ನು ಅನುಕ್ರಮವಾಗಿ ರಫ್ತು ಮಾಡುತ್ತದೆ.
- **ಕರ್ಸರ್** — SQLite ನ ಅಂತರ್ಗತ `call_logs.rowid`, ಇದನ್ನು ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ
  `log_export_destinations.cursor_row_id` ನಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ. `timestamp` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಕರ್ಸರ್ ಆಗಿ ಬಳಸುವುದಿಲ್ಲ: ಕರೆ ಮಾಡುವವರು
  ತಮ್ಮದೇ ಮೌಲ್ಯವನ್ನು ಒದಗಿಸಬಹುದು; ಹೀಗಾಗಿ ನಂತರ ಪ್ರಾರಂಭವಾದ ವೇಗದ ವಿನಂತಿಯ ಬಳಿಕ ನಿಧಾನವಾದ ವಿನಂತಿಯನ್ನು
  ಬರೆಯಬಹುದು, ಮತ್ತು ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಕರ್ಸರ್ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.
- **ಬ್ಯಾಚಿಂಗ್** — ಪ್ರತಿ ವಿನಂತಿಗೆ `batch_size` ಸಾಲುಗಳು (ಡೀಫಾಲ್ಟ್ 500), ಪ್ರತಿ ಚಾಲನೆಗೆ `max_rows_per_run` ಸಾಲುಗಳು
  (ಡೀಫಾಲ್ಟ್ 10000); ಇದರಿಂದ ದೊಡ್ಡ ಪ್ರಮಾಣದ ಬಾಕಿ ದಾಖಲೆಗಳು ಒಂದೇ ಆವರ್ತನವನ್ನು ತಡೆಯುವ ಬದಲು ಹಲವು ಆವರ್ತನಗಳಲ್ಲಿ ರಫ್ತಾಗುತ್ತವೆ.
- **ವಿತರಣೆ** — `send()` ಯಶಸ್ವಿಯಾಗಿ ಪೂರ್ಣಗೊಂಡ ನಂತರವೇ ಕರ್ಸರ್ ಮುಂದುವರಿಯುತ್ತದೆ. ಬ್ಯಾಚ್ ವಿಫಲವಾದರೆ
  ಕರ್ಸರ್ ಇದ್ದಲ್ಲೇ ಉಳಿಯುತ್ತದೆ, ಆದ್ದರಿಂದ ಮುಂದಿನ ಚಾಲನೆಯಲ್ಲಿ ಅದೇ ಸಾಲುಗಳನ್ನು ಮತ್ತೆ ಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ. ಇದರ ಖಾತರಿಯು
  ಕನಿಷ್ಠ ಒಮ್ಮೆ ವಿತರಣೆ ಮತ್ತು ಗಮ್ಯಸ್ಥಾನದ ಕಡೆಯ ನಕಲು ನಿವಾರಣೆಯಾಗಿದೆ; ನಿಜವಾದ ನಿಖರವಾಗಿ-ಒಮ್ಮೆ ವಿತರಣೆಯಲ್ಲ: BigQuery ಪ್ರತಿ
  ಸಾಲಿಗೆ ಕರೆ-ಲಾಗ್ id ಅನ್ನು ಕೀಲಿಯಾಗಿ ಬಳಸುತ್ತದೆ ಮತ್ತು ತನ್ನದೇ ನಕಲು ನಿವಾರಣಾ ಕಾಲಮಿತಿಯೊಳಗೆ ಅದನ್ನು ಸಾಧ್ಯವಾದಷ್ಟು ಮಟ್ಟಿಗೆ ಪಾಲಿಸುತ್ತದೆ.
- **ಏಕಕಾಲಿಕ ಚಾಲನೆ ತಡೆ** — cron ಆವರ್ತನ ಮತ್ತು `POST .../run` ಒಟ್ಟಿಗೆ ಪ್ರಚೋದಿತವಾಗಬಹುದು. ಈಗಾಗಲೇ
  ರಫ್ತು ನಡೆಯುತ್ತಿರುವ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಎರಡು ಬಾರಿ ರಫ್ತು ಮಾಡುವ ಬದಲು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ (ಚಾಲನೆಯ ಫಲಿತಾಂಶದಲ್ಲಿ `skipped: true`),
  ಆದ್ದರಿಂದ ಏಕಕಾಲಿಕ ಚಾಲನೆಯು ಬ್ಯಾಚ್ ಅನ್ನು ಮರುಕಳುಹಿಸಲು ಅಥವಾ ಕರ್ಸರ್ ಅನ್ನು ಹಿಂದಕ್ಕೆ ಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ.
- **ಸಂಪೂರ್ಣ ತೆರವಿನ ನಂತರದ ಚೇತರಿಕೆ** — `cursor_row_id`, `MAX(rowid)` ಗಿಂತ ಹೆಚ್ಚಾದರೆ (ಇಡೀ ಟೇಬಲ್ ಅನ್ನು
  ತೆರವುಗೊಳಿಸಿ rowid ಗಳನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿದ್ದರೆ), ರನ್ನರ್ ಶಾಶ್ವತವಾಗಿ ದಾಖಲೆಗಳನ್ನು ಕಾಣದೇ ಉಳಿಯುವ ಬದಲು 0 ಗೆ ಹಿಂದಿರುಗುತ್ತದೆ.

### ಪ್ರತ್ಯೇಕಿತ ರನ್ನರ್ ಮತ್ತು ಮಿತಿಗಳು

Node ನಲ್ಲಿ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ ಚಾಲನೆಯು ಪ್ರತ್ಯೇಕ, ಅಲ್ಪಾವಧಿಯ OS ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ (IPC ಹೊಂದಿರುವ `child_process`,
`worker_threads` ಅಲ್ಲ). ಬಾಡಿ ಓದುವಿಕೆ, ಪೇಲೋಡ್ JSON ಪಾರ್ಸಿಂಗ್/ಸೀರಿಯಲೈಸೇಶನ್, ಗಮ್ಯಸ್ಥಾನದ
`prepare()` ಮತ್ತು ಗಮ್ಯಸ್ಥಾನದ ನೆಟ್‌ವರ್ಕ್ I/O ಎಲ್ಲವೂ ಅಲ್ಲಿಯೇ ನಡೆಯುತ್ತವೆ, ಸರ್ವರ್‌ನ ಈವೆಂಟ್ ಲೂಪ್‌ನಲ್ಲಿ ಅಲ್ಲ.
ಕಾನ್ಫಿಗರೇಶನ್ ಮತ್ತು ಸಣ್ಣ ಪ್ರಗತಿ ಸಂದೇಶಗಳು ಮಾತ್ರ IPC ಮೂಲಕ ಸಾಗುತ್ತವೆ; ರಫ್ತು ಮಾಡಿದ ದಾಖಲೆಗಳು ಎಂದಿಗೂ
ಸರ್ವರ್‌ಗೆ ಹಿಂತಿರುಗುವುದಿಲ್ಲ. cron ಕಾರ್ಯ ಮತ್ತು ಈಗ ಚಲಾಯಿಸಿ ಮಾರ್ಗವು ಅದೇ ಸಾರ್ವಜನಿಕ ಫಲಿತಾಂಶ ಮತ್ತು ಏಕಕಾಲಿಕ ಚಾಲನೆ ತಡೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಯು ಸರ್ವರ್ ನಿರ್ಧರಿಸಿದ `DATA_DIR/storage.sqlite` ಅನ್ನು `node:sqlite` ಬಳಸಿ ಓದಲು-ಮಾತ್ರ ತೆರೆಯುತ್ತದೆ,
ಜೊತೆಗೆ `busy_timeout=5000` ಮತ್ತು `query_only=ON` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಅದು ಯಾವುದೇ DB ಸಿಂಗಲ್‌ಟನ್ ಅನ್ನು ಆಮದು ಮಾಡುವುದಿಲ್ಲ ಮತ್ತು
ಯಾವುದೇ ಮೈಗ್ರೇಶನ್‌ಗಳು, ಬ್ಯಾಕಪ್‌ಗಳು ಅಥವಾ SQLite ನವೀಕರಣಗಳನ್ನು ಮಾಡುವುದಿಲ್ಲ. ಕಾಣೆಯಾದ/ಹಾನಿಗೊಂಡ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್‌ಗಳ ದಾಖಲೆ ನಿರ್ವಹಣೆ (ಹಾನಿಗೊಂಡ
ಆರ್ಟಿಫ್ಯಾಕ್ಟ್‌ನ UPDATE ಸೇರಿದಂತೆ) ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ವಿವರದ ಮಾರ್ಗದಲ್ಲಿ ಮಾತ್ರ ಉಳಿಯುತ್ತದೆ. ಎರಡೂ ಮಾರ್ಗಗಳು ಶುದ್ಧ
ವಿವರ ಪರಿಹಾರಕವನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ; ರಫ್ತು ಅಸಮಕಾಲಿಕ ಫೈಲ್‌ಸಿಸ್ಟಮ್ ಓದುವಿಕೆಗಳನ್ನು ಮತ್ತು ಅದೇ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ → ಹಳೆಯ
ಇನ್‌ಲೈನ್ → ಹಳೆಯ ಡಿಸ್ಕ್ → ಯಾವುದೂ ಇಲ್ಲ ಎಂಬ ಪರಿಹಾರ ಕ್ರಮವನ್ನು ಬಳಸುತ್ತದೆ. ಚೈಲ್ಡ್ ತನ್ನ ರೀಡರ್ ಅನ್ನು ತೆರೆದಾಗ ಚಾಲನೆಯು ಗರಿಷ್ಠ ಸೇರ್ಪಡೆ rowid ಯ
ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ; ನಂತರದ ಸೇರ್ಪಡೆಗಳು ಮುಂದಿನ ಚಾಲನೆಗಾಗಿ ಕಾಯುತ್ತವೆ. ಇದು ಸೇರ್ಪಡೆಯ
ಗಡಿಯಾಗಿದೆ, ದೀರ್ಘಾವಧಿಯ SQLite ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಅಲ್ಲ: ನೆಟ್‌ವರ್ಕ್ ಕಾಯುವಿಕೆಯ ಸಮಯದಲ್ಲಿ WAL ಬರಹಗಾರರು ಮತ್ತು ಚೆಕ್‌ಪಾಯಿಂಟ್‌ಗಳು ಮುಕ್ತವಾಗಿರುತ್ತವೆ.
ಈ ಗಡಿಯು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಾಲುಗಳ ನವೀಕರಣ/ಅಳಿಸುವಿಕೆಯನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುವುದಿಲ್ಲ.

ಪ್ರತಿ ಸ್ವೀಕೃತ ಬ್ಯಾಚ್ ನಂತರ, ಚೈಲ್ಡ್ ದೃಢೀಕರಣಕ್ಕಾಗಿ ಕಾಯುತ್ತದೆ. ಸರ್ವರ್ ಮೊದಲು
`advanceLogExportCursor` ಮೂಲಕ ಕರ್ಸರ್ ಅನ್ನು ಉಳಿಸುತ್ತದೆ, ನಂತರ `ack` ಕಳುಹಿಸುತ್ತದೆ; ಅದಕ್ಕೂ ಮೊದಲು ಮುಂದಿನ ಬ್ಯಾಚ್ ಪ್ರಾರಂಭವಾಗುವುದಿಲ್ಲ.
ಕಳುಹಿಸುವಿಕೆ ವಿಫಲವಾದರೆ, ಕ್ರ್ಯಾಶ್ ಆದರೆ ಅಥವಾ ಸಮಯ ಮೀರಿದರೆ, ಆ ಬ್ಯಾಚ್ ಅನ್ನು ಮುಂದುವರಿಸದೆ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ. ಹಿಂದೆ
ದೃಢೀಕರಿಸಲಾದ ಬ್ಯಾಚ್‌ಗಳು ಕಮಿಟ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತವೆ; ಗರಿಷ್ಠ ಒಂದು ದೃಢೀಕರಿಸದ ಬ್ಯಾಚ್ ಮಾತ್ರ ಮರುಕಳುಹಿಸಲ್ಪಡಬಹುದು.
`done` ಮತ್ತು ಚೈಲ್ಡ್‌ನ ದೋಷರಹಿತ ನಿರ್ಗಮನದ ನಂತರವೇ ಯಶಸ್ಸನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ. ವೈಫಲ್ಯಗಳು ಚೈಲ್ಡ್ ಅನ್ನು
SIGTERM ಮೂಲಕ ಅಂತ್ಯಗೊಳಿಸುತ್ತವೆ, 500 ms ನಂತರ SIGKILL ಗೆ ಏರಿಸುತ್ತವೆ, ಮತ್ತು ರನ್ನರ್ ಪ್ರಕ್ರಿಯೆ ಮುಚ್ಚುವವರೆಗೆ ಕಾಯುತ್ತದೆ.

| ಪರಿಸರ ಚರ                                      | ಡೀಫಾಲ್ಟ್ | ಉದ್ದೇಶ                              |
| --------------------------------------------- | -------- | ----------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000   | ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ ನೈಜ ಕಳೆದ ಸಮಯದ ಮಿತಿ |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024     | MB ಯಲ್ಲಿ ಚೈಲ್ಡ್ V8 old-space ಮಿತಿ   |

ಅಮಾನ್ಯ/ಧನಾತ್ಮಕವಲ್ಲದ/ಪೂರ್ಣಾಂಕವಲ್ಲದ ಮೌಲ್ಯಗಳಿದ್ದರೆ ಡೀಫಾಲ್ಟ್‌ಗಳನ್ನು ಬಳಸಲಾಗುತ್ತದೆ. ಹೀಪ್ ಸೆಟ್ಟಿಂಗ್ ಒಟ್ಟು
RSS ಮಿತಿಯಲ್ಲ; ಅತಿ ದೊಡ್ಡ ಬ್ಯಾಚ್‌ಗಳು ಇನ್ನೂ ಚೈಲ್ಡ್ ಮೆಮೊರಿಯನ್ನು ಖಾಲಿ ಮಾಡಿ ಚಾಲನೆಯನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲಗೊಳಿಸಬಹುದು.
1024 MB ಡೀಫಾಲ್ಟ್, ಬಾಡಿಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿದ 512 KiB ಆರ್ಟಿಫ್ಯಾಕ್ಟ್‌ಗಳ ಡೀಫಾಲ್ಟ್ 500-ಸಾಲು ಬ್ಯಾಚ್‌ಗೆ
ಸಾಕಷ್ಟು ಹೆಚ್ಚುವರಿ ಸಾಮರ್ಥ್ಯವನ್ನು ಬಿಡುತ್ತದೆ; ಇದರಲ್ಲಿ BigQuery ಯ ಬೈಟ್-ಚಂಕ್ ಮಾಡಿದ JSON ಸೀರಿಯಲೈಸೇಶನ್ ಕೂಡ ಸೇರಿದೆ. ಇದು
10000-ಸಾಲುಗಳ ಬಾಡಿಗಳ ಬ್ಯಾಚ್ ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿಸುವುದಿಲ್ಲ. V8 ಹೀಪ್ ಖಾಲಿಯಾದಾಗ ಕ್ರಮ ಕೈಗೊಳ್ಳಬಹುದಾದ ವೈಫಲ್ಯವನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ: ಬ್ಯಾಚ್
ಗಾತ್ರವನ್ನು ಕಡಿಮೆ ಮಾಡಿ ಅಥವಾ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` ಅನ್ನು ಹೆಚ್ಚಿಸಿ; ಕರ್ಸರ್ ಕೊನೆಯದಾಗಿ
ದೃಢೀಕರಿಸಲಾದ ಬ್ಯಾಚ್‌ನಲ್ಲೇ ಉಳಿಯುತ್ತದೆ. ಹಿಂದಿನ ಇನ್‌ಲೈನ್/ಡಿಸ್ಕ್ ಬಾಡಿಗಳು ಆಧುನಿಕ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಮಿತಿಗೆ ಒಳಪಡುವುದಿಲ್ಲ.
ನಿರ್ವಾಹಕರು RSS ಗಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಸಾಮರ್ಥ್ಯವನ್ನು ಮೀಸಲಿಡಬೇಕು, ವಿಶೇಷವಾಗಿ ಮೆಮೊರಿ-ಮಿತಿಯ ಕಂಟೈನರ್‌ಗಳ ಒಳಗೆ.

ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಯು ನಿರ್ಧರಿಸಲಾದ `DATA_DIR`, `NODE_ENV`, ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸಲಾದ `TZ` (ಹಳೆಯ ಫೈಲ್‌ಹೆಸರಿನ
ಸ್ಥಳೀಯ-ಸಮಯ ನಿರ್ಧಾರ), ಲಭ್ಯವಿದ್ದಾಗ `ELECTRON_RUN_AS_NODE`, ಮತ್ತು ಈ ಕೆಳಗಿನ ಹೊರಹೋಗುವ ಸಂಪರ್ಕದ ಇನ್‌ಪುಟ್‌ಗಳನ್ನು ಮಾತ್ರ ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯುತ್ತದೆ:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (ಮತ್ತು ಅವುಗಳ ಸಣ್ಣಕ್ಷರದ ರೂಪಗಳು),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
ಜಾಗತಿಕ Undici ಡಿಸ್ಪ್ಯಾಚರ್ ಸರ್ವರ್‌ನ ಪರಿಸರ-ಆಧಾರಿತ ಪ್ರಾಕ್ಸಿ ನಿರ್ಧಾರ ಮತ್ತು ಸ್ಥಳೀಯ-ಹೋಸ್ಟ್
ಬೈಪಾಸ್ ನಿಯಮಗಳನ್ನು, `NO_PROXY` ಸೇರಿದಂತೆ, ಹಂಚಿಕೊಳ್ಳುತ್ತದೆ; ಇದು `proxyFetch.ts` ಅಥವಾ ಅದರ DB/ವೈಶಿಷ್ಟ್ಯದ ಫ್ಲ್ಯಾಗ್‌ಗಳನ್ನು ಆಮದು ಮಾಡಿಕೊಳ್ಳುವುದಿಲ್ಲ.
ಫಾರ್ವರ್ಡ್ ಮಾಡಲಾದ ಔಟ್‌ಪುಟ್ ಮತ್ತು ದಾಖಲಿಸಲಾದ ದೋಷಗಳಿಂದ ಪ್ರಾಕ್ಸಿ ಪ್ರವೇಶ ವಿವರಗಳನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ. ಗಮ್ಯಸ್ಥಾನದ ಪ್ರವೇಶ ವಿವರಗಳು
ಒಂದೇ ಪ್ರಾರಂಭಿಕ IPC ಸಂದೇಶದಲ್ಲಿ ಮಾತ್ರ ರವಾನೆಯಾಗುತ್ತವೆ, argv ಅಥವಾ ಪರಿಸರದಲ್ಲಿ ಎಂದಿಗೂ ಅಲ್ಲ; ಔಟ್‌ಪುಟ್/ದೋಷ ಫಾರ್ವರ್ಡಿಂಗ್‌ಗೆ
ಪೂರ್ವಪ್ರತ್ಯಯ ಸೇರಿಸಿ ಸೂಕ್ಷ್ಮ ಮಾಹಿತಿಯನ್ನು ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ. ಪ್ರತಿ cron ಚಾಲನೆಯಲ್ಲಿ Node‌ನ SQLite ಎಚ್ಚರಿಕೆ
ಮರುಕಳಿಸದಂತೆ ಚೈಲ್ಡ್ exec ಆರ್ಗ್ಯುಮೆಂಟ್‌ಗಳಲ್ಲಿ `ExperimentalWarning` ಅನ್ನು ಮಾತ್ರ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗುತ್ತದೆ; ಇತರ ಎಚ್ಚರಿಕೆ ಪ್ರಕಾರಗಳು ಕಾಣಿಸುತ್ತಲೇ ಇರುತ್ತವೆ.

ಗಮ್ಯಸ್ಥಾನ ಮಾಡ್ಯೂಲ್‌ಗಳನ್ನು Next.js/ಸರ್ವರ್‌ಗೆ ಮಾತ್ರ ಸೀಮಿತವಾದ ಅವಲಂಬನೆಗಳಿಲ್ಲದೆ ಆಮದು ಮಾಡಿಕೊಳ್ಳಲು ಸಾಧ್ಯವಾಗಬೇಕು. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
BigQuery ಅನುಷ್ಠಾನವು ಈಗಾಗಲೇ ಆ ಒಪ್ಪಂದವನ್ನು ಪೂರೈಸುತ್ತದೆ. ಪ್ರವೇಶ-ಟೋಕನ್ ಕ್ಯಾಶ್‌ಗಳು ಚೈಲ್ಡ್
ಚಾಲನೆಯ ಅವಧಿಗೆ ಮಾತ್ರ ಉಳಿಯುತ್ತವೆ, ಚಾಲನೆಗಳ ನಡುವೆ ಅಲ್ಲ. Node ಬೆಂಬಲಿತ ರನ್‌ಟೈಮ್ ಆಗಿದೆ (`package.json` engines), ಆದರೆ READMEಯ Bun
ಸ್ಥಾಪನಾ ವಿಭಾಗ ಮತ್ತು `Dockerfile.bun` ಕೂಡ
`bun:sqlite` (`src/lib/db/core.ts` / ಅಡಾಪ್ಟರ್‌ಗಳು) ಬಳಸುವ ಉತ್ಪಾದನಾ ಹೊಂದಾಣಿಕೆಯ ಮಾರ್ಗವನ್ನು ಸೂಚಿಸುತ್ತವೆ. ಆದ್ದರಿಂದ Bun ಅಡಿಯಲ್ಲಿ, ಎಕ್ಸ್‌ಪೋರ್ಟ್‌ಗಳು ಹಿಂದಿನ
ಪ್ರಕ್ರಿಯೆಯೊಳಗಿನ ಮಾರ್ಗವನ್ನು ಉಳಿಸಿಕೊಂಡು ಒಂದು ಬಾರಿಯ ಎಚ್ಚರಿಕೆಯನ್ನು ನೀಡುತ್ತವೆ: ಚೈಲ್ಡ್ ಹೀಪ್/ಟೈಮ್‌ಔಟ್ ಪ್ರತ್ಯೇಕತೆ ಲಭ್ಯವಿಲ್ಲ.
ಈವೆಂಟ್-ಲೂಪ್ ಮತ್ತು OOM ಪ್ರತ್ಯೇಕತೆಗಾಗಿ Node ಬಳಸಿ; ಇಲ್ಲಿ Bun ಅನ್ನು ಅಭಿವೃದ್ಧಿಗೆ ಮಾತ್ರ ಸೀಮಿತವೆಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`includeBodies` ಸಕ್ರಿಯವಾಗಿದ್ದಾಗ, ಗಂಟೆಗೊಮ್ಮೆ ಪೇಲೋಡ್‌ಗಳ ಬಾಕಿ ಸಂಗ್ರಹವಾಗುವುದಕ್ಕಿಂತ
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ ನಿಮಿಷ-ಮಟ್ಟದ ಆವರ್ತನಕ್ಕೆ ಆದ್ಯತೆ ನೀಡಿ.
ಬ್ಯಾಚ್ ಮತ್ತು ಸಾಲು ಮಿತಿಗಳು ಪ್ರತಿ ಚಾಲನೆಯನ್ನು ಇನ್ನೂ ಮಿತಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿ ಚಾಲನೆಯಲ್ಲಿ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೂ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭದ ವೆಚ್ಚ ತಗಲುತ್ತದೆ;
ಇದು ಸರ್ವರ್ ಈವೆಂಟ್-ಲೂಪ್ ಪ್ರತ್ಯೇಕತೆಗಾಗಿ ಸಣ್ಣ ಪ್ರಾರಂಭಿಕ ವೆಚ್ಚವನ್ನು ವಹಿಸುತ್ತದೆ, ಒಟ್ಟು CPU ಬಳಕೆಯನ್ನು ಕಡಿಮೆ ಮಾಡುವುದಿಲ್ಲ.

### ಪೇಲೋಡ್‌ಗಳು (ಪ್ರಾಂಪ್ಟ್‌ಗಳು ಮತ್ತು ಪೂರ್ಣಗೊಳಿಕೆಗಳು)

ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಎಕ್ಸ್‌ಪೋರ್ಟ್‌ನಲ್ಲಿ ಲಾಗ್‌ಗಳ **ಪಟ್ಟಿ** ತೋರಿಸುವ ಸಾರಾಂಶ ಕ್ಷೇತ್ರಗಳು ಮಾತ್ರ ಇರುತ್ತವೆ.
**ಪ್ರಾಂಪ್ಟ್‌ಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡಿ** (`includeBodies`) ಸಕ್ರಿಯಗೊಳಿಸಿದರೆ, ಪ್ರತಿ ಕರೆಯ ಕುರಿತು ಲಾಗ್‌ಗಳ **ವಿವರ**
ಫಲಕ ತೋರಿಸುವ ಮಾಹಿತಿಯನ್ನೂ ಹೆಚ್ಚುವರಿಯಾಗಿ ಕಳುಹಿಸಲಾಗುತ್ತದೆ:

| ಕ್ಷೇತ್ರ                          | ಅದು ಒಳಗೊಂಡಿರುವುದು                                                        |
| -------------------------------- | ------------------------------------------------------------------------ |
| `request_body` / `response_body` | ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಪ್ರದರ್ಶಿಸುವ ರೂಪದಲ್ಲಿರುವ ಕರೆಯ ಪೇಲೋಡ್‌ಗಳು                    |
| `pipeline_route_decision`        | ರೂಟರ್ ಆಯ್ಕೆ ಮಾಡಿದ ಗುರಿ ಮತ್ತು ಮಾಡೆಲ್                                      |
| `pipeline_client_request`        | ಕ್ಲೈಂಟ್ ಕಳುಹಿಸಿದ ಯಥಾವತ್ತಾದ ಮೂಲ ವಿನಂತಿ                                    |
| `pipeline_openai_request`        | ಆಂತರಿಕ OpenAI ರೂಪಕ್ಕೆ ಪರಿವರ್ತಿಸಿದ ನಂತರದ ವಿನಂತಿ                           |
| `pipeline_provider_request`      | ಪೂರೈಕೆದಾರರ ಸ್ವರೂಪದಲ್ಲಿ ಅಪ್‌ಸ್ಟ್ರೀಮ್‌ಗೆ ನಿಜವಾಗಿ ಕಳುಹಿಸಿದ ವಿನಂತಿ           |
| `pipeline_provider_response`     | ಮೂಲ ಅಪ್‌ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆ                                             |
| `pipeline_client_response`       | ಕರೆ ಮಾಡಿದವರಿಗೆ ಹಿಂತಿರುಗಿಸಲಾದ ಮಾಹಿತಿ                                      |
| `pipeline_error`                 | ವಿಫಲವಾದ ಕರೆಯ ಪೈಪ್‌ಲೈನ್-ಮಟ್ಟದ ದೋಷ ವಿವರ                                    |
| `bodies_truncated`               | ಮೇಲಿನ ಯಾವುದೇ ಕ್ಷೇತ್ರವು `maxBodyBytes` ಮಿತಿಯನ್ನು ತಲುಪಿದಾಗ ಸತ್ಯವಾಗಿರುತ್ತದೆ |

ಇದು ಪ್ರಾಂಪ್ಟ್ ವಿಷಯವಾಗಿರುವುದರಿಂದ, ಇದು **ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ** ಮತ್ತು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೂ ಪ್ರತ್ಯೇಕ ಆಯ್ಕೆಯಾಗಿದೆ.
ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ತೋರಿಸುವುದನ್ನೇ ಕಳುಹಿಸಲಾಗುತ್ತದೆ, ಏಕೆಂದರೆ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮತ್ತು `getCallLogById` ಒಂದೇ ವಿವರ
ನಿರ್ಧಾರ ವಿಧಾನವನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ: ಪೇಲೋಡ್‌ಗಳನ್ನು
ಬರೆಯುವಾಗಲೇ ವೈಯಕ್ತಿಕ ಗುರುತಿನ ಮಾಹಿತಿ (PII) ತೆಗೆದುಹಾಕಿ ರಹಸ್ಯಗಳನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ, ಮತ್ತು
`noLog` API ಕೀಯೊಂದಿಗೆ ಮಾಡಿದ ಕರೆಯು ಯಾವುದೇ ಪೇಲೋಡ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡಲು ಏನೂ ಇರುವುದಿಲ್ಲ.

ಪೇಲೋಡ್‌ಗಳನ್ನು ಪ್ರತಿ ಸಾಲಿಗೂ ಫೈಲ್‌ಸಿಸ್ಟಮ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್‌ನಿಂದ ಓದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಅವುಗಳನ್ನು ಲೋಡ್ ಮಾಡುವ ಪ್ರಕ್ರಿಯೆಯು
ಅದನ್ನು ವಿನಂತಿಸಿದ ಗಮ್ಯಸ್ಥಾನಗಳಿಗೆ ಮಾತ್ರ ನಡೆಯುತ್ತದೆ. ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಕಾಣೆಯಾಗಿದ್ದರೆ ಅಥವಾ ಹಾಳಾಗಿದ್ದರೆ, ಬ್ಯಾಚ್ ವಿಫಲವಾಗಿ ಕರ್ಸರ್ ಸಿಲುಕಿಕೊಳ್ಳುವ ಬದಲು
ಅದರ ಸಾರಾಂಶವನ್ನು ನಲ್ ಪೇಲೋಡ್‌ಗಳೊಂದಿಗೆ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ.

`maxBodyBytes` (ಪೂರ್ವನಿಯೋಜಿತ 262144) ಪ್ರತಿ ಕ್ಷೇತ್ರಕ್ಕೂ ಮಿತಿ ವಿಧಿಸುತ್ತದೆ. ದೊಡ್ಡ ಪೇಲೋಡ್‌ಗಳನ್ನು **ಕೈಬಿಡುವ ಬದಲು
ಮೊಟಕುಗೊಳಿಸಲಾಗುತ್ತದೆ** — ಮೊಟಕುಗೊಳಿಸಿದ ಪ್ರಾಂಪ್ಟ್ ಕೂಡ "ಏನು ಕೇಳಲಾಗಿತ್ತು" ಎಂಬುದಕ್ಕೆ ಉತ್ತರ ನೀಡುತ್ತದೆ — ಮತ್ತು ಆ ಸಾಲಿಗೆ
`bodies_truncated` ಗುರುತು ಹಾಕಲಾಗುತ್ತದೆ. ಸ್ಟ್ರೀಮ್ ಮಾಡಲಾದ ತುಣುಕು-ತುಣುಕಿನ ಬದಲಾವಣೆಗಳನ್ನು ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡುವುದಿಲ್ಲ; ಒಟ್ಟುಗೂಡಿಸಿದ ಪ್ರತಿಕ್ರಿಯೆಯು
ಈಗಾಗಲೇ `pipeline_provider_response` ಮತ್ತು `pipeline_client_response` ನಲ್ಲಿರುತ್ತದೆ.

## 3. REST API

ಎಲ್ಲಾ ಮಾರ್ಗಗಳಿಗೂ ನಿರ್ವಹಣಾ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ (`requireManagementAuth`). ರಹಸ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ:
ಸಂಗ್ರಹಿಸಿದ ರಹಸ್ಯವನ್ನು ಅಕ್ಷರಶಃ `__stored__` ಎಂಬ ಮೌಲ್ಯವಾಗಿ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ನವೀಕರಣದ ಸಮಯದಲ್ಲಿ ಆ ಮೌಲ್ಯವನ್ನು ಮರಳಿ ಕಳುಹಿಸಿದರೆ
ಸಂಗ್ರಹಿಸಿದ ದೃಢೀಕರಣ ಮಾಹಿತಿಯನ್ನು ಹಾಗೆಯೇ ಉಳಿಸಲಾಗುತ್ತದೆ.

ರಹಸ್ಯವನ್ನು ಘೋಷಿಸುವ ಪ್ರಕಾರದ ಗಮ್ಯಸ್ಥಾನವನ್ನು ರಚಿಸಲು ಅಥವಾ ನವೀಕರಿಸಲು **`STORAGE_ENCRYPTION_KEY`
ಅಗತ್ಯವಿದೆ**. ಅದು ಇಲ್ಲದಿದ್ದರೆ `encrypt()` ಯಾವುದೇ ಬದಲಾವಣೆ ಮಾಡದೆ ಮೌನವಾಗಿ ದತ್ತಾಂಶವನ್ನು ಮುಂದಕ್ಕೆ ಕಳುಹಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ದೃಢೀಕರಣ ಮಾಹಿತಿಯನ್ನು
SQLite ನಲ್ಲಿ ಸರಳ ಪಠ್ಯವಾಗಿ ಸಂಗ್ರಹಿಸುವ ಬದಲು ಬರವಣಿಗೆಯನ್ನು 400 ಪ್ರತಿಕ್ರಿಯೆಯೊಂದಿಗೆ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ (Telegram webhook
ಅನ್ವಯಿಸುವ ಅದೇ ರಕ್ಷಣೆ).

## 4. BigQuery ಗಮ್ಯಸ್ಥಾನ

ಸಂರಚನಾ ಕೀಗಳು (`type: "bigquery"`):

| ಕೀ                   | ಟಿಪ್ಪಣಿಗಳು                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `projectId`          | ಡೇಟಾಸೆಟ್ ಹೊಂದಿರುವ GCP ಪ್ರಾಜೆಕ್ಟ್                                                               |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                |
| `location`           | ಡೇಟಾಸೆಟ್ ರಚಿಸಬೇಕಾದಾಗ ಮಾತ್ರ ಬಳಸಲಾಗುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `EU`)                                        |
| `serviceAccountJson` | ಸೇವಾ ಖಾತೆಯ ಕೀ. ರಹಸ್ಯ: ಸಂಗ್ರಹದಲ್ಲಿರುವಾಗ ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ, ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ |
| `autoCreate`         | ಮೊದಲ ರಫ್ತಿನ ವೇಳೆ ಡೇಟಾಸೆಟ್ ಮತ್ತು ಟೇಬಲ್ ರಚಿಸಿ (ಡೀಫಾಲ್ಟ್ `true`)                                  |

ಸೇವಾ ಖಾತೆಗೆ ಗುರಿ ಟೇಬಲ್‌ನಲ್ಲಿ `bigquery.tables.updateData` ಅಗತ್ಯವಿದೆ; ಜೊತೆಗೆ
`autoCreate` ಸಕ್ರಿಯವಾಗಿರುವಾಗ `bigquery.datasets.create` / `bigquery.tables.create` ಅಗತ್ಯವಿದೆ.

ಸಂರಚಿಸಲಾದ ಬ್ಯಾಚ್ ಒಂದು **ಕರ್ಸರ್** ಘಟಕವಾಗಿದೆ, HTTP ಘಟಕವಲ್ಲ: `send()` ಅದನ್ನು ಗರಿಷ್ಠ 500 ಸಾಲುಗಳ insertAll
ಕರೆಗಳಾಗಿ ವಿಭಜಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ದೊಡ್ಡ `batch_size` BigQuery ಯ 10 MB ವಿನಂತಿ ಮಿತಿಯನ್ನು ಮೀರಲು ಸಾಧ್ಯವಿಲ್ಲ.
ತಾತ್ಕಾಲಿಕ ಸ್ಥಿತಿಗಳನ್ನು (408/429/500/502/503/504) ಅದೇ insertIds ಮರುಬಳಸಿ, ಘಾತೀಯವಾಗಿ ಹೆಚ್ಚುವ
ವಿಳಂಬದೊಂದಿಗೆ ಗರಿಷ್ಠ ಮೂರು ಬಾರಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ; ದೃಢೀಕರಣ ಮತ್ತು ಸ್ಕೀಮಾ ವೈಫಲ್ಯಗಳು ರನ್‌ನ ಪ್ರಯತ್ನಗಳನ್ನು ವ್ಯರ್ಥಗೊಳಿಸುವ ಬದಲು
ಮೊದಲ ಪ್ರಯತ್ನದಲ್ಲೇ ದೋಷವನ್ನು ಎಸೆಯುತ್ತವೆ.

ಕೆಲವೇ ಕ್ಷಣಗಳ ಹಿಂದೆ ರಚಿಸಿದ ಟೇಬಲ್ ಸ್ಟ್ರೀಮಿಂಗ್ ಎಂಡ್‌ಪಾಯಿಂಟ್‌ಗೆ ಇನ್ನೂ ಗೋಚರಿಸುವುದಿಲ್ಲ; ಅದು
ಕೆಲವು ಸೆಕೆಂಡುಗಳ ಕಾಲ 404 ಪ್ರತಿಕ್ರಿಯೆ ನೀಡುತ್ತದೆ. ಆ 404 ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ, ಆದರೆ **ಈ ರನ್ ಟೇಬಲ್ ರಚಿಸಿದ್ದಾಗ ಮಾತ್ರ** —
ನಿಜವಾಗಿಯೂ ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದ ಟೇಬಲ್ ತಕ್ಷಣವೇ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಇತ್ತೀಚೆಗೆ ಅಳಿಸಿದ ಹೆಸರಿನಲ್ಲೇ ಟೇಬಲ್ ಮರುರಚಿಸುವುದರಿಂದ
BigQuery ಹಲವು ನಿಮಿಷಗಳವರೆಗೆ ಸ್ಟ್ರೀಮಿಂಗ್ ಇನ್‌ಸರ್ಟ್‌ಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ಗಮನಿಸಿ; ಇದು
ಅಳಿಸಿ-ನಂತರ-ಮರುರಚಿಸುವ ಪ್ರಕ್ರಿಯೆಯ ಗುಣಲಕ್ಷಣವಾಗಿದೆ, ಆದ್ದರಿಂದ ಟೇಬಲ್ ಅಳಿಸಿ ಮತ್ತೆ ಸೇರಿಸುವ ಬದಲು ಹೊಸ ಟೇಬಲ್ ಹೆಸರನ್ನು ಬಳಸಿ.

**ಭಾಗಶಃ ವೈಫಲ್ಯವು ಖಾಲಿಯಲ್ಲದ `insertErrors[]` ಜೊತೆಗೆ HTTP 200 ಆಗಿ ಬರುತ್ತದೆ.** ಅದನ್ನು
ವೈಫಲ್ಯವೆಂದು ಪರಿಗಣಿಸಿ ದೋಷವನ್ನು ಎಸೆಯಲಾಗುತ್ತದೆ; ಇದರಿಂದ BigQuery ಸ್ವೀಕರಿಸದ ಸಾಲುಗಳನ್ನು ದಾಟಿ ಕರ್ಸರ್
ಮುಂದುವರಿಯುವುದು ನಿಲ್ಲುತ್ತದೆ; `tests/unit/log-export-bigquery.test.ts` ಈ ನಡವಳಿಕೆಯನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ.

ಸಂವಹನವು ಸರಳ REST ಮೂಲಕ ನಡೆಯುತ್ತದೆ — ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ RS256 ಅಸರ್ಷನ್ ಅನ್ನು
`https://oauth2.googleapis.com/token` ನಲ್ಲಿ ಪ್ರವೇಶ ಟೋಕನ್‌ಗಾಗಿ ವಿನಿಮಯ ಮಾಡಲಾಗುತ್ತದೆ, ನಂತರ ಸಾಲುಗಳನ್ನು `tabledata.insertAll` ಗೆ ಕಳುಹಿಸಲಾಗುತ್ತದೆ. ಯಾವುದೇ Google SDK ಅನ್ನು
ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ. ಪ್ರವೇಶ ಟೋಕನ್‌ಗಳನ್ನು ಪ್ರತಿ (ಸೇವಾ ಖಾತೆ, ವ್ಯಾಪ್ತಿ) ಜೋಡಿಗೆ ಪ್ರಕ್ರಿಯೆಯೊಳಗೆ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ.

ರಚಿಸಿದ ಟೇಬಲ್‌ನಲ್ಲಿ Logs-ಟ್ಯಾಬ್‌ನ ಪ್ರತಿ ಫೀಲ್ಡ್‌ಗೆ ಒಂದು ಕಾಲಮ್ ಹಾಗೂ `exported_at` ಇರುತ್ತದೆ, ಮತ್ತು
ಕಾಲ್ ಲಾಗ್‌ಗಳನ್ನು ವಾಸ್ತವವಾಗಿ ಹೇಗೆ ಕ್ವೆರಿ ಮಾಡಲಾಗುತ್ತದೆ ಎಂಬುದಕ್ಕೆ ತಕ್ಕಂತೆ ವಿನ್ಯಾಸಗೊಳಿಸಲಾಗಿದೆ:

- **`timestamp` ಆಧಾರದಲ್ಲಿ ದಿನವಾರು ಪಾರ್ಟಿಷನ್ ಮಾಡಲಾಗಿದೆ**, ಆದ್ದರಿಂದ ದಿನಾಂಕದಿಂದ ಸೀಮಿತಗೊಳಿಸಿದ ಕ್ವೆರಿಯು ಆ ದಿನಗಳನ್ನು ಮಾತ್ರ ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತದೆ.
- **`api_key_name`, `provider`, `model`, `status` ಆಧಾರದಲ್ಲಿ ಕ್ಲಸ್ಟರ್ ಮಾಡಲಾಗಿದೆ** (ಅದೇ ಕ್ರಮದಲ್ಲಿ), ಆದ್ದರಿಂದ
  ಯಾರು ಚಲಾಯಿಸಿದರು, ಅದು ಎಲ್ಲಿಗೆ ಹೋಯಿತು, ಅಥವಾ ಅದು ವಿಫಲವಾಯಿತೇ ಎಂಬುದರ ಆಧಾರದ ಫಿಲ್ಟರ್‌ಗಳು ಪ್ರತಿ ಪಾರ್ಟಿಷನ್‌ನೊಳಗಿನ ಅನಗತ್ಯ ಬ್ಲಾಕ್‌ಗಳನ್ನು ಹೊರಗಿಡುತ್ತವೆ. BigQuery
  ಗರಿಷ್ಠ ನಾಲ್ಕು ಕ್ಲಸ್ಟರಿಂಗ್ ಕಾಲಮ್‌ಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ ಮತ್ತು ಅವುಗಳ ಕ್ರಮ ಮುಖ್ಯವಾಗಿದೆ: ಕೇವಲ `api_key_name` ಮೇಲಿನ ಫಿಲ್ಟರ್
  ಬ್ಲಾಕ್‌ಗಳನ್ನು ಹೊರಗಿಡುತ್ತದೆ, ಕೇವಲ `status` ಮೇಲಿನ ಫಿಲ್ಟರ್ ಹಾಗೆ ಮಾಡುವುದಿಲ್ಲ.
- **ಐಚ್ಛಿಕ ಪಾರ್ಟಿಷನ್ ಧಾರಣಾವಧಿ**, `partitionExpirationDays` ಮೂಲಕ (0 ಎಲ್ಲವನ್ನೂ ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ), ಇದನ್ನು
  ಟೇಬಲ್ ರಚಿಸುವಾಗ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.

ಎರಡೂ ಸೆಟ್ಟಿಂಗ್‌ಗಳು ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಅನ್ವಯಿಸುತ್ತವೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್ ತನ್ನ ಈಗಿನ ವಿನ್ಯಾಸವನ್ನೇ ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ
ಅವುಗಳನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳಲು ಬಯಸಿದರೆ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಹೊಸ ಟೇಬಲ್ ಐಡಿಗೆ ಸೂಚಿಸಿ.

`tests/unit/log-export-bigquery.test.ts` ಮ್ಯಾಪರ್ ಮತ್ತು ಟೇಬಲ್ ಸ್ಕೀಮಾ ಪರಸ್ಪರ ಹೊಂದಿಕೆಯಾಗಿರುವುದನ್ನು
ಖಚಿತಪಡಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಹೊಸ ಕಾಲ್-ಲಾಗ್ ಕಾಲಮ್ ರಫ್ತಾಗುವಾಗ ಮೌನವಾಗಿ ಕೈಬಿಡಲಾಗುವುದಿಲ್ಲ.

ಬ್ಯಾಚ್‌ಗಳನ್ನು ಸಾಲುಗಳ ಸಂಖ್ಯೆ ಮತ್ತು ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಬೈಟ್‌ಗಳ ಪ್ರಮಾಣ **ಎರಡರ** ಆಧಾರದಲ್ಲಿ ಭಾಗಗಳಾಗಿ ವಿಭಜಿಸಲಾಗುತ್ತದೆ. ಪೇಲೋಡ್‌ಗಳನ್ನು ರಫ್ತು ಮಾಡಿದಾಗ
ಸಾಲುಗಳ ಸಂಖ್ಯೆ ಮಾತ್ರ ಸಾಕಾಗುವುದಿಲ್ಲ: ಪ್ರಾಂಪ್ಟ್‌ಗಳನ್ನು ಹೊಂದಿರುವ 500 ಸಾಲುಗಳು ಹತ್ತಾರು ಮೆಗಾಬೈಟ್‌ಗಳಾಗಿರಬಹುದು, ಮತ್ತು insertAll
10 MB ಮೀರಿದ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. 500 ಸಾಲುಗಳು ಅಥವಾ 9 MB, ಇವೆರಡರಲ್ಲಿ ಯಾವುದು ಮೊದಲು ತಲುಪುತ್ತದೆಯೋ ಅಲ್ಲಿ ಭಾಗಗಳನ್ನು ಮುಚ್ಚಲಾಗುತ್ತದೆ.

## 5. OTLP/HTTP ಟ್ರೇಸ್‌ಗಳ ಗಮ್ಯಸ್ಥಾನ

ಕಾನ್ಫಿಗರೇಶನ್ `type: "otlp-http"` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಇದು ಸಂಗ್ರಹಿತ ಕರೆ ಲಾಗ್‌ಗಳ ನಿಗದಿತ, ಕರ್ಸರ್-ಆಧಾರಿತ
ರಫ್ತು; ಇದು `open-sse/services/routing/otel.ts` ನಲ್ಲಿರುವ ಸಾಧ್ಯವಾದಷ್ಟು ಉತ್ತಮ ಪ್ರಯತ್ನದ ಲೈವ್ ರೂಟಿಂಗ್-ಈವೆಂಟ್ ಸಿಂಕ್ ಅಲ್ಲ.
ಇದು ಆ ಸಿಂಕ್‌ನ ಪರಿಸರ ಚರಗಳು, ಟೈಮರ್‌ಗಳು ಅಥವಾ ಬಫರ್‌ಗಳನ್ನು ಓದುವುದಿಲ್ಲ ಅಥವಾ ಬದಲಾಯಿಸುವುದಿಲ್ಲ.
ಎರಡನ್ನೂ ಸಕ್ರಿಯಗೊಳಿಸಿದರೆ ಎರಡು ಸ್ವತಂತ್ರ ಬಗೆಯ ಸ್ಪ್ಯಾನ್‌ಗಳು ಉತ್ಪತ್ತಿಯಾಗಬಹುದು;
ಈ ಕರೆ-ಲಾಗ್ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಗುರುತಿಸಲು `omniroute.log-export` ಇನ್‌ಸ್ಟ್ರುಮೆಂಟೇಶನ್ ವ್ಯಾಪ್ತಿಯನ್ನು ಬಳಸಿ.

| ಕೀ                       | ಡೀಫಾಲ್ಟ್ / ಉದ್ದೇಶ                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| `endpoint`               | ಪೂರ್ಣ HTTP(S) ಟ್ರೇಸ್‌ಗಳ URL ಅಗತ್ಯ; `/v1/traces` ಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ                  |
| `headers`                | ಐಚ್ಛಿಕ `Name: value` ಸಾಲುಗಳು ಅಥವಾ ಸ್ಟ್ರಿಂಗ್‌ಗಳ JSON ಆಬ್ಜೆಕ್ಟ್; ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ       |
| `requestHeaderAllowlist` | ಖಾಲಿ (ನಿಷ್ಕ್ರಿಯ); ಸ್ಪ್ಯಾನ್ ಗುಣಲಕ್ಷಣಗಳಾಗಿ ಸೆರೆಹಿಡಿಯಬೇಕಾದ ಕ್ಲೈಂಟ್ ಹೆಡರ್ ಹೆಸರುಗಳು/ಪೂರ್ವಪ್ರತ್ಯಯಗಳು |
| `serviceName`            | `omniroute`; ಸಂಪನ್ಮೂಲ `service.name`                                                           |
| `langfuseMapping`        | `false`; Langfuse ಜನರೇಶನ್/ಸೆಷನ್/ಬಳಕೆದಾರ ಗುಣಲಕ್ಷಣಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ                             |
| `identity`               | `pseudonymous`, `keyName`, ಅಥವಾ `none`                                                         |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                        |
| `timeoutMs`              | ಪ್ರತಿ HTTP ಪ್ರಯತ್ನಕ್ಕೆ `30000`                                                                 |

ಸಾಮಾನ್ಯ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಈ ಕ್ಷೇತ್ರಗಳನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ. `paths` ಒಂದು API ಅರೇ ಅಥವಾ ಹೊಸಸಾಲುಗಳು/ಅಲ್ಪವಿರಾಮಗಳಿಂದ
ಬೇರ್ಪಡಿಸಲಾದ ನಿಖರ ಪಥಗಳಿರುವ ಪಠ್ಯಪ್ರದೇಶವನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ. ಸ್ಪಷ್ಟವಾಗಿ ಅನುಮತಿಸದಿದ್ದರೆ ಎಂಬೆಡಿಂಗ್‌ಗಳು, ರೀರ್ಯಾಂಕ್ ಮತ್ತು ಇತರ ಪಥಗಳನ್ನು
ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ. ಬಿಟ್ಟುಬಿಟ್ಟ ಸಾಲುಗಳೂ ಕರ್ಸರ್ ಅನ್ನು ಮುಂದಕ್ಕೆ ಸಾಗಿಸುತ್ತವೆ; ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ರನ್ನರ್‌ನ `exported`/`exportedTotal` ಎಣಿಕೆಗಳು ಸ್ವೀಕರಿಸಿದ ಸ್ಪ್ಯಾನ್‌ಗಳ ಬದಲು, ಫಿಲ್ಟರ್ ಮಾಡಿದ ಸಾಲುಗಳನ್ನೂ ಒಳಗೊಂಡಂತೆ
ಪ್ರಕ್ರಿಯೆಗೊಳಿಸಿದ ಮೂಲ ಸಾಲುಗಳನ್ನು ಎಣಿಸುತ್ತವೆ. ಅದರ IPC/ಕರ್ಸರ್ ಒಪ್ಪಂದವನ್ನು ಬದಲಾಯಿಸದೆ,
ಚೈಲ್ಡ್‌ನಲ್ಲಿ ಫಿಲ್ಟರಿಂಗ್ ಮಾಡಲಾಗುತ್ತದೆ.

URL ಪರಿಶೀಲನೆಯು `src/shared/network/outboundUrlGuard.ts` ನಲ್ಲಿರುವ DB-ರಹಿತ
`parseAndValidateNonMetadataUrl` ಸಹಾಯಕವನ್ನು ಬಳಸುತ್ತದೆ: `block-metadata` ನೀತಿ. ಖಾಸಗಿ URLಗಳನ್ನು ಅನುಮತಿಸಿರುವ
ವೆಬ್‌ಹುಕ್ ಪರಿಶೀಲಕದಲ್ಲಿರುವಂತೆಯೇ ಷರತ್ತುರಹಿತ ಮೆಟಾಡೇಟಾ/ಪ್ರೋಟೋಕಾಲ್/ಅಂತರ್ಗತ-ರುಜುವಾತು ಪರಿಶೀಲನೆಗಳು ಇದರಲ್ಲಿವೆ,
ಆದರೆ ಜಾಗತಿಕ ಫೀಚರ್-ಫ್ಲ್ಯಾಗ್ ಓವರ್‌ರೈಡ್ ಇಲ್ಲದೆಯೇ localhost/LAN ಗುರಿಗಳನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
ಅನುಮತಿಸುತ್ತದೆ. ಇದು ಖಾಸಗಿ HTTP ಎಂಡ್‌ಪಾಯಿಂಟ್‌ಗಳು ಸೇರಿದಂತೆ ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ Langfuse, Phoenix, Tempo ಮತ್ತು Collector
ಎಂಡ್‌ಪಾಯಿಂಟ್‌ಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ. ಕ್ಲೌಡ್-ಮೆಟಾಡೇಟಾ ಹೋಸ್ಟ್‌ಗಳನ್ನು ಯಾವಾಗಲೂ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ.
ಮರುನಿರ್ದೇಶನಗಳನ್ನು ಅನುಸರಿಸಲಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಕಲೆಕ್ಟರ್ ರುಜುವಾತುಗಳನ್ನು ಬೇರೆ ಹೋಸ್ಟ್‌ಗೆ ಮರುನಿರ್ದೇಶಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಪದರೂಪ-ಆಧಾರಿತ URL ಗಾರ್ಡ್‌ನಂತೆಯೇ, ಇದು DNS ರೆಸಲ್ಯೂಶನ್ ಅನ್ನು ಸ್ಥಿರಗೊಳಿಸುವುದಿಲ್ಲ; ಆಪರೇಟರ್ ನಿಯಂತ್ರಣದಲ್ಲಿರುವ
ಹೋಸ್ಟ್‌ಗಳನ್ನು ಮಾತ್ರ ಕಾನ್ಫಿಗರ್ ಮಾಡಿ. ಎಂಡ್‌ಪಾಯಿಂಟ್ ವಿಶ್ವಾಸಾರ್ಹ ನೆಟ್‌ವರ್ಕ್‌ನಲ್ಲಿ ಇಲ್ಲದಿದ್ದಾಗಲೆಲ್ಲ HTTPS ಗೆ ಆದ್ಯತೆ ನೀಡಿ.

`src/lib/usage/callLogs.ts` ನಲ್ಲಿರುವ `saveCallLogOperation` ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಡೀಫಾಲ್ಟ್ ಆಗಿ ಬರೆಯುವ
(ಪೂರ್ಣಗೊಳ್ಳುವ) ಸಮಯಕ್ಕೆ ಹೊಂದಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ರಫ್ತು ಅಂತ್ಯ = ಸಾಲಿನ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಮತ್ತು ಆರಂಭ = ಅಂತ್ಯ − ಅವಧಿ ಎಂದು ಹೊಂದಿಸುತ್ತದೆ
(ಮಿಲಿಸೆಕೆಂಡ್‌ಗಳನ್ನು ದಶಮಾಂಶ ನ್ಯಾನೊಸೆಕೆಂಡ್‌ಗಳಿಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ). ಕರೆ ಮಾಡುವವರು ಒದಗಿಸಿದ ಹಿಂದಿನ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳನ್ನೂ
ಅಂತ್ಯದ ಸಮಯವಾಗಿ ಉಳಿಸಲಾಗುತ್ತದೆ; ಪ್ರತಿ ಸಾಲಿಗೆ ಆರಂಭ/ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಯನ್ನು ಪ್ರತ್ಯೇಕಿಸುವ ಸೂಚಕವಿಲ್ಲ.
null ಅವಧಿಯು ಶೂನ್ಯವಾಗುತ್ತದೆ. ಅಮಾನ್ಯ/ಕಾಣೆಯಾದ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳು ಅನಿರ್ಧಾರಿತ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಸೃಷ್ಟಿಸುವ ಬದಲು
ಬ್ಯಾಚ್ ವಿಫಲಗೊಳ್ಳುವಂತೆ ಮಾಡುತ್ತವೆ. `ttftMs` null ಆಗಿರಬಹುದು ಮತ್ತು ಅದು `omniroute.ttft_ms` ಗೆ ಮ್ಯಾಪ್ ಆಗುತ್ತದೆ.

ಗುಣಲಕ್ಷಣಗಳಲ್ಲಿ `gen_ai.operation.name="chat"`, ಪೂರೈಕೆದಾರ, ವಿನಂತಿಸಿದ/ಪ್ರತಿಕ್ರಿಯೆಯ ಮಾಡೆಲ್,
ಇನ್‌ಪುಟ್/ಔಟ್‌ಪುಟ್ ಟೋಕನ್‌ಗಳು, ಐಚ್ಛಿಕ ಕ್ಯಾಶ್-ಓದು/ಕ್ಯಾಶ್-ರಚನೆ/ತಾರ್ಕಿಕ ಟೋಕನ್‌ಗಳು, HTTP ಸ್ಥಿತಿ,
ಕಾಂಬೊ, ಕ್ಯಾಶ್ ಮೂಲ, ಸೆಷನ್ ಟ್ಯಾಗ್ ಮತ್ತು ಸಹಸಂಬಂಧ ಐಡಿ ಸೇರಿವೆ. ಪೂರ್ಣಾಂಕ OTLP ಮೌಲ್ಯಗಳು ಮತ್ತು ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳು
ದಶಮಾಂಶ ಸ್ಟ್ರಿಂಗ್‌ಗಳಾಗಿರುತ್ತವೆ; ಸ್ಟ್ರಿಂಗ್‌ಗಳು, ಬೂಲಿಯನ್‌ಗಳು ಮತ್ತು ಭಿನ್ನರಾಶಿ ಸಂಖ್ಯೆಗಳು ಅವುಗಳ ಸ್ಥಳೀಯ OTLP ಮೌಲ್ಯ
ರೂಪಾಂತರಗಳನ್ನು ಬಳಸುತ್ತವೆ. ದೋಷ ಸ್ಪ್ಯಾನ್‌ಗಳು ERROR ಸ್ಥಿತಿ ಮತ್ತು ಶುದ್ಧೀಕರಿಸಿದ ಸ್ಥಿತಿ ಸಂದೇಶವನ್ನು ಹೊಂದಿರುತ್ತವೆ. ಪ್ರಮಾಣಿತ
ದಾಖಲೆಯಲ್ಲಿ ಅಪ್‌ಸ್ಟ್ರೀಮ್ ಹೋಸ್ಟ್ URL ಇಲ್ಲ, ಆದ್ದರಿಂದ ಕಲೆಕ್ಟರ್ ಅನ್ನು ಮಾಡೆಲ್ ಸರ್ವರ್ ಎಂದು ತಪ್ಪಾಗಿ
ಗುರುತಿಸುವ ಬದಲು `server.address` ಅನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ವೆಚ್ಚವನ್ನು ರಫ್ತು ಮಾಡಲಾಗುವುದಿಲ್ಲ.

`includeBodies=true` ಮಾತ್ರ ವಿಷಯವನ್ನು ಲೋಡ್ ಮಾಡುತ್ತದೆ. `langfuseMapping=false` ಇದ್ದಾಗ,
`gen_ai.input.messages` / `gen_ai.output.messages` ಮರುರೂಪಿಸಿದ semconv ಸಂದೇಶಗಳ ಅರೇ ಬದಲಾಗಿ,
OmniRoute ಸಂಗ್ರಹಿಸಿದಂತೆ ಶುದ್ಧೀಕರಿಸಿದ ವಿನಂತಿ/ಪ್ರತಿಕ್ರಿಯೆ ಬಾಡಿ JSON ಅನ್ನು ಹೊತ್ತೊಯ್ಯುತ್ತವೆ
(ಪಾರ್ಸ್ ಮಾಡಬಹುದಾದಾಗ ಪ್ರಮಾಣಿತ ರೂಪಕ್ಕೆ ತರಲಾಗುತ್ತದೆ). ಕಡಿತಗೊಳಿಸಿದ/JSON ಅಲ್ಲದ ಬಾಡಿಗಳು ಕಚ್ಚಾ ಪಠ್ಯವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ. `langfuseMapping=true` ಇದ್ದಾಗ,
ಬಾಡಿಗಳನ್ನು `langfuse.observation.input` / `langfuse.observation.output` ಆಗಿ ಮಾತ್ರ ಹೊರಹಾಕಲಾಗುತ್ತದೆ;
ಪ್ರತಿ ಬಾಡಿಯನ್ನು ಒಮ್ಮೆ ಮಾತ್ರ ಕಳುಹಿಸುವಂತೆ `gen_ai.*.messages` ಗುಣಲಕ್ಷಣಗಳನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ಎರಡೂ ಮೋಡ್‌ಗಳು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ವಿಷಯ-ಲೋಡಿಂಗ್ ಪಥದಿಂದ `maxBodyBytes` ಅನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯುತ್ತವೆ;
`omniroute.bodies_truncated=true` ಕಡಿತಗೊಳಿಸುವಿಕೆಯನ್ನು ಸೂಚಿಸುತ್ತದೆ.
ಈ ಗಮ್ಯಸ್ಥಾನವು ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಪೈಪ್‌ಲೈನ್ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್‌ಗಳು ಅಥವಾ ಶುದ್ಧೀಕರಿಸದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಓದುಗಳನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ;
ಐಚ್ಛಿಕ ವಿನಂತಿ-ಹೆಡರ್ ಸೆರೆಹಿಡಿಯುವಿಕೆಯು ಕೆಳಗೆ ವಿವರಿಸಿದ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲೋಡ್ ಮಾಡಿದ ಕ್ಲೈಂಟ್ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ಅನ್ನು ಬಳಸುತ್ತದೆ.
ಬಾಡಿಗಳನ್ನು ರಫ್ತು ಮಾಡುವಾಗ ಗಂಟೆಗೊಮ್ಮೆ ಬಾಕಿ ಕೆಲಸವನ್ನು ಸಂಗ್ರಹಿಸುವ ಬದಲು,
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ನಂತಹ ನಿಮಿಷ-ಮಟ್ಟದ ಆವರ್ತನವನ್ನು ಬಳಸಿ.

### ಐಚ್ಛಿಕ ಕ್ಲೈಂಟ್ ವಿನಂತಿ ಹೆಡರ್‌ಗಳು

ಹೆಡರ್ ಸೆರೆಹಿಡಿಯುವಿಕೆಯು **ಡೀಫಾಲ್ಟ್ ಆಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ**. ಗಮ್ಯಸ್ಥಾನದ ಕಾನ್ಫಿಗರೇಶನ್‌ನಲ್ಲಿ `requestHeaderAllowlist` ಅನ್ನು ಹೊಂದಿಸಿ
ಮತ್ತು **ಪ್ರಾಂಪ್ಟ್‌ಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ರಫ್ತು ಮಾಡಿ** ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ (ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ `includeBodies: true`).
ಅನುಮತಿ ಪಟ್ಟಿಯು API ಅರೇ ಅಥವಾ ಹೊಸಸಾಲು/ಅಲ್ಪವಿರಾಮದಿಂದ ಬೇರ್ಪಡಿಸಿದ ಹೆಸರುಗಳಿರುವ ಪಠ್ಯಪ್ರದೇಶವನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ಒಂದು ಕೊನೆಯ `*` ಖಾಲಿಯಲ್ಲದ ಹೆಡರ್-ಹೆಸರಿನ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಆಯ್ಕೆಮಾಡುವ ಸಂದರ್ಭವನ್ನು ಹೊರತುಪಡಿಸಿ, ಹೆಸರುಗಳು ದೊಡ್ಡಕ್ಷರ-ಚಿಕ್ಕಕ್ಷರ ಭೇದವಿಲ್ಲದೆ ಮತ್ತು ನಿಖರವಾಗಿ ಹೊಂದಿಕೆಯಾಗುತ್ತವೆ.
ಕೇವಲ `*`, ಮಧ್ಯದಲ್ಲಿ ಬರುವ ವೈಲ್ಡ್‌ಕಾರ್ಡ್‌ಗಳು ಮತ್ತು ಅಮಾನ್ಯ HTTP ಹೆಡರ್ ಹೆಸರುಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.
ಗರಿಷ್ಠ 64 ಆಯ್ಕೆಕಾರಕಗಳಿರಬಹುದು; ಪ್ರತಿಯೊಂದರ ಹೆಸರು/ಪೂರ್ವಪ್ರತ್ಯಯವು ಗರಿಷ್ಠ 256 ASCII ಬೈಟ್‌ಗಳಾಗಿರಬಹುದು.
ಈ ಸೆಟ್ಟಿಂಗ್ `headers` ನಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿದೆ; `headers` ಎಕ್ಸ್‌ಪೋರ್ಟರ್ ಅನ್ನು ಕಲೆಕ್ಟರ್‌ಗೆ ದೃಢೀಕರಿಸುತ್ತದೆ.

ಕ್ಯಾಪ್ಚರ್ ಕೇವಲ `pipeline_client_request` ಅನ್ನು ಓದುತ್ತದೆ; ಇದನ್ನು ಉಳಿಸಿದ ವಿವರವಾದ ಪೈಪ್‌ಲೈನ್‌ನ
`clientRawRequest` ನಿಂದ (ಅಥವಾ ಹಳೆಯ `clientRequest` ನಿಂದ) ತುಂಬಲಾಗುತ್ತದೆ. ಇದು ಎಂದಿಗೂ ಪೂರೈಕೆದಾರರ ವಿನಂತಿ ಹೆಡರ್‌ಗಳನ್ನು ಪರ್ಯಾಯವಾಗಿ ಬಳಸುವುದಿಲ್ಲ.
ವಿನಂತಿಯನ್ನು ದಾಖಲಿಸಿದಾಗ ವಿವರವಾದ ಪೈಪ್‌ಲೈನ್ ಲಾಗಿಂಗ್ ಸಕ್ರಿಯವಾಗಿರಬೇಕು.
`includeBodies` ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದರೆ, ಅಥವಾ ಕ್ಲೈಂಟ್-ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ JSON ಇಲ್ಲದಿದ್ದರೆ, ಹಾಳಾಗಿದ್ದರೆ ಅಥವಾ ಮೊಟಕುಗೊಂಡಿದ್ದರೆ, ಯಾವುದೇ ಹೆಡರ್
ಗುಣಲಕ್ಷಣಗಳನ್ನು ಹೊರಹಾಕಲಾಗುವುದಿಲ್ಲ. `maxBodyBytes` ಹೆಚ್ಚಿಸುವುದರಿಂದ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ಮೊಟಕುಗೊಳ್ಳುವುದನ್ನು ತಪ್ಪಿಸಬಹುದು;
ಆದರೆ ಎಂದಿಗೂ ಉಳಿಸದ ವಿವರಗಳನ್ನು ಅದು ಮರುಸ್ಥಾಪಿಸಲಾರದು. 1 MiB ಗಿಂತ ದೊಡ್ಡದಾದ ಅಥವಾ
256 ಕ್ಕಿಂತ ಹೆಚ್ಚು ಹೆಡರ್ ನಮೂದುಗಳನ್ನು ಹೊಂದಿರುವ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ಅನ್ನು ಕಡೆಗಣಿಸಲಾಗುತ್ತದೆ. ಹೆಡರ್ ಕ್ಯಾಪ್ಚರ್ ಜೊತೆಗೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಪ್ರಾಂಪ್ಟ್/ಪ್ರತಿಕ್ರಿಯೆ ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಸಕ್ರಿಯವಾಗಿಯೇ ಇರುತ್ತದೆ;
ಅನುಮತಿ ಪಟ್ಟಿಯು ಹೆಡರ್‌ಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತವಾದ ಹೈಡ್ರೇಶನ್ ಮೋಡ್ ಅನ್ನು ಒದಗಿಸುವುದಿಲ್ಲ.

ಆಯ್ಕೆಮಾಡಿದ ಮೌಲ್ಯಗಳು `http.request.header.<full lowercase header name>` OTLP ಸ್ಟ್ರಿಂಗ್ ಅರೇಗಳಾಗುತ್ತವೆ,
ಒಂದೇ ಸ್ಟ್ರಿಂಗ್ ಇದ್ದರೂ ಸಹ. ಉದಾಹರಣೆಗೆ, `X-OmniRoute-Meta-Team: example-team` ಎಂಬುದು
`http.request.header.x-omniroute-meta-team` ಆಗುತ್ತದೆ, ಜೊತೆಗೆ
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}` ಇರುತ್ತದೆ.
ಪೂರ್ಣ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ: ಇವು ಸಾಮಾನ್ಯ ಹೆಡರ್‌ಗಳಾಗಿವೆ; ಯಾವುದೇ ವ್ಯವಹಾರ-ಕ್ಷೇತ್ರ ಪಾರ್ಸಿಂಗ್ ಅಥವಾ
`omniroute.metadata.*` / Langfuse ಮೆಟಾಡೇಟಾ ಪರಿವರ್ತನೆ ಇರುವುದಿಲ್ಲ. `langfuseMapping` ಹೆಡರ್‌ಗಳ
ಅರ್ಥವ್ಯವಸ್ಥೆಯನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ. ಆಯ್ಕೆಮಾಡಿದ ಏಕ-ಮೌಲ್ಯದ `User-Agent` ಪ್ರಮಾಣಿತ ಸ್ಕೇಲರ್
`user_agent.original` ಅನ್ನೂ ಹೊಂದಿಸುತ್ತದೆ. ಒಂದೇ ಮೌಲ್ಯದೊಳಗಿನ ಅಲ್ಪವಿರಾಮಗಳ ಆಧಾರದಲ್ಲಿ ವಿಭಜಿಸಲಾಗುವುದಿಲ್ಲ. ದೊಡ್ಡಕ್ಷರ-ಚಿಕ್ಕಕ್ಷರ ರೂಪಾಂತರಗಳು ಉಳಿಸಿದ
ನಮೂದುಗಳ ಕ್ರಮದಲ್ಲಿ ವಿಲೀನಗೊಳ್ಳುತ್ತವೆ; ಯಾವುದೇ ಅಮಾನ್ಯ ರೂಪಾಂತರವಿದ್ದರೆ ಆ ಸಂಪೂರ್ಣ ಹೆಡರ್ ಅನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ಗುಣಲಕ್ಷಣಗಳನ್ನು ಚಿಕ್ಕಕ್ಷರದ ಹೆಸರಿನ ಕ್ರಮದಲ್ಲಿ ಜೋಡಿಸಲಾಗುತ್ತದೆ.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-ಕೀ ಹೆಡರ್‌ಗಳು, auth/token/secret/password/credential
ಗುರುತುಗಳನ್ನು ಹೊಂದಿರುವ ಹೆಸರುಗಳು ಮತ್ತು ಆಂತರಿಕ ಗೇಟ್‌ವೇ ಪ್ರವೇಶ ರುಜುವಾತುಗಳನ್ನು ಯಾವಾಗಲೂ
ಹೊರಗಿಡಲಾಗುತ್ತದೆ; ಆಯ್ಕೆಮಾಡಿದ್ದರೂ ಅಥವಾ ಸಂಗ್ರಹಣೆಯಲ್ಲಿ ಭಾಗಶಃ ಮರೆಮಾಚಿದ್ದರೂ ಸಹ. ತಿಳಿದಿರುವ ಪ್ರವೇಶ ರುಜುವಾತು ಮಾದರಿಗಳು
ಹಂಚಿಕೆಯ ಪ್ರವೇಶ ರುಜುವಾತು ಪತ್ತೆಕಾರಕವನ್ನು ಮರುಬಳಸುತ್ತವೆ; ಮರೆಮಾಚುವಿಕೆಯ ಗುರುತುಗಳನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ, ಸುರಕ್ಷಿತ ಮೌಲ್ಯಗಳೆಂದು ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ.
ಸ್ಟ್ರಿಂಗ್‌ಗಳು ಮತ್ತು ಖಾಲಿಯಲ್ಲದ ಸ್ಟ್ರಿಂಗ್ ಅರೇಗಳನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; ಸಂಖ್ಯೆಗಳು ಅಥವಾ ಆಬ್ಜೆಕ್ಟ್‌ಗಳನ್ನು ಪರಿವರ್ತಿಸಲಾಗುವುದಿಲ್ಲ.
ಅಮಾನ್ಯ ಹೆಸರುಗಳು, ಪ್ರೋಟೋಟೈಪ್ ಕೀಗಳು, ನಿಯಂತ್ರಣ ಅಕ್ಷರಗಳು (ಅಡ್ಡ ಟ್ಯಾಬ್ ಹೊರತುಪಡಿಸಿ) ಮತ್ತು ತಪ್ಪಾಗಿ ರೂಪುಗೊಂಡ Unicode ಅನ್ನು
ಬ್ಯಾಚ್ ವಿಫಲಗೊಳಿಸದೆ ಅಥವಾ ಅವುಗಳ ವಿಷಯವನ್ನು ದೋಷಗಳಲ್ಲಿ ಪ್ರತಿಬಿಂಬಿಸದೆ ಕಡೆಗಣಿಸಲಾಗುತ್ತದೆ.

ಪ್ರತಿ ಸ್ಪ್ಯಾನ್ ಗರಿಷ್ಠ 32 ಹೆಡರ್‌ಗಳನ್ನು, ಪ್ರತಿ ಹೆಡರ್‌ಗೆ 16 ಮೌಲ್ಯಗಳನ್ನು, ಪ್ರತಿ ಮೌಲ್ಯಕ್ಕೆ 4096 UTF-8 ಬೈಟ್‌ಗಳನ್ನು,
ಮತ್ತು ಕ್ಯಾಪ್ಚರ್ ಮಾಡಿದ ಹೆಡರ್ ಹೆಸರುಗಳು ಹಾಗೂ ಮೌಲ್ಯಗಳಾದ್ಯಂತ ಒಟ್ಟು 16384 UTF-8 ಬೈಟ್‌ಗಳನ್ನು ಕ್ಯಾಪ್ಚರ್ ಮಾಡುತ್ತದೆ. ಮಿತಿಮೀರಿದ/ಅಮಾನ್ಯ ಹೆಡರ್‌ಗಳನ್ನು
ಸಂಪೂರ್ಣವಾಗಿ ಕೈಬಿಡಲಾಗುತ್ತದೆ, ಮೊಟಕುಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ. ಆಯ್ಕೆಯು ನಿರ್ವಾಹಕರ ಗೌಪ್ಯತಾ ನಿರ್ಧಾರವಾಗಿದೆ: ಸುರಕ್ಷಿತವಾಗಿ ಕಾಣುವ ಹೆಸರುಗಳೂ
ವೈಯಕ್ತಿಕ ಡೇಟಾವನ್ನು ಹೊಂದಿರಬಹುದು, ಮತ್ತು ಈ ಮಿತಿಗಳು/ಪತ್ತೆಕಾರಕಗಳು ಸಾಮಾನ್ಯ PII ಶುದ್ಧೀಕರಣ ಸಾಧನವಲ್ಲ.

### ವಿತರಣೆಯ ಮಿತಿಗಳು

ವಿನಂತಿಗಳನ್ನು 500 ಸ್ಪ್ಯಾನ್‌ಗಳು ಮತ್ತು ಎನ್‌ವೆಲಪ್ ಸೇರಿದಂತೆ 4 MiB UTF-8 JSON ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ.
ಕರ್ಸರ್ ಬ್ಯಾಚ್‌ನ ಮೊದಲ ವಿನಂತಿಗೂ ಮೊದಲು ಅನುಮತಿಸಲಾದ ಪ್ರತಿ ಸ್ಪ್ಯಾನ್‌ನ ಗಾತ್ರವನ್ನು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಪ್ರತ್ಯೇಕ
ಸ್ಪ್ಯಾನ್ ಮಿತಿಗಿಂತ ದೊಡ್ಡದಾಗಿದ್ದರೆ, ಆ ಬ್ಯಾಚ್‌ನ ಯಾವುದೇ ಭಾಗವನ್ನು ಕಳುಹಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು
`maxBodyBytes` ಕಡಿಮೆ ಮಾಡುವ ಮಾರ್ಗದರ್ಶನದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; ಅದನ್ನು ಮೌನವಾಗಿ ಕೈಬಿಡಲಾಗುವುದಿಲ್ಲ. ಪೂರ್ವಪರಿಶೀಲನೆಯು ದಾಖಲೆ ಉಲ್ಲೇಖಗಳು ಮತ್ತು
ಬೈಟ್ ಎಣಿಕೆಗಳನ್ನು ಮಾತ್ರ ಉಳಿಸಿಕೊಂಡು, ಪ್ರತಿ ತಾತ್ಕಾಲಿಕ ಸ್ಪ್ಯಾನ್/JSON ಅನ್ನು ತ್ಯಜಿಸುತ್ತದೆ; ಬ್ಯಾಚ್‌ನ ಎರಡನೇ ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಪ್ರತಿಯನ್ನು
ಇಟ್ಟುಕೊಳ್ಳುವ ಬದಲು, ಸೀಮಿತ ಗಾತ್ರದ ಚಂಕ್‌ಗಳಿಗಾಗಿ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಮರುನಿರ್ಮಿಸಲಾಗುತ್ತದೆ. HTTP 408/429/5xx, ನೆಟ್‌ವರ್ಕ್ ವೈಫಲ್ಯಗಳು ಮತ್ತು ಸಮಯಮೀರಿಕೆಗಳಿಗೆ ಗರಿಷ್ಠ
ಮೂರು ಪ್ರಯತ್ನಗಳನ್ನು ಮಾಡಲಾಗುತ್ತದೆ, 250/500 ms ಘಾತೀಯ ಹಿಂಜರಿಕೆ ವಿಳಂಬದೊಂದಿಗೆ. `Retry-After` ಸೆಕೆಂಡುಗಳು ಅಥವಾ HTTP ದಿನಾಂಕಗಳು
ವಿಳಂಬವನ್ನು 5 ಸೆಕೆಂಡುಗಳವರೆಗೆ ವಿಸ್ತರಿಸಬಹುದು. ಇತರ ಸ್ಥಿತಿಗಳು ತಕ್ಷಣ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ. OTLP 2xx ಭಾಗಶಃ ತಿರಸ್ಕಾರವೂ ಕಳೆದುಹೋದ ಸ್ಪ್ಯಾನ್ ಅನ್ನು
ಸ್ವೀಕರಿಸಲಾಗಿದೆ ಎಂದು ದೃಢೀಕರಿಸುವ ಬದಲು ದೋಷವನ್ನು ಎಸೆಯುತ್ತದೆ; ಖಾಲಿ ಅಥವಾ ಮಾನ್ಯ JSON ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣಗಳನ್ನು ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ,
ಪ್ರತಿಕ್ರಿಯೆ ಓದುವಿಕೆಗೆ 64 KiB ಮಿತಿಯೊಂದಿಗೆ.

ದೋಷಗಳು ಎಕ್ಸ್‌ಪೋರ್ಟರ್‌ಗೆ ಸೇರಿದ ಸಂಗತಿಗಳನ್ನು ಮಾತ್ರ ಒಳಗೊಂಡಿರುತ್ತವೆ: HTTP ಸ್ಥಿತಿ, ಮರುಪ್ರಯತ್ನ ವರ್ಗ, ಪ್ರಯತ್ನಗಳು ಮತ್ತು ಕಳುಹಿಸಿದ ಸ್ಪ್ಯಾನ್
ಎಣಿಕೆಗಳು, ಅಥವಾ ನಿಗದಿತ ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣ/ನೆಟ್‌ವರ್ಕ್ ವೈಫಲ್ಯದ ಪಠ್ಯ. ಕಲೆಕ್ಟರ್ ಪ್ರತಿಕ್ರಿಯೆಯ ಬಾಡಿಗಳು,
ಭಾಗಶಃ ಯಶಸ್ಸಿನ ಎಣಿಕೆಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಹೆಡರ್‌ಗಳನ್ನು ದೋಷಗಳು, ಲಾಗ್‌ಗಳು ಅಥವಾ
ಡ್ಯಾಶ್‌ಬೋರ್ಡ್‌ಗೆ ಎಂದಿಗೂ ನಕಲಿಸಲಾಗುವುದಿಲ್ಲ. ವಿಫಲವಾದ ಅಥವಾ ಭಾಗಶಃ ಸ್ವೀಕರಿಸಲಾದ ಬ್ಯಾಚ್‌ಗೆ ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣ ನೀಡಲಾಗುವುದಿಲ್ಲ: ಗಮ್ಯಸ್ಥಾನವು
ಆ ಸ್ಥಿತಿಯೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತಿದೆ ಎಂದು ತೋರಿಸುತ್ತದೆ, ಕರ್ಸರ್ ಕೊನೆಯದಾಗಿ ದೃಢೀಕರಿಸಲಾದ ಬ್ಯಾಚ್‌ನಲ್ಲೇ ಉಳಿಯುತ್ತದೆ, ಮತ್ತು ಮುಂದಿನ ಚಾಲನೆಯು
ಅದೇ ಸಾಲುಗಳನ್ನು ಮತ್ತೆ ಕಳುಹಿಸುತ್ತದೆ. ಕಲೆಕ್ಟರ್ ಅಥವಾ ಸಂರಚನೆಯನ್ನು ಸರಿಪಡಿಸುವವರೆಗೆ ಶಾಶ್ವತ ಸ್ಥಿತಿಗಳು ವಿಫಲಗೊಳ್ಳುತ್ತಲೇ ಇರುತ್ತವೆ.
ಪ್ರತಿಕ್ರಿಯೆ ವಿವರಗಳಿಗಾಗಿ ಕಲೆಕ್ಟರ್‌ನ ಸ್ವಂತ ಲಾಗ್‌ಗಳನ್ನು ಬಳಸಿ. ಕಾಲ್-ಲಾಗ್ ದೋಷ ಸಾರಾಂಶಗಳು
ತಮ್ಮ ಪ್ರತ್ಯೇಕ ಮರೆಮಾಚುವಿಕೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.
`prepare()` ಯಾವುದನ್ನೂ ಸಿದ್ಧಪಡಿಸುವುದಿಲ್ಲ; ಪರೀಕ್ಷೆಯು ನಿಖರವಾಗಿ `{"resourceSpans":[]}` ಅನ್ನು ಪೋಸ್ಟ್ ಮಾಡಿ,
ಕಾಲ್-ಲಾಗ್ ಸ್ಪ್ಯಾನ್‌ಗಳನ್ನು ಬರೆಯದೆ HTTP ಸ್ಥಿತಿಯನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

ಟ್ರೇಸ್ ಐಡಿಗಳು ಮತ್ತು ಸ್ಪ್ಯಾನ್ ಐಡಿಗಳು ಕ್ರಮವಾಗಿ
`"omniroute.trace\\0" + callLogId` ಮತ್ತು `"omniroute.span\\0" + callLogId` ಮೇಲಿನ SHA-256 ನ ಮೊದಲ 32/16 ಹೆಕ್ಸ್ ಅಂಕೆಗಳಾಗಿವೆ. ಮರುಕಳುಹಿಸುವಿಕೆಗಳು
ಒಂದೇ ರೀತಿಯ ಐಡಿಗಳನ್ನು ಹೊಂದಿರುತ್ತವೆ. ಇದು ನಕಲು ನಿವಾರಣೆಯ ಖಾತರಿಯಲ್ಲ: Langfuse
v4 ಇಂಜೆಶನ್ ಸೇರಿದಂತೆ ಕೆಲವು ಬ್ಯಾಕ್‌ಎಂಡ್‌ಗಳು ಒಂದೇ ಐಡಿಯ ಸ್ಪ್ಯಾನ್‌ಗಳ ನಕಲುಗಳನ್ನು ನಿವಾರಿಸುವುದಿಲ್ಲ. ಕ್ರ್ಯಾಶ್ ಅಥವಾ ಭಾಗಶಃ ಚಂಕ್ ವೈಫಲ್ಯವು
ಸ್ವೀಕೃತಿ ದೃಢೀಕರಣ ಪಡೆಯದ ಒಂದೇ ಕರ್ಸರ್ ಬ್ಯಾಚ್ ಅನ್ನು ಗರಿಷ್ಠವಾಗಿ ಮರುಕಳುಹಿಸಬಹುದು; ಆ ಸಂಪೂರ್ಣ ಬ್ಯಾಚ್ ನಕಲಾಗಬಹುದು,
ಅದರ ಕೊನೆಯ HTTP ಚಂಕ್ ಮಾತ್ರವಲ್ಲ. ಈ ಹೊಂದಾಣಿಕೆಯನ್ನು ಮನಸ್ಸಿನಲ್ಲಿಟ್ಟುಕೊಂಡು ಕರ್ಸರ್ ಬ್ಯಾಚ್ ಗಾತ್ರವನ್ನು ಆಯ್ಕೆಮಾಡಿ.

### Langfuse ಉದಾಹರಣೆ

ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ Langfuse ಇನ್‌ಸ್ಟನ್ಸ್‌ಗಾಗಿ ಈ ಕ್ಷೇತ್ರಗಳನ್ನು ಸಂರಚಿಸಿ:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

ನಿಖರವಾದ `public-key:secret-key` ಸ್ಟ್ರಿಂಗ್‌ನ Base64 ರೂಪವಾಗಿ Authorization ಮೌಲ್ಯವನ್ನು ಸ್ಥಳೀಯವಾಗಿ ರಚಿಸಿ
(ಉದಾಹರಣೆಗೆ `Buffer.from(publicKey + ":" + secretKey).toString("base64")` ಬಳಸಿ).
ನಿಜವಾದ ಪ್ರವೇಶ ರುಜುವಾತುಗಳನ್ನು ಲಾಗ್‌ಗಳು, ಸ್ಕ್ರೀನ್‌ಶಾಟ್‌ಗಳು ಅಥವಾ ಇಶ್ಯೂಗಳಲ್ಲಿ ಅಂಟಿಸಬೇಡಿ. ಮ್ಯಾಪಿಂಗ್ ಸ್ವಯಂಚಾಲಿತವಾಗಿ
`x-langfuse-ingestion-version: 4` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ; Authorization ಅನ್ನು ಇನ್ನೂ `headers` ನಲ್ಲಿ ಒದಗಿಸಲಾಗುತ್ತದೆ.
ಹೆಡರ್‌ಗಳು ಮತ್ತು ರಚಿಸಲಾದ ಗುರುತಿನ ಸಾಲ್ಟ್ ಎರಡೂ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ರಹಸ್ಯ-ಕ್ಷೇತ್ರ
ಕಾರ್ಯವಿಧಾನ ಮತ್ತು API ಪ್ಲೇಸ್‌ಹೋಲ್ಡರ್‌ಗಳನ್ನು ಬಳಸುತ್ತವೆ; `STORAGE_ENCRYPTION_KEY` ಅಗತ್ಯವಾಗಿದೆ.

ಮ್ಯಾಪಿಂಗ್‌ನಲ್ಲಿ ಜನರೇಷನ್ ಪ್ರಕಾರ/ಮಾದರಿ, JSON ಬಳಕೆಯ ವಿವರಗಳು (ಇನ್‌ಪುಟ್/ಔಟ್‌ಪುಟ್/ಒಟ್ಟು ಮತ್ತು ಲಭ್ಯವಿರುವ
ಕ್ಯಾಶ್ ಕೀಗಳು), JSON ಇನ್‌ಪುಟ್/ಔಟ್‌ಪುಟ್ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್‌ಗಳು, ERROR/DEFAULT ಮಟ್ಟ, ಶುದ್ಧೀಕರಿಸಿದ ಸ್ಥಿತಿ ಸಂದೇಶ,
ಟ್ರೇಸ್ ಹೆಸರು, ಸೆಷನ್ ಐಡಿ, ಐಚ್ಛಿಕ ಪರಿಸರ ಮತ್ತು ಪ್ರೊವೈಡರ್, ವಿನಂತಿಸಿದ ಮಾದರಿ, ಪಾಥ್, ಕಾಂಬೊ, ಕ್ಯಾಶ್
ಮೂಲ ಮತ್ತು ಸ್ಥಿತಿಗಾಗಿ ಫಿಲ್ಟರ್ ಮಾಡಬಹುದಾದ
`langfuse.observation.metadata.<key>` ಸೇರಿಸಲಾಗುತ್ತದೆ. TTFT ತಿಳಿದಿದ್ದು, ಅದು ಅವಧಿಯೊಳಗೆ ಇದ್ದಾಗ ಮಾತ್ರ
`langfuse.observation.completion_start_time` ಅನ್ನು ಪ್ರಾರಂಭ + TTFT ಸಮಯಕ್ಕೆ ISO 8601 ಸ್ವರೂಪದಲ್ಲಿ ಹೊಂದಿಸಲಾಗುತ್ತದೆ. ಯಾವುದೇ ವೆಚ್ಚದ ಗುಣಲಕ್ಷಣಗಳನ್ನು ಕಳುಹಿಸಲಾಗುವುದಿಲ್ಲ.

ಗುರುತಿನ ವಿಧಾನಗಳು `langfuse.user.id` ಗೆ ಅನ್ವಯಿಸುತ್ತವೆ:

- `pseudonymous` (ಡೀಫಾಲ್ಟ್): ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಯಾದೃಚ್ಛಿಕವಾದ
  32-ಬೈಟ್ ಸಾಲ್ಟ್ ಬಳಸಿ API ಕೀಯ ಆಂತರಿಕ ಐಡಿಯ HMAC-SHA256. ಸಾಲ್ಟ್ ಇಲ್ಲದಿದ್ದರೆ ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಅದನ್ನು ಉತ್ಪಾದಿಸಿ,
  `identitySalt` ಆಗಿ ಎನ್‌ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ; ಅದನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು ಸಂಪಾದನೆಗಳ ಸಮಯದಲ್ಲಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. ಮೂಲ ಕೀ ಐಡಿಗಳನ್ನು ಎಂದಿಗೂ
  ಸ್ಪ್ಯಾನ್ ಗುಣಲಕ್ಷಣಗಳಲ್ಲಿ ಇರಿಸಲಾಗುವುದಿಲ್ಲ. ಗಮ್ಯಸ್ಥಾನದ ಸಾಲ್ಟ್ ಅನ್ನು ಮರುರಚಿಸುವುದು/ರೊಟೇಟ್ ಮಾಡುವುದು ಗುರುತುಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
- `keyName`: ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ API ಕೀ ಹೆಸರು; ಇದು ಆ ಆಪರೇಟರ್ ಲೇಬಲ್ ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.
- `none`: ಬಳಕೆದಾರ ಐಡಿ ಇಲ್ಲ. ಸೆಷನ್ ಟ್ಯಾಗ್‌ಗಳು ಇದ್ದಾಗ ಅವುಗಳನ್ನು ಇನ್ನೂ ರಫ್ತು ಮಾಡಲಾಗುತ್ತದೆ; ಈ ವಿಧಾನಗಳು
  ಯಾವುದೇ ಪ್ರಾಂಪ್ಟ್ ವಿಷಯವನ್ನು ಅಥವಾ ಆಪರೇಟರ್ ಒದಗಿಸಿದ ಸೆಷನ್/ಸಹಸಂಬಂಧ ಲೇಬಲ್‌ಗಳನ್ನು ಅನಾಮಧೇಯಗೊಳಿಸುವುದಿಲ್ಲ.

### ಬ್ಯಾಕ್‌ಫಿಲ್ ಇಲ್ಲದೆ ಪ್ರಾರಂಭಿಸುವುದು

ರಚನೆಯ ಸಮಯದಲ್ಲಿ ಮಾತ್ರ, **ಪ್ರಸ್ತುತ ಸ್ಥಾನದಿಂದ ಪ್ರಾರಂಭಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲಾಗ್‌ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಿ)** ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ ಅಥವಾ
ರಚನೆಯ API ಪೇಲೋಡ್‌ನ ಮೇಲಿನ ಹಂತದಲ್ಲಿ `startFromCurrentPosition: true` ಅನ್ನು ನೀಡಿ. ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕರ್ಸರ್
ಸಹಾಯಕಗಳನ್ನು ಬಳಸಿ, ಯಾವುದೇ ಮೈಗ್ರೇಷನ್ ಇಲ್ಲದೆ, `cursor_row_id` ಅನ್ನು ಪ್ರಸ್ತುತ ಉಳಿಸಿಕೊಂಡಿರುವ ಕಾಲ್-ಲಾಗ್‌ನ ಗರಿಷ್ಠ rowid ಗೆ
ಆರಂಭಿಸುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ false ಆಗಿರುತ್ತದೆ (ಕರ್ಸರ್ 0 ಮತ್ತು ಉಳಿಸಿಕೊಂಡಿರುವ ಇತಿಹಾಸದ ಬ್ಯಾಕ್‌ಫಿಲ್).
ಇದು ನವೀಕರಣದ ಸಮಯದಲ್ಲಿ ಕರ್ಸರ್ ಮರುಹೊಂದಿಸುವ ಸೆಟ್ಟಿಂಗ್ ಅಲ್ಲ.

ಹಂಚಿಕೆಯ `ttftMs` ಸೇರ್ಪಡೆಯು BigQuery ಮ್ಯಾಪರ್
ಮತ್ತು ಹೊಸ-ಟೇಬಲ್ ಸ್ಕೀಮಾಗೆ nullable `ttft_ms` ಕಾಲಮ್ ಅನ್ನೂ ಸೇರಿಸುತ್ತದೆ: ಅದರ ಸ್ಕೀಮಾ ಪರೀಕ್ಷೆಯು ಪ್ರತಿ ಕ್ಯಾನಾನಿಕಲ್ ರೆಕಾರ್ಡ್ ಫೀಲ್ಡ್‌ಗೆ
ಒಂದು ಕಾಲಮ್ ಇರಬೇಕೆಂದು ನಿರೀಕ್ಷಿಸುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಟೇಬಲ್‌ಗಳು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ರಫ್ತು ಮಾಡುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ: `prepare()` ಟೇಬಲ್ ಸ್ಕೀಮಾವನ್ನು ಓದುತ್ತದೆ ಮತ್ತು
ಆ ಕಾಲಮ್ ಇಲ್ಲದಿದ್ದಾಗ `ttft_ms` ಅನ್ನು ಮಾತ್ರ ಹೊರಗಿಡುತ್ತದೆ. ಮುಂದಿನ ಚಾಲನೆಯಲ್ಲಿ TTFT ಪಡೆಯಲು nullable INT64 ಕಾಲಮ್ ಅನ್ನು ಸೇರಿಸಿ,
ಅಥವಾ ಹೊಸ ಟೇಬಲ್ ಬಳಸಿ. ಯಾವುದೇ PATCH, ಸ್ವಯಂಚಾಲಿತ ಸ್ಕೀಮಾ ಬದಲಾವಣೆ ಅಥವಾ ಹೆಚ್ಚುವರಿ
ಅನುಮತಿಗಳು ಅಗತ್ಯವಿಲ್ಲ; ಇತರ ಎಲ್ಲಾ ಸಾಲಿನ ಫೀಲ್ಡ್‌ಗಳು ಕಟ್ಟುನಿಟ್ಟಾದ ಸ್ಕೀಮಾ ಪರಿಶೀಲನೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

## 6. ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸುವುದು

1. `LogExportDestinationType` ಅನ್ನು ಎಕ್ಸ್‌ಪೋರ್ಟ್ ಮಾಡುವ `src/lib/logExport/destinations/<name>.ts` ಅನ್ನು ರಚಿಸಿ:
   ಒಂದು Zod `configSchema`, UI ಗಾಗಿ `fields` ವಿವರಣಾ ಅರೇ, `secretFields`, ಮತ್ತು
   `test()` / `prepare()` / `send(records)` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವ `createClient(config)`.
2. ಅದನ್ನು `src/lib/logExport/registry.ts` ನಲ್ಲಿರುವ `DESTINATIONS` ಅರೇಗೆ ಸೇರಿಸಿ.
3. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ.

ಇಷ್ಟೇ ಸಂಪೂರ್ಣ ಬದಲಾವಣೆ: ಶಾಶ್ವತ ಸಂಗ್ರಹಣೆ, cron ಕೆಲಸ, REST ಪದರ, ರಹಸ್ಯಗಳ ಎನ್‌ಕ್ರಿಪ್ಶನ್ ಮತ್ತು
ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಫಾರ್ಮ್ ಎಲ್ಲವೂ ರಿಜಿಸ್ಟ್ರಿಯನ್ನು ಓದುತ್ತವೆ.

ಹೊಸ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಎರಡು ನಿಯಮಗಳು:

- ಭಾಗಶಃ ವೈಫಲ್ಯವಾದಾಗ `send()` **ಕಡ್ಡಾಯವಾಗಿ ದೋಷವನ್ನು ಎಸೆಯಬೇಕು**. ಯಶಸ್ವಿಯಾಗಿ ಪೂರ್ಣಗೊಳ್ಳುವುದರ ಅರ್ಥ "ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ ಈ ಸಾಲುಗಳಿವೆ",
  ಮತ್ತು ಕರ್ಸರ್ ಅವುಗಳನ್ನು ಶಾಶ್ವತವಾಗಿ ದಾಟಿ ಮುಂದೆ ಸಾಗುತ್ತದೆ.
- ಬಳಕೆದಾರರು ಒದಗಿಸಿದ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವ ಗಮ್ಯಸ್ಥಾನವು, ಅದರಿಂದ ಡೇಟಾ ಪಡೆಯುವ ಮೊದಲು,
  ವೆಬ್‌ಹುಕ್‌ಗಳು ಮಾಡುವಂತೆಯೇ `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`)
  ಮೂಲಕ ಅದನ್ನು ಮೌಲ್ಯೀಕರಿಸಬೇಕು. BigQuery ಗೆ ಇದು ಅಗತ್ಯವಿಲ್ಲ: ಅದರ ಹೋಸ್ಟ್‌ಗಳು ಸ್ಥಿರವಾಗಿವೆ.

## 7. ಇದನ್ನು ನಿರ್ವಹಿಸುವುದು

- **ಡ್ಯಾಶ್‌ಬೋರ್ಡ್**: ಸಂಯೋಜನೆಗಳು → ಲಾಗ್ ಎಕ್ಸ್‌ಪೋರ್ಟ್. ಗಮ್ಯಸ್ಥಾನವನ್ನು ಸೇರಿಸಿ, ಸಾಲುಗಳನ್ನು ಬರೆಯದೆ
  ಪ್ರವೇಶ ರುಜುವಾತುಗಳನ್ನು ಪರಿಶೀಲಿಸಲು **ಪರೀಕ್ಷೆ** ಚಲಾಯಿಸಿ, ನಂತರ ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ.
- **ಬಾಕಿ ಸಾಲುಗಳು**: ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ ಕಾರ್ಡ್ ಬಾಕಿ ಇರುವ ಸಾಲುಗಳು ಮತ್ತು ಕರ್ಸರ್ ಅನ್ನು ತೋರಿಸುತ್ತದೆ; `GET
/api/log-export/status` ಅದೇ ಅಂಕಿಅಂಶಗಳ ಜೊತೆಗೆ ಕೊನೆಯ 20 ಕೆಲಸದ ಚಾಲನೆಗಳನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
- **ಒಂದು ಗಮ್ಯಸ್ಥಾನದ ವೈಫಲ್ಯವು ಇತರವುಗಳನ್ನು ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ** — ಚಾಲನೆಯ ಸಾರಾಂಶವು ಪ್ರತಿ ಗಮ್ಯಸ್ಥಾನದ
  ಸ್ಥಿತಿಯನ್ನು `last_status` / `last_error` ನಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ, ಮತ್ತು ಕೆಲಸದ ಚಾಲನೆಗಳ ಇತಿಹಾಸವು ಒಟ್ಟಾರೆ ವಿವರಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.
- **ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸಿದರೆ ಅದರ ಕರ್ಸರ್ ಕೂಡ ಅಳಿಯುತ್ತದೆ.** ಅದನ್ನು ಮತ್ತೆ ಸೇರಿಸಿದಾಗ ಉಳಿಸಿಕೊಳ್ಳಲಾದ ಅತ್ಯಂತ ಹಳೆಯ
  ಕರೆ ಲಾಗ್‌ನಿಂದ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ; ಇದರಿಂದ ಗಮ್ಯಸ್ಥಾನದಲ್ಲಿ ಈಗಾಗಲೇ ಇರಬಹುದಾದ ಸಾಲುಗಳನ್ನು ಮರುಕಳುಹಿಸಲಾಗುತ್ತದೆ. BigQuery ಯಲ್ಲಿ ಪ್ರತಿ ಸಾಲಿನ
  `insertId` ಇದನ್ನು BigQuery ಯ ಸ್ವಂತ ನಕಲು ನಿವಾರಣೆಯ ಕಾಲಾವಧಿಯೊಳಗೆ ಮಾತ್ರ ನಿಭಾಯಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ
  ಗಮ್ಯಸ್ಥಾನವನ್ನು ಅಳಿಸುವ ಬದಲು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದಕ್ಕೆ ಆದ್ಯತೆ ನೀಡಿ.
