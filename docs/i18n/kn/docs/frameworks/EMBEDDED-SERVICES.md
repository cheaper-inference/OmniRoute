- OmniRoute ಅವುಗಳನ್ನು `DATA_DIR/services/{name}/` ಅಡಿಯಲ್ಲಿ ಸ್ಥಾಪಿಸುತ್ತದೆ ( OmniRoute ನ ಸ್ವಂತ `package.json` ನಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ)
- OmniRoute ಮೊಟ್ಟೆಯಿಡುತ್ತದೆ ಮತ್ತು ಮಕ್ಕಳ ಪ್ರಕ್ರಿಯೆಗಳಂತೆ ಅವುಗಳನ್ನು ಮೇಲ್ವಿಚಾರಣೆ ಮಾಡುತ್ತದೆ
- OmniRoute ಮಗುವಿನ ಪರಿಸರಕ್ಕೆ ಅಲ್ಪಕಾಲಿಕ API ಕೀಲಿಯನ್ನು ಚುಚ್ಚುತ್ತದೆ ಮತ್ತು ಅಲಭ್ಯತೆಯಿಲ್ಲದೆ ಅದನ್ನು ತಿರುಗಿಸುತ್ತದೆ (ಅನ್ವಯವಾಗುವಲ್ಲಿ)
- ಎಲ್ಲಾ ನಿರ್ವಹಣಾ ಮಾರ್ಗಗಳು (`/api/services/*`) ಇವೆ**LOCAL_ONLY** — ಲೂಪ್ಬ್ಯಾಕ್ನಿಂದ ಮಾತ್ರ ಪ್ರವೇಶಿಸಬಹುದು (ಹಾರ್ಡ್ ನಿಯಮ #17)

## 2. ಆರ್ಕಿಟೆಕ್ಚರ್ — 4 ಪದರಗಳು

```
┌────────────────────────────────────────────────────────────────────┐
│  Layer 1 — UI                                                      │
│  /dashboard/providers/services  (tabs: CLIProxyAPI | 9Router | Mux)│
│  Logs live (SSE), Start/Stop/Restart/Update, Settings, Install     │
│                                                                    │
│  src/app/(dashboard)/dashboard/providers/services/                 │
│    ├── page.tsx               Shell + tab routing by ?tab=         │
│    ├── tabs/                  CliproxyServiceTab, NinerouterServiceTab,│
│    │                          MuxServiceTab                        │
│    └── components/            ServiceStatusCard, ServiceLifecycleButtons,│
│                               ServiceLogsPanel, ApiKeyCard, ...    │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ HTTP (Next.js fetch)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 2 — API (LOCAL_ONLY — loopback only)                        │
│                                                                    │
│  /api/services/9router/{install|start|stop|restart|update|         │
│                          rotate-key|status|auto-start|logs}        │
│  /api/services/cliproxy/{install|start|stop|restart|update|        │
│                           status|auto-start|logs}                  │
│  /api/services/mux/{install|start|stop|restart|update|             │
│                      status|auto-start|logs}                       │
│  /dashboard/providers/services/9router/embed/[...path]             │
│    (reverse HTTP + WebSocket proxy → 9Router upstream)             │
│                                                                    │
│  Gate: LOCAL_ONLY_API_PREFIXES includes "/api/services/" and       │
│        "/dashboard/providers/services/*/embed/"                    │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ in-process calls
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 3 — ServiceSupervisor (src/lib/services/)                   │
│                                                                    │
│  ServiceSupervisor.ts   Generic supervisor (child_process.spawn)   │
│    ├── install:    execFile('npm', ['install', pkg, '--prefix'])    │
│    ├── start:      spawn(node, [entrypoint], {env, cwd})           │
│    ├── api_key:    crypto.randomBytes(32) → env NINEROUTER_API_KEY  │
│    ├── port:       20130 for 9Router (configurable)                │
│    ├── logs:       stdio ring buffer 5 MB → SSE events             │
│    ├── health:     HTTP GET /health every 2–5 s, lazy recovery     │
```

## 3. ಜೀವನಚಕ್ರ ಸ್ಥಿತಿ ಯಂತ್ರ

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
              ಆರೋಗ್ಯ ಪರಿಶೀಲನೆ ಯಶಸ್ವಿ │         crash / SIGTERM    │
                               ┌────▼─────┐  (5s ಒಳಗೆ ನಿರ್ಗಮನ)   │
                               │ running  │──── crash ──────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

ಸ್ಥಿತಿಗಳನ್ನು `version_manager` DB ಕೋಷ್ಟಕದಲ್ಲಿ (`status` ಕಾಲಮ್) ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`ServiceSupervisor`-ನ ಮೆಮೊರಿಯೊಳಗಿನ ಸ್ಥಿತಿಯಲ್ಲಿ ಪ್ರತಿಬಿಂಬಿಸಲಾಗುತ್ತದೆ. ಚಾಲನೆಯಲ್ಲಿರುವ
ಪ್ರಕ್ರಿಯೆಗೆ ಮೆಮೊರಿಯೊಳಗಿನ ಸ್ಥಿತಿಯೇ ಅಧಿಕೃತವಾಗಿರುತ್ತದೆ; ಬೂಟ್ ಸಮಯದಲ್ಲಿ DB ಸ್ಥಿತಿಯು
ದೀರ್ಘಕಾಲಿಕ ಪರ್ಯಾಯವಾಗಿರುತ್ತದೆ.

### ಸ್ಥಿತಿ ಪರಿವರ್ತನೆಗಳು

| ಇದರಿಂದ          | ಘಟನೆ                                            | ಇದಕ್ಕೆ                  |
| --------------- | ----------------------------------------------- | ----------------------- |
| `not_installed` | `install()` ಯಶಸ್ವಿಯಾಗುತ್ತದೆ                     | `stopped`               |
| `stopped`       | `start()` ಕರೆಯಲಾಗುತ್ತದೆ                         | `starting`              |
| `starting`      | ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಯು 200 ಹಿಂತಿರುಗಿಸುತ್ತದೆ          | `running`               |
| `starting`      | ಆರೋಗ್ಯಕರವಾಗುವ ಮೊದಲು ಪ್ರಕ್ರಿಯೆ ನಿರ್ಗಮಿಸುತ್ತದೆ    | `error`                 |
| `running`       | `stop()` ಕರೆಯಲಾಗುತ್ತದೆ                          | `stopping` → `stopped`  |
| `running`       | ಪ್ರಕ್ರಿಯೆ ಅನಿರೀಕ್ಷಿತವಾಗಿ ನಿರ್ಗಮಿಸುತ್ತದೆ (< 5 s) | `error` (ವೇಗದ ಕ್ರ್ಯಾಶ್) |
| `running`       | ಪ್ರಕ್ರಿಯೆ ಅನಿರೀಕ್ಷಿತವಾಗಿ ನಿರ್ಗಮಿಸುತ್ತದೆ (> 5 s) | `error`                 |
| `error`         | `start()` ಕರೆಯಲಾಗುತ್ತದೆ                         | `starting`              |
| ಯಾವುದೇ          | `stopping` ಸಮಯದಲ್ಲಿ `stop()`                    | ಯಾವುದೇ ಕಾರ್ಯವಿಲ್ಲ       |

### ಕಾರ್ಯಾಚರಣೆ ಲಾಕ್

`ServiceSupervisor`, ಅಸಿಂಕ್ ಕಾರ್ಯಾಚರಣೆ ಲಾಕ್ (`withLock()`) ಮೂಲಕ ಜೀವನಚಕ್ರ
ಕಾರ್ಯಾಚರಣೆಗಳನ್ನು ಅನುಕ್ರಮಗೊಳಿಸುತ್ತದೆ. ಅದೇ ಸೂಪರ್ವೈಸರ್ನಲ್ಲಿ ಏಕಕಾಲದಲ್ಲಿ ಮಾಡುವ
`start()` ಕರೆಗಳು ನಿಖರವಾಗಿ ಒಂದೇ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತವೆ; ಎರಡನೇ ಕರೆಗಾರನು
ಕಾಯುತ್ತಾನೆ ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸ್ಥಿತಿಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತಾನೆ. ಉದಾಹರಣೆಗೆ, ಸ್ವಯಂ-ಪ್ರಾರಂಭ
ಮತ್ತು UI ಬಟನ್ ಏಕಕಾಲದಲ್ಲಿ ಸಕ್ರಿಯವಾದಾಗ ಉಂಟಾಗಬಹುದಾದ ರೇಸ್ ಪರಿಸ್ಥಿತಿಗಳನ್ನು ಇದು ತಡೆಯುತ್ತದೆ.

## 4. API ಉಲ್ಲೇಖ

`/api/services/` ಅಡಿಯಲ್ಲಿ ಎಲ್ಲಾ ಮಾರ್ಗಗಳು**LOCAL_ONLY** (ಲೂಪ್ಬ್ಯಾಕ್ ಮಾತ್ರ, ಕಠಿಣ ನಿಯಮ #17). ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ವಿನಂತಿಗಳು ದೃಢೀಕರಣ ಟೋಕನ್ ಅನ್ನು ಲೆಕ್ಕಿಸದೆ `403 LOCAL_ONLY` ಸ್ವೀಕರಿಸುತ್ತವೆ.

### 4.1 9 ರೂಟರ್ ಅಂತ್ಯಬಿಂದುಗಳು (11 ಮಾರ್ಗಗಳು)

#### `POST /api/services/9router/install`

npm ನಿಂದ 9 ರೂಟರ್ ಅನ್ನು ಸ್ಥಾಪಿಸಿ. ತನ್ನದೇ ಆದ `package.json` ಮತ್ತು `node_modules/` ನೊಂದಿಗೆ `DATA_DIR/services/9router/` ರಚಿಸುತ್ತದೆ. OmniRoute ನ ಸ್ವಂತ deps ನೊಂದಿಗೆ ಸಂಘರ್ಷ ಮಾಡುವುದಿಲ್ಲ.

**ದೇಹವನ್ನು ವಿನಂತಿಸಿ** (ಎಲ್ಲಾ ಐಚ್ಛಿಕ):

```json
{ "version": "latest" }
```

| ಕ್ಷೇತ್ರ   | ಟೈಪ್ ಮಾಡಿ | ಡೀಫಾಲ್ಟ್   | ವಿವರಣೆ                                   |
| --------- | --------- | ---------- | ---------------------------------------- |
| `version` | `string`  | `"latest"` | ಸ್ಥಾಪಿಸಲು npm ಆವೃತ್ತಿ ಟ್ಯಾಗ್ ಅಥವಾ semver |

**ಪ್ರತಿಕ್ರಿಯೆಗಳು:**

| ಸ್ಥಿತಿ | ವಿವರಣೆ                                                        |
| ------ | ------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`        |
| `400`  | ಅಮಾನ್ಯ ವಿನಂತಿಯ ದೇಹ (Zod ಮೌಲ್ಯೀಕರಣ ವೈಫಲ್ಯ)                     |
| `409`  | ಈಗಾಗಲೇ ಸ್ಥಾಪಿಸಲಾಗುತ್ತಿದೆ (ಲಾಕ್ ಹಿಡಿದಿದೆ)                      |
| `500`  | npm ಅನುಸ್ಥಾಪಿಸಲು ವಿಫಲವಾಗಿದೆ — ಸ್ನೇಹಿ ದೋಷಕ್ಕಾಗಿ `message` ನೋಡಿ |

**ಟಿಪ್ಪಣಿಗಳು:** `execFile('npm', [...])` — ಇಲ್ಲ ಶೆಲ್ ಅನ್ನು ಬಳಸುತ್ತದೆ, ಯಾವುದೇ ಇಂಟರ್ಪೋಲೇಷನ್ ಇಲ್ಲ (ಹಾರ್ಡ್ ನಿಯಮ #13). EACCES ದೋಷಗಳು ಸ್ನೇಹಪರ ಸಂದೇಶಗಳಾಗಿ ಹೊರಹೊಮ್ಮುತ್ತವೆ.

**ಪ್ರತಿಕ್ರಿಯೆಗಳು:**

#### `POST /api/services/9router/rotate-key`

9Router ಗಾಗಿ ಹೊಸ API ಕೀಯನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ, ಅದನ್ನು ವಿಶ್ರಾಂತಿ ಸಮಯದಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸೇವೆಯನ್ನು ಮರುಪ್ರಾರಂಭಿಸುತ್ತದೆ (ಚಾಲನೆ ಮಾಡುತ್ತಿದ್ದರೆ) ಆದ್ದರಿಂದ ಅದು ತನ್ನ ಪರಿಸರದಿಂದ ಹೊಸ ಕೀಲಿಯನ್ನು ಎತ್ತಿಕೊಳ್ಳುತ್ತದೆ. ಹಳೆಯ ಕೀಯನ್ನು ತಕ್ಷಣವೇ ಅಮಾನ್ಯಗೊಳಿಸಲಾಗುತ್ತದೆ.

**ವಿನಂತಿ ದೇಹ:** ಯಾವುದೂ ಇಲ್ಲ

**ಪ್ರತಿಕ್ರಿಯೆಗಳು:**

| ಸ್ಥಿತಿ | ವಿವರಣೆ                                     |
| ------ | ------------------------------------------ |
| `200`  | `{ keyRotated: true, restarted: boolean }` |
| `500`  | ತಿರುಗುವಿಕೆ ವಿಫಲವಾಗಿದೆ                      |

| ------ | --------------------------------- | ----------------------------------------------------------- |

| `POST` | `/api/services/openwa/start`      | ಪೋರ್ಟ್ 8323 ನಲ್ಲಿ ಓಪನ್-ವಾ ಪ್ರಾರಂಭಿಸಿ (ಡೀಫಾಲ್ಟ್)             |
| `POST` | `/api/services/openwa/stop`       | ಓಪನ್-ವಾ ನಿಲ್ಲಿಸಿ                                            |

| `GET`  | `/api/services/openwa/logs`       | SSE ಲಾಗ್ ಟೈಲ್ (ಹಂಚಿಕೊಂಡ `[name]/logs` ಡೈನಾಮಿಕ್ ಮಾರ್ಗದ ಮೂಲಕ) |

**API ಕೀ:** `WA_KEY` — open-wa ನ ಜೆನೆರಿಕ್ `WA_*` -prefixed env ಅತಿಕ್ರಮಿಸಿ ಅದನ್ನು `--key`/`-k` CLI ಆಯ್ಕೆಯ ಮೇಲೆ ಮ್ಯಾಪ್ ಮಾಡುತ್ತದೆ (`dist/cli/setup.js::envArgs()`, ಸ್ಥಾಪಿಸಲಾದ 4.76.0 ಪ್ಯಾಕೇಜ್ ವಿರುದ್ಧ ಪರಿಶೀಲಿಸಲಾಗಿದೆ). `generateServiceApiKey()` ನಿಂದ ರಚಿಸಿದಾಗ ಪೂರ್ವಪ್ರತ್ಯಯ `ow_`. open-wa ಕೀಲಿಯನ್ನು `key`/`api_key` HTTP ಹೆಡರ್ನಿಂದ ಹಿಂತಿರುಗಿಸುತ್ತದೆ ( `Authorization: Bearer` ಅಲ್ಲ); `/api-docs*` ಚೆಕ್ನಿಂದ ಸ್ಪಷ್ಟವಾಗಿ ವಿನಾಯಿತಿ ನೀಡಲಾಗಿದೆ ( `dist/cli/server.js` ನಲ್ಲಿ`setupAuthenticationLayer` ), ಆದ್ದರಿಂದ ಆರೋಗ್ಯ ತನಿಖೆಗೆ ಯಾವುದೇ ದೃಢೀಕರಣ ಹೆಡರ್ ಅಗತ್ಯವಿಲ್ಲ.

**ಜೋಡಿಸುವಿಕೆ:** open-wa ಅನಧಿಕೃತವಾಗಿದೆ ಮತ್ತು WhatsApp — ನೊಂದಿಗೆ ಸಂಬಂಧ ಹೊಂದಿಲ್ಲದ ಸಂಪರ್ಕಿತ ಸಂಖ್ಯೆಯು WhatsApp ನ ಸ್ವಂತ ಯಾಂತ್ರೀಕೃತಗೊಂಡ ಪತ್ತೆಯಿಂದ ನಿಷೇಧದ ಅಪಾಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ. ಮೊದಲ ಪ್ರಾರಂಭದಲ್ಲಿ, ಜೋಡಿಸುವ QR ಕೋಡ್ ಅನ್ನು stdout ಗೆ ಮುದ್ರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲಾಗ್ಗಳ panel/SSE ಸ್ಟ್ರೀಮ್ — ಮೂಲಕ ಹೊರಹೊಮ್ಮುತ್ತದೆ ಈ ಏಕೀಕರಣದಲ್ಲಿ ಇನ್ನೂ ಯಾವುದೇ ಮೀಸಲಾದ QR-ಇಮೇಜ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಇಲ್ಲ.

### 4.9 ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ (9 ರೂಟರ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಎಂಬೆಡ್)

ಡ್ಯಾಶ್ಬೋರ್ಡ್ 9Router ವೆಬ್ UI ಅನ್ನು iframe ಒಳಗೆ ಆಂತರಿಕ ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ಎಂಬೆಡ್ ಮಾಡುತ್ತದೆ:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

ಈ ಪ್ರಾಕ್ಸಿ:

- ವಿನಂತಿಯನ್ನು `http://127.0.0.1:{port}/{path}` ಗೆ ಫಾರ್ವರ್ಡ್ ಮಾಡಿ (ಲೂಪ್ಬ್ಯಾಕ್ ಮಾತ್ರ)
- ಒಳಬರುವ `cookie` ಮತ್ತು `authorization` ಹೆಡರ್ಗಳನ್ನು ಪಟ್ಟಿಗಳು ( OmniRoute ಸೆಷನ್ನ ಸೋರಿಕೆ ಇಲ್ಲ)
- 9 ರೂಟರ್ ದೃಢೀಕರಣಕ್ಕಾಗಿ `Authorization: Bearer {apiKey}` ಚುಚ್ಚುತ್ತದೆ
- ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` ಪಟ್ಟಿಗಳು
- `<base href>` ಇಂಜೆಕ್ಟ್ ಮಾಡಲು ಮತ್ತು ಸಂಪೂರ್ಣ ಮಾರ್ಗಗಳನ್ನು ಸಾಮಾನ್ಯಗೊಳಿಸಲು HTML ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ಪುನಃ ಬರೆಯುತ್ತದೆ (`/foo` → `/dashboard/.../embed/foo`)

ಎಂಬೆಡೆಡ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಾಗಿWebSocket ನವೀಕರಣಗಳನ್ನು ಮೀಸಲಾದ ಪೋರ್ಟ್ನಲ್ಲಿ ಕಂಪ್ಯಾನಿಯನ್ ಸರ್ವರ್ ನಿರ್ವಹಿಸುತ್ತದೆ ( `src/lib/services/embedWsProxy.ts` ನೋಡಿ).

**ಭದ್ರತೆ:** ಎಂಬೆಡ್ ಪ್ರಾಕ್ಸಿ ಮಾರ್ಗಗಳನ್ನು `LOCAL_ONLY_API_PREFIXES` ಅಡಿಯಲ್ಲಿ ವರ್ಗೀಕರಿಸಲಾಗಿದೆ ಮತ್ತು ಲೂಪ್ಬ್ಯಾಕ್ನಿಂದ ಮಾತ್ರ ತಲುಪಬಹುದು. Cloudflare/Ngrok ಸುರಂಗದ ಮೂಲಕ JWT ಅನ್ನು ಪಡೆಯುವ ಆಕ್ರಮಣಕಾರರು ಎಂಬೆಡೆಡ್ ಸೇವೆಗಳಿಗೆ ಪ್ರಾಕ್ಸಿ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ.

## 5. ಭದ್ರತೆ

### LOCAL_ONLY ಜಾರಿಗೊಳಿಸುವಿಕೆ (ಕಠಿಣ ನಿಯಮ #17)

`/api/services/` ಮತ್ತು `/dashboard/providers/services/*/embed/` ಅಡಿಯಲ್ಲಿರುವ ಎಲ್ಲಾ ಮಾರ್ಗಗಳನ್ನು
`src/server/authz/routeGuard.ts` ನಲ್ಲಿ LOCAL_ONLY ಎಂದು ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆಗೆ ಮೊದಲು
ಲೂಪ್ಬ್ಯಾಕ್ ಪರಿಶೀಲನೆಯು ಬೇಷರತ್ತಾಗಿ ನಡೆಯುತ್ತದೆ:

```
ವಿನಂತಿ ಬರುತ್ತದೆ
  → isLocalOnlyPath(path)?
      → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದಿದ್ದರೆ → 403 LOCAL_ONLY (ಯಾವಾಗಲೂ, ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗೆ ಮೊದಲು)
      → ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿದ್ದರೆ    → ಸಾಮಾನ್ಯ ದೃಢೀಕರಣಕ್ಕೆ ಮುಂದುವರಿಯುತ್ತದೆ
```

ಇದು ಸೋರಿಕೆಯಾದ JWT (ಉದಾ., ಟನಲ್ ಮೂಲಕ) `npm install` ಅನ್ನು ಪ್ರಚೋದಿಸುವುದನ್ನು ಅಥವಾ
ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವುದನ್ನು ತಡೆಯುತ್ತದೆ. ಸಂಪೂರ್ಣ ಶ್ರೇಣಿ ಮ್ಯಾಟ್ರಿಕ್ಸ್ಗಾಗಿ
`docs/security/ROUTE_GUARD_TIERS.md` ನೋಡಿ.

### API ಕೀ ಇಂಜೆಕ್ಷನ್

9Router ಮತ್ತು Mux ಗೆ ಅವುಗಳ ಸ್ವಂತ HTTP ಎಂಡ್ಪಾಯಿಂಟ್ಗಳಿಗಾಗಿ API ಕೀ/ಬೇರರ್ ಟೋಕನ್ ಅಗತ್ಯವಿದೆ.
OmniRoute:

1. ಸೇವೆ-ನಿರ್ದಿಷ್ಟ ಪೂರ್ವಪ್ರತ್ಯಯದೊಂದಿಗೆ (`nr_` 9Router ಗಾಗಿ, `mx_` Mux ಗಾಗಿ)
   `crypto.randomBytes(32).toString("base64url")` ಮೂಲಕ ಕೀಯನ್ನು ರಚಿಸುತ್ತದೆ.
2. AES-256-GCM ಬಳಸಿಕೊಂಡು ಅದನ್ನು ಸಂಗ್ರಹಿತ ಸ್ಥಿತಿಯಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ (ಪ್ರೊವೈಡರ್ ರುಜುವಾತುಗಳಿಗೆ ಬಳಸುವ ಅದೇ ಸೈಫರ್).
3. ಪ್ರಾರಂಭಿಸುವ ಸಮಯದಲ್ಲಿ ಅದನ್ನು ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿ ಪರಿಸರ ವೇರಿಯಬಲ್ ಆಗಿ ಇಂಜೆಕ್ಟ್ ಮಾಡುತ್ತದೆ —
   9Router ಗಾಗಿ `NINEROUTER_API_KEY`, Mux ಗಾಗಿ `MUX_SERVER_AUTH_TOKEN` (ಎಂದಿಗೂ CLI
   ಫ್ಲ್ಯಾಗ್ ಆಗಿ ಅಲ್ಲ, ಆದ್ದರಿಂದ ಟೋಕನ್ ಎಂದಿಗೂ `ps`/ಪ್ರಕ್ರಿಯೆ ಪಟ್ಟಿಗಳಲ್ಲಿ ಕಾಣಿಸುವುದಿಲ್ಲ).
4. ಯಾವುದೇ HTTP ಪ್ರತಿಕ್ರಿಯೆಯಲ್ಲಿ ಪ್ಲೇನ್ಟೆಕ್ಸ್ಟ್ ಕೀಯನ್ನು ಎಂದಿಗೂ ಹಿಂದಿರುಗಿಸುವುದಿಲ್ಲ.

CLIProxyAPI ಪ್ರಾರಂಭಿಸುವಾಗ ಇಂಜೆಕ್ಟ್ ಮಾಡಲಾದ ಮೀಸಲಾದ ಡೇಟಾ-ಪ್ಲೇನ್ ಕೀಯನ್ನು ಪಡೆಯುತ್ತದೆ
(`needsApiKey: true` — ಅಡಾಪ್ಟರ್ ವಿರುದ್ಧದ ಮಾದರಿ ಸಿಂಕ್ಗಾಗಿ ಬಳಸಲಾಗುತ್ತದೆ).

### SSRF ರಕ್ಷಣೆ

ರಿವರ್ಸ್ HTTP ಪ್ರಾಕ್ಸಿ (`/dashboard/.../embed/[...path]`) ಅನ್ನು
`http://127.0.0.1:{port}` ಗೆ ಮಾತ್ರ ಫಾರ್ವರ್ಡ್ ಮಾಡುವಂತೆ ಹಾರ್ಡ್ಕೋಡ್ ಮಾಡಲಾಗಿದೆ. ಇದು
ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಗಮ್ಯಸ್ಥಾನಗಳಿಗೆ ಮರುನಿರ್ದೇಶನಗಳನ್ನು ಎಂದಿಗೂ ಅನುಸರಿಸುವುದಿಲ್ಲ.
ಲೂಪ್ಬ್ಯಾಕ್ ವ್ಯಾಪ್ತಿಯ ಹೊರಗೆ ರೆಸಾಲ್ವ್ ಆಗುವ ಯಾವುದೇ ಅಪ್ಸ್ಟ್ರೀಮ್ URL ಅನ್ನು ತಿರಸ್ಕರಿಸಲು
`ssrf-req-filter` ಲೈಬ್ರರಿಯನ್ನು ಬಳಸಲಾಗುತ್ತದೆ.

### ಶೆಲ್ ಸುರಕ್ಷತೆ (ಕಠಿಣ ನಿಯಮ #13)

`npm install` ಅನ್ನು `execFile('npm', ['install', pkg, '--prefix', dir])` ಮೂಲಕ ಆಹ್ವಾನಿಸಲಾಗುತ್ತದೆ —
ಟೆಂಪ್ಲೇಟ್ ಲಿಟರಲ್ಗಳಿಲ್ಲ, ಶೆಲ್ ಇಲ್ಲ ಮತ್ತು ಬಾಹ್ಯ ಪಥಗಳನ್ನು ಕಮಾಂಡ್ ಸ್ಟ್ರಿಂಗ್ಗೆ
ಇಂಟರ್ಪೊಲೇಟ್ ಮಾಡುವುದಿಲ್ಲ. ರನ್ಟೈಮ್ ಮೌಲ್ಯಗಳನ್ನು (ಪೋರ್ಟ್ಗಳು, API ಕೀಗಳು) ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಯ
`env` ಆಬ್ಜೆಕ್ಟ್ ಮೂಲಕ ರವಾನಿಸಲಾಗುತ್ತದೆ.

### ದೋಷ ಶುದ್ಧೀಕರಣ (ಕಠಿಣ ನಿಯಮ #12)

`/api/services/*` ನಿಂದ ಬರುವ ಎಲ್ಲಾ ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳು `buildErrorBody()` ಅಥವಾ
`sanitizeErrorMessage()` ಮೂಲಕ ಹಾದುಹೋಗುತ್ತವೆ. ಕಚ್ಚಾ `err.stack` ಮತ್ತು `err.message` ಅನ್ನು
ಕರೆ ಮಾಡುವವರಿಗೆ ಎಂದಿಗೂ ಯಥಾವತ್ತಾಗಿ ಹಿಂದಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ.

## 6. ಹೊಸ ಎಂಬೆಡೆಡ್ ಸೇವೆಯನ್ನು ಸೇರಿಸುವುದು

ಈ 8 ಹಂತಗಳನ್ನು ಅನುಸರಿಸಿ. ಅಧಿಕೃತ ಉಲ್ಲೇಖವಾಗಿ `src/lib/services/installers/`
ಮತ್ತು `src/app/api/services/` ನಲ್ಲಿರುವ ಅಸ್ತಿತ್ವದಲ್ಲಿನ ಅನುಷ್ಠಾನಗಳನ್ನು ಓದಿ.

### ಹಂತ 1 — ಇನ್ಸ್ಟಾಲರ್ ರಚಿಸಿ

`ninerouter.ts` ಅನ್ನು ಮಾದರಿಯಾಗಿ ಬಳಸಿಕೊಂಡು `src/lib/services/installers/{name}.ts` ರಚಿಸಿ:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // ಖಾಲಿ ಪೋರ್ಟ್ ಒಂದನ್ನು ಆಯ್ಕೆಮಾಡಿ

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

`installers/utils.ts` ನಿಂದ `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` ಬಳಸಿ
— `execSync` ಅಥವಾ ಶೆಲ್ ಇಂಟರ್ಪೊಲೇಷನ್ ಅನ್ನು ಎಂದಿಗೂ ಬಳಸಬೇಡಿ.

### ಹಂತ 2 — ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ನಲ್ಲಿ ನೋಂದಾಯಿಸಿ

`src/lib/services/bootstrap.ts` ನಲ್ಲಿರುವ `SERVICES` ಅರೆಗೆ `ServiceEntry` ಒಂದನ್ನು ಸೇರಿಸಿ:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // API ಕೀ ಅಗತ್ಯವಿಲ್ಲದಿದ್ದರೆ false
}
```

`cfg.tool === "myservice"` ಅನ್ನು ನಿರ್ವಹಿಸುವಂತೆ `buildSpawnArgsFactory()` ಅನ್ನು ವಿಸ್ತರಿಸಿ.

#### ಪ್ಲಗ್ ಮಾಡಬಹುದಾದ ಪ್ರೊವೈಡರ್-ಪ್ಲಗಿನ್ ಒಪ್ಪಂದ (ಹಂತ 1, #7333)

`src/lib/services/providerPlugins/` ಒಂದು ಬ್ಯಾಕೆಂಡ್ನ `bootstrap.ts` `ServiceEntry` ಕ್ಷೇತ್ರಗಳು
ಮತ್ತು `serviceBackends.ts` ಮ್ಯಾನಿಫೆಸ್ಟ್-ಟೆಂಪ್ಲೇಟ್ ಕ್ಷೇತ್ರಗಳನ್ನು ಒಂದೇ ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ
ಪ್ಯಾಕೇಜ್ ಮಾಡುವ `ServiceProviderPlugin` ಒಪ್ಪಂದವನ್ನು ಪರಿಚಯಿಸುತ್ತದೆ. ಇದರಿಂದ ಒಂದೇ ಬ್ಯಾಕೆಂಡ್ನ
ಸ್ವರೂಪವನ್ನು ಸಂಬಂಧವಿಲ್ಲದ ಎರಡು ಪ್ರತ್ಯೇಕ ಫೈಲ್ಗಳಲ್ಲಿ ವ್ಯಕ್ತಪಡಿಸುವ ಅಗತ್ಯವಿರುವುದಿಲ್ಲ. ಇದನ್ನು
ಬರೆಯುತ್ತಿರುವ ಸಮಯದಲ್ಲಿ **`9router` ಮಾತ್ರ ಮೈಗ್ರೇಟ್ ಆಗಿದೆ** — `bootstrap.ts` ತನ್ನ
`SERVICES[]` ಎಂಟ್ರಿಯನ್ನು `getServiceProviderPlugin("9router")`
(`src/lib/services/providerPlugins/registry.ts`) ನಿಂದ ಪಡೆಯುತ್ತದೆ; ಪ್ಲಗಿನ್ ಎಂದಾದರೂ
ಕಾಣೆಯಾಗಿದ್ದರೆ ಪ್ರಾರಂಭದ ದೋಷವನ್ನು ಎಸೆಯುತ್ತದೆ. `cliproxy`, `mux`, ಮತ್ತು `bifrost` ಯಾವುದೇ
ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದ ಇನ್ಲೈನ್ `SERVICES[]` ಲಿಟರಲ್ಗಳಲ್ಲಿಯೇ ಉಳಿದಿವೆ.

`open-sse/config/providerPluginManifest.ts` ಗೆ
`SERVICE_BACKEND_MANIFEST_TEMPLATE` ಎಂಟ್ರಿಯಿಂದ ಸಮರ್ಪಕವಾಗಿ ರೂಪುಗೊಂಡ
`ProviderPluginManifestEntry` ಅನ್ನು ನಿರ್ಮಿಸುವ ಸೇರ್ಪಡೆ ಸ್ವರೂಪದ
`createServiceBackendManifestEntry(pluginId, template)` ಸಹಾಯಕವನ್ನೂ ಸೇರಿಸಲಾಗಿದೆ — ಇದನ್ನು
ಇನ್ನೂ ಯಾವುದೇ ಲೈವ್ ವಿನಂತಿ ಪಥಕ್ಕೆ ಸಂಪರ್ಕಿಸಲಾಗಿಲ್ಲ (`generateProviderPluginManifestFromRegistry()`
ಅಥವಾ `/v1/providers/[provider]/models` ಎರಡಕ್ಕೂ ಅಲ್ಲ); ಎರಡನೇ ಬ್ಯಾಕೆಂಡ್ಗಾಗಿ ಒಪ್ಪಂದವು
ಸಾಬೀತಾದ ನಂತರ ಇದನ್ನು ಅನುಸರಿಸಲಾಗುತ್ತದೆ.

ಮುಂದಿನ PR ಗಳಿಗೆ ಮುಂದೂಡಲಾಗಿದೆ ಮತ್ತು issue #7333 ಅಡಿಯಲ್ಲಿ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗಿದೆ:
ಅದೇ ರಿಜಿಸ್ಟ್ರಿ ಮೂಲಕ `cliproxyapi` ಅನ್ನು ಮೈಗ್ರೇಟ್ ಮಾಡುವುದು, `mux`/`bifrost` ಅನ್ನು
`ServiceBackendPluginId` ಯೂನಿಯನ್ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುವುದು, ಎಕ್ಸಿಕ್ಯೂಟರ್-ರೂಟಿಂಗ್ನ ವಿಶೇಷ
ನಿರ್ವಹಣೆಯನ್ನು (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) ಪ್ಲಗಿನ್ ಒಪ್ಪಂದದೊಳಗೆ ಸೇರಿಸುವುದು ಮತ್ತು
`createServiceBackendManifestEntry()` ಅನ್ನು ಲೈವ್ ಮ್ಯಾನಿಫೆಸ್ಟ್/ಮಾದರಿಗಳ ಕೋಡ್ ಪಥಕ್ಕೆ
ಸಂಪರ್ಕಿಸುವುದು.

### ಹಂತ 3 — ಮೈಗ್ರೇಶನ್ ಮತ್ತು DB ಸೀಡ್ ಸೇರಿಸಿ

`src/lib/db/migrations/` ನಲ್ಲಿನ ಮೈಗ್ರೇಶನ್ ಮೂಲಕ ಸೇವೆಯು `version_manager` ನಲ್ಲಿ ಒಂದು
ಸಾಲನ್ನು ಹೊಂದಿರುವುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ. ಸಾಲು ಈ ಕೆಳಗಿನಂತಿರಬೇಕು:

```sql
INSERT OR IGNORE INTO version_manager (tool, status, auto_start, provider_expose)
VALUES ('myservice', 'not_installed', 0, 0);
```

### ಹಂತ 4 — 7 API ಎಂಡ್ಪಾಯಿಂಟ್ಗಳನ್ನು ರಚಿಸಿ

`src/app/api/services/{name}/` ಅಡಿಯಲ್ಲಿ:

```
_lib.ts            getOrInitSupervisor() ಸಹಾಯಕ
install/route.ts   POST — installer.install() ಅನ್ನು ಕರೆಯುತ್ತದೆ
start/route.ts     POST — supervisor.start() ಅನ್ನು ಕರೆಯುತ್ತದೆ
stop/route.ts      POST — supervisor.stop() ಅನ್ನು ಕರೆಯುತ್ತದೆ
restart/route.ts   POST — supervisor.restart() ಅನ್ನು ಕರೆಯುತ್ತದೆ
update/route.ts    POST — installer.update() ಅನ್ನು ಕರೆಯುತ್ತದೆ
status/route.ts    GET  — ಲೈವ್ + DB ಸ್ಥಿತಿಯನ್ನು ವಿಲೀನಗೊಳಿಸುತ್ತದೆ
auto-start/route.ts POST — auto_start ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಟಾಗಲ್ ಮಾಡುತ್ತದೆ
```

ಹಂಚಿಕೊಂಡಿರುವ `GET /api/services/[name]/logs` ಮಾರ್ಗವನ್ನು ಈಗಾಗಲೇ ಸಂಪರ್ಕಿಸಲಾಗಿದೆ — ಅಲ್ಲಿ ಯಾವುದೇ ಬದಲಾವಣೆಗಳು
ಅಗತ್ಯವಿಲ್ಲ.

ಎಲ್ಲಾ ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು `createErrorResponse()` / `buildErrorBody()` ಮೂಲಕ ನಿರ್ವಹಿಸಿ.

### ಹಂತ 5 — LOCAL_ONLY_API_PREFIXESಗೆ ಸೇರಿಸಿ

`src/server/authz/routeGuard.ts` ನಲ್ಲಿ, `/api/services/` ಈಗಾಗಲೇ ಪಟ್ಟಿಯಲ್ಲಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ.
ನೀವು ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಪರಿಚಯಿಸಿದರೆ (ಉದಾ., `/api/tools/`), ಅದನ್ನು
`LOCAL_ONLY_API_PREFIXES` ಮತ್ತು, ಅದು ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಪ್ರಾರಂಭಿಸುವುದಾದರೆ, `SPAWN_CAPABLE_PREFIXES` ಎರಡಕ್ಕೂ ಸೇರಿಸಿ.
`tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಒಂದು ಪರೀಕ್ಷೆಯನ್ನು ಸೇರಿಸಿ.

### ಹಂತ 6 — UI ಟ್ಯಾಬ್ ಸೇರಿಸಿ

`src/app/(dashboard)/dashboard/providers/services/tabs/{Name}ServiceTab.tsx` ರಚಿಸಿ.
ಹಂಚಿಕೊಂಡಿರುವ ಘಟಕಗಳನ್ನು ಮರುಬಳಸಿ:

`ServicesPageShell.tsx` ನಲ್ಲಿ ಟ್ಯಾಬ್ ಅನ್ನು ನೋಂದಾಯಿಸಿ.

### ಹಂತ 7 — ಪ್ರೊವೈಡರ್ ನಮೂದನ್ನು ಸೇರಿಸಿ (ಸೇವೆಯು ರೂಟಿಂಗ್ ಗುರಿಯಾಗಿದ್ದರೆ)

ಎಂಬೆಡ್ ಮಾಡಲಾದ ಸೇವೆಯು OpenAI-ಹೊಂದಾಣಿಕೆಯ `/v1/chat/completions` ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಒದಗಿಸಿದರೆ:

1. `src/shared/constants/providers.ts` ನಲ್ಲಿ `isEmbeddedService: true` ಜೊತೆಗೆ ಪ್ರೊವೈಡರ್ ನಮೂದನ್ನು ಸೇರಿಸಿ.
2. `BaseExecutor` ಅನ್ನು ವಿಸ್ತರಿಸುವ `open-sse/executors/{name}.ts` ರಚಿಸಿ. ಪ್ರತಿ ವಿನಂತಿಗೂ ಪೋರ್ಟ್ ಮತ್ತು
   API ಕೀಯನ್ನು ಮರು-ಹುಡುಕಿ (ಕನ್ಸ್ಟ್ರಕ್ಟರ್ನಲ್ಲಿ ಎಂದಿಗೂ ಕ್ಯಾಶ್ ಮಾಡಬೇಡಿ). ಸೂಪರ್ವೈಸರ್ ಸ್ಥಿತಿ `"running"` ಅಲ್ಲದಿದ್ದಾಗ
   `503 service_not_running` ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸಿ.
3. ಸೇವೆಯ ಪೂರ್ವಪ್ರತ್ಯಯದೊಂದಿಗೆ `open-sse/config/providerRegistry.ts` ನಲ್ಲಿ ಮಾಡೆಲ್ಗಳನ್ನು ನೋಂದಾಯಿಸಿ
   (ಉದಾ., `myservice/sub/model`). `modelSync.ts` ಅವುಗಳನ್ನು ನವೀಕೃತವಾಗಿರಿಸುತ್ತದೆ.

### ಹಂತ 8 — ದಾಖಲಿಸಿ ಮತ್ತು ಪರೀಕ್ಷಿಸಿ

1. `docs/frameworks/EMBEDDED-SERVICES.md` (ಈ ಫೈಲ್) ಅನ್ನು ನವೀಕರಿಸಿ — §1 ರಲ್ಲಿನ
   ಕೋಷ್ಟಕಕ್ಕೆ ಸೇವೆಯನ್ನು ಮತ್ತು §4 ಗೆ ಯಾವುದೇ ಹೊಸ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳನ್ನು ಸೇರಿಸಿ.
2. `tests/unit/services/` ನಲ್ಲಿ ಯೂನಿಟ್ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಲೈಫ್ಸೈಕಲ್, ಇನ್ಸ್ಟಾಲರ್, API ಆಕಾರ).
3. `tests/integration/services/` ನಲ್ಲಿ ಇಂಟಿಗ್ರೇಷನ್ ಪರೀಕ್ಷೆಯನ್ನು ಸೇರಿಸಿ (`RUN_SERVICES_INT=1` ಹಿಂದೆ).
4. ಹೊಸ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳೊಂದಿಗೆ `docs/openapi.yaml` ಅನ್ನು ನವೀಕರಿಸಿ.

## 7. ಸಮಸ್ಯೆ ನಿವಾರಣೆ

### ಸೇವೆ ಪ್ರಾರಂಭವಾಗುವುದಿಲ್ಲ

**ಲಕ್ಷಣಗಳು:** Start ಬಟನ್ 503 ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ, ಸ್ಥಿತಿಯು `"error"` ಅಥವಾ `"starting"` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ.

**ಪರಿಶೀಲನಾ ಪಟ್ಟಿ:**

1. `GET /api/services/{name}/logs` ಅನ್ನು ಪರಿಶೀಲಿಸಿ (ಅಥವಾ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ Logs ಪ್ಯಾನೆಲ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ). `Error: ENOENT`, `address already in use`, ಅಥವಾ `Cannot find module` ರೀತಿಯ ಸಾಲುಗಳಿಗಾಗಿ ನೋಡಿ.
2. OmniRoute ಅನ್ನು ಚಲಾಯಿಸುವ ಅದೇ ಬಳಕೆದಾರ ಖಾತೆಯಿಂದ `which npm` ಅನ್ನು ಚಲಾಯಿಸಿ, `npm` PATH ನಲ್ಲಿ ಇದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ.
3. ಸೇವೆಯು ಇನ್ಸ್ಟಾಲ್ ಆಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ: `installedVersion` ಗಾಗಿ `GET /api/services/{name}/status` ಅನ್ನು ಪರಿಶೀಲಿಸಿ. ಅದು `null` ಆಗಿದ್ದರೆ, ಮೊದಲು ಇನ್ಸ್ಟಾಲ್ ಮಾಡಿ.
4. `DATA_DIR/services/{name}/node_modules/` ಅಸ್ತಿತ್ವದಲ್ಲಿದೆಯೇ ಮತ್ತು ಖಾಲಿಯಾಗಿಲ್ಲವೇ ಎಂದು ಪರಿಶೀಲಿಸಿ.
5. ಸ್ವಚ್ಛಗೊಳಿಸಲಾದ ನಿರ್ಗಮನ ಕಾರಣಕ್ಕಾಗಿ ಸ್ಥಿತಿ ಪ್ರತಿಕ್ರಿಯೆಯಲ್ಲಿನ `lastError` ಫೀಲ್ಡ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ.

---

### ಕೋಲ್ಡ್ ಸ್ಟಾರ್ಟ್ ನಿಧಾನವಾಗಿದೆ (`running` ತಲುಪಲು > 10 s)

**ಲಕ್ಷಣಗಳು:** `"running"` ಅಥವಾ `"error"` ಗೆ ಬದಲಾಗುವ ಮೊದಲು ಸ್ಥಿತಿಯು ದೀರ್ಘಕಾಲ `"starting"` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ.

**ವಿವರಣೆ:** 9Router ನ ಕೋಲ್ಡ್ ಸ್ಟಾರ್ಟ್ ದೊಡ್ಡ ಡಿಪೆಂಡೆನ್ಸಿ ಟ್ರೀಗಳನ್ನು (DNS, tunnel, MITM ಮಾಡ್ಯೂಲ್ಗಳು) ಆಮದು ಮಾಡುವುದನ್ನು ಒಳಗೊಂಡಿದೆ. ಡೀಫಾಲ್ಟ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನಾ ಮಧ್ಯಂತರವು 2 s ಆಗಿದ್ದು, ಮೇಲ್ವಿಚಾರಕವು ಟೈಮ್ಔಟ್ ಎಂದು ಘೋಷಿಸುವ ಮೊದಲು 3 ಪ್ರಯತ್ನಗಳನ್ನು ಮಾಡುತ್ತದೆ (ಆದರೆ ಪೋಲಿಂಗ್ ಅನ್ನು ಮುಂದುವರಿಸುತ್ತದೆ).

**ಪರಿಹಾರ:** `healthIntervalMs` ಮತ್ತು `waitForHealthy` ಟೈಮ್ಔಟ್ (`healthIntervalMs * 3`) ಅನ್ನು `bootstrap.ts` ನಲ್ಲಿ ಸಂರಚಿಸಬಹುದು. ಹೆಚ್ಚು ಪ್ರಾರಂಭ ಸಮಯ ಬೇಕಾಗುವ ಸೇವೆಗಳಿಗಾಗಿ, `healthIntervalMs` ಅನ್ನು 5000 ಗೆ ಮತ್ತು `stopTimeoutMs` ಅನ್ನು 30 000 ಗೆ ಹೆಚ್ಚಿಸಿ.

---

### ಪೋರ್ಟ್ ಸಂಘರ್ಷ (`EADDRINUSE`)

**ಲಕ್ಷಣಗಳು:** ಲಾಗ್ಗಳು `address already in use :::20130` ಅನ್ನು ತೋರಿಸುತ್ತವೆ.

**ಕಾರಣಗಳು:**

- ಮತ್ತೊಂದು ಪ್ರಕ್ರಿಯೆಯು ಈಗಾಗಲೇ ಪೋರ್ಟ್ 20130 ಅನ್ನು ಬಳಸುತ್ತಿದೆ.
- ಹಿಂದಿನ 9Router ಪ್ರಕ್ರಿಯೆಯನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಿಲ್ಲಿಸಲಾಗಿಲ್ಲ (ಝಾಂಬಿ PID).

**ಪರಿಹಾರ:**

1. `.env` ನಲ್ಲಿನ `NINEROUTER_PORT` ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯೇಬಲ್ ಮೂಲಕ ಡೀಫಾಲ್ಟ್ ಪೋರ್ಟ್ ಅನ್ನು ಬದಲಾಯಿಸಿ.
2. ಸಂಘರ್ಷ ಉಂಟುಮಾಡುತ್ತಿರುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪತ್ತೆಹಚ್ಚಿ ಮತ್ತು ಕೊನೆಗೊಳಿಸಿ: `lsof -ti :20130 | xargs kill -9`.
3. `bootstrap.ts` ನಲ್ಲಿ `port` ಫೀಲ್ಡ್ ಮೂಲಕ ಪ್ರತಿ ಸೇವೆಗೆ ಪೋರ್ಟ್ ಅನ್ನು ಸಂರಚಿಸಬಹುದು.

**ಗಮನಿಸಿ:** OmniRoute ನ ಡೀಫಾಲ್ಟ್ ಪೋರ್ಟ್ 20128 ರೊಂದಿಗೆ ಸಂಘರ್ಷವಾಗುವುದನ್ನು ತಪ್ಪಿಸಲು 9Router ನಿರ್ದಿಷ್ಟವಾಗಿ ಪೋರ್ಟ್ 20130 ಅನ್ನು ಡೀಫಾಲ್ಟ್ ಆಗಿ ಬಳಸುತ್ತದೆ.

---

### ಇನ್ಸ್ಟಾಲ್ ಮಾಡುವಾಗ ಅನುಮತಿ ನಿರಾಕರಿಸಲಾಗಿದೆ (EACCES)

**ಲಕ್ಷಣಗಳು:** ಇನ್ಸ್ಟಾಲ್ 500 ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ, ಲಾಗ್ಗಳು `EACCES` ಅಥವಾ `permission denied` ಅನ್ನು ತೋರಿಸುತ್ತವೆ.

**ಕಾರಣಗಳು:**

- `DATA_DIR` ಅಥವಾ ಅದರ ಪೇರೆಂಟ್ ಡೈರೆಕ್ಟರಿಯಲ್ಲಿ OmniRoute ಪ್ರಕ್ರಿಯೆಗೆ ಬರೆಯುವ ಅನುಮತಿ ಇಲ್ಲ.
- ಮ್ಯಾಪ್ ಮಾಡಲಾದ ವಾಲ್ಯೂಮ್ಗೆ ಬರೆಯುವ ಪ್ರವೇಶವಿಲ್ಲದೆ ರೂಟ್ಲೆಸ್ Docker ಒಳಗೆ ಚಲಾಯಿಸಲಾಗುತ್ತಿದೆ.

**ಪರಿಹಾರ:**

1. `DATA_DIR` ಅನ್ನು ಪರಿಶೀಲಿಸಿ (ಡೀಫಾಲ್ಟ್: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. OmniRoute ಪ್ರಕ್ರಿಯೆಯ ಬಳಕೆದಾರರು ಡೈರೆಕ್ಟರಿಯ ಮಾಲೀಕರಾಗಿದ್ದಾರೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ: `chown -R $USER ~/.omniroute/`
3. Docker ನಲ್ಲಿ, ಕಂಟೇನರ್ ಬಳಕೆದಾರರಿಗೆ ವಾಲ್ಯೂಮ್ ಮೌಂಟ್ ಸರಿಯಾದ ಅನುಮತಿಗಳನ್ನು ಹೊಂದಿದೆಯೇ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ.

### ಅಪ್ಡೇಟ್ ವಿಫಲವಾಗುತ್ತದೆ (`npm install` ಟೈಮ್ಔಟ್ ಅಥವಾ ನೆಟ್ವರ್ಕ್ ದೋಷ)

**ಲಕ್ಷಣಗಳು:** ಅಪ್ಡೇಟ್ `InstallError` ಜೊತೆಗೆ 500 ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ, ಲಾಗ್ಗಳು ನೆಟ್ವರ್ಕ್ ಟೈಮ್ಔಟ್ ಅನ್ನು ತೋರಿಸುತ್ತವೆ.

**ಪರಿಶೀಲನಾ ಪಟ್ಟಿ:**

1. npm ರಿಜಿಸ್ಟ್ರಿಯನ್ನು ತಲುಪಬಹುದೇ ಎಂದು ದೃಢೀಕರಿಸಿ: `npm ping`.
2. ಕಾರ್ಪೊರೇಟ್ ಪ್ರಾಕ್ಸಿಗಾಗಿ ಪರಿಶೀಲಿಸಿ: `npm config get proxy`, `npm config get https-proxy`.
3. ಇನ್ಸ್ಟಾಲ್ ಅನ್ನು ಹಸ್ತಚಾಲಿತವಾಗಿ ಪ್ರಯತ್ನಿಸಿ: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. ಏರ್-ಗ್ಯಾಪ್ನ ಹಿಂದೆ ಇದ್ದರೆ, tarball ಅನ್ನು ಮುಂಚಿತವಾಗಿ ಡೌನ್ಲೋಡ್ ಮಾಡಿ ಮತ್ತು `npm install /path/to/tarball.tgz` ಅನ್ನು ಬಳಸಿ.

### ಪ್ರಾರಂಭಿಸಿದ ತಕ್ಷಣ ಸೇವೆಯು `"error"` ಸ್ಥಿತಿಯನ್ನು ತೋರಿಸುತ್ತದೆ (ತ್ವರಿತ ಕ್ರ್ಯಾಶ್)

**ಲಕ್ಷಣಗಳು:** ಸ್ಥಿತಿಯು 5 ಸೆಕೆಂಡುಗಳಿಗಿಂತ ಕಡಿಮೆ ಅವಧಿಯಲ್ಲಿ `"starting"` ಇಂದ `"error"` ಗೆ ಬದಲಾಗುತ್ತದೆ. `lastError` `"Fast crash (exited with code 1)"` ಅನ್ನು ತೋರಿಸುತ್ತದೆ.

**ಪರಿಶೀಲನಾ ಪಟ್ಟಿ:**

1. ಸಂಪೂರ್ಣ ಲಾಗ್ನ ಕೊನೆಯ ಭಾಗವನ್ನು ಓದಿ: `GET /api/services/{name}/logs?tail=500`.
2. ಸಾಮಾನ್ಯ ಕಾರಣ: ಸೇವೆಯು ನಿರೀಕ್ಷಿಸುವ ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯೇಬಲ್ಗಳು ಕಾಣೆಯಾಗಿರುವುದು.
3. 9Router ಗಾಗಿ: ಸ್ಪಾನ್ ಮಾಡುವಾಗ ರವಾನಿಸಲಾದ env ನಲ್ಲಿ `NINEROUTER_DISABLE_MITM=true` ಮತ್ತು `NINEROUTER_DISABLE_TUNNEL=true` ಇವೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (`installers/ninerouter.ts` ನಲ್ಲಿನ `resolveSpawnArgs` ಅನ್ನು ನೋಡಿ).

## 8. ಪದೇ ಪದೇ ಕೇಳಲಾಗುವ ಪ್ರಶ್ನೆಗಳು

**ಪ್ರ: ಎಂಬೆಡ್ ಮಾಡಲಾದ ಸೇವೆಗಳ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಕ್ಲೈಂಟ್ಗಳಿಗೆ ಬಹಿರಂಗಪಡಿಸಬಹುದೇ?**

ಇಲ್ಲ. LOCAL_ONLY ಹಂತವನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೀಗೆ ವಿನ್ಯಾಸಗೊಳಿಸಲಾಗಿದೆ (ಕಠಿಣ ನಿಯಮ #17). `npm install` ಅನ್ನು ಆಹ್ವಾನಿಸಬಲ್ಲ ಅಥವಾ `node` ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಪ್ರಾರಂಭಿಸಬಲ್ಲ ರೂಟ್ಗಳು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ನಿಂದ ತಲುಪಲು ಸಾಧ್ಯವಾಗಬಾರದು, ಏಕೆಂದರೆ ಟನಲ್ (Cloudflare, Ngrok, Tailscale) ಮೂಲಕ ಸೋರಿಕೆಯಾದ JWT ಇಲ್ಲದಿದ್ದರೆ ಅನಿಯಂತ್ರಿತ ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಪ್ರಾರಂಭಿಸಲು ಅವಕಾಶ ನೀಡುತ್ತದೆ. `/api/services/` ಗೆ ಈ ನಿಯಮದಿಂದ ಹೊರಗುಳಿಯುವ ಆಯ್ಕೆ ಇಲ್ಲ — `/api/mcp/` ಗಿಂತ ಭಿನ್ನವಾಗಿ, ಇದನ್ನು manage-scope ಬೈಪಾಸ್ ಪಟ್ಟಿಯಿಂದ ಹೊರಗಿಡಲಾಗಿದೆ. `docs/security/ROUTE_GUARD_TIERS.md` ನೋಡಿ.

---

**ಪ್ರ: ಪ್ರೊಡಕ್ಷನ್/ಕ್ಲೌಡ್ ನಿಯೋಜನೆಗಳಲ್ಲಿ 9Router ಮತ್ತು CLIProxyAPI ಲಭ್ಯವಿರುತ್ತವೆಯೇ?**

ಹೌದು. ಎರಡೂ ಸೇವೆಗಳು OmniRoute ಅನುಸರಿಸುವ ಅದೇ local-first ಮಾದರಿಯನ್ನು ಅನುಸರಿಸುತ್ತವೆ. ಅವು ಒಂದೇ ಯಂತ್ರದಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ ಮತ್ತು ಲೂಪ್ಬ್ಯಾಕ್ ಮೂಲಕ ಸಂವಹನ ನಡೆಸುತ್ತವೆ. ಇಲ್ಲಿ "ಪ್ರೊಡಕ್ಷನ್" ಎಂದರೆ OmniRoute ಅನ್ನು ನಿಯೋಜಿಸಿರುವ VPS ಅಥವಾ ಸ್ಥಳೀಯ ಸರ್ವರ್; ದೂರಸ್ಥ ಕ್ಲೌಡ್ ಪೂರೈಕೆದಾರರಲ್ಲ.

---

**ಪ್ರ: ಸೂಪರ್ವೈಸರ್ ಅನ್ನು ಡೀಬಗ್ ಮಾಡುವುದು ಹೇಗೆ?**

1. SSE ಲಾಗ್ ಸ್ಟ್ರೀಮ್ ಅನ್ನು ಅನುಸರಿಸಿ: `curl -N http://localhost:20128/api/services/9router/logs`.
2. `service:supervisor` ನೇಮ್ಸ್ಪೇಸ್ ಮೂಲಕ ಫಿಲ್ಟರ್ ಮಾಡಲಾದ OmniRoute ನ pino ಔಟ್ಪುಟ್ನಲ್ಲಿರುವ ರಚನಾತ್ಮಕ ಲಾಗ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
3. DB ಸಾಲನ್ನು ಪರಿಶೀಲಿಸಿ: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. ಪ್ರಸ್ತುತ ಲೈವ್ ಸ್ಥಿತಿ, PID, ಆರೋಗ್ಯ ಮತ್ತು `lastError` ಅನ್ನು ಒಂದೇ ಕರೆಗೆ ನೋಡಲು `GET /api/services/9router/status` ಬಳಸಿ.

---

**ಪ್ರ: ಸೂಪರ್ವೈಸರ್ `health: "degraded"` ಅಥವಾ `health: "unknown"` ಎಂದು ತೋರಿಸುತ್ತದೆ, ಆದರೆ ಸ್ಥಿತಿಯು `"running"` ಆಗಿದೆ. ಇದು ಸಮಸ್ಯೆಯೇ?**

`"degraded"` ಎಂದರೆ ಆರೋಗ್ಯ ಪ್ರೋಬ್ 200 ಅಲ್ಲದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ನೀಡಿದೆ. `"unknown"` ಎಂದರೆ ಇನ್ನೂ ಯಾವುದೇ ಪ್ರೋಬ್ ಪೂರ್ಣಗೊಂಡಿಲ್ಲ (ಮೊದಲ ಪೋಲ್ನೊಂದಿಗೆ ರೇಸ್). ಪ್ರಾರಂಭದ ಸಮಯದಲ್ಲಿ ಇವೆರಡೂ ತಾತ್ಕಾಲಿಕವಾಗಿರುತ್ತವೆ. `"running"` ಆದ ನಂತರ `healthIntervalMs * 3` ms ಗಿಂತ ಹೆಚ್ಚು ಕಾಲ ಆರೋಗ್ಯವು `"degraded"` ಆಗಿಯೇ ಉಳಿದರೆ, ಎಂಬೆಡ್ ಮಾಡಲಾದ ಸೇವೆ ಚಾಲನೆಯಲ್ಲಿದ್ದರೂ ಅದರ HTTP API ಪ್ರತಿಕ್ರಿಯಿಸುತ್ತಿಲ್ಲ ಎಂದರ್ಥ. ಸ್ಥಿತಿ ಪ್ರತಿಕ್ರಿಯೆಯಲ್ಲಿರುವ ಪೋರ್ಟ್ ಸರಿಯಾಗಿದೆಯೇ ಮತ್ತು ಸೇವೆಯು ವಾಸ್ತವವಾಗಿ ಆ ಪೋರ್ಟ್ನಲ್ಲಿ ಆಲಿಸುತ್ತಿದೆಯೇ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ.

---

**ಪ್ರ: ಪೂರ್ಣ ಮರುಪ್ರಾರಂಭವಿಲ್ಲದೆ 9Router API ಕೀಲಿಯನ್ನು ಬದಲಾಯಿಸಬಹುದೇ?**

ಇಲ್ಲ. ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವಾಗ ಪರಿಸರ ವೇರಿಯಬಲ್ ಮೂಲಕ API ಕೀಲಿಯನ್ನು 9Router ಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ. ಚಾಲನೆಯಲ್ಲಿರುವ ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿ ಪರಿಸರ ವೇರಿಯಬಲ್ಗಳನ್ನು ಬದಲಾಯಿಸಲಾಗುವುದಿಲ್ಲ. ಹೊಸ ಕೀಲಿಯನ್ನು ಅನ್ವಯಿಸಲು `POST .../rotate-key` ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸೇವೆಯನ್ನು ನಿಲ್ಲಿಸಿ ಮರುಪ್ರಾರಂಭಿಸುತ್ತದೆ. ಕೀಲಿ ರೊಟೇಶನ್ ಸೇವೆಯ `stopTimeoutMs` (ಡೀಫಾಲ್ಟ್ 15 s) ಮತ್ತು ಅದರ ಪ್ರಾರಂಭದ ಸಮಯದೊಳಗೆ ಜಾರಿಗೆ ಬರುತ್ತದೆ.

---

**ಪ್ರ: ರಿಂಗ್ ಬಫರ್ ಮಿತಿ ಎಷ್ಟು ಮತ್ತು ಅದು ತುಂಬಿದಾಗ ಏನಾಗುತ್ತದೆ?**

ಪ್ರತಿ ಸೇವೆಯು ಮೀಸಲಾದ 5 MB ರಿಂಗ್ ಬಫರ್ ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ. ಬಫರ್ ತುಂಬಿದಾಗ, ಹೊಸ ಲಾಗ್ ಸಾಲುಗಳಿಗೆ ಸ್ಥಳಾವಕಾಶ ಕಲ್ಪಿಸಲು ಅತ್ಯಂತ ಹಳೆಯ ಲಾಗ್ ಸಾಲುಗಳನ್ನು ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ. SSE `snapshot` ಈವೆಂಟ್ `tail` ಮಿತಿಯೊಳಗಿನ ಅತ್ಯಂತ ಇತ್ತೀಚಿನ ಸಾಲುಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. DB ಸಾಲಿನಲ್ಲಿ `logsBufferPath` ಅನ್ನು ಹೊಂದಿಸದ ಹೊರತು ಲಾಗ್ಗಳನ್ನು ಡಿಸ್ಕ್ನಲ್ಲಿ ಶಾಶ್ವತವಾಗಿ ಉಳಿಸಲಾಗುವುದಿಲ್ಲ.
