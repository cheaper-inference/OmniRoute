| ಪುಟ            | ಮಾರ್ಗ                   | ಪರಿಕಲ್ಪನೆ                                                                                 | ಸಂಖ್ಯೆ               |

## ಇದು ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ

```
CLI Code's / CLI Agents (ಬಳಕೆಯ ಹರಿವು):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (ಎಲ್ಲವೂ OmniRoute ಕಡೆಗೆ ನಿರ್ದೇಶಿಸುತ್ತವೆ)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute ಸರಿಯಾದ ಪೂರೈಕೆದಾರನಿಗೆ ಮಾರ್ಗನಿರ್ದೇಶಿಸುತ್ತದೆ)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (ವಿಲೋಮ ಪ್ರಾರಂಭ ಹರಿವು):
    ಕ್ಲೈಂಟ್ ವಿನಂತಿ → OmniRoute → stdio/ACP ಮೂಲಕ CLI ಅನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ → ಪ್ರತಿಕ್ರಿಯೆ
```

**ಪ್ರಯೋಜನಗಳು:**

- ಎಲ್ಲಾ ಪರಿಕರಗಳನ್ನು ನಿರ್ವಹಿಸಲು ಒಂದೇ API ಕೀಲಿ
- ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಎಲ್ಲಾ CLIಗಳಾದ್ಯಂತ ವೆಚ್ಚದ ಟ್ರ್ಯಾಕಿಂಗ್
- ಪ್ರತಿಯೊಂದು ಪರಿಕರವನ್ನು ಮರುಸಂರಚಿಸದೆಯೇ ಮಾದರಿ ಬದಲಾವಣೆ
- ಸ್ಥಳೀಯವಾಗಿ ಮತ್ತು ದೂರಸ್ಥ ಸರ್ವರ್ಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ (VPS, Docker, Akamai, Cloudflare Tunnel)

## `setup-*` ಮೂಲಕ ಸ್ವಯಂ-ಕಾನ್ಫಿಗರ್ ಮಾಡಿ

ಪ್ರತಿ ಉಪಕರಣದ ಕಾನ್ಫಿಗ್ ಅನ್ನು ನೀವು ಕೈಯಾರೆ ಬರೆಯಬೇಕಾಗಿಲ್ಲ. ಚಾಲನೆಯಲ್ಲಿರುವ
OmniRoute (ಸ್ಥಳೀಯ ಅಥವಾ ರಿಮೋಟ್) ನಿಂದ **ಲೈವ್** ಮಾದರಿ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಓದಿ, ನಿಮ್ಮ
ಗಣಕದಲ್ಲಿ ಉಪಕರಣದ ಸ್ವಂತ ಕಾನ್ಫಿಗ್ ಅನ್ನು ಬರೆಯುವಂತೆ, ಬೆಂಬಲಿತ ಪ್ರತಿಯೊಂದು CLI ಗಾಗಿ
OmniRoute ಒಂದು `setup-*` ಕಮಾಂಡ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
```

ಪ್ರತಿಯೊಂದೂ `--remote <url> --api-key <key>` (ರಿಮೋಟ್ OmniRoute ಗೆ ವಿರುದ್ಧವಾಗಿ
ಸ್ಥಳೀಯ ಉಪಕರಣವನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿ), `--dry-run` (ಬರೆಯದೆ ಪೂರ್ವವೀಕ್ಷಿಸಿ), ಮತ್ತು
`--port` ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ. ಸ್ವಯಂಚಾಲಿತ ಮಾದರಿ ಅನ್ವೇಷಣೆಯಿಲ್ಲದ ಉಪಕರಣಗಳು (Cline,
Kilo, Roo, Goose, Aider, Qwen, 5dive) `--model <id>` ಅನ್ನು (ಮತ್ತು
ಸಂವಾದಾತ್ಮಕವಲ್ಲದ ಚಾಲನೆಗಳಿಗಾಗಿ `--yes` ಅನ್ನು) ಸ್ವೀಕರಿಸುತ್ತವೆ. `$HOME` ಅಡಿಯಲ್ಲಿ
ಬರೆಯದ ಏಕೈಕ ವಿಧಾನ `setup-5dive` ಆಗಿದೆ: ಇದು ಫ್ಲೀಟ್ ಹೋಸ್ಟ್ನಲ್ಲಿ root ಮಾಲೀಕತ್ವದ
ದೃಢೀಕರಣ ಪ್ರೊಫೈಲ್ ಅನ್ನು ಬರೆಯುವ ಮೂಲಕ 5dive ಏಜೆಂಟ್ ಫ್ಲೀಟ್ ಅನ್ನು ಕಾನ್ಫಿಗರ್
ಮಾಡುತ್ತದೆ; ಆದ್ದರಿಂದ ಇದು `sudo` ಮೂಲಕ ಮರು-ಕಾರ್ಯಗತಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ತನ್ನದೇ ಆದ
ರಿಮೋಟ್ ಮೋಡ್ ಅನ್ನು ಹೊಂದಿಲ್ಲ. ಸರಿಯಾದ env ಅನ್ನು ಸೇರಿಸಿ, ಯಾವುದೇ ಕಾನ್ಫಿಗ್ ಅನ್ನು
ಬರೆಯದೆಯೇ CLI ಅನ್ನು ಪ್ರಾರಂಭಿಸಲು, ಸಾಮಾನ್ಯ `omniroute run <target>` ಲಾಂಚರ್
ಬಳಸಿ (claude, codex, aider, goose, opencode, qwen, gemini — ಟಾರ್ಗೆಟ್ಗಳು ಮತ್ತು
ಅಲಿಯಾಸ್ಗಳು `bin/cli/cli-manifest.mjs` ನಿಂದ ಬರುತ್ತವೆ); ಹಳೆಯ ಪ್ರತ್ಯೇಕ-ಉಪಕರಣ
ಲಾಂಚರ್ಗಳಾದ `omniroute launch` (Claude Code) ಮತ್ತು `omniroute launch-codex`
(Codex) ಇನ್ನೂ ಲಭ್ಯವಿವೆ. Gemini CLI ಕೇವಲ ಲಾಂಚ್ಗೆ ಮಾತ್ರ: ಅದು ಒಂದು
`omniroute run` ಟಾರ್ಗೆಟ್ ಆಗಿದೆ, ಆದರೆ ಯಾವುದೇ `setup-*`/`configure` ವಿಧಾನವನ್ನು
ಹೊಂದಿಲ್ಲ.

> **ಸಂಪೂರ್ಣ ಉಲ್ಲೇಖ:** ಪ್ರಧಾನ ಕೋಷ್ಟಕ — ಪ್ರತಿಯೊಂದು ಕಮಾಂಡ್ ಏನನ್ನು ಬರೆಯುತ್ತದೆ,
> ಪ್ರತಿಯೊಂದು ಫ್ಲ್ಯಾಗ್, ಸ್ಥಳೀಯ ಮತ್ತು ರಿಮೋಟ್ ನಡುವಿನ ವ್ಯತ್ಯಾಸ, ಹಾಗೂ ಯಾವ
> ಉಪಕರಣಗಳಿಗೆ `/v1` ಸಫಿಕ್ಸ್ ಅಗತ್ಯವಿದೆ — ಇವೆಲ್ಲವೂ
> **[CLI ಏಕೀಕರಣಗಳು](../guides/CLI-INTEGRATIONS.md)** ಪುಟದಲ್ಲಿವೆ.

### ಇವುಗಳನ್ನು ಕಂಟೈನರ್ನೊಳಗೆ ಚಲಾಯಿಸುವುದು

OmniRoute ಕಂಟೈನರ್ನೊಳಗೆ ಕಾರ್ಯಗತಗೊಳಿಸಲಾದ `setup-*` ಕಮಾಂಡ್, ಕಂಟೈನರ್ನ ಸ್ವಂತ
ಹೋಮ್ಗೆ ಬರೆಯುತ್ತದೆ; ಅದನ್ನು ಯಾವುದೇ ಹೋಸ್ಟ್ CLI ಓದುವುದಿಲ್ಲ ಮತ್ತು ಕಂಟೈನರ್ ಜೊತೆಗೆ
ಅದು ಕಣ್ಮರೆಯಾಗುತ್ತದೆ. OmniRoute ಇದನ್ನು ಪತ್ತೆಮಾಡಿ, ಬರೆಯುವ ಬದಲು ಸೂಚನೆಗಳೊಂದಿಗೆ
`2` ಸ್ಥಿತಿಯಲ್ಲಿ ನಿರ್ಗಮಿಸುತ್ತದೆ. ಮುಂದುವರಿಯಲು ಬೆಂಬಲಿತ ಎರಡು ಮಾರ್ಗಗಳಿವೆ — CLI ಅನ್ನು
ಹೋಸ್ಟ್ನಲ್ಲಿ ಸ್ಥಾಪಿಸಿ ಮತ್ತು ಕಂಟೈನರ್ಗೆ `omniroute connect` ಮಾಡಿ, ಅಥವಾ ಕಾನ್ಫಿಗ್
ಡೈರೆಕ್ಟರಿಗಳನ್ನು bind-mount ಮಾಡಿ ಮತ್ತು `CLI_CONFIG_HOME` ಅನ್ನು ಹೊಂದಿಸಿ (compose
`host` ಪ್ರೊಫೈಲ್). ಕಂಟೈನರ್ನ ಸ್ವಂತ CLI ಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುವುದೇ ನಿಮ್ಮ ನಿಜವಾದ
ಉದ್ದೇಶವಾಗಿದ್ದರೆ, ಪ್ರತಿಯೊಂದು `setup-*` ಕಮಾಂಡ್ ಜೊತೆಗೆ `omniroute configure` ಮತ್ತು
`omniroute config set` ಸಹ `--allow-container-write` ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತವೆ;
ಸರ್ವರ್ಗಾಗಿ `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ಅದೇ ಕೆಲಸವನ್ನು
ಮಾಡುತ್ತದೆ. ನೋಡಿ:
[Docker ಮಾರ್ಗದರ್ಶಿ → ಹೋಸ್ಟ್ CLI ಉಪಕರಣಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುವುದು](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker).

ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ **ಅನ್ವಯಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್** (`POST /api/cli-tools/apply`) ಸಹ
ಅದೇ ನಿರ್ಬಂಧವನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ: ಕಂಟೈನರ್ನಲ್ಲಿ, ಹೋಸ್ಟ್ನಿಂದ bind-mount
ಮಾಡದ ಟಾರ್ಗೆಟ್ಗೆ ಬರೆಯಲು ಪ್ರಯತ್ನಿಸಿದಾಗ, ಅದು ಸುರಕ್ಷಿತ ದೋಷ ಪಠ್ಯದೊಂದಿಗೆ
**`422`** ಮತ್ತು `containerEphemeralTarget: true` ಅನ್ನು ಉತ್ತರಿಸುತ್ತದೆ; ಜೊತೆಗೆ
ಹೋಸ್ಟ್ ವಿಧಾನವಿರುವ ಉಪಕರಣಗಳಿಗಾಗಿ (claude, codex, opencode, cline, kilo,
continue), ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಲಾಯಿಸಲು ಒಂದು `hostSetupCommand` (ಉದಾ.
`omniroute setup-opencode`) ಅನ್ನು ನೀಡುತ್ತದೆ; ಯಾವುದನ್ನೂ ಬರೆಯಲಾಗುವುದಿಲ್ಲ.
ಕಂಟೈನರ್ ಮೋಡ್ನಲ್ಲಿ `dryRun: true` ಕಾರ್ಯನಿರ್ವಹಿಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತದೆ ಮತ್ತು
ಡಿಸ್ಕ್ ಅನ್ನು ಸ್ಪರ್ಶಿಸದೆ ಪರಿಷ್ಕೃತ ಪೂರ್ವವೀಕ್ಷಣೆ + ಟಾರ್ಗೆಟ್ ಪಥವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
ಪೂರ್ವವೀಕ್ಷಣೆಯ ವಿಷಯವು ನಕಲಿಸಲು ಅಥವಾ ಆಮದು ಮಾಡಲು ಬಳಸಬಹುದಾದ ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವ
ಕಾನ್ಫಿಗರೇಶನ್ ಅಲ್ಲ. ಮೂಲ ಉಪಕರಣ/base URL/API key/model ಇನ್ಪುಟ್ಗಳೊಂದಿಗೆ ಹೋಸ್ಟ್ನಲ್ಲಿ
ಅನ್ವಯಿಸಿ, ಅಥವಾ ಸೂಚಿಸಲಾದ ಹೋಸ್ಟ್-ಸೈಡ್ ಸೆಟಪ್ ಕಮಾಂಡ್ ಅನ್ನು ಬಳಸಿ. ಪೂರ್ವವೀಕ್ಷಣೆ ಹೆಡರ್
ಮತ್ತು ವಿನಂತಿ ಒಪ್ಪಂದಕ್ಕಾಗಿ [CLI ಕಾನ್ಫಿಗರೇಶನ್ ಭದ್ರತೆ](../security/CLI-CONFIGURATION.md)
ನೋಡಿ. ಈ ನಡವಳಿಕೆ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದ್ದು,
`tests/unit/api/cli-tools/apply-container-guard.test.ts` ಮೂಲಕ ರಿಗ್ರೆಷನ್ ವಿರುದ್ಧ
ರಕ್ಷಿಸಲಾಗಿದೆ — ನಿರ್ಬಂಧವನ್ನು ತೆಗೆದುಹಾಕುವ ಮೂಲಕ `422` ಅನ್ನು ಎಂದಿಗೂ "ಸರಿಪಡಿಸಬೇಡಿ".

## 5. ಬ್ಯಾಚ್ ಪತ್ತೆ API

ಎಲ್ಲಾ ಪರಿಕರಗಳ ಪತ್ತೆಯನ್ನು ಒಂದೇ ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ ಒಟ್ಟುಗೂಡಿಸಲಾಗಿದೆ:

**`GET /api/cli-tools/all-statuses`**

- ದೃಢೀಕರಣ: `requireCliToolsAuth(request)` (ಇತರ `/api/cli-tools/` ಮಾರ್ಗಗಳಂತೆಯೇ)
- ಹಿಂತಿರುಗಿಸುವುದು: `Record<toolId, ToolBatchStatus>` (ಪ್ರಕಾರ: `src/shared/types/cliBatchStatus.ts`)
- ಕಾರ್ಯತಂತ್ರ: ಎಲ್ಲಾ ಪರಿಕರಗಳ ಮೇಲೆ `Promise.all`, ಪ್ರತಿ ಪರಿಕರಕ್ಕೆ 5 ಸೆಕೆಂಡ್ ಕಾಲಾವಧಿ ಮಿತಿ
- ಕ್ಯಾಶ್: ಕಾನ್ಫಿಗರೇಶನ್ ಫೈಲ್ನ `mtime` ಮೂಲಕ ಸೂಚ್ಯಂಕಗೊಳಿಸಲಾದ ಇನ್-ಮೆಮೊರಿ LRU. mtime ಬದಲಾದಾಗ ಕ್ಯಾಶ್ ಅಮಾನ್ಯಗೊಳ್ಳುತ್ತದೆ. ಸರ್ವರ್ ಮರುಪ್ರಾರಂಭವಾದಾಗ ಮರುಹೊಂದಿಸಲಾಗುತ್ತದೆ.

ಪ್ರತಿ ಪರಿಕರದ ಪ್ರತಿಕ್ರಿಯೆಯ ವಿನ್ಯಾಸ:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // ಶುದ್ಧೀಕರಿಸಲಾಗಿದೆ, ಸ್ಟ್ಯಾಕ್ ಟ್ರೇಸ್ಗಳಿಲ್ಲ
}
```

**ಟಿಪ್ಪಣಿಗಳು:**

- `sk-your-omniroute-key` ಅನ್ನು OmniRoute ನಲ್ಲಿ ರಚಿಸಿದ API ಕೀಲಿಯಿಂದ ಬದಲಾಯಿಸಿ.

- URL ನಲ್ಲಿ ಅಳವಡಿಸಲಾದ ಟೋಕನ್ಗಳು ಹೊಂದಾಣಿಕೆಗಾಗಿ ಬಳಸುವ ಪರ್ಯಾಯ ವಿಧಾನವಾಗಿದ್ದು, ಅವು ಎಡಿಟರ್ ಲಾಗ್ಗಳು ಅಥವಾ ಪ್ರಾಕ್ಸಿ ಇತಿಹಾಸದಲ್ಲಿ ಕಾಣಿಸಬಹುದು.

## 10. ಆಂತರಿಕ OmniRoute CLI

`omniroute` ಬೈನರಿ ಸರ್ವರ್ ಜೀವನಚಕ್ರ, ಸೆಟಪ್, ದೋಷನಿರ್ಣಯ ಮತ್ತು ಪೂರೈಕೆದಾರರ ನಿರ್ವಹಣೆಗಾಗಿ ಕಮಾಂಡ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಪ್ರವೇಶ ಬಿಂದು: `bin/omniroute.mjs`.

```bash
omniroute                              # ಸರ್ವರ್ ಪ್ರಾರಂಭಿಸಿ (ಡೀಫಾಲ್ಟ್ ಪೋರ್ಟ್ 20128)
omniroute setup                        # ಸಂವಾದಾತ್ಮಕ ಸೆಟಪ್ ವಿಝಾರ್ಡ್
omniroute doctor                       # ಕಾನ್ಫಿಗ್, DB, ಪೋರ್ಟ್ಗಳು ಮತ್ತು ರನ್ಟೈಮ್ ಪರಿಶೀಲಿಸಿ
omniroute providers list               # ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳು
omniroute providers test-all           # ಪ್ರತಿ ಸಕ್ರಿಯ ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸಿ
omniroute reset-password               # ನಿರ್ವಾಹಕರ ಪಾಸ್ವರ್ಡ್ ಮರುಹೊಂದಿಸಿ
omniroute logs                         # ವಿನಂತಿ ಲಾಗ್ಗಳನ್ನು ಸ್ಟ್ರೀಮ್ ಮಾಡಿ
omniroute health                       # ವಿವರವಾದ ಆರೋಗ್ಯ ಸ್ಥಿತಿ (ಬ್ರೇಕರ್ಗಳು, ಕ್ಯಾಶ್, ಮೆಮೊರಿ)
omniroute --version                    # ಆವೃತ್ತಿಯನ್ನು ಮುದ್ರಿಸಿ
omniroute --help                       # ಎಲ್ಲಾ ಕಮಾಂಡ್ಗಳನ್ನು ತೋರಿಸಿ
```

### ಸೆಟಪ್ ಮತ್ತು ಪ್ರಾರಂಭೀಕರಣ

```bash
omniroute setup                        # ಸಂವಾದಾತ್ಮಕ ಸೆಟಪ್ ವಿಝಾರ್ಡ್
omniroute setup --non-interactive      # CI/ಸ್ವಯಂಚಾಲನಾ ಮೋಡ್ (ಪರಿಸರ ಚರಗಳು + ಫ್ಲ್ಯಾಗ್ಗಳನ್ನು ಓದುತ್ತದೆ)
omniroute setup --password '<value>'   # ನಿರ್ವಾಹಕರ ಪಾಸ್ವರ್ಡ್ ಅನ್ನು ನೇರವಾಗಿ ಹೊಂದಿಸಿ
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # ಒಂದೇ ಹಂತದಲ್ಲಿ ಪೂರೈಕೆದಾರರನ್ನು ಸೇರಿಸಿ ಮತ್ತು ಪರೀಕ್ಷಿಸಿ
```

ಸಂವಾದರಹಿತ ಸೆಟಪ್ಗಾಗಿ ಗುರುತಿಸಲಾಗುವ ಪರಿಸರ ಚರಗಳು:

| ಚರ                  | ಉದ್ದೇಶ                                                                 |
| ------------------- | ---------------------------------------------------------------------- |
| `OMNIROUTE_API_KEY` | ಪೂರೈಕೆದಾರ API ಕೀ (Commander `.env()` ಮೂಲಕ `--api-key`ಗೆ ಸಂಯೋಜಿಸಲಾಗಿದೆ) |
| `DATA_DIR`          | OmniRoute ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯನ್ನು ಅತಿಕ್ರಮಿಸಿ                               |

ಇತರ ಎಲ್ಲಾ ಸಂವಾದರಹಿತ ಇನ್ಪುಟ್ಗಳನ್ನು ಪರಿಸರ ಚರಗಳಾಗಿ ಅಲ್ಲದೆ ಫ್ಲ್ಯಾಗ್ಗಳಾಗಿ ರವಾನಿಸಲಾಗುತ್ತದೆ:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(ಮೇಲಿನ `omniroute setup` ಆಯ್ಕೆಗಳನ್ನು ನೋಡಿ).

### ದೋಷನಿರ್ಣಯ

```bash
omniroute doctor                       # ಕಾನ್ಫಿಗ್, DB, ಪೋರ್ಟ್ಗಳು, ರನ್ಟೈಮ್, ಮೆಮೊರಿ ಮತ್ತು ಸಕ್ರಿಯತೆಯನ್ನು ಪರಿಶೀಲಿಸಿ
omniroute doctor --json                # ಯಂತ್ರ-ಓದಬಲ್ಲ JSON
omniroute doctor --no-liveness         # HTTP ಆರೋಗ್ಯ ಪ್ರೋಬ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡಿ
omniroute doctor --host 0.0.0.0        # ಸಕ್ರಿಯತೆ ಹೋಸ್ಟ್ ಅನ್ನು ಅತಿಕ್ರಮಿಸಿ
omniroute doctor --liveness-url <url>  # ಸಂಪೂರ್ಣ ಆರೋಗ್ಯ ಎಂಡ್ಪಾಯಿಂಟ್ URL ಅನ್ನು ಅತಿಕ್ರಮಿಸಿ
```

doctor ಈ ಪರಿಶೀಲನೆಗಳನ್ನು ನಡೆಸುತ್ತದೆ: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` ಮತ್ತು `Server liveness`. ಯಾವುದೇ ಪರಿಶೀಲನೆಯು `fail` ಆಗಿದ್ದರೆ, ಇದು ಶೂನ್ಯವಲ್ಲದ ಕೋಡ್ನೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ.

### ಪೂರೈಕೆದಾರರ ನಿರ್ವಹಣೆ

```bash
omniroute providers available                       # OmniRoute ಪೂರೈಕೆದಾರರ ಕ್ಯಾಟಲಾಗ್
omniroute providers available --search openai       # id/ಹೆಸರು/ಅಲಿಯಾಸ್/ವರ್ಗದ ಆಧಾರದಲ್ಲಿ ಕ್ಯಾಟಲಾಗ್ ಫಿಲ್ಟರ್ ಮಾಡಿ
omniroute providers available --category api-key    # ವರ್ಗದ ಆಧಾರದಲ್ಲಿ ಫಿಲ್ಟರ್ ಮಾಡಿ (api-key, oauth, free, ...)
omniroute providers available --json                # ಯಂತ್ರ-ಓದಬಲ್ಲ JSON

omniroute providers list                            # ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳು
omniroute providers list --json

omniroute providers test <id|name>                  # ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಒಂದು ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸಿ
omniroute providers test-all                        # ಪ್ರತಿ ಸಕ್ರಿಯ ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸಿ
omniroute providers validate                        # ಸ್ಥಳೀಯ-ಮಾತ್ರ ರಚನಾತ್ಮಕ ಮೌಲ್ಯೀಕರಣ
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OAuth ಹರಿವು
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` API-ಪ್ರಥಮವಾಗಿವೆ ಮತ್ತು ಆದ್ದರಿಂದ ಸಕ್ರಿಯ
ಸ್ಥಳೀಯ ಅಥವಾ ದೂರಸ್ಥ ಸಂದರ್ಭದ ವಿರುದ್ಧ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ. ರುಜುವಾತು ಇನ್ಪುಟ್ಗಾಗಿ
`--credential-stdin` ಅಥವಾ `--credential-env` ಬಳಸಬೇಕು; `--dry-run --json` ಕೇವಲ
ಮರೆಮಾಡಲಾದ ಅಸ್ತಿತ್ವ/ಆಕಾರವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. `providers available` OmniRoute ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಓದುತ್ತದೆ;
`providers list/test/test-all/validate` ತಮ್ಮ ಸ್ಥಳೀಯ SQLite ವರ್ತನೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ ಮತ್ತು
ಸರ್ವರ್ ಚಾಲನೆಯಲ್ಲಿರುವ ಅಗತ್ಯವಿಲ್ಲ.

ಕಸ್ಟಮ್ OpenAI-ಹೊಂದಾಣಿಕೆಯ ಅಥವಾ Anthropic-ಹೊಂದಾಣಿಕೆಯ ನೋಡ್ಗಾಗಿ, `omniroute nodes add` ಹಿಂದಿರುಗಿಸಿದ
ನೋಡ್ IDಗೆ ರುಜುವಾತುಗಳನ್ನು ಲಗತ್ತಿಸಲು `omniroute keys add "$NODE_ID" --stdin` ಬಳಸಿ.
ಇದಕ್ಕೆ ಚಾಲನೆಯಲ್ಲಿರುವ ಸರ್ವರ್ ಮತ್ತು ಸಕ್ರಿಯ ಸಂದರ್ಭಕ್ಕಾಗಿ ನಿರ್ವಹಣಾ ದೃಢೀಕರಣದ ಅಗತ್ಯವಿದೆ.
CLI `POST /api/providers` ಅನ್ನು ಬಳಸುತ್ತದೆ; ಇದು ನೋಡ್ ಅನ್ನು ಮೌಲ್ಯೀಕರಿಸಿ, ಅದರ ಎಂಡ್ಪಾಯಿಂಟ್
ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಸಂಪರ್ಕಕ್ಕೆ ನಕಲಿಸುತ್ತದೆ. ನೋಡ್ ಇಲ್ಲದಿರುವುದು, ದೃಢೀಕರಣ ವೈಫಲ್ಯ ಅಥವಾ ಲಭ್ಯವಿಲ್ಲದ
ಸರ್ವರ್—ಇವು ಸ್ಥಳೀಯ ಫಾಲ್ಬ್ಯಾಕ್ ರುಜುವಾತನ್ನು ರಚಿಸದೆಯೇ ದೋಷವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತವೆ.

`nodes add --base-url` ನೋಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ; ಇದು
`OMNIROUTE_BASE_URL`ನಲ್ಲಿರುವ ಸರ್ವರ್ ವಿಳಾಸಕ್ಕಿಂತ ಭಿನ್ನವಾಗಿದೆ. OpenAPI ಫೈಲ್ಗಳಿಗಾಗಿ,
`omniroute openapi dump --format json --out ./openapi.json` ಬಳಸಿ; ಜಾಗತಿಕ `--output`
CLI ಪ್ರದರ್ಶನ ಫಾರ್ಮ್ಯಾಟಿಂಗ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ, ಗಮ್ಯಸ್ಥಾನ ಫೈಲ್ಹೆಸರನ್ನಲ್ಲ.

### ಮರುಪಡೆಯುವಿಕೆ ಮತ್ತು ಮರುಹೊಂದಿಸುವಿಕೆ

```bash
omniroute reset-password                # ನಿರ್ವಾಹಕರ ಪಾಸ್ವರ್ಡ್ ಮರುಹೊಂದಿಸಿ (ಇದಾಗಿಯೂ ಲಭ್ಯ: omniroute-reset-password)
omniroute reset-encrypted-columns       # ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ರುಜುವಾತುಗಳ ಮರುಹೊಂದಿಸುವಿಕೆಗಾಗಿ ಎಚ್ಚರಿಕೆ + ಡ್ರೈ-ರನ್ ತೋರಿಸಿ
omniroute reset-encrypted-columns --force  # SQLiteನಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ರುಜುವಾತುಗಳನ್ನು ನಿಜವಾಗಿಯೂ ಶೂನ್ಯಗೊಳಿಸಿ
```

### ರುಜುವಾತು ರಫ್ತು (⚠ ಎಚ್ಚರಿಕೆಯಿಂದ ನಿರ್ವಹಿಸಿ)

```bash
omniroute auth export                                 # ಎಚ್ಚರಿಕೆ + ದೃಢೀಕರಣ ಹಂತವನ್ನು ತೋರಿಸಿ — DB ಪ್ರವೇಶವಿಲ್ಲ
omniroute auth export --force                          # ಎಲ್ಲಾ ಸಂಪರ್ಕಗಳ ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ರುಜುವಾತುಗಳನ್ನು JSON ಆಗಿ stdoutಗೆ ರಫ್ತು ಮಾಡಿ
omniroute auth export --force --id <id>                 # ಹೊಂದಿಕೆಯಾಗುವ ಸಂಪರ್ಕವನ್ನು ಮಾತ್ರ ರಫ್ತು ಮಾಡಿ
omniroute auth export --force --format env               # OMNIROUTE_<PROVIDER>_<FIELD>=<value> ಸಾಲುಗಳನ್ನು ಹೊರಸೂಸಿ
omniroute auth export --force --out creds.json           # ಫೈಲ್ಗೆ ಬರೆಯಿರಿ (0600 ಅನುಮತಿಗಳೊಂದಿಗೆ ರಚಿಸಲಾಗುತ್ತದೆ)
```

`auth export` **ಸ್ಥಳೀಯವಾಗಿ ಮಾತ್ರ** ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ (ನೇರ SQLite ಓದುವಿಕೆ, ಯಾವುದೇ HTTP route ಇಲ್ಲ) ಮತ್ತು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
**ಸರಳಪಠ್ಯ** `apiKey`/`accessToken`/`refreshToken`/`idToken` ಮೌಲ್ಯಗಳನ್ನು ಮುದ್ರಿಸುತ್ತದೆ/ಬರೆಯುತ್ತದೆ — ಇದು ವೈಶಿಷ್ಟ್ಯವೇ ಹೊರತು
ದೋಷವಲ್ಲ. `--force` ಇಲ್ಲದೆ ಡೇಟಾಬೇಸ್ನಿಂದ ಏನನ್ನೂ ಓದಲಾಗುವುದಿಲ್ಲ ಮತ್ತು ಯಾವುದನ್ನೂ ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಯಾವುದೇ ಸರಳಪಠ್ಯವನ್ನು ಹೊರಸೂಸುವ ಮೊದಲು stderr
ಎಚ್ಚರಿಕೆ ಬ್ಯಾನರ್ ಯಾವಾಗಲೂ ಮುದ್ರಿಸಲಾಗುತ್ತದೆ. `STORAGE_ENCRYPTION_KEY` ಹೊಂದಿಸಿರಬೇಕು.
ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲು ವಿಫಲವಾದ ಕ್ಷೇತ್ರವನ್ನು (ಹಳತಾದ ಕೀ, ದೋಷಪೂರಿತ ciphertext) ಸಂಪೂರ್ಣ export ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುವ ಅಥವಾ ಮೂಲ ದೋಷವನ್ನು ಬಹಿರಂಗಪಡಿಸುವ ಬದಲು
`<field>DecryptFailed: true` ಎಂದು ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ.

### ಇತರ ಉಪಕಮಾಂಡ್ಗಳು

ಬೇರೆ ರೀತಿಯಲ್ಲಿ ಸೂಚಿಸದ ಹೊರತು, ಇವು ಚಾಲನೆಯಲ್ಲಿರುವ OmniRoute ಸರ್ವರ್ ಅನ್ನು ಅವಲಂಬಿಸಿವೆ:

```bash
omniroute status                       # ಸಮಗ್ರ runtime ಸ್ಥಿತಿ
omniroute logs                         # ವಿನಂತಿ ಲಾಗ್ಗಳನ್ನು ಸ್ಟ್ರೀಮ್ ಮಾಡಿ (--json, --search, --follow)
omniroute config list                  # ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ CLI ಉಪಕರಣಗಳನ್ನು ಪ್ರದರ್ಶಿಸಿ

omniroute provider list                # ಲಭ್ಯವಿರುವ providerಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡಿ (providers list ನ alias)
omniroute provider add                 # ಉಪಕರಣವೊಂದರಲ್ಲಿ OmniRoute ಅನ್ನು provider ಆಗಿ ನೋಂದಾಯಿಸಿ
omniroute keys add | list | remove     # API ಕೀಗಳನ್ನು ನಿರ್ವಹಿಸಿ
omniroute models [provider]            # ಮಾಡೆಲ್ಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡಿ (--json, --search)
omniroute combo list | switch | create | delete

omniroute backup                       # config + DB snapshot ರಚಿಸಿ
omniroute restore                      # ಹಿಂದಿನ snapshot ನಿಂದ ಮರುಸ್ಥಾಪಿಸಿ

omniroute health                       # ವಿವರವಾದ ಆರೋಗ್ಯ ಸ್ಥಿತಿ (breakers, cache, memory)
omniroute quota                        # provider quota ಬಳಕೆ
omniroute cache                        # cache ಸ್ಥಿತಿ
omniroute cache clear                  # semantic + signature cacheಗಳನ್ನು ತೆರವುಗೊಳಿಸಿ

omniroute mcp status | restart         # MCP ಸರ್ವರ್ ಸ್ಥಿತಿ / ಮರುಪ್ರಾರಂಭ
omniroute a2a status | card            # A2A ಸರ್ವರ್ ಸ್ಥಿತಿ / agent card

omniroute tunnel list | create | stop  # tunnelಗಳನ್ನು ನಿರ್ವಹಿಸಿ (cloudflare/tailscale/ngrok)
omniroute env show | get <k> | set <k> <v>  # env vars ಪರಿಶೀಲಿಸಿ / ಹೊಂದಿಸಿ (ತಾತ್ಕಾಲಿಕ)

omniroute test                         # provider ಸಂಪರ್ಕದ smoke test
omniroute update                       # updateಗಳಿಗಾಗಿ ಪರಿಶೀಲಿಸಿ
omniroute completion                   # shell completion ರಚಿಸಿ
```

## OmniRoute CLI ಮೂಲಕ ಇನ್ಫರೆನ್ಸ್-ಕೀ ನೀತಿಯನ್ನು ನಿರ್ವಹಿಸಿ

ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಇನ್ಫರೆನ್ಸ್ ಕೀಯನ್ನು ಅದರ ID ಮೂಲಕ ಪರಿಶೀಲಿಸಲು ಅಥವಾ ನವೀಕರಿಸಲು ದೃಢೀಕೃತ ನಿರ್ವಹಣಾ ಸಂದರ್ಭವನ್ನು ಬಳಸಿ ([ರಿಮೋಟ್ ಮೋಡ್](../guides/REMOTE-MODE.md) ನೋಡಿ):

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted` ಎಂಬುದು `--model-access-mode all` ಗೆ ಪರ್ಯಾಯ ಹೆಸರು. ನವೀಕರಣವು
ಮಾದರಿ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ. ಇದು ಸ್ಕೋಪ್ಗಳು, ಸಂಪರ್ಕ ನಿಯಮಗಳು, ನಿರ್ಬಂಧಿತ ಮಾದರಿಗಳು, ದರ ಮಿತಿಗಳು
ಮತ್ತು ವೆಚ್ಚ ಮಿತಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ; ಆದ್ದರಿಂದ ಆ ಇತರ ನಿಯಂತ್ರಣಗಳು ಇನ್ನೂ ವಿನಂತಿಯನ್ನು ನಿರಾಕರಿಸಬಹುದು. ಸ್ಪಷ್ಟವಾದ
`--allowed-models ""` ಸಹ `all` ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ; ಯಾವುದೇ ಅನುಮತಿಸಲಾದ ಮಾದರಿಗಳಿಲ್ಲದ ನಿರ್ಬಂಧಿತ ಕೀಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲು ಅದನ್ನು
`--model-access-mode restricted` ಜೊತೆಗೆ ಬಳಸಿ.
ಖಾಲಿಯಲ್ಲದ, ಅಲ್ಪವಿರಾಮದಿಂದ ಬೇರ್ಪಡಿಸಿದ ಪಟ್ಟಿಯು ಸ್ಪಷ್ಟವಾಗಿ ನಿರ್ದಿಷ್ಟಪಡಿಸದ ಹೊರತು `restricted` ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ.
ಪರಸ್ಪರ ವಿರೋಧಾಭಾಸದ `all` ಮತ್ತು ಖಾಲಿಯಲ್ಲದ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಹೊಂದಿರುವ ಸಂಯೋಜನೆಯು ವಿನಂತಿಯನ್ನು ಕಳುಹಿಸುವ ಮೊದಲು ತಿರಸ್ಕರಿಸಲ್ಪಡುತ್ತದೆ.

`--rate-limit 30` ಪ್ರತಿ ನಿಮಿಷದ ವಿನಂತಿಗಳ ಸಂಖ್ಯೆಯನ್ನು ಹೊಂದಿಸುತ್ತದೆ ಮತ್ತು ಇತರ ಸಮಯ
ವಿಂಡೋಗಳ ನಿಯಮಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ. `--max-cost 5` ಸಾಪ್ತಾಹಿಕ ಮಿತಿಯನ್ನು ಬದಲಾಯಿಸದೆ ದೈನಂದಿನ USD ಮಿತಿಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ;
`--max-cost 0` ದೈನಂದಿನ ಮಿತಿಯನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಬಳಕೆ-ಮಿತಿ ಟಾಗಲ್
ಮತ್ತು ಸಾಪ್ತಾಹಿಕ ಮಿತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ. ಬಿಟ್ಟುಬಿಡಲಾದ ನೀತಿ ಕ್ಷೇತ್ರಗಳು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತವೆ. ದರ ಬದಲಾವಣೆಗಳು ಮೊದಲು
ಪ್ರಸ್ತುತ ನೀತಿಯನ್ನು ಓದುತ್ತವೆ; ಅದೇ ಕೀಯ ದರ-ಮಿತಿ ಅರೇಗೆ ಏಕಕಾಲಿಕ ಸಂಪಾದನೆಗಳನ್ನು ತಪ್ಪಿಸಿ.

ನೀತಿ ಕಮಾಂಡ್ಗಳು ದೃಢೀಕೃತ `GET`/`PATCH /api/keys/{id}` ಅನ್ನು ಬಳಸುತ್ತವೆ ಮತ್ತು ಸಕ್ರಿಯ
ಸಂದರ್ಭ ಹಾಗೂ ಜಾಗತಿಕ `--api-key` ಆಯ್ಕೆಯನ್ನು ಪಾಲಿಸುತ್ತವೆ. JSON ಔಟ್ಪುಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಿದ ಕೀ ಅಥವಾ ಅದರ ಮರೆಮಾಡಿದ ನಿರೂಪಣೆ ಇಲ್ಲದೆ,
ನೀತಿ ಕ್ಷೇತ್ರಗಳು ಮಾತ್ರ ಇರುತ್ತವೆ. ಕೇವಲ ಇನ್ಫರೆನ್ಸ್ಗಾಗಿ ಇರುವ ಕ್ರೆಡೆನ್ಶಿಯಲ್
ನಿರ್ವಹಣಾ ಬದಲಾವಣೆಗಳಿಗೆ ಅನುಮತಿ ನೀಡಲಾಗುವುದಿಲ್ಲ. 401/403 ಬಂದರೆ ನಿರ್ವಹಣಾ
ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಮತ್ತು ಸಂದರ್ಭವನ್ನು ಪರಿಶೀಲಿಸಬೇಕು; ಅದು ಸ್ಥಳೀಯ CLI-ಟೋಕನ್ ಅಥವಾ ಸಾಲ್ಟ್ ವೈಫಲ್ಯವನ್ನು ಸಾಬೀತುಪಡಿಸುವುದಿಲ್ಲ.
ಪ್ರತ್ಯೇಕ ಸ್ಥಳೀಯ ದೃಢೀಕರಣ ಒಪ್ಪಂದಕ್ಕಾಗಿ [CLI ಟೋಕನ್](../security/CLI_TOKEN.md) ನೋಡಿ.
