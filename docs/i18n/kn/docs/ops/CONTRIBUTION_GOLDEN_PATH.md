ಪುಲ್ ರಿಕ್ವೆಸ್ಟ್ಗಾಗಿ ಅತ್ಯಂತ ಚಿಕ್ಕದಾದ ವಿಶ್ವಾಸಾರ್ಹ ಅಭಿವೃದ್ಧಿ ಲೂಪ್ ಅನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಈ ಮಾರ್ಗದರ್ಶಿಯನ್ನು ಬಳಸಿ. ಇದು ಕೆಳಗೆ ಲಿಂಕ್
ಮಾಡಲಾದ ಕ್ಷೇತ್ರ-ನಿರ್ದಿಷ್ಟ ಆರ್ಕಿಟೆಕ್ಚರ್ ಮತ್ತು ಭದ್ರತಾ ದಾಖಲೆಗಳನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ; ಇದು ಪ್ರತಿಯೊಂದು ಸಾಮಾನ್ಯ
ಬದಲಾವಣೆಯ ಪ್ರಕಾರವನ್ನು ಅದರ ಒಪ್ಪಂದಗಳು, ಕೇಂದ್ರೀಕೃತ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು CI ವ್ಯಾಪ್ತಿಯೊಂದಿಗೆ ಸಂಪರ್ಕಿಸುತ್ತದೆ.

## ಪ್ರತಿಯೊಂದು ಬದಲಾವಣೆಯೂ ಅನುಸರಿಸುವ ಮಾರ್ಗ

1. **ಸಂಪಾದಿಸುವ ಮೊದಲು ಮೂಲ ಶಾಖೆಯನ್ನು ಆಯ್ಕೆಮಾಡಿ.** ಅತ್ಯುನ್ನತ ಸಕ್ರಿಯ `release/v*` ಶಾಖೆಯನ್ನು ಹುಡುಕಿ ಮತ್ತು
   ಅದರ ತುದಿಯಿಂದ ಶಾಖೆಯನ್ನು ರಚಿಸಿ. `main` ಅನ್ನು ಅಲ್ಲ, ಆ ಶಾಖೆಯನ್ನು ಗುರಿಯಾಗಿಸಿ. ಬಿಡುಗಡೆ ಸ್ಥಗಿತವು ಸಕ್ರಿಯವಾಗಿದ್ದರೆ, ಸ್ಥಗಿತಗೊಂಡ
   ಶಾಖೆಯನ್ನು ಗುರಿಯಾಗಿಸಬೇಡಿ; [ಶಾಖೆಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಬಿಡುಗಡೆ ಮಾದರಿ](BRANCHING_MODEL.md)ಯಲ್ಲಿ
   ವಿವರಿಸಲಾದ ಮುಂದಿನ ಸಕ್ರಿಯ ಚಕ್ರವನ್ನು ಬಳಸಿ.
2. **ಒಪ್ಪಂದಗಳನ್ನು ಹೆಸರಿಸಿ.** ಬದಲಾವಣೆಯು ಪರಿಣಾಮ ಬೀರುವ ಪ್ರತಿಯೊಂದು ಕ್ಯಾಟಲಾಗ್, ಸ್ಕೀಮಾ, ರಚಿಸಲಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್, ಸಾರ್ವಜನಿಕ API, ಅಥವಾ ಬಳಕೆದಾರ
   ಇಂಟರ್ಫೇಸ್ ಅನ್ನು ಗುರುತಿಸಿ. ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಕನಿಷ್ಠ ಆರಂಭಿಕ ಸಮೂಹವನ್ನು ನೀಡುತ್ತದೆ.
3. **ಕೇಂದ್ರೀಕೃತ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ ಅಥವಾ ನವೀಕರಿಸಿ.** `src/`, `open-sse/`, `electron/`, ಅಥವಾ
   `bin/`ನಲ್ಲಿನ ಪ್ರೊಡಕ್ಷನ್ ಬದಲಾವಣೆಗಳಿಗೆ ಅದೇ PRನಲ್ಲಿ ಸ್ವಯಂಚಾಲಿತ ಪರೀಕ್ಷೆಯ ಅಗತ್ಯವಿದೆ. ನಡವಳಿಕೆಯನ್ನು ಸಾಬೀತುಪಡಿಸುವ ಅತ್ಯಂತ ಚಿಕ್ಕ
   ಪರೀಕ್ಷಾ ಫೈಲ್ಗಳನ್ನು ಚಲಾಯಿಸಿ, ನಂತರ ಪಟ್ಟಿ ಮಾಡಲಾದ ಕೇಂದ್ರೀಕೃತ ಗೇಟ್ಗಳನ್ನು ಚಲಾಯಿಸಿ.
4. **ವಿಶಾಲ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು CI ಚಲಾಯಿಸಲು ಬಿಡಿ.** ಸಂಪೂರ್ಣ ಯೂನಿಟ್ ಶಾರ್ಡ್ಗಳು, Vitest, ಕವರೆಜ್ ರ್ಯಾಚೆಟ್ ಮತ್ತು
   ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ PRನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ. ಕೇಂದ್ರೀಕೃತ ವೈಫಲ್ಯವು ವ್ಯಾಪಕ ಪರಿಣಾಮವನ್ನು ಸೂಚಿಸಿದಾಗ ಅಥವಾ ಬದಲಾವಣೆಯು
   ಹಲವಾರು ಉಪವ್ಯವಸ್ಥೆಗಳನ್ನು ವ್ಯಾಪಿಸಿದಾಗ ಮಾತ್ರ ವಿಶಾಲ ಸೂಟ್ ಅನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಿ.
5. **ಪರಿಶೀಲನೆಗೂ ಮೊದಲು ಸಮನ್ವಯಗೊಳಿಸಿ.** ಸಕ್ರಿಯ ಮೂಲ ಶಾಖೆಯನ್ನು ಫೆಚ್ ಮಾಡಿ, ಅದರ ಹೊಸ ಕಮಿಟ್ಗಳು ಮತ್ತು ಅದಕ್ಕೆ ಹೋಲಿಸಿದಾಗ ನಿಮ್ಮ ಡಿಫ್ ಅನ್ನು
   ಪರಿಶೀಲಿಸಿ, ನಂತರ ಕೊಡುಗೆದಾರರ ವರ್ಕ್ಫ್ಲೋಗೆ ಅನುಗುಣವಾಗಿ ಮೂಲ ಶಾಖೆಯನ್ನು ರಿಬೇಸ್ ಅಥವಾ ಮರ್ಜ್ ಮಾಡಿ. ರಚಿಸಲಾದ ಫೈಲ್
   ಮತ್ತು ಕ್ಯಾಟಲಾಗ್ ಸಂಘರ್ಷಗಳನ್ನು ಅವುಗಳ ಮೂಲದಿಂದ ಪರಿಹರಿಸಿ, ಅವುಗಳನ್ನು ಮರುರಚಿಸಿ, ಕೇಂದ್ರೀಕೃತ ಲೂಪ್ ಅನ್ನು ಮರುಚಲಾಯಿಸಿ ಮತ್ತು
   PR ಇನ್ನೂ ಸಕ್ರಿಯ ಬಿಡುಗಡೆ ಶಾಖೆಯನ್ನೇ ಗುರಿಯಾಗಿಸಿದೆ ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ.
6. **ಸಾಕ್ಷ್ಯವನ್ನು ದಾಖಲಿಸಿ.** PR ಟೆಂಪ್ಲೇಟ್ನಲ್ಲಿ, ಚಲಾಯಿಸಿದ ಕಮಾಂಡ್ಗಳು, ಸೇರಿಸಿದ ಅಥವಾ ಬದಲಾಯಿಸಿದ ಪ್ರತಿಯೊಂದು ಪರೀಕ್ಷಾ ಫೈಲ್,
   ಮೈಗ್ರೇಶನ್ಗಳು ಅಥವಾ ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ಗಳು ಮತ್ತು ಇನ್ನೂ ಬಾಕಿಯಿರುವ ಯಾವುದೇ CI-ಮಾತ್ರದ ಮೌಲ್ಯೀಕರಣವನ್ನು ಪಟ್ಟಿ ಮಾಡಿ.

## ಬದಲಾವಣೆಯ ಪ್ರಕಾರದ ಸುವರ್ಣ ಮಾರ್ಗಗಳು

ಕೆಳಗಿನ ಕಮಾಂಡ್ಗಳು ಕನಿಷ್ಠ ಕೇಂದ್ರೀಕೃತ ಪರಿಶೀಲನೆಗಳಾಗಿವೆ; ನೀವು ಬದಲಾಯಿಸಿದ ನಡವಳಿಕೆಯನ್ನು ನೇರವಾಗಿ ಒಳಗೊಳ್ಳುವ ಪರೀಕ್ಷೆಯನ್ನು
ಬಿಟ್ಟುಬಿಡಲು ಇವು ಅನುಮತಿಯಲ್ಲ.

### ಪ್ರೊವೈಡರ್

**ಒಪ್ಪಂದಗಳು**

- `src/shared/constants/providers/`ನಲ್ಲಿನ ಪ್ರೊವೈಡರ್ ವ್ಯಾಖ್ಯಾನ ಮತ್ತು
  `src/shared/constants/providers.ts`ನಲ್ಲಿನ ಅದರ ಸಂಯೋಜನೆ.
- `open-sse/config/providerRegistry.ts` ಅಥವಾ ಅದರಿಂದ ಹೊರತೆಗೆಯಲಾದ ರಿಜಿಸ್ಟ್ರಿ ಫೈಲ್ಗಳಲ್ಲಿನ ಮಾಡೆಲ್ಗಳು ಮತ್ತು ಸಾಮರ್ಥ್ಯಗಳು.
- ಅನ್ವಯಿಸುವಾಗ ಎಕ್ಸಿಕ್ಯೂಟರ್/ಟ್ರಾನ್ಸ್ಲೇಟರ್ ಆಯ್ಕೆ, OAuth ಅಥವಾ API-ಕೀ ಕಾನ್ಫಿಗರೇಶನ್, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಅಸೆಟ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ
  ಪ್ರೊವೈಡರ್ ಉಲ್ಲೇಖ.
- ಸಾರ್ವಜನಿಕ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು `resolvePublicCred()` ಅನ್ನು ಬಳಸಬೇಕು; ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳು ಹಂಚಿಕೊಂಡ ಸ್ಯಾನಿಟೈಸ್ ಮಾಡಿದ
  ದೋಷ ಸಹಾಯಕಗಳನ್ನು ಬಳಸಬೇಕು. `docs/security/PUBLIC_CREDS.md` (git; `/docs`ನಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ) ಮತ್ತು
  [ದೋಷ ಸ್ಯಾನಿಟೈಸೇಶನ್](../security/ERROR_SANITIZATION.md) ನೋಡಿ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # ಕ್ಯಾಟಲಾಗ್ ಬದಲಾದಾಗ; ರಚಿಸಲಾದ ಡಿಫ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ
npm run lint
```

ಪರಿಣಾಮ ಬೀರುವ ಪ್ರತಿಯೊಂದು ವಿನಂತಿ ಕುಟುಂಬವನ್ನೂ ಪರೀಕ್ಷಿಸಿ: chat, Responses, images, embeddings, audio, ಅಥವಾ video.
ರಚಿಸಲಾದ ಕ್ಯಾಟಲಾಗ್ ಮತ್ತು ಗೋಲ್ಡನ್ ಡಿಫ್ಗಳನ್ನು ಒಪ್ಪಂದದ ಬದಲಾವಣೆಗಳಾಗಿ ಪರಿಶೀಲಿಸಿ; ಅವುಗಳನ್ನು ಕುರುಡಾಗಿ ಸ್ವೀಕರಿಸಬೇಡಿ.

### ರೂಟಿಂಗ್

**ಒಪ್ಪಂದಗಳು**

- `src/shared/constants/routingStrategies.ts`ನಲ್ಲಿನ ಸಾರ್ವಜನಿಕ ಸ್ಟ್ರಾಟಜಿ ಮೌಲ್ಯಗಳು ಮತ್ತು UI ಮೆಟಾಡೇಟಾ.
- `open-sse/services/combo.ts` ಮತ್ತು `open-sse/services/combo/` ಅಡಿಯಲ್ಲಿನ ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು ಕ್ರಮಗೊಳಿಸುವಿಕೆ.
- ಕಾಂಬೊ ಸ್ಕೀಮಾಗಳು, ಪರ್ಸಿಸ್ಟೆನ್ಸ್, ರೆಸಿಲಿಯನ್ಸ್ ಸ್ಥಿತಿ, ಮಾಡೆಲ್ ಸಾಮರ್ಥ್ಯಗಳು ಮತ್ತು API/UI ನಿಯಂತ್ರಣಗಳು.
- ನಡವಳಿಕೆ ಬದಲಾದಾಗ [ಆಟೋ-ಕಾಂಬೊ ಎಂಜಿನ್](../routing/AUTO-COMBO.md) ಮತ್ತು ರೆಸಿಲಿಯನ್ಸ್ ದಾಖಲೆ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ಸ್ಟ್ರಾಟಜಿ ಅಥವಾ ಡಿಸ್ಪ್ಯಾಚ್ ಬದಲಾವಣೆಗಳು
npm run check:known-symbols      # ಸ್ಟ್ರಾಟಜಿ ನೋಂದಣಿ ಬದಲಾವಣೆಗಳು
```

### ಬಿಲ್ಡ್ / ನಿಯೋಜನೆ

**ಒಪ್ಪಂದಗಳು**

- ರೂಟ್ ಮತ್ತು ವರ್ಕ್ಸ್ಪೇಸ್ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳು/ಲಾಕ್ಫೈಲ್, `scripts/build/`, Next.js ಸ್ಟ್ಯಾಂಡ್ಅಲೋನ್ ಅಸೆಂಬ್ಲಿ, `dist/`
  ಪ್ಯಾಕೇಜ್ ವಿಷಯಗಳು, Electron ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಮೆಟಾಡೇಟಾ, CI ವರ್ಕ್ಫ್ಲೋಗಳು ಮತ್ತು ನಿಯೋಜನೆ ಸೆಂಟಿನಲ್ಗಳು.
- ಬೆಂಬಲಿತ Node ಶ್ರೇಣಿಗಳು ಮತ್ತು `CLAUDE.md` ನಲ್ಲಿನ ಅನುಮತಿ-ಪಟ್ಟಿಯ Bun ಬಳಕೆ ಅಬಾಧಿತವಾಗಿರಬೇಕು.
- ಬಿಲ್ಡ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು ಟ್ರ್ಯಾಕ್ ಮಾಡದೆ ಉಳಿಯಬೇಕು; ಡಿಪೆಂಡೆನ್ಸಿ, ಪರವಾನಗಿ, ವರ್ಕ್ಫ್ಲೋ ಮತ್ತು ಪ್ಯಾಕೇಜ್ ನೀತಿಗಳು ಅನ್ವಯಿಸುತ್ತವೆ.

**ಕೇಂದ್ರೀಕೃತ ಚಕ್ರ**

ಬದಲಾವಣೆಯು ಕಂಪೈಲೇಶನ್, ಸ್ಟ್ಯಾಂಡ್ಅಲೋನ್ ಅಸೆಂಬ್ಲಿ, ಅಸೆಟ್ಗಳು ಅಥವಾ ರನ್ಟೈಮ್ ಬಂಡ್ಲಿಂಗ್ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರಿದಾಗ ಮಾತ್ರ ಸ್ಥಳೀಯವಾಗಿ `npm run build` ಬಳಸಿ. ಬಿಡುಗಡೆ/ನಿಯೋಜನೆ ಮೌಲ್ಯೀಕರಣಕ್ಕಾಗಿ ಮಾತ್ರ `npm run build:release` ಬಳಸಿ. CI ಬಿಲ್ಡ್ ಅಂತಿಮ ಕ್ರಾಸ್-ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಸಂಕೇತವಾಗಿದೆ; ಪ್ಲಾಟ್ಫಾರ್ಮ್-ನಿರ್ದಿಷ್ಟ Electron ಬದಲಾವಣೆಗಳಿಗೆ ಹೊಂದಾಣಿಕೆಯ ಕೇಂದ್ರೀಕೃತ ಬಿಲ್ಡ್ ಅಥವಾ ಸ್ಮೋಕ್ ಪರೀಕ್ಷೆಯ ಸಾಕ್ಷ್ಯ ಅಗತ್ಯವಿದೆ.

## ಹಂಚಿಕೆಯ ಯಂತ್ರಕ್ಕಾಗಿ ಡೆವಲಪರ್ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು

ಇತರ ಸೆಷನ್ಗಳು ಸಕ್ರಿಯವಾಗಿರುವ devboxನಲ್ಲಿ ಸ್ಥಳೀಯ ಲೂಪ್ ಅನ್ನು ಎರಡು `scripts/dev/` ಸಹಾಯಕಗಳು ಸಂಕೇತಿಸುತ್ತವೆ:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD ನಿಂದ ಫೈಲ್ಗಳು
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ನಿಖರವಾಗಿ ಈ ಫೈಲ್ಗಳು
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # ಪ್ರತ್ಯೇಕ worktree, ಸಮಾನಾಂತರವಾಗಿ ಸುರಕ್ಷಿತ
```

- `typecheck-touched.sh` 6 GB heap ಅಡಿಯಲ್ಲಿ ತಾತ್ಕಾಲಿಕ
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ಮೂಲಕ ಸ್ಪರ್ಶಿಸಲಾದ `.ts/.tsx` ಫೈಲ್ಗಳಿಗೆ ಮಾತ್ರ typecheck ಮಾಡುತ್ತದೆ; ಆದ್ದರಿಂದ, ಲೋಡ್ ಆಗಿರುವ ಯಂತ್ರದಲ್ಲಿ OOM ಆಗುವ ಪ್ರಾಜೆಕ್ಟ್-ವ್ಯಾಪಿ `tsc -p tsconfig.json`
  ಅನ್ನು ಇದು ಬದಲಿಸುತ್ತದೆ. ಇದು ಸ್ಪರ್ಶಿಸಲಾದ ಫೈಲ್ಗಳಲ್ಲಿನ ದೋಷಗಳ ಜೊತೆಗೆ ಒಂದು ಸಾರಾಂಶ ಸಾಲನ್ನು ಮುದ್ರಿಸುತ್ತದೆ ಮತ್ತು ಸ್ಪರ್ಶಿಸಲಾದ ಫೈಲ್ಗಳಲ್ಲಿ ದೋಷಗಳಿದ್ದರೆ
  `1`, ದೋಷಗಳು ಆಮದು ಮಾಡಿಕೊಂಡ ಫೈಲ್ಗಳಲ್ಲಿ ಮಾತ್ರ ಇದ್ದರೆ ಅಥವಾ diagnostics ಇಲ್ಲದೆ tsc ಸ್ಥಗಿತಗೊಂಡಿದ್ದರೆ `2`
  (`_artifacts/typecheck-touched/` ಅಡಿಯಲ್ಲಿ ಅದು ಹೆಸರಿಸುವ ಲಾಗ್ ಅನ್ನು ಓದಿ), ಯಾವುದೇ ದೋಷವಿಲ್ಲದಿದ್ದರೆ `0` ನೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ.
  ತಾತ್ಕಾಲಿಕ tsconfig ಅನ್ನು ಯಾವಾಗಲೂ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ; ಅದನ್ನು ಎಂದಿಗೂ commit ಮಾಡಬೇಡಿ.
- `new-worktree.sh` ಏಕಕಾಲಿಕ ರನ್ಗಳನ್ನು `<git-common-dir>/omniroute-new-worktree.lock` ಮೇಲೆ ಕ್ರಮಬದ್ಧಗೊಳಿಸುತ್ತದೆ
  (ಡೀಫಾಲ್ಟ್ ಆಗಿ ಗರಿಷ್ಠ 600 s ಕಾಯುತ್ತದೆ ಮತ್ತು ಕಾಣಿಸುವ ಸಂದೇಶವನ್ನು ತೋರಿಸುತ್ತದೆ; ಅದನ್ನು ಅತಿಕ್ರಮಿಸುವ ವಿಧಾನವನ್ನು ಸ್ಕ್ರಿಪ್ಟ್ header ದಾಖಲಿಸುತ್ತದೆ)
  ಹಾಗೂ worktree ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು `git worktree add` ವಿಫಲವಾದಾಗ ಅದು ರಚಿಸಿದ branch ಅನ್ನು ಹಿಂದಕ್ಕೆ ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ; ಆದ್ದರಿಂದ ಮರುಪ್ರಯತ್ನಕ್ಕೆ
  ಕೈಯಾರೆ `git branch -D` ಮಾಡುವ ಅಗತ್ಯವಿಲ್ಲ. hard-link ಮಾಡಲಾದ `node_modules` ಮತ್ತು `.husky/_` ನಕಲು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತವೆ.

## ಸ್ಥಳೀಯ candidate ಲೂಪ್

ಪ್ಯಾಕೇಜ್ ಮಾಡಿದ artifact boot ಆಗುತ್ತದೆ ಎಂಬುದನ್ನು source tests ಸಾಬೀತುಪಡಿಸಲಾರವು: packaging ಪಟ್ಟಿಗಳು, prune ಮಾಡಿದ dependencies
ಮತ್ತು native binaries, tarball ಅನ್ನು install ಮಾಡಿ start ಮಾಡಿದ ನಂತರವೇ ವಿಫಲವಾಗುತ್ತವೆ. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ಎಂಬುದು RFC #8084 ರ build-once / validate / promote flow ನ ಸ್ಥಳೀಯ ಭಾಗವಾಗಿದೆ:
ಇದು ಒಂದು candidate ಅನ್ನು build ಮಾಡುತ್ತದೆ, ಅದೇ artifact ಅನ್ನು validate ಮಾಡುತ್ತದೆ, directory rename ಗಳ ಮೂಲಕ ಅದನ್ನು promote ಮಾಡುತ್ತದೆ
ಮತ್ತು promote ಮಾಡಿದ slot ನ health check ವಿಫಲವಾದಾಗ ಅದನ್ನು rollback ಮಾಡುತ್ತದೆ.

```bash
npm run dev:candidate -- run --dry-run --json  # ಯೋಜನೆಯನ್ನು ಮುದ್ರಿಸಿ, ಏನನ್ನೂ ಬದಲಿಸಬೇಡಿ
npm run dev:candidate -- run                   # build + validate + promote, ಸ್ವಯಂಚಾಲಿತ rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ಒಳಗೆ install
npm run dev:candidate -- validate --id <id>    # ಲಭ್ಯವಿರುವ port ನಲ್ಲಿ boot ಮಾಡಿ, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current ಮತ್ತು previous ಅನ್ನು ಅದಲುಬದಲು ಮಾಡಿ
npm run dev:candidate -- run --from-tarball <file.tgz>  # ಬೇರೆಡೆ build ಮಾಡಿದ tarball ಅನ್ನು ಮರುಬಳಸಿ (CI)
```

- **ಒಮ್ಮೆ build ಮಾಡಿ.** `build` ಪ್ರಸ್ತುತ tree ಅನ್ನು pack ಮಾಡುತ್ತದೆ (ಇದಕ್ಕೆ `dist/server.js` ಅಗತ್ಯವಿರುವುದರಿಂದ, ಮೊದಲು
  `npm run build:release` ಚಲಾಯಿಸಿ) ಅಥವಾ `--from-tarball` ಅನ್ನು ನಕಲಿಸುತ್ತದೆ; ನಂತರ tarball ಅನ್ನು ಪ್ರತ್ಯೇಕ npm prefix ಒಳಗೆ install ಮಾಡುತ್ತದೆ,
  ಏಕೆಂದರೆ tarball ನಲ್ಲಿ `node_modules` ಇರುವುದಿಲ್ಲ. id ಎಂದರೆ ಸಂಕ್ಷಿಪ್ತ `HEAD`
  sha (tree ನಲ್ಲಿ ಸ್ಥಳೀಯ ಬದಲಾವಣೆಗಳಿದ್ದಾಗ `-dirty`) ಅಥವಾ tarball ಗಾಗಿ `tgz-<sha256>`. ಈಗಾಗಲೇ build ಆಗಿರುವ clean id ಅನ್ನು
  ಪುನಃ build ಮಾಡುವ ಬದಲು ಮರುಬಳಕೆ ಮಾಡಲಾಗುತ್ತದೆ; ಅದನ್ನು ಪುನಃ build ಮಾಡಲು `--force` ನೀಡಿ.
- **Source ಅನ್ನು ಅಲ್ಲ, package ಅನ್ನು validate ಮಾಡಿ.** `validate` ಹೊಸ `DATA_DIR=<candidate>/data`, ನಕಲಿ secrets ಮತ್ತು
  environment ನಿಂದ ತೆಗೆದುಹಾಕಲಾದ operator ನ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ಹಾಗೂ `INITIAL_PASSWORD` ಜೊತೆಗೆ install ಮಾಡಿದ CLI
  (`serve --port <free port>`) ಅನ್ನು start ಮಾಡುತ್ತದೆ; ಹೀಗಾಗಿ ಇದು ಹೊಸ install ನ keyless loopback posture ಅನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ. ಇದು
  `GET /api/health` 200 ಅನ್ನು ಮರಳಿಸುವವರೆಗೆ ಕಾಯುತ್ತದೆ, `GET /v1/models` 200 ಅನ್ನು ಮರಳಿಸುವುದನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ, process group ಅನ್ನು ನಿಲ್ಲಿಸುತ್ತದೆ
  ಮತ್ತು tarball hash ಜೊತೆಗೆ ತೀರ್ಪನ್ನು `validation.json` ನಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ.
- **ಅದೇ artifact ಅನ್ನು promote ಮಾಡಿ.** ಪ್ರಸ್ತುತ tarball hash ಗಾಗಿ ಯಶಸ್ವಿಯಾದ validation ಇಲ್ಲದ candidate ಅನ್ನು `promote` ನಿರಾಕರಿಸುತ್ತದೆ.
  ಡೀಫಾಲ್ಟ್ active slot `_artifacts/candidate/current` ಆಗಿದೆ; `--target <dir>`
  ಅದೇ filesystem ನಲ್ಲಿರುವ ಮತ್ತೊಂದು directory ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ ಮತ್ತು ಅದರ previous slot `<dir>.previous` ಆಗಿರುತ್ತದೆ.
  ಪ್ರತಿಯೊಂದು rename atomic ಆಗಿರುತ್ತದೆ ಮತ್ತು ಮಧ್ಯದಲ್ಲಿ ವಿಫಲವಾದರೆ, ಈಗಾಗಲೇ ನಡೆದ rename ಗಳನ್ನು ಹಿಮ್ಮುಖಗೊಳಿಸುತ್ತದೆ.
- **Rollback ಮಾಡಿ.** `run` promote ಮಾಡಿದ slot ಅನ್ನು ಮತ್ತೊಮ್ಮೆ validate ಮಾಡುತ್ತದೆ ಮತ್ತು ಆ ಪರಿಶೀಲನೆ ವಿಫಲವಾದಾಗ
  `current` ಹಾಗೂ `previous` ಅನ್ನು ಮತ್ತೆ ಅದಲುಬದಲು ಮಾಡುತ್ತದೆ. ಮೊದಲ validation ನಲ್ಲಿ ವಿಫಲವಾದ candidate ಅನ್ನು ಎಂದಿಗೂ promote ಮಾಡಲಾಗುವುದಿಲ್ಲ.

ಎಲ್ಲವನ್ನೂ gitignore ಮಾಡಲಾದ `_artifacts/candidate/` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ; ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OmniRoute
installation ಮತ್ತು ಅದರ data directory ಅನ್ನು ಎಂದಿಗೂ ಸ್ಪರ್ಶಿಸಲಾಗುವುದಿಲ್ಲ. promote ಮಾಡಿದ CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ಆಗಿದೆ; ಅದನ್ನು ಬಳಸುವಾಗ ನಿಮ್ಮದೇ `DATA_DIR` ಜೊತೆಗೆ start ಮಾಡಿ.
Exit codes: `0` ಯಶಸ್ಸು, `1` validation ಅಥವಾ promotion ವಿಫಲವಾಗಿದೆ, `2` ಬಳಕೆಯ ದೋಷ ಅಥವಾ build ಕಾಣೆಯಾಗಿದೆ.

## ಸ್ಥಳೀಯ ಲೂಪ್ ಮತ್ತು CI ನಡುವಿನ ಹೋಲಿಕೆ

| ಪ್ರತಿ ಪ್ಯಾಚ್ಗೆ ಸ್ಥಳೀಯವಾಗಿ ರನ್ ಮಾಡಿ                                                                     | CI ವ್ಯಾಪಕ ಸಂಕೇತವನ್ನು ಒದಗಿಸುತ್ತದೆ                                           |
| ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| ಮೇಲಿನ ನೇರ ವರ್ತನೆ ಪರೀಕ್ಷೆಗಳು ಮತ್ತು ವರ್ಗ ಗೇಟ್ಗಳು                                                         | ಶಾರ್ಡ್ ಮಾಡಿದ ಸಂಪೂರ್ಣ ಯುನಿಟ್ ಸೂಟ್ ಮತ್ತು ಸರಣಿ ಪರೀಕ್ಷೆಗಳು                     |
| `npm run lint`                                                                                         | Vitest ಸೂಟ್ಗಳು ಮತ್ತು ಕವರೇಜ್/ಗುಣಮಟ್ಟದ ರ್ಯಾಚೆಟ್ಗಳು                           |
| ಪರಿಣಾಮ ಬೀರುವ ಒಪ್ಪಂದಕ್ಕೆ ಅಗತ್ಯವಿದ್ದಾಗ ಮಾತ್ರ ಟೈಪ್ಚೆಕ್ ಅಥವಾ ಬಿಲ್ಡ್                                        | ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್, ಭದ್ರತೆ, ಡಾಕ್ಸ್, ಅವಲಂಬನೆ ಮತ್ತು PR-ನೀತಿ ಗೇಟ್ಗಳು           |
| ಸ್ವಯಂಚಾಲಿತಗೊಳಿಸುವಿಕೆಯು ವರ್ತನೆಯನ್ನು ಸಾಬೀತುಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ ಮಾತ್ರ ಹಸ್ತಚಾಲಿತ ಸಂವಾದ/ಲೈವ್ ಪರಿಶೀಲನೆಗಳು | ವರ್ಕ್ಫ್ಲೋ ಮೂಲಕ ಸಂರಚಿಸಲಾದ ಕ್ರಾಸ್-ಜಾಬ್ ಏಕೀಕರಣ ಮತ್ತು ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಪರಿಶೀಲನೆಗಳು |

ಯಶಸ್ವಿಯಾದ ಕೇಂದ್ರೀಕೃತ ಲೂಪ್ ಬದಲಾದ ಒಪ್ಪಂದದ ಕುರಿತಾದ ಸಾಕ್ಷ್ಯವೇ ಹೊರತು, ಸಂಬಂಧವಿಲ್ಲದ CI ಪರಿಶೀಲನೆಗಳು
ಯಶಸ್ವಿಯಾಗುತ್ತವೆ ಎಂಬುದಕ್ಕೆ ಪುರಾವೆಯಲ್ಲ. ಇದಕ್ಕೆ ವಿರುದ್ಧವಾಗಿ, ಪ್ರತಿ ಸ್ಥಳೀಯ ತಿದ್ದುಪಡಿಯೂ ಸಂಪೂರ್ಣ ರೆಪೊಸಿಟರಿ ಮ್ಯಾಟ್ರಿಕ್ಸ್ಗಾಗಿ ಕಾಯುವಂತೆ ಮಾಡಬೇಡಿ.

## ಸಮನ್ವಯ ಪರಿಶೀಲನಾಪಟ್ಟಿ

ವಿಮರ್ಶೆಯನ್ನು ವಿನಂತಿಸುವ ಮೊದಲು:

- PR ಬೇಸ್ ಇನ್ನೂ ಅತ್ಯುನ್ನತ ಸಕ್ರಿಯ `release/v*` ಬ್ರಾಂಚ್ ಆಗಿದೆಯೇ ಎಂದು ದೃಢಪಡಿಸಿ.
- ಆ ಬೇಸ್ ಅನ್ನು ಫೆಚ್ ಮಾಡಿ ಮತ್ತು ನೀವು ಬ್ರಾಂಚ್ ಮಾಡಿದ ನಂತರ ಸೇರಿಸಲಾದ ಕಮಿಟ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
- ಆಕಸ್ಮಿಕ ಅಥವಾ ರಚಿಸಲಾದ ಅನಗತ್ಯ ಬದಲಾವಣೆಗಳಿಗಾಗಿ `git diff <active-base>...HEAD` ಅನ್ನು ಪರಿಶೀಲಿಸಿ.
- ಮೂಲವನ್ನು ನವೀಕರಿಸಿ ಮತ್ತು ಔಟ್ಪುಟ್ ಅನ್ನು ಮರುರಚಿಸುವ ಮೂಲಕ ಕ್ಯಾಟಲಾಗ್ ಮತ್ತು ರಚಿಸಲಾದ ಡಾಕ್ಯುಮೆಂಟ್ ಸಂಘರ್ಷಗಳನ್ನು ಪರಿಹರಿಸಿ.
- ಸಮನ್ವಯದ ನಂತರ PR ವಿವರಣೆಯಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾದ ಪ್ರತಿಯೊಂದು ಕೇಂದ್ರೀಕೃತ ಪರೀಕ್ಷೆ/ಗೇಟ್ ಅನ್ನು ಮರುರನ್ ಮಾಡಿ.
- ಬದಲಾಗಿರುವ ಬೇಸ್ಗೆ ಹೊಂದಿಸಲು ಮಾತ್ರ ಅಸರ್ಷನ್ಗಳನ್ನು ಎಂದಿಗೂ ದುರ್ಬಲಗೊಳಿಸಬೇಡಿ ಅಥವಾ ಅಗತ್ಯವಿರುವ ಪರೀಕ್ಷೆಗಳನ್ನು ತೆಗೆದುಹಾಕಬೇಡಿ.

ರಿಲೀಸ್-ಫ್ರೀಜ್ ಮತ್ತು ರೀಟಾರ್ಗೆಟಿಂಗ್ ನಿಯಮಗಳಿಗಾಗಿ,
[ಬ್ರಾಂಚಿಂಗ್ ಮತ್ತು ರಿಲೀಸ್ ಮಾದರಿ](BRANCHING_MODEL.md) ಬಳಸಿ. ಸಂಪೂರ್ಣ CI ಪಟ್ಟಿಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳ ಉಲ್ಲೇಖ](../architecture/QUALITY_GATES.md) ಬಳಸಿ.
