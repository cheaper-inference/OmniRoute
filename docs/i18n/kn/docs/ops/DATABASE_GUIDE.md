> **ಸಂಕ್ಷಿಪ್ತವಾಗಿ**: OmniRoute ತನ್ನ ಪ್ರಾಥಮಿಕ ಸಂಗ್ರಹವಾಗಿ **WAL ಜರ್ನಲಿಂಗ್ನೊಂದಿಗೆ SQLite** ಅನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು ಸೂಕ್ಷ್ಮ ಕ್ಷೇತ್ರಗಳಿಗೆ ನಿಷ್ಕ್ರಿಯ ಸ್ಥಿತಿಯಲ್ಲಿ **AES-256-GCM** ಎನ್ಕ್ರಿಪ್ಶನ್ ಒದಗಿಸುತ್ತದೆ. ಈ ಮಾರ್ಗದರ್ಶಿಯು ಸ್ಕೀಮಾ, ಮೈಗ್ರೇಶನ್ಗಳು, ಬ್ಯಾಕಪ್/ಮರುಪಡೆಯುವಿಕೆ ಮತ್ತು ಕಾರ್ಯಾಚರಣೆಯ ರನ್ಬುಕ್ಗಳನ್ನು ಒಳಗೊಂಡಿದೆ.

**ಮೂಲಗಳು:**

- `src/lib/db/core.ts` — ಸಿಂಗಲ್ಟನ್ + SCHEMA_SQL (17 ಮೂಲ ಕೋಷ್ಟಕಗಳು)
- `src/lib/db/migrationRunner.ts` — ಆವೃತ್ತಿಗೊಳಿಸಿದ ಮೈಗ್ರೇಶನ್ಗಳು
- `src/lib/db/migrations/` — 167 ಆವೃತ್ತಿಗೊಳಿಸಿದ SQL ಫೈಲ್ಗಳು
- `src/lib/db/encryption.ts` — ಎನ್ಕ್ರಿಪ್ಶನ್ ಸಹಾಯಕಗಳು
- `src/lib/db/backup.ts` — ಬ್ಯಾಕಪ್ ರಫ್ತು/ಆಮದು
- `src/lib/db/healthCheck.ts` — ಆರೋಗ್ಯ ಸ್ಥಿತಿಯ ರೋಗನಿರ್ಣಯಗಳು

## SQLite ಏಕೆ?

ಹಲವಾರು ಕಾರಣಗಳಿಂದ OmniRoute, PostgreSQL/MySQL ಬದಲಿಗೆ SQLite ಅನ್ನು ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡಿದೆ:

| ಅಂಶ              | SQLite                                       | PostgreSQL                              |
| ---------------- | -------------------------------------------- | --------------------------------------- |
| **ನಿಯೋಜನೆ**      | ಎಂಬೆಡೆಡ್ — ಪ್ರತ್ಯೇಕ ಸರ್ವರ್ ಅಗತ್ಯವಿಲ್ಲ        | ಸರ್ವರ್ ಸೆಟಪ್ ಅಗತ್ಯವಿದೆ                  |
| **ಎನ್ಕ್ರಿಪ್ಶನ್** | ಅಪ್ಲಿಕೇಶನ್-ಪದರದ (AES-256-GCM)                | ಅಂತರ್ನಿರ್ಮಿತ TDE                        |
| **ಕಾರ್ಯಕ್ಷಮತೆ**  | ಸಣ್ಣ/ಮಧ್ಯಮ ಕಾರ್ಯಭಾರಗಳಿಗೆ ವೇಗವಾಗಿದೆ           | ಬೃಹತ್ ಸಮಕಾಲೀನ ಬರವಣಿಗೆಗಳಿಗೆ ಉತ್ತಮವಾಗಿದೆ  |
| **ಸಮಕಾಲೀನತೆ**    | WAL ಮೋಡ್ ಸಮಕಾಲೀನ ಓದುವಿಕೆಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ | ಸಂಪೂರ್ಣ MVCC                            |
| **ಬ್ಯಾಕಪ್**      | ಏಕ-ಫೈಲ್ ನಕಲು                                 | `pg_dump` ಅಥವಾ ಫೈಲ್ಸಿಸ್ಟಮ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ |
| **ಬಳಕೆಯ ಸಂದರ್ಭ** | ಪ್ರತಿ-ಬಳಕೆದಾರ ಸ್ಥಾಪನೆ, ಎಂಬೆಡೆಡ್              | ಬಹು-ಟೆನೆಂಟ್ SaaS                        |

**ಏಕ-ಬಳಕೆದಾರ, ಏಕ-ಇನ್ಸ್ಟೆನ್ಸ್** ನಿಯೋಜನೆಗಳಿಗೆ (OmniRoute ನ ಪ್ರಾಥಮಿಕ ಬಳಕೆಯ ಸಂದರ್ಭ), SQLite ಸರಳವೂ ವೇಗವೂ ಆಗಿದೆ.

### WAL ಜರ್ನಲಿಂಗ್

`core.ts` ಡೇಟಾಬೇಸ್ ಅನ್ನು **WAL (Write-Ahead Logging) ಮೋಡ್ನಲ್ಲಿ** ತೆರೆಯುತ್ತದೆ:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

ಬರವಣಿಗೆಗಳ ಸಮಯದಲ್ಲಿ **ಸಮಕಾಲೀನ ಓದುವಿಕೆಗಳನ್ನು** WAL ಅನುಮತಿಸುತ್ತದೆ — ವಿನಂತಿಗಳು ದಾಖಲಾಗುತ್ತಿರುವಾಗಲೇ ಪ್ರಶ್ನೆಗಳನ್ನು ನಡೆಸುವ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗೆ ಇದು ಮುಖ್ಯವಾಗಿದೆ.

ಡೀಫಾಲ್ಟ್ ಕ್ಯಾಶ್ ಗಾತ್ರವು **65,536 KiB (64 MiB)** ಆಗಿದೆ. ಋಣಾತ್ಮಕ
`cache_size` ಅನ್ನು KiB ನಲ್ಲಿನ ಅಂದಾಜು ಮೇಲಿನ ಮಿತಿಯಾಗಿ SQLite ಪರಿಗಣಿಸುತ್ತದೆ ಮತ್ತು ಅಗತ್ಯಕ್ಕೆ ತಕ್ಕಂತೆ ಪುಟಗಳನ್ನು ಹಂಚಿಕೆ ಮಾಡುತ್ತದೆ.
**ಸೆಟ್ಟಿಂಗ್ಗಳು > ಸಿಸ್ಟಮ್ ಮತ್ತು ಸಂಗ್ರಹಣೆ > ಕ್ಯಾಶ್ ಗಾತ್ರ** **1 ರಿಂದ
1,000,000 KiB** ವರೆಗಿನ ಪೂರ್ಣಾಂಕ ಮೌಲ್ಯಗಳನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ; ಸೆಟ್ಟಿಂಗ್ ಅನ್ನು ಉಳಿಸಿದಾಗ ಅದು ಚಾಲ್ತಿಯಲ್ಲಿರುವ ಡೇಟಾಬೇಸ್ ಸಂಪರ್ಕಕ್ಕೆ ಅನ್ವಯವಾಗುತ್ತದೆ,
ಮತ್ತು ಪ್ರಾರಂಭದ ಸಮಯದಲ್ಲಿ OmniRoute ಉಳಿಸಲಾದ ಮೌಲ್ಯವನ್ನು ಮರುಸ್ಥಾಪಿಸುತ್ತದೆ.

## ಡೇಟಾಬೇಸ್ ಸ್ಥಳ

SQLite ಫೈಲ್ ಅನ್ನು ಇಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ:

| OS      | ಪಥ                                                              |
| ------- | --------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                   |
| macOS   | `~/.omniroute/storage.sqlite`                                   |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                       |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` ಮೂಲಕ ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದು) |

ಜೊತೆಗಿರುವ ಫೈಲ್ಗಳು:

- `storage.sqlite-wal` — ರೈಟ್-ಅಹೆಡ್ ಲಾಗ್
- `storage.sqlite-shm` — ಹಂಚಿಕೆಯ ಮೆಮೊರಿ ಫೈಲ್
- `call_logs/` — ವಿನಂತಿ ಪೇಲೋಡ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು (ಸಕ್ರಿಯಗೊಳಿಸಿದ್ದರೆ)

**ಸ್ಥಳವನ್ನು ಅತಿಕ್ರಮಿಸಿ:**

```bash
DATA_DIR=/custom/path omniroute
```

## ಡೊಮೇನ್ ಮಾಡ್ಯೂಲ್ ಆರ್ಕಿಟೆಕ್ಚರ್

OmniRoute ನ ಡೇಟಾಬೇಸ್ `src/lib/db/` ನಲ್ಲಿ **110 ಉನ್ನತ-ಹಂತದ TypeScript ಮಾಡ್ಯೂಲ್ಗಳನ್ನು** ಹೊಂದಿದೆ. ಪ್ರತಿಯೊಂದು ಡೊಮೇನ್ ಮಾಡ್ಯೂಲ್:

- ಒಂದು ಅಥವಾ ಹೆಚ್ಚು ನಿರ್ದಿಷ್ಟ ಟೇಬಲ್ಗಳ ಮಾಲೀಕತ್ವವನ್ನು ಹೊಂದಿರುತ್ತದೆ
- ಟೈಪ್ ಮಾಡಲಾದ CRUD ಫಂಕ್ಷನ್ಗಳನ್ನು ರಫ್ತು ಮಾಡುತ್ತದೆ
- ಮತ್ತೊಂದು ಮಾಡ್ಯೂಲ್ನ ಟೇಬಲ್ಗಳನ್ನು ಎಂದಿಗೂ ಬಳಸುವುದಿಲ್ಲ
- DB ಅನ್ನು ಪ್ರವೇಶಿಸಲು `core.ts` ನಿಂದ `getDbInstance()` ಅನ್ನು ಬಳಸುತ್ತದೆ

### ಮಾಡ್ಯೂಲ್ ಗಡಿಗಳು

ಒಂದು ಪ್ರಮುಖ ಆರ್ಕಿಟೆಕ್ಚರಲ್ ನಿಯಮ: **ಮಾಡ್ಯೂಲ್ಗಳು ಪರಸ್ಪರರ ಟೇಬಲ್ಗಳನ್ನು ನೇರವಾಗಿ ಪ್ರವೇಶಿಸುವುದಿಲ್ಲ**. ಮತ್ತೊಂದು ಮಾಡ್ಯೂಲ್ನ ಡೇಟಾದೊಂದಿಗೆ ಕೆಲಸ ಮಾಡಲು, ಆ ಮಾಡ್ಯೂಲ್ನಿಂದ ಫಂಕ್ಷನ್ ಅನ್ನು ಆಮದು ಮಾಡಿ.

```ts
// ❌ ತಪ್ಪು: ಮತ್ತೊಂದು ಮಾಡ್ಯೂಲ್ನಿಂದ ನೇರ SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ಸರಿ: providers ಮಾಡ್ಯೂಲ್ನ ಫಂಕ್ಷನ್ ಅನ್ನು ಬಳಸಿ
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

ಈ ನಿಯಮವನ್ನು ಕೋಡ್ ಪರಿಶೀಲನೆಯ ಮೂಲಕ ಜಾರಿಗೊಳಿಸಲಾಗುತ್ತದೆ — ಯಾವುದೇ ಸ್ಥಿರ ಪರಿಶೀಲನೆ ಇಲ್ಲ, ಆದರೆ ಉಲ್ಲಂಘನೆಗಳನ್ನು ಗುರುತಿಸಲಾಗುತ್ತದೆ.

## ವಲಸೆಗಳು

ಏಕೆ ಬದಲಾವಣೆ: ಅನುಕ್ರಮ ಸಂಖ್ಯೆಗಳೊಂದಿಗೆ, ಸಮಾನಾಂತರ PRs ಅದೇ ಮುಂದಿನ ಸಂಖ್ಯೆಯನ್ನು ಆರಿಸಿಕೊಂಡಿದೆ ಮತ್ತು ವಿಲೀನಗೊಳ್ಳುವ ಮೊದಲು ಒಂದನ್ನು ಹೊರತುಪಡಿಸಿ ಎಲ್ಲವನ್ನೂ ಮರುಸಂಖ್ಯೆ ಮಾಡಬೇಕಾಗಿತ್ತು. ಒಂದು UTC ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಪ್ರತಿ PR ಗೆ ತನ್ನದೇ ಆದ ಆವೃತ್ತಿಯನ್ನು ನೀಡುತ್ತದೆ.

ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಫಾರ್ಮ್ಯಾಟ್ಗಾಗಿ ನಿಯಮಗಳು ( `npm run check:migration-numbering` ನಿಂದ ಜಾರಿಗೊಳಿಸಲಾಗಿದೆ, `scripts/check/lib/migrationNaming.mjs` ನಲ್ಲಿ ಜನರೇಟರ್ನೊಂದಿಗೆ ಹಂಚಿಕೊಳ್ಳಲಾಗಿದೆ):

- ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ನಿಜವಾದ UTC ದಿನಾಂಕ ಮತ್ತು ಸಮಯ, `20261113000000` ಗಿಂತ ಹಿಂದಿನದಲ್ಲ ಮತ್ತು ಭವಿಷ್ಯದಲ್ಲಿ 10 ನಿಮಿಷಗಳಿಗಿಂತ ಹೆಚ್ಚಿಲ್ಲ.
- ವಿವರಣೆಯು ಲೋವರ್ಕೇಸ್ `snake_case` ಆಗಿದ್ದು, ಒಂದು ಅಕ್ಷರದಿಂದ ಪ್ರಾರಂಭವಾಗುವುದು (`a-z`, `0-9`, ಪದಗಳ ನಡುವೆ ಒಂದೇ `_` ), ಹೆಚ್ಚೆಂದರೆ 80 ಅಕ್ಷರಗಳು.
- ಒಂದೇ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಹೊಂದಿರುವ ಎರಡು ಫೈಲ್ಗಳು ನಕಲು.
- ನೋ-ಗ್ಯಾಪ್ ನಿಯಮವು ಹಳೆಯ ಸರಣಿಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ: ತಿಳಿದಿರುವ ಅಂತರಗಳಾದ `026`, `055` ಮತ್ತು `121` ಹೊರತುಪಡಿಸಿ `001` ನಿಂದ `241` ವರೆಗಿನ ಪ್ರತಿಯೊಂದು ಸಂಖ್ಯೆಯು ಅಸ್ತಿತ್ವದಲ್ಲಿರಬೇಕು. `241` (ಅಥವಾ ಯಾವುದೇ ಹಳೆಯ ಫೈಲ್) ಅಳಿಸುವುದು ಗೇಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. `001` ಮತ್ತು `241` ಎಂದಿಗೂ `KNOWN_GAPS` ಅನುಮತಿ ಪಟ್ಟಿಗೆ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ. ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ಫೈಲ್ಗಳು ಎಂದಿಗೂ ಅಂತರವನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ.
- `src/lib/db/migrations/` ನಲ್ಲಿನ ಪ್ರತಿ ನಮೂದು ಮಾನ್ಯವಾದ ಲೋವರ್ಕೇಸ್ `.sql` ಹೆಸರಿನೊಂದಿಗೆ ನಿಯಮಿತ ಫೈಲ್ ಆಗಿರಬೇಕು. ಡೈರೆಕ್ಟರಿ, ಸಿಮ್ಲಿಂಕ್, `.SQL` ಅಥವಾ `.sql.bak` ಫೈಲ್, ಗುಪ್ತ ಫೈಲ್ ಅಥವಾ ಸ್ಥಳಾವಕಾಶವಿರುವ ಹೆಸರು ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ, ಏಕೆಂದರೆ ರನ್ನರ್ ಅದನ್ನು ಮೌನವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತಾನೆ ಅಥವಾ ಬೂಟ್ನಲ್ಲಿ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತಾನೆ.

**ಆದೇಶವನ್ನು ಅನ್ವಯಿಸಿ.** ಓಟಗಾರನು ಪೂರ್ವಪ್ರತ್ಯಯದ ಸಂಖ್ಯಾ ಮೌಲ್ಯದಿಂದ ವಿಂಗಡಿಸುತ್ತಾನೆ, ಪಠ್ಯದಿಂದ ಅಲ್ಲ: ಹಳೆಯ `001`–`241` ಫೈಲ್ಗಳು, ನಂತರ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಕ್ರಮದಲ್ಲಿ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ಫೈಲ್ಗಳು, ನಂತರ `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ನೊಂದಿಗೆ ನೋಂದಾಯಿಸಲಾದ ಯಾವುದೇ ನೇಮ್ಸ್ಪೇಸ್ಡ್ ಡೈರೆಕ್ಟರಿಗಳು ( `ee-001` ನಂತಹ ಆವೃತ್ತಿಗಳು). ಬಾಕಿಯಿರುವ ಸ್ಥಳಾಂತರವು `_omniroute_migrations` ನಲ್ಲಿ ಇಲ್ಲದ ಯಾವುದೇ ಫೈಲ್ ಆಗಿದೆ, ಆದ್ದರಿಂದ ಹೊಸದಾದ ನಂತರ ವಿಲೀನಗೊಳ್ಳುವ ಹಳೆಯ ಶಾಖೆಯಿಂದ ವಲಸೆ ಇನ್ನೂ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಡೇಟಾಬೇಸ್ಗಳಲ್ಲಿ ಅನ್ವಯಿಸುತ್ತದೆ.

**ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ರಚನೆಯ ಕ್ರಮವಾಗಿದೆ, ವಿಲೀನ ಕ್ರಮವಲ್ಲ.** ನಿಮ್ಮ ವಲಸೆಯು ಟೇಬಲ್ ಅಥವಾ ಕಾಲಮ್ನ ಮೇಲೆ ಅವಲಂಬಿತವಾಗಿದ್ದರೆ a ನೊಂದಿಗೆ ವಲಸೆಯಿಂದ ರಚಿಸಲಾಗಿದೆ** ಹೊಸದು** ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ (ಉದಾಹರಣೆಗೆ, ಮೊದಲು ವಿಲೀನಗೊಂಡ ಮತ್ತೊಂದು PR ಯಿಂದ ಒಂದು), ತಾಜಾ ಡೇಟಾಬೇಸ್ ನಿಮ್ಮದನ್ನು ಮೊದಲು ರನ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ನಿಮ್ಮ PR ಇನ್ನೂ ತೆರೆದಿರುವಾಗ, ಫೈಲ್ ಹೆಸರನ್ನು `npm run db:new-migration` ನೊಂದಿಗೆ ಮರುಸೃಷ್ಟಿಸಿ ಇದರಿಂದ ಅದು ಹೊಸ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಪಡೆಯುತ್ತದೆ ಅಥವಾ ಅದನ್ನು ಸ್ವತಂತ್ರವಾಗಿಸಿ. `npm run test:migrations:fresh` ಪ್ರತಿ ವಲಸೆಯನ್ನು ಖಾಲಿ ಡೇಟಾಬೇಸ್ಗೆ ಅನ್ವಯಿಸುತ್ತದೆ ಮತ್ತು ಇದನ್ನು ಹಿಡಿಯುತ್ತದೆ.

### ವಿಲೀನಗೊಂಡ ವಲಸೆಯನ್ನು ಎಂದಿಗೂ ಅಳಿಸಲಾಗುವುದಿಲ್ಲ ಅಥವಾ ಮರುಹೆಸರಿಸಲಾಗುವುದಿಲ್ಲ

ಒಮ್ಮೆ ವಲಸೆ ಫೈಲ್ ಬಿಡುಗಡೆಯ ಶಾಖೆ ಅಥವಾ `main` ನಲ್ಲಿದ್ದರೆ, ಅದು ಈಗಾಗಲೇ ಹೋಮೋಲಾಗ್ ಮತ್ತು ಡೆವಲಪರ್ ಡೇಟಾಬೇಸ್ಗಳಲ್ಲಿ, VPS ಸ್ಥಾಪನೆಗಳಲ್ಲಿ ಮತ್ತು ಎಂಟರ್ಪ್ರೈಸ್ ಸಿಂಕ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ. ಅಂದಿನಿಂದ:

- **ಅದನ್ನು ಎಂದಿಗೂ ಅಳಿಸಬೇಡಿ.** ನವೀಕರಿಸಿದ ಡೇಟಾಬೇಸ್ಗಳು ಅದನ್ನು ಇರಿಸಿಕೊಳ್ಳುವಾಗ ತಾಜಾ ಸ್ಥಾಪನೆಗಳು ಅದರ ಸ್ಕೀಮಾವನ್ನು ಕಳೆದುಕೊಳ್ಳುತ್ತವೆ.
- **ಅದನ್ನು ಎಂದಿಗೂ ಮರುಹೆಸರಿಸಬೇಡಿ.** `_omniroute_migrations` ನಲ್ಲಿನ ಆವೃತ್ತಿಯು ಇನ್ನು ಮುಂದೆ ಫೈಲ್ಗೆ ಹೊಂದಿಕೆಯಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಈಗಾಗಲೇ ಅನ್ವಯಿಸಿದ ಪ್ರತಿಯೊಂದು ಡೇಟಾಬೇಸ್ ಅದನ್ನು ಮತ್ತೆ ರನ್ ಮಾಡುತ್ತದೆ. Idempotent ಅಲ್ಲದ SQL ನಂತರ ಡೇಟಾವನ್ನು ನಕಲು ಮಾಡುತ್ತದೆ ಅಥವಾ ಬೂಟ್ ಅನ್ನು ನಿಲ್ಲಿಸುತ್ತದೆ.
- **ಬೇರೆ ಸ್ಕೀಮಾ ಬೇಕೇ?** `npm run db:new-migration` ನೊಂದಿಗೆ ಹೊಸ ವಲಸೆಯನ್ನು ರಚಿಸಿ.

ಮರುಹೆಸರಿಸುವಿಕೆಯು ಇನ್ನೂ ವಿಲೀನಗೊಳ್ಳದ ಫೈಲ್ಗೆ ಮಾತ್ರ ಸುರಕ್ಷಿತವಾಗಿದೆ, ಇದು ಗೇಟ್ನ ಸುಳಿವುಗಳನ್ನು ಉಲ್ಲೇಖಿಸುತ್ತದೆ. ಬಿಡುಗಡೆ ಟ್ಯಾಗ್ ಇಲ್ಲಿ ಏನನ್ನೂ ಬದಲಾಯಿಸುವುದಿಲ್ಲ: `release/v*` ಶಾಖೆಗೆ ಪ್ರತಿ ಪುಶ್ Docker `:next` ಇಮೇಜ್ ಅನ್ನು ಪ್ರಕಟಿಸುತ್ತದೆ ಮತ್ತು ಹೋಮೋಲಾಗ್, VPS ಇನ್ಸ್ಟಾಲ್ಗಳು ಮತ್ತು ಎಂಟರ್ಪ್ರೈಸ್ ಸಿಂಕ್ನಲ್ಲಿ ಚಲಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ `vX.Y.Z` ಟ್ಯಾಗ್ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವುದಕ್ಕಿಂತ ಮೊದಲು ವಿಲೀನಗೊಂಡ ವಲಸೆಯು ನೈಜ ಡೇಟಾಬೇಸ್ಗಳಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ. ಟ್ಯಾಗ್ ಮಾಡಲಾದ ಅಥವಾ ಇಲ್ಲದಿರುವ ಬೇಸ್ ಫೈಲ್ ಅನ್ನು ತೆಗೆದುಹಾಕುವಲ್ಲಿ ಗೇಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

- **ವಿಲೀನಗೊಂಡ ವಲಸೆಯನ್ನು ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತಿದೆ.** ಫೈಲ್ ಅನ್ನು ಅಳಿಸುವ `git revert` ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ. ಫೈಲ್ ಅನ್ನು ಇರಿಸಿ ಮತ್ತು ಹೊಸ ವಲಸೆಯಲ್ಲಿ ಅದರ ಸ್ಕೀಮಾವನ್ನು ರದ್ದುಗೊಳಿಸಿ: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` ಮತ್ತು ಹೀಗೆ. ನವೀಕರಿಸಿದ ಮತ್ತು ತಾಜಾ ಡೇಟಾಬೇಸ್ಗಳು ನಂತರ ಅದೇ ಸ್ಕೀಮಾದೊಂದಿಗೆ ಕೊನೆಗೊಳ್ಳುತ್ತವೆ.
- **ಸ್ವೀಕರಿಸಿದ ಮರುಹೆಸರು: ಹೊಂದಾಣಿಕೆಯ ನಮೂದು ಮತ್ತು ಒಂದೇ ರೀತಿಯ ವಿಷಯ.** ವಿಲೀನಗೊಂಡ ಫೈಲ್ ಚಲಿಸಬೇಕಾದರೆ (ಉದಾಹರಣೆಗೆ, ಎರಡು ವಿಲೀನಗೊಂಡ ಫೈಲ್ಗಳು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಹಂಚಿಕೊಂಡರೆ ಮತ್ತು ರನ್ನರ್ ಆವೃತ್ತಿಯ ಘರ್ಷಣೆಯೊಂದಿಗೆ ನಿಲ್ಲುತ್ತದೆ), ಅದರ SQL ಮುಟ್ಟದೆಯೇ ನಂತರದದನ್ನು ಮರುಹೆಸರಿಸಿ ಮತ್ತು `src/lib/db/migrationRunner/constants.ts` ನಲ್ಲಿ `RENAMED_MIGRATION_COMPATIBILITY` ಗೆ `{ fromVersion, fromName, toVersion, toName }` ಸೇರಿಸಿ. ಹಳೆಯ ಆವೃತ್ತಿಯನ್ನು ಅನ್ವಯಿಸಿದ ಡೇಟಾಬೇಸ್ಗಳು ಫೈಲ್ ಅನ್ನು ಮತ್ತೆ ರನ್ ಮಾಡುವ ಬದಲು ಅವುಗಳ `_omniroute_migrations` ಸಾಲನ್ನು ಸರಿಸಲಾಗಿದೆ. ಗೇಟ್ ಅಂತಹ ಮರುಹೆಸರಿನ ಬಗ್ಗೆ ಎಚ್ಚರಿಸುತ್ತದೆ ಮತ್ತು ಅದರ ಮೇಲೆ ಯಾವಾಗಲೂ ಕಮ್ಯುಟೇಶನ್ ಚೆಕ್ ಅನ್ನು ರನ್ ಮಾಡುತ್ತದೆ, ಯಾವುದೇ ಹೊಸ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್: ತಾಜಾ ಇನ್ಸ್ಟಾಲ್ಗಳು ಫೈಲ್ ಅನ್ನು ಅದರ ಹೊಸ ಸ್ಥಾನದಲ್ಲಿ ಅನ್ವಯಿಸುತ್ತದೆ, ಅಪ್ಗ್ರೇಡ್ ಮಾಡಿದ ಡೇಟಾಬೇಸ್ಗಳು ಮಾಡುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಹಳೆಯದಕ್ಕೆ ಹತ್ತಿರ ಹೊಸ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಆರಿಸಿ. ಕಂಟೆಂಟ್ ಬದಲಾದರೆ (ಸ್ಕೀಮಾ ಬದಲಾವಣೆಯು ಇನ್ನೂ ಹೊಸ ವಲಸೆಯಲ್ಲಿ ಹೋಗುತ್ತದೆ) ಅಥವಾ ಪ್ರವೇಶದ ಗುರಿ ಫೈಲ್ ಡಿಸ್ಕ್ನಲ್ಲಿ ಇಲ್ಲದಿದ್ದರೆ ಗೇಟ್ ಮರುಹೆಸರಿಸಲು ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.
- **ಒಂದೇ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ನಲ್ಲಿ ಎಂದಿಗೂ ಮರುಹೆಸರಿಸಬೇಡಿ.** ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಇರಿಸಿಕೊಳ್ಳುವ ಮತ್ತು ವಿವರಣೆಯನ್ನು ಮಾತ್ರ ಬದಲಾಯಿಸುವ ಮರುಹೆಸರು ಪ್ರವೇಶದೊಂದಿಗೆ ಅಥವಾ ಇಲ್ಲದೆಯೇ ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ. `toVersion` ಅದರ `fromVersion` ಸಮನಾಗಿರುವ ಒಂದು ನಮೂದುನೊಂದಿಗೆ, ರನ್ನರ್ ಹಳೆಯ `_omniroute_migrations` ಸಾಲನ್ನು ಅಳಿಸುತ್ತಾನೆ ಮತ್ತು ಅದನ್ನು ಈಗಾಗಲೇ ರನ್ ಮಾಡಿದ ಪ್ರತಿಯೊಂದು ಡೇಟಾಬೇಸ್ನಲ್ಲಿ ಮತ್ತೆ ಫೈಲ್ ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ. ನಮೂದು ಇಲ್ಲದೆ, ರನ್ನರ್ ಆವೃತ್ತಿಯನ್ನು ಮಾತ್ರ ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ: ಅದು ಆ ಡೇಟಾಬೇಸ್ಗಳಲ್ಲಿನ ಫೈಲ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (ಹೊಸ ವಿಷಯವು ಅಲ್ಲಿಗೆ ಎಂದಿಗೂ ಚಲಿಸುವುದಿಲ್ಲ) ಮತ್ತು ಪ್ರತಿ ಬೂಟ್ನಲ್ಲಿ ಮರುಸಂಖ್ಯೆಯ ದೋಷವನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ. ಮತ್ತೊಂದು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಜೊತೆಗೆ ಹೊಂದಾಣಿಕೆಯ ನಮೂದನ್ನು ಬಳಸಿ ಅಥವಾ ಹೆಸರನ್ನು ಇರಿಸಿ.
- **ಮರುಹೆಸರಿಸಿದ ಫೈಲ್ ಮತ್ತೆ ರನ್ ಆಗುವುದಿಲ್ಲ ಎಂದು ಗೇಟ್ ಪರಿಶೀಲಿಸುತ್ತದೆ.** ಪ್ರತಿ ಮುಚ್ಚಿದ ಮರುಹೆಸರಿಗಾಗಿ, ಗೇಟ್ ಹೊಸ ಫೈಲ್ ಹೆಸರನ್ನು `--must-not-apply` ನೊಂದಿಗೆ ಕಮ್ಯುಟೇಶನ್ ಚೆಕ್ಗೆ ರವಾನಿಸುತ್ತದೆ. ಚೆಕ್ ಅಪ್ಗ್ರೇಡ್ ಮಾಡಲಾದ ಡೇಟಾಬೇಸ್ ಅನ್ನು ನೈಜ ರನ್ನರ್ನೊಂದಿಗೆ ಬೂಟ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ರನ್ನರ್ ಆ ಫೈಲ್ ಅನ್ನು ಮತ್ತೆ ಅನ್ವಯಿಸಿದರೆ (ಉದಾಹರಣೆಗೆ, ಪ್ರವೇಶವು ತಪ್ಪಾದ ಆವೃತ್ತಿ ಅಥವಾ ಹೆಸರನ್ನು ಹೊಂದಿರುವುದರಿಂದ ಅಥವಾ ಗೇಟ್ನ ಪಠ್ಯ ಪಾರ್ಸರ್ TypeScript ಯಿಂದ ವಿಭಿನ್ನವಾಗಿ `constants.ts` ಓದಿರುವುದರಿಂದ), ಗೇಟ್ `migration renomeada rodaria de novo` ಯೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಪ್ರವೇಶದ ಹಳೆಯ ಮತ್ತು ಹೊಸ ಆವೃತ್ತಿಯನ್ನು ಪರಿಶೀಲಿಸಲು ನಿಮ್ಮನ್ನು ಕೇಳುತ್ತದೆ.

### ಬೇಸ್ ವಿರುದ್ಧ ಗೇಟ್ ಏನು ಪರಿಶೀಲಿಸುತ್ತದೆ

ಪುಲ್ ವಿನಂತಿ ಮತ್ತು ವಿಲೀನ-ಕ್ಯೂ ರನ್ಗಳಲ್ಲಿ, `npm run check:migration-numbering` ಡಿಸ್ಕ್ನಲ್ಲಿ `src/lib/db/migrations/` ಮೂಲ ಶಾಖೆಯಲ್ಲಿ ಅದೇ ಡೈರೆಕ್ಟರಿಯೊಂದಿಗೆ ಹೋಲಿಸುತ್ತದೆ. ಆಧಾರವೆಂದರೆ, ಈ ಕ್ರಮದಲ್ಲಿ: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` ವೇರಿಯೇಬಲ್, ಅಥವಾ, `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` ಅಥವಾ `merge_group` ಆಗಿರುವಾಗ, ವಿಲೀನ ಬದ್ಧತೆಯ ಮೊದಲ ಪೋಷಕ, ಈವೆಂಟ್ ಪೇಲೋಡ್ನ `merge_group.base_sha`, ಅಥವಾ `git merge-base HEAD origin/$GITHUB_BASE_REF`. ಪುಲ್ ವಿನಂತಿಯಲ್ಲಿ ಅಥವಾ ವಿಲೀನ-ಸರದಿಯಲ್ಲಿ ಯಾವುದೇ ಪರಿಹರಿಸಬಹುದಾದ ಆಧಾರವಿಲ್ಲದೆ ಗೇಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. `--base` ಇಲ್ಲದೆ CI ಹೊರಗೆ ಇದು `comparação com a base: pulada (sem --base)` ಮುದ್ರಿಸುತ್ತದೆ ಮತ್ತು ಈ ನಿಯಮಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

`--base-latest-tag` ಹೊಸ ಬಿಡುಗಡೆ ಟ್ಯಾಗ್ನೊಂದಿಗೆ ಹೋಲಿಸುತ್ತದೆ (ಸೆಮ್ವರ್ ಕ್ರಮದಲ್ಲಿ`vX.Y.Z` ; ರಾತ್ರಿಯಂತಹ ಪ್ರತ್ಯಯ ಟ್ಯಾಗ್ಗಳು ಲೆಕ್ಕಿಸುವುದಿಲ್ಲ) ಇದು `HEAD` ನ ಇತಿಹಾಸದಲ್ಲಿದೆ, `--base` ಯಂತೆಯೇ ಅದೇ ನಿಯಮಗಳೊಂದಿಗೆ. ಬಿಡುಗಡೆ-ಹಸಿರು (`scripts/quality/validate-release-green.mjs`) ಈ ರೀತಿಯಲ್ಲಿ ಗೇಟ್ ಅನ್ನು ನಡೆಸುತ್ತದೆ, ಏಕೆಂದರೆ ಪುಶ್ ಮತ್ತು ನಿಗದಿತ ರನ್ಗಳು ಪುಲ್ ವಿನಂತಿಯ ಆಧಾರವನ್ನು ಹೊಂದಿಲ್ಲ ಮತ್ತು ವಿಲೀನವು ತಾಜಾ CI ರನ್ ಇಲ್ಲದೆ ಇಳಿಯಬಹುದು. ಇತಿಹಾಸದಲ್ಲಿ ಯಾವುದೇ ಬಿಡುಗಡೆಯ ಟ್ಯಾಗ್ ಇಲ್ಲದೆ ಗೇಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; `git fetch --tags` ರನ್ ಮಾಡಿ ( CI ನಲ್ಲಿ, `actions/checkout` ಜೊತೆಗೆ `fetch-depth: 0` ಟ್ಯಾಗ್ಗಳನ್ನು ತರುತ್ತದೆ).

ಕಮ್ಯುಟೇಶನ್ ಚೆಕ್ನ ಒಂದು ರನ್ ಔಟ್-ಆಫ್-ಆರ್ಡರ್, ಎಡಿಟ್ ಮಾಡಿದ ಮತ್ತು ಮರುಹೆಸರಿಸಿದ ಫೈಲ್ಗಳನ್ನು ಒಟ್ಟಿಗೆ ಒಳಗೊಳ್ಳುತ್ತದೆ.

ಕಮ್ಯುಟೇಶನ್ ಚೆಕ್ (`scripts/check/migration-commutation.ts`) ಎರಡು ತಾತ್ಕಾಲಿಕ ಡೇಟಾಬೇಸ್ಗಳನ್ನು ನೈಜ ಅನುಸ್ಥಾಪನ ಮಾರ್ಗದೊಂದಿಗೆ ನಿರ್ಮಿಸುತ್ತದೆ: a** ಮೇಲ್ದರ್ಜೆಗೇರಿಸಲಾಗಿದೆ** ಒಂದು (ಮೂಲ ವಲಸೆಯೊಂದಿಗೆ ಬೂಟ್ ಮಾಡಿ, ನಂತರ ಪುಲ್ ವಿನಂತಿಯ ವಲಸೆಯೊಂದಿಗೆ ಅದೇ ಫೈಲ್ನಲ್ಲಿ ಮತ್ತೆ ಬೂಟ್ ಮಾಡಿ) ಮತ್ತು a** ತಾಜಾ** ಒಂದು (ಪುಲ್ ವಿನಂತಿಯ ವಲಸೆಯೊಂದಿಗೆ ಒಂದು ಬೂಟ್). ಇದು ಫಲಿತಾಂಶದ ಸ್ಕೀಮಾಗಳನ್ನು ಹೋಲಿಸುತ್ತದೆ: ಕೋಷ್ಟಕಗಳು ಮತ್ತು ಕಾಲಮ್ಗಳು (ಕಾಲಮ್ ಕ್ರಮವನ್ನು ನಿರ್ಲಕ್ಷಿಸುವುದು), UNIQUE / PRIMARY KEY ಮತ್ತು FOREIGN KEY ನಿರ್ಬಂಧಗಳು, ಪ್ರತಿ ಕೋಷ್ಟಕದ ಸಾಮಾನ್ಯೀಕರಿಸಿದ `CREATE TABLE` ಪಠ್ಯ (ಇದು CHECK ನಿರ್ಬಂಧಗಳು, ಸಂಯೋಜನೆಗಳು, ರಚಿಸಲಾದ ಕಾಲಮ್ಗಳು ಮತ್ತು ಟೇಬಲ್ ಆಯ್ಕೆಗಳನ್ನು ಒಳಗೊಂಡಿದೆ), ಸೂಚ್ಯಂಕಗಳು, ಟ್ರಿಗ್ಗರ್ಗಳು ಮತ್ತು ವೀಕ್ಷಣೆಗಳು. ಸಾಲು ಡೇಟಾವನ್ನು ಹೋಲಿಸಲಾಗಿಲ್ಲ. ಅವು ಹೊಂದಾಣಿಕೆಯಾದರೆ, ಫೈಲ್ ಕ್ರಮಬದ್ಧವಾಗಿಲ್ಲ ಆದರೆ ಪ್ರಯಾಣಿಸುತ್ತದೆ ಮತ್ತು ಹಾದುಹೋಗುತ್ತದೆ ಎಂದು ಗೇಟ್ ಮುದ್ರಿಸುತ್ತದೆ. ಅವು ಭಿನ್ನವಾಗಿದ್ದರೆ, ಗೇಟ್ ವ್ಯತ್ಯಾಸದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಪ್ರಕರಣದ ಸುಳಿವು: ಔಟ್-ಆಫ್-ಆರ್ಡರ್ ಫೈಲ್ಗಾಗಿ, ಅದರ ಹೆಸರನ್ನು `npm run db:new-migration` ನೊಂದಿಗೆ ಮರುಸೃಷ್ಟಿಸಿ, ಇದು ಫೈಲ್ ಇನ್ನೂ ವಿಲೀನಗೊಳ್ಳದ ಕಾರಣ ಸುರಕ್ಷಿತವಾಗಿದೆ; ಸಂಪಾದಿತ ಬೇಸ್ ಫೈಲ್ಗಾಗಿ, ಮೂಲ ವಿಷಯವನ್ನು ಮರುಸ್ಥಾಪಿಸಿ ಮತ್ತು ಬದಲಾವಣೆಯನ್ನು ಹೊಸ ವಲಸೆಯಲ್ಲಿ ಇರಿಸಿ; ಮರುಹೆಸರಿಸಿದ ಫೈಲ್ಗಾಗಿ, ಮರುಹೆಸರಿಸುವಿಕೆಯನ್ನು ರದ್ದುಗೊಳಿಸಿ ಅಥವಾ ಅದು ಪ್ರಯಾಣಿಸುವಲ್ಲಿ ಮತ್ತೊಂದು ಹೊಸ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಆರಿಸಿ, ಮತ್ತೊಂದು ಹೆಸರಿನೊಂದಿಗೆ ಒಂದೇ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಎಂದಿಗೂ ಆರಿಸಬೇಡಿ. ಚೆಕ್ ಸ್ವತಃ ಚಲಾಯಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ, ಗೇಟ್ CI ನಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಸ್ಥಳೀಯವಾಗಿ ಮಾತ್ರ ಎಚ್ಚರಿಸುತ್ತದೆ. ಸಂಪಾದಿತ ಬೇಸ್ ಫೈಲ್ಗಾಗಿ, ಅಪ್ಗ್ರೇಡ್ ಮಾಡಿದ ಡೇಟಾಬೇಸ್ ಅನ್ನು ಆ ಫೈಲ್ನ ಬೇಸ್ನ ವಿಷಯದೊಂದಿಗೆ ನಿರ್ಮಿಸಲಾಗಿದೆ ಮತ್ತು ಅದರ ಆವೃತ್ತಿಯು ಈಗಾಗಲೇ ರೆಕಾರ್ಡ್ ಆಗಿರುವುದರಿಂದ ಎರಡನೇ ಬೂಟ್ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ. ಮರುಹೆಸರಿಸಿದ ಫೈಲ್ಗಾಗಿ, ನವೀಕರಿಸಿದ ಡೇಟಾಬೇಸ್ ಅನ್ನು ಅದರ ಹಳೆಯ ಹೆಸರಿನಲ್ಲಿ ಫೈಲ್ನೊಂದಿಗೆ ನಿರ್ಮಿಸಲಾಗಿದೆ, ಮತ್ತು ಎರಡನೇ ಬೂಟ್ ಅದರ `_omniroute_migrations` ಸಾಲನ್ನು ಮತ್ತೆ ಚಾಲನೆ ಮಾಡುವ ಬದಲು ಹೊಂದಾಣಿಕೆಯ ಪ್ರವೇಶದ ಮೂಲಕ ಚಲಿಸುತ್ತದೆ; ಗೇಟ್ ಹೊಸ ಹೆಸರನ್ನು `--must-not-apply` ನೊಂದಿಗೆ ಹಾದುಹೋಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಎರಡನೇ ಬೂಟ್ ಅದನ್ನು ಅನ್ವಯಿಸಿದರೆ ಚೆಕ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಅಪ್ಗ್ರೇಡ್ ಮಾಡಿದ ಹಾದಿಯಲ್ಲಿ ಪುಲ್ ವಿನಂತಿಯ ವಲಸೆಯು ವಿಫಲವಾದಲ್ಲಿ, ಅಂದರೆ, ಪ್ರತಿ ಬೇಸ್ ವಲಸೆಯ ನಂತರ (ಹೊಸ ಇನ್ಸ್ಟಾಲ್ನಲ್ಲಿ ಅದು ವಿಫಲವಾಗಲಿ ಅಥವಾ ಇಲ್ಲದಿರಲಿ), ಗೇಟ್ `migration do PR não aplica` ವರದಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಬೇಸ್ನ ಪ್ರಸ್ತುತ ಸ್ಕೀಮಾಗೆ ವಿರುದ್ಧವಾಗಿ SQL ಅನ್ನು ಸರಿಪಡಿಸಲು ನಿಮ್ಮನ್ನು ಕೇಳುತ್ತದೆ; ಫೈಲ್ ನಂತರದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ನೊಂದಿಗೆ ಮತ್ತೊಂದು ಪುಲ್ ವಿನಂತಿಯ ವಲಸೆಯ ಮೇಲೆ ಅವಲಂಬಿತವಾಗಿದ್ದರೆ, ಅದರ ಹೆಸರನ್ನು `npm run db:new-migration` ನೊಂದಿಗೆ ಮರುಸೃಷ್ಟಿಸಿ.

ಅದೇ ಹೋಲಿಕೆಯನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಲು, ಬೇಸ್ ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ರವಾನಿಸಿ, ಉದಾಹರಣೆಗೆ `npm run check:migration-numbering -- --base origin/<base-branch>`, ಅಥವಾ ಇತ್ತೀಚಿನ ಬಿಡುಗಡೆಯೊಂದಿಗೆ ಹೋಲಿಸಲು `npm run check:migration-numbering -- --base-latest-tag`.

### ಓಪನ್ PR ನ `NNN` ವಲಸೆಯನ್ನು ಪರಿವರ್ತಿಸಲಾಗುತ್ತಿದೆ

ಸ್ವಿಚ್ ಮೊದಲು ತೆರೆಯಲಾದ ಪುಲ್ ವಿನಂತಿಯು ಇನ್ನೂ `242_add_widgets.sql` ನಂತಹ ಅನುಕ್ರಮ ಫೈಲ್ ಅನ್ನು ಒಯ್ಯಬಹುದು. `241` ಮೇಲಿನ ಹಳೆಯ ಸಂಖ್ಯೆಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗಿದೆ, ಆದ್ದರಿಂದ ವಿಲೀನಗೊಳಿಸುವ ಮೊದಲು ಅದನ್ನು ಪರಿವರ್ತಿಸಿ:

1. **ವಿವರಣೆಯನ್ನು ಇಟ್ಟುಕೊಂಡು ಜನರೇಟರ್ನೊಂದಿಗೆ ಫೈಲ್ ಅನ್ನು ಮರುಹೆಸರಿಸಿ.** ಹೊಸ ಹೆಸರನ್ನು ಪಡೆಯಲು `npm run db:new-migration -- <same description>` ರನ್ ಮಾಡಿ, SQL ಅನ್ನು ಅದರೊಳಗೆ ಸರಿಸಿ ಮತ್ತು ಹಳೆಯ `NNN_` ಫೈಲ್ ಅನ್ನು ಅಳಿಸಿ. ವಿವರಣೆಯು ಒಂದೇ ಆಗಿರಬೇಕು: ಕೆಳಗಿನ ಹೊಂದಾಣಿಕೆಯ ನಮೂದು ಅದರ ಮೇಲೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ.
2. **ನಿರಂತರ ಡೇಟಾಬೇಸ್ ಹಳೆಯ ಸಂಖ್ಯೆಯನ್ನು ರನ್ ಮಾಡಿದರೆ ಹೊಂದಾಣಿಕೆಯ ನಮೂದನ್ನು ಸೇರಿಸಿ.** ಇರಿಸಲಾಗಿರುವ ಯಾವುದೇ ಡೇಟಾಬೇಸ್ (ಹೋಮೊಲಾಗ್, a VPS, ಕೊಡುಗೆದಾರರ ಸ್ವಂತ ಸ್ಥಾಪನೆ) `NNN_` ಫೈಲ್ನೊಂದಿಗೆ PR ನ ನಿರ್ಮಾಣವನ್ನು ನಡೆಸಿದರೆ, `src/lib/db/migrationRunner/constants.ts` ನಲ್ಲಿ `RENAMED_MIGRATION_COMPATIBILITY` ಗೆ `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` ಸೇರಿಸಿ. ಇದು** `237` ಗೆ `241` ಗೆ ಅಗತ್ಯವಿದೆ** : ಆ ಸ್ಲಾಟ್ಗಳು ಈಗ ಅಂಗೀಕೃತ `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` ಮತ್ತು `241_seen_models.sql` ಅನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುತ್ತವೆ ಮತ್ತು ಪ್ರವೇಶವಿಲ್ಲದೆ ಅಂತಹ ಡೇಟಾಬೇಸ್ ಕ್ಯಾನೊನಿಕಲ್ ವಲಸೆಯನ್ನು ಶಾಶ್ವತವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು ಪರಿವರ್ತಿಸಲಾದ ಒಂದನ್ನು ಮತ್ತೆ ರನ್ ಮಾಡುತ್ತದೆ. ಗಮ್ಯಸ್ಥಾನವು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಆಗಿರುವಾಗ `242` ನಂತಹ ಖಾಲಿ ಇರುವ ಸ್ಲಾಟ್ಗಾಗಿ ಸಹ ಇದು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ. ಸಂದೇಹವಿದ್ದಲ್ಲಿ, ನಮೂದನ್ನು ಸೇರಿಸಿ. ನೀವು ಅದನ್ನು ರಚನೆಯಲ್ಲಿ ಎಲ್ಲಿ ಸೇರಿಸುತ್ತೀರಿ ಎಂಬುದು ಮುಖ್ಯವಲ್ಲ: ಪ್ರವೇಶದ ಗುರಿಯ ಸ್ಲಾಟ್ ಇನ್ನೂ ಮತ್ತೊಂದು ನಮೂದು ದೂರ ಸರಿಯುವ ಸಾಲನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಂಡಾಗ (ಉದಾಹರಣೆಗೆ `237` PR ಸಾಲನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವುದು ಹಳೆಯ `usage_history_calculated_cost` ಸಾಲು `237` ಗೆ ಚಲಿಸಲು ಕಾಯುತ್ತಿರುವಾಗ), ರನ್ನರ್ ಆ ಪ್ರವೇಶವನ್ನು ಸ್ಲಾಟ್ ಮುಕ್ತವಾಗುವವರೆಗೆ ಕಾಯಲು ಅನುಮತಿಸುತ್ತದೆ. ಸ್ಲಾಟ್ನ ಪ್ರವೇಶವಿಲ್ಲದ ಸಾಲು ಅಥವಾ ಸ್ಲಾಟ್ಗಳನ್ನು ಬದಲಾಯಿಸುವ ಎರಡು ನಮೂದುಗಳಿಂದ ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವಂತಹ ನಿಜವಾದ ಸಂಘರ್ಷವು `Cannot reconcile ...` ನೊಂದಿಗೆ ಬೂಟ್ ಅನ್ನು ನಿಲ್ಲಿಸುತ್ತದೆ.
3. **SQL ಶಕ್ತಿಯುತವಾಗಿರಲಿ** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), ಏಕೆಂದರೆ ಪರಿವರ್ತಿತ ವಲಸೆಯು ಅದರ ಸ್ಕೀಮಾ ಈಗಾಗಲೇ ಇರುವ ಡೇಟಾಬೇಸ್ ಅನ್ನು ಭೇಟಿ ಮಾಡಬಹುದು.
4. **ಆವೃತ್ತಿಯ ಪ್ರಮುಖ ವಿಶೇಷ ಪ್ರಕರಣಗಳನ್ನು ಸರಿಸಿ.** PR ತನ್ನ ಹಳೆಯ ಸಂಖ್ಯೆಗೆ `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) ಅಥವಾ `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) ನಲ್ಲಿ ಕೇಸ್ ಅನ್ನು ಸೇರಿಸಿದರೆ, ಕೀಲಿಯನ್ನು ಹೊಸ ಸಮಯಸ್ಟ್ಯಾಂಪ್ಗೆ ಬದಲಾಯಿಸಿ.

`tests/unit/db/codex-fence-migration-rename.test.ts` ಮರುಹೆಸರಿಸಿದ ವಲಸೆಯ ಪರೀಕ್ಷೆಯ ಒಂದು ಕಾರ್ಯ ಉದಾಹರಣೆಯಾಗಿದೆ.

### ಸ್ವಿಚ್ ಮೊದಲು ಶಾಖೆಗಳಿಗೆ ಬ್ಯಾಕ್ಪೋರ್ಟ್ಗಳು

ಚೆರ್ರಿ-ಪಿಕ್ ಅಥವಾ ಸ್ವಿಚ್ಗೆ ಹಿಂದಿನ ಶಾಖೆಗೆ `YYYYMMDDHHMMSS_` ಫೈಲ್ ಅನ್ನು ಬ್ಯಾಕ್ಪೋರ್ಟ್ ಮಾಡಬೇಡಿ (ಉದಾಹರಣೆಗೆ ಹಳೆಯ `release/v*` ಶಾಖೆ). ಓಟಗಾರನು ಫೈಲ್ ಹೆಸರುಗಳನ್ನು ಪಠ್ಯದಂತೆ ವಿಂಗಡಿಸುತ್ತಾನೆ, ಆದ್ದರಿಂದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ಫೈಲ್ ತಾಜಾ ಡೇಟಾಬೇಸ್ನಲ್ಲಿ `201_` ಮತ್ತು `202_` ನಡುವೆ ಚಲಿಸುತ್ತದೆ ಮತ್ತು ಹಳೆಯ ಗೇಟ್ 14-ಅಂಕಿಯ ಪೂರ್ವಪ್ರತ್ಯಯಗಳನ್ನು ಅರ್ಥಮಾಡಿಕೊಳ್ಳುವುದಿಲ್ಲ. ಅಂತಹ ಶಾಖೆಯಲ್ಲಿ, ಬದಲಾವಣೆಯನ್ನು ಆ ಶಾಖೆಯ ಸ್ವಂತ ಮುಂದಿನ `NNN_` ಫೈಲ್ ಎಂದು ಬರೆಯಿರಿ, idempotent, ಆದ್ದರಿಂದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ಆವೃತ್ತಿಯು ನಂತರ ಬಂದಾಗ ಅದು ನೋ-ಆಪ್ ಆಗಿದೆ.

### ವಲಸೆಗಳು ಹೇಗೆ ನಡೆಯುತ್ತವೆ

ಪ್ರಾರಂಭದಲ್ಲಿ, `migrationRunner.ts`:

1. ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದಿದ್ದರೆ `_omniroute_migrations` ಟೇಬಲ್ ಅನ್ನು ರಚಿಸುತ್ತದೆ
2. ಈಗಾಗಲೇ ಅನ್ವಯಿಸಲಾದ ವಲಸೆಗಳಿಗಾಗಿ ಪ್ರಶ್ನೆಗಳು
3. ಯಾವುದೇ ಹೊಸ ವಲಸೆಗಳನ್ನು ಕ್ರಮವಾಗಿ ಅನ್ವಯಿಸುತ್ತದೆ, ಪ್ರತಿಯೊಂದೂ ವಹಿವಾಟಿನಲ್ಲಿ
4. ಪ್ರತಿ ಅನ್ವಯಿಕ ವಲಸೆಯನ್ನು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ನೊಂದಿಗೆ ದಾಖಲಿಸುತ್ತದೆ

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### ಐಡೆಂಪೊಟೆನ್ಸಿ

ವಲಸೆಗಳು ಇರಬೇಕು** ಬುದ್ಧಿಹೀನ** — ಅವುಗಳನ್ನು ಎರಡು ಬಾರಿ ಚಾಲನೆ ಮಾಡುವುದು ನೋ-ಆಪ್ ಆಗಿರಬೇಕು:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, ಮತ್ತು `OR IGNORE` / `OR REPLACE` ಷರತ್ತುಗಳನ್ನು ಧಾರಾಳವಾಗಿ ಬಳಸಿ.

### ಹೊಸ ವಲಸೆಯನ್ನು ಸೇರಿಸಲಾಗುತ್ತಿದೆ

1. **ಜನರೇಟರ್ನೊಂದಿಗೆ ಫೈಲ್ ಅನ್ನು ರಚಿಸಿ** : `npm run db:new-migration -- <description>` (ಉದಾಹರಣೆಗೆ `npm run db:new-migration -- add combo priority`). ಇದು ಪ್ರಸ್ತುತ UTC ಸಮಯ ಮತ್ತು ಕಾಮೆಂಟ್ ಹೆಡರ್ನೊಂದಿಗೆ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` ಬರೆಯುತ್ತದೆ, ಆ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ತೆಗೆದುಕೊಂಡರೆ ಒಂದು ಸೆಕೆಂಡ್ ಮುಂದಕ್ಕೆ ಚಲಿಸುತ್ತದೆ ಮತ್ತು ಫೈಲ್ ಅನ್ನು ಎಂದಿಗೂ ಓವರ್ರೈಟ್ ಮಾಡುವುದಿಲ್ಲ. ಕೈಯಿಂದ ಸಂಖ್ಯೆಯನ್ನು ಆರಿಸಬೇಡಿ.
2. **ಸುರಕ್ಷಿತ DDL ಬಳಸಿ** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **ಡೇಟಾವನ್ನು ಎಚ್ಚರಿಕೆಯಿಂದ ಬ್ಯಾಕ್ಫಿಲ್ ಮಾಡಿ** : ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಾಲುಗಳನ್ನು ನಿರ್ವಹಿಸಲು `UPDATE ... WHERE ...` ಬಳಸಿ
4. **ಆದೇಶ ಮತ್ತು ಹೆಸರಿಸುವಿಕೆಯನ್ನು ಪರಿಶೀಲಿಸಿ** : `npm run test:migrations:fresh` (ಖಾಲಿ ಡೇಟಾಬೇಸ್ನಲ್ಲಿ ಎಲ್ಲಾ ವಲಸೆಗಳು) ಮತ್ತು `npm run check:migration-numbering`
5. **ನಕಲಿನಲ್ಲಿ ಪರೀಕ್ಷಿಸಿ** : ಉತ್ಪಾದನೆಯ ಮೇಲೆ ಎಂದಿಗೂ ಪರೀಕ್ಷಿಸದ ವಲಸೆಗಳನ್ನು ನಡೆಸಬೇಡಿ
6. **ಕೋಡ್ನಿಂದ ರಚಿಸಲಾದ ಟೇಬಲ್ಗೆ ವಲಸೆಯ ಅಗತ್ಯವಿದೆ** : ಮಾಡ್ಯೂಲ್ ಸಹ ಟೇಬಲ್ ಅನ್ನು ಸೋಮಾರಿಯಾಗಿ ರಚಿಸಿದರೆ (`CREATE TABLE IF NOT EXISTS`, ಸ್ವಯಂ-ಗುಣಪಡಿಸುವ ಮಾರ್ಗವಾಗಿ ಇರಿಸಲಾಗುತ್ತದೆ), ವಲಸೆಯು ಅದನ್ನು ಅದೇ DDL ನೊಂದಿಗೆ ರಚಿಸಬೇಕು. ಇಲ್ಲದಿದ್ದರೆ ಒಂದು ಕ್ಲೀನ್ ಇನ್ಸ್ಟಾಲ್ ಮತ್ತು ಅಪ್ಗ್ರೇಡ್ ಮಾಡಿದ ಇನ್ಸ್ಟಾಲ್ ಆ ಕೋಡ್ ಪಾತ್ ರನ್ ಆಗಿದೆಯೇ ಎಂಬುದನ್ನು ಅವಲಂಬಿಸಿ ವಿಭಿನ್ನ ಸ್ಕೀಮಾಗಳೊಂದಿಗೆ ಕೊನೆಗೊಳ್ಳುತ್ತದೆ. `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` ಮತ್ತು `open-sse/` ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ವಲಸೆಯಿಲ್ಲದೆ (#20557) ಸೋಮಾರಿಯಾದ `CREATE` ನಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಉದಾಹರಣೆ: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

ಉದಾಹರಣೆ:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **ಹಿಮ್ಮುಖ-ಹೊಂದಾಣಿಕೆಯಿಲ್ಲದ ಬದಲಾವಣೆಗಳು** (ಉದಾ, ಕಾಲಮ್ಗಳನ್ನು ಬಿಡುವುದು) ಟ್ರಿಕಿ. OmniRoute NOT ಬೆಂಬಲಿಸುತ್ತದೆ — ಡೌನ್ಗ್ರೇಡ್ ಒಮ್ಮೆ ವಲಸೆಯನ್ನು ಅನ್ವಯಿಸಿದರೆ, ಸ್ಕೀಮಾ ಬದಲಾವಣೆಯು ಶಾಶ್ವತವಾಗಿರುತ್ತದೆ. ಅದಕ್ಕೆ ತಕ್ಕಂತೆ ಯೋಜನೆ ಮಾಡಿ.

## ಸಂಗ್ರಹಿತ ಡೇಟಾದ ಎನ್ಕ್ರಿಪ್ಶನ್

ಸೂಕ್ಷ್ಮ ಫೀಲ್ಡ್ಗಳನ್ನು (API ಕೀಗಳು, OAuth ಟೋಕನ್ಗಳು, ಕನೆಕ್ಷನ್ ಸ್ಟ್ರಿಂಗ್ಗಳು) **AES-256-GCM** ಬಳಸಿ ಸಂಗ್ರಹಿತ ಸ್ಥಿತಿಯಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ.

### ಇದು ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ

```ts
// src/lib/db/encryption.ts (ಸರಳೀಕೃತ)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### ಇದನ್ನು ಎಲ್ಲಿ ಬಳಸಲಾಗುತ್ತದೆ

- `provider_connections.api_key` — ಅಪ್ಲಿಕೇಶನ್ ಮಟ್ಟದಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗಿದೆ
- `provider_connections.access_token`, `refresh_token`, `id_token` — ಅಪ್ಲಿಕೇಶನ್ ಮಟ್ಟದಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗಿದೆ
- `namespace = "secrets"` ಹೊಂದಿರುವ `key_value` ನಮೂದುಗಳು — ಅಪ್ಲಿಕೇಶನ್ ಮಟ್ಟದಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗಿದೆ
- `proxy_registry.auth` — ಅಪ್ಲಿಕೇಶನ್ ಮಟ್ಟದಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗಿದೆ (ಇದ್ದರೆ)

### ಎನ್ಕ್ರಿಪ್ಶನ್ ಕೀ

ಎನ್ಕ್ರಿಪ್ಶನ್ ಕೀಯನ್ನು ಒಂದು **ಪಾಸ್ಫ್ರೇಸ್** (`STORAGE_ENCRYPTION_KEY` ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ ಮೂಲಕ ಹೊಂದಿಸಲಾಗಿದೆ) ಮತ್ತು ಒಂದು **ಸಾಲ್ಟ್** (DB ಯಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ) ನಿಂದ ಪಡೆಯಲಾಗುತ್ತದೆ. ಡೇಟಾವನ್ನು ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲು ಇವೆರಡೂ ಅಗತ್ಯವಿವೆ.

```bash
# ಸುರಕ್ಷಿತ ಪಾಸ್ಫ್ರೇಸ್ ರಚಿಸಿ
openssl rand -hex 32

# .env ನಲ್ಲಿ ಹೊಂದಿಸಿ
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **ಅತ್ಯಂತ ಮುಖ್ಯ**: ಎನ್ಕ್ರಿಪ್ಶನ್ ಕೀ ಕಳೆದುಹೋದರೆ, ಎಲ್ಲಾ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ಡೇಟಾಗೆ ಪ್ರವೇಶವನ್ನು ಕಳೆದುಕೊಳ್ಳುತ್ತೀರಿ. **ಕೀಯನ್ನು ಡೇಟಾಬೇಸ್ನಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿ ಬ್ಯಾಕಪ್ ಮಾಡಿ**.

### ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡದಿರುವುದು ಯಾವುದು

ಕಾರ್ಯಕ್ಷಮತೆಯ ಕಾರಣಗಳಿಂದ, ಕೆಳಗಿನವುಗಳನ್ನು ಪ್ಲೇನ್ಟೆಕ್ಸ್ಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ:

- ಪ್ರೊವೈಡರ್ ಪ್ರದರ್ಶನ ಹೆಸರುಗಳು
- ಮಾಡೆಲ್ ವ್ಯಾಖ್ಯಾನಗಳು (ಈಗಾಗಲೇ ಸಾರ್ವಜನಿಕವಾಗಿವೆ)
- ರೂಟಿಂಗ್ ನಿಯಮಗಳು
- ಬಳಕೆಯ ದಾಖಲೆಗಳು (ಯಾವುದೇ PII ಇಲ್ಲ)

## ಎನ್ಕ್ರಿಪ್ಶನ್ ಮುನ್ನೆಚ್ಚರಿಕೆಗಳು (v3.8.16+)

ಎರಡು ಎನ್ಕ್ರಿಪ್ಶನ್ ವಿಧಾನಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ನಿರ್ವಹಿಸಲು OmniRoute **`migrateLegacyEncryptedString()`** ಅನ್ನು ಬಳಸುತ್ತದೆ:

- **ಹಳೆಯದು** (v3.5.0 ಕ್ಕಿಂತ ಮೊದಲು): XOR-ಆಧಾರಿತ "ಎನ್ಕ್ರಿಪ್ಶನ್" (ನೈಜ ಕ್ರಿಪ್ಟೋಗ್ರಫಿ ಅಲ್ಲ)
- **ಪ್ರಸ್ತುತ**: ಸೂಕ್ತ IV ಮತ್ತು ದೃಢೀಕರಣ ಟ್ಯಾಗ್ನೊಂದಿಗೆ AES-256-GCM

ವಲಸೆ ಸಹಾಯಕವು ಹಳೆಯ ಸ್ವರೂಪವನ್ನು ಪತ್ತೆಹಚ್ಚಿ, ಮೊದಲ ಬಾರಿ ಓದುವಾಗ ಹೊಸ ವಿಧಾನದಿಂದ ಮರು-ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ. ಇದರರ್ಥ ರುಜುವಾತುಗಳನ್ನು ಕಳೆದುಕೊಳ್ಳದೆ ನೀವು ಹಳೆಯ ಡೇಟಾಬೇಸ್ ಅನ್ನು ಅಪ್ಗ್ರೇಡ್ ಮಾಡಬಹುದು.

## ಓದುವಿಕೆ ಕ್ಯಾಶ್

ಆಗಾಗ್ಗೆ ಓದಲಾಗುವ ಡೇಟಾಕ್ಕಾಗಿ (ಮಾದರಿಗಳು, ಪೂರೈಕೆದಾರರು, ಸೆಟ್ಟಿಂಗ್ಗಳು), `readCache.ts` ಒಂದು **ಇನ್-ಮೆಮೊರಿ ಕ್ಯಾಶ್** ಅನ್ನು ಒದಗಿಸುತ್ತದೆ:

```ts
// ಪ್ರಾರಂಭದ ಸಮಯದಲ್ಲಿ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ, ಬರೆಯುವಾಗ ಅಮಾನ್ಯಗೊಳಿಸಲಾಗುತ್ತದೆ
const providers = await getCachedProviders(); // ವೇಗವಾದ, ಇನ್-ಮೆಮೊರಿ
const fresh = await listProviders(); // ನಿಧಾನವಾದ, DB ಅನ್ನು ಪ್ರವೇಶಿಸುತ್ತದೆ
```

| ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಘಟಕ      | ಕ್ಯಾಶ್ ಕೀ      | TTL         |
| ---------------------- | -------------- | ----------- |
| `models`               | `models:v1`    | ಬರೆಯುವವರೆಗೆ |
| `provider_connections` | `providers:v1` | ಬರೆಯುವವರೆಗೆ |
| `settings`             | `settings:v1`  | ಬರೆಯುವವರೆಗೆ |
| `combos`               | `combos:v1`    | ಬರೆಯುವವರೆಗೆ |

ಅನುಗುಣವಾದ ಕೋಷ್ಟಕಕ್ಕೆ ಪ್ರತಿ ಬಾರಿ ಬರೆಯುವಾಗ ಕ್ಯಾಶ್ ಅನ್ನು ಅಮಾನ್ಯಗೊಳಿಸಲಾಗುತ್ತದೆ.

- ಎಲ್ಲಾ DB ಕೋಷ್ಟಕಗಳು (JSON ಗೆ ಸೀರಿಯಲೈಸ್ ಮಾಡಲಾದವು)
- ಕರೆ ಲಾಗ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು (base64-ಎನ್ಕೋಡ್ ಮಾಡಲಾದವು, ಐಚ್ಛಿಕ)
- ಸೆಟ್ಟಿಂಗ್ಗಳು + ರಹಸ್ಯಗಳು (ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾದವು)
- ಪ್ಲಗಿನ್ ಸಂರಚನೆ

### ಮರುಸ್ಥಾಪನೆ

```bash
# CLI ಮೂಲಕ
omniroute restore pre-migration

# API ಮೂಲಕ
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **ಎಚ್ಚರಿಕೆ**: ಮರುಸ್ಥಾಪನೆಯು ಸಂಪೂರ್ಣ DB ಅನ್ನು ತಿದ್ದಿಬರೆಯುತ್ತದೆ. ಮೊದಲು ಎಲ್ಲಾ ಕ್ಲೈಂಟ್ಗಳನ್ನು ನಿಲ್ಲಿಸಿ.

### ಸ್ವಯಂಚಾಲಿತ ಬ್ಯಾಕಪ್ಗಳು

```bash
# CLI ಮೂಲಕ ಸ್ವಯಂಚಾಲಿತ ದೈನಂದಿನ ಬ್ಯಾಕಪ್ಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

ವೇಳಾಪಟ್ಟಿಯನ್ನು ಸರ್ವರ್ನಲ್ಲಿನ ಹಿನ್ನೆಲೆ ಜಾಬ್ ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆ; ಅದು ಪ್ರತಿ 30 ಸೆಕೆಂಡಿಗೆ
(ಡೀಫಾಲ್ಟ್) ಟಿಕ್ ಆಗುತ್ತದೆ ಮತ್ತು ಸ್ಥಳೀಯ ಸರ್ವರ್ ಸಮಯದ ವಿರುದ್ಧ cron ಎಕ್ಸ್ಪ್ರೆಶನ್ ಅನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡುತ್ತದೆ.

| ವೇರಿಯಬಲ್                                    | ಡೀಫಾಲ್ಟ್ | ವಿವರಣೆ                                                                                                               |
| ------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`  | ms ನಲ್ಲಿ ಟಿಕ್ ಮಧ್ಯಂತರ (ಕನಿಷ್ಠ `5000`). ಹೊಂದಿಕೆಯಾಗುವ cron ನಿಮಿಷದೊಳಗೆ ವಿಶ್ವಾಸಾರ್ಹವಾಗಿ ಬರಲು ಇದು 60 s ಗಿಂತ ಕಡಿಮೆ ಇರಬೇಕು. |

### SQLite ಹಾಟ್ ಬ್ಯಾಕಪ್

ಚಾಲನೆಯಲ್ಲಿರುವ DB ಯನ್ನು ಯಾವುದೇ ಡೌನ್ಟೈಮ್ ಇಲ್ಲದೆ ಬ್ಯಾಕಪ್ ಮಾಡಲು:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

ಇದು SQLite ನ ಆನ್ಲೈನ್ ಬ್ಯಾಕಪ್ API ಅನ್ನು ಬಳಸುತ್ತದೆ — OmniRoute ಚಾಲನೆಯಲ್ಲಿರುವಾಗಲೂ ಇದನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ಚಲಾಯಿಸಬಹುದು.

## ಕಾರ್ಯಕ್ಷಮತೆ ಶ್ರುತಿ

### WAL ಮೋಡ್

WAL ಅನ್ನು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ. ಹೆಚ್ಚಿನ ಬರೆಯುವ ಕೆಲಸದ ಹೊರೆಗಳಿಗಾಗಿ, ಪರಿಗಣಿಸಿ:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` ಹೊಂದಿಸುವುದಿಲ್ಲ. ಒಂದು ಚೆಕ್ಪಾಯಿಂಟ್ WAL ಫ್ರೇಮ್ಗಳನ್ನು ಮುಖ್ಯ ಫೈಲ್ಗೆ ಚಲಿಸುತ್ತದೆ, ಆದರೆ WAL ಫೈಲ್ ತನ್ನ ದೊಡ್ಡ ಹಂಚಿಕೆ ಗಾತ್ರವನ್ನು ಇರಿಸುತ್ತದೆ. `OMNIROUTE_WAL_GUARD_MAX_MB` ಗಾರ್ಡ್ `wal_checkpoint(RESTART)` ಮಾತ್ರ ಎಚ್ಚರಿಸುತ್ತದೆ ಮತ್ತು ರನ್ ಮಾಡುತ್ತದೆ; ಇದು ಡಿಸ್ಕ್ ಗಾತ್ರದ ಕ್ಯಾಪ್ ಅಲ್ಲ.

### ಸೂಚ್ಯಂಕಗಳು

ಕಾರ್ಯಕ್ಷಮತೆಗಾಗಿ ಪ್ರಮುಖ ಸೂಚ್ಯಂಕಗಳು (ವಲಸೆಯಿಂದ ಸ್ವಯಂ-ರಚಿಸಲಾಗಿದೆ):

- ಒದಗಿಸುವವರಿಂದ `idx_models_provider` — ಮಾದರಿಯ ಹುಡುಕಾಟಗಳು
- `idx_combo_targets_combo_id` — ಕಾಂಬೊ ಗುರಿ ವಿಸ್ತರಣೆ
- `idx_usage_history_api_key_timestamp` — ಬಳಕೆಯ ವಿಶ್ಲೇಷಣೆ
- `idx_quota_snapshots_api_key_window` — ಕೋಟಾ ಟ್ರ್ಯಾಕಿಂಗ್
- `idx_call_logs_timestamp` — ಕರೆ ಲಾಗ್ ಪ್ರಶ್ನೆಗಳು

ಹೊಸ ಸೂಚಿಯನ್ನು ಸೇರಿಸಲು, ವಲಸೆಯನ್ನು ರಚಿಸಿ:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### ಮೆಮೊರಿ-ಮ್ಯಾಪ್ ಮಾಡಿದ I/O

ದೊಡ್ಡ ಡೇಟಾಬೇಸ್ಗಳಿಗಾಗಿ (> 10GB), ಮೆಮೊರಿ ಮ್ಯಾಪಿಂಗ್ ಅನ್ನು SQLite ಪ್ರಾಗ್ಮಾ ಮೂಲಕ ಸರಿಹೊಂದಿಸಬಹುದು:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### ಸಂಕೋಚನ

ದೀರ್ಘಾವಧಿಯ OmniRoute ನಿದರ್ಶನಗಳು ಸಾಂದರ್ಭಿಕ `VACUUM` ನಿಂದ ಪ್ರಯೋಜನ ಪಡೆಯುತ್ತವೆ:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

ಕಡಿಮೆ ಟ್ರಾಫಿಕ್ ವಿಂಡೋಗಳಲ್ಲಿ ಮಾಸಿಕ ರನ್ ಮಾಡಿ. (WAL ಮೋಡ್ ಅಗತ್ಯವನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ, ಆದರೆ ಅದನ್ನು ತೊಡೆದುಹಾಕುವುದಿಲ್ಲ.)

## ಆರೋಗ್ಯ ಪರಿಶೀಲನೆ

`src/lib/db/healthCheck.ts` **DB-ಮಟ್ಟದ ಆರೋಗ್ಯ ತಪಾಸಣೆಗಳನ್ನು** ಒದಗಿಸುತ್ತದೆ:

ಎರಡೂ ಕ್ರಿಯಾಪದಗಳಿಗೆ ದೃಢೀಕರಣದ ಅಗತ್ಯವಿದೆ (ಇಲ್ಲದಿದ್ದರೆ `401`). `GET` ಕೇವಲ ರೋಗನಿರ್ಣಯ ಮಾಡುತ್ತದೆ; `POST`,
`autoRepair` ಸಕ್ರಿಯಗೊಳಿಸಿ ಅದೇ ಪರಿಶೀಲನೆಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ.

```bash
GET  /api/db/health   # ರೋಗನಿರ್ಣಯ
POST /api/db/health   # ರೋಗನಿರ್ಣಯ + ದುರಸ್ತಿ
```

ಪ್ರತಿಕ್ರಿಯೆಯು `runDbHealthCheck()` ಉತ್ಪಾದಿಸಿದ `DbHealthCheckResult` ಆಗಿದೆ
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Domain budgets referenced API keys that no longer exist.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ಕ್ಷೇತ್ರ           | ಅರ್ಥ                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `issues` ಖಾಲಿಯಾಗಿದ್ದಾಗ `true`. `driver` ಎಂದಿಗೂ ಇದರ ಮೇಲೆ ಪ್ರಭಾವ ಬೀರುವುದಿಲ್ಲ.                                                                 |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` ಇವುಗಳಲ್ಲಿ ಒಂದು.                                             |
| `repairedCount`   | ಈ ಚಾಲನೆಯ ಸಮಯದಲ್ಲಿ ದುರಸ್ತಿಗೊಳಿಸಲಾದ ಸಾಲುಗಳು; `autoRepair` false ಆಗಿರುವಾಗ ಯಾವಾಗಲೂ `0`.                                                         |
| `backupCreated`   | ದುರಸ್ತಿ ಮಾಡುವ ಮೊದಲು ಬ್ಯಾಕಪ್ ತೆಗೆದುಕೊಳ್ಳಲಾಗಿದೆಯೇ ಎಂಬುದು.                                                                                     |
| `checkedAt`       | ಚಾಲನೆ ಮತ್ತು ಅದು ಬರೆಯುವ ಯಾವುದೇ ದುರಸ್ತಿ ಟಿಪ್ಪಣಿ ಹಂಚಿಕೊಳ್ಳುವ ISO ಕಾಲಮುದ್ರೆ.                                                                    |
| `driver.name`     | ಪರಿಶೀಲಿಸಲಾದ ಡೇಟಾಬೇಸ್ಗೆ ಸೇವೆ ಒದಗಿಸುವ SQLite ಡ್ರೈವರ್.                                                                                         |
| `driver.degraded` | ಬರವಣಿಗೆಗಳು ಡೇಟಾಬೇಸ್ ಫೈಲ್ನಿಂದ ಸ್ಥಿರವಾಗಿ ಬೆಂಬಲಿತವಾಗಿಲ್ಲದಾಗ `true` — `sql.js` WASM ಫಾಲ್ಬ್ಯಾಕ್ (ಸಂಪೂರ್ಣ-ಫೈಲ್ ಸ್ಥಿರತೆ) ಅಥವಾ ಇನ್-ಮೆಮೊರಿ ಡೇಟಾಬೇಸ್. |

ಅದೇ ಪೇಲೋಡ್ ಅನ್ನು `omniroute_db_health_check` MCP ಉಪಕರಣವು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.

ದೋಷಪೂರಿತತೆಯನ್ನು ಪತ್ತೆಹಚ್ಚಲು `PRAGMA integrity_check` ಅನ್ನು ಚಲಾಯಿಸಿ:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ಇದನ್ನು ಮುದ್ರಿಸಬೇಕು: ok
```

ಇದು `ok` ಹೊರತುಪಡಿಸಿ ಬೇರೆ ಯಾವುದನ್ನಾದರೂ ಹಿಂತಿರುಗಿಸಿದರೆ, **ಡೇಟಾಬೇಸ್ ಬಳಸುವುದನ್ನು ತಕ್ಷಣ ನಿಲ್ಲಿಸಿ** ಮತ್ತು ಬ್ಯಾಕಪ್ನಿಂದ ಮರುಸ್ಥಾಪಿಸಿ.

## ವಿಪತ್ತು ಮರುಪಡೆಯುವಿಕೆ

### ಸನ್ನಿವೇಶ 1: WAL ಫೈಲ್ ಕಳೆದುಹೋಗಿದೆ

`-wal` ಫೈಲ್ ಕಾಣೆಯಾಗಿದೆ, ಆದರೆ `-shm` ಮತ್ತು ಮುಖ್ಯ DB ಸುಸ್ಥಿತಿಯಲ್ಲಿವೆ:

```bash
# ಮುಂದಿನ ಬಾರಿ ತೆರೆದಾಗ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮರುಪಡೆಯುತ್ತದೆ
omniroute
```

SQLite ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮರುಪಡೆಯಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### ಸನ್ನಿವೇಶ 2: ಮುಖ್ಯ DB ಫೈಲ್ ಹಾನಿಗೊಳಗಾಗಿದೆ

ಬ್ಯಾಕಪ್ನಿಂದ ಮರುಸ್ಥಾಪಿಸಿ:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` ಚಾಲನೆಯಲ್ಲಿರುವ ಸರ್ವರ್ನಿಂದ ಸಂಪೂರ್ಣ `.tar.gz` ಆರ್ಕೈವ್ ಅನ್ನು ಮಾತ್ರ ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ
(`GET /api/db-backups/exportAll`, ಆಪರೇಟರ್ ರುಜುವಾತು ಅಗತ್ಯವಿದೆ); ಅದು ಯಾವುದನ್ನೂ ಮರುಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

### ಸನ್ನಿವೇಶ 3: ಎನ್ಕ್ರಿಪ್ಶನ್ ಕೀ ಕಳೆದುಹೋಗಿದೆ

ಕೀ ಇಲ್ಲದೆ **ಮರುಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ**. ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ಫೀಲ್ಡ್ಗಳನ್ನು ಓದಲು ಸಾಧ್ಯವಿಲ್ಲ. ಹೊಸ ರುಜುವಾತುಗಳೊಂದಿಗೆ ಎಲ್ಲಾ ಪೂರೈಕೆದಾರರನ್ನು ಹಸ್ತಚಾಲಿತವಾಗಿ ಪುನಃ ಸೇರಿಸಿ.

> **ತಗ್ಗಿಸುವ ಕ್ರಮ**: ಎನ್ಕ್ರಿಪ್ಶನ್ ಕೀಯನ್ನು ಯಾವಾಗಲೂ ಪ್ರತ್ಯೇಕವಾಗಿ ಬ್ಯಾಕಪ್ ಮಾಡಿ; ಸಾಧ್ಯವಾದರೆ ಪಾಸ್ವರ್ಡ್ ಮ್ಯಾನೇಜರ್ ಅಥವಾ KMS ನಲ್ಲಿ ಇರಿಸಿ.

### ಸನ್ನಿವೇಶ 4: ಡಿಸ್ಕ್ ತುಂಬಿದೆ

SQLite `SQLITE_FULL` ದೋಷಗಳನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ. ಡಿಸ್ಕ್ ಸ್ಥಳವನ್ನು ತೆರವುಗೊಳಿಸಿ, ನಂತರ:

```bash
# ಸ್ಥಳವನ್ನು ಮುಕ್ತಗೊಳಿಸಲು WAL ಚೆಕ್ಪಾಯಿಂಟ್ ಮಾಡಿ
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## ಸಮಸ್ಯೆ ನಿವಾರಣೆ

### "ಡೇಟಾಬೇಸ್ ಲಾಕ್ ಆಗಿದೆ"

ಮತ್ತೊಂದು ಪ್ರಕ್ರಿಯೆಯು ಬರವಣಿಗೆ ಲಾಕ್ ಅನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಂಡಿದೆ. ಈ ಕೆಳಗಿನವುಗಳಲ್ಲಿ ಒಂದನ್ನು ಮಾಡಿ:

- ಮತ್ತೊಂದು ಪ್ರಕ್ರಿಯೆ ಪೂರ್ಣಗೊಳ್ಳುವವರೆಗೆ ಕಾಯಿರಿ (`lsof | grep storage.sqlite` ಪರಿಶೀಲಿಸಿ)
- ಮತ್ತೊಂದು ಪ್ರಕ್ರಿಯೆಯನ್ನು ಕೊನೆಗೊಳಿಸಿ
- ಸಮಸ್ಯೆ ಮುಂದುವರಿದರೆ, OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ

### "ಫಾರಿನ್ ಕೀ ನಿರ್ಬಂಧ ವಿಫಲವಾಗಿದೆ"

ಡೊಮೇನ್ ಮಾಡ್ಯೂಲ್ ಒಂದು ಉಲ್ಲೇಖಾತ್ಮಕ ಸಮಗ್ರತೆಯನ್ನು ಉಲ್ಲಂಘಿಸುತ್ತಿದೆ. ಇವುಗಳನ್ನು ಪರಿಶೀಲಿಸಿ:

- ಅವಲಂಬಿತ ಟೇಬಲ್ಗಳಲ್ಲಿನ ಅನಾಥ ಸಾಲುಗಳು
- ಪ್ರಸಾರವಾಗದ ಕ್ಯಾಸ್ಕೇಡಿಂಗ್ ಅಳಿಸುವಿಕೆಗಳು
- ಫಾರಿನ್ ಕೀಯನ್ನು ಬದಲಾಯಿಸಿದ ಇತ್ತೀಚಿನ ಮೈಗ್ರೇಶನ್

ಉಲ್ಲಂಘನೆಗಳನ್ನು ಕಂಡುಹಿಡಿಯಲು `PRAGMA foreign_key_check;` ಅನ್ನು ಚಲಾಯಿಸಿ.

### "ಮೆಮೊರಿ ಖಾಲಿಯಾಗಿದೆ"

SQLite ನ ಮೆಮೊರಿ-ಮ್ಯಾಪ್ ಮಾಡಿದ I/O, OS ಮಿತಿಯನ್ನು ಮೀರುತ್ತಿದೆ. SQLite pragma ಮೂಲಕ ಅದನ್ನು ಕಡಿಮೆ ಮಾಡಿ:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB ಬದಲಿಗೆ 128MB
```

ಅಥವಾ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿ:

```sql
PRAGMA mmap_size = 0;
```

### "ಮೈಗ್ರೇಶನ್ ಮಧ್ಯದಲ್ಲೇ ವಿಫಲವಾಗಿದೆ"

ಮೈಗ್ರೇಶನ್ ಒಂದು ಟ್ರಾನ್ಸಾಕ್ಷನ್ನಲ್ಲಿ ಚಲಿಸಿದ್ದರಿಂದ, ಅದು ರೋಲ್ಬ್ಯಾಕ್ ಆಗಿರಬೇಕು. ಹಾಗಾಗದಿದ್ದರೆ:

1. **OmniRoute ಅನ್ನು ನಿಲ್ಲಿಸಿ** (ಮುಂದಿನ ಪ್ರಯತ್ನಗಳನ್ನು ತಡೆಯಿರಿ)
2. `sqlite3` ಮೂಲಕ **DB ಸ್ಥಿತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ**
3. ಅಪೂರ್ಣ ಮೈಗ್ರೇಶನ್ ಅನ್ನು **ಹಸ್ತಚಾಲಿತವಾಗಿ ಸರಿಪಡಿಸಿ**
4. OmniRoute ಅನ್ನು **ಮರುಚಲಾಯಿಸಿ** (ಮೈಗ್ರೇಶನ್ ಅನ್ನು ಪುನಃ ಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ)

ಇದನ್ನು ತಡೆಯಲು, ಯಾವಾಗಲೂ ಮೊದಲು ನಕಲಿನ ಮೇಲೆ ಮೈಗ್ರೇಶನ್ಗಳನ್ನು ಪರೀಕ್ಷಿಸಿ.
