> **ಸತ್ಯದ ಮೂಲ:** `src/lib/db/reasoningCache.ts`, `open-sse/services/reasoningCache.ts`** ಕೊನೆಯದಾಗಿ ನವೀಕರಿಸಲಾಗಿದೆ:** 2026-06-28 — v3.8.40

OmniRoute ಥಿಂಕಿಂಗ್-ಮೋಡ್ ಮಾಡೆಲ್ಗಳಿಂದ ಉತ್ಪತ್ತಿಯಾಗುವ ಸಹಾಯಕ `reasoning_content` ಸೆರೆಹಿಡಿಯುತ್ತದೆ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರಿಗೆ ಅಗತ್ಯವಿರುವಾಗ ಬಹು-ತಿರುವು ವಿನಂತಿಗಳಲ್ಲಿ ಅದನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ಮರುಪಂದ್ಯ ಮಾಡುತ್ತದೆ. ಕ್ಲೈಂಟ್ನ ಸಂಭಾಷಣೆಯ ಇತಿಹಾಸವು ಹಿಂದಿನ ಸರದಿಯ ತಾರ್ಕಿಕತೆಯನ್ನು ಕಳೆದುಕೊಂಡಿರುವಾಗ ಕಟ್ಟುನಿಟ್ಟಾದ ಪೂರೈಕೆದಾರರು ಹೆಚ್ಚಿಸುವ HTTP 400 ದೋಷಗಳನ್ನು ಇದು ನಿವಾರಿಸುತ್ತದೆ.

## ಇದು ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ

ಹಲವಾರು ಥಿಂಕಿಂಗ್-ಮೋಡ್ ಪೂರೈಕೆದಾರರು ಫಾಲೋ-ಅಪ್ ಟರ್ನ್ ಅನ್ನು ತಿರಸ್ಕರಿಸುತ್ತಾರೆ** ಹಿಂದಿನ ಸಹಾಯಕ ಸಂದೇಶವು ಮೂಲ `reasoning_content` ಅನ್ನು ಒಳಗೊಂಡಿದೆ** . ಅಪ್ಸ್ಟ್ರೀಮ್ ಈ ರೀತಿಯ ಸಂದೇಶಗಳೊಂದಿಗೆ 400 ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ:

```
Param Incorrect: The reasoning_content in the thinking mode must be passed back to the API.
```

ಆದರೆ ವಿಶಿಷ್ಟ ಕ್ಲೈಂಟ್ಗಳು (Cursor, Cline, Roo Code, OpenAI SDK) ಅವರು ರಿಪ್ಲೇ ಮಾಡುವ ಇತಿಹಾಸದಿಂದ `reasoning_content` ತೆಗೆದುಹಾಕುತ್ತಾರೆ. OmniRoute ಅದನ್ನು ಸರ್ವರ್-ಸೈಡ್ ಕ್ಯಾಶ್ನಿಂದ ಮರುಸ್ಥಾಪಿಸುತ್ತದೆ ಆದ್ದರಿಂದ ಅಪ್ಸ್ಟ್ರೀಮ್ ನೋಡುವ ವಿನಂತಿಯು ಸ್ಥಿರವಾಗಿರುತ್ತದೆ. ಸಂಚಿಕೆ #1628 ಹೈಬ್ರಿಡ್ memory/SQLite ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಅನ್ನು ಪರಿಚಯಿಸಿತು ಆದ್ದರಿಂದ ಸಂಗ್ರಹವು ಉಳಿದಿರುವ ಪ್ರಕ್ರಿಯೆ ಮರುಪ್ರಾರಂಭಗೊಳ್ಳುತ್ತದೆ.

## ವಾಸ್ತುಶಿಲ್ಪ

```
Turn N (assistant generates):
  → response contains reasoning_content + tool_calls
  → if requiresReasoningReplay(provider, model): cacheReasoningFromAssistantMessage()
      writes (memory + DB), one entry per tool_call.id within the request scope
  → forward response to client (which may or may not retain reasoning)

Turn N+1 (client sends follow-up):
  → translator detects: requiresReasoningReplay(provider, model) === true
  → for each assistant message with tool_calls and no reasoning_content:
      lookupReasoning(buildToolCallCacheKey(scope, toolCalls[0].id)) → memory → DB
      hit  → msg.reasoning_content = cached; recordReplay()
      miss → msg.reasoning_content = "" (legacy fallback for older DeepSeek)
  → upstream sees consistent history → no 400
```

ಸೆರೆಹಿಡಿಯುವಿಕೆಯು `open-sse/handlers/chatCore.ts` ನಲ್ಲಿ ನಡೆಯುತ್ತದೆ (ಎರಡು ಸೈಟ್ಗಳು, ಎರಡು `cacheReasoningFromAssistantMessage` ಕರೆ ಸೈಟ್ಗಳಲ್ಲಿ). ಸ್ಕೀಮಾ ಬಲವಂತದ ನಂತರ ಆದರೆ ಕಳುಹಿಸುವ ಮೊದಲು `open-sse/translator/index.ts` ನಲ್ಲಿ ಮರುಪಂದ್ಯ ನಡೆಯುತ್ತದೆ.

ಟೂಲ್-ಕಾಲ್ ನಮೂದುಗಳನ್ನು `buildToolCallCacheKey()` ಅಡಿಯಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ, ವಿನಂತಿಯ ಸ್ಕೋಪ್ ಮತ್ತು ಟೂಲ್ ಕರೆ ಐಡಿ ಡೈಜೆಸ್ಟ್, ಆದ್ದರಿಂದ ಮತ್ತೊಂದು API ಕೀ ಅಥವಾ ಸೆಶನ್ ಬಳಸುವ ಅದೇ ಐಡಿ ನಮೂದನ್ನು ಆಯ್ಕೆ ಮಾಡುವುದಿಲ್ಲ. ಸ್ಕೋಪ್ `buildReasoningCacheScope()` ನಿಂದ ಬರುತ್ತದೆ : API ಕೀ ಐಡಿ, ಜೊತೆಗೆ ವಿನಂತಿಯು ಒಂದನ್ನು ಹೊಂದಿರುವಾಗ ಸೆಷನ್ ಕೀ. ಆದ್ದರಿಂದ `tool_call_id` ಕಾಲಮ್ ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಆ ನಮೂದುಗಳಿಗಾಗಿ ಈ ಡೈಜೆಸ್ಟ್ ಅನ್ನು ತೋರಿಸುತ್ತದೆ.

ಸರಳವಾದ (ಉಪಕರಣ-ಅಲ್ಲದ) ಸಹಾಯಕ ತಿರುವುಗಳನ್ನು ವಿಭಿನ್ನವಾಗಿ ಕೀ ಮಾಡಲಾಗಿದೆ: `buildAssistantMessageCacheKey()` ಸೆಷನ್ ಸ್ಕೋಪ್ ಮತ್ತು ಸಾಮಾನ್ಯೀಕರಿಸಿದ OpenAI-ಫಾರ್ಮ್ಯಾಟ್ ಪ್ರತಿಲೇಖನವನ್ನು ಆ ತಿರುವಿನವರೆಗೆ ಜೀರ್ಣಿಸುತ್ತದೆ, ಏಕೆಂದರೆ DeepSeek ಒಮ್ಮೆ `tools` ಇದ್ದಾಗ _every_ ಹಿಂದಿನ ತಿರುವಿನ ತಾರ್ಕಿಕತೆಯ ಅಗತ್ಯವಿರುತ್ತದೆ. ಪ್ರತಿಕ್ರಿಯೆಗಳು-API ಗುರಿಗಳಿಗಾಗಿ (ಉದಾಹರಣೆಗೆ `opencode-go/deepseek-v4-flash`, `/responses` ಗೆ ರೂಟ್ ಮಾಡಲಾಗಿದೆ ) ಅಪ್ಸ್ಟ್ರೀಮ್ ದೇಹವು `input` ಅಲ್ಲ `messages` ಅನ್ನು ಒಯ್ಯುತ್ತದೆ, ಆದ್ದರಿಂದ `translateRequest()` (`open-sse/translator/index.ts`) ಇದು ಕಾಲ್ಬ್ಯಾಕ್ ಆಯ್ಕೆಯ ಮೂಲಕ ಜೀರ್ಣಿಸಿದ ಪಿವೋಟ್ ಪ್ರತಿಲೇಖನವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಕ್ಯಾಪ್ಚರ್ ಸೈಟ್ಗಳು ಅದೇ ಪ್ರತಿಲೇಖನವನ್ನು ಜೀರ್ಣಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಪ್ರತಿಕ್ರಿಯೆಗಳ ಮರುಪಂದ್ಯದ ಪಾಸ್ ಪ್ರತಿ ಮೂಲ ಸ್ವರೂಪಕ್ಕಾಗಿ OpenAI ಪಿವೋಟ್ನಲ್ಲಿ ಚಲಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ Anthropic ಸಂದೇಶಗಳ ಕ್ಲೈಂಟ್ಗಳು (Claude → OpenAI → ಪ್ರತಿಕ್ರಿಯೆಗಳು) ಸಹ ಮರುಪಂದ್ಯವನ್ನು ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ.

## ಸ್ಟೋರೇಜ್ — ಹೈಬ್ರಿಡ್ ಮೆಮೊರಿ + SQLite

ಹಾಟ್ ಪಾತ್ ಕ್ರ್ಯಾಶ್ ರಿಕವರಿ ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಗೋಚರತೆಗಾಗಿ SQLite ಟೇಬಲ್ನಿಂದ ಬೆಂಬಲಿತವಾದ ಇನ್-ಮೆಮೊರಿ `Map` (LRU-by-creation) ಅನ್ನು ಬಳಸುತ್ತದೆ.

| ಪದರ    | ಅನುಷ್ಠಾನ                                         | ಉದ್ದೇಶ                                                  |
| ------ | ------------------------------------------------ | ------------------------------------------------------- |
| ಸ್ಮರಣೆ | `open-sse/services/reasoningCache.ts` ನಲ್ಲಿ`Map` | ವೇಗದ ಲುಕ್ಅಪ್ಗಳು, 200 ವರ್ಷಕ್ಕಿಂತ ಹಳೆಯವರನ್ನು ಹೊರಹಾಕುತ್ತದೆ |
| DB     | `reasoning_cache` ಟೇಬಲ್ (`src/lib/db/`)          | ಪುನರಾರಂಭಗಳು, ಡ್ರೈವ್ ಅಂಕಿಅಂಶಗಳಾದ್ಯಂತ ಮುಂದುವರಿಯುತ್ತದೆ     |

ಬರಹಗಳು ಎರಡಕ್ಕೂ ಹೋಗುತ್ತವೆ. ಮೊದಲು ಮೆಮೊರಿಯನ್ನು ಸಮಾಲೋಚಿಸಿ ಓದುತ್ತದೆ, ನಂತರ DB ಗೆ ಹಿಂತಿರುಗಿ (DB ಹಿಟ್ಗಳನ್ನು ಮತ್ತೆ ಮೆಮೊರಿಗೆ ಉತ್ತೇಜಿಸಲಾಗುತ್ತದೆ). DB ವೈಫಲ್ಯಗಳು ಮಾರಣಾಂತಿಕವಲ್ಲದ — ಇನ್-ಮೆಮೊರಿ ಸಂಗ್ರಹವು ಹಾಟ್ ಪಾಥ್ಗೆ ಸೇವೆ ಸಲ್ಲಿಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತದೆ.

**ಡೀಫಾಲ್ಟ್ಗಳು:**

- TTL: `2h` (`TTL_MS = 2 * 60 * 60 * 1000`)
- ಗರಿಷ್ಠ ಮೆಮೊರಿ ನಮೂದುಗಳು: `200` (`MAX_MEMORY_ENTRIES`)
- ಹೊರಹಾಕುವಿಕೆ: ಅತ್ಯಂತ ಹಳೆಯ `createdAt` ಮೊದಲು

## ಡೇಟಾಬೇಸ್ ಸ್ಕೀಮಾ

ವಲಸೆ: `src/lib/db/migrations/033_create_reasoning_cache.sql`

```sql
CREATE TABLE IF NOT EXISTS reasoning_cache (
  tool_call_id   TEXT PRIMARY KEY,
  provider       TEXT NOT NULL,
  model          TEXT NOT NULL,
  reasoning      TEXT NOT NULL,
  char_count     INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL DEFAULT (datetime('now')),
  expires_at     INTEGER NOT NULL
);
```

ಸೂಚ್ಯಂಕಗಳು: `expires_at`, `provider`, `model`, `created_at`. `expires_at` ಯುನಿಕ್ಸ್ ಯುಗ ಸೆಕೆಂಡುಗಳಂತೆ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ; SELECT ಪದರವು `EXPIRES_AT_EPOCH_SQL` ಮೂಲಕ ಪರಂಪರೆಯ ಪಠ್ಯ ಮೌಲ್ಯಗಳನ್ನು ಸಾಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ.

ಹೊಸ ಕಟ್ಟುನಿಟ್ಟಾದ provider/model ಸೇರಿಸುವುದು ಎಂದರೆ ಈ ಪಟ್ಟಿಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ ಸೇರಿಸುವುದು ಮತ್ತು ಮರುಪಂದ್ಯದ ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಪ್ರತಿಪಾದಿಸುವ ಘಟಕ ಪರೀಕ್ಷೆಯನ್ನು ಬರೆಯುವುದು ಎಂದರ್ಥ. PR ವಿವರಣೆಯು ಬದಲಾವಣೆಯನ್ನು ಪ್ರೇರೇಪಿಸಿದ ನಿಖರವಾದ ಅಪ್ಸ್ಟ್ರೀಮ್ 400 ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು ಉಲ್ಲೇಖಿಸಬೇಕು.

## ಕಾರ್ಯಾಚರಣೆಯ ಟಿಪ್ಪಣಿಗಳು

- **ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ:** `cleanupReasoningCache()` ಅವಧಿ ಮೀರಿದ ಮೆಮೊರಿ ನಮೂದುಗಳನ್ನು ಶುದ್ಧೀಕರಿಸುತ್ತದೆ ಮತ್ತು `DELETE FROM reasoning_cache WHERE expires_at <= unixepoch('now')` ರನ್ ಮಾಡುತ್ತದೆ. ಆರೋಗ್ಯ ತಪಾಸಣೆ ಕಾರ್ಯಕರ್ತರು ಇದನ್ನು ನಿಯತಕಾಲಿಕವಾಗಿ ಕರೆಯುತ್ತಾರೆ.
- **ಕ್ರ್ಯಾಶ್ ಚೇತರಿಕೆ:** ಮರುಪ್ರಾರಂಭಿಸಿದ ನಂತರ, ಮೆಮೊರಿ ಖಾಲಿಯಾಗಿದೆ ಆದರೆ DB ಇನ್ನೂ ಅವಧಿ ಮೀರಿದ ನಮೂದುಗಳನ್ನು ಹೊಂದಿದೆ. ನೀಡಿರುವ `tool_call_id` ಗಾಗಿ ಮೊದಲ ನೋಟವು DB ಹಿಟ್ ಆಗಿದೆ; ನಂತರದ ಲುಕಪ್ಗಳು ಮೆಮೊರಿ ಹಿಟ್ಗಳಾಗಿವೆ.
- **ತರ್ಕವಿಲ್ಲ, ಸಂಗ್ರಹವಿಲ್ಲ:** ಸಹಾಯಕ ಸಂದೇಶವು `reasoning_content` / `reasoning` ಕ್ಷೇತ್ರವನ್ನು ಹೊಂದಿರದಿದ್ದಾಗ `cacheReasoningFromAssistantMessage` `0` ಹಿಂತಿರುಗಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಯೋಚಿಸದ ಪ್ರತಿಕ್ರಿಯೆಗಳಿಗೆ ಏನೂ ವೆಚ್ಚವಾಗುವುದಿಲ್ಲ.
- **ಬರೆಯುವುದು ಕೂಡ ಗೇಟ್ ಆಗಿದೆ:** `chatCore.ts` ನಲ್ಲಿನ ಎರಡೂ ಕರೆ ಸೈಟ್ಗಳು (ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದ ಮತ್ತು ಸ್ಟ್ರೀಮಿಂಗ್) `requiresReasoningReplay(provider, model)` `true` — ಆಗಿರುವಾಗ ಮಾತ್ರ `cacheReasoningFromAssistantMessage()` ಕರೆ ಮಾಡಿ ಅದೇ ರೀಡ್ ಸೈಡ್ ಚೆಕ್ಗಳನ್ನು ಸೂಚಿಸುತ್ತದೆ. ರಿಪ್ಲೇ ಪೂರೈಕೆದಾರರನ್ನು ಎಂದಿಗೂ ಸ್ಪರ್ಶಿಸದ ಇನ್ಸ್ಟಾಲ್ಗಳು ಪ್ರತಿ ತಾರ್ಕಿಕ-ಬೇರಿಂಗ್ ಪ್ರತಿಕ್ರಿಯೆಯಲ್ಲಿ ಬರಹ, ಸೂಚ್ಯಂಕ ನವೀಕರಣ ಮತ್ತು try/catch ಗೆ ಪಾವತಿಸುವುದನ್ನು ನಿಲ್ಲಿಸುತ್ತವೆ.
- **ಕಠಿಣವಲ್ಲದ ಪೂರೈಕೆದಾರರು:** `requiresReasoningReplay` `false` ಆಗಿದ್ದರೆ ಮತ್ತು ಗುರಿ ಸ್ವರೂಪವು OpenAI ಆಗಿದ್ದರೆ, ಅನುವಾದಕ** ಪಟ್ಟಿಗಳು** ಹೊರಹೋಗುವ ಸಂದೇಶಗಳಿಂದ ಯಾವುದೇ `reasoning_content` ಕ್ಷೇತ್ರವು — OpenAI ಚಾಟ್ ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳು ಅದನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

## ಮ್ಯೂಸ್ ಅಪಾರದರ್ಶಕ-ತಾರ್ಕಿಕ ಮಾಲೀಕತ್ವ

ಮ್ಯೂಸ್ (`muse-code`) ಕಾಲರ್-ಬೌಂಡ್ ಅಪಾರದರ್ಶಕ ತಾರ್ಕಿಕತೆಯನ್ನು (`encrypted_content`) ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಬೇರೆ ಖಾತೆಯ ಅಡಿಯಲ್ಲಿ ಅದನ್ನು ಮರುಪ್ಲೇ ಮಾಡುವುದು ಅಥವಾ ಮರುಮುದ್ರಿಸಿದ ರುಜುವಾತುಗಳು ಅಪ್ಸ್ಟ್ರೀಮ್ನಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ ಸ್ಥಳೀಯ OAuth ವಿನಂತಿಗಳು ಪ್ರತಿ ವಿನಂತಿಯ ತಿರುಗುವಿಕೆಯ ಬದಲಿಗೆ ಸೆಷನ್-ಮಟ್ಟದ ಮಾಲೀಕತ್ವವನ್ನು ಬಳಸುತ್ತವೆ (`src/sse/services/museSessionOwnership.ts`, `src/sse/handlers/chat.ts` ನಲ್ಲಿ ಜಾರಿಗೊಳಿಸಲಾಗಿದೆ). ಸ್ಪಷ್ಟವಾಗಿ ಆಯ್ಕೆಮಾಡಿದ API-ಕೀ ಸಂಪರ್ಕಗಳು ಮತ್ತು API-ಕೀ-ಮಾತ್ರ ಕಾನ್ಫಿಗರೇಶನ್ಗಳು ಈ ಮಾಲೀಕತ್ವ ಮೋಡ್ ಇಲ್ಲದೆಯೇ ತಮ್ಮ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ರೂಟಿಂಗ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

- ಪ್ರತಿ ತಿರುವಿನಲ್ಲಿಯೂ ಸ್ಥಿರವಾದ ಸೆಷನ್ ID ಪೂರೈಸಿ: `x-omniroute-session-id`, `x-omniroute-session`, `x-session-id`, ಅಥವಾ `x-codex-session-id`; ಪರ್ಯಾಯವಾಗಿ ದೇಹದಲ್ಲಿ `prompt_cache_key`, `session_id`, `conversation_id`, ಅಥವಾ `metadata.session_id` ಬಳಸಿ (ಆ ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ). ಎರಡು ಅಥವಾ ಹೆಚ್ಚಿನ ಸ್ಥಳೀಯ OAuth ಖಾತೆಗಳು ಸಕ್ರಿಯವಾಗಿರುವಾಗ ಕಾಣೆಯಾದ ಅಥವಾ ಖಾಲಿ IDs ರಿಟರ್ನ್ 400; ಒಂದೇ OAuth ಖಾತೆಯೊಂದಿಗೆ ತಿರುಗಿಸಲು ಏನೂ ಇರುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಅಂತಹ ವಿನಂತಿಯು ಅನ್ಪಿನ್ ಮಾಡದ ರೂಟಿಂಗ್ ಅನ್ನು ಇರಿಸುತ್ತದೆ. ವ್ಯಾಪ್ತಿ ಕಾಲರ್ನ OmniRoute API-ಕೀ ID ಒಳಗೊಂಡಿದೆ.
- API-ಕೀ ಸಂಪರ್ಕ ನೀತಿಯಿಂದ ಅನುಮತಿಸಲಾದ ಸಕ್ರಿಯ ಸ್ಥಳೀಯ OAuth ಖಾತೆಗಳಾದ್ಯಂತ ತಾಜಾ ಸ್ವತಂತ್ರ ಅವಧಿಗಳು ರೌಂಡ್-ರಾಬಿನ್, ಸಂಪರ್ಕ ID. ರೌಂಡ್-ರಾಬಿನ್ ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಯೊಂದಿಗೆ (`banned`, `expired`, `credits_exhausted`) ಸಂಪರ್ಕದ ಕೂಲ್ಡೌನ್ನಲ್ಲಿ ಖಾತೆಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಅಥವಾ ವಿನಂತಿಸಿದ ಮಾದರಿಗೆ ಮಾದರಿ ಲಾಕ್ ಮಾಡಲಾಗಿದೆ; ಮ್ಯೂಸ್ ಅಪ್ಸ್ಟ್ರೀಮ್ ವೈಫಲ್ಯಗಳು ಇತರ ಪೂರೈಕೆದಾರರಂತೆ ಕೂಲ್ಡೌನ್ ಮತ್ತು ಬ್ರೇಕರ್ ಸ್ಥಿತಿಯನ್ನು ದಾಖಲಿಸುತ್ತವೆ. ಸ್ಪಷ್ಟವಾಗಿ ಬಲವಂತದ ಸಂಪರ್ಕವು ಹೊಸ ಸೆಶನ್ಗಾಗಿ ರೌಂಡ್-ರಾಬಿನ್ ಅನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತದೆ ಆದರೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಮಾಲೀಕರನ್ನು ಅತಿಕ್ರಮಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.
- ಮಾಲೀಕರು ಯಶಸ್ವಿ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ನೀಡುವವರೆಗೆ, ಮಾಲೀಕರು ಅಲಭ್ಯವಾಗಿರುವ ಸೆಷನ್ ಅನ್ನು ಆರೋಗ್ಯಕರ ಖಾತೆಗೆ ಮರು-ಕ್ಲೈಮ್ ಮಾಡಲಾಗುತ್ತದೆ. ಮೊದಲ ಯಶಸ್ವಿ ಪ್ರತಿಕ್ರಿಯೆಯ ನಂತರ, ಸೆಶನ್ 30 ದಿನಗಳವರೆಗೆ ನಿಷ್ಕ್ರಿಯವಾಗಿರುವವರೆಗೆ ಆ ಮಾಲೀಕರಿಗೆ ಪಿನ್ ಆಗಿರುತ್ತದೆ (`MUSE_SESSION_IDLE_TTL_MS`).
- ಪ್ರತಿ ಮುಂದುವರಿಕೆ ಮತ್ತು ಟೂಲ್-ಫಲಿತಾಂಶದ ತಿರುವು ಸೆಷನ್ ಮಾಲೀಕರಿಗೆ ಪಿನ್ ಆಗಿರುತ್ತದೆ: ಸಂಪರ್ಕ, ಖಾತೆಯ ಗುರುತು, ಮತ್ತು ನಿರ್ಣಯ-ರುಜುವಾತುಗಳ ಉತ್ಪಾದನೆ, ರುಜುವಾತು-ರಿಫ್ರೆಶ್ ಮರುಪ್ರಯತ್ನಗಳು ಸೇರಿದಂತೆ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರಯತ್ನಗಳ ಮೊದಲು ಮತ್ತೊಮ್ಮೆ ಪರಿಶೀಲಿಸಲಾಗಿದೆ. ಪ್ರತಿಕ್ರಿಯೆಗಳು ಕರೆ IDs/item ಉಲ್ಲೇಖಗಳು ಮತ್ತು Chat Completions ಟೂಲ್-ಕರೆ IDs ಆ ಸೆಷನ್ ಮತ್ತು ಜನರೇಷನ್ಗಾಗಿ ರೆಕಾರ್ಡ್ ಮಾಡಿರಬೇಕು.
- SQLite `key_value` ದಾಖಲೆಗಳು `muse_session_ownership` ನೇಮ್ಸ್ಪೇಸ್ನಲ್ಲಿ (`src/lib/db/museSessionOwnership.ts`) ಮಾಲೀಕತ್ವವನ್ನು ಮುಂದುವರೆಸುತ್ತವೆ ಮತ್ತು ಮರುಪ್ರಾರಂಭದಾದ್ಯಂತ ತಿರುಗುವಿಕೆ ಕರ್ಸರ್. ಪ್ರತಿ ಹಕ್ಕು ಮತ್ತು ಸೇವೆ ಸಲ್ಲಿಸಿದ ಪ್ರತಿಕ್ರಿಯೆಯು ಅಧಿವೇಶನದ ಚಟುವಟಿಕೆಯ ಮುದ್ರೆಯನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುತ್ತದೆ; `MUSE_SESSION_IDLE_TTL_MS` ಗಿಂತ ದೀರ್ಘಾವಧಿಯ ಐಡಲ್ ಅವಧಿಯನ್ನು ಕತ್ತರಿಸಲಾಗುತ್ತದೆ (ಮಾಲೀಕ ಪಿನ್, ಸರ್ವ್ ಮಾಡಿದ ಫ್ಲ್ಯಾಗ್ ಮತ್ತು ರೆಕಾರ್ಡ್ ಮಾಡಿದ opaque/reference ಹ್ಯಾಶ್ಗಳು), ಪ್ರತಿ 10 ನಿಮಿಷಗಳಿಗೊಮ್ಮೆ ಮತ್ತು ಬೌಂಡೆಡ್ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ, ಆದ್ದರಿಂದ ಅದರ ಇತಿಹಾಸದ ನಂತರದ ಮರುಪಂದ್ಯವು ಅಜ್ಞಾತ ಮಾಲೀಕರಂತೆ ಮುಚ್ಚಲ್ಪಡುತ್ತದೆ. ದಾಖಲೆಗಳು ಸಂಪರ್ಕ IDs ಮತ್ತು ಖಾತೆಯ ಗುರುತಿನ ಹ್ಯಾಶ್ಗಳು, ರುಜುವಾತುಗಳು, ಅಪಾರದರ್ಶಕ ವಿಷಯ ಮತ್ತು ಮುಂದುವರಿಕೆ ಉಲ್ಲೇಖಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತವೆ, ರಹಸ್ಯಗಳು ಅಥವಾ ಸಂಭಾಷಣೆ ಇತಿಹಾಸವಲ್ಲ. ಗ್ರಾಹಕರು ತಮ್ಮ ಸಂಪೂರ್ಣ ಇತಿಹಾಸ ಮತ್ತು ಅಪಾರದರ್ಶಕ ತಾರ್ಕಿಕತೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಬೇಕು ಮತ್ತು ಕಳುಹಿಸಬೇಕು.
- ಅಜ್ಞಾತ ಅಥವಾ ವಿದೇಶಿ ಅಪಾರದರ್ಶಕ ತಾರ್ಕಿಕತೆ, ಕಾಣೆಯಾದ ಮಾಲೀಕರು, ಅಲಭ್ಯ ಮಾಲೀಕರ ಖಾತೆ, ಅಥವಾ ರೆಕಾರ್ಡ್ ಮಾಡಿದ ಇತಿಹಾಸದೊಂದಿಗೆ ಪೀಳಿಗೆಯ ಬದಲಾವಣೆ ವಿಫಲವಾದರೆ ಸ್ಪಷ್ಟವಾದ 4xx/503 — ನೊಂದಿಗೆ ಮುಚ್ಚಲಾಗಿದೆ ಕ್ರಾಸ್ ಅಕೌಂಟ್ ವಿಫಲತೆ ಎಂದಿಗೂ ಮೌನವಾಗಿರುವುದಿಲ್ಲ ಮತ್ತು ತಾರ್ಕಿಕತೆಯನ್ನು ಎಂದಿಗೂ ಕೈಬಿಡುವುದಿಲ್ಲ.
- ಮರುಪಾವತಿಸಬಹುದಾದ ಇತಿಹಾಸವನ್ನು ಸೆಷನ್ ದಾಖಲಿಸದೇ ಇದ್ದಾಗ ಮಾತ್ರ ಮರುಮುದ್ರಿಸಿದ ಅದೇ ಖಾತೆಯ ಕೀಯನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ; ರೆಕಾರ್ಡ್ ಮಾಡಿದ ಸೆಷನ್ಗಳು ಹೊಸದಾಗಿ ಪ್ರಾರಂಭವಾಗುವವರೆಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತಲೇ ಇರುತ್ತವೆ.
- ಖಾಲಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆ (`upstream_empty_response` / `empty_response`, ಕರೆ ಮಾಡಿದವರಿಗೆ ಏನನ್ನೂ ಹೊರಸೂಸಲಾಗಿಲ್ಲ) ಒಂದೇ ಮಾಲೀಕರ ಮೇಲೆ ಎರಡು ಬಾರಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ, 0.5 ಸೆ ನಂತರ 1.5 ಸೆ (`MUSE_EMPTY_RESPONSE_RETRY_DELAYS_MS`). ಎಲ್ಲಾ ಪ್ರಯತ್ನಗಳು ಖಾಲಿಯಾಗಿದ್ದರೆ, ಮೂಲ 502 ಅನ್ನು ಕೂಲ್ಡೌನ್ ಅಥವಾ ಬ್ರೇಕರ್ ಗುರುತು ಇಲ್ಲದೆ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಫ್ಲಾಕಿ ಪ್ರತ್ಯುತ್ತರವು ಮಾಲೀಕರನ್ನು ಎಂದಿಗೂ ಲಾಕ್ ಮಾಡುವುದಿಲ್ಲ.
- ಎಲ್ಲಾ `muse-code` ವಿನಂತಿಗಳು ಸ್ಟ್ರೀಮಿಂಗ್ ಬರಹಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಶಬ್ದಾರ್ಥ-ಸಂಗ್ರಹ ಓದುವಿಕೆ ಮತ್ತು ಬರಹಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತವೆ, ಆದ್ದರಿಂದ ಕ್ಯಾಶ್ ಮಾಡಿದ ಅಪಾರದರ್ಶಕ ಔಟ್ಪುಟ್ ಬೇರೆ ಸೆಶನ್ ಮಾಲೀಕರನ್ನು ಪಡೆದುಕೊಳ್ಳುವುದಿಲ್ಲ.
