## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಶ್ರೇಣಿಗಳು

### ಶ್ರೇಣಿ 1 — LOCAL_ONLY

**ಜಾರಿಗೊಳಿಸುವುದು:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆ
**ಬೈಪಾಸ್:** ಡೀಫಾಲ್ಟ್ ಆಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ಸ್ಕೋಪ್ ಹೊಂದಿರುವ
ಮಾನ್ಯ API ಕೀಲಿಯನ್ನು ಹೊತ್ತಿದ್ದಾಗ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
ನಲ್ಲಿರುವ ಪಥಗಳಿಗೆ ಮಾತ್ರ ಕಿರಿದಾದ ಹೊರತು
([Manage-scope ಹೊರತು](#manage-scope-carve-out) ನೋಡಿ).

ಈ ರೂಟ್ಗಳು ಚೈಲ್ಡ್ ಪ್ರೊಸೆಸ್ಗಳನ್ನು ಸ್ಪಾನ್ ಮಾಡುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು
ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಅವುಗಳನ್ನು ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್ ಟ್ರಾಫಿಕ್ಗೆ ಒಡ್ಡುವುದರಿಂದ,
ಮಾನ್ಯ JWT ಪಡೆದ ದಾಳಿಕಾರಕನು (ಉದಾ., Cloudflared/Ngrok ಟನ್ನೆಲ್ ಮೂಲಕ) ಪ್ರೊಸೆಸ್
ಸ್ಪಾನ್ ಅನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ — ಇದು ಪರಿಚಿತ CVE ವರ್ಗ
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ದಾಳಿ ವರ್ಗ):** ನಿರ್ವಹಣಾ/ಏಜೆಂಟ್ ಸರ್ವರ್
ಸಬ್ಪ್ರೊಸೆಸ್ ಅನ್ನು ಪ್ರಾರಂಭಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ
(`npm install`, `node`, ಬ್ರೌಸರ್, ಪ್ರಾಕ್ಸಿ, `git`, `tar`, …). ಆ ಎಂಡ್ಪಾಯಿಂಟ್
ಅನ್ನು ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ತಲುಪಬಹುದಾದರೆ — ಆಪರೇಟರ್ OmniRoute ಅನ್ನು
nginx/Cloudflare/Tailscale ಟನ್ನೆಲ್ ಹಿಂದೆ ಇರಿಸಿದ್ದರಿಂದ ಹಾಗೂ JWT
ಸೋರಿಕೆಯಾಗಿದ್ದರೆ, ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾಗಿದ್ದರೆ —
ದಾಳಿಕಾರಕನು "API ಅನ್ನು ಕರೆಯುವುದು" ಅನ್ನು "ಹೋಸ್ಟ್ನಲ್ಲಿ ಆಜ್ಞೆಯನ್ನು
ಚಲಾಯಿಸುವುದಕ್ಕೆ" ಪರಿವರ್ತಿಸುತ್ತಾನೆ (ದೂರಸ್ಥ ಕೋಡ್ ಕಾರ್ಯನಿರ್ವಹಣೆ). OmniRoute ಪ್ರತಿ
ಸ್ಪಾನ್-ಸಮರ್ಥ ರೂಟ್ನ ಮೇಲೆ **ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗಿಂತ ಮೊದಲು, ನಿಷ್ಠೆಯಿಲ್ಲದಂತೆ
ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆಯನ್ನು** ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ ಈ ಅಂಚನ್ನು ಮುಚ್ಚುತ್ತದೆ:
ಟನ್ನೆಲ್ ಮೂಲಕ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಕೂಡ ಸ್ಪಾನ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಾಗುವುದಿಲ್ಲ.

**ಪೂರ್ಣ LOCAL_ONLY ಸೆಟ್.** ಅಧಿಕೃತ ಮೂಲವು
`src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು
ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ. `check-route-guard-membership` ಗೇಟ್
ಸ್ಪಾನ್-ಸಮರ್ಥ ಪ್ರಿಫಿಕ್ಸ್ಗಳ ಅಡಿಯಲ್ಲಿರುವ ಪ್ರತಿ `route.ts` ಅನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ
ಮತ್ತು ಯಾವುದಾದರೂ ಲೋಕಲ್-ಒನ್ಲಿ ಎಂದು ವರ್ಗೀಕರಿಸಲಾಗಿಲ್ಲದಿದ್ದರೆ CI ವಿಫಲವಾಗುತ್ತದೆ.

#### Manage-ಸ್ಕೋಪ್ ಕಾರ್ವ್-ಔಟ್

LOCAL_ONLY ಪಾತ್ಗಳ ಉಪಗುಂಪವನ್ನು non-loopback ನಿಂದಲೂ ಆಕ್ಸೆಸ್ ಮಾಡಬಹುದು, ವಿನಂತಿಯು `Authorization: Bearer <api-key>` ಅನ್ನು ಹೊಂದಿದ್ದರೆ ಮತ್ತು ಅದರ ಮೆಟಾಡೇಟಾವು `manage` ಸ್ಕೋಪ್ (ಅಥವಾ `admin`) ಅನ್ನು ಒಳಗೊಂಡಿದ್ದರೆ ಮಾತ್ರ. ಕಾರ್ವ್-ಔಟ್ ಅನ್ನು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಮೂಲಕ ಪ್ರತಿ-ಪಾತ್ ಸ್ಪಷ್ಟವಾಗಿ ಗೇಟ್ ಮಾಡಲಾಗಿದೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಹೊಸ LOCAL_ONLY ಪಾತ್ಗೆ ಡೀಫಾಲ್ಟ್ ಕಟ್ಟುನಿಟ್ಟಾದ-ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ದೃಢೀಕರಿಸದ ವಿನಂತಿಗಳು ಮತ್ತು manage-ಅಲ್ಲದ ಕೀಗಳೊಂದಿಗಿನ ವಿನಂತಿಗಳನ್ನು ಇನ್ನೂ `403 LOCAL_ONLY` ನೊಂದಿಗೆ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಇಂದು ಏಕೈಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪ್ರಿಫಿಕ್ಸ್ `/api/mcp/` ಆಗಿದೆ. `/api/cli-tools/runtime/` ಮತ್ತು `/api/services/` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ ಏಕೆಂದರೆ ಅವು ನಿರ್ದಿಷ್ಟವಲ್ಲದ (arbitrary) ಸಬ್ಪ್ರಾಸೆಸ್ಗಳನ್ನು (`npm install`, `node`) ಸ್ಪಾನ್ ಮಾಡಬಹುದು, ಇದು LOCAL_ONLY ಟೈರ್ ತಡೆಯಲು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ CVE ವರ್ಗವಾಗಿದೆ.

**#7895 — `mcp:connect` ಸಂಕುಚಿತ ಸ್ಕೋಪ್:** `/api/mcp/` ಕಾರ್ವ್-ಔಟ್ ಸಂಕುಚಿತ `mcp:connect` ಸ್ಕೋಪ್ ಹೊಂದಿರುವ Bearer ಕೀಯನ್ನು **ಸಹ** ಸ್ವೀಕರಿಸುತ್ತದೆ (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), ಅದನ್ನು `src/server/authz/policies/management.ts` ನಲ್ಲಿರುವ `hasMcpConnectOrManageScope()` ಮೂಲಕ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಇದು `/api/mcp/` ಗೆ **ಮಾತ್ರ** ಸ್ಕೋಪ್ ಮಾಡಲಾಗಿದೆ — `mcp:connect` ಬೇರೆ ಯಾವುದೇ ಮ್ಯಾನೇಜ್ಮೆಂಟ್ ರೂಟ್ನಲ್ಲಿ ಏನನ್ನೂ ನೀಡುವುದಿಲ್ಲ (ಬೇರೆ ಪ್ರತಿಯೊಂದು LOCAL_ONLY ಬೈಪಾಸ್ ಪ್ರಿಫಿಕ್ಸ್ ಸೇರಿದಂತೆ, ಒಂದನ್ನು ಎಂದಾದರೂ ಸೇರಿಸಿದರೂ), ಮತ್ತು ಅದನ್ನು `MANAGEMENT_API_KEY_SCOPES` ನಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ. `manage`/`admin` ಹೊಂದಿರುವ ಕೀ ಇನ್ನೂ ಹಿಂದಿನಂತೆಯೇ ಕಾರ್ವ್-ಔಟ್ ಅನ್ನು ಪಾಸ್ ಮಾಡುತ್ತದೆ; ವಿಸ್ತृत ಮ್ಯಾನೇಜ್ಮೆಂಟ್ ಆಕ್ಸೆಸ್ ಅಗತ್ಯವಿಲ್ಲದ ರಿಮೋಟ್ MCP-ಮಾತ್ರ ಕಾಲರ್ಗಳಿಗೆ `mcp:connect` ಕಡಿಮೆ-ಪ್ರಿವಿಲೇಜ್ ಪರ್ಯಾಯವಾಗಿದೆ.

#### ಆಪರೇಟರ್ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಆಡಿಟಿಂಗ್

ನೀವು OmniRoute ಅನ್ನು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಟನೆಲ್ (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok) ಹಿಂದೆ ರನ್ ಮಾಡುತ್ತಿದ್ದರೂ, ಲೂಪ್ಬ್ಯಾಕ್ ಚೆಕ್ ಮೇಲಿನ ಸ್ಪಾನ್-ಸಮರ್ಥ ರೂಟ್ಗಳನ್ನು ಇನ್ನೂ ರಕ್ಷಿಸುತ್ತದೆ — ಕ್ಲಯಂಟ್ ವಿಳಾಸವು non-loopback ಆಗಿರುವ ವಿನಂತಿಯನ್ನು `403 LOCAL_ONLY` ನೊಂದಿಗೆ **ಆಥ್ ರನ್ ಆಗುವ ಮೊದಲೇ** ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT ಸ್ಪಾನ್ ಅನ್ನು ತಲುಪಲಾಗುವುದಿಲ್ಲ. ಎರಡು ಆಪರೇಟರ್ ಜವಾಬ್ದಾರಿಗಳು ಉಳಿದಿವೆ:

- **ಕ್ಲೈಂಟ್ IP ಅನ್ನು loopback ಆಗಿ ನಕಲಿಮಾಡುವ ಮೂಲಕ 403 ಅನ್ನು "ಸರಿಪಡಿಸಬೇಡಿ".**
  `X-Forwarded-For: 127.0.0.1` ಅನ್ನು ಹೊಂದಿಸುವುದು, ಅಥವಾ ಮೂಲ ವಿಳಾಸವನ್ನು loopback ಗೆ
  ಮರುಬರೆಯುವ ಪ್ರಾಕ್ಸಿ, ಈ ಶ್ರೇಣಿ ಮುಚ್ಚುವ RCE ವರ್ಗವನ್ನು ನಿಖರವಾಗಿ ಮತ್ತೆ ತೆರೆಯುತ್ತದೆ.
  ಡ್ಯಾಶ್ಬೋರ್ಡ್/API ಅನ್ನು ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ಬಹಿರಂಗಪಡಿಸಿ — spawn-ಸಮರ್ಥ ರೂಟ್ಗಳನ್ನು ಎಂದಿಗೂ ಅಲ್ಲ.
- **manage-ಸ್ಕೋಪ್ ಬೈಪಾಸ್ ಅನ್ನು ಕನಿಷ್ಠವಾಗಿಟ್ಟುಕೊಳ್ಳಿ.** `/api/mcp/` ಮಾತ್ರ ಬೈಪಾಸ್ ಮಾಡಬಹುದು,
  ಮತ್ತು `manage`-ಸ್ಕೋಪ್ ಹೊಂದಿರುವ API ಕೀಲಿಯೊಂದಿಗೆ ಮಾತ್ರ. `SPAWN_CAPABLE_PREFIXES` ಅನ್ನು
  ಬೈಪಾಸ್ ಪಟ್ಟಿಗೆ ಎಂದಿಗೂ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ — zod ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು
  `isLocalOnlyBypassableByManageScope` ರನ್ಟೈಮ್ನಲ್ಲಿ ಅವುಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ
  (ಆಳಸ್ತರ ರಕ್ಷಣೆ, defence-in-depth), ಡ್ಯಾಶ್ಬೋರ್ಡ್ "cannot be made bypassable" ಎಂದು
  ಹೇಳುವುದರ ಅರ್ಥ ಇದನ್ನೇ. ಅದೇ deny-list ನಲ್ಲಿ spawn ಮಾಡದ ಆದರೆ ಅದರೂ ಎಂದಿಗೂ ರಿಮೋಟ್ಲಿ
  ತಲುಪಬಾರದಾದ ಕೆಲವು LOCAL_ONLY ರೂಟ್ಗಳೂ ಇವೆ — `/api/oauth/kiro/auto-import` (ಹೋಸ್ಟ್-ಲೋಕಲ್
  Kiro ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಫೈಲ್ಗಳನ್ನು ಓದುತ್ತದೆ), `/api/discovery/` ಮತ್ತು `/api/issue-agent/`.
  ರನ್ಟೈಮ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಲೋಡರ್ ಸಹ ಸಂಗ್ರಹಿಸಲಾದ settings ಸರಣಿಯಿಂದ ಅಂತಹ ಎಂಟ್ರಿಗಳನ್ನು
  ಕೈಬಿಡುತ್ತದೆ, ಮತ್ತು legacy JSON ಇಂಪೋರ್ಟ್ (`/api/settings/import-json`) ಬೈಪಾಸ್ ಕೀಲಿಗಳನ್ನು
  ಎಂದಿಗೂ ಬರೆಯುವುದಿಲ್ಲ. ಪ್ರತಿ `LOCAL_ONLY_API_PREFIXES` ಎಂಟ್ರಿ deny-list ನಲ್ಲಿರಬೇಕು ಅಥವಾ
  bypass-ಅರ್ಹವಾಗಿ ಪರಿಶೀಲಿಸಲ್ಪಡಬೇಕು
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/` ಅಡಿಯಲ್ಲಿನ
  ಡೈನಮಿಕ್-ಸೆಗ್ಮೆಂಟ್ ಮತ್ತು ಸ್ಟ್ಯಾಟಿಕ್-ಪಾತ್ spawn-ಸಮರ್ಥ ರೂಟ್ಗಳನ್ನು (ಉದಾ. `/login`,
  `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿನ regex-ಆಧಾರಿತ
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಕಂಪ್ಯಾನಿಯನ್ ಒಳಗೊಳ್ಳುತ್ತದೆ,
  ಫ್ಲ್ಯಾಟ್ `SPAWN_CAPABLE_PREFIXES` ಅರೇ ಅಲ್ಲ — ಫ್ಲ್ಯಾಟ್ ಅರೇ ಅವುಗಳನ್ನು ಹಿಡಿಯಲು ಇಡೀ
  `/api/providers/` ಪ್ರಿಫಿಕ್ಸ್ ಅನ್ನು ಒಳಗೊಂಡಿರಬೇಕಾಗುತ್ತದೆ, ಇದು ರಿಮೋಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು
  provider CRUD ಗಾಗಿ ಕಾನೂನುಬದ್ಧವಾಗಿ ಬಳಸುವ ರೂಟ್ ಟ್ರೀಯನ್ನು ಅತಿಯಾಗಿ ವಿಶಾಲಗೊಳಿಸುತ್ತದೆ.

  spawn-ಸಮರ್ಥ ("cannot be made bypassable") ಸೆಟ್ ಅನ್ನು ರೆಂಡರ್ ಮಾಡುತ್ತದೆ.
- ಮೇಲಿನ ಪ್ರಿಫಿಕ್ಸ್ಗಳನ್ನು non-loopback ಕ್ಲೈಂಟ್ ವಿಳಾಸದೊಂದಿಗೆ ಜೋಡಿಸಿ ನಿಮ್ಮ ರಿವರ್ಸ್-ಪ್ರಾಕ್ಸಿ /
  ಆಕ್ಸೆಸ್ ಲಾಗ್ಗಳಲ್ಲಿ grep ಮಾಡಿ. `403 LOCAL_ONLY` ಬದಲಿಗೆ `200` ಹಿಂತಿರುಗಿಸಿದ ಯಾವುದೇ ಅಂತಹ ಹಿಟ್
  ಎಂದರೆ ಪ್ರಾಕ್ಸಿ ನಿಜವಾದ ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಮರೆಮಾಚುತ್ತಿದೆ — ಪ್ರಾಕ್ಸಿಯನ್ನು ಸರಿಪಡಿಸಿ.
- ಈ ಪಾತ್ಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ OmniRoute ನ ಲಾಗ್ಗಳಲ್ಲಿ ಕಂಡ `403 LOCAL_ONLY` ಎಂಬುದು ಗಾರ್ಡ್
  ಉದ್ದೇಶಿಸಿದಂತೆ ಕೆಲಸ ಮಾಡುತ್ತಿದೆ ಎಂಬುದರ ಸೂಚನೆ, ಅದನ್ನು ಹತ್ತಿಕ್ಕಬೇಕಾದ ದೋಷವಲ್ಲ.

#### ಕಾಲ್-ಸೈಟ್ ಪ್ರೋಬ್ ಗೇಟ್ ಹೊಂದಿರುವ ರಿಮೋಟ್-ತಲುಪಬಹುದಾದ ರೂಟ್ಗಳು

ಕೆಲವು ರೂಟ್ಗಳು ರಿಮೋಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ತಲುಪಬಹುದಾಗಿದ್ದರೂ, ಲೋಕಲ್ ಕಾಲರ್ಗಳಿಗಾಗಿ ಹೋಸ್ಟ್-ಸೈಡ್
ಪ್ರೋಬ್ (`which <binary>`, `<binary> --version`, `tailscale status --json`) ಅನ್ನು ಚಲಾಯಿಸುತ್ತವೆ.
ಅವು `GET` ಗೆ LOCAL_ONLY ಅಲ್ಲ; ಬದಲಾಗಿ ಹ್ಯಾಂಡಲರ್ `getRequestPeerLocality()`
(`src/shared/utils/apiAuth.ts`) ಮೂಲಕ ವಿಶ್ವಾಸಾರ್ಹ ಪೀರ್ ತೀರ್ಪನ್ನು ಓದುತ್ತದೆ ಮತ್ತು `loopback` /
`lan` ಕಾಲರ್ಗಳಿಗೆ ಮಾತ್ರ ಪ್ರೋಬ್ ಚಲಾಯಿಸುತ್ತದೆ. `remote` ಕಾಲರ್ಗೆ spawn ಮಾಡದ ಮೂಲಗಳಿಂದ
(ಸಂಗ್ರಹಿತ ಸ್ಥಿತಿ, ಸೆಟ್ಟಿಂಗ್ಗಳು, fs ಪರಿಶೀಲನೆಗಳು) ನಿರ್ಮಿಸಲಾದ ಅದೇ ಪ್ರತಿಕ್ರಿಯೆ ಆಕಾರ ಸಿಗುತ್ತದೆ,
ಅದನ್ನು `probed: false` ಎಂದು ಫ್ಲ್ಯಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ.

GHSA-62vw ಕೇವಲ `GET` ಪಾಸ್ವರ್ಡ್ ಬಹಿರಂಗವನ್ನು ಮರೆಮಾಚಿತು; ನೀಡಿಕೆಯು ಇನ್ನೂ fail-open ಶ್ರೇಣಿಯಲ್ಲಿತ್ತು (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` ಹೆಚ್ಚುವರಿಯಾಗಿ ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯೇ ಆಗಿರುವ, ಅದರೊಳಗಿರುವ, ಅಥವಾ ಅದನ್ನು ಒಳಗೊಂಡಿರುವ ವಾಲ್ಟ್ ಅನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ.

#### ರುಜುವಾತು ರಫ್ತುಗಳು ಮತ್ತು ಮರುಸ್ಥಾಪನೆಗಳು ಆಪರೇಟರ್-ಮಾತ್ರ

ಮೇಲಿನ ಶ್ರೇಣಿಯು _ಕೆಲವು_ ರುಜುವಾತು ಅಗತ್ಯವಿದೆಯೇ ಎಂಬುದನ್ನು ಮಾತ್ರ ನಿರ್ಧರಿಸುತ್ತದೆ. ಸಂಗ್ರಹಿಸಿದ ರುಜುವಾತುಗಳನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುವ ರೂಟ್ಗಳು ಹ್ಯಾಂಡಲರ್ನಲ್ಲಿ ಎರಡನೇ ಪರಿಶೀಲನೆಯನ್ನು ಸೇರಿಸುತ್ತವೆ: `GET /api/settings/export-json` (ಡಿಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ಪ್ರೊವೈಡರ್ ಸಂಪರ್ಕಗಳು ಮತ್ತು ಕಚ್ಚಾ API ಕೀಗಳು), `GET /api/db-backups/export` (SQLite ಫೈಲ್) ಮತ್ತು `GET /api/db-backups/exportAll` (ಪೂರ್ಣ ಆರ್ಕೈವ್) `requireOperatorCredential()` ಅನ್ನು ಕರೆಯುತ್ತವೆ (`src/lib/api/operatorCredential.ts`). ಇದು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್, ಸ್ಥಳೀಯ CLI ಸಬ್ಜೆಕ್ಟ್, ಅಥವಾ ಲಾಗಿನ್ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿದ ಇನ್ಸ್ಟನ್ಸ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ, ಮತ್ತು ಯಾವುದೇ ಸ್ಕೋಪ್ನ API ಕೀಗಳಿಗೆ (`manage` ಮತ್ತು `admin` ಸೇರಿದಂತೆ) ಮತ್ತು `oma_` ಆಕ್ಸೆಸ್ ಟೋಕನ್ಗಳಿಗೆ `403` ಎಂದು ಉತ್ತರಿಸುತ್ತದೆ. ವಿನಾಶಕಾರಿ ಪ್ರತಿರೂಪಗಳು ಅದೇ ಗಡಿಯನ್ನು ಕಾಯ್ದುಕೊಳ್ಳುತ್ತವೆ: `POST /api/db-backups/import` (ಅಪ್ಲೋಡ್ ಮಾಡಿದ `.sqlite`, `dryRun=true` ಸೇರಿದಂತೆ), `POST /api/db-backups` (ಸಂಗ್ರಹಿಸಿದ ಬ್ಯಾಕಪ್ ಅನ್ನು id ಮೂಲಕ ಮರುಸ್ಥಾಪಿಸಿ) ಮತ್ತು `POST /api/settings/import-json` (ಲೆಗಸಿ JSON ಮರುಸ್ಥಾಪನೆ) ಲೈವ್ ಡೇಟಾಬೇಸ್ ಅಥವಾ ಸಂಪೂರ್ಣ ಸೆಟ್ಟಿಂಗ್ಗಳು/ಸಂಪರ್ಕಗಳು/API-ಕೀ ಸೆಟ್ ಅನ್ನು ಬದಲಾಯಿಸುತ್ತವೆ, ಆದ್ದರಿಂದ ಮಷಿನ್ ರುಜುವಾತುವು ಸಹ ಅವುಗಳನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮರುಸ್ಥಾಪನಾ ಬಿಂದುಗಳನ್ನು ನಾಶಮಾಡುವುದು ಅದೇ ಗಡಿಯನ್ನು ಕಾಯ್ದುಕೊಳ್ಳುತ್ತದೆ: `DELETE /api/db-backups` (ಕ್ಲೀನಪ್ — ಇತ್ತೀಚಿನ N ಅನ್ನು ಇರಿಸಿ / D ದಿನಗಳಿಗಿಂತ ಹಳೆಯದನ್ನು ಬಿಡಿ) ಮತ್ತು `PATCH /api/db-backups` (ರಿಟೆನ್ಷನ್ ಸೆಟ್ಟಿಂಗ್ಗಳು), ಏಕೆಂದರೆ ಮುಂದುವರೆಸಿದ ರಿಟೆನ್ಷನ್ ಎಂಬುದು ಪ್ರತಿ ಸ್ವಯಂಚಾಲಿತ ಬ್ಯಾಕಪ್ನ ನಂತರ `cleanupDbBackups()` ಅನ್ವಯಿಸುವುದೇ ಆಗಿದೆ (`src/lib/db/backup.ts`), ಆದ್ದರಿಂದ `keepLatest: 1` ಅನ್ನು ಉಳಿಸಬಹುದಾದ ಮಷಿನ್ ರುಜುವಾತು ಮುಂದಿನ ಸ್ನ್ಯಾಪ್ಶಾಟ್ನಲ್ಲಿ ಎಲ್ಲವನ್ನೂ ಕತ್ತರಿಸುತ್ತದೆ. ಬ್ಯಾಕಪ್ಗಳನ್ನು ಪಟ್ಟಿಮಾಡುವುದು ಮತ್ತು ರಚಿಸುವುದು (`GET`/`PUT /api/db-backups`) ಸಾಮಾನ್ಯ ನಿರ್ವಹಣಾ ದೃಢೀಕರಣವನ್ನು ಇರಿಸುತ್ತದೆ. ಸಿಂಕ್ ಟೋಕನ್ ನೀಡಿಕೆ (`POST /api/sync/tokens`) ಅದೇ ಹೆಲ್ಪರ್ ಅನ್ನು ಬಳಸುತ್ತದೆ, ಜೊತೆಗೆ ವಿಶ್ವಾಸಾರ್ಹ ಲೂಪ್ಬ್ಯಾಕ್ ಆಂತರಿಕ-ಸೇವಾ ಟೋಕನ್.

### ಫ್ರೆಶ್-ಇನ್ಸ್ಟಾಲ್ ಬೂಟ್ಸ್ಟ್ರಾಪ್ ಲೂಪ್ಬ್ಯಾಕ್-ಮಾತ್ರ — ನಿಜವಾದ ಪೀಯರ್ ಮೂಲಕ, `Host` ಅಲ್ಲ

ಯಾವುದೇ ನಿರ್ವಹಣಾ ಪಾಸ್ವರ್ಡ್ ಕಾನ್ಫಿಗರ್ ಮಾಡಿಲ್ಲದಿದ್ದಾಗ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲದಿದ್ದಾಗ), `src/shared/utils/apiAuth.ts` ನಲ್ಲಿರುವ `isAuthRequired()` ಅನಾಮಧೇಯ ಬೂಟ್ಸ್ಟ್ರಾಪ್ ಅನ್ನು **ಕೇವಲ ಲೂಪ್ಬ್ಯಾಕ್ ಪೀಯರ್ಗಳಿಗೆ** ತೆರೆದಿಡುತ್ತದೆ. ಲೂಪ್ಬ್ಯಾಕ್ ಅನ್ನು ವಿಶ್ವಾಸಾರ್ಹ ಪೀಯರ್ ಸಂಕೇತಗಳಿಂದ ಕ್ರಮವಾಗಿ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ: ಟೋಕನ್-ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ನಿಜವಾದ TCP ಪೀಯರ್ (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ಪಾಲಿಸಿ ನೋಡುವುದು), ಪೈಪ್ಲೈನ್ನ ಸ್ವಂತ `AUTHZ_HEADER_PEER_LOCALITY` ತೀರ್ಪು (ರೂಟ್ ಹ್ಯಾಂಡಲರ್ಗಳು ನೋಡುವುದು, `OMNIROUTE_PEER_STAMP_TOKEN` ಸೆಟ್ ಆಗಿರುವಾಗ ಮಾತ್ರ ವಿಶ್ವಾಸಾರ್ಹ), ಅಥವಾ ನೇರ ಕರೆಕರ್ತರಿಗೆ ನಿಜವಾದ ಸಾಕెಟ್ ಪೀಯರ್. `Host` / `nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಪರಾಮರ್ಶಿಸಲಾಗುವುದಿಲ್ಲ, ಮತ್ತು ಮೊದಲ-ಪಾಸ್ವರ್ಡ್ ಬರಹ (`POST /api/settings/require-login`) ಪ್ರತಿ ನೆಟ್ವರ್ಕ್ ಪೀಯರ್ಗೆ ತೆರೆದಿರುವುದರ ಬದಲು ಅದೇ ನಿರ್ಬಂಧದಲ್ಲಿದೆ (GHSA-7pq4-8pvv-rx7r). `managementPolicy` ತನ್ನ ಸ್ವಂತ `peerContext` ತೀರ್ಪನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಕೆಳಗೆ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಮೂಲ (ಸ್ಟ್ರಿಪ್-ಪೂರ್ವ) ವಿನಂತಿಯ ಹೆಡರ್ಗಳು ಅದನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಶ್ರೇಣಿ 3 — MANAGEMENT (ಡೀಫಾಲ್ಟ್)

ಉಳಿದ ಎಲ್ಲಾ ನಿರ್ವಹಣಾ ರೂಟ್ಗಳು. `requireLogin=false` ಕಾನ್ಫಿಗರ್ ಮಾಡಿಲ್ಲದಿದ್ದರೆ ದೃಢೀಕರಣ ಅಗತ್ಯ. CLI ಟೋಕನ್ಗಳು ಈ ರೂಟ್ಗಳನ್ನು ದೃಢೀಕರಿಸಬಹುದು (ಲೂಪ್ಬ್ಯಾಕ್ + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

### ಮೌಲ್ಯೀಕರಣ

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
