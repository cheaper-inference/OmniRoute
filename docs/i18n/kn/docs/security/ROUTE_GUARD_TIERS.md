## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಹಂತಗಳು

### ಹಂತ 1 — LOCAL_ONLY

**ಜಾರಿಗೊಳಿಸುವುದು:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆ  
**ಬೈಪಾಸ್:** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ವ್ಯಾಪ್ತಿಯ ಮಾನ್ಯ API ಕೀಲಿಯನ್ನು ಹೊಂದಿರುವಾಗ, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿರುವ ಪಥಗಳಿಗೆ ಸೀಮಿತ ವಿನಾಯಿತಿ ಅನ್ವಯಿಸುತ್ತದೆ ([ನಿರ್ವಹಣಾ-ವ್ಯಾಪ್ತಿಯ ವಿನಾಯಿತಿ](#manage-scope-carve-out) ನೋಡಿ).

ಈ ಮಾರ್ಗಗಳು ಚೈಲ್ಡ್ ಪ್ರೊಸೆಸ್ಗಳನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಅವುಗಳನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ಗೆ ಬಹಿರಂಗಪಡಿಸುವುದರಿಂದ, ಮಾನ್ಯ JWT ಪಡೆದ ದಾಳಿಕೋರನಿಗೆ (ಉದಾ., Cloudflared/Ngrok ಟನಲ್ ಮೂಲಕ) ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸುವಿಕೆಯನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ — ಇದು ತಿಳಿದಿರುವ CVE ವರ್ಗವಾಗಿದೆ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ದಾಳಿಯ ವರ್ಗ):** ನಿರ್ವಹಣಾ/ಏಜೆಂಟ್ ಸರ್ವರ್ ಒಂದು ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು (`npm install`, `node`, ಬ್ರೌಸರ್, ಪ್ರಾಕ್ಸಿ, `git`, `tar`, …) ಪ್ರಾರಂಭಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. ಆ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ತಲುಪಬಹುದಾದರೆ — ಆಪರೇಟರ್ OmniRoute ಅನ್ನು nginx/Cloudflare/Tailscale ಟನಲ್ನ ಹಿಂದೆ ಇರಿಸಿ JWT ಸೋರಿಕೆಯಾಗಿರುವುದರಿಂದ, ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಿರುವುದರಿಂದ — ದಾಳಿಕೋರನು "API ಅನ್ನು ಕರೆಮಾಡುವುದನ್ನು" "ಹೋಸ್ಟ್ನಲ್ಲಿ ಕಮಾಂಡ್ ಚಲಾಯಿಸುವುದಾಗಿ" (ರಿಮೋಟ್ ಕೋಡ್ ಎಕ್ಸಿಕ್ಯೂಷನ್) ಪರಿವರ್ತಿಸುತ್ತಾನೆ. ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪ್ರತಿಯೊಂದು ಮಾರ್ಗದಲ್ಲೂ **ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗೂ ಮೊದಲು, ಬೇಷರತ್ತಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆಯನ್ನು** ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ OmniRoute ಇದನ್ನು ತಡೆಯುತ್ತದೆ: ಟನಲ್ ಮೂಲಕ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಇದ್ದರೂ ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸುವಿಕೆಯನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಸಂಪೂರ್ಣ LOCAL_ONLY ಸಮೂಹ.** ಅಧಿಕೃತ ಮೂಲವು `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ಆಗಿದೆ; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ. `check-route-guard-membership` ಗೇಟ್ ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪ್ರಿಫಿಕ್ಸ್ಗಳ ಅಡಿಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು `route.ts` ಅನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಅವುಗಳಲ್ಲಿ ಯಾವುದಾದರೂ ಲೋಕಲ್-ಓನ್ಲಿ ಎಂದು ವರ್ಗೀಕರಿಸದಿದ್ದರೆ CI ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

#### ನಿರ್ವಹಣಾ-ಸ್ಕೋಪ್ ವಿನಾಯಿತಿ

ವಿನಂತಿಯು `Authorization: Bearer <api-key>` ಅನ್ನು ಹೊಂದಿದ್ದು, ಅದರ
ಮೆಟಾಡೇಟಾದಲ್ಲಿ `manage` ಸ್ಕೋಪ್ (ಅಥವಾ `admin`) ಸೇರಿದ್ದರೆ ಮತ್ತು ಆಗ ಮಾತ್ರ,
LOCAL_ONLY ಪಥಗಳ ಉಪಸಮೂಹವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ವಿಳಾಸದಿಂದಲೂ ಪ್ರವೇಶಿಸಬಹುದು.
ಯಾವುದೇ ಹೊಸ LOCAL_ONLY ಪಥದ ಡೀಫಾಲ್ಟ್ ಕಟ್ಟುನಿಟ್ಟಾದ-ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುವಂತೆ,
ಈ ವಿನಾಯಿತಿಯನ್ನು ಪ್ರತಿ ಪಥಕ್ಕೆ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಮೂಲಕ
ಸ್ಪಷ್ಟವಾಗಿ ನಿಯಂತ್ರಿಸಲಾಗುತ್ತದೆ. ದೃಢೀಕರಣವಿಲ್ಲದ ವಿನಂತಿಗಳು ಮತ್ತು `manage` ಅಲ್ಲದ
ಕೀಲಿಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗಳನ್ನು ಈಗಲೂ `403 LOCAL_ONLY` ಮೂಲಕ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ವಿನಾಯಿತಿ ನೀಡಬಹುದಾದ ಏಕೈಕ ಪ್ರಿಫಿಕ್ಸ್ `/api/mcp/` ಆಗಿದೆ. `/api/cli-tools/runtime/` ಮತ್ತು
`/api/services/` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ, ಏಕೆಂದರೆ ಅವು ಅನಿಯಂತ್ರಿತ
ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು (`npm install`, `node`) ಪ್ರಾರಂಭಿಸಬಲ್ಲವು; LOCAL_ONLY ಹಂತವು
ತಡೆಯಲು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ CVE ವರ್ಗವೇ ಇದು.

#### ಆಪರೇಟರ್ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಲೆಕ್ಕಪರಿಶೋಧನೆ

ನೀವು OmniRoute ಅನ್ನು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಟನಲ್ನ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ಹಿಂದೆ ಚಲಾಯಿಸಿದರೆ, ಮೇಲಿನ ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭಿಸಬಲ್ಲ
ರೂಟ್ಗಳನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಪರಿಶೀಲನೆಯು ಇನ್ನೂ ರಕ್ಷಿಸುತ್ತದೆ — ಕ್ಲೈಂಟ್ ವಿಳಾಸವು
ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ವಿನಂತಿಯನ್ನು **ದೃಢೀಕರಣ ನಡೆಯುವ ಮೊದಲೇ** `403 LOCAL_ONLY` ಮೂಲಕ
ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT ಕೂಡ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವ ಹಂತವನ್ನು
ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಆಪರೇಟರ್ಗೆ ಎರಡು ಜವಾಬ್ದಾರಿಗಳು ಉಳಿಯುತ್ತವೆ:

- **ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ನಂತೆ ನಕಲಿ ಮಾಡಿ 403 ಅನ್ನು "ಸರಿಪಡಿಸಬೇಡಿ".** `X-Forwarded-For: 127.0.0.1` ಅನ್ನು ಹೊಂದಿಸುವುದು ಅಥವಾ ಮೂಲ ವಿಳಾಸವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮರುಬರೆಯುವ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಳಸುವುದು, ಈ ಹಂತವು ಮುಚ್ಚುವ ಅದೇ RCE ವರ್ಗವನ್ನು ಮತ್ತೆ ತೆರೆಯುತ್ತದೆ. ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ಡ್ಯಾಶ್ಬೋರ್ಡ್/API ಅನ್ನು ಬಹಿರಂಗಪಡಿಸಿ — ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಹುಟ್ಟುಹಾಕಬಲ್ಲ ಮಾರ್ಗಗಳನ್ನು ಎಂದಿಗೂ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.
- **manage-ವ್ಯಾಪ್ತಿಯ ಬೈಪಾಸ್ ಅನ್ನು ಕನಿಷ್ಠ ಮಟ್ಟದಲ್ಲಿರಿಸಿ.** ಕೇವಲ `/api/mcp/` ಅನ್ನು ಮಾತ್ರ ಬೈಪಾಸ್ ಮಾಡಬಹುದು, ಅದೂ `manage`-ವ್ಯಾಪ್ತಿಯ API ಕೀಲಿಯೊಂದಿಗೆ ಮಾತ್ರ. `SPAWN_CAPABLE_PREFIXES` ಅನ್ನು ಬೈಪಾಸ್ ಪಟ್ಟಿಗೆ ಎಂದಿಗೂ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ — zod ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು `isLocalOnlyBypassableByManageScope` ರನ್ಟೈಮ್ನಲ್ಲಿ ಅವುಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ (ಬಹುಪದರ ರಕ್ಷಣೆ); ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿರುವ "ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ" ಎಂಬುದರ ಅರ್ಥ ಇದೇ. ಅದೇ ನಿರಾಕರಣೆ ಪಟ್ಟಿಯಲ್ಲಿ ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಹುಟ್ಟುಹಾಕದಿದ್ದರೂ ಎಂದಿಗೂ ದೂರದಿಂದ ತಲುಪಲು ಸಾಧ್ಯವಾಗಬಾರದ ಕೆಲವು LOCAL_ONLY ಮಾರ್ಗಗಳೂ ಇವೆ — `/api/oauth/kiro/auto-import` (ಹೋಸ್ಟ್ನ ಸ್ಥಳೀಯ Kiro ರುಜುವಾತು ಫೈಲ್ಗಳನ್ನು ಓದುತ್ತದೆ), `/api/discovery/` ಮತ್ತು `/api/issue-agent/`. ರನ್ಟೈಮ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಲೋಡರ್ ಕೂಡ ಸಂಗ್ರಹಿಸಿದ ಸೆಟ್ಟಿಂಗ್ಗಳ ಸಾಲಿನಿಂದ ಅಂತಹ ನಮೂದುಗಳನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ ಮತ್ತು ಹಳೆಯ JSON ಆಮದು (`/api/settings/import-json`) ಎಂದಿಗೂ ಬೈಪಾಸ್ ಕೀಲಿಗಳನ್ನು ಬರೆಯುವುದಿಲ್ಲ. ಪ್ರತಿಯೊಂದು `LOCAL_ONLY_API_PREFIXES` ನಮೂದು ನಿರಾಕರಣೆ ಪಟ್ಟಿಯಲ್ಲಿರಬೇಕು ಅಥವಾ ಬೈಪಾಸ್ಗೆ ಅರ್ಹವೇ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿರಬೇಕು (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/` ಅಡಿಯಲ್ಲಿ ಡೈನಾಮಿಕ್-ಸೆಗ್ಮೆಂಟ್ ಮತ್ತು ಸ್ಥಿರ-ಪಥದ ಪ್ರಕ್ರಿಯೆ-ಹುಟ್ಟುಹಾಕಬಲ್ಲ ಮಾರ್ಗಗಳು (ಉದಾ. `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿರುವ regex-ಆಧಾರಿತ `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಸಹಚರದಿಂದ ಆವರಿಸಲ್ಪಟ್ಟಿವೆ, ಸಮತಟ್ಟಾದ `SPAWN_CAPABLE_PREFIXES` ಅರೆಯಿಂದಲ್ಲ — ಅವುಗಳನ್ನು ಪತ್ತೆಹಚ್ಚಲು ಸಮತಟ್ಟಾದ ಅರೆಯು ಸಂಪೂರ್ಣ `/api/providers/` ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಆವರಿಸಬೇಕಾಗುತ್ತದೆ; ಇದರಿಂದ ರಿಮೋಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು ಪ್ರೊವೈಡರ್ CRUD ಗಾಗಿ ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಬಳಸುವ ಮಾರ್ಗ ವೃಕ್ಷವು ಅಗತ್ಯಕ್ಕಿಂತ ಹೆಚ್ಚು ವಿಸ್ತೃತವಾಗಿ ನಿರ್ಬಂಧಿಸಲ್ಪಡುತ್ತದೆ.

**ಪ್ರವೇಶದ ಆಡಿಟ್** — ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ಯಾವುದೂ ಈ ಮಾರ್ಗಗಳನ್ನು ತಲುಪುತ್ತಿಲ್ಲವೆಂದು ಪರಿಶೀಲಿಸಲು:

- `/dashboard/settings/security` ನಲ್ಲಿ **ಅಧಿಕಾರ ನೀಡಿಕೆ ಇನ್ವೆಂಟರಿ** ತೆರೆಯಿರಿ: ಇದು ಲೈವ್ LOCAL_ONLY ಪೂರ್ವಪ್ರತ್ಯಯಗಳ ಪಟ್ಟಿ, ಯಾವ ಪೂರ್ವಪ್ರತ್ಯಯಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡಬಹುದು ಮತ್ತು ಕಂಪೈಲ್-ಸಮಯದ ಪ್ರಕ್ರಿಯೆ-ಹುಟ್ಟುಹಾಕಬಲ್ಲ ("ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ") ಸಮೂಹವನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ.
- ಮೇಲಿನ ಪೂರ್ವಪ್ರತ್ಯಯಗಳು ಮತ್ತು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಕ್ಲೈಂಟ್ ವಿಳಾಸದ ಜೋಡಿಗಾಗಿ ನಿಮ್ಮ ರಿವರ್ಸ್-ಪ್ರಾಕ್ಸಿ / ಪ್ರವೇಶ ಲಾಗ್ಗಳಲ್ಲಿ grep ಮಾಡಿ. `403 LOCAL_ONLY` ಬದಲಿಗೆ `200` ಅನ್ನು ಹಿಂದಿರುಗಿಸಿದ ಅಂತಹ ಯಾವುದೇ ಹಿಟ್, ಪ್ರಾಕ್ಸಿಯು ನಿಜವಾದ ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಮರೆಮಾಚುತ್ತಿದೆ ಎಂದರ್ಥ — ಪ್ರಾಕ್ಸಿಯನ್ನು ಸರಿಪಡಿಸಿ.
- ಈ ಪಥಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ OmniRoute ಲಾಗ್ಗಳಲ್ಲಿ ಕಾಣುವ `403 LOCAL_ONLY`, ರಕ್ಷಣಾ ವ್ಯವಸ್ಥೆಯು ಉದ್ದೇಶಿಸಿದಂತೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆ ಎಂಬುದನ್ನು ಸೂಚಿಸುತ್ತದೆ; ಅದು ಮರೆಮಾಡಬೇಕಾದ ದೋಷವಲ್ಲ.

#### ಕರೆ-ಸ್ಥಳದ ಪ್ರೋಬ್ ಗೇಟ್ ಹೊಂದಿರುವ ರಿಮೋಟ್ನಿಂದ ತಲುಪಬಹುದಾದ ಮಾರ್ಗಗಳು

ಕೆಲವು ಮಾರ್ಗಗಳು ರಿಮೋಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ತಲುಪಲು ಸಾಧ್ಯವಾಗಿಯೇ ಇರಬೇಕು, ಆದರೆ ಸ್ಥಳೀಯ ಕರೆಗಾರರಿಗಾಗಿ ಹೋಸ್ಟ್-ಬದಿಯ ಪ್ರೋಬ್ ಅನ್ನು (`which <binary>`, `<binary> --version`, `tailscale status --json`) ಚಲಾಯಿಸುತ್ತವೆ. `GET` ಗಾಗಿ ಅವು LOCAL_ONLY ಅಲ್ಲ; ಬದಲಿಗೆ ಹ್ಯಾಂಡ್ಲರ್ `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) ಮೂಲಕ ವಿಶ್ವಾಸಾರ್ಹ ಪಿಯರ್ ನಿರ್ಣಯವನ್ನು ಓದುತ್ತದೆ ಮತ್ತು `loopback` / `lan` ಕರೆಗಾರರಿಗೆ ಮಾತ್ರ ಪ್ರೋಬ್ ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. `remote` ಕರೆಗಾರನಿಗೆ ಪ್ರಕ್ರಿಯೆ ಹುಟ್ಟುಹಾಕದ ಮೂಲಗಳಿಂದ (ಸಂಗ್ರಹಿತ ಸ್ಥಿತಿ, ಸೆಟ್ಟಿಂಗ್ಗಳು, fs ಪರಿಶೀಲನೆಗಳು) ನಿರ್ಮಿಸಲಾದ ಅದೇ ಪ್ರತಿಕ್ರಿಯೆ ಆಕಾರವು `probed: false` ಎಂದು ಗುರುತಿಸಲ್ಪಟ್ಟು ದೊರೆಯುತ್ತದೆ.

### ಹಂತ 2 — ALWAYS_PROTECTED

**ಜಾರಿಗೊಳಿಸುವುದು:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ಬೈಪಾಸ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡಿ  
**ಬೈಪಾಸ್:** `requireLogin=false` ಆಗಿರುವಾಗ ಯಾವುದೂ ಇಲ್ಲ; JWT ಯಾವಾಗಲೂ ಅಗತ್ಯ

ಈ ಮಾರ್ಗಗಳು ವಿನಾಶಕಾರಿ ಅಥವಾ ಬದಲಾಯಿಸಲಾಗದವು. "ಪಾಸ್ವರ್ಡ್-ಇಲ್ಲದ" ಸ್ಥಾಪನೆಯಲ್ಲಿ ಅವುಗಳನ್ನು ಅನುಮತಿಸಿದರೆ, ಅದೇ LAN ನಲ್ಲಿರುವ ಯಾರಾದರೂ ಡೇಟಾಬೇಸ್ ಅನ್ನು ಅಳಿಸಬಹುದು ಅಥವಾ ಸರ್ವರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ನಿಲ್ಲಿಸಬಹುದು.

#### ರುಜುವಾತುಗಳ ರಫ್ತುಗಳು ಆಪರೇಟರ್ಗಳಿಗೆ ಮಾತ್ರ

ಮೇಲಿನ ಹಂತವು _ಯಾವುದಾದರೂ_ ರುಜುವಾತು ಅಗತ್ಯವಿದೆಯೇ ಎಂಬುದನ್ನು ಮಾತ್ರ ನಿರ್ಧರಿಸುತ್ತದೆ. ಸಂಗ್ರಹಿಸಿದ
ರುಜುವಾತುಗಳನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುವ ಮಾರ್ಗಗಳು ಹ್ಯಾಂಡ್ಲರ್ನಲ್ಲಿ ಎರಡನೇ ಪರಿಶೀಲನೆಯನ್ನು ಸೇರಿಸುತ್ತವೆ: `GET /api/settings/export-json` (ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿದ
ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳು ಮತ್ತು ಕಚ್ಚಾ API ಕೀಗಳು), `GET /api/db-backups/export` (SQLite ಫೈಲ್) ಮತ್ತು
`GET /api/db-backups/exportAll` (ಸಂಪೂರ್ಣ ಆರ್ಕೈವ್) ಇವು `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`) ಅನ್ನು ಕರೆ ಮಾಡುತ್ತವೆ. ಇದು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್, ಸ್ಥಳೀಯ CLI ಸಬ್ಜೆಕ್ಟ್ ಅಥವಾ
ಲಾಗಿನ್ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿರುವ ಇನ್ಸ್ಟೆನ್ಸ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ ಸ್ಕೋಪ್ನ API ಕೀಗಳಿಗೆ (`manage`
ಮತ್ತು `admin` ಸೇರಿದಂತೆ) ಹಾಗೂ `oma_` ಪ್ರವೇಶ ಟೋಕನ್ಗಳಿಗೆ `403` ಎಂದು ಪ್ರತಿಕ್ರಿಯಿಸುತ್ತದೆ. ಸಿಂಕ್ ಟೋಕನ್ ನೀಡುವಿಕೆ (`POST /api/sync/tokens`) ಇದೇ
ಸಹಾಯಕವನ್ನು, ಜೊತೆಗೆ ವಿಶ್ವಾಸಾರ್ಹ ಲೂಪ್ಬ್ಯಾಕ್ ಆಂತರಿಕ-ಸೇವಾ ಟೋಕನ್ ಅನ್ನು ಬಳಸುತ್ತದೆ.

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### ಹೊಸ-ಸ್ಥಾಪನೆಯ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮಾತ್ರ ಸೀಮಿತ — `Host` ನಿಂದಲ್ಲ, ನಿಜವಾದ ಪೀರ್ನಿಂದ

ಯಾವುದೇ ನಿರ್ವಹಣಾ ಪಾಸ್ವರ್ಡ್ ಕಾನ್ಫಿಗರ್ ಮಾಡದಿದ್ದಾಗ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲದಿದ್ದಾಗ),
`src/shared/utils/apiAuth.ts` ನಲ್ಲಿರುವ `isAuthRequired()` ಅನಾಮಧೇಯ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಅನ್ನು **ಲೂಪ್ಬ್ಯಾಕ್ ಪೀರ್ಗಳಿಗೆ ಮಾತ್ರ** ತೆರೆದಿಡುತ್ತದೆ.
ವಿಶ್ವಾಸಾರ್ಹ ಪೀರ್ ಸಂಕೇತಗಳಿಂದ, ಈ ಕ್ರಮದಲ್ಲಿ, ಲೂಪ್ಬ್ಯಾಕ್ ಅನ್ನು ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ: ಟೋಕನ್-ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ನಿಜವಾದ TCP ಪೀರ್
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ನೀತಿಯು ನೋಡುವುದು), ಪೈಪ್ಲೈನ್ನ ಸ್ವಂತ
`AUTHZ_HEADER_PEER_LOCALITY` ತೀರ್ಪು (ಮಾರ್ಗ ಹ್ಯಾಂಡ್ಲರ್ಗಳು ನೋಡುವುದು, `OMNIROUTE_PEER_STAMP_TOKEN`
ಹೊಂದಿಸಿರುವಾಗ ಮಾತ್ರ ವಿಶ್ವಾಸಾರ್ಹ), ಅಥವಾ ನೇರ ಕರೆಗಾರರಿಗಾಗಿ ನಿಜವಾದ ಸಾಕೆಟ್ ಪೀರ್. `Host` /
`nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ, ಮತ್ತು ಮೊದಲ-ಪಾಸ್ವರ್ಡ್ ಬರವಣಿಗೆ
(`POST /api/settings/require-login`) ಪ್ರತಿ ನೆಟ್ವರ್ಕ್ ಪೀರ್ಗೆ ತೆರೆದಿರುವ ಬದಲು ಇದೇ
ನಿರ್ಬಂಧಕ್ಕೆ ಒಳಪಟ್ಟಿರುತ್ತದೆ (GHSA-7pq4-8pvv-rx7r). `managementPolicy` ತನ್ನದೇ ಆದ `peerContext` ತೀರ್ಪನ್ನು
ಸ್ಪಷ್ಟವಾಗಿ ಕೆಳಕ್ಕೆ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ORIGINAL (ತೆಗೆದುಹಾಕುವ ಮೊದಲು) ವಿನಂತಿಯ ಹೆಡರ್ಗಳು ಅದನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಹಂತ 3 — MANAGEMENT (ಡೀಫಾಲ್ಟ್)

ಉಳಿದ ಎಲ್ಲಾ ನಿರ್ವಹಣಾ ಮಾರ್ಗಗಳು. `requireLogin=false` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿರದ ಹೊರತು ದೃಢೀಕರಣ
ಅಗತ್ಯ. CLI ಟೋಕನ್ಗಳು ಈ ಮಾರ್ಗಗಳನ್ನು ದೃಢೀಕರಿಸಬಹುದು (ಲೂಪ್ಬ್ಯಾಕ್ + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

## OpenAPI ನಲ್ಲಿ ಭದ್ರತಾ ಹಂತಗಳನ್ನು ದಾಖಲಿಸುವುದು

`docs/openapi.yaml` ಗೆ ಹೊಸ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವಾಗ, ಮಾರ್ಗವನ್ನು `routeGuard.ts` ವರ್ಗೀಕರಿಸಿದ್ದರೆ ಅದಕ್ಕೆ ಅನುಗುಣವಾದ vendor extension ಅನ್ನು ಅನ್ವಯಿಸಿ:

| routeGuard.ts ವರ್ಗೀಕರಣ                     | YAML ಟಿಪ್ಪಣಿ                | ಜಾರಿಗೊಳಿಸುವಿಕೆ                                                     |
| ------------------------------------------ | --------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`     | ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಮೂಲಗಳಿಂದ ಬರುವುದನ್ನು ಬೇಷರತ್ತಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`  | `requireLogin=false` ಇದ್ದರೂ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ                      |
| ಆಂತರಿಕ admin/debug ಮಾರ್ಗ                   | `x-internal: true`          | ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ /dashboard/api-endpoints ನಿಂದ ಮರೆಮಾಡಲಾಗುತ್ತದೆ     |
| ಯಾವುದೂ ಇಲ್ಲ (ಸಾರ್ವಜನಿಕ / ಪ್ರಮಾಣಿತ ದೃಢೀಕರಣ) | (ಯಾವುದೇ ಟಿಪ್ಪಣಿ ಅಗತ್ಯವಿಲ್ಲ) | ಪ್ರಮಾಣಿತ `requireLogin`-ನಿಯಂತ್ರಿತ ಪ್ರವೇಶ                           |

### ಮೌಲ್ಯೀಕರಣ

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
