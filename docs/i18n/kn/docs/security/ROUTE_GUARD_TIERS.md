## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಶ್ರೇಣಿಗಳು

### ಶ್ರೇಣಿ 1 — LOCAL_ONLY

**ಇವರಿಂದ ಜಾರಿಗೊಳಿಸಲಾಗಿದೆ:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಚೆಕ್** ಬೈಪಾಸ್:** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ಸ್ಕೋಪ್ನೊಂದಿಗೆ ಮಾನ್ಯವಾದ API ಕೀಲಿಯನ್ನು ಹೊಂದಿರುವಾಗ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿ ಮಾರ್ಗಗಳಿಗಾಗಿ ಕಿರಿದಾದ ಕಾರ್ವ್-ಔಟ್ ( [ನಿರ್ವಹಣೆ-ವ್ಯಾಪ್ತಿಯ ಕಾರ್ವ್-ಔಟ್ ಅನ್ನು](#manage-scope-carve-out) ನೋಡಿ).

ಈ ಮಾರ್ಗಗಳು ಮಕ್ಕಳ ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಹುಟ್ಟುಹಾಕುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ಗೆ ಅವರನ್ನು ಒಡ್ಡುವುದರಿಂದ ಮಾನ್ಯವಾದ JWT (ಉದಾಹರಣೆಗೆ, Cloudflared/Ngrok ಸುರಂಗದ ಮೂಲಕ) ಪಡೆದ ಆಕ್ರಮಣಕಾರರಿಗೆ ತಿಳಿದಿರುವ CVE ವರ್ಗ ( [GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj) ) — ಮೊಟ್ಟೆಯಿಡುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಚೋದಿಸಲು ಅನುಮತಿಸುತ್ತದೆ.

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ದಾಳಿ ವರ್ಗ):** management/agent ಪರಿಚಾರಕವು ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವ ಅಂತಿಮ ಬಿಂದುವನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ (`npm install`, `node`, ಬ್ರೌಸರ್, ಪ್ರಾಕ್ಸಿ, `git`, `tar`, ...). ಆ ಎಂಡ್ಪಾಯಿಂಟ್ ಆಫ್-ಹೋಸ್ಟ್ — ನಿಂದ ತಲುಪಬಹುದು ಏಕೆಂದರೆ ಆಪರೇಟರ್ nginx/Cloudflare/Tailscale ಸುರಂಗದ ಹಿಂದೆ OmniRoute ಇರಿಸಿದರೆ ಮತ್ತು JWT ಸೋರಿಕೆಯಾಗಿದೆ, ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ್ದರೆ — ಆಕ್ರಮಣಕಾರನು " API ಅನ್ನು ಕರೆ ಮಾಡಿ" ಅನ್ನು "ಹೋಸ್ಟ್ನಲ್ಲಿ ಆಜ್ಞೆಯನ್ನು ಚಲಾಯಿಸಿ" (ರಿಮೋಟ್ ಕೋಡ್ ಎಕ್ಸಿಕ್ಯೂಶನ್) ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತಾನೆ. OmniRoute a ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ ಇದನ್ನು ಮುಚ್ಚುತ್ತದೆ** ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಅನ್ನು ಬೇಷರತ್ತಾಗಿ ಪರಿಶೀಲಿಸಿ, ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಯ ಮೊದಲು** , ಪ್ರತಿ ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯ ಮಾರ್ಗದಲ್ಲಿ: ಸುರಂಗದ ಮೇಲೆ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಇನ್ನೂ ಸ್ಪಾನ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಪೂರ್ಣ LOCAL_ONLY ಸೆಟ್.** ಅಧಿಕೃತ ಮೂಲವು `src/server/authz/routeGuard.ts` ನಲ್ಲಿ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ಆಗಿದೆ; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ. `check-route-guard-membership` ಗೇಟ್ ಪ್ರತಿ `route.ts` ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯದ ಪೂರ್ವಪ್ರತ್ಯಯಗಳ ಅಡಿಯಲ್ಲಿ ಎಣಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದಾದರೂ ಸ್ಥಳೀಯವಾಗಿ ವರ್ಗೀಕರಿಸದಿದ್ದರೆ CI ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

#### ನಿರ್ವಹಣೆ-ವ್ಯಾಪ್ತಿ ಕೆತ್ತನೆ-ಔಟ್

A subset of LOCAL_ONLY paths MAY also be accessed from non-loopback if and only if the request carries an `Authorization: Bearer <api-key>` whose metadata includes the `manage` scope (or `admin`). The carve-out is gated explicitly per-path via `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` so the default for any new LOCAL_ONLY path remains strict-loopback. Unauthenticated requests and requests with non-manage keys are still rejected with `403 LOCAL_ONLY`.

ಇಂದು ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪೂರ್ವಪ್ರತ್ಯಯವು `/api/mcp/` ಆಗಿದೆ. `/api/cli-tools/runtime/` ಮತ್ತು `/api/services/` ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ ಏಕೆಂದರೆ ಅವುಗಳು ಅನಿಯಂತ್ರಿತ ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು (`npm install`, `node`) ಹುಟ್ಟುಹಾಕಬಹುದು, ಇದು LOCAL_ONLY ಶ್ರೇಣಿಯು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ CVE ವರ್ಗವಾಗಿದೆ.

#### ಆಪರೇಟರ್ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಲೆಕ್ಕಪರಿಶೋಧನೆ

ನೀವು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಸುರಂಗದ ಹಿಂದೆ OmniRoute ಚಲಾಯಿಸಿದರೆ (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), ಲೂಪ್ಬ್ಯಾಕ್ ಚೆಕ್ — ಮೇಲಿನ ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯದ ಮಾರ್ಗಗಳನ್ನು ರಕ್ಷಿಸುತ್ತದೆ, ಅದರ ಕ್ಲೈಂಟ್ ವಿಳಾಸವು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ವಿನಂತಿಯನ್ನು `403 LOCAL_ONLY` ನೊಂದಿಗೆ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.** auth ರನ್ ಆಗುವ ಮೊದಲು** , ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT ಸ್ಪಾನ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಎರಡು ಆಪರೇಟರ್ ಜವಾಬ್ದಾರಿಗಳು ಉಳಿದಿವೆ:

- **ಕ್ಲೈಂಟ್ IP ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿ ಫೋರ್ಜ್ ಮಾಡುವ ಮೂಲಕ 403 ಅನ್ನು "ಫಿಕ್ಸ್" ಮಾಡಬೇಡಿ.** `X-Forwarded-For: 127.0.0.1` ಹೊಂದಿಸುವುದು ಅಥವಾ ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮೂಲ ವಿಳಾಸವನ್ನು ಪುನಃ ಬರೆಯುವ ಪ್ರಾಕ್ಸಿ, ಈ ಶ್ರೇಣಿಯನ್ನು ಮುಚ್ಚುವ RCE ವರ್ಗವನ್ನು ನಿಖರವಾಗಿ ಮರು-ತೆರೆಯುತ್ತದೆ. ಪ್ರಾಕ್ಸಿ — ಮೂಲಕ dashboard/API ಅನ್ನು ಎಂದಿಗೂ ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯದ ಮಾರ್ಗಗಳ ಮೂಲಕ ಬಹಿರಂಗಪಡಿಸಿ.
- **ಮ್ಯಾನೇಜ್-ಸ್ಕೋಪ್ ಬೈಪಾಸ್ ಅನ್ನು ಕನಿಷ್ಠವಾಗಿ ಇರಿಸಿ.** `/api/mcp/` ಮಾತ್ರ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾಗಿದೆ ಮತ್ತು `manage` -scoped API ಕೀಲಿಯೊಂದಿಗೆ ಮಾತ್ರ. `SPAWN_CAPABLE_PREFIXES` ಬೈಪಾಸ್ ಪಟ್ಟಿಗೆ ಎಂದಿಗೂ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ — zod ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು `isLocalOnlyBypassableByManageScope` ರನ್ಟೈಮ್ನಲ್ಲಿ (ಡಿಫೆನ್ಸ್-ಇನ್-ಡೆಪ್ತ್) ನಿರಾಕರಿಸುತ್ತದೆ, ಇದು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಎಂದರೆ "ಬೈಪಾಸ್ ಮಾಡಲಾಗದು". ಅದೇ ನಿರಾಕರಣೆ-ಪಟ್ಟಿಯು ಕೆಲವು LOCAL_ONLY ಮಾರ್ಗಗಳನ್ನು ಹೊಂದಿದ್ದು, ಅವು ಹುಟ್ಟಿಕೊಳ್ಳುವುದಿಲ್ಲ ಆದರೆ ಎಂದಿಗೂ ರಿಮೋಟ್ ಆಗಿ ತಲುಪಬಾರದು — `/api/oauth/kiro/auto-import` (ಹೋಸ್ಟ್-ಸ್ಥಳೀಯ Kiro ರುಜುವಾತು ಫೈಲ್ಗಳನ್ನು ಓದುತ್ತದೆ), `/api/discovery/` ಮತ್ತು `/api/issue-agent/`. ರನ್ಟೈಮ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಲೋಡರ್ ಕೂಡ ಅಂತಹ ನಮೂದುಗಳನ್ನು ಸಂಗ್ರಹಿಸಲಾದ ಸೆಟ್ಟಿಂಗ್ಗಳ ಸಾಲಿನಿಂದ ಬಿಡುತ್ತದೆ, ಮತ್ತು ಲೆಗಸಿ JSON ಆಮದು (`/api/settings/import-json`) ಎಂದಿಗೂ ಬೈಪಾಸ್ ಕೀಗಳನ್ನು ಬರೆಯುವುದಿಲ್ಲ. ಪ್ರತಿ `LOCAL_ONLY_API_PREFIXES` ಪ್ರವೇಶವು ನಿರಾಕರಣೆ-ಪಟ್ಟಿಯಲ್ಲಿರಬೇಕು ಅಥವಾ ಬೈಪಾಸ್-ಅರ್ಹತೆ (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`) ಎಂದು ಪರಿಶೀಲಿಸಬೇಕು. `/api/providers/` (ಉದಾ `/login`, `/refresh-cursor`) ಅಡಿಯಲ್ಲಿ ಡೈನಾಮಿಕ್-ಸೆಗ್ಮೆಂಟ್ ಮತ್ತು ಸ್ಟ್ಯಾಟಿಕ್-ಪಾತ್ ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯದ ಮಾರ್ಗಗಳು `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿನ ರಿಜೆಕ್ಸ್-ಆಧಾರಿತ `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಕಂಪ್ಯಾನಿಯನ್ನಿಂದ ಆವರಿಸಲ್ಪಟ್ಟಿವೆ, ಫ್ಲಾಟ್ `SPAWN_CAPABLE_PREFIXES` ಅರೇ — ಯಿಂದ ಅಲ್ಲ, ಫ್ಲಾಟ್ ಅರೇಯು ಅವುಗಳನ್ನು ಪೂರ್ವ- `/api/providers/` ಟ್ರೀ ಅನ್ನು ಹಿಡಿಯುವ ಮಾರ್ಗವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಆವರಿಸಬೇಕು. ಪೂರೈಕೆದಾರ CRUD ಗಾಗಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಬಳಸುತ್ತವೆ.

**ಆಡಿಟಿಂಗ್ ಪ್ರವೇಶ** ಆಫ್-ಹೋಸ್ಟ್ ಈ ಮಾರ್ಗಗಳನ್ನು ತಲುಪುತ್ತಿಲ್ಲ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಲು — :

- ತೆರೆಯಿರಿ** ದೃಢೀಕರಣ ದಾಸ್ತಾನು** `/dashboard/settings/security` ನಲ್ಲಿ : ಇದು ಲೈವ್ LOCAL_ONLY ಪೂರ್ವಪ್ರತ್ಯಯ ಪಟ್ಟಿಯನ್ನು ನಿರೂಪಿಸುತ್ತದೆ, ಇದು ಪೂರ್ವಪ್ರತ್ಯಯಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡಬಹುದಾಗಿದೆ ಮತ್ತು ಕಂಪೈಲ್-ಟೈಮ್ ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯವನ್ನು ("ಬೈಪಾಸ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ") ಸೆಟ್ ಮಾಡುತ್ತದೆ.
- ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಕ್ಲೈಂಟ್ ವಿಳಾಸದೊಂದಿಗೆ ಜೋಡಿಸಲಾದ ಮೇಲಿನ ಪೂರ್ವಪ್ರತ್ಯಯಗಳಿಗಾಗಿ ನಿಮ್ಮ ರಿವರ್ಸ್-ಪ್ರಾಕ್ಸಿ / ಪ್ರವೇಶ ಲಾಗ್ಗಳನ್ನು ಗ್ರೆಪ್ ಮಾಡಿ. `403 LOCAL_ONLY` ಬದಲಿಗೆ `200` ಹಿಂತಿರುಗಿಸಿದ ಯಾವುದೇ ಹಿಟ್ ಎಂದರೆ ಪ್ರಾಕ್ಸಿಯು ನಿಜವಾದ ಕ್ಲೈಂಟ್ IP — ಅನ್ನು ಮರೆಮಾಚುತ್ತಿದೆ ಎಂದರೆ ಪ್ರಾಕ್ಸಿಯನ್ನು ಸರಿಪಡಿಸುತ್ತದೆ.
- ಈ ಪಥಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ OmniRoute ನ ಲಾಗ್ನಲ್ಲಿರುವ `403 LOCAL_ONLY` ಎಂದರೆ ಸಿಬ್ಬಂದಿ ಉದ್ದೇಶಿಸಿದಂತೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ, ನಿಗ್ರಹಿಸುವ ದೋಷವಲ್ಲ.

#### ಕರೆ-ಸೈಟ್ ಪ್ರೋಬ್ ಗೇಟ್ನೊಂದಿಗೆ ರಿಮೋಟ್-ತಲುಪಬಹುದಾದ ಮಾರ್ಗಗಳು

ಕೆಲವು ಮಾರ್ಗಗಳು ರಿಮೋಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ತಲುಪಬಹುದು ಆದರೆ ಸ್ಥಳೀಯ ಕರೆ ಮಾಡುವವರಿಗೆ ಹೋಸ್ಟ್-ಸೈಡ್ ಪ್ರೋಬ್ (`which <binary>`, `<binary> --version`, `tailscale status --json`) ಅನ್ನು ರನ್ ಮಾಡಬೇಕು. ಅವು `GET` ಗೆ LOCAL_ONLY ಅಲ್ಲ; ಬದಲಿಗೆ ಹ್ಯಾಂಡ್ಲರ್ ವಿಶ್ವಾಸಾರ್ಹ ಪೀರ್ ತೀರ್ಪನ್ನು `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) ನೊಂದಿಗೆ ಓದುತ್ತಾನೆ ಮತ್ತು `loopback` / `lan` ಕರೆ ಮಾಡುವವರಿಗೆ ಮಾತ್ರ ತನಿಖೆ ನಡೆಸುತ್ತಾನೆ. `remote` ಕಾಲರ್ ಮೊಟ್ಟೆಯಿಡದ ಮೂಲಗಳಿಂದ ನಿರ್ಮಿಸಲಾದ ಅದೇ ಪ್ರತಿಕ್ರಿಯೆಯ ಆಕಾರವನ್ನು ಪಡೆಯುತ್ತದೆ (ನಿರಂತರ ಸ್ಥಿತಿ, ಸೆಟ್ಟಿಂಗ್ಗಳು, fs ಚೆಕ್ಗಳು), ಫ್ಲ್ಯಾಗ್ ಮಾಡಿದ `probed: false`.

#### ರುಜುವಾತು ರಫ್ತುಗಳು ಮತ್ತು ಮರುಸ್ಥಾಪನೆಗಳು ಆಪರೇಟರ್-ಮಾತ್ರ

ಮೇಲಿನ ಶ್ರೇಣಿಯು _some_ ರುಜುವಾತು ಅಗತ್ಯವಿದೆಯೇ ಎಂಬುದನ್ನು ಮಾತ್ರ ನಿರ್ಧರಿಸುತ್ತದೆ. ಸಂಗ್ರಹಿಸಿದ ರುಜುವಾತುಗಳನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುವ ಮಾರ್ಗಗಳು ಹ್ಯಾಂಡ್ಲರ್ನಲ್ಲಿ ಎರಡನೇ ಚೆಕ್ ಅನ್ನು ಸೇರಿಸುತ್ತವೆ: `GET /api/settings/export-json` (ಡಿಕ್ರಿಪ್ಟ್ ಮಾಡಲಾದ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳು ಮತ್ತು ಕಚ್ಚಾ API ಕೀಗಳು), `GET /api/db-backups/export` ( SQLite ಫೈಲ್) ಮತ್ತು `GET /api/db-backups/exportAll` (ಪೂರ್ಣ ಆರ್ಕೈವ್) `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`) ಕರೆ. ಇದು ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್, ಸ್ಥಳೀಯ CLI ವಿಷಯ, ಅಥವಾ ಲಾಗಿನ್ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಉದಾಹರಣೆಯನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ ವ್ಯಾಪ್ತಿಯ ( `manage` ಮತ್ತು `admin` ಸೇರಿದಂತೆ) API ಕೀಗಳಿಗೆ ಮತ್ತು `oma_` ಪ್ರವೇಶ ಟೋಕನ್ಗಳಿಗೆ `403` ಗೆ ಉತ್ತರಿಸುತ್ತದೆ. ವಿನಾಶಕಾರಿ ಕೌಂಟರ್ಪಾರ್ಟ್ಸ್ ಒಂದೇ ಗಡಿಯನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುತ್ತದೆ: `POST /api/db-backups/import` (ಅಪ್ಲೋಡ್ ಮಾಡಲಾದ `.sqlite`, `dryRun=true` ಒಳಗೊಂಡಿತ್ತು), `POST /api/db-backups` (ಐಡಿ ಮೂಲಕ ಸಂಗ್ರಹಿಸಲಾದ ಬ್ಯಾಕ್ಅಪ್ ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ) ಮತ್ತು `POST /api/settings/import-json` (ಲೆಗಸಿ JSON ಮರುಸ್ಥಾಪನೆ) ಲೈವ್ ಡೇಟಾಬೇಸ್ ಅಥವಾ ಸಂಪೂರ್ಣ settings/connections/API-key ಸೆಟ್ ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಯಂತ್ರದ ರುಜುವಾತು ಅವುಗಳನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪುನಃಸ್ಥಾಪನೆ ಬಿಂದುಗಳನ್ನು ನಾಶಮಾಡುವುದು ಒಂದೇ ಗಡಿಯನ್ನು ಹೊಂದಿದೆ: `DELETE /api/db-backups` (ಕ್ಲೀನಪ್ — ಇತ್ತೀಚಿನ N / ಡ್ರಾಪ್ ಅನ್ನು D ದಿನಗಳಿಗಿಂತ ಹಳೆಯದಾಗಿ ಇರಿಸುತ್ತದೆ) ಮತ್ತು `PATCH /api/db-backups` (ಧಾರಣ ಸೆಟ್ಟಿಂಗ್ಗಳು), ಏಕೆಂದರೆ ನಿರಂತರವಾದ ಧಾರಣವು ಪ್ರತಿ ಸ್ವಯಂಚಾಲಿತ ಬ್ಯಾಕಪ್ (`src/lib/db/backup.ts`) ನಂತರ ನಿಖರವಾಗಿ `cleanupDbBackups()` ಅನ್ವಯಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ `keepLatest: 1` ನಲ್ಲಿ ಎಲ್ಲವನ್ನೂ ಉಳಿಸುವ ಯಂತ್ರದ ರುಜುವಾತು ಮುಂದಿನ prunenapshot. ಬ್ಯಾಕ್ಅಪ್ಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡುವುದು ಮತ್ತು ರಚಿಸುವುದು (`GET`/`PUT /api/db-backups`) ಸಾಮಾನ್ಯ ನಿರ್ವಹಣೆ ದೃಢೀಕರಣವನ್ನು ಇರಿಸಿಕೊಳ್ಳಿ. ಸಿಂಕ್ ಟೋಕನ್ ನೀಡಿಕೆ (`POST /api/sync/tokens`) ಅದೇ ಸಹಾಯಕವನ್ನು ಮತ್ತು ವಿಶ್ವಾಸಾರ್ಹ ಲೂಪ್ಬ್ಯಾಕ್ ಆಂತರಿಕ-ಸೇವಾ ಟೋಕನ್ ಅನ್ನು ಬಳಸುತ್ತದೆ.

### ಫ್ರೆಶ್-ಇನ್ಸ್ಟಾಲ್ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ನಿಜವಾದ ಪೀರ್ನಿಂದ ಲೂಪ್ಬ್ಯಾಕ್-ಮಾತ್ರ — ಆಗಿದೆ, `Host` ಅಲ್ಲ

ಯಾವುದೇ ನಿರ್ವಹಣಾ ಗುಪ್ತಪದವನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದೆ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲ), `src/shared/utils/apiAuth.ts` ನಲ್ಲಿನ `isAuthRequired()` ಅನಾಮಧೇಯ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಅನ್ನು ತೆರೆದಿರುತ್ತದೆ** ಲೂಪ್ಬ್ಯಾಕ್ ಗೆಳೆಯರಿಗೆ ಮಾತ್ರ** . ಲೂಪ್ಬ್ಯಾಕ್ ಅನ್ನು ವಿಶ್ವಾಸಾರ್ಹ ಪೀರ್ ಸಿಗ್ನಲ್ಗಳಿಂದ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ, ಈ ಕ್ರಮದಲ್ಲಿ: ಟೋಕನ್-ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ನೈಜ TCP ಪೀರ್ (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ನೀತಿಯು ಏನು ನೋಡುತ್ತದೆ), ಪೈಪ್ಲೈನ್ನ ಸ್ವಂತ `AUTHZ_HEADER_PEER_LOCALITY` ತೀರ್ಪು (ಯಾವ ಮಾರ್ಗ ನಿರ್ವಾಹಕರು ನೋಡುತ್ತಾರೆ, `OMNIROUTE_PEER_STAMP_TOKEN` ಹೊಂದಿಸಿದಾಗ ಮಾತ್ರ ನಂಬುತ್ತಾರೆ), ಅಥವಾ ನೇರ ಕರೆ ಮಾಡುವವರಿಗೆ ನಿಜವಾದ ಸಾಕೆಟ್ ಪೀರ್. `Host` / `nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಸಮಾಲೋಚಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು ಮೊದಲ-ಪಾಸ್ವರ್ಡ್ ರೈಟ್ (`POST /api/settings/require-login`) ಪ್ರತಿ ನೆಟ್ವರ್ಕ್ ಪೀರ್ಗೆ (GHSA-7pq4-8pvv-rx7r) ತೆರೆದಿರುವುದಕ್ಕಿಂತ ಅದೇ ನಿರ್ಬಂಧದ ಅಡಿಯಲ್ಲಿದೆ. `managementPolicy` ತನ್ನದೇ ಆದ `peerContext` ತೀರ್ಪನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಕೆಳಗೆ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ORIGINAL (ಪ್ರಿ-ಸ್ಟ್ರಿಪ್) ವಿನಂತಿಯ ಹೆಡರ್ಗಳು ಅದನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಶ್ರೇಣಿ 3 — MANAGEMENT (ಡೀಫಾಲ್ಟ್)

ಎಲ್ಲಾ ಇತರ ನಿರ್ವಹಣಾ ಮಾರ್ಗಗಳು. `requireLogin=false` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದ ಹೊರತು ದೃಢೀಕರಣದ ಅಗತ್ಯವಿದೆ. CLI ಟೋಕನ್ಗಳು ಈ ಮಾರ್ಗಗಳನ್ನು ದೃಢೀಕರಿಸಬಹುದು (ಲೂಪ್ಬ್ಯಾಕ್ + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

## OpenAPI ನಲ್ಲಿ ಭದ್ರತಾ ಹಂತಗಳನ್ನು ದಾಖಲಿಸುವುದು

`docs/openapi.yaml` ಗೆ ಹೊಸ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವಾಗ, ಮಾರ್ಗವನ್ನು `routeGuard.ts` ವರ್ಗೀಕರಿಸಿದ್ದರೆ ಅದಕ್ಕೆ ಅನುಗುಣವಾದ vendor extension ಅನ್ನು ಅನ್ವಯಿಸಿ:

| routeGuard.ts ವರ್ಗೀಕರಣ                     | YAML ಟಿಪ್ಪಣಿ                | ಜಾರಿಗೊಳಿಸುವಿಕೆ                                                     |
| ------------------------------------------ | --------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`     | ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಮೂಲಗಳಿಂದ ಬರುವುದನ್ನು ಬೇಷರತ್ತಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`  | `requireLogin=false` ಇದ್ದರೂ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ                      |
| ಆಂತರಿಕ admin/debug ಮಾರ್ಗ                   | `x-internal: true`          | ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ /dashboard/api-endpoints ನಿಂದ ಮರೆಮಾಡಲಾಗುತ್ತದೆ     |
| ಯಾವುದೂ ಇಲ್ಲ (ಸಾರ್ವಜನಿಕ / ಪ್ರಮಾಣಿತ ದೃಢೀಕರಣ) | (ಯಾವುದೇ ಟಿಪ್ಪಣಿ ಅಗತ್ಯವಿಲ್ಲ) | ಪ್ರಮಾಣಿತ `requireLogin`-ನಿಯಂತ್ರಿತ ಪ್ರವೇಶ                           |

### ಮೌಲ್ಯೀಕರಣ

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
