> **ಸತ್ಯದ ಮೂಲ:** `src/lib/guardrails/`
> **ಕೊನೆಯ ನವೀಕರಣ:** 2026-10-17 — v3.8.52 ([ವ್ಯಾಪ್ತಿ ಮತ್ತು ಮಿತಿಗಳು](#coverage-and-limits) ಸೇರಿಸಲಾಗಿದೆ:
> hooks ಯಾವ routes ಮತ್ತು response pathಗಳನ್ನು ತಲುಪುತ್ತವೆ, ವಿಲೀನಗೊಂಡ disable headers (#16412), ಕಡ್ಡಾಯ
> ಗಡಿಯಾಗಿ injection block mode (#16413), ಮತ್ತು post-call ಮೊದಲು response ಅನ್ನು ಏನು ನೋಡುತ್ತದೆ)

ಗಾರ್ಡ್ರೇಲ್ಗಳು OmniRoute ಮತ್ತು upstream ಪೂರೈಕೆದಾರರ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ಸುರಕ್ಷತೆ, ನೀತಿ ಮತ್ತು ವಿಷಯ
ರೂಪಾಂತರಣಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿ ಗಾರ್ಡ್ರೇಲ್ request payloadಗಳನ್ನು (`preCall`) ಮತ್ತು
upstream responseಗಳನ್ನು (`postCall`) ಪರಿಶೀಲಿಸಬಹುದು (ಮತ್ತು ಐಚ್ಛಿಕವಾಗಿ ತಿರಸ್ಕರಿಸಬಹುದು,
ರೂಪಾಂತರಿಸಬಹುದು ಅಥವಾ ಟಿಪ್ಪಣಿ ಸೇರಿಸಬಹುದು).

ಈ ವ್ಯವಸ್ಥೆ **fail-open**: ಗಾರ್ಡ್ರೇಲ್ ಕಾರ್ಯನಿರ್ವಹಣೆಯ ವೇಳೆ error ಎಸೆದರೆ, registry ದೋಷವನ್ನು
ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು request ಅನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು ಮುಂದಿನ ಗಾರ್ಡ್ರೇಲ್ನೊಂದಿಗೆ ಮುಂದುವರಿಯುತ್ತದೆ.
ನಿರ್ಬಂಧವು ಸ್ಪಷ್ಟವಾದ ನಿರ್ಧಾರ (`block: true`), ಎಂದಿಗೂ ಆಕಸ್ಮಿಕವಲ್ಲ. ಒಂದೇ ಅಪವಾದವೆಂದರೆ ಸ್ಥಗಿತಗೊಂಡ
request: ಕರೆಗಾರರ `signal` ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಿದಾಗ, error ಎಸೆಯುವ ಗಾರ್ಡ್ರೇಲ್ skip ಆಗುವ ಬದಲು
hook run ಅನ್ನು reject ಮಾಡುತ್ತದೆ.

ಈ hooks ಪ್ರತಿ route ಅಥವಾ ಪ್ರತಿ response ಮೇಲೂ **ರನ್ ಆಗುವುದಿಲ್ಲ**. ಗಾರ್ಡ್ರೇಲ್ ಅನ್ನು ಭದ್ರತಾ
ನಿಯಂತ್ರಣವಾಗಿ ಅವಲಂಬಿಸುವ ಮೊದಲು [ವ್ಯಾಪ್ತಿ ಮತ್ತು ಮಿತಿಗಳು](#coverage-and-limits) ಓದಿ.

## ಅಂತರ್ನಿರ್ಮಿತ ಗಾರ್ಡ್ರೇಲ್ಗಳು

import ಮಾಡಿದಾಗ registry ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ಆರು ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಸ್ವಯಂ-ಲೋಡ್ ಮಾಡುತ್ತದೆ
(`registry.ts` → `registerDefaultGuardrails()` ನೋಡಿ):

| ಆದ್ಯತೆ | ಹೆಸರು               | ಹಂತ(ಗಳು)       | ಫೈಲ್                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ಕಡಿಮೆ ಆದ್ಯತೆಯ ಸಂಖ್ಯೆಗಳು **ಮೊದಲು** ರನ್ ಆಗುತ್ತವೆ.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

GLM 5.3 base ಮಾಡೆಲ್ ಮತ್ತು `glm-5.3-{low,high,max}` ಸ್ಪಷ್ಟವಾದ `supportsVision:false`
registry/spec ಮೆಟಾಡೇಟಾವನ್ನು ಹೊಂದಿವೆ. GLM 5.3 Flash variants native-vision ಮಾಡೆಲ್ಗಳಾಗಿ
ಉಳಿದಿವೆ. Claude Code ನ `/v1/messages` route, Claude-to-OpenAI ಭಾಷಾಂತರಕ್ಕೆ **ಮೊದಲು** ಹಂಚಿಕೆ
`handleChat` pre-call ಗಾರ್ಡ್ರೇಲ್ ಸರಪಳಿಯನ್ನು ಪ್ರವೇಶಿಸುತ್ತದೆ; ಆ ಭಾಷಾಂತರವು ಅವುಗಳನ್ನು OpenAI
`image_url` content ಆಗಿ ಪರಿವರ್ತಿಸುವ ಮೊದಲು nested `Read` tool-result ಚಿತ್ರಗಳನ್ನು ವಿವರಿಸಲಾಗಬೇಕು
ಅಥವಾ ನಿರ್ವಹಿಸಲಾಗಬೇಕು (#17069).

**non-vision ಮಾಡೆಲ್ಗಳನ್ನು** ಗುರಿಯಾಗಿಟ್ಟುಕೊಂಡ ಚಿತ್ರ-ಹೊಂದಿರುವ requestಗಳನ್ನು intercept ಮಾಡುತ್ತದೆ
ಮತ್ತು upstream call ಮೊದಲು ಇಡೀ request ಅನ್ನು vision-capable ಮಾಡೆಲ್ಗೆ ಮರುನಿರ್ದೇಶಿಸುತ್ತದೆ ಅಥವಾ
ಚಿತ್ರ ಭಾಗಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ vision ಮಾಡೆಲ್ ಉತ್ಪಾದಿಸಿದ ಪಠ್ಯ ವಿವರಣೆಗಳೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತದೆ.
ಇದು text-only ಪೂರೈಕೆದಾರರಿಗೆ multimodal payloadಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ನಿರ್ವಹಿಸಲು ಅನುವು ಮಾಡಿಕೊಡುತ್ತದೆ.

ಹರಿವು:

1. ಟಾರ್ಗೆಟ್ ಮಾಡೆಲ್ ಈಗಾಗಲೇ vision ಬೆಂಬಲಿಸಿದರೆ skip ಮಾಡಿ (ಅದು forced-bridge ಪಟ್ಟಿ
   `isVisionBridgeForcedModel` ನಲ್ಲಿ ಕಾಣಿಸಿಕೊಂಡರೆ ಹೊರತು).
2. `extractImageParts(messages)` (`visionBridgeHelpers.ts`) ಮೂಲಕ ಚಿತ್ರ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ,
   ಇದು `open-sse/utils/mediaParts.ts` ನಲ್ಲಿರುವ **unified media detector** `detectMediaParts()`
   ಗೆ ಡೆಲಿಗೇಟ್ ಮಾಡುತ್ತದೆ — combo ಹೊಂದಾಣಿಕೆ ಫಿಲ್ಟರ್ನೊಂದಿಗೆ ಹಂಚಿಕೊಂಡ ಏಕೈಕ ಸತ್ಯದ ಮೂಲ.
   ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು `replaceImageParts` ಮತ್ತೆ splice ಮಾಡಬಹುದಾದ ಆಕಾರಗಳಿಗೆ allowlist
   ಮಾಡಲಾಗಿದೆ (extract↔replace ಒಪ್ಪಂದ): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, ಮತ್ತು Responses
   API `input_image`. Claude Code `tool_result.content` ಮತ್ತು Responses tool outputಗಳ ಒಳಗೆ
   nested ಆಗಿರುವ ಹೊಂದಾಣಿಕೆಯ ಚಿತ್ರಗಳನ್ನು ಸಹ ಹೊರತೆಗೆಯಲಾಗುತ್ತದೆ ಮತ್ತು ಅವುಗಳ ಮೂಲ pathಗಳಲ್ಲಿ
   ಬದಲಾಯಿಸಲಾಗುತ್ತದೆ; indicator-only ಆಕಾರಗಳು combo-filter ವಸ್ತುಗಳಾಗಿವೆ ಮತ್ತು
   ಹೊರತೆಗೆಯಲಾಗುವುದಿಲ್ಲ. ಯಾವುದೂ ಕಂಡುಬರದಿದ್ದರೆ skip ಮಾಡಿ.
3. `resolveVisionBridgeRuntimeSettings()` ಮೂಲಕ runtime config ಅನ್ನು resolve ಮಾಡಿ
   (`src/shared/constants/modalityBridgeDefaults.ts`): ಹೊಸ `modalityBridge*` settings keys
   ಗೆಲ್ಲುತ್ತವೆ; legacy `visionBridge*` keys **one-cycle fallback** ಆಗಿ ಉಳಿದಿವೆ (rollback
   window). ಬ್ರಿಡ್ಜ್ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿದಾಗ ಯಾವುದೇ media traversal ಮೊದಲು skip ಮಾಡಿ.
4. ಮೋಡ್ ಸೆಲೆಕ್ಟರ್ (`modalityBridgeVisionMode`, ಕೆಳಗಿನ ಕೋಷ್ಟಕ ನೋಡಿ) reroute vs describe
   ಅನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ. Reroute ಕೇವಲ `model` ಅನ್ನು ಬದಲಾಯಿಸಿದ `modifiedPayload` ಅನ್ನು
   ಹಿಂದಿರುಗಿಸುತ್ತದೆ, ಜೊತೆಗೆ meta `{ rerouted, fromModel, toModel, imagesKept }`.
5. Describe path: ಚಿತ್ರಗಳನ್ನು `maxImages` ಗೆ ಮಿತಿಗೊಳಿಸಿ, task-aware prompt ಅನ್ನು ರಚಿಸಿ,
   describe cache ಅನ್ನು ಪರಿಶೀಲಿಸಿ, vision ಮಾಡೆಲ್ ಅನ್ನು **ಸಮಾನಾಂತರವಾಗಿ**
   (`Promise.allSettled`) ಕರೆಯಿರಿ, ಮತ್ತು ಅವುಗಳ ಸ್ಥಳದಲ್ಲಿ `[Image N]: <description>` text
   ಭಾಗಗಳನ್ನು inject ಮಾಡಿ. ವಿಫಲವಾದ describe `null` ನೀಡುತ್ತದೆ: ಅಜ್ಞಾತ/vision-capable
   ಟಾರ್ಗೆಟ್ಗಳಿಗಾಗಿ ಕಚ್ಚಾ ಚಿತ್ರವನ್ನು ಸಂರಕ್ಷಿಸಲಾಗುತ್ತದೆ (#4012), ಆದರೆ **ದೃಢೀಕೃತ text-only
   ನೇರ ಟಾರ್ಗೆಟ್** ಅಥವಾ zero-vision combo, ಭಾಗಶಃ ವೈಫಲ್ಯಗಳು ಮತ್ತು describe-call ಮಿತಿಯ ಮೀರಿದ
   ಚಿತ್ರಗಳು ಸೇರಿದಂತೆ ಪ್ರತಿಯೊಂದು ವಿವರಿಸಲ್ಪಡದ ಚಿತ್ರಕ್ಕೂ ಸ್ಪಷ್ಟ
   `(unavailable — no vision-capable provider connected)` text stub ಅನ್ನು ಪಡೆಯುತ್ತದೆ
   (#17069). ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ all-failed combo describe fallback ಹಾಗೆಯೇ ಉಳಿದಿದೆ (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`, `processingTimeMs`,
   `visionModel`) ಹಿಂದಿರುಗಿಸಿ.

#### ಮೋಡ್ ಸೆಲೆಕ್ಟರ್ (`modalityBridgeVisionMode`)

| ಮೋಡ್       | ಡೀಫಾಲ್ಟ್ | ವರ್ತನೆ                                                                                                                                                                                                                                                                                                             |
| ---------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔        | ಲೆಗಸಿ ಹ್ಯೂರಿಸ್ಟಿಕ್, ಮುಟ್ಟದಂತೆಯೇ ಇರುವ (#6640/#7204): ಕಾಂಬೋ-ಅಲ್ಲದ/`auto/` ಮಾದರಿಗಳು ಅತ್ಯುತ್ತಮ ವಿಷನ್ ಮಾದರಿಗೆ ಮರುನಿರ್ದೇಶನಗೊಳ್ಳುತ್ತವೆ, ಮೂಲ ಮಾದರಿಯು ಈಗಾಗಲೇ ಬಳಸಬಹುದಾದ ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿದ್ದರೆ ಹೊರತು (ಆಗ ವಿವರಣೆ); ಕಾಂಬೋ ಟಾರ್ಗೆಟ್ಗಳು ಯಾವಾಗಲೂ ವಿವರಿಸುತ್ತವೆ.                                                                 |
| `describe` |          | ಯಾವಾಗಲೂ ವಿವರಣೆ — ಮರುನಿರ್ದೇಶನ ಬ್ಲಾಕ್ ಅನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ; ಬಳಕೆದಾರರು ಆಯ್ದ ಮಾದರಿಯು ಯಾವಾಗಲೂ ಉತ್ತರಿಸುತ್ತದೆ.                                                                                                                                                                                            |
| `reroute`  |          | ಫೋರ್ಸ್ ಮರುನಿರ್ದೇಶನ: keep-credentialed-model ಗಾರ್ಡ್ ಅನ್ನು ಬೈಪಾಸ್ ಮಾಡಲಾಗುತ್ತದೆ. ಮರುನಿರ್ದೇಶನ-**ಟಾರ್ಗೆಟ್** ರುಜುವಾತು ಗಾರ್ಡ್ ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ — ಯಾವುದೇ ಬಳಸಬಹುದಾದ ವಿಷನ್ ಟಾರ್ಗೆಟ್ ಇಲ್ಲದಿದ್ದಾಗ, ಬ್ರಿಡ್ಜ್ ವಿವರಿಸುವ ಬದಲು ಅಥವಾ ಕಚ್ಚಾ ಚಿತ್ರಗಳನ್ನು ಟೆಕ್ಸ್ಟ್-ಮಾತ್ರ ಟಾರ್ಗೆಟ್ಗೆ ಕಳುಹಿಸುವ ಬದಲು ಸ್ಪಷ್ಟ ದೋಷದೊಂದಿಗೆ ನಿರ್ಬಂಧಿಸುತ್ತದೆ. |

ಫೋರ್ಸ್ ಮಾಡಿದ ಮೋಡ್ಗಳು ಆಟೋ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಚಾಲನೆಯಾಗುವ **ಮೊದಲು** ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತವೆ; `auto`
ವರ್ತನೆಯು pre-PR-1 ಗಾರ್ಡ್ರೇಲ್ಗೆ ಬೈಟ್-ಅಭಿನ್ನವಾಗಿದೆ.

#### API-ಕೀ ವ್ಯಾಪ್ತಿ (`visionBridgeKeyScope.ts`)

ಕಾಲರ್ನ API ಕೀಯು `allowedConnections`, ಕೋಟಾ ಪೂಲ್ಗಳು
(`allowedQuotas`) ಅಥವಾ ಮಾದರಿಗಳನ್ನು (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ನಿರ್ಬಂಧಿಸಿದಾಗ, ಬ್ರಿಡ್ಜ್
ಕೀಯು ಬಳಸಬಹುದಾದ ಮರುನಿರ್ದೇಶನ ಮತ್ತು ವಿವರಣೆ ಮಾದರಿಗಳನ್ನು ಮಾತ್ರ ಆಯ್ಕೆ ಮಾಡುತ್ತದೆ,
ಕೀಯು ಬಳಸಬಹುದಾದ ಸಂಪರ್ಕಗಳ ಮೇಲೆ. ವಿವರಣೆ ಕರೆಯು ನಂತರ ಯಾವಾಗಲೂ
`x-omniroute-self-loop-key-id` ಹೆಡರ್ನೊಂದಿಗೆ OmniRoute ಸೆಲ್ಫ್-ಲೂಪ್ ಮೂಲಕ ಹೋಗುತ್ತದೆ, ಆದ್ದರಿಂದ
ಸ್ವೀಕರಿಸುವ ಚಾಟ್ ವಿನಂತಿಯು ಆ ಕೀಯ ಸಂಪರ್ಕ ಮತ್ತು ಮಾದರಿ ನೀತಿಯನ್ನು ಮತ್ತೆ
ಜಾರಿಗೊಳಿಸುತ್ತದೆ. `enforceApiKeyPolicy()` ಆ ಹೆಡರ್ ಅನ್ನು ಸೆಲ್ಫ್-ಲೂಪ್
ಬಿಯರರ್ನೊಂದಿಗೆ ಮಾತ್ರ ಗೌರವಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದು ಪ್ರವೇಶವನ್ನು ಕೇವಲ
ಕಡಿಮೆ ಮಾಡಬಲ್ಲದು, ಮತ್ತು ಪರಿಹರಿಸದ ಐಡಿಯನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಕೀಗೆ ಯಾವುದೇ ವಿಷನ್ ಮಾದರಿಯನ್ನು ಅನುಮತಿಸಿಲ್ಲದಿದ್ದರೆ, **ದೃಢೀಕೃತ
ಟೆಕ್ಸ್ಟ್-ಮಾತ್ರ ಟಾರ್ಗೆಟ್** ಚಿತ್ರದ ವಿನಂತಿಯನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಸ್ಪಷ್ಟ HTTP 400
ನೊಂದಿಗೆ ತಿರಸ್ಕರಿಸುತ್ತದೆ, ಅಸಮರ್ಥ ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ಚಿತ್ರದ ಬೈಟ್ಗಳನ್ನು ಫಾರ್ವರ್ಡ್
ಮಾಡುವ ಬದಲು (#17069). ಅಜ್ಞಾತ ಅಥವಾ ಸ್ಥಳೀಯ ವಿಷನ್ ಸಾಮರ್ಥ್ಯವಿರುವ
ಟಾರ್ಗೆಟ್ಗಳಿಗೆ, ವಿವರಣೆ ಮಾರ್ಗವು ತನ್ನ ಹಿಂದಿನ ಫೇಲ್-ಓಪನ್
ವರ್ತನೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ (ಮೆಟಾ `{ skipped: true, reason: "no_permitted_vision_model" }`).
ಕೀ ಇಲ್ಲದ ವಿನಂತಿಗಳು ಮತ್ತು ಈ ನಿರ್ಬಂಧಗಳಿಲ್ಲದ ಕೀಗಳು ಹಿಂದಿನಂತೆಯೇ
ವರ್ತಿಸುತ್ತವೆ.

#### ಟಾಸ್ಕ್-ಅವೇರ್ ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್ (`modalityBridgeVisionTaskAware`)

ಡೀಫಾಲ್ಟ್ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`)
**ಕೊನೆಯ ಬಳಕೆದಾರ ಸಂದೇಶ**ದ ಪಠ್ಯವನ್ನು (500 ಅಕ್ಷರಗಳಿಗೆ ಕತ್ತರಿಸಲಾಗಿದೆ) ಮೂಲ
ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್ಗೆ ಸೇರಿಸುತ್ತದೆ, ಬಳಕೆದಾರರು ನಿಜವಾಗಿ ಕೇಳಿದ್ದಕ್ಕೆ ವಿವರಣೆಯನ್ನು
ಮಾರ್ಗದರ್ಶನ ಮಾಡುತ್ತದೆ (codex-vision-proxy ಮಾದರಿ) ಮತ್ತು ಗೋಚರಿಸುವ
ಪಠ್ಯವನ್ನು ಲಿಪ್ಯಂತರಿಸಲು ವಿಷನ್ ಮಾದರಿಯನ್ನು ಕೇಳುತ್ತದೆ. ಫ್ಲ್ಯಾಗ್ ಆಫ್ ಆಗಿದ್ದರೆ —
ಅಥವಾ ಬಳಕೆದಾರ ಪಠ್ಯವಿಲ್ಲದಿದ್ದರೆ — ಮೂಲ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಬದಲಾಯಿಸದೆ
ಬಳಸಲಾಗುತ್ತದೆ.

ವಿವರಣೆ ಸೆಲ್ಫ್-ಲೂಪ್ನ ಸ್ವಂತ OpenAI-ಹೊಂದಾಣಿಕೆಯ ವಿನಂತಿಯು
(`visionBridgeHelpers.ts` ನಲ್ಲಿ `callVisionModelSingle()`) ಯಾವಾಗಲೂ
`image_url.detail: "high"` ಅನ್ನು ವಿನಂತಿಸುತ್ತದೆ — ಷರತ್ತುರಹಿತವಾಗಿ, ಪ್ರತಿ
ಕಾಲರ್/ಪ್ರೊವೈಡರ್ಗಾಗಿ, ಯಾವುದೇ ಕ್ಲೈಂಟ್ ಸಿಗ್ನಲ್ನ ಮೇಲೆ ಗೇಟ್ ಆಗಿಲ್ಲ. ಕಡಿಮೆ-ವಿವರದ
ಮಾದರೀಕರಣವು ಈ ಪ್ರಾಂಪ್ಟ್ ಕೇಳುವ ಪಠ್ಯ-ಲಿಪ್ಯಂತರಣ ಕಾರ್ಯಕ್ಕೆ
OCR ನಿಖರತೆಯನ್ನು ಕುಂದಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಮೂಲ ಒಳಬರುವ ವಿನಂತಿಯು ಯಾವ
ವಿವರ ಮಟ್ಟವನ್ನು ಬಳಸಿದ್ದರೂ ವಿವರಣೆ ಕರೆಯು ಯಾವಾಗಲೂ
ಹೆಚ್ಚಿನ ವಿವರವನ್ನು ಕೇಳುತ್ತದೆ. ಇದು ಆಂತರಿಕ ವಿವರಣೆ ವಿನಂತಿ ದೇಹವನ್ನು ಮಾತ್ರ
ಪರಿಣಾಮ ಬೀರುತ್ತದೆ; ಪ್ರಾಥಮಿಕ ವಿನಂತಿಯಲ್ಲಿ OmniRoute ಕಾಲರ್ನ ಸ್ವಂತ
`image_url.detail` ಅನ್ನು ಹೇಗೆ ಫಾರ್ವರ್ಡ್ ಮಾಡುತ್ತದೆ ಎಂಬುದನ್ನು ಇದು ಬದಲಾಯಿಸುವುದಿಲ್ಲ — ಆ ಡೀಫಾಲ್ಟ್
ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ಪತ್ತೆಹಚ್ಚಿದ OpenCode ಕ್ಲೈಂಟ್ಗಳಿಗೆ ಮಾತ್ರ,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) ನಲ್ಲಿ. ವಿವರಣೆ
ಸೆಲ್ಫ್-ಲೂಪ್ನ Anthropic ವೈರ್-ಫಾರ್ಮ್ಯಾಟ್ ಶಾಖೆಯು `detail` ಕ್ಷೇತ್ರವನ್ನು
ಹೊಂದಿಲ್ಲ ಮತ್ತು ಎರಡೂ ಡೀಫಾಲ್ಟ್ಗಳಿಂದ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

#### ವಿವರಣೆ ಔಟ್ಪುಟ್ ಕ್ಯಾಪ್ (`modalityBridgeVisionMaxChars`)

| ಕೀ                             | ಡೀಫಾಲ್ಟ್ | ವ್ಯಾಪ್ತಿ           |
| ------------------------------ | -------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`      | `0` ಅಥವಾ 100–50000 |

`0` (ಡೀಫಾಲ್ಟ್) ಎಂದರೆ **ಕ್ಯಾಪ್ ಇಲ್ಲ** —
`callVisionModel()` ಹಿಂದಿರುಗಿಸಿದ ವಿವರಣೆಯನ್ನು ಬದಲಾಯಿಸದೆ ಹಾದುಹೋಗುತ್ತದೆ,
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ವರ್ತನೆಯನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ. 100–50000 ವ್ಯಾಪ್ತಿಯಲ್ಲಿನ ಯಾವುದೇ
ಮೌಲ್ಯವು ವಿವರಣೆಯನ್ನು `…` ಸರ್ಫಿಕ್ಸ್ನೊಂದಿಗೆ ಕತ್ತರಿಸುತ್ತದೆ, ಅದನ್ನು
`[Image N]: <description>` ಎಂದು ಮರಳಿ ಸೇರಿಸುವ ಮೊದಲು
(`src/lib/guardrails/visionBridge.ts` ನಲ್ಲಿ `VisionBridgeGuardrail.preCall()`).
ಡೌನ್ಸ್ಟ್ರೀಮ್ ಮಾದರಿಗೆ ಸಂಪೂರ್ಣ ಲಿಪ್ಯಂತರಣದ ಅಗತ್ಯವಿರುವ ವಿವರ-ಭಾರಿತ OCR
ಕಾರ್ಯಗಳಿಗೆ ಇದನ್ನು ಹೆಚ್ಚಿಸಿ; ಚಾಟಿ ವಿಷನ್ ಮಾದರಿಗಳಲ್ಲಿ ಟೋಕನ್ ಬಳಕೆಯನ್ನು ಮಿತಿಗೊಳಿಸಲು
ಇದನ್ನು ಕಡಿಮೆ ಮಾಡಿ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಕ್ಷೇತ್ರವು ವಿಷನ್ ಟ್ಯಾಬ್ನ Advanced ಪ್ಯಾನೆಲ್ನಲ್ಲಿದೆ
(`ModalityBridgeVisionTab.tsx` ನಲ್ಲಿ `modality-bridge-max-chars`) ಮತ್ತು 1 ಮತ್ತು 99 ನಡುವಿನ
ಯಾವುದೇ ಮೌಲ್ಯವನ್ನು 100 ಮಹಡಿಗೆ ಕ್ಲಾಂಪ್ ಮಾಡುತ್ತದೆ, ಸ್ಪಷ್ಟ `0` ಅನ್ನು ಮುಟ್ಟದೆ
ಬಿಡುತ್ತದೆ — `0` ಎಂಬುದು ತನ್ನದೇ ಆದ ಮಾನ್ಯ Zod ಮೌಲ್ಯ
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ಕೇವಲ "unset"
ಡೀಫಾಲ್ಟ್ ಅಲ್ಲ.

`callVisionModel` ಆಂತರಿಕವಾಗಿ ಫಾಲ್ಬ್ಯಾಕ್ ಆಗಬಹುದು, ಮತ್ತು ಪ್ರತಿ ಪ್ರಯತ್ನಕ್ಕೆ
ಕೀ ಮಾಡುವುದು ಕ್ಯಾಶೆಯನ್ನು ಛಿದ್ರಗೊಳಿಸುತ್ತದೆ. ವಿಫಲವಾದ ವಿವರಣೆಗಳನ್ನು ಎಂದಿಗೂ
ಕ್ಯಾಶೆ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಸೆಟ್ಟಿಂಗ್ಗಳು:

**2048px ಉದ್ದನೆಯ ಅಂಚು**ಗೆ ಇಳಿಸಲಾಗುತ್ತದೆ (OpenAI/Anthropic ಈಗಾಗಲೇ ಸರ್ವರ್-ಸೈಡ್ನಲ್ಲಿ
ಅನ್ವಯಿಸುವ ರಿಸೈಜ್ ಮಿತಿಗೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ), ಇದು ವಿಷನ್ ಮಾಡೆಲ್ ನೋಡುವುದನ್ನು
ಬದಲಾಯಿಸದೆ ಅಪ್ಲೋಡ್ ಬೈಟ್ಗಳು/ಲೇಟೆನ್ಸಿಯನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ. ರಿಸೈಜ್
`sharp` ಅನ್ನು ಬಳಸುತ್ತದೆ, ಡೈನಮಿಕ್ ಇಂಪೋರ್ಟ್ ಮೂಲಕ ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ: ಅದರ ನೇಟಿವ್
ಬೈನರಿ ಲೋಡ್ ಆಗಲು ವಿಫಲವಾಗುವ ಪ್ಲಾಟ್ಫಾರ್ಮ್ನಲ್ಲಿ, `normalizeDataUri()` **ಎಂದಿಗೂ
ಥ್ರೋ ಮಾಡುವುದಿಲ್ಲ** — ಅದು ಮೂಲ ಬೈಟ್ಗಳ ಪಾಸ್ಥ್ರೂಗೆ ಫಾಲ್ ಬ್ಯಾಕ್ ಆಗುತ್ತದೆ,
ಆದ್ದರಿಂದ ಡಿಸ್ಕ್ರೈಬ್/base64-ಪರಿವರ್ತನೆ ಮಾರ್ಗವು ಯಾವಾಗಲೂ ಕೆಲಸ ಮಾಡುತ್ತಿರುತ್ತದೆ.
ಚಿತ್ರವಲ್ಲದ ಬೈಟ್ಗಳು (ಡಿಕೋಡ್ ಮಾಡಬಹುದಾದ ಚಿತ್ರವನ್ನು ಹಿಂತಿರುಗಿಸದ ಫೆಚ್) ಸಹ
ಮುಟ್ಟದಂತೆ ಪಾಸ್ಥ್ರೂ ಮಾಡಲಾಗುತ್ತದೆ. ಈ ನಾರ್ಮಲೈಸೇಶನ್ ಬ್ರಿಡ್ಜ್ ತನ್ನ ಸೆಲ್ಫ್-ಕಾಲ್ಗಾಗಿ
ಫೆಚ್ ಮಾಡುವ ಚಿತ್ರಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿದೆ — ಇದನ್ನು ಕಾಲರ್ನ ಕಚ್ಚಾ ಪಾಸ್ಥ್ರೂ
ಪೇಲೋಡ್ಗೆ ಎಂದಿಗೂ ಅನ್ವಯಿಸಲಾಗುವುದಿಲ್ಲ, ಆಪ್ಟ್-ಇನ್-ಮಾತ್ರ ಮ್ಯೂಟೇಶನ್ ತತ್ವಕ್ಕೆ
ಹೊಂದಿಕೆಯಾಗಿ (ಕಠಿಣ ನಿಯಮ #20).

ಪೇಲೋಡ್ ಮುಟ್ಟಿರಲಿಲ್ಲ ಮತ್ತು ಮಾಡೆಲ್ ಸ್ವ್ಯಾಪ್ ಈಗಾಗಲೇ ಪ್ರತಿಕ್ರಿಯೆ ಬಾಡಿಯ `model`

`GET /api/modality-bridge/stats` (ಮ್ಯಾನೇಜ್ಮೆಂಟ್ ಆಥ್, `GET /api/settings` ಗೆ
ಸಮನಾದ ಟೈರ್) `vision`, `audio` ಮತ್ತು `video` ಗಾಗಿ ಇನ್-ಮೆಮೊರಿ ಪ್ರತಿ-ಮೊಡಾಲಿಟಿ

ಕಲ್ಪಿಸುವುದಿಲ್ಲ. `bridged` ಯಶಸ್ವಿ ಪರಿವರ್ತನೆಗಳಿಗೆ ಹಿಂಬದಿ-ಹೊಂದಾಣಿಕೆಯ ಅಲಿಯಾಸ್ ಆಗಿ
ಉಳಿದುಕೊಂಡಿದೆ; ವಿಫಲ ಪ್ರಯತ್ನಗಳು ಅದನ್ನು ಹೆಚ್ಚಿಸುವುದಿಲ್ಲ.
ಕೌಂಟರ್ಗಳು ವಿನ್ಯಾಸದಂತೆಯೇ ಪ್ರಾಸೆಸ್ ಮರುಪ್ರಾರಂಭದಲ್ಲಿ ರೀಸೆಟ್ ಆಗುತ್ತವೆ

ಟೈಮ್ಔಟ್/ಇಮೇಜ್/ಡಿಸ್ಕ್ರಿಪ್ಷನ್-ಲೆಂಗ್ತ್/ಕ್ಯಾಶೆ ಮಿತಿಗಳು, ರನ್ಟೈಮ್
ಕೌಂಟರ್ಗಳು ಮತ್ತು ಗಾರ್ಡ್ ಮಾಡಿದ ಸ್ಯಾಂಪಲ್ ವಿನಂತಿಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. Audio ಟ್ಯಾಬ್ ಸಹ
ಲೈವ್ ಆಗಿದೆ: ಅದು ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ, Auto ಸಹಿತ STT-ಮಾತ್ರ ಮಾಡೆಲ್ ಪಿಕ್ಕರ್,
ಟೈಮ್ಔಟ್/ಮ್ಯಾಕ್ಸ್-ಕ್ಲಿಪ್ ಮಿತಿಗಳು, ಆಡಿಯೊ ಕೌಂಟರ್ಗಳು ಮತ್ತು `input_audio` ಸ್ಯಾಂಪಲ್

FFmpeg/ffprobe ರನ್ಟೈಮ್ ಸ್ಥಿತಿಯನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ — ನಾಲ್ಕು ಸ್ಪಷ್ಟ UI ಸ್ಥಿತಿಗಳಲ್ಲಿ
ಒಂದು (ಪ್ರೋಬ್ ಪ್ರಗತಿಯಲ್ಲಿರುವಾಗ ಅಥವಾ ಪೂರ್ಣಗೊಳಿಸಲಾಗದಿದ್ದಾಗ `unknown`, ಪ್ರೋಬ್ ಅನ್ನು
ಕ್ಲೈಂಟ್-ಸೈಡ್ನಲ್ಲಿ ಬಿಟ್ಟುಬಿಡುವ ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಹೋಸ್ಟ್ನಲ್ಲಿ

FFmpeg/ffprobe ಆವೃತ್ತಿಗಳೊಂದಿಗೆ `available`) — ಎನೇಬಲ್/ಮಾಡೆಲ್/ಫ್ರೇಮ್/ವೀಡಿಯೊ/ಟೈಮ್ಔಟ್
ಮಿತಿಗಳನ್ನು ಕಾಯ್ದಿರಿಸುತ್ತದೆ, ಮಾಡೆಲ್ ಪಿಕ್ಕರ್ ಅನ್ನು ವಿಷನ್-ಸಮರ್ಥ ಮಾಡೆಲ್ಗಳಿಗೆ ಫಿಲ್ಟರ್
ಮಾಡುತ್ತದೆ ಮತ್ತು ವೀಡಿಯೊ ಕೌಂಟರ್ಗಳನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.

AI ಸೆಟ್ಟಿಂಗ್ಸ್ ಅಡಿಯಲ್ಲಿದ್ದ ಹಿಂದಿನ Vision Bridge ಕಾರ್ಡ್ ಈಗ ಹೊಸ ಪುಟಕ್ಕೆ
ಹೊಂದಾಣಿಕೆ ಲಿಂಕ್ ಆಗಿದೆ; ಅದು ಈಗ ಫಾರ್ಮ್ನ ಎರಡನೇ ನಕಲನ್ನು ಹೊಂದಿಲ್ಲ. Media Providers

ತೆಗೆದುಹಾಕದೆ.

### ಆಡಿಯೊ ಬ್ರಿಡ್ಜ್ (`audioBridge.ts`) — Modality Bridge PR-3

ಆಡಿಯೊ ಇನ್ಪುಟ್ ಅನ್ನು ಸ್ವೀಕರಿಸುವುದಾಗಿ ತಿಳಿದಿಲ್ಲದ ಗುರಿಯನ್ನು ತಲುಪುವ ಮೊದಲು
ಆಡಿಯೊ-ಹೊಂದಿರುವ ಚಾಟ್ ವಿನಂತಿಗಳನ್ನು ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡುತ್ತದೆ. ಇದು ಚಾಟ್ ವಿನಂತಿಯನ್ನು
ಎಂದಿಗೂ ರೀರೂಟ್ ಮಾಡುವುದಿಲ್ಲ: ಆಡಿಯೊ ಭಾಗಗಳನ್ನು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OpenAI-ಹೊಂದಾಣಿಕೆಯ
ಮಲ್ಟಿಪಾರ್ಟ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ ಟ್ರಾನ್ಸ್ಕ್ರೈಬ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಆಯ್ದ ಚಾಟ್ ಮಾಡೆಲ್
ಟೆಕ್ಸ್ಟ್ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ಗಳೊಂದಿಗೆ ಮುಂದುವರಿಯುತ್ತದೆ.

ಫ್ಲೋ:

1. `getResolvedModelCapabilities()` ಮೂಲಕ `supportsAudio` ಅನ್ನು ಪರಿಹರಿಸಿ. ಸ್ಪಷ್ಟ
   ಪ್ರೊವೈಡರ್-ರಿಜಿಸ್ಟ್ರಿ ಮೆಟಾಡೇಟಾ ಗೆಲ್ಲುತ್ತದೆ, ನಂತರ ಸ್ಥಿರ ಮಾಡೆಲ್ ಮೆಟಾಡೇಟಾ, ನಂತರ ಸಿಂಕ್
   ಮಾಡಲಾದ `modalities_input`. `audio` ಇಲ್ಲದ ಘೋಷಿತ ಇನ್ಪುಟ್ ಪಟ್ಟಿ `false` ಆಗುತ್ತದೆ; ಯಾವುದೇ
   ಸಾಮರ್ಥ್ಯ ಪುರಾವೆ ಇಲ್ಲದಿದ್ದರೆ `null` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. `false` ಮತ್ತು `null` ಎರಡೂ
   ಸಂಪ್ರದಾಯವಾದಿ ಬ್ರಿಜ್ ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ಆದರೆ `true` ಅದನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತದೆ.
2. `modalityBridgeAudio*` ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಪರಿಹರಿಸಿ ಮತ್ತು ಹಂಚಿಕೊಂಡ `detectMediaParts()`
   ಡಿಟೆಕ್ಟರ್ ಮೂಲಕ ಪ್ರತಿ ಸಂದೇಶದಿಂದ ಸ್ಪ್ಲೈಸ್ ಮಾಡಬಹುದಾದ ಟಾಪ್-ಲೆವೆಲ್
   ಆಡಿಯೊ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ. ಬೆಂಬಲಿತ ವೈರ್ ಆಕಾರಗಳು OpenAI `input_audio`, `audio_url`, ಮತ್ತು
   `source.media_type: "audio/*"`. ನೆಸ್ಟೆಡ್ ಆಡಿಯೊವನ್ನು ರೂಟಿಂಗ್ಗಾಗಿ ಪತ್ತೆಹಚ್ಚಲಾಗುತ್ತದೆ ಆದರೆ
   ಸ್ಪ್ಲೈಸ್ ಪಾತ್ ಮೂಲಕ ತೆಗೆದುಹಾಕಲಾಗುವುದಿಲ್ಲ. ಕೆಲಸವನ್ನು `modalityBridgeAudioMaxClips` ಮೂಲಕ
   ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ; ನಂತರದ ಭಾಗಗಳು ಮುಟ್ಟದಂತೆ ಉಳಿಯುತ್ತವೆ.
3. ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ `provider/model` ಅನ್ನು ಗೌರವಿಸಿ, ಅಥವಾ `selectAudioBridgeModel()`
   ಸ್ಥಿರ ಕ್ಯಾಟಲಾಗ್ ಕ್ರಮದಲ್ಲಿ `AUDIO_TRANSCRIPTION_PROVIDERS` ಅನ್ನು ಸಂಚರಿಸಿ
   ಬಳಸಬಹುದಾದ ಸಕ್ರಿಯ ಪ್ರೊವೈಡರ್ ರುಜುವಾತು ಹೊಂದಿರುವ ಮೊದಲ ಮಾಡೆಲ್ ಅನ್ನು
   ಆಯ್ಕೆಮಾಡಲು ಅನುಮತಿಸಿ.
4. `callAudioTranscription()` base64/data-URI ಆಡಿಯೊವನ್ನು ಮಲ್ಟಿಪಾರ್ಟ್
   `file` ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ, ಅಥವಾ DNS ಪಿನ್ನಿಂಗ್ ಮತ್ತು 25 MB ಮಿತಿಯೊಂದಿಗೆ
   ಪಬ್ಲಿಕ್-ಓನ್ಲಿ ಔಟ್ಬೌಂಡ್ ಗಾರ್ಡ್ ಮೂಲಕ ರಿಮೋಟ್ `audio_url` ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ.
   ನಂತರ ಅದು ಫೈಲ್ ಮತ್ತು ಆಯ್ದ ಮಾಡೆಲ್ ಅನ್ನು `resolveSelfLoopBearer()` ಮೂಲಕ ಪ್ರಮಾಣೀಕರಿಸಲಾದ
   ಸ್ಥಳೀಯ `/v1/audio/transcriptions` ಸೆಲ್ಫ್-ಲೂಪ್ಗೆ POST ಮಾಡುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
   ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ ರೂಟ್ ಸಾಮಾನ್ಯ ರುಜುವಾತು ಲುಕಪ್, ಕೂಲ್ಡೌನ್/ರೇಟ್-ಲಿಮಿಟ್
   ನಿರ್ವಹಣೆ ಮತ್ತು ಪ್ರೊವೈಡರ್ ಡಿಸ್ಪ್ಯಾಚ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
5. ಯಶಸ್ವಿ ಕರೆಗಳು ತಮ್ಮ ಭಾಗಗಳನ್ನು `[Audio N]: <transcript>` ನಿಂದ ಬದಲಾಯಿಸುತ್ತವೆ. ಕರೆಗಳು
   `Promise.allSettled` ನೊಂದಿಗೆ ಚಲಾಯಿಸಲಾಗುತ್ತವೆ: ವೈಯಕ್ತಿಕ ವಿಫಲತೆಯು ಆ ಮೂಲ
   ಆಡಿಯೊ ಭಾಗವನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ (#4012 ಕಾಂಟ್ರಾಕ್ಟ್). ಪ್ರತಿ ಕರೆ ವಿಫಲವಾದರೆ ಮತ್ತು ಗುರಿಯು
   `supportsAudio === false` ಎಂದು ಸಾಬೀತಾದರೆ, ಭಾಗಗಳು
   `[Audio N]: (unavailable — no STT provider connected)` ಆಗುತ್ತವೆ
   (#8430 ಕಾಂಟ್ರಾಕ್ಟ್). ಅಜ್ಞಾತ ಗುರಿಗೆ (`null`), ಸಂಪೂರ್ಣ-ವಿಫಲತೆಯ ಫಲಿತಾಂಶವು
   ಮುಟ್ಟದಂತೆ ಉಳಿಯುತ್ತದೆ. ಬಳಸಬಹುದಾದ STT ರುಜುವಾತು ಇಲ್ಲದ ಸಾಬೀತಾದ ಟೆಕ್ಸ್ಟ್-ಓನ್ಲಿ
   ಗುರಿಯು ನೆಟ್ವರ್ಕ್ ಕರೆಯನ್ನು ಮಾಡದೆಯೇ ಅದೇ ಸ್ಪಷ್ಟ ಸ್ಟಬ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ.

ಯಶಸ್ವಿ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ಗಳು ಪ್ರೊಸೆಸ್-ವೈಡ್ Modality Bridge LRU/TTL ಕ್ಯಾಶ್ ಅನ್ನು ಬಳಸುತ್ತವೆ.
ಕೀಲಿಯು ಆಡಿಯೊ ರೆಫರೆನ್ಸ್, ಸ್ಥಿರ `audio-transcription` ಆಪರೇಷನ್
ಲೇಬಲ್ ಮತ್ತು ಆಯ್ದ STT ಮಾಡೆಲ್ ಅನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ; ವಿಫಲತೆಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್
ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಆಡಿಯೊ ಪ್ರಯತ್ನಗಳು ಹಂಚಿಕೊಂಡ `bridged`, `cacheHits`, `failures`, ಮತ್ತು
`lastUsedAt` ಕೌಂಟರ್ಗಳನ್ನು ನವೀಕರಿಸುತ್ತವೆ. ರೂಪಾಂತರಿತ ಪ್ರತಿಕ್ರಿಯೆಗಳು
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ಅನ್ನು ಹೊಂದಿರುತ್ತವೆ; ಮುಟ್ಟದ
ವಿನಂತಿಗಳು Audio Bridge ವಿಭಾಗವನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

ರನ್ಟೈಮ್ ಸೆಟ್ಟಿಂಗ್ಗಳು DB-ಬ್ಯಾಕ್ಡ್ ಮತ್ತು Zod-ವ್ಯಾಲಿಡೇಟೆಡ್ ಆಗಿವೆ:

| ಕೀಲಿ                          | ಡೀಫಾಲ್ಟ್ | ವ್ಯಾಪ್ತಿ        |
| ----------------------------- | -------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`   | —               |
| `modalityBridgeAudioModel`    | `""`     | ಆಟೋ ಅಥವಾ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10            |

ಹಂಚಿಕೊಂಡ ಕ್ಯಾಶ್ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ಮತ್ತು `modalityBridgeCacheMaxEntries` ಮೂಲಕ ನಿಯಂತ್ರಣದಲ್ಲಿರುತ್ತದೆ.

### ವೀಡಿಯೊ ಬ್ರಿಜ್ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ತಿಳಿದಿರುವ ನೇಟಿವ್ ವೀಡಿಯೊ ಬೆಂಬಲವಿಲ್ಲದ ಗುರಿಯನ್ನು ಕರೆಯುವ ಮೊದಲು Chat Completions `messages` ಮತ್ತು Responses
API `input` ನಲ್ಲಿ ಟಾಪ್-ಲೆವೆಲ್ ವೀಡಿಯೊ ಭಾಗಗಳನ್ನು ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡುತ್ತದೆ.
ಬೆಂಬಲಿತ ಆಕಾರಗಳು `input_video`, `video_url`, `video_source`, HTTPS URLಗಳು,
ಮತ್ತು `data:video/*;base64,...` ಡೇಟಾ URIಗಳು. ಟೆಕ್ಸ್ಟ್ನಲ್ಲಿನ ಸರಳ ಫೈಲ್ಹೆಸರುಗಳನ್ನು
ವೀಡಿಯೊ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ವಿನಂತಿ ಟ್ರಾವರ್ಸಲ್,
ಸಾಮರ್ಥ್ಯ/ಪಾಲಿಸಿ ಪರಿಶೀಲನೆ, ಪ್ರತಿ-ವಿನಂತಿ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು
ಹೊಂದಿದೆ. ಪ್ರತಿ-ವೀಡಿಯೊ ಕೆಲಸ — ಸ್ವಾಧೀನ, ಸಂಪೂರ್ಣ-ಫಲಿತಾಂಶ ಕ್ಯಾಶ್, ಫ್ರೇಮ್
ಸೀಕ್ವೆನ್ಸ್ ಅನ್ನು ವಿವರಿಸುವುದು (ಇದು ಯಾವುದೇ ಕಾಲರ್-ಘೋಷಿತ ಆಡಿಯೊ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಅನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ), ಮತ್ತು ಪ್ರತಿ-ಪ್ರಯತ್ನ
ಮೆಟ್ರಿಕ್ಸ್/ಅಬಾರ್ಟ್/ಕ್ಲೀನಪ್ — `videoBridgePipeline.ts` ನಲ್ಲಿರುವ `processVideoPart` ಹಿಂದೆ ಮರೆಯಾಗಿದೆ,
ಇದನ್ನು `preCall` ಲೂಪ್ ಒಳಗೆ ಪ್ರತಿ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಒಮ್ಮೆ
ಕರೆಯಲಾಗುತ್ತದೆ. ಆ ಮಾಡ್ಯೂಲ್ ಸ್ಪಷ್ಟ ಪೋರ್ಟ್ ಗಡಿಗಳಾದ `VideoMediaBrokerPort`
(ಬೈಟ್ಗಳನ್ನು ಸ್ವಾಧೀನಪಡಿಸಿಕೊಳ್ಳುವುದು ಮತ್ತು ಸ್ಯಾಂಪಲ್ ಮಾಡಿದ ಫ್ರೇಮ್ಗಳನ್ನು ಹೊರತೆಗೆಯುವುದು), `VideoAudioTranscriptionPort`
(ಕಾಲರ್-ಘೋಷಿತ ಆಡಿಯೊ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಅನ್ನು ಸ್ಯಾಂಪಲ್ ಮಾಡಿದ ಕ್ಯಾಪ್ಷನ್ಗಳೊಂದಿಗೆ ಸಂಯೋಜಿಸುವುದು), ಮತ್ತು
`VideoDrilldownPort` (ಫ್ರೇಮ್ ಡ್ರಿಲ್-ಡೌನ್ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಗಡಿ; ಇನ್ನೂ
`processVideoPart` ಗೆ ವೈರ್ ಮಾಡಲಾಗಿಲ್ಲ — ಇಂದು ಪ್ರತ್ಯೇಕ `/api/modality-bridge/video/drilldown`
ರೂಟ್ ಮಾತ್ರ ಡ್ರಿಲ್-ಡೌನ್ ಎಂಟ್ರಿಗಳನ್ನು ಬರೆಯುತ್ತದೆ) ಅನ್ನು ಸಹ ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ.

ಸಾರ್ವಜನಿಕ `/v1` ವಿನಂತಿ ಪಾತ್ ಎಂದಿಗೂ ಸಬ್ಪ್ರೊಸೆಸ್ ಅನ್ನು ಇಂಪೋರ್ಟ್ ಮಾಡುವುದಿಲ್ಲ ಅಥವಾ ಕರೆಯುವುದಿಲ್ಲ. ರಿಮೋಟ್
ವೀಡಿಯೊಗಳನ್ನು 50 MiB ಮಿತಿಯೊಳಗೆ ಡೌನ್ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ; ಇನ್ಲೈನ್ base64 ವೀಡಿಯೊಗಳು
ಸಂಪ್ರದಾಯವಾದಿ 36 MiB ಡೀಕೋಡ್ ಮಾಡಿದ ಪ್ರತಿ-ವೀಡಿಯೊ ಮಿತಿಯನ್ನು ಹೊಂದಿರುತ್ತವೆ, ಇದರಿಂದ
ಮಾಡೆಲ್/ಸಂದೇಶಗಳು/ಫ್ರೇಮಿಂಗ್ ಎನ್ವಲಪ್ 50 MiB ಸಾರ್ವಜನಿಕ JSON ವಿನಂತಿ
ಪ್ರವೇಶ ಮಿತಿಯೊಳಗೆ ಉಳಿಯಬಹುದು. ಇನ್ಲೈನ್
ಉದ್ದ ಮತ್ತು ಡೀಕೋಡ್-ಗಾತ್ರದ ಅಂದಾಜುಗಳನ್ನು ಅಲೊಕೇಶನ್ ಮೊದಲು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಆರಂಭಿಕ ರಿಮೋಟ್
URL ಮತ್ತು ಪ್ರತಿ ರೀಡೈರೆಕ್ಟ್ನಲ್ಲಿ HTTPS ಅಗತ್ಯವಿದೆ, ಇದಕ್ಕಾಗಿ DNS ಪಿನ್ನಿಂಗ್ ಹೊಂದಿರುವ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಪಬ್ಲಿಕ್-ಓನ್ಲಿ ಔಟ್ಬೌಂಡ್ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ. ನಂತರ ಬೈಟ್ಗಳು ನಿಖರವಾದ ಆಂತರಿಕ
`POST /api/modality-bridge/video/extract` ಬ್ರೋಕರ್ ಗಡಿಯನ್ನು ದಾಟುತ್ತವೆ. ಆ ರೂಟ್
`LOCAL_ONLY` ಮತ್ತು `SPAWN_CAPABLE` ಎರಡೂ ಆಗಿದೆ, ಕೇವಲ ಪ್ರತಿ-ಪ್ರೊಸೆಸ್ ಪ್ರಮಾಣೀಕೃತ,
ಟ್ರಸ್ಟೆಡ್-ಲೂಪ್ಬ್ಯಾಕ್ ವಿನಂತಿಯನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸುತ್ತದೆ, ಮತ್ತು ಎಂದಿಗೂ URL, ಫೈಲ್ಸಿಸ್ಟಮ್
ಪಾತ್, ಎಕ್ಸಿಕ್ಯೂಟಬಲ್ ಅಥವಾ ಆರ್ಗ್ಯುಮೆಂಟ್ ಪಟ್ಟಿಯನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. API
ಬಾಡಿ-ಸೈಜ್ ಪೈಪ್ಲೈನ್ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ನ ಇಂಕ್ರಿಮೆಂಟಲ್ ಬಾಡಿ
ರೀಡರ್ ಸ್ವತಂತ್ರವಾಗಿ 50 MiB ಬ್ರೋಕರ್ ಇನ್ಪುಟ್ ಮಿತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಅದರ ಬೌಂಡೆಡ್ ಕ್ಯೂ
ಒಮ್ಮೆಗೆ ಒಂದು ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್ ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ, ನಾಲ್ಕು ಪೆಂಡಿಂಗ್ ಜಾಬ್ಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ, ಮತ್ತು

OmniRoute FFmpeg ಅನ್ನು ಬಂಡಲ್ ಮಾಡುವುದಿಲ್ಲ ಮತ್ತು ಕಸ್ಟಮ್ ಎಕ್ಸಿಕ್ಯೂಟಬಲ್ ಪಾಥ್ ಅನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಕ್ಯಾಪ್ಷನ್ ಮಾಡುವ ಮೊದಲು, ಬ್ರಿಜ್ ಸಂಪ್ರದಾಯವಾದಿ ದೃಶ್ಯ ಡಿಡುಪ್ಲಿಕೇಶನ್ ಪಾಸ್ ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ: ಪ್ರತಿಯೊಂದು JPEG ಅನ್ನು 16×16 ಗ್ರೇಸ್ಕೇಲ್ ಬಫರ್ಗೆ ಇಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಕೇವಲ ಕೊನೆಯದಾಗಿ ಉಳಿಸಿಕೊಂಡ ಫ್ರೇಮ್ನೊಂದಿಗೆ ಹೋಲಿಸಲಾಗುತ್ತದೆ. ಒಂದು ಫ್ರೇಮ್ಗಿಂತ ಹೆಚ್ಚಿನ ವಿನಂತಿಸಿದ ಕ್ಯಾಪ್ಷನ್ ಬಜೆಟ್ಗಾಗಿ, ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್ ಆ ಬಜೆಟ್ನ ಎರಡರಷ್ಟು ಮಿತೀಕೃತ ಉಮ್ಮೇದವಾರ ಪೂಲ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ ಮತ್ತು ಎಂದಿಗೂ 16 ಫ್ರೇಮ್ಗಳಿಗಿಂತ ಹೆಚ್ಚಾಗುವುದಿಲ್ಲ. ವಿನಂತಿಸಿದ ಮಿತಿಯನ್ನು ಡಿಡುಪ್ಲಿಕೇಶನ್ ನಂತರ ಮಾತ್ರ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ, ಬಜೆಟ್ ಕನಿಷ್ಠ ಎರಡು ಇದ್ದಾಗ ಅಂತಿಮ ವಿರಳೀಕರಣದ ಸಮಯದಲ್ಲಿ ಮೊದಲ ಮತ್ತು ಅಂತಿಮ ಆಯ್ದ ಉಮ್ಮೇದವಾರಗಳನ್ನು ಸಂರಕ್ಷಿಸಲಾಗುತ್ತದೆ. ಆವೃತ್ತಿಗೊಳಿಸಿದ `grayscale-16x16-mean-cells-v2` ನೀತಿಯು ಸರಾಸರಿ ಲೂಮಾ ಡೆಲ್ಟಾ ಮತ್ತು ಸಾಮಾನ್ಯೀಕೃತ ಡೆಲ್ಟಾ ಕನಿಷ್ಠ 0.05 ಆಗಿರುವ ಥಂಬ್ನೇಲ್ ಸೆಲ್ಗಳ ಅನುಪಾತದಲ್ಲಿ ದೊಡ್ದದನ್ನು ಬಳಸುತ್ತದೆ. ಡುಪ್ಲಿಕೇಟ್ ಮಿತಿಯು ಸ್ಥಿರಾಂಕ 0.04 ಆಗಿದೆ, ಇದನ್ನು ರನ್ಟೈಮ್ ಸೆಟ್ಟಿಂಗ್ ಆಗಿ ಬಹಿರಂಗಪಡಿಸದೆ ಊಹಿಸಬಹುದಾದ ಸ್ವಭಾವಕ್ಕಾಗಿ ಆಯ್ದುಕೊಳ್ಳಲಾಗಿದೆ. ಈ ದ್ವಿತೀಯಕ ಹೈ-ಕಾಂಟ್ರಾಸ್ಟ್ ಸಂಕೇತವು ಸರಾಸರಿ-ಮಾತ್ರ ಹೋಲಿಕೆಯು ಮರೆಮಾಚಬಹುದಾದ ಸಣ್ಣ ಚಲನೆ ಮತ್ತು ಗೋಚರ ಪಠ್ಯ ಬದಲಾವಣೆಗಳನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ. ಹೋಲಿಕೆದಾರ ಅಥವಾ ಡಿಕೋಡರ್ ದೋಷಗಳು ಫೇಲ್ ಓಪನ್ ಆಗುತ್ತವೆ ಮತ್ತು ಕವರೇಜ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಔಟ್ಪುಟ್ ಮೆಟಾಡೇಟಾವು ಹೊರತೆಗೆದ ಉಮ್ಮೇದವಾರಗಳು, ಯಶಸ್ವಿಯಾಗಿ ಬಳಸಿದ ಫ್ರೇಮ್ಗಳು ಮತ್ತು ಕೈಬಿಟ್ಟ ದೃಶ್ಯ ಡುಪ್ಲಿಕೇಟ್ಗಳನ್ನು ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ.

ಸ್ಪಷ್ಟವಾಗಿ ಗುರುತಿಸಿದ ವೀಡಿಯೊ ಭಾಗವು ಟೈಮ್ಸ್ಟಾಂಪ್ ಮಾಡಿದ ಕಾಂಟಾಕ್ಟ್ ಶೀಟ್ ಅನ್ನು ವಿನಂತಿಸಬಹುದು. ಬ್ರಿಜ್ ಗರಿಷ್ಠ 4-ಕಾಲಮ್, 16-ಫ್ರೇಮ್ JPEG ಗ್ರಿಡ್ ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು 512-ಪಿಕ್ಸೆಲ್ ಸೆಲ್ ತನ್ನ ಮೂಲ ಟೈಮ್ಸ್ಟಾಂಪ್ ಅನ್ನು ಹೈ-ಕಾಂಟ್ರಾಸ್ಟ್ ಕೆಳಗಿನ ಬ್ಯಾಂಡ್ನಲ್ಲಿ ಬರ್ನ್ ಮಾಡುತ್ತದೆ, ಆದರೆ ಅದೇ ಟೈಮ್ಸ್ಟಾಂಪ್ಗಳು ಡೌನ್ಸ್ಟ್ರೀಮ್ ಸಂಬಂಧ ಮತ್ತು ಆಡಿಟ್ಗಾಗಿ ಪಠ್ಯ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಉಳಿಯುತ್ತವೆ. ಸಂಪೂರ್ಣ JPEG 32 MiB ನಲ್ಲಿ ಮಿತಿಯಾಗಿರುತ್ತದೆ. `sharp` ಗ್ರಿಡ್ ಅನ್ನು ಡಿಕೋಡ್ ಮಾಡಲು ಅಥವಾ ರಚಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ, ಬ್ರಿಜ್ ವೈಯಕ್ತಿಕ JPEG ಫ್ರೇಮ್ಗಳಿಗೆ ಹಿಂದಿರುಗುತ್ತದೆ; ಕ್ಲಯಂಟ್ ಅಬಾರ್ಟ್ ಇನ್ನೂ ಶೀಟ್ ಕಾರ್ಯಾಚರಣೆಯ ಮೂಲಕ ಪ್ರಸಾರವಾಗುತ್ತದೆ.

ಪ್ರಮೋಶನ್ ಪುರಾವೆಯನ್ನು ಸಿಂಥೆಟಿಕ್ ಕಂಪೋಸಿಷನ್ ಮೈಕ್ರೋಬೆಂಚ್ಮಾರ್ಕ್ನಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ. `scripts/perf/video-bridge-contact-sheet-eval.ts` ನಿಜವಾದ OpenAI-ಹೊಂದಾಣಿಕೆಯ ವಿಷನ್ ಮಾದರಿಗಳಿಗಾಗಿ ಸ್ಕೀಮಾ-ಆವೃತ್ತಿಗೊಳಿಸಿದ A/B ಹಾರ್ನೆಸ್ ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. ಇದು ಪ್ರೊವೈಡರ್-ವರದಿ ಮಾಡಿದ ಟೋಕನ್ಗಳು, ಎಂಡ್-ಟು-ಎಂಡ್ ವಾಲ್ ಲೆಟೆನ್ಸಿ (ಶೀಟ್ ಕಂಪೋಸಿಷನ್ ಸೇರಿದಂತೆ), ಮಾಡೆಲ್-ಕಾಲ್ ಸಂಖ್ಯೆ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್-ವ್ಯಾಖ್ಯಾನಿತ ಫ್ಯಾಕ್ಟ್ ರಿಟೆನ್ಷನ್ ಅನ್ನು ಅಳೆಯುತ್ತದೆ. ಕಚ್ಚಾ ಮಾದರಿ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ವರದಿಗೆ ಬರೆಯಲಾಗುವುದಿಲ್ಲ; ಕೇವಲ SHA-256 ಡೈಜೆಸ್ಟ್ಗಳು ಮತ್ತು ಹೊಂದಾಣಿಕೆಯಾದ ಫ್ಯಾಕ್ಟ್ ID ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. `--execute-real` ಅನ್ನು ರವಾನಿಸದ ಹೊರತು ಮತ್ತು `--model`, `OMNIROUTE_BASE_URL`, ಮತ್ತು `OMNIROUTE_API_KEY` ಕಾನ್ಫಿಗರ್ ಮಾಡದ ಹೊರತು ಹಾರ್ನೆಸ್ ಯಾವುದೇ ನೆಟ್ವರ್ಕ್ ಅಥವಾ ಪಾವತಿಸಿದ ಮಾದರಿ ಕರೆಯನ್ನು ಮಾಡುವುದಿಲ್ಲ. ಆ ಸ್ಪಷ್ಟ ನಿಜವಾದ ರನ್ ಇಲ್ಲದೆ, ಅದರ ಮಷಿನ್-ಓದಬಲ್ಲ ತೀರ್ಪು `HOLD` ಆಗಿ ಉಳಿಯುತ್ತದೆ; ಸಿಂಥೆಟಿಕ್ ಪೇಲೋಡ್/ಕಾಲ್-ಕೌಂಟ್ ಅಳತೆಗಳು ಮಾತ್ರ ಪ್ರಮೋಶನ್ ಪುರಾವೆಯಾಗುವುದಿಲ್ಲ.

ಕಾಲರ್ಗಳು ಈಗಾಗಲೇ ಜೋಡಿಸಿದ ಪಠ್ಯವನ್ನು ಹೊಂದಿದ್ದಾಗ, ಬೆಂಬಲಿತ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಐಚ್ಛಿಕ `transcript.cues` ಅರ್ರೆ ಅನ್ನು ಲಗತ್ತಿಸಬಹುದು. ಪ್ರತಿಯೊಂದು ಕ್ಯೂ `text`, ಪ್ರೋಬ್ ಮಾಡಿದ ಅವಧಿಯೊಳಗೆ ಪರಿಮಿತ `start`/`end` ಮಧ್ಯಂತರ ಮತ್ತು ವೈಟ್ಲಿಸ್ಟ್ ಮಾಡಿದ `source` (`client`, `embedded`, ಅಥವಾ `audio-bridge`) ಅನ್ನು ಹೊಂದಿರಬೇಕು; `confidence` ಡೀಫಾಲ್ಟ್ ಆಗಿ `1` ಆಗಿದೆ ಮತ್ತು `0` ಮತ್ತು `1` ನಡುವೆ ಉಳಿಯಬೇಕು. ನಿಖರ ಡುಪ್ಲಿಕೇಟ್ ಕ್ಯೂಗಳನ್ನು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸಲಾಗುತ್ತದೆ. OmniRoute ಈ ಮೆಟಾಡೇಟಾದಿಂದ ಎಂದಿಗೂ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ ಅನ್ನು ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ: ಮೌಲ್ಯೀಕರಿಸಿದ ಕ್ಯೂಗಳನ್ನು ಮೂಲ, ವಿಶ್ವಾಸಾರ್ಹತೆ ಮತ್ತು ಮಧ್ಯಂತರದೊಂದಿಗೆ ವಿವರಿಸಿದ ಫಲಿತಾಂಶಕ್ಕೆ ನಕಲಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ಫ್ರೇಮ್ ಕ್ಯಾಪ್ಷನ್ಗಳ ಜೊತೆಗೆ ಅವಿಶ್ವಾಸಾರ್ಹ ವೀಕ್ಷಣೆಗಳಾಗಿ ನಿರೂಪಿಸಲಾಗುತ್ತದೆ. ಅಮಾನ್ಯ, ವ್ಯಾಪ್ತಿಯ ಹೊರಗಿನ, ಅಥವಾ ಮೂಲ-ರಹಿತ ಪಠ್ಯವನ್ನು ಕ್ಯಾಪ್ಷನ್ ಸ್ಟ್ರೀಮ್ಗೆ ಬೆರೆಸುವ ಬದಲು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. ಎರಡೂ ರಿಕ್ವೆಸ್ಟ್-ಬಾಡಿ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಚಾನೆಲ್ಗಳು ಸಪ್ಲೈ ಮಾಡಿದ ಮೂಲವನ್ನು `client` ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತವೆ, ಸ್ವಯಂ-ಘೋಷಿತ `embedded` ಅಥವಾ `audio-bridge` ಲೇಬಲ್ಗಳನ್ನು ಸೇರಿದಂತೆ. ಸರ್ವರ್-ಒಡೆತನದ ಅಡಾಪ್ಟರ್ ಮಾತ್ರ ಕೋಡ್-ಮಾತ್ರ `trustedSource` ಆರ್ಗ್ಯುಮೆಂಟ್ ಮೂಲಕ ಆ ವಿಶ್ವಾಸಾರ್ಹ ಲೇಬಲ್ಗಳನ್ನು ನಿಯೋಜಿಸಬಹುದು; ರಿಕ್ವೆಸ್ಟ್ JSON ಫೀಲ್ಡ್ ಆ ಆರ್ಗ್ಯುಮೆಂಟ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಪಠ್ಯವು ಅದರ ಮೂಲವನ್ನು ಲೆಕ್ಕಿಸದೆ ಅವಿಶ್ವಾಸಾರ್ಹ ಮೀಡಿಯಾ-ಪಡೆದ ವಿಷಯವಾಗಿ ಉಳಿಯುತ್ತದೆ ಮತ್ತು ಎಂದಿಗೂ ಅಧೀಕರಣವನ್ನು ನಿರ್ಧರಿಸಬಾರದು.

ಸುಧಾರಿತ ಕಾಲರ್ ಅದೇ ವೀಡಿಯೊಗಾಗಿ `audioTranscript` ಟ್ರ್ಯಾಕ್ ಅನ್ನು ಒದಗಿಸಬಹುದು; ಇದನ್ನು ಕ್ಲಯಂಟ್-ಒದಗಿಸಿದ ಪಠ್ಯವಾಗಿ ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ, ಸರ್ವರ್ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ನ ಪುರಾವೆಯಾಗಿ ಅಲ್ಲ. ಫ್ಯೂಷನ್ ಸೀಮ್ ಒಂದೇ ಗಡುವು ಮತ್ತು ಅಬಾರ್ಟ್ ಸಿಗ್ನಲ್ ಅಡಿಯಲ್ಲಿ ದೃಶ್ಯ ಮತ್ತು ಆಡಿಯೊ ವೀಕ್ಷಣೆಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ, ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ಟೈಮ್ಲೈನ್ನಲ್ಲಿ ಕ್ರಮಗೊಳಿಸುತ್ತದೆ, ನಿಖರ ಡುಪ್ಲಿಕೇಟ್ಗಳನ್ನು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಕೇವಲ ಒಂದು ಬದಿ ಯಶಸ್ವಿಯಾದಾಗ ಭಾಗಶಃ ಫಲಿತಾಂಶವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಅಮಾನ್ಯ `audioTranscript` ಆ ಭಾಗಶಃ ಫಲಿತಾಂಶಕ್ಕೆ ಇಳಿಯುತ್ತದೆ — ದೃಶ್ಯ ವಿವರಣೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ ಮತ್ತು ಆಡಿಯೊ ಬ್ರಾಂಚ್ ಸ್ಯಾನಿಟೈಜ್ ಮಾಡಿದ ವೈಫಲ್ಯ ಕೋಡ್ ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ — ಇಡೀ ವೀಡಿಯೊವನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು. ಪ್ರತಿ-ಬ್ರಾಂಚ್ ಲಭ್ಯತೆ, ಭಾಗಶಃ ಫ್ಲ್ಯಾಗ್ ಮತ್ತು ಸ್ಯಾನಿಟೈಜ್ ಮಾಡಿದ ವೈಫಲ್ಯ ಕೋಡ್ಗಳನ್ನು ವಿವರಿಸಿದ ಫಲಿತಾಂಶದಲ್ಲಿ, ಗಾರ್ಡ್ರೇಲ್ ಮೆಟಾಡೇಟಾದಲ್ಲಿ (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), ಫಲಿತಾಂಶ-ಕ್ಯಾಶೆ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ಬ್ರಿಜ್ ಫ್ಯೂಷನ್ ಕೌಂಟರ್ಗಳಲ್ಲಿ ಸಂರಕ್ಷಿಸಲಾಗುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ ವೀಡಿಯೊ ಬ್ರಿಜ್ ಪಾತ್ ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಅನ್ನು ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ ಅಥವಾ ಎರಡನೇ ಮೀಡಿಯಾ ನಕಲನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ; ಆ ಸ್ಪಷ್ಟ ಟ್ರ್ಯಾಕ್ ಇಲ್ಲದೆ, ಅದು ವೀಡಿಯೊ-ಮಾತ್ರವಾಗಿ ಉಳಿಯುತ್ತದೆ.

| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` ಜೆನೆರಿಕ್ ಕ್ಯಾಪ್ಷನ್ಗಳನ್ನು ಉಳಿಸುತ್ತದೆ; `focused` ಬೌಂಡಡ್, ಅವಿಶ್ವಾಸಾರ್ಹ ಲೇಟಸ್ಟ್-ಯೂಸರ್ ಕಾಂಟೆಕ್ಸ್ಟ್ ಬಳಸುತ್ತದೆ  |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge ಮಾಡೆಲ್ ಅನ್ನು ಆನುಕ್ರಮಿಸುತ್ತದೆ                                                                      |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                            |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, ಅಥವಾ ಪ್ರopoರ್ಷನಲ್ `segment_aware`; ಡಿಟೆಕ್ಟರ್ ವಿಫಲತೆ `uniform` ಗೆ ಫಾಲ್ ಬ್ಯಾಕ್ ಆಗುತ್ತದೆ |

120 ಸೆಕೆಂಡುಗಳಿಗಿಂತ ಮೇಲಿನ ಲెಗಸಿ ಪರ್ಸಿಸ್ಟೆಡ್ Video ಟೈಮ್ಔಟ್ ಮೌಲ್ಯಗಳನ್ನು
ಬ್ರೋಕರ್ ಡೆಡ್ಲೈನ್ಗೆ ಕ್ಲಾಂಪ್ ಮಾಡಲಾಗುತ್ತದೆ; ಆ ಮಿತಿಗಿಂತ ಮೇಲಿನ ಹೊಸ ಸೆಟ್ಟಿಂಗ್ಗಳ ಬರಹಗಳನ್ನು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ.
`GET /api/modality-bridge/video/runtime` ಗೆ ಪ್ರಮಾಣೀಕರಣ ಅಥವಾ ರನ್ಟೈಮ್ ಪ್ರೋಬಿಂಗ್ಗೆ ಮೊದಲು ವಿಶ್ವಾಸಾರ್ಹ ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಲಾದ ಲೂಪ್ಬ್ಯಾಕ್
ಲೊಕಾಲಿಟಿ ಬೇಕಾಗುತ್ತದೆ, ನಂತರ ಮ್ಯಾನೇಜ್ಮೆಂಟ್
ಅಥ್ ಬೇಕಾಗುತ್ತದೆ. ರನ್ಟೈಮ್ ಲಭ್ಯವಿಲ್ಲದಿದ್ದಾಗ ಇದು ಕೇವಲ `available`, ಸ್ಯಾನಿಟೈಜ್ ಮಾಡಲಾದ FFmpeg/ffprobe ಆವೃತ್ತಿಗಳು ಮತ್ತು ಸ್ಥಿರ
ಕಾರಣವನ್ನು ಮಾತ್ರ ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಆಂತರಿಕ ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್ ಎಂಡ್ಪಾಯಿಂಟ್
ಸಾರ್ವಜನಿಕ ಅಪ್ಲೋಡ್ API ಅಲ್ಲ: ಕ್ಯೂ ಸ್ಯಾಚurೇಶನ್ `503` ಜೊತೆಗೆ `Retry-After` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ, ಕಾಲರ್
ಡಿಸ್ಕನెక్ట್ `499` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ, ಮತ್ತು ಸ್ಥಿರ ಬ್ರೋಕರ್ ಡೆಡ್ಲೈನ್ `504` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಪರಿವರ್ತಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆಗಳು ಕೇಂದ್ರೀಯ
`x-omniroute-modality-bridge` ಹೆಡರ್ಗೆ
`video->text;model=<visionModel>;parts=<videos>` ಅನ್ನು Vision ಅಥವಾ Audio ಸೆಗ್ಮೆಂಟ್ಗಳನ್ನು ತೆಗೆದುಹಾಕದೆ ಸೇರಿಸುತ್ತವೆ.

### PII ಮಾಸ್ಕರ್ (`piiMasker.ts`)

**ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ.

- **`preCall`** ಪೇಲೋಡ್ ಅನ್ನು ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `system`, `messages`, `input`, ಮತ್ತು
  `prompt` ಅನ್ನು (ಸರಳ ಸ್ಟ್ರಿಂಗ್ ಐಟಂಗಳು ಸೇರಿದಂತೆ) ಹಾದುಹೋಗುತ್ತದೆ, ಮತ್ತು ಸ್ಟ್ರಿಂಗ್
  `content`/`text` ಫೀಲ್ಡ್ಗಳಿಗೆ `processPII()` ಅನ್ನು
  (`@/shared/utils/inputSanitizer` ನಿಂದ) ಅನ್ವಯಿಸುತ್ತದೆ. `PII_REDACTION_ENABLED=true`
  ಆಗಿದ್ದಾಗ, ಪತ್ತೆಯಾದ PII ಅನ್ನು ಹೊರಹೋಗುವ ಪೇಲೋಡ್ನಲ್ಲಿ ಮರೆಮಾಚಲಾಗುತ್ತದೆ. ಇದು
  `INPUT_SANITIZER_MODE` ಗೆ ಸ್ವತಂತ್ರವಾಗಿದೆ (ಅದು ಕೇವಲ ಪ್ರಾಂಪ್ಟ್-ಇಂಜೆಕ್ಷನ್ ನೀತಿಯನ್ನು
  ನಿಯಂತ್ರಿಸುತ್ತದೆ). ಮರೆಮಾಚುವಿಕೆ ಆಫ್ ಆಗಿದ್ದಾಗ, ಕರೆಯು ವಿಷಯವನ್ನು ಮರುಬರೆಯದೇ ಪತ್ತೆ
  ಎಣಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ.
- **`postCall`** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಡೀಪ್-ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `sanitizePIIResponse()`
  ಜೊತೆಗೆ Responses-API-ಆಕಾರದ ಮಾಸ್ಕರ್ ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (`maskResponsesOutput` —
  `output_text` ಮತ್ತು `output[].content[].text` ಅನ್ನು ಒಳಗೊಂಡಿದೆ). ಯಾವುದಾದರೂ
  ಮರೆಮಾಚುವಿಕೆ ಸಂಭವಿಸಿದರೆ, ಮಾರ್ಪಡಿಸಿದ ಪ್ರತಿಕ್ರಿಯೆಯು ಮೂಲದ ಸ್ಥಾನವನ್ನು ತಾಳುತ್ತದೆ.

ಗಾರ್ಡ್ರೈಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಕೇವಲ ಟಿಪ್ಪಣಿ ಮಾಡುತ್ತದೆ (`meta.detections`,
`meta.redacted`) ಅಥವಾ ಮರುಬರೆಯುತ್ತದೆ.

#### ಪ್ರತಿ-ಪ್ರಕಾರದ ಆಯ್ಕೆ, ಕಸ್ಟಮ್ ಮಾದರಿಗಳು ಮತ್ತು ಪತ್ತೆ ಕೌಂಟರ್ಗಳು

**ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು → ಭದ್ರತೆ → PII ಮಾಸ್ಕಿಂಗ್** _ಏನನ್ನು_ ಮಾಸ್ಕ್ ಮಾಡಬೇಕು
ಎಂಬುದನ್ನು ಆಯ್ದುಕೊಳ್ಳುತ್ತದೆ. ಅದು ಮಾಸ್ಕಿಂಗ್ ಅನ್ನು ಆನ್ ಮಾಡುವುದಿಲ್ಲ: ಅದಕ್ಕಾಗಿ ಇನ್ನೂ
`PII_REDACTION_ENABLED` (ವಿನಂತಿ) ಮತ್ತು `PII_RESPONSE_SANITIZATION` (ಪ್ರತಿಕ್ರಿಯೆ +
SSE) ಬೇಕು, ಎರಡೂ ಡೀಫಾಲ್ಟ್ ಆಗಿ ಆಫ್ ಆಗಿವೆ.

- **ಪ್ರತಿ-ಪ್ರಕಾರದ ಆಯ್ಕೆ** — ಅಂತರ್ನಿರ್ಮಿತ id ಗಳನ್ನು
  `src/shared/constants/piiTypes.ts` ನಲ್ಲಿ (`PII_BUILTIN_TYPES`) ಪಟ್ಟಿ ಮಾಡಲಾಗಿದೆ.
  ಸೆಟ್ ಮಾಡದಿದ್ದರೆ ಎಲ್ಲಾ ಪ್ರಕಾರಗಳು ಎಂದರ್ಥ (ಈ ಸೆಟ್ಟಿಂಗ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲಿನ
  ನಡವಳಿಕೆ). ವಿನಂತಿ ಎಂಜಿನ್ನ `ssn_us` ಮಾದರಿಯು `ssn` ಗೆ ಮ್ಯಾಪ್ ಆಗುತ್ತದೆ. ಟೆಂಪ್ಲೇಟ್ಗಳು
  (Minimal, Standard, Financial, Brazilian, USA, Full) UI ಯಲ್ಲಿನ ಚೆಕ್ಬಾಕ್ಸ್ಗಳನ್ನು
  ಮಾತ್ರ ತುಂಬಿಸುತ್ತವೆ.
- **ಕಸ್ಟಮ್ ಮಾದರಿಗಳು** — ಗರಿಷ್ಠ 20 regex ಅಥವಾ ವೈಲ್ಡ್ಕಾರ್ಡ್ ಮಾದರಿಗಳು (`*` = ಗರಿಷ್ಠ 64
  ಬಿಟ್ಟರೆಹಿನ ಅಕ್ಷರಗಳು, `?` = ಒಂದು). ಹೊಂದಾಣಿಕೆಗಳು `[CUSTOM_REDACTED]` ಆಗುತ್ತವೆ.
  ಪ್ರತಿ ಮಾದರಿಯು `compilePiiCustomPattern()` ಮೂಲಕ ಹೋಗುತ್ತದೆ
  (`src/shared/utils/piiCustomPatterns.ts`): ಗರಿಷ್ಠ 500 ಅಕ್ಷರಗಳು, ಫ್ಲ್ಯಾಗ್ಗಳು
  `g i m s u` ಗೆ ಸೀಮಿತ, ಕಂಪೈಲ್ ಆಗಬೇಕು, `safe-regex` ಅನ್ನು ಪಾಸ್ ಮಾಡಬೇಕು (ವಿನಾಶಕಾರಿ
  ಬ್ಯಾಕ್ಟ್ರ್ಯಾಕಿಂಗ್), ಮತ್ತು ಖಾಲಿ ಸ್ಟ್ರಿಂಗ್ ಅಥವಾ ಮರೆಮಾಚುವ ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ ಅನ್ನು
  ಹೊಂದಿಸಕೂಡದು. ವಿಫಲವಾಗುವ ಮಾದರಿಯನ್ನು ಉಳಿಸುವಾಗ ಮತ್ತು ಪರೀಕ್ಷಿಸುವಾಗ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ,
  ಮತ್ತು ವಿಫಲವಾಗುವ ಶೇಖರಿತ ಸಾಲನ್ನು ರನ್ಟೈಮ್ನಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡುವ ಬದಲು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ.
  ಕಸ್ಟಮ್ ಮಾದರಿಗಳು ಮಾಸ್ಕಿಂಗ್ ಆನ್ ಆಗಿರುವಾಗ ಮಾತ್ರ ಚಾಲನೆಯಾಗುತ್ತವೆ.
- **ಪತ್ತೆ ಕೌಂಟರ್ಗಳು** — ಪ್ರತಿ-ಪ್ರಕಾರದ ಎಣಿಕೆಗಳು (ಹೊಂದಿದ ಮೌಲ್ಯಗಳನ್ನು ಎಂದಿಗೂ
  ಇರಿಸುವುದಿಲ್ಲ), ಮೆಮೊರಿಯಲ್ಲಿ ಇರಿಸಲಾಗುತ್ತವೆ ಮತ್ತು ಮರುಪ್ರಾರಂಭದಲ್ಲಿ ಮರುಹೊಂದಿಸಲಾಗುತ್ತವೆ
  (`src/lib/pii/piiDetectionStats.ts`). ಅವು ಮಾಸ್ಕಿಂಗ್ ಆನ್ ಆಗಿರುವಾಗ ಮಾತ್ರ ಹೆಚ್ಚುತ್ತವೆ.

ಸೆಟ್ಟಿಂಗ್ಗಳು `key_value` ಟೇಬಲ್ನಲ್ಲಿ (ನೇಮ್ಸ್ಪೇಸ್ `pii_settings`,
`src/lib/db/piiSettings.ts`) ಇರುತ್ತವೆ ಮತ್ತು 1 ಸೆಕೆಂಡ್ ಕ್ಯಾಶೆ ಮೂಲಕ ಓದಲಾಗುತ್ತವೆ. API:

| ವಿಧಾನ  | ಮಾರ್ಗ                    | ಉದ್ದೇಶ                                                                                    |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | ಫ್ಲ್ಯಾಗ್ ಸ್ಥಿತಿ, `enabledTypes`, `customPatterns`, ಪತ್ತೆ ಕೌಂಟರ್ಗಳು                        |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = ಎಲ್ಲಾ) ಮತ್ತು/ಅಥವಾ `customPatterns` ಅನ್ನು ಬದಲಾಯಿಸಿ                |
| `POST` | `/api/settings/pii/test` | ಗರಿಷ್ಠ 8 KB ಗಾತ್ರದ ಮಾದರಿಯ ವಿರುದ್ಧ ಒಂದು ಮಾದರಿಯನ್ನು ಡ್ರೈ-ರನ್ ಮಾಡಿ; ಏನನ್ನೂ ಶೇಖರಿಸಲಾಗುವುದಿಲ್ಲ |

ಮೂರೂ ನಿರ್ವಹಣಾ ದೃಢೀಕರಣವನ್ನು ಬಯಸುತ್ತವೆ ಮತ್ತು ಬಾಡಿಯನ್ನು Zod ಮೂಲಕ ಮಾನ್ಯಗೊಳಿಸುತ್ತವೆ
(`src/shared/validation/schemas/piiSettings.ts`).

### ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ (`promptInjection.ts`)

ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ವಿಷಯದಲ್ಲಿ ಪ್ರತಿಕೂಲ ರಚನೆಗಳನ್ನು ಪತ್ತೆ ಮಾಡುತ್ತದೆ ಮತ್ತು ಕಾನ್ಫಿಗರ್
ಮಾಡಿದ ನೀತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ. ನಡವಳಿಕೆಯನ್ನು ಪರಿಸರ ವೇರಿಯಬಲ್ಗಳು ಮತ್ತು ಕನ್ಸ್ಟ್ರಕ್ಟರ್
ಆಯ್ಕೆಗಳು ನಿಯಂತ್ರಿಸುತ್ತವೆ:

| ಸೆಟ್ಟಿಂಗ್         | ಪರಿಸರ ವೇರಿಯಬಲ್                                                                                         | ಡೀಫಾಲ್ಟ್ | ಪರಿಣಾಮ                                                                                                                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ | `INPUT_SANITIZER_ENABLED`                                                                              | `true`   | `false` ಆಗಿದ್ದಾಗ, ಗಾರ್ಡ್ರೈಲ್ ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತದೆ.                                                                                                                                                               |
| ಮೋಡ್              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                        | `warn`   | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `block`, `warn`, ಅಥವಾ `log`. (`redact` ಅನ್ನು ಹಿಂದಿನ ಹೊಂದಾಣಿಕೆಗಾಗಿ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ ಆದರೆ ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು **ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ**; ವಿನಂತಿಯ PII ಮರುಬರಹವನ್ನು `PII_REDACTION_ENABLED` ನಿಯಂತ್ರಿಸುತ್ತದೆ.) |
| ನಿರ್ಬಂಧ ಮಿತಿ      | `blockThreshold` ಆಯ್ಕೆ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ಅಲಿಯಾಸ್ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`   | ನಿರ್ಬಂಧಿಸಲು ಬೇಕಾದ ಕನಿಷ್ಠ ತೀವ್ರತೆ. ಡೀಫಾಲ್ಟ್ನಲ್ಲಿ Medium ಕೇವಲ ವೀಕ್ಷಣೆ-ಮಾತ್ರ.                                                                                                                                            |

**ಮೋಡ್ ಆದ್ಯತೆ** (`getMode`): ಕರೆಮಾಡುವವರ `options.mode` →
`INJECTION_GUARD_MODE` **DB ಫೀಚರ್-ಫ್ಲ್ಯಾಗ್ ಓವರ್ರೈಡ್** (ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು →
ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ಗಳು) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. ಆದ್ದರಿಂದ ಡ್ಯాశ್ಬೋರ್ಡ್ ಓವರ್ರೈಡ್ env ವೇರಿಯಬಲ್ಗಳ ಮೇಲೆ ಗೆಲ್ಲುತ್ತದೆ, ಆದ್ದರಿಂದ
ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ಗಳ UI ಚಾಲ್ತಿಯಲ್ಲಿರುವ ಗಾರ್ಡ್ ಅನ್ನು ಲೈವ್ ಆಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ
(ಮರುಪ್ರಾರಂಭ ಬೇಡ). DB ಓದುವಿಕೆ ಫೇಲ್-ಸೇಫ್ ಆಗಿದೆ: ಅದು ದೋಷವನ್ನುಂಟುಮಾಡಿದರೆ, ಗಾರ್ಡ್
env-ಆಧಾರಿತ ನಡವಳಿಕೆಗೆ ಹಿಂತಿರುಗುತ್ತದೆ, ಮತ್ತು ಯಾವುದೇ ಓವರ್ರೈಡ್ ಸೆಟ್ ಮಾಡದಿದ್ದಾಗ
ನಡವಳಿಕೆಯು env-ಮಾತ್ರ ಪರಿಹಾರಕ್ಕೆ ಸಮಾನವಾಗಿರುತ್ತದೆ.

ಪತ್ತೆ ಮೂಲಗಳು:

1. `@/shared/utils/inputSanitizer` ನಿಂದ `sanitizeRequest()` (ಪೈಪ್ಲೈನ್ನಲ್ಲಿ ಬೇರೆಡೆ
   ಬಳಸುವ ಹಂಚಿಕೆಯ ಡಿಟೆಕ್ಟರ್ ಸೆಟ್).
2. ಅಂತರ್ನಿರ್ಮಿತ `DEFAULT_GUARD_PATTERNS` (ಪ್ರಸ್ತುತ `system_override_inline` ಮತ್ತು
   `markdown_system_block`, ಎರಡೂ `high` ತೀವ್ರತೆ).
3. ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳ ಮೂಲಕ ರವಾನಿಸುವ ಐಚ್ಛಿಕ `customPatterns` (ಸ್ಟ್ರಿಂಗ್ಗಳು,
   regex, ಅಥವಾ `{ name, pattern, severity }` ದಾಖಲೆಗಳು).

`mode === "block"` ಆಗಿರುವಾಗ **ಮತ್ತು** ಕನಿಷ್ಠ ಒಂದು detection severity threshold ಅನ್ನು ಪೂರೈಸಿದಾಗ, `preCall` `{ block: true, message: "Request rejected: suspicious content detected" }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ. `warn`/`log` mode ಗಳಲ್ಲಿ guardrail ಲಾಗ್ ಮಾಡುತ್ತದೆ ಆದರೆ call ಅನ್ನು ಅನುಮತಿಸುತ್ತದೆ. registry ಮೂಲಕ ಹೋಗದೆ prompt ಗಳನ್ನು evaluate ಮಾಡಬೇಕಾದ caller ಗಳಿಗಾಗಿ ಹಂಚಿಕೊಂಡ helper `evaluatePromptInjection()` ಸಹ export ಮಾಡಲಾಗಿದೆ.

**ಸ್ಕ್ಯಾನ್ ಮಿತಿ (v3.8.20):** detector ಸೇರಿಸಿದ prompt ಪಠ್ಯದ **ಮೊದಲ 16 KB** ಅನ್ನು ಮಾತ್ರ ಪರಿಶೀಲಿಸುತ್ತದೆ — `src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿ `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes). `detectInjection()` ಮತ್ತು `evaluatePromptInjection()` ಎರಡೂ pattern loop ಚಲಾಯಿಸುವ ಮೊದಲು `slice(0, MAX_INJECTION_SCAN_BYTES)` ಮಾಡುತ್ತವೆ. injection ಸೂಚನೆಗಳು input ನ ಮೇಲಿನ ಭಾಗದಲ್ಲಿರುತ್ತವೆ, ಆದ್ದರಿಂದ ಇದು detection ಅನ್ನು ದುರ್ಬಲಗೊಳಿಸದೆ multi-hundred-KB payload ಗಳಲ್ಲಿ regex CPU/GC ಅನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ (cf. #3932, #4041).

### ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಮಾಸ್ಕರ್ (`credentialMasker.ts`)

ಡೀಫಾಲ್ಟ್ chain ನಲ್ಲಿ ಕೊನೆಯದಾಗಿ **ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ಚಾಲನೆಯಾಗುತ್ತದೆ (priority `95`). ಹೊರಹೋಗುವ payload (message content, tool-call arguments, tool results) **ಮತ್ತು** provider response ಎರಡರಿಂದಲೂ ಪ್ರಸಿದ್ದ API-key / secret-token pattern ಗಳನ್ನು redact ಮಾಡುತ್ತದೆ, ಇದರಿಂದ prompt ಗೆ ಅಂಟಿಸಲಾದ (ಅಥವಾ tool result ಮೂಲಕ ಮರುಳಿಸಲಾದ) ಕ್ರೆಡೆನ್ಷಿಯಲ್ upstream provider ಗೆ ಅಥವಾ client ಗೆ leak ಆಗುವುದಿಲ್ಲ.

- **Opt-in ಮಾತ್ರ**, PII redaction ನಂತೆಯೇ (Hard Rule #20-adjacent): `settings.credentialRedactionEnabled === true` **ಅಥವಾ** `CREDENTIAL_REDACTION_ENABLED=true` ಆಗದ ಹೊರತು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ. ಅದು ಆಫ್ ಆಗಿದ್ದರೆ, guardrail ಒಂದು no-op — ಅದು ಎಂದಿಗೂ block ಮಾಡುವುದಿಲ್ಲ ಮತ್ತು rewrite ಮಾಡುವುದಿಲ್ಲ.
- `redactCredentials()` ಸಂಪೂರ್ಣ payload/response tree ಅನ್ನು ಹಾದುಹೋಗುತ್ತದೆ (`walkValue()`, prototype-pollution-safe, `WeakSet` ಮೂಲಕ cycle-safe) ಮತ್ತು ಹೊಂದಾಣಿಕೆಗಳನ್ನು `[REDACTED:<type>]` placeholder ನಿಂದ ಬದಲಾಯಿಸುತ್ತದೆ, ನಿಜವಾಗಿ ಬದಲಾದ branch ಗಳನ್ನು ಮಾತ್ರ clone ಮಾಡುತ್ತದೆ.
- `CREDENTIAL_PATTERNS` LLM provider key ಗಳನ್ನು (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), VCS/SaaS token ಗಳನ್ನು (GitHub, Slack, Linear, Notion, npm, Postman, Discord), payment key ಗಳನ್ನು (Stripe, Square), cloud key ಗಳನ್ನು (AWS access key, Twilio, SendGrid, Mailgun), private key ಗಳು / JWT ಗಳು, ಕ್ರೆಡೆನ್ಷಿಯಲ್-ಹೊಂದಿರುವ connection string ಗಳು (`mongodb://user:pass@...`, ಇತ್ಯಾದಿ), ಮತ್ತು generic `Authorization`/`x-api-key`/`api-key`/`apikey` header-value pattern ಅನ್ನು ಒಳಗೊಂಡಿದೆ. Header-ಆಕಾರದ key ಗಳು (`authorization`, `x-api-key`, `api-key`, `apikey`) generic text regex ಬದಲು ರಚನಾತ್ಮಕವಾಗಿ redact ಮಾಡಲಾಗುತ್ತವೆ (value ಮಾತ್ರ, `Bearer `/`Basic ` ನಂತಹ scheme prefix ಅನ್ನು ಸಂರಕ್ಷಿಸಲಾಗುತ್ತದೆ).
- guardrail ಎಂದಿಗೂ block ಮಾಡುವುದಿಲ್ಲ; ಅದು ಕೇವಲ rewrite ಮಾಡುತ್ತದೆ (`modifiedPayload` / `modifiedResponse`) ಮತ್ತು annotate ಮಾಡುತ್ತದೆ (`meta.credentialsRedacted`, `meta.count`).

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

## ಮೂಲ ಒಪ್ಪಂದ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ಸರಣಿಯನ್ನು ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಮಾಡುತ್ತದೆ
  message?: string; // ನಿರ್ಬಂಧಿಸುವಾಗ ತೋರಿಸಲಾಗುತ್ತದೆ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ವಿನಂತಿಯನ್ನು ಮರುಬರೆಯಲು preCall ಹಿಂದಿರುಗಿಸುತ್ತದೆ
  modifiedResponse?: TValue; // ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯಲು postCall ಹಿಂದಿರುಗಿಸುತ್ತದೆ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ಗಾರ್ಡ್ರೈಲ್ ಒಂದು `void`, `{}` ಅಥವಾ `{ block: false }` ಹಿಂದಿರುಗಿಸುವ ಮೂಲಕ "ಬದಲಾವಣೆ ಇಲ್ಲ" ಎಂದು ಸೂಚಿಸುತ್ತದೆ. `modifiedPayload`/`modifiedResponse` ಹಿಂದಿರುಗಿಸುವುದು ಕೆಳಹರಿವಿನ ಗಾರ್ಡ್ರೈಲ್ಗಳಿಗಾಗಿ ಸರಣಿಯ ಮೂಲಕ ಹರಿಯುವ ಮೌಲ್ಯವನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ. `signal?: AbortSignal` ಕರೆಮಾಡುವವರ ಜೀವನಚಕ್ರವನ್ನು ಗಾರ್ಡ್ರೈಲ್ಗಳೊಳಗೆ ಸಾಗಿಸುತ್ತದೆ. ವಿನಂತಿ ರದ್ದತಿಯು ಉದ್ದೇಶಪೂರ್ವಕ ಫೇಲ್-ಓಪನ್ ಹೊರತಾಗಿದೆ: ಮೀಡಿಯಾ ಬ್ರಿಡ್ಜ್ಗಳು ಕೆಲಸ ಮತ್ತು ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆಯನ್ನು ನಿಲ್ಲಿಸುತ್ತವೆ, ಅದನ್ನು ಬೆಂಬಲಿಸುವುದಿಲ್ಲ ಎಂದು ತಿಳಿದಿರುವ ಗುರಿಗೆ ಕಚ್ಚಾ ಮೀಡಿಯಾವನ್ನು ಮರುಸ್ಥಾಪಿಸದೆ.

## ರಿಜಿಸ್ಟ್ರಿ (`registry.ts`)

ಸಿಂಗಲ್ಟನ್ `guardrailRegistry` ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ:

- `register(guardrail)` — ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಅಥವಾ ಸಾಮಾನ್ಯೀಕೃತ ಹೆಸರಿನಿಂದ
  ಬದಲಾಯಿಸುತ್ತದೆ) ಮತ್ತು ಏರಿಕೆ `priority` ಪ್ರಕಾರ ಮರು-ವಿಂಗಡಿಸುತ್ತದೆ.
- `clear()` / `list()` — ಆಡಳಿತಾತ್ಮಕ ಸಹಾಯಕಗಳು.
- `runPreCallHooks(payload, context)` — ಸಕ್ರಿಯ ಗಾರ್ಡ್ರೈಲ್ಗಳ ಮೂಲಕ ಪುನರಾವರ್ತಿಸುತ್ತದೆ,
  ಪೇಲೋಡ್ ಅನ್ನು `modifiedPayload` ಮೂಲಕ ಸಾಗಿಸುತ್ತದೆ, ಮತ್ತು ಮೊದಲ `block: true` ನಲ್ಲಿ ನಿಲ್ಲಿಸುತ್ತದೆ.
- `runPostCallHooks(response, context)` — ಪ್ರತಿಕ್ರಿಯೆಯ ಬದಿಯಲ್ಲಿಯೂ ಅದೇ ಹರಿವು.
- `resetGuardrailsForTests({ registerDefaults })` — ಸ್ಥಿತಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ ಮತ್ತು
  ಸ್ವಚ್ಛ ಪರೀಕ್ಷಾ ಪ್ರತ್ಯೇಕತೆಗಾಗಿ ಬಯಸಿದರೆ ಡೀಫಾಲ್ಟ್ಗಳನ್ನು ಮರು-ನೋಂದಾಯಿಸುತ್ತದೆ.

ಎರಡೂ ರನ್ನರ್ಗಳು `{ blocked, payload|response, results, guardrail?, message? }` ಹಿಂದಿರುಗಿಸುತ್ತವೆ; ಇಲ್ಲಿ `results` ಎಂಬುದು `GuardrailExecutionResult` ದಾಖಲೆಗಳ ಶ್ರೇಣಿಯಾಗಿದ್ದು, ಪ್ರತಿ-ಗಾರ್ಡ್ರೈಲ್ `blocked`, `skipped`, `modified`, `error` ಮತ್ತು `meta` ಕ್ಷೇತ್ರಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ — ಇದು ಟ್ರೇಸಿಂಗ್ಗೆ ಉಪಯುಕ್ತ.

### ಪ್ರತಿ-ವಿನಂತಿಗೆ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ಪ್ರಸ್ತುತ ವಿನಂತಿಗೆ ಬಿಟ್ಟುಬಿಡಬೇಕಾದ ಗಾರ್ಡ್ರೈಲ್ ಹೆಸರುಗಳ ನಕಲು-ತೆಗೆದ ಪಟ್ಟಿಯನ್ನು ಒಂದುಗೂಡಿಸುತ್ತದೆ. ಐದು ಚಾನೆಲ್ಗಳಿವೆ; ಅವುಗಳನ್ನು ಈ ಕ್ರಮದಲ್ಲಿ ಓದಲಾಗುತ್ತದೆ ಮತ್ತು ಒಂದೇ ಪಟ್ಟಿಯಾಗಿ ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ (ನಕಲು-ತೆಗೆಯುವಾಗ ಮೊದಲ ಆಗಮನವೇ ಗೆಲ್ಲುತ್ತದೆ):

1. `apiKeyInfo.disabledGuardrails`
2. ವಿನಂತಿ ಬಾಡಿಯ `disabledGuardrails` (ಮೇಲ್ಮಟ್ಟ)
3. ವಿನಂತಿ ಬಾಡಿಯ `metadata.disabledGuardrails` (`metadata` ಆಬ್ಜೆಕ್ಟ್ ಆಗಿರುವಾಗ ಮಾತ್ರ)
4. ಹೆಡರ್ `x-omniroute-disabled-guardrails`
5. ಲೆಗಸಿ ಹೆಡರ್ `x-disabled-guardrails`

ಎಲ್ಲಾ ಐದು ಚಾನೆಲ್ಗಳು ವಿಲೀನಗೊಳ್ಳುತ್ತವೆ — ಎರಡು ಹೆಡರ್ಗಳೂ ಸೇರಿದಂತೆ: `x-omniroute-disabled-guardrails` ಮತ್ತು `x-disabled-guardrails` ಎರಡನ್ನೂ ಕಳುಹಿಸಿದರೆ ಅವುಗಳ ಪಟ್ಟಿಗಳ ಯೂನಿಯನ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ, ಮತ್ತು ಖಾಲಿ ಆಧುನಿಕ ಹೆಡರ್ ಇನ್ನುಮುಂದೆ ಲೆಗಸಿ ಹೆಡರ್ ಅನ್ನು ಮರೆಮಾಚುವುದಿಲ್ಲ ([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), [#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) ನಲ್ಲಿ ಸರಿಪಡಿಸಲಾಗಿದೆ).

ಮೌಲ್ಯಗಳು ಸ್ಟ್ರಿಂಗ್ಗಳ ಶ್ರೇಣಿಗಳಾಗಿರಬಹುದು ಅಥವಾ ಕಾಮಾ-ಬೇರ್ಪಡಿಸಿದ ಸ್ಟ್ರಿಂಗ್ ಆಗಿರಬಹುದು; ಹೆಸರುಗಳನ್ನು ಟ್ರಿಮ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಚಿಕ್ಕಕ್ಷರ kebab-case ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ (`pii_masker` → `pii-masker`), ಮತ್ತು ಖಾಲಿ ನಮೂದುಗಳನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ. ಫಲಿತಾಂಶವನ್ನು `context.disabledGuardrails` ಮೂಲಕ ರಿಜಿಸ್ಟ್ರಿಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ; ಅದು ಹೊಂದಿಕೆಯಾಗುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`results` ನಲ್ಲಿ `skipped: true`).

ನಿಷ್ಕ್ರಿಯ ಪಟ್ಟಿಯು ಕೇವಲ **ರಿಜಿಸ್ಟ್ರಿ**ಯನ್ನು ಮಾತ್ರ ಪರಿಣಾಮ ಬೀರುತ್ತದೆ. ಪ್ರಾಂಪ್ಟ್-ಇಂಜೆಕ್ಷನ್ `block` ಮೋಡ್ ಕಡ್ಡಾಯ ಗಡಿಯಾಗಿದೆ: ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ಮಿಡಲ್ವೇರ್ (`src/middleware/promptInjectionGuard.ts`) ಯಾವುದೇ ಕರೆಮಾಡುವವರ-ನಿಯಂತ್ರಿತ ನಿಷ್ಕ್ರಿಯ ಪಟ್ಟಿಯಿಲ್ಲದೆ `evaluatePromptInjection()` ಅನ್ನು ಕರೆಯುತ್ತದೆ (ಅದು ಹಿಂದೆ ಮಾಡುತ್ತಿದ್ದ ನಿಷ್ಪ್ರಯೋಜಕ `resolveDisabledGuardrails({ body })` ಕರೆಯನ್ನು [#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934) ನಲ್ಲಿ ತೆಗೆದುಹಾಕಲಾಗಿದೆ), ಆದ್ದರಿಂದ `prompt-injection` ಅನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವ ವಿನಂತಿಯನ್ನು `block` ಮೋಡ್ನಲ್ಲಿಯೂ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕ ವಿನ್ಯಾಸ. ನಿಷ್ಕ್ರಿಯ ಚಾನೆಲ್ಗಳು ಕರೆಮಾಡುವವರ ನಿಯಂತ್ರಣದಲ್ಲಿವೆ (ವಿನಂತಿ ಬಾಡಿ, metadata, ಹೆಡರ್ಗಳು), ಮತ್ತು ಆಪರೇಟರ್ ಹೊಂದಿಸಿದ ಭದ್ರತಾ ನಿಯಂತ್ರಣವನ್ನು ಕರೆಮಾಡುವವರು ಆಫ್ ಮಾಡಲು ಸಾಧ್ಯವಾಗಬಾರದು ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) ರ ಹೆಡರ್ ಯೂನಿಯನ್ ಯಾವ ರಿಜಿಸ್ಟ್ರಿ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ ಎಂಬುದನ್ನು ಮಾತ್ರ ಬದಲಾಯಿಸುತ್ತದೆ; ಅದು ಕ್ಲಯಂಟ್ಗೆ ಮಿಡಲ್ವೇರ್ ಅನ್ನು bypass ಮಾಡಲು ಅನುಮತಿಸುವುದಿಲ್ಲ. ಕಡ್ಡಾಯ ಪ್ರತಿ-ಕೀ ಮತ್ತು ಪ್ರತಿ-ಗುಂಪು ಗಾರ್ಡ್ರೈಲ್ ನೀತಿಗಳನ್ನು v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417) ನಲ್ಲಿ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿದೆ. [ವ್ಯಾಪ್ತಿ ಮತ್ತು ಮಿತಿಗಳು](#coverage-and-limits) ನೋಡಿ.

## ಕಾರ್ಯನಿರ್ವಹಣೆಯ ಕ್ರಮ

`src/sse/handlers/chat.ts` ಮತ್ತು `open-sse/handlers/chatCore.ts` ಮೂಲಕ ಹರಿದುಬರುವ ಪ್ರತಿ ವಿನಂತಿಗಾಗಿ
([ವ್ಯಾಪ್ತಿ ಮತ್ತು ಮಿತಿಗಳು](#coverage-and-limits) ಅಡಿಯಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾದ ಚಾಟ್-ಕುಟುಂಬದ ರೂಟ್ಗಳು):

1. `resolveDisabledGuardrails(...)` API ಕೀ, ಬಾಡಿ ಮತ್ತು ಹೆಡರ್ಗಳಿಂದ ಸ್ಕಿಪ್ ಪಟ್ಟಿಯನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ಏರಿಕೆ ಆದ್ಯತಾ ಕ್ರಮದಲ್ಲಿ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ:
   - ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು `skipped` ಎಂದು ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
   - ಪ್ರತಿ ಗಾರ್ಡ್ರೈಲ್ನ `preCall` `modifiedPayload` ಮೂಲಕ ಪೇಲೋಡ್ ಅನ್ನು ಮರುಬರೆಯಬಹುದು.
   - ಮೊದಲ `block: true` ಸರಪಳಿಯನ್ನು ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ ಗಾರ್ಡ್ರೈಲ್ ತಿರಸ್ಕಾರ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
3. (ಬಹುಷಃ ಮರುಬರೆಯಲಾದ) ಪೇಲೋಡ್ ಕಾಂಬೊ ರೂಟಿಂಗ್ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಹರಿಯುತ್ತದೆ.
4. **ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದವು ಮಾತ್ರ:** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಜೋಡಿಸಿದ ನಂತರ,
   `guardrailRegistry.runPostCallHooks(...)` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೇಲೆ ಅದೇ ಸರಪಳಿಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ.
   ಇಲ್ಲಿ `block: true` ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಕೈಬಿಡುತ್ತದೆ ಮತ್ತು HTTP 400 ಹಿಂತಿರುಗಿಸುತ್ತದೆ. ಸ್ಟ್ರೀಮ್ ಮಾಡಲಾದ ಪ್ರತಿಕ್ರಿಯೆಗಳು ಈ ಹಂತವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತವೆ.

ಥ್ರೋ ಮಾಡುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು `error: <message>` ನೊಂದಿಗೆ ದಾಖಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`logger.warn` ಮೂಲಕ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸರಪಳಿ ಮುಂದುವರಿಯುತ್ತದೆ — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ಫೆಯಿಲ್-ಓಪನ್.

### ಯಾವುದು ವ್ಯಾಪ್ತಿಯಲ್ಲಿಲ್ಲ

- **ಮೀಡಿಯಾ, ಎಂಬೆಡಿಂಗ್ಗಳು ಮತ್ತು ಡೇಟಾ ರೂಟ್ಗಳು** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) ಎಂದಿಗೂ ರಿಜಿಸ್ಟ್ರಿಯನ್ನು ತಲುಪುವುದಿಲ್ಲ. ಅಲ್ಲಿ
  PII ಮಾಸ್ಕಿಂಗ್, ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಮಾಸ್ಕಿಂಗ್ ಅಥವಾ ಮೊಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ ಓಡುವುದಿಲ್ಲ. ಅವುಗಳ
  ಏಕೈಕ ಪರಿಶೀಲನೆ ಲೆಗಸಿ ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ಮಿಡಲ್ವೇರ್ ಆಗಿದೆ.
- **ಸ್ಟ್ರೀಮ್ ಮಾಡಲಾದ ಪ್ರತಿಕ್ರಿಯೆಗಳು** ಯಾವುದೇ ಪೋಸ್ಟ್-ಕಾಲ್ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಪಡೆಯುವುದಿಲ್ಲ: `pii-masker` ಅಥವಾ
  `credential-masker` ಪೋಸ್ಟ್-ಕಾಲ್ ಇಲ್ಲ, ಮತ್ತು ಪೋಸ್ಟ್-ಕಾಲ್ ಬ್ಲಾಕ್ ಇಲ್ಲ. ಸ್ಟ್ರೀಮಿಂಗ್ PII
  ಟ್ರಾನ್ಸ್ಫಾರ್ಮ್ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ (`PII_RESPONSE_SANITIZATION` ಆನ್ ಆಗಿರುವಾಗ). ಸ್ಟ್ರೀಮ್ ಮಾಡಲಾದ
  ಪ್ರತಿಕ್ರಿಯೆಯಲ್ಲಿ ಮರುಪ್ರತಿಧ್ವನಿಸಿದ ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಅನ್ನು ಮರೆಮಾಚಲಾಗುವುದಿಲ್ಲ.
- **ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವ ಚಾನೆಲ್ಗಳು ವಿರುದ್ಧ ಮಿಡಲ್ವೇರ್ (ವಿನ್ಯಾಸದ ಪ್ರಕಾರ):** ಮಿಡಲ್ವೇರ್
  ಯಾವುದೇ ಕಾಲರ್-ನಿಯಂತ್ರಿತ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವ ಪಟ್ಟಿಯನ್ನು ರವಾನಿಸದೆ, `evaluatePromptInjection()` ಗೆ ತನ್ನದೇ ಆದ
  ಕರೆಯೊಂದಿಗೆ ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡುತ್ತದೆ. `block` ಮೋಡ್ ಕಡ್ಡಾಯ
  ಗಡಿಯಾಗಿದ್ದು, ಚಾಟ್-ಕುಟುಂಬ ರೂಟ್ಗಳು ಸೇರಿದಂತೆ ಕಾಲರ್-ನಿಯಂತ್ರಿತ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವಿಕೆಗಳು
  ಅದನ್ನು ಬೈಪಾಸ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection` ಅನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು
  ರಿಜಿಸ್ಟ್ರಿ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ಮಾತ್ರ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

### ಪೋಸ್ಟ್-ಕಾಲ್ಗೆ ಮೊದಲು ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಯಾವುದು ನೋಡುತ್ತದೆ

ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದ ಮಾರ್ಗದಲ್ಲಿ ಕ್ರಮವು ಹೀಗಿರುತ್ತದೆ: ಮೆಮರಿ ಹೊರತೆಗೆಯುವಿಕೆ → ಅಂತರ್ನಿರ್ಮಿತ ಟೂಲ್
ಎಕ್ಸಿಕ್ಯೂಶನ್ → ಪೋಸ್ಟ್-ಕಾಲ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು → ಪೋಸ್ಟ್-ಕಾಲ್ ಬ್ಲಾಕ್ ನಿರ್ಗಮನ → ಸೆಮಾಂಟಿಕ್-ಕ್ಯಾಶೆ ಸ್ಟೋರ್.

- **ಮೆಮೊರಿ ಹೊರತೆಗೆಯುವಿಕೆ** ಮತ್ತು **ಟೂಲ್ ಎಕ್ಸಿಕ್ಯೂಷನ್** ಪೋಸ್ಟ್-ಕಾಲ್
  ಗಾರ್ಡ್ರೇಲ್ಗಳು ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯುವ ಅಥವಾ ನಿರ್ಬಂಧಿಸುವ ಮೊದಲೇ ಅದನ್ನು
  ನೋಡುತ್ತವೆ.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) ರಿಂದ, ಮೆಮೊರಿ
  ಹೊರತೆಗೆಯುವಿಕೆಯು `PII_RESPONSE_SANITIZATION` ಆನ್ ಆಗಿರುವಾಗ ಹೊರತೆಗೆದ ಪಠ್ಯವನ್ನು
  `sanitizePII` ಮೂಲಕ ಚಲಾಯಿಸುತ್ತದೆ (ಸ್ಟ್ರೀಮಿಂಗ್ ಮತ್ತು ನಾನ್-ಸ್ಟ್ರೀಮಿಂಗ್
  ಎರಡರಲ್ಲೂ), ಆದರೆ ಪೋಸ್ಟ್-ಕಾಲ್ ನಂತರ ನಿರ್ಬಂಧಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಆಗಸ್ಟಕ್ಕೂ
  ಮೆಮೊರಿ ಮತ್ತು ಟೂಲ್ಗಳಿಗೆ ನೀಡಲಾಗಿರುತ್ತದೆ.
- **ಸೆಮಾಂಟಿಕ್ ಕ್ಯಾಶೆ** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಪೋಸ್ಟ್-ಕಾಲ್ ನಂತರ ಸಂಗ್ರಹಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದು
  ಮರುಬರೆದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ, ಮತ್ತು ನಿರ್ಬಂಧಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಎಂದಿಗೂ
  ಕ್ಯಾಶೆ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಕ್ಯಾಶೆ ಎಂಟ್ರಿಗಳು ಪ್ರತಿ API ಕೀಯ ಪ್ರಕಾರ ಕೀಲಿ ಮಾಡಲಾಗುತ್ತವೆ.

## ಸಂರಚನೆ

ಅಂತರ್ನಿರ್ಮಿತ ಗಾರ್ಡ್ರೇಲ್ಗಳು ಓದುವ ಪರಿಸರ ವೇರಿಯೇಬಲ್ಗಳು:

| ವೇರಿಯೇಬಲ್                             | ಬಳಸುವುದು                    | ಪರಿಣಾಮ                                                                                                    |
| ------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`          | ಪತ್ತೆಹಚ್ಚುವಿಕೆಯನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲು `false` ಎಂದು ಹೊಂದಿಸಿ.                                    |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`          | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `warn`, `block`, ಅಥವಾ `log`. ಪಾರಂಪರಿಕ ಮೌಲ್ಯ `redact` ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು ಮರುಬರೆಯುವುದಿಲ್ಲ. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`          | ಇಂಜೆಕ್ಷನ್ ಗಾರ್ಡ್ಗಾಗಿ ಮೋಡ್; ಎನ್ವಿ ವೇರಿಯೇಬಲ್ಗಳನ್ನು **ಅತಿಕ್ರಮಿಸುವ** DB ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ ಕೂಡ ಆಗಿದೆ (DB > ENV).  |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | `MODE=block` ತಿರಸ್ಕರಿಸುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ: `high` (ಡೀಫಾಲ್ಟ್), `medium`, ಅಥವಾ `low`.                         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | `INPUT_SANITIZER_BLOCK_THRESHOLD` ಗಾಗಿ ಪಾರಂपರिक ಅಲಿಯಾಸ್.                                                  |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | `true` ಆಗಿದ್ದಾಗ, ವಿನಂತಿಯ PII ಅನ್ನು ಮರ್ಜನೆ ಮಾಡಲಾಗುತ್ತದೆ (ಇಂಜೆಕ్షನ್ ಮೋಡ್ಗೆ ಸ್ವತಂತ್ರವಾಗಿ).                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ಡೌನ್ಸ್ಟ್ರೀಮ್) | ಪ್ರತಿಕ್ರಿಯೆ-ಭಾಗದ ಮಾಸ್ಕರ್ ವರ್ತನೆಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.                                                     |

ಅಲ್ಲದೆ, DB-ಬೆಂಬಲಿತ ಸೆಟ್ಟಿಂಗ್ಸ್ ಸ್ಟೋರ್ (`getSettings()`) ನಿಂದ ಓದುತ್ತವೆ. ವಿಷನ್ನ
ಪ್ರಾಥಮಿಕ ಕೀಲಿಗಳು
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, ಮತ್ತು
`modalityBridgeCacheMaxEntries`. ಪಾರಂपरिक
`visionBridge*` ಕೀಲಿಗಳನ್ನು ದಾಖಲೀकृत ಏಕ-ಚಕ್ರ ಓದು ಫಾಲ್ಬ್ಯಾಕ್ ಆಗಿ ಮಾತ್ರ
ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಬರವಣಿಗೆಗಳು ಪ್ರಾಥಮಿಕ ಕೀಲಿಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಡೀಫಾಲ್ಟ್ಗಳು
ಮತ್ತು ಫಾಲ್ಬ್ಯಾಕ್ ರಿಸಾಲ್ವರ್ `src/shared/constants/modalityBridgeDefaults.ts` ನಲ್ಲಿವೆ,

ಆಡಿಯೊ `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,

## ಕಸ್ಟಮ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ಹಂತಗಳು:

1. `BaseGuardrail` ಅನ್ನು ವಿಸ್ತರಿಸುವ `src/lib/guardrails/myGuardrail.ts` ಅನ್ನು ರಚಿಸಿ.
2. `preCall` ಮತ್ತು/ಅಥವಾ `postCall` ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ.
3. ಇಂಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿ ನೋಂದಾಯಿಸಿ (`registerDefaultGuardrails` ನಿಂದ ಪುಶ್ ಮಾಡಿ) ಅಥವಾ
   ರನ್ಟೈಮ್ನಲ್ಲಿ `guardrailRegistry.register(...)` ಅನ್ನು ಕರೆಯಿರಿ — ರಿಜಿಸ್ಟ್ರಿಯು ಒಂದೇ
   ಸಾಮಾನ್ಯೀಕೃತ ಹೆಸರಿನ ಹಿಂದಿನ ಯಾವುದೇ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
4. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉದಾಹರಣೆಗಳು:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ಪರೀಕ್ಷಣ

ಪರೀಕ್ಷೆಗಳ ನಡುವೆ ತಿಳಿದಿರುವ ಸ್ಥಿತಿಯಿಂದ ಪ್ರಾರಂಭಿಸಲು `resetGuardrailsForTests()` ಬಳಸಿ.
ಖಾಲಿ ರಿಜಿಸ್ಟ್ರಿಯೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಲು ಮತ್ತು ಪರೀಕ್ಷೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಮಾತ್ರ
ನೋಂದಾಯಿಸಲು `{ registerDefaults: false }` ಅನ್ನು ರವಾನಿಸಿ. Vision Bridge ಡಿಪೆಂಡೆನ್ಸಿ
ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge
ಸೆಟ್ಟಿಂಗ್ಗಳು, ಸಾಮರ್ಥ್ಯಗಳು, STT ಮಾದರಿ ಆಯ್ಕೆ, ರುಜುವಾತು ಪರಿಶೀಲನೆಗಳು ಮತ್ತು
ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಶನ್ಗಾಗಿ ಸಮಾನ ಸೀಮ್ಗಳನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು DB ಅಥವಾ
ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶವಿಲ್ಲದೆ ಎರಡೂ ಹರಿವುಗಳನ್ನು ಚಾಲನೆ ಮಾಡಬಹುದು.

## ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ರೂಟ್ ಕವರೇಜ್ ಮತ್ತು ರೆಡ್-ಟೀಮ್ (ಹಂತ 8 · ಬ್ಲಾಕ್ D)

ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ (`createInjectionGuard` / `withInjectionGuard`) ಬಳಕೆದಾರ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು
ಸ್ವೀಕರಿಸುವ ಎಲ್ಲಾ ರೂಟ್ಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ. ಇದು `INJECTION_GUARD_MODE` ಅನ್ನು ಗೌರವಿಸುತ್ತದೆ
(ಡೀಫಾಲ್ಟ್ `warn` = ಲಾಗ್ ಮಾತ್ರ; `block` = HTTP 400 `SECURITY_001` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ).

| ಪ್ರಕಾರ                      | ರೂಟ್ಗಳು                                                                                                                                              | ಡೀಫಾಲ್ಟ್ ಮೋಡ್ |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| ಟೆಕ್ಸ್ಟ್ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| ಜನರೇಟಿವ್                    | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| ಡೇಟಾ                        | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

ಟೆಕ್ಸ್ಟ್ ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ.

**ರೆಡ್-ಟೀಮ್ (ರಾತ್ರಿಕಾಲದ, `nightly-llm-security.yml`):** promptfoo ಪ್ರತಿ ರೂಟ್
`INJECTION_GUARD_MODE=block` ನಲ್ಲಿ OWASP-LLM ಕಾರ್ಪಸ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಎಂದು
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; garak ಪ್ರೋಬ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ).
ಸ್ಥಿರತೆಗಾಗಿ `moderations` ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ. ಬ್ಲಾಕ್ ಮೋಡ್ ಕಡ್ಡಾಯ ಗಡಿಯಾಗಿದೆ:
`evaluatePromptInjection()` ಮಿಡಲ್ವೇರ್ ಅದಕ್ಕೆ ರವಾನಿಸುವ ಪ್ರತಿ-ವಿನಂತಿಯ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವ
ಪಟ್ಟಿಯನ್ನು ನಿರ್ಲಕ್ಷಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ `disabledGuardrails` ರೂಟ್ ಅನ್ನು ಇದರಿಂದ ವಿನಾಯಿತಿ
ನೀಡುವುದಿಲ್ಲ ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

ರಾತ್ರಿಕಾಲದ ವರ್ಕ್ಫ್ಲೋ (`.github/workflows/nightly-llm-security.yml`, cron + ಮ್ಯಾನುಯಲ್
ಡಿಸ್ಪ್ಯಾಚ್) ಎರಡು ಜಾಬ್ಗಳನ್ನು ಹೊಂದಿದೆ:

- **`promptfoo-guard` (ಬ್ಲಾಕಿಂಗ್)** — `INJECTION_GUARD_MODE=block` ನೊಂದಿಗೆ
  `promptfoo eval -c promptfooconfig.yaml` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರತಿ ಎಡ್ವರ್ಸರಿಯಲ್
  ಕೇಸ್ (ಉದಾ. "ignore all previous instructions…", DAN-ಶೈಲಿಯ ಜೈಲ್ಬ್ರೇಕ್ಗಳು)
  ಪ್ರತಿಕ್ರಿಯೆಯು `error.code === "SECURITY_001"` ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ ಎಂದು
  ಖಚಿತಪಡಿಸುತ್ತದೆ, ಅಂದರೆ ಗಾರ್ಡ್ ನಿಜವಾಗಿಯೂ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಿದೆ ಎಂದು.
- **`garak` (ಅಡ್ವೈಸರಿ)** — ಸ್ಥಳೀಯ OmniRoute ಇನ್ಸ್ಟನ್ಸ್
  (`http://localhost:20128/v1`) ವಿರುದ್ಧ garak `--probes promptinject,dan,leakreplay`
  ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರೊವೈಡರ್ ಸೀಕ್ರೆಟ್ (`PROMPTFOO_PROVIDER_KEY`) ಮೇಲೆ ಗೇಟ್ ಆಗಿದೆ;
  ಸುಗಮವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು `|| true` ಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿದೆ, ಆದ್ದರಿಂದ CI ಅನ್ನು
  ವಿಫಲಗೊಳಿಸದೆ ವರದಿ ಮಾಡುತ್ತದೆ.

ಗಾರ್ಡ್ ಹೆಲ್ಪರ್ (`createInjectionGuard` / `withInjectionGuard`) ಕವರೇಜ್ ಪ್ರಾಂಪ್ಟ್ ಹೊಂದಿರುವ
ಪ್ರತಿ `/v1` ರೂಟ್ ಅನ್ನು ವ್ಯಾಪಿಸುತ್ತದೆ; `src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿರುವ
`extractMessageContents()` ಮೂಲಕ `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
ನಿಂದ ಪ್ರಾಂಪ್ಟ್ ಟೆಕ್ಸ್ಟ್ ಅನ್ನು ತೆಗೆಯಲಾಗುತ್ತದೆ.
