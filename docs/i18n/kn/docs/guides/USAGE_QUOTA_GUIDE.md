> **ಸಂಕ್ಷಿಪ್ತವಾಗಿ**: OmniRoute ಪ್ರತಿ ವಿನಂತಿಯ ಟೋಕನ್ ಬಳಕೆಯನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ, ವೆಚ್ಚವನ್ನು ಲೆಕ್ಕಾಚಾರ ಮಾಡುತ್ತದೆ, ಪ್ರತಿ API ಕೀಗೆ ಕೋಟಾವನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ವಿಶ್ಲೇಷಣೆಯನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ. ಇವೆಲ್ಲವೂ ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ ಎಂಬುದನ್ನು ಈ ಮಾರ್ಗದರ್ಶಿ ವಿವರಿಸುತ್ತದೆ.

**ಮೂಲಗಳು:**

- `open-sse/services/usage.ts` (~70KB) — ಮುಖ್ಯ ಬಳಕೆ ಟ್ರ್ಯಾಕಿಂಗ್
- `src/lib/usageAnalytics.ts` (~10KB) — ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಾಗಿ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ
- `src/lib/db/quotaSnapshots.ts` — ಐತಿಹಾಸಿಕ ಕೋಟಾ ಡೇಟಾ
- `src/lib/db/usage*.ts` — ಬಳಕೆಗೆ ಸಂಬಂಧಿಸಿದ ಹಲವು DB ಮಾಡ್ಯೂಲ್ಗಳು

## ಅವಲೋಕನ

OmniRoute ಮೂಲಕ ಸಾಗುವ ಪ್ರತಿಯೊಂದು ವಿನಂತಿಯೂ ಈ ವಿವರಗಳನ್ನು ದಾಖಲಿಸುವ **ಬಳಕೆ ದಾಖಲೆ**ಯನ್ನು ರಚಿಸುತ್ತದೆ:

- **ಗುರುತು**: ಯಾವ API ಕೀ, ಪೂರೈಕೆದಾರ, ಮಾದರಿ, ಕಾಂಬೊ
- **ಟೋಕನ್ಗಳು**: ಪ್ರಾಂಪ್ಟ್ ಟೋಕನ್ಗಳು, ಪೂರ್ಣಗೊಳಿಸುವಿಕೆ ಟೋಕನ್ಗಳು, ಕ್ಯಾಶ್ ಮಾಡಿದ ಟೋಕನ್ಗಳು, ಒಟ್ಟು
- **ವೆಚ್ಚ**: USD ಮೊತ್ತ (ಬೆಲೆ ಡೇಟಾದಿಂದ ಲೆಕ್ಕಾಚಾರ ಮಾಡಲಾಗಿದೆ)
- **ಸಮಯ**: ವಿಳಂಬ, ಪ್ರಾರಂಭ/ಅಂತ್ಯದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ಗಳು
- **ಸ್ಥಿತಿ**: ಯಶಸ್ಸು, ದೋಷ, ದರ-ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ, ಇತ್ಯಾದಿ.

ಈ ದಾಖಲೆಗಳನ್ನು **ವಿಶ್ಲೇಷಣೆ**ಯಾಗಿ ಒಟ್ಟುಗೂಡಿಸಲಾಗುತ್ತದೆ, **ಕೋಟಾ ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಳು** ಆಗಿ ಉಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು **ಪ್ರತಿ-ಕೀ ಬಜೆಟ್ ಮಿತಿಗಳನ್ನು** ಜಾರಿಗೊಳಿಸಲು ಬಳಸಲಾಗುತ್ತದೆ.

```
ವಿನಂತಿ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ವಿಶ್ಲೇಷಣೆ   ಕೋಟಾ    ಬಿಲ್ಲಿಂಗ್
                   (ಡ್ಯಾಶ್ಬೋರ್ಡ್) (ಜಾರಿ) (ರಫ್ತು)
```

## ಏನನ್ನು ದಾಖಲಿಸಲಾಗುತ್ತದೆ

`usage.ts` ಸೇವೆಯು ಪ್ರತಿ ವಿನಂತಿಗೂ ಒಂದು **ಬಳಕೆಯ ಘಟನೆಯನ್ನು** ದಾಖಲಿಸುತ್ತದೆ:

| ಕ್ಷೇತ್ರ            | ವಿಧ     | ಮೂಲ                                                            |
| ------------------ | ------- | -------------------------------------------------------------- |
| `id`               | string  | ದಾಖಲಿಸುವಾಗ ರಚಿಸಲಾದ UUID                                        |
| `apiKeyId`         | string  | ವಿನಂತಿಯನ್ನು ಪ್ರಾರಂಭಿಸಿದ API ಕೀಲಿ                               |
| `provider`         | string  | ಪೂರೈಕೆದಾರರ ID (openai, anthropic, ಇತ್ಯಾದಿ)                     |
| `model`            | string  | ಮಾಡೆಲ್ ID (gpt-5, claude-opus-4-6, ಇತ್ಯಾದಿ)                    |
| `comboId`          | string? | ಕಾಂಬೊ ಮೂಲಕ ರವಾನಿಸಿದ್ದರೆ ಕಾಂಬೊ ID                               |
| `promptTokens`     | number  | ಅಪ್‌ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ                                   |
| `completionTokens` | number  | ಅಪ್‌ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ                                   |
| `cachedTokens`     | number  | ಕ್ಯಾಶ್ ಹಿಟ್ ಟೋಕನ್‌ಗಳು (Anthropic ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶಿಂಗ್, ಇತ್ಯಾದಿ) |
| `totalTokens`      | number  | ಪ್ರಾಂಪ್ಟ್ + ಪೂರ್ಣಗೊಳಿಸುವಿಕೆ                                    |
| `costUsd`          | number  | ಬೆಲೆ ದತ್ತಾಂಶದಿಂದ ಲೆಕ್ಕಹಾಕಲಾಗುತ್ತದೆ                             |
| `latencyMs`        | number  | ವಿನಂತಿಯ ಆರಂಭದಿಂದ ಅಂತ್ಯದವರೆಗಿನ ಅವಧಿ                             |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`     |
| `errorClass`       | string? | ಸ್ಥಿತಿ ಯಶಸ್ವಿಯಾಗಿಲ್ಲದಿದ್ದರೆ ದೋಷ ವರ್ಗ                           |
| `timestamp`        | string  | ISO 8601 UTC                                                   |
| `metadata`         | object  | ಪ್ಲಗಿನ್ ಸೇರಿಸಿದ ಕಸ್ಟಮ್ ದತ್ತಾಂಶ                                 |

### ಟೋಕನ್‌ಗಳು ಎಲ್ಲಿಂದ ಬರುತ್ತವೆ

ಅಪ್‌ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ **ಪ್ರತಿಕ್ರಿಯೆ ನಿರ್ವಹಕದಲ್ಲಿ** ಟೋಕನ್‌ಗಳನ್ನು ಹೊರತೆಗೆಯಲಾಗುತ್ತದೆ:

```ts
// open-sse/handlers/chatCore.ts ನಿಂದ
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

ಬಳಕೆಯ ಮಾಹಿತಿಯನ್ನು ಹಿಂತಿರುಗಿಸದ ಪೂರೈಕೆದಾರರಿಗೆ (ಕೆಲವು ವೆಬ್-ಕುಕೀ ಪೂರೈಕೆದಾರರು), OmniRoute `~4 chars per token` ಅಂದಾಜು ನಿಯಮವನ್ನು ಬಳಸಿ ಟೋಕನ್‌ಗಳನ್ನು **ಅಂದಾಜಿಸುತ್ತದೆ** (`open-sse/services/autoCombo/pipelineRouter.ts` ನೋಡಿ).

### ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಟೋಕನ್‌ಗಳು

OmniRoute `cached_tokens` ಅನ್ನು `prompt_tokens` ನಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿ ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ, ಏಕೆಂದರೆ:

- Anthropic ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶಿಂಗ್ ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಟೋಕನ್‌ಗಳಿಗೆ ಕಡಿಮೆ ದರವನ್ನು ವಿಧಿಸುತ್ತದೆ (ಸಾಮಾನ್ಯ ದರದ 10%)
- ಕೆಲವು ಪೂರೈಕೆದಾರರು `cache_read_input_tokens` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತಾರೆ; ಇವುಗಳಿಗೆ ವಿಭಿನ್ನ ದರವನ್ನು ಅನ್ವಯಿಸಬೇಕು
- ವಿಶ್ಲೇಷಣೆಯಲ್ಲಿ **ಕ್ಯಾಶ್ ಹಿಟ್ ದರ** = `cached_tokens / prompt_tokens` ಅನ್ನು ತೋರಿಸಬಹುದು

### ಕ್ಯಾಶ್-ಬರೆಯುವಿಕೆ ಶ್ರೇಣಿಯ ರೋಗನಿರ್ಣಯಗಳು

ವಿಶ್ಲೇಷಣೆ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್‌ನ ಪ್ರಾಂಪ್ಟ್-ಕ್ಯಾಶ್ ಆರೋಗ್ಯ ಫಲಕವು ಪೂರೈಕೆದಾರರು ವರದಿ ಮಾಡಿದ
5-ನಿಮಿಷ ಮತ್ತು 1-ಗಂಟೆಯ ಕ್ಯಾಶ್ ಬರೆಯುವಿಕೆಗಳನ್ನು ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ. Anthropic ನ
`usage.cache_creation.ephemeral_5m_input_tokens` ಮತ್ತು
`usage.cache_creation.ephemeral_1h_input_tokens` ಅನ್ನು ಸ್ಟ್ರೀಮಿಂಗ್ ಮತ್ತು
ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದ ಬಳಕೆ ಪರಿವರ್ತನೆಯಾದ್ಯಂತ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ ಮತ್ತು ಕರೆ-ಲಾಗ್ ಸಾರಾಂಶಗಳೊಂದಿಗೆ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ. ಒಟ್ಟು
ಕ್ಯಾಶ್-ಬರೆಯುವಿಕೆಯ ಮೊತ್ತವನ್ನು ಆ ವಿಭಾಗಗಳಿಗೆ ಎರಡನೇ ಬಾರಿ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ.

ಹಳೆಯ ದಾಖಲೆಗಳೂ ಸೇರಿದಂತೆ, ಕೇವಲ ಒಟ್ಟು ಬರೆಯುವಿಕೆ ಕೌಂಟರ್ ಹೊಂದಿರುವ ಕರೆಗಳ ಶ್ರೇಣಿ
ಅಜ್ಞಾತವಾಗಿರುತ್ತದೆ. ಭಾಗಶಃ ವಿಭಜನೆ ಇದ್ದರೆ, ಅದರ ಹಂಚಿಕೆಯಾಗದ ಉಳಿದ ಭಾಗವನ್ನು ಅಜ್ಞಾತವಾಗಿಯೇ ಉಳಿಸಲಾಗುತ್ತದೆ; ಅಮಾನ್ಯ ಅಥವಾ
ಪರಸ್ಪರ ವಿರೋಧಿ ಕೌಂಟರ್‌ಗಳಿಗೆ ಮೌನವಾಗಿ TTL ನಿಯೋಜಿಸುವ ಬದಲು ಅವುಗಳನ್ನು ಗುರುತಿಸಲಾಗುತ್ತದೆ. ವಿನಂತಿಯ ಕಡೆಯ
TTL ಗುರುತುಗಳು ಬಿಲ್ ಮಾಡಲಾದ ಶ್ರೇಣಿಗೆ ಸಾಕ್ಷಿಯಲ್ಲ.

ಫಲಕದ API-ಸಮಾನ ಬರೆಯುವಿಕೆ ಅಂದಾಜು ವರದಿ ಮಾಡಲಾದ, ಬೆಲೆ ನಿಗದಿಪಡಿಸಲಾದ ಶ್ರೇಣಿಗಳನ್ನು ಮಾತ್ರ ಒಳಗೊಳ್ಳುತ್ತದೆ,
ಸಂಪೂರ್ಣ ವಿನಂತಿಯನ್ನಲ್ಲ. ಸ್ಥಳೀಯ Claude/Anthropic ಮಾಡೆಲ್ ಬೆಲೆ ನಿಗದಿಗೆ, ಇದು
5-ನಿಮಿಷದ ಬರೆಯುವಿಕೆಗಳಿಗೆ ಇನ್‌ಪುಟ್ ದರದ 1.25 ಪಟ್ಟು ಮತ್ತು 1-ಗಂಟೆಯ ಬರೆಯುವಿಕೆಗಳಿಗೆ ಇನ್‌ಪುಟ್ ದರದ ಎರಡು ಪಟ್ಟು ಬಳಸುತ್ತದೆ. ಬೆಲೆ
ಮಾಹಿತಿ ಇಲ್ಲದಿದ್ದರೆ ಅದು ಲಭ್ಯವಿಲ್ಲ ಎಂದರ್ಥ, ಶೂನ್ಯವಲ್ಲ. ಪ್ರತಿ ಹೊಸ ಕರೆಯನ್ನು ದಾಖಲಿಸುವಾಗ ಬೆಲೆಗಳನ್ನು ಸೆರೆಹಿಡಿಯಲಾಗುತ್ತದೆ;
ಐತಿಹಾಸಿಕ ದಾಖಲೆಗಳಿಗೆ ಮರುಬೆಲೆ ನಿಗದಿಪಡಿಸಲಾಗುವುದಿಲ್ಲ. ಆದ್ದರಿಂದ ಚಂದಾದಾರಿಕೆ ಖಾತೆಗಳು
ಆ ಮೊತ್ತವನ್ನು ನಗದು ವೆಚ್ಚವಾಗಿ ಭರಿಸದೆ ಅಥವಾ ಚಂದಾದಾರಿಕೆ
ಕೋಟಾದಿಂದ ಕಡಿತವಾಗದೆ API-ಸಮಾನ ಅಂದಾಜನ್ನು ಹೊಂದಿರಬಹುದು. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕೋಟಾ, ಬಜೆಟ್ ಮತ್ತು ಪೂರೈಕೆದಾರರ ನಿಖರ ವೆಚ್ಚದ ಲೆಕ್ಕಾಚಾರಗಳು ಬದಲಾಗುವುದಿಲ್ಲ.

ಈ ರೋಗನಿರ್ಣಯಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಮಿತಿಗೊಳಿಸಿದ ಕ್ಯಾಶ್-ಆರೋಗ್ಯ ಸಾರಾಂಶ ಮತ್ತು ಕರೆ-ಲಾಗ್
ಉಳಿಸಿಕೊಳ್ಳುವಿಕೆಯನ್ನು ಬಳಸುತ್ತವೆ. ಇವು ವಿನಂತಿಯ ಡೀಫಾಲ್ಟ್ TTL ಮೌಲ್ಯಗಳು, ರೂಟಿಂಗ್ ಅಥವಾ ಖಾತೆ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.
ಪೂರೈಕೆದಾರರಿಗೆ ಕಳುಹಿಸುವ ಗಡಿಯಲ್ಲಿ ಕ್ಲೈಂಟ್ ವಿನಂತಿಸಿದ TTL ಮತ್ತು ಪರಿಣಾಮಕಾರಿಯಾಗಿ ಹೊರಹೋಗುವ TTL ಅನ್ನು
ಸೆರೆಹಿಡಿಯುವುದನ್ನು ಮುಂದೂಡಲಾಗಿದೆ; ಈ ಫಲಕವು ಸ್ವೀಕೃತಿ ಶ್ರೇಣಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ, ಪರಿಣಾಮಕಾರಿಯಾಗಿ ಹೊರಹೋಗುವ TTL ಅನ್ನಲ್ಲ.

ಅನುಷ್ಠಾನ: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, ಮತ್ತು `open-sse/utils/cacheWriteUsage.ts`.

## ವೆಚ್ಚದ ಲೆಕ್ಕಾಚಾರ

LiteLLM ನಿಂದ ಸಿಂಕ್ ಮಾಡಲಾದ **ಬೆಲೆ ದತ್ತಾಂಶ** (`src/lib/pricingSync.ts`) ಬಳಸಿ ವೆಚ್ಚಗಳನ್ನು ಲೆಕ್ಕಹಾಕಲಾಗುತ್ತದೆ:

| ಮಾದರಿ             | ಇನ್ಪುಟ್ $/1M | ಔಟ್ಪುಟ್ $/1M | ಕ್ಯಾಶ್ ಮಾಡಿದ $/1M |
| ----------------- | ------------ | ------------ | ----------------- |
| gpt-5             | $2.50        | $10.00       | —                 |
| claude-opus-4-6   | $15.00       | $75.00       | $1.50             |
| claude-sonnet-4-5 | $3.00        | $15.00       | $0.30             |
| gemini-2.5-pro    | $1.25        | $10.00       | —                 |

ವೆಚ್ಚದ ಸೂತ್ರ (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **ಪ್ರಾಂಪ್ಟ್ನಿಂದ ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಭಾಗವನ್ನು ಏಕೆ ಕಳೆಯಬೇಕು?** ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಭಾಗಕ್ಕೆ ಪ್ರತ್ಯೇಕವಾಗಿ ಬೆಲೆ ನಿಗದಿಪಡಿಸಲಾಗುತ್ತದೆ; ಸಂಪೂರ್ಣ ಪ್ರಾಂಪ್ಟ್ಗೆ ಇನ್ಪುಟ್ ಬೆಲೆಯನ್ನು ವಿಧಿಸಿದರೆ ಹೆಚ್ಚುವರಿಯಾಗಿ ಲೆಕ್ಕ ಹಾಕಿದಂತಾಗುತ್ತದೆ.

### ಬೆಲೆ ಸಿಂಕ್

ಅಂತರ್ನಿರ್ಮಿತ cron ಕಾರ್ಯದಿಂದ ಪ್ರಚೋದಿಸಲ್ಪಡುವ `/api/pricing/sync` ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ LiteLLM ನಿಂದ ಬೆಲೆ ದತ್ತಾಂಶವು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸಿಂಕ್ ಆಗುತ್ತದೆ (ಇದು ಬಳಕೆದಾರರಿಗೆ ಲಭ್ಯವಿರುವ env var ಅಲ್ಲ):

```bash
# ಹಸ್ತಚಾಲಿತ ಪ್ರಚೋದನೆ
curl -X POST http://localhost:20128/api/pricing/sync
```

ಬೆಲೆ ದತ್ತಾಂಶವಿಲ್ಲದ ಮಾದರಿಗಳಿಗೆ, ಆಂತರಿಕ ಸರಾಸರಿ ದರಗಳನ್ನು (LiteLLM ನ ಬೆಲೆ ದತ್ತಾಂಶದಿಂದ ಪಡೆದವು) ಬಳಸಿಕೊಂಡು **ವೆಚ್ಚವನ್ನು ಅಂದಾಜಿಸುವುದಕ್ಕೆ** OmniRoute ಹಿಂತಿರುಗುತ್ತದೆ.

## ದಿನಾಂಕ ವ್ಯಾಪ್ತಿಯ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ

`usageAnalytics.ts` ಮಾಡ್ಯೂಲ್ ಕಚ್ಚಾ ಬಳಕೆಯ ದತ್ತಾಂಶದಿಂದ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ವಿಜೆಟ್‌ಗಳನ್ನು ಲೆಕ್ಕಾಚಾರ ಮಾಡುತ್ತದೆ. ಇದು 7 ಸಮಯ ವ್ಯಾಪ್ತಿಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ:

| ವ್ಯಾಪ್ತಿ | ಅವಧಿ                               | ಬಳಕೆಯ ಸಂದರ್ಭ                          |
| -------- | ---------------------------------- | ------------------------------------- |
| `1d`     | ಕಳೆದ 24 ಗಂಟೆಗಳು                    | ಗಂಟೆಗೊಮ್ಮೆ ವೆಚ್ಚದ ದಿಢೀರ್ ಏರಿಕೆ ಪತ್ತೆ  |
| `7d`     | ಕಳೆದ 7 ದಿನಗಳು                      | ಸಾಪ್ತಾಹಿಕ ಪರಿಶೀಲನೆ                    |
| `30d`    | ಕಳೆದ 30 ದಿನಗಳು                     | ಮಾಸಿಕ ಬಿಲ್ಲಿಂಗ್                       |
| `90d`    | ಕಳೆದ 90 ದಿನಗಳು                     | ತ್ರೈಮಾಸಿಕ ವಿಶ್ಲೇಷಣೆ                   |
| `ytd`    | ಪ್ರಸ್ತುತ ವರ್ಷದ ಜನವರಿ 1 ರಿಂದ        | ವಾರ್ಷಿಕ ಬಜೆಟ್ ಟ್ರ್ಯಾಕಿಂಗ್             |
| `all`    | ಸಂಪೂರ್ಣ ಅವಧಿ                       | ಜೀವಿತಾವಧಿಯ ಅಂಕಿಅಂಶಗಳು                 |
| `custom` | ಬಳಕೆದಾರರು ನಿರ್ಧರಿಸಿದ ಪ್ರಾರಂಭ/ಅಂತ್ಯ | ಲೆಕ್ಕಪರಿಶೋಧನೆಗಳು, ತಾತ್ಕಾಲಿಕ ಕ್ವೆರಿಗಳು |

### ಲೆಕ್ಕಾಚಾರ ಮಾಡಲಾಗುವ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ವಿಜೆಟ್‌ಗಳು

ಯಾವುದೇ ದಿನಾಂಕ ವ್ಯಾಪ್ತಿಗೆ, ವಿಶ್ಲೇಷಣಾ ಪದರವು ಇವುಗಳನ್ನು ಲೆಕ್ಕಾಚಾರ ಮಾಡುತ್ತದೆ:

| ವಿಜೆಟ್                       | ವಿವರಣೆ                                                    |
| ---------------------------- | --------------------------------------------------------- |
| **ಸಾರಾಂಶ ಕಾರ್ಡ್‌ಗಳು**        | ಒಟ್ಟು ವಿನಂತಿಗಳು, ಒಟ್ಟು ವೆಚ್ಚ, ಒಟ್ಟು ಟೋಕನ್‌ಗಳು, ಯಶಸ್ಸಿನ ದರ |
| **ದೈನಂದಿನ ಪ್ರವೃತ್ತಿ ಚಾರ್ಟ್** | ದಿನಕ್ಕೆ ವೆಚ್ಚ + ಟೋಕನ್‌ಗಳು, ಮಾದರಿಯ ಪ್ರಕಾರ ಜೋಡಿಸಲಾದವು       |
| **ಚಟುವಟಿಕೆಯ ಹೀಟ್‌ಮ್ಯಾಪ್**    | ದಿನದ ಗಂಟೆ × ವಾರದ ದಿನದ ಗ್ರಿಡ್, ಬಣ್ಣ = ವಿನಂತಿಗಳ ಸಂಖ್ಯೆ      |
| **ಮಾದರಿವಾರು ವಿಂಗಡಣೆ**        | ಮಾದರಿವಾರು ವೆಚ್ಚದ ಪೈ ಚಾರ್ಟ್                                |
| **ಪೂರೈಕೆದಾರವಾರು ವಿಂಗಡಣೆ**    | ಪೂರೈಕೆದಾರವಾರು ವಿನಂತಿಗಳ ಬಾರ್ ಚಾರ್ಟ್                        |
| **ಅಗ್ರ API ಕೀಗಳು**           | ವೆಚ್ಚದ ಆಧಾರದ ಮೇಲೆ ಅಗ್ರ 10 ಕೀಗಳ ಕೋಷ್ಟಕ                     |
| **ದೋಷ ವಿಶ್ಲೇಷಣೆ**            | ಕಾಲಾನುಗತ ದೋಷದ ದರ, ಪ್ರಮುಖ ದೋಷ ವರ್ಗಗಳು                      |

### ಪ್ರೋಗ್ರಾಮ್ ಮೂಲಕ ಪ್ರವೇಶ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // ಬಳಕೆಯ ಇತಿಹಾಸದ ದಾಖಲೆಗಳು
  "7d",                 // ಸಮಯ ವ್ಯಾಪ್ತಿ: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕ ಮ್ಯಾಪ್ (connectionId → ಖಾತೆಯ ಹೆಸರು)
  {
    startDate: "2025-01-01",  // ಐಚ್ಛಿಕ: "custom" ವ್ಯಾಪ್ತಿಗಾಗಿ
    endDate: "2025-06-01",   // ಐಚ್ಛಿಕ: "custom" ವ್ಯಾಪ್ತಿಗಾಗಿ
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (ಸೆಂಟ್‌ಗಳು)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ಕೋಟಾ ಜಾರಿ

ಪ್ರತಿ API ಕೀಯ ಕೋಟಾವನ್ನು ಎರಡು ಸ್ಥಳಗಳಲ್ಲಿ ಜಾರಿಗೊಳಿಸಲಾಗುತ್ತದೆ:

1. **ಮೃದು ಮಿತಿ** (`quotaWarnAt`): ಬಳಕೆಯು ನಿಗದಿತ ಮಿತಿಯನ್ನು ಮೀರಿದಾಗ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್‌ನಲ್ಲಿ ಎಚ್ಚರಿಕೆ
2. **ಕಠಿಣ ಮಿತಿ** (`quotaLimit`): ಮಿತಿಯನ್ನು ಮೀರಿದಾಗ HTTP 429 ನೊಂದಿಗೆ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ

### ಸಂರಚನೆ

```ts
// ಪ್ರತಿ API ಕೀಗೆ
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — ಎಚ್ಚರಿಕೆ ತೋರಿಸಿ
  quotaLimit: 10_00,    // $10.00 — ಸಂಪೂರ್ಣ ತಡೆ
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### ಜಾರಿ ಪ್ರಕ್ರಿಯೆ

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### ಕೋಟಾ ಸ್ನ್ಯಾಪ್‌ಶಾಟ್‌ಗಳು

ಪ್ರವೃತ್ತಿ ವಿಶ್ಲೇಷಣೆಗಾಗಿ `quotaSnapshots` ಕೋಷ್ಟಕವು **ಐತಿಹಾಸಿಕ ಕೋಟಾ ಸ್ಥಿತಿಯನ್ನು** ಸಂಗ್ರಹಿಸುತ್ತದೆ:

| ಕ್ಷೇತ್ರ | ವಿವರಣೆ |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿರುವ ಕೀ |
| `window` | "day" | "week" | "month" |
| `used` | ಈ ಅವಧಿಯಲ್ಲಿ ಬಳಸಿದ ವೆಚ್ಚ (ಸೆಂಟ್‌ಗಳು) |
| `limit` | ಮಿತಿ (ಸೆಂಟ್‌ಗಳು) |
| `resetAt` | ಅವಧಿಯು ಮರುಹೊಂದುವ ಸಮಯ |
| `createdAt` | ಸ್ನ್ಯಾಪ್‌ಶಾಟ್ ತೆಗೆದ ಸಮಯ |

ವೆಚ್ಚವು > 0 ಇರುವ **ಪ್ರತಿ ವಿನಂತಿಯಲ್ಲೂ** ಸ್ನ್ಯಾಪ್‌ಶಾಟ್‌ಗಳನ್ನು ತೆಗೆದುಕೊಳ್ಳಲಾಗುತ್ತದೆ, ಮತ್ತು ಅವುಗಳನ್ನು ಈ ಉದ್ದೇಶಗಳಿಗೆ ಬಳಸಲಾಗುತ್ತದೆ:

- ಡ್ಯಾಶ್‌ಬೋರ್ಡ್‌ನಲ್ಲಿ ಕೋಟಾ ಪ್ರಗತಿ ಪಟ್ಟಿಯನ್ನು ಪ್ರದರ್ಶಿಸಲು
- 30 ದಿನಗಳ ಕೋಟಾ ಪ್ರವೃತ್ತಿ ಚಾರ್ಟ್‌ಗಳನ್ನು ತೋರಿಸಲು
- ಬಳಕೆಯು ಮಿತಿಯನ್ನು ಸಮೀಪಿಸಿದಾಗ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಪ್ರಚೋದಿಸಲು

### ಬಳಕೆಯ ವಿಶ್ಲೇಷಣೆಯನ್ನು ಪ್ರಶ್ನಿಸಿ

ಬಳಕೆಯ ಡೇಟಾವನ್ನು ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಅಥವಾ MCP ಪರಿಕರಗಳ ಮೂಲಕ ಪ್ರವೇಶಿಸಲಾಗುತ್ತದೆ, ನೇರ REST ರಫ್ತು ಎಂಡ್‌ಪಾಯಿಂಟ್‌ಗಳ ಮೂಲಕ ಅಲ್ಲ. ಲಭ್ಯವಿರುವ ವಿಶ್ಲೇಷಣೆಗಳು:

- **`/api/usage/analytics`** — ಒಟ್ಟುಗೂಡಿಸಿದ ಬಳಕೆಯ ಮಾಪನಗಳು (ಮಾದರಿ, ಪೂರೈಕೆದಾರ, ಕೀ ಆಧಾರಿತ ಗುಂಪು)
- **`/api/usage/quota`** — ಪ್ರತಿ API ಕೀಯ ಪ್ರಸ್ತುತ ಕೋಟಾ ಸ್ಥಿತಿ
- **`/api/usage/history`** — ವಿನಂತಿಗಳ ಇತಿಹಾಸದ ಲಾಗ್‌ಗಳು

## MCP ಪರಿಕರಗಳು

ಎರಡು MCP ಪರಿಕರಗಳು ಏಜೆಂಟ್‌ಗಳಿಗೆ ಬಳಕೆಯ ಡೇಟಾವನ್ನು ಒದಗಿಸುತ್ತವೆ (`open-sse/mcp-server/tools/` ನೋಡಿ):

| ಪರಿಕರ                   | ವಿವರಣೆ                                                 |
| ----------------------- | ------------------------------------------------------ |
| `omniroute_cost_report` | ನಿರ್ದಿಷ್ಟ ಅವಧಿಗೆ ಪ್ರತಿ ಕೀಯ ವೆಚ್ಚದ ವರದಿಯನ್ನು ರಚಿಸುತ್ತದೆ |
| `omniroute_check_quota` | API ಕೀಯ ಪ್ರಸ್ತುತ ಕೋಟಾ ಸ್ಥಿತಿಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ     |

ಏಜೆಂಟ್ ಕರೆಯ ಉದಾಹರಣೆ:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## ಉಳಿಸಿಕೊಳ್ಳುವಿಕೆ ಮತ್ತು ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ

ಪ್ರತಿ ವಿನಂತಿಗೆ ಬಳಕೆಯ ಡೇಟಾ ~1-10KB ಹೆಚ್ಚಾಗುತ್ತದೆ. ದೊಡ್ಡ ಪ್ರಮಾಣದಲ್ಲಿ, ಇದು ಗಣನೀಯವಾಗಿರಬಹುದು.

### ಉಳಿಸಿಕೊಳ್ಳುವಿಕೆಯ ಸೆಟ್ಟಿಂಗ್‌ಗಳು

ಬಳಕೆಯ ಇತಿಹಾಸವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುವಿಕೆಯನ್ನು UI ನಲ್ಲಿನ ಡೇಟಾಬೇಸ್ ಸೆಟ್ಟಿಂಗ್‌ಗಳ ಮೂಲಕ ಅಥವಾ `/api/settings/database` ಮೂಲಕ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾಗುತ್ತದೆ.

ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ, ಬಳಕೆಯ ಇತಿಹಾಸವನ್ನು **90 ದಿನಗಳವರೆಗೆ** ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

### ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ

ಹಳೆಯ ದಾಖಲೆಗಳನ್ನು `src/lib/db/cleanup.ts` ಮೂಲಕ ಸ್ವಚ್ಛಗೊಳಿಸಲಾಗುತ್ತದೆ:

- ಹಿನ್ನೆಲೆಯ cron ಪ್ರಕ್ರಿಯೆಯಿಂದ ಪ್ರಚೋದಿಸಲಾಗುತ್ತದೆ
- ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ `usageHistory` ಉಳಿಸಿಕೊಳ್ಳುವಿಕೆಯ ಅವಧಿಗಿಂತ ಹಳೆಯ ದಾಖಲೆಗಳನ್ನು `usage_history` ನಿಂದ ಅಳಿಸುತ್ತದೆ

### ಸಂಗ್ರಹಣೆಯ ಅಂದಾಜು

| ವಿನಂತಿ ದರ             | 30 ದಿನಗಳ ಸಂಗ್ರಹಣೆ | 90 ದಿನಗಳ ಸಂಗ್ರಹಣೆ |
| --------------------- | ----------------- | ----------------- |
| 100 ವಿನಂತಿಗಳು/ದಿನ     | ~3MB              | ~9MB              |
| 1,000 ವಿನಂತಿಗಳು/ದಿನ   | ~30MB             | ~90MB             |
| 10,000 ವಿನಂತಿಗಳು/ದಿನ  | ~300MB            | ~900MB            |
| 100,000 ವಿನಂತಿಗಳು/ದಿನ | ~3GB              | ~9GB              |

ಅತಿ ಹೆಚ್ಚಿನ ಟ್ರಾಫಿಕ್‌ಗಾಗಿ, ಇವುಗಳನ್ನು ಪರಿಗಣಿಸಿ:

- ಡೇಟಾಬೇಸ್ ಸೆಟ್ಟಿಂಗ್‌ಗಳ ಮೂಲಕ ಉಳಿಸಿಕೊಳ್ಳುವಿಕೆಯ ಅವಧಿಯನ್ನು ಕಡಿಮೆ ಮಾಡುವುದು
- ಮೂಲ ದಾಖಲೆಗಳ ಬದಲಿಗೆ `aggregated_metrics` ಬಳಸುವುದು (ವಿಶ್ಲೇಷಣೆಗಾಗಿ ಮಾತ್ರ)

## ವೆಚ್ಚ ಆಪ್ಟಿಮೈಸೇಶನ್ ಸಲಹೆಗಳು

### 1. ಸರಿಯಾದ ಮಾದರಿಯನ್ನು ಬಳಸಿ

```bash
# ತ್ವರಿತ ಉತ್ತರ — ಕಡಿಮೆ ವೆಚ್ಚದ + ವೇಗವಾದ ಮಾದರಿ ಬಳಸಿ
curl -d '{"model":"auto/fast","messages":[...]}'

# ಸಂಕೀರ್ಣ ಕಾರ್ಯ — ಗುಣಮಟ್ಟದ ಮಾದರಿ ಬಳಸಿ
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. ಕ್ಯಾಶಿಂಗ್ ಸಕ್ರಿಯಗೊಳಿಸಿ

Anthropic ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶಿಂಗ್ **ಪುನರಾವರ್ತಿತ ಸಂದರ್ಭದ ವೆಚ್ಚದಲ್ಲಿ 90% ಉಳಿಸುತ್ತದೆ**:

```ts
// ಕ್ಯಾಶಿಂಗ್ ಸ್ವಯಂಚಾಲಿತವಾಗಿದೆ — ಅದೇ ದೊಡ್ಡ ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಸೇರಿಸಿದರೆ ಸಾಕು
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಕ್ಯಾಶ್ ಆಗುತ್ತದೆ
  messages: [{ role: "user", content: "..." }],
});
```

### 3. ಸಂಕುಚನವನ್ನು ಬಳಸಿ

RTK + Caveman ಸಂಕುಚನವು **ಪರಿಕರಗಳ ಬಳಕೆ ಹೆಚ್ಚಿರುವ ಸೆಷನ್‌ಗಳಲ್ಲಿ 15-95% ಉಳಿಸುತ್ತದೆ**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. ಪ್ರತಿ ಕೀಲಿಗೂ ಕೋಟಾಗಳನ್ನು ಹೊಂದಿಸಿ

ವೆಚ್ಚವು ನಿಯಂತ್ರಣ ಮೀರಿ ಏರದಂತೆ ತಡೆಯಲು ಯಾವಾಗಲೂ `quotaLimit` ಹೊಂದಿಸಿ:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // ತಿಂಗಳಿಗೆ $10 ಮಿತಿ
```

### 5. ಹೆಚ್ಚು ಬಳಕೆ ಮಾಡುವವರನ್ನು ಪರಿಶೀಲಿಸಿ

API ಕೀ ಪ್ರಕಾರ ಗುಂಪು ಮಾಡಲು ಮತ್ತು ವೆಚ್ಚದ ಪ್ರಕಾರ ವಿಂಗಡಿಸಲು ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಅಥವಾ **`/api/usage/analytics`** ಬಳಸಿ:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## ದೋಷನಿವಾರಣೆ

### "ವೆಚ್ಚವು ನಿರೀಕ್ಷೆಗಿಂತ ಹೆಚ್ಚಾಗಿದೆ"

1. **`/api/usage/analytics?groupBy=model`** ಪರಿಶೀಲಿಸಿ — ದುಬಾರಿ ಮಾದರಿಯನ್ನು ಹುಡುಕಿ
2. **`/api/usage/analytics?groupBy=apiKey`** ಪರಿಶೀಲಿಸಿ — ಹೆಚ್ಚು ಬಳಕೆ ಮಾಡುವವರನ್ನು ಹುಡುಕಿ
3. ಬೆಲೆ ದತ್ತಾಂಶವು ನವೀಕೃತವಾಗಿದೆ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ: `POST /api/pricing/sync`

### "ದಾಖಲೆಗಳು ಕಾಣೆಯಾಗಿವೆ"

- ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ → ದತ್ತಸಂಚಯ → ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ ಅಡಿಯಲ್ಲಿ DB ಧಾರಣಾ ಸೆಟ್ಟಿಂಗ್‌ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ — ಆವರ್ತಕ ಸ್ವಚ್ಛಗೊಳಿಸುವ ಕಾರ್ಯವು ಹಳೆಯ ದಾಖಲೆಗಳನ್ನು ಅಳಿಸುತ್ತದೆ (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts` ನಲ್ಲಿ ದೋಷಗಳಿವೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ — DB ಬರವಣಿಗೆ ವೈಫಲ್ಯಗಳನ್ನು ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಪ್ರದರ್ಶಿಸಲಾಗುವುದಿಲ್ಲ
- ವಿನಂತಿಯು ನಿಜವಾಗಿಯೂ `chatCore` ತಲುಪಿದೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ — ಕಾಂಬೊ ರೂಟಿಂಗ್ ಪರಿಶೀಲಿಸಿ

### "ಕೋಟಾ ಜಾರಿಯಾಗುತ್ತಿಲ್ಲ"

- ಕೀಯ `quotaLimit` ಸೆಟ್ಟಿಂಗ್ ಪರಿಶೀಲಿಸಿ
- `quotaWindow` ಸರಿಯಾಗಿ ಹೊಂದಿಸಲಾಗಿದೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ
- `quotaSnapshots` ದಾಖಲೆಗಳನ್ನು ಹುಡುಕಿ — ಪ್ರತಿ ವಿನಂತಿಯಲ್ಲೂ ಅವು ರಚನೆಯಾಗಬೇಕು
