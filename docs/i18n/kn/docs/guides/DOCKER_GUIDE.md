## ತ್ವರಿತ ಚಾಲನೆ

> **ಒಂದೇ ಕಮಾಂಡ್ನಲ್ಲಿ ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಬೇಕೇ?**
> [ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾರ್ಗದರ್ಶಿ](../getting-started/SELF_HOST_GUIDE.md) ನೋಡಿ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ಪ್ರಕಟಿತ ಇಮೇಜ್ +
> Redis, ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮಾತ್ರ, ಪ್ರೊಫೈಲ್ ಆಯ್ಕೆ ಇಲ್ಲ). ಕೆಳಗಿನ ತ್ವರಿತ ಚಾಲನೆಯು
> ಈಗಾಗಲೇ ಬೇರೆಡೆ Redis ಚಾಲನೆ ಮಾಡುತ್ತಿರುವ ಬಳಕೆದಾರರಿಗಾಗಿ ಏಕ-ಕಂಟೇನರ್ ಮಾರ್ಗವಾಗಿದೆ.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## ಪರಿಸರ ಫೈಲ್ನೊಂದಿಗೆ

```bash
# ಮೊದಲು .env ಅನ್ನು ನಕಲಿಸಿ ಮತ್ತು ಸಂಪಾದಿಸಿ
```

## Docker Compose

```bash
# ಮೂಲ ಪ್ರೊಫೈಲ್ (CLI ಪರಿಕರಗಳಿಲ್ಲ)
docker compose --profile base up -d

# CLI ಪ್ರೊಫೈಲ್ (Claude Code, Codex, OpenClaw ಅಂತರ್ನಿರ್ಮಿತ)
docker compose --profile cli up -d

# ಹೋಸ್ಟ್ ಪ್ರೊಫೈಲ್ (ಮುಖ್ಯವಾಗಿ Linux ಗಾಗಿ; ಹೋಸ್ಟ್ CLI ಬೈನರಿಗಳನ್ನು ಓದಲು ಮಾತ್ರ ಅನುಮತಿಯೊಂದಿಗೆ ಮೌಂಟ್ ಮಾಡುತ್ತದೆ)
docker compose --profile host up -d

# ವೆಬ್ ಪ್ರೊಫೈಲ್ (ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರಿಗಾಗಿ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI ಸೈಡ್ಕಾರ್ ಅನ್ನು ಸಂಯೋಜಿಸಿ
docker compose --profile cli --profile cliproxyapi up -d
```

## ಲಭ್ಯವಿರುವ ಪ್ರೊಫೈಲ್ಗಳು

ಮುಖ್ಯ ನಿಯೋಜನಾ ವಿನ್ಯಾಸಗಳಿಗಾಗಿ OmniRoute Compose ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಹೊಂದುವಂತಹದನ್ನು ಆಯ್ಕೆಮಾಡಿ.

| ಪ್ರೊಫೈಲ್          | ಸೇವೆ             | ಯಾವಾಗ ಬಳಸಬೇಕು                                                                                                                                                           | ಕಮಾಂಡ್                                       |
| ----------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ಡೀಫಾಲ್ಟ್) | `omniroute-base` | ಹೆಡ್ಲೆಸ್ ಸರ್ವರ್ / ಕನಿಷ್ಠ ರನ್ಟೈಮ್, ಯಾವುದೇ ಪೂರೈಕೆದಾರ CLIಗಳನ್ನು ಒಳಗೊಂಡಿಲ್ಲ                                                                                                 | `docker compose --profile base up -d`        |
| `cli`             | `omniroute-cli`  | `omniroute providers/setup/doctor` ಮತ್ತು ಒಳಗೊಂಡಿರುವ CLIಗಳನ್ನು (Codex, Claude Code, Droid, OpenClaw) ಕರೆಯುವ ಏಜೆಂಟಿಕ್ ಕಾರ್ಯಪ್ರವಾಹಗಳು                                      | `docker compose --profile cli up -d`         |
| `host`            | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` ಮುಂತಾದವುಗಳನ್ನು ಓದಲು ಮಾತ್ರ ಅನುಮತಿಯೊಂದಿಗೆ ಮೌಂಟ್ ಮಾಡುವ ಮೂಲಕ ಹೋಸ್ಟ್ CLIಗಳಿಗೆ `network_mode`-ರೀತಿಯ ಪ್ರವೇಶವನ್ನು ಬಯಸುವ Linux ಹೋಸ್ಟ್ಗಳು | `docker compose --profile host up -d`        |
| `cliproxyapi`     | `cliproxyapi`    | ಅಪ್ಸ್ಟ್ರೀಮ್ CLI ಪ್ರಾಕ್ಸಿಯಿಂಗ್ಗಾಗಿ `8317` ಪೋರ್ಟ್ನಲ್ಲಿ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ಸೈಡ್ಕಾರ್ ಅನ್ನು ಚಾಲನೆ ಮಾಡಿ                              | `docker compose --profile cliproxyapi up -d` |
| `web`             | `omniroute-web`  | ಬ್ರೌಸರ್ ಅಗತ್ಯವಿರುವ ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರು: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ಅನ್ನು ಬಿಲ್ಡ್ ಮಾಡುತ್ತದೆ, Chromium ಒಳಗೊಂಡಿದೆ)                     | `docker compose --profile web up -d`         |

> ಅನೇಕ ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಸಂಯೋಜಿಸಬಹುದು: `docker compose --profile cli --profile cliproxyapi up -d`.

## OmniRoute ಅನ್ನು Docker ನಲ್ಲಿ ಚಲಾಯಿಸುವಾಗ ಹೋಸ್ಟ್ CLI ಪರಿಕರಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುವುದು

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ
**ಕಾನ್ಫಿಗ್ ಉಳಿಸಿ** ಬಟನ್ ಇವೆಲ್ಲವೂ `~/.codex/*.config.toml` ರೀತಿಯ ಫೈಲ್ಗಳನ್ನು ಬರೆಯುತ್ತವೆ. ಆ ಪಥಗಳು
CLI ನಿಜವಾಗಿ ಚಲಿಸುವ ಯಂತ್ರದಲ್ಲಿ ಮಾತ್ರ ಅರ್ಥಪೂರ್ಣವಾಗಿರುತ್ತವೆ. ಅವುಗಳನ್ನು
ಕಂಟೇನರ್ನೊಳಗೆ ಚಲಾಯಿಸಿದರೆ, ಬರವಣಿಗೆಯು ಕಂಟೇನರ್ನ ಸ್ವಂತ ಹೋಮ್ಗೆ (`/home/node` —
ಇಮೇಜ್ `USER node` ಆಗಿ ಚಲಿಸುತ್ತದೆ) ಸೇರುತ್ತದೆ; ಯಾವುದೇ ಹೋಸ್ಟ್ CLI ಅದನ್ನು ಎಂದಿಗೂ ಓದುವುದಿಲ್ಲ ಮತ್ತು
ಕಂಟೇನರ್ ಅನ್ನು ಮರುರಚಿಸಿದ ಕ್ಷಣವೇ ಅದು ಅಳಿಸಿಹೋಗುತ್ತದೆ.

OmniRoute ಇದನ್ನು ಪತ್ತೆಹಚ್ಚಿ, ನೀವು ಬಳಸಲಾಗದ ಯಶಸ್ಸನ್ನು ವರದಿ ಮಾಡುವ ಬದಲು
ಸೂಚನೆಗಳೊಂದಿಗೆ ಬರವಣಿಗೆಯನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ: CLI `2` ನೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ ಮತ್ತು API
`containerEphemeralTarget: true` ಜೊತೆಗೆ `422` ಉತ್ತರಿಸುತ್ತದೆ.

### ಶಿಫಾರಸು ಮಾಡಿರುವ ವಿಧಾನ: CLI ಅನ್ನು ಹೋಸ್ಟ್ನಲ್ಲಿ, OmniRoute ಅನ್ನು Docker ನಲ್ಲಿ ಚಲಾಯಿಸಿ

ಕಂಟೇನರ್ API ಅನ್ನು ಒದಗಿಸುತ್ತದೆ; CLI ನಿಮ್ಮ ಹೋಸ್ಟ್ ಪರಿಕರಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುತ್ತದೆ.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI ಅನ್ನು ಕಂಟೇನರ್ಗೆ ನಿರ್ದೇಶಿಸಿ
omniroute setup-codex                      # ನಿಮ್ಮ ಹೋಸ್ಟ್ನ ನಿಜವಾದ ~/.codex ಗೆ ಬರೆಯುತ್ತದೆ
```

Codex, Claude Code, Cursor ಅಥವಾ ಅಂತಹುದೇ ಪರಿಕರಗಳು ನಿಮ್ಮ
ಲ್ಯಾಪ್ಟಾಪ್ನಲ್ಲಿ ಚಲಿಸುವಾಗ ಇದು ಸರಿಯಾದ ಆಯ್ಕೆಯಾಗಿದೆ — ಸಾಮಾನ್ಯವಾಗಿ ಬಳಸುವ ಸಂರಚನೆಯೂ ಇದೇ.

### ಪರ್ಯಾಯ: ಹೋಸ್ಟ್ ಕಾನ್ಫಿಗ್ ಡೈರೆಕ್ಟರಿಗಳನ್ನು bind-mount ಮಾಡಿ (`host` ಪ್ರೊಫೈಲ್)

ಕಂಟೇನರ್ ಸ್ವತಃ ನಿಮ್ಮ ಹೋಸ್ಟ್ ಕಾನ್ಫಿಗ್ ಅನ್ನು ಬರೆಯಬೇಕೆಂದು ನೀವು ಬಯಸಿದರೆ,
ಡೈರೆಕ್ಟರಿಗಳನ್ನು ಮೌಂಟ್ ಮಾಡಿ ಮತ್ತು `CLI_CONFIG_HOME` ಅನ್ನು ಮೌಂಟ್ ರೂಟ್ಗೆ ನಿರ್ದೇಶಿಸಿ. `host` ಪ್ರೊಫೈಲ್
ಈಗಾಗಲೇ ಇದನ್ನು ಮಾಡುತ್ತದೆ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

bind mount ಪಥವನ್ನು ವಿಶ್ವಾಸಾರ್ಹವಾಗಿಸುತ್ತದೆ: OmniRoute
`/proc/self/mountinfo` ಅನ್ನು ಓದುತ್ತದೆ ಮತ್ತು ಮೌಂಟ್ ಮಾಡಿದ ಪಥಗಳಿಗೆ (ಮತ್ತು ಮಕ್ಕಳಾಗಿ ಮೌಂಟ್ಗಳನ್ನು ಹೊಂದಿರುವ
ಡೈರೆಕ್ಟರಿಗಳಿಗೆ — ಮೇಲಿನ `/host-home` ವಿನ್ಯಾಸವು ನಿಖರವಾಗಿ ಇದೇ ರೀತಿಯದು) ಬರೆಯಲು ಅನುಮತಿಸುತ್ತದೆ, ಹಾಗೆಯೇ
ಮೌಂಟ್ ಮಾಡದ ಪಥಗಳನ್ನು ಇನ್ನೂ ನಿರಾಕರಿಸುತ್ತದೆ.

### ತುರ್ತು ಪರ್ಯಾಯ: ಕಂಟೇನರ್ನ ಸ್ವಂತ CLI ಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿ (ಮಿತವಾಗಿ ಬಳಸಿ)

CLI ಗಳು ನಿಜವಾಗಿಯೂ ಕಂಟೇನರ್ನೊಳಗೇ ಇರುವಾಗ (`cli` ಪ್ರೊಫೈಲ್), ಬರವಣಿಗೆಯು
ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿರುತ್ತದೆ. ಯಾವುದೇ `setup-*` ಕಮಾಂಡ್ಗೆ `--allow-container-write` ಅನ್ನು ರವಾನಿಸಿ ಅಥವಾ
ಸರ್ವರ್ಗಾಗಿ `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ಅನ್ನು ಹೊಂದಿಸಿ. ಬರವಣಿಗೆ ಮುಂದುವರಿಯುತ್ತದೆ,
ಆದರೆ ಅದು ಕಂಟೇನರ್ ಮರುರಚನೆಯ ನಂತರ ಉಳಿಯುವುದಿಲ್ಲ ಎಂಬ ಎಚ್ಚರಿಕೆಯನ್ನು ನೀಡಲಾಗುತ್ತದೆ.

> **ಭದ್ರತಾ ಎಚ್ಚರಿಕೆ — `cli` ಪ್ರೊಫೈಲ್ + `docker.sock` ಮೌಂಟ್.**
> ಕಂಟೇನರ್ನೊಳಗಿನ ಸ್ವಯಂ-ನವೀಕರಣಕಾರವು ಹೋಸ್ಟ್ ಡೀಮನ್ನಿಂದ ಸ್ಟ್ಯಾಕ್ ಅನ್ನು ಮರುರಚಿಸಲು ಸಾಧ್ಯವಾಗುವಂತೆ
> `cli` ಪ್ರೊಫೈಲ್ `/var/run/docker.sock` ಅನ್ನು bind-mount ಮಾಡುತ್ತದೆ
> (`src/lib/system/autoUpdate.ts` ಆ ಸಾಕೆಟ್ ಅನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ ಮತ್ತು ಅದು ಇಲ್ಲದಿದ್ದಾಗ
> Docker ಪಥವನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ). ಆ ಸಾಕೆಟ್ **ಹೋಸ್ಟ್-root ವಿಶ್ವಾಸದ
> ಗಡಿ** ಆಗಿದೆ: ಅದನ್ನು ತಲುಪಬಲ್ಲ ಯಾವುದಾದರೂ ಹೋಸ್ಟ್ Docker ಡೀಮನ್ ಅನ್ನು
> root ಆಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ — ಅದು ಹೋಸ್ಟ್ನಲ್ಲಿರುವ ಯಾವುದೇ ಕಂಟೇನರ್ ಅನ್ನು ರಚಿಸಬಹುದು, ಪರಿಶೀಲಿಸಬಹುದು,
> ನಿಲ್ಲಿಸಬಹುದು ಮತ್ತು ತೆಗೆದುಹಾಕಬಹುದು. ಪರಿಣಾಮಗಳು:
>
> 1. **`cli` ಪ್ರೊಫೈಲ್ನ ಪೋರ್ಟ್ ಅನ್ನು ಎಂದಿಗೂ ನೆಟ್ವರ್ಕ್ಗೆ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.** ಅದನ್ನು
>    `127.0.0.1` ನಲ್ಲಿ ಪ್ರಕಟಿಸಿ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN ಮೂಲಕ ತಲುಪಬಹುದಾದ `cli` ಪ್ರೊಫೈಲ್ ಯಾವುದೇ ಡ್ಯಾಶ್ಬೋರ್ಡ್-ಮಟ್ಟದ RCE ಅನ್ನು
>    ಸಂಪೂರ್ಣ ಹೋಸ್ಟ್ ರಾಜಿಗೆ ಪರಿವರ್ತಿಸುತ್ತದೆ.
> 2. **ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಹೋಸ್ಟ್ ಡೈರೆಕ್ಟರಿಗಳನ್ನು `cli` ಪ್ರೊಫೈಲ್ಗೆ bind ಮಾಡಬೇಡಿ.**
>    Docker ಸಾಕೆಟ್ ಜೊತೆಗೆ ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಮೌಂಟ್ ಕಂಟೇನರ್ಗೆ ನಿಮ್ಮ ಫೈಲ್ಸಿಸ್ಟಮ್ ಮತ್ತು ಹೋಸ್ಟ್
>    ಕಾನ್ಫಿಗ್ ಮೇಲೆ ಸಂಪೂರ್ಣ ಓದು/ಬರಹ ಪ್ರವೇಶವನ್ನು ನೀಡುತ್ತದೆ. ಯಾವುದಾದರೂ ಪರಿಕರವು ಪ್ರಾಜೆಕ್ಟ್ ಅನ್ನು
>    ನೋಡಬೇಕಾದರೆ, ಅದನ್ನು CLI ಬೈನರಿಯೊಂದಿಗೆ ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಿ — ಅದನ್ನು
>    `cli` ಕಂಟೇನರ್ಗೆ ಮೌಂಟ್ ಮಾಡಬೇಡಿ.
>
> ಕಂಟೇನರ್ನೊಳಗಿನ ಸ್ವಯಂ-ನವೀಕರಣ ನಿಮಗೆ ಅಗತ್ಯವಿಲ್ಲದಿದ್ದರೆ, `cli` ಪ್ರೊಫೈಲ್ ಅನ್ನು ನಿಷ್ಕ್ರಿಯವಾಗಿಯೇ ಬಿಡಿ
> (`COMPOSE_PROFILES=core,redis` ಅಥವಾ ಇನ್ನೂ ಸಂಕ್ಷಿಪ್ತವಾಗಿ). ಇತರ ಪ್ರೊಫೈಲ್ಗಳು
> Docker ಸಾಕೆಟ್ ಅನ್ನು ಮೌಂಟ್ ಮಾಡುವುದಿಲ್ಲ.
>
> MITM ಗೆ ಸಂಬಂಧಿಸಿದ ಅಪಾಯ ಮಾದರಿಗಾಗಿ `docs/security/MITM-TPROXY-DECRYPT.md` ಅನ್ನು ನೋಡಿ (git; `/docs` ಒಳಗೆ ಕಂಪೈಲ್ ಮಾಡಲಾಗಿಲ್ಲ),
> ಮತ್ತು `codex`/`claude-code`/`droid`/`openclaw` ಬೈನರಿ ಮೂಲ ಸರಪಳಿಗಾಗಿ
> `docs/security/SUPPLY_CHAIN.md` ಅನ್ನು ನೋಡಿ.

## Redis ಸೈಡ್ಕಾರ್

ವಿತರಿತ ದರ ಮಿತಿಕಾರಕ ಮತ್ತು ಹಂಚಿದ ಕ್ಯಾಶ್ಗೆ ಬೆಂಬಲ ನೀಡಲು OmniRoute, Redis ಅನ್ನು ಅವಲಂಬಿಸಿದೆ. `redis` ಸೇವೆಯನ್ನು `docker-compose.yml` ನಲ್ಲಿ **ಯಾವಾಗಲೂ ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿರುತ್ತದೆ** (ಇದಕ್ಕೆ ಯಾವುದೇ ಪ್ರೊಫೈಲ್ ಗೇಟ್ ಇಲ್ಲ) ಮತ್ತು ಅದು ಇತರ ಯಾವುದೇ ಪ್ರೊಫೈಲ್ನೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ.

| ವಿವರ                     | ಮೌಲ್ಯ                                        |
| ------------------------ | -------------------------------------------- |
| ಇಮೇಜ್                    | `redis:7-alpine`                             |
| ಕಂಟೇನರ್ ಹೆಸರು            | `omniroute-redis`                            |
| ಆಂತರಿಕ ಪೋರ್ಟ್            | `6379`                                       |
| ಹೋಸ್ಟ್ ಪೋರ್ಟ್ (ಓವರ್ರೈಡ್) | `REDIS_PORT` (ಡೀಫಾಲ್ಟ್ ಆಗಿ `6379`)           |
| ಹೋಸ್ಟ್ ಬೈಂಡ್ (ಓವರ್ರೈಡ್)  | `REDIS_BIND_HOST` (ಡೀಫಾಲ್ಟ್ ಆಗಿ `127.0.0.1`) |
| ವಾಲ್ಯೂಮ್                 | `omniroute-redis-data` → `/data`             |
| ಆರೋಗ್ಯ ಪರಿಶೀಲನೆ          | `redis-cli ping` (10s ಮಧ್ಯಂತರ)               |

ಸಂಬಂಧಿತ ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ಗಳು:

- `REDIS_URL` — ಆ್ಯಪ್ಗೆ ಸೇರಿಸಲಾಗುವ ಸಂಪರ್ಕ ಸ್ಟ್ರಿಂಗ್ (ಡೀಫಾಲ್ಟ್ ಆಗಿ `redis://redis:6379`).
- `REDIS_PORT` — Redis ಕಂಟೇನರ್ಗಾಗಿ ಹೋಸ್ಟ್-ಬದಿಯ ಪೋರ್ಟ್ ಮ್ಯಾಪಿಂಗ್.
- `REDIS_BIND_HOST` — ಪೋರ್ಟ್ ಪ್ರಕಟಿಸಲಾಗುವ ಹೋಸ್ಟ್ ಇಂಟರ್ಫೇಸ್. ಡೀಫಾಲ್ಟ್ ಆಗಿ `127.0.0.1`.

> **ಡೀಫಾಲ್ಟ್ ಆಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಏಕೆ:** ಸೈಡ್ಕಾರ್ `requirepass` ಇಲ್ಲದೆ ಚಾಲನೆಯಾಗುತ್ತದೆ ಮತ್ತು ಆ್ಯಪ್
> ಕಂಟೇನರ್ಗಳು compose ನೆಟ್ವರ್ಕ್ (`redis:6379`) ಮೂಲಕ ಅದನ್ನು ತಲುಪುತ್ತವೆ — ಪ್ರಕಟಿಸಿದ ಪೋರ್ಟ್
> ಹೋಸ್ಟ್-ಬದಿಯ ಪರಿಕರಗಳಿಗಾಗಿ (`redis-cli`, ಸ್ಥಳೀಯ `npm run dev`) ಮಾತ್ರ ಇರುತ್ತದೆ. ಅದನ್ನು
> `0.0.0.0` ನಲ್ಲಿ ಪ್ರಕಟಿಸುವುದರಿಂದ ದೃಢೀಕರಣವಿಲ್ಲದ Redis ನಿಮ್ಮ LANನಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು ಹೋಸ್ಟ್ಗೂ ಬಹಿರಂಗವಾಗುತ್ತದೆ. ನೀವು
> `REDIS_BIND_HOST=0.0.0.0` ಹೊಂದಿಸಿದರೆ, ಸೇವೆಯ `command:` ಗೆ `--requirepass` ಅನ್ನು ಸಹ ಸೇರಿಸಿ.

**Redis ಅನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದನ್ನು** ಶಿಫಾರಸು ಮಾಡುವುದಿಲ್ಲ (ದರ ಮಿತಿಕಾರಕವು ಇನ್-ಮೆಮೊರಿ ಫಾಲ್ಬ್ಯಾಕ್ಗೆ ಹಿಮ್ಮೆಟ್ಟುತ್ತದೆ). ಹಾಗೆ ಮಾಡಲೇಬೇಕಾದರೆ, `docker-compose.yml` ನಲ್ಲಿರುವ `redis:` ಸೇವಾ ಬ್ಲಾಕ್ ಅನ್ನು ತೆಗೆದುಹಾಕಿ/ಕಾಮೆಂಟ್ ಮಾಡಿ ಅಥವಾ ಅದನ್ನು ಶೂನ್ಯಕ್ಕೆ ಸ್ಕೇಲ್ ಮಾಡಿ:

```bash
docker compose up -d --scale redis=0
```

## ಪ್ರೊಡಕ್ಷನ್ Compose

ಡೆವ್ನೊಂದಿಗೆ ಸಮಾನಾಂತರವಾಗಿ ಚಾಲನೆಯಾಗುವ ಪ್ರತ್ಯೇಕಿತ ಪ್ರೊಡಕ್ಷನ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಾಗಿ `docker-compose.prod.yml` ಬಳಸಿ.

| ವಿವರ                         | ಮೌಲ್ಯ                                                                                           |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| ಫೈಲ್                         | `docker-compose.prod.yml`                                                                       |
| ಡೀಫಾಲ್ಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪೋರ್ಟ್ | `PROD_DASHBOARD_PORT=20130` (ಆಂತರಿಕ `${DASHBOARD_PORT:-20128}` ಗೆ ಮ್ಯಾಪ್ ಮಾಡಲಾಗಿದೆ)             |
| ಡೀಫಾಲ್ಟ್ API ಪೋರ್ಟ್          | `PROD_API_PORT=20131`                                                                           |
| ಇಮೇಜ್                        | `omniroute:prod` (`runner-cli` ಟಾರ್ಗೆಟ್ನಿಂದ ನಿರ್ಮಿಸಲಾಗಿದೆ)                                      |
| Redis ಕಂಟೇನರ್                | `omniroute-redis-prod` (`redis:8.6.2`, ಮೀಸಲಾದ `redis-prod-data` ವಾಲ್ಯೂಮ್)                       |
| ಡೇಟಾ ವಾಲ್ಯೂಮ್                | `omniroute-prod-data` (ಹೆಸರಿಸಲಾದ, ಮರುನಿರ್ಮಾಣಗಳಾದ್ಯಂತ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ)                       |
| ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಗಳು           | `node healthcheck.mjs` + `redis-cli ping`, Redis ಆರೋಗ್ಯದ ಆಧಾರದ ಮೇಲೆ `depends_on` ಗೇಟ್ ಮಾಡಲಾಗಿದೆ |

ಬಳಸುವ ವಿಧಾನ:

```bash
# ಪ್ರೊಡಕ್ಷನ್ ಸ್ಟ್ಯಾಕ್ ಅನ್ನು ನಿರ್ಮಿಸಿ ಮತ್ತು ಪ್ರಾರಂಭಿಸಿ
docker compose -f docker-compose.prod.yml up -d --build

# ಲಾಗ್ಗಳನ್ನು ನಿರಂತರವಾಗಿ ವೀಕ್ಷಿಸಿ
docker compose -f docker-compose.prod.yml logs -f

# ಸ್ಥಗಿತಗೊಳಿಸಿ (ವಾಲ್ಯೂಮ್ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ)
docker compose -f docker-compose.prod.yml down
```

ಪ್ರೊಡ್ ಸ್ಟ್ಯಾಕ್, ಡೆವ್ compose ಜೊತೆ ಸಮಾನಾಂತರವಾಗಿ ಚಾಲನೆಯಾಗುತ್ತದೆ (ವಿಭಿನ್ನ ಕಂಟೇನರ್ ಹೆಸರುಗಳು, ಪೋರ್ಟ್ಗಳು ಮತ್ತು ವಾಲ್ಯೂಮ್ಗಳು), ಆದ್ದರಿಂದ ಪ್ರೊಡಕ್ಷನ್ ಚಾಲನೆಯಲ್ಲಿರುವಾಗಲೂ ನೀವು ಸ್ಥಳೀಯವಾಗಿ ಪುನರಾವರ್ತಿತ ಅಭಿವೃದ್ಧಿಯನ್ನು ಮುಂದುವರಿಸಬಹುದು.

## Dockerfile ಹಂತಗಳು

ರೆಪೊಸಿಟರಿಯು ಬಹು-ಹಂತದ Dockerfile (`Dockerfile`) ಅನ್ನು ಒದಗಿಸುತ್ತದೆ. ನಾಲ್ಕು ಹಂತಗಳನ್ನು ಲಭ್ಯಗೊಳಿಸಲಾಗಿದೆ; ನಿಮ್ಮ ಬಳಕೆಯ ಸಂದರ್ಭಕ್ಕೆ ಸರಿಯಾದ `target` ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ.

| ಹಂತ           | ಮೂಲ ಇಮೇಜ್             | ಉದ್ದೇಶ                                                                                                                                                                                                                                                                                                                   |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `builder`     | `node:26-trixie-slim` | ಅವಲಂಬನೆಗಳನ್ನು ಸ್ಥಾಪಿಸುತ್ತದೆ (`npm ci --legacy-peer-deps`) ಮತ್ತು `npm run build` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ Turbopack — ಕೆಳಗಿನ ಬಿಲ್ಡ್-ಸಮಯದ ಸಂಪನ್ಮೂಲಗಳನ್ನು ನೋಡಿ)                                                                                                                                                 |
| `runner-base` | `node:26-trixie-slim` | Next.js ಸ್ವತಂತ್ರ ಔಟ್ಪುಟ್ನೊಂದಿಗೆ ಉತ್ಪಾದನಾ ರನ್ಟೈಮ್. **ಯಾವುದೇ ಪೂರೈಕೆದಾರ CLIಗಳನ್ನು ಸೇರಿಸಲಾಗಿಲ್ಲ.**                                                                                                                                                                                                                           |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ಮತ್ತು ಜಾಗತಿಕ CLIಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`. **ಏಜೆಂಟಿಕ್ ಕಾರ್ಯಪ್ರವಾಹಗಳಿಗಾಗಿ ಇದನ್ನು ಆಯ್ಕೆಮಾಡಿ.**                                                                                                                            |
| `runner-web`  | `runner-base`         | ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರಾದ `gemini-web`, `claude-web`, `claude-turnstile` ಗಾಗಿ Playwright + Chromium ಬ್ರೌಸರ್ (`--with-deps`) ಅನ್ನು ಸೇರಿಸುತ್ತದೆ. **ನೀವು ಆ ಪೂರೈಕೆದಾರರನ್ನು ಬಳಸುವಾಗ ಇದನ್ನು ಆಯ್ಕೆಮಾಡಿ** — ಇದು ಇಲ್ಲದಿದ್ದರೆ ಸಾಮಾನ್ಯ ಇಮೇಜ್ ವಿನಂತಿಯ ಸಮಯದಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ (ಬಿಡುಗಡೆ ಚಾನಲ್ಗಳ ಅಡಿಯಲ್ಲಿರುವ `-web` ಟಿಪ್ಪಣಿಯನ್ನು ನೋಡಿ). |

ನಿರ್ದಿಷ್ಟ target ಅನ್ನು ಕೈಯಾರೆ ಬಿಲ್ಡ್ ಮಾಡಿ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ಬಿಲ್ಡ್-ಸಮಯದ ಸಂಪನ್ಮೂಲಗಳು

ಮೂರು ಬಿಲ್ಡ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳು `builder` ಹಂತದ ವೆಚ್ಚವನ್ನು ನಿಯಂತ್ರಿಸುತ್ತವೆ. ಅವು ಬಿಲ್ಡ್ ಸಮಯಕ್ಕೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತವೆ —
`OMNIROUTE_MEMORY_MB` (ಕೆಳಗೆ) ಪ್ರತ್ಯೇಕ ರನ್ಟೈಮ್ ನಿಯಂತ್ರಣವಾಗಿದೆ.

| ಬಿಲ್ಡ್ ಆರ್ಗ್ಯುಮೆಂಟ್         | ಪೂರ್ವನಿಯೋಜಿತ | ಪರಿಣಾಮ                                                                                                        |
| --------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`          | `0` webpack ಬಳಸಿ ಬಿಲ್ಡ್ ಮಾಡುತ್ತದೆ: ಕಡಿಮೆ ಗರಿಷ್ಠ ಮೆಮೊರಿ, ನಿಧಾನ. `1` Turbopack ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ.            |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`       | ಪ್ರಾರಂಭಿಸಲಾದ `next build` ಗಾಗಿ V8 ಹೀಪ್ ಮಿತಿ (`--max-old-space-size`).                                         |
| `OMNIROUTE_BUILD_WORKERS`   | `2`          | `CIRCLE_NODE_TOTAL` ಗೆ ಮೌಲ್ಯ ಒದಗಿಸುತ್ತದೆ; ಪುಟ-ಡೇಟಾ ಸಂಗ್ರಹಣೆಗಾಗಿ Next, `workers = N - 1` ಅನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ. |

ದೊಡ್ಡ ಬಿಲ್ಡರ್ನಲ್ಲಿ ಹೆಚ್ಚಿಸಬೇಕಾದ ಮತ್ತು ಸಂಪನ್ಮೂಲ-ನಿರ್ಬಂಧಿತ ಬಿಲ್ಡ್
`✓ Compiled successfully` **ನಂತರ** ಸ್ಥಗಿತಗೊಂಡಾಗ ಅನುಮಾನಿಸಬೇಕಾದ ಮೌಲ್ಯವೆಂದರೆ `OMNIROUTE_BUILD_WORKERS`.
ಪ್ರತಿಯೊಂದು ಪುಟ-ಡೇಟಾ ವರ್ಕರ್ ತನ್ನದೇ ಪ್ರಕ್ರಿಯೆಯಾಗಿರುತ್ತದೆ ಮತ್ತು ಮೂಲ `next build` ಕೂಡ
ಪ್ರತ್ಯೇಕ ಪ್ರಕ್ರಿಯೆಯಾಗಿರುತ್ತದೆ; ನೇರ VPS ಪುನರುತ್ಪಾದನೆಯಲ್ಲಿ (issue #7518), ಪ್ರತಿಯೊಂದು ಪ್ರಕ್ರಿಯೆಯ
ಗರಿಷ್ಠ RSS ಅನ್ನು `NODE_OPTIONS` ಹೀಪ್ ಫ್ಲ್ಯಾಗ್ನಿಂದ ಸ್ವತಂತ್ರವಾಗಿ ~4.5 GB ಎಂದು ಅಳೆಯಲಾಯಿತು
(Turbopack, V8 ಹೀಪ್ನ ಹೊರಗಿನ ಸ್ಥಳೀಯ/Rust ಮೆಮೊರಿಯಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡುತ್ತದೆ).
`2` ಎಂಬ ಪೂರ್ವನಿಯೋಜಿತ ಮೌಲ್ಯವು (→ 1 ವರ್ಕರ್, ಒಟ್ಟು 2 ಪ್ರಕ್ರಿಯೆಗಳು) ಪ್ರಕಟಣಾ ಪೈಪ್ಲೈನ್ ಬಳಸುವ
16 GB / 4 vCPU GitHub-ಹೋಸ್ಟ್ ಮಾಡಿದ ರನ್ನರ್ಗಳಿಗೆ ಹೊಂದಿಸಲಾಗಿದೆ. `8` ನಲ್ಲಿ (→ 7 ವರ್ಕರ್ಗಳು)
ಆ ರನ್ನರ್ನ ಮೆಮೊರಿ ಮುಗಿದುಹೋಯಿತು ಮತ್ತು buildkit `ResourceExhausted: ... cannot allocate memory`
ದೊಂದಿಗೆ ಹಂತವನ್ನು ವಿಫಲಗೊಳಿಸಿತು; ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಯ RSS ಅನ್ನು ಊಹಿಸುವ ಬದಲು ನೇರವಾಗಿ ಅಳೆದಾಗ,
`3` (→ 2 ವರ್ಕರ್ಗಳು) ಕೂಡ ಸರಿಹೊಂದಲಿಲ್ಲ.
`tests/unit/docker-build-memory-budget.test.ts` ಅಳೆಯಲಾದ ಅಂಕಿಯನ್ನು ಆಧರಿಸಿ ಲೆಕ್ಕಾಚಾರ ಮಾಡುತ್ತದೆ
ಮತ್ತು ಯಾವುದಾದರೂ ನಿಯಂತ್ರಣವು ರನ್ನರ್ನ ಸಾಮರ್ಥ್ಯವನ್ನು ಮೀರಿದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

Turbopack, V8 ಹೀಪ್ನ **ಹೊರಗೆ** ಇರುವ ಸ್ಥಳೀಯ Rust ಮೆಮೊರಿಯಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡುತ್ತದೆ, ಆದ್ದರಿಂದ
`OMNIROUTE_BUILD_MEMORY_MB` ಅದಕ್ಕೆ ಮಿತಿ ವಿಧಿಸುವುದಿಲ್ಲ. ಮೆಮೊರಿ ಮಿತಿಯನ್ನು ಹೊಂದಿರುವ ಹೋಸ್ಟ್ನಲ್ಲಿ,
ಯಾವುದೇ ದೋಷ ಪಠ್ಯವಿಲ್ಲದೆ OOM ಕಿಲ್ಲರ್ ಬಿಲ್ಡ್ ಅನ್ನು SIGKILL ಮಾಡುತ್ತದೆ — ಅದು
`Creating an optimized production build` ಮಧ್ಯದಲ್ಲೇ ನಿಂತುಹೋಗುತ್ತದೆ; ಇದರಿಂದ ಮೆಮೊರಿ
ಕೊರತೆಯ ಬದಲು ಸ್ಥಗಿತಗೊಂಡಂತೆ ಕಾಣುತ್ತದೆ. ಆದ್ದರಿಂದ `Dockerfile`, `npm run dev` /
`npm run build` ಗಿಂತ ಭಿನ್ನವಾಗಿ, webpack ಅನ್ನು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಬಳಸುತ್ತದೆ
(`OMNIROUTE_USE_TURBOPACK=0`); ಅಲ್ಲಿ Turbopack ಕೋಡ್ನ ಪೂರ್ವನಿಯೋಜಿತ ಆಯ್ಕೆಯಾಗಿದೆ:
ಯಾವುದೇ ಬಿಲ್ಡ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳಿಲ್ಲದ ಸಾಮಾನ್ಯ `docker build .` (Railway ಮತ್ತು ಇತರ
ಒಂದು-ಕ್ಲಿಕ್ ಹೋಸ್ಟ್ಗಳು ಚಲಾಯಿಸುವುದು) ಮೆಮೊರಿ-ಮಿತಿಗೊಳಿಸಿದ ಬಿಲ್ಡರ್ನಲ್ಲಿ ಮೌನವಾಗಿ
ವಿಫಲಗೊಳ್ಳಬಾರದು. ಪ್ರಕಟಿಸಲಾದ ಇಮೇಜ್ಗಳು ಈಗಾಗಲೇ `docker-publish.yml` ನಲ್ಲಿ
`OMNIROUTE_USE_TURBOPACK=0` ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಪಾಸ್ ಮಾಡುತ್ತವೆ. ಸಾಕಷ್ಟು RAM ಇರುವ
ಬಿಲ್ಡರ್ನಲ್ಲಿ, ವೇಗವಾದ ಬಿಲ್ಡ್ಗಾಗಿ Turbopack ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ, ಆದ್ದರಿಂದ `next build` ಒಂದು ಮೂಲ ಪ್ರಕ್ರಿಯೆ
**ಮತ್ತು** ಒಂದು ವರ್ಕರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ ಹಾಗೂ ಪ್ರತಿಯೊಂದೂ
`OMNIROUTE_BUILD_MEMORY_MB` ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಪಾಲಿಸುತ್ತದೆ. ಕಂಟೇನರ್ ಮಿತಿಯನ್ನು ಆ ಮೌಲ್ಯದ
ಒಂದು ಪಟ್ಟು ಅಲ್ಲ, ಸುಮಾರು ಎರಡು ಪಟ್ಟಿಗಿಂತ ಹೆಚ್ಚಾಗಿ ನಿಗದಿಪಡಿಸಿ.

ಈ ಟ್ರೀಯಲ್ಲಿ ಅಳೆಯಲಾಗಿದೆ (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ಬಂಡ್ಲರ್   | ಕಂಟೇನರ್ ಮಿತಿ   | ಫಲಿತಾಂಶ                                     |
| --------- | -------------- | ------------------------------------------- |
| Turbopack | 8 GiB / 16 GiB | ಎರಡರಲ್ಲೂ OOM ಮೂಲಕ ಮೌನವಾಗಿ ಸ್ಥಗಿತಗೊಳಿಸಲಾಯಿತು |
| webpack   | 8 GiB          | ಬಿಲ್ಡ್ ವರ್ಕರ್ ಅನ್ನು SIGKILL ಮಾಡಲಾಯಿತು       |
| webpack   | 12 GiB         | ಯಶಸ್ವಿಯಾಯಿತು, ಗರಿಷ್ಠ 11.1 GiB ತಲುಪಿತು       |

### ರನ್ಟೈಮ್ ಪೂರ್ವನಿಯೋಜಿತಗಳು

`runner-base` ರಫ್ತು ಮಾಡುವ ಪೂರ್ವನಿಯೋಜಿತಗಳು: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Dockerನಲ್ಲಿನ ಮೆಮೊರಿ ವರ್ತನೆ:

- ಇಮೇಜ್ `OMNIROUTE_MEMORY_MB=1024` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ ಮತ್ತು ಅದರಿಂದ `NODE_OPTIONS=--max-old-space-size=1024` ಅನ್ನು ಪಡೆಯುತ್ತದೆ.
- ನೈಜ ಸರ್ವರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು standalone launcher ಪ್ರಾರಂಭಿಸುತ್ತದೆ; ಇದು `OMNIROUTE_MEMORY_MB` ಅನ್ನು ಓದಿ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ಅನ್ನು ಸೇರಿಸುತ್ತದೆ.
- ಪುನರಾವರ್ತಿತ `--max-old-space-size` ಮೌಲ್ಯಗಳಲ್ಲಿ ಕೊನೆಯದನ್ನು Node ಬಳಸುತ್ತದೆ, ಆದ್ದರಿಂದ `OMNIROUTE_MEMORY_MB` ಅನ್ನು ಹೊಂದಿಸುವುದರಿಂದ ಪರಿಣಾಮಕಾರಿ Docker heap ಮಿತಿ ನಿಯಂತ್ರಿಸಲ್ಪಡುತ್ತದೆ.
- ಇಮೇಜ್ ಇದನ್ನು ಯಾವಾಗಲೂ ಹೊಂದಿಸುವುದರಿಂದ, launcherನ ಸ್ವಂತ RAM-ಆಧಾರಿತ fallback Docker ಅಡಿಯಲ್ಲಿ ಎಂದಿಗೂ ಅನ್ವಯಿಸುವುದಿಲ್ಲ. ಕಾರ್ಯಭಾರಕ್ಕೆ ಅನುಗುಣವಾಗಿ ಇದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೆಚ್ಚಿಸಿ (ಕೆಳಗಿನ ಕೋಷ್ಟಕ). coding-agent `/v1/responses` ಗಾಗಿ `2048` ಇನ್ನೂ ತುಂಬಾ ಚಿಕ್ಕದಾಗಿದೆ.

### ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ಗಳಿಗೆ ರನ್ಟೈಮ್ RAM

1 GiB Docker ಡೀಫಾಲ್ಟ್ ಎಂಬುದು ಡ್ಯಾಶ್ಬೋರ್ಡ್/ಹಗುರ ಚಾಟ್ಗೆ ಬೇಕಾದ ಕನಿಷ್ಠ ಮಟ್ಟವೇ ಹೊರತು, ಪ್ರೊಡಕ್ಷನ್ ಗಾತ್ರವಲ್ಲ. ದೀರ್ಘವಾದ `POST /v1/responses` bodyಗಳು (ನೂರಾರು ಸಂದೇಶಗಳು, ಹತ್ತಾರು tools) compression ಸಮಯದಲ್ಲಿ ಅನೇಕ in-memory graphಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಏಕಕಾಲದಲ್ಲಿ ಚಾಲನೆಯಲ್ಲಿರುವ ಎರಡು ~3 MiB / ~750k-token ವಿನಂತಿಗಳು **12 GiB** old-space ನಲ್ಲಿ V8 ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಿವೆ (`FATAL ERROR: Reached heap limit`) ಮತ್ತು 16 GiB cgroup OOM ಅನ್ನು ಸಹ ತಲುಪಿವೆ. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ನೋಡಿ.

**heapಗಿಂತ ಹೆಚ್ಚಿನ ಗಾತ್ರಕ್ಕೆ cgroup `--memory` ಅನ್ನು ಹೊಂದಿಸಿ** — native bufferಗಳು, SQLite ಮತ್ತು compression intermediateಗಳು V8 ಹೊರಗೆ ಇರುತ್ತವೆ.

| ಕಾರ್ಯಭಾರ                                 | `OMNIROUTE_MEMORY_MB`     | Container / cgroup          | ಟಿಪ್ಪಣಿಗಳು                                                                                                                  |
| ---------------------------------------- | ------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| ಡ್ಯಾಶ್ಬೋರ್ಡ್, ಒಂದು ಹಗುರ ಚಾಟ್             | `1024` (ಇಮೇಜ್ ಡೀಫಾಲ್ಟ್)   | ≥2 GiB                      |                                                                                                                             |
| ಒಂದು ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ (Claude/Codex/Grok)  | `8192`                    | ≥10 GiB                     | ಸಾಮಾನ್ಯ ಏಕ-session `/v1/responses`                                                                                          |
| ಏಕಕಾಲದ ಎರಡು ದೀರ್ಘ `/v1/responses`        | `10240`–`12288`           | ≥12–16 GiB                  | ~12 GiB heap ನಲ್ಲಿ V8 ಸ್ಥಗಿತವನ್ನು ಅಳೆಯಲಾಗಿದೆ                                                                                |
| ಏಕಕಾಲದ ಮೂರು ಅಥವಾ ಹೆಚ್ಚು ದೀರ್ಘ contextಗಳು | ಒಂದೇ processನಲ್ಲಿ ಮಾಡಬೇಡಿ | serialize ಮಾಡಿ / ಹೆಚ್ಚು RAM | ಡೀಫಾಲ್ಟ್ heavyweight admissionನಲ್ಲಿ 1 in-flight ಮಾತ್ರ ಇರುತ್ತದೆ; RAM ಇಲ್ಲದೆ ಇದನ್ನು ಹೆಚ್ಚಿಸುವುದರಿಂದ ಸ್ಥಗಿತ ಮತ್ತೆ ಸಂಭವಿಸುತ್ತದೆ |

bare metalನಲ್ಲಿ `omniroute serve`, `OMNIROUTE_MEMORY_MB` ಅನ್ನು **ಹೊಂದಿಸದಿದ್ದಾಗ**, RAMನ ~35% ಅನ್ನು (`[512, 4096]` ಮಿತಿಗೆ ಒಳಪಡಿಸಿ) ಹೊಂದಿಸುತ್ತದೆ. Docker ಯಾವಾಗಲೂ `1024` ಅನ್ನು ಹೊಂದಿಸುವುದರಿಂದ, ಅಧಿಕೃತ ಇಮೇಜ್ನಲ್ಲಿ ಆ ಹೊಂದಾಣಿಕೆ ಎಂದಿಗೂ ನಡೆಯುವುದಿಲ್ಲ.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ಉಪಪಥದಲ್ಲಿ ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ (Traefik / nginx)

Next.js `basePath` ಅನ್ನು ಸ್ಟ್ಯಾಂಡ್ಅಲೋನ್ ಬಂಡಲ್ನಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡಲಾಗುತ್ತದೆ. OmniRoute, ಆ್ಯಪ್ನ ರೂಟ್ನಲ್ಲಿರುವ ಸೆಂಟಿನಲ್ ಫೈಲ್ನಲ್ಲಿ ಬಿಲ್ಡ್ ಸಮಯದಲ್ಲಿ ಅಳವಡಿಸಲಾದ ಮೌಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ (`npm run build` ಸಮಯದಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ; `scripts/docker/ensure-docker-base-path.mjs` ಮೂಲಕ ಓದಲಾಗುತ್ತದೆ) ಮತ್ತು ಕಂಟೇನರ್ ಪ್ರಾರಂಭವಾದಾಗ ಅದನ್ನು `OMNIROUTE_BASE_PATH` ಜೊತೆಗೆ ಹೋಲಿಸುತ್ತದೆ. ಅವು ಭಿನ್ನವಾಗಿದ್ದು ಇಮೇಜ್ ಅನ್ನು ಡೊಮೇನ್ ರೂಟ್ಗಾಗಿ ಬಿಲ್ಡ್ ಮಾಡಿದ್ದರೆ, `node dev/run-standalone.mjs` ರನ್ ಆಗುವ ಮೊದಲು ಎಂಟ್ರಿಪಾಯಿಂಟ್ ಸ್ಟ್ಯಾಂಡ್ಅಲೋನ್ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳು, ಎಂಬೆಡ್ ಮಾಡಲಾದ `basePath`/`assetPrefix` ಲಿಟರಲ್ಗಳು (Next 16, SSR ಅಸೆಟ್ URLಗಳನ್ನು `assetPrefix` ಒಂದರಿಂದಲೇ ರೆಂಡರ್ ಮಾಡುತ್ತದೆ — ಪ್ಯಾಚರ್ ಉಪಪಥವನ್ನು ಅದರಲ್ಲಿಯೂ ಪ್ರತಿರೂಪಿಸುತ್ತದೆ), ಬಿಲ್ಡ್ನಲ್ಲಿ ಅಳವಡಿಸಲಾದ `/_next/static` ಅಸೆಟ್ URLಗಳು (ಕ್ಲೈಂಟ್-ರೆಫರೆನ್ಸ್ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳು, ಮೀಡಿಯಾ ಇಂಪೋರ್ಟ್ಗಳು, ಪೂರ್ವ-ರೆಂಡರ್ ಮಾಡಿದ ದೋಷ ಪುಟಗಳು) ಮತ್ತು ಕ್ಲೈಂಟ್ `process.env` ಶಿಮ್ ಅನ್ನು ಮರುಬರೆಯುತ್ತದೆ.

### Compose ಬಿಲ್ಡ್ (ಶಿಫಾರಸು ಮಾಡಲಾಗಿದೆ)

ಎರಡೂ ವೇರಿಯಬಲ್ಗಳನ್ನು `.env` ನಲ್ಲಿ ಹೊಂದಿಸಿ, ನಂತರ ಇಮೇಜ್ ಮತ್ತು ರನ್ಟೈಮ್ ಹೊಂದಾಣಿಕೆಯಾಗುವಂತೆ ಮರುಬಿಲ್ಡ್ ಮಾಡಿ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH` ಅನ್ನು Docker ಬಿಲ್ಡ್-ಆರ್ಗ್ ಆಗಿಯೂ ರನ್ಟೈಮ್ ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ ಆಗಿಯೂ ಫಾರ್ವರ್ಡ್ ಮಾಡುತ್ತದೆ.

### ಪೂರ್ವ-ಬಿಲ್ಡ್ ಮಾಡಿದ ರೂಟ್ ಇಮೇಜ್ + ರನ್ಟೈಮ್ ಉಪಪಥ

ಪ್ರಕಟಿತ `diegosouzapw/omniroute:*` ಇಮೇಜ್ಗಳನ್ನು ಡೊಮೇನ್ ರೂಟ್ಗಾಗಿ ಬಿಲ್ಡ್ ಮಾಡಲಾಗಿದೆ. ಆದರೂ ನೀವು ರನ್ಟೈಮ್ನಲ್ಲಿ `OMNIROUTE_BASE_PATH` ಅನ್ನು ಹೊಂದಿಸಬಹುದು; ಕಂಟೇನರ್ ಪ್ರಾರಂಭವಾಗುವಾಗ ಬಂಡಲ್ ಅನ್ನು ಒಮ್ಮೆ ಪ್ಯಾಚ್ ಮಾಡುತ್ತದೆ. ಅದಕ್ಕೆ ಹೊಂದುವ ಸಾರ್ವಜನಿಕ ಒರಿಜಿನ್ ಅನ್ನು ಸಹ ಹೊಂದಿಸಿ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿಯು **ಸಂಪೂರ್ಣ** ಬಾಹ್ಯ ಪಥವನ್ನು ಫಾರ್ವರ್ಡ್ ಮಾಡುವಂತೆ ಕಾನ್ಫಿಗರ್ ಮಾಡಿ (ಪ್ರಿಫಿಕ್ಸ್ ಅನ್ನು ತೆಗೆದುಹಾಕಬೇಡಿ). Traefik, `StripPrefix` ಇಲ್ಲದೆ `PathPrefix(`/omniroute`)` ಅನ್ನು ಕಂಟೇನರ್ಗೆ ರೂಟ್ ಮಾಡಬೇಕು; ಇದರಿಂದ Next.js `/omniroute/...` ಅನ್ನು ಸ್ವೀಕರಿಸಿ, `/omniroute/_next/...` ನಿಂದ ಅಸೆಟ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ.

Docker ಹೆಲ್ತ್ಚೆಕ್, ಸಕ್ರಿಯ `OMNIROUTE_BASE_PATH` ಪ್ರಿಫಿಕ್ಸ್ ಹೊಂದಿರುವ ಹಗುರವಾದ `/healthz` ಲೈಫ್ಸೈಕಲ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಪ್ರೋಬ್ ಮಾಡುತ್ತದೆ. ಮಾನವ/ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಸ್ಗಾಗಿ `/api/monitoring/health` ಲಭ್ಯವಿರುತ್ತದೆ; ಕಂಟೇನರ್ HEALTHCHECK ಅನ್ನು ಮತ್ತೆ ಅದರತ್ತ ನಿರ್ದೇಶಿಸಲು (ಉದಾಹರಣೆಗೆ, ಆಳವಾದ ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಯನ್ನು ಜಾರಿಗೊಳಿಸಲು), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ಅನ್ನು ಹೊಂದಿಸಿ. ಆ ಪಥವು **ಆಳವಾದ** ಪರಿಶೀಲನೆಯಾಗಿದೆ (DB + ಮಾನಿಟರಿಂಗ್ ಸಾರಾಂಶ) — ನೀವು ಮತ್ತೆ ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡರೆ Docker ನ ಅಪರೂಪದ `HEALTHCHECK` ಗೆ ಸೂಕ್ತವಾಗಿದೆ, ಆದರೆ Kubernetes `livenessProbe` ಇಂಟರ್ವಲ್ಗಳಿಗೆ **ಸೂಕ್ತವಲ್ಲ**.

ಆರ್ಕೆಸ್ಟ್ರೇಟರ್ಗಳಿಗಾಗಿ (Kubernetes, Nomad, ಇತ್ಯಾದಿ):

| ಪ್ರೋಬ್                 | ಆದ್ಯತೆ ನೀಡಿ                                                              | ತಪ್ಪಿಸಿ                                                                   |
| ---------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| ಲೈವ್ನೆಸ್               | HTTP `GET /livez`, ಅಥವಾ ಮುಖ್ಯ ಪೋರ್ಟ್ನಲ್ಲಿ TCP (`PORT`, ಡೀಫಾಲ್ಟ್ `20128`) | ಲೈವ್ನೆಸ್ ಆಗಿ `/api/monitoring/health`                                     |
| ರೆಡಿನೆಸ್               | HTTP `GET /healthz`                                                      | ಈವೆಂಟ್-ಲೂಪ್ ಕಾರ್ಯನಿರತವಾಗಿರುವುದನ್ನು ಸ್ಥಗಿತವೆಂದು ಪರಿಗಣಿಸುವ ಕಡಿಮೆ ಟೈಮ್ಔಟ್ಗಳು |
| ಆಳವಾದ / ಬ್ಲ್ಯಾಕ್ಬಾಕ್ಸ್ | `/api/monitoring/health`                                                 | —                                                                         |

`/healthz`, ಪ್ರೊಸೆಸ್ ಲೈಫ್ಸೈಕಲ್ ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ (`ok` / `starting` / `stopping`). `/livez` ಕೇವಲ ಪ್ರೊಸೆಸ್ ಜೀವಂತವಾಗಿದೆಯೇ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ (ಹ್ಯಾಂಡ್ಲರ್ ರನ್ ಆಗಬಲ್ಲಾಗಲೆಲ್ಲ 200; ಇದು ರೆಡಿನೆಸ್ಗಾಗಿ ಕಾಯುವುದಿಲ್ಲ). ಇವೆರಡೂ ರಿಕ್ವೆಸ್ಟ್ ಹ್ಯಾಂಡ್ಲಿಂಗ್ನಂತೆಯೇ ಅದೇ Node ಈವೆಂಟ್ ಲೂಪ್ನಲ್ಲಿ ರನ್ ಆಗುವುದರಿಂದ, CPU-ಬೌಂಡ್ ಕ್ಯಾಟಲಾಗ್ ಅಥವಾ ಕಂಪ್ರೆಷನ್ ಕೆಲಸವು ಅವುಗಳನ್ನು ವಿಳಂಬಗೊಳಿಸಬಹುದು — ಕಾರ್ಯನಿರತ ≠ ಸ್ಥಗಿತ. HTTP ಪ್ರೋಬ್ಗಳು ಟೈಮ್ಔಟ್ ಆದರೆ TCP ಲೈವ್ನೆಸ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ. ಸಂಪೂರ್ಣ ಪ್ರೋಬ್ ಮಾರ್ಗದರ್ಶನ:
[ಮಾನಿಟರಿಂಗ್ ಮಾರ್ಗದರ್ಶಿ — Kubernetes ಪ್ರೋಬ್ ಶಿಫಾರಸುಗಳು](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Caddy ಜೊತೆಗೆ Docker Compose (HTTPS Auto-TLS)

Caddy ಯ ಸ್ವಯಂಚಾಲಿತ SSL ಒದಗಿಸುವಿಕೆಯನ್ನು ಬಳಸಿಕೊಂಡು OmniRoute ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ಬಹಿರಂಗಪಡಿಸಬಹುದು. ನಿಮ್ಮ ಡೊಮೇನ್ನ DNS A ದಾಖಲೆಯು ನಿಮ್ಮ ಸರ್ವರ್ನ IP ವಿಳಾಸವನ್ನು ಸೂಚಿಸುತ್ತಿದೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ.

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth ಕಾಲ್ಬ್ಯಾಕ್ಗಳು, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಲಿಂಕ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ ಸಾರ್ವಜನಿಕ URL ಗಳಿಗಾಗಿ ಬ್ರೌಸರ್ಗೆ ಗೋಚರಿಸುವ ಮೂಲ.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ನಿಗದಿತ ಕಾರ್ಯಗಳು / ಸ್ವಯಂ-ಫೆಚ್ಗಳಿಗಾಗಿ ಆಂತರಿಕ ಸರ್ವರ್-ಟು-ಸರ್ವರ್ URL.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy ಅಪ್ಸ್ಟ್ರೀಮ್ ಕಂಟೇನರ್ಗಾಗಿ ಪ್ರಮಾಣಿತ ಫಾರ್ವರ್ಡಿಂಗ್ ಹೆಡರ್ಗಳನ್ನು ಹೊಂದಿಸುತ್ತದೆ. OAuth ಕಾಲ್ಬ್ಯಾಕ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ ಸಾರ್ವಜನಿಕ
ಲಿಂಕ್ಗಳಿಗೆ OmniRoute `NEXT_PUBLIC_BASE_URL` ಅನ್ನು ಅಧಿಕೃತ ಸಾರ್ವಜನಿಕ ಮೂಲವಾಗಿ ಬಳಸುತ್ತದೆ;
ದೃಢೀಕೃತ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಬರಹಗಳು ಅದೇ-ಮೂಲದ ವಿನಂತಿಗಳ ಜೊತೆಗೆ ಸೆಷನ್ಗೆ ಬದ್ಧವಾದ CSRF
ರಕ್ಷಣೆಯನ್ನು ಬಳಸುತ್ತವೆ. ಸ್ಪಷ್ಟವಾದ ಸಂರಚನೆಯ ಬದಲಿಗೆ ವಿಶ್ವಾಸಾರ್ಹ ಫಾರ್ವರ್ಡ್ ಹೆಡರ್ಗಳಿಂದ ಸಾರ್ವಜನಿಕ ಮೂಲವನ್ನು
OmniRoute ಪಡೆದುಕೊಳ್ಳಬೇಕೆಂದು ನೀವು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಬಯಸುವ ಸುಧಾರಿತ ನಿಯೋಜನೆಗಳಿಗೆ ಮಾತ್ರ `OMNIROUTE_TRUST_PROXY` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ.

## Cloudflare Quick Tunnel

Docker ನಿಯೋಜನೆಗಳಿಗಾಗಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಬೆಂಬಲವು `Dashboard → Endpoints` ನಲ್ಲಿ ಒಂದು-ಕ್ಲಿಕ್ **Cloudflare Quick Tunnel** ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಮೊದಲ ಬಾರಿ ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಅಗತ್ಯವಿದ್ದರೆ ಮಾತ್ರ `cloudflared` ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ, ನಿಮ್ಮ ಪ್ರಸ್ತುತ `/v1` ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ತಾತ್ಕಾಲಿಕ ಟನಲ್ ಅನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ ಮತ್ತು ರಚಿಸಲಾದ `https://*.trycloudflare.com/v1` URL ಅನ್ನು ನಿಮ್ಮ ಸಾಮಾನ್ಯ ಸಾರ್ವಜನಿಕ URL ನ ನೇರವಾಗಿ ಕೆಳಗೆ ತೋರಿಸುತ್ತದೆ.

ಸಕ್ರಿಯ ಟನಲ್ ಸ್ಥಿತಿಯನ್ನು ಬದಲಾಯಿಸದೆಯೇ ಎಂಡ್ಪಾಯಿಂಟ್ ಟನಲ್ ಫಲಕಗಳನ್ನು (Cloudflare, Tailscale, ngrok) `Settings → Appearance` ನಿಂದ ತೋರಿಸಬಹುದು ಅಥವಾ ಮರೆಮಾಡಬಹುದು.

### ಟನಲ್ ಟಿಪ್ಪಣಿಗಳು

- Quick Tunnel URL ಗಳು ತಾತ್ಕಾಲಿಕವಾಗಿದ್ದು, ಪ್ರತಿ ಮರುಪ್ರಾರಂಭದ ನಂತರ ಬದಲಾಗುತ್ತವೆ.
- OmniRoute ಅಥವಾ ಕಂಟೇನರ್ ಮರುಪ್ರಾರಂಭವಾದ ನಂತರ Quick Tunnels ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮರುಸ್ಥಾಪನೆಯಾಗುವುದಿಲ್ಲ. ಅಗತ್ಯವಿದ್ದಾಗ ಅವುಗಳನ್ನು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ಮರು-ಸಕ್ರಿಯಗೊಳಿಸಿ.
- ನಿರ್ವಹಿತ ಸ್ಥಾಪನೆಯು ಪ್ರಸ್ತುತ `x64` / `arm64` ನಲ್ಲಿನ Linux, macOS ಮತ್ತು Windows ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ.
- ನಿರ್ಬಂಧಿತ ಕಂಟೇನರ್ ಪರಿಸರಗಳಲ್ಲಿ ಗದ್ದಲದ QUIC UDP ಬಫರ್ ಎಚ್ಚರಿಕೆಗಳನ್ನು ತಪ್ಪಿಸಲು ನಿರ್ವಹಿತ Quick Tunnels ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ HTTP/2 ಸಾರಿಗೆಯನ್ನು ಬಳಸುತ್ತವೆ. ನಿಮಗೆ ಬೇರೆ ಸಾರಿಗೆ ಬೇಕಿದ್ದರೆ `CLOUDFLARED_PROTOCOL=quic` ಅಥವಾ `auto` ಹೊಂದಿಸಿ.
- Docker ಇಮೇಜ್ಗಳು ಸಿಸ್ಟಮ್ CA ರೂಟ್ಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತವೆ ಮತ್ತು ಅವುಗಳನ್ನು ನಿರ್ವಹಿತ `cloudflared` ಗೆ ರವಾನಿಸುತ್ತವೆ; ಇದರಿಂದ ಕಂಟೇನರ್ ಒಳಗೆ ಟನಲ್ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಆಗುವಾಗ TLS ವಿಶ್ವಾಸ ವೈಫಲ್ಯಗಳು ತಪ್ಪುತ್ತವೆ.
- OmniRoute ಡೌನ್ಲೋಡ್ ಮಾಡುವ ಬದಲು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಬೈನರಿಯನ್ನು ಬಳಸಬೇಕೆಂದರೆ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ಹೊಂದಿಸಿ.

## ಇಮೇಜ್ ಟ್ಯಾಗ್ಗಳು

| ಇಮೇಜ್                    | ಟ್ಯಾಗ್   | ಗಾತ್ರ  | ವಿವರಣೆ                                               |
| ------------------------ | -------- | ------ | ---------------------------------------------------- |
| `diegosouzapw/omniroute` | `latest` | ~250MB | ಅತ್ಯುನ್ನತ **ಪ್ರಕಟಿತ** ಸ್ಥಿರ SemVer (git `main` ಅಲ್ಲ) |
| `diegosouzapw/omniroute` | `3.8.0`  | ~250MB | GitOps ಗಾಗಿ ಈ ವರ್ಗದ ಟ್ಯಾಗ್ ಅನ್ನು ಪಿನ್ ಮಾಡಿ           |

ಬಹು-ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಮ್ಯಾನಿಫೆಸ್ಟ್: `linux/amd64` + `linux/arm64` ನೇಟಿವ್ (Apple Silicon, AWS Graviton, Raspberry Pi). Docker ಹೊಂದಾಣಿಕೆಯಾಗುವ ಆರ್ಕಿಟೆಕ್ಚರ್ ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಆಯ್ಕೆಮಾಡುತ್ತದೆ; ARM ಹೋಸ್ಟ್ಗಳಲ್ಲಿ AMD64 ಎಮ್ಯುಲೇಶನ್ ಅನ್ನು ಬಲವಂತಪಡಿಸಬೇಕಾದರೆ `--platform linux/amd64` ರವಾನಿಸಿ.

### ಬಿಡುಗಡೆ ಚಾನೆಲ್ಗಳು

OmniRoute ಸ್ಥಿರ ಬಿಡುಗಡೆಗಳು, ಸಕ್ರಿಯ ಬಿಡುಗಡೆ-ಶಾಖೆಯ ಪರೀಕ್ಷೆ ಮತ್ತು ಅಭಿವೃದ್ಧಿ ಬಿಲ್ಡ್ಗಳಿಗಾಗಿ ಪ್ರತ್ಯೇಕ Docker ಚಾನೆಲ್ಗಳನ್ನು ಪ್ರಕಟಿಸುತ್ತದೆ.

| ಚಾನೆಲ್                          | ಮೂಲ                                 | ಬದಲಾಯಿಸಬಹುದಾದ ಸ್ವರೂಪ                 | ಶಿಫಾರಸು ಮಾಡಲಾದ ಬಳಕೆ                                                                                                                 |
| ------------------------------- | ----------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `:<version>` / `:<version>-web` | ಸಹಿ ಮಾಡಲಾದ/ಆವೃತ್ತಿಗೊಳಿಸಲಾದ ಬಿಡುಗಡೆ  | ಬದಲಾಯಿಸಲಾಗದು                         | ನಿಖರವಾದ ಬಿಡುಗಡೆಯನ್ನು ಪಿನ್ ಮಾಡುವ ಉತ್ಪಾದನಾ ನಿಯೋಜನೆಗಳು                                                                                 |
| `:latest` / `:latest-web`       | ಅತ್ಯುನ್ನತ **ಪ್ರಕಟಿತ** ಸ್ಥಿರ SemVer  | ಬದಲಾಯಿಸಬಹುದಾದ ಸ್ಥಿರ ಪಾಯಿಂಟರ್         | SemVer ಪ್ರಕಟಣೆ ಕಾರ್ಯದ **ನಂತರ** ಸ್ಥಿರ ಬಿಡುಗಡೆಗಳನ್ನು ಅನುಸರಿಸುತ್ತದೆ — `main` ಅಥವಾ ಬಿಡುಗಡೆಯಾಗದ `release/v*` ಕಮಿಟ್ಗಳನ್ನು ಅನುಸರಿಸುವುದಿಲ್ಲ |
| `:next` / `:next-web`           | ಪ್ರಸ್ತುತ ಡೀಫಾಲ್ಟ್ `release/v*` ಶಾಖೆ | ಬದಲಾಯಿಸಬಹುದಾದ ಪೂರ್ವ-ಬಿಡುಗಡೆ ಪಾಯಿಂಟರ್ | ಸಕ್ರಿಯ ಬಿಡುಗಡೆ ಶಾಖೆಗೆ ಸೇರಿಸಲಾದ, ಆದರೆ ಇನ್ನೂ ಸ್ಥಿರ ಬಿಡುಗಡೆಯ ಭಾಗವಾಗದಿರುವ ಪರಿಹಾರಗಳ ಪರೀಕ್ಷೆ                                              |
| `:main` / `:main-web`           | `main` ಶಾಖೆ                         | ಬದಲಾಯಿಸಬಹುದಾದ ಅಭಿವೃದ್ಧಿ ಪಾಯಿಂಟರ್     | ಅಭಿವೃದ್ಧಿ ಮತ್ತು ಏಕೀಕರಣ ಪರೀಕ್ಷೆಗೆ ಮಾತ್ರ                                                                                              |

#### ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರು: `-web` ಇಮೇಜ್ಗಳು

ಮೇಲಿನ ಪ್ರತಿಯೊಂದು ಚಾನೆಲ್ ಕೂಡ `-web` ಟ್ಯಾಗ್ನಂತೆ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ಲಭ್ಯವಿದ್ದು, `runner-web` ಹಂತದಿಂದ ನಿರ್ಮಿಸಲಾಗಿದೆ — ಅದೇ ಇಮೇಜ್ಗೆ Playwright ಮತ್ತು Chromium ಬ್ರೌಸರ್ ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ. ಸಾಮಾನ್ಯ ಇಮೇಜ್ Chromium **ಇಲ್ಲದೆ** ಬರುತ್ತದೆ; `gemini-web`, `claude-web` ಮತ್ತು `claude-turnstile` ಗೆ ಅದು ಅಗತ್ಯವಿದೆ.

ವೈಫಲ್ಯವು ಆರಂಭದ ಸಮಯದಲ್ಲಿ ಸಂಭವಿಸದೆ ಮುಂದೂಡಲ್ಪಡುತ್ತದೆ: ಆ ಪೂರೈಕೆದಾರರು ತಮ್ಮ ಮಾದರಿಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತಾರೆ ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಸಂಪರ್ಕಗೊಂಡಂತೆ ಕಾಣಿಸುತ್ತಾರೆ; ಮೊದಲ ವಿನಂತಿ ಮಾತ್ರ ಈ ಕೆಳಗಿನ ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ನೀವು ಆ ಪೂರೈಕೆದಾರರನ್ನು ಬಳಸುತ್ತಿದ್ದರೆ, ಈಗಾಗಲೇ ಬಳಸುತ್ತಿರುವ ಚಾನೆಲ್ನ `-web` ಟ್ಯಾಗ್ ಅನ್ನು ಪುಲ್ ಮಾಡಿ — ಬೇರೆ ಯಾವುದೂ ಬದಲಾಗುವುದಿಲ್ಲ. npm/CLI ಸ್ಥಾಪನೆಯಲ್ಲಿ (Docker ಇಮೇಜ್ ಇಲ್ಲದೆ), ಇದಕ್ಕೆ ಸಮಾನವಾಗಿ ಕಾಣೆಯಾಗಿರುವ ಭಾಗವು ಬ್ರೌಸರ್ ಬೈನರಿಯಾಗಿದೆ: ಹೋಸ್ಟ್ನಲ್ಲಿ `npx playwright install chromium` ಚಲಾಯಿಸಿ.

#### ಪೂರ್ವ-ಬಿಡುಗಡೆ ಚಾನೆಲ್ನ ಬಳಕೆ

`next` ಚಾನಲ್ ಅನ್ನು ಪ್ರಸ್ತುತ ಡೀಫಾಲ್ಟ್ `release/v*` ಬ್ರಾಂಚ್ಗೆ ಮಾಡುವ ಪ್ರತಿಯೊಂದು push ಸಂದರ್ಭದಲ್ಲೂ ಮರುನಿರ್ಮಿಸಲಾಗುತ್ತದೆ ಮತ್ತು AMD64 ಹಾಗೂ ARM64 ಎರಡಕ್ಕೂ ಪ್ರಕಟಿಸಲಾಗುತ್ತದೆ. ಹಳೆಯ ನಿರ್ವಹಣಾ ಬ್ರಾಂಚ್ಗಳು ಅದನ್ನು ತಿದ್ದಿ ಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮುಂದಿನ ಸ್ಥಿರ tag ರಚಿಸುವ ಮೊದಲು ಸಕ್ರಿಯ release ಬ್ರಾಂಚ್ಗೆ ವಿಲೀನಗೊಂಡಿರುವ ಸರಿಪಡಿಕೆಗಳಿಗಾಗಿ ಈ ಚಾನಲ್ pull ಮಾಡಬಹುದಾದ image ಅನ್ನು ಒದಗಿಸುತ್ತದೆ.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ಗಾಗಿ, ಆಯ್ಕೆಮಾಡಿದ profile ಬಳಸುವ image tag ಅನ್ನು override ಮಾಡಿ, ನಂತರ service ಅನ್ನು pull ಮಾಡಿ ಮರುರಚಿಸಿ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ಸುರಕ್ಷತೆ ಮತ್ತು ಹಿಂದಕ್ಕೆ ಮರಳಿಸುವಿಕೆ

`next` ಒಂದು ಬದಲಾಗುತ್ತಲೇ ಇರುವ pre-release ಚಾನಲ್ ಆಗಿದೆ. ಸಕ್ರಿಯ release ಬ್ರಾಂಚ್ಗೆ ಮಾಡುವ ಯಾವುದೇ push ಸಂದರ್ಭದಲ್ಲಿ ಇದು ಬದಲಾಗಬಹುದು ಮತ್ತು **production ಬಳಕೆಗೆ ಬೆಂಬಲಿತವಾಗಿಲ್ಲ**. ನಿರ್ದಿಷ್ಟ build ಅನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡುವಾಗ image digest ಅನ್ನು pin ಮಾಡಿ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ಪರೀಕ್ಷಿಸುವ ಮೊದಲು, OmniRoute data volume ಅಥವಾ bind-mounted data directory ಅನ್ನು backup ಮಾಡಿ. ಹಿಂದಕ್ಕೆ ಮರಳಿಸಲು, ಹಿಂದೆ ಬಳಸಿದ ಸ್ಥಿರ version ಅಥವಾ digest ಅನ್ನು ಪುನಃಸ್ಥಾಪಿಸಿ ಮತ್ತು container ಅನ್ನು ಮರುರಚಿಸಿ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

release-branch build ಎಂದಿಗೂ `latest` ಅನ್ನು ಬದಲಾಯಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ; ಅರ್ಹವಾದ ಸ್ಥಿರ semantic version ಮಾತ್ರ ಸ್ಥಿರ pointer ಅನ್ನು ಮೇಲ್ದರ್ಜೆಗೇರಿಸಬಹುದು. `next` images, release image ಪರಿಶೀಲನೆ ಮತ್ತು ತಡೆಹಿಡಿಯುವ CRITICAL-vulnerability gate ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

**`latest` ಎಂಬುದು git ಗೆ ನವೀನತೆಯ ಖಾತರಿಯಲ್ಲ.** `main` ಅಥವಾ ಸಕ್ರಿಯ `release/v*` ಬ್ರಾಂಚ್ಗೆ ವಿಲೀನಗೊಂಡ ಸರಿಪಡಿಕೆಗಳು, ಸ್ಥಿರ SemVer image ಪ್ರಕಟವಾಗಿ publish job `:latest` ಅನ್ನು ಮೇಲ್ದರ್ಜೆಗೇರಿಸುವವರೆಗೆ (ಆ SemVer ನಂತೆಯೇ ಅದೇ digest) `:latest` ನಲ್ಲಿ ಇರುವುದಿಲ್ಲ. GitHub ನಲ್ಲಿ ಸರಿಪಡಿಕೆ ಈಗಾಗಲೇ ಕಾಣಿಸುತ್ತಿದ್ದರೂ `latest` ಸ್ಥಗಿತಗೊಂಡಂತೆ ಕಂಡುಬಂದರೆ, release ಬ್ರಾಂಚ್ ಅನ್ನು ಪರೀಕ್ಷಿಸಲು `:next` ಅನ್ನು pull ಮಾಡಿ ಅಥವಾ SemVer tag ಗಾಗಿ ಕಾಯಿರಿ.

| ನಿಮಗೆ ಬೇಕಾಗಿರುವುದು                                                                     | ಬಳಸಿ                                              |
| -------------------------------------------------------------------------------------- | ------------------------------------------------- |
| ಬದಲಾಗಬಾರದ GitOps / production                                                          | `:X.Y.Z` ಅನ್ನು pin ಮಾಡಿ (ಅಥವಾ image digest ಅನ್ನು) |
| ಪ್ರಕಟಿತ ಸ್ಥಿರ ಬಿಡುಗಡೆಗಳನ್ನು ಅನುಸರಿಸಿ ಮತ್ತು ಪ್ರತಿ ಬಿಡುಗಡೆಯಲ್ಲೂ ಮರುರಚನೆಯನ್ನು ಒಪ್ಪಿಕೊಳ್ಳಿ | `:latest`                                         |
| ಬಿಡುಗಡೆಯಾಗದ `release/v*` commits ಅನ್ನು ಪರೀಕ್ಷಿಸಿ                                       | `:next` (production ಅಲ್ಲ)                         |
| `main` ಅನ್ನು ಪರೀಕ್ಷಿಸಿ                                                                 | `:main` (production ಅಲ್ಲ)                         |

## Docker ನಲ್ಲಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಅಪ್ಡೇಟ್ಗಳು

ಪ್ರಕಟಿತ-ಇಮೇಜ್ ಕಂಟೇನರ್ ತನ್ನನ್ನೇ ಬದಲಾಯಿಸಿಕೊಳ್ಳಲು ಸಾಧ್ಯವಿಲ್ಲ. OmniRoute ತಾನು ಕಂಟೇನರ್ನೊಳಗೆ
ಚಾಲನೆಯಾಗುತ್ತಿರುವುದನ್ನು (`.git` checkout ಇಲ್ಲದೆ, npm ಸ್ಥಾಪನೆಯಾಗಿರದೆ) ಪತ್ತೆಹಚ್ಚಿದಾಗ, ಮುಖಪುಟ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ ಅಪ್ಡೇಟ್ ಬ್ಯಾನರ್
npm/git ಸೂಚನೆಗಳ ಬದಲಿಗೆ ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಲಾಯಿಸಬೇಕಾದ ಕಮಾಂಡ್ ಅನ್ನು ನಕಲಿಸುವ ಬಟನ್ನೊಂದಿಗೆ ತೋರಿಸುತ್ತದೆ:

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

ಸೇವೆಯ ಹೆಸರು `AUTO_UPDATE_SERVICE` ನಿಂದ ಬರುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `omniroute`, ಇದು
`docker-compose.selfhost.yml` ನಲ್ಲಿರುವ ಸೇವೆ). `pull` ಕೇವಲ ಬದಲಾಗುವ ಟ್ಯಾಗ್ ಅನ್ನು (`latest`, `next`) ಮಾತ್ರ ಮುಂದಕ್ಕೆ ಕೊಂಡೊಯ್ಯುತ್ತದೆ; ಸ್ಥಿರಗೊಳಿಸಿದ
`:X.Y.Z` ಟ್ಯಾಗ್ ಇದ್ದರೆ, ಮೊದಲು ಟ್ಯಾಗ್ ಅನ್ನು ತಿದ್ದುಪಡಿ ಮಾಡಿ.

### ಹೋಸ್ಟ್ ಟ್ರಿಗರ್ ಫೈಲ್ನೊಂದಿಗೆ ಒಂದು-ಕ್ಲಿಕ್ ಅಪ್ಡೇಟ್ಗಳು

`/var/run/docker.sock` ಅನ್ನು ಮೌಂಟ್ ಮಾಡದೆಯೇ **Update Now** ಕಾರ್ಯನಿರ್ವಹಿಸುವಂತೆ ಇರಿಸಲು (ಇದು ಕಂಟೇನರ್ಗೆ
ಹೋಸ್ಟ್ನಲ್ಲಿ root ಪ್ರವೇಶವನ್ನು ನೀಡುತ್ತದೆ — ಮೇಲಿನ `cli` ಪ್ರೊಫೈಲ್ ಎಚ್ಚರಿಕೆಯನ್ನು ನೋಡಿ), OmniRoute ಸೇವೆಯಲ್ಲಿ `DOCKER_UPDATE_TRIGGER_FILE` ಅನ್ನು ಹೊಂದಿಸಿ ಮತ್ತು ಹೋಸ್ಟ್ನಲ್ಲಿ ವಾಚರ್ ಅನ್ನು ಚಲಾಯಿಸಿ:

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

ಪಥವು `DATA_DIR` ಒಳಗೇ ಇರಬೇಕು (ಸಾಪೇಕ್ಷ ಮೌಲ್ಯಗಳನ್ನು ಅದಕ್ಕೆ ಅನುಗುಣವಾಗಿ ಪರಿಹರಿಸಲಾಗುತ್ತದೆ); ಬೇರೆ ಯಾವುದನ್ನಾದರೂ
ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. ನಂತರ **Update Now**, `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }` ಅನ್ನು ಆ
ಫೈಲ್ಗೆ ಬರೆಯುತ್ತದೆ, `202` ನೊಂದಿಗೆ ಪ್ರತಿಕ್ರಿಯಿಸುತ್ತದೆ ಮತ್ತು ಹೊಸ ಆವೃತ್ತಿ ಸಕ್ರಿಯವಾಗುವವರೆಗೆ ಡ್ಯಾಶ್ಬೋರ್ಡ್ `/api/system/version` ಅನ್ನು ಪೋಲ್ ಮಾಡಿ
ಮರುಲೋಡ್ ಆಗುತ್ತದೆ. ಈ ಮೋಡ್ನಲ್ಲಿ OmniRoute ಎಂದಿಗೂ shell ಅಥವಾ Docker ಕಮಾಂಡ್ ಅನ್ನು ಚಲಾಯಿಸುವುದಿಲ್ಲ. ಪ್ರತಿಯೊಂದು ಅಪ್ಡೇಟ್
ಕ್ರಿಯೆಯಂತೆಯೇ, ವಿನಂತಿಯನ್ನು loopback/LAN ಕ್ಲೈಂಟ್ಗಳಿಂದ ಮಾತ್ರ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ.

ಬೈಂಡ್-ಮೌಂಟ್ ಮಾಡಿದ ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯು ಹೋಸ್ಟ್ಗೆ ಮೇಲ್ವಿಚಾರಣೆ ಮಾಡಲು ಸ್ಥಿರವಾದ ಪಥವನ್ನು ನೀಡುತ್ತದೆ. ಮಾದರಿ `systemd` ಯೂನಿಟ್ಗಳು
(`/srv/omniroute` ಅನ್ನು ನಿಮ್ಮ compose ಫೈಲ್ ಮತ್ತು `data/` ಹೊಂದಿರುವ ಡೈರೆಕ್ಟರಿಗೆ ಅನುಗುಣವಾಗಿ ಹೊಂದಿಸಿ):

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=Watch for OmniRoute dashboard update requests

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=Pull and recreate the OmniRoute container

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

ವಿಫಲವಾದ ಚಾಲನೆಯು ಲೂಪ್ ಆಗದಂತೆ, ಸೇವೆಯು pull ಮಾಡುವ ಮೊದಲು ವಿನಂತಿಯನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ.
`DOCKER_UPDATE_TRIGGER_FILE` ಇಲ್ಲದಿದ್ದರೆ, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಕೈಯಾರೆ ಕಮಾಂಡ್ ಚಲಾಯಿಸುವ ಪ್ರಕ್ರಿಯೆಯನ್ನೇ ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.

## ಲಭ್ಯತೆ: ಡೀಫಾಲ್ಟ್ SQLite ಏಕ-ರೆಪ್ಲಿಕಾ ಆಗಿದೆ

ಪ್ರಮಾಣಿತ Docker / Kubernetes OmniRoute ಎಂದರೆ **ಒಂದು Node ಪ್ರಕ್ರಿಯೆ + ಒಂದು SQLite ರೈಟರ್**. ಈ ಟೋಪಾಲಜಿಯಲ್ಲಿ ಹೆಚ್ಚಿನ ಲಭ್ಯತೆ **ಬೆಂಬಲಿತವಾಗಿಲ್ಲ**.

| ನಿರ್ಬಂಧ                                   | ಪರಿಣಾಮ                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಏಕ ರೈಟರ್                                  | ಒಂದೇ SQLite ಫೈಲ್ ವಿರುದ್ಧ ಬಹು ರೆಪ್ಲಿಕಾಗಳನ್ನು ಚಲಾಯಿಸ**ಬೇಡಿ**. ಅದು DB ಅನ್ನು ಹಾಳುಮಾಡುತ್ತದೆ.                                                                                                                                                                                                                                                                                            |
| ಮರುಸೃಷ್ಟಿ / ಮರುಪ್ರಾರಂಭ / HEALTHCHECK kill | ಪ್ರಗತಿಯಲ್ಲಿರುವ SSE, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್ಗಳು ಮತ್ತು ಇನ್-ಮೆಮೊರಿ ಸ್ಥಿತಿಗೆ **ಸಂಪೂರ್ಣ ಸ್ಥಗಿತ** ಉಂಟಾಗುತ್ತದೆ. ಸಂಪರ್ಕಗೊಂಡಿರುವ ಪ್ರತಿಯೊಂದು ಕ್ಲೈಂಟ್ನ ಸಂಪರ್ಕ ಕಡಿತಗೊಳ್ಳುತ್ತದೆ. ಎಂಡ್ಪಾಯಿಂಟ್ ಇಲ್ಲದಿರುವ ಅವಧಿಯಲ್ಲಿ ಹೊಸ ವಿನಂತಿಗಳು OmniRoute JSON ಬದಲಿಗೆ ರಿವರ್ಸ್-ಪ್ರಾಕ್ಸಿಯಿಂದ **`502 Bad Gateway: Unknown error`** ಪಡೆಯುತ್ತವೆ — ಕ್ಲೈಂಟ್ಗಳು ಇದನ್ನು ಪ್ರೊವೈಡರ್ ವೈಫಲ್ಯದಿಂದ ಪ್ರತ್ಯೇಕಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ (#11015). |
| `/healthz` ನಂತೆಯೇ ಅದೇ event loop          | ಕಾರ್ಯನಿರತ catalog ಅಥವಾ compression tick ಪ್ರೋಬ್ಗಳನ್ನು ವಿಳಂಬಗೊಳಿಸಬಹುದು; ಆಗ ಕಡಿಮೆ timeout **ಏಕೈಕ** ರೆಪ್ಲಿಕಾವನ್ನು ಮರುಪ್ರಾರಂಭಿಸುತ್ತದೆ.                                                                                                                                                                                                                                                  |

**ಪ್ರೋಬ್ ಮ್ಯಾಟ್ರಿಕ್ಸ್** ([Kubernetes ಪ್ರೋಬ್ ಶಿಫಾರಸುಗಳು](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ಅನ್ನೂ ನೋಡಿ):

| ಪ್ರೋಬ್         | ಗುರಿ                                                           | ಬಳಸಬಾರದು                                                                     |
| -------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Liveness       | `PORT` ನಲ್ಲಿ TCP (ಡೀಫಾಲ್ಟ್ `20128`), ಅಥವಾ ಮೃದು HTTP `/healthz` | `/api/monitoring/health`                                                     |
| Readiness      | HTTP `GET /healthz`                                            | event-loop ಕಾರ್ಯನಿರತವಾಗಿರುವುದನ್ನು ನಿಷ್ಕ್ರಿಯವೆಂದು ಪರಿಗಣಿಸುವ ಕಡಿಮೆ timeout ಗಳು |
| ಆಳವಾದ / ಮಾನವರು | `/api/monitoring/health`                                       | ಸ್ವಯಂಚಾಲಿತ kubelet liveness                                                  |

**ಅಪ್ಗ್ರೇಡ್ಗಳು:** ಪ್ರತಿಯೊಂದು ಸೆಷನ್ನ ಸಂಪರ್ಕ ಕಡಿತಗೊಳ್ಳುತ್ತದೆ ಎಂದು ನಿರೀಕ್ಷಿಸಿ. ಸಾಧ್ಯವಾದರೆ ಕ್ಲೈಂಟ್ಗಳನ್ನು drain ಮಾಡಿ; ಡೀಫಾಲ್ಟ್ SQLite ನಲ್ಲಿ rolling update ಇಲ್ಲ. Compose `restart: unless-stopped` ಜೊತೆಗೆ Docker `HEALTHCHECK` ಸಹ ಕಂಟೇನರ್ Unhealthy ಆದಾಗ ಏಕೈಕ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ — ಪರಿಣಾಮದ ವ್ಯಾಪ್ತಿಯೂ ಅದೇ ಆಗಿರುತ್ತದೆ.

**ಏಕ ರೆಪ್ಲಿಕಾ**ಗಾಗಿ Kubernetes ಸ್ನಿಪೆಟ್ (Recreate ಅಗತ್ಯವಿದೆ; ಒಂದೇ SQLite ಫೈಲ್ ವಿರುದ್ಧ `replicas` ಅನ್ನು ಹೆಚ್ಚಿಸಬೇಡಿ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` sleep, SIGTERMಗೆ ಮೊದಲು kubeಗೆ Service ಎಂಡ್ಪಾಯಿಂಟ್ಗಳನ್ನು ತೆಗೆದುಹಾಕಲು ಅವಕಾಶ ನೀಡುತ್ತದೆ; ಹೀಗಾಗಿ **ಹೊಸ** ಟ್ರಾಫಿಕ್ ಸ್ಥಗಿತಗೊಳ್ಳುತ್ತಿರುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ತಲುಪುವುದು ನಿಲ್ಲುತ್ತದೆ. ಪ್ರಗತಿಯಲ್ಲಿರುವ `/v1/responses` SSE ಅನ್ನು heavyweight admission leases (#11015) ಮೂಲಕ `SHUTDOWN_TIMEOUT_MS` (ಡೀಫಾಲ್ಟ್ 30s) ವರೆಗೆ ಪೂರ್ಣಗೊಳ್ಳಲು ಅವಕಾಶ ನೀಡಲಾಗುತ್ತದೆ. ಇನ್ನೂ ಪ್ರಕ್ರಿಯೆಯನ್ನು ತಲುಪುವ ಹೊಸ ವಿನಂತಿಗಳಿಗೆ `503` + `Retry-After: 5` ದೊರೆಯುತ್ತದೆ. ಬದಲಿ ಘಟಕವು Ready ಆಗುವವರೆಗೆ ಇರುವ Recreate ಖಾಲಿ-ಎಂಡ್ಪಾಯಿಂಟ್ ಅಂತರವು ಸಂಪೂರ್ಣ ಸೇವಾ ಸ್ಥಗಿತವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ — ಅದು SQLite ಟೊಪಾಲಜಿಯ ಪರಿಣಾಮ, probe ತಪ್ಪು ಸಂರಚನೆಯಲ್ಲ.

ಬಾಹ್ಯ Postgres / multi-writer HA ಒಂದು ದಾಖಲಿತ stock ಮಾರ್ಗ **ಅಲ್ಲ**. ನಿಮಗೆ HA ಅಗತ್ಯವಿದ್ದರೆ, ಒಂದೇ replica ಇಟ್ಟುಕೊಳ್ಳಿ ಅಥವಾ ಪ್ರಾಜೆಕ್ಟ್ ಪ್ರತ್ಯೇಕವಾಗಿ ಪರೀಕ್ಷಿಸಿ ದಾಖಲಿಸಿರುವ ಟೊಪಾಲಜಿಯನ್ನು ಚಲಾಯಿಸಿ. Postgres/MySQL ಸಂಬಂಧಿತ ಕೆಲಸವು [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ನಲ್ಲಿದೆ. ಅದು ಬಿಡುಗಡೆಯಾಗುವವರೆಗೆ, **ದೊಡ್ಡ** `/v1/responses` ಸಾಮರ್ಥ್ಯವನ್ನು ಹೆಚ್ಚಿಸಲು ಬೆಂಬಲಿತವಾಗಿರುವ ಏಕೈಕ ಮಾರ್ಗವೆಂದರೆ N ಸ್ವತಂತ್ರ ಪ್ರಕ್ರಿಯೆಗಳು (ಮುಂದಿನ ವಿಭಾಗ); ಒಂದೇ volume ಮೇಲೆ `replicas > 1` ಅಲ್ಲ.

## ಸ್ಕೇಲ್-ಔಟ್: N ಸ್ವತಂತ್ರ ಪ್ರಕ್ರಿಯೆಗಳು

ಒಂದು Node ಪ್ರಕ್ರಿಯೆಯು **ಒಂದು V8 heap** ಆಗಿರುತ್ತದೆ. ಒಂದರ ಮೇಲೊಂದು ಚಲಿಸುವ ~3 MiB / ~750k-token coding-agent `POST /v1/responses` ವಿನಂತಿಗಳು (RTK + Caveman) ~12 Gi ನಲ್ಲಿ ಆ heap ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತವೆ (`FATAL ERROR: Reached heap limit`) ಮತ್ತು 16 Gi cgroup ನಲ್ಲಿ OOM ಉಂಟುಮಾಡಬಹುದು. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ನೋಡಿ. ಆ ಮಾಪನವು **ಮೆಮೊರಿ-ಬಜೆಟ್** ಎಚ್ಚರಿಕೆಯೇ ಹೊರತು, ಏಕಕಾಲೀನ ದೀರ್ಘ `/v1/responses` ವಿನಂತಿಗಳಿಗೆ ಉತ್ಪನ್ನದ ಗರಿಷ್ಠ ಮಿತಿ ಎರಡು ಎಂದಲ್ಲ. ಹೆವಿವೇಟ್ ಚಾಟ್ ಪ್ರವೇಶವನ್ನು ಅದೇ V8/cgroup ಮಿತಿಯಿಂದ ಗಾತ್ರ ನಿರ್ಧರಿಸಲಾದ, ಸ್ವಯಂಚಾಲಿತವಾಗಿ ವ್ಯುತ್ಪನ್ನವಾಗುವ ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ನಿಯಂತ್ರಿಸುತ್ತದೆ — ಈಗಾಗಲೇ ಗಾತ್ರಗೊಳಿಸಿದ ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿ ಅದನ್ನು ಹೆಚ್ಚಿಸುವುದು (ಅಥವಾ ಹಳೆಯ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` request-count ಮಿತಿಯನ್ನು ಹೊಂದಿಸುವುದು) ಸ್ಥಗಿತವನ್ನು ಮತ್ತೆ ಉಂಟುಮಾಡುತ್ತದೆ. ಸಣ್ಣ ಚಾಟ್ಗಳು, `/healthz`, `/v1/models`, ಮತ್ತು MCP ಆ ಮಿತಿಯೊಳಗೆ **ಇಲ್ಲ**.

### ಏಕ-ಪ್ರಕ್ರಿಯೆ: ಎರಡಕ್ಕಿಂತ ಹೆಚ್ಚು ದೀರ್ಘ `/v1/responses`

ಒಂದು **ಆರೋಗ್ಯಕರ** ಪ್ರಕ್ರಿಯೆಯು (heap `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ಗಿಂತ ಕೆಳಗಿರುವಾಗ, ಡೀಫಾಲ್ಟ್ `0.75`) ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪಿ inflight-byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ನಲ್ಲಿ ಇನ್ನೂ ಸ್ಥಳವಿದ್ದರೆ, ಏಕಕಾಲದಲ್ಲಿ ಎರಡಕ್ಕಿಂತ ಹೆಚ್ಚು ದೀರ್ಘ `POST /v1/responses` ವಿನಂತಿಗಳನ್ನು ಚಲಾಯಿಸಬಹುದು. `OMNIROUTE_CHAT_LARGE_BODY_BYTES` ಗೆ ಸಮನಾದ ಅಥವಾ ಅದಕ್ಕಿಂತ ದೊಡ್ಡ body ಗಳು (ಡೀಫಾಲ್ಟ್ 256 KiB) ರಚನೆ-ಭಾರೀ ವಿನಂತಿಗಳಂತೆಯೇ ಅದೇ ಹೆವಿವೇಟ್ lease ಅನ್ನು ಪಡೆಯುತ್ತವೆ ಮತ್ತು ಅದೇ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` ವಿನಾಯಿತಿಯನ್ನು (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ಬಳಸುತ್ತವೆ. ಹತ್ತಾರು ಏಕಕಾಲೀನ ದೀರ್ಘ SSE ಕ್ಲೈಂಟ್ಗಳು (ಆಪರೇಟರ್ಗಳಿಗೆ ಸಾಮಾನ್ಯವಾಗಿ 40–50 ಬೇಕಾಗುತ್ತವೆ) ಒಂದು **ಮೆಮೊರಿ-ಬಜೆಟ್** ಪ್ರಶ್ನೆಯಾಗಿದೆ — heap + primary/headroom slots + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ಅನ್ನು ಸೂಕ್ತವಾಗಿ ಗಾತ್ರಗೊಳಿಸಿ — ಇದು ಉತ್ಪನ್ನದ ಕಟ್ಟುನಿಟ್ಟಾದ “ಗರಿಷ್ಠ 2” ಮಿತಿಯಲ್ಲ. ಒತ್ತಡದಲ್ಲಿರುವ heap ಇನ್ನೂ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಮೂಲಕ ಲೋಡ್ ತಗ್ಗಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ #7849 ಮರುಕಳಿಸುವುದಿಲ್ಲ.

**heap ಗಳನ್ನು ಗುಣಿಸಲು** (ಸ್ವತಂತ್ರ V8 old-spaces) **ಇಂದು**:

| ಮಾಡಬೇಕಾದುದು                                                                                                                                                     | ಮಾಡಬಾರದು                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **N containers/pods** ಅನ್ನು ಚಲಾಯಿಸಿ; ಪ್ರತಿಯೊಂದಕ್ಕೂ ಅದರ **ಸ್ವಂತ** `DATA_DIR` / volume ಇರಲಿ                                                                       | ಒಂದೇ SQLite file ವಿರುದ್ಧ `replicas > 1` ಹೊಂದಿಸುವುದು              |
| heap / inflight-byte budget ಆಧರಿಸಿ heavy in-flight + healthy-headroom ಅನ್ನು ಗಾತ್ರಗೊಳಿಸಿ; 1–2 ಎಂಬುದು ಸಂಯಮದ #7849 ಡೀಫಾಲ್ಟ್, ಕಟ್ಟುನಿಟ್ಟಾದ ಉತ್ಪನ್ನದ ಗರಿಷ್ಠ ಮಿತಿಯಲ್ಲ | ಒಂದು ಪ್ರಕ್ರಿಯೆಗೆ 8× RAM ಮತ್ತು ಮಿತಿಯಿಲ್ಲದ count cap ನೀಡುವುದು      |
| ಐಚ್ಛಿಕ: **ಹಂಚಿಕೆಯ quota counters** ಗಾಗಿ `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                    | Redis ಅನ್ನು ಹಂಚಿಕೆಯ SQLite ಎಂದು ಪರಿಗಣಿಸುವುದು — ಅದು ಹಾಗಲ್ಲ        |
| ಪ್ರತಿಯೊಂದು instance ಗೆ provider secrets ಅನ್ನು ನಕಲಿಸಿ (ಅಥವಾ ವಿಭಜಿತ dashboards ಅನ್ನು ಒಪ್ಪಿಕೊಳ್ಳಿ)                                                                 | instances ಗಳಾದ್ಯಂತ ಒಂದೇ dashboard / ಒಂದೇ call-log ನಿರೀಕ್ಷಿಸುವುದು |
| ಯಾವುದೇ load balancer ಅನ್ನು ಮುಂಭಾಗದಲ್ಲಿ ಇರಿಸಿ; API key ಅಥವಾ session ಆಧಾರಿತ sticky routing ಸಾಕು                                                                   | vendor-specific size-aware middleware ಅನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುವುದು     |

ಹಾರ್ಡ್ವೇರ್: ಪ್ರತಿ-instance ನ ಏಕಕಾಲೀನ ದೀರ್ಘ `/v1/responses` ಸಾಮರ್ಥ್ಯವು ಒಂದು **ಮೆಮೊರಿ-ಬಜೆಟ್** ಪ್ರಶ್ನೆಯಾಗಿದೆ (heap + inflight-byte / #10110). `N` ಸ್ವತಂತ್ರ `DATA_DIR` ಗಳು ಇನ್ನೂ heap ಗಳನ್ನು ಗುಣಿಸುತ್ತವೆ: host RAM, `N × cgroup` ಅನ್ನು ನಿಭಾಯಿಸಬೇಕು; “N=8 ಹೊಂದಿರುವ ಒಂದು 16 Gi pod” ಅನ್ನು ಅಲ್ಲ. ಒಂದೇ SQLite file ಮೇಲೆ ಎಂದಿಗೂ `replicas > 1` ಬಳಸಬೇಡಿ.

Compose ಮಾದರಿ (ಎರಡು heap ಗಳು, ಎರಡು volume ಗಳು — `deploy.replicas: 2` ಅಲ್ಲ):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

In-process density (HTTP isolate ನಿಂದ compression ಅನ್ನು ಹೊರಗಿಡುವುದು) ಕುರಿತು [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ನೋಡಿ. ಹಂಚಿಕೆಯ durable state ಮೇಲಿನ ಒಂದು logical cluster ಕುರಿತು [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ನೋಡಿ.

## Docker ಒಳಗಿನ Gemini ಪ್ರಾದೇಶಿಕ ದೋಷಗಳು

Google AI Studio / Gemini API, FAILED_PRECONDITION ಜೊತೆಗೆ HTTP 400 ಮತ್ತು
`User location is not supported for the API use.` ದೋಷವನ್ನು ಹಿಂತಿರುಗಿಸಬಹುದು. ಹೋಸ್ಟ್ನಲ್ಲಿ ವಿನಂತಿಯೊಂದು ಯಶಸ್ವಿಯಾದರೆ,
ಕಂಟೈನರ್ ಸಹ ಅದೇ ಹೊರಹೋಗುವ ಮಾರ್ಗವನ್ನು ಬಳಸುತ್ತದೆ ಎಂಬುದು ಸಾಬೀತಾಗುವುದಿಲ್ಲ. DNS ಕ್ರಮ,
IPv4/IPv6 ಸಂಪರ್ಕ, VPN ರೂಟಿಂಗ್ ಮತ್ತು ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಪ್ರಾಕ್ಸಿಗಳು ಭಿನ್ನವಾಗಿರಬಹುದು.
[Google ಬೆಂಬಲಿಸುವ ಪ್ರದೇಶಗಳು](https://ai.google.dev/gemini-api/docs/available-regions)
ಹಾಗೂ ನಿಜವಾದ ಸಂಪರ್ಕ ಮಾರ್ಗವನ್ನು ಪರಿಶೀಲಿಸಿ; ಈ ದೋಷವೊಂದರಿಂದಲೇ API key ದೋಷಪೂರಿತವಾಗಿದೆ ಎಂದು ನಿರ್ಧರಿಸಲಾಗುವುದಿಲ್ಲ.

### ಸಂಪರ್ಕ-ನಿರ್ದಿಷ್ಟ ಪ್ರಾಕ್ಸಿಗೆ ಆದ್ಯತೆ ನೀಡಿ

ಬಾಧಿತ Gemini ಸಂಪರ್ಕಕ್ಕಾಗಿ OmniRouteನ [ಪ್ರತಿ-ಸಂಪರ್ಕದ ಪ್ರಾಕ್ಸಿ ಕಾನ್ಫಿಗರೇಶನ್](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ಅನ್ನು ಬಳಸಿ, ನಂತರ ಅದೇ ಮಾದರಿಯೊಂದಿಗೆ **ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸಿ** ಮತ್ತು ಒಂದು ಸಣ್ಣ ವಿನಂತಿಯನ್ನು
ಮತ್ತೆ ಪ್ರಯತ್ನಿಸಿ. ಇದರಿಂದ ರೂಟಿಂಗ್ ಬದಲಾವಣೆಯು ಆ ಸಂಪರ್ಕಕ್ಕೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿರುತ್ತದೆ. ಕಂಟೈನರ್ನಿಂದ
ಪ್ರಾಕ್ಸಿಯನ್ನು ತಲುಪಬಹುದೇ ಮತ್ತು ಸಂಪರ್ಕವು ನಿಜವಾಗಿಯೂ ಅದನ್ನೇ ಆಯ್ಕೆಮಾಡುತ್ತದೆಯೇ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ.
ಮಾರ್ಗವನ್ನು ಬದಲಾಯಿಸುವುದರಿಂದ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರಾದೇಶಿಕ ಅರ್ಹತೆ ಖಚಿತವಾಗುವುದಿಲ್ಲ.

### ಹೋಸ್ಟ್ ಮತ್ತು ಕಂಟೈನರ್ ನೆಟ್ವರ್ಕಿಂಗ್ ಹೋಲಿಸಿ

ದೃಢೀಕರಿಸಿದ ಫಲಿತಾಂಶಗಳನ್ನು ಹೋಲಿಸುವಾಗ key, model ಮತ್ತು request ಅನ್ನು ಒಂದೇ ರೀತಿಯಲ್ಲಿ ಇರಿಸಿ; ರುಜುವಾತುಗಳು,
ಪ್ರಾಕ್ಸಿ ಪಾಸ್ವರ್ಡ್ಗಳು ಅಥವಾ ಸಂಪೂರ್ಣ ದೃಢೀಕರಣ ಹೆಡರ್ಗಳನ್ನು issue ಒಂದರಲ್ಲಿ ಎಂದಿಗೂ ಅಂಟಿಸಬೇಡಿ.
ಮೊದಲು OS resolver ಯಾವ address family ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ; ಹೋಸ್ಟ್ನಲ್ಲಿ ಮತ್ತು
ಕಂಟೈನರ್ನ ಒಳಗೆ ಒಂದೇ command ಬಳಸಿ:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` ಅನ್ನು ನೀವು ಚಲಾಯಿಸುವ serviceನಿಂದ ಬದಲಾಯಿಸಿ (ಉದಾಹರಣೆಗೆ, `omniroute-web`). ಈ
command ಗಳು ರುಜುವಾತುಗಳು ಅಥವಾ IP ವಿಳಾಸಗಳಿಲ್ಲದೆ address family ಗಳನ್ನು ಮುದ್ರಿಸುತ್ತವೆ. ಹಿಂತಿರುಗಿದ `6`
ಕೇವಲ IPv6 DNS ಫಲಿತಾಂಶವನ್ನು ತೋರಿಸುತ್ತದೆ: ಅದು ಬಳಸಬಹುದಾದ IPv6 ಮಾರ್ಗ ಅಥವಾ API ಪ್ರವೇಶವನ್ನು
ಸಾಬೀತುಪಡಿಸುವುದಿಲ್ಲ. `curl` ಸ್ಥಾಪಿಸಿರುವಲ್ಲಿ, ಎರಡೂ ಪರಿಸರಗಳಲ್ಲಿ
`curl -4 -I https://generativelanguage.googleapis.com` ಅನ್ನು
`curl -6 -I https://generativelanguage.googleapis.com` ಜೊತೆಗೆ ಹೋಲಿಸಿ.
ದೃಢೀಕರಣವಿಲ್ಲದ ದೋಷವಾಗಿದ್ದರೂ ಸಹ, HTTP ಪ್ರತಿಕ್ರಿಯೆಯು ಆ ಪರೀಕ್ಷೆಗೆ ಸಂಪರ್ಕವಿದೆ ಎಂಬುದನ್ನು ಸಾಬೀತುಪಡಿಸುತ್ತದೆ;
ದೃಢೀಕರಿಸಿದ model request ಮಾತ್ರ Gemini ಅರ್ಹತೆಯನ್ನು ಪರೀಕ್ಷಿಸುತ್ತದೆ.

### ಹೋಸ್ಟ್-ಮಟ್ಟದ ಪರ್ಯಾಯ: ಕಾರ್ಯನಿರ್ವಹಿಸುವ IPv6 ಮತ್ತು resolver ನೀತಿ

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) ವರದಿಗಾರರು ತಮ್ಮ ಪರಿಸರದಲ್ಲಿ
ಕಂಟೈನರ್ IPv6 ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ ಮತ್ತು glibc ವಿಳಾಸ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸುವ ಮೂಲಕ ಪ್ರವೇಶವನ್ನು ಮರುಸ್ಥಾಪಿಸಿದರು.
ಇದನ್ನು ಪರಿಸರ-ನಿರ್ದಿಷ್ಟ ಪರ್ಯಾಯವೆಂದು ಪರಿಗಣಿಸಿ. resolver ಆದ್ಯತೆಗಳನ್ನು ಸರಿಹೊಂದಿಸುವ ಮೊದಲು ಕಾರ್ಯನಿರ್ವಹಿಸುವ
ಹೋಸ್ಟ್ IPv6, ಕಂಟೈನರ್ egress/routing ಮತ್ತು firewall ನಿಯಮಗಳನ್ನು ದೃಢಪಡಿಸಿ. ಖಾಸಗಿ ULA ವಿಳಾಸವೊಂದೇ
ಸಾರ್ವಜನಿಕ IPv6 ಸಂಪರ್ಕವನ್ನು ಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

ಈಗಾಗಲೇ Composeನ default networkಗೆ ಜೋಡಿಸಲಾದ service ಗಳಿಗಾಗಿ, ಈ ತುಣುಕು ಆ networkನಲ್ಲಿ
IPv6 ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ; ನಿಮ್ಮ ಉಳಿದ service, ports, volumes ಮತ್ತು configuration ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ:

```yaml
networks:
  default:
    enable_ipv6: true
```

ಹೆಸರಿಸಲಾದ networkಗಾಗಿ, service ನಿಜವಾಗಿ ಸೇರುವ networkನಲ್ಲಿ ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ. Docker ಒಂದು
ULA subnet ಅನ್ನು ನಿಯೋಜಿಸಬಹುದು; ನಿಮ್ಮ networkಗೆ ಅಗತ್ಯವಿದ್ದಾಗ ಮಾತ್ರ ಸ್ಪಷ್ಟವಾಗಿ ನಿರ್ದಿಷ್ಟಪಡಿಸಿದ,
ಅತಿಕ್ರಮಿಸದ subnet ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ. [Docker IPv6 ನೆಟ್ವರ್ಕಿಂಗ್](https://docs.docker.com/engine/daemon/ipv6/)
ಮತ್ತು [Compose network ಆಯ್ಕೆಗಳು](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ನೋಡಿ.

**glibc-ಆಧಾರಿತ image** ಒಂದರಲ್ಲಿ, `/etc/gai.conf` ವಿಳಾಸ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸಬಹುದು. ಪ್ರಸ್ತುತ
repository Dockerfile Debian ಅನ್ನು ಬಳಸುತ್ತದೆ; ಕಸ್ಟಮ್ musl-ಆಧಾರಿತ image ಗಳು ಈ ಕಾರ್ಯವಿಧಾನವನ್ನು
ಹಂಚಿಕೊಳ್ಳುವುದಿಲ್ಲ. ವರದಿ ಮಾಡಲಾದ ಹೊಂದಾಣಿಕೆಯು ULA label ಅನ್ನು `label fc00::/7 6` ಇಂದ
`label fc00::/7 1` ಗೆ ಬದಲಾಯಿಸುತ್ತದೆ. imageನ ಸಂಪೂರ್ಣ policy tableನಿಂದ ಪ್ರಾರಂಭಿಸಿ ಮತ್ತು ಅದರ ಇತರ
entry ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ: `label` ಅಥವಾ `precedence` entry ಸೇರಿಸುವುದರಿಂದ ಆ default table
ಬದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಬದಲಾಯಿಸಿದ ಸಾಲು ಮಾತ್ರ ಇರುವ file ಸಾಕಾಗುವುದಿಲ್ಲ.
[glibc ಕಾನ್ಫಿಗರೇಶನ್ ಉಲ್ಲೇಖ](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ಆ ಅರ್ಥವಿಧಾನಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಪರಿಶೀಲಿಸಿದ file ಅನ್ನು `/etc/gai.conf` ನಲ್ಲಿ read-only ಆಗಿ
bind-mount ಮಾಡಿ ಮತ್ತು ಅದನ್ನು ಅನ್ವಯಿಸಲು service ಅನ್ನು ಮರುರಚಿಸಿ.

ಇದು **ಆ ಕಂಟೈನರ್ನಲ್ಲಿನ ಎಲ್ಲಾ ಹೊರಹೋಗುವ ಟ್ರಾಫಿಕ್ಗಾಗಿ** OS ವಿಳಾಸ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
ಇದು ಪ್ರತಿಯೊಂದು application ಅನ್ನು IPv6 ಆಯ್ಕೆಮಾಡುವಂತೆ ಒತ್ತಾಯಿಸುವುದಿಲ್ಲ: Nodeನ DNS order ಮತ್ತು
connection selection ಕೂಡ ಮುಖ್ಯವಾಗುತ್ತವೆ. ವಿಶೇಷವಾಗಿ, `--dns-result-order=ipv4first` IPv4 ಗೆ
ಆದ್ಯತೆ ನೀಡುತ್ತದೆ ಮತ್ತು IPv4-ಮಾತ್ರದ ವೈಫಲ್ಯಕ್ಕೆ ಪರಿಹಾರವಲ್ಲ. [Node DNS ಕ್ರಮ](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ನೋಡಿ.

ಯಾವುದೇ ಹೋಸ್ಟ್-ಮಟ್ಟದ ಬದಲಾವಣೆಯ ನಂತರ Gemini ಮತ್ತು ನಿಮ್ಮ ಇತರ provider ಗಳನ್ನು ಮರುಪರೀಕ್ಷಿಸಿ.
ಹಿಂದಿನ ಸ್ಥಿತಿಗೆ ಮರಳಲು, ಕಸ್ಟಮ್ `gai.conf` mount ತೆಗೆದುಹಾಕಿ, ಹಿಂದಿನ network configuration ಅನ್ನು
ಮರುಸ್ಥಾಪಿಸಿ ಮತ್ತು maintenance window ಸಮಯದಲ್ಲಿ ಬಾಧಿತ service/network ಅನ್ನು ಮರುರಚಿಸಿ. network ಅನ್ನು
ಮರುರಚಿಸುವುದರಿಂದ ಅದಕ್ಕೆ ಜೋಡಿಸಲಾದ ಇತರ ಕಂಟೈನರ್ಗಳಿಗೆ ಅಡಚಣೆಯಾಗಬಹುದು; persistent data volume ಅನ್ನು ಅಳಿಸಬೇಡಿ.

## ಪ್ರಮುಖ ಟಿಪ್ಪಣಿಗಳು

- **SQLite WAL ಮೋಡ್:** OmniRoute ಇತ್ತೀಚಿನ ಬದಲಾವಣೆಗಳನ್ನು `storage.sqlite` ಗೆ ಮರಳಿ checkpoint ಮಾಡಲು ಸಾಧ್ಯವಾಗುವಂತೆ `docker stop` ಪೂರ್ಣಗೊಳ್ಳಲು ಅವಕಾಶ ನೀಡಬೇಕು. ಜೊತೆಗೆ ಒದಗಿಸಲಾದ Compose ಫೈಲ್ಗಳಲ್ಲಿ ಈಗಾಗಲೇ 40s stop grace period ಹೊಂದಿಸಲಾಗಿದೆ. ನೀವು image ಅನ್ನು ನೇರವಾಗಿ ಚಲಾಯಿಸಿದರೆ, `--stop-timeout 40` ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ನಿಯಮಿತ/pre-write backupಗಳನ್ನು ಬಾಹ್ಯವಾಗಿ ನಿರ್ವಹಿಸುತ್ತಿದ್ದರೆ ಇದನ್ನು `true` ಗೆ ಹೊಂದಿಸಿ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ database migrationಗಳಿಗೆ ಇನ್ನೂ ತಮ್ಮದೇ ಆದ ಬಾಳಿಕೆ ಬರುವ ಸುರಕ್ಷತಾ snapshot ಮತ್ತು mass-migration guard ಅಗತ್ಯವಿರುತ್ತದೆ.
- **ಡೇಟಾ ನಿರಂತರತೆ:** container ಮರುಪ್ರಾರಂಭಗಳಾದಾಗಲೂ ನಿಮ್ಮ database, keyಗಳು ಮತ್ತು configurationಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲು ಯಾವಾಗಲೂ `/app/data` ಗೆ volume ಅನ್ನು mount ಮಾಡಿ.
- **ಪೋರ್ಟ್ ಸಂರಚನೆ:** ಡೀಫಾಲ್ಟ್ `20128` ಪೋರ್ಟ್ ಅನ್ನು ಬದಲಾಯಿಸಲು `PORT` environment variable ಅನ್ನು override ಮಾಡಿ.
