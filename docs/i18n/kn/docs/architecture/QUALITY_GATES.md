ಈ ದಸ್ತಾವೇಜು OmniRouteನಲ್ಲಿನ ಎಲ್ಲಾ CI ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳಿಗೆ ಅಧಿಕೃತ ಉಲ್ಲೇಖವಾಗಿದೆ.
ಇದು ಪ್ರತಿಯೊಂದು ಗೇಟ್, ಅದು ಏನನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ, ಅದು ಯಾವ CI ಜಾಬ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ, ಅದು
ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ ಅಥವಾ ಪಾಸ್/ಫೇಲ್ ನೀತಿಯನ್ನು ಬಳಸುತ್ತದೆಯೇ ಮತ್ತು ಅದು ಬಿಲ್ಡ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆಯೇ ಅಥವಾ ಸಲಹಾತ್ಮಕವಾಗಿದೆಯೇ ಎಂಬುದನ್ನು ವಿವರಿಸುತ್ತದೆ.

ಸಂಕ್ಷಿಪ್ತ ಸಾರಾಂಶ ಮತ್ತು ಅನುಮತಿಪಟ್ಟಿ ನೀತಿಗಾಗಿ, `AGENTS.md`ನಲ್ಲಿರುವ "ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳು ಮತ್ತು ರ್ಯಾಚೆಟ್ಗಳು" ವಿಭಾಗವನ್ನು
ನೋಡಿ. ಇದೇ ಸಿಸ್ಟಮ್ನ ವಿಮರ್ಶಾತ್ಮಕ ಮೌಲ್ಯಮಾಪನ, ಪಕ್ವತೆಯ ವರ್ಗೀಕರಣ ಮತ್ತು ಉಪಕರಣ-ಸ್ವತಂತ್ರ
ಮರುಅನುಷ್ಠಾನ ಯೋಜನೆಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ ಪ್ಲೇಬುಕ್](../ops/QUALITY_GATE_PLAYBOOK.md) ನೋಡಿ.

## ಗೇಟ್ ಇನ್ವೆಂಟರಿ ಮತ್ತು ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆ ಪ್ರೊಫೈಲ್ಗಳು

### ಅಭ್ಯರ್ಥಿಯ ಸ್ವೀಕಾರ

CI ಮತ್ತು Quality Gates ವರ್ಕ್ಫ್ಲೋಗಳು ಪ್ರತಿಯೊಂದೂ ಸ್ಥಿರವಾದ ತೀರ್ಪನ್ನು ಹೊರಸೂಸುತ್ತವೆ: `Gate / CI` ಮತ್ತು
`Gate / Quality`. ಅವುಗಳ ಆವೃತ್ತಿಗೊಳಿಸಲಾದ ಸ್ವೀಕಾರ ನೀತಿಯು ಪ್ರತಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ಜಾಬ್ ಅನ್ನು
ಕಡ್ಡಾಯ ಅಥವಾ ಸಲಹಾತ್ಮಕ ಎಂದು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ. ಅನ್ವಯವಾಗುವ ಕಡ್ಡಾಯ ಜಾಬ್ ಯಶಸ್ವಿಯಾಗಲೇಬೇಕು:
ಕಾಣೆಯಾಗಿರುವ, ರದ್ದುಗೊಂಡ, ಬಿಟ್ಟುಬಿಡಲಾದ, ಬಾಕಿಯಿರುವ ಮತ್ತು ಅಜ್ಞಾತ ಫಲಿತಾಂಶಗಳು PASS ಅನ್ನು ಸ್ಥಾಪಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮಾನ್ಯವಾದ
docs-only ಅಥವಾ catalog-only ವರ್ಗೀಕರಣವು ಕೋಡ್ ಲೇನ್ ಅನ್ನು ಅನ್ವಯವಾಗದಂತೆ ಮಾಡಬಹುದು;
ಕರಡು PR ಅನ್ನು ಸ್ವೀಕೃತ ಅಭ್ಯರ್ಥಿಯೆಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ. `hotfix` ಲೇಬಲ್ ಸಾಕ್ಷ್ಯದ ಅಗತ್ಯವನ್ನು ಮನ್ನಾ ಮಾಡುವುದಿಲ್ಲ.

ಎರಡೂ ವರ್ಕ್ಫ್ಲೋಗಳು main/release ಬ್ರಾಂಚ್ಗಳಿಗೆ ಬರುವ PRಗಳು, `main` ಗೆ ಪುಷ್ಗಳು, ಹಸ್ತಚಾಲಿತ ಡಿಸ್ಪ್ಯಾಚ್
ಮತ್ತು merge-group ಈವೆಂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ. ಪುಷ್, ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು merge-group ಪೂರ್ಣ ಆಯ್ಕೆಯನ್ನು ರನ್ ಮಾಡುತ್ತವೆ.
`release/**` ಗೆ ಪುಷ್ಗಳು ಅವುಗಳನ್ನು ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ (2026-10-18): ಪ್ರತಿಯೊಂದು ಬದಲಾವಣೆಯೂ ಈಗಾಗಲೇ ಅದರ PRನಲ್ಲಿ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು ರನ್ ಮಾಡಿದೆ
ಮತ್ತು ವಿಲೀನಗೊಂಡ ಸಂಯೋಜನೆಯು Release-Greenನ ಜವಾಬ್ದಾರಿಯಾಗಿದೆ (`docs/ops/RUNNER_BOX.md` → Hosted lane). ಫೋರ್ಕ್ಗಳು
ಮತ್ತು merge groupಗಳು ಸಾಮಾನ್ಯವಾಗಿ self-hosted ರನ್ನರ್ಗಳನ್ನು ಆಯ್ಕೆಮಾಡುವ ಜಾಬ್ಗಳಿಗೆ hosted ರನ್ನರ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ;
ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಸಾಕಷ್ಟು hosted ಸಾಮರ್ಥ್ಯವನ್ನು ಪರಿಶೀಲಿಸಬೇಕು.

ಪ್ರತಿ JSON ರಸೀದಿಯು ಚೆಕ್ಔಟ್ ಮಾಡಲಾದ SHA, ವರ್ಕ್ಫ್ಲೋ ರನ್ ಮತ್ತು ಪ್ರಯತ್ನವನ್ನು ಗುರುತಿಸುತ್ತದೆ.
ಚೆಕ್ಔಟ್/event SHA ಅಸಂಗತತೆಯನ್ನು CLI ತಿರಸ್ಕರಿಸುತ್ತದೆ. ವರ್ಕ್ಫ್ಲೋ ಪರೀಕ್ಷೆಗಳು ನೀತಿಯ ಸದಸ್ಯತ್ವವನ್ನು
ತೀರ್ಪು ಜಾಬ್ನ `needs` ಪಟ್ಟಿಗೆ ಬದ್ಧಗೊಳಿಸುತ್ತವೆ, ಆದ್ದರಿಂದ ಹೊಸ ಅಥವಾ ತೆಗೆದುಹಾಕಲಾದ ಲೇನ್ ಮೌನವಾಗಿ ಕಣ್ಮರೆಯಾಗಲು ಸಾಧ್ಯವಿಲ್ಲ.
ರಸೀದಿಗಳು ತಮ್ಮದೇ ವರ್ಕ್ಫ್ಲೋವನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ; ಪ್ರಕಟಣೆ, ನಿಯೋಜನೆ ಅಥವಾ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಸಲಹಾತ್ಮಕ ಸ್ಕ್ಯಾನರ್ನ ಆಂತರಿಕ ಕಾರ್ಯವಿಧಾನಗಳನ್ನು ಅಲ್ಲ. ಬ್ರಾಂಚ್ ನಿಯಮಗಳಲ್ಲಿ ಎರಡೂ ಚೆಕ್ ಹೆಸರುಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದು
ಪ್ರತ್ಯೇಕ ಆಡಳಿತಾತ್ಮಕ ಬದಲಾವಣೆಯಾಗಿದೆ; ಈ ಜಾಬ್ಗಳನ್ನು ಸೇರಿಸುವುದರಿಂದ ಮಾತ್ರ ಬ್ರಾಂಚ್ ರಕ್ಷಿತವಾಗುವುದಿಲ್ಲ.

### ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಇನ್ವೆಂಟರಿ

ಆವೃತ್ತಿಗೊಳಿಸಲಾದ npm-alias ಇನ್ವೆಂಟರಿ ಮತ್ತು static-scan ಸದಸ್ಯತ್ವವು
`config/quality/gate-manifest.json` ನಲ್ಲಿವೆ. ಸ್ಕ್ರಿಪ್ಟ್ ಹೆಸರುಗಳು ಮತ್ತು ನಿಖರವಾದ ಕಮಾಂಡ್ಗಳನ್ನು
`package.json` ಗೆ ಹೋಲಿಸಿ ಮೌಲ್ಯೀಕರಿಸಲು `npm run check:gate-manifest` ಅನ್ನು ರನ್ ಮಾಡಿ; ಸೇರ್ಪಡೆಗಳು, ತೆಗೆದುಹಾಕುವಿಕೆಗಳು
ಮತ್ತು ಕಮಾಂಡ್ ವ್ಯತ್ಯಾಸಗಳು ಸ್ಥಳೀಯ hook ಹಾಗೂ CIಯಲ್ಲಿನ ಬದಲಾವಣೆ-ವರ್ಗೀಕರಣ ಜಾಬ್ಗಳೆರಡನ್ನೂ ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
alias ಒಂದು ವರ್ಕ್ಫ್ಲೋ ಜಾಬ್, matrix instance ಅಥವಾ test case ಅಲ್ಲ: ಈ ಎಣಿಕೆಗಳನ್ನು
ಪರಸ್ಪರ ವಿನಿಮಯಯೋಗ್ಯವೆಂದು ಪ್ರಸ್ತುತಪಡಿಸಬಾರದು.

ಆಯ್ಕೆಮಾಡಲಾದ aliasಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸದೆ ಪರಿಶೀಲಿಸಲು `npm run quality:scan -- --list` ಅಥವಾ
`npm run quality:scan:fast -- --list` ಅನ್ನು ಬಳಸಿ. ರನ್ನರ್
npm entrypoint ಅನ್ನು ಆಹ್ವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದರ runtime ಅನ್ನು (ಕಾನ್ಫಿಗರ್ ಮಾಡಿರುವಲ್ಲಿ Bun ಸೇರಿದಂತೆ) ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.
ಮ್ಯಾನಿಫೆಸ್ಟ್ ಆ ಪ್ರೊಫೈಲ್ಗಳ ಹೊರಗಿನ aliasಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಆಹ್ವಾನಿಸಲ್ಪಡುವವುಗಳೆಂದು ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು
read-only ಸ್ಕ್ಯಾನ್ ಪ್ರೊಫೈಲ್ಗಳಲ್ಲಿ ನಿರ್ವಹಣಾ ಕಮಾಂಡ್ಗಳನ್ನು ನಿಷೇಧಿಸಲಾಗಿದೆ.

ಈ ಪ್ರೊಫೈಲ್ಗಳು static scan ಅನ್ನು ಮಾತ್ರ ಒಳಗೊಳ್ಳುತ್ತವೆ. ಅವು product tests,
coverage, packaging, external checks ಅಥವಾ ಅಭ್ಯರ್ಥಿಯ ಸಂಪೂರ್ಣ release acceptance ಅನ್ನು ಪ್ರಮಾಣೀಕರಿಸುವುದಿಲ್ಲ.
ವರ್ಕ್ಫ್ಲೋ ಸ್ವೀಕಾರವು ಲಿಂಕ್ ಮಾಡಲಾದ `config/quality/admission-policy.json` ಮತ್ತು
`scripts/quality/admission-verdict.mjs` ಅನ್ನು ಬಳಸುತ್ತದೆ. Release-observer ಪ್ರೊಫೈಲ್ಗಳು ಪ್ರತ್ಯೇಕವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ;
ಅವುಗಳಿಗೆ ಅನ್ವಯವಾಗುವ ಚೆಕ್ಗಳು ಮತ್ತು ರಸೀದಿಗಳನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸಿ. ಕೆಳಗಿನ ವಿವರಣಾತ್ಮಕ
ಇನ್ವೆಂಟರಿ ಒಂದು ಉಲ್ಲೇಖ ಮಾತ್ರ; ಗೇಟ್ ನಿಜವಾಗಿಯೂ ರನ್ ಆಗಿದೆ ಎಂಬುದಕ್ಕೆ ಅದು ಪುರಾವೆಯಲ್ಲ.

ಸ್ಕ್ರಿಪ್ಟ್ಗಳು `scripts/check/` (policy gates) ಮತ್ತು `scripts/quality/` (ratchet engine) ಅಡಿಯಲ್ಲಿ ಇರುತ್ತವೆ.
CIಯ ಅಧಿಕೃತ ಮೂಲವು `.github/workflows/ci.yml` ಆಗಿದೆ.

### Release PR ವೇಗದ ಮಾರ್ಗ (`quality.yml`)

`.github/workflows/quality.yml` main/release PRಗಳು, `main` ಗೆ ಪುಷ್ಗಳು,
ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು merge groupಗಳಲ್ಲಿ CIಗೆ ಪೂರಕವಾಗಿದೆ. PRಗಳು path-filtered ವೇಗದ ಚೆಕ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಶಾಶ್ವತವಾಗಿ

#### ಮರೆತುಹೋದ sibling tests ವರದಿ

`npm run check:forgotten-sibling-tests` ಪರೀಕ್ಷಾ-ಪ್ರಭಾವ ನಕ್ಷೆಯ ಹಿಂದಿರುವ ಆಮದು ರಿಸಾಲ್ವರ್ ಅನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ.
ಬದಲಾಯಿಸಲಾದ ಪ್ರತಿಯೊಂದು ಪ್ರೊಡಕ್ಷನ್ ಮಾಡ್ಯೂಲ್ಗಾಗಿ, ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆಯು ಪುಲ್ ರಿಕ್ವೆಸ್ಟ್ ಡಿಫ್ನಲ್ಲಿ
ಇಲ್ಲದಿದ್ದಾಗ, ಇದು ನಿರ್ಣಾಯಕವಾದ `changed module/symbol -> static consumer -> candidate sibling test`
ಸರಪಳಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಯಾವುದೇ ನಿರ್ಬಂಧಕ ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಮಾಪನಾಂಕ ನಿರ್ಣಯಕ್ಕಾಗಿ Markdown
ಸಾರಾಂಶ ಮತ್ತು JSON ಫಲಿತಾಂಶವನ್ನು `forgotten-sibling-tests` ವರ್ಕ್ಫ್ಲೋ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

ಬ್ಯಾರೆಲ್ ಮರು-ರಫ್ತುಗಳು ಮತ್ತು ಡೈನಾಮಿಕ್ ಆಮದುಗಳು ರೆಸಲ್ಯೂಷನ್ ಡಯಾಗ್ನಾಸ್ಟಿಕ್ಗಳು ಮಾತ್ರ; ಅವು ಎಂದಿಗೂ
ನಿರ್ಬಂಧಕ ಕಂಡುಹಿಡಿಯುವಿಕೆಯನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ. ಪರಿಶೀಲಿಸಲಾದ ವಿನಾಯಿತಿಗಳು
`config/quality/forgotten-sibling-allowlist.json` ನಲ್ಲಿ ಇರುತ್ತವೆ. ಪ್ರತಿಯೊಂದು ನಮೂದು ಗ್ರಾಹಕ ಮತ್ತು
ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆಯನ್ನು ಹೆಸರಿಸಬೇಕು, ನಿರ್ದಿಷ್ಟ ತಾರ್ಕಿಕ ಕಾರಣವನ್ನು ನೀಡಬೇಕು ಮತ್ತು GitHub ಇಶ್ಯೂ ಅಥವಾ
ಪುಲ್ ರಿಕ್ವೆಸ್ಟ್ಗೆ ಲಿಂಕ್ ಮಾಡಬೇಕು. ದೋಷಪೂರಿತ ನಮೂದುಗಳು ಮುಚ್ಚಿದ ಸ್ಥಿತಿಯಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ.
ಅಳಿಸಲಾದ ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆಯನ್ನು ಅಥವಾ `.skip`/`.todo` ಸೇರಿಸುವ ಡಿಫ್ ಅನ್ನು ವಿನಾಯಿತಿಗಳು
ನಿಗ್ರಹಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ; ಅಸರ್ಷನ್ ದುರ್ಬಲಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಇತರ ಮರೆಮಾಚುವಿಕೆಗಳು ಸ್ವತಂತ್ರವಾಗಿ ನಿರ್ಬಂಧಿಸುವ
`check:test-masking` ಗೇಟ್ನ ವ್ಯಾಪ್ತಿಯಲ್ಲಿಯೇ ಉಳಿಯುತ್ತವೆ.

#### `check-ui-value-drift` — ಹಳೆಯ-ಅನುವಾದದ ಗೇಟ್

ಇತರ ಗೇಟ್ಗಳು ರಚನಾತ್ಮಕವಾಗಿ ಗುರುತಿಸಲಾಗದ ಒಂದು i18n regression ಅನ್ನು ಇದು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ: ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯವನ್ನು
ಪುನಃ ಬರೆಯಲಾಗಿದ್ದರೂ _ಹಿಂದಿನ_ ಇಂಗ್ಲಿಷ್ನಿಂದ ಪಡೆದ ಅನುವಾದಗಳು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತವೆ; ಆದ್ದರಿಂದ
ಇಂಗ್ಲಿಷ್ ಅಲ್ಲದ ಭಾಷೆಯ ಬಳಕೆದಾರರು ಖಚಿತ ಧಾಟಿಯಲ್ಲಿರುವ, ಆದರೆ ಈಗ ತಪ್ಪಾಗಿರುವ ಪಠ್ಯವನ್ನೇ ಓದುತ್ತಿರುತ್ತಾರೆ.

ಇದು ನಿಜವಾಗಿಯೂ ಬಿಡುಗಡೆಗೊಂಡಿತ್ತು. Antigravity login helper ಸೇರಿಸಿದಾಗ (#5203)
`oauthModal.googleOAuthWarning` ಅನ್ನು ಪುನಃ ಬರೆಯಲಾಯಿತು; **43 locale ಗಳಲ್ಲಿ 39** ರಲ್ಲಿ ಆಪರೇಟರ್ಗಳಿಗೆ "ಸಂಪೂರ್ಣ
URL ಅನ್ನು ನಕಲಿಸಿ ಮತ್ತು ಕೆಳಗೆ ಅಂಟಿಸಿ" ಎಂದು ಹೇಳುವ ಪಠ್ಯವೇ ಉಳಿದಿತ್ತು — ಆ ಪೂರೈಕೆದಾರರಿಗೆ ಪೂರ್ಣಗೊಳಿಸಲಾಗದ flow. ಇದು
#8463 ವರೆಗೆ ಗಮನಕ್ಕೆ ಬರಲಿಲ್ಲ, ಏಕೆಂದರೆ:

- `sync-ui-keys` **ಇಲ್ಲದಿರುವ** key ಗಳನ್ನು ಮಾತ್ರ backfill ಮಾಡುತ್ತದೆ, **ಹಳೆಯದಾದವುಗಳನ್ನು** ಎಂದಿಗೂ ಮಾಡುವುದಿಲ್ಲ;
- `check-ui-keys-coverage` key _ಇರುವಿಕೆಯನ್ನು_ ಎಣಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಹಳೆಯ ಅನುವಾದವನ್ನೂ ಒಳಗೊಂಡಿದೆ ಎಂದು ಪರಿಗಣಿಸುತ್ತದೆ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` documentation mirror ಗಳನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ —
  ಅದು `src/i18n/messages/*.json` ಅನ್ನು ಎಂದಿಗೂ ಓದುವುದಿಲ್ಲ. 2026-09 re-sync ನಿಂದ `docs-sync-strict` ಕೆಲಸದಲ್ಲಿ
  ತಡೆಯಲಾಗುತ್ತಿದೆ: ಮೂಲ doc ಅನ್ನು ಸಂಪಾದಿಸಿ → `npm run i18n:run -- --files=<doc>` (ವಿಭಾಗ-ಮಟ್ಟದ, ಕಡಿಮೆ ವೆಚ್ಚದ).

**ವ್ಯತ್ಯಾಸ-ಅರಿವುಳ್ಳದ್ದು, ಮೂಲಮಾನ-ಆಧಾರಿತವಲ್ಲ.** ಇದು ವಿಲೀನ ಮೂಲದಲ್ಲಿರುವ `en.json` ಅನ್ನು
ಕಾರ್ಯನಿರತ ಟ್ರೀಯೊಂದಿಗೆ ಹೋಲಿಸುತ್ತದೆ; ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯ ಬದಲಾಗಿರುವ ಪ್ರತಿಯೊಂದು ಕೀಲಿಗೆ, ಇನ್ನೂ
ಬದಲಾಗದ ಅನುವಾದವನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಲೊಕೇಲ್ ಹಳತಾಗಿದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
**ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಋಣವನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ** — ದೀರ್ಘಕಾಲದಿಂದ ಇರುವ ಅನುವಾದವು ಯಾವ ಹಳೆಯ
ಇಂಗ್ಲಿಷ್ನಿಂದ ಬಂದಿದೆ ಎಂಬುದನ್ನು ವ್ಯತ್ಯಾಸದಿಂದ ಕಂಡುಹಿಡಿಯಲಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಗೇಟ್ ಪ್ರಸ್ತುತ ಬದಲಾವಣೆಯು
ಸ್ಪರ್ಶಿಸುವುದನ್ನು ಮಾತ್ರ ನಿರ್ಣಯಿಸುತ್ತದೆ. ಪರ್ಯಾಯವು (ಪ್ರತಿ-ಕೀಲಿಯ ಹ್ಯಾಶ್ ಮೂಲಮಾನ) ~600 KB ರಚಿಸಲಾದ
ಫೈಲ್ನ ವೆಚ್ಚವನ್ನು ಉಂಟುಮಾಡುತ್ತದೆ, ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅತಿದೊಡ್ಡ ಮೂಲಮಾನಕ್ಕಿಂತ 3× ದೊಡ್ಡದಾಗಿದ್ದು, ಪ್ರತಿ i18n PRನಲ್ಲಿ ಬದಲಾಗುತ್ತಿರುತ್ತದೆ.

ಇದನ್ನು ಪೂರೈಸಲು ಎರಡು ಮಾರ್ಗಗಳಿವೆ:

1. ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಅನುವಾದಗಳನ್ನು ನವೀಕರಿಸಿ, ಅಥವಾ
2. ಅವುಗಳನ್ನು `__MISSING__:<new english>` ಗೆ ಹೊಂದಿಸಿ — ಆಗ ರನ್ಟೈಮ್ ಸರಿಪಡಿಸಿದ ಇಂಗ್ಲಿಷ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ಮತ್ತು ಕೀಲಿಯು ಅನುವಾದದ ಸರತಿಗೆ ಸೇರುತ್ತದೆ.

ಸ್ಟ್ರಿಂಗ್ನ **ಅರ್ಥ** ಬದಲಾಗಿದ್ದರೆ, **ಕೀಲಿಯನ್ನು ಮರುಹೆಸರಿಸುವುದಕ್ಕೆ** ಆದ್ಯತೆ ನೀಡಿ: ಹೊಸ ಕೀಲಿಯು
ಹಳತಾದ ಅನುವಾದವನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. #8463 ಬಳಸಿದ ಮಾದರಿ ಇದೇ ಆಗಿದೆ.

- **ಸಲಹಾತ್ಮಕ** — ಸ್ಥಿರಗೊಳಿಸಿದ ಬೇಸ್ಲೈನ್ಗೆ ಹೋಲಿಸಿದ ಜಾಗತಿಕ ಒಟ್ಟು. ಆನುವಂಶಿಕ ಡ್ರಿಫ್ಟ್ ನಿರಪರಾಧ PR ಅನ್ನು
  ಎಂದಿಗೂ ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ; ಬಿಡುಗಡೆ ಹೊಂದಾಣಿಕೆಯ ಸಮಯದಲ್ಲಿ ಡ್ರಿಫ್ಟ್ ಅನ್ನು ಮರು-ಸ್ಥಿರಗೊಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
  ಹೆಡ್ರೂಮ್ ಜಾಬ್ ಅದನ್ನು ಮೇಲ್ವಿಚಾರಣೆ ಮಾಡುತ್ತದೆ.

`check:file-size` ತನ್ನದೇ ನಿಯಮಗಳ ಪ್ರಕಾರ ಬೇಸ್ ರೆಫ್ ಅನ್ನು ಬಳಸುತ್ತದೆ
(`scripts/check/check-file-size.mjs`, #8522): ಇದು ಟ್ರೀಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು ಸೋರ್ಸ್ ಮತ್ತು ಟೆಸ್ಟ್ ಫೈಲ್ ಅನ್ನು
ಪರಿಶೀಲಿಸುತ್ತದೆ, `git show` ಮೂಲಕ PR ಬೇಸ್ನಲ್ಲಿನ ಪ್ರತಿಯೊಂದರ ಸಾಲಿನ ಎಣಿಕೆಯನ್ನು ಓದುತ್ತದೆ ಮತ್ತು ಫೈಲ್ ತನ್ನ
ಬೇಸ್ಲೈನ್ ಗರಿಷ್ಠ ಮಿತಿ (`frozen` / `testFrozen`, ಅಥವಾ ಬೇಸ್ಲೈನ್ನ ಹೊರಗಿನ ಫೈಲ್ಗಾಗಿ `cap` / `testCap`)
ಮತ್ತು ಅದರ ಬೇಸ್ ಗಾತ್ರ — ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದಾದ ಮೌಲ್ಯವನ್ನು ಮೀರಿದಾಗ ಮಾತ್ರ ಅದನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ.
ಆದ್ದರಿಂದ ಬೇಸ್ನಲ್ಲಿ ಈಗಾಗಲೇ ಡ್ರಿಫ್ಟ್ ಆಗಿರುವ ಫೈಲ್ ನಿರಪರಾಧ PR ಅನ್ನು ಎಂದಿಗೂ ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ.

`check:boundary:ratchet` ತನ್ನ ಏಕೈಕ ಸಂಖ್ಯೆಗೆ ಅದೇ ನಿಯಮವನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ಈವೆಂಟ್ಗಳಲ್ಲಿ
`quality.yml` ಫಾಸ್ಟ್-ಗೇಟ್ಗಳು ಮತ್ತು `ci.yml` lint ಜಾಬ್ ಎರಡೂ PR ಬೇಸ್ SHA ಅನ್ನು ರವಾನಿಸುತ್ತವೆ, ಬೇಸ್ ಕಮಿಟ್ ಅನ್ನು
`git archive` ಎಕ್ಸ್ಪೋರ್ಟ್ನಿಂದ ಅಳೆಯಲಾಗುತ್ತದೆ, ಮತ್ತು ಅದರ `open-sse → src` ಎಡ್ಜ್
ಎಣಿಕೆಯು `metrics.boundaryOpenSseToSrc` ಹಾಗೂ ಬೇಸ್ನಲ್ಲಿನ ಎಣಿಕೆ—ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದಾದ ಮೌಲ್ಯವನ್ನು ಮೀರಿದಾಗ ಮಾತ್ರ PR ವಿಫಲವಾಗುತ್ತದೆ. ಮಿತಿಗಿಂತ
ಹೆಚ್ಚಿರುವ ಬೇಸ್ ಡ್ರಿಫ್ಟ್ ಅನ್ನು (`base drift herdado`) ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಅದರಿಂದ ದೋಷವಿಲ್ಲದ PR ಎಂದಿಗೂ ವಿಫಲವಾಗುವುದಿಲ್ಲ; push → main
ಸಂಪೂರ್ಣ ಮಿತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಮತ್ತು ಪರಿಹರಿಸಲಾಗದ ಬೇಸ್ SHA ಎಚ್ಚರಿಕೆಯೊಂದಿಗೆ ಅದನ್ನೇ ಪರ್ಯಾಯವಾಗಿ ಬಳಸುತ್ತದೆ.

`workflow_dispatch` ರನ್ಗಳು, release-green ಸ್ವೀಪ್ ಮತ್ತು ರಾತ್ರಿಯ headroom ಜಾಬ್ಗೆ PR ಬೇಸ್
ಇರುವುದಿಲ್ಲ ಮತ್ತು ಅವು ಸಂಪೂರ್ಣ (ಜಾಗತಿಕ) ಹೋಲಿಕೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಕವರೇಜ್, ಡುಪ್ಲಿಕೇಶನ್ ಮತ್ತು type-coverage ಸದ್ಯಕ್ಕೆ ಜಾಗತಿಕವಾಗಿಯೇ
ಉಳಿಯುತ್ತವೆ (ಅವುಗಳ ಪರಿಕರಗಳು ಪ್ರತಿ-ಫೈಲ್ diff ಅನ್ನು ಕಡಿಮೆ ವೆಚ್ಚದಲ್ಲಿ ಉತ್ಪಾದಿಸುವುದಿಲ್ಲ) — ಇವುಗಳಿಗೂ ಇದೇ ವಿಧಾನವನ್ನು ಅನ್ವಯಿಸಬಹುದು.

**v4.0 ನಲ್ಲಿ ಹಂತವನ್ನು ಮುಕ್ತಾಯಗೊಳಿಸುವುದು (LTS = ಹಿಂದಿಗಿಂತ ಹೆಚ್ಚು ಕಟ್ಟುನಿಟ್ಟು, "back to normal" ಅಲ್ಲ)**

1. ಶುದ್ಧ `release/v4.0.0` ತುದಿಯಲ್ಲಿ: ದಾಖಲಿಗಾಗಿ `npm run quality:headroom --json`, ನಂತರ
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ಪ್ರತಿ typecheck ಗೇಟ್ನ
   `--update` — ಪ್ರತಿಯೊಂದು ಬೇಸ್ಲೈನ್ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕೆ ಇಳಿಯುತ್ತದೆ.
2. `quality-baseline.json` ನಿಂದ `_policy` ಅನ್ನು ಅಳಿಸಿ (`--require-tighten` ಮತ್ತು ರಾತ್ರಿಯ
   ಬ್ಯಾಂಕಿಂಗ್ ಅನ್ನು ಮರುಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ), `check-openapi-coverage.mjs` ನಲ್ಲಿ `THRESHOLD = 36` (ಅಥವಾ ಹೆಚ್ಚಿನದಕ್ಕೆ) ಮರುಸ್ಥಾಪಿಸಿ.
3. ಮಾಡ್ಯುಲರೈಸೇಶನ್ ಫಲ ನೀಡಿದ ಕಡೆಗಳಲ್ಲಿ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕಿಂತಲೂ ಹೆಚ್ಚು ಕಟ್ಟುನಿಟ್ಟುಗೊಳಿಸಿ: file-size `cap` ಅನ್ನು ಮತ್ತೆ 1000
   (ಅಥವಾ 800) ಗೆ, ಕವರೇಜ್ ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು +5 ಗೆ, ಮಾಡ್ಯುಲರೈಸ್ ಮಾಡಿದ ಪ್ಯಾಕೇಜ್ಗಳಿಗೆ dead exports ಅನ್ನು 0 ಗೆ ಹೊಂದಿಸಿ.

## ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ (`quality-baseline.json`)

ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ಅನ್ನು ಓದಿ,
ಹೊಸದಾಗಿ ಸಂಗ್ರಹಿಸಲಾದ `quality-metrics.json` ಜೊತೆ ಹೋಲಿಸುತ್ತದೆ. ಯಾವುದೇ ಮೆಟ್ರಿಕ್ ಅದರ ಎಪ್ಸಿಲಾನ್ಗಿಂತ
ಹೆಚ್ಚು ಹಿಂಜರಿದರೆ, ಬಿಲ್ಡ್ ವಿಫಲವಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿರುವ ಮೆಟ್ರಿಕ್ಗಳು:

| ಮೆಟ್ರಿಕ್              | ದಿಕ್ಕು | ಅರ್ಥ                                  |
| --------------------- | ------ | ------------------------------------- |
| `eslintWarnings`      | `down` | ESLint ಎಚ್ಚರಿಕೆಗಳ ಸಂಖ್ಯೆ ಹೆಚ್ಚಾಗಬಾರದು |
| `coverage.statements` | `up`   | ಸ್ಟೇಟ್ಮೆಂಟ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು      |
| `coverage.lines`      | `up`   | ಲೈನ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು             |
| `coverage.functions`  | `up`   | ಫಂಕ್ಷನ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು          |
| `coverage.branches`   | `up`   | ಬ್ರಾಂಚ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು          |

ನೈಜ ಸುಧಾರಣೆಯ ನಂತರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ನವೀಕರಿಸಲು:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` ಫ್ಲ್ಯಾಗ್ ಪ್ರಸ್ತುತ ಅಳೆಯಲಾದ ಮೌಲ್ಯಗಳನ್ನು `quality-baseline.json` ಗೆ ಬರೆಯುತ್ತದೆ.
ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸಿದ ಬದಲಾವಣೆಯ ಜೊತೆಯಲ್ಲೇ ಈ ಫೈಲ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ. ಬೇಸ್ಲೈನ್ ಅನ್ನು
ನವೀಕರಿಸದೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸುವ PR ಅನ್ನು `--require-tighten` ಪತ್ತೆಹಚ್ಚುತ್ತದೆ (ಹಂತ 6A.5,
ಅನುಷ್ಠಾನ ಬಾಕಿಯಿದೆ).

### CodeQL ರ್ಯಾಚೆಟ್: ರಿಫ್ರೆಶ್ ಆವರ್ತನೆ ಮತ್ತು ಹಸ್ತಚಾಲಿತ ಟ್ರಿಗರ್

`check:codeql-ratchet` **ರೆಪೊ ಸ್ಥಿತಿಯನ್ನು ಓದುತ್ತದೆ; ಅದನ್ನು ವೇಳಾಪಟ್ಟಿಯ ಪ್ರಕಾರ ರಿಫ್ರೆಶ್ ಮಾಡಲಾಗುತ್ತದೆ — ಪ್ರತಿ PR ಗೆ ಅಲ್ಲ.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ವರದಿ ಮಾಡುವ
`state: configured`, `schedule: weekly` ಎಂಬುದು GitHub ನ ಡೀಫಾಲ್ಟ್-ಸೆಟಪ್ ಸ್ಕ್ಯಾನ್ ಆಗಿದ್ದು,
ಪ್ರತಿ ಪುಶ್ಗೆ ನಡೆಯುವ ವಿಶ್ಲೇಷಣೆಯಲ್ಲ. ಪರಿಣಾಮ: ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸುವ PR ವಿಲೀನಗೊಂಡ ನಂತರವೂ,
ಮುಂದಿನ ನಿಗದಿತ ಸ್ಕ್ಯಾನ್ ನಡೆಯುವವರೆಗೆ ರ್ಯಾಚೆಟ್ ಹಳೆಯ, ಹೆಚ್ಚಿನ ಸಂಖ್ಯೆಯನ್ನೇ ಓದುತ್ತಿರುತ್ತದೆ —
ಆದ್ದರಿಂದ ಸ್ಕ್ಯಾನ್ ನವೀಕರಿಸುವವರೆಗೆ, ಸರಿಪಡಿಸಿದ PR ನ ಸ್ವಂತ ಫಾಲೋ-ಅಪ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಪ್ರತಿಯೊಂದು
ತೆರೆದ PR ನಲ್ಲಿಯೂ ಅದು ಹಿಂಜರಿತವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

**ಹಸ್ತಚಾಲಿತ ರಿಫ್ರೆಶ್**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ವಿಶ್ಲೇಷಣೆಯನ್ನು
ಮತ್ತೆ ಚಲಾಯಿಸಿ, ಕೆಲವೇ ನಿಮಿಷಗಳಲ್ಲಿ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಮರುಪ್ರಕಟಿಸುತ್ತದೆ. ಮೊದಲು `.github/workflows/codeql.yml`
ಓದಿ — GitHub ನ **"default setup" ಜೊತೆಗೆ ಅದು ಸಂಘರ್ಷಿಸುವುದರಿಂದಲೇ** ಇದು `workflow_dispatch`-ಗೆ ಮಾತ್ರ
ಸೀಮಿತವಾಗಿದೆ ಎಂದು ಅದರ ಹೆಡರ್ ವಿವರಿಸುತ್ತದೆ (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). `push`/`pull_request`/
`schedule` ಟ್ರಿಗರ್ಗಳನ್ನು ಮರುಸ್ಥಾಪಿಸಲು ಮೊದಲು **ಮಾಲೀಕರ ಕ್ರಮ** ಅಗತ್ಯ: Settings → Code security →
CodeQL: Default → Advanced. ಆ ಬದಲಾವಣೆ ಮಾಡದೆ `schedule:` ಟ್ರಿಗರ್ ಸೇರಿಸಬೇಡಿ — ಅದು
ವಿಫಲಗೊಳ್ಳುವ ರನ್ಗಳನ್ನು ಮಾತ್ರ ಉಂಟುಮಾಡುತ್ತದೆ.

**ಸಂಖ್ಯೆ ಕಡಿಮೆಯಾದ ನಂತರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ಬಿಗಿಗೊಳಿಸಿ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ಹೊಸದಾಗಿ ಅಳೆಯಲಾದ ಸಂಖ್ಯೆಯನ್ನು `quality-baseline.json` →
`metrics.codeqlAlerts.value` ಗೆ ಬರೆಯುತ್ತದೆ; ಹೀಗಾಗಿ ಹಳೆಯ ಗರಿಷ್ಠ ಮಿತಿಯವರೆಗೆ ಮತ್ತೆ ಹಿಂಜರಿಯುವುದನ್ನು
ರ್ಯಾಚೆಟ್ ಮೌನವಾಗಿ ಅನುಮತಿಸುವುದಿಲ್ಲ. ಕಾರ್ಯನಿರ್ವಹಿತ ಉದಾಹರಣೆ (2026-09-02/03): PR #12502 ನೈಜವಾದ
7 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸಿತು (ಅಳೆಯಲಾದ ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳು 13 → 6); ಅದಕ್ಕೆ ಹೊಂದುವಂತೆ PR #12530
ಸ್ಥಿರಗೊಳಿಸಲಾದ ಬೇಸ್ಲೈನ್ ಅನ್ನು 11 → 6 ಗೆ ಬಿಗಿಗೊಳಿಸಿತು; ನಂತರ ಉಳಿದ 6 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಪ್ರತಿಯೊಂದು
ಎಚ್ಚರಿಕೆಗೆ ಪ್ರತ್ಯೇಕ ಸಮರ್ಥನೆ ನೀಡಿ ವಜಾಗೊಳಿಸಿ, ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳ ಸಂಖ್ಯೆಯನ್ನು 0 ಗೆ ಇಳಿಸಲಾಯಿತು.

**ವಜಾಗೊಳಿಸುವಿಕೆಗಳು ಆಪರೇಟರ್ನ ನಿರ್ಧಾರ (ಕಠಿಣ ನಿಯಮ #14)** — ವಜಾಗೊಳಿಸುವಿಕೆಯ ಕಾಮೆಂಟ್ನಲ್ಲಿ

`false positive` (ಪೂರ್ವನಿದರ್ಶನ: `docs/security/ERROR_SANITIZATION.md`).

## ಪರೀಕ್ಷಾ ಮರುಪ್ರಯತ್ನ ನೀತಿ (WS5.4, v3.8.49)

ಮರುಪ್ರಯತ್ನವು ಪ್ರತಿ ರನ್ನರ್ಗೆ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತದೆ, ಎಂದಿಗೂ ಜಾಗತಿಕವಾಗಿ ಎಲ್ಲಕ್ಕೂ ಅನ್ವಯಿಸುವುದಿಲ್ಲ — ಎಲ್ಲಕ್ಕೂ ಅನ್ವಯಿಸುವ ಮರುಪ್ರಯತ್ನವು ನೈಜ ರಿಗ್ರೆಷನ್ಗಳನ್ನು
ಕಾಣದಂತಾಗುವ ಫ್ಲೇಕ್ಗಳಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ:

| ರನ್ನರ್           | ನೀತಿ                                                                                                                                                         | ಕಾರಣ                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Playwright (e2e) | CI ನಲ್ಲಿ ಮಾತ್ರ `retries: 1`, ಜೊತೆಗೆ `trace: on-first-retry`                                                                                                  | ಬ್ರೌಸರ್/ನೆಟ್ವರ್ಕ್ ಸಮಯವು ನಿಜವಾಗಿಯೂ ನಿರ್ಧಾರಾತ್ಮಕವಲ್ಲ; ಟ್ರೇಸ್ನೊಂದಿಗೆ ಒಂದು ಮರುಪ್ರಯತ್ನವು ಫ್ಲೇಕ್ ಅನ್ನು ರೋಗನಿರ್ಣಯ ಮಾಡಬಹುದಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ |

("ಈಗಲೇ ಸರಿಪಡಿಸಿ" ಮಿತಿ), ಪ್ರತಿ ಪೈಪ್ಲೈನ್ಗೆ ≥95% ಉತ್ತೀರ್ಣ ದರ. ಇವು ಉದ್ಯಮದ ಉಲ್ಲೇಖ ಮೌಲ್ಯಗಳು —
ನಮ್ಮ ಸ್ವಂತ ಮಾಪನಗಳಿಗೆ ಅನುಗುಣವಾಗಿ ಮರುಮಾಪನಾಂಕ ಮಾಡಿ.

## ರಿಲೀಸ್-ಮಟ್ಟದ ರ್ಯಾಚೆಟ್ ಡ್ರಿಫ್ಟ್ (WS5.5, v3.8.49)

PURE ರಿಲೀಸ್ ಟಿಪ್ನಲ್ಲಿ ಒಂದು ರ್ಯಾಚೆಟ್ (ಫೈಲ್ ಗಾತ್ರ, ಸಂಕೀರ್ಣತೆ, eslint ಎಚ್ಚರಿಕೆಗಳು) ಹಿಮ್ಮೆಟ್ಟಿದಾಗ —
ಅಂದರೆ, ಮರ್ಜ್ಗಳ ಸಂಯೋಜನೆಯು ಅದನ್ನು ಹಿಮ್ಮೆಟ್ಟಿಸಿದೆ ಮತ್ತು ಯಾವುದೇ ಒಂದು PR ತನ್ನದೇ ಬ್ರಾಂಚ್ನಲ್ಲಿ ಆ
ರಿಗ್ರೆಷನ್ ಅನ್ನು ಪುನರುತ್ಪಾದಿಸುವುದಿಲ್ಲವಾದರೆ — ಅದನ್ನು ಸರಿಪಡಿಸುವ ಹೊಣೆ **ರಿಲೀಸ್ ಕ್ಯಾಪ್ಟನ್ಗೆ, ಒಮ್ಮೆ ಮಾತ್ರ,
ರಿಲೀಸ್ ಬ್ರಾಂಚ್ನಲ್ಲಿ** ಸೇರಿದೆ: ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್/ರಿಫ್ಯಾಕ್ಟರ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ; ದಾಖಲಿಸಲಾದ
ಸಮರ್ಥನೆ ನಮೂದಿನೊಂದಿಗೆ ಮಾತ್ರ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಿ. ಸಂಯೋಜನೆಯಿಂದಾದ ಡ್ರಿಫ್ಟ್ ಅನ್ನು ಕೊಡುಗೆದಾರರ PR ಮೇಲೆ ಎಂದಿಗೂ
ಹೊರಿಸಬೇಡಿ ಮತ್ತು ಪ್ರತಿ-PR ಗೆ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಬೇಡಿ (ಅದು ನೈಜ ರಿಗ್ರೆಷನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ). ಮೊದಲು ವ್ಯತ್ಯಾಸವನ್ನು ಗುರುತಿಸಿ:
ನಿಮ್ಮ PR ಅದಕ್ಕೆ ಕಾರಣವೆಂದು ಊಹಿಸುವ ಮೊದಲು ಪ್ರೋಬ್ ವರ್ಕ್ಟ್ರೀಯಲ್ಲಿ ಶುದ್ಧ ಟಿಪ್ ವಿರುದ್ಧದ ಕೆಂಪು ಸ್ಥಿತಿಯನ್ನು ಪುನರುತ್ಪಾದಿಸಿ.

## ರ್ಯಾಚೆಟ್ ಇಳಿಕೆಗಳನ್ನು ಬ್ಯಾಂಕ್ ಮಾಡುವುದು — ಕೆಳಮುಖ ದಿಕ್ಕು (#8584)

ರ್ಯಾಚೆಟ್ ಅರ್ಧದಷ್ಟು ಮಾತ್ರ ಸ್ವಯಂಚಾಲಿತವಾಗಿದೆ, ಮತ್ತು ಅದು ತಪ್ಪಾದ ಅರ್ಧವಾಗಿದೆ. ಮಿತಿಯನ್ನು **ಹೆಚ್ಚಿಸುವುದು**
ಹತ್ತು ಸೆಕೆಂಡ್ ತೆಗೆದುಕೊಳ್ಳುವ ಕೈಯಾರೆ JSON ತಿದ್ದುಪಡಿಯಾಗಿದ್ದು, ಕೆಂಪಾಗಿರುವ PR ಅನ್ನು ಅನ್ಬ್ಲಾಕ್ ಮಾಡುವ ಅತ್ಯಂತ ವೇಗದ ವಿಧಾನವಾಗಿದೆ.
ಮಿತಿಯನ್ನು **ಕಡಿಮೆ ಮಾಡಲು** ಯಾರಾದರೂ `--update` ಚಲಾಯಿಸಿ ಫಲಿತಾಂಶವನ್ನು ಕಮಿಟ್ ಮಾಡಬೇಕು — ಮತ್ತು
`bank-ratchet-shrinks` ಜಾಬ್ ಬರುವವರೆಗೂ, ಯಾವುದೇ ವರ್ಕ್ಫ್ಲೋ ಅದನ್ನು ಚಲಾಯಿಸುತ್ತಿರಲಿಲ್ಲ. ಮಾಪನ ಮಾಡಿದ ಪರಿಣಾಮ
(2026-07-25): ಈಗಾಗಲೇ 800-ಸಾಲಿನ ಹೊಸ-ಫೈಲ್ ಮಿತಿಯಲ್ಲಿ ಅಥವಾ ಅದಕ್ಕಿಂತ ಕೆಳಗಿರುವ 18 ಸ್ಥಗಿತಗೊಳಿಸಿದ ಫೈಲ್ಗಳು, ಅತ್ಯಂತ ಕೆಟ್ಟದ್ದು
132× (`src/shared/validation/schemas.ts`, 2,523 ಮಿತಿಯನ್ನು ಹೊಂದಿರುವ 19 ಸಾಲುಗಳು); ಸಂಕೀರ್ಣತೆಯ ಗರಿಷ್ಠ ಮಿತಿ
~37 ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸುವ ಟಿಪ್ಪಣಿಗಳಾದ್ಯಂತ `1794 → 2169` ಕ್ಕೆ ಏರಿತು, ನಿಖರವಾಗಿ ಒಂದೇ ಇಳಿಕೆಯೊಂದಿಗೆ
(−1); ಮತ್ತು "ಮುಂದಿನ ಚಕ್ರದಲ್ಲಿ `--update` ಮೂಲಕ ಬಿಗಿಗೊಳಿಸಿ" ಎಂದು 31 ಬಾರಿ ಬರೆದು, ಒಮ್ಮೆ ಮಾತ್ರ ಪಾಲಿಸಲಾಯಿತು.
ಅದಕ್ಕೆ ಕಾರಣವಾದ ಕೋಡ್ಗಿಂತಲೂ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯುವ ಮಿತಿಯು, ಪೂರ್ಣಗೊಂಡ ಪ್ರತಿಯೊಂದು ವಿಭಜನೆಯನ್ನು ಆ ಫೈಲ್ ಅನ್ನು ಮುಂದಿನ ಬಾರಿ
ತಿದ್ದುಪಡಿ ಮಾಡುವವರಿಗೆ ಬೆಳವಣಿಗೆಯ ಅನುಮತಿಯಾಗಿ ಮೌನವಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ.

### ಸುರಕ್ಷತಾ ಪರಿಶೀಲಕ

ಜಾಬ್ ಮೇಲ್ವಿಚಾರಣೆಯಿಲ್ಲದೆ ಬೇಸ್ಲೈನ್ಗಳಿಗೆ ಬರೆಯುತ್ತದೆ, ಆದ್ದರಿಂದ `verify-ratchet-bank.mjs` ಅದನ್ನು
ಸ್ವೀಕಾರಾರ್ಹವಾಗಿಸುತ್ತದೆ. ಅದು `--update` ನಂತರದ ಟ್ರೀ ಅನ್ನು `HEAD` ವಿರುದ್ಧ diff ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು
ಬದಲಾವಣೆಯೂ ಕೆಳಗಿನವುಗಳಲ್ಲಿ ಒಂದಾಗಿರದಿದ್ದರೆ, **ಯಾವುದೇ ಕಮಿಟ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು ಜಾಬ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ**
— ಯಾವುದೇ PR ತೆರೆಯುವುದಿಲ್ಲ:

- `frozen` / `testFrozen` ಸಂಖ್ಯಾತ್ಮಕ ನಮೂದನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ** ಅಥವಾ **ತೆಗೆದುಹಾಕಲಾಗಿದೆ**
- `complexity-baseline.json` → `count` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**

ಬೇರಾವುದೇ ಬದಲಾವಣೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ: ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸುವುದು, ನಮೂದನ್ನು ಸೇರಿಸುವುದು, `cap`/`testCap` ಅನ್ನು ಬದಲಿಸುವುದು ಅಥವಾ
`_rebaseline_*` ಟಿಪ್ಪಣಿಯನ್ನು ಅಳಿಸುವುದು/ಮರುಬರೆಯುವುದು (ಪ್ರತಿ ಗರಿಷ್ಠ ಮಿತಿ ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ ಎಂಬುದಕ್ಕೆ ಆ ಟಿಪ್ಪಣಿಗಳು ಆಡಿಟ್ ದಾಖಲೆಯಾಗಿದ್ದು,
ಫೈಲ್ ನಮೂದುಗಳಂತೆಯೇ ಅದೇ `frozen` ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ).
ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಬಲ್ಲ ಬಾಟ್ ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಗಿಂತ ಖಂಡಿತವಾಗಿಯೂ ಕೆಟ್ಟದಾಗಿರುತ್ತದೆ. ರಿಗ್ರೆಷನ್
ಗಾರ್ಡ್: `tests/unit/verify-ratchet-bank.test.ts`.

ಜಾಬ್ ಎಂದಿಗೂ `release/*` ಗೆ push ಮಾಡುವುದಿಲ್ಲ — ಒಬ್ಬ ವ್ಯಕ್ತಿ PR ಅನ್ನು ಮರ್ಜ್ ಮಾಡುತ್ತಾರೆ, ಆದ್ದರಿಂದ ತಪ್ಪಾದ ಮಾಪನವು
ಪರಿಶೀಲಿಸದೆ ಸೇರಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಅನುಮತಿ ಪಟ್ಟಿ ನೀತಿ

ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉಲ್ಲಂಘನೆಗಳಿಂದ ವಿಫಲವಾಗಬಾರದ ಪ್ರತಿಯೊಂದು ಗೇಟ್ ಸ್ಥಿರಗೊಳಿಸಲಾದ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸುತ್ತದೆ
(ಉದಾ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). ನೀತಿ ಹೀಗಿದೆ:

**ಮೂಲ ಕಾರಣವನ್ನು ಸರಿಪಡಿಸಿ; ಉಲ್ಲಂಘನೆಯು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದು, ಅದನ್ನು ಅದೇ PRನಲ್ಲಿ
ಸರಿಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ ಮಾತ್ರ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸಿ.**

ಅನುಮತಿ ಪಟ್ಟಿಗೆ ನಮೂದನ್ನು ಸೇರಿಸುವಾಗ:

1. ಸಮರ್ಥನೆಯೊಂದಿಗೆ ಒಂದು ಕಾಮೆಂಟ್ ಸೇರಿಸಿ.
2. ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯನ್ನು ಉಲ್ಲೇಖಿಸಿ (ಉದಾ., `// #3498 — ಹಂತ 2ರ ವೈಶಿಷ್ಟ್ಯ, ಇನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸಿಲ್ಲ`).
3. ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸುವ ಅದೇ PRನಲ್ಲಿ ನಮೂದನ್ನು ತೆಗೆದುಹಾಕಿ — ಇನ್ನು ಮುಂದೆ ಸಕ್ರಿಯ ಉಲ್ಲಂಘನೆಯನ್ನು
   ನಿಗ್ರಹಿಸದ ಹಳತಾದ ನಮೂದು ಸ್ವತಃ ಒಂದು ದೋಷವಾಗಿದೆ (ಅನುಷ್ಠಾನಗೊಂಡ ನಂತರ 6A.3 stale-enforcement,
   ಅನಾಥ ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದಿನ ಕಾರಣದಿಂದ ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ).

ಪರೀಕ್ಷೆಗಳು ವೇಗವಾಗಿ ಪಾಸ್ ಆಗುವಂತೆ ಮಾಡಲು ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದುಗಳನ್ನು ಸೇರಿಸ**ಬೇಡಿ**. ಬೆಳೆಯುತ್ತಿರುವ
ಅನುಮತಿ ಪಟ್ಟಿಯೊಂದಿಗಿನ ಹಸಿರು ಗೇಟ್ ಗುಣಮಟ್ಟದ ಕುರಿತು ತಪ್ಪು ಭರವಸೆಯನ್ನು ನೀಡುತ್ತದೆ.

### ನಿಮ್ಮ PRನಲ್ಲಿ ಗೇಟ್ ವಿಫಲವಾದಾಗ

1. **ಗೇಟ್ ಔಟ್ಪುಟ್ ಅನ್ನು ಎಚ್ಚರಿಕೆಯಿಂದ ಓದಿ** — ಯಾವ ಫೈಲ್ ಅಥವಾ ಸಂಕೇತವು ನಿಯಮವನ್ನು ಉಲ್ಲಂಘಿಸಿದೆ
   ಎಂಬುದನ್ನು ಅದು ನಿಖರವಾಗಿ ತಿಳಿಸುತ್ತದೆ.
2. **ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸಿ** — ಬಹುತೇಕ ಗೇಟ್ಗಳು ನಿರ್ಣಾಯಕ ಫೈಲ್ಸಿಸ್ಟಮ್ ಪರಿಶೀಲನೆಗಳಾಗಿದ್ದು,
   ಕೋಡ್ ಸರಿಯಾದ ತಕ್ಷಣವೇ ಪಾಸ್ ಆಗುತ್ತವೆ.
3. **ಉಲ್ಲಂಘನೆಯು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದರೆ** (ಅಂದರೆ, ನೀವು ಅದನ್ನು ಪರಿಚಯಿಸಿಲ್ಲ, ಆದರೆ ಈಗ ಗೇಟ್
   ಅದನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ): ಸಮರ್ಥನೆಯ ಕಾಮೆಂಟ್ ಮತ್ತು ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯೊಂದಿಗೆ ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದನ್ನು ಸೇರಿಸಿ.
4. **ಗೇಟ್ ರ್ಯಾಚೆಟ್ ಆಗಿದ್ದರೆ** (ವ್ಯಾಪ್ತಿ, ESLint ಎಚ್ಚರಿಕೆಗಳು, ನಕಲು, ಸಂಕೀರ್ಣತೆ):
   ನಿಮ್ಮ ಬದಲಾವಣೆಯು ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹದಗೆಡಿಸಿದೆ. ಮೂಲ ಸಮಸ್ಯೆಯನ್ನು ಸರಿಪಡಿಸಿ ಅಥವಾ (ಅಪರೂಪವಾಗಿ) ಬದಲಾವಣೆಯು
   ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದ್ದು ಮೆಟ್ರಿಕ್ ಕುಸಿತವು ಸ್ವೀಕಾರಾರ್ಹವಾಗಿದ್ದರೆ `npm run quality:ratchet -- --update`
   ಅನ್ನು ಚಲಾಯಿಸಿ — ಆದರೆ PR ವಿವರಣೆಯಲ್ಲಿ ಕಾರಣವನ್ನು ದಾಖಲಿಸಿ.
5. **ಸಲಹಾತ್ಮಕ ಗೇಟ್ಗಳು** (`continue-on-error: true`) ಮಾಹಿತಿಗಾಗಿ ಮಾತ್ರ — ಅವು ವಿಲೀನವನ್ನು
   ತಡೆಯುವುದಿಲ್ಲ, ಆದರೆ CI ಸಾರಾಂಶದಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಆದರೂ ಅವುಗಳನ್ನು ಸರಿಪಡಿಸಿ.

## ಹೊಸ ಗೇಟ್ ಸೇರಿಸುವುದು

1. `scripts/check/check-<name>.mjs` (ಅಥವಾ `.ts`) ರಚಿಸಿ. ನೀತಿ ಗೇಟ್ಗಳು 0/1 ಸ್ಥಿತಿಯೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತವೆ.
   ರ್ಯಾಚೆಟ್-ಶೈಲಿಯ ಗೇಟ್ಗಳು `collect-metrics.mjs` ಮೂಲಕ `quality-metrics.json` ಗೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹೊರಸೂಸುತ್ತವೆ.
2. `package.json` ಗೆ `"check:<name>": "node scripts/check/check-<name>.mjs"` ಸೇರಿಸಿ.
3. ಸೂಕ್ತ ಜಾಬ್ ಅಡಿಯಲ್ಲಿ `.github/workflows/ci.yml` ನಲ್ಲಿ ಅದನ್ನು ಜೋಡಿಸಿ
   (ನೀತಿ → `lint` ಅಥವಾ `docs-sync-strict`; ರ್ಯಾಚೆಟ್ → `quality-gate`).
4. ಅದಕ್ಕೆ ಅನುಮತಿ ಪಟ್ಟಿ ಇದ್ದರೆ, ಹಳತಾದ ನಮೂದುಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪತ್ತೆಯಾಗುವಂತೆ
   `scripts/check/lib/allowlist.mjs` ನಿಂದ `reportStaleEntries()` ಅನ್ನು ಅನ್ವಯಿಸಿ.
5. ಗೇಟ್ನ ಪತ್ತೆ ತರ್ಕವನ್ನು ಒಳಗೊಂಡ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/build/` ನಲ್ಲಿ ಬರೆಯಿರಿ.
6. ಈ ಡಾಕ್ಯುಮೆಂಟ್ ಅನ್ನು ನವೀಕರಿಸಿ (ಸಂಬಂಧಿತ ಜಾಬ್ ಟೇಬಲ್ಗೆ ಒಂದು ಸಾಲನ್ನು ಸೇರಿಸಿ).

## ಏಜೆಂಟ್ ಉಪಕರಣಗಳು: LSP-in-the-loop (ಆಯ್ಕೆಯ ಮೇರೆಗೆ)

CI ಗೇಟ್ಗಳ ಜೊತೆಗೆ, OmniRoute ಒಂದು **ಆಯ್ಕೆಯ ಮೇರೆಗೆ ಬಳಸಬಹುದಾದ** `agent-lsp` ಸ್ಕ್ಯಾಫೋಲ್ಡ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
(ಪ್ರಾಜೆಕ್ಟ್-ಮಟ್ಟದ `.mcp.json`, Fase 7 Task 15). ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ಗಳಿಗೆ TypeScript ಭಾಷಾ ಸರ್ವರ್ ಅನ್ನು
ಒದಗಿಸಲು `.mcp.json` ರಚಿಸಿ, ಇದರಿಂದ ಅವು ಕೋಡ್ ಬರೆಯುವ **ಮೊದಲು** ಸಂಕೇತಗಳು /
ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಗಳನ್ನು ಪರಿಹರಿಸುತ್ತವೆ — ಮೂಲದಲ್ಲೇ "ಕಲ್ಪಿತ ಸಂಕೇತ" ದೋಷಗಳನ್ನು ಕಡಿತಗೊಳಿಸುವ
`typecheck:core` ಗೆ ಕಂಪೈಲ್-ಬಿಫೋರ್-ಕ್ಲೇಮ್ ಸಹಚರ. ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
ಸ್ವಯಂ-ಲೋಡ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ (MCP↔LSP ಬ್ರಿಡ್ಜ್ ಅನ್ನು ನೀವು ಆಯ್ಕೆಮಾಡಿ ಪರಿಶೀಲಿಸುತ್ತೀರಿ); ದೋಷಪೂರಿತ ನಮೂದು
ಕೇವಲ ಸಂಪರ್ಕ ದೋಷವನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸೆಷನ್ಗಳನ್ನು ಎಂದಿಗೂ ಸ್ಥಗಿತಗೊಳಿಸುವುದಿಲ್ಲ.

## ತರ್ಕಬದ್ಧಗೊಳಿಸುವಿಕೆ ಬಾಕಿಪಟ್ಟಿ (ROI ಪರಿಶೀಲನೆ — ಹಂತ 9 ಅಲೆ 3)

ಈ ಪಟ್ಟಿಯನ್ನು 2026-06-17 ರಂದು `ci.yml` ಜೊತೆಗೆ ಹೊಂದಾಣಿಕೆ ಮಾಡಲಾಗಿದೆ (ಹಿಂದಿನ ಆವೃತ್ತಿಯಲ್ಲಿ
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` ಬಿಟ್ಟುಹೋಗಿದ್ದವು). ಹೊಂದಾಣಿಕೆ ಮಾಡಿದ ಸಮೂಹದ ROI ಪರಿಶೀಲನೆಯು
ಕೆಳಗಿನ ತರ್ಕಬದ್ಧಗೊಳಿಸುವಿಕೆ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಗುರುತಿಸಿದೆ. **ವಿಲೀನಗಳು ಯಾಂತ್ರಿಕ CI
ಬದಲಾವಣೆಗಳಾಗಿವೆ; ತಿರುಗಿಸುವಿಕೆಗಳು/ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ನಿರ್ವಾಹಕರಿಗೆ ಮೀಸಲಾದ ನೀತಿ ನಿರ್ಧಾರಗಳಾಗಿವೆ.** ಕೆಳಗಿನ ಯಾವುದನ್ನೂ
ಇನ್ನೂ ಅನ್ವಯಿಸಲಾಗಿಲ್ಲ.

**ಮೇಲೆ ದಾಖಲಿಸದಿರುವವುಗಳೂ ಇವೆ** (ಸಲಹಾತ್ಮಕ, ಕಡಿಮೆ ಸಂಕೇತ): `docs-lint` ಜಾಬ್
(markdownlint + Vale, ಸಂಪೂರ್ಣ ಜಾಬ್ಗೆ `continue-on-error`) ಮತ್ತು ಸ್ವತಂತ್ರ ಸ್ಕ್ಯಾನರ್ ವರ್ಕ್ಫ್ಲೋಗಳಾದ
`semgrep.yml` / `codeql.yml` / `scorecard.yml`. `semgrepFindings: 0` ಎಂಬುದು
`quality-baseline.json` ನಲ್ಲಿದೆ, ಆದರೆ `ci.yml` ನಲ್ಲಿ ತಡೆಹಿಡಿಯುವ ರ್ಯಾಚೆಟ್ಗೆ ಜೋಡಿಸಲಾಗಿಲ್ಲ — ಈ ಮೆಟ್ರಿಕ್ ಪ್ರಸ್ತುತ
ಅನಾಥವಾಗಿದೆ.

### ವಿಲೀನ / ನಕಲು ನಿವಾರಣೆ (ಯಾಂತ್ರಿಕ, ಕಡಿಮೆ ಅಪಾಯ)

ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯನ್ನೂ 2026-06-17 ರಂದು ಲೈವ್ ಗೇಟ್ ಸ್ಥಿತಿಯ ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸಲಾಗಿದೆ (ನಂಬಿ, ಆದರೆ ಪರಿಶೀಲಿಸಿ);
ಹಲವಾರು "ಸ್ಪಷ್ಟ" ವಿಲೀನಗಳು ಸಾಲವನ್ನು ಮರೆಮಾಡಿರುವುದು ಕಂಡುಬಂದಿದ್ದು, ಅವು **ಸ್ವಚ್ಛ ಪರ್ಯಾಯಗಳಲ್ಲ**.

- **`check:docs-sync` ಎರಡು ಬಾರಿ ರನ್ ಆಗುತ್ತದೆ** — `lint` ಜಾಬ್ನಲ್ಲಿ ಸ್ವತಂತ್ರವಾಗಿ ಮತ್ತು `check:docs-all` (`docs-sync-strict`) ಒಳಗೆ ಮತ್ತೊಮ್ಮೆ, ಹಾಗೆಯೇ husky pre-commit hookನಲ್ಲಿಯೂ. ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** — ಸ್ವತಂತ್ರ `lint` ಆಹ್ವಾನವನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ.
- **CVE ಸ್ಕ್ಯಾನಿಂಗ್** — ❌ **ಸ್ವಚ್ಛ ವಿಲೀನವಲ್ಲ.** ಯಾವುದೇ high/critical CVE ಕಂಡುಬಂದರೆ `audit:deps` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; `check:vuln-ratchet` (osv) baselineಗೆ ಹೋಲಿಸಿದಾಗ _ಹಿಂಜರಿತ_ ಉಂಟಾದರೆ ಮಾತ್ರ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ (ಪ್ರಸ್ತುತ 1 MODERATE). ಅರ್ಥವ್ಯವಸ್ಥೆಗಳು ವಿಭಿನ್ನವಾಗಿವೆ — `audit:deps` ತೆಗೆದುಹಾಕಿದರೆ ಸಂಪೂರ್ಣ high/critical ಗೇಟ್ ಕಳೆದುಹೋಗುತ್ತದೆ. ಎರಡನ್ನೂ ಉಳಿಸಿ.
- **ಚಕ್ರ ಪತ್ತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (#15159 G-01/G-02). ಇಲ್ಲಿನ ಹಳೆಯ ಪಠ್ಯವು `check:cycles` ಅನ್ನು "ಹಸಿರು, ಆಯ್ದ" ಗೇಟ್ ಎಂದು ಕರೆದಿತ್ತು ಮತ್ತು `check:circular-deps` (dpdm) 91 ಚಕ್ರಗಳನ್ನು ವರದಿ ಮಾಡಿದ್ದರಿಂದ ಅದನ್ನು ತಡೆಹಿಡಿಯುವ ಗೇಟ್ ಆಗಿ ಉಳಿಸುವುದನ್ನು ಸಮರ್ಥಿಸಿತ್ತು. ಆ ಹಸಿರು ಸ್ಥಿತಿ **ತಪ್ಪು ಹಸಿರು** ಆಗಿತ್ತು: `check:cycles` 5 ಉಪಡೈರೆಕ್ಟರಿಗಳನ್ನು (450 ಫೈಲ್ಗಳು) ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತಿತ್ತು, ಸ್ಥಿರ `import|export … from` ಮಾತ್ರ ಹೊಂದಿಸುತ್ತಿತ್ತು ಮತ್ತು ಪ್ರತಿಯೊಂದು `@/` ಹಾಗೂ `@omniroute/open-sse/` ಸ್ಪೆಸಿಫೈಯರ್ ಅನ್ನು ಕೈಬಿಡುತ್ತಿತ್ತು; ಆದ್ದರಿಂದ ರೆಪೊದಲ್ಲಿ ಪ್ರಾಬಲ್ಯ ಹೊಂದಿದ್ದ dynamic-import + alias ಚಕ್ರಗಳನ್ನು ಅದು ನೋಡಲಾಗುತ್ತಿರಲಿಲ್ಲ. ಸರಿಪಡಿಸಲಾಗಿದೆ: ಗೇಟ್ ಈಗ `src` + `open-sse` (5023 ಫೈಲ್ಗಳು) ಅನ್ನು ಸಂಚರಿಸುತ್ತದೆ, TypeScript AST ನಿಂದ ಸ್ಪೆಸಿಫೈಯರ್ಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ (ಹೀಗಾಗಿ `import("…")` ಎಣಿಕೆಯಾಗುತ್ತದೆ ಮತ್ತು type-position `typeof import("…")` ಎಣಿಕೆಯಾಗುವುದಿಲ್ಲ), ಹಾಗೂ tsconfig `paths` ಅನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. ಇದು 0 ಅಲ್ಲ, **14** ಚಕ್ರಗಳನ್ನು ಕಂಡುಹಿಡಿಯುತ್ತದೆ. ಗೇಟ್ PRನಲ್ಲಿ ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ 14 ಚಕ್ರಗಳನ್ನು ಸರಿಪಡಿಸಲಾಗದ ಕಾರಣ, `check:cycles` ಈಗ ಒಂದು **ರ್ಯಾಚೆಟ್** ಆಗಿದೆ (`--ratchet`, `quality-baseline.json` ನಲ್ಲಿ ಗರಿಷ್ಠ ಮಿತಿ `metrics.cycles.value = 14`, `direction: down`) — ಇದು ಯಾವುದೇ _ಹಿಂಜರಿತವನ್ನು_ ತಡೆಯುತ್ತದೆ ಮತ್ತು ಎಣಿಕೆ ಕೇವಲ ಕಡಿಮೆಯಾಗಬಹುದು. CI `npm run check:cycles:ratchet` ಅನ್ನು ರನ್ ಮಾಡುತ್ತದೆ. ಕ್ರಮೇಣ ಕಡಿತವು **A-01** ಜೊತೆಗೆ ಸಾಗುತ್ತದೆ. ವಿಶಾಲವಾದ ಎರಡನೇ ಅಭಿಪ್ರಾಯವಾಗಿ `check:circular-deps` (dpdm) ಸಲಹಾತ್ಮಕವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ.
- **ಸಂಕೀರ್ಣತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ಒಂದು ESLint ಸಂಚಾರ, ruleId ಪ್ರಕಾರ ಎಣಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ cyclomatic+max-lines ಮತ್ತು cognitive baselineಗಳು ಸ್ವತಂತ್ರವಾಗಿರುತ್ತವೆ; ಪ್ರತ್ಯೇಕ `check:complexity` / `check:cognitive-complexity` ಸ್ಥಳೀಯ `--update` ಗಾಗಿ ಉಳಿಯುತ್ತವೆ.
- **`/api` ಭ್ರಮೆ-ವಿರೋಧಿ ಪರಿಶೀಲನೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ಯ ಒಂದು FS ಪಟ್ಟಿ; openapi-routes + docs-symbols ಇನ್ನೂ ಸ್ವತಂತ್ರವಾಗಿ ವರದಿ ಮಾಡುತ್ತವೆ; ಪ್ರತ್ಯೇಕ ಪರಿಶೀಲನೆಗಳು ಸ್ಥಳೀಯ ರನ್ಗಳಿಗಾಗಿ ಉಳಿಯುತ್ತವೆ.
- **`check:node-runtime` 11 ಜಾಬ್ಗಳಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ** — ⚠️ **ಕಡಿಮೆ ROI.** ಪ್ರತಿಯೊಂದೂ ಪ್ರತ್ಯೇಕ ರನ್ನರ್ ಆಗಿದ್ದು, ಪರಿಶೀಲನೆಗೆ <1s ಬೇಕಾಗುತ್ತದೆ; ಅಗ್ಗದ ಪ್ರತಿ-ಜಾಬ್ ಸುರಕ್ಷತಾ ಪರಿಶೀಲನೆಯನ್ನು ಕಳೆದುಕೊಳ್ಳುವ ಬದಲಾಗಿ ಒಟ್ಟು ಉಳಿತಾಯ ~10s ಮಾತ್ರ. ಈ ಬದಲಾವಣೆಯ ಗೊಂದಲಕ್ಕೆ ತಕ್ಕ ಮೌಲ್ಯವಿಲ್ಲ.
