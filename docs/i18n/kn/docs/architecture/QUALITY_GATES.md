ಈ ದಸ್ತಾವೇಜು OmniRouteನಲ್ಲಿನ ಎಲ್ಲಾ CI ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳಿಗೆ ಅಧಿಕೃತ ಉಲ್ಲೇಖವಾಗಿದೆ.
ಇದು ಪ್ರತಿಯೊಂದು ಗೇಟ್, ಅದು ಏನನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ, ಅದು ಯಾವ CI ಜಾಬ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ, ಅದು
ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ ಅಥವಾ ಪಾಸ್/ಫೇಲ್ ನೀತಿಯನ್ನು ಬಳಸುತ್ತದೆಯೇ ಮತ್ತು ಅದು ಬಿಲ್ಡ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆಯೇ ಅಥವಾ ಸಲಹಾತ್ಮಕವಾಗಿದೆಯೇ ಎಂಬುದನ್ನು ವಿವರಿಸುತ್ತದೆ.

ಸಂಕ್ಷಿಪ್ತ ಸಾರಾಂಶ ಮತ್ತು ಅನುಮತಿಪಟ್ಟಿ ನೀತಿಗಾಗಿ, `AGENTS.md`ನಲ್ಲಿರುವ "ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳು ಮತ್ತು ರ್ಯಾಚೆಟ್ಗಳು" ವಿಭಾಗವನ್ನು
ನೋಡಿ. ಇದೇ ಸಿಸ್ಟಮ್ನ ವಿಮರ್ಶಾತ್ಮಕ ಮೌಲ್ಯಮಾಪನ, ಪಕ್ವತೆಯ ವರ್ಗೀಕರಣ ಮತ್ತು ಉಪಕರಣ-ಸ್ವತಂತ್ರ
ಮರುಅನುಷ್ಠಾನ ಯೋಜನೆಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ ಪ್ಲೇಬುಕ್](../ops/QUALITY_GATE_PLAYBOOK.md) ನೋಡಿ.

## ಗೇಟ್ ಇನ್ವೆಂಟರಿ ಮತ್ತು ಕಾರ್ಯಗತಗೊಳಿಸುವ ಪ್ರೊಫೈಲ್ಗಳು

### ಅಭ್ಯರ್ಥಿ ಅಂಗೀಕಾರ

CI ಮತ್ತು Quality Gates ವರ್ಕ್ಫ್ಲೋಗಳು ಪ್ರತಿಯೊಂದೂ ಸ್ಥಿರವಾದ ತೀರ್ಪನ್ನು ನೀಡುತ್ತವೆ: `Gate / CI` ಮತ್ತು
`Gate / Quality`. ಅವುಗಳ ಆವೃತ್ತಿಗೊಳಿಸಲಾದ ಅಂಗೀಕಾರ ನೀತಿಯು ಪ್ರತಿಯೊಂದು ಅಪ್ಸ್ಟ್ರೀಮ್ ಜಾಬ್ ಅನ್ನು
ಕಡ್ಡಾಯ ಅಥವಾ ಸಲಹಾತ್ಮಕ ಎಂದು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ. ಅನ್ವಯವಾಗುವ ಕಡ್ಡಾಯ ಜಾಬ್ ಯಶಸ್ವಿಯಾಗಲೇಬೇಕು: ಕಾಣೆಯಾದ,
ರದ್ದಾದ, ಬಿಟ್ಟುಬಿಡಲಾದ, ಬಾಕಿ ಇರುವ ಮತ್ತು ಅಜ್ಞಾತ ಫಲಿತಾಂಶಗಳು PASS ಅನ್ನು ಸ್ಥಾಪಿಸಲಾರವು. ಮಾನ್ಯವಾದ
docs-only ಅಥವಾ catalog-only ವರ್ಗೀಕರಣವು ಕೋಡ್ ಲೇನ್ ಅನ್ನು ಅನ್ವಯವಾಗದಂತೆ ಮಾಡಬಹುದು;
ಕರಡು PR ಅನ್ನು ಅಂಗೀಕೃತ ಅಭ್ಯರ್ಥಿಯಾಗಿ ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ. `hotfix` ಲೇಬಲ್ ಸಾಕ್ಷ್ಯದ ಅಗತ್ಯವನ್ನು ಮನ್ನಾ ಮಾಡುವುದಿಲ್ಲ.

ಎರಡೂ ವರ್ಕ್ಫ್ಲೋಗಳು main/release ಬ್ರಾಂಚ್ಗಳಿಗೆ ಬರುವ PRಗಳು, `main` ಗೆ ಪುಷ್ಗಳು, ಹಸ್ತಚಾಲಿತ ಡಿಸ್ಪ್ಯಾಚ್
ಮತ್ತು merge-group ಈವೆಂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ. ಪುಷ್, ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು merge-group ಪೂರ್ಣ ಆಯ್ಕೆಯನ್ನು ರನ್ ಮಾಡುತ್ತವೆ.
`release/**` ಗೆ ಪುಷ್ಗಳು ಅವುಗಳನ್ನು ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ (2026-10-18): ಪ್ರತಿಯೊಂದು ಬದಲಾವಣೆಯೂ ಈಗಾಗಲೇ ತನ್ನ PR ನಲ್ಲಿ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು ರನ್ ಮಾಡಿದೆ
ಮತ್ತು ವಿಲೀನಗೊಂಡ ಸಂಯೋಜನೆಯು Release-Green ನ ಜವಾಬ್ದಾರಿಯಾಗಿದೆ (`docs/ops/RUNNER_BOX.md` → ಹೋಸ್ಟ್ ಮಾಡಿದ ಲೇನ್). ಫೋರ್ಕ್ಗಳು
ಮತ್ತು merge groupಗಳು ಬೇರೆ ಸಂದರ್ಭಗಳಲ್ಲಿ self-hosted
ರನ್ನರ್ಗಳನ್ನು ಆಯ್ಕೆಮಾಡುವ ಜಾಬ್ಗಳಿಗೆ hosted ರನ್ನರ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ; ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಸಾಕಷ್ಟು hosted ಸಾಮರ್ಥ್ಯವನ್ನು ಪರಿಶೀಲಿಸಬೇಕು.

ಪ್ರತಿಯೊಂದು JSON ರಸೀದಿಯು ಚೆಕ್ಔಟ್ ಮಾಡಿದ SHA, ವರ್ಕ್ಫ್ಲೋ ರನ್ ಮತ್ತು ಪ್ರಯತ್ನವನ್ನು ಗುರುತಿಸುತ್ತದೆ.
ಚೆಕ್ಔಟ್/ಈವೆಂಟ್ SHA ಹೊಂದಿಕೆಯಾಗದಿದ್ದರೆ CLI ಅದನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ವರ್ಕ್ಫ್ಲೋ ಪರೀಕ್ಷೆಗಳು ನೀತಿ ಸದಸ್ಯತ್ವವನ್ನು
ತೀರ್ಪು ಜಾಬ್ನ `needs` ಪಟ್ಟಿಗೆ ಬಂಧಿಸುತ್ತವೆ, ಆದ್ದರಿಂದ ಹೊಸ ಅಥವಾ ತೆಗೆದುಹಾಕಿದ ಲೇನ್ ಮೌನವಾಗಿ ಕಣ್ಮರೆಯಾಗಲು ಸಾಧ್ಯವಿಲ್ಲ.
ರಸೀದಿಗಳು ತಮ್ಮದೇ ಕಾರ್ಯಪ್ರವಾಹವನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ; ಪ್ರಕಟಣೆ, ನಿಯೋಜನೆ ಅಥವಾ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಲಹಾ ಸ್ಕ್ಯಾನರ್ನ ಆಂತರಿಕ ಅಂಶಗಳನ್ನು ಅಲ್ಲ. ಅನ್ವಯಿಸುವ ಪರಿಶೀಲನೆಗಳನ್ನು ಶಾಖೆಯ ನಿಯಮಗಳಲ್ಲಿ ಕಡ್ಡಾಯಗೊಳಿಸುವುದು ಪ್ರತ್ಯೇಕ ಆಡಳಿತಾತ್ಮಕ ಬದಲಾವಣೆಯಾಗಿದೆ; ಅವುಗಳ ಕಾರ್ಯಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುವುದರಿಂದ ಮಾತ್ರ ಶಾಖೆಗೆ ರಕ್ಷಣೆ ದೊರೆಯುವುದಿಲ್ಲ.

`API Route Typecheck` ಒಂದು ಸ್ವತಂತ್ರ ಕಾರ್ಯಪ್ರವಾಹ ಪರಿಶೀಲನೆಯಾಗಿದ್ದು, ಎರಡೂ ಸಮಗ್ರ ತೀರ್ಪುಗಳು ಮತ್ತು ಸ್ಥಳೀಯ ಪೂರ್ಣ ವೀಕ್ಷಕದ ಸ್ಥಿರ ಪ್ರೊಫೈಲ್ನ ಹೊರಗಿದೆ. ನಿಖರವಾದ ಅಭ್ಯರ್ಥಿಗಾಗಿ ಅದರ ಫಲಿತಾಂಶವನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಪರಿಶೀಲಿಸಿ. `.github/workflows/api-route-typecheck.yml` ಎಂಬುದು `main` ಅಥವಾ `release/**` ಗೆ ಬರುವ PRಗಳು, ಆ ಎರಡೂ ಶಾಖಾ ಕುಟುಂಬಗಳಿಗೆ ಮಾಡುವ ಪುಷ್ಗಳು ಮತ್ತು ಹಸ್ತಚಾಲಿತ ರವಾನೆಯಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ. ಇದಕ್ಕೆ ಪಥ ಫಿಲ್ಟರ್ ಇಲ್ಲ. PRನ ಮೂಲ ಶಾಖೆಯನ್ನು ಮರುಗುರಿಪಡಿಸುವುದು ಹೊಸ ಪರಿಶೀಲನೆಯನ್ನು ವಿನಂತಿಸುತ್ತದೆ; ಬಾಡಿ/ಶೀರ್ಷಿಕೆ ತಿದ್ದುಪಡಿಗಳು ವೀಕ್ಷಣೆಗಾಗಿ ಮಾತ್ರ ಇರುವ `Admission not requested / API Route Typecheck` ಹೆಸರನ್ನು ಬಳಸುತ್ತವೆ ಮತ್ತು ಪ್ರವೇಶ ಪರಿಶೀಲನೆಯನ್ನು ಬದಲಿಸಲಾಗುವುದಿಲ್ಲ. ಈ ಕಾರ್ಯಪ್ರವಾಹವು ವಿಲೀನ-ಗುಂಪು ಟ್ರಿಗರ್ ಅನ್ನು ಘೋಷಿಸುವುದಿಲ್ಲ. ಈ ಪರಿಶೀಲನೆಯನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುವ ಯಾವುದೇ ವಿಲೀನ-ಸರತಿ ಜಾರಿಯು ಮೊದಲು ಆ ಈವೆಂಟ್ಗಾಗಿ ಅದರ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯನ್ನು ಸ್ಥಾಪಿಸಬೇಕು.

### UI ಕಾರ್ಯಗತಗೊಳಿಸುವ ಸಾಮರ್ಥ್ಯ

CI ಪೂರ್ಣ UI ಇನ್ವೆಂಟರಿಯನ್ನು ನಾಲ್ಕು `test-vitest` ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಶಾರ್ಡ್ಗಳಾಗಿ ರನ್ ಮಾಡುತ್ತದೆ; ಪ್ರತಿಯೊಂದರಲ್ಲಿ ಗರಿಷ್ಠ
ಎರಡು ವರ್ಕರ್ಗಳು ಮತ್ತು ಈಗಿರುವ 15 ನಿಮಿಷಗಳ ಜಾಬ್ ಗಡುವು ಇರುತ್ತದೆ. ಮೊದಲ ಶಾರ್ಡ್
MCP/autoCombo Vitest ಸೂಟ್ ಅನ್ನು ಸಹ ರನ್ ಮಾಡುತ್ತದೆ. ಕಡ್ಡಾಯ ಜಾಬ್ ಫಲಿತಾಂಶವು ಪ್ರತಿಯೊಂದು ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಲೆಗ್ ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ; ಒಂದು ಶಾರ್ಡ್ನ ವೈಫಲ್ಯ
ಅಥವಾ ರದ್ದತಿ ಅಭ್ಯರ್ಥಿ ಅಂಗೀಕಾರವನ್ನು ಸ್ಥಾಪಿಸಲಾರದು.

ನೈಟ್ಲಿ ಅಬ್ಸರ್ವರ್ ಪ್ರತಿ UI ಶಾರ್ಡ್ಗೆ ಪ್ರತ್ಯೇಕ ನಿಖರ-ಅಭ್ಯರ್ಥಿ ರಸೀದಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ,
ಮೊದಲ ರಸೀದಿಯಲ್ಲಿ MCP ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯೂ ಸೇರಿರುತ್ತದೆ. ಎಲ್ಲಾ ನಾಲ್ಕು ರಸೀದಿಗಳು, ಲಾಗ್ಗಳು ಮತ್ತು ಹೊಂದಾಣಿಕೆಯ
ಕಾರ್ಯಗತಗೊಳಿಸುವ ಗುರುತುಗಳು ಕಡ್ಡಾಯ. ಸ್ಥಳೀಯ `npm run test:vitest:ui` ಇನ್ನೂ
ಪೂರ್ಣ ಸೂಟ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ; ಒಂದು `--shard` ರನ್ ಭಾಗಶಃ ಸಾಕ್ಷ್ಯ ಮಾತ್ರ.

### ಯುನಿಟ್ ಕವರೇಜ್ ಸಂಗ್ರಹಣೆ

ಹನ್ನೆರಡು ಯುನಿಟ್ ಶಾರ್ಡ್ಗಳು ತಮ್ಮ ಈಗಿರುವ ಪರೀಕ್ಷಾ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯ ವೇಳೆ V8 ಕವರೇಜ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುತ್ತವೆ. ಯಶಸ್ವಿಯಾದ
ಶಾರ್ಡ್ ಮಧ್ಯಂತರ Istanbul ವರದಿಯನ್ನು ರಚಿಸದೆ ಮೂಲ ಫೈಲ್ಗಳನ್ನು ಸಂಕುಚಿತಗೊಳಿಸಲು `scripts/ci/compact-v8-coverage.mjs` ಅನ್ನು ರನ್ ಮಾಡುತ್ತದೆ.
ಅಂತಿಮ Coverage ಜಾಬ್ ಅಭ್ಯರ್ಥಿ SHA, ರನ್ಟೈಮ್, ಮೂಲ ರೂಟ್ ಮತ್ತು ಡೇಟಾ ಹ್ಯಾಶ್ಗಳ ವಿರುದ್ಧ ಎಲ್ಲಾ ಹನ್ನೆರಡು ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ,
ನಂತರ c8 ನ ರಿಪೋರ್ಟರ್ಗಳು ಮತ್ತು ಈಗಿರುವ ಕವರೇಜ್ ಮಿತಿಗಳನ್ನು ರನ್ ಮಾಡುತ್ತದೆ. ಇನ್ಪುಟ್ಗಳು c8 ನ ಜಾಗತಿಕ ಫೈಲ್ಹೆಸರು ಕ್ರಮವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ; ಮಿಶ್ರ function/block ಕವರೇಜ್ಗಾಗಿ
ಪ್ರತಿ-ಶಾರ್ಡ್ ಪೂರ್ವ-ವಿಲೀನವು ಅಸುರಕ್ಷಿತವಾಗಿದೆ. ಕಾಣೆಯಾದ, ದೋಷಪೂರಿತ ಅಥವಾ ಹೊಂದಾಣಿಕೆಯಾಗದ ಶಾರ್ಡ್ಗಳು ಅಂಗೀಕಾರವನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
ವಿಫಲವಾದ ಪರೀಕ್ಷಾ ಶಾರ್ಡ್ಗಳು ಕಚ್ಚಾ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ ಕವರೇಜ್ ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ; ಅದು ಅಂತಿಮ ವಿಲೀನವನ್ನು ಪ್ರವೇಶಿಸಲಾರದು.

### ಯೂನಿಟ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯ ಪ್ರಗತಿ ರಸೀದಿಗಳು

ಹಂಚಿಕೊಂಡಿರುವ `test:unit:ci:shard` ಕಮಾಂಡ್, `scripts/ci/unit-progress-reporter.mjs` ಮೂಲಕ `primary`, `dashboard` ಮತ್ತು `serial`
ಹಂತಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಸಾಮಾನ್ಯ ಪರೀಕ್ಷಾ ವರದಿಯು ಲಭ್ಯವಾಗಿಯೇ ಇರುತ್ತದೆ.
ಪ್ರತ್ಯೇಕವಾದ, ಮೆಟಾಡೇಟಾ-ಮಾತ್ರದ ರಸೀದಿಯು ಪ್ರತಿ ಫೈಲ್ನ ಪ್ರಾರಂಭ ಮತ್ತು ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಯನ್ನು ದಾಖಲಿಸುತ್ತದೆ,
ಮತ್ತು 30-ಸೆಕೆಂಡ್ನ ಹಾರ್ಟ್ಬೀಟ್ ಇನ್ನೂ ಸಕ್ರಿಯವಾಗಿರುವ ಫೈಲ್ಗಳು ಹಾಗೂ ಅವುಗಳ ಕಳೆದ ಸಮಯವನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ. ಇದು
ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿರುವ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆ ಮೆಟಾಡೇಟಾವನ್ನು ಮಾತ್ರ ದಾಖಲಿಸುತ್ತದೆ; ಪರೀಕ್ಷಾ ವಿವರಣೆಗಳು, ಔಟ್ಪುಟ್, ದೋಷದ ವಿವರಗಳು ಮತ್ತು ಸಂಪೂರ್ಣ
ಎನ್ವಿರಾನ್ಮೆಂಟ್ ಅನ್ನು ಸೀರಿಯಲೈಸ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ.

CI ಮತ್ತು Quality, JSONL ಫೈಲ್ಗಳನ್ನು `unit-progress-ci-<run>-<attempt>-<shard>` ಮತ್ತು
`unit-progress-quality-<run>-<attempt>-<shard>` ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಜಾಬ್ ಟೈಮ್ಔಟ್ ನಂತರದ ಅಪ್ಲೋಡ್ ಅನ್ನು ತಡೆಯಬಹುದು;
ಈಗಾಗಲೇ ಹೊರಸೂಸಲಾದ ಹಾರ್ಟ್ಬೀಟ್ಗಳು ರೋಗನಿರ್ಣಯದ ಸಾಕ್ಷ್ಯವಾಗಿ ಉಳಿಯುತ್ತವೆ. ಹಾರ್ಟ್ಬೀಟ್ಗಳು ಕಾಣೆಯಾಗಿರುವುದು
ನಿರ್ಬಂಧಿಸಲಾದ ಅಥವಾ ಕೊನೆಗೊಳಿಸಲಾದ ರನ್ನರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನೂ ಸೂಚಿಸಬಹುದು. ಈ ರಸೀದಿಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಪರೀಕ್ಷಾ ಆಯ್ಕೆ,
ಸಮಕಾಲೀನತೆ, ಗಡುವುಗಳು ಮತ್ತು ನಿರ್ಗಮನ ಸ್ಥಿತಿಯನ್ನು ಸಂರಕ್ಷಿಸುತ್ತವೆ; ಅವು ಅಭ್ಯರ್ಥಿ-ಸ್ವೀಕೃತಿಯ ತೀರ್ಪುಗಳಲ್ಲ.

### ಅಂಗೀಕಾರ ಫಲಿತಾಂಶಗಳನ್ನು ಒಗ್ಗೂಡಿಸುವ ಘಟಕದಲ್ಲಿ ಉಳಿಸಿದ ಸಾಕ್ಷ್ಯಗಳು

`scripts/quality/validate-release-acceptance.mjs` ನೀಡಲಾದ ಯೋಜನೆ ಮತ್ತು ಅದರ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳನ್ನು ಒಗ್ಗೂಡಿಸುತ್ತದೆ; ಯೋಜನೆಯು ಸಂಪೂರ್ಣ ಬಿಡುಗಡೆ ಪೈಪ್ಲೈನ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ ಎಂದು ಅದು ಸ್ಥಾಪಿಸುವುದಿಲ್ಲ. ಯೋಜನೆ `VERIFIED` ಆಗಿದ್ದರೂ ಅದರ ವರದಿಗಳು ಸ್ಪಷ್ಟವಾಗಿ `releaseAcceptance: false` ಅನ್ನು ಹೊಂದಿಸುತ್ತವೆ. `release-acceptance.yml` ವರ್ಕ್ಫ್ಲೋ ಇನ್ನೂ shadow ಪರೀಕ್ಷಾ ಫಿಕ್ಸ್ಚರ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ, ನೈಜ build, package, boot ಅಥವಾ promotion ರಸೀದಿಗಳನ್ನಲ್ಲ.

ಉಳಿಸಿದ ಸಾಕ್ಷ್ಯಗಳನ್ನು ಪರಿಶೀಲಿಸಲು CLI ಗೆ `--evidence-root` ಅಗತ್ಯವಿದೆ. ಫೈಲ್ಗಳನ್ನು `<evidence-root>/<artifact_id>/<member>` ಪಥದಲ್ಲಿ ಹುಡುಕಿ SHA-256 ಹ್ಯಾಶ್ ಲೆಕ್ಕಹಾಕಲಾಗುತ್ತದೆ. ಸಾಕ್ಷ್ಯವಿಲ್ಲದ PASS ದಾಖಲೆ, ಕಾಣೆಯಾದ ಅಥವಾ ಬದಲಾದ ಫೈಲ್, ಸುರಕ್ಷಿತವಲ್ಲದ ಪಥ ಅಥವಾ ಸಿಮ್ಲಿಂಕ್ ದೃಢೀಕರಣವನ್ನು ತಡೆಯುತ್ತದೆ. ಕಾಣೆಯಾದ ಫೈಲ್ಗಳು ಯಶಸ್ವಿ ರನ್ಗಳ ಖಾಲಿ ಲಾಗ್ಗಳಿಗೆ ಸಮಾನವಲ್ಲ. ಈಗಿರುವ SHA/run/attempt ಪರಿಶೀಲನೆಗಳು ಸ್ವತಂತ್ರವಾಗಿಯೇ ಇರುತ್ತವೆ: ಹೊಂದುವ ಬೈಟ್ಗಳು ಹಳೆಯ ರಸೀದಿಯನ್ನು ಮಾನ್ಯವಾಗಿಸಲಾರವು. ಫೈಲ್ನ ಸಮಗ್ರತೆಯು ಕಾರ್ಯನಿರ್ವಹಣೆಯ ನೈಜತೆಗೆ ಅಥವಾ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ನ promotion ಗೆ ಸಾಕ್ಷ್ಯವಲ್ಲ.

### ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಇನ್ವೆಂಟರಿ

ಆವೃತ್ತಿಗೊಳಿಸಲಾದ npm-alias ಇನ್ವೆಂಟರಿ ಮತ್ತು ಸ್ಥಿರ-ಸ್ಕ್ಯಾನ್ ಸದಸ್ಯತ್ವವು
`config/quality/gate-manifest.json` ನಲ್ಲಿ ಇವೆ. ಸ್ಕ್ರಿಪ್ಟ್ ಹೆಸರುಗಳು ಮತ್ತು ನಿಖರ ಕಮಾಂಡ್ಗಳನ್ನು
`package.json` ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸಲು `npm run check:gate-manifest` ಅನ್ನು ರನ್ ಮಾಡಿ; ಸೇರ್ಪಡೆಗಳು, ತೆಗೆದುಹಾಕುವಿಕೆಗಳು
ಮತ್ತು ಕಮಾಂಡ್ ಬದಲಾವಣೆಗಳು ಸ್ಥಳೀಯ ಹುಕ್ ಮತ್ತು CI ಯಲ್ಲಿನ ಬದಲಾವಣೆ-ವರ್ಗೀಕರಣ ಜಾಬ್ಗಳೆರಡನ್ನೂ ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
ಅಲಿಯಾಸ್ ಎಂಬುದು ವರ್ಕ್ಫ್ಲೋ ಜಾಬ್, ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಇನ್ಸ್ಟನ್ಸ್ ಅಥವಾ ಪರೀಕ್ಷಾ ಕೇಸ್ ಅಲ್ಲ: ಈ ಎಣಿಕೆಗಳನ್ನು
ಪರಸ್ಪರ ವಿನಿಮಯಯೋಗ್ಯವೆಂದು ಪ್ರಸ್ತುತಪಡಿಸಬಾರದು.

ಆಯ್ಕೆಮಾಡಿದ ಅಲಿಯಾಸ್ಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸದೆ ಪರಿಶೀಲಿಸಲು `npm run quality:scan -- --list` ಅಥವಾ `npm run quality:scan:fast -- --list`
ಅನ್ನು ಬಳಸಿ. ರನ್ನರ್ npm ಎಂಟ್ರಿಪಾಯಿಂಟ್ ಅನ್ನು ಆಹ್ವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದರ ರನ್ಟೈಮ್ (ಕಾನ್ಫಿಗರ್ ಮಾಡಿರುವಲ್ಲಿ Bun ಸೇರಿದಂತೆ) ಉಳಿಯುತ್ತದೆ.
ಮ್ಯಾನಿಫೆಸ್ಟ್ ಆ ಪ್ರೊಫೈಲ್ಗಳ ಹೊರಗಿನ ಅಲಿಯಾಸ್ಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಆಹ್ವಾನಿಸಲಾದವುಗಳೆಂದು ದಾಖಲಿಸುತ್ತದೆ, ಮತ್ತು
ನಿರ್ವಹಣಾ ಕಮಾಂಡ್ಗಳನ್ನು read-only ಸ್ಕ್ಯಾನ್ ಪ್ರೊಫೈಲ್ಗಳಲ್ಲಿ ನಿಷೇಧಿಸಲಾಗಿದೆ.

ಈ ಪ್ರೊಫೈಲ್ಗಳು ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಅನ್ನು ಮಾತ್ರ ಒಳಗೊಳ್ಳುತ್ತವೆ. ಅವು ಉತ್ಪನ್ನ ಪರೀಕ್ಷೆಗಳು,
ಕವರೇಜ್, ಪ್ಯಾಕೇಜಿಂಗ್, ಬಾಹ್ಯ ಚೆಕ್ಗಳು ಅಥವಾ ಅಭ್ಯರ್ಥಿಯ ಪೂರ್ಣ ಬಿಡುಗಡೆ ಅಂಗೀಕಾರವನ್ನು ಪ್ರಮಾಣೀಕರಿಸುವುದಿಲ್ಲ.
ವರ್ಕ್ಫ್ಲೋ ಅಂಗೀಕಾರವು ಲಿಂಕ್ ಮಾಡಲಾದ `config/quality/admission-policy.json` ಮತ್ತು
`scripts/quality/admission-verdict.mjs` ಅನ್ನು ಬಳಸುತ್ತದೆ. Release-observer ಪ್ರೊಫೈಲ್ಗಳು ಪ್ರತ್ಯೇಕವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ;
ಅವುಗಳ ಅನ್ವಯವಾಗುವ ಚೆಕ್ಗಳು ಮತ್ತು ರಸೀದಿಗಳನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸಿ. ಪೂರ್ಣ ಅಬ್ಸರ್ವರ್ನ ಸ್ಥಿರ
ಕಮಾಂಡ್ಗಳನ್ನು `config/quality/release-green-static-profile.json` ನಲ್ಲಿ ಘೋಷಿಸಲಾಗಿದೆ, ಇದರಲ್ಲಿ
`audit:deps`, mutation-test ಆಯ್ಕೆ ಮತ್ತು ಅನುವಾದ ಚೆಕ್ಗಳು ಸೇರಿವೆ. ಲೋಡರ್ npm
ಕಮಾಂಡ್ಗಳನ್ನು package.json ಮತ್ತು ಮಾದರಿಗೊಳಿಸಲಾದ CI/Quality ಘೋಷಣೆಗಳ ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; shell ಟೋಕನ್ಗಳನ್ನು ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳಾಗಿ ಕಾರ್ಯಗತಗೊಳಿಸುವ ಬದಲು ಬದಲಾವಣೆಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ಕಡ್ಡಾಯ ಸ್ಕ್ಯಾನರ್ನ SKIP/INCOMPLETE ಔಟ್ಪುಟ್
PASS ಅನ್ನು ಸ್ಥಾಪಿಸಲಾರದು. ಪ್ರೊಫೈಲ್ ತನ್ನ ಬಾಹ್ಯ ಹೊರತುಪಡಿಸುವಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು
ಹೋಸ್ಟ್ ಮಾಡಿದ ಕವರೇಜ್, ಪರೀಕ್ಷಾ ಮ್ಯಾಟ್ರಿಕ್ಸ್ಗಳು, ಪ್ಯಾಕೇಜ್ ಅಥವಾ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ ಸಾಕ್ಷ್ಯವನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ. ಕೆಳಗಿನ ಗದ್ಯರೂಪದ ಇನ್ವೆಂಟರಿ
ಒಂದು ಉಲ್ಲೇಖ ಮಾತ್ರ; ಗೇಟ್ ನಿಜವಾಗಿಯೂ ರನ್ ಆಗಿದೆ ಎಂಬುದಕ್ಕೆ ಪುರಾವೆಯಲ್ಲ.

ಸ್ಕ್ರಿಪ್ಟ್ಗಳು `scripts/check/` (ನೀತಿ ಗೇಟ್ಗಳು) ಮತ್ತು `scripts/quality/` (ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್) ಅಡಿಯಲ್ಲಿ ಇವೆ.
CI ಯ ಏಕೈಕ ಅಧಿಕೃತ ಮೂಲವು `.github/workflows/ci.yml` ಆಗಿದೆ.

### ಪ್ರಕಟಿತ ಮೂಲ ದಸ್ತಾವೇಜೀಕರಣದ ಆರೋಗ್ಯ

`.github/workflows/i18n-base-health.yml` ಆಯ್ದ ಪುಷ್ಗಳ ನಂತರ `main` ಮತ್ತು `release/v*` ಶಾಖೆಗಳಲ್ಲಿ ಹಾಗೂ ಹಸ್ತಚಾಲಿತವಾಗಿ ಚಾಲನೆ ಮಾಡಿದಾಗ ದಸ್ತಾವೇಜೀಕರಣದ ಆರೋಗ್ಯವನ್ನು ಗಮನಿಸುತ್ತದೆ. ಇದರ ಫಿಲ್ಟರ್ಗಳು ದಸ್ತಾವೇಜೀಕರಣ, ರೂಟ್ Markdown, `llm.txt`, ಅನುವಾದದ ಸ್ಥಿತಿ/ಸಂರಚನೆ ಮತ್ತು ಸಂಬಂಧಿತ i18n ಪರಿಕರಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ. ಏಕೈಕ `Published base documentation health` ಜಾಬ್ ಹೋಸ್ಟ್ ಮಾಡಲಾದ Ubuntu ಮತ್ತು ಐದು ನಿಮಿಷಗಳ ಕಾಲಮಿತಿಯನ್ನು ಬಳಸುತ್ತದೆ. ಇದು ಅವಲಂಬನೆಗಳ ಸ್ಥಾಪನೆ, ಅನುವಾದ ಅಥವಾ ಸ್ಥಿತಿ ಅಳವಡಿಕೆ ಇಲ್ಲದೆ, ಓದಲು-ಮಾತ್ರವಾದ ಮೌಲ್ಯೀಕರಣವನ್ನು ನಿರ್ವಹಿಸಿ ರೋಗನಿರ್ಣಯದ ರಸೀದಿಯನ್ನು ಬರೆಯುತ್ತದೆ.

`scripts/i18n/check-base-health.mjs` ಗೆ ಮೂಲ-ಹ್ಯಾಶ್, ಕಾಣೆಯಾದ ಗುರಿ, ಗುರಿ-ಹ್ಯಾಶ್, ಹಳೆಯದಾದ ಅನುವಾದ ಮತ್ತು ವಿಭಾಗ-ಕ್ಯಾಶ್ ಅಸಂಗತತೆಗಳು ಶೂನ್ಯವಾಗಿರಬೇಕು. ಇದು ಪ್ರಸ್ತುತ ಪ್ರಮುಖ ದಸ್ತಾವೇಜು/ಲೊಕೇಲ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು ಅದರ ದಾಖಲಿತ ಮೂಲೋತ್ಪತ್ತಿಯನ್ನೂ ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ. ಅಮಾನ್ಯ ಸಂದರ್ಭ, ಅಪೂರ್ಣ ವ್ಯಾಪ್ತಿ ಅಥವಾ ಮಧ್ಯದಲ್ಲೇ ಅಡಚಣೆಗೊಂಡ ಪರಿಶೀಲಕವು `INCOMPLETE` ಅನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ; ದೃಢೀಕರಿಸಿದ ವ್ಯತ್ಯಾಸವು `FAIL` ಅನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ. ಇವೆರಡೂ ವಿಫಲತೆಯನ್ನು ಸೂಚಿಸುವ ನಿರ್ಗಮನ ಸ್ಥಿತಿಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತವೆ. ರಸೀದಿಯನ್ನು ಚೆಕ್ಔಟ್ SHA, ವರ್ಕ್ಫ್ಲೋ, ರನ್ ಮತ್ತು ಪ್ರಯತ್ನಕ್ಕೆ ಬಂಧಿಸಲಾಗುತ್ತದೆ ಹಾಗೂ `i18n-base-health-<sha>-<run>-<attempt>` ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

ಇದು ಪ್ರಕಟಿತ ಮೂಲದ ಸ್ವತಂತ್ರ ಅವಲೋಕನವಾಗಿದೆ. ಇದು PR ಅಥವಾ ವಿಲೀನ-ಗುಂಪಿನ ಈವೆಂಟ್, ಕಡ್ಡಾಯ PR ಪರಿಶೀಲನೆ, npm ಅಲಿಯಾಸ್ ಅಥವಾ ಸ್ಥಿರ-ಸ್ಕ್ಯಾನ್ ಪ್ರೊಫೈಲ್ನ ಸದಸ್ಯನನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಭೇದಾತ್ಮಕ PR ನೀತಿ ಮತ್ತು ಆಧಾರವಾಗಿರುವ ಪರಿಶೀಲಕದ ಸಲಹಾತ್ಮಕ ವರ್ಗೀಕರಣಗಳು ಪ್ರತ್ಯೇಕವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ. ಯಶಸ್ವಿ ಅಪ್ಲೋಡ್ ವಿಫಲವಾದ ಆರೋಗ್ಯ ಫಲಿತಾಂಶವನ್ನು PASS ಆಗಿ ಪರಿವರ್ತಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

#### ಮರೆತುಹೋದ ಸಿಬ್ಲಿಂಗ್ ಪರೀಕ್ಷೆಗಳ ವರದಿ

`npm run check:forgotten-sibling-tests` ಪರೀಕ್ಷಾ-ಪ್ರಭಾವ ನಕ್ಷೆಯ ಹಿಂದಿರುವ ಇಂಪೋರ್ಟ್ ರಿಸಾಲ್ವರ್ ಅನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ.
ಬದಲಾದ ಪ್ರತಿಯೊಂದು ಪ್ರೊಡಕ್ಷನ್ ಮಾಡ್ಯೂಲ್ಗಾಗಿ, ಸಂಭಾವ್ಯ ಪರೀಕ್ಷೆಯು
ಪುಲ್-ರಿಕ್ವೆಸ್ಟ್ ಡಿಫ್ನಲ್ಲಿ ಇಲ್ಲದಿದ್ದಾಗ ಇದು ನಿರ್ಧಾರಿತ
`changed module/symbol -> static consumer -> candidate sibling test` ಸರಪಳಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಯಾವುದೇ ನಿರ್ಬಂಧಿಸುವ ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಕ್ಯಾಲಿಬ್ರೇಶನ್ಗಾಗಿ Markdown ಸಾರಾಂಶ ಮತ್ತು JSON ಫಲಿತಾಂಶವನ್ನು
`forgotten-sibling-tests` ವರ್ಕ್ಫ್ಲೋ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

ಬ್ಯಾರೆಲ್ ಮರು-ಎಕ್ಸ್ಪೋರ್ಟ್ಗಳು ಮತ್ತು ಡೈನಾಮಿಕ್ ಇಂಪೋರ್ಟ್ಗಳು ರೆಸಲ್ಯೂಶನ್ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಗಳು ಮಾತ್ರ; ಅವು ಎಂದಿಗೂ
ನಿರ್ಬಂಧಿಸುವ ಕಂಡುಹಿಡಿತವನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ. ಪರಿಶೀಲಿಸಲಾದ ವಿನಾಯಿತಿಗಳು
`config/quality/forgotten-sibling-allowlist.json` ನಲ್ಲಿ ಇರುತ್ತವೆ. ಪ್ರತಿಯೊಂದು ನಮೂದು ಬಳಕೆದಾರ ಮತ್ತು ಸಂಭಾವ್ಯ
ಪರೀಕ್ಷೆಯನ್ನು ಹೆಸರಿಸಬೇಕು, ನಿರ್ದಿಷ್ಟ ಸಮರ್ಥನೆಯನ್ನು ನೀಡಬೇಕು ಮತ್ತು GitHub ಇಶ್ಯೂ ಅಥವಾ ಪುಲ್ ರಿಕ್ವೆಸ್ಟ್ಗೆ ಲಿಂಕ್ ಮಾಡಬೇಕು. ದೋಷಪೂರಿತ ನಮೂದುಗಳು
ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ. ವಿನಾಯಿತಿಗಳು ಅಳಿಸಲಾದ ಸಂಭಾವ್ಯ ಪರೀಕ್ಷೆಯನ್ನು ಅಥವಾ `.skip`/`.todo` ಸೇರಿಸುವ ಡಿಫ್ ಅನ್ನು ಮರೆಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ;
ಅಸರ್ಶನ್ ದುರ್ಬಲಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಇತರ ಮರೆಮಾಚುವಿಕೆಗಳು ಸ್ವತಂತ್ರವಾಗಿ ನಿರ್ಬಂಧಿಸುವ
`check:test-masking` ಗೇಟ್ನ ವ್ಯಾಪ್ತಿಯಲ್ಲೇ ಉಳಿಯುತ್ತವೆ.

### ಜಾಬ್: `quality-extended`

ಈ ಜಾಬ್ ಅನ್ವಯಿಸುವ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ. ಬಂಡಲ್ ಗಾತ್ರ, ರಹಸ್ಯಗಳ ಪತ್ತೆಗಳು, ದುರ್ಬಲತೆಗಳ
ಪತ್ತೆಗಳು, ವರ್ಕ್ಫ್ಲೋ ಪತ್ತೆಗಳು ಮತ್ತು OpenAPI ಬದಲಾವಣೆಗಳನ್ನು ಅಗತ್ಯ ರ್ಯಾಚೆಟ್ಗಳೊಂದಿಗೆ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ.

`scripts/ci/install-quality-scanners.sh` ಪಿನ್ ಮಾಡಲಾದ ಆವೃತ್ತಿಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ ಮತ್ತು ಸ್ಥಾಪನಾ
ವೈಫಲ್ಯಗಳನ್ನು ಮುಂದಕ್ಕೆ ರವಾನಿಸುತ್ತದೆ. ಲಭ್ಯವಿಲ್ಲದ ಪರಿಕರಗಳು, ಅಮಾನ್ಯ ವರದಿಗಳು ಅಥವಾ ಲಭ್ಯವಿಲ್ಲದ ಬೇಸ್ಲೈನ್ಗಳು
ಅಗತ್ಯ ಸ್ಕ್ಯಾನರ್ ಗೇಟ್ ಅನ್ನು ಅಪೂರ್ಣ ಸ್ಥಿತಿಯಲ್ಲಿ ಬಿಡುತ್ತವೆ.

### ಕೆಲಸ: `docs-sync-strict`

`main` ಅಥವಾ `release/**` ಗೆ ಬರುವ pull request ಗಳಲ್ಲಿ, ಈ ಕೆಲಸವು ಕರಡುಗಳಲ್ಲದ (ಅಥವಾ ವಿಶ್ವಾಸಾರ್ಹ ಕ್ಯೂನಲ್ಲಿರುವ) ಮತ್ತು ದಸ್ತಾವೇಜು ಅಥವಾ ಕೋಡ್ ಬದಲಾವಣೆಗಳೆಂದು ವರ್ಗೀಕರಿಸಿದ ಅಭ್ಯರ್ಥಿಗಳಿಗೆ ಮಾತ್ರ ಚಲಿಸುತ್ತದೆ. PR ಅಲ್ಲದ CI ಘಟನೆಗಳಲ್ಲೂ ಇದು ಚಲಿಸುತ್ತದೆ; ಈ workflow ನ push trigger `main` ಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ, `release/**` ಗೆ ಅಲ್ಲ. ಶೂನ್ಯವಲ್ಲದ ನಿರ್ಗಮನ ಕೋಡ್ನೊಂದಿಗೆ ಮುಗಿಯುವ ಹಂತವು ಕೆಲಸವನ್ನು ತಡೆಯುತ್ತದೆ; ಕೆಳಗೆ ದಾಖಲಿಸಿದ ವರದಿ-ಮಾತ್ರದ ಫಲಿತಾಂಶಗಳು ಮತ್ತು ವಿನಾಯಿತಿಗಳು ತಡೆಯುವುದಿಲ್ಲ.

ಹಳತಾಗಿದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ **ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಬಾಕಿಯನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ** — ದೀರ್ಘಕಾಲದಿಂದ ಇರುವ ಅನುವಾದವು
ಯಾವ ಹಳೆಯ ಇಂಗ್ಲಿಷ್ನಿಂದ ಬಂದಿದೆ ಎಂಬುದನ್ನು ವ್ಯತ್ಯಾಸವು ಬಹಿರಂಗಪಡಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ; ಆದ್ದರಿಂದ ಗೇಟ್ ಪ್ರಸ್ತುತ ಬದಲಾವಣೆಯು
ಸ್ಪರ್ಶಿಸುವುದನ್ನು ಮಾತ್ರ ನಿರ್ಣಯಿಸುತ್ತದೆ. ಪರ್ಯಾಯವಾದ (ಪ್ರತಿ-ಕೀ ಹ್ಯಾಶ್ ಬೇಸ್ಲೈನ್) ವಿಧಾನಕ್ಕೆ ~600 KB ಗಾತ್ರದ ರಚಿತ ಫೈಲ್
ಅಗತ್ಯವಾಗುತ್ತದೆ; ಇದು ಈಗಿರುವ ಅತಿದೊಡ್ಡ ಬೇಸ್ಲೈನ್ಗಿಂತ 3× ದೊಡ್ಡದಾಗಿದ್ದು, ಪ್ರತಿ i18n PRನಲ್ಲೂ ಬದಲಾಗುತ್ತಿರುತ್ತದೆ.

ಇದನ್ನು ಪೂರೈಸಲು ಎರಡು ಮಾರ್ಗಗಳಿವೆ:

1. ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಅನುವಾದಗಳನ್ನು ನವೀಕರಿಸಿ, ಅಥವಾ
2. ಅವುಗಳನ್ನು `__MISSING__:<new english>` ಗೆ ಹೊಂದಿಸಿ — ಆಗ ರನ್ಟೈಮ್ ಸರಿಪಡಿಸಿದ ಇಂಗ್ಲಿಷ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ಮತ್ತು ಕೀಯನ್ನು ಅನುವಾದಕ್ಕಾಗಿ ಸರತಿಗೆ ಸೇರಿಸಲಾಗುತ್ತದೆ.

ಸ್ಟ್ರಿಂಗ್ನ **ಅರ್ಥ** ಬದಲಾಗಿದ್ದರೆ, **ಕೀಯ ಹೆಸರನ್ನು ಬದಲಿಸುವುದಕ್ಕೆ** ಆದ್ಯತೆ ನೀಡಿ: ಹೊಸ ಕೀ ಹಳತಾದ
ಅನುವಾದವನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. #8463 ಬಳಸಿದ ಮಾದರಿ ಇದೇ.

```bash
npm run i18n:check-value-drift          # ಕಟ್ಟುನಿಟ್ಟಾದದ್ದು (CI ಚಲಾಯಿಸುವುದು)
npm run i18n:check-value-drift:warn     # ವರದಿ ಮಾತ್ರ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ಮೌಲ್ಯ-ವ್ಯತ್ಯಾಸ ಮತ್ತು ಹೊಸ-ಕೀ ಗೇಟ್ಗಳು `scripts/i18n/resolve-ui-diff-base.mjs` ನಿಂದ ಒಂದೇ ಬದಲಾಯಿಸಲಾಗದ ಹೋಲಿಕೆಯನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ. ವರ್ಕ್ಫ್ಲೋ ಎರಡೂ ಪರಿಶೀಲನೆಗಳಿಗೆ ಒಂದೇ base, base-tip ಮತ್ತು candidate SHAಗಳನ್ನು ರವಾನಿಸುತ್ತದೆ. PR/base-retarget, push ಮತ್ತು merge-group ರನ್ಗಳು ತಮ್ಮ event ಸಂದರ್ಭವನ್ನು ಬಳಸುತ್ತವೆ. candidate branch ಅನ್ನು dispatch ಮಾಡಲು ಅದರ ನಿಖರವಾದ ತೆರೆದ PR ಅಥವಾ ಸ್ಪಷ್ಟವಾದ `i18n_base_sha` ಇನ್ಪುಟ್ ಅಗತ್ಯವಿದೆ. ಆ ಇನ್ಪುಟ್ ಇಲ್ಲದೆ `main` ಅಥವಾ `release/vX.Y.Z` ಅನ್ನು dispatch ಮಾಡುವಾಗ ಅಥವಾ ನಿಗದಿತ ವೇಳಾಪಟ್ಟಿಯಲ್ಲಿ ಪರಿಶೀಲಿಸುವಾಗ, ಕೊನೆಯ commit ಅನ್ನು ಅದರ ಮೊದಲ parent ಜೊತೆಗೆ ಹೋಲಿಸಲಾಗುತ್ತದೆ; ಇದು ಆನುವಂಶಿಕವಾಗಿ ಬಂದಿರುವ ಎಲ್ಲಾ ಅನುವಾದ ಬಾಕಿಯ audit ಅಲ್ಲ. ಸ್ಥಳೀಯ invocation ಗೆ ಸ್ಪಷ್ಟವಾದ comparison base ಅಗತ್ಯವಿದೆ; ಉದಾಹರಣೆಗೆ, ಮೇಲಿನ `BASE_REF` command.

ಹೋಲಿಕೆಯ ಸಂದರ್ಭ ಕಾಣೆಯಾಗಿದ್ದರೆ ಅಥವಾ ಅಸ್ಪಷ್ಟವಾಗಿದ್ದರೆ, ಅಗತ್ಯವಿರುವ catalog ಅನ್ನು ಓದಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ ಅಥವಾ ಅದು ಅಮಾನ್ಯವಾಗಿದ್ದರೆ, ಮತ್ತು candidate ಬದಲಾಗಿದ್ದರೆ, warn mode ನಲ್ಲಿಯೂ ಸಹ exit code **2** ಜೊತೆಗೆ `INCOMPLETE` ಫಲಿತಾಂಶ ದೊರೆಯುತ್ತದೆ. Catalog ಅನ್ನು ಓದಲು `scripts/i18n/read-ui-catalog.mjs` ಬಳಸಲಾಗುತ್ತದೆ; ಓದುವಿಕೆಯ ವೈಫಲ್ಯಗಳನ್ನು ಖಾಲಿ object ಗಳಿಂದ ಬದಲಿಸಲಾಗುವುದಿಲ್ಲ. ಲಭ್ಯವಿಲ್ಲದ base ಆಗಲಿ ಅಥವಾ ಅಪೂರ್ಣ input ಆಗಲಿ `PASS` ಅನ್ನು ಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

  ನವೀಕರಿಸುವುದಿಲ್ಲ; #12149 ಹಿಂದಿನ ವರದಿ ಇತಿಹಾಸವನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ.

**ಹೊಸ-ಕೋಡ್ ಮೋಡ್ (Clean-as-You-Code) — 2026-08-30 ರಿಂದ, PR ತ್ವರಿತ ಮಾರ್ಗಕ್ಕೆ ಮಾತ್ರ**

`pull_request` ಈವೆಂಟ್ಗಳಲ್ಲಿ `quality.yml`, `check:file-size`,
`check:complexity-ratchets` ಮತ್ತು `check:dead-code` ಗೆ `--base-ref <PR base SHA>` ಅನ್ನು ರವಾನಿಸುತ್ತದೆ.
`check:complexity-ratchets` ಮತ್ತು `check:dead-code` ಗಾಗಿ, ಗೇಟ್ HEAD ಅನ್ನು ಮರ್ಜ್-ಬೇಸ್ನೊಂದಿಗೆ
**PR ಬದಲಾಯಿಸಿದ ಫೈಲ್ಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತಗೊಳಿಸಿ** ಹೋಲಿಸುತ್ತದೆ (`scripts/check/newCodeMode.mjs`:
ಮರ್ಜ್-ಬೇಸ್ ಅನ್ನು ತಾತ್ಕಾಲಿಕ `git worktree` ನಲ್ಲಿ ರಚಿಸಲಾಗುತ್ತದೆ, ESLint/knip ಅನ್ನು ಅಲ್ಲಿ ಮತ್ತು HEAD ಮೇಲೆ
ಚಲಾಯಿಸಲಾಗುತ್ತದೆ ಹಾಗೂ ಪ್ರತಿ-ಫೈಲ್ ಎಣಿಕೆಗಳ ವ್ಯತ್ಯಾಸವನ್ನು ಲೆಕ್ಕಿಸಲಾಗುತ್ತದೆ):

- **ತಡೆಗಟ್ಟುವ** — PR ತಾನು ಬದಲಾಯಿಸಿದ ಫೈಲ್ಗಳಲ್ಲಿ ಸೈಕ್ಲೊಮ್ಯಾಟಿಕ್/ಕಾಗ್ನಿಟಿವ್ ಉಲ್ಲಂಘನೆಗಳು ಅಥವಾ ಡೆಡ್ ಎಕ್ಸ್ಪೋರ್ಟ್ಗಳನ್ನು ಸೇರಿಸಿದೆ
  (ಲಾಗ್ನಲ್ಲಿ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ಸಲಹಾತ್ಮಕ** — ಸ್ಥಗಿತಗೊಳಿಸಿದ ಮೂಲಾಧಾರದ ವಿರುದ್ಧದ ಜಾಗತಿಕ ಒಟ್ಟು. ಆನುವಂಶಿಕವಾಗಿ ಬಂದ ವ್ಯತ್ಯಾಸವು
  ನಿರ್ದೋಷಿ PR ಅನ್ನು ಎಂದಿಗೂ ಕೆಂಪು ಎಂದು ಗುರುತಿಸುವುದಿಲ್ಲ; ಬಿಡುಗಡೆ ಸಮನ್ವಯದ ವೇಳೆ ಸರಿಪಡಿಸಲು ಈ ವ್ಯತ್ಯಾಸವನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು
  ಹೆಡ್ರೂಮ್ ಜಾಬ್ನಿಂದ ಮೇಲ್ವಿಚಾರಣೆ ಮಾಡಲಾಗುತ್ತದೆ.

`check:file-size` ತನ್ನದೇ ನಿಯಮಗಳ ಪ್ರಕಾರ ಬೇಸ್ ರೆಫ್ ಅನ್ನು ಬಳಸುತ್ತದೆ
(`scripts/check/check-file-size.mjs`, #8522): ಇದು ಟ್ರೀಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು ಸೋರ್ಸ್ ಮತ್ತು ಟೆಸ್ಟ್ ಫೈಲ್ ಅನ್ನು
ಪರಿಶೀಲಿಸುತ್ತದೆ, `git show` ಮೂಲಕ PR ಬೇಸ್ನಲ್ಲಿನ ಪ್ರತಿಯೊಂದರ ಸಾಲಿನ ಎಣಿಕೆಯನ್ನು ಓದುತ್ತದೆ ಮತ್ತು ಫೈಲ್ ತನ್ನ
ಬೇಸ್ಲೈನ್ ಗರಿಷ್ಠ ಮಿತಿ (`frozen` / `testFrozen`, ಅಥವಾ ಬೇಸ್ಲೈನ್ನ ಹೊರಗಿನ ಫೈಲ್ಗಾಗಿ `cap` / `testCap`)
ಮತ್ತು ಅದರ ಬೇಸ್ ಗಾತ್ರ — ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದಾದ ಮೌಲ್ಯವನ್ನು ಮೀರಿದಾಗ ಮಾತ್ರ ಅದನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ.
ಆದ್ದರಿಂದ ಬೇಸ್ನಲ್ಲಿ ಈಗಾಗಲೇ ಡ್ರಿಫ್ಟ್ ಆಗಿರುವ ಫೈಲ್ ನಿರಪರಾಧ PR ಅನ್ನು ಎಂದಿಗೂ ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ.

`check:boundary:ratchet` ತನ್ನ ಏಕೈಕ ಸಂಖ್ಯೆಗೆ ಅದೇ ನಿಯಮವನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ಈವೆಂಟ್ಗಳಲ್ಲಿ
`quality.yml` ಫಾಸ್ಟ್-ಗೇಟ್ಗಳು ಮತ್ತು `ci.yml` lint ಜಾಬ್ ಎರಡೂ PR ಬೇಸ್ SHA ಅನ್ನು ರವಾನಿಸುತ್ತವೆ, ಬೇಸ್ ಕಮಿಟ್ ಅನ್ನು
`git archive` ಎಕ್ಸ್ಪೋರ್ಟ್ನಿಂದ ಅಳೆಯಲಾಗುತ್ತದೆ, ಮತ್ತು ಅದರ `open-sse → src` ಎಡ್ಜ್
ಎಣಿಕೆಯು `metrics.boundaryOpenSseToSrc` ಹಾಗೂ ಬೇಸ್ನಲ್ಲಿನ ಎಣಿಕೆ—ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದಾದ ಮೌಲ್ಯವನ್ನು ಮೀರಿದಾಗ ಮಾತ್ರ PR ವಿಫಲವಾಗುತ್ತದೆ. ಮಿತಿಗಿಂತ
ಹೆಚ್ಚಿರುವ ಬೇಸ್ ಡ್ರಿಫ್ಟ್ ಅನ್ನು (`base drift herdado`) ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಅದರಿಂದ ದೋಷವಿಲ್ಲದ PR ಎಂದಿಗೂ ವಿಫಲವಾಗುವುದಿಲ್ಲ; push → main
ಸಂಪೂರ್ಣ ಮಿತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಮತ್ತು ಪರಿಹರಿಸಲಾಗದ ಬೇಸ್ SHA ಎಚ್ಚರಿಕೆಯೊಂದಿಗೆ ಅದನ್ನೇ ಪರ್ಯಾಯವಾಗಿ ಬಳಸುತ್ತದೆ.

`check:codeql-ratchet` **ರೆಪೊ ಸ್ಥಿತಿಯನ್ನು ಓದುತ್ತದೆ; ಅದನ್ನು ವೇಳಾಪಟ್ಟಿಯ ಪ್ರಕಾರ ರಿಫ್ರೆಶ್ ಮಾಡಲಾಗುತ್ತದೆ — ಪ್ರತಿ PR ಗೆ ಅಲ್ಲ.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ವರದಿ ಮಾಡುವ
`state: configured`, `schedule: weekly` ಎಂಬುದು GitHub ನ ಡೀಫಾಲ್ಟ್-ಸೆಟಪ್ ಸ್ಕ್ಯಾನ್ ಆಗಿದ್ದು,
ಪ್ರತಿ ಪುಶ್ಗೆ ನಡೆಯುವ ವಿಶ್ಲೇಷಣೆಯಲ್ಲ. ಪರಿಣಾಮ: ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸುವ PR ವಿಲೀನಗೊಂಡ ನಂತರವೂ,
ಮುಂದಿನ ನಿಗದಿತ ಸ್ಕ್ಯಾನ್ ನಡೆಯುವವರೆಗೆ ರ್ಯಾಚೆಟ್ ಹಳೆಯ, ಹೆಚ್ಚಿನ ಸಂಖ್ಯೆಯನ್ನೇ ಓದುತ್ತಿರುತ್ತದೆ —
ಆದ್ದರಿಂದ ಸ್ಕ್ಯಾನ್ ನವೀಕರಿಸುವವರೆಗೆ, ಸರಿಪಡಿಸಿದ PR ನ ಸ್ವಂತ ಫಾಲೋ-ಅಪ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಪ್ರತಿಯೊಂದು
ತೆರೆದ PR ನಲ್ಲಿಯೂ ಅದು ಹಿಂಜರಿತವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

**ಹಸ್ತಚಾಲಿತ ರಿಫ್ರೆಶ್**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ವಿಶ್ಲೇಷಣೆಯನ್ನು
ಮತ್ತೆ ಚಲಾಯಿಸಿ, ಕೆಲವೇ ನಿಮಿಷಗಳಲ್ಲಿ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಮರುಪ್ರಕಟಿಸುತ್ತದೆ. ಮೊದಲು `.github/workflows/codeql.yml`
ಓದಿ — GitHub ನ **"default setup" ಜೊತೆಗೆ ಅದು ಸಂಘರ್ಷಿಸುವುದರಿಂದಲೇ** ಇದು `workflow_dispatch`-ಗೆ ಮಾತ್ರ

processed when the default setup is enabled`). `push`/`pull_request`/

7 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸಿತು (ಅಳೆಯಲಾದ ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳು 13 → 6); ಅದಕ್ಕೆ ಹೊಂದುವಂತೆ PR #12530

## ರಿಲೀಸ್-ಮಟ್ಟದ ರ್ಯಾಚೆಟ್ ಡ್ರಿಫ್ಟ್ (WS5.5, v3.8.49)

ಅಂದರೆ, ಮರ್ಜ್ಗಳ ಸಂಯೋಜನೆಯು ಅದನ್ನು ಹಿಮ್ಮೆಟ್ಟಿಸಿದೆ ಮತ್ತು ಯಾವುದೇ ಒಂದು PR ತನ್ನದೇ ಬ್ರಾಂಚ್ನಲ್ಲಿ ಆ
ರಿಗ್ರೆಷನ್ ಅನ್ನು ಪುನರುತ್ಪಾದಿಸುವುದಿಲ್ಲವಾದರೆ — ಅದನ್ನು ಸರಿಪಡಿಸುವ ಹೊಣೆ **ರಿಲೀಸ್ ಕ್ಯಾಪ್ಟನ್ಗೆ, ಒಮ್ಮೆ ಮಾತ್ರ,
ರಿಲೀಸ್ ಬ್ರಾಂಚ್ನಲ್ಲಿ** ಸೇರಿದೆ: ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್/ರಿಫ್ಯಾಕ್ಟರ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ; ದಾಖಲಿಸಲಾದ
ಸಮರ್ಥನೆ ನಮೂದಿನೊಂದಿಗೆ ಮಾತ್ರ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಿ. ಸಂಯೋಜನೆಯಿಂದಾದ ಡ್ರಿಫ್ಟ್ ಅನ್ನು ಕೊಡುಗೆದಾರರ PR ಮೇಲೆ ಎಂದಿಗೂ
ಹೊರಿಸಬೇಡಿ ಮತ್ತು ಪ್ರತಿ-PR ಗೆ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಬೇಡಿ (ಅದು ನೈಜ ರಿಗ್ರೆಷನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ). ಮೊದಲು ವ್ಯತ್ಯಾಸವನ್ನು ಗುರುತಿಸಿ:
ನಿಮ್ಮ PR ಅದಕ್ಕೆ ಕಾರಣವೆಂದು ಊಹಿಸುವ ಮೊದಲು ಪ್ರೋಬ್ ವರ್ಕ್ಟ್ರೀಯಲ್ಲಿ ಶುದ್ಧ ಟಿಪ್ ವಿರುದ್ಧದ ಕೆಂಪು ಸ್ಥಿತಿಯನ್ನು ಪುನರುತ್ಪಾದಿಸಿ.

| ರವಾನೆ     | ರಿಲೀಸ್ ಬ್ರಾಂಚ್ ವಿರುದ್ಧ ಯಾವಾಗಲೂ ಪ್ರಸ್ತುತವಾಗಿರುವ ಒಂದೇ PR — ಬಲವಂತವಾಗಿ ಅಪ್ಡೇಟ್ ಮಾಡಲಾಗುತ್ತದೆ, ಎಂದಿಗೂ ಸ್ಪ್ಯಾಮ್ ಮಾಡುವುದಿಲ್ಲ |

ಬ್ಯಾಂಕಿಂಗ್ ಅನ್ನು ಪ್ರತಿ-push ಬದಲಿಗೆ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ ಮಾಡಲಾಗುತ್ತದೆ, ಏಕೆಂದರೆ ಇದಕ್ಕೆ ಯಾವುದೇ ಲೇಟೆನ್ಸಿ ಅವಶ್ಯಕತೆ ಇಲ್ಲ
(8 ಗಂಟೆಗಳೊಳಗೆ ಬ್ಯಾಂಕ್ ಮಾಡಿದ ಇಳಿಕೆ ಸಾಕು), ಆದರೆ ಪ್ರತಿ-ಮರ್ಜ್ ಚಾಲನೆಯು ಮರ್ಜ್ ಅಭಿಯಾನಗಳ ಸಮಯದಲ್ಲಿ PR ಬ್ರಾಂಚ್ ಅನ್ನು
ಪದೇಪದೇ ಮರುನಿರ್ಮಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಬಾರಿ ಪೂರ್ಣ ESLint ಸ್ಕ್ಯಾನ್ನ ವೆಚ್ಚವನ್ನು ಭರಿಸುತ್ತದೆ. ಪತ್ತೆಹಚ್ಚುವಿಕೆಯು
push (`release-green`) ನಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ; ಬ್ಯಾಂಕಿಂಗ್ ಮಾತ್ರ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ ನಡೆಯುತ್ತದೆ.

### ಸುರಕ್ಷತಾ ಪರಿಶೀಲಕ

ಜಾಬ್ ಮೇಲ್ವಿಚಾರಣೆಯಿಲ್ಲದೆ ಬೇಸ್ಲೈನ್ಗಳಿಗೆ ಬರೆಯುತ್ತದೆ, ಆದ್ದರಿಂದ `verify-ratchet-bank.mjs` ಅದನ್ನು
ಸ್ವೀಕಾರಾರ್ಹವಾಗಿಸುತ್ತದೆ. ಅದು `--update` ನಂತರದ ಟ್ರೀ ಅನ್ನು `HEAD` ವಿರುದ್ಧ diff ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು
ಬದಲಾವಣೆಯೂ ಕೆಳಗಿನವುಗಳಲ್ಲಿ ಒಂದಾಗಿರದಿದ್ದರೆ, **ಯಾವುದೇ ಕಮಿಟ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು ಜಾಬ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ**
— ಯಾವುದೇ PR ತೆರೆಯುವುದಿಲ್ಲ:

- `frozen` / `testFrozen` ಸಂಖ್ಯಾತ್ಮಕ ನಮೂದನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ** ಅಥವಾ **ತೆಗೆದುಹಾಕಲಾಗಿದೆ**
- `complexity-baseline.json` → `count` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**

ಬೇರಾವುದೇ ಬದಲಾವಣೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ: ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸುವುದು, ನಮೂದನ್ನು ಸೇರಿಸುವುದು, `cap`/`testCap` ಅನ್ನು ಬದಲಿಸುವುದು ಅಥವಾ
`_rebaseline_*` ಟಿಪ್ಪಣಿಯನ್ನು ಅಳಿಸುವುದು/ಮರುಬರೆಯುವುದು (ಪ್ರತಿ ಗರಿಷ್ಠ ಮಿತಿ ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ ಎಂಬುದಕ್ಕೆ ಆ ಟಿಪ್ಪಣಿಗಳು ಆಡಿಟ್ ದಾಖಲೆಯಾಗಿದ್ದು,
ಫೈಲ್ ನಮೂದುಗಳಂತೆಯೇ ಅದೇ `frozen` ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ).
ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಬಲ್ಲ ಬಾಟ್ ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಗಿಂತ ಖಂಡಿತವಾಗಿಯೂ ಕೆಟ್ಟದಾಗಿರುತ್ತದೆ. ರಿಗ್ರೆಷನ್
ಗಾರ್ಡ್: `tests/unit/verify-ratchet-bank.test.ts`.

ಜಾಬ್ ಎಂದಿಗೂ `release/*` ಗೆ push ಮಾಡುವುದಿಲ್ಲ — ಒಬ್ಬ ವ್ಯಕ್ತಿ PR ಅನ್ನು ಮರ್ಜ್ ಮಾಡುತ್ತಾರೆ, ಆದ್ದರಿಂದ ತಪ್ಪಾದ ಮಾಪನವು
ಪರಿಶೀಲಿಸದೆ ಸೇರಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಅನುಮತಿಪಟ್ಟಿ ನೀತಿ

ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉಲ್ಲಂಘನೆಗಳಿಂದ ವಿಫಲವಾಗಬಾರದ ಪ್ರತಿಯೊಂದು ಗೇಟ್ ಸ್ಥಿರೀಕೃತ ಅನುಮತಿಪಟ್ಟಿಯನ್ನು ಬಳಸುತ್ತದೆ
(ಉದಾ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). ನೀತಿ ಹೀಗಿದೆ:

**ಮೂಲ ಕಾರಣವನ್ನು ಸರಿಪಡಿಸಿ; ಉಲ್ಲಂಘನೆಯು ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದು, ಅದೇ PR ನಲ್ಲಿ
ಸರಿಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ ಮಾತ್ರ ಅನುಮತಿಪಟ್ಟಿಯನ್ನು ಬಳಸಿ.**

ಅನುಮತಿಪಟ್ಟಿಗೆ ನಮೂದನ್ನು ಸೇರಿಸುವಾಗ:

1. ಸಮರ್ಥನೆಯೊಂದಿಗೆ ಒಂದು ಕಾಮೆಂಟ್ ಅನ್ನು ಸೇರಿಸಿ.
2. ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯನ್ನು ಉಲ್ಲೇಖಿಸಿ (ಉದಾ., `// #3498 — Phase 2 feature, not yet implemented`).
3. ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸುವ ಅದೇ PR ನಲ್ಲಿ ನಮೂದನ್ನು ತೆಗೆದುಹಾಕಿ — ಸಕ್ರಿಯ ಉಲ್ಲಂಘನೆಯನ್ನು ಇನ್ನು ಮುಂದೆ
   ನಿಗ್ರಹಿಸದ ಹಳತಾದ ನಮೂದು ಸ್ವತಃ ಒಂದು ದೋಷವಾಗಿದೆ (ಅನುಷ್ಠಾನಗೊಂಡ ನಂತರ, ಅನಾಥ ಅನುಮತಿಪಟ್ಟಿ ನಮೂದಿನ
   ಮೇಲೆ 6A.3 ಹಳತಾದ-ಜಾರಿಗೊಳಿಸುವಿಕೆಯು ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ).

ಪರೀಕ್ಷೆಗಳು ಬೇಗ ಉತ್ತೀರ್ಣವಾಗುವಂತೆ ಮಾಡಲು ಅನುಮತಿಪಟ್ಟಿ ನಮೂದುಗಳನ್ನು ಸೇರಿಸಬೇಡಿ. ಬೆಳೆಯುತ್ತಿರುವ
ಅನುಮತಿಪಟ್ಟಿಯೊಂದಿಗೆ ಹಸಿರು ಗೇಟ್ ಗುಣಮಟ್ಟದ ಬಗ್ಗೆ ತಪ್ಪು ಭರವಸೆಯಾಗಿದೆ.

### ನಿಮ್ಮ PR ನಲ್ಲಿ ಗೇಟ್ ವಿಫಲವಾದಾಗ

1. **ಗೇಟ್ ಔಟ್ಪುಟ್ ಅನ್ನು ಎಚ್ಚರಿಕೆಯಿಂದ ಓದಿ** — ಯಾವ ಫೈಲ್ ಅಥವಾ ಸಿಂಬಲ್ ನಿಯಮವನ್ನು
   ಉಲ್ಲಂಘಿಸಿದೆ ಎಂಬುದನ್ನು ಅದು ನಿಖರವಾಗಿ ತಿಳಿಸುತ್ತದೆ.
2. **ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸಿ** — ಹೆಚ್ಚಿನ ಗೇಟ್ಗಳು ನಿರ್ಧಾರಾತ್ಮಕ ಫೈಲ್ಸಿಸ್ಟಮ್ ಪರಿಶೀಲನೆಗಳಾಗಿದ್ದು,
   ಕೋಡ್ ಸರಿಯಾದ ತಕ್ಷಣವೇ ಉತ್ತೀರ್ಣವಾಗುತ್ತವೆ.
3. **ಉಲ್ಲಂಘನೆಯು ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದರೆ** (ಅಂದರೆ, ನೀವು ಅದನ್ನು ಪರಿಚಯಿಸಿಲ್ಲ, ಆದರೆ ಈಗ ಗೇಟ್
   ಅದನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ): ಸಮರ್ಥನೆಯ ಕಾಮೆಂಟ್ ಮತ್ತು ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯೊಂದಿಗೆ ಅನುಮತಿಪಟ್ಟಿ ನಮೂದನ್ನು ಸೇರಿಸಿ.
4. **ಗೇಟ್ ಒಂದು ರ್ಯಾಚೆಟ್ ಆಗಿದ್ದರೆ** (ಕವರೇಜ್, ESLint ಎಚ್ಚರಿಕೆಗಳು, ನಕಲು, ಸಂಕೀರ್ಣತೆ):
   ನಿಮ್ಮ ಬದಲಾವಣೆಯು ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹದಗೆಡಿಸಿದೆ. ಆಧಾರವಾಗಿರುವ ಸಮಸ್ಯೆಯನ್ನು ಸರಿಪಡಿಸಿ ಅಥವಾ (ಅಪರೂಪವಾಗಿ),
   ಬದಲಾವಣೆಯು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದ್ದು ಮೆಟ್ರಿಕ್ನ ಕುಸಿತವು ಸ್ವೀಕಾರಾರ್ಹವಾಗಿದ್ದರೆ
   `npm run quality:ratchet -- --update` ಅನ್ನು ಚಲಾಯಿಸಿ — ಆದರೆ ಏಕೆ ಎಂಬುದನ್ನು PR ವಿವರಣೆಯಲ್ಲಿ ದಾಖಲಿಸಿ.
5. **ಸಲಹಾತ್ಮಕ ಗೇಟ್ಗಳು** (`continue-on-error: true`) ಮಾಹಿತಿಗಾಗಿ ಮಾತ್ರ — ಅವು ವಿಲೀನವನ್ನು
   ತಡೆಯುವುದಿಲ್ಲ, ಆದರೆ CI ಸಾರಾಂಶದಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಆದರೂ ಅವುಗಳನ್ನು ಸರಿಪಡಿಸಿ.

## ಹೊಸ ಗೇಟ್ ಸೇರಿಸುವುದು

1. `scripts/check/check-<name>.mjs` (ಅಥವಾ `.ts`) ರಚಿಸಿ. ನೀತಿ ಗೇಟ್ಗಳು 0/1 ಸ್ಥಿತಿಯೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತವೆ.
   ರ್ಯಾಚೆಟ್-ಶೈಲಿಯ ಗೇಟ್ಗಳು `collect-metrics.mjs` ಮೂಲಕ `quality-metrics.json` ಗೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹೊರಸೂಸುತ್ತವೆ.
2. `package.json` ಗೆ `"check:<name>": "node scripts/check/check-<name>.mjs"` ಅನ್ನು ಸೇರಿಸಿ, ಮತ್ತು
   `config/quality/gate-manifest.json` ನಲ್ಲಿ ಅಲಿಯಾಸ್ ಹಾಗೂ ಅದರ ನಿಖರವಾದ ಕಮಾಂಡ್ ಅನ್ನು ಸಮನ್ವಯಗೊಳಿಸಿ.
   ಈಗಿರುವ ಮೌಲ್ಯೀಕರಣ ಅಲಿಯಾಸ್ ಅನ್ನು ಬದಲಾಯಿಸುವಾಗ ಅಥವಾ ತೆಗೆದುಹಾಕುವಾಗಲೂ ಇದೇ ಸಮನ್ವಯವನ್ನು ಅನ್ವಯಿಸಿ.
   `npm run check:gate-manifest` ಅನ್ನು ಚಲಾಯಿಸಿ; pre-commit hook ಮತ್ತು CI ಬದಲಾವಣೆ ವರ್ಗೀಕರಣವು
   ಈ ಒಪ್ಪಂದವನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ.
3. ಸೂಕ್ತ ಜಾಬ್ ಅಡಿಯಲ್ಲಿ `.github/workflows/ci.yml` ನಲ್ಲಿ ಅದನ್ನು ಜೋಡಿಸಿ
   (ನೀತಿ → `lint` ಅಥವಾ `docs-sync-strict`; ರ್ಯಾಚೆಟ್ → `quality-gate`).
4. ಅದಕ್ಕೆ ಅನುಮತಿ ಪಟ್ಟಿ ಇದ್ದರೆ, ಹಳತಾದ ನಮೂದುಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪತ್ತೆಯಾಗುವಂತೆ
   `scripts/check/lib/allowlist.mjs` ನಿಂದ `reportStaleEntries()` ಅನ್ನು ಅನ್ವಯಿಸಿ.
5. ಗೇಟ್ನ ಪತ್ತೆ ತರ್ಕವನ್ನು ಒಳಗೊಂಡ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/build/` ನಲ್ಲಿ ಬರೆಯಿರಿ.
6. ಈ ಡಾಕ್ಯುಮೆಂಟ್ ಅನ್ನು ನವೀಕರಿಸಿ (ಸಂಬಂಧಿತ ಜಾಬ್ ಟೇಬಲ್ಗೆ ಒಂದು ಸಾಲನ್ನು ಸೇರಿಸಿ).

## ಏಜೆಂಟ್ ಉಪಕರಣಗಳು: LSP-in-the-loop (ಆಯ್ಕೆಯ ಮೇರೆಗೆ)

CI ಗೇಟ್ಗಳ ಜೊತೆಗೆ, OmniRoute ಒಂದು **ಆಯ್ಕೆಯ ಮೇರೆಗೆ ಬಳಸಬಹುದಾದ** `agent-lsp` ಸ್ಕ್ಯಾಫೋಲ್ಡ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
(ಪ್ರಾಜೆಕ್ಟ್-ಮಟ್ಟದ `.mcp.json`, Fase 7 Task 15). ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ಗಳಿಗೆ TypeScript ಭಾಷಾ ಸರ್ವರ್ ಅನ್ನು
ಒದಗಿಸಲು `.mcp.json` ರಚಿಸಿ, ಇದರಿಂದ ಅವು ಕೋಡ್ ಬರೆಯುವ **ಮೊದಲು** ಸಂಕೇತಗಳು /
ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಗಳನ್ನು ಪರಿಹರಿಸುತ್ತವೆ — ಮೂಲದಲ್ಲೇ "ಕಲ್ಪಿತ ಸಂಕೇತ" ದೋಷಗಳನ್ನು ಕಡಿತಗೊಳಿಸುವ
`typecheck:core` ಗೆ ಕಂಪೈಲ್-ಬಿಫೋರ್-ಕ್ಲೇಮ್ ಸಹಚರ. ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
ಸ್ವಯಂ-ಲೋಡ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ (MCP↔LSP ಬ್ರಿಡ್ಜ್ ಅನ್ನು ನೀವು ಆಯ್ಕೆಮಾಡಿ ಪರಿಶೀಲಿಸುತ್ತೀರಿ); ದೋಷಪೂರಿತ ನಮೂದು
ಕೇವಲ ಸಂಪರ್ಕ ದೋಷವನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸೆಷನ್ಗಳನ್ನು ಎಂದಿಗೂ ಸ್ಥಗಿತಗೊಳಿಸುವುದಿಲ್ಲ.

## ತರ್ಕಬದ್ಧಗೊಳಿಸುವಿಕೆ ಬ್ಯಾಕ್ಲಾಗ್ (ROI ಪರಿಶೀಲನೆ — ಹಂತ 9 ಅಲೆ 3)

ಈ ಇನ್ವೆಂಟರಿಯನ್ನು 2026-06-17 ರಂದು `ci.yml` ಗೆ ಹೋಲಿಸಿ ಸಮನ್ವಯಗೊಳಿಸಲಾಗಿದೆ (ಹಿಂದಿನ ಆವೃತ್ತಿಯಲ್ಲಿ
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` ಬಿಟ್ಟುಹೋಗಿದ್ದವು). ಸಮನ್ವಯಗೊಳಿಸಿದ ಗುಂಪಿನ ROI ಪರಿಶೀಲನೆಯು
ಕೆಳಗಿನ ತರ್ಕಬದ್ಧಗೊಳಿಸುವಿಕೆ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಗುರುತಿಸಿದೆ. **ವಿಲೀನಗಳು ಯಾಂತ್ರಿಕ CI
ಬದಲಾವಣೆಗಳಾಗಿವೆ; ಫ್ಲಿಪ್ಗಳು/ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ಆಪರೇಟರ್ಗಾಗಿ ಕಾಯ್ದಿರಿಸಲಾದ ನೀತಿ ನಿರ್ಧಾರಗಳಾಗಿವೆ.** ಕೆಳಗಿನ ಯಾವುದನ್ನೂ
ಇನ್ನೂ ಅನ್ವಯಿಸಲಾಗಿಲ್ಲ.

**ಮೇಲೆ ದಾಖಲಿಸದಿರುವವು ಸಹ** (ಸಲಹಾತ್ಮಕ, ಕಡಿಮೆ ಸಂಕೇತ): `docs-lint` ಜಾಬ್
(markdownlint + Vale, ಸಂಪೂರ್ಣ ಜಾಬ್ `continue-on-error`) ಮತ್ತು ಪ್ರತ್ಯೇಕ ಸ್ಕ್ಯಾನರ್ ವರ್ಕ್ಫ್ಲೋಗಳು
`semgrep.yml` / `codeql.yml` / `scorecard.yml`. `semgrepFindings: 0` ಎಂಬುದು
`quality-baseline.json` ನಲ್ಲಿದೆ, ಆದರೆ `ci.yml` ನಲ್ಲಿ ತಡೆಹಿಡಿಯುವ ರ್ಯಾಚೆಟ್ಗೆ ಸಂಪರ್ಕಿಸಲಾಗಿಲ್ಲ — ಈ ಮೆಟ್ರಿಕ್
ಪ್ರಸ್ತುತ ಅನಾಥವಾಗಿದೆ.

### ವಿಲೀನ / ನಕಲು ನಿವಾರಣೆ (ಯಾಂತ್ರಿಕ, ಕಡಿಮೆ ಅಪಾಯ)

ಪ್ರತಿಯೊಂದು ಅಭ್ಯರ್ಥಿಯನ್ನು 2026-06-17 ರ ಲೈವ್ ಗೇಟ್ ಸ್ಥಿತಿಗೆ ಹೋಲಿಸಿ ಮೌಲ್ಯೀಕರಿಸಲಾಗಿದೆ (ನಂಬಿ-ಆದರೆ-ಪರಿಶೀಲಿಸಿ);
ಹಲವಾರು "ಸ್ಪಷ್ಟ" ವಿಲೀನಗಳು ಅಡಗಿದ ತಾಂತ್ರಿಕ ಸಾಲವನ್ನು ಹೊಂದಿರುವುದು ಕಂಡುಬಂದಿದ್ದು, ಅವು **ಸ್ವಚ್ಛ ಪರ್ಯಾಯಗಳಲ್ಲ**.

- **`check:docs-sync` ಎರಡು ಬಾರಿ ರನ್ ಆಗುತ್ತದೆ** — `lint` ಜಾಬ್ನಲ್ಲಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಮತ್ತು `check:docs-all` (`docs-sync-strict`) ಒಳಗೆ ಹಾಗೂ husky pre-commit ಹುಕ್ನಲ್ಲಿ ಮತ್ತೊಮ್ಮೆ. ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** — ಪ್ರತ್ಯೇಕ `lint` ಆಹ್ವಾನವನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ.
- **CVE ಸ್ಕ್ಯಾನಿಂಗ್** — ❌ **ಸ್ವಚ್ಛ ವಿಲೀನವಲ್ಲ.** `audit:deps` ಎಲ್ಲಾ ಐದು ಲಾಕ್ಫೈಲ್ಗಳಲ್ಲಿ ಗಂಭೀರ ಸಲಹೆಗಳು ಮತ್ತು ಅಪೂರ್ಣ ಆಡಿಟ್ಗಳನ್ನು ತಡೆಯುತ್ತದೆ, ಹಾಗೆಯೇ ಪ್ರಸ್ತುತ ನೀತಿಯಡಿ ಹೆಚ್ಚಿನ ತೀವ್ರತೆಯ ಸಲಹೆಗಳನ್ನು ಎಚ್ಚರಿಕೆಗಳಾಗಿ ವರದಿ ಮಾಡುತ್ತದೆ; `check:vuln-ratchet` (osv) ಚೆಕ್-ಇನ್ ಮಾಡಲಾದ ಬೇಸ್ಲೈನ್ಗೆ ಹೋಲಿಸಿದಾಗ _ರಿಗ್ರೆಷನ್_ ಕಂಡುಬಂದರೆ ಮಾತ್ರ ವಿಫಲವಾಗುತ್ತದೆ ಮತ್ತು ಅಗತ್ಯವಿರುವಾಗ ಮಾಪನಗಳು ಕಾಣೆಯಾಗಿದ್ದರೆ ತಿರಸ್ಕರಿಸುತ್ತದೆ. ಅರ್ಥವ್ಯತ್ಯಾಸವಿದೆ — `audit:deps` ಅನ್ನು ತೆಗೆದುಹಾಕಿದರೆ ನಿರಪೇಕ್ಷ ಗಂಭೀರ ಗೇಟ್ ಮತ್ತು ಸ್ವತಂತ್ರ ಪ್ಯಾಕೇಜ್ ಆಡಿಟ್ ರಸೀದಿಗಳು ಕಳೆದುಹೋಗುತ್ತವೆ. ಎರಡನ್ನೂ ಉಳಿಸಿ.
- **ಚಕ್ರ ಪತ್ತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (#15159 G-01/G-02). ಇಲ್ಲಿನ ಹಳೆಯ ಪಠ್ಯವು `check:cycles` ಅನ್ನು "ಹಸಿರು, ಆಯ್ದ" ಗೇಟ್ ಎಂದು ಕರೆದಿತ್ತು ಮತ್ತು `check:circular-deps` (dpdm) 91 ಚಕ್ರಗಳನ್ನು ವರದಿ ಮಾಡಿದ್ದರಿಂದ ಅದನ್ನು ತಡೆಹಿಡಿಯುವ ಗೇಟ್ ಆಗಿ ಉಳಿಸುವುದನ್ನು ಸಮರ್ಥಿಸಿತ್ತು. ಆ ಹಸಿರು ಸ್ಥಿತಿ **ತಪ್ಪು ಹಸಿರು** ಆಗಿತ್ತು: `check:cycles` 5 ಉಪಡೈರೆಕ್ಟರಿಗಳನ್ನು (450 ಫೈಲ್ಗಳು) ಸ್ಕ್ಯಾನ್ ಮಾಡಿತ್ತು, ಸ್ಥಿರ `import|export … from` ಅನ್ನು ಮಾತ್ರ ಹೊಂದಿಸಿತ್ತು ಮತ್ತು ಪ್ರತಿಯೊಂದು `@/` ಹಾಗೂ `@omniroute/open-sse/` ಸ್ಪೆಸಿಫೈಯರ್ ಅನ್ನು ಕೈಬಿಟ್ಟಿತ್ತು; ಆದ್ದರಿಂದ ರೆಪೊದಲ್ಲಿ ಪ್ರಾಬಲ್ಯ ಹೊಂದಿದ್ದ dynamic-import + alias ಚಕ್ರಗಳನ್ನು ಅದು ನೋಡಲು ಸಾಧ್ಯವಾಗಲಿಲ್ಲ. ಸರಿಪಡಿಸಲಾಗಿದೆ: ಗೇಟ್ ಈಗ `src` + `open-sse` (5023 ಫೈಲ್ಗಳು) ಮೂಲಕ ಸಾಗುತ್ತದೆ, TypeScript AST ಯಿಂದ ಸ್ಪೆಸಿಫೈಯರ್ಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ (ಆದ್ದರಿಂದ `import("…")` ಅನ್ನು ಎಣಿಸಲಾಗುತ್ತದೆ ಮತ್ತು type-position `typeof import("…")` ಅನ್ನು ಎಣಿಸಲಾಗುವುದಿಲ್ಲ) ಮತ್ತು tsconfig `paths` ಅನ್ನು ರಿಸಾಲ್ವ್ ಮಾಡುತ್ತದೆ. ಇದು 0 ಅಲ್ಲ, **14** ಚಕ್ರಗಳನ್ನು ಕಂಡುಹಿಡಿಯುತ್ತದೆ. ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ 14 ಚಕ್ರಗಳನ್ನು ಗೇಟ್ PR ನಲ್ಲಿ ಸರಿಪಡಿಸಲಾಗದ ಕಾರಣ, `check:cycles` ಈಗ ಒಂದು **ರ್ಯಾಚೆಟ್** ಆಗಿದೆ (`--ratchet`, `quality-baseline.json` ನಲ್ಲಿ ಮಿತಿ `metrics.cycles.value = 14`, `direction: down`) — ಇದು ಯಾವುದೇ _ರಿಗ್ರೆಷನ್_ ಅನ್ನು ತಡೆಯುತ್ತದೆ ಮತ್ತು ಎಣಿಕೆಯು ಕಡಿಮೆಯಾಗಲು ಮಾತ್ರ ಸಾಧ್ಯ. CI `npm run check:cycles:ratchet` ಅನ್ನು ರನ್ ಮಾಡುತ್ತದೆ. ಕ್ರಮೇಣ ಕಡಿಮೆಗೊಳಿಸುವಿಕೆಯು **A-01** ಜೊತೆಗೆ ಸಾಗುತ್ತದೆ. `check:circular-deps` (dpdm) ವಿಶಾಲವಾದ ಎರಡನೇ ಅಭಿಪ್ರಾಯವಾಗಿ ಸಲಹಾತ್ಮಕವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ.
- **ಸಂಕೀರ್ಣತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ಒಂದೇ ESLint ಸುತ್ತಾಟ, ruleId ಪ್ರಕಾರ ಎಣಿಕೆ ಮಾಡುತ್ತದೆ; ಇದರಿಂದ cyclomatic+max-lines ಮತ್ತು cognitive ಬೇಸ್ಲೈನ್ಗಳು ಸ್ವತಂತ್ರವಾಗಿ ಉಳಿಯುತ್ತವೆ; ಪ್ರತ್ಯೇಕ `check:complexity` / `check:cognitive-complexity` ಸ್ಥಳೀಯ `--update` ಗಾಗಿ ಉಳಿಯುತ್ತವೆ.
- **`/api` ಆಂಟಿ-ಹ್ಯಾಲ್ಯೂಸಿನೇಷನ್** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ಯ ಒಂದೇ FS ಇನ್ವೆಂಟರಿ, openapi-routes + docs-symbols ಇನ್ನೂ ಸ್ವತಂತ್ರವಾಗಿ ವರದಿ ಮಾಡುತ್ತವೆ; ಪ್ರತ್ಯೇಕವುಗಳು ಸ್ಥಳೀಯ ರನ್ಗಳಿಗಾಗಿ ಉಳಿಯುತ್ತವೆ.
- **`check:node-runtime` 11 ಜಾಬ್ಗಳಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ** — ⚠️ **ಕಡಿಮೆ ROI.** ಪ್ರತಿಯೊಂದೂ ಪ್ರತ್ಯೇಕ ರನ್ನರ್ ಆಗಿದೆ ಮತ್ತು ಪರಿಶೀಲನೆಯು <1s ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ; ಅಗ್ಗದ ಪ್ರತಿ-ಜಾಬ್ ರಕ್ಷಣೆಯನ್ನು ಕಳೆದುಕೊಳ್ಳುವುದಕ್ಕೆ ಪ್ರತಿಯಾಗಿ ಒಟ್ಟು ಉಳಿತಾಯ ~10s ಮಾತ್ರ. ಈ ಬದಲಾವಣೆಯ ತೊಂದರೆಗೆ ಇದು ಯೋಗ್ಯವಲ್ಲ.
- **CI lint ನಲ್ಲಿ `typecheck:noimplicit:core`** — ✅ **lint ಜಾಬ್ನಿಂದ ತೆಗೆದುಹಾಕಲಾಗಿದೆ** (ಇದು ಸಲಹಾತ್ಮಕ `continue-on-error` ಆಗಿತ್ತು); ತಡೆಹಿಡಿಯುವ ಟೈಪ್ ಮೇಲ್ಮೈ `typecheck:core` + `check:type-coverage` ಆಗಿದೆ. ಸ್ಥಳೀಯ ಸ್ಕ್ರಿಪ್ಟ್ ಅನ್ನು ಉಳಿಸಲಾಗಿದೆ.

### ಫ್ಲಿಪ್ / ನಿರ್ಧಾರ (ಆಪರೇಟರ್ ನೀತಿ)

- `check:openapi-security-tiers` (ಸಲಹಾತ್ಮಕ) — ❌ **ಸ್ವಚ್ಛವಾಗಿ ಫ್ಲಿಪ್ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ.** ಇದು 0 ಸ್ಥಿತಿಯೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ, ಆದರೆ `LOCAL_ONLY_API_PREFIXES` ಅಡಿಯಲ್ಲಿರುವ ಹಲವಾರು `traffic-inspector` ರೂಟ್ಗಳಲ್ಲಿ `x-loopback-only: true` ಅನೋಟೇಶನ್ ಇಲ್ಲವೆಂದು ಎಚ್ಚರಿಸುತ್ತದೆ. ಇದನ್ನು ಜಾರಿಗೊಳಿಸುವ ಮೊದಲು ಆ ಅನೋಟೇಶನ್ಗಳನ್ನು `openapi.yaml` ಗೆ ಸೇರಿಸಬೇಕು.
- `typecheck:noimplicit:core` (ಸಲಹಾತ್ಮಕ) — ತಡೆಹಿಡಿಯುವ `check:type-coverage` ರ್ಯಾಚೆಟ್ನಿಂದ ಬಹುತೇಕ ಒಳಗೊಳ್ಳಲ್ಪಟ್ಟಿದೆ. ಇದನ್ನು ರ್ಯಾಚೆಟ್ಗೆ ಫ್ಲಿಪ್ ಮಾಡಿ ಅಥವಾ ಅನಗತ್ಯವಾದ ಎರಡನೇ `tsc` ಪಾಸ್ ಅನ್ನು ತೆಗೆದುಹಾಕಿ.
- `test:vitest:ui` (ಈಗ **ತಡೆಹಿಡಿಯುವ**) — ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ವೈಫಲ್ಯಗಳನ್ನು `vitest.config.ts` ನಲ್ಲಿ `// #8618` ಟ್ರ್ಯಾಕಿಂಗ್ ಕಾಮೆಂಟ್ಗಳೊಂದಿಗೆ ಸ್ಪಷ್ಟವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ; ಹೊಸ ವೈಫಲ್ಯಗಳು ಜಾಬ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
- `check:secrets` (gitleaks, ತಡೆಹಿಡಿಯುವ ರ್ಯಾಚೆಟ್) — ಪ್ರಸ್ತುತ ಮಿತಿಯು `quality-baseline.json` ನಲ್ಲಿರುವ `metrics.secretFindings` ಆಗಿದೆ. ಯಾವುದೇ ವಿನಾಯಿತಿಗೆ ಸಮರ್ಥಿಸಲಾದ `.gitleaks.toml` ನಮೂದು ಅಗತ್ಯವಿದೆ; ಲಭ್ಯವಿಲ್ಲದ ಮಾಪನವು INCOMPLETE ಆಗಿರುತ್ತದೆ. ಈ ಸ್ಕ್ಯಾನ್ GitHub ನ ಮೂಲ secret scanning ಮತ್ತು `check:public-creds` ಗೆ ಪೂರಕವಾಗಿದೆ.
- `check:pr-evidence` (ತಡೆಹಿಡಿಯುವ, PR-body ಗದ್ಯದಲ್ಲಿ greps ಮಾಡುತ್ತದೆ) — ತಪ್ಪು ಧನಾತ್ಮಕ ಫಲಿತಾಂಶಗಳ ಹೆಚ್ಚಿನ ಅಪಾಯವಿದೆ; ತೆಗೆದುಹಾಕಿದರೆ Hard Rule #18 ಜಾರಿಯನ್ನು ದುರ್ಬಲಗೊಳಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಇದು ನೈಜ ನೀತಿ ನಿರ್ಧಾರವಾಗಿದೆ.
- `semgrep` (ಸಲಹಾತ್ಮಕ ಪ್ರತ್ಯೇಕ) — OWASP ಕುಟುಂಬಗಳ ವಿಷಯದಲ್ಲಿ CodeQL ಜೊತೆಗೆ ಅತಿಕ್ರಮಿಸುತ್ತದೆ; ಇದರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ರ್ಯಾಚೆಟ್ಗೆ ಸಂಪರ್ಕಿಸಿ ಅಥವಾ ತೆಗೆದುಹಾಕಿ.
