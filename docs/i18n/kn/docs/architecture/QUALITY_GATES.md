ಈ ದಸ್ತಾವೇಜು OmniRouteನಲ್ಲಿನ ಎಲ್ಲಾ CI ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳಿಗೆ ಅಧಿಕೃತ ಉಲ್ಲೇಖವಾಗಿದೆ.
ಇದು ಪ್ರತಿಯೊಂದು ಗೇಟ್, ಅದು ಏನನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ, ಅದು ಯಾವ CI ಜಾಬ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ, ಅದು
ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ ಅಥವಾ ಪಾಸ್/ಫೇಲ್ ನೀತಿಯನ್ನು ಬಳಸುತ್ತದೆಯೇ ಮತ್ತು ಅದು ಬಿಲ್ಡ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆಯೇ ಅಥವಾ ಸಲಹಾತ್ಮಕವಾಗಿದೆಯೇ ಎಂಬುದನ್ನು ವಿವರಿಸುತ್ತದೆ.

ಸಂಕ್ಷಿಪ್ತ ಸಾರಾಂಶ ಮತ್ತು ಅನುಮತಿಪಟ್ಟಿ ನೀತಿಗಾಗಿ, `AGENTS.md`ನಲ್ಲಿರುವ "ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳು ಮತ್ತು ರ್ಯಾಚೆಟ್ಗಳು" ವಿಭಾಗವನ್ನು
ನೋಡಿ. ಇದೇ ಸಿಸ್ಟಮ್ನ ವಿಮರ್ಶಾತ್ಮಕ ಮೌಲ್ಯಮಾಪನ, ಪಕ್ವತೆಯ ವರ್ಗೀಕರಣ ಮತ್ತು ಉಪಕರಣ-ಸ್ವತಂತ್ರ
ಮರುಅನುಷ್ಠಾನ ಯೋಜನೆಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ ಪ್ಲೇಬುಕ್](../ops/QUALITY_GATE_PLAYBOOK.md) ನೋಡಿ.

## ಗೇಟ್ ದಾಸ್ತಾನು ಮತ್ತು ಮರಣದಂಡನೆ ಪ್ರೊಫೈಲ್ಗಳು

### ಅಭ್ಯರ್ಥಿ ಪ್ರವೇಶ

CI ಮತ್ತು ಕ್ವಾಲಿಟಿ ಗೇಟ್ಸ್ ವರ್ಕ್ಫ್ಲೋಗಳು ಪ್ರತಿಯೊಂದೂ ಸ್ಥಿರವಾದ ತೀರ್ಪನ್ನು ಹೊರಸೂಸುತ್ತವೆ: `Gate / CI` ಮತ್ತು `Gate / Quality`. ಅವರ ಆವೃತ್ತಿಯ ಪ್ರವೇಶ ನೀತಿಯು ಅಗತ್ಯವಿರುವ ಅಥವಾ ಸಲಹೆಯಂತೆ ಪ್ರತಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ಕೆಲಸವನ್ನು ಎಣಿಸುತ್ತದೆ. ಅನ್ವಯವಾಗುವ ಅಗತ್ಯವಿರುವ ಕೆಲಸವು ಯಶಸ್ವಿಯಾಗಬೇಕು: ಕಾಣೆಯಾಗಿದೆ, ರದ್ದುಗೊಳಿಸಲಾಗಿದೆ, ಸ್ಕಿಪ್ ಮಾಡಲಾಗಿದೆ, ಬಾಕಿ ಉಳಿದಿದೆ ಮತ್ತು ಅಜ್ಞಾತ ಫಲಿತಾಂಶಗಳು PASS ಸ್ಥಾಪಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮಾನ್ಯವಾದ ಡಾಕ್ಸ್-ಮಾತ್ರ ಅಥವಾ ಕ್ಯಾಟಲಾಗ್-ಮಾತ್ರ ವರ್ಗೀಕರಣವು ಕೋಡ್ ಲೇನ್ ಅನ್ನು ಅನ್ವಯಿಸದಂತೆ ಮಾಡಬಹುದು; ಡ್ರಾಫ್ಟ್ PR ಸ್ವೀಕರಿಸಿದ ಅಭ್ಯರ್ಥಿಯಾಗಿಲ್ಲ. `hotfix` ಲೇಬಲ್ ಸಾಕ್ಷ್ಯವನ್ನು ಬಿಟ್ಟುಕೊಡುವುದಿಲ್ಲ.

ಎರಡೂ ವರ್ಕ್ಫ್ಲೋಗಳು PRs main/release ಶಾಖೆಗಳಾಗಿ ಒಳಗೊಳ್ಳುತ್ತವೆ, `main` ಗೆ ತಳ್ಳುತ್ತದೆ, ಹಸ್ತಚಾಲಿತ ರವಾನೆ ಮತ್ತು ವಿಲೀನ-ಗುಂಪು ಈವೆಂಟ್ಗಳು. ಪುಶ್, ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು ವಿಲೀನ-ಗುಂಪು ಪೂರ್ಣ ಆಯ್ಕೆಯನ್ನು ರನ್ ಮಾಡಿ. `release/**` ಗೆ ತಳ್ಳುತ್ತದೆ ಅವುಗಳನ್ನು ಪ್ರಾರಂಭಿಸಬೇಡಿ (2026-10-18): ಪ್ರತಿ ಬದಲಾವಣೆಯು ಈಗಾಗಲೇ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು ಅದರ PR ನಲ್ಲಿ ರನ್ ಮಾಡಿದೆ ಮತ್ತು ವಿಲೀನಗೊಂಡ ಸಂಯೋಜನೆಯು ಬಿಡುಗಡೆ-ಗ್ರೀನ್ನ ಕೆಲಸವಾಗಿದೆ (`docs/ops/RUNNER_BOX.md` → ಹೋಸ್ಟ್ ಮಾಡಿದ ಲೇನ್). ಫೋರ್ಕ್ಸ್ ಮತ್ತು ವಿಲೀನ ಗುಂಪುಗಳು ಉದ್ಯೋಗಗಳಿಗಾಗಿ ಹೋಸ್ಟ್ ಮಾಡಿದ ಓಟಗಾರರನ್ನು ಬಳಸುತ್ತವೆ, ಇಲ್ಲದಿದ್ದರೆ ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ ಓಟಗಾರರನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತವೆ; ರೋಲ್ಔಟ್ ಮಾಡುವ ಮೊದಲು ಸಾಕಷ್ಟು ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಸಾಮರ್ಥ್ಯವನ್ನು ಪರಿಶೀಲಿಸಬೇಕು.

ಸಾಮಾನ್ಯ PR ವೇಗದ ಆಯ್ಕೆಯನ್ನು ನಡೆಸುತ್ತದೆ. ಪ್ರವೇಶ ನೀತಿಯ `full-code` ಮತ್ತು `full-code-e2e` ಲೇನ್ಗಳು (E2E, ಏಕೀಕರಣ, ಪ್ಯಾಕೇಜ್ ಕಲಾಕೃತಿ, Electron ಸ್ಮೋಕ್, Bun SQLite, ಪರಿಸರ ವ್ಯವಸ್ಥೆ ಮತ್ತು ಪ್ರೋಟೋಕಾಲ್ ಕ್ಲೈಂಟ್ಗಳು) ಮರ್ಜಿಫೈ ಕ್ಯೂ ಡ್ರಾಫ್ಟ್ನಲ್ಲಿ ಅಥವಾ ಪೂರ್ಣ ರನ್ನಲ್ಲಿ ಮಾತ್ರ ರನ್ ಆಗುತ್ತವೆ: `gh workflow run ci.yml --ref <branch>`.

ಪ್ರತಿಯೊಂದು JSON ರಶೀದಿಯು ಚೆಕ್-ಔಟ್ SHA, ವರ್ಕ್ಫ್ಲೋ ರನ್ ಮತ್ತು ಪ್ರಯತ್ನವನ್ನು ಗುರುತಿಸುತ್ತದೆ. CLI checkout/event SHA ಹೊಂದಾಣಿಕೆಯನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ವರ್ಕ್ಫ್ಲೋ ಪರೀಕ್ಷೆಗಳು ನೀತಿಯ ಸದಸ್ಯತ್ವವನ್ನು ತೀರ್ಪು ಕೆಲಸದ `needs` ಪಟ್ಟಿಗೆ ಬಂಧಿಸುತ್ತವೆ ಆದ್ದರಿಂದ ಹೊಸ ಅಥವಾ ತೆಗೆದುಹಾಕಲಾದ ಲೇನ್ ಮೌನವಾಗಿ ಕಣ್ಮರೆಯಾಗುವುದಿಲ್ಲ. ರಸೀದಿಗಳು ತಮ್ಮದೇ ಆದ ಕೆಲಸದ ಹರಿವನ್ನು ಒಳಗೊಂಡಿರುತ್ತವೆ, ಪ್ರಕಟಣೆ, ನಿಯೋಜನೆ ಅಥವಾ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಲಹಾ ಸ್ಕ್ಯಾನರ್ನ ಆಂತರಿಕ ಅಂಶಗಳಲ್ಲ. ಶಾಖೆಯ ನಿಯಮಗಳಲ್ಲಿ ಎರಡೂ ಚೆಕ್ ಹೆಸರುಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದು ಪ್ರತ್ಯೇಕ ಆಡಳಿತಾತ್ಮಕ ಬದಲಾವಣೆಯಾಗಿದೆ; ಈ ಉದ್ಯೋಗಗಳನ್ನು ಸೇರಿಸುವುದರಿಂದ ಸ್ವತಃ ಶಾಖೆಯನ್ನು ರಕ್ಷಿಸುವುದಿಲ್ಲ.

### ಸರದಿಯನ್ನು ವಿಲೀನಗೊಳಿಸಿ

`queue` ಲೇಬಲ್ ಒಂದು PR Mergify ಕ್ಯೂ (`.mergify.yml`) ಗೆ ಕಳುಹಿಸುತ್ತದೆ. Mergify ಒಂದು `mergify/merge-queue/` ಶಾಖೆಯಲ್ಲಿ ಡ್ರಾಫ್ಟ್ PR ತೆರೆಯುತ್ತದೆ, CI ಅಲ್ಲಿ ಪೂರ್ಣ ಆಯ್ಕೆಯನ್ನು ನಡೆಸುತ್ತದೆ ಮತ್ತು `Gate / CI`, `Gate / Quality` ಮತ್ತು `Merge integrity (changelog + generated skills)` ಪಾಸ್ ಮಾಡಿದಾಗ ಮೂಲ PR ವಿಲೀನಗೊಳ್ಳುತ್ತದೆ.

Mergify ತನ್ನ ಸರದಿ ಸಾರಾಂಶವನ್ನು ಡ್ರಾಫ್ಟ್ನ ವಿವರಣೆಯಲ್ಲಿ ಬರೆಯುತ್ತದೆ ಮತ್ತು ಇತರ ಅಪ್ಲಿಕೇಶನ್ಗಳು ಸಹ ಅದನ್ನು ಸಂಪಾದಿಸಬಹುದು. ಅಂತಹ ಡ್ರಾಫ್ಟ್ನಲ್ಲಿನ `pull_request` `edited` ಈವೆಂಟ್ ತನ್ನದೇ ಆದ ಏಕಕಾಲಿಕ ಗುಂಪನ್ನು ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ (`-queue-edit-<run_id>`) ಆದ್ದರಿಂದ ಅದು ಡ್ರಾಫ್ಟ್ನ ನೈಜ ಓಟವನ್ನು ರದ್ದುಗೊಳಿಸುವುದಿಲ್ಲ ಮತ್ತು ಅದು ಗೇಟ್ ಮತ್ತು ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ. `Merge integrity` ಮಾತ್ರ ಇನ್ನೂ ಚಾಲನೆಯಲ್ಲಿದೆ. ಸ್ಕಿಪ್ಡ್ ಗೇಟ್ ಕೆಲಸವು ವಿಭಿನ್ನ ಚೆಕ್ ಹೆಸರನ್ನು ಹೊಂದಿದೆ, ಏಕೆಂದರೆ Mergify ಸ್ಕಿಪ್ ಮಾಡಿದ `Gate / CI` ಅನ್ನು ವಿಫಲವಾದ ಚೆಕ್ ಎಂದು ಓದುತ್ತದೆ ಮತ್ತು PR ಅನ್ನು ಡಿಕ್ಯೂ ಮಾಡುತ್ತದೆ.

ಡಿಕ್ಯೂ ನಂತರ, ಒಂದು ಪುಶ್ ಯಾವಾಗಲೂ PR ಅನ್ನು ರೀಕ್ಯೂ ಮಾಡುವುದಿಲ್ಲ. ಅದರ ಮೇಲೆ `@mergifyio queue` ಎಂದು ಕಾಮೆಂಟ್ ಮಾಡಿ.

### ಸ್ವೀಕಾರ ಕಡಿತಗಾರದಲ್ಲಿ ಪುರಾವೆಗಳನ್ನು ಉಳಿಸಿಕೊಂಡಿದೆ

`scripts/quality/validate-release-acceptance.mjs` ಸರಬರಾಜು ಮಾಡಿದ ಯೋಜನೆ ಮತ್ತು ಅದರ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ; ಯೋಜನೆಯು ಸಂಪೂರ್ಣ ಬಿಡುಗಡೆಯ ಪೈಪ್ಲೈನ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ ಎಂದು ಅದು ಸ್ಥಾಪಿಸುವುದಿಲ್ಲ. ಅದರ ವರದಿಗಳು ಸ್ಪಷ್ಟವಾಗಿ `releaseAcceptance: false` ಹೊಂದಿಸುತ್ತದೆ, ಆ ಯೋಜನೆಯು `VERIFIED` ಆಗಿದ್ದರೂ ಸಹ. `release-acceptance.yml` ವರ್ಕ್ಫ್ಲೋ ಇನ್ನೂ ನೆರಳು ನೆಲೆವಸ್ತುಗಳನ್ನು ಬಳಸುತ್ತದೆ, ನಿಜವಾದ ನಿರ್ಮಾಣ, ಪ್ಯಾಕೇಜ್, ಬೂಟ್ ಅಥವಾ ಪ್ರಚಾರದ ರಸೀದಿಗಳನ್ನು ಅಲ್ಲ.

ಉಳಿಸಿಕೊಂಡಿರುವ ಪುರಾವೆಗಳನ್ನು ಪರಿಶೀಲಿಸಲು CLI `--evidence-root` ಅಗತ್ಯವಿದೆ. ಫೈಲ್ಗಳನ್ನು `<evidence-root>/<artifact_id>/<member>` ಎಂದು ಪರಿಹರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು SHA-256 ಎಂದು ಹ್ಯಾಶ್ ಮಾಡಲಾಗಿದೆ. ಪುರಾವೆಗಳಿಲ್ಲದ PASS ದಾಖಲೆ, ಕಾಣೆಯಾದ ಅಥವಾ ಬದಲಾದ ಫೈಲ್, ಅಸುರಕ್ಷಿತ ಮಾರ್ಗ ಅಥವಾ ಸಿಮ್ಲಿಂಕ್ ಪರಿಶೀಲನೆಯನ್ನು ತಡೆಯುತ್ತದೆ. ಕಾಣೆಯಾದ ಫೈಲ್ಗಳು ಖಾಲಿ ಯಶಸ್ವಿ ಲಾಗ್ಗಳಿಗೆ ಸಮನಾಗಿರುವುದಿಲ್ಲ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ SHA/run/attempt ಚೆಕ್ಗಳು ಸ್ವತಂತ್ರವಾಗಿರುತ್ತವೆ: ಹೊಂದಾಣಿಕೆಯ ಬೈಟ್ಗಳು ಹಳೆಯ ರಸೀದಿಯನ್ನು ರಕ್ಷಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಫೈಲ್ ಸಮಗ್ರತೆಯು ಮರಣದಂಡನೆಯ ದೃಢೀಕರಣ ಅಥವಾ ಕಲಾಕೃತಿ ಪ್ರಚಾರದ ಪುರಾವೆಯಲ್ಲ.

### ಸ್ಥಾಯೀ ಸ್ಕ್ಯಾನ್ ದಾಸ್ತಾನು

ಆವೃತ್ತಿಯ npm-ಅಲಿಯಾಸ್ ಇನ್ವೆಂಟರಿ ಮತ್ತು ಸ್ಟ್ಯಾಟಿಕ್-ಸ್ಕ್ಯಾನ್ ಸದಸ್ಯತ್ವವು `config/quality/gate-manifest.json` ನಲ್ಲಿ ಲೈವ್ ಆಗಿದೆ. `package.json` ವಿರುದ್ಧ ಸ್ಕ್ರಿಪ್ಟ್ ಹೆಸರುಗಳು ಮತ್ತು ನಿಖರವಾದ ಆಜ್ಞೆಗಳನ್ನು ಮೌಲ್ಯೀಕರಿಸಲು `npm run check:gate-manifest` ರನ್ ಮಾಡಿ; ಸೇರ್ಪಡೆಗಳು, ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ಮತ್ತು ಕಮಾಂಡ್ ಡ್ರಿಫ್ಟ್ ಸ್ಥಳೀಯ ಹುಕ್ ಮತ್ತು CI ನಲ್ಲಿನ ಬದಲಾವಣೆ-ವರ್ಗೀಕರಣ ಕೆಲಸಗಳೆರಡನ್ನೂ ವಿಫಲಗೊಳಿಸುತ್ತದೆ. ಅಲಿಯಾಸ್ ಎನ್ನುವುದು ವರ್ಕ್ಫ್ಲೋ ಕೆಲಸ, ಮ್ಯಾಟ್ರಿಕ್ಸ್ ನಿದರ್ಶನ ಅಥವಾ ಪರೀಕ್ಷಾ ಪ್ರಕರಣವಲ್ಲ: ಈ ಎಣಿಕೆಗಳನ್ನು ಪರಸ್ಪರ ಬದಲಾಯಿಸಬಹುದಾದಂತೆ ಪ್ರಸ್ತುತಪಡಿಸಬಾರದು.

ಆಯ್ಕೆಮಾಡಿದ ಅಲಿಯಾಸ್ಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸದೆ ಪರಿಶೀಲಿಸಲು `npm run quality:scan -- --list` ಅಥವಾ `npm run quality:scan:fast -- --list` ಬಳಸಿ. ರನ್ನರ್ npm ಎಂಟ್ರಿಪಾಯಿಂಟ್ ಅನ್ನು ಆಹ್ವಾನಿಸುತ್ತಾನೆ, ಆದ್ದರಿಂದ ಅದರ ರನ್ಟೈಮ್ (ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ Bun ಸೇರಿದಂತೆ) ಸಂರಕ್ಷಿಸಲಾಗಿದೆ. ಮ್ಯಾನಿಫೆಸ್ಟ್ ರೆಕಾರ್ಡ್ಗಳು ಆ ಪ್ರೊಫೈಲ್ಗಳ ಹೊರಗಿನ ಅಲಿಯಾಸ್ಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಆಹ್ವಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಓದಲು-ಮಾತ್ರ ಸ್ಕ್ಯಾನ್ ಪ್ರೊಫೈಲ್ಗಳಲ್ಲಿ ನಿರ್ವಹಣೆ ಆಜ್ಞೆಗಳನ್ನು ನಿಷೇಧಿಸಲಾಗಿದೆ.

ಈ ಪ್ರೊಫೈಲ್ಗಳು ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಅನ್ನು ಮಾತ್ರ ಒಳಗೊಂಡಿರುತ್ತವೆ. ಅವರು ಉತ್ಪನ್ನ ಪರೀಕ್ಷೆಗಳು, ಕವರೇಜ್, ಪ್ಯಾಕೇಜಿಂಗ್, ಬಾಹ್ಯ ತಪಾಸಣೆ ಅಥವಾ ಅಭ್ಯರ್ಥಿಯ ಪೂರ್ಣ ಬಿಡುಗಡೆ ಸ್ವೀಕಾರವನ್ನು ಪ್ರಮಾಣೀಕರಿಸುವುದಿಲ್ಲ. ವರ್ಕ್ಫ್ಲೋ ಪ್ರವೇಶವು ಲಿಂಕ್ ಮಾಡಲಾದ `config/quality/admission-policy.json` ಮತ್ತು `scripts/quality/admission-verdict.mjs` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಬಿಡುಗಡೆ-ವೀಕ್ಷಕರ ಪ್ರೊಫೈಲ್ಗಳು ಪ್ರತ್ಯೇಕವಾಗಿ ಉಳಿಯುತ್ತವೆ; ಅವರ ಅನ್ವಯವಾಗುವ ಚೆಕ್ಗಳು ಮತ್ತು ರಶೀದಿಗಳನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರೀಕ್ಷಿಸಿ. ಪೂರ್ಣ ವೀಕ್ಷಕನ ಸ್ಥಿರ ಆಜ್ಞೆಗಳನ್ನು `audit:deps`, ರೂಪಾಂತರ-ಪರೀಕ್ಷೆ ಆಯ್ಕೆ ಮತ್ತು ಅನುವಾದ ಪರಿಶೀಲನೆಗಳನ್ನು ಒಳಗೊಂಡಂತೆ `config/quality/release-green-static-profile.json` ನಲ್ಲಿ ಘೋಷಿಸಲಾಗಿದೆ. ಲೋಡರ್ package.json ಮತ್ತು ಮಾದರಿಯ CI/Quality ಘೋಷಣೆಗಳ ವಿರುದ್ಧ npm ಆಜ್ಞೆಗಳನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; ಇದು ಶೆಲ್ ಟೋಕನ್ಗಳನ್ನು ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳಾಗಿ ಕಾರ್ಯಗತಗೊಳಿಸುವ ಬದಲು ಡ್ರಿಫ್ಟ್ ಅನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ಅಗತ್ಯವಿರುವ ಸ್ಕ್ಯಾನರ್ SKIP/INCOMPLETE ಔಟ್ಪುಟ್ PASS ಸ್ಥಾಪಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪ್ರೊಫೈಲ್ ಅದರ ಬಾಹ್ಯ ಹೊರಗಿಡುವಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಕವರೇಜ್, ಪರೀಕ್ಷಾ ಮ್ಯಾಟ್ರಿಕ್ಸ್, ಪ್ಯಾಕೇಜ್ ಅಥವಾ ನಿಯೋಜನೆ ಪುರಾವೆಗಳನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ. ಕೆಳಗಿನ ಗದ್ಯ ದಾಸ್ತಾನು ಒಂದು ಉಲ್ಲೇಖವಾಗಿದೆ, ಗೇಟ್ ನಿಜವಾಗಿ ಓಡಿದೆ ಎಂಬುದಕ್ಕೆ ಪುರಾವೆ ಅಲ್ಲ.

ಸ್ಕ್ರಿಪ್ಟ್ಗಳು `scripts/check/` (ಪಾಲಿಸಿ ಗೇಟ್ಗಳು) ಮತ್ತು `scripts/quality/` (ರಾಟ್ಚೆಟ್ ಎಂಜಿನ್) ಅಡಿಯಲ್ಲಿ ವಾಸಿಸುತ್ತವೆ. ಸತ್ಯದ CI ಮೂಲವು `.github/workflows/ci.yml` ಆಗಿದೆ.

### PR ವೇಗದ ಮಾರ್ಗವನ್ನು ಬಿಡುಗಡೆ ಮಾಡಿ (`quality.yml`)

`.github/workflows/quality.yml` main/release PRs ನಲ್ಲಿ CI ಪೂರೈಸುತ್ತದೆ, `main` ಗೆ ತಳ್ಳುತ್ತದೆ, ಗುಂಪುಗಳನ್ನು ರವಾನಿಸುತ್ತದೆ ಮತ್ತು ವಿಲೀನಗೊಳಿಸುತ್ತದೆ. PRs ಪಾಥ್-ಫಿಲ್ಟರ್ಡ್ ಫಾಸ್ಟ್ ಚೆಕ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ. ಶಾಶ್ವತವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ನಕಲಿ ನಿರ್ಮಾಣವನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ; ನಿಜವಾದ build/package/boot ಚೆಕ್ಗಳು CI ನಲ್ಲಿ ಉಳಿಯುತ್ತವೆ. ಯುನಿಟ್ ಸೂಟ್ ಮತ್ತು ವಿಟೆಸ್ಟ್ CI (`Unit Tests (N/8)` ಮತ್ತು `Vitest`) ನಲ್ಲಿ ಮಾತ್ರ ರನ್ ಆಗುತ್ತದೆ.

#### ಮರೆತುಹೋದ ಒಡಹುಟ್ಟಿದವರ ಪರೀಕ್ಷೆಗಳ ವರದಿ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ನ ಸಲಹಾ ಹಂತವಾಗಿ ಚಲಿಸುತ್ತದೆ ಮತ್ತು ಪರೀಕ್ಷಾ-ಪರಿಣಾಮದ ನಕ್ಷೆಯ ಹಿಂದೆ ಆಮದು ಪರಿಹಾರಕವನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ. ಪ್ರತಿ ಬದಲಾದ ಪ್ರೊಡಕ್ಷನ್ ಮಾಡ್ಯೂಲ್ಗೆ, ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆಯು ಪುಲ್-ರಿಕ್ವೆಸ್ಟ್ ಡಿಫ್ನಿಂದ ಗೈರುಹಾಜರಾದಾಗ ನಿರ್ಣಾಯಕ `changed module/symbol -> static consumer -> candidate sibling test` ಸರಪಳಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಮಾರ್ಕ್ಡೌನ್ ಸಾರಾಂಶ ಮತ್ತು JSON ಫಲಿತಾಂಶವನ್ನು ಯಾವುದೇ ತಡೆಯುವ ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಮಾಪನಾಂಕ ನಿರ್ಣಯಕ್ಕಾಗಿ `forgotten-sibling-tests` ವರ್ಕ್ಫ್ಲೋ ಕಲಾಕೃತಿಯಾಗಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

ಬ್ಯಾರೆಲ್ ಮರು-ರಫ್ತುಗಳು ಮತ್ತು ಡೈನಾಮಿಕ್ ಆಮದುಗಳು ರೆಸಲ್ಯೂಶನ್ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಸ್ ಮಾತ್ರ; ಅವರು ಎಂದಿಗೂ ತಡೆಯುವ ಶೋಧನೆಯನ್ನು ರಚಿಸುವುದಿಲ್ಲ. ಪರಿಶೀಲಿಸಿದ ವಿನಾಯಿತಿಗಳು `config/quality/forgotten-sibling-allowlist.json` ನಲ್ಲಿ ಲೈವ್ . ಪ್ರತಿ ನಮೂದು ಗ್ರಾಹಕ ಮತ್ತು ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆಯನ್ನು ಹೆಸರಿಸಬೇಕು, ನಿರ್ದಿಷ್ಟ ತಾರ್ಕಿಕತೆಯನ್ನು ನೀಡಬೇಕು ಮತ್ತು GitHub ಸಂಚಿಕೆಯನ್ನು ಲಿಂಕ್ ಮಾಡಬೇಕು ಅಥವಾ ವಿನಂತಿಯನ್ನು ಎಳೆಯಬೇಕು. ದೋಷಪೂರಿತ ನಮೂದುಗಳನ್ನು ವಿಫಲಗೊಳಿಸಲಾಗಿದೆ ಮುಚ್ಚಲಾಗಿದೆ. ವಿನಾಯಿತಿಗಳು ಅಳಿಸಲಾದ ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆ ಅಥವಾ `.skip`/`.todo` ಅನ್ನು ಸೇರಿಸುವ ವ್ಯತ್ಯಾಸವನ್ನು ನಿಗ್ರಹಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ; ಸಮರ್ಥನೆ ದುರ್ಬಲಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಇತರ ಮರೆಮಾಚುವಿಕೆಗಳು ಸ್ವತಂತ್ರವಾಗಿ ನಿರ್ಬಂಧಿಸುವ `check:test-masking` ಗೇಟ್ನ ಮಾಲೀಕತ್ವದಲ್ಲಿ ಉಳಿಯುತ್ತವೆ.

#### ಎರಡು ಟೈಪ್ ಚೆಕ್ ಪ್ರೋಗ್ರಾಂಗಳು ವಿಭಿನ್ನವಾಗಿ ಉತ್ತರಿಸುತ್ತವೆ

`typecheck:core` ಮತ್ತು `check:build-typecheck` ವಿಭಿನ್ನ ಆಯ್ಕೆಗಳ ಅಡಿಯಲ್ಲಿ ವಿಭಿನ್ನ ಪ್ರೋಗ್ರಾಂಗಳನ್ನು ಕಂಪೈಲ್ ಮಾಡುತ್ತವೆ, ಮತ್ತು ಒಂದೇ ಫೈಲ್ ಒಂದರಲ್ಲಿ ಕ್ಲೀನ್ ಆಗಿರಬಹುದು ಮತ್ತು ಇನ್ನೊಂದರಲ್ಲಿ ದೋಷಗಳು ತುಂಬಿರುತ್ತವೆ.

`tsconfig.build.json` `"strict": false` ಹೊಂದಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ `noImplicitAny` ಆಫ್ ಆಗಿದೆ. ಕೋರ್ ಕಾನ್ಫಿಗರ್ ಕಟ್ಟುನಿಟ್ಟಾದ ಆಯ್ಕೆಗಳೊಂದಿಗೆ ಕ್ಯುರೇಟೆಡ್ 27-ಫೈಲ್ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಕಂಪೈಲ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಪ್ರವೇಶದ ಆಮದು ಗ್ರಾಫ್ ಅನ್ನು ಅನುಸರಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಬಿಲ್ಡ್ ಪ್ರೋಗ್ರಾಂನಲ್ಲಿ ಎಂದಿಗೂ ಕಾಣಿಸದ ಫೈಲ್ಗಳನ್ನು ಇನ್ನೂ ಅಲ್ಲಿ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ.

ಫೈಲ್ ಅನ್ನು ಟೈಪ್ ಮಾಡಲಾಗಿದೆಯೇ ಎಂದು ನಿರ್ಣಯಿಸುವಾಗ ಇದರ ಪರಿಣಾಮವು ಮುಖ್ಯವಾಗಿದೆ:** `check:build-typecheck` ಅಡಿಯಲ್ಲಿ ಶೂನ್ಯ ರೋಗನಿರ್ಣಯವು ಶೂನ್ಯ ಎಂದು ಅರ್ಥವಲ್ಲ** . 26 ಫೈಲ್ಗಳಿಂದ `@ts-nocheck` ಸ್ಟ್ರಿಪ್ ಮಾಡುವುದರಿಂದ ಬಿಲ್ಡ್ ಪ್ರೋಗ್ರಾಂನಲ್ಲಿ 23 ಕ್ಲೀನ್ ಅನ್ನು ತೋರಿಸಿದೆ; ಅವುಗಳಲ್ಲಿ ಹದಿನಾರು ಸುಮಾರು 120 ಸೂಚ್ಯವಾಗಿ ಕಾಣಿಸಿಕೊಂಡಿವೆ - ಕಟ್ಟುನಿಟ್ಟಾದ ಒಂದರಲ್ಲಿ ಯಾವುದೇ ದೋಷಗಳು. ಫೈಲ್ ಅನ್ನು ಕ್ಲೀನ್ ಎಂದು ಕರೆಯುವ ಮೊದಲು ಎರಡನ್ನೂ ಪರಿಶೀಲಿಸಿ.

#### `check-ui-value-drift` — ಸ್ಥಬ್ದ-ಅನುವಾದ ಗೇಟ್

ಒಂದು i18n ರಿಗ್ರೆಶನ್ ಅನ್ನು ಇತರ ಗೇಟ್ಗಳು ರಚನಾತ್ಮಕವಾಗಿ ನೋಡುವುದಿಲ್ಲ: ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯವನ್ನು ಪುನಃ ಬರೆಯಲಾಗಿದೆ ಮತ್ತು _previous_ ಇಂಗ್ಲಿಷ್ನಿಂದ ಪಡೆದ ಅನುವಾದಗಳು ಹಿಂದೆ ಉಳಿಯುತ್ತವೆ, ಆದ್ದರಿಂದ ಇಂಗ್ಲಿಷ್ ಅಲ್ಲದ ಬಳಕೆದಾರರು ಆತ್ಮವಿಶ್ವಾಸದಿಂದ ಪದಗಳ, ಈಗ-ತಪ್ಪಾದ ಪ್ರತಿಯನ್ನು ಓದುತ್ತಾರೆ.

ಇದನ್ನು ನೈಜವಾಗಿ ರವಾನಿಸಲಾಗಿದೆ. Antigravity ಲಾಗಿನ್ ಸಹಾಯಕ ಇಳಿದಾಗ `oauthModal.googleOAuthWarning` ಪುನಃ ಬರೆಯಲಾಗಿದೆ (#5203);** 43 ಸ್ಥಳಗಳಲ್ಲಿ 39** "ಪೂರ್ಣ URL ಅನ್ನು ನಕಲಿಸಿ ಮತ್ತು ಅದನ್ನು ಕೆಳಗೆ ಅಂಟಿಸಿ" ಎಂದು ಆಪರೇಟರ್ಗಳಿಗೆ ಹೇಳುವ ಪಠ್ಯವನ್ನು ಇರಿಸಲಾಗಿದೆ, ಆ ಪೂರೈಕೆದಾರರಿಗೆ ಪೂರ್ಣಗೊಳ್ಳದ ಹರಿವನ್ನು —. ಇದು #8463 ವರೆಗೆ ಗಮನಕ್ಕೆ ಬರಲಿಲ್ಲ ಏಕೆಂದರೆ:

- `sync-ui-keys` ಮಾತ್ರ ಬ್ಯಾಕ್ಫಿಲ್ ಕೀಗಳನ್ನು** ಗೈರು** , ಎಂದಿಗೂ ಇಲ್ಲ** ಹಳಸಿದ** ;
- `check-ui-keys-coverage` ಕೀ _ ಉಪಸ್ಥಿತಿ_ ಅನ್ನು ಎಣಿಕೆ ಮಾಡುತ್ತದೆ, ಆದ್ದರಿಂದ ಹಳೆಯ ಅನುವಾದವು ಮುಚ್ಚಿದಂತೆ ಸ್ಕೋರ್ ಮಾಡುತ್ತದೆ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ದಸ್ತಾವೇಜನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ — ಇದು ಎಂದಿಗೂ `src/i18n/messages/*.json` ಓದುವುದಿಲ್ಲ. 2026-09 ಮರು-ಸಿಂಕ್ನಿಂದ ಉದ್ಯೋಗ `docs-sync-strict` ನಲ್ಲಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತಿದೆ: ಕೋರ್ ಡಾಕ್ → `npm run i18n:run -- --files=<doc>` ಅನ್ನು ಎಡಿಟ್ ಮಾಡಿ (ವಿಭಾಗ-ಹಂತ, ಅಗ್ಗದ).

**ಡಿಫ್-ಅವೇರ್, ಬೇಸ್ಲೈನ್-ಬೆಂಬಲಿತವಲ್ಲ.** ಇದು ಕೆಲಸ ಮಾಡುವ ಮರದ ವಿರುದ್ಧ ವಿಲೀನ ತಳದಲ್ಲಿ `en.json` ಹೋಲಿಸುತ್ತದೆ; ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯವನ್ನು ಬದಲಾಯಿಸಿದ ಪ್ರತಿಯೊಂದು ಕೀಲಿಗಾಗಿ, ಯಾವುದೇ ಲೊಕೇಲ್ ಇನ್ನೂ ಅಸ್ಪೃಶ್ಯ ಅನುವಾದವನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುತ್ತದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ** ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಾಲವನ್ನು ಫ್ರೀಜ್ ಮಾಡುತ್ತದೆ** — a diff ಯಾವ ಹಳೆಯ ಇಂಗ್ಲಿಷ್ನಿಂದ ದೀರ್ಘಕಾಲದ ಅನುವಾದ ಬಂದಿದೆ ಎಂಬುದನ್ನು ಬಹಿರಂಗಪಡಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ, ಆದ್ದರಿಂದ ಪ್ರಸ್ತುತ ಬದಲಾವಣೆಯು ಏನನ್ನು ಮುಟ್ಟುತ್ತದೆ ಎಂಬುದನ್ನು ಮಾತ್ರ ಗೇಟ್ ನಿರ್ಣಯಿಸುತ್ತದೆ. ಪರ್ಯಾಯವು (ಪ್ರತಿ-ಕೀ ಹ್ಯಾಶ್ ಬೇಸ್ಲೈನ್) ~ 600 KB ರಚಿತವಾದ ಫೈಲ್ಗೆ ವೆಚ್ಚವಾಗುತ್ತದೆ, 3 × ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅತಿದೊಡ್ಡ ಬೇಸ್ಲೈನ್, ಪ್ರತಿ i18n PR ನಲ್ಲಿ ಮಂಥನವಾಗುತ್ತದೆ.

ಅದನ್ನು ಪೂರೈಸಲು ಎರಡು ಮಾರ್ಗಗಳು:

1. ಪೀಡಿತ ಅನುವಾದಗಳನ್ನು ನವೀಕರಿಸಿ, ಅಥವಾ
2. ಅವುಗಳನ್ನು `__MISSING__:<new english>` — ಗೆ ಹೊಂದಿಸಿ ರನ್ಟೈಮ್ ನಂತರ ಸರಿಪಡಿಸಿದ ಇಂಗ್ಲಿಷ್ (`src/i18n/request.ts::deepMergeFallback`, #7258) ಮತ್ತು ಅನುವಾದಕ್ಕಾಗಿ ಪ್ರಮುಖ ಸಾಲುಗಳನ್ನು ಪೂರೈಸುತ್ತದೆ.

ಸ್ಟ್ರಿಂಗ್ ವೇಳೆ** ಅರ್ಥ** ಬದಲಾಗಿದೆ, ಆದ್ಯತೆ** ಕೀಲಿಯನ್ನು ಮರುಹೆಸರಿಸುವುದು** : ಹೊಸ ಕೀಲಿಯು ಹಳೆಯ ಅನುವಾದವನ್ನು ಪಡೆದುಕೊಳ್ಳಲು ಸಾಧ್ಯವಿಲ್ಲ. ಅದು #8463 ಮಾದರಿಯನ್ನು ಬಳಸಲಾಗುತ್ತದೆ.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ಮೂಲ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಓದಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ `SKIP reason=base-unresolved` ನೊಂದಿಗೆ 0 ನಿರ್ಗಮಿಸುತ್ತದೆ (ಮೂಲ ಉಲ್ಲೇಖವಿಲ್ಲದೆ ಆಳವಿಲ್ಲದ ಕ್ಲೋನ್), `check-openapi-breaking` ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ.

ಪರಿಶೀಲಿಸುತ್ತದೆ, `git show` ಮೂಲಕ PR ಬೇಸ್ನಲ್ಲಿನ ಪ್ರತಿಯೊಂದರ ಸಾಲಿನ ಎಣಿಕೆಯನ್ನು ಓದುತ್ತದೆ ಮತ್ತು ಫೈಲ್ ತನ್ನ

ಮತ್ತು ಅದರ ಬೇಸ್ ಗಾತ್ರ — ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದಾದ ಮೌಲ್ಯವನ್ನು ಮೀರಿದಾಗ ಮಾತ್ರ ಅದನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ.
ಆದ್ದರಿಂದ ಬೇಸ್ನಲ್ಲಿ ಈಗಾಗಲೇ ಡ್ರಿಫ್ಟ್ ಆಗಿರುವ ಫೈಲ್ ನಿರಪರಾಧ PR ಅನ್ನು ಎಂದಿಗೂ ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ.

`check:boundary:ratchet` ತನ್ನ ಏಕೈಕ ಸಂಖ್ಯೆಗೆ ಅದೇ ನಿಯಮವನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ಈವೆಂಟ್ಗಳಲ್ಲಿ
`quality.yml` ಫಾಸ್ಟ್-ಗೇಟ್ಗಳು ಮತ್ತು `ci.yml` lint ಜಾಬ್ ಎರಡೂ PR ಬೇಸ್ SHA ಅನ್ನು ರವಾನಿಸುತ್ತವೆ, ಬೇಸ್ ಕಮಿಟ್ ಅನ್ನು
`git archive` ಎಕ್ಸ್ಪೋರ್ಟ್ನಿಂದ ಅಳೆಯಲಾಗುತ್ತದೆ, ಮತ್ತು ಅದರ `open-sse → src` ಎಡ್ಜ್
ಎಣಿಕೆಯು `metrics.boundaryOpenSseToSrc` ಹಾಗೂ ಬೇಸ್ನಲ್ಲಿನ ಎಣಿಕೆ—ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದಾದ ಮೌಲ್ಯವನ್ನು ಮೀರಿದಾಗ ಮಾತ್ರ PR ವಿಫಲವಾಗುತ್ತದೆ. ಮಿತಿಗಿಂತ
ಹೆಚ್ಚಿರುವ ಬೇಸ್ ಡ್ರಿಫ್ಟ್ ಅನ್ನು (`base drift herdado`) ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಅದರಿಂದ ದೋಷವಿಲ್ಲದ PR ಎಂದಿಗೂ ವಿಫಲವಾಗುವುದಿಲ್ಲ; push → main
ಸಂಪೂರ್ಣ ಮಿತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಮತ್ತು ಪರಿಹರಿಸಲಾಗದ ಬೇಸ್ SHA ಎಚ್ಚರಿಕೆಯೊಂದಿಗೆ ಅದನ್ನೇ ಪರ್ಯಾಯವಾಗಿ ಬಳಸುತ್ತದೆ.

`workflow_dispatch` ರನ್ಗಳು, release-green ಸ್ವೀಪ್ ಮತ್ತು ರಾತ್ರಿಯ headroom ಜಾಬ್ಗೆ PR ಬೇಸ್
ಇರುವುದಿಲ್ಲ ಮತ್ತು ಅವು ಸಂಪೂರ್ಣ (ಜಾಗತಿಕ) ಹೋಲಿಕೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಕವರೇಜ್, ಡುಪ್ಲಿಕೇಶನ್ ಮತ್ತು type-coverage ಸದ್ಯಕ್ಕೆ ಜಾಗತಿಕವಾಗಿಯೇ
ಉಳಿಯುತ್ತವೆ (ಅವುಗಳ ಪರಿಕರಗಳು ಪ್ರತಿ-ಫೈಲ್ diff ಅನ್ನು ಕಡಿಮೆ ವೆಚ್ಚದಲ್ಲಿ ಉತ್ಪಾದಿಸುವುದಿಲ್ಲ) — ಇವುಗಳಿಗೂ ಇದೇ ವಿಧಾನವನ್ನು ಅನ್ವಯಿಸಬಹುದು.

**v4.0 ನಲ್ಲಿ ಹಂತವನ್ನು ಮುಕ್ತಾಯಗೊಳಿಸುವುದು (LTS = ಹಿಂದಿಗಿಂತ ಹೆಚ್ಚು ಕಟ್ಟುನಿಟ್ಟು, "back to normal" ಅಲ್ಲ)**

1. ಶುದ್ಧ `release/v4.0.0` ತುದಿಯಲ್ಲಿ: ದಾಖಲಿಗಾಗಿ `npm run quality:headroom --json`, ನಂತರ
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ಪ್ರತಿ typecheck ಗೇಟ್ನ
   `--update` — ಪ್ರತಿಯೊಂದು ಬೇಸ್ಲೈನ್ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕೆ ಇಳಿಯುತ್ತದೆ.
2. `quality-baseline.json` ನಿಂದ `_policy` ಅನ್ನು ಅಳಿಸಿ (`--require-tighten` ಮತ್ತು ರಾತ್ರಿಯ

3. ಮಾಡ್ಯುಲರೈಸೇಶನ್ ಫಲ ನೀಡಿದ ಕಡೆಗಳಲ್ಲಿ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕಿಂತಲೂ ಹೆಚ್ಚು ಕಟ್ಟುನಿಟ್ಟುಗೊಳಿಸಿ: file-size `cap` ಅನ್ನು ಮತ್ತೆ 1000
   (ಅಥವಾ 800) ಗೆ, ಕವರೇಜ್ ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು +5 ಗೆ, ಮಾಡ್ಯುಲರೈಸ್ ಮಾಡಿದ ಪ್ಯಾಕೇಜ್ಗಳಿಗೆ dead exports ಅನ್ನು 0 ಗೆ ಹೊಂದಿಸಿ.

## ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ (`quality-baseline.json`)

ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ಅನ್ನು ಓದಿ,
ಹೊಸದಾಗಿ ಸಂಗ್ರಹಿಸಲಾದ `quality-metrics.json` ಜೊತೆ ಹೋಲಿಸುತ್ತದೆ. ಯಾವುದೇ ಮೆಟ್ರಿಕ್ ಅದರ ಎಪ್ಸಿಲಾನ್ಗಿಂತ
ಹೆಚ್ಚು ಹಿಂಜರಿದರೆ, ಬಿಲ್ಡ್ ವಿಫಲವಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿರುವ ಮೆಟ್ರಿಕ್ಗಳು:

| ಮೆಟ್ರಿಕ್              | ದಿಕ್ಕು | ಅರ್ಥ                                  |
| --------------------- | ------ | ------------------------------------- |
| `eslintWarnings`      | `down` | ESLint ಎಚ್ಚರಿಕೆಗಳ ಸಂಖ್ಯೆ ಹೆಚ್ಚಾಗಬಾರದು |
| `coverage.statements` | `up`   | ಸ್ಟೇಟ್ಮೆಂಟ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು      |
| `coverage.lines`      | `up`   | ಲೈನ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು             |
| `coverage.functions`  | `up`   | ಫಂಕ್ಷನ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು          |
| `coverage.branches`   | `up`   | ಬ್ರಾಂಚ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು          |

ನೈಜ ಸುಧಾರಣೆಯ ನಂತರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ನವೀಕರಿಸಲು:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` ಫ್ಲ್ಯಾಗ್ ಪ್ರಸ್ತುತ ಅಳೆಯಲಾದ ಮೌಲ್ಯಗಳನ್ನು `quality-baseline.json` ಗೆ ಬರೆಯುತ್ತದೆ.
ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸಿದ ಬದಲಾವಣೆಯ ಜೊತೆಯಲ್ಲೇ ಈ ಫೈಲ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ. ಬೇಸ್ಲೈನ್ ಅನ್ನು
ನವೀಕರಿಸದೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸುವ PR ಅನ್ನು `--require-tighten` ಪತ್ತೆಹಚ್ಚುತ್ತದೆ (ಹಂತ 6A.5,
ಅನುಷ್ಠಾನ ಬಾಕಿಯಿದೆ).

### CodeQL ರ್ಯಾಚೆಟ್: ರಿಫ್ರೆಶ್ ಆವರ್ತನೆ ಮತ್ತು ಹಸ್ತಚಾಲಿತ ಟ್ರಿಗರ್

`check:codeql-ratchet` **ರೆಪೊ ಸ್ಥಿತಿಯನ್ನು ಓದುತ್ತದೆ; ಅದನ್ನು ವೇಳಾಪಟ್ಟಿಯ ಪ್ರಕಾರ ರಿಫ್ರೆಶ್ ಮಾಡಲಾಗುತ್ತದೆ — ಪ್ರತಿ PR ಗೆ ಅಲ್ಲ.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ವರದಿ ಮಾಡುವ
`state: configured`, `schedule: weekly` ಎಂಬುದು GitHub ನ ಡೀಫಾಲ್ಟ್-ಸೆಟಪ್ ಸ್ಕ್ಯಾನ್ ಆಗಿದ್ದು,
ಪ್ರತಿ ಪುಶ್ಗೆ ನಡೆಯುವ ವಿಶ್ಲೇಷಣೆಯಲ್ಲ. ಪರಿಣಾಮ: ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸುವ PR ವಿಲೀನಗೊಂಡ ನಂತರವೂ,
ಮುಂದಿನ ನಿಗದಿತ ಸ್ಕ್ಯಾನ್ ನಡೆಯುವವರೆಗೆ ರ್ಯಾಚೆಟ್ ಹಳೆಯ, ಹೆಚ್ಚಿನ ಸಂಖ್ಯೆಯನ್ನೇ ಓದುತ್ತಿರುತ್ತದೆ —
ಆದ್ದರಿಂದ ಸ್ಕ್ಯಾನ್ ನವೀಕರಿಸುವವರೆಗೆ, ಸರಿಪಡಿಸಿದ PR ನ ಸ್ವಂತ ಫಾಲೋ-ಅಪ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಪ್ರತಿಯೊಂದು
ತೆರೆದ PR ನಲ್ಲಿಯೂ ಅದು ಹಿಂಜರಿತವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

**ಹಸ್ತಚಾಲಿತ ರಿಫ್ರೆಶ್**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ವಿಶ್ಲೇಷಣೆಯನ್ನು
ಮತ್ತೆ ಚಲಾಯಿಸಿ, ಕೆಲವೇ ನಿಮಿಷಗಳಲ್ಲಿ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಮರುಪ್ರಕಟಿಸುತ್ತದೆ. ಮೊದಲು `.github/workflows/codeql.yml`
ಓದಿ — GitHub ನ **"default setup" ಜೊತೆಗೆ ಅದು ಸಂಘರ್ಷಿಸುವುದರಿಂದಲೇ** ಇದು `workflow_dispatch`-ಗೆ ಮಾತ್ರ
ಸೀಮಿತವಾಗಿದೆ ಎಂದು ಅದರ ಹೆಡರ್ ವಿವರಿಸುತ್ತದೆ (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). `push`/`pull_request`/
`schedule` ಟ್ರಿಗರ್ಗಳನ್ನು ಮರುಸ್ಥಾಪಿಸಲು ಮೊದಲು **ಮಾಲೀಕರ ಕ್ರಮ** ಅಗತ್ಯ: Settings → Code security →
CodeQL: Default → Advanced. ಆ ಬದಲಾವಣೆ ಮಾಡದೆ `schedule:` ಟ್ರಿಗರ್ ಸೇರಿಸಬೇಡಿ — ಅದು
ವಿಫಲಗೊಳ್ಳುವ ರನ್ಗಳನ್ನು ಮಾತ್ರ ಉಂಟುಮಾಡುತ್ತದೆ.

**ಸಂಖ್ಯೆ ಕಡಿಮೆಯಾದ ನಂತರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ಬಿಗಿಗೊಳಿಸಿ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ಹೊಸದಾಗಿ ಅಳೆಯಲಾದ ಸಂಖ್ಯೆಯನ್ನು `quality-baseline.json` →

ರ್ಯಾಚೆಟ್ ಮೌನವಾಗಿ ಅನುಮತಿಸುವುದಿಲ್ಲ. ಕಾರ್ಯನಿರ್ವಹಿತ ಉದಾಹರಣೆ (2026-09-02/03): PR #12502 ನೈಜವಾದ
7 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸಿತು (ಅಳೆಯಲಾದ ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳು 13 → 6); ಅದಕ್ಕೆ ಹೊಂದುವಂತೆ PR #12530

ಎಚ್ಚರಿಕೆಗೆ ಪ್ರತ್ಯೇಕ ಸಮರ್ಥನೆ ನೀಡಿ ವಜಾಗೊಳಿಸಿ, ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳ ಸಂಖ್ಯೆಯನ್ನು 0 ಗೆ ಇಳಿಸಲಾಯಿತು.

**ವಜಾಗೊಳಿಸುವಿಕೆಗಳು ಆಪರೇಟರ್ನ ನಿರ್ಧಾರ (ಕಠಿಣ ನಿಯಮ #14)** — ವಜಾಗೊಳಿಸುವಿಕೆಯ ಕಾಮೆಂಟ್ನಲ್ಲಿ

("ಈಗಲೇ ಸರಿಪಡಿಸಿ" ಮಿತಿ), ಪ್ರತಿ ಪೈಪ್ಲೈನ್ಗೆ ≥95% ಉತ್ತೀರ್ಣ ದರ. ಇವು ಉದ್ಯಮದ ಉಲ್ಲೇಖ ಮೌಲ್ಯಗಳು —
ನಮ್ಮ ಸ್ವಂತ ಮಾಪನಗಳಿಗೆ ಅನುಗುಣವಾಗಿ ಮರುಮಾಪನಾಂಕ ಮಾಡಿ.

## ರಿಲೀಸ್-ಮಟ್ಟದ ರ್ಯಾಚೆಟ್ ಡ್ರಿಫ್ಟ್ (WS5.5, v3.8.49)

PURE ರಿಲೀಸ್ ಟಿಪ್ನಲ್ಲಿ ಒಂದು ರ್ಯಾಚೆಟ್ (ಫೈಲ್ ಗಾತ್ರ, ಸಂಕೀರ್ಣತೆ, eslint ಎಚ್ಚರಿಕೆಗಳು) ಹಿಮ್ಮೆಟ್ಟಿದಾಗ —
ಅಂದರೆ, ಮರ್ಜ್ಗಳ ಸಂಯೋಜನೆಯು ಅದನ್ನು ಹಿಮ್ಮೆಟ್ಟಿಸಿದೆ ಮತ್ತು ಯಾವುದೇ ಒಂದು PR ತನ್ನದೇ ಬ್ರಾಂಚ್ನಲ್ಲಿ ಆ
ರಿಗ್ರೆಷನ್ ಅನ್ನು ಪುನರುತ್ಪಾದಿಸುವುದಿಲ್ಲವಾದರೆ — ಅದನ್ನು ಸರಿಪಡಿಸುವ ಹೊಣೆ **ರಿಲೀಸ್ ಕ್ಯಾಪ್ಟನ್ಗೆ, ಒಮ್ಮೆ ಮಾತ್ರ,
ರಿಲೀಸ್ ಬ್ರಾಂಚ್ನಲ್ಲಿ** ಸೇರಿದೆ: ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್/ರಿಫ್ಯಾಕ್ಟರ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ; ದಾಖಲಿಸಲಾದ
ಸಮರ್ಥನೆ ನಮೂದಿನೊಂದಿಗೆ ಮಾತ್ರ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಿ. ಸಂಯೋಜನೆಯಿಂದಾದ ಡ್ರಿಫ್ಟ್ ಅನ್ನು ಕೊಡುಗೆದಾರರ PR ಮೇಲೆ ಎಂದಿಗೂ
ಹೊರಿಸಬೇಡಿ ಮತ್ತು ಪ್ರತಿ-PR ಗೆ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಬೇಡಿ (ಅದು ನೈಜ ರಿಗ್ರೆಷನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ). ಮೊದಲು ವ್ಯತ್ಯಾಸವನ್ನು ಗುರುತಿಸಿ:
ನಿಮ್ಮ PR ಅದಕ್ಕೆ ಕಾರಣವೆಂದು ಊಹಿಸುವ ಮೊದಲು ಪ್ರೋಬ್ ವರ್ಕ್ಟ್ರೀಯಲ್ಲಿ ಶುದ್ಧ ಟಿಪ್ ವಿರುದ್ಧದ ಕೆಂಪು ಸ್ಥಿತಿಯನ್ನು ಪುನರುತ್ಪಾದಿಸಿ.

## ರ್ಯಾಚೆಟ್ ಇಳಿಕೆಗಳನ್ನು ಬ್ಯಾಂಕ್ ಮಾಡುವುದು — ಕೆಳಮುಖ ದಿಕ್ಕು (#8584)

ರ್ಯಾಚೆಟ್ ಅರ್ಧದಷ್ಟು ಮಾತ್ರ ಸ್ವಯಂಚಾಲಿತವಾಗಿದೆ, ಮತ್ತು ಅದು ತಪ್ಪಾದ ಅರ್ಧವಾಗಿದೆ. ಮಿತಿಯನ್ನು **ಹೆಚ್ಚಿಸುವುದು**
ಹತ್ತು ಸೆಕೆಂಡ್ ತೆಗೆದುಕೊಳ್ಳುವ ಕೈಯಾರೆ JSON ತಿದ್ದುಪಡಿಯಾಗಿದ್ದು, ಕೆಂಪಾಗಿರುವ PR ಅನ್ನು ಅನ್ಬ್ಲಾಕ್ ಮಾಡುವ ಅತ್ಯಂತ ವೇಗದ ವಿಧಾನವಾಗಿದೆ.
ಮಿತಿಯನ್ನು **ಕಡಿಮೆ ಮಾಡಲು** ಯಾರಾದರೂ `--update` ಚಲಾಯಿಸಿ ಫಲಿತಾಂಶವನ್ನು ಕಮಿಟ್ ಮಾಡಬೇಕು — ಮತ್ತು
`bank-ratchet-shrinks` ಜಾಬ್ ಬರುವವರೆಗೂ, ಯಾವುದೇ ವರ್ಕ್ಫ್ಲೋ ಅದನ್ನು ಚಲಾಯಿಸುತ್ತಿರಲಿಲ್ಲ. ಮಾಪನ ಮಾಡಿದ ಪರಿಣಾಮ
(2026-07-25): ಈಗಾಗಲೇ 800-ಸಾಲಿನ ಹೊಸ-ಫೈಲ್ ಮಿತಿಯಲ್ಲಿ ಅಥವಾ ಅದಕ್ಕಿಂತ ಕೆಳಗಿರುವ 18 ಸ್ಥಗಿತಗೊಳಿಸಿದ ಫೈಲ್ಗಳು, ಅತ್ಯಂತ ಕೆಟ್ಟದ್ದು
132× (`src/shared/validation/schemas.ts`, 2,523 ಮಿತಿಯನ್ನು ಹೊಂದಿರುವ 19 ಸಾಲುಗಳು); ಸಂಕೀರ್ಣತೆಯ ಗರಿಷ್ಠ ಮಿತಿ

ಅದಕ್ಕೆ ಕಾರಣವಾದ ಕೋಡ್ಗಿಂತಲೂ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯುವ ಮಿತಿಯು, ಪೂರ್ಣಗೊಂಡ ಪ್ರತಿಯೊಂದು ವಿಭಜನೆಯನ್ನು ಆ ಫೈಲ್ ಅನ್ನು ಮುಂದಿನ ಬಾರಿ
ತಿದ್ದುಪಡಿ ಮಾಡುವವರಿಗೆ ಬೆಳವಣಿಗೆಯ ಅನುಮತಿಯಾಗಿ ಮೌನವಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ.

### ಸುರಕ್ಷತಾ ಪರಿಶೀಲಕ

ಜಾಬ್ ಮೇಲ್ವಿಚಾರಣೆಯಿಲ್ಲದೆ ಬೇಸ್ಲೈನ್ಗಳಿಗೆ ಬರೆಯುತ್ತದೆ, ಆದ್ದರಿಂದ `verify-ratchet-bank.mjs` ಅದನ್ನು
ಸ್ವೀಕಾರಾರ್ಹವಾಗಿಸುತ್ತದೆ. ಅದು `--update` ನಂತರದ ಟ್ರೀ ಅನ್ನು `HEAD` ವಿರುದ್ಧ diff ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು
ಬದಲಾವಣೆಯೂ ಕೆಳಗಿನವುಗಳಲ್ಲಿ ಒಂದಾಗಿರದಿದ್ದರೆ, **ಯಾವುದೇ ಕಮಿಟ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು ಜಾಬ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ**
— ಯಾವುದೇ PR ತೆರೆಯುವುದಿಲ್ಲ:

- `frozen` / `testFrozen` ಸಂಖ್ಯಾತ್ಮಕ ನಮೂದನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ** ಅಥವಾ **ತೆಗೆದುಹಾಕಲಾಗಿದೆ**
- `complexity-baseline.json` → `count` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**

ಬೇರಾವುದೇ ಬದಲಾವಣೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ: ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸುವುದು, ನಮೂದನ್ನು ಸೇರಿಸುವುದು, `cap`/`testCap` ಅನ್ನು ಬದಲಿಸುವುದು ಅಥವಾ
`_rebaseline_*` ಟಿಪ್ಪಣಿಯನ್ನು ಅಳಿಸುವುದು/ಮರುಬರೆಯುವುದು (ಪ್ರತಿ ಗರಿಷ್ಠ ಮಿತಿ ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ ಎಂಬುದಕ್ಕೆ ಆ ಟಿಪ್ಪಣಿಗಳು ಆಡಿಟ್ ದಾಖಲೆಯಾಗಿದ್ದು,
ಫೈಲ್ ನಮೂದುಗಳಂತೆಯೇ ಅದೇ `frozen` ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ).
ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಬಲ್ಲ ಬಾಟ್ ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಗಿಂತ ಖಂಡಿತವಾಗಿಯೂ ಕೆಟ್ಟದಾಗಿರುತ್ತದೆ. ರಿಗ್ರೆಷನ್
ಗಾರ್ಡ್: `tests/unit/verify-ratchet-bank.test.ts`.

ಜಾಬ್ ಎಂದಿಗೂ `release/*` ಗೆ push ಮಾಡುವುದಿಲ್ಲ — ಒಬ್ಬ ವ್ಯಕ್ತಿ PR ಅನ್ನು ಮರ್ಜ್ ಮಾಡುತ್ತಾರೆ, ಆದ್ದರಿಂದ ತಪ್ಪಾದ ಮಾಪನವು
ಪರಿಶೀಲಿಸದೆ ಸೇರಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಅನುಮತಿ ಪಟ್ಟಿ ನೀತಿ

ಪೂರ್ವ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉಲ್ಲಂಘನೆಗಳಲ್ಲಿ ವಿಫಲವಾಗದ ಪ್ರತಿ ಗೇಟ್ ಫ್ರೀಜ್ ಅನುಮತಿಪಟ್ಟಿಯನ್ನು ಬಳಸುತ್ತದೆ (ಉದಾ, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). ನೀತಿ ಹೀಗಿದೆ:

**ಮೂಲ ಕಾರಣವನ್ನು ಸರಿಪಡಿಸಿ; ಉಲ್ಲಂಘನೆಯು ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವಾಗ ಮತ್ತು ಅದೇ PR ನಲ್ಲಿ ಸರಿಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ ಮಾತ್ರ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸಿ.**

ಅನುಮತಿ ಪಟ್ಟಿಗೆ ನಮೂದನ್ನು ಸೇರಿಸುವಾಗ:

1. ಸಮರ್ಥನೆಯೊಂದಿಗೆ ಕಾಮೆಂಟ್ ಅನ್ನು ಸೇರಿಸಿ.
2. ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯನ್ನು ಉಲ್ಲೇಖಿಸಿ (ಉದಾ, `// #3498 — Phase 2 feature, not yet implemented`).
3. ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸುವ ಅದೇ PR ನಲ್ಲಿನ ನಮೂದನ್ನು ತೆಗೆದುಹಾಕಿ — ಇನ್ನು ಮುಂದೆ ಸಕ್ರಿಯ ಉಲ್ಲಂಘನೆಯನ್ನು ನಿಗ್ರಹಿಸದ ಹಳೆಯ ನಮೂದು ಸ್ವತಃ ದೋಷವಾಗಿದೆ (6A.3 ಸ್ಥಬ್ದ-ಜಾರಿಯು ಒಮ್ಮೆ ಕಾರ್ಯಗತಗೊಳಿಸಿದ ಅನಾಥ ಅನುಮತಿ ಪಟ್ಟಿಯ ಪ್ರವೇಶದ ಮೇಲೆ ಗೇಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ).

ಮಾಡು** ಅಲ್ಲ** ಪರೀಕ್ಷೆಗಳು ವೇಗವಾಗಿ ಉತ್ತೀರ್ಣರಾಗಲು ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದುಗಳನ್ನು ಸೇರಿಸಿ. ಬೆಳೆಯುತ್ತಿರುವ ಅನುಮತಿ ಪಟ್ಟಿಯೊಂದಿಗೆ ಹಸಿರು ಗೇಟ್ ಗುಣಮಟ್ಟದ ತಪ್ಪು ಅರ್ಥವಾಗಿದೆ.

### ನಿಮ್ಮ PR ನಲ್ಲಿ ಗೇಟ್ ವಿಫಲವಾದಾಗ

1. **ಗೇಟ್ ಔಟ್ಪುಟ್ ಅನ್ನು ಎಚ್ಚರಿಕೆಯಿಂದ ಓದಿ** — ಇದು ನಿಖರವಾಗಿ ಯಾವ ಫೈಲ್ ಅಥವಾ ಚಿಹ್ನೆಯು ನಿಯಮವನ್ನು ಉಲ್ಲಂಘಿಸಿದೆ ಎಂದು ನಿಮಗೆ ತಿಳಿಸುತ್ತದೆ.
2. **ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸಿ** — ಹೆಚ್ಚಿನ ಗೇಟ್ಗಳು ಡಿಟರ್ಮಿನಿಸ್ಟಿಕ್ ಫೈಲ್ಸಿಸ್ಟಮ್ ಚೆಕ್ಗಳಾಗಿವೆ, ಅದು ಕೋಡ್ ಸರಿಯಾಗಿದ್ದ ತಕ್ಷಣ ಹಾದುಹೋಗುತ್ತದೆ.
3. **ಉಲ್ಲಂಘನೆಯು ಮೊದಲೇ ಇದ್ದರೆ** (ಅಂದರೆ, ನೀವು ಅದನ್ನು ಪರಿಚಯಿಸಲಿಲ್ಲ ಆದರೆ ಗೇಟ್ ಈಗ ಅದನ್ನು ಆವರಿಸುತ್ತದೆ): ಸಮರ್ಥನೆ ಕಾಮೆಂಟ್ ಮತ್ತು ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯೊಂದಿಗೆ ಅನುಮತಿ ಪಟ್ಟಿಯ ನಮೂದನ್ನು ಸೇರಿಸಿ.
4. **ಗೇಟ್ ರಾಟ್ಚೆಟ್ ಆಗಿದ್ದರೆ** (ಕವರೇಜ್, ESLint ಎಚ್ಚರಿಕೆಗಳು, ನಕಲು, ಸಂಕೀರ್ಣತೆ): ನಿಮ್ಮ ಬದಲಾವಣೆಯು ಮೆಟ್ರಿಕ್ ಅನ್ನು ಇನ್ನಷ್ಟು ಹದಗೆಡಿಸಿದೆ. ಆಧಾರವಾಗಿರುವ ಸಮಸ್ಯೆಯನ್ನು ಸರಿಪಡಿಸಿ, ಅಥವಾ (ವಿರಳವಾಗಿ) ಬದಲಾವಣೆಯು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದ್ದರೆ ಮತ್ತು `npm run quality:ratchet -- --update` ರನ್ ಮಾಡಿ ಮತ್ತು ಮೆಟ್ರಿಕ್ ಅವನತಿಯು ಸ್ವೀಕಾರಾರ್ಹ — ಆದರೆ PR ವಿವರಣೆಯಲ್ಲಿ ಏಕೆ ಎಂದು ದಾಖಲಿಸಿ.
5. **ಸಲಹಾ ದ್ವಾರಗಳು** (`continue-on-error: true`) ಮಾಹಿತಿ — ಅವು ವಿಲೀನವನ್ನು ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ ಆದರೆ CI ಸಾರಾಂಶದಲ್ಲಿ ಗೋಚರಿಸುತ್ತವೆ. ಹೇಗಾದರೂ ಅವುಗಳನ್ನು ಸರಿಪಡಿಸಿ.

## ಹೊಸ ಗೇಟ್ ಸೇರಿಸುವುದು

1. `scripts/check/check-<name>.mjs` (ಅಥವಾ `.ts`) ರಚಿಸಿ. ನೀತಿ ಗೇಟ್ಗಳು 0/1 ಸ್ಥಿತಿಯೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತವೆ.
   ರ್ಯಾಚೆಟ್-ಶೈಲಿಯ ಗೇಟ್ಗಳು `collect-metrics.mjs` ಮೂಲಕ `quality-metrics.json` ಗೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹೊರಸೂಸುತ್ತವೆ.
2. `package.json` ಗೆ `"check:<name>": "node scripts/check/check-<name>.mjs"` ಸೇರಿಸಿ.
3. ಸೂಕ್ತ ಜಾಬ್ ಅಡಿಯಲ್ಲಿ `.github/workflows/ci.yml` ನಲ್ಲಿ ಅದನ್ನು ಜೋಡಿಸಿ
   (ನೀತಿ → `lint` ಅಥವಾ `docs-sync-strict`; ರ್ಯಾಚೆಟ್ → `quality-gate`).
4. ಅದಕ್ಕೆ ಅನುಮತಿ ಪಟ್ಟಿ ಇದ್ದರೆ, ಹಳತಾದ ನಮೂದುಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪತ್ತೆಯಾಗುವಂತೆ
   `scripts/check/lib/allowlist.mjs` ನಿಂದ `reportStaleEntries()` ಅನ್ನು ಅನ್ವಯಿಸಿ.
5. ಗೇಟ್ನ ಪತ್ತೆ ತರ್ಕವನ್ನು ಒಳಗೊಂಡ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/build/` ನಲ್ಲಿ ಬರೆಯಿರಿ.
6. ಈ ಡಾಕ್ಯುಮೆಂಟ್ ಅನ್ನು ನವೀಕರಿಸಿ (ಸಂಬಂಧಿತ ಜಾಬ್ ಟೇಬಲ್ಗೆ ಒಂದು ಸಾಲನ್ನು ಸೇರಿಸಿ).

## ತರ್ಕಬದ್ಧ ಬ್ಯಾಕ್ಲಾಗ್ (ROI ವಿಮರ್ಶೆ — Fase 9 Onda 3)

ಈ ದಾಸ್ತಾನು 2026-06-17 ರಂದು `ci.yml` ವಿರುದ್ಧ ಸಮನ್ವಯಗೊಳಿಸಲಾಗಿದೆ (ಹಿಂದಿನ ಆವೃತ್ತಿಯು ಬಿಟ್ಟುಬಿಡಲಾಗಿದೆ `audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`, `check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`, `check:codeql-ratchet`, `check:pr-evidence`). ಸಮನ್ವಯಗೊಳಿಸಿದ ಗುಂಪಿನ ROI ವಿಮರ್ಶೆಯು ಈ ಕೆಳಗಿನ ತರ್ಕಬದ್ಧಗೊಳಿಸುವ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಗುರುತಿಸಿದೆ.** ವಿಲೀನಗಳು ಯಾಂತ್ರಿಕ CI ಬದಲಾವಣೆಗಳಾಗಿವೆ; flips/drops ಆಪರೇಟರ್ಗೆ ಕಾಯ್ದಿರಿಸಿದ ನೀತಿ ನಿರ್ಧಾರಗಳಾಗಿವೆ.** ಕೆಳಗಿನ ಯಾವುದನ್ನೂ ಇನ್ನೂ ಅನ್ವಯಿಸಲಾಗಿಲ್ಲ.

**ಮೇಲೆ ದಾಖಲೆಗಳಿಲ್ಲ** (ಸಲಹೆ, ಕಡಿಮೆ ಸಂಕೇತ): `docs-lint` ಕೆಲಸ (markdownlint + Vale, whole job `continue-on-error`) ಮತ್ತು ಸ್ವತಂತ್ರ ಸ್ಕ್ಯಾನರ್ ವರ್ಕ್ಫ್ಲೋಗಳು `semgrep.yml` / `codeql.yml` / `scorecard.yml`. `semgrepFindings: 0` `quality-baseline.json` ನಲ್ಲಿದೆ ಆದರೆ `ci.yml` — ನಲ್ಲಿ ತಡೆಯುವ ರಾಟ್ಚೆಟ್ಗೆ ವೈರ್ ಮಾಡಲಾಗಿಲ್ಲ ಮೆಟ್ರಿಕ್ ಪ್ರಸ್ತುತ ಅನಾಥವಾಗಿದೆ.

### ವಿಲೀನ / ಕಡಿತ (ಯಾಂತ್ರಿಕ, ಕಡಿಮೆ ಅಪಾಯ)

ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯನ್ನು 2026-06-17 ರಂದು ಲೈವ್ ಗೇಟ್ ರಾಜ್ಯದ ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸಲಾಗಿದೆ (ನಂಬಿಕೆ-ಆದರೆ-ಪರಿಶೀಲಿಸಿ); ಹಲವಾರು "ಸ್ಪಷ್ಟ" ವಿಲೀನಗಳು ಸಾಲವನ್ನು ಮರೆಮಾಡಲು ಹೊರಹೊಮ್ಮಿದವು ಮತ್ತು ಅವು** ಅಲ್ಲ** ಕ್ಲೀನ್ ಡ್ರಾಪ್-ಇನ್ಗಳು.

- **`check:docs-sync` ಎರಡು ಬಾರಿ ಓಡುತ್ತದೆ** — ಸ್ವತಂತ್ರವಾಗಿ `lint` ಕೆಲಸದಲ್ಲಿ ಮತ್ತು ಮತ್ತೆ ಒಳಗೆ `check:docs-all` (`docs-sync-strict`) ಮತ್ತು ಹಸ್ಕಿ ಪೂರ್ವ ಕಮಿಟ್ ಹುಕ್. ✅**DONE** — ಸ್ವತಂತ್ರ `lint` ಆಹ್ವಾನವನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ.
- **CVE ಸ್ಕ್ಯಾನಿಂಗ್** — ❌**NOT ಒಂದು ಕ್ಲೀನ್ ವಿಲೀನ.** `audit:deps` ಎಲ್ಲಾ ಐದು ಲಾಕ್ಫೈಲ್ಗಳಲ್ಲಿ ನಿರ್ಣಾಯಕ ಸಲಹೆಗಳು ಮತ್ತು ಅಪೂರ್ಣ ಲೆಕ್ಕಪರಿಶೋಧನೆಗಳನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ, ಆದರೆ ಪ್ರಸ್ತುತ ನೀತಿಯ ಅಡಿಯಲ್ಲಿ ಹೆಚ್ಚಿನ ಸಲಹೆಗಳನ್ನು ಎಚ್ಚರಿಕೆಗಳಾಗಿ ವರದಿ ಮಾಡುತ್ತದೆ; `check:vuln-ratchet` (osv) _regression_ ವಿರುದ್ಧ ಚೆಕ್-ಇನ್ ಬೇಸ್ಲೈನ್ನಲ್ಲಿ ಮಾತ್ರ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಅಗತ್ಯವಿದ್ದಾಗ ಕಾಣೆಯಾದ ಅಳತೆಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ವಿಭಿನ್ನ ಅರ್ಥಶಾಸ್ತ್ರ — ಡ್ರಾಪ್ `audit:deps` ಸಂಪೂರ್ಣ ನಿರ್ಣಾಯಕ ಗೇಟ್ ಮತ್ತು ಸ್ವತಂತ್ರ ಪ್ಯಾಕೇಜ್ ಆಡಿಟ್ ರಸೀದಿಗಳನ್ನು ಕಳೆದುಕೊಳ್ಳುತ್ತದೆ. ಎರಡನ್ನೂ ಇಟ್ಟುಕೊಳ್ಳಿ.
- **ಸೈಕಲ್ ಪತ್ತೆ** — ✅**DONE** (#15159 G-01/G-02). ಇಲ್ಲಿರುವ ಹಳೆಯ ಪಠ್ಯವು `check:cycles` "ಹಸಿರು, ಕ್ಯುರೇಟೆಡ್" ಗೇಟ್ ಎಂದು ಕರೆಯುತ್ತದೆ ಮತ್ತು `check:circular-deps` (dpdm) 91 ಚಕ್ರಗಳನ್ನು ವರದಿ ಮಾಡಿರುವುದರಿಂದ ಅದನ್ನು ನಿರ್ಬಂಧಿಸುವುದನ್ನು ಸಮರ್ಥಿಸುತ್ತದೆ. ಆ ಹಸಿರು ಎ** ಸುಳ್ಳು ಹಸಿರು** : `check:cycles` 5 ಉಪ ಡೈರೆಕ್ಟರಿಗಳನ್ನು (450 ಫೈಲ್ಗಳು) ಸ್ಕ್ಯಾನ್ ಮಾಡಿದೆ, ಕೇವಲ ಸ್ಟ್ಯಾಟಿಕ್ `import|export … from` ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ `@/` ಮತ್ತು `@omniroute/open-sse/` ಸ್ಪೆಸಿಫೈಯರ್ ಅನ್ನು ಕೈಬಿಟ್ಟಿದೆ, ಆದ್ದರಿಂದ ರೆಪೊದಲ್ಲಿ ಪ್ರಾಬಲ್ಯ ಹೊಂದಿರುವ ಡೈನಾಮಿಕ್-ಆಮದು + ಅಲಿಯಾಸ್ ಸೈಕಲ್ಗಳನ್ನು ನೋಡಲು ಸಾಧ್ಯವಾಗಲಿಲ್ಲ. ಸ್ಥಿರವಾಗಿದೆ: ಗೇಟ್ ಈಗ `src` + `open-sse` (5023 ಫೈಲ್ಗಳು), TypeScript AST ನಿಂದ ಸ್ಪೆಸಿಫೈಯರ್ಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ (ಆದ್ದರಿಂದ `import("…")` ಎಣಿಕೆಗಳು ಮತ್ತು ಟೈಪ್-ಪೋಸಿಷನ್ `typeof import("…")` ಅಲ್ಲ), ಮತ್ತು tsconfig `paths` ಪರಿಹರಿಸುತ್ತದೆ. ಇದು ಕಂಡುಕೊಳ್ಳುತ್ತದೆ** 14** ಚಕ್ರಗಳು, 0 ಅಲ್ಲ. ಏಕೆಂದರೆ 14 ಪೂರ್ವ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಚಕ್ರಗಳನ್ನು ಗೇಟ್ PR ನಲ್ಲಿ ಸರಿಪಡಿಸಲಾಗುವುದಿಲ್ಲ, `check:cycles` ಈಗ a** ರಾಟ್ಚೆಟ್** (`--ratchet`, `quality-baseline.json` ನಲ್ಲಿ ಸೀಲಿಂಗ್ `metrics.cycles.value = 14`, `direction: down`) — ಇದು ಯಾವುದೇ _regression_ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಮತ್ತು ಎಣಿಕೆ ಮಾತ್ರ ಬೀಳಬಹುದು.
