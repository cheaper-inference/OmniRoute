OmniRoute ಮೂರು ವಿಭಿನ್ನ ಆದರೆ ಸಂಬಂಧಿತ ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ ಕಾರ್ಯವಿಧಾನಗಳನ್ನು ಹೊಂದಿದೆ. ಪ್ರತಿಯೊಂದಕ್ಕೂ ವಿಭಿನ್ನ ವ್ಯಾಪ್ತಿ ಮತ್ತು ಉದ್ದೇಶವಿದೆ. ರೂಟಿಂಗ್ ನಡವಳಿಕೆಯನ್ನು ಡೀಬಗ್ ಮಾಡುವಾಗ ಅವುಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಇರಿಸಿ.

![3-layer resilience model](../diagrams/exported/resilience-3layers.svg)

> ಮೂಲ: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd)

> **ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ ಟಾಗಲ್ಗಳಿಗೆ Env-vs-ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪ್ರಾಶಸ್ತ್ಯ.** ಆಯ್ಕೆಯ ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವವು ಪರಿಸರದಿಂದ — `QUOTA_PREFLIGHT_CUTOFF_ENABLED`, `PROVIDER_COOLDOWN_ENABLED`, `STREAM_RECOVERY_ENABLED`, `STREAM_RECOVERY_MIDSTREAM_ENABLED`, `STREAM_THROUGHPUT_WATCHDOG_ENABLED` — ಅನ್ನು ಟಾಗಲ್ ಮಾಡುತ್ತದೆ _default_ (`DEFAULT_RESILIENCE_SETTINGS`, `src/lib/resilience/settings.ts`) ಅನ್ನು ಮಾತ್ರ ಪೂರೈಸುತ್ತದೆ. ಒಂದು ಬೂಲಿಯನ್ `resilienceSettings` (ಡ್ಯಾಶ್ಬೋರ್ಡ್ →** ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ** / `PATCH /api/resilience`, `key_value` ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ ) env ಮೌಲ್ಯದ ಮೇಲೆ ಗೆಲ್ಲುತ್ತದೆ: ಸಾಮಾನ್ಯೀಕರಣವು (`toBoolean`, `src/lib/resilience/settings/normalize.ts`) ಒಂದು ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದಾಗ ಸಂಗ್ರಹಿಸಲಾದ ಬೂಲಿಯನ್ ಅನ್ನು ಇರಿಸುತ್ತದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಈಗಾಗಲೇ `false` ಉಳಿಸಿರುವ ನಿಯೋಜನೆಯಲ್ಲಿ ಅಂತಹ env var ಅನ್ನು `true` ಗೆ ಹೊಂದಿಸುವುದರಿಂದ ಏನನ್ನೂ ಬದಲಾಯಿಸುವುದಿಲ್ಲ — ಟಾಗಲ್ ಅನ್ನು ಫ್ಲಿಪ್ ಇನ್ ಮಾಡಿ** ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ** (ಅಥವಾ ಸಂಗ್ರಹಿಸಿದ ಕ್ಷೇತ್ರವನ್ನು ತೆರವುಗೊಳಿಸಿ) ಬದಲಿಗೆ.

## 1. ಪ್ರೊವೈಡರ್ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್

**ವ್ಯಾಪ್ತಿ:** ಇಡೀ ಪ್ರೊವೈಡರ್ (ಉದಾ., `glm`, `openai`, `anthropic`).

**ಉದ್ದೇಶ:** ಅಪ್ಸ್ಟ್ರೀಮ್/ಸೇವಾ ಮಟ್ಟದಲ್ಲಿ ಪದೇ ಪದೇ ವಿಫಲವಾಗುತ್ತಿರುವ ಪ್ರೊವೈಡರ್ಗೆ ಟ್ರಾಫಿಕ್ ಕಳುಹಿಸುವುದನ್ನು ನಿಲ್ಲಿಸುವುದು.

**ಅನುಷ್ಠಾನ:**

- ಪ್ರಧಾನ ಕ್ಲಾಸ್: `src/shared/utils/circuitBreaker.ts`
- ವೈರಿಂಗ್: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- ಸ್ಥಿತಿ API: `GET /api/monitoring/health`
- ರಿಸೆಟ್ API: `POST /api/resilience/reset`
- ರ್ಯಾಪರ್ಗಳು: `open-sse/services/accountFallback.ts`
- DB ಟೇಬಲ್: `domain_circuit_breakers`

**ಸ್ಥಿತಿಗಳು:**

- `CLOSED` — ಸಾಮಾನ್ಯ ಟ್ರಾಫಿಕ್ ಅನುಮತಿಸಲಾಗಿದೆ
- `DEGRADED` — ಟ್ರಾಫಿಕ್ ಇನ್ನೂ ಅನುಮತಿಸಲಾಗಿದೆ, ಆದರೆ ಹೆಚ್ಚುತ್ತಿರುವ ಪ್ರೊವೈಡರ್ ವಿಫಲತೆಗಳನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿದೆ; ಸಾಕಷ್ಟು ಯಶಸ್ಸುಗಳಾದಾಗ, ಮಾನ್ಯ ಸಂಪರ್ಕ ಪರೀಕ್ಷೆಯಾದಾಗ, ಅಥವಾ ಕೊನೆಯ ವಿಫಲತೆಯ ಪ್ರಕಾರದ ಅತ್ಯುದ್ದನೆಯ `OPEN` ಹೋಲ್ಡ್ ಅವಧಿಯ ನಂತರ (ಅದರ `cooldownByKind` ಮೌಲ್ಯ, ಇಲ್ಲದಿದ್ದರೆ `resetTimeout`, × `maxBackoffMultiplier`, ಕನಿಷ್ಠ ಒಂದು ಕೂಲ್ಡೌನ್) ಹೊಸ ವಿಫಲತೆಯಾಗದಿದ್ದರೆ `CLOSED` ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ
- `OPEN` — ಪ್ರೊವೈಡರ್ ತಾತ್ಕಾಲಿಕವಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗಿದೆ; ಕಾಂಬೊ ರೂಟಿಂಗ್ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ
- `HALF_OPEN` — ರಿಸೆಟ್ ಟೈಮ್ಔಟ್ ಮುಗಿದಿದೆ; ಪ್ರೋಬ್ ವಿನಂತಿಯನ್ನು ಅನುಮತಿಸಲಾಗಿದೆ

**ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ ಡೀಫಾಲ್ಟ್ಗಳು (`open-sse/config/constants.ts`, ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು → ರೆಸಿಲಿಯನ್ಸ್ ನಲ್ಲಿ ಅನಾವರಣಗೊಂಡಿವೆ):**

| ವರ್ಗ    | ಡಿಗ್ರೇಡ್ ಆಗುವುದು | ಓಪನ್ ಆಗುವುದು | ರಿಸೆಟ್ ಟೈಮ್ಔಟ್ |
| ------- | ---------------- | ------------ | -------------- |
| OAuth   | 5 ವಿಫಲತೆಗಳು      | 8 ವಿಫಲತೆಗಳು  | 60s            |
| API-key | 7 ವಿಫಲತೆಗಳು      | 12 ವಿಫಲತೆಗಳು | 30s            |
| Local   | ಲೆಕ್ಕಹಾಕಲಾಗಿದೆ   | 2 ವಿಫಲತೆಗಳು  | 15s            |

`degradationThreshold` ಪ್ರೊವೈಡರ್ ಯಾವಾಗ `DEGRADED` ಗೆ ಪ್ರವೇಶಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ; `failureThreshold` ಅದು ಯಾವಾಗ ಓಪನ್ ಆಗುತ್ತದೆ ಮತ್ತು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ ಎಂಬುದನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ. ಸ್ಥಳೀಯ ಪ್ರೊವೈಡರ್ ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಇನ್ನೂ ರೆಸಿಲಿಯನ್ಸ್ ಸೆಟ್ಟಿಂಗ್ಗಳ ಪುಟದಲ್ಲಿ ಅನಾವರಣಗೊಳಿಸಲಾಗಿಲ್ಲ.

**ಟ್ರಿಪ್ ಕೋಡ್ಗಳು:** ಕೇವಲ ಪ್ರೊವೈಡರ್-ಮಟ್ಟದ ಸ್ಥಿತಿಗಳು `[408, 500, 502, 503, 504]`. ಖಾತೆ-ಮಟ್ಟದ ದೋಷಗಳಿಗೆ ಟ್ರಿಪ್ ಮಾಡಬೇಡಿ (ಹೆಚ್ಚಿನ 401/403/429 — ಅವು ಕೂಲ್ಡೌನ್ ಅಥವಾ ಲಾಕ್ಔಟ್ಗೆ ಸೇರಿದವು).

**ಲೇಜಿ ರಿಕವರಿ:** `OPEN` ಅವಧಿ ಮುಗಿದಾಗ, `getStatus()`, `canExecute()`, `getRetryAfterMs()` ಸ್ಥಿತಿಯನ್ನು `HALF_OPEN` ಗೆ ರಿಫ್ರೆಶ್ ಮಾಡುತ್ತವೆ. ಅದೇ ಓದುವಿಕೆಗಳು (ಮತ್ತು ಮುಂದಿನ ವಿಫಲತೆ) ಹಳೆಯಾದ `DEGRADED` ಅನ್ನು ಮತ್ತೆ `CLOSED` ಗೆ ಕ್ಷಯಿಸುತ್ತವೆ. ಬ್ಯಾಕ್ಗ್ರೌಂಡ್ ಟೈಮರ್ ಅಗತ್ಯವಿಲ್ಲ.

### ಆಪ್ಟ್-ಇನ್ ಜಾಗತಿಕ ಪ್ರೊವೈಡರ್ ಕೂಲ್ಡೌನ್ (ವಿಂಡೋ ಗೇಟ್)

ನಾಲ್ಕನೆಯ, **ಆಪ್ಟ್-ಇನ್** ಪದರ (`PROVIDER_COOLDOWN_ENABLED`, ಡೀಫಾಲ್ಟ್ **ಆಫ್**) `open-sse/services/providerCooldownTracker.ts` ನಲ್ಲಿ ವಿಫಲವಾಗುತ್ತಿರುವ ಪ್ರೊವೈಡರ್ಗಳ ಕ್ರಾಸ್-ರಿಕ್ವೆಸ್ಟ್ ಮೆಮೊರಿಯನ್ನು ಇರಿಸುತ್ತದೆ; ಕಾಂಬೊ ಟಾರ್ಗೆಟ್ ರೆಸಲ್ಯೂಶನ್ ಇದನ್ನು ಸಂಪರ್ಕಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಸತತ ಕಾಂಬೊ ವಿನಂತಿಗಳು ಈಗಷ್ಟೇ ವಿಫಲವಾದ ಪ್ರೊವೈಡರ್ ಅನ್ನು ಮತ್ತೆ ಹಾದುಹೋಗುವುದನ್ನು ನಿಲ್ಲಿಸುತ್ತವೆ. ಪ್ರೊವೈಡರ್-ಮಟ್ಟದ ಎಂಟ್ರಿಗಳು `PROVIDER_PROFILES` ವಿಂಡೋ ಗೇಟ್ ಅನ್ನು ಗೌರವಿಸುತ್ತವೆ:

| ಪ್ರೊಫೈಲ್ | ಟ್ರಿಪ್ ಆಗುವುದು (`providerFailureThreshold`) | ಅವಧಿಯೊಳಗೆ (`providerFailureWindowMs`) | ಕೂಲ್ ಆಗುವ ಅವಧಿ (`providerCooldownMs`) |
| -------- | ------------------------------------------: | ------------------------------------: | ------------------------------------: |
| OAuth    |                                        `10` |                               `15min` |                                `5min` |
| API key  |                                        `15` |                               `30min` |                               `10min` |

ಮಿತಿಗಿಂತ ಕೆಳಗೆ ಪ್ರೊವೈಡರ್ ಕೂಲಿಂಗ್ನಲ್ಲಿ **ಇಲ್ಲ** ಎಂದು ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ; ಯಶಸ್ಸು ವಿಂಡೋವನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ. ಸಂಪರ್ಕ-ಮಟ್ಟದ ಎಂಟ್ರಿಗಳು (`provider:connectionId`) ಬದಲಾಗಿ ಘಾತಾಂಕೀಯ `minRetryCooldownMs → maxRetryCooldownMs` ಬ್ಯಾಕ್ಆಫ್ ಅನ್ನು ಇರಿಸುತ್ತವೆ. ಓವರ್ರೈಡ್ಗಳು: `OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`. ರಿಗ್ರೆಶನ್ ಗಾರ್ಡ್: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್

**ವ್ಯಾಪ್ತಿ:** ಏಕ ಪೂರೈಕೆದಾರ connection/account/key.

**ಉದ್ದೇಶ:** ಒಂದೇ ಪೂರೈಕೆದಾರರ ಇತರ ಸಂಪರ್ಕಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿರುವಾಗ ಒಂದು ಕೆಟ್ಟ ಕೀಲಿಯನ್ನು ಬಿಟ್ಟುಬಿಡಿ.

**ಅನುಷ್ಠಾನ:**

- ಅಲಭ್ಯವೆಂದು ಗುರುತಿಸಿ: `src/sse/services/auth.ts::markAccountUnavailable()`
- ಆಯ್ಕೆ: ಅದೇ ಕಡತದಲ್ಲಿ `getProviderCredentials*`
- ಕೂಲ್ಡೌನ್ ಕ್ಯಾಲ್ಕ್: `open-sse/services/accountFallback.ts::checkFallbackError()`
- ಸೆಟ್ಟಿಂಗ್ಗಳು: `src/lib/resilience/settings.ts`

**ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ ಕ್ಷೇತ್ರಗಳು:**

- ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ`rateLimitedUntil` — ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — ಘಾತೀಯ ಬ್ಯಾಕ್ಆಫ್ ಕೌಂಟರ್

**ಡೀಫಾಲ್ಟ್ ಕೂಲ್ಡೌನ್ಗಳು:**

- OAuth ಬೇಸ್: 5 ಸೆ
- API-ಕೀ ಬೇಸ್: 3 ಸೆ
- API-ಕೀ 429: ಅಪ್ಸ್ಟ್ರೀಮ್ `Retry-After`/ headers/parseable ಮರುಹೊಂದಿಸುವ ಪಠ್ಯವನ್ನು ಮರುಹೊಂದಿಸಲು ಆದ್ಯತೆ ನೀಡುತ್ತದೆ
- ಬ್ಯಾಕ್ಆಫ್: `baseCooldownMs * 2 ** failureIndex`

**ಪ್ರತಿ ಪೂರೈಕೆದಾರರ ಮರುಪ್ರಯತ್ನ ವಿಳಂಬ.** ಒದಗಿಸುವವರ ವಿವರ ಪುಟವು a** ವಿಳಂಬವನ್ನು ಮರುಪ್ರಯತ್ನಿಸಿ** ಆಯ್ಕೆಮಾಡಿ (ಸ್ವಯಂ, 15 ಸೆ ವರೆಗೆ 1ಗಂ). ಇದು `resilienceSettings.providerQuotaOverrides[<providerId>].rateLimitCooldownSeconds` (1–21600, `PATCH /api/resilience` ಮೂಲಕ) ಉಳಿಸುತ್ತದೆ. ದರ-ಮಿತಿ ದೋಷವು ಅಪ್ಸ್ಟ್ರೀಮ್ ಮರುಪ್ರಯತ್ನದ ಸುಳಿವು ಹೊಂದಿಲ್ಲದಿದ್ದರೆ, ಆ ಮೌಲ್ಯವು ಪೂರೈಕೆದಾರರಿಗೆ ಸ್ಕೇಲ್ಡ್ ಬ್ಯಾಕ್ಆಫ್ ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ ಮತ್ತು `backoffLevel` 0 (`open-sse/services/rotationConfig.ts::overrideFor`) ಗೆ ಮರುಹೊಂದಿಸುತ್ತದೆ. ದರ-ಸೀಮಿತ ದೋಷಕ್ಕೆ ಆದ್ಯತೆ, ಮೊದಲು ಅತ್ಯಧಿಕ: ಅಪ್ಸ್ಟ್ರೀಮ್ ಮರುಪ್ರಯತ್ನದ ಸುಳಿವು, ನಂತರ ಪ್ರತಿ-ಸಂಪರ್ಕಕ್ಕೆ `providerSpecificData.rotationOverrides.rateLimitResetSeconds`, ನಂತರ ಪ್ರತಿ-ಒದಗಿಸುವವರ ಮರುಪ್ರಯತ್ನ ವಿಳಂಬ, ನಂತರ env `OMNIROUTE_ROTATION_RATE_LIMIT_RESET_SECONDS`, ನಂತರ ಸ್ಕೇಲ್ಡ್ ಬ್ಯಾಕ್ಆಫ್. ಸ್ವಯಂ ಕ್ಷೇತ್ರವನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ. ಇದು ದರ-ಮಿತಿ ಕಾರಣವನ್ನು ಮಾತ್ರ ಪರಿಣಾಮ ಬೀರುತ್ತದೆ, ಎಂದಿಗೂ ಟರ್ಮಿನಲ್ ಸ್ಟೇಟ್ಸ್.

**ಗುಡುಗು-ವಿರೋಧಿ ಹಿಂಡಿನ ಕಾವಲು:** ಕೂಲ್ಡೌನ್ ಅಥವಾ ಡಬಲ್-ಇನ್ಕ್ರಿಮೆಂಟಿಂಗ್ `backoffLevel` ನಿಂದ ಏಕಕಾಲೀನ ವೈಫಲ್ಯಗಳನ್ನು ತಡೆಯುತ್ತದೆ.

**ಕನ್ಕರೆನ್ಸಿ-ಮಿತಿ 429ಗಳು ಬ್ಯಾಕ್ಆಫ್ ಲ್ಯಾಡರ್ ಅನ್ನು ಹತ್ತುವುದಿಲ್ಲ.** ದೇಹವು ಏಕಕಾಲಿಕ ಮಿತಿಯನ್ನು ವರದಿ ಮಾಡುವ `429` ("ಹಲವು ಏಕಕಾಲಿಕ ವಿನಂತಿಗಳು", "ಸಮಾಂತರ ಮಿತಿ", "ಸಮಾನಾಂತರ ವಿನಂತಿ ಮಿತಿ", GLM `并发数过高`) ಎಂದರೆ ಖಾತೆಯು ಆರೋಗ್ಯಕರವಾಗಿದೆ ಆದರೆ ಕಾರ್ಯನಿರತವಾಗಿದೆ. `checkFallbackError()` ಕಾರಣ `concurrency_limited` ಹಿಂತಿರುಗಿಸುತ್ತದೆ: ಈಗ ಮುಂದಿನ ಸಂಪರ್ಕಕ್ಕೆ ವಿಫಲವಾಗಿದೆ, ಸ್ಥಿರವಾದ `CONCURRENCY_LIMIT_COOLDOWN_MS` (1 ಸೆ) ಅಥವಾ ಅಪ್ಸ್ಟ್ರೀಮ್ ಮರುಪ್ರಯತ್ನದ ಸುಳಿವುಗಾಗಿ ಇದನ್ನು ತಂಪಾಗಿಸಿ, `backoffLevel` ಬದಲಾಗದೆ ಇರಿಸಿ ಮತ್ತು `skipProviderBreaker` ಹೊಂದಿಸಿ. ಸ್ಪಷ್ಟವಾದ ಕೋಟಾ ದೇಹವು ಇನ್ನೂ ಗೆಲ್ಲುತ್ತದೆ, ಆದ್ದರಿಂದ ಕೋಟಾ ಮಾದರಿಗೆ ಹೊಂದಿಕೆಯಾಗುವ ದೇಹವು ಕೋಟಾ ತೀರ್ಪಿನಲ್ಲಿ ಉಳಿಯುತ್ತದೆ. ಪತ್ತೆ: `looksLikeConcurrencyLimit()` ರಲ್ಲಿ `src/shared/utils/classify429.ts`; ತೀರ್ಪು: `open-sse/services/accountFallback/concurrencyLimit429.ts` `classify429()` (ಬ್ರೇಕರ್ನ `FailureKind`) ಬದಲಾಗಿಲ್ಲ ಮತ್ತು ಈ ಕಾಯಗಳಿಗೆ `rate_limit` ಇನ್ನೂ ಓದುತ್ತದೆ.

**ಸ್ಟ್ರೀಮ್ ವಿಷಯ ಮಳಿಗೆಗಳು ಖಾತೆಯನ್ನು ತಂಪಾಗಿಸುವುದಿಲ್ಲ.** ಕಂಟೆಂಟ್-ಸ್ಟಾಲ್ ವಾಚ್ಡಾಗ್ (`open-sse/utils/streamHandler.ts`) ಯಾವುದೇ ಮಾದರಿಯ ಔಟ್ಪುಟ್ ಅನ್ನು ಸಮಯಕ್ಕೆ ಕಳುಹಿಸದ ಸ್ಟ್ರೀಮ್ನಲ್ಲಿ ಬಿಟ್ಟುಕೊಟ್ಟಾಗ, `markAccountUnavailable()` ಸಂಪರ್ಕದಲ್ಲಿ ದೋಷವನ್ನು ದಾಖಲಿಸುತ್ತದೆ ಆದರೆ ಯಾವುದೇ ಕೂಲ್ಡೌನ್ ಅನ್ನು ಹೊಂದಿಸುವುದಿಲ್ಲ: ಸ್ಟಾಲ್ ಆ ವಿನಂತಿಗೆ ಸೇರಿದೆ, ಇನ್ನೂ ಯಾವುದೇ ಔಟ್ಪುಟ್ ಇಲ್ಲದ ದೀರ್ಘ ತಾರ್ಕಿಕ ತಿರುವು. ನಿರ್ವಾಹಕರು `resilienceSettings.streamStallCooldown.enabled` (ಡೀಫಾಲ್ಟ್ `false`) ನೊಂದಿಗೆ ಮತ್ತೆ ಆಯ್ಕೆ ಮಾಡಬಹುದು.

**`p2c` ಖಾತೆಯ ಆಯ್ಕೆಗಾಗಿ ಆಪ್ಟ್-ಇನ್ ಲೇಟೆನ್ಸಿ ಸಿಗ್ನಲ್.** ಪ್ರತಿ ಕಳುಹಿಸಲಾದ ಪ್ರಯತ್ನವು ಅದರ ಸಮಯದಿಂದ ಮೊದಲ ಬೈಟ್ ಮತ್ತು ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ (ಮತ್ತು ಪ್ರತಿ ಸಂಪರ್ಕ + ಮಾದರಿ) ಫಲಿತಾಂಶವನ್ನು ಇನ್-ಮೆಮೊರಿ ರೋಲಿಂಗ್ ವಿಂಡೋದಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ: ಕೊನೆಯ 20 ಮಾದರಿಗಳು 15 ನಿಮಿಷಗಳಲ್ಲಿ (`open-sse/services/connectionLatencyTracker.ts`, `safeLogEvents()` ನಿಂದ `src/sse/handlers/chatHelpers.ts` ನಲ್ಲಿ ದಾಖಲಿಸಲಾಗಿದೆ). `resilienceSettings.p2cLatency.weight` `0` ಗಿಂತ ಹೆಚ್ಚಿರುವಾಗ (ಶ್ರೇಣಿ 0-20, ಡೀಫಾಲ್ಟ್ `0` = ಆಫ್), `src/sse/services/auth.ts` ನಲ್ಲಿ `compareP2CConnections()` ಜೋಡಿಯ ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಗೆ `weight` ಅಂಕಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ. ಅದರಲ್ಲಿ ಅರ್ಧದಷ್ಟು ವೇಗದ ಅಭ್ಯರ್ಥಿಗೆ ಅನುಪಾತವಾಗಿ ಲೇಟೆನ್ಸಿಯಿಂದ ಬರುತ್ತದೆ (ಎರಡು ಬಾರಿ ನಿಧಾನವಾಗಿ ಪೂರ್ಣ ಅರ್ಧವನ್ನು ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ) ಮತ್ತು ಅರ್ಧದಷ್ಟು ರೋಲಿಂಗ್ ದೋಷ ದರದಿಂದ ಬರುತ್ತದೆ. ಎರಡೂ ಅಭ್ಯರ್ಥಿಗಳು ಕನಿಷ್ಟ 3 ಮಾದರಿಗಳನ್ನು ಹೊಂದಿರುವಾಗ ಮಾತ್ರ ಈ ಪದವು ಅನ್ವಯಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಹೊಸ ಖಾತೆಗಳಿಗೆ ದಂಡ ವಿಧಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು ಅದರ ಸೀಲಿಂಗ್ ಕೋಟಾ-ನಿರ್ಬಂಧಿತ ಮತ್ತು ಕೋಟಾ-ನಿಷ್ಕಾಸ ದಂಡದ ಕೆಳಗೆ ಇರುತ್ತದೆ. ಇದು ತನ್ನದೇ ಆದ ಯಾವುದೇ ಸರ್ಕ್ಯೂಟ್ ಅನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ: ವಿಫಲವಾದ ಖಾತೆಗಳನ್ನು ಇನ್ನೂ ಕೂಲ್ಡೌನ್, ಲಾಕ್ಔಟ್ ಮತ್ತು ಬ್ರೇಕರ್ ಲೇಯರ್ಗಳಿಂದ ನಿರ್ವಹಿಸಲಾಗುತ್ತದೆ. ಇದನ್ನು `PATCH /api/resilience` `{ "p2cLatency": { "weight": 10 } }` ನೊಂದಿಗೆ ಹೊಂದಿಸಿ.

**ತಾರ್ಕಿಕ ಚೌಕಟ್ಟುಗಳು ಕಂಟೆಂಟ್-ಸ್ಟಾಲ್ ಬಜೆಟ್ ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸುತ್ತವೆ.** ಒಂದು ತಾರ್ಕಿಕ ಮಾದರಿಯು ತನ್ನ ಮೊದಲ ಗೋಚರ ಟೋಕನ್ನ ಮೊದಲು ನಿಮಿಷಗಳ ಕಾಲ ಯೋಚಿಸಬಹುದು: Claude ಸ್ಟ್ರೀಮ್ಗಳು `thinking_delta` ಫ್ರೇಮ್ಗಳ ಚಿಂತನೆಯ ಪಠ್ಯವು ಖಾಲಿಯಾಗಿರಬಹುದು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳು API ಸ್ಟ್ರೀಮ್ಗಳು ಒಂದರ ನಂತರ ಒಂದು ತಾರ್ಕಿಕ ಐಟಂ. `isReasoningProgressFrame()` (`open-sse/utils/streamReadiness.ts`) ಈ ಚೌಕಟ್ಟುಗಳನ್ನು ಗುರುತಿಸುತ್ತದೆ, ಮತ್ತು ವಾಚ್ಡಾಗ್ ಟರ್ನ್ ಅನ್ನು ರದ್ದುಗೊಳಿಸುವ ಬದಲು ಪ್ರತಿಯೊಂದರಲ್ಲೂ ಅದರ ಬಜೆಟ್ ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸುತ್ತದೆ. ಅವು ಇನ್ನೂ ಮಾದರಿಯ ಔಟ್ಪುಟ್ ಆಗಿಲ್ಲ, ಆದ್ದರಿಂದ ತಾರ್ಕಿಕ ಕ್ರಿಯೆಯೊಂದಿಗೆ ಕೊನೆಗೊಳ್ಳುವ ತಿರುವು ಇನ್ನೂ ಖಾಲಿ ಎಂದು ವರದಿಯಾಗಿದೆ ಮತ್ತು ತಾರ್ಕಿಕತೆಯನ್ನು ನಿಲ್ಲಿಸುವ ಮತ್ತು ಹೃದಯ ಬಡಿತಗಳನ್ನು ಮಾತ್ರ ಕಳುಹಿಸುವ ತಿರುವು ಇನ್ನೂ ವಾಚ್ಡಾಗ್ ಅನ್ನು ಟ್ರಿಪ್ ಮಾಡುತ್ತದೆ.

ಖಾಲಿ ಅಲ್ಲದ ಸಹಿಯನ್ನು ಹೊಂದಿರುವ Kiro ನ ಬೈನರಿ `reasoningContentEvent` ಫ್ರೇಮ್ಗಳು ಈ ತಾರ್ಕಿಕ ಚಟುವಟಿಕೆಯನ್ನು ಎಕ್ಸಿಕ್ಯೂಟರ್ ಮೂಲಕ ಖಾಲಿ `reasoning_content` ಡೆಲ್ಟಾದಂತೆ ಸಂರಕ್ಷಿಸುತ್ತದೆ. ಸಹಿಯನ್ನು ರವಾನಿಸಲಾಗಿಲ್ಲ. ಮೆಟಾಡೇಟಾ, ಅಪೂರ್ಣ ಚೌಕಟ್ಟುಗಳು ಮತ್ತು ಖಾಲಿ ಸಹಿಗಳು ವಿಷಯ ಬಜೆಟ್ ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ; ಸ್ವತಂತ್ರ ಸಕ್ರಿಯ-ಸ್ಟ್ರೀಮ್ ಅವಧಿ ಮೀರುವಿಕೆ ಮತ್ತು ಕ್ಲೈಂಟ್ ರದ್ದತಿ ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ (`open-sse/executors/kiro/reasoning.ts`).

**ಟರ್ಮಿನಲ್ ಸ್ಟೇಟ್ಸ್ (NOT ಕೂಲ್ಡೌನ್ಗಳು):**

- ನಿಷೇಧಿತ-ಕೀವರ್ಡ್ / ಖಾತೆ-ನಿಷೇಧ ಪತ್ತೆ ( [BAN_DETECTION](../security/BAN_DETECTION.md) ನೋಡಿ) ಮತ್ತು ಮೂರು ಸತತ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿ ವಿನಂತಿಯ ನಿರಾಕರಣೆಗಳ ಮೂಲಕ `banned` — ಸೆಟ್ ಮಾಡಲಾಗಿದೆ (`request_rejected`, ಉದಾ Anthropic OAuth 403 "ವಿನಂತಿಯನ್ನು ಅನುಮತಿಸಲಾಗುವುದಿಲ್ಲ" — `open-sse/services/requestRejectedStreak.ts`); ಒಂದೇ ಒಂದು ನಿರಾಕರಣೆಯು ಸಂಪರ್ಕವನ್ನು ತಂಪಾಗಿಸುತ್ತದೆ
- `expired` (ಪರಿಮಿತ ಮರುಪ್ರಯತ್ನಗಳ ನಂತರ ಟರ್ಮಿನಲ್ಗೆ ಪರಿವರ್ತನೆಗಳು — `EXPIRED_RETRY_MAX = 3` ಘಾತೀಯ ಬ್ಯಾಕ್ಆಫ್ — ಜೊತೆಗೆ ಖಾತೆಯನ್ನು ಶಾಶ್ವತವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವ ಮೊದಲು ಕ್ಷಣಿಕ OAuth ದೋಷಗಳು ಸ್ವಯಂ-ಗುಣಪಡಿಸಬಹುದು)
- `credits_exhausted`

ರುಜುವಾತುಗಳನ್ನು ಬದಲಾಯಿಸುವವರೆಗೆ ಅಥವಾ ಆಪರೇಟರ್ ಅವುಗಳನ್ನು ಮರುಹೊಂದಿಸುವವರೆಗೆ ಇವುಗಳು ಇರುತ್ತವೆ. ಅಸ್ಥಿರ ಕೂಲ್ಡೌನ್ ಸ್ಥಿತಿಯೊಂದಿಗೆ ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳನ್ನು ಓವರ್ರೈಟ್ ಮಾಡಬೇಡಿ.

**ಸೋಮಾರಿಯಾದ ಚೇತರಿಕೆ:** `rateLimitedUntil` ಕಳೆದಿರುವಾಗ, ಸಂಪರ್ಕವು ಮತ್ತೆ ಅರ್ಹವಾಗುತ್ತದೆ. ಯಶಸ್ವಿ ಬಳಕೆಯಲ್ಲಿ, `clearAccountError()` ಎಲ್ಲಾ ದೋಷ ಕ್ಷೇತ್ರಗಳನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.

### Claude OAuth ಬಳಕೆಯ ಗೋಡೆ: ಕಡಿಮೆ ಆದ್ಯತೆಯ ಲೇನ್ + ಸೆಷನ್-ಮಿತಿ ಮರುಹೊಂದಿಸಿ

**ವ್ಯಾಪ್ತಿ:** ಒಂದು Claude ಚಂದಾದಾರಿಕೆ (OAuth) ಸಂಪರ್ಕ. ಎರಡೂ ವೈಶಿಷ್ಟ್ಯಗಳು** ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ ಆಯ್ಕೆ** (ಸಂಪರ್ಕವನ್ನು ಸಂಪಾದಿಸಿ → Claude ವಿಭಾಗ → `lowPriorityMode` / `autoLimitReset` ರಲ್ಲಿ `providerSpecificData`, ಎರಡೂ ಡೀಫಾಲ್ಟ್ ಆಫ್) ಮತ್ತು ಕನ್ನಡಿ Claude ಕೋಡ್ನ `/low-priority` ಮತ್ತು `/limit-reset` ಆಜ್ಞೆಗಳನ್ನು ( Claude ಕೋಡ್ 2.1.263 ರಿಂದ ವಶಪಡಿಸಿಕೊಂಡ ವೈರ್ ಒಪ್ಪಂದ).

**ಅನುಷ್ಠಾನ:**

- ರಾಜ್ಯ ಯಂತ್ರ + ಪ್ರತಿಕ್ರಿಯೆ ವರ್ಗೀಕರಣ: `open-sse/services/claudeLowPriority.ts`
- status/claim ಕ್ಲೈಂಟ್ ಅನ್ನು ಮರುಹೊಂದಿಸಿ: `open-sse/services/claudeLimitReset.ts`
- ಎಕ್ಸಿಕ್ಯೂಟರ್ ಹುಕ್ (ಹೆಡರ್ ಇಂಜೆಕ್ಷನ್ + ಅದೇ-ಖಾತೆ ಮರುಪ್ರಯತ್ನ): `open-sse/executors/base.ts::execute()`
- ಆಯ್ಕೆಯ ನಿರಂತರತೆ: `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**ಪ್ರಚೋದಕ:** 5-ಗಂಟೆಯ ಬಳಕೆಯ ಗೋಡೆ — a `429` ಇದರ ಹೆಡರ್ `anthropic-ratelimit-unified-status: rejected` ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ ಮತ್ತು ಖಾತೆಯು ಅರ್ಹವಾದಾಗ, `anthropic-ratelimit-unified-slow-offer: treatment`. ಆ ಮೊದಲ ಗೋಡೆಯ ಮುಂದೆ ಏನನ್ನೂ ಕಳುಹಿಸಲಾಗಿಲ್ಲ 429; ಏಕೀಕೃತ ಹೆಡರ್ ಇಲ್ಲದೆ ಬರ್ಸ್ಟ್ 429 ಸಾಮಾನ್ಯ ಕೂಲ್ಡೌನ್ ಮಾರ್ಗದ ಮೂಲಕ ಹೋಗುತ್ತದೆ.

**ಕಡಿಮೆ ಆದ್ಯತೆಯ ಲೇನ್** (`lowPriorityMode`):

- ಗೋಡೆಯ 429 ನಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಾಹಕರು ಪ್ರಸ್ತಾಪವನ್ನು ಸ್ವೀಕರಿಸುತ್ತಾರೆ ಮತ್ತು ತಕ್ಷಣವೇ ಮರುಪ್ರಯತ್ನಿಸುತ್ತಾರೆ** ಅದೇ** `anthropic-usage-limit: slow` ನೊಂದಿಗೆ ಖಾತೆ; ಘೋಷಿತ `anthropic-ratelimit-unified-reset` (+ 60s ಗ್ರೇಸ್) ತನಕ ಲೇನ್ ಸಕ್ರಿಯವಾಗಿರುತ್ತದೆ ಮತ್ತು ಆ ವಿಂಡೋದಲ್ಲಿನ ಪ್ರತಿಯೊಂದು ವಿನಂತಿಯು ಹೆಡರ್ ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ. ತಡೆಹಿಡಿಯಲಾದ 429 ಎಂದಿಗೂ `handleChatCore` ತಲುಪುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಸಂಪರ್ಕವಾಗಿದೆ** ಅಲ್ಲ** ಕೂಲ್ಡೌನ್ನಲ್ಲಿ ಇರಿಸಿ ಮತ್ತು ತಿರುಗಿಸಲಾಗಿಲ್ಲ.
- ನಂತರದ ಪ್ರತಿಕ್ರಿಯೆಗಳಲ್ಲಿ`anthropic-ratelimit-unified-slow-status` : `active` / `not_needed` ಲೇನ್ ಅನ್ನು ಇರಿಸಿಕೊಳ್ಳಿ; `slot_busy` (429) ಅಥವಾ ಒಂದು `529` ಸರ್ವರ್ನ `anthropic-ratelimit-unified-slow-retry-after` ನಿರೀಕ್ಷಿಸಿ (ಡೀಫಾಲ್ಟ್ 20 ಸೆ, ಕ್ಲ್ಯಾಂಪ್ 5–600 ಸೆ, ± 30% ಜಿಟ್ಟರ್) ಮತ್ತು ಮರುಪ್ರಯತ್ನಿಸಿ, `anthropic-ratelimit-unified-slow-max-wait` (ಡೀಫಾಲ್ಟ್ 20 ನಿಮಿಷ, ಕ್ಲ್ಯಾಂಪ್ 1 ನಿಮಿಷ–6 ಗಂ) — ನಿಮಿಷವನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ ಮತ್ತು la1 ಅನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ ಮರು-ಸ್ವೀಕಾರ. ವಿನಂತಿಯ ಸ್ವಂತ ಅಪ್ಸ್ಟ್ರೀಮ್-ಪ್ರಾರಂಭದ ಅವಧಿಯ (`resolveFetchStartTimeout`, ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ 10 ನಿಮಿಷ) 5 ಸೆ ಮಾರ್ಜಿನ್ನಿಂದ ಉಳಿದಿರುವ ಕಾಯುವಿಕೆಗೆ ಹೆಚ್ಚುವರಿಯಾಗಿ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ: ಆ ಮಿತಿಯಿಲ್ಲದೆಯೇ 20-ನಿಮಿಷದ ಡೀಫಾಲ್ಟ್ ಗರಿಷ್ಠ-ನಿರೀಕ್ಷಣೆಯು `TimeoutError` ಮೀರುತ್ತದೆ ಮತ್ತು ನಿದ್ರೆಯು ಮಧ್ಯ- `max_wait` ಬದಲಾಗಿ ಕೊನೆಗೊಳ್ಳುತ್ತದೆ. + -ಆಫ್.
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, 5h-ವಿಂಡೋ ರೋಲ್ಓವರ್, ಅಥವಾ `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (ಯಾವುದೇ ಸ್ಥಿತಿಯ ಮೇಲೆ `extra_usage` ಎಂದು ಕೊನೆಗೊಳ್ಳುತ್ತದೆ, ಏಕೆಂದರೆ ಪಾವತಿಸಿದ ಓವರ್ಜ್ ಈಗ ಗೋಡೆಯನ್ನು ಆವರಿಸುತ್ತದೆ) ಲೇನ್ ಅನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ; ಪ್ರತಿಕ್ರಿಯೆಯು ನಂತರ ಸಾಮಾನ್ಯ ಕೂಲ್ಡೌನ್ ಮಾರ್ಗಕ್ಕೆ ಹರಿಯುತ್ತದೆ. ಘೋಷಿಸಿದ ಬಜೆಟ್ ಮರುಹೊಂದಿಸುವವರೆಗೆ (≤ 8 ದಿನಗಳು) `budget_exhausted` ನೆನಪಿನಲ್ಲಿರುತ್ತದೆ.
- ಎಕ್ಸಿಕ್ಯೂಟರ್ನ ಸ್ವಂತ 400-ಚಾಲಿತ ಇಂಟ್ರಾ-ಪ್ರಯತ್ನದ ಮರುಪ್ರಯತ್ನಗಳ ನಂತರ ವಾಲ್ ಚೆಕ್ ರನ್ ಆಗುತ್ತದೆ (ಸಂದರ್ಭ ಸಂಪಾದನೆ, thinking/effort ಕ್ಲಾಂಪ್ಗಳು, ಪ್ಯಾರಮ್ ಸ್ವಯಂ-ಕಲಿಕೆ), ಆದ್ದರಿಂದ ಆ ಮರುಪ್ರಯತ್ನಗಳಲ್ಲಿ ಒಂದನ್ನು ಮಾತ್ರ ಮೇಲ್ಮೈ ಮಾಡುವ ಗೋಡೆ 429 ಅನ್ನು ತಂಪಾಗಿಸುವ ಮಾರ್ಗವನ್ನು ತಲುಪುವ ಬದಲು ಇನ್ನೂ ತಡೆಹಿಡಿಯಲಾಗುತ್ತದೆ.
- ರಾಜ್ಯವು ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ ಸ್ಮರಣೆಯಲ್ಲಿದೆ (ಮರುಪ್ರಾರಂಭಕ್ಕೆ ಒಂದು ಹೆಚ್ಚುವರಿ ಗೋಡೆಯ ವೆಚ್ಚ 429 ಮರು-ಅಂಗೀಕರಿಸಲು).

**ಸೆಷನ್-ಮಿತಿ ಮರುಹೊಂದಿಸುವಿಕೆ** (`autoLimitReset`, ಎರಡೂ ಆನ್ ಆಗಿರುವಾಗ ಲೇನ್ಗೆ ಮೊದಲು ಪ್ರಯತ್ನಿಸಲಾಗಿದೆ):

- `GET https://api.anthropic.com/api/oauth/usage?at_wall=1&skip_spend=1` → `juniper_tide` ಬ್ಲಾಕ್; ಯಾವಾಗ `arm: "reset"` ಮತ್ತು `available: true`, `POST https://api.anthropic.com/api/organizations/{orgUUID}/reset_rate_limits` ಜೊತೆಗೆ `{ "program": "juniper_tide" }` ( `providerSpecificData.organizationUUID` ನಿಂದ ಸಂಸ್ಥೆ UUID, ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಫಾಲ್ಬ್ಯಾಕ್).
- `result: reset|not_limited` → ವಿನಂತಿಯನ್ನು ಪೂರ್ಣ ವೇಗದಲ್ಲಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗಿದೆ (ನಿಧಾನ ಹೆಡರ್ ಇಲ್ಲ). `already_used` / `not_offered` memoise `next_available_at` (ಡೀಫಾಲ್ಟ್ ಒಂದು ವಾರ); ಯಾವುದೇ ವೈಫಲ್ಯವು 15 ನಿಮಿಷಗಳನ್ನು ಹಿಮ್ಮೆಟ್ಟಿಸುತ್ತದೆ. ಮರುಹೊಂದಿಸುವಿಕೆಯು ವಾರಕ್ಕೊಮ್ಮೆ ಮತ್ತು ಇನ್ನೂ ಸಾಪ್ತಾಹಿಕ ಮಿತಿಗೆ ಎಣಿಕೆಯಾಗುತ್ತದೆ.

ರಿಗ್ರೆಶನ್ ಗಾರ್ಡ್ಗಳು: `tests/unit/claude-low-priority-mode.test.ts`, `tests/unit/claude-limit-reset.test.ts`, `tests/unit/claude-low-priority-executor.test.ts`.

### ಸೆಷನ್ ಅಫಿನಿಟಿ (#7274)

**ವ್ಯಾಪ್ತಿ:** ಒಂದು ಕ್ಲೈಂಟ್ ಸೆಷನ್ (`X-Session-Id` / `x-codex-session-id` / `x-omniroute-session` ಹೆಡರ್) ಒಂದು ಸಂಪರ್ಕಕ್ಕೆ ಪಿನ್ ಮಾಡಲಾಗಿದೆ, ಇದಕ್ಕಾಗಿ** ಯಾವುದೇ** ಒದಗಿಸುವವರು.

**ಉದ್ದೇಶ:** ಬಹು-ತಿರುವು ಏಜೆಂಟ್ (Claude ಕೋಡ್, ಸಹಾಯಕ, ಕಸ್ಟಮ್ ಏಜೆಂಟ್) ಅನ್ನು ವಿನಂತಿಗಳಾದ್ಯಂತ ಒಂದೇ ಖಾತೆಯಲ್ಲಿ ಇರಿಸಿಕೊಳ್ಳಿ, ಕ್ರಾಸ್-ಖಾತೆ ಸಂದರ್ಭ ನಷ್ಟವನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ-ಖಾತೆಯ ಸೆಶನ್ ಸ್ಥಿತಿಯನ್ನು ಹೊಂದಿರುವ ಪೂರೈಕೆದಾರರ ಮೇಲೆ ಪುನರಾವರ್ತಿತ ಶೀತ-ಪ್ರಾರಂಭ 429s.

**ಅನುಷ್ಠಾನ:**

- TTL ರೆಸಲ್ಯೂಶನ್: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- ಪಿನ್ selection/creation: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- ಹೆಡರ್ ಹೊರತೆಗೆಯುವಿಕೆ (ಜೆನೆರಿಕ್, ಯಾವುದೇ ಪೂರೈಕೆದಾರ): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- ನಿರಂತರ ಪಿನ್ ಟೇಬಲ್: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- ಸೆಟ್ಟಿಂಗ್: `sessionAffinityTtlMs` (ms ನಲ್ಲಿ ಜಾಗತಿಕ TTL, `0` ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ) — `src/lib/db/settings.ts`. ವಲಸೆ `124_generic_session_affinity_ttl.sql` ಯಿಂದ ಕೋಡೆಕ್ಸ್-ಮಾತ್ರ `codexSessionAffinityTtlMs` ನಿಂದ ಮರುಹೆಸರಿಸಲಾಗಿದೆ, ಇದು ಯಾವುದೇ ಹಿಂದೆ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ Codex TTL ಹೊಸ ಡೀಫಾಲ್ಟ್ ಆಗಿ ಒಯ್ಯುತ್ತದೆ.

#7274 ಕ್ಕಿಂತ ಮೊದಲು, `0` ಹೊರತುಪಡಿಸಿ ಪ್ರತಿ ಪೂರೈಕೆದಾರರಿಗೆ `resolveSessionAffinityTtlMs()` ಹಾರ್ಡ್ `codex` ಬೈಲ್ ಮಾಡಲಾಗಿತ್ತು, ಆದ್ದರಿಂದ TTL ಸೆಟ್ಟಿಂಗ್ (ಮತ್ತು ಸೆಷನ್ ಹೆಡರ್ಗಳು) ಪಿನ್ನಿಂಗ್ ಕಾರ್ಯವಿಧಾನ ಮತ್ತು ಹೆಡರ್ ಹೊರತೆಗೆಯುವಿಕೆ ಈಗಾಗಲೇ ಪೂರೈಕೆದಾರ-ಅಜ್ಞೇಯತಾವಾದಿಯಾಗಿದ್ದರೂ ಸಹ ಬೇರೆಲ್ಲಿಯೂ ಯಾವುದೇ ಪರಿಣಾಮ ಬೀರಲಿಲ್ಲ. ಸರಿಪಡಿಸುವಿಕೆಯು ಆ ಆರಂಭಿಕ-ಹಿಂತಿರುಗುವಿಕೆಯನ್ನು ತೆಗೆದುಹಾಕಿತು; TTL ಈಗ ಜಾಗತಿಕವಾಗಿ `0` ಮೇಲೆ ಹೊಂದಿಸಲಾದ ಪ್ರತಿ ಪೂರೈಕೆದಾರರಿಗೆ ಏಕರೂಪವಾಗಿ ಅನ್ವಯಿಸುತ್ತದೆ.

ಮೂರು ಸೆಷನ್-ಅಫಿನಿಟಿ ಹೆಡರ್ಗಳನ್ನು ಎಂದಿಗೂ ಫಾರ್ವರ್ಡ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ ಅಪ್ಸ್ಟ್ರೀಮ್ — ಎಕ್ಸಿಕ್ಯೂಟರ್ಗಳು ಕ್ಲೈಂಟ್ ಹೆಡರ್ಗಳನ್ನು ಹಾದುಹೋಗುವ ಬದಲು ಮೊದಲಿನಿಂದ ತಮ್ಮದೇ ಆದ ಅಪ್ಸ್ಟ್ರೀಮ್ ಹೆಡರ್ಗಳನ್ನು ನಿರ್ಮಿಸುತ್ತಾರೆ, ಆದ್ದರಿಂದ ಇದು ಆಂತರಿಕ ಪರಸ್ಪರ ಸಂಬಂಧದ ಐಡಿ ಮಾತ್ರ.

### ವಿಶೇಷ ನಿರ್ವಹಿಸಿದ ಅಧಿವೇಶನ ಸಂಪರ್ಕ ಗುತ್ತಿಗೆಗಳು

**ವ್ಯಾಪ್ತಿ:** ಒಂದು ಸಕ್ರಿಯ ನಿರ್ವಹಿಸಿದ HTTP client/session ಒಂದು ಅರ್ಹ OmniRoute ಸಂಪರ್ಕವನ್ನು ಹೊಂದಿದೆ.

**ಉದ್ದೇಶ:** ವಿನಂತಿಗಳಾದ್ಯಂತ ಹಾರ್ಡ್ ರೂಟಿಂಗ್ ಬೇಲಿ ಅಗತ್ಯವಿರುವ ಗ್ರಾಹಕರಿಗೆ ಬಾಳಿಕೆ ಬರುವ ವಿಶೇಷ ಸಂಪರ್ಕ ಮಾಲೀಕತ್ವವನ್ನು ಒದಗಿಸಿ. ಇದು ಸೆಷನ್ ಅಫಿನಿಟಿಯಿಂದ ಭಿನ್ನವಾಗಿದೆ, ಇದು ಮೃದುವಾದ ನಿರಂತರತೆಯ ಆದ್ಯತೆಯಾಗಿದೆ: ವಿಶೇಷವಾದ ಗುತ್ತಿಗೆಯು SQLite ನಲ್ಲಿ ಜೀವನಚಕ್ರ ಸ್ಥಿತಿಯನ್ನು ಮುಂದುವರೆಸುತ್ತದೆ, ಜಾಗತಿಕ ಸಕ್ರಿಯ-ಮಾಲೀಕ ಮತ್ತು ಸಕ್ರಿಯ-ಸಂಪರ್ಕ ಅನನ್ಯತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಪೂರೈಕೆದಾರರ ರವಾನೆಗೆ ಮೊದಲು ಹಳೆಯ ಪೀಳಿಗೆಯನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ.

ವೈಶಿಷ್ಟ್ಯವು ಪ್ರತಿ API ಕೀಗೆ ಆಯ್ಕೆಯಾಗಿದೆ. ನಿರ್ವಹಿಸಲಾದ ಕೀಲಿಯು `lease:exclusive` ಸ್ಕೋಪ್ ಮತ್ತು ಸ್ಪಷ್ಟವಾದ ಖಾಲಿ-ಅಲ್ಲದ `allowedConnections` ಪಟ್ಟಿಯನ್ನು ಹೊಂದಿರಬೇಕು. ಯಾವುದೇ HTTP ಕ್ಲೈಂಟ್ ಜೀವನಚಕ್ರದ ಅಂತ್ಯಬಿಂದುವನ್ನು ಬಳಸಬಹುದು; ಯಾವುದೇ ಕ್ಲೈಂಟ್ ಹೆಸರು, ಬಳಕೆದಾರ ಏಜೆಂಟ್, ಪೂರೈಕೆದಾರರು, OAuth ವಿಧಾನ ಅಥವಾ ಮಾದರಿ ಅಗತ್ಯವಿಲ್ಲ. ಗುತ್ತಿಗೆಯು ಒಂದು ಸಂಪರ್ಕವನ್ನು ಹೊಂದಿದೆ, ಒಂದು ಮಾದರಿಯಲ್ಲ, ಆದ್ದರಿಂದ ಸಂಪರ್ಕವು ಸಾಮಾನ್ಯವಾಗಿ ಅರ್ಹವಾಗಿರುವಾಗ ಮಾದರಿ ಬದಲಾವಣೆಯು ಬೈಂಡಿಂಗ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ. ಸಾಮಾನ್ಯ ಮಾದರಿ, ಕೋಟಾ, ಆರೋಗ್ಯ, ಕೂಲ್ಡೌನ್ ಮತ್ತು ಅನುಮತಿ ಪಟ್ಟಿ ನಿಯಮಗಳು ಅಧಿಕೃತವಾಗಿರುತ್ತವೆ ಮತ್ತು ಅದೇ ಪೀಳಿಗೆಯನ್ನು ಮತ್ತೊಂದು ಉಚಿತ ಅರ್ಹ ಸಂಪರ್ಕಕ್ಕೆ ಪರಿವರ್ತಿಸಬಹುದು.

ಜೀವನಚಕ್ರವು JSON ಕ್ರಿಯೆಗಳೊಂದಿಗೆ `POST /api/v1/session-leases` ಆಗಿದೆ `acquire`, `renew`, ಮತ್ತು `release`. ನಿರ್ವಹಿಸಿದ ನಿರ್ಣಯ ವಿನಂತಿಗಳು ಅಪಾರದರ್ಶಕ `X-OmniRoute-Lease-Owner` ಮೌಲ್ಯ ಮತ್ತು ನಿಖರವಾದ `X-OmniRoute-Lease-Generation` ಪ್ರಸ್ತುತಪಡಿಸುತ್ತವೆ. ಮಾಲೀಕರು 43 base64url ಅಕ್ಷರಗಳ ನಂತರ `vlo_` ಬಳಸುತ್ತಾರೆ; ಅದರ SHA-256 ಹ್ಯಾಶ್ ಅನ್ನು ಮಾತ್ರ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ. ಪ್ರತಿ ಅಂತಿಮ ರವಾನೆ ಬೇಲಿಯು ದೃಢೀಕೃತ API ಕೀ ID ಮತ್ತು ಸಕ್ರಿಯ ಸಂಪರ್ಕ ID ಸಹ ಬಂಧಿಸುತ್ತದೆ. ಲೀಸ್ ಕಂಟ್ರೋಲ್ ಹೆಡರ್ಗಳನ್ನು ಲಾಗ್ಗಳು, ರಿಟೈನ್ಡ್ ರಿಕ್ವೆಸ್ಟ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಳು ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಎಕ್ಸಿಕ್ಯೂಟರ್ ಹೆಡರ್ಗಳಿಂದ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ.

ಸಾಮಾನ್ಯ ರೂಟಿಂಗ್ ಅರ್ಹವಾದ ನಿರ್ವಹಣಾ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಹೊಂದಿದ್ದರೆ ಆದರೆ ಪ್ರತಿ ಉಚಿತ ಅಭ್ಯರ್ಥಿಯು ವಿದೇಶಿ ಸಕ್ರಿಯ ಗುತ್ತಿಗೆಯಿಂದ ಆಕ್ರಮಿಸಿಕೊಂಡಿದ್ದರೆ, OmniRoute HTTP `429`, ಗುತ್ತಿಗೆ-ಸಾಮರ್ಥ್ಯ-ಲಭ್ಯವಿಲ್ಲದ ಕೋಡ್, ಸಾಮರ್ಥ್ಯಕ್ಕಾಗಿ ಕಾಯುವ ಸ್ಥಿತಿ ಮತ್ತು ಆರಂಭಿಕ ಸಂಬಂಧಿತ ಮುಕ್ತಾಯದಿಂದ ಪಡೆದ `Retry-After` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಸಾಮಾನ್ಯ ಖಾಲಿ ಅರ್ಹತೆಯು ಗುತ್ತಿಗೆ ವಿವಾದವಲ್ಲ ಮತ್ತು ಅದರ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ರೂಟಿಂಗ್ ದೋಷ ಶಬ್ದಾರ್ಥವನ್ನು ಇರಿಸುತ್ತದೆ.

ಸಂಬಂಧಿತ ಕಾರ್ಯವಿಧಾನಗಳು ಪ್ರತ್ಯೇಕವಾಗಿ ಉಳಿದಿವೆ:

- OAuth ಸೆಷನ್ ಆಕ್ಯುಪೆನ್ಸಿ ಎನ್ನುವುದು OAuth ಖಾತೆಗಳಿಗೆ ಪ್ರಕ್ರಿಯೆ-ಸ್ಥಳೀಯ ಮೃದು ವಿತರಣೆಯಾಗಿದೆ.
- ಅಕೌಂಟ್ ಸೆಮಾಫೋರ್ಗಳು ವಿನಂತಿ-ಕಾಕರೆನ್ಸಿ ಅನುಮತಿಗಳನ್ನು ನೀಡುತ್ತವೆ ಮತ್ತು ವಿನಂತಿಯು ಪೂರ್ಣಗೊಂಡಾಗ ಕೊನೆಗೊಳ್ಳುತ್ತದೆ.
- ವಿಶೇಷ ನಿರ್ವಹಣಾ ಅವಧಿಯ ಗುತ್ತಿಗೆಗಳು ಪೀಳಿಗೆಯ ಬೇಲಿಯೊಂದಿಗೆ ಬಾಳಿಕೆ ಬರುವ ಜೀವನಚಕ್ರದ ಮಾಲೀಕತ್ವವಾಗಿದೆ.

## 3. ಮಾದರಿ ಲಾಕ್ಔಟ್

**ವ್ಯಾಪ್ತಿ:** ಪ್ರೊವೈಡರ್ + ಕನೆಕ್ಷನ್ + ಮಾದರಿ ತ್ರಯ.

**ಸ್ಥಿತಿ ಆಧಾರಿತ ಕೀಲಿ ವ್ಯಾಪ್ತಿ:** ವಿಫಲವಾದ ಸ್ಥಿತಿಯು ಲಾಕ್ಔಟ್ ಯಾವ ಕೀಲಿಗೆ ಬರೆಯುತ್ತದೆ ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ (`open-sse/services/accountFallback/exactModelLock.ts` ನಲ್ಲಿರುವ `resolveLockoutScope()`):

- `429` / `403` / `402` — ಕೋಟಾ ಅಥವಾ ಎಂಟೈಟಲ್ಮೆಂಟ್ ಸಂಕೇತ — **ಕೋಟಾ ಕುಟುಂಬ**ವನ್ನು ಲಾಕ್ ಮಾಡಿ:
  codex ಗಾಗಿ ಇಡೀ `codex` / `spark` ವ್ಯಾಪ್ತಿ (ಕನೆಕ್ಷನ್ನ ಪ್ರತಿಯೊಂದು `gpt-5*` ಮಾದರಿ), ಇತರ ಪ್ರೊವೈಡರ್ಗಳಿಗೆ `getQuotaScopedModelForProvider()`.
- `404` ಕೇವಲ ಮಾದರಿಯನ್ನು ಮಾತ್ರ ಲಾಕ್ ಮಾಡುತ್ತದೆ (`getModelLockKey()` `not_found` ಅನ್ನು ಕಿರಿದಾಗಿಸುತ್ತದೆ).
- ಬೇರೆ ಯಾವುದೇ ಸ್ಥಿತಿ — `5xx` ಸಾರಿಗೆ/ಸರ್ವರ್ ವೈಫಲ್ಯಗಳು ಮತ್ತು ಗುಣಮಟ್ಟ ಮೌಲ್ಯೀಕರಣದಿಂದ OmniRoute ಸ್ವತಃ ಸಂಶ್ಲೇಷಿಸಿದ `502` — ಕೇವಲ **ನಿಖರ** ಪ್ರೊವೈಡರ್/ಕನೆಕ್ಷನ್/ಮಾದರಿ ಟಪಲ್ ಅನ್ನು ಮಾತ್ರ ಲಾಕ್ ಮಾಡುತ್ತದೆ. ಒಂದು ಮಾದರಿಯ ಕೆಟ್ಟ ಸ್ಟ್ರೀಮ್ ಅಕೌಂಟ್ನ ಕೋಟಾ ಬಗ್ಗೆ ಪುರಾವೆಯಾಗುವುದಿಲ್ಲ; ಈ ನಿಯಮಕ್ಕೆ ಮೊದಲು `codex/gpt-5.6-luna` ನಲ್ಲಿ ಒಂದು ಖಾಲಿ ಪ್ರತಿಕ್ರಿಯೆಯು ಆ ಕನೆಕ್ಷನ್ನ ಎಲ್ಲಾ `gpt-5*` ಮಾದರಿಗಳನ್ನು 2–30 ನಿಮಿಷಗಳವರೆಗೆ (ಹಂತಹಂತವಾಗಿ ಹೆಚ್ಚುತ್ತಾ) ರೂಟಿಂಗ್ನಿಂದ ತೆಗೆದುಹಾಕುತ್ತಿತ್ತು, ಅದರ ಕೋಟಾ ಮುಟ್ಟದೆಯೇ ಇದ್ದರೂ.
- ಕರೆಗಾರನ ಸ್ಪಷ್ಟ `scope` ಆಯ್ಕೆ ಯಾವಾಗಲೂ ಜಯಿಸುತ್ತದೆ (Antigravity `"exact"` ಅನ್ನು ರವಾನಿಸುತ್ತದೆ).

**ಉದ್ದೇಶ:** ಒಂದೇ ಮಾದರಿ ಲಭ್ಯವಿಲ್ಲದಿರುವಾಗ ಅಥವಾ ಕೋಟಾ-ಸೀಮಿತವಾಗಿರುವಾಗ ಇಡೀ ಕನೆಕ್ಷನ್ ಅನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದನ್ನು ತಪ್ಪಿಸುವುದು.

**ಉದಾಹರಣೆಗಳು:**

- 429 ಹಿಂದಿರುಗಿಸುವ ಮಾದರಿ-ವಾರು ಕೋಟಾ ಪ್ರೊವೈಡರ್ಗಳು
- ಒಂದು ಕಾಣೆಯಾದ ಮಾದರಿಗೆ 404 ಹಿಂದಿರುಗಿಸುವ ಸ್ಥಳೀಯ ಪ್ರೊವೈಡರ್ಗಳು
- ಪ್ರೊವೈಡರ್-ನಿರ್ದಿಷ್ಟ ಮೋಡ್/ಮಾದರಿ ಅನುಮತಿ ವೈಫಲ್ಯಗಳು (ಉದಾ., Grok ಮೋಡ್ಗಳು)

**ಅನುಷ್ಠಾನ:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

### ಮಾದರಿ ಕೂಲ್ಡೌನ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ (v3.8.0)

UI: ಸೆಟ್ಟಿಂಗ್ಗಳು → ಮಾದರಿ ಕೂಲ್ಡೌನ್ಗಳು (`src/app/(dashboard)/dashboard/settings/components/ModelCooldownsCard.tsx`)

ಸಕ್ರಿಯ ಲಾಕ್ಔಟ್ಗಳನ್ನು ಇವುಗಳೊಂದಿಗೆ ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ: ಪ್ರೊವೈಡರ್, ಕನೆಕ್ಷನ್, ಮಾದರಿ, ಕಾರಣ, expiresAt. ಆಪರೇಟರ್ಗಳು ಕಾರ್ಡ್ನಿಂದ ಮಾದರಿಯನ್ನು ಹಸ್ತಚಾಲಿತವಾಗಿ ಮರು-ಸಕ್ರಿಯಗೊಳಿಸಬಹುದು.

**REST API:**

- `GET /api/resilience/model-cooldowns` — ಸಕ್ರಿಯ ಲಾಕ್ಔಟ್ಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡಿ
- `DELETE /api/resilience/model-cooldowns` — ಹಸ್ತಚಾಲಿತ ಮರು-ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ. ಬಾಡಿ: `{provider, connection, model}`. ದೃಢೀಕರಣ: management.

### ಕೂಲ್ಡೌನ್ ಮ್ಯಾನೇಜರ್

UI: ಮಾನಿಟರಿಂಗ್ → ಕೂಲ್ಡೌನ್ ಮ್ಯಾನೇಜರ್ (`src/app/(dashboard)/dashboard/resilience/cooldowns/`).

ಪ್ರತಿ ಪ್ರೊವೈಡರ್ ಪುಟವನ್ನು ತೆರೆಯುವ ಬದಲು, ತಾತ್ಕಾಲಿಕ ಕಾರಣದಿಂದ ರೂಟಿಂಗ್ನಿಂದ ಹೊರಗಿರುವ ಪ್ರತಿಯೊಂದು ಕನೆಕ್ಷನ್ಗಾಗಿ ಒಂದೇ ಪುಟ. ಇದು ಕನೆಕ್ಷನ್ ಕೂಲ್ಡೌನ್ಗಳು, ಮಾದರಿ ಲಾಕ್ಔಟ್ಗಳು ಮತ್ತು ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ, ಅವುಗಳನ್ನು ಪ್ರತಿ ಕನೆಕ್ಷನ್ಗೆ, ಆಯ್ದ ಒಂದು ಗುಂಪಿಗೆ, ಅಥವಾ ಪ್ರೊವೈಡರ್ನ ಎಲ್ಲಾ ಕನೆಕ್ಷನ್ಗಳಿಗೆ ತೆರವುಗೊಳಿಸುತ್ತದೆ, ಮತ್ತು ಅತ್ಯಂತ ಹೆಚ್ಚು ಟ್ಯೂನ್ ಮಾಡಲಾದ ಕೂಲ್ಡೌನ್ ನಿಯಮಗಳನ್ನು ಸಂಪಾದಿಸುತ್ತದೆ: `streamStallCooldown.enabled` ಮತ್ತು OAuth / API-ಕೀ `connectionCooldown` ಮೂಲ ಕೂಲ್ಡೌನ್ ಹಾಗೂ ಗರಿಷ್ಠ ಬ್ಯಾಕ್ಆಫ್ ಹಂತಗಳು (`PATCH /api/resilience` ಮೂಲಕ ಉಳಿಸಲಾಗುತ್ತದೆ). ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳನ್ನು (`banned`, `expired`, `credits_exhausted`) ಪಟ್ಟಿ ಮಾಡಲಾಗುತ್ತದೆ ಆದರೆ ಇಲ್ಲಿ ಎಂದಿಗೂ ತೆರವುಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ.

**REST API** (`src/lib/resilience/cooldownManager.ts`, ದೃಢೀಕರಣ: management):

- `GET /api/resilience/cooldowns[?provider=]` — ಸ್ಥಿತಿ, ಉಳಿದ ಕೂಲ್ಡೌನ್, ಬ್ಯಾಕ್ಆಫ್ ಮಟ್ಟ, ಕೊನೆಯ ದೋಷ ಪ್ರಕಾರ ಮತ್ತು ಮಾದರಿ ಲಾಕ್ಔಟ್ಗಳೊಂದಿಗೆ ಕನೆಕ್ಷನ್ಗಳು (ರುಜುವಾತುಗಳಿಲ್ಲ)
- `POST /api/resilience/cooldowns` — ಬಾಡಿ `{connectionIds: string[]}` ಅಥವಾ
  `{all: true, provider?}`; `{cleared, unchanged, skippedTerminal, lockoutsCleared}` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

### ಲಾಕ್ಔಟ್ ಸೆಟ್ಟಿಂಗ್ಗಳ UI + ಯಶಸ್ಸು-ಕ್ಷಯ ಚೇತರಿಕೆ (v3.8.23)

ಮಾದರಿ ಲಾಕ್ಔಟ್ ಯಾವಾಗಲೂ-ಆನ್ ಆಗಿರುವ ಹಾರ್ಡ್ಕೋಡ್ ಮಾಡಿದ ನಡವಳಿಕೆಯಿಂದ, ತನ್ನ ಸ್ವಂತ ಸೆಟ್ಟಿಂಗ್ಗಳ ಕಾರ್ಡ್ ಮತ್ತು ಸ್ವಯಂ-ಗುಣಮುಖ ಚೇತರಿಕೆ ಮಾರ್ಗದೊಂದಿಗೆ, ಸಂಪೂರ್ಣವಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ ಆಪ್ಟ್-ಇನ್ ವೈಶಿಷ್ಟ್ಯಕ್ಕೆ ಬದಲಾಗಿದೆ.

**ಸೆಟ್ಟಿಂಗ್ಗಳ ಕಾರ್ಡ್:** ಸೆಟ್ಟಿಂಗ್ಗಳು → ಮಾದರಿ ಲಾಕ್ಔಟ್
(`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`).
ಇದು ಮೇಲಿನ ಓದಲು-ಮಾತ್ರದ `ModelCooldownsCard` ನಿಂದ **ಭಿನ್ನವಾಗಿದೆ** (ಅದು ಕೇವಲ ಸಕ್ರಿಯ ಲಾಕ್ಔಟ್ಗಳನ್ನು _ಪಟ್ಟಿ_ ಮಾಡುತ್ತದೆ) — ಹೊಸ ಕಾರ್ಡ್ _ನಿಯತಾಂಕಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುತ್ತದೆ_. ಡೀಫಾಲ್ಟ್ಗಳು `DEFAULT_MODEL_LOCKOUT_SETTINGS` ನಲ್ಲಿ ಇವೆ
(`src/lib/resilience/modelLockoutSettings.ts`):

| ಸೆಟ್ಟಿಂಗ್               | ಡೀಫಾಲ್ಟ್                         | ಅರ್ಥ                                                               |
| ----------------------- | -------------------------------- | ------------------------------------------------------------------ |
| `enabled`               | `false`                          | ಮಾಸ್ಟರ್ ಟಾಗಲ್ — ಮಾದರಿ ಲಾಕ್ಔಟ್ **ಡೀಫಾಲ್ಟ್ ಆಗಿ ಆಫ್ ಆಗಿದೆ**.          |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | ಮಾದರಿ-ವ್ಯಾಪ್ತಿಯ ವೈಫಲ್ಯವಾಗಿ ಪರಿಗಣಿಸಲಾಗುವ ಅಪ್ಸ್ಟ್ರೀಮ್ ಸ್ಥಿತಿಗಳು.     |
| `baseCooldownMs`        | `120_000` (120 ಸೆ)               | ಮೊದಲ ವೈಫಲ್ಯಕ್ಕೆ ಆರಂಭಿಕ ಲಾಕ್ಔಟ್ ಅವಧಿ.                               |
| `maxCooldownMs`         | `1_800_000` (30 ನಿಮಿಷ)           | ಹೆಚ್ಚಿಸಿದ ಕೂಲ್ಡೌನ್ನ ಮೇಲಿನ ಮಿತಿ.                                    |
| `maxBackoffSteps`       | `10`                             | ಗರಿಷ್ಠ ಘಾತಾಂಕೀಯ-ಬ್ಯಾಕ್ಆಫ್ ಹೆಚ್ಚಳದ ಹಂತಗಳು.                          |
| `useExponentialBackoff` | `true`                           | ಪುನರಾವರ್ತಿತ ವೈಫಲ್ಯಗಳು ಕೂಲ್ಡೌನ್ ಅನ್ನು ಘಾತಾಂಕೀಯವಾಗಿ ಹೆಚ್ಚಿಸುತ್ತವೆಯೇ. |

ಸೆಟ್ಟಿಂಗ್ಗಳು ಸಾಮಾನ್ಯ ಸೆಟ್ಟಿಂಗ್ಗಳ ಸ್ಟೋರ್ ಮೂಲಕ ಶೇಖರಿಸಲ್ಪಡುತ್ತವೆ ಮತ್ತು ರೆಸಿಲಿಯೆನ್ಸ್ ಸೆಟ್ಟಿಂಗ್ಗಳ ಸ್ಕೀಮಾ ಮೂಲಕ ಮಾನ್ಯಗೊಳಿಸಲ್ಪಡುತ್ತವೆ; ಕಾರ್ಡ್ `baseCooldownMs`/`maxCooldownMs` (`maxCooldownMs ≥ baseCooldownMs` ಆಗುವಂತೆ) ಮತ್ತು `maxBackoffSteps` ಅನ್ನು ಕ್ಲಾಂಪ್ ಮಾಡುತ್ತದೆ.

**ಯಶಸ್ಸು-ಕ್ಷಯ ಚೇತರಿಕೆ:** ಚೇತರಿಕೆಯು **ಕೇವಲ** ಟೈಮರ್ ಮುಗಿಯುವಿಕೆಯಲ್ಲ. ಆರೋಗ್ಯಕರ ಪ್ರತಿಕ್ರಿಯೆಯು ಮಾದರಿಯ ವೈಫಲ್ಯ ಸಂಖ್ಯೆಯನ್ನು ಮತ್ತೆ ಕೆಳಗಿಳಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಮಧ್ಯ-ವಿಂಡೋದಲ್ಲಿ ಚೇತರಿಸಿಕೊಂಡ ಮಾದರಿಯು ಅದರ ಟೈಮರ್ ಮುಗಿಯುವ ಮೊದಲೇ ಹೆಚ್ಚಳವನ್ನು ನಿಲ್ಲಿಸುತ್ತದೆ (ಮತ್ತು ತೆರವಾಗುತ್ತದೆ). ಯಶಸ್ವಿ ಕಾಂಬೊ ಗುರಿಯ ಮೇಲೆ, `open-sse/services/combo.ts` `decayModelFailureCount()` ಅನ್ನು ಕರೆಯುತ್ತದೆ
(`open-sse/services/accountFallback.ts`), ಇದು ಸಂಗ್ರಹಿಸಲಾದ `failureCount` ಅನ್ನು **ಅರ್ಧ** ಮಾಡುತ್ತದೆ (`Math.floor(failureCount / 2)`); ಅದು `0` ಅನ್ನು ತಲುಪಿದಾಗ ಲಾಕ್ಔಟ್ ಎಂಟ್ರಿಯನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಅಳಿಸಲಾಗುತ್ತದೆ. ಅದರ ಪ್ರತಿರೂಪ `recordModelLockoutFailure()` ಹೆಚ್ಚಳದ ವಿಂಡೋವೊಳಗಿನ ವೈಫಲ್ಯಗಳಲ್ಲಿ ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸುತ್ತದೆ (ಮತ್ತು ಕೂಲ್ಡೌನ್ ಅನ್ನು ಹೆಚ್ಚಿಸುತ್ತದೆ). ಈ ಯಶಸ್ಸು-ಕ್ಷಯವು ಸರಳ ಟೈಮರ್ ಮುಗಿಯುವಿಕೆಗೆ ಹೆಚ್ಚುವರಿಯಾಗಿದೆ — ಎರಡು ಮಾರ್ಗಗಳಲ್ಲಿ ಯಾವುದಾದರೂ ಮಾದರಿಯನ್ನು ಮರು-ಸಕ್ರಿಯಗೊಳಿಸಬಹುದು.

**ಸ್ಥಿತಿ:** ಲಾಕ್ಔಟ್ಗಳನ್ನು **ಇನ್-ಮೆಮೊರಿ**ಯಲ್ಲಿ ಹಿಡಿಸಲಾಗುತ್ತದೆ (`provider:connectionId:model` ಕೀಲಿಯಿಂದ ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಯ `Map` ಗಳಲ್ಲಿ `ModelLockoutEntry` ಆಗಿ, ನಿಖರ-ವ್ಯಾಪ್ತಿಯ ಲಾಕ್ಗಳು `provider:connectionId:exact:model` ಕೀಲಿಯಿಂದ), DB ಗೆ ಶೇಖರಿಸಲಾಗುವುದಿಲ್ಲ — ಅವು ಮರುಪ್ರಾರಂಭದಲ್ಲಿ ಕಳೆದುಹೋಗುತ್ತವೆ. _ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು_ ಶೇಖರಿಸಲಾಗುತ್ತದೆ; ಸಕ್ರಿಯ ಲಾಕ್ಔಟ್ _ಸ್ಥಿತಿ_ ಕ್ಷಣಿಕವಾಗಿದೆ.

## 4. ಕೋಟಾ-ಹಂಚಿಕೆ ಏಕಕಾಲಿಕ ನಿಯಂತ್ರಣ (v3.8.36)

ಚಂದಾದಾರಿಕೆ ಖಾತೆಗಳು (GLM, MiniMax, ಇತ್ಯಾದಿ) ಸಾಮಾನ್ಯವಾಗಿ ~ 1-3 ಏಕಕಾಲೀನ ವಿನಂತಿಗಳನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸುತ್ತವೆ; ಮೀರಿದರೆ 429ಗಳು ಮತ್ತು ಕೂಲ್ಡೌನ್ಗಳನ್ನು ಪ್ರಚೋದಿಸುತ್ತದೆ. ಇದು ಅಡಿಯಲ್ಲಿ ತೀವ್ರವಾಗಿರುತ್ತದೆ** ಕೋಟಾ-ಪಾಲು** (`qtSd/…`) ಕಾಂಬೊಗಳು, ಅಲ್ಲಿ ಹಲವಾರು API ಕೀಗಳು ಒಂದು ಅಪ್ಸ್ಟ್ರೀಮ್ ಖಾತೆಯನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ. ಮೂರು ಲೇಯರ್ಗಳು ಹಂಚಿದ ಖಾತೆಯನ್ನು ಪ್ರವಾಹಕ್ಕೆ ಒಳಗಾಗದಂತೆ ಇರಿಸುತ್ತವೆ.

### ಪ್ರತಿ-ಸಂಪರ್ಕ ಏಕಕಾಲಿಕ ಕ್ಯಾಪ್ (`max_concurrent`)

ಪ್ರತಿ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕವು `max_concurrent` ಸೀಲಿಂಗ್ ಅನ್ನು ಘೋಷಿಸಬಹುದು (`provider_connections.max_concurrent`, ಸಂಪರ್ಕ ಮಾದರಿಯಲ್ಲಿ ಹೊಂದಿಸಲಾಗಿದೆ / API / DB). ಯಾವುದೇ ಮಿತಿಯಿಲ್ಲದೆ ಅದನ್ನು ಖಾಲಿ ಬಿಡಿ. ಇದು — ಕೆಳಗಿನ ಧಾರಾವಾಹಿ ಲೇಯರ್ ಅನ್ನು ಚಾಲನೆ ಮಾಡುವ ಏಕೈಕ ನಾಬ್ ಆಗಿದ್ದು ಅದನ್ನು ಖಾತೆಯ ನೈಜ ಏಕಕಾಲಿಕತೆಗೆ ಹೊಂದಿಸುತ್ತದೆ (ಉದಾ GLM ~ 1, MiniMax ~ 2).

### ಪ್ರತಿ ಮಾದರಿಯ ಏಕಕಾಲಿಕ ಕ್ಯಾಪ್ಸ್ (`modelConcurrency`)

ಸಂಪರ್ಕವು ಅದರ `rateLimitOverrides` ನಕ್ಷೆಯೊಳಗೆ ನಿಖರವಾದ ಪ್ರತಿ-ಮಾದರಿ ಏಕಕಾಲಿಕ ಸೀಲಿಂಗ್ಗಳನ್ನು ಹೆಚ್ಚುವರಿಯಾಗಿ ಘೋಷಿಸಬಹುದು:

```json
{
  "rateLimitOverrides": {
    "maxConcurrent": 4,
    "modelConcurrency": { "glm-5": 1, "glm-4.7": 3 }
  }
}
```

ಸಂಪರ್ಕ ಮಾದರಿಯಲ್ಲಿ ಹೊಂದಿಸಿ (** ದರ ಮಿತಿಯು → ಪ್ರತಿ-ಮಾದರಿ ಏಕಕಾಲಿಕ ಕ್ಯಾಪ್ಗಳನ್ನು ಅತಿಕ್ರಮಿಸುತ್ತದೆ** , ಪ್ರತಿ ಸಾಲಿಗೆ ಒಂದು `model=cap` ) ಅಥವಾ ಅದೇ JSON ಆಕಾರದೊಂದಿಗೆ `PATCH /api/providers/[id]` ಮೂಲಕ. ಪ್ರಮುಖ ಶಬ್ದಾರ್ಥಗಳು:

- **ಸಂಪರ್ಕ-ವ್ಯಾಪಕ ಮತ್ತು ಮಾದರಿ-ನಿರ್ದಿಷ್ಟ:** `maxConcurrent` ಹಂಚಿಕೆಯ ಸಂಪರ್ಕ-ವಿಶಾಲ ಸೀಲಿಂಗ್ ಆಗಿ ಉಳಿದಿದೆ. ಎರಡೂ ಅನ್ವಯಿಸಿದಾಗ, ಎರಡೂ ಗೇಟ್ಗಳನ್ನು ಒಂದೇ ಸಂಯೋಜಿತ ಗೇಟ್ನಲ್ಲಿ (`global → provider → account → model`) ಪರಮಾಣುವಾಗಿ ಪಡೆದುಕೊಳ್ಳಲಾಗುತ್ತದೆ; ಪರಿಣಾಮಕಾರಿ ನಡವಳಿಕೆಯು ಕಟ್ಟುನಿಟ್ಟಾದ ಅನ್ವಯವಾಗುವ ಮಿತಿಯಾಗಿದೆ.
- **ನಿಖರವಾದ ಮಾದರಿ-ಕೀ ಹೊಂದಾಣಿಕೆ:** ಕೀಲಿಯೆಂದರೆ — ರೆಸಲ್ಯೂಶನ್ ಅನ್ನು ರೂಟಿಂಗ್ ಮಾಡಿದ ನಂತರ ಎಕ್ಸಿಕ್ಯೂಟರ್ಗೆ ರವಾನಿಸಲಾದ ಮಾದರಿ ಸ್ಟ್ರಿಂಗ್ ಸಾಮಾನ್ಯವಾಗಿ ಬೇರ್ ಅಪ್ಸ್ಟ್ರೀಮ್ ಮಾಡೆಲ್ ಐಡಿ (`glm-5`), ಕ್ಲೈಂಟ್-ಸೈಡ್ `provider/model` ಅಲಿಯಾಸ್ ಅಲ್ಲ (`zai/glm-5` `glm-5` ಹೊಂದಿಕೆಯಾಗುವುದಿಲ್ಲ). ಮೌಲ್ಯಗಳು ಧನಾತ್ಮಕ-ಪೂರ್ಣಾಂಕ ಏಕಕಾಲೀನ-ವಿನಂತಿ ಸೀಲಿಂಗ್ಗಳಾಗಿವೆ.
- **ಸ್ಥಳೀಯ ಸರತಿ ಸಾಲಿನಲ್ಲಿ, ಯಾವುದೇ ಅನ್ವೇಷಣೆ ಇಲ್ಲ:** ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ queue/timeout ಸೆಮ್ಯಾಂಟಿಕ್ಸ್ನೊಂದಿಗೆ ಹೆಚ್ಚುವರಿ ವಿನಂತಿಗಳು ಸ್ಥಳೀಯವಾಗಿ ಸರದಿಯಲ್ಲಿವೆ (ಟೈಪ್ ಮಾಡಿದ `SEMAPHORE_TIMEOUT` / `SEMAPHORE_QUEUE_FULL` ಪ್ರವೇಶ ದೋಷಗಳು). OmniRoute ಅಪ್ಸ್ಟ್ರೀಮ್ ನೀತಿಯನ್ನು ಕಂಡುಹಿಡಿಯುವುದಿಲ್ಲ ಅಥವಾ ಊಹಿಸುವುದಿಲ್ಲ — ಇದು ಆಪರೇಟರ್ ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ ನಿಖರವಾದ ಸೀಲಿಂಗ್ಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ. ಸ್ಯಾಚುರೇಟೆಡ್ ಮಾಡೆಲ್ ಗೇಟ್ ಒದಗಿಸುವವರನ್ನು ಎಂದಿಗೂ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದಿಲ್ಲ ಮತ್ತು ಶಾಶ್ವತ ಮಾದರಿ ಲಾಕ್ಔಟ್ ಅನ್ನು ಎಂದಿಗೂ ರಚಿಸುವುದಿಲ್ಲ; ಅಪ್ಸ್ಟ್ರೀಮ್ 429/cooldown/fallback ವರ್ತನೆಯು ದೋಷ ಬ್ಯಾಕ್ಸ್ಟಾಪ್ ಆಗಿ ಉಳಿದಿದೆ.
- **ಪ್ರತಿ ಸಂಪರ್ಕ, ಪ್ರತಿ ಪ್ರಕ್ರಿಯೆಯ ವ್ಯಾಪ್ತಿ:** ಕ್ಯಾಪ್ಸ್ ಪ್ರತಿ ಡೇಟಾಬೇಸ್ ಸಂಪರ್ಕ ಮತ್ತು ಮೆಮೊರಿಯಲ್ಲಿ ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ ಒಂದೇ ಅಪ್ಸ್ಟ್ರೀಮ್ API ಕೀಯನ್ನು ಮರುಬಳಕೆ ಮಾಡುವ ಎರಡು ಸಂಪರ್ಕಗಳು ಪರಸ್ಪರ ಹೊಂದಾಣಿಕೆಯಾಗುವುದಿಲ್ಲ.
- **ಕಾನ್ಫಿಗರ್ ಮಾಡದಿರುವುದು ಎಂದರೆ ಬದಲಾಗದೆ:** ನಕ್ಷೆಯನ್ನು ಬಿಟ್ಟುಬಿಡುವುದು (ಅಥವಾ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಕ್ಷೇತ್ರವನ್ನು ಖಾಲಿ ಬಿಡುವುದು) ಯಾವುದೇ ಮಾದರಿ ಗೇಟ್ ಅನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ. ಯಾವುದೇ ಸಾರ್ವತ್ರಿಕ ಪೂರೈಕೆದಾರರ ಮಿತಿಯನ್ನು ಪ್ರತಿಪಾದಿಸದೆಯೇ ಉದಾಹರಣೆ ಕಾನ್ಫಿಗರೇಶನ್:

```text
glm-5=1
glm-4.7=3
```

### ಕೋಟಾ-ಹಂಚಿಕೆ ವಿನಂತಿ ಧಾರಾವಾಹಿ

ಕೋಟಾ-ಹಂಚಿಕೆ ರವಾನೆಯು ಧನಾತ್ಮಕ `max_concurrent` ಘೋಷಿಸುವ ಸಂಪರ್ಕವನ್ನು ಗುರಿಪಡಿಸಿದಾಗ, ಅದಕ್ಕೆ ಏಕಕಾಲಿಕ ವಿನಂತಿಗಳು** ಖಾತೆ** ಪ್ರತಿ-ಕನೆಕ್ಷನ್ ಸೆಮಾಫೋರ್ (ಕೀ `qsconn:<connectionId>`) ಮೂಲಕ ಧಾರಾವಾಹಿ ಮಾಡಲಾಗುತ್ತದೆ: ಹೆಚ್ಚುವರಿ ವಿನಂತಿಗಳು** ಸರದಿಯಲ್ಲಿ ಕಾಯಿರಿ** ಬದಲಿಗೆ ಖಾತೆಗೆ ಪ್ರವಾಹ. ಇದು** ವಿಫಲ-ತೆರೆದ** — ಒಂದು ಸ್ಯಾಚುರೇಟೆಡ್ ಕ್ಯೂ ಅಥವಾ ಟೈಮ್ಔಟ್ ಸ್ಲಾಟ್ ಇಲ್ಲದೆ ಮುಂದುವರಿಯುತ್ತದೆ ಬದಲಿಗೆ ಕಳುಹಿಸಬಹುದಾದ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ಟಾಗಲ್ ಇನ್ ಮಾಡಿ** ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಕೋಟಾ-ಹಂಚಿಕೆ ಪ್ರತಿ-ಸಂಪರ್ಕ ಏಕಕಾಲಿಕತೆ** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, ಡೀಫಾಲ್ಟ್ ಆನ್). `max_concurrent` ಕ್ಯಾಪ್ ಇಲ್ಲದೆ ವರ್ತನೆಯು ಬದಲಾಗುವುದಿಲ್ಲ.

> ಕೋಟಾ-ಶೇರ್ ರೂಟಿಂಗ್ ಗೇಟ್ (`selectQuotaShareTarget`, DRR + P2C) ಸ್ವತಃ ವಿಫಲವಾಗಿದೆ-ತೆರೆದಿದೆ ಮತ್ತು ಏಕ-ಸಂಪರ್ಕ ಪೂಲ್ನೊಂದಿಗೆ ಅಟ್-ಕ್ಯಾಪ್ ಸಂಪರ್ಕ — ಅನ್ನು ಮಾತ್ರ _deprioritizes_ ಇದು ಕಠಿಣ-ಮಿತಿಗೊಳಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ, ಆದ್ದರಿಂದ ಈ ಸೆಮಾಫೋರ್ ನಿಜವಾಗಿ ಪ್ರವಾಹವನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ.

### ಕಾಂಬೊ ಕೂಲ್ಡೌನ್-ಅರಿವು ಮರುಪ್ರಯತ್ನಿಸಿ

ಪ್ರತಿ ಕಾಂಬೊ ತಂತ್ರಕ್ಕೆ (ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ), SHORT ಅಸ್ಥಿರ ಕೂಲ್ಡೌನ್ಗಾಗಿ 429 ಅನ್ನು ಸ್ಫಟಿಕೀಕರಿಸುವ ವಿನಂತಿಯು ಅದನ್ನು ಕಾಯುತ್ತದೆ ಮತ್ತು 429 — ಅನ್ನು ಹಿಂತಿರುಗಿಸುವ ಬದಲು ಮರು-ರವಾನೆ ಮಾಡುತ್ತದೆ, ಇದು ಜೆಮಿನಿ-ಕ್ಲಾಸ್ TPM/RPM ವಿಂಡೋಗಳನ್ನು (~ 60s ಮರುಪ್ರಯತ್ನದ ನಂತರ) ಬಹು-ಮಾದರಿ 2 ಹಿಟ್ ಕಾಂಬೋಸ್ನ ಕಾಂಬೊಸ್-ಎರಡೂ ಟಾರ್ಗೆಟ್ಮೊಗಳಲ್ಲಿ ಪ್ರತಿ ಮಾದರಿ ದರ ಮಿತಿ. ರಲ್ಲಿ `comboCooldownWait` (`enabled`, `maxWaitMs`, `maxAttempts`, `budgetMs`) ನಿಂದ ಸುತ್ತುವರಿದಿದೆ** ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ** . ಇದು ಎಂದಿಗೂ `quota_exhausted` (ಮಧ್ಯರಾತ್ರಿಯವರೆಗೆ ಲಾಕ್) ಅಥವಾ auth/not-found ಕಾರಣಗಳಿಗಾಗಿ ಕಾಯುವುದಿಲ್ಲ.

`config.comboCooldownWaitEnabled: false` ನೊಂದಿಗೆ ಕಾಂಬೊ ಆಯ್ಕೆಯಿಂದ ಹೊರಗುಳಿಯಬಹುದು. ಅಕ್ಷರಶಃ `false` ಮಾತ್ರ ಈ ಹಂಚಿದ ಕಾಂಬೊ ವೇಯ್ಟ್ಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ (ಪೋಸ್ಟ್ ಡಿಸ್ಪ್ಯಾಚ್ ಕೂಲ್ಡೌನ್ ಮತ್ತು ಪ್ರಿ-ಡಿಸ್ಪ್ಯಾಚ್ circuit-open/model-lock ವೇಟ್ಸ್) ಮತ್ತು ಅವರ ವೇಯ್ಟ್-ಬಜೆಟ್ ಟೈಮ್ಔಟ್-ಫ್ಲೋರ್ ಎಕ್ಸ್ಟೆನ್ಶನ್. ಕಾಣೆಯಾಗಿದೆ ಅಥವಾ `true` ಜಾಗತಿಕ ನೀತಿಯನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ; `true` ಜಾಗತಿಕವಾಗಿ ಅಶಕ್ತಗೊಂಡ ಕಾಯುವಿಕೆಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಸ್ಪಷ್ಟವಾದ `targetTimeoutMs` ಇನ್ನೂ ಗೆಲ್ಲುತ್ತದೆ. ಈ ಆಯ್ಕೆಯಿಂದ ಹೊರಗುಳಿಯುವಿಕೆಯು ಪ್ರತ್ಯೇಕ ಸ್ಥಳೀಯ-ಕೋಡೆಕ್ಸ್ ಟರ್ನ್-ಪಿನ್ ಪೂರ್ವ-ರವಾನೆ ಕಾಯುವಿಕೆಯನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

ಅದೇ ಗೇಟ್ ಪ್ರೀ-ಡಿಸ್ಪ್ಯಾಚ್ ಕೇಸ್ (#16319) ಅನ್ನು ಆವರಿಸುತ್ತದೆ: ಯಾವುದೇ ಪ್ರಯತ್ನವನ್ನು ಮಾಡುವ ಮೊದಲು ಕಾಂಬೊದ ಪ್ರತಿಯೊಂದು ಗುರಿಯನ್ನು ಸ್ಕಿಪ್ ಮಾಡಿದಾಗ, ಅದರ ಮಾದರಿಯು ಒಂದು ಸಣ್ಣ ತಾತ್ಕಾಲಿಕ ಲಾಕ್ಔಟ್ನಲ್ಲಿ ಕುಳಿತುಕೊಳ್ಳುತ್ತದೆ, ಶೂನ್ಯ-ಪ್ರಯತ್ನದ ಮಾರ್ಗವು ಸುಳಿವು-ಕಡಿಮೆ `503 ALL_TARGETS_SKIPPED` ಉತ್ತರಿಸುವ ಬದಲು ಅದೇ ಸೀಲಿಂಗ್ಗಳ ಅಡಿಯಲ್ಲಿ ಲಾಕ್ ಔಟ್ ಅನ್ನು ಕಾಯುತ್ತದೆ ಮತ್ತು ಮರು-ರವಾನೆ ಮಾಡುತ್ತದೆ. ಯಾವುದೇ ಕಾಯುವಿಕೆಯನ್ನು ಅನುಮತಿಸದಿದ್ದಾಗ (ಸೀಲಿಂಗ್, ಪ್ರಯತ್ನ ಅಥವಾ ಬಜೆಟ್ ಖಾಲಿಯಾಗಿದೆ, ಅಥವಾ ವೈಶಿಷ್ಟ್ಯವು ಆಫ್ ಆಗಿದೆ), ಟರ್ಮಿನಲ್ ಪ್ರತಿಕ್ರಿಯೆಯು `429 rate_limit_error` ಸಾಗಿಸುವ `retry_after` / `reset_at` ಗೆ ಆರಂಭಿಕ ಅಸ್ಥಿರ ಲಾಕ್ ಮುಕ್ತಾಯದಿಂದ ನವೀಕರಿಸುತ್ತದೆ; ಕೋಟಾ, ದೃಢೀಕರಣ ಮತ್ತು ಕಂಡುಬಂದಿಲ್ಲದ ಲಾಕ್ಗಳು ಸುಳಿವು-ಕಡಿಮೆ 503 ಅನ್ನು ಇರಿಸುತ್ತವೆ.

```text
#16319 · comboCooldownWait · pre-dispatch (attempts = 0)
all targets skipped + transient model lockout:
  enabled ∧ 0 < waitMs ≤ maxWaitMs ∧ attempt < maxAttempts ∧ budgetLeftMs ≥ waitMs
    → wait → re-dispatch
  wait = false → HTTP 429 rate_limit_error
  retry_after / reset_at ← earliest transient lock expiry
quota_exhausted / auth_error / not_found / not_found_local:
  no transient hint → HTTP 503 ALL_TARGETS_SKIPPED
```

## 5. ರಿಕ್ವೆಸ್ಟ್ ಕ್ಯೂ ಅಡ್ಮಿಷನ್ ಕಂಟ್ರೋಲ್ (v3.8.49 · issue #6593)

**ವ್ಯಾಪ್ತಿ**: ಪ್ರತಿ-ಪ್ರೊವೈಡರ್+ಕನೆಕ್ಷನ್ ಸ್ಥಳೀಯ ರೇಟ್-ಲಿಮಿಟ್ ಕ್ಯೂ (`open-sse/services/rateLimitManager.ts`, Bottleneck ಮೂಲಕ ಬೆಂಬಲಿತ), ಮೇಲಿನ ಮೂರು ಕ್ರಮಗಳಿಗಿಂತ ಒಂದು ಪದರ ಕೆಳಗಿನದ್ದು.

**`maxWaitMs` ಕ್ಯೂ ಕಾಯುವಿಕೆಯನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ; `executionMaxWaitMs` ಎಕ್ಸಿಕ್ಯೂಶನ್ ಅನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ.** ಈ ಎರಡನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ, ಮತ್ತು ಯಾವುದೂ ಇನ್ನೊಂದಕ್ಕೆ ಪೂರೈಕೆ ನೀಡುವುದಿಲ್ಲ.

`resilienceSettings.requestQueue.maxWaitMs` ಎಂದರೆ **ಕ್ಯೂ-ಕಾಯುವಿಕೆ ಬಜೆಟ್**: ಇದು ಪ್ರೊವೈಡರ್ ಸ್ಲಾಟ್ಗಾಗಿ ಕಾಯುವುದನ್ನು ಮತ್ತು ನಂತರ QUEUED ಸ್ಥಿತಿಯಲ್ಲಿ ಕುಳಿತಿರುವುದನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ, ಮತ್ತು ಜಾಬ್ QUEUED ಸ್ಥಿತಿಯನ್ನು ಬಿಟ್ಟು ಎಕ್ಸಿಕ್ಯೂಟ್ ಆಗಲಾರಂಭಿಸಿದ ಕ್ಷಣವೇ ಅದರ ಟೈಮರ್ ತೆರವುಗೊಳ್ಳುತ್ತದೆ (`rateLimitManager.ts`, `wrappedFn`). ಇದನ್ನು ಮೀರಿದ ರಿಕ್ವೆಸ್ಟ್ ಎಂದಿಗೂ ಅಪ್ಸ್ಟ್ರೀಮ್ ತಲುಪುವುದಿಲ್ಲ. ಡೀಫಾಲ್ಟ್ 30000ms, ಇದನ್ನು `src/lib/resilience/settings.ts` ನಲ್ಲಿ `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS` ಪೂರೈಸುತ್ತದೆ ಮತ್ತು `tests/unit/ratelimit-admission-control-6593.test.ts` ಪಿನ್ ಮಾಡುತ್ತದೆ — ಆದ್ದರಿಂದ ಇದನ್ನು ಬದಲಾಯಿಸಿದರೆ ಆ ಟೆಸ್ಟ್ ಕೆಂಪಾಗುತ್ತದೆ, ಈ ಪ್ಯಾರಾಗ್ರಾಫ್ ಮೌನವಾಗಿ ಹಳೆಯದಾಗಿ ಉಳಿಯುವುದಿಲ್ಲ.

`resilienceSettings.requestQueue.executionMaxWaitMs` ಅನ್ನು Bottleneck ಜಾಬ್ `expiration` ಆಗಿ ಸ್ವೀಕರಿಸುತ್ತದೆ, ಇದರ ಟೈಮರ್ ಡಿಸ್ಪ್ಯಾಚ್ ನಂತರ ಮಾತ್ರ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ. ತಮ್ಮದೇ ಆದ ಅಪ್ಸ್ಟ್ರೀಮ್ ಟೈಮ್ಔಟ್ ಇಲ್ಲದ ಎಕ್ಸಿಕ್ಯೂಟರ್ಗಳಿಗೆ ಇದು ಬ್ಯಾಕ್ಸ್ಟಾಪ್ ಆಗಿದೆ, ಮತ್ತು ಎಕ್ಸಿಕ್ಯೂಟರ್ನ ಸ್ವಂತ fetch-start ಟೈಮ್ಔಟ್ ಇದಕ್ಕಿಂತ ಉದ್ದವಾಗಿದ್ದಾಗ ಅದರ ಮಟ್ಟಕ್ಕೆ ಏರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಇದು ಆರೋಗ್ಯಕರ ಇನ್-ಫ್ಲೈಟ್ ರೆಸ್ಪಾನ್ಸ್ ಅನ್ನು ಕತ್ತರಿಸುವುದಿಲ್ಲ. ಡೀಫಾಲ್ಟ್ 600000ms (10 ನಿಮಿಷ).

ಕ್ಯೂ ಬಜೆಟ್ ಅನ್ನು `expiration` ಗೆ ಪೂರೈಸುವುದೇ ಹಿಂದೆ ನಾನ್-ಇಂಕ್ರಿಮೆಂಟಲ್ ಗೇಟ್ವೇಗಳನ್ನು ಮಿಡ್-ಫ್ಲೈಟ್ನಲ್ಲಿ ಕೊಲ್ಲುತ್ತಿದ್ದದ್ದು — ಅವು ಮೊದಲ ಬೈಟ್ಗಳಿಗೆ ಮೊದಲು ನಿಮಿಷಗಳ ಕಾಲ ಕಾನೂನುಬದ್ಧವಾಗಿ ರನ್ ಆಗುತ್ತವೆ — ಮತ್ತು ಅದಕ್ಕಾಗಿಯೇ expiration ಅನ್ನು `code: "RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504) ಆಗಿ ಮೇಲ್ಮೈಗೆ ತರಲಾಗುತ್ತದೆ, ಆದರೆ ಕ್ಯೂ ಬಜೆಟ್ ಕ್ಯೂ-ಟೈಮ್ಔಟ್ ಕೋಡ್ ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ. ಎರಡನ್ನೂ `RATE_LIMIT_MAX_WAIT_MS` / `RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (env) ಅಥವಾ ಡ್ಯಾಶ್ಬೋರ್ಡ್ (**Settings → Resilience**) ಮೂಲಕ ಓವರ್ರೈಡ್ ಮಾಡಬಹುದು. ಎರಡನ್ನೂ ನಾರ್ಮಲೈಜ್ ಮಾಡಿದಾಗ 1ms–24h ಗೆ ಕ್ಲಾಂಪ್ ಮಾಡಲಾಗುತ್ತದೆ.

**ಎರಡಕ್ಕೂ ಆದ್ಯತೆ:** env var ಕೇವಲ _ಡೀಫಾಲ್ಟ್_ ಅನ್ನು ಪೂರೈಸುತ್ತದೆ. `resilienceSettings.requestQueue` ನಲ್ಲಿ ಪರ್ಸಿಸ್ಟ್ ಮಾಡಲಾದ ಮೌಲ್ಯ (ಡ್ಯಾಶ್ಬೋರ್ಡ್ / API patch, `key_value` ನಲ್ಲಿ ಸಂಗ್ರಹ) ಅದನ್ನು ಗೆಲ್ಲುತ್ತದೆ, ಮತ್ತು ಪ್ರತಿ-ಕನೆಕ್ಷನ್ `rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` ಅದನ್ನೂ ಗೆಲ್ಲುತ್ತದೆ. ಆದ್ದರಿಂದ ಈಗಾಗಲೇ ಪರ್ಸಿಸ್ಟ್ ಮಾಡಲಾದ ಮೌಲ್ಯವಿರುವ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ನಲ್ಲಿ env var ಹೊಂದಿಸಿದರೆ ಏನೂ ಬದಲಾಗುವುದಿಲ್ಲ — ಬದಲಿಗೆ ಪರ್ಸಿಸ್ಟ್ ಮಾಡಲಾದ ಸೆಟ್ಟಿಂಗ್ ಅನ್ನು ತೆರವುಗೊಳಿಸಿ ಅಥವಾ ಅಪ್ಡೇಟ್ ಮಾಡಿ.

ಕ್ಯೂ ನಿವಾಸ ಅವಧಿಯನ್ನು `maxWaitMs` ಮಿತಿಗೊಳಿಸುತ್ತದೆ; ಕೆಳಗಿನ `maxQueueDepth` ಒಮ್ಮೆ ಎಷ್ಟು ಕಾಲರ್ಗಳು ಕ್ಯೂನಲ್ಲಿರಬಹುದು ಎಂಬುದನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ.

**ಬಾಡಿ-ಸೂಚಿತ ರಿಟ್ರೈಗಳು: ಪೇಸಿಂಗ್ vs ಲಾಕ್ಔಟ್.** 429 ಬಾಡಿ ತನ್ನದೇ ಕಾಯುವಿಕೆಯನ್ನು ಹೆಸರಿಸಬಹುದು (Gemini `RetryInfo.retryDelay`, "retry after Ns" ಪಠ್ಯ), ಇದನ್ನು `updateFromResponseBody` ಓದುತ್ತದೆ. ಕನೆಕ್ಷನ್ನ `maxWaitMs` ಗೆ ಹೊಂದುವ ಕಾಯುವಿಕೆ ಪೇಸಿಂಗ್ ಆಗಿದೆ: ಲಿಮಿಟರ್ ಆ ಅವಧಿಗೆ ತನ್ನ ರಿಸರ್ವಾಯರ್ ಅನ್ನು ಖಾಲಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಅದು ಮತ್ತೆ ತುಂಬಿದಾಗ ಕ್ಯೂನಲ್ಲಿರುವ ಕಾಲ್ಗಳು ಡಿಸ್ಪ್ಯಾಚ್ ಆಗುತ್ತವೆ. `maxWaitMs` ಗಿಂತ ಉದ್ದವಾದ ಕಾಯುವಿಕೆಯನ್ನು ಕ್ಯೂ ಕುಳಿತು ಕಾಯಲು ಸಾಧ್ಯವಿಲ್ಲ — Gemini ಖಾಲಿಯಾದ ದೈನಂದಿನ ಕೋಟಾಕ್ಕೆ `retryDelay: "86399s"` ನೊಂದಿಗೆ ಉತ್ತರಿಸುತ್ತದೆ. ಮರುನಿರ್ಮಿತ 429 ರ ಮೇಲಿನ ರಿಲೇ ಆಗಿರುವ `Retry-After` (#16528) ಈಗಾಗಲೇ ಫಾಲ್ಬ್ಯಾಕ್ ಎಂಜಿನ್ ಆ ವಿಂಡೋಗೆ ಮಾಡೆಲ್ ಅನ್ನು ಲಾಕ್ ಮಾಡುವಂತೆ ಮಾಡುತ್ತದೆ, ಆದರೆ ಅದಕ್ಕಾಗಿ ಲಿಮಿಟರ್ ಅನ್ನೂ ಪಾಜ್ ಮಾಡುವುದು ಕೀಯನ್ನು ಮುಂಚಿತವಾಗಿ ತಲುಪುವ ಯಾವುದೇ ಕಾಲ್ ಅನ್ನು (ಉದಾಹರಣೆಗೆ ರೆಸಿಲಿಯನ್ಸ್ ರಿಸೆಟ್ ನಂತರ) ಇಡೀ `maxWaitMs` ಅವಧಿಗೆ ನಿಲ್ಲಿಸುತ್ತದೆ. ಅಂಥ ಕಾಯುವಿಕೆ ಟೈಪ್ಡ್ Google `RetryInfo` ವಿವರದಿಂದ (`google_rpc_retry_info` ಪ್ರೊವೆನೆನ್ಸ್) ಬಂದಾಗ ಮತ್ತು ಕೀಯ ಲಿಮಿಟರ್ ಈಗಾಗಲೇ ಮಾಡೆಲ್ಗೆ ಸ್ಕೋಪ್ ಆಗಿದ್ದಾಗ (`getLimiterKey` ನೋಡಿ), 429 ಬದಲಿಗೆ ಆ ಕನೆಕ್ಷನ್ನಲ್ಲಿ ಮಾಡೆಲ್ ಲಾಕ್ಔಟ್ ಆಗುತ್ತದೆ (`open-sse/services/rateLimitManager/bodyRetryPause.ts` ನಲ್ಲಿರುವ `lockModelForLongBodyRetry`, 24h ಗೆ ಕ್ಯಾಪ್), ಮತ್ತು ಲಿಮಿಟರ್ ಅನ್ನು ಪಾಜ್ ಮಾಡದೆ ಬಿಡಲಾಗುತ್ತದೆ. ಅಕೌಂಟ್ ಸಿಲೆಕ್ಷನ್ ಆ ಲಾಕ್ ಮೂಲಕ `isModelLocked()` ನಿಂದ ಸ್ಕಿಪ್ ಆಗುತ್ತದೆ, ಮತ್ತು ಕನೆಕ್ಷನ್ಗೆ ಪಿನ್ ಆದ ಟಾರ್ಗೆಟ್ಗಳಿಗಾಗಿ ಕಾಂಬೊ ಪ್ರಿ-ಡಿಸ್ಪ್ಯಾಚ್ ಗೇಟ್ ಕೂಡ ಹಾಗೆಯೇ ಸ್ಕಿಪ್ ಆಗುತ್ತದೆ. antigravity ನಲ್ಲಿ, ಅದರ ಲಿಮಿಟರ್ ಪ್ರತಿ ಕೋಟಾ ಕುಟುಂಬಕ್ಕೆ ಇರುವುದರಿಂದ, ಲಾಕ್ ನಿಖರವಾದ ಮಾಡೆಲ್ ಮೇಲಿರುತ್ತದೆ — ಅದರ ಇತರ ಕೋಟಾ ಲಾಕ್ಗಳಂತೆಯೇ. ಅಲಿಯಾಸ್ ಅದನ್ನು ಆ ಮಾಡೆಲ್ಗೆ ರಿಸಾಲ್ವ್ ಮಾಡಿದಾಗ ಕ್ಲಯಂಟ್ ಕೇಳಿದ ಹೆಸರನ್ನೂ ಲಾಕ್ ಮಾಡಲಾಗುತ್ತದೆ, ಏಕೆಂದರೆ ಆ ಚೆಕ್ಗಳು ರಿಕ್ವೆಸ್ಟ್ ಮಾಡಲಾದ ಹೆಸರನ್ನು ಬಳಸುತ್ತವೆ; ಅದನ್ನು ನಿಖರವಾಗಿ ಲಾಕ್ ಮಾಡಲಾಗುತ್ತದೆ (`lockExactModel`), ಆದ್ದರಿಂದ antigravity ಕೋಟಾ ಕುಟುಂಬವನ್ನೋ ಅಥವಾ codex ಸ್ಕೋಪ್ ಅನ್ನೋ ದಾಟುವ ಅಲಿಯಾಸ್ ಎಂದಿಗೂ ತನ್ನದನ್ನೇ ಲಾಕ್ ಮಾಡುವುದಿಲ್ಲ. ಪ್ರೋಸ್ ಹಿಂಟ್, ಟೈಪ್ ಮಾಡದ `retryDelay`, ಅಥವಾ ಇಡೀ ಕನೆಕ್ಷನ್ನಿಂದ ಹಂಚಿಕೊಂಡ ಲಿಮಿಟರ್ ಪಾಜ್ ಅನ್ನು ಉಳಿಸುತ್ತದೆ. 429 ಪಾತ್ ಈಗಷ್ಟೇ ಮರುನಿರ್ಮಿಸಿದ ಲಿಮಿಟರ್ ಪಾಜ್ ಆದಾಗ, ಉಳಿದ ಕ್ಯೂ ಸಮಯವು ಪಾಜ್ ಮುಗಿಯುವ ಮೊದಲೇ ಮುಗಿಯುವ ಕಾಲರ್ ಅನ್ನು ಕೂಡಲೇ ಕ್ಯೂ-ಟೈಮ್ಔಟ್ ಕೋಡ್ನೊಂದಿಗೆ (`checkLimiterPause`) ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ — ಆ ಸಮಯವನ್ನು ಕಾಯುವ ಬದಲು; ದಾಖಲಾದ ಅಂತ್ಯವನ್ನು ಲಿಮಿಟರ್ ನಿರ್ಮಾಣಕ್ಕೆ ಮೊದಲು ಆಂಕರ್ ಮಾಡಲಾಗುತ್ತದೆ, ಅಲ್ಲಿ Bottleneck ತನ್ನ ರಿಫ್ರೆಶ್ ಕ್ಲಾಕ್ ಅನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ, ಮತ್ತು ರಿಸರ್ವಾಯರ್ಗೆ ನಂತರದ ಯಾವುದೇ ಬದಲಾವಣೆ ಅದನ್ನು ಮರೆತುಬಿಡುತ್ತದೆ. `tests/unit/rate-limit-long-body-retry-lockout.test.ts` ಮತ್ತು `tests/unit/rate-limit-body-retry-pause.test.ts` ಮೂಲಕ ಕವರ್ ಆಗಿದೆ.

**`maxQueueDepth` — ಆಪ್ಟ್-ಇನ್ ಅಡ್ಮಿಷನ್ ಕ್ಯಾಪ್ (ಹೊಸದು).** `resilienceSettings.requestQueue.maxQueueDepth` ಒಂದು ಪ್ರೊವೈಡರ್+ಕನೆಕ್ಷನ್ಗೆ ಒಮ್ಮೆ ಎಷ್ಟು ರಿಕ್ವೆಸ್ಟ್ಗಳು ಕ್ಯೂನಲ್ಲಿ ಕುಳಿತಿರಬಹುದು (ಇನ್ನೂ ಡಿಸ್ಪ್ಯಾಚ್ ಆಗಿಲ್ಲದಿರುವವು) ಎಂಬುದನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ. ಕ್ಯೂ ಈಗಾಗಲೇ `maxQueueDepth` ರಿಕ್ವೆಸ್ಟ್ಗಳನ್ನು ಹೊಂದಿದ್ದಾಗ, ಹೊಸ ರಿಕ್ವೆಸ್ಟ್ `limiter.schedule()` ಅನ್ನು ತಲುಪುವ **ಮೊದಲೇ** ಟೈಪ್ಡ್ `code: "RATE_LIMIT_QUEUE_FULL"` ಎರರ್ನೊಂದಿಗೆ ಫಾಸ್ಟ್-ರಿಜೆಕ್ಟ್ ಆಗುತ್ತದೆ — ಆದ್ದರಿಂದ ತಿರಸ್ಕಾರವು ಅಗ್ಗದಾಗಿದ್ದು, ಆ ರಿಕ್ವೆಸ್ಟ್ಗಾಗಿ ಯಾವುದೇ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಪ್ರಾಂಪ್ಟ್-ಕಂಪ್ರೆಶನ್ / ಟ್ರಾನ್ಸ್ಲೇಶನ್ ಕೆಲಸಕ್ಕಿಂತ ಮೊದಲು ನಡೆಯುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ `0` = ಡಿಸೇಬಲ್ಡ್, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅನ್ಬೌಂಡಡ್-ಕ್ಯೂ ಬಿಹೇವಿಯರ್ ಅನ್ನು ಉಳಿಸುತ್ತದೆ; 0–100000 ಗೆ ಬೌಂಡ್ ಮಾಡಲಾಗಿದೆ. `RATE_LIMIT_MAX_QUEUE_DEPTH` (env) ಅಥವಾ `resilienceSettings.requestQueue.maxQueueDepth` (ಡ್ಯಾಶ್ಬೋರ್ಡ್/API patch) ಮೂಲಕ ಓವರ್ರೈಡ್ ಮಾಡಬಹುದು.

ಅಡ್ಮಿಷನ್ ಚೆಕ್ ಸ್ವತಃ ಒಂದು ಪ್ಯೂರ್ ಫಂಕ್ಷನ್ ಆಗಿದೆ (`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), ಆದ್ದರಿಂದ ನಿಜವಾದ Bottleneck ಲಿಮಿಟರ್ ಇಲ್ಲದೆಯೂ ಅದನ್ನು ಯುನಿಟ್-ಟೆಸ್ಟ್ ಮಾಡಬಹುದು.

> #6593 ಅನ್ನು ತೆರೆದ RFC, `bypassCompressionOnRateLimit`
> ಫ್ಲ್ಯಾಗ್ ಅನ್ನೂ ಪ್ರಸ್ತಾಪಿಸಿತ್ತು. ಈ repo ಯ `open-sse/services/compression/` ಪೈಪ್ಲೈನ್
> ಹೊರಹೋಗುವ LLM ವಿನಂತಿಯ ಮೇಲಿನ ಪ್ರಾಂಪ್ಟ್/ಕಾಂಟೆಕ್ಸ್ಟ್ ಸಂಕುಚನವಾಗಿದೆ (`chatCore.ts`,
> `resolveCompressionSettings`/`selectCompressionStrategy` ಬ್ಲಾಕ್ನ ಆಸುಪಾಸಿನಲ್ಲಿ),
> ಸಂಶ್ಲೇಷಿತ 429 ಬಾಡಿಗಳ ಮೇಲಿನ HTTP ಪ್ರತಿಕ್ರಿಯೆ ಸಂಕುಚನವಲ್ಲ — ನೇರವಾದ bypass ಫ್ಲ್ಯಾಗ್ಗೆ
> ಹೊಂದುವ ಯಾವುದೇ ಕೋಡ್ ಪಥವಿಲ್ಲ. ಆ ಪ್ರಾಂಪ್ಟ್-ಸಂಕುಚನ ಹಂತವು ಪ್ರಸ್ತುತ ವಿನಂತಿ ಪೈಪ್ಲೈನ್ನಲ್ಲಿ
> `withRateLimit()` ಗಿಂತ _ಮೊದಲು_ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಕ್ಯೂ-ತುಂಬಿದೆ ಎಂಬ ನಿರಾಕರಣೆಯ
> ಸಂದರ್ಭದಲ್ಲಿ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡಲು ಕ್ರಮವನ್ನು ಬದಲಿಸುವುದು ಈ ಸಮಸ್ಯೆಯ ವ್ಯಾಪ್ತಿಗಿಂತ ಪ್ರತ್ಯೇಕವಾದ,
> ದೊಡ್ಡ ಬದಲಾವಣೆಯಾಗಿದೆ; ಇದನ್ನು ಇಲ್ಲಿ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ **ಅನುಷ್ಠಾನಗೊಳಿಸಲಾಗಿಲ್ಲ** ಮತ್ತು CPU
> ಉಳಿತಾಯದ ಲಾಭವು ಕ್ರಮ ಬದಲಾವಣೆಯ ಅಪಾಯಕ್ಕೆ ತಕ್ಕದ್ದಾಗಿದ್ದರೆ, ಅದನ್ನು ಅನುಸರಣಾ ಕಾರ್ಯವಾಗಿ ಬಿಡಲಾಗಿದೆ.

### ದರ-ಮಿತಿ ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವ ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆ ಮತ್ತು ಸಂಪರ್ಕ ರಕ್ಷಣೆ (`rateLimitProtection`)

**ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವ ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆ** (`resilienceSettings.requestQueue.autoEnableApiKeyProviders`, ಡೀಫಾಲ್ಟ್ `true`):
ಡೀಫಾಲ್ಟ್ ಆಗಿ, OmniRoute ಎಲ್ಲಾ ಸಕ್ರಿಯ API-key ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕಗಳಿಗೆ (`getProviderCategory(provider) === "apikey"`) ದರ-ಮಿತಿ ಕ್ಯೂ ರಕ್ಷಣೆಯನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ. ಇದು ದರಕ್ಕೆ ಸೂಕ್ಷ್ಮವಾಗಿರುವ ಅಪ್ಸ್ಟ್ರೀಮ್ API ಕೀಗಳಿಗೆ ಬರುವ ವಿನಂತಿಗಳು ಅಪ್ಸ್ಟ್ರೀಮ್ 429 ದೋಷಗಳಾಗಿ ಏಕಾಏಕಿ ಹೆಚ್ಚಾಗುವ ಬದಲು Bottleneck ಮೂಲಕ ಕ್ಯೂಗೆ ಸೇರಿಸಲ್ಪಟ್ಟು ನಿಯಂತ್ರಿಸಲ್ಪಡುವುದನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ. `RATE_LIMIT_AUTO_ENABLE` ಪರಿಸರ ಚರದ ಮೂಲಕ ಈ ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆಯನ್ನು ಅತಿಕ್ರಮಿಸಬಹುದು (`false`/`0`/`off` ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ, `true`/`1`/`on` ಬಲವಂತವಾಗಿ ಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ); ಇದು ಉಳಿಸಲಾದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಟ್ಟಿಂಗ್ಗಿಂತ (**Settings → Resilience** / `PATCH /api/resilience`) ಆದ್ಯತೆ ಪಡೆಯುತ್ತದೆ.

**ಪ್ರತಿ-ಸಂಪರ್ಕದ `rateLimitProtection` ನ ಅರ್ಥವ್ಯಾಪ್ತಿ:**
ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕಗಳಲ್ಲಿನ `rateLimitProtection` ಬೂಲಿಯನ್ ಕ್ಷೇತ್ರದ ಮೂಲಕ ಪ್ರತಿ-ಸಂಪರ್ಕದ ದರ-ಮಿತಿ ರಕ್ಷಣೆಯನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತದೆ (SQLite ನಲ್ಲಿ `rate_limit_protection` ಆಗಿ ಉಳಿಸಲಾಗುತ್ತದೆ):

- **ಸ್ಪಷ್ಟವಾಗಿ ಆನ್ (`rateLimitProtection === true`)**: ಪೂರೈಕೆದಾರರ ವರ್ಗ ಅಥವಾ ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವ ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆ ಆನ್ ಆಗಿದೆಯೇ ಎಂಬುದನ್ನು ಲೆಕ್ಕಿಸದೆ, ಈ ಸಂಪರ್ಕಕ್ಕೆ ದರ-ಮಿತಿ ರಕ್ಷಣೆಯನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಸಕ್ರಿಯಗೊಳಿಸಲಾಗುತ್ತದೆ.
- **ಸ್ಪಷ್ಟವಾಗಿ ಆಫ್ (`rateLimitProtection === false`)**: ಸ್ಪಷ್ಟ ರಕ್ಷಣೆಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ, ಆದರೆ ಸಕ್ರಿಯ API-key ಸಂಪರ್ಕವನ್ನು ಜಾಗತಿಕ ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವ ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆಯಿಂದ **ಹೊರಗಿಡುವುದಿಲ್ಲ**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) ನಲ್ಲಿ `false` ಮತ್ತು `undefined` ಸಮಾನವಾಗಿವೆ: `rateLimitProtection === true` ಅನ್ನು ಮಾತ್ರ ಸ್ಪಷ್ಟ ಅತಿಕ್ರಮಣವೆಂದು ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ. `rateLimitProtection` `false` ಆಗಿದ್ದರೆ (ಅಥವಾ ಹೊಂದಿಸದಿದ್ದರೆ), ಸಕ್ರಿಯ API-key ಸಂಪರ್ಕವು ಇನ್ನೂ ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವ ಷರತ್ತಿಗೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ ಮತ್ತು ದರ-ಮಿತಿ ರಕ್ಷಣೆಯ ಅಡಿಯಲ್ಲೇ ಉಳಿಯುತ್ತದೆ.
- **ಪ್ರತಿ-ಸಂಪರ್ಕದ ಹೊರಗುಳಿಯುವಿಕೆ ಇಲ್ಲ**: ಇತರ ಸಂಪರ್ಕಗಳಿಗೆ ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆಯನ್ನು ಚಾಲ್ತಿಯಲ್ಲಿಟ್ಟುಕೊಂಡೇ, "ಈ ಒಂದು ಸಕ್ರಿಯ API-key ಸಂಪರ್ಕವು ದರ-ಮಿತಿ ಕ್ಯೂ ರಕ್ಷಣೆಯಿಲ್ಲದೆ ಕಾರ್ಯನಿರ್ವಹಿಸಬೇಕು" ಎಂದು ಆಪರೇಟರ್ ಪ್ರಸ್ತುತ ಸೂಚಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. API-key ಸಂಪರ್ಕಗಳನ್ನು ದರ-ಮಿತಿ ಕ್ಯೂಗಳಿಲ್ಲದೆ ಸಂಪೂರ್ಣವಾಗಿ ಚಲಾಯಿಸಲು, ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆಯನ್ನು ಜಾಗತಿಕವಾಗಿ ಆಫ್ ಮಾಡಬೇಕು (`RATE_LIMIT_AUTO_ENABLE=false` ಅಥವಾ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`).

**ಬೆಂಬಲಿತ ಬರವಣಿಗೆ ಪಥಗಳು:**

- **`POST /api/rate-limits`**: ಸಂಪರ್ಕಕ್ಕಾಗಿ `rateLimitProtection` ಅನ್ನು ಟಾಗಲ್ ಮಾಡಲು ಬೆಂಬಲಿತ ನಿರ್ವಹಣಾ ಬರವಣಿಗೆ ಪಥ (`{ connectionId: string, enabled: boolean }`). ಇದನ್ನು `enabled: true` ಜೊತೆಗೆ ಕರೆ ಮಾಡುವುದರಿಂದ ಸ್ಪಷ್ಟ ರಕ್ಷಣೆ ಆನ್ ಆಗುತ್ತದೆ; `enabled: false` ಜೊತೆಗೆ ಕರೆ ಮಾಡುವುದರಿಂದ ಸ್ಪಷ್ಟ ರಕ್ಷಣೆ ತೆಗೆದುಹಾಕಲ್ಪಡುತ್ತದೆ (ಆದರೂ ಸ್ವಯಂ-ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಆನ್ ಆಗಿದ್ದರೆ, ಸಕ್ರಿಯ API-key ಸಂಪರ್ಕಗಳು ಜಾಗತಿಕ ಸುರಕ್ಷತಾ ವ್ಯವಸ್ಥೆಯ ಅಡಿಯಲ್ಲೇ ಉಳಿಯುತ್ತವೆ).
- **`PUT /api/providers/[id]`**: ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ `rateLimitProtection` ಅನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ ಅಥವಾ ಬದಲಿಸುವುದಿಲ್ಲ (#11278). `PUT /api/providers/[id]` ಮೂಲಕ ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕದ ಮೆಟಾಡೇಟಾವನ್ನು ನವೀಕರಿಸುವುದರಿಂದ ಉಳಿಸಲಾದ ದರ-ಮಿತಿ ರಕ್ಷಣೆಯ ಸ್ಥಿತಿ ಎಂದಿಗೂ ಬದಲಾಗುವುದಿಲ್ಲ.

## 6. ಸ್ಲೋ-ಸ್ಟ್ರೀಮ್ ಥ್ರೋಪುಟ್ ವಾಚ್ಡಾಗ್ (#9709)

ಐಚ್ಛಿಕ `resilienceSettings.streamRecovery.throughputWatchdog` ಸಿಬ್ಬಂದಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ಅನ್ನು ಪತ್ತೆ ಮಾಡುತ್ತದೆ, ಅದು ಇನ್ನೂ ಭಾಗಗಳನ್ನು ಕಳುಹಿಸುತ್ತಿದೆ ಆದರೆ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಉಪಯುಕ್ತ-ಔಟ್ಪುಟ್ ದರಕ್ಕಿಂತ ಕಡಿಮೆ ಸಹಾಯಕ ಔಟ್ಪುಟ್ ಅನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ. ಇದು ಐಡಲ್ ಟೈಮ್ಔಟ್ನಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಭಿನ್ನವಾಗಿದೆ: ಹೃದಯ ಬಡಿತಗಳು ಮತ್ತು ಮೆಟಾಡೇಟಾ ಟೈಮರ್ ಅನ್ನು ಮರುಹೊಂದಿಸುವುದಿಲ್ಲ ಮತ್ತು ಪ್ರಗತಿ ಎಂದು ಪರಿಗಣಿಸುವುದಿಲ್ಲ. ಇದು ಹಾರ್ಡ್ ಅಟೆಂಪ್ಟ್ ಡೆಡ್ಲೈನ್ನಿಂದ (#9153) ಭಿನ್ನವಾಗಿದೆ, ಇದು ಔಟ್ಪುಟ್ ಗುಣಮಟ್ಟವನ್ನು ಲೆಕ್ಕಿಸದೆ ಸಂಪೂರ್ಣ ಸುರಕ್ಷತಾ ಸೀಲಿಂಗ್ ಆಗಿ ಉಳಿದಿದೆ.

ವಾಚ್ಡಾಗ್ಗೆ ವಾರ್ಮ್-ಅಪ್ ಅವಧಿಯ ಅಗತ್ಯವಿರುತ್ತದೆ, ನಂತರ ಅದು ಸ್ಥಗಿತಗೊಳ್ಳುವ ಮೊದಲು ಸಂಪೂರ್ಣ ರೋಲಿಂಗ್ ವಿಂಡೋದ ಅಗತ್ಯವಿದೆ. ಇದು ಚಾಟ್ ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳು ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಗಳ API ಔಟ್ಪುಟ್ ಈವೆಂಟ್ಗಳಿಂದ ಪಠ್ಯ ಡೆಲ್ಟಾಗಳನ್ನು ಎಣಿಕೆ ಮಾಡುತ್ತದೆ (ಸಂಪ್ರದಾಯವಾದಿ UTF-8 ಬೈಟ್ ಪ್ರಾಕ್ಸಿ), ಬಳಕೆ-ಮಾತ್ರ ಮತ್ತು ಖಾಲಿ ಈವೆಂಟ್ಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸುತ್ತದೆ ಮತ್ತು ಟೂಲ್-ಕಾಲ್ ಅಥವಾ ತಾರ್ಕಿಕ ಘಟನೆಗಳು ಹಾರಾಟದಲ್ಲಿರುವಾಗ ತೀರ್ಪನ್ನು ಅಮಾನತುಗೊಳಿಸುತ್ತದೆ. ಇದನ್ನು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ ಮತ್ತು `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true` ನೊಂದಿಗೆ ಸಕ್ರಿಯಗೊಳಿಸಬಹುದು (ಆ env ಮೌಲ್ಯವು ಡೀಫಾಲ್ಟ್ — ಉಳಿಸಿದ `resilienceSettings.streamRecovery.throughputWatchdog.enabled` ಬೂಲಿಯನ್ ಗೆಲ್ಲುತ್ತದೆ; ಈ ಮಾರ್ಗದರ್ಶಿಯ ಮೇಲ್ಭಾಗದಲ್ಲಿರುವ env-vs-ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಆದ್ಯತೆಯ ಟಿಪ್ಪಣಿಯನ್ನು ನೋಡಿ); ವಿಂಡೋ, ವಾರ್ಮ್-ಅಪ್, ಕನಿಷ್ಠ ದರ ಮತ್ತು ಕನಿಷ್ಠ ಅಳೆಯಬಹುದಾದ ಔಟ್ಪುಟ್ ಅನ್ನು ಸಾಮಾನ್ಯ ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ-ಸೆಟ್ಟಿಂಗ್ಗಳ ಸಾಮಾನ್ಯೀಕರಣ ಪದರದಿಂದ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ.

ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಸಕ್ರಿಯ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರಯತ್ನಕ್ಕೆ ಮಾತ್ರ ವಾಚ್ಡಾಗ್ ಸ್ಥಗಿತವನ್ನು ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ. ಯಾವುದೇ ಕ್ಲೈಂಟ್-ಗೋಚರ ಬೈಟ್ಗಳ ಮೊದಲು, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅದೇ ಖಾತೆಯ ಆರಂಭಿಕ ಮರುಪಡೆಯುವಿಕೆ ಮಾರ್ಗವು ಪ್ರಯತ್ನವನ್ನು ಪುನಃ ತೆರೆಯಬಹುದು. ಬದ್ಧತೆಯ ನಂತರ, ಸ್ಟ್ರೀಮ್ ಅನ್ನು ಎಂದಿಗೂ ಕುರುಡಾಗಿ ಮರುಪ್ಲೇ ಮಾಡಲಾಗುವುದಿಲ್ಲ; ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸುರಕ್ಷಿತ ಮಧ್ಯ-ಸ್ಟ್ರೀಮ್ ಮುಂದುವರಿಕೆ ಒಪ್ಪಂದವು ಮಾತ್ರ ಪ್ರತ್ಯಯವನ್ನು ಹೊಲಿಯಬಹುದು. ಅಂತಿಮಗೊಳಿಸುವಿಕೆಯು ಏಕ-ಶಾಟ್ ಆಗಿ ಉಳಿದಿದೆ, ಆದ್ದರಿಂದ ಬಳಕೆಯ ಲೆಕ್ಕಪತ್ರ ನಿರ್ವಹಣೆ ಮತ್ತು ಸೆಮಾಫೋರ್ ಬಿಡುಗಡೆಯು ನಕಲು ಮಾಡಲಾಗಿಲ್ಲ.

## 7. ಅಪ್ಸ್ಟ್ರೀಮ್ ಸ್ಥಿತಿ ಮರುಹೇಳಿಕೆ (ತಪ್ಪಾಗಿ ಹೇಳಲಾದ ಕೋಟಾ ದೋಷಗಳು)

**ವ್ಯಾಪ್ತಿ:** ತಾತ್ಕಾಲಿಕ ಕೋಟಾ ಕೊರತೆಯನ್ನು ತಪ್ಪಾದ HTTP ಸ್ಥಿತಿಯೊಂದಿಗೆ ವರದಿ ಮಾಡುವ ಒಂದು ಅಪ್ಸ್ಟ್ರೀಮ್ ಗೇಟ್ವೇ.

**ಉದ್ದೇಶ:** ವರ್ಗೀಕರಣಕ್ಕೆ ಮೊದಲು ದಾರಿತಪ್ಪಿಸುವ ಸ್ಥಿತಿಯನ್ನು ಸರಿಪಡಿಸುವುದು, ಇದರಿಂದ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಬಳಸುವವರು (ಫಾಲ್ಬ್ಯಾಕ್ ಎಂಜಿನ್, ಕಾಂಬೊ ಸಂಗ್ರಹಣೆ, ಕ್ಲೈಂಟ್-ಎದುರಿನ ಪ್ರತಿಕ್ರಿಯೆ) ವೈಫಲ್ಯದ ನಿಜವಾದ ಮರುಪ್ರಯತ್ನ-ಯೋಗ್ಯ ಸ್ವಭಾವವನ್ನು ನೋಡುತ್ತಾರೆ.

ಕೆಲವು ಗೇಟ್ವೇಗಳು ಮರುಪ್ರಯತ್ನ-ಯೋಗ್ಯವಲ್ಲದ HTTP ಸ್ಥಿತಿಯೊಂದಿಗೆ ತಾತ್ಕಾಲಿಕ ಕೋಟಾ
ಕೊರತೆಯನ್ನು ಸೂಚಿಸುತ್ತವೆ. `agentrouter.org` ಪ್ರಮಾಣಿತ `429` ಬದಲಿಗೆ ಚೈನೀಸ್
ಬಾಡಿಯೊಂದಿಗೆ (`用户额度不足` / `额度不足`) `403` (ಕೆಲವೊಮ್ಮೆ `400`) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
Claude Code ನಂತಹ ಕ್ಲೈಂಟ್ಗಳು `403` ಅನ್ನು ಶಾಶ್ವತವೆಂದು ಪರಿಗಣಿಸಿ ಸೆಷನ್ ಅನ್ನು
ರದ್ದುಗೊಳಿಸುತ್ತವೆ, ಮತ್ತು ಸರಿಪಡಿಸದಿದ್ದರೆ ಫಾಲ್ಬ್ಯಾಕ್ ಎಂಜಿನ್ ಅದನ್ನು ಕೋಟಾ ಘಟನೆಯ
ಬದಲಿಗೆ `AUTH_ERROR` ಎಂದು ವರ್ಗೀಕರಿಸುತ್ತದೆ.

**ಅನುಷ್ಠಾನ:**

- ರಿಜಿಸ್ಟ್ರಿ + ಹೊಂದಾಣಿಕೆಕಾರ: `open-sse/config/upstreamStatusRestatement.ts` — ಪ್ರತಿ-ಪ್ರೊವೈಡರ್
  ನಿಯಮಗಳ ಪಟ್ಟಿ (`{id, fromStatuses, toStatus, textMarkers,
excludeMarkers, defaultRetryAfterMs}`), `applyStatusRestatement()` ಮೂಲಕ
  ಹೊಂದಾಣಿಕೆಯಾಗುತ್ತದೆ.
- ಕರೆ ಸ್ಥಳ: `open-sse/handlers/chatCore.ts` ನಲ್ಲಿನ `providerFailure:` ಬ್ಲಾಕ್
  (ಸುಮಾರು ಸಾಲು 3654), `parseUpstreamError()` ದೋಷ HTTP ಸ್ಥಿತಿಯುಳ್ಳ ಅಪ್ಸ್ಟ್ರೀಮ್
  ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು (`!providerResponse.ok`) ಪಾರ್ಸ್ ಮಾಡಿದ ಒಡನೆ, ಮತ್ತು ಯಾವುದೇ
  ವರ್ಗೀಕರಣ ನಡೆಯುವ ಮೊದಲು, ಇದರಿಂದ ಪ್ರತಿ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಬಳಸುವವರು ಸರಿಪಡಿಸಿದ
  ಸ್ಥಿತಿಯನ್ನು ನೋಡುತ್ತಾರೆ. `200` SSE ಸ್ಟ್ರೀಮ್ನ ಒಳಗೆ ಬಿಂಬಿತವಾದ ದೋಷಗಳು ಪ್ರತ್ಯೇಕ,
  ನಂತರದ ಸ್ಟ್ರೀಮ್-ಪಾರ್ಸಿಂಗ್ ಮಾರ್ಗವನ್ನು ಅನುಸರಿಸುತ್ತವೆ ಮತ್ತು ಇಂದು ಈ ಹುಕ್ನಿಂದ
  ಒಳಗೊಂಡಿಲ್ಲ — ತಿಳಿದಿರುವ ಮಿತಿ, agentrouter ನ ತಪ್ಪು-ಸ್ಥಿತಿಗೆ ಇನ್ನೂ ಅಗತ್ಯವಿಲ್ಲ
  (ಅದು ದೋಷ HTTP ಸ್ಥಿತಿಯಾಗಿ ಹೊರಬರುತ್ತದೆ).
- ಮರುಪ್ರಯತ್ನ ಅರ್ಹತೆ: `429` `RETRY_AFTER_ELIGIBLE_STATUSES` ನಲ್ಲಿದೆ
  (`open-sse/services/combo/unavailableRetryGate.ts`), ಆದ್ದರಿಂದ ಮರುಹೇಳಿದ ದೋಷವು
  ಸತ್ತ `403` ಆಗಿ ಹೊರಬರದೇ ನಿಜವಾದ ಮರುಪ್ರಯತ್ನ ಕಿಟಕಿಯನ್ನು ಹೊಂದಿರುತ್ತದೆ.
- ಸಿಂಥೆಟಿಕ್ `60s` `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`) ಎನ್ನುವುದು
  ಮರುಹೇಳಿದ ಪ್ರತಿಕ್ರಿಯೆ **ಕ್ಲೈಂಟ್**ಗೆ ಹೇಳುವುದಷ್ಟೇ; ಅದು ಸ್ವತಃ ಸಂಪರ್ಕದ ಆಂತರಿಕ
  ಕೂಲ್ಡೌನ್/ಲಾಕ್ಔಟ್ ಅವಧಿಯಲ್ಲ — ಅದನ್ನು ಮರುಹೇಳಿದ ದೋಷವನ್ನು ನಿಜವಾಗಿ ನಿಭಾಯಿಸುವ
  ಯಾವ ಯಂತ್ರಾಂಶವೋ ಅದು ಪ್ರತ್ಯೇಕವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ (Connection Cooldown ನ
  ಏರುತ್ತಿರುವ ಬ್ಯಾಕ್ಆಫ್, §2, API-ಕೀ ಪ್ರೊವೈಡರ್ಗಳಿಗೆ ಬೇಸ್ `3s`; ಅಥವಾ
  Model Lockout, §3, agentrouter ನಂತಹ ಪ್ರತಿ-ಮಾದರಿ-ಕೋಟಾ ಪ್ರೊವೈಡರ್ಗಳಿಗೆ).
  ಕ್ಲೈಂಟ್ಗೆ ಅದು ಪ್ರಕಟಿಸುವ 60s ಕಿಟಕಿಗಿಂತ ಮೊದಲು ರೂಟರ್ ಆಂತರಿಕವಾಗಿ
  ಮರುಪ್ರಯತ್ನಿಸಲು ಅರ್ಹವಾಗಬಹುದು — ಉದ್ದೇಶಪೂರ್ವಕ ಹೆಡ್ರೂಮ್, ಬಗ್ ಅಲ್ಲ.

ಶಾಶ್ವತ ದೋಷಗಳನ್ನು (agentrouter ನ `无权访问模型` — ಈ ಮಾದರಿಗೆ ಪ್ರವೇಶವಿಲ್ಲ) ಎಂದಿಗೂ
ಮರುಹೇಳಲಾಗುವುದಿಲ್ಲ: `textMarkers` ಹೊಳೆದರೂ `excludeMarkers` ನಿಯಮವನ್ನು ವಿಟೋ
ಮಾಡುತ್ತದೆ, ಆದ್ದರಿಂದ ದೋಷವು ತನ್ನ ಮೂಲ ಸ್ಥಿತಿಯನ್ನು ಇರಿಸಿಕೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಏನೂ
ಅದನ್ನು ಶಾಶ್ವತವಾಗಿ ಮರುಪ್ರಯತ್ನಿಸುವುದಿಲ್ಲ. ಹೊಂದಾಣಿಕೆಯಾದ ಪ್ರೊವೈಡರ್ ವರ್ಗೀಕರಣ ನಿಯಮವನ್ನು
(`open-sse/config/providerErrorRules.ts` ನಲ್ಲಿನ `agentrouter-model-access-denied`:
`reason: "auth_error"`, `scope: "model"`, `6h` ಘೋಷಿತ ಬೇಸ್ ಕೂಲ್ಡೌನ್)
`checkFallbackError` (`open-sse/services/accountFallback.ts`) ಸಾಮಾನ್ಯ
apikey-ವರ್ಗದ `FORBIDDEN` ಎರ್ಲಿ-ರಿಟರ್ನ್ಗೆ _ಮೊದಲು_ ಸಂಪರ್ಕಿಸುತ್ತದೆ,
`honorsRuleLockScope(provider)` ಮೇಲೆ ಗೇಟ್ ಮಾಡಲಾಗಿದೆ (#10334 — ಪ್ರಸ್ತುತ
`providerErrorRules.ts` ನಲ್ಲಿನ `HONORS_RULE_LOCK_SCOPE_PROVIDERS` ಅನುಮತಿ-ಪಟ್ಟಿಯ
ಮೂಲಕ agentrouter-ಏಕಸ್ವಾಮ್ಯ). ನಿಯಮದ ಘೋಷಿತ 6h ಕೂಲ್ಡೌನ್ `fallbackResult.baseCooldownMs`
ಆಗಿ ಹರಿದುಹೋಗುತ್ತದೆ, ಆದರೆ ಅದು ಇನ್ನೂ ಹಿಂದೆ-ಇದ್ದ ಪ್ರತಿ-ಮಾದರಿ-ಕೋಟಾ ಲಾಕ್ಔಟ್ ಮಾರ್ಗವನ್ನೇ
ತುಂಬಿಸುತ್ತದೆ (`lockModelIfPerModelQuota()` / `recordModelLockoutFailure()`, ಕೂಲ್ಡೌನ್
ಮೂಲವನ್ನು ಹೊರತುಪಡಿಸಿ #10334 ರಿಂದ ಬದಲಾಗಿಲ್ಲ): ಇತರ ಎಲ್ಲಾ ಮಾದರಿ ಲಾಕ್ಔಟ್ಗಳಂತೆ ಅದು
ಆಪರೇಟರ್ನ `mlSettings.maxCooldownMs` ಗೆ (ಡೀಫಾಲ್ಟ್ `1_800_000ms` / 30min)
ಕುಗ್ಗಿಸಲ್ಪಡುತ್ತದೆ, ಮತ್ತು _ಕಾಯ್ದಿರಿಸಿದ ಲಾಕ್ಔಟ್ ಕಾರಣ_ ಹಿಂದೆ-ಇದ್ದ ಹಾರ್ಡ್ಕೋಡ್ ಮಾಡಿದ
`"forbidden"` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ, ನಿಯಮದ `"auth_error"` ಅಲ್ಲ — ಕೂಲ್ಡೌನ್ ಅವಧಿಯನ್ನು
ಮಾತ್ರ ಎಂಡ್-ಟು-ಎಂಡ್ ಗೌರವಿಸಲಾಗುತ್ತದೆ, ಕಾರಣ ಸ್ಟ್ರಿಂಗ್ ಅಲ್ಲ. ಸಂಪರ್ಕವೇ ಸಕ್ರಿಯವಾಗಿ
ಉಳಿಯುತ್ತದೆ; ಅದೇ ಸಂಪರ್ಕದ ಸಹೋದರ ಮಾದರಿಗಳಿಗೆ ಪರಿಣಾಮವಾಗುವುದಿಲ್ಲ.

ಮರುಹೇಳಿದ ಕೋಟಾ ದೋಷಗಳು (`额度不足`) ಪ್ರೊಡಕ್ಷನ್ನಲ್ಲಿ ಪ್ರೊವೈಡರ್ ನಿಯಮವನ್ನು ತಲುಪುತ್ತವೆ
(`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`, `scope:
"connection"`, ತನ್ನದೇ ಘೋಷಿತ ಕೂಲ್ಡೌನ್ ಇಲ್ಲ — ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಲೇಯರ್ನ ಸ್ಕೇಲ್ಡ್
ಬ್ಯಾಕ್ಆಫ್ ಡೀಫಾಲ್ಟ್ ಅನ್ವಯಿಸುತ್ತದೆ). #10334 ರಿಂದ, `ProviderErrorRuleMatch` ನ ಮೇಲಿನ
`scope` ಎಂಡ್-ಟು-ಎಂಡ್ ಬಳಸಲ್ಪಡುತ್ತದೆ, ಆದರೆ `HONORS_RULE_LOCK_SCOPE_PROVIDERS`
ಅನುಮತಿ-ಪಟ್ಟಿಯಲ್ಲಿರುವ ಪ್ರೊವೈಡರ್ಗಳಿಗೆ **ಮಾತ್ರ** (`providerErrorRules.ts` — ಇಂದು ಕೇವಲ
`"agentrouter"`, `honorsRuleLockScope()` ಮೂಲಕ ಗೇಟ್ ಮಾಡಲಾಗಿದೆ). ಪ್ರತಿಯೊಂದು ಇತರ
ಪ್ರೊವೈಡರ್ಗೆ `scope` ಮಾಹಿತಿ-ಮಾತ್ರವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ, #10334 ರ ಮೊದಲಿನಂತೆಯೇ.
`checkFallbackError` ಹೊಂದಾಣಿಕೆಯಾದ ನಿಯಮದ scope ಅನ್ನು `fallbackResult.ruleScope`
ಆಗಿ ಹೊರತರುತ್ತದೆ; `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) ಒಂದು `ruleScope` ಅನ್ನು ಸಂಪರ್ಕ-ವ್ಯಾಪ್ತಿಯ,
ಸ್ವಯಂ-ಚೇತರಿಸಿಕೊಳ್ಳುವ ಸಂಕೇತವಾಗಿ ಗೌರವಿಸಲು ನಿಜವಾಗಿಯೂ ಸುರಕ್ಷಿತವೆಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳುವ
ಹಂಚಿಕೆ ಗಾರ್ಡ್ ಆಗಿದೆ (scope `"connection"`, ಕಾರಣ `quota_exhausted`, ಎಂದಿಗೂ
`permanent` ಅಲ್ಲ, ಎಂದಿಗೂ `creditsExhausted` ಅಲ್ಲ — scope `"connection"` ಅನ್ನು
ಶಾಶ್ವತ ಖಾತೆ ಸ್ಥಿತಿಯೊಂದಿಗೆ ಜೋಡಿಸುವ ಭವಿಷ್ಯದ ನಿಯಮದ ವಿರುದ್ಧದ ರಕ್ಷಣೆ). ಎರಡು ಬಳಸುವವರು
ಅದನ್ನು ಕರೆಯುತ್ತಾರೆ:

- **ಸ್ಥಿರತೆ** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  ಪಾಸ್ಥ್ರೂ-ಪ್ರೊವೈಡರ್ನ **ಪ್ರತಿ-ಮಾದರಿ** ಲಾಕ್ಔಟ್
  ಶಾಖೆಗೆ ಹೋಗುವ ಬದಲು (agentrouter ಎಂಬುದು `passthroughModels: true` → `hasPerModelQuota()`
  `true` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ), ಇದು **ತಾತ್ಕಾಲಿಕ ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್** ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ —
  `testStatus: "unavailable"` + `rateLimitedUntil`, ಎಂದಿಗೂ ಅಂತಿಮ ಸ್ಥಿತಿಯನ್ನು
  (`credits_exhausted`/`banned`/`expired`) ಅನ್ವಯಿಸುವುದಿಲ್ಲ — ಆದ್ದರಿಂದ ಕೂಲ್ಡೌನ್
  ಅವಧಿ ಮುಗಿದ ಬಳಿಕ, ಕೈಯಾರೆ ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಮರುಹೊಂದಿಸುವ ಅಗತ್ಯವಿಲ್ಲದೆ ಸಂಪರ್ಕವು
  ಸ್ವತಃ ಚೇತರಿಸಿಕೊಳ್ಳುತ್ತದೆ. `disableCooling: true` ಹೊಂದಿರುವ ಸಂಪರ್ಕಗಳಿಗೆ
  ಇದನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ (#2997): ಬದಲಿಗೆ ಆ ಆಯ್ಕೆಯಿಂದ ಹೊರಗುಳಿಯುವಿಕೆಯು
  ಪ್ರತಿ-ಮಾದರಿ ಲಾಕ್ಔಟ್ಗೆ ಹೋಗುತ್ತದೆ (ದಾಖಲೀಕರಿಸಲಾದ ರಾಜಿ —
  ಶಾಖೆಯ ಮೇಲಿರುವ ಕೋಡ್ ಕಾಮೆಂಟ್ ನೋಡಿ).
- **ಅದೇ-ವಿನಂತಿಯ ಕಾಂಬೊ ರೂಟಿಂಗ್** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): ಅದೇ ಗಾರ್ಡ್ ಸಂಪರ್ಕವನ್ನು
  `${provider}:${connectionId}` ಕೀಲಿಯಿಂದ ಗುರುತಿಸಲಾದ, ಮೆಮೊರಿಯಲ್ಲಿರುವ
  `exhaustedConnections` ಸೆಟ್ನಲ್ಲಿ ಗುರುತಿಸುತ್ತದೆ. ಇದು ಉಳಿದಿರುವ ಅದೇ-ವಿನಂತಿಯ
  ಗುರಿಯನ್ನು, ಆ ಗುರಿಯ ಸ್ವಂತ ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ _ಅದೇ ನಿಖರವಾದ `connectionId` ಅನ್ನು
  ಈಗಾಗಲೇ ಹೊಂದಿದ್ದರೆ ಮಾತ್ರ_ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` ಎಂಬುದು `exhaustedConnections` ಲುಕ್ಅಪ್ಗಿಂತ ಮೊದಲು) — ಸಹೋದರ
  ಗುರಿಗಳು ತಮ್ಮದೇ ಪಿನ್ ಮಾಡಿದ `connectionId` ಅನ್ನು ಹೊಂದಿರದ ಮತ್ತು ಪ್ರತಿಯೊಂದು
  ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಒಂದನ್ನು ಪ್ರತಿಕ್ರಿಯೆಯ `X-OmniRoute-Selected-Connection-Id`
  ಹೆಡರ್ನಿಂದ ಮಾತ್ರ ಪರಿಹರಿಸುವ ಸರಳ ಮಾದರಿ-ಪಟ್ಟಿ ಕಾಂಬೊ ಎಂದಿಗೂ ಆ ಕೀ ಹೊಂದಾಣಿಕೆಯನ್ನು
  ತಲುಪುವುದಿಲ್ಲ. ಆ ಸಾಮಾನ್ಯ ಸಂದರ್ಭದಲ್ಲಿ, ಉಳಿದಿರುವ ಲೆಗ್ ಇದೀಗ ಖಾಲಿಯಾದ ಖಾತೆಯನ್ನು
  ಮರುಬಳಸದಂತೆ ಮಾಡುವ ನಿಜವಾದ ರಕ್ಷಣೆ ಈ ಸೆಟ್ ಅಲ್ಲ — ಅದು ಮೇಲಿನ ಸ್ಥಿರತೆ ಪದರ
  (ಸಂಪರ್ಕದ `rateLimitedUntil` ಈಗ ಭವಿಷ್ಯದಲ್ಲಿದೆ) ಮತ್ತು ಇದೇ ಗಾರ್ಡ್ ವೈಫಲ್ಯಕ್ಕಾಗಿ
  `transientRateLimitedProviders` ಅನ್ನು ನಿಗ್ರಹಿಸುವುದರ ಸಂಯೋಜನೆಯಾಗಿದೆ
  ("ಎರಡು-ಹಂತದ ವಿನ್ಯಾಸ" ಮತ್ತು `targetExhaustion.ts` ನಲ್ಲಿನ
  `isAgentrouterConnectionQuotaScope` ಶಾಖೆಯ ಕೋಡ್ ಕಾಮೆಂಟ್ ನೋಡಿ): ಆ ಸೆಟ್ ಅನ್ನು
  ಗುರುತಿಸದೆ ಬಿಟ್ಟಿರುವುದರಿಂದ, `combo.ts` ನ `allowRateLimitedConnection`
  ಬಲವಂತದ-ಅನುಮತಿ (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`)
  ಪ್ರೊವೈಡರ್ನ ಉಳಿದ ಲೆಗ್ಗಳಿಗೆ ಸಕ್ರಿಯವಾಗುವುದಿಲ್ಲ; ಆದ್ದರಿಂದ ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಆಯ್ಕೆಯ
  `rateLimitedUntil` ಫಿಲ್ಟರ್ (`src/sse/services/auth.ts:1238`) ಅನ್ನು
  ಸಾಮಾನ್ಯವಾಗಿ ಗೌರವಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಉಳಿದ ಲೆಗ್ ಬೇರೆ, ಇನ್ನೂ ಅರ್ಹವಾಗಿರುವ
  agentrouter ಸಂಪರ್ಕವನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ ಅಥವಾ ಲಭ್ಯವಿರುವ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳಿಲ್ಲದೆ
  ವಿಫಲವಾಗುತ್ತದೆ — ಈ ಶಾಖೆ ಇದೀಗ ಕೂಲ್ಡೌನ್ಗೆ ಒಳಪಡಿಸಿದ ಸಂಪರ್ಕಕ್ಕೆ ಅದು ಬಲವಂತವಾಗಿ
  ಮರಳುವುದಿಲ್ಲ.

### ಎರಡು-ಹಂತದ ವಿನ್ಯಾಸ: ಸ್ಥಿತಿಯ ಮರುನಿರೂಪಣೆ, ನಂತರ ವರ್ಗೀಕರಣ

ಸ್ಥಿತಿಯ ಮರುನಿರೂಪಣೆ (`upstreamStatusRestatement.ts`) ಮತ್ತು ಪ್ರೊವೈಡರ್
ವರ್ಗೀಕರಣ ನಿಯಮಗಳು (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) ಎರಡೂ ಪ್ರೊವೈಡರ್ ಐಡಿ ಮತ್ತು ಪಠ್ಯ ಗುರುತುಗಳನ್ನು ಕೀಲಿಗಳಾಗಿ
ಬಳಸುವ ಪ್ರತ್ಯೇಕ ರಿಜಿಸ್ಟ್ರಿಗಳಾಗಿವೆ, ಆದರೆ ಅವು ವಿಭಿನ್ನ ಸ್ಥಳಗಳಲ್ಲಿ ಚಲಿಸುತ್ತವೆ ಮತ್ತು
ವಿಭಿನ್ನ ಉದ್ದೇಶಗಳನ್ನು ಪೂರೈಸುತ್ತವೆ: ಮರುನಿರೂಪಣೆಯು `chatCore.ts` ನಲ್ಲಿ HTTP
ಸ್ಥಿತಿಯನ್ನು ಆರಂಭದಲ್ಲೇ ಮರುಬರೆಯುತ್ತದೆ; ವರ್ಗೀಕರಣ ನಿಯಮಗಳು `checkFallbackError()`
(`open-sse/services/accountFallback.ts`) ಒಳಗೆ ಫಾಲ್ಬ್ಯಾಕ್ `reason` ಮತ್ತು ಲಾಕ್
`scope` (`model` / `provider` / `connection`) ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತವೆ.

ವರ್ಗೀಕರಣ ನಿಯಮಗಳು `providerErrorRules.ts` ನಲ್ಲಿನ `FULL_TEXT_RULE_PROVIDERS`
ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿ ಸೇರಿಸಲಾದ ಪ್ರೊವೈಡರ್ಗಳಿಗೆ ಮಾತ್ರ ಸಂಪೂರ್ಣ ದೋಷ **ಪಠ್ಯ**ವನ್ನು
ನೋಡುತ್ತವೆ (`额度不足` ನಂತಹ ಬಾಡಿ ಗುರುತುಗಳನ್ನು ಹೊಂದಿಸಲು ಇದು ಅಗತ್ಯ) — ಪ್ರಸ್ತುತ
ಕೇವಲ `"agentrouter"`. ಇತರ ಪ್ರತಿಯೊಂದು **ಅಂತರ್ನಿರ್ಮಿತ ಕ್ಯಾಟಲಾಗ್**
ಪ್ರೊವೈಡರ್ಗಾಗಿ, `checkFallbackError` ಎಂಬುದು `getProviderErrorRuleMatch` ಗೆ
ರಚನಾತ್ಮಕ ದೋಷವನ್ನು (`{code, type}`) ಮಾತ್ರ ನೀಡುತ್ತದೆ; ಇದು ಹೆಡರ್/ಸ್ಥಿತಿ/ಕೋಡ್
ಆಧಾರಿತ ನಿಯಮಗಳಿಗೆ ಸಾಕಾಗುತ್ತದೆ, ಆದರೆ ಬಾಡಿ-ಪಠ್ಯದ ಗುರುತುಗಳನ್ನು ಕಾಣುವುದಿಲ್ಲ.
`resolveRuleMatchBody()` ಸಹಾಯಕವು ಈ ಆಯ್ಕೆಯನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ: ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿರುವ
ಪ್ರೊವೈಡರ್ಗಳಿಗೆ ಸಂಪೂರ್ಣ ದೋಷ ಪಠ್ಯ, ಇಲ್ಲದಿದ್ದರೆ ರಚನಾತ್ಮಕ ದೋಷ. ಒಂದು
**ಅಂತರ್ನಿರ್ಮಿತ** ಪ್ರೊವೈಡರ್ ಅನ್ನು `FULL_TEXT_RULE_PROVIDERS` ಗೆ ಸೇರಿಸುವುದು
ಸ್ಪಷ್ಟವಾದ ಪ್ರತಿ-ಪ್ರೊವೈಡರ್ ಆಯ್ಕೆಯಾಗಿದೆ — ಪಟ್ಟಿಯಲ್ಲಿಲ್ಲದ ಪ್ರತಿಯೊಂದು
ಪ್ರೊವೈಡರ್ನ ಡೀಫಾಲ್ಟ್ ಮಾರ್ಗವು ಬೈಟ್ಗೆ-ಬೈಟ್ ಬದಲಾಗದಂತೆ ಉಳಿಯಲು ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ.

ನಿಯಮದ `scope` (`model` / `provider` / `connection`) ಎಂಬುದು
`FULL_TEXT_RULE_PROVIDERS` ಗಿಂತ ಪ್ರತ್ಯೇಕವಾದ ಆಯ್ಕೆಯಾಗಿದೆ:
`checkFallbackError` ಅದನ್ನು `fallbackResult.ruleScope` ಆಗಿ ಮಾತ್ರ ಹೊರತರುತ್ತದೆ;
ಅದೇ ಫೈಲ್ನಲ್ಲಿರುವ `HONORS_RULE_LOCK_SCOPE_PROVIDERS` ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿರುವ
ಪ್ರೊವೈಡರ್ಗಳಿಗೆ ಮಾತ್ರ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಬಳಕೆದಾರರು ಅದನ್ನು ಮಾಹಿತಿಪೂರ್ಣ ಲೇಬಲ್ಗಿಂತ
ಹೆಚ್ಚಾಗಿ ಗೌರವಿಸುತ್ತಾರೆ (`honorsRuleLockScope()` ಮೂಲಕ ನಿಯಂತ್ರಿಸಲಾಗಿದೆ —
ಇಂದು ಕೇವಲ `"agentrouter"`). ಪ್ರೊವೈಡರ್ ಆ ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿ ಸೇರಿದ ಬಳಿಕ
`scope: "connection"` ಹೊಂದಾಣಿಕೆ ವಾಸ್ತವವಾಗಿ ಏನು ಮಾಡುತ್ತದೆ ಎಂಬುದಕ್ಕಾಗಿ ಮೇಲಿನ
"ಮರುನಿರೂಪಿಸಲಾದ ಕೋಟಾ ದೋಷಗಳು" ನೋಡಿ.

**#11104 — ಆಪರೇಟರ್ ಘೋಷಿಸಿದ ನಿಯಮಗಳು ಎರಡೂ ಅನುಮತಿಪಟ್ಟಿಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತವೆ.**
ಆಪರೇಟರ್ ಈ ಫೈಲ್ ಅನ್ನು ಸಂಪಾದಿಸದೆಯೇ ರನ್ಟೈಮ್ನಲ್ಲಿ
`settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`)
ಮೂಲಕ ಪ್ರತಿ-ಪ್ರೊವೈಡರ್ ನಿಯಮವನ್ನು ಘೋಷಿಸಬಹುದು. ಅಂತರ್ನಿರ್ಮಿತ ಕ್ಯಾಟಲಾಗ್ ನಿಯಮಗಳ
**ಡೀಫಾಲ್ಟ್** ನಡವಳಿಕೆಯನ್ನು ರಕ್ಷಿಸಲು ಉದ್ದೇಶಿಸಲಾದ
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` ಅನುಮತಿಪಟ್ಟಿಗಳ
ಹಿಂದೆ ಆಪರೇಟರ್ ನಿಯಮವನ್ನು ನಿಯಂತ್ರಿಸಿದರೆ, ಈಗಾಗಲೇ ಅಲ್ಲಿ ಪಟ್ಟಿಮಾಡಿರುವ
ಪ್ರೊವೈಡರ್ಗಳನ್ನು ಹೊರತುಪಡಿಸಿ ಉಳಿದ ಪ್ರತಿಯೊಂದು ಪ್ರೊವೈಡರ್ಗೆ ಸೆಟ್ಟಿಂಗ್ಗಳ
ಕಾರ್ಯವಿಧಾನವು ನಿಷ್ಕ್ರಿಯವಾಗುತ್ತದೆ; ಏಕೆಂದರೆ ನಿಯಮವನ್ನು ಘೋಷಿಸುವುದೇ ಆಪರೇಟರ್ನ
ಸ್ಪಷ್ಟ ಆಯ್ಕೆಯಾಗಿದೆ. `resolveRuleMatchBody()` ಮತ್ತು `honorsRuleLockScope()`
ಎರಡೂ ಮೊದಲು `hasOperatorRuleForProvider()` ಅನ್ನು ಪರಿಶೀಲಿಸುತ್ತವೆ: ಆಪರೇಟರ್

ಎಂಬುದನ್ನು ಲೆಕ್ಕಿಸದೆ, ಕಚ್ಚಾ ದೋಷ ಪಠ್ಯವನ್ನು ಪಡೆಯುತ್ತದೆ ಮತ್ತು ಅದರ ಘೋಷಿತ `scope`

ಸಂಕೇತಕ್ಕೆ ಸಮನಾದ ಸಂಕೇತ. ಪ್ರಾಮಾಣಿಕ ಮಿತಿಗಳು:

- **ಬೆಸ್ಟ್-ಎಫರ್ಟ್**: ಲಾಕ್ ಕನೆಕ್ಷನ್ನ ಕೊನೆಯ ತಿಳಿದ `egress_ip` ಅನ್ನು
  `proxy_logs` ನಿಂದ ರಿಸಾಲ್ವ್ ಮಾಡುತ್ತದೆ (24h ವಿಂಡೋ, ಸಿಂಕ್ರೊನಸ್, ಕ್ಯಾಶೆ
  ಇಲ್ಲ). ಕೋಲ್ಡ್ ಕ್ಯಾಶೆ (egress IP ಅನ್ನು ಎಂದಿಗೂ ಪ್ರೋಬ್ ಮಾಡಲಾಗಿಲ್ಲ) ಅಥವಾ
  ರೋವೇ ಇಲ್ಲ → ವಿಫಲ ಕನೆಕ್ಷನ್ ಅನ್ನು ಬ್ರಾಂಚ್ ಇನ್ನೂ ಕೂಲ್ ಮಾಡುತ್ತದೆ (ಇಂದಿನಂತೆಯೇ
  ದಾಖಲಿಸಲಾಗುತ್ತದೆ), ಕೇವಲ ಯಾವುದೇ ಸಿಬ್ಲಿಂಗ್ ಲಾಕ್ ಆಗುವುದಿಲ್ಲ.
- **ಎಂದಿಗೂ ಟರ್ಮಿನಲ್ ಅಲ್ಲ**: ಕೂಲ್ಡೌನ್ ಎಂಬುದು ರಿನ್ಯೂ ಆಗುವ ಕೋಟಾ ವಿಂಡೋ
  (`testStatus: "unavailable"`); IP-ಮಟ್ಟದ ಸಿಗ್ನಲ್ನಿಂದ ಶಾಶ್ವತ ಸ್ಥಿತಿಯನ್ನು
  ಎಂದಿಗೂ ತರಲಾಗುವುದಿಲ್ಲ. `disableCooling` ಕನೆಕ್ಷನ್ಗಳು ಬ್ರಾಂಚ್ ಅನ್ನು
  ಸಂಪೂರ್ಣವಾಗಿ ಸ್ಕಿಪ್ ಮಾಡುತ್ತವೆ.
- **ಅಲೋಲಿಸ್ಟ್ ಮಾಡಲಾದ ಫ್ಯಾಮಿಲಿಗೆ ಲಾಕ್ ಗ್ರ್ಯಾನುಲಾರಿಟಿ ಬದಲಾಗುತ್ತದೆ**: ಇದು
  ಸ್ಕೋಪ್ ಬದಲಾವಣೆ, ಕೇವಲ ಸಿಬ್ಲಿಂಗ್ ಆಪ್ಟಿಮೈಸೇಶನ್ ಅಲ್ಲ. opencode ಒಂದು
  `passthroughModels` ಪ್ರೊವೈಡರ್ ಆಗಿರುವುದರಿಂದ, ಈ ಬ್ರಾಂಚ್ಗೆ ಮೊದಲು 429
  ಪ್ರತಿ-MODEL ಲಾಕ್ಔಟ್ ಅನ್ನು ಉಂಟುಮಾಡುತ್ತಿತ್ತು; ಈಗ ಅದು ಕನೆಕ್ಷನ್ ಕೂಲ್ಡೌನ್
  ಅನ್ನು ಉಂಟುಮಾಡುತ್ತದೆ — ಯಾವುದೇ ಸಿಬ್ಲಿಂಗ್ ಇಲ್ಲದೆ ಏಕೈಕ ಕನೆಕ್ಷನ್ ಅನ್ನು ರನ್
  ಮಾಡುವ ಆಪರೇಟರ್ಗೂ ಸಹ. opencode ರೂಲ್ ಟೇಬಲ್ ಈಗಾಗಲೇ ಸರಿಯೆಂದು ಘೋಷಿಸಿರುವ
  ಗ್ರ್ಯಾನುಲಾರಿಟಿ ಅದೇ (`scope: "connection"`, `providerErrorRules.ts`),
  opencode `HONORS_RULE_LOCK_SCOPE_PROVIDERS` ನಲ್ಲಿ ಇಲ್ಲದ ಕಾರಣ ಇಲ್ಲಿಯವರೆಗೆ
  ಎಂದಿಗೂ ಅನುಸರಿಸಲಾಗಿಲ್ಲ. ಬ್ರಾಂಚ್ ವಿಫಲ ಕನೆಕ್ಷನ್ನ ಕೂಲ್ಡೌನ್ + `backoffLevel`
  ಅನ್ನು ಸ್ವತಃ ಬರೆಯುತ್ತದೆ, ಕನೆಕ್ಷನ್-ಸ್ಕೋಪ್ಡ್ agentrouter ಬ್ರಾಂಚ್ ಅನ್ನು
  ಮಿರರ್ ಮಾಡುತ್ತದೆ, ಮತ್ತು ರಿಟರ್ನ್ ಮಾಡುತ್ತದೆ — ಪ್ರತಿ-ಮಾಡೆಲ್ ಬ್ಲಾಕ್ ಮತ್ತು
  ಕೆಳಗಿನ ಜೆನೆರಿಕ್ ಪಾತ್ ಅನ್ನು ಎಂದಿಗೂ ತಲುಪಲಾಗುವುದಿಲ್ಲ.
- **ಕಾಂಬೊ ಸೇರಿದೆ**: agentrouter ಬ್ರಾಂಚ್ನಂತೆ, ಈ ಸ್ಕೋಪ್ ಕಾಂಬೊ ಕಾಲರ್ 429 ಗೆ
  ಅನ್ವಯಿಸುವ `persistUnavailableState`/`isCombo` ಡೌನ್ಗ್ರೇಡ್ ಅನ್ನು
  ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ನಿರ್ಲಕ್ಷಿಸುತ್ತದೆ. ಪ್ರತಿ-ಮಾಡೆಲ್ ಲಾಕ್ಔಟ್ ಈ ಸ್ಕೋಪ್ನ
  ದುರ್ಬಲ ರೂಪವಲ್ಲ, ಅದು ತಪ್ಪು ಯೂನಿಟ್: ಅದು ಎಕ್ಸಾಸ್ಟ್ ಆದ IP ಬಗ್ಗೆ ಏನನ್ನೂ
  ಹೇಳುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಕಾಂಬೊ ರೊಟೇಶನ್ ಪ್ರತಿ ಸಿಬ್ಲಿಂಗ್ಗೆ ಖಚಿತವಾಗಿ
  ವಿಫಲವಾಗುವ ಒಂದು ಕರೆಯನ್ನು ಸುಡುತ್ತಲೇ ಇರುತ್ತದೆ.
- **ಸಿಬ್ಲಿಂಗ್ ಸುರಕ್ಷತೆ**: ಈಗಾಗಲೇ ಟರ್ಮಿನಲ್ ಆಗಿರುವ (banned/credits_exhausted)
  ಅಥವಾ ಈಗಾಗಲೇ ಹೆಚ್ಚು ಉದ್ದದ ಕೂಲ್ಡೌನ್ನಲ್ಲಿರುವ ಸಿಬ್ಲಿಂಗ್ ಅನ್ನು ಎಂದಿಗೂ
  ಓವರ್ರೈಟ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ.
- **ಎಕ್ಸ್ಕ್ಲೂಸಿವ್ ಅಲೋಲಿಸ್ಟ್**: `EGRESS_BUCKETED_LOCK_PROVIDERS` ಅನ್ನು
  ವಿಸ್ತರಿಸುವುದು ಸ್ಪಷ್ಟ ಓನರ್ ನಿರ್ಧಾರ; ಯಾವುದೇ ಜೆನೆರಿಕ್ ವೈರಿಂಗ್ ಇಲ್ಲ (ಪ್ಯಾಟರ್ನ್
  #10334/#10419). ಸಿಬ್ಲಿಂಗ್ ಕ್ವೆರಿ ಅದನ್ನು SQL ಲಿಟರಲ್ ಆಗಿ ಪುನರಾವರ್ತಿಸುವ
  ಬದಲು ಅದೇ ಅಲೋಲಿಸ್ಟ್ ಅನ್ನು ಬೈಂಡ್ ಮಾಡುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದನ್ನು ವಿಸ್ತರಿಸುವುದು
  ಒಂದು-ಸಾಲಿನ ಬದಲಾವಣೆಯಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ.
- **Egress IP ರೊಟೇಶನ್, ಎರಡೂ ದಿಕ್ಕುಗಳಲ್ಲಿ**: ಲುಕ್ಅಪ್ ವಿಂಡೋ (24h) egress-IP
  ಕ್ಯಾಶೆ TTL (5 ನಿಮಿಷ) ಗಿಂತ ಬಹಳ ವಿಶಾಲವಾಗಿದೆ, ಆದ್ದರಿಂದ "ಕೊನೆಯ ತಿಳಿದ IP"
  ಎಂಬುದು ಇತಿಹಾಸ, ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯಲ್ಲ. ಕನೆಕ್ಷನ್ನ ಪ್ರಾಕ್ಸಿ ವಿಂಡೋದೊಳಗೆ
  ರೊಟೇಟ್ ಆಗಿದ್ದರೆ, ಲಾಕ್ ನಿಜವಾಗಿ ಹಂಚಿಕೊಂಡ IP ಅನ್ನು **ಮಿಸ್ ಮಾಡಬಹುದು**
  (ದಾಖಲಾದ IP ಹೊಸದು, ಎಕ್ಸಾಸ್ಟ್ ಆಗದ್ದು) — ಮತ್ತು ಸಮ್ಮಿತೀಯವಾಗಿ, ಎಕ್ಸಾಸ್ಟ್ ಆದ
  IP ಯಿಂದ **ಈ ನಡುವೆ ರೊಟೇಟ್ ಆಗಿ ಹೋಗಿರುವ ಸಿಬ್ಲಿಂಗ್ ಅನ್ನು ಕೂಲ್ ಮಾಡಬಹುದು**.
  ಎರಡನೇ ಸಂದರ್ಭ ಆ ಸಿಬ್ಲಿಂಗ್ಗೆ ಒಂದು ಕೂಲ್ಡೌನ್ ವಿಂಡೋ ಬೆಲೆ ಬೀರುತ್ತದೆ; ಎರಡೂ
  ಇತಿಹಾಸ-ಆಧಾರಿತ ಲುಕ್ಅಪ್ನ ಸ್ವೀಕರಿಸಲಾದ ಬೆಸ್ಟ್-ಎಫರ್ಟ್ ಮಿತಿಗಳು.
- **ವೆಚ್ಚ**: `proxy_logs` ನ ಎರಡು ಬೌಂಡೆಡ್ ಸ್ಕ್ಯಾನ್ಗಳು (`idx_pl_timestamp`
  ಮೂಲಕ ವಿಂಡೋ-ಫಿಲ್ಟರ್ ಮಾಡಲಾಗಿದೆ), ಕೇವಲ 429 ಆವೃತ್ತಿಯಲ್ಲಿ. ಹೊಸ ಇಂಡೆಕ್ಸ್
  ಇಲ್ಲ (ಮೈಗ್ರೇಶನ್ 134 YAGNI). ಮಧ್ಯಮ ಗಾತ್ರದ ನಿಜ-ಟ್ರಾಫಿಕ್ DB ಕಾಪಿಯಲ್ಲಿ
  ಅಳೆಯಲಾಗಿದೆ; ಹೈ-ಥ್ರೂಪುಟ್ ಇನ್ಸ್ಟಾನ್ಸ್ ಅದೇ ವಿಂಡೋದಲ್ಲಿ ಅನುಪಾತದಲ್ಲಿಯೇ
  ಹೆಚ್ಚು ರೋಗಳನ್ನು ಹೊಂದಿರುತ್ತದೆ.

## ಡೀಬಗ್ಗಿಂಗ್

- Weighted combo `503 all_targets_cooling_down` ಎಂದು ಉತ್ತರಿಸಿದಾಗ (`Retry-After` ಸೆಟ್ ಮಾಡಲಾಗಿದೆ, `diagnostics.excluded` ಪ್ರತಿ ಟಾರ್ಗೆಟ್ ಅನ್ನು `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable` ನೊಂದಿಗೆ ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ) → ಪೂಲ್ ಕಾನ್ಫಿಗರ್ ಆಗಿದೆ ಮತ್ತು ಸಂಪರ್ಕಗೊಂಡಿದೆ, ಪ್ರತಿ ಟಾರ್ಗೆಟ್ ಕೇವಲ ಸ್ಥೈರ್ಯ ಟೈಮರ್ ಮೂಲಕ ಹೊರಗಿಡಲಾಗಿದೆ; `[COMBO] Weighted selection: every target excluded before dispatch — …` ಎಚ್ಚರಿಕೆಯು ಕಾರಣಗಳು ಮತ್ತು ಉಳಿದ ಸೆಕೆಂಡುಗಳನ್ನು ಹೆಸರಿಸುತ್ತದೆ. ಅದೇ ಕಾಂಬೊದಿಂದ ಬಂದ `404 no_executable_targets` ಎಂದರೆ ಯಾವುದೇ ಸ್ಥೈರ್ಯ ಟೈಮರ್ ಭಾಗವಹಿಸಿಲ್ಲ (ಚಲಾಯಿಸಲು ಏನೂ ಇಲ್ಲ, ಅಥವಾ ಪ್ರತಿ ಖಾತೆಯು ಲಭ್ಯತೆ ಪರೀಕ್ಷೆಯಲ್ಲಿ ವಿಫಲವಾಗಿದೆ). `targetResolution.ts` ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾದ ಹೊರತಾಕಿಕೆಗಳಿಂದ `open-sse/services/combo/pinRecovery.ts` ನಲ್ಲಿ ನಿರ್ಮಿಸಲಾಗಿದೆ.
- ಪ್ರೊವೈಡರ್ಗೆ ಎಲ್ಲಾ ಕೀಲಿಗಳನ್ನು ಸ್ಕಿಪ್ ಮಾಡಲಾಗಿದೆ → circuit breaker ಸ್ಥಿತಿ ಮತ್ತು ಪ್ರತಿ ಸಂಪರ್ಕದ `rateLimitedUntil`/`testStatus` ಎರಡನ್ನೂ ಪರಿಶೀಲಿಸಿ.
- ಮರುಹೊಂದಿಸುವ ವಿಂಡೋ ನಂತರ ಪ್ರೊವೈಡರ್ ಶಾಶ್ವತವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ → `getStatus()`/`canExecute()` ಬದಲಿಗೆ ಕಚ್ಚಾ `state` ಓದುವ ಕೋಡ್.
- ಒಂದು ಕೀಲಿ ವಿಫಲವಾಗಿದೆ, ಇತರವು ಕೆಲಸ ಮಾಡಬೇಕು → circuit breaker ಗಿಂತ connection cooldown ಅನ್ನು ಆದ್ಯತೆ ನೀಡಿ.
- ಕೇವಲ ಒಂದು ಮಾಡೆಲ್ ವಿಫಲವಾಗಿದೆ → connection cooldown ಗಿಂತ model lockout ಅನ್ನು ಆದ್ಯತೆ ನೀಡಿ.
- ಸ್ಥಿತಿ ಸ್ವಯಂ-ಚೇತರಿಸಿಕೊಳ್ಳಬೇಕು ಆದರೆ ಆಗುತ್ತಿಲ್ಲ → ಭವಿಷ್ಯದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ + ಅವಧಿ ಮೀರಿದ ಸ್ಥಿತಿಯನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವ ಓದುವ ಮಾರ್ಗವನ್ನು ಪರಿಶೀಲಿಸಿ. ಶಾಶ್ವತ ಸ್ಥಿತಿಗಳಿಗೆ ಕೈಯಾರೆ ಬದಲಾವಣೆಗಳು ಅಗತ್ಯ.

### ಪ್ರೊವೈಡರ್ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್

**ವ್ಯಾಪ್ತಿ**: ಇಡೀ ಪ್ರೊವೈಡರ್, ಉದಾ. `glm`, `openai`, `anthropic`.

**ಉದ್ದೇಶ**: ಅಪ್ಸ್ಟ್ರೀಮ್/ಸೇವಾ ಮಟ್ಟದಲ್ಲಿ ಪದೇ ಪದೇ ವಿಫಲವಾಗುತ್ತಿರುವ ಪ್ರೊವೈಡರ್ಗೆ ಟ್ರಾಫಿಕ್ ಕಳುಹಿಸುವುದನ್ನು
ನಿಲ್ಲಿಸುವುದು, ಇದರಿಂದ ಒಂದು ಅನಾರೋಗ್ಯಕರ ಪ್ರೊವೈಡರ್ ಪ್ರತಿ ವಿನಂತಿಯನ್ನು ನಿಧಾನಗೊಳಿಸುವುದಿಲ್ಲ.

**ಅನುಷ್ಠಾನ**:

- ಕೋರ್ ಕ್ಲಾಸ್: `src/shared/utils/circuitBreaker.ts`
- ಚಾಟ್ ಗೇಟ್/ಎಕ್ಸಿಕ್ಯೂಶನ್ ವೈರಿಂಗ್: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- ರನ್ಟೈಮ್ ಸ್ಥಿತಿ API: `src/app/api/monitoring/health/route.ts`
- ಹಂಚಿಕೊಂಡ ರ್ಯಾಪರ್ಗಳು: `open-sse/services/accountFallback.ts`
- ಶೇಖರಿಸಲಾದ ಸ್ಥಿತಿ ಟೇಬಲ್: `domain_circuit_breakers`

**ಸ್ಥಿತಿಗಳು** (4 — `src/shared/utils/circuitBreaker.ts`):

- `CLOSED`: ಸಾಮಾನ್ಯ ಟ್ರಾಫಿಕ್ ಅನ್ನು ಅನುಮತಿಸಲಾಗಿದೆ.
- `DEGRADED`: ಮುಂಚಿನ-ಎಚ್ಚರಿಕೆ ಬ್ಯಾಂಡ್ — ವಿಫಲತೆಗಳು ಡಿಗ್ರಡೇಶನ್ ಮಿತಿಯನ್ನು ದಾಟಿವೆ ಆದರೆ ಇನ್ನೂ
  ಬ್ರೇಕರ್ ಮಿತಿಯನ್ನು ದಾಟಿಲ್ಲ; ಟ್ರಾಫಿಕ್ ಇನ್ನೂ ಹರಿಯುತ್ತದೆ, ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು ಎಚ್ಚರಿಕೆಯನ್ನು ತೋರಿಸುತ್ತವೆ. ಮಾನ್ಯ
  ಸಂಪರ್ಕ ಪರೀಕ್ಷೆ ಅಥವಾ ಹೊಸ ವಿಫಲತೆಯಿಲ್ಲದ ಶಾಂತ ವಿಂಡೋ ಅದನ್ನು `CLOSED` ಗೆ
  ಹಿಂತಿರುಗಿಸುತ್ತದೆ (`docs/architecture/RESILIENCE_GUIDE.md` ನಲ್ಲಿ ವಿಂಡೋ ಇದೆ).
- `OPEN`: ಪ್ರೊವೈಡರ್ ತಾತ್ಕಾಲಿಕವಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗಿದೆ; ಕರೆದವರಿಗೆ ಪ್ರೊವೈಡರ್-ಸರ್ಕ್ಯೂಟ್-ತೆರೆದ
  ಪ್ರತಿಕ್ರಿಯೆ ಸಿಗುತ್ತದೆ ಅಥವಾ ಕಾಂಬೊ ರೌಟಿಂಗ್ ಬೇರೆ ಟಾರ್ಗೆಟ್ಗೆ ಸ್ಕಿಪ್ ಮಾಡುತ್ತದೆ.
- `HALF_OPEN`: ಮರುಹೊಂದಿಸುವ ಸಮಯಮಿತಿ ಕಳೆದಿದೆ; ಪರೀಕ್ಷಾ ವಿನಂತಿಯನ್ನು ಅನುಮತಿಸಿ. ಯಶಸ್ಸು
  ಬ್ರೇಕರ್ ಅನ್ನು ಮುಚ್ಚುತ್ತದೆ, ವಿಫಲತೆಯು ಅದನ್ನು ಮತ್ತೆ ತೆರೆಯುತ್ತದೆ.

**ಡೀಫಾಲ್ಟ್ಗಳು** (`open-sse/config/constants.ts` → `PROVIDER_PROFILES`,
`src/lib/resilience/settings.ts` ನಲ್ಲಿರುವ `DEFAULT_RESILIENCE_SETTINGS.providerBreaker`
ಮೂಲಕ ಬಳಸಲಾಗುತ್ತದೆ → `src/sse/handlers/chatHelpers.ts` ನಲ್ಲಿ
`getCircuitBreaker(provider, …)`). ಇಡೀ-ಪ್ರೊವೈಡರ್ ಬ್ರೇಕರ್ `circuitBreakerThreshold` /
`circuitBreakerReset` ಮೇಲೆ ಚಲಿಸುತ್ತದೆ:

| ಪ್ರೊಫೈಲ್ | ಡಿಗ್ರೇಡ್ ಆಗುವ ಸ್ಥಾನ | ತೆರೆಯುವ ಸ್ಥಾನ (`circuitBreakerThreshold`) | ಮರುಹೊಂದಿಸುವುದು (`circuitBreakerReset`) |
| -------- | ------------------: | ----------------------------------------: | -------------------------------------: |
| OAuth    |                 `5` |                                       `8` |                                  `60s` |
| API key  |                 `7` |                                      `12` |                                  `30s` |
| Local    |       (ಲೆಕ್ಕಹಾಕಲಾದ) |                                       `2` |                                  `15s` |

`PROVIDER_PROFILES` ಸಹ `providerFailureThreshold` (10/15/2),
`providerFailureWindowMs` (15/30/5 ನಿಮಿಷ) ಮತ್ತು `providerCooldownMs` (5/10/1 ನಿಮಿಷ) ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ: ಇವು
**ಆಪ್ಟ್-ಇನ್ ಗ್ಲೋಬಲ್ Provider Cooldown ನ ವಿಂಡೋ ಗೇಟ್** ಅನ್ನು ಚಾಲಾಯಿಸುತ್ತವೆ (`PROVIDER_COOLDOWN_ENABLED`, ಡೀಫಾಲ್ಟ್
ಆಫ್) — `open-sse/services/providerCooldownTracker.ts` ನಲ್ಲಿನ ಪ್ರೊವೈಡರ್-ಮಟ್ಟದ ಎಂಟ್ರಿಯು
`providerFailureWindowMs` ಒಳಗೆ `providerFailureThreshold` ವಿಫಲತೆಗಳ ನಂತರ ಮಾತ್ರ
ಕೂಲಿಂಗ್ ಆಗುತ್ತಿದೆ ಎಂದು ಎಣಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ನಂತರ `providerCooldownMs` ಗಾಗಿ ಕೂಲ್ ಆಗುತ್ತದೆ. ಇವು
ಲೈವ್ ಬ್ರೇಕರ್ನ ಮಿತಿಗಳಲ್ಲ — ಬ್ರೇಕರ್ ನಡವಳಿಕೆಯನ್ನು ನಿರೀಕ್ಷಿಸಿ ಅವುಗಳನ್ನು ಟ್ಯೂನ್ ಮಾಡಬೇಡಿ. ಪ್ರತಿ ಡೀಫಾಲ್ಟ್ ಅನ್ನು
`OMNIROUTE_PROVIDER_BREAKER_*` ಮತ್ತು `OMNIROUTE_CIRCUIT_BREAKER_*` ಎನ್ವಿ ವೇರಿಯೇಬಲ್ಗಳ ಮೂಲಕ
ಅಧಿಕ್ರಮಿಸಬಹುದು; ರನ್ಟೈಮ್-ನಿಖರ ಉಲ್ಲೇಖ ಟೇಬಲ್ `docs/architecture/RESILIENCE_GUIDE.md`
ನಲ್ಲಿ ಇದೆ.

ಪ್ರೊವೈಡರ್-ಮಟ್ಟದ ವಿಫಲತೆ ಸ್ಥಿತಿಗಳು ಮಾತ್ರ ಪ್ರೊವೈಡರ್ ಬ್ರೇಕರ್ ಅನ್ನು ಟ್ರಿಪ್ ಮಾಡಬೇಕು:

```ts
(408, 500, 502, 503, 504);
```

ಹೆಚ್ಚಿನ `401`, `403`, ಅಥವಾ `429` ಸಂದರ್ಭಗಳಂತಹ ಸಾಮಾನ್ಯ ಖಾತೆ/ಕೀಲಿ/ಮಾಡೆಲ್ ದೋಷಗಳಿಗೆ
ಇಡೀ-ಪ್ರೊವೈಡರ್ ಬ್ರೇಕರ್ ಅನ್ನು ಟ್ರಿಪ್ ಮಾಡಬೇಡಿ. ಅವು ಸಾಮಾನ್ಯವಾಗಿ connection cooldown ಅಥವಾ
model lockout ಗೆ ಸೇರಿವೆ. ಸಾಮಾನ್ಯ API-ಕೀಲಿ ಪ್ರೊವೈಡರ್ `403` ಅನ್ನು ಟರ್ಮಿನಲ್
ಪ್ರೊವೈಡರ್/ಖಾತೆ ದೋಷವೆಂದು ವರ್ಗೀಕರಿಸದ ಹೊರತು ಚೇತರಿಸಿಕೊಳ್ಳಬಹುದಾದುದಾಗಿರಬೇಕು.

ಬ್ರೇಕರ್ ಹಿನ್ನೆಲೆ ಟೈಮರ್ ಬಳಸದೆ, ಸೋಮಾರಿ ಚೇತರಿಕೆಯನ್ನು (lazy recovery) ಬಳಸುತ್ತದೆ. `OPEN` ಅವಧಿ ಮುಗಿದಾಗ, `getStatus()`, `canExecute()`, ಮತ್ತು `getRetryAfterMs()` ನಂತಹ ಓದುವಿಕೆಗಳು ಸ್ಥಿತಿಯನ್ನು `HALF_OPEN` ಗೆ ರಿಫ್ರೆಶ್ ಮಾಡುತ್ತವೆ, ಆದ್ದರಿಂದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು ಮತ್ತು ಕಾಂಬೊ ಅಭ್ಯರ್ಥಿ ನಿರ್ಮಾಪಕರು ಅವಧಿ ಮೀರಿದ ಪ್ರೊವೈಡರ್ ಅನ್ನು ಶಾಶ್ವತವಾಗಿ ಹೊರಗಿಡುತ್ತಲೇ ಇರುವುದಿಲ್ಲ.

### ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್

**ವ್ಯಾಪ್ತಿ**: ಒಂದು ಪ್ರೊವೈಡರ್ ಸಂಪರ್ಕ/ಖಾತೆ/ಕೀ.

**ಉದ್ದೇಶ**: ಅದೇ ಪ್ರೊವೈಡರ್ಗಾಗಿ ಇತರ ಸಂಪರ್ಕಗಳು ವಿನಂತಿಗಳನ್ನು ಸೇವಿಸುತ್ತಲೇ ಇರಲು ಅವಕಾಶ ನೀಡುತ್ತಾ, ಒಂದು ಕೆಟ್ಟ ಕೀ/ಖಾತೆಯನ್ನು ತಾತ್ಕಾಲಿಕವಾಗಿ ಬಿಟ್ಟುಬಿಡುವುದು.

**ಅನುಷ್ಠಾನ**:

- ಬರಹ/ನವೀಕರಣ ಮಾರ್ಗ: `src/sse/services/auth.ts::markAccountUnavailable()`
- ಖಾತೆ ಆಯ್ಕೆ/ಶೋಧನೆ: `src/sse/services/auth.ts::getProviderCredentials...`
- ಕೂಲ್ಡೌನ್ ಲೆಕ್ಕಾಚಾರ: `open-sse/services/accountFallback.ts::checkFallbackError()`
- ಸೆಟ್ಟಿಂಗ್ಗಳು: `src/lib/resilience/settings.ts`

ಪ್ರೊವೈಡರ್ ಸಂಪರ್ಕಗಳ ಮೇಲಿನ ಪ್ರಮುಖ ಫೀಲ್ಡ್ಗಳು:

```ts
rateLimitedUntil;
testStatus: "unavailable";
lastError;
lastErrorType;
errorCode;
backoffLevel;
```

ಖಾತೆ ಆಯ್ಕೆಯ ಸಮಯದಲ್ಲಿ, ಈ ಕೆಳಗಿನ ಸ್ಥಿತಿಯಿದ್ದಾಗ ಸಂಪರ್ಕವನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ:

```ts
new Date(rateLimitedUntil).getTime() > Date.now();
```

ಕೂಲ್ಡೌನ್ಗಳು ಸಹ ಸೋಮಾರಿಯಾಗಿವೆ: `rateLimitedUntil` ಹಿಂದಿನ ಸಮಯದಲ್ಲಿದ್ದಾಗ, ಸಂಪರ್ಕವು ಮತ್ತೆ ಅರ್ಹವಾಗುತ್ತದೆ. ಯಶಸ್ವಿ ಬಳಕೆಯ ನಂತರ, `clearAccountError()` `testStatus`, `rateLimitedUntil`, ದೋಷ ಫೀಲ್ಡ್ಗಳು ಮತ್ತು `backoffLevel` ಅನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.

ಡೀಫಾಲ್ಟ್ ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್ ನಡವಳಿಕೆ:

- OAuth ಮೂಲ ಕೂಲ್ಡೌನ್: `5s`.
- API-ಕೀ ಮೂಲ ಕೂಲ್ಡೌನ್: `3s`.
- API-ಕೀ `429` ಲಭ್ಯವಿದ್ದಾಗ ಅಪ್ಸ್ಟ್ರೀಮ್ ಮರುಪ್ರಯತ್ನ ಸುಳಿವುಗಳಿಗೆ (`Retry-After`, ರೀಸೆಟ್ ಹೆಡರ್ಗಳು, ಅಥವಾ ಪಾರ್ಸ್ ಮಾಡಬಹುದಾದ ರೀಸೆಟ್ ಪಠ್ಯ) ಆದ್ಯತೆ ನೀಡಬೇಕು.
- ಪುನರಾವರ್ತಿತ ಚೇತರಿಸಿಕೊಳ್ಳಬಹುದಾದ ವಿಫಲತೆಗಳು ಘಾತಾಂಕೀಯ ಬ್ಯಾಕ್ಆಫ್ ಅನ್ನು ಬಳಸುತ್ತವೆ:

```ts
baseCooldownMs * 2 ** failureIndex;
```

ಆಂಟಿ-ಥಂಡರಿಂಗ್-ಹರ್ಡ್ ರಕ್ಷಣೆಯು (anti-thundering-herd guard) ಅದೇ ಸಂಪರ್ಕದ ಮೇಲಿನ ಏಕಕಾಲಿಕ ವಿಫಲತೆಗಳು ಕೂಲ್ಡೌನ್ ಅನ್ನು ಪದೇ ಪದೇ ವಿಸ್ತರಿಸುವುದನ್ನು ಅಥವಾ `backoffLevel` ಅನ್ನು ಎರಡು ಬಾರಿ ಹೆಚ್ಚಿಸುವುದನ್ನು ತಡೆಯುತ್ತದೆ.

ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳು ಕೂಲ್ಡೌನ್ಗಳಲ್ಲ. `banned`, `expired` (`EXPIRED_RETRY_MAX` ಮೂಲಕ N ಸೀಮಿತ ಮರುಪ್ರಯತ್ನಗಳ ನಂತರ ಮಾತ್ರ ಟರ್ಮಿನಲ್ ಆಗುತ್ತದೆ), ಮತ್ತು `credits_exhausted` ಗಳು ರುಜುವಾತುಗಳು/ಸೆಟ್ಟಿಂಗ್ಗಳು ಬದಲಾಗುವವರೆಗೆ ಅಥವಾ ಆಪರೇಟರ್ ಅವುಗಳನ್ನು ರೀಸೆಟ್ ಮಾಡುವವರೆಗೆ ಲಭ್ಯವಿಲ್ಲದಂತೆಯೇ ಉಳಿಯುವುದು ಉದ್ದೇಶ. ತಾತ್ಕಾಲಿಕ ಕೂಲ್ಡೌನ್ ಸ್ಥಿತಿಯೊಂದಿಗೆ ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳನ್ನು ಬದಲಾಯಿಸಬೇಡಿ.

### ಮಾದರಿ ಲಾಕ್ಔಟ್

**ವ್ಯಾಪ್ತಿ**: ಪ್ರೊವೈಡರ್ + ಸಂಪರ್ಕ + ಮಾದರಿ.

**ಉದ್ದೇಶ**: ಆ ಸಂಪರ್ಕಕ್ಕೆ ಕೇವಲ ಒಂದು ಮಾದರಿ ಲಭ್ಯವಿಲ್ಲದಿದ್ದಾಗ ಅಥವಾ ಕೋಟಾ-ಸೀಮಿತವಾಗಿದ್ದಾಗ, ಇಡೀ ಸಂಪರ್ಕವನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದನ್ನು ತಪ್ಪಿಸುವುದು.

ಉದಾಹರಣೆಗಳು:

- ಪ್ರತಿ-ಮಾದರಿ ಕೋಟಾ ಪ್ರೊವೈಡರ್ಗಳು `429` ಹಿಂತಿರುಗಿಸುವುದು.
- ಒಂದು ಕಾಣೆಯಾದ ಮಾದರಿಗಾಗಿ ಸ್ಥಳೀಯ ಪ್ರೊವೈಡರ್ಗಳು `404` ಹಿಂತಿರುಗಿಸುವುದು.
- ಆಯ್ದ Grok ಮೋಡ್ಗಳಂತಹ ಪ್ರೊವೈಡರ್-ನಿರ್ದಿಷ್ಟ ಮೋಡ್/ಮಾದರಿ ಅನುಮತಿ ವಿಫಲತೆಗಳು.

ಮಾದರಿ ಲಾಕ್ಔಟ್ `open-sse/services/accountFallback.ts` ನಲ್ಲಿ ಇದೆ ಮತ್ತು ಅದೇ ಸಂಪರ್ಕವು ಇತರ ಮಾದರಿಗಳಿಗೆ ಸೇವೆ ಸಲ್ಲಿಸುತ್ತಲೇ ಇರಲು ಅನುಮತಿಸುತ್ತದೆ.

### ಡಿಬಗ್ಗಿಂಗ್ ಮಾರ್ಗದರ್ಶನ

- ಪ್ರೊವೈಡರ್ಗಾಗಿ ಎಲ್ಲಾ ಕೀಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗಿದ್ದರೆ, ಪ್ರೊವೈಡರ್ ಬ್ರೇಕರ್ ಸ್ಥಿತಿ ಮತ್ತು ಪ್ರತಿ ಸಂಪರ್ಕದ `rateLimitedUntil`/`testStatus` ಎರಡನ್ನೂ ಪರಿಶೀಲಿಸಿ.
- ರೀಸೆಟ್ ವಿಂಡೋ ನಂತರ ಪ್ರೊವೈಡರ್ ಶಾಶ್ವತವಾಗಿ ಹೊರಗಿಡಲಾಗಿರುವಂತೆ ತೋಚಿದರೆ, `getStatus()`/`canExecute()` ಬಳಸುವ ಬದಲು ಕೋಡ್ ಕಚ್ಚಾ `state` ಅನ್ನು ಓದುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ.
- ಒಂದು ಪ್ರೊವೈಡರ್ ಕೀ ವಿಫಲವಾದರೆ ಆದರೆ ಇತರವು ಕೆಲಸ ಮಾಡಬೇಕಾದರೆ, ಪ್ರೊವೈಡರ್ ಬ್ರೇಕರ್ಗಿಂತ ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್ ಅನ್ನು ಆದ್ಯತೆ ನೀಡಿ.
- ಕೇವಲ ಒಂದು ಮಾದರಿ ವಿಫಲವಾದರೆ, ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್ಗಿಂತ ಮಾದರಿ ಲಾಕ್ಔಟ್ ಅನ್ನು ಆದ್ಯತೆ ನೀಡಿ.
- ಒಂದು ಸ್ಥಿತಿ ತಾನಾಗಿ ಚೇತರಿಸಿಕೊಳ್ಳಬೇಕಾದರೆ, ಅದು ಭವಿಷ್ಯದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್/ರೀಸೆಟ್ ಟೈಮ್ಔಟ್ ಮತ್ತು ಅವಧಿ ಮೀರಿದ ಸ್ಥಿತಿಯನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವ ಓದುವ ಮಾರ್ಗವನ್ನು ಹೊಂದಿರಬೇಕು. ಶಾಶ್ವತ ಸ್ಥಿತಿಗಳಿಗೆ ಹಸ್ತಚಾಲಿತ ರುಜುವಾತು ಅಥವಾ ಕಾನ್ಫಿಗ್ ಬದಲಾವಣೆಗಳು ಅಗತ್ಯವಿರುತ್ತವೆ.
