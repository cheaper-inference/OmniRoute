> ಅರ್ಹ ಸಂದರ್ಭದ ಮೇಲೆ ಸ್ವಯಂಚಾಲಿತವಾಗಿ 15-95% ಉಳಿಸಿ. ತ್ವರಿತ ಅವಲೋಕನಕ್ಕಾಗಿ, [README ಸಂಕೋಚನ ವಿಭಾಗವನ್ನು](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) ನೋಡಿ.

## ಅವಲೋಕನ

OmniRoute ವಿನಂತಿಗಳು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರನ್ನು ತಲುಪುವ ಮೊದಲು **ಪೂರ್ವಭಾವಿಯಾಗಿ** ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮಾಡ್ಯುಲರ್ ಪ್ರಾಂಪ್ಟ್ ಸಂಕೋಚನ ಪೈಪ್ಲೈನ್ ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸುತ್ತದೆ. ಅಂದರೆ, ನಿಮ್ಮ ಟೋಕನ್ ಉಳಿತಾಯವು ಪಾರದರ್ಶಕವಾಗಿ ಸಂಭವಿಸುತ್ತದೆ — ನಿಮ್ಮ ಕಾರ್ಯವಿಧಾನದಲ್ಲಿ ಯಾವುದೇ ಬದಲಾವಣೆಗಳ ಅಗತ್ಯವಿಲ್ಲ.

```
ಕ್ಲೈಂಟ್ ವಿನಂತಿ
  → ಸಂಕೋಚನ ತಂತ್ರದ ಆಯ್ಕೆಗಾರ
    → ಕಾಂಬೊ ಅತಿಕ್ರಮಣವಿದೆಯೇ? → ಕಾಂಬೊ ಸೆಟ್ಟಿಂಗ್ ಬಳಸಿ
    → ಸ್ವಯಂ-ಪ್ರಚೋದನೆ ಮಿತಿಯೇ? → ಸ್ವಯಂ ಮೋಡ್ ಬಳಸಿ
    → ಡೀಫಾಲ್ಟ್ ಮೋಡ್? → ಜಾಗತಿಕ ಸೆಟ್ಟಿಂಗ್ ಬಳಸಿ
    → ಆಫ್ ಆಗಿದೆಯೇ? → ಸಂಕೋಚನವನ್ನು ಬಿಟ್ಟುಬಿಡಿ
  → ಆಯ್ಕೆಮಾಡಿದ ಸಂಕೋಚನ ಮೋಡ್
    → ಆಫ್: ಸಂಕೋಚನವಿಲ್ಲ
    → ಲೈಟ್: ಸುರಕ್ಷಿತ ಖಾಲಿ ಜಾಗ/ಫಾರ್ಮ್ಯಾಟಿಂಗ್ ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ (~15%)
    → ಸ್ಟ್ಯಾಂಡರ್ಡ್: Caveman-ಶೈಲಿಯ ಅನಗತ್ಯ ಪದಗಳ ತೆಗೆದುಹಾಕುವಿಕೆ (~30%)
    → ಅಗ್ರೆಸಿವ್: ಇತಿಹಾಸದ ವಯೋಮಾನ ನಿರ್ವಹಣೆ + ಸಾರಾಂಶಗೊಳಿಸುವಿಕೆ (~50%)
    → ಅಲ್ಟ್ರಾ: ಹ್ಯೂರಿಸ್ಟಿಕ್ ಕಡಿತಗೊಳಿಸುವಿಕೆ + ಕೋಡ್-ಬ್ಲಾಕ್ ತೆಳುಗೊಳಿಸುವಿಕೆ (~75%)
    → RTK: ಕಮಾಂಡ್-ಅರಿವಿನ ಟರ್ಮಿನಲ್/ಟೂಲ್-ಔಟ್ಪುಟ್ ಫಿಲ್ಟರಿಂಗ್ (60-90% ಅಪ್ಸ್ಟ್ರೀಮ್ ವ್ಯಾಪ್ತಿ)
    → ಸ್ಟ್ಯಾಕ್ಡ್: ಕ್ರಮಬದ್ಧ ಬಹು-ಎಂಜಿನ್ ಪೈಪ್ಲೈನ್, ಸಾಮಾನ್ಯವಾಗಿ RTK ನಂತರ Caveman (78-95% ಅರ್ಹ ವ್ಯಾಪ್ತಿ)
  → ಸಂಕುಚಿತ ವಿನಂತಿ → ಪೂರೈಕೆದಾರ
```

## ಸಂಕುಚನ ಮೋಡ್ಗಳು

### ಆಫ್

ಯಾವುದೇ ಸಂಕುಚನ ಅನ್ವಯಿಸಲಾಗಿಲ್ಲ. ಎಲ್ಲ ಸಂದೇಶಗಳು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಸಾಗುತ್ತವೆ.

### ಲೈಟ್ ಮೋಡ್ (~15% ಉಳಿತಾಯ, <1ms ವಿಳಂಬ)

ಅತ್ಯಂತ ಸುರಕ್ಷಿತ ಮೋಡ್ — ಫಾರ್ಮ್ಯಾಟಿಂಗ್ ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ. ಇದರ tool-result truncation ನಷ್ಟಕಾರಕವಾಗಿರುವುದರಿಂದ, ಡೀಫಾಲ್ಟ್
ಪಥದಲ್ಲಿ (`allow-lossy`, `engine:lite` ಅಥವಾ ಹೆಸರಿಸಲಾದ-ಕಾಂಬೋ opt-in ಇಲ್ಲದೆ) `compressToolResults: false` ಸಹಿತ ಲೈಟ್ ಮೋಡ್ ನಡೆಯುತ್ತದೆ:
ಹಿಂದಿನ tool ಫಲಿತಾಂಶಗಳು provider ಗೆ ಬದಲಾವಣೆಯಿಲ್ಲದೆ ತಲುಪುತ್ತವೆ.

| ತಂತ್ರ                    | ವಿವರಣೆ                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | ಸತತ ಖಾಲಿ ಸಾಲುಗಳು ಮತ್ತು ಕೊನೆಯಲ್ಲಿನ ಖಾಲಿ ಜಾಗಗಳನ್ನು ವಿಲೀನಗೊಳಿಸಿ                                |
| `dedupSystemPrompt`      | ನಕಲಿ system ಸಂದೇಶಗಳನ್ನು ತೆಗೆದುಹಾಕಿ                                                          |
| `compressToolResults`    | ಹಿಂದಿನ tool ಫಲಿತಾಂಶಗಳನ್ನು ಲೈಟ್ ಮಿತಿಗೆ truncate ಮಾಡಿ (ನಷ್ಟಕಾರಕ: request opt-in ಇದ್ದಾಗ ಮಾತ್ರ) |
| `removeRedundantContent` | ಪುನರಾವರ್ತಿತ ಸೂಚನೆಗಳನ್ನು ತೆಗೆದುಹಾಕಿ                                                          |
| `replaceImageUrls`       | base64 image data URI ಗಳನ್ನು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸಿ                                                |

**ಇವುಗಳಿಗೆ ಸೂಕ್ತ:** ಯಾವಾಗಲೂ ಸಕ್ರಿಯ ಬಳಕೆ, ಸುರಕ್ಷತೆ-ನಿರ್ಣಾಯಕ ಕಾರ್ಯಪ್ರವಾಹಗಳು.

### ಸ್ಟ್ಯಾಂಡರ್ಡ್ ಮೋಡ್ (~30% ಉಳಿತಾಯ)

[Caveman](https://github.com/JuliusBrussee/caveman) ನಿಂದ ಪ್ರೇರಿತ — ಅರ್ಥವನ್ನು ಉಳಿಸಿಕೊಂಡೇ ತುಂಬುವ ಪದಗಳು ಮತ್ತು ವಿಸ್ತೃತ ವಾಕ್ಯಪ್ರಯೋಗವನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ:

- ತುಂಬುವ ಪದಗಳನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ ("please", "I think", "basically", "actually")
- ವಿಸ್ತೃತ ವಾಕ್ಯಪ್ರಯೋಗವನ್ನು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸುತ್ತದೆ ("in order to" → "to", "as a result of" → "because")
- ವಿನಯಪೂರ್ವಕ ಅನಿಶ್ಚಿತತೆಯನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ ("Would you mind...", "If you could possibly...")
- coding prompts ಗಾಗಿ ಹೊಂದುವಂತೆ ರೂಪಿಸಲಾದ 30+ regex ನಿಯಮಗಳು

**ಇವುಗಳಿಗೆ ಸೂಕ್ತ:** ದೈನಂದಿನ coding ಕಾರ್ಯಪ್ರವಾಹಗಳು, ವೆಚ್ಚ-ಜಾಗರೂಕ ತಂಡಗಳು.

### ಅಗ್ರೆಸಿವ್ ಮೋಡ್ (~50% ಉಳಿತಾಯ)

ದೀರ್ಘ ಅವಧಿಯ ಸೆಷನ್ಗಳಿಗಾಗಿ ಸ್ಮಾರ್ಟ್ ಇತಿಹಾಸ ನಿರ್ವಹಣೆ:

- **ಸಂದೇಶ ವಯಸ್ಸುಗೊಳಿಸುವಿಕೆ** — ಹಳೆಯ ಸಂದೇಶಗಳನ್ನು ಕ್ರಮೇಣ ಹೆಚ್ಚು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸಲಾಗುತ್ತದೆ
- **Tool ಫಲಿತಾಂಶ ಸಂಕುಚನ** — ದೀರ್ಘ tool output ಗಳನ್ನು truncate ಅಥವಾ elide ಮಾಡಲಾಗುತ್ತದೆ (ಮೊದಲ/ಕೊನೆಯ ಸಾಲುಗಳು,
  match-line filtering, JSON key compaction)
- **ರಚನಾ ಸಮಗ್ರತೆ ರಕ್ಷಣೆಗಳು** — `tool_use` + `tool_result` ಜೋಡಿಗಳು ಸुसಂಗತವಾಗಿಯೇ ಉಳಿಯುವುದನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ
- **Context Window ಅರಿವು** — ಪ್ರತಿ model ನ token ಮಿತಿಗಳನ್ನು ಗೌರವಿಸುತ್ತದೆ

**ಇವುಗಳಿಗೆ ಸೂಕ್ತ:** ವಿಸ್ತೃತ debugging ಸೆಷನ್ಗಳು, ದೊಡ್ಡ codebase ಗಳು.

### ಅಲ್ಟ್ರಾ ಮೋಡ್ (~75% ಉಳಿತಾಯ)

Token-ನಿರ್ಣಾಯಕ ಸಂದರ್ಭಗಳಿಗಾಗಿ ಗರಿಷ್ಠ ಸಂಕುಚನ:

- **ಹ್ಯೂರಿಸ್ಟಿಕ್ Pruning** — score ಆಧಾರಿತ prose token pruning
- **ರಚನೆ ಸಂರಕ್ಷಣೆ** — fenced code blocks, inline code, URLs ಮತ್ತು identifiers ಗಳನ್ನು tombstone ಮಾಡಿ verbatim ಆಗಿ ಮರುಜೋಡಿಸಲಾಗುತ್ತದೆ; ಎಂದಿಗೂ prune ಮಾಡಲಾಗುವುದಿಲ್ಲ
- **ಐಚ್ಛಿಕ SLM tier** — configure ಮಾಡಿದಾಗ, ಸಣ್ಣ local model prune ಅನ್ನು refine ಮಾಡಬಹುದು
- Aggressive mode ನಿಂದ ಸ್ವತಂತ್ರ: ಇದು message aging, tool-result compression ಅಥವಾ fallback summarizer ಅನ್ನು ನಡೆಸುವುದಿಲ್ಲ (SLM-tier ವಿಫಲವಾದಾಗ ಮಾತ್ರ fallback pass ಅನ್ನು aggressive ಮೂಲಕ route ಮಾಡಬಹುದು)

**ಇವುಗಳಿಗೆ ಸೂಕ್ತ:** ನೀವು ಪದೇಪದೇ context ಮಿತಿಗಳನ್ನು ತಲುಪುತ್ತಿರುವಾಗ.

### RTK ಮೋಡ್ (60-90% upstream ವ್ಯಾಪ್ತಿ)

Coding-agent ಸೆಷನ್ಗಳಲ್ಲಿ ಕಾಣಿಸುವ verbose tool outputs ಗಾಗಿ RTK mode ಅನ್ನು ಹೊಂದಿಸಲಾಗಿದೆ:

- `git status`, `git diff`, `git log`, test runners,
  TypeScript/Vite/Webpack builds, ESLint/Biome/Prettier, npm audit/installs, Docker logs, infra
  output ಮತ್ತು ಸಾಮಾನ್ಯ shell output ಗಳಂತಹ command/output ವರ್ಗಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ
- `open-sse/services/compression/engines/rtk/filters/` ನಿಂದ JSON filter packs ಅನ್ವಯಿಸುತ್ತದೆ
- Project ಅಥವಾ global `filters.toml` files ನಿಂದ RTK TOML schema v1 filters ಅನ್ನು import ಮಾಡುತ್ತದೆ; project files ಗಾಗಿ inline-test
  validation ಮತ್ತು trust-gating ಸಹಿತ
- Inline verify samples ಸಹಿತ 56 built-in filters ಒದಗಿಸುತ್ತದೆ
- ANSI control sequences, progress bars, ಪುನರಾವರ್ತಿತ ಸಾಲುಗಳು ಮತ್ತು actionable ಅಲ್ಲದ noise ಅನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ
- Failures, errors, warnings, ಬದಲಾದ files, summaries ಮತ್ತು ದೀರ್ಘ output ನ tail ಅನ್ನು ಉಳಿಸುತ್ತದೆ
- Trust-gated project filters, global filters ಮತ್ತು ಐಚ್ಛಿಕ redacted raw-output recovery ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ

**ಇವುಗಳಿಗೆ ಸೂಕ್ತ:** shell, build, test, git, grep ಮತ್ತು file-output transcripts ಹೊಂದಿರುವ agent ಸೆಷನ್ಗಳು.

### ಸ್ಟ್ಯಾಕ್ಡ್ ಮೋಡ್ (78-95% eligible ವ್ಯಾಪ್ತಿ)

ಸ್ಟ್ಯಾಕ್ಡ್ ಮೋಡ್ ಅನೇಕ ಸಂಕುಚನ engines ಅನ್ನು ನಿರ್ಧಾರಾತ್ಮಕ ಕ್ರಮದಲ್ಲಿ ನಡೆಸುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ pipeline:

```txt
RTK -> Caveman
```

ಈ ಕ್ರಮವು ಮೊದಲು terminal/tool output ಅನ್ನು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸುತ್ತದೆ, ನಂತರ ಉಳಿದ natural-language prompt ಗೆ Caveman semantic condensation ಅನ್ವಯಿಸುತ್ತದೆ. Stacked pipelines ಅನ್ನು
ಜಾಗತಿಕವಾಗಿ ಅಥವಾ routing combos ಗೆ ನಿಯೋಜಿಸಲಾದ compression combos ಮೂಲಕ configure ಮಾಡಬಹುದು.

**ಇವುಗಳಿಗೆ ಸೂಕ್ತ:** ದೊಡ್ಡ tool logs ಜೊತೆಗೆ ಮಾನವ ಸೂಚನೆಗಳು ಅಥವಾ assistant summaries ಹೊಂದಿರುವ ಮಿಶ್ರ context.

## ಅಪ್ಸ್ಟ್ರೀಮ್ ಉಳಿತಾಯದ ಲೆಕ್ಕಾಚಾರ

OmniRoute ಎರಡು ಮೂಲಗಳಿಂದ ಕಂಪ್ರೆಷನ್ ಉಳಿತಾಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ: ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರಾಜೆಕ್ಟ್ ಬೆಂಚ್ಮಾರ್ಕ್ಗಳು ಮತ್ತು
OmniRouteನ ಸ್ವಂತ ಎಂಜಿನ್ ಸಂಯೋಜನೆ.

| ಮೂಲ     | ಇಲ್ಲಿ ಬಳಸಲಾದ ಅಪ್ಸ್ಟ್ರೀಮ್ README ಸಂಖ್ಯೆ                                                                                        |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` ಕಡಿಮೆ ಔಟ್ಪುಟ್ ಟೋಕನ್ಗಳು, `65%` ಬೆಂಚ್ಮಾರ್ಕ್ ಸರಾಸರಿ ಔಟ್ಪುಟ್ ಉಳಿತಾಯ, `22-87%` ವ್ಯಾಪ್ತಿ ಮತ್ತು `~46%` ಇನ್ಪುಟ್ ಕಂಪ್ರೆಷನ್ ಸಾಧನ |
| RTK     | `60-90%` ಕಮಾಂಡ್-ಔಟ್ಪುಟ್ ಉಳಿತಾಯ; ಮಾದರಿ ಸೆಷನ್ನಲ್ಲಿ `~118,000 -> ~23,900` ಟೋಕನ್ಗಳು, ಅಂದರೆ `79.7%` ಉಳಿತಾಯ (`~80%`)                |

ಒಂದಕ್ಕೊಂದು ಅತಿಕ್ರಮಿಸುವ ಸಾಧನ/ಕಾಂಟೆಕ್ಸ್ಟ್ ಪೇಲೋಡ್ಗಳಿಗೆ, ಡೀಫಾಲ್ಟ್ OmniRoute ಕಾಂಬೊ ಎಂಜಿನ್ಗಳನ್ನು ಹೀಗೆ ಜೋಡಿಸುತ್ತದೆ:

```txt
RTK -> Caveman
```

ಸಂಯೋಜಿತ ಉಳಿತಾಯವು ಗುಣಾತ್ಮಕವಾಗಿರುತ್ತದೆ, ಸಂಕಲನಾತ್ಮಕವಾಗಿರುವುದಿಲ್ಲ:

```txt
combined = 1 - (1 - RTK ಉಳಿತಾಯ) * (1 - Caveman ಇನ್ಪುಟ್ ಉಳಿತಾಯ)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK ಮತ್ತು Caveman ಎರಡೂ ಒಂದೇ ಇನ್ಪುಟ್/ಕಾಂಟೆಕ್ಸ್ಟ್ ಪೇಲೋಡ್ ಅನ್ನು ಕಡಿಮೆ ಮಾಡಲು ಸಾಧ್ಯವಾದಾಗ ಆ `78-95%` ಸಂಖ್ಯೆಯು ಅನ್ವಯಿಸುತ್ತದೆ.
Caveman ಪ್ರತಿಕ್ರಿಯೆ ಔಟ್ಪುಟ್ ಮೋಡ್ ಪ್ರತ್ಯೇಕವಾಗಿದೆ: ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, Cavemanನ ಸ್ವಂತ ಔಟ್ಪುಟ್ ಉಳಿತಾಯವನ್ನು (`65%`
ಸರಾಸರಿ, `~75%` ಮುಖ್ಯಾಂಶ, `22-87%` ವ್ಯಾಪ್ತಿ) ಬಳಸಿ. ಒಟ್ಟು ಬಿಲ್ಲಿಂಗ್ ಉಳಿತಾಯವು ನಿಮ್ಮ ಪ್ರಾಂಪ್ಟ್/ಔಟ್ಪುಟ್ ಮಿಶ್ರಣವನ್ನು ಅವಲಂಬಿಸಿರುತ್ತದೆ.

### "ಅರ್ಹ" ಎಂದರೆ ನಿಜವಾಗಿ ಏನು

15-95% ಮುಖ್ಯಾಂಶದ ವ್ಯಾಪ್ತಿಯು ನೈಜವಾಗಿದೆ, ಆದರೆ ಅದು **ಪುನರಾವರ್ತಿತ ಅಥವಾ ಅನಗತ್ಯವಾಗಿ ವಿಸ್ತೃತವಾದ** ವಿಷಯಕ್ಕೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ — ಪುನರಾವರ್ತಿತ
ದೋಷ ಸಾಲುಗಳು, ಅದೇ ಎಚ್ಚರಿಕೆಯನ್ನು ಪದೇಪದೇ ಹೊರಹಾಕುವ ಬಿಲ್ಡ್ ಲಾಗ್, ಅತಿಯಾಗಿ ದೊಡ್ಡದಾದ `grep`/ಫೈಲ್-ರೀಡ್ ಡಂಪ್. ಇದರರ್ಥ
ಪ್ರತಿ ವಿನಂತಿಯೂ ಅಷ್ಟೊಂದು ಉಳಿತಾಯ ಮಾಡುತ್ತದೆ ಎಂದಲ್ಲ.

ಪ್ರಾಯೋಗಿಕವಾಗಿ ಪರಿಶೀಲಿಸಲಾಗಿದೆ (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): ಒಂದೇ ರೀತಿಯ 300
ದೋಷ ಸಾಲುಗಳನ್ನು ಹೊಂದಿರುವ Anthropic-ಆಕಾರದ `tool_result` ಬ್ಲಾಕ್ನಲ್ಲಿ `stacked` (RTK + Caveman) ರನ್ ಮಾಡಿದಾಗ
**95.93% ಟೋಕನ್ ಉಳಿತಾಯ / 96.26% ಅಕ್ಷರ ಉಳಿತಾಯ** ದೊರೆಯಿತು — ಇದು ಜಾಹೀರಾತು ಮಾಡಲಾದ
ವ್ಯಾಪ್ತಿಯಲ್ಲೇ ಸ್ಪಷ್ಟವಾಗಿ ಬರುತ್ತದೆ. ಆದರೆ ಸಾಮಾನ್ಯವಾದ, ಪುನರಾವರ್ತನೆಯಿಲ್ಲದ ಸಾಧನ ಔಟ್ಪುಟ್ನಲ್ಲಿ (ಸ್ವಚ್ಛವಾದ `grep` ಹೊಂದಾಣಿಕೆ ಪಟ್ಟಿ,
ಚಿಕ್ಕ ಫೈಲ್ ರೀಡ್, ಸಾಮಾನ್ಯ ಸಂಭಾಷಣಾ ಪಠ್ಯ) ಅದೇ ಪೈಪ್ಲೈನ್ ಅನ್ನು ರನ್ ಮಾಡಿದಾಗ **ಶೂನ್ಯಕ್ಕೆ ಸಮೀಪದ ಉಳಿತಾಯ** ಸರಿಯಾಗಿಯೇ ದೊರೆಯುತ್ತದೆ, ಏಕೆಂದರೆ
ತೆಗೆದುಹಾಕಲು ಯಾವುದೇ ಪುನರಾವರ್ತನೆ ಇರುವುದಿಲ್ಲ ಮತ್ತು ಕೋಡ್ ಬ್ಲಾಕ್ಗಳು, URLಗಳು, ಶೀರ್ಷಿಕೆಗಳು, ಆವೃತ್ತಿಗಳು ಅಥವಾ ALL-CAPS ಸ್ಥಿರಾಂಕ ಐಡೆಂಟಿಫೈಯರ್ಗಳನ್ನು
ತೆಗೆದುಹಾಕುವ ಅಥವಾ ಬದಲಾಯಿಸುವ ಪುನರ್ಬರಹವನ್ನು ಕಳುಹಿಸಲು `validateCompression()` (`validation.ts`) ನಿರಾಕರಿಸುತ್ತದೆ.

ಇದು ನಿರೀಕ್ಷಿತವಾದ, ಸುರಕ್ಷಿತ ನಡವಳಿಕೆಯೇ ಹೊರತು ಬಗ್ ಅಲ್ಲ: ಹೆಚ್ಚಾಗಿ ಸ್ವಚ್ಛ ಫೈಲ್ಗಳನ್ನು ಓದುವ/grep ಮಾಡುವ ಕೋಡಿಂಗ್ ಸೆಷನ್ನಲ್ಲಿ
ಕಂಪ್ರೆಷನ್ ಸಂಪೂರ್ಣವಾಗಿ ಸಕ್ರಿಯವಾಗಿದ್ದರೂ ಒಟ್ಟು ಉಳಿತಾಯ ಸಾಧಾರಣವಾಗಿರುತ್ತದೆ; ಆದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತಿರುವ
ಲೂಪ್ ಅಥವಾ ಅತಿಯಾಗಿ ಸಂದೇಶಗಳನ್ನು ಹೊರಹಾಕುವ ಲಿಂಟರ್ ಎದುರಾಗುವ ಸೆಷನ್ನಲ್ಲಿ ಆ ಟ್ರಾಫಿಕ್ಗೆ ಸಂಪೂರ್ಣ 78-95% ವ್ಯಾಪ್ತಿಯ ಉಳಿತಾಯ ದೊರೆಯುತ್ತದೆ. ಒಂದೇ ಸೆಷನ್ನ
ಕಡಿಮೆ ಒಟ್ಟು ಉಳಿತಾಯದ ಶೇಕಡಾವಾರನ್ನು ಕಂಪ್ರೆಷನ್ ತಪ್ಪಾಗಿ ಕಾನ್ಫಿಗರ್ ಆಗಿದೆ ಎಂಬುದಕ್ಕೆ ಪುರಾವೆಯಾಗಿ ಬಳಸಬೇಡಿ — ಮೊದಲು
ಆಧಾರವಾಗಿರುವ ಸಾಧನ ಔಟ್ಪುಟ್ ನಿಜವಾಗಿಯೂ ಪುನರಾವರ್ತಿತವಾಗಿತ್ತೇ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ.

## ಸಂರಚನೆ

### ಡ್ಯಾಶ್ಬೋರ್ಡ್

`Dashboard → Context & Cache` ಗೆ ನ್ಯಾವಿಗೇಟ್ ಮಾಡಿ:

- **Caveman** — ಮೋಡ್ ಆಯ್ಕೆ, ಭಾಷಾ ಪ್ಯಾಕ್ಗಳು, ಪೂರ್ವವೀಕ್ಷಣೆ ಮತ್ತು ಜಾಗತಿಕ ಡೀಫಾಲ್ಟ್ಗಳು
- **RTK** — ಕಮಾಂಡ್-ಫಿಲ್ಟರ್ ಪೂರ್ವವೀಕ್ಷಣೆ, RTK ಸುರಕ್ಷತಾ ಸೆಟ್ಟಿಂಗ್ಗಳು ಮತ್ತು ಫಿಲ್ಟರ್ ಕ್ಯಾಟಲಾಗ್
- **Compression Combos** — ರೂಟಿಂಗ್ ಕಾಂಬೋಗಳಿಗೆ ನಿಯೋಜಿಸಲಾದ ಹೆಸರಿಸಲಾದ ಎಂಜಿನ್ ಪೈಪ್ಲೈನ್ಗಳು
- **Auto-Trigger Threshold** — ಟೋಕನ್ ಎಣಿಕೆ ಮಿತಿಯನ್ನು ಮೀರಿದಾಗ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಕಂಪ್ರೆಷನ್ ಸಕ್ರಿಯಗೊಳಿಸಿ

### ಪ್ರತಿ-ಕಾಂಬೋ ಓವರ್ರೈಡ್

`Dashboard → Context & Cache → Compression Combos` ನಲ್ಲಿ ರೂಟಿಂಗ್
ಕಾಂಬೋಗೆ ಕಂಪ್ರೆಷನ್ ಕಾಂಬೋ ನಿಯೋಜಿಸಿ:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ಇದರಿಂದ ಪಾವತಿಸಿದ ಸಬ್ಸ್ಕ್ರಿಪ್ಶನ್ಗಳಲ್ಲಿ ಲೈಟ್ ಮೋಡ್ ಅನ್ನು ಉಳಿಸಿಕೊಂಡು, ಉಚಿತ/ಕೋಡಿಂಗ್ ಪ್ರೊವೈಡರ್ಗಳಲ್ಲಿ ಸ್ಟ್ಯಾಕ್ ಮಾಡಲಾದ ಕಂಪ್ರೆಷನ್ ಬಳಸಬಹುದು.

ಈ "Per-Combo Override" ನಿಯೋಜನೆಯು **ರೂಟಿಂಗ್-ಕಾಂಬೋ ಕಂಪ್ರೆಷನ್
ಮೋಡ್** ಓವರ್ರೈಡ್ಗಿಂತ (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ಫೀಲ್ಡ್ನ ಸ್ಕೀಮಾ
`rtk`, `stacked` ಮತ್ತು `omniglyph` ಗಳನ್ನೂ ಸ್ವೀಕರಿಸುತ್ತದೆ) ವಿಭಿನ್ನ ನಿಯಂತ್ರಣವಾಗಿದೆ — ಆ ಓವರ್ರೈಡ್ ಹೆಸರಿಸಲಾದ
ಕಂಪ್ರೆಷನ್-ಕಾಂಬೋ ಪೈಪ್ಲೈನ್ ಅನ್ನು ಆಯ್ಕೆ ಮಾಡುವುದಿಲ್ಲ; ಅದು ಕೇವಲ
`resolveCompressionPlan` ಪರಿಶೀಲಿಸುವ `compressionMode` ಫೀಲ್ಡ್ ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ. ಇದನ್ನು ಕಾಂಬೋ ಕಾರ್ಡ್ನಲ್ಲಿ (`Dashboard → Combos`) ಅಥವಾ
#6760 ರಿಂದ, `Dashboard → Context & Cache → Compression Combos` ನಲ್ಲಿರುವ "Assign to routing" ಪಟ್ಟಿಯಲ್ಲಿ ಪ್ರತಿ ರೂಟಿಂಗ್ ಕಾಂಬೋಗಾಗಿ,
ಮೇಲೆ ದಾಖಲಿಸಿರುವ ಪೈಪ್ಲೈನ್-ನಿಯೋಜನೆ ಚೆಕ್ಬಾಕ್ಸ್ನ ಪಕ್ಕದಲ್ಲೇ ಹೊಂದಿಸಬಹುದು. ಎರಡೂ ಮೇಲ್ಮೈಗಳು ಒಂದೇ `PUT /api/combos/{id}` ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ ನಿರಂತರಗೊಳಿಸಲ್ಪಡುತ್ತವೆ.

### ಪ್ರತಿ-ವಿನಂತಿ ಓವರ್ರೈಡ್

ಒಂದೇ ವಿನಂತಿಗಾಗಿ ಕಂಪ್ರೆಷನ್ ಯೋಜನೆಯನ್ನು ಓವರ್ರೈಡ್ ಮಾಡಲು `x-omniroute-compression` ವಿನಂತಿ ಹೆಡರ್ ಕಳುಹಿಸಿ. ಇದು ಅತ್ಯುನ್ನತ ಆದ್ಯತೆಯನ್ನು ಹೊಂದಿದೆ — ರೂಟಿಂಗ್-ಕಾಂಬೋ ಓವರ್ರೈಡ್, ಸಕ್ರಿಯ ಪ್ರೊಫೈಲ್, ಸ್ವಯಂ-ಟ್ರಿಗರ್ ಮತ್ತು ಪ್ಯಾನೆಲ್ ಡೀಫಾಲ್ಟ್ಗಳನ್ನೆಲ್ಲ ಮೀರಿಸುತ್ತದೆ. ತಿಳಿಯದ ಮೌಲ್ಯಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ (ವಿನಂತಿಯನ್ನು ಎಂದಿಗೂ ತಿರಸ್ಕರಿಸಲಾಗುವುದಿಲ್ಲ) ಮತ್ತು ಜಾಗತಿಕ ಮಾಸ್ಟರ್ ಸ್ವಿಚ್ ಎಲ್ಲವನ್ನೂ ನಿಯಂತ್ರಿಸುತ್ತದೆ: ಜಾಗತಿಕವಾಗಿ ಕಂಪ್ರೆಷನ್ ಆಫ್ ಆಗಿದ್ದರೆ, ಹೆಡರ್ ಅದನ್ನು ಆನ್ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮೌಲ್ಯಗಳು:

| ಮೌಲ್ಯ         | ಪರಿಣಾಮ                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | ಈ ವಿನಂತಿಗೆ ಯಾವುದೇ ಕಂಪ್ರೆಷನ್ ಇಲ್ಲ.                                                                                   |
| `default`     | ಪ್ಯಾನೆಲ್ನಿಂದ ಪಡೆದ Default ಪ್ರೊಫೈಲ್ (ಸಕ್ರಿಯ ಪ್ರೊಫೈಲ್ ಅನ್ನು ನಿರ್ಲಕ್ಷಿಸುತ್ತದೆ). ನಷ್ಟಕಾರಕ ಎಂಜಿನ್ಗಳು ಆಫ್ ಆಗಿಯೇ ಇರುತ್ತವೆ. |
| `safe`        | ಹೆಡರ್ ಬಿಟ್ಟಿರುವಂತೆಯೇ.                                                                                               |
| `allow-lossy` | ಸಾರಾಂಶಗಳು, ಪ್ರಸ್ತುತತೆ ಫಿಲ್ಟರ್ಗಳು ಮತ್ತು ಶೈಲಿ ಮರುಬರಹಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಈ ವಿನಂತಿಯ ಆಪರೇಟರ್ ಯೋಜನೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ.        |
| `engine:<id>` | ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ ಒಂದೇ ಎಂಜಿನ್, ಉದಾ. `engine:rtk`. ಇದು ಆ ಎಂಜಿನ್ಗಾಗಿ ಪ್ರತಿ-ವಿನಂತಿ ಆಯ್ಕೆಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆಯಾಗಿದೆ.          |
| `<combo>`     | ಹೆಸರಿನಿಂದ (ಕೇಸ್-ಇನ್ಸೆನ್ಸಿಟಿವ್) ಮೊದಲು, ನಂತರ ಐಡಿಯಿಂದ ಹೊಂದಿಸಲಾದ ಹೆಸರಿನ ಕಾಂಬೋ.                                          |

`allow-lossy`, `engine:<id>` ಅಥವಾ ಹೆಸರಿನ ಕಾಂಬೋ ಇಲ್ಲದೆ, ನಷ್ಟಕಾರಕ ಎಂಜಿನ್ಗಳನ್ನು ಅನ್ವಯಿಸಲಾಗುವುದಿಲ್ಲ. ನಷ್ಟಕಾರಕ Default, ಸ್ವಯಂ-ಟ್ರಿಗರ್ ಅಥವಾ ರೂಟಿಂಗ್ ಓವರ್ರೈಡ್ ಅನ್ನು ಡೌನ್ಗ್ರೇಡ್ ಮಾಡಿದಾಗ, OmniRoute ಸಂರಚಿಸಲಾದ ಸ್ಟ್ಯಾಕ್ ಮಾಡಿದ ಪೈಪ್ಲೈನ್ನಿಂದ ಗುರುತಿಸಲಾದ ನಷ್ಟರಹಿತ ಹಂತಗಳನ್ನು ಸಂರಚಿಸಲಾದ ಕ್ರಮದಲ್ಲೇ ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ. ಯಾವುದೇ ಸಂರಚಿಸಲಾದ ನಷ್ಟರಹಿತ ಹಂತ ಉಳಿಯದಿದ್ದಾಗ ಮಾತ್ರ ಇದು `session-dedup → lite` ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ.

Settings ಪ್ಯಾನೆಲ್ನ **Effective pipeline** ಪೂರ್ವವೀಕ್ಷಣೆಯು ಸಾಮಾನ್ಯ ಸ್ಥಿತಿಯಲ್ಲಿನ ಯೋಜನೆಯನ್ನು ತೋರಿಸುತ್ತದೆ. ಸ್ವಯಂ-ಟ್ರಿಗರ್ ರನ್ ಆಗಬಹುದಾದಾಗ, ಅದೇ ಪೂರ್ವವೀಕ್ಷಣೆಯು ಅದರ ಷರತ್ತುಬದ್ಧ ಪರಿಣಾಮಕಾರಿ ಪೈಪ್ಲೈನ್ನ್ನೂ ತೋರಿಸುತ್ತದೆ, ಇದರಿಂದ ಪ್ಯಾನೆಲ್ ಮತ್ತು ಹೆಡರ್ರಹಿತ ರನ್ಟೈಮ್ ಪರಿಹಾರವು ಹೊಂದಿಕೆಯಲ್ಲಿ ಉಳಿಯುತ್ತದೆ.

ಅನ್ವಯಿಸಲಾದ ಯೋಜನೆಯು `X-OmniRoute-Compression: <mode>; source=<source>` ಪ್ರತಿಕ್ರಿಯೆ ಹೆಡರ್ನಲ್ಲಿ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ, ಇಲ್ಲಿ `<source>` ಇವುಗಳಲ್ಲಿ ಒಂದಾಗಿರುತ್ತದೆ: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ಅಥವಾ `off`.

### API

```bash
# ಕಂಪ್ರೆಷನ್ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಪಡೆಯಿರಿ
curl http://localhost:20128/api/settings/compression

# ಕಂಪ್ರೆಷನ್ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ನವೀಕರಿಸಿ
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ನಿರ್ದಿಷ್ಟ RTK/stacked ಪೇಲೋಡ್ನ ಪೂರ್ವವೀಕ್ಷಣೆ ಮಾಡಿ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK ಫಿಲ್ಟರ್ ಪ್ಯಾಕ್ಗಳ ಪಟ್ಟಿಯನ್ನು ಪಡೆಯಿರಿ
curl http://localhost:20128/api/context/rtk/filters

# ಐಚ್ಛಿಕ ಕಮಾಂಡ್ ಮೆಟಾಡೇಟಾದೊಂದಿಗೆ RTK ಅನ್ನು ನೇರವಾಗಿ ಪರೀಕ್ಷಿಸಿ
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

- ✅ ಕೋಡ್ ಬ್ಲಾಕ್ಗಳು (ಬೇಲಿಯುಕ್ತ ಮತ್ತು ಇನ್ಲೈನ್)

- ✅ ಐಡೆಂಟಿಫೈಯರ್ಗಳು ಮತ್ತು ಸಂರಕ್ಷಿತ ತಾಂತ್ರಿಕ ಟೋಕನ್ಗಳು
- ✅ ಗಣಿತೀಯ ಅಭಿವ್ಯಕ್ತಿಗಳು
- ✅ ಟೂಲ್/ಫಂಕ್ಷನ್ ಕರೆ ವ್ಯಾಖ್ಯಾನಗಳು

ಪಾಸ್ವರ್ಡ್ಗಳು, ಟೋಕನ್ಗಳು ಮತ್ತು ರಹಸ್ಯಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ.

## ಕೃತಜ್ಞತೆಗಳು

ಸ್ಟ್ಯಾಂಡರ್ಡ್ ಮೋಡ್ನ ಸಂಕುಚನ ನಿಯಮಗಳು **[JuliusBrussee](https://github.com/JuliusBrussee)** ಅವರ **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) — ವೈರಲ್ ಆದ "ಹೆಚ್ಚು ಟೋಕನ್ಗಳನ್ನು ಏಕೆ ಬಳಸಬೇಕು, ಕಡಿಮೆ ಟೋಕನ್ಗಳಿಂದ ಕೆಲಸವಾದಾಗ" ಯೋಜನೆಯಿಂದ ಪ್ರೇರಿತವಾಗಿವೆ. Caveman `~75%` ಕಡಿಮೆ ಔಟ್ಪುಟ್ ಟೋಕನ್ಗಳು, ಬೆಂಚ್ಮಾರ್ಕ್ನಲ್ಲಿ ಸರಾಸರಿ `65%` ಔಟ್ಪುಟ್ ಉಳಿತಾಯ, `22-87%` ಔಟ್ಪುಟ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು `~46%` ಇನ್ಪುಟ್-ಸಂಕುಚನ ಟೂಲ್ ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

RTK ಮೋಡ್ **[RTK AI](https://github.com/rtk-ai)** ಅವರ **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** — ಟರ್ಮಿನಲ್, ಬಿಲ್ಡ್, ಟೆಸ್ಟ್, git ಮತ್ತು ಟೂಲ್-ಔಟ್ಪುಟ್ ಫಿಲ್ಟರಿಂಗ್ಗಾಗಿ ಇರುವ ಉನ್ನತ-ಕಾರ್ಯಕ್ಷಮತೆಯ ಕಮಾಂಡ್-ಔಟ್ಪುಟ್ ಸಂಕುಚನ ಯೋಜನೆಯಿಂದ ಪ್ರೇರಿತವಾಗಿದೆ. RTK `60-90%` ಉಳಿತಾಯವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಅದರ README ಮಾದರಿ ಸೆಷನ್ನಲ್ಲಿ `~80%` ಉಳಿತಾಯವನ್ನು ತೋರಿಸಲಾಗಿದೆ.

## ಸುಧಾರಿತ ಕಂಪ್ರೆಷನ್ ಸಿಸ್ಟಮ್ಸ್

ಮೇಲೆ ವಿವರಿಸಿದ 7 ವಿಧಾನಗಳ ಆಚೆಗೆ (ಮೂಲವು `codex-responses` ಮತ್ತು `omniglyph` ಮೋಡ್ಗಳನ್ನು ಸಹ ಸ್ವೀಕರಿಸುತ್ತದೆ, ಈ ಮಾರ್ಗದರ್ಶಿಯು ಒಳಗೊಳ್ಳುವುದಿಲ್ಲ), ಕೆಳಗಿನ ವಿಭಾಗಗಳು ಆ ಮೋಡ್ಗಳ ಒಳಗೆ ಅಥವಾ ಅದರ ಜೊತೆಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ವೈಶಿಷ್ಟ್ಯಗಳನ್ನು ಒಳಗೊಂಡಿದೆ: ಟೂಲ್ ಫಲಿತಾಂಶ ಸಂಕೋಚನ ಮತ್ತು ಪ್ರಗತಿಶೀಲ ವಯಸ್ಸಾದವು ಆಕ್ರಮಣಕಾರಿ ಎಂಜಿನ್ನ 1 ಮತ್ತು 2 ಹಂತಗಳಾಗಿವೆ (ಆಕ್ರಮಣಕಾರಿ ಮೋಡ್ ಮತ್ತು `aggressive` ಪೈಪ್ಲೈನ್ ಹಂತ), ಸ್ಟ್ಯಾಕ್ನ ಸ್ಟ್ಯಾಕ್ಡ್ ಪೈಪ್ಲೈನ್ ಹೇಗೆ ಚಲಿಸುತ್ತದೆ Cache-Aware Compression `aggressive` ಮತ್ತು `ultra` ಅನ್ನು ಕ್ಯಾಶಿಂಗ್ ಪ್ರೊವೈಡರ್ಗಳಿಗಾಗಿ `standard` ಗೆ ಡೌನ್ಗ್ರೇಡ್ ಮಾಡುತ್ತದೆ, ಮತ್ತು ಕೇವ್ಮ್ಯಾನ್ ಔಟ್ಪುಟ್ ಮೋಡ್ ಮತ್ತು ಔಟ್ಪುಟ್ ಸ್ಟೈಲ್ಗಳು ಸಿಸ್ಟಮ್-ಪ್ರಾಂಪ್ಟ್ ಸೂಚನೆಗಳಾಗಿದ್ದು, ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಆಫ್ ಆಗಿರುತ್ತವೆ, ಅದು ವಿನಂತಿಯನ್ನು ಕುಗ್ಗಿಸುವ ಬದಲು ಮಾದರಿಯ ಔಟ್ಪುಟ್ ಅನ್ನು ರೂಪಿಸುತ್ತದೆ.

### ಕ್ಯಾಷ್-ಅವೇರ್ ಕಂಪ್ರೆಷನ್

ಕೆಲವು ಪೂರೈಕೆದಾರರು (ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶಿಂಗ್ನೊಂದಿಗೆ Anthropic ನಂತಹ) ಬೆಂಬಲ** ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶಿಂಗ್** , ಇದು ವೆಚ್ಚಗಳು ಮತ್ತು ಸುಪ್ತತೆಯನ್ನು ಕಡಿಮೆ ಮಾಡಲು ಪ್ರಾಂಪ್ಟ್ನ ಭಾಗಗಳನ್ನು ಸಂಗ್ರಹಿಸಲು ಅನುವು ಮಾಡಿಕೊಡುತ್ತದೆ. ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವಿಕೆಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಆಕ್ರಮಣಕಾರಿ ಸಂಕೋಚನವನ್ನು ವಾಸ್ತವವಾಗಿ ಮಾಡಬಹುದು** ನೋವುಂಟು ಮಾಡಿದೆ** ಕಾರ್ಯಕ್ಷಮತೆ ಏಕೆಂದರೆ ಇದು ಕ್ಯಾಶ್ ಮಾಡಿದ ಟೋಕನ್ಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ, ಸಂಗ್ರಹವನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ.

`cachingAware.ts` ಮಾಡ್ಯೂಲ್ ಇದನ್ನು ಪರಿಹರಿಸುತ್ತದೆ** ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವ ಸಂದರ್ಭವನ್ನು ಕಂಡುಹಿಡಿಯುವುದು** ಮತ್ತು** ಸಂಕೋಚನ ತಂತ್ರವನ್ನು ಸರಿಹೊಂದಿಸುವುದು** ಅದರಂತೆ.

#### ಇದು ಹೇಗೆ ಕೆಲಸ ಮಾಡುತ್ತದೆ

1. **ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವ ಸಂದರ್ಭವನ್ನು ಪತ್ತೆ ಮಾಡಿ** — `cache_control` ಮಾರ್ಕರ್ಗಳಿಗಾಗಿ ವಿನಂತಿಯ ದೇಹವನ್ನು ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತದೆ
2. **ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವ ಪೂರೈಕೆದಾರರನ್ನು ಗುರುತಿಸಿ** ಗುರಿ ಪೂರೈಕೆದಾರರು ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವಿಕೆಯನ್ನು ಬೆಂಬಲಿಸಿದರೆ — ಪರಿಶೀಲಿಸುತ್ತದೆ
3. **ತಂತ್ರವನ್ನು ಹೊಂದಿಸಿ** — ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವ ಪೂರೈಕೆದಾರರಿಗೆ `aggressive`/`ultra` ಅನ್ನು `standard` ಗೆ ಡೌನ್ಗ್ರೇಡ್ ಮಾಡುತ್ತದೆ
4. **ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡಿ** — ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸಾಮಾನ್ಯವಾಗಿ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಅವುಗಳನ್ನು ಸಂಕುಚಿತಗೊಳಿಸಬೇಡಿ

ಕಾರ್ಯತಂತ್ರದ ಸಹಾಯಕರು ಸಹ `deterministicOnly` ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತಾರೆ, ಆದರೆ ಪ್ಲಾನ್ ಬಿಲ್ಡರ್ ಸ್ಟ್ರ್ಯಾಟಜಿ — ಅನ್ನು ಮಾತ್ರ ಬಳಸುತ್ತಾರೆ, ಕೆಳಗೆ ಯಾವುದೂ ಇಂದು ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಓದುವುದಿಲ್ಲ.

#### ಕೋಡ್ ಉದಾಹರಣೆ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ಯಾವಾಗ ಬಳಸಬೇಕು

ಕ್ಯಾಷ್-ಅವೇರ್ ಕಂಪ್ರೆಷನ್ ಆಗಿದೆ** ಯಾವಾಗಲೂ ಆನ್** — ಯಾವುದೇ ಸಂರಚನೆ ಅಗತ್ಯವಿಲ್ಲ. ಕಂಪ್ರೆಷನ್ ಆನ್ ಆಗಿರುವಾಗ ಅದು ಕಿಕ್ ಆಗುತ್ತದೆ ಮತ್ತು ಗುರಿ ಒದಗಿಸುವವರು ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶಿಂಗ್ ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತಾರೆ (Anthropic, OpenAI, ಇತ್ಯಾದಿ); ಸ್ಪಷ್ಟವಾದ `cache_control` ಮಾರ್ಕರ್ಗಳು ಅಗತ್ಯವಿಲ್ಲ — ಕ್ಯಾಶಿಂಗ್ ಪ್ರೊವೈಡರ್ ಮಾತ್ರ ಡೌನ್ಗ್ರೇಡ್ ಅನ್ನು ಪ್ರಚೋದಿಸುತ್ತದೆ ಮತ್ತು ಮಾರ್ಕರ್ಗಳು ಮಾತ್ರ ಎಂದಿಗೂ ಮಾಡುವುದಿಲ್ಲ (ಮಾರ್ಕರ್ ಡಿಟೆಕ್ಷನ್ ಕ್ಯಾಶ್ ಟೆಲಿಮೆಟ್ರಿಯನ್ನು ನೀಡುತ್ತದೆ, ತಂತ್ರದ ನಿರ್ಧಾರವಲ್ಲ).

OpenRouter `anthropic/*` ಮಾದರಿಗಳಿಗೆ ಮಾತ್ರ ಹಿಡಿದಿಟ್ಟುಕೊಳ್ಳುವ ಪೂರೈಕೆದಾರರಾಗಿ ಎಣಿಕೆ ಮಾಡುತ್ತದೆ: Claude ಕೋಡ್ ವಿನಂತಿಗಳು ತಮ್ಮ `cache_control` ಬ್ರೇಕ್ಪಾಯಿಂಟ್ಗಳನ್ನು (ಹೆಚ್ಚಿನ 4) ಇರಿಸುತ್ತವೆ ಮತ್ತು ಗಾರ್ಡ್ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ರಕ್ಷಿಸುತ್ತದೆ, ಆದರೆ ಪ್ರತಿ ಇತರ OpenRouter ಕುಟುಂಬ (`openai/`, `google/`, `qwen/`, …) ಸ್ಟ್ರಿಪ್ಡ್ ಮತ್ತು ಅನಾವಶ್ಯಕವಾಗಿರುತ್ತದೆ.

### ಪ್ರಗತಿಶೀಲ ವಯಸ್ಸಾದ

ದೀರ್ಘ ಸಂಭಾಷಣೆಗಳು ಅನೇಕ ಸಂದೇಶ ತಿರುವುಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತವೆ, ಆದರೆ ಹಳೆಯ ತಿರುವುಗಳು ಕಡಿಮೆ ಸಂಬಂಧಿತವಾಗುತ್ತವೆ. `progressiveAging.ts` ಮಾಡ್ಯೂಲ್** ತಿರುವು ಅಂತರದಿಂದ ಸಂದೇಶಗಳನ್ನು ಕುಗ್ಗಿಸುತ್ತದೆ** (ಸಂಭಾಷಣೆಯ ಅಂತ್ಯದಿಂದ ದೂರವನ್ನು ಅಳೆಯಲಾಗುತ್ತದೆ). ರವಾನಿಸಲಾದ ಡೀಫಾಲ್ಟ್ಗಳೊಂದಿಗೆ (`verbatim: 2, light: 2, moderate: 3`):

- **ಕೊನೆಯ 2 ತಿರುವುಗಳು (ದೂರ ≤ 2)** : ಮಾತಿನಲ್ಲಿ ಇರಿಸಲಾಗಿದೆ
- **ದೂರ 3** : ಕೇವ್ಮ್ಯಾನ್ ಕಂಪ್ರೆಷನ್ (ಫಿಲ್ಲರ್ ತೆಗೆಯುವಿಕೆ)
- **ದೂರ 4 +** ಸಹಾಯಕ ಸಂದೇಶಗಳ ಸಾರಾಂಶ; ಬಳಕೆದಾರರ ಸಂದೇಶಗಳನ್ನು ಅವುಗಳ ಮೊದಲ ಸಾಲಿಗೆ ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ, 120 ಅಕ್ಷರಗಳಿಗೆ ಮುಚ್ಚಲಾಗಿದೆ; ಇತರ ಪಾತ್ರಗಳನ್ನು ಮುಟ್ಟಲಿಲ್ಲ. ಸಿಸ್ಟಂ ಪ್ರಾಂಪ್ಟ್ಗಳು, ಈಗಾಗಲೇ ವಯಸ್ಸಾದ ಸಂದೇಶಗಳು ಮತ್ತು ಇತ್ತೀಚಿನ ಬಳಕೆದಾರ ಸಂದೇಶವನ್ನು ಯಾವಾಗಲೂ ದೂರವನ್ನು ಲೆಕ್ಕಿಸದೆ ಅಕ್ಷರಶಃ ಇರಿಸಲಾಗುತ್ತದೆ. ಯಾವುದನ್ನೂ ಸಂಪೂರ್ಣವಾಗಿ ಕೈಬಿಡಲಾಗಿಲ್ಲ, ಮತ್ತು `light` ಬ್ಯಾಂಡ್ ರವಾನೆಯಾದ ಡಿಫಾಲ್ಟ್ಗಳೊಂದಿಗೆ ತಲುಪಲಾಗುವುದಿಲ್ಲ (`light` ಸಮಾನವಾಗಿರುತ್ತದೆ `verbatim`).

#### ಕೋಡ್ ಉದಾಹರಣೆ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### ಯಾವಾಗ ಬಳಸಬೇಕು

ಪ್ರಗತಿಶೀಲ ವಯಸ್ಸಾಗಿದೆ** ಯಾವಾಗಲೂ ಆನ್** `aggressive` ಮೋಡ್ — ಗೆ ಇದು `compressAggressive()` ಯ ಹಂತ 2 ಆಗಿದೆ. ಅಲ್ಟ್ರಾ ಮೋಡ್ ಅದನ್ನು ರನ್ ಮಾಡುವುದಿಲ್ಲ. ಇದು ವಿಶೇಷವಾಗಿ ಪರಿಣಾಮಕಾರಿಯಾಗಿದೆ:

- ದೀರ್ಘಾವಧಿಯ ಕೋಡಿಂಗ್ ಅವಧಿಗಳು
- ಬಹು ದಿನದ ಸಂಭಾಷಣೆಗಳು
- ಅನೇಕ ಟೂಲ್ ಕರೆಗಳೊಂದಿಗೆ ಏಜೆಂಟ್ ವರ್ಕ್ಫ್ಲೋಗಳು

### ಕೇವ್ಮ್ಯಾನ್ ಔಟ್ಪುಟ್ ಮೋಡ್

ಕೇವ್ಮ್ಯಾನ್ ಔಟ್ಪುಟ್ ಮೋಡ್ ಸೇರಿಸುತ್ತದೆ** ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ ಸೂಚನೆಗಳು** — ಗಾಗಿ ಮಾದರಿಯನ್ನು ಕೇಳಿದರೆ, `lite` ಮಟ್ಟವು ಪೂರ್ಣ ವಾಕ್ಯಗಳನ್ನು ಇರಿಸುವ ಸಂಕ್ಷಿಪ್ತ ಉತ್ತರಗಳನ್ನು ಕೇಳುತ್ತದೆ, `full` ಅದನ್ನು "ಸ್ಮಾರ್ಟ್ ಕೇವ್ಮ್ಯಾನ್ನಂತೆ ಕಠಿಣವಾಗಿ ಪ್ರತಿಕ್ರಿಯಿಸಲು" ಕೇಳುತ್ತದೆ ಮತ್ತು `ultra` ಟೆಲಿಗ್ರಾಫಿಕ್ ಔಟ್ಪುಟ್ಗಾಗಿ ಕೇಳುತ್ತದೆ; ಸೂಚನೆಗಳು ಮಾತ್ರ ಕೇಳುತ್ತವೆ, ಅವರು ಅದನ್ನು ಖಾತರಿಪಡಿಸುವುದಿಲ್ಲ. ವಿನಂತಿಗಳು ಅವುಗಳನ್ನು `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ಮೂಲಕ ಸ್ವೀಕರಿಸುತ್ತವೆ: `open-sse/handlers/chatCore.ts` ಮೊದಲು ಬ್ಯಾಕ್-ಕಾಂಪ್ಯಾಟ್ ಶಿಮ್ನೊಂದಿಗೆ ಆಯ್ಕೆಯನ್ನು ಪರಿಹರಿಸುತ್ತದೆ ( `open-sse/services/compression/outputStyles/backCompat.ts` ನಲ್ಲಿ`resolveOutputStyleSelection()` ), ಇದು `outputStyles` ಖಾಲಿಯಾಗಿರುವಾಗ, `cavemanOutputMode.intensity` ನಲ್ಲಿ `terse-prose` ಔಟ್ಪುಟ್ ಶೈಲಿಗೆ ಸಕ್ರಿಯಗೊಳಿಸಲಾದ `cavemanOutputMode` ಅನ್ನು ನಕ್ಷೆ ಮಾಡುತ್ತದೆ (ಕೆಳಗೆ ಬ್ಯಾಕ್-ಕಂಪ್ಯಾಟ್ ಅನ್ನು ನೋಡಿ); ಖಾಲಿ ಅಲ್ಲದ `outputStyles` ಆಯ್ಕೆಯನ್ನು ಹಾಗೆಯೇ ಬಳಸಲಾಗುತ್ತದೆ, ಮತ್ತು `cavemanOutputMode.enabled` ಮತ್ತು `intensity` ನಂತರ ಯಾವುದೇ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ, ಆದರೆ ಅದರ `autoClarity` ಟಾಗಲ್ ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ. `outputMode.ts` ಸೂಚನಾ ಪಠ್ಯಗಳನ್ನು (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), ವಿಷಯ ಬೈಪಾಸ್ ಮತ್ತು ಇಂಜೆಕ್ಷನ್ ಬಳಸುವ ಪ್ಲೇಸ್ಮೆಂಟ್ ಸಹಾಯಕವನ್ನು ಹೊಂದಿದೆ; ತನ್ನದೇ ಆದ `applyCavemanOutputMode()` ಇಂಜೆಕ್ಟರ್ ಯಾವುದೇ ಉತ್ಪಾದನಾ ಕರೆಯನ್ನು ಹೊಂದಿಲ್ಲ.

#### ಇದು ಹೇಗೆ ಕೆಲಸ ಮಾಡುತ್ತದೆ

ಈ ಮೋಡ್ ಇನ್ಪುಟ್ ಅನ್ನು ಕುಗ್ಗಿಸುವುದಿಲ್ಲ. ಇದು ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ಗೆ ಸೂಚನಾ ಬ್ಲಾಕ್ ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಕೆಳಗೆ ಇಂಜೆಕ್ಷನ್ ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ನೋಡಿ), ಮತ್ತು ವಿನಂತಿಗಾಗಿ ಆಯ್ಕೆಮಾಡಿದ ಯಾವುದೇ ಇನ್ಪುಟ್ ಕಂಪ್ರೆಷನ್ ಮೋಡ್ ನಂತರವೂ ಚಲಿಸುತ್ತದೆ, ಈಗ ಬ್ಲಾಕ್ ಅನ್ನು ಹೊಂದಿರುವ ದೇಹದಲ್ಲಿ. ಪ್ರತಿ ಹಂತವು ಕೊನೆಗೊಳ್ಳುವ ಹಂಚಿಕೆಯ ಗಡಿಗಳ ಷರತ್ತಿನ ಮುಂದೆ, ಇಂಗ್ಲಿಷ್ `full` ಮಟ್ಟವು ಓದುತ್ತದೆ:

> "ಸ್ಮಾರ್ಟ್ ಕೇವ್ಮ್ಯಾನ್ನಂತೆ ಕಠಿಣವಾಗಿ ಪ್ರತಿಕ್ರಿಯಿಸಿ. ಡ್ರಾಪ್ ಲೇಖನಗಳು (a/an/the), ಫಿಲ್ಲರ್ (just/really/basically/actually/simply), ಪ್ಲೆಸೆಂಟ್ರೀಸ್, ಹೆಡ್ಜಿಂಗ್. ತುಣುಕುಗಳು OK. ಸಣ್ಣ ಸಮಾನಾರ್ಥಕಗಳು (ದೊಡ್ಡದು ವಿಸ್ತಾರವಾಗಿಲ್ಲ, ಫಿಕ್ಸ್ ಮಾಡಿಲ್ಲ) ಎಲ್ಲಾ ತಾಂತ್ರಿಕ ವಸ್ತು, ಕೋಡ್, ದೋಷಗಳು, URLs, ಗುರುತಿಸುವಿಕೆಗಳನ್ನು ನಿಖರವಾಗಿ ಇರಿಸಿ."

ಇದು ವಿಶೇಷವಾಗಿ ಉತ್ತಮವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ:

- ಕೋಡ್ ಉತ್ಪಾದನೆ (ಟರ್ಸರ್ ಔಟ್ಪುಟ್ = ಕಡಿಮೆ ಟೋಕನ್ಗಳು)
- ತ್ವರಿತ ಪ್ರಶ್ನೋತ್ತರ (ವಿಸ್ತೃತ ವಿವರಣೆಗಳ ಅಗತ್ಯವಿಲ್ಲ)
- ಬ್ಯಾಚ್ ಸಂಸ್ಕರಣೆ (ಗರಿಷ್ಠ ಥ್ರೋಪುಟ್)

#### ಯಾವಾಗ ಬಳಸಬೇಕು

ಕೇವ್ಮ್ಯಾನ್ ಔಟ್ಪುಟ್ ಮೋಡ್ ಆಗಿದೆ** ಆಯ್ಕೆ** . ಕಂಪ್ರೆಷನ್ ಆನ್ನೊಂದಿಗೆ (`enabled: true`, ಕಂಪ್ರೆಷನ್ ಸೆಟ್ಟಿಂಗ್ಗಳ ಪುಟದಲ್ಲಿ ಮಾಸ್ಟರ್ ಟಾಗಲ್), ಅದನ್ನು `cavemanOutputMode.enabled` ನೊಂದಿಗೆ ಆನ್ ಮಾಡಿ; `intensity` ಪಿಕ್ಸ್ `lite`, `full` ಅಥವಾ `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ಸಂಕೋಚನ ಸಂಯೋಜನೆ** ಔಟ್ಪುಟ್ ಮೋಡ್** ಟಾಗಲ್ (`outputMode`, `outputModeIntensity` ನಲ್ಲಿನ ಮಟ್ಟ) ಕಾಂಬೊ ಅನ್ವಯಿಸುವ ವಿನಂತಿಗಳಿಗೆ ಅದೇ ಸ್ವಿಚ್ ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ ಮತ್ತು `omniroute_set_compression_engine` MCP ಉಪಕರಣವು ಅದರ ಬೂಲಿಯನ್ `outputMode` ಆರ್ಗ್ಯುಮೆಂಟ್ ಮೂಲಕ ಅದನ್ನು ಬರೆಯುತ್ತದೆ. ಖಾಲಿ ಅಲ್ಲದ `outputStyles` ಆಯ್ಕೆಯು ಈ ಸ್ವಿಚ್ಗಿಂತ ಆದ್ಯತೆಯನ್ನು ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ, ಸಕ್ರಿಯಗೊಳಿಸಲಾಗುತ್ತಿದೆ** ಕಟುವಾದ ಗದ್ಯ** ಔಟ್ಪುಟ್ ಶೈಲಿಯು ಅದೇ ಬ್ಲಾಕ್ ಅನ್ನು ಚುಚ್ಚುತ್ತದೆ (ಕೆಳಗಿನ ಔಟ್ಪುಟ್ ಶೈಲಿಗಳನ್ನು ನೋಡಿ).

ಪ್ರತಿಯೊಂದು ಶೈಲಿಯು ಮೂರು ತೀವ್ರತೆಯ ಹಂತಗಳನ್ನು — `lite`, `full`, `ultra` — ರವಾನಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಹಂತವು ಹಂಚಿದ ಗಡಿಗಳ ಷರತ್ತು ( `outputMode.ts` ನಲ್ಲಿ`SHARED_BOUNDARIES` ) ನೊಂದಿಗೆ ಕೊನೆಗೊಳ್ಳುತ್ತದೆ, ಇದು ಕೋಡ್ ಬ್ಲಾಕ್ಗಳು, ಫೈಲ್ ಪಾತ್ಗಳು, ಆಜ್ಞೆಗಳು, ದೋಷಗಳು ಮತ್ತು URLs ನಿಖರವಾಗಿ ಇರಿಸುತ್ತದೆ. `terse-prose` ಮತ್ತು `terse-cjk` ಮಟ್ಟದ ಪಠ್ಯಗಳು ಆ ಪಟ್ಟಿಗೆ ಗುರುತಿಸುವಿಕೆಗಳನ್ನು ಸೇರಿಸುತ್ತವೆ.

`terse-cjk` ಎರಡು ಸ್ಥಳಗಳಲ್ಲಿ `zh` ಗೆ ಲೊಕೇಲ್-ಗೇಟ್ ಆಗಿದೆ. ಸಂಕೋಚನ ಸೆಟ್ಟಿಂಗ್ಗಳ ಪುಟವು ಡ್ಯಾಶ್ಬೋರ್ಡ್ UI ಭಾಷೆ ಚೈನೀಸ್ ಆಗಿರುವಾಗ ಮಾತ್ರ ಅದರ ಸಾಲನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ (`zh-CN` ಅಥವಾ `zh-TW`), ಮತ್ತು ವಿನಂತಿಯ ಪರಿಹರಿಸಲಾದ ಭಾಷೆ (ಕೆಳಗಿನ ಭಾಷೆಯ ಆಯ್ಕೆಯನ್ನು ನೋಡಿ) `zh` ಆಗಿದ್ದಾಗ ಮಾತ್ರ `applyOutputStyles()` ಅದನ್ನು ಚುಚ್ಚುತ್ತದೆ. ಸಾಲನ್ನು ಮರೆಮಾಡುವುದು ಉಳಿಸಿದ `terse-cjk` ಆಯ್ಕೆಯನ್ನು ತೆರವುಗೊಳಿಸುವುದಿಲ್ಲ: ಸೆಟ್ಟಿಂಗ್ಗಳು API ಯಾವುದೇ ಶೈಲಿ ಐಡಿಯನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು ಪುಟದಲ್ಲಿ ಇತರ ಶೈಲಿಗಳನ್ನು ಉಳಿಸುವುದರಿಂದ ಅದನ್ನು ಇರಿಸುತ್ತದೆ. ವಿನಂತಿಯ ಸಮಯದಲ್ಲಿ, `applyOutputStyles()` ಭಾಷಾ ಪರಿಶೀಲನೆಯು ಏಕೈಕ ಲೊಕೇಲ್ ಗೇಟ್ ಆಗಿದೆ.

#### ಇಂಜೆಕ್ಷನ್ ಹೇಗೆ ಕೆಲಸ ಮಾಡುತ್ತದೆ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ಕ್ಯಾಟಲಾಗ್ ವಿರುದ್ಧ ಆಯ್ಕೆಯನ್ನು ಪರಿಹರಿಸುತ್ತದೆ (ಅಜ್ಞಾತ ಐಡಿಗಳು ಮತ್ತು ಲೊಕೇಲ್-ಹೊಂದಾಣಿಕೆಯಿಲ್ಲದ ಶೈಲಿಗಳನ್ನು ಕೈಬಿಡಲಾಗಿದೆ, ಎಂದಿಗೂ ದೋಷ; ಯಾವುದೇ ಶೈಲಿಯನ್ನು ಪರಿಹರಿಸದ ಆಯ್ಕೆಯು ದೇಹವನ್ನು ಬದಲಾಗದೆ ಬಿಡುತ್ತದೆ, `no_styles` ಎಂದು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ), ಆಯ್ದ ಸೂಚನೆಗಳನ್ನು ಕ್ಯಾಟಲಾಗ್ ಕ್ರಮದಲ್ಲಿ ಸಂಯೋಜಿಸುತ್ತದೆ, ಗಡಿ ಷರತ್ತುಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ** ಒಮ್ಮೆ** (ಜೊತೆಗೆ ಸುರಕ್ಷತಾ ಷರತ್ತು, `SAFETY_BOUNDARIES` ಅಥವಾ ಅದರ ಅನುವಾದ, `less-code` ಅಥವಾ `ponytail` ಅನ್ನು ಆಯ್ಕೆ ಮಾಡಿದಾಗ), ಮತ್ತು ಬ್ಲಾಕ್ ಅನ್ನು ಒಂದೇ ಐಡೆಂಪೊಟೆನ್ಸಿ ಮಾರ್ಕರ್ (`[OmniRoute Output Styles]`) ನೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಮರು-ಅನ್ವಯಿಸುವುದು ಯಾವುದೇ-ಆಪ್ ಆಗಿದೆ. ಪರಿಹರಿಸಿದ ಭಾಷೆ (ಕೆಳಗಿನ ಭಾಷೆಯ ಆಯ್ಕೆಯನ್ನು ನೋಡಿ) ಅನುವಾದವನ್ನು ಹೊಂದಿರುವಾಗ, ಇಂಗ್ಲಿಷ್ ಬದಲಿಗೆ ಸ್ಥಳೀಯ ಸೂಚನೆಯನ್ನು ಚುಚ್ಚಲಾಗುತ್ತದೆ.

ಖಾಲಿ ಅಲ್ಲದ `messages` ಅರೇ ಹೊಂದಿರುವ ದೇಹದಲ್ಲಿ, ವಿಷಯ ಬೈಪಾಸ್ಗಿಂತ ಮೊದಲು ಐಡೆಂಪೊಟೆನ್ಸಿ ಚೆಕ್ ರನ್ ಆಗುತ್ತದೆ: `[OmniRoute Output Styles]` ಮಾರ್ಕರ್ ಈಗಾಗಲೇ ಉನ್ನತ ಮಟ್ಟದ `system` ಕ್ಷೇತ್ರದಲ್ಲಿರುವಾಗ (ಸ್ಟ್ರಿಂಗ್ ಅಥವಾ ಕಂಟೆಂಟ್-ಬ್ಲಾಕ್ ಅರೇ) ಅಥವಾ ಸ್ಟ್ರಿಂಗ್ ವಿಷಯದೊಂದಿಗೆ ಸಿಸ್ಟಮ್ ಸಂದೇಶದಲ್ಲಿ, ದೇಹವು ಬದಲಾಗದೆ ಉಳಿದಿದೆ `already_applied` ಮತ್ತು ಯಾವುದೇ ಕೀವರ್ಡ್ ರನ್ ಆಗುವುದಿಲ್ಲ. ಇಲ್ಲದಿದ್ದರೆ ಕಂಟೆಂಟ್ ಬೈಪಾಸ್ (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) ಕೊನೆಯ ಮೂರು ಸಂದೇಶಗಳ ಪಠ್ಯವನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ, ಅವುಗಳ ಪಾತ್ರ ಏನೇ ಇರಲಿ ಮತ್ತು ಆ ಪಠ್ಯವು ಅದರ ಭದ್ರತೆ, ಬದಲಾಯಿಸಲಾಗದ ಕ್ರಿಯೆ ಅಥವಾ ಸ್ಪಷ್ಟೀಕರಣದ ಕೀವರ್ಡ್ಗಳು ಅಥವಾ ಆರ್ಡರ್ `deploy` ಸೆನ್ಸಿಟಿವ್ ಸೀಕ್ವೆನ್ಸ್ಗೆ ಹೊಂದಿಕೆಯಾದಾಗ ಸಂಪೂರ್ಣ ತಿರುವಿನ ಶೈಲಿಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ: `first`, `then`, `after that`, `before` ಒಳಗೆ `delete`, `drop`, `migrate`, `rollback` ಅಥವಾ `backup` ಮೂಲಕ `release` ಅಕ್ಷರಗಳು. ಈ ಸಮಯದಲ್ಲಿ ಬೈಪಾಸ್ ಸಾಗುತ್ತದೆ** ಸ್ವಯಂ ಸ್ಪಷ್ಟತೆ ಬೈಪಾಸ್** ಟಾಗಲ್ (`cavemanOutputMode.autoClarity`, ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಆನ್) ಆನ್ ಆಗಿದೆ; ಟಾಗಲ್ ಆಫ್ ಮಾಡುವುದರಿಂದ ಕೀವರ್ಡ್ ಚೆಕ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

ಬೈಪಾಸ್ ಮೂಲಕ ತಿರುಗಲು ಅನುಮತಿಸಿದಾಗ, `placeSystemInstruction()` (ಅದೇ ಫೈಲ್), ಅದು ಎಂದಿಗೂ ಹೊಸ `messages[0]` ರಚಿಸುವುದಿಲ್ಲ, ಬ್ಲಾಕ್ ಅನ್ನು ಇದು ಕಂಡುಕೊಳ್ಳುವ ಮೊದಲನೆಯದರಲ್ಲಿ ಇರಿಸುತ್ತದೆ:

1. ಸ್ಟ್ರಿಂಗ್ ವಿಷಯದೊಂದಿಗೆ ಪ್ರಮುಖ ಸಿಸ್ಟಮ್ ಸಂದೇಶ: ಬ್ಲಾಕ್ ಅನ್ನು ಅದರ ಪಠ್ಯದ ನಂತರ ಸೇರಿಸಲಾಗಿದೆ.
2. ಉನ್ನತ ಮಟ್ಟದ `system` ಕ್ಷೇತ್ರ: ಸ್ಟ್ರಿಂಗ್ನ ಪಠ್ಯದ ನಂತರ ಬ್ಲಾಕ್ ಅನ್ನು ಸೇರಿಸಲಾಗುತ್ತದೆ ಅಥವಾ ವಿಷಯ-ಬ್ಲಾಕ್ ಅರೇಗೆ ಹೊಸ ಪಠ್ಯ ಬ್ಲಾಕ್ನಂತೆ ಸೇರಿಸಲಾಗುತ್ತದೆ.
3. ಸ್ಟ್ರಿಂಗ್ ವಿಷಯದೊಂದಿಗೆ ಮೊದಲ ನಂತರದ ಸಿಸ್ಟಮ್ ಸಂದೇಶ: ಬ್ಲಾಕ್ ಅನ್ನು ಅದರ ಪಠ್ಯದ ನಂತರ ಸೇರಿಸಲಾಗಿದೆ.
4. ಮೇಲಿನ ಯಾವುದೂ ಅಲ್ಲ: ಬ್ಲಾಕ್ `messages` ನ ಕೊನೆಯಲ್ಲಿ ಹೊಸ ಸಿಸ್ಟಮ್ ಸಂದೇಶಕ್ಕೆ ಹೋಗುತ್ತದೆ.

`messages` ಅರೇ ಇಲ್ಲದ ದೇಹದಲ್ಲಿ (ಅಥವಾ ಖಾಲಿ ಒಂದರ ಜೊತೆಗೆ), ಯಾವುದೇ ವಿಷಯ ಬೈಪಾಸ್ ರನ್ ಆಗುವುದಿಲ್ಲ ಮತ್ತು ಉನ್ನತ ಮಟ್ಟದ `system` ಕ್ಷೇತ್ರವನ್ನು ಸಮಾಲೋಚಿಸಲಾಗುವುದಿಲ್ಲ. ಸ್ಟ್ರಿಂಗ್ `instructions` ಕ್ಷೇತ್ರದ ಪಠ್ಯದ ನಂತರ ಬ್ಲಾಕ್ ಅನ್ನು ಲಗತ್ತಿಸಲಾಗಿದೆ, ಆ ಕ್ಷೇತ್ರವು ಈಗಾಗಲೇ `[OmniRoute Output Styles]` ಮಾರ್ಕರ್ ಅನ್ನು ಹೊಂದಿರದ ಹೊರತು, ಈ ಸಂದರ್ಭದಲ್ಲಿ ದೇಹವು `already_applied` ನಂತೆ ಬದಲಾಗದೆ ಉಳಿದಿದೆ. ದೇಹವು ಯಾವುದೇ ಸ್ಟ್ರಿಂಗ್ `instructions` ಕ್ಷೇತ್ರವನ್ನು ಹೊಂದಿರದಿದ್ದಾಗ ಆದರೆ `input` (ಒಂದು ಸ್ಟ್ರಿಂಗ್ ಅಥವಾ ಅರೇ) ಅನ್ನು ಹೊಂದಿರುವಾಗ, ಬ್ಲಾಕ್ `instructions` ಆಗುತ್ತದೆ, ಇದು ಯಾವುದೇ ಸ್ಟ್ರಿಂಗ್ ಅಲ್ಲದ ಮೌಲ್ಯವನ್ನು ಬದಲಿಸುತ್ತದೆ. ಸ್ಟ್ರಿಂಗ್ `instructions` ಕ್ಷೇತ್ರ ಅಥವಾ ಸ್ಟ್ರಿಂಗ್ ಅಥವಾ ಅರೇ `input` ಇಲ್ಲದ ದೇಹವನ್ನು ಬದಲಾಗದೆ ಬಿಡಲಾಗುತ್ತದೆ ಮತ್ತು `no_messages` ಎಂದು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ.

#### ಸಕ್ರಿಯಗೊಳಿಸುವುದು ಹೇಗೆ

ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ:** ಸಂಕೋಚನ ಸಂದರ್ಭ → ಸಂಕೋಚನ ಸೆಟ್ಟಿಂಗ್ಗಳು** (`/dashboard/context/settings`), ಔಟ್ಪುಟ್ ಶೈಲಿಗಳ ವಿಭಾಗ: on/off ಟಾಗಲ್ ಮತ್ತು ಲೆವೆಲ್ ಸೆಲೆಕ್ಟರ್ನೊಂದಿಗೆ ಪ್ರತಿ ಶೈಲಿಗೆ ಒಂದು ಸಾಲು. ಕಂಪ್ರೆಷನ್ ಆನ್ ಆಗಿರುವಾಗ ಶೈಲಿಗಳು ಇಂಜೆಕ್ಟ್ ಆಗುತ್ತವೆ (ಪುಟದ ಮಾಸ್ಟರ್ ಟಾಗಲ್, `enabled`). ದಿ** ಸ್ವಯಂ ಸ್ಪಷ್ಟತೆ ಬೈಪಾಸ್** ಟಾಗಲ್ ಆನ್ ಆಗಿದೆ** ಗುಹಾನಿವಾಸಿ** ಪುಟ (`/dashboard/context/caveman`), ಅದರಲ್ಲಿ** ಔಟ್ಪುಟ್ ಮೋಡ್** ಕಾರ್ಡ್. ಪ್ರೋಗ್ರಾಮಿಕ್ ಆಗಿ, ಕಂಪ್ರೆಷನ್ ಕಾನ್ಫಿಗರೇಶನ್ ಆಯ್ಕೆಯನ್ನು ಹೀಗೆ ಮುಂದುವರಿಸುತ್ತದೆ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ಬ್ಯಾಕ್-ಕಂಪ್ಯಾಟ್: `outputStyles` ಖಾಲಿಯಾಗಿರುವಾಗ, ಲೆಗಸಿ `cavemanOutputMode.enabled` ನಕ್ಷೆಗಳನ್ನು `cavemanOutputMode.intensity` ನಲ್ಲಿ `terse-prose` ಗೆ ಹೊಂದಿಸುತ್ತದೆ. ಬ್ಲಾಕ್ ನಂತರ `[OmniRoute Output Styles]` ಮಾರ್ಕರ್ನೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ, ಅಲ್ಲಿ ಲೆಗಸಿ `applyCavemanOutputMode()` ಇಂಜೆಕ್ಟರ್ `[OmniRoute Caveman Output Mode]` ಎಂದು ಬರೆಯುತ್ತದೆ. ಮಾರ್ಕರ್ನ ಕೆಳಗೆ, ಪಠ್ಯವು en, pt-BR, es, de, fr, it, ru, id ಮತ್ತು vi ನಲ್ಲಿ ಲೆಗಸಿ ಇಂಜೆಕ್ಷನ್ಗೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ; ja ಮತ್ತು zh ನಲ್ಲಿ ಇದು ಗಡಿಗಳ ಷರತ್ತಿನ ಮೊದಲು ಒಂದು ಹೆಚ್ಚುವರಿ ಜಾಗವನ್ನು ಹೊಂದಿರುತ್ತದೆ. `terse-prose` ಅನ್ನು pt-BR, es, de, fr, it, ru, zh, ja, id ಮತ್ತು vi ಎಂದು ಅನುವಾದಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ `hu` ಅನ್ನು ಪರಿಹರಿಸಿದ ಭಾಷೆಯ ವಿನಂತಿಯು ಇಂಗ್ಲಿಷ್ ಪಠ್ಯವನ್ನು ಪಡೆಯುತ್ತದೆ, ಅಲ್ಲಿ ಪರಂಪರೆ ಇಂಜೆಕ್ಟರ್ ಅದರ ಹಂಗೇರಿಯನ್ ಒಂದನ್ನು ಬಳಸಿದೆ.

ಔಟ್ಪುಟ್-ಶೈಲಿಯ ಭಾಷಾ ಆಯ್ಕೆ ( `outputStyles/apply.ts` ನಲ್ಲಿ`resolveOutputStyleLanguage()` ): `languageConfig.enabled` ಆನ್ನೊಂದಿಗೆ, `autoDetect` ವಿನಂತಿಯ `messages` ರಚನೆಯಲ್ಲಿ ಪಠ್ಯವನ್ನು ಹೊಂದಿರುವ ಇತ್ತೀಚಿನ ಬಳಕೆದಾರ ಸಂದೇಶವನ್ನು ಮಾದರಿ ಮಾಡುತ್ತದೆ (ಸ್ಟ್ರಿಂಗ್ ವಿಷಯ, ಅಥವಾ ಅದರ ವಿಷಯ ಭಾಗಗಳ `text` ) ಮತ್ತು ಅದರ ಮೇಲೆ ಕೇವ್ಮ್ಯಾನ್ ಎಂಜಿನ್ನ ಡಿಟೆಕ್ಟರ್ (`detectCompressionLanguage()`) ಅನ್ನು ರನ್ ಮಾಡುತ್ತದೆ. ಡಿಟೆಕ್ಟರ್ ಹ್ಯಾನ್ ಅಕ್ಷರಗಳೊಂದಿಗೆ ಪಠ್ಯಕ್ಕಾಗಿ `zh` ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಮತ್ತು ಕಾನಾ ಇಲ್ಲ; ಇಲ್ಲದಿದ್ದರೆ ಅದು `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` ಮತ್ತು `id` ಗಳಲ್ಲಿ ಯಾವುದು ಹೆಚ್ಚು ಸುಳಿವು ಹೊಂದಿಕೆಗಳನ್ನು ಹೊಂದಿದೆ ಎಂಬುದನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಮತ್ತು `en` ಯಾವುದೇ — ಪಠ್ಯಕ್ಕೆ ಹೊಂದಿಕೆಯಾಗದಿದ್ದಲ್ಲಿ `defaultLanguage` `vi` ಇಂಗ್ಲಿಷ್ ಸಿಗುವುದಿಲ್ಲ, ಆದರೆ `vi` ಶೈಲಿಯು ಎಂದಿಗೂ ಪತ್ತೆಹಚ್ಚುವುದಿಲ್ಲ. ಪ್ರತಿಕ್ರಿಯೆಗಳ API ದೇಹವು ಅದರ ತಿರುವುಗಳನ್ನು `input` ನಲ್ಲಿ ಇರಿಸುತ್ತದೆ, ಅದು ಮಾದರಿಯಾಗಿಲ್ಲ, ಆದ್ದರಿಂದ ಅದು `defaultLanguage` ಪಡೆಯುತ್ತದೆ, ನಂತರ ಇಂಗ್ಲಿಷ್. `messages` ನಲ್ಲಿ ಯಾವುದೇ ಬಳಕೆದಾರ ಸಂದೇಶವು ಪಠ್ಯವನ್ನು ಹೊಂದಿಲ್ಲದಿದ್ದರೆ ಅಥವಾ `autoDetect` ಆಫ್ನೊಂದಿಗೆ, `defaultLanguage` ಅನ್ವಯಿಸುತ್ತದೆ, ನಂತರ ಇಂಗ್ಲಿಷ್. `languageConfig.enabled` ಆಫ್ನೊಂದಿಗೆ, ಸಂಕೋಚನ ಸಂಯೋಜನೆಯು ವಿನಂತಿಗೆ ಅನ್ವಯಿಸದ ಹೊರತು ಭಾಷೆ ಇಂಗ್ಲಿಷ್ — ಆಗಿರುತ್ತದೆ (ವಿನಂತಿಯ ರೂಟಿಂಗ್ ಕಾಂಬೊಗೆ ನಿಯೋಜಿಸಲಾದ ಕಾಂಬೊ, ಅಥವಾ ಡೀಫಾಲ್ಟ್ ಕಂಪ್ರೆಷನ್ ಕಾಂಬೊ chatCore ಅಂತರ್ನಿರ್ಮಿತ ಸ್ಟ್ಯಾಕ್ ಮಾಡಿದ ಪೈಪ್ಲೈನ್ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ): ಕಾಂಬೊವನ್ನು ಅನ್ವಯಿಸುವುದರಿಂದ `languageConfig.enabled` ಪ್ಯಾಕ್ನಿಂದ `defaultLanguage` ಉಳಿಸುತ್ತದೆ ಇದು ಕಾಂಬೊ ಪ್ಯಾಕ್ಗಳಲ್ಲಿ ಒಂದಾಗಿದ್ದರೆ, ಇಲ್ಲದಿದ್ದರೆ ಕಾಂಬೊದ ಮೊದಲ ಪ್ಯಾಕ್, `en` ಗೆ ಡೀಫಾಲ್ಟ್ ಆಗಿರುತ್ತದೆ, ಆದರೆ ಉಳಿಸಿದ `autoDetect` (ಡೀಫಾಲ್ಟ್ ಆಗಿ) ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ. ಕೇವ್ಮ್ಯಾನ್ ಇನ್ಪುಟ್ ಎಂಜಿನ್ ತನ್ನ ನಿಯಮ-ಪ್ಯಾಕ್ ಭಾಷೆಯನ್ನು ಪ್ರತಿ ಪಠ್ಯ ಭಾಗಕ್ಕೆ ವಿಭಿನ್ನವಾಗಿ — ಆಯ್ಕೆ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸ್ವಯಂ-ಪತ್ತೆಹಚ್ಚುವಿಕೆಯೊಂದಿಗೆ, `enabledPacks` ನಲ್ಲಿ ಗೇಟ್ ಮಾಡಲಾಗಿದೆ.

ಶೈಲಿಯ × ಭಾಷಾ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು `tests/unit/compression/output-styles-i18n-matrix.test.ts` ನಿಂದ ಪಿನ್ ಮಾಡಲಾಗಿದೆ: ಪ್ರತಿ ಕ್ಯಾಟಲಾಗ್ ಶೈಲಿಗೆ ಪರೀಕ್ಷೆಯ `BASELINE_LANGUAGES` ನಲ್ಲಿ ನಮೂದು ಅಗತ್ಯವಿದೆ; ಲೊಕೇಲ್-ಗೇಟೆಡ್ ಅಲ್ಲದ ಶೈಲಿಯು pt-BR ಅನುವಾದವನ್ನು ರವಾನಿಸಬೇಕು (ಲೋಕೇಲ್-ಗೇಟೆಡ್ `terse-cjk` ಈ ನಿಯಮದಿಂದ ವಿನಾಯಿತಿ ಪಡೆದಿದೆ) ಅದನ್ನು `KNOWN_ENGLISH_ONLY` ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡದ ಹೊರತು, ಯಾವುದೇ ಅನುವಾದಗಳಿಲ್ಲದ ಶೈಲಿಗಳನ್ನು ಮಾತ್ರ ಹೊಂದಿರಬಹುದು — ಯಾವುದೇ ಅನುವಾದವನ್ನು ಹೊಂದಿರುವ ಪಟ್ಟಿ ಮಾಡಲಾದ ಶೈಲಿಯು ಪರೀಕ್ಷೆಯಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; ಮತ್ತು ಅದರ `BASELINE_LANGUAGES` ನಮೂದು ಪಟ್ಟಿ ಮಾಡುವ ಭಾಷೆಯನ್ನು ಕಳೆದುಕೊಂಡಾಗ ಶೈಲಿಯು ಪರೀಕ್ಷೆಯಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಶೈಲಿಯನ್ನು ಸೇರಿಸಲು, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) ನೋಡಿ.

### ಟೂಲ್ ಫಲಿತಾಂಶ ಸಂಕುಚನ

`open-sse/services/compression/toolResultCompressor.ts` ನಲ್ಲಿನ `compressToolResult()` ಟೂಲ್-ಫಲಿತಾಂಶದ ಪಠ್ಯವನ್ನು ಸಂಕುಚಿತಗೊಳಿಸುತ್ತದೆ** 5 ತಂತ್ರಗಳು** . ಇದು ಈ ಕ್ರಮದಲ್ಲಿ ಅವುಗಳನ್ನು ಪ್ರಯತ್ನಿಸುತ್ತದೆ, ಮತ್ತು ಮೊದಲ ಸಕ್ರಿಯಗೊಳಿಸಿದ ಕಾರ್ಯತಂತ್ರವು ಅದರ ಚೆಕ್ ಅನ್ನು ಹೊಂದುವ ವಿಷಯವು ಫಲಿತಾಂಶವನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ:

1. **`fileContent`** : ಪ್ರಮುಖ ಇಂಡೆಂಟೇಶನ್ ಅನ್ನು ನಿರ್ಲಕ್ಷಿಸಿ ಕನಿಷ್ಠ ಒಂದು ಸಾಲಿನ 3 ಅಥವಾ ಹೆಚ್ಚಿನ ಸಾಲುಗಳ ವಿಷಯವು `import `, `export `, `function `, `class `, `const `, `let `, `var ` ಅಥವಾ `return ` (ಕೀವರ್ಡ್ ಜೊತೆಗೆ ಒಂದು ಸ್ಪೇಸ್) ನೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ ಅಥವಾ ` (` ನಂತರ `if` `(` `for` ನೊಂದಿಗೆ , `while` ನೊಂದಿಗೆ 20 ಮತ್ತು ಕೊನೆಯ 5 ಸಾಲುಗಳು, ಎಲಿಡೆಡ್ ಮಧ್ಯವನ್ನು ಗುರುತಿಸಲಾಗಿದೆ.
2. **`grepSearch`** : `<path>:<digits>:` ಫಾರ್ಮ್ನ ಕನಿಷ್ಠ ಒಂದು ಸಾಲಿನಲ್ಲಿರುವ ವಿಷಯ, ಮೊದಲ ಕೊಲೊನ್ನ ಮೊದಲಿನ ಪಠ್ಯವು ಯಾವುದೇ ವೈಟ್ಸ್ಪೇಸ್ ಅನ್ನು ಹೊಂದಿಲ್ಲ, ಆ ಸಾಲುಗಳನ್ನು ಮಾತ್ರ ಇರಿಸುತ್ತದೆ, ಹೆಚ್ಚೆಂದರೆ 30, ನಂತರ ಯಾವುದೇ ಹೊಂದಾಣಿಕೆಗಳ ಎಣಿಕೆ ಮತ್ತು ಹೊಂದಾಣಿಕೆಯ ಫೈಲ್ಗಳ ಪಟ್ಟಿ; ಪ್ರತಿ ಇತರ ಸಾಲುಗಳನ್ನು ಕೈಬಿಡಲಾಗಿದೆ. ತಂತ್ರವನ್ನು ಪ್ರಚೋದಿಸಲು ಅಂತಹ ಒಂದು ಸಾಲು ಸಾಕು, ಆದ್ದರಿಂದ `12:30:45` ನಂತಹ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ನೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುವ ಲಾಗ್ ಲೈನ್ ಸಹ ಎಣಿಕೆಯಾಗುತ್ತದೆ.
3. **`shellOutput`** : ANSI CSI ಅನುಕ್ರಮವನ್ನು ಒಳಗೊಂಡಿರುವ ಔಟ್ಪುಟ್ (`ESC[` ನಂತರ ಅಂಕೆಗಳು ಅಥವಾ ಅರ್ಧವಿರಾಮ ಚಿಹ್ನೆಗಳು ನಂತರ ಒಂದು ಅಕ್ಷರ, ಬಣ್ಣ ಕೋಡ್ಗಳಲ್ಲಿ) ಅಥವಾ ಪಠ್ಯದಲ್ಲಿ ಎಲ್ಲಿಯಾದರೂ ವೈಟ್ಸ್ಪೇಸ್ನಿಂದ `$` ಆ ಅನುಕ್ರಮಗಳನ್ನು ಕಳೆದುಕೊಳ್ಳುತ್ತದೆ ( `ESC[?25l` ಅಥವಾ OSC ವಿಂಡೋ-ಶೀರ್ಷಿಕೆ ಅನುಕ್ರಮದಂತಹ ಇತರ ಎಸ್ಕೇಪ್ಗಳು, ಇರಿಸಲಾಗುತ್ತದೆ) ಮತ್ತು ಅದರ ಕೊನೆಯ ಸಾಲುಗಳನ್ನು ಕುಗ್ಗಿಸುತ್ತದೆ. ಏಕೆಂದರೆ ಈ ಪರಿಶೀಲನೆಯು `json` ಮತ್ತು `errorMessage`, JSON ಅಥವಾ `$` ಅನ್ನು ಒಳಗೊಂಡಿರುವ ದೋಷದ ಔಟ್ಪುಟ್ಗೆ ಮೊದಲು ರನ್ ಆಗುವ ಕಾರಣ `shellOutput` ಆನ್ ಆಗಿರುವಾಗ ಅವುಗಳನ್ನು ಎಂದಿಗೂ ತಲುಪುವುದಿಲ್ಲ.
4. **`json`** : `{` ಅಥವಾ `[` (ಐಚ್ಛಿಕ ವೈಟ್ಸ್ಪೇಸ್ ನಂತರ) ಮತ್ತು ಪಾರ್ಸ್ಗಳೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುವ 2,000 ಅಕ್ಷರಗಳಿಗಿಂತ ಹೆಚ್ಚಿನ JSON ಪೇಲೋಡ್ ಅನ್ನು ಸಂಕ್ಷಿಪ್ತಗೊಳಿಸಲಾಗಿದೆ: 7 ಕ್ಕಿಂತ ಹೆಚ್ಚು ಐಟಂಗಳ ಒಂದು ಶ್ರೇಣಿಯು ತನ್ನ ಮೊದಲ 5 ಮತ್ತು ಕೊನೆಯ 2 ಐಟಂಗಳನ್ನು ಮತ್ತು ಅದರ ಒಟ್ಟು ಎಣಿಕೆಯನ್ನು ಇಟ್ಟುಕೊಳ್ಳುತ್ತದೆ, ಮತ್ತು ಒಂದು ವಸ್ತುವು ತನ್ನ ಮೊದಲ 20 ಕೀಗಳನ್ನು ಇರಿಸುತ್ತದೆ, ಪ್ರತಿ ನೆಸ್ಟೆಡ್ ಆಬ್ಜೆಕ್ಟ್ ಅಥವಾ ಅರೇಗೆ ಬದಲಾಗಿ ಇರಿಸಲಾಗುತ್ತದೆ. ಅದರ ಉದ್ದ) ಮತ್ತು ಕೀಲಿಗಳನ್ನು ಎಣಿಸುವ `{…N keys}` ಮಾರ್ಕರ್ ಮೊದಲ 20 ಕ್ಕಿಂತ ಕಡಿಮೆಯಾಗಿದೆ `_remaining_<N>_keys` ಸ್ಕೇಲಾರ್ ಮೌಲ್ಯಗಳನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಕಲಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ ನೆಸ್ಟೆಡ್ ಮೌಲ್ಯಗಳಿಲ್ಲದ 20 ಕೀಗಳು ಅಥವಾ ಅದಕ್ಕಿಂತ ಕಡಿಮೆ ಇರುವ ವಸ್ತುವನ್ನು ಮರು-ಇಂಡೆಂಟ್ ಮಾಡಲಾಗುತ್ತದೆ — ಒಂದು ಮಿನಿಫೈಡ್ ಅಕ್ಷರಗಳನ್ನು ಗಳಿಸುತ್ತದೆ ಮತ್ತು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತದೆ.
5. **`errorMessage`** : ಔಟ್ಪುಟ್, ಎಲ್ಲಿಯಾದರೂ ಮತ್ತು ಯಾವುದೇ ಅಕ್ಷರದ ಸಂದರ್ಭದಲ್ಲಿ, `error:`, `error ` ( `no error found` ನಲ್ಲಿರುವಂತೆ ಒಂದು ಜಾಗವನ್ನು ಅನುಸರಿಸುವ ಪದ), `[error]`, `exception:`, `exception `, `[exception]` ಅಥವಾ `traceback` ಅದರ ಮೊದಲ ಸಾಲು, ಮುಂದಿನ 10 ಸಾಲುಗಳು ಮತ್ತು ಕೊನೆಯ 3 ಅನ್ನು ಅವುಗಳ ನಡುವೆ `… [N frames elided] …` ಮಾರ್ಕರ್ನೊಂದಿಗೆ ಇರಿಸುತ್ತದೆ. 13 ಕ್ಕಿಂತ ಹೆಚ್ಚು ಸಾಲುಗಳು ಮೊದಲ ಸಾಲನ್ನು ಅನುಸರಿಸಿದಾಗ ಮಾತ್ರ ಮಾರ್ಕರ್ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ 14 ಅಥವಾ ಅದಕ್ಕಿಂತ ಕಡಿಮೆ ಸಾಲುಗಳ ದೋಷ ಔಟ್ಪುಟ್ ಅನ್ನು ಕಡಿಮೆಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ (12 ಅಥವಾ 13 ಸಾಲುಗಳಲ್ಲಿ ಕೊನೆಯ 3 ಪುನರಾವರ್ತಿತ ಸಾಲುಗಳನ್ನು ಈಗಾಗಲೇ ಇರಿಸಲಾಗಿದೆ).

ಒಂದು ತಂತ್ರವು ಹೊಂದಿಕೆಯಾದ ನಂತರ, ಏನನ್ನೂ ಉಳಿಸದಿದ್ದರೂ ಸಹ, ನಂತರದ ತಂತ್ರಗಳನ್ನು ಪ್ರಯತ್ನಿಸಲಾಗುವುದಿಲ್ಲ. ಹೊಂದಾಣಿಕೆಯ ತಂತ್ರವು ಯಾವುದೇ ಅಂದಾಜು ಟೋಕನ್ಗಳನ್ನು ಉಳಿಸದಿದ್ದಾಗ ( ÷ 4 ಉದ್ದ, ದುಂಡಾದ) — ಉದಾಹರಣೆಗೆ 25 ಸಾಲುಗಳು ಅಥವಾ ಅದಕ್ಕಿಂತ ಕಡಿಮೆ ಇರುವ ಕೋಡ್-ರೀತಿಯ ಫೈಲ್, ಅಥವಾ 7 ಐಟಂಗಳನ್ನು ಹೊಂದಿರುವ 2,000 ಅಕ್ಷರಗಳ JSON ಅರೇ ಅಥವಾ ಕಡಿಮೆ — `compressAnthropicToolResultBlock()` ಎಂಜಿನ್ ಮೂಲ ಟೂಲ್ ಅನ್ನು ಇರಿಸಿದಾಗ `compressAggressive()` ಕರೆದಾರರು `saved` ಅಥವಾ ಕೆಳಗೆ, `compressToolResult()` ಸ್ವತಃ ಇನ್ನೂ ಆ ತಂತ್ರದ ಔಟ್ಪುಟ್ ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಟೂಲ್-ಫಲಿತಾಂಶದ ಹಂತವು ಕೊನೆಯ ಪದವಲ್ಲ: ಎಂಜಿನ್ನ ಫಾಲ್ಬ್ಯಾಕ್ ಸಾರಾಂಶವು ಇನ್ನೂ 8,192 ಅಕ್ಷರಗಳಿಗಿಂತ ಹೆಚ್ಚು ಉದ್ದವಾದ `tool` ಅಥವಾ `function` ಸಂದೇಶವನ್ನು ಕಡಿಮೆ ಮಾಡಬಹುದು (`maxTokensPerMessage`, 2,048, ಬಾರಿ 4).

#### ಯಾವಾಗ ಬಳಸಬೇಕು

ಉಪಕರಣದ ಫಲಿತಾಂಶದ ಸಂಕೋಚನವು ಆಕ್ರಮಣಕಾರಿ ಎಂಜಿನ್ನ ಹಂತ 1 ( `open-sse/services/compression/aggressive.ts` ನಲ್ಲಿ`compressAggressive()` ), ಆದ್ದರಿಂದ ಇದು ಆಕ್ರಮಣಕಾರಿ ಮೋಡ್ನಲ್ಲಿ ಮತ್ತು ಜೋಡಿಸಲಾದ ಪೈಪ್ಲೈನ್ನ `aggressive` ಹಂತದಲ್ಲಿ ಚಲಿಸುತ್ತದೆ. ಇದು OpenAI- ಆಕಾರದ `tool` ಮತ್ತು `function` ಸಂದೇಶಗಳನ್ನು ಮತ್ತು Anthropic `tool_result` ಬ್ಲಾಕ್ಗಳೊಳಗಿನ ಪಠ್ಯವನ್ನು ಸಂಕುಚಿತಗೊಳಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ತಂತ್ರವು `aggressive.toolStrategies` ಅಡಿಯಲ್ಲಿ ತನ್ನದೇ ಆದ ಸ್ವಿಚ್ ಅನ್ನು ಹೊಂದಿದೆ, ಎಲ್ಲವೂ ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಆನ್ ಆಗಿದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ, ಸ್ವಿಚ್ಗಳು ಕೇವ್ಮ್ಯಾನ್ ಪುಟದಲ್ಲಿವೆ** ಸುಧಾರಿತ** ಕಂಪ್ರೆಷನ್ ಆನ್ ಆಗಿರುವಾಗ ವೀಕ್ಷಿಸಿ ಮತ್ತು ಡೀಫಾಲ್ಟ್ ಮೋಡ್ ಆಕ್ರಮಣಕಾರಿಯಾಗಿದೆ.

### ಜೋಡಿಸಲಾದ ಪೈಪ್ಲೈನ್

ಜೋಡಿಸಲಾದ ಮೋಡ್ ರನ್ ಆಗುತ್ತದೆ** ಅನುಕ್ರಮದಲ್ಲಿ ಬಹು ಎಂಜಿನ್ಗಳು** — ಸಾಮಾನ್ಯವಾಗಿ ಮೊದಲು RTK (ಟೂಲ್ ಔಟ್ಪುಟ್ನಲ್ಲಿ 60-90% ಉಳಿತಾಯ), ನಂತರ ಉಳಿದ ಪಠ್ಯದಲ್ಲಿ ಕೇವ್ಮ್ಯಾನ್ (~ 46% ಇನ್ಪುಟ್ ಉಳಿತಾಯ). ಸಂಯೋಜಿಸಲಾಗಿದೆ, ಅದು** 78-95% ಅರ್ಹ ಶ್ರೇಣಿ** (ಮೇಲಿನ ಅಪ್ಸ್ಟ್ರೀಮ್ ಉಳಿತಾಯ ಗಣಿತವನ್ನು ನೋಡಿ): `1 - (1 - 0.60..0.90) × (1 - 0.46)` ಸರಾಸರಿ ≈ 89%.

#### ಇದು ಹೇಗೆ ಕೆಲಸ ಮಾಡುತ್ತದೆ

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### ಯಾವಾಗ ಬಳಸಬೇಕು

ಇದಕ್ಕಾಗಿ ಜೋಡಿಸಲಾದ ಮೋಡ್ ಅನ್ನು ಬಳಸಿ:

- ಟೂಲ್-ಹೆವಿ ವರ್ಕ್ಫ್ಲೋಗಳು (ಏಜೆಂಟಿಕ್ ಕೋಡಿಂಗ್, ಸಂಶೋಧನೆ)
- ವೆಚ್ಚ-ಸೂಕ್ಷ್ಮ ಬ್ಯಾಚ್ ಪ್ರಕ್ರಿಯೆ
- ನಿಮಗೆ ಗರಿಷ್ಠ ಟೋಕನ್ ಉಳಿತಾಯ ಬೇಕಾದಾಗ

ಸ್ಟಾಕ್ ಮಾಡಲಾದ ಪೈಪ್ಲೈನ್ಗಳನ್ನು ಜಾಗತಿಕ `stackedPipeline` ಕಂಪ್ರೆಷನ್ ಸೆಟ್ಟಿಂಗ್ ಮೂಲಕ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾಗಿದೆ ಅಥವಾ ರೂಟಿಂಗ್ ಕಾಂಬೊಗೆ ನಿಯೋಜಿಸಲಾದ ಹೆಸರಿನ ಕಂಪ್ರೆಷನ್ ಕಾಂಬೊ ಮೂಲಕ (ಮೇಲಿನ ಪ್ರತಿ-ಕಾಂಬೋ ಓವರ್ರೈಡ್ ಅನ್ನು ನೋಡಿ) — ಸ್ವಯಂ-ಕಾಂಬೋ `modePack` ಮೂಲಕ ಅಲ್ಲ (ಆ ಕ್ಷೇತ್ರವು ಸ್ವಯಂ-ಕಾಂಬೋ ಮಾದರಿಯ ಆಯ್ಕೆಯನ್ನು ಮಾತ್ರ ಮರು-ತೂಕ ಮಾಡುತ್ತದೆ ಮತ್ತು `stacked` ಮಾನ್ಯವಾದ ಪ್ಯಾಕ್ ಹೆಸರು ಅಲ್ಲ).

## ಕಂಪ್ರೆಷನ್ ಕಾಂಬೊ ಓವರ್ರೈಡ್ಗಳು

ವಿಭಿನ್ನ ಬಳಕೆಯ ಸಂದರ್ಭಗಳಿಗೆ ವರ್ತನೆಯನ್ನು ಸೂಕ್ಷ್ಮವಾಗಿ ಹೊಂದಿಸಲು, ಜಾಗತಿಕ ಕಂಪ್ರೆಷನ್ ಮೋಡ್ ಅನ್ನು **ಪ್ರತಿ ಕಾಂಬೊಗೆ ಪ್ರತ್ಯೇಕವಾಗಿ** ಓವರ್ರೈಡ್ ಮಾಡಬಹುದು:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ಇದು ಈ ಸಂದರ್ಭಗಳಲ್ಲಿ ಉಪಯುಕ್ತವಾಗಿದೆ:

- **ಕೋಡಿಂಗ್ ಕಾಂಬೊಗಳು**: ದೀರ್ಘ ಅವಧಿಯ ಸೆಷನ್ಗಳಿಗೆ `aggressive` ಮೋಡ್ ಬಳಸಿ
- **ತ್ವರಿತ ಪ್ರಶ್ನೋತ್ತರ ಕಾಂಬೊಗಳು**: ವೇಗದ ಪ್ರತಿಕ್ರಿಯೆಗಳಿಗಾಗಿ `lite` ಮೋಡ್ ಬಳಸಿ
- **ಹೆಚ್ಚು ಟೂಲ್ಗಳನ್ನು ಬಳಸುವ ಕಾಂಬೊಗಳು**: ಗರಿಷ್ಠ ಉಳಿತಾಯಕ್ಕಾಗಿ `stacked` ಮೋಡ್ ಬಳಸಿ
- **ಪ್ರೊಡಕ್ಷನ್ ಕಾಂಬೊಗಳು**: ಕ್ಯಾಶಿಂಗ್ ಪ್ರೊವೈಡರ್ಗಳಿಗಾಗಿ ಓವರ್ರೈಡ್ ಅನ್ನು ಆಫ್ ಆಗಿಯೇ ಬಿಡಿ — ಸದಾ ಸಕ್ರಿಯವಾಗಿರುವ
  ಕ್ಯಾಶ್-ಅವೇರ್ ಹೊಂದಾಣಿಕೆಯು `aggressive`/`ultra` ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ `standard` ಗೆ ಡೌನ್ಗ್ರೇಡ್ ಮಾಡುತ್ತದೆ
  (ಆಯ್ಕೆ ಮಾಡಬಹುದಾದ `cache-aware` ಮೋಡ್ ಇಲ್ಲ)
