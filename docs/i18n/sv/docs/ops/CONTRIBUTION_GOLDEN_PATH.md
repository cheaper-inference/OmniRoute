Använd den här guiden för att välja den minsta tillförlitliga utvecklingsloopen för en pull request. Den
ersätter inte de områdesspecifika arkitektur- och säkerhetsdokument som länkas nedan; den kopplar varje vanlig
ändringstyp till dess kontrakt, fokuserade kontroller och CI-täckning.

## Flödet som varje ändring följer

1. **Välj basen innan du börjar redigera.** Hitta den högsta aktiva `release/v*`-grenen och skapa en gren från
   dess senaste commit. Rikta din pull request mot den grenen, inte `main`. Om en releasefrysning är aktiv ska du inte rikta den mot den frysta
   grenen; använd nästa aktiva cykel som beskrivs i
   [Modell för grenar och releaser](BRANCHING_MODEL.md).
2. **Ange kontrakten.** Identifiera varje katalog, schema, genererad artefakt, publikt API eller
   användargränssnitt som ändringen påverkar. Tabellen nedan anger den minsta uppsättningen att utgå från.
3. **Skriv eller uppdatera fokuserade tester.** Produktionsändringar i `src/`, `open-sse/`, `electron/` eller
   `bin/` kräver ett automatiserat test i samma pull request. Kör de minsta testfilerna som verifierar
   beteendet och därefter de angivna fokuserade kontrollerna.
4. **Låt CI köra den breda matrisen.** De fullständiga enhetstestdelarna, Vitest, täckningströskeln och
   produktionsbygget körs för pull requesten. Kör endast en bred testsvit lokalt när ett fokuserat fel pekar på
   en större påverkan eller när ändringen omfattar flera delsystem.
5. **Synkronisera före granskning.** Hämta den aktiva basen, granska dess nya commits och din diff mot
   den och gör sedan rebase eller merge av basen enligt arbetsflödet för bidragsgivare. Lös konflikter i genererade filer
   och kataloger utifrån deras källa, generera dem på nytt, kör om den fokuserade loopen och bekräfta att
   pull requesten fortfarande är riktad mot den aktiva releasegrenen.
6. **Dokumentera underlag.** Ange i mallen för pull requests vilka kommandon som körts, varje testfil som lagts till eller ändrats,
   migreringar eller funktionsflaggor samt eventuell validering som endast utförs i CI och fortfarande väntar.

## Standardflöden per ändringstyp

Kommandona nedan är de minsta fokuserade kontrollerna, inte ett tillstånd att hoppa över ett test som direkt täcker
beteendet du ändrade.

### Leverantör

**Kontrakt**

- Leverantörsdefinitionen i `src/shared/constants/providers/` och dess sammansättning i
  `src/shared/constants/providers.ts`.
- Modeller och funktioner i `open-sse/config/providerRegistry.ts` eller dess extraherade registerfiler.
- Val av exekverare/översättare, OAuth- eller API-nyckelkonfiguration, resurser för kontrollpanelen och genererad
  leverantörsreferens där det är tillämpligt.
- Publika autentiseringsuppgifter måste använda `resolvePublicCred()`; felsvar måste använda de delade sanerade
  felhjälparna. Se `docs/security/PUBLIC_CREDS.md` (git; kompileras inte till `/docs`) och
  [Felsanering](../security/ERROR_SANITIZATION.md).

**Fokuserad loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # när katalogen ändras; committa den genererade diffen
npm run lint
```

Testa även varje påverkad typ av begäran: chatt, Responses, bilder, inbäddningar, ljud eller video.
Granska genererade katalog- och golden-diffar som kontraktsändringar; godkänn dem inte blint.

### Routning

**Kontrakt**

- Publika strategivärden och UI-metadata i `src/shared/constants/routingStrategies.ts`.
- Dirigering och ordning under `open-sse/services/combo.ts` och `open-sse/services/combo/`.
- Combo-scheman, persistens, resiliensstatus, modellfunktioner och API-/UI-kontroller.
- [Auto-Combo-motorn](../routing/AUTO-COMBO.md) och resiliensdokumentationen när beteendet ändras.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ändringar av strategi eller dirigering
npm run check:known-symbols      # ändringar av strategiregistrering
npm run lint
```

Använd deterministiska tester med mockade uppströmstjänster lokalt. Live-smoketester för combo kräver autentiseringsuppgifter och är
manuella, inte ersättningar för CI.

### UI / UX

**Kontrakt**

- Next.js-rutt/-sida och gränser för delade komponenter under `src/app/` och
  `src/shared/components/`.
- Former för API-svar, laddnings-, tom- och feltillstånd, beteende för tangentbord och skärmläsare,
  responsiv layout, teman och utökning av språkversioner.
- Engelska UI-källsträngar i `src/i18n/messages/en.json`; hårdkoda inte ny användarsynlig text.

**Fokuserad loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Kör appen för interaktions- eller visuella ändringar och kontrollera både smala och breda visningsytor. CI kör
produktionsbygget och bredare testsviter; visuellt beteende kräver fortfarande ett fokuserat komponenttest, Playwright-test
eller en dokumenterad manuell kontroll som är lämplig för ändringen.

### i18n

**Kontrakt**

- `src/i18n/messages/en.json` är UI-källan; `config/i18n.json` är källan för språkversioner.
- CLI-kataloger finns separat under `bin/cli/locales/`.
- Bevara ICU-platshållare och taggar exakt. Översätt inte produkt-, leverantörs- eller modellnamn,
  protokoll- och rubriknamn, kommandon, kod-/JSON-identifierare, URL:er, miljövariabler eller
  skyddade termer som `OmniRoute`, `OAuth`, `MCP` och `A2A`. Den aktuella källistan är
  `scripts/i18n/glossary/protected-terms.json`.

**Fokuserad loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # när CLI-strängar/-kataloger ändras
npm run lint
```

Detta är vägledning för det befintliga systemet, inte en uppmaning att utöka dess verktyg eller nyckelmodell.
Håll i18n-patchar avgränsade medan ersättningssystemet utformas. Kör inte översättningskommandon
som anropar externa tjänster om inte uppgiften uttryckligen kräver genererade översättningar och
du har granskat den resulterande diffen.

### CLI

**Kontrakt**

- Publika kommandon och flaggor i `bin/cli/`, genererade API-kommandon, slutkoder, stdout/stderr och
  strukturer för JSON-utdata, konfigurations-/miljöbeteende samt paketerade filer.
- Användarvända strängar i CLI måste använda CLI:ns i18n-lager och hålla katalogerna `en`/`pt-BR` synkroniserade.
- Bevara Node som den runtime som stöds och kontraktet för den publicerade binärfilen.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ändringar i genererad/paketerad CLI
npm run check:pack-policy     # ändringar i paketets publika yta
npm run lint
```

Använd det exakta kommandot i en tillfällig datakatalog när beteendet beror på parsning, filer eller
slutstatus. CI utför de bredare kontrollerna av paketartefakter och ekosystem.

### Databas

**Kontrakt**

- Domänmoduler under `src/lib/db/`; importera specifika moduler direkt (det gamla återexportlagret `localDb.ts` har tagits bort).
- Numrerade, idempotenta SQL-migreringar under `src/lib/db/migrations/`, transaktionssäkerhet, uppgraderingsbeteende,
  index och varje anropare som påverkas av schemat.
- Routes och hanterare kör aldrig rå SQL direkt.

**Fokuserad loop**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Testa både en ny databas och uppgradering från det föregående schemat när du lägger till en migrering. Databastester
måste stänga handles och anropa `resetDbInstance()` under upprensningen. Kör `npm run test:bun:db` endast när
adaptervägen för Bun enligt bästa förmåga ändras; Node förblir auktoritativ.

### Bygge / driftsättning

**Kontrakt**

- Rot- och workspace-manifest/låsfil, `scripts/build/`, fristående Next.js-sammansättning, paketinnehåll i `dist/`,
  Electron-plattformsmetadata, CI-arbetsflöden och driftsättningssentineler.
- Node-intervallen som stöds och den uttryckligen tillåtna användningen av Bun i `CLAUDE.md` måste förbli intakta.
- Byggartefakter förblir ospårade; policyer för beroenden, licenser, arbetsflöden och paket gäller.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ändringar i beroenden eller låsfil
npm run check:pack-policy      # ändringar i det publicerade paketets yta
npm run lint
```

Använd `npm run build` lokalt endast när ändringen påverkar kompilering, fristående sammansättning, resurser
eller runtime-paketering. Använd `npm run build:release` endast för validering av release/driftsättning. CI:s bygge är
den slutliga plattformsöverskridande signalen; plattformsspecifika Electron-ändringar kräver motsvarande fokuserat bygge
eller smoke-testbevis.

## Utvecklarskript för en delad maskin

Två hjälpskript i `scripts/dev/` kodifierar den lokala loopen på en utvecklingsmaskin där andra sessioner är aktiva:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # filer från merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # exakt dessa filer
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # isolerat worktree, säkert att köra parallellt
```

- `typecheck-touched.sh` typkontrollerar endast de berörda `.ts/.tsx`-filerna via en tillfällig
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) med en heap på 6 GB, så det ersätter den projektomfattande `tsc -p tsconfig.json`
  som får slut på minne på en belastad maskin. Det skriver ut felen i berörda filer plus en sammanfattningsrad och avslutas med
  `1` för fel i berörda filer, `2` när de enda felen finns i importerade filer eller tsc avslutades
  utan diagnostik (läs loggen som anges under `_artifacts/typecheck-touched/`), `0` när
  inga fel finns. Den tillfälliga tsconfig-filen tas alltid bort; checka aldrig in någon sådan.
- `new-worktree.sh` serialiserar samtidiga körningar med `<git-common-dir>/omniroute-new-worktree.lock`
  (väntar som standard i upp till 600 s, med ett synligt meddelande; skripthuvudet dokumenterar hur
  detta åsidosätts) och återställer
  grenen som skapades när `git worktree add` misslyckas innan worktree-katalogen finns, så ett nytt försök
  inte kräver något manuellt `git branch -D`. De hårdlänkade `node_modules` och kopian av `.husky/_` är oförändrade.

## Lokal kandidatloop

Källkodstester kan inte bevisa att den paketerade artefakten startar: paketeringslistor, beskurna beroenden
och systemspecifika binärfiler orsakar fel först när tar-arkivet installeras och startas. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) är den lokala sidan av flödet bygg en gång / validera / lansera från
RFC #8084: det bygger en kandidat, validerar exakt den artefakten, lanserar den genom namnbyten av
kataloger och återställer den när den lanserade platsen inte klarar sin hälsokontroll.

```bash
npm run dev:candidate -- run --dry-run --json  # skriv ut planen, ändra ingenting
npm run dev:candidate -- run                   # bygg + validera + lansera, automatisk återställning
npm run dev:candidate -- build                 # npm pack + installera i _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # starta på en ledig port, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # byt plats på current och previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # återanvänd ett tar-arkiv byggt någon annanstans (CI)
```

- **Bygg en gång.** `build` paketerar det aktuella trädet (det kräver `dist/server.js`, så kör
  `npm run build:release` först) eller kopierar `--from-tarball` och installerar sedan tar-arkivet i ett
  isolerat npm-prefix, eftersom tar-arkivet inte innehåller några `node_modules`. Id:t är den korta `HEAD`-
  sha:n (`-dirty` när trädet har lokala ändringar) eller `tgz-<sha256>` för ett tar-arkiv. Ett rent id som
  redan har byggts återanvänds i stället för att byggas om; ange `--force` för att bygga om det.
- **Validera paketet, inte källkoden.** `validate` startar den installerade CLI:n
  (`serve --port <free port>`) med en ny `DATA_DIR=<candidate>/data`, falska hemligheter och med
  operatörens `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` och `INITIAL_PASSWORD` borttagna från
  miljön, så att den nyckellösa loopback-konfigurationen för en ny installation kontrolleras. Det väntar på att
  `GET /api/health` ska returnera 200, kräver att `GET /v1/models` returnerar 200, stoppar processgruppen
  och registrerar resultatet i `validation.json` tillsammans med tar-arkivets hash.
- **Lansera samma artefakt.** `promote` avvisar en kandidat utan en godkänd validering för dess
  aktuella tar-arkivshash. Den aktiva standardplatsen är `_artifacts/candidate/current`; `--target <dir>`
  väljer en annan katalog på samma filsystem, och dess föregående plats är `<dir>.previous`.
  Varje namnbyte är atomärt, och ett fel halvvägs återställer de namnbyten som redan har genomförts.
- **Återställ.** `run` validerar den lanserade platsen igen och byter tillbaka `current` och `previous` när
  den kontrollen misslyckas. En kandidat som inte klarar den första valideringen lanseras aldrig.

Allt skrivs under den git-ignorerade katalogen `_artifacts/candidate/`; en befintlig OmniRoute-
installation och dess datakatalog ändras aldrig. Den lanserade CLI:n finns i
`_artifacts/candidate/current/prefix/bin/omniroute`; starta den med din egen `DATA_DIR` när du använder
den. Avslutningskoder: `0` lyckades, `1` misslyckad validering eller lansering, `2` användningsfel eller saknat bygge.

## Lokal loop kontra CI

| Kör lokalt för varje ändring                                                                 | CI ger den breda signalen                                                            |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Direkta beteendetester och kategorikontroller ovan                                           | Uppdelad fullständig enhetstestsvit och seriella tester                              |
| `npm run lint`                                                                               | Vitest-sviter samt spärrar för täckning och kvalitet                                 |
| Typkontroll eller bygg endast när det berörda kontraktet kräver det                          | Produktionsbygge samt säkerhets-, dokumentations-, beroende- och PR-policykontroller |
| Manuella interaktions-/livekontroller endast när automatisering inte kan verifiera beteendet | Integrations- och plattformskontroller mellan jobb, konfigurerade av arbetsflödet    |

En grön fokuserad loop är belägg för det ändrade kontraktet, inte ett bevis på att orelaterade CI-kontroller
kommer att passera. Omvänt ska inte varje lokal ändring behöva vänta på hela repositorymatrisen.

## Checklista för avstämning

Innan du begär granskning:

- Bekräfta att PR-basgrenen fortfarande är den högsta aktiva `release/v*`-grenen.
- Hämta den basgrenen och granska commits som har lagts till sedan du skapade din gren.
- Granska `git diff <active-base>...HEAD` efter oavsiktliga eller genererade ändringar.
- Lös konflikter i kataloger och genererade dokument genom att uppdatera källan och generera utdata på nytt.
- Kör om varje fokuserat test/kontroll som anges i PR-beskrivningen efter avstämningen.
- Försvaga aldrig assertions och ta inte bort obligatoriska tester enbart för att anpassa till en flyttad basgren.

För regler om releasefrysning och omriktning, se
[Förgrenings- och releasemodell](BRANCHING_MODEL.md). För den fullständiga CI-förteckningen, se
[Referens för kvalitetskontroller](../architecture/QUALITY_GATES.md).
