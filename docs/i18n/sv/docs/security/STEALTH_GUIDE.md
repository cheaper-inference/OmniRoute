OmniRoute integreras med leverantörer vars edge-system aktivt skapar fingeravtryck av inofficiella klienter (TLS JA3/JA4, ordning på headers, JSON-brödtextens form, integritetstoken). Den här sidan dokumenterar de stealth-ytor som OmniRoute exponerar och var de är implementerade.

## Juridiskt och etiskt meddelande

Stealth-funktionerna finns för att OmniRoute ska kunna fungera som ett kompatibilitetslager mellan användarägda officiella konton (Claude Code CLI, Codex, Antigravity, Cursor osv.) och OmniRoutes enhetliga API. De är **inte** avsedda för att kringgå bedrägeriidentifiering, dela autentiseringsuppgifter eller bryta mot leverantörernas användarvillkor. Underhållarna förväntar sig att operatörer följer de uppströmsvillkor som de godkände när kontona skapades.

## Lager för TLS-fingeravtryck

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

Beständiga `wreq-js`-sessioner skapas lat omedelbart per kontoomfång och matchad proxy. Den
processomfattande `TlsClient`-poolen innehåller högst 128 sessioner som imiterar **Chrome 124 på macOS** för
uppströmsservrar bakom Cloudflare. `TlsClient.fetch()` avbryts säkert när den systemspecifika exekveringsmiljön
inte är tillgänglig; en anropare kan uttryckligen välja en reservlösning utanför denna omslutning.

- Sessionsprofil: `browser: "chrome_124", os: "macos"`
- Proxymatchning (prioritet): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (även gemener)
- Tidsgräns: `TLS_CLIENT_TIMEOUT_MS` (ärver från `FETCH_TIMEOUT_MS`, standardvärde 600000)
- Svaret från `wreq-js` är fetch-kompatibelt (`headers`, `text()`, `json()`, `clone()`, `body`).
- Övervakning av första byte (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): `TlsClient.fetch()`
  slutförs så snart uppströmshuvudena anländer, vilket innebär att enbart `TLS_CLIENT_TIMEOUT_MS` inte kan begränsa en
  svarskropp som aldrig levererar sin första byte. `guardTlsFirstByte()` tävlar mellan svarskroppens första `read()`
  och `TLS_FIRST_BYTE_WATCHDOG_MS` (standardvärde `10000`, `0` inaktiverar den); en fungerande svarskropp
  påverkas inte, medan en blockerad svarskropp avbryter wreq-läsaren och låter den befintliga
  TLS-reservlogiken i `proxyFetch` fortsätta till direkt-/proxydispatchern (en begäran som inte säkert kan spelas upp igen, t.ex.
  ett POST-anrop med en kropp, utlöser fortfarande ett fel i stället för att tyst skickas på nytt).

### Transport för leverantörer med webbcookies — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` är den gemensamma adaptern för de fem specialiserade
webbcookietransporterna nedan. Varje tunt leverantörsomslag väljer en webbläsar-/OS-profil. Adaptern
använder den gemensamma wreq-inläsaren och transportpoolen i `open-sse/utils/tlsClient.ts`, nycklad efter
profil + OS + matchad proxy, medan varje begäran använder `cookieMode: "ephemeral"`. Konton och
begäranden delar därför anslutningar på transportnivå, men aldrig en wreq-session eller cookiebehållare.

| Leverantör | Profil        | Emulerat OS | Policy för EOF i ström                  |
| ---------- | ------------- | ----------- | --------------------------------------- |
| Claude     | `chrome_146`  | Linux       | inkludera `[DONE]`                      |
| Perplexity | `firefox_151` | macOS       | inkludera `event: end_of_stream`        |
| Grok       | `chrome_146`  | Linux       | exkludera `[DONE]`                      |
| Notion     | `chrome_146`  | Windows     | inkludera `[DONE]`                      |
| LMArena    | `chrome_146`  | Windows     | ingen sentinel; stäng vid systemets EOF |

- Strömning använder det systemspecifika svarets `ReadableStream` direkt; ingen temporär fil eller sidoprocess
  skapas.
- Upp till 256 inledande byte inspekteras innan en ström exponeras. SSE-leverantörer buffrar fel som inte är SSE;
  Grok/LMArena mappar Cloudflare-utmaningar till `403` och HTML-mellansidor till `502`.
- Den systemspecifika tidsgränsen för begäran omsluts fortfarande av en absolut hård JS-tidsgräns. Vid en blockering ogiltigförklaras
  och stängs endast den berörda profil-/OS-/proxytransporten innan nästa begäran återskapar den.
- Prioriteten för proxymatchning är `proxyUrl` per anrop → kontots/instrumentpanelens begäransspecifika kontext →
  `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (inklusive varianter med gemener). Matchningsfel avbryts
  säkert i stället för att läcka en direktanslutning. LMArena matchar avsiktligt mot `arena.ai`.
- `byteResponse` returnerar en innehållstypad `data:`-URL utan UTF-8-korruption.
- Felen är `TlsClientUnavailableError` (paket/tillägg ej tillgängligt), `TlsClientHangError`
  (tidsgränsen överskreds) och `WreqTransportCapacityError` (den gemensamma felkoden för sessionskapacitet)
  när alla 128 begränsade profil-/OS-/proxyplatser är aktiva eller håller på att stängas.

Den generiska `TlsClient`-sessionen ovan är fortsatt specialiserad för beständigt webbläsarbaserat
cookietillstånd. Båda vägarna återanvänder samma cachade wreq-modulinläsare och livscykelkrok för processen; deras pooler förblir
separata eftersom deras cookielivslängder avsiktligt skiljer sig åt.

Profilerna stöds av det fixerade paketet, men faktisk WAF-acceptans kan ändras oberoende
av lokala kontraktstester. Validera ändringar av fingeravtryck mot ett uttryckligen auktoriserat livekonto
innan du hävdar likvärdighet med en uppströmswebbläsare.

## Claude Code Stealth-paket

När `cliCompatMode` är aktiverat omformar OmniRoute utgående Claude-förfrågningar så att de inte går att skilja från `claude-cli`-trafik. Tre moduler samarbetar:

### `claudeCodeFingerprint.ts`

Beräknar det 3 tecken långa `cc_version`-fingeravtrycket som bäddas in i faktureringshuvudet:

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (hårdkodat; matchar den officiella klienten)
- Indata: tecknen vid index 4, 7 och 20 i texten i det första användarmeddelandet + versionssträngen
- Utdata: hexadecimalt prefix med 3 tecken

### `claudeCodeCCH.ts` (Client Content Hash)

Integritetskontroll på serversidan som den officiella Claude Code CLI-klienten beräknar via Bun/Zig. OmniRoute implementerar den på nytt med `xxhash-wasm`:

1. Serialisera innehållet med platshållaren `cch=00000;`
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. Utfyllt med inledande nollor till 5 gemena hexadecimala tecken
4. Ersätt `cch=00000;` med den beräknade tokenen

Konstanter:

- Seed: `0x6e52736ac806831e`
- Mönster: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

Infogar en Unicode-**sammanfogare utan bredd** (`U+200D`) efter det första tecknet i ”känsliga” klientnamn så att uppströmsfilter inte kan hitta dem med grep. Standardordlista:

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

Tillämpas på: `system`-block, allt `messages[].content` samt `tools[].description` / `tools[].function.description`. Kan åsidosättas av operatören via `setSensitiveWords()`.

### `claudeCodeCompatible.ts` — `anthropic-compatible-cc-*`-leverantörer

För Anthropic-reläer från tredje part som endast accepterar ”äkta Claude Code”-trafik:

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.280 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"` som standard
- Växlingsknappen ”Enable redact-thinking beta” per anslutning lägger till `redact-thinking-2026-02-12` när en CC Compatible-uppström specifikt kräver redigerade resonemangsströmmar
- Växlingsknappen ”Enable summarized thinking display” per anslutning lagrar `providerSpecificData.requestDefaults.summarizeThinking` och lägger till `display: "summarized"` i CC Compatible-resonemangsförfrågningar som inte redan har angett ett visningsläge
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (Opus/Sonnet 4.x-familjen)
- Standardsökväg: `/v1/messages?beta=true`

Närliggande moduler i samma paket:

- `claudeCodeConstraints.ts` — regler för temperatur och cachekontroll
- `claudeCodeToolRemapper.ts` — ommappning av verktygsnamn
- `claudeCodeExtraRemap.ts` — extra normalisering av nyttolast

## Antigravity Stealth

Antigravity förfrågningar bevara uppringarens text byte-för-byte. OmniRoute infogar inte nollbreddstecken i uppmaningar eller rename/inject verktyg för att imitera en IDE klient.

### `antigravityHeaderScrub.ts`

Avlägsnar rostfria SDK -markörer (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`) innan vidarebefordran.

### ⚠️ risk: `ANTIGRAVITY_CREDITS=always` (hot spot för kontoförbud)

`ANTIGRAVITY_CREDITS=always` (konsumeras av `open-sse/executors/antigravity.ts`) rutter **varje** begär genom Antigravity AI Credit Overages (betalda Google krediter) istället för att låta Google:s fria kvoter gate saker. Detta är dokumenterat som en funktion, men det är det **den enskilt vanligaste ToS-överträdelserapporten vi ser** — flera Google Ultra-konton har förbjudits med `403 / "service disabled for ToS violation" / insufficient_quota` efter att ha körts i några timmar med `=always`.

Uppströmstillämpningen är på **Google:s sida** , inget OmniRoute kan förhindra. Env var-namnet och de befintliga dokumenten får det att låta som en säker ratt att vända på; det är det inte.

**Varför detta drar upp upptäckt av missbruk mer aggressivt än användning av enbart fria nivåer:**

- Ihållande automatiserade utgifter på ett enda Google konto flaggas annorlunda än gratisnivå träffar-kvoter-och-stopp.
- Kreditöverskott har inget tak, så en felkonfigurerad klient kan bränna igenom flera hundra USD på några minuter och se ut som API-nyckelåterförsäljning eller bottrafik.
- Flera OmniRoute användare som träffar överskottskrediter parallellt från samma externa IP förstärker signalen.

**Rekommenderad hållning:**

1. Behåll standard `ANTIGRAVITY_CREDITS=off` såvida inte operatören uttryckligen accepterar betald kredit- och kontotillämpningsrisk. `retry` skickar den normala begäran först och tillför krediter högst en gång efter en kvalificerad kvot 429; `always` injicerar krediter vid första begäran.
2. **Sprid belastningen mellan leverantörer via Auto-Combo** (`model: "auto"` eller `kr/glm/etc` -combo) istället för att mätta ett enda Antigravity konto.
3. **Ställ in RPM -gränser per anslutning** på Antigravity -leverantörens redigeringssida (Dashboard → Providers → Antigravity → anslutning → hastighetsgräns). 30–60 RPM är en försvarbar övre gräns för långvarig användning.
4. **Använd stabila, operatörskontrollerade uppströmsnätverk** och undvik att dela ett konto mellan orelaterade användare eller arbetsbelastningar.
5. **Om det förbjuds** : överklagande via `support.google.com` → "Återställ Workspace/Account åtkomst" med exakt `quota_exceeded` / `service disabled` -svarsorgan Google skickat. Återställning kan inte garanteras.

Miljöreferensen dokumenterar konto- och utgiftskonsekvenserna för varje kreditläge.

#### Inte bara `=always`: Antigravity OAuth -routing i allmänhet

Avstängningarna är inte begränsade till kreditöverskott. Rapporter i november 2026 (#19223, #19266) beskriver flera Google konton avstängda under routing genom `antigravity` och `agy` (Antigravity CLI)-leverantörer, med:

```
403: This service has been disabled in this account for violation of Terms of Service.
Please submit an appeal to continue using this product.
```

Båda leverantörerna autentiserar med Antigravity produktens OAuth session, vilket är fallet som instrumentpanelens riskmeddelande ("Denna leverantör använder din officiella produkt session/OAuth, som inte är auktoriserad för proxy/router användning") varnar om innan en anslutning läggs till. Ingen av rekommendationerna ovan tillåter användningen; de minskar bara hur mycket trafik ett konto bär.

**Auktoriserade API gränssnitt för Gemini -modeller.** Google erbjuder programmatisk åtkomst till Gemini genom sin APIs, som OmniRoute stöder som vanliga API-nyckelleverantörer:

| Leverantörs-id | Namn på instrumentpanelen | Inloggningsuppgifter                                                             |
| -------------- | ------------------------- | -------------------------------------------------------------------------------- |
| `gemini`       | Gemini (Google AI Studio) | Gemini API nyckel från Google AI Studio (gratis nivå tillgänglig)                |
| `vertex`       | Vertex AI                 | Servicekonto JSON, OAuth -åtkomsttoken eller Vertex Express API -nyckel (Gemini) |

Dessa leverantörer använder Google -uppgifter för API -åtkomst, till skillnad från Antigravity -produktsessionen. De gör inte varje användning förenlig eller tar bort risken för verkställighet: var och en styrs av sina egna villkor, som operatören måste kontrollera för deras utplacering. Till exempel tillåter [Gemini API Ytterligare användarvillkor](https://ai.google.dev/gemini-api/terms) endast betaltjänster när API -klienter görs tillgängliga för användare i Europeiska ekonomiska samarbetsområdet, Schweiz eller Storbritannien, och innehåll som skickas till obetalda tjänster kan användas för att förbättra Google produkter. Vertex AI faller under Google Cloud-villkoren istället ( [Service Specific Terms](https://cloud.google.com/terms/service-terms) ). Prissättning och kvoter följer dessa API villkor snarare än en Antigravity -prenumeration.

Operatörer som vill undvika Antigravity avstängningarna som beskrivs ovan bör dirigera Gemini trafik genom en av dessa leverantörer istället för `antigravity` / `agy`, efter att ha kontrollerat att deras användning överensstämmer med leverantörens villkor.

Beröringspunkter:

- `open-sse/executors/antigravity.ts` — läser `process.env.ANTIGRAVITY_CREDITS`
- `src/lib/oauth/providers/antigravity.ts` — legitimation VVS
- Ursprunglig incidentrapport: Diskussion [#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## CLI-fingeravtrycksregister — `open-sse/config/cliFingerprints.ts`

Tabell per leverantör som låser den **exakta** ordningen på headers och fält i JSON-brödtexten, hämtad från mitmproxy-spårningar av de officiella CLI-verktygen. För närvarande registrerade: `codex`, `claude`, samt profiler som härleds vid körning i `providerHeaderProfiles.ts` för `antigravity` och `github`.

```ts
interface CliFingerprint {
  headerOrder: string[]; // skiftlägeskänslig
  bodyFieldOrder: string[]; // JSON-nycklar på toppnivå
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

Aktivera eller inaktivera per leverantör via miljövariabler (se nedan). När detta är inaktiverat visas headers/brödtextnycklar i den ordning som Node/JSON gav dem — enkelt att skapa fingeravtryck från.

## MITM-proxy (Antigravity, Linux/macOS/Windows)

För CLI-verktyg vars binärfiler inte kan omdirigeras via `OPENAI_BASE_URL` kör OmniRoute en lokal TLS-terminerande proxy. Slutpunkterna finns under `src/app/api/cli-tools/antigravity-mitm/`.

| Metod  | Slutpunkt                               | Syfte                                          |
| ------ | --------------------------------------- | ---------------------------------------------- |
| GET    | `/api/cli-tools/antigravity-mitm`       | Status — körs, pid, dnsConfigured, certExists  |
| POST   | `/api/cli-tools/antigravity-mitm`       | Starta MITM (kräver `apiKey` + `sudoPassword`) |
| DELETE | `/api/cli-tools/antigravity-mitm`       | Stoppa MITM                                    |
| GET    | `/api/cli-tools/antigravity-mitm/alias` | Lista modellalias                              |
| PUT    | `/api/cli-tools/antigravity-mitm/alias` | Spara modellalias för ett verktyg              |

Målvärd som avlyssnas: **`daily-cloudcode-pa.googleapis.com`** (Antigravitys uppströmsserver).

### Startsekvens (`src/mitm/manager.ts::startMitm`)

1. Generera ett självsignerat certifikat via `selfsigned` (RSA-2048, SHA-256, 1 år) — `cert/generate.ts`
2. Installera certifikatet i systemets betrodda certifikatarkiv — `cert/install.ts`
3. Lägg till hosts-posten `127.0.0.1 daily-cloudcode-pa.googleapis.com` — `dns/dnsConfig.ts`
4. Starta `src/mitm/server.cjs` med `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (standardvärde `443`)
5. Spara PID i `<DATA_DIR>/mitm/.mitm.pid`

### Dynamisk identifiering av betrodda certifikatarkiv i Linux — `cert/install.ts`

`getLinuxCertConfig()` går igenom en prioriteringslista och väljer den första befintliga katalogen:

| Distributionsfamilj      | Katalog                                     | Uppdateringskommando     |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Certifikatets filnamn: `omniroute-mitm.crt`. Fingeravtrycksmatchning via `getCertFingerprint()` (SHA-1 av DER).

Dessutom installerar `updateNssDatabases()` certifikatet i NSS-databaser per användare när `certutil` är tillgängligt: `~/.pki/nssdb`, `~/snap/chromium/.../nssdb`, alla Firefox-profiler (inklusive snap), under smeknamnet **`OmniRoute MITM Root CA`**.

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** PowerShell med förhöjda behörigheter → `certutil -addstore Root`

### Autentisering

Alla MITM-slutpunkter kräver hanteringsautentisering (`requireCliToolsAuth`). Sudo-lösenordet cachelagras inom modulens omfång (aldrig i `globalThis`) och rensas vid `stopMitm()`.

## Sanering av inkommande huvuden

OmniRoute rensar inkommande klienthuvuden före vidarebefordran, så att en begäran som kommer från Cursor inte läcker `User-Agent: Cursor/X.Y.Z` till en Claude-uppströmsserver. Se `src/shared/constants/upstreamHeaders.ts` för spärrlistan, som hålls synkroniserad med Zod-schemana och enhetstesterna.

## Uppdatera fingeravtryck när en leverantör byter dem

1. Samla in trafik från det officiella CLI-verktyget med `mitmproxy` (TLS-avlyssning + dump)
2. Extrahera JA3/JA4 och den exakta ordningen på huvudena
3. Uppdatera den relevanta posten i `CLI_FINGERPRINTS[...]`
4. Uppdatera det matchande standardvärdet för `*_USER_AGENT` i `.env.example`
5. Om själva TLS-handskakningen har ändrats, uppdatera den relevanta leverantörswrappern eller alternativet `browser:` för wreq-js
6. Kör de leverantörsspecifika TLS-testerna och ett manuellt kanarietest mot den aktiva leverantören
7. Leverera i en patchversion; dokumentera i `CHANGELOG.md`
