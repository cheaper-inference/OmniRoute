## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Skriv en funktion som..."}
  ],
  "stream": true
}
```

### Anpassade headers

| Header                   | Riktning | Beskrivning                                                                                                                                                                                                         |
| ------------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Begäran  | Ange `true` för att kringgå cachen                                                                                                                                                                                  |
| `x-omniroute-no-memory`  | Begäran  | Ange `true` för att hoppa över injicering av minne och färdigheter för denna begäran (motsvarar no-cache och undviker overhead för token och kostnad per anrop)                                                     |
| `X-OmniRoute-Progress`   | Begäran  | Ange `true` för förloppshändelser                                                                                                                                                                                   |
| `X-Session-Id`           | Begäran  | Beständig sessionsnyckel för extern sessionstillhörighet                                                                                                                                                            |
| `x_session_id`           | Begäran  | Varianten med understreck accepteras också (direkt HTTP)                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | Begäran  | Sessions-/konversationstagg som anges av anroparen (används även av minnet). När den finns sparas den ordagrant i `call_logs.session_tag` för kostnadsfördelning per session (#8249) — skapas aldrig när den saknas |
| `Idempotency-Key`        | Begäran  | Nyckel för deduplicering (5 s fönster)                                                                                                                                                                              |
| `X-Request-Id`           | Begäran  | Alternativ nyckel för deduplicering                                                                                                                                                                                 |
| `x-omniroute-connection` | Begäran  | Lås en begäran för en enskild modell till en leverantörsanslutning (ett konto) via dess id — se [Kontolåsning per begäran](#account-pinning-per-request)                                                            |
| `X-OmniRoute-Cache`      | Svar     | `HIT` eller `MISS` (utan strömning)                                                                                                                                                                                 |
| `X-OmniRoute-Idempotent` | Svar     | `true` om deduplicerad                                                                                                                                                                                              |
| `X-OmniRoute-Progress`   | Svar     | `enabled` om förloppsspårning är aktiverad                                                                                                                                                                          |
| `X-OmniRoute-Session-Id` | Svar     | Effektivt sessions-ID som används av OmniRoute                                                                                                                                                                      |
| `X-OmniRoute-Request-Id` | Svar     | Korrelations-id för begäran (när det är känt)                                                                                                                                                                       |
| `X-OmniRoute-Version`    | Svar     | OmniRoutes byggversion (alltid angiven)                                                                                                                                                                             |
| `X-OmniRoute-Cost-Saved` | Svar     | USD som cachen sparade vid en HIT (endast cacheträffar)                                                                                                                                                             |
| `X-OmniRoute-Decision`   | Svar     | Routningsspårning: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` är kombinationsstrategin eller `single` för en begäran utan kombination) — anges alltid i slutförda svar                           |

> Nginx-anmärkning: om du använder headers med understreck (till exempel `x_session_id`) ska du aktivera `underscores_in_headers on;`.

#### Kontolåsning per begäran

När en leverantör har flera anslutningar (konton eller nycklar) väljer OmniRoute normalt en
via sin strategi för kontoval. En begäran kan i stället låsas till en specifik anslutning
med headern `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <din OmniRoute-API-nyckel>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hej"}]}'
```

- **Var du hittar id:t.** Öppna leverantörssidan i kontrollpanelen
  (**Kontrollpanel → Leverantörer → <provider>**) och klicka på id-brickan `xxxxxxxx…` på en
  anslutningsrad – då kopieras hela anslutnings-id:t.
- **Vilka förfrågningar som respekterar det.** Förfrågningar med en enda modell (`provider/model`) till
  `/v1/chat/completions`, `/v1/messages` och `/v1/responses`. Kombinationer ignorerar headern: fäst
  i stället ett konto för varje kombinationssteg via stegets egen anslutning.
- **Fästningen är strikt, inte en preferens.** Den fästa anslutningen används exklusivt. Ett
  fel i förfrågningen registrerar kontots nedkylningsperiod men växlar **inte** till ett
  annat konto hos samma leverantör.
- **Nedkylning och kvotbegränsningar frigör fästningen.** Medan den fästa anslutningen är i en nedkylningsperiod,
  har förbrukat sin kvot eller blockeras av en kvotpolicy, faller senare förfrågningar tillbaka till leverantörens
  andra anslutningar, precis som trafik utan fästning.
- **Okända eller inaktiverade id:n misslyckas.** Ett id som inte finns i leverantörens aktiva pool (raderat,
  inaktiverat eller tillhörande en annan leverantör) innebär att det inte finns något kvalificerat konto, så förfrågningen
  misslyckas i stället för att obemärkt dirigeras någon annanstans.

Claude Code skickar anpassade headrar via `ANTHROPIC_CUSTOM_HEADERS`. Placera den i `env`-blocket
i `~/.claude/settings.json`, eller i en `.claude/settings.json` på projektnivå för att fästa ett annat
konto för varje projekt:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Källa: `src/sse/handlers/chat.ts` (läsning av header), `src/sse/services/auth.ts` och
`src/sse/services/sessionAffinityPin.ts` (frigöring av fästning och kontroll av frånvaro i poolen).

> **Headrar för kostnadstelemetri:** lyckade svar utan strömning innehåller också uppsättningen `X-OmniRoute-*` för kostnadstelemetri – `X-OmniRoute-Response-Cost` (USD, exakt 10 decimaler; `0.0000000000` för kostnadsfria/prissättningslösa anrop), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` och `X-OmniRoute-Fallback-Attempts` (endast när > 0), samt `X-OmniRoute-Request-Id` och `X-OmniRoute-Version`. Dessa skickas av chat completions, `/v1/responses`, `/v1/messages` **och medieändpunkterna** – `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` och `/v1/moderations` (alltid kostnad `0`). Mediekostnaden beräknas per modalitet (per bild, per sekund, per tecken eller per sökenhet) när prissättning finns tillgänglig, annars `0` (tillåtande vid fel).

> **Kostnadssemantik vid cacheträff:** vid en TRÄFF i den semantiska cachen (`X-OmniRoute-Cache-Hit: true`) görs inget anrop uppströms, så `X-OmniRoute-Response-Cost` är `0.0000000000` (den **inkrementella** kostnaden för att leverera träffen). Den ursprungliga/kostnaden som annars skulle ha uppstått rapporteras separat i `X-OmniRoute-Cost-Saved`. Faktureringssystem bör summera `X-OmniRoute-Response-Cost` (träffar kostar ingenting); cacheanalys kan aggregera `X-OmniRoute-Cost-Saved`.

## Exklusiva hanterade sessionsleasingavtal

Exklusiv hanterad sessionsleasing är ett frivilligt, klientneutralt routingkontrakt: en aktiv ägare
innehar en kvalificerad OmniRoute-anslutning. Det leasar inte en modell, kräver OAuth, identifierar en
specifik klient eller kräver en specifik leverantör.

Den autentiserande API-nyckeln måste ha scope `lease:exclusive` och en explicit icke-tom
`allowedConnections`-lista. Databasens mutationsgräns upprätthåller båda fälten tillsammans vid nyckel-
skapande och partiella uppdateringar.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Framgångsrika svar för förvärv, förnyelse och frigörelse exponerar tidsstämplar, `state` och den exakta positiva
`generation`, men aldrig den valda anslutningen eller autentiseringsuppgifterna. Förnyelse och frigörelse tillhandahåller
generationen i JSON-kroppen:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

En aktiv leasingägare kan uttryckligen begära integritetssäker visningsmetadata för sin nuvarande bindning:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Denna frivilliga statusåtgärd är avgränsad av den opaka ägaren, autentiserad hanterad API-nyckel och exakt
aktiv generation i en databastransaktion. `displayName` är endast det trimmade konfigurerade
anslutningsnamnet; det är `null` när inget säkert konfigurerat namn finns. OmniRoute ersätter aldrig en
e-postadress eller genererad kontoidentitet. Leverantörsvärdet är en icke-känslig visningsetikett och aldrig
en genererad kompatibel-leverantörsidentifierare. Autentiseringsuppgifter, tokens, cookies, råa anslutnings- eller API-
nyckel-ID, ägarhashar, avgränsningshemligheter och interna routingdata är exkluderade.

Felaktig nyckel, felaktig ägare, föråldrad generation, saknade, utgångna, frigivna och ogiltigförklarade uppslagningar
returnerar alla samma `409 LEASE_FENCE_STALE`-fel utan anslutningsmetadata. En klient som fick kapacitetsväntesvaret har ingen aktiv bindning att inspektera. När routing övergår en aktiv leasing,
förblir samma generation giltig och status returnerar atomärt den nya bindningen, aldrig den gamla.
Befintliga klienter förblir oförändrade eftersom förvärv, förnyelse, frigörelse och väntande svar behåller
sina tidigare former.

Detta serverkontrakt ändrar inte standard OpenAI Codex `/status`. Standard Codex rapporterar för närvarande sin
modellleverantör och inbyggda autentiserings-/kontostatus men återger inte godtycklig anpassad
leverantörskontometadata; en senare klientintegration måste anropa denna åtgärd och bestämma hur man
visar `connection.displayName`.

Varje hanterad inferensförfrågan tillhandahåller sedan båda kontrollhuvudena:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Den exakta ägaren, generationen, aktiva anslutningen och autentiserade API-nyckeln avgränsas omedelbart
före varje stödd uppströmsförsök. Att spela upp ägare och generation med en annan nyckel misslyckas även
när den nyckeln tillåter samma anslutning. Råa ägare sparas inte, loggas, behålls i
förfrågningsögonblicksbilden eller vidarebefordras uppströms.

Tillfällig konkurrens returnerar HTTP `429` med `Retry-After` och:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Detta svar betyder endast att den vanliga kvalificerade uppsättningen var icke-tom och varje ledig kandidat hölls av en främmande aktiv leasing. Ej stödda modeller/leverantörer, policyavvikelser, nedkylning, kvot, hälsa och andra vanliga kvalificeringsfel behåller sina befintliga OmniRoute-svar.

### `x-omniroute-compression`

Åsidosättning per begäran av komprimeringsplanen. Högsta prioritet – slår routing-combo-
åsidosättningen, den aktiva profilen, auto-trigger och panelens standard. Värden:

| Värde         | Effekt                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------- |
| `off`         | Ingen komprimering för denna begäran.                                                                     |
| `default`     | Den panelhärledda standardprofilen (ignorerar den aktiva profilen). Förlustfria motorer lämnas avstängda. |
| `safe`        | Endast deduplicering och hopfällning av blanksteg.                                                        |
| `allow-lossy` | Behåll operatörsplanen för denna begäran, inklusive sammanfattningar och stilomskrivningar.               |
| `engine:<id>` | En enda motor när den är aktiverad, t.ex. `engine:rtk`. Frivillig per begäran för den motorn.             |
| `<combo>`     | En namngiven kombination, matchas först efter namn (skiftlägesokänsligt), sedan efter ID.                 |

Anmärkningar:

- Okända värden ignoreras (begäran avvisas aldrig); upplösningen faller igenom till den normala operatörsprioriteten.
- Om flera kombinationer delar ett namn, skicka kombinations-**ID** för en deterministisk matchning.
- En kombination vars namn är `off` eller `default` kan inte väljas med namn (dessa nyckelord tolkas först); referera till en sådan kombination med dess ID.
- Huvudkomprimeringsomkopplaren är en hård grind: när komprimering är globalt inaktiverad kan denna rubrik inte aktivera den.

Den tillämpade planen återges i svarshuvudet:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

där `<source>` är en av `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` eller `off`.

## Inbäddningar

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Tillgängliga leverantörer: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog-ID:n anges som `provider/model` (exempel: `jina-ai/jina-embeddings-v5-omni-small`). Fristående Jina-modell-ID:n som förekommer i registret (exempelvis `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) kan också matchas. Jinas funktioner för inbäddning, omrankning, klassificering och segmentering använder först autentiseringsuppgifterna för `jina-ai` från kontrollpanelen; `JINA_AI_API_KEY` används endast som reserv när det inte finns någon nyckel i kontrollpanelen. Kortet `jina-reader` är endast avsett för Reader / `r.jina.ai` (`POST /v1/web/fetch`) och tillhandahåller aldrig inbäddningar eller omrankning.

Registermodeller som anger stöd för multimodalitet accepterar även upp till 32 leverantörsneutrala strukturerade
objekt. Medieobjektens typer är `text`, `image`, `audio`, `video` och `document`. Deras `source`
är antingen `{"type":"url","url":"https://..."}` eller
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
och familjealiaset `jina-ai/jina-embeddings-v5-omni` → omni-small) accepterar även Jinas inbyggda
EmbeddingsV5Request-dokument och **vidarebefordrar dem oförändrade** till `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

Inbyggda värden för `{ image | audio | video | pdf }` kan vara en offentlig HTTPS-URL, en `data:`-URI eller rå
base64. OmniRoute konverterar inte dessa objekt till strängar och hämtar inte inbyggda bild-URL:er – Jina hämtar
offentliga medier själv. Ytterligare Jina-fält (`task`, `normalized`, `truncate`, `embedding_type`)
vidarebefordras. Jina-SKU:er som endast stöder text avvisar fortfarande dokument som inte är text.

Säkerhets- och transportgränser:

- URL:er till externa medier måste vara offentliga och använda HTTPS. Kanoniska `{type,source:url}`-objekt hämtas
  på serversidan (förnyad validering av omdirigeringar, tidsgräns, storleksgränser, offentlig DNS, anslutningslåsning) och
  bäddas in före leverantörsanropet. Jinas inbyggda `{image:"https://..."}`-objekt vidarebefordras som de är
  efter samma kontroll av offentlig HTTPS; Jina hämtar URL:en.
- Infogade base64-medier är begränsade till 8 MiB avkodad data per objekt och 16 MiB avkodad data för hela begäran.

Leverantörsöversättning (kanoniska objekt vidarebefordras aldrig oförändrade):

- Jinas multimodala modeller: varje objekt på toppnivå blir ett modalitetsnycklat objekt
  (`text` / `image` / `audio` / `video` / `pdf`) som använder data-URI:er för infogade medier; en vektor per
  objekt på toppnivå.
- Gemini Embedding 2-familjen: en array på toppnivå blir en enda inbyggd
  `models/{model}:embedContent`-begäran med `content.parts` (`text` eller `inline_data`).
- llama.cpp (`llama-cpp/<model>`, valfri modell som den lokala servern har läst in): kanoniska `text`-objekt
  blir vanliga strängar, medan `image` / `audio` / `video` blir varsitt
  `{"content": [part]}`-objekt som använder llama-servers innehållsdelar för chatt (`image_url`,
  `input_audio` med formatet `wav` / `mp3` / `flac`, `input_video`) med infogade data; en vektor
  per objekt på toppnivå. Servern måste köras med `--embedding --mmproj …`; utan en projektor
  avvisar den själv medier. `document` stöds inte.
- Okända/dynamiska modeller utan explicit metadata om modaliteter avvisar strukturerade indata med HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Kombinationer av modell och modalitet som inte stöds returnerar HTTP 400 i stället för att konvertera objektet. Utökningsfält
som inte är indata i äldre sträng-/tokenbegäranden fortsätter att skickas vidare oförändrade.


## Bildgenerering

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Tillgängliga leverantörer inkluderar OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokalt), ComfyUI (lokalt).

`n` returnerar `n` bilder i `data[]`. För leverantörer vars överordnade API returnerar en bild per anrop
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) görs `n` separata anrop till den överordnade tjänsten, med högst 4 samtidiga anrop. Ett
fast `seed` förskjuts med anropets index (`seed`, `seed + 1`, …), så att bilderna skiljer sig åt men förblir
reproducerbara. `n` är begränsat till 10. Hela begäran misslyckas om något anrop misslyckas. Listan
över format som använder parallella anrop finns i `SINGLE_IMAGE_FANOUT_FORMATS` i
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux återanvänder den befintliga API-nyckelanslutningen och accepterar prefixen `zenmux/` eller `zm/`:

- `zenmux/openai/gpt-image-2` använder ZenMux OpenAI Images API. Alternativen inkluderar `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` och `response_format`.
- Andra utgivare, såsom `zm/meta/muse-image-1.0`, använder ZenMux Vertex AI-ändpunkt `:predict`.
  `n` mappas till `sampleCount`, `aspect_ratio` till `aspectRatio` och `image_size`
  (`1K`, `2K`, `4K`) till `sampleImageSize`. Ett pixelvärde för `size` anger endast ett bildförhållande,
  inte garanterade pixeldimensioner. Vilka bildförhållanden, upplösningar och antal som stöds varierar beroende på modell.
- `zm/inclusionai/ming-image-0.1-design` väljer sina egna dimensioner. Utelämna `size`,
  `aspect_ratio` och `image_size`; uttryckliga värden returnerar HTTP 400. PNG, JPEG och WebP
  kan begäras med `output_format`.

Den här integrationen stöder text-till-bild-generering, inte redigering med referensbilder. Utdata från Vertex
normaliseras till `data[].b64_json`; `response_format: "url"` returnerar en överordnad
HTTPS-URL eller en base64-data-URL när endast bilddata är tillgängliga. Tomma eller filtrerade utdata
returnerar ett fel i stället för ett tomt lyckat svar. Modellåtkomst beror på ZenMux-kontot.
Se [ZenMux Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) och
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

`model` väljer OCR-leverantör via prefixet `provider/model`. Ett modell-id utan prefix (t.ex.

| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Synkron, via Vertex AI:s partner-endpoint `openapi/chat/completions` — se nedan för autentisering/webbadress. |

Alla tre leverantörerna svarar med samma Mistral-formaterade innehåll:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extraherad text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Pollingflöde för Azure Document Intelligence

Azure Document Intelligences `analyze`-API är asynkront: den ursprungliga begäran returnerar ett
`Operation-Location`-huvud i stället för ett svarsinnehåll, och resultatet måste hämtas genom polling. Hanteraren
(`open-sse/handlers/ocr.ts`) frågar denna webbadress varje sekund i upp till 30 försök, avbryter omedelbart (fortsätter
inte att fråga) vid ett pollingsvar som inte är `ok` eller vid statusen `"failed"`, och returnerar `504` om
åtgärden fortfarande körs efter att antalet tillåtna försök har förbrukats. Det slutliga Azure-svaret
normaliseras till samma `pages`-/`markdown`-format som används av Mistral innan det returneras till
anroparen, så klientkoden behöver inte specialhantera leverantören.

### Autentisering och endpoint-matchning för Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` återanvänder samma Vertex AI-autentisering som OmniRoute redan stöder för
chatt-/bildtrafik (`open-sse/executors/vertex.ts`): anslutningens API-nyckel är antingen autentiseringsuppgifter
i Service Account JSON-format (som byts ut mot en kortlivad OAuth-åtkomsttoken via JWT Bearer-flödet)
eller en redan utfärdad OAuth-åtkomsttoken som används i befintligt skick. Webbadressen till uppströms-endpointen är Vertex generiska
partner-endpoint `openapi/chat/completions`, som skapas utifrån anslutningens projekt och
region — ett explicit `providerSpecificData.project`/`providerSpecificData.region` har alltid företräde;
annars härleds projektet från Service Account JSON-objektets `project_id` och regionens
standardvärde är `us-central1`. Båda matchningarna sker i `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) och används av
`src/app/api/v1/ocr/route.ts` innan anropet skickas vidare till `handleOcr`.

### Modell-id-prefix (`?prefix=`)

De flesta modeller publiceras under ett **leverantörsprefix**. Vilket prefix du får styrs av
funktionsflaggan `MODELS_CATALOG_PREFIX_MODE` och kan åsidosättas **per begäran** med en
frågeparameter – användbart för en klient som vill ha en ren lista utan att ändra den
serverövergripande inställningen för alla andra:

```bash
GET /v1/models?prefix=alias        # ett id per modell – det korta aliasprefixet
GET /v1/models?prefix=dual         # båda formerna (serverns standardvärde)
GET /v1/models?prefix=canonical    # endast det fullständiga leverantörs-id-prefixet
```

| Läge        | Genererar                                                 | Kommentarer                                                                                                                                                                                         |
| ----------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **och** `claude/claude-sonnet-4-6` | **Standard.** Båda id:n dirigeras till samma modell; behålls så att klientkonfigurationer där någon av formerna är hårdkodad fortsätter att fungera. Fördubblar katalogen ungefär.                  |
| `alias`     | `cc/claude-sonnet-4-6`                                    | En post per modell. Leverantörer utan ett separat alias genererar fortfarande sin post, så ingenting går förlorat.                                                                                  |
| `canonical` | `claude/claude-sonnet-4-6`                                | En post per modell under det fullständiga leverantörs-id-prefixet. Leverantörer utan ett separat alias (t.ex. `antigravity/…`, `agy/…`) genererar även här sitt enda id, så ingenting går förlorat. |

En spegling i läget `dual` kan också identifieras utan frågeparametern: den innehåller ett
`parent`-fält som pekar på det primära id:t.

Klienter som återger en modellväljare bör begära `?prefix=alias` – det är vad
[OmniCopilot-tillägget för VS Code](../guides/VSCODE-COPILOT.md) gör.

### Identifieringsfilter (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accepterar valfria identifieringsfilter. Utan något av dem är svaret
oförändrat. De begränsar katalogen som anroparen redan kan se (API-nyckelbehörigheter tillämpas först),
och de körs före OpenAI-liknande sidindelning med `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # varje angiven funktion måste vara aktiverad
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogens `type`; rader utan en sådan är `chat`
GET /v1/models?q=sonnet&limit=10                           # skiftlägesokänslig matchning mot id eller namn
```

| Parameter     | Värden                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | icke-negativt heltal, jämförs med `context_length`                                                  |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 tecken                                                                                        |

Ett okänt värde, eller ett `min_context` som inte är ett icke-negativt heltal (till exempel `1.5`),
returnerar HTTP `400`, och meddelandet listar de giltiga värdena. Implementering:
`src/app/api/v1/models/catalogFilters.ts`.

### Begränsad modellista (`POST /v1/models/query`)

`POST /v1/models/query` returnerar en kort, deterministisk lista från samma katalog, med samma
autentisering och synlighet per nyckel som `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Alla fält är valfria. `capabilities` och `exclude` tar en matris eller en kommaseparerad sträng;
`max_output` jämförs med `max_output_tokens`. Resultaten sorteras efter `owned_by` och därefter `id`.
`limit` har standardvärdet `20`, och värden över `100` begränsas till `100`. Ogiltig JSON, ett okänt
fält eller ett ogiltigt värde returnerar HTTP `400`.

### Individuellt dolda chattmodeller

En modell som är markerad som **Dold** på sin leverantörssida utesluts från katalogen och avvisas
med HTTP `404` / `model_not_found` när den begärs uttryckligen. Kontrollen använder den matchade
leverantören och modellen, inklusive leverantörsalias, nodprefix för kompatibla leverantörer och
standardvärden för anslutningar. En kombination hoppar över dolda mål och kan använda ett synligt syskon; när inget
körbart mål återstår returneras samma felkod. Att sluta dölja en modell börjar gälla vid nästa
begäran. Synlighetsåsidosättningar enbart för bilder döljer inte chattmodellen med samma id.

Den här individuella modellinställningen är separat från
[tillåt-/neka-listorna för modellexponering](../routing/MODEL_EXPOSURE_LIST.md), som filtrerar katalogens
publicerade modeller och kandidater för automatisk dirigering, samtidigt som uttrycklig dirigering behålls. Modellbehörigheter
för API-nycklar fortsätter att gälla oberoende. Katalogens standardläge för prefix förblir `dual`.

### Modellvarianter utan tänkande

För Claude-modeller med stöd för tänkande publicerar `/v1/models` även en variant **utan tänkande** vars id har prefixet `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Om du väljer detta id (t.ex. i en Claude Code-konfiguration som alltid bifogar ett `thinking`-block) matchas det tillbaka till den verkliga `<provider>/<model>` med resonemang inaktiverat — `thinking:{type:"disabled"}` på sökvägen `/v1/messages`, eller genom att fälten `reasoning`/`reasoning_effort` tas bort på sökvägen `/v1/chat/completions`. Varianten listas endast för modeller i Claude-familjen som stöder thinking **och** respekterar `disabled` (så t.ex. modeller som enbart stöder adaptivt läge och avvisar `disabled` exkluderas). Operatörer kan aktivera eller inaktivera varianten per modell via `ModelSpec.noThinkingAlias`.

### Exa och Tavily `provider_options`

Exa och Tavily läser leverantörsspecifika fält från en namnrymdsindelad behållare:
`provider_options.exa` (eller `provider_options["exa-search"]`) och `provider_options.tavily`
(eller `provider_options["tavily-search"]`). Endast nycklarna nedan vidarebefordras. Var och en
kontrolleras mot sitt eget Zod-schema i `open-sse/handlers/search/providerOptionsPassthrough.ts`,
och en nyckel med fel typ tas bort. Alla andra nycklar ignoreras, inklusive autentisering, bas-URL,
`stream` och `outputSchema`. De platta nycklar som används av andra leverantörer (`cx`, `depth`, ...) fungerar
som tidigare.

| Leverantör | Fält på toppnivå                                                                                                                                                                                                                                                                                                                                                          | Nästlade                                                                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa        | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (platta primitiva värden), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` sammanfogas ovanpå standardvärdet `{ text: true, highlights: true }` |
| Tavily     | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                           |

De generiska fälten har alltid företräde: `query`, `max_results`, `filters` (domäner), `country` och det
ämne som härleds från `search_type`. För Exa behåller `search_type: "news"` värdet `category: "news"`.
Tavily accepterar även `search_type: "finance"` (`topic: "finance"`).

Det generiska `time_range` når nu båda leverantörerna: Exa får `startPublishedDate` (ISO-
tidsstämpel) och Tavily får `start_date` (`YYYY-MM-DD`). Ett explicit datum i `provider_options`
åsidosätter det mappade datumet.

Exa-resultat behåller `id`, `highlight_scores`, `summary`, `subpages`, `entities` och `extras` i
`provider_raw`. Tavily-resultat behåller `images` och `favicon`.

Kostnadsredovisningen använder fortfarande det platta registret `costPerQuery`. Tavily debiterar
fler krediter per anrop för `search_depth: "advanced"`, och denna skillnad återspeglas inte i
`usage.search_cost_usd`.

## API för webbhämtning

Extrahera innehåll från en URL via en konfigurerad leverantör för webbhämtning (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, samma API-nyckel som Parallel Search) returnerar endast Markdown
— alla andra `format` ger `400` — och begränsar innehållet till 100 000 tecken. När
målsidan i sig inte kan extraheras rapporterar den överordnade tjänsten detta inuti ett HTTP 200-svar;
OmniRoute exponerar det som ett `422` med ett fast meddelande.

| Metod | Sökväg          | Beskrivning                                                      |
| ----- | --------------- | ---------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Hämta/skrapa en URL — brödtexten valideras av `v1WebFetchSchema` |

**Autentisering:** Bearer-API-nyckel (`extractApiKey` + `isValidApiKey`). Policyn tillämpas via `enforceApiKeyPolicy`.

**Kvotmedveten reservlösning (#8297):** när ingen uttrycklig `provider` anges gås poolen
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) igenom i fast
prioritetsordning (fyll först) — en hastighetsbegränsad men konfigurerad leverantör hoppas över
i stället för att avsluta begäran direkt, och ett återförsökbart/kvotrelaterat fel från den överordnade tjänsten
(HTTP 429 alltid; 402/403 för kvotrelaterade kostnadsfria nivåer hos Firecrawl/Tavily/TinyFish —
inte för Jina Reader och aldrig för en vanlig felaktig 400-begäran) går vidare till
nästa ännu oprövade leverantör med konfigurerade autentiseringsuppgifter vid tidpunkten för begäran. När alla leverantörer i
poolen är uttömda returnerar ändpunkten ett enda `429` (med ett `Retry-After`-
huvud) i stället för det tidigare generiska `400`. När en uttrycklig `provider`
begärs sker **ingen** tyst reservväxling — en hastighetsbegränsad eller felande uttrycklig
leverantör exponerar sitt eget fel (`429` vid hastighetsbegränsning, annars den överordnade tjänstens
status).

### Responses API över WebSocket (endast codex)

```bash
# Samma värd:port som HTTP-API:t (standard 20128); uppgradera anslutningen:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (eller: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Den första ramen MÅSTE vara response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

En proxy för Responses-API-over-WebSocket är kopplad **uteslutande till `codex`** (ChatGPT-
serverdelen). Den lyssnar på samma port som API:t/instrumentpanelen på sökvägarna `/v1/responses`,
`/responses` och `/api/v1/responses`. Vid den första `response.create`-ramen
autentiserar och förbereder den via den interna bryggan `codex-responses-ws`, väljer en
codex OAuth-anslutning och tunnlar till `wss://chatgpt.com/backend-api/codex/responses`
via transporten `wreq-js`. **Modeller som inte är codex avvisas** (`codex_ws_provider_required`).
För kvotdelningsroutning, använd `model: "qtSd/<group>/codex/<model>"`. Implementerat i
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autentisering:** Bearer-API-nyckel under handskakningen. Den medföljande HTTP-servern (`server-ws.mjs`)
måste vara den aktiva startpunkten (vilket den är som standard när `app/server-ws.mjs` finns).

#### Modell-id: använd det rena ChatGPT-id:t (utan prefixet `codex/`)

OpenAI **Codex CLI** validerar modellnamnet på klientsidan när
`supports_websockets = true` och **avvisar id:n med leverantörsprefix** såsom
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Skicka det **rena** id:t (t.ex. `gpt-5.5`). OmniRoutes brygga är
endast avsedd för codex, så den matchar om ett rent id som en codex-modell
(`resolveCodexWsModelInfo`) innan den tunnlar uppströms — även om ett rent
`gpt-5.5` annars skulle routas till en annan leverantör över HTTP.

#### Konfigurera OpenAI Codex CLI

Rikta Codex CLI mot OmniRoute genom att lägga till en anpassad leverantör med WebSocket-
stöd i `~/.codex/config.toml` (använd en separat `CODEX_HOME` för att undvika att ändra
en befintlig konfiguration):

```toml
model = "gpt-5.5"                 # rent id — INTE "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # inget avslutande snedstreck; WS-URL:en härleds (använd https/wss i produktion)
wire_api = "responses"                    # enda värdet som stöds sedan februari 2026
supports_websockets = true                # aktiverar Responses-over-WS-transporten
env_key = "OMNIROUTE_API_KEY"             # innehåller OmniRoute-API-nyckeln (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # en OmniRoute-API-nyckel (valfri nyckel om REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI:t uppgraderar `base_url + /responses` till en WebSocket och OmniRoute tunnlar den
till den valda codex OAuth-anslutningen. Validerat från början till slut mot den lokala
servern: ChatGPT returnerar `codex.rate_limits` + `response.created` och strömmar
slutförandet.

## Självbetjäningsanvändning (`/api/usage/om-usage`)

Alla API-nycklar kan läsa **sin egen** användning och sina kvoter — ingen hanteringsautentisering krävs. Det här är slutpunkten som en
klient (CLI, OmniCopilot-panelen) använder för att visa nyckelinnehavaren dennes kostnader.

```bash
# Textformat (det historiska kontraktet — vanlig text för en terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Strukturerat format — det som ett användargränssnitt använder
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Nyckeln måste ha **`allowUsageCommand`** aktiverat (inaktiverat som standard — kontrollpanelens hanterare för API-nycklar
växlar detta per nyckel). Utan det svarar slutpunkten med `403`.

`?format=json` returnerar en diskriminerad struktur så att en anropare aldrig läser ett datafält från ett
avslag. Vid framgång:

```jsonc
{
  "allowed": true,
  // finns endast när nyckeln har valt att använda användningsgränser per nyckel (dagligen/veckovis i USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ögonblicksbilden av kvoten för den valda leverantören, eller null när inget ännu har cachelagrats:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // ögonblicksbilden för varje anslutning, så att ett användargränssnitt kan visa flera leverantörer sida vid sida:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Vid avslag (`401` felaktig nyckel / `403` inte tillåtet) returnerar samma rutt
`{ "allowed": false, "error": { "message": "…" } }` — ett befintligt men tomt `personal`/`provider`
(nyckeln är tillåten, men inget har ännu hämtats) är ett annat tillstånd än ett avslag, och endast JSON-formatet
skiljer dem åt.

**Autentisering:** anroparens egen Bearer API-nyckel, validerad med `isValidApiKey` — detta är _inte_
hanteringsgränssnittet (`/api/keys/…`), som fortfarande skyddas av `requireManagementAuth`.

### Råa kontra brytgränsjusterade kvotprocent

Vid användning av `/api/usage/om-usage` bör anropare observera skillnaden mellan de
procentvärden som visas i **klartextutdata** och strukturerade **JSON-utdata**:

| Aspekt                | Klartextformat (`/api/usage/om-usage` / `@@om-usage`)                                     | JSON-format (`?format=json`)                                                 |
| :-------------------- | :---------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **Utdatafält**        | `NN% left` (t.ex. `20% left`)                                                             | `provider.quotas` / `providers[].quotas`                                     |
| **Mätning**           | **Brytgränsjusterat användbart utrymme**: återstående kapacitet över brytgränsen          | **Rå uppströmskvot**: ojusterat mätvärde från leverantören                   |
| **Brytgränsskalning** | Skalas via `effectiveRemainingPercent()` så att den skyddade reserven visas som `0% left` | Ingen (råa ögonblicksbildsvärden som rapporterats av leverantören)           |
| **Tröskeldata**       | Ingår i det visade procentvärdet                                                          | Lagras i `quotaWindowThresholds` per anslutning (eller serverstandardvärden) |
| **Primär konsument**  | Interaktiva CLI-verktyg, terminalprompter, mänskliga operatörer                           | Programmatiska integrationer, kontrollpaneler, analys, kostnadsspårare       |

#### Formeln för brytgränsjustering

OmniRoute stöder proaktiva kvotgränser för att förhindra att uppströmsresurser tar slut (konfigurerat via anslutningens
`quotaWindowThresholds`, leverantörens standardvärden eller globala inställningar för motståndskraft). När en brytgräns
(t.ex. `cutoff = 25%`) är aktiv för ett kvotfönster beräknar textrenderaren återstående utrymme så här:

- Om `remaining <= cutoff`: returnerar `0%`.
- Om `remaining > cutoff`: returnerar `((remaining - cutoff) / (100 - cutoff)) * 100`.

Den formaterade textutdatan avrundar detta till närmaste heltal (`Math.round(...)`).

#### Illustrativt exempel

Anta ett leverantörsfönster med **60 % rå användning** (och därmed **40 % rå återstående kvot**) och en konfigurerad
brytgräns på **25 % återstående kvot**:

| Representation               | Beräkning                                          | Återstående |               Underförstått använt               |
| :--------------------------- | :------------------------------------------------- | :---------: | :----------------------------------------------: |
| **Rå JSON (`?format=json`)** | Uppströmsögonblicksbild (`quotas[window]`)         |  **40 %**   |                     **60 %**                     |
| **Textformat (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20 %**   | **80 %** (om det beräknas som `100 - remaining`) |

- **Varför texten visar 20 % kvar:** Av de 40 % av den fysiska kvoten som återstår på kontot reserveras 25 % av
  brytgränspolicyn. Anroparen har endast 15 % av 75 % användbart utrymme kvar innan routern slutar
  dirigera till denna anslutning. Skalningen säkerställer att anslutningen signalerar uttömning (`0% left`) exakt när
  dirigeringen upphör.
- **Varför JSON bevarar råvärden:** JSON-nyttolasten returnerar den exakta ögonblicksbilden från leverantören (`UsageSnapshot`)
  så att externa verktyg får tillgång till den faktiska uppströmsanvändningen och anslutningsspecifika
  `quotaWindowThresholds` utan informationsförlorande skalning på serversidan.

#### Vägledning för migrering av konsumenter

Om en extern integration (t.ex. ett redigeringsinsticksprogram eller agenttillägg) tidigare skrapade textslutpunkten
(`NN% left`) och beräknade använd procent som `100 - NN`, innebär en migrering till `?format=json` följande:

- Avläsning av råa JSON-värden återspeglar **den faktiska uppströmsförbrukningen** (60 % använt i exemplet ovan).
- Om integrationen vill bevara textslutpunktens semantik för användbart utrymme kan den utvärdera
  formeln för effektivt återstående utrymme på klientsidan med hjälp av `quotaWindowThresholds` för anslutningsspecifika åsidosättningar.

## Semantisk cache

```bash
# Hämta cachestatistik
GET /api/cache/stats

# Rensa alla cachar
DELETE /api/cache/stats
```

Exempel på svar:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Påverkan på latens

En TRÄFF i den semantiska cachen levererar svaret från cachen **utan ett uppströmsanrop**, så den rapporterade `X-OmniRoute-Response-Latency` är nära noll
(oavsett den ursprungliga uppströmslatensen). Latenskänsliga klienter
(prestandamätning, p50/p99-övervakning) bör kontrollera svarshuvudet
`X-OmniRoute-Cache-Latency`:

| Värde       | Betydelse                                                             |
| ----------- | --------------------------------------------------------------------- |
| `synthetic` | Svaret levererades från cachen; latensen är inte verklig uppströmstid |
| _(saknas)_  | Svar från ett verkligt uppströmsanrop                                 |

### Förbigång av cache per nyckel

API-nycklar kan välja bort läsningar från den semantiska cachen via `cacheDefaultMode`:

| Värde    | Beteende                                                    |
| -------- | ----------------------------------------------------------- |
| `legacy` | Normalt cachebeteende (standard)                            |
| `bypass` | Hoppa över cacheuppslagningen helt; anropa alltid uppströms |

Ange vid skapande av nyckel (`POST /api/keys`) eller uppdatering (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Förbigång per begäran

Alla begäranden kan kringgå cachen oavsett nyckelinställningar:

```
X-OmniRoute-No-Cache: true
```

För synkroniserade/importerade modeller accepterar `PUT /api/provider-models` `provider`,
`modelId` och `maxOutputTokenOverride`: ett positivt heltal ställer in det manuella taket för
utdatatoken, och `null` rensar det för att återställa standardvärdet.
`GET /api/provider-models?provider=<provider>` returnerar dessa värden i `modelOutputOverrides`,
inklusive modeller utan en rad för anpassad modell. Åsidosättandet använder körtidsegenskapen
`max_output_tokens` och överlever en omsynkronisering av modellen. Den OpenAI-kompatibla
leverantörssidan erbjuder samma kontroller för redigering/rensning och markerar modeller med
explicit visionstöd.

Anpassade Chat Completions-noder anpassar explicita avståenden från resonemang till
uppströmsbackenden. Ett lyckat anslutningstest väljer automatiskt kontroller för chattmallar
för varje exakt modell-ID vars `/models`-post visar ett känt `owned_by`-värde: `vllm`, `sglang`
eller `llamacpp`. Transparenta OpenAI-kompatibla wrappers kan bevara den ursprungliga
modellposten inuti ett nästlat `openai`-objekt; identifieringen följer upp till tre sådana
kuvert. Modeller med saknat, okänt eller motstridigt ägarskap behåller det vanliga
OpenAI-beteendet. Identifieringen återanvänder den befintliga katalogförfrågan, genererar inga
completion-token och ogiltigförklaras när anslutningens slutpunkt ändras.

För att låsa beteendet för en backend som inte exponerar dessa metadata, använd det befintliga
API:et för partiell leverantörsuppdatering:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Skicka den bodyn med `PUT /api/providers/<connection-id>`. På den anslutningen skickas en explicit
reasoning-effort på `none` som `chat_template_kwargs.thinking=false` och
`chat_template_kwargs.enable_thinking=false`. Explicita nativa mallvärden förblir auktoritativa
om inte en reasoning-regel på serversidan tvingar fram en effort. Inställningen gäller endast när en anpassad
OpenAI-kompatibel anslutning skickar en Chat Completions-body; Responses-förfrågningar och vanliga
providers behåller sin nativa förfrågningsform. Sätt `reasoningControl` till `openai` för att tvinga fram vanlig OpenAI-
`reasoning_effort`-vidarebefordran, eller utelämna det/sätt det till `null` för att använda automatisk detektering.

Klassificerarförfrågningar i Claude Code auto-läge ställer som standard in nativ thinking på inaktiverad
när de inte innehåller några explicita reasoning-kontroller. Detekteringen använder klassificerarens
systemmarkör i förfrågningar i Claude-format, inte modellnamn eller completion-gränser. Explicita
body-kontroller, stödda effort/thinking-headers, routing-regler och resolvad modell-effort behåller sin
befintliga prioritet. Båda klassificerarstadierna behåller sina prompts, completion-gränser, stoppsekvenser
och riktiga upstream-behörighetsbeslut; det andra stadiet kan fortfarande producera sin efterfrågade
synliga reasoning som vanlig text.

### Version och releasekanal

```bash
GET /api/system/version
```

Hanteringsroute som endast är åtkomlig via loopback (admin-autentisering). Returnerar den version som körs, den senast publicerade versionen och statusen för automatiska uppdateringar. `releaseChannel` och `channels` är additiva fält (rail 3.8.54); `channel` behåller sin betydelse — distributionsläget som dashboardens uppdaterare använder (`npm`, `source` eller `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-kanal för den byggnad som körs: `nightly` för versioner av typen `-nightly.*`,
  `next` för andra förhandsversioner (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` för en stabil version av en
  äldre major än `channels.latest`, annars `latest`. Samma regler som
  `scripts/release/dist-tag.mjs`, som väljer npm-dist-taggen vid publicering.
- `channels` — publicerad head för varje dist-tag, från `npm view omniroute dist-tags` (HTTP-fallback
  mot registret), cachad med samma TTL på 10 minuter som `latest`. `latest` finns alltid med
  (faller tillbaka på fältet `latest`, sedan `"unavailable"`); `next`, `nightly` och `lts` visas
  bara när den dist-taggen existerar. En begäran med `Cache-Control: no-cache` uppdaterar båda uppslagen.

Kanalmodellen (`latest` = v3 fram till 4.0 GA, `next` = rc, `nightly` = `develop`-byggen,
`lts` = v3-patchar efter 4.0 GA) beskrivs i `docs/ops/RELEASE_STRATEGY.md`.

## Tokengränser

**Tokenbudgetar** per API-nyckel (separata från den USD-baserade budgeten ovan). Tillämpas direkt i begäransflödet: när en nyckels användning i det aktuella fönstret når gränsen avvisas begäranden med `429 Too Many Requests`. Gränser kan avgränsas till en specifik `model`, en `provider` eller tillämpas `global`t för hela nyckeln. När flera gränser matchar en begäran gäller den mest restriktiva.

```bash
# Lista en nyckels tokengränser (inkluderar aktuell användning i fönstret)
GET /api/usage/token-limits?apiKeyId=key-123

# Skapa eller uppdatera en tokengräns
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Ta bort en tokengräns efter id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schemaanteckningar** (`setTokenLimitSchema`): `apiKeyId` och `scopeType` (`model` | `provider` | `global`) är obligatoriska. `scopeValue` är obligatoriskt om inte `scopeType` är `global` (t.ex. ett modell-id för omfattningen `model`, ett leverantörs-id för omfattningen `provider`). `tokenLimit` måste vara ett positivt heltal (konverteras från en sträng). Valfritt: `id` (utelämna för att skapa, ange för att uppdatera), `resetInterval` (`daily` | `weekly` | `monthly`, standardvärde `monthly`), `resetTime` (`HH:MM`), `enabled` (standardvärde `true`). `GET`-svar utökar varje gräns med `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` och `nextResetAt`. Detta är en endpoint av hanteringsklass (autentisering tillämpas centralt av authz-pipelinen).

## Bearbetning av begäranden

1. Klienten skickar en begäran till `/v1/*`
2. Route-hanteraren anropar `handleChat`, `handleEmbedding`, `handleAudioTranscription` eller `handleImageGeneration`
3. Modellen matchas (direkt leverantör/modell eller alias/kombination)
4. Autentiseringsuppgifter väljs från den lokala databasen med filtrering efter kontotillgänglighet
5. För chatt: `handleChatCore` kontrollerar semantisk cache/signaturcache och matchar kombinationens komprimeringsinställningar
6. Proaktiv komprimering körs före leverantörsöversättningen när den är aktiverad (`lite`, Caveman, RTK eller staplad)
7. Leverantörsexekveraren skickar begäran uppströms
8. Svaret översätts tillbaka till klientformatet (chatt) eller returneras i befintligt skick (inbäddningar/bilder/ljud)
9. Användning, komprimeringsanalys och begärandeloggar registreras
10. Reservlösning tillämpas vid fel enligt kombinationsreglerna

Fullständig arkitekturreferens: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Återhämtning (utökad)

OmniRoute exponerar tre oberoende mekanismer för tillfälliga fel; hanteringsendpointerna nedan låter operatörer läsa och åsidosätta dem:

| Omfattning               | Tillståndslagring                           | Läs                                       | Återställ / rensa                                 |
| ------------------------ | ------------------------------------------- | ----------------------------------------- | ------------------------------------------------- |
| Providerbrytare          | `domain_circuit_breakers` + i minnet        | `/api/monitoring/health`                  | `POST /api/resilience/reset`                      |
| Nedkylning av anslutning | `rateLimitedUntil` på provideranslutningar  | `/api/rate-limits`, `/api/providers/[id]` | (återaktiveras vid behov; rensa via provider-PUT) |
| Modellspärr              | Register över modelltillgänglighet i minnet | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`          |

`PATCH /api/resilience` accepterar åsidosättanden av providerbrytare under `providerBreaker.oauth` och `providerBreaker.apikey`. Varje profil stödjer `degradationThreshold`, `failureThreshold` och `resetTimeoutMs`; samma fält exponeras i Dashboard → Settings → Resilience.

```bash
# Rensa en enskild modellspärr
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Rensa alla spärrar
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Fullständig konceptuell referens och standardvärden för brytare: se [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" och [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Rate limit-kö och säkerhetsnät för automatisk aktivering

- **Skrivsökväg som stöds**: `POST /api/rate-limits` med body `{"connectionId": "<id>", "enabled": true|false}` är den hanteringsendpoint som stöds för att slå på/av rate limit-skydd för en anslutning. `PUT /api/providers/[id]` ändrar eller växlar avsiktligt inte `rateLimitProtection` (#11278).
- **Semantiken hos `enabled: false`**: Att sätta `enabled: false` tar bort explicit skydd för anslutningen, men exkluderar **inte** en aktiv API-nyckelanslutning från det globala säkerhetsnätet för automatisk aktivering (`autoEnableApiKeyProviders = true`). I `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) är `false` och `undefined` likvärdiga; aktiva API-nyckelanslutningar utan explicit skydd förblir skyddade under säkerhetsnätet för automatisk aktivering.
- **Global inaktivering**: För att köra API-nyckelanslutningar utan rate limit-köer, inaktivera säkerhetsnätet globalt via `RATE_LIMIT_AUTO_ENABLE=false` (miljövariabel) eller `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`).

## MCP-server

OmniRoute levereras med en inbäddad Model Context Protocol-server med 3 transporter (stdio, SSE, streamable-http) och verktyg med avgränsade behörigheter. Kontrollpanelens slutpunkter nedan läser status-/granskningsdata och fungerar som proxy för HTTP-transporterna.

| Metod | Sökväg | Beskrivning |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Hjärtslag, transport, onlinestatus, senaste anrop, vanligaste verktyg, lyckandefrekvens under 24 timmar |
| GET | `/api/mcp/tools` | Lista över MCP-verktyg med `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Öppna SSE-ström för SSE-transporten (returnerar `503` om MCP är inaktiverat eller transporten inte matchar) |
| POST | `/api/mcp/sse` | Skicka JSON-RPC-ram via SSE-transporten |
| GET | `/api/mcp/stream` | Öppna SSE-sidan av Streamable HTTP-transporten (serverinitierade meddelanden) |
| POST | `/api/mcp/stream` | Skicka JSON-RPC-ram via Streamable HTTP-transporten |
| DELETE | `/api/mcp/stream` | Avsluta en Streamable HTTP-session |
| GET | `/api/mcp/audit` | Fråga granskningsloggen — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Aggregerad granskningsstatistik (totalt antal, lyckandefrekvens, genomsnittlig varaktighet, vanligaste verktyg) |

**Autentisering:** transporterna `sse`/`stream` använder den MCP-specifika autentiseringsytan (Bearer-API-nyckel med omfånget `mcp`); vägarna `status`/`tools`/`audit*` kan läsas från kontrollpanelen (ingen ytterligare autentisering krävs utöver åtkomst till kontrollpanelens värd).

> Båda HTTP-transporterna styrs av `settings.mcpEnabled` och `settings.mcpTransport` — en transport som inte matchar returnerar `400`, medan ett inaktiverat MCP-tillstånd returnerar `503`.

## A2A-server

OmniRoute exponerar en A2A-slutpunkt (agent-till-agent) för JSON-RPC 2.0 samt ett REST-gränssnitt för inspektion och användning i kontrollpanelen.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # valfritt om inte OMNIROUTE_API_KEY har angetts
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Metoder som stöds (samtliga styrs av `settings.a2aEnabled`):

| Metod            | Beskrivning                                                               |
| ---------------- | ------------------------------------------------------------------------- |
| `message/send`   | Synkron körning av en färdighet; returnerar `{task, artifacts, metadata}` |
| `message/stream` | Strömmande SSE-körning av samma uppsättning färdigheter                   |
| `tasks/get`      | Hämtar en uppgift via `taskId`                                            |
| `tasks/cancel`   | Avbryter en uppgift via `taskId`                                          |

Inbyggda färdigheter: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agentkort

```bash
GET /.well-known/agent.json
```

Returnerar det offentliga A2A-agentkortet (namn, beskrivning, funktioner, färdighetskatalog och autentiseringsschema) — cachelagrat offentligt i 1 timme. Ingen autentisering krävs.

### REST-hjälpfunktioner

| Metod | Sökväg                       | Beskrivning                                                                                                           |
| ----- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A-status + uppgiftsstatistik + sammanfattning av det cachelagrade agentkortet                                       |
| GET   | `/api/a2a/tasks`             | Listar uppgifter — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Inte implementerat som en REST-hjälpfunktion — skapa via JSON-RPC `message/send`)                                    |
| GET   | `/api/a2a/tasks/[id]`        | Hämtar en uppgift                                                                                                     |
| POST  | `/api/a2a/tasks/[id]/cancel` | Avbryter en uppgift                                                                                                   |

**Autentisering:** REST-hjälpfunktionerna körs utan administrationsautentisering (läsbara från kontrollpanelen); JSON-RPC-rutten `/a2a` använder Bearer `OMNIROUTE_API_KEY` om den är konfigurerad.

## Autentisering

Se [Autentisering för administration](../guides/MANAGEMENT-AUTH.md) för de fyra
typerna av autentiseringsuppgifter (inloggningssession för kontrollpanelen, lokal CLI-token, `oma_live_…`-åtkomsttoken och API-nyckel med administrationsbehörighet) och hur de skiljer sig från inferensnycklar.

- Kontrollpanelsrutter (`/dashboard/*`) använder cookien `auth_token`
- Inloggning använder den sparade lösenordshashen, med `INITIAL_PASSWORD` som reserv
- `requireLogin` kan aktiveras eller inaktiveras via `/api/settings/require-login`
- `/v1/*`-rutter kan kräva en Bearer-API-nyckel när `REQUIRE_API_KEY=true`
- ”administrationstoken”/”API-nyckel med administrationsbehörighet” i denna referens avser en av typerna i den guiden – inte någon odefinierad ytterligare typ av hemlighet

> **Bakåtinkompatibel ändring (v3.8.0)** – `/api/v1/agents/tasks/*` och slutpunkterna för cooldown-administration kräver nu **administrationsautentisering** (kontrollpanelens `auth_token`-cookie eller en API-nyckel med administrationsbehörighet). Klienter som tidigare anropade dessa rutter utan autentisering får nu svaret `401 Unauthorized`. Se commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
