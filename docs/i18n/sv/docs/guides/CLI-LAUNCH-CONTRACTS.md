Det neutrala `config/cli-tools-manifest.json` kontraktet deklarerar kanoniskt IDs, alias, binära kandidater, inställningsrecept, modellargument och möjligheter. Den vanliga nodadaptern i `bin/cli/cli-manifest.mjs` och TypeScript adaptern i `src/shared/constants/cliIntegrationManifest.ts` läser samma fil. Körtid, katalog, konfigurering, slutförande, generatorer och backend-registrering kontrolleras tillsammans av `tests/unit/cli/cli-manifest-drift.test.ts`. Att vara katalogiserad betyder inte att ett verktyg kan startas eller konfigureras. I synnerhet förblir 5dive endast konfigurerad.

## Barnmiljö och livscykel

`omniroute run`, `omniroute launch` och `omniroute launch-codex` ärver en godkännandelista för OS/terminal kompatibilitet och injicerar det valda målets autentiseringsuppgifter. Orelaterade leverantörs- och databashemligheter ärvs inte som standard. `--inherit-env` återställer uttryckligen fullständigt arv från föräldermiljön; använd den endast när den valda tredjepartsprocessen ska ta emot dessa värden. Detta är miljöfiltrering, inte en OS sandlåda: processen körs fortfarande med anroparens filsystembehörigheter.

Avbrotts- och avslutningssignaler vidarebefordras till barnet. Startprogrammet väntar på barnets stängningshändelse innan den tillfälliga konfigurationen tas bort. `OMNIROUTE_CHILD_SIGNAL_TIMEOUT_MS` styr respitperioden före tvångsavslut (standard 5000 millisekunder).

## Gemini beständig inställning

```bash
omniroute setup-gemini --remote https://omni.example --model provider/model --yes
omniroute configure gemini --model provider/model --yes
omniroute run gemini --model provider/model --dry-run --json
```

De två första kommandona konfigurerar den här maskinen för den valda lokala eller fjärrservern. Installationen bevarar orelaterade JSON inställningar, väljer Gemini API-nyckelauth och skriver slutpunkten och autentiseringsuppgifterna till en privat `.gemini/.env` fil. Den vägrar ogiltig JSON snarare än att skriva över den. Endpoint URLs måste vara HTTP(S), utan inbäddade autentiseringsuppgifter, frågeparametrar eller fragment. Dry-run skriver ut sökvägar, inte referensvärden.

`GEMINI_CLI_HOME` eller `--gemini-home` väljer den beständiga hemroten. En verklig `run gemini` skapar och tar senare bort sitt eget tillfälliga hem. Inget av lägena kringgår Gemini:s kontroller av förtroende för arbetsytan.

## Codex profiler

`configure codex` skriver en privat `<name>.config.toml` med en modell och dess slutpunkt för OmniRoute leverantör. Referenser refereras till via `OMNIROUTE_API_KEY`, aldrig inbäddade. Startkommandot ställer in den valda modellen på `model` -tangenten på översta nivån, inte inuti `model_providers`.

Separata profilfiler är det aktuella dokumenterade Codex kontraktet; de överlagrar användarkonfigurationen när de väljs med `codex --profile <name>`. Se [den officiella profilreferensen](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) och [OmniRoute Codex guiden](./CODEX-CLI-CONFIGURATION.md).

## Hermetiskt kommandoutförande

Med en explicit `DATA_DIR` förhindrar inställningen av `OMNIROUTE_CLI_SKIP_DEFAULT_DATA_ENV=1` uppstart från att falla igenom till standardanvändardatakatalogens autentiseringsmiljö. Detta är användbart för isolerade tester. Det inaktiverar inte andra explicit valda miljöfiler.

## Arbetskatalog `.env`

CLI läser `.env` filer i denna ordning, och den första filen som ställer in en nyckel vinner: den explicita `DATA_DIR`, standarddatakatalogen, den aktuella arbetskatalogen, sedan paketkatalogen. Skalvariabler vinner alltid.

Arbetskatalogen kan tillhöra någon annan (ett klonat arkiv, ett uppackat arkiv), och `omniroute serve` skickar CLI miljön vidare till servern och till varje verktyg som servern kör. Så en `.env` där kan bara ställa in dessa nycklar, listade i `bin/cli/utils/untrustedCwdEnv.mjs`:

| Nyckel                          | Godkända värden                                                                  |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `REQUIRE_API_KEY`               | `true`, `1` eller `yes` i alla fall, de värden servern behandlar som på          |
| `LANG`, `LC_ALL`, `LC_MESSAGES` | upp till 64 bokstäver, siffror, `_`, `.`, `@` eller `-`                          |
| `LANGUAGE`                      | samma, plus `:`                                                                  |
| `TZ`                            | upp till 64 bokstäver, siffror, `_`, `+`, `-` eller `/`, som inte börjar med `/` |
| `NO_COLOR`, `FORCE_COLOR`       | upp till 16 bokstäver och siffror                                                |

Varje värde `REQUIRE_API_KEY` accepterar aktiverar kontrollen, så filen kan inte stänga av kontrollen själv. Det avgör dock inte resultatet: servern läser en `REQUIRE_API_KEY` -åsidosättning lagrad i databasen före miljön, medan startvarningen om att lyssna på alla gränssnitt utan en API nyckel endast läser miljön. Med en lagrad åsidosättning av `false` lämnar en arbetskatalog `REQUIRE_API_KEY=true` API öppen och döljer den varningen. `TZ` regeln är smalare än POSIX: den avvisar `.`, `:`, `,` och `<>`, så `:Area/City` formen och regler som `EST5EDT,M3.2.0,M11.1.0` måste ställas in i skalet eller i `<DATA_DIR>/.env`.

Namnen måste matcha exakt, med versaler. Alla andra rader, ett värde som inte klarar sin kontroll och ett namn som inte är vanliga ASCII bokstäver, siffror och `_` (till exempel en med en NUL byte eller en bokstav som liknar varandra) hoppas över. CLI skriver ut en varning som namnger nycklarna som den inte kan ställa in och en som namnger tillåtna nycklar som den ignoreras, var och en med vad som ska ändras (`TZ (expected a zone name such as Europe/Berlin)`, `lang (write the name as LANG)`). Ingen av dem skriver ut värdena. Filsökvägar i dessa meddelanden, och `.env` path `omniroute doctor` rapporterna, escapes när de innehåller kontroll- eller bidi-tecken. Begränsningen gäller inte när arbetskatalogen är datakatalogen eller paketkatalogen.

`PORT`, `API_PORT` och `DASHBOARD_PORT` finns inte på listan. Utan en bas URL från en källa med högre prioritet pratar CLI med `localhost:<PORT>`, och vad som än lyssnar där får CLIAPI nyckel, kontexttoken och CLI maskintoken (`x-omniroute-cli-token`, se [CLI_TOKEN.md](../security/CLI_TOKEN.md) ), som den lokala servern accepterar för hanteringsanrop från loopback. En port från arbetskatalogen skulle låta den filen välja lyssnaren, så ställ in portarna i skalet, i `<DATA_DIR>/.env` eller med `--port` alternativet för kommandon som har en (`serve`, `launch`, `run`).

Parsern har ingen `export` syntax. En rad som `export LD_PRELOAD=...` namnger en variabel `export LD_PRELOAD`; från arbetskatalogen hoppas den över, och i andra `.env` -filer ställer den in det bokstavliga namnet, som ingenting läser.

CLI parar en kontexts lagrade token (åtkomsttoken eller äldre API nyckel) endast med det sammanhangets eget ursprung: schema, värd och port, jämfört med `URL.origin`. Detta gäller för förfrågningar som görs via CLI:s HTTP klient (`--base-url`, `OMNIROUTE_BASE_URL`, `omniroute connect <new-url>`) och för `launch`, `launch codex`, `configure` och `setup-*` -kommandona som skriver en bas URL och knappar in i ett annat verktygs konfiguration. Pekade på en annan server med `--remote`, de använder en explicit `--api-key` eller `OMNIROUTE_API_KEY` om en är inställd, och ingen kontexttoken. Jämförelsen är exakt, så `localhost` och `127.0.0.1`, eller en värd med och utan en avslutande prick, räknas som olika servrar och får ingen kontexttoken. En URL med användarinformation, ett omvänt snedstreck eller blanksteg matchar aldrig, eftersom andra URL parsers (Pythons `urllib` och `httpx`, till exempel) kan läsa en annan värd från den. För förfrågningar som CLI skickar sig själv, täcker den kontrollen endast schemat och auktoriteten, så ett id med ett mellanslag i sökvägen eller frågan behåller token.
