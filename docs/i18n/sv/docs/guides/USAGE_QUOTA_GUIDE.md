> **Kort sagt**: OmniRoute spårar tokenanvändningen för varje begäran, beräknar kostnaden, tillämpar kvoter per API-nyckel och visar analysdata i kontrollpanelen. Den här guiden förklarar hur allt fungerar.

**Källor:**

- `open-sse/services/usage.ts` (~70KB) — huvudsaklig spårning av användning
- `src/lib/usageAnalytics.ts` (~10KB) — aggregering för kontrollpanelen
- `src/lib/db/quotaSnapshots.ts` — historiska kvotdata
- `src/lib/db/usage*.ts` — flera användningsrelaterade databasmoduler

---

## Översikt

Varje begäran som passerar genom OmniRoute genererar en **användningspost** som registrerar:

- **Identitet**: vilken API-nyckel, leverantör, modell och kombination
- **Token**: prompttoken, slutförandetoken, cachelagrade token och totalt antal
- **Kostnad**: belopp i USD (beräknat från prisdata)
- **Tidsinformation**: latens samt start- och sluttidsstämplar
- **Status**: lyckad, fel, hastighetsbegränsad osv.

Dessa poster aggregeras till **analysdata**, sparas som **kvotögonblicksbilder** och används för att tillämpa **budgetgränser per nyckel**.

```
Begäran ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                     analys    kvot   fakturering
                  (kontrollpanel) (tillämpning) (export)
```

## Vad som registreras

Tjänsten `usage.ts` registrerar en **användningshändelse** för varje begäran:

| Fält               | Typ     | Källa                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID som genereras vid registrering                        |
| `apiKeyId`         | string  | API-nyckeln som initierade begäran                         |
| `provider`         | string  | Leverantörs-ID (openai, anthropic osv.)                    |
| `model`            | string  | Modell-ID (gpt-5, claude-opus-4-6 osv.)                    |
| `comboId`          | string? | Kombinations-ID om begäran routas via en kombination       |
| `promptTokens`     | number  | Från uppströmsleverantörens svar                           |
| `completionTokens` | number  | Från uppströmsleverantörens svar                           |
| `cachedTokens`     | number  | Token vid cacheträff (Anthropics promptcachelagring osv.)  |
| `totalTokens`      | number  | prompt + komplettering                                     |
| `costUsd`          | number  | Beräknas utifrån prisdata                                  |
| `latencyMs`        | number  | Begärans totala varaktighet                                |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | Felklass om status != success                              |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | Anpassade data som infogas av insticksprogram              |

### Varifrån token kommer

Token extraheras från uppströmsleverantörens svar i **svarshanteraren**:

```ts
// Från open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

För leverantörer som inte returnerar användningsdata (vissa leverantörer som använder webbkakor) **uppskattar** OmniRoute antalet token med heuristiken `~4 chars per token` (se `open-sse/services/autoCombo/pipelineRouter.ts`).

### Cachelagrade token

OmniRoute spårar `cached_tokens` separat från `prompt_tokens` eftersom:

- Anthropics promptcachelagring debiteras till ett reducerat pris för cachelagrade token (10 % av det normala)
- Vissa leverantörer returnerar `cache_read_input_tokens` som ska prissättas annorlunda
- Analysen kan visa **cacheträffsfrekvensen** = `cached_tokens / prompt_tokens`

### Diagnostik för cacheskrivningsnivåer

Panelen för promptcachens hälsa på analysinstrumentpanelen skiljer mellan leverantörsrapporterade
cacheskrivningar med 5 minuters respektive 1 timmes giltighetstid. Anthropics
`usage.cache_creation.ephemeral_5m_input_tokens` och
`usage.cache_creation.ephemeral_1h_input_tokens` bevaras vid översättning av användningsdata för både strömmande och
icke-strömmande svar och lagras med sammanfattningar av anropsloggar. Den sammanlagda
cacheskrivningssumman läggs inte till i dessa kategorier en andra gång.

Anrop med enbart en sammanlagd skrivräknare, inklusive äldre poster, har en okänd
nivå. Vid en partiell uppdelning förblir den ofördelade återstoden okänd; ogiltiga eller
motstridiga räknare flaggas i stället för att tilldelas en TTL utan förvarning. TTL-markörer i
begäran är inte belägg för en debiterad nivå.

Panelens API-ekvivalenta kostnadsuppskattning för skrivningar omfattar endast rapporterade, prissatta nivåer, inte
hela begäran. Vid inbyggd modellprissättning för Claude/Anthropic används 1,25 gånger
indatapriset för skrivningar med 5 minuters giltighetstid och dubbla indatapriset för skrivningar med 1 timmes giltighetstid. Saknade
priser anges som otillgängliga, inte som noll. Priser registreras när varje nytt anrop loggas;
historiska poster prissätts inte på nytt. Prenumerationskonton kan därför ha en
API-ekvivalent uppskattning utan att det beloppet medför en faktisk utgift eller förbrukar
prenumerationskvoten. Befintliga beräkningar av kvoter, budgetar och leverantörsexakta kostnader är oförändrade.

Denna diagnostik använder den befintliga avgränsade sammanfattningen av cachehälsa och lagringstiden för
anropsloggar. Den ändrar inte standardvärden för begärans TTL, routning eller kontoval.
Registrering av klientbegärd TTL jämfört med effektiv utgående TTL vid överföringen
till leverantören har skjutits upp; den här panelen rapporterar nivåer enligt kvittot, inte effektiv utgående TTL.

Implementering: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` och `open-sse/utils/cacheWriteUsage.ts`.

## Kostnadsberäkning

Kostnader beräknas från **prisdata** som synkroniserats från LiteLLM (`src/lib/pricingSync.ts`):

| Modell            | Indata $/1M | Utdata $/1M | Cachad $/1M |
| ----------------- | ----------- | ----------- | ----------- |
| gpt-5             | $2.50       | $10.00      | —           |
| claude-opus-4-6   | $15.00      | $75.00      | $1.50       |
| claude-sonnet-4-5 | $3.00       | $15.00      | $0.30       |
| gemini-2.5-pro    | $1.25       | $10.00      | —           |

Kostnadsformeln (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Varför subtraheras cachade token från prompten?** Den cachade delen prissätts separat; om indatapriset tillämpades på hela prompten skulle kostnaden räknas för högt.

### Prissynkronisering

Prisdata synkroniseras automatiskt från LiteLLM via slutpunkten `/api/pricing/sync` (utlöses av den inbyggda cron-uppgiften, inte av en användartillgänglig miljövariabel):

```bash
# Manuell utlösning
curl -X POST http://localhost:20128/api/pricing/sync
```

För modeller utan prisdata använder OmniRoute i stället en **uppskattad kostnad** baserad på interna genomsnittspriser (hämtade från LiteLLM:s prisdata).

## Aggregering för datumintervall

Modulen `usageAnalytics.ts` beräknar widgetar för instrumentpanelen utifrån rådata om användning. Den stöder 7 tidsintervall:

| Intervall | Period                         | Användningsfall                           |
| --------- | ------------------------------ | ----------------------------------------- |
| `1d`      | Senaste 24 timmarna            | Identifiering av kostnadstoppar per timme |
| `7d`      | Senaste 7 dagarna              | Veckogenomgång                            |
| `30d`     | Senaste 30 dagarna             | Månadsfakturering                         |
| `90d`     | Senaste 90 dagarna             | Kvartalsanalys                            |
| `ytd`     | Sedan 1 januari innevarande år | Uppföljning av årsbudget                  |
| `all`     | Hela perioden                  | Statistik för hela perioden               |
| `custom`  | Användardefinierad start/slut  | Revisioner, ad hoc-frågor                 |

### Beräknade widgetar för instrumentpanelen

För varje datumintervall beräknar analyslagret:

| Widget                        | Beskrivning                                                                |
| ----------------------------- | -------------------------------------------------------------------------- |
| **Sammanfattningskort**       | Totalt antal anrop, total kostnad, totalt antal token, andel lyckade anrop |
| **Dagligt trenddiagram**      | Kostnad + token per dag, staplade per modell                               |
| **Värmekarta över aktivitet** | Rutnät med timme på dygnet × veckodag, färg = antal anrop                  |
| **Fördelning per modell**     | Cirkeldiagram över kostnad per modell                                      |
| **Fördelning per leverantör** | Stapeldiagram över anrop per leverantör                                    |
| **Främsta API-nycklar**       | Tabell över de 10 nycklarna med högst kostnad                              |
| **Felanalys**                 | Felfrekvens över tid, vanligaste felklasserna                              |

### Programmatisk åtkomst

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // poster i användningshistoriken
  "7d",                 // tidsintervall: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // mappning av leverantörsanslutningar (connectionId → kontonamn)
  {
    startDate: "2025-01-01",  // valfritt: för intervallet "custom"
    endDate: "2025-06-01",   // valfritt: för intervallet "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (cent)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Kvotkontroll

Kvoten per API-nyckel kontrolleras på två ställen:

1. **Mjuk gräns** (`quotaWarnAt`): varning i instrumentpanelen när användningen överskrider tröskelvärdet
2. **Hård gräns** (`quotaLimit`): anropet avvisas med HTTP 429 när gränsen överskrids

### Konfiguration

```ts
// Per API-nyckel
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — visa varning
  quotaLimit: 10_00,    // $10.00 — ovillkorligt stopp
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Kontrollflöde

```
Anrop ──▶ quotaCheck()
              │
              ├── Inom gränsen?  ──▶ tillåt
              │
              └── Över gränsen?  ──▶ 429 Too Many Requests
                                   med Retry-After-header
```

### Ögonblicksbilder av kvoter

Tabellen `quotaSnapshots` lagrar **historisk kvotstatus** för trendanalys:

| Fält | Beskrivning |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Nyckeln som följs upp |
| `window` | "day" | "week" | "month" |
| `used` | Förbrukad kostnad under denna period (cent) |
| `limit` | Gränsen (cent) |
| `resetAt` | När perioden återställs |
| `createdAt` | När ögonblicksbilden togs |

Ögonblicksbilder tas **vid varje anrop** som medför en kostnad > 0 och används för att:

- Visa kvotens förloppsindikator i instrumentpanelen
- Visa trenddiagram över kvoten för 30 dagar
- Utlösa aviseringar när användningen närmar sig gränsen

## Lagringstid och rensning

Användningsdata växer med ~1–10 KB per anrop. I stor skala kan detta bli betydande.

### Inställningar för lagringstid

Lagringstiden för användningshistorik konfigureras via databasinställningarna i användargränssnittet eller via `/api/settings/database`.

Som standard sparas användningshistoriken i **90 dagar**.

### Rensning

Gamla poster rensas av `src/lib/db/cleanup.ts`:

- Utlöses av cron-processen i bakgrunden
- Tar bort poster från `usage_history` som är äldre än den konfigurerade lagringstiden i inställningen `usageHistory`

### Uppskattning av lagringsutrymme

| Anropsfrekvens    | Lagring i 30 dagar | Lagring i 90 dagar |
| ----------------- | ------------------ | ------------------ |
| 100 anrop/dag     | ~3MB               | ~9MB               |
| 1 000 anrop/dag   | ~30MB              | ~90MB              |
| 10 000 anrop/dag  | ~300MB             | ~900MB             |
| 100 000 anrop/dag | ~3GB               | ~9GB               |

Vid mycket hög trafik kan du överväga att:

- Minska lagringstiden via databasinställningarna
- Använda `aggregated_metrics` i stället för råposter (endast för analys)

## Tips för kostnadsoptimering

### 1. Använd rätt modell

```bash
# Snabbt svar — använd billigt + snabbt
curl -d '{"model":"auto/fast","messages":[...]}'

# Komplex uppgift — använd kvalitet
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Aktivera cachning

Anthropics promptcachning sparar **90% på upprepad kontext**:

```ts
// Cachningen sker automatiskt — inkludera bara samma stora systemprompt
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Cachas automatiskt
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Använd komprimering

RTK + Caveman-komprimering sparar **15-95% i sessioner med omfattande verktygsanvändning**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Ange kvoter per nyckel

Ange alltid `quotaLimit` för att förhindra skenande kostnader:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Tak på 10 USD/månad
```

### 5. Granska de största förbrukarna

Använd kontrollpanelen eller **`/api/usage/analytics`** för att gruppera efter API-nyckel och sortera efter kostnad:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Felsökning

### "Kostnaden är högre än förväntat"

1. Kontrollera **`/api/usage/analytics?groupBy=model`** — hitta den dyra modellen
2. Kontrollera **`/api/usage/analytics?groupBy=apiKey`** — hitta storförbrukaren
3. Kontrollera att prisuppgifterna är aktuella: `POST /api/pricing/sync`

### "Poster saknas"

- Kontrollera databasens lagringsinställningar under Kontrollpanel → Databas → Rensning — gamla poster tas bort av den periodiska rensningsuppgiften (`src/lib/db/cleanup.ts`)
- Kontrollera om det finns fel i `src/lib/db/usage*.ts` — misslyckade databasskrivningar loggas men visas inte
- Kontrollera att begäran faktiskt nådde `chatCore` — kontrollera komboroutningen

### "Kvoten upprätthålls inte"

- Kontrollera nyckelns inställning för `quotaLimit`
- Kontrollera att `quotaWindow` är korrekt inställd
- Leta efter `quotaSnapshots`-poster — de ska skapas vid varje begäran
