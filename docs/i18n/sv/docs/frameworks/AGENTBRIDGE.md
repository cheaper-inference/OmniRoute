AgentBridge är OmniRoutes MITM-proxy (Man-in-the-Middle) som avlyssnar HTTPS-trafik från AI-agenter i IDE:er och omdirigerar den genom OmniRoutes enhetliga routningsmotor. Den stöder **10 IDE-agenter** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code och Trae (under utredning) — vilket gör OmniRoute till den MITM-proxy för AI-kodningsassistenter som har bredast täckning på marknaden.

**Plats i instrumentpanelen:** `/dashboard/tools/agent-bridge`
**Grupp i sidofältet:** Verktyg (efter Molnagenter)
**Se även:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — övervaka all avlyssnad trafik i realtid; `docs/security/MITM-TPROXY-DECRYPT.md` (git; kompileras inte till `/docs`) — Linux-baserat TPROXY-läge för transparent dekrypteringsinsamling som styrs via routen `/api/tools/agent-bridge/tproxy`.

## §1 Översikt

### Vad är AgentBridge?

När en IDE-agent (t.ex. GitHub Copilot, Cursor, Claude Code) gör ett API-anrop ansluter den direkt till AI-leverantören uppströms (OpenAI, Anthropic osv.). AgentBridge fångar upp anslutningen transparent på TLS-nivå — utan att någon ändring av agentens konfiguration krävs — och skriver om begäran via OmniRoute.

Det innebär att du kan:

- **Dirigera om valfri agent till valfri leverantör**: Pratar Copilot med OpenAI? Omdirigera den till Anthropic Claude, Gemini eller någon av OmniRoutes 375 leverantörer.
- **Tillämpa modellmappningar**: `gemini-3-flash` → `claude-sonnet-4.7` transparent på hanterarnivå.
- **Observera all agenttrafik**: varje uppfångad begäran publiceras till [Traffic Inspector](./TRAFFIC_INSPECTOR.md).
- **Utnyttja OmniRoutes motståndskraft**: komboroutning, circuit breakers, fallback-mekanismer och kostnadsspårning fungerar även för IDE-agenttrafik.

## §2 Arkitektur

### 2.1 Komponentöversikt

```
IDE-agent (VS Code / Cursor / osv.)
    │  HTTPS (port 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS-omdirigering
    │
    ▼
src/mitm/server.cjs  (port 443, CJS-underprocess)
    │  matchar målet utifrån SNI i Host-headern
    │  genererar TLS-certifikat per SNI, signerat av AgentBridge CA
    ├── Matchning i undantagslistan? → TCP-vidarekoppling (ingen dekryptering)
    ├── Målmatchning? → fetch → OmniRoute-router (port 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() på begärans body/headers
    │               ├── TrafficBuffer.push() — publicerar till Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── Ingen matchning? → TCP-vidarekoppling (ingen dekryptering)
```

### 2.2 MITM-server (`src/mitm/server.cjs`)

MITM-kärnservern körs som en Node.js CJS-underprocess (för att undvika att skriva om den befintliga CJS-kodbasen). Den:

- Lyssnar på port 443 (kräver behörighet eller `authbind`/`setcap`)
- Tar emot CONNECT-tunnlar från operativsystemet (via DNS-omdirigering i `/etc/hosts`)
- Genererar TLS-certifikat per SNI, signerade av AgentBridge CA (`DATA_DIR/mitm/ca.crt`)
- Matchar målagenten utifrån Host-headern via registret `targets/index.ts`
- Vidarebefordrar till TypeScript-hanterarlagret via HTTP till `http://127.0.0.1:20128`

`TARGET_HOSTS` läses in från `DATA_DIR/mitm/targets.json` (som skrivs av `targets/index.ts` vid start), vilket möjliggör dynamiska uppdateringar utan att CJS-servern behöver startas om.

> **Rot-CA-modell (#6684).** Beskrivningen ovan med certifikat per SNI, signerat av en CA,
> är den beständiga rot-CA-modell som lades till i #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, som återanvänder CA-/slutcertifikatskryptografin som redan
> verifierats för TPROXY i `src/mitm/tproxy/dynamicCert.ts`) — den ersätter det
> äldre, enskilda statiska självsignerade slutcertifikatet (`src/mitm/cert/generate.ts`, fortfarande
> begränsat till endast antigravity-värdarna) som indikeras av ett ensamt `server.crt`/`server.key`-par
> på disk. **Migreringsbeteende**: en ny installation (utan tidigare
> `server.crt`) får rot-CA-modellen automatiskt; en installation som redan
> litade på det gamla statiska slutcertifikatet fortsätter att använda det tills operatören anger
> `MITM_ROOT_CA_ENABLED=true` och startar om bryggan (`src/mitm/cert/migration.ts`
> är den rena beslutsfunktionen — en betrodd MITM-CA som kan signera ett slutcertifikat för
> **vilken** värd som helst är väsentligt kraftfullare än det gamla slutcertifikatet med fast SAN, så
> bytet sker aldrig i det tysta för en installation som redan är betrodd). CA-certifikatet installeras
> i samma `omniroute-mitm.crt`-plats i betroddhetsarkivet som det gamla slutcertifikatet använde
> (`cert/install.ts::installCaCert`) — ingen rensning av dubbla betrodda certifikat behövs.

### 2.3 Bashanterare (`src/mitm/handlers/base.ts`)

Alla agenthanterare utökar `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Skyddade hjälpmetoder: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Varje hanterare anropar `hookBufferStart()` före proxyförmedlingen och `hookBufferUpdate()` när den är klar. Dessa skickar `InterceptedRequest`-poster till `globalTrafficBuffer` (se [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Målregister (`src/mitm/targets/`)

Varje agent har en deklarativ målfil:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Registret (`targets/index.ts`) exporterar `ALL_TARGETS` och genererar `DATA_DIR/mitm/targets.json` vid start.

### 2.5 Vidarekoppling och undantagslista (`src/mitm/passthrough.ts`)

**Undantagslista** (kontrolleras först och har företräde framför målmatchning):

- Standardmönster: bankvärdar, `.gov.`, OAuth-/SSO-leverantörer (Okta, Auth0) osv.
- Användarmönster: lagras i databastabellen `agent_bridge_bypass`
- Undantagna värdar får en transparent TCP-tunnel — TLS dekrypteras **aldrig**

**Standardvidarekoppling** (ingen målmatchning och inte med i undantagslistan):

- Får också en TCP-tunnel — anslutningar bryts aldrig
- Förhindrar att AgentBridge stör allmän HTTPS-trafik i systemet

Prioritetsordning för routning:

```
undantagslista → målmatchning → vidarekoppling
```

### 2.6 Uppströms CA-certifikat (`src/mitm/upstreamTrust.ts`)

För företagsnätverksmiljöer med en anpassad CA:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

När den är angiven konfigureras `undici`:s globala dispatcher med det extra CA-certifikatet, vilket gör att AgentBridge kan nå uppströmsleverantörer genom företagsproxyservrar för TLS-terminering.

### 2.7 Maskering av hemligheter (`src/mitm/maskSecrets.ts`)

Den oberoende clean-room-skannern tillämpas på begärandekroppar och autentiseringsheaders
**innan** de hamnar i Traffic Inspectors buffert eller någon logg. Den utför en enda linjär genomgång:

- Token med prefixen `sk-` / `ak-` / `pk-` (OpenAI-/Anthropic-stil)
- RFC 6750-autentiseringsuppgifter av typen `Authorization: Bearer <token>`, där hela token har företräde
- Generiska, långa, ogenomskinliga token (≥40 tecken), inklusive punktseparerade och utfyllda former

`sanitizeHeaders()` konverterar bibehållna namn till gemener, sammanfogar arrayvärden deterministiskt, tar bort den
delade blockeringslistan för hopp-för-hopp-/ramindelningsheaders (inklusive proxyautentisering), maskerar `cookie` och
`set-cookie` fullständigt och delegerar autentiseringsvärden till skannern.

## §3 Konfiguration

### 3.1 Starta/stoppa MITM-servern

Använd AgentBridge-serverkortet på `/dashboard/tools/agent-bridge`:

| Åtgärd               | Beskrivning                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Starta servern       | Startar `src/mitm/server.cjs` på port 443. Med rot-CA-modellen skapas `ca.crt` vid första starten och det aktiva certifikatet betros när ett sudo-lösenord är tillgängligt                                                                                                                                                                                                                               |
| Stoppa servern       | Stänger ned den underordnade processen kontrollerat                                                                                                                                                                                                                                                                                                                                                      |
| Starta om servern    | Stoppar + startar (läser in måländringar och ett återskapat certifikat)                                                                                                                                                                                                                                                                                                                                  |
| Betro certifikat     | Installerar det aktiva certifikatet i operativsystemets betrodda certifikatarkiv: `DATA_DIR/mitm/ca.crt` med rot-CA-modellen, `DATA_DIR/mitm/server.crt` i en äldre installation med lövcertifikat                                                                                                                                                                                                       |
| Ladda ned certifikat | Laddar ned det aktiva certifikatet för manuell installation (`omniroute-mitm-ca.crt` = `ca.crt`, eller `omniroute-mitm.crt` = `server.crt` i en äldre installation med lövcertifikat)                                                                                                                                                                                                                    |
| Återskapa certifikat | Ändrar aldrig certifikatmodellen. Äldre installation med lövcertifikat: utfärdar nya `server.crt`/`server.key` (starta om servern för att använda dem). Rot-CA-modell: roterar `ca.crt`/`ca.key`, vilket nekas medan servern körs; en tidigare betrodd CA tas först bort från betrodda certifikat (kräver sudo-lösenordet), annars avbryts rotationen. Klienterna måste därefter betro den nya CA:n igen |

### 3.2 Betro certifikatet

AgentBridge-CA-certifikatet måste vara betrott av operativsystemet innan IDE:er accepterar MITM-anslutningen.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Nyckelring):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Du kan också använda knappen "Betro certifikat" på instrumentpanelen (den kör rätt kommando för ditt operativsystem och visar en sudo-prompt vid behov).

#### Electron-baserade IDE:er ignorerar operativsystemets betrodda certifikatarkiv (`NODE_EXTRA_CA_CERTS`)

Vissa IDE:er — särskilt **Antigravity IDE** och andra appar baserade på Electron/VS Code — levereras med
en egen Node.js-körmiljö som **inte använder operativsystemets betrodda certifikatarkiv** för utgående
`fetch`/HTTPS. Att betro CA:n på OS-/NSS-nivå räcker för IDE:ns inbyggda **bakände**
(t.ex. en Go-språkserver som använder operativsystemets CA-paket), men **Electron-gränssnittet**
kommer fortfarande att misslyckas med TLS — detta visar sig genom att appen är _utloggad_ eller visar ett
_"anslutningsfel"_, trots att MITM-loggen visar att bakändens bootstrap-anrop returnerar `200`. Två steg
krävs, och båda är viktiga:

1. Peka uttryckligen ut CA:n för körmiljön:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Starta IDE:n från det skalet.** Om den startas via skrivbordsikonen/Dock/Start-menyn
   ärvs **inte** skalets exporter, och `~/.config/environment.d/*.conf` börjar gälla först efter
   en ny grafisk inloggning. Avsluta först IDE:n helt — Electrons singleton-lås innebär att en andra
   start bara fokuserar den befintliga processen och att den nya miljön ignoreras.

Steget ovan för betrodd OS-CA + NSS är fortfarande nödvändigt (Chromiums nätverksstack, som används av vissa
autentiseringsflöden, läser användarens NSS-arkiv och har egna statiska pins för `*.googleapis.com` som en
lokalt betrodd CA åsidosätter). `NODE_EXTRA_CA_CERTS` täcker dessutom Nodes `fetch`-sökväg.

### 3.3 DNS-dirigering

För varje agent du vill avlyssna måste dess API-värd(ar) matchas mot `127.0.0.1`. AgentBridge hanterar poster i `/etc/hosts` automatiskt när du växlar DNS för en agent i konfigurationsguiden.

Exempel på poster i `/etc/hosts` för GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Modellmappning

Använd modellmappningstabellen på varje agentkort för att definiera mappningar från källa → mål:

| Källmodell (agentens ursprungliga) | Målmodell (OmniRoute) |
| ---------------------------------- | --------------------- |
| `gpt-4o`                           | `claude-sonnet-4.7`   |
| `*` (jokertecken)                  | `claude-haiku-4.7`    |

Jokertecknet `*` mappar alla okända modeller till det angivna målet. Sparas i tabellen `agent_bridge_mappings`.

> **Tips – ta reda på agentens verkliga modell-ID:n.** En IDE kan skicka modellnamn som skiljer sig från
> etiketterna i dess användargränssnitt och som ändras mellan större versioner. Exempelvis skickar **Antigravity 2**
> `gemini-3.1-pro-low`, `gemini-pro-agent` och `gemini-3.1-flash-lite` över anslutningen – inte
> `gemini-2.5-pro` som visas i äldre dokumentation. Skicka en chatt utan att ha någon matchande mappning på plats: MITM
> loggar det exakta inkommande `model:` och släpper igenom begäran. Mappa det bokstavliga värdet, så
> fångas nästa begäran upp och dirigeras till ditt mål.

### 3.5 Riskmeddelande

AgentBridge fångar upp autentiseringsuppgifter (OAuth-token, API-nycklar) som IDE:n använder för att autentisera sig hos uppströmsleverantörer. Dessa **maskeras före loggning** (se §2.7) men är synliga för OmniRoutes MITM-lager. Vid den första aktiveringen av varje agent visas en avfärdbar modal dialogruta med ett riskmeddelande.

### 3.6 Underhåll och diagnostik

Instrumentpanelen innehåller ett kort för **Underhåll och diagnostik** (`AgentBridgeMaintenanceCard`, i `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) som visar operativa MITM-rutter som tidigare saknade användargränssnitt. Dess underrubrik är: _"Självtesta infångningskedjan, återställ kvarlämnat systemtillstånd och flytta konfigurationen mellan datorer."_ Kortets klienthjälpfunktioner finns i `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Knapp                       | Rutt                                   | Vad den gör                                                                                                                                                                                                      |
| --------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Diagnostisera**           | `GET /api/tools/agent-bridge/diagnose` | Kör infångningskedjans självtest och visar en rapport för varje kontroll (✓/✗ + åtgärdsförslag).                                                                                                                 |
| **Reparera**                | `POST /api/tools/agent-bridge/repair`  | Återställer övergivet MITM-systemtillstånd (DNS-förfalskningsposter, rot-CA, systemproxy) som lämnats kvar efter en krasch eller SIGKILL. Idempotent – rapporterar "Inget att reparera" när tillståndet är rent. |
| **Ta bort CA**              | `DELETE /api/tools/agent-bridge/cert`  | Tar bort förtroendet för och raderar MITM-rot-CA:n från operativsystemets betrodda arkiv (explicit, idempotent). Visas endast när CA:n för närvarande är betrodd; kräver en infogad bekräftelse: "Ta bort CA?".  |
| **Exportera konfiguration** | `GET /api/tools/agent-bridge/config`   | Hämtar den portabla konfigurationen som JSON (se §3.7).                                                                                                                                                          |
| **Importera konfiguration** | `POST /api/tools/agent-bridge/config`  | Laddar upp en tidigare exporterad konfiguration i JSON-format (se §3.7).                                                                                                                                         |

Varje agentkort har också en egen knapp för **Återställ standardinställningar** (`POST
/api/tools/agent-bridge/agents/{id}/reset`) – en återställning per agent med ett enda klick som tar bort förfalskningen endast för den
agentens värdar, rensar dess sparade modellmappningar och återställer dess `dns_enabled`-/`setup_completed`-
tillstånd, så att IDE:n återigen kommunicerar med den verkliga uppströmsleverantören efter en fullständig omstart. Den påverkar **inte** den
delade MITM-servern eller rot-CA:n (andra agenter kan fortfarande vara beroende av dem) – dessa förblir åtkomliga
via serverkortet och åtgärden **Ta bort CA** ovan. I Windows kör den även
`ipconfig /flushdns` efter bästa förmåga, eftersom Windows DNS-klient cachelagrar poster i hosts-filen och annars inte tar bort en
nyligen borttagen förfalskning.

**Diagnostikkontroller** (`summarizeDiagnostics()` i `src/mitm/inspector/diagnostics.ts`). Rutten kör den sidoeffektskapande kontrollen för var och en och matar in de booleska värdena i den rena sammanfattningsfunktionen; ett enda `healthy`-utlåtande samt ett åtgärdsförslag för varje fel returneras:

| Kontrollnamn       | Vad den verifierar                                              | Förslag vid fel                                                                                                                                      |
| ------------------ | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM-serverprocessen är aktiv                                   | "MITM-servern körs inte. Starta den från fliken AgentBridge."                                                                                        |
| `server-reachable` | MITM-servern accepterar anslutningar på sin port (TCP-kontroll) | "MITM-servern accepterar inte anslutningar på sin port. Kontrollera att porten är ledig och att du har behörighet att binda den."                    |
| `cert-exists`      | MITM-certifikatet har genererats på disken                      | "Inget MITM-certifikat har genererats ännu. Generera ett från fliken AgentBridge."                                                                   |
| `cert-trusted`     | MITM-rot-CA:n finns i operativsystemets betrodda arkiv          | "MITM-rot-CA:n är inte betrodd av operativsystemets arkiv, så TLS-avlyssningen kommer att misslyckas. Lita på certifikatet från fliken AgentBridge." |
| `dns-configured`   | Målvärdnamnen är förfalskade i `/etc/hosts`                     | "Målvärdnamnen är inte förfalskade i /etc/hosts, så trafiken når aldrig proxyn. Aktivera DNS för den eller de agenter som du vill fånga in."         |

**Banderoll för övergivet tillstånd:** när sidan upptäcker tillstånd som lämnats kvar efter en krasch (DNS-förfalskning/CA/systemproxy) visar kortet en bärnstensfärgad banderoll – _"En tidigare session lämnade kvar systemtillstånd (DNS-förfalskning, CA eller systemproxy). Kör Reparera för att rensa det."_ – och framhäver knappen **Reparera**. `Repair` är motsvarigheten på programlagret till ProxyBridges flagga `--cleanup` (den delegerar till `repairMitm()` i `src/mitm/manager.ts`).

> MITM-rot-CA:t förblir installerat mellan stopp/start för att undvika upprepade sudo-
> frågor (samma beteende som mitmproxy/Charles), så borttagning sker via en uttrycklig
> **Ta bort CA**-åtgärd i stället för automatiskt vid stopp.

### 3.7 Portabel import/export av konfiguration

AgentBridge kan serialisera det **operatörsjusterbara** tillståndet till ett versionshanterat JSON-objekt så att en konfiguration kan replikeras mellan datorer. Serialiseraren är `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) och valideras av `AgentBridgeConfigSchema`.

Exporten innehåller exakt tre delar (inbyggda standardvärden exporteras avsiktligt **INTE**, så att import aldrig duplicerar dem eller skapar konflikter med dem):

| Fält             | Källa                                                           | Anmärkningar                                                          |
| ---------------- | --------------------------------------------------------------- | --------------------------------------------------------------------- |
| `bypassPatterns` | användardefinierade undantagsmönster (`agent_bridge_bypass`)    | standardmönster för banker/myndigheter/okta undantas                  |
| `customHosts`    | anpassade värdar i Traffic Inspector (`inspector_custom_hosts`) | var och en: `{ host, kind: "llm"\|"app"\|"custom", label? }`          |
| `agentMappings`  | modellsamband per agent (`agent_bridge_mappings`)               | `{ [agentId]: [{ source, target }] }` för varje agent som har samband |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Importbeteende** (`POST /api/tools/agent-bridge/config`): undantagsmönster och samband per agent **ersätts i sin helhet**; anpassade värdar läggs till **idempotent** (`INSERT OR IGNORE`). Svaret anger hur många av varje typ som tillämpades:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Vad som **INTE** ingår i konfigurationen: serverns körningstillstånd, certifikatsökvägar, DNS-tillstånd per agent, sökväg till uppströms CA och TPROXY-inställningar – dessa utgör värd-/körningstillstånd, inte portabla inställningar.

## §5 Säkerhet

### Tillämpade strikta regler

| Regel                             | Tillämpning                                                                                  |
| --------------------------------- | -------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Alla hanterarfel saneras före svar eller post i bufferten                                    |
| **#13** Överföring via skalmiljö  | Ändringar i `/etc/hosts` använder alternativet `env` — ingen stränginterpolering av sökvägar |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/agent-bridge/` är LOCAL_ONLY + SPAWN_CAPABLE — loopback krävs före autentisering |

### Förbikopplingslista för känsliga värdar

Förbikopplingslistan säkerställer att finansinstitut, OAuth-/SSO-leverantörer och andra känsliga värdar **aldrig dekrypteras**. Deras TLS-trafik passerar genom en transparent TCP-tunnel — OmniRoute ser aldrig klartexten.

Standardmönstren för förbikoppling omfattar:

- `*.bank.*`, `*.gov.*` (finans/myndigheter)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identitet)
- `*.apple.com`, `*.icloud.com` (Apples systemtjänster)

Förbikopplingsmönster som användaren lägger till lagras i tabellen `agent_bridge_bypass` och har företräde framför allt annat.

### Maskering av hemligheter

`maskSecrets()` från `src/mitm/maskSecrets.ts` tillämpas:

- På varje begärandetext före `TrafficBuffer.push()`
- På varje rubrik före loggning eller utsändning

Mönster: token med prefixet `sk-`/`ak-`/`pk-`, `Bearer`-token och generiska token med minst 40 tecken.

### Uppströms CA-certifikat

När `AGENTBRIDGE_UPSTREAM_CA_CERT` har angetts läses filen vid start. Om sökvägen finns men filen inte kan läsas loggar AgentBridge ett tydligt fel och vägrar att starta (förhindrar tysta TLS-fel i företagsmiljöer).

### Kända begränsningar

- **Port 443 kräver behörighet**: På Linux behöver AgentBridge `setcap 'cap_net_bind_service=+ep'` på Node-binärfilen eller köras via `authbind`. Installationsguiden visar operativsystemspecifika instruktioner.
- **IDE:n måste startas om**: Efter DNS-omdirigeringen måste IDE:n startas om för att den nya värdnamnsupplösningen ska börja gälla.
- **Hårdkodade OAuth-token**: Vissa agenter (Kiro, Antigravity) lagrar OAuth-uppdateringstoken lokalt. Dessa är transparenta för AgentBridge — den ser `Bearer`-token i varje begäran, som maskeras före loggning.
- **Electron-gränssnitt behöver `NODE_EXTRA_CA_CERTS`**: IDE:er vars gränssnitt körs i en medföljande Node-/Electron-körmiljö ignorerar operativsystemets/NSS betrodda certifikatarkiv och måste startas från ett skal där `NODE_EXTRA_CA_CERTS` har angetts (se §3.2). Symptom när detta saknas: IDE:ns serverdel autentiseras (MITM visar `200`-svar), men användargränssnittet förblir utloggat.
- **Flera installationer av samma IDE är oberoende**: en systeminstallation (t.ex. `/usr/share/antigravity/antigravity`) och en användarlokal Full-installation (t.ex. `~/AntigravityIDE_Full/antigravity-ide`) är separata processer med egna körmiljöer — var och en måste startas om med CA-certifikatet injicerat. Identifiera vilken som körs via dess binärsökväg före omstart.
- **Identiteten anges av agentens systemprompt, inte den dirigerade modellen**: när du mappar om en agents modell till en annan leverantör hävdar svaret fortfarande agentens ursprungliga identitet (t.ex. svarar Antigravity ”I am powered by Gemini”) eftersom IDE:n infogar detta i systemprompten. Bekräfta den verkliga serverdelen i `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), inte genom att fråga modellen vem den är.

## §6 Felsökning

### Konflikt på port 443

Om en annan process redan lyssnar på port 443 (webbserver, VPN osv.):

```bash
lsof -i :443          # hitta processen
sudo fuser -k 443/tcp  # tvångsavsluta (använd med försiktighet)
```

Alternativt kan du konfigurera en icke-privilegierad port i AgentBridge-inställningarna och skapa omdirigeringsregler med `iptables` / `pf`.

### Certifikatet är inte betrott

Om IDE:n visar TLS-fel efter att AgentBridge har startats:

1. Kontrollera att certifikatet installerades: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) eller `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Vissa appar använder ett eget betrott certifikatarkiv (Firefox, Chrome på Linux). Kör "Trust Cert" igen och kontrollera det NSS-/Firefox-specifika certifikatarkivet.
3. Starta om IDE:n efter att certifikatet har gjorts betrott — pågående TLS-sessioner använder den tidigare betrodda statusen.

### IDE:n är utloggad / visar "anslutningsfel" trots en betrodd CA

Symptom: efter att DNS har omdirigerats och CA:n gjorts betrodd öppnas en Electron-baserad IDE (t.ex. Antigravity)
**utloggad** eller visar ett autentiserings-/anslutningsfel, trots att MITM-loggen visar att
bootstrap-anropen (`loadCodeAssist`, `fetchAvailableModels`, …) returnerar `200`.

Orsak: IDE:ns **medföljande Node-/Electron-körmiljö ignorerar operativsystemets betrodda certifikatarkiv**. Den inbyggda
backend-komponenten (en Go-språkserver) litar på operativsystemets CA och autentiserar sig, men Electron-gränssnittet
gör det inte — därför tror användargränssnittet att det är offline.

Lösning (båda stegen): exportera `NODE_EXTRA_CA_CERTS=<ca.crt>` **och starta om IDE:n från samma
skal**, inte från skrivbordsikonen. Avsluta först IDE:n helt — Electrons singleton-lås innebär att
en andra start bara fokuserar den befintliga processen och att den nya miljön ignoreras. Se §3.2.
Detta motsvarar en öppen rapport uppströms där en fristående agent fungerar via en MITM, men IDE-
varianten misslyckas med samma konfiguration.

### DNS-ändringen har inte slagit igenom

Kontrollera att `/etc/hosts` har uppdaterats:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Töm DNS-cachen:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE:n identifieras inte

Automatisk identifiering använder vanliga installationssökvägar. Om identifieringen misslyckas trots att IDE:n är installerad:

- Kontrollera om IDE-binärfilen finns på en icke-standardiserad plats
- Installationsguiden fungerar ändå — misslyckad identifiering innebär bara att märket inte visar installationssökvägen

### Hanterarfel (hämtning uppströms misslyckas)

Om AgentBridge fångar upp förfrågningar men alla misslyckas:

1. Kontrollera att minst en leverantör är ansluten på `/dashboard/providers`
2. Kontrollera OmniRoute-serverloggarna: `APP_LOG_LEVEL=debug` i `.env`
3. Kontrollera att `OMNIROUTE_BASE_URL` pekar på rätt routerslutpunkt (standard: `http://127.0.0.1:20128`)

## §8 Färdplan

### Undersökning av Trae

Trae är en relativt ny AI-kodningsassistent. Innan en hanterare implementeras:

1. Identifiera binärfilen/tillägget på marknadsplatserna för VS Code/JetBrains eller som en fristående app
2. Samla in trafik med mitmproxy för att upptäcka API-värdar och slutpunkternas struktur
3. Fastställ autentiseringsmekanismen
4. Bedöm om arbetet ska fortsätta eller avbrytas baserat på användarvillkoren och API:ets upptäckbarhet

Tills undersökningen är slutförd visar Trae-kortet på instrumentpanelen märket "Undersöks" med länken "Rapportera genomförbarhet". Hanterarstubben i `src/mitm/handlers/trae.ts` genererar ett strukturerat `Ännu inte implementerat`-fel.

### Agenter i backloggen (MITM krävs — inget stöd för anpassad bas-URL)

Följande verktyg stöder inte anpassade bas-URL:er i sina nuvarande versioner, vilket gör MITM till den enda vägen för avlyssning. Bedömning av genomförbarheten återstår:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — separat från Kiro IDE)
- **Cowork** (Anthropics skrivbordsapp)

Obs! GitHub Copilot CLI ≥v1.0.19 stöder `COPILOT_PROVIDER_BASE_URL` — använd direkt konfiguration i stället för MITM för det verktyget.
