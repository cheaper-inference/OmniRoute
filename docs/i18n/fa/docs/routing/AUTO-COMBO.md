## مسیریابی خودکار بدون پیکربندی (پیشوند `auto/`)

> **جدید:** نیازی به ایجاد combo نیست. پیشوند `auto/` را مستقیماً در هر کلاینتی استفاده کنید.

### مثالهای سریع

| شناسه مدل      | گونه    | رفتار                                                           |
| -------------- | ------- | --------------------------------------------------------------- |
| `auto`         | پیشفرض  | همه ارائهدهندگان متصل، راهبرد LKGP، وزنهای متعادل               |
| `auto/coding`  | کدنویسی | وزنهای مبتنی بر اولویت کیفیت، مناسب برای تولید کد               |
| `auto/fast`    | سریع    | انتخاب وزندار با تأخیر کم                                       |
| `auto/cheap`   | ارزان   | مسیریابی بهینهشده از نظر هزینه (ابتدا کمترین هزینه)             |
| `auto/offline` | آفلاین  | ارائهدهندگانی با بیشترین سهمیه در دسترس را ترجیح میدهد          |
| `auto/smart`   | هوشمند  | اولویت کیفیت + نرخ کاوش بالاتر (10٪) برای کشف بهتر مدلها        |
| `auto/lkgp`    | lkgp    | LKGP صریح (همان `auto` پیشفرض)                                  |
| `auto/chaos`   | آشوب    | توزیع موازی درخواستها، یک مدل برای هر ارائهدهنده (نه تزریق خطا) |

### ترکیب دستهبندی × سطح (`auto/<category>:<tier>`)

پسوندهای سبک OpenRouter، **نوع مسیر** (دستهبندی) را از **نحوه بهینهسازی آن** (سطح) جدا میکنند تا بتوانید آزادانه آنها را ترکیب کنید (#4235 Phase B، `open-sse/services/autoCombo/suffixComposition.ts`):

- **دستهبندیها** (مجموعه نامزدها را بر اساس قابلیت فیلتر میکنند): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. گزینههای `vision`/`multimodal` مدلهای دارای قابلیت بینایی را نگه میدارند؛ `reasoning` مدلهای استدلال/تفکر را نگه میدارد.
- **سطوح** (وزنهای امتیازدهی / فیلتر مجموعه را انتخاب میکنند): `fast` (عرضه سریع) · `cheap` (نام مستعار `floor`، صرفهجویی در هزینه) · `reliable` (سلامت مدارشکن + پایداری تأخیر) · `free` / `pro` (فیلتر کردن مجموعه بر اساس سطح مدل از طریق `classifyTier` — سطح رایگان در برابر ممتاز).

| مثال                   | نتیجه                                                                  |
| ---------------------- | ---------------------------------------------------------------------- |
| `auto/coding:fast`     | مجموعه کدنویسی، وزنهای با تأخیر کم                                     |
| `auto/coding:cheap`    | مجموعه کدنویسی، بهینهشده از نظر هزینه (نام مستعار `auto/coding:floor`) |
| `auto/reasoning:pro`   | فقط مدلهای استدلال/تفکر، سطح ممتاز                                     |
| `auto/vision`          | مدلهای دارای قابلیت بینایی (بدون سطح ← وزنهای متعادل)                  |
| `auto/multimodal:free` | مدلهای دارای قابلیت چندوجهی، فقط سطح رایگان                            |

هر الگوی معتبر `auto/<category>[:<tier>]` در لحظه تفسیر میشود؛ یک زیرمجموعه منتخب در `/v1/models` و داشبورد اعلام میشود (`AUTO_SUFFIX_VARIANTS` در `open-sse/services/autoCombo/builtinCatalog.ts`). فیلتر کردن بهصورت **fail-open** است — اگر هیچ مدل متصلی با یک محدودیت مطابقت نداشته باشد، از کل مجموعه استفاده میشود تا مسیریابی هرگز مختل نشود. امتیازدهنده اصلی (`combo.ts`) بدون تغییر باقی میماند؛ فیلتر دستهبندی/سطح در `buildAutoCandidates` اعمال میشود.

> **هوشمندی زنده مدل:** تناسب مسیریابی خودکار، هنگامی که پرچم `ARENA_ELO_SYNC_ENABLED` روشن باشد، از رتبهبندیهای زنده **Arena ELO** و دادههای سطح **models.dev** استفاده میکند (در غیر این صورت به نگاشت ایستای تناسب بازمیگردد).

**نحوه استفاده:**

```bash
# هر ابزار IDE یا CLI که از قالب OpenAI پشتیبانی میکند
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# در کد/پیکربندی خود، مدل را به این صورت تنظیم کنید:
model: "auto"                 # حالت پیشفرض متعادل
model: "auto/coding"          # بهترین گزینه برای وظایف کدنویسی
model: "auto/fast"            # سریعترین گزینه موجود
model: "auto/cheap"           # ارزانترین گزینه بهازای هر توکن
```

**چه اتفاقی میافتد:**

1. OmniRoute پیشوند `auto/` را در `src/sse/handlers/chat.ts` تشخیص میدهد
2. همه **اتصالهای فعال ارائهدهندگان** را از پایگاه داده واکشی میکند
3. مواردی را نگه میدارد که اعتبارنامه معتبر دارند (کلید API یا توکن OAuth)
4. مدل هر اتصال را تعیین میکند (`connection.defaultModel` یا اولین مدل ارائهدهنده)
5. یک **combo مجازی** در حافظه میسازد (در DB ذخیره نمیشود)
6. با استفاده از پروفایل وزن گونه انتخابشده + راهبرد LKGP مسیریابی میکند

**ویژگیهای کلیدی:**

- ✅ **همیشه فعال:** بدون نیاز به کلید تغییر وضعیت، ایجاد combo یا پیکربندی
- ✅ **پویا:** ارائهدهندگان متصل فعلی را بهطور خودکار منعکس میکند
- ✅ **چسبندگی نشست:** LKGP تضمین میکند آخرین ارائهدهنده موفق در اولویت قرار گیرد
- ✅ **آگاه از چند حساب:** هر اتصال ارائهدهنده به یک نامزد جداگانه تبدیل میشود
- ✅ **بدون نوشتن در DB:** combo مجازی فقط برای همان درخواست وجود دارد و سربار ماندگاری آن صفر است

### کنترل نامزدها بهازای هر کلید (#7819، سطح 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = پسوند پس از `auto/`، یا
مقدار لفظی `auto` برای کانال پایه) یک نقطه پایانی **فقط خواندنی** است که مجموعه
نامزدهای فعلی یک کانال `auto/*` را همراه با دسترسپذیری زنده فهرست میکند و
خواندنهای موجود تابآوری را مجدداً بهکار میگیرد (و هرگز `state` خام مدارشکن را نمیخواند):

- مدارشکن ارائهدهنده — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- دوره انتظار اتصال — `rateLimitedUntil` / `testStatus` در ردیف تفسیرشده
  `provider_connections`
- قفل مدل — `isModelLocked(provider, connectionId, model)`

هر نامزد همچنین پرچم `excluded` مربوط به این کلید API را دربر دارد. استثناها
بهازای هر کلید API ذخیره میشوند (جدول `auto_candidate_overrides`، مهاجرت `128`) — OmniRoute
تکمستأجری است و جدول `users` ندارد، بنابراین `apiKeyId` نزدیکترین هویت واقعی
بهازای هر فراخواننده است — و در گلوگاه مجموعه نامزدها در
`open-sse/services/autoCombo/virtualFactory.ts` از طریق تابع خالص و آزمونشده با تست واحد
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`)
اعمال میشوند. این فیلتر بهصورت **fail-open** است: تنظیم نبودن apiKeyId/channel یا شکست
در جستوجوی DB، هر دو مجموعه را بدون فیلتر باقی میگذارند؛ بنابراین اپراتوری که هیچ
نادیدهگیریای برایش پیکربندی نشده باشد، مسیریابیای کاملاً یکسان در سطح بایت با پیش از
این قابلیت مشاهده میکند.

**به یک ایشوی پیگیری موکول شد:** وزندهی به هر کاندیدا + ترتیبدهی صریح (سطح 3
— به مسیرهای راهبرد وزندار/اولویتدار موجود وارد میشود) و پینکردن یک راهبرد مشخص
`combo.ts` برای هر کانال `auto/*` (سطح 4). برای پرسش باز دربارهٔ اینکه با توجه به
مدل تکمستأجری، بازنویسیها باید بهازای هر کلید API باقی بمانند یا سراسری شوند،
به برنامهٔ #7819 مراجعه کنید.

**پشت صحنه:**

```txt
درخواست: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts پیشوند را تشخیص میدهد
   ↓
createVirtualAutoCombo('coding') → candidatePool از اتصالهای فعال
   ↓
handleComboChat (همان موتور کمبوهای ذخیرهشده)
   ↓
امتیازدهی خودکار، بهترین ارائهدهنده/مدل را برای هر درخواست انتخاب میکند
```

**فایلهای پیادهسازی:**

| فایل                                                      | هدف                                          |
| --------------------------------------------------------- | -------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | تجزیهکنندهٔ پیشوند (`parseAutoPrefix`)       |
| `open-sse/services/autoCombo/virtualFactory.ts`           | اشیای مجازی `AutoComboConfig` را ایجاد میکند |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | هوک تست برای شبیهسازی رجیستری ارائهدهندگان   |
| `src/sse/handlers/chat.ts`                                | یکپارچهسازی: میانبُر پیشوند خودکار           |
| `src/shared/constants/providers.ts`                       | ورودی سیستمی `SYSTEM_PROVIDERS.auto`         |

## تنظیمات برگزیده حساب برای ترکیبهای خودکار ذخیرهشده

ویرایشگر خودکار هوشمند یک گزینه اختیاری ارائه می دهد** تنظیمات برگزیده حساب** بخش هر اتصال می تواند ترجیحی، عادی (پیش فرض)، رزرو یا حذف شود. چندین اتصال می توانند یک لایه را به اشتراک بگذارند. خودکار در اولین ردیف واجد شرایط انتخاب می کند و رفتار scoring/router خود را در آنجا حفظ می کند. تلاشهای ناموفق به حسابهای مشخص باقیمانده میرسند، که قبل از ذخیره، ترجیح داده میشوند. اتصالات استثنا شده هرگز توسط این ترکیب استفاده نمی شود.

تنظیم به صورت `config.accountPreferences` ذخیره می شود و با اتصال ID کلید می خورد:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

یک نقشه حذف شده یا خالی مسیریابی موجود را حفظ می کند. تنظیمات برگزیده اتصالات غیرفعال را فعال نمی کنند، دسترسی به کلید API را اعطا نمی کنند، نامزدهای مسدود شده در سهمیه را بازیابی نمی کنند، یا بررسی های بودجه را دور می زنند. هر تلاشی محدود به اتصال بتن آن است، بنابراین بازگرداندن حساب نمی تواند سطوح را پشت سر مسیریاب ترکیبی بپرد. وابستگی جلسه موجود ممکن است یک حساب واجد شرایط را حفظ کند. به استثنای حسابی که به یک نوبت بومی متصل است، به جای تغییر بیصدا حسابها، چرخش متوقف میشود.

تنظیمات برگزیده پیکربندی شده از مسیر خودکار مربوط به حساب کاربری استفاده میکنند: میانبرهای متن پنهان، خط لوله هوشمند، آشفتگی و سایهای ارسال نمیشوند. پوشش سوداگرانه برای این درخواستها غیرفعال است، بنابراین حسابهای ذخیره نمیتوانند با حسابهای ترجیحی رقابت کنند. سایر استراتژی های ترکیبی این تنظیم را تفسیر نمی کنند. تغییر یک ترکیب ترکیبی به دور از خودکار، تنظیمات برگزیده ذخیره شده را برای یک سوئیچ بعدی حفظ می کند.

## نامهای Combo که با شناسه یک مدل واقعی مطابقت دارند

یک combo که `name` آن با شناسه بدون پیشوند یک مدل یکسان است (برای مثال، comboای با نام
`gpt-5.5`)، یک **الگوی عمدی و پشتیبانیشده** است، نه یک باگ: این همان
سازوکار بازگشت به ارائهدهنده جایگزین برای هر شناسه مدل است که در
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) مستند شده است. از آنجا که
تفکیک combo پیش از تفکیک شناسه بدون پیشوند مدل بررسی میشود
(`getComboForModel()` در `src/sse/services/model.ts`)، درخواست برای شناسه بدون پیشوند
`gpt-5.5` بهجای اینکه مستقیماً به یک ارائهدهنده واحد هدایت شود، از طریق
مقصدهای combo (برای مثال،
`acme-responses/gpt-5.5` و `backup-responses/gpt-5.5`) مسیریابی میشود — این رفتار
از اولویت combo پیش از بازنویسی که برای
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) ساخته شده بود
دوباره استفاده میکند و در برابر رگرسیون توسط `tests/unit/responses-combo-resolution-3227.test.ts` و
`tests/unit/combo-name-codex-responses-rewrite.test.ts` آزمایش میشود.

ایجاد یا تغییر نام یک combo به نامی که شناسه یک مدل واقعی را تحتالشعاع قرار میدهد
**هرگز رد نمیشود** — انجام این کار گردشکار مستندشده را مختل میکند. در عوض
(#8530)، `POST /api/combos` و `PUT /api/combos/[id]` هنگامی که نام (جدید) با شناسه
یک مدل واقعی تداخل داشته باشد، یک فیلد غیرمسدودکننده `warning` به پاسخ اضافه
میکنند:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

هنگام راهاندازی، `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) همچنین یک هشدار تکخطی `[STARTUP]` ثبت میکند که
تمام comboهای موجودی را که یک شناسه مدل را تحتالشعاع قرار میدهند فهرست میکند؛
در نتیجه، اپراتورهایی که بهطور تصادفی با این وضعیت روبهرو شدهاند (و نه بهصورت
عمدی، مطابق #6940)، نشانهای برای تشخیص آن خواهند داشت.
تابع کمکی تشخیص در `src/lib/combos/modelNameCollision.ts` قرار دارد.

## فراخوانی یک Combo سفارشی از یک کلاینت

comboهای ذخیرهشده (Settings → Combos) فقط زمانی استفاده میشوند که کلاینت **نام دقیق** combo را در فیلد `model` ارسال کند — هیچ تطبیق مبهم یا جزئی برای نام combo انجام نمیشود و پیشوند `auto/` نیز در کار نیست. ترتیب تفکیک (`getComboForModel()` در `src/sse/services/model.ts`):

1. تطبیق دقیق نام combo (`model: "my-combo"`)،
2. پیشوند `combo/<name>` (`model: "combo/my-combo"`)،
3. نگاشتهای glob از مدل به combo (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

دو اشتباه رایج:

- **`auto` از comboهای شما استفاده نمیکند.** `auto`/`auto/*` مجموعه کاندیداهای بدون نیاز به پیکربندی خودش را ایجاد میکند و تنها در صورتی comboهای ذخیرهشده را بررسی میکند که یک combo دقیقاً `auto` نام داشته باشد (توصیه نمیشود). برای مسیریابی از طریق یک combo، نام دقیق آن را ارسال کنید — نه `auto`.
- **`openrouter/auto` یک محصول واقعی و پولی OpenRouter است** ("Auto Best Available")، نه یک نام مستعار OmniRoute. این مورد، تنها ورودی مدل ایستای رجیستری OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) است و هزینه آن جداگانه محاسبه میشود. برای حذف آن از مجموعههای `auto`، از Settings → Routing → Hide paid models استفاده کنید.

برای سردرگمی اولیهای که این بخش مستند میکند، به [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) و [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) مراجعه کنید.

## چگونه کار می کند (ترکیب خودکار مداوم)

Auto-Combo Engine به صورت پویا بهترین provider/model برای هر درخواست با استفاده از a انتخاب می کند** تابع امتیاز دهی 16 عاملی** (در `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` تعریف شده است). مجموع وزن های پیش فرض به `1.0`; وزن های سفارشی توسط `normalizeScoringWeights()` دوباره عادی می شوند. دو تا از 16 — `cacheAffinity` و `resetWindowAffinity` — دارای وزن پیش فرض `0` هستند. `reliability` `0` در `DEFAULT_WEIGHTS` اما `0.03` در بستههای عمومی و `0.04` در `reliability-first` حمل میکند و `quality` `0.02` در بستهها حمل میکند (`0.03` در `quality-first`): آنها همچنان برای هر نامزد محاسبه میشوند، و `cacheAffinity` دروازههای خارج از امتیاز را از حافظه پنهان خارج میکند، بنابراین فاکتورهای پیشفرض صفر در حالی که بستهها بهطور پیشفرض رای نمیدهند.

> **سهمیه ناخوانا (#15347).** وقتی ارائهدهنده سهمیه واکشی دارد اما چیزی قابل خواندن بر نمیگرداند (واکشی ناموفق، اعتبارنامههای از دست رفته، استفاده فقط از پیام، یا یک عکس فوری ناقص بدون `windows` قابل تجزیه و بدون `percentUsed` محدود، از جمله `percentUsed: null`)، کاندید `0` را در محور `quota` میگیرد و امتیاز نهایی آن `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR`, `autoStrategy.ts` برابر میشود. الگوی پنالتی نرم به عنوان جریمه وضعیت اتصال. خواندن ناموفق استفاده شواهدی در مورد تله متری است، نه ارائه دهنده، بنابراین به شدت پایین تر از هر قرائت واقعی، از جمله 100%-used تایید شده، قرار می گیرد، اما هرگز به سختی مسدود یا خارج نمی شود. ارائه دهنده بدون سقف `unlimited: true` گزارش می کند و به عنوان سهمیه کامل امتیاز می گیرد. ارائهدهندهای که واکشی سهمیه ثبتشده ندارد، اصلاً منبع تلهمتری ندارد و پیشفرض `100` را حفظ میکند.

**جمع:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` همانطور که در `DEFAULT_WEIGHTS` اعلام شده است; وزنهای پیکربندی شده توسط کاربر قبل از امتیازدهی مجدداً به یک توزیع توسط `normalizeScoringWeights()` تبدیل میشوند.

### کنترلهای هر درخواست (هدر) — #6023 / #6024 / #6025 / #3470

یک کمبو `auto` را می توان هدایت کرد** در هر درخواست** از طریق سه هدر، بدون تغییر در پیکربندی ذخیره شده ترکیبی. اینها فقط برای استراتژی `auto` و فقط برای درخواستی که آنها را حمل می کند اعمال می شود. `modePack`/`budgetCap`/`budgetFallback` ذخیره شده ترکیبی زمانی استفاده می شود که هدر وجود نداشته باشد.

```bash
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

وضوح یک تابع خالص (`open-sse/services/autoCombo/requestControls.ts`) است. مقادیر حل شده ورودی های `config.modePack` / `config.budgetCap` / `config.budgetFallback` موجود موتور را تغذیه می کند. `config.budgetFallback` ذخیره شده یک ترکیب ("سخت" | "ارزانترین") خط مشی پایدار را تعیین می کند. هدر آن را برای یک درخواست لغو می کند.

### معناشناسی `weighted`

`weighted` یک است** قرعه کشی تصادفی متناسب در هر درخواست** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)، نه یک اکولایزر:

- هر درخواست قرعه کشی می کند** یکی** گام با احتمال `weight / totalWeight`; مراحل باقی مانده با وزن نزولی به عنوان زنجیره بازگشتی برای آن درخواست مرتب می شوند.
- گامی که وزن آن `0` (یا مفقود) است** هرگز ترسیم نشده است** در حالی که هر پله دیگری دارای وزن > 0 — است، تنها پس از شکست مرحله ترسیم شده می تواند به عنوان یک بازگشتی عمل کند. فقط وقتی** همه** وزن ها 0 هستند آیا انتخاب یکنواخت می شود.
- مراحلی که هدفهای آنها همگی در دسترس نیستند، قطعکننده مدار — ارائهدهنده `OPEN`، خنکسازی اتصال، قفل مدل — قبل از انجام قرعهکشی حذف میشوند (`open-sse/services/combo/targetResolution.ts`)، بنابراین یک مرحله سالم میتواند موقتاً هر درخواستی را برنده شود.
- `stickyWeightedLimit` (پیکربندی ترکیبی، `1` پیشفرض = خاموش) مرحله ترسیم شده را برای موفقیتهای متوالی زیادی قبل از ترسیم مجدد پین میکند.

برای چرخش دقیق `round-robin` استفاده کنید. وزنهای مساوی روی `weighted` — آماری را نشان میدهد نه تعادل — دقیق.

### حالت خط لوله عاملی

یک ترکیب `pipeline` با حداقل دو مدل میتواند مسیریابی planner/executor را با `config.agenticOrchestration.enabled` انتخاب کند. اولین هدف صاحب برنامه ریزی و پاسخ های نهایی است. هدف دوم فراخوانی های ابزار بومی کلاینت را منتشر می کند. OmniRoute ادامه نتایج ابزار را از پروتکل درخواست تشخیص میدهد، از برنامهریز میپرسد که آیا به دور ابزار دیگری نیاز است یا خیر، و به صورت پویا یا مجری یا برنامهریز را به مرحله نهایی مشتری تبدیل میکند.

`config.agenticOrchestration.contextCompaction` اختیاری قبل از ارسال هر برنامهریز یا مجری بودجه جداگانهای را اعمال میکند. آن را به صراحت فعال کنید:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

اینها بودجههای کاراکتر JSON سریالی هستند که توسط اپراتور انتخاب شدهاند، نه پنجرههای زمینه رمزی یا محدودیتهای بالادستی تضمینشده. مدل دقیق IDs پیش فرض را نادیده می گیرد. بالاتر از آستانه، فشرده سازی تعاریف ابزار یکسان را حذف می کند، شواهد ابزار بزرگ را با یک خلاصه حذف می کند، و گروه های سابقه کامل قدیمی را به نسبت هدف حذف می کند. دستورالعملهای system/developer ، آخرین درخواست کاربر، آخرین دور ابزار شامل calls/results موازی، و دستورالعمل مسیریابی پیشرو Gemini را حفظ میکند. دستورالعمل های سطح بالا و تنظیمات ابزار حفظ می شوند. یک نشانگر حذف سابقه حذف شده را ثبت می کند. این یک پیرایش قطعی است، نه یک خلاصه معنایی. اگر زمینه پین شده همچنان از بودجه بیشتر باشد، درخواست قبل از تماس با مدل، 413 را برمی گرداند. با فشرده سازی غیرفعال یا زیر آستانه، درخواست بدون تغییر عبور می کند.

در ادامه نتیجه ابزار، زمانی که دو دور تکمیل شده متوالی، همان فراخوانی ابزار را با نتایج بدون تغییر تکرار میکنند، یا زمانی که هر نتیجه مشخصاً علامتگذاری شده در دو دور متوالی با شکست مواجه میشود، OmniRoute اجرا را متوقف میکند. نتایج تغییر یافته اجازه تماس های مکرر را می دهد (به عنوان مثال، نظرسنجی). گارد بر اساس درخواست کاربر جدید بازنشانی میشود، تماسهای موازی را در یک دور گروهبندی میکند و از Anthropic، تکمیلهای چت، پاسخها و تاریخچههای Gemini پشتیبانی میکند. برنامه ریز دلیل را دریافت می کند و صاحب پاسخ نهایی می شود حتی اگر دور ابزار دیگری را درخواست کند.

مدلهای اضافی پس از هدف دوم، نسخههای پشتیبان مجری سفارش داده میشوند. پاسخ ناموفق HTTP یا استثنای حمل و نقل به مجری بعدی میرود، که همان تصمیم برنامهریز و ابزارهای اصلی را دارد، اما اتصال سریع و حلشده خود اجراکننده. اولین پاسخ موفق بدون تغییر بازگردانده می شود، از جمله جریان SSE. شکستهای پس از شروع یک جریان موفقیتآمیز را نمیتوان در اینجا دوباره امتحان کرد. اگر همه مجری ها از کار بیفتند، آخرین شکست برگردانده می شود. مشتری ارسال توقف را متوقف می کند.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

مجری ممکن است چندین تماس مستقل را در یک پاسخ ارسال کند. تماسهای وابسته در نوبتهای بعدی نتیجه ابزار مشتری، با برنامهریزی که هر نتیجه را بررسی میکند، انجام میشود. `maxToolRounds` پیش فرض `8` است و `1`–`32` را می پذیرد. پس از رسیدن، برنامه ریز باید بهترین پاسخ نهایی موجود را ارائه دهد. تصمیمهای برنامهریز داخلی بافر میشوند، در حالی که پاسخ انتخابی رو به مشتری، اولویت اصلی جریان را حفظ میکند.

### `round-robin` چسبنده دسته و گسترش حساب

دوره گرد به صورت دسته ای است، نه یک درخواست در هر مرحله:

- `stickyRoundRobinLimit` (پیکربندی ترکیبی، سپس `comboStickyRoundRobinLimit`، سپس `settings.stickyRoundRobinLimit`، پیشفرض** 3** ) قبل از چرخش، همان هدف را برای آن تعداد از موفقیت های متوالی حفظ می کند. برای چرخش یک درخواست، override ترکیبی را روی `1` تنظیم کنید. ویرایشگر ترکیبی مقدار موثر و اینکه از کدام لایه آمده را نشان می دهد.
- `connectionAwareExpansion` (پیکربندی ترکیبی، سپس تنظیمات، پیشفرض** نادرست** ) هر مرحله در سطح ارائه دهنده را قبل از چرخش به اهداف هر حساب گسترش می دهد. استراتژیهای گروه B (اولویت، وزن، گرد، تصادفی، p2c، کم استفاده، بهینهسازی هزینه، lkgp، پر کردن اول، تصادفی دقیق، بهینهسازی زمینه، بهینهسازی حافظه پنهان، رله زمینه، تلفیقی، خط لوله، jev) یک نمای سطح ارائهدهنده را تا زمانی که روشن شود حفظ میکنند. ویرایشگر ترکیبی وراثت / روشن / خاموش را در معرض نمایش قرار می دهد. inherit از پیش فرض جهانی (خاموش) استفاده می کند.
- مسیریابی محل اعلان حافظه پنهان (`promptCacheAffinityEnabled`، پیشفرض** درست است** ) اتصالات پین شده را دوباره ترتیب می دهد تا کلیدهای حافظه پنهان مطابق با یک حساب باقی بمانند. این روش بر چرخش چرخشی و وزنی در سراسر مراحل پین شده در هر حساب ارجحیت دارد. اگر به چرخش دقیق نیاز دارید، آن را در زیر تنظیمات پیشفرض → Combo خاموش کنید. هیچ تغییری در هر ترکیب وجود ندارد.

برای چرخش چند حساب در یک مدل، ترجیح دهید** یک مرحله حساب پویا** ( `connectionId` خالی، کل استخر) با حد چسبنده `1`، نه سه `connectionId` پین شده. حتی زمانی که شمارنده RR پیشرفت میکند، مراحل پینشده بهعلاوه قرابت بر روی یک حساب جمع میشوند.

## راهبرد Fusion

`fusion` تنها راهبردی است که یک مقصد واحد را انتخاب **نمیکند**. این راهبرد پرامپت را بهصورت
موازی به **تمام مدلهای پنل** ارسال میکند و سپس یک **مدل داور** قابلپیکربندی، از همه پاسخهای
پنل یک پاسخ نهایی واحد میسازد. این قابلیت از `decolua/9router` بالادستی
(طراحی Fusion متعلق به OpenRouter) منتقل شده است؛ پیادهسازی آن در `open-sse/services/fusion.ts` قرار دارد.

نحوه کار:

0. **عبور مستقیم درخواستهای دارای ابزار** — درخواستی که یک آرایه غیرخالی `tools` داشته باشد و
   مقدار `tool_choice` آن صراحتاً `"none"` نباشد، پنل را کاملاً کنار میگذارد: درخواست مستقیماً به
   یک مدل واحد (داور پیکربندیشده یا `panel[0]`) هدایت میشود و `tools`/`tool_choice`
   بدون تغییر عبور داده میشوند. اعضای پنل به ابزارها دسترسی ندارند و دستورالعمل
   ترکیب پاسخِ داور، تولید فراخوانی ابزار را منع میکند؛ بنابراین کلاینتهای عاملی/فراخواننده ابزار
   بهجای متن ترکیبشده، یک تصمیم واقعی برای فراخوانی ابزار دریافت میکنند (#6771).
1. **ارسال همزمان** (فقط برای درخواستهای بدون ابزار) — پرامپت بهطور همزمان به همه مدلهای
   پنل ارسال میشود؛ حالت غیرجریانی بهاجبار فعال و ابزارها حذف میشوند (داور برای ترکیب پاسخ
   به متن کامل نیاز دارد).
2. **گردآوری با حد نصاب و مهلت** — بهمحض رسیدن `minPanel` پاسخ، یک زمانسنج کوتاه برای
   مدلهای عقبمانده آغاز میشود؛ سپس Fusion با هر تعداد پاسخی که گردآوری شده است ادامه میدهد.
   این کار تأثیر کندترین مدل بر زمان سپریشده را محدود میکند و یک مهلت نهایی سخت نیز آن را
   کراندار نگه میدارد.
3. **ترکیب توسط داور** — پاسخهای پنل ناشناسسازی میشوند (`Source 1`، `Source 2`، … — تا
   داور محتوا را بسنجد، نه برند مدل) و در اختیار داور قرار میگیرند. داور توافقها /
   تناقضها / پوشش ناقص / بینشهای منحصربهفرد / نقاط کور را تحلیل میکند و سپس
   **یک** پاسخ معتبر مینویسد. فراخوانی داور، پرچم اصلی `stream` کلاینت و ابزارها را
   حفظ میکند؛ بنابراین پخش جریانی و استفاده پاییندستی از ابزارها همچنان کار میکنند.
4. **افت تدریجی و کنترلشده** — ۰ پاسخ پنل ← `503`؛ دقیقاً ۱ پاسخ باقیمانده ← همان پاسخ
   مستقیماً برگردانده میشود (چیزی برای ترکیب وجود ندارد)؛ پنلی با یک مدل نیز مستقیماً پاسخ میدهد.

یکی از اعضای پنل میتواند یک مرحله `combo-ref` نیز باشد (`{kind: "combo-ref", comboName: "..."}`) که
به ترکیب دیگری ارجاع میدهد — این مرحله بهعنوان **یک صدای مستقل و جعبهسیاه در پنل** حل میشود
(یک ارسال بازگشتی کامل به ترکیب مورد ارجاع، نه ارسال همزمان به مقصدهای خود آن ترکیب)، با همان
محافظت در برابر عمق/چرخه که همه راهبردهای دیگرِ مصرفکننده combo-ref از آن استفاده میکنند (#6764).

### پیکربندی

پیکربندی در داده `config` ترکیب انجام میشود (بدون مهاجرت طرحواره — از جدول موجود
`combos` دوباره استفاده میکند):

| فیلد                                     | نوع      | پیشفرض        | هدف                                                                             |
| :--------------------------------------- | :------- | :------------ | :------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | اولین مدل پنل | مدلی که پاسخ نهایی را ترکیب میکند                                               |
| `config.fusionTuning.minPanel`           | `number` | `2`           | تعداد پاسخهای موفق لازم پیش از شروع زمانسنج مهلت (محدودشده به `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`        | مدت انتظار برای مدلهای عقبمانده پس از رسیدن به حد نصاب                          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`       | سقف مطلق برای جلوگیری از اینکه یک مدل متوقفشده، درخواست را معطل کند             |

مقادیر پیشفرض در `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) قرار دارند.

### مثال

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

سپس آن را مانند هر ترکیب دیگری فراخوانی کنید: `{"model":"fusion-panel","messages":[...]}`.

## کارخانهٔ مجازی Auto-Combo

موتور Auto Combo به کمبوهای ازپیشتعریفشده نیازی ندارد. در عوض، `open-sse/services/autoCombo/virtualFactory.ts` کاندیداها را بهصورت پویا میسازد:

1. `getProviderConnections({ isActive: true })` را دریافت میکند (همهٔ اتصالهای فعال)
2. مواردی را که اعتبارنامهٔ معتبر دارند فیلتر میکند (کلید API یا توکن OAuth منقضینشده از طریق `hasUsableOAuthToken()`)
3. برای بررسی دسترسپذیری مدل و قیمتگذاری، آنها را با `getProviderRegistry()` تطبیق میدهد
4. برای هر سهتایی `(provider, model, connection)`، یک `VirtualAutoComboCandidate` میسازد
5. `connection.defaultModel` (یا اولین مدل رجیستری) را بهعنوان مقصد ارسال انتخاب میکند
6. هر کاندیدا را با استفاده از `scorePool()` شانزدهعاملی و بستهٔ وزن آن واریانت امتیازدهی میکند
7. `AutoComboConfig` حاصل را که در حافظه قرار دارد، برای `handleComboChat()` برمیگرداند — و هرگز آن را در DB ذخیره نمیکند

این یعنی **افزودن یک ارائهدهندهٔ جدید که `auto/*` برای آن فعال است، بهطور خودکار مجموعهٔ کاندیداها را گسترش میدهد** — و نیازی به ویرایش دستی کمبو نیست. کمبوی مجازی برای هر درخواست از نو ساخته میشود، بنابراین اتصالهایی که بهتازگی اضافه شدهاند یا دوباره سالم شدهاند، بلافاصله در نظر گرفته میشوند.

## خودترمیمی

- **حذف موقت**: امتیاز < 0.2 ← حذف بهمدت ۵ دقیقه (عقبنشینی تدریجی، حداکثر ۳۰ دقیقه)
- **آگاهی از قطعکنندهٔ مدار**: OPEN ← حذف خودکار؛ HALF_OPEN ← درخواستهای آزمایشی
- **حالت رخداد**: بیش از ۵۰٪ OPEN ← غیرفعالکردن کاوش و بهحداکثررساندن پایداری
- **بازیابی پس از دورهٔ انتظار**: پس از پایان حذف، اولین درخواست یک «آزمایش» با زمانانتظار کاهشیافته است

## کاوش Bandit

۵٪ از درخواستها (قابل پیکربندی) برای کاوش به ارائهدهندگان تصادفی هدایت میشوند. این قابلیت در حالت رخداد غیرفعال است.

## API

**هیچ نقطه پایانی اختصاصی `POST /api/combos/auto` وجود ندارد** — Auto-Combo به دو روش استفاده میشود:

1. **بدون پیکربندی (توصیهشده):** هر درخواست تکمیل چت را با `model: "auto"` یا `model: "auto/<variant>"` ارسال کنید. کارخانه مجازی برای هر درخواست ترکیب را میسازد — نیازی به ذخیرهسازی دائمی یا فراخوانیهای API نیست.

2. **ترکیب ذخیرهشده با `strategy: "auto"`:** یک ترکیب معمولی را از طریق `POST /api/combos` ایجاد کنید و `strategy: "auto"` را همراه با `config.auto.weights` / `config.auto.candidatePool` تنظیم کنید. از همان موتور امتیازدهی استفاده میشود؛ ترکیب در `combos` ذخیره شده و از طریق شناسه قابل استفاده مجدد است.

برای کشف، `GET /api/combos/auto` تمام گونهها را همراه با مجموعه کاندیداهای نهاییشده و نیز `context_length` / `max_output_tokens` فهرست میکند — یعنی مقدار MAX در میان پنجرههای مجموعه کاندیداها. کلاینتها (برای مثال افزونه opencode) باید این مقادیر را بهجای `0` اعلام کنند: زمینه صفر، فشردهسازی خودکار opencode را کاملاً غیرفعال میکند و اجازه میدهد نشستها آنقدر رشد کنند تا پاکسازی تاریخچه در درگاه، زمینه را از بین ببرد. اعلام مقدار MAX ایمن است، زیرا پیشفیلتر زمینه Auto-Combo درخواستهای بیشازحد بزرگ را به کاندیداهایی با پنجره بزرگ هدایت میکند.

```bash
# استفاده بدون پیکربندی (بدون ایجاد ترکیب)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ترکیب خودکار ذخیرهشده از طریق نقطه پایانی معمول ترکیبها
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### راهبردهای مسیریاب خودکار

ترکیبهای ذخیرهشده با `strategy: "auto"` میتوانند `config.routerStrategy` (یا گزینه قدیمی
`config.auto.routerStrategy`) را روی یکی از موارد زیر تنظیم کنند:

- `rules` — امتیازدهی وزنی پیشفرض
- `score` — بالاترین امتیاز وزنی پیکربندیشده را انتخاب میکند. در صورت تساوی دقیق، ترتیب
  پیکربندیشده کاندیداها حفظ میشود؛ `explorationRate` موجود از کل مجموعه رتبهبندیشده نمونهبرداری میکند.
- `cost` / `eco` — ارزانترین ارائهدهنده سالم
- `latency` / `fast` — کمترین تأخیر p95 همراه با جریمه قابلیت اطمینان
- `sla-aware` / `sla` — کاندیداهایی را ترجیح میدهد که SLOهای تأخیر p95، نرخ خطا و در صورت وجود
  هزینه را برآورده میکنند
- `lkgp` — ابتدا آخرین ارائهدهنده شناختهشده سالم
- `nadir` — از API تصمیمگیری [Nadir](https://getnadir.com) میپرسد که اعلان به کدام مدل موجود در مجموعه
  نیاز دارد؛ استفاده از آن اختیاری است و در صورت شکست بهصورت باز به `rules` بازمیگردد

### جزئیات راهبردهای مسیریاب

موتور Auto-Combo هفت پیادهسازی قابلتعویض **RouterStrategy** را ارائه میکند که
میتوانید آنها را از طریق `config.routerStrategy` (یا گزینه قدیمی `config.auto.routerStrategy`) تعویض کنید.
هر راهبرد با توجه به یک `RoutingContext`، یک ارائهدهنده را از مجموعه کاندیداها انتخاب میکند
(نوع وظیفه، نشانههای ابزار/بینایی، تخمین توکن، سیاست اختیاری SLA و آخرین
ارائهدهنده شناختهشده سالمِ اختیاری).

#### 1. `rules` (پیشفرض) — امتیازدهی وزنی با ۱۶ عامل

موتور امتیازدهی موجود را در بر میگیرد. کاندیداهای مدارشکن با وضعیت `OPEN` را
حذف میکند، سپس `scorePool()` را با نوع وظیفه فعلی و `getTaskFitness()` اجرا کرده و
ارائهدهنده دارای بالاترین امتیاز را انتخاب میکند.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**زمان استفاده**: پیشفرض. زمانی استفاده کنید که به موازنهای متعادل میان همه سیگنالها نیاز دارید.

**نام مستعار**: `rules` (بدون نام مستعار)

---

#### 2. `cost` / `eco` — ارزانترین ارائهدهنده سالم

مجموعه کاندیداها را بر اساس `costPer1MTokens` (صعودی) مرتب کرده و ارزانترین گزینه را انتخاب میکند.
ابتدا کاندیداهای دارای وضعیت `OPEN` را حذف میکند.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**زمان استفاده**: بارهای کاری حساس به هزینه، پردازش دستهای یا کارهای پسزمینه.

**نامهای مستعار**: `cost`، `eco`

---

#### 3. `latency` / `fast` — کمترین تأخیر p95 همراه با جریمه قابلیت اطمینان

بر اساس `p95LatencyMs + (errorRate * 1000)` مرتب میکند. جریمه نرخ خطا تضمین میکند
ارائهدهندگان غیرقابلاعتماد، حتی اگر تأخیر اسمی آنها کم باشد، در رتبه پایینتری قرار گیرند.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**زمان استفاده**: بارهای کاری حساس به تأخیر، مانند چت بلادرنگ، تکمیل خودکار یا
دستیارهای تعاملی کدنویسی.

**نامهای مستعار**: `latency`، `fast`

---

#### 4. `sla-aware` / `sla` — انطباق با SLO تأخیر/خطا/هزینه

هر کاندیدا را بر اساس میزان انطباق آن با سیاست SLO پیکربندیشده امتیازدهی میکند:

| عامل           | وزن | فرمول                                             |
| -------------- | --- | ------------------------------------------------- |
| امتیاز تأخیر   | 35% | `threshold / max(value, ε)`                       |
| امتیاز خطا     | 35% | `threshold / max(value, ε)`                       |
| امتیاز سلامت   | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| امتیاز هزینه   | 10% | `threshold / max(value, ε)` یا نرمالسازی معکوس    |
| امتیاز پایداری | 5%  | انحراف معیار تأخیر با نرمالسازی معکوس             |

وقتی `hardConstraints: true` باشد، گزینهها ابتدا بر اساس **امتیاز نقض**
(اینکه تا چه اندازه از هر SLO فراتر میروند) و سپس بر اساس امتیاز ترکیبی مرتب میشوند. در غیر این صورت،
فقط امتیاز ترکیبی ملاک است.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... هر گزینه را بر اساس policy امتیازدهی میکند: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**فیلدهای SLA** (در پیکربندی combo تنظیم میشوند):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**زمان استفاده**: بارهای کاری محیط عملیاتی با بودجههای سختگیرانه برای تأخیر، نرخ خطا یا هزینه.

**نامهای مستعار**: `sla-aware`، `sla`

---

#### 5. `lkgp` — ابتدا آخرین ارائهدهنده سالم شناختهشده

ابتدا **آخرین ارائهدهنده سالم شناختهشده** را (در صورت تنظیم بودن) امتحان میکند و سپس به
استراتژی `rules` برمیگردد. این روش برای چسبندگی نشست مفید است؛ یعنی همان ارائهدهنده
درخواستهای بعدی یک مکالمه را مدیریت میکند.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // بازگشت به استراتژی rules
    return getStrategy("rules").select(pool, context);
  }
}
```

**زمان استفاده**: مکالمات چندمرحلهای که میخواهید همان ارائهدهنده درخواستهای
بعدی را مدیریت کند (برای مثال، جهت کشکردن، تداوم زمینه یا ثبات قیمتگذاری).

**نام مستعار**: `lkgp` (بدون نام مستعار)

---

#### 6. `nadir` — انتخاب مدل آگاه از پرامپت از طریق Nadir

هر یک از استراتژیهای بالا گزینهها را بر اساس تلهمتری خود رتبهبندی میکند؛ هیچیک از آنها
درخواست را نمیخواند. `nadir` آخرین نوبت کاربر را بههمراه شناسههای مدل موجود در pool به
API تصمیمگیری [Nadir](https://getnadir.com) (`POST /v1/bucket`) میفرستد و درخواست را به مدلی
هدایت میکند که Nadir از آن فهرست انتخاب کرده است (`simple` → ارزانترین مدل توانمند، `complex` → مدل
پیشرو). اتصال ارائهدهنده آن مدل همچنان توسط `rules` انتخاب میشود؛ بنابراین سهمیه،
سلامت و هزینه همچنان تعیین میکنند که از کدام حساب استفاده شود.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` و `OMNIROUTE_NADIR_BASE_URL` جایگزینهای محیطی برای این دو
رشته هستند. `baseUrl` فقط برای Nadir خودمیزبان لازم است (وجود `/v1` در انتهای آن قابل قبول است).
درخواستهای بدون کلید وارد سطح ناشناس Nadir میشوند که برای هر IP دارای محدودیت نرخ است. با یک کلید
([یکی ایجاد کنید](https://app.getnadir.com/dashboard/api-keys))، هر تصمیم
در داشبورد Nadir شما ثبت میشود. راهاندازی و تأیید کامل:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/).

دادههایی که از سیستم خارج میشوند: متن آخرین پیام کاربر (اولین 16k نویسه)، شناسههای
مدلهای گزینه و یک برچسب کانال `source: "omniroute"`. هیچ پرامپت سیستمی، تاریخچه، ابزار یا
هدرهایی ارسال نمیشوند.

رفتار در زمان شکست بهصورت fail-open است: timeout (پیشفرض 2000 ms)، پاسخ غیر 2xx، میزبان
غیرقابلدسترسی، پاسخ نامعتبر یا انتخابی خارج از pool، همگی با تصمیم `rules`
حل میشوند و پیشوند `NadirStrategy: fallback (…)` به دلیل افزوده میشود. پس از یک فراخوانی ناموفق،
استراتژی بهمدت 30 s از ارسال درخواست شبکه خودداری میکند؛ بنابراین یک قطعی، بهجای یک timeout
برای هر درخواست، تنها یک timeout در هر 30 s ایجاد میکند. رویدادهای مسیریابی فقط زمانی
`strategy: "nadir"` را گزارش میکنند که Nadir واقعاً انتخاب را انجام داده باشد.

**زمان استفاده**: ترافیکی با سطح دشواری متنوع روی poolای که چند سطح مدل را در بر میگیرد (یک مدل کوچک، یک مدل
میانی و یک مدل پیشرو)، زمانی که میخواهید هزینه ناشی از استفاده همیشگی از مدل پیشرو را کاهش دهید.

**نام مستعار**: `nadir` (بدون نام مستعار)

### استراتژیهای سفارشی مسیریاب

میتوانید پیادهسازی `RouterStrategy` خود را از طریق API عمومی ثبت کنید:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // منطق مسیریابی شما در اینجا قرار میگیرد
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

سپس از آن استفاده کنید:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### راهنمای انتخاب استراتژی مسیریاب

| مورد استفاده          | راهبرد      | دلیل                                           |
| --------------------- | ----------- | ---------------------------------------------- |
| بار کاری متعادل       | `rules`     | پیشفرض — همه عوامل را در نظر میگیرد            |
| به حداقل رساندن هزینه | `cost`      | همیشه ارزانترین گزینه را انتخاب میکند          |
| به حداقل رساندن تأخیر | `latency`   | سریعترین ارائهدهنده قابلاعتماد را انتخاب میکند |
| SLOهای سختگیرانه      | `sla-aware` | بر اساس آستانههای p95/خطا/هزینه فیلتر میکند    |
| گفتوگوی چندمرحلهای    | `lkgp`      | حفظ وابستگی نشست                               |
| دشواری ترکیبی         | `nadir`     | رده مدل را برای هر پرامپت انتخاب میکند         |

فیلدهای آگاه از SLA:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## تناسب وظیفه

بیش از ۳۰ مدل در ۶ نوع وظیفه (`coding`، `review`، `planning`، `analysis`، `debugging`، `documentation`) امتیازدهی شدهاند. از الگوهای wildcard پشتیبانی میشود (برای مثال، `*-coder` → امتیاز بالای کدنویسی).

## مرور گونههای Auto

با احتساب `auto` ساده (پیشفرض) بهعلاوهٔ ۶ مقدار `AutoVariant` تعریفشده در `autoPrefix.ts`، در مجموع **۷ شناسهٔ مدل قابل فراخوانی** وجود دارد:

`auto`، `auto/coding`، `auto/fast`، `auto/cheap`، `auto/offline`، `auto/smart`، `auto/lkgp`

(`AutoVariant` خود شامل ۶ مقدار است؛ گزینهٔ هفتم «بدون گونه» — یعنی `auto` ساده — است که توسط `parseAutoPrefix()` بهشکل `variant: undefined` مدیریت میشود.)

## جایگاه سطوح در Auto-Combo

تابع امتیازدهی ۱۶عاملی (`open-sse/services/autoCombo/scoring.ts`) عضویت در سطح را بهعنوان دو سیگنال در نظر میگیرد: `tierPriority` (0.0476) و `tierAffinity` (0.0476). برای مشاهده مجموعه کامل `DEFAULT_WEIGHTS`، جدول مرجع [عوامل امتیازدهی](#how-it-works-persisted-auto-combos) در بالا را ببینید — مقادیر بازنویسیشده برای هر بسته (ship-fast/cost-saver/quality-first/
offline-friendly) در جدول «پروفایلهای وزن برای هر بسته» فهرست شدهاند.

سطح بهتنهایی **باعث نمیشود** سطح ۱ در اولویت قرار گیرد — اگر تأخیر سطح ۱ نامطلوب باشد یا
نسبت هزینه به کیفیت بهینه نباشد، سطح ۲ انتخاب میشود. برای اجبار ترتیب سطوح، از استراتژی
`priority` برای ترکیب استفاده کنید و ارائهدهندگان را بر اساس سطح مرتب کنید.

برای ترجیح قوی سطح ۱ (اشتراکی)، وزن `tierPriority` را افزایش دهید:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

برای تعاریف سطوح و دستهبندی ارائهدهندگان، به [`docs/guides/TIERS.md`](../guides/TIERS.md) مراجعه کنید.

## تست و پوشش

### ماتریس مسیریابی-تصمیم قطعی (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` مسیریابی را ثابت می کند** تصمیم گیری** از تمام 21 استراتژی عمومی از طریق خط لوله ترکیبی واقعی با یک بالادست مسخره شده، سرتاسر. پوشش شامل:

- همه 21 استراتژی `ROUTING_STRATEGY_VALUES` (مرتب، وزن، هزینه، زمینه، ترکیب، ...).
- `quota-share` (داخلی) انتها به انتها: DRR انصاف + اولویتبندی اشباع از طریق درز `selectQuotaShareTarget` واقعی (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`).
- پوشش جهانی دستیابی `context-relay` در هر تعداد هدف.

این مجموعه در CI (`test:integration` job) با `--test-concurrency=1` و `--test-force-exit` اجرا می شود، بنابراین قطعی است و نیازی به اعتبارنامه زنده ندارد.

### دود زنده دردار (NOT در ارائه دهندگان واقعی CI — )

| فرمان                                  | کاری که انجام می دهد                                                              |
| :------------------------------------- | :-------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | مسیریابی واقعی در فرآیند با `RUN_COMBO_LIVE=1`; عکس های فوری یک OmniRoute DB زنده |
| `npm run test:combo:live:vps`          | تماسهای HTTP علیه سرور OmniRoute زنده (تنظیم `COMBO_LIVE_BASE_URL`)               |
| `npm run test:combo:live:vps:failover` | همان، با سناریوهای شکست عمدی                                                      |

این تستهای دود، مسیر سیم واقعی را اعمال میکنند (تکمیل → ارائهدهنده ترکیبی → ). آنها عمداً از CI مستثنی شده اند زیرا به اعتبارنامه زنده و دسترسی VPS نیاز دارند.
