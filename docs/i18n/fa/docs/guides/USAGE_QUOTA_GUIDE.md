> **خلاصه**: OmniRoute مصرف توکنِ هر درخواست را ردیابی میکند، هزینه را محاسبه میکند، سهمیهٔ هر کلید API را اعمال میکند و تحلیلها را در داشبورد نمایش میدهد. این راهنما نحوهٔ عملکرد همهٔ این بخشها را توضیح میدهد.

**منابع:**

- `open-sse/services/usage.ts` (~70KB) — ردیابی اصلی مصرف
- `src/lib/usageAnalytics.ts` (~10KB) — تجمیع دادهها برای داشبورد
- `src/lib/db/quotaSnapshots.ts` — دادههای تاریخی سهمیه
- `src/lib/db/usage*.ts` — چندین ماژول پایگاه داده مرتبط با مصرف

## نمای کلی

هر درخواستی که از OmniRoute عبور میکند، یک **رکورد مصرف** ایجاد میکند که موارد زیر را ثبت میکند:

- **هویت**: کلید API، ارائهدهنده، مدل و ترکیب مربوطه
- **توکنها**: توکنهای پرامپت، توکنهای تکمیل، توکنهای کششده و مجموع
- **هزینه**: مبلغ به دلار آمریکا (محاسبهشده از دادههای قیمتگذاری)
- **زمانبندی**: تأخیر و مهرهای زمانی شروع/پایان
- **وضعیت**: موفق، خطا، محدودشده بر اساس نرخ و غیره

این رکوردها در قالب **تحلیلها** تجمیع میشوند، بهصورت **تصاویر لحظهای سهمیه** ذخیره میشوند و برای اعمال **محدودیت بودجهٔ هر کلید** مورد استفاده قرار میگیرند.

```
درخواست ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    تحلیلها   سهمیه   صورتحساب
                    (داشبورد)  (اعمال)  (خروجی)
```

## چه چیزهایی ثبت می‌شوند

سرویس `usage.ts` برای هر درخواست یک **رویداد مصرف** ثبت می‌کند:

| فیلد               | نوع    | منبع                                                         |
| ------------------ | ------ | ------------------------------------------------------------ |
| `id`               | رشته   | UUID تولیدشده هنگام ثبت                                      |
| `apiKeyId`         | رشته   | کلید API که درخواست را آغاز کرده است                         |
| `provider`         | رشته   | شناسهٔ ارائه‌دهنده (openai، anthropic و غیره)                |
| `model`            | رشته   | شناسهٔ مدل (gpt-5، claude-opus-4-6 و غیره)                   |
| `comboId`          | رشته؟  | شناسهٔ ترکیب، اگر مسیریابی از طریق یک ترکیب انجام شده باشد   |
| `promptTokens`     | عدد    | از پاسخ بالادستی                                             |
| `completionTokens` | عدد    | از پاسخ بالادستی                                             |
| `cachedTokens`     | عدد    | توکن‌های بازیابی‌شده از کش (کش‌کردن پرامپت Anthropic و غیره) |
| `totalTokens`      | عدد    | پرامپت + تکمیل                                               |
| `costUsd`          | عدد    | محاسبه‌شده بر اساس داده‌های قیمت‌گذاری                       |
| `latencyMs`        | عدد    | مدت‌زمان سرتاسری درخواست                                     |
| `status`           | شمارشی | `success`, `error`, `rate_limited`, `timeout`, `cancelled`   |
| `errorClass`       | رشته؟  | کلاس خطا، اگر وضعیت برابر با success نباشد                   |
| `timestamp`        | رشته   | ISO 8601 UTC                                                 |
| `metadata`         | شیء    | داده‌های سفارشی تزریق‌شده توسط افزونه                        |

### توکن‌ها از کجا می‌آیند

توکن‌ها در **پردازشگر پاسخ** از پاسخ ارائه‌دهندهٔ بالادستی استخراج می‌شوند:

```ts
// از open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

برای ارائه‌دهندگانی که اطلاعات مصرف را برنمی‌گردانند (برخی ارائه‌دهندگان مبتنی بر کوکی وب)، OmniRoute توکن‌ها را با استفاده از قاعدهٔ تقریبی `~4 chars per token` **تخمین می‌زند** (به `open-sse/services/autoCombo/pipelineRouter.ts` مراجعه کنید).

### توکن‌های کش‌شده

OmniRoute مقدار `cached_tokens` را جدا از `prompt_tokens` ردیابی می‌کند، زیرا:

- قابلیت کش‌کردن پرامپت Anthropic برای توکن‌های کش‌شده هزینهٔ کمتری دریافت می‌کند (10% نرخ عادی)
- برخی ارائه‌دهندگان مقدار `cache_read_input_tokens` را برمی‌گردانند که باید با نرخ متفاوتی قیمت‌گذاری شود
- تحلیل‌ها می‌توانند **نرخ اصابت کش** = `cached_tokens / prompt_tokens` را نمایش دهند

### عیب‌یابی رده‌های نوشتن در کش

پنل سلامت کش پرامپت در داشبورد تحلیل‌ها، نوشتن‌های 5 دقیقه‌ای و 1 ساعته در کش را که ارائه‌دهنده گزارش می‌کند،
از یکدیگر تفکیک می‌کند. مقادیر
`usage.cache_creation.ephemeral_5m_input_tokens` و
`usage.cache_creation.ephemeral_1h_input_tokens` در Anthropic، طی تبدیل اطلاعات مصرف در حالت جریانی و
غیرجریانی حفظ می‌شوند و همراه با خلاصه‌های گزارش فراخوانی ذخیره می‌شوند. مجموع
نوشتن در کش، بار دیگر به این دسته‌ها اضافه نمی‌شود.

فراخوانی‌هایی که فقط شمارندهٔ تجمیعی نوشتن دارند، از جمله رکوردهای قدیمی‌تر، رده‌ای نامشخص
دارند. در تفکیک جزئی، باقی‌ماندهٔ تخصیص‌نیافته همچنان نامشخص می‌ماند؛ شمارنده‌های نامعتبر یا
متناقض علامت‌گذاری می‌شوند، نه اینکه بدون اطلاع به آن‌ها TTL اختصاص داده شود. نشانگرهای
TTL سمت درخواست، مدرکی برای ردهٔ صورتحساب‌شده نیستند.

برآورد نوشتن معادل API در این پنل فقط رده‌های گزارش‌شده و دارای قیمت را پوشش می‌دهد، نه
کل درخواست را. برای قیمت‌گذاری بومی مدل‌های Claude/Anthropic، این برآورد از 1.25 برابر
نرخ ورودی برای نوشتن‌های 5 دقیقه‌ای و دو برابر نرخ ورودی برای نوشتن‌های 1 ساعته استفاده می‌کند. نبود
اطلاعات قیمت‌گذاری به معنای در دسترس نبودن آن است، نه صفر بودن. قیمت‌ها هنگام ثبت هر فراخوانی جدید ذخیره می‌شوند؛
رکوردهای تاریخی دوباره قیمت‌گذاری نمی‌شوند. بنابراین حساب‌های اشتراکی می‌توانند
برآوردی معادل API داشته باشند، بدون آنکه آن مبلغ به‌عنوان هزینهٔ نقدی یا سهمیهٔ اشتراک
از آن‌ها کسر شود. محاسبات فعلی سهمیه، بودجه و هزینهٔ دقیق ارائه‌دهنده بدون تغییر باقی می‌مانند.

این ابزارهای عیب‌یابی از خلاصهٔ محدود و موجود سلامت کش و سازوکار نگهداری گزارش فراخوانی
استفاده می‌کنند. آن‌ها پیش‌فرض‌های TTL درخواست، مسیریابی یا انتخاب حساب را تغییر نمی‌دهند.
ثبت TTL درخواستی کلاینت در مقایسه با TTL مؤثر خروجی در نقطهٔ ارسال به ارائه‌دهنده
به آینده موکول شده است؛ این پنل رده‌های رسید را گزارش می‌کند، نه TTL مؤثر خروجی را.

پیاده‌سازی: `src/lib/usage/cacheWriteEstimate.ts`،
`src/lib/usage/cacheHealth.ts` و `open-sse/utils/cacheWriteUsage.ts`.

## محاسبه هزینه

هزینهها بر اساس **دادههای قیمتگذاری** همگامسازیشده از LiteLLM (`src/lib/pricingSync.ts`) محاسبه میشوند:

| مدل               | ورودی $/1M | خروجی $/1M | کششده $/1M |
| ----------------- | ---------- | ---------- | ---------- |
| gpt-5             | $2.50      | $10.00     | —          |
| claude-opus-4-6   | $15.00     | $75.00     | $1.50      |
| claude-sonnet-4-5 | $3.00      | $15.00     | $0.30      |
| gemini-2.5-pro    | $1.25      | $10.00     | —          |

فرمول هزینه (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **چرا مقدار کششده از پرامپت کم میشود؟** بخش کششده بهصورت جداگانه قیمتگذاری میشود؛ اعمال قیمت ورودی بر کل پرامپت باعث محاسبه بیشازحد هزینه خواهد شد.

### همگامسازی قیمتگذاری

دادههای قیمتگذاری از طریق نقطه پایانی `/api/pricing/sync` بهطور خودکار از LiteLLM همگامسازی میشوند (این فرایند توسط وظیفه cron داخلی اجرا میشود، نه یک متغیر محیطی در دسترس کاربر):

```bash
# اجرای دستی
curl -X POST http://localhost:20128/api/pricing/sync
```

برای مدلهایی که داده قیمتگذاری ندارند، OmniRoute با استفاده از نرخهای میانگین داخلی (برگرفته از دادههای قیمتگذاری LiteLLM)، **هزینه را تخمین میزند**.

## تجمیع بازه‌های زمانی

ماژول `usageAnalytics.ts` ویجت‌های داشبورد را از داده‌های خام مصرف محاسبه می‌کند. این ماژول از 7 بازهٔ زمانی پشتیبانی می‌کند:

| بازه     | پنجرهٔ زمانی                    | مورد استفاده               |
| -------- | ------------------------------- | -------------------------- |
| `1d`     | 24 ساعت گذشته                   | تشخیص جهش ساعتی هزینه      |
| `7d`     | 7 روز گذشته                     | بررسی هفتگی                |
| `30d`    | 30 روز گذشته                    | صورت‌حساب ماهانه           |
| `90d`    | 90 روز گذشته                    | تحلیل سه‌ماهه              |
| `ytd`    | از 1 ژانویهٔ سال جاری           | پیگیری بودجهٔ سالانه       |
| `all`    | کل دوره                         | آمار کل دوره               |
| `custom` | شروع/پایان تعیین‌شده توسط کاربر | ممیزی‌ها، پرس‌وجوهای موردی |

### ویجت‌های محاسبه‌شدهٔ داشبورد

برای هر بازهٔ زمانی، لایهٔ تحلیل موارد زیر را محاسبه می‌کند:

| ویجت                          | توضیحات                                                  |
| ----------------------------- | -------------------------------------------------------- |
| **کارت‌های خلاصه**            | مجموع درخواست‌ها، مجموع هزینه، مجموع توکن‌ها، نرخ موفقیت |
| **نمودار روند روزانه**        | هزینه + توکن‌ها در هر روز، به‌صورت انباشته به تفکیک مدل  |
| **نقشهٔ حرارتی فعالیت**       | شبکهٔ ساعت روز × روز هفته، رنگ = تعداد درخواست‌ها        |
| **تفکیک بر اساس مدل**         | نمودار دایره‌ای هزینه به تفکیک مدل                       |
| **تفکیک بر اساس ارائه‌دهنده** | نمودار میله‌ای درخواست‌ها به تفکیک ارائه‌دهنده           |
| **کلیدهای API برتر**          | جدول 10 کلید برتر بر اساس هزینه                          |
| **تحلیل خطا**                 | نرخ خطا در طول زمان، پرتکرارترین دسته‌های خطا            |

### دسترسی برنامه‌نویسی

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // رکوردهای تاریخچهٔ مصرف
  "7d",                 // بازهٔ زمانی: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // نگاشت اتصال ارائه‌دهنده (connectionId → نام حساب)
  {
    startDate: "2025-01-01",  // اختیاری: برای بازهٔ "custom"
    endDate: "2025-06-01",   // اختیاری: برای بازهٔ "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (سنت)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## اعمال سهمیه

سهمیهٔ هر کلید API در دو نقطه اعمال می‌شود:

1. **محدودیت نرم** (`quotaWarnAt`): هشدار داشبورد هنگامی که مصرف از آستانه فراتر می‌رود
2. **محدودیت سخت** (`quotaLimit`): رد درخواست با HTTP 429 هنگام عبور از محدودیت

### پیکربندی

```ts
// برای هر کلید API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — نمایش هشدار
  quotaLimit: 10_00,    // $10.00 — توقف قطعی
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### جریان اعمال سهمیه

```
درخواست ──▶ quotaCheck()
              │
              ├── در محدودهٔ مجاز؟  ──▶ اجازه
              │
              └── فراتر از محدودیت؟  ──▶ 429 Too Many Requests
                                   همراه با سرآیند Retry-After
```

### تصاویر لحظه‌ای سهمیه

جدول `quotaSnapshots` **وضعیت تاریخی سهمیه** را برای تحلیل روند ذخیره می‌کند:

| فیلد | توضیحات |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | کلید تحت پیگیری |
| `window` | "day" | "week" | "month" |
| `used` | هزینهٔ مصرف‌شده در این پنجرهٔ زمانی (سنت) |
| `limit` | محدودیت (سنت) |
| `resetAt` | زمان بازنشانی پنجرهٔ زمانی |
| `createdAt` | زمان ثبت تصویر لحظه‌ای |

تصاویر لحظه‌ای **در هر درخواست** با هزینهٔ > 0 ثبت می‌شوند و برای موارد زیر به کار می‌روند:

- نمایش نوار پیشرفت سهمیه در داشبورد
- نمایش نمودارهای روند سهمیهٔ 30 روزه
- فعال‌سازی هشدارها هنگام نزدیک شدن مصرف به محدودیت

### پرس‌وجوی تحلیل‌های مصرف

دسترسی به داده‌های مصرف از طریق داشبورد یا ابزارهای MCP انجام می‌شود، نه از طریق نقاط پایانی REST برای خروجی‌گیری مستقیم. تحلیل‌های در دسترس:

- **`/api/usage/analytics`** — معیارهای تجمیع‌شدهٔ مصرف (گروه‌بندی بر اساس مدل، ارائه‌دهنده، کلید)
- **`/api/usage/quota`** — وضعیت فعلی سهمیه برای هر کلید API
- **`/api/usage/history`** — گزارش‌های تاریخچهٔ درخواست‌ها

## نگهداری و پاک‌سازی

حجم داده‌های مصرف به‌ازای هر درخواست حدود 1 تا 10 کیلوبایت افزایش می‌یابد. در مقیاس بالا، این مقدار می‌تواند قابل‌توجه باشد.

### تنظیمات نگهداری

مدت نگهداری تاریخچهٔ مصرف از طریق تنظیمات پایگاه داده در رابط کاربری یا از طریق `/api/settings/database` پیکربندی می‌شود.

به‌طور پیش‌فرض، تاریخچهٔ مصرف به‌مدت **90 روز** نگهداری می‌شود.

### پاک‌سازی

رکوردهای قدیمی توسط `src/lib/db/cleanup.ts` پاک‌سازی می‌شوند:

- توسط فرایند cron پس‌زمینه اجرا می‌شود
- رکوردهای `usage_history` را که قدیمی‌تر از مدت نگهداری پیکربندی‌شده در تنظیم `usageHistory` هستند، حذف می‌کند

### برآورد فضای ذخیره‌سازی

| نرخ درخواست            | فضای ذخیره‌سازی 30 روزه | فضای ذخیره‌سازی 90 روزه |
| ---------------------- | ----------------------- | ----------------------- |
| 100 درخواست در روز     | حدود 3 مگابایت          | حدود 9 مگابایت          |
| 1,000 درخواست در روز   | حدود 30 مگابایت         | حدود 90 مگابایت         |
| 10,000 درخواست در روز  | حدود 300 مگابایت        | حدود 900 مگابایت        |
| 100,000 درخواست در روز | حدود 3 گیگابایت         | حدود 9 گیگابایت         |

برای ترافیک بسیار بالا، موارد زیر را در نظر بگیرید:

- کاهش مدت نگهداری از طریق تنظیمات پایگاه داده
- استفاده از `aggregated_metrics` به‌جای رکوردهای خام (فقط برای تحلیل‌ها)

## نکات بهینه‌سازی هزینه

### 1. از مدل مناسب استفاده کنید

```bash
# پاسخ سریع — از مدل ارزان و سریع استفاده کنید
curl -d '{"model":"auto/fast","messages":[...]}'

# کار پیچیده — از مدل باکیفیت استفاده کنید
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. کش را فعال کنید

کش‌کردن پرامپت در Anthropic باعث **۹۰٪ صرفه‌جویی در هزینهٔ زمینهٔ تکراری** می‌شود:

```ts
// کش‌کردن خودکار است — کافی است همان پرامپت سیستمی طولانی را وارد کنید
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // به‌صورت خودکار کش می‌شود
  messages: [{ role: "user", content: "..." }],
});
```

### 3. از فشرده‌سازی استفاده کنید

فشرده‌سازی RTK + Caveman باعث **۱۵ تا ۹۵٪ صرفه‌جویی در نشست‌های با استفادهٔ زیاد از ابزارها** می‌شود:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. برای هر کلید سهمیه تعیین کنید

همیشه `quotaLimit` را تنظیم کنید تا از افزایش مهارنشدهٔ هزینه‌ها جلوگیری شود:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // سقف ۱۰ دلار در ماه
```

### 5. پرمصرف‌ترین‌ها را بررسی کنید

از داشبورد یا **`/api/usage/analytics`** برای گروه‌بندی بر اساس کلید API و مرتب‌سازی بر اساس هزینه استفاده کنید:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## عیب‌یابی

### «هزینه بیشتر از حد انتظار است»

1. **`/api/usage/analytics?groupBy=model`** را بررسی کنید — مدل پرهزینه را پیدا کنید
2. **`/api/usage/analytics?groupBy=apiKey`** را بررسی کنید — مصرف‌کنندهٔ پرمصرف را پیدا کنید
3. مطمئن شوید داده‌های قیمت‌گذاری به‌روز هستند: `POST /api/pricing/sync`

### «رکوردها موجود نیستند»

- تنظیمات نگهداری پایگاه داده را در داشبورد → پایگاه داده → پاک‌سازی بررسی کنید — رکوردهای قدیمی توسط وظیفهٔ پاک‌سازی دوره‌ای حذف می‌شوند (`src/lib/db/cleanup.ts`)
- خطاهای `src/lib/db/usage*.ts` را بررسی کنید — خطاهای نوشتن در پایگاه داده ثبت می‌شوند، اما نمایش داده نمی‌شوند
- مطمئن شوید درخواست واقعاً به `chatCore` رسیده است — مسیریابی ترکیبی را بررسی کنید

### «سهمیه اعمال نمی‌شود»

- تنظیم `quotaLimit` کلید را بررسی کنید
- مطمئن شوید `quotaWindow` به‌درستی تنظیم شده است
- به‌دنبال رکوردهای `quotaSnapshots` بگردید — این رکوردها باید در هر درخواست ایجاد شوند
