> بهصورت خودکار 15 تا 95٪ در محتوای واجد شرایط صرفهجویی کنید. برای یک مرور سریع، به [بخش فشردهسازی README](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) مراجعه کنید.

## نمای کلی

OmniRoute یک خط لولهٔ ماژولار برای فشردهسازی پرامپت پیادهسازی میکند که **بهصورت پیشگیرانه** پیش از رسیدن درخواستها به ارائهدهندگان بالادستی اجرا میشود. این یعنی صرفهجویی در توکنها بهطور شفاف انجام میشود — نیازی به تغییر در گردش کار شما نیست.

```
درخواست کلاینت
  → انتخابگر راهبرد فشردهسازی
    → بازنویسی توسط ترکیب؟ → استفاده از تنظیم ترکیب
    → آستانهٔ فعالسازی خودکار؟ → استفاده از حالت خودکار
    → حالت پیشفرض؟ → استفاده از تنظیم سراسری
    → خاموش؟ → صرفنظر از فشردهسازی
  → حالت فشردهسازی انتخابشده
    → خاموش: بدون فشردهسازی
    → سبک: پاکسازی ایمن فاصلهها/قالببندی (~15%)
    → استاندارد: حذف کلمات زائد به سبک Caveman (~30%)
    → تهاجمی: قدیمیسازی تاریخچه + خلاصهسازی (~50%)
    → فوقفشرده: هرس اکتشافی + تُنُکسازی بلوکهای کد (~75%)
    → RTK: پالایش آگاه از فرمانِ خروجی ترمینال/ابزار (بازهٔ بالادستی 60-90%)
    → انباشته: خط لولهٔ چندموتورهٔ مرتب، معمولاً ابتدا RTK و سپس Caveman (بازهٔ واجد شرایط 78-95%)
  → درخواست فشردهشده → ارائهدهنده
```

## حالت خاموش

هیچ فشردهسازیای اعمال نمیشود. همهٔ پیامها بدون تغییر عبور میکنند.

### حالت Lite (~15% صرفهجویی، <1ms تأخیر)

ایمنترین حالت — پاکسازی قالببندی. کوتاهسازی نتیجهٔ ابزار آن همراه با از دست رفتن داده است؛ بنابراین مسیر پیشفرض
(بدون `allow-lossy`، `engine:lite` یا فعالسازی ترکیب نامگذاریشده) حالت lite را با
`compressToolResults: false` اجرا میکند: نتایج قبلی ابزار بدون تغییر به ارائهدهنده میرسند.

| تکنیک                    | توضیح                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | ادغام خطوط خالی متوالی و فاصلههای انتهایی                                             |
| `dedupSystemPrompt`      | حذف پیامهای سیستمی تکراری                                                             |
| `compressToolResults`    | کوتاهسازی نتایج قبلی ابزار تا سقف lite (با از دست رفتن داده: فقط با فعالسازی درخواست) |
| `removeRedundantContent` | حذف دستورالعملهای تکراری                                                              |
| `replaceImageUrls`       | کوتاهسازی URIهای دادهای تصویر بر پایهٔ base64                                         |

**مناسب برای:** استفادهٔ همیشگی، گردشکارهای حساس از نظر ایمنی.

### حالت استاندارد (~30% صرفهجویی)

با الهام از [Caveman](https://github.com/JuliusBrussee/caveman) — واژههای زائد و عبارتبندیهای طولانی را حذف میکند و معنا را حفظ میکند:

- حذف واژههای پرکننده («لطفاً»، «فکر میکنم»، «اساساً»، «در واقع»)
- خلاصهسازی عبارتهای طولانی («بهمنظورِ» → «برای»، «در نتیجهٔ» → «به دلیلِ»)
- حذف احتیاطهای مؤدبانه («آیا ممکن است...»، «اگر امکانش هست...»)
- بیش از ۳۰ قاعدهٔ regex تنظیمشده برای درخواستهای کدنویسی

**مناسب برای:** گردشکارهای روزمرهٔ کدنویسی، تیمهای حساس به هزینه.

### حالت تهاجمی (~50% صرفهجویی)

مدیریت هوشمند تاریخچه برای نشستهای طولانی:

- **کهنهسازی پیامها** — پیامهای قدیمیتر بهصورت تدریجی فشرده میشوند
- **فشردهسازی نتیجهٔ ابزار** — خروجیهای طولانی ابزار کوتاه یا حذف میشوند (خطوط ابتدا/انتها،
  فیلترگذاری بر اساس خطوط منطبق، فشردهسازی کلیدهای JSON)
- **محافظهای یکپارچگی ساختاری** — اطمینان میدهد جفتهای `tool_use` + `tool_result` سازگار باقی بمانند
- **آگاهی از پنجرهٔ زمینه** — محدودیتهای توکن هر مدل را رعایت میکند

**مناسب برای:** نشستهای اشکالزدایی طولانی، پایگاههای کد بزرگ.

### حالت فوقالعاده (~75% صرفهجویی)

بیشینهٔ فشردهسازی برای سناریوهای حساس به تعداد توکن:

- **هرس اکتشافی** — هرس مبتنی بر امتیازدهی توکنهای نثر
- **حفظ ساختار** — بلوکهای کد محصورشده، کد درونخطی، URLها و شناسهها بهصورت موقت ذخیره و دوباره
  دقیقاً بازسازی میشوند و هرگز هرس نمیشوند
- **لایهٔ اختیاری SLM** — یک مدل محلی کوچک میتواند هرس را در صورت پیکربندی اصلاح کند
- مستقل از حالت تهاجمی است: کهنهسازی پیام، فشردهسازی نتیجهٔ ابزار یا خلاصهساز جایگزین را اجرا نمیکند
  (فقط شکست لایهٔ SLM میتواند یک گذر جایگزین را از طریق حالت تهاجمی مسیریابی کند)

**مناسب برای:** زمانی که بارها به محدودیتهای زمینه برخورد میکنید.

### حالت RTK (۶۰ تا ۹۰٪ در بازهٔ بالادستی)

حالت RTK برای خروجیهای طولانی ابزار که در نشستهای عامل کدنویسی ظاهر میشوند بهینه شده است:

- کلاسهای فرمان/خروجی مانند `git status`، `git diff`، `git log`، اجراکنندههای آزمون،
  ساختهای TypeScript/Vite/Webpack، ESLint/Biome/Prettier، ممیزی/نصبهای npm، گزارشهای Docker، خروجی
  زیرساخت و خروجی عمومی shell را شناسایی میکند
- بستههای فیلتر JSON را از `open-sse/services/compression/engines/rtk/filters/` اعمال میکند
- فیلترهای طرحوارهٔ TOML نسخهٔ ۱ RTK را از فایلهای `filters.toml` پروژه یا سراسری وارد میکند و اعتبارسنجی
  آزمون درونخطی و کنترل اعتماد برای فایلهای پروژه را انجام میدهد
- ۵۶ فیلتر داخلی را همراه با نمونههای تأیید درونخطی ارائه میکند
- دنبالههای کنترلی ANSI، نوارهای پیشرفت، خطوط تکراری و نویز غیرقابلاقدام را حذف میکند
- شکستها، خطاها، هشدارها، فایلهای تغییرکرده، خلاصهها و انتهای خروجیهای طولانی را حفظ میکند
- از فیلترهای پروژهٔ مشروط به اعتماد، فیلترهای سراسری و بازیابی اختیاری خروجی خامِ پالایششده پشتیبانی میکند

**مناسب برای:** نشستهای عامل با رونوشتهای shell، ساخت، آزمون، git، grep و خروجی فایل.

### حالت ترکیبی (۷۸ تا ۹۵٪ در بازهٔ واجد شرایط)

حالت ترکیبی چند موتور فشردهسازی را با ترتیبی قطعی اجرا میکند. خط لولهٔ پیشفرض:

```txt
RTK -> Caveman
```

این ترتیب ابتدا خروجی ترمینال/ابزار را فشرده نگه میدارد و سپس فشردهسازی معنایی Caveman را روی
پرامپت زبان طبیعی باقیمانده اعمال میکند. خط لولههای ترکیبی را میتوان بهصورت سراسری یا از طریق
ترکیبهای فشردهسازی اختصاصیافته به ترکیبهای مسیریابی پیکربندی کرد.

**مناسب برای:** زمینهٔ ترکیبی دارای گزارشهای بزرگ ابزار و همچنین دستورالعملهای انسانی یا خلاصههای دستیار.

## محاسبهٔ صرفهجویی بالادستی

OmniRoute صرفهجویی ناشی از فشردهسازی را بر اساس دو منبع مستند میکند: بنچمارکهای پروژههای بالادستی و
ترکیب موتورهای خود OmniRoute.

| منبع    | عدد استفادهشده از README بالادستی در اینجا                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` توکن خروجی کمتر، میانگین `65%` صرفهجویی در خروجی بنچمارک، بازهٔ `22-87%` و ابزار فشردهسازی ورودی با نرخ `~46%` |
| RTK     | `60-90%` صرفهجویی در خروجی فرمان؛ نشست نمونه با `~118,000 -> ~23,900` توکن، یا `79.7%` صرفهجویی (`~80%`)              |

برای بارهای همپوشان ابزار/بافت، ترکیب پیشفرض OmniRoute موتورها را بهصورت زنجیرهای به کار میگیرد:

```txt
RTK -> Caveman
```

صرفهجویی ترکیبی بهصورت ضربی محاسبه میشود، نه جمعی:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

عدد `78-95%` زمانی صدق میکند که RTK و Caveman هر دو بتوانند همان بار ورودی/بافت را کاهش دهند.
حالت خروجی پاسخ Caveman مستقل است: وقتی فعال باشد، از ارقام صرفهجویی خروجی خود Caveman استفاده کنید (میانگین `65%`،
عدد شاخص `~75%` و بازهٔ `22-87%`). صرفهجویی کلی در هزینه به ترکیب پرامپت/خروجی شما بستگی دارد.

### «واجد شرایط» واقعاً به چه معناست

بازهٔ شاخص 15-95% واقعی است، اما فقط برای محتوای **تکراری یا بیشازحد مفصل** صدق میکند — خطوط خطای تکراری،
گزارش ساختی که یک هشدار را مدام تکرار میکند، یا خروجی بیشازحد بزرگ `grep`/خواندن فایل. این
**به این معنا نیست** که هر درخواست تا این اندازه صرفهجویی ایجاد میکند.

بهصورت تجربی تأیید شده است (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): اجرای
`stacked` (RTK + Caveman) روی یک بلوک `tool_result` با ساختار Anthropic که شامل 300 خط خطای یکسان بود،
**95.93% صرفهجویی در توکن / 96.26% صرفهجویی در نویسه** ایجاد کرد — کاملاً در محدودهٔ بازهٔ اعلامشده.
اما اجرای همان خط لوله روی خروجی عادی و غیرتکراری ابزار (فهرستی تمیز از تطبیقهای `grep`،
خواندن کوتاه یک فایل یا متن مکالمهای معمولی) بهدرستی **صرفهجویی نزدیک به صفر** ایجاد میکند، زیرا
هیچ محتوای تکراریای برای حذف وجود ندارد و `validateCompression()` (`validation.ts`) اجازه نمیدهد
بازنویسیای ارسال شود که بلوکهای کد، URLها، عنوانها، نسخهها یا شناسههای ثابت تماماً با حروف بزرگ را حذف یا تغییر دهد.

این رفتاری مورد انتظار و ایمن است، نه یک باگ: یک نشست کدنویسی که عمدتاً فایلهای تمیز را میخواند یا در آنها
جستوجو میکند، حتی با فعال بودن کامل فشردهسازی نیز صرفهجویی کلی محدودی خواهد داشت؛ درحالیکه نشستی که با یک
حلقهٔ ناموفق یا یک لینتر پرحرف مواجه میشود، روی آن ترافیک از تمام بازهٔ 78-95% بهرهمند خواهد شد. درصد پایین
صرفهجویی تجمیعی در یک نشست را بهتنهایی نشانهٔ پیکربندی نادرست فشردهسازی ندانید — ابتدا بررسی کنید که آیا
خروجی زیربنایی ابزار واقعاً تکراری بوده است یا خیر.

## نمایش بصری صرفهجویی در توکن

```
بدون فشردهسازی:      47K توکن ارسالشده به LLM
با Lite:              40K توکن ارسالشده          (15% صرفهجویی — ایمن و همیشه فعال)
با Standard:          33K توکن ارسالشده          (30% صرفهجویی — قواعد caveman-speak)
با Aggressive:        24K توکن ارسالشده          (50% صرفهجویی — کهنهسازی + خلاصهسازی)
با Ultra:             12K توکن ارسالشده          (75% صرفهجویی — هرس ابتکاری)
با RTK:               19K-5K توکن ارسالشده       (60-90% صرفهجویی در خروجی فرمان/ابزار)
با Stacked:           10K-2.5K توکن ارسالشده     (بازهٔ واجد شرایط 78-95% برای RTK+Caveman)
```

## پیکربندی

### داشبورد

به `Dashboard → Context & Cache` بروید:

- **Caveman** — انتخاب حالت، بستههای زبانی، پیشنمایش و پیشفرضهای سراسری
- **RTK** — پیشنمایش فیلتر فرمان، تنظیمات ایمنی RTK و فهرست فیلترها
- **Compression Combos** — پایپلاینهای نامگذاریشدهٔ موتور که به ترکیبهای مسیریابی اختصاص داده شدهاند
- **Auto-Trigger Threshold** — فعالسازی خودکار فشردهسازی هنگام عبور تعداد توکنها از آستانه

### بازنویسی برای هر ترکیب

در `Dashboard → Context & Cache → Compression Combos`، یک ترکیب فشردهسازی را به یک
ترکیب مسیریابی اختصاص دهید:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

با این کار میتوانید از فشردهسازی زنجیرهای برای ارائهدهندگان رایگان/کدنویسی استفاده کنید و در
اشتراکهای پولی حالت lite را حفظ کنید.

این تخصیص «بازنویسی برای هر ترکیب» کنترلی متفاوت از بازنویسی **حالت فشردهسازی ترکیب
مسیریابی** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — طرحوارهٔ این فیلد
همچنین `rtk`، `stacked` و `omniglyph` را میپذیرد) است — این بازنویسی یک پایپلاین فشردهسازی
نامگذاریشده را انتخاب نمیکند؛ فقط فیلد `compressionMode` را تنظیم میکند که توسط
`resolveCompressionPlan` بررسی میشود. این گزینه را میتوان روی کارت ترکیب
(`Dashboard → Combos`) یا، از زمان #6760، برای هر ترکیب مسیریابی در فهرست «Assign to routing» در
`Dashboard → Context & Cache → Compression Combos`، درست کنار چکباکس تخصیص پایپلاین که در بالا
مستند شده است، تنظیم کرد. هر دو بخش از طریق همان نقطهٔ پایانی `PUT /api/combos/{id}` ذخیره میشوند.

### بازنویسی برای هر درخواست

برای بازنویسی طرح فشردهسازی یک درخواست منفرد، هدر درخواست `x-omniroute-compression` را ارسال
کنید. این گزینه بالاترین اولویت را دارد — بر بازنویسی ترکیب مسیریابی، نمایهٔ فعال، فعالسازی
خودکار و Default پنل غلبه میکند. مقادیر ناشناخته نادیده گرفته میشوند (درخواست هرگز رد
نمیشود) و کلید اصلی سراسری همچنان همهچیز را کنترل میکند: وقتی فشردهسازی بهصورت سراسری
خاموش باشد، این هدر نمیتواند آن را روشن کند. مقادیر:

| مقدار         | تأثیر                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | بدون فشردهسازی برای این درخواست.                                                                                    |
| `default`     | نمایهٔ Default مشتقشده از پنل (نمایهٔ فعال را نادیده میگیرد). موتورهای زیانبار خاموش میمانند.                       |
| `safe`        | همانند ارسال نکردن هدر.                                                                                             |
| `allow-lossy` | طرح عملیاتی این درخواست، شامل خلاصهها، فیلترهای مرتبطبودن و بازنویسیهای سبک، حفظ میشود.                             |
| `engine:<id>` | در صورت فعال بودن، یک موتور منفرد؛ برای مثال `engine:rtk`. این گزینهٔ صریح هر درخواست برای آن موتور است.            |
| `<combo>`     | یک ترکیب نامگذاریشده که ابتدا بر اساس نام (بدون حساسیت به بزرگی و کوچکی حروف) و سپس بر اساس شناسه تطبیق داده میشود. |

بدون `allow-lossy`، `engine:<id>` یا یک ترکیب نامگذاریشده، موتورهای زیانبار اعمال نمیشوند.
هنگامی که یک Default زیانبار، فعالسازی خودکار یا بازنویسی مسیریابی تنزل داده میشود،
OmniRoute مراحل بدون زیانِ شناختهشده را از پایپلاین زنجیرهای پیکربندیشده و به ترتیب پیکربندیشده
حفظ میکند. فقط زمانی به `session-dedup → lite` بازمیگردد که هیچ مرحلهٔ بدون زیانِ
پیکربندیشدهای باقی نمانده باشد.

پیشنمایش **Effective pipeline** در پنل Settings، طرح معمولِ ذخیرهشده را نشان میدهد. هنگامی
که فعالسازی خودکار قابلیت اجرا داشته باشد، همین پیشنمایش پایپلاین مؤثرِ شرطی آن را نیز نشان
میدهد تا وضوح پنل و حلوفصل زمان اجرا بدون هدر هماهنگ باقی بمانند.

طرح اعمالشده در هدر پاسخ `X-OmniRoute-Compression: <mode>; source=<source>` بازتاب داده میشود؛
در اینجا `<source>` یکی از `request-header`، `routing-override`، `active-profile`،
`auto-trigger`، `default` یا `off` است.

## قدردانیها

قواعد فشردهسازی حالت Standard از پروژه **[Caveman](https://github.com/JuliusBrussee/caveman)** ساخته **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ بیش از 51K) الهام گرفتهاند — پروژه فراگیر «چرا وقتی با توکن کم کار انجام میشود، از توکن زیاد استفاده کنیم». طبق گزارش Caveman، خروجی آن `~75%` توکن کمتر دارد، میانگین صرفهجویی خروجی در بنچمارکها `65%` است، دامنه صرفهجویی خروجی آن `22-87%` است و یک ابزار فشردهسازی ورودی با نرخ `~46%` ارائه میکند.

حالت RTK از **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** ساخته **[RTK AI](https://github.com/rtk-ai)** الهام گرفته است — پروژهای با کارایی بالا برای فشردهسازی خروجی فرمانها در ترمینال، ساخت، آزمون، git و پالایش خروجی ابزارها. طبق گزارش RTK، میزان صرفهجویی `60-90%` است و نشست نمونه در README آن، صرفهجویی `~80%` را نشان میدهد.

## سیستم های فشرده سازی پیشرفته

فراتر از 7 حالتی که در بالا توضیح داده شد (منبع حالتهای `codex-responses` و `omniglyph` را نیز میپذیرد، که این راهنما آنها را پوشش نمیدهد)، بخشهای زیر ویژگیهایی را پوشش میدهند که در داخل یا در کنار آن حالتها کار میکنند: فشردهسازی نتیجه ابزار و پیری پیشرونده، مراحل 1 و 2 موتور تهاجمی هستند (حالت تهاجمی و یک گام `aggressive` از یک Pipeline Stacked Pipeline چگونه است). فشردهسازی `aggressive` و `ultra` را به `standard` برای ارائهدهندگان ذخیرهسازی در هنگام فشردهسازی کاهش میدهد، و حالت خروجی Caveman و سبکهای خروجی بهطور پیشفرض دستورالعملهای درخواستی سیستم هستند که بهجای فشردهسازی درخواست، خروجی مدل را شکل میدهند.

### فشرده سازی Cache-Aware

برخی از ارائه دهندگان (مانند Anthropic با ذخیره سریع) پشتیبانی می کنند** ذخیره سریع** ، که به آنها امکان می دهد بخش هایی از درخواست را در حافظه پنهان ذخیره کنند تا هزینه ها و تأخیر کاهش یابد. هنگامی که حافظه پنهان فعال است، فشرده سازی تهاجمی در واقع می تواند** صدمه دیده** عملکرد زیرا توکن های کش را تغییر می دهد و کش را باطل می کند.

ماژول `cachingAware.ts` این مشکل را توسط** شناسایی زمینه ذخیره سازی** و** تنظیم استراتژی فشرده سازی** بر این اساس.

#### چگونه کار می کند

1. **زمینه ذخیره سازی را شناسایی کنید** — بدنه درخواست را برای نشانگرهای `cache_control` اسکن می کند
2. **ارائه دهندگان کش را شناسایی کنید** — بررسی می کند که آیا ارائه دهنده هدف از حافظه پنهان پشتیبانی می کند
3. **استراتژی را تنظیم کنید** — `aggressive`/`ultra` را به `standard` برای ارائهدهندگان حافظه پنهان تنزل میدهد
4. **رد شدن از درخواست سیستم** درخواستهای سیستم — معمولاً کش هستند، بنابراین آنها را فشرده نکنید

کمک کننده استراتژی همچنین یک پرچم `deterministicOnly` را برمی گرداند، اما سازنده برنامه فقط استراتژی — مصرف می کند، هیچ چیز پایین دست امروز پرچم را نمی خواند.

#### نمونه کد

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### زمان استفاده

فشرده سازی کش آگاه است** همیشه روشن** — بدون نیاز به پیکربندی هر زمان فشرده سازی فعال باشد و ارائه دهنده هدف از ذخیره سریع (Anthropic، OpenAI و غیره) پشتیبانی می کند، وارد می شود. نشانگرهای `cache_control` صریح مورد نیاز نیستند — یک ارائهدهنده ذخیرهسازی به تنهایی باعث کاهش رتبه میشود، و نشانگرها به تنهایی هرگز انجام نمیدهند (تشخیص نشانگر تلهمتری کش را تغذیه میکند، نه تصمیم استراتژی).

OpenRouter تنها برای مدلهای `anthropic/*` بهعنوان ارائهدهنده ذخیرهسازی به حساب میآید: درخواستهای کد Claude نقاط شکست `cache_control` خود را حفظ میکنند (حداکثر 4) و محافظ از پیشوند محافظت میکند، در حالی که سایر خانوادههای OpenRouter (`openai/`، `google/`، `qwen/`، ...) خالی و بدون محافظ میمانند.

### پیری پیشرونده

مکالمههای طولانی پیامهای زیادی را جمع میکنند، اما نوبتهای قدیمیتر کمتر مرتبط میشوند. `progressiveAging.ts`** پیام ها را با فاصله دور کاهش می دهد** (فاصله اندازه گیری شده از پایان مکالمه). با پیش فرض های ارسال شده (`verbatim: 2, light: 2, moderate: 3`):

- **2 پیچ آخر (فاصله ≤ 2)** : کلمه به کلمه حفظ شد
- **فاصله 3** : فشرده سازی غارنشین (حذف پرکننده)
- **مسافت 4 +** : پیام های دستیار خلاصه شده است. پیامهای کاربر به خط اول خود کاهش مییابد که دارای حداکثر 120 کاراکتر است. نقش های دیگر دست نخورده اعلانهای سیستم، پیامهای قدیمی و آخرین پیام کاربر همیشه بدون در نظر گرفتن فاصله، بهلفظ نگه داشته میشوند. هیچ چیز به طور کامل حذف نمیشود و باند `light` با پیشفرضهای ارسال شده قابل دسترسی نیست (`light` برابر `verbatim`).

#### نمونه کد

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### زمان استفاده

پیری پیشرونده است** همیشه روشن** برای حالت `aggressive` — مرحله 2 `compressAggressive()` است. حالت اولترا آن را اجرا نمی کند. به ویژه برای:

- جلسات برنامه نویسی طولانی مدت
- مکالمات چند روزه
- گردش کار نمایندگی با فراخوانی ابزارهای فراوان

### حالت خروجی غارنشین

حالت خروجی غارنشین اضافه می کند** دستورالعمل های سریع سیستم** که از خود مدل خروجی مختصر — میخواهد، سطح `lite` پاسخهای مختصری میخواهد که جملات کامل را حفظ میکند، `full` از آن میخواهد «مثل غارنشین هوشمند به صورت مختصر پاسخ دهد» و `ultra` خروجی تلگرافی میخواهد. دستورالعمل ها فقط درخواست می کنند، آنها نمی توانند آن را تضمین کنند. درخواست ها آنها را از طریق `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) دریافت می کنند: `open-sse/handlers/chatCore.ts` ابتدا انتخاب را با شیم back-compat حل می کند (`resolveOutputStyleSelection()` در `open-sse/services/compression/outputStyles/backCompat.ts`)، که در حالی که `outputStyles` خالی است، `cavemanOutputMode` فعال شده را به سبک خروجی `terse-prose` در `cavemanOutputMode.intensity` نگاشت می کند (به Back-compat زیر مراجعه کنید). یک انتخاب `outputStyles` غیر خالی همانطور که هست استفاده میشود، و `cavemanOutputMode.enabled` و `intensity` هیچ تاثیری ندارند، در حالی که ضامن `autoClarity` آن همچنان اعمال میشود. `outputMode.ts` متون دستورالعمل (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`)، بای پس محتوا و کمک کننده قرارگیری را که تزریق استفاده می کند، نگه می دارد. انژکتور `applyCavemanOutputMode()` خودش هیچ فراخوان تولیدی ندارد.

#### چگونه کار می کند

این حالت ورودی را فشرده نمی کند. یک بلوک دستورالعمل را به اعلان سیستم اضافه می کند (به نحوه عملکرد تزریق در زیر نگاه کنید)، و هر حالت فشرده سازی ورودی انتخاب شده برای درخواست همچنان روی بدنه ای که اکنون بلوک را حمل می کند، اجرا می شود. قبل از بند مرزهای مشترک که هر سطح به آن ختم می شود، سطح `full` انگلیسی می گوید:

> "مثل غارنشین هوشمند پاسخ دهید. مقالات را رها کنید (a/an/the)، پرکننده (just/really/basically/actually/simply)، چیزهای خوشایند، پرچین. تکههای OK. مترادفهای کوتاه (بزرگ نه گسترده، رفع نشده است). همه مواد فنی، کد، خطاها، URLs، شناسهها را دقیق نگه دارید."

این به ویژه برای:

- تولید کد (خروجی ترسر توکن های = کمتر)
- پرسش و پاسخ سریع (بدون نیاز به توضیحات مفصل)
- پردازش دسته ای (به حداکثر رساندن توان عملیاتی)

#### زمان استفاده

حالت خروجی غارنشین است** انتخاب کنید** . با فشرده سازی روشن (`enabled: true`، کلید اصلی در صفحه تنظیمات فشرده سازی)، آن را با `cavemanOutputMode.enabled` روشن کنید. `intensity` `lite`، `full` یا `ultra` را انتخاب می کند:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

یک ترکیب فشرده سازی** حالت خروجی** toggle (`outputMode`، سطح در `outputModeIntensity`) همان سوئیچ را برای درخواست هایی که ترکیبی برای آنها اعمال می شود تنظیم می کند و ابزار `omniroute_set_compression_engine` MCP آن را از طریق آرگومان `outputMode` بولی خود می نویسد. انتخاب `outputStyles` غیر خالی بر این سوئیچ اولویت دارد. در داشبورد، فعال کردن** نثر کوتاه** سبک خروجی همان بلوک را تزریق می کند (به سبک های خروجی زیر مراجعه کنید).

#### نحوه عملکرد تزریق

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) انتخاب را با کاتالوگ حل میکند (شناسههای ناشناخته و سبکهای ناهمخوان حذف میشوند، هرگز خطایی ایجاد نمیشود؛ انتخابی که به هیچ سبکی حل نمیشود، بدنه را بدون تغییر باقی میگذارد، به عنوان `no_styles` رد میشود)، دستورالعملهای انتخابشده را به ترتیب کاتالوگ به هم متصل میکند، بند مرزها را اضافه میکند.** یک بار** (به علاوه بند ایمنی، `SAFETY_BOUNDARIES` یا ترجمه آن، زمانی که `less-code` یا `ponytail` انتخاب شده است)، و بلوک را با یک نشانگر ناتوانی واحد (`[OmniRoute Output Styles]`) شروع میکند، بنابراین اعمال مجدد ممنوع است. هنگامی که زبان حل شده (به انتخاب زبان در زیر مراجعه کنید) ترجمه دارد، دستورالعمل محلی به جای انگلیسی تزریق می شود.

در بدنهای با آرایه `messages` غیر خالی، بررسی idempotency قبل از دور زدن محتوا اجرا میشود: زمانی که نشانگر `[OmniRoute Output Styles]` در فیلد `system` سطح بالا (رشته یا آرایه بلوک محتوا) یا در یک پیام سیستمی با محتوای رشته باشد، بدنه بدون تغییر بهعنوان `already_applied` باقی میماند و هیچ بررسی کلیدواژهای اجرا نمیشود. در غیر این صورت، یک دور زدن محتوا (`shouldBypassCavemanOutputMode()` در `open-sse/services/compression/outputMode.ts`) متن سه پیام آخر را، هر نقشی که باشد، بررسی میکند، و زمانی `deploy` متن با کلمات کلیدی امنیتی، عملکرد غیرقابل برگشت یا شفافسازی آن مطابقت `then`، یا یک توالی حساس به `delete` `before` متن سه پیام آخر `drop` بررسی میکند `migrate` `first` `after that` `rollback` `release` `backup` بای پس اجرا می شود در حالی که** بای پس شفافیت خودکار** toggle (`cavemanOutputMode.autoClarity`، به طور پیشفرض روشن) روشن است. با خاموش کردن کلید، بررسی کلیدواژه رد می شود.

هنگامی که بای پس به چرخش اجازه می دهد، `placeSystemInstruction()` (همان فایل)، که هرگز `messages[0]` جدیدی ایجاد نمی کند، بلوک را در اولین موردی که پیدا می کند قرار می دهد:

1. یک پیام سیستم اصلی با محتوای رشته: بلوک بعد از متن آن اضافه می شود.
2. فیلد `system` سطح بالا: بلوک بعد از متن یک رشته اضافه می شود یا به عنوان یک بلوک متن جدید به آرایه بلوک محتوا اضافه می شود.
3. اولین پیام سیستم بعدی با محتوای رشته: بلوک بعد از متن آن اضافه می شود.
4. هیچ یک از موارد بالا: بلوک به یک پیام سیستم جدید در انتهای `messages` می رود.

در بدنهای بدون آرایه `messages` (یا با آرایه خالی)، هیچ دور زدن محتوا اجرا نمیشود و از یک فیلد `system` سطح بالا استفاده نمیشود. بلوک بعد از متن رشته `instructions` اضافه می شود، مگر اینکه آن فیلد قبلاً حاوی نشانگر `[OmniRoute Output Styles]` باشد، در این صورت بدنه بدون تغییر به عنوان `already_applied` باقی می ماند. وقتی بدنه رشته `instructions` ندارد اما `input` (رشته یا آرایه) را حمل میکند، بلوک `instructions` میشود و جایگزین هر مقدار غیر رشتهای میشود که آن فیلد نگهداری میشود. بدنه ای که نه رشته `instructions` فیلد دارد و نه رشته یا آرایه `input` بدون تغییر باقی می ماند و به عنوان `no_messages` رد می شود.

#### نحوه فعال کردن

در داشبورد:** تنظیمات فشرده سازی متن →** (`/dashboard/context/settings`)، بخش سبک های خروجی: یک ردیف برای هر سبک با کلید on/off و انتخابگر سطح. هنگامی که فشردهسازی روشن است، سبکها تزریق میشوند (تغییر اصلی صفحه، `enabled`). را** بای پس شفافیت خودکار** ضامن روی است** غارنشین** صفحه (`/dashboard/context/caveman`)، در آن** حالت خروجی** کارت از نظر برنامهریزی، پیکربندی فشردهسازی انتخاب را به صورت زیر ادامه میدهد:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Back-compat: در حالی که `outputStyles` خالی است، تنظیم `cavemanOutputMode.enabled` قدیمی به `terse-prose` در `cavemanOutputMode.intensity` نگاشت می شود. سپس بلوک با نشانگر `[OmniRoute Output Styles]` شروع می شود، جایی که انژکتور قدیمی `applyCavemanOutputMode()` `[OmniRoute Caveman Output Mode]` را نوشته است. در زیر نشانگر، متن با تزریق میراث در en، pt-BR، es، de، fr، it، ru، id و vi مطابقت دارد. در ja و zh یک فضای اضافی قبل از بند مرزی دارد. `terse-prose` به pt-BR، es، de، fr، it، ru، zh، ja، id و vi ترجمه میشود، بنابراین درخواستی که زبان حلشده آن `hu` است، متن انگلیسی را دریافت میکند که در آن انژکتور قدیمی از مجارستانی خود استفاده کرده است.

انتخاب زبان به سبک خروجی (`resolveOutputStyleLanguage()` در `outputStyles/apply.ts`): با `languageConfig.enabled` روشن، `autoDetect` آخرین پیام کاربر را در آرایه `messages` درخواست که دارای متن است (محتوای رشته یا `text` قسمتهای محتوای آن) نمونهبرداری میکند و آشکارساز موتور غارنشین (`detectCompressionLanguage()`) را روی آن اجرا میکند. آشکارساز `zh` را برای متن با حروف هان و بدون کانا برمیگرداند. در غیر این صورت هر کدام از `it`، `pt-BR`، `es`، `de`، `fr`، `ru`، `ja`، `hu` و `id` بیشترین تطابقات را داشته باشد را برمیگرداند، و `en` زمانی که هیچ کدام با متن — مطابقت نداشته باشد، انگلیسی میشود، هرگز `defaultLanguage` نمیشود، و `vi` هرگز شناسایی نمیشود، اگرچه سبکهای `vi` را ارسال میکنند. یک بدنه Responses API چرخش خود را در `input` نگه میدارد، که نمونهبرداری نمیشود، بنابراین `defaultLanguage` و سپس انگلیسی میشود. وقتی هیچ پیام کاربری در `messages` متن ندارد، یا با `autoDetect` خاموش، `defaultLanguage` اعمال میشود، سپس انگلیسی. با خاموش کردن `languageConfig.enabled` ، زبان — انگلیسی است، مگر اینکه ترکیب فشردهسازی برای درخواست اعمال شود (یک ترکیب ترکیبی اختصاص داده شده به ترکیب مسیریابی درخواست، یا ترکیب فشرده فشردهسازی پیشفرض chatCore برای خط لوله پشتهای داخلی برمیگردد): اعمال یک ترکیب ترکیبی، `languageConfig.enabled` را برای آن درخواست روشن میکند و آن را تنظیم میکند (یکی از زبان `defaultLanguage` از مقدار ذخیره میکند). بسته های ترکیبی، در غیر این صورت اولین بسته ترکیبی، که پیش فرض `en` است، در حالی که `autoDetect` ذخیره شده (به طور پیش فرض روشن) همچنان اعمال می شود. موتور ورودی Caveman زبان بسته قانون خود را بهطور متفاوت — در هر قسمت متن انتخاب میکند و با تشخیص خودکار خاموش، در `enabledPacks` قرار میگیرد.

ماتریس زبان × با `tests/unit/compression/output-styles-i18n-matrix.test.ts` پین شده است: هر سبک کاتالوگ نیاز به یک ورودی در `BASELINE_LANGUAGES` آزمون دارد. سبکی که دارای دروازه محلی نیست باید یک ترجمه pt-BR ارسال کند ( `terse-cjk` دارای دروازه محلی از این قاعده مستثنی است) مگر اینکه در `KNOWN_ENGLISH_ONLY` فهرست شده باشد، که ممکن است فقط سبک هایی را داشته باشد که اصلاً ترجمه نداشته باشند — و یک سبک زمانی که زبانی را که ورودی `BASELINE_LANGUAGES` آن فهرست میکند از دست میدهد در آزمون مردود میشود. برای افزودن یک سبک، [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) را ببینید.

### فشرده سازی نتیجه ابزار

`compressToolResult()` در `open-sse/services/compression/toolResultCompressor.ts` متن نتیجه ابزار را با فشرده سازی می کند** 5 استراتژی** . آنها را به این ترتیب امتحان می کند، و اولین استراتژی فعال که بررسی آن با محتوا مطابقت دارد، نتیجه را تعیین می کند:

1. **`fileContent`** : محتوایی از 3 یا چند خط که در آن حداقل یک خط، بدون توجه به تورفتگی پیشرو، با `import `، `export `، `function `، `class `، `const `، `let `، `var ` یا `return ` (کلید واژه به اضافه یک فاصله) شروع میشود، یا با `if`، `for` یا `while` و به دنبال آن `(` یا ` (` اول باقی میماند. وسط مشخص شده
2. **`grepSearch`** : محتوای دارای حداقل یک خط از شکل `<path>:<digits>:`، که در آن متن قبل از دو نقطه اول فاقد فضای خالی است، فقط آن خطوط را حداکثر 30 نگه میدارد و به دنبال آن تعداد تطابقهای بیشتر و فهرست فایلهای مطابقت داده میشود. هر خط دیگر حذف می شود. یکی از این خطوط برای راه اندازی استراتژی کافی است، بنابراین یک خط ورود که با مهر زمانی مانند `12:30:45` شروع می شود نیز حساب می شود.
3. **`shellOutput`** : خروجی که حاوی یک دنباله ANSI CSI است (`ESC[` سپس ارقام یا نیم ویرگول و سپس یک حرف، مانند کدهای رنگی) یا یک `$` به دنبال فضای خالی در هر نقطه از متن، آن توالی ها را از دست می دهد (سایر فرارها، مانند `ESC[?25l` یا دنباله عنوان پنجره OSC ، نگه داشته می شوند) و خطوط برش آخر را با 5 حفظ می کند. از آنجایی که این بررسی قبل از `json` و `errorMessage` اجرا میشود، JSON یا خروجی خطایی که حاوی چنین `$` است هرگز در زمانی که `shellOutput` روشن است به آنها نمیرسد.
4. **`json`** : یک بار JSON بیش از 2000 کاراکتر که با `{` یا `[` شروع می شود (بعد از فضای سفید اختیاری) و تجزیه می شود خلاصه می شود: آرایه ای از بیش از 7 مورد، 5 مورد اول و 2 مورد آخر و تعداد کل آن را حفظ می کند، و یک شی 20 کلید اول خود را نگه می دارد، با طول هر شی تو در تو یا آرایه یک مقدار آرایه با `{…N keys}` جایگزین شده است. نشانگر `_remaining_<N>_keys` شمارش کلیدهایی که از 20 عدد اول گذشته است. مقادیر اسکالر به طور کامل کپی می شوند، بنابراین یک شی با 20 کلید یا کمتر بدون مقادیر تو در تو، فقط — فرورفته می شود.
5. **`errorMessage`** : خروجی که در هر جایی و در هر حروفی حاوی `error:`, `error ` (کلمه ای که با فاصله مانند `no error found`) دنبال می شود، `[error]`, `exception:`, `exception `, `[exception]` یا `traceback` است که اولین خط خود، 10 خط بعدی و 3 خط آخر را با یک نشانگر `… [N frames elided] …` به جای خطوط بین آنها حفظ می کند. نشانگر فقط زمانی ظاهر میشود که بیش از 13 خط از خط اول پیروی میکنند، بنابراین خروجی خطای 14 خط یا کمتر کوتاه نمیشود (در 12 یا 13 خط، 3 خط تکرار آخر قبلاً حفظ شدهاند).

پس از تطبیق یک استراتژی، حتی استراتژی که چیزی را ذخیره نمی کند، استراتژی های بعدی امتحان نمی شوند. وقتی استراتژی تطبیق هیچ توکن تخمینی ذخیره نمیکند (طول ÷ 4، گرد شده) — برای مثال یک فایل کد مانند از 25 خط یا کمتر، یا یک آرایه JSON بیش از 2000 کاراکتر با 7 آیتم یا — کمتر، موتور تهاجمی نتیجه ابزار اصلی را حفظ میکند: هر دو تماسگیرنده (`compressAggressive()` و `compressAnthropicToolResultBlock()` در زمانی که ثابت هستند، `saved` و `compressToolResult()` زیر هستند) خروجی آن استراتژی را برمی گرداند. مرحله ابزار-نتیجه آخرین کلمه نیست: خلاصهکننده بازگشتی موتور همچنان میتواند پیام `tool` یا `function` طولانیتر از 8192 کاراکتر را کوتاه کند (`maxTokensPerMessage`، 2048، ضربدر 4).

#### زمان استفاده

فشرده سازی نتیجه ابزار مرحله 1 موتور تهاجمی (`compressAggressive()` در `open-sse/services/compression/aggressive.ts`) است، بنابراین در حالت تهاجمی و در مرحله `aggressive` یک خط لوله انباشته اجرا می شود. پیامهای `tool` و `function` به شکل OpenAI و متن داخل بلوکهای Anthropic `tool_result` را فشرده میکند. هر استراتژی سوئیچ مخصوص به خود را تحت `aggressive.toolStrategies` دارد که همه به طور پیش فرض روشن هستند. در داشبورد، سوئیچ ها در صفحه Caveman قرار دارند** پیشرفته** مشاهده در حالی که فشرده سازی روشن است و حالت پیش فرض تهاجمی است.

### خط لوله انباشته

حالت انباشته اجرا می شود** چندین موتور به ترتیب** — معمولا ابتدا RTK (60-90٪ صرفه جویی در خروجی ابزار)، سپس Caveman در متن باقی مانده (~ 46٪ صرفه جویی در ورودی). تشکیل شده، که است** 78-95٪ محدوده واجد شرایط** (به ریاضی پس انداز بالادستی در بالا مراجعه کنید): `1 - (1 - 0.60..0.90) × (1 - 0.46)` میانگین ≈ 89٪ است.

#### چگونه کار می کند

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### زمان استفاده

از حالت انباشته برای موارد زیر استفاده کنید:

- گردش کار با ابزار سنگین (کدنویسی عاملی، تحقیق)
- پردازش دسته ای حساس به هزینه
- زمانی که به حداکثر پس انداز رمز نیاز دارید

خطوط لوله انباشته شده از طریق تنظیمات فشرده سازی جهانی `stackedPipeline` یا از طریق یک ترکیب فشرده سازی نامگذاری شده که به یک ترکیب مسیریابی اختصاص داده شده است (به گزینه Per-Combo Override در بالا مراجعه کنید) — می شوند و نه از طریق `modePack` ترکیبی خودکار (این فیلد فقط انتخاب مدل ترکیبی خودکار را دوباره وزن می کند و `stacked` نام بسته معتبری نیست).

## بازنویسیهای ترکیب برای فشردهسازی

میتوانید حالت سراسری فشردهسازی را **برای هر ترکیب** بازنویسی کنید تا رفتار آن را
برای کاربردهای مختلف بهدقت تنظیم کنید:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

این قابلیت برای موارد زیر مفید است:

- **ترکیبهای کدنویسی**: برای نشستهای طولانی از حالت `aggressive` استفاده کنید
- **ترکیبهای پرسشوپاسخ سریع**: برای پاسخهای سریع از حالت `lite` استفاده کنید
- **ترکیبهای متکی بر ابزار**: برای بیشترین صرفهجویی از حالت `stacked` استفاده کنید
- **ترکیبهای عملیاتی**: برای ارائهدهندگان دارای کش، بازنویسی را غیرفعال بگذارید — تنظیم همیشهفعال
  و آگاه از کش، حالتهای `aggressive`/`ultra` را بهطور خودکار به `standard` تنزل میدهد
  (حالت قابلانتخابی به نام `cache-aware` وجود ندارد)
