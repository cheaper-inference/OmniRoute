از این راهنما برای انتخاب کوچکترین چرخهٔ توسعهٔ قابلاعتماد برای یک pull request استفاده کنید. این راهنما
جایگزین اسناد معماری و امنیت مختص هر حوزه که در ادامه پیوند داده شدهاند نیست؛ بلکه هر نوع تغییر رایج را
به قراردادها، بررسیهای متمرکز و پوشش CI مربوط به آن متصل میکند.

## مسیری که هر تغییر طی میکند

1. **پیش از ویرایش، شاخهٔ مبنا را انتخاب کنید.** بالاترین شاخهٔ فعال `release/v*` را پیدا کنید و شاخهٔ خود را از
   نوک آن بسازید. همان شاخه را هدف قرار دهید، نه `main`. اگر توقف انتشار فعال است، شاخهٔ متوقفشده را
   هدف قرار ندهید؛ از چرخهٔ فعال بعدی که در
   [مدل شاخهبندی و انتشار](BRANCHING_MODEL.md) توضیح داده شده است استفاده کنید.
2. **قراردادها را مشخص کنید.** هر کاتالوگ، schema، artifact تولیدشده، API عمومی یا رابط کاربریای را که
   تغییر تحت تأثیر قرار میدهد شناسایی کنید. جدول زیر حداقل مجموعهٔ شروع را ارائه میکند.
3. **تستهای متمرکز را بنویسید یا بهروزرسانی کنید.** تغییرات محیط production در `src/`، `open-sse/`، `electron/` یا
   `bin/` به یک تست خودکار در همان PR نیاز دارند. ابتدا کوچکترین فایلهای تستی را که رفتار را
   اثبات میکنند اجرا کنید و سپس gateهای متمرکز فهرستشده را اجرا کنید.
4. **اجازه دهید CI ماتریس گسترده را اجرا کند.** همهٔ shardهای unit، Vitest، ratchet پوشش و
   build محیط production روی PR اجرا میشوند. یک suite گسترده را فقط زمانی بهصورت محلی اجرا کنید که یک failure متمرکز به
   تأثیر گستردهتر اشاره کند یا تغییر چندین زیرسیستم را دربر بگیرد.
5. **پیش از بازبینی، تغییرات را همگام کنید.** شاخهٔ مبنای فعال را fetch کنید، commitهای جدید آن و diff خود را نسبت به
   آن بررسی کنید، سپس مطابق workflow مشارکتکنندگان، شاخهٔ مبنا را rebase یا merge کنید. تعارضهای فایلهای تولیدشده
   و کاتالوگ را از منبع آنها رفع کنید، دوباره آنها را تولید کنید، چرخهٔ متمرکز را مجدداً اجرا کنید و تأیید کنید که
   PR همچنان شاخهٔ انتشار فعال را هدف قرار میدهد.
6. **شواهد را ثبت کنید.** در قالب PR، فرمانهای اجراشده، همهٔ فایلهای تست افزودهشده یا تغییریافته،
   migrationها یا feature flagها و هر اعتبارسنجی مختص CI را که هنوز در انتظار است فهرست کنید.

## مسیرهای طلایی بر اساس نوع تغییر

فرمانهای زیر حداقل بررسیهای متمرکز هستند، نه مجوزی برای نادیده گرفتن تستی که مستقیماً رفتار
تغییریافته را پوشش میدهد.

### Provider

**قراردادها**

- تعریف Provider در `src/shared/constants/providers/` و ترکیب آن در
  `src/shared/constants/providers.ts`.
- مدلها و قابلیتها در `open-sse/config/providerRegistry.ts` یا فایلهای registry استخراجشدهٔ آن.
- انتخاب Executor/translator، پیکربندی OAuth یا API key، assetهای dashboard و مرجع تولیدشدهٔ
  Provider، در صورت کاربرد.
- credentialهای عمومی باید از `resolvePublicCred()` استفاده کنند؛ پاسخهای خطا باید از helperهای مشترک
  پاکسازی خطا استفاده کنند. به `docs/security/PUBLIC_CREDS.md` (در git؛ در `/docs` کامپایل نمیشود) و
  [پاکسازی خطا](../security/ERROR_SANITIZATION.md) مراجعه کنید.

**چرخهٔ متمرکز**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # هنگام تغییر کاتالوگ؛ diff تولیدشده را commit کنید
npm run lint
```

همهٔ خانوادههای request تحت تأثیر را نیز تست کنید: chat، Responses، images، embeddings، audio یا video.
diffهای کاتالوگ تولیدشده و golden را بهعنوان تغییرات قرارداد بازبینی کنید؛ آنها را بدون بررسی نپذیرید.

### Routing

**قراردادها**

- مقادیر عمومی strategy و metadata رابط کاربری در `src/shared/constants/routingStrategies.ts`.
- dispatch و ترتیبدهی در `open-sse/services/combo.ts` و `open-sse/services/combo/`.
- schemaهای Combo، persistence، وضعیت resilience، قابلیتهای مدل و کنترلهای API/UI.
- [موتور Auto-Combo](../routing/AUTO-COMBO.md) و مستندات resilience، هنگامی که رفتار تغییر میکند.

**چرخهٔ متمرکز**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # تغییرات strategy یا dispatch
npm run check:known-symbols      # تغییرات ثبت strategy
npm run lint
```

بهصورت محلی از تستهای deterministic با upstream شبیهسازیشده استفاده کنید. تستهای smoke زندهٔ Combo به credential نیاز دارند و
دستی هستند؛ آنها جایگزین CI نیستند.

### UI / UX

**قراردادها**

- route/page مربوط به Next.js و مرزهای componentهای مشترک در `src/app/` و
  `src/shared/components/`.
- شکل پاسخهای API، وضعیتهای loading/empty/error، رفتار صفحهکلید و screen reader،
  layout واکنشگرا، theming و گسترش locale.
- رشتههای مبدأ انگلیسی رابط کاربری در `src/i18n/messages/en.json`؛ متن جدیدِ قابلمشاهده برای کاربر را hard-code نکنید.

**چرخهٔ متمرکز**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

برای تغییرات تعاملی یا بصری، برنامه را اجرا کنید و viewportهای باریک و عریض را بررسی کنید. CI
build محیط production و suiteهای گستردهتر را اجرا میکند؛ رفتار بصری همچنان به یک component متمرکز، Playwright،
یا بررسی دستی مستندشده و متناسب با تغییر نیاز دارد.

### i18n

**قراردادها**

- `src/i18n/messages/en.json` منبع رابط کاربری است؛ `config/i18n.json` منبع locale است.
- کاتالوگهای CLI بهصورت جداگانه در `bin/cli/locales/` قرار دارند.
- placeholderها و tagهای ICU را دقیقاً حفظ کنید. نام محصولات/Providerها/مدلها،
  نام protocolها و headerها، فرمانها، شناسههای code/JSON، URLها، environment variableها یا
  اصطلاحات محافظتشدهای مانند `OmniRoute`، `OAuth`، `MCP` و `A2A` را ترجمه نکنید. فهرست مبدأ فعلی
  `scripts/i18n/glossary/protected-terms.json` است.

**چرخهٔ متمرکز**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # هنگامی که رشتهها/کاتالوگهای CLI تغییر میکنند
npm run lint
```

این راهنمایی برای سیستم موجود است، نه دعوتی برای گسترش tooling یا مدل key آن.
تا زمانی که سیستم جایگزین در حال طراحی است، patchهای i18n را محدود و دقیق نگه دارید. فرمانهای ترجمهای را که
سرویسهای خارجی را فراخوانی میکنند اجرا نکنید، مگر اینکه task صراحتاً به ترجمههای تولیدشده نیاز داشته باشد و
diff حاصل را بازبینی کرده باشید.

### CLI

**قراردادها**

- دستورات عمومی و فلگها در `bin/cli/`، دستورات API تولیدشده، کدهای خروج، stdout/stderr و
  ساختار خروجی JSON، رفتار پیکربندی/محیط و فایلهای بستهبندیشده.
- رشتههای قابلمشاهده برای کاربران CLI باید از لایه i18n در CLI استفاده کنند و کاتالوگهای `en`/`pt-BR` را همگام نگه دارند.
- Node را بهعنوان محیط اجرای پشتیبانیشده و قرارداد باینری منتشرشده حفظ کنید.

**چرخه متمرکز**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تغییرات CLI تولیدشده/باندلشده
npm run check:pack-policy     # تغییرات سطح بسته
npm run lint
```

هنگامی که رفتار به تجزیه، فایلها یا وضعیت خروج وابسته است، دستور دقیق را در یک پوشه داده موقت اجرا کنید.
CI بررسیهای گستردهتر مصنوعات بسته و اکوسیستم را انجام میدهد.

### پایگاه داده

**قراردادها**

- ماژولهای دامنه در `src/lib/db/`؛ ماژولهای مشخص را مستقیماً import کنید (لایه قدیمی re-export در `localDb.ts` حذف شده است).
- migrationهای SQL شمارهگذاریشده و idempotent در `src/lib/db/migrations/`، ایمنی تراکنش، رفتار
  ارتقا، ایندکسها و تمام فراخوانهایی که تحت تأثیر schema قرار میگیرند.
- routeها و handlerها هرگز نباید مستقیماً SQL خام اجرا کنند.

**چرخه متمرکز**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

هنگام افزودن یک migration، هم یک پایگاه داده تازه و هم ارتقا از schema قبلی را آزمایش کنید. تستهای پایگاه داده
باید handleها را ببندند و هنگام پاکسازی `resetDbInstance()` را فراخوانی کنند. فقط زمانی `npm run test:bun:db` را اجرا کنید که
مسیر آداپتور Bun با پشتیبانی best-effort تغییر کرده باشد؛ Node همچنان مرجع اصلی است.

### ساخت / استقرار

**قراردادها**

- manifestها/lockfile ریشه و workspace، `scripts/build/`، مونتاژ standalone در Next.js، محتوای بسته
  `dist/`، metadata پلتفرم Electron، workflowهای CI و sentinelهای استقرار.
- بازههای پشتیبانیشده Node و استفاده allow-listed از Bun در `CLAUDE.md` باید دستنخورده باقی بمانند.
- مصنوعات ساخت نباید track شوند؛ سیاستهای وابستگی، مجوز، workflow و بسته اعمال میشوند.

**چرخه متمرکز**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # تغییرات وابستگی یا lockfile
npm run check:pack-policy      # تغییرات سطح بسته منتشرشده
npm run lint
```

فقط زمانی `npm run build` را بهصورت محلی اجرا کنید که تغییر بر کامپایل، مونتاژ standalone، assetها
یا باندلسازی زمان اجرا اثر بگذارد. از `npm run build:release` فقط برای اعتبارسنجی انتشار/استقرار استفاده کنید. ساخت CI
سیگنال نهایی میانپلتفرمی است؛ تغییرات مختص پلتفرم Electron به ساخت متمرکز متناظر
یا شواهد smoke نیاز دارند.

## اسکریپتهای توسعهدهنده برای یک ماشین اشتراکی

دو ابزار کمکی در `scripts/dev/` چرخهٔ محلی را روی یک devbox که نشستهای دیگری نیز روی آن فعالاند، پیادهسازی میکنند:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # فایلهای merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # دقیقاً همین فایلها
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # worktree ایزوله، امن برای اجرای موازی
```

- `typecheck-touched.sh` فقط فایلهای `.ts/.tsx` تغییریافته را از طریق یک
  `tsconfig.touched.tmp.json` موقت (`extends ./tsconfig.json`،‏ `types: ["node"]`،‏ `noEmit`،
  `incremental: false`) و با heap معادل 6 GB بررسی نوع میکند؛ بنابراین جایگزین
  `tsc -p tsconfig.json` در سطح کل پروژه میشود که روی یک ماشین پربار با کمبود حافظه مواجه میشود.
  این اسکریپت خطاهای فایلهای تغییریافته را بههمراه یک خط خلاصه چاپ میکند و در صورت وجود خطا در
  فایلهای تغییریافته با کد `1`، هنگامی که تنها خطاها در فایلهای importشده باشند یا tsc بدون
  diagnostics متوقف شده باشد با کد `2` (لاگی را که در مسیر `_artifacts/typecheck-touched/` نام
  میبرد بخوانید) و در صورت نبود خطا با کد `0` خارج میشود. tsconfig موقت همیشه حذف میشود؛ هرگز
  چنین فایلی را commit نکنید.
- `new-worktree.sh` اجراهای همزمان را با قفل `<git-common-dir>/omniroute-new-worktree.lock`
  بهصورت ترتیبی اجرا میکند (بهطور پیشفرض تا 600 s منتظر میماند و پیامی قابلمشاهده نمایش
  میدهد؛ هدر اسکریپت نحوهٔ override کردن آن را مستند کرده است) و اگر `git worktree add` پیش از
  ایجاد worktree شکست بخورد، branch ایجادشده را برمیگرداند؛ بنابراین تلاش مجدد به اجرای دستی
  `git branch -D` نیاز ندارد. `node_modules` با hard link و کپی `.husky/_` بدون تغییر باقی
  میمانند.

## چرخهٔ محلی candidate

آزمونهای سورس نمیتوانند ثابت کنند که artifact بستهبندیشده راهاندازی میشود: فهرستهای
بستهبندی، dependencyهای حذفشده و binaryهای native فقط پس از نصب و اجرای tarball دچار خطا
میشوند. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) بخش محلی جریان
build-once / validate / promote از RFC #8084 است: یک candidate را build میکند، دقیقاً همان
artifact را اعتبارسنجی میکند، با تغییر نام directoryها آن را promote میکند و اگر slot
promoteشده در health check ناموفق باشد، آن را roll back میکند.

```bash
npm run dev:candidate -- run --dry-run --json  # plan را چاپ کن، چیزی را تغییر نده
npm run dev:candidate -- run                   # build + validate + promote، با rollback خودکار
npm run dev:candidate -- build                 # npm pack + نصب در _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # راهاندازی روی یک port آزاد، /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current، current → previous
npm run dev:candidate -- rollback              # جابهجایی current و previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # استفادهٔ مجدد از tarball ساختهشده در جایی دیگر (CI)
```

- **یکبار build کنید.** `build` درخت فعلی را pack میکند (به `dist/server.js` نیاز دارد، پس ابتدا
  `npm run build:release` را اجرا کنید) یا `--from-tarball` را کپی میکند، سپس tarball را در یک
  npm prefix ایزوله نصب میکند، زیرا tarball شامل `node_modules` نیست. شناسه، sha کوتاه `HEAD`
  است (`-dirty` هنگامی که درخت تغییرات محلی دارد) یا برای یک tarball برابر با `tgz-<sha256>`
  است. یک شناسهٔ clean که قبلاً build شده باشد، بهجای build مجدد دوباره استفاده میشود؛ برای
  build مجدد آن، `--force` را ارسال کنید.
- **بسته را اعتبارسنجی کنید، نه سورس را.** `validate`، CLI نصبشده
  (`serve --port <free port>`) را با یک `DATA_DIR=<candidate>/data` تازه، secretهای جعلی و با حذف
  `OMNIROUTE_API_KEY`،‏ `STORAGE_ENCRYPTION_KEY` و `INITIAL_PASSWORD` متعلق به operator از
  environment اجرا میکند تا وضعیت keyless loopback یک نصب تازه را بررسی کند. این فرمان منتظر
  میماند تا `GET /api/health` مقدار 200 را برگرداند، الزام میکند که `GET /v1/models` نیز مقدار
  200 را برگرداند، process group را متوقف میکند و نتیجه را همراه با hash مربوط به tarball در
  `validation.json` ثبت میکند.
- **همان artifact را promote کنید.** `promote` از پذیرش candidateای که برای hash فعلی tarball خود
  اعتبارسنجی موفقی ندارد، خودداری میکند. slot فعال پیشفرض `_artifacts/candidate/current` است؛
  `--target <dir>` یک directory دیگر روی همان filesystem را انتخاب میکند و slot قبلی آن
  `<dir>.previous` است. هر تغییر نام atomic است و اگر در میانهٔ عملیات خطایی رخ دهد، تغییر
  نامهایی که پیشتر انجام شدهاند معکوس میشوند.
- **Roll back کنید.** `run`، slot promoteشده را دوباره اعتبارسنجی میکند و اگر آن بررسی ناموفق
  باشد، `current` و `previous` را دوباره جابهجا میکند. candidateای که در اعتبارسنجی اول ناموفق
  باشد، هرگز promote نمیشود.

همهچیز در مسیر gitignored یعنی `_artifacts/candidate/` نوشته میشود؛ نصب موجود OmniRoute و
directory دادهٔ آن هرگز تغییر نمیکنند. CLI promoteشده در
`_artifacts/candidate/current/prefix/bin/omniroute` قرار دارد؛ هنگام استفاده، آن را با
`DATA_DIR` خودتان راهاندازی کنید. کدهای خروج: `0` برای موفقیت، `1` برای اعتبارسنجی یا promotion
ناموفق و `2` برای خطای نحوهٔ استفاده یا build مفقود.

## چرخهٔ محلی در برابر CI

| برای هر وصله بهصورت محلی اجرا کنید                                              | CI سیگنال گسترده را فراهم میکند                                           |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| آزمونهای مستقیم رفتار و دروازههای دستهبندی بالا                                 | مجموعهٔ کامل آزمونهای واحد بهصورت تقسیمشده و آزمونهای ترتیبی              |
| `npm run lint`                                                                  | مجموعهآزمونهای Vitest و سازوکارهای افزایش تدریجی پوشش/کیفیت               |
| بررسی نوعها یا ساخت، فقط زمانی که قرارداد تحت تأثیر آن را ایجاب میکند           | ساخت نسخهٔ عملیاتی، امنیت، مستندات، وابستگیها و دروازههای خطمشی PR        |
| بررسیهای تعاملی/زندهٔ دستی، فقط زمانی که خودکارسازی نمیتواند رفتار را اثبات کند | بررسیهای یکپارچهسازی میان jobها و پلتفرم که توسط workflow پیکربندی شدهاند |

سبز بودن چرخهٔ متمرکز، شاهدی دربارهٔ قرارداد تغییریافته است، نه اثباتی بر اینکه بررسیهای نامرتبط CI
با موفقیت عبور خواهند کرد. از سوی دیگر، برای هر ویرایش محلی منتظر اجرای ماتریس کامل مخزن نمانید.

## چکلیست تطبیق

پیش از درخواست بازبینی:

- تأیید کنید که پایهٔ PR همچنان بالاترین شاخهٔ فعال `release/v*` است.
- آن پایه را واکشی کنید و commitهایی را که از زمان ایجاد شاخهٔ شما ادغام شدهاند، بازبینی کنید.
- برای یافتن تغییرات ناخواسته یا تولیدشده، `git diff <active-base>...HEAD` را بازبینی کنید.
- تعارضهای کاتالوگ و سندهای تولیدشده را با بهروزرسانی منبع و تولید مجدد خروجی برطرف کنید.
- پس از تطبیق، همهٔ آزمونها/دروازههای متمرکز فهرستشده در توضیحات PR را دوباره اجرا کنید.
- هرگز صرفاً برای انطباق با پایهای که جابهجا شده است، assertionها را تضعیف نکنید یا آزمونهای الزامی را حذف نکنید.

برای قوانین توقف انتشار و هدفگذاری مجدد، از
[مدل شاخهبندی و انتشار](BRANCHING_MODEL.md) استفاده کنید. برای فهرست کامل CI، از
[مرجع دروازههای کیفیت](../architecture/QUALITY_GATES.md) استفاده کنید.
