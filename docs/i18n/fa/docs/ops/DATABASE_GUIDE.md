## چرا SQLite؟

OmniRoute به دلایل مختلفی SQLite را به PostgreSQL/MySQL ترجیح داده است:

| عامل             | SQLite                                | PostgreSQL                           |
| ---------------- | ------------------------------------- | ------------------------------------ |
| **استقرار**      | توکار — بدون نیاز به سرور جداگانه     | نیازمند راهاندازی سرور               |
| **رمزنگاری**     | لایه برنامه (AES-256-GCM)             | TDE داخلی                            |
| **عملکرد**       | سریعتر برای بارهای کاری کوچک/متوسط    | بهتر برای نوشتنهای همزمان بسیار حجیم |
| **همزمانی**      | حالت WAL امکان خواندن همزمان را میدهد | MVCC کامل                            |
| **پشتیبانگیری**  | کپی یک فایل                           | `pg_dump` یا اسنپشات فایلسیستم       |
| **مورد استفاده** | نصب برای هر کاربر، توکار              | SaaS چندمستاجری                      |

برای استقرارهای **تککاربره و تکنمونهای** (مورد استفاده اصلی OmniRoute)، SQLite سادهتر و سریعتر است.

### ژورنالنویسی WAL

`core.ts` پایگاه داده را در **حالت WAL (ثبت پیشاپیش نوشتن)** باز میکند:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL امکان **خواندن همزمان** حین نوشتن را فراهم میکند — قابلیتی مهم برای داشبورد که همزمان با ثبت درخواستها، کوئری اجرا میکند.

اندازه پیشفرض کش **۶۵٬۵۳۶ KiB (۶۴ MiB)** است. SQLite مقدار منفی
`cache_size` را بهعنوان یک حد بالای تقریبی بر حسب KiB تفسیر میکند و صفحهها را در صورت نیاز تخصیص میدهد.
بخش **تنظیمات > سیستم و فضای ذخیرهسازی > اندازه کش** مقادیر صحیح بین **۱ تا
۱٬۰۰۰٬۰۰۰ KiB** را میپذیرد؛ ذخیره تنظیمات، آن را روی اتصال فعال پایگاه داده اعمال میکند
و OmniRoute مقدار ذخیرهشده را هنگام راهاندازی بازیابی میکند.

## محل پایگاه داده

فایل SQLite در مسیر زیر ذخیره میشود:

| سیستمعامل | مسیر                                                          |
| --------- | ------------------------------------------------------------- |
| Linux     | `~/.omniroute/storage.sqlite`                                 |
| macOS     | `~/.omniroute/storage.sqlite`                                 |
| Windows   | `%USERPROFILE%\.omniroute\storage.sqlite`                     |
| Docker    | `/app/data/storage.sqlite` (قابل پیکربندی از طریق `DATA_DIR`) |

فایلهای همراه:

- `storage.sqlite-wal` — گزارش ثبت پیشاپیش نوشتن
- `storage.sqlite-shm` — فایل حافظه اشتراکی
- `call_logs/` — مصنوعات محتوای درخواست (در صورت فعال بودن)

**بازنویسی محل ذخیرهسازی:**

```bash
DATA_DIR=/custom/path omniroute
```

### مرزهای ماژولها

یک قاعده معماری اصلی: **ماژولها مستقیماً به جداول یکدیگر دسترسی ندارند**. برای کار با دادههای ماژولی دیگر، تابع موردنظر را از همان ماژول import کنید.

```ts
// ❌ نادرست: اجرای مستقیم SQL از ماژولی دیگر
db.prepare("SELECT * FROM provider_connections").all();

// ✅ درست: استفاده از تابع ماژول providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

این قاعده از طریق بازبینی کد اعمال میشود — هیچ بررسی ایستاییای وجود ندارد، اما تخلفها علامتگذاری میشوند.

## مهاجرت ها

OmniRoute استفاده می کند** مهاجرتهای نسخهای و بیتوان** در `src/lib/db/migrations/`. هر مهاجرت یک فایل SQL است. دو قالب نامگذاری با هم وجود دارند. نسخه ثبت شده در `_omniroute_migrations` پیشوند عددی است.

### نامگذاری مهاجرت

| قالب                                           | مثال                                 | استفاده شده برای                                                                                                                                          |
| ---------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (دقیقا 3 رقمی)           | `241_seen_models.sql`                | سریال قدیمی `001`–`241`. هنگامی که قالب مهر زمانی فرود آمد ثابت شد (`240` و `241` درست قبل از آن ادغام شدند): هیچ فایل جدیدی شماره ترتیبی دریافت نمی کند. |
| `YYYYMMDDHHMMSS_description.sql` (14 رقم، UTC) | `20261113120000_add_usage_index.sql` | هر مهاجرت ایجاد شده از 2026-11-13 به بعد.                                                                                                                 |

چرا تغییر: با اعداد متوالی، PRs موازی همان عدد بعدی را انتخاب کرد و همه به جز یک باید قبل از ادغام مجدد شماره گذاری می شدند. یک مهر زمانی UTC به هر PR نسخه خاص خود را می دهد.

قوانین مربوط به قالب مهر زمانی (اجرا شده توسط `npm run check:migration-numbering`، به اشتراک گذاشته شده با ژنراتور در `scripts/check/lib/migrationNaming.mjs`):

- مهر زمانی یک تاریخ و زمان واقعی UTC است، نه زودتر از `20261113000000` و نه بیشتر از 10 دقیقه در آینده.
- توضیحات به صورت حروف کوچک `snake_case` است که با یک حرف (`a-z`، `0-9`، تک `_` بین کلمات) شروع می شود، حداکثر 80 کاراکتر.
- دو فایل با مهر زمانی یکسان تکراری هستند.
- قانون بدون شکاف فقط برای سری های قدیمی اعمال می شود: هر عدد از `001` تا `241` باید وجود داشته باشد، به جز شکاف های شناخته شده `026`، `055` و `121`. حذف `241` (یا هر فایل قدیمی) گیت را با شکست مواجه می کند. `001` و `241` هرگز نمی توانند به لیست مجاز `KNOWN_GAPS` اضافه شوند. فایل های دارای مهر زمانی هرگز شکاف ایجاد نمی کنند.
- هر ورودی در `src/lib/db/migrations/` باید یک فایل معمولی با نام `.sql` با حروف کوچک معتبر باشد. یک دایرکتوری، یک پیوند نمادین، یک فایل `.SQL` یا `.sql.bak` ، یک فایل مخفی یا یک نام با فاصله، گیت را از کار می اندازد، زیرا رانر آن را بی صدا رد می کند یا در هنگام بوت خراب می شود.

**سفارش را اعمال کنید.** رانر بر اساس مقدار عددی پیشوند مرتب میکند، نه بر اساس متن: ابتدا فایلهای قدیمی `001`–`241` ، سپس فایلهای مهر زمانی به ترتیب مهر زمانی، سپس هر فهرست راهنما با فضای نام ثبت شده با `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (نسخههایی مانند `ee-001`). یک مهاجرت در انتظار هر فایلی است که نسخه آن در `_omniroute_migrations` نیست، بنابراین مهاجرت از یک شاخه قدیمی که پس از یک شاخه جدید ادغام می شود، همچنان در پایگاه داده های موجود اعمال می شود.

**مهر زمانی دستور ایجاد است، نه ترتیب ادغام.** اگر مهاجرت شما به جدول یا ستون ایجاد شده توسط یک مهاجرت با a بستگی دارد** جدیدتر** مهر زمانی (به عنوان مثال، یکی از PR دیگری که ابتدا ادغام شد)، یک پایگاه داده جدید ابتدا پایگاه داده شما را اجرا می کند و از کار می افتد. در حالی که PR شما هنوز باز است، نام فایل را با `npm run db:new-migration` بازسازی کنید تا مهر زمانی جدیدتری دریافت کند یا آن را مستقل کنید. `npm run test:migrations:fresh` هر مهاجرت را به یک پایگاه داده خالی اعمال می کند و این را می گیرد.

### یک مهاجرت ادغام شده هرگز حذف یا تغییر نام نمی یابد

هنگامی که یک فایل مهاجرت در یک شاخه انتشار یا `main` قرار گرفت، قبلاً روی پایگاههای داده همولوگ و توسعهدهنده، در نصبهای VPS و در همگامسازی Enterprise اجرا شده است. از آن به بعد:

- **هرگز آن را حذف نکنید.** نصب های تازه طرحواره خود را از دست می دهند در حالی که پایگاه داده های ارتقا یافته آن را حفظ می کنند.
- **هرگز نام آن را تغییر ندهید.** نسخه موجود در `_omniroute_migrations` دیگر با یک فایل مطابقت ندارد، بنابراین هر پایگاه داده ای که قبلاً آن را اعمال کرده است، دوباره آن را اجرا می کند. SQL غیر idempotent سپس داده ها را کپی می کند یا بوت را متوقف می کند.
- **به یک طرح واره متفاوت نیاز دارید؟** یک مهاجرت جدید با `npm run db:new-migration` ایجاد کنید.

تغییر نام فقط برای فایلی ایمن است که هنوز ادغام نشده است، این موردی است که نکات گیت به آن اشاره دارد. یک تگ انتشار در اینجا چیزی را تغییر نمیدهد: هر فشار به یک شاخه `release/v*` تصویر Docker `:next` را منتشر میکند و روی homolog، نصب VPS و همگامسازی Enterprise اجرا میشود، بنابراین یک مهاجرت ادغامشده در پایگاههای داده واقعی قبل از وجود هر تگ `vX.Y.Z` اجرا شده است. گیت در هر حذف یک فایل پایه، برچسب گذاری شده یا نشده، با شکست مواجه می شود.

- **برگرداندن یک مهاجرت ادغام شده** `git revert` که فایل را حذف می کند، گیت را از کار می اندازد. فایل را نگه دارید و طرح آن را در یک مهاجرت جدید لغو کنید: `npm run db:new-migration -- <description>`، با `DROP TABLE IF EXISTS`، `DROP INDEX IF EXISTS` و غیره. پایگاه داده های ارتقا یافته و جدید سپس با همان طرح پایان می یابند.
- **تغییر نام پذیرفته شده: ورودی سازگاری و محتوای یکسان.** اگر یک فایل ادغام شده باید جابجا شود (به عنوان مثال، دو فایل ادغام شده یک مهر زمانی به اشتراک می گذارند و اجرا کننده با برخورد نسخه متوقف می شود)، نام فایل بعدی را بدون لمس SQL تغییر دهید و `{ fromVersion, fromName, toVersion, toName }` را به `RENAMED_MIGRATION_COMPATIBILITY` در `src/lib/db/migrationRunner/constants.ts` اضافه کنید. پایگاههای دادهای که نسخه قدیمی را اعمال کردهاند، به جای اجرای مجدد فایل، ردیف `_omniroute_migrations` خود را جابهجا میکنند. گیت در مورد چنین تغییر نامی هشدار میدهد و همیشه بررسی کموتاسیون را روی آن اجرا میکند، صرف نظر از مهر زمانی جدید: نصبهای تازه فایل را در موقعیت جدیدش اعمال میکنند، پایگاههای داده ارتقایافته این کار را نمیکنند، بنابراین یک مهر زمانی جدید نزدیک به مهر زمانی قدیمی انتخاب کنید. اگر محتوا تغییر کند (تغییر طرحواره همچنان در انتقال جدید انجام می شود)، یا اگر فایل هدف ورودی روی دیسک نباشد، گیت در تغییر نام ناموفق است.
- **هرگز در همان مُهر زمانی تغییر نام ندهید.** تغییر نامی که مُهر زمانی را نگه میدارد و فقط توضیحات را تغییر میدهد، با یا بدون ورودی، دروازه را از بین میبرد. با ورودی که `toVersion` برابر `fromVersion` آن است، رانر ردیف قدیمی `_omniroute_migrations` را حذف میکند و فایل را دوباره در هر پایگاه دادهای که قبلاً آن را اجرا کرده است اعمال میکند. بدون ورودی، رانر فقط نسخه را ردیابی میکند: فایل را در آن پایگاههای داده پرش میکند (محتوای جدید هرگز در آنجا اجرا نمیشود) و یک خطای شمارهگذاری مجدد را در هر بوت ثبت میکند. از مهر زمانی دیگر به اضافه ورودی سازگاری استفاده کنید یا نام را نگه دارید.
- **گیت بررسی می کند که فایل تغییر نام یافته دوباره اجرا نشود.** برای هر تغییر نام پوشانده شده، گیت نام فایل جدید را با `--must-not-apply` به بررسی کموتاسیون ارسال می کند. چک پایگاه داده ارتقا یافته را با runner واقعی بوت میکند، و اگر رانر دوباره آن فایل را اعمال کند (مثلاً چون ورودی نسخه یا نام اشتباهی دارد، یا به دلیل اینکه تجزیهکننده متن گیت `constants.ts` با TypeScript متفاوت میخواند)، گیت با `migration renomeada rodaria de novo` خراب میشود و از شما میخواهد که نسخهها و نامهای ورودی قدیمی و جدید را بررسی کنید.

### آنچه که گیت در مقابل پایگاه بررسی می کند

در درخواست کشش و اجرای صف ادغام، `npm run check:migration-numbering` `src/lib/db/migrations/` روی دیسک با همان فهرست در شاخه پایه مقایسه می کند. پایه به این ترتیب است: `--base-latest-tag`، `--base <ref>`، متغیر `MIGRATION_BASE_REF` ، یا، زمانی که `GITHUB_EVENT_NAME` `pull_request` است، `pull_request_target` یا `merge_group`، اولین والد تعهد ادغام، `merge_group.base_sha` محموله رویداد یا `git merge-base HEAD origin/$GITHUB_BASE_REF` است. در یک درخواست کشش یا اجرای صف ادغام بدون پایه قابل حل، گیت با شکست مواجه می شود. در خارج از CI بدون `--base` `comparação com a base: pulada (sem --base)` را چاپ می کند و از این قوانین صرف نظر می کند.

`--base-latest-tag` با جدیدترین تگ انتشار (`vX.Y.Z` به ترتیب semver؛ برچسبهای پسوندی مانند شبانهها به حساب نمیآیند) که در تاریخ `HEAD` وجود دارد، با همان قوانین `--base` مقایسه میشود. Release-Green (`scripts/quality/validate-release-green.mjs`) گیت را به این صورت اجرا میکند، زیرا اجراهای فشاری و برنامهریزیشده پایه درخواست کشش ندارند و ادغام میتواند بدون اجرای CI جدید فرود بیاید. بدون هیچ برچسب انتشار در تاریخ، دروازه با شکست مواجه می شود. `git fetch --tags` را اجرا کنید (در CI، `actions/checkout` با `fetch-depth: 0` تگ ها را می آورد).

یک اجرای بررسی کموتاسیون فایل های خارج از نظم، ویرایش شده و تغییر نام را با هم پوشش می دهد.

چک کموتاسیون (`scripts/check/migration-commutation.ts`) دو پایگاه داده موقت با مسیر نصب واقعی می سازد: an** ارتقا یافته است** یک (با مهاجرت های پایه بوت شود، سپس دوباره روی همان فایل با مهاجرت های درخواست کشش بوت شود) و یک** تازه** یک (یک بوت با مهاجرت های درخواست کشش). این طرحوارههای حاصل را مقایسه میکند: جداول و ستونها (نادیده گرفتن ترتیب ستون)، محدودیتهای UNIQUE / PRIMARY KEY و FOREIGN KEY ، متن `CREATE TABLE` نرمال شده هر جدول (که محدودیتهای CHECK ، تلفیقی، ستونهای تولید شده و گزینههای جدول را پوشش میدهد)، فهرستها، محرکها و نماها. داده های ردیف مقایسه نمی شوند. اگر مطابقت داشته باشند، دروازه چاپ می کند که فایل از کار افتاده است اما رفت و آمد می کند، و عبور می کند. اگر آنها متفاوت باشند، گیت با تفاوت و یک اشاره برای مورد از کار می افتد: برای یک فایل خارج از نظم، نام آن را با `npm run db:new-migration` بازسازی کنید، که امن است زیرا فایل هنوز ادغام نشده است. برای یک فایل پایه ویرایش شده، محتوای پایه را بازیابی کنید و تغییر را در یک مهاجرت جدید قرار دهید. برای یک فایل تغییر نام یافته، تغییر نام را لغو کنید یا مُهر زمانی جدید دیگری را در جایی که رفت و آمد می کند انتخاب کنید، هرگز همان مُهر زمانی را با نام دیگری انتخاب نکنید. اگر خود چک نتواند اجرا شود، گیت در CI از کار می افتد و فقط به صورت محلی هشدار می دهد. برای یک فایل پایه ویرایش شده، پایگاه داده ارتقا یافته با محتوای پایه آن فایل ساخته می شود و بوت دوم آن را پرش می کند زیرا نسخه آن قبلاً ضبط شده است. برای یک فایل تغییر نام داده شده، پایگاه داده ارتقا یافته با فایلی تحت نام قدیمی خود ساخته می شود و بوت دوم به جای اجرای مجدد، ردیف `_omniroute_migrations` خود را از طریق ورودی سازگاری حرکت می دهد. گیت نام جدید را با `--must-not-apply` ارسال می کند، بنابراین اگر بوت دوم آن را اعمال کند، چک ناموفق می شود. اگر یک انتقال درخواست کشش در مسیر ارتقا یافته اعمال نشود، یعنی پس از هر انتقال پایه (خواه در نصب جدید نیز با شکست مواجه شود یا نه)، گیت `migration do PR não aplica` گزارش میکند و از شما میخواهد SQL را در برابر طرح کنونی پایه اصلاح کنید. اگر فایل به انتقال درخواست کشش دیگری با مهر زمانی بعدی بستگی دارد، نام آن را با `npm run db:new-migration` بازسازی کنید.

برای اجرای همان مقایسه به صورت محلی، پایه را به طور صریح عبور دهید، برای مثال `npm run check:migration-numbering -- --base origin/<base-branch>` یا `npm run check:migration-numbering -- --base-latest-tag` برای مقایسه با آخرین نسخه.

### تبدیل یک Open PR's `NNN` migration

یک درخواست کشش که قبل از سوئیچ باز می شود ممکن است همچنان دارای یک فایل متوالی مانند `242_add_widgets.sql` باشد. اعداد قدیمی بالای `241` رد می شوند، بنابراین قبل از ادغام آن را تبدیل کنید:

1. **با حفظ توضیحات، نام فایل را با ژنراتور تغییر دهید.** `npm run db:new-migration -- <same description>` را اجرا کنید تا نام جدید را دریافت کنید، SQL را به آن منتقل کنید و فایل `NNN_` قدیمی را حذف کنید. توضیحات باید یکسان بماند: ورودی سازگاری زیر با آن مطابقت دارد.
2. **اگر یک پایگاه داده دائمی شماره قدیمی را اجرا می کرد، یک ورودی سازگاری اضافه کنید.** اگر هر پایگاه داده ای که نگهداری می شود (هومولوژی، VPS، نصب خود مشارکت کننده) یک بیلد از PR با فایل `NNN_` اجرا کرد، `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` به `RENAMED_MIGRATION_COMPATIBILITY` در `src/lib/db/migrationRunner/constants.ts` اضافه کنید. این است** برای `237` به `241` مورد نیاز است** : آن اسلات ها اکنون `237_usage_history_calculated_cost.sql`، `238_codex_connection_fences.sql`، `239_call_logs_pending_detail_index.sql`، `240_provider_node_custom_json_config.sql` و `241_seen_models.sql` متعارف را نگه می دارند و بدون ورودی، چنین پایگاه داده ای مهاجرت متعارف را برای همیشه نادیده می گیرد و دوباره نسخه تبدیل شده را اجرا می کند. همچنین برای یک اسلات که خالی می ماند، مانند `242`، زمانی که مقصد یک مهر زمانی است، کار می کند. در صورت شک، ورودی را اضافه کنید. جایی که آن را در آرایه اضافه میکنید، مهم نیست: وقتی شکاف هدف ورودی هنوز ردیفی را نگه میدارد که ورودی دیگری دور میشود (برای مثال `237` یک ردیف PR را نگه میدارد در حالی که یک ردیف `usage_history_calculated_cost` قدیمی منتظر انتقال به `237` است)، رانر به ورودی اجازه میدهد تا زمانی که شکاف آزاد شود منتظر بماند. فقط یک تضاد واقعی، مانند شکافی که توسط یک ردیف بدون ورود حرکت میکند، یا دو ورودی که اسلاتها را عوض میکنند، بوت را با `Cannot reconcile ...` متوقف میکند.
3. **SQL ناتوان نگه دار** (`CREATE TABLE IF NOT EXISTS`، `CREATE INDEX IF NOT EXISTS`، `INSERT OR IGNORE`)، زیرا مهاجرت تبدیل شده ممکن است با پایگاه داده ای روبرو شود که طرح آن از قبل وجود دارد.
4. **جابجایی موارد ویژه با کلید نسخه.** اگر PR یک مورد برای عدد قدیمی خود به `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) یا `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) اضافه کرده است، کلید را به مهر زمانی جدید تغییر دهید.

`tests/unit/db/codex-fence-migration-rename.test.ts` یک نمونه کاربردی از یک آزمایش برای مهاجرت تغییر نام یافته است.

### پورت های پشتیبان به شاخه ها قبل از سوئیچ

هرگز یک فایل `YYYYMMDDHHMMSS_` را به شاخهای که قبل از سوئیچ است (برای مثال یک شاخه `release/v*` قدیمیتر) انتخاب نکنید یا پسپورت نکنید. رانر در آنجا نام فایل ها را به صورت متن مرتب می کند، بنابراین یک فایل مهر زمانی بین `201_` و `202_` در یک پایگاه داده جدید اجرا می شود و گیت قدیمی آنجا پیشوندهای 14 رقمی را نمی فهمد. در چنین شاخهای، تغییر را بهعنوان فایل `NNN_` بعدی خود آن شعبه، idempotent بنویسید، بنابراین زمانی که نسخه مهر زمانی بعداً میرسد، بدون عملیات است.

### مهاجرت ها چگونه اجرا می شود

در هنگام راه اندازی، `migrationRunner.ts`:

1. در صورت نبود جدول `_omniroute_migrations` ایجاد می کند
2. پرس و جوهایی برای مهاجرت های قبلاً اعمال شده
3. هر انتقال جدید را به ترتیب، هر کدام در یک تراکنش اعمال می کند
4. هر مهاجرت اعمال شده را با مهر زمانی ثبت می کند

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### ناتوانی

مهاجرت ها باید باشد** ناتوان** اجرای دوبار — باید بدون عملیات باشد:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

از بندهای `IF NOT EXISTS`، `IF EXISTS` و `OR IGNORE` / `OR REPLACE` به طور آزادانه استفاده کنید.

### اضافه کردن یک مهاجرت جدید

1. **فایل را با ژنراتور ایجاد کنید** : `npm run db:new-migration -- <description>` (مثلا `npm run db:new-migration -- add combo priority`). `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` با زمان UTC فعلی و هدر نظر مینویسد، اگر آن مُهر زمانی گرفته شود، یک ثانیه به جلو حرکت میکند و هرگز یک فایل را بازنویسی نمیکند. شماره را با دست انتخاب نکنید.
2. **از DDL ایمن استفاده کنید** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **داده ها را با دقت پر کنید** : `UPDATE ... WHERE ...` برای مدیریت ردیف های موجود استفاده کنید
4. **ترتیب و نامگذاری را بررسی کنید** : `npm run test:migrations:fresh` (همه مهاجرت ها در یک پایگاه داده خالی) و `npm run check:migration-numbering`
5. **تست روی یک کپی** : هرگز مهاجرت های آزمایش نشده را در تولید اجرا نکنید
6. **جدولی که از کد ایجاد شده است نیز نیاز به انتقال دارد** : اگر یک ماژول جدول را نیز با تنبلی ایجاد کند (`CREATE TABLE IF NOT EXISTS` که به عنوان یک مسیر خوددرمانی نگهداری می شود)، یک مهاجرت باید آن را با همان DDL ایجاد کند. در غیر این صورت، نصب تمیز و نصب ارتقا یافته، بسته به اینکه آیا مسیر کد اجرا شده باشد، با طرحوارههای متفاوتی ختم میشود. `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` و `open-sse/` را اسکن می کند و در `CREATE` تنبل بدون مهاجرت (#20557) با شکست مواجه می شود. مثال: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

مثال:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **تغییرات ناسازگار با عقب** (به عنوان مثال، انداختن ستون ها) مشکل است. پس از اعمال مهاجرت — OmniRoute از کاهش رتبه NOT پشتیبانی میکند، تغییر طرح دائمی است. بر این اساس برنامه ریزی کنید.

## رمزنگاری دادههای ذخیرهشده

فیلدهای حساس (کلیدهای API، توکنهای OAuth و رشتههای اتصال) در حالت ذخیرهشده با استفاده از **AES-256-GCM** رمزنگاری میشوند.

### نحوه کارکرد

```ts
// src/lib/db/encryption.ts (نسخه سادهشده)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### محلهای استفاده

- `provider_connections.api_key` — رمزنگاریشده در سطح برنامه
- `provider_connections.access_token`، `refresh_token`، `id_token` — رمزنگاریشده در سطح برنامه
- ورودیهای `key_value` با `namespace = "secrets"` — رمزنگاریشده در سطح برنامه
- `proxy_registry.auth` — رمزنگاریشده در سطح برنامه (در صورت وجود)

### کلید رمزنگاری

کلید رمزنگاری از یک **عبارت عبور** (تنظیمشده از طریق متغیر محیطی `STORAGE_ENCRYPTION_KEY`) و یک **salt** (ذخیرهشده در پایگاه داده) مشتق میشود. برای رمزگشایی دادهها، هر دو مورد ضروری هستند.

```bash
# یک عبارت عبور امن ایجاد کنید
openssl rand -hex 32

# آن را در .env تنظیم کنید
STORAGE_ENCRYPTION_KEY=<کلید-شما>
```

> **بسیار مهم**: از دست دادن کلید رمزنگاری بهمعنای از دست دادن دسترسی به تمام دادههای رمزنگاریشده است. **از کلید، جدا از پایگاه داده نسخه پشتیبان تهیه کنید**.

### مواردی که رمزنگاری نمیشوند

به دلایل عملکردی، موارد زیر بهصورت متن ساده ذخیره میشوند:

- نامهای نمایشی ارائهدهندگان
- تعاریف مدلها (از قبل عمومی هستند)
- قواعد مسیریابی
- سوابق استفاده (بدون اطلاعات هویتی شخصی)

## پشتیبانگیری و بازیابی

### پشتیبانگیری دستی

```bash
# برای ایجاد یک نسخه پشتیبان محلی از CLI استفاده کنید
omniroute backup create --name pre-migration

# یا از طریق API
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

فایل پشتیبان شامل موارد زیر است:

- همه جداول پایگاه داده (سریالسازیشده به JSON)
- آرتیفکتهای گزارش تماس (با کدگذاری base64، اختیاری)
- تنظیمات + اطلاعات محرمانه (رمزنگاریشده)
- پیکربندی افزونه

### بازیابی

```bash
# از طریق CLI
omniroute restore pre-migration

# از طریق API
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **هشدار**: بازیابی، کل پایگاه داده را بازنویسی میکند. ابتدا همه کلاینتها را متوقف کنید.

### پشتیبانگیری خودکار

```bash
# پشتیبانگیری خودکار روزانه را از طریق CLI فعال کنید
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

زمانبندی در سمت سرور توسط یک کار پسزمینه اجرا میشود که هر ۳۰ ثانیه
(بهصورت پیشفرض) فعال شده و عبارت cron را بر اساس زمان محلی سرور ارزیابی میکند.

| متغیر                                       | پیشفرض  | توضیحات                                                                                                                     |
| ------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000` | فاصله زمانی اجرا بر حسب میلیثانیه (حداقل `5000`). برای قرار گرفتن مطمئن در دقیقه منطبق cron، باید کوتاهتر از ۶۰ ثانیه باشد. |

### پشتیبانگیری داغ SQLite

برای پشتیبانگیری بدون قطعی از یک پایگاه داده فعال:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

این دستور از API پشتیبانگیری آنلاین SQLite استفاده میکند — اجرای آن هنگام فعال بودن OmniRoute ایمن است.

## تنظیم عملکرد

### حالت WAL

WAL به طور پیش فرض فعال است. برای بارهای کاری با نوشتن بالا، در نظر بگیرید:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` را تنظیم نمی کند. یک چک پوینت فریم های WAL را به فایل اصلی منتقل می کند، اما فایل WAL بزرگترین اندازه اختصاص داده شده خود را حفظ می کند. نگهبان `OMNIROUTE_WAL_GUARD_MAX_MB` فقط هشدار می دهد و `wal_checkpoint(RESTART)` را اجرا می کند ; این یک درپوش اندازه دیسک نیست.

### شاخص ها

شاخص های کلیدی برای عملکرد (ایجاد خودکار توسط مهاجرت):

- جستجوی مدل `idx_models_provider` — توسط ارائه دهنده
- توسعه هدف ترکیبی `idx_combo_targets_combo_id` —
- تجزیه و تحلیل استفاده `idx_usage_history_api_key_timestamp` —
- پیگیری سهمیه `idx_quota_snapshots_api_key_window` —
- پرس و جوهای ثبت تماس `idx_call_logs_timestamp` —

برای افزودن یک نمایه جدید، یک مهاجرت ایجاد کنید:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### I/O دارای نقشه حافظه

برای پایگاه داده های بسیار بزرگ (> 10 گیگابایت)، نقشه برداری حافظه را می توان از طریق SQLite pragma تنظیم کرد:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### فشرده سازی

نمونه های طولانی مدت OmniRoute از `VACUUM` گاه به گاه سود می برند:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

در پنجره های کم ترافیک هر ماه اجرا شود. (حالت WAL نیاز را کاهش می دهد، اما آن را برطرف نمی کند.)

## بررسی سلامت

`src/lib/db/healthCheck.ts` **تشخیصهای سلامت در سطح پایگاه داده** را ارائه میکند:

هر دو فعل به احراز هویت نیاز دارند (در غیر این صورت `401`). `GET` فقط عیبیابی میکند؛ `POST` همان
بررسی را با فعال بودن `autoRepair` اجرا میکند.

```bash
GET  /api/db/health   # عیبیابی
POST /api/db/health   # عیبیابی + تعمیر
```

پاسخ، همان `DbHealthCheckResult` تولیدشده توسط `runDbHealthCheck()` است
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "بودجههای دامنه به کلیدهای APIای ارجاع دادهاند که دیگر وجود ندارند.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| فیلد              | معنا                                                                                                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | هنگامی `true` است که `issues` خالی باشد. `driver` هرگز بر آن تأثیر نمیگذارد.                                                                                                     |
| `issues[].type`   | یکی از مقادیر `integrity_check_failed`، `broken_reference`، `stale_snapshot` یا `invalid_state` است.                                                                             |
| `repairedCount`   | تعداد ردیفهای تعمیرشده در این اجرا؛ هنگامی که `autoRepair` برابر با false باشد، همیشه `0` است.                                                                                   |
| `backupCreated`   | مشخص میکند آیا پیش از تعمیر، نسخهٔ پشتیبان تهیه شده است یا خیر.                                                                                                                  |
| `checkedAt`       | برچسب زمانی ISO که میان اجرا و هر یادداشت تعمیری که نوشته میشود مشترک است.                                                                                                       |
| `driver.name`     | درایور SQLite که پایگاه داده بررسیشده را ارائه میکند.                                                                                                                            |
| `driver.degraded` | هنگامی `true` است که نوشتنها بهصورت ماندگار توسط فایل پایگاه داده پشتیبانی نشوند — یعنی در حالت جایگزین WASM مبتنی بر `sql.js` (ماندگاری کل فایل) یا یک پایگاه داده درونحافظهای. |

همین محتوای پاسخ توسط ابزار MCP با نام `omniroute_db_health_check` نیز بازگردانده میشود.

برای شناسایی خرابی، `PRAGMA integrity_check` را اجرا کنید:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# باید چاپ شود: ok
```

اگر مقداری غیر از `ok` برگرداند، **استفاده از پایگاه داده را فوراً متوقف کنید** و آن را از نسخهٔ پشتیبان بازیابی کنید.

## بازیابی پس از فاجعه

### سناریوی 1: فایل WAL از دست رفته است

فایل `-wal` وجود ندارد، اما `-shm` و پایگاه دادهٔ اصلی سالم هستند:

```bash
# در بازگشایی بعدی بهطور خودکار بازیابی میشود
omniroute
```

اگر SQLite نتواند بهطور خودکار بازیابی کند:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### سناریوی 2: فایل پایگاه دادهٔ اصلی خراب شده است

از نسخهٔ پشتیبان بازیابی کنید:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` فقط یک آرشیو کامل `.tar.gz` را از یک سرور در حال اجرا دانلود میکند
(`GET /api/db-backups/exportAll`، نیازمند اعتبارنامهٔ اپراتور)؛ این فرمان چیزی را بازیابی نمیکند.

### سناریوی 3: کلید رمزنگاری از دست رفته است

بدون کلید، **هیچ امکانی برای بازیابی وجود ندارد**. فیلدهای رمزنگاریشده قابل خواندن نیستند. همهٔ ارائهدهندگان را با اعتبارنامههای جدید بهصورت دستی دوباره اضافه کنید.

> **راهکار کاهش ریسک**: همیشه از کلید رمزنگاری بهصورت جداگانه نسخهٔ پشتیبان تهیه کنید؛ ترجیحاً در یک مدیر گذرواژه یا KMS.

### سناریوی 4: دیسک پر است

SQLite خطاهای `SQLITE_FULL` را برمیگرداند. فضای دیسک را آزاد کنید، سپس:

```bash
# برای آزاد کردن فضا، از WAL نقطهٔ بررسی بگیرید
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## عملیات رایج

### بررسی یک جدول

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### شمارش ردیفهای همه جدولها

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### بازنشانی (پاکسازی) همه دادهها

```bash
# ابتدا OmniRoute را متوقف کنید
omniroute stop

# فایل پایگاه داده را حذف کنید
rm ~/.omniroute/storage.sqlite*

# راهاندازی مجدد کنید (یک پایگاه داده خالی دوباره ایجاد میشود)
omniroute
```

برای بازنشانی **انتخابی** (حفظ ارائهدهندگان و پاکسازی دادههای مصرف):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### خروجی گرفتن از یک جدول

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## عیبیابی

### «پایگاه داده قفل است»

فرایند دیگری قفل نوشتن را در اختیار دارد. یکی از کارهای زیر را انجام دهید:

- منتظر بمانید تا فرایند دیگر تمام شود (`lsof | grep storage.sqlite` را بررسی کنید)
- فرایند دیگر را خاتمه دهید
- اگر مشکل ادامه داشت، OmniRoute را مجدداً راهاندازی کنید

### «محدودیت کلید خارجی نقض شد»

یک ماژول دامنه، یکپارچگی ارجاعی را نقض میکند. موارد زیر را بررسی کنید:

- ردیفهای یتیم در جدولهای وابسته
- حذفهای آبشاری که منتشر نشدهاند
- مهاجرت اخیری که یک کلید خارجی را تغییر داده است

برای یافتن موارد نقض، `PRAGMA foreign_key_check;` را اجرا کنید.

### «حافظه کافی نیست»

ورودی/خروجی نگاشتشده به حافظه SQLite از محدودیت سیستمعامل فراتر رفته است. با استفاده از pragma در SQLite آن را کاهش دهید:

```sql
PRAGMA mmap_size = 134217728;  -- 128MB بهجای 256MB
```

یا آن را غیرفعال کنید:

```sql
PRAGMA mmap_size = 0;
```

### «مهاجرت در میانه فرایند شکست خورد»

مهاجرت درون یک تراکنش اجرا شده است، بنابراین باید بازگردانی شده باشد. اگر چنین نشده است:

1. **OmniRoute را متوقف کنید** (برای جلوگیری از تلاشهای بیشتر)
2. **وضعیت پایگاه داده را** با `sqlite3` **بررسی کنید**
3. مهاجرت ناقص را **بهصورت دستی اصلاح کنید**
4. OmniRoute را **دوباره اجرا کنید** (مهاجرت مجدداً امتحان خواهد شد)

برای جلوگیری از این مشکل، همیشه ابتدا مهاجرتها را روی یک کپی آزمایش کنید.
