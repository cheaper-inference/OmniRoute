Käytä tätä opasta valitaksesi pienimmän luotettavan kehityssilmukan pull requestille. Se ei
korvaa alla linkitettyjä aluekohtaisia arkkitehtuuri- ja tietoturva-asiakirjoja, vaan yhdistää kunkin yleisen
muutostyypin sen sopimuksiin, kohdennettuihin tarkistuksiin ja CI-kattavuuteen.

## Jokaisen muutoksen etenemispolku

1. **Valitse pohja ennen muokkaamista.** Etsi korkein aktiivinen `release/v*`-haara ja luo haarasi
   sen kärjestä. Kohdista PR tähän haaraan, älä `main`-haaraan. Jos julkaisujäädytys on voimassa, älä kohdista jäädytettyyn
   haaraan, vaan käytä seuraavaa aktiivista sykliä, joka on kuvattu asiakirjassa
   [Haarautumis- ja julkaisumalli](BRANCHING_MODEL.md).
2. **Nimeä sopimukset.** Tunnista jokainen katalogi, skeema, generoitu artefakti, julkinen API tai käyttäjä-
   käyttöliittymä, johon muutos vaikuttaa. Alla oleva taulukko antaa vähimmäislähtökohdan.
3. **Kirjoita tai päivitä kohdennetut testit.** Tuotantokoodin muutokset hakemistoissa `src/`, `open-sse/`, `electron/` tai
   `bin/` edellyttävät automatisoitua testiä samassa PR:ssä. Suorita pienimmät testitiedostot, jotka todentavat
   toiminnan, ja sen jälkeen luetellut kohdennetut tarkistusportit.
4. **Anna CI:n suorittaa laaja matriisi.** Täydelliset yksikkötestiosiot, Vitest, kattavuuden kiristys ja
   tuotantokoonti suoritetaan PR:lle. Suorita laaja testikokonaisuus paikallisesti vain, kun kohdennettu virhe viittaa
   laajempaan vaikutukseen tai kun muutos kattaa useita alijärjestelmiä.
5. **Yhdenmukaista ennen katselmointia.** Nouda aktiivinen pohjahaara, tarkista sen uudet commitit ja siihen verrattu
   diffisi ja tee sitten rebase tai merge pohjahaaraan osallistujan työnkulun mukaisesti. Ratkaise generoitujen tiedostojen
   ja katalogien ristiriidat niiden lähteestä, generoi ne uudelleen, suorita kohdennettu silmukka uudelleen ja varmista, että
   PR kohdistuu edelleen aktiiviseen julkaisuhaaraan.
6. **Kirjaa todisteet.** Luettele PR-mallipohjassa suoritetut komennot, kaikki lisätyt tai muutetut testitiedostot,
   migraatiot tai ominaisuusliput sekä kaikki vielä odottavat, vain CI:ssä tehtävät tarkistukset.

## Vakiopolut muutostyypeittäin

Alla olevat komennot ovat kohdennettujen tarkistusten vähimmäisvaatimuksia, eivät lupa ohittaa testiä, joka kattaa suoraan
muuttamasi toiminnan.

### Palveluntarjoaja

**Sopimukset**

- Palveluntarjoajan määrittely hakemistossa `src/shared/constants/providers/` ja sen koostaminen tiedostossa
  `src/shared/constants/providers.ts`.
- Mallit ja ominaisuudet tiedostossa `open-sse/config/providerRegistry.ts` tai siitä erotetuissa rekisteritiedostoissa.
- Suorittimen/kääntäjän valinta, OAuth- tai API-avainmääritykset, hallintapaneelin resurssit ja generoitu
  palveluntarjoajaviite soveltuvin osin.
- Julkisten tunnistetietojen on käytettävä `resolvePublicCred()`-funktiota; virhevastauksissa on käytettävä jaettuja puhdistettuja
  virheapufunktioita. Katso `docs/security/PUBLIC_CREDS.md` (gitissä; ei käännetä `/docs`-hakemistoon) ja
  [Virheiden puhdistus](../security/ERROR_SANITIZATION.md).

**Kohdennettu silmukka**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kun katalogi muuttuu; commitoi generoitu diff
npm run lint
```

Testaa myös jokainen muutoksen kohteena oleva pyyntöperhe: chat, Responses, kuvat, upotukset, ääni tai video.
Käsittele generoituja katalogi- ja golden-diffejä sopimusmuutoksina; älä hyväksy niitä sokeasti.

### Reititys

**Sopimukset**

- Julkiset strategiavaihtoehdot ja käyttöliittymän metadata tiedostossa `src/shared/constants/routingStrategies.ts`.
- Välitys ja järjestys tiedoston `open-sse/services/combo.ts` sekä hakemiston `open-sse/services/combo/` alla.
- Combo-skeemat, pysyvyys, vikasietoisuuden tila, mallien ominaisuudet sekä API- ja käyttöliittymäohjaimet.
- [Auto-Combo-moottori](../routing/AUTO-COMBO.md) ja vikasietoisuusdokumentaatio, kun toiminta muuttuu.

**Kohdennettu silmukka**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategian tai välityksen muutokset
npm run check:known-symbols      # strategian rekisteröinnin muutokset
npm run lint
```

Käytä paikallisesti deterministisiä testejä, joissa upstream on mockattu. Reaaliaikaiset combon savutestit edellyttävät tunnistetietoja ja ovat
manuaalisia, eivät CI:n korvikkeita.

### Käyttöliittymä / käyttökokemus

**Sopimukset**

- Next.js-reitin/sivun ja jaettujen komponenttien rajat hakemistoissa `src/app/` ja
  `src/shared/components/`.
- API-vastausten muodot, lataus-/tyhjä-/virhetilat, näppäimistö- ja ruudunlukijakäyttäytyminen,
  responsiivinen asettelu, teemat ja lokaalien laajentaminen.
- Englanninkieliset käyttöliittymän lähdemerkkijonot tiedostossa `src/i18n/messages/en.json`; älä kovakoodaa uutta käyttäjälle näkyvää tekstiä.

**Kohdennettu silmukka**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Käynnistä sovellus vuorovaikutukseen tai ulkoasuun vaikuttavia muutoksia varten ja tarkista sekä kapeat että leveät näkymät. CI suorittaa
tuotantokoontiversion ja laajemmat testikokonaisuudet; visuaalinen toiminta tarvitsee silti muutokseen sopivan kohdennetun komponentti- tai Playwright-
testin tai dokumentoidun manuaalisen tarkistuksen.

### Kansainvälistäminen

**Sopimukset**

- `src/i18n/messages/en.json` on käyttöliittymän lähde; `config/i18n.json` on lokaalien lähde.
- CLI-katalogit sijaitsevat erikseen hakemistossa `bin/cli/locales/`.
- Säilytä ICU-paikkamerkit ja tagit täsmälleen ennallaan. Älä käännä tuote-, palveluntarjoaja- tai mallinimiä,
  protokollien ja otsakkeiden nimiä, komentoja, koodi-/JSON-tunnisteita, URL-osoitteita, ympäristömuuttujia tai
  suojattuja termejä, kuten `OmniRoute`, `OAuth`, `MCP` ja `A2A`. Nykyinen lähdeluettelo on
  `scripts/i18n/glossary/protected-terms.json`.

**Kohdennettu silmukka**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kun CLI-merkkijonot tai -katalogit muuttuvat
npm run lint
```

Tämä on olemassa olevan järjestelmän ohjeistus, ei kehotus laajentaa sen työkaluja tai avainmallia.
Pidä kansainvälistämiseen liittyvät korjaukset tarkkarajaisina korvaavan järjestelmän suunnittelun aikana. Älä suorita käännös-
komentoja, jotka kutsuvat ulkoisia palveluita, ellei tehtävä nimenomaisesti edellytä generoituja käännöksiä ja
ellet ole tarkistanut tuloksena syntyvää diffiä.

### CLI

**Sopimukset**

- Julkiset komennot ja valitsimet hakemistossa `bin/cli/`, generoidut API-komennot, poistumiskoodit, stdout/stderr ja
  JSON-tulosteiden rakenteet, määritysten/ympäristön toiminta sekä paketoidut tiedostot.
- CLI:n käyttäjälle näkyvien merkkijonojen on käytettävä CLI:n i18n-kerrosta, ja `en`/`pt-BR`-luettelot on pidettävä yhdenmukaisina.
- Säilytä Node tuettuna suoritusympäristönä ja julkaistun binääritiedoston sopimus muuttumattomana.

**Kohdennettu kehityssilmukka**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generoidun/paketoidun CLI:n muutokset
npm run check:pack-policy     # paketin julkisen pinnan muutokset
npm run lint
```

Käytä täsmällistä komentoa väliaikaisessa datahakemistossa, kun toiminta riippuu jäsentämisestä, tiedostoista tai poistumistilasta. CI suorittaa laajemmat pakettiartefaktien ja ekosysteemin tarkistukset.

### Tietokanta

**Sopimukset**

- Toimialuemoduulit ovat hakemistossa `src/lib/db/`; tuo yksittäiset moduulit suoraan (vanha `localDb.ts`-uudelleenvientikerros on poistettu).
- Numeroiduista, idempotenteista SQL-migraatioista hakemistossa `src/lib/db/migrations/`, transaktioturvallisuudesta, päivitystoiminnasta, indekseistä ja jokaisesta skeeman muutoksen vaikutuspiirissä olevasta kutsujasta on huolehdittava.
- Reitit ja käsittelijät eivät koskaan suorita raakaa SQL:ää suoraan.

**Kohdennettu kehityssilmukka**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Kun lisäät migraation, testaa sekä uusi tietokanta että päivitys edellisestä skeemasta. Tietokantatestien on suljettava kahvat ja kutsuttava `resetDbInstance()`-funktiota siivouksen aikana. Suorita `npm run test:bun:db` vain, kun parhaaseen yritykseen perustuva Bun-sovitinpolku muuttuu; Node on edelleen ensisijainen.

### Koonti / käyttöönotto

**Sopimukset**

- Juuren ja työtilojen manifestit/lukkotiedosto, `scripts/build/`, Next.js:n itsenäisen version kokoaminen, `dist/`-paketin sisältö, Electron-alustojen metatiedot, CI-työnkulut ja käyttöönoton tarkistuspisteet.
- Tuettujen Node-versioiden vaihteluvälit ja `CLAUDE.md`-tiedostossa sallittujen Bun-käyttötapojen luettelo on säilytettävä ennallaan.
- Koontiartefakteja ei seurata versionhallinnassa; riippuvuus-, lisenssi-, työnkulku- ja pakettikäytäntöjä sovelletaan.

**Kohdennettu kehityssilmukka**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # riippuvuuden tai lukkotiedoston muutokset
npm run check:pack-policy      # julkaistun paketin pinnan muutokset
npm run lint
```

Käytä komentoa `npm run build` paikallisesti vain, kun muutos vaikuttaa kääntämiseen, itsenäisen version kokoamiseen, resursseihin tai suorituksenaikaiseen paketointiin. Käytä komentoa `npm run build:release` vain julkaisun tai käyttöönoton validointiin. CI:n koonti on lopullinen alustariippumaton signaali; alustakohtaiset Electron-muutokset edellyttävät vastaavaa kohdennettua koontia tai smoke-testinäyttöä.

## Kehittäjäskriptit jaetulle koneelle

Kaksi `scripts/dev/`-apukomentosarjaa toteuttaa paikallisen kehityssilmukan kehityskoneella, jolla on käynnissä muitakin istuntoja:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # tiedostot alueelta merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # täsmälleen nämä tiedostot
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # eristetty työhakemisto, turvallinen rinnakkaisessa käytössä
```

- `typecheck-touched.sh` suorittaa tyyppitarkistuksen vain muokatuille `.ts/.tsx`-tiedostoille väliaikaisen
  `tsconfig.touched.tmp.json`-tiedoston avulla (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) käyttäen 6 Gt:n kekoa, joten se korvaa koko projektin kattavan `tsc -p tsconfig.json`-komennon,
  joka kuluttaa muistin loppuun kuormitetulla koneella. Se tulostaa muokattujen tiedostojen virheet sekä yhden yhteenvetorivin ja palauttaa
  arvon `1`, jos muokatuissa tiedostoissa on virheitä, arvon `2`, jos ainoat virheet ovat tuoduissa tiedostoissa tai tsc keskeytyi
  ilman diagnostiikkaa (lue sen nimeämä loki hakemistosta `_artifacts/typecheck-touched/`), ja arvon `0`, jos
  virheitä ei ole. Väliaikainen tsconfig poistetaan aina; älä koskaan commitoi sellaista.
- `new-worktree.sh` sarjallistaa samanaikaiset suoritukset lukolla `<git-common-dir>/omniroute-new-worktree.lock`
  (odottaa oletusarvoisesti enintään 600 s ja näyttää siitä ilmoituksen; komentosarjan otsake dokumentoi
  ohitusasetuksen) ja peruu
  luomansa haaran, jos `git worktree add` epäonnistuu ennen työhakemiston luomista, joten uudelleenyritys
  ei edellytä manuaalista `git branch -D`-komentoa. Kovilla linkeillä linkitetty `node_modules` ja `.husky/_`-kopio säilyvät ennallaan.

## Paikallinen ehdokassilmukka

Lähdekooditestit eivät voi todistaa, että paketoitu artefakti käynnistyy: paketointiluettelot, karsitut riippuvuudet
ja natiivibinäärit epäonnistuvat vasta, kun tar-paketti asennetaan ja käynnistetään. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) on RFC #8084:n käännä kerran / validoi / ota käyttöön -prosessin
paikallinen osa: se kääntää yhden ehdokkaan, validoi juuri kyseisen artefaktin, ottaa sen käyttöön nimeämällä
hakemistoja uudelleen ja palauttaa sen edeltäjän, jos käyttöön otetun paikan kuntotarkistus epäonnistuu.

```bash
npm run dev:candidate -- run --dry-run --json  # tulosta suunnitelma muuttamatta mitään
npm run dev:candidate -- run                   # käännä + validoi + ota käyttöön, automaattinen palautus
npm run dev:candidate -- build                 # npm pack + asennus hakemistoon _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # käynnistä vapaassa portissa, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # vaihda current- ja previous-paikat keskenään
npm run dev:candidate -- run --from-tarball <file.tgz>  # käytä muualla (CI:ssä) luotua tar-pakettia uudelleen
```

- **Käännä kerran.** `build` paketoi nykyisen puun (se tarvitsee tiedoston `dist/server.js`, joten suorita
  ensin `npm run build:release`) tai kopioi `--from-tarball`-tiedoston ja asentaa sitten tar-paketin
  eristettyyn npm-etuliitteeseen, koska tar-paketti ei sisällä `node_modules`-hakemistoa. Tunniste on lyhyt `HEAD`-sha
  (`-dirty`, kun puussa on paikallisia muutoksia) tai tar-paketille `tgz-<sha256>`. Muuttumaton tunniste, jonka
  käännös on jo olemassa, käytetään uudelleen kääntämisen sijaan; käännä se uudelleen antamalla `--force`.
- **Validoi paketti, älä lähdekoodia.** `validate` käynnistää asennetun CLI:n
  (`serve --port <free port>`) käyttäen uutta `DATA_DIR=<candidate>/data`-hakemistoa ja valesalaisuuksia sekä poistamalla
  operaattorin `OMNIROUTE_API_KEY`-, `STORAGE_ENCRYPTION_KEY`- ja `INITIAL_PASSWORD`-arvot
  ympäristöstä, jotta se tarkistaa uuden asennuksen avaimettoman loopback-tilan. Se odottaa, että
  `GET /api/health` palauttaa tilan 200, edellyttää, että `GET /v1/models` palauttaa tilan 200, pysäyttää prosessiryhmän
  ja tallentaa tuloksen `validation.json`-tiedostoon yhdessä tar-paketin tiivisteen kanssa.
- **Ota sama artefakti käyttöön.** `promote` hylkää ehdokkaan, jolla ei ole hyväksyttyä validointia sen
  nykyiselle tar-paketin tiivisteelle. Oletusarvoinen aktiivinen paikka on `_artifacts/candidate/current`; `--target <dir>`
  valitsee toisen samalla tiedostojärjestelmällä sijaitsevan hakemiston, ja sen edellinen paikka on `<dir>.previous`.
  Jokainen uudelleennimeäminen on atominen, ja kesken prosessin tapahtuva virhe peruu jo suoritetut uudelleennimeämiset.
- **Palauta edeltäjä.** `run` validoi käyttöön otetun paikan uudelleen ja vaihtaa `current`- ja `previous`-paikat takaisin, jos
  tarkistus epäonnistuu. Ensimmäisen validoinnin läpäisemätöntä ehdokasta ei koskaan oteta käyttöön.

Kaikki kirjoitetaan Gitin ohittamaan `_artifacts/candidate/`-hakemistoon; olemassa olevaan OmniRoute-asennukseen
ja sen datahakemistoon ei koskaan kosketa. Käyttöön otettu CLI on
`_artifacts/candidate/current/prefix/bin/omniroute`; käynnistä se omalla `DATA_DIR`-arvollasi, kun käytät
sitä. Poistumiskoodit: `0` onnistuminen, `1` epäonnistunut validointi tai käyttöönotto, `2` käyttövirhe tai puuttuva käännös.

## Paikallinen silmukka verrattuna CI:hin

| Suorita paikallisesti jokaiselle korjaukselle                                                          | CI tarjoaa laaja-alaisen signaalin                                                |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Yllä mainitut suorat toimintatestit ja kategoriaportit                                                 | Ositettu täysi yksikkötestikokonaisuus ja sarjalliset testit                      |
| `npm run lint`                                                                                         | Vitest-testikokonaisuudet sekä kattavuus- ja laatukynnykset                       |
| Tyyppitarkistus tai koonti vain, kun muutettu sopimus sitä edellyttää                                  | Tuotantokoonti sekä tietoturva-, dokumentaatio-, riippuvuus- ja PR-käytäntöportit |
| Manuaalinen vuorovaikutus / reaaliaikaiset tarkistukset vain, kun automaatio ei voi todentaa toimintaa | Työnkulun määrittämät töiden väliset integraatio- ja alustatarkistukset           |

Vihreä kohdennettu silmukka on näyttöä muutetusta sopimuksesta, ei todiste siitä, että asiaan liittymättömät CI-tarkistukset
läpäistään. Älä myöskään anna jokaisen paikallisen muutoksen odottaa koko repositorion matriisin valmistumista.

## Täsmäytyksen tarkistuslista

Ennen katselmoinnin pyytämistä:

- Varmista, että PR:n pohjahaara on edelleen korkein aktiivinen `release/v*`-haara.
- Nouda kyseinen pohjahaara ja tarkista haarautumisesi jälkeen siihen lisätyt commitit.
- Tarkista komennolla `git diff <active-base>...HEAD`, ettei mukana ole tahattomia tai generoituja muutoksia.
- Ratkaise luetteloiden ja generoitujen dokumenttien ristiriidat päivittämällä lähde ja generoimalla tuloste uudelleen.
- Suorita täsmäytyksen jälkeen uudelleen kaikki PR-kuvauksessa luetellut kohdennetut testit ja portit.
- Älä koskaan heikennä odotuksia tai poista vaadittuja testejä vain mukautuaksesi siirtyneeseen pohjahaaraan.

Julkaisujäädytystä ja uudelleenkohdistamista koskevat säännöt löytyvät dokumentista
[Haarautumis- ja julkaisumalli](BRANCHING_MODEL.md). Kattava CI-luettelo löytyy dokumentista
[Laatuporttien viite](../architecture/QUALITY_GATES.md).
