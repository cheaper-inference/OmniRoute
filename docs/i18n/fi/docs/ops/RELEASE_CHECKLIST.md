## npm Trusted Publishing (oletus versiosta v3.8.51 lähtien) — pyynnöstä vaiheistettu, varamenetelmänä suora

`npm-publish.yml` julkaisee oletusarvoisesti **npm Trusted Publishing (OIDC)** -toiminnolla:
`stage-npm`-työ (GitHubin isännöimä) vaihtaa GitHubin id-tokenin kyseisen ajon ajaksi
lyhytikäiseen npm-tunnistetietoon — repositorion salaisuuksissa ei ole pitkäikäistä npm-tokenia,
2FA-kehotetta ei näytetä ja alkuperätiedot liitetään mukaan.
Tämä on npm:n nyt hyväksymä ohitusmenetelmä, kun 2FA:n ohittavat tokenit poistuvat käytöstä;
se palauttaa projektin versioon v3.8.48 asti käyttämän täysin automaattisen prosessin säilyttäen
samalla WS1.3-takuun (vuotanut token ei yksinään voi julkaista — tokenia ei ole).

**Kertaluonteinen määritys (omistaja):** npmjs.com → paketti `omniroute` → Settings → _Trusted
Publisher_ → GitHub: omistaja `diegosouzapw`, repositorio `OmniRoute`, työnkulku `npm-publish.yml`
(ympäristö: ei mitään). Kunnes tämä on määritetty, automaattinen vaihe epäonnistuu virheeseen `ENEEDAUTH`:
käynnistä työnkulku uudelleen asetuksella `publish_mode=staged` (alla) tai `direct`.

### Vaiheistettu julkaiseminen (pyynnöstä — `publish_mode=staged`)

npm-publish-työnkulku ei enää julkaise suoraan: se käynnistää pakatun tarball-tiedoston
(`check:pack-boot`) ja suorittaa sitten komennon `npm stage publish` — täsmälleen nämä tavut
siirretään rekisteriin, mutta ne **eivät ole asennettavissa**, ennen kuin omistaja hyväksyy ne.
Käyttäjän 2FA-portti siirtyi todennuksen JÄLKEEN, ei sitä edeltäväksi.

**Omistajan työnkulku sen jälkeen, kun työnkulku muuttuu vihreäksi:**

1. `npm stage list omniroute` — etsi vaiheen tunnus (se tulostetaan myös työnkulun yhteenvetoon).
2. Tarkista vaiheistetut tavut (suositeltavaa): `npm stage download <id>`, asenna sitten
   ladattu tarball väliaikaiseen prefix-hakemistoon ja käynnistä se (`npm run check:pack-boot` automatisoi
   saman pakkaus→asennus→käynnistys-tarkistuksen CI:ssä).
3. `npm stage approve <id>` — 2FA-kehote ON julkaisu. `npm stage reject <id>` hylkää sen.
4. Julkaisun jälkeinen turvaverkko: julkaisun jälkeinen tarkistin (v3.8.49-suunnitelman WS1.4) asentaa
   julkaistun version julkisesta rekisteristä puhtaaseen konttiin ja käynnistää sen.

**Hätätilanteen varamenetelmä:** `workflow_dispatch` asetuksella `publish_mode=direct` palauttaa
aiemman välittömän `npm publish` -toiminnan (käytä vain, jos itse vaiheistus toimii virheellisesti; kirjaa syy).

**Kertaluonteinen suojaus (omistaja, npmjs.com):** määritä Trusted Publisher
paketille `omniroute` vain vaiheistuksen sallivaan tilaan, jotta vuotaneella pitkäikäisellä tokenilla ei voi suorittaa
komentoa `npm publish` suoraan mistään — CI voi vain vaiheistaa; ainoastaan omistajan 2FA vapauttaa julkaisun.

**Viallisen artefaktin toimintamalli (ennallaan):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
on ensisijainen reaktio (kestää minuutteja ja on peruttavissa); käytä komentoa `npm unpublish` vain 72 tunnin
aikarajan sisällä, kun riippuvaisia paketteja ei ole, äläkä koskaan ensimmäisenä toimenpiteenä. Dockerissa:
älä koskaan kirjoita versiotunnistetta uudelleen — palautus tehdään osoittamalla `latest` viimeisimpään toimivaan digest-arvoon.

**Docker Hubin `latest` (pakollinen jokaisessa vakaassa SemVer-julkaisussa):**
`docker-publish`-työnkulun on merkittävä **sekä** `X.Y.Z` että, kun
`should-promote-latest.sh` vahvistaa tämän olevan uusin vakaa SemVer-versio, `:latest`
**samalla digest-arvolla**. Työn jälkeen Hubin `latest`-digest vastaa uutta
SemVer-digestiä ja `last_updated` on päivittynyt. Älä jätä `:latest`-tunnistetta viittaamaan vanhempaan
koosteeseen, jos julkaisutiedotteessa kerrotaan korjauksista, jotka ovat olemassa vain gitissä. Composen
pika-aloitukset käyttävät `:latest`-tunnistetta; GitOpsin tulee edelleen kiinnittää versio tunnisteeseen `X.Y.Z`. Katso
[Dockerin julkaisukanavat](../guides/DOCKER_GUIDE.md#release-channels) ja #10317.

## Hotfix-pikakaista (tunniste `hotfix`)

Tunnisteella `hotfix` merkitty PR ohittaa raskaan CI-matriisin (9-osainen E2E, kattavuuden kiristys,
quality-gate, quality-extended) ja säilyttää nopeat, luotettavat tarkistukset: koonti,
yksikkötestiosiot, integraatiotestit, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
sekä tarball-paketin käynnistyksen smoke-testin (`check:pack-boot`). Tavoite: vihreä tulos ≤15 minuutissa noin 33 minuutin sijaan.

**Käyttöehdot — kaikkien neljän on täytyttävä (mallina Chromiumin, VS Coden ja Noden hätäkaistat):**

1. **Vakavuus**: tuotanto on rikki — julkaistu artefakti kaatuu käynnistyksessä / kyseessä on
   tietoturvakorjaus / ongelma vaikuttaa julkaisun jokaiseen käyttäjään. ”Tärkeä” ei tarkoita ”rikki”.
2. **Valtuutus**: vain repositorion omistaja lisää `hotfix`-tunnisteen. Tunniste ON
   hyväksyntä — sitä ei koskaan lisätä itse kampanja-PR:ään.
3. **Todisteet**: PR:n kuvaus linkittää edelliseen täysin vihreään raskaaseen ajoon (testikokonaisuuteen,
   jonka ohitetut työt vahvistaisivat uudelleen) sekä korjauksen omaan testiin, joka ensin epäonnistuu ja sitten onnistuu.
4. **Laajuus**: vain cherry-pick — pienin mahdollinen korjaus, ei refaktorointeja eikä oheismuutoksia.

Ohitettu kattavuus-/kiristyspinta vahvistetaan uudelleen release-haaran seuraavassa täydessä ajossa
(jatkuvasti vihreä julkaisu) — kaista ohittaa vain ODOTUKSEN, ei koskaan validointia.
Vain testejä koskevat muutokset (kaikki tiedostot hakemistossa `tests/`, ei yhtään hakemistossa `tests/e2e/`) ohittavat E2E-matriisin
automaattisesti ilman tunnistetta.

### Rakenna asettelu

Arkisto käyttää kolmea erillistä tuloshakemistoa — koskaan sekoita niitä:

| Hakemisto | Tarkoitus                                                      | Seurattu?             |
| --------- | -------------------------------------------------------------- | --------------------- |
| `src/`    | Sovelluslähde (TypeScript / TSX)                               | Kyllä                 |
| `.build/` | Rakenna välituotteet — `next build` -lähtö (`distDir`)         | Ei (huomioon jätetty) |
| `dist/`   | Toimitettava npm-nippu — jonka on koonnut `assembleStandalone` | Ei (huomioon jätetty) |

> **Käyttäjän huomautus:** kauko- VPS -kuvahakemisto säilyy `/usr/lib/node_modules/omniroute/app/`. Vain** repossa** koontilähtö siirretty (`app/` → `dist/`). Käyttöönottotaidot rsync `dist/` sisällön etä- `app/` dir — ei vaadi VPS polun muutoksia.

**Yhden rakennuksen virtaus:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Suorita NOT `npm run build` ja sen jälkeen erillinen `npm run build:cli` — käyttöönottoa varten. Käytä `npm run build:release`, joka tekee puhtaan + sentinelin uudelleenrakentamisen yhdessä komennossa.

## 3.9.0 LTS-haarautus (harjoiteltu versiossa 3.8.58)

Version v3.8.59 jälkeen seuraava versio on 3.9.0, ja sen kärjestä muodostetaan kaksi pitkäikäistä haaraa:
`stable/v3` (v3:n LTS-linja, npm `latest`) ja `develop` (v4, jonka versioksi nostetaan 4.0.0, npm
`nightly`). Haara-/kanavamalli, eteenpäin siirto ja tunnisteet on kuvattu tiedostossa
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md); suunnitelma on [ROADMAPissa](../../ROADMAP.md) (vaihe 3). Haarautus suoritetaan kerran;
versiossa 3.8.58 se harjoitellaan alusta loppuun forkissa, ja 3.8.59 viimeistellään
[GO/NO-GO-tarkistuslistalla](./LTS_GO_NO_GO.md).

### Kuivaharjoittelu (vain luku, turvallinen milloin tahansa)

```bash
npm run release:dry-run-lts-cut                       # varsinainen haarautus: 3.9.0 HEADista, edellinen tunniste v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # kiinnitä lähde-commit
```

`scripts/release/dry-run-lts-cut.mjs` ei suorita mitään: se lukee gitin ja `gh`:n tiedot ja tulostaa
koko sarjan — ennakkoehdot (lähde voidaan selvittää, lähderepossa on täydellinen historia —
matalasta kloonista ei voi puskea `stable/v3`-haaraa, koska vastaanottava osapuoli hylkää paketin ensimmäisen
liitetyn vanhemman kohdalla, joten tee haarautus täydestä kloonista tai suorita ensin `git fetch --unshallow origin` —
edellinen tunniste on olemassa, `package.json` sisältää kohdeversion, avoin `release-freeze`-issue on olemassa eikä
olemassa olevassa julkaisuhaarassa ole avointa
`Release branch not green` -issuea
— haara, jota ei ole olemassa, ilmoitetaan tuntemattomaksi `?`, ei koskaan vihreäksi —
Mergifyn `release`-jono on määritetty (G11: `queue_rules`, `checks_timeout`,
tunniste `queue`), `release/*`-sääntöjoukko estää edelleen poistamisen ja pakotetun puskemisen, eivätkä
`stable/v3` ja `develop` ole vielä olemassa), kaksi haaravaihetta, mitkä käyttämättöminä olleiden työnkulkujen
laukaisimet ja `if:`-ehdot muuttuvat tosiksi (ja mitkä pysyvät repomuuttujan estäminä tai
kanoniseen repoon kiinnitettyinä), odotetut dist-tagit (`latest` → 3.9.0, `next` ja
`nightly` tyhjiä) sekä palautus. Poistumiskoodi `0` = `RESULT: READY`, `1` = estävä ennakkoehto
epäonnistui (`✗`), `2` = käyttövirhe. `--advisory <id,...>` alentaa tarkistuksen varoitukseksi (`!`)
piilottamatta sitä.

Suorita varsinaisen haarautuksen kuivaharjoittelu, kun version 3.9.0 julkaisujäädytys on vielä voimassa — haarat
luodaan tunnisteen jälkeen ja ennen kuin vaihe 12c päättää jäädytyksen.

### Version 3.8.58 harjoittelu (vain forkissa)

```bash
# 1. Kuivaharjoittele nykyisellä kärjellä käyttäen harjoitteluparametreja
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. Suorita FORK-etärepoa vasten (origin tai mikä tahansa etärepo, jonka URL on kanonisen
#    repon URL, hylätään; jokainen vaihe pyytää vahvistuksen päätteessä)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. Testaa forkissa käyttämättöminä olleet työnkulut (workflow_dispatch, jos kuivaharjoittelu
#    ilmoittaa kiinnityksestä kanoniseen repoon) ja palauta sitten muutokset
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

Develop-versionnostocommit muodostetaan gitin matalan tason komennoilla (työpuuhun ei kosketa), ja se päivittää
samat viisi tiedostoa kuin kehityssyklin avaava commit: `package.json`, `open-sse/package.json`,
`electron/package.json`, `package-lock.json` ja `docs/openapi.yaml`. CHANGELOGin `[4.0.0]`-osio
ja sen i18n-vastineet avataan tämän jälkeen `develop`-haarassa ennen sen ensimmäistä
PR:ää. Skripti ei koskaan muuta npm:n dist-tageja — harjoittele niitä testipaketilla.

### PR-esikatseluartifakti (koosta kerran, ylennä samat tavut)

`.github/workflows/preview-artifact.yml` koostaa yhden tuotantotarballin PR:n kärjestä ja
validoi täsmälleen kyseisen koosteen (#8084:n osa (a)). Vain saman repon PR:t; mitään ei julkaista.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # tai lisää `preview-artifact`-tunniste
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # esikatseluasennus
```

Suoritus ajaa komennot `npm ci`, `npm run build:release` ja `npm run check:pack-artifact`, paketoi
tarballin, ajaa komennon `npm run check:pack-boot` (väärennetyt salaisuudet, tilapäinen datahakemisto), paketoi uudelleen ja
epäonnistuu, ellei tiiviste ole identtinen, minkä jälkeen se tallentaa tiedoston `artifact-identity.json` (kärjen SHA, pohjan

ylentäminen tarkoittaa kyseisen tarballin asentamista: älä koskaan koosta sitä uudelleen lähdekoodista.

## Palautus

Jos julkaisussa on kriittinen ongelma:

1. `gh release edit vX.Y.Z --prerelease` (merkitsee, ettei julkaisu ole uusin)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (vain jos käyttäjät eivät ole vielä ottaneet sitä käyttöön)
3. Tai: hotfix-haara `release/vX.Y.0`-haarasta → korjausjulkaisu `vX.Y.(Z+1)`
4. Tiedota asiasta välittömästi GitHub Discussionsissa ja Discordissa

## Ehdottomat säännöt

- Älä koskaan tee commitia suoraan `main`-haaraan
- Älä koskaan käytä `git push --force` -komentoa `main`- tai `release/*`-haaroihin
- Älä koskaan ohita Husky-koukkuja (`--no-verify`)
- Älä koskaan commitoi salaisuuksia, tunnistetietoja tai `.env`-tiedostoja
- Kattavuuden on pysyttävä tasolla ≥60/60/60/60 (lauseet/rivit/funktiot/haarat)
- Lisää tai päivitä testit aina, kun muutat tuotantokoodia hakemistoissa `src/`, `open-sse/`, `electron/` tai `bin/`
