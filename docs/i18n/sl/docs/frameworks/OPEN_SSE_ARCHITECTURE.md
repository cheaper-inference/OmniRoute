> **Na kratko**: `open-sse/` je osrednji pretočni mehanizem, ki poganja vsako zahtevo LLM v OmniRoute. Vsebuje približno 1.400 datotek, ki implementirajo cevovod zahtev, izvajalnike, storitve, strežnik MCP in prevajalsko plast. Ta vodnik pojasnjuje, kako so ti deli povezani.

**Vir:** `open-sse/` (paket delovnega prostora, približno 1.440 netestnih datotek `.ts`)

---

## Zakaj ločen paket delovnega prostora?

`open-sse/` je **samostojen delovni prostor** v monorepozitoriju OmniRoute iz več razlogov:

1. **Ponovna uporabnost** — `open-sse` je objavljen kot `@omniroute/open-sse` na npm, zato ga lahko drugi projekti uporabljajo neodvisno
2. **Jasne meje** — pretočni mehanizem je ločen od plasti uporabniškega vmesnika/podatkovne zbirke, specifične za OmniRoute
3. **Zmogljivost** — mehanizem nima odvisnosti od Next.js, kar omogoča hitrejše hladne zagone v okoljih CLI/brezstrežniških okoljih
4. **Različice** — `open-sse` lahko izdaja različice po lastnem urniku

```json
// package.json
"workspaces": ["open-sse"]
```

## Cevovod zahtev

Vsaka zahteva LLM potuje skozi **5-stopenjski cevovod**:

```
                              ┌──────────────┐
   Zahteva HTTP                │  1. USMERI   │   razreševanje kombinacije, izbira modela
   (pot Next.js)               └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. PREVEDI  │   pretvorba formata (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. IZVEDI   │   izvajalnik ponudnika, HTTP, ponovni poskus, odklopnik
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. PRETAKAJ │   pretvorba SSE, povratni pritisk
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ZABELEŽI │   sledenje uporabi, dnevnik klicev, razvrščanje napak
                              └──────┬───────┘
                                     │
                                     ▼
                              Odgovor HTTP (SSE ali JSON)
```

### 1. stopnja: Usmerjanje (services/combo.ts)

**Vstopna točka**: `handleComboChat()` v `services/combo.ts`

Razreši zahtevo v konkreten nabor `(provider, model, account, credentials)`:

- Poišče kombinacijo po ID-ju (ali ustvari navidezno kombinacijo za modele `auto/*`)
- Uporabi strategijo usmerjanja (prednostna, utežena, krožna itd.)
- Izloči ponudnike, ki ne delujejo pravilno (odklopnik)
- Izbere naslednji izvedljivi cilj

Za modele `auto/*` ta stopnja tudi:

- Izvede algoritem **ocenjevanja s 16 dejavniki** (`services/autoCombo/`)
- Izbere par `provider+model` glede na stanje, stroške, zakasnitev itd.

### 2. stopnja: Prevajanje (translator/)

Če se izvorni format (npr. OpenAI) razlikuje od ciljnega formata (npr. Claude), se zahteva **prevede**:

- Sistemski poziv → sistemsko sporočilo
- Definicije orodij → format orodij, specifičen za ponudnika
- Parametri sklepanja/razmišljanja → ustrezniki, specifični za ponudnika
- Normalizacija vlog sporočil (`developer` → `system` za ponudnike, ki niso OpenAI)

`translator/index.ts` izpostavlja:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 3. stopnja: Izvajanje (executors/)

**Vstopna točka**: `getExecutor(providerId).execute(request, options)`

Vsi ponudniki uporabljajo `DefaultExecutor` (`executors/default.ts`) prek nadomestne tovarne `getExecutor()`. Izvajalnik:

- Sestavi URL nadrejene storitve (`buildUrl()`)
- Doda glave, specifične za ponudnika (`buildHeaders()`)
- Pretvori telo zahteve (`transformRequest()`)
- Pošlje zahtevo HTTP s ponovnimi poskusi in eksponentnim podaljševanjem čakanja
- Po potrebi osveži avtentikacijo (ponudniki OAuth)

Vsi izvajalniki razširjajo `BaseExecutor` (`executors/base.ts`, 1170 LOC), ki zagotavlja:

- Skupno logiko ponovnih poskusov
- Integracijo posredniškega strežnika
- Integracijo odklopnika
- Kavlje za beleženje uporabe

### 4. stopnja: Pretakanje (utils/stream.ts)

Pri pretočnih odgovorih izvajalnik vrne **ReadableStream**. Obdelovalnik:

- Pretok preusmeri skozi pretvorbo SSE (`createSSETransformStreamWithLogger`)
- Uporabi periodične signale za zaznavanje prekinjenih povezav
- Elegantno obravnava prekinitev povezave odjemalca (`pipeWithDisconnect`)
- Pretvori SSE → JSON za odjemalce brez pretakanja

Pri nepretočnih odgovorih izvajalnik vrne razčlenjen objekt JSON, ki je posredovan naprej brez sprememb.

### 5. stopnja: Beleženje (services/usage.ts)

Po odgovoru (uspešnem ali neuspešnem) se zabeleži uporaba:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` iz odgovora
- `cost_usd`, izračunan na podlagi podatkov o cenah
- `latency_ms`, `status`, `error_class` v primeru neuspeha
- Shranjeno v tabelo `usage_history`

Artefakti dnevnika klicev (če so omogočeni) se zapišejo v `${DATA_DIR}/call_logs/`.

## Poglobljeni potop v ključne datoteke

### chatCore.ts (5977 vrstic)

The** glavni obdelovalec zahtev** . Kljub svoji velikosti ima jasno strukturo:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

Čeprav gre za eno velikansko funkcijo, je organizirana v** komentiranih odsekov** ki se preslika na 5-stopenjski cevovod.

### combo.ts (4456 LOC)

The** usmerjevalni mehanizem** ki razreši kombinacijo na urejene cilje.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

### base.ts (1170 LOC)

The** abstraktni izvajalec** da se vsak izvajalski razred razširi (neposredno ali preko `DefaultExecutor` in drugih podrazredov). Vsebuje:

- `buildUrl()` — privzeta konstrukcija URL (podrazredi preglasijo po meri)
- privzete glave `buildHeaders()` — (avtentika, vrsta vsebine)
- `transformRequest()` — prehod privzeto
- `execute()` — glavna zanka HTTP z retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

Obnašanje, specifično za ponudnika (glave za preverjanje avtorizacije, osnovni URL, glave različice), je konfigurirano prek registra ponudnika, ne prek ločenih razredov izvajalcev.

## Izvajalci (150 modulov)

Večinoma ena datoteka na ponudnika. Izvajalski razredi vsi razširjajo `BaseExecutor` in preglasijo tisto, kar se razlikuje; drugi moduli so pomočniki za vsakega ponudnika (sheme orodij, adapterji fetch/TTS, obdelovalci quirk).

### Pogosti vzorci

Ponudniki se razrešijo prek `getExecutor(providerId)`, ki vrne konfiguriranega izvajalca. ponudniki OpenAI/Anthropic-compatible uporabljajo `DefaultExecutor` (`executors/default.ts`). Vedenje, specifično za ponudnika (osnovni URL, glave avtorja, različica API ), je konfigurirano v `open-sse/config/providers/`, medtem ko se transformacije telesa zahteve obravnavajo v `open-sse/translator/`.

**URL** se nastavi prek konfiguracije ponudnika:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Avtorizacija po meri** se upravlja prek konfiguracije avtenzije registra ponudnika (ključ API, OAuth, profili glave).

**Telo zahteve po meri** transformacije (npr. Anthropic ki ločuje `system` od `messages`) so registrirane za vsakega ponudnika v `open-sse/translator/`.

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Ločevanje gre skozi `ExecutorRegistry` (`executors/registry.ts`): vsak specializiran izvajalec je deklariran v vgrajeni tabeli `executors/index.ts` in registriran prek `registerExecutor(alias, instance)` ob nalaganju modula; `getExecutor()` se posvetuje z registrom in se vrne k pomnjenemu `DefaultExecutor` za katerega koli ponudnika brez posebnega vnosa. Za celotno preslikavo izvajalca vzdevka → je značilen zlati test `tests/unit/executor-map-golden.test.ts`.

## Prevajalniki

Prevajajte med **3 formati**: OpenAI, Anthropic, Gemini ter novim Responses API.

### Kdaj se izvede prevajanje

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Pogoste pretvorbe:

- `OpenAI → Anthropic`: ločeno polje `system`, glava `x-api-key`
- `OpenAI → Gemini`: `contents` namesto `messages`, `systemInstruction`
- `OpenAI → Responses API`: polje `input`, stanje `previous_response_id`

### Obravnavani robni primeri

- vloga `developer` → `system` za ponudnike, ki niso OpenAI
- vloga `system` → združena v prvo uporabniško sporočilo za GLM/ERNIE
- `json_schema` → Gemini-jeva `responseMimeType` + `responseSchema`
- `tools` → oblika orodij, specifična za ponudnika
- Parametri razmišljanja (o1, Claude) → ustreznice, specifične za ponudnika

## Strežnik MCP

`open-sse/mcp-server/` implementira strežnik **Model Context Protocol**:

- **110 orodij** (upravljanje ponudnikov, kombinacije, pomnilnik, predpomnilnik, stiskanje, posredniški strežnik, veščine, igrifikacija, vtičniki, Notion, Obsidian, lokalni korpus)
- **3 prenosi**: stdio, SSE, Streamable HTTP
- **33 obsegov** za natančno določanje pooblastil

### Registracija orodij

Orodja so registrirana kot samostojne datoteke v `open-sse/mcp-server/tools/`, pri čemer vsaka izvaža ime, shemo, obravnavalnik in obseg:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Prenosi

```ts
// stdio (uporaba prek CLI-ja)
startMcpStdio(server);

// SSE (pretočno pošiljanje na osnovi HTTP-ja)
startMcpSse(server, port);

// Streamable HTTP (sodobni MCP)
startMcpStreamable(server, port);
```

### Pooblastila

Vsak klic orodja gre skozi preverjanje obsegov (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Pretvorniki

`open-sse/transformer/` pretvarja med formatoma **Chat Completions** in **Responses API**.

### Zakaj ločen pretvornik?

Responses API je novi format OpenAI s **pogovori s stanjem** (`previous_response_id`). Ko odjemalec pošlje zahtevo Responses, OmniRoute:

1. Interno pretvori Responses → Chat Completions
2. Pošlje ponudniku (kateremu koli ponudniku, ki podpira Chat Completions)
3. Pretvori odgovor nazaj v format Responses
4. Pretočno pošlje pretvorjeni odgovor odjemalcu

Pretvornik (`transformer/responsesTransformer.ts`) zagotavlja:

```ts
createResponsesApiTransformStream(): TransformStream
```

Ta obravnava:

- dogodke `response.output_item.added`
- dogodke `response.output_text.delta`
- dogodek `response.completed`
- Preslikavo klicev orodij (`function_call` ↔ `tool_calls`)

## Konfiguracija

`open-sse/config/` vsebuje konfiguracijski sloj:

| Datoteka                      | Namen                                                 |
| ----------------------------- | ----------------------------------------------------- |
| `providerRegistry.ts`         | Register modelov klepeta prek kataloga 394 ponudnikov |
| `providerModels.ts`           | Vzdevki modela, preslikava formata                    |
| `constants.ts`                | Časovne omejitve, omejitve, statusne kode             |
| `defaultThinkingSignature.ts` | Privzeti podpis razmišljanja Claude                   |
| `modelStrip.ts` (v storitvah) | Odstranjevanje polja na ponudnika                     |

### Shema registra ponudnika

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Validacija Zod pri nalaganju modula zagotavlja, da so vse konfiguracije ponudnika veljavne.

## Omejitve zmogljivosti

Usmerjevalni mehanizem ima strogo določene zmogljivostne omejitve:

| Operacija                                             | Cilj  | Meritev                        |
| ----------------------------------------------------- | ----- | ------------------------------ |
| Razreševanje kombinacij                               | <10ms | Za 50 ciljev                   |
| Preverjanje omejitve hitrosti                         | <1ms  | Žetonovni vedro v pomnilniku   |
| Nadomestni model iz družine modelov                   | <5ms  | Predpomnjene definicije družin |
| Posredovanje zahteve v usmerjanje                     | <2ms  | Kritična pot                   |
| **Brez blokirajočega V/I v kritični poti usmerjanja** | —     | Vse je asinhrono               |

## Vzorci, ki se jim je treba izogibati

❌ **Sinhroni klici podatkovne zbirke v `combo.ts`** — vnaprej izračunajte in predpomnite
❌ **Logika ponovnih poskusov v obdelovalnikih** — uporabite `retry()` iz storitve za odpornost
❌ **Neposreden dostop do konfiguracije ponudnika** — uporabite metode za pridobivanje iz `providerRegistry`
❌ **Trdo kodirane verige nadomestnih možnosti** — definirajte jih v `modelFamilyFallback.ts`
❌ **Spreminjanje stanja med sočasnimi zahtevami** — uporabljajte samo kontekst z obsegom zahteve

## Dodajanje nove komponente

### Dodajanje nove storitve

1. Ustvarite `open-sse/services/[serviceName].ts` z jasno opredeljeno odgovornostjo
2. Izvozite glavno funkcijo obdelovalnika in vse konstante
3. Dodajte teste enot v `tests/unit/services/[serviceName].test.mjs`
4. Integrirajte jo v cevovod zahtev v `handlers/chatCore.ts` (če je povezana z usmerjanjem)
5. Posodobite logiko usmerjanja v `combo.ts`, če storitev vpliva na izbiro cilja
6. Dokumentirajte jo v tej datoteki

### Dodajanje novega izvajalnika

1. Ustvarite `open-sse/executors/[provider].ts`, ki razširja `BaseExecutor`
2. Registrirajte ga v `config/providerRegistry.ts`
3. Dodajte ga v tovarniško funkcijo v `executors/index.ts`
4. Dodajte teste enot za izvajalnik
5. Dokumentirajte ga v `docs/architecture/ARCHITECTURE.md`

### Dodajanje novega orodja MCP

1. Ustvarite ali posodobite `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definirajte shemo Zod za vhode
3. Registrirajte orodje v `mcp-server/index.ts`
4. Dodajte ga v matriko obsegov v `mcp-server/auth/`
5. Dodajte teste enot
