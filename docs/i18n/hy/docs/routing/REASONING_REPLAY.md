> **Ճշմարտության աղբյուրը.** `src/lib/db/reasoningCache.ts`, `open-sse/services/reasoningCache.ts`** Վերջին թարմացումը՝** 2026-06-28 — v3.8.40

OmniRoute ֆիքսում է օգնական `reasoning_content` որը արտադրվում է մտածողության ռեժիմի մոդելների կողմից և թափանցիկ կերպով վերարտադրում է այն բազմակի շրջադարձային հարցումների դեպքում, երբ դա պահանջում է վերին հոսքի մատակարարը: Սա վերացնում է HTTP 400 սխալները, որոնք խիստ պրովայդերները բարձրացնում են, երբ հաճախորդի խոսակցությունների պատմությունը բացակայում է նախորդ հերթի պատճառաբանությունը:

## Ինչու Սա գոյություն ունի

Մտածողության ռեժիմի մի քանի մատակարարներ մերժում են հետագա շրջադարձը, եթե դա** Օգնականի նախորդ հաղորդագրությունը ներառում է բնօրինակ `reasoning_content`** . Վերին հոսքը վերադարձնում է 400 հաղորդագրություններով, ինչպիսիք են.

```
Param Incorrect: The reasoning_content in the thinking mode must be passed back to the API.
```

Բայց տիպիկ հաճախորդները (Cursor, Cline, Roo Code, OpenAI SDK) հեռացնում են `reasoning_content` իրենց վերարտադրման պատմությունից: OmniRoute վերականգնում է այն սերվերի կողմի քեշից, որպեսզի այն հարցումը, որը տեսնում է հոսանքին հակառակ, համահունչ լինի: Թիվ #1628-ը ներկայացրեց հիբրիդային memory/SQLite կայունությունը, որպեսզի քեշը պահպանի գործընթացի վերագործարկումը:

## Ճարտարապետություն

```
Turn N (assistant generates):
  → response contains reasoning_content + tool_calls
  → if requiresReasoningReplay(provider, model): cacheReasoningFromAssistantMessage()
      writes (memory + DB), keyed by every tool_call.id
  → forward response to client (which may or may not retain reasoning)

Turn N+1 (client sends follow-up):
  → translator detects: requiresReasoningReplay(provider, model) === true
  → for each assistant message with tool_calls and no reasoning_content:
      lookupReasoning(toolCalls[0].id) → memory → DB
      hit  → msg.reasoning_content = cached; recordReplay()
      miss → msg.reasoning_content = "" (legacy fallback for older DeepSeek)
  → upstream sees consistent history → no 400
```

Գրավումը տեղի է ունենում `open-sse/handlers/chatCore.ts` ում (երկու կայք, երկու `cacheReasoningFromAssistantMessage` զանգի կայքերում): Կրկնումը տեղի է ունենում `open-sse/translator/index.ts` ում սխեմայի հարկադրանքից հետո, բայց նախքան ուղարկումը:

Օգնականի պարզ (ոչ գործիքային) շրջադարձերը ստեղնավորված են այլ կերպ. `buildAssistantMessageCacheKey()` մարսում է նիստի շրջանակը, գումարած մինչև այդ շրջադարձը նորմալացված OpenAI ձևաչափի տառադարձումը, քանի որ DeepSeek պահանջում է _every_ նախորդ հերթի հիմնավորումը, երբ `tools` առկա է: Responses-API թիրախների համար (օրինակ `opencode-go/deepseek-v4-flash`, ուղղորդված դեպի `/responses`) վերին հոսքի մարմինը կրում է `input`, ոչ թե `messages`, այնպես որ `translateRequest()` (`open-sse/translator/index.ts`) հաղորդում է առանցքային տառադարձումը, որը մարսվել է հետ կանչի տարբերակի միջոցով, և գրավման կայքերը մարսում են այդ նույն տառադարձումը: Responses replay pass-ը աշխատում է OpenAI առանցքում յուրաքանչյուր աղբյուրի ձևաչափի համար, այնպես որ Anthropic Messages-ի հաճախորդները (Claude → OpenAI → Responses) նույնպես վերարտադրվում են:

## Պահպանման — հիբրիդային հիշողություն + SQLite

Թեժ ուղին օգտագործում է հիշողության մեջ `Map` (LRU-by-creation)՝ ապահովված SQLite աղյուսակով՝ վթարի վերականգնման և վահանակի տեսանելիության համար:

| Շերտ         | Իրականացում                                   | Նպատակը                                                                |
| ------------ | --------------------------------------------- | ---------------------------------------------------------------------- |
| Հիշողություն | `Map` ի `open-sse/services/reasoningCache.ts` | Արագ որոնումներ, վտարում է ամենահինը՝ 200 տարեկան                      |
| DB           | `reasoning_cache` սեղան (`src/lib/db/`)       | Պահպանում է վերագործարկումների ընթացքում, ապահովում է վիճակագրությունը |

Գրում է երկուսին էլ։ Սկզբում կարդում է խորհրդակցել հիշողության հետ, այնուհետև վերադառնում է DB (DB հիթերը կրկին վերականգնվում են հիշողության մեջ): DB ձախողումները ոչ ճակատագրական են — հիշողության քեշը շարունակում է սպասարկել տաք ուղին:

**Կանխադրվածներ:**

- TTL: `2h` (`TTL_MS = 2 * 60 * 60 * 1000`)
- Հիշողության առավելագույն մուտքերը՝ `200` (`MAX_MEMORY_ENTRIES`)
- Վտարում. ամենահին `createdAt` նախ

## REST API

## Գործառնական նշումներ

- **Մաքրում:** `cleanupReasoningCache()` մաքրում է ժամկետանց հիշողության գրառումները և գործարկում `DELETE FROM reasoning_cache WHERE expires_at <= unixepoch('now')`: Առողջության ստուգման աշխատողները պարբերաբար զանգահարում են դրան:
- **Վթարի վերականգնում.** Վերագործարկումից հետո հիշողությունը դատարկ է, սակայն DB դեռևս պահում է չսպառված գրառումները: Առաջին որոնումը տրված `tool_call_id` համար DB հարվածն է. հետագա որոնումները հիշողության հարվածներ են:
- **Ոչ հիմնավորում, ոչ քեշ.** `cacheReasoningFromAssistantMessage` վերադարձնում է `0` երբ օգնականի հաղորդագրությունը չունի `reasoning_content` / `reasoning` դաշտ, ուստի չմտածող պատասխանները ոչինչ չեն արժենա:
- **Գրել նաև փակված է.** երկու զանգերի կայքերը `chatCore.ts` ում (չհոսքային և հոսքային) զանգում են `cacheReasoningFromAssistantMessage()` միայն այն դեպքում, երբ `requiresReasoningReplay(provider, model)` `true` — նույն պրեդիկատը, որը ստուգում է ընթերցված կողմը: Տեղադրումները, որոնք երբեք չեն դիպչում վերարտադրող մատակարարին, դադարում են վճարել գրելու, ինդեքսի թարմացման և try/catch համար յուրաքանչյուր պատճառաբանող պատասխանի համար:
- **Ոչ խիստ մատակարարներ.** Երբ `requiresReasoningReplay` `false` է, իսկ թիրախային ձևաչափը՝ OpenAI, թարգմանիչը** շերտեր** ցանկացած `reasoning_content` դաշտ ելքային հաղորդագրություններից — OpenAI Զրույցի ավարտումները չի ընդունում այն:

## Muse Անթափանց-պատճառաբանության սեփականություն

Muse (`muse-code`) վերադարձնում է զանգահարողին կապված անթափանց պատճառաբանությունը (`encrypted_content`): Մեկ այլ հաշվի կամ հիշվող հավատարմագրով այն վերարտադրելը ձախողվում է հոսանքին հակառակ, այնպես որ հայրենի OAuth հարցումները օգտագործում են նիստի մակարդակի սեփականության իրավունքը՝ յուրաքանչյուր հարցումով ռոտացիայի փոխարեն (`src/sse/services/museSessionOwnership.ts`, ուժի մեջ է `src/sse/handlers/chat.ts` ում): Բացահայտորեն ընտրված API-բանալինների միացումները և միայն API-բանալին կազմաձևերը պահպանում են իրենց գոյություն ունեցող երթուղին առանց սեփականության այս ռեժիմի:

- Ապահովեք կայուն նստաշրջան ID յուրաքանչյուր հերթափոխում՝ `x-omniroute-session-id`, `x-omniroute-session`, `x-session-id` կամ `x-codex-session-id`; որպես այլընտրանք օգտագործեք `prompt_cache_key`, `session_id`, `conversation_id` կամ `metadata.session_id` մարմնում (այդ գերակայության կարգով): Բացակայում է կամ դատարկ IDs վերադարձնում է 400, երբ երկու կամ ավելի բնիկ OAuth հաշիվներ ակտիվ են. մեկ OAuth հաշվում պտտվելու ոչինչ չկա, ուստի նման հարցումը շարունակում է չամրացված երթուղին: Շրջանակը ներառում է զանգահարողի OmniRoute API-ստեղն ID.
- Թարմ անկախ նիստերը շրջանցվում են ակտիվ բնիկ OAuth հաշիվներում, որոնք թույլատրված են API-բանալին միացման քաղաքականության համաձայն՝ պատվիրված ID կապով: Շրջանակային ռեժիմով բաց է թողնում հաշիվները կապի սառեցման ժամանակ, տերմինալային կարգավիճակով (`banned`, `expired`, `credits_exhausted`), կամ մոդելով կողպված է պահանջվող մոդելի համար. Muse-ի հոսանքին հակառակ ձախողումները գրանցում են սառեցման և անջատիչի վիճակը, ինչպես մյուս մատակարարները: Հստակորեն հարկադրված կապը շրջանցում է շրջանաձև ռեժիմը նոր աշխատաշրջանի համար, բայց չի կարող անտեսել գոյություն ունեցող սեփականատիրոջը:
- Քանի դեռ սեփականատերը չի ստացել հաջող պատասխան, աշխատաշրջանը, որի սեփականատերը դարձել է անհասանելի, կրկին բողոքարկվում է առողջ հաշվի վրա: Առաջին հաջող պատասխանից հետո նիստը կցված է մնում այդ սեփականատիրոջը, մինչև այն անգործուն մնա 30 օր (`MUSE_SESSION_IDLE_TTL_MS`):
- Շարունակության և գործիքի արդյունքի յուրաքանչյուր հերթափոխ մնում է աշխատաշրջանի սեփականատիրոջը. կապը, հաշվի ինքնությունը և եզրակացության հավատարմագրերի ստեղծումը, նորից ստուգվում են մինչև վերին հոսքի փորձերը, ներառյալ հավատարմագրերի թարմացման կրկնությունները: Պատասխանները կանչում են IDs/item հղումներ և Զրույցի ավարտման գործիք՝ IDs զանգը պետք է գրանցված լինեն այդ նստաշրջանի և սերնդի համար:
- SQLite `key_value` գրառումները `muse_session_ownership` անվանատարածքում (`src/lib/db/museSessionOwnership.ts`) պահպանում են սեփականության իրավունքը և պտտման կուրսորը վերագործարկումների ընթացքում: Յուրաքանչյուր հայցի և մատուցված պատասխանը թարմացնում է նիստի գործունեության դրոշմը. `MUSE_SESSION_IDLE_TTL_MS` ից երկար պարապ նիստն էտվում է (սեփականատիրոջ փին, մատուցվող դրոշակ և գրանցված opaque/reference հեշեր), առավելագույնը 10 րոպեն մեկ և սահմանափակ խմբաքանակներով, ուստի դրա պատմության ավելի ուշ կրկնությունը չի փակվում որպես անհայտ սեփականատեր: Գրառումները պարունակում են կապի IDs և հաշվի ինքնության հեշեր, հավատարմագրեր, անթափանց բովանդակություն և շարունակական հղումներ, ոչ թե գաղտնիքներ կամ խոսակցությունների պատմություն: Հաճախորդները պետք է պահպանեն և ուղարկեն իրենց ամբողջական պատմությունը և անթափանց պատճառաբանությունը:
- Անհայտ կամ արտասահմանյան անթափանց պատճառաբանությունը, անհայտ կորած սեփականատերը, անհասանելի սեփականատիրոջ հաշիվը կամ գրանցված պատմությամբ սերնդափոխությունը ձախողվում է բացահայտ 4xx/503 — երբեք լուռ խաչաձև հաշվի ձախողմամբ և երբեք չհեռացված պատճառաբանությամբ:
- Հիշեցված նույն հաշվի բանալին ընդունվում է միայն այն դեպքում, երբ նիստը չի գրանցել կրկնվող պատմություն; ձայնագրված նիստերը շարունակում են փակվել մինչև թարմացումները:
- Հոսանքից դուրս գտնվող դատարկ պատասխանը (`upstream_empty_response` / `empty_response`, զանգահարողին ոչինչ չի ուղարկվում) առավելագույնը երկու անգամ փորձարկվում է նույն սեփականատիրոջ վրա՝ 0,5 վրկ հետո, ապա 1,5 վրկ (`MUSE_EMPTY_RESPONSE_RETRY_DELAYS_MS`): Եթե բոլոր փորձերը դատարկ են, օրիգինալ 502-ը վերադարձվում է առանց սառեցման կամ անջատիչի նշագրման, այնպես որ շերտավոր պատասխանը երբեք չի արգելափակում սեփականատիրոջը:
- Բոլոր `muse-code` հարցումները շրջանցում են իմաստային քեշի ընթերցումները և գրությունները, ներառյալ հոսքային գրությունները, ուստի քեշավորված անթափանց ելքը չի կարող ձեռք բերել այլ նստաշրջանի սեփականատեր:
