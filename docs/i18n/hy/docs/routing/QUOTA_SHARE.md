## Ընդհանուր նկարագրություն

Քվոտաների համօգտագործման շարժիչը մատակարարի՝ ժամանակի վրա հիմնված քվոտան (օրինակ՝ Codex-ի
5-ժամյա պատուհանը, Kimi-ի 1500 հարցում/ժամը) արդարացիորեն բաշխում է միևնույն
միացումը համօգտագործող մի քանի API բանալիների միջև։

**Լուծվող խնդիրը.** OmniRoute-ը բազմաթիվ API բանալիների հարցումները պրոքսիավորում է դեպի միևնույն վերին մակարդակի
մատակարարի հաշիվ։ Առանց համօգտագործման տրամաբանության՝ A բանալուց հարցումների կտրուկ աճը կարող է սպառել
մատակարարի ժամային քվոտան՝ B և C բանալիներն արգելափակված թողնելով մինչև պատուհանի զրոյացումը։
Շարժիչը կանխում է դա՝

1. Հետևելով յուրաքանչյուր բանալու սահող սպառմանը՝ ըստ չափման միավորի (%, հարցումներ, թոքեններ, $)։
2. Կիրառելով աշխատանքը պահպանող արդար բաժանման ալգորիթմ. բանալին կարող է փոխառել չօգտագործվող
   բաժիններից, քանի դեռ ընդհանուր պաշարը հագեցած չէ։
3. Արդյունքը կիրառելով թեժ ուղում (`chatCore.ts`)՝ նախքան հարցումը
   կհասնի վերին մակարդակի կատարիչին։

## Ալգորիթմ. Արդար բաշխում աշխատանքի պահպանում

Իրականացվել է `src/lib/quota/fairShare.ts` ում:

### Ռեժիմներ

| Վիճակ                                      | Ռեժիմ         | Վարքագիծ                                                                  |
| ------------------------------------------ | ------------- | ------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **Առատաձեռն** | Բանալին կարող է վերցնել մինչև գլոբալ սահմանաչափը հանած սպառված-ընդհանուրը |
| `globalUsedPercent >= saturationThreshold` | **Խիստ**      | Խստորեն կիրառել անհատական արդար բաժնեմասը                                 |

Կանխադրված `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`):

Այս երկու ռեժիմները նկարագրում են լողավազան լռելյայն փոխառության ռեժիմում, `saturation`: `consent` ռեժիմով լողավազանը միշտ կիրառում է խիստ կանոններ, անկախ նրանից, թե որքան է հագեցվածությունը: Տես [«Համաձայնեցված վարկավորում» (յուրաքանչյուր լողավազանի մասնակցության համար)](#consented-lending-per-pool-opt-in) :

### Չափման որոշում

Լողավազանի յուրաքանչյուր ակտիվ չափման համար շարժիչը հաշվարկում է.

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent` չափումների համար `consumed` դրա փոխարեն գալիս է վերագրման գրքից (տես [Տոկոսային չափումներ. մեկ բանալին վերագրում](#percent-dimensions-per-key-attribution) ):

Ապա.

- **`policy = hard`** եթե `consumed > fairShareAllowed` և ռեժիմը խիստ → է** արգելափակել** .
- **`policy = soft`** եթե `consumed > fairShareAllowed` և ռեժիմը խիստ → է** պատժել** (անհրաժեշտ է համակցված, երբեք կոշտ արգելափակում):
- **`policy = burst`** թույլատրել, քանի դեռ գլոբալ տարածքը գոյություն ունի՝ անկախ արդար բաժնեմասից:

### Բացարձակ գլխարկ

`capValue` + `capUnit` բաշխման վրա կոշտ առաստաղ է՝ անկախ ռեժիմից կամ քաղաքականությունից: Ցանկացած հարթություն, որտեղ `consumed >= capValue` միշտ** բլոկներ** խնդրանքը։ `percent` գլխարկի համար `consumed` միայն բանալիին վերագրվող մասն է:

### Բազմաչափ ստուգում

Հարցումն արգելափակված է, եթե** ցանկացած** չափսերը լողավազանում կփակեն այն: Չափերը անկախ են — 5h% սպառումը չի ազդում շաբաթական% չափի վրա:

### Փոխառություն

Առատաձեռն ռեժիմում բանալին, որի տեղաբաշխումը քիչ է սպառվում, կարող է օգտագործել այլ բանալիների չբաշխված բաժնետոմսերի ավելցուկը: Բանաձևը հետևյալն է.

```
maxAllowed = globalLimit - consumedByOtherKeys
```

որտեղ `consumedByOtherKeys = consumedTotal - consumedByThisKey`. Teto գլոբալը (pool `limit` այդ հարթության համար) միշտ կոշտ առաստաղ է:

### Համաձայնեցված վարկավորում (յուրաքանչյուր խմբի մասնակցության համար)

Յուրաքանչյուր լողավազան ունի փոխառության ռեժիմ: `saturation` լռելյայն է և պահպանում է վերը նշված կանոնները: `consent` ռեժիմում `hard` ստեղնը փոխանցում է իր մասնաբաժինը միայն այն հզորության չափով, որը մյուս ստեղները համաձայնել են տալ: Ադմինիստրատորը սահմանում է յուրաքանչյուր լողավազանի ռեժիմը: Յուրաքանչյուր բանալի սեփականատեր սահմանում է իր սեփական համաձայնությունը [Վարկավորման համաձայնության](#lending-consent) միջոցով:

Համաձայնությունը 0-ից 100 տոկոս է և կամընտիր վերջնաժամկետ՝ դարաշրջանի միլիվայրկյաններով: Բանալին տալիս է իր անգործուն մասնաբաժնի այդ տոկոսը, քանի դեռ վերջնաժամկետն ապագայում է:

Մեկ հարթության համար `L` արդյունավետ սահմանն է. պլանի սահմանաչափը բազմապատկվում է լողավազանի հաշիվների վրա: Դարպասը հաշվարկում է պահանջվող բանալու համար.

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` `lend_k` քաշն է, կամ `100 / n` յուրաքանչյուր ստեղնի համար, երբ կշիռը 0-ից բարձր չէ: Բանալին հայցող սեփական համաձայնությունը երբեք չի հաշվվում: `hard` ստեղնը մերժվում է, երբ դրա սպառումը հասնում է իր մասնաբաժնի գումարած `borrowAvailable`:

Հզորությունը, որը ոչ մի տեղաբաշխում չի պահանջում (100 հանած կշիռների գումարը) փոխառության ենթակա չէ: Ոչ մի բանալի չի համաձայնվել այն փոխառել:

**Օրինակ.** `L` 1000 է:

| Բանալին | Քաշը | Կիսվել | Սպառված | Պարտավորում է |
| ------- | ---- | ------ | ------- | ------------- |
| Ա       | 50   | 500    | 530     | 0%            |
| Բ       | 30   | 300    | 100     | 50%           |
| Գ       | 0    | 0      | 60      | 0%            |

- B-ն պարտք է տալիս իր պարապ 200-ի 50%-ը, որը 100 է: A կարող է պարտք վերցնել 40.
- Ա-ն մատուցվում է 530-ով և հրաժարվում է, երբ սպառումը հասնում է 540-ի։
- Մինչ C-ն որևէ բան կօգտագործեր, A-ն իր մասնաբաժնի չափով կամ պակասով, C-ն կարող էր փոխառել 100-ը:
- Մինչ C-ն որևէ բան կօգտագործեր, երբ A-ն 530-ում էր, C-ն կարող էր վերցնել 70-ը:

**Զրո քաշ.** 0 քաշով բանալին ունի 0 մասնաբաժին: Այն մատուցվում է միայն այն ժամանակ, երբ դրա սպառումը ցածր է, քան մյուսները տալիս են: Երբ ոչ ոք պարտք չի տալիս, մերժվում է առաջին իսկ խնդրանքից։

**Վերջնաժամկետներ.** Ոչ մի ֆոնային առաջադրանք չի սպառվում համաձայնության: Յուրաքանչյուր հարցում վերջնաժամկետը համեմատում է իր ժամանակի հետ, և այդ ժամանակին հավասար ժամկետ է անցել: Պահված վերջնաժամկետը, որը վերջավոր թիվ չէ կամ լրացել է `Date` ամենամեծ ամսաթիվը, համարվում է անցած:

**`soft` եւ `burst`.** Վարկավորումը նրանց չի սահմանափակում։ `soft` ստեղնը զրկվում է առաջնահերթությունից, երբ անցնում է իր մասնաբաժինը: A `burst` բանալին անցնում է, մինչ լողավազանը տեղ ունի: Լողավազանի առաստաղը շարունակում է մերժել յուրաքանչյուր բանալին, երբ լողավազանի ընդհանուր գումարը հասնում է իր սահմանին:

**Արժեքը հարցման ուղու վրա:** `saturation` լողավազանն ավելին չի կարդում, քան նախկինում: `consent` լողավազանում հաշվելի չափումը կարդում է մյուս ստեղները միայն `hard` ստեղնի համար իր մասնաբաժնի վրա կամ ավելի բարձր, մինչդեռ մեկ այլ բանալին փոխում է: Այնուհետև այն զուգահեռաբար կատարում է մեկ այլ բանալի ընթերցում: Անհաջող ընթերցումը հաշվվում է որպես 0 սպառում այդ բանալի համար: `percent` չափումը չի ավելացնում կարդալ, քանի որ վերագրման գիրքը պահում է բոլոր բանալիները:

**Լողավազանի խմբագրում.** Խմբագրումը պահպանում է մնացած ստեղների համաձայնությունը: Սա վերաբերում է տեղաբաշխման փոփոխություններին, ամբողջ խմբի փոխարինմանը և `ensure` զանգերին: Հեռացված բանալին կորցնում է իր համաձայնությունը, և հետ ավելացված բանալին սկսվում է 0-ից: Ադմինիստրատորի երթուղիները վերադարձնում են յուրաքանչյուր բանալի համաձայնությունը և երբեք չեն գրում այն: Լողավազանը հետ `saturation` ին փոխելը պահպանում է յուրաքանչյուր պահված համաձայնությունը, որն այդ ռեժիմում որևէ ազդեցություն չունի: Լողավազանը կրկին `consent` ին անցնելը նորից ակտիվացնում է պահված համաձայնությունները, որոնց վերջնաժամկետը չի լրացել: Բանալին կրողը կարող է մաքրել պահված համաձայնությունը ցանկացած ռեժիմում:

**Արդիականացում.** Եթե `lending_percent` և `lending_until` սյունակներն արդեն գոյություն ունեն, միգրացիան ավելացնում է միայն `borrow_mode`, և պահված տոկոսները մնում են այնպես, ինչպես կան: Յուրաքանչյուր լողավազան սկսվում է `saturation` ռեժիմով: Միացրեք `consent` լողավազանի հրաշագործի յուրաքանչյուր լողավազանում: Պահված արժեքներից ոչինչ չի ենթադրվում:

**Սահմանափակումներ.**

- Վարկատուն կարող է գտնել լողավազանն իր առաստաղի մոտ՝ նախքան իր սեփական մասնաբաժինը օգտագործելը: Ուրիշների փոխառած հզորությունը հաշվվում է լողավազանի ընդհանուր ծավալում:
- Չեկը գործում է մինչև հարցումը և ոչինչ չի պահում: Միաժամանակյա հարցումները կարդում են սպառումը նախքան որևէ մեկի գրանցումը, ուստի տրված թողունակությունը կարող է ծախսվել մեկից ավելի անգամ՝ սահմանափակված թռիչքի ժամանակ կատարվող հարցումներով: Նույն հատկությունն ունի `saturation` ռեժիմի բաժնետոմսերի ստուգումը։

## Սահող պատուհանի հաշվիչ

Իրականացված է `src/lib/quota/sqliteQuotaStore.ts`-ում և `redisQuotaStore.ts`-ում։

Երկու հատված յուրաքանչյուր `(apiKeyId, dimensionKey)`-ի համար՝

- `curr`՝ ընթացիկ հատված (`floor(nowMs / windowMs)`)
- `prev`՝ նախորդ հատված (`curr - 1`)

Արդյունավետ սահող արժեքը՝

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**Ճշգրտություն**՝ մոտ 99%։ Սխալն առավելագույնը պատուհանի չափի 1%-ն է՝
հատվածների սահմանի մոտ (երկու հատվածով մոտարկման անխուսափելի հետևանք)։

### Զուգահեռություն

SQLite դրայվեր. `(apiKeyId | dimensionKey)` յուրաքանչյուր բանալու համար հիշողության մեջ պահվող mutex-ը կանխում է
կարդալ-փոփոխել-գրել մրցավիճակը։ Կաղապարը կրկնում է `src/sse/services/auth.ts`-ի՝ միաժամանակյա զանգվածային հարցումները կանխելու մոտեցումը։

Redis դրայվեր. ատոմային ավելացման համար օգտագործվում է Lua EVAL սկրիպտ, որն աշխատում է որպես մեկ Redis հրաման։

## Դրայվերներ

### SQLite (լռելյայն, տեղադրում չի պահանջվում)

- Աղյուսակ՝ `quota_consumption` (տե՛ս `073_quota_pools.sql` / `074_quota_consumption.sql` միգրացիաները)։
- Լավագույնն է մեկ ինստանսով տեղակայումների համար։
- Բոլոր տվյալները պահպանվում են գոյություն ունեցող OmniRoute SQLite ՏԲ-ում (`DATA_DIR/storage.sqlite`)։

### Redis (ըստ ցանկության, բազմաինստանս)

- Պահանջում է `ioredis` npm փաթեթը։
- Հաշվիչները պահվում են Redis-ում, իսկ մետատվյալները (փուլերը/բաշխումները)՝ դեռևս SQLite-ում։
- Լավագույնն է մի քանի ռեպլիկայով տեղակայումների համար, երբ հաշվիչները պետք է համօգտագործվեն։

### Դրայվերների փոխարկում

Կարգավորումների միջերեսի միջոցով (`/dashboard/settings` → Quota Store) կամ միջավայրի փոփոխականների միջոցով՝

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

ՏԲ-ի կարգավորումն առաջնահերթ է միջավայրի փոփոխականի նկատմամբ։ Եթե `driver=redis`, բայց URL-ը բացակայում է կամ
`ioredis`-ը տեղադրված չէ, ֆաբրիկան անցնում է SQLite-ի և գրանցում նախազգուշացում։

Դրայվերի ընտրության հերթականությունը՝

1. ՏԲ-ի `quotaStore.driver` կարգավորումը
2. Միջավայրի `QUOTA_STORE_DRIVER` փոփոխականը
3. Լռելյայն՝ `sqlite`

## Բազմաչափ

Լողավազանը կարող է ունենալ մի քանի չափսեր: Յուրաքանչյուր հարթություն անկախ է.

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**Օրինակ՝ Codex plan** (5h% + շաբաթական%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

Հարցումը պետք է բավարարի բոլոր չափերը, որպեսզի թույլատրվի:

### Տոկոսային չափսեր՝ մեկ բանալու վերագրում

Տոկոսային պլանը հաղորդում է մեկ օգտագործման ցուցանիշ յուրաքանչյուր հաշվի և պլանի պատուհանի համար: Պրովայդերը ոչ մի հաշվիչ չի տալիս API ստեղնի համար:

Այդ թիվը բանալիների միջև բաժանելու համար յուրաքանչյուր լողավազան պահում է վերագրման գիրք յուրաքանչյուր հաշվի և պլանի պատուհանի համար: `src/lib/quota/percentLedger.ts` պահպանում է գրքի կանոնները: `src/lib/quota/percentAttribution.ts` գիրքը վերածում է այն թվերի, որոնք օգտագործում են հարկադիր կատարողները: Արդյունքը յուրաքանչյուր հիմնական երթուղիների նշաններից կառուցված գնահատական է:

#### Ընթերցումներ, որոնք շարժում են գիրքը

Գիրքը շարժվում է միայն մատակարարի սեփական գործչի վրա՝ պահանջվող պլանի պատուհանի համար: Այս կապերը հաղորդում են մեկին.

| Մատակարար                  | Պլանավորեք պատուհանները |
| -------------------------- | ----------------------- |
| Claude, OAuth կապի միջոցով | `5h`, `weekly`          |
| Codex                      | `5h`, `weekly`          |

Սրանք չեն համարվում ընթերցում.

- պատասխանը, որը մատակարար հաճախորդը նշում է որպես հնացած
- Claude պատուհան, որի տոկոսը մատակարարը չի հայտնել
- մեկ այլ պատուհանի գործիչ, կամ ամենավատ դեպքը պատուհանների միջով
- փոխարժեքի սահմանաչափի վերնագրի վերադարձը
- անհաջող ընթերցում

Այլ մատակարարներ, ներառյալ Claude API բանալիով, գիրք չունեն: Յուրաքանչյուր բանալի գանձվում է 0-ով իրենց տոկոսային չափերով, ինչպես մինչ այս փոփոխությունը:

Ընթերցումը կիսում է հագեցվածության ազդանշանի 30 վայրկյանանոց քեշը: Claude ընթերցումը թվագրվում է այն պահով, երբ ցուցանիշը դիտարկվել է պատասխան վերնագրերում կամ կարդացվել է օգտագործման վերջնակետից, երբ այդ ժամանակը հայտնի է: Մյուս ընթերցումները թվագրվում են այն պահով, երբ ստեղծվել է այդ քեշի մուտքը:

#### Այն, ինչ պահպանում է գիրքը

Յուրաքանչյուր գրանցված հարցում մեկ անգամ ավելացնում է իր նշանները հաշվիչին յուրաքանչյուր լողավազանի, հաշվի և բանալիի համար: Հաշվիչը միայն աճում է: Գիրքը պահպանում է երեք բան.

- ելակետային գիծ. այն թիվը, երբ գիրքը բացվեց կամ պատուհանը վերջին անգամ շրջվեց
- վերջին կիրառված ցուցանիշը
- մեկ բանալիով, նրա նշանային հաշվիչը նույն պահին կանչեց իր նշանը

Գիրքը թարմացվում է, երբ կիրարկումը կամ օգտագործման երթուղին հաշվարկում է վերագրումը: Գրությունները համեմատվում և տեղադրվում են վերանայման համարի վրա: Գրողը, որը պարտվում է, մեկ անգամ նորից է փորձում նոր ընթերցմամբ:

#### Ինչպես է հաշվարկվում բանալու մասը

Յուրաքանչյուր բանալի մասը հաշվարկվում է գիրքը կարդալիս: Նկարի աճը, քանի որ բազային գիծը բաժանված է ստեղների միջև՝ յուրաքանչյուրը իր նշանից ի վեր ուղղված նշանների համամասնությամբ:

Together, այդ նշանները բացատրում են թվի առավելագույնը մեկ կետ յուրաքանչյուր `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` նշանի համար (կանխադրված 1000): Աճը, որ նրանք չեն բացատրում, արտաքին է։ Հիմքը նույնպես արտաքին է:

Օրինակ, գիրքը բացվում է 0-ով: Բանալին A-ն այնուհետև ուղղում է 900,000 նշան, իսկ B բանալին՝ 100,000: 60 թվի դեպքում Ա-ի մասը 54 միավոր է, իսկ Բ-ի մասը՝ 6:

Բանալու նշանից ցածր հաշվիչը վերագործարկվել է և ամբողջությամբ հաշվում է: Առանց նշանի բանալին, ինչպես, օրինակ, պատուհանի մեջտեղում գտնվող լողավազանին միացող բանալին հաշվում է իր բոլոր նշանները: Նշաններին զիջող ցուցանիշը առաջացնում է սխալ, որը անհետանում է հաջորդ ընթերցման ժամանակ: Այն չի կուտակվում։

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` կարդացվում է յուրաքանչյուր վերագրման վրա: Արժեքը, որը առնվազն 1-ի վերջավոր թիվ չէ, հետ է ընկնում մինչև 1000:

#### Ինչպես է ընթերցումը փոխում գիրքը

Առաջին համապատասխանության կանոնը կիրառվում է.

1. **Դեռևս գիրք չկա.** ընթերցանությունը բացում է գիրքը: Դրա թիվը բազային է, և յուրաքանչյուր հաշվիչը նշված է:
2. **Ավելի հին ընթերցում.** վերջին կիրառվածից առաջ թվագրված ընթերցումը անտեսվում է: Այդպես է ընթերցումը, որի վերակայման ժամանակը ավելի քան 30 րոպե շուտ է, քան պահվածը:
3. **Նոր մատակարարի պատուհան.** վերակայման ժամանակը ավելի քան 30 րոպե ուշ, քան պահվածը շրջում է գիրքը: Նկարը դառնում է բազային, և յուրաքանչյուր հաշվիչը կրկին նշվում է: Առանց հաշվիչի բանալիները թողնում են գիրքը:
4. **Ավարտված պատուհան.** Վերակայման պահված ժամանակը, որը չի անցել ընթերցման տվյալների ժամանակից, նշանակում է, որ պատուհանն ավարտվել է: Ընթերցանությունը շրջում է գիրքը, անկախ նրանից, թե ինչ ցուցանիշ է:
5. **Ավելի բարձր ցուցանիշ.** շարժվում է միայն վերջին գործիչը: Հիմքը և նշանները մնում են:
6. **Նույն ցուցանիշը.** գործիչը, ելակետը և նշանները մնում են: Գրքում գրված է միայն վերակայման ժամանակը:
7. **Ստորին ցուցանիշ.** ավելի ցածր ցուցանիշ որպես այդպիսին երբեք չի կիրառվում: Այն շրջում է գիրքը միայն այն ժամանակ, երբ երեք բան պահում է: Այն առնվազն երկու րոպե ավելի նոր է, քան վերջին կիրառված ընթերցումը: Ոչինչ չի ասում, որ պատուհանը նույն բաց պատուհանն է: Այն ավելի քան մեկ միավորով ցածր է։

Պատուհանը հաշվվում է որպես նույն բացը, երբ երեք բան պահվում է: Վերականգնման երկու ժամանակներն էլ հայտնի են: Նրանք գտնվում են միմյանցից 30 րոպեի ընթացքում: Պահվածը դեռ ընթերցանությունից առաջ է։ Այդ պատուհանի ներսում ավելի ցածր ցուցանիշը ոչինչ չի փոխում:

Վերականգնման ժամանակը պահվում է միայն այն ժամանակ, երբ այն գերազանցում է այն փոխանցող ընթերցման տվյալների ժամանակին: Ավելի բարձր ցուցանիշը պահպանում է իր ընթերցման վերակայման ժամանակը, երբ այն օգտագործելի է, և պահում է պահվածը հակառակ դեպքում: Հավասար ցուցանիշը գրանցում է իր ընթերցման վերականգնման ժամանակը միայն այն դեպքում, երբ գիրքը չունի: Ուրիշ ոչինչ չի փոխում։ Ավելի ցածր ցուցանիշը, որը չի շրջում գիրքը, չի գրանցում վերակայման ժամանակ:

#### Երբ գիրքն օգտագործվում է

Ընթերցանությունից հետո գիրքն օգտագործվում է, եթե դրա վերակայման պահված ժամանակը չի անցնում ընթացիկ ժամից: Այդ դեպքն առաջանում է, երբ վերակայումից անմիջապես առաջ վերցված ընթերցումը, ինչպես օրինակ՝ քեշից մատուցված ընթերցումը, դիտվում է անմիջապես դրանից հետո:

Առանց օգտագործելի ընթերցման, պահված գիրքն օգտագործվում է միայն այն ժամանակ, երբ այն դեռ կարող է լինել ընթացիկ պատուհանի գիրքը: Դա վերաբերում է երկու դեպքում.

- դրա վերակայման ժամանակը հայտնի է և դեռ առջևում է
- այն չունի վերակայման ժամանակ, և վերջին ընթերցումը, որը փոխել է այն, ամենաշատը 15 րոպեի վաղեմություն ունի

Հակառակ դեպքում ոչինչ չի վերագրվում, ինչպես երբ գիրք չկա։ Այն գիրքը, որի վերակայման ժամանակն անցել է, երբեք չի գանձվում:

#### Հարկադիր կատարում

Բանալու սպառումը տոկոսային չափման վրա նրա վերագրվող մասն է, գումարած արտաքին մասի մասնաբաժինը: Արտաքին մասը նախ օգտագործում է հզորությունը, առանց բաշխման պահանջների (100 հանած կշիռների գումարը): Միայն ավելցուկը բաժանվում է բանալիների մեջ ըստ քաշի։

Այդ սպառումը համեմատվում է բանալու արդար բաժնեմասի հետ, ինչպես ցանկացած այլ հարթության դեպքում: Խիստ ռեժիմը դեռ սկսվում է, երբ հագեցվածության ազդանշանը հասնում է `QUOTA_SATURATION_THRESHOLD` (կանխադրված 0.5): Յուրաքանչյուր թիվ մասշտաբավորվում է արդյունավետ սահմանաչափով. յուրաքանչյուր հաշվի սահմանաչափը բազմապատկվում է ֆոնդում գտնվող հաշիվների քանակի վրա:

`capUnit: "percent"` ով բացարձակ գլխարկը հաշվում է միայն այն մասը, որը վերագրվում է բանալիին, որը մասշտաբավորվում է նույն կերպ: Վերցրեք մեկ հաշվի սահմանաչափը 100 և k հաշիվ: Այնուհետև հասնում է N-ի շեմը, երբ սպասարկող հաշվի թվի բանալի մասը հասնում է N/k կետերին: Յուրաքանչյուր հաշիվ ստուգվում է իր գրքում: Օրինակ, երկու հաշիվների դեպքում մեկ հաշվի ցուցանիշի 5 կետում հասնում է 10-ի սահմանաչափ:

Երբ խանութը հնարավոր չէ կարդալ, ոչինչ չի վերագրվում, և յուրաքանչյուր բանալի այդ հարթության վրա գանձվում է 0: Երբ գիրք գրելը ձախողվում է, այդ վերագրումն օգտագործում է գիրքն այնպես, ինչպես կարդացվել է: Նշանների ձախողման դեպքում այդ հարցումի նշանները դուրս են թողնում գրքից: Այս ձախողումներից ոչ մեկը չի արգելափակում հարցումը:

`consent` լողավազանում վարկավորման բանաձևը օգտագործում է յուրաքանչյուր բանալի սպառումը տոկոսային չափման վրա, ինչպես նկարագրված է վերևում: Երբ մեկ այլ բանալի է տալիս, գիրքը կարդում են մեկ անգամ և վերագրում յուրաքանչյուր բանալի: Առանց օգտագործելի գրքի յուրաքանչյուր բանալին լիցքավորվում է 0-ով: Քաշ ունեցող բանալին այնուհետև անցնում է, իսկ 0 քաշով բանալին անցնում է միայն այն ժամանակ, երբ մեկ այլ բանալի է տալիս:

#### Օգտագործման երթուղի

`GET /api/quota/pools/{id}/usage` հաղորդում է նույն թվերը նույն ֆունկցիայի միջոցով: Տոկոսային չափումը ունի մեկ մուտք մեկ լողավազանի միացման `accounts` ում: Դրա վերին մակարդակի `consumedTotal` և `perKey` արտացոլում են առաջին մուտքը:

Երթուղին կիրառում է նաև ընթացիկ ընթերցանությունը, այնպես որ այն կարող է առաջ տանել գիրքը, ինչպես խնդրանքը: `internal + external` կարող է տարբերվել `consumedTotal` ից, երբ չկա օգտագործելի ընթերցում, կամ երբ ավելի ցածր ցուցանիշ չի կիրառվում:

#### Պահպանում և պահպանում

Երկու քվոտա խանութները պահում են գիրքը: SQLite ում տվյալների բազայի ավտոմատ մաքրումը, երբ միացված է, հեռացնում է 60 օրվա ընթացքում չթարմացված տողերը: Redis ում լողավազանի միացման գրքերն ու հաշվիչները կիսում են մեկ բանալի: Դրա ժամկետը լրանում է 60 օր հետո, երբ վերջին նշանը գրելը կամ գիրքը փոխել. Գիրքը, որը չի փոխվում, չի վերաշարադրվում, ուստի կտրվածքը դրված է ամենաերկար պլանի պատուհանի վերևում: Օգտագործման պատմության ձեռքով զրոյացումը նաև մաքրում է SQLite ի գրքերը (տես Սահմանափակումներ):

#### Սահմանափակումներ

- Հաշվի ամբողջ աճը, քանի որ բազային գիծը բաժանվում է այն ժամանակվանից յուրաքանչյուր բանալին ուղղորդված նշաններով: Երբ այդ աճը տեղի ունեցավ, նշանակություն չունի։
- Այսպիսով, OmniRoute դուրս կատարված օգտագործումը գանձվում է ստեղների վրա այնքանով, որքանով թույլ են տալիս դրանց նշանները: Դա ներառում է այն օգտագործումը, որն արվել է նախքան պատուհանի բանալի առաջին պահանջը, երբ գիրքն արդեն բաց էր:
- Օրինակ, արտաքին օգտագործումը հաշիվը բարձրացնում է 60 միավորով, մինչդեռ առանցքային երթուղիներ չկան: Բանալին այնուհետև ուղղում է 30000 նշան և այդ թիվը հասնում է 60,6-ի:
- Եթե գիրքը բաց է եղել մինչ այդ օգտագործումը, ապա բանալին 30 միավոր է: Այն նաև կրում է արտաքին օգտագործման 7,65 միավոր, չորս ստեղներով՝ 25 քաշով:
- Եթե գիրքը բացվել է այդ օգտագործումից հետո, ապա 60 միավորները բազային են: Բանալին ունի 0,6 միավոր և կրում է արտաքին օգտագործման 15 միավոր:
- Խնդրանքը կամ այցելությունը օգտագործման երթուղին բացում է գիրքը: Այսպիսով, արդյոք նման օգտագործումը հաշվվում է որպես ելակետ, կախված է նրանից, թե երբ է բացվել գիրքը:
- Լռելյայն հատակով, բանալին, որը ուղղորդում է 60,000 նշան, մինչդեռ արտաքին օգտագործումը, բարձրացնում է հաշիվը 60 միավորով, ստանում է բոլոր 60-ը՝ որպես իր մաս:
- 50000 հարկով սեփական մասը 1,2 միավոր է։ Մնացած 58.8-ը արտաքին են և լիցքավորված են ըստ քաշի, ինչպես ցանկացած արտաքին օգտագործման:
- Սահմանեք `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` մոտ ձեր ծրագրի մեկ միավորի արժեքին: Արտաքին օգտագործումը ներառում է նույն հաշվի երթևեկությունը լողավազանից դուրս գտնվող բանալիներից:
- Տոկոսային շեմը կիրառվում է յուրաքանչյուր ռեժիմում: Ծածկված բանալին կարող է մերժվել, երբ հաշիվը շատ ցածր է հագեցվածության շեմից:
- Վերցրեք 10 և 12 կետերով արտաքին օգտագործման գլխարկ ավելի վաղ պատուհանում: Բանալին, որը ուղղորդում է 20,000 նշան, այնուհետև մերժվում է 12,4% հաշվի դեպքում:
- Պառակտումը գնահատական է ըստ խորհրդանշական ծավալի: Հարցումը հաշվվում է որպես դրա արագ նշան, գումարած դրա ավարտման նշաններ: Քեշի զեղչերը և մոդելի գները չեն փոխում այդ հաշվարկը:
- Հարցումը, որը չի ավարտվում 200 կարգավիճակով, չի գրանցում որևէ նշան: Օրինակներ են հոսքը, որը հաճախորդն անջատում է, և վերին հոսքի սխալ՝ օգտագործումից հետո:
- Նման խնդրանքով առաջացած օգտագործումը գանձվում է այն ստեղների վրա, որոնք ձայնագրել են թոքենները՝ ընդհուպ մինչև այն, ինչ թույլ են տալիս դրանց նշանները: Մնացածը արտաքին է։ Այն հետ չի շարժվում։ Արձագանքը, որը հաղորդում է ոչ մի նշանի օգտագործման մասին, նույնպես չի գրանցում որևէ նշան:
- Ընթացքի մեջ գտնվող հարցումի օգտագործումը կարող է ցուցադրվել մեկ այլ ակտիվ բանալու մասում՝ ամբողջ հարցման համար: Այն հետ է շարժվում միայն այն դեպքում, երբ հարցումն ավարտվում է 200 կարգավիճակով:
- Օգտագործումն արդեն հաշվում, երբ գիրքը բացվում է, համարվում է արտաքին: Սա ներառում է թարմացում, նոր լողավազան և նոր հաշիվ: Օգտագործումը նոր պատուհանում, նախքան դրա առաջին ընթերցումը, նույնպես համարվում է արտաքին:
- Յուրաքանչյուր բանալի սկսվում է այդ օգտագործման իր քաշի մասնաբաժնից հետո, այն բանից հետո, երբ ոչ մի տեղաբաշխում չի պահանջվում: Մեկ հաշվի 85%-ով և հինգ ստեղներով 20 կշռով, յուրաքանչյուրը սկսվում է օգտագործված 20-ից 17-ով:
- Մի քանի հաշիվներով լողավազանում սպասարկվող հաշվի թիվը կիրառվում է ամփոփված բյուջեի վրա: Սա գրքի կողմից անփոփոխ է:
- Պատուհանի ներսում ավելի ցածր ցուցանիշը, որը մատակարարը հայտնում է որպես բաց, չի կիրառվում: Վերակայման ժամանակը, որը հետ է շարժվում ավելի քան 30 րոպեով, համարվում է հին ընթերցում:
- Երկու դեպքում էլ գիրքը պահպանում է իր վիճակը, մինչև չանցնի պահված վերակայման ժամանակը: Դրանից հետո գիրքը չի գանձվում, քանի դեռ ընթերցանությունն այն չի դարձնում այն:
- Բուժումը ձեռքով օգտագործման պատմության վերակայումն է (`POST /api/settings/purge-usage-history`): Այն մաքրում է վերագրման գրքերը և դրանց նշանների հաշվիչները SQLite տվյալների բազայում:
- `all` ժամանակաշրջանը մաքրում է յուրաքանչյուր գիրք և հաշվիչ: Ավելի կարճ ժամանակահատվածը սկզբում մաքրում է այն գրքերը, որոնք գրված չեն դրա մեջ: Այնուհետև այն մաքրում է դրա մեջ չգրված հաշվիչները, այլ միայն լողավազանի միացման համար, որի վրա գիրք չի մնացել: Պահված գիրքը դեռևս նշում է յուրաքանչյուր բանալի իր հաշվիչի դիմաց:
- Գիրքը, որի պատկերը չի շարժվել, չի վերագրվում, ուստի ավելի կարճ ժամանակահատվածը կարող է նաև մաքրել ընթացիկ պատուհանի գիրքը: Այնուհետև հաջորդ ընթերցումը նոր գիրք է բացում ներկայիս ցուցանիշով:
- Վերակայումը չի դիպչում Redis քվոտայի խանութին: Այնտեղ գիրքն ավարտվում է իր պատուհանով կամ ավարտվում է վերջին գրվելուց 60 օր հետո:
- Երբ մատակարարը չի ուղարկում վերակայման ժամանակ, պատուհանը, որը վերակայվում և լիցքավորվում է հին թվի վերևում երկու ընթերցումների միջև, ավելի բարձր ցուցանիշ է թվում: Գիրքը պահպանում է հին հիմքը և նշումները:
- Ընթերցումները թվագրվում են տեղական ժամացույցով: Երբ այն աշխատում է մատակարարից առաջ, կամ աղբյուրը հայտնում է վերակայման ժամանակի մասին մի փոքր շուտ, գիրքը կարող է շուտ հասնել այդ տարբերությունին:
- Այդ կարճ ժամանակահատվածում աճը բաժանվում է դրանում երթուղված նշաններով: Հաջորդ պատուհանի առաջին ընթերցումը ուղղում է այն: Երբ շրջված գիրքը չի պահում զրոյացման ժամանակ, այդ ուղղումը պահանջում է ավելի ցածր ցուցանիշ, քան վերջին կիրառված ընթերցումը առնվազն երկու րոպեով ավելի նոր:
- Օրինակներ, որոնք կիսում են Redis խանութի ամսաթվերի ընթերցումները սեփական ժամացույցների հետ, այնպես որ այդ ժամացույցները համաժամեցված պահեք: Օրինակների ընթերցումները, որոնց ժամացույցը ետևում է, ավելի հին են թվում և անտեսվում են:
- Երբ պահված վերակայման ժամանակից հետո ոչ մի օգտագործելի ընթերցում չի ստացվում, մեկ բանալիով տոկոսային բաժնետոմսերը և տոկոսային սահմանաչափերը չեն ուժի մեջ մտնում, մինչև չվերադառնա ընթերցումը: Առանց վերակայման ժամանակի, սա սկսվում է գիրքը փոխած վերջին ընթերցումից 15 րոպե անց:
- Redis խանութում 60 օր անգործության մատնված գրքի ժամկետը կարող է ավարտվել գրողի չեկի և դրա գրման միջև: Այնուհետև այն նորից ստեղծվում է 1-ից բարձր վերանայման դեպքում, որը վավեր վիճակ է:

## Խողովակաշարերի ինտեգրում

### PRE hook (`open-sse/handlers/chatCore.ts`)

Գործում է վերին հոսանքով կատարողից առաջ, վավերացման և քաղաքականության ստուգումներից հետո.

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**Անհաջող բաց** Եթե `enforceQuotaShare` նետում է, ապա հարցումը թույլատրվում է `pino.warn` մատյանով: Սա կանխում է քվոտա-շարժիչի վրիպակը արգելափակելու ամբողջ տրաֆիկը:

**Երբ հզորությունը վերադառնում է:** Բանալին կամ լողավազանի առաստաղից հրաժարվելը ավարտվում է երկու նախադասություններից մեկով, երկու փոխառության եղանակներով.

- `percent` պատուհան. `. The <window> window resets at <time>.` Ժամանակն է զրոյացնել, որը մատակարարը հայտնում է:
- Հաշվելի միավոր՝ `. Enough <window> usage is expected to clear by <time>.` Ժամանակը լոգարիթմական պատուհանի վերին սահմանն է, եթե բանալին այլ բան չի ուղարկում:

`<time>` ISO 8601 ակնթարթ է UTC ում: Այնուհետև մերժումը կրում է `Retry-After`. ամբողջ վայրկյանը մինչև այդ ակնթարթը, գումարած մեկ: Հաճախորդը, որը սպասում է այդքան երկար, կրկնում է ակնթարթից առավելագույնը մեկ վայրկյան հետո: Երբ ակնթարթը հայտնի չէ, մերժումը չի կրում ոչ նախադասությունը, ոչ էլ վերնագիրը: Բացարձակ գլխարկի մերժումը չի ենթադրում ոչ մեկը: Հանրային կոդը մնում է `quota_share_blocked`:

Բաժնետոմսերի մերժումը չի դիպչում ընդհանուր կապին: Այն չի սահմանում սառեցում, մոդելի կողպեք և մատակարարի անջատիչի խափանում, և լողավազանի մյուս բանալիները շարունակում են սպասարկվել: Երբ կոմբինատի յուրաքանչյուր թիրախ հրաժարվում է իր մասնաբաժնի բանալին, կոմբոն առանց սպասելու պատասխանում է 429-ին: Դրա պատասխանը կրում է ակնարկը որպես `Retry-After`: Ներդրումների ուղին ավարտում է իր մերժումը նույն նախադասությամբ և ուղարկում ոչ `Retry-After`:

### POST կեռիկ (ռեկորդային սպառում)

Հաջող պատասխանից հետո.

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**Դրեյֆ նշում** Եթե `consume` ձախողվում է պատասխանից հետո, պտտվող հաշվիչը թերհաշվում է: Մատակարարի հագեցվածության ազդանշանը (օրինակ՝ `anthropic-ratelimit-unified-5h-utilization`) ուղղում է գլոբալ գնահատումը հաջորդ հարցման դեպքում:

### Կոմբո փափուկ տուգանային (`open-sse/services/combo.ts`)

Երբ `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

Տույժը կիրառվում է բոլոր մյուս միավորային գործոններից հետո: Այն նվազեցնում է հագեցած բանալի ընտրելու ավտոմատ համակցման հավանականությունը՝ առանց այն կոշտ արգելափակելու:

## Self-service Quota API (միացնել)

`GET /api/v1/me/quota/{provider}` (նաև մատուցվում է `/v1/me/quota/{provider}` ում) թույլ է տալիս API բանալին սեփականատիրոջը կարդալ սեփական բանալիով, թե որքանն է իրեն պատկանող ընդհանուր բաժանորդագրությունը և ինչն է նրանց արգելափակում: Երթուղին բարակ շերտ է `src/server/selfService/quotaHandler.ts` վրայով; տեսարանը կառուցված է `src/lib/quota/selfView.ts` կողմից և դրա պատասխանի պայմանագիրը `src/shared/schemas/selfQuota.ts` է (`SelfQuotaView` in `docs/openapi.yaml`):

### Միացում և նույնականացում

- Խաղարկային դրոշ `QUOTA_SELF_PANEL`, լռելյայն `false`: Մինչ այն անջատված է, երթուղին հասնող հարցումը ստանում է 404: `REQUIRE_API_KEY=true` դեպքում հաճախորդի API քաղաքականությունը հրաժարվում է 401-ով բացակայող կամ անվավեր բանալիից մինչև երթուղու գործարկումը, անկախ դրոշից: Հարցումը առանց բանալի, բայց մուտք գործած վահանակի աշխատաշրջանն անցնում է այդ քաղաքականությունը և ստանում է երթուղու սեփական պատասխանը: Դրոշը լուծվում է, ինչպես մյուս դրոշները (վահանակի կամ REST անտեսումը, այնուհետև նույնանուն միջավայրի փոփոխականը); տես [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md).
- Յուրաքանչյուր լողավազանի ցուցադրվող անունը և յուրաքանչյուր ժամանակացույցի պիտակը վերադարձվում են լողավազանի բանալիների կրողներին ճիշտ այնպես, ինչպես դրանք գրել է ադմինիստրատորը: Նախքան դրոշակը միացնելը, ստուգեք, որ դրանք հարմար են այդ բանալիների կողմից կարդալու համար:
- Բանալին կարդացվում է միայն վերնագրերից՝ `Authorization: Bearer <key>` կամ `x-api-key: <key>`: Երբ երկուսն էլ ուղարկվում են, օգտագործվում է առաջինը, որը վավերացնում է: Հարցման տողի բանալին կամ թխուկը անտեսվում է: Սերվերի շրջակա միջավայրի բանալին մերժված է (401):
- Բանալին պետք է `self:usage` շրջանակը (403 առանց դրա):
- Մատակարարի հատվածը կտրված է, փոքրատառով և ստուգվում է `^[a-z0-9][a-z0-9._-]{0,63}$` հետ (400 հակառակ դեպքում), այնուհետև լուծվում է մատակարարի ռեեստրի միջոցով, այնպես որ `cc` նման այլանունը կարդում է `claude` լողավազանները: `claude` և `anthropic` կարդում են նույն լողավազանները:

### Ինչ է ցույց տալիս յուրաքանչյուր տեսանելիությունը

| ---------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Սեփական բաժնեմաս | `self:usage`                                                                           | `pools[]` (ref, անուն, մատակարար, քաղաքականություն, քաշ, գլխարկ), `dimensions[].yourShare`, `accounts[]` `yourShare` ( `percent` պատուհանի վրա առանց `attributed` և `external`), `blocks`, `availableModels`, `expiresAt`, `apiBaseUrl`                                        |

- `sharedQuotaProviders` `null` բանալիի կարգավորում է (`PUT /api/keys/[id]/self-service`). `[]` նշանակում է ոչ մեկը: Յուրաքանչյուր լողավազանի `accountVisible` ասում է, թե որ տեսանելիությունը վերաբերում է դրան:
- Հաշվի գծերը և մոդելի պատուհանները ցուցադրվում են միայն այն հաշիվների համար, որոնց կապը կարող է օգտագործել բանալին: Երբ բանալին ունի թույլատրված կապերի ցանկ, հաշիվը դրանից դուրս պահպանում է իր `Account N` մուտքն առանց `account` կամ `modelWindows`: Դատարկ ցուցակը նշանակում է ոչ մի սահմանափակում, ինչ վերաբերում է `/v1/me/status`: Լողավազանի ընդհանուր թիվը (`dimensions[].total`) կախված չէ այդ ցանկից:
- Միայն `self:usage` ով ցուցադրված երկու թվեր բխում են այլ բանալիների օգտագործումից: Ժամանակացույցի բյուջեի `exhausted` արտացոլում է այդ ժամանակացույցի ներքո գտնվող յուրաքանչյուր ստեղնի սպառումը: Լողավազանում, որի կշիռները բոլորը զրո են, բանալին `weight` ն `100 / number of members` է: Երկուսն էլ այն են, ինչ կիրարկումը վերաբերում է բանալին:
- Լողավազանը նույնականացվում է միայն `ref` ով, որը անթափանց արժեք է, որը կապված է կանչող ստեղնին: Դրա ցուցադրման անունը (`name`) ներառված է այնպես, ինչպես գրել է ադմինիստրատորը: `ref` ստացվում է բանալիից և ավազանից՝ սերվերի API ստեղնի գաղտնիքով (`API_KEY_SECRET`): Հաճախորդները չպետք է շարունակեն դա. այն փոխվում է, եթե այդ գաղտնիքը պտտվում է:
- Հաշիվները թվարկված են որպես `Account 1`, `Account 2`, … ըստ լողավազանի հերթականության: Ոչ մի լողավազանի ID, կապի ID, հաշվի էլ. փոստ կամ հաշվի անուն չի վերադարձվում, և պատասխանն անցնում է պայմանագրի սխեմայի միջոցով, որը բացում է որևէ դաշտ դրա սահմաններից դուրս:
- `limit` միավորները = `requests`, `tokens`, `usd`) հաղորդվում են որպես `fairShare` `limit` × = ուժի `fairShare` է = քվոտայի դարպասը `remaining` × `consumed` `consumed` − = :
- `blocks.schedules` թվարկում է բանալիների ժամանակացույցի պատուհանները (`open`/`closed`, `blackout` կամ `outside-window`, `retryAfterSeconds`, պահուստային հարկեր և արդյոք ծախսվել է պատուհանի բյուջեն); `blocks.modelCaps` թվարկում է իր մեկ մոդելի ժամային շեմերը՝ սպառման հետ:
- Պրովայդերի յուրաքանչյուր լողավազանից դուրս գտնվող բանալին ստանում է 200 `pools: []` ով; `availableModels` ( `qtSd/` id-ները, որը բանալին տեսնում է `/v1/models` ում), `expiresAt` և `apiBaseUrl` դեռ լցված են:
- `apiBaseUrl` է `OMNIROUTE_PUBLIC_API_BASE_URL`, ապա `OMNIROUTE_PUBLIC_BASE_URL`, այլապես `null`: Դա երբեք չի հանդիսանում խնդրանքի սեփական ծագումը:

| `not_supported`                   | OmniRoute չի կարող կարդալ հաշվի մատակարարի օգտագործման սահմանափակումները:                                                                       |
| `fetch_failed`                    | Ոչ մի քեշավորված ընթերցում հնարավոր չէր օգտագործել, և մատակարարի սահմանաչափերի թարմացումը ձախողվեց:                                             |
| `not_available`                   | Ընթերցումը չունի օգտագործման պատուհաններ, կամ հաշիվն ընդհանրապես ընթերցում չունի:                                                               |

Երբ քվոտայի պահեստը հնարավոր չէ կարդալ, `blocks` ի պահեստային դաշտերը (ժամանակացույցի բյուջեի `exhausted`, մոդելի գլխարկի `consumed` և `reached`) նույնպես `null` են:

### Վարկավորման համաձայնություն

`PATCH /api/v1/me/quota/{provider}` գրանցում է կանչող բանալիի սեփական համաձայնությունը մեկ լողավազանի համար: Այն օգտագործում է `GET` ի դրոշը, վերնագրերը և մատակարարի կանոնները: `self:usage` շրջանակը թույլատրում է այս մեկ գրառմանը, թեև դրա անունը կարդում է որպես միայն կարդալու համար:

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` այն `ref` է, որը `GET` վերադարձնում է այդ լողավազանի համար:
- `lendingPercent` ամբողջ թիվ է 0-ից մինչև 100: 0-ի արժեքը մաքրում է համաձայնությունը և դրա վերջնաժամկետը: `lendingPercent` 0-ով մարմինն ընդունվում է ցանկացած ռեժիմում:
- `lendingUntil` ընտրովի է՝ դարաշրջանի միլիվայրկյաններ կամ `null` առանց վերջնաժամկետների: Այն պետք է լինի ապագայում և առավելագույնը 8640000000000000: 1000000000000-ից ցածր արժեքը կարդում է որպես վայրկյան և մերժվում է:
- Ցանկացած այլ բնագավառ մերժվում է։ 4096 բայթից ավելի մարմինը մերժվում է: Ընթերցումը կանգ է առնում այդ չափի վրա, ուստի երկար մարմինը երբեք ամբողջությամբ չի պահվում:

Ստուգումները կատարվում են այս աղյուսակի հերթականությամբ: Յուրաքանչյուր մերժում օգտագործում է ստանդարտ սխալի մարմինը ֆիքսված հաղորդագրությամբ: Այս չեկերից մեկի մերժումը ոչինչ չի գրում:

| Կարգավիճակ | Հաղորդագրություն                                                                                   | Երբ                                                                    |
| ---------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 404        | `Not found`                                                                                        | `QUOTA_SELF_PANEL` դրոշն անջատված է:                                   |
| 401        | `Valid API key required`                                                                           | Բանալին բացակայում է կամ անվավեր է, կամ սերվերի միջավայրի բանալին է:   |
| 403        | `API key lacks the self:usage scope`                                                               | Բանալին բացակայում է `self:usage`:                                     |
| 400        | `Invalid provider`                                                                                 | Մատակարարի հատվածն անվավեր է:                                          |
| 429        | `Too many lending changes. Retry later.`                                                           | Բանալին անցավ իր սահմանը։ Պատասխանը կրում է `Retry-After`.             |
| 400        | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | Մարմինը JSON չէ, չափազանց երկար է կամ չի համապատասխանում սխեմային:     |
| 400        | `lendingUntil must be a Unix time in milliseconds`                                                 | Վերջնաժամկետը նշվում է որպես վայրկյան:                                 |
| 400        | `lendingUntil must be in the future`                                                               | Վերջնաժամկետը հարցման ժամին է կամ դրանից առաջ:                         |
| 404        | `Pool not found`                                                                                   | `ref` այս մատակարարի համար այս բանալիի լողավազան չի անվանում:          |
| 403        | `Lending is not enabled for this pool`                                                             | Լողավազանը `saturation` ռեժիմում է, իսկ `lendingPercent` 0-ից բարձր է: |
| 500        | `Failed to build quota view`                                                                       | Ցանկացած այլ ձախողում: Դրա պատճառը գրանցված է սերվերում:               |

Սահմանաչափը յուրաքանչյուր բանալիի համար 20 հարցում է 60 վայրկյանում: Յուրաքանչյուր հարցում, որն անցնում է մատակարարի ստուգումը, հաշվվում է, նույնիսկ այն մեկը, որը մերժվել է ավելի ուշ, կամ մեկը, որը ոչինչ չի փոխում: Այն ունի իր սեփական հաշվիչը՝ բացառությամբ բանալու հարցման տոկոսադրույքի սահմանաչափի:

Պահված համաձայնությունը փոխող հարցումը գրում է մեկ `quota.pool.lending.updated` աուդիտի գրառում: Այն անվանում է բանալին հին և նոր արժեքներով: Երկու անգամ ուղարկված նույն մարմինը մեկ անգամ գրում է, մեկ անգամ ստուգում է: Պատասխանը 200 է ամբողջական `GET` դիտմամբ, որը կառուցվել է գրելուց հետո։

`GET` view-ը վարկավորման մասին հաղորդում է հետևյալ կերպ.

- Յուրաքանչյուր լողավազան կրում է `borrowMode` (`saturation` կամ `consent`) և բանալու սեփական `lendingPercent` և `lendingUntil`:
- `lendingActive` ն `true` է միայն `consent` լողավազանում, 0-ից բարձր տոկոսով և վերջնաժամկետով չհասած:
- `consent` լողավազանում յուրաքանչյուր հաշվելի `dimensions[].yourShare` կրում է `borrowAvailable`: Դա այն է, ինչ բանալին այժմ կարող է օգտագործել իր մասնաբաժնի վերևում, որը տրված է մյուս բանալիներով:
- `borrowAvailable` օգտագործում է դարպասի բանաձևը. Այն կարդում է բոլոր մյուս բանալիները, ինչպես նաև այն ժամանակ, երբ բանալին գտնվում է իր բաժնի տակ: `hard` ստեղնի համար, որը մեկ այլ ստեղնի և հաշվելի չափման մեկ լրացուցիչ ընթերցում է, զուգահեռաբար:
- `borrowAvailable` `null` է `soft` կամ `burst` ստեղնաշարի համար, իսկ `null` երբ ընթերցումը ձախողվում է:
- `borrowAvailable` ն մեկ գործիչ է բոլոր մյուս ստեղների համար միասին: Երկու բանալիներից բաղկացած լողավազանում դա մյուս բանալու պատկերն է:
- `borrowAvailable` դեռ չի հաղորդվում `percent` windows-ի կամ `accounts[]` ում:
- `saturation` լողավազանում տեսքը հաղորդում է պահված համաձայնությունը `lendingActive: false` ով և առանց `borrowAvailable`:

### Սխալներ

Այս երթուղու յուրաքանչյուր արձագանք՝ հաջողություն կամ սխալ, կրում է `Cache-Control: no-store`: Մերժումը, որը տեղի է ունենում նախքան երթուղու գործարկումը, չի կրում այն, օրինակ հաճախորդի API քաղաքականության 401-ը կամ IP `self:usage` 403-ը: Երթուղու սխալներն օգտագործում են ստանդարտ սխալի մարմինը ֆիքսված `Failed to build quota view`. 500-ը ծածկում է ցանկացած ձախողում, երբ հարցումը հասնում է երթուղուն, ներառյալ բանալու որոնումը. դրա պատճառը գրանցված է սերվերում և երբեք չի վերադարձվել: `PATCH` ի սխալները թվարկված են [Վարկի համաձայնությունում](#lending-consent) :

### Սահմանափակումներ

- `remaining` այն բանալու արդար մասնաբաժնի մասն է, որը նա չի օգտագործել: Դա երաշխիք չէ։ Մինչև լողավազանում տեղ կա, բանալի կարելի է մատուցել դրանից այն կողմ: Երբ լողավազանի ընդհանուր գումարը հասնում է `limit`, լողավազանի յուրաքանչյուր բանալի մերժվում է, անկախ նրանից, թե իր `remaining` է, և առանց `self:account-quota` բանալին չի կարող տեսնել այդ գումարը:
- `remaining` հաշվի չի առնում հատկացման բացարձակ `cap` : Հարկադիր կատարողը հրաժարվում է բանալին, երբ իր սեփական սպառումը գլխարկի միավորի պատուհանում հասնում է գլխարկի արժեքին:
- Հաշվի մակարդակի բարը գալիս է մատակարարի սահմանափակումների քեշից և կարող է մի քանի րոպեով հետաձգել կատարման որոշումը: Ընթերցումը, որի վերակայման ժամանակը անցել է, հաղորդվում է որպես `stale`:
- Մեկ մոդելի պատուհանները (`modelWindows`) հաղորդվում են միայն մատակարարների համար, որոնք ունեն պլան-պատուհանների քարտեզագրում՝ Claude և Codex այսօր: Այլ մատակարարների համար `modelWindows` դեռ առկա է, երբ ցուցադրվում են հաշվի տվյալները՝ դատարկ `windows` ցուցակով:
- Բանալին `percent` պատուհանի սեփական մասնաբաժինը գնահատական է: Այն բխում է վերագրման գրքից և պարունակում է բոլոր սահմանափակումները, որոնք նշված են վերևում «Տոկոսային չափսեր. բանալու վերագրում» բաժնում:
- `consumed` թվի կատարումն է, որը համեմատվում է արդար մասնաբաժնի հետ: Դա `attributed` գումարած `external` է, ճիշտ է: `attributed` ն այն մասն է, որը գիրքը տալիս է իր կողմից ուղարկված նշանների բանալին: `external` հաշվի օգտագործման այն մասն է, որը լողավազանի բանալիները հաշվի չեն առնվում:
- Երկու մասերն էլ ուղարկվում են միայն այն դեպքում, երբ լողավազանի `accountVisible` ճշմարիտ է. բանալին ունի `self:account-quota`, իսկ մատակարարը գտնվում է իր `sharedQuotaProviders` ում: Առանց դրա բանալին ստանում է միայն `consumed`, նույն `status` և `reason`:
- Երկու մասերի և սեփական քաշի շնորհիվ կրողը կարող է մշակել լողավազանից դուրս կատարված օգտագործումը, որը լիցքավորվում է լողավազանի բանալիների վրա: Հաշվի տիրույթ ունեցող սեփականատերն արդեն տեսնում է հաշվի ընդհանուր գումարը:
- Բանալին, որը ոչինչ չի ուղղորդել պատուհանում, դեռ կարող է կարդալ իր արտաքին լիցքը `consumed` ից, քանի որ դրա վերագրված մասը 0 է:
- Օրինակ, գիրքը բացվում է 0-ով, A և B ստեղներով յուրաքանչյուրը 50 քաշով: Key A-ն ուղղորդում է 900,000 ժետոն, իսկ B բանալին՝ 100,000: Այնուհետև հաշիվը հասնում է 100-ի սահմանաչափի 60%-ին: Այնուհետև `attributed` 54 է A ստեղնի համար և 6՝ ստեղնի համար, իսկ `external` երկուսի համար էլ 0 է:
- Տեսարանը կարդում է գիրքը և երբեք չի գրում դրա վիճակը: Այն գիրք չի բացում և երբեք չի խնդրում մատակարարից ընթերցանություն: Redis խանութի միջոցով ընթերցումը հեռացնում է փոխարինված վերանայման դաշտերը հետին պլանում, ինչպես դա անում են դարպասի ընթերցումները:
- Բաժնետոմսը `ok` է միայն այն ժամանակ, երբ դարպասի քեշը պահում է հաշվի ընթերցումը: Առանց մեկի այն `stale` է, ուստի լողավազանում, որտեղ վերջին հարցում չկա, այն ցույց է տալիս, որ հնարավոր է հնացած է:
- Քանի դեռ հարցումը չի անցել լողավազանով, բաժնետոմսն անհասանելի է: Այդ խնդրանքը բացում է գիրքը, և հաշվի ցուցանիշն այդ պահին համարվում է լողավազանից դուրս կատարված օգտագործում:
- Մի քանի հաշիվներով լողավազանում, յուրաքանչյուր հաշվի մուտքն օգտագործում է այդ հաշվի սեփական գիրքը և մեկ հաշվի սահմանաչափը: Հարկադիր կատարման սանդղակը երկու կողմերն էլ չափում է հաշիվների քանակով, ուստի համամասնությունը նույնն է:
- Մեկ մոդելի պատուհանները բանալու համար բաժնեմաս չունեն: Գիրքը չի պահում տվյալներ յուրաքանչյուր մոդելի համար:
- Ժամանակացույցի պահուստային հարկերը չեն գնահատվում տեսադաշտով. գրաֆիկը կարող է ցուցադրվել որպես `open` մինչդեռ հարցումը մերժվում է `schedule-reserve` պատճառաբանությամբ:
- Երբ նույն բանալու երկու լողավազաններ կիսում են կապը, կիրառումը կիրառում է դրանցից մեկը, և տեսքը ցույց է տալիս երկուսն էլ:
- Բանալին ձախողված փորձերի համար յուրաքանչյուր հասցեի սահմանափակում չկա. հակադարձ վստահված անձի հետևում զանգահարողները կարող են կիսվել մեկ հասցեով (դա կախված է նրանից, թե արդյոք փոխանցված հաճախորդի հասցեները վստահելի են), ուստի արգելափակումը կարող է մերժել երթուղին դեպի յուրաքանչյուր բանալու տնօրինող: `REQUIRE_API_KEY=true` դեպքում հաճախորդի API քաղաքականության կողմից անվավեր բանալին մերժվում է նախքան երթուղու գործարկումը, և այդ քաղաքականության 401 մարմինը այս երթուղու փոխարեն:

### Անդամների օգտագործումը

Ադմինիստրատորը կարող է բանալի կրողներին թույլ տալ տեսնել, թե ինչպես է պատուհանի օգտագործումը բաժանվում լողավազանի անդամների միջև: Տարբերակը լողավազանի `memberBreakdown` է, լռելյայն անջատված է: Այն տեղադրված է լողավազանի մոգում կամ `PATCH /api/quota/pools/{id}` ով: `GET /api/quota/pools` և `GET /api/quota/pools/{id}` հաղորդում են այն:

Տեսարանի չափումը կրում է `members` միայն այն դեպքում, երբ այս բոլորը պահպանվում են.

- լողավազանի տարբերակը միացված է
- լողավազանն ունի առավելագույնը 20 հատկացված բանալի, և դրանցից առնվազն երեքը կարող են հարցումներ կատարել՝ ակտիվ, չեղարկված, չարգելված և ժամկետանց
- լողավազանի `accountVisible` ճիշտ է. բանալին ունի `self:account-quota`, իսկ մատակարարը գտնվում է իր `sharedQuotaProviders` ում
- `percent` պատուհանում հաշվի միացումն այն բանալին է, որը կարող է օգտագործվել
- այդ պատուհանի բանալու սեփական բաժինը կարդացվել է՝ նրա `status` `unavailable` չէ

Հակառակ դեպքում `members` բացակայում է։ Այն երբեք դատարկ ցուցակ չէ:

- Յուրաքանչյուր կտոր `{ slot, consumed, isYou }` է: Պատասխանների սխեման մերժում է որևէ այլ հատկություն մեկ հատվածի վրա և 20-ից ավելի հատվածների ցանկը: Շերտերը նշված են անցքերի հերթականությամբ:
- Յուրաքանչյուր հատկացված բանալիի համար կա մեկ հատված, ներառյալ բանալի, որն այլևս չի կարող հարցումներ կատարել: Անօգուտ անդամը ցույց է տալիս իրական զրո:
- Սլոտ 1-ը միշտ հարցվող բանալին է՝ `isYou` true-ով: Մյուս բնիկ համարները ստեղնավորված հեշի շարքեր են: Այն բանալի է `API_KEY_SECRET` ով և ծածկում է լողավազանը, հարցնող բանալին և անդամը:
- Այսպիսով, թվերը չեն համընկնում սեփականատերերի միջև: Մեկ տիրոջ համար դրանք նույնն են մնում այցելությունների միջև: Դրանք կարող են փոխվել, երբ բանալին միանում կամ դուրս է գալիս լողավազանից, կամ երբ այդ գաղտնիքը պտտվում է:
- Հաշվելի պատուհանի վրա մի կտոր անդամի հաշվիչն է քվոտաների խանութում, նույնը, ինչ սեփական `consumed`:
- `percent` պատուհանի վրա մի կտոր անդամի `attributed` մասն է, նույն գրքից, որը կարդացվում է որպես բանալու սեփական բաժին: Լողավազանից դուրս կատարված օգտագործումը երբեք չի բաժանվում կտորների: Այդ լիցքը բաժանվում է ըստ քաշի, ուստի այն կրող կտորները ցույց կտան կշիռները:
- Յուրաքանչյուր դիտում կարդում է մեկ արժեք մեկ այլ անդամի և հաշվելի պատուհանի համար՝ զուգահեռաբար: `percent` պատուհանի վրա հատվածները կարդալու արժեք չունեն, քան բաժնետոմսի սեփական ընթերցված գիրքը: Երբ մեկ արժեք չի կարող կարդալ, այդ պատուհանը չունի `members`, և բանալու սեփական մասնաբաժինը մնում է:
- Ընտրանքը և օգտագործելի բանալիների քանակը կարդում են մեկ անգամ մեկ լողավազանում և միայն այն բանալիի համար, որը կարող է տեսնել հաշվի տվյալները: Ընտրանքի կամ օգտագործելի բանալիների քանակի ձախողումը անջատում է այդ լողավազանի գծերը: Սերվերը գրանցում է նախազգուշացում, իսկ մնացած տեսքը կառուցված է:

Ձողերը չեն կրում անուններ կամ ID: Նրանք դեռևս բանալի տիրոջն ասում են մյուս անդամների մասին.

- Սեփականատերերը դեռ կարող են համապատասխանեցնել շերտերն ըստ իրենց արժեքների:
- Կայուն համարակալումը թույլ է տալիս տիրոջը ժամանակի ընթացքում հետևել մեկ անդամի:
- Շերտերի քանակը ցույց է տալիս, թե քանի բանալի է հատկացված լողավազանում:
- Երեք բանալիներից բաղկացած լողավազանում, մեկը, ով գիտի, թե ինչ է օգտագործել մեկ բանալին, կարող է ասել, թե ինչ է օգտագործել վերջին բանալին:
- Երբ լողավազանն ընկնում է երեք օգտագործելի ստեղների տակ, ձողերն անհետանում են: Ավելի վաղ արված դիտումները դեռ ցույց են տալիս, թե ինչ է օգտագործել յուրաքանչյուր անդամ:
- Հաշվելի պատուհանի վրա լողավազանի ընդհանուր գումարը հանած հատվածները կարող են ցույց տալ ստեղների օգտագործումը, որոնք այլևս չեն հատկացվում:
- Անդամը, որը ցույց է տալիս զրո մի հաշվում և օգտագործում մեկ այլ հաշվի վրա, կարող է ցույց տալ, թե որ անդամն է օգտագործում որ հաշիվը:
- `hard` քաղաքականության հետ հաշվարկվող ավազանում, մի հատված, որը դադարում է աճել անդամի արդար բաժնեմասով, հուշում է այդ անդամի քաշի մասին:

### Օգտագործման շարք (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` (նաև մատուցվում է `/v1/me/usage` ում) վերադարձնում է զանգահարող բանալիի սեփական հարցումների օգտագործումը և արժեքը. ընդհանուր գումարներ, մեկ մուտք UTC օրվա համար, օրական և մոդելի, յուրաքանչյուր մոդելի և յուրաքանչյուր մատակարարի համար: Այն կիսում է դրոշը, նույնականացման կանոնները, `self:usage` շրջանակը, `Cache-Control: no-store` և վերը նշված քվոտայի երթուղու սխալ վարքագիծը: Բանալին ստուգվում է `range` առաջ: Սխալներն են 400 (`Invalid range`), 401, 403, 404 և 500 (`Failed to build usage`):

- `range` `1d`, `7d`, `30d` (կանխադրված) կամ `90d` ից մեկն է: Ցանկացած այլ արժեք, դատարկ արժեք կամ կրկնվող պարամետր 400 է: Կոմպլեկտը կանգ է առնում `90d` վրա՝ կապելու համար զանգի արժեքը: Տեսարանը կարդում է միայն չմշակված օգտագործման պատմությունը, ոչ երբեք ամենօրյա ամփոփագրերը, որոնք առանց որևէ բանալի են պարունակում:
- Տողերն ընտրվում են կանչող ստեղնի ID-ով: Բանալու անվան սյունակը երբեք չի համընկնում, և առանց բանալու ID-ի գրանցված տողերը երբեք չեն հաշվվում:
- Շարքի կառուցումը կատարում է հինգ խմբավորված հարցումներ պատուհանի բանալիների տողերի վրա: Կառուցված շարքը կրկին օգտագործվում է 60 վայրկյան յուրաքանչյուր ստեղնի և տիրույթի համար, և նորից օգտագործված զանգը չի կատարվում: Նրա `generatedAt` տալիս է իր տարիքը:
- Պատուհանը ավարտվում է, երբ սերիան կառուցվում է: Հետագայում դրոշմված շարքը, օրինակ՝ ժամացույցի թեքությամբ, չի հաշվվում:
- `coverage.retentionDays` օպերատորի չմշակված օգտագործման պատմության պահպանման կարգավորումն է (`retention.usageHistory` տվյալների բազայի կարգավորումներում): `coverage.truncatedByRetention` ճշմարիտ է, երբ պահանջվող միջակայքն ավելի երկար է, քան այդ կարգավորումը: Այն համեմատում է երկու թվերը և չի ստուգում, թե իրականում տողերը բացակայում են:
- Մատակարարը վերադարձվում է այնպես, ինչպես գրանցված է բանալիի սեփական հարցումների համար: Մոդելը գրանցված անունն է իր վերջին `/` հետո, և տողերը խմբավորված են դրանով: Համակցված հարցումը, որի յուրաքանչյուր թիրախ մերժվել է, գրանցվում է երթուղային պիտակի հետ՝ որպես մատակարար (համակցված անվանումը, `auto` կամ `combo`) և հաճախորդի կողմից ուղարկված մոդելի տողը: Այլ մերժված հարցումները, օրինակ՝ բաց անջատիչի, մոդելի սառեցման կամ քվոտայով կայանված բաց թողնելու միջոցով, պահեք թիրախային մատակարարին և մոդելին:
- Բացի հաշվարկներից և ծախսերից, պատասխանը պարունակում է միջին ուշացում, հաջողության տեմպեր և առաջին և վերջին հարցման ժամանակները:
- `byModel` թվարկում է 50 մատակարար-մոդել զույգերն ամենաշատ հարցումներով: Ավելի շատ զույգերով նրա գրառումները չեն գումարվում `summary`, և `summary.uniqueModels` հաշվում է յուրաքանչյուր գրանցված մոդելի ուղղագրությունը: `byModelTruncated` այդ դեպքում ճշմարիտ է, և մոդելը, որի զույգերն ընկնում են կտրվածքի երկու կողմերում, ցույց է տալիս մասնակի գումարներ:
- Նշվում է երկու ծախս. `costUsd` հաշվարկված արժեքն է, ինչպես դա ցույց է տալիս օգտագործման վերլուծությունը: Բաժանորդագրության հաստատագրված մատակարարները, ինչպիսին է Claude Code պլանը, այնտեղ հաշվում են $0: `listPriceUsd` նույն օգտագործումն է, որը գներով է նշված ցուցակի գնով, ներառյալ բաժանորդագրությունները: Հարցումը, որի մոդելը չունի գնային տող, հաշվում է դրա պահպանված արժեքը. այն արժեքը, որը մատակարարը հայտնել է, կամ այն, որը հաշվարկվել է, երբ հարցումը գրանցվել է: Միայն ոչ մեկով խնդրանքը չի հաշվում 0, առանց նշիչի, ուստի ընդհանուրը կարող է մասնակի լինել:
- Պատասխանի պայմանագիրը `src/shared/schemas/selfUsage.ts` է (`SelfUsageSeries` in `docs/openapi.yaml`):

### Ինքնասպասարկման էջ

Միացված `QUOTA_SELF_PANEL` ով, `/quota/{provider}` հանրային էջ է: Բանալատերը այնտեղ տպում է API բանալի և տեսնում է այդ բանալու լողավազանները մատակարարի համար: Յուրաքանչյուր լողավազան ցույց է տալիս մեկ քարտ յուրաքանչյուր լողավազանի պատուհանում՝ լողավազանի օգտագործմամբ բոլորի համար և բանալու սեփական բաժնեմասով: Լողավազանի յուրաքանչյուր հաշիվ ունի իր քարտերը՝ հաշվի օգտագործման և բանալու բաժնեմասով: Հաշվի օգտագործումը հայտնվում է միայն այն ժամանակ, երբ բանալին կարող է տեսնել հաշվի տվյալները: Էջը նաև թվարկում է յուրաքանչյուր հաշվի յուրաքանչյուր մոդելի սահմանաչափերը և բանալու սեփական օգտագործումը: Ծանուցում է հայտնվում, երբ ժամանակացույցն արգելափակում է բանալին հենց հիմա: Քարտը թվարկում է բանալու յուրաքանչյուր մոդելի գլխարկն իր օգտագործմամբ և նշում, թե որոնք են հասել: `{provider}` մատակարարի id-ն է կամ նրա կեղծանունը (`/quota/claude`, `/quota/cc`): Անհայտ մատակարարը և յուրաքանչյուր `/quota/*` ուղի, երբ դրոշն անջատված է, պատասխանեք 404-ին: Հատուկ OpenAI-ի կամ Anthropic-ի հետ համատեղելի հանգույցի լողավազանները էջ չունեն: API դեռ պատասխանում է նրանց փոխարեն։

Էջը նիստ չունի: Բանալին ուղարկվում է `GET /api/v1/me/quota/{provider}`, `PATCH /api/v1/me/quota/{provider}` և `GET /api/v1/me/usage` միայն `Authorization` վերնագրում, երբեք URL ում: Բանալին, որն ընդունում է սերվերը, պահվում է ներդիրի `sessionStorage` ում: «Remember on this device»-ի փոխարեն այն պահվում է `localStorage` ում, իսկ «Forget key»-ը հեռացնում է այն երկուսից: Բանալին, որը սերվերը մերժում է, հեռացվում է պահեստից:

`consent` ռեժիմով լողավազանը ցույց է տալիս վարկային քարտ: Այնտեղ բանալի տերը սահմանում է 0-ից մինչև 100 բանալի պարապ բաժնեմասի մի ամբողջ տոկոս՝ պարտք տալու համար: Սեփականատերը նաև ընտրում է, թե որքան ժամանակ է տևում համաձայնությունը՝ մինչև անջատումը, 1 ժամ, 8 ժամ, 24 ժամ, 7 օր կամ 30 օր: Տևողությունը հաշվվում է խնայողության պահից: Մինչև վերջնաժամկետը ուժի մեջ է, սեփականատերը կարող է այն պահպանել դրա փոխարեն: Եթե այդ ժամկետն անցնում է Save-ից առաջ, քարտը ոչինչ չի ուղարկում և այլ ընտրություն է խնդրում: 0%-ով վերջնաժամկետ չի ուղարկվում։ Քարտը ցույց է տալիս պահված վերջնաժամկետը՝ իր անվանված ժամային գոտիով: Համաձայնությունը, որի վերջնաժամկետը լրացել է, ցուցադրվում է որպես ավարտված:

`hard` բանալիի համար քարտը նաև նշում է, թե ինչ այլ ստեղներ են տալիս բանալին հենց հիմա: Յուրաքանչյուր տող մեկ թիվ է բոլոր մյուս ստեղների համար միասին: Երկու բանալիներից բաղկացած լողավազանում դա մյուս բանալու պատկերն է: Թիվը, որը դիտումը չի հաղորդում, կարդում է որպես անհասանելի, ոչ թե զրո: `soft` կամ `burst` ստեղնաշարի համար քարտը նշում է, որ ոչ մի ցուցանիշ չի կիրառվում:

`saturation` ռեժիմով լողավազան, որի բանալին պահում է 0-ից բարձր տոկոս, ցույց է տալիս միայն դուրսբերում: Այնտեղ գրված է, որ պահպանված տոկոսն այնտեղ ազդեցություն չունի։ Դրա «Հանել» կոճակը ուղարկում է 0 առանց վերջնաժամկետների: `saturation` ռեժիմում գտնվող լողավազանը պահված 0-ով ցույց չի տալիս վարկային քարտ: Պահումից հետո քարտը, որն այլևս կարիք չունի վերադարձված դիտմանը, մնում է իր հաղորդագրության մեջ, մինչև էջի տեսքը նորից փոխվի:

Ոչինչ չի պահպանվում, քանի դեռ սեփականատերը չի սեղմել «Պահպանել» կամ «Հետ վերցնել»: Յուրաքանչյուր մամուլ ուղարկում է մեկ `PATCH /api/v1/me/quota/{provider}` հարցում, իսկ երկրորդ սեղմումը ոչինչ չի ուղարկում, մինչ առաջինը սպասվում է: Մարմինը կրում է լողավազանի անթափանց `ref` տեսադաշտից, տոկոսից և վերջնաժամկետից: Պատասխանը վերակառուցված քվոտայի տեսքն է, և էջը ցույց է տալիս այն առանց երկրորդ ընթերցման: Երբ երկու պահումներ համընկնում են, էջը կարդում է քվոտան մեկ անգամ վերջին պատասխանից հետո: Էջը չի պահպանում համաձայնությունը դիտարկիչի պահեստում:

Մերժված փոփոխությունը բացատրվում է քարտի վրա HTTP կարգավիճակից ընտրված տեքստով: Սխալի մարմինը չի կարդացվում: 401-ն ասում է, որ բանալին չի ընդունվել և վերաբեռնում է քվոտան: 403-ն ասում է, որ լողավազանը չի ընդունում վարկի փոփոխությունները, իսկ 404-ը ասում է, որ լողավազանը չկա: Երկուսն էլ առաջարկում են կոճակ, որը վերաբեռնում է քվոտան: 400 կամ մեկ այլ 4xx պատասխանը սեփականատիրոջը խնդրում է ստուգել տոկոսը և վերջնաժամկետը: A 429-ը խնդրում է տնօրինողին սպասել՝ `Retry-After` ի վայրկյաններով, երբ պատասխանը տալիս է դրանք: 5xx պատասխանը, 408-ը կամ ցանցի խափանումը ասում է, որ փոփոխությունը հնարավոր է չի պահպանվել և պահպանում է մուտքագրված արժեքները: Պայմանագրից դուրս պատասխանը վերաբեռնում է քվոտան: Անհաջող պահումը չի հեռացնում բանալին ինքնին: Երբ վերաբեռնումը մերժվելուց հետո, էջը հեռացնում է բանալին, ինչպես ցանկացած մերժված ընթերցման դեպքում:

Բանալին ընդունելուց հետո էջը ցույց է տալիս նաև «Կարգավորեք ձեր գործիքները» քարտը երեք ներդիրով: «Claude Code»-ը տալիս է `env` բլոկը `~/.claude/settings.json` համար: «Shell»-ը տալիս է նույն փոփոխականները, ինչ `export` տողերը: «Claude Desktop»-ը տալիս է իր երրորդ կողմի եզրակացության պատուհանի արժեքները: Մոդելները քվոտային բաժնետոմսերի մոդելներ են, որոնք բանալին կարող է կանչել այդ մատակարարի համար: Երբ բանալիով նման ցուցակ չկա, դրա փոխարեն բլոկը միացնում է դարպասի մոդելի հայտնաբերումը: Դարպասի հասցեն այն հանրային API ծագումն է, որը սերվերը հաղորդում է (`OMNIROUTE_PUBLIC_API_BASE_URL`, ապա `OMNIROUTE_PUBLIC_BASE_URL`): Երբ ոչ մեկը սահմանված չէ, քարտը ցույց է տալիս տեղապահ և ասում է տիրոջը խնդրել ադմինիստրատորին: Բանալին ցուցադրվում է որպես տեղապահ: «Include my key»-ը ամբողջ բանալին տեքստի մեջ է դնում էկրանին և այն, ինչ պատճենում է կոճակը: Դա տևում է մինչև տուփը մաքրվի, բանալին մոռացվի կամ փոխարինվի, կամ էջը մնա: Քարտը ոչ մի հարցում չի ուղարկում և չի առաջարկում ֆայլի ներբեռնում:

API նշումը `stale` ի ընթերցումը ցուցադրվում է որպես հնարավոր հնացած: Ցուցանիշը, որը նշում է `unavailable` ցուցադրվում է իր պատճառներով, երբեք որպես զրո:

Տոկոսային պլանների վրա էջը նկարում է բանալու սեփական բաժինը, երբ API հաղորդում է այդ մասին: Ասում է, որ թիվը գնահատական է և անվանում է դրա երկու մասերը։ Մեկ մոդելի սահմանաչափերը ցույց են տալիս միայն հաշիվը:

Երբ պատուհանը կրում է `members`, դրա քարտը նաև ցույց է տալիս յուրաքանչյուր անդամի մեկ հատվածով գծիկ՝ ըստ բնիկի հերթականության: Հարցնող բանալու հատվածն օգտագործում է շեշտադրման գույնը: Մյուս հատվածները շրջում են թեմայի գծապատկերների գույներով: Տեքստի լեգենդը թվարկում է յուրաքանչյուր հատված իր արժեքով, ուստի ոչինչ կախված չէ գույնից: Հատվածները պիտակավորված են `You` կամ `Member N`, որտեղ N-ը բնիկն է:

### Նվիրված նավահանգիստ էջի համար

`QUOTA_PANEL_PORT` բացում է երկրորդ լսող, որը սպասարկում է միայն ինքնասպասարկման էջը: Այն անջատված է, եթե փոփոխականը սահմանված չէ: `QUOTA_PANEL_HOST` կապի հասցե է և լռելյայն է `127.0.0.1` ին:

Լսողը փոխանցում է այս ուղիները դեպի հիմնական նավահանգիստ և յուրաքանչյուր այլ ճանապարհի համար պատասխանում է 404.

| Ճանապարհ                                                                 | Ծառայում է                                |
| ------------------------------------------------------------------------ | ----------------------------------------- |
| `/quota/{provider}`                                                      | Էջը                                       |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | Քվոտայի դիտումը էջը կարդում է             |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | Օգտագործման շարքը, որը կարդացվում է էջում |
| `/_next/static/`                                                         | Կառուցման սցենարներ, ոճեր և տառատեսակներ  |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | Սրբապատկերներ                             |

`GET` և `HEAD` փոխանցվում են առանց մարմնի: Փոխանցվում է նաև մարմնի հետ մեկ հարցում՝ քվոտայի դիտման ուղու `PATCH`, որը էջն ուղարկում է վարկավորման ընտրությունը պահպանելու համար: Ցանկացած այլ մեթոդ պատասխանում է 404-ին, բացի CONNECT հարցումից, որի կապը փակվում է առանց պատասխանի: Ցանկացած այլ հարցում, որը հայտարարում է մարմին, պատասխանում է 404-ին, և դրա միացումը փակ է։ Թարմացման հարցումները մերժվում են, և դրանց կապը փակ է: Կետային հատվածով կամ բեկորային նշիչով ուղին մերժվում է, ինչպես API նավահանգստում: Այդպես է նաև խնդրանքի թիրախը տպագրվող ASCII դուրս գրանշանով: Թիրախում չմշակված կառավարման նիշը HTTP վերլուծիչի կողմից պատասխանվում է 400, նախքան այս պորտի սեփական ստուգումը: Հայցեք վերնագրեր, որոնք շրջանակը պահում է իր սեփական օգտագործման համար. անուններ, որոնք սկսվում են `x-middleware-`, `x-invoke-`, `x-nextjs-`, `x-now-` կամ `x-next-`, և `x-matched-path` և `next-resume` անունները: Հարցումը փոխանցվում է առանց դրանց: Վահանակին, մուտքի էջին, կառավարման API և եզրակացության երթուղիներին հնարավոր չէ հասնել այս նավահանգստի միջոցով:

`PATCH` պետք է կրի `Content-Type: application/json`, առանց պարամետրի կամ միայն `charset=utf-8` ով: Այն պետք է ունենա մեկ `Content-Length` 1-ից մինչև 4096, գրված որպես պարզ թվանշան, և ոչ `Transfer-Encoding`: `PATCH`, որը խախտում է այս կանոններից մեկը, պատասխանում է 404-ին: Որոշ սխալ ձևավորված երկարություններ, ինչպիսիք են ստորագրվածը կամ կրկնվողը, HTTP վերլուծիչը պատասխանում է 400-ով մինչև այս պորտի սեփական ստուգումը: Նավահանգիստը կարդում է հայտարարագրված բայթերը, նախքան այն կապվում է հիմնական պորտի հետ և սպասում է դրանց համար առավելագույնը 5 վայրկյան: Մարմինը, որը մինչ այդ ամբողջական չէ, պատասխանում է 404-ին, և նրա կապը փակ է։ Հիմնական պորտին ոչինչ չի հասնում այդ դեպքում, կամ երբ հաճախորդը առաջինը հեռանում է։ Նավահանգիստը փոխանցում է հենց հայտարարված բայթերը՝ նույն `Content-Length` ով: Նրանցից հետո բայթերը կարդացվում են որպես կապի հաջորդ հարցում: Առջևում գտնվող TLS հակադարձ վստահված անձը պետք է փոխանցի `Content-Length` և չպետք է նորից մասնատի հարցման մարմինը: Հիմնական նավահանգիստը ստուգում է API ստեղնը `Authorization` վերնագրում, ինչպես `GET`.

404 մարմինը `{"error":"not_found","message":"Not found."}`. Անհաջող ռելեը պատասխանում է 502 (`api_bridge_unavailable`) կամ 504 (`api_bridge_timeout`) առանց `detail` դաշտի:

Լսողը `QUOTA_SELF_PANEL` չի կարդում և էջը չի բացում։ Մինչ դրոշակը անջատված է, էջը և դրա API պատասխանում են 404-ին հիմնական պորտում, և լսողը փոխանցում է այդ պատասխանը:

Զարգացման սերվերի ներքո (`next dev`) էջը չի դառնում ինտերակտիվ այս պորտի միջոցով: Զարգացման «hot-reload socket»-ը արդիականացման հարցում է, և նավահանգիստը մերժում է այն: Զարգացնելիս օգտագործեք հիմնական նավահանգիստը:

Նավահանգիստը սպասարկում է պարզ HTTP, իսկ էջը ուղարկում է API ստեղներ: Պահպանեք լռելյայն կապի հասցեն և դրա դիմաց դրեք TLS ով հակառակ պրոքսի: Loopback-ից տարբեր կապի հասցե գրանցում է այս ծանուցումը.

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

Loopback գործընկերը, որը չի ուղարկում վերահասցեավորման վերնագիր, հաշվվում է որպես տեղական հիմնական նավահանգստում: Այսպիսով, նույն հյուրընկալողի վստահված անձը պետք է ուղարկի `X-Forwarded-For`: Մասնավոր հասցեի վստահված անձը վստահված է այդ վերնագրի համար միայն `OMNIROUTE_TRUST_PROXY=private` ով (կամ `lan`): Ցանկացած այլ գործընկեր հաղորդում է իր կապի հասցեով, և նրա ուղարկած վերահասցեավորման վերնագրերը հանվում են:

Լսողը միաժամանակ պահում է առավելագույնը 256 կապ: Հաճախորդը 10 վայրկյան ունի հարցումների վերնագրերն ուղարկելու և 30 վայրկյան՝ ամբողջ հարցումն ուղարկելու համար: Անգործուն պահվող կապը փակվում է մոտ 5 վայրկյան հետո: 60 վայրկյան առանց ակտիվության կապը փակ է: Այս արժեքները ամրագրված են: Սահմանեք կապի և տոկոսադրույքի սահմանաչափերը նաև առջևի հակառակ վստահված անձի վրա: Առջևի հակադարձ պրոքսի-ն պետք է պահի իր անգործուն հոսանքին հակառակ միացումները 5 վայրկյանից պակաս, կամ չվերօգտագործի դրանք: Հիմնական նավահանգիստ տանող ռելեն օգտագործում է API նավահանգստի (`API_BRIDGE_*`) վերին հոսքի ժամանակային անջատումները:

Լսողը սկսում է նաև այն ժամանակ, երբ `API_PORT` կարգավորված չէ: `QUOTA_PANEL_PORT` պետք է լինի 1-ից մինչև 65535 պորտ և գրված լինի միայն թվանշաններով: Այն պետք է տարբերվի վահանակի միացքից և API պորտից: Մինչ կենդանի WebSocket սերվերը միացված է, այն նաև պետք է տարբերվի `LIVE_WS_PORT` ից (կանխադրված 20132): Ցանկացած այլ արժեք ոչինչ չի բացում և նախազգուշացում գրանցում: Մերժված արժեքի մասին նախազգուշացումն անվանում է փոփոխականը և չի կրկնում արժեքը: Մի նավահանգիստ, որն արդեն օգտագործվում է, ոչինչ չի բացում և գրանցում է այս նախազգուշացումը.

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH` set-ի դեպքում ունկնդիրն ակնկալում է վերևում գտնվող յուրաքանչյուր ուղի այդ նախածանցի ներքո: Օգտագործեք նույն `OMNIROUTE_BASE_PATH` կառուցման և գործարկման ժամանակ: Գրեք այն առաջատար շեղով և առանց հետին շեղի, օրինակ `/omniroute`. Մեկ այլ ձև, ներառյալ `/` և `/omniroute/`, դուրս է թողնում նավահանգիստը նախազգուշացումով, թեև կառուցվածքն ընդունում է այդ ձևերը: Այսպես է վարվում նաև բազային ուղին, որի առաջին հատվածը անվանում է կիրառման երթուղի. `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0` կամ `connect`, ամեն դեպքում:

Սահմանափակումներ.

- `/quota/{provider}/` հետընթաց շեղով պատասխանում է 404-ին այս նավահանգստում:
- Ծառայության աշխատողը և վեբ հավելվածի մանիֆեստը չեն սպասարկվում այս միացքում:
- Վահանակի վրա տեղադրված հատուկ ֆավիկոն չի ցուցադրվում այս նավահանգստում:
- Սրբապատկերները չեն ցուցադրվում, երբ հավելվածն աշխատում է բազային ուղու տակ:
- Նավահանգիստը խոսում է պարզ HTTP/1.1.
- Ձախողվող կապը չի կրկնվում մինչև գործընթացը վերսկսվի:
- Լսողը չունի կապի կամ տոկոսադրույքի սահմանափակում յուրաքանչյուր հաճախորդի հասցեի համար:
- Բեռնարկղերի կարգավորումները չեն ընդգրկվում այս բաժնում:

## Խնդիրների ախտորոշում

### Redis-ը կազմաձևված է, բայց չի միանում

Ստուգեք, որ `ioredis`-ը տեղադրված է (`npm ls ioredis`), և `QUOTA_STORE_REDIS_URL`-ը
հասանելի է։ Միացման ձախողման դեպքում ֆաբրիկան անցնում է SQLite-ի օգտագործմանը
(գրանցվում է `warn` մակարդակով)։

### `peek`-ը վերադարձնում է հնացած տվյալներ / աշխատում է բաց թողնելու սկզբունքով

Եթե `peek`-ը սխալ է նետում, `enforceQuotaShare`-ը արդյունքը դիտարկում է որպես «թույլատրել»
(ձախողման դեպքում՝ բաց թողնել)։ Հիմնական պատճառը բացահայտելու համար `pino` մատյաններում
ստուգեք `quota:enforce` և `quota:factory` գրառումները։

### Սպառման հաշվիչի շեղում

Եթե մատակարարի փաստացի օգտագործումը տարբերվում է հաշվիչների տվյալներից, դա սպասելի է․
2 բաքեթով սահող պատուհանը պատուհանների սահմաններին ունի մոտ 1% սխալ, իսկ `consume`-ը
պատասխանից հետո գործարկվում է առանց ավարտին սպասելու։ Հագեցվածության ազդանշանը (`saturationSignals.ts`)
30 վրկ. TTL-ով կարդում է մատակարարի իրական օգտագործումը և համապատասխանաբար ճշգրտում `globalUsedPercent`-ը։

### Փուլը սպառման արագության համար ցույց է տալիս «տվյալներ չկան»

`computeBurnRate`-ը պահանջում է առնվազն 2 պատմական նմուշ։ Առանց նախորդ
`consume` կանչերի նոր փուլերը ցույց կտան `tokensPerSecond: 0` և `timeToExhaustionMs: null`։

## Տեղափոխում localStorage-ից

Երբ `/dashboard/costs/quota-share`-ն առաջին անգամ բեռնվում է, `useLocalStoragePoolMigration` հուքը ստուգում է՝

1. `localStorage.getItem("omniroute:quota-share:pools")`-ը դատարկ չէ։
2. `GET /api/quota/pools`-ը վերադարձնում է `[]` (DB-ն դատարկ է)։

Եթե երկու պայմաններն էլ ճշմարիտ են, այն խմբաքանակով ուղարկում է յուրաքանչյուր հին փուլը դեպի `POST /api/quota/pools`, ապա հեռացնում է localStorage-ի բանալին։ Տեղափոխումն իդեմպոտենտ է․ 2-րդ պայմանը կանխում է կրկնակի տեղափոխումը։

## DB սխեմայի ամփոփում

`078`, `079` և `085` միգրացիաներով ավելացված երեք աղյուսակ.

- `quota_pools` + `quota_allocations` — լողավազանի սահմանումներ և մեկ բանալու հատկացումներ:
- `quota_consumption` — շարժակազմի 2 դույլով հաշվիչներ մեկ `(apiKeyId, dimensionKey)` համար:
- `provider_plans` — ձեռնարկի մատակարարի պլանը վերացնում է (չափերը JSON մեկ connectionId):

Բոլոր աղյուսակները ավելացվել են idempotent `CREATE TABLE IF NOT EXISTS` միգրացիաների միջոցով:

Համաձայնեցված վարկավորումն ավելացնում է երեք սյունակ՝ `quota_allocations.lending_percent` (ամբողջ թիվ, լռելյայն 0), `quota_allocations.lending_until` (դարաշրջան միլիվայրկյաններ կամ `NULL` առանց վերջնաժամկետների) և `quota_pools.borrow_mode` (կանխադրված `saturation`): Դրա միգրացիան միայն ավելացնում է այս սյունակները և չի գրում գոյություն ունեցող տող:

Տոկոսների վերագրման գրքում ավելացվում է `quota_percent_ledger` (մեկ տող յուրաքանչյուր լողավազանի, հաշվի և պլանի պատուհանի համար) և `quota_percent_ledger_tokens` (մեկ նշանային հաշվիչ յուրաքանչյուր լողավազանի, հաշվի և API բանալի): `src/lib/db/quotaPercentLedger.ts` կարդում և գրում է դրանք։
