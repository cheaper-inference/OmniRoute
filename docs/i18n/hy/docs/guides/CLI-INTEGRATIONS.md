Համօգտագործվող գործարկվող մանիֆեստի, երեխաների սահմանափակ միջավայրերի և Gemini մշտական կարգավորումների համար տե՛ս [CLI գործարկման պայմանագրերը](./CLI-LAUNCH-CONTRACTS.md) :

OmniRoute ուղարկում է `setup-*` հրամանների ընտանիք, որոնք կարգավորում են կոդավորման CLI (Codex, Claude Code, OpenCode, Cline,…)՝ OmniRoute օգտագործելու համար որպես ետնամաս, այնպես որ գործիքը խոսում է** մեկ** վերջնական կետ և OmniRoute երթուղիներ դեպի ճիշտ մատակարար՝ ավտոմատ հետադարձով: Յուրաքանչյուր հրաման կարդում է** ապրել** մոդելի կատալոգը գործող OmniRoute ից (տեղական կամ հեռավոր) և գրում է գործիքի սեփական կազմաձևման ֆայլը** քո** մեքենա. API ստեղնին հղում է արվում շրջակա միջավայրի փոփոխականով, որտեղ էլ որ գործիքն այն աջակցում է: Ստորև նշված են հրամանները, որոնք պահպանում են գործիքի տեղական միջավայրի ֆայլը:

Կա նաև ընդհանուր գործարկիչ՝ `omniroute run <target>`, որը ստեղծում է `claude`, `codex`, `aider`, `goose`, `opencode`, `qwen`, `gemini` կամ `whycodes` ՝ ներարկված ճիշտ env-ով, առանց որևէ կոնֆիգուր գրելու: Թիրախները և դրանց փոխանունները գալիս են կանոնական մանիֆեստից `bin/cli/cli-manifest.mjs` (`claude-code|cc|anthropic`, `codex-cli|openai-codex|openai`, `goose-cli`, `open-code`, `qwen-code`, `gemini-cli`, `why-codes|why`), իսկ `omniroute completion` առաջարկում է նույն մանիֆեստից ստացված թիրախային բառերը։ Հնացած մեկ գործիքի գործարկիչները՝ `omniroute launch` (Claude Code) և `omniroute launch-codex` (Codex) - մնում են հասանելի:

Մատակարարի մուտքը հասանելի է նույն local/remote համատեքստից: Ստորև բերված API-ի առաջին հրամանները կառավարման նույնականացումը անջատ են պահում մատակարարի հավատարմագրերից և երբեք հավատարմագրեր չեն տպում կառուցվածքային ելքում.

```bash
omniroute providers add glm --credential-env GLM_API_KEY --name work
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth openai
omniroute providers edit <connection-id> --default-model glm/glm-5.2
omniroute providers remove <connection-id> --yes
```

Սցենարների համար նախընտրեք `--credential-stdin` կամ `--credential-env`; `--credential` պահպանվում է վերահսկվող տեղական օգտագործման համար: `providers remove` պահանջում է `--yes` ոչ ինտերակտիվ տերմինալում, և բոլոր հինգ հրամանները հարգում են ակտիվ համատեքստը կամ գլոբալ `--base-url`/`--api-key` տարբերակները:

Մատակարարների ընտրողները մերժում են ոչ միանշանակ ID նախածանցները, անունները կամ մատակարարների անունները. օգտագործել ամբողջական միացում ID, երբ մի քանի կապեր համընկնում են: Ստեղծեք և խմբագրեք հրամաններ, որոնք կարդում են պահպանված կապը, և հեռացումը հաստատում է, որ այն այլևս ընթեռնելի է: Ներմուծումը բաց է թողնում գոյություն ունեցող provider/name զույգը: Ներմուծված գրառումները չեն կարող վերացնել CLI ին տրամադրված կառավարման վերջնակետը, համատեքստը կամ կառավարման հավատարմագրերը:

Երկու ամենահարուստ ինտեգրումների մեկանգամյա, ձեռքով գրված բազայի տեղադրման համար տե՛ս յուրաքանչյուր գործիքի խորը սուզումները.

- [Codex CLI կոնֆիգուրացիա](./CODEX-CLI-CONFIGURATION.md)
- [Հեռակառավարման ռեժիմ](./REMOTE-MODE.md) — ձեր նոութբուքից վարեք հեռակառավարվող OmniRoute (VPS / Tailnet):

## Վարպետ սեղան

Յուրաքանչյուր հրաման հարգում է** ակտիվ համատեքստ** (սահմանված է `omniroute connect` ով, տես [Հեռակա ռեժիմ](./REMOTE-MODE.md) ) կամ բացահայտ `--remote <url> --api-key <key>` դրոշներ: «Տեղական ընդդեմ հեռավոր» ստորև նշանակում է. առանց դրոշների այն թիրախավորում է `http://localhost:20128`; `--remote` ով (կամ ակտիվ հեռակա համատեքստով) այն վերցնում է կատալոգը այդ սերվերից և գրում կոնֆիգուրը տեղայնորեն:

| `omniroute setup-whycodes` | WhyCodes                                   | WhyCodes `config.toml` (`[providers.omniroute]` + `[default_model]`); ճանապարհը `$WHYCODES_HOME/config.toml` կամ `~/.whycodes/config.toml` է                                            | `--remote` `--api-key` `--model` `--yes` `--dry-run` `--port` `--config-path`                                                              | Երկուսն էլ             |
| `omniroute run <target>`   | Գործարկման ժամանակի գործարկում (ընդհանուր) | Ոչինչ — ձել `claude`/`codex`/`aider`/`goose`/`opencode`/`qwen`/`gemini`/`whycodes` ճիշտ env-ով և args-ով; Qwen և Gemini օգտագործում են ժամանակավոր մեկուսացված տուն                     | `--remote` `--base-url` `--context` `--provider` `--model` `--api-key` `--api-key-env` `--dry-run` `--json` `--port` `--profile` `--token` | Երկուսն էլ             |
| `omniroute launch`         | Claude ծածկագիր                            | Ոչինչ — ձվադրում է `claude` հետ `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` ներարկվել                                                                                                   | `--remote` `--api-key` `--token` `--profile` `--port`                                                                                      | Երկուսն էլ             |
| `omniroute launch-codex`   | OpenAI Codex CLI                           | Ոչինչ — առաջացնում է `codex` `omniroute` մատակարարի հետ, որը ներարկվում է `-c` դրոշների միջոցով                                                                                         | `--remote` `--api-key` `--profile` (`-p`) `--port`                                                                                         | Երկուսն էլ             |

Նշումներ դրոշների վերաբերյալ (ստուգված հրամանի աղբյուրում).

- `--remote <url>` — բերեք կատալոգը հեռավոր OmniRoute ից (շրջանցում է `--port` և ակտիվ համատեքստը): `--api-key <key>` տրամադրում է այդ սերվերի հավատարմագրերը (կանխադրված է `OMNIROUTE_API_KEY` env var-ին կամ ակտիվ համատեքստի նշանին):
- `--only <patterns>` - ստորակետերով բաժանված ենթատողեր; պահել միայն IDs մոդելը, որը համապատասխանում է (օր. `--only glm,kimi`): Հասանելի է `setup-codex`, `setup-claude`, `setup-opencode`, `setup-continue`, `setup-cursor`, `setup-crush`, `setup-zed`.
- `--dry-run` — տպեք ճիշտ այն, ինչ կգրվեր՝ առանց ֆայլային համակարգին դիպչելու: Հասանելի է յուրաքանչյուր `setup-*` հրամանի վրա** բացի** `setup-cursor` (որը երբեք ֆայլ չի գրում):
- `--model <id>` — պահանջվում է (կամ ընտրվում է ինտերակտիվորեն) այն գործիքների համար, որոնք չունեն մոդելի ավտոմատ հայտնաբերում. Cline, Kilo, Roo, Goose, Qwen, Aider, 5dive, WhyCodes: Այդ գործիքները նաև ընդունում են `--yes` ոչ ինտերակտիվ գործարկումների համար (որն այնուհետև պահանջում է `--model`): `setup-opencode` վերցնում է `--model` վերին մակարդակի լռելյայն մոդելը սահմանելու համար:
- `--model <id>` `omniroute run` ում հետևում է մանիֆեստի մեկ թիրախային լարերին (`bin/cli/cli-manifest.mjs`):** օգնական** ստանում է `--model openai/<id>` եւ** բաց կոդ** `--model omniroute/<id>` (նախածանցն ավելացվում է միայն այն դեպքում, երբ id-ն այն արդեն չի կրում);** qwen** և** երկվորյակներ** ստանալ id բառացի;** Կլոդ** այն ստանում է `ANTHROPIC_MODEL` միջոցով,** սագ** `GOOSE_MODEL` միջոցով,** ինչու կոդերը** միջոցով `-P omniroute -m <id>`, եւ** կոդեքս** միջոցով `-c model_providers.omniroute.*` args.**Qwen միակ գործարկվող թիրախն է, որը խիստ պահանջում է `--model`** — `omniroute run qwen` առանց դրա դուրս է գալիս `2` բացահայտ սխալով:
- `--port <port>` — տեղական OmniRoute միացք (կանխադրված `20128`, անտեսվում է, երբ `--remote` սահմանված է): Ներկա բոլոր `setup-*` և երկու գործարկիչների վրա:
- `omniroute run` ելքի կոդեր. երեխայի CLI ի սեփական ելքի կոդը տարածվում է բառացիորեն. `2` = անվավեր արգումենտներ (չաջակցվող թիրախ, բացակայում է պարտադիր `--model`, կոնտեյների պաշտպանիչ); `127` = թիրախային երկուականը `PATH` ում չէ. `130`/`143`/`129` երբ գործարկումն ավարտվում է `SIGINT`/`SIGTERM`/`SIGHUP`; `1` = այլ գործարկման ժամանակի ձախողում:
- Երկու գործարկիչները (`launch`, `launch-codex`) ընդունում են `--profile <name>` `setup-claude` / `setup-codex` ի կողմից գրված պրոֆիլ ընտրելու համար, գումարած արգիզերի անցումը՝ հիմքում ընկած `claude` / `codex` երկուականի համար:

Ինտերակտիվ ընտրիչը տարածվում է նաև տեղադրման բաղադրատոմսերով.

```bash
# Pick from the active local or remote model catalog and configure the target.
omniroute configure claude
omniroute configure opencode --provider glm
omniroute configure qwen --model qwen/qwen3.8-max-preview --yes
```

`configure` ներկայումս պատվիրակում է `codex`, `claude`, `opencode`, `qwen`, `aider`, `goose`, `cline`, `continue`, `kilo` և `5dive` փորձարկված բաղադրատոմսերը: Միայն IDE-ի, MITM և միայն ուղեցույցի կատալոգի գրառումները մնում են հստակ `setup-*`/ձեռնարկ հոսքեր և չեն ներկայացվում որպես գործարկվող թիրախներ:

> `setup-opencode` է** թեթև բաց՝ համատեղելի** OpenCode ինտեգրում. Կա նաև ավելի հարուստ պլագինների ինտեգրում՝ `omniroute setup opencode`, որը տեղադրում է `@omniroute/opencode-plugin`: Դրանք տարբեր հրամաններ են. վերը նշված աղյուսակը փաստաթղթերը `setup-opencode`.
>
> Փլագինը գալիս է երկու փաթեթով, մեկը՝ OpenCode major-ի համար, քանի որ երկու բեռնիչները ակնկալում են տարբեր մուտքի կետեր՝ `@omniroute/opencode-plugin` OpenCode v1-ի համար և `@omniroute/opencode-plugin-v2` OpenCode v2-ի համար: v2 փաթեթը նոր է (`0.1.0`) և հետևում է հյուրընկալող պայմանագրին, որը դեռ շարժվում է, ուստի այն կարդում է OpenCode սերմերի ձևը կատալոգի նախագծում, այլ ոչ թե ենթադրում է: Տեղադրեք այն `opencode.json` ին ավելացնելով `plugins` մուտք; `omniroute setup opencode` դեռ տեղադրում է v1 փաթեթը: Ընտրանքները և հավատարմագրերի որոնման կարգը գտնվում են README փաթեթում:

## Տեղային օգտագործում

Երբ OmniRoute-ն աշխատում է `localhost:20128` հասցեում, պարզապես գործարկեք ձեր գործիքի կարգավորման հրամանը։ Կատալոգը ներբեռնվում է տեղային սերվերից։

```bash
# Codex. յուրաքանչյուր համընկնող մոդելի համար պրոֆիլ գրել ~/.codex/-ում
omniroute setup-codex
codex --profile glm52            # օգտագործել ստեղծված պրոֆիլը

# Claude Code. գրել առանձին պրոֆիլներ յուրաքանչյուր մոդելի համար, ապա գործարկել դրանցից մեկը
omniroute setup-claude
omniroute launch --profile glm52

# OpenCode. գրել openai-ի հետ համատեղելի մատակարար՝ կատալոգի բոլոր մոդելներով
omniroute setup-opencode
export OMNIROUTE_API_KEY=sk-...  # հղվում է {env:OMNIROUTE_API_KEY}-ի միջոցով, երբեք չի պահվում սկավառակի վրա
opencode -m omniroute/glm/glm-5.2 "..."

# Ավտոմատ հայտնաբերում չունեցող գործիքներին անհրաժեշտ է մոդելի հստակ նշում.
omniroute setup-aider --model glm/glm-5.2
omniroute setup-qwen --model qwen/qwen3.8-max-preview

# Նախադիտել՝ առանց որևէ բան գրելու.
omniroute setup-continue --dry-run
```

Գործարկել՝ ընդհանրապես որևէ կազմաձև չգրելով (միայն միջավայրի փոփոխականների ներարկմամբ).

```bash
omniroute launch                 # Claude Code → տեղային OmniRoute
omniroute launch-codex           # Codex CLI → տեղային OmniRoute
omniroute launch-codex --profile glm52
omniroute run claude --model openai/gpt-5.4
omniroute run codex --model openai/gpt-5.4 --dry-run --json
omniroute run aider --model glm/glm-5.2 -- --message "reply OK"
omniroute run goose --model glm/glm-5.2
omniroute run opencode --model glm/glm-5.2 -- run "reply OK"
omniroute run qwen --model glm/glm-5.2 -- -p "reply OK"
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "reply OK"

# Հրամանի հստակ ուղի. անփոփոխ փոխանցել այն ամենը, ինչ գալիս է -- նշանից հետո
omniroute run claude -- --print-system-prompt "review this diff"
```

## Հեռակա օգտագործում

Կարգավորման ցանկացած հրաման ուղղեք դեպի հեռակա OmniRoute՝ օգտագործելով `--remote` + `--api-key`։ Կատալոգը ներբեռնվում է հեռակա սերվերից, իսկ կազմաձևը գրվում է ձեր տեղային համակարգչում։

```bash
# OpenCode-ը հեռակա VPS-ի հետ՝ պահելով միայն glm/kimi մոդելները
omniroute setup-opencode --remote http://192.168.0.15:20128 --api-key oma_live_xxx \
  --only glm,kimi
opencode -m omniroute/glm/glm-5.2 "..."   # նախ արտահանել OMNIROUTE_API_KEY-ը

# Codex պրոֆիլներ՝ հեռակա կատալոգից
omniroute setup-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx

# Գործարկել CLI-ն անմիջապես հեռակա սերվերի հետ
omniroute launch       --remote http://192.168.0.15:20128 --api-key oma_live_xxx
omniroute launch-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx
```

Ամեն անգամ `--remote`/`--api-key` փոխանցելու փոխարեն մեկ անգամ մուտք գործեք և թույլ տվեք, որ **ակտիվ համատեքստը** դրանք տրամադրի ավտոմատ կերպով.

```bash
omniroute connect 192.168.0.15        # ստեղծում է սահմանափակ տիրույթով թոքեն և պահում համատեքստը
omniroute setup-codex                 # ← այժմ օգտագործում է հեռակա կատալոգը
omniroute setup-opencode              # ← նույնը
omniroute launch                      # ← Claude Code-ը հեռակա սերվերի հետ
```

Համատեքստերի, տիրույթների և թոքենների կառավարման մասին տե՛ս [Հեռակա ռեժիմ](./REMOTE-MODE.md) բաժինը։

## 5dive գործակալների խմբեր

[5dive](https://5dive.ai)-ը գործարկում է երկարատև աշխատող կոդավորման գործակալների խումբ, որոնցից յուրաքանչյուրը systemd միավոր է՝ իր առանձին Unix օգտատիրոջ ներքո։ Այն ինքնին կոդավորման CLI չէ, ուստի `omniroute run`-ը գործարկելու որևէ բան չունի. `5dive`-ը **միայն կազմաձևման համար նախատեսված** թիրախ է։

```bash
omniroute configure 5dive --model failover-demo --yes
omniroute setup-5dive --model failover-demo --auth-profile omniroute --agent worker1
```

Երկու ձևն էլ գրում են մեկ 5dive **նույնականացման պրոֆիլ**, որից հետո այդ պրոֆիլին կապակցված յուրաքանչյուր `claude` տեղ աշխատում է OmniRoute-ի միջոցով։ Այս թիրախին հատուկ են երեք հանգամանք.

- **Այն գործարկվում է խմբի հոսթում՝ որպես root։** 5dive-ի հրամանները գործում են տեղային systemd միավորների և root-ին պատկանող վիճակի պանակի հետ. հեռակա ռեժիմ չկա։ Եթե բաղադրատոմսն արդեն root-ի իրավունքներով չի աշխատում, այն վերագործարկվում է `sudo`-ի միջոցով (`--no-sudo`-ն անջատում է դա և փոխարենը տպում հրամանը)։
- **Վերջնակետը պետք է օգտագործի `https://`, եթե այն loopback հասցե չէ։** Գործակալի API բանալին յուրաքանչյուր հարցման ժամանակ փոխանցվում է այդ URL-ով, և 5dive-ը մերժում է չգաղտնագրված, տվյալ համակարգչից դուրս գտնվող վերջնակետը։ Մասնավոր LAN հասցեն բացառություն չէ։
- **Յուրաքանչյուր տեղի սեփական ամրագրված մոդելն ավելի բարձր առաջնահերթություն ունի, քան պրոֆիլինը։** Պրոֆիլը պարունակում է `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`, սակայն ստանդարտ մոդելի id-ին դեռևս ամրագրված տեղն իր առաջին հարցման ժամանակ ձախողվում է՝ _«Ընտրված մոդելի հետ կապված խնդիր կա»_ հաղորդագրությամբ։ Փոխանցեք `--agent <name>` (կարելի է կրկնել)՝ նաև տեղերի համար մոդելն ամրագրելու նպատակով. հակառակ դեպքում բաղադրատոմսը տպում է հրամանը։

API բանալին 5dive-ին փոխանցվում է **stdin**-ով (`--api-key=-`), ուստի այն երբեք չի հայտնվում `ps`-ի ելքում։

Պրոֆիլը մեկ մոդելի փոխարեն OmniRoute-ի **combo**-ին ուղղելն ապահովում է խմբի մատակարարների միջև խափանման դեպքում ավտոմատ անցումը. երբ [#11578](https://github.com/diegosouzapw/OmniRoute/issues/11578)-ում գրանցված գործարկման ընթացքում հիմնական վերջնակետն աշխատանքի կեսին ամբողջությամբ անհասանելի դարձավ, գործակալն իր մնացած քայլերն ավարտեց պահուստային տարբերակով և օգտատիրոջը չցուցադրեց խափանումը։

## Թարմացման ժամանակ բնիկ կախվածությունների պահպանումը՝ `--include=optional`

Երբ թարմացնում եք `omniroute update`-ի միջոցով (հաստատելուց հետո կամ `--apply`-ով),
OmniRoute-ը տեղադրումը գործարկում է ներկառուցված `--include=optional`-ով․

```bash
npm install -g omniroute@latest --include=optional
```

Սա **չի** հանդիսանում դրոշակ, որը պետք է փոխանցեք `omniroute update`-ին․ այն միշտ կիրառվում է
թարմացնողի կողմից։ Սա երաշխավորում է, որ `optionalDependencies`-ը (`better-sqlite3`, `keytar`,
`tls-client`, LLMLingua SLM ստեկը) կպահպանվեն թարմացումից հետո, նույնիսկ եթե ձեր npm-ի կազմաձևում
սահմանված է `omit=optional`, ինչը հակառակ դեպքում առանց զգուշացման կհեռացներ SQLite-ի բնիկ
դրայվերը և ՕՀ-ի բանալիների շտեմարանի կապակցումը։ Ճշգրիտ հրամանը առանց կիրառելու նախադիտելու համար․

```bash
omniroute update --dry-run
# [ՓՈՐՁՆԱԿԱՆ ԳՈՐԾԱՐԿՈՒՄ] Կգործարկվեր՝ npm install -g omniroute@latest --include=optional
```

`omniroute update`-ի այլ դրոշակներ (ստուգված են սկզբնաղբյուրում)՝ `--check` (ավարտվել 1 կոդով, եթե
հնացած է), `--apply` (տեղադրել առանց հաստատում պահանջելու), `--changelog`, `--no-backup`,
`--yes`։

## Google Gemini CLI-ն՝ `omniroute run gemini`-ի միջոցով

Պայմանագիրը ստուգված է `@google/gemini-cli` 0.50.0-ի նկատմամբ․ CLI-ն հաշվի է առնում
`GOOGLE_GEMINI_BASE_URL`-ը և դրան ուղարկում է `POST /v1beta/models/<model>:generateContent`
(ինչպես նաև `:streamGenerateContent?alt=sse`) հարցումներ՝ ճիշտ OmniRoute-ի բնիկ
Gemini ինտերֆեյսին (`/v1beta`)։ `omniroute run gemini`-ն սա կարգավորում է ինքնաշխատ կերպով․

- `GOOGLE_GEMINI_BASE_URL` → OmniRoute-ի ակտիվ Base URL-ը (արմատային, առանց `/v1`-ի),
- `GEMINI_API_KEY` → որոշված OmniRoute հավատարմագիրը (ընտրանք/env/համատեքստ),
- **ժամանակավոր, մեկուսացված `GEMINI_CLI_HOME`**, որի `.gemini/settings.json`-ն
  ընտրում է `gemini-api-key` նույնականացումը, որպեսզի պահպանված Google OAuth աշխատաշրջանը (Code Assist)
  երբեք չգերակայի OmniRoute-ին ուղղված գործարկմանը․ այն հեռացվում է ավարտից հետո,
- **env-ի հիգիենա**․ ենթապրոցեսի env-ից հեռացվում են `GOOGLE_API_KEY`,
  `GOOGLE_GENAI_USE_VERTEXAI` և `GOOGLE_GENAI_USE_GCA` փոփոխականները (որոնք նույնականացումը
  կվերաուղղորդեին դեպի Vertex/Code Assist), իսկ `GEMINI_DEFAULT_AUTH_TYPE=gemini-api-key`-ը
  սահմանվում է որպես լրացուցիչ ապահովագրական պահուստային տարբերակ․ մյուս `run` թիրախներն իրենց
  հակասող փոփոխականների համար ստանում են նույն մոտեցումը,
- `--model <id>`-ի ներարկում `--provider`/`--model`-ից։

```bash
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "hello"
```

Gemini-ի աշխատանքային տարածքի վստահության պաշտպանիչ ստուգումը գործում է նաև առանց ինտերֆեյսի ռեժիմում․ ինքներդ փոխանցեք
`--skip-trust`-ը (կամ ինտերակտիվ կերպով վստահեք պանակին)․ գործարկիչը միտումնավոր չի շրջանցում այն։
Այս գործարկիչը տարբերվում է **ACP գրանցումից**
(`src/lib/acp/registry.ts`, `gemini --acp`), որը շարունակում է մնալ
`/dashboard/acp-agents`-ի համար գործակալի արձանագրության ինտեգրումը։

## Իրական smoke ստուգում (ըստ ցանկության)

Դետերմինիստական գործարկման պլանի ռեգրեսիոն ստուգումները կատարվում են CI-ում (`tests/unit/cli/run-command.test.ts`,
`tests/unit/cli/run-execution.test.ts`)։ ԻՐԱԿԱՆ բինար ֆայլերը ԻՐԱԿԱՆ
OmniRoute սերվերի հետ վավերացնելու համար առկա է ըստ ցանկության գործարկվող փորձարկման հարմարանք՝
`tests/integration/upstream-cli-smoke.int.test.ts`։ Այն երբեք ինքնաբերաբար չի գործարկվում
(յուրաքանչյուր ենթաթեստ բաց է թողնվում, եթե սահմանված չէ `RUN_CLI_SMOKE=1`), հավատարմագրային տվյալը փոխանցում է միջավայրի փոփոխականի
ԱՆՈՒՆՈՎ (երբեք ոչ արժեքով), գրանցված ցանկացած ելքից քողարկում է բանալու ձևաչափ ունեցող տողերը, բաց է թողնում
այն թիրախները, որոնց բինար ֆայլը տեղադրված չէ, և ձախողումները դասակարգում է որպես
նույնականացման / վերին հոսքի / կազմաձևման՝ պարզ բուլյան արժեքի փոխարեն.

```bash
RUN_CLI_SMOKE=1 \
OMNIROUTE_SMOKE_BASE_URL="http://localhost:20128" \
OMNIROUTE_SMOKE_MODEL="<provider/model>" \
OMNIROUTE_SMOKE_API_KEY_ENV="OMNIROUTE_API_KEY" \
node --import tsx/esm --test tests/integration/upstream-cli-smoke.int.test.ts
```

Ըստ ցանկության՝ `OMNIROUTE_SMOKE_TARGETS="codex,opencode,qwen"`-ը սահմանափակում է ստուգման շրջանակը.
`OMNIROUTE_SMOKE_TIMEOUT_MS`-ը փոխարինում է յուրաքանչյուր թիրախի համար նախատեսված 120 վրկ․ սպասման սահմանաչափը։
