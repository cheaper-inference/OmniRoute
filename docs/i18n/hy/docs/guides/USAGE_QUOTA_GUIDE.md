> **Կարճ ասած**․ OmniRoute-ը հետևում է յուրաքանչյուր հարցման թոքենների օգտագործմանը, հաշվարկում է արժեքը, կիրառում է յուրաքանչյուր API բանալու քվոտան և վերլուծական տվյալները ցուցադրում կառավարման վահանակում։ Այս ուղեցույցը բացատրում է, թե ինչպես է այդ ամենն աշխատում։

**Աղբյուրներ․**

- `open-sse/services/usage.ts` (~70KB) — օգտագործման հետևման հիմնական մոդուլ
- `src/lib/usageAnalytics.ts` (~10KB) — կառավարման վահանակի համար ագրեգացում
- `src/lib/db/quotaSnapshots.ts` — քվոտայի պատմական տվյալներ
- `src/lib/db/usage*.ts` — օգտագործման հետ կապված տվյալների բազայի մի քանի մոդուլներ

## Ընդհանուր ակնարկ

OmniRoute-ով անցնող յուրաքանչյուր հարցում ստեղծում է **օգտագործման գրառում**, որը պարունակում է՝

- **Ինքնություն**․ որ API բանալին, մատակարարը, մոդելը և համակցությունն են օգտագործվել
- **Թոքեններ**․ հուշման թոքեններ, լրացման թոքեններ, քեշավորված թոքեններ, ընդհանուր քանակ
- **Արժեք**․ գումարը ԱՄՆ դոլարով՝ հաշվարկված գնագոյացման տվյալներից
- **Ժամանակագրություն**․ ուշացում, սկզբի/ավարտի ժամանակային դրոշմներ
- **Կարգավիճակ**․ հաջողություն, սխալ, արագության սահմանափակում և այլն

```
Հարցում ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                  վերլուծություն քվոտա  հաշվարկներ
                  (վահանակ)     (կիրառում) (արտահանում)
```

## Ինչ է գրանցվում

`usage.ts` ծառայությունը յուրաքանչյուր հարցման համար գրանցում է **օգտագործման իրադարձություն**.

| Դաշտ               | Տիպ      | Աղբյուր                                                                |
| ------------------ | -------- | ---------------------------------------------------------------------- |
| `id`               | տող      | Գրանցման պահին գեներացված UUID                                         |
| `apiKeyId`         | տող      | Հարցումը նախաձեռնած API բանալին                                        |
| `provider`         | տող      | Մատակարարի ID (openai, anthropic և այլն)                               |
| `model`            | տող      | Մոդելի ID (gpt-5, claude-opus-4-6 և այլն)                              |
| `comboId`          | տող?     | Համակցության ID, եթե երթուղավորումն իրականացվել է համակցության միջոցով |
| `promptTokens`     | թիվ      | Վերին օղակի պատասխանից                                                 |
| `completionTokens` | թիվ      | Վերին օղակի պատասխանից                                                 |
| `cachedTokens`     | թիվ      | Քեշում գտնված թոքեններ (Anthropic-ի հուշումների քեշավորում և այլն)     |
| `totalTokens`      | թիվ      | Հուշում + լրացում                                                      |
| `costUsd`          | թիվ      | Հաշվարկվում է գնային տվյալների հիման վրա                               |
| `latencyMs`        | թիվ      | Հարցման ամբողջական տևողությունը                                        |
| `status`           | թվարկում | `success`, `error`, `rate_limited`, `timeout`, `cancelled`             |
| `errorClass`       | տող?     | Սխալի դասը, եթե կարգավիճակը != success                                 |
| `timestamp`        | տող      | ISO 8601 UTC                                                           |
| `metadata`         | օբյեկտ   | Փլագինի կողմից ներարկված հատուկ տվյալներ                               |

### Որտեղից են ստացվում թոքենները

Թոքենները դուրս են բերվում վերին օղակի մատակարարի պատասխանից՝ **պատասխանի մշակիչում**.

```ts
// open-sse/handlers/chatCore.ts-ից
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Այն մատակարարների համար, որոնք օգտագործման տվյալներ չեն վերադարձնում (վեբ քուքիներով աշխատող որոշ մատակարարներ), OmniRoute-ը **գնահատում է** թոքենների քանակը՝ կիրառելով `~4 chars per token` մոտավոր կանոնը (տե՛ս `open-sse/services/autoCombo/pipelineRouter.ts`)։

### Քեշավորված թոքեններ

OmniRoute-ը հետևում է `cached_tokens`-ին՝ `prompt_tokens`-ից առանձին, քանի որ.

- Anthropic-ի հուշումների քեշավորման դեպքում քեշավորված թոքենները հաշվարկվում են նվազեցված սակագնով (սովորականի 10%-ը)
- Որոշ մատակարարներ վերադարձնում են `cache_read_input_tokens`, որոնց համար պետք է կիրառվի այլ սակագին
- Վերլուծությունը կարող է ցույց տալ **քեշում գտնվելու գործակիցը** = `cached_tokens / prompt_tokens`

### Քեշում գրելու մակարդակների ախտորոշում

Վերլուծության վահանակի հուշումների քեշի վիճակի բաժինը տարբերակում է մատակարարի հաղորդած
5-րոպեանոց և 1-ժամյա քեշային գրառումները։ Anthropic-ի
`usage.cache_creation.ephemeral_5m_input_tokens` և
`usage.cache_creation.ephemeral_1h_input_tokens` տվյալները պահպանվում են հոսքային և
ոչ հոսքային օգտագործման տվյալների փոխակերպման ընթացքում և պահվում կանչերի մատյանի ամփոփագրերի հետ։ Քեշում գրելու
ընդհանուր գումարը երկրորդ անգամ չի ավելացվում այդ խմբերին։

Միայն գրելու ընդհանուր հաշվիչ ունեցող կանչերի, այդ թվում՝ ավելի հին գրառումների մակարդակն
անհայտ է։ Մասնակի բաշխման դեպքում չբաշխված մնացորդը մնում է անհայտ, իսկ անվավեր կամ
հակասական հաշվիչները նշվում են՝ դրանց լռելյայն TTL վերագրելու փոխարեն։ Հարցման կողմի
TTL նշիչները չեն հաստատում վճարագրված մակարդակը։

Բաժնի՝ քեշում գրելու API-համարժեք գնահատականն ընդգրկում է միայն հաղորդված և գնորոշված մակարդակները, ոչ թե
ամբողջ հարցումը։ Claude/Anthropic մոդելների բնիկ գնագոյացման դեպքում այն օգտագործում է մուտքային սակագնի 1.25-ապատիկը՝
5-րոպեանոց գրառումների համար, և մուտքային սակագնի կրկնապատիկը՝ 1-ժամյա գրառումների համար։ Բացակայող
գինը համարվում է անհասանելի, ոչ թե զրո։ Գները պահպանվում են յուրաքանչյուր նոր կանչի գրանցման պահին.
նախկին գրառումների գները չեն վերահաշվարկվում։ Հետևաբար բաժանորդագրությամբ հաշիվները կարող են ունենալ
API-համարժեք գնահատական՝ առանց այդ գումարի չափով դրամական ծախս կամ բաժանորդագրության
քվոտայի սպառում ունենալու։ Քվոտայի, բյուջեի և մատակարարի ճշգրիտ արժեքի առկա հաշվարկները մնում են անփոփոխ։

Այս ախտորոշիչ տվյալներն օգտագործում են քեշի վիճակի առկա սահմանափակ ամփոփագիրը և կանչերի մատյանի
պահպանման մեխանիզմը։ Դրանք չեն փոխում հարցումների TTL-ի լռելյայն արժեքները, երթուղավորումը կամ հաշվի ընտրությունը։
Հաճախորդի պահանջած և փաստացի ելքային TTL-ի գրանցումը մատակարարին ուղարկելու
սահմանային կետում հետաձգված է. այս բաժինը ներկայացնում է ստացականներում նշված մակարդակները, ոչ թե փաստացի ելքային TTL-ը։

Իրականացում՝ `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` և `open-sse/utils/cacheWriteUsage.ts`։

## Արժեքի հաշվարկ

Արժեքները հաշվարկվում են LiteLLM-ից համաժամացված **գնագոյացման տվյալների** հիման վրա (`src/lib/pricingSync.ts`)․

| Մոդել             | Մուտքային $/1M | Ելքային $/1M | Քեշավորված $/1M |
| ----------------- | -------------- | ------------ | --------------- |
| gpt-5             | $2.50          | $10.00       | —               |
| claude-opus-4-6   | $15.00         | $75.00       | $1.50           |
| claude-sonnet-4-5 | $3.00          | $15.00       | $0.30           |
| gemini-2.5-pro    | $1.25          | $10.00       | —               |

Արժեքի բանաձևը (`src/lib/usage/costCalculator.ts`)․

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Ինչո՞ւ են քեշավորված թոքենները հանվում հարցման թոքեններից։** Քեշավորված մասը գնագոյացվում է առանձին․ ամբողջ հարցման նկատմամբ մուտքային գինը կիրառելը կհանգեցներ կրկնակի հաշվարկի։

### Գնագոյացման համաժամացում

Գնագոյացման տվյալներն ավտոմատ կերպով համաժամացվում են LiteLLM-ից՝ `/api/pricing/sync` վերջնակետի միջոցով (այն գործարկվում է ներկառուցված cron առաջադրանքով, այլ ոչ թե օգտատիրոջ համար նախատեսված միջավայրի փոփոխականով)․

```bash
# Ձեռքով գործարկում
curl -X POST http://localhost:20128/api/pricing/sync
```

Այն մոդելների համար, որոնց գնագոյացման տվյալները հասանելի չեն, OmniRoute-ը **մոտավոր հաշվարկում է արժեքը**՝ օգտագործելով ներքին միջին դրույքաչափերը (որոնց աղբյուրը LiteLLM-ի գնագոյացման տվյալներն են)։

## Ամսաթվերի միջակայքի ագրեգացում

`usageAnalytics.ts` մոդուլը հաշվարկում է կառավարման վահանակի վիջեթները՝ օգտագործման չմշակված տվյալներից։ Այն աջակցում է 7 ժամանակային միջակայքի.

| Միջակայք | Ժամանակահատված                 | Կիրառություն                              |
| -------- | ------------------------------ | ----------------------------------------- |
| `1d`     | Վերջին 24 ժամը                 | Ծախսերի ժամային կտրուկ աճի հայտնաբերում   |
| `7d`     | Վերջին 7 օրը                   | Շաբաթական վերանայում                      |
| `30d`    | Վերջին 30 օրը                  | Ամսական հաշիվների կազմում                 |
| `90d`    | Վերջին 90 օրը                  | Եռամսյակային վերլուծություն               |
| `ytd`    | Ընթացիկ տարվա հունվարի 1-ից    | Տարեկան բյուջեի վերահսկում                |
| `all`    | Ամբողջ ժամանակահատվածը         | Ամբողջ ժամանակահատվածի վիճակագրություն    |
| `custom` | Օգտատիրոջ սահմանած սկիզբ/ավարտ | Աուդիտներ, ըստ անհրաժեշտության հարցումներ |

### Հաշվարկվող կառավարման վահանակի վիջեթներ

Ամսաթվերի ցանկացած միջակայքի համար վերլուծական շերտը հաշվարկում է.

| Վիջեթ                           | Նկարագրություն                                                                               |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| **Ամփոփիչ քարտեր**              | Հարցումների ընդհանուր քանակ, ընդհանուր ծախս, թոքենների ընդհանուր քանակ, հաջողության ցուցանիշ |
| **Օրական միտումների գծապատկեր** | Օրական ծախս + թոքեններ՝ շերտավորված ըստ մոդելի                                               |
| **Ակտիվության ջերմային քարտեզ** | Օրվա ժամ × շաբաթվա օր ցանց, գույնը = հարցումների քանակը                                      |
| **Բաշխում ըստ մոդելի**          | Ծախսերի շրջանաձև գծապատկեր՝ ըստ մոդելի                                                       |
| **Բաշխում ըստ մատակարարի**      | Հարցումների սյունակային գծապատկեր՝ ըստ մատակարարի                                            |
| **Առաջատար API բանալիներ**      | Ըստ ծախսի առաջատար 10 բանալիների աղյուսակ                                                    |
| **Սխալների վերլուծություն**     | Սխալների հաճախականությունը ժամանակի ընթացքում, սխալների հիմնական դասերը                      |

### Ծրագրային հասանելիություն

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // օգտագործման պատմության գրառումներ
  "7d",                 // ժամանակային միջակայք՝ "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // մատակարարի միացումների քարտեզ (connectionId → հաշվի անուն)
  {
    startDate: "2025-01-01",  // ոչ պարտադիր՝ "custom" միջակայքի համար
    endDate: "2025-06-01",   // ոչ պարտադիր՝ "custom" միջակայքի համար
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (ցենտ)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Քվոտայի սահմանափակումների կիրառում

Յուրաքանչյուր API բանալու քվոտան վերահսկվում է երկու տեղում.

1. **Փափուկ սահմանաչափ** (`quotaWarnAt`)՝ կառավարման վահանակում նախազգուշացում, երբ օգտագործումը գերազանցում է շեմը
2. **Խիստ սահմանաչափ** (`quotaLimit`)՝ գերազանցման դեպքում հարցումը մերժվում է HTTP 429 կարգավիճակով

### Կարգավորում

```ts
// Յուրաքանչյուր API բանալու համար
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — ցուցադրել նախազգուշացում
  quotaLimit: 10_00,    // $10.00 — խիստ արգելափակում
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Սահմանափակումների կիրառման ընթացք

```
Հարցում ──▶ quotaCheck()
              │
              ├── Սահմանաչափի ներսո՞ւմ է  ──▶ թույլատրել
              │
              └── Սահմանաչափը գերազանցվա՞ծ է  ──▶ 429 Չափազանց շատ հարցումներ
                                   Retry-After վերնագրով
```

### Քվոտայի վիճակի պատկերներ

`quotaSnapshots` աղյուսակը պահում է **քվոտայի պատմական վիճակը**՝ միտումների վերլուծության համար.

| Դաշտ | Նկարագրություն |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Հետևվող բանալին |
| `window` | "day" | "week" | "month" |
| `used` | Այս ժամանակահատվածում օգտագործված ծախսը (ցենտ) |
| `limit` | Սահմանաչափը (ցենտ) |
| `resetAt` | Երբ է ժամանակահատվածը վերակայվում |
| `createdAt` | Երբ է արվել վիճակի պատկերը |

Վիճակի պատկերներն արվում են **յուրաքանչյուր հարցման ժամանակ**, որի ծախսը > 0 է, և օգտագործվում են՝

- Կառավարման վահանակում քվոտայի առաջընթացի սանդղակը ցուցադրելու համար
- Քվոտայի 30-օրյա միտումների գծապատկերները ցուցադրելու համար
- Երբ օգտագործումը մոտենում է սահմանաչափին, ծանուցումներ գործարկելու համար

### Օգտագործման վերլուծական տվյալների հարցում

Օգտագործման տվյալները հասանելի են կառավարման վահանակի կամ MCP գործիքների միջոցով, այլ ոչ թե արտահանման ուղիղ REST վերջնակետերի։ Հասանելի վերլուծական տվյալներ՝

- **`/api/usage/analytics`** — օգտագործման համախմբված ցուցանիշներ (խմբավորում ըստ մոդելի, մատակարարի, բանալու)
- **`/api/usage/quota`** — յուրաքանչյուր API բանալու քվոտայի ընթացիկ կարգավիճակը
- **`/api/usage/history`** — հարցումների պատմության մատյաններ

## Պահպանում և մաքրում

Օգտագործման տվյալների ծավալն ավելանում է յուրաքանչյուր հարցման համար մոտ 1-10 ԿԲ-ով։ Մեծ ծավալների դեպքում սա կարող է նշանակալի լինել։

### Պահպանման կարգավորումներ

Օգտագործման պատմության պահպանումը կարգավորվում է օգտատիրական միջերեսի տվյալների բազայի կարգավորումներում կամ `/api/settings/database`-ի միջոցով։

Լռելյայն օգտագործման պատմությունը պահպանվում է **90 օր**։

### Մաքրում

Հին գրառումները մաքրվում են `src/lib/db/cleanup.ts`-ի միջոցով՝

- Գործարկվում է ֆոնային cron գործընթացի կողմից
- Ջնջում է `usage_history`-ի այն գրառումները, որոնք ավելի հին են, քան պահպանման `usageHistory` կարգավորմամբ սահմանված ժամկետը

### Պահեստավորման ծավալի գնահատում

| Հարցումների հաճախականություն | 30 օրվա պահեստավորում | 90 օրվա պահեստավորում |
| ---------------------------- | --------------------- | --------------------- |
| 100 հարցում/օր               | ~3 ՄԲ                 | ~9 ՄԲ                 |
| 1,000 հարցում/օր             | ~30 ՄԲ                | ~90 ՄԲ                |
| 10,000 հարցում/օր            | ~300 ՄԲ               | ~900 ՄԲ               |
| 100,000 հարցում/օր           | ~3 ԳԲ                 | ~9 ԳԲ                 |

Շատ մեծ տրաֆիկի դեպքում դիտարկեք՝

- Պահպանման ժամկետի կրճատումը տվյալների բազայի կարգավորումների միջոցով
- Չմշակված գրառումների փոխարեն `aggregated_metrics`-ի օգտագործումը (միայն վերլուծության համար)

## Ծախսերի օպտիմալացման խորհուրդներ

### 1. Օգտագործեք համապատասխան մոդելը

```bash
# Արագ պատասխան — օգտագործեք էժան և արագ մոդել
curl -d '{"model":"auto/fast","messages":[...]}'

# Բարդ առաջադրանք — ընտրեք որակը
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Միացրեք քեշավորումը

Anthropic-ի հարցումների քեշավորումը խնայում է **90%՝ կրկնվող համատեքստի դեպքում**.

```ts
// Քեշավորումն ավտոմատ է. պարզապես ներառեք նույն ծավալուն համակարգային հրահանգը
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Կքեշավորվի ավտոմատ կերպով
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Օգտագործեք սեղմում

RTK + Caveman սեղմումը խնայում է **15-95%՝ գործիքների ինտենսիվ օգտագործմամբ աշխատաշրջաններում**.

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Սահմանեք յուրաքանչյուր բանալու քվոտաները

Միշտ սահմանեք `quotaLimit`՝ անվերահսկելի ծախսերը կանխելու համար.

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Ամսական $10 սահմանաչափ
```

### 5. Ստուգեք ամենաշատ սպառողներին

Օգտագործեք կառավարման վահանակը կամ **`/api/usage/analytics`**՝ ըստ API բանալու խմբավորելու և ըստ ծախսի դասավորելու համար.

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Խնդիրների վերացում

### «Ծախսը սպասվածից բարձր է»

1. Ստուգեք **`/api/usage/analytics?groupBy=model`** — գտեք թանկ մոդելը
2. Ստուգեք **`/api/usage/analytics?groupBy=apiKey`** — գտեք մեծ սպառում ունեցողին
3. Համոզվեք, որ գնային տվյալները թարմ են՝ `POST /api/pricing/sync`

### «Գրառումները բացակայում են»

- Ստուգեք տվյալների բազայի պահպանման կարգավորումները՝ Կառավարման վահանակ → Տվյալների բազա → Մաքրում բաժնում — հին գրառումները ջնջվում են պարբերական մաքրման առաջադրանքի միջոցով (`src/lib/db/cleanup.ts`)
- Ստուգեք սխալները `src/lib/db/usage*.ts`-ում — տվյալների բազայում գրելու ձախողումները գրանցվում են մատյանում, բայց չեն ցուցադրվում
- Համոզվեք, որ հարցումն իսկապես հասել է `chatCore` — ստուգեք համակցված երթուղավորումը

### «Քվոտան չի կիրառվում»

- Ստուգեք բանալու `quotaLimit` կարգավորումը
- Համոզվեք, որ `quotaWindow`-ը ճիշտ է սահմանված
- Փնտրեք `quotaSnapshots` գրառումները — դրանք պետք է ստեղծվեն յուրաքանչյուր հարցման ժամանակ
