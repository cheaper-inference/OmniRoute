> **Կարճ ասած**․ OmniRoute-ը տրամադրվում է ներկառուցված առողջական վիճակի մշտադիտարկմամբ, մատակարարների ավտոպիլոտով, քվոտաների հետագծմամբ և դիտարկելիության ինտեգրման կետերով։ Այս ուղեցույցն անդրադառնում է կառավարման վահանակին, ծանուցումներին և խնդիրների ախտորոշմանը։

**Աղբյուրներ․**

- `src/lib/monitoring/observability.ts` — դիտարկելիության ակնթարթային պատկեր
- `src/lib/monitoring/comboHealthAutopilot.ts` — կոմբինացիաների առողջական վիճակի ավտոպիլոտ
- `src/lib/monitoring/providerHealthAutopilot.ts` — մատակարարների ավտոպիլոտ
- `src/lib/monitoring/providerHealthMatrix.ts` — մատակարարների առողջական վիճակի մատրից
- `src/lib/localHealthCheck.ts` — տեղային առողջական վիճակի ստուգում
- `src/lib/tokenHealthCheck.ts` — թոքենի թարմացման առողջական վիճակ
- `src/lib/proxyHealth.ts` — պրոքսիի առողջական վիճակի քեշ (նկարագրված է PROXY_GUIDE.md-ում)

## Կառավարման վահանակի էջեր

### `/dashboard/health` (Համակարգի առողջական վիճակ)

Առողջական վիճակի վերին մակարդակի կառավարման վահանակը ցուցադրում է․

| Բաժին                       | Ինչ է ցուցադրում                                        |
| --------------------------- | ------------------------------------------------------- |
| **Սերվերի վիճակ**           | Աշխատաժամանակ, տարբերակ, պորտ, ակտիվ կապեր              |
| **Տվյալների բազա**          | Կապ, ամբողջականություն, WAL-ի չափ, վերջին միգրացիաներ   |
| **Մատակարարների ամփոփում**  | Ակտիվների քանակ, առողջների քանակ, բաց անջատիչների քանակ |
| **Քվոտայի մշտադիտարկիչներ** | Ակտիվ աշխատաշրջաններ, ծանուցումներ, սպառված քվոտաներ    |
| **Վերջին սխալներ**          | Վերջին 10 սխալները՝ կանչերի ստեկերով                    |
| **Ռեսուրսների օգտագործում** | Հիշողություն, CPU, կույտի ճնշման ցուցիչ                 |

## Առողջության ստուգում API

OmniRoute մերկացնում է** երկու** HTTP առողջության մակերեսներ. Նրանք փոխարինելի չեն նվագախմբի հետ:

| Ճանապարհ                     | Նպատակը                                                                   | Քաշը                                           | Օգտագործել համար                                                                              |
| ---------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `GET /healthz`               | Կյանքի ցիկլ liveness/readiness (`ok` / `starting` / `stopping`)           | Չնչին (միայն փուլային դրոշակ)                  | Կուբերնետես** պատրաստակամություն** ; փափուկ** աշխուժություն** եթե դուք պետք է օգտագործեք HTTP |
| `GET /api/monitoring/health` | Deep համակարգի + մատակարարի ամփոփում (DB, կույտ, կատալոգի հաշվառումներ,…) | Ծանր (համաժամեցնել DB / մոնիտորինգի աշխատանքը) | Վահանակներ, սև տուփի խորը ստուգումներ, Docker ի ներկառուցված առողջության ստուգում             |

> **Նշում.** Մատակարարի առողջության մատրիցները, ավտոմատ օդաչուի խնդիրները, քվոտայի մոնիտորները, նշանների առողջությունը և `/api/monitoring/health` ից դուրս ուշացման մանրամասները հասանելի են**MCP գործիք** `observability_snapshot` կամ the** վահանակ** էջեր — չկան հատուկ REST երթուղիներ նրանց համար:

Երկու երթուղիներն էլ անցնում են** նույն հանգույցի իրադարձությունների հանգույցը** որպես հարցումների մշակում: CPU-ով կապված ուղին (խոշոր `GET /v1/models` կատալոգի աշխատանք, երկար համատեքստի սեղմում / նշանների հաշվարկ) կարող է հետաձգել** բոլորը** HTTP կարգավորիչներ, ներառյալ `/healthz`: Event-loop զբաղված ≠ գործընթացը մեռած է: Նախընտրում են խոզը ամրացնել; զոնդի թյունինգը միայն նվազեցնում է կեղծ սպանությունները:

### Նվագախմբի թեթև զոնդ

```bash
GET /healthz
# or HEAD /healthz
```

- **200 թ** + body `ok`, երբ սերվերի կյանքի ցիկլի փուլը պատրաստ է
- **503 թ** + `starting` / `stopping` բեռնման կամ անջատման ժամանակ
- Իրականացում՝ `src/app/healthz/route.ts` (առանց DB ping)


#### `credentialHealth`. զոնդ-քեշ ընդդեմ SQLite `test_status`

`GET /api/monitoring/health` → `credentialHealth` է** հիշողության մեջ զոնդ-cache չափիչ** , ոչ մի կենդանի աղբանոց `provider_connections.test_status`. #12532 ից հետո հարցման ուղին կարդում է միայն `getCachedCredentialHealthSummary()` ; ֆոնային զոնդերը թարմացնում են քեշը իրադարձությունների հանգույցից:

| Շերտ                       | Որտեղ                                                                 | Ինչ է դա նշանակում                                                                                                                                                                                                                        |
| -------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Զոնդ-քեշաչափ               | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | Վերջին հավատարմագրային-առողջական հետազոտության արդյունքները դեռ պահպանվում են գործընթացի հիշողության մեջ: `source` միշտ `probe-cache`.                                                                                                    |
| Չհաջողվեց կապի մանրամասներ | `credentialHealth.failedConnections`                                  | Ներկա** միայն այն ժամանակ, երբ `failed > 0`** . Քեշի տողերի սահմանափակված ցուցակ `status=error` ով (`connectionId`, `status`, sanitized `lastError` / `lastErrorType`): `failedOmitted` սահմանվում է այն ժամանակ, երբ ցուցակը ծածկված էր: |
| SQLite կպչուն կարգավիճակ   | `credentialHealth.staleDbNonOkCount`                                  | Համարը** ակտիվ** (`is_active=1`) միացման տողեր, որոնց պահպանված `test_status` հայտնի ոչ ok է (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`):                                                           |

Երկու շերտերը կարող են դիտավորյալ չհամաձայնվել.

- Չափել `failed=0` մինչդեռ `staleDbNonOkCount>0` — SQLite դեռևս ունի կպչուն `test_status` (օրինակ `expired` կամ `credits_exhausted`), որը վերջին զոնդ-քեշի լուսանկարը չի համարվում `status=error`:
- Չափիչ `failed>0` մինչդեռ SQLite առողջ տեսք ունի — վերջին հետաքննությունը ձախողվեց և պահվում է քեշում; DB տողը չի թարմացվել կամ ավելի ուշ մաքրվել է:

Այս վերջնակետը քերելիս մի զգուշացրեք միայն `provider_connections.test_status` վրա: Օգտագործեք `failed` + `failedConnections` կենդանի զոնդերի խափանումների համար, և `staleDbNonOkCount` երբ ձեզ անհրաժեշտ է կայուն կպչուն կարգավիճակի հաշվարկ:

### Kubernetes-ի հետաքննության առաջարկություններ

OmniRoute է ա** մեկ հանգույցի գործընթաց** (մեկ իրադարձության հանգույց): Stock Docker `HEALTHCHECK` թիրախ է թեթև `/healthz`: `/api/monitoring/health` է** չափազանց ծանր** կուբելետի աշխուժության ընդմիջումների համար:

| Զոնդ                   | Առաջարկվող թիրախ                                                                      | Նշումներ                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Սկսնակ**             | HTTP `GET /healthz` երկար `failureThreshold` ով (կամ մեծ `startPeriod`)               | Cold start + SQLite միգրացիան կարող է գերազանցել մի քանի վայրկյան                                                                                                                                                                                                                                                                                                                                              |
| **Պատրաստակամություն** | HTTP `GET /healthz`                                                                   | Կյանքի ցիկլ `ok` / `starting` / `stopping` (200 ընդդեմ 503): Դեռևս փչում է, եթե հանգույցն արգելափակված է պրոցեսորով: Ա** 200-ը մի քանի վայրկյանում առողջարար չէ** (#10303) — դա նշանակում է, որ իրադարձությունների հանգույցը սովամահ է եղել նախքան 3 բայթ մշակողի գործարկումը                                                                                                                                  |
| **Կենսունակություն**   | HTTP `GET /livez`,** կամ TCP** հիմնական սպասարկման պորտում (`PORT`, լռելյայն `20128`) | `/livez` ն գործում է միայն գործընթացում (միշտ 200, եթե կառավարիչը աշխատում է): Այն դեռևս կիսում է իրադարձությունների հանգույցը — զբաղված ≠ dead, և այն ավելի լավ չի հայտնաբերում իրադարձությունների հանգույցի սովը (#10303), քան TCP ն: Նախընտրել**TCP** եթե HTTP զոնդերը դուրս են եկել catalog/compression բեռի տակ; անել** ոչ** սպանել պատիճը կարճ իրադարձությունների հանգույցի կրպակների վրա, ցանկացած կերպ |
| **Խորը առողջություն**  | `GET /api/monitoring/health` արտաքին ստուգիչից                                        | Ոչ թե kubelet `livenessProbe` / tight `readinessProbe`                                                                                                                                                                                                                                                                                                                                                         |

Ձևի օրինակ (կարգավորեք շեմերը ձեր սառը մեկնարկի և սեղմման բեռի համաձայն).

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Under event-loop stall HTTP /livez can still time out. TCP is the
  # conservative alternative:
  # tcpSocket:
  #   port: http
```

**Մի՛** կետ kubelet** աշխուժություն** ժամը `/api/monitoring/health`. Այդ ուղին իրական DB/monitoring աշխատանք է կատարում և բեռի տակ կեղծ դրական կլինի:

Առնչվող՝ [#10052](https://github.com/cheaper-inference/OmniRoute/issues/10052) (զոնդեր, երբ իրադարձության հանգույցը զբաղված է), [#9685](https://github.com/cheaper-inference/OmniRoute/issues/9685) / [#10055](https://github.com/cheaper-inference/OmniRoute/pull/10055) (կատալոգի գնագոյացման խոզ), [#10117](https://github.com/cheaper-inference/OmniRoute/issues/10117) (սեղմման նշանի հաշվարկի խոզ):

### systemd watchdog (սառեցված իրադարձությունների հանգույց)

Systemd host-ում OmniRoute ասում է ծառայության մենեջերին, երբ այն պատրաստ է և շարունակում է այն ձայնագրել, այնպես որ սերվերը, որի իրադարձությունների հանգույցը խրված է, սպանվում և վերագործարկվում է՝ արթուն մնալու և լռելու փոխարեն: Ping-երը գալիս են սերվերի սեփական իրադարձությունների հանգույցից. երբ այն արգելափակվում է, դրանք դադարում են, և systemd-ը վերագործարկում է ծառայությունը, երբ `WatchdogSec` անցնում է առանց մեկի:

[`omniroute autostart enable`](../../bin/cli/tray/autostart.mjs) սրանով արդեն օգտատերերի միավոր է գրում։ Մի միավոր, որը դուք ինքներդ եք գրում (կանխադրված `Type=simple`) չի ստանում հսկիչ, այնպես որ ավելացրեք այս տողերը դրա `[Service]` բաժնում.

```ini
[Service]
Type=notify
NotifyAccess=all
WatchdogSec=180
TimeoutStartSec=300
```

Ստեղծված միավորը սահմանում է `Restart=on-failure`, այնպես որ ավելացրե՛ք այդ տողը նաև — առանց դրա, պահակորդը միայն սպանում է խրված ծառայությունը՝ այն վերագործարկելու փոխարեն:

- `Type=notify`. ծառայությունը «սկսվում է», երբ սերվերը ուղարկում է `READY=1`, այլ ոչ թե երբ պրոցեսը ընդհատվում է: `TimeoutStartSec` սահմանում է դանդաղ մեկնարկ:
- `NotifyAccess=all`. ping-երը ուղարկվում են սերվերի պրոցեսի միջոցով, որը `omniroute serve` վերահսկիչի երեխա է:
- `WatchdogSec`: ping-երը դուրս են գալիս ամեն 60 վայրկյանը մեկ, այնպես որ օգտագործեք** 120 կամ ավելի** . Ավելի փոքր արժեքները կվերագործարկեն առողջ սերվերը:
- Գործարկել `omniroute serve` առաջին պլանում: `--daemon` անջատում է սերվերը միավորի cխմբից և ծանուցման ձեռքսեղմումը երբեք չի ավարտվում:

Ստուգեք, որ այն ակտիվ է վերագործարկումից հետո.

```bash
systemctl --user show omniroute -p WatchdogUSec -p WatchdogTimestamp
```

`WatchdogUSec` ցույց է տալիս կազմաձևված ուշացումը և `WatchdogTimestamp` առաջ է շարժվում ամեն րոպե: Վերագործարկումը, որն առաջացել է հսկիչ շան կողմից, գրանցվում է որպես `Result=watchdog`: Պինգերն անջատելու համար միավորը ինչպես կա, սահմանեք `OMNIROUTE_DISABLE_SD_NOTIFY=1`; առանց `NOTIFY_SOCKET` (տերմինալ, Docker, Electron, Windows) ոչինչ չի ուղարկվում։

Դիտորդը միայն ստուգում է, որ իրադարձությունների հանգույցը շարունակում է աշխատել: Դանդաղ, բայց դեռ պտտվող սերվերը չի վերագործարկվում:

### Ընտրովի հարցում-ուղու աշխատանք (հիշողություն, հմտություններ, նշանի թարմացում)

Հիշողության արդյունահանումը, հմտությունների ներարկումը և OAuth նշանի թարմացումը կիսում են** հիմնական հանգույցի իրադարձությունների հանգույց** `/healthz`. Դրանք վահանակի անջատման գործառույթներ են (`memoryEnabled`, `skillsEnabled`), այլ ոչ թե աշխատողների լողավազան: Տես [Environment — event-loop cost](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349).

## Մատակարարի առողջության ավտոպիլոտ

`providerHealthAutopilot.ts` մոդուլը **ինքնավերականգնվող համակարգ** է, որը՝

1. Հայտնաբերում է մատակարարի խնդիրները (շղթայի բաց վիճակ, սպասման ժամանակահատվածներ, արգելափակումներ, քվոտայի նախազգուշացումներ)
2. Ստեղծում է դրանք լուծելու համար **առաջարկվող գործողություններ**
3. Ընտրովի կերպով **ինքնաշխատ կատարում է** ցածր ռիսկով գործողությունները

### Հայտնաբերվող խնդիրների տեսակները

| Խնդրի տեսակ                  | Լրջություն     | Պայմանի օրինակ                             |
| ---------------------------- | -------------- | ------------------------------------------ |
| `provider_circuit_open`      | կրիտիկական     | Շղթայի անջատիչը բաց է 5 ձախողումից հետո    |
| `provider_circuit_half_open` | նախազգուշացում | Շղթան ստուգում է վերականգնումը             |
| `connection_cooldown`        | նախազգուշացում | Միացումը սպասման ռեժիմում է 429-ից հետո    |
| `stale_connection_error`     | նախազգուշացում | Վերջին թարմացումը ձախողվել է 30+ րոպե առաջ |
| `terminal_connection_error`  | կրիտիկական     | OAuth-ը հետ է կանչվել, բանալին անվավեր է   |
| `inactive_connection`        | տեղեկատվական   | Միացումն անջատված է կարգավորումներում      |
| `model_lockout`              | նախազգուշացում | Որոշակի մոդել կարանտինում է                |
| `quota_monitor_warning`      | նախազգուշացում | Քվոտայի օգտագործումը 80%+ է                |

### Ստեղծվող գործողությունների տեսակները

| Գործողություն                  | Ռիսկ  | Նկարագրություն                           |
| ------------------------------ | ----- | ---------------------------------------- |
| `clear_provider_breaker`       | միջին | Շղթայի անջատիչը վերակայել փակ վիճակի     |
| `clear_connection_cooldown`    | ցածր  | Հեռացնել միացման սպասման ժամանակահատվածը |
| `clear_stale_connection_error` | ցածր  | Մաքրել հնացած սխալի դրոշակը              |
| `clear_model_lockout`          | ցածր  | Կրկին միացնել կարանտինում գտնվող մոդելը  |
| `reactivate_connection`        | միջին | Կրկին միացնել ապաակտիվացված միացումը     |
| `deactivate_connection`        | բարձր | Անջատել խնդրահարույց միացումը            |

### API

> **REST վերջնակետ չկա։** Ավտոպիլոտի խնդիրները հասանելի են MCP-ի `observability_snapshot` գործիքի կամ կառավարման վահանակի միջոցով։ Ավտոպիլոտն աշխատում է ներքին մակարդակում․ դրա վարքագիծը կարգավորվում է կարգավորումների DB-ի միջոցով (յուրաքանչյուր միացման `autopilotMode` դաշտով), ոչ թե միջավայրի փոփոխականներով. ավտոպիլոտի ռեժիմի միջավայրի փոփոխականի համար `grep -rn`-ը վերադարձնում է զրո արդյունք։

### Ավտոպիլոտի ռեժիմ

Լռելյայնորեն ավտոպիլոտն աշխատում է **ձեռքով ռեժիմում**․ այն հայտնաբերում է խնդիրները և ստեղծում առաջարկվող գործողություններ, սակայն դրանք ինքնաշխատ չի կիրառում։ Գործողությունները կարելի է կիրառել կառավարման վահանակի միջոցով։

- Առաջարկում է անջատել չաշխատող թիրախները

## Քվոտայի մոնիտորներ

`observability.ts`-ը տրամադրում է **յուրաքանչյուր աշխատաշրջանին հատուկ քվոտայի մոնիտորներ** բաժանորդագրային մատակարարների համար (Claude Code, Codex, GitHub Copilot)․

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### Կարգավիճակների նշանակությունները

| Կարգավիճակ  | Երբ                              | UI գործողություն                                   |
| ----------- | -------------------------------- | -------------------------------------------------- |
| `starting`  | Սկզբնական հարցումն ընթացքի մեջ է | Բեռնման պտտվող ցուցիչ                              |
| `idle`      | Վերջերս ակտիվություն չի եղել     | Թաքցված է կառավարման վահանակից                     |
| `healthy`   | Մնացել է քվոտայի > 50%-ը         | Կանաչ կետ                                          |
| `warning`   | Մնացել է քվոտայի < 50%-ը         | Դեղին նախազգուշացում                               |
| `exhausted` | Քվոտան = 0% է                    | Կարմիր արգելափակում, ուղղորդում հաջորդ մատակարարին |
| `error`     | Հարցումը ձախողվել է              | Կարմիր կետ, շուտով կրկնել                          |

### API

> **REST վերջնակետ չկա։** Քվոտայի մոնիտորի տվյալները հասանելի են MCP-ի `observability_snapshot` գործիքի կամ կառավարման վահանակի միջոցով։

## Թոքենի վիճակի ստուգում

OAuth մատակարարներին (Claude Code, GitHub Copilot, Cursor) անհրաժեշտ է **թոքենների պարբերական թարմացում**։ `src/lib/tokenHealthCheck.ts`-ը գործարկում է ֆոնային ժամանակացույց.

- **Ստուգման ցիկլ**. յուրաքանչյուր 60 վայրկյանը մեկ (`TICK_MS = 60 * 1000` ստուգման ցիկլը՝ `src/lib/tokenHealthCheck.ts:30`-ում)
- **Յուրաքանչյուր կապի վիճակի ստուգման միջակայք**. լռելյայն՝ 60 րոպե (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`), կարգավորվում է կարգավորումների DB-ի միջոցով
- **Կանխարգելիչ թարմացում 401-ի դեպքում**. մշակվում է յուրաքանչյուր կապի interceptor-ի կողմից

### Թոքենի վիճակի կարգավիճակ

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### Կազմաձևում

Թոքենի վիճակի ստուգման կազմաձևումը ներքին կերպով մշակվում է `tokenHealthCheck.ts`-ի կողմից։

### Թոքենի վիճակ

> **REST վերջնակետ չկա։** Թոքենի վիճակի տվյալները հասանելի են կառավարման վահանակի կամ MCP-ի `observability_snapshot` գործիքի միջոցով։

> Webhook զգուշացումները կազմաձևելու համար օգտագործվում է Settings միջերեսի նույն ընթացակարգը։ PagerDuty Events API v2-ի երթուղավորման բանալիները կազմաձևվում են Settings միջերեսում։

### Հատուկ Webhook (JSON)

> Կաշխատի ցանկացած HTTP վերջնակետ, որն ընդունում է JSON մարմնով POST հարցումներ։ URL-ը կազմաձևեք Settings միջերեսում։

```json
  }
```

## Խնդիրների ախտորոշում

### «Մատակարարը նշված է որպես առողջ, բայց հարցումները ձախողվում են»

1. Ստուգեք **ինքնավար կառավարման խնդիրները**. հնարավոր է՝ որևէ մոդել արգելափակված է
2. Դիտեք **վերջին սխալները**՝ սխալի կոնկրետ դասը պարզելու համար
3. Փորձեք մատակարարի քարտում առկա **կապի ստուգումը**
4. Ստուգեք՝ արդյոք մատակարարը **վերին մակարդակում արագության սահմանափակման տակ է** (տեղային մակարդակում տեսանելի չէ)

### «Քվոտան առողջ է նշված, բայց ես տեսնում եմ 429 սխալներ»

- 429-ը նշանակում է, որ, ըստ մատակարարի, դուք սպառել եք ձեր քվոտան
- OmniRoute-ի քվոտայի հետևման տվյալները կարող են **հնացած** լինել. հավաստի տվյալները գտնվում են մատակարարի կողմում
- Քվոտայի տվյալներն ավտոմատ թարմացվում են ներքին քվոտայի մոնիթորի միջոցով

### «Համակցությունը ձախողվում է, բայց բոլոր թիրախներն առողջ են երևում»

- Թիրախների դասավորման խնդիրների համար ստուգեք **համակցության առողջության** կառավարման վահանակը
- Դիտեք **պահուստային տարբերակին անցնելու իրադարձությունները**. հնարավոր է՝ համակցությունը չափազանց արագ է սպառում բոլոր տարբերակները
- Համոզվեք, որ **ռազմավարությունը** համապատասխանում է ձեր օգտագործման դեպքին (առաջնահերթություն, հերթափոխային բաշխում կամ ավտոմատ)

### «Տվյալների բազայի առողջության ստուգումը ձախողվում է»

- Գործարկեք `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- Եթե արդյունքը "ok" է՝ սա կեղծ տագնապ է, առողջության ստուգումը չափազանց խիստ է
- Ցանկացած այլ արդյունքի դեպքում **կանգնեցրեք OmniRoute-ը** և հետևեք [աղետից վերականգնման ուղեցույցին](./DATABASE_GUIDE.md#disaster-recovery)

### «Հիշողության կույտի ճնշումը կրիտիկական է»

```bash
# Ստուգեք կույտի ընթացիկ վիճակը
node -e "console.log(process.memoryUsage())"

# Գործարկեք GC-ն ձեռքով (եթե օգտագործվում է --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# Նվազեցրեք միաժամանակյա հարցումների քանակը (սահմանեք կառավարման վահանակի Settings էջի միջոցով, ոչ թե միջավայրի փոփոխականով)
# `MAX_CONCURRENT_REQUESTS` միջավայրի փոփոխական գոյություն չունի. կազմաձևեք այն Settings → Concurrency բաժնում։
```
