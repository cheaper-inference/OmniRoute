Օգտագործեք այս ուղեցույցը՝ pull request-ի համար մշակման նվազագույն հուսալի ցիկլն ընտրելու նպատակով։ Այն չի
փոխարինում ստորև հղված՝ առանձին ոլորտներին վերաբերող ճարտարապետական և անվտանգության փաստաթղթերին․ այն կապում է յուրաքանչյուր տարածված
փոփոխության տեսակն իր պայմանագրերի, նպատակային ստուգումների և CI ծածկույթի հետ։

## Յուրաքանչյուր փոփոխության անցած ուղին

1. **Խմբագրելուց առաջ ընտրեք բազային ճյուղը։** Գտեք ամենաբարձր ակտիվ `release/v*` ճյուղը և ստեղծեք նոր ճյուղ
   դրա վերջին commit-ից։ Որպես թիրախ ընտրեք այդ ճյուղը, ոչ թե `main`-ը։ Եթե թողարկման սառեցում է գործում, մի ընտրեք սառեցված
   ճյուղը որպես թիրախ․ օգտագործեք հաջորդ ակտիվ ցիկլը, որը նկարագրված է
   [Ճյուղավորման և թողարկման մոդելում](BRANCHING_MODEL.md)։
2. **Նշեք պայմանագրերը։** Բացահայտեք յուրաքանչյուր կատալոգ, schema, գեներացված արտեֆակտ, հանրային API կամ օգտատիրոջ
   միջերես, որի վրա ազդում է փոփոխությունը։ Ստորև բերված աղյուսակը ներկայացնում է նվազագույն մեկնարկային հավաքածուն։
3. **Գրեք կամ թարմացրեք նպատակային թեստերը։** `src/`, `open-sse/`, `electron/` կամ
   `bin/` պանակներում production փոփոխությունները պահանջում են ավտոմատացված թեստ նույն PR-ում։ Գործարկեք վարքագիծը
   հաստատող ամենափոքր թեստային ֆայլերը, ապա՝ նշված նպատակային ստուգումները։
4. **Թույլ տվեք CI-ին գործարկել լայն մատրիցը։** Ամբողջական unit բաժինները, Vitest-ը, coverage ratchet-ը և
   production build-ը գործարկվում են PR-ում։ Լայն փաթեթը տեղային միջավայրում գործարկեք միայն այն դեպքում, երբ նպատակային ձախողումը ցույց է տալիս
   ավելի լայն ազդեցություն, կամ երբ փոփոխությունն ընդգրկում է մի քանի ենթահամակարգ։
5. **Վերանայելուց առաջ համաժամեցրեք։** Ներբեռնեք ակտիվ բազային ճյուղը, ուսումնասիրեք դրա նոր commit-ները և դրա նկատմամբ
   ձեր diff-ը, ապա կատարեք բազային ճյուղի rebase կամ merge՝ համաձայն մասնակցի աշխատանքային հոսքի։ Գեներացված ֆայլերի
   և կատալոգների conflict-ները լուծեք դրանց սկզբնաղբյուրում, կրկին գեներացրեք դրանք, վերագործարկեք նպատակային ցիկլը և հաստատեք, որ
   PR-ը դեռ ուղղված է ակտիվ թողարկման ճյուղին։
6. **Գրանցեք ապացույցները։** PR ձևանմուշում թվարկեք գործարկված հրամանները, ավելացված կամ փոփոխված բոլոր թեստային ֆայլերը,
   migration-ները կամ feature flag-երը և CI-ին հատուկ՝ դեռևս սպասվող ցանկացած վավերացում։

## Հիմնական ուղիներն ըստ փոփոխության տեսակի

Ստորև նշված հրամանները նվազագույն նպատակային ստուգումներ են, այլ ոչ թե փոփոխված վարքագիծն ուղղակիորեն
ծածկող թեստը բաց թողնելու թույլտվություն։

### Provider

**Պայմանագրեր**

- Provider-ի սահմանումը `src/shared/constants/providers/`-ում և դրա կազմավորումը
  `src/shared/constants/providers.ts`-ում։
- Model-ները և հնարավորությունները `open-sse/config/providerRegistry.ts`-ում կամ դրանից առանձնացված registry ֆայլերում։
- Executor/translator-ի ընտրությունը, OAuth-ի կամ API key-ի կազմաձևումը, dashboard-ի asset-ները և գեներացված
  provider reference-ը՝ կիրառելի լինելու դեպքում։
- Հանրային credential-ները պետք է օգտագործեն `resolvePublicCred()`․ error response-ները պետք է օգտագործեն ընդհանուր sanitized
  error helper-ները։ Տե՛ս `docs/security/PUBLIC_CREDS.md` (git-ում է, չի ներառվում `/docs`-ում) և
  [Սխալների սանիտարացում](../security/ERROR_SANITIZATION.md)։

**Նպատակային ցիկլ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # երբ կատալոգը փոխվում է․ commit արեք գեներացված diff-ը
npm run lint
```

Թեստավորեք նաև ազդեցության ենթարկված յուրաքանչյուր request family՝ chat, Responses, images, embeddings, audio կամ video։
Գեներացված կատալոգի և golden diff-երը վերանայեք որպես պայմանագրային փոփոխություններ․ դրանք կուրորեն մի ընդունեք։

### Routing

**Պայմանագրեր**

- Հանրային strategy արժեքները և UI metadata-ն `src/shared/constants/routingStrategies.ts`-ում։
- Dispatch-ը և հերթականությունը `open-sse/services/combo.ts`-ում և `open-sse/services/combo/`-ում։
- Combo schema-ները, persistence-ը, resilience state-ը, model-ի հնարավորությունները և API/UI կառավարները։
- [Auto-Combo շարժիչը](../routing/AUTO-COMBO.md) և resilience-ի փաստաթղթերը, երբ վարքագիծը փոխվում է։

**Նպատակային ցիկլ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy-ի կամ dispatch-ի փոփոխություններ
npm run check:known-symbols      # strategy-ի գրանցման փոփոխություններ
npm run lint
```

Տեղային միջավայրում օգտագործեք deterministic mocked-upstream թեստեր։ Live combo smoke թեստերը պահանջում են credential-ներ և
ձեռքով են կատարվում․ դրանք չեն փոխարինում CI-ին։

### UI / UX

**Պայմանագրեր**

- Next.js route/page-ի և ընդհանուր component-ների սահմանները `src/app/`-ում և
  `src/shared/components/`-ում։
- API response-ի կառուցվածքները, loading/empty/error վիճակները, keyboard-ի և screen reader-ի վարքագիծը,
  responsive դասավորությունը, theming-ը և locale-ի ընդլայնումը։
- Անգլերեն UI սկզբնաղբյուր տողերը `src/i18n/messages/en.json`-ում․ օգտատիրոջը ցուցադրվող նոր տեքստը մի hard-code արեք։

**Նպատակային ցիկլ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Փոխազդեցության կամ տեսողական փոփոխությունների դեպքում գործարկեք հավելվածը և ստուգեք ինչպես նեղ, այնպես էլ լայն viewport-ներում։ CI-ն գործարկում է
production build-ը և ավելի լայն փաթեթները․ տեսողական վարքագիծը, միևնույն է, պահանջում է նպատակային component, Playwright
կամ փոփոխությանը համապատասխան՝ փաստաթղթավորված ձեռքով ստուգում։

### i18n

**Պայմանագրեր**

- `src/i18n/messages/en.json`-ը UI-ի սկզբնաղբյուրն է, իսկ `config/i18n.json`-ը՝ locale-ի սկզբնաղբյուրը։
- CLI կատալոգները պահվում են առանձին՝ `bin/cli/locales/`-ում։
- ICU placeholder-ներն ու tag-երը պահպանեք ճշգրտորեն։ Մի թարգմանեք product/provider/model անունները,
  protocol-ի և header-ի անունները, հրամանները, code/JSON identifier-ները, URL-ները, environment variable-ները կամ
  պաշտպանված տերմինները, ինչպիսիք են `OmniRoute`, `OAuth`, `MCP` և `A2A`։ Ընթացիկ սկզբնաղբյուր ցանկը գտնվում է
  `scripts/i18n/glossary/protected-terms.json`-ում։

**Նպատակային ցիկլ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # երբ CLI տողերը կամ կատալոգները փոխվում են
npm run lint
```

Սա ուղեցույց է առկա համակարգի համար, այլ ոչ թե դրա գործիքակազմը կամ key model-ն ընդլայնելու հրավեր։
i18n patch-երը պահեք խիստ նպատակային, քանի դեռ նախագծվում է փոխարինող համակարգը։ Մի գործարկեք արտաքին ծառայություններ
կանչող թարգմանության հրամաններ, եթե առաջադրանքը բացահայտորեն չի պահանջում գեներացված թարգմանություններ, և դուք
չեք վերանայել ստացված diff-ը։

### CLI

**Պայմանագրեր**

- Հանրային հրամաններն ու դրոշները `bin/cli/`-ում, գեներացված API հրամանները, ելքի կոդերը, stdout/stderr-ը և
  JSON ելքի կառուցվածքները, կազմաձևման/միջավայրի վարքագիծը և փաթեթավորված ֆայլերը։
- CLI-ի՝ օգտատիրոջը ցուցադրվող տողերը պետք է օգտագործեն CLI i18n շերտը և համաժամեցված պահեն `en`/`pt-BR` կատալոգները։
- Պահպանեք Node-ը որպես աջակցվող կատարման միջավայր և հրապարակված բինար պայմանագիրը։

**Կենտրոնացված ցիկլ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # գեներացված/փաթեթավորված CLI-ի փոփոխություններ
npm run check:pack-policy     # փաթեթի հանրային մակերեսի փոփոխություններ
npm run lint
```

Օգտագործեք ճշգրիտ հրամանը ժամանակավոր տվյալների գրացուցակում, երբ վարքագիծը կախված է վերլուծումից, ֆայլերից կամ ելքի
կարգավիճակից։ CI-ն կատարում է փաթեթի արտեֆակտների և էկոհամակարգի ավելի լայն ստուգումները։

### Տվյալների բազա

**Պայմանագրեր**

- Դոմենային մոդուլները գտնվում են `src/lib/db/`-ում․ ներմուծեք կոնկրետ մոդուլներն անմիջապես (`localDb.ts`-ի հին վերաարտահանման շերտը հեռացվել է)։
- Համարակալված, իդեմպոտենտ SQL միգրացիաները՝ `src/lib/db/migrations/`-ում, տրանզակցիաների անվտանգությունը, թարմացման
  վարքագիծը, ինդեքսները և սխեմայից կախված յուրաքանչյուր կանչող։
- Երթուղիներն ու մշակիչները երբեք ուղղակիորեն չպետք է կատարեն չմշակված SQL։

**Կենտրոնացված ցիկլ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Միգրացիա ավելացնելիս փորձարկեք և՛ նոր տվյալների բազան, և՛ նախորդ սխեմայից թարմացումը։ Տվյալների բազայի թեստերը
պետք է փակեն նկարագրիչները և մաքրման ընթացքում կանչեն `resetDbInstance()`։ Գործարկեք `npm run test:bun:db` միայն այն դեպքում,
երբ փոխվում է Bun-ի՝ հնարավորության սահմաններում աշխատող ադապտերի ուղին․ Node-ը շարունակում է մնալ հեղինակավոր հենքը։

### Կառուցում / տեղակայում

**Պայմանագրեր**

- Արմատային և աշխատանքային տարածքների մանիֆեստները/կողպման ֆայլը, `scripts/build/`-ը, Next.js-ի ինքնուրույն փաթեթի հավաքումը, `dist/`
  փաթեթի բովանդակությունը, Electron-ի հարթակային մետատվյալները, CI աշխատանքային հոսքերը և տեղակայման վերահսկիչ նշիչները։
- Node-ի աջակցվող միջակայքերը և `CLAUDE.md`-ում Bun-ի թույլատրված օգտագործումը պետք է անփոփոխ մնան։
- Կառուցման արտեֆակտները չպետք է հետագծվեն․ կիրառվում են կախվածությունների, լիցենզիաների, աշխատանքային հոսքերի և փաթեթների քաղաքականությունները։

**Կենտրոնացված ցիկլ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # կախվածության կամ կողպման ֆայլի փոփոխություններ
npm run check:pack-policy      # հրապարակված փաթեթի մակերեսի փոփոխություններ
npm run lint
```

Տեղային միջավայրում օգտագործեք `npm run build` միայն այն դեպքում, երբ փոփոխությունն ազդում է կոմպիլյացիայի, ինքնուրույն փաթեթի հավաքման, ռեսուրսների
կամ կատարման միջավայրի փաթեթավորման վրա։ Օգտագործեք `npm run build:release` միայն թողարկման/տեղակայման վավերացման համար։ CI-ի կառուցումը
վերջնական միջհարթակային ազդանշանն է․ հարթակին հատուկ Electron-ի փոփոխությունների համար անհրաժեշտ է համապատասխան կենտրոնացված կառուցման
կամ արագ ստուգման ապացույց։

## Մշակողի սկրիպտներ համօգտագործվող մեքենայի համար

Երկու `scripts/dev/` օժանդակ սկրիպտներ սահմանում են տեղային աշխատանքային ցիկլը devbox-ում, որտեղ այլ աշխատաշրջաններ նույնպես ակտիվ են․

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD միջակայքի ֆայլերը
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # հենց այս ֆայլերը
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # մեկուսացված worktree, անվտանգ զուգահեռ աշխատանքի համար
```

- `typecheck-touched.sh`-ը տիպերի ստուգում է կատարում միայն փոփոխված `.ts/.tsx` ֆայլերի համար՝ օգտագործելով ժամանակավոր
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`)՝ 6 GB heap-ով, ուստի այն փոխարինում է ամբողջ նախագծի համար նախատեսված `tsc -p tsconfig.json`
  հրամանին, որը ծանրաբեռնված մեքենայի վրա սպառում է ամբողջ հիշողությունը։ Այն ցուցադրում է փոփոխված ֆայլերի սխալները՝ գումարած մեկ ամփոփ տող, և ավարտվում է
  `1` կոդով՝ փոփոխված ֆայլերում սխալների դեպքում, `2` կոդով՝ երբ միակ սխալները ներմուծված ֆայլերում են կամ tsc-ն դադարել է
  առանց ախտորոշիչ հաղորդագրությունների (կարդացեք նրա նշած մատյանը՝ `_artifacts/typecheck-touched/`-ի ներքո), և `0` կոդով՝ երբ
  սխալներ չկան։ Ժամանակավոր tsconfig-ը միշտ հեռացվում է․ երբեք այն մի commit արեք։
- `new-worktree.sh`-ը հաջորդականացնում է միաժամանակյա գործարկումները `<git-common-dir>/omniroute-new-worktree.lock`-ի միջոցով
  (լռելյայն սպասում է մինչև 600 վրկ՝ ցուցադրելով տեսանելի հաղորդագրություն․ սկրիպտի վերնամասում նկարագրված է
  այս արժեքը վերասահմանելու եղանակը) և հետ է շրջում
  իր ստեղծած ճյուղը, երբ `git worktree add`-ը ձախողվում է մինչև worktree-ի գոյանալը, ուստի կրկին փորձելու համար
  ձեռքով `git branch -D` գործարկելու կարիք չկա։ Կոշտ հղումներով `node_modules`-ը և `.husky/_` պատճենը մնում են անփոփոխ։

## Տեղային թեկնածուի աշխատանքային ցիկլ

Ելակոդի թեստերը չեն կարող ապացուցել, որ փաթեթավորված արտեֆակտը գործարկվում է․ փաթեթավորման ցանկերը, կրճատված կախվածությունները
և բնիկ երկուական ֆայլերը ձախողվում են միայն tarball-ը տեղադրելուց և գործարկելուց հետո։ `npm run dev:candidate`
-ը (`scripts/dev/candidate.mjs`) RFC #8084-ի մեկ անգամ կառուցել / վավերացնել / առաջ մղել հոսքի տեղային մասն է․
այն կառուցում է մեկ թեկնածու, վավերացնում հենց այդ արտեֆակտը, առաջ է մղում այն՝ վերանվանելով պանակները,
և հետ է շրջում այն, երբ առաջ մղված slot-ի առողջական ստուգումը ձախողվում է։

```bash
npm run dev:candidate -- run --dry-run --json  # ցուցադրել պլանը՝ ոչինչ չփոխելով
npm run dev:candidate -- run                   # կառուցել + վավերացնել + առաջ մղել, ավտոմատ հետշրջում
npm run dev:candidate -- build                 # npm pack + տեղադրում _artifacts/candidate/<id>/ պանակում
npm run dev:candidate -- validate --id <id>    # գործարկել ազատ port-ով, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # փոխանակել current-ը և previous-ը
npm run dev:candidate -- run --from-tarball <file.tgz>  # կրկին օգտագործել այլ տեղում կառուցված tarball-ը (CI)
```

- **Կառուցեք մեկ անգամ։** `build`-ը փաթեթավորում է ընթացիկ ծառը (դրա համար անհրաժեշտ է `dist/server.js`, ուստի նախ գործարկեք
  `npm run build:release`) կամ պատճենում է `--from-tarball`-ը, այնուհետև tarball-ը տեղադրում է
  մեկուսացված npm prefix-ում, քանի որ tarball-ը չի պարունակում `node_modules`։ id-ն `HEAD`-ի կարճ
  sha-ն է (`-dirty` վերջածանցով, երբ ծառում տեղային փոփոխություններ կան) կամ `tgz-<sha256>`՝ tarball-ի դեպքում։ Արդեն
  կառուցված մաքուր id-ն վերակառուցվելու փոխարեն կրկին օգտագործվում է․ այն վերակառուցելու համար փոխանցեք `--force`։
- **Վավերացրեք փաթեթը, ոչ թե ելակոդը։** `validate`-ը գործարկում է տեղադրված CLI-ն
  (`serve --port <free port>`)՝ թարմ `DATA_DIR=<candidate>/data`-ով և կեղծ գաղտնիքներով, իսկ օպերատորի
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` և `INITIAL_PASSWORD` արժեքները հեռացնում է
  միջավայրից, որպեսզի ստուգի թարմ տեղադրման՝ առանց բանալու loopback ռեժիմը։ Այն սպասում է, մինչև
  `GET /api/health`-ը վերադարձնի 200, պահանջում է, որ `GET /v1/models`-ը վերադարձնի 200, կանգնեցնում է պրոցեսների խումբը
  և արդյունքը tarball-ի hash-ի հետ միասին գրանցում է `validation.json`-ում։
- **Առաջ մղեք նույն արտեֆակտը։** `promote`-ը մերժում է թեկնածուին, եթե նրա ընթացիկ
  tarball hash-ի համար հաջող վավերացում չկա։ Լռելյայն ակտիվ slot-ը `_artifacts/candidate/current`-ն է․ `--target <dir>`-ը
  ընտրում է նույն ֆայլային համակարգում գտնվող այլ պանակ, իսկ դրա նախորդ slot-ը `<dir>.previous`-ն է։
  Յուրաքանչյուր վերանվանում ատոմար է, իսկ գործընթացի կեսին տեղի ունեցած ձախողումը հետ է շրջում արդեն կատարված վերանվանումները։
- **Հետ շրջեք։** `run`-ը կրկին վավերացնում է առաջ մղված slot-ը և փոխանակում է `current`-ն ու `previous`-ը, երբ
  այդ ստուգումը ձախողվում է։ Առաջին վավերացումը չանցած թեկնածուն երբեք առաջ չի մղվում։

Ամեն ինչ գրվում է git-ի կողմից անտեսվող `_artifacts/candidate/`-ի ներքո․ գոյություն ունեցող OmniRoute
տեղադրումը և դրա տվյալների պանակը երբեք չեն փոփոխվում։ Առաջ մղված CLI-ն
`_artifacts/candidate/current/prefix/bin/omniroute`-ն է․ այն օգտագործելիս գործարկեք ձեր սեփական `DATA_DIR`-ով։
Ելքի կոդեր՝ `0`՝ հաջողություն, `1`՝ ձախողված վավերացում կամ առաջ մղում, `2`՝ օգտագործման սխալ կամ բացակայող build։

## Տեղային ցիկլն ընդդեմ CI-ի

| Յուրաքանչյուր փոփոխության համար տեղային գործարկում                                              | CI-ն ապահովում է լայնածավալ ազդանշանը                                                               |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Վերևում նշված վարքագծի ուղիղ թեստերը և կատեգորիաների անցակետերը                                 | Բաժանված ամբողջական միավորային թեստերի հավաքածուն և հաջորդական թեստերը                              |
| `npm run lint`                                                                                  | Vitest թեստերի հավաքածուները և ծածկույթի/որակի աստիճանական շեմերը                                   |
| Տիպերի ստուգում կամ կառուցում՝ միայն երբ դա պահանջում է փոփոխված պայմանագիրը                    | Արտադրական կառուցման, անվտանգության, փաստաթղթերի, կախվածությունների և PR քաղաքականության անցակետերը |
| Ձեռքով փոխազդեցության/կենդանի ստուգումներ՝ միայն երբ ավտոմատացումը չի կարող ապացուցել վարքագիծը | Աշխատանքների միջև ինտեգրման և հարթակների ստուգումները՝ կազմաձևված աշխատանքային հոսքով               |

Կանաչ կարգավիճակով նպատակային ցիկլը փոփոխված պայմանագրի վերաբերյալ ապացույց է, այլ ոչ թե երաշխիք, որ կապ չունեցող CI ստուգումները
կանցնեն։ Եվ հակառակը՝ մի ստիպեք, որ յուրաքանչյուր տեղային խմբագրում սպասի պահոցի ամբողջական մատրիցի ավարտին։

## Համաձայնեցման ստուգացանկ

Նախքան վերանայում խնդրելը՝

- Հաստատեք, որ PR-ի բազային ճյուղը դեռևս ամենաբարձր ակտիվ `release/v*` ճյուղն է։
- Ներբեռնեք այդ բազային ճյուղի թարմացումները և վերանայեք ձեր ճյուղավորման պահից ի վեր ավելացված commit-ները։
- Ստուգեք `git diff <active-base>...HEAD`-ը՝ պատահական կամ գեներացված ավելորդ փոփոխությունների առկայության համար։
- Լուծեք կատալոգի և գեներացված փաստաթղթերի հակասությունները՝ թարմացնելով սկզբնաղբյուրը և վերագեներացնելով ելքը։
- Համաձայնեցումից հետո կրկին գործարկեք PR-ի նկարագրության մեջ նշված յուրաքանչյուր նպատակային թեստ/անցակետ։
- Երբեք մի թուլացրեք հաստատումները կամ մի հեռացրեք պարտադիր թեստերը՝ պարզապես փոփոխված բազային ճյուղին համապատասխանելու համար։

Թողարկման սառեցման և վերաթիրախավորման կանոնների համար օգտագործեք
[Ճյուղավորման և թողարկման մոդել](BRANCHING_MODEL.md)։ CI-ի ամբողջական ցանկի համար օգտագործեք
[Որակի անցակետերի տեղեկատու](../architecture/QUALITY_GATES.md)։
