> **Կարճ ասած**․ OmniRoute-ը որպես հիմնական պահոց օգտագործում է **SQLite՝ WAL մատենավորմամբ**, իսկ զգայուն դաշտերի հանգստի վիճակում կոդավորման համար՝ **AES-256-GCM**։ Այս ուղեցույցն ընդգրկում է սխեման, միգրացիաները, պահուստավորումն ու վերականգնումը և շահագործման ընթացակարգերը։

**Աղբյուրներ․**

- `src/lib/db/core.ts` — եզակի օրինակ + SCHEMA_SQL (17 հիմնական աղյուսակ)
- `src/lib/db/migrationRunner.ts` — տարբերակավորված միգրացիաներ
- `src/lib/db/migrations/` — 167 տարբերակավորված SQL ֆայլ
- `src/lib/db/encryption.ts` — կոդավորման օժանդակ գործառույթներ
- `src/lib/db/backup.ts` — պահուստային պատճենի արտահանում/ներմուծում
- `src/lib/db/healthCheck.ts` — վիճակի ախտորոշում

## Ինչո՞ւ SQLite։

OmniRoute-ը մի քանի պատճառով PostgreSQL/MySQL-ի փոխարեն ընտրել է SQLite-ը․

| Գործոն                  | SQLite                                                | PostgreSQL                                                      |
| ----------------------- | ----------------------------------------------------- | --------------------------------------------------------------- |
| **Տեղակայում**          | Ներկառուցված է՝ առանձին սերվեր չի պահանջվում          | Պահանջում է սերվերի կարգավորում                                 |
| **Կոդավորում**          | Հավելվածի մակարդակում (AES-256-GCM)                   | Ներկառուցված TDE                                                |
| **Արտադրողականություն** | Ավելի արագ է փոքր/միջին ծանրաբեռնվածությունների համար | Ավելի հարմար է հսկայական քանակի միաժամանակյա գրանցումների համար |
| **Զուգահեռություն**     | WAL ռեժիմը թույլ է տալիս միաժամանակյա ընթերցումներ    | Ամբողջական MVCC                                                 |
| **Պահուստավորում**      | Մեկ ֆայլի պատճենում                                   | `pg_dump` կամ ֆայլային համակարգի ակնթարթային պատճեն             |
| **Կիրառման դեպք**       | Յուրաքանչյուր օգտատիրոջ համար տեղադրում, ներկառուցված | Բազմավարձակալ SaaS                                              |

**Մեկ օգտատիրոջ, մեկ օրինակի** տեղակայումների դեպքում (OmniRoute-ի հիմնական կիրառման դեպքը) SQLite-ն ավելի պարզ և արագ է։

### WAL մատենավորում

`core.ts`-ը տվյալների բազան բացում է **WAL (նախնական գրանցմամբ մատենավորում) ռեժիմով**․

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL-ը գրանցման ընթացքում թույլ է տալիս **միաժամանակյա ընթերցումներ**, ինչը կարևոր է կառավարման վահանակի համար, որը հարցումներ է կատարում այն ժամանակ, երբ հարցումները գրանցվում են։

Քեշի լռելյայն չափը **65,536 KiB (64 MiB)** է։ SQLite-ը բացասական
`cache_size`-ը մեկնաբանում է որպես KiB-երով արտահայտված մոտավոր վերին սահման և էջերը հատկացնում է ըստ պահանջի։
**Կարգավորումներ > Համակարգ և պահոց > Քեշի չափ** բաժինն ընդունում է **1-ից
1,000,000 KiB** ամբողջ արժեքներ․ կարգավորումը պահպանելիս այն կիրառվում է տվյալների բազայի ակտիվ կապի նկատմամբ,
իսկ գործարկման ժամանակ OmniRoute-ը վերականգնում է պահպանված արժեքը։

## Տվյալների բազայի տեղադրությունը

SQLite ֆայլը պահվում է հետևյալ վայրում․

| ՕՀ      | Ուղի                                                             |
| ------- | ---------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                    |
| macOS   | `~/.omniroute/storage.sqlite`                                    |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                        |
| Docker  | `/app/data/storage.sqlite` (կարգավորվում է `DATA_DIR`-ի միջոցով) |

Ուղեկցող ֆայլեր․

- `storage.sqlite-wal` — նախնական գրանցման մատյան
- `storage.sqlite-shm` — համօգտագործվող հիշողության ֆայլ
- `call_logs/` — հարցման օգտակար տվյալների արտեֆակտներ (եթե միացված է)

**Տեղադրությունը վերասահմանելու համար․**

```bash
DATA_DIR=/custom/path omniroute
```

## Դոմենային մոդուլների ճարտարապետություն

OmniRoute-ի տվյալների բազան `src/lib/db/`-ում ունի **վերին մակարդակի 110 TypeScript մոդուլ**։ Յուրաքանչյուր դոմենային մոդուլ՝

- Տիրապետում է մեկ կամ մի քանի որոշակի աղյուսակների
- Արտահանում է տիպավորված CRUD ֆունկցիաներ
- Երբեք չի աշխատում այլ մոդուլի աղյուսակների հետ
- Տվյալների բազա մուտք գործելու համար օգտագործում է `core.ts`-ի `getDbInstance()` ֆունկցիան

Ճարտարապետական հիմնական կանոն՝ **մոդուլներն ուղղակիորեն հասանելիություն չեն ստանում միմյանց աղյուսակներին**։ Մեկ այլ մոդուլի տվյալների հետ աշխատելու համար ներմուծեք ֆունկցիան այդ մոդուլից։

```ts
// ❌ ՍԽԱԼ․ ուղղակի SQL հարցում մեկ այլ մոդուլից
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ՃԻՇՏ․ օգտագործեք providers մոդուլի ֆունկցիան
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

Այս կանոնը վերահսկվում է կոդի վերանայման ընթացքում․ ստատիկ ստուգում չկա, սակայն խախտումները նշվում են։

## Միգրացիաներ

OmniRoute օգտագործում** տարբերակված, անիմաստ միգրացիաներ** `src/lib/db/migrations/`. Յուրաքանչյուր միգրացիա մեկ SQL ֆայլ է: Անվանման երկու ձևաչափեր գոյակցում են. `_omniroute_migrations` ում գրանցված տարբերակը թվային նախածանցն է:

### Միգրացիայի անվանումը

| Ձևաչափ                                         | Օրինակ                               | Օգտագործված է                                                                                                                                                             |
| ---------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (ուղիղ 3 նիշ)            | `241_seen_models.sql`                | Հին սերիա `001`–`241`. Սառեցված է, երբ ժամադրոշմի ձևաչափը վայրէջք կատարեց (`240` և `241` միաձուլվեցին դրանից անմիջապես առաջ). ոչ մի նոր ֆայլ հաջորդական համար չի ստանում: |
| `YYYYMMDDHHMMSS_description.sql` (14 նիշ, UTC) | `20261113120000_add_usage_index.sql` | Յուրաքանչյուր միգրացիա ստեղծված 2026-11-13-ից սկսած:                                                                                                                      |

Ինչու է փոփոխությունը. հաջորդական թվերով զուգահեռ PRs ընտրեց նույն հաջորդ թիվը, և բոլորը, բացառությամբ մեկի, պետք է վերահամարակալեին մինչև միաձուլվելը: UTC ժամադրոշմը յուրաքանչյուր PR ին տալիս է իր սեփական տարբերակը:

Ժամանակի դրոշմանիշի ձևաչափի կանոններ (պարտադրվում է `npm run check:migration-numbering` կողմից, կիսվում է `scripts/check/lib/migrationNaming.mjs` ում գեներատորի հետ).

- Ժամացույցը իրական UTC ամսաթիվն ու ժամը է, ոչ շուտ, քան `20261113000000` և ոչ ավելի, քան 10 րոպե ապագայում:
- Նկարագրությունը փոքրատառ է `snake_case` որը սկսվում է տառով (`a-z`, `0-9`, մեկ `_` բառերի միջև), առավելագույնը 80 նիշ:
- Միևնույն ժամանակի կնիքով երկու ֆայլ կրկնօրինակ են:
- Ոչ բացերի կանոնը կիրառվում է միայն հին շարքի համար. `001` ից `241` յուրաքանչյուր թիվ պետք է գոյություն ունենա, բացառությամբ `026`, `055` և `121` հայտնի բացերի: `241` (կամ ցանկացած հին ֆայլ) ջնջելով դարպասը ձախողվում է: `001` և `241` երբեք չեն կարող ավելացվել `KNOWN_GAPS` թույլտվությունների ցանկում: Ժամանակի դրոշմված ֆայլերը երբեք բաց չեն ստեղծում:
- `src/lib/db/migrations/` ի յուրաքանչյուր մուտք պետք է լինի սովորական ֆայլ՝ վավեր փոքրատառ `.sql` անունով: Գրացուցակը, symlink, `.SQL` կամ `.sql.bak` ֆայլը, թաքնված ֆայլը կամ բացատ ունեցող անունը ձախողում է դարպասը, քանի որ վազորդը անաղմուկ բաց է թողնում այն կամ խափանում է բեռնման ժամանակ:

**Կիրառել պատվերը.** Runer-ը դասավորում է ըստ նախածանցի թվային արժեքի, այլ ոչ թե տեքստի. սկզբում հին `001`–`241` ֆայլերը, ապա ժամանակի դրոշմավորված ֆայլերը ըստ ժամանակի դրոշմանիշի, այնուհետև `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ով գրանցված ցանկացած անվանատարածքով գրացուցակ (տարբերակներ, ինչպիսիք են `ee-001`): Սպասող միգրացիան ցանկացած ֆայլ է, որի տարբերակը `_omniroute_migrations` ում չէ, ուստի ավելի հին մասնաճյուղից միգրացիան, որը միաձուլվում է ավելի նորից հետո, դեռևս կիրառվում է առկա տվյալների բազաների վրա:

**Ժամանակի դրոշմը ստեղծման կարգն է, ոչ թե միաձուլման կարգը:** Եթե ձեր միգրացիան կախված է աղյուսակից կամ սյունակից, որը ստեղծվել է a** ավելի նոր** ժամանակի դրոշմակնիք (օրինակ, մեկը մեկ այլ PR ից, որն առաջինը միաձուլվեց), թարմ տվյալների բազան առաջինը կաշխատի ձերը և ձախողվի: Քանի դեռ ձեր PR դեռ բաց է, ֆայլի անունը վերականգնեք `npm run db:new-migration` ով, որպեսզի այն ստանա ավելի նոր ժամանակացույց կամ դարձրեք այն անկախ: `npm run test:migrations:fresh` կիրառում է յուրաքանչյուր միգրացիա դատարկ տվյալների բազայի վրա և բռնում է դա:

### Միաձուլված միգրացիան երբեք չի ջնջվում կամ վերանվանվում

Երբ միգրացիոն ֆայլը գտնվում է թողարկման ճյուղում կամ `main` ում, այն արդեն գործարկվել է հոմոլոգ և մշակողների տվյալների բազաներում, VPS տեղադրումներում և Enterprise-ի համաժամացման մեջ: Այս պահից սկսած.

- **Երբեք մի ջնջեք այն:** Թարմ տեղադրումները կկորցնեն իրենց սխեման, մինչդեռ արդիականացված տվյալների բազաները պահպանում են այն:
- **Երբեք մի վերանվանեք այն:** `_omniroute_migrations` ի տարբերակն այլևս չի համընկնի ֆայլի հետ, ուստի յուրաքանչյուր տվյալների բազա, որն արդեն կիրառել է այն, այն նորից կաշխատի: Ոչ idempotent SQL այնուհետև կրկնօրինակում է տվյալները կամ դադարեցնում բեռնումը:
- **Պետք է այլ սխեմա:** Ստեղծեք նոր միգրացիա `npm run db:new-migration` ով:

Անվանափոխումն անվտանգ է միայն այն ֆայլի համար, որը դեռևս միաձուլված չէ, ինչին վերաբերում են դարպասի ակնարկները: Թողարկման պիտակը այստեղ ոչինչ չի փոխում. `release/v*` մասնաճյուղի յուրաքանչյուր հրում հրապարակում է Docker `:next` պատկերը և աշխատում է հոմոլոգի, VPS տեղադրումների և Enterprise-ի համաժամացման վրա, ուստի միաձուլված միգրացիան գործարկվել է իրական տվյալների բազաների վրա՝ նախքան որևէ `vX.Y.Z` պիտակի գոյությունը: Դարպասը ձախողվում է բազային ֆայլի յուրաքանչյուր հեռացում՝ հատկորոշված թե ոչ:

- **Միավորված միգրացիայի վերադարձ:** `git revert`, որը ջնջում է ֆայլը, ձախողում է դարպասը: Պահեք ֆայլը և չեղարկեք դրա սխեման նոր միգրացիայի մեջ՝ `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` և այլն։ Թարմացված և թարմ տվյալների բազաները այնուհետև ավարտվում են նույն սխեմայով:
- **Ընդունվածը վերանվանվել է՝ համատեղելիության մուտք և նույնական բովանդակություն:** Եթե միաձուլված ֆայլը պետք է տեղափոխվի (օրինակ, երկու միաձուլված ֆայլ կիսում են ժամանակի դրոշմը, և վազողը դադարում է տարբերակի բախման դեպքում), վերանվանեք վերջինը՝ առանց դրա SQL դիպչելու և `{ fromVersion, fromName, toVersion, toName }` ին ավելացրեք `RENAMED_MIGRATION_COMPATIBILITY` ին `src/lib/db/migrationRunner/constants.ts` ում: Տվյալների շտեմարանները, որոնք կիրառում էին հին տարբերակը, իրենց `_omniroute_migrations` տողը տեղափոխվում է ֆայլը նորից գործարկելու փոխարեն: Դարպասը նախազգուշացնում է նման անվանափոխության մասին և միշտ գործարկում է փոխարկման ստուգումը դրա վրա՝ անկախ նոր ժամանակի դրոշմից. թարմ տեղադրումները ֆայլը կիրառում են նոր դիրքում, արդիականացված տվյալների բազաները՝ ոչ, ուստի ընտրեք նոր ժամանակի դրոշմակնիք՝ հնի մոտ: Դարպասը չի վերանվանվի, եթե բովանդակությունը փոխվի (սխեմայի փոփոխությունը դեռ շարունակվում է նոր միգրացիայի ժամանակ), կամ եթե մուտքի թիրախային ֆայլը սկավառակի վրա չէ:
- **Երբեք մի վերանվանեք նույն ժամանակի դրոշմանիշի մեջ:** Վերանվանումը, որը պահպանում է ժամանակի կնիքը և փոխում է միայն նկարագրությունը, ձախողում է դարպասը՝ մուտքով կամ առանց մուտքի: Գրառման դեպքում, որի `toVersion` հավասար է իր `fromVersion`, վազորդը ջնջում է հին `_omniroute_migrations` տողը և նորից կիրառում ֆայլը յուրաքանչյուր տվյալների բազայում, որն արդեն գործարկել է այն: Առանց մուտքագրման, վազորդը հետևում է միայն տարբերակին. այն բաց է թողնում այդ տվյալների բազայի ֆայլը (նոր բովանդակությունը երբեք այնտեղ չի աշխատում) և գրանցում է վերահամարակալման սխալ յուրաքանչյուր բեռնման ժամանակ: Օգտագործեք մեկ այլ ժամադրոշմ՝ գումարած համատեղելիության գրառում կամ պահպանեք անունը:
- **Դարպասը ստուգում է, որ վերանվանված ֆայլը նորից չաշխատի:** Յուրաքանչյուր ծածկված վերանվանման համար դարպասը փոխանցում է նոր ֆայլի անունը `--must-not-apply` ով փոխարկման ստուգմանը: Չեկը բեռնում է արդիականացված տվյալների բազան իրական runner-ով, և եթե runner-ը նորից կիրառում է այդ ֆայլը (օրինակ, քանի որ մուտքն ունի սխալ տարբերակ կամ անուն, կամ քանի որ դարպասի տեքստային վերլուծիչը `constants.ts` է կարդացել TypeScript ից), դարպասը ձախողվում է `migration renomeada rodaria de novo` ով և խնդրում է ստուգել մուտքի հին և նոր տարբերակներն ու անունները:

### Ինչ է ստուգում դարպասը բազայի դեմ

Ձգման հարցում և միաձուլման հերթ գործարկվելիս `npm run check:migration-numbering` համեմատում է `src/lib/db/migrations/` սկավառակի վրա նույն գրացուցակով բազային ճյուղում: Հիմքը հետևյալ հաջորդականությամբ է՝ `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` փոփոխական կամ, երբ `GITHUB_EVENT_NAME` `pull_request` է, `pull_request_target` կամ `merge_group`, միաձուլման կատարման առաջին ծնողը, իրադարձության օգտակար բեռի `merge_group.base_sha` կամ `git merge-base HEAD origin/$GITHUB_BASE_REF`: Ձգման հարցում կամ միաձուլման հերթում առանց լուծելի հիմքի դարպասը ձախողվում է: CI ից դուրս՝ առանց `--base` այն տպում է `comparação com a base: pulada (sem --base)` և բաց է թողնում այս կանոնները:

`--base-latest-tag` համեմատում է թողարկման նորագույն պիտակի հետ (`vX.Y.Z` ըստ semver հերթականության; վերջածանցով պիտակները, ինչպիսիք են գիշերային երեկոները, չեն հաշվվում), որը `HEAD` ի պատմության մեջ է, նույն կանոններով, ինչ `--base`: Release-Green-ը (`scripts/quality/validate-release-green.mjs`) վազում է դարպասն այս կերպ, քանի որ հրում և պլանավորված վազքները չունեն ձգման պահանջի հիմք, և միաձուլումը կարող է վայրէջք կատարել առանց CI թարմ գործարկման: Պատմության մեջ առանց թողարկման պիտակի դարպասը ձախողվում է. վազել `git fetch --tags` ( CI ում, `actions/checkout` `fetch-depth: 0` ով բերում է պիտակները):

| Ժամանակի դրոշմավորված ֆայլը ավելացվում է բազայի ամենանորից ոչ ավելի նոր ժամանակի դրոշմով                             | Գործարկում է ստորև նկարագրված փոխարկման ստուգումը:                                                                                                                                                                                                                                                                                                                                        |
| Հին ձևաչափով `NNN_` ֆայլ ավելացվում է բազայի նորագույն հին ձևաչափի ֆայլի տակ գտնվող թվով                             | **Ձախողվում է** , նույնիսկ եթե `KNOWN_GAPS` խմբագրված է նույն ձգման հարցումով. հին շարքը սառեցված է, ստեղծեք միգրացիան `npm run db:new-migration` ով: Ընդունվում են հին ձևաչափի ֆայլեր, որոնք գտնվում են բազայի ամենանորից վերևում ( `release/v*` ից `main` ձգման հարցում):                                                                                                               |
| Անկանոն, խմբագրված կամ վերանվանված ֆայլը պարունակում է `INSERT`, `UPDATE`, `DELETE` կամ `REPLACE` հայտարարություններ | **Զգուշացում** Փոխանցման ստուգումը չի համեմատում տվյալները, այնպես որ ստուգեք, թե արդյոք արդիականացված և թարմ տվյալների բազաների կիրառման հերթականությունը փոխում է արդյունքը:                                                                                                                                                                                                            |

Փոխանցման ստուգման մեկ գործարկումը ներառում է շարքից դուրս եկած, խմբագրված և վերանվանված ֆայլերը միասին:

Փոխադրման ստուգումը (`scripts/check/migration-commutation.ts`) կառուցում է երկու ժամանակավոր տվյալների բազա իրական տեղադրման ուղով. an** արդիականացված** մեկը (գործարկեք բազային միգրացիաներով, այնուհետև նորից բեռնեք նույն ֆայլի վրա՝ pull request-ի միգրացիաներով) և a** թարմ** մեկը (մեկ բեռնախցիկ՝ ձգման խնդրանքի միգրացիաներով): Այն համեմատում է ստացված սխեմաները՝ աղյուսակներ և սյունակներ (անտեսելով սյունակների հերթականությունը), UNIQUE / PRIMARY KEY և FOREIGN KEY սահմանափակումները, յուրաքանչյուր աղյուսակի նորմալացված `CREATE TABLE` տեքստը (որն ընդգրկում է CHECK սահմանափակումները, համադրումները, գեներացված սյունակները և աղյուսակի տարբերակները), ինդեքսները, գործարկիչները և դիտումները: Տողերի տվյալները չեն համեմատվում: Եթե դրանք համընկնում են, դարպասը տպում է, որ ֆայլը շարքից դուրս է եկել, բայց շարժվում է, և անցնում է: Եթե դրանք տարբերվում են, դարպասը ձախողվում է տարբերությամբ և ակնարկով դեպքի համար. շարքից դուրս եկած ֆայլի համար վերարտադրեք դրա անունը `npm run db:new-migration` ով, որն անվտանգ է, քանի որ ֆայլը դեռ միաձուլված չէ; խմբագրված բազային ֆայլի համար վերականգնել բազային բովանդակությունը և փոփոխությունը դնել նոր միգրացիայի մեջ. Վերանվանված ֆայլի համար հետարկեք վերանվանումը կամ ընտրեք մեկ այլ նոր ժամանակի դրոշմակնիք, որտեղ այն շարժվում է, երբեք միևնույն ժամանակի դրոշմը այլ անունով: Եթե ստուգումն ինքնին չի կարող գործարկվել, դարպասը ձախողվում է CI ում և նախազգուշացնում է միայն տեղում: Խմբագրված բազային ֆայլի համար արդիականացված տվյալների բազան կառուցվում է այդ ֆայլի բազայի բովանդակությամբ, և երկրորդ բեռնումը բաց է թողնում այն, քանի որ դրա տարբերակն արդեն գրանցված է: Վերանվանված ֆայլի համար արդիականացված տվյալների բազան կառուցվում է հին անունով ֆայլով, իսկ երկրորդ բեռնախցիկը տեղափոխում է իր `_omniroute_migrations` տողը համատեղելիության մուտքի միջով՝ այն նորից գործարկելու փոխարեն. դարպասը փոխանցում է նոր անունը `--must-not-apply` ով, ուստի ստուգումը ձախողվում է, եթե երկրորդ բեռնախցիկը կիրառի այն: Եթե pull-ի հարցումների միգրացիան չկիրառվի արդիականացված ուղու վրա, այսինքն՝ յուրաքանչյուր բազային միգրացիայից հետո (անկախ նրանից, թե այն նաև ձախողվում է նոր տեղադրման ժամանակ), դարպասը հայտնում է `migration do PR não aplica` և խնդրում է ձեզ ուղղել SQL բազայի ընթացիկ սխեմայի հետ։ եթե ֆայլը կախված է ավելի ուշ ժամանակի դրոշմակնիքով մեկ այլ pull հայտի միգրացիայից, վերարտադրեք նրա անունը `npm run db:new-migration` ով:

Նույն համեմատությունը լոկալ կերպով իրականացնելու համար բացահայտորեն փոխանցեք բազան, օրինակ՝ `npm run check:migration-numbering -- --base origin/<base-branch>`, կամ `npm run check:migration-numbering -- --base-latest-tag` վերջին թողարկման հետ համեմատելու համար:

### Բաց PR ի `NNN` միգրացիայի վերածում

Անջատիչից առաջ բացված ձգման հարցումը դեռ կարող է ունենալ հաջորդական ֆայլ, ինչպիսին `242_add_widgets.sql` է: `241` վերևում գտնվող հին թվերը մերժվում են, այնպես որ միաձուլվելուց առաջ փոխարկեք այն.

1. **Վերանվանել ֆայլը գեներատորի հետ՝ պահպանելով նկարագրությունը։** Գործարկեք `npm run db:new-migration -- <same description>` նոր անունը ստանալու համար, տեղափոխեք SQL դրա մեջ և ջնջեք հին `NNN_` ֆայլը: Նկարագրությունը պետք է մնա նույնական. ստորև նշված համատեղելիության գրառումը համընկնում է դրա վրա:
2. **Ավելացրեք համատեղելիության գրառում, եթե մշտական տվյալների բազան գործարկեց հին համարը:** Եթե որևէ տվյալների բազա, որը պահվում է (հոմոլոգ, VPS, ներդրողի սեփական տեղադրում) `NNN_` ֆայլով գործարկվել է PR, ավելացրեք `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` `RENAMED_MIGRATION_COMPATIBILITY` ին `src/lib/db/migrationRunner/constants.ts` ում: Սա է** պահանջվում է `237` ից `241`** Այդ սլոտներն այժմ պահում են կանոնական `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` և `241_seen_models.sql`, և առանց մուտքի նման տվյալների բազան ընդմիշտ բաց է թողնում կանոնական միգրացիան և նորից գործարկում փոխարկվածը: Այն նաև աշխատում է այն հատվածի համար, որը դատարկ է մնում, օրինակ՝ `242`, երբ նպատակակետը ժամանակի դրոշմ է: Եթե կասկածում եք, ավելացրեք մուտքը: Այն, թե որտեղ եք այն ավելացնում զանգվածում, նշանակություն չունի. երբ մուտքի թիրախային բնիկը դեռևս պահում է մի տող, որը հեռանում է մեկ այլ մուտքից (օրինակ, `237` պահում է PR տողը, մինչդեռ ավելի հին `usage_history_calculated_cost` տողը սպասում է տեղափոխվելու `237`), վազողը թույլ է տալիս, որ մուտքը սպասի մինչև բնիկը ազատվի: Միայն իրական կոնֆլիկտը, օրինակ՝ մի շարքով պահվող բնիկը, առանց մուտքի շարժվում է, կամ երկու մուտք, որոնք փոխանակում են սլոտները, դադարեցնում է բեռնախցիկը `Cannot reconcile ...` ով:
3. **SQL իդեմպոտենտ պահեք** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), քանի որ փոխարկված միգրացիան կարող է հանդիպել տվյալների բազայի, որտեղ դրա սխեման արդեն գոյություն ունի:
4. **Տեղափոխեք տարբերակով հատուկ պատյաններ:** Եթե PR ավելացրել է իր հին թվի գործը `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) կամ `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`), բանալին փոխեք նոր ժամանակի դրոշմակնիքով:

`tests/unit/db/codex-fence-migration-rename.test.ts` վերանվանված միգրացիայի փորձարկման աշխատանքային օրինակ է:

### Փոխարկիչները դեպի մասնաճյուղեր նախքան անջատիչը

Երբեք մի ընտրեք կամ մի՛ ուղարկեք `YYYYMMDDHHMMSS_` ֆայլը մի ճյուղին, որը նախորդում է անջատիչին (օրինակ՝ ավելի հին `release/v*` ճյուղ): Այնտեղ վազողը ֆայլերի անունները դասավորում է որպես տեքստ, այնպես որ ժամանակի դրոշմավորված ֆայլը կաշխատի `201_` և `202_` միջև թարմ տվյալների բազայում, և այնտեղի հին դարպասը չի հասկանում 14 նիշանոց նախածանցները: Նման ճյուղի վրա փոփոխությունը գրեք որպես այդ ճյուղի սեփական հաջորդ `NNN_` ֆայլ՝ idempotent, այնպես որ այն ոչ-օպ է, երբ ժամադրոշմված տարբերակը ժամանում է ավելի ուշ:

### Ինչպես են վազում միգրացիաները

Գործարկման ժամանակ `migrationRunner.ts`:

1. Ստեղծում է `_omniroute_migrations` աղյուսակը, եթե գոյություն չունի
2. Հարցումներ արդեն իսկ կիրառված միգրացիաների համար
3. Կիրառում է ցանկացած նոր միգրացիա ըստ հերթականության՝ յուրաքանչյուրը գործարքի մեջ
4. Գրանցում է յուրաքանչյուր կիրառված միգրացիա ժամանակի դրոշմով

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

Օգտագործեք `IF NOT EXISTS`, `IF EXISTS` և `OR IGNORE` / `OR REPLACE` կետերը առատորեն:

### Նոր միգրացիայի ավելացում

1. **Ստեղծեք ֆայլը գեներատորի միջոցով** : `npm run db:new-migration -- <description>` (օրինակ `npm run db:new-migration -- add combo priority`). Այն գրում է `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` ընթացիկ UTC ժամանակով և մեկնաբանության վերնագրով, մեկ վայրկյան առաջ է շարժվում, եթե այդ ժամանակի դրոշմը վերցված է, և երբեք չի վերագրում ֆայլը: Ձեռքով թիվ մի ընտրեք։
2. **Օգտագործեք անվտանգ DDL** ՝ `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **Զգուշորեն լրացրեք տվյալները** Օգտագործեք `UPDATE ... WHERE ...` գոյություն ունեցող տողերը կարգավորելու համար
4. **Ստուգեք կարգը և անվանումը** `npm run test:migrations:fresh` (բոլոր միգրացիաները դատարկ տվյալների բազայում) և `npm run check:migration-numbering`
5. **Փորձարկում պատճենի վրա** երբեք մի գործարկեք չստուգված միգրացիաներ արտադրության վրա
6. **Կոդից ստեղծված աղյուսակը նույնպես միգրացիայի կարիք ունի** Եթե մոդուլը նույնպես ծույլ է ստեղծում աղյուսակը (`CREATE TABLE IF NOT EXISTS`, պահվում է որպես ինքնաբուժման ուղի), միգրացիան պետք է ստեղծի այն նույն DDL ով: Հակառակ դեպքում, մաքուր տեղադրումը և արդիականացված տեղադրումը ավարտվում են տարբեր սխեմաներով՝ կախված նրանից, թե արդյոք այդ կոդային ուղին գործարկվել է: `tests/unit/db/lazy-table-migration-guard.test.ts` սկանավորում է `src/` և `open-sse/` և ձախողվում է ծույլ `CREATE` վրա՝ առանց միգրացիայի (#20557): Օրինակ՝ `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

Օրինակ՝

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **Հետադարձ-անհամատեղելի փոփոխություններ** (օրինակ՝ սյունակներ թողնելը) բարդ է: OmniRoute NOT աջակցում է — իջեցմանը, երբ միգրացիան կիրառվի, սխեմայի փոփոխությունը մշտական է: Պլանավորեք համապատասխանաբար:

## Պահպանված տվյալների կոդավորում

Զգայուն դաշտերը (API բանալիներ, OAuth տոկեններ, կապի տողեր) պահպանման ժամանակ կոդավորվում են **AES-256-GCM**-ի միջոցով։

### Ինչպես է այն աշխատում

```ts
// src/lib/db/encryption.ts (պարզեցված)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### Որտեղ է այն օգտագործվում

- `provider_connections.api_key` — կոդավորվում է հավելվածի մակարդակում
- `provider_connections.access_token`, `refresh_token`, `id_token` — կոդավորվում են հավելվածի մակարդակում
- `key_value` գրառումները, որոնցում `namespace = "secrets"` — կոդավորվում են հավելվածի մակարդակում
- `proxy_registry.auth` — կոդավորվում է հավելվածի մակարդակում (եթե առկա է)

### Կոդավորման բանալի

Կոդավորման բանալին ստացվում է **գաղտնաբառային արտահայտությունից** (սահմանվում է `STORAGE_ENCRYPTION_KEY` միջավայրի փոփոխականի միջոցով) և **աղից** (պահվում է ՏԲ-ում)։ Տվյալների վերծանման համար երկուսն էլ անհրաժեշտ են։

```bash
# Ստեղծել անվտանգ գաղտնաբառային արտահայտություն
openssl rand -hex 32

# Սահմանել .env-ում
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **Խիստ կարևոր է**․ կոդավորման բանալին կորցնելը նշանակում է կորցնել բոլոր կոդավորված տվյալների հասանելիությունը։ **Բանալու պահուստային պատճենը պահեք տվյալների բազայից առանձին**։

### Ինչը ՉԻ կոդավորվում

Արդյունավետության նկատառումներով հետևյալ տվյալները պահվում են բաց տեքստով․

- Մատակարարների ցուցադրվող անունները
- Մոդելների սահմանումները (արդեն հանրային են)
- Երթուղավորման կանոնները
- Օգտագործման գրառումները (PII չեն պարունակում)

## Գաղտնագրման կարևոր նկատառումներ (v3.8.16+)

OmniRoute-ը կիրառում է **`migrateLegacyEncryptedString()`**՝ գաղտնագրման երկու սխեմաներն աննկատ կերպով մշակելու համար․

- **Հին** (մինչև v3.5.0)․ XOR-ի վրա հիմնված «գաղտնագրում» (իրական գաղտնագրում չէ)
- **Ընթացիկ**․ AES-256-GCM՝ պատշաճ IV-ով և իսկորոշման պիտակով

Միգրացիայի օժանդակ գործառույթը հայտնաբերում է հին ձևաչափը և առաջին ընթերցման ժամանակ վերագաղտնագրում է այն նոր սխեմայով։ Սա նշանակում է, որ կարող եք թարմացնել հին տվյալների բազան՝ առանց մուտքային տվյալները կորցնելու։

## Ընթերցման քեշ

Հաճախ ընթերցվող տվյալների համար (մոդելներ, մատակարարներ, կարգավորումներ) `readCache.ts`-ը տրամադրում է **հիշողության մեջ պահվող քեշ**․

```ts
// Քեշավորվում է մեկնարկի ժամանակ, անվավեր է դառնում գրանցման ժամանակ
const providers = await getCachedProviders(); // Արագ է, հիշողության մեջ
const fresh = await listProviders(); // Դանդաղ է, հարցում է կատարում DB-ին
```

| Քեշավորված էություն    | Քեշի բանալի    | TTL             |
| ---------------------- | -------------- | --------------- |
| `models`               | `models:v1`    | Մինչև գրանցումը |
| `provider_connections` | `providers:v1` | Մինչև գրանցումը |
| `settings`             | `settings:v1`  | Մինչև գրանցումը |
| `combos`               | `combos:v1`    | Մինչև գրանցումը |

Քեշն անվավեր է դառնում համապատասխան աղյուսակում յուրաքանչյուր գրանցումից հետո։

## Պահուստավորում և վերականգնում

### Ձեռքով պահուստավորում

```bash
# Տեղային պահուստային պատճեն ստեղծելու համար օգտագործեք CLI-ն
omniroute backup create --name pre-migration

# Կամ API-ի միջոցով
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

Պահուստային ֆայլը ներառում է․

- DB-ի բոլոր աղյուսակները (սերիականացված JSON-ի)
- Կանչերի մատյանի արտեֆակտները (base64-ով կոդավորված, ընտրովի)
- Կարգավորումներ + գաղտնի տվյալներ (գաղտնագրված)
- Փլագինների կազմաձևում

### Վերականգնում

```bash
# CLI-ի միջոցով
omniroute restore pre-migration

# API-ի միջոցով
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **Զգուշացում**․ Վերականգնումը վերագրում է ամբողջ DB-ն։ Նախ դադարեցրեք բոլոր սպասառուները։

### Ավտոմատացված պահուստավորումներ

```bash
# CLI-ի միջոցով միացրեք ամենօրյա ավտոմատացված պահուստավորումները
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

Ժամանակացույցը սերվերի կողմում կատարվում է ֆոնային առաջադրանքով, որն աշխատում է յուրաքանչյուր 30 վայրկյանը մեկ
(լռելյայն) և cron արտահայտությունը գնահատում է սերվերի տեղական ժամանակի նկատմամբ։

| Փոփոխական                                   | Լռելյայն | Նկարագրություն                                                                                                                  |
| ------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`  | Քայլի միջակայքը՝ մվ-ով (նվազագույնը՝ `5000`)։ Պետք է 60 վ-ից կարճ լինի՝ համապատասխան cron րոպեի մեջ հուսալիորեն ընկնելու համար։ |

### SQLite-ի թեժ պահուստավորում

Գործող DB-ն առանց աշխատանքի ընդհատման պահուստավորելու համար․

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

Սա օգտագործում է SQLite-ի առցանց պահուստավորման API-ն. անվտանգ է գործարկել OmniRoute-ի աշխատանքի ընթացքում։

## Performance Tuning

### WAL ռեժիմ

WAL լռելյայն միացված է: Բարձր գրելու ծանրաբեռնվածության դեպքում հաշվի առեք.

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute չի դնում `journal_size_limit`. Անցակետը WAL շրջանակները տեղափոխում է հիմնական ֆայլ, բայց WAL ֆայլը պահպանում է իր ամենամեծ հատկացված չափը: `OMNIROUTE_WAL_GUARD_MAX_MB` պահակը միայն զգուշացնում է և վազում `wal_checkpoint(RESTART)`; դա սկավառակի չափի գլխարկ չէ:

### Ցուցանիշներ

Արդյունավետության հիմնական ցուցանիշները (ավտոմատ ստեղծվել են միգրացիաների միջոցով).

- `idx_models_provider` — մոդելի որոնումներ մատակարարի կողմից
- `idx_combo_targets_combo_id` — համակցված թիրախի ընդլայնում
- `idx_usage_history_api_key_timestamp` — օգտագործման վերլուծություն
- `idx_quota_snapshots_api_key_window` — քվոտայի հետևում
- `idx_call_logs_timestamp` — զանգերի մատյան հարցումներ

Նոր ինդեքս ավելացնելու համար ստեղծեք միգրացիա.

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### Հիշողության քարտեզագրված I/O

Շատ մեծ տվյալների բազաների համար (> 10GB), հիշողության քարտեզագրումը կարող է ճշգրտվել SQLite pragma-ի միջոցով.

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### Կծկում

OmniRoute երկարատև դեպքերը օգուտ են քաղում երբեմն-երբեմն `VACUUM` ից.

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

Աշխատեք ամեն ամիս ցածր երթևեկության պատուհանների ժամանակ: (WAL ռեժիմը նվազեցնում է անհրաժեշտությունը, բայց չի վերացնում այն:)

## Աշխատունակության ստուգում

`src/lib/db/healthCheck.ts`-ը տրամադրում է **ՏԲ մակարդակի աշխատունակության ախտորոշում**՝

Երկու HTTP բայերն էլ պահանջում են նույնականացում (հակառակ դեպքում՝ `401`)։ `GET`-ը միայն ախտորոշում է, իսկ `POST`-ը կատարում է նույն ստուգումը՝ միացված `autoRepair`-ով։

```bash
GET  /api/db/health   # ախտորոշել
POST /api/db/health   # ախտորոշել + վերականգնել
```

Պատասխանը `runDbHealthCheck()`-ի ստեղծած `DbHealthCheckResult`-ն է
(`src/lib/db/healthCheck.ts`)՝

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Domain budgets referenced API keys that no longer exist.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| Դաշտ              | Նշանակություն                                                                                                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `true`, երբ `issues`-ը դատարկ է։ `driver`-ը երբեք չի ազդում դրա վրա։                                                                                                                               |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` արժեքներից մեկը։                                                                                                   |
| `repairedCount`   | Այս գործարկման ընթացքում վերականգնված տողերի քանակը․ միշտ `0` է, երբ `autoRepair`-ը false է։                                                                                                       |
| `backupCreated`   | Արդյոք վերականգնումից առաջ պահուստային պատճեն է ստեղծվել։                                                                                                                                          |
| `checkedAt`       | ISO ժամանակային դրոշմ, որը ընդհանուր է գործարկման և դրա գրանցած ցանկացած վերականգնման նշման համար։                                                                                                 |
| `driver.name`     | Ստուգվող տվյալների բազան սպասարկող SQLite դրայվերը։                                                                                                                                                |
| `driver.degraded` | `true`, երբ գրանցումները տվյալների բազայի ֆայլով հուսալիորեն չեն պահպանվում՝ `sql.js` WASM պահուստային տարբերակի (ամբողջական ֆայլի պահպանում) կամ հիշողության մեջ գտնվող տվյալների բազայի դեպքում։ |

Նույն օգտակար բեռը վերադարձվում է `omniroute_db_health_check` MCP գործիքի կողմից։

Վնասվածությունը հայտնաբերելու համար գործարկեք `PRAGMA integrity_check`՝

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# Պետք է արտածի՝ ok
```

Եթե այն վերադարձնում է `ok`-ից տարբերվող որևէ արդյունք, **անմիջապես դադարեցրեք տվյալների բազայի օգտագործումը** և վերականգնեք այն պահուստային պատճենից։

## Աղետից հետո վերականգնում

### Սցենար 1․ WAL ֆայլը կորել է

`-wal` ֆայլը բացակայում է, սակայն `-shm`-ը և հիմնական տվյալների բազան անվնաս են․

```bash
# Հաջորդ բացման ժամանակ ինքնաբերաբար վերականգնվում է
omniroute
```

Եթե SQLite-ը չի կարող ինքնաբերաբար վերականգնել․

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### Սցենար 2․ Տվյալների բազայի հիմնական ֆայլը վնասված է

Վերականգնեք պահուստային պատճենից․

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]`-ը միայն ներբեռնում է ամբողջական `.tar.gz` արխիվը գործարկվող սերվերից
(`GET /api/db-backups/exportAll`, պահանջվում են օպերատորի հավատարմագրեր)․ այն ոչինչ չի վերականգնում։

### Սցենար 3․ Գաղտնագրման բանալին կորել է

Առանց բանալու **վերականգնումն անհնար է**։ Գաղտնագրված դաշտերն անընթեռնելի են։ Ձեռքով կրկին ավելացրեք բոլոր մատակարարներին՝ նոր հավատարմագրերով։

> **Կանխարգելում**․ Միշտ առանձին պահուստավորեք գաղտնագրման բանալին՝ ցանկալի է գաղտնաբառերի կառավարչում կամ KMS-ում։

### Սցենար 4․ Սկավառակը լցված է

SQLite-ը կվերադարձնի `SQLITE_FULL` սխալներ։ Ազատեք սկավառակային տարածք, ապա կատարեք․

```bash
# Կատարել WAL-ի checkpoint՝ տարածք ազատելու համար
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## Տարածված գործողություններ

### Աղյուսակի դիտարկում

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### Բոլոր աղյուսակների տողերի քանակի հաշվարկ

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### Բոլոր տվյալների զրոյացում (ջնջում)

```bash
# Նախ կանգնեցնել OmniRoute-ը
omniroute stop

# Ջնջել տվյալների բազայի ֆայլը
rm ~/.omniroute/storage.sqlite*

# Վերագործարկել (կստեղծվի նոր դատարկ տվյալների բազա)
omniroute
```

**Ընտրովի** զրոյացման համար (պահպանել մատակարարներին, ջնջել օգտագործման տվյալները).

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### Մեկ աղյուսակի արտահանում

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## Խնդիրների լուծում

### «Տվյալների բազան կողպված է»

Մեկ այլ գործընթաց պահում է գրառման կողպումը։ Կարող եք.

- Սպասել, մինչև մյուս գործընթացն ավարտվի (ստուգեք `lsof | grep storage.sqlite`)
- Դադարեցնել մյուս գործընթացը
- Եթե խնդիրը պահպանվում է, վերագործարկել OmniRoute-ը

### «Արտաքին բանալու սահմանափակումը խախտվել է»

Դոմենի մոդուլը խախտում է հղումային ամբողջականությունը։ Ստուգեք.

- Կախյալ աղյուսակներում առկա որբացած տողերը
- Շղթայական ջնջումները, որոնք չեն տարածվել
- Վերջին միգրացիան, որը փոխել է արտաքին բանալին

Խախտումները գտնելու համար գործարկեք `PRAGMA foreign_key_check;`։

### «Հիշողությունը սպառվել է»

SQLite-ի՝ հիշողության մեջ արտապատկերված մուտք/ելքը գերազանցում է օպերացիոն համակարգի սահմանաչափը։ Նվազեցրեք այն SQLite-ի pragma-ի միջոցով.

```sql
PRAGMA mmap_size = 134217728;  -- 256MB-ի փոխարեն՝ 128MB
```

Կամ անջատեք.

```sql
PRAGMA mmap_size = 0;
```

### «Միգրացիան ընդհատվել է ընթացքի կեսին»

Միգրացիան կատարվել է տրանզակցիայի ներսում, ուստի այն պետք է հետ շրջված լիներ։ Եթե դա տեղի չի ունեցել.

1. **Կանգնեցրեք OmniRoute-ը** (կանխեք հետագա փորձերը)
2. **Ստուգեք տվյալների բազայի վիճակը** `sqlite3`-ի միջոցով
3. **Ձեռքով շտկեք** մասնակի միգրացիան
4. **Կրկին գործարկեք** OmniRoute-ը (միգրացիան նորից կփորձարկվի)

Սա կանխելու համար միշտ նախ փորձարկեք միգրացիաները պատճենի վրա։
