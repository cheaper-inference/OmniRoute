Ինքնուրույն հոսթավորվող pool-ն աշխատում է **.113** մեքենայի վրա (`tomni-proxmox-113`)։ 2026-10-18-ից սկսած՝
OmniRoute-ի յուրաքանչյուր runner ունի **մեկ դեր**, մեկ պիտակ և հիշողության/CPU-ի բյուջե՝ իր workload-ի
չափված պահանջներին համապատասխան։ Turbopack-ի slot-ը ստանում է build-ի համար անհրաժեշտ ռեսուրսները, իսկ մյուս slot-երը չափաբաժնված են ըստ իրենց
չափված առավելագույն արժեքների։ Մեքենան գերբաշխում է ռեսուրսները միայն այն դեպքում, երբ Turbopack build-ը համընկնում է Release-Green-ի
webpack build-ի և lint job-ի հետ․ host-ի swap-ը (16 GB) կլանում է այդ ծանրաբեռնվածությունը, իսկ քանի որ pull request-ների Build-երն աշխատում են
հոսթավորված միջավայրում, Turbopack-ի slot-ը ժամանակի մեծ մասում անգործուն է․

## Տեղադրեք janitor-ը (մեկ անգամ՝ սերվերի վրա)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root)՝ յուրաքանչյուր 30 րոպեն մեկ, գրանցել /var/log/runner-janitor.log-ում
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof`-ը պարտադիր է. նախքան որևէ ուղի հեռացնելը janitor-ը բաց ֆայլերի մեկ ակնթարթային պատկերով հաստատում է, որ այն պարապ է, իսկ առանց այդ գործիքի ոչինչ չի հեռացնում և այդ մասին հաղորդում է (ելքի կոդ՝ 1)։ Ցանկացած փոփոխություն նախ փորձեք `--dry-run`-ով. այն ճշգրիտ ցույց է տալիս, թե ինչ կաներ, և ոչինչ չի փոփոխում։

Յուրաքանչյուր գործարկման ժամանակ այն կատարում է հետևյալը. մաքրում է մեր սեփական մնացորդները (`runner-*`, `omniroute-*`, `next-build*`, `e2e-build.tar.gz`)՝ **tmpfs-ում 3 ժ անց**, իսկ սկավառակի `_work/_temp`-ում՝ 24 ժ անց, դադարեցնում է 75 րոպեից ավելի հին `next-build`-ը (ոչ մի առաջադրանք այդքան երկար չի աշխատում. 2026-08-27-ին մեկն աշխատել է 70 րոպե այն բանից հետո, երբ GitHub-ն արդեն հայտարարել էր, որ առաջադրանքը կորել է), հեռացնում է այն runner-ների 48 ժամվա վաղեմության աշխատանքային պատճենները, որոնց unit-ը **կանգնեցված է**, զգուշացնում է, երբ սկավառակի օգտագործումը ≥ 85 % է, հիշողության PSI-ի `full/avg60`-ը ≥ 10 % է, կամ listener-ների քանակը գերազանցում է `MAX_ACTIVE_RUNNERS`-ը (omniroute/այլ բաժանմամբ)։ Ելքի կոդ 1 = ուշադրություն է պահանջվում. կարդացեք լոգը։

75 րոպեի կանոնը չի հայտնաբերում այն build-ը, որի առաջադրանքից GitHub-ն արդեն հրաժարվել է։ Երբ `Runner.Listener`-ը չի կարողանում թարմացնել իր առաջադրանքը, `_diag/Runner_*.log`-ում երևում է `POST request to …/renewjob timed out after 100 seconds`, API-ն վերջին հաջող թարմացումից մոտ տասը րոպե անց առաջադրանքի վիճակը հայտնում է որպես `completed` (ձախողում), իսկ `next-build`-ը շարունակում է աշխատել՝ առանց կցված առաջադրանքի (2026-10-18-ին #17066-ի Build-ը ձախողված է հայտարարվել 19:43-ին, իսկ դրա build-ը հինգ րոպե անց դեռ զբաղեցնում էր 40 GB)։ Ստուգեք ref-ը ամենանոր `_diag/Worker_*.log`-ում, ապա PID-ով SIGTERM ուղարկեք միայն build-ի գործընթացների ծառին՝ `next-build`, `npm run build`, `build-next-isolated.mjs` և `_work` worker-ներ։ Երբեք մի՛ դիպչեք `Runner.Listener`-ին, `RunnerService.js`-ին կամ `Runner.Worker`-ին. worker-ը առաջադրանքը նշում է որպես չեղարկված, իսկ listener-ն ինքնուրույն կրկին անցնում է առցանց վիճակի։

## Runner unit-ներ. KillMode

Runner-ի լռելյայն `KillMode=process`-ը unit-ի կանգնեցման կամ վերագործարկման ժամանակ աշխատող է թողնում `Runner.Worker → npm → next-build`-ը. որբացած build-ը շարունակում է սպառել RAM և CPU՝ առանց կցված առաջադրանքի։ OmniRoute-ի յուրաքանչյուր unit ունի drop-in կազմաձևում (`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)՝ `KillMode=mixed`-ով. նախ SIGTERM է ուղարկվում listener-ին, ապա `TimeoutStop`-ի պահին SIGKILL է ուղարկվում ամբողջ cgroup-ին։ Այն ուժի մեջ է մտնում unit-ի հաջորդ վերագործարկման ժամանակ. վերագործարկեք **միաժամանակ միայն մեկ runner՝ միայն երբ այն պարապ է**, ընդ որում պարապ լինելու ստուգումն ու վերագործարկումը պետք է լինեն նույն հրամանում։

(`devbox-vm-06-dev002`, 24 vCPU / 54 GB) կարող էր հոսթավորել runner, սակայն գործակալի սեսիաներն արդեն դրա բեռնվածությունը պահում են 20–26-ի սահմաններում, գործակալի կոնտեյները չունի Docker daemon, իսկ գերբեռնված գիծը հոսթավորվածն է։ Նույն պահին `.113` մեքենայի վրա ազատ էր 71 GB, իսկ բեռնվածությունը 5–8 էր. դրա սահմանափակումը վերևում նշված յուրաքանչյուր listener-ի հիշողության բյուջեն է (առավելագույնը՝ 6 listener), ոչ թե CPU-ն։ Մնացած լծակները գործընթացային են՝ արշավի PR-ները միաձուլել Mergify-ի հերթի միջոցով (`label=queue`, փաթեթները համատեղ օգտագործում են մեկ `merge_group` CI գործարկում՝ յուրաքանչյուր PR-ի համար մեկ գործարկման և յուրաքանչյուր push-ի համար ևս մեկ գործարկման փոխարեն), կրճատել CodeQL-ի լռելյայն կարգավորման լեզուների ցանկը և `release-acceptance.yml`-ը զտել ըստ այն ֆայլերի, որոնք այն կարդում է։
