## npm Trusted Publishing (կանխադրված է v3.8.51-ից) — բեմադրվել է խնդրանքով, ուղղակի որպես հետադարձ

`npm-publish.yml` հրապարակում է միջոցով** npm Trusted Publishing (OIDC)** լռելյայնորեն. `stage-npm` աշխատանքը (github-հոսթինգ) փոխանակում է GitHub ի id-token-ը կարճատև npm հավատարմագրով այդ գործարկման համար — ոչ երկարատև npm նշան պահոցի գաղտնիքներում, ոչ 2FA հուշում, կցված ծագում: Դա շրջանցող npm պատժամիջոցներն են, երբ այն նշանները, որոնք բաց թողնում են 2FA-ն, հեռացվում են. այն վերականգնում է լիովին ավտոմատ հոսքը, որն ուներ նախագիծը մինչև v3.8.48՝ պահպանելով WS1.3 երաշխիքը (արտահոսած նշանը չի կարող միայնակ հրապարակել — չկա նշան):

**Միանգամյա կարգավորում (սեփականատեր).** npmjs.com → փաթեթ `omniroute` → Կարգավորումներ → _Trusted Publisher_ → GitHub. սեփականատեր `diegosouzapw`, repo `OmniRoute`, աշխատանքային հոսք `npm-publish.yml` (միջավայր՝ ոչ մեկը): Քանի դեռ դա գոյություն չունի, ավտոմատ քայլը ձախողվում է `ENEEDAUTH` ով. նորից ուղարկել `publish_mode=staged` ով (ներքևում) կամ `direct`:

### Բեմական հրատարակություն (ըստ ցանկության — `publish_mode=staged`)

npm-publish աշխատանքային հոսքն այլևս ուղղակիորեն չի հրապարակվում. այն բեռնում է փաթեթավորված tarball-ը (`check:pack-boot`) և այնուհետև գործարկում `npm stage publish` — ճշգրիտ բայթերը կայանված են գրանցամատյանում,** տեղադրման ենթակա չէ** մինչև սեփականատերը հաստատի: Մարդկային 2FA դարպասը շարժվեց AFTER համար, ոչ թե դրանից առաջ:

**Աշխատանքային ընթացքից հետո սեփականատերերի հոսքը կանաչ է դառնում.**

1. `npm stage list omniroute` — գտեք փուլի id-ը (նաև տպված է աշխատանքային հոսքի ամփոփագրում):
2. `npm stage download <id>` փուլային բայթերը ( CI `npm run check:pack-boot` տրվում →→
3. `npm stage approve <id>` — 2FA հուշում է IS հրապարակել: `npm stage reject <id>` մերժում է.
4. Հետհրապարակման ցանց. հետհրապարակման ստուգիչը (v3.8.49 պլանի WS1.4) տեղադրում է հրապարակված տարբերակը հանրային ռեեստրից մաքուր կոնտեյներով և բեռնաթափում այն:

**Արտակարգ իրավիճակների վերադարձ.** `workflow_dispatch` `publish_mode=direct` ով վերականգնում է ժառանգական անմիջական `npm publish` (օգտագործել միայն այն դեպքում, եթե բեմադրությունն ինքն իրեն սխալ է պահում. գրանցել ինչու):

**Միանգամյա կարծրացում (սեփականատեր, npmjs.com):** կարգավորեք Trusted Publisher-ը `omniroute` համար միայն փուլային ռեժիմում, որպեսզի արտահոսած երկարատև նշանը չկարողանա `npm publish` ուղղակիորեն ցանկացած վայրից, որտեղ — CI կարող է միայն բեմադրել. միայն սեփականատիրոջ 2FA թողարկումները:

**Կոտրված արտեֆակտ խաղագիրք (անփոփոխ).** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` որպես լռելյայն ռեֆլեքս (րոպե, շրջելի); `npm unpublish` միայն 72h/no-dependents պատուհանի ներսում և երբեք որպես առաջին քայլ: Docker. երբեք մի վերագրիր տարբերակի պիտակը — հետադարձը վերահղում է `latest` մինչև վերջին լավ ամփոփումը:

**Docker Hub `latest` (պահանջվում է յուրաքանչյուր կայուն SemVer հրապարակման համար).** `docker-publish` աշխատանքային հոսքը պետք է հատկորոշվի** երկուսն էլ** `X.Y.Z` եւ, երբ `should-promote-latest.sh` համաձայնում է սա ամենաբարձր կայուն SemVer, `:latest` հետ** նույն մարսողությունը** . Աշխատանքից հետո. Hub `latest` digest-ը հավասար է նոր SemVer digest-ին և `last_updated` տեղափոխվածին: Մի թողեք `:latest` ավելի հին նախագծում, մինչդեռ թողարկման նշումները խոսում են շտկումների մասին, որոնք գոյություն ունեն միայն git-ում: Կազմեք արագ մեկնարկներ, օգտագործեք `:latest`; GitOps պետք է շարունակի կապել `X.Y.Z`: Տես [Docker թողարկման ալիքները](../guides/DOCKER_GUIDE.md#release-channels) և #10317:

**Docker Hub կազմակերպության պահոց (`cheaperinference/omniroute`):** Docker Hub-ը չի կարող պահեստը տեղափոխել անվանատարածքների միջև, ուստի `diegosouzapw/omniroute` պահպանում է իր ձգման պատմությունը և յուրաքանչյուր թողարկում, իսկ `docker-publish` ի `mirror-org-dockerhub` աշխատանքը պատճենում է յուրաքանչյուր թողարկված տարբերակը (և `:latest`, երբ առաջխաղացվում է) `ghcr.io/cheaper-inference/omniroute` ից կազմակերպության պահեստ: Դրան անհրաժեշտ են `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` գաղտնիքները; առանց դրանց աշխատանքը մնում է կանաչ՝ «Docker Hub org mirror-ը բաց է թողնվել» նախազգուշացումով, իսկ մյուս գրանցամատյանները սովորաբար հրապարակվում են: Ավելի ուշ այնտեղ թողարկված տարբերակը հրապարակելու համար գործարկեք** Գործողություններ → Հայելի Docker պատկերը Docker Hub org → Գործարկել աշխատանքային հոսքը** `version=X.Y.Z` ով (և `promote_latest` ամենաբարձր կայուն տարբերակի համար). այն պատճենում է առկա պատկերները, առանց վերակառուցման:

## Թեժ շտկումների արագ ուղի (պիտակ՝ `hotfix`)

`hotfix` պիտակով PR-ը շրջանցում է CI-ի ծանր մատրիցը (9-շարդանոց E2E, ծածկույթի շեմի բարձրացում,
quality-gate, quality-extended) և պահպանում է արագ, բարձր ազդանշանային ստուգումները՝ build,
unit շարդեր, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
և tarball-ի մեկնարկային smoke ստուգումը (`check:pack-boot`)։ Նպատակ՝ կանաչ արդյունք ստանալ ≤15 րոպեում՝ ~33 րոպեի փոխարեն։

**Մուտքի քաղաքականություն — բոլոր չորս պահանջները պարտադիր են (մոդելավորված Chromium/VS Code/Node արտակարգ ուղիների հիման վրա).**

1. **Խստություն**. production-ը խափանված է՝ հրապարակված արտեֆակտը մեկնարկի ժամանակ խափանվում է /
   անվտանգության շտկում է / թողարկման յուրաքանչյուր օգտատեր տուժում է։ «Կարևոր»-ը չի նշանակում «խափանված»։
2. **Լիազորություն**. միայն պահոցի սեփականատերն է կիրառում `hotfix` պիտակը։ Պիտակն ԻՆՔՆԻՆ
   հաստատումն է՝ երբեք ինքնուրույն մի կիրառեք campaign PR-ի վրա։
3. **Ապացույց**. PR-ի նկարագրությունը հղում է տալիս նախորդ՝ ամբողջությամբ կանաչ ծանր գործարկմանը (այն հավաքակազմին,
   որը շրջանցված առաջադրանքները կրկին կվավերացնեին), ինչպես նաև տվյալ շտկման՝ սկզբում ձախողվող, ապա հաջող անցնող թեստին։
4. **Ծավալ**. միայն cherry-pick-ի համար՝ նվազագույն շտկում, առանց վերակառուցումների և կողմնակի փոփոխությունների։

Շրջանցված coverage/ratchet մակերեսը կրկին վավերացվում է release ճյուղի հաջորդ ամբողջական գործարկմամբ
(թողարկման շարունակական կանաչ վիճակ)՝ այս ուղին շրջանցում է ՍՊԱՍՈՒՄԸ, ոչ երբեք վավերացումը։
Միայն թեստեր պարունակող տարբերությունները (բոլոր ֆայլերը՝ `tests/`-ի տակ, ոչ մեկը՝ `tests/e2e/`-ի տակ) ավտոմատ կերպով շրջանցում են E2E
մատրիցը՝ առանց որևէ պիտակի։

### Կառուցման դասավորությունը

Պահեստն օգտագործում է երեք հստակ ելքային դիրեկտորիա — երբեք չի խառնում դրանք.

| տեղեկատու | Նպատակը                                                  | Հետևե՞լ եք:   |
| --------- | -------------------------------------------------------- | ------------- |
| `src/`    | Հավելվածի աղբյուրը (TypeScript / TSX)                    | Այո՛          |
| `.build/` | Կառուցեք միջանկյալ — `next build` ելք (`distDir`)        | Ոչ (անտեսված) |
| `dist/`   | Առաքվող npm փաթեթ — հավաքված `assembleStandalone` կողմից | Ոչ (անտեսված) |

> **Օպերատորի նշում.** հեռավոր VPS պատկերների գրացուցակը մնում է `/usr/lib/node_modules/omniroute/app/`: Միայն** ռեպո-ում** build output տեղափոխվել (`app/` → `dist/`). Հմտությունների տեղակայումը rsync `dist/` բովանդակությունը հեռավոր `app/` dir — չի պահանջվում VPS ճանապարհի փոփոխություններ:

**Մեկ կառուցման հոսք.**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Կատարեք NOT գործարկեք `npm run build` որին հաջորդում է առանձին `npm run build:cli` — տեղակայման համար, օգտագործեք `npm run build:release`, որը մաքուր վերակառուցում է + պահակետը մեկ հրամանով:

## 3.9.0 LTS cut (փորձված է 3.8.58-ում)

v3.8.59-ից հետո հաջորդ տարբերակը 3.9.0-ն է, և դրա ծայրը դառնում է երկու երկարակյաց ճյուղեր՝ `stable/v3` (v3 LTS գիծ, npm `latest`) և `develop` (v4, bumped 4.0.0, npm `nightly`): branch/channel մոդելը, առաջ-պորտը և պիտակները [RELEASE_STRATEGY են .md](./RELEASE_STRATEGY.md) ; պլանը գտնվում է [ROADMAP](../../ROADMAP.md) ում (փուլ 3): Կտրումը կատարվում է մեկ անգամ; 3.8.58-ը կրկնում է այն ծայրից ծայր պատառաքաղի վրա, իսկ 3.8.59-ը փակվում է [GO/NO-GO ստուգաթերթով](./LTS_GO_NO_GO.md) :

### Չոր աշխատանք (միայն կարդալու, ցանկացած պահի անվտանգ)

```bash
npm run release:dry-run-lts-cut                       # the real cut: 3.9.0 from HEAD, previous tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # pin the source commit
```

`scripts/release/dry-run-lts-cut.mjs` executes nothing: it reads git and `gh` and prints the whole sequence — preconditions (source resolves, the source repository has full history — a shallow clone cannot push `stable/v3`, the receiving side rejects the pack at the first grafted parent, so cut from a full clone or `git fetch --unshallow origin` first — previous tag exists, `package.json` is the target version, a `release-freeze` issue is open, no open `Release branch not green` issue on an existing release branch — a branch that does not exist reports `?` unknown, never green — omni-queue lands the release PRs (G11: `config/merge-queue/config.json` valid, its `bases` manage the release branch, `mode` `live`, its label exists), the `release/*` ruleset still blocks deletion and force-push, and `stable/v3` and `develop` do not exist yet), the two branch steps, which dormant-workflow triggers and `if:` conditions turn true (and which stay gated by a repository variable or pinned to the canonical repository), the expected dist-tags (`latest` → 3.9.0, `next` and `nightly` empty) and the rollback. Exit `0` = `RESULT: READY`, `1` = a blocking precondition failed (`✗`), `2` = usage error. `--advisory <id,...>` downgrades a check to a warning (`!`) without hiding it.

Գործարկեք իրական կտրվածքի չոր գործարկումը, — 3.9.0 թողարկման սառեցումը դեռ բաց է:

### 3.8.58 փորձ (միայն պատառաքաղ)

```bash
# 1. Dry-run on the current tip with rehearsal parameters
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. Execute against a FORK remote (origin, or any remote whose URL is the canonical
#    repository, is refused; every step asks for confirmation on the terminal)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. Exercise the dormant workflows in the fork (workflow_dispatch where the dry-run
#    reports a canonical-repository pin), then roll back
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

Development bump commit-ը կառուցված է git plumbing-ով (աշխատող ծառ չի դիպչում) և բախվում է նույն հինգ ֆայլերին, ինչ ցիկլային բաց կոմիտը՝ `package.json`, `open-sse/package.json`, `electron/package.json`, `package-lock.json` և `docs/openapi.yaml`: `[4.0.0]` CHANGELOG հատվածը և նրա i18n հայելիները բացվում են `develop` վրա այնուհետև՝ առաջին PR ից առաջ: Սցենարը երբեք չի փոխվում npm dist-tags — rehearse of a scratch փաթեթի վրա:

### PR նախադիտման արտեֆակտ (կառուցել մեկ անգամ, խթանել նույն բայթերը)

`.github/workflows/preview-artifact.yml` կառուցում է մեկ արտադրական tarball PR գլխից և հաստատում է այդ ճշգրիտ կառուցվածքը (#8084 կտոր (a)): Միայն PRs նույն պահոցը; ոչինչ չի հրապարակվում.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # or add the `preview-artifact` label
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview install
```

Գործարկումը կատարում է `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, փաթեթավորում է tarball-ը, գործարկում `npm run check:pack-boot` (կեղծ գաղտնիքներ, ժամանակավոր տվյալների dir), նորից փաթեթավորում և ձախողվում է, քանի դեռ ամփոփումը նույնական չէ, այնուհետև գրանցում է `artifact-identity.json` (գլուխ SHA, բազային SHA, lockfile hash, ABI, քաղաքականություն, — attest `scripts/release/artifact-identity.mjs`): թարբոլը առանձին աշխատանքում։ Նախադիտման խթանումը նշանակում է տեղադրել այդ tarball-ը. երբեք մի վերակառուցեք աղբյուրից:

### Կտրումը (3.9.0, GO ից հետո)
