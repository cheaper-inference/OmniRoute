## npm Trusted Publishing (կանխադրված՝ սկսած v3.8.51-ից) — ըստ պահանջի՝ փուլային, որպես պահուստային տարբերակ՝ ուղղակի

`npm-publish.yml`-ը կանխադրված կերպով հրապարակում է **npm Trusted Publishing (OIDC)**-ի միջոցով․
`stage-npm` առաջադրանքը (GitHub-ի կողմից սպասարկվող) GitHub-ի id-token-ը փոխանակում է այդ գործարկման համար
կարճաժամկետ npm հավատարմագրի հետ՝ առանց պահոցում երկարաժամկետ npm նշագրի, առանց 2FA հուշման և կցված ծագման տվյալներով։
Սա npm-ի թույլատրած շրջանցման եղանակն է այժմ, երբ 2FA-ն շրջանցող նշագրերը հանվում են գործածությունից․
այն վերականգնում է մինչև v3.8.48-ը նախագծում առկա լիովին ավտոմատ հոսքը՝ միաժամանակ պահպանելով
WS1.3-ի երաշխիքը (արտահոսած նշագիրը միայնակ չի կարող հրապարակում կատարել, քանի որ նշագիր չկա)։

**Մեկանգամյա կարգավորում (սեփականատեր)՝** npmjs.com → `omniroute` փաթեթ → Settings → _Trusted
Publisher_ → GitHub՝ owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)։ Քանի դեռ սա գոյություն չունի, ավտոմատ քայլը ձախողվում է `ENEEDAUTH` սխալով․
կրկին գործարկեք `publish_mode=staged`-ով (ստորև) կամ `direct`-ով։

### Փուլային հրապարակում (ըստ պահանջի՝ `publish_mode=staged`)

npm-publish աշխատանքային հոսքն այլևս ուղղակիորեն չի հրապարակում․ այն գործարկում է փաթեթավորված tarball-ը
(`check:pack-boot`), ապա կատարում է `npm stage publish`․ հենց այդ բայթերը տեղադրվում են
գրանցամատյանում, սակայն **տեղադրման համար հասանելի չեն**, մինչև սեփականատերը չհաստատի։ Մարդու մասնակցությամբ 2FA սահմանը
տեղափոխվել է ապացույցից ՀԵՏՈ, ոչ թե դրանից առաջ։

**Սեփականատիրոջ ընթացակարգը աշխատանքային հոսքի կանաչ դառնալուց հետո՝**

1. `npm stage list omniroute` — գտեք փուլի id-ն (այն նաև ցուցադրվում է աշխատանքային հոսքի ամփոփագրում)։
2. Ստուգեք փուլավորված բայթերը (խորհուրդ է տրվում)՝ `npm stage download <id>`, ապա ներբեռնված
   tarball-ը տեղադրեք ժամանակավոր prefix-ում և գործարկեք այն (`npm run check:pack-boot`-ը CI-ում ավտոմատացնում է
   նույն pack→install→boot ստուգման արդյունքը)։
3. `npm stage approve <id>` — 2FA հուշումն ԻՆՔՆԻՆ հրապարակումն է։ `npm stage reject <id>`-ը չեղարկում է այն։
4. Հրապարակումից հետո անվտանգության ցանց․ հրապարակումից հետո ստուգիչը (v3.8.49 ծրագրի WS1.4-ը)
   մաքուր կոնտեյներում տեղադրում է հրապարակված տարբերակը հանրային գրանցամատյանից և գործարկում այն։

**Արտակարգ պահուստային տարբերակ՝** `workflow_dispatch`-ը `publish_mode=direct`-ով վերականգնում է
նախկին անմիջական `npm publish`-ը (օգտագործեք միայն այն դեպքում, եթե փուլավորումն ինքնին սխալ է աշխատում, և գրանցեք պատճառը)։

**Մեկանգամյա խստացում (սեփականատեր, npmjs.com)՝** կարգավորեք Trusted Publisher-ը
`omniroute`-ի համար միայն փուլավորման ռեժիմով, որպեսզի արտահոսած երկարաժամկետ նշագիրը չկարողանա որևէ տեղից ուղղակիորեն կատարել `npm publish`․
CI-ն կարող է միայն փուլավորել, իսկ հրապարակել կարող է միայն սեփականատիրոջ 2FA-ն։

**Խափանված արտեֆակտի գործելակարգ (անփոփոխ)՝** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
որպես կանխադրված արձագանք (րոպեներ է տևում, շրջելի է)․ `npm unpublish`՝ միայն 72h/կախյալներ-չկան
պատուհանի ընթացքում և երբեք՝ որպես առաջին քայլ։ Docker-ի դեպքում երբեք մի վերագրեք տարբերակի պիտակը․ հետադարձ անցումը
`latest`-ը վերջին աշխատող digest-ին վերաուղղելն է։

**Docker Hub-ի `latest` (պարտադիր՝ յուրաքանչյուր կայուն SemVer հրապարակման ժամանակ)՝**
`docker-publish` աշխատանքային հոսքը պետք է պիտակավորի **և՛** `X.Y.Z`-ը, և՛, երբ
`should-promote-latest.sh`-ը հաստատում է, որ սա ամենաբարձր կայուն SemVer-ն է, `:latest`-ը՝
**նույն digest-ով**։ Առաջադրանքից հետո Hub-ի `latest` digest-ը պետք է հավասար լինի նոր
SemVer digest-ին, իսկ `last_updated`-ը՝ թարմացված լինի։ `:latest`-ը մի թողեք ավելի հին
հավաքման վրա, երբ թողարկման նշումները խոսում են ուղղումների մասին, որոնք գոյություն ունեն միայն git-ում։
Compose-ի արագ մեկնարկի օրինակներն օգտագործում են `:latest`, իսկ GitOps-ը պետք է շարունակի ամրագրել `X.Y.Z`-ը։ Տե՛ս
[Docker-ի թողարկման ալիքները](../guides/DOCKER_GUIDE.md#release-channels) և #10317։

## Թեժ շտկումների արագ ուղի (պիտակ՝ `hotfix`)

`hotfix` պիտակով PR-ը շրջանցում է CI-ի ծանր մատրիցը (9-շարդանոց E2E, ծածկույթի շեմի բարձրացում,
quality-gate, quality-extended) և պահպանում է արագ, բարձր ազդանշանային ստուգումները՝ build,
unit շարդեր, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
և tarball-ի մեկնարկային smoke ստուգումը (`check:pack-boot`)։ Նպատակ՝ կանաչ արդյունք ստանալ ≤15 րոպեում՝ ~33 րոպեի փոխարեն։

**Մուտքի քաղաքականություն — բոլոր չորս պահանջները պարտադիր են (մոդելավորված Chromium/VS Code/Node արտակարգ ուղիների հիման վրա).**

1. **Խստություն**. production-ը խափանված է՝ հրապարակված արտեֆակտը մեկնարկի ժամանակ խափանվում է /
   անվտանգության շտկում է / թողարկման յուրաքանչյուր օգտատեր տուժում է։ «Կարևոր»-ը չի նշանակում «խափանված»։
2. **Լիազորություն**. միայն պահոցի սեփականատերն է կիրառում `hotfix` պիտակը։ Պիտակն ԻՆՔՆԻՆ
   հաստատումն է՝ երբեք ինքնուրույն մի կիրառեք campaign PR-ի վրա։
3. **Ապացույց**. PR-ի նկարագրությունը հղում է տալիս նախորդ՝ ամբողջությամբ կանաչ ծանր գործարկմանը (այն հավաքակազմին,
   որը շրջանցված առաջադրանքները կրկին կվավերացնեին), ինչպես նաև տվյալ շտկման՝ սկզբում ձախողվող, ապա հաջող անցնող թեստին։
4. **Ծավալ**. միայն cherry-pick-ի համար՝ նվազագույն շտկում, առանց վերակառուցումների և կողմնակի փոփոխությունների։

Շրջանցված coverage/ratchet մակերեսը կրկին վավերացվում է release ճյուղի հաջորդ ամբողջական գործարկմամբ
(թողարկման շարունակական կանաչ վիճակ)՝ այս ուղին շրջանցում է ՍՊԱՍՈՒՄԸ, ոչ երբեք վավերացումը։
Միայն թեստեր պարունակող տարբերությունները (բոլոր ֆայլերը՝ `tests/`-ի տակ, ոչ մեկը՝ `tests/e2e/`-ի տակ) ավտոմատ կերպով շրջանցում են E2E
մատրիցը՝ առանց որևէ պիտակի։

Պահեստն օգտագործում է երեք հստակ ելքային դիրեկտորիա — երբեք չի խառնում դրանք.

| տեղեկատու | Նպատակը                                                  | Հետևե՞լ եք:   |
| --------- | -------------------------------------------------------- | ------------- |
| `src/`    | Հավելվածի աղբյուրը (TypeScript / TSX)                    | Այո՛          |
| `.build/` | Կառուցեք միջանկյալ — `next build` ելք (`distDir`)        | Ոչ (անտեսված) |
| `dist/`   | Առաքվող npm փաթեթ — հավաքված `assembleStandalone` կողմից | Ոչ (անտեսված) |

> **Օպերատորի նշում.** հեռավոր VPS պատկերների գրացուցակը մնում է `/usr/lib/node_modules/omniroute/app/`: Միայն** ռեպո-ում** build output տեղափոխվել (`app/` → `dist/`). Հմտությունների տեղակայումը rsync `dist/` բովանդակությունը հեռավոր `app/` dir — չի պահանջվում VPS ճանապարհի փոփոխություններ:

**Մեկ կառուցման հոսք.**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Կատարեք NOT գործարկեք `npm run build` որին հաջորդում է առանձին `npm run build:cli` — տեղակայման համար, օգտագործեք `npm run build:release` որը մաքուր վերակառուցում է + պահակետը մեկ հրամանով:

## 3.9.0 LTS ճյուղավորումը (փորձարկվել է 3.8.58-ում)

v3.8.59-ից հետո հաջորդ տարբերակը 3.9.0-ն է, և դրա վերջին commit-ից ստեղծվում են երկու երկարաժամկետ ճյուղեր՝
`stable/v3` (v3 LTS գիծը, npm `latest`) և `develop` (v4, տարբերակը բարձրացված է մինչև 4.0.0, npm
`nightly`)։ Ճյուղերի/ալիքների մոդելը, առաջ փոխադրումը և պիտակները նկարագրված են
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md)-ում, իսկ պլանը՝ [ROADMAP](../../ROADMAP.md)-ում (Փուլ 3)։ Ճյուղավորումն իրականացվում է մեկ անգամ.
3.8.58-ը սկզբից մինչև վերջ փորձարկում է այն fork-ում, իսկ 3.8.59-ն ավարտվում է
[GO/NO-GO ստուգաթերթով](./LTS_GO_NO_GO.md)։

### Փորձնական գործարկում (միայն ընթերցում, անվտանգ է ցանկացած պահի)

```bash
npm run release:dry-run-lts-cut                       # իրական ճյուղավորումը՝ 3.9.0՝ HEAD-ից, նախորդ թեգը՝ v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # ամրագրել սկզբնաղբյուր commit-ը
```

`scripts/release/dry-run-lts-cut.mjs`-ը ոչինչ չի կատարում. այն կարդում է git-ի և `gh`-ի տվյալները և արտածում ամբողջ
հաջորդականությունը՝ նախապայմանները (սկզբնաղբյուրը որոշվում է, սկզբնաղբյուր պահոցն ունի ամբողջական պատմություն.
մակերեսային clone-ը չի կարող push անել `stable/v3`, ընդունող կողմը մերժում է փաթեթը առաջին
արհեստականորեն միացված ծնող commit-ի մոտ, ուստի նախ կատարեք ճյուղավորումն ամբողջական clone-ից կամ
`git fetch --unshallow origin` — նախորդ թեգը գոյություն ունի, `package.json`-ում նշված է նպատակային տարբերակը,
բաց է `release-freeze` issue, գոյություն ունեցող թողարկման ճյուղում բաց
`Release branch not green` issue չկա. գոյություն չունեցող ճյուղը հաղորդում է անհայտ `?` վիճակ և երբեք
կանաչ չի համարվում. Mergify-ի `release` հերթը կազմաձևված է (G11՝ `queue_rules`, `checks_timeout`,
`queue` պիտակ), `release/*` կանոնների հավաքածուն դեռ արգելափակում է ջնջումը և force-push-ը, իսկ
`stable/v3`-ը և `develop`-ը դեռ գոյություն չունեն), ճյուղերի երկու քայլերը, dormant workflow-ների
որ trigger-ներն ու `if:` պայմաններն են դառնում true (և որոնք են մնում պահոցի փոփոխականով սահմանափակված կամ
կանոնական պահոցին ամրագրված), սպասվող dist-tag-երը (`latest` → 3.9.0, `next` և
`nightly`՝ դատարկ) և հետադարձումը։ Ելքի `0` = `RESULT: READY`, `1` = արգելափակող նախապայմանը
չի կատարվել (`✗`), `2` = օգտագործման սխալ։ `--advisory <id,...>`-ը ստուգումը դարձնում է նախազգուշացում (`!`)՝
առանց այն թաքցնելու։

Իրական ճյուղավորման փորձնական գործարկումը կատարեք, քանի դեռ 3.9.0-ի թողարկման սառեցումը բաց է. ճյուղերը
ստեղծվում են թեգից հետո և մինչև Փուլ 12c-ում սառեցումը վերացնելը։

### 3.8.58-ի փորձարկում (միայն fork-ում)

```bash
# 1. Փորձնական գործարկում ընթացիկ վերջին commit-ի վրա՝ փորձարկման պարամետրերով
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. Կատարել FORK remote-ի նկատմամբ (origin-ը կամ ցանկացած remote, որի URL-ը կանոնական
#    պահոցինն է, մերժվում է. յուրաքանչյուր քայլի համար տերմինալում հաստատում է պահանջվում)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. Գործարկել dormant workflow-ները fork-ում (workflow_dispatch այնտեղ, որտեղ փորձնական գործարկումը
#    հայտնում է կանոնական պահոցին ամրագրում), ապա հետադարձել
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

develop-ի տարբերակը բարձրացնող commit-ը ստեղծվում է git plumbing-ի միջոցով (աշխատանքային ծառը չի փոփոխվում) և թարմացնում է
նույն հինգ ֆայլերը, ինչ ցիկլը բացող commit-ը՝ `package.json`, `open-sse/package.json`,
`electron/package.json`, `package-lock.json` և `docs/openapi.yaml`։ `[4.0.0]`
CHANGELOG բաժինը և դրա i18n պատճենները դրանից հետո բացվում են `develop`-ում՝ մինչև դրա առաջին
PR-ը։ Սկրիպտը երբեք չի փոփոխում npm dist-tag-երը. դրանք փորձարկեք ժամանակավոր փաթեթի վրա։

### PR-ի նախադիտման արտեֆակտ (կառուցել մեկ անգամ, առաջխաղացնել նույն բայթերը)

`.github/workflows/preview-artifact.yml`-ը PR-ի head-ից կառուցում է մեկ production tarball և
վավերացնում հենց այդ build-ը (#8084 հատված (a))։ Միայն նույն պահոցի PR-ներ. ոչինչ չի հրապարակվում։

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # կամ ավելացրեք `preview-artifact` պիտակը
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # նախադիտման տեղադրում
```

Գործարկումը կատարում է `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, փաթեթավորում է
tarball-ը, գործարկում `npm run check:pack-boot` (կեղծ գաղտնիքներ, ժամանակավոր տվյալների գրացուցակ), կրկին փաթեթավորում է և
ձախողվում, եթե digest-ը նույնական չէ, ապա գրանցում է `artifact-identity.json`-ը (head SHA, base
SHA, lockfile hash, հարթակ, ճարտարապետություն, node ABI, bundler, կառուցման քաղաքականություն՝
`scripts/release/artifact-identity.mjs`) և առանձին job-ում հաստատում է tarball-ի ծագումը։ Նախադիտման
առաջխաղացումը նշանակում է տեղադրել այդ tarball-ը. երբեք մի վերակառուցեք սկզբնաղբյուրից։

### Ճյուղավորումը (3.9.0, GO-ից հետո)

1. GO-ն գրանցված է [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)-ում։
2. `npm run release:dry-run-lts-cut -- --from v3.9.0`-ն արտածում է `RESULT: READY`։
3. Ձեռքով ստեղծեք ճյուղերը `origin`-ում՝ փորձնական գործարկման արտածած հրամաններով.
   սկրիպտը հրաժարվում է push անել դեպի `origin`։ Վերանայված develop commit-ը կրկին օգտագործելու համար նախ
   կատարեք `--execute` փորձարկումը 3.9.0-ի վերջին commit-ի վրա՝ ձեր fork-ի նկատմամբ. այն արտածում է երկու SHA-ներն էլ, և
   նույն commit-ները կարելի է push անել.

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. Պաշտպանեք `stable/v3`-ը և `develop`-ը (կանոնների հավաքածուներ + միաձուլման հերթ), նախքան առաջին PR-ի մուտքը։
5. Չգործարկված աշխատանքային հոսքերն ակտիվանում են ճյուղի առկայությամբ՝ `forward-port.yml` (`stable/v3`
   ուղարկման դեպքում), `validate-stable-pr.yml` (`stable/v3`-ին ուղղված PR-ների համար) և `nightly-v4-build.yml`
   (`develop`-ի կառուցումներ)։ Նախքան գործարկումը սահմանեք պահոցի `secrets.FORWARD_PORT_TOKEN` գաղտնիքը (որպեսզի CI-ն աշխատի
   առաջ տեղափոխման PR-ների համար)։ Գիշերային հրապարակումը կմնա անջատված, մինչև պատասխանատուն պահոցի
   `vars.NIGHTLY_PUBLISH` փոփոխականի արժեքը սահմանի `true`, իսկ npm Trusted Publishing-ը ընդունի
   `nightly-v4-build.yml`-ը։ Ալիքի որոշումն իրականացնում է `scripts/release/dist-tag.mjs`-ը՝ նույն
   որոշիչը, որն օգտագործում է `npm-publish.yml`-ը։
6. Ստուգեք ալիքները․ `npm view omniroute dist-tags --json`-ը պետք է ցույց տա `latest` = 3.9.0 և չպարունակի
   `next` / `nightly`, մինչև v4-ի հրապարակումը։
7. Անհրաժեշտության դեպքում հետ գլորեք փոփոխությունները՝ `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   և `npm dist-tag add omniroute@3.8.59 latest`։

## Հետադարձում

Եթե թողարկումն ունի լուրջ խնդիր՝

1. `gh release edit vX.Y.Z --prerelease` (նշում է որպես ոչ վերջին)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (միայն եթե օգտատերերը դեռ չեն սկսել օգտագործել այն)
3. Կամ՝ թեժ շտկում `release/vX.Y.0`-ում → շտկող թողարկում `vX.Y.(Z+1)`
4. Անմիջապես տեղեկացնել GitHub Discussions-ում և Discord-ում

- Երբեք կոմիթ չանել գաղտնիքներ, մուտքային տվյալներ կամ `.env` ֆայլեր

- `src/`, `open-sse/`, `electron/` կամ `bin/` պանակներում արտադրական կոդը փոփոխելիս միշտ ներառել կամ թարմացնել թեստերը

## Համաժամացման ավտոմատացված ստուգում

Նախքան PR բացելը՝ տեղային միջավայրում գործարկեք փաստաթղթերի համաժամացման պաշտպանիչ ստուգումը՝

```bash
npm run check:docs-sync
```

CI-ն նույնպես գործարկում է այս ստուգումը `.github/workflows/ci.yml`-ում (lint առաջադրանք)։
