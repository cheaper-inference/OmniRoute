## Զրույցի լրացումներ

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Հատուկ վերնագրեր

| Վերնագիր                 | Ուղղություն | Նկարագրություն                                                                                                                                                                                                                                          |
| ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Հարցում     | Սահմանեք `true`՝ քեշը շրջանցելու համար                                                                                                                                                                                                                  |
| `x-omniroute-no-memory`  | Հարցում     | Սահմանեք `true`՝ այս հարցման համար հիշողության և հմտությունների ներարկումը բաց թողնելու նպատակով (համարժեք է no-cache-ին և խուսափում է յուրաքանչյուր կանչի թոքենների/արժեքի լրացուցիչ ծախսից)                                                           |
| `X-OmniRoute-Progress`   | Հարցում     | Սահմանեք `true`՝ առաջընթացի իրադարձություններ ստանալու համար                                                                                                                                                                                            |
| `X-Session-Id`           | Հարցում     | Մշտակայուն աշխատաշրջանի բանալի՝ արտաքին աշխատաշրջանի կապակցվածության համար                                                                                                                                                                              |
| `x_session_id`           | Հարցում     | Ընդունվում է նաև ընդգծման նիշով տարբերակը (ուղղակի HTTP)                                                                                                                                                                                                |
| `X-OmniRoute-Session-Id` | Հարցում     | Կանչող կողմի տրամադրած աշխատաշրջանի/զրույցի պիտակ (նաև փոխանցվում է հիշողությանը)։ Առկայության դեպքում անփոփոխ պահպանվում է `call_logs.session_tag`-ում՝ ըստ աշխատաշրջանի ծախսերի վերագրման համար (#8249), իսկ բացակայության դեպքում երբեք չի ստեղծվում |
| `Idempotency-Key`        | Հարցում     | Կրկնությունների վերացման բանալի (5 վրկ պատուհան)                                                                                                                                                                                                        |
| `X-Request-Id`           | Հարցում     | Կրկնությունների վերացման այլընտրանքային բանալի                                                                                                                                                                                                          |
| `x-omniroute-connection` | Հարցում     | Մեկ մոդելով հարցումն ամրագրեք մատակարարի մեկ կապին (հաշվին)՝ ըստ դրա id-ի — տե՛ս [Հաշվի ամրագրում յուրաքանչյուր հարցման համար](#account-pinning-per-request)                                                                                            |
| `X-OmniRoute-Cache`      | Պատասխան    | `HIT` կամ `MISS` (ոչ հոսքային ռեժիմում)                                                                                                                                                                                                                 |
| `X-OmniRoute-Idempotent` | Պատասխան    | `true`, եթե կրկնությունը հեռացվել է                                                                                                                                                                                                                     |
| `X-OmniRoute-Progress`   | Պատասխան    | `enabled`, եթե առաջընթացի հետևումը միացված է                                                                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | Պատասխան    | OmniRoute-ի կողմից օգտագործված փաստացի աշխատաշրջանի ID-ն                                                                                                                                                                                                |
| `X-OmniRoute-Request-Id` | Պատասխան    | Հարցումների համակցման id-ն (երբ հայտնի է)                                                                                                                                                                                                               |
| `X-OmniRoute-Version`    | Պատասխան    | OmniRoute-ի հավաքման տարբերակը (միշտ առկա է)                                                                                                                                                                                                            |
| `X-OmniRoute-Cost-Saved` | Պատասխան    | Քեշի շնորհիվ խնայված գումարը՝ USD-ով, HIT-ի դեպքում (միայն քեշի համընկնումների համար)                                                                                                                                                                   |
| `X-OmniRoute-Decision`   | Պատասխան    | Ուղղորդման հետագիծ՝ `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>`-ը համակցության ռազմավարությունն է, իսկ ոչ համակցված հարցման դեպքում՝ `single`) — միշտ առկա է ավարտական պատասխաններում                                                 |

> Nginx-ի նշում․ եթե ապավինում եք ընդգծման գծիկ պարունակող վերնագրերին (օրինակ՝ `x_session_id`), միացրեք `underscores_in_headers on;`։

#### Հաշվի ամրագրում՝ յուրաքանչյուր հարցման համար

Երբ մատակարարն ունի մի քանի միացում (հաշիվներ կամ բանալիներ), OmniRoute-ը սովորաբար ընտրում է դրանցից մեկը՝
հաշվի ընտրության իր ռազմավարության միջոցով։ Փոխարենը՝ հարցումը կարող է ամրագրել մեկ կոնկրետ միացում՝
օգտագործելով `x-omniroute-connection` վերնագիրը․

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Որտեղ գտնել նույնացուցիչը։** Կառավարման վահանակում բացեք մատակարարի էջը
  (**Կառավարման վահանակ → Մատակարարներ → <մատակարար>**) և միացման տողում սեղմեք `xxxxxxxx…` նույնացուցիչի նշիկի վրա․
  այն պատճենում է միացման ամբողջական նույնացուցիչը։
- **Որ հարցումներն են այն հաշվի առնում։** Մեկ մոդելով հարցումները (`provider/model`)՝
  `/v1/chat/completions`, `/v1/messages` և `/v1/responses` հասցեներում։ Կոմբինացիաներն անտեսում են վերնագիրը․
  դրա փոխարեն յուրաքանչյուր կոմբինացիայի քայլի համար ամրագրեք հաշիվ՝ այդ քայլի սեփական միացման միջոցով։
- **Ամրագրումը խիստ է, ոչ թե նախապատվություն։** Օգտագործվում է բացառապես ամրագրված միացումը։ Հարցման
  ընթացքում առաջացած խափանումը գրանցում է հաշվի սառեցման ժամանակահատվածը, բայց **չի** անցնում
  նույն մատակարարի մեկ այլ հաշվին։
- **Սառեցման ժամանակահատվածը և քվոտան չեղարկում են ամրագրումը։** Քանի դեռ ամրագրված միացումը գտնվում է սառեցման փուլում,
  սպառել է քվոտան կամ արգելափակված է քվոտայի քաղաքականությամբ, հետագա հարցումները անցնում են մատակարարի
  մյուս միացումներին՝ ճիշտ այնպես, ինչպես չամրագրված երթևեկության դեպքում։
- **Անհայտ կամ անջատված նույնացուցիչների դեպքում հարցումը ձախողվում է։** Մատակարարի ակտիվ միացումների խմբում չգտնվող նույնացուցիչը (ջնջված,
  ապաակտիվացված կամ մեկ այլ մատակարարին պատկանող) չի թողնում որևէ համապատասխան հաշիվ, ուստի հարցումը
  ձախողվում է՝ այլ ուղղությամբ աննկատ փոխանցվելու փոխարեն։

Claude Code-ը հատուկ վերնագրերն ուղարկում է `ANTHROPIC_CUSTOM_HEADERS`-ի միջոցով։ Տեղադրեք այն `env` բլոկում՝
`~/.claude/settings.json` ֆայլում, կամ նախագծի մակարդակի `.claude/settings.json` ֆայլում՝ յուրաքանչյուր նախագծի
համար տարբեր հաշիվ ամրագրելու նպատակով․

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Աղբյուր՝ `src/sse/handlers/chat.ts` (վերնագրի ընթերցում), `src/sse/services/auth.ts` և
`src/sse/services/sessionAffinityPin.ts` (ամրագրման չեղարկում և ակտիվ խմբում բացակայելու ստուգում)։

> **Արժեքի հեռաչափության վերնագրեր․** առանց հոսքային փոխանցման հաջող պատասխանները նաև պարունակում են արժեքի հեռաչափության `X-OmniRoute-*` հավաքածուն՝ `X-OmniRoute-Response-Cost` (USD, տասնորդական կետից հետո հաստատուն 10 նիշով, իսկ անվճար/չգնահատված դեպքերի համար՝ `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` և `X-OmniRoute-Fallback-Attempts` (միայն երբ > 0), ինչպես նաև `X-OmniRoute-Request-Id` և `X-OmniRoute-Version`։ Դրանք տրամադրվում են զրույցի լրացումների, `/v1/responses`, `/v1/messages`, **ինչպես նաև մեդիա վերջնակետերի** կողմից՝ `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` և `/v1/moderations` (արժեքը միշտ `0`)։ Երբ գնագոյացումը հասանելի է, մեդիայի արժեքը հաշվարկվում է ըստ եղանակի (յուրաքանչյուր պատկերի, վայրկյանի, նիշի կամ որոնման միավորի համար), հակառակ դեպքում այն `0` է (fail-open)։

> **Պահոցում համընկնման արժեքի իմաստաբանություն․** իմաստային պահոցում HIT-ի դեպքում (`X-OmniRoute-Cache-Hit: true`) վերին հոսքի հարցում չի կատարվում, ուստի `X-OmniRoute-Response-Cost`-ը `0.0000000000` է (համընկնումը սպասարկելու **հավելաճային** արժեքը)։ Սկզբնական/հնարավոր արժեքը հաղորդվում է առանձին՝ `X-OmniRoute-Cost-Saved`-ում։ Վճարումների տվյալների սպառողները պետք է գումարեն `X-OmniRoute-Response-Cost`-ը (համընկնումներն անվճար են), իսկ պահոցի վերլուծության համակարգերը կարող են համախմբել `X-OmniRoute-Cost-Saved`-ը։

## Բացառիկ կառավարվող սեսիայի վարձակալություններ

Բացառիկ կառավարվող սեսիայի վարձակալումն ըստ ցանկության միացվող, հաճախորդից անկախ երթուղավորման պայմանագիր է․ մեկ ակտիվ սեփականատեր տիրապետում է մեկ համապատասխան OmniRoute կապի։ Այն չի վարձակալում մոդել, չի պահանջում OAuth, չի նույնականացնում որոշակի հաճախորդ և չի պահանջում որոշակի մատակարար։

Նույնականացման համար օգտագործվող API բանալին պետք է ունենա `lease:exclusive` հասանելիության տիրույթ և բացահայտ սահմանված, ոչ դատարկ `allowedConnections` ցանկ։ Տվյալների բազայի փոփոխության սահմանը պարտադրում է երկու դաշտերի համատեղ առկայությունը թե՛ բանալի ստեղծելիս, թե՛ մասնակի թարմացումների ժամանակ։

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Հաջող ձեռքբերման, երկարաձգման և ազատման պատասխանները տրամադրում են ժամանակային դրոշմներ, `state`-ը և ճշգրիտ դրական `generation`-ը, սակայն երբեք չեն բացահայտում ընտրված կապը կամ հավատարմագրերը։ Երկարաձգման և ազատման դեպքում սերունդը փոխանցվում է JSON մարմնում․

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Ակտիվ վարձակալության սեփականատերը կարող է բացահայտորեն պահանջել գաղտնիությանը չվնասող ցուցադրման մետատվյալներ իր ընթացիկ կապակցման համար․

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ըստ ցանկության կիրառվող այս կարգավիճակի գործողությունը մեկ տվյալների բազայի գործարքի շրջանակում սահմանափակվում է անթափանց սեփականատիրոջով, նույնականացված կառավարվող API բանալիով և ակտիվ սերնդի ճշգրիտ արժեքով։ `displayName`-ը միայն կապի կազմաձևված անվան՝ եզրերից բացատները հեռացված տարբերակն է․ այն `null` է, երբ անվտանգ կազմաձևված անուն գոյություն չունի։ OmniRoute-ը երբեք այն չի փոխարինում էլփոստի հասցեով կամ ստեղծված հաշվի նույնությամբ։ Մատակարարի արժեքը ոչ զգայուն ցուցադրման պիտակ է և երբեք համատեղելի մատակարարի ստեղծված նույնացուցիչ չէ։ Հավատարմագրերը, թոքենները, cookie-ները, կապի կամ API բանալու անմշակ նույնացուցիչները, սեփականատիրոջ հեշերը, սահմանազատման գաղտնիքները և ներքին երթուղավորման տվյալները բացառվում են։

Սխալ բանալիով, սխալ սեփականատիրոջով, հնացած սերնդով, բացակայող, ժամկետանց, ազատված և անվավեր ճանաչված հարցումներն առանց կապի մետատվյալների վերադարձնում են նույն `409 LEASE_FENCE_STALE` սխալը։ Տարողության սպասման պատասխան ստացած հաճախորդը չունի ստուգման ենթակա ակտիվ կապակցում։ Երբ երթուղավորումը տեղափոխում է ակտիվ վարձակալությունը, նույն սերունդը մնում է վավեր, իսկ կարգավիճակը ատոմային եղանակով վերադարձնում է նոր կապակցումը, ոչ երբեք՝ հինը։ Գոյություն ունեցող հաճախորդները մնում են անփոփոխ, քանի որ ձեռքբերման, երկարաձգման, ազատման և սպասման պատասխանները պահպանում են իրենց նախկին կառուցվածքները։

Սերվերի այս պայմանագիրը չի փոխում ստանդարտ OpenAI Codex `/status`-ը։ Ստանդարտ Codex-ը ներկայում հաղորդում է իր մոդելի մատակարարը և ներկառուցված նույնականացման/հաշվի վիճակը, սակայն չի ցուցադրում կամայական հատուկ մատակարարի հաշվի մետատվյալները․ հաճախորդի հետագա ինտեգրումը պետք է կանչի այս գործողությունը և որոշի, թե ինչպես ցուցադրել `connection.displayName`-ը։

Այնուհետև յուրաքանչյուր կառավարվող ինֆերենսի հարցում փոխանցում է կառավարման երկու վերնագրերն էլ․

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Ճշգրիտ սեփականատերը, սերունդը, ակտիվ կապը և նույնականացված API բանալին սահմանազատվում են յուրաքանչյուր աջակցվող արտաքին ծառայության փորձից անմիջապես առաջ։ Այլ բանալիով սեփականատիրոջ և սերնդի կրկնակի օգտագործումը ձախողվում է նույնիսկ այն դեպքում, երբ այդ բանալին թույլատրում է նույն կապը։ Սեփականատերերի անմշակ արժեքները չեն պահպանվում, չեն գրանցվում մատյաններում, չեն պահվում հարցման պատկերի մեջ և չեն փոխանցվում արտաքին ծառայությանը։

Ժամանակավոր մրցակցությունը վերադարձնում է HTTP `429`՝ `Retry-After`-ի և հետևյալի հետ․

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Այս պատասխանը միայն նշանակում է, որ սովորական համապատասխան կապերի բազմությունը դատարկ չէր, և յուրաքանչյուր ազատ թեկնածու զբաղեցված էր այլ սեփականատիրոջ ակտիվ վարձակալությամբ։ Չաջակցվող մոդելները/մատակարարները, քաղաքականության անհամապատասխանությունը, դադարի ժամանակահատվածը, քվոտան, առողջական վիճակը և սովորական համապատասխանության այլ ձախողումները պահպանում են OmniRoute-ի իրենց առկա պատասխանները։

### `x-omniroute-compression`

Սեղմման պլանի՝ յուրաքանչյուր հարցման համար նախատեսված վերասահմանում։ Ունի ամենաբարձր առաջնահերթությունը՝ գերակայում է երթուղավորման կոմբինացիայի վերասահմանմանը, ակտիվ պրոֆիլին, ավտոմատ գործարկիչին և վահանակի լռելյայն կարգավորմանը։ Արժեքները՝

| Արժեք         | Ազդեցություն                                                                                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | Այս հարցման համար սեղմում չի կիրառվում։                                                                           |
| `default`     | Վահանակից ստացված լռելյայն պրոֆիլը (ակտիվ պրոֆիլն անտեսվում է)։ Կորուստներով շարժիչները մնում են անջատված։        |
| `safe`        | Միայն կրկնօրինակների հեռացում և բացատների միավորում։                                                              |
| `allow-lossy` | Այս հարցման համար պահպանվում է օպերատորի պլանը՝ ներառյալ ամփոփումները և ոճի վերաշարադրումները։                    |
| `engine:<id>` | Միացված լինելու դեպքում՝ մեկ շարժիչ, օրինակ՝ `engine:rtk`։ Այդ շարժիչի՝ յուրաքանչյուր հարցման համար ակտիվացում։   |
| `<combo>`     | Անվանակոչված կոմբինացիա, որը նախ համընկեցվում է անվամբ (առանց մեծատառ/փոքրատառ տարբերակման), ապա՝ նույնացուցիչով։ |

Նշումներ․

- Անհայտ արժեքներն անտեսվում են (հարցումը երբեք չի մերժվում)․ որոշման ընթացքն անցնում է օպերատորի առաջնահերթության սովորական կարգին։
- Եթե մի քանի կոմբինացիաներ ունեն նույն անունը, միարժեք համընկնման համար փոխանցեք կոմբինացիայի **նույնացուցիչը**։
- Այն կոմբինացիան, որի անունը `off` կամ `default` է, չի կարող ընտրվել անվամբ (այդ հիմնաբառերը մեկնաբանվում են առաջին հերթին)․ նման կոմբինացիային հղվեք դրա նույնացուցիչով։
- Սեղմման գլխավոր անջատիչը խիստ սահմանափակում է․ երբ սեղմումը գլոբալ անջատված է, այս վերնագիրը չի կարող այն միացնել։

Կիրառված պլանը կրկնվում է պատասխանի վերնագրում․

```
X-OmniRoute-Compression: <mode>; source=<source>
```

որտեղ `<source>`-ը `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` կամ `off` արժեքներից մեկն է։

## Ներդրումներ

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Հասանելի մատակարարներ՝ Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI։

Կատալոգի նույնացուցիչներն ունեն `provider/model` ձևաչափը (օրինակ՝ `jina-ai/jina-embeddings-v5-omni-small`)։ Ռեեստրում առկա Jina մոդելների կարճ նույնացուցիչները (օրինակ՝ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) նույնպես լուծվում են։ Jina-ի embed/rerank/classify/segment գործողությունները նախ օգտագործում են կառավարման վահանակի `jina-ai` հավատարմագրերը․ `JINA_AI_API_KEY`-ը պահուստային տարբերակ է միայն այն դեպքում, երբ կառավարման վահանակի բանալի չկա։ `jina-reader` քարտը նախատեսված է միայն Reader / `r.jina.ai`-ի համար (`POST /v1/web/fetch`) և երբեք չի սպասարկում ներդրումներ կամ վերադասակարգում։

Ռեեստրի այն մոդելները, որոնք հայտարարում են բազմամոդալ աջակցության մասին, ընդունում են նաև մինչև 32 մատակարարից անկախ կառուցվածքային
տարր։ Մեդիա տարրերի տեսակներն են՝ `text`, `image`, `audio`, `video` և `document`։ Դրանց մեդիայի `source`-ը
կա՛մ `{"type":"url","url":"https://..."}` է, կա՛մ
`{"type":"base64","data":"...","media_type":"..."}`։

Jina v5 Omni-ն (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
և ընտանեկան կեղծանունը՝ `jina-ai/jina-embeddings-v5-omni` → omni-small) ընդունում է նաև Jina-ի բնիկ
EmbeddingsV5Request փաստաթղթերը և **անփոփոխ փոխանցում է դրանք** `https://api.jina.ai/v1/embeddings` հասցեին․

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Բնիկ `{ image | audio | video | pdf }` արժեքները կարող են լինել հանրային HTTPS URL, `data:` URI կամ անմշակ
base64։ OmniRoute-ը չի փոխակերպում այդ օբյեկտները տողերի և չի ներբեռնում բնիկ պատկերների URL-ները․ Jina-ն ինքն է առբերում
հանրային մեդիան։ Jina-ի լրացուցիչ դաշտերը (`task`, `normalized`, `truncate`, `embedding_type`) փոխանցվում են։
Միայն տեքստ աջակցող Jina SKU-ները շարունակում են մերժել ոչ տեքստային փաստաթղթերը։

Անվտանգության և փոխանցման սահմանափակումներ․

- Հեռակա մեդիայի URL-ները պետք է լինեն հանրային HTTPS հասցեներ։ Կանոնական `{type,source:url}` տարրերն առբերվում են
  սերվերի կողմից (վերահղումների վերավավերացում, ժամանակի սահմանափակում, չափի սահմանափակումներ, հանրային DNS, կապի ամրագրում) և
  ներկառուցվում են մինչև մատակարարին կանչելը։ Jina-ի բնիկ `{image:"https://..."}` տարրերը նույն հանրային HTTPS ստուգումից հետո փոխանցվում են անփոփոխ․
  Jina-ն առբերում է URL-ը։
- Ներկառուցված base64 մեդիայի ապակոդավորված չափը սահմանափակված է մինչև 8 MiB՝ յուրաքանչյուր տարրի համար, և մինչև 16 MiB՝ ամբողջ հարցման համար։

Մատակարարին համապատասխան փոխակերպում (կանոնական տարրերը երբեք անփոփոխ չեն փոխանցվում)․

- Jina-ի բազմամոդալ մոդելներ․ վերին մակարդակի յուրաքանչյուր տարր վերածվում է եղանակը նշող մեկ օբյեկտի
  (`text` / `image` / `audio` / `video` / `pdf`)՝ ներկառուցված մեդիայի համար օգտագործելով data URI-ներ․ վերին մակարդակի յուրաքանչյուր
  տարրին համապատասխանում է մեկ վեկտոր։
- Gemini Embedding 2 ընտանիք․ վերին մակարդակի մեկ զանգվածը վերածվում է մեկ բնիկ
  `models/{model}:embedContent` հարցման՝ `content.parts`-ով (`text` կամ `inline_data`)։
- llama.cpp (`llama-cpp/<model>`, տեղական սերվերի բեռնած ցանկացած մոդել)․ կանոնական `text` տարրերը
  վերածվում են սովորական տողերի, իսկ `image` / `audio` / `video` տարրերից յուրաքանչյուրը՝ մեկ
  `{"content": [part]}` օբյեկտի՝ օգտագործելով llama-server-ի զրույցի բովանդակության մասերը (`image_url`,
  `input_audio`՝ `wav` / `mp3` / `flac` ձևաչափով, `input_video`)՝ ներկառուցված տվյալներով․ վերին մակարդակի յուրաքանչյուր
  տարրին համապատասխանում է մեկ վեկտոր։ Սերվերը պետք է գործարկվի `--embedding --mmproj …` տարբերակներով․ առանց պրոյեկտորի այն
  ինքն է մերժում մեդիան։ `document`-ը չի աջակցվում։
- Առանց եղանակների հստակ մետատվյալների անհայտ/դինամիկ մոդելները մերժում են կառուցվածքային մուտքը՝ վերադարձնելով HTTP 400։

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Մոդելի և եղանակի չաջակցվող համակցությունները տարրի հարկադիր փոխակերպման փոխարեն վերադարձնում են HTTP 400։ Մուտքին չվերաբերող
ընդլայնման դաշտերը հին տողային/թոքենային հարցումներում շարունակում են փոխանցվել անփոփոխ։

```bash
# Ցուցադրել ներդրման բոլոր մոդելները
GET /v1/embeddings
```

## Պատկերի գեներացում

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Հասանելի պրովայդերների թվում են OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (տեղային), ComfyUI (տեղային)։

`n`-ը վերադարձնում է `n` պատկեր `data[]`-ում։ Այն պրովայդերների համար, որոնց վերին մակարդակի API-ն յուրաքանչյուր կանչի դեպքում վերադարձնում է մեկ պատկեր
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), կատարվում է `n` առանձին վերին մակարդակի կանչ՝ միաժամանակ ընթացքի մեջ ունենալով առավելագույնը 4-ը։ Հաստատուն
`seed`-ը շեղվում է ըստ կանչի ինդեքսի (`seed`, `seed + 1`, …), ուստի պատկերները տարբերվում են, բայց մնում են
վերարտադրելի։ `n`-ի առավելագույն արժեքը 10 է։ Եթե որևէ կանչ ձախողվում է, հարցումն ամբողջությամբ ձախողվում է։ Զուգահեռացման
ձևաչափերի ցանկը `SINGLE_IMAGE_FANOUT_FORMATS`-ն է՝
`open-sse/handlers/imageGeneration/fanOut.ts` ֆայլում։

ZenMux-ը վերօգտագործում է API բանալիով առկա կապը և ընդունում է `zenmux/` կամ `zm/` նախածանցներ․

- `zenmux/openai/gpt-image-2`-ն օգտագործում է ZenMux-ի OpenAI Images API-ն։ Ընտրանքները ներառում են `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` և `response_format`։
- Այլ հրատարակիչներ, օրինակ՝ `zm/meta/muse-image-1.0`, օգտագործում են ZenMux-ի Vertex AI `:predict`
  վերջնակետը։ `n`-ը համապատասխանեցվում է `sampleCount`-ին, `aspect_ratio`-ն՝ `aspectRatio`-ին, իսկ `image_size`-ը
  (`1K`, `2K`, `4K`)՝ `sampleImageSize`-ին։ Պիքսելներով տրված `size`-ը սահմանում է միայն կողմերի հարաբերակցությունը,
  այլ ոչ թե երաշխավորված պիքսելային չափերը։ Աջակցվող հարաբերակցությունները, լուծաչափերը և քանակները տարբերվում են ըստ մոդելի։
- `zm/inclusionai/ming-image-0.1-design`-ն ինքն է ընտրում իր չափերը։ Բաց թողեք `size`,
  `aspect_ratio` և `image_size` դաշտերը․ հստակ նշված արժեքները վերադարձնում են HTTP 400։ PNG, JPEG և WebP
  ձևաչափերը կարելի է պահանջել `output_format`-ի միջոցով։

Այս ինտեգրումն աջակցում է տեքստից պատկերի գեներացմանը, այլ ոչ թե հղումային պատկերի խմբագրմանը։ Vertex-ի
ելքը նորմալացվում է որպես `data[].b64_json`, իսկ `response_format: "url"`-ը վերադարձնում է վերին մակարդակի
HTTPS URL կամ base64 տվյալների URL, երբ հասանելի են միայն պատկերի բայթերը։ Դատարկ/զտված ելքերի դեպքում
դատարկ հաջող պատասխանի փոխարեն վերադարձվում է սխալ։ Մոդելների հասանելիությունը կախված է ZenMux հաշվից։
Տե՛ս [ZenMux-ի Vertex API-ն](https://docs.zenmux.ai/api/vertexai/generate-images) և
[OpenAI Images API-ն](https://docs.zenmux.ai/api/openai/generate-an-image)։

```bash
# Ցուցադրել պատկերների բոլոր մոդելները
GET /v1/images/generations
```

## Փաստաթղթերի OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`-ն ընտրում է OCR պրովայդերը `provider/model` նախածանցի միջոցով․ առանց նախածանցի մոդելի նույնացուցիչը (օրինակ՝
`mistral-ocr-latest`) համապատասխանեցվում է իր գրանցված պրովայդերին, իսկ բաց թողնված `model`-ի համար լռելյայն
օգտագործվում է Mistral-ը (`mistral-ocr-latest`)։ Գրանցված պրովայդերները (`open-sse/config/ocrRegistry.ts`)․

| Պրովայդերի նույնացուցիչ       | Մոդելի նույնացուցիչ  | `model`-ի արժեքը                                                         | Նշումներ                                                                                                                                 |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (կամ առանց նախածանցի՝ `mistral-ocr-latest`) | Սինխրոն է․ պատասխանը վերադարձվում է անմիջապես վերին մակարդակի մեկ կանչից։                                                                |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                              | Վերին մակարդակում ասինխրոն է (`analyze` + հարցումներով ստուգում)․ տե՛ս ստորև։                                                            |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                  | Սինխրոն է և օգտագործում է Vertex AI-ի `openapi/chat/completions` գործընկերային վերջնակետը․ նույնականացման/URL-ի մանրամասները տե՛ս ստորև։ |

Բոլոր երեք պրովայդերները պատասխանում են Mistral-ի ձևաչափին համապատասխան նույն մարմնով․

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence-ի հարցումներով ստուգման հոսքը

Azure Document Intelligence-ի `analyze` API-ն ասինխրոն է․ սկզբնական հարցումը մարմնի փոխարեն վերադարձնում է
`Operation-Location` վերնագիր, և արդյունքը պետք է պարբերաբար հարցումներով ստուգվի։ Մշակիչը
(`open-sse/handlers/ocr.ts`) այդ URL-ը ստուգում է յուրաքանչյուր վայրկյանը մեկ՝ առավելագույնը 30 փորձի ընթացքում, անմիջապես ձախողվում է (չի
շարունակում հարցումներով ստուգումը), եթե ստուգման պատասխանը `ok` չէ կամ կարգավիճակը `"failed"` է, և վերադարձնում է `504`, եթե
գործողությունը փորձերի սահմանը սպառելուց հետո դեռ ընթացքի մեջ է։ Azure-ի վերջնական պատասխանը, նախքան կանչողին
վերադարձվելը, նորմալացվում է Mistral-ի կողմից օգտագործվող նույն `pages`/`markdown` ձևաչափին, ուստի հաճախորդի կոդում
պրովայդերի համար հատուկ մշակում անհրաժեշտ չէ։

### Vertex AI DeepSeek OCR-ի նույնականացումը և վերջնակետի որոշումը

`vertex-deepseek-ocr`-ը վերօգտագործում է Vertex AI-ի նույնականացման նույն մեխանիզմը, որն OmniRoute-ն արդեն աջակցում է
չաթի/պատկերների տրաֆիկի համար (`open-sse/executors/vertex.ts`)․ կապի API բանալին կամ
Service Account JSON հավատարմագիր է (որը JWT bearer
հոսքի միջոցով փոխանակվում է կարճաժամկետ OAuth հասանելիության թոքենի հետ), կամ արդեն ստեղծված OAuth հասանելիության թոքեն, որն օգտագործվում է անփոփոխ։ Վերին մակարդակի վերջնակետի URL-ը Vertex-ի
ընդհանուր `openapi/chat/completions` գործընկերային վերջնակետն է, որը կազմվում է կապի նախագծից և
տարածաշրջանից․ հստակ նշված `providerSpecificData.project`/`providerSpecificData.region` արժեքները միշտ առաջնահերթ են,
հակառակ դեպքում նախագիծը ստացվում է Service Account JSON-ի `project_id`-ից, իսկ տարածաշրջանի լռելյայն արժեքն է
`us-central1`։ Երկու արժեքներն էլ որոշվում են `open-sse/handlers/ocr.ts`-ում
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) և օգտագործվում
`src/app/api/v1/ocr/route.ts`-ում՝ նախքան հարցումը `handleOcr`-ին փոխանցելը։

### Մոդելների գները (`pricing`)

Գրառումը պարունակում է `pricing` օբյեկտ, երբ OmniRoute-ին հայտնի է մոդելի գինը։ Գինը վերցվում է
ծախսերի հաշվառման համար օգտագործվող գնային աղյուսակից՝ ներկառուցված լռելյայն արժեքներից, համաժամեցված գներից և
`/api/pricing`-ի միջոցով սահմանված վերասահմանումներից։ Սրանք հրապարակային գներ են, ուստի բաժանորդագրային մատակարարները նույնպես
ցուցադրում են մեկ տոկենի գինը։

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Դաշտեր                                                          | Միավոր                                      | Նշումներ                                                                                                                                                                          |
| --------------------------------------------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | ԱՄՆ դոլար մեկ տոկենի համար, տասնորդական տող | Համատեղելի է OpenRouter-ի հետ, երբեք չի օգտագործվում էքսպոնենցիալ գրառում։ Քեշի երկու դաշտերը հայտնվում են միայն այն դեպքում, երբ առկա է քեշի գին։                                |
| `input`, `output`, `cached`, `cache_creation`                   | ԱՄՆ դոլար 1 մլն տոկենի համար, թիվ           | Նախորդ կատալոգի տարբերակների դաշտեր, որոնք պահպանվել են առկա հաճախորդների համար։ `reasoning` և `long_context` դաշտերը նույնպես հայտնվում են, երբ գնային տողը պարունակում է դրանք։ |

- **Կոմբինացիաները** կրում են իրենց առաջին տեսանելի թիրախի գինը։ Ներկառուցված `auto/*` կոմբինացիաները
  հարցման պահին ընտրում են թիրախ, ուստի չունեն `pricing`։
- **Անվճար մոդելները** ցուցադրում են `"0"` (և `0`), երբ դրանց գինը զրո է։ Գնային տող չունեցող մոդելը
  նույնպես ցուցադրում է `"0"`, երբ կատալոգն այն նշում է որպես անվճար (`free: true`), կամ երբ այն ներառված է ներկառուցված անվճար մոդելների
  կատալոգում։
- **Անհայտ գին․** գրառումը չունի `pricing` բանալի։
- **Կրեդիտներով հաշվառվող մատակարարները** (օրինակ՝ Kiro-ն) գանձում են ըստ հարցման, այլ ոչ թե ըստ տոկենի։ Նրանց
  գրառումները պահպանում են նախկինում ունեցած՝ մեկ միլիոնի համար թվային դաշտերը և չեն պարունակում մեկ տոկենի համար նախատեսված տողային դաշտեր։
- **Տարբերակները** (reasoning-effort նույնացուցիչներ, no-thinking կեղծանուններ, հայտնաբերման և gateway հայելիներ)
  պատճենում են այն մոդելի գինը, որին ուղղորդում են։
- Դաշտերը պարունակում են միայն բազային սակագները։ Երկար համատեքստի մակարդակները (թվային `long_context` դաշտը) և
  ծառայության մակարդակի բազմապատկիչները (օրինակ՝ Codex fast կամ flex) չեն փոխում `prompt`-ը կամ
  `completion`-ը։
- Օբյեկտը նույնն է նույնականացման բոլոր եղանակների համար, այդ թվում՝ Anthropic ոճի
  հարցման դեպքում՝ `x-api-key`-ով և `anthropic-version`-ով (պատասխանը մնում է `{ "object": "list",
"data": [...] }`)։ Իրականացում՝ `src/app/api/v1/models/catalogPricing.ts`։

### Մոդելի նույնացուցիչների նախածանցներ (`?prefix=`)

Մոդելների մեծ մասը ներկայացվում է **մատակարարի նախածանցով**։ Թե որ նախածանցը կստանաք, կառավարվում է
`MODELS_CATALOG_PREFIX_MODE` հնարավորության դրոշակով և կարող է վերասահմանվել **յուրաքանչյուր հարցման համար**
հարցման պարամետրով․ սա օգտակար է այն հաճախորդի համար, որը ցանկանում է մաքուր ցանկ՝ առանց բոլորի համար սերվերի ընդհանուր
կարգավորումը փոխելու։

```bash
GET /v1/models?prefix=alias        # մեկ նույնացուցիչ յուրաքանչյուր մոդելի համար՝ կարճ կեղծանվան նախածանցը
GET /v1/models?prefix=dual         # երկու ձևերն էլ (սերվերի լռելյայն տարբերակը)
GET /v1/models?prefix=canonical    # միայն մատակարարի ամբողջական նույնացուցիչի նախածանցը
```

| Ռեժիմ       | Արտածում է                                              | Նշումներ                                                                                                                                                                                                                                          |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **և** `claude/claude-sonnet-4-6` | **Լռելյայն։** Երկու նույնացուցիչներն էլ ուղղորդվում են նույն մոդելին․ պահպանվել են, որպեսզի դրանցից որևէ մեկը կոշտ կոդավորած հաճախորդի կազմաձևումները շարունակեն աշխատել։ Մոտավորապես կրկնապատկում է կատալոգը։                                    |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Մեկ գրառում յուրաքանչյուր մոդելի համար։ Առանձին կեղծանուն չունեցող մատակարարները շարունակում են արտածել իրենց գրառումը, ուստի ոչինչ չի կորչում։                                                                                                   |
| `canonical` | `claude/claude-sonnet-4-6`                              | Մեկ գրառում յուրաքանչյուր մոդելի համար՝ մատակարարի ամբողջական նույնացուցիչի նախածանցով։ Առանձին կեղծանուն չունեցող մատակարարները (օրինակ՝ `antigravity/…`, `agy/…`) այստեղ նույնպես արտածում են իրենց միակ նույնացուցիչը, ուստի ոչինչ չի կորչում։ |

`dual` ռեժիմի հայելին կարելի է ճանաչել նաև առանց հարցման պարամետրի․ այն ունի հիմնական նույնացուցիչը մատնանշող `parent`
դաշտ։

Մոդելի ընտրիչ ցուցադրող հաճախորդները պետք է հարցում կատարեն `?prefix=alias`-ով․ հենց սա է անում
[OmniCopilot VS Code ընդլայնումը](../guides/VSCODE-COPILOT.md)։

### Հայտնաբերման զտիչներ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models`-ն ընդունում է ըստ ցանկության միացվող հայտնաբերման զտիչներ։ Առանց դրանցից որևէ մեկի պատասխանը
չի փոխվում։ Դրանք նեղացնում են այն կատալոգը, որն արդեն տեսնում է կանչողը (API բանալու թույլտվությունները կիրառվում են առաջինը),
և գործարկվում են OpenAI ոճի `limit` / `after` էջավորման նախքան։

```bash
GET /v1/models?capability=vision&capability=tool_calling   # թվարկված յուրաքանչյուր հնարավորություն պետք է ճշմարիտ լինի
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # կատալոգի `type`-ը․ այն չունեցող տողերը համարվում են `chat`
GET /v1/models?q=sonnet&limit=10                           # ռեգիստրից անկախ համընկնում նույնացուցիչի կամ անվան հետ
```

| Պարամետր      | Արժեքներ                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ոչ բացասական ամբողջ թիվ, որը համեմատվում է `context_length`-ի հետ                                   |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 նիշ                                                                                           |

Անհայտ արժեքը կամ ոչ բացասական ամբողջ թիվ չհանդիսացող `min_context`-ը (օրինակ՝ `1.5`)
վերադարձնում է HTTP `400`, իսկ հաղորդագրությունը թվարկում է վավեր արժեքները։ Իրականացումը՝
`src/app/api/v1/models/catalogFilters.ts`։

### Մոդելների կարճ ցանկ (`POST /v1/models/query`)

`POST /v1/models/query`-ը նույն կատալոգից վերադարձնում է կարճ, որոշակի ցանկ՝ նույն
նույնականացմամբ և ըստ բանալու տեսանելիությամբ, ինչ `GET /v1/models`-ը։

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Յուրաքանչյուր դաշտ պարտադիր չէ։ `capabilities`-ը և `exclude`-ը ընդունում են զանգված կամ ստորակետերով բաժանված տող,
իսկ `max_output`-ը համեմատվում է `max_output_tokens`-ի հետ։ Արդյունքները դասավորվում են նախ ըստ `owned_by`-ի, ապա՝ `id`-ի։
`limit`-ի լռելյայն արժեքը `20` է, իսկ `100`-ից մեծ արժեքները սահմանափակվում են `100`-ով։ Անվավեր JSON-ը, անհայտ
դաշտը կամ անվավեր արժեքը վերադարձնում է HTTP `400`։

### Առանձին թաքցված զրույցի մոդելներ

Պրովայդերի էջում **Թաքնված** նշված մոդելը բացառվում է կատալոգից և բացահայտ
հարցման դեպքում մերժվում է HTTP `404` / `model_not_found`-ով։ Ստուգումն օգտագործում է որոշված
պրովայդերն ու մոդելը՝ ներառյալ պրովայդերի այլանունները, համատեղելի պրովայդերի հանգույցների նախածանցները և
կապի լռելյայն կարգավորումները։ Համակցությունը բաց է թողնում թաքնված թիրախները և կարող է օգտագործել տեսանելի հարակից տարբերակ․ եթե
կատարելի թիրախ չի մնում, այն վերադարձնում է նույն սխալի կոդը։ Թաքցված կարգավիճակի անջատումն ուժի մեջ է մտնում հաջորդ
հարցման ժամանակ։ Միայն պատկերների տեսանելիության վերասահմանումները չեն թաքցնում նույն ID-ն ունեցող զրույցի մոդելը։

Մոդելի այս անհատական կարգավորումն առանձին է
[մոդելների հասանելիության թույլատրման/արգելման ցանկերից](../routing/MODEL_EXPOSURE_LIST.md), որոնք զտում են կատալոգում
ցուցադրումն ու ավտոմատ երթուղավորման թեկնածուները՝ պահպանելով բացահայտ ուղղորդումը։ API բանալու՝ մոդելների
թույլտվությունները շարունակում են կիրառվել անկախորեն։ Կատալոգի նախածանցի լռելյայն ռեժիմը մնում է `dual`։

### Առանց մտածողության մոդելային տարբերակներ

Մտածողություն աջակցող Claude մոդելների համար `/v1/models`-ը նաև ներկայացնում է **առանց մտածողության** տարբերակ, որի ID-ի նախածանցն է `claude-3-omniroute-no-thinking/`։

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Այս ID-ն ընտրելիս (օրինակ՝ Claude Code-ի կարգավորումներում, որոնք միշտ կցում են `thinking` բլոկ) այն կրկին որոշվում է որպես իրական `<provider>/<model>`՝ տրամաբանական հիմնավորման ճնշմամբ՝ `thinking:{type:"disabled"}`՝ `/v1/messages` ուղու դեպքում, կամ `reasoning`/`reasoning_effort` դաշտերի հեռացմամբ՝ `/v1/chat/completions` ուղու դեպքում։ Տարբերակը ցուցակագրվում է միայն Claude ընտանիքի այն մոդելների համար, որոնք աջակցում են մտածողությանը **և** հաշվի են առնում `disabled`-ը (այսպիսով, օրինակ, բացառվում են միայն հարմարվողական ռեժիմ աջակցող այն մոդելները, որոնք մերժում են `disabled`-ը)։ Օպերատորները կարող են յուրաքանչյուր մոդելի համար հարկադրաբար միացնել կամ անջատել այս տարբերակը՝ `ModelSpec.noThinkingAlias`-ի միջոցով։

## ElevenLabs աուդիոյի ստեղծում

OmniRoute-ում կազմաձևեք `elevenlabs` մատակարարի կապը՝ օգտագործելով ձեր ElevenLabs API բանալին։
Հաճախորդները նույնականացվում են իրենց **OmniRoute** բանալիով (`Authorization: Bearer $OMNIROUTE_API_KEY`),
իսկ դարպասը պահպանված մատակարարի բանալին փոխանցում է որպես `xi-api-key`։ Երբեք ElevenLabs-ի բանալին
մի ուղարկեք որպես դարպասի bearer թոքեն։

| Մեթոդ | Ուղի                        | Պատասխան                                     | API բանալու վերջնակետի կատեգորիա |
| ----- | --------------------------- | -------------------------------------------- | -------------------------------- |
| POST  | `/v1/sound-generation`      | Բնօրինակ աուդիո բայթեր                       | `elevenlabs`                     |
| POST  | `/v1/music`                 | Բնօրինակ աուդիո բայթեր                       | `music`                          |
| POST  | `/v1/music/stream`          | Հոսքային աուդիո բայթեր                       | `music`                          |
| POST  | `/v1/music/detailed`        | Բնօրինակ բազմամաս աուդիո և կոմպոզիցիայի պլան | `music`                          |
| POST  | `/v1/music/detailed/stream` | Բնօրինակ SSE մետատվյալներ և աուդիո հատվածներ | `music`                          |
| POST  | `/v1/music/plan`            | JSON կոմպոզիցիայի պլան                       | `music`                          |

Այս վերջնակետերը լրացնում են առկա `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` և `/v1/speech-to-text` երթուղիները։ Բնօրինակ JSON դաշտերն
ու հարցման պարամետրերը, ինչպիսիք են `output_format` և `enable_logging`, պահպանվում են։
`/v1/music/detailed` պատասխանները պահպանում են իրենց բազմամաս սահմանազատիչները․ վերլուծեք դրանք որպես multipart։
`/v1/music/detailed/stream`-ը վերադարձնում է `text/event-stream`՝ կոմպոզիցիայի մետատվյալներով և
base64 աուդիո հատվածներով SSE իրադարձություններում։ Բոլոր վեց երթուղիներն աջակցում են CORS-ի նախնական հարցումներին։

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Կարճ ձայնային էֆեկտ։ Տևողությունը՝ 0.5-ից 30 վայրկյան։
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Երաժշտության տևողությունն արտահայտվում է միլիվայրկյաններով՝ 3000-ից 600000։
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Աուդիոյի աստիճանական փոխանցման համար նույն JSON մարմնի հետ օգտագործեք `/v1/music/stream`։ Կոմպոզիցիան
ընդունում է `prompt`-ից կամ `composition_plan`-ից միայն մեկը․ `/v1/music/plan`-ը պահանջում է `prompt`
և ըստ ցանկության ընդունում է `source_composition_plan`։ Բնօրինակ սխեմաները պահպանում են մատակարարի լրացուցիչ
դաշտերը, որպեսզի կոմպոզիցիայի պլանի տարբերակները և ճշգրտման ընտրանքները հասնեն ElevenLabs-ին։

Միասնական `/v1/music/generations` վերջնակետը նույնպես ընդունում է `elevenlabs/music_v1`,
`elevenlabs/music_v2` և `elevenlabs/music_v2_5`։ ElevenLabs-ի ակտիվ կապի դեպքում
այս մոդելները հասանելի են երաժշտության կատալոգում։ Այս վերջնակետը վերադարձնում է
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`։ Դրա `duration` դաշտը չափվում է
վայրկյաններով և համապատասխանեցվում է `music_length_ms`-ին․ բացահայտ նշված `music_length_ms`-ն ունի առաջնահերթություն։
`instrumental`-ը համապատասխանեցվում է `force_instrumental`-ին, ընդ որում բնօրինակ դաշտն ունի առաջնահերթություն։
Հոսքային փոխանցման համար օգտագործեք բնօրինակ հոսքային վերջնակետերը, իսկ միայն կոմպոզիցիայի պլանով պայմանավորված
հարցումների համար՝ բնօրինակ կոմպոզիցիայի վերջնակետը։

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Վերջնակետի, մոդելի, բյուջեի և կապի սահմանափակումները կիրառվում են մինչև վերին հոսքի կանչը։ Բնօրինակ
երթուղիները վերադարձնում են վերին հոսքի կարգավիճակի կոդերը և սխալի մարմիններն անփոփոխ, ներառյալ `402`-ը՝ պլանի
սահմանափակման համար, և `429`-ը՝ քվոտայի սահմանաչափի համար։ Առկայության դեպքում `character-cost`, `song-id`, `request-id` և `retry-after`
վերնագրերը պահպանվում են։ Անվճար վարկային մնացորդը չի երաշխավորում հասանելիություն յուրաքանչյուր
երաժշտական մոդելին, ելքային ձևաչափին կամ API գործառույթին․ ElevenLabs-ը որոշում է յուրաքանչյուր հարցման հասանելիության իրավունքը։
Միասնական վերջնակետը պահպանում է սխալի կարգավիճակի կոդերը OmniRoute-ի նորմալացված սխալի ծրարում։

Վերին հոսքի պայմանագրեր՝ [ձայնային էֆեկտներ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[երաժշտական կոմպոզիցիա](https://elevenlabs.io/docs/api-reference/music/compose) և
[հոսքային երաժշտության մանրամասներ](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)։

Այն հաճախորդների համար, որոնք չեն կարող կցել `Authorization: Bearer ...`, OmniRoute-ը նաև ընդունում է URL-ում փոխանցված API բանալիներ՝ կամ հարցման տողի հետ համատեղելիության միջոցով (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`), կամ ստորև փաստաթղթավորված հատուկ `/api/v1/vscode/{token}/...` վերջնակետերի միջոցով։

```bash
# Վերադասակարգում (ամպային գրանցամատյանի մատակարար կամ OpenAI-ի հետ համատեղելի մատակարարի հանգույց՝ որպես "<prefix>/<model>")
```

> **Վերադասակարգման պրովայդերային հանգույցներ․** `POST /v1/rerank`-ը հարցումները նաև ուղղորդում է OpenAI-ի հետ համատեղելի պրովայդերային հանգույցներ
> (oMLX, vLLM, Infinity, դարպասի հետևում գտնվող TEI և այլն), որոնց հասցեագրումն ունի `<node-prefix>/<model>` ձևաչափը։ Հետադարձ կապի
> հանգույցները (`localhost`, `127.0.0.1`, `172.16.0.0/12`) միշտ թույլատրելի են, ինչպես նաև այն հոսթանունները, որոնք
> օպերատորը նշում է `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`-ում (օրինակ՝ Docker/Compose ծառայության անունը, ինչպիսին է
> `http://reranker:8080/v1`; դրանց կանչերն իրականացվում են անմիջապես՝ երբեք չօգտագործելով `HTTP(S)_PROXY`-ն կամ
> կապին ամրակցված պրոքսին)։ Ցանկացած այլ
> հոսթի հանգույցները՝ LAN համակարգիչ կամ Tailscale գործընկեր, թույլատրելի են միայն այն դեպքում, երբ օպերատորը միացնում է
> `RERANK_REMOTE_PROVIDER_NODES` հնարավորության դրոշակը, **և** հանգույցի բազային URL-ն անցնում է պրովայդերի
> ելքային URL-ների քաղաքականության ստուգումը (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)։
> Հիշողության շարժիչի վերադասակարգման քայլն այս երթուղին կանչում է
> հետադարձ կապով, ուստի նույն կանոնը կիրառվում է Հիշողության կարգավորումներում գտնվող `rerankProviderModel`-ի նկատմամբ։
>
> **Տեղային սերվերի ձևաչափեր․** հանգույցը կանչվում է `<base>/v1/rerank` հասցեով, իսկ 404-ի դեպքում՝ `<base>/rerank`
> հասցեով (Infinity, TEI)։ Վերին մակարդակ ուղարկվող մարմինը պարունակում է ինչպես Cohere/OpenAI-ի անվանումները (`documents`,
> `return_documents`), այնպես էլ TEI-ի անվանումները (`texts`, `return_text`), իսկ վերին մակարդակից ստացված պատասխանը
> նորմալացվում է Cohere-ի պատյանի ձևաչափին․ TEI-ի պարզ `[{index, score, text}]`-ը, թեթև դարպասներից ստացվող `{results: [{index, score}]}`
> ձևաչափը և Voyage-ի ոճով `{data: [...]}` ձևաչափը հաճախորդին վերադարձվում են
> `{results: [{index, relevance_score, document?}]}` ձևաչափով՝ դասավորված ըստ գնահատականի և սահմանափակված `top_n`-ով։

> **Պրովայդերային հանգույցների հայտնաբերում․** OpenAI-ի հետ համատեղելի պրովայդերային հանգույցի մոդելները `GET /v1/models`-ում հայտնվում են
> հանգույցի նախածանցի ներքո։ Վերջնակետի մետատվյալներ չպարունակող տողերը (սովորաբար տեղային `/v1/models` ցանկերում)
> ժառանգում են հանգույցի `apiType`-ը, ուստի `embeddings` հանգույցի մոդելներն ունեն `type: "embedding"`, իսկ
> `rerank` հանգույցի մոդելները՝ `type: "rerank"`՝ լռելյայն չդառնալով չաթի մոդելներ․ համաժամացված կամ ձեռքով ավելացված տողի վրա բացահայտորեն նշված
> `supportedEndpoints`-ը շարունակում է առաջնահերթություն ունենալ։

## Ֆայլերի API

OpenAI-ի հետ համատեղելի ֆայլերի վերջնակետ՝ փաթեթային մուտքային/ելքային տվյալների և ըստ նշանակության ֆայլերի վերբեռնման համար։

| Մեթոդ  | Ուղի                     | Նկարագրություն                                                                                                          |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | Վերբեռնել ֆայլ (բազմամաս՝ `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — առավելագույնը 512 MiB |
| GET    | `/v1/files`              | Ցուցակել նույնականացված API բանալիին պատկանող ֆայլերը                                                                   |
| GET    | `/v1/files/[id]`         | Ստանալ ֆայլի մետատվյալները                                                                                              |
| DELETE | `/v1/files/[id]`         | Ջնջել ֆայլը                                                                                                             |
| GET    | `/v1/files/[id]/content` | Հոսքային եղանակով վերադարձնել ֆայլի չմշակված բովանդակությունը                                                           |

**Նույնականացում՝** Bearer API բանալի — ֆայլերի հասանելիությունը սահմանափակվում է ըստ API բանալու՝ `getApiKeyRequestScope`-ի միջոցով։ Բանալին
տեսնում, ներբեռնում և ջնջում է միայն իրեն պատկանող ֆայլերը․ առանց բանալու կառավարման վահանակի աշխատաշրջանը կարդում է
ամբողջ օրինակը․ սեփականատեր չունեցող ֆայլը (անանուն կամ կառավարման վահանակի աշխատաշրջանից վերբեռնված) մերժվում է բոլոր
ոչ աշխատաշրջանային կանչողների համար։ `GET /v1/files`-ը անանուն կանչողին, ինչպես նաև ներկայացված, բայց
չճանաչված բանալիով կանչողին վերադարձնում է `401`, նույնիսկ երբ `REQUIRE_API_KEY=false`, այլ ոչ թե ցուցակելով բոլոր վարձակալների
ֆայլերը (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)։

## Փաթեթների API

OpenAI-ի հետ համատեղելի փաթեթային մշակում։

| Մեթոդ  | Ուղի                      | Նկարագրություն                                                                                                            |
| ------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | Ստեղծել փաթեթ — հարցման մարմինը վավերացվում է `v1BatchCreateSchema`-ով (`input_file_id`, `endpoint`, `completion_window`) |
| GET    | `/v1/batches`             | Ցուցակել փաթեթները                                                                                                        |
| GET    | `/v1/batches/[id]`        | Ստանալ փաթեթի կարգավիճակը և `request_counts`-ը                                                                            |
| DELETE | `/v1/batches/[id]`        | Ջնջել ավարտված/ձախողված փաթեթը                                                                                            |
| POST   | `/v1/batches/[id]/cancel` | Չեղարկել ընթացքի մեջ գտնվող փաթեթը                                                                                        |

**Նույնականացում՝** Bearer API բանալի։ Փաթեթների հասանելիությունը սահմանափակվում է ըստ API բանալու՝ նույն եռակողմ կանոնի համաձայն, ինչ
ֆայլերի դեպքում․ միայն սեփական բանալի, կառավարման վահանակի աշխատաշրջանի համար՝ ամբողջ օրինակը, իսկ սեփականատիրոջը չպատկանող գրառումները մերժվում են բոլոր
ոչ աշխատաշրջանային կանչողների համար (ստացում, ջնջում, չեղարկում և ստեղծման ժամանակ `input_file_id`-ի ստուգում)։
`GET /v1/batches`-ը անանուն կանչողին վերադարձնում է `401`, նույնիսկ երբ `REQUIRE_API_KEY=false`։

## Որոնել API

Web/search մատակարարի աբստրակցիա (Tavily, Brave, Exa, Serper և այլն):

| Մեթոդ | Ճանապարհ               | Նկարագրություն                                                                                        |
| ----- | ---------------------- | ----------------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | Ցուցակեք կազմաձևված որոնման մատակարարների + հնարավորությունները                                       |
| POST  | `/v1/search`           | Գործարկեք որոնման հարցում — մարմինը վավերացված `v1SearchSchema` կողմից, աջակցում է caching/coalescing |
| GET   | `/v1/search/analytics` | Յուրաքանչյուր մատակարարի hit/latency/cache վիճակագրություն                                            |

**Auth:** Կրող API բանալի (`extractApiKey` + `isValidApiKey`). Որոնման քաղաքականությունն իրականացվում է `enforceApiKeyPolicy` միջոցով:

### Exa եւ Tavily `provider_options`

Exa-ն և Tavily-ը կարդում են մատակարարի համար նախատեսված դաշտերը անունների տարածության պայուսակից՝ `provider_options.exa` (կամ `provider_options["exa-search"]`) և `provider_options.tavily` (կամ `provider_options["tavily-search"]`): Փոխանցվում են միայն ստորև նշված ստեղները: Յուրաքանչյուրը ստուգվում է `open-sse/handlers/search/providerOptionsPassthrough.ts` ում իր սեփական Zod սխեմայի համեմատ, և սխալ տիպով բանալին հանվում է: Ցանկացած այլ ստեղն անտեսվում է, ներառյալ auth, base URL, `stream` և `outputSchema`: Այլ պրովայդերների կողմից օգտագործվող հարթ ստեղները (`cx`, `depth`, ...) աշխատում են ինչպես նախկինում:

| Մատակարար | Բարձր մակարդակի դաշտեր                                                                                                                                                                                                                                                                                                                                                    | Բնադրված                                                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (հարթ պարզունակներ), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` միավորվել է լռելյայն `{ text: true, highlights: true }` վրա |
| Թավիլի    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                         |

Միշտ հաղթում են ընդհանուր դաշտերը՝ `query`, `max_results`, `filters` (տիրույթներ), `country` և `search_type` ից ստացված թեման։ Exa-ում `search_type: "news"` պահպանում է `category: "news"`: Թավիլը նույնպես ընդունում է `search_type: "finance"` (`topic: "finance"`)։

Firecrawl որոնման արժեքը գրանցվում է 10 վերադարձված արդյունքների մեկնարկած բլոկի համար՝ $0,002 (2 վարկ) մեկ բլոկ և առնվազն մեկ բլոկ մեկ զանգի համար ( [Firecrawl billing](https://docs.firecrawl.dev/billing) ). 11 արդյունքն արժե $0,004:

Ընդհանուր `time_range` այժմ հասնում է երկու մատակարարներին. Exa-ն ստանում է `startPublishedDate` (ISO ժամադրոշմ) և Tavily-ն ստանում է `start_date` (`YYYY-MM-DD`): `provider_options` ում հստակ ամսաթիվը գերակայում է քարտեզագրվածին:

Exa արդյունքները պահպանում են `id`, `highlight_scores`, `summary`, `subpages`, `entities` և `extras` `provider_raw` ում: Tavilly արդյունքները պահպանում են `images` և `favicon`:

Linkup որոնման արժեքը գրանցվում է $0,005 `depth` `fast` և `standard` համար և $0,05-ի համար `deep` համար ( [Linkup pricing](https://docs.linkup.so/pages/documentation/development/pricing) ), անկախ նրանից `depth` գալիս է `provider_options` ից կամ կապի կարգավորումներից:

Exa `type: "lite"` (Exa 3.0) ընդունում է դաշտերի ավելի փոքր շարք և մերժում է ամբողջ հարցումը, երբ որևէ այլ դաշտ է սահմանված: Lite-ի համար `additionalQueries`, `systemPrompt` և բոլոր `contents` ստեղները, բացի `text` և `highlights` հանվում են զանգից առաջ: Հնացած `subpages`, `subpageTarget`, `highlights.numSentences` և `highlights.highlightsPerUrl` այլևս չեն փոխանցվում:

Ծախսերի հաշվառումը `costPerQuery` հարթ ռեգիստրն `instant`, բացառությամբ Exa- `auto`, որը հետևում `fast` `lite` ի սեփական գներին. $0,001 յուրաքանչյուր հետագա արդյունքի համար; և $0,001 մեկ վերադարձված արդյունքի համար, երբ `contents.summary` սահմանվում է: Tavily-ն գրանցվում է 1 կրեդիտով ($0,008) `search_depth` `basic`, `fast` և `ultra-fast` համար, իսկ 2 վարկ (0,016$) `advanced` համար ( [Tavily API վարկեր](https://docs.tavily.com/documentation/api-credits) ): `auto_parameters: true` ով զանգը, որը Tavily-ն թարմացնում է առաջադեմի, դեռ գրանցվում է 1 կրեդիտով:

## Web Fetch API

Կարգավորված վեբ բովանդակության ստացման մատակարարի (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) միջոցով ստացեք բովանդակություն URL-ից։

Parallel Extract-ը (`parallel-search`, նույն API բանալին, ինչ Parallel Search-ի համար) վերադարձնում է միայն
Markdown. ցանկացած այլ `format` հանգեցնում է `400` պատասխանի, իսկ բովանդակության ծավալը սահմանափակվում է 100,000 նիշով։ Երբ
նպատակային էջը հնարավոր չէ ստանալ, վերին մակարդակի ծառայությունը դա հաղորդում է HTTP 200 պատասխանի մեջ.
OmniRoute-ը դա ներկայացնում է որպես `422`՝ ֆիքսված հաղորդագրությամբ։

| Մեթոդ | Ուղի            | Նկարագրություն                                                          |
| ----- | --------------- | ----------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Ստանալ/քերել URL-ը. հարցման մարմինը վավերացվում է `v1WebFetchSchema`-ով |

**Նույնականացում․** Bearer API բանալի (`extractApiKey` + `isValidApiKey`)։ Քաղաքականությունը կիրառվում է `enforceApiKeyPolicy`-ի միջոցով։

**Քվոտան հաշվի առնող պահուստային անցում (#8297)․** երբ հստակ `provider` նշված չէ, մատակարարների ցանկը
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) շրջանցվում է ֆիքսված
առաջնահերթության կարգով (նախ լրացվող). արագության սահմանափակման հասած, բայց կարգավորված մատակարարը բաց է թողնվում՝
հարցումը անմիջապես ավարտելու փոխարեն, իսկ վերին մակարդակի ծառայության կրկնելի/քվոտային խափանման դեպքում
(HTTP 429՝ միշտ, 402/403՝ Firecrawl/Tavily/TinyFish-ի քվոտայով սահմանափակված անվճար մակարդակների համար,
բայց ոչ Jina Reader-ի և երբեք ոչ սովորական 400 սխալ հարցման համար) հարցման կատարման պահին փորձ է արվում օգտագործել
հաջորդ՝ դեռ չփորձված և հավատարմագրեր ունեցող մատակարարին։ Երբ ցանկի բոլոր մատակարարների
հնարավորությունները սպառված են, վերջնակետը նախկին ընդհանուր `400`-ի փոխարեն վերադարձնում է մեկ `429`
պատասխան (`Retry-After` վերնագրով)։ Երբ հստակ `provider` է
պահանջվում, աննկատ պահուստային անցում **չկա**. արագության սահմանափակման հասած կամ խափանված հստակ նշված
մատակարարի սեփական սխալն է վերադարձվում (`429`, եթե արագությունը սահմանափակված է, հակառակ դեպքում՝ վերին մակարդակի ծառայության
կարգավիճակը)։

## WebSocket հոսքային փոխանցում

```bash
GET /v1/ws?handshake=1
```

Վավերացնում է WebSocket-ի արդիականացման հաստատման ընթացակարգը և վերադարձնում ցանցային արձանագրության հաղորդագրությունների օրինակները (`request`, `cancel`)։ Իրական WS կադրերը մշակվում են փաթեթում ներառված WS սերվերի կողմից՝ Next.js-ի երթուղիների աղյուսակից դուրս։

**Նույնականացում․** Bearer API բանալի՝ հաստատման ընթացակարգի ժամանակ։

### Responses API-ն WebSocket-ի միջոցով (միայն codex)

```bash
# Նույն հոսթը և պորտը, ինչ HTTP API-ի համար (լռելյայն՝ 20128). արդիականացրեք կապը.
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (կամ՝ -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Առաջին կադրը ՊԵՏՔ Է լինի response.create.
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket պրոքսին միացված է **բացառապես `codex`-ին** (ChatGPT
բեքենդ)։ Այն սպասարկում է API-ի/կառավարման վահանակի հետ նույն պորտում՝ `/v1/responses`,
`/responses` և `/api/v1/responses` ուղիներով։ Առաջին `response.create` կադրի դեպքում այն
նույնականացնում և նախապատրաստում է հարցումը ներքին `codex-responses-ws` կամրջի միջոցով, ընտրում է
codex OAuth կապ և `wreq-js` տրանսպորտի միջոցով թունելավորում դեպի `wss://chatgpt.com/backend-api/codex/responses`։
**Ոչ codex մոդելները մերժվում են** (`codex_ws_provider_required`)։
Քվոտայի բաժնեմասով երթուղավորման համար օգտագործեք `model: "qtSd/<group>/codex/<model>"`։ Իրականացված է
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ֆայլերում։

**Նույնականացում․** Bearer API բանալի՝ հաստատման ընթացակարգի ժամանակ։ Փաթեթում ներառված HTTP սերվերը (`server-ws.mjs`)
պետք է լինի ակտիվ մուտքի կետը (այն լռելյայն այդպիսին է, երբ առկա է `app/server-ws.mjs`)։

#### Մոդելի ID. օգտագործեք ChatGPT-ի պարզ ID-ն (առանց `codex/` նախածանցի)

OpenAI **Codex CLI**-ն մոդելի անունը վավերացնում է հաճախորդի կողմում, երբ
`supports_websockets = true`, և **մերժում է մատակարարի նախածանցով ID-ները**, օրինակ՝
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)։ Ուղարկեք **պարզ** ID-ն (օրինակ՝ `gpt-5.5`)։ OmniRoute-ի կամուրջն
աշխատում է միայն codex-ի հետ, ուստի վերին մակարդակ թունելավորելուց առաջ այն պարզ ID-ն կրկին
որոշում է որպես codex մոդել (`resolveCodexWsModelInfo`), թեև պարզ
`gpt-5.5`-ը HTTP-ի միջոցով հակառակ դեպքում կուղղորդվեր մեկ այլ մատակարարի։

#### OpenAI Codex CLI-ի կարգավորում

Codex CLI-ն ուղղեք դեպի OmniRoute՝ WebSocket-ի աջակցությամբ հատուկ մատակարար ավելացնելով
`~/.codex/config.toml`-ում (օգտագործեք առանձին `CODEX_HOME`, որպեսզի չփոփոխեք
առկա կարգավորումները)։

```toml
model = "gpt-5.5"                 # պարզ ID՝ ՈՉ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # առանց վերջնական շեղ գծի. WS URL-ը ձևավորվում է դրանից (արտադրական միջավայրում օգտագործեք https/wss)
wire_api = "responses"                    # միակ աջակցվող արժեքը 2026 թ. փետրվարից ի վեր
supports_websockets = true                # միացնում է Responses-over-WS տրանսպորտը
env_key = "OMNIROUTE_API_KEY"             # պարունակում է OmniRoute API բանալին (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API բանալի (ցանկացած բանալի, եթե REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI-ն `base_url + /responses` հասցեն արդիականացնում է WebSocket-ի, իսկ OmniRoute-ն այն
թունելավորում է դեպի ընտրված codex OAuth կապը։ Ամբողջական շղթայով վավերացվել է տեղային
սերվերի նկատմամբ. ChatGPT-ն վերադարձնում է `codex.rate_limits` + `response.created` և հոսքային եղանակով փոխանցում է
ամբողջացումը։

## Ինքնասպասարկման օգտագործում (`/api/usage/om-usage`)

Ցանկացած API բանալի կարող է դիտել **իր սեփական** օգտագործումն ու քվոտաները՝ առանց կառավարման նույնականացման։ Սա այն վերջնակետն է, որն
օգտագործում է հաճախորդը (CLI-ն, OmniCopilot վահանակը)՝ բանալու տիրոջ ծախսերը ցուցադրելու համար։

```bash
# Տեքստային ձևաչափ (պատմական պայմանագիրը՝ պարզ տեքստ տերմինալի համար)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Կառուցվածքային ձևաչափ՝ այն, ինչ օգտագործում է UI-ն
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Բանալու համար **`allowUsageCommand`**-ը պետք է միացված լինի (լռելյայն անջատված է․ կառավարման վահանակի API բանալիների
կառավարիչը դա փոխարկում է յուրաքանչյուր բանալու համար առանձին)։ Առանց դրա վերջնակետը պատասխանում է `403`։

`?format=json`-ը վերադարձնում է տարբերակիչ կառուցվածք, որպեսզի կանչողը մերժման պատասխանից երբեք չկարդա տվյալների դաշտ։ Հաջողության դեպքում՝

```jsonc
{
  "allowed": true,
  // առկա է միայն այն դեպքում, երբ բանալու համար միացված են առանձին օգտագործման սահմանաչափեր (օրական/շաբաթական՝ USD-ով).
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ընտրված մատակարարի քվոտայի ակնթարթային պատկերը կամ null, երբ դեռ ոչինչ քեշավորված չէ.
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // յուրաքանչյուր միացման ակնթարթային պատկերը, որպեսզի UI-ն կարողանա մի քանի մատակարարներ ցուցադրել կողք կողքի.
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Մերժման դեպքում (`401`՝ սխալ բանալի / `403`՝ թույլատրված չէ) նույն երթուղին վերադարձնում է
`{ "allowed": false, "error": { "message": "…" } }`․ առկա, բայց դատարկ `personal`/`provider`
(բանալին թույլատրված է, սակայն դեռ ոչինչ հայտնի չէ) դաշտերը մերժումից տարբերվող վիճակ են, և միայն JSON ձևաչափն է
տարբերակում դրանք։

**Նույնականացում՝** կանչողի սեփական Bearer API բանալին, որը վավերացվում է `isValidApiKey`-ով․ սա կառավարման
մակերեսը (`/api/keys/…`) _չէ_, որը շարունակում է պաշտպանված լինել `requireManagementAuth`-ով։

### Քվոտայի սկզբնական և սահմանաշեմով ճշգրտված տոկոսներ

`/api/usage/om-usage`-ն օգտագործելիս կանչողները պետք է հաշվի առնեն **պարզ տեքստային ելքում** և կառուցվածքային
**JSON ելքում** ներկայացված տոկոսների տարբերությունը․

| Բնութագիր                         | Պարզ տեքստային ձևաչափ (`/api/usage/om-usage` / `@@om-usage`)                                                     | JSON ձևաչափ (`?format=json`)                                                                                  |
| :-------------------------------- | :--------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| **Ելքային դաշտ**                  | `NN% left` (օրինակ՝ `20% left`)                                                                                  | `provider.quotas` / `providers[].quotas`                                                                      |
| **Չափում**                        | **Սահմանաշեմով ճշգրտված օգտագործելի թույլատրելի ծավալ**․ սահմանաշեմից բարձր մնացած հզորություն                   | **Սկզբնական վերին հոսքի քվոտա**․ մատակարարի չճշգրտված չափում                                                  |
| **Սահմանաշեմային մասշտաբավորում** | Մասշտաբավորվում է `effectiveRemainingPercent()`-ի միջոցով, որպեսզի պաշտպանված պահուստը ցուցադրվի որպես `0% left` | Չկա (սկզբնական ակնթարթային արժեքները՝ ինչպես հաղորդվել են մատակարարի կողմից)                                  |
| **Շեմի տվյալներ**                 | Ներառված են ցուցադրվող տոկոսի մեջ                                                                                | Պահվում են յուրաքանչյուր միացման `quotaWindowThresholds`-ում (կամ օգտագործվում են սերվերի լռելյայն արժեքները) |
| **Հիմնական սպառող**               | Ինտերակտիվ CLI-ներ, տերմինալի հուշումներ, մարդկային օպերատորներ                                                  | Ծրագրային ինտեգրումներ, կառավարման վահանակներ, վերլուծական համակարգեր, վճարումների հետագծիչներ                |

#### Սահմանաշեմային ճշգրտման բանաձևը

OmniRoute-ն աջակցում է քվոտայի կանխարգելիչ սահմանաշեմեր՝ վերին հոսքի ռեսուրսի սպառումը կանխելու համար (կարգավորվում են միացման
`quotaWindowThresholds`-ի, մատակարարի լռելյայն արժեքների կամ գլոբալ դիմակայունության կարգավորումների միջոցով)։ Երբ քվոտայի պատուհանի համար ակտիվ է սահմանաշեմ
(օրինակ՝ `cutoff = 25%`), տեքստի ձևավորիչը մնացած թույլատրելի ծավալը հաշվարկում է հետևյալ կերպ․

- Եթե `remaining <= cutoff`՝ վերադարձնում է `0%`։
- Եթե `remaining > cutoff`՝ վերադարձնում է `((remaining - cutoff) / (100 - cutoff)) * 100`։

Ձևաչափված տեքստային ելքը դա կլորացնում է մինչև մոտակա ամբողջ թիվը (`Math.round(...)`)։

#### Պատկերավոր օրինակ

Դիտարկենք մատակարարի պատուհան՝ **60% սկզբնական օգտագործմամբ** (հետևաբար՝ **40% սկզբնական մնացած քվոտայով**) և կազմաձևված
**մնացած քվոտայի 25% սահմանաշեմով**․

| Ներկայացում                         | Հաշվարկ                                            | Մնացած  |           Ենթադրվող օգտագործված մասը            |
| :---------------------------------- | :------------------------------------------------- | :-----: | :---------------------------------------------: |
| **Սկզբնական JSON (`?format=json`)** | Վերին հոսքի ակնթարթային պատկեր (`quotas[window]`)  | **40%** |                     **60%**                     |
| **Տեքստային ձևաչափ (`NN% left`)**   | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` հաշվարկելու դեպքում) |

- **Ինչու է տեքստը ցուցադրում 20% մնացորդ․** հաշվում մնացած 40% ֆիզիկական քվոտայից 25%-ը պահուստավորված է
  սահմանաշեմային քաղաքականությամբ։ Կանչողին հասանելի է օգտագործելի 75% միջակայքից միայն 15% ազատ պաշար, մինչև երթուղիչը դադարեցնի
  հարցումները դեպի այս միացում ուղղորդելը։ Մասշտաբավորումն ապահովում է, որ միացումը սպառման մասին ազդանշան տա (`0% left`) հենց այն պահին, երբ
  երթուղավորումը դադարի։
- **Ինչու է JSON-ը պահպանում սկզբնական արժեքները․** JSON օգտակար բեռը վերադարձնում է մատակարարի ճշգրիտ ակնթարթային պատկերը (`UsageSnapshot`),
  որպեսզի արտաքին գործիքներին հասանելի լինեն վերին հոսքի օգտագործման իրական տվյալները և միացման մակարդակի
  `quotaWindowThresholds`-ը՝ առանց սերվերի կողմից տվյալներ կորցնող մասշտաբավորման։

#### Սպառողների միգրացիայի ուղեցույց

Եթե արտաքին ինտեգրումը (օրինակ՝ խմբագրիչի պլագինը կամ գործակալի ընդլայնումը) նախկինում քաղում էր տեքստային
վերջնակետի (`NN% left`) տվյալները և օգտագործված տոկոսը հաշվարկում էր որպես `100 - NN`, ապա `?format=json`-ի անցնելը նշանակում է՝

- Չմշակված JSON արժեքների ընթերցումը կարտացոլի **վերադաս աղբյուրի փաստացի սպառումը** (վերևի օրինակում օգտագործված է 60%-ը)։
- Եթե ինտեգրումը ցանկանում է պահպանել տեքստային վերջնակետի՝ օգտագործման համար հասանելի քանակի իմաստաբանությունը, այն կարող է
  հաճախորդի կողմից հաշվարկել արդյունավետ մնացորդի բանաձևը՝ օգտագործելով `quotaWindowThresholds`-ը՝ կապի մակարդակի վերասահմանումների համար։

### Ազդեցությունը ուշացման վրա

Սեմանտիկ քեշի HIT-ի դեպքում պատասխանը տրամադրվում է քեշից՝ **առանց վերին հոսքի
կանչի**, ուստի հաղորդվող `X-OmniRoute-Response-Latency`-ն գրեթե զրոյական է
(անկախ վերին հոսքի սկզբնական ուշացումից)։ Ուշացման նկատմամբ զգայուն հաճախորդները
(հենանիշային թեստավորում, p50/p99 մոնիթորինգ) պետք է ստուգեն պատասխանի
`X-OmniRoute-Cache-Latency` վերնագիրը՝

| Արժեք            | Նշանակություն                                                          |
| ---------------- | ---------------------------------------------------------------------- |
| `synthetic`      | Պատասխանը տրամադրվել է քեշից․ ուշացումը վերին հոսքի իրական ժամանակը չէ |
| _(բացակայում է)_ | Պատասխանն ստացվել է վերին հոսքի իրական կանչից                          |

### Քեշի շրջանցում՝ ըստ բանալու

API բանալիները կարող են հրաժարվել սեմանտիկ քեշից ընթերցումներից՝ օգտագործելով `cacheDefaultMode`-ը՝

| Արժեք    | Վարքագիծ                                                        |
| -------- | --------------------------------------------------------------- |
| `legacy` | Քեշի սովորական վարքագիծ (լռելյայն)                              |
| `bypass` | Ամբողջությամբ բաց թողնել քեշի որոնումը․ միշտ կանչել վերին հոսքը |

Սահմանեք բանալու ստեղծման (`POST /api/keys`) կամ թարմացման (`PATCH /api/keys/[id]`) ժամանակ՝

```json
{ "cacheDefaultMode": "bypass" }
```

### Շրջանցում՝ ըստ հարցման

Ցանկացած հարցում կարող է շրջանցել քեշը՝ անկախ բանալու կարգավորումներից՝

```
X-OmniRoute-No-Cache: true
```

Համաժամացված/ներմուծված մոդելների համար `PUT /api/provider-models`-ն ընդունում է `provider`, `modelId` և
`maxOutputTokenOverride`․ դրական ամբողջ թիվը սահմանում է ելքային թոքենների ձեռքով նշված առավելագույն քանակը, իսկ `null`-ը
մաքրում է այն՝ վերականգնելով լռելյայն արժեքը։ `GET /api/provider-models?provider=<provider>`-ը վերադարձնում է այս
արժեքները `modelOutputOverrides`-ում՝ ներառյալ հատուկ մոդելի տող չունեցող մոդելները։ Վերասահմանումն
օգտագործում է կատարման ժամանակի `max_output_tokens` հնարավորությունը և պահպանվում է մոդելի կրկնակի համաժամացումից հետո։ OpenAI-ի հետ համատեղելի
մատակարարի էջն առաջարկում է խմբագրման/մաքրման նույն կառավարիչները և նշում է տեսողական աջակցություն բացահայտորեն ունեցող մոդելները։

Հատուկ Chat Completions հանգույցները վերադաս backend-ին հարմարեցնում են reasoning-ից բացահայտ հրաժարումները։ Կապի
հաջող փորձարկումն ինքնաբերաբար ընտրում է chat-template կառավարիչները յուրաքանչյուր ճշգրիտ մոդելի ID-ի համար,
որի `/models` գրառումն ապացուցում է ճանաչված `owned_by` արժեքի առկայությունը՝ `vllm`, `sglang` կամ `llamacpp`։
OpenAI-ի հետ համատեղելի թափանցիկ wrapper-ները կարող են պահպանել մոդելի սկզբնական գրառումը ներդրված
`openai` օբյեկտի ներսում․ հայտնաբերումն անցնում է առավելագույնը երեք այդպիսի շերտով։ Բացակայող, անհայտ կամ
հակասական պատկանելություն ունեցող մոդելները պահպանում են OpenAI-ի սովորական վարքագիծը։ Հայտնաբերումը կրկին օգտագործում է կատալոգի առկա հարցումը,
չի գեներացնում ավարտման թոքեններ և անվավերացվում է, երբ փոխվում է կապի վերջնակետը։

Այդ մետատվյալները չտրամադրող backend-ի համար վարքագիծը ամրագրելու նպատակով օգտագործեք մատակարարի մասնակի
թարմացման առկա API-ն․

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Այդ body-ն ուղարկեք `PUT /api/providers/<connection-id>`-ի միջոցով։ Այդ կապում `none` բացահայտ
reasoning effort-ն ուղարկվում է որպես `chat_template_kwargs.thinking=false` և
`chat_template_kwargs.enable_thinking=false`։ Կաղապարի բացահայտ բնիկ արժեքները շարունակում են գերակայել,
եթե սերվերային reasoning կանոնը չի պարտադրում effort։ Կարգավորումը կիրառվում է միայն այն դեպքում, երբ հատուկ
OpenAI-ի հետ համատեղելի կապն ուղարկում է Chat Completions body․ Responses հարցումները և սովորական
մատակարարները պահպանում են իրենց բնիկ հարցման կառուցվածքը։ Սահմանեք `reasoningControl`-ը որպես `openai`՝ OpenAI-ի սովորական
`reasoning_effort`-ի անփոփոխ փոխանցումը պարտադրելու համար, կամ բաց թողեք այն/սահմանեք որպես `null`՝ ավտոմատ հայտնաբերումն օգտագործելու համար։

Claude Code-ի ավտոմատ ռեժիմի դասակարգիչի հարցումները, երբ չեն պարունակում reasoning-ի բացահայտ կառավարիչներ,
լռելյայն անջատում են բնիկ thinking-ը։ Հայտնաբերումն օգտագործում է դասակարգիչի համակարգային նշիչը Claude ձևաչափով
հարցումներում, այլ ոչ թե մոդելների անունները կամ ավարտման սահմանաչափերը։ Body-ի բացահայտ կառավարիչները, աջակցվող effort/thinking
վերնագրերը, երթուղավորման կանոնները և մոդելի որոշված effort-ը պահպանում են իրենց գործող առաջնահերթությունը։ Դասակարգիչի
երկու փուլերն էլ պահպանում են իրենց հուշումները, ավարտման սահմանաչափերը, կանգի հաջորդականությունները և վերադաս համակարգի թույլտվության իրական
վճիռները․ երկրորդ փուլը դեռ կարող է իր պահանջած տեսանելի reasoning-ը տրամադրել որպես սովորական տեքստ։

`/api/db-backups/export`, `/api/db-backups/exportAll` և `/api/settings/export-json` վերջնակետերը տրամադրում են
պահպանված բոլոր հավատարմագրերը, ուստի դրանք պահանջում են կառավարման վահանակի աշխատաշրջան կամ տեղային CLI (կամ անջատված
մուտքագրում)։ Ցանկացած տիրույթի API բանալիները և `oma_` հասանելիության թոքենները ստանում են `403`։ Վերականգնումների համար գործում է նույն
սահմանափակումը. `POST /api/db-backups/import` (ներառյալ `dryRun=true`), `POST /api/db-backups` (վերականգնում
ըստ id-ի) և `POST /api/settings/import-json` փոխարինում են գործող տվյալների բազան կամ կարգավորումները, ուստի մեքենայական
հավատարմագիրն այնտեղ նույնպես ստանում է `403`։ `omniroute sync import`-ը ուղարկում է տեղային CLI-ի հավատարմագիրը։ Նույնը վերաբերում է
`DELETE /api/db-backups`-ին (պահվող պահուստային պատճենների կրճատում) և `PATCH /api/db-backups`-ին (պահպանման կարգավորումներ.
պահպանված արժեքները կառավարում են յուրաքանչյուր պահուստավորումից հետո կատարվող ավտոմատ կրճատումը)։ Ցուցադրումը (`GET`) և ձեռքով
պահուստային պատճենի ստեղծումը (`PUT`) շարունակում են օգտագործել սովորական կառավարման նույնականացումը։

### Տարբերակը և թողարկման ալիքը

```bash
GET /api/system/version
```

Միայն loopback-ից հասանելի կառավարման երթուղի (ադմինիստրատորի նույնականացմամբ)։ Վերադարձնում է գործարկվող տարբերակը, վերջին
հրապարակված տարբերակը և ավտոմատ թարմացման կարգավիճակը։ `releaseChannel` և `channels` դաշտերն ավելացվող
դաշտեր են (ճյուղ 3.8.54), իսկ `channel`-ը պահպանում է իր իմաստը՝ տեղակայման եղանակը, որն օգտագործում է կառավարման վահանակի թարմացնողը
(`npm`, `source` կամ `docker-compose`)։

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — գործարկվող հավաքման npm ալիքը՝ `nightly`՝ `-nightly.*` տարբերակների համար,
  `next`՝ այլ նախնական թողարկումների համար (`-rc.*`, `-beta.*`, `-alpha.*`), `lts`՝
  `channels.latest`-ից ավելի հին հիմնական տարբերակի կայուն թողարկման համար, իսկ մնացած դեպքերում՝ `latest`։ Կիրառվում են նույն կանոնները, ինչ
  `scripts/release/dist-tag.mjs`-ում, որն ընտրում է npm dist-tag-ը հրապարակման պահին։
- `channels` — յուրաքանչյուր dist-tag-ի վերջին հրապարակված տարբերակը՝ ստացված `npm view omniroute dist-tags`-ից (ռեեստրի
  HTTP պահուստային տարբերակով), որը քեշավորվում է նույն 10 րոպեանոց TTL-ով, ինչ `latest`-ը։ `latest`-ը միշտ առկա է
  (բացակայության դեպքում օգտագործվում է `latest` դաշտը, ապա՝ `"unavailable"`), իսկ `next`, `nightly` և `lts` դաշտերը հայտնվում են
  միայն այն դեպքում, երբ տվյալ dist-tag-ը գոյություն ունի։ `Cache-Control: no-cache` հարցումը թարմացնում է երկու որոնումներն էլ։

Ալիքների մոդելը (`latest` = v3 մինչև 4.0 GA թողարկումը, `next` = rc, `nightly` = `develop` հավաքումներ,
`lts` = v3 ուղղումներ 4.0 GA թողարկումից հետո) նկարագրված է `docs/ops/RELEASE_STRATEGY.md`-ում։

## Ձայնագրության տառադարձում

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Տառադարձեք ձայնային ֆայլերը՝ օգտագործելով կազմաձևված ցանկացած STT մատակարար։ Ուղու առաջին
հատվածն ընտրում է բնիկ մատակարարին (`openai/…`, `deepgram/…`)։ Այլ մատակարարի մոդելը
վերարտահանող դարպասներն օգտագործում են որակավորված նույնացուցիչ
(`openrouter/deepgram/nova-3`)։

**Հարցում՝**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Պատասխան՝**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Մոդելների նույնացուցիչների օրինակներ՝** `openai/whisper-1` (պահանջում է OpenAI բանալի),
`openrouter/deepgram/nova-3` (պահանջում է OpenRouter բանալի),
`deepgram/nova-3` (պահանջում է բնիկ Deepgram բանալի)։ Առանց որակավորման
`deepgram/nova-3` հարցումը **չի** օգտագործում OpenRouter։

**Աջակցվող ձևաչափեր՝** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`։

Նշումներ՝

- Թոքենավորված այլանուններն օգտագործում են նույն մշակիչները, ինչ `/v1/*`-ը և `/api/tags`-ը․ պատասխանների կառուցվածքները մնում են նույնը։
- Նախընտրեք `Authorization: Bearer ...`, երբ հաճախորդն աջակցում է հատուկ վերնագրեր։
- URL-ի վրա հիմնված թոքենները կարող են հայտնվել հակադարձ պրոքսիի մատյաններում, դիտարկիչի պատմության մեջ և OmniRoute-ից դուրս գտնվող հեռաչափության տվյալներում։ Դրանք դիտարկեք որպես համատեղելիության տարբերակ, ոչ թե նույնականացման լռելյայն եղանակ։

## Բյուջե

```bash
# Ստանալ բյուջեի կարգավիճակը բոլոր API բանալիների համար
GET /api/usage/budget

# Սահմանել կամ թարմացնել բյուջեն
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **Սխեմայի նշումներ** (`setBudgetSchema`)՝ `apiKeyId`-ը պարտադիր է․ `dailyLimitUsd`, `weeklyLimitUsd` կամ `monthlyLimitUsd` դաշտերից առնվազն մեկը պետք է զրոյից մեծ լինի։ Ոչ պարտադիր դաշտեր՝ `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`)։ Հնացած `{keyId, limit, period}` կառուցվածքը վերադարձնում է `400 Bad Request`։

## Թոքենների սահմանաչափեր

Յուրաքանչյուր API բանալու համար սահմանվող **թոքենների** բյուջեներ (տարբերվում են վերը նշված՝ USD-ով հաշվարկվող բյուջեից)։ Դրանք կիրառվում են անմիջապես հարցման մշակման ուղու վրա․ երբ բանալու ընթացիկ ժամանակահատվածի օգտագործումը հասնում է սահմանաչափին, հարցումները մերժվում են `429 Too Many Requests` պատասխանով։ Սահմանաչափերը կարող են վերաբերել որոշակի `model`-ի, `provider`-ի կամ կիրառվել ամբողջ բանալու համար՝ `global` շրջանակով։ Երբ հարցմանը համապատասխանում են մի քանի սահմանաչափեր, կիրառվում է ամենախիստը։

```bash
# Ցուցադրել բանալու թոքենների սահմանաչափերը (ներառյալ ընթացիկ ժամանակահատվածի օգտագործումը)
GET /api/usage/token-limits?apiKeyId=key-123

# Ստեղծել կամ թարմացնել թոքենների սահմանաչափը
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Հեռացնել թոքենների սահմանաչափը՝ ըստ id-ի
DELETE /api/usage/token-limits?id=tl-abc
```

> **Սխեմայի նշումներ** (`setTokenLimitSchema`)․ `apiKeyId`-ը և `scopeType`-ը (`model` | `provider` | `global`) պարտադիր են։ `scopeValue`-ն անհրաժեշտ է, եթե `scopeType`-ը `global` չէ (օրինակ՝ մոդելի id՝ `model` շրջանակի համար, մատակարարի id՝ `provider` շրջանակի համար)։ `tokenLimit`-ը պետք է լինի դրական ամբողջ թիվ (տողից փոխակերպվող)։ Ընտրովի դաշտեր՝ `id` (ստեղծելու համար բաց թողեք, թարմացնելու համար տրամադրեք), `resetInterval` (`daily` | `weekly` | `monthly`, լռելյայն՝ `monthly`), `resetTime` (`HH:MM`), `enabled` (լռելյայն՝ `true`)։ `GET` պատասխաններում յուրաքանչյուր սահմանաչափ լրացվում է `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` և `nextResetAt` դաշտերով։ Սա կառավարման դասի վերջնակետ է (նույնականացման ստուգումը կենտրոնացված կերպով իրականացվում է authz մշակման շղթայի միջոցով)։

## Հարցումների մշակում

1. Հաճախորդը հարցում է ուղարկում `/v1/*`
2. Երթուղու մշակիչը կանչում է `handleChat`, `handleEmbedding`, `handleAudioTranscription` կամ `handleImageGeneration`
3. Որոշվում է մոդելը (ուղղակի մատակարար/մոդել կամ կեղծանուն/համակցություն)
4. Հավաստագրերը ընտրվում են տեղային ՏԲ-ից՝ հաշվի առնելով հաշիվների հասանելիությունը
5. Չաթի դեպքում `handleChatCore`-ը ստուգում է իմաստային/ստորագրության քեշը և որոշում համակցման սեղմման կարգավորումները
6. Երբ միացված է, կանխարգելիչ սեղմումն իրականացվում է մինչև մատակարարի ձևաչափին փոխակերպումը (`lite`, Caveman, RTK կամ դրանց համակցում)
7. Մատակարարի կատարիչը հարցումն ուղարկում է վերին մակարդակի ծառայությանը
8. Պատասխանը փոխակերպվում է հաճախորդի ձևաչափին (չաթի դեպքում) կամ վերադարձվում է անփոփոխ (ներդրումներ/պատկերներ/աուդիո)
9. Գրանցվում են օգտագործումը, սեղմման վերլուծական տվյալները և հարցումների մատյանները
10. Սխալների դեպքում պահուստային տարբերակն ընտրվում է համակցման կանոնների համաձայն

Ճարտարապետության ամբողջական նկարագրություն՝ [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

| GET    | `/api/model-combo-mappings`      | Ցուցադրել մոդել→համակցություն բոլոր համապատասխանեցումները                                           |

| GET    | `/api/model-combo-mappings/[id]` | Ստանալ մեկ համապատասխանեցում                                                                        |
| PUT    | `/api/model-combo-mappings/[id]` | Թարմացնել գոյություն ունեցող համապատասխանեցման դաշտերը                                              |
| DELETE | `/api/model-combo-mappings/[id]` | Հեռացնել համապատասխանեցումը                                                                         |

| GET    | `/api/webhooks`           | Ցուցադրել վեբհուկերը (գաղտնիքները քողարկվում են որպես `<prefix>...`)             |

| DELETE | `/api/webhooks/[id]`      | Հեռացնել վեբհուկը                                                                |

**Նույնականացում՝** կառավարման աշխատաշրջան/API բանալի (`requireManagementAuth`)։

## Գրանցված բանալիներ (ինքնակառավարում)

Օգտագործվում է բանալիների ինքնակառավարման ենթահամակարգի կողմից՝ հիմքում ընկած մատակարարի/հաշվի համար API բանալիներ տրամադրելու և ռոտացիայի ենթարկելու նպատակով՝ օրական/ժամային քվոտաներով։

| Մեթոդ  | Ուղի                                  | Նկարագրություն                                                                                                                                                                                                                                   |
| ------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/registered-keys`             | Ցուցադրել գրանցված բանալիները (միայն քողարկված նախածանցը)                                                                                                                                                                                        |
| POST   | `/api/v1/registered-keys`             | Տրամադրել նոր գրանցված բանալի — հարցման մարմին՝ `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`։ Վերադարձնում է չմշակված բանալին **մեկ անգամ**։ Քվոտայի պատճառով մերժման դեպքում վերադարձնում է `429`։ |
| GET    | `/api/v1/registered-keys/[id]`        | Ստանալ գրանցված բանալու մետատվյալները (առանց չմշակված գաղտնի տվյալների)                                                                                                                                                                          |
| DELETE | `/api/v1/registered-keys/[id]`        | Չեղարկել գրանցված բանալին                                                                                                                                                                                                                        |
| POST   | `/api/v1/registered-keys/[id]/revoke` | Չեղարկման բացահայտ վերջնակետ (ունի նույն ազդեցությունը, ինչ DELETE-ը)                                                                                                                                                                            |

**Նույնականացում՝** կառավարման աշխատաշրջան/API բանալի (`requireManagementAuth`)՝ նույն պաշտպանիչ ստուգումը, ինչ `/api/keys`-ի համար՝ կառավարման վահանակի աշխատաշրջան, տեղային CLI թոքեն կամ `manage`/`admin` հասանելիության տիրույթով API բանալի։ Միայն ինֆերենցիայի համար նախատեսված API բանալիները ստանում են `403`։ Տե՛ս նաև `/v1/quotas/check` և `/v1/issues/report`։

## Գործակալների արձանագրություն

Ամպային գործակալների առաջադրանքներ (Claude Code, Codex Cloud, OpenHands և այլն), որոնք հեռակա կարգով կատարվում են OmniRoute-ի օգտատերերի անունից։

| Մեթոդ  | Ուղի                          | Նկարագրություն                                                                                                                                                                |
| ------ | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/agents/tasks`        | Առաջադրանքների ցանկ — ընտրովի `?provider=`, `?status=`, `?limit=` (1–500, լռելյայն՝ 50)                                                                                       |
| POST   | `/api/v1/agents/tasks`        | Առաջադրանքի ստեղծում — հարցման մարմինը վավերացվում է `CreateCloudAgentTaskSchema`-ով (`providerId`, `prompt`, `source`, `options?`)։ Վերադարձնում է `201`՝ առաջադրանքի ծրարով |

## Կառավարման պրոքսիներ

Ելքային HTTP(S)/SOCKS պրոքսիներ, որոնք կարող են նշանակվել մատակարարներին, հաշիվներին կամ գլոբալ մակարդակով։

| Մեթոդ  | Ուղի                                         | Նկարագրություն                                                                                                                                        |
| ------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | Պրոքսիների ցանկ (`?id=`-ով վերադարձնում է մեկը, իսկ `?id=&where_used=1`-ով՝ նշանակումների գրաֆը)                                                      |
| POST   | `/api/v1/management/proxies`                 | Պրոքսիի ստեղծում — հարցման մարմինը վավերացվում է `createProxyRegistrySchema`-ով                                                                       |
| PATCH  | `/api/v1/management/proxies`                 | Պրոքսիի թարմացում — հարցման մարմինը վավերացվում է `updateProxyRegistrySchema`-ով (պահանջվում է `id`)                                                  |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | Պրոքսիի ջնջում (նշանակումներն անջատելու համար օգտագործեք `force=1`)                                                                                   |
| GET    | `/api/v1/management/proxies/assignments`     | Նշանակումների ցանկ — զտելի է ըստ `proxy_id`, `scope`, `scope_id` դաշտերի․ փոխանցեք `resolve_connection_id=<id>`՝ միացման ակտիվ պրոքսին որոշելու համար |
| PUT    | `/api/v1/management/proxies/assignments`     | Նշանակում — հարցման մարմինը վավերացվում է `proxyAssignmentSchema`-ով (`{scope, scopeId?, proxyId?}`)։ Մաքրում է դիսպետչերի քեշը                       |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | Զանգվածային նշանակում — հարցման մարմինը վավերացվում է `bulkProxyAssignmentSchema`-ով (`{scope, scopeIds[], proxyId?}`)                                |
| GET    | `/api/v1/management/proxies/health?hours=24` | Պրոքսիների առողջական վիճակի համախմբված տվյալները (հաջող/ձախողված փորձերի քանակ, ուշացում) տվյալ ժամանակահատվածի համար                                 |

**Նույնականացում․** կառավարման աշխատաշրջան/API բանալի՝ յուրաքանչյուր երթուղու համար (`requireManagementAuth`)։

## Դիմակայունություն (ընդլայնված)

OmniRoute-ը տրամադրում է ժամանակավոր խափանումների երեք անկախ մեխանիզմ. ստորև նշված կառավարման վերջնակետերը թույլ են տալիս օպերատորներին դիտել և վերասահմանել դրանք.

| Տիրույթ                      | Վիճակի պահեստ                                          | Դիտում                                    | Վերակայում / մաքրում                                                   |
| ---------------------------- | ------------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------------------- |
| Մատակարարի շղթայական անջատիչ | `domain_circuit_breakers` + հիշողության մեջ            | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                           |
| Միացման սպասման շրջան        | `rateLimitedUntil`՝ մատակարարի միացումների վրա         | `/api/rate-limits`, `/api/providers/[id]` | (կրկին միացվում է ըստ անհրաժեշտության. մաքրեք մատակարարի PUT հարցմամբ) |
| Մոդելի արգելափակում          | Հիշողության մեջ պահվող մոդելների հասանելիության ռեեստր | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                               |

`PATCH /api/resilience`-ն ընդունում է մատակարարի շղթայական անջատիչի վերասահմանումներ `providerBreaker.oauth` և `providerBreaker.apikey` բաժիններում։ Յուրաքանչյուր պրոֆիլ աջակցում է `degradationThreshold`, `failureThreshold` և `resetTimeoutMs` դաշտերը. նույն դաշտերը հասանելի են նաև Կառավարման վահանակ → Կարգավորումներ → Դիմակայունություն բաժնում։

```bash
# Մաքրել մեկ մոդելի արգելափակումը
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Մաքրել բոլոր արգելափակումները
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Ամբողջական հայեցակարգային տեղեկատուի և շղթայական անջատիչի լռելյայն արժեքների համար տես [`CLAUDE.md`](../../CLAUDE.md) → «Դիմակայունության կատարման ժամանակի վիճակ» և [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)։

### Հաճախականության սահմանափակման հերթ և ավտոմատ միացման անվտանգության մեխանիզմ

- **Աջակցվող գրանցման ուղի**. `POST /api/rate-limits`՝ `{"connectionId": "<id>", "enabled": true|false}` մարմնով, միացման հաճախականության սահմանափակման պաշտպանությունը միացնելու կամ անջատելու համար աջակցվող կառավարման վերջնակետն է։ `PUT /api/providers/[id]`-ը միտումնավոր չի փոփոխում կամ շրջում `rateLimitProtection`-ի արժեքը (#11278)։
- **`enabled: false`-ի իմաստը**. `enabled: false` սահմանելը հեռացնում է միացման հստակորեն սահմանված պաշտպանությունը, սակայն **չի** հանում API բանալիով ակտիվ միացումը համընդհանուր ավտոմատ միացման անվտանգության մեխանիզմից (`autoEnableApiKeyProviders = true`)։ `reconcileEnabledConnections`-ում (`open-sse/services/rateLimitManager.ts`) `false`-ը և `undefined`-ը համարժեք են. API բանալիով ակտիվ միացումները, որոնց համար պաշտպանությունը հստակորեն սահմանված չէ, շարունակում են պաշտպանված մնալ ավտոմատ միացման անվտանգության մեխանիզմով։
- **Համընդհանուր անջատում**. API բանալիով միացումներն առանց հաճախականության սահմանափակման հերթերի գործարկելու համար անջատեք անվտանգության մեխանիզմը համընդհանուր մակարդակով՝ `RATE_LIMIT_AUTO_ENABLE=false` (միջավայրի փոփոխական) կամ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Կարգավորումներ → Դիմակայունություն / `PATCH /api/resilience`)։

## MCP սերվեր

OmniRoute-ը տրամադրվում է ներկառուցված Model Context Protocol սերվերով, որն ունի 3 փոխադրամիջոց (stdio, SSE, streamable-http) և սահմանափակված գործիքներ։ Ստորև նշված կառավարման վահանակի վերջնակետերը կարդում են կարգավիճակի/աուդիտի տվյալները և միջնորդում HTTP փոխադրամիջոցների հարցումները։

| Մեթոդ | Ուղի | Նկարագրություն |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Պարբերական ազդանշան, փոխադրամիջոց, առցանց վիճակ, վերջին կանչ, ամենաշատ օգտագործվող գործիքներ, վերջին 24 ժամվա հաջողության գործակից |
| GET | `/api/mcp/tools` | MCP գործիքների ցանկ՝ `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` դաշտերով |
| GET | `/api/mcp/sse` | Բացել SSE հոսք SSE փոխադրամիջոցի համար (վերադարձնում է `503`, եթե MCP-ն անջատված է կամ փոխադրամիջոցը չի համապատասխանում) |
| POST | `/api/mcp/sse` | Ուղարկել JSON-RPC շրջանակ SSE փոխադրամիջոցով |
| GET | `/api/mcp/stream` | Բացել Streamable HTTP փոխադրամիջոցի SSE կողմը (սերվերի նախաձեռնած հաղորդագրություններ) |
| POST | `/api/mcp/stream` | Ուղարկել JSON-RPC շրջանակ Streamable HTTP փոխադրամիջոցով |
| DELETE | `/api/mcp/stream` | Ավարտել Streamable HTTP աշխատաշրջանը |
| GET | `/api/mcp/audit` | Հարցում կատարել աուդիտի մատյանում — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Աուդիտի ամփոփ վիճակագրություն (ընդհանուր թվեր, հաջողության գործակից, միջին տևողություն, ամենաշատ օգտագործվող գործիքներ) |

**Նույնականացում․** `sse`/`stream` փոխադրամիջոցները կիրառում են MCP-ին հատուկ նույնականացման միջերեսը (`mcp` շրջանակով Bearer API բանալի), իսկ `status`/`tools`/`audit*` երթուղիները հասանելի են կառավարման վահանակից կարդալու համար (կառավարման վահանակի հոսթին հասանելիությունից բացի լրացուցիչ նույնականացում չի պահանջվում)։

> Երկու HTTP փոխադրամիջոցների հասանելիությունն էլ կառավարվում է `settings.mcpEnabled` և `settings.mcpTransport` կարգավորումներով․ փոխադրամիջոցի անհամապատասխանության դեպքում վերադարձվում է `400`, իսկ MCP-ի անջատված վիճակի դեպքում՝ `503`։

## A2A սերվեր

OmniRoute-ը տրամադրում է A2A (գործակալից գործակալ) JSON-RPC 2.0 վերջնակետ, ինչպես նաև REST փաթեթավորում՝ ստուգման և կառավարման վահանակում օգտագործելու համար։

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # պարտադիր չէ, եթե OMNIROUTE_API_KEY-ը սահմանված չէ
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Աջակցվող մեթոդները (բոլորը կառավարվում են `settings.a2aEnabled`-ով).

| Մեթոդ            | Նկարագրություն                                                                 |
| ---------------- | ------------------------------------------------------------------------------ |
| `message/send`   | Հմտության համաժամանակյա կատարում․ վերադարձնում է `{task, artifacts, metadata}` |
| `message/stream` | Նույն հմտությունների հավաքածուի հոսքային SSE կատարում                          |
| `tasks/get`      | Առաջադրանքի ստացում ըստ `taskId`-ի                                             |
| `tasks/cancel`   | Առաջադրանքի չեղարկում ըստ `taskId`-ի                                           |

Ներկառուցված հմտություններ՝ `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`։

### Գործակալի քարտ

```bash
GET /.well-known/agent.json
```

Վերադարձնում է հանրային A2A գործակալի քարտը (անուն, նկարագրություն, հնարավորություններ, հմտությունների կատալոգ, նույնականացման սխեմա), որը հրապարակայնորեն պահվում է քեշում 1 ժամով։ Նույնականացում չի պահանջվում։

### REST օժանդակ մեթոդներ

| Մեթոդ | Ուղի                         | Նկարագրություն                                                                                                           |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| GET   | `/api/a2a/status`            | A2A-ի միացված լինելու վիճակ + առաջադրանքների վիճակագրություն + քեշավորված գործակալի քարտի ամփոփում                       |
| GET   | `/api/a2a/tasks`             | Առաջադրանքների ցանկ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Իրականացված չէ որպես REST օժանդակ մեթոդ․ ստեղծեք JSON-RPC `message/send`-ի միջոցով)                                     |
| GET   | `/api/a2a/tasks/[id]`        | Մեկ առաջադրանքի ստացում                                                                                                  |
| POST  | `/api/a2a/tasks/[id]/cancel` | Առաջադրանքի չեղարկում                                                                                                    |

**Նույնականացում․** REST օժանդակ մեթոդներն աշխատում են առանց կառավարման նույնականացման (ընթեռնելի են կառավարման վահանակից), իսկ JSON-RPC `/a2a` երթուղին օգտագործում է Bearer `OMNIROUTE_API_KEY`, եթե այն կազմաձևված է։

## Ամպ, Evals և Assess

| Մեթոդ | Ուղի | Նկարագրություն |
| ------ | ------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------- | ----------------------------------- |
| POST | `/api/cloud/auth` | Ստուգել Bearer բանալին և վերադարձնել քողարկված մատակարարների կապերն ու մոդելների այլանունները՝ ամպային համաժամացման սպասառուների համար |
| POST | `/api/cloud/credentials/update` | Թարմացնել ամպի հետ համաժամացված մատակարարի գաղտնագրված հավատարմագրերը |
| POST | `/api/cloud/model/resolve` | Տրամաբանական մոդելի ID-ն վերածել կոնկրետ մատակարարի/մոդելի՝ օգտագործելով տեղային երթուղավորման աղյուսակը |
| GET | `/api/cloud/models/alias` | Ցուցադրել ամպային համաժամացման համար հասանելի մոդելների այլանունները |
| GET | `/api/assess` | Կարդալ գնահատման վերջին դասակարգումները (ըստ մատակարարի/մոդելի) |
| POST | `/api/assess` | Գործարկել գնահատում — հարցման մարմին՝ `{scope: {type:"all"}                                                   | {type:"provider", providerId} | {type:"model", modelId}, trigger?}` |
| GET | `/api/evals` | Ցուցադրել ներկառուցված գնահատման փաթեթները և ամենավերջին գործարկումները |
| POST | `/api/evals` | Սկսել գնահատման գործարկում |
| POST | `/api/evals/suites` | Ստեղծել անհատական գնահատման փաթեթ․ հարցման մարմինը վավերացվում է `evalSuiteSaveSchema`-ով |
| GET | `/api/evals/suites/[id]` | Ստանալ անհատական գնահատման փաթեթը |

**Նույնականացում․** `/api/cloud/auth`-ն ուղղակիորեն վավերացնում է Bearer բանալին և յուրաքանչյուր կապի համար վերադարձնում է քողարկված բանալին ու `projectId`-ն միայն `manage` / `admin` իրավասություն ունեցող բանալու դեպքում։ Մյուս `/api/cloud/*`, `/api/evals/*` և `/api/assess` երթուղիները պահանջում են կառավարման աշխատաշրջան/API բանալի։ `/api/assess` POST-ը օգտագործում է `validateBody`՝ տարբերակիչ միավորման շրջանակի սխեմայով։

## ACP-ի (Agent Client Protocol) կառավարում

որպես ենթապրոցեսներ։ Այս վերջնակետերը կառավարում են ACP գործակալների հայտնաբերումը և հատուկ գործակալների գրանցումը։

| Մեթոդ  | Ուղի              | Նկարագրություն                                                                                                                                                      |
| ------ | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | Ցուցադրել բոլոր հայտնի CLI գործակալները (ներկառուցված + հատուկ)՝ տեղադրման կարգավիճակով, տարբերակով և բինար ֆայլով                                                  |
| POST   | `/api/acp/agents` | Գրանցել հատուկ ACP գործակալ կամ թարմացնել քեշը — հարցման մարմին՝ `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` կամ `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | Հեռացնել հատուկ ACP գործակալ — հարցման պարամետր՝ `?id=<agentId>`                                                                                                    |

**Պատասխանի օրինակ** (`GET /api/acp/agents`)․

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**Նույնականացում․** Պահանջվում է կառավարման աշխատաշրջան (վահանակի `auth_token` cookie) կամ կառավարման տիրույթով API բանալի։

Ամբողջական մանրամասների համար տե՛ս [ACP հենքը](../frameworks/ACP.md)։

## Վերլուծություն և դիտարկելիություն

Իրական ժամանակում աշխատող վերլուծական վերջնակետեր՝ երթուղավորումը, սեղմումը և մատակարարների բազմազանությունը վերահսկելու համար։ Դրանք սպասարկում են `/dashboard/analytics/*` էջերը։

### Ավտոմատ երթուղավորման վերլուծություն

| Մեթոդ | Ուղի                                 | Նկարագրություն                                                                                                                                      |
| ----- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/analytics/auto-routing`        | Ավտոմատ երթուղավորման համախմբված վիճակագրություն՝ կանչերի ընդհանուր քանակ, ռազմավարությունների բաշխում, մակարդակների բաշխում, առաջատար մատակարարներ |

### Մատակարարների բազմազանության հետևում

Մատակարարների ստվերային / A-B համեմատությունը **ինքնուրույն REST միջերես չէ**․ այն կազմաձևվում է համակցված երթուղավորման միջոցով (տե՛ս [Ավտոմատ համակցում](../routing/AUTO-COMBO.md))։ Յուրաքանչյուր համակցման համեմատական չափորոշիչները տրամադրվում են `GET /api/combos/metrics`-ի միջոցով։

## Պաշտպանիչ սահմանափակումներ

Ստուգեք կատարման ժամանակի պաշտպանիչ սահմանափակումները (PII-ի հայտնաբերում, հուշման ներարկման հայտնաբերում, տեսողական մոդալության կամրջում)։ Պաշտպանիչ սահմանափակումները գործարկվում են յուրաքանչյուր հարցման դեպքում․ յուրաքանչյուր կանչի համար դրանցից հրաժարումը կատարվում է `x-omniroute-disabled-guardrails` հարցման վերնագրի միջոցով․ պահպանվող միացման/անջատման միջերես չկա։

| Մեթոդ | Ուղի                   | Նկարագրություն                                                                                                               |
| ----- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/guardrails`      | Ցուցադրել գրանցված պաշտպանիչ սահմանափակումները և դրանց կարգավիճակը (անուն / միացվածություն / առաջնահերթություն)              |
| POST  | `/api/guardrails/test` | Փորձնականորեն գործարկել նախականչային խողովակաշարը նմուշային մուտքային տվյալների վրա — մարմին՝ `{input, disabledGuardrails?}` |

**Նույնականացում․** Պահանջվում է կառավարման աշխատաշրջան։

Ամբողջական մանրամասների համար տե՛ս [Անվտանգություն > Պաշտպանիչ սահմանափակումներ](../security/GUARDRAILS.md)։

## Նույնականացում

Հավատարմագրերի չորս ընտանիքների (վահանակի աշխատաշրջան, տեղային CLI թոքեն, `oma_live_…` հասանելիության թոքեն, կառավարման տիրույթով API բանալի) և ինֆերենսի բանալիներից դրանց տարբերությունների մասին տե՛ս [Կառավարման նույնականացում](../guides/MANAGEMENT-AUTH.md) ուղեցույցը։

- Վահանակի երթուղիները (`/dashboard/*`) օգտագործում են `auth_token` cookie-ն
- Մուտք գործելու համար օգտագործվում է պահպանված գաղտնաբառի հեշը, իսկ անհաջողության դեպքում՝ `INITIAL_PASSWORD`
- `requireLogin`-ը կարելի է փոխարկել `/api/settings/require-login`-ի միջոցով
- Երբ `REQUIRE_API_KEY=true`, `/v1/*` երթուղիները կարող են պահանջել Bearer API բանալի
- Այս տեղեկատուում «կառավարման թոքեն» / «կառավարման տիրույթով API բանալի» նշանակում է այդ ուղեցույցում նշված ընտանիքներից մեկը, այլ ոչ թե չսահմանված լրացուցիչ գաղտնիքի տեսակ

> **Հետադարձ համատեղելիությունը խախտող փոփոխություն (v3.8.0)** — `/api/v1/agents/tasks/*`-ը և cooldown-ի կառավարման վերջնակետերն այժմ պահանջում են **կառավարման նույնականացում** (վահանակի `auth_token` cookie կամ կառավարման տիրույթով API բանալի)։ Այն հաճախորդները, որոնք նախկինում այս երթուղիները կանչում էին առանց նույնականացման, կստանան `401 Unauthorized`։ Տե՛ս `588a0333` commit-ը (`fix(auth): require management auth for agent and cooldown APIs`)։
