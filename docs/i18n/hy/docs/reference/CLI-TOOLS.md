## Ինչպես է այն աշխատում

```
CLI Code's / CLI Agents (սպառման հոսք)․
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (բոլորն ուղղորդվում են դեպի OmniRoute)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute-ն ուղղորդում է դեպի համապատասխան մատակարարը)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (հակադարձ գործարկման հոսք)․
    Հաճախորդի հարցում → OmniRoute → գործարկում է CLI-ն stdio/ACP-ի միջոցով → պատասխան
```

**Առավելություններ․**

- Մեկ API բանալի՝ բոլոր գործիքները կառավարելու համար
- Ծախսերի հետևում բոլոր CLI-ների համար՝ կառավարման վահանակում
- Մոդելի փոխարկում՝ առանց յուրաքանչյուր գործիքը վերակազմաձևելու
- Աշխատում է տեղային և հեռակա սերվերներում (VPS, Docker, Akamai, Cloudflare Tunnel)

## Ինքնակազմաձևում `setup-*`-ի միջոցով

Կարիք չկա յուրաքանչյուր գործիքի կազմաձևումը ձեռքով գրել։ OmniRoute-ը յուրաքանչյուր աջակցվող CLI-ի համար տրամադրում է `setup-*` հրաման, որը գործարկվող OmniRoute-ից (տեղային կամ հեռավար) կարդում է մոդելների **ընթացիկ** կատալոգը և ձեր համակարգչում գրում տվյալ գործիքի սեփական կազմաձևումը․

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
```

Յուրաքանչյուրն ընդունում է `--remote <url> --api-key <key>` (տեղային գործիքը հեռավար OmniRoute-ի հետ աշխատելու համար կազմաձևելու նպատակով), `--dry-run` (առանց գրելու նախադիտելու համար) և `--port`։ Մոդելների ինքնահայտնաբերում չունեցող գործիքներն (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive) ընդունում են `--model <id>` (ինչպես նաև `--yes`՝ ոչ ինտերակտիվ գործարկումների համար)։ `setup-5dive`-ը միակ բաղադրատոմսն է, որը `$HOME`-ի ներքո չի գրում․ այն կազմաձևում է 5dive գործակալների խումբը՝ խմբի հոսթում գրելով `root`-ին պատկանող նույնականացման պրոֆիլ, ուստի վերագործարկվում է `sudo`-ի միջոցով և չունի սեփական հեռավար ռեժիմ։ CLI-ն անհրաժեշտ միջավայրային փոփոխականներով և ընդհանրապես առանց որևէ կազմաձևում գրելու գործարկելու համար օգտագործեք ընդհանուր `omniroute run <target>` գործարկիչը (claude, codex, aider, goose, opencode, qwen, gemini․ թիրախներն ու այլանունները վերցվում են `bin/cli/cli-manifest.mjs`-ից)։ Յուրաքանչյուր գործիքի համար նախատեսված հին գործարկիչները՝ `omniroute launch` (Claude Code) և `omniroute launch-codex` (Codex), շարունակում են հասանելի մնալ։ Gemini CLI-ն նախատեսված է միայն գործարկման համար․ այն `omniroute run`-ի թիրախ է, սակայն չունի `setup-*`/`configure` բաղադրատոմս։

> **Ամբողջական տեղեկատու․** գլխավոր աղյուսակը՝ ինչ է գրում յուրաքանչյուր հրաման, բոլոր դրոշակները, տեղային և հեռավար ռեժիմների տարբերությունները, ինչպես նաև այն, թե որ գործիքներն են պահանջում `/v1` վերջածանց, գտնվում է
> **[CLI ինտեգրումներ](../guides/CLI-INTEGRATIONS.md)** էջում։

### Սրանց գործարկումը կոնտեյների ներսում

OmniRoute-ի կոնտեյների ներսում կատարված `setup-*` հրամանը գրում է կոնտեյների սեփական տնային պանակում, որը հոսթի ոչ մի CLI չի կարդում և որը անհետանում է կոնտեյների հետ միասին։ OmniRoute-ը հայտնաբերում է դա և գրելու փոխարեն հրահանգներով ավարտում է աշխատանքը `2` ելքի կոդով։ Շարունակելու երկու աջակցվող եղանակ կա՝ տեղադրել CLI-ն հոսթում և `omniroute connect`-ի միջոցով միանալ կոնտեյներին, կամ bind-mount անել կազմաձևման պանակները և սահմանել `CLI_CONFIG_HOME`-ը (compose-ի `host` պրոֆիլը)։ Յուրաքանչյուր `setup-*` հրաման, ինչպես նաև `omniroute configure`-ը և `omniroute config set`-ը, ընդունում են `--allow-container-write`, երբ իրականում ցանկանում եք կազմաձևել հենց կոնտեյների սեփական CLI-ները։ Սերվերի համար նույնն անում է `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true`-ը։ Տե՛ս
[Docker ուղեցույց → Հոսթի CLI գործիքների կազմաձևում](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker)։

Կառավարման վահանակի **կիրառման վերջնակետը** (`POST /api/cli-tools/apply`) կիրառում է նույն պաշտպանությունը․ կոնտեյներում գրելու փորձը, որի թիրախը հոսթից bind-mount արված չէ, պատասխանում է **`422`** կոդով՝ `containerEphemeralTarget: true`-ով, անվտանգ սխալի տեքստով և, հոսթի համար բաղադրատոմս ունեցող գործիքների դեպքում (claude, codex, opencode, cline, kilo, continue), հոսթում գործարկելու համար նախատեսված `hostSetupCommand`-ով (օրինակ՝ `omniroute setup-opencode`)։ Ոչինչ չի գրվում։ `dryRun: true`-ը շարունակում է աշխատել կոնտեյների ռեժիմում և առանց սկավառակին դիպչելու վերադարձնում է գաղտնազերծված տվյալները թաքցնող նախադիտում և թիրախային ուղին։ Նախադիտման բովանդակությունը հավատարմագրեր պարունակող կազմաձևում չէ, որը կարելի է պատճենել կամ ներմուծել։ Կիրառեք այն հոսթում՝ սկզբնական գործիքի/հիմնական URL-ի/API բանալու/մոդելի մուտքային տվյալներով, կամ օգտագործեք նշված հոսթային տեղակայման հրամանը։ Նախադիտման վերնագրի և հարցման պայմանագրի համար տե՛ս [CLI կազմաձևման անվտանգություն](../security/CLI-CONFIGURATION.md)։ Այս վարքագիծը միտումնավոր է և հետընթաց փոփոխություններից պաշտպանված է
`tests/unit/api/cli-tools/apply-container-guard.test.ts` թեստով․ երբեք մի «շտկեք» 422 սխալը՝ հեռացնելով այդ պաշտպանությունը։

## Ճշմարտության աղբյուր

Միասնական կատալոգը գտնվում է `src/shared/constants/cliTools.ts` ֆայլում՝ որպես `CLI_TOOLS: Record<string, CliCatalogEntry>`։

Յուրաքանչյուր գրառում ունի հետևյալ դաշտերը (սահմանված են `src/shared/schemas/cliCatalog.ts`-ում).

| Դաշտ                                            | Տիպ                                                          | Նկարագրություն                                                  |
| ----------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| `category`                                      | `"code" \| "agent"`                                          | Որ էջում է ցուցադրվում գործիքը                                  |
| `vendor`                                        | `string`                                                     | Գործիքի ծագումը («Anthropic», «OSS (P. Gauthier)»)              |
| `acpSpawnable`                                  | `boolean`                                                    | Կարող է օգտագործվել նաև որպես ACP Agent (ցուցադրվում է նշան)    |

## 5. Փաթեթային հայտնաբերման API

Բոլոր գործիքների հայտնաբերումը համախմբվում է մեկ endpoint-ի միջոցով.

**`GET /api/cli-tools/all-statuses`**

- Նույնականացում՝ `requireCliToolsAuth(request)` (նույնը, ինչ `/api/cli-tools/` մյուս երթուղիների համար)
- Վերադարձնում է՝ `Record<toolId, ToolBatchStatus>` (տիպ՝ `src/shared/types/cliBatchStatus.ts`)
- Ռազմավարություն՝ `Promise.all` բոլոր գործիքների համար, յուրաքանչյուր գործիքի համար՝ 5 վրկ. ժամանակային սահմանափակում
- Քեշ՝ հիշողության մեջ պահվող LRU՝ ինդեքսավորված կազմաձևման ֆայլի `mtime`-ով։ Քեշը անվավեր է դառնում, երբ `mtime`-ը փոխվում է։ Վերակայվում է սերվերի վերագործարկման ժամանակ։

Յուրաքանչյուր գործիքի պատասխանի կառուցվածքը.

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // մաքրված է, stack trace-ներ չկան
}
```

#### VS Code Insiders (`chatLanguageModels.json`)

Օգտագործեք սա, երբ VS Code Insiders-ը կազմաձևված է հատուկ վերջնակետերի մոդելների համար, և ցանկանում եք, որ OmniRoute-ն աշխատի առանց հատուկ վերնագրի դաշտի։

**Օրինակ՝ օգտագործելով թոքենացված OmniRoute կեղծանունը.**

```json
[
  {
    "vendor": "customendpoint",
    "id": "auto",
    "name": "OmniRoute Auto",
    "family": "gpt-4",
    "version": "1.0.0",
    "url": "http://localhost:20128/api/v1/vscode/sk-your-omniroute-key/chat/completions",

    "maxOutputTokens": 32768,

      "type": "none"
    }
  }

```

**Նշումներ.**

- `sk-your-omniroute-key`-ը փոխարինեք OmniRoute-ում ստեղծված API բանալիով։
- `url` դաշտը պետք է մատնանշի `/api/v1/vscode/{token}/chat/completions` հասցեն։
- `modelsUrl` դաշտը պետք է մատնանշի `/api/v1/vscode/{token}/models` հասցեն։
- Երբ հաճախորդը աջակցում է հատուկ վերնագրեր, նախընտրեք սովորական `/v1` + Bearer վերնագրի հոսքը։
- URL-ում ներդրված թոքենները համատեղելիության համար նախատեսված պահուստային տարբերակ են և կարող են հայտնվել խմբագրիչի մատյաններում կամ պրոքսիի պատմության մեջ։

## 10. Ներքին OmniRoute CLI

`omniroute` գործարկվող ֆայլը տրամադրում է հրամաններ սերվերի կենսացիկլի, կարգավորման, ախտորոշման և մատակարարների կառավարման համար։ Մուտքի կետ՝ `bin/omniroute.mjs`։

```bash
omniroute                              # Գործարկել սերվերը (կանխադրված պորտը՝ 20128)
omniroute setup                        # Ինտերակտիվ կարգավորման օգնական
omniroute doctor                       # Ստուգել կազմաձևը, DB-ն, պորտերը և կատարման միջավայրը
omniroute providers list               # Կազմաձևված մատակարարների կապերը
omniroute providers test-all           # Փորձարկել յուրաքանչյուր ակտիվ կապ
omniroute reset-password               # Վերակայել ադմինիստրատորի գաղտնաբառը
omniroute logs                         # Հոսքային եղանակով ցուցադրել հարցումների մատյանները
omniroute health                       # Մանրամասն առողջական վիճակ (անջատիչներ, քեշ, հիշողություն)
omniroute --version                    # Տպել տարբերակը
omniroute --help                       # Ցուցադրել բոլոր հրամանները
```

### Կարգավորում և սկզբնավորում

```bash
omniroute setup                        # Ինտերակտիվ կարգավորման օգնական
omniroute setup --non-interactive      # CI/ավտոմատացման ռեժիմ (կարդում է միջավայրի փոփոխականները + դրոշները)
omniroute setup --password '<value>'   # Ուղղակիորեն սահմանել ադմինիստրատորի գաղտնաբառը
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # Մեկ քայլով ավելացնել և փորձարկել մատակարարին
```

Ոչ ինտերակտիվ կարգավորման համար ճանաչվող միջավայրի փոփոխականները՝

| Փոփոխական           | Նպատակ                                                                         |
| ------------------- | ------------------------------------------------------------------------------ |
| `OMNIROUTE_API_KEY` | Մատակարարի API բանալի (կապված է `--api-key`-ին Commander-ի `.env()`-ի միջոցով) |
| `DATA_DIR`          | Վերասահմանել OmniRoute-ի տվյալների պանակը                                      |

Մնացած բոլոր ոչ ինտերակտիվ մուտքային տվյալները փոխանցվում են որպես դրոշներ, այլ ոչ թե միջավայրի փոփոխականներ՝
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(տե՛ս վերևում ներկայացված `omniroute setup` ընտրանքները)։

### Ախտորոշում

```bash
omniroute doctor                       # Ստուգել կազմաձևը, DB-ն, պորտերը, կատարման միջավայրը, հիշողությունը և հասանելիությունը
omniroute doctor --json                # Մեքենայորեն ընթեռնելի JSON
omniroute doctor --no-liveness         # Բաց թողնել HTTP առողջական վիճակի ստուգումը
omniroute doctor --host 0.0.0.0        # Վերասահմանել հասանելիության հոսթը
omniroute doctor --liveness-url <url>  # Ամբողջական առողջական վերջնակետի URL-ի վերասահմանում
```

Doctor-ը կատարում է հետևյալ ստուգումները՝ `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` և `Server liveness`։ Այն ավարտվում է ոչ զրոյական ելքի կոդով, եթե որևէ ստուգման արդյունքը `fail` է։

```bash

omniroute providers available --category api-key    # Զտել ըստ կատեգորիայի (api-key, oauth, free, ...)
omniroute providers available --json                # Մեքենայորեն ընթեռնելի JSON

omniroute providers list                            # Կազմաձևված մատակարարների կապերը
omniroute providers list --json

omniroute providers test <id|name>                  # Փորձարկել մեկ կազմաձևված կապ
omniroute providers test-all                        # Փորձարկել յուրաքանչյուր ակտիվ կապ
omniroute providers validate                        # Միայն տեղային կառուցվածքային վավերացում
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # Գոյություն ունեցող OAuth գործընթաց
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` հրամաններն առաջին հերթին օգտագործում են API-ն և, հետևաբար, աշխատում են
ակտիվ տեղային կամ հեռակա համատեքստի հետ։ Հավատարմագրերը պետք է մուտքագրել
`--credential-stdin` կամ `--credential-env` հրամանով․ `--dry-run --json`-ը հաղորդում է միայն
քողարկված առկայության/կառուցվածքի մասին։ `providers available`-ը կարդում է OmniRoute-ի կատալոգը․
`providers list/test/test-all/validate`-ը պահպանում են իրենց տեղային SQLite վարքագիծը և
չեն պահանջում, որ սերվերը գործարկված լինի։

OpenAI-ի կամ Anthropic-ի հետ համատեղելի հատուկ հանգույցի համար հավատարմագրերը կցեք
`omniroute nodes add`-ի վերադարձրած հանգույցի ID-ին՝ օգտագործելով `omniroute keys add "$NODE_ID" --stdin`։
Դրա համար անհրաժեշտ է գործող սերվեր և ակտիվ համատեքստի կառավարման նույնականացում։
CLI-ն օգտագործում է `POST /api/providers`, որը վավերացնում է հանգույցը և դրա վերջնակետի
կարգավորումները պատճենում կապի մեջ։ Բացակայող հանգույցի, լիազորման ձախողման կամ անհասանելի
սերվերի դեպքում վերադարձվում է սխալ՝ առանց տեղային պահուստային հավատարմագիր ստեղծելու։

`nodes add --base-url`-ը սահմանում է հանգույցի վերջնակետը․ այն տարբերվում է
`OMNIROUTE_BASE_URL`-ում նշված սերվերի հասցեից։ OpenAPI ֆայլերի համար օգտագործեք
`omniroute openapi dump --format json --out ./openapi.json`․ գլոբալ `--output`-ն
ընտրում է CLI-ի ցուցադրման ձևաչափը, այլ ոչ թե նպատակային ֆայլի անունը։

### Վերականգնում և վերակայում

```bash
omniroute reset-password                # Վերակայել ադմինիստրատորի գաղտնաբառը (նաև՝ omniroute-reset-password)
omniroute reset-encrypted-columns       # Ցուցադրել զգուշացում + փորձնական գործարկում՝ կոդավորված հավատարմագրերը վերակայելու համար
omniroute reset-encrypted-columns --force  # Իրականում SQLite-ում կոդավորված հավատարմագրերը դարձնել null
```

### Հավատարմագրերի արտահանում (⚠ զգուշությամբ օգտագործեք)

```bash
omniroute auth export                                 # Ցուցադրել զգուշացում + հաստատման քայլ՝ առանց DB մուտքի
omniroute auth export --force                          # ԲՈԼՈՐ կապերի ՎԵՐԾԱՆՎԱԾ հավատարմագրերը JSON ձևաչափով արտահանել stdout
omniroute auth export --force --id <id>                 # Արտահանել միայն համապատասխան կապը
omniroute auth export --force --format env               # Արտածել OMNIROUTE_<PROVIDER>_<FIELD>=<value> տողեր
omniroute auth export --force --out creds.json           # Գրել ֆայլում (ստեղծվում է 0600 թույլտվություններով)
```

`auth export`-ը աշխատում է **միայն տեղային միջավայրում** (SQLite-ի ուղղակի ընթերցում՝ առանց HTTP երթուղու) և միտումնավոր տպում/գրում է
`apiKey`/`accessToken`/`refreshToken`/`idToken` **բաց տեքստային** արժեքները․ սա գործառույթ է, ոչ թե
սխալ։ Առանց `--force`-ի տվյալների բազայից ոչինչ չի ընթերցվում և ոչինչ չի վերծանվում։ Մինչև որևէ բաց տեքստի արտածումը stderr-ում
միշտ տպվում է նախազգուշացնող ցուցապաստառ։ Պահանջվում է, որ սահմանված լինի `STORAGE_ENCRYPTION_KEY`-ը։
Այն դաշտը, որի վերծանումը ձախողվում է (հնացած բանալի, վնասված գաղտնագիր), ամբողջ արտահանումը դադարեցնելու կամ հիմքում ընկած սխալը բացահայտելու փոխարեն ներկայացվում է որպես
`<field>DecryptFailed: true`։

### Այլ ենթահրամաններ

Սրանք ենթադրում են, որ OmniRoute սերվերն աշխատում է, եթե այլ բան նշված չէ․

```bash
omniroute status                       # Կատարման միջավայրի համապարփակ կարգավիճակ
omniroute logs                         # Հարցումների մատյանների հոսքային ցուցադրում (--json, --search, --follow)
omniroute config list                  # Կազմաձևված CLI գործիքների ցուցադրում

omniroute provider list                # Հասանելի մատակարարների ցանկ (providers list-ի այլանունը)
omniroute provider add                 # Գրանցել OmniRoute-ը որպես մատակարար որևէ գործիքում
omniroute keys add | list | remove     # API բանալիների կառավարում
omniroute models [provider]            # Մոդելների ցանկ (--json, --search)
omniroute combo list | switch | create | delete

omniroute backup                       # Կազմաձևի և ՏԲ-ի ակնթարթային պատճենի ստեղծում
omniroute restore                      # Վերականգնել նախորդ ակնթարթային պատճենից

omniroute health                       # Առողջական վիճակի մանրամասներ (անջատիչներ, քեշ, հիշողություն)
omniroute quota                        # Մատակարարի չափաբաժնի օգտագործում
omniroute cache                        # Քեշի կարգավիճակ
omniroute cache clear                  # Մաքրել իմաստային և ստորագրությունների քեշերը

omniroute mcp status | restart         # MCP սերվերի կարգավիճակ / վերագործարկում
omniroute a2a status | card            # A2A սերվերի կարգավիճակ / գործակալի քարտ

omniroute tunnel list | create | stop  # Թունելների կառավարում (cloudflare/tailscale/ngrok)
omniroute env show | get <k> | set <k> <v>  # Միջավայրի փոփոխականների դիտում / սահմանում (ժամանակավոր)

omniroute test                         # Մատակարարի կապակցման արագ ստուգում
omniroute update                       # Թարմացումների ստուգում
omniroute completion                   # Կեղևի ավտոլրացման ստեղծում
```

## Կառավարեք inference բանալու քաղաքականությունը OmniRoute CLI-ի միջոցով

Օգտագործեք նույնականացված կառավարման համատեքստ (տես [Հեռակա ռեժիմ](../guides/REMOTE-MODE.md))
՝ գոյություն ունեցող inference բանալին իր ID-ով ստուգելու կամ թարմացնելու համար.

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted`-ը `--model-access-mode all`-ի այլանունն է։ Թարմացումը մաքրում է
մոդելների թույլատրելի ցանկը։ Այն պահպանում է շրջանակները, կապի կանոնները, արգելափակված մոդելները, հաճախականության սահմանաչափերը
և ծախսերի սահմանաչափերը, ուստի այդ մյուս վերահսկիչները դեռ կարող են մերժել հարցումը։ Հստակ նշված
`--allowed-models ""`-ը նույնպես ընտրում է `all`․ համադրեք այն
`--model-access-mode restricted`-ի հետ՝ սահմանափակված բանալին առանց թույլատրված մոդելների պահելու համար։
Ստորակետերով բաժանված ոչ դատարկ ցանկն ընտրում է `restricted`, եթե այլ բան հստակ նշված չէ։
Հակասական `all`-ը՝ ոչ դատարկ թույլատրելի ցանկի հետ, մերժվում է նախքան հարցումն ուղարկելը։

`--rate-limit 30`-ը սահմանում է րոպեում հարցումների քանակը և պահպանում այլ ժամանակային
պատուհանների կանոնները։ `--max-cost 5`-ը միացնում է օրական USD սահմանաչափը՝ առանց շաբաթական սահմանաչափը փոխելու․
`--max-cost 0`-ն հեռացնում է օրական սահմանաչափը և պահպանում օգտագործման սահմանաչափի առկա փոխարկիչը
և շաբաթական սահմանաչափը։ Քաղաքականության բաց թողնված դաշտերը մնում են անփոփոխ։ Հաճախականության փոփոխությունները նախ կարդում են
ընթացիկ քաղաքականությունը․ խուսափեք միևնույն բանալու հաճախականության սահմանաչափերի զանգվածը զուգահեռ խմբագրելուց։

Քաղաքականության հրամաններն օգտագործում են նույնականացված `GET`/`PATCH /api/keys/{id}` հարցումներ և հաշվի են առնում ակտիվ
համատեքստն ու գլոբալ `--api-key` տարբերակը։ JSON ելքը պարունակում է միայն քաղաքականության դաշտերը՝
առանց պահված բանալու կամ դրա քողարկված ներկայացման։ Միայն inference-ի համար նախատեսված հավատարմագիրը
չի կարող թույլատրել կառավարման փոփոխությունները։ 401/403 պատասխանը պահանջում է ստուգել կառավարման
հավատարմագիրն ու համատեքստը․ այն չի հաստատում տեղային CLI տոկենի կամ salt-ի խափանումը։
Տեղային նույնականացման առանձին պայմանագրի համար տես [CLI տոկեն](../security/CLI_TOKEN.md)։
