> Համապատասխան կոնտեքստի վրա ավտոմատ խնայեք 15-95%։ Արագ ակնարկի համար տե՛ս [README-ի սեղմման բաժինը](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically)։

## Ակնարկ

OmniRoute-ն իրականացնում է հուշումների սեղմման մոդուլային շղթա, որն աշխատում է **նախապես**՝ մինչև հարցումների՝ վերին մակարդակի մատակարարներին հասնելը։ Սա նշանակում է, որ թոքենների խնայողությունը կատարվում է թափանցիկ՝ առանց ձեր աշխատանքային գործընթացը փոխելու անհրաժեշտության։

```
Հաճախորդի հարցում
  → Սեղմման ռազմավարության ընտրիչ
    → Կոմբոյի վերասահմանո՞ւմ → Օգտագործել կոմբոյի կարգավորումը
    → Ավտոմատ գործարկման շե՞մ → Օգտագործել ավտոմատ ռեժիմը
    → Լռելյայն ռեժի՞մ → Օգտագործել գլոբալ կարգավորումը
    → Անջատվա՞ծ է → Բաց թողնել սեղմումը
  → Ընտրված սեղմման ռեժիմ
    → Անջատված․ առանց սեղմման
    → Թեթև․ բացատների/ձևաչափման անվտանգ մաքրում (~15%)
    → Ստանդարտ․ պարզունակ խոսքի ոճով ավելորդ բառերի հեռացում (~30%)
    → Ագրեսիվ․ պատմության հնեցում + ամփոփում (~50%)
    → Ուլտրա․ էվրիստիկ կրճատում + կոդային բլոկների նոսրացում (~75%)
    → RTK․ հրամանները հաշվի առնող տերմինալի/գործիքների ելքի զտում (վերին մակարդակում՝ 60-90% միջակայք)
    → Շերտավորված․ կարգավորված բազմաշարժիչ շղթա, սովորաբար RTK, ապա Caveman (համապատասխան կոնտեքստի 78-95% միջակայք)
  → Սեղմված հարցում → Մատակարար
```

## Սեղմման ռեժիմներ

### Անջատված

Սեղմում չի կիրառվում։ Բոլոր հաղորդագրություններն անցնում են անփոփոխ։

### Lite ռեժիմ (~15% խնայողություն, <1ms ուշացում)

Ամենաանվտանգ ռեժիմը՝ ձևաչափման մաքրում։ Գործիքների արդյունքների կրճատումը կորուստներով է, ուստի լռելյայն ուղին (`allow-lossy`, `engine:lite` կամ անվանական համակցման միացման բացակայության դեպքում) գործարկում է lite-ը՝
`compressToolResults: false` արժեքով․ ավելի վաղ գործիքների արդյունքները հասնում են մատակարարին անփոփոխ։

| Տեխնիկա                  | Նկարագրություն                                                                                                          |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | Միավորում է իրար հաջորդող դատարկ տողերն ու տողերի վերջի բացատները                                                       |
| `dedupSystemPrompt`      | Հեռացնում է կրկնվող համակարգային հաղորդագրությունները                                                                   |
| `compressToolResults`    | Ավելի վաղ գործիքների արդյունքները կրճատում է lite-ի սահմանաչափով (կորուստներով՝ միայն հարցման բացահայտ միացման դեպքում) |
| `removeRedundantContent` | Հեռացնում է կրկնվող հրահանգները                                                                                         |
| `replaceImageUrls`       | Կրճատում է base64 պատկերների տվյալների URI-ները                                                                         |

**Լավագույնը՝** Մշտապես միացված օգտագործման, անվտանգության համար կարևոր աշխատանքային հոսքերի դեպքում։

### Standard ռեժիմ (~30% խնայողություն)

Ոգեշնչված է [Caveman](https://github.com/JuliusBrussee/caveman)-ից․ հեռացնում է ավելորդ բառերն ու ծավալուն ձևակերպումները՝ պահպանելով իմաստը․

- Հեռացնում է ավելորդ բառերը («please», «I think», «basically», «actually»)
- Խտացնում է ծավալուն արտահայտությունները («in order to» → «to», «as a result of» → «because»)
- Հեռացնում է քաղաքավարի վերապահումները («Would you mind...», «If you could possibly...»)
- Կոդավորման հարցումների համար հարմարեցված ավելի քան 30 regex կանոն

**Լավագույնը՝** Ամենօրյա կոդավորման աշխատանքային հոսքերի և ծախսերը վերահսկող թիմերի դեպքում։

### Aggressive ռեժիմ (~50% խնայողություն)

Երկարատև սեսիաների պատմության խելացի կառավարում․

- **Հաղորդագրությունների հնացում** — հին հաղորդագրություններն աստիճանաբար ավելի են սեղմվում
- **Գործիքների արդյունքների սեղմում** — գործիքների երկար ելքերը կրճատվում կամ բաց են թողնվում (առաջին/վերջին տողեր, համընկնող տողերի զտում, JSON բանալիների խտացում)
- **Կառուցվածքային ամբողջականության պաշտպանիչ մեխանիզմներ** — ապահովում է, որ `tool_use` + `tool_result` զույգերը մնան համահունչ
- **Համատեքստի պատուհանի իրազեկում** — հաշվի է առնում յուրաքանչյուր մոդելի թոքենների սահմանաչափերը

**Լավագույնը՝** Ընդլայնված վրիպազերծման սեսիաների և մեծ կոդային բազաների դեպքում։

### Ultra ռեժիմ (~75% խնայողություն)

Առավելագույն սեղմում՝ թոքենների նկատմամբ խիստ սահմանափակումներով սցենարների համար․

- **Էվրիստիկ կրճատում** — շարադրանքի թոքենների միավորների վրա հիմնված կրճատում
- **Կառուցվածքի պահպանում** — կոդի բլոկները, ներդրված կոդը, URL-ները և նույնացուցիչները պահվում և կրկին տեղադրվում են բառացիորեն՝ երբեք չկրճատվելով
- **SLM-ի կամընտիր մակարդակ** — կարգավորված լինելու դեպքում փոքր տեղային մոդելը կարող է կատարելագործել կրճատումը
- Անկախ է Aggressive ռեժիմից․ չի գործարկում հաղորդագրությունների հնացում, գործիքների արդյունքների սեղմում կամ պահուստային ամփոփիչ (միայն SLM մակարդակի ձախողումը կարող է պահուստային փուլը ուղղորդել aggressive-ի միջոցով)

**Լավագույնը՝** Երբ բազմիցս բախվում եք համատեքստի սահմանաչափերին։

### RTK ռեժիմ (վերևի հոսքի 60-90% միջակայք)

RTK ռեժիմը օպտիմիզացված է կոդավորման գործակալի սեսիաներում հանդիպող ծավալուն գործիքների ելքերի համար․

- Հայտնաբերում է հրամանների/ելքերի դասեր, օրինակ՝ `git status`, `git diff`, `git log`, թեստերի գործարկիչներ, TypeScript/Vite/Webpack հավաքումներ, ESLint/Biome/Prettier, npm audit/installs, Docker-ի մատյաններ, ենթակառուցվածքի ելք և ընդհանուր shell-ի ելք
- Կիրառում է JSON զտիչների փաթեթներ `open-sse/services/compression/engines/rtk/filters/`-ից
- Ներմուծում է RTK TOML սխեմայի v1 զտիչներ նախագծի կամ գլոբալ `filters.toml` ֆայլերից՝ նախագծի ֆայլերի համար ներդրված թեստերի վավերացմամբ և վստահության վերահսկմամբ
- Ներառում է 56 ներկառուցված զտիչ՝ ներդրված ստուգման նմուշներով
- Հեռացնում է ANSI կառավարման հաջորդականությունները, առաջընթացի գծերը, կրկնվող տողերը և գործողության համար ոչ պիտանի աղմուկը
- Պահպանում է ձախողումները, սխալները, նախազգուշացումները, փոփոխված ֆայլերը, ամփոփումները և երկար ելքի վերջնամասը
- Աջակցում է վստահությամբ վերահսկվող նախագծի զտիչներին, գլոբալ զտիչներին և չմշակված ելքի վերականգնման կամընտիր հնարավորությանը՝ խմբագրված տարբերակով

**Լավագույնը՝** Shell-ի, հավաքման, թեստերի, git-ի, grep-ի և ֆայլերի ելքերի տրանսկրիպտներով գործակալի սեսիաների դեպքում։

### Stacked ռեժիմ (իրավասու միջակայք՝ 78-95%)

Stacked ռեժիմը գործարկում է սեղմման մի քանի շարժիչներ՝ որոշակի հերթականությամբ։ Լռելյայն խողովակաշարն է՝

```txt
RTK -> Caveman
```

Այս հերթականությունը նախ կոմպակտ է դարձնում տերմինալի/գործիքի ելքը, այնուհետև կիրառում է Caveman-ի իմաստային խտացումը մնացած բնական լեզվով գրված հարցման նկատմամբ։ Stacked խողովակաշարերը կարող են կարգավորվել գլոբալ կերպով կամ երթուղավորման համակցություններին վերագրված սեղմման համակցությունների միջոցով։

**Լավագույնը՝** Խառը համատեքստի դեպքում, երբ առկա են գործիքների մեծ մատյաններ, ինչպես նաև մարդու հրահանգներ կամ օգնականի ամփոփումներ։

## Սկզբնաղբյուր նախագծերի խնայողությունների հաշվարկը

OmniRoute-ը ներկայացնում է սեղմման խնայողությունները՝ հիմնվելով երկու աղբյուրի վրա՝ սկզբնաղբյուր նախագծերի չափորոշիչների և
OmniRoute-ի սեփական շարժիչների համադրման։

| Աղբյուր | Այստեղ օգտագործված՝ սկզբնաղբյուր README-ի ցուցանիշը                                                                                |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%`-ով պակաս ելքային թոքեններ, չափորոշիչներում ելքի միջին `65%` խնայողություն, `22-87%` միջակայք և մուտքի `~46%` սեղմման գործիք |
| RTK     | Հրամանների ելքի `60-90%` խնայողություն․ օրինակելի աշխատաշրջանում՝ `~118,000 -> ~23,900` թոքեն, կամ `79.7%` խնայողություն (`~80%`)  |

Գործիքների/համատեքստի համընկնող բովանդակության դեպքում OmniRoute-ի լռելյայն համակցությունը շարժիչները կիրառում է հաջորդաբար․

```txt
RTK -> Caveman
```

Համակցված խնայողությունները բազմապատկվում են, ոչ թե գումարվում․

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Այդ `78-95%` ցուցանիշը կիրառելի է, երբ և՛ RTK-ն, և՛ Caveman-ը կարող են կրճատել նույն մուտքային/համատեքստային բովանդակությունը։
Caveman-ի պատասխանների ելքային ռեժիմն առանձին է․ երբ այն միացված է, օգտագործեք Caveman-ի ելքային խնայողության սեփական ցուցանիշները (`65%`
միջին, `~75%` հիմնական ցուցանիշ, `22-87%` միջակայք)։ Վճարումների ընդհանուր խնայողությունը կախված է ձեր հուշումների և ելքերի հարաբերակցությունից։

### Ինչ է իրականում նշանակում «կիրառելի»

Հիմնական 15-95% միջակայքն իրական է, սակայն այն կիրառելի է միայն **կրկնվող կամ չափազանց ծավալուն** բովանդակության համար՝ կրկնվող
սխալի տողեր, նույն նախազգուշացումը շարունակաբար արտածող կառուցման մատյան կամ չափազանց մեծ `grep`/ֆայլի ընթերցման արտածում։ Դա
**չի** նշանակում, որ յուրաքանչյուր հարցում այդքան խնայողություն է ապահովում։

Փորձնականորեն հաստատված է (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`)․ Anthropic-ի ձևաչափով `tool_result` բլոկի նկատմամբ,
որը պարունակում էր սխալի 300 նույնական տող, `stacked` (RTK + Caveman) գործարկումն ապահովել է **թոքենների 95.93% խնայողություն / նիշերի 96.26% խնայողություն**՝ լիովին
տեղավորվելով հայտարարված միջակայքում։ Սակայն նույն մշակաշարը սովորական, չկրկնվող գործիքային ելքի նկատմամբ գործարկելիս (`grep`-ի համընկնումների մաքուր ցանկ,
ֆայլի կարճ ընթերցում, սովորական զրույցի տեքստ) ճիշտ կերպով ապահովում է **գրեթե զրոյական խնայողություն**, քանի որ
հեռացնելու ենթակա կրկնվող բովանդակություն չկա, իսկ `validateCompression()`-ը (`validation.ts`) հրաժարվում է տրամադրել այնպիսի
վերաշարադրում, որը կհեռացներ կամ կփոխեր կոդի բլոկները, URL-ները, վերնագրերը, տարբերակները կամ ԱՄԲՈՂՋՈՎԻՆ ՄԵԾԱՏԱՌ հաստատունների նույնացուցիչները։

Սա ակնկալվող և անվտանգ վարքագիծ է, ոչ թե սխալ․ ծրագրավորման աշխատաշրջանը, որը հիմնականում մաքուր ֆայլեր է ընթերցում կամ դրանցում որոնում կատարում,
կունենա ընդհանուր համեստ խնայողություն՝ նույնիսկ լիովին միացված սեղմման դեպքում, մինչդեռ խափանվող
ցիկլի կամ չափազանց շատ հաղորդագրություններ արտածող linter-ի հանդիպած աշխատաշրջանն այդ տվյալների հոսքի համար կապահովի ամբողջ 78-95% միջակայքը։ Մի օգտագործեք առանձին աշխատաշրջանի
ընդհանուր խնայողության ցածր տոկոսը որպես ապացույց, որ սեղմումը սխալ է կազմաձևված․ նախ ստուգեք՝ արդյոք
գործիքի սկզբնական ելքն իրականում կրկնվող էր։

## Կազմաձևում

### Վահանակ

Նավարկեք դեպի `Dashboard → Context & Cache`․

- **Caveman** — ռեժիմի ընտրություն, լեզվային փաթեթներ, նախադիտում և գլոբալ լռելյայն կարգավորումներ
- **RTK** — հրամանների զտիչի նախադիտում, RTK-ի անվտանգության կարգավորումներ և զտիչների կատալոգ
- **Compression Combos** — երթուղման կոմբինացիաներին նշանակված՝ անուններով շարժիչների խողովակաշարեր
- **Auto-Trigger Threshold** — ավտոմատ կերպով միացնել սեղմումը, երբ թոքենների քանակը գերազանցում է շեմը

### Կոմբինացիայի անհատական վերասահմանում

`Dashboard → Context & Cache → Compression Combos` բաժնում սեղմման կոմբինացիա նշանակեք երթուղման
կոմբինացիային․

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Սա թույլ է տալիս օգտագործել կուտակված սեղմում անվճար/կոդավորման մատակարարների համար՝ պահպանելով
lite ռեժիմը վճարովի բաժանորդագրությունների դեպքում։

Այս «Per-Combo Override» նշանակումը տարբերվում է **routing-combo compression
mode** վերասահմանումից (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — դաշտի սխեման
նաև ընդունում է `rtk`, `stacked` և `omniglyph`)․ այդ վերասահմանումը չի ընտրում անունով
սեղմման-կոմբինացիայի խողովակաշար, այլ պարզապես սահմանում է `compressionMode` դաշտը, որը
կարդում է `resolveCompressionPlan`-ը։ Այն կարող է սահմանվել կամ կոմբինացիայի քարտում
(`Dashboard → Combos`), կամ, սկսած #6760-ից, յուրաքանչյուր երթուղման կոմբինացիայի համար՝
`Dashboard → Context & Cache → Compression Combos` բաժնի «Assign to routing» ցանկում՝
վերևում փաստագրված խողովակաշարի նշանակման վանդակի կողքին։ Երկու մակերեսներն էլ տվյալները
պահպանում են նույն `PUT /api/combos/{id}` վերջնակետի միջոցով։

### Յուրաքանչյուր հարցման վերասահմանում

Ուղարկեք `x-omniroute-compression` հարցման վերնագիրը՝ մեկ հարցման համար սեղմման պլանը
վերասահմանելու նպատակով։ Այն ունի ամենաբարձր առաջնահերթությունը՝ գերազանցում է երթուղման
կոմբինացիայի վերասահմանումը, ակտիվ պրոֆիլը, ավտոմատ գործարկումը և վահանակի Default-ը։
Անհայտ արժեքներն անտեսվում են (հարցումը երբեք չի մերժվում), իսկ գլոբալ գլխավոր անջատիչը
շարունակում է վերահսկել ամեն ինչ․ երբ սեղմումը գլոբալ անջատված է, վերնագիրը չի կարող այն
միացնել։ Արժեքներ․

| Value         | Effect                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | Այս հարցման համար սեղմում չի կիրառվում։                                                                               |
| `default`     | Վահանակից ստացված Default պրոֆիլը (անտեսում է ակտիվ պրոֆիլը)։ Կորուստներով շարժիչները մնում են անջատված։              |
| `safe`        | Նույնը, ինչ վերնագիրը չնշելու դեպքում։                                                                                |
| `allow-lossy` | Պահպանել այս հարցման օպերատորի պլանը՝ ներառյալ ամփոփումները, համապատասխանության զտիչները և ոճի վերագրումները։         |
| `engine:<id>` | Միակ շարժիչը, երբ այն միացված է, օրինակ՝ `engine:rtk`։ Սա տվյալ շարժիչի համար հարցման մակարդակով միացման տարբերակն է։ |
| `<combo>`     | Անունով կոմբինացիա, որը նախ համադրվում է ըստ անվան (առանց մեծատառերի և փոքրատառերի տարբերակման), ապա՝ ըստ id-ի։       |

Առանց `allow-lossy`-ի, `engine:<id>`-ի կամ անունով կոմբինացիայի՝ կորուստներով շարժիչները չեն
կիրառվում։ Երբ կորուստներով Default-ը, ավտոմատ գործարկումը կամ երթուղման վերասահմանումը
իջեցվում է, OmniRoute-ը կազմաձևված կուտակված խողովակաշարից պահպանում է ճանաչված՝ առանց
կորուստների քայլերը՝ կազմաձևված հերթականությամբ։ Այն վերադառնում է
`session-dedup → lite` տարբերակին միայն այն դեպքում, երբ կազմաձևված՝ առանց կորուստների ոչ մի
քայլ չի պահպանվում։

Settings վահանակի **Effective pipeline** նախադիտումը ցուցադրում է սովորական՝ պահպանված
պլանը։ Երբ ավտոմատ գործարկումը կարող է աշխատել, նույն նախադիտումը ցուցադրում է նաև դրա
պայմանական արդյունավետ խողովակաշարը, որպեսզի վահանակի և առանց վերնագրի գործարկման
լուծումները մնան համաժամեցված։

Կիրառված պլանը վերադարձվում է `X-OmniRoute-Compression: <mode>; source=<source>` պատասխանի
վերնագրում, որտեղ `<source>`-ը հետևյալներից մեկն է՝ `request-header`, `routing-override`,
`active-profile`, `auto-trigger`, `default` կամ `off`։

### API

```bash
# Ստանալ սեղմման կարգավորումները
curl http://localhost:20128/api/settings/compression

# Թարմացնել սեղմման կարգավորումները
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# Նախադիտել RTK/stacked-ով որոշակի payload
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# Ցուցակել RTK զտիչների փաթեթները
curl http://localhost:20128/api/context/rtk/filters

# RTK-ն ուղղակիորեն փորձարկել՝ հրամանի ընտրովի մետատվյալներով
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## Երախտագիտություն

Standard ռեժիմի սեղմման կանոնները ոգեշնչված են **[Caveman](https://github.com/JuliusBrussee/caveman)** նախագծից՝ հեղինակ **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+)։ Սա վիրուսային տարածում գտած «ինչու օգտագործել շատ թոքեն, երբ քիչ թոքենն էլ գործը կանի» նախագիծն է։ Caveman-ը հաղորդում է ելքային թոքենների `~75%` կրճատման, հենանիշային փորձարկումներում ելքի միջին `65%` խնայողության, ելքի `22-87%` միջակայքի և մուտքի սեղմման `~46%` գործիքի մասին։

RTK ռեժիմը ոգեշնչված է **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** նախագծից՝ հեղինակ **[RTK AI](https://github.com/rtk-ai)**։ Այն բարձր արդյունավետությամբ հրամանների ելքի սեղմման նախագիծ է՝ տերմինալի, կառուցման, փորձարկման, git-ի և գործիքների ելքը զտելու համար։ RTK-ն հաղորդում է `60-90%` խնայողության մասին, իսկ դրա README-ի օրինակային աշխատաշրջանը ցույց է տալիս `~80%` խնայողություն։

## Ընդլայնված սեղմման համակարգեր

Վերևում նկարագրված 7 ռեժիմներից դուրս (աղբյուրն ընդունում է նաև `codex-responses` և `omniglyph` ռեժիմները, որոնք այս ուղեցույցը չի ընդգրկում), ստորև բերված բաժինները ներառում են գործառույթներ, որոնք աշխատում են այդ ռեժիմների ներսում կամ դրանց կողքին. Կոմպրեսիան նվազեցնում է `aggressive` և `ultra` `aggressive` `standard` քեշավորման պրովայդերների համար, երբ սեղմումը միացված է, իսկ Caveman Output Mode-ը և Output Styles-ը լռելյայնորեն անջատված համակարգի հրահանգներ են, որոնք ձևավորում են մոդելի ելքը՝ հարցումը սեղմելու փոխարեն:

### Cache-Aware սեղմում

Որոշ պրովայդերներ (ինչպես Anthropic արագ քեշավորման միջոցով) աջակցում են** արագ քեշավորում** , որը թույլ է տալիս նրանց քեշավորել հուշագրի մասերը՝ նվազեցնելու ծախսերն ու հետաձգումը: Երբ քեշավորումը միացված է, ագրեսիվ սեղմումը կարող է իրականում** վիրավորվել** կատարումը, քանի որ այն փոխում է քեշավորված նշանները՝ անվավեր դարձնելով քեշը:

`cachingAware.ts` մոդուլը դա լուծում է** քեշավորման համատեքստի հայտնաբերում** և** սեղմման ռազմավարության ճշգրտում** համապատասխանաբար.

#### Ինչպես է այն աշխատում

1. **Հայտնաբերել քեշավորման համատեքստը** — Սկանավորում է հարցման մարմինը `cache_control` մարկերների համար
2. **Բացահայտեք քեշավորման մատակարարներին** — Ստուգում է, արդյոք թիրախ մատակարարն աջակցում է քեշավորմանը
3. **Կարգավորել ռազմավարությունը** — իջեցնում է `aggressive`/`ultra` `standard` ի քեշավորման մատակարարների համար
4. **Բաց թողնել համակարգի հուշումը** — System-ի հուշումները սովորաբար պահվում են քեշում, այնպես որ մի սեղմեք դրանք

Ռազմավարության օգնականը նաև վերադարձնում է `deterministicOnly` դրոշը, բայց պլանի կառուցողը սպառում է միայն ռազմավարությունը — այսօր չի կարդում դրոշը:

#### Կոդի օրինակ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Երբ օգտագործել

Cache-aware սեղմում է** միշտ միացված** — կոնֆիգուրացիա չի պահանջվում: Այն միանում է ամեն անգամ, երբ սեղմումը միացված է, և թիրախ մատակարարն աջակցում է արագ քեշավորմանը (Anthropic, OpenAI և այլն); Հստակ `cache_control` մարկերներ չեն պահանջվում, — քեշավորման մատակարարը միայնակ է խթանում իջեցումը, և միայն մարկերները երբեք չեն անում (մարկերների հայտնաբերումը սնուցում է քեշի հեռաչափությունը, ոչ թե ռազմավարության որոշումը):

OpenRouter հաշվվում է որպես քեշավորման մատակարար միայն `anthropic/*` մոդելների համար. Claude Code հարցումները պահում են իրենց `cache_control` ընդմիջման կետերը (առավելագույնը 4), իսկ պահակախումբը պաշտպանում է նախածանցը, մինչդեռ յուրաքանչյուր այլ OpenRouter ընտանիք (`openai/`, `google/`, `qwen/`,…) մնում է մերկ և անպաշտպան:

### Պրոգրեսիվ ծերացում

Երկար խոսակցությունները կուտակում են բազմաթիվ հաղորդագրությունների շրջադարձեր, բայց ավելի հին շրջադարձերը դառնում են ավելի քիչ տեղին: `progressiveAging.ts` մոդուլը** նսեմացնում է հաղորդագրությունները ըստ հերթի հեռավորության** (հեռավորությունը չափվում է զրույցի ավարտից): Առաքված լռելյայններով (`verbatim: 2, light: 2, moderate: 3`):

- **Վերջին 2 շրջադարձերը (հեռավորությունը ≤ 2)** Պահվում է բառացի
- **Հեռավորությունը 3** Caveman-ի սեղմում (լցանյութի հեռացում)
- **Հեռավորությունը 4 +** Օգնականի հաղորդագրությունները ամփոփված; օգտատիրոջ հաղորդագրությունները կրճատվել են մինչև իրենց առաջին տողը, սահմանափակված 120 նիշով; այլ դերեր անձեռնմխելի. Համակարգի հուշումները, արդեն հնացած հաղորդագրությունները և օգտվողի վերջին հաղորդագրությունը միշտ պահվում են բառացի՝ անկախ հեռավորությունից: Ոչինչ ուղղակիորեն չի հանվում, և `light` գոտին անհասանելի է առաքված լռելյայններով (`light` հավասար է `verbatim`):

#### Կոդի օրինակ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### Երբ օգտագործել

Պրոգրեսիվ ծերացումն է** միշտ միացված** `aggressive` ռեժիմի համար — դա `compressAggressive()` ի 2-րդ քայլն է: Ուլտրա ռեժիմը չի աշխատում: Այն հատկապես արդյունավետ է հետևյալի համար.

- Երկարատև կոդավորման նիստեր
- Բազմօրյա խոսակցություններ
- Գործակալական աշխատանքային հոսքեր բազմաթիվ գործիքների զանգերով

### Caveman ելքային ռեժիմ

Caveman ելքային ռեժիմն ավելացնում է** համակարգի արագ հրահանգներ** որոնք մոդելից պահանջում են կարճ ելք — `lite` մակարդակը պահանջում է հակիրճ պատասխաններ, որոնք պահպանում են ամբողջական նախադասությունները, `full` խնդրում է նրան «կարճ արձագանքել ինչպես խելացի քարանձավային մարդ», իսկ `ultra` խնդրում է հեռագրական ելք. հրահանգները միայն հարցնում են, նրանք չեն կարող դա երաշխավորել: Հարցումները դրանք ստանում են `applyOutputStyles()` միջոցով (`open-sse/services/compression/outputStyles/apply.ts`). `open-sse/handlers/chatCore.ts` նախ լուծում է ընտրությունը back-compat shim-ի միջոցով (`resolveOutputStyleSelection()` in `open-sse/services/compression/outputStyles/backCompat.ts`), որը, քանի դեռ `outputStyles` դատարկ է, միացված `cavemanOutputMode` քարտեզագրում է `terse-prose` ելքի ոճին `cavemanOutputMode.intensity` ում (տես Ստորև՝ Back-compat); ոչ դատարկ `outputStyles` ընտրությունն օգտագործվում է այնպես, ինչպես կա, և `cavemanOutputMode.enabled` և `intensity` այնուհետև ազդեցություն չունեն, մինչդեռ դրա `autoClarity` անջատիչը դեռևս գործում է: `outputMode.ts` պահում է հրահանգների տեքստերը (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), բովանդակության շրջանցումը և տեղադրման օգնականը, որն օգտագործում է ներարկումը. իր սեփական `applyCavemanOutputMode()` ներարկիչը չունի արտադրական զանգահարող:

#### Ինչպես է այն աշխատում

Այս ռեժիմը չի սեղմում մուտքագրումը: Այն ավելացնում է հրահանգների բլոկ համակարգի հուշումին (տես, թե ինչպես է ներարկումն աշխատում ստորև), և հարցման համար ընտրված ցանկացած մուտքային սեղմման ռեժիմ դեռ աշխատում է այնուհետև այն մարմնի վրա, որն այժմ կրում է բլոկը: Ընդհանուր սահմանների դրույթից առաջ, որով ավարտվում է յուրաքանչյուր մակարդակ, անգլերեն `full` մակարդակը կարդում է.

> «Արձագանքեք հակիրճ, ինչպես խելացի քարանձավային մարդ: Բաց թողեք հոդվածները (a/an/the), լցոնիչ (just/really/basically/actually/simply), հաճելի բաներ, հեջավորում: Հատվածներ OK. Կարճ հոմանիշներ (մեծ ոչ ծավալուն, ուղղեք ոչ իրագործում): Պահպանեք բոլոր տեխնիկական էությունը, կոդը, սխալները, URLs, նույնացուցիչները ճշգրիտ:

Սա հատկապես լավ է աշխատում հետևյալի համար.

- Կոդերի ստեղծում (տրերսերի ելքային = ավելի քիչ նշաններ)
- Արագ հարցուպատասխան (մանրամասն բացատրությունների կարիք չկա)
- Խմբաքանակի մշակում (առավելագույնի հասցնել թողունակությունը)

#### Երբ օգտագործել

Caveman ելքային ռեժիմն է** միանալ** . Եթե սեղմումը միացված է (`enabled: true`, հիմնական փոխարկիչը սեղմման կարգավորումների էջում), միացրեք այն `cavemanOutputMode.enabled` ով; `intensity` ընտրում է `lite`, `full` կամ `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Կոմպրեսիոն կոմբինացիա** Ելքային ռեժիմ** toggle-ը (`outputMode`, մակարդակը `outputModeIntensity` ում) սահմանում է նույն անջատիչը այն հարցումների համար, որոնց վրա կիրառվում է համադրությունը, և `omniroute_set_compression_engine` MCP գործիքը գրում է այն իր բուլյան `outputMode` արգումենտի միջոցով: Ոչ դատարկ `outputStyles` ընտրությունը գերակայություն ունի այս անջատիչի նկատմամբ: Վահանակի վրա՝ միացնելով** Կտրուկ արձակ** ելքային ոճը ներարկում է նույն բլոկը (տես Ստորև բերված Ելքային ոճերը):

| Terse CJK (文言)                      | `terse-cjk`     | `full`/`ultra` պատասխան դասական չինարենով (文言); `lite` պահանջում է միայն հակիրճ պատասխաններ՝ առանց ֆունկցիայի բառերի, հաճելի բաների կամ զարդարանքի:                                                                                                                                          | zh (տեղական մուտքով, տես ստորև)               |

Յուրաքանչյուր ոճ ուղարկվում է երեք ինտենսիվության մակարդակ — `lite`, `full`, `ultra` —, և յուրաքանչյուր մակարդակ ավարտվում է ընդհանուր սահմանների դրույթով (`SHARED_BOUNDARIES` in `outputMode.ts`), որը պահպանում է կոդի բլոկները, ֆայլերի ուղիները, հրամանները, սխալները և URLs ճշգրիտ: `terse-prose` և `terse-cjk` մակարդակի տեքստերը նույնացուցիչներ են ավելացնում այդ ցանկին:

`terse-cjk` երկու տեղից `zh` -ին լոկալացված է: Կոմպրեսիոն Կարգավորումների էջը թվարկում է իր տողը միայն այն դեպքում, երբ վահանակի UI լեզուն չինարեն է (`zh-CN` կամ `zh-TW`), իսկ `applyOutputStyles()` այն ներարկում է միայն այն դեպքում, երբ հարցման լուծված լեզուն (տես ստորև Լեզվի ընտրությունը) `zh` է: Տողը թաքցնելով չի ջնջվում պահպանված `terse-cjk` ընտրությունը. API կարգավորումները ընդունում են ցանկացած ոճի ID, իսկ էջի վրա այլ ոճեր պահելը պահպանում է այն: Հարցման ժամանակ, `applyOutputStyles()` լեզվի ստուգումը միակ տեղային դարպասն է:

#### Ինչպես է ներարկումն աշխատում

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ընտրությունը լուծում է կատալոգի հետ (անհայտ ID-ները և տեղայնացման հետ չհամապատասխանող ոճերը հանվում են, երբեք սխալ չի լինում. ընտրությունը, որը որոշվում է առանց ոճի, թողնում է մարմինը անփոփոխ, բաց թողնում է որպես `no_styles`), միացնում է ընտրված հրահանգները կատալոգի հերթականությամբ, ավելացնում է սահմանների դրույթը:** մեկ անգամ** (գումարած անվտանգության կետը, `SAFETY_BOUNDARIES` կամ դրա թարգմանությունը, երբ ընտրված է `less-code` կամ `ponytail` ), և բլոկը սկսում է անզորության մեկ նշիչով (`[OmniRoute Output Styles]`), ուստի նորից կիրառելը արգելված է: Երբ լուծված լեզուն (տես ստորև Լեզվի ընտրությունը) թարգմանություն ունի, տեղայնացված հրահանգը ներարկվում է անգլերենի փոխարեն:

Ոչ դատարկ `messages` զանգվածով մարմնի վրա անզորության ստուգումն անցնում է բովանդակության շրջանցումից առաջ. երբ `[OmniRoute Output Styles]` նշիչը արդեն վերին մակարդակի `system` դաշտում է (տող կամ բովանդակության բլոկի զանգված) կամ տողերի բովանդակությամբ համակարգային հաղորդագրության մեջ, մարմինը մնում է անփոփոխ որպես `already_applied`, և հիմնաբառի ստուգում չի կատարվում: Հակառակ դեպքում բովանդակության շրջանցումը (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) ստուգում է վերջին երեք հաղորդագրությունների տեքստը, անկախ նրանց դերից, և բաց է թողնում ոճերը ամբողջ հերթի համար `deploy` երբ այդ տեքստը համընկնում է իր անվտանգության, անշրջելի գործողության կամ պարզաբանման հիմնաբառերի կամ կարգի զգայուն հաջորդականության հետ՝ `first`, `then`, `after that`, որին հաջորդում է `before` կամ `rollback` նիշը: , `delete`, `drop`, `migrate` կամ `backup` `release` Շրջանցումն անցնում է, մինչդեռ** Ավտո-պարզության շրջանցում** toggle (`cavemanOutputMode.autoClarity`, լռելյայն միացված) միացված է; անջատիչն անջատելը բաց է թողնում հիմնաբառի ստուգումը:

Երբ շրջանցիկը թույլ է տալիս շրջադարձը անցնել, `placeSystemInstruction()` (նույն ֆայլը), որը երբեք նոր `messages[0]` չի ստեղծում, բլոկը տեղադրում է դրանցից առաջինի մեջ, որը գտնում է.

1. Առաջատար համակարգային հաղորդագրություն՝ տողերի բովանդակությամբ. բլոկը կցվում է իր տեքստից հետո:
2. Վերին մակարդակի `system` դաշտ. բլոկը կցվում է տողի տեքստից հետո կամ ավելացվում է որպես նոր տեքստային բլոկ բովանդակության բլոկի զանգվածին:
3. Համակարգի առաջին ավելի ուշ հաղորդագրությունը տողերի բովանդակությամբ. բլոկը կցվում է իր տեքստից հետո:
4. Վերոնշյալներից ոչ մեկը. բլոկը մտնում է նոր համակարգի հաղորդագրություն `messages` ի վերջում:

Առանց `messages` զանգվածի (կամ դատարկ զանգվածով) մարմնի վրա բովանդակության շրջանցում չի կատարվում, և վերին մակարդակի `system` դաշտը չի քննարկվում: Բլոկը կցվում է տողային `instructions` դաշտի տեքստից հետո, բացառությամբ այն դեպքերի, երբ այդ դաշտն արդեն պարունակում է `[OmniRoute Output Styles]` նշիչը, որի դեպքում մարմինը մնում է անփոփոխ որպես `already_applied`: Երբ մարմինը չունի տող `instructions` դաշտ, բայց կրում է `input` (տող կամ զանգված), բլոկը դառնում է `instructions`՝ փոխարինելով այդ դաշտում պահվող ցանկացած ոչ տողային արժեք։ Ոչ տողային `instructions` դաշտ, ոչ տող կամ զանգված `input` ունեցող մարմինը մնում է անփոփոխ և բաց է թողնվում որպես `no_messages`:

#### Ինչպես միացնել

Վահանակի վրա.** Կոմպրեսիոն համատեքստ → Կոմպրեսիոն կարգավորումներ** (`/dashboard/context/settings`), Արդյունքների ոճերի բաժին՝ մեկ տող յուրաքանչյուր ոճի համար on/off անջատիչով և մակարդակի ընտրիչով: Ոճերը ներարկվում են, երբ սեղմումն ինքնին միացված է (էջի հիմնական անջատիչը, `enabled`): Այն** Ավտո-պարզության շրջանցում** անջատիչը միացված է** Քարանձավային մարդ** էջ (`/dashboard/context/caveman`), իր** Ելքային ռեժիմ** քարտ. Ծրագրային առումով, սեղմման կազմաձևը պահպանում է ընտրությունը հետևյալ կերպ.

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Back-compat. քանի դեռ `outputStyles` դատարկ է, ժառանգական `cavemanOutputMode.enabled` կարգավորումը քարտեզագրվում է `terse-prose` `cavemanOutputMode.intensity`: Այնուհետև բլոկը սկսվում է `[OmniRoute Output Styles]` նշիչով, որտեղ ժառանգական `applyCavemanOutputMode()` ներարկիչը գրել է `[OmniRoute Caveman Output Mode]`: Մարկերի տակ տեքստը համընկնում է en, pt-BR, es, de, fr, it, ru, id և vi-ի ժառանգական ներարկման հետ; ja-ում և zh-ում այն կրում է մեկ հավելյալ տարածություն սահմանների դրույթից առաջ: `terse-prose` թարգմանվում է pt-BR, es, de, fr, it, ru, zh, ja, id և vi, ուստի հարցումը, որի լուծված լեզուն `hu` է, ստանում է անգլերեն տեքստը, որտեղ ժառանգական ներարկիչն օգտագործել է իր հունգարերենը:

Ելքի ոճի լեզվի ընտրություն (`resolveOutputStyleLanguage()` in `outputStyles/apply.ts`). միացված `languageConfig.enabled` ով, `autoDetect` նմուշառում է վերջին օգտվողի հաղորդագրությունը հարցման `messages` զանգվածում, որն ունի տեքստ (լարային բովանդակություն կամ դրա բովանդակության մասերի `text` ) և գործարկում է Caveman շարժիչի դետեկտորը (`detectCompressionLanguage()`): Դետեկտորը վերադարձնում է `zh` տեքստի համար Han նիշերով և առանց kana; հակառակ դեպքում այն վերադարձնում է `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` և `id` ից որն ունի ամենաշատ ակնարկը համընկնում, իսկ `en` երբ ոչ մեկը չի համապատասխանում — տեքստին, այն չի կարող դասակարգել, ստանում է անգլերեն, երբեք `defaultLanguage`, և `vi` երբեք չի հայտնաբերվում, թեև ոճերը ուղարկվում են `vi` : Responses API մարմինն իր շրջադարձերը պահում է `input` ում, որը նմուշառված չէ, ուստի այն ստանում է `defaultLanguage`, այնուհետև անգլերեն: Երբ `messages` ում օգտվողի ոչ մի հաղորդագրություն չունի տեքստ, կամ `autoDetect` անջատված է, կիրառվում է `defaultLanguage`, այնուհետև անգլերենը: Եթե `languageConfig.enabled` անջատված է, լեզուն անգլերենն է — բացառությամբ այն դեպքերի, երբ հարցումին չի կիրառվում կոմպրեսիոն կոմբինացիա (հարցման երթուղային համակցված կոմբինատը կամ լռելյայն սեղմման կոմբինատը chatCore հետ է `languageConfig.enabled` ներկառուցված կուտակված խողովակաշարի համար). Combo-ի փաթեթները, հակառակ դեպքում կոմբինատի առաջին փաթեթը, որը `en` `defaultLanguage`, մինչդեռ պահպանված `autoDetect` (միացված է լռելյայնորեն) դեռ գործում է: Caveman ներածման շարժիչն ընտրում է իր կանոնների փաթեթի լեզուն — տեքստի յուրաքանչյուր մասի համար և, ավտոմատ հայտնաբերելով անջատված, փակում է `enabledPacks` վրա:

Ոճի × լեզվի մատրիցը ամրացված է `tests/unit/compression/output-styles-i18n-matrix.test.ts` ով. կատալոգի յուրաքանչյուր ոճ պետք է մուտքագրվի թեստի `BASELINE_LANGUAGES` ում; ոճը, որը լոկալով փակված չէ, պետք է ուղարկի pt-BR թարգմանություն (տեղականով փակված `terse-cjk` ազատված է այս կանոնից), եթե այն նշված չէ `KNOWN_ENGLISH_ONLY` ում, որը կարող է պարունակել միայն թարգմանություններ չունեցող ոճեր — և ոճը ձախողում է թեստը, երբ կորցնում է լեզուն, որն իր `BASELINE_LANGUAGES` մուտքագրված է: Ոճ ավելացնելու համար տե՛ս [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### Գործիքի արդյունքների սեղմում

`compressToolResult()` `open-sse/services/compression/toolResultCompressor.ts` ում սեղմում է գործիքի արդյունքի տեքստը** 5 ռազմավարություն** . Այն փորձում է դրանք այս հերթականությամբ, և առաջին միացված ռազմավարությունը, որի ստուգումը համապատասխանում է բովանդակությանը, որոշում է արդյունքը.

1. **`fileContent`** 3 կամ ավելի տողերի բովանդակություն, որոնցում առնվազն մեկ տող, անտեսելով առաջատար նահանջը, սկսվում է `import `, `export `, `function `, `class `, `const `, `let `, `var ` կամ `return ` (հիմնաբառը գումարած բացատ) կամ `if`, `for` կամ `while` տողերով, որին հաջորդում է `(` կամ ` (` e20 տողերով, իսկ վերջինը՝ el20 տողերով, միջին նշված.
2. **`grepSearch`** բովանդակությունը `<path>:<digits>:` ձևի առնվազն մեկ տողով, որտեղ առաջին կետից առաջ տեքստը բացակայում է, պահպանում է միայն այդ տողերը, առավելագույնը 30, որին հաջորդում է հետագա համընկնումների և համընկնող ֆայլերի ցանկը. յուրաքանչյուր մյուս տողը հանվում է: Այդպիսի մեկ տողը բավական է ռազմավարությունը գործարկելու համար, այնպես որ մատյան գիծը, որը սկսվում է ժամանակի դրոշմով, ինչպիսին `12:30:45` է, նույնպես հաշվում է:
3. **`shellOutput`** ելքը, որը պարունակում է ANSI CSI հաջորդականություն (`ESC[` այնուհետև թվանշաններ կամ կետ-ստորակետեր, ապա տառ, ինչպես գունային կոդերում) կամ `$` որին հաջորդում է տեքստի ցանկացած կետում բացատ, կորցնում է այդ հաջորդականությունները (այլ փախուստները, օրինակ՝ `ESC[?25l` կամ OSC պատուհանի վերնագրի հաջորդականությունը, պահվում են) և պահպանում են 5-ով կրկնվող տողերը, և պահպանում են կրկնվող տողերը: Քանի որ այս ստուգումը կատարվում է `json` և `errorMessage` առաջ, JSON կամ սխալի ելքը, որը պարունակում է նման `$` երբեք չի հասնում դրանց, քանի դեռ `shellOutput` միացված է:
4. **`json`** 2000 նիշից ավելի JSON ծանրաբեռնվածությունը, որը սկսվում է `{` կամ `[` (ըստ ցանկության բացատից հետո) և վերլուծում է ամփոփված. 7-ից ավելի տարրից բաղկացած զանգվածը պահպանում է իր առաջին 5 և վերջին 2 տարրերը և ընդհանուր թիվը, իսկ օբյեկտը պահում է իր առաջին 20 ստեղները՝ յուրաքանչյուր ներկառուցված օբյեկտի կամ զանգվածի երկարությունը փոխարինված է `{…N keys}` ով (a) `_remaining_<N>_keys` մարկեր, որը հաշվում է առաջին 20-ից անցած ստեղները: Սկալարային արժեքները պատճենվում են ամբողջությամբ, ուստի 20 ստեղներից կամ ավելի քիչից բաղկացած օբյեկտը, առանց ներդիր արժեքների, միայն նորից նահանջ է արվում — փոքրացված մեկը ստանում է նիշեր և մնում է անփոփոխ:
5. **`errorMessage`** ելք, որը պարունակում է, ցանկացած վայրում և ցանկացած տառի դեպքում, `error:`, `error ` (բառը, որը հաջորդում է բացատին, ինչպես `no error found` ում), `[error]`, `exception:`, `exception `, `[exception]` կամ `traceback` պահպանում է իր առաջին տողը, հաջորդ 10 տողերը և վերջին 3-ը, նրանց միջև եղած տողերի փոխարեն `… [N frames elided] …` նշիչով: Նշիչը հայտնվում է միայն այն դեպքում, երբ առաջին տողին հաջորդում է ավելի քան 13 տող, ուստի 14 կամ ավելի տողերի սխալի արդյունքը չի կրճատվում (12 կամ 13 տողում վերջին 3 կրկնվող տողերն արդեն պահպանված են):

Այն բանից հետո, երբ ռազմավարությունը համընկնում է, նույնիսկ այն, որը ոչինչ չի փրկում, հետագա ռազմավարությունները չեն փորձարկվում: Երբ համընկնող ռազմավարությունը չի պահպանում գնահատված նշաններ (երկարությունը ÷ 4, կլորացված վերև), — օրինակ՝ 25 տողով կամ ավելի քիչ կոդային ֆայլ, կամ 2000 նիշից ավելի JSON զանգված՝`compressAggressive()` `saved` կամ ավելի քիչ —, `compressAnthropicToolResultBlock()` `compressToolResult()` պահպանում է գործիքի սկզբնական արդյունքը. վերադարձնում է այդ ռազմավարության արդյունքը: Գործիքների արդյունքի քայլը վերջին բառը չէ. շարժիչի հետադարձ ամփոփիչը դեռ կարող է կրճատել `tool` կամ `function` հաղորդագրությունը ավելի քան 8192 նիշ (`maxTokensPerMessage`, 2048, 4 անգամ):

#### Երբ օգտագործել

Գործիքի արդյունքի սեղմումը ագրեսիվ շարժիչի 1-ին քայլն է (`compressAggressive()` in `open-sse/services/compression/aggressive.ts`), այնպես որ այն աշխատում է ագրեսիվ ռեժիմով և ցցված խողովակաշարի `aggressive` քայլով: Այն սեղմում է OpenAI-ի ձևի `tool` և `function` հաղորդագրությունները և տեքստը Anthropic `tool_result` բլոկների ներսում: Յուրաքանչյուր ռազմավարություն `aggressive.toolStrategies` ի տակ ունի իր սեփական անջատիչը, որը լռելյայն միացված է: Վահանակի վահանակում անջատիչները գտնվում են Caveman էջում** Ընդլայնված** դիտել, երբ սեղմումը միացված է, իսկ լռելյայն ռեժիմը ագրեսիվ է:

### Խցանված խողովակաշար

Գործում է կուտակված ռեժիմը** մի քանի շարժիչներ հաջորդականությամբ** — սովորաբար սկզբում RTK (60-90% խնայողություն գործիքի թողարկման վրա), այնուհետև Caveman-ը մնացած տեքստի վրա (~ 46% մուտքագրման խնայողություն): Կազմված, դա է** 78-95% իրավասու միջակայք** (տե՛ս Վերևում գտնվող խնայողությունների մաթեմատիկան). `1 - (1 - 0.60..0.90) × (1 - 0.46)` միջինում է ≈ 89%:

#### Ինչպես է այն աշխատում

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### Երբ օգտագործել

Օգտագործեք կուտակված ռեժիմը հետևյալի համար.

- Գործիքների համար ծանրաբեռնված աշխատանքային հոսքեր (գործակալական կոդավորում, հետազոտություն)
- Ծախսերի նկատմամբ զգայուն խմբաքանակի մշակում
- Երբ Ձեզ անհրաժեշտ է առավելագույն խորհրդանշական խնայողություն

Խցանված խողովակաշարերը կազմաձևվում են գլոբալ `stackedPipeline` սեղմման պարամետրի միջոցով կամ անվանակոչված կոմպրեսիոն կոմբինացիայի միջոցով, որը վերագրված է երթուղային համակցվածին (տես Per-Combo Override վերևում) — ոչ թե auto-combo `modePack` ի միջոցով (այդ դաշտը միայն վերակշռում է ավտոմատ համակցված մոդելի ընտրությունը, իսկ `stacked` վավեր փաթեթի անուն չէ):

## Կոմպրեսիայի համակցությունների վերասահմանումներ

Դուք կարող եք վերասահմանել կոմպրեսիայի գլոբալ ռեժիմը **յուրաքանչյուր համակցության համար առանձին**՝ տարբեր օգտագործման դեպքերում վարքագիծը ճշգրտելու նպատակով.

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Սա օգտակար է հետևյալ դեպքերում.

- **Ծրագրավորման համակցություններ**. երկարատև աշխատաշրջանների համար օգտագործեք `aggressive` ռեժիմը
- **Արագ հարցուպատասխանի համակցություններ**. արագ պատասխանների համար օգտագործեք `lite` ռեժիմը
- **Գործիքների ինտենսիվ օգտագործմամբ համակցություններ**. առավելագույն խնայողության համար օգտագործեք `stacked` ռեժիմը
- **Արտադրական համակցություններ**. քեշավորում ապահովող մատակարարների դեպքում վերասահմանումն անջատված թողեք. մշտապես միացված՝ քեշավորումը հաշվի առնող ճշգրտումն ավտոմատ կերպով իջեցնում է `aggressive`/`ultra` ռեժիմները մինչև `standard`
  (ընտրելի `cache-aware` ռեժիմ գոյություն չունի)
