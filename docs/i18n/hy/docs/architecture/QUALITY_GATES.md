աստիճանական ելակետ, թե անցնել/ձախողվել քաղաքականություն, և արդյոք արգելափակում է կառուցումը, թե ունի խորհրդատվական բնույթ։

## Դարպասի գույքագրման և կատարման պրոֆիլներ

### Թեկնածուների ընդունելություն

CI և Quality Gates-ի աշխատանքային հոսքերը յուրաքանչյուրն արձակում է կայուն դատավճիռ՝ `Gate / CI` և `Gate / Quality`: Նրանց տարբերակված ընդունելության քաղաքականությունը թվարկում է յուրաքանչյուր վերին հոսքի աշխատանքը որպես պահանջվող կամ խորհրդատվական: Կիրառելի պահանջվող աշխատանքը պետք է հաջողվի. բացակայող, չեղարկված, բաց թողնված, սպասող և անհայտ արդյունքները չեն կարող հաստատել PASS: Միայն փաստաթղթերի կամ միայն կատալոգի համար նախատեսված վավեր դասակարգումը կարող է անկիրառելի դարձնել ծածկագրի գոտին. սովորական նախագիծը PR ընդունված թեկնածու չէ: `hotfix` պիտակը չի հրաժարվում ապացույցներից:

Երկու աշխատանքային հոսքերն էլ ընդգրկում են PRs main/release մասնաճյուղերում, մղում դեպի `main`, ձեռքով ուղարկում և միավորում խմբային իրադարձություններ: Հրել, ուղարկել և միաձուլել ամբողջ ընտրությունը: Վստահելի Mergify հերթի նախագիծը նաև գործարկում է կիրառելի `full-code`/`full-code-e2e` աշխատանքներ. սովորական PRs բաց թողնել դրանք: Նախքան ձեռքով միաձուլումը, կատարեք ամբողջական հաղորդագրություն ճշգրիտ թեկնածուի վերաբերյալ: `release/**` ի հղումները չեն սկսում այս աշխատանքային հոսքերը. Release-Green-ը դիտում է միաձուլված բազան առանձին (`docs/ops/RUNNER_BOX.md` → Hosted lane): Forks-ը և միաձուլման խմբերը օգտագործում են հյուրընկալված վազորդներ այն աշխատանքների համար, որոնք այլ կերպ ընտրում են ինքնուրույն վազորդներ. Բավարար հյուրընկալող հզորությունը պետք է ստուգվի նախքան թողարկումը:

Սովորական PR վարում է արագ ընտրությունը: Ընդունման քաղաքականության `full-code` և `full-code-e2e` ուղիները (E2E, ինտեգրում, փաթեթի արտեֆակտ, Electron ծուխ, Bun SQLite, էկոհամակարգ և արձանագրության հաճախորդներ) աշխատում են միայն Mergify հերթի նախագիծով կամ ամբողջական գործարկումով՝ `gh workflow run ci.yml --ref <branch>`:

Յուրաքանչյուր JSON անդորրագիր նույնականացնում է դուրս գրված SHA, աշխատանքային հոսքի գործարկումը և փորձը: CLI ն մերժում է checkout/event SHA անհամապատասխանությունը: Աշխատանքային հոսքի թեստերը կապում են քաղաքականության անդամակցությունը դատավճիռների աշխատանքի `needs` ցանկին, այնպես որ նոր կամ հեռացված գոտին չի կարող լուռ անհետանալ: Անդորրագրերը ծածկում են իրենց սեփական աշխատանքային հոսքը, այլ ոչ թե հրապարակումը, տեղակայումը կամ առկա խորհրդատվական սկաների ներքին կառուցվածքը: Մասնաճյուղի կանոններով պահանջվող կիրառելի ստուգումներ կատարելը առանձին վարչական փոփոխություն է. նրանց աշխատանքի սահմանումն ինքնին չի պաշտպանում մասնաճյուղը:

`API Route Typecheck` աշխատանքի հոսքի անկախ ստուգում է՝ ինչպես ընդհանուր դատավճիռներից, այնպես էլ տեղական դիտորդի ստատիկ պրոֆիլից դուրս: Ստուգեք դրա արդյունքը առանձին՝ ճշգրիտ թեկնածուի համար: `.github/workflows/api-route-typecheck.yml` աշխատում է PRs ով `main` կամ `release/**` մեջ, հրում է դեպի մասնաճյուղային ընտանիք, ձեռքով ուղարկում և `merge_group` տիպի `checks_requested` իրադարձություններ: Այն չունի ուղու զտիչ: Միավորել խմբերը ստուգել `merge_group.head_sha`; այլ իրադարձություններ ստուգեք `github.sha`: Բոլոր իրադարձությունները օգտագործում են նույն API ախտորոշիչ դարպասի և դարպասի միավորի թեստերը: PR բազայի վերաթիրախները պահանջում են նոր ստուգում. body/title խմբագրումները օգտագործում են միայն դիտարկման համար նախատեսված `Admission not requested / API Route Typecheck` անվանումը և չեն կարող փոխարինել ընդունելության ստուգումը:

### Պահպանված ապացույցներ ընդունման կրճատիչում

`scripts/quality/validate-release-acceptance.mjs` նվազեցնում է մատակարարված պլանը և դրա դրսևորումները. այն չի սահմանում, որ պլանն ընդգրկում է ամբողջական թողարկման խողովակաշարը: Նրա հաշվետվությունները հստակորեն սահմանում են `releaseAcceptance: false`, նույնիսկ երբ այդ պլանը `VERIFIED` է: `release-acceptance.yml` աշխատանքային հոսքը դեռ օգտագործում է ստվերային հարմարանքներ, այլ ոչ թե իրական կառուցվածք, փաթեթ, բեռնախցիկ կամ առաջխաղացման անդորրագրեր:

CLI ն պահանջում է `--evidence-root` ստուգել պահպանված ապացույցները: Ֆայլերը լուծվում են որպես `<evidence-root>/<artifact_id>/<member>` և հեշացված են որպես SHA-256: PASS գրառումն առանց ապացույցների, բացակայող կամ փոփոխված ֆայլի, անապահով ուղու կամ սիմվոլկի կանխում է ստուգումը: Բացակայող ֆայլերը համարժեք չեն դատարկ հաջողված տեղեկամատյաններին: Առկա SHA/run/attempt ստուգումները մնում են անկախ. համապատասխան բայթերը չեն կարող փրկել հնացած անդորրագիրը: Ֆայլի ամբողջականությունը կատարման իսկության կամ արտեֆակտի առաջմղման ապացույց չէ:

### DAST սպառում է ստուգված CI կառուցվածքը

Պահանջվող `dast-smoke` CI աշխատանքը կանչում է `.github/workflows/dast-smoke.yml` `build` ից հետո: Այն հետևում է նույն code/draft ընտրությանը, ինչ կառուցումը, ներառյալ աջակցվող պատառաքաղը PRs, թողարկում-թիրախային PRs և միաձուլման խմբեր: DAST բացակայող, ձախողված, չեղարկված կամ անսպասելիորեն բաց թողնված աշխատանքը արգելափակում է `Gate / CI`: Կրկնակի օգտագործման աշխատանքային հոսքը չունի անկախ PR/dispatch ձգան; Ձեռքով վավերացումն օգտագործում է CI ի առաքումը, այնպես որ կառուցումը և սպառողը մնում են մեկ գործարկման մեջ:

`scripts/ci/next-build-provenance.mjs` կնքում է հաջորդ ամբողջ արտեֆակտը իր tar digest-ով, repository/event/run, արտադրողի փորձով, head/base/checkout/tree, աշխատանքային հոսքի նույնականացումներով, lockfile-ով, ճշգրիտ Node version/ABI, հարթակով և փաթեթավորմամբ: DAST `needs.build.outputs` ից ընտրում է ID անփոփոխ արտեֆակտը, պահանջում է ներբեռնման ամփոփման ստուգում և ինքնուրույն զտում է ZIP արտադրողի դիջիստի հետ՝ նախքան `scripts/ci/unpack-ci-build.py` միջոցով արդյունահանվող իր երկու թույլատրելի անդամները: Մանիֆեստը և tar արխիվը պետք է նաև համապատասխանեն անկախ արտադրողի արդյունքներին, նախքան Հաջորդ ծառը հանելը: Այն երբեք չի որոնում վերջին հաջող մասնաճյուղի կառուցումը: Մասնակի կրկնությունը կարող է վերօգտագործել նույն արտադրողի փորձը, երբ նրա ID ու բոլոր մուտքերը դեռ համընկնում են. անդորրագիրը գրանցում է երկու փորձերը:

Սպառողը մնում է հյուրընկալված Linux վրա՝ միայն կարդալու պահուստի թույլտվությամբ և պահեստի գաղտնիքներ չունենալով: Այն տեղադրում է արտադրողի ճշգրիտ Node տարբերակը, այնուհետև CLI ն `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` ով հավաքում: `scripts/build/standaloneInput.mjs` մերժում է բացակայող առանձին սերվերը ցանկացած հետադարձ կառուցումից առաջ. նորմալ տեղական CLI կառուցումները պահպանում են իրենց առկա հետադարձ կապը: Սերվերի պատրաստակամությունը, Schemathesis-ը և promptfoo-ն պետք է հաջողության հասնեն անփոփոխ 25 րոպե աշխատանքային սահմանաչափի շրջանակներում: Ծագման անդորրագիրը ապացուցում է մուտքի ինքնությունը և բայթերը, այլ ոչ թե հաջողված DAST սկանավորումը: Արտեֆակտի ժամկետի ավարտը, վազքի ընդհատումը կամ ձախողված սկաները մնում են թերի կամ ձախողված ապացույցներ. այն չի կարող դառնալ PASS խորհրդատվական փաթեթի միջոցով:

### UI կատարողական հզորություն

CI իրականացնում է UI ամբողջական գույքագրումը որպես չորս `test-vitest` մատրիցային բեկորներ, որոնցից յուրաքանչյուրում կա առավելագույնը երկու աշխատող յուրաքանչյուր բեկորից և գործող 15 րոպեանոց աշխատանքի վերջնաժամկետը: Առաջին բեկորը նաև գործարկում է MCP/autoCombo Vitest փաթեթը: Աշխատանքի պահանջվող արդյունքը ներառում է մատրիցայի յուրաքանչյուր ոտքը. մեկ բեկորի ձախողումը կամ չեղարկումը չի կարող հաստատել թեկնածուի ընդունելություն:

Գիշերային դիտորդը պահպանում է առանձին ճշգրիտ թեկնածուական անդորրագիր UI յուրաքանչյուր բեկորի համար, ներառյալ MCP կատարումը առաջին անդորրագրում: Բոլոր չորս անդորրագրերը, տեղեկամատյանները և կատարման նույնականացումը պարտադիր են: Տեղական `npm run test:vitest:ui` դեռ ընտրում է ամբողջական փաթեթը. մեկ `--shard` գործարկումը միայն մասնակի ապացույց է:

### Միավոր ծածկույթի հավաքածու

Տասներկու միավոր բեկորները հավաքում են V8 ծածկույթ իրենց առկա փորձարկման ընթացքում: Հաջող բեկորը գործարկում է `scripts/ci/compact-v8-coverage.mjs` ՝ սեղմելու բնօրինակ ֆայլերը՝ առանց Ստամբուլի միջանկյալ հաշվետվություն ստեղծելու: Ծածկույթի վերջնական աշխատանքը ստուգում է բոլոր տասներկու մանիֆեստները թեկնածու SHA, գործարկման ժամանակի, աղբյուրի արմատի և տվյալների հեշերի դեմ, այնուհետև գործարկում է c8-ի թղթակիցները և լուսաբանման առկա շեմերը: Մուտքերը պահպանում են c8-ի ֆայլի անվանման գլոբալ կարգը. յուրաքանչյուր բեկորի նախնական միաձուլումը վտանգավոր է խառը function/block ծածկույթի համար: Բացակայող, սխալ ձևավորված կամ անհամատեղելի բեկորները չեն ընդունվում: Անհաջող փորձարկման բեկորները առանձին պահպանում են չմշակված ախտորոշիչ ծածկույթը. այն չի կարող մտնել վերջնական միաձուլման մեջ:

### Միավորի կատարման առաջընթացի անդորրագրերը

Համօգտագործվող `test:unit:ci:shard` հրամանը գրանցում է `primary`, `dashboard` և `serial` փուլերը `scripts/ci/unit-progress-reporter.mjs` միջոցով: Նորմալ թեստի հաշվետվությունը մնում է հասանելի: Միայն մետատվյալների համար նախատեսված առանձին անդորրագիրը գրանցում է յուրաքանչյուր ֆայլի սկիզբն ու ավարտը, իսկ 30 վայրկյան տևողությամբ սրտի բաբախյունը ցույց է տալիս այն ֆայլերը, որոնք դեռ ակտիվ են և դրանց անցած ժամանակը: Այն գրանցում է միայն թույլատրված կատարման մետատվյալները. թեստի նկարագրությունները, ելքը, սխալի մարմինները և ամբողջական միջավայրը սերիականացված չեն:

CI պահպանում է JSONL ֆայլերը որպես `unit-progress-ci-<run>-<attempt>-<shard>`: Աշխատանքի դադարեցումը կարող է կանխել հետագա վերբեռնումը. արդեն իսկ արձակված սրտի զարկերը մնում են ախտորոշիչ ապացույց: Սրտի զարկերի բացակայությունը կարող է նաև արտացոլել վազորդի արգելափակված կամ դադարեցված գործընթացը: Այս անդորրագրերը պահպանում են առկա թեստի ընտրությունը, միաժամանակությունը, ժամկետները և ելքի կարգավիճակը. դրանք թեկնածուական դատավճիռներ չեն։

### Միավորել հերթ

`queue` պիտակը ուղարկում է PR Mergify հերթին (`.mergify.yml`): Mergify-ը բացում է PR նախագիծը `mergify/merge-queue/` մասնաճյուղում, CI այնտեղ գործարկում է ամբողջական ընտրությունը, իսկ սկզբնական PR միաձուլվում է, երբ անցնում են `Gate / CI`, `Gate / Quality` և `Merge integrity (changelog + generated skills)` :

Mergify-ը գրում է իր հերթի ամփոփագիրը նախագծի նկարագրության մեջ: Body/title-only `pull_request` `edited` իրադարձությունները օգտագործում են գործարկման հատուկ համաժամանակյա խումբ և չեն կրկնում դասակարգումը, թեստային մատրիցները, միաձուլման ամբողջականությունը կամ ընդունման վճիռը: Միայն դիտարկման համար նախատեսված չեկերի անունները չեն կարող փոխարինել `Gate / CI` կամ `Gate / Quality`: Թիրախային բազան փոխող խմբագրումը պահանջում է թեկնածուի նոր վավերացում:

Dequeue-ից հետո մղումը միշտ չէ, որ պահանջում է PR: Մեկնաբանեք դրա վերաբերյալ `@mergifyio queue` :

### Ստատիկ սկանավորման գույքագրում

npm-alias-ի տարբերակված գույքագրումը և ստատիկ սկանավորման անդամակցությունը գործում են `config/quality/gate-manifest.json` ում: Գործարկեք `npm run check:gate-manifest` սկրիպտների անունները և ճշգրիտ հրամանները `package.json` դեմ վավերացնելու համար; լրացումները, հեռացումները և հրամանի դրեյֆը ձախողվում են և՛ տեղական կեռիկը, և՛ փոփոխության դասակարգման աշխատանքները CI ում: Այլանունը աշխատանքային հոսքի աշխատանք, մատրիցային օրինակ կամ փորձնական դեպք չէ. այս հաշվումները չպետք է ներկայացվեն որպես փոխարինելի:

Օգտագործեք `npm run quality:scan -- --list` կամ `npm run quality:scan:fast -- --list` ՝ ստուգելու ընտրված կեղծանունները՝ առանց դրանք գործարկելու: Վազողը կանչում է npm մուտքի կետը, ուստի դրա գործարկման ժամանակը (ներառյալ Bun, որտեղ կազմաձևված է) պահպանվում է: Մանիֆեստը գրանցում է այլանուններ այդ պրոֆիլներից դուրս՝ որպես առանձին կանչված, և սպասարկման հրամաններն արգելված են միայն կարդալու սկանավորման պրոֆիլներում:

Այս պրոֆիլները ծածկում են միայն ստատիկ սկանավորումը: Նրանք չեն հավաստում արտադրանքի թեստերը, ծածկույթը, փաթեթավորումը, արտաքին ստուգումները կամ թեկնածուի թողարկման ամբողջական ընդունումը: Աշխատանքային հոսքի ընդունումը օգտագործում է կապված `config/quality/admission-policy.json` և `scripts/quality/admission-verdict.mjs`: Ազատման դիտորդի պրոֆիլները մնում են առանձին. ինքնուրույն ստուգել դրանց կիրառելի չեկերն ու անդորրագրերը: Դիտորդի ամբողջական ստատիկ հրամանները հայտարարված են `config/quality/release-green-static-profile.json` ում, ներառյալ `audit:deps`, մուտացիայի թեստի ընտրությունը և թարգմանության ստուգումները: Բեռնիչը վավերացնում է npm հրամանները package.json և մոդելավորված CI/Quality հայտարարագրերի դեմ. այն մերժում է դրեյֆը՝ shell նշանները որպես փաստարկներ գործարկելու փոխարեն: Պահանջվող սկաների SKIP/INCOMPLETE ելքը չի կարող հաստատել PASS: Պրոֆիլը գրանցում է իր արտաքին բացառումները և չի փոխարինում հյուրընկալված ծածկույթին, փորձարկման մատրիցներին, փաթեթին կամ տեղակայման ապացույցներին: Ստորև բերված արձակի գույքագրումը հղում է, այլ ոչ թե ապացույց, որ դարպասը իրականում վազել է:

Սցենարները ապրում են `scripts/check/` (քաղաքականության դարպասների) և `scripts/quality/` (չեղջավոր շարժիչի) տակ: CI ճշմարտության աղբյուրը `.github/workflows/ci.yml` է:

### Հրապարակված բազային փաստաթղթերի առողջություն

`.github/workflows/i18n-base-health.yml` հետևում է փաստաթղթերի առողջությանը `main` և `release/v*` ընտրված հրումներից և ձեռքով ուղարկելուց հետո: Դրա զտիչները ներառում են փաստաթղթեր, արմատային Markdown, `llm.txt`, թարգմանչական state/configuration և համապատասխան i18n գործիքներ: Մեկ `Published base documentation health` աշխատանքը օգտագործում է հյուրընկալված Ubuntu-ն և հինգ րոպեանոց վերջնաժամկետ: Այն իրականացնում է միայն կարդալու վավերացում և գրում է ախտորոշիչ անդորրագիր՝ առանց կախվածության տեղադրման, թարգմանության կամ պետական ընդունման:

`scripts/i18n/check-base-health.mjs` պահանջում է զրոյական աղբյուր-հեշ, բացակայող-թիրախ, թիրախ-հեշ, հնացած թարգմանություն և հատված-քեշի անհամապատասխանություններ: Այն նաև հաստատում է ընթացիկ հիմնական document/locale շրջանակը և դրա գրանցված ծագումը: Անվավեր համատեքստը, թերի լուսաբանումը կամ ընդհատված ստուգիչը առաջացնում է `INCOMPLETE`; հաստատված դրեյֆը արտադրում է `FAIL`: Երկուսն էլ վերադարձնում են ձախողված ելքի կարգավիճակ: Անդորրագիրը պարտավորվում է վճարել SHA, աշխատանքային հոսքը, գործարկել և փորձել, և պահվում է որպես `i18n-base-health-<sha>-<run>-<attempt>`:

Սա հրապարակված բազայի անկախ դիտարկումն է։ Այն չի ավելացնում PR կամ միաձուլման խմբի իրադարձություն, պահանջվող PR ստուգում, npm կեղծանուն կամ ստատիկ սկանավորման պրոֆիլի անդամ: Հիմնական ստուգիչը նաև արգելափակում է բոլոր հինգ դասերը բացարձակ ռեժիմում: Սովորական PR պատրաստումը մնում է առանձին ընդունելությունից: Հաջող վերբեռնումը չի կարող ձախողված առողջական արդյունքը վերածել PASS:

Սովորական PR օգտագործում է `--preflight` `--baseline-evidence` ի կողմից ստեղծված բազային զեկույցով: Այն կարող է առկախ թողնել անգլերեն աղբյուրը միայն այն դեպքում, երբ թարգմանության ամբողջական գրառումը և իրական թիրախային բայթերը անփոփոխ լինեն հենց այդ բազայից: Նոր թիրախի կամ հատվածի քեշի անհամապատասխանությունները դեռ արգելափակված են, և թերի ապացույցները չեն կարող թույլատրել նախապատրաստումը: Զեկույցը բացահայտում է `preparationPending` և `mergeReady` առանձին-առանձին. հաջող նախապատրաստումը պատրաստ չի դարձնում սպասող թարգմանությունները միաձուլման: Թարմացրեք ազդակիր հայելիները կազմված թեկնածուի մեջ մինչև ընդունելությունը: Mergify-ի վստահելի հերթի թեկնածուն, `merge_group`, ճյուղային մղումները և ձեռքով CI գործարկումները օգտագործում են բացարձակ ստուգիչը՝ առանց `--warn` կամ ժառանգական ձախողումների ներման: Բացակայող թիրախային հեշերը և ջնջված ձայնագրված հիմնական ֆայլերով կրճատված շրջանակը չեն կարող հաջող բացարձակ դատավճիռ առաջացնել:

### Թողարկեք PR արագ ճանապարհը (`quality.yml`)

`.github/workflows/quality.yml` լրացնում է CI main/release PRs ում, մղում է դեպի `main`, ուղարկում և միավորում խմբերը: PRs օգտագործում է ճանապարհով զտված արագ ստուգումներ: Մշտապես անջատված կրկնօրինակ կառուցվածքը հեռացվել է. իրական build/package/boot չեկերը մնում են CI ում: Միավոր հավաքակազմը և վիտեստը գործում են միայն CI ում (`Unit Tests (N/12)` և `Vitest`):

| Աշխատանք                                         | Շրջանակ                                                                                                                                                                                                                     | Արգելափակում                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API docs refs և docs-all                                                                                                                                                                                     | Այո՛                        |
| `Fast Quality Gates`                             | Կոդ PRs; ստատիկ ստուգումներ, տիպի ստուգում, վահանակի տիպի ստուգում, ազդակիր միավորի թեստեր                                                                                                                                  | Այո՛                        |
| `Forgotten sibling tests`                        | Կոդ PRs; փոփոխված մոդուլները, որոնք հետագծվել են ստատիկ սպառողների և թեկնածուների քրոջ կամ քույրերի թեստերի վրա. տակառի և դինամիկ ներմուծման ուղիները հաղորդվում են որպես խորհրդատվական ախտորոշում՝ նշված բացառություններով | **Խորհրդատվական**           |
| `No new ESLint warnings`                         | Կոդ PRs; suppressions-aware lint guard                                                                                                                                                                                      | Այո, ներառյալ պատառաքաղները |
| `Merge integrity (changelog + generated skills)` | Ոչ նախագիծ PRs; փոփոխության մատյան և գեներացված հմտությունների համաժամեցում                                                                                                                                                 | Այո, ներառյալ պատառաքաղները |

#### Մոռացված եղբայրների կամ քույրերի թեստերի հաշվետվություն

`npm run check:forgotten-sibling-tests` աշխատում է որպես `Fast Quality Gates` ի խորհրդատվական քայլ և նորից օգտագործում է ներմուծման լուծիչը փորձարկման ազդեցության քարտեզի հետևում: Յուրաքանչյուր փոփոխված արտադրական մոդուլի համար այն հայտնում է դետերմինիստական `changed module/symbol -> static consumer -> candidate sibling test` շղթաներ, երբ թեկնածուի թեստը բացակայում է ձգման պահանջի տարբերությունից: Markdown-ի ամփոփագիրը և JSON արդյունքը պահպանվում են որպես `forgotten-sibling-tests` աշխատանքային հոսքի արտեֆակտ՝ նախքան որևէ արգելափակման տեղակայումը չափորոշման համար:

Տակառի վերաարտահանումը և դինամիկ ներմուծումը միայն լուծման ախտորոշիչ են. նրանք երբեք արգելափակող գտածո չեն ստեղծում: Վերանայված բացառությունները ապրում են `config/quality/forgotten-sibling-allowlist.json` ում: Յուրաքանչյուր գրառում պետք է անվանի սպառողի և թեկնածուի թեստը, տա կոնկրետ հիմնավորում և կապի GitHub խնդիր կամ ձգողական հարցում: Սխալ մուտքերը փակ են: Բացառությունները չեն կարող ճնշել ջնջված թեկնածուի թեստը կամ տարբերությունը, որն ավելացնում է `.skip`/`.todo`; պնդումների թուլացումը և այլ դիմակավորումը մնում են անկախ արգելափակող `check:test-masking` դարպասի սեփականությունը:

| `check:build-typecheck`           | Ամբողջական հավելվածի արտադրության տեսակի ստուգում `tsconfig.build.json` միջոցով (`src`, `open-sse`, `packages`, `bin`, `scripts`, `electron/**/*.d.ts`), մակերեսային `typecheck:core` ի 27 ֆայլերի թույլտվության ցանկը և վահանակի դարպասը չեն ծածկում: Տարբերություններ `config/quality/build-typecheck-baseline.json` դեմ; մեկ (ֆայլ, կոդ) նոր կամ բարձրացված հաշվարկը ձախողվում է, ավելի ցածր հաշվարկը խնդրում է ձեզ արագացնել: `--update` հրաժարվում է, քանի դեռ գործարկումը պարունակում է նոր կամ բարձրացված զույգ, եթե `--force-regressions` չհանձնվի, և հրաժարվում է նոր խլացված ֆայլից, եթե `--force-nocheck` չհանձնվի, ուստի բազային գծի ընդլայնումը կանաչ ստանալու համար և մշտական լռություն տրամադրելը երկու առանձին կանխամտածված գործողություններ են: Մերկ `--force` մերժվում է: Նաև սկանավորում է `@ts-nocheck` ի կառուցման շրջանակը `config/quality/ts-nocheck-baseline.json` դեմ, քանի որ այն օգտագործող ֆայլը բացարձակապես չի հայտնում ախտորոշման մասին և հակառակ դեպքում անտեսանելի կլիներ յուրաքանչյուր դարպասի համար: | Այո՛                                          |

#### Երկու տիպի ստուգման ծրագրեր տարբեր կերպ են պատասխանում

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) և `check:build-typecheck` տարբեր ծրագրեր են կազմում տարբեր տարբերակների ներքո, և նույն ֆայլը կարող է մեկում մաքուր լինել, իսկ մյուսում՝ լի սխալներով:

`tsconfig.build.json` սահմանում է `"strict": false`, ուստի `noImplicitAny` անջատված է: Հիմնական կազմաձևը կազմում է ընտրված 27 ֆայլի թույլտվությունների ցանկ՝ ավելի խիստ ընտրանքներով և հետևում է յուրաքանչյուր մուտքի ներմուծման գրաֆիկին, այնպես որ ֆայլերը, որոնք երբեք չեն հայտնվում կառուցման ծրագրում, դեռ ստուգվում են այնտեղ:

Հետևանքը կարևոր է, երբ դատում ենք, թե արդյոք ֆայլը մուտքագրված է.**`check:build-typecheck` ի ներքո զրոյական ախտորոշումը չի նշանակում զրո** . `@ts-nocheck` ի 26 ֆայլից հեռացնելը ցույց տվեց, որ դրանցից 23-ը մաքուր են build ծրագրում; Նրանցից տասնվեցը բացահայտեցին մոտ 120 անուղղակի սխալներ խիստ սխալի մեջ: Ստուգեք երկուսն էլ՝ նախքան ֆայլը մաքուր կանչելը:

### Աշխատանք՝ `docs-sync-strict`

`main` կամ `release/**` ին ուղղված խնդրանքների դեպքում այս աշխատանքը գործում է միայն ոչ սևագիր (կամ վստահելի հերթում) թեկնածուների համար, որոնք դասակարգված են որպես փաստաթղթեր կամ կոդի փոփոխություններ: Այն նաև աշխատում է ոչ PR CI իրադարձությունների վրա. Այս աշխատանքային հոսքի մղիչ ձգանն ընդգրկում է միայն `main`, ոչ թե `release/**`: Քայլը, որը դուրս է գալիս ոչ զրոյից, արգելափակում է աշխատանքը. Ստորև բերված միայն հաշվետվության բացահայտումները և փաստաթղթավորված բացառությունները չեն:

#### `check-ui-value-drift` — հնացած-թարգմանական դարպաս

Բռնում է i18n մեկ ռեգրեսիան, որը մյուս դարպասները կառուցվածքային առումով չեն կարող տեսնել. անգլերեն արժեքը վերագրվում է, իսկ _նախորդ_ անգլերենից ստացված թարգմանությունները մնում են հետևում, այնպես որ ոչ անգլերեն օգտվողները շարունակում են կարդալ վստահորեն ձևակերպված, այժմ սխալ պատճենը:

Սա առաքվել է իրական: `oauthModal.googleOAuthWarning` վերագրվել է, երբ Antigravity մուտքի օգնականը վայրէջք կատարեց (#5203);**43 տեղանքից 39-ը** պահպանեց տեքստը, որով ասվում էր օպերատորներին «պատճենել ամբողջական URL և տեղադրել այն ներքևում» — հոսքը, որը չի կարող ավարտվել այդ մատակարարի համար: Այն աննկատ մնաց մինչև #8463 քանի որ.

- `sync-ui-keys` լրացնում է միայն այն բանալիները, որոնք կան **բացակայում է** , երբեք այնպիսիք, որ կան **հնացած** ;
- `check-ui-keys-coverage` հաշվում է բանալին _presence_, ուստի հնացած թարգմանությունը գնահատվում է որպես ծածկված;
- `check-translation-drift` հետևում է `docs/i18n/<locale>/**.md` փաստաթղթերին, ինչպես նաև — այն երբեք չի կարդում `src/i18n/messages/*.json`: Արգելափակում է `docs-sync-strict` աշխատանքը 2026-09 թվականների վերահամաժամեցումից հետո. խմբագրել → `npm run i18n:run -- --files=<doc>` հիմնական փաստաթուղթը (հատվածի մակարդակի, էժան):

**Տարբերությունների գիտակցում, ոչ բազային հիմքով:** Այն համեմատում է `en.json` միաձուլման հիմքում աշխատող ծառի հետ; յուրաքանչյուր ստեղնի համար, որի անգլերեն արժեքը փոխվել է, ցանկացած տեղանք, որը դեռևս անձեռնմխելի թարգմանություն է պահում, հնացած է: Սա միտումնավոր **սառեցնում է նախկինում գոյություն ունեցող պարտքը** — ի տարբերությունը չի կարող բացահայտել, թե որ հին անգլերենից է առաջացել երկարամյա թարգմանությունը, ուստի դարպասը դատում է միայն այն, ինչ վերաբերում է ընթացիկ փոփոխությունին: Այլընտրանքը (յուրաքանչյուր բանալիով հեշ ելակետային գիծ) կարժենա ~ 600 KB գեներացված ֆայլ, 3 × ամենամեծ գոյություն ունեցող բազային գիծը, որը խառնվում է յուրաքանչյուր i18n PR վրա:

Այն բավարարելու երկու եղանակ.

1. թարմացնել ազդակիր թարգմանությունները, կամ
2. դրեք դրանք `__MISSING__:<new english>` — գործարկման ժամանակի վրա, այնուհետև սպասարկում է շտկված անգլերենը (`src/i18n/request.ts::deepMergeFallback`, #7258) և թարգմանության հիմնական հերթերը:

Եթե լարը **իմաստը** փոխվել, նախընտրել **բանալին վերանվանելով** Նոր բանալին չի կարող ժառանգել հնացած թարգմանություն: Դա այն օրինակն է, որն օգտագործվում է #8463 :

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Արժեքի դրեյֆը և նոր բանալիների դարպասները կիսում են մեկ անփոփոխ համեմատություն `scripts/i18n/resolve-ui-diff-base.mjs` ից: Աշխատանքային հոսքը փոխանցում է նույն բազան, բազային ծայրը և թեկնածու SHAs երկու ստուգումներին: PR/base-retarget, push և merge-group runs-ը օգտագործում են իրենց իրադարձությունների համատեքստը: Թեկնածու մասնաճյուղի առաքումը պահանջում է դրա ճշգրիտ բաց PR կամ հստակ `i18n_base_sha` մուտքագրում: `main` ի կամ `release/vX.Y.Z` ի առաքումը կամ պլանավորված դիտարկումն առանց այդ մուտքագրման համեմատում է վերջին կատարումը իր առաջին ծնողի հետ. դա ամբողջ ժառանգած թարգմանչական պարտքի աուդիտ չէ: Տեղական կանչը պահանջում է բացահայտ համեմատական բազա, օրինակ վերը նշված `BASE_REF` հրամանը:

Համեմատության բացակայող կամ երկիմաստ համատեքստը, անընթեռնելի կամ անվավեր պահանջվող կատալոգը և փոփոխված թեկնածուն արտադրում են `INCOMPLETE` ելքի կոդով **2** , ներառյալ նախազգուշացման ռեժիմում: Կատալոգի ընթերցումները օգտագործում են `scripts/i18n/read-ui-catalog.mjs`; կարդալու ձախողումները չեն փոխարինվում դատարկ օբյեկտներով: Ոչ անհասանելի բազան, ոչ էլ թերի մուտքագրումը չեն հաստատում PASS:

  չափում է յուրաքանչյուր թվային դարպաս այնպես, ինչպես դա անում է CI-ն, և արտածում յուրաքանչյուր դարպասի մնացած պահուստը
  (`scripts/quality/baseline-headroom.mjs`)։ Գիշերային `baseline-headroom` առաջադրանքը հրապարակում է
  աղյուսակը աշխատանքային հոսքի գործարկման ամփոփագրում և վերբեռնում դրա JSON/Markdown հաշվետվությունը որպես
  `baseline-headroom-<run_id>`՝ պահպանելով այն 90 օր։ Նախազգուշացման և կրիտիկական տողերը ցույց են տալիս այն դարպասները,
  որոնք գտնվում են իրենց սահմանաչափից մինչև 10% հեռավորության վրա կամ արդեն գերազանցել են այն։ Դիտարկեք այս հաշվետվությունները՝
  որպես բյուջեների սպառման վաղ նախազգուշացում. ուսումնասիրեք խնդրահարույց դարպասի `_rebaseline_*` նշումները։ Առաջադրանքն այլևս
  չի ստեղծում կամ թարմացնում մշտական issue. #12149-ը պահպանում է հաշվետվությունների նախկին պատմությունը։

  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` մատյանում).
- **խորհրդատվական** — գլոբալ ընդհանուր քանակը՝ սառեցված ելակետային արժեքի համեմատ։ Ժառանգված շեղումը երբեք չի
  ձախողեցնում անմեղ PR-ը․ շեղումը հետևվում է՝ թողարկման համադրման ժամանակ շտկվելու համար, և վերահսկվում է
  ազատ պաշարի առաջադրանքի կողմից։

`check:file-size`-ը բազային հղումն օգտագործում է իր կանոններով (`scripts/check/check-file-size.mjs`, #8522).

և ֆայլը ձախողված է համարում միայն այն դեպքում, երբ այն աճում է՝ գերազանցելով իր ելակետային վերին սահմանից
(`frozen` / `testFrozen`, կամ `cap` / `testCap`՝ ելակետում չներառված ֆայլի համար) և բազային չափից
ավելի մեծ արժեքը։ Հետևաբար բազայում արդեն շեղված ֆայլը երբեք չի ձախողեցնում դրա հետ կապ չունեցող PR-ը։

`check:boundary:ratchet`-ը նույն կանոնը կիրառում է իր միակ թվի նկատմամբ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`)․ PR իրադարձությունների դեպքում և՛
`quality.yml`-ի արագ դարպասները, և՛ `ci.yml`-ի lint առաջադրանքը փոխանցում են PR-ի բազային SHA-ն, բազային commit-ը
չափվում է `git archive` արտահանումից, իսկ PR-ը ձախողվում է միայն այն դեպքում, երբ դրա `open-sse → src` եզրերի
քանակը գերազանցում է `metrics.boundaryOpenSseToSrc`-ի և բազային տարբերակի քանակի առավելագույնը։ Շեմից
բարձր բազային շեղման մասին հաղորդվում է (`base drift herdado`), սակայն այն երբեք չի ձախողում անմեղ PR-ը․ push → main-ը
պահպանում է բացարձակ շեմը, իսկ չլուծվող բազային SHA-ի դեպքում նախազգուշացմամբ կիրառվում է այդ շեմը։

`workflow_dispatch` գործարկումները, release-green ամբողջական ստուգումը և գիշերային ազատ պաշարի առաջադրանքը PR-ի բազային տարբերակ
չունեն և պահպանում են բացարձակ (գլոբալ) համեմատությունը։ Ծածկույթը, կրկնօրինակումն ու տիպերի ծածկույթն առայժմ մնում են գլոբալ

## Ratchet-ի ելակետային մակարդակ (`quality-baseline.json`)

Ratchet շարժիչը (`scripts/quality/check-quality-ratchet.mjs`) կարդում է `quality-baseline.json`-ը
և համեմատում այն նոր հավաքված `quality-metrics.json`-ի հետ։ Ցանկացած չափիչի՝ իր epsilon-ից
ավելի վատթարացումը ձախողում է build-ը։

Ներկայումս հետևվող չափիչները՝

| Չափիչ                 | Ուղղություն | Նշանակություն                                  |
| --------------------- | ----------- | ---------------------------------------------- |
| `eslintWarnings`      | `down`      | ESLint-ի նախազգուշացումների քանակը չպետք է աճի |
| `coverage.statements` | `up`        | Հրահանգների ծածկույթը չպետք է նվազի            |
| `coverage.lines`      | `up`        | Տողերի ծածկույթը չպետք է նվազի                 |
| `coverage.functions`  | `up`        | Ֆունկցիաների ծածկույթը չպետք է նվազի           |
| `coverage.branches`   | `up`        | Ճյուղերի ծածկույթը չպետք է նվազի               |

Իրական բարելավումից հետո ելակետային մակարդակը թարմացնելու համար՝

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` դրոշը ներկայումս չափված արժեքները գրում է `quality-baseline.json`-ում։
Commit արեք այս ֆայլը չափիչը բարելաված փոփոխության հետ միասին։ Չափիչը բարելավող,
սակայն ելակետային մակարդակը չթարմացնող PR-ը կբացահայտվի `--require-tighten`-ի միջոցով (փուլ 6A.5,
իրականացումը սպասվում է)։

### CodeQL արգելանիվ. թեկնածուների ընդունելության և պահեստի գույքագրում

CI `codeql-scan` `node scripts/check/check-codeql-ratchet.mjs --candidate` CodeQL մուտքը կախվածության `codeql-admission` միջոցով `codeql.yml` `Gate / CI` պահանջում է երկու արդյունք: Որակը պահպանում է իր սեփական թվային ստուգումները, բայց չի հարցնում սկաներին մինչև արտադրողի ավարտը. Միայն `Gate / Quality` թեկնածուի ամբողջական ընդունում չէ: CodeQL պահանջվում է միայն փաստաթղթեր ունեցող թեկնածուների համար:

`config/quality/codeql-admission-policy.json` ի քաղաքականությունն ընտրում է Գործողություններ, C/C++, JavaScript/TypeScript և Python, հարցումների փաթեթի լռելյայն, հեռավոր սպառնալիքի մոդել և կառուցման ռեժիմ՝ ոչ: Արտադրողի նախնական թռիչքը մերժում է սպասվող ակտիվացման գրառումը և ճյուղավորում է բացահայտ թիրախային ցանկից դուրս: Ընթացիկ թիրախները հիմնական են, և release/v3.8.54. պայմանագրի թեստերը համեմատում են այս վերջավոր ցանկը և պահպանման հրում գործարկիչը փաթեթի տարբերակի հետ. հաջորդ թողարկումը պետք է վերանայվի: CI ի գոյություն ունեցող ավելի լայն թողարկման PR ձգան պահպանվում է, բայց չբռնկված թիրախը հայտնում է HOLD մինչ արդյունահանումը, այլ ոչ թե չչափված PASS ստանալու:

Յուրաքանչյուր մատրիցային աշխատանք գրանցում է իր իրական SARIF վերբեռնման ID, լեզուն, կատեգորիան, գործարկումը և փորձը, զանգահարողի աշխատանքային հոսքի ինքնությունը, իրադարձությունը ref/head/base/merge SHA և քաղաքականության հեշը: Կախված աշխատանքը ներբեռնում է միայն այս գործարկման անդորրագրերը և վավերացնում է արտեֆակտի ամփոփումները: Այն պահանջում է բոլոր չորս կատեգորիաները, հաջողակ արտադրող և յուրաքանչյուր ճշգրիտ վերբեռնման ավարտված մշակում: Այն օգտագործում է API ի sarif_id ֆիլտրը, այլ ոչ թե ճյուղի վրա հայտնաբերված վերջին վերլուծությունը: Մասնակի կրկնությունները կարող են վերօգտագործել նույն առաջադրանքի և թեկնածուի ավելի վաղ փորձից հաջողված կատեգորիաները՝ պահպանելով արտադրության փորձը. ձախողված ընթացիկ արտադրողը չի կարող կրկին օգտագործել նախկին կանաչ ապացույցները:

CodeQL գործողությունը սպասում է մշակման, բայց դրա ամրացված իրականացումը կարող է նախազգուշացնել և շարունակել կարգավիճակի ընթերցման ձախողումից կամ սպառված սպասելուց հետո: Հետևաբար, ընդունելությունը կրկին ստուգում է վերամշակումը: Բացակայող կատեգորիաները, սպասվող մշակումը, ձախողված կամ չեղարկված աշխատանքները, հնացած ինքնությունը, թերի էջադրումը կամ անհասանելի APIs արտադրում են HOLD և ելք 2: Սկաների անկախ աշխատանքային հոսքի համար ֆիքսված սպասել չի մնում: Չսկանավորված PR չի կարող անցնել, քանի որ զգուշացման հարցումը վերադարձրել է 0: `metrics.codeqlAlerts.value` բարձր չափված թիվը դուրս է գալիս 1-ից; բազային գիծը չի բարձրացվում մեկ այլ ճյուղի ահազանգերը կլանելու համար: [Վերբեռնման կարգավիճակը և վերլուծության որոնումը](https://docs.github.com/en/rest/code-scanning/code-scanning) :

Անդորրագիրը գրանցում է վերբեռնման և վերլուծության IDs, կատեգորիաները, գործիքների տարբերակները, ref/SHA, ելակետային և ազդանշանային համարները: SARIF identity/result հաշվարկը, նվազագույն կանոնների հաշվարկը և զգոնության ճշգրիտ դեպքերը մնում են պարտադիր: PR/analysis ինքնությունը կրկին ստուգվում է ընդունելուց առաջ: Այս ստուգումները սահմանում են կազմաձևված կատեգորիայի ծածկույթ, այլ ոչ թե յուրաքանչյուր արդյունահանված աղբյուրի ֆայլի գույքագրում: C/C++ առանց կառուցման արդյունահանումը չի ներառում ծրագրի կառուցման ընթացքում ստեղծված ծածկագիրը: Աղբյուրի բացառումները դեռևս վերանայման կարիք ունեն, իսկ ներդրողի վերագրումը պետք է համադրելի ճշգրիտ բազային ապացույցների:

`codeql-maintenance.yml` տրամադրում է ակտիվ արձակման սեղմման սկանավորումներ և շաբաթական գրաֆիկ՝ առանց PR/main արտադրողների կրկնօրինակման: `nightly-codeql-inventory.yml` պահում է պահեստի բազային գիծը առանձին՝ `--strict-measurement` ով և ձախողմամբ, երբ չափումն անհասանելի է: Տեղական ժառանգության կոլեկցիոների նազելի բաց թողնելը թեկնածուի ընդունելություն չէ: Խստացումը մնում է բացահայտ `--update` ստուգված ցածր գլոբալ հաշվարկից հետո:

Ընդլայնված աշխատանքային հոսքը չպետք է հրապարակվի, քանի դեռ կանխադրված կարգավորումը կազմաձևված է. GitHub մերժում է այդ համակցությունը: Նրա տարբերակված քաղաքականությունը մնում է առկախ, մինչև վերանայված վարչական անցումը հետ չկարդացվի: Հրապարակումից առաջ օպերատորը ամրացնում է պահոցը, head/base/tree, policy/patch/rollback հեշերը և դիտարկվող տեղադրման վիճակը; `node scripts/quality/codeql-producer.mjs verify-admin-readback` ստուգում է մատակարարված ակնկալվող և փաստացի JSON գրառումները: Սա տեխնիկական պահակ է, այլ ոչ թե օպերատորի հաստատում կամ փոխարինում է թարմ հետադարձ կապ ստանալու համար: PR նշանը երբեք չի պահանջում Ադմինիստրացիայի մուտք: Տարածումը և սկաների ցանկացած փոփոխություն պահանջում են առանձին ընթերցում, գումարած իրական PR, պատառաքաղ և միավորման խմբերի համատեղելիության ապացույցներ:

Forks-ը օգտագործում է հյուրընկալված վազորդներ, վճարումներ՝ առանց մշտական հավատարմագրերի, ոչ մի install/build նախագիծ արտադրողի մեջ և ոչ ժառանգական պահեստային գաղտնիքներ: GitHub աջակցում է SARIF վերբեռնումը pull_request իրադարձության համար իր կրճատված պատառաքաղի նշանով; առաջին անգամ ներդրման կատարման հաստատումը մնում է GitHub քաղաքականությունը: Երբեք մի օգտագործեք pull_request_target՝ անվստահելի կոդ գործարկելու համար: Հաստատեք փաստացի նշանների թույլտվությունները, analysis_key-ը և բոլոր կատեգորիաների միջավայրերը վերահսկվող դեղձանիկում՝ նախքան միգրացիան ավարտված համարելը: [Պատառաքաղի վերբեռնման կանոններ](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible), [հակասական կարգավորումների ռեժիմներ](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows) :

**Ազատումները օպերատորի կոչն են (Hard Rule #14)** — երբեք չի մերժում CodeQL ազդանշանը՝ առանց աշխատանքից ազատման մեկնաբանությունում տեխնիկական հիմնավորումը գրանցելու. `won't fix` վերին հոսանքով արձանագրության պահանջի համար, `used in tests` թեստային սարքի համար, `false positive` ախտահանիչի համար CodeQL չի կարող տեսնել (նախադեպ՝ `docs/security/ERROR_SANITIZATION.md`):

## Թեստերի կրկնափորձի քաղաքականություն (WS5.4, v3.8.49)

Կրկնափորձը սահմանվում է յուրաքանչյուր գործարկիչի համար առանձին, երբեք՝ որպես համընդհանուր կանոն. համընդհանուր կրկնափորձը իրական ռեգրեսիաները վերածում է անտեսանելի անկայուն խափանումների.

| Գործարկիչ        | Քաղաքականություն                                                                                                                    | Պատճառ                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Playwright (e2e) | `retries: 1`՝ միայն CI-ում, `trace: on-first-retry`-ով                                                                              | Բրաուզերի/ցանցի ժամանակային վարքն իսկապես ոչ որոշակի է. հետագծմամբ մեկ կրկնափորձը անկայուն խափանումը դարձնում է ախտորոշելի արտեֆակտ |
| Vitest           | Համընդհանուր կրկնափորձ ՉԿԱ։ Ապացուցված անկայուն թեստը ստանում է հստակ, թեստին հատուկ կրկնափորձ (տեսանելի diff-ում, ստուգված PR-ում) | Կարանտինային ցանկը պահում է ռեպոզիտորիում՝ երբեք չդարձնելով այն ոչ թափանցիկ                                                         |
| node:test (unit) | Կրկնափորձ ՉԿԱ՝ երբեք                                                                                                                | Անկայուն միավորային թեստը սխալ է թեստում. շտկեք այն, այլ ոչ թե պարզապես նորից գործարկեք                                             |

Թիրախային SLO-ները՝ անկայունության հեռաչափության ներդրումից հետո (WS5.2/5.3). յուրաքանչյուր թեստի համար անկայունության մակարդակը՝ <1%
(«շտկել հիմա» շեմ), յուրաքանչյուր խողովակաշարի համար անցման մակարդակը՝ ≥95%։ Ոլորտի հղումային արժեքներ են.
վերաչափարկեք դրանք՝ ըստ մեր սեփական չափումների։

վերջնակետում, այսինքն՝ հետընթացն առաջացել է միաձուլումների ՀԱՄԱԿՑՈՒԹՅՈՒՆԻՑ, և ոչ մի առանձին PR այն չի վերարտադրում
իր սեփական ճյուղում, շտկումը պատկանում է **թողարկման պատասխանատուին՝ մեկ անգամ, թողարկման
ճյուղում**. նախընտրեք առանձնացումը/վերակառուցումը, իսկ ելակետը փոխեք միայն փաստաթղթավորված
հիմնավորման գրառմամբ։ Երբեք համակցությունից առաջացած շեղումը մի վերագրեք մասնակցի PR-ին և երբեք
մի փոխեք ելակետը յուրաքանչյուր PR-ի համար (դա թաքցնում է իրական ռեգրեսիաները)։ Նախ տարբերակեք պատճառը.
կարմիր կարգավիճակը վերարտադրեք մաքուր վերջնակետի նկատմամբ՝ փորձնական worktree-ում, նախքան ենթադրելը, որ այն առաջացրել է ձեր PR-ը։

## Սահմանափակիչների նվազեցումների ամրագրում՝ նվազման ուղղությունը (#8584)

Սահմանափակիչն ավտոմատ է միայն կիսով չափ, ընդ որում՝ սխալ կեսով։ Սահմանաչափի **բարձրացումը**
ձեռքով JSON-ի խմբագրում է, որը տևում է տասը վայրկյան և կարմիր PR-ն ապաշրջափակելու ամենաարագ եղանակն է։
Այն **նվազեցնելու** համար որևէ մեկը պետք է գործարկի `--update` և commit անի արդյունքը, իսկ մինչև
`bank-ratchet-shrinks` առաջադրանքի ներդրումը դա չէր անում ոչ մի workflow։ Չափված հետևանքը
(2026-07-25). 18 սառեցված ֆայլ արդեն գտնվում էր նոր ֆայլերի 800 տող սահմանաչափի մակարդակին կամ դրանից ներքև, իսկ վատագույնը՝
132× (`src/shared/validation/schemas.ts`, 19 տող՝ 2,523 սահմանաչափով), բարդության վերին շեմը
մոտավորապես 37 ելակետի փոփոխման նշումների ընթացքում բարձրացել էր `1794 → 2169`՝ ունենալով ճիշտ մեկ
նվազում (−1), իսկ «հաջորդ շրջափուլում խստացնել `--update`-ի միջոցով» գրառվել էր 31 անգամ և կատարվել՝
մեկ անգամ։ Սահմանաչափը, որը շարունակում է գոյություն ունենալ իրեն առաջացրած կոդից ավելի երկար, յուրաքանչյուր ավարտված
տրոհում աննկատ վերածում է աճի թույլտվության՝ ֆայլը հաջորդը խմբագրող անձի համար։

`nightly-release-green.yml` → **`bank-ratchet-shrinks`** առաջադրանքը փակում է այդ շրջափուլը.

|               |                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Գործարկվում է | `schedule` (օրական 3×) + `workflow_dispatch` — միտումնավոր **ոչ** `push`-ով                                              |
| Չափում է      | ամենաբարձր `release/vX.Y.Z`-ը՝ նույն լուծման և ներմուծումից պաշտպանության մեխանիզմով, ինչ `release-green`-ը              |
| Գրում է       | `check:file-size --update` և `check:complexity-ratchets --update` (երկուսն էլ կառուցվածքով միայն նվազեցնող են)           |
| Ստուգում է    | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                 |
| Առաքում է     | թողարկման ճյուղի նկատմամբ միշտ արդիական մեկ PR՝ հարկադրաբար թարմացվող, երբեք ավելորդ հաղորդագրություններով չծանրաբեռնված |

Ամրագրումը կատարվում է խմբաքանակով, ոչ թե յուրաքանչյուր push-ի դեպքում, քանի որ այն չունի ուշացման պահանջ
(8 ժամվա ընթացքում ամրագրված նվազեցումը լիովին ընդունելի է), մինչդեռ յուրաքանչյուր միաձուլման գործարկումը բազմիցս կվերակառուցեր
PR-ի ճյուղը միաձուլման արշավների ընթացքում և ամեն անգամ կվճարեր ESLint-ի ամբողջական անցման արժեքը։ Հայտնաբերումը
շարունակում է կատարվել push-ի ժամանակ (`release-green`), իսկ խմբաքանակով կատարվում է միայն ամրագրումը։

### Անվտանգության ստուգիչը

Առաջադրանքն առանց վերահսկման գրում է ելակետերում, ուստի հենց `verify-ratchet-bank.mjs`-ն է դա
ընդունելի դարձնում։ Այն համեմատում է `--update`-ից հետո ստացված ծառը `HEAD`-ի հետ և **ընդհատում է առաջադրանքը
նախքան որևէ commit-ի ստեղծումը**՝ առանց PR բացելու, եթե բոլոր փոփոխությունները հետևյալներից որևէ մեկը չեն.

- `frozen` / `testFrozen` թվային գրառում, որը **նվազեցվել** կամ **հեռացվել** է
- `complexity-baseline.json` → `count`՝ **նվազեցված**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value`՝ **նվազեցված**

Ցանկացած այլ բան հանգեցնում է ձախողման՝ թվի բարձրացումը, գրառման ավելացումը, `cap`/`testCap`-ի փոփոխությունը կամ
`_rebaseline_*` նշման ջնջումը/վերագրումը (այդ նշումները յուրաքանչյուր վերին շեմի գոյության պատճառների աուդիտային պատմությունն են
և պահվում են նույն `frozen` օբյեկտում, ինչ ֆայլերի գրառումները)։
Բոտը, որը կարող է բարձրացնել սահմանաչափը, հաստատ ավելի վատ կլիներ, քան առկա վիճակը։ Ռեգրեսիայից պաշտպանություն՝
`tests/unit/verify-ratchet-bank.test.ts`։

Առաջադրանքը երբեք push չի անում դեպի `release/*`. PR-ը միաձուլում է մարդը, ուստի սխալ չափումը
չի կարող հայտնվել համակարգում առանց ստուգման։

## Թույլատրելի բացառությունների ցանկի քաղաքականություն

Նախկինում առկա խախտումների դեպքում ձախողվել չկարողացող յուրաքանչյուր ստուգիչ օգտագործում է սառեցված թույլատրելի բացառությունների ցանկ
(օրինակ՝ `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)։ Քաղաքականությունը հետևյալն է․

**Ուղղեք բուն պատճառը․ թույլատրելի բացառությունների ցանկն օգտագործեք միայն այն դեպքում, երբ խախտումը նախկինում առկա է եղել և
հնարավոր չէ այն ուղղել նույն PR-ում։**

Թույլատրելի բացառությունների ցանկում գրառում ավելացնելիս՝

1. Ներառեք հիմնավորմամբ մեկնաբանություն։
2. Հղում կատարեք հետևման խնդրին (օրինակ՝ `// #3498 — Phase 2 feature, not yet implemented`)։
3. Հեռացրեք գրառումը խախտումն ուղղող նույն PR-ում․ հնացած գրառումը, որն այլևս
   չի ճնշում ակտիվ խախտումը, ինքնին թերություն է (6A.3-ի հնացած կիրարկման ստուգումը,
   իրականացվելուց հետո, կձախողի որբացած գրառում պարունակող ստուգիչը)։

**Մի՛** ավելացրեք գրառումներ թույլատրելի բացառությունների ցանկում՝ թեստերն ավելի արագ անցկացնելու համար։ Ընդլայնվող
թույլատրելի բացառությունների ցանկով հաջողված ստուգիչը որակի կեղծ զգացողություն է ստեղծում։

### Երբ ստուգիչը ձախողվում է ձեր PR-ում

1. **Ուշադիր կարդացեք ստուգիչի ելքը**․ այն ճշգրտորեն հայտնում է, թե որ ֆայլը կամ սիմվոլն է խախտել
   կանոնը։
2. **Ուղղեք խախտումը**․ ստուգիչների մեծ մասը ֆայլային համակարգի դետերմինիստական ստուգումներ են, որոնք հաջողվում են, հենց որ
   կոդը ճիշտ է։
3. **Եթե խախտումը նախկինում առկա է եղել** (այսինքն՝ դուք չեք այն ներմուծել, սակայն ստուգիչն այժմ
   ընդգրկում է այն), թույլատրելի բացառությունների ցանկում ավելացրեք գրառում՝ հիմնավորող մեկնաբանությամբ և հետևման խնդրի հղմամբ։
4. **Եթե ստուգիչը կապանվագ է** (ծածկույթ, ESLint-ի զգուշացումներ, կրկնօրինակում, բարդություն),
   ձեր փոփոխությունը վատթարացրել է չափանիշը։ Ուղղեք հիմքում ընկած խնդիրը կամ (հազվադեպ) գործարկեք
   `npm run quality:ratchet -- --update`, եթե փոփոխությունը միտումնավոր է, և չափանիշի
   վատթարացումն ընդունելի է, սակայն PR-ի նկարագրության մեջ փաստաթղթավորեք պատճառը։
5. **Խորհրդատվական ստուգիչները** (`continue-on-error: true`) տեղեկատվական են․ դրանք չեն արգելափակում
   միավորումը, սակայն հայտնվում են CI ամփոփագրում։ Միևնույն է, ուղղեք դրանք։

## Նոր ստուգիչի ավելացում

1. Ստեղծեք `scripts/check/check-<name>.mjs` (կամ `.ts`)։ Քաղաքականության ստուգիչներն ավարտվում են 0/1 կոդով։
   Ռատչետ տեսակի ստուգիչները չափանիշ են գրում `quality-metrics.json`-ում՝ `collect-metrics.mjs`-ի միջոցով։
2. Ավելացրեք `"check:<name>": "node scripts/check/check-<name>.mjs"`-ը `package.json`-ում և
   համաժամացրեք կեղծանունն ու դրա ճշգրիտ հրամանը `config/quality/gate-manifest.json`-ում։
   Նույն համաժամացումը կիրառեք նաև գոյություն ունեցող վավերացման կեղծանունը փոփոխելիս կամ հեռացնելիս։
   Գործարկեք `npm run check:gate-manifest`․ նախնական commit-ի hook-ը և CI-ի փոփոխությունների դասակարգումը
   ապահովում են այս պայմանագրի պահպանումը։
3. Միացրեք այն `.github/workflows/ci.yml`-ում՝ համապատասխան job-ի ներքո
   (քաղաքականություն → `lint` կամ `docs-sync-strict`, ռատչետ → `quality-gate`)։
4. Եթե այն ունի թույլատրվածների ցանկ, կիրառեք `reportStaleEntries()`-ը
   `scripts/check/lib/allowlist.mjs`-ից, որպեսզի հնացած գրառումները հայտնաբերվեն ինքնաբերաբար։
5. `tests/unit/build/`-ում գրեք թեստ, որն ընդգրկում է ստուգիչի հայտնաբերման տրամաբանությունը։
6. Թարմացրեք այս փաստաթուղթը (համապատասխան job-ի աղյուսակում ավելացրեք տող)։

## Գործակալների գործիքակազմ․ LSP-in-the-loop (ըստ ցանկության)

CI ստուգիչներից բացի, OmniRoute-ը ներառում է **ըստ ցանկության միացվող** `agent-lsp` հիմնակմախք

## Ռացիոնալացման հերթացուցակ (ROI-ի վերանայում — Փուլ 9 Ալիք 3)

Այս գույքացանկը 2026-06-17-ին համադրվել է `ci.yml`-ի հետ (նախորդ տարբերակում բացակայում էին
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence`): Համադրված բազմության ROI-ի վերանայումը
բացահայտեց ռացիոնալացման հետևյալ թեկնածուները։ **Միավորումները CI-ի մեխանիկական
փոփոխություններ են, իսկ միացումները/հեռացումները քաղաքականության որոշումներ են, որոնք վերապահված են օպերատորին։** Ստորև նշվածներից
դեռ ոչինչ կիրառված չէ։

**Վերևում նաև չփաստաթղթավորված են** (խորհրդատվական, թույլ ազդանշան)՝ `docs-lint` առաջադրանքը (markdownlint + Vale, ամբողջ առաջադրանքը՝ `continue-on-error`) և անկախ սկաների `semgrep.yml` / `scorecard.yml` հոսքերը։ CodeQL-ն այժմ `Gate / CI`-ի ներքո ունի պարտադիր արտադրող և ընդունման առաջադրանքներ՝ վերը նշված ակտիվացման պահանջներով։ `semgrepFindings: 0`-ը կա `quality-baseline.json`-ում, բայց միացված չէ `ci.yml`-ի արգելափակող սահմանին․ չափանիշն այժմ գործնական կապ չունի։

### Միավորում / կրկնությունների վերացում (մեխանիկական, ավելի ցածր ռիսկով)

Յուրաքանչյուր թեկնածու 2026-06-17-ին ստուգվել է գործող դարպասների վիճակի համեմատ (վստահել, բայց ստուգել)։
Մի քանի «ակնհայտ» միավորումներ պարզվեց՝ թաքցնում են տեխնիկական պարտք և **չեն** կարող անմիջապես փոխարինել եղածը։

- **`check:docs-sync`-ը գործարկվում է երկու անգամ**՝ առանձին `lint` առաջադրանքում և կրկին `check:docs-all`-ի (`docs-sync-strict`) ու husky-ի pre-commit hook-ի ներսում։ ✅ **ԿԱՏԱՐՎԱԾ Է** — առանձին `lint` գործարկումը հեռացվել է։
- **CVE սկանավորում** — ❌ **Մաքուր միավորում ՉԷ։** `audit:deps`-ն արգելափակում է կրիտիկական զգուշացումները և թերի աուդիտները բոլոր հինգ lockfile-երում, իսկ բարձր աստիճանի զգուշացումները ընթացիկ քաղաքականության համաձայն ներկայացնում է որպես նախազգուշացումներ։ Մինչդեռ `check:vuln-ratchet`-ը (osv) ձախողվում է միայն գրանցված ելակետային մակարդակի համեմատ _հետընթացի_ դեպքում և, երբ պահանջվում է, մերժում է բացակայող չափումները։ Իմաստաբանությունը տարբեր է. `audit:deps`-ը հեռացնելը կվերացներ բացարձակ կրիտիկական դարպասը և փաթեթների անկախ աուդիտի ապացույցները։ Պահել երկուսն էլ։
- **Ցիկլերի հայտնաբերում** — ✅ **ԿԱՏԱՐՎԱԾ Է** (#15159 G-01/G-02)։ Այստեղի հին տեքստը `check:cycles`-ն անվանում էր «կանաչ, ընտրովի» դարպաս և հիմնավորում էր դրա արգելափակող կարգավիճակի պահպանումը նրանով, որ `check:circular-deps`-ը (dpdm) հաղորդում էր 91 ցիկլի մասին։ Այդ կանաչ վիճակը **կեղծ կանաչ** էր. `check:cycles`-ը սկանավորում էր 5 ենթապանակ (450 ֆայլ), համընկնում էր միայն ստատիկ `import|export … from`-ին և բաց էր թողնում բոլոր `@/` ու `@omniroute/open-sse/` սահմանիչները, ուստի չէր կարող տեսնել դինամիկ import-ի և alias-ի ցիկլերը, որոնք գերակշռում էին շտեմարանում։ Ուղղված է. դարպասն այժմ շրջանցում է `src` + `open-sse`-ը (5023 ֆայլ), TypeScript AST-ից հավաքում է սահմանիչները (այսպիսով՝ `import("…")`-ը հաշվվում է, իսկ տիպային դիրքում գտնվող `typeof import("…")`-ը՝ ոչ) և լուծում է tsconfig-ի `paths`-ը։ Այն գտնում է **14** ցիկլ, ոչ թե 0։ Քանի որ նախկինում գոյություն ունեցող 14 ցիկլերը հնարավոր չէ ուղղել դարպասի PR-ում, `check:cycles`-ն այժմ **շեմապահ** է (`--ratchet`, առաստաղը՝ `metrics.cycles.value = 14`՝ `quality-baseline.json`-ում, `direction: down`)՝ այն արգելափակում է ցանկացած _հետընթաց_, իսկ թիվը կարող է միայն նվազել։ CI-ն գործարկում է `npm run check:cycles:ratchet`։ Նվազեցումն իրականացվում է **A-01**-ի հետ միասին։ `check:circular-deps`-ը (dpdm) մնում է խորհրդատվական՝ որպես ավելի լայն երկրորդ կարծիք։
- **Բարդություն** — ✅ **ԿԱՏԱՐՎԱԾ Է** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`)՝ ESLint-ի մեկ անցում, հաշվարկ ըստ ruleId-ի, որպեսզի ցիկլոմատիկ+max-lines և կոգնիտիվ ելակետային մակարդակները մնան անկախ։ Առանձին `check:complexity` / `check:cognitive-complexity` հրամանները պահպանվում են տեղային `--update`-ի համար։
- **`/api` հակահալյուցինացիոն ստուգում** — ✅ **ԿԱՏԱՐՎԱԾ Է** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`)՝ `src/app/api`-ի FS-ի մեկ գույքագրում, openapi-routes + docs-symbols-ը շարունակում են առանձին հաշվետվություններ ներկայացնել։ Առանձին հրամանները պահպանվում են տեղային գործարկումների համար։
- **`check:node-runtime`-ը գործարկվում է 11 առաջադրանքում** — ⚠️ **ցածր ROI։** Յուրաքանչյուրը գործարկվում է առանձին runner-ում, իսկ ստուգումը տևում է <1վ։ Ընդհանուր խնայողությունը մոտավորապես 10վ է՝ էժան, յուրաքանչյուր առաջադրանքի համար առանձին պաշտպանիչ ստուգումը կորցնելու դիմաց։ Փոփոխությունների իրարանցումը չարժե։
- **`typecheck:noimplicit:core`-ը CI-ի lint-ում** — ✅ **հեռացվել է lint առաջադրանքից** (խորհրդատվական էր՝ `continue-on-error`)։ Արգելափակող տիպային մակերեսը `typecheck:core` + `check:type-coverage` է։ Տեղային սկրիպտը պահպանվել է։

### Միացնել / որոշել (օպերատորի քաղաքականություն)

- `check:openapi-security-tiers` (խորհրդատվական) — ❌ **Հնարավոր չէ մաքուր կերպով միացնել։** Այն ավարտվում է 0 կոդով, բայց նախազգուշացնում է, որ `LOCAL_ONLY_API_PREFIXES`-ի տակ գտնվող մի քանի `traffic-inspector` երթուղիներում բացակայում է `x-loopback-only: true` նշումը։ Դրա հարկադիր կիրառումը պահանջում է նախ ավելացնել այդ նշումները `openapi.yaml`-ում։
- `typecheck:noimplicit:core` (խորհրդատվական) — հիմնականում ներառված է արգելափակող `check:type-coverage` շեմապահում։ Փոխարկել շեմապահի կամ հեռացնել կրկնվող երկրորդ `tsc` անցումը։

- `check:secrets` (gitleaks, արգելափակող շեմապահ) — ընթացիկ առաստաղը `quality-baseline.json`-ի `metrics.secretFindings`-ն է։ Ցանկացած բացառություն պահանջում է հիմնավորված `.gitleaks.toml` գրառում։ Անհասանելի չափումը համարվում է ԹԵՐԻ։ Սկանավորումը լրացնում է GitHub-ի ներկառուցված գաղտնիքների սկանավորումը և `check:public-creds`-ը։
- `check:pr-evidence` (արգելափակող, grep-ով ստուգում է PR մարմնի արձակը) — կեղծ դրական արդյունքների բարձր ռիսկ ունի։ Հեռացնելու դեպքում թուլացնում է Կոշտ կանոն #18-ի կիրառումը, ուստի սա քաղաքականության իրական որոշում է։
- `semgrep` (խորհրդատվական առանձին հոսք) — OWASP ընտանիքների մասով համընկնում է CodeQL-ի հետ։ Դրա ելակետային մակարդակը կապել շեմապահի հետ կամ հեռացնել։

#### `check-key-completeness` — բանալիների հավաքածուների համարժեքության արգելափակիչ

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, առաջադրանք՝ `i18n-ui-coverage`)։
Համեմատում է յուրաքանչյուր `src/i18n/messages/<locale>.json`-ի վերջնային բանալիների հավաքածուն `en.json`-ի հետ և ձախողվում է ցանկացած բացակայող կամ ավելորդ վերջնային բանալու դեպքում՝ անկախ նրանից, թե երբ է բանալին ավելացվել։ `__MISSING__:` տեղապահները համարվում են առկա (դրանց բովանդակությունը հարաբերակցության արգելափակիչի գործն է)։ Սա տարբերությունների վրա հիմնված/տոկոսային երկու արգելափակիչների բացարձակ լրացումն է․ `check-ui-keys-coverage`-ը յուրաքանչյուր տեղայնացման համար պարտադրում է 80 % նվազագույն շեմ (մոտավորապես 13,000-ից 43 բացակայող բանալու դեպքում ցուցանիշը դեռ 99.7 % է), իսկ `check-new-key-coverage`-ը գնահատում է միայն այն բանալիները, որոնք PR-ն ավելացնում է `en.json`-ում։ Տեղայնացումների խմբաքանակը ստեղծվում է այն օրվա `en.json`-ից, երբ դրա ճյուղը առանձնացվում է, և թարգմանվում է օրեր շարունակ, մինչ հիմնական ճյուղում շարունակվում են բանալիների ավելացումները․ խմբաքանակային PR-ն ինքնուրույն որևէ բանալի չի ավելացնում, ուստի հարակից երկու արգելափակիչներն էլ լուռ մնացին, երբ խմբաքանակ 1-ը (#13044) միաձուլվեց ինը տեղայնացումներում 43 բանալու, իսկ խմբաքանակ 2-ը (#13660)՝ ութ տեղայնացումներում 10 բանալու պակասով (2026-09-15)։ Կարմիր կարգավիճակը շտկեք հետևյալով՝
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`․ `extra` վերջնային բանալին նշանակում է, որ այն հեռացվել է սկզբնաղբյուրից. ջնջեք այն տեղայնացումից։ `--warn`-ը հաղորդում է խնդրի մասին՝ առանց ձախողման։
`--catalog=cli`-ն նույն համեմատությունն իրականացնում է `bin/cli/locales`-ի համար (`npm run i18n:check-keys:cli`)․ երկու քայլերն էլ գտնվում են `i18n-ui-coverage` առաջադրանքում։

#### `check-new-key-coverage` — նոր բանալիների i18n արգելափակիչ

`check-ui-value-drift`-ի հարակից արգելափակիչը։ Վերջինս հայտնաբերում է անգլերեն արժեք, որը **վերաշարադրվել է**, մինչդեռ դրա թարգմանությունները մնացել են անփոփոխ, իսկ այս մեկը հայտնաբերում է անգլերեն բանալի, որը **ավելացվել է**, մինչդեռ որոշ տեղայնացումներ այն այդպես էլ չեն ստացել։

`check-ui-keys-coverage`-ը չի կարող տեսնել այս դեպքը․ այն յուրաքանչյուր տեղայնացման համար պարտադրում է տոկոսային նվազագույն շեմ, իսկ մոտավորապես 13,000 վերջնային բանալուց տասնմեկի բացակայության դեպքում ծածկույթը մնում է 99.9%։ Յուրաքանչյուր լեզվի համար առանձին տոկոսը չի կարող արտահայտել «այս հնարավորությունը թողարկվել է առանց թարգմանության» միտքը․ մի ամբողջ հնարավորություն կարող է հայտնվել նոր տեղայնացման մեջ՝ առանց որևէ տեքստի, և ցուցանիշը երբեք չփոխվի։

Դրա հիմքում ընկած միջադեպը հետևյալն է․ Orchestration Canvas-ի Phase 3-ը թարգմանեց իր տասնմեկ բանալիներն այդ պահին գոյություն ունեցող 42 տեղայնացումներում։ Ժամեր անց ԵՄ լեզուների խմբաքանակը (#13044) պահոցում տեղայնացումների թիվը հասցրեց 51-ի, իսկ ինը նոր տեղայնացումները (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) այդ բանալիներն այդպես էլ չստացան։ `deepMergeFallback`-ը բացակայող բանալու փոխարեն տեղադրում է անգլերենը, ուստի ձախողումն արտահայտվեց ոչ թե դատարկ, այլ չթարգմանված UI-ով՝ իրական խնդիր, որն իր կառուցվածքով լուռ էր։

Ինչպես իր հարակից արգելափակիչը, այն նույնպես **հաշվի է առնում տարբերությունները**՝ համեմատելով միաձուլման բազայում գտնվող անգլերենը աշխատանքային ծառի հետ, այնպես որ նախապես գոյություն ունեցող բացերը մնում են սառեցված, և արգելափակիչը միացնելու համար որևէ միգրացիա պետք չէր։

**`__MISSING__:<english>` նշիչը չի բավարարում դրա պահանջներին (2026-09-17-ից սկսած)։** Նախկինում դա հետաձգման փաստաթղթավորված միջոցն էր. կատարման ժամանակ համակարգը հետ է անցնում ճիշտ անգլերենին, մինչև 2026-09-16-ին հնարավորություններ ավելացնող ութ PR ավելացրին 61 բանալի և դրանք թարգմանելու փոխարեն նշիչը դրեցին բոլոր 65 տեղայնացումներում․ այս արգելափակիչն ընդունեց դրանցից յուրաքանչյուրը, ոչինչ չարգելափակեց PR-ները, իսկ իրական թարգմանությունների հարաբերակցության արգելափակող արգելափակիչն այնուհետև ձախողվեց թողարկման վերջնակետում բոլորի համար (pt-BR 3.2 % > 2.5 % + 0.5)։ Այժմ նշիչը գնահատվում է որպես բացակայող թարգմանություն։ Կարմիր կարգավիճակը շտկեք հետևյալով՝
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40`, կամ բոլոր տեղայնացումների համար զուգահեռաբար՝ `npm run i18n:translate-new-keys` (`scripts/i18n/translate-new-keys.sh`,
ապահով է detached վիճակում, հրաժարվում է գործարկվել առանց `OMNIROUTE_TRANSLATION_*` միջավայրի փոփոխականների)։ Բանալին, որը պետք է մնա անգլերեն (ամրագրված արտադրանքի/շարժիչի/դրոշակի անուն), պետք է գտնվի `scripts/i18n/untranslatable-keys.json`-ում և երբեք չթաքցվի նշիչի հետևում։ `vi`-ն ամբողջությամբ արգելում է նշիչները (`tests/unit/i18n-vi-completeness.test.ts`)։

#### `check-vitest-exclusions` — մի կողմ դրված թեստերի արգելափակիչ

`vitest.config.ts`-ի `exclude` ցանկում գտնվող ֆայլը չգործարկվող թեստ է, որը ծածկույթ է թվում յուրաքանչյուրին, ով դիտում է ծառը։ Վաթսուներկու ֆայլ էր կուտակվել `// #8618 — pre-existing failure; remove this exclusion when fixed` մեկնաբանության հետևում։ #8618 խնդիրը փակվել էր 2026-08-11-ին, մինչդեռ դրա հետևած ցանկն աճել էր 45-ից մինչև 62 գրառում, որոնցից յուրաքանչյուր նորը ժառանգել էր փակ խնդրին հղվող մեկնաբանությունը։ Երբ վերջապես ցանկը չափվեց ֆայլ առ ֆայլ (#13204), **62-ից 51-ը հաջողությամբ անցավ ընթացիկ ծառի վրա՝ առանց սկզբնաղբյուրի որևէ փոփոխության**։

Արգելափակիչը պահանջում է, որ իրական ֆայլի վերածվող յուրաքանչյուր բացառություն (a) նշի հետևման խնդիրը և (b) առկա լինի `config/quality/vitest-exclusions.json`-ում՝ իր չափված կարգավիճակով, որպեսզի նոր բացառության ավելացումը լինի առանձին ֆայլում վերանայելի տարբերություն, այլ ոչ թե ևս մեկ տող 60 գրառում ունեցող զանգվածում։ Այն միտումնավոր կրկին չի գործարկում բացառված թեստերը․ դա տևում է մոտավորապես 10 րոպե և պետք է կատարվի պարբերական առաջադրանքի շրջանակում, իսկ գույքացանկում գրանցվում է, թե յուրաքանչյուրն ամենավերջին անգամ երբ է չափվել։
