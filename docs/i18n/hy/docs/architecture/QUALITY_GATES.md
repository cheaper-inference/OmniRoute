Այս փաստաթուղթը OmniRoute-ի բոլոր CI որակի անցակետերի հեղինակավոր տեղեկատուն է։
Այն նկարագրում է յուրաքանչյուր անցակետը, թե ինչ է այն վավերացնում, որ CI առաջադրանքում է գործարկվում, արդյոք օգտագործում է
աստիճանական ելակետ, թե անցնել/ձախողվել քաղաքականություն, և արդյոք արգելափակում է կառուցումը, թե ունի խորհրդատվական բնույթ։

Համառոտ ամփոփագրի և թույլատրվածների ցանկի քաղաքականության համար տե՛ս "Quality Gates & Ratchets" բաժինը

## Դարպասի գույքագրման և կատարման պրոֆիլներ

### Թեկնածուների ընդունելություն

CI և Quality Gates-ի աշխատանքային հոսքերը յուրաքանչյուրն արձակում է կայուն դատավճիռ՝ `Gate / CI` և `Gate / Quality`: Նրանց տարբերակված ընդունելության քաղաքականությունը թվարկում է յուրաքանչյուր վերին հոսքի աշխատանքը որպես պահանջվող կամ խորհրդատվական: Կիրառելի պահանջվող աշխատանքը պետք է հաջողվի. բացակայող, չեղարկված, բաց թողնված, սպասող և անհայտ արդյունքները չեն կարող հաստատել PASS: Միայն փաստաթղթերի կամ միայն կատալոգի համար նախատեսված վավեր դասակարգումը կարող է անկիրառելի դարձնել ծածկագրի գոտին. a draft PR ընդունված թեկնածու չէ: `hotfix` պիտակը չի հրաժարվում ապացույցներից:

Երկու աշխատանքային հոսքերն էլ ներառում են PRs main/release ճյուղերի, մղումներ դեպի `main`, ձեռքով ուղարկում և միաձուլման խմբավորման իրադարձություններ: Հրել, ուղարկել և միաձուլել ամբողջ ընտրությունը: `release/**` վրա սեղմումները չեն սկսում դրանք (2026-10-18). յուրաքանչյուր փոփոխություն արդեն գործարկել է մատրիցը իր PR վրա, և միաձուլված համակցությունը Release-Green-ի գործն է (`docs/ops/RUNNER_BOX.md` → Hosted lane): Forks-ը և միաձուլման խմբերը օգտագործում են հյուրընկալված վազորդներ այն աշխատանքների համար, որոնք այլ կերպ ընտրում են ինքնուրույն վազորդներ. Բավարար հյուրընկալող հզորությունը պետք է ստուգվի նախքան թողարկումը:

Սովորական PR վարում է արագ ընտրությունը: Ընդունման քաղաքականության `full-code` և `full-code-e2e` ուղիները (E2E, ինտեգրում, փաթեթի արտեֆակտ, Electron smoke, Bun SQLite, էկոհամակարգ և արձանագրության հաճախորդներ) աշխատում են միայն Mergify հերթի նախագծի վրա կամ ամբողջական գործարկումով՝ `gh workflow run ci.yml --ref <branch>`:

Յուրաքանչյուր JSON անդորրագիր նույնականացնում է դուրս գրված SHA, աշխատանքային հոսքի գործարկումը և փորձը: CLI ն մերժում է checkout/event SHA անհամապատասխանությունը: Աշխատանքային հոսքի թեստերը կապում են քաղաքականության անդամակցությունը դատավճիռների աշխատանքի `needs` ցուցակին, այնպես որ նոր կամ հեռացված գոտին չի կարող լուռ անհետանալ: Անդորրագրերը ծածկում են իրենց սեփական աշխատանքային հոսքը, այլ ոչ թե հրապարակումը, տեղակայումը կամ առկա խորհրդատվական սկաների ներքին կառուցվածքը: Մասնաճյուղի կանոններում երկու ստուգման անվանումների ակտիվացումը առանձին վարչական փոփոխություն է. Այս աշխատատեղերի ավելացումն ինքնին չի պաշտպանում մասնաճյուղը:

### Միավորել հերթ

`queue` պիտակը PR է ուղարկում Mergify հերթին (`.mergify.yml`): Mergify-ը բացում է PR նախագիծը `mergify/merge-queue/` ճյուղում, CI այնտեղ գործարկում է ամբողջական ընտրությունը, իսկ սկզբնական PR միաձուլվում է, երբ `Gate / CI`, `Gate / Quality` և `Merge integrity (changelog + generated skills)` անցնում են:

Mergify-ը գրում է իր հերթի ամփոփագիրը սևագրի նկարագրության մեջ, և մյուս հավելվածները նույնպես կարող են խմբագրել այն: Նման սևագրի վրա `pull_request` `edited` իրադարձությունը վերցնում է իր համաժամանակյա խումբը (`-queue-edit-<run_id>`), ուստի այն չի կարող չեղարկել սևագրի իրական ընթացքը և բաց է թողնում դարպասը և մատրիցը: Միայն `Merge integrity` է դեռ աշխատում: Բաց թողնված դարպասի աշխատանքը կրում է այլ ստուգման անուն, քանի որ Mergify-ը կարդում է բաց թողնված `Gate / CI` որպես ձախողված ստուգում և փակում է PR ը:

Dequeue-ից հետո մղումը միշտ չէ, որ պահանջում է PR: Մեկնաբանություն `@mergifyio queue` դրա վերաբերյալ:

### Պահպանված ապացույցներ ընդունման կրճատիչում

`scripts/quality/validate-release-acceptance.mjs` նվազեցնում է մատակարարված պլանը և դրա դրսևորումները. այն չի սահմանում, որ պլանն ընդգրկում է ամբողջական թողարկման խողովակաշարը: Նրա հաշվետվությունները հստակորեն սահմանում են `releaseAcceptance: false`, նույնիսկ երբ այդ պլանը `VERIFIED` է: `release-acceptance.yml` աշխատանքային հոսքը դեռ օգտագործում է ստվերային հարմարանքներ, այլ ոչ թե իրական կառուցվածք, փաթեթ, բեռնախցիկ կամ առաջխաղացման անդորրագրեր:

CLI ն պահանջում է `--evidence-root` ՝ պահպանված ապացույցները ստուգելու համար: Ֆայլերը լուծվում են որպես `<evidence-root>/<artifact_id>/<member>` և հեշացված են որպես SHA-256: PASS գրառումն առանց ապացույցների, բացակայող կամ փոփոխված ֆայլի, անապահով ուղու կամ սիմվոլկի կանխում է ստուգումը: Բացակայող ֆայլերը համարժեք չեն դատարկ հաջողված տեղեկամատյաններին: Առկա SHA/run/attempt ստուգումները մնում են անկախ. համապատասխան բայթերը չեն կարող փրկել հնացած անդորրագիրը: Ֆայլի ամբողջականությունը կատարման իսկության կամ արտեֆակտի առաջմղման ապացույց չէ:

### Ստատիկ սկանավորման գույքագրում

Տարբերակված npm-alias գույքագրումը և ստատիկ սկանավորման անդամակցությունը ապրում են `config/quality/gate-manifest.json` ում: Գործարկեք `npm run check:gate-manifest` սկրիպտների անունները և ճշգրիտ հրամանները `package.json` դեմ վավերացնելու համար; լրացումները, հեռացումները և հրամանների դրեյֆը ձախողվում են ինչպես տեղական կեռիկը, այնպես էլ փոփոխության դասակարգման աշխատանքները CI ում: Այլանունը աշխատանքային հոսքի աշխատանք, մատրիցային օրինակ կամ փորձնական դեպք չէ. այս հաշվումները չպետք է ներկայացվեն որպես փոխարինելի:

Օգտագործեք `npm run quality:scan -- --list` կամ `npm run quality:scan:fast -- --list` ՝ ստուգելու ընտրված այլանունները՝ առանց դրանք գործարկելու: Վազողը կանչում է npm մուտքի կետը, ուստի դրա գործարկման ժամանակը (ներառյալ Bun, որտեղ կազմաձևված է) պահպանվում է: Մանիֆեստը գրանցում է այլանուններ այդ պրոֆիլներից դուրս՝ որպես առանձին կանչված, և սպասարկման հրամաններն արգելված են միայն կարդալու սկանավորման պրոֆիլներում:

Այս պրոֆիլները ծածկում են միայն ստատիկ սկանավորումը: Նրանք չեն հավաստում արտադրանքի թեստերը, ծածկույթը, փաթեթավորումը, արտաքին ստուգումները կամ թեկնածուի թողարկման ամբողջական ընդունումը: Աշխատանքային հոսքի ընդունումը օգտագործում է կապված `config/quality/admission-policy.json` և `scripts/quality/admission-verdict.mjs`: Ազատման դիտորդի պրոֆիլները մնում են առանձին. ինքնուրույն ստուգել դրանց կիրառելի չեկերն ու անդորրագրերը: Դիտորդի ամբողջական ստատիկ հրամանները հայտարարված են `config/quality/release-green-static-profile.json` ում, ներառյալ `audit:deps`, մուտացիայի թեստի ընտրությունը և թարգմանության ստուգումները: Բեռնիչը վավերացնում է npm հրամանները package.json և մոդելավորված CI/Quality հայտարարագրերի դեմ; այն մերժում է դրեյֆը՝ shell նշանները որպես փաստարկներ գործարկելու փոխարեն: Պահանջվող սկաների SKIP/INCOMPLETE ելքը չի կարող հաստատել PASS: Պրոֆիլը գրանցում է իր արտաքին բացառումները և չի փոխարինում հյուրընկալված ծածկույթին, փորձարկման մատրիցներին, փաթեթին կամ տեղակայման ապացույցներին: Ստորև բերված արձակի գույքագրումը հղում է, այլ ոչ թե ապացույց, որ դարպասը իրականում վազել է:

Սցենարները ապրում են `scripts/check/` (քաղաքականության դարպասների) և `scripts/quality/` (չեղջավոր շարժիչի) տակ: Ճշմարտության CI աղբյուրը `.github/workflows/ci.yml` է:

### Թողարկեք PR արագ ճանապարհը (`quality.yml`)

`.github/workflows/quality.yml` լրացնում է CI main/release PRs ում, հրում է `main`, ուղարկում և միավորում խմբերը: PRs օգտագործում է ճանապարհով զտված արագ ստուգումներ: Մշտապես անջատված կրկնօրինակ կառուցվածքը հեռացվել է. իրական build/package/boot չեկերը մնում են CI. Միավոր հավաքակազմը և վիտեստը գործում են միայն CI ով (`Unit Tests (N/8)` և `Vitest`):

| Աշխատանք                                         | Շրջանակ                                                                                                                                             | Արգելափակում                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API docs refs և docs-all                                                                                                             | Այո՛                        |
| `Fast Quality Gates`                             | Կոդ PRs; ստատիկ ստուգումներ, տիպի ստուգում, վահանակի տիպի ստուգում, ազդակիր միավորի թեստեր, մոռացված եղբայրների և եղբայրների թեստեր (խորհրդատվական) |
| `No new ESLint warnings`                         | Կոդ PRs; suppressions-aware lint guard                                                                                                              | Այո, ներառյալ պատառաքաղները |
| `Merge integrity (changelog + generated skills)` | Ոչ նախագիծ PRs; փոփոխության մատյան և գեներացված հմտությունների համաժամեցում                                                                         | Այո, ներառյալ պատառաքաղները |

#### Մոռացված եղբայրների կամ քույրերի թեստերի հաշվետվություն

`npm run check:forgotten-sibling-tests` աշխատում է որպես `Fast Quality Gates` ի խորհրդատվական քայլ և նորից օգտագործում է ներմուծման լուծիչը փորձարկման ազդեցության քարտեզի հետևում: Յուրաքանչյուր փոփոխված արտադրական մոդուլի համար այն հաղորդում է որոշիչ `changed module/symbol -> static consumer -> candidate sibling test` շղթաներ, երբ թեկնածուի թեստը բացակայում է ձգման պահանջի տարբերությունից: Markdown-ի ամփոփագիրը և JSON արդյունքը պահպանվում են որպես `forgotten-sibling-tests` աշխատանքային հոսքի արտեֆակտ՝ նախքան որևէ արգելափակման տեղակայումը չափորոշման համար:

Տակառի վերաարտահանումը և դինամիկ ներմուծումը միայն լուծման ախտորոշիչ են. նրանք երբեք արգելափակող գտածո չեն ստեղծում: Վերանայված բացառությունները ապրում են `config/quality/forgotten-sibling-allowlist.json` ում: Յուրաքանչյուր գրառում պետք է անվանի սպառողի և թեկնածուի թեստը, տա կոնկրետ հիմնավորում և կապի GitHub խնդիր կամ ձգողական հարցում: Սխալ մուտքերը փակ են: Բացառությունները չեն կարող ճնշել ջնջված թեկնածուի թեստը կամ տարբերությունը, որն ավելացնում է `.skip`/`.todo`; պնդման թուլացումը և այլ դիմակավորումը մնում են ինքնուրույն արգելափակող `check:test-masking` gate-ի սեփականությունը:

| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |

| `check:cycles`                    | Շրջանաձև ներմուծումներ ամբողջ `src/` + `open-sse/` (AST-ի վրա հիմնված, tsconfig `paths` լուծված): Bare-ը դուրս է գալիս 1-ից, երբ որևէ ցիկլ գոյություն ունի (fail-փակ է #15281 ից) և թվարկում է SCCs ը: `check:cycles:ratchet` (ինչ է աշխատում CI ) արգելափակում է, երբ հաշվարկը գերազանցում է `metrics.cycles` առաստաղը `quality-baseline.json` — ում ներկայումս 14, `direction: down`, այնպես որ այն կարող է ընկնել միայն (#15159 G-01/G-02)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Այո (չարչան)                                  |

#### Երկու տիպի ստուգման ծրագրեր տարբեր կերպ են պատասխանում

`typecheck:core` և `check:build-typecheck` տարբեր ծրագրեր են կազմում տարբեր տարբերակների ներքո, և նույն ֆայլը կարող է մեկում մաքուր լինել, իսկ մյուսում՝ լի սխալներով:

`tsconfig.build.json` սահմանում է `"strict": false`, ուստի `noImplicitAny` անջատված է: Հիմնական կազմաձևը կազմում է ընտրված 27 ֆայլի թույլտվությունների ցանկ՝ ավելի խիստ ընտրանքներով և հետևում է յուրաքանչյուր մուտքի ներմուծման գրաֆիկին, այնպես որ ֆայլերը, որոնք երբեք չեն հայտնվում կառուցման ծրագրում, դեռ ստուգվում են այնտեղ:

Հետևանքը կարևոր է, երբ դատում ենք, թե արդյոք ֆայլը մուտքագրված է.** զրոյական ախտորոշումը `check:build-typecheck` տակ չի նշանակում զրո** . 26 ֆայլերից `@ts-nocheck` ից հեռացնելը ցույց տվեց, որ դրանցից 23-ը մաքուր են build ծրագրում; Նրանցից տասնվեցը բացահայտեցին մոտ 120 անուղղակի սխալներ խիստ սխալի մեջ: Ստուգեք երկուսն էլ՝ նախքան ֆայլը մաքուր կանչելը:

#### Թարգմանության հայելիները ստացված ֆայլեր են (PR ռեժիմ ընդդեմ թողարկման ռեժիմի)

PR հատկանիշը խմբագրում է միայն անգլերեն աղբյուրները: `docs/i18n/<locale>/**` հայելիները (ներառյալ 66 `llm.txt` պատճենները և թարգմանված `CHANGELOG.md` ֆայլերը) և `.i18n-state.json` մեկ քայլով վերագրվում են թարգմանության ալիքով (`docs/i18n-*` / `chore/i18n-*` ճյուղեր, պլանավորված `i18n-mirror-refresh.yml`) և թողարկումով (`npm run release:sync-changelog-i18n`): Հետևաբար, հայելային դարպասներն աշխատում են երկու ռեժիմով, որոնք լուծվում են `scripts/check/lib/gateMode.mjs` ով (`--mode=pr|release`, այնուհետև `OMNIROUTE_GATE_MODE`, այնուհետև Գործողություններ իրադարձությունը. տեղական գործարկումը `release` է):

- `check:docs-sync` — թողարկման ռեժիմն աշխատում է յուրաքանչյուր ստուգում: PR ռեժիմը պահպանում է package.json/OpenAPI տարբերակը, արմատային CHANGELOG վերնագրերը և փոխարինող փաստաթղթերի պահակախումբը և տպում `SKIP reason=pr-mode` `llm.txt` հայելային պատճենների և թարգմանված CHANGELOG հատվածների համար — `CHANGELOG.md` եթե PR `docs/i18n/<locale>/llm.txt` `docs/i18n/**` `config/quality/derived-paths/*.json` է այդ ստուգումը խստորեն: Տարբերության հիմքը չի լուծվում depth-1 վճարման ժամանակ ( `docs-sync-strict` աշխատանք), այնպես որ PR ռեժիմը նաև կատարում է մեկ ստուգում, որը հիմքի կարիք չունի. ամեն `llm.txt` հայելի պետք է գոյություն ունենա, պահպանի իր `---` տարանջատիչը և կրի կամ արմատային մարմինը կամ այն մարմինը, որը շատ հայելիներ ունեն: Շարժվող հիմքը թողնում է բոլոր հայելիները հավասարապես հնացած և անցնում; մեկ հայելու ձեռքով խմբագրումը ձախողվում է: Թարգմանված `CHANGELOG.md` ֆայլերը նման ստուգում չունեն depth-1 PR դրամարկղում:
- Pre-commit hook-ն աշխատում է `check-docs-sync.mjs --mode=pr`. հանձնառությունը գնահատվում է նրա արածի հիման վրա: Առանց դրոշի, տեղական գործարկումը թողարկման ռեժիմ է, և միաձուլված PR, որը խմբագրում է `llm.txt` արմատը, արգելափակում է յուրաքանչյուր հետագա կատարումը այդ բազայի վրա, մինչև ալիքը գործարկվի: Նույն կանոնը գործում է ցանկացած ռեժիմի մասին տեղեկացված դարպասի համար, որն անցնում է Husky-ի կեռիկը. կեռիկը անցնում է `--mode=pr`, և խիստ դատավճիռը մնում է թողարկման ռեժիմի գործարկումների հետ (արձակումը PR, հրում է `main`, պարզ տեղային վազք):
- Հայելի բովանդակության միավորի թեստերը (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) — թողարկման ռեժիմը հաստատում է յուրաքանչյուր տեղայնությունը: PR ռեժիմը հաստատում է միայն այն հայելիները, որոնք ընթացիկ են անգլերեն աղբյուրի հետ՝ ըստ `.i18n-state.json` (ամբողջական ֆայլի հեշ, կամ բաժնի գրանցված հատվածի հեշը՝ թեստային կապում) և բաց է թողնում հնացածները՝ պատճառաբանելով: `target_hash` ծագման ստուգումները գործում են յուրաքանչյուր տեղանքի համար երկու ռեժիմով: Թարմությունը ըստ `## ` հատվածի, միավորը `run-translation.mjs` հեշեր; երկար բաժինը (այս ֆայլի դարպասի գույքագրումը մոտավորապես դրա կեսն է) նշանակում է, որ դրանում կատարված ցանկացած փոփոխություն թողնում է այդ հայելիները հնացած, և նրանց PR ռեժիմի պնդումները բաց են թողնում մինչև հաջորդ ալիքը: Անգլերեն աղբյուրն այլևս չպարունակող խարիսխը վերադառնում է ամբողջ ֆայլի համեմատությանը:
- `i18n translation drift` — խորհրդատվական PRs վերաբերյալ, խիստ սեղմման, գիշերային ժամերին և արձակման կտրվածքի վերաբերյալ, ուստի հնացած հայելին չի կարող առաքվել արձակման մեջ:

`scripts/i18n/sync-llm-mirrors.mjs` (նաև արտահանվում է որպես `syncLlmMirrors()`, `--dry-run` ով) վերաշարադրում է `llm.txt` հայելիները; թողարկման թարմացումը, թարգմանության ալիքը և պլանավորված `i18n-mirror-refresh.yml` գործարկում են այն (թարմացումը հայտնաբերում է հնացած `llm.txt` հայելիները չոր վազքով, քանի որ դրեյֆ զեկույցում դրանք չեն թվարկվում, և դրանք համաժամեցնում են `check:docs-all` առաջ):

Տասներկու README SVGs `docs/diagrams/` ի տակ գեներացվում են (`scripts/docs/gen-readme-<name>.mjs`; `npm run docs:readme-diagrams` վերածնում է բոլորին): Յուրաքանչյուրն ունի բայթ-համեմատման միավորի թեստ (`tests/unit/docs/readme-*-svg.test.ts`, job `test-unit`), որը ձախողվում է, երբ պարտավորված ֆայլը հնացած է թողարկման ռեժիմում; PR ում `check:generated-artifacts` դատում է SVG PR խմբագրումները, և բազայի դրեյֆը թողնվում է թողարկման թարմացմանը (տես [Ստեղծված ֆայլեր և ստացված բազային տողեր](#generated-files-and-derived-baselines-written-at-release) ) — և `check:docs-counts` կարդում են կանոնական թվեր իրենց `<text>` հանգույցներից — ինչի պատճառով ուրվագծման քայլը յուրաքանչյուր ուրվագծված `<text>` տողը պահում է որպես վիդեո ֆայլում: SVG կանոնական թվերի ստուգումը կարդում է `SVG_DIAGRAM_FILES` (`scripts/check/check-docs-counts-sync.mjs`) թվարկված ֆայլերը՝ `docs/diagrams/readme-hero.svg`, `free-tier-budget.svg`, `promise-pillars.svg`, `comparison-table.svg`, `cli-terminal.svg`, `tier-cascade.svg`, գումարած `public/images/tier-flow-dark.svg` եւ `tier-flow-light.svg`; «Ազատ ընդմիշտ», կատալոգի մուտքի, կրկնվող լողավազանի և միավորների գործակիցների պահանջները նույնպես կարդում են `promise-pillars.svg`, `free-tier-budget.svg` և `strategies-grid.svg`: Այս գեներատորների հաշվարկները (մատակարարի ընդհանուր, MCP գործիքներ, երթուղային ռազմավարություններ, ընդմիշտ անվճար մատակարարներ, …) գալիս են `docs/reference/derived-facts.json` ի միջոցով `scripts/docs/readmeFacts.mjs` միջոցով նկարահանված փաստերի պատկերից, ոչ թե բառացի, այնպես որ ցանկացած ճյուղի վրա դիագրամի վերականգնումը վերարտադրում է կատարված ֆայլը: `free-tier-budget.svg` իր տողերը նկարում է նույն նկարից (`code.freeTierBudget`, կատալոգի ամփոփագիրը փաստերի հետաքննության գրառումները), այնպես որ `FREE_MODEL_BUDGETS` ի փոփոխությունը հասնում է քարտին հաջորդ թարմացման ժամանակ՝ CI կարմիր դարձնելու փոխարեն:

### Ստացված արժեքներ՝ `pr` և `release` դարպասի ռեժիմները

PR հատկանիշը երբեք չի գրում արժեք, որը կախված է իր բազայի վիճակից՝ մատակարարից, միգրացիայից, MCP-գործիքների և ռազմավարության թվերից, README SVG թվերից, փաստերի նկարից: Մեկ քայլը վերահաշվարկում է դրանք բոլորին, `npm run release:refresh-derived`, գործարկված թողարկմամբ և գիշերային ստացված թարմացման PR ով: Այսպիսով** թողարկումների միջև բազան դիզայնով գտնվում է կենդանի կոդի հետևում** , և դարպասը կամ թեստը, որը համեմատում է ծառը կենդանի կոդի հետ, կարմիր կլինի յուրաքանչյուր PR վրա այն բանից հետո, երբ քույրը կամ եղբայրը մատակարար ավելացնի: Հետևաբար, դարպասները, որոնք գնահատում են ստացված արժեքները, գործում են երկու ռեժիմներից մեկով, որը լուծվում է `scripts/check/lib/gateMode.mjs` ով (առաջին խաղում հաղթում է).

1. `--mode=pr|release` հրամանի տողում;
2. `OMNIROUTE_GATE_MODE` միջավայրի փոփոխական (`pr` կամ `release`);
3. ավտոմատ, GitHub Actions իրադարձությունից. a `pull_request` որի գլուխը `release/v*` չէ, a `merge_group` կամ մղում է `omni-queue/**` → `pr`; մնացած ամեն ինչ (հրում, ժամանակացույց, առաքում, թողարկում PR `release/v* → main`, ցանկացած տեղական վազք) → `release`.

Ինչ `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) ձախողվում է յուրաքանչյուր ռեժիմում.

| Ռեժիմ     | Ձախողվում է                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Անհրաժեշտ են կենդանի փաստեր |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `release` | Յուրաքանչյուր ստուգում, խիստ հավասարություն ծառից հավաքված փաստերի նկատմամբ ( STRICT պահվածքը, SVG դարպասը միշտ ունեցել է).                                                                                                                                                                                                                                                                                                                                      | Այո՛                        |
| `pr`      | Միայն այն, ինչ արեց փոփոխությունը, տարբերվեց PR բազայի հետ նույն պահանջի արդյունահանմամբ. (1) կառավարվող արժեք, որը գոյություն չուներ այդ ստուգման և ֆայլի հիմքում («PR խմբագրել է կառավարվող համարը — վերականգնել տողը հիմնական տեքստին»); (2) պահանջվող պահանջ, որը կրել է բազան, և գլուխը կորցրել է: Բովանդակության անփոփոխները, որոնք փաստերի կարիք չունեն, գործարկվում են ինչպես թողարկման ռեժիմում. միայն թողարկման ստուգումները նշված են և բաց են թողնվել | Ոչ                          |

Գործակալ-հրահանգի ֆայլերը կրում են** ոչ** ածանցյալ հաշվարկն ընդհանրապես՝ `AGENTS.md`, `llm.txt` (և դրա `docs/i18n/*/llm.txt` պատճենները), bs `AGENTS.md` fork, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` և ամեն `skills/*/SKILL.md` մատնանշում են աղբյուրը (օրինակ `ROUTING_STRATEGY_VALUES` `src/shared/constants/routingStrategies.ts` ում) և փոխարենը՝ `npm run facts` ։ Անփոփոխ «Ոչ ստացված հաշվարկներ (գործակալ-հրահանգի ֆայլ…)» չի հաշվարկվում այնտեղ (մատակարարներ, միգրացիաներ, MCP գործիքներ և շրջանակներ, երթուղային ռազմավարություններ, միավորների գործակիցներ, ռեժիմների փաթեթներ) երկու ռեժիմներում, այնպես որ թողարկման թարմացումը երբեք ստիպված չի լինի վերաշարադրել հրահանգների ֆայլը:

**Երկու ռեժիմ (2026-11-13-ից):** PR հատկանիշը ավելացնում կամ վերաշարադրում է ստեղները `en.json` (և `bin/cli/locales/en.json`) բառերով և չի դիպչում որևէ այլ տեղանքի. `check:pr-derived-paths` (աշխատանք `pr-test-policy`, ընտանիք `config/quality/derived-paths/translation.json`) ձախողվում է PR հատկանիշը, որն անում է: Մյուս տեղանքները լրացվում են մեկ թողարկումով `release:refresh-derived` ի կողմից, որը `syncUiKeys()` կանչում է `scripts/i18n/sync-ui-keys.mjs` ով (ավելացնել բացակայող ստեղները, կտրել բաց թողնվածները, նշել վերագրված անգլերենի թարգմանությունները `rewrittenSinceRef` ով, թարգմանել) կամ թարգմանության ալիքով: Դարպասները կարդում են ռեժիմը `scripts/check/lib/gateMode.mjs` ից. `pr` ռեժիմում (հատկանիշ PRs, `merge_group`, `omni-queue/**`) բացման ռեժիմի դարպասները վերևում տպում են `SKIP reason=pr-mode` և ելք 0; `release` ռեժիմում (թողարկում PR, մղում է `main`, `workflow_dispatch`, լոկալ գործարկումներ) դրանք նախկինի պես խիստ են, իսկ PR թողարկման ժամանակ diff-ը տեղեկացվածները ստանում են `BASE_REF=origin/main`, ուստի նրանք դատում են յուրաքանչյուր ստեղնի ավելացված կամ վերագրված ցիկլը։ Նախադիտեք feature-PR դատավճիռը տեղական `--mode=pr` ով:

PR, որը դեռ փոխում է տեղային կատալոգները `pr` ռեժիմում (թարգմանության ալիք, թողարկման թարմացում, միայն թարգմանության ուղղում), `en.json` չի թողնվում. `check-key-completeness` of a `__MISSING__:` string PR `scripts/i18n/lib/touched-catalogs.mjs` placeholders/tags PR ում նոր կատալոգը պետք է ունենա `en.json` ստեղների ամբողջ հավաքածուն: Դա ներառում է կատալոգների համար PR շոշափում է, թե ինչ կտեսնեն հարաբերակցությունը և CLI-հավասարակշռության դարպասները:

Տեղական հավասարության միավորի թեստերը (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) հետևում են նույն ռեժիմներին `tests/_helpers/localeParityMode.ts` միջոցով. `pr` ռեժիմում նրանք բաց են թողնում բանալու հավասարության պնդումները և թողնում են թողարկմանը թարմացնել այն ստեղների տեղապահի հավասարությունը, որոնց անգլերենը փոխվել է միաձուլման հիմքից հետո (յուրաքանչյուր ստեղն չի կարող կարդալ այն ծանծաղ տողում): Այդ օգնականն է** միայն** թույլատրված ռեժիմ-պայմանական բաց թողնել. `check:test-masking` հաշվում է `.skip(` և `{ skip: true }`, բայց ոչ հաշվարկված `{ skip: "<reason>" }`, այն վերադարձնում է, ուստի `tests/unit/locale-parity-mode.test.ts` ամրացնում է այն օգտագործելու համար թույլատրված թեստերի ցանկը — ավելացնելով, որ այդ ցուցակում վերանայված խմբագրում է:

#### `check-ui-value-drift` — հնացած-թարգմանական դարպաս

Բռնում է i18n մեկ ռեգրեսիան, որը մյուս դարպասները կառուցվածքային առումով չեն կարող տեսնել. անգլերեն արժեքը վերագրվում է, իսկ _նախորդ_ անգլերենից ստացված թարգմանությունները մնում են հետևում, այնպես որ ոչ անգլերեն օգտվողները շարունակում են կարդալ վստահորեն ձևակերպված, այժմ սխալ պատճենը:

Սա առաքվել է իրական: `oauthModal.googleOAuthWarning` նորից գրվեց, երբ Antigravity մուտքի օգնականը վայրէջք կատարեց (#5203);** 43 տեղանքից 39-ը** պահպանեց տեքստը, որով օպերատորներին ասում էր «պատճենել ամբողջական URL և տեղադրել այն ներքևում» — մի հոսք, որը չի կարող ավարտվել այդ մատակարարի համար: Այն աննկատ մնաց մինչև #8463 քանի որ.

- `sync-ui-keys` լցնում է միայն այն բանալիները, որոնք կան** բացակայում է** , երբեք այնպիսիք, որ կան** հնացած** ;
- `check-ui-keys-coverage` հաշվում է բանալին _presence_, ուստի հնացած թարգմանությունը գնահատվում է որպես ծածկված;
- `check-translation-drift` հետևում է `docs/i18n/<locale>/**.md` փաստաթղթերին, հայելիներ — այն երբեք չի կարդում `src/i18n/messages/*.json`: Այն աշխատում է աշխատանքի `docs-sync-strict` ում. խորհրդատվական PRs վերաբերյալ, խիստ հրում և գիշերային ժամերին; թարգմանության ալիքը թարմացնում է հայելիները, ոչ թե PR հատկանիշը:

**Տարբերությունների գիտակցում, ոչ բազային հիմքով:** Այն համեմատում է `en.json` միաձուլման հիմքում աշխատող ծառի հետ; յուրաքանչյուր ստեղնի համար, որի անգլերեն արժեքը փոխվել է, ցանկացած տեղանք, որը դեռևս անձեռնմխելի թարգմանություն է պահում, հնացած է: Սա միտումնավոր** սառեցնում է նախկինում գոյություն ունեցող պարտքը** — a diff-ը չի կարող բացահայտել, թե որ հին անգլերենից է առաջացել երկարամյա թարգմանությունը, ուստի դարպասը դատում է միայն այն, թե ինչ է շոշափում ընթացիկ փոփոխությունը: Այլընտրանքը (յուրաքանչյուր բանալիի հեշի բազային գիծ) կարժենա ~ 600 KB գեներացված ֆայլ, 3 × ամենամեծ գոյություն ունեցող բազային գիծը, որը կծկվի յուրաքանչյուր i18n PR վրա:

Այն բավարարելու երկու եղանակ.

1. թարմացնել ազդակիր թարգմանությունները, կամ
2. դրեք դրանք `__MISSING__:<new english>` — գործարկման ժամանակի վրա, այնուհետև սպասարկում է շտկված անգլերենը (`src/i18n/request.ts::deepMergeFallback`, #7258) և թարգմանության հիմնական հերթերը:

Եթե լարը** իմաստը** փոխվել, նախընտրել** բանալին վերանվանելը** Նոր բանալին չի կարող ժառանգել հնացած թարգմանություն: Դա #8463 օրինաչափությունն է:

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Դուրս է գալիս 0-ից `SKIP reason=base-unresolved` ով, երբ բազային կատալոգը հնարավոր չէ կարդալ (ծանր կլոն առանց բազային ref-ի), արտացոլելով `check-openapi-breaking`: Միայն թողարկման ռեժիմ. PR ֆունկցիան վերաշարադրում է անգլերենը և կանգ է առնում այնտեղ; թողարկման թարմացումը նշում է իր թողած թարգմանությունները (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, նույն `findStaleTranslations`):

Աշխատանքն այլևս մշտական խնդիր չի ստեղծում կամ թարմացնում. #12149 պահպանում է ավելի վաղ զեկույցի պատմությունը:

**Նոր կոդային ռեժիմ (Clean-as-You-Code) — 2026-08-30-ից, միայն PR արագ ճանապարհ**

`pull_request` իրադարձությունների վրա `quality.yml` `--base-ref <PR base SHA>` անցնում է `check:file-size`, `check:complexity-ratchets` և `check:dead-code`: `check:complexity-ratchets` և `check:dead-code` համար դարպասը HEAD համեմատում է միաձուլման հիմքի հետ** սահմանափակված է այն ֆայլերով, որոնց դիպչել է PR** (`scripts/check/newCodeMode.mjs`. միաձուլման հիմքը նյութականացված է նետված `git worktree` ում, ESLint/knip գործարկվում է այնտեղ, իսկ HEAD ում յուրաքանչյուր ֆայլի հաշվարկները տարբերվում են).

- **արգելափակում** — the PR ավելացրել է cyclomatic/cognitive խախտումներ կամ մահացած արտահանումներ իր փոխված ֆայլերում (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` մատյանում);
- **խորհրդատվական** — գլոբալ ընդհանուրն ընդդեմ սառեցված բազային: Ժառանգական դրեյֆը երբեք չի կարմրում անմեղ PR ին; դրեյֆը կրկին սառեցվում է ազատման հաշտեցման ժամանակ և դիտվում է գլխամասային աշխատանքի կողմից:

`check:file-size` օգտագործում է բազային ref-ն իր տերմիններով (`scripts/check/check-file-size.mjs`, #8522). այն ստուգում է ծառի յուրաքանչյուր աղբյուր և թեստային ֆայլ, կարդում է յուրաքանչյուրի տողերի քանակը PR հիմքում `git show` ով և ձախողում է ֆայլը միայն այն ժամանակ, երբ այն մեծանում է իր բազային առաստաղից (`frozen` / `testFrozen` կամ `cap` / `testCap` ) և ֆայլի բազային չափից դուրս: Ֆայլը, որն արդեն շեղվել է հիմքի վրա, հետևաբար երբեք չի կարմրում անմեղ PR:

`check:boundary:ratchet` կիրառում է նույն կանոնը իր մեկ համարի (`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`) նկատմամբ. PR իրադարձությունների դեպքում և՛ `quality.yml` արագ դարպասները, և՛ `ci.yml` lint աշխատանքը անցնում են PR հիմքը SHA, բազային պարտավորությունը չափվում է `git archive` արտահանումից, և PR ն ձախողվում է միայն այն ժամանակ, երբ դրա `open-sse → src` եզրերի քանակը գերազանցում է `metrics.boundaryOpenSseToSrc` ի և բազայի վրա հաշվարկված մեծը: Հաղորդվում է առաստաղի վերևի հիմքի շեղում (`base drift herdado`), բայց երբեք չի կարմիրում անմեղ PR; push → main-ը պահում է բացարձակ առաստաղը, և անլուծելի հիմքը SHA հետ է ընկնում նախազգուշացումով։

Բոլոր հերթերի թեկնածուն (հրում դեպի `omni-queue/**`, տե՛ս [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ) ստանում է նույն վերաբերմունքը, ինչ ձգման հարցումը. երկու աշխատանքային հոսքերն էլ անցնում են թեկնածուի բազան (`needs.changes.outputs.candidateBase`) որպես `--base-ref`, և `check:ts7-diagnostics-ratchet` նույնպես դեմ է: Երկու նոր կոդի դարպասների համար համեմատության հիմքն այն է, որ SHA ինքն է, այլ ոչ թե վերին միաձուլման առաջին ծնողը, այնպես որ խմբաքանակի յուրաքանչյուր ձգման հարցումը գնահատվում է:

Չարչնավոր շարժիչը (`scripts/quality/check-quality-ratchet.mjs`) կարդում է `quality-baseline.json` և համեմատում այն նոր հավաքված `quality-metrics.json` հետ: Ցանկացած չափիչ, որը հետընթաց է ապրում իր էպսիլոնից այն կողմ, չի հաջողվում կառուցել:

Ընթացիկ հետևվող չափումներ.


`--update` դրոշակը գրում է ընթացիկ չափված արժեքները `quality-baseline.json` ում: Բանկային բարելավումը release/nightly աշխատանք է, այլ ոչ թե PR ի հատկանիշ. `--require-tighten` (Fase 6A.5) չի հաջողվում առանց բանկային բարելավման միայն թողարկման ռեժիմում (հրում, ժամանակացույց, թողարկում PR, տեղային գործարկումներ): PR ֆունկցիայի մեջ (`pr` gate ռեժիմ) այն տպում է բարելավումը որպես տեղեկատվություն և անցնում; հետընթացը ձախողվում է երկու ռեժիմներում էլ: Արագության փուլում ամենուր խորհուրդ է տրվում (`_policy.requireTighten: false`): Տեսեք [Ստեղծված ֆայլերը և ստացված ելակետերը](#generated-files-and-derived-baselines-written-at-release) :

### CodeQL ratchet. թարմացման արագություն և ձեռքով ձգան

`check:codeql-ratchet` կարդում է** ռեպո վիճակ, թարմացվել է ժամանակացույցով — ոչ մեկ PR.** `gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` հաղորդում է `state: configured`, `schedule: weekly`. GitHub ի լռելյայն տեղադրման սկանավորումը, ոչ թե մեկ սեղմման վերլուծություն: Հետևանք. PR հետո, որը FIXES ահազանգերը միաձուլվում են, զրահը շարունակում է կարդալ հին, ավելի բարձր թիվը, մինչև հաջորդ պլանավորված սկանավորումը կատարվի — այնպես որ այն հայտնում է ռեգրեսիա յուրաքանչյուր բաց PR վրա, ներառյալ ֆիքսող PR ի սեփական հետևումները, մինչև որ սկանավորումը հասնի:

**Ձեռքով թարմացում** `gh workflow run codeql.yml --ref release/vX.Y.Z` վերագործարկում է վերլուծությունը և րոպեների ընթացքում վերահրապարակում ահազանգերը: Կարդացեք `.github/workflows/codeql.yml` նախ — դրա վերնագիրը բացատրում է, որ դա `workflow_dispatch` -only է** քանի որ այն հակասում է GitHub ի «կանխադրված կարգավորումներին»** (`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`). `push`/`pull_request`/ `schedule` գործարկիչները վերականգնելու համար անհրաժեշտ է** սեփականատիրոջ գործողությունը նախ** Կարգավորումներ → Կոդի անվտանգություն → CodeQL. Կանխադրված → Ընդլայնված: Մի ավելացրեք `schedule:` գործարկիչ առանց այդ անջատիչ — դա միայն կառաջացնի ձախողված գործարկումներ:

**Հաշվի անկումից հետո բազային գիծը խստացրեք** — `node scripts/check/check-codeql-ratchet.mjs --update` գրում է նոր չափված հաշվարկը `quality-baseline.json` → `metrics.codeqlAlerts.value` ի մեջ, այնպես որ կապանքը լուռ թույլ չի տալիս հետընթաց կատարել մինչև հին առաստաղը: PR #12502 → 2026-09-02/03). PR #12530 խստացրեց սառեցված բազային գիծը 11 → 6, որպեսզի համապատասխանի; մնացած 6-ն այնուհետև հեռացվեցին մեկ ահազանգի հիմնավորումով մինչև 0 բաց:

վերջնակետում, այսինքն՝ հետընթացն առաջացել է միաձուլումների ՀԱՄԱԿՑՈՒԹՅՈՒՆԻՑ, և ոչ մի առանձին PR այն չի վերարտադրում

ճյուղում**. նախընտրեք առանձնացումը/վերակառուցումը, իսկ ելակետը փոխեք միայն փաստաթղթավորված
հիմնավորման գրառմամբ։ Երբեք համակցությունից առաջացած շեղումը մի վերագրեք մասնակցի PR-ին և երբեք
մի փոխեք ելակետը յուրաքանչյուր PR-ի համար (դա թաքցնում է իրական ռեգրեսիաները)։ Նախ տարբերակեք պատճառը.

Ընտանիքում չէ, միտումնավոր. մարդկանց կողմից որոշված քաղաքականության ֆայլերը (`gate-manifest.json`, թույլտվությունների ցանկերը, `admission-policy.json`, `provider-assets-provenance.jsonl`, `model-lifecycle.json`) և առաստաղներ, PR հատկանիշը կարող է ստիպված լինել խմբագրել կոդի հետ միասին (`quality-baseline.json` մետրային գրառումներ, typecheck/file-size/complexity բազային գծեր, `eslint-suppressions.json` — ՝ նախապես կատարված ESLint գործարկմամբ, երբ PR ֆիքսում է խախտումը): `src/i18n/routeNamespaces.generated.json` նույնպես ստեղծվում է, բայց մնում է PRs ֆունկցիայի մեջ. հավելվածը ներմուծում է այն գործարկման ժամանակ, ուստի չի կարող սպասել թարմացման:

## Սահմանափակիչների նվազեցումների ամրագրում՝ նվազման ուղղությունը (#8584)

Սահմանափակիչն ավտոմատ է միայն կիսով չափ, ընդ որում՝ սխալ կեսով։ Սահմանաչափի **բարձրացումը**
ձեռքով JSON-ի խմբագրում է, որը տևում է տասը վայրկյան և կարմիր PR-ն ապաշրջափակելու ամենաարագ եղանակն է։
Այն **նվազեցնելու** համար որևէ մեկը պետք է գործարկի `--update` և commit անի արդյունքը, իսկ մինչև
`bank-ratchet-shrinks` առաջադրանքի ներդրումը դա չէր անում ոչ մի workflow։ Չափված հետևանքը
(2026-07-25). 18 սառեցված ֆայլ արդեն գտնվում էր նոր ֆայլերի 800 տող սահմանաչափի մակարդակին կամ դրանից ներքև, իսկ վատագույնը՝
132× (`src/shared/validation/schemas.ts`, 19 տող՝ 2,523 սահմանաչափով), բարդության վերին շեմը
մոտավորապես 37 ելակետի փոփոխման նշումների ընթացքում բարձրացել էր `1794 → 2169`՝ ունենալով ճիշտ մեկ
նվազում (−1), իսկ «հաջորդ շրջափուլում խստացնել `--update`-ի միջոցով» գրառվել էր 31 անգամ և կատարվել՝
մեկ անգամ։ Սահմանաչափը, որը շարունակում է գոյություն ունենալ իրեն առաջացրած կոդից ավելի երկար, յուրաքանչյուր ավարտված
տրոհում աննկատ վերածում է աճի թույլտվության՝ ֆայլը հաջորդը խմբագրող անձի համար։

`nightly-release-green.yml` → **`bank-ratchet-shrinks`** առաջադրանքը փակում է այդ շրջափուլը.

PR-ի ճյուղը միաձուլման արշավների ընթացքում և ամեն անգամ կվճարեր ESLint-ի ամբողջական անցման արժեքը։ Հայտնաբերումը

### Անվտանգության ստուգիչը

Առաջադրանքն առանց վերահսկման գրում է ելակետերում, ուստի հենց `verify-ratchet-bank.mjs`-ն է դա
ընդունելի դարձնում։ Այն համեմատում է `--update`-ից հետո ստացված ծառը `HEAD`-ի հետ և **ընդհատում է առաջադրանքը
նախքան որևէ commit-ի ստեղծումը**՝ առանց PR բացելու, եթե բոլոր փոփոխությունները հետևյալներից որևէ մեկը չեն.

- `frozen` / `testFrozen` թվային գրառում, որը **նվազեցվել** կամ **հեռացվել** է
- `complexity-baseline.json` → `count`՝ **նվազեցված**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value`՝ **նվազեցված**

Ցանկացած այլ բան հանգեցնում է ձախողման՝ թվի բարձրացումը, գրառման ավելացումը, `cap`/`testCap`-ի փոփոխությունը կամ
`_rebaseline_*` նշման ջնջումը/վերագրումը (այդ նշումները յուրաքանչյուր վերին շեմի գոյության պատճառների աուդիտային պատմությունն են
և պահվում են նույն `frozen` օբյեկտում, ինչ ֆայլերի գրառումները)։
Բոտը, որը կարող է բարձրացնել սահմանաչափը, հաստատ ավելի վատ կլիներ, քան առկա վիճակը։ Ռեգրեսիայից պաշտպանություն՝
`tests/unit/verify-ratchet-bank.test.ts`։

Առաջադրանքը երբեք push չի անում դեպի `release/*`. PR-ը միաձուլում է մարդը, ուստի սխալ չափումը
չի կարող հայտնվել համակարգում առանց ստուգման։

## Թույլտվությունների ցանկի քաղաքականություն

Յուրաքանչյուր դարպաս, որը չի կարող ձախողել նախկինում գոյություն ունեցող խախտումները, օգտագործում է սառեցված թույլտվությունների ցուցակ (օրինակ՝ `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`): Քաղաքականությունը հետևյալն է.

**Ուղղել հիմնական պատճառը; օգտագործեք թույլտվությունների ցանկը միայն այն դեպքում, երբ խախտումը նախապես գոյություն ունի և չի կարող ֆիքսվել նույն PR ում:**

Թույլտվությունների ցանկում գրառում ավելացնելիս՝

1. Ներառեք մեկնաբանություն հիմնավորման հետ:
2. Անդրադարձեք հետևելու խնդրին (օրինակ՝ `// #3498 — Phase 2 feature, not yet implemented`):
3. Հեռացրեք այն նույն PR ի մուտքը, որը ֆիքսում է խախտումը — հնացած գրառումը, որն այլևս չի ճնշում ակտիվ խախտումը, ինքնին թերություն է (6A.3 հնացած կիրարկումը թույլ չի տա որբացած թույլտվության ցուցակի մուտքը, երբ իրականացվի):

Արեք** ոչ** ավելացրեք թույլտվությունների ցանկը, որպեսզի թեստերն ավելի արագ անցնեն: Աճող թույլտվությունների ցանկով կանաչ դարպասը որակի կեղծ զգացում է:

### Երբ դարպասը ձախողվում է ձեր PR վրա

1. **Ուշադիր կարդացեք դարպասի ելքը** — այն հստակ ասում է, թե որ ֆայլը կամ խորհրդանիշն է խախտել կանոնը:
2. **Ուղղել խախտումը** — դարպասների մեծ մասը դետերմինիստական ֆայլային համակարգի ստուգումներ են, որոնք անցնում են հենց կոդը ճիշտ է:
3. **Եթե խախտումը նախապես գոյություն ունի** (այսինքն, դուք չեք ներկայացրել այն, բայց դարպասն այժմ ծածկում է այն). ավելացրեք թույլտվության ցուցակի գրառում՝ հիմնավորման մեկնաբանությունով և հետևելու խնդրի հետ:
4. **Եթե դարպասը ճարմանդ է** (ծածկույթ, ESLint նախազգուշացումներ, կրկնօրինակում, բարդություն). Ուղղեք հիմքում ընկած խնդիրը կամ (հազվադեպ) գործարկեք `npm run quality:ratchet -- --update`, եթե փոփոխությունը միտումնավոր է, և մետրային դեգրադացիան ընդունելի է — բայց փաստեք, թե ինչու է PR նկարագրության մեջ:
5. **Խորհրդատվական դարպասներ** (`continue-on-error: true`) տեղեկատվական — են, դրանք չեն արգելափակում միաձուլումը, այլ հայտնվում են CI ամփոփագրում: Ուղղեք դրանք ամեն դեպքում:

## Նոր ստուգիչի ավելացում

1. Ստեղծեք `scripts/check/check-<name>.mjs` (կամ `.ts`)։ Քաղաքականության ստուգիչներն ավարտվում են 0/1 կոդով։
   Ռատչետ տեսակի ստուգիչները չափանիշ են գրում `quality-metrics.json`-ում՝ `collect-metrics.mjs`-ի միջոցով։
2. `package.json`-ում ավելացրեք `"check:<name>": "node scripts/check/check-<name>.mjs"`։
3. Միացրեք այն `.github/workflows/ci.yml`-ում՝ համապատասխան job-ի ներքո
   (քաղաքականություն → `lint` կամ `docs-sync-strict`, ռատչետ → `quality-gate`)։
4. Եթե այն ունի թույլատրվածների ցանկ, կիրառեք `reportStaleEntries()`-ը
   `scripts/check/lib/allowlist.mjs`-ից, որպեսզի հնացած գրառումները հայտնաբերվեն ինքնաբերաբար։
5. `tests/unit/build/`-ում գրեք թեստ, որն ընդգրկում է ստուգիչի հայտնաբերման տրամաբանությունը։
6. Թարմացրեք այս փաստաթուղթը (համապատասխան job-ի աղյուսակում ավելացրեք տող)։

## Գործակալների գործիքակազմ․ LSP-in-the-loop (ըստ ցանկության)

միացման սխալ և երբեք չի խափանում աշխատաշրջանները։

## Ռացիոնալացման հետնախագիծ (ROI ակնարկ — Fase 9 Onda 3)

Այս գույքագրումը հաշտվել է `ci.yml` հետ 2026-06-17-ին (նախորդ տարբերակը բաց է թողել `audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`, `check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`, `check:codeql-ratchet`, `check:pr-evidence`): Հաշտեցված հավաքածուի ROI վերանայումը բացահայտեց ռացիոնալացման հետևյալ թեկնածուներին.** Միաձուլումները մեխանիկական CI փոփոխություններ են. flips/drops ը քաղաքական որոշումներ են, որոնք վերապահված են օպերատորին:** Ստորև բերված ոչինչ դեռ չի կիրառվում։

**Նաև չփաստաթղթավորված վերևում** (խորհրդատվական, ցածր ազդանշան). `docs-lint` աշխատանքը (markdownlint + Vale, ամբողջ աշխատանք `continue-on-error`) և ինքնուրույն սկաների աշխատանքային հոսքերը `semgrep.yml` / `codeql.yml` / `scorecard.yml`: `semgrepFindings: 0` `quality-baseline.json` ով է, բայց միացված չէ `ci.yml` — ում արգելափակող կապանքին, մետրիկը ներկայումս որբ է:

### Միաձուլում / անջատում (մեխանիկական, ցածր ռիսկ)

Յուրաքանչյուր թեկնածու վավերացվել է ուղիղ դարպասի վիճակի դեմ 2026-06-17 (վստահել-բայց ստուգել); մի քանի «ակնհայտ» միաձուլումներ ստացվել են պարտքը թաքցնելու նպատակով և են** ոչ** մաքուր կաթիլներ:

- **`check:docs-sync` վազում է երկու անգամ** — ինքնուրույն `lint` աշխատանքում և կրկին `check:docs-all` ի ներսում (`docs-sync-strict`) և husky pre-commit hook-ում: ✅**DONE** — ինքնուրույն `lint` կոչումը հանվել է:

- **Ցիկլի հայտնաբերում** — ✅**DONE** (#15159 G-01/G-02). #### `check-key-completeness` — բանալի-սահմանված հավասարության դարպաս

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, job `i18n-ui-coverage`). Համեմատում է յուրաքանչյուր `src/i18n/messages/<locale>.json` ի տերևային ստեղների հավաքածուն `en.json` հետ և ձախողվում է որևէ բացակայող կամ ավելորդ տերևի վրա՝ անկախ նրանից, թե երբ է ավելացվել բանալին: `__MISSING__:` տեղապահները հաշվում են որպես ներկա (նրանց բովանդակությունը հարաբերակցության դարպասի գործն է): `check-ui-keys-coverage` `check-new-key-coverage` diff-based/percentage դարպասների `en.json` լրացումն PR ~ Տեղական խմբաքանակը ստեղծվում է `en.json` ից այն օրը, երբ նրա ճյուղը կտրվում է և թարգմանվում է օրերով, մինչդեռ բազան շարունակում է ավելացնել բանալիներ. PR խմբաքանակն ինքնին ոչ մի բանալի չի ավելացնում, այնպես որ երկու եղբայրներն էլ լուռ մնացին, երբ խմբաքանակ 1 (#13044) վայրէջք կատարեց 43 ստեղնով կարճ ինը տեղանքում, իսկ խմբաքանակ 2 (#13660) 10 ստեղն կարճ ութում (2026-09-15): Կարմիրը ամրացրեք `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` ով; `extra` տերեւը նշանակում է, որ աղբյուրը գցել է այն — `sync-ui-keys` գցել այն (`--prune-extra`, լռելյայն): `--warn` առանց ձախողման հաղորդում է. `--catalog=cli` կատարում է նույն համեմատությունը `bin/cli/locales` (`npm run i18n:check-keys:cli`) նկատմամբ; երկու քայլերն էլ ապրում են աշխատանքում `i18n-ui-coverage`. Բացարձակ ստուգումը միայն թողարկման ռեժիմն է. PR հատկանիշը տեսնում է `SKIP reason=pr-mode` և ուղղումը գործարկվում է թողարկման թարմացման կամ թարգմանության ալիքի մեջ, երբեք PR ֆունկցիայի մեջ; PR, որը փոխում է տեղանքների կատալոգները, դրանցից յուրաքանչյուրը գնահատում է միաձուլման հիմքի փոխարեն (տես «Երկու ռեժիմ» աշխատանքը `i18n-ui-coverage` ում):

#### `check-new-key-coverage` — նոր բանալին i18n դարպաս

`check-ui-value-drift` քույրը կամ եղբայրը: Այդ մեկը բռնում է անգլիական արժեք, որը եղել է** վերաշարադրված** մինչդեռ դրա թարգմանությունները մնացել էին ետևում. սա բռնում է անգլերեն բանալին, որը եղել է** ավելացրել է** մինչդեռ որոշ տեղացիներ այն երբեք չեն ստացել:

`check-ui-keys-coverage` չի կարող տեսնել այս դասը. այն սահմանում է տոկոսային մակարդակ յուրաքանչյուր տեղանքի համար, և տասնմեկ բացակայող ստեղներ ~ ից 13,000 ծածկույթը թողնում է 99,9%: Մեկ լեզվի տոկոսը չի կարող արտահայտել «այս հատկանիշը ուղարկվել է չթարգմանված» — մի ամբողջ հատկանիշ կարող է հայտնվել նոր տեղանքում՝ առանց տեքստի և երբեք չտեղափոխել համարը:

Միջադեպը, որն այն ծածկագրում է. Նվագախմբի 3-րդ փուլը թարգմանել է իր տասնմեկ բանալիները այն ժամանակվա 42 տեղանքով: Ժամեր անց ԵՄ լեզվով խմբաքանակը (#13044) տարավ ռեպո 51 տեղանք, իսկ ինը նորեկները (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) երբեք չստացան դրանք։ `deepMergeFallback` անգլերենը փոխարինում է բացակայող բանալիով, ուստի ձախողման ռեժիմը թարգմանված չէ UI քան դատարկ UI — իրական, և անաղմուկ՝ ըստ կառուցման:

Ինչպես իր եղբայրն ու եղբայրը** տարբերվող** , համեմատելով անգլերենը միաձուլման հիմքում աշխատող ծառի հետ, այնպես որ նախկինում գոյություն ունեցող բացերը մնում են սառեցված, և դարպասը միացնելու համար միգրացիայի կարիք չուներ:

**`__MISSING__:<english>` նշիչը դա չի բավարարում (2026-09-17-ից):** Նախկինում դա եղել է փաստաթղթավորված հետաձգման — գործարկման ժամանակը վերադառնում է ուղղելու անգլերեն — մինչև ութ հատկանիշ PRs 2026-09-16-ին ավելացրին 61 ստեղներ և դրոշմեցին նշիչը բոլոր 65 տեղանքում թարգմանելու փոխարեն. > 2,5 % PRs 0,5 + : Մարկերն այժմ գնահատվում է որպես բացակայող թարգմանություն: Թողարկման ռեժիմը միայն 2026-11-13-ից. PR հատկանիշը տեսնում է `SKIP reason=pr-mode`, և PR (`BASE_REF=origin/main`) թողարկման ժամանակ դարպասը դատում է ավելացված ցիկլը յուրաքանչյուր բանալին: Ուղղեք կարմիր գույնը թողարկման թարմացման մեջ կամ թարգմանության ալիքը `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` ով, կամ բոլոր տեղանքները `npm run i18n:translate-new-keys` հետ զուգահեռ (`scripts/i18n/translate-new-keys.sh`, անջատված-անվտանգ, հրաժարվում է սկսել առանց `OMNIROUTE_TRANSLATION_*` env-ի): Բանալին, որը պետք է մնա անգլերեն (կցված product/engine/flag անուն) պատկանում է `scripts/i18n/untranslatable-keys.json` ին և երբեք չի գտնվում ցուցիչի հետևում: `vi` ուղղակիորեն արգելում է մարկերները (`tests/unit/i18n-vi-completeness.test.ts`):

#### `check-vitest-exclusions` — կայանված-թեստային դարպաս

`vitest.config.ts` ի `exclude` ցուցակի ֆայլը թեստ է, որը չի գործարկվում, և այն կարծես ծածկույթ է ով կարդում է ծառը: `// #8618 — pre-existing failure; remove this exclusion when fixed` մեկնաբանության հետևում կուտակվել է վաթսուներկու ֆայլ: #8618 թողարկումը փակվել է 2026-08-11-ին, մինչդեռ ցուցակը, որին հետևել է, 45 գրառումից հասել է 62-ի, որոնցից յուրաքանչյուրը ժառանգում է մեկնաբանություն, որը մատնանշում է մեռած խնդիր: Երբ ցուցակը վերջապես չափվեց ֆայլ առ ֆայլ (#13204),** 62-ից 51-ն ընդունվել է ընթացիկ ծառի դեմ՝ առանց աղբյուրի փոփոխության** .

Դարպասը պահանջում է իրական ֆայլի ցանկացած բացառում՝ (ա) անվանելու հետագծման խնդիր և (բ) `config/quality/vitest-exclusions.json` ում երևալու իր չափված կարգավիճակով, ուստի դրանց ավելացումը հատուկ ֆայլում վերանայվող տարբերություն է, այլ ոչ թե ևս մեկ տող 60 մուտք ունեցող զանգվածում: Այն միտումնավոր չի վերագործարկում բացառված թեստերը —, որոնք արժեն ~ 10 րոպե և պատկանում են պարբերական աշխատանքին. գույքագրման գրառումները, երբ յուրաքանչյուրը վերջին անգամ չափվել է:
