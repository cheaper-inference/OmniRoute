Այս փաստաթուղթը OmniRoute-ի բոլոր CI որակի անցակետերի հեղինակավոր տեղեկատուն է։
Այն նկարագրում է յուրաքանչյուր անցակետը, թե ինչ է այն վավերացնում, որ CI առաջադրանքում է գործարկվում, արդյոք օգտագործում է
աստիճանական ելակետ, թե անցնել/ձախողվել քաղաքականություն, և արդյոք արգելափակում է կառուցումը, թե ունի խորհրդատվական բնույթ։

Համառոտ ամփոփագրի և թույլատրվածների ցանկի քաղաքականության համար տե՛ս "Quality Gates & Ratchets" բաժինը

## Դարպասի գույքագրման և կատարման պրոֆիլներ

### Թեկնածուների ընդունելություն

CI և Quality Gates-ի աշխատանքային հոսքերը յուրաքանչյուրն արձակում է կայուն դատավճիռ՝ `Gate / CI` և `Gate / Quality`: Նրանց տարբերակված ընդունելության քաղաքականությունը թվարկում է յուրաքանչյուր վերին հոսքի աշխատանքը որպես պահանջվող կամ խորհրդատվական: Կիրառելի պահանջվող աշխատանքը պետք է հաջողվի. բացակայող, չեղարկված, բաց թողնված, սպասող և անհայտ արդյունքները չեն կարող հաստատել PASS: Միայն փաստաթղթերի կամ միայն կատալոգի համար նախատեսված վավեր դասակարգումը կարող է անկիրառելի դարձնել ծածկագրի գոտին. a draft PR ընդունված թեկնածու չէ: `hotfix` պիտակը չի հրաժարվում ապացույցներից:

Երկու աշխատանքային հոսքերն էլ ներառում են PRs main/release ճյուղերի, մղումներ դեպի `main`, ձեռքով ուղարկում և միաձուլման խմբավորման իրադարձություններ: Հրել, ուղարկել և միաձուլել ամբողջ ընտրությունը: `release/**` վրա սեղմումները չեն սկսում դրանք (2026-10-18). յուրաքանչյուր փոփոխություն արդեն գործարկել է մատրիցը իր PR վրա, և միաձուլված համակցությունը Release-Green-ի գործն է (`docs/ops/RUNNER_BOX.md` → Hosted lane): Forks-ը և միաձուլման խմբերը օգտագործում են հյուրընկալված վազորդներ այն աշխատանքների համար, որոնք այլ կերպ ընտրում են ինքնուրույն վազորդներ. Բավարար հյուրընկալող հզորությունը պետք է ստուգվի նախքան թողարկումը:

Սովորական PR վարում է արագ ընտրությունը: Ընդունման քաղաքականության `full-code` և `full-code-e2e` ուղիները (E2E, ինտեգրում, փաթեթի արտեֆակտ, Electron smoke, Bun SQLite, էկոհամակարգ և արձանագրության հաճախորդներ) աշխատում են միայն Mergify հերթի նախագծի վրա կամ ամբողջական գործարկումով՝ `gh workflow run ci.yml --ref <branch>`:

Յուրաքանչյուր JSON անդորրագիր նույնականացնում է դուրս գրված SHA, աշխատանքային հոսքի գործարկումը և փորձը: CLI ն մերժում է checkout/event SHA անհամապատասխանությունը: Աշխատանքային հոսքի թեստերը կապում են քաղաքականության անդամակցությունը դատավճիռների աշխատանքի `needs` ցուցակին, այնպես որ նոր կամ հեռացված գոտին չի կարող լուռ անհետանալ: Անդորրագրերը ծածկում են իրենց սեփական աշխատանքային հոսքը, այլ ոչ թե հրապարակումը, տեղակայումը կամ առկա խորհրդատվական սկաների ներքին կառուցվածքը: Մասնաճյուղի կանոններում երկու ստուգման անվանումների ակտիվացումը առանձին վարչական փոփոխություն է. Այս աշխատատեղերի ավելացումն ինքնին չի պաշտպանում մասնաճյուղը:

### Միավորել հերթ

`queue` պիտակը PR է ուղարկում Mergify հերթին (`.mergify.yml`): Mergify-ը բացում է PR նախագիծը `mergify/merge-queue/` ճյուղում, CI այնտեղ գործարկում է ամբողջական ընտրությունը, իսկ սկզբնական PR միաձուլվում է, երբ `Gate / CI`, `Gate / Quality` և `Merge integrity (changelog + generated skills)` անցնում են:

Mergify-ը գրում է իր հերթի ամփոփագիրը սևագրի նկարագրության մեջ, և մյուս հավելվածները նույնպես կարող են խմբագրել այն: Նման սևագրի վրա `pull_request` `edited` իրադարձությունը վերցնում է իր համաժամանակյա խումբը (`-queue-edit-<run_id>`), ուստի այն չի կարող չեղարկել սևագրի իրական ընթացքը և բաց է թողնում դարպասը և մատրիցը: Միայն `Merge integrity` է դեռ աշխատում: Բաց թողնված դարպասի աշխատանքը կրում է այլ ստուգման անուն, քանի որ Mergify-ը կարդում է բաց թողնված `Gate / CI` որպես ձախողված ստուգում և փակում է PR ը:

Dequeue-ից հետո մղումը միշտ չէ, որ պահանջում է PR: Մեկնաբանություն `@mergifyio queue` դրա վերաբերյալ:

### Պահպանված ապացույցներ ընդունման կրճատիչում

`scripts/quality/validate-release-acceptance.mjs` նվազեցնում է մատակարարված պլանը և դրա դրսևորումները. այն չի սահմանում, որ պլանն ընդգրկում է ամբողջական թողարկման խողովակաշարը: Նրա հաշվետվությունները հստակորեն սահմանում են `releaseAcceptance: false`, նույնիսկ երբ այդ պլանը `VERIFIED` է: `release-acceptance.yml` աշխատանքային հոսքը դեռ օգտագործում է ստվերային հարմարանքներ, այլ ոչ թե իրական կառուցման, փաթեթի, բեռնախցիկի կամ առաջխաղացման անդորրագրեր:

CLI ն պահանջում է `--evidence-root` ՝ պահպանված ապացույցները ստուգելու համար: Ֆայլերը լուծվում են որպես `<evidence-root>/<artifact_id>/<member>` և հեշացված են որպես SHA-256: PASS գրառումն առանց ապացույցների, բացակայող կամ փոփոխված ֆայլի, անապահով ուղու կամ սիմվոլկի կանխում է ստուգումը: Բացակայող ֆայլերը համարժեք չեն դատարկ հաջողված տեղեկամատյաններին: Առկա SHA/run/attempt ստուգումները մնում են անկախ. համապատասխան բայթերը չեն կարող փրկել հնացած անդորրագիրը: Ֆայլի ամբողջականությունը կատարման իսկության կամ արտեֆակտի առաջմղման ապացույց չէ:

### Ստատիկ սկանավորման գույքագրում

Տարբերակված npm-alias գույքագրումը և ստատիկ սկանավորման անդամակցությունը ապրում են `config/quality/gate-manifest.json` ում: Գործարկեք `npm run check:gate-manifest` սկրիպտների անունները և ճշգրիտ հրամանները `package.json` դեմ վավերացնելու համար; լրացումները, հեռացումները և հրամանների դրեյֆը ձախողվում են ինչպես տեղական կեռիկը, այնպես էլ փոփոխության դասակարգման աշխատանքները CI ում: Այլանունը աշխատանքային հոսքի աշխատանք, մատրիցային օրինակ կամ փորձնական դեպք չէ. այս հաշվումները չպետք է ներկայացվեն որպես փոխարինելի:

Օգտագործեք `npm run quality:scan -- --list` կամ `npm run quality:scan:fast -- --list` ՝ ստուգելու ընտրված այլանունները՝ առանց դրանք գործարկելու: Վազողը կանչում է npm մուտքի կետը, ուստի դրա գործարկման ժամանակը (ներառյալ Bun, որտեղ կազմաձևված է) պահպանվում է: Մանիֆեստը գրանցում է այլանուններ այդ պրոֆիլներից դուրս՝ որպես առանձին կանչված, և սպասարկման հրամաններն արգելված են միայն կարդալու սկանավորման պրոֆիլներում:

Այս պրոֆիլները ծածկում են միայն ստատիկ սկանավորումը: Նրանք չեն հավաստում արտադրանքի թեստերը, ծածկույթը, փաթեթավորումը, արտաքին ստուգումները կամ թեկնածուի թողարկման ամբողջական ընդունումը: Աշխատանքային հոսքի ընդունումը օգտագործում է կապված `config/quality/admission-policy.json` և `scripts/quality/admission-verdict.mjs`: Ազատման դիտորդի պրոֆիլները մնում են առանձին. ինքնուրույն ստուգել դրանց կիրառելի չեկերն ու անդորրագրերը: Դիտորդի ամբողջական ստատիկ հրամանները հայտարարված են `config/quality/release-green-static-profile.json`, ներառյալ `audit:deps`, մուտացիայի թեստի ընտրությունը և թարգմանության ստուգումները: Բեռնիչը վավերացնում է npm հրամանները package.json և մոդելավորված CI/Quality հայտարարագրերի դեմ; այն մերժում է դրեյֆը՝ shell նշանները որպես փաստարկներ գործարկելու փոխարեն: Պահանջվող սկաների SKIP/INCOMPLETE ելքը չի կարող հաստատել PASS: Պրոֆիլը գրանցում է իր արտաքին բացառումները և չի փոխարինում հյուրընկալված ծածկույթին, փորձարկման մատրիցներին, փաթեթին կամ տեղակայման ապացույցներին: Ստորև բերված արձակի գույքագրումը հղում է, այլ ոչ թե ապացույց, որ դարպասը իրականում վազել է:

Սցենարները ապրում են `scripts/check/` (քաղաքականության դարպասների) և `scripts/quality/` (չեղջավոր շարժիչի) տակ: Ճշմարտության CI աղբյուրը `.github/workflows/ci.yml` է:

### Թողարկեք PR արագ ճանապարհը (`quality.yml`)

`.github/workflows/quality.yml` լրացնում է CI main/release PRs ում, հրում է `main`, ուղարկում և միավորում խմբերը: PRs օգտագործում է ճանապարհով զտված արագ ստուգումներ: Մշտապես անջատված կրկնօրինակ կառուցվածքը հեռացվել է. իրական build/package/boot չեկերը մնում են CI. Միավոր հավաքակազմը և վիտեստը գործում են միայն CI ով (`Unit Tests (N/8)` և `Vitest`):

| Աշխատանք                                         | Շրջանակ                                                                                                                                                   | Արգելափակում                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API docs refs և docs-all                                                                                                                   | Այո՛                        |
| `Fast Quality Gates`                             | Կոդ PRs; ստատիկ ստուգումներ, տիպի ստուգում, վահանակի տառատեսակի ստուգում, ազդակիր միավորի թեստեր, մոռացված եղբայրների և եղբայրների թեստեր (խորհրդատվական) |
| `No new ESLint warnings`                         | Կոդ PRs; suppressions-aware lint guard                                                                                                                    | Այո, ներառյալ պատառաքաղները |
| `Merge integrity (changelog + generated skills)` | Ոչ նախագիծ PRs; փոփոխության մատյան և գեներացված հմտությունների համաժամեցում                                                                               | Այո, ներառյալ պատառաքաղները |

#### Մոռացված եղբայրների կամ քույրերի թեստերի հաշվետվություն

`npm run check:forgotten-sibling-tests` աշխատում է որպես `Fast Quality Gates` ի խորհրդատվական քայլ և նորից օգտագործում է ներմուծման լուծիչը փորձարկման ազդեցության քարտեզի հետևում: Յուրաքանչյուր փոփոխված արտադրական մոդուլի համար այն հաղորդում է որոշիչ `changed module/symbol -> static consumer -> candidate sibling test` շղթաներ, երբ թեկնածուի թեստը բացակայում է ձգման պահանջի տարբերությունից: Markdown-ի ամփոփագիրը և JSON արդյունքը պահպանվում են որպես `forgotten-sibling-tests` աշխատանքային հոսքի արտեֆակտ՝ նախքան որևէ արգելափակման տեղակայումը չափորոշման համար:

Տակառի վերաարտահանումը և դինամիկ ներմուծումը միայն լուծման ախտորոշիչ են. նրանք երբեք արգելափակող գտածո չեն ստեղծում: Վերանայված բացառությունները ապրում են `config/quality/forgotten-sibling-allowlist.json` ում: Յուրաքանչյուր գրառում պետք է անվանի սպառողի և թեկնածուի թեստը, տա կոնկրետ հիմնավորում և կապի GitHub խնդիր կամ ձգողական հարցում: Սխալ մուտքերը փակ են: Բացառությունները չեն կարող ճնշել ջնջված թեկնածուի թեստը կամ տարբերությունը, որն ավելացնում է `.skip`/`.todo`; պնդման թուլացումը և այլ դիմակավորումը մնում են ինքնուրույն արգելափակող `check:test-masking` gate-ի սեփականությունը:

### Աշխատանքը՝ `lint`

Աշխատում է յուրաքանչյուր PR վրա `main` վրա: Բլոկները միաձուլվում են ձախողման դեպքում:

| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `check:node-runtime`              | Node.js տարբերակը գտնվում է աջակցվող տիրույթում                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Այո՛                                          |
| `check:cycles`                    | Շրջանաձև ներմուծումներ ամբողջ `src/` + `open-sse/` (AST-ի վրա հիմնված, tsconfig `paths` լուծված): Bare-ը դուրս է գալիս 1-ից, երբ որևէ ցիկլ գոյություն ունի (fail-փակ է #15281 ից) և թվարկում է SCCs ը: `check:cycles:ratchet` (ինչ է աշխատում CI ) արգելափակում է, երբ հաշվարկը գերազանցում է `metrics.cycles` առաստաղը `quality-baseline.json` — ում ներկայումս 14, `direction: down`, այնպես որ այն կարող է ընկնել միայն (#15159 G-01/G-02)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Այո (չարչան)                                  |

#### Երկու տիպի ստուգման ծրագրեր տարբեր կերպ են պատասխանում

`typecheck:core` և `check:build-typecheck` տարբեր ծրագրեր են կազմում տարբեր տարբերակների ներքո, և նույն ֆայլը կարող է մեկում մաքուր լինել, իսկ մյուսում՝ լի սխալներով:

`tsconfig.build.json` սահմանում է `"strict": false`, ուստի `noImplicitAny` անջատված է: Հիմնական կազմաձևը կազմում է ընտրված 27 ֆայլի թույլտվությունների ցանկ՝ ավելի խիստ ընտրանքներով և հետևում է յուրաքանչյուր մուտքի ներմուծման գրաֆիկին, այնպես որ ֆայլերը, որոնք երբեք չեն հայտնվում կառուցման ծրագրում, դեռ ստուգվում են այնտեղ:

Հետևանքը կարևոր է, երբ դատում ենք, թե արդյոք ֆայլը մուտքագրված է.** զրոյական ախտորոշումը `check:build-typecheck` տակ չի նշանակում զրո** . 26 ֆայլերից `@ts-nocheck` ից հեռացնելը ցույց տվեց, որ դրանցից 23-ը մաքուր են build ծրագրում; Նրանցից տասնվեցը բացահայտեցին մոտ 120 անուղղակի սխալներ խիստ սխալի մեջ: Ստուգեք երկուսն էլ՝ նախքան ֆայլը մաքուր կանչելը:

#### `check-ui-value-drift` — հնացած-թարգմանական դարպաս

Բռնում է i18n մեկ ռեգրեսիան, որը մյուս դարպասները կառուցվածքային առումով չեն կարող տեսնել. անգլերեն արժեքը վերագրվում է, իսկ _նախորդ_ անգլերենից ստացված թարգմանությունները մնում են հետևում, այնպես որ ոչ անգլերեն օգտվողները շարունակում են կարդալ վստահորեն ձևակերպված, այժմ սխալ պատճենը:

Սա առաքվել է իրական: `oauthModal.googleOAuthWarning` նորից գրվեց, երբ Antigravity մուտքի օգնականը վայրէջք կատարեց (#5203);** 43 տեղանքից 39-ը** պահպանեց տեքստը, որով օպերատորներին ասում էր «պատճենել ամբողջական URL և տեղադրել այն ներքևում» — մի հոսք, որը չի կարող ավարտվել այդ մատակարարի համար: Այն աննկատ մնաց մինչև #8463 քանի որ.

- `sync-ui-keys` լցնում է միայն այն բանալիները, որոնք կան** բացակայում է** , երբեք այնպիսիք, որ կան** հնացած** ;
- `check-ui-keys-coverage` հաշվում է բանալին _presence_, ուստի հնացած թարգմանությունը գնահատվում է որպես ծածկված;
- `check-translation-drift` հետևում է `docs/i18n/<locale>/**.md` փաստաթղթերին, հայելիներ — այն երբեք չի կարդում `src/i18n/messages/*.json`: Արգելափակվում է `docs-sync-strict` աշխատանքը 2026-09 թվականների վերահամաժամեցումից հետո. խմբագրել → `npm run i18n:run -- --files=<doc>` հիմնական փաստաթուղթը (հատվածի մակարդակ, էժան):

**Տարբերությունների գիտակցում, ոչ բազային հիմքով:** Այն համեմատում է `en.json` միաձուլման հիմքում աշխատող ծառի հետ. յուրաքանչյուր ստեղնի համար, որի անգլերեն արժեքը փոխվել է, ցանկացած տեղանք, որը դեռևս անձեռնմխելի թարգմանություն է պահում, հնացած է: Սա միտումնավոր** սառեցնում է նախկինում գոյություն ունեցող պարտքը** — a diff-ը չի կարող բացահայտել, թե որ հին անգլերենից է առաջացել երկարամյա թարգմանությունը, ուստի դարպասը դատում է միայն այն, թե ինչ է շոշափում ընթացիկ փոփոխությունը: Այլընտրանքը (յուրաքանչյուր բանալիի հեշի բազային գիծ) կարժենա ~ 600 KB գեներացված ֆայլ, 3 × ամենամեծ գոյություն ունեցող բազային գիծը, որը կծկվի յուրաքանչյուր i18n PR վրա:

Այն բավարարելու երկու եղանակ.

1. թարմացնել ազդակիր թարգմանությունները, կամ
2. դրեք դրանք `__MISSING__:<new english>` — գործարկման ժամանակի վրա, այնուհետև սպասարկում է շտկված անգլերենը (`src/i18n/request.ts::deepMergeFallback`, #7258) և թարգմանության հիմնական հերթերը:

Եթե լարը** իմաստը** փոխվել, նախընտրել** բանալին վերանվանելով** Նոր բանալին չի կարող ժառանգել հնացած թարգմանություն: Դա #8463 օրինաչափությունն է:

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Դուրս է գալիս 0-ից `SKIP reason=base-unresolved` ով, երբ բազային կատալոգը հնարավոր չէ կարդալ (ծանր կլոն առանց բազային ref-ի), արտացոլելով `check-openapi-breaking`:

(`scripts/check/newCodeMode.mjs`. merge-base-ը տեղակայվում է ժամանակավոր
`git worktree`-ում, ESLint/knip-ը գործարկվում են այնտեղ և HEAD-ի վրա, ապա համեմատվում են յուրաքանչյուր ֆայլի քանակները).

- **արգելափակող** — PR-ն ավելացրել է ցիկլոմատիկ/կոգնիտիվ բարդության խախտումներ կամ չօգտագործվող արտահանումներ իր փոփոխած ֆայլերում
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` մատյանում).
- **խորհրդատվական** — գլոբալ ընդհանուր արժեքը՝ սառեցված ելակետային արժեքի համեմատ։ Ժառանգված շեղումը երբեք չի ձախողեցնում
  դրա հետ կապ չունեցող PR-ը. շեղումը կրկին սառեցվում է թողարկման համաձայնեցման ժամանակ և վերահսկվում պահուստի առաջադրանքի կողմից։

`check:file-size`-ը բազային հղումն օգտագործում է իր կանոններով (`scripts/check/check-file-size.mjs`, #8522).
այն ստուգում է ծառի յուրաքանչյուր սկզբնաղբյուրային և թեստային ֆայլ, `git show`-ի միջոցով կարդում է դրանցից յուրաքանչյուրի տողերի քանակը PR-ի բազայում
և ֆայլը ձախողված է համարում միայն այն դեպքում, երբ այն աճում է՝ գերազանցելով իր ելակետային վերին սահմանից
(`frozen` / `testFrozen`, կամ `cap` / `testCap`՝ ելակետում չներառված ֆայլի համար) և բազային չափից
ավելի մեծ արժեքը։ Հետևաբար բազայում արդեն շեղված ֆայլը երբեք չի ձախողեցնում դրա հետ կապ չունեցող PR-ը։

`check:boundary:ratchet`-ը նույն կանոնը կիրառում է իր միակ թվի նկատմամբ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`)․ PR իրադարձությունների դեպքում և՛
`quality.yml`-ի արագ դարպասները, և՛ `ci.yml`-ի lint առաջադրանքը փոխանցում են PR-ի բազային SHA-ն, բազային commit-ը
չափվում է `git archive` արտահանումից, իսկ PR-ը ձախողվում է միայն այն դեպքում, երբ դրա `open-sse → src` եզրերի
քանակը գերազանցում է `metrics.boundaryOpenSseToSrc`-ի և բազային տարբերակի քանակի առավելագույնը։ Շեմից
բարձր բազային շեղման մասին հաղորդվում է (`base drift herdado`), սակայն այն երբեք չի ձախողում անմեղ PR-ը․ push → main-ը
պահպանում է բացարձակ շեմը, իսկ չլուծվող բազային SHA-ի դեպքում նախազգուշացմամբ կիրառվում է այդ շեմը։

`workflow_dispatch` գործարկումները, release-green ամբողջական ստուգումը և գիշերային ազատ պաշարի առաջադրանքը PR-ի բազային տարբերակ
չունեն և պահպանում են բացարձակ (գլոբալ) համեմատությունը։ Ծածկույթը, կրկնօրինակումն ու տիպերի ծածկույթն առայժմ մնում են գլոբալ
(դրանց գործիքները չեն ստեղծում ըստ ֆայլերի տարբերությունը ցածր ծախսով)՝ նույն մոտեցումը հետագայում կիրառելու թեկնածուներ։

**Փուլի ավարտը v4.0-ում (LTS = նախկինից ավելի խիստ, ոչ թե «վերադարձ բնականոն վիճակին»)**

1. Մաքուր `release/v4.0.0` ճյուղի վերջին commit-ի վրա՝ արձանագրության համար գործարկել `npm run quality:headroom --json`, ապա՝
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ինչպես նաև յուրաքանչյուր typecheck դարպասի
   `--update`-ը․ յուրաքանչյուր բազային արժեք իջեցվում է մինչև չափված արժեքը։
2. Հեռացնել `_policy`-ն `quality-baseline.json`-ից (կրկին ակտիվացնում է `--require-tighten`-ը և գիշերային
   կուտակումը), վերականգնել `THRESHOLD = 36`-ը (կամ ավելի բարձր արժեք) `check-openapi-coverage.mjs`-ում։
3. Այնտեղ, որտեղ մոդուլավորումն արդյունք է տվել, սահմանները չափված արժեքներից էլ ավելի խստացնել․ file-size `cap`-ը վերադարձնել 1000-ի
   (կամ 800-ի), ծածկույթի նվազագույն շեմերը՝ +5, իսկ մոդուլավորված փաթեթների dead exports-ը՝ 0։

## Ratchet-ի ելակետային մակարդակ (`quality-baseline.json`)

Ratchet շարժիչը (`scripts/quality/check-quality-ratchet.mjs`) կարդում է `quality-baseline.json`-ը
և համեմատում այն նոր հավաքված `quality-metrics.json`-ի հետ։ Ցանկացած չափիչի՝ իր epsilon-ից
ավելի վատթարացումը ձախողում է build-ը։

Ներկայումս հետևվող չափիչները՝

| Չափիչ                 | Ուղղություն | Նշանակություն                                  |
| --------------------- | ----------- | ---------------------------------------------- |
| `eslintWarnings`      | `down`      | ESLint-ի նախազգուշացումների քանակը չպետք է աճի |
| `coverage.statements` | `up`        | Հրահանգների ծածկույթը չպետք է նվազի            |
| `coverage.lines`      | `up`        | Տողերի ծածկույթը չպետք է նվազի                 |
| `coverage.functions`  | `up`        | Ֆունկցիաների ծածկույթը չպետք է նվազի           |
| `coverage.branches`   | `up`        | Ճյուղերի ծածկույթը չպետք է նվազի               |

Իրական բարելավումից հետո ելակետային մակարդակը թարմացնելու համար՝

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` դրոշը ներկայումս չափված արժեքները գրում է `quality-baseline.json`-ում։
Commit արեք այս ֆայլը չափիչը բարելաված փոփոխության հետ միասին։ Չափիչը բարելավող,
սակայն ելակետային մակարդակը չթարմացնող PR-ը կբացահայտվի `--require-tighten`-ի միջոցով (փուլ 6A.5,
իրականացումը սպասվում է)։

### CodeQL ratchet. թարմացման հաճախականությունը և ձեռքով գործարկումը

`check:codeql-ratchet`-ը կարդում է **պահոցի վիճակը, որը թարմացվում է ժամանակացույցով, այլ ոչ թե յուրաքանչյուր PR-ի համար։**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup`-ը հաղորդում է
`state: configured`, `schedule: weekly`՝ GitHub-ի լռելյայն կարգավորմամբ սկանավորում, այլ ոչ թե յուրաքանչյուր push-ի
վերլուծություն։ Հետևանքը՝ ահազանգերը ՇՏԿՈՂ PR-ի միաձուլումից հետո ratchet-ը շարունակում է կարդալ
հին՝ ավելի մեծ քանակը, մինչև հաջորդ ժամանակացուցային սկանավորումը գործարկվի, ուստի այն հետընթաց է արձանագրում
յուրաքանչյուր բաց PR-ի համար՝ ներառյալ շտկող PR-ի հետագա փոփոխությունները, մինչև սկանավորումը հասնի դրանց։

**Ձեռքով թարմացում**. `gh workflow run codeql.yml --ref release/vX.Y.Z`-ը կրկին գործարկում է
վերլուծությունը և րոպեների ընթացքում վերահրապարակում ահազանգերը։ Նախ կարդացեք `.github/workflows/codeql.yml`-ը.
դրա վերնագիրը բացատրում է, որ այն միայն `workflow_dispatch`-ով է գործարկվում, **քանի որ հակասում է
GitHub-ի «լռելյայն կարգավորմանը»** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`)։ `push`/`pull_request`/
`schedule` գործարկիչների վերականգնումը նախ պահանջում է **սեփականատիրոջ գործողություն**՝ Settings → Code security →
CodeQL: Default → Advanced։ Առանց այդ փոխարկման մի ավելացրեք `schedule:` գործարկիչ՝ այն
միայն ձախողված գործարկումներ կառաջացնի։

**Քանակի նվազումից հետո խստացրեք ելակետային մակարդակը** — `node scripts/check/check-codeql-ratchet.mjs
--update`-ը նոր չափված քանակը գրում է `quality-baseline.json` →
`metrics.codeqlAlerts.value`-ում, որպեսզի ratchet-ը լռելյայն չթույլատրի հետընթաց դեպի
հին վերին շեմը։ Իրական օրինակ (2026-09-02/03). PR #12502-ը շտկեց 7 իրական ահազանգ
(չափված բաց ահազանգերը՝ 13 → 6), PR #12530-ը սառեցված ելակետային մակարդակը խստացրեց 11 → 6՝ համապատասխանեցնելու համար, իսկ
մնացած 6-ը հետագայում մերժվեցին՝ յուրաքանչյուր ահազանգի համար հիմնավորում ներկայացնելով, մինչև բաց ահազանգերի քանակը դարձավ 0։

**Մերժումները օպերատորի որոշումն են (Կոշտ կանոն #14)** — երբեք մի մերժեք CodeQL ահազանգը
առանց մերժման մեկնաբանությունում տեխնիկական հիմնավորումը գրանցելու. `won't fix`՝
վերին մակարդակի արձանագրության պահանջի համար, `used in tests`՝ թեստային ֆիքստուրայի համար, `false positive`՝
այն sanitizer-ի համար, որը CodeQL-ը չի կարող տեսնել (նախադեպ՝ `docs/security/ERROR_SANITIZATION.md`)։

Թիրախային SLO-ները՝ անկայունության հեռաչափության ներդրումից հետո (WS5.2/5.3). յուրաքանչյուր թեստի համար անկայունության մակարդակը՝ <1%
(«շտկել հիմա» շեմ), յուրաքանչյուր խողովակաշարի համար անցման մակարդակը՝ ≥95%։ Ոլորտի հղումային արժեքներ են.
վերաչափարկեք դրանք՝ ըստ մեր սեփական չափումների։

## Թողարկման մակարդակի սահմանափակիչի շեղում (WS5.5, v3.8.49)

Երբ սահմանափակիչը (ֆայլի չափ, բարդություն, eslint-ի զգուշացումներ) հետընթաց է գրանցում ՄԱՔՈՒՐ թողարկման
վերջնակետում, այսինքն՝ հետընթացն առաջացել է միաձուլումների ՀԱՄԱԿՑՈՒԹՅՈՒՆԻՑ, և ոչ մի առանձին PR այն չի վերարտադրում
իր սեփական ճյուղում, շտկումը պատկանում է **թողարկման պատասխանատուին՝ մեկ անգամ, թողարկման
ճյուղում**. նախընտրեք առանձնացումը/վերակառուցումը, իսկ ելակետը փոխեք միայն փաստաթղթավորված
հիմնավորման գրառմամբ։ Երբեք համակցությունից առաջացած շեղումը մի վերագրեք մասնակցի PR-ին և երբեք
մի փոխեք ելակետը յուրաքանչյուր PR-ի համար (դա թաքցնում է իրական ռեգրեսիաները)։ Նախ տարբերակեք պատճառը.
կարմիր կարգավիճակը վերարտադրեք մաքուր վերջնակետի նկատմամբ՝ փորձնական worktree-ում, նախքան ենթադրելը, որ այն առաջացրել է ձեր PR-ը։

## Սահմանափակիչների նվազեցումների ամրագրում՝ նվազման ուղղությունը (#8584)

Սահմանափակիչն ավտոմատ է միայն կիսով չափ, ընդ որում՝ սխալ կեսով։ Սահմանաչափի **բարձրացումը**
ձեռքով JSON-ի խմբագրում է, որը տևում է տասը վայրկյան և կարմիր PR-ն ապաշրջափակելու ամենաարագ եղանակն է։
Այն **նվազեցնելու** համար որևէ մեկը պետք է գործարկի `--update` և commit անի արդյունքը, իսկ մինչև
`bank-ratchet-shrinks` առաջադրանքի ներդրումը դա չէր անում ոչ մի workflow։ Չափված հետևանքը
(2026-07-25). 18 սառեցված ֆայլ արդեն գտնվում էր նոր ֆայլերի 800 տող սահմանաչափի մակարդակին կամ դրանից ներքև, իսկ վատագույնը՝
132× (`src/shared/validation/schemas.ts`, 19 տող՝ 2,523 սահմանաչափով), բարդության վերին շեմը
մոտավորապես 37 ելակետի փոփոխման նշումների ընթացքում բարձրացել էր `1794 → 2169`՝ ունենալով ճիշտ մեկ
նվազում (−1), իսկ «հաջորդ շրջափուլում խստացնել `--update`-ի միջոցով» գրառվել էր 31 անգամ և կատարվել՝
մեկ անգամ։ Սահմանաչափը, որը շարունակում է գոյություն ունենալ իրեն առաջացրած կոդից ավելի երկար, յուրաքանչյուր ավարտված
տրոհում աննկատ վերածում է աճի թույլտվության՝ ֆայլը հաջորդը խմբագրող անձի համար։

`nightly-release-green.yml` → **`bank-ratchet-shrinks`** առաջադրանքը փակում է այդ շրջափուլը.

|               |                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Գործարկվում է | `schedule` (օրական 3×) + `workflow_dispatch` — միտումնավոր **ոչ** `push`-ով                                              |
| Չափում է      | ամենաբարձր `release/vX.Y.Z`-ը՝ նույն լուծման և ներմուծումից պաշտպանության մեխանիզմով, ինչ `release-green`-ը              |
| Գրում է       | `check:file-size --update` և `check:complexity-ratchets --update` (երկուսն էլ կառուցվածքով միայն նվազեցնող են)           |
| Ստուգում է    | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                 |
| Առաքում է     | թողարկման ճյուղի նկատմամբ միշտ արդիական մեկ PR՝ հարկադրաբար թարմացվող, երբեք ավելորդ հաղորդագրություններով չծանրաբեռնված |

Ամրագրումը կատարվում է խմբաքանակով, ոչ թե յուրաքանչյուր push-ի դեպքում, քանի որ այն չունի ուշացման պահանջ
(8 ժամվա ընթացքում ամրագրված նվազեցումը լիովին ընդունելի է), մինչդեռ յուրաքանչյուր միաձուլման գործարկումը բազմիցս կվերակառուցեր
PR-ի ճյուղը միաձուլման արշավների ընթացքում և ամեն անգամ կվճարեր ESLint-ի ամբողջական անցման արժեքը։ Հայտնաբերումը
շարունակում է կատարվել push-ի ժամանակ (`release-green`), իսկ խմբաքանակով կատարվում է միայն ամրագրումը։

### Անվտանգության ստուգիչը

Առաջադրանքն առանց վերահսկման գրում է ելակետերում, ուստի հենց `verify-ratchet-bank.mjs`-ն է դա
ընդունելի դարձնում։ Այն համեմատում է `--update`-ից հետո ստացված ծառը `HEAD`-ի հետ և **ընդհատում է առաջադրանքը
նախքան որևէ commit-ի ստեղծումը**՝ առանց PR բացելու, եթե բոլոր փոփոխությունները հետևյալներից որևէ մեկը չեն.

- `frozen` / `testFrozen` թվային գրառում, որը **նվազեցվել** կամ **հեռացվել** է
- `complexity-baseline.json` → `count`՝ **նվազեցված**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value`՝ **նվազեցված**

Ցանկացած այլ բան հանգեցնում է ձախողման՝ թվի բարձրացումը, գրառման ավելացումը, `cap`/`testCap`-ի փոփոխությունը կամ
`_rebaseline_*` նշման ջնջումը/վերագրումը (այդ նշումները յուրաքանչյուր վերին շեմի գոյության պատճառների աուդիտային պատմությունն են
և պահվում են նույն `frozen` օբյեկտում, ինչ ֆայլերի գրառումները)։
Բոտը, որը կարող է բարձրացնել սահմանաչափը, հաստատ ավելի վատ կլիներ, քան առկա վիճակը։ Ռեգրեսիայից պաշտպանություն՝
`tests/unit/verify-ratchet-bank.test.ts`։

Առաջադրանքը երբեք push չի անում դեպի `release/*`. PR-ը միաձուլում է մարդը, ուստի սխալ չափումը
չի կարող հայտնվել համակարգում առանց ստուգման։

## Թույլտվությունների ցանկի քաղաքականություն

Յուրաքանչյուր դարպաս, որը չի կարող ձախողել նախկինում գոյություն ունեցող խախտումները, օգտագործում է սառեցված թույլտվությունների ցուցակ (օրինակ՝ `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`): Քաղաքականությունը հետևյալն է.

**Ուղղել հիմնական պատճառը; օգտագործեք թույլտվությունների ցանկը միայն այն դեպքում, երբ խախտումը նախապես գոյություն ունի և չի կարող ֆիքսվել նույն PR ում:**

Թույլտվությունների ցանկում գրառում ավելացնելիս՝

1. Ներառեք մեկնաբանություն հիմնավորման հետ:
2. Անդրադարձեք հետևելու խնդրին (օրինակ՝ `// #3498 — Phase 2 feature, not yet implemented`):
3. Հեռացրեք այն նույն PR ի մուտքը, որը ֆիքսում է խախտումը — հնացած գրառումը, որն այլևս չի ճնշում ակտիվ խախտումը, ինքնին թերություն է (6A.3 հնացած կիրարկումը թույլ չի տա որբացած թույլտվության ցուցակի մուտքը, երբ իրականացվի):

Արեք** ոչ** ավելացրեք թույլտվությունների ցանկը, որպեսզի թեստերն ավելի արագ անցնեն: Աճող թույլտվությունների ցանկով կանաչ դարպասը որակի կեղծ զգացում է:

### Երբ դարպասը ձախողվում է ձեր PR վրա

1. **Ուշադիր կարդացեք դարպասի ելքը** — այն հստակ ասում է, թե որ ֆայլը կամ խորհրդանիշն է խախտել կանոնը:
2. **Ուղղել խախտումը** — դարպասների մեծ մասը դետերմինիստական ֆայլային համակարգի ստուգումներ են, որոնք անցնում են հենց կոդը ճիշտ է:
3. **Եթե խախտումը նախապես գոյություն ունի** (այսինքն, դուք չեք ներկայացրել այն, բայց դարպասն այժմ ծածկում է այն). ավելացրեք թույլտվության ցուցակի գրառում՝ հիմնավորման մեկնաբանությունով և հետևելու խնդրի հետ:
4. **Եթե դարպասը ճարմանդ է** (ծածկույթ, ESLint նախազգուշացումներ, կրկնօրինակում, բարդություն). Ուղղեք հիմքում ընկած խնդիրը կամ (հազվադեպ) գործարկեք `npm run quality:ratchet -- --update`, եթե փոփոխությունը միտումնավոր է, և մետրային դեգրադացիան ընդունելի է — բայց փաստեք, թե ինչու է PR նկարագրության մեջ:
5. **Խորհրդատվական դարպասներ** (`continue-on-error: true`) տեղեկատվական — են, դրանք չեն արգելափակում միաձուլումը, այլ հայտնվում են CI ամփոփագրում: Ուղղեք դրանք ամեն դեպքում:

## Նոր ստուգիչի ավելացում

1. Ստեղծեք `scripts/check/check-<name>.mjs` (կամ `.ts`)։ Քաղաքականության ստուգիչներն ավարտվում են 0/1 կոդով։
   Ռատչետ տեսակի ստուգիչները չափանիշ են գրում `quality-metrics.json`-ում՝ `collect-metrics.mjs`-ի միջոցով։
2. `package.json`-ում ավելացրեք `"check:<name>": "node scripts/check/check-<name>.mjs"`։
3. Միացրեք այն `.github/workflows/ci.yml`-ում՝ համապատասխան job-ի ներքո
   (քաղաքականություն → `lint` կամ `docs-sync-strict`, ռատչետ → `quality-gate`)։
4. Եթե այն ունի թույլատրվածների ցանկ, կիրառեք `reportStaleEntries()`-ը
   `scripts/check/lib/allowlist.mjs`-ից, որպեսզի հնացած գրառումները հայտնաբերվեն ինքնաբերաբար։
5. `tests/unit/build/`-ում գրեք թեստ, որն ընդգրկում է ստուգիչի հայտնաբերման տրամաբանությունը։
6. Թարմացրեք այս փաստաթուղթը (համապատասխան job-ի աղյուսակում ավելացրեք տող)։

## Գործակալների գործիքակազմ․ LSP-in-the-loop (ըստ ցանկության)

PR խմբաքանակն ինքնին ոչ մի բանալի չի ավելացնում, այնպես որ երկու եղբայրներն էլ լուռ մնացին, երբ խմբաքանակ 1 (#13044) վայրէջք կատարեց 43 ստեղնով կարճ ինը տեղանքում, իսկ խմբաքանակ 2 (#13660) 10 ստեղն կարճ ութում (2026-09-15): Կարմիրը ամրացրեք `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` ով; `extra` տերևը նշանակում է, որ աղբյուրը թողել է այն — ջնջել այն տեղանքից: `--warn` առանց ձախողման հաղորդում է. `--catalog=cli` կատարում է նույն համեմատությունը `bin/cli/locales` վրա (`npm run i18n:check-keys:cli`); երկու քայլերն էլ ապրում են աշխատանքում `i18n-ui-coverage`.

#### `check-new-key-coverage` — նոր բանալին i18n դարպաս

`check-ui-value-drift` քույրը կամ եղբայրը: Այդ մեկը բռնում է անգլիական արժեք, որը եղել է** վերաշարադրված** մինչդեռ դրա թարգմանությունները մնացել էին ետևում. սա բռնում է անգլերեն բանալին, որը եղել է** ավելացրել է** մինչդեռ որոշ տեղացիներ այն երբեք չեն ստացել:

`check-ui-keys-coverage` չի կարող տեսնել այս դասը. այն սահմանում է տոկոսային մակարդակ յուրաքանչյուր տեղանքի համար, և տասնմեկ բացակայող ստեղներ ~ ից 13,000 ծածկույթը թողնում է 99,9%: Մեկ լեզվի տոկոսը չի կարող արտահայտել «այս հատկանիշը ուղարկվել է չթարգմանված» — մի ամբողջ հատկանիշ կարող է հայտնվել նոր տեղանքում՝ առանց տեքստի և երբեք չտեղափոխել համարը:

Միջադեպը, որն այն ծածկագրում է. Նվագախմբի 3-րդ փուլը թարգմանել է իր տասնմեկ բանալիները այն ժամանակվա 42 տեղանքով: Ժամեր անց ԵՄ լեզվով խմբաքանակը (#13044) տարավ ռեպո 51 տեղանք, իսկ ինը նորեկները (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) երբեք չստացան դրանք։ `deepMergeFallback` անգլերենը փոխարինում է բացակայող բանալիով, ուստի ձախողման ռեժիմը թարգմանված չէ UI քան դատարկ UI — իրական, և անաղմուկ՝ ըստ կառուցման:

Ինչպես իր եղբայրն ու եղբայրը** տարբերվող** , համեմատելով անգլերենը միաձուլման հիմքում աշխատող ծառի հետ, այնպես որ նախկինում գոյություն ունեցող բացերը մնում են սառեցված, և դարպասը միացնելու համար միգրացիայի կարիք չուներ:

**`__MISSING__:<english>` նշիչը դա չի բավարարում (2026-09-17-ից):** Նախկինում դա եղել է փաստաթղթավորված հետաձգման — գործարկման ժամանակը վերադառնում է ուղղելու անգլերեն — մինչև ութ հատկանիշ PRs 2026-09-16-ին ավելացրին 61 ստեղներ և դրոշմեցին նշիչը բոլոր 65 տեղանքում թարգմանելու փոխարեն. > 2,5 % PRs 0,5 + : Մարկերն այժմ գնահատվում է որպես բացակայող թարգմանություն: Կարմիրը ուղղեք `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` ով կամ բոլոր տեղանքները `npm run i18n:translate-new-keys` հետ զուգահեռ (`scripts/i18n/translate-new-keys.sh`, անջատված-անվտանգ, հրաժարվում է սկսել առանց `OMNIROUTE_TRANSLATION_*` env-ի): Բանալին, որը պետք է մնա անգլերեն (կցված product/engine/flag անուն) պատկանում է `scripts/i18n/untranslatable-keys.json` ին, երբեք ցուցիչի հետևում: `vi` ուղղակիորեն արգելում է մարկերները (`tests/unit/i18n-vi-completeness.test.ts`):

#### `check-vitest-exclusions` — կայանված-թեստային դարպաս

`vitest.config.ts` ի `exclude` ցուցակում գտնվող ֆայլը թեստ է, որը չի գործարկվում, և կարծես ծածկույթ լինի բոլոր նրանց համար, ովքեր կարդում են ծառը: `// #8618 — pre-existing failure; remove this exclusion when fixed` մեկնաբանության հետևում կուտակվել է վաթսուներկու ֆայլ: #8618 թողարկումը փակվել է 2026-08-11-ին, մինչդեռ ցուցակը, որին հետևել է, 45 գրառումից հասել է 62-ի, որոնցից յուրաքանչյուրը ժառանգում է մեկնաբանություն, որը մատնանշում է մեռած խնդիր: Երբ ցուցակը վերջապես չափվեց ֆայլ առ ֆայլ (#13204),** 62-ից 51-ն ընդունվել է ընթացիկ ծառի դեմ՝ առանց աղբյուրի փոփոխության** .

Դարպասը պահանջում է իրական ֆայլի ցանկացած բացառում՝ (ա) անվանելու հետագծման խնդիր և (բ) `config/quality/vitest-exclusions.json` ում երևալու իր չափված կարգավիճակով, ուստի դրանց ավելացումը հատուկ ֆայլում վերանայվող տարբերություն է, այլ ոչ թե ևս մեկ տող 60 մուտք ունեցող զանգվածում: Այն միտումնավոր չի վերագործարկում բացառված թեստերը —, որոնք արժեն ~ 10 րոպե և պատկանում են պարբերական աշխատանքին. գույքագրման գրառումները, երբ յուրաքանչյուրը վերջին անգամ չափվել է:
