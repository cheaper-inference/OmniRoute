OmniRoute-ը հրապարակում է npm + Docker արտեֆակտներ։ Այս դարպասներն ապահովում են ծագումնաբանություն, գույքագրում (SBOM) և CVE սկանավորում, բոլորը՝ OSS, ինտեգրված թողարկման աշխատանքային հոսքերին։ **Խորհրդատվական-առաջնային** դիրքորոշում — դրանք հիմա են զեկուցում, արգելափակողի են վերածվում 1-ին հաջող թողարկումից հետո։

| Դարպաս                        | Գործիք                                         | Որտեղ                         | Արգելափակո՞ւմ է                    | Ելք                                                               |
| :---------------------------- | :--------------------------------------------- | :---------------------------- | :--------------------------------- | :---------------------------------------------------------------- |
| SLSA ծագումնաբանություն (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | միայն հրապարակման ձախողման դեպքում | նշան npmjs / `npm audit signatures`                               |
| SBOM npm                      | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | միայն ստեղծման ձախողման դեպքում    | Թողարկման ակտիվ + արտեֆակտ                                        |
| SBOM պատկեր                   | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | խորհրդատվական                      | CycloneDX արտեֆակտ                                                |
| Trivy CVE (SARIF)             | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | խորհրդատվական                      | SARIF (ԲԱՐՁՐ+ԿՐԻՏԻԿԱԿԱՆ) → Անվտանգության ներդիր                   |
| Trivy ԿՐԻՏԻԿԱԿԱՆ դարպաս       | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **արգելափակող**                    | `exit-code: '1'` շտկվող ԿՐԻՏԻԿԱԿԱՆ-ի դեպքում                      |
| osv vulnCount                 | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **արգելափակող**                    | սահմանում է շեմ `metrics.vulnCount`-ի համար (ուղղություն՝ նվազող) |
| OpenSSF Scorecard             | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | խորհրդատվական                      | SARIF → Անվտանգություն + նշան                                     |

Պատկերի CVE շեմը `docker-publish.yml`-ում օգտագործում է **երկու քայլ**. SARIF քայլը (`HIGH,CRITICAL`, `exit-code: 0`) պահում է ԲԱՐՁՐ+ԿՐԻՏԻԿԱԿԱՆ-ը տեսանելի Անվտանգության ներդիրում՝ առանց արգելափակելու. _ԿՐԻՏԻԿԱԿԱՆ դարպասի_ քայլը (`severity: CRITICAL`, `ignore-unfixed: true`, `exit-code: 1`) ձախողում է թողարկումը ԿՐԻՏԻԿԱԿԱՆ CVE-ի դեպքում՝ **առկա շտկումով**։ `ignore-unfixed`-ը կանխում է թողարկման արգելափակումը բազային պատկերի CVE-ի համար՝ առանց վերին հոսքի կարկատանի։

## ⚠️ CVE-ի փոփոխականություն (արգելափակող osv/Trivy դարպասներ)

osv-ն և Trivy-ն կախվածությունները համեմատում են CVE տվյալների շտեմարանների հետ, որոնք **անընդհատ աճում են**։ PR-ը, որը **չի փոխում որևէ կախվածություն**, կարող է հանկարծ կարմրել, քանի որ գոյություն ունեցող կախվածության համար հրապարակվել է նոր CVE (osv՝ չափված `vulnCount`-ը գերազանցում է ելակետային արժեքը, Trivy՝ պատկերի մեջ կա շտկման ենթակա նոր CRITICAL խոցելիություն)։ **Սա արգելափակող CVE դարպասի ՍՊԱՍՎՈՂ գործառնական վարքագիծն է, ոչ թե պրոդուկտի հետընթաց։**

Երբ osv-ն կամ Trivy-ն կարմրում են նոր հրապարակված CVE-ի պատճառով, լուծումը հետևյալն է.

1. **Թարմացրեք ազդակիր կախվածությունը** (նախընտրելի տարբերակ)՝ անցեք շտկված տարբերակին `package.json`-ի
   `overrides`-ի միջոցով (անցումային կախվածությունների համար) կամ վերակառուցեք պատկերը շտկված հիմքային պատկերի վրա։
2. **Եթե վերին հոսքում շտկում չկա.**
   - **osv.** վերահաստատեք `metrics.vulnCount`-ի ելակետային արժեքը `config/quality/quality-baseline.json`-ում
     (`npm run quality:ratchet -- --update`-ը չի ընդգրկում առանձին դարպասները․ արժեքը խմբագրեք
     ձեռքով՝ `direction:down`)՝ ավելացնելով հիմնավորման նշում և հետևման խնդիր։
   - **Trivy.** `.trivyignore`-ում ավելացրեք գրառում (յուրաքանչյուր տողում՝ CVE-ID)՝ հիմնավորման
     մեկնաբանությամբ և հետևման խնդրով։ `ignore-unfixed: true`-ն արդեն ավտոմատ կերպով ընդգրկում է
     շտկումներ չունեցող CVE-ները։

Պարտադիր OSV գործարկումները (`check:vuln-ratchet -- --ratchet`) փակման սկզբունքով ձախողվում են՝ վերադարձնելով
`INCOMPLETE` և ելքի 2 կոդ, երբ սկաները, հաշվետվությունը կամ ելակետային արժեքը հնարավոր չէ վավերացնել։
Չափված հետընթացի դեպքում վերադարձվում է ելքի 1 կոդ։ Խորհրդատվական գործարկումը դեռ կարող է հաղորդել `SKIP`՝
ելքի 0 կոդով, ինչը չի հաստատում, որ կախվածությունները հաջողությամբ անցել են սկանավորումը։ Արգելափակող
Trivy քայլը նույնպես պահանջում է հաջող չափում. անհասանելի գործիքները, ձախողված առաջադրանքները
և պատկերի բացակայող ապացույցները չեն կարող հավաստել, որ պատկերը մաքուր է։

## Հեռացված կախվածության ռիսկ

Արմատային lockfile-ն այլևս չի ներառում `extract-zip`-ը կամ դրան տանող կախվածության կապ՝ ամրագրված promptfoo մշակման գործիքի թարմացումից հետո։ Սա հեռացնում է նախկինում ընդունված `promptfoo` → `@openai/codex-security` → `extract-zip` շղթան, որին հետևում էին #14482-ում։ `tests/unit/extract-zip-14482-exposure.test.ts`-ում առկա ռեգրեսիայի ստուգումները մերժում են դրա կրկնակի ներմուծումը և պահպանում են արտադրական կոդից ներմուծումների արգելքը։

Կախվածությունների ընթացիկ շտկումը նաև սահմանափակում է համատեղելիության վերասահմանումները՝ դրանք կիրառելով Azure identity-ի MSAL հաճախորդի, get-uri-ի FTP հաճախորդի և OpenCode v1 SDK-ի Zod կախվածության նկատմամբ։ Azure թոքենների ստացումը և FTP-ով տվյալների առբերումը ստուգվում են վերահսկվող տրանսպորտային միջոցներով․ OpenCode-ի երկու փաթեթներն էլ գործարկում են իրենց սեփական կառուցման և թեստավորման համալիրները։ Ռեեստրի անվտանգության ծանուցումների քանակները տվյալ պահին կատարված չափումներ են և կարող են փոխվել lockfile-ը commit անելուց հետո։

## Հետաձգված. Scorecard խորհրդատվություն → արգելափակում

Scorecard-ի հաշվետվությամբ առաջին հաջող թողարկումից հետո.

- Scorecard. միավորի ռաչետ (սառեցնում է չափված միավորը. չի կարող նվազել)։

Լրացնում է Փուլ 7-ի դարպասները (osv-scanner, gitleaks, actionlint+zizmor). zizmor-ը ստուգում է հենց աշխատանքային հոսքերը. Scorecard-ը չափում է պահոցի վիճակը ընդհանուր առմամբ։
