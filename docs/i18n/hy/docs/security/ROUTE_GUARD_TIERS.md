## Ընդհանուր ակնարկ

OmniRoute-ի կառավարման API-ի բոլոր երթուղիները դասակարգվում են պաշտպանության երեք
մակարդակներից մեկում։ Դասակարգումը ստատիկ է, սահմանված է `src/server/authz/routeGuard.ts`-ում
և գնահատվում է նախքան նույնականացման որևէ այլ ճյուղի գործարկումը։

## Մակարդակներ

### Մակարդակ 1 — LOCAL_ONLY

**Կիրարկվում է՝** `isLocalOnlyPath(path)` → loopback հոսթի ստուգում  
**Շրջանցում՝** Լռելյայն՝ չկա։ Սահմանափակ բացառություն է նախատեսված
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում ներառված ուղիների համար, երբ հարցումը պարունակում է
`manage` scope-ով վավեր API բանալի (տե՛ս [Manage-scope-ի բացառությունը](#manage-scope-carve-out))։

Այս երթուղիները ստեղծում են ենթապրոցեսներ կամ կատարում են runtime կոդ։ Դրանք
ոչ loopback տրաֆիկի համար հասանելի դարձնելը թույլ կտար վավեր JWT ձեռք բերած հարձակվողին (օրինակ՝
Cloudflared/Ngrok թունելի միջոցով) գործարկել պրոցեսների ստեղծումը՝ հայտնի CVE
դաս ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))։

**Ինչ է GHSA-fhh6-4qxv-rpqj-ը (հարձակման դասը)՝** կառավարման/ագենտի սերվերը
հասանելի է դարձնում endpoint, որը գործարկում է ենթապրոցես (`npm install`, `node`, դիտարկիչ,
պրոքսի, `git`, `tar`, …)։ Եթե այդ endpoint-ը հասանելի է հոսթից դուրս՝ քանի որ
օպերատորը OmniRoute-ը տեղադրել է nginx/Cloudflare/Tailscale թունելի հետևում, և JWT-ն
արտահոսել է, կամ նույնականացման կարգավորումը սխալ է եղել, ապա հարձակվողը «API կանչելը» վերածում է «հոսթի վրա
հրաման գործարկելու» (կոդի հեռակա կատարում)։ OmniRoute-ը կանխում է սա՝ յուրաքանչյուր
պրոցես ստեղծելու ունակ երթուղու վրա **անվերապահորեն, նույնականացման ցանկացած ստուգումից առաջ, կիրառելով
loopback հոսթի ստուգում**․ թունելով փոխանցված արտահոսած նշանը միևնույն է չի կարող հասնել պրոցեսի ստեղծման գործառույթին։

**LOCAL_ONLY-ի ամբողջական բազմությունը։** Հեղինակավոր աղբյուրներն են
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`-ը
`src/server/authz/routeGuard.ts`-ում․ ստորև բերված աղյուսակն արտացոլում է ընթացիկ վիճակը։  
`check-route-guard-membership` դարպասը թվարկում է պրոցեսներ ստեղծելու ունակ
նախածանցների տակ գտնվող յուրաքանչյուր `route.ts` և CI-ն ձախողում է, եթե դրանցից որևէ մեկը դասակարգված չէ որպես միայն տեղային։

**Պատասխան խախտման դեպքում՝** `403 LOCAL_ONLY`

#### Կառավարման հասանելիության բացառություն

LOCAL_ONLY ուղիների ենթաբազմությանը ԿԱՐՈՂ ԵՆ նաև դիմել ոչ loopback հասցեներից, եթե և
միայն եթե հարցումը պարունակում է `Authorization: Bearer <api-key>`, որի
մետատվյալները ներառում են `manage` հասանելիության տիրույթը (կամ `admin`)։ Բացառությունը յուրաքանչյուր ուղու համար
բացահայտորեն կառավարվում է `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ի միջոցով, որպեսզի
ցանկացած նոր LOCAL_ONLY ուղու լռելյայն վարքագիծը մնա խիստ loopback-ով սահմանափակված։ Չնույնականացված
հարցումները և `manage` չունեցող բանալիներով հարցումները նախկինի պես մերժվում են
`403 LOCAL_ONLY` պատասխանով։

Այս պահին բացառությունը կիրառելի է միայն `/api/mcp/` նախածանցի համար։ `/api/cli-tools/runtime/`-ը և
`/api/services/`-ը միտումնավոր բացառված են, քանի որ դրանք կարող են գործարկել կամայական
ենթագործընթացներ (`npm install`, `node`), ինչը հենց այն CVE դասն է, որը
LOCAL_ONLY մակարդակը նախատեսված է կանխելու համար։

**#7895 — `mcp:connect` նեղ հասանելիության տիրույթ՝** `/api/mcp/` բացառությունը ՆԱԵՎ ընդունում է
նեղ `mcp:connect` հասանելիության տիրույթն ունեցող Bearer բանալի
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), որը ստուգվում է
`src/server/authz/policies/management.ts`-ի `hasMcpConnectOrManageScope()`-ի միջոցով։
Սա սահմանափակված է ՄԻԱՅՆ `/api/mcp/`-ով. `mcp:connect`-ը հասանելիություն չի տրամադրում կառավարման որևէ այլ
երթուղու նկատմամբ (ներառյալ LOCAL_ONLY-ի շրջանցման ցանկացած այլ նախածանց, եթե երբևէ այդպիսին
ավելացվի), և այն միտումնավոր բացառված է
`MANAGEMENT_API_KEY_SCOPES`-ից։ `manage`/`admin` ունեցող բանալին նախկինի պես
անցնում է այս բացառության ստուգումը. `mcp:connect`-ը ավելի ցածր արտոնություններով այլընտրանք է
հեռակա, միայն MCP օգտագործող կանչողների համար, որոնց կառավարման լայն հասանելիություն պետք չէ։

| Հարցում                                                    | Ուղի                       | Արդյունք                     |
| ---------------------------------------------------------- | -------------------------- | ---------------------------- |
| Ոչ loopback, առանց Bearer-ի                                | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Ոչ loopback, `manage` հասանելիության տիրույթով Bearer      | `/api/mcp/*`               | Թույլատրել                   |
| Ոչ loopback, `mcp:connect` հասանելիության տիրույթով Bearer | `/api/mcp/*`               | Թույլատրել                   |
| Ոչ loopback, առանց `manage`/`mcp:connect`-ի Bearer         | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Ոչ loopback, `mcp:connect` հասանելիության տիրույթով Bearer | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Ոչ loopback, `manage` հասանելիության տիրույթով Bearer      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Loopback, ցանկացած/առանց Bearer-ի                          | ցանկացած LOCAL_ONLY        | Թույլատրել (պատնեշն անցած է) |

#### Օպերատորի ուղեցույց և աուդիտ

Եթե OmniRoute-ը գործարկում եք հակադարձ պրոքսիի կամ թունելի (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) հետևում, loopback ստուգումը շարունակում է պաշտպանել վերոնշյալ՝
գործընթացներ գործարկելու ունակ երթուղիները. հարցումը, որի հաճախորդի հասցեն loopback չէ, մերժվում է
`403 LOCAL_ONLY` պատասխանով՝ **մինչև նույնականացման գործարկումը**, ուստի արտահոսած JWT-ն չի կարող հասնել գործընթացի գործարկմանը։ Մնում է
օպերատորի երկու պարտականություն.

- **Մի՛ փորձեք «շտկել» 403-ը՝ կեղծելով հաճախորդի IP հասցեն որպես loopback։** Սահմանելով
  `X-Forwarded-For: 127.0.0.1` կամ օգտագործելով proxy, որը սկզբնաղբյուրի հասցեն վերագրում է
  որպես loopback, կրկին բացվում է հենց այն RCE դասը, որը փակում է այս մակարդակը։ Proxy-ի
  միջոցով հասանելի դարձրեք dashboard/API-ն, բայց երբեք՝ գործընթացներ գործարկելու ունակ երթուղիները։
- **`manage` scope-ի շրջանցումը պահեք նվազագույն։** Միայն `/api/mcp/`-ն է հնարավոր շրջանցել, և
  միայն `manage` scope-ով API բանալիով։ `SPAWN_CAPABLE_PREFIXES`-ը երբեք չի կարող
  ավելացվել շրջանցման ցանկում․ zod սխեման մերժում է դրանք, իսկ
  `isLocalOnlyBypassableByManageScope`-ը արգելում է դրանք կատարման պահին (բազմաշերտ պաշտպանություն),
  ինչն էլ dashboard-ում նշանակում է «չի կարող շրջանցելի դառնալ»։ Նույն
  արգելման ցանկը ներառում է նաև մի քանի LOCAL_ONLY երթուղիներ, որոնք գործընթաց չեն գործարկում, բայց
  նույնպես երբեք չպետք է հեռակա հասանելի լինեն՝ `/api/oauth/kiro/auto-import` (կարդում է հոսթում
  տեղային Kiro հավատարմագրերի ֆայլերը), `/api/discovery/` և `/api/issue-agent/`։ Կատարման ժամանակի
  snapshot բեռնիչը նաև հեռացնում է նման գրառումները պահված կարգավորումների տողից, իսկ
  հին JSON ներմուծումը (`/api/settings/import-json`) երբեք չի գրանցում շրջանցման բանալիները։
  `LOCAL_ONLY_API_PREFIXES`-ի յուրաքանչյուր գրառում պետք է կամ լինի արգելման ցանկում, կամ
  ստուգված լինի որպես շրջանցման համար թույլատրելի (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)։ Դինամիկ հատվածներով
  և ստատիկ ուղիներով գործընթացներ գործարկելու ունակ երթուղիները `/api/providers/`-ի ներքո (օր.՝ `/login`,
  `/refresh-cursor`) ընդգրկված են regex-ի վրա հիմնված `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ուղեկցող սահմանումներով՝
  `src/shared/constants/spawnCapablePrefixes.ts`-ում, այլ ոչ թե հարթ
  `SPAWN_CAPABLE_PREFIXES` զանգվածով․ դրանք հայտնաբերելու համար հարթ զանգվածը պետք է ընդգրկեր
  ամբողջ `/api/providers/` նախածանցը՝ չափազանց լայն սահմանելով այն երթուղիների ծառը,
  որը հեռակա dashboard-ները օրինականորեն օգտագործում են մատակարարների CRUD գործողությունների համար։

**Հասանելիության աուդիտ** — ստուգելու համար, որ հոսթից դուրս ոչինչ չի հասնում այս երթուղիներին՝

- Բացեք **Authorization Inventory**-ն `/dashboard/settings/security`-ում․ այն ցուցադրում է
  գործող LOCAL_ONLY նախածանցների ցանկը, շրջանցելի նախածանցները և կոմպիլացման պահին սահմանված
  գործընթացներ գործարկելու ունակ («չեն կարող շրջանցելի դառնալ») հավաքածուն։
- Reverse proxy-ի / հասանելիության մատյաններում grep կատարեք՝ փնտրելով վերևում նշված նախածանցները՝
  զուգակցված ոչ loopback հաճախորդի հասցեի հետ։ Ցանկացած նման հարցում, որը `403 LOCAL_ONLY`-ի
  փոխարեն վերադարձրել է `200`, նշանակում է, որ proxy-ն քողարկում է հաճախորդի իրական IP հասցեն․ ուղղեք proxy-ն։
- OmniRoute-ի մատյաններում այս ուղիներից որևէ մեկի համար `403 LOCAL_ONLY`-ը նշանակում է, որ պաշտպանիչ
  մեխանիզմն աշխատում է ըստ նախատեսվածի, այլ ոչ թե սխալ է, որը պետք է ճնշել։

#### Հեռակա հասանելի երթուղիներ՝ կանչի վայրում probe-ի արգելափակմամբ

Որոշ երթուղիներ պետք է հասանելի մնան հեռակա dashboard-ից, բայց տեղային կանչողների համար կատարեն
հոսթի կողմում probe (`which <binary>`, `<binary> --version`, `tailscale status --json`)։
Դրանք `GET`-ի համար LOCAL_ONLY չեն․ փոխարենը handler-ը կարդում է վստահելի peer-ի որոշումը
`getRequestPeerLocality()`-ով (`src/shared/utils/apiAuth.ts`) և probe-ն կատարում է միայն
`loopback` / `lan` կանչողների համար։ `remote` կանչողը ստանում է նույն կառուցվածքով պատասխան՝ կազմված
գործընթաց չգործարկող աղբյուրներից (պահպանված վիճակ, կարգավորումներ, fs ստուգումներ) և նշված որպես `probed: false`։

| Երթուղի                                                          | Հեռակա կանչողների համար բաց թողնվող probe-ը                                         |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI կատարման միջավայրի probe (`allowLocalRuntimeProbe`) և CLI fallback-ի գործարկում |
| `GET /api/headroom/status`                                       | `which headroom` և python-ի `--version` probe-երը                                   |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`                   |
| `GET /api/tunnels/cloudflared` (`GET`-ը ազատված է LOCAL_ONLY-ից) | `which cloudflared` PATH որոնում                                                    |

Հոսթը probe կատարող նոր ընթերցման երթուղին հետևում է նույն օրինաչափությանը կամ ամբողջությամբ
դասակարգվում է որպես LOCAL_ONLY։

### Մակարդակ 2 — ALWAYS_PROTECTED

**Կիրարկվում է՝** `isAlwaysProtectedPath(path)` → բաց թողնել `requireLogin=false` շրջանցումը
**Շրջանցում՝** չկա, երբ `requireLogin=false` է․ JWT-ն միշտ պարտադիր է

Այս երթուղիները կործանարար են կամ անդառնալի։ Դրանց թույլատրումը «առանց գաղտնաբառի»
տեղադրման դեպքում կնշանակեր, որ նույն LAN-ում գտնվող ցանկացած անձ կարող է մաքրել տվյալների բազան կամ դադարեցնել
սերվերի գործընթացը։

| Ուղի                                      | Պատճառ                                                                          |
| ----------------------------------------- | ------------------------------------------------------------------------------- |

| `/api/settings/database`                  | Տվյալների բազայի արտահանում, ներմուծում և մաքրում                               |

որը սպասարկվում է հատուկ Node շերտով՝ Next.js-ից առաջ և այս pipeline-ից դուրս, ուղղում է կանչողի ընտրած root-ին

Obsidian REST API token-ը։ GHSA-62vw-ը միայն քողարկում էր գաղտնաբառի բացահայտումը `GET`-ով, մինչդեռ տրամադրումը
դեռ fail-open մակարդակում էր (GHSA-7pq4-8pvv-rx7r)։ `enableObsidianVaultSync()`-ը նաև
մերժում է այն vault-ը, որը տվյալների գրացուցակն է, գտնվում է դրա ներսում կամ պարունակում է այն։

#### Հավատարմագրերի արտահանումը միայն օպերատորների համար է

Վերևում նշված մակարդակը միայն որոշում է, թե արդյոք պահանջվում է _որևէ_ հավատարմագիր։ Պահված
հավատարմագրերը ներբեռնող երթուղիները մշակիչում կատարում են երկրորդ ստուգում՝ `GET /api/settings/export-json` (վերծանված
մատակարարի կապեր և չմշակված API բանալիներ), `GET /api/db-backups/export` (SQLite ֆայլը) և
`GET /api/db-backups/exportAll` (ամբողջական արխիվը) կանչում են `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`)։ Այն ընդունում է կառավարման վահանակի աշխատաշրջանը, տեղային CLI սուբյեկտը կամ
մուտքն անջատված օրինակը և `403` է պատասխանում ցանկացած շրջանակի API բանալիներին (ներառյալ `manage`
և `admin`) ու `oma_` մուտքի թոքեններին։ Համաժամացման թոքենների թողարկումը (`POST /api/sync/tokens`) օգտագործում է
նույն օգնականը՝ գումարած վստահելի հետադարձ կապի ներքին ծառայության թոքենը։

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### Նոր տեղադրման սկզբնական կարգավորումը հասանելի է միայն հետադարձ կապից՝ ըստ իրական հանգույցի, ոչ թե `Host`-ի

Երբ կառավարման գաղտնաբառ կազմաձևված չէ (և `INITIAL_PASSWORD` չկա),
`src/shared/utils/apiAuth.ts`-ի `isAuthRequired()`-ը անանուն սկզբնական կարգավորումը բաց է պահում **միայն հետադարձ կապի հանգույցների համար**։
Հետադարձ կապը որոշվում է վստահելի հանգույցի ազդանշաններից՝ հետևյալ հերթականությամբ․ թոքենով դրոշմված իրական TCP հանգույցը
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, որը տեսնում է քաղաքականությունը), մշակման շղթայի սեփական
`AUTHZ_HEADER_PEER_LOCALITY` վճիռը (որը տեսնում են երթուղիների մշակիչները և որին վստահում են միայն այն ժամանակ, երբ
`OMNIROUTE_PEER_STAMP_TOKEN`-ը սահմանված է), կամ ուղղակի կանչողների իրական սոկետային հանգույցը։ `Host`-ը /
`nextUrl.hostname`-ը երբեք չեն դիտարկվում, իսկ առաջին գաղտնաբառի գրանցումը
(`POST /api/settings/require-login`) ենթարկվում է նույն սահմանափակմանը՝ բոլոր
ցանցային հանգույցների համար բաց լինելու փոխարեն (GHSA-7pq4-8pvv-rx7r)։ `managementPolicy`-ն իր սեփական `peerContext` վճիռը
բացահայտորեն փոխանցում է ներքև, որպեսզի ՍԿԶԲՆԱԿԱՆ (մինչև հեռացումը) հարցման վերնագրերը երբեք չորոշեն այն։

### Մակարդակ 3 — ԿԱՌԱՎԱՐՈՒՄ (լռելյայն)

Կառավարման մնացած բոլոր երթուղիները։ Նույնականացումը պահանջվում է, եթե կազմաձևված չէ
`requireLogin=false`։ CLI թոքենները կարող են նույնականացնել այս երթուղիները (հետադարձ կապ + վավեր HMAC)։

## Գնահատման հերթականությունը

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → անցնել հաջորդ քայլին
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → թույլատրել (management_key)
     → հակառակ դեպքում                           → մերժել 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → թույլատրել (system)
  3. hasValidCliToken(headers)?
     → թույլատրել (cli) [loopback + timingSafeEqual HMAC ստուգում]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → թույլատրել (dashboard_session)
     → manage-scope Bearer չշրջանցվող ուղու վրա?
        → թույլատրել (management_key)
     → մերժել 401/403
  5. requireLogin=false?
     → թույլատրել (anonymous)
```

Քայլ 1-ի manage-scope ճյուղը նույնականացված միակ ուղին է, որը կարող է բավարարել
LOCAL_ONLY երթուղու պահանջները․ auth-backend-ի խափանման ռեժիմը վերադարձնում է 503 (ոչ թե 403), որպեսզի
ժամկետանց DB-ն աննկատ չանցնի «մերժել» ռեժիմի։

## Նոր՝ spawn-ի հնարավորություն ունեցող երթուղու ավելացում

1. Ուղու նախածանցն ավելացրեք `LOCAL_ONLY_API_PREFIXES`-ում՝
   `src/server/authz/routeGuard.ts`
2. `tests/unit/authz/routeGuard.test.ts`-ում ավելացրեք թեստ, որը հաստատում է, որ
   `isLocalOnlyPath()`-ը նոր նախածանցի համար վերադարձնում է true
3. **Երբեք բաց մի թողեք այս քայլը** — տե՛ս Hard Rule #15-ը `CLAUDE.md`-ում
4. Որոշեք՝ արդյո՞ք այս երթուղին ՆԱԵՎ պետք է լինի `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում։
   Լռելյայն պատասխանը **ոչ** է։ Ներառեք միայն այն դեպքում, երբ երթուղին անվտանգ է
   manage-scope կրողին հասանելի դարձնելու համար (այսինքն՝ ՉԻ գործարկում օգտատիրոջ կողմից կառավարվող կամայական կոդ)։

## Manage-scope-ով շրջանցվող ուղու ավելացում

1. Համոզվեք, որ երթուղին չի կատարում օգտատիրոջ տրամադրած կոդը կամ հրամանները։ Եթե
   կատարում է, կանգ առեք․ այս բացառությունը ճիշտ գործիք չէ։
2. Նախածանցն ավելացրեք `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ին՝
   `src/server/authz/routeGuard.ts`
3. `tests/unit/authz/management-policy.test.ts`-ում ավելացրեք ծածկույթ հարցման բոլոր չորս
   ձևերի համար՝ առանց Bearer-ի (403), manage Bearer (թույլատրել), ոչ manage Bearer
   (403), ինչպես նաև ըստ նախածանցի ռեգրեսիոն թեստ, որը հաստատում է, որ `/api/cli-tools/runtime/*`-ը
   մնում է խիստ loopback՝ նույնիսկ manage Bearer-ի առկայության դեպքում։

### Կեղծ դրական արդյունքի կանոն

Եթե `x-always-protected`-ը կամ `x-loopback-only`-ը նշված է այնպիսի երթուղու վրա, որը ՉԿԱ
`routeGuard.ts` հաստատունում, ծածկույթի սկրիպտը ձախողվում է։ Ուղղումը միշտ YAML-ը
`routeGuard.ts`-ի իրական կիրառած կանոններին համապատասխանեցնելն է, այլ ոչ թե երթուղիները `routeGuard.ts`-ում
ավելացնելը՝ առանց կիրառման տրամաբանությունը նույնպես իրականացնելու։
