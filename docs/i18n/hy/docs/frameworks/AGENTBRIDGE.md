AgentBridge-ը OmniRoute-ի MITM (Man-in-the-Middle՝ «միջնորդ») պրոքսին է, որը որսում է IDE-ի AI գործակալների HTTPS տրաֆիկը և այն վերահղում OmniRoute-ի երթուղավորման միասնական շարժիչի միջոցով։ Այն աջակցում է **10 IDE գործակալի**՝ Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code և Trae (ուսումնասիրման փուլում), ինչի շնորհիվ OmniRoute-ը շուկայում AI կոդավորման օգնականների համար ամենալայն ծածկույթն ունեցող MITM պրոքսին է։

**Վահանակի տեղադրությունը՝** `/dashboard/tools/agent-bridge`
**Կողագոտու խումբը՝** Գործիքներ (Cloud Agents-ից հետո)
**Տես նաև՝** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — իրական ժամանակում վերահսկեք ամբողջ որսված տրաֆիկը, `docs/security/MITM-TPROXY-DECRYPT.md` (git-ում է, չի ներառվում `/docs`-ում) — Linux TPROXY-ի թափանցիկ վերծանմամբ որսման ռեժիմը, որը կառավարվում է `/api/tools/agent-bridge/tproxy` երթուղու միջոցով։

## §1 Ընդհանուր ակնարկ

### Ի՞նչ է AgentBridge:

Երբ IDE գործակալը (օրինակ՝ GitHub Copilot, Cursor, Claude Code) կատարում է API զանգ, այն ուղղակիորեն միանում է AI մատակարարին (OpenAI, Anthropic և այլն): AgentBridge թափանցիկ կերպով ընդհատում է այդ կապը TLS մակարդակում, առանց որևէ գործակալի կազմաձևման փոփոխություն պահանջելու, և վերագրում է հարցումը OmniRoute միջոցով:

Սա նշանակում է, որ դուք կարող եք.

- **Վերահղեք ցանկացած գործակալ ցանկացած մատակարարի** Copilot խոսում OpenAI? Վերահղեք այն Anthropic Claude, Gemini կամ OmniRoute ի 377 մատակարարներից որևէ մեկին:

- **Դիտեք բոլոր գործակալների երթևեկությունը** Յուրաքանչյուր գաղտնալսված հարցում հրապարակվում է [Ճանապարհային տեսուչին](./TRAFFIC_INSPECTOR.md) :
- **Կիրառել OmniRoute առաձգականություն** Համակցված երթուղում, անջատիչներ, հետադարձ կապ և ծախսերի հետագծում աշխատում են նաև IDE գործակալների տրաֆիկի համար:

## §2 Ճարտարապետություն

### 2.1 Բաղադրիչների ակնարկ

```
IDE գործակալ (VS Code / Cursor / և այլն)
    │  HTTPS (պորտ 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS վերահղում
    │
    ▼
src/mitm/server.cjs  (պորտ 443, CJS ենթագործընթաց)
    │  որոշում է թիրախը՝ ըստ Host վերնագրի SNI-ի
    │  ստեղծում է յուրաքանչյուր SNI-ի համար TLS հավաստագիր՝ ստորագրված AgentBridge CA-ի կողմից
    ├── Համընկնո՞ւմ է շրջանցման ցանկին → TCP-ի անմիջական փոխանցում (առանց վերծանման)
    ├── Համընկնո՞ւմ է թիրախին → fetch → OmniRoute երթուղիչ (պորտ 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets()՝ հարցման մարմնի/վերնագրերի վրա
    │               ├── TrafficBuffer.push() — հրապարակում է Traffic Inspector-ում
    │               └── fetchRouter() → /v1/chat/completions
    └── Համընկնում չկա՞ → TCP-ի անմիջական փոխանցում (առանց վերծանման)
```

### 2.2 MITM սերվեր (`src/mitm/server.cjs`)

Հիմնական MITM սերվերն աշխատում է որպես Node.js CJS ենթագործընթաց (գոյություն ունեցող CJS կոդային բազան վերաշարադրելուց խուսափելու համար)։ Այն՝

- Լսում է 443 պորտը (պահանջում է արտոնություն կամ `authbind`/`setcap`)
- Օպերացիոն համակարգից ստանում է CONNECT թունելներ (`/etc/hosts`-ի DNS վերահղման միջոցով)
- Ստեղծում է յուրաքանչյուր SNI-ի համար TLS հավաստագրեր՝ ստորագրված AgentBridge CA-ի կողմից (`DATA_DIR/mitm/ca.crt`)
- `targets/index.ts` ռեգիստրի միջոցով որոշում է թիրախային գործակալը՝ ըստ Host վերնագրի
- HTTP-ի միջոցով հարցումն ուղղորդում է TypeScript մշակիչների շերտին՝ `http://127.0.0.1:20128`

`TARGET_HOSTS`-ը բեռնվում է `DATA_DIR/mitm/targets.json`-ից (որը մեկնարկման ժամանակ գրվում է `targets/index.ts`-ի կողմից)՝ թույլ տալով դինամիկ թարմացումներ՝ առանց CJS սերվերը վերագործարկելու։

> **Արմատային CA-ի մոդել (#6684)։** Վերը նկարագրված՝ յուրաքանչյուր SNI-ի համար CA-ի կողմից ստորագրված հավաստագրի
> մոտեցումը #6684-ում ավելացված պահպանվող արմատային CA-ի մոդելն է (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, որը վերաօգտագործում է TPROXY-ի համար արդեն
> փորձարկված CA/վերջնական հավաստագրի կրիպտոգրաֆիան՝ `src/mitm/tproxy/dynamicCert.ts`-ից)․ այն փոխարինում է
> ավելի հին՝ մեկ ստատիկ ինքնաստորագրված վերջնական հավաստագրին (`src/mitm/cert/generate.ts`, որը դեռ
> սահմանափակված է միայն antigravity հոսթերով), որի առկայությունը սկավառակի վրա ցույց է տալիս սովորական `server.crt`/`server.key`
> զույգը։ **Միգրացիայի վարքագիծ**․ նոր տեղադրումը (առանց նախկին
> `server.crt`-ի) ավտոմատ ստանում է արմատային CA-ի մոդելը, իսկ այն տեղադրումը, որն արդեն
> վստահում է հին ստատիկ վերջնական հավաստագրին, շարունակում է օգտագործել այն, մինչև օպերատորը սահմանի
> `MITM_ROOT_CA_ENABLED=true` և վերագործարկի կամուրջը (`src/mitm/cert/migration.ts`-ը
> որոշման մաքուր ֆունկցիան է․ վստահված MITM CA-ն, որը կարող է վերջնական հավաստագիր ստորագրել
> **ցանկացած** հոսթի համար, զգալիորեն ավելի հզոր է, քան հին՝ ֆիքսված SAN-երով վերջնական հավաստագիրը, ուստի
> արդեն վստահված տեղադրման դեպքում անցումը երբեք անձայն չի կատարվում)։ CA հավաստագիրը տեղադրվում է
> վստահության պահոցի նույն `omniroute-mitm.crt` բնիկում, որն օգտագործում էր հին վերջնական հավաստագիրը
> (`cert/install.ts::installCaCert`)․ երկու վստահված հավաստագրերի մաքրման կարիք չկա։

### 2.3 Մշակիչի հիմք (`src/mitm/handlers/base.ts`)

Գործակալների բոլոր մշակիչները ժառանգում են `MitmHandlerBase`-ից․

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Պաշտպանված օժանդակ մեթոդներ՝ fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Յուրաքանչյուր մշակիչ, նախքան պրոքսիավորումը, կանչում է `hookBufferStart()`, իսկ ավարտից հետո՝ `hookBufferUpdate()`։ Դրանք `InterceptedRequest` գրառումներ են ավելացնում `globalTrafficBuffer`-ում (տե՛ս [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4)։

### 2.4 Թիրախների ռեգիստր (`src/mitm/targets/`)

Յուրաքանչյուր գործակալ ունի թիրախի հայտարարական ֆայլ․

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Ռեգիստրը (`targets/index.ts`) արտահանում է `ALL_TARGETS`-ը և մեկնարկման ժամանակ ստեղծում է `DATA_DIR/mitm/targets.json`-ը։

### 2.5 Անմիջական փոխանցում և շրջանցման ցանկ (`src/mitm/passthrough.ts`)

**Շրջանցման ցանկ** (ստուգվում է առաջինը և գերակայում է թիրախի համընկնման նկատմամբ)․

- Լռելյայն ձևանմուշներ՝ բանկային հոսթեր, `.gov.`, OAuth/SSO մատակարարներ (Okta, Auth0) և այլն
- Օգտատիրոջ ձևանմուշներ՝ պահվում են ՏԲ-ի `agent_bridge_bypass` աղյուսակում
- Շրջանցվող հոսթերը ստանում են թափանցիկ TCP թունել․ TLS-ը **երբեք չի վերծանվում**

**Լռելյայն անմիջական փոխանցում** (թիրախի հետ համընկնում չկա և շրջանցման ցանկում չէ)․

- Նույնպես ստանում է TCP թունել․ միացումները երբեք չեն խզվում
- Կանխում է AgentBridge-ի կողմից համակարգի ընդհանուր HTTPS տրաֆիկի խափանումը

Երթուղավորման առաջնահերթությունը․

```
շրջանցման ցանկ → թիրախի համընկնում → անմիջական փոխանցում
```

### 2.6 Վերին հոսքի CA հավաստագիր (`src/mitm/upstreamTrust.ts`)

Հատուկ CA ունեցող կորպորատիվ ցանցային միջավայրերի համար․

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Սահմանված լինելու դեպքում `undici`-ի գլոբալ դիսպետչերը կազմաձևվում է լրացուցիչ CA հավաստագրով՝ AgentBridge-ին թույլ տալով վերին հոսքի մատակարարներին հասնել կորպորատիվ TLS-ի ավարտման պրոքսիների միջոցով։

### 2.7 Գաղտնիքների քողարկում (`src/mitm/maskSecrets.ts`)

Անկախ, զրոյից մշակված սկաները կիրառվում է հարցումների մարմինների և նույնականացման տվյալներ պարունակող վերնագրերի նկատմամբ՝
**նախքան** դրանք կհայտնվեն Traffic Inspector-ի բուֆերում կամ որևէ մատյանում։ Այն կատարում է մեկ գծային անցում․

- `sk-` / `ak-` / `pk-` նախածանցներով թոքեններ (OpenAI/Anthropic ոճով)
- RFC 6750 `Authorization: Bearer <token>` նույնականացման տվյալներ՝ ամբողջական թոքենի գերակայությամբ
- Ընդհանուր երկար անթափանց թոքեններ (≥40 նիշ), ներառյալ կետերով և լրացմամբ ձևերը

`sanitizeHeaders()`-ը պահպանվող անունները դարձնում է փոքրատառ, զանգվածների արժեքները միավորում է որոշակի հերթականությամբ, հեռացնում է
ընդհանուր՝ հանգույցից հանգույց/շրջանակավորման արգելացանկում գտնվող վերնագրերը (ներառյալ պրոքսիի նույնականացումը), ամբողջությամբ խմբագրում է `cookie`-ն և
`set-cookie`-ն, իսկ նույնականացման տվյալների արժեքները փոխանցում է սկաներին։

### 3.1 MITM սերվերի գործարկում/կանգնեցում

Օգտագործեք AgentBridge Server Card-ը՝ `/dashboard/tools/agent-bridge` հասցեում.

| Գործողություն           | Նկարագրություն                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Գործարկել սերվերը       | Գործարկում է `src/mitm/server.cjs`-ը 443 պորտում։ Արմատային CA-ի մոդելի դեպքում առաջին գործարկման ժամանակ ստեղծում է `ca.crt` և վստահելի է դարձնում ակտիվ հավաստագիրը, երբ հասանելի է sudo գաղտնաբառը                                                                                                                                                                                                                                          |

| Վստահել հավաստագրին     | Տեղադրում է ակտիվ հավաստագիրը ՕՀ-ի վստահելի հավաստագրերի պահոցում՝ արմատային CA-ի մոդելի դեպքում `DATA_DIR/mitm/ca.crt`, իսկ հին տերևային տեղադրման դեպքում՝ `DATA_DIR/mitm/server.crt`                                                                                                                                                                                                                                                        |

### 3.2 Վստահել հավաստագրին

AgentBridge CA հավաստագիրը պետք է վստահելի լինի ՕՀ-ի համար, որպեսզի IDE-ներն ընդունեն MITM կապը։

**Linux (NSS — Chrome/Firefox).**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain).**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr).**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Կամ օգտագործեք կառավարման վահանակի «Trust Cert» կոճակը (այն գործարկում է ձեր ՕՀ-ին համապատասխան հրամանը՝ անհրաժեշտության դեպքում ցուցադրելով sudo գաղտնաբառի հարցումը)։

#### Electron-ի վրա հիմնված IDE-ներն անտեսում են ՕՀ-ի վստահելի հավաստագրերի պահոցը (`NODE_EXTRA_CA_CERTS`)

Որոշ IDE-ներ, հատկապես **Antigravity IDE**-ն և Electron / VS Code-ից ածանցված այլ հավելվածներ, ներառում են
սեփական Node.js գործարկման միջավայրը, որը ելքային
`fetch`/HTTPS կապերի համար **չի դիմում ՕՀ-ի վստահելի հավաստագրերի պահոցին**։ ՕՀ/NSS մակարդակում CA-ին վստահելը բավարար է IDE-ի բնիկ **հետին մասի**
համար (օրինակ՝ Go լեզվի սերվերի, որն օգտագործում է ՕՀ-ի CA փաթեթը), սակայն **Electron-ի դիմային մասը**
դեռևս TLS սխալ կստանա. դա դրսևորվում է որպես հավելվածից _դուրս գրված_ վիճակ կամ _«կապի սխալ»_
հաղորդագրություն, թեև MITM մատյանը ցույց է տալիս, որ հետին մասի սկզբնական բեռնման հարցումները վերադարձնում են `200`։ Անհրաժեշտ է
երկու քայլ, և երկուսն էլ կարևոր են.

1. Գործարկման միջավայրին հստակ նշեք CA-ն.
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Գործարկեք IDE-ն այդ shell-ից։** Աշխատասեղանի պատկերակից / Dock-ից / Start ընտրացանկից
   գործարկելիս shell-ի արտահանումները **չեն** ժառանգվում, իսկ `~/.config/environment.d/*.conf`-ը կիրառվում է միայն
   գրաֆիկական միջավայր նոր մուտք գործելուց հետո։ Նախ ամբողջությամբ փակեք IDE-ն. Electron-ի եզակի օրինակի արգելափակման պատճառով երկրորդ
   գործարկումը պարզապես ակտիվացնում է արդեն գոյություն ունեցող գործընթացը, և նոր միջավայրն անտեսվում է։

Վերևում նշված ՕՀ-ի վստահության + NSS քայլը շարունակում է անհրաժեշտ լինել (որոշ նույնականացման
հոսքերի կողմից օգտագործվող Chromium ցանցային շերտը կարդում է յուրաքանչյուր օգտատիրոջ NSS պահոցը և ունի իր ստատիկ ամրակցումները `*.googleapis.com`-ի համար, որոնք
տեղային վստահելի CA-ն փոխարինում է)։ `NODE_EXTRA_CA_CERTS`-ը լրացուցիչ ծածկում է Node-ի `fetch` ուղին։

### 3.3 DNS երթուղավորում

Յուրաքանչյուր գործակալի համար, որի երթևեկը ցանկանում եք որսալ, դրա API հոսթ(եր)ը պետք է վերածվեն `127.0.0.1` հասցեի։ AgentBridge-ն ինքնաշխատ կերպով կառավարում է `/etc/hosts` գրառումները, երբ Setup Wizard-ում միացնում կամ անջատում եք գործակալի DNS-ը։

GitHub Copilot-ի համար `/etc/hosts` գրառումների օրինակ.

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Մոդելների համապատասխանեցում

Օգտագործեք յուրաքանչյուր գործակալի քարտում առկա Model Mapping Table-ը՝ սկզբնաղբյուր → թիրախ համապատասխանությունները սահմանելու համար.

| Սկզբնաղբյուր մոդել (գործակալի բնիկ) | Թիրախային մոդել (OmniRoute) |
| ----------------------------------- | --------------------------- |
| `gpt-4o`                            | `claude-sonnet-4.7`         |
| `*` (փոխարինող նիշ)                 | `claude-haiku-4.7`          |

`*` փոխարինող նիշը ցանկացած չճանաչված մոդել համապատասխանեցնում է նշված թիրախին։ Պահպանվում է `agent_bridge_mappings` աղյուսակում։

> **Հուշում — բացահայտեք գործակալի իրական մոդելի ID-ները։** IDE-ն կարող է ուղարկել մոդելների անուններ, որոնք տարբերվում են
> իր միջերեսում ցուցադրվող պիտակներից և փոխվում են հիմնական տարբերակների միջև։ Օրինակ՝ **Antigravity 2**-ը ցանցով ուղարկում է
> `gemini-3.1-pro-low`, `gemini-pro-agent` և `gemini-3.1-flash-lite`, այլ ոչ թե հին փաստաթղթերում
> նշված `gemini-2.5-pro`-ը։ Ուղարկեք մեկ զրույցի հարցում՝ առանց համապատասխան արտապատկերման. MITM-ը
> գրանցամատյանում կարձանագրի մուտքային ճշգրիտ `model:`-ը և հարցումն անփոփոխ կփոխանցի։ Արտապատկերեք այդ բառացի արժեքը, և
> հաջորդ հարցումը կկալանվի ու կուղղորդվի դեպի ձեր նպատակային մոդելը։

### 3.5 Ռիսկերի մասին ծանուցում

AgentBridge-ը կալանում է այն հավատարմագրերը (OAuth թոքեններ, API բանալիներ), որոնք IDE-ն օգտագործում է վերին մակարդակի մատակարարներում նույնականացման համար։ Դրանք **քողարկվում են նախքան գրանցամատյանում արձանագրվելը** (տե՛ս §2.7), սակայն տեսանելի են OmniRoute-ի MITM շերտին։ Յուրաքանչյուր գործակալի առաջին ակտիվացման ժամանակ ցուցադրվում է ռիսկերի մասին փակվող մոդալ ծանուցում։

### 3.6 Սպասարկում և ախտորոշում

Կառավարման վահանակում հասանելի է **Սպասարկում և ախտորոշում** քարտը (`AgentBridgeMaintenanceCard`, տեղակայված՝ `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`), որը ներկայացնում է MITM-ի գործառնական երթուղիները, որոնք նախկինում չունեին օգտատիրոջ միջերես։ Դրա ենթավերնագիրն է՝ _«Ինքնաստուգեք կալանման հոսքաշարը, չեղարկեք համակարգի մնացորդային վիճակը և ձեր կարգավորումները տեղափոխեք համակարգիչների միջև»_։ Քարտի հաճախորդային օժանդակ գործառույթները գտնվում են `src/lib/inspector/agentBridgeMaintenanceApi.ts`-ում։

| Կոճակ                  | Երթուղի                                | Ինչ է անում                                                                                                                                                                                                                                           |
| ---------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ախտորոշել**          | `GET /api/tools/agent-bridge/diagnose` | Գործարկում է կալանման հոսքաշարի ինքնաստուգումը և ցուցադրում յուրաքանչյուր ստուգման հաշվետվությունը (✓/✗ + շտկման հուշում)։                                                                                                                            |
| **Վերականգնել**        | `POST /api/tools/agent-bridge/repair`  | Չեղարկում է վթարից կամ SIGKILL-ից հետո մնացած MITM համակարգային որբ վիճակը (DNS կեղծման գրառումներ, արմատային CA, համակարգային պրոքսի)։ Իդեմպոտենտ է. երբ վիճակը մաքուր է, հայտնում է «Վերականգնելու ոչինչ չկա»։                                      |
| **Հեռացնել CA-ն**      | `DELETE /api/tools/agent-bridge/cert`  | Հետ է կանչում MITM արմատային CA-ի վստահությունը և հեռացնում այն ՕՀ-ի վստահության պահոցից (բացահայտ, իդեմպոտենտ գործողություն)։ Ցուցադրվում է միայն այն ժամանակ, երբ CA-ն տվյալ պահին վստահելի է. պահանջում է ներկառուցված «Հեռացնե՞լ CA-ն» հաստատում։ |
| **Արտահանել կազմաձևը** | `GET /api/tools/agent-bridge/config`   | Ներբեռնում է փոխադրելի կազմաձևի JSON-ը (տե՛ս §3.7)։                                                                                                                                                                                                   |
| **Ներմուծել կազմաձևը** | `POST /api/tools/agent-bridge/config`  | Վերբեռնում է նախկինում արտահանված կազմաձևի JSON-ը (տե՛ս §3.7)։                                                                                                                                                                                        |

Յուրաքանչյուր գործակալի քարտ ունի նաև իր **Վերականգնել լռելյայնը** կոճակը (`POST
/api/tools/agent-bridge/agents/{id}/reset`)՝ մեկ սեղմումով, ըստ գործակալի չեղարկման գործողություն, որը վերացնում է միայն տվյալ
գործակալի հոսթերի կեղծումը, մաքրում է մոդելների պահպանված արտապատկերումները և վերակայում դրա `dns_enabled`/`setup_completed`
վիճակը, որպեսզի IDE-ն ամբողջական վերագործարկումից հետո կրկին կապվի իրական վերին մակարդակի ծառայության հետ։ Այն **չի** փոխում
ընդհանուր MITM սերվերը կամ արմատային CA-ն (այլ գործակալներ դեռ կարող են կախված լինել դրանցից). դրանք շարունակում են հասանելի մնալ
Սերվերի քարտի և վերևում նշված **Հեռացնել CA-ն** գործողության միջոցով։ Windows-ում այն նաև հնարավորության սահմաններում գործարկում է
`ipconfig /flushdns`, քանի որ Windows DNS Client-ը քեշավորում է hosts ֆայլի գրառումները և հակառակ դեպքում չի հեռացնի
հենց նոր ջնջված կեղծումը։

**Ախտորոշման ստուգումներ** (`summarizeDiagnostics()`՝ `src/mitm/inspector/diagnostics.ts`-ում)։ Երթուղին յուրաքանչյուրի համար գործարկում է կողմնակի ազդեցություն ունեցող ստուգումը և բուլյան արժեքները փոխանցում մաքուր ամփոփիչին. վերադարձվում է մեկ `healthy` եզրակացություն՝ յուրաքանչյուր ձախողման համար առանձին հուշումով։

| Ստուգման անուն     | Ինչ է ստուգում                                                | Հուշում ձախողման դեպքում                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM սերվերի գործընթացն ակտիվ է                               | «MITM սերվերը չի աշխատում։ Գործարկեք այն AgentBridge ներդիրից»։                                                                                                              |
| `server-reachable` | MITM սերվերն իր պորտում ընդունում է միացումներ (TCP ստուգում) | «MITM սերվերն իր պորտում միացումներ չի ընդունում։ Ստուգեք, որ պորտն ազատ է, և որ ունեք դրան կապակցվելու արտոնություններ»։                                                    |
| `cert-exists`      | MITM վկայագիրը սկավառակի վրա ստեղծվել է                       | «MITM վկայագիր դեռ չի ստեղծվել։ Ստեղծեք այն AgentBridge ներդիրից»։                                                                                                           |
| `cert-trusted`     | MITM արմատային CA-ն գտնվում է ՕՀ-ի վստահության պահոցում       | «MITM արմատային CA-ն վստահելի չէ ՕՀ-ի պահոցի համար, ուստի TLS կալանումը չի աշխատի։ Վստահեք վկայագրին AgentBridge ներդիրից»։                                                  |
| `dns-configured`   | Թիրախային հոսթերի անունները կեղծված են `/etc/hosts`-ում       | «Թիրախային հոսթերի անունները կեղծված չեն /etc/hosts-ում, ուստի թրաֆիկը երբեք չի հասնում պրոքսիին։ Միացրեք DNS-ն այն գործակալների համար, որոնց թրաֆիկը ցանկանում եք կալանել»։ |

**Որբ վիճակի նշագոտի.** երբ էջը հայտնաբերում է վթարից հետո մնացած վիճակ (DNS կեղծում / CA / համակարգային պրոքսի), քարտը ցուցադրում է սաթագույն նշագոտի՝ _«Նախորդ աշխատաշրջանը թողել է համակարգային վիճակ (DNS կեղծում, CA կամ համակարգային պրոքսի)։ Գործարկեք Վերականգնել-ը՝ այն մաքրելու համար»_ և ընդգծում է **Վերականգնել** կոճակը։ `Repair`-ը ProxyBridge-ի `--cleanup` դրոշակի կիրառական շերտի համարժեքն է (այն պատվիրակում է աշխատանքը `src/mitm/manager.ts`-ում գտնվող `repairMitm()`-ին)։

> MITM արմատային CA-ն տեղադրված է մնում կանգնեցման/մեկնարկի ընթացքում՝ `sudo`-ի
> կրկնվող հարցումներից խուսափելու համար (նույն վարքագիծը, ինչ mitmproxy/Charles-ում), ուստի այն հեռացվում է
> բացահայտ **Հեռացնել CA-ն** գործողությամբ, այլ ոչ թե ինքնաբերաբար՝ կանգնեցնելիս։

### 3.7 Դյուրակիր կարգավորումների ներմուծում/արտահանում

AgentBridge-ը կարող է **օպերատորի կողմից կարգավորվող** վիճակը սերիականացնել տարբերակավորված JSON բլոբի մեջ, որպեսզի կարգավորումը հնարավոր լինի կրկնօրինակել տարբեր մեքենաներում։ Սերիականացնողը `src/lib/inspector/configPortability.ts`-ն է (`exportConfig()` / `importConfig()`), որը վավերացվում է `AgentBridgeConfigSchema`-ի միջոցով։

Արտահանումը ներառում է ճիշտ երեք բաղադրիչ (ներկառուցված լռելյայն արժեքները միտումնավոր **ՉԵՆ** արտահանվում, որպեսզի ներմուծումը երբեք չկրկնօրինակի դրանք կամ հակասության մեջ չմտնի դրանց հետ)։

| Դաշտ             | Աղբյուր                                                                          | Նշումներ                                                                                          |
| ---------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `bypassPatterns` | օգտագործողի սահմանած շրջանցման օրինաչափություններ (`agent_bridge_bypass`)        | bank/gov/okta լռելյայն օրինաչափությունները բացառված են                                            |
| `customHosts`    | Traffic Inspector-ի հատուկ հոսթեր (`inspector_custom_hosts`)                     | յուրաքանչյուրը՝ `{ host, kind: "llm"\|"app"\|"custom", label? }`                                  |
| `agentMappings`  | յուրաքանչյուր գործակալի մոդելների համապատասխանեցումներ (`agent_bridge_mappings`) | `{ [agentId]: [{ source, target }] }`՝ համապատասխանեցումներ ունեցող յուրաքանչյուր գործակալի համար |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Ներմուծման վարքագիծը** (`POST /api/tools/agent-bridge/config`)՝ շրջանցման օրինաչափությունները և յուրաքանչյուր գործակալի համապատասխանեցումները **ամբողջությամբ փոխարինվում են**, իսկ հատուկ հոսթերն ավելացվում են **իդեմպոտենտ կերպով** (`INSERT OR IGNORE`)։ Պատասխանը հայտնում է, թե յուրաքանչյուրից քանիսն են կիրառվել․

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Ինչը **ՉԿԱ** կարգավորումներում՝ սերվերի գործարկման վիճակը, հավաստագրերի ուղիները, յուրաքանչյուր գործակալի DNS վիճակը, վերին մակարդակի CA-ի ուղին և TPROXY-ի կարգավորումները․ դրանք հոսթի/կատարման միջավայրի վիճակ են, այլ ոչ թե դյուրակիր նախապատվություններ։

### Բացառման ցանկ՝ զգայուն հոսթերի համար

Բացառման ցանկը երաշխավորում է, որ ֆինանսական հաստատությունների, OAuth/SSO մատակարարների և այլ զգայուն հոսթերի տվյալները **երբեք չեն վերծանվում**։ Դրանց TLS տրաֆիկը փոխանցվում է թափանցիկ TCP թունելի միջոցով. OmniRoute-ը երբեք չի տեսնում բաց տեքստը։

Բացառման լռելյայն օրինաչափությունները ներառում են.

- `*.bank.*`, `*.gov.*` (ֆինանսական/պետական)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/ինքնություն)
- `*.apple.com`, `*.icloud.com` (Apple-ի համակարգային ծառայություններ)

Օգտատիրոջ ավելացրած բացառման օրինաչափությունները պահվում են `agent_bridge_bypass` աղյուսակում և գերակայում են մնացած ամեն ինչից։

### Գաղտնիքների քողարկում

Կիրառվում է `src/mitm/maskSecrets.ts`-ի `maskSecrets()`-ը.

- Յուրաքանչյուր հարցման մարմնի նկատմամբ՝ նախքան `TrafficBuffer.push()`-ը
- Յուրաքանչյուր վերնագրի նկատմամբ՝ նախքան գրանցումը կամ հեռարձակումը

Օրինաչափություններ՝ `sk-`/`ak-`/`pk-` նախածանցով տոկեններ, `Bearer` տոկեններ և առնվազն 40 նիշից բաղկացած ընդհանուր տոկեններ։

### Վերին հոսքի CA վկայագիր

Երբ `AGENTBRIDGE_UPSTREAM_CA_CERT`-ը սահմանված է, ֆայլը կարդացվում է գործարկման պահին։ Եթե ուղին գոյություն ունի, սակայն ֆայլը հնարավոր չէ կարդալ, AgentBridge-ը գրանցում է հստակ սխալ և հրաժարվում է գործարկվել (սա կանխում է կորպորատիվ միջավայրերում TLS-ի աննկատ խափանումները)։

### Հայտնի սահմանափակումներ

- **443 պորտը պահանջում է արտոնություն**. Linux-ում AgentBridge-ին անհրաժեշտ է Node-ի գործարկելի ֆայլի վրա կիրառված `setcap 'cap_net_bind_service=+ep'`, կամ այն պետք է գործարկվի `authbind`-ի միջոցով։ Կարգաբերման օգնականը ցուցադրում է օպերացիոն համակարգին հատուկ հրահանգներ։
- **Պահանջվում է IDE-ի վերագործարկում**. DNS վերահղումից հետո IDE-ն պետք է վերագործարկվի, որպեսզի հոսթի նոր լուծումը ուժի մեջ մտնի։
- **Կոշտ կոդավորված OAuth տոկեններ**. Որոշ գործակալներ (Kiro, Antigravity) OAuth թարմացման տոկենները պահում են տեղային կերպով։ Դրանք թափանցիկ են AgentBridge-ի համար. այն յուրաքանչյուր հարցման մեջ տեսնում է Bearer տոկենը, որը քողարկվում է գրանցումից առաջ։
- **Electron ճակատային մասերին անհրաժեշտ է `NODE_EXTRA_CA_CERTS`**. այն IDE-ները, որոնց ճակատային մասն աշխատում է ներկառուցված Node/Electron կատարման միջավայրում, անտեսում են OS/NSS վստահության պահոցը և պետք է գործարկվեն shell-ից՝ սահմանված `NODE_EXTRA_CA_CERTS`-ով (տե՛ս §3.2)։ Բացակայության ախտանիշը՝ IDE-ի հետին մասը նույնականացվում է (MITM-ը ցույց է տալիս `200` պատասխաններ), սակայն UI-ը մնում է դուրս գրված վիճակում։
- **Նույն IDE-ի մի քանի տեղադրումներ անկախ են**. համակարգային տեղադրումը (օրինակ՝ `/usr/share/antigravity/antigravity`) և օգտատիրոջ տեղային «Full» տեղադրումը (օրինակ՝ `~/AntigravityIDE_Full/antigravity-ide`) առանձին գործընթացներ են՝ իրենց կատարման միջավայրերով. յուրաքանչյուրը պետք է վերագործարկվի՝ CA-ն ներարկված վիճակում։ Նախքան վերագործարկումը որոշեք, թե որն է աշխատում՝ ըստ դրա գործարկելի ֆայլի ուղու։
- **Ինքնությունը սահմանվում է գործակալի համակարգային հուշմամբ, ոչ թե ուղղորդված մոդելով**. երբ գործակալի մոդելը վերանշանակում եք այլ մատակարարի, պատասխանը շարունակում է պնդել գործակալի բնօրինակ ինքնությունը (օրինակ՝ Antigravity-ն պատասխանում է «Իմ հիմքում Gemini-ն է»), քանի որ IDE-ն դա ներարկում է համակարգային հուշման մեջ։ Իրական հետին մասը հաստատեք `call_logs` / `proxy_logs`-ում (`provider`, `model`, `target_format`), այլ ոչ թե մոդելին հարցնելով, թե ով է այն։

## §6 Խնդիրների լուծում

### 443 պորտի հակասություն

Եթե մեկ այլ գործընթաց արդեն լսում է 443 պորտը (վեբ սերվեր, VPN և այլն)՝

```bash
lsof -i :443          # գտնել գործընթացը
sudo fuser -k 443/tcp  # հարկադրաբար դադարեցնել (օգտագործեք զգուշությամբ)
```

Որպես այլընտրանք՝ AgentBridge-ի կարգավորումներում նշեք արտոնություններ չպահանջող պորտ և կազմաձևեք `iptables` / `pf` վերահղման կանոններ։

### Վկայագիրը վստահելի չէ

Եթե AgentBridge-ը գործարկելուց հետո IDE-ն ցուցադրում է TLS սխալներ՝

1. Ստուգեք, որ վկայագիրը տեղադրված է՝ `security find-certificate -c "OmniRoute AgentBridge"` (macOS) կամ `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Որոշ հավելվածներ պահպանում են վստահելի վկայագրերի սեփական շտեմարանը (Firefox, Chrome-ը Linux-ում)։ Կրկին գործարկեք «Trust Cert»-ը և ստուգեք NSS/Firefox-ին հատուկ վկայագրերի շտեմարանը։
3. Վստահություն սահմանելուց հետո վերագործարկեք IDE-ն. ընթացիկ TLS աշխատաշրջաններն օգտագործում են վստահության հին վիճակը։

### IDE-ից ելք է կատարվել / «միացման սխալ»՝ չնայած վստահելի CA-ին

Ախտանիշ. DNS-ը վերահղելուց և CA-ին վստահություն սահմանելուց հետո Electron-ի վրա հիմնված IDE-ն (օրինակ՝ Antigravity-ը) բացվում է՝ **հաշվից ելք կատարված** վիճակում, կամ ցուցադրում է իսկորոշման/միացման սխալ, թեև MITM մատյանը ցույց է տալիս, որ սկզբնավորման կանչերը (`loadCodeAssist`, `fetchAvailableModels`, …) վերադարձնում են `200`։

Պատճառ. IDE-ի հետ տրամադրվող **Node/Electron գործարկման միջավայրն անտեսում է ՕՀ-ի վստահելի վկայագրերի շտեմարանը**։ Բնիկ հետնամասը (Go լեզվի սերվերը) վստահում է ՕՀ-ի CA-ին և հաջողությամբ իսկորոշվում է, սակայն Electron ճակատային մասը՝ ոչ, ուստի միջերեսը կարծում է, որ անցանց է։

Լուծում (երկու քայլն էլ). արտահանեք `NODE_EXTRA_CA_CERTS=<ca.crt>` **և վերագործարկեք IDE-ն այդ կեղևից**, ոչ թե աշխատասեղանի պատկերակից։ Նախ ամբողջությամբ փակեք IDE-ն. Electron-ի եզակի օրինակի կողպման պատճառով երկրորդ գործարկումն ընդամենը կենտրոնանում է արդեն գործող գործընթացի վրա, և նոր միջավայրն անտեսվում է։ Տե՛ս §3.2։
Սա համընկնում է վերին մակարդակի բաց զեկույցի հետ, որտեղ առանձին գործակալն աշխատում է MITM-ի միջոցով, սակայն IDE տարբերակը նույն կազմաձևմամբ չի աշխատում։

### DNS փոփոխությունները չեն տարածվել

Ստուգեք, որ `/etc/hosts`-ը թարմացվել է՝

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Մաքրեք DNS քեշը՝

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE-ն չի հայտնաբերվել

Ավտոմատ հայտնաբերումն օգտագործում է տեղադրման տարածված ուղիները։ Եթե հայտնաբերումը ձախողվում է, սակայն IDE-ն տեղադրված է՝

- Ստուգեք՝ արդյոք IDE-ի երկուական ֆայլը գտնվում է ոչ ստանդարտ տեղադրությունում
- Կարգավորման օգնականը շարունակում է աշխատել. հայտնաբերման ձախողումը պարզապես նշանակում է, որ նշանը չի ցուցադրի տեղադրման ուղին

### Մշակիչի սխալներ (վերին մակարդակից տվյալների ստացումը ձախողվում է)

Եթե AgentBridge-ը որսում է հարցումները, սակայն դրանք բոլորը ձախողվում են՝

1. Ստուգեք, որ առնվազն մեկ մատակարար միացված է `/dashboard/providers` հասցեում
2. Ստուգեք OmniRoute սերվերի մատյանները՝ `APP_LOG_LEVEL=debug`՝ `.env`-ում
3. Ստուգեք, որ `OMNIROUTE_BASE_URL`-ը մատնանշում է երթուղիչի ճիշտ վերջնակետը (լռելյայն՝ `http://127.0.0.1:20128`)

## §8 Ճանապարհային քարտեզ

### Trae-ի ուսումնասիրություն

Trae-ը համեմատաբար նոր AI կոդավորման օգնական է։ Մշակիչն իրագործելուց առաջ՝

1. Հայտնաբերել բինար ֆայլը/ընդլայնումը VS Code-ի / JetBrains-ի շուկաներում կամ որպես առանձին հավելված
2. mitmproxy-ի միջոցով որսալ թրաֆիկը՝ API հոսթերը և վերջնակետերի կառուցվածքները բացահայտելու համար
3. Որոշել նույնականացման մեխանիզմը
4. Գնահատել իրագործելիությունը՝ հիմնվելով ծառայության պայմանների և API-ի բացահայտելիության վրա

Մինչ ուսումնասիրության ավարտը, կառավարման վահանակի Trae քարտը ցուցադրում է «Ուսումնասիրվում է» կրծքանշան՝ «Հաղորդել իրագործելիության մասին» հղումով։ `src/mitm/handlers/trae.ts`-ում մշակիչի նախատիպը վերադարձնում է կառուցվածքավորված `Դեռ իրագործված չէ` սխալ։

### Սպասող գործակալներ (պահանջվում է MITM — հատուկ բազային URL-ի աջակցություն չկա)

Հետևյալ գործիքներն իրենց ընթացիկ տարբերակներում չեն աջակցում հատուկ բազային URL-ներ, ինչի պատճառով MITM-ը միջամտության միակ ուղին է։ Իրագործելիության գնահատումը դեռևս ընթացքի մեջ է՝

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDE-ից առանձին)
- **Cowork** (Anthropic-ի աշխատասեղանի հավելված)
