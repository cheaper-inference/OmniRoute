### Կառավարվող պրոքսի միջուկներ

Custom proxy host դաշտը նույնպես ընդունում է V2Ray աղբյուրի հղումը: Ընտրել** sing-box** կամ** Ռենտգեն** հստակորեն, ապա սեղմեք Պահպանել: Մուտքագրումը երբեք չի ներբեռնում կամ սկսում միջուկ: Save-ը ստուգում է թողարկման պաշտոնական արխիվը, վավերացնում է բնիկ կոնֆիգուրացիան, սկսում է հստակ localhost SOCKS լսող և միայն դրանից հետո գրում վստահված անձի ռեեստրի հանձնարարությունը: Չհաջողված ակտիվացումը վերականգնում է նախկին կառավարվող կոնֆիգուրացիան և գործընթացը: `STORAGE_ENCRYPTION_KEY` պահանջվում է; աղբյուրի հղումները կոդավորված են:

Կառավարվող ֆայլերը ապրում են `DATA_DIR/services/managed-proxy/` ներքո, TPROXY ից առանձին: Ընտրված միջուկի համար կա մեկ սեփական գործընթաց՝ մինչև 100 լսող: Ավտոմատ մեկնարկի կամ գլոբալ երթուղման լռելյայն չի փոխվել: Հաջող պահումը հիշում է ակտիվացումը միայն այս կառավարվող միջուկի համար. հավելվածի գործարկումը վերականգնում է միացված պահված միջուկները՝ օգտագործելով արդեն իսկ հաստատված երկուականը, երբեք բեռնման ժամանակի ներբեռնում: Բացահայտ կանգառը ջնջում է այդ ակտիվացման դրոշը: Բացակայող կամ վնասված երկուականը պահանջում է նորից պահպանել աղբյուրը: Ռեեստրի ջնջումը հեռացնում է աղբյուրը և լսողին տեղական; սովորական վերջնակետի խմբագրումները մերժվում են կառավարվող տողերի համար, այնպես որ պահպանված աղբյուրը չի կարող լուռ հեռանալ իր ուղղորդված լսողից:

| XHTTP URI տրանսպորտ                   | Մերժված է                                                                    | Աջակցված փոխակերպում                                                         |
| Մայրենի ելքային JSON                  | Ընտրված միջուկի թույլատրված վստահված անձը protocols/options, ստուգված է բնիկ | Ընտրված միջուկի թույլատրված վստահված անձը protocols/options, ստուգված է բնիկ |

Անհայտ լարերի ընտրանքները, անապահով TLS դրոշները, արտաքին պլագինները, տեղական ֆայլերի ուղիների ընտրանքները և չաջակցվող համակցությունները մերժվում են, այլ ոչ թե լուռ անտեսվում: Մայրենի օբյեկտները ելքային սահմանումներ են, այլ ոչ թե ամբողջ հիմնական կազմաձևեր. control/direct/bypass ելքերը չեն ընդունվում: sing-box 1.14-ում WireGuard օգտագործում է վերջնակետեր, ուստի այն չի ընդունվում որպես բնիկ արտագնա: Սա բոլոր ձևաչափերի փոխարկիչ չէ. SSR, ժառանգական whole-base64 Shadowsocks հղումները, կամայական Clash օբյեկտները և աղյուսակից բացակայող տրանսպորտի տարբերակները կարիք ունեն առանձին աջակցվող աղբյուրի ձևաչափի:

`/api/services/managed-proxy` վավերացված է և միայն շրջադարձային տարբերակով. GET թվարկում է խմբագրված մետատվյալները, POST պահպանում է `{core,name,sourceLink,id?,assignment?}`, PATCH ընդունում է `{core,action:"start"|"stop"}`: Պետք է ներկա լինի հյուրընկալողի վստահելի գործընկերների նամականիշը: Մայրենի հիմնական ախտորոշումը ճնշված է, քանի որ դրանք կարող են պարունակել հավատարմագրեր. կյանքի ցիկլի իրադարձությունները օգտագործում են գոյություն ունեցող կառուցվածքային հավելվածի ֆայլի գրանցիչը՝ առանց աղբյուրի հղումների կամ վերին հոսքի բեռների: Աջակցության համար կցեք միայն ախտահանված հավելվածների մատյանները: Պաշտոնական տարբերակները ամրացված են sing-box 1.14.3 և Xray 26.3.27-ին՝ թողարկում-ակտիվ SHA-256 մանիֆեստներով; ապագա թարմացումները պահանջում են փոխել տարբերակը և բոլոր ստուգված ամփոփումները միասին:

## 3. Կենսացիկլի վիճակների մեքենա

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
        առողջության ստուգումը հաջող է │         խափանում / SIGTERM │
                               ┌────▼─────┐  (ելք 5 վ-ի ընթացքում) │
                               │ running  │──── խափանում ────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Վիճակները պահվում են `version_manager` ՏԲ աղյուսակում (`status` սյունակ) և արտացոլվում
են `ServiceSupervisor`-ի հիշողության վիճակում։ Հիշողության վիճակը գործարկվող
գործընթացի համար հեղինակավոր աղբյուրն է, իսկ ՏԲ վիճակը՝ բեռնման ժամանակ օգտագործվող մշտական պահուստային աղբյուրը։

### Վիճակների անցումներ

| Սկզբնական վիճակ | Իրադարձություն                             | Վերջնական վիճակ         |
| --------------- | ------------------------------------------ | ----------------------- |
| `not_installed` | `install()`-ը հաջողվում է                  | `stopped`               |
| `stopped`       | կանչվում է `start()`                       | `starting`              |
| `starting`      | առողջության ստուգումը վերադարձնում է 200   | `running`               |
| `starting`      | գործընթացն ավարտվում է մինչև առողջ դառնալը | `error`                 |
| `running`       | կանչվում է `stop()`                        | `stopping` → `stopped`  |
| `running`       | գործընթացն անսպասելի ավարտվում է (< 5 վ)   | `error` (արագ խափանում) |
| `running`       | գործընթացն անսպասելի ավարտվում է (> 5 վ)   | `error`                 |
| `error`         | կանչվում է `start()`                       | `starting`              |
| ցանկացած        | `stop()`՝ `stopping` վիճակում              | գործողություն չկա       |

### Գործողությունների կողպեք

`ServiceSupervisor`-ը կենսացիկլի գործողությունները հաջորդականացնում է ասինխրոն գործողությունների կողպեքի
(`withLock()`) միջոցով։ Նույն վերահսկիչի վրա միաժամանակյա `start()` կանչերը հանգեցնում են ճիշտ
մեկ գործընթացի ստեղծման․ երկրորդ կանչողը սպասում է և վերադարձնում առկա վիճակը։ Սա կանխում է
մրցակցային պայմանները, երբ, օրինակ, ավտոմեկնարկը և UI կոճակը գործարկվում են միաժամանակ։

## 4. API հղում

Բոլոր երթուղիները `/api/services/` ի տակ են**LOCAL_ONLY** (միայն loopback, կոշտ կանոն #17): Ոչ loopback հարցումները ստանում են `403 LOCAL_ONLY` անկախ վավերացման նշանից:

### 4.1 9 Երթուղիչի վերջնակետեր (11 երթուղիներ)

#### `POST /api/services/9router/install`

Տեղադրեք 9 երթուղիչը npm-ից: Ստեղծում է `DATA_DIR/services/9router/` իր սեփական `package.json` և `node_modules/`: Չի հակասում OmniRoute ի սեփական ադմիններին:

**Հարցման մարմին** (բոլորը ընտրովի):

```json
{ "version": "latest" }
```

| Դաշտ      | Տեսակ    | Կանխադրված | Նկարագրություն                                  |
| --------- | -------- | ---------- | ----------------------------------------------- |
| `version` | `string` | `"latest"` | npm տարբերակի պիտակ կամ semver տեղադրելու համար |

**Պատասխաններ:**

| Կարգավիճակ | Նկարագրություն                                                |

| `400`      | Հարցման անվավեր մարմին (Zod վավերացման ձախողում)              |

**API բանալի:** ներարկվել է որպես `WA_KEY` — open-wa-ի ընդհանուր `WA_*` -prefixed env անտեսումը քարտեզագրում է այն `--key`/`-k` CLI տարբերակի վրա (`dist/cli/setup.js::envArgs()`, ստուգված է տեղադրված 4.76.0 փաթեթի հետ): Նախածանցով `ow_`, երբ ստեղծվում է `generateServiceApiKey()`: open-wa-ն կարդում է բանալին `key`/`api_key` HTTP վերնագրից (ոչ `Authorization: Bearer`); `/api-docs*` բացահայտորեն ազատված է ստուգումից (`setupAuthenticationLayer` in `dist/cli/server.js`), այնպես որ առողջական զոնդը հաստատման վերնագրի կարիք չունի:

### 4.9 Հակադարձ պրոքսի (9 Երթուղիչի վահանակի ներդրում)

Վահանակի վահանակը տեղադրում է 9Router web UI ն iframe-ի ներսում՝ ներքին հակադարձ պրոքսիի միջոցով՝

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Այս վստահված անձը.

- Փոխանցում է հարցումը `http://127.0.0.1:{port}/{path}` ին (միայն loopback)
- Հեռացնում է մուտքային `cookie` և `authorization` վերնագրերը ( OmniRoute նիստի արտահոսք չկա)
- Ներարկում է `Authorization: Bearer {apiKey}` 9 երթուղիչի նույնականացման համար
- Արձագանքից քերթում է `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*`
- Վերագրում է HTML պատասխանները՝ `<base href>` ներարկելու և բացարձակ ուղիները նորմալացնելու համար (`/foo` → `/dashboard/.../embed/foo`)

Ներկառուցված վահանակի համար WebSocket արդիականացումները մշակվում են ուղեկցող սերվերի կողմից՝ նվիրված հատուկ նավահանգստի վրա (տես `src/lib/services/embedWsProxy.ts`):

**Անվտանգություն:** Ներկառուցված պրոքսի երթուղիները դասակարգված են `LOCAL_ONLY_API_PREFIXES` տակ և հնարավոր է հասնել միայն շրջադարձից: Հարձակվողը, ով JWT է ստանում Cloudflare/Ngrok թունելի միջոցով, չի կարող միջնորդ դառնալ ներկառուցված ծառայությունների մեջ:

## 5. Անվտանգություն

### LOCAL_ONLY-ի կիրարկում (խիստ կանոն #17)

`/api/services/` և `/dashboard/providers/services/*/embed/` ուղիների ներքո գտնվող բոլոր երթուղիները
`src/server/authz/routeGuard.ts`-ում դասակարգված են որպես LOCAL_ONLY։ Հետադարձ կապի հասցեի ստուգումը
կատարվում է անվերապահորեն՝ նույնականացման ցանկացած ճյուղից առաջ․

```
հարցումը հասնում է
  → isLocalOnlyPath(path)?
      → ոչ հետադարձ կապի հասցե → 403 LOCAL_ONLY (միշտ՝ նույնականացման ստուգումից առաջ)
      → հետադարձ կապի հասցե    → անցում սովորական նույնականացմանը
```

Սա թույլ չի տալիս, որ արտահոսած JWT-ն (օրինակ՝ թունելի միջոցով) գործարկի `npm install`-ը կամ
պրոցեսների ստեղծումը։ Մակարդակների ամբողջական մատրիցը տե՛ս
`docs/security/ROUTE_GUARD_TIERS.md`-ում։

### API բանալու ներարկում

9Router-ը և Mux-ը սեփական HTTP վերջնակետերի համար պահանջում են API բանալի/կրող թոքեն։
OmniRoute-ը՝

1. Ստեղծում է բանալի `crypto.randomBytes(32).toString("base64url")`-ի միջոցով՝
   ծառայությանը հատուկ նախածանցով (`nr_`՝ 9Router-ի համար, `mx_`՝ Mux-ի համար)։
2. Պահպանման վիճակում կոդավորում է այն AES-256-GCM-ի միջոցով (նույն գաղտնագիրը, որն օգտագործվում է մատակարարի հավատարմագրերի համար)։
3. Ապակոդավորում և պրոցեսի ստեղծման պահին ներարկում է այն որպես միջավայրի փոփոխական՝
   `NINEROUTER_API_KEY`՝ 9Router-ի համար, `MUX_SERVER_AUTH_TOKEN`՝ Mux-ի համար (երբեք ոչ որպես CLI
   դրոշ, որպեսզի թոքենը երբեք չհայտնվի `ps`/պրոցեսների ցուցակներում)։
4. Երբեք որևէ HTTP պատասխանում չի վերադարձնում բանալու բաց տեքստը։

CLIProxyAPI-ն ստանում է տվյալների հարթակի հատուկ բանալի, որը ներարկվում է պրոցեսի ստեղծման պահին
(`needsApiKey: true` — օգտագործվում է ադապտերի հետ մոդելների համաժամացման համար)։

### Պաշտպանություն SSRF-ից

Հակադարձ HTTP պրոքսին (`/dashboard/.../embed/[...path]`) կոշտ կերպով կազմաձևված է հարցումները փոխանցելու
միայն `http://127.0.0.1:{port}` հասցեին։ Այն երբեք չի հետևում դեպի ոչ հետադարձ կապի
նպատակակետեր ուղղորդող վերահղումներին։ `ssrf-req-filter` գրադարանն օգտագործվում է՝ մերժելու վերին հոսքի ցանկացած URL, որը
որոշվում է հետադարձ կապի տիրույթից դուրս։

### Կեղևի անվտանգություն (խիստ կանոն #13)

`npm install`-ը կանչվում է `execFile('npm', ['install', pkg, '--prefix', dir])`-ի միջոցով՝
առանց ձևանմուշային տողերի, կեղևի կամ արտաքին ուղիները հրամանի տողի մեջ ներմուծելու։
Կատարման ժամանակի արժեքները (պորտեր, API բանալիներ) փոխանցվում են զավակ պրոցեսի `env` օբյեկտի միջոցով։

### Սխալների մաքրում (խիստ կանոն #12)

`/api/services/*`-ից ստացվող բոլոր սխալի պատասխաններն անցնում են `buildErrorBody()`-ի կամ
`sanitizeErrorMessage()`-ի միջով։ Չմշակված `err.stack`-ը և `err.message`-ը երբեք բառացիորեն չեն վերադարձվում
կանչողին։

## 6. Նոր ներկառուցված ծառայության ավելացում

Հետևեք այս 8 քայլերին։ Որպես կանոնական հղում՝ ուսումնասիրեք `src/lib/services/installers/`
և `src/app/api/services/` հասցեներում առկա իրականացումները։

### Քայլ 1 — Ստեղծեք տեղադրիչը

Ստեղծեք `src/lib/services/installers/{name}.ts`՝ որպես մոդել օգտագործելով `ninerouter.ts`-ը․

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // ընտրեք ազատ պորտ

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

Օգտագործեք `runNpm(['install', NAME_PACKAGE, '--prefix', dir])`-ը `installers/utils.ts`-ից՝
երբեք մի օգտագործեք `execSync` կամ կեղևային միջարկում։

### Քայլ 2 — Գրանցեք սկզբնական մեկնարկում

`src/lib/services/bootstrap.ts`-ի `SERVICES` զանգվածում ավելացրեք `ServiceEntry`․

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // false, եթե API բանալի պետք չէ
}
```

Ընդլայնեք `buildSpawnArgsFactory()`-ն այնպես, որ այն մշակի `cfg.tool === "myservice"` պայմանը։

#### Միացվող մատակարարի հավելման պայմանագիր (Փուլ 1, #7333)

`src/lib/services/providerPlugins/`-ը ներկայացնում է `ServiceProviderPlugin` պայմանագիր, որը
հետնամասի `bootstrap.ts`-ի `ServiceEntry` դաշտերը և `serviceBackends.ts`-ի
հայտագրի ձևանմուշի դաշտերը միավորում է մեկ օբյեկտի մեջ՝ փոխարենը նույն հետնամասի կառուցվածքը
երկու անկապ ֆայլերում առանձին արտահայտելու։ Այս գրության պահին **միայն `9router`-ն է
տեղափոխված**․ `bootstrap.ts`-ը ստանում է իր `SERVICES[]` գրառումը
`getServiceProviderPlugin("9router")`-ից (`src/lib/services/providerPlugins/registry.ts`)՝
գործարկման սխալ առաջացնելով, եթե հավելումը երբևէ բացակայի։ `cliproxy`-ն, `mux`-ը և `bifrost`-ը
մնում են նախկինում գոյություն ունեցող ներկառուցված `SERVICES[]` լիտերալներում՝ առանց փոփոխության։

`open-sse/config/providerPluginManifest.ts`-ը նաև ստացել է հավելող
`createServiceBackendManifestEntry(pluginId, template)` օգնական, որը
`SERVICE_BACKEND_MANIFEST_TEMPLATE` գրառումից կառուցում է պատշաճ ձևավորված
`ProviderPluginManifestEntry`․ այն **դեռ միացված չէ** որևէ գործող հարցման ուղու
(ո՛չ `generateProviderPluginManifestFromRegistry()`-ի,
ո՛չ `/v1/providers/[provider]/models`-ի)։ Դա մնում է որպես հետագա աշխատանք, երբ պայմանագիրը
փորձարկված լինի երկրորդ հետնամասի համար։

Հետաձգված է հետագա PR-ներին և հետևարկվում է #7333 խնդրի ներքո՝ `cliproxyapi`-ի տեղափոխումը նույն
ռեեստրի միջոցով, `mux`/`bifrost`-ի ընդհանրացումը `ServiceBackendPluginId` միության մեջ,
կատարողի երթուղավորման հատուկ մշակման (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) ներառումը հավելման պայմանագրում և
`createServiceBackendManifestEntry()`-ի միացումը գործող հայտագրի/մոդելների կոդային ուղուն։

## 7. Խնդիրների լուծում

### Ծառայությունը չի մեկնարկում

**Ախտանիշներ․** Մեկնարկի կոճակը վերադարձնում է 503, վիճակը մնում է `"error"` կամ `"starting"`։

**Ստուգաթերթ․**

1. Ստուգեք `GET /api/services/{name}/logs`-ը (կամ կառավարման վահանակի Logs վահանակը)։ Փնտրեք
   այնպիսի տողեր, ինչպիսիք են՝ `Error: ENOENT`, `address already in use` կամ `Cannot find module`։
2. Համոզվեք, որ `npm`-ը PATH-ում է․ OmniRoute-ն աշխատեցնող նույն օգտահաշվից գործարկեք `which npm`։
3. Համոզվեք, որ ծառայությունը տեղադրված է․ `installedVersion`-ի առկայությունը ստուգեք
   `GET /api/services/{name}/status`-ում։ Եթե այն `null` է, նախ կատարեք տեղադրումը։
4. Ստուգեք, որ `DATA_DIR/services/{name}/node_modules/`-ը գոյություն ունի և դատարկ չէ։
5. Մաքրված ելքի պատճառը տեսնելու համար ստուգեք կարգավիճակի պատասխանի `lastError` դաշտը։

### Սառը մեկնարկը դանդաղ է (`running` վիճակին հասնելու համար պահանջվում է > 10 վ)

**Ախտանիշներ․** Վիճակը երկար ժամանակ մնում է `"starting"`, նախքան `"running"` կամ `"error"` դառնալը։

**Բացատրություն․** 9Router-ի սառը մեկնարկը ներառում է կախվածությունների մեծ ծառերի ներմուծում (DNS,
թունել, MITM մոդուլներ)։ Աշխատունակության ստուգման լռելյայն միջակայքը 2 վ է՝ 3 փորձով, որից հետո
վերահսկիչը հայտարարում է ժամանակի սպառում (սակայն շարունակում է հարցումները)։

**Լուծում․** `healthIntervalMs`-ը և `waitForHealthy`-ի ժամանակի սահմանաչափը
(`healthIntervalMs * 3`) կարգավորվում են `bootstrap.ts`-ում։ Ավելի երկար մեկնարկի
ժամանակ պահանջող ծառայությունների համար `healthIntervalMs`-ը մեծացրեք մինչև 5000, իսկ `stopTimeoutMs`-ը՝ մինչև 30 000։

### Պորտի բախում (`EADDRINUSE`)

**Ախտանիշներ․** Մատյաններում ցուցադրվում է `address already in use :::20130`։

**Պատճառներ․**

- Մեկ այլ գործընթաց արդեն օգտագործում է 20130 պորտը։
- 9Router-ի նախորդ գործընթացն ամբողջությամբ չի դադարեցվել (զոմբի PID)։

**Լուծում․**

1. Փոխեք լռելյայն պորտը `.env`-ի `NINEROUTER_PORT` միջավայրի փոփոխականի միջոցով։
2. Գտեք և հարկադիր ավարտեք բախում առաջացնող գործընթացը․ `lsof -ti :20130 | xargs kill -9`։
3. Պորտը յուրաքանչյուր ծառայության համար կարգավորվում է `bootstrap.ts`-ի `port` դաշտի միջոցով։

**Նշում․** 9Router-ը լռելյայն օգտագործում է հենց 20130 պորտը՝
OmniRoute-ի լռելյայն 20128 պորտի հետ բախումից խուսափելու համար։

### Տեղադրման ժամանակ թույլտվությունը մերժվում է (EACCES)

**Ախտանիշներ․** Տեղադրումը վերադարձնում է 500, մատյաններում ցուցադրվում է `EACCES` կամ `permission denied`։

**Պատճառներ․**

- OmniRoute-ի գործընթացը գրելու իրավունք չունի `DATA_DIR`-ում կամ դրա ծնող գրացուցակում։
- Աշխատեցվում է ոչ արմատային Docker միջավայրում՝ առանց կապակցված հատորում գրելու հասանելիության։

**Լուծում․**

1. Ստուգեք `DATA_DIR`-ը (լռելյայն՝ `~/.omniroute/`)․ `ls -la ~/.omniroute/`
2. Համոզվեք, որ գրացուցակը պատկանում է OmniRoute-ի գործընթացն աշխատեցնող օգտատիրոջը․ `chown -R $USER ~/.omniroute/`
3. Docker-ում համոզվեք, որ հատորի միացումն ունի կոնտեյների օգտատիրոջ համար ճիշտ թույլտվություններ։

---

### Թարմացումը ձախողվում է (`npm install`-ի ժամանակի սպառում կամ ցանցային սխալ)

**Ախտանիշներ․** Թարմացումը վերադարձնում է 500՝ `InstallError`-ով, իսկ մատյաններում ցուցադրվում է ցանցային ժամանակի սպառում։

**Ստուգաթերթ․**

1. Համոզվեք, որ npm ռեեստրը հասանելի է․ `npm ping`։
2. Ստուգեք կորպորատիվ միջնորդ սերվերի առկայությունը․ `npm config get proxy`, `npm config get https-proxy`։
3. Փորձեք տեղադրումը կատարել ձեռքով․ `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`։
4. Մեկուսացված ցանցում աշխատելու դեպքում նախապես ներբեռնեք tarball-ը և օգտագործեք `npm install /path/to/tarball.tgz`։

---

### Ծառայությունը մեկնարկից անմիջապես հետո ցուցադրում է `"error"` վիճակ (արագ խափանում)

**Ախտանիշներ․** Վիճակը 5 վայրկյանից պակաս ժամանակում `"starting"`-ից անցնում է `"error"`-ի։
`lastError`-ը ցուցադրում է `"Fast crash (exited with code 1)"`։

**Ստուգաթերթ․**

1. Կարդացեք մատյանի վերջին հատվածն ամբողջությամբ․ `GET /api/services/{name}/logs?tail=500`։
2. Տարածված պատճառ է ծառայության կողմից ակնկալվող միջավայրի փոփոխականների բացակայությունը։
3. 9Router-ի համար համոզվեք, որ `NINEROUTER_DISABLE_MITM=true`-ը և
   `NINEROUTER_DISABLE_TUNNEL=true`-ը փոխանցվում են գործարկման միջավայրում (տե՛ս
   `installers/ninerouter.ts`-ի `resolveSpawnArgs`-ը)։

---

## 8. ՀՏՀ

**Հ.՝ Կարո՞ղ եմ ներկառուցված ծառայությունների վերջնակետերը հասանելի դարձնել ոչ loopback հաճախորդների համար։**

Ոչ։ LOCAL_ONLY մակարդակը միտումնավոր է սահմանված (խիստ կանոն #17)։ Այն երթուղիները, որոնք կարող են կանչել
`npm install` կամ գործարկել `node` գործընթացներ, չպետք է հասանելի լինեն ոչ loopback
թրաֆիքից, քանի որ հակառակ դեպքում թունելի (Cloudflare, Ngrok, Tailscale) միջոցով արտահոսած JWT-ն
թույլ կտար կամայական գործընթացներ գործարկել։ Բացառման հնարավորություն
`/api/services/`-ի համար չկա․ ի տարբերություն `/api/mcp/`-ի՝ այն ներառված չէ manage-scope շրջանցման
ցանկում։ Տե՛ս `docs/security/ROUTE_GUARD_TIERS.md`։

---

**Հ.՝ 9Router-ը և CLIProxyAPI-ն հասանելի կլինե՞ն production/cloud տեղակայումներում։**

Այո։ Երկու ծառայություններն էլ հետևում են նույն՝ նախ տեղային օգտագործման մոդելին, ինչ հենց OmniRoute-ը։ Դրանք աշխատում են
նույն մեքենայի վրա և հաղորդակցվում են loopback-ի միջոցով։ Այստեղ «Production»-ը նշանակում է այն VPS-ը
կամ տեղային սերվերը, որտեղ տեղակայված է OmniRoute-ը, այլ ոչ թե հեռավոր ամպային մատակարար։

---

**Հ.՝ Ինչպե՞ս վրիպազերծել supervisor-ը։**

1. Հետևեք SSE մատյանների հոսքին՝ `curl -N http://localhost:20128/api/services/9router/logs`։
2. Ստուգեք OmniRoute-ի pino ելքում կառուցվածքավորված մատյանները՝ զտված
   `service:supervisor` անվանատարածքով։
3. Ստուգեք DB տողը՝ `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`։
4. Օգտագործեք `GET /api/services/9router/status`՝ մեկ կանչով տեսնելու ընթացիկ կենդանի վիճակը, PID-ը, առողջական վիճակը
   և `lastError`-ը։

---

**Հ.՝ Supervisor-ը ցույց է տալիս `health: "degraded"` կամ `health: "unknown"`, սակայն վիճակը `"running"` է։ Արդյո՞ք դա խնդիր է։**

`"degraded"`-ը նշանակում է, որ առողջական վիճակի ստուգումը վերադարձրել է ոչ 200 պատասխան։ `"unknown"`-ը նշանակում է, որ դեռևս ոչ մի
ստուգում չի ավարտվել (առաջին հարցման հետ մրցակցային վիճակ)։ Գործարկման ընթացքում երկուսն էլ ժամանակավոր են։
Եթե `"running"` վիճակին անցնելուց հետո առողջական վիճակը `"degraded"` է մնում ավելի քան `healthIntervalMs * 3` մվ,
ներկառուցված ծառայությունն աշխատում է, սակայն դրա HTTP API-ն չի արձագանքում։ Ստուգեք՝ արդյոք կարգավիճակի պատասխանում
նշված պորտը ճիշտ է, և արդյոք ծառայությունն իրականում
լսում է այդ պորտում։

---

**Հ.՝ Կարո՞ղ եմ փոխել 9Router API բանալին՝ առանց ամբողջական վերագործարկման։**

Ոչ։ API բանալին գործարկման պահին փոխանցվում է 9Router-ին միջավայրի փոփոխականի միջոցով։
Աշխատող գործընթացում միջավայրի փոփոխականները հնարավոր չէ փոխել։ `POST .../rotate-key`-ն
ինքնաշխատ կերպով կանգնեցնում և վերագործարկում է ծառայությունը՝ նոր բանալին կիրառելու համար։ Բանալու փոփոխությունն
ուժի մեջ է մտնում ծառայության `stopTimeoutMs`-ի (լռելյայն՝ 15 վ) և դրա գործարկման
ժամանակի հանրագումարի սահմաններում։

---

**Հ.՝ Ո՞րն է օղակաձև բուֆերի սահմանաչափը, և ի՞նչ է տեղի ունենում, երբ այն լցվում է։**

Յուրաքանչյուր ծառայություն ունի առանձին 5 ՄԲ օղակաձև բուֆեր։ Երբ բուֆերը լցվում է, ամենահին
մատյանային տողերը հեռացվում են՝ նորերի համար տեղ ազատելու նպատակով։ SSE `snapshot` իրադարձությունը վերադարձնում է
`tail` սահմանաչափի շրջանակում ամենավերջին տողերը։ Մատյանները սկավառակում չեն պահպանվում, եթե
DB տողում սահմանված չէ `logsBufferPath`-ը։
