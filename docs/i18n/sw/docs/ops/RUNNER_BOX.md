Bwawa linalojiendesha lenyewe linaendeshwa kwenye seva ya **.113** (`tomni-proxmox-113`). Tangu 2026-10-18 kila
runner ya OmniRoute ina **jukumu moja**, lebo moja, na bajeti ya kumbukumbu/CPU iliyowekwa kulingana na vipimo vya mzigo wake
wa kazi. Nafasi ya Turbopack hupata rasilimali zinazohitajika na build; nafasi nyingine zimewekewa rasilimali kulingana na
viwango vyao vya juu vilivyopimwa. Seva huzidisha mgao wa rasilimali pale tu ambapo build ya Turbopack inatokea wakati mmoja na build ya webpack ya Release-Green
pamoja na kazi ya lint; swap ya seva mwenyeji (16 GB) hufidia hali hiyo, na kwa sababu Builds za pull-request zinaendeshwa

## Sakinisha janitor (mara moja, kwenye mashine)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): kila baada ya dakika 30, andika kumbukumbu kwenye /var/log/runner-janitor.log
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` inahitajika: janitor huthibitisha kuwa njia haitumiki kwa picha moja ya hali ya faili
zilizofunguliwa kabla ya kuiondoa, na bila zana hiyo haiondoi chochote na husema hivyo
(exit 1). Jaribu mabadiliko yoyote kwa `--dry-run` kwanza — huchapisha kwa usahihi kile ambacho
ingefanya bila kubadilisha chochote.

Kile inachofanya kila inapotekelezwa: hufagia mabaki yetu wenyewe (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) baada ya **saa 3 kwenye tmpfs** na saa 24 kwenye diski ya
`_work/_temp`; huua `next-build` yenye umri wa zaidi ya dakika 75 (hakuna job inayotekelezwa kwa muda huo — mnamo
2026-08-27 moja ilitekelezwa kwa dakika 70 baada ya GitHub kutangaza kuwa job yake imepotea); hupogoa checkout
zenye umri wa saa 48 za runner ambazo unit zake **zimesimamishwa**; hutoa tahadhari diski inapofikia ≥ 85 %, PSI ya
kumbukumbu ya `full/avg60` inapofikia ≥ 10 %, na visikilizi vinapozidi `MAX_ACTIVE_RUNNERS` (pamoja na
mgawanyo wa omniroute/nyingine). Msimbo wa kutoka 1 = hatua inahitajika; soma logi.

Kanuni ya dakika 75 haigundui build ambayo GitHub tayari imeikatia tamaa. Wakati
`Runner.Listener` haiwezi kufanya upya job yake, `_diag/Runner_*.log` huonyesha
`POST request to …/renewjob timed out after 100 seconds`, API huripoti job kuwa `completed`
(failure) takribani dakika kumi baada ya ufanyaji upya wa mwisho uliofanikiwa, na `next-build` huendelea kutekelezwa bila
job iliyoambatishwa (2026-10-18: Build ya #17066 ilishindwa saa 19:43 na build yake bado
ilikuwa inashikilia GB 40 dakika tano baadaye). Thibitisha ref katika `_diag/Worker_*.log` mpya zaidi, kisha
tuma SIGTERM kwa mti wa build pekee kwa kutumia PID — `next-build`, `npm run build`, `build-next-isolated.mjs` na
worker za `_work`. Kamwe usiguse `Runner.Listener`, `RunnerService.js` au `Runner.Worker`: worker
huripoti job kuwa imeghairiwa na listener hurudi mtandaoni yenyewe.

## Unit za runner: KillMode

`KillMode=process` chaguo-msingi ya runner huacha `Runner.Worker → npm → next-build`
zikiendelea kutekelezwa wakati unit inaposimamishwa au kuanzishwa upya — build yatima huendelea kutumia RAM na
CPU bila job iliyoambatishwa. Kila unit ya OmniRoute ina faili ya nyongeza
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
yenye `KillMode=mixed`: SIGTERM hutumwa kwa listener kwanza, kisha SIGKILL kwa cgroup nzima wakati wa
`TimeoutStop`. Huanza kutumika unit itakapoanzishwa upya mara inayofuata — anzisha upya **runner moja kwa
wakati mmoja, wakati tu haitumiki**, huku ukaguzi wa kutotumika na uanzishaji upya vikiwa katika command moja.

## Kanuni za uendeshaji

- **Build moja ya Turbopack kwa wakati mmoja — inadhibitiwa kwa lebo.** Kila job inayoendesha
  `next build` kamili ya Turbopack inalenga `[self-hosted, omni-build]`, na ni **`omniroute-113-5`**
  pekee iliyo na lebo hiyo: `ci.yml` `Build`, `npm-publish.yml` `publish`, `nightly-v4-build`,
  `preview-artifact`, build ya kila usiku ya a11y (#16853) na **amd64** ya `docker-publish.yml`
  (webpack ndani ya BuildKit — Turbopack ilipata panic humo, run 33253576569). Sehemu ya Docker ya
  arm64 inabaki kwenye `ubuntu-24.04-arm`. amd64 ya `docker-publish` inashiriki kikundi cha concurrency
  cha `heavy-build-main` na `ci.yml` `Build` (`cancel-in-progress: false`). Docker Engine lazima iwe
  kwenye `omniroute-113-5`. Nafasi ya pili ya Turbopack haitoshi ndani ya GB 78 (GB 33–37 × 2 pamoja
  na matumizi mengine ya mashine); nafasi ya pili ni salama tu kwa build za webpack.
- **Build za pull request huendeshwa kwenye runner zinazohostiwa (2026-10-18).** `ci.yml` `Build`
  hufikia `omni-build` kwa `push` na `workflow_dispatch` pekee; kila Build ya `pull_request`
  (kutoka hazina yenyewe au fork) na `merge_group` huendeshwa kwenye `ubuntu-latest` kwa kutumia
  webpack. Kila PR kutoka hazina yenyewe ilipoelekezwa kwenye nafasi hiyo, Build ya Turbopack
  iliishikilia kwa dakika 29–58, Build 18 zilisubiri kwenye foleni kwa hadi saa 18, na Build ya
  push ya tawi la release yenyewe ilipata nafasi hiyo mara moja tu katika job 40. Kwenye runner
  zinazohostiwa, Build hiyo hiyo ya PR huchukua dakika 8–12 sambamba na job nyingine za PR.
  Turbopack, bundler ambayo `npm-publish` husambaza, inaendelea kujaribiwa kwenye tawi la release
  kupitia build ya kila usiku ya a11y ya tawi chaguo-msingi (04:41 UTC), kupitia kila Build ya push
  au dispatch inayofikia nafasi hiyo, na kupitia `npm-publish` yenyewe.
  `tests/unit/build/heavy-build-queue.test.ts` hufunga sharti lenye vipengele vinne.
- **Kamwe usipunguze ukubwa wa nafasi ya Turbopack chini ya hitaji lake lililopimwa.** Mnamo
  2026-10-18 saa 18:06 nafasi hiyo ilipunguzwa kutoka 56G/60G hadi 40G/44G ili kutoa nafasi kwa
  `omni-release`. Awamu ya compile ilikaa kwenye `MemoryHigh` wakati wote wa run yake (memory PSI
  `full` 30–43 %), na `Runner.Listener`, ambayo inashiriki cgroup hiyo, haikuweza kufanya upya job
  yake. Mipangilio ya mmiliki ya 56G/60G ya 2026-10-17 ilirejeshwa siku hiyo hiyo. Chini ya thamani
  hiyo build haifeli; inahangaika kwa kubadilishana kumbukumbu, na job inapotea.
- **Release-Green ina nafasi yake yenyewe (2026-10-18).** Hadi wakati huo uthibitishaji wote wawili
  wa Release-Green uliendeshwa kwenye `omni-build`: kwa kila push (~10/saa, run 97 kati ya 100 za
  push zilighairiwa zikiwa katikati ya kazi kwa siku moja) na sweep tatu kamili za takriban saa 2
  kwa siku (sweep ya 05:29 ilisubiri nafasi kwa saa 6) — nafasi moja ya build ilikuwa imezidiwa
  uwezo mara kadhaa na Build za PR kutoka hazina yenyewe zilisubiri kwa saa nyingi.
  `release-green` na `main-green` sasa zinalenga `omni-release` (`omniroute-113-6` pekee) kwa
  `OMNIROUTE_USE_TURBOPACK=0`, na run iliyoanza haig hairiwi tena na push mpya zaidi (nafasi
  inayosubiri bado hupunguza msururu huo). `tests/unit/build/runner-capacity-routing.test.ts`
  hufunga uelekezaji, ubadilishaji wa webpack na kuhakikisha kwamba hakuna chochote kwenye
  `omni-release` kinachofanya build kwa Turbopack.
- **Pool nyepesi: `omni-light`.** `omniroute-113` na `omniroute-113-2` huendesha run za kila usiku
  zinazohitaji `next build` ya backend pekee (~GB 5–6; webpack) na `quality.yml` `lint-guard`.
  `omniroute-113` ilikuwa na `MemoryHigh=4G` hadi 2026-10-18 — build ya promptfoo ilijikokota kwa
  kurejesha kumbukumbu kwa dakika 54 humo; GB 8 huondoa ubanaji huo.
- **Listener chache kwa makusudi.** Unit nne za OmniRoute zilizimwa mnamo 2026-08-29 — kila listener
  ya ziada ni mtumiaji mwingine wa bajeti ya kumbukumbu iliyo hapo juu. Kikomo cha janitor ni 6
  (`MAX_ACTIVE_RUNNERS=6` katika cron): huhesabu kila `Runner.Listener` kwenye mashine, na OmniHeuris
  - OmniMind huongeza mbili kwenye nne zetu.
- **Kamwe usisafishe `/tmp` au `_work` kwa mkono wakati runner yoyote ina shughuli.** Utaratibu wa
  kukagua-kisha-kufuta wenye pengo kati ya hatua hizo ndio uliosababisha job hai ya Build kupoteza
  `_work` yake mnamo 2026-08-27. Janitor hufanya ukaguzi na uondoaji katika hatua moja;
  mwache ifanye hivyo.
- Kusimamisha runner katikati ya job hughairi job hiyo (ilionekana moja kwa moja): tumia
  `systemctl stop` tu wakati listener yake haina child ya `Runner.Worker` — na ufanye hivyo kwa
  command moja.
- Workflow hazipaswi kuhifadhi artefakti kwenye `/tmp` (hiyo ni RAM). Pakua kwenda
  `$RUNNER_TEMP` (kwenye diski, kwa kila runner) — artefakti ya `next-build` ya GB 1.3 ilichukua
  dakika 27–32 kufika kwenye tmpfs na dakika 2 kupakiwa kutoka kwenye diski.
- VPS ya `.15` ni ya homologation pekee — kamwe haiendeshi runner za CI.

## Mkondo unaohudumiwa (runners zinazoendeshwa na GitHub)

Akaunti iko kwenye mpango wa **Pro**: **kazi 40 zinazoweza kuendeshwa kwa wakati mmoja kwenye runners zinazohudumiwa**, zinazoshirikiwa na kila ukaguzi wa PR,
kila workflow inayochochewa na push na usanidi chaguomsingi wa CodeQL. Ilipimwa tarehe 2026-10-18 wakati wa
kampeni ya merge (~merge 10 kwa saa kwenye `release/v3.8.52`): **workflow runs 2,500 ziliundwa ndani ya
saa 24**, push 44 kwenye branch ndani ya saa 6, **kazi 106 zinazohudumiwa zikiwa kwenye foleni** huku ukaguzi wa PR ukisubiri kwa
saa nyingi na PR zikiunganishwa bila ukaguzi huo. Workflow tisa zilianzishwa kwa kila push kwenye branch hiyo:

| kwa kila push kwenda `release/v*`           | kazi zinazohudumiwa | matokeo wakati wa msongamano                                              | tangu 2026-10-18                                                                         |
| ------------------------------------------- | ------------------: | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `ci.yml` (matrix kamili)                    |             hadi 30 | ilighairiwa na push iliyofuata, 24 kati ya 24 kwa siku                    | haianzishwi kwenye push za `release/**` (PR run + Release-Green)                         |
| `quality.yml`                               |                  ~6 | ilighairiwa, 23 kati ya 23                                                | haianzishwi kwenye push za `release/**`                                                  |
| `Release-Green` `--quick`                   |                   0 | iliendeshwa kwenye `omni-build`, 97 kati ya 100 zikaghairiwa              | nafasi ya `omni-release`, haighairiwi kamwe, run inayosubiri huunganishwa                |
| `Lock released branch`, `OpenSSF Scorecard` |                   2 | run moja ya foleni kwa kila push                                          | run moja kwa kila ref (`tests/unit/build/hosted-lane-concurrency.test.ts`)               |
| `Release acceptance` (ripoti kivuli)        |                   1 | `npm ci` moja inayohudumiwa kwa kila push, haighairiwi kamwe              | haijabadilishwa — inafaa kuwekewa kichujio cha `paths:`                                  |
| `Publish to Docker Hub` → `Deploy to VPS`   |                   2 | ilighairiwa kwa kila push; sehemu ya amd64 hushindana kwenye `omni-build` | haijabadilishwa — mkondo wa deployment wa mmiliki                                        |
| usanidi chaguomsingi wa CodeQL (`dynamic`)  |                   4 | `javascript-typescript`, `actions`, `c-cpp`, `python` kwa kila push       | haijabadilishwa — Settings → Code security; `c-cpp`/`python` hazichanganui chochote hapa |

`tests/unit/build/push-storm-diet.test.ts` huhakikisha kichochezi cha push cha `ci.yml` na
`quality.yml` kinatumika kwenye `main` pekee. Athari ya pembeni: Codecov haipokei tena upload ya msingi kwa kila push ya release (hatua hiyo
ni ya taarifa tu na ina `continue-on-error`); kizuizi cha coverage kilicho ndani ya repo na maoni ya PR
hayaathiriki.

**Kuongeza uwezo wa self-hosted hakutatui foleni ya hosted.** Devbox
(`devbox-vm-06-dev002`, vCPU 24 / GB 54) ingeweza kuhudumia runner, lakini vipindi vya agent tayari
hudumisha load yake kati ya 20–26, container ya agent haina Docker daemon, na mkondo uliojaa ni
ule wa hosted. Mashine ya `.113` ilikuwa na GB 71 zilizo wazi na load ya 5–8 wakati huohuo; kizuizi chake
ni bajeti ya kumbukumbu kwa kila listener iliyo hapo juu (kikomo cha listener 6), si CPU. Njia zilizobaki
ni za mchakato: unganisha PR za kampeni kupitia foleni ya Mergify (`label=queue`, batch hushiriki
CI run moja ya `merge_group` badala ya run moja kwa kila PR pamoja na moja kwa kila push), punguza lugha za
usanidi chaguomsingi wa CodeQL, na uchuje `release-acceptance.yml` kulingana na faili inazosoma.
