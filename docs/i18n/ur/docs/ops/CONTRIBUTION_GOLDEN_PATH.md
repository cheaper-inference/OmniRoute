اس رہنما کو کسی pull request کے لیے سب سے مختصر قابلِ اعتماد ترقیاتی چکر منتخب کرنے کے لیے استعمال کریں۔ یہ ذیل میں منسلک شعبہ جاتی architecture اور security دستاویزات کی جگہ
نہیں لیتا؛ بلکہ یہ ہر عام قسم کی تبدیلی کو اس کے contracts، مرکوز checks، اور CI coverage سے جوڑتا ہے۔

## وہ راستہ جس پر ہر تبدیلی چلتی ہے

1. **ترمیم سے پہلے base منتخب کریں۔** سب سے اعلیٰ فعال `release/v*` branch تلاش کریں اور اس کے
   تازہ ترین سرے سے branch بنائیں۔ اسی branch کو target کریں، `main` کو نہیں۔ اگر release freeze فعال ہو تو منجمد
   branch کو target نہ کریں؛
   [Branching & Release Model](BRANCHING_MODEL.md) میں بیان کردہ اگلا فعال cycle استعمال کریں۔
2. **Contracts کی نشان دہی کریں۔** ہر اس catalog، schema، generated artifact، public API، یا user
   interface کی شناخت کریں جسے تبدیلی متاثر کرتی ہے۔ ذیل کا جدول کم از کم ابتدائی مجموعہ فراہم کرتا ہے۔
3. **مرکوز tests لکھیں یا اپ ڈیٹ کریں۔** `src/`، `open-sse/`، `electron/`، یا
   `bin/` میں production تبدیلیوں کے لیے اسی PR میں ایک automated test درکار ہے۔ پہلے وہ مختصر ترین test files چلائیں جو
   رویے کو ثابت کرتی ہوں، پھر درج شدہ مرکوز gates چلائیں۔
4. **وسیع matrix کو CI پر چلنے دیں۔** مکمل unit shards، Vitest، coverage ratchet، اور
   production build PR پر چلتے ہیں۔ مقامی طور پر وسیع suite صرف اس وقت چلائیں جب کوئی مرکوز failure
   زیادہ وسیع اثر کی نشان دہی کرے یا تبدیلی کئی subsystems پر محیط ہو۔
5. **Review سے پہلے ہم آہنگ کریں۔** فعال base کو fetch کریں، اس کے نئے commits اور اس کے مقابلے میں اپنے diff کا جائزہ
   لیں، پھر contributor workflow کے مطابق base کو rebase یا merge کریں۔ Generated-file
   اور catalog conflicts کو ان کے source سے حل کریں، انہیں دوبارہ generate کریں، مرکوز loop پھر چلائیں، اور تصدیق کریں کہ
   PR اب بھی فعال release branch کو target کرتا ہے۔
6. **شواہد درج کریں۔** PR template میں چلائے گئے commands، شامل یا تبدیل کی گئی ہر test file،
   migrations یا feature flags، اور CI-only validation جو ابھی زیرِ التوا ہو، درج کریں۔

## تبدیلی کی قسم کے لحاظ سے Golden paths

ذیل کے commands کم از کم مرکوز checks ہیں، اور یہ کسی ایسے test کو چھوڑنے کی اجازت نہیں دیتے جو آپ کے
تبدیل کردہ رویے کا براہِ راست احاطہ کرتا ہو۔

### Provider

**Contracts**

- `src/shared/constants/providers/` میں Provider definition اور
  `src/shared/constants/providers.ts` میں اس کی composition۔
- `open-sse/config/providerRegistry.ts` یا اس سے اخذ کردہ registry files میں Models اور capabilities۔
- Executor/translator selection، OAuth یا API-key configuration، dashboard assets، اور جہاں قابلِ اطلاق ہو generated
  provider reference۔
- Public credentials کے لیے `resolvePublicCred()` استعمال کرنا لازم ہے؛ error responses کے لیے مشترکہ sanitized
  error helpers استعمال کرنا لازم ہے۔ `docs/security/PUBLIC_CREDS.md` (git؛ `/docs` میں compile نہیں ہوتی) اور
  [Error Sanitization](../security/ERROR_SANITIZATION.md) دیکھیں۔

**مرکوز loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # جب catalog تبدیل ہو؛ generated diff کو commit کریں
npm run lint
```

ہر متاثرہ request family کو بھی test کریں: chat، Responses، images، embeddings، audio، یا video۔
Generated catalog اور golden diffs کا contract تبدیلیوں کے طور پر جائزہ لیں؛ انہیں آنکھ بند کر کے قبول نہ کریں۔

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts` میں Public strategy values اور UI metadata۔
- `open-sse/services/combo.ts` اور `open-sse/services/combo/` کے تحت dispatch اور ordering۔
- Combo schemas، persistence، resilience state، model capabilities، اور API/UI controls۔
- رویہ تبدیل ہونے پر [Auto-Combo Engine](../routing/AUTO-COMBO.md) اور resilience documentation۔

**مرکوز loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy یا dispatch تبدیلیاں
npm run check:known-symbols      # strategy registration تبدیلیاں
npm run lint
```

مقامی طور پر deterministic mocked-upstream tests استعمال کریں۔ Live combo smokes کے لیے credentials درکار ہوتے ہیں اور یہ
دستی ہیں، CI کے متبادل نہیں۔

### UI / UX

**Contracts**

- `src/app/` اور `src/shared/components/` کے تحت Next.js route/page اور مشترکہ component boundaries۔
- API response shapes، loading/empty/error states، keyboard اور screen-reader behavior،
  responsive layout، theming، اور locale expansion۔
- `src/i18n/messages/en.json` میں English UI source strings؛ نئی user-facing عبارت کو hard-code نہ کریں۔

**مرکوز loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction یا visual تبدیلیوں کے لیے app چلائیں اور تنگ اور چوڑے، دونوں viewports کی جانچ کریں۔ CI
production build اور وسیع تر suites چلاتا ہے؛ visual behavior کے لیے پھر بھی تبدیلی کے مطابق ایک مرکوز component، Playwright،
یا دستاویزی manual check درکار ہے۔

### i18n

**Contracts**

- `src/i18n/messages/en.json`، UI source ہے؛ `config/i18n.json`، locale source ہے۔
- CLI catalogs الگ سے `bin/cli/locales/` کے تحت موجود ہیں۔
- ICU placeholders اور tags کو بالکل اسی طرح برقرار رکھیں۔ Product/provider/model names،
  protocol اور header names، commands، code/JSON identifiers، URLs، environment variables، یا
  `OmniRoute`، `OAuth`، `MCP`، اور `A2A` جیسی محفوظ اصطلاحات کا ترجمہ نہ کریں۔ موجودہ source list
  `scripts/i18n/glossary/protected-terms.json` ہے۔

**مرکوز loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # جب CLI strings/catalogs تبدیل ہوں
npm run lint
```

یہ موجودہ system کے لیے رہنمائی ہے، اس کے tooling یا key model کو وسعت دینے کی دعوت نہیں۔
جب تک متبادل system تیار کیا جا رہا ہے، i18n patches کو محدود اور ہدف پر مرکوز رکھیں۔ ایسے translation
commands نہ چلائیں جو external services کو call کرتے ہوں، الا یہ کہ task میں generated translations واضح طور پر درکار ہوں اور
آپ نے نتیجے میں بننے والے diff کا جائزہ لے لیا ہو۔

### CLI

**Contracts**

- `bin/cli/` میں عوامی کمانڈز اور فلیگز، تیار کردہ API کمانڈز، exit codes، stdout/stderr اور
  JSON آؤٹ پٹ کی ساختیں، config/environment کا برتاؤ، اور پیکیج کی گئی فائلیں۔
- CLI میں صارف کو دکھائی دینے والی strings کو لازماً CLI i18n layer استعمال کرنی چاہیے اور `en`/`pt-BR` catalogs کو ہم آہنگ رکھنا چاہیے۔
- Node کو معاونت یافتہ runtime اور شائع شدہ binary contract کے طور پر برقرار رکھیں۔

**مرکوز عمل**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تیار کردہ/بنڈل شدہ CLI تبدیلیاں
npm run check:pack-policy     # پیکیج کی عوامی سطح کی تبدیلیاں
npm run lint
```

جب برتاؤ parsing، فائلوں، یا exit status پر منحصر ہو تو عارضی data directory میں عین وہی command استعمال کریں۔ CI پیکیج artifacts اور ecosystem کی زیادہ وسیع جانچیں انجام دیتا ہے۔

### ڈیٹابیس

**معاہدے**

- `src/lib/db/` کے تحت domain modules؛ مخصوص modules کو براہِ راست import کریں (پرانا `localDb.ts` re-export layer ہٹا دیا گیا تھا)۔
- `src/lib/db/migrations/` کے تحت نمبر شدہ، idempotent SQL migrations، transaction کی حفاظت، upgrade کا برتاؤ، indexes، اور schema سے متاثر ہونے والا ہر caller۔
- Routes اور handlers کبھی بھی براہِ راست raw SQL جاری نہیں کرتے۔

**مرکوز عمل**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration شامل کرتے وقت تازہ database اور سابقہ schema سے upgrade، دونوں کی جانچ کریں۔ Database tests کو cleanup کے دوران handles بند کرنے اور `resetDbInstance()` کو call کرنے کی ضرورت ہے۔ `npm run test:bun:db` صرف اس وقت چلائیں جب best-effort Bun adapter path تبدیل ہو؛ Node ہی مستند رہتا ہے۔

### Build / deploy

**معاہدے**

- Root اور workspace manifests/lockfile، `scripts/build/`، Next.js standalone assembly، `dist/`
  پیکیج کا مواد، Electron platform metadata، CI workflows، اور deployment sentinels۔
- معاونت یافتہ Node ranges اور `CLAUDE.md` میں allow-listed Bun کا استعمال برقرار رہنا چاہیے۔
- Build artifacts کو untracked رکھیں؛ dependency، license، workflow، اور package policies لاگو ہوتی ہیں۔

**مرکوز عمل**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency یا lockfile کی تبدیلیاں
npm run check:pack-policy      # شائع شدہ پیکیج کی عوامی سطح کی تبدیلیاں
npm run lint
```

`npm run build` کو مقامی طور پر صرف اس وقت استعمال کریں جب تبدیلی compilation، standalone assembly، assets، یا runtime bundling کو متاثر کرے۔ `npm run build:release` صرف release/deploy validation کے لیے استعمال کریں۔ CI کا build حتمی cross-platform اشارہ ہے؛ platform-specific Electron تبدیلیوں کے لیے متعلقہ مرکوز build یا smoke evidence درکار ہے۔

## مشترکہ مشین کے لیے ڈیولپر اسکرپٹس

دو `scripts/dev/` معاون اسکرپٹس ایک ایسی devbox پر مقامی لوپ کو وضع کرتے ہیں جہاں دیگر سیشنز فعال ہوں:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD سے فائلیں
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # عین یہی فائلیں
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # علیحدہ worktree، متوازی استعمال میں محفوظ
```

- `typecheck-touched.sh` صرف تبدیل شدہ `.ts/.tsx` فائلوں کی typecheck ایک عارضی
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`، `types: ["node"]`، `noEmit`،
  `incremental: false`) کے ذریعے 6 GB heap کے تحت کرتا ہے، اس لیے یہ پورے پروجیکٹ کے `tsc -p tsconfig.json`
  کی جگہ لیتا ہے، جو مصروف مشین پر OOM ہو جاتا ہے۔ یہ تبدیل شدہ فائلوں کی خرابیوں کے ساتھ ایک خلاصہ سطر پرنٹ کرتا ہے اور
  تبدیل شدہ فائلوں میں خرابیاں ہونے پر `1`، جب صرف درآمد شدہ فائلوں میں خرابیاں ہوں یا tsc
  بغیر تشخیصی معلومات کے بند ہو جائے تو `2` (اس کی بتائی ہوئی لاگ `_artifacts/typecheck-touched/` کے تحت پڑھیں)، اور
  سب کچھ درست ہونے پر `0` کے ساتھ خارج ہوتا ہے۔ عارضی tsconfig ہمیشہ حذف کر دیا جاتا ہے؛ اسے کبھی commit نہ کریں۔
- `new-worktree.sh` بیک وقت ہونے والے runs کو `<git-common-dir>/omniroute-new-worktree.lock` پر سلسلہ وار کرتا ہے
  (پہلے سے طے شدہ طور پر 600 s تک، ایک نمایاں پیغام کے ساتھ انتظار کرتا ہے؛ اسکرپٹ کا header
  override کو دستاویز کرتا ہے) اور جب worktree کے وجود میں آنے سے پہلے `git worktree add` ناکام ہو تو
  اس کی بنائی ہوئی branch کو واپس ہٹا دیتا ہے، لہٰذا دوبارہ کوشش کے لیے دستی `git branch -D`
  درکار نہیں ہوتا۔ hard-linked `node_modules` اور `.husky/_` کی نقل میں کوئی تبدیلی نہیں ہوتی۔

## مقامی candidate لوپ

سورس ٹیسٹس یہ ثابت نہیں کر سکتے کہ پیکیج شدہ artifact شروع ہو سکتا ہے: packaging lists، pruned dependencies،
اور native binaries صرف tarball کو انسٹال کرکے شروع کرنے پر ناکام ہوتے ہیں۔ `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 کے build-once / validate / promote بہاؤ کا مقامی حصہ ہے:
یہ ایک candidate بناتا ہے، عین اسی artifact کی توثیق کرتا ہے، directory renames کے ذریعے اسے promote
کرتا ہے، اور promoted slot کے health check میں ناکامی پر اسے roll back کر دیتا ہے۔

```bash
npm run dev:candidate -- run --dry-run --json  # منصوبہ پرنٹ کریں، کوئی تبدیلی نہ کریں
npm run dev:candidate -- run                   # build + validate + promote، خودکار rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ میں انسٹال
npm run dev:candidate -- validate --id <id>    # دستیاب port پر شروع کریں، /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current، current → previous
npm run dev:candidate -- rollback              # current اور previous کو باہم تبدیل کریں
npm run dev:candidate -- run --from-tarball <file.tgz>  # کسی دوسری جگہ (CI) بنائے گئے tarball کو دوبارہ استعمال کریں
```

- **ایک بار build کریں۔** `build` موجودہ tree کو pack کرتا ہے (اسے `dist/server.js` درکار ہے، اس لیے پہلے
  `npm run build:release` چلائیں) یا `--from-tarball` کی نقل بناتا ہے، پھر tarball کو ایک
  علیحدہ npm prefix میں انسٹال کرتا ہے، کیونکہ tarball میں `node_modules` شامل نہیں ہوتا۔ id مختصر `HEAD`
  sha ہوتا ہے (جب tree میں مقامی تبدیلیاں ہوں تو `-dirty`) یا tarball کے لیے `tgz-<sha256>`۔ پہلے سے build شدہ
  clean id کو دوبارہ build کرنے کے بجائے دوبارہ استعمال کیا جاتا ہے؛ اسے دوبارہ build کرنے کے لیے `--force` دیں۔
- **سورس کی نہیں، package کی توثیق کریں۔** `validate` انسٹال شدہ CLI کو
  (`serve --port <free port>`) ایک تازہ `DATA_DIR=<candidate>/data`، جعلی secrets، اور
  ماحول سے operator کی `OMNIROUTE_API_KEY`، `STORAGE_ENCRYPTION_KEY` اور `INITIAL_PASSWORD` ہٹا کر
  شروع کرتا ہے، تاکہ یہ تازہ installation کی keyless loopback posture کو جانچ سکے۔ یہ
  `GET /api/health` سے 200 واپس آنے کا انتظار کرتا ہے، `GET /v1/models` سے 200 واپس آنے کو لازمی قرار دیتا ہے، process group
  کو روکتا ہے، اور tarball hash کے ساتھ فیصلہ `validation.json` میں ریکارڈ کرتا ہے۔
- **اسی artifact کو promote کریں۔** `promote` کسی ایسے candidate کو قبول نہیں کرتا جس کی
  موجودہ tarball hash کے لیے کامیاب validation موجود نہ ہو۔ پہلے سے طے شدہ active slot `_artifacts/candidate/current` ہے؛ `--target <dir>`
  اسی filesystem پر کوئی دوسری directory منتخب کرتا ہے، اور اس کا previous slot `<dir>.previous` ہوتا ہے۔
  ہر rename atomic ہوتا ہے، اور دورانِ عمل ناکامی کی صورت میں پہلے سے مکمل شدہ renames کو الٹ دیا جاتا ہے۔
- **Roll back کریں۔** `run` promoted slot کی دوبارہ توثیق کرتا ہے اور وہ check ناکام ہونے پر
  `current` اور `previous` کو واپس باہم تبدیل کر دیتا ہے۔ پہلی validation میں ناکام ہونے والے candidate کو کبھی promote نہیں کیا جاتا۔

ہر چیز gitignored `_artifacts/candidate/` کے تحت لکھی جاتی ہے؛ موجودہ OmniRoute
installation اور اس کی data directory کو کبھی نہیں چھیڑا جاتا۔ promoted CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ہے؛ اسے استعمال کرتے وقت اپنے `DATA_DIR` کے ساتھ
شروع کریں۔ Exit codes: کامیابی کے لیے `0`، ناکام validation یا promotion کے لیے `1`، اور usage error یا build موجود نہ ہونے کے لیے `2`۔

## مقامی لوپ بمقابلہ CI

| ہر پیچ کے لیے مقامی طور پر چلائیں                                   | CI وسیع تر اشارہ فراہم کرتا ہے                                        |
| ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| اوپر دیے گئے براہِ راست رویّے کے ٹیسٹس اور زمرہ جاتی گیٹس           | تقسیم شدہ مکمل یونٹ سوٹ اور سلسلہ وار ٹیسٹس                           |
| `npm run lint`                                                      | Vitest سوٹس اور کوریج/معیار کے تدریجی سخت معیارات                     |
| ٹائپ چیک یا بلڈ صرف اس وقت جب متاثرہ کنٹریکٹ اس کا تقاضا کرے        | پروڈکشن بلڈ، سیکیورٹی، دستاویزات، انحصارات، اور PR پالیسی گیٹس        |
| دستی تعامل/لائیو جانچ صرف اس وقت جب آٹومیشن رویّے کو ثابت نہ کر سکے | ورک فلو کے ذریعے ترتیب دی گئی کراس جاب انٹیگریشن اور پلیٹ فارم جانچیں |

ایک کامیاب مرکوز لوپ تبدیل شدہ کنٹریکٹ کے بارے میں ثبوت ہے، یہ اس بات کا ثبوت نہیں کہ غیر متعلقہ CI جانچیں
کامیاب ہوں گی۔ اس کے برعکس، ہر مقامی ترمیم کو مکمل ریپوزٹری میٹرکس کا انتظار نہ کروائیں۔

## ہم آہنگی کی چیک لسٹ

جائزے کی درخواست کرنے سے پہلے:

- تصدیق کریں کہ PR کی بیس اب بھی سب سے اعلیٰ فعال `release/v*` برانچ ہے۔
- اس بیس کو فیچ کریں اور اپنی برانچ بنانے کے بعد شامل ہونے والے کمیٹس کا جائزہ لیں۔
- غیر ارادی یا جنریٹ شدہ تبدیلیوں کے لیے `git diff <active-base>...HEAD` کا جائزہ لیں۔
- ماخذ کو اپ ڈیٹ کرکے اور آؤٹ پٹ دوبارہ جنریٹ کرکے کیٹلاگ اور جنریٹ شدہ دستاویزات کے تنازعات حل کریں۔
- ہم آہنگی کے بعد PR کی تفصیل میں درج ہر مرکوز ٹیسٹ/گیٹ دوبارہ چلائیں۔
- تبدیل شدہ بیس سے مطابقت پیدا کرنے کے لیے کبھی بھی اسَرشنز کمزور نہ کریں یا مطلوبہ ٹیسٹس حذف نہ کریں۔

ریلیز فریز اور دوبارہ ہدف مقرر کرنے کے قواعد کے لیے
[برانچنگ اور ریلیز ماڈل](BRANCHING_MODEL.md) استعمال کریں۔ CI کی مکمل فہرست کے لیے
[کوالٹی گیٹس کا حوالہ](../architecture/QUALITY_GATES.md) استعمال کریں۔
