## ریلیز برانچ پر لینڈنگ

omni-queue `release/vX.Y.Z` میں لینڈنگ کو کنٹرول کرتی ہے۔ PR پر اترنے سے پہلے ڈیفالٹ برانچ پر `config/merge-queue/config.json` میں ٹاپ لیول `mode` پڑھیں۔ [Omni-Queue](OMNI_QUEUE.md) دیکھیں۔

- **`shadow`** توثیق چلاتا ہے اور لینڈنگ کو دستی انضمام پر چھوڑ دیتا ہے۔ `omni-queue` منظور شدہ PR پر اس کے آخری سر پر لگائیں۔ `npm run queue -- why <PR>` کے ساتھ اہلیت کی جانچ کریں۔ `npm run queue -- history --base <branch>` میں اس سر کے فیصلے کا انتظار کریں۔ `would-land` پر آگے بڑھیں۔ `culprit-found` یا `would-dequeue` پر، مرج کو تھامیں اور وجہ کو ٹھیک کریں۔
- **شیڈو مستثنیات۔** موجودہ بیس ٹِپ کے خلاف سبز مکمل CI والی ٹرین علیحدہ قطار کے فیصلے کے بغیر آگے بڑھ سکتی ہے۔ اسی استثناء کا اطلاق ہوتا ہے جب PR ہیڈ میں پہلے سے موجودہ بنیادی ٹپ موجود ہو۔
- **`live`** لینڈنگ کو متحرک کرنے کے لیے `omni-queue` لیبل استعمال کرتا ہے۔ اکیلے قطار PR پر اترتی ہے۔ ضم کرنے کے احکامات چھوڑیں اور قطار میں براہ راست دھکیلیں۔

ہر لینڈنگ کے لیے مالک کی اجازت اور قابل اطلاق مطلوبہ چیک کی ضرورت ہوتی ہے۔ مالک کے لینڈنگ کی اجازت کے بعد ہی `omni-queue` اطلاق کریں۔ قطار میں لگے PRs کو چھونے والے محفوظ راستوں کو بھی اس PR کے لیے مالک کے `protected-approved` فیصلے کی ضرورت ہوتی ہے۔

"ایکٹو ریلیز پر گرین گیٹس کی ضرورت ہے" رول سیٹ کے لیے سر پر سبز `Gate / CI` اور `Gate / Quality` ضرورت ہوتی ہے۔ سرخ دروازے کو نظرانداز کرنے کے لیے کبھی بھی `--admin` استعمال نہ کریں۔ ایک ریلیز منجمد بلاکس منجمد برانچ میں ضم ہو جاتے ہیں۔ [سخت اصول 21](HARD_RULES_DETAIL.md) دیکھیں۔ کسی پل کی درخواست پر کبھی لیبل نہ لگائیں، ضم کریں یا پش نہ کریں کہ دوسرا سیشن کام کر رہا ہے۔ [سخت اصول 22](HARD_RULES_DETAIL.md) دیکھیں۔

## ٹرین پل کی درخواست

1. موجودہ ریلیز بیس ٹپ پر ٹرین برانچ شروع کریں۔ انضمام کی کمٹ کا استعمال کرتے ہوئے درست منظور شدہ ممبر ہیڈز کو ضم کریں۔ اسکواش اور ریبیس سے گریز کرتے ہوئے اپنی کمٹ کی تاریخ کو محفوظ رکھیں۔
2. ٹرین برانچ کے لیے ایک پل کی درخواست کھولیں۔ موجودہ بیس ٹپ پر اس کے اپنے مکمل CI کے ساتھ اس PR توثیق کریں۔ لینڈنگ سے پہلے بیس ٹپ اور منظور شدہ ممبر ہیڈز کو دوبارہ چیک کریں۔ جب تصدیق شدہ امیدوار تبدیل ہو جائے تو ٹرین اور اس کے CI ریفریش کریں۔
3. قابل اطلاق قطار موڈ کے تحت ایک مرج کمٹ کے ساتھ ٹرین PR لینڈ کریں۔ لائیو موڈ میں، قطار کا `merge-ff` لینڈنگ کا طریقہ مرج کمٹ کو محفوظ رکھتا ہے۔ اصل رکن سربراہان ریلیز برانچ سے قابل رسائی ہو جاتے ہیں۔ GitHub ممبر PRs انضمام کے طور پر نشان زد کرتا ہے اور کمٹ اپنے مصنفین کو برقرار رکھتے ہیں۔

ایک عوامی مثال [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071) ہے۔ اس نے 18 ممبرز PRs ملایا اور 24-11-2026 کو انضمام کے عہد کے ساتھ اترا۔

`main` سے اگلی ریلیز برانچ میں مطابقت پذیری بھی ایک مرج کمٹ کے ذریعے اترتی ہے۔ بعد میں سنک بیکس کے لیے `main` نسب کو محفوظ کرنا ضروری ہے۔ [ورک ٹری آئسولیشن](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash) دیکھیں۔

## مقامی انضمام ٹرین کی تصدیق کنندہ

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

توثیق کرنے والا بیس اور PR ہیڈز لاتا ہے اور انہیں ڈسپوز ایبل ورک ٹری میں جوڑتا ہے۔ یہ نتیجہ کے درخت پر ایک بار اپنا برابری سوٹ چلاتا ہے۔ ایک ناکام ہیڈ بازیافت یا ضم کرنے کا تنازعہ اس PR کو خارج کرتا ہے اور اسکرپٹ باقی PRs کے ساتھ جاری رہتا ہے۔

- **`--plan`** منتخب موڈ کے مراحل کو پرنٹ کرتا ہے اور ورک ٹری بنائے یا ریموٹ سے رابطہ کیے بغیر باہر نکلتا ہے۔ تیز رفتار منصوبے کا معائنہ کرنے کے لیے اسے `--fast` کے ساتھ جوڑیں۔
- **`--fast`** عام جامد دروازے چلاتا ہے، `tests/unit/` اور `npm run test:vitest` کے تحت منتخب کردہ تبدیل شدہ `node:test` فائلوں کو۔ فاسٹ موڈ استعمال کرتے وقت جمع شدہ ٹپ پر دن میں کم از کم ایک بار مکمل مقامی توثیق چلائیں۔
- **مکمل موڈ** مکمل صرف جامد دروازے شامل کرتا ہے اور `npm run test:unit` اور `npm run test:vitest` چلاتا ہے۔

اگر بیس پروب دستیاب ہو تو ایک ناکام جامد گیٹ اچھوت بیس پر دوبارہ چلایا جاتا ہے۔ اسکرپٹ وراثت میں ملنے والی ناکامیوں کی اطلاع دیتا ہے اور جاری رہتا ہے جب ہر تسلیم شدہ خلاف ورزی کی لائن بھی بنیاد پر ظاہر ہوتی ہے اور کل تعداد میں اضافہ نہیں ہوتا ہے۔

| باہر نکلیں۔ | مطلب                                                                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`         | منصوبہ پرنٹ کیا یا سویٹ مکمل کیا۔ سوٹ کا خلاصہ کسی بھی وراثت میں ملنے والی جامد ناکامیوں اور خارج شدہ PRs کی فہرست دیتا ہے۔                              |
| `1`         | غلط دلائل، کوئی Git چیک آؤٹ، ناکام پری فلائٹ، یا کوئی PR بورڈ نہیں ہوا۔                                                                                  |
| `2`         | ایک سوٹ چیک ناکام ہو گیا اور وراثت میں ملنے کے اہل نہیں ہوا۔ آپریٹر بیچ کو دو حصوں میں تقسیم کر سکتا ہے، ناگوار PR نکال سکتا ہے، اور دوبارہ چلا سکتا ہے۔ |

مقامی پاس صرف مالک کے ڈوزیئر کے لیے تشخیصی ثبوت فراہم کرتا ہے۔ ہر لینڈنگ کے لیے اب بھی مالک کی اجازت، اس کے اپنے مطلوبہ چیک، اور قابل اطلاق ہونے پر شیڈو قطار کے فیصلے کی ضرورت ہوتی ہے۔

## ٹائرنگ

- **فی PR** تبدیل شدہ راستوں کی بنیاد پر CI اور کوالٹی سلیکٹ چیکس۔ کوڈ PRs CI میں علیحدہ یونٹ اور Vitest ملازمتوں کے ساتھ تیز رفتار کوالٹی گیٹس اور متاثرہ ٹیسٹ چلاتا ہے۔
- **فی قطار امیدوار۔** CI اور کوالٹی کمپوزڈ امیدوار کے لیے مکمل پروفائل کو اپنی قطار ریف پر چلاتے ہیں۔
- **فی ریلیز ٹپ۔** ریلیز گرین پُشز پر فوری سخت گیٹ چلاتا ہے جو اس کے پاتھ فلٹرز سے مماثل ہے۔ فی دن تین طے شدہ رنز ریلیز برانچ کے لیے مکمل جھاڑو کا استعمال کرتے ہیں۔
- **فی ریلیز۔** مکمل CI میٹرکس میں E2E شارڈز، پیکج کی توثیق، ٹربال بوٹ سموک، اور کوریج چیک شامل ہیں۔ [ریلیز چیک لسٹ](RELEASE_CHECKLIST.md) دیکھیں۔

## `merge-train.sh` کے لیے تازہ چیک آؤٹ کی شرائط

پری فلائٹ ورک ٹریز بنانے سے پہلے چلتی ہے۔ `npm ci` کے ساتھ انحصار انسٹال کریں۔ تصدیق کریں کہ `node_modules/.bin/tsc` قابل عمل ہے اور یہ کہ `node_modules/node_modules` غیر حاضر ہے۔ چیک کریں کہ `node_modules/.bin/bun --version` کامیاب ہوتا ہے۔

اگر Bun پوسٹ انسٹال کو چھوڑ دیا گیا تھا، `(cd node_modules/bun && node install.js)` چلائیں۔ فراہم کنندہ کی مستقل مزاجی اور معلوم علامت کی جانچ Bun استعمال کرتی ہے۔ توثیق کرنے والا `npm run check:cycles:ratchet` بلاکنگ گیٹ کے طور پر چلاتا ہے۔ اسٹینڈ اسٹون `npm run check:cycles` کمانڈ مشاورتی ہے۔
