## npm ٹرسٹڈ پبلشنگ (v3.8.51 سے پہلے سے طے شدہ) — درخواست پر پیش کیا گیا، براہ راست فال بیک کے طور پر

`npm-publish.yml` کے ذریعے شائع ہوتا ہے۔** npm ٹرسٹڈ پبلشنگ (OIDC)** بذریعہ ڈیفالٹ: `stage-npm` جاب (github-hosted) GitHub کے id-token کا تبادلہ کرتا ہے ایک مختصر مدت کے npm اسناد کے لیے اس رن کے لیے — کوئی طویل المدتی npm ٹوکن ریپوزٹری سیکریٹ میں نہیں، کوئی 2FA پرامپٹ، پرووینس منسلک نہیں۔ یہ ہے بائی پاس این پی ایم پابندیاں اب 2FA کو چھوڑنے والے ٹوکنز کو ریٹائر کیا جا رہا ہے۔ یہ WS1.3 گارنٹی رکھتے ہوئے پروجیکٹ کے v3.8.48 تک مکمل طور پر خودکار بہاؤ کو بحال کرتا ہے (ایک لیک شدہ ٹوکن اکیلے — شائع نہیں کر سکتا کوئی ٹوکن نہیں ہے)۔

**ایک وقتی سیٹ اپ (مالک):** npmjs.com → پیکیج `omniroute` → ترتیبات → _Trusted Publisher_ → GitHub: مالک `diegosouzapw`، repo `OmniRoute`، ورک فلو `npm-publish.yml` (ماحول: کوئی نہیں)۔ جب تک یہ موجود نہ ہو، خودکار مرحلہ `ENEEDAUTH` کے ساتھ ناکام ہو جاتا ہے : `publish_mode=staged` (نیچے) یا `direct` کے ساتھ دوبارہ بھیجیں۔

### مرحلہ وار اشاعت (درخواست پر — `publish_mode=staged`)

npm-publish ورک فلو اب براہ راست شائع نہیں کرتا ہے: یہ پیکڈ ٹربال (`check:pack-boot`) کو بوٹ کرتا ہے اور پھر `npm stage publish` — چلاتا ہے بالکل صحیح بائٹس رجسٹری پر کھڑی ہیں،** انسٹال نہیں** جب تک مالک منظور نہیں کرتا۔ انسانی 2FA گیٹ AFTER ثبوت میں منتقل ہوا، اس سے پہلے نہیں۔

**ورک فلو سبز ہونے کے بعد مالک کا بہاؤ:**

1. `npm stage list omniroute` — اسٹیج آئی ڈی تلاش کریں ( ورک فلو سمری میں بھی پرنٹ کیا گیا ہے)۔
2. اسٹیج شدہ بائٹس کی تصدیق کریں (تجویز کردہ): `npm stage download <id>`، پھر ڈاؤن لوڈ کردہ ٹربال کو ایک عارضی سابقہ میں انسٹال کریں اور اسے بوٹ کریں (`npm run check:pack-boot` اسی پیک کو خودکار کرتا ہے → install → boot verdict CI میں)۔
3. `npm stage approve <id>` — 2FA پرامپٹ IS شائع کریں۔ `npm stage reject <id>` رد کرتا ہے۔
4. پوسٹ پبلش نیٹ: پوسٹ پبلش تصدیق کنندہ (v3.8.49 پلان کا WS1 4) پبلک رجسٹری سے شائع شدہ ورژن کو صاف کنٹینر میں انسٹال کرتا ہے اور اسے بوٹ کرتا ہے۔

**ایمرجنسی فال بیک:** `workflow_dispatch` `publish_mode=direct` کے ساتھ وراثت کو فوری طور پر بحال کرتا ہے `npm publish` (صرف اس صورت میں استعمال کریں جب اسٹیجنگ خود غلط برتاؤ کرے؛ کیوں ریکارڈ کریں)۔

**ایک بار سخت ہونا (مالک، npmjs.com):** `omniroute` کے لیے ٹرسٹڈ پبلشر کو صرف اسٹیج موڈ میں کنفیگر کریں تاکہ ایک لیک ہونے والا طویل المیعاد ٹوکن براہ راست کسی بھی جگہ سے `npm publish` نہیں کرسکتا — CI صرف اسٹیج کر سکتا ہے۔ صرف مالک کی 2FA ریلیز۔

**ٹوٹے ہوئے آرٹفیکٹ پلے بک (بغیر تبدیل شدہ):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` بطور ڈیفالٹ اضطراری (منٹ، ریورس ایبل)؛ `npm unpublish` صرف 72h/no-dependents ونڈو کے اندر اور کبھی بھی پہلی حرکت کے طور پر نہیں۔ Docker: کبھی بھی ورژن ٹیگ کو دوبارہ نہ لکھیں — رول بیک `latest` آخری اچھے ڈائجسٹ پر دوبارہ اشارہ کر رہا ہے۔

**Docker Hub `latest` (ہر مستحکم SemVer اشاعت پر ضروری ہے):** `docker-publish` ورک فلو کو ٹیگ کرنا ضروری ہے۔** دونوں** `X.Y.Z` اور، جب `should-promote-latest.sh` اتفاق کرتا ہے تو یہ سب سے زیادہ مستحکم SemVer ہے، `:latest` کے ساتھ** ایک ہی ڈائجسٹ** . کام کے بعد: حب `latest` ڈائجسٹ نئے SemVer ڈائجسٹ اور `last_updated` منتقل ہونے کے برابر ہے۔ `:latest` پرانی تعمیر پر مت چھوڑیں جب کہ ریلیز نوٹ ان اصلاحات کے بارے میں بات کرتے ہیں جو صرف گٹ پر موجود ہیں۔ کمپوز کوئیک سٹارٹس `:latest` استعمال کرتے ہیں؛ GitOps `X.Y.Z` کو پن کرتے رہنا چاہئے۔ [Docker ریلیز چینلز](../guides/DOCKER_GUIDE.md#release-channels) اور #10317 دیکھیں۔

**Docker حب تنظیمی ذخیرہ (`cheaperinference/omniroute`):** Docker Hub نام کی جگہوں کے درمیان کسی ذخیرے کو منتقل نہیں کرسکتا، لہذا `diegosouzapw/omniroute` اپنی پل ہسٹری اور ہر ریلیز کو برقرار رکھتا ہے، اور `docker-publish` کی `mirror-org-dockerhub` جاب ہر جاری کردہ ورژن (اور `:latest` کو فروغ دینے پر) `ghcr.io/cheaper-inference/omniroute` سے تنظیم کے ذخیرے میں کاپی کرتی ہے۔ اسے `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` راز کی ضرورت ہے۔ ان کے بغیر کام "Docker Hub org mirror skipped" وارننگ کے ساتھ سبز رہتا ہے اور دوسری رجسٹریاں عام طور پر شائع ہوتی ہیں۔ وہاں بعد میں جاری کردہ ورژن شائع کرنے کے لیے، چلائیں۔** ایکشنز → Mirror Docker امیج کو Docker Hub org → رن ورک فلو پر** `version=X.Y.Z` کے ساتھ (اور اعلی ترین مستحکم ورژن کے لیے `promote_latest` ): یہ موجودہ امیجز کو کاپی کرتا ہے، کوئی دوبارہ تعمیر نہیں۔

## ہاٹ فکس فاسٹ لین (لیبل `hotfix`)

`hotfix` لیبل والا PR بھاری CI میٹرکس (9-shard E2E، coverage ratchet،
quality-gate، quality-extended) کو چھوڑ دیتا ہے اور تیز، زیادہ مؤثر گیٹس برقرار رکھتا ہے: build،
unit shards، integration، vitest، lint/typecheck، docs-sync، `check:pack-artifact`
اور tarball boot-smoke (`check:pack-boot`)۔ ہدف: ~33min کے بجائے ≤15min میں گرین۔

**داخلے کی پالیسی — چاروں شرائط لازم ہیں (Chromium/VS Code/Node کی ایمرجنسی لینز کی طرز پر):**

1. **شدت**: پروڈکشن خراب ہے — شائع شدہ artifact بوٹ ہوتے وقت کریش کرتا ہے / کوئی
   سیکیورٹی فکس ہے / ریلیز کا ہر صارف متاثر ہے۔ "اہم" کا مطلب "خراب" نہیں۔
2. **اختیار**: صرف repository کا مالک `hotfix` لیبل لگاتا ہے۔ لیبل ہی
   منظوری ہے — campaign PR پر اسے کبھی خود سے استعمال نہ کریں۔
3. **ثبوت**: PR باڈی میں پچھلی مکمل طور پر گرین بھاری رَن کا لنک شامل ہو (وہ suite جسے
   چھوڑے گئے jobs دوبارہ validate کرتے)، نیز خود فکس کا پہلے ناکام اور پھر کامیاب ہونے والا test۔
4. **دائرۂ کار**: صرف cherry-pick — کم سے کم فکس، کوئی refactors نہیں، کوئی اضافی تبدیلیاں نہیں۔

چھوڑی گئی coverage/ratchet سطح کی اگلے مکمل رَن میں
release branch پر دوبارہ توثیق کی جاتی ہے (مسلسل release-green) — یہ لین صرف انتظار کو چھوڑتی ہے، validation کو کبھی نہیں۔
صرف tests والی diffs (`tests/` کے تحت تمام files، `tests/e2e/` کے تحت کوئی نہیں) بغیر کسی لیبل کے
خودکار طور پر E2E میٹرکس چھوڑ دیتی ہیں۔

### لے آؤٹ بنائیں

ریپوزٹری تین الگ آؤٹ پٹ ڈائریکٹریز کا استعمال کرتی ہے — ان کو کبھی نہیں ملاتا:

| ڈائریکٹری | مقصد                                                  | ٹریک کیا؟        |
| --------- | ----------------------------------------------------- | ---------------- |
| `src/`    | درخواست کا ذریعہ (TypeScript / TSX)                   | جی ہاں           |
| `.build/` | انٹرمیڈیٹس کی تعمیر — `next build` آؤٹ پٹ (`distDir`) | نہیں (نظر انداز) |
| `dist/`   | `assembleStandalone` کی طرف سے جمع کردہ npm بنڈل —    | نہیں (نظر انداز) |

> **آپریٹر نوٹ:** ریموٹ VPS امیج ڈائرکٹری `/usr/lib/node_modules/omniroute/app/` ہی رہتی ہے۔ صرف** ریپو میں** تعمیر آؤٹ پٹ منتقل (`app/` → `dist/`)۔ ریموٹ `app/` dir — میں rsync `dist/` مشمولات کی تعیناتی کی مہارتیں VPS راستے میں تبدیلی کی ضرورت نہیں ہے۔

**سنگل بلڈ فلو:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

کیا NOT `npm run build` چلائیں اس کے بعد — تعیناتی کے لیے علیحدہ `npm run build:cli` استعمال کریں `npm run build:release` جو ایک کمانڈ میں کلین ریبلڈ + سینٹینل کرتا ہے۔

`scripts/release/dry-run-lts-cut.mjs` کچھ بھی نہیں چلاتا: یہ git اور `gh` پڑھتا ہے اور پوری ترتیب — پیشگی شرائط کو پرنٹ کرتا ہے (ماخذ حل کرتا ہے، سورس ریپوزٹری کی پوری تاریخ ہوتی ہے — ایک اتلی کلون `stable/v3` آگے نہیں بڑھا سکتا، وصول کرنے والا فریق پہلے گرافٹ شدہ پیرنٹ پر پیک کو مسترد کرتا ہے، لہذا پہلے سے پہلے — ٹیگ کو کاٹ دیں یا پہلے سے موجود `git fetch --unshallow origin` ٹیگ کو کاٹ دیں۔ `package.json` ٹارگٹ ورژن ہے، `release-freeze` ایشو کھلا ہے، موجودہ ریلیز برانچ پر کوئی کھلا `Release branch not green` ایشو نہیں ہے — ایسی برانچ جو موجود نہیں ہے رپورٹ `?` نامعلوم، کبھی گرین — اومنی-قطار ریلیز PRs کو نہیں لاتا ہے (G11: `config/merge-queue/config.json` `live`، اس کا `bases` ریلیز برانچ کا انتظام کرتا ہے، `mode` `release/*` قوانین ابھی بھی موجود ہیں) ڈیلیٹ اور force-push، اور `stable/v3` اور `develop` ابھی تک موجود نہیں ہیں)، دو برانچ سٹیپس، جو غیر فعال ورک فلو کو متحرک کرتے ہیں اور `if:` حالات درست ہو جاتے ہیں (اور جو ریپوزٹری کے متغیر کے ذریعے گیٹ رہتے ہیں یا کینونیکل ریپوزٹری پر پن ہوتے ہیں)، متوقع ڈسٹ ٹیگز (`latest` → `next` and the `nightly` 9. `0` = `RESULT: READY` باہر نکلیں , `1` = بلاک کرنے کی پیشگی شرط ناکام ہوگئی (`✗`) , `2` = استعمال کی خرابی۔ `--advisory <id,...>` چیک کو چھپائے بغیر انتباہ (`!`) میں نیچے کر دیتا ہے۔

### PR پیش نظارہ آرٹفیکٹ (ایک بار بنائیں، اسی بائٹس کو فروغ دیں)

`.github/workflows/preview-artifact.yml` PR ہیڈ سے ایک پروڈکشن ٹربال بناتا ہے اور اس کی درست تعمیر (#8084 سلائس (a)) کی توثیق کرتا ہے۔ صرف ایک ہی ذخیرہ PRs ؛ کچھ بھی شائع نہیں ہوا.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # or add the `preview-artifact` label
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview install
```

The run does `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, packs the tarball, runs `npm run check:pack-boot` (fake secrets, ephemeral data dir), re-packs and fails unless the digest is identical, then records `artifact-identity.json` (head SHA, base SHA, lockfile hash, platform, arch, node ABI, bundler, build policy — `scripts/release/artifact-identity.mjs`) and attests the tarball in a separate job. Promoting a preview means installing that tarball: never rebuild from source.
