## SQLite کیوں؟

OmniRoute نے کئی وجوہات کی بنا پر PostgreSQL/MySQL کے بجائے SQLite کا انتخاب کیا:

| عنصر         | SQLite                                  | PostgreSQL                         |
| ------------ | --------------------------------------- | ---------------------------------- |
| **تعیناتی**  | ایمبیڈڈ — علیحدہ سرور کی ضرورت نہیں     | سرور سیٹ اپ درکار ہے               |
| **انکرپشن**  | ایپلیکیشن کی سطح پر (AES-256-GCM)       | بلٹ اِن TDE                        |
| **کارکردگی** | چھوٹے/درمیانے ورک لوڈز کے لیے زیادہ تیز | بہت بڑی متوازی تحریروں کے لیے بہتر |
| **ہم زمانی** | WAL موڈ متوازی ریڈز کی اجازت دیتا ہے    | مکمل MVCC                          |
| **بیک اپ**   | ایک فائل کی نقل                         | `pg_dump` یا فائل سسٹم اسنیپ شاٹ   |
| **استعمال**  | فی صارف انسٹالیشن، ایمبیڈڈ              | ملٹی ٹیننٹ SaaS                    |

**ایک صارف، ایک انسٹینس** والی تعیناتیوں کے لیے (جو OmniRoute کا بنیادی استعمال ہے)، SQLite زیادہ سادہ اور تیز ہے۔

### WAL جرنلنگ

`core.ts` ڈیٹابیس کو **WAL (Write-Ahead Logging) موڈ** کے ساتھ کھولتا ہے:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL تحریر کے دوران **متوازی ریڈز** کی اجازت دیتا ہے — یہ ڈیش بورڈ کے لیے اہم ہے، جو ریکویسٹ ریکارڈ ہوتے وقت کوئریز چلاتا ہے۔

ڈیفالٹ کیش سائز **65,536 KiB (64 MiB)** ہے۔ SQLite منفی
`cache_size` کو KiB میں ایک تخمینی بالائی حد سمجھتا ہے اور ضرورت کے مطابق پیجز مختص کرتا ہے۔
**Settings > System & Storage > Cache Size** میں **1 سے
1,000,000 KiB** تک عددی اقدار قبول کی جاتی ہیں؛ سیٹنگ محفوظ کرنے سے یہ براہِ راست ڈیٹابیس کنکشن پر لاگو ہو جاتی ہے،
اور OmniRoute آغاز کے وقت محفوظ شدہ قدر بحال کر دیتا ہے۔

## ڈیٹابیس کا مقام

SQLite فائل یہاں محفوظ ہوتی ہے:

| OS      | راستہ                                                        |
| ------- | ------------------------------------------------------------ |
| Linux   | `~/.omniroute/storage.sqlite`                                |
| macOS   | `~/.omniroute/storage.sqlite`                                |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                    |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` کے ذریعے قابلِ ترتیب) |

ساتھی فائلیں:

- `storage.sqlite-wal` — رائٹ اَہیڈ لاگ
- `storage.sqlite-shm` — مشترکہ میموری فائل
- `call_logs/` — ریکویسٹ پے لوڈ کے اجزا (اگر فعال ہوں)

**مقام تبدیل کریں:**

```bash
DATA_DIR=/custom/path omniroute
```

### ماڈیول کی حدود

ایک بنیادی آرکیٹیکچرل اصول: **ماڈیولز ایک دوسرے کے ٹیبلز تک براہِ راست رسائی حاصل نہیں کرتے**۔ کسی دوسرے ماڈیول کے ڈیٹا کے ساتھ کام کرنے کے لیے، اسی ماڈیول سے فنکشن امپورٹ کریں۔

```ts
// ❌ غلط: دوسرے ماڈیول سے براہِ راست SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ درست: providers ماڈیول کا فنکشن استعمال کریں
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

اس اصول کا نفاذ کوڈ ریویو کے ذریعے کیا جاتا ہے — کوئی جامد جانچ موجود نہیں، لیکن خلاف ورزیوں کی نشاندہی کی جاتی ہے۔

## ہجرتیں

OmniRoute استعمال کرتا ہے۔** ورژن شدہ، کمزور ہجرت** `src/lib/db/migrations/` میں ہر منتقلی ایک واحد SQL فائل ہے۔ نام کے دو فارمیٹس ایک ساتھ رہتے ہیں۔ `_omniroute_migrations` میں ریکارڈ شدہ ورژن عددی سابقہ ہے۔

### ہجرت کا نام دینا

| فارمیٹ                                           | مثال                                 | کے لیے استعمال کیا جاتا ہے۔                                                                                                                        |

### ضم شدہ ہجرت کو کبھی حذف یا نام تبدیل نہیں کیا جاتا ہے۔

ایک بار جب منتقلی کی فائل ریلیز برانچ یا `main` پر ہوتی ہے، تو یہ پہلے سے ہی ہومولوگ اور ڈویلپر ڈیٹا بیسز، VPS انسٹالز اور انٹرپرائز سنک میں چل چکی ہے۔ تب سے:

- **اسے کبھی حذف نہ کریں۔** تازہ تنصیبات اپنا سکیما کھو دیں گی جبکہ اپ گریڈ شدہ ڈیٹا بیس اسے برقرار رکھیں گے۔
- **اس کا نام تبدیل نہ کریں۔** `_omniroute_migrations` میں ورژن اب کسی فائل سے مماثل نہیں ہوگا، لہذا ہر وہ ڈیٹا بیس جو پہلے ہی اسے لاگو کر چکا ہے اسے دوبارہ چلائے گا۔ Non-idempotent SQL پھر ڈیٹا کو ڈپلیکیٹ کرتا ہے یا بوٹ کو روکتا ہے۔
- **ایک مختلف اسکیما کی ضرورت ہے؟** `npm run db:new-migration` کے ساتھ ایک نیا ہجرت بنائیں۔

نام تبدیل کرنا صرف اس فائل کے لیے محفوظ ہے جو ابھی تک ضم نہیں ہوئی ہے، جس صورت میں گیٹ کے اشارے کا حوالہ دیا گیا ہے۔ ریلیز ٹیگ یہاں کچھ بھی نہیں بدلتا: `release/v*` برانچ میں ہر دھکا Docker `:next` امیج کو شائع کرتا ہے اور homolog، VPS انسٹالز اور انٹرپرائز سنک پر چلتا ہے، اس لیے کسی بھی `vX.Y.Z` ٹیگ کے موجود ہونے سے پہلے ہی ضم شدہ ہجرت حقیقی ڈیٹا بیس پر چلتی ہے۔ گیٹ بیس فائل کو ہٹانے میں ناکام ہو جاتا ہے، ٹیگ کیا گیا ہو یا نہیں۔

- **ضم شدہ منتقلی کو واپس لانا۔** ایک `git revert` جو فائل کو حذف کرتا ہے گیٹ کو ناکام بنا دیتا ہے۔ فائل کو رکھیں اور اس کے اسکیما کو ایک نئی منتقلی میں کالعدم کریں: `npm run db:new-migration -- <description>`، `DROP TABLE IF EXISTS`، `DROP INDEX IF EXISTS` اور اسی طرح کے ساتھ۔ اپ گریڈ شدہ اور تازہ ڈیٹا بیس پھر اسی اسکیما کے ساتھ ختم ہوتے ہیں۔
- **ایک قبول شدہ نام: ایک مطابقت اندراج اور یکساں مواد۔** اگر ضم شدہ فائل کو منتقل ہونا ضروری ہے (مثال کے طور پر، دو ضم شدہ فائلیں ایک ٹائم اسٹیمپ کا اشتراک کرتی ہیں اور رنر ورژن کے تصادم کے ساتھ رک جاتا ہے)، اس کے SQL چھوئے بغیر بعد والی فائل کا نام تبدیل کریں اور `src/lib/db/migrationRunner/constants.ts` میں `{ fromVersion, fromName, toVersion, toName }` کو `RENAMED_MIGRATION_COMPATIBILITY` میں شامل کریں۔ پرانے ورژن کو لاگو کرنے والے ڈیٹا بیس فائل کو دوبارہ چلانے کے بجائے اپنی `_omniroute_migrations` قطار کو منتقل کر دیتے ہیں۔ گیٹ ایسے نام تبدیل کرنے کے بارے میں خبردار کرتا ہے اور ہمیشہ اس پر کمیوٹیشن چیک چلاتا ہے، جو بھی نیا ٹائم اسٹیمپ ہو: تازہ انسٹال فائل کو اس کی نئی پوزیشن پر لاگو کرتا ہے، اپ گریڈ شدہ ڈیٹا بیس ایسا نہیں کرتے، اس لیے پرانے کے قریب ایک نیا ٹائم اسٹیمپ چنیں۔ گیٹ نام تبدیل کرنے میں ناکام ہو جاتا ہے اگر مواد تبدیل ہو جاتا ہے (اسکیما کی تبدیلی اب بھی ایک نئی منتقلی میں ہوتی ہے)، یا اگر اندراج کی ہدف فائل ڈسک پر نہیں ہے۔
- **ایک ہی ٹائم اسٹیمپ کے اندر کبھی بھی نام تبدیل نہ کریں۔** ایک ایسا نام جو ٹائم اسٹیمپ کو برقرار رکھتا ہے اور صرف تفصیل کو تبدیل کرتا ہے وہ داخلے کے ساتھ یا اس کے بغیر گیٹ کو ناکام کرتا ہے۔ ایک اندراج کے ساتھ جس کا `toVersion` اس کے `fromVersion` برابر ہے، رنر پرانی `_omniroute_migrations` قطار کو حذف کر دیتا ہے اور فائل کو ہر اس ڈیٹا بیس پر دوبارہ لاگو کرتا ہے جو اسے پہلے سے چلا چکا ہے۔ اندراج کے بغیر، رنر صرف ورژن کو ٹریک کرتا ہے: یہ ان ڈیٹا بیس پر فائل کو چھوڑ دیتا ہے (نیا مواد وہاں کبھی نہیں چلتا ہے) اور ہر بوٹ پر دوبارہ نمبر کی غلطی کو لاگ کرتا ہے۔ ایک اور ٹائم اسٹیمپ کے علاوہ مطابقت کے اندراج کا استعمال کریں، یا نام رکھیں۔
- **گیٹ چیک کرتا ہے کہ نام تبدیل شدہ فائل دوبارہ نہیں چلتی ہے۔** ہر احاطہ شدہ نام کے لیے، گیٹ نئے فائل کا نام `--must-not-apply` کے ساتھ کمیوٹیشن چیک میں منتقل کرتا ہے۔ چیک اپ گریڈ شدہ ڈیٹا بیس کو اصلی رنر کے ساتھ بوٹ کرتا ہے، اور اگر رنر اس فائل کو دوبارہ لاگو کرتا ہے (مثال کے طور پر، کیونکہ اندراج میں غلط ورژن یا نام ہے، یا گیٹ کے ٹیکسٹ پارسر نے `constants.ts` TypeScript سے مختلف طریقے سے پڑھا ہے)، گیٹ `migration renomeada rodaria de novo` کے ساتھ ناکام ہوجاتا ہے اور آپ سے اندراج کے پرانے اور نئے ورژن اور ناموں کو چیک کرنے کو کہتا ہے۔

### گیٹ اڈے کے خلاف کیا چیک کرتا ہے۔

پل ریکوئسٹ اور merge-queue رن پر، `npm run check:migration-numbering` ڈسک پر موجود `src/lib/db/migrations/` بیس برانچ پر اسی ڈائرکٹری سے موازنہ کرتا ہے۔ بنیاد، اس ترتیب میں ہے: `--base-latest-tag`، `--base <ref>`، `MIGRATION_BASE_REF` متغیر، یا، جب `GITHUB_EVENT_NAME` `pull_request`، `pull_request_target` یا `merge_group` ہے، مرج کمٹ کا پہلا پیرنٹ، ایونٹ پے لوڈ کا `merge_group.base_sha` ، یا `git merge-base HEAD origin/$GITHUB_BASE_REF`۔ ایک پل کی درخواست یا ضم کرنے والی قطار میں بغیر کسی قابل حل بیس کے گیٹ ناکام ہوجاتا ہے۔ CI کے باہر `--base` کے بغیر یہ `comparação com a base: pulada (sem --base)` پرنٹ کرتا ہے اور ان اصولوں کو چھوڑ دیتا ہے۔

`--base-latest-tag` تازہ ترین ریلیز ٹیگ کے ساتھ موازنہ کرتا ہے ( semver ترتیب میں `vX.Y.Z` ؛ لاحقہ ٹیگز جیسے نائٹلیز شمار نہیں ہوتے ہیں) جو `HEAD` کی تاریخ میں ہے، `--base` جیسے ہی اصولوں کے ساتھ۔ ریلیز-گرین (`scripts/quality/validate-release-green.mjs`) گیٹ کو اس طرح چلاتا ہے، کیونکہ دھکا اور شیڈول رنز کی کوئی پل ریکوئسٹ بیس نہیں ہوتی ہے اور انضمام نئے CI رن کے بغیر اتر سکتا ہے۔ تاریخ میں کوئی ریلیز ٹیگ کے بغیر گیٹ ناکام ہو جاتا ہے۔ `git fetch --tags` چلائیں ( CI میں، `actions/checkout` `fetch-depth: 0` کے ساتھ ٹیگز لاتا ہے)۔

| ایک آؤٹ آف آرڈر، ترمیم شدہ یا تبدیل شدہ فائل میں `INSERT`، `UPDATE`، `DELETE` یا `REPLACE` بیانات ہوتے ہیں           | **وارننگ** : کمیوٹیشن چیک ڈیٹا کا موازنہ نہیں کرتا، اس لیے جائزہ لیں کہ آیا جس ترتیب میں اپ گریڈ اور تازہ ڈیٹا بیس لاگو ہوتے ہیں وہ نتیجہ بدلتا ہے۔                                                                                                                                                                                             |

کمیوٹیشن چیک کا ایک رن آؤٹ آف آرڈر، ترمیم شدہ اور نام تبدیل شدہ فائلوں کا ایک ساتھ احاطہ کرتا ہے۔

کمیوٹیشن چیک (`scripts/check/migration-commutation.ts`) اصلی انسٹال پاتھ کے ساتھ دو عارضی ڈیٹا بیس بناتا ہے: ایک** اپ گریڈ** ایک (بیس ہجرت کے ساتھ بوٹ کریں، پھر پل کی درخواست کی منتقلی کے ساتھ اسی فائل پر دوبارہ بوٹ کریں) اور ایک** تازہ** ایک (ایک بوٹ پل کی درخواست کی منتقلی کے ساتھ)۔ یہ نتیجے میں آنے والے اسکیموں کا موازنہ کرتا ہے: ٹیبلز اور کالم (کالم آرڈر کو نظر انداز کرتے ہوئے)، UNIQUE / PRIMARY KEY اور FOREIGN KEY رکاوٹیں، ہر ٹیبل کا نارملائزڈ `CREATE TABLE` ٹیکسٹ (جس میں CHECK رکاوٹوں، کولیشنز، جنریٹڈ کالمز اور ٹیبل ویو کے آپشنز شامل ہیں)، قطار کے اعداد و شمار کا موازنہ نہیں کیا جاتا ہے۔ اگر وہ مماثل ہیں، گیٹ پرنٹ کرتا ہے کہ فائل غیر ترتیب شدہ ہے لیکن سفر کرتی ہے، اور گزر جاتی ہے۔ اگر وہ مختلف ہوتے ہیں، تو گیٹ فرق کے ساتھ ناکام ہو جاتا ہے اور کیس کے لیے ایک اشارہ: ایک آؤٹ آف آرڈر فائل کے لیے، اس کا نام `npm run db:new-migration` کے ساتھ دوبارہ تخلیق کریں، جو محفوظ ہے کیونکہ فائل ابھی ضم نہیں ہوئی ہے۔ ترمیم شدہ بیس فائل کے لیے، بنیادی مواد کو بحال کریں اور تبدیلی کو نئی منتقلی میں ڈالیں۔ نام تبدیل کرنے والی فائل کے لیے، نام تبدیل کریں یا ایک اور نیا ٹائم اسٹیمپ منتخب کریں جہاں یہ سفر کرتا ہے، کبھی بھی دوسرے نام کے ساتھ ایک ہی ٹائم اسٹیمپ نہیں۔ اگر خود چیک نہیں چل سکتا تو گیٹ CI میں ناکام ہوجاتا ہے اور صرف مقامی طور پر انتباہ کرتا ہے۔ ترمیم شدہ بیس فائل کے لیے، اپ گریڈ شدہ ڈیٹا بیس اس فائل کے بیس کے مواد کے ساتھ بنایا گیا ہے، اور دوسرا بوٹ اسے چھوڑ دیتا ہے کیونکہ اس کا ورژن پہلے سے ہی ریکارڈ ہے۔ ایک تبدیل شدہ فائل کے لیے، اپ گریڈ شدہ ڈیٹا بیس فائل کے ساتھ اس کے پرانے نام کے ساتھ بنایا گیا ہے، اور دوسرا بوٹ اسے دوبارہ چلانے کے بجائے مطابقت کے اندراج کے ذریعے اپنی `_omniroute_migrations` قطار کو منتقل کرتا ہے۔ گیٹ `--must-not-apply` کے ساتھ نیا نام پاس کرتا ہے، لہذا اگر دوسرا بوٹ اسے لاگو کرتا ہے تو چیک ناکام ہوجاتا ہے۔ اگر پل کی درخواست منتقلی اپ گریڈ شدہ راستے پر لاگو ہونے میں ناکام ہوجاتی ہے، یعنی ہر بیس منتقلی کے بعد (چاہے یہ تازہ انسٹال پر بھی ناکام ہو یا نہ ہو)، گیٹ `migration do PR não aplica` رپورٹ کرتا ہے اور آپ سے SQL بیس کے موجودہ اسکیما کے خلاف ٹھیک کرنے کو کہتا ہے۔ اگر فائل بعد کے ٹائم اسٹیمپ کے ساتھ کسی اور پل کی درخواست کی منتقلی پر منحصر ہے، تو اس کا نام `npm run db:new-migration` کے ساتھ دوبارہ تخلیق کریں۔

اسی موازنہ کو مقامی طور پر چلانے کے لیے، بیس کو واضح طور پر پاس کریں، مثال کے طور پر `npm run check:migration-numbering -- --base origin/<base-branch>`، یا `npm run check:migration-numbering -- --base-latest-tag` تازہ ترین ریلیز کے ساتھ موازنہ کرنے کے لیے۔

### اوپن PR کی `NNN` ہجرت کو تبدیل کرنا

سوئچ سے پہلے کھولی گئی پل کی درخواست اب بھی ایک ترتیب وار فائل لے سکتی ہے جیسے `242_add_widgets.sql`۔ `241` کے اوپر کے پرانے نمبر مسترد کر دیے گئے ہیں، اس لیے ضم کرنے سے پہلے اسے تبدیل کر لیں:

1. **تفصیل کو مدنظر رکھتے ہوئے جنریٹر کے ساتھ فائل کا نام تبدیل کریں۔** نیا نام حاصل کرنے کے لیے `npm run db:new-migration -- <same description>` چلائیں، SQL کو اس میں منتقل کریں، اور پرانی `NNN_` فائل کو حذف کریں۔ تفصیل ایک جیسی ہونی چاہیے: ذیل میں مطابقت کا اندراج اس پر مماثل ہے۔
2. **اگر ایک مستقل ڈیٹا بیس پرانا نمبر چلاتا ہے تو مطابقت کا اندراج شامل کریں۔** اگر کوئی ڈیٹا بیس رکھا گیا ہے (homolog، a VPS، ایک تعاون کنندہ کا اپنا انسٹال) `NNN_` فائل کے ساتھ PR کی تعمیر چلاتا ہے، `src/lib/db/migrationRunner/constants.ts` میں `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` کو `RENAMED_MIGRATION_COMPATIBILITY` میں شامل کریں۔ یہ ہے** `237` سے `241` کے لیے درکار ہے۔** : وہ سلاٹ اب کینونیکل `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` اور `241_seen_models.sql` رکھتے ہیں اور بغیر اندراج کے اس طرح کا ڈیٹا بیس کینونیکل منتقلی کو ہمیشہ کے لیے چھوڑ دیتا ہے اور تبدیل شدہ کو دوبارہ چلاتا ہے۔ یہ اس سلاٹ کے لیے بھی کام کرتا ہے جو خالی رہتا ہے، جیسے `242`، جب منزل ٹائم اسٹیمپ ہو۔ جب شک ہو تو اندراج شامل کریں۔ جہاں آپ اسے صف میں شامل کرتے ہیں اس سے کوئی فرق نہیں پڑتا: جب کسی اندراج کے ہدف کی سلاٹ میں اب بھی ایک قطار ہوتی ہے جس سے کوئی اور اندراج چلا جاتا ہے (مثال کے طور پر `237` PR قطار کو پکڑ رکھا ہے جبکہ ایک پرانی `usage_history_calculated_cost` قطار `237` میں جانے کا انتظار کرتی ہے)، رنر اس اندراج کو اس وقت تک انتظار کرنے دیتا ہے جب تک کہ سلاٹ خالی نہ ہو۔ صرف ایک حقیقی تنازعہ، جیسے ایک سلاٹ جس میں ایک قطار میں کوئی اندراج نہیں چلتا، یا دو اندراج جو سلاٹ کو تبدیل کرتے ہیں، بوٹ کو `Cannot reconcile ...` کے ساتھ روکتا ہے۔
3. **SQL کمزور رکھیں** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`) کیونکہ تبدیل شدہ منتقلی ایک ایسے ڈیٹا بیس سے مل سکتی ہے جہاں اس کا سکیما پہلے سے موجود ہو۔
4. **منتقلی ورژن-کیڈ خصوصی مقدمات.** اگر PR اپنے پرانے نمبر کے لیے `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) یا `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) میں کیس شامل کیا ہے، تو کلید کو نئے ٹائم اسٹیمپ میں تبدیل کریں۔

`tests/unit/db/codex-fence-migration-rename.test.ts` تبدیل شدہ ہجرت کے لیے ٹیسٹ کی ایک عملی مثال ہے۔

### سوئچ کرنے سے پہلے شاخوں میں بیک پورٹ

`YYYYMMDDHHMMSS_` فائل کو کبھی بھی ایسی برانچ میں چیری پک یا بیک پورٹ نہ کریں جو سوئچ سے پہلے کی ہو (مثال کے طور پر پرانی `release/v*` برانچ)۔ وہاں کا رنر فائل کے ناموں کو متن کے طور پر ترتیب دیتا ہے، لہذا ایک ٹائم اسٹیمپ فائل ایک تازہ ڈیٹا بیس پر `201_` اور `202_` کے درمیان چلتی ہے، اور وہاں کا پرانا گیٹ 14 ہندسوں کے سابقے کو نہیں سمجھتا ہے۔ ایسی برانچ پر، تبدیلی کو اس برانچ کی اپنی اگلی `NNN_` فائل کے طور پر لکھیں، idempotent، اس لیے جب ٹائم اسٹیمپڈ ورژن بعد میں آتا ہے تو یہ کوئی نہیں ہے۔

### ہجرت کیسے چلتی ہے۔

آغاز پر، `migrationRunner.ts`:

1. اگر موجود نہ ہو تو `_omniroute_migrations` ٹیبل بناتا ہے۔
2. پہلے سے لاگو ہجرت کے لیے سوالات
3. کسی بھی نئی منتقلی کو ترتیب سے لاگو کرتا ہے، ہر ایک ٹرانزیکشن میں
4. ٹائم اسٹیمپ کے ساتھ لاگو کردہ ہر منتقلی کو ریکارڈ کرتا ہے۔

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### بے حسی

ہجرتیں ہونی چاہئیں** کمزور** — ان کو دو بار چلانا ایک نہیں ہونا چاہئے:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`، `IF EXISTS`، اور `OR IGNORE` / `OR REPLACE` شقوں کو آزادانہ طور پر استعمال کریں۔

### ایک نئی ہجرت شامل کرنا

1. **جنریٹر کے ساتھ فائل بنائیں** : `npm run db:new-migration -- <description>` (مثال کے طور پر `npm run db:new-migration -- add combo priority`)۔ یہ موجودہ UTC وقت اور ایک تبصرہ ہیڈر کے ساتھ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` لکھتا ہے، اگر ٹائم اسٹیمپ لیا جائے تو ایک سیکنڈ آگے بڑھتا ہے، اور کبھی بھی فائل کو اوور رائٹ نہیں کرتا ہے۔ ہاتھ سے نمبر نہ چنیں۔
2. **محفوظ DDL استعمال کریں۔** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **ڈیٹا کو احتیاط سے بیک فل کریں۔** : موجودہ قطاروں کو سنبھالنے کے لیے `UPDATE ... WHERE ...` استعمال کریں۔
4. **ترتیب اور نام کی جانچ کریں۔** : `npm run test:migrations:fresh` (خالی ڈیٹا بیس پر تمام منتقلی) اور `npm run check:migration-numbering`
5. **ایک کاپی پر ٹیسٹ کریں۔** : پیداوار پر کبھی بھی غیر تجربہ شدہ منتقلی نہ چلائیں۔

مثال:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **پیچھے کی طرف متضاد تبدیلیاں** (مثال کے طور پر، کالم چھوڑنا) مشکل ہیں۔ OmniRoute کیا NOT — ڈاؤن گریڈ کرنے کی حمایت کرتا ہے ایک بار منتقلی لاگو ہونے کے بعد، اسکیما کی تبدیلی مستقل ہوتی ہے۔ اس کے مطابق منصوبہ بندی کریں۔

## محفوظ شدہ ڈیٹا کی خفیہ کاری

حساس فیلڈز (API کیز، OAuth ٹوکنز، کنکشن اسٹرنگز) کو **AES-256-GCM** کے ذریعے محفوظ حالت میں خفیہ کیا جاتا ہے۔

### یہ کیسے کام کرتا ہے

```ts
// src/lib/db/encryption.ts (آسان کردہ)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### یہ کہاں استعمال ہوتا ہے

- `provider_connections.api_key` — ایپلیکیشن کی سطح پر خفیہ کردہ
- `provider_connections.access_token`، `refresh_token`، `id_token` — ایپلیکیشن کی سطح پر خفیہ کردہ
- `namespace = "secrets"` والی `key_value` انٹریز — ایپلیکیشن کی سطح پر خفیہ کردہ
- `proxy_registry.auth` — ایپلیکیشن کی سطح پر خفیہ کردہ (اگر موجود ہو)

### خفیہ کاری کی کلید

خفیہ کاری کی کلید ایک **پاس فریز** (`STORAGE_ENCRYPTION_KEY` env var کے ذریعے سیٹ کردہ) اور ایک **سالٹ** (DB میں محفوظ) سے اخذ کی جاتی ہے۔ ڈیٹا کو غیر خفیہ کرنے کے لیے دونوں درکار ہیں۔

```bash
# ایک محفوظ پاس فریز بنائیں
openssl rand -hex 32

# .env میں سیٹ کریں
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **انتہائی اہم**: خفیہ کاری کی کلید کھو دینے کا مطلب تمام خفیہ کردہ ڈیٹا تک رسائی کھو دینا ہے۔ **کلید کا بیک اپ ڈیٹابیس سے الگ رکھیں**۔

### کیا خفیہ نہیں کیا جاتا

کارکردگی کی وجوہات کی بنا پر، درج ذیل کو سادہ متن میں محفوظ کیا جاتا ہے:

- پرووائیڈر کے ڈسپلے نام
- ماڈل کی تعریفیں (پہلے ہی عوامی ہیں)
- راؤٹنگ کے قواعد
- استعمال کے ریکارڈز (کوئی PII نہیں)

- **Legacy** (v3.5.0 سے پہلے): XOR پر مبنی "انکرپشن" (حقیقی کرپٹوگرافی نہیں)
- **موجودہ**: مناسب IV اور auth tag کے ساتھ AES-256-GCM

مائیگریشن ہیلپر Legacy فارمیٹ کا پتہ لگاتا ہے اور پہلی بار پڑھنے پر نئے طریقے سے دوبارہ انکرپٹ کرتا ہے۔ اس کا مطلب ہے کہ آپ اسناد ضائع کیے بغیر پرانے ڈیٹابیس کو اپ گریڈ کر سکتے ہیں۔

## ریڈ کیش

کثرت سے پڑھے جانے والے ڈیٹا (ماڈلز، پرووائیڈرز، سیٹنگز) کے لیے، `readCache.ts` ایک **اِن میموری کیش** فراہم کرتا ہے:

```ts
// اسٹارٹ اپ پر کیش کیا جاتا ہے، لکھنے پر غیر مؤثر کر دیا جاتا ہے
const providers = await getCachedProviders(); // تیز، اِن میموری
const fresh = await listProviders(); // سست، DB تک رسائی کرتا ہے
```

| کیش شدہ اکائی          | کیش کلید       | TTL      |
| ---------------------- | -------------- | -------- |
| `models`               | `models:v1`    | لکھنے تک |
| `provider_connections` | `providers:v1` | لکھنے تک |
| `settings`             | `settings:v1`  | لکھنے تک |
| `combos`               | `combos:v1`    | لکھنے تک |

متعلقہ ٹیبل میں ہر بار لکھنے پر کیش غیر مؤثر کر دیا جاتا ہے۔

## بیک اپ اور بحالی

### دستی بیک اپ

```bash
# مقامی بیک اپ بنانے کے لیے CLI استعمال کریں
omniroute backup create --name pre-migration

# یا API کے ذریعے
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

بیک اپ فائل میں یہ شامل ہوتا ہے:

- تمام DB ٹیبلز (JSON میں سیریلائز کیے گئے)
- کال لاگ آرٹیفیکٹس (base64-encoded، اختیاری)
- سیٹنگز + راز (انکرپٹ شدہ)
- پلگ اِن کنفیگریشن

### بحالی

```bash
# CLI کے ذریعے
omniroute restore pre-migration

# API کے ذریعے
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **انتباہ**: بحالی پورے DB کو اوور رائٹ کر دیتی ہے۔ پہلے تمام کلائنٹس کو روکیں۔

### خودکار بیک اپس

```bash
# CLI کے ذریعے خودکار یومیہ بیک اپس فعال کریں
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

شیڈول سرور کی جانب سے ایک بیک گراؤنڈ جاب کے ذریعے چلایا جاتا ہے جو ہر 30 سیکنڈ
(ڈیفالٹ) بعد فعال ہوتی ہے اور مقامی سرور وقت کے مطابق cron ایکسپریشن کا جائزہ لیتی ہے۔

| متغیر                                       | ڈیفالٹ  | وضاحت                                                                                                                          |
| ------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000` | ملی سیکنڈز میں ٹِک وقفہ (کم از کم `5000`)۔ مماثل cron منٹ کے اندر قابلِ اعتماد طور پر آنے کے لیے 60 سیکنڈ سے کم ہونا ضروری ہے۔ |

### SQLite ہاٹ بیک اپ

چلتے ہوئے DB کا زیرو ڈاؤن ٹائم بیک اپ بنانے کے لیے:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

یہ SQLite کا آن لائن بیک اپ API استعمال کرتا ہے — OmniRoute کے چلتے ہوئے اسے چلانا محفوظ ہے۔

## پرفارمنس ٹیوننگ

### WAL موڈ

WAL بطور ڈیفالٹ فعال ہے۔ زیادہ تحریری کام کے بوجھ کے لیے، غور کریں:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` سیٹ نہیں کرتا ہے۔ ایک چیک پوائنٹ WAL فریموں کو مین فائل میں منتقل کرتا ہے، لیکن WAL فائل اپنا سب سے بڑا مختص سائز رکھتی ہے۔ `OMNIROUTE_WAL_GUARD_MAX_MB` گارڈ صرف خبردار کرتا ہے اور `wal_checkpoint(RESTART)` چلاتا ہے۔ یہ ڈسک کے سائز کی ٹوپی نہیں ہے۔

### اشاریہ جات

کارکردگی کے لیے کلیدی اشاریہ جات (ہجرت کے ذریعے خود بخود تخلیق کردہ):

- فراہم کنندہ کے ذریعہ `idx_models_provider` — ماڈل کی تلاش
- `idx_combo_targets_combo_id` — کومبو ہدف کی توسیع
- `idx_usage_history_api_key_timestamp` — استعمال کے تجزیات
- `idx_quota_snapshots_api_key_window` — کوٹہ سے باخبر رہنا
- `idx_call_logs_timestamp` — کال لاگ کے سوالات

ایک نیا انڈیکس شامل کرنے کے لیے، ایک منتقلی بنائیں:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### میموری میپڈ I/O

بہت بڑے ڈیٹا بیس (> 10GB) کے لیے، میموری میپنگ کو SQLite پراگما کے ذریعے ایڈجسٹ کیا جا سکتا ہے:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### کومپیکشن

طویل عرصے سے چلنے والی OmniRoute مثالیں کبھی کبھار `VACUUM` سے فائدہ اٹھاتی ہیں:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

کم ٹریفک والی ونڈوز کے دوران ماہانہ چلائیں۔ (WAL موڈ ضرورت کو کم کرتا ہے، لیکن اسے ختم نہیں کرتا ہے۔)

## صحت کی جانچ

`src/lib/db/healthCheck.ts` **ڈیٹابیس کی سطح پر صحت کی تشخیص** فراہم کرتا ہے:

دونوں verbs کے لیے توثیق درکار ہے (بصورت دیگر `401`)۔ `GET` صرف تشخیص کرتا ہے؛ `POST` یہی جانچ `autoRepair` فعال کر کے چلاتا ہے۔

```bash
GET  /api/db/health   # تشخیص
POST /api/db/health   # تشخیص + مرمت
```

رسپانس `runDbHealthCheck()` کے ذریعے تیار کردہ `DbHealthCheckResult` ہے
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "ڈومین بجٹس نے ایسی API کیز کا حوالہ دیا جو اب موجود نہیں ہیں۔",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| فیلڈ              | مطلب                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | جب `issues` خالی ہو تو `true` ہوتا ہے۔ `driver` کبھی اس پر اثر انداز نہیں ہوتا۔                                                                         |
| `issues[].type`   | `integrity_check_failed`، `broken_reference`، `stale_snapshot`، `invalid_state` میں سے ایک۔                                                             |
| `repairedCount`   | اس رن کے دوران مرمت کی گئی قطاریں؛ جب `autoRepair` false ہو تو ہمیشہ `0`۔                                                                               |
| `backupCreated`   | آیا مرمت سے پہلے بیک اپ لیا گیا تھا۔                                                                                                                    |
| `checkedAt`       | رن اور اس کے ذریعے لکھی جانے والی کسی بھی مرمتی یادداشت کے لیے مشترکہ ISO ٹائم اسٹیمپ۔                                                                  |
| `driver.name`     | جانچے گئے ڈیٹابیس کو سروس فراہم کرنے والا SQLite ڈرائیور۔                                                                                               |
| `driver.degraded` | جب تحریریں ڈیٹابیس فائل کے ذریعے پائیدار طور پر محفوظ نہ ہوں تو `true` — `sql.js` WASM فال بیک (مکمل فائل کی پائیدار ذخیرہ کاری) یا اِن میموری ڈیٹابیس۔ |

یہی پے لوڈ `omniroute_db_health_check` MCP ٹول کے ذریعے بھی واپس کیا جاتا ہے۔

خرابی کا پتہ لگانے کے لیے `PRAGMA integrity_check` چلائیں:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# اسے یہ پرنٹ کرنا چاہیے: ok
```

اگر یہ `ok` کے علاوہ کچھ بھی واپس کرے تو **فوری طور پر ڈیٹابیس کا استعمال روک دیں** اور بیک اپ سے بحال کریں۔

## ڈیزاسٹر ریکوری

### منظرنامہ 1: WAL فائل ضائع ہو گئی

`-wal` فائل موجود نہیں ہے، لیکن `-shm` اور مرکزی DB صحیح حالت میں ہیں:

```bash
# اگلی بار کھولنے پر خودکار طور پر بحال ہو جاتا ہے
omniroute
```

اگر SQLite خودکار طور پر بحال نہ کر سکے:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### منظرنامہ 2: مرکزی DB فائل خراب ہو گئی

بیک اپ سے بحال کریں:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` صرف چلتے ہوئے سرور سے مکمل `.tar.gz` آرکائیو ڈاؤن لوڈ کرتا ہے
(`GET /api/db-backups/exportAll`، آپریٹر کی اسناد درکار ہیں)؛ یہ کسی چیز کو بحال نہیں کرتا۔

### منظرنامہ 3: انکرپشن کلید ضائع ہو گئی

کلید کے بغیر **بحالی ممکن نہیں ہے**۔ انکرپٹ شدہ فیلڈز ناقابلِ مطالعہ ہیں۔ نئی اسناد کے ساتھ تمام پرووائیڈرز کو دستی طور پر دوبارہ شامل کریں۔

> **تدارک**: انکرپشن کلید کا بیک اپ ہمیشہ الگ سے رکھیں، مثالی طور پر کسی پاس ورڈ مینیجر یا KMS میں۔

### منظرنامہ 4: ڈسک بھر گئی

SQLite، `SQLITE_FULL` نقائص واپس کرے گا۔ ڈسک کی جگہ خالی کریں، پھر:

```bash
# جگہ خالی کرنے کے لیے WAL کا چیک پوائنٹ بنائیں
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## عام کارروائیاں

### ٹیبل کا معائنہ کریں

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### تمام ٹیبلز میں قطاریں شمار کریں

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### تمام ڈیٹا ری سیٹ (صاف) کریں

```bash
# پہلے OmniRoute کو روکیں
omniroute stop

# DB فائل حذف کریں
rm ~/.omniroute/storage.sqlite*

# دوبارہ شروع کریں (خالی DB دوبارہ تخلیق ہو جائے گا)
omniroute
```

**منتخب** ری سیٹ کے لیے (پرووائیڈرز برقرار رکھیں، استعمال کا ڈیٹا صاف کریں):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### ایک ٹیبل ایکسپورٹ کریں

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## خرابیوں کا ازالہ

### "ڈیٹابیس مقفل ہے"

کوئی دوسرا پراسیس رائٹ لاک برقرار رکھے ہوئے ہے۔ درج ذیل میں سے کوئی ایک طریقہ اختیار کریں:

- دوسرے پراسیس کے مکمل ہونے کا انتظار کریں (`lsof | grep storage.sqlite` سے جانچیں)
- دوسرے پراسیس کو ختم کریں
- اگر مسئلہ برقرار رہے تو OmniRoute کو دوبارہ شروع کریں

### "فارِن کلید کی پابندی ناکام ہو گئی"

کوئی ڈومین ماڈیول حوالہ جاتی سالمیت کی خلاف ورزی کر رہا ہے۔ درج ذیل کی جانچ کریں:

- منحصر ٹیبلز میں یتیم قطاریں
- سلسلہ وار حذف جو آگے منتقل نہیں ہوئے
- حالیہ مائیگریشن جس نے فارِن کلید تبدیل کی ہو

خلاف ورزیاں تلاش کرنے کے لیے `PRAGMA foreign_key_check;` چلائیں۔

### "میموری ختم ہو گئی"

SQLite کا میموری میپڈ I/O، OS کی حد سے تجاوز کر رہا ہے۔ SQLite pragma کے ذریعے اسے کم کریں:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB کی بجائے 128MB
```

یا غیر فعال کریں:

```sql
PRAGMA mmap_size = 0;
```

### "مائیگریشن درمیان میں ناکام ہو گئی"

مائیگریشن ایک ٹرانزیکشن میں چلی تھی، اس لیے اسے رول بیک ہو جانا چاہیے تھا۔ اگر ایسا نہ ہوا ہو:

1. **OmniRoute کو روکیں** (مزید کوششوں کو روکنے کے لیے)
2. `sqlite3` کے ذریعے **DB کی حالت جانچیں**
3. جزوی مائیگریشن کو **دستی طور پر درست کریں**
4. OmniRoute کو **دوبارہ چلائیں** (مائیگریشن کی دوبارہ کوشش کی جائے گی)

اس سے بچنے کے لیے، مائیگریشنز کو ہمیشہ پہلے کسی نقل پر آزمائیں۔
