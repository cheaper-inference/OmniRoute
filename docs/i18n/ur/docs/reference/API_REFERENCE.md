OpenAI سے مطابقت رکھنے والے مخصوص پروٹوکول اور فراہم کنندہ کی صلاحیتوں کی میٹرکس کے لیے
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md) دیکھیں۔

ہر تعیناتی `/openapi.yaml` پر اپنی اسپیک کی نقل فراہم کرتی ہے، جو بلڈ کے دوران `docs/openapi.yaml` سے تیار کی جاتی ہے۔ اس میں بلڈ کا ورژن اور متعلقہ سرور URL (`./`) شامل ہوتا ہے، تاکہ درخواستیں اسی میزبان پر بھیجی جائیں جس نے دستاویز فراہم کی ہو۔ ڈاؤن لوڈ کی گئی فائل درآمد کرنے والے ٹول کے پاس ایسا کوئی میزبان نہیں ہوتا، اس لیے بنیادی URL دستی طور پر مقرر کرنا ضروری ہے۔

## چیٹ تکمیلات

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### کسٹم ہیڈرز

| Header                   | Direction | Description                                                                                                                                                                                                                           |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | درخواست   | کیش کو نظرانداز کرنے کے لیے `true` پر سیٹ کریں                                                                                                                                                                                        |
| `x-omniroute-no-memory`  | درخواست   | اس درخواست کے لیے میموری + اسکلز انجیکشن کو چھوڑنے کے لیے `true` پر سیٹ کریں (no-cache کی عکاسی کرتا ہے؛ فی کال ٹوکن/لاگت کے اضافی بوجھ سے بچاتا ہے)                                                                                  |
| `X-OmniRoute-Progress`   | درخواست   | پیش رفت کے ایونٹس کے لیے `true` پر سیٹ کریں                                                                                                                                                                                           |
| `X-Session-Id`           | درخواست   | بیرونی سیشن وابستگی کے لیے مستقل سیشن کلید                                                                                                                                                                                            |
| `x_session_id`           | درخواست   | انڈر اسکور والا متبادل بھی قبول کیا جاتا ہے (براہِ راست HTTP)                                                                                                                                                                         |
| `X-OmniRoute-Session-Id` | درخواست   | کال کرنے والے کی فراہم کردہ سیشن/گفتگو ٹیگ (میموری میں بھی شامل ہوتا ہے)۔ موجود ہونے پر اسے `call_logs.session_tag` میں فی سیشن لاگت کی نسبت کے لیے لفظ بہ لفظ محفوظ کیا جاتا ہے (#8249) — غیر موجود ہونے پر کبھی تخلیق نہیں کیا جاتا |
| `Idempotency-Key`        | درخواست   | ڈپلی کیشن کلید (5s ونڈو)                                                                                                                                                                                                              |
| `X-Request-Id`           | درخواست   | متبادل ڈپلی کیشن کلید                                                                                                                                                                                                                 |
| `x-omniroute-connection` | درخواست   | ایک ماڈل والی درخواست کو ایک فراہم کنندہ کنکشن (اکاؤنٹ) سے اس کی آئی ڈی کے ذریعے منسلک کریں — [فی درخواست اکاؤنٹ پن کرنا](#account-pinning-per-request) دیکھیں                                                                        |
| `X-OmniRoute-Cache`      | جواب      | `HIT` یا `MISS` (نان اسٹریمنگ)                                                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | جواب      | ڈپلی کیشن ہونے کی صورت میں `true`                                                                                                                                                                                                     |
| `X-OmniRoute-Progress`   | جواب      | پیش رفت کی ٹریکنگ فعال ہونے کی صورت میں `enabled`                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | جواب      | OmniRoute کے ذریعے استعمال کی گئی مؤثر سیشن آئی ڈی                                                                                                                                                                                    |
| `X-OmniRoute-Request-Id` | جواب      | درخواست کا ارتباطی آئی ڈی (جب معلوم ہو)                                                                                                                                                                                               |
| `X-OmniRoute-Version`    | جواب      | OmniRoute بلڈ ورژن (ہمیشہ موجود)                                                                                                                                                                                                      |
| `X-OmniRoute-Cost-Saved` | جواب      | `HIT` پر کیش کے ذریعے بچائی گئی امریکی ڈالر کی رقم (صرف کیش ہٹس)                                                                                                                                                                      |
| `X-OmniRoute-Decision`   | جواب      | روٹنگ ٹریس: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` کومبو اسٹریٹجی ہے، یا نان کومبو درخواست کے لیے `single`) — تکمیل کے جوابات پر ہمیشہ موجود ہوتا ہے                                                           |

> Nginx نوٹ: اگر آپ انڈر اسکور والے ہیڈرز (مثلاً `x_session_id`) پر انحصار کرتے ہیں تو `underscores_in_headers on;` فعال کریں۔

#### فی درخواست اکاؤنٹ پن کرنا

جب کسی فراہم کنندہ کے پاس متعدد کنکشن (اکاؤنٹس یا کیز) ہوں، تو OmniRoute عموماً اپنی اکاؤنٹ-انتخاب اسٹریٹجی کے ذریعے ایک کا انتخاب کرتا ہے۔ درخواست اس کے بجائے `x-omniroute-connection` ہیڈر کے ذریعے ایک مخصوص کنکشن کو پن کر سکتی ہے:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **آئی ڈی کہاں تلاش کریں۔** ڈیش بورڈ میں فراہم کنندہ کا صفحہ کھولیں
  (**Dashboard → Providers → <provider>**) اور کنکشن کی قطار میں موجود `xxxxxxxx…` آئی ڈی چِپ پر کلک کریں — اس سے مکمل کنکشن آئی ڈی کاپی ہو جاتی ہے۔
- **کون سی درخواستیں اسے تسلیم کرتی ہیں۔** `/v1/chat/completions`، `/v1/messages` اور `/v1/responses` پر سنگل ماڈل درخواستیں (`provider/model`)۔ کومبو درخواستیں اس ہیڈر کو نظرانداز کرتی ہیں: ہر کومبو مرحلے کے لیے اس کے اپنے کنکشن کے ذریعے اکاؤنٹ پن کریں۔
- **پن سختی سے نافذ ہوتا ہے، یہ محض ترجیح نہیں۔** پن کیا گیا کنکشن خصوصی طور پر استعمال ہوتا ہے۔ درخواست کے اندر ناکامی اکاؤنٹ کے کول ڈاؤن کو ریکارڈ کرتی ہے، لیکن اسی فراہم کنندہ کے کسی ہم مرتبہ اکاؤنٹ پر منتقل نہیں ہوتی۔
- **کول ڈاؤن اور کوٹا پن ختم کر دیتے ہیں۔** جب پن کیا گیا کنکشن کول ڈاؤن میں ہو، کوٹا ختم ہو چکا ہو یا کوٹا پالیسی کی وجہ سے مسدود ہو، تو بعد کی درخواستیں فراہم کنندہ کے دوسرے کنکشنز پر واپس چلی جاتی ہیں، بالکل غیر پن شدہ ٹریفک کی طرح۔
- **نامعلوم یا غیر فعال آئی ڈیز ناکام ہو جاتی ہیں۔** ایسی آئی ڈی جو فراہم کنندہ کے فعال پول میں موجود نہ ہو (حذف شدہ، غیر فعال، یا کسی دوسرے فراہم کنندہ سے متعلق) کوئی اہل اکاؤنٹ باقی نہیں چھوڑتی، اس لیے درخواست خاموشی سے کہیں اور بھیجے جانے کے بجائے ناکام ہو جاتی ہے۔

Claude Code حسبِ ضرورت ہیڈرز `ANTHROPIC_CUSTOM_HEADERS` کے ذریعے بھیجتا ہے۔ اسے `~/.claude/settings.json` کے `env` بلاک میں رکھیں، یا ہر پروجیکٹ کے لیے مختلف اکاؤنٹ پن کرنے کی خاطر پروجیکٹ کی سطح کی `.claude/settings.json` فائل میں رکھیں:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ماخذ: `src/sse/handlers/chat.ts` (ہیڈر پڑھنا)، `src/sse/services/auth.ts` اور
`src/sse/services/sessionAffinityPin.ts` (پن کا اجراء اور پول سے غائب ہونے کی جانچ)۔

> **لاگت سے متعلق ٹیلی میٹری ہیڈرز:** نان اسٹریمِنگ کامیابی کے جوابات میں `X-OmniRoute-*` لاگت سے متعلق ٹیلی میٹری سیٹ بھی شامل ہوتا ہے — `X-OmniRoute-Response-Cost` (امریکی ڈالر، مقررہ 10 اعشاریے؛ مفت/غیر قیمت شدہ کے لیے `0.0000000000`)، `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`، `X-OmniRoute-Model`، `X-OmniRoute-Provider`، `X-OmniRoute-Latency-Ms`، `X-OmniRoute-Cache-Hit`، اور `X-OmniRoute-Fallback-Attempts` (صرف اس وقت جب یہ `0` سے زیادہ ہو)، نیز `X-OmniRoute-Request-Id` اور `X-OmniRoute-Version`۔ یہ چیٹ کمپلیشنز، `/v1/responses`، `/v1/messages`، **اور میڈیا اینڈ پوائنٹس** — `/v1/embeddings`، `/v1/images/generations`، `/v1/audio/speech`، `/v1/audio/transcriptions`، `/v1/rerank`، `/v1/videos/generations`، `/v1/music/generations`، اور `/v1/moderations` — سے جاری ہوتے ہیں (لاگت ہمیشہ `0`)۔ میڈیا کی لاگت ہر موڈیلٹی کے لحاظ سے (فی تصویر، فی سیکنڈ، فی کریکٹر، فی سرچ یونٹ) اس وقت شمار کی جاتی ہے جب قیمت مقرر ہو؛ بصورتِ دیگر یہ `0` ہوتی ہے (فیل اوپن)۔

> **کیش ہٹ کی لاگت کا مفہوم:** سیمینٹک کیش کے HIT (`X-OmniRoute-Cache-Hit: true`) پر کوئی اپ اسٹریم کال نہیں کی جاتی، اس لیے `X-OmniRoute-Response-Cost` `0.0000000000` ہوتی ہے (ہٹ فراہم کرنے کی **اضافی** لاگت)۔ اصل/متوقع لاگت الگ سے `X-OmniRoute-Cost-Saved` میں رپورٹ کی جاتی ہے۔ بلنگ کے صارفین کو `X-OmniRoute-Response-Cost` کا مجموعہ لینا چاہیے (ہٹس کی کوئی لاگت نہیں ہوتی)؛ کیش اینالیٹکس `X-OmniRoute-Cost-Saved` کو مجموعی طور پر اکٹھا کر سکتی ہے۔

## خصوصی منظم سیشن لیزز

خصوصی منظم سیشن لیزنگ ایک اختیاری، کلائنٹ سے غیر جانب دار روٹنگ معاہدہ ہے: ایک فعال مالک ایک اہل
OmniRoute کنکشن رکھتا ہے۔ یہ کسی ماڈل کو لیز پر نہیں دیتا، OAuth درکار نہیں کرتا، کسی مخصوص
کلائنٹ کی شناخت نہیں کرتا، اور نہ ہی کسی مخصوص فراہم کنندہ کا تقاضا کرتا ہے۔

تصدیقی API کلید کے دائرۂ کار میں `lease:exclusive` شامل ہونا چاہیے اور ایک واضح، غیر خالی
`allowedConnections` فہرست موجود ہونی چاہیے۔ ڈیٹابیس کی تبدیلی کی حد کلید بناتے اور جزوی اپ ڈیٹس
کرتے وقت دونوں فیلڈز کو ایک ساتھ نافذ کرتی ہے۔

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

کامیاب acquire، renew، اور release جوابات ٹائم اسٹیمپس، `state`، اور عین مثبت
`generation` ظاہر کرتے ہیں، لیکن منتخب کنکشن یا اسناد کبھی ظاہر نہیں کرتے۔ Renew اور release
JSON باڈی میں generation فراہم کرتے ہیں:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

ایک فعال لیز مالک اپنی موجودہ بائنڈنگ کے لیے رازداری سے محفوظ ڈسپلے میٹا ڈیٹا واضح طور پر طلب کر سکتا ہے:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

یہ اختیاری status ایکشن ایک ہی ڈیٹابیس ٹرانزیکشن میں غیر شفاف مالک، تصدیق شدہ منظم API کلید، اور
عین فعال generation کے ذریعے محفوظ کیا جاتا ہے۔ `displayName` صرف ترتیب دیے گئے کنکشن کا تراشا ہوا
نام ہوتا ہے؛ جب کوئی محفوظ ترتیب شدہ نام موجود نہ ہو تو یہ `null` ہوتا ہے۔ OmniRoute کبھی بھی
ای میل یا تیار کردہ اکاؤنٹ شناخت کو متبادل کے طور پر استعمال نہیں کرتا۔ provider کی قدر غیر حساس
ڈسپلے لیبل ہوتی ہے اور کبھی بھی تیار کردہ compatible-provider شناخت کنندہ نہیں ہوتی۔ اسناد، ٹوکنز،
کوکیز، خام کنکشن یا API کلید کی IDs، مالک کے ہیشز، fencing secrets، اور اندرونی روٹنگ ڈیٹا خارج کر دیے جاتے ہیں۔

غلط کلید، غلط مالک، فرسودہ generation، غیر موجود، میعاد ختم شدہ، جاری کردہ، اور باطل شدہ lookups سب
ایک ہی `409 LEASE_FENCE_STALE` خرابی واپس کرتے ہیں، کنکشن میٹا ڈیٹا کے بغیر۔ جس کلائنٹ کو capacity-wait
جواب موصول ہوا ہو، اس کے معائنے کے لیے کوئی فعال بائنڈنگ موجود نہیں ہوتی۔ جب روٹنگ کسی فعال لیز کو
منتقل کرتی ہے تو وہی generation درست رہتا ہے اور status نئی بائنڈنگ کو ایٹمی طور پر واپس کرتا ہے،
پرانے کو کبھی نہیں۔ موجودہ کلائنٹس میں کوئی تبدیلی نہیں آتی کیونکہ acquire، renew، release، اور
waiting جوابات اپنی سابقہ شکلیں برقرار رکھتے ہیں۔

یہ سرور معاہدہ اسٹاک OpenAI Codex `/status` کو تبدیل نہیں کرتا۔ اسٹاک Codex فی الحال اپنے
ماڈل فراہم کنندہ اور اندرونی تصدیق/اکاؤنٹ کی حالت رپورٹ کرتا ہے، لیکن من مانے حسبِ ضرورت
فراہم کنندہ کے اکاؤنٹ میٹا ڈیٹا کو پیش نہیں کرتا؛ بعد کی کلائنٹ انٹیگریشن کو اس ایکشن کو کال کرنا
اور یہ طے کرنا ہوگا کہ `connection.displayName` کو کیسے دکھایا جائے۔

اس کے بعد ہر منظم inference درخواست دونوں کنٹرول ہیڈرز فراہم کرتی ہے:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ہر معاون upstream کوشش سے فوراً پہلے عین مالک، generation، فعال کنکشن، اور تصدیق شدہ API کلید کی
fencing کی جاتی ہے۔ مالک اور generation کو کسی دوسری کلید کے ساتھ دوبارہ استعمال کرنا ناکام ہو جاتا
ہے، حتیٰ کہ جب وہ کلید اسی کنکشن کی اجازت دیتی ہو۔ خام مالکان کو محفوظ، لاگ، برقرار، request snapshot
میں شامل، یا upstream کو فارورڈ نہیں کیا جاتا۔

عارضی مسابقت HTTP `429` کو `Retry-After` اور اس کے ساتھ واپس کرتی ہے:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

اس جواب کا صرف یہ مطلب ہے کہ عام اہل سیٹ غیر خالی تھا اور ہر آزاد امیدوار کسی غیر متعلقہ فعال لیز
کے پاس تھا۔ غیر معاون ماڈلز/فراہم کنندگان، پالیسی عدم مطابقت، cooldown، quota، health، اور اہلیت
کی دیگر عام ناکامیاں اپنے موجودہ OmniRoute جوابات برقرار رکھتی ہیں۔

### `x-omniroute-compression`

ہر درخواست کے لیے compression plan کو override کرتا ہے۔ سب سے زیادہ ترجیح — routing-combo
override، فعال پروفائل، auto-trigger، اور panel Default سب پر غالب:

| Value         | Effect                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------- |
| `off`         | اس درخواست کے لیے کوئی compression نہیں۔                                                          |
| `default`     | پینل سے اخذ کردہ Default پروفائل (فعال پروفائل کو نظر انداز کرتا ہے)۔ Lossy engines بند رہتے ہیں۔ |
| `safe`        | صرف Dedup اور whitespace folding۔                                                                 |
| `allow-lossy` | اس درخواست کے لیے operator plan برقرار رکھتا ہے، بشمول summaries اور style rewrites۔              |
| `engine:<id>` | فعال ہونے پر ایک واحد engine، مثلاً `engine:rtk`۔ اس engine کے لیے فی درخواست opt-in۔             |
| `<combo>`     | نام سے مماثل ایک نام زدہ combo، پہلے نام (case-insensitive) سے، پھر id سے۔                        |

نوٹس:

- نامعلوم قدروں کو نظر انداز کیا جاتا ہے (درخواست کبھی مسترد نہیں کی جاتی)؛ resolution معمول کی operator precedence کے مطابق جاری رہتی ہے۔
- اگر متعدد combos کا نام ایک جیسا ہو تو deterministic match کے لیے combo **id** بھیجیں۔
- جس combo کا نام `off` یا `default` ہو، اسے نام کے ذریعے منتخب نہیں کیا جا سکتا (ان keywords کی پہلے تشریح کی جاتی ہے)؛ ایسے combo کو اس کی id کے ذریعے reference کریں۔
- master compression switch ایک سخت gate ہے: جب compression عالمی طور پر غیر فعال ہو تو یہ header اسے فعال نہیں کر سکتا۔

نافذ شدہ plan جواب کے header میں واپس echo کیا جاتا ہے:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

جہاں `<source>` ان میں سے ایک ہوگا: `request-header`، `routing-override`، `active-profile`، `auto-trigger`، `default`، یا `off`۔

## ایمبیڈنگز

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

دستیاب فراہم کنندگان: Nebius، OpenAI، Mistral، Together AI، Fireworks، NVIDIA، **OpenRouter**، Jina AI۔

کیٹلاگ آئی ڈیز `provider/model` کی شکل میں ہوتی ہیں (مثال: `jina-ai/jina-embeddings-v5-omni-small`)۔ رجسٹری میں موجود Jina کے غیر مختص ماڈل آئی ڈیز (مثلاً `jina-embeddings-v5-text-small`، `jina-reranker-v3.5`) بھی حل ہو جاتی ہیں۔ Jina کے embed/rerank/classify/segment ماڈلز پہلے ڈیش بورڈ کی `jina-ai` اسناد استعمال کرتے ہیں؛ `JINA_AI_API_KEY` صرف اس وقت متبادل کے طور پر استعمال ہوتا ہے جب ڈیش بورڈ کی کوئی کلید موجود نہ ہو۔ `jina-reader` کارڈ صرف Reader / `r.jina.ai` کے لیے ہے (`POST /v1/web/fetch`) اور ایمبیڈنگز یا rerank فراہم نہیں کرتا۔

رجسٹری کے وہ ماڈلز جو کثیر الوسائط معاونت ظاہر کرتے ہیں، زیادہ سے زیادہ 32 فراہم کنندہ-غیر جانب دار ساخت یافتہ
آئٹمز بھی قبول کرتے ہیں۔ میڈیا آئٹم کی اقسام `text`، `image`، `audio`، `video`، اور `document` ہیں۔ ان کے میڈیا `source`
کی شکل یا تو `{"type":"url","url":"https://..."}` ہوتی ہے یا
`{"type":"base64","data":"...","media_type":"..."}`۔

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`، `jina-ai/jina-embeddings-v5-omni-nano`،
اور فیملی عرف `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina کے مقامی
EmbeddingsV5Request دستاویزات بھی قبول کرتا ہے اور انہیں جوں کا توں
`https://api.jina.ai/v1/embeddings` کو فارورڈ کرتا ہے:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

مقامی `{ image | audio | video | pdf }` قدریں عوامی HTTPS URL، `data:` URI، یا خام
base64 ہو سکتی ہیں۔ OmniRoute ان آبجیکٹس کو string میں تبدیل نہیں کرتا اور مقامی image URLs کو fetch نہیں کرتا — Jina
خود عوامی میڈیا حاصل کرتا ہے۔ اضافی Jina فیلڈز (`task`، `normalized`، `truncate`، `embedding_type`) بھی
فارورڈ کی جاتی ہیں۔ صرف متن والے Jina SKUs غیر متنی دستاویزات اب بھی مسترد کرتے ہیں۔

سیکیورٹی اور ٹرانسپورٹ کی حدود:

- ریموٹ میڈیا URLs عوامی HTTPS ہونے چاہییں۔ معیاری `{type,source:url}` آئٹمز سرور کی جانب سے fetch کیے جاتے ہیں
  (ری ڈائریکٹ کی دوبارہ توثیق، ٹائم آؤٹ، سائز کی حدود، عوامی DNS، کنکشن پننگ) اور فراہم کنندہ کو کال کرنے سے پہلے
  inline کیے جاتے ہیں۔ Jina-native `{image:"https://..."}` آئٹمز اسی public-HTTPS جانچ کے بعد جوں کے توں فارورڈ کیے جاتے ہیں؛ Jina
  URL کو fetch کرتا ہے۔
- Inline base64 میڈیا فی آئٹم 8 MiB decoded اور پوری درخواست میں 16 MiB decoded تک محدود ہے۔

فراہم کنندہ کے لیے ترجمہ (معیاری آئٹمز کبھی بھی بغیر تبدیلی کے فارورڈ نہیں کیے جاتے):

- Jina کے کثیر الوسائط ماڈلز: ہر اعلیٰ سطحی آئٹم ایک modality-keyed آبجیکٹ
  (`text` / `image` / `audio` / `video` / `pdf`) بن جاتا ہے، جس میں inline میڈیا کے لیے data URIs استعمال ہوتی ہیں؛ ہر
  اعلیٰ سطحی آئٹم کے لیے ایک ویکٹر۔
- Gemini Embedding 2 فیملی: ایک اعلیٰ سطحی array ایک واحد مقامی
  `models/{model}:embedContent` درخواست بن جاتی ہے، جس میں `content.parts` (`text` یا `inline_data`) شامل ہوتے ہیں۔
- llama.cpp (`llama-cpp/<model>`، یعنی کوئی بھی ماڈل جسے مقامی سرور نے لوڈ کیا ہو): معیاری `text` آئٹمز
  سادہ strings بن جاتی ہیں، جبکہ `image` / `audio` / `video` ہر ایک الگ
  `{"content": [part]}` آبجیکٹ بن جاتا ہے، جس میں llama-server کے chat content parts (`image_url`،
  `input_audio` بمعہ format `wav` / `mp3` / `flac`، `input_video`) اور inline data استعمال ہوتے ہیں؛ ہر اعلیٰ سطحی آئٹم کے لیے ایک ویکٹر۔ `document` معاونت یافتہ نہیں ہے۔
  سرور کو `--embedding --mmproj …` کے ساتھ چلنا چاہیے؛ projector کے بغیر یہ خود میڈیا مسترد کر دیتا ہے۔
- نامعلوم/متحرک ماڈلز جن کے پاس واضح modality metadata نہ ہو، ساخت یافتہ input کو HTTP 400 کے ساتھ مسترد کرتے ہیں۔

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

غیر معاونت یافتہ model/modality امتزاج آئٹم کو زبردستی تبدیل کرنے کے بجائے HTTP 400 واپس کرتے ہیں۔ پرانی string/token درخواستوں میں موجود non-input extension فیلڈز بدستور بغیر تبدیلی کے آگے منتقل ہوتے رہتے ہیں۔

```bash
# تمام ایمبیڈنگ ماڈلز کی فہرست
GET /v1/embeddings
```

## تصویر سازی

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

دستیاب providers میں OpenAI (GPT Image 2)، xAI (Grok Image)، Together AI (FLUX)، Fireworks AI، Nebius (FLUX)، Hyperbolic، NanoBanana، **OpenRouter**، **ZenMux**، SD WebUI (local)، اور ComfyUI (local) شامل ہیں۔

`n`، `data[]` میں `n` تصاویر واپس کرتا ہے۔ جن providers کی upstream API ہر call کے لیے ایک تصویر واپس کرتی ہے
(Black Forest Labs، Stability AI، Leonardo، Ideogram، Haiper، Hyperbolic، Magnific/Freepik،
NVIDIA NIM، Cloudflare Workers AI)، ان کے لیے `n` الگ upstream calls کی جاتی ہیں، جن میں بیک وقت زیادہ سے زیادہ 4 calls چلتی ہیں۔ ایک
مقررہ `seed` کو call index کے ذریعے offset کیا جاتا ہے (`seed`، `seed + 1`، …)، اس طرح تصاویر مختلف ہوتی ہیں لیکن
قابلِ اعادہ رہتی ہیں۔ `n` کی زیادہ سے زیادہ قدر 10 ہے۔ اگر کوئی بھی call ناکام ہو جائے تو پوری request ناکام ہو جاتی ہے۔ fan-out formats کی فہرست
`open-sse/handlers/imageGeneration/fanOut.ts` میں `SINGLE_IMAGE_FANOUT_FORMATS` ہے۔

ZenMux موجودہ API-key connection کو دوبارہ استعمال کرتا ہے اور `zenmux/` یا `zm/` prefixes قبول کرتا ہے:

- `zenmux/openai/gpt-image-2`، ZenMux کی OpenAI Images API استعمال کرتا ہے۔ Options میں `size`،
  `quality`، `n`، `output_format`، `output_compression`، `background`، اور `response_format` شامل ہیں۔
- دیگر publishers، مثلاً `zm/meta/muse-image-1.0`، ZenMux کا Vertex AI `:predict`
  endpoint استعمال کرتے ہیں۔ `n`، `sampleCount` سے map ہوتا ہے، `aspect_ratio`،
  `aspectRatio` سے، اور `image_size` (`1K`، `2K`، `4K`)، `sampleImageSize` سے map ہوتا ہے۔ Pixel
  `size` صرف aspect ratio فراہم کرتا ہے، pixel dimensions کی ضمانت نہیں دیتا۔ Supported ratios،
  resolutions، اور counts model کے لحاظ سے مختلف ہوتے ہیں۔
- `zm/inclusionai/ming-image-0.1-design` اپنے dimensions خود منتخب کرتا ہے۔ `size`،
  `aspect_ratio`، اور `image_size` کو omit کریں؛ واضح values دینے پر HTTP 400 واپس آتا ہے۔ `output_format` کے ذریعے
  PNG، JPEG، اور WebP طلب کیے جا سکتے ہیں۔

یہ integration text-to-image generation کو support کرتی ہے، reference-image editing کو نہیں۔ Vertex
output کو `data[].b64_json` میں normalize کیا جاتا ہے؛ `response_format: "url"` کی صورت میں upstream
HTTPS URL واپس آتا ہے، یا جب صرف image bytes دستیاب ہوں تو base64 data URL واپس آتا ہے۔ خالی یا filter کیے گئے outputs
خالی success کے بجائے error واپس کرتے ہیں۔ Model تک رسائی ZenMux account پر منحصر ہے۔
[ZenMux کی Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) اور
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) دیکھیں۔

```bash
# تمام image models کی فہرست حاصل کریں
GET /v1/images/generations
```

## دستاویز OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`، `provider/model` prefix کے ذریعے OCR provider منتخب کرتا ہے؛ bare model id، مثلاً
`mistral-ocr-latest`، اپنے registered provider سے resolve ہوتی ہے، اور اگر `model` نہ دیا جائے تو
Mistral (`mistral-ocr-latest`) default ہوتا ہے۔ Registered providers (`open-sse/config/ocrRegistry.ts`):

| Provider id                   | Model id             | `model` value                                               | Notes                                                                                                            |
| ----------------------------- | -------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (یا bare `mistral-ocr-latest`) | Synchronous — response براہِ راست single upstream call سے واپس آتا ہے۔                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                 | Asynchronous upstream (`analyze` + poll) — ذیل میں دیکھیں۔                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                     | Synchronous، Vertex AI کے `openapi/chat/completions` partner endpoint کے ذریعے — auth/URL کے لیے ذیل میں دیکھیں۔ |

تینوں providers ایک ہی Mistral-shaped body میں response دیتے ہیں:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence کا poll flow

Azure Document Intelligence کی `analyze` API asynchronous ہے: ابتدائی request body کے بجائے
`Operation-Location` header واپس کرتی ہے، اور result کے لیے poll کرنا ضروری ہوتا ہے۔ Handler
(`open-sse/handlers/ocr.ts`) ہر سیکنڈ بعد زیادہ سے زیادہ 30 attempts تک اس URL کو poll کرتا ہے، non-`ok` poll response یا
`"failed"` status کی صورت میں فوراً ناکام ہو جاتا ہے (polling جاری نہیں رکھتا)، اور اگر attempt budget ختم ہونے کے بعد بھی
operation جاری ہو تو `504` واپس کرتا ہے۔ حتمی Azure response کو واپس کرنے سے پہلے Mistral کے استعمال کردہ
اسی `pages`/`markdown` shape میں normalize کیا جاتا ہے، اس لیے client code کو provider کے لحاظ سے الگ منطق کی ضرورت نہیں ہوتی۔

### Vertex AI DeepSeek OCR کی auth اور endpoint resolution

`vertex-deepseek-ocr` وہی Vertex AI authentication دوبارہ استعمال کرتا ہے جسے OmniRoute پہلے ہی
chat/image traffic کے لیے support کرتا ہے (`open-sse/executors/vertex.ts`): connection کی API key یا تو
Service Account JSON credential ہوتی ہے (جسے JWT-bearer flow کے ذریعے مختصر مدت کے OAuth access token میں تبدیل کیا جاتا ہے)
یا پہلے سے جاری کیا گیا OAuth access token ہوتا ہے، جسے جوں کا توں استعمال کیا جاتا ہے۔ Upstream endpoint URL، Vertex کے
generic `openapi/chat/completions` partner endpoint کا ہوتا ہے، جو connection کے project اور
region سے بنایا جاتا ہے — واضح `providerSpecificData.project`/`providerSpecificData.region` ہمیشہ ترجیح رکھتے ہیں؛
بصورتِ دیگر project، Service Account JSON کے `project_id` سے اخذ کیا جاتا ہے اور region کی default قدر
`us-central1` ہے۔ دونوں resolutions `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`، `resolveVertexOcrBaseUrl`) میں ہوتی ہیں، اور
`src/app/api/v1/ocr/route.ts` میں `handleOcr` کو dispatch کرنے سے پہلے استعمال کی جاتی ہیں۔

## ماڈلز کی فہرست

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ OpenAI فارمیٹ میں تمام چیٹ، ایمبیڈنگ، اور امیج ماڈلز + کومبو واپس کرتا ہے
```

### ماڈل کی قیمتیں (`pricing`)

جب OmniRoute کو ماڈل کی قیمت معلوم ہو تو اندراج میں ایک `pricing` آبجیکٹ شامل ہوتا ہے۔ قیمت
اس پرائسنگ ٹیبل سے آتی ہے جسے لاگت کا حساب کتاب استعمال کرتا ہے: پہلے سے شامل ڈیفالٹس، ہم وقت ساز
قیمتیں، اور `/api/pricing` کے ذریعے متعین کردہ اووررائیڈز۔ یہ فہرست کی قیمتیں ہیں، اس لیے
سبسکرپشن فراہم کنندگان کے لیے بھی فی ٹوکن قیمت دکھائی جاتی ہے۔

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| فیلڈز                                                           | اکائی                               | نوٹس                                                                                                                                                            |
| --------------------------------------------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | فی ٹوکن امریکی ڈالر، اعشاریہ اسٹرنگ | OpenRouter کے ساتھ مطابقت رکھنے والا، کبھی exponent notation میں نہیں۔ کیش کے دونوں فیلڈز صرف اس وقت ظاہر ہوتے ہیں جب کیش کی قیمت موجود ہو۔                     |
| `input`, `output`, `cached`, `cache_creation`                   | فی 1M ٹوکن امریکی ڈالر، عدد         | پہلے کے کیٹلاگ ورژنز کے فیلڈز، موجودہ کلائنٹس کے لیے برقرار رکھے گئے ہیں۔ جب پرائسنگ قطار میں یہ موجود ہوں تو `reasoning` اور `long_context` بھی ظاہر ہوتے ہیں۔ |

- **کومبو** اپنے پہلے نظر آنے والے ہدف کی قیمت رکھتے ہیں۔ پہلے سے شامل `auto/*` کومبو درخواست کے
  وقت ہدف منتخب کرتے ہیں، اس لیے ان میں `pricing` نہیں ہوتا۔
- **مفت ماڈلز** اس وقت `"0"` (اور `0`) دکھاتے ہیں جب ان کی قیمت صفر ہو۔ جس ماڈل کی پرائسنگ قطار
  نہ ہو وہ بھی `"0"` دکھاتا ہے، اگر کیٹلاگ اسے مفت (`free: true`) نشان زد کرے یا پہلے سے شامل مفت-ماڈل
  کیٹلاگ میں درج ہو۔
- **نامعلوم قیمت:** اندراج میں `pricing` کلید نہیں ہوتی۔
- **کریڈٹ کے حساب سے بل کرنے والے فراہم کنندگان** (جیسے Kiro) فی ٹوکن کے بجائے فی درخواست بل کرتے ہیں۔ ان کے
  اندراجات میں پہلے سے موجود فی 1M عددی فیلڈز برقرار رہتے ہیں اور فی ٹوکن اسٹرنگ فیلڈز شامل نہیں ہوتے۔
- **ویریئنٹس** (reasoning-effort ids، no-thinking aliases، discovery اور gateway mirrors)
  اس ماڈل کی قیمت نقل کرتے ہیں جس کی طرف وہ روٹ ہوتے ہیں۔
- فیلڈز صرف بنیادی شرحیں رکھتے ہیں۔ طویل سیاق کے درجے (عددی `long_context` فیلڈ) اور
  سروس-ٹئیر ملٹی پلائرز (مثلاً Codex fast یا flex) `prompt` یا
  `completion` کو تبدیل نہیں کرتے۔
- یہ آبجیکٹ ہر قسم کے توثیقی طریقے کے لیے یکساں ہے، بشمول `x-api-key` اور
  `anthropic-version` کے ساتھ Anthropic طرز کی درخواست (جواب بدستور `{ "object": "list",
"data": [...] }` رہتا ہے)۔ نفاذ: `src/app/api/v1/models/catalogPricing.ts`۔

### ماڈل آئی ڈی کے سابقے (`?prefix=`)

زیادہ تر ماڈلز **فراہم کنندہ کے سابقے** کے تحت مشتہر کیے جاتے ہیں۔ آپ کو کون سا سابقہ ملے گا، یہ
`MODELS_CATALOG_PREFIX_MODE` فیچر فلیگ سے کنٹرول ہوتا ہے، اور اسے **ہر درخواست کے لیے** کوئری
پیرامیٹر کے ذریعے اووررائیڈ کیا جا سکتا ہے — یہ ایسے کلائنٹ کے لیے مفید ہے جو سب کے لیے سرور کی
وسیع ترتیب تبدیل کیے بغیر صاف فہرست چاہتا ہو:

```bash
GET /v1/models?prefix=alias        # فی ماڈل ایک آئی ڈی — مختصر alias سابقہ
GET /v1/models?prefix=dual         # دونوں صورتیں (سرور ڈیفالٹ)
GET /v1/models?prefix=canonical    # صرف مکمل provider-id سابقہ
```

| موڈ         | جاری کرتا ہے                                              | نوٹس                                                                                                                                                                                                       |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **اور** `claude/claude-sonnet-4-6` | **ڈیفالٹ۔** دونوں آئی ڈیز ایک ہی ماڈل کو روٹ کرتی ہیں؛ انہیں اس لیے برقرار رکھا گیا ہے کہ جن کلائنٹ کنفیگریشنز میں کسی ایک صورت کو ہارڈ کوڈ کیا گیا ہو، وہ کام کرتی رہیں۔ کیٹلاگ تقریباً دوگنا ہو جاتا ہے۔ |
| `alias`     | `cc/claude-sonnet-4-6`                                    | فی ماڈل ایک اندراج۔ جن فراہم کنندگان کا الگ alias نہیں ہے وہ بھی اپنا اندراج جاری کرتے ہیں، اس لیے کچھ ضائع نہیں ہوتا۔                                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                                | مکمل provider-id سابقے کے تحت فی ماڈل ایک اندراج۔ جن فراہم کنندگان کا الگ alias نہیں ہے (مثلاً `antigravity/…`، `agy/…`) وہ یہاں بھی اپنی واحد آئی ڈی جاری کرتے ہیں، اس لیے کچھ ضائع نہیں ہوتا۔            |

`dual`-موڈ کے mirror کو کوئری پیرامیٹر کے بغیر بھی پہچانا جا سکتا ہے: اس میں بنیادی آئی ڈی کی طرف
اشارہ کرنے والا `parent` فیلڈ ہوتا ہے۔

ماڈل منتخب کرنے والا انٹرفیس دکھانے والے کلائنٹس کو `?prefix=alias` کی درخواست کرنی چاہیے — یہی
[OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md) کرتا ہے۔

### دریافت کے فلٹرز (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` اختیاری دریافت کے فلٹرز قبول کرتا ہے۔ ان میں سے کوئی بھی نہ ہونے پر جواب
غیر تبدیل رہتا ہے۔ یہ کال کرنے والے کو پہلے سے نظر آنے والے کیٹلاگ کو محدود کرتے ہیں (API-key کی
اجازتیں پہلے لاگو ہوتی ہیں)، اور OpenAI طرز کی `limit` / `after` صفحہ بندی سے پہلے چلتے ہیں:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # درج کردہ ہر قابلیت کا true ہونا ضروری ہے
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # کیٹلاگ کا `type`؛ جن قطاروں میں یہ نہ ہو وہ `chat` ہیں
GET /v1/models?q=sonnet&limit=10                           # id یا name پر کیس سے بے نیاز مطابقت
```

| پیرامیٹر      | اقدار                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | غیر منفی عدد صحیح، جس کا موازنہ `context_length` سے کیا جاتا ہے                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 حروف                                                                                          |

نامعلوم قدر، یا ایسا `min_context` جو غیر منفی عدد صحیح نہ ہو (مثلاً `1.5`)،
HTTP `400` لوٹاتا ہے اور پیغام میں درست اقدار کی فہرست شامل ہوتی ہے۔ نفاذ:
`src/app/api/v1/models/catalogFilters.ts`.

### ماڈل کی مختصر فہرست (`POST /v1/models/query`)

`POST /v1/models/query` اسی کیٹلاگ سے ایک مختصر، متعین فہرست لوٹاتا ہے، اور اس میں
`GET /v1/models` جیسی توثیق اور فی-کلید مرئیت لاگو ہوتی ہے:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ہر فیلڈ اختیاری ہے۔ `capabilities` اور `exclude` کے لیے ارے یا کوما سے جدا کردہ اسٹرنگ
استعمال کی جا سکتی ہے؛ `max_output` کا موازنہ `max_output_tokens` سے کیا جاتا ہے۔ نتائج
پہلے `owned_by` اور پھر `id` کے لحاظ سے ترتیب دیے جاتے ہیں۔ `limit` کی طے شدہ قدر `20`
ہے، اور `100` سے زیادہ اقدار کو `100` تک محدود کر دیا جاتا ہے۔ غیر درست JSON، نامعلوم
فیلڈ یا غیر درست قدر HTTP `400` لوٹاتی ہے۔

### انفرادی طور پر مخفی چیٹ ماڈلز

اپنے فراہم کنندہ کے صفحے پر **مخفی** نشان زد ماڈل کو کیٹلاگ سے خارج کر دیا جاتا ہے اور
واضح طور پر درخواست کیے جانے پر HTTP `404` / `model_not_found` کے ساتھ مسترد کر دیا جاتا ہے۔
یہ جانچ حل شدہ فراہم کنندہ اور ماڈل کو استعمال کرتی ہے، جس میں فراہم کنندہ کے عرف،
مطابقت رکھنے والے فراہم کنندہ کے نوڈ سابقے، اور کنکشن کی طے شدہ اقدار بھی شامل ہیں۔ کومبو
مخفی اہداف کو چھوڑ کر کسی ظاہر ساتھی کو استعمال کر سکتا ہے؛ جب کوئی قابلِ اجرا ہدف باقی نہ
رہے تو یہی ایرر کوڈ لوٹایا جاتا ہے۔ مخفی حیثیت ختم کرنے کا اثر اگلی درخواست پر ہوتا ہے۔
صرف تصاویر کے لیے مرئیت کی اووررائیڈ اسی ID والے چیٹ ماڈل کو مخفی نہیں کرتی۔

یہ انفرادی ماڈل ترتیب
[ماڈل کی نمائش کی اجازت/ممانعت کی فہرستوں](../routing/MODEL_EXPOSURE_LIST.md) سے الگ ہے،
جو واضح ڈسپیچ برقرار رکھتے ہوئے کیٹلاگ کے اشتہار اور خودکار روٹنگ کے امیدواروں کو فلٹر کرتی
ہیں۔ API-key کی ماڈل اجازتیں بدستور الگ سے لاگو ہوتی ہیں۔ کیٹلاگ کے سابقہ موڈ کی طے شدہ
قدر `dual` رہتی ہے۔

### سوچ کے بغیر ماڈل کی اقسام

سوچنے کی صلاحیت رکھنے والے Claude ماڈلز کے لیے `/v1/models` ایک **سوچ کے بغیر** قسم بھی
اشتہار کرتا ہے، جس کی ID کا سابقہ `claude-3-omniroute-no-thinking/` ہوتا ہے:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

اس ID کو منتخب کرنے پر (مثلاً Claude Code کی ایسی ترتیب میں جو ہمیشہ `thinking` بلاک شامل
کرتی ہو) یہ حقیقی `<provider>/<model>` پر واپس حل ہو جاتی ہے، اور reasoning کو غیر فعال کر
دیا جاتا ہے — `/v1/messages` پاتھ پر `thinking:{type:"disabled"}` کے ذریعے، یا
`/v1/chat/completions` پاتھ پر `reasoning`/`reasoning_effort` فیلڈز حذف کر کے۔ یہ قسم صرف
ان Claude-family ماڈلز کے لیے درج کی جاتی ہے جو thinking کو سپورٹ کرتے **اور** `disabled`
کو قبول کرتے ہوں (لہٰذا، مثال کے طور پر، صرف adaptive ماڈلز جو `disabled` مسترد کرتے ہیں،
خارج کر دیے جاتے ہیں)۔ آپریٹرز `ModelSpec.noThinkingAlias` کے ذریعے فی ماڈل اس قسم کو
زبردستی فعال یا غیر فعال کر سکتے ہیں۔

## ElevenLabs آڈیو جنریشن

OmniRoute میں اپنی ElevenLabs API key کے ساتھ ایک `elevenlabs` فراہم کنندہ کنکشن configure کریں۔
کلائنٹس اپنی **OmniRoute** key (`Authorization: Bearer $OMNIROUTE_API_KEY`) کے ذریعے تصدیق کرتے ہیں؛
gateway محفوظ شدہ فراہم کنندہ key کو `xi-api-key` کے طور پر فراہم کرتا ہے۔ ElevenLabs key کو
gateway bearer token کے طور پر کبھی نہ بھیجیں۔

| طریقہ | راستہ                       | جواب                                   | API key endpoint category |
| ----- | --------------------------- | -------------------------------------- | ------------------------- |
| POST  | `/v1/sound-generation`      | مقامی آڈیو بائٹس                       | `elevenlabs`              |
| POST  | `/v1/music`                 | مقامی آڈیو بائٹس                       | `music`                   |
| POST  | `/v1/music/stream`          | اسٹریمنگ آڈیو بائٹس                    | `music`                   |
| POST  | `/v1/music/detailed`        | مقامی multipart آڈیو اور کمپوزیشن پلان | `music`                   |
| POST  | `/v1/music/detailed/stream` | مقامی SSE میٹا ڈیٹا اور آڈیو چنکس      | `music`                   |
| POST  | `/v1/music/plan`            | JSON کمپوزیشن پلان                     | `music`                   |

یہ endpoints موجودہ `/v1/audio/speech`، `/v1/audio/transcriptions`،
`/v1/voices`، `/v1/text-to-speech/{voiceId}` اور `/v1/speech-to-text` routes کی تکمیل کرتے ہیں۔ مقامی JSON فیلڈز
اور query parameters جیسے `output_format` اور `enable_logging` محفوظ رہتے ہیں۔
`/v1/music/detailed` کے جوابات اپنی multipart boundaries برقرار رکھتے ہیں؛ انہیں multipart کے طور پر parse کریں۔
`/v1/music/detailed/stream` کمپوزیشن میٹا ڈیٹا اور SSE events میں
base64 آڈیو چنکس کے ساتھ `text/event-stream` واپس کرتا ہے۔ تمام چھ routes CORS preflight کو سپورٹ کرتے ہیں۔

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# ایک مختصر صوتی اثر۔ دورانیہ: 0.5 سے 30 سیکنڈ۔
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# موسیقی کا دورانیہ ملی سیکنڈز میں ظاہر کیا جاتا ہے: 3000 سے 600000۔
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

اضافی آڈیو کی ترسیل کے لیے اسی JSON body کے ساتھ `/v1/music/stream` استعمال کریں۔ Composition
بالکل ایک `prompt` یا `composition_plan` قبول کرتا ہے؛ `/v1/music/plan` کے لیے `prompt`
لازمی ہے اور یہ اختیاری طور پر `source_composition_plan` قبول کرتا ہے۔ مقامی
schemas اضافی فراہم کنندہ فیلڈز کو محفوظ رکھتے ہیں تاکہ composition-plan ورژنز اور fine-tuning اختیارات ElevenLabs تک پہنچ سکیں۔

متحدہ `/v1/music/generations` endpoint `elevenlabs/music_v1`،
`elevenlabs/music_v2` اور `elevenlabs/music_v2_5` بھی قبول کرتا ہے۔ فعال ElevenLabs کنکشن کے ساتھ،
یہ ماڈلز music catalog کے ذریعے دستیاب ہوتے ہیں۔ یہ endpoint
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` واپس کرتا ہے۔ اس کا `duration` فیلڈ
سیکنڈز میں ہوتا ہے اور `music_length_ms` سے map ہوتا ہے؛ واضح طور پر فراہم کیا گیا `music_length_ms` ترجیح رکھتا ہے۔
`instrumental`، `force_instrumental` سے map ہوتا ہے، جبکہ مقامی فیلڈ کو ترجیح حاصل ہوتی ہے۔
اسٹریمنگ کے لیے مقامی streaming endpoints اور صرف composition plan سے چلنے والی درخواستوں کے لیے
مقامی composition endpoint استعمال کریں۔

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Endpoint، model، budget اور connection restrictions upstream call سے پہلے لاگو ہوتی ہیں۔ مقامی
routes upstream status codes اور error bodies کو بغیر تبدیلی کے واپس کرتے ہیں، جن میں plan restriction کے لیے `402`
اور quota limit کے لیے `429` بھی شامل ہیں۔ `character-cost`، `song-id`، `request-id` اور `retry-after`
headers موجود ہونے پر محفوظ رہتے ہیں۔ مفت credit balance ہر
music model، output format یا API feature تک رسائی کی ضمانت نہیں دیتا: ہر درخواست کے لیے entitlement کا فیصلہ ElevenLabs کرتا ہے۔
متحدہ endpoint، OmniRoute کے normalized error envelope میں error status codes محفوظ رکھتا ہے۔

Upstream contracts: [صوتی اثرات](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)،
[موسیقی کی composition](https://elevenlabs.io/docs/api-reference/music/compose) اور
[streaming music کی تفصیلات](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)۔

تمام POST روٹس ایک ہی ساخت کی پیروی کرتے ہیں: `Bearer your-api-key` + Zod سے توثیق شدہ JSON باڈی (`v1RerankSchema`، `v1ModerationSchema`، `v1AudioSpeechSchema` وغیرہ، `src/shared/validation/schemas.ts` دیکھیں)۔ اسکیما کی ناکامی پر 4xx واپس کیا جاتا ہے۔

ایسے کلائنٹس کے لیے جو `Authorization: Bearer ...` شامل نہیں کر سکتے، OmniRoute URL میں API کیز بھی قبول کرتا ہے۔ اس کے لیے یا تو کوئری اسٹرنگ مطابقت (`?token=...`، `?apiKey=...`، `?api_key=...`، `?key=...`) یا ذیل میں دستاویزی مخصوص `/api/v1/vscode/{token}/...` اینڈ پوائنٹس استعمال کیے جا سکتے ہیں۔

```bash
# دوبارہ درجہ بندی (کلاؤڈ رجسٹری فراہم کنندہ، یا "<prefix>/<model>" کے طور پر OpenAI-compatible provider node)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina کی درجہ بندی (Foundation API credentials)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina سیگمنٹَر
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina سرچ (s.jina.ai؛ فراہم کنندہ کے عرف: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# ماڈریشنز
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (یا مطلوبہ فارمیٹ) باڈی واپس کرتا ہے
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS کے لیے زبان اور آواز درکار ہوتی ہے: `language` بطور ڈیفالٹ "en" ہوتی ہے؛ اگر
# آواز موجود نہ ہو یا OpenAI کی اسٹاک آواز کا نام (alloy, nova, …) ہو تو یہ "Adrian" بن جاتی ہے
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# تصویر میں ترمیم (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# ویڈیو / موسیقی کی تخلیق (فراہم کنندہ کے سابقہ والا ماڈل ID)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **پرووائیڈر نوڈز کی دوبارہ درجہ بندی:** `POST /v1/rerank` اوپن اے آئی سے ہم آہنگ پرووائیڈر نوڈز (oMLX، vLLM، Infinity، گیٹ وے کے پیچھے TEI، …) کو بھی روٹ کرتا ہے، جنہیں `<node-prefix>/<model>` کے طور پر ایڈریس کیا جاتا ہے۔ لوپ بیک نوڈز (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ہمیشہ اہل ہوتے ہیں، اور وہ ہوسٹ نام بھی اہل ہوتے ہیں جنہیں آپریٹر `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` میں درج کرتا ہے (مثلاً Docker/Compose سروس کا نام جیسے `http://reranker:8080/v1`؛ ان سے براہِ راست رابطہ کیا جاتا ہے، کبھی بھی `HTTP(S)_PROXY` یا کنکشن کے پن شدہ پراکسی کے ذریعے نہیں)۔ کسی بھی دوسرے ہوسٹ — LAN مشین یا Tailscale peer — پر موجود نوڈز صرف اسی وقت اہل ہوتے ہیں جب آپریٹر `RERANK_REMOTE_PROVIDER_NODES` فیچر فلیگ فعال کرے **اور** نوڈ کا بنیادی URL پرووائیڈر آؤٹ باؤنڈ URL پالیسی (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) پر پورا اترے۔ میموری انجن کا دوبارہ درجہ بندی والا مرحلہ اس روٹ کو لوپ بیک کے ذریعے کال کرتا ہے، اس لیے یہی اصول Memory کی ترتیبات میں `rerankProviderModel` پر بھی لاگو ہوتا ہے۔
>
> **مقامی سرور کی ساختیں:** نوڈ کو `<base>/v1/rerank` پر کال کیا جاتا ہے اور 404 کی صورت میں `<base>/rerank` پر (Infinity، TEI)۔ اپ اسٹریم باڈی میں Cohere/OpenAI املا (`documents`, `return_documents`) اور TEI املا (`texts`, `return_text`) دونوں شامل ہوتے ہیں، جبکہ اپ اسٹریم کے جواب کو Cohere envelope میں معمول پر لایا جاتا ہے: TEI کا سادہ `[{index, score, text}]`، باریک گیٹ ویز سے آنے والا `{results: [{index, score}]}`، اور Voyage طرز کا `{data: [...]}` — یہ سب کلائنٹ کو `{results: [{index, relevance_score, document?}]}` کی صورت میں واپس ملتے ہیں، اسکور کے لحاظ سے ترتیب دیے ہوئے اور `top_n` تک محدود۔

> **پرووائیڈر نوڈ کی دریافت:** اوپن اے آئی سے ہم آہنگ پرووائیڈر نوڈ پر موجود ماڈلز `GET /v1/models` میں نوڈ کے سابقے کے تحت ظاہر ہوتے ہیں۔ وہ قطاریں جن میں endpoint کا کوئی میٹا ڈیٹا نہیں ہوتا (جو عموماً مقامی `/v1/models` فہرستوں میں ہوتا ہے)، نوڈ کے `apiType` کو اختیار کرتی ہیں؛ اس لیے `embeddings` نوڈ کے ماڈلز `type: "embedding"` اور `rerank` نوڈ کے ماڈلز `type: "rerank"` ہوتے ہیں، بجائے اس کے کہ انہیں بطورِ پیش فرض chat سمجھا جائے۔ تاہم، ہم وقت ساز یا دستی طور پر شامل کی گئی قطار میں موجود واضح `supportedEndpoints` کو ترجیح حاصل رہتی ہے۔

### مخصوص پرووائیڈر روٹس

POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations

حل نہ ہو سکے — کو `401` کے ساتھ مسترد کرتا ہے، چاہے `REQUIRE_API_KEY=false` ہو، بجائے اس کے کہ ہر ٹیننٹ کی
فائلوں کی فہرست دکھائے (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)۔

## سرچ API

| طریقہ | پاتھ                   | وضاحت                                                                                            |
| ----- | ---------------------- | ------------------------------------------------------------------------------------------------ |
| GET   | `/v1/search`           | تشکیل شدہ سرچ فراہم کنندگان اور ان کی صلاحیتوں کی فہرست                                          |
| POST  | `/v1/search`           | سرچ استفسار چلائیں — باڈی کی توثیق `v1SearchSchema` سے ہوتی ہے، کیشنگ/کوایلیسنگ کو سپورٹ کرتا ہے |
| GET   | `/v1/search/analytics` | ہر فراہم کنندہ کے ہٹس/تاخیر/کیش کے اعداد و شمار                                                  |

**تصدیق:** Bearer API key (`extractApiKey` + `isValidApiKey`)۔ سرچ پالیسی `enforceApiKeyPolicy` کے ذریعے نافذ کی جاتی ہے۔

### Exa اور Tavily کے `provider_options`

Exa اور Tavily فراہم کنندہ سے مخصوص فیلڈز نامیاتی بیگ سے پڑھتے ہیں:
`provider_options.exa` (یا `provider_options["exa-search"]`) اور `provider_options.tavily`
(یا `provider_options["tavily-search"]`)۔ صرف ذیل کی کلیدیں آگے بھیجی جاتی ہیں۔ ہر کلید کو
`open-sse/handlers/search/providerOptionsPassthrough.ts` میں موجود اس کی اپنی Zod اسکیما کے خلاف
چیک کیا جاتا ہے، اور غلط قسم والی کلید خارج کر دی جاتی ہے۔ دیگر تمام کلیدیں نظر انداز کی جاتی ہیں،
جن میں auth، base URL، `stream` اور `outputSchema` بھی شامل ہیں۔ دیگر فراہم کنندگان کے زیرِ استعمال
فلیٹ کلیدیں (`cx`، `depth`، ...) حسبِ سابق کام کرتی ہیں۔

| فراہم کنندہ | بالائی سطح کے فیلڈز                                                                                                                                                                                                                                                                                                                                                       | نیسٹڈ                                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa         | `type`، `category`، `userLocation`، `moderation`، `additionalQueries`، `objective`، `systemPrompt`، `compliance` (فلیٹ پرِمِٹو)، `startPublishedDate`، `endPublishedDate`                                                                                                                                                                                                 | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` پہلے سے طے شدہ `{ text: true, highlights: true }` پر ضم کیے جاتے ہیں |
| Tavily      | `search_depth`، `chunks_per_source`، `time_range`، `start_date`، `end_date`، `include_published_date`، `filter_by_published_date`، `include_answer`، `include_raw_content`، `include_images`، `include_image_descriptions`، `include_favicon`، `include_domains_mode`، `language`، `filter_by_language`، `auto_parameters`، `exact_match`، `include_usage`، `safe_search` | —                                                                                                                                                  |

عمومی فیلڈز ہمیشہ فوقیت رکھتے ہیں: `query`، `max_results`، `filters` (ڈومینز)، `country` اور
`search_type` سے اخذ کیا گیا موضوع۔ Exa میں `search_type: "news"`، `category: "news"` کو برقرار
رکھتا ہے۔ Tavily `search_type: "finance"` (`topic: "finance"`) بھی قبول کرتا ہے۔

Firecrawl سرچ کی لاگت ہر شروع کیے گئے 10 واپس کیے گئے نتائج کے بلاک کے حساب سے ریکارڈ کی جاتی ہے،
جس کی قیمت فی بلاک $0.002 (2 کریڈٹس) ہے، اور ہر کال کے لیے کم از کم ایک بلاک شمار ہوتا ہے
([Firecrawl بلنگ](https://docs.firecrawl.dev/billing)): 11 نتائج کی قیمت $0.004 ہے۔

عمومی `time_range` اب دونوں فراہم کنندگان تک پہنچتا ہے: Exa کو `startPublishedDate` (ISO ٹائم اسٹیمپ)
اور Tavily کو `start_date` (`YYYY-MM-DD`) ملتا ہے۔ `provider_options` میں واضح طور پر دی گئی تاریخ
نقشہ شدہ تاریخ پر فوقیت رکھتی ہے۔

Exa کے نتائج `id`، `highlights` (ہر ہائی لائٹ، نہ کہ صرف پہلی ہائی لائٹ جو
`snippet` کے طور پر استعمال ہوتی ہے)، `highlight_scores`، `summary`، `subpages`، `entities` اور
`extras` کو `provider_raw` میں برقرار رکھتے ہیں۔ Tavily کے نتائج `images` اور `favicon` کو برقرار
رکھتے ہیں۔

Linkup سرچ کی لاگت `depth` کی قدر `fast` اور `standard` کے لیے $0.005، اور `deep` کے لیے $0.05
پر ریکارڈ کی جاتی ہے ([Linkup قیمت گذاری](https://docs.linkup.so/pages/documentation/development/pricing))،
خواہ `depth` `provider_options` سے آیا ہو یا کنکشن کی ترتیبات سے۔

Exa `type: "lite"` (Exa 3.0) فیلڈز کے ایک محدود مجموعے کو قبول کرتا ہے، اور کوئی بھی دوسرا فیلڈ
مقرر ہونے پر پوری درخواست مسترد کر دیتا ہے۔ lite کے لیے کال سے پہلے `additionalQueries`،
`systemPrompt` اور `contents` کی `text` اور `highlights` کے علاوہ تمام کلیدیں خارج کر دی جاتی ہیں۔
فرسودہ `subpages`، `subpageTarget`، `highlights.numSentences` اور `highlights.highlightsPerUrl`
اب آگے نہیں بھیجے جاتے۔

لاگت کا حساب فلیٹ رجسٹری `costPerQuery` کے مطابق ہوتا ہے، سوائے Exa کے، جو Exa کی اپنی قیمت گذاری
کی پیروی کرتا ہے: `auto` (اور پرانا `fast`) کے لیے فی کال $0.007، یا `lite` (اور پرانا `instant`)
کے لیے $0.004، جس میں 10 نتائج شامل ہیں؛ ہر اضافی نتیجے کے لیے $0.001؛ اور
`contents.summary` مقرر ہونے پر ہر واپس کیے گئے نتیجے کے لیے $0.001۔ Tavily کے لیے
`search_depth` کی قدروں `basic`، `fast` اور `ultra-fast` پر 1 کریڈٹ ($0.008)، اور `advanced`
پر 2 کریڈٹس ($0.016) ریکارڈ کیے جاتے ہیں
([Tavily API کریڈٹس](https://docs.tavily.com/documentation/api-credits))۔ `auto_parameters: true`
والی کال میں اگر Tavily کو `advanced` پر اپ گریڈ کیا جائے، تب بھی اسے 1 کریڈٹ کے طور پر ریکارڈ کیا جاتا ہے۔

## Web Fetch API

کنفیگر کردہ ویب-فچ فراہم کنندہ (Firecrawl، Jina
Reader، Tavily Extract، TinyFish Fetch، Nimble Extract، Parallel Extract) کے ذریعے URL سے مواد اخذ کریں۔

Parallel Extract (`parallel-search`، وہی API key جو Parallel Search کے لیے ہے) صرف Markdown واپس کرتا ہے — کوئی بھی دوسری
`format` ایک `400` ہے — اور مواد کو 100,000 حروف تک محدود کرتا ہے۔ جب ہدف صفحہ خود اخذ نہ کیا جا سکے، تو upstream اسے HTTP 200 کے اندر رپورٹ کرتا ہے؛ OmniRoute اسے ایک مقررہ پیغام کے ساتھ `422` کے طور پر ظاہر کرتا ہے۔

| طریقہ | پاتھ            | وضاحت                                                                        |
| ----- | --------------- | ---------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL کو fetch/scrape کریں — body کی توثیق `v1WebFetchSchema` کے ذریعے ہوتی ہے |

**Auth:** Bearer API key (`extractApiKey` + `isValidApiKey`)۔ پالیسی `enforceApiKeyPolicy` کے ذریعے نافذ ہوتی ہے۔

**Quota-aware fallback (#8297):** جب کوئی واضح `provider` نہ دیا جائے، تو pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) کو مقررہ
ترجیحی ترتیب (fill-first) میں
آزمایا جاتا ہے — rate-limited لیکن configured فراہم کنندہ کو request کو short-circuit کرنے کے بجائے چھوڑ دیا جاتا ہے، اور retryable/quota upstream failure (HTTP 429 ہمیشہ؛ Firecrawl/Tavily/TinyFish کے quota-style free tiers کے لیے 402/403 — Jina Reader کے لیے نہیں، اور عام 400 bad request کے لیے کبھی نہیں) request کے وقت اگلے غیر آزمودہ credentialed فراہم کنندہ تک پہنچتا ہے۔ جب pool کا ہر فراہم کنندہ exhausted ہو جائے، تو endpoint پچھلے عمومی `400` کے بجائے ایک واحد `429` (`Retry-After` header کے ساتھ) واپس کرتا ہے۔ جب واضح `provider` کی درخواست کی جائے، تو کوئی خاموش fallback نہیں ہوتا — rate-limited یا ناکام واضح فراہم کنندہ اپنی خرابی ظاہر کرتا ہے (`429` اگر rate-limited ہو، ورنہ upstream status)۔

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake کی توثیق کرتا ہے اور wire protocol کے مثال کے پیغامات (`request`، `cancel`) واپس کرتا ہے۔ اصل WS frames bundled WS server کے ذریعے Next.js route table کے باہر handle کیے جاتے ہیں۔

**Auth:** handshake کے دوران Bearer API key۔

### Responses API over WebSocket (صرف codex)

```bash
# HTTP API جیسا ہی host:port (default 20128)؛ connection کو upgrade کریں:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (یا: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# پہلا frame لازماً response.create ہونا چاہیے:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy **صرف `codex`** (ChatGPT
backend) کے لیے منسلک ہے۔ یہ API/dashboard کے اسی port پر paths `/v1/responses`,
`/responses`، اور `/api/v1/responses` پر سنتا ہے۔ پہلے `response.create` frame پر یہ
internal `codex-responses-ws` bridge کے ذریعے authentication اور تیاری کرتا ہے، ایک
codex OAuth connection منتخب کرتا ہے، اور `wreq-js` transport کے ذریعے
`wss://chatgpt.com/backend-api/codex/responses` تک tunnel کرتا ہے۔ **Non-codex models مسترد کیے جاتے ہیں** (`codex_ws_provider_required`)۔
Quota-share routing کے لیے `model: "qtSd/<group>/codex/<model>"` استعمال کریں۔ اسے
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` میں نافذ کیا گیا ہے۔

**Auth:** handshake کے دوران Bearer API key۔ bundled HTTP server (`server-ws.mjs`)
فعال entrypoint ہونا چاہیے (جب `app/server-ws.mjs` موجود ہو تو یہ default طور پر یہی ہوتا ہے)۔

#### Model id: bare ChatGPT id استعمال کریں (`codex/` prefix کے بغیر)

OpenAI **Codex CLI** client-side طور پر model name کی توثیق کرتا ہے جب
`supports_websockets = true` ہو، اور provider-prefixed ids جیسے
`codex/gpt-5.5` کو مسترد کرتا ہے (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)۔ **bare** id بھیجیں (مثلاً `gpt-5.5`)۔ OmniRoute کا bridge صرف
codex کے لیے ہے، اس لیے یہ tunnel کرنے سے پہلے bare id کو codex model کے طور پر دوبارہ resolve کرتا ہے
(`resolveCodexWsModelInfo`) — اگرچہ HTTP کے ذریعے bare
`gpt-5.5` بصورت دیگر کسی دوسرے فراہم کنندہ کو route ہو گا۔

#### OpenAI Codex CLI کو کنفیگر کرنا

OmniRoute کی طرف Codex CLI کی سمت متعین کرنے کے لیے `~/.codex/config.toml` میں WebSocket
support کے ساتھ custom provider شامل کریں (موجودہ config کو متاثر ہونے سے بچانے کے لیے علیحدہ
`CODEX_HOME` استعمال کریں):

```toml
model = "gpt-5.5"                 # bare id — "codex/gpt-5.5" نہیں
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # آخری slash کے بغیر؛ WS URL اسی سے اخذ ہوتا ہے (production میں https/wss استعمال کریں)
wire_api = "responses"                    # Feb 2026 سے صرف یہی supported value ہے
supports_websockets = true                # Responses-over-WS transport فعال کرتا ہے
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key (Bearer) رکھتا ہے
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key (اگر REQUIRE_API_KEY=false ہو تو کوئی بھی key)
codex exec "Responda apenas: PONG"
```

CLI `base_url + /responses` کو WebSocket میں upgrade کرتا ہے اور OmniRoute اسے منتخب کردہ
codex OAuth connection تک tunnel کرتا ہے۔ مقامی server کے خلاف end-to-end توثیق کی گئی ہے: ChatGPT `codex.rate_limits` + `response.created` واپس کرتا ہے اور completion کو stream کرتا ہے۔

### کوٹا سیشن کی بحالی (اختیاری)

ایک non-streaming `POST /v1/chat/completions` یا `POST /v1/responses` درخواست جو
حتمی کوٹا خرابی (`402`/`429`/`503` جس کے body میں کوٹا یا کریڈٹس ختم ہونے کا ذکر ہو) کے ساتھ ناکام ہو،
اسے خرابی واپس کرنے کے بجائے بعد میں دوبارہ چلانے کے لیے محفوظ کیا جا سکتا ہے۔ کالر ہر درخواست کے لیے
درج ذیل تین headers کے ذریعے اس خصوصیت کو فعال کرتا ہے:

| Header                       | قدر                                   |
| ---------------------------- | ------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                |
| `x-omniroute-session`        | سیشن ID، `[A-Za-z0-9._:-]{1,128}`     |
| `x-omniroute-recovery-turn`  | سیشن کے اندر منفرد turn ID (وہی اصول) |

صرف `stream: false` والے turns جن میں tools، tool history یا `previous_response_id` نہ ہو، اور
`x-omniroute-connection` pin نہ ہو، اہل ہیں، اور `STORAGE_ENCRYPTION_KEY` متعین ہونا چاہیے
(درخواست کو زیادہ سے زیادہ 24 گھنٹوں کے لیے encrypted حالت میں محفوظ کیا جاتا ہے)۔ اس کے بعد جواب
`202` ہوتا ہے جس میں `recovery.poll` شامل ہوتا ہے؛ poll کے لیے `GET /v1/quota-recoveries/{id}` استعمال کریں
(`202` زیر التوا حالت میں، تکمیل کے بعد بحال شدہ body کے ساتھ `200`) یا `DELETE` کے ذریعے منسوخ کریں۔
Tickets صرف اس API کلید کو دکھائی دیتے ہیں جس نے انہیں بنایا ہو۔ ایسی replay جس کا نتیجہ غیر یقینی ہو،
دو مرتبہ بھیجے جانے کے بجائے `needs_confirmation` حالت میں ختم ہوتی ہے۔ ماخذ: `src/lib/quota/quotaSessionRecovery.ts`۔

## خود سروس استعمال (`/api/usage/om-usage`)

کوئی بھی API کلید **اپنا** استعمال اور کوٹے پڑھ سکتی ہے — management auth درکار نہیں۔ یہی وہ endpoint ہے جسے
کوئی client (CLI، OmniCopilot panel) کلید رکھنے والے کو اس کے اخراجات دکھانے کے لیے استعمال کرتا ہے۔

```bash
# متنی صورت (تاریخی معاہدہ — ٹرمینل کے لیے سادہ متن)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ساختی صورت — UI کے استعمال کے لیے
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

کلید میں **`allowUsageCommand`** فعال ہونا چاہیے (بطورِ ڈیفالٹ غیر فعال — dashboard کا API-key
manager اسے ہر کلید کے لیے تبدیل کرتا ہے)۔ اس کے بغیر endpoint `403` واپس کرتا ہے۔

`?format=json` ایک ایسی discriminated shape واپس کرتا ہے جس سے caller کبھی refusal سے data field نہیں پڑھتا۔
کامیابی کی صورت میں:

```jsonc
{
  "allowed": true,
  // صرف اس وقت موجود ہوتا ہے جب کلید نے فی کلید استعمال کی حدود (روزانہ/ہفتہ وار USD) فعال کی ہوں:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // منتخب provider کا کوٹا snapshot، یا null جب ابھی کچھ cache نہ ہوا ہو:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // ہر connection کا snapshot، تاکہ UI متعدد providers کو ساتھ ساتھ دکھا سکے:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Refusal (`401` غلط کلید / `403` اجازت نہیں) کی صورت میں یہی route
`{ "allowed": false, "error": { "message": "…" } }` واپس کرتا ہے — موجود مگر خالی `personal`/`provider`
(کلید کو اجازت ہے، لیکن ابھی کچھ معلوم نہیں ہوا) refusal سے مختلف حالت ہے، اور صرف JSON صورت ہی
ان دونوں میں فرق کرتی ہے۔

**توثیق:** caller کی اپنی Bearer API کلید، `isValidApiKey` کے ذریعے validated — یہ management surface
(`/api/keys/…`) **نہیں** ہے، جو `requireManagementAuth` کے پیچھے برقرار رہتا ہے۔

### خام اور Cutoff سے ایڈجسٹ شدہ کوٹے کے فیصد

`/api/usage/om-usage` استعمال کرتے وقت callers کو **plain-text output** اور ساختی **JSON output** میں
دکھائے جانے والے فیصد کے فرق کا خیال رکھنا چاہیے:

| پہلو               | Plain-text format (`/api/usage/om-usage` / `@@om-usage`)                                      | JSON format (`?format=json`)                                                         |
| :----------------- | :-------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------- |
| **Output field**   | `NN% left` (مثلاً `20% left`)                                                                 | `provider.quotas` / `providers[].quotas`                                             |
| **پیمائش**         | **Cutoff سے ایڈجسٹ شدہ قابلِ استعمال allowance**: cutoff threshold سے اوپر باقی گنجائش        | **خام upstream quota**: provider کی غیر ایڈجسٹ شدہ پیمائش                            |
| **Cutoff scaling** | `effectiveRemainingPercent()` کے ذریعے scale کیا جاتا ہے، تاکہ محفوظ reserve `0% left` دکھائے | کوئی نہیں (provider کے رپورٹ کردہ خام snapshot values)                               |
| **Threshold data** | دکھائے گئے فیصد میں شامل کیا جاتا ہے                                                          | فی connection `quotaWindowThresholds` میں (یا server defaults میں) محفوظ کیا جاتا ہے |
| **بنیادی صارف**    | Interactive CLIs، terminal prompts، انسانی operators                                          | Programmatic integrations، dashboards، analytics، billing trackers                   |

#### Cutoff ایڈجسٹمنٹ کا فارمولا

OmniRoute upstream exhaustion کو روکنے کے لیے proactive quota cutoffs کو سپورٹ کرتا ہے (یہ connection
کے `quotaWindowThresholds`، provider defaults، یا global resilience settings کے ذریعے configure ہوتے ہیں)۔
جب کسی quota window پر cutoff threshold (مثلاً `cutoff = 25%`) فعال ہو، تو text renderer باقی allowance
اس طرح calculate کرتا ہے:

- اگر `remaining <= cutoff`: `0%` واپس کرتا ہے۔
- اگر `remaining > cutoff`: `((remaining - cutoff) / (100 - cutoff)) * 100` واپس کرتا ہے۔

Formatted text output اسے قریب ترین integer (`Math.round(...)`) تک round کرتا ہے۔

#### وضاحتی مثالેણ

ایسے provider window پر غور کریں جس میں **60% خام استعمال** (لہٰذا **40% خام باقی کوٹہ**) ہو اور ترتیب دیا گیا
**25% باقی کوٹے کا کٹ آف** تھریش ہولڈ ہو:

| نمائندگی                      | حساب                                               |  باقی   |                   مضمر استعمال                   |
| :---------------------------- | :------------------------------------------------- | :-----: | :----------------------------------------------: |
| **خام JSON (`?format=json`)** | اپ اسٹریم اسنیپ شاٹ (`quotas[window]`)             | **40%** |                     **60%**                      |
| **متنی فارمیٹ (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (اگر `100 - remaining` کا حساب کیا جائے) |

- **متن میں 20% باقی کیوں دکھتا ہے:** اکاؤنٹ پر موجود 40% جسمانی کوٹے میں سے 25% کٹ آف پالیسی کے ذریعے محفوظ ہے۔ راؤٹر اس کنکشن پر روٹنگ روکنے سے پہلے کالر کے پاس قابلِ استعمال 75% گنجائش میں سے صرف 15% باقی رہ جاتی ہے۔ اسکیلنگ اس بات کو یقینی بناتی ہے کہ روٹنگ رکنے کے عین وقت کنکشن ختم ہونے کا سگنل (`0% left`) دے۔
- **JSON خام اقدار کیوں برقرار رکھتا ہے:** JSON پے لوڈ عین provider اسنیپ شاٹ (`UsageSnapshot`) واپس کرتا ہے، تاکہ بیرونی ٹولز کو حقیقی اپ اسٹریم استعمال اور کنکشن سطح کے `quotaWindowThresholds` تک سرور کی جانب سے کسی نقصان دہ اسکیلنگ کے بغیر رسائی حاصل ہو۔

#### صارف کی منتقلی کے لیے رہنمائی

اگر کسی بیرونی انٹیگریشن (جیسے ایڈیٹر پلگ ان یا ایجنٹ ایکسٹینشن) نے پہلے متنی اینڈ پوائنٹ (`NN% left`) سے ڈیٹا حاصل کیا ہو اور استعمال کی شرح `100 - NN` کے طور پر شمار کی ہو، تو `?format=json` پر منتقل ہونے کا مطلب ہے:

- خام JSON اقدار پڑھنے سے **حقیقی اپ اسٹریم کھپت** ظاہر ہوگی (اوپر کی مثال میں 60% استعمال شدہ)۔
- اگر انٹیگریشن متنی اینڈ پوائنٹ کے قابلِ استعمال الاؤنس کے مفہوم کو برقرار رکھنا چاہتی ہے، تو وہ کنکشن سطح کی اوور رائیڈز کے لیے `quotaWindowThresholds` استعمال کرتے ہوئے مؤثر باقی رہنے کے فارمولے کا کلائنٹ سائیڈ پر جائزہ لے سکتی ہے۔

## سیمینٹک کیش

```bash
# کیش کے اعداد و شمار حاصل کریں
GET /api/cache/stats

# تمام کیشز صاف کریں
DELETE /api/cache/stats
```

جواب کی مثال:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### تاخیر پر اثر

سیمینٹک کیش کا HIT جواب کیش سے فراہم کرتا ہے، **بغیر کسی upstream
کال کے**، اس لیے رپورٹ کردہ `X-OmniRoute-Response-Latency` تقریباً صفر ہوتا ہے
(اصل upstream تاخیر سے قطع نظر)۔ تاخیر کے لیے حساس کلائنٹس
(بینچ مارکنگ، p50/p99 مانیٹرنگ) کو `X-OmniRoute-Cache-Latency` جوابی
ہیڈر چیک کرنا چاہیے:

| Value       | Meaning                                                     |
| ----------- | ----------------------------------------------------------- |
| `synthetic` | جواب کیش سے فراہم کیا گیا؛ تاخیر حقیقی upstream وقت نہیں ہے |
| _(absent)_  | جواب حقیقی upstream کال سے آیا ہے                           |

### فی کلید کیش بائی پاس

API keys `cacheDefaultMode` کے ذریعے سیمینٹک کیش ریڈز سے آپٹ آؤٹ کر سکتی ہیں:

| Value    | Behavior                                                   |
| -------- | ---------------------------------------------------------- |
| `legacy` | معمول کا کیش رویہ (پہلے سے طے شدہ)                         |
| `bypass` | کیش تلاش کو مکمل طور پر چھوڑیں؛ ہمیشہ upstream کو کال کریں |

کلید بناتے وقت (`POST /api/keys`) یا اپ ڈیٹ کرتے وقت (`PATCH /api/keys/[id]`) سیٹ کریں:

```json
{ "cacheDefaultMode": "bypass" }
```

### فی درخواست بائی پاس

کلید کی ترتیبات سے قطع نظر، کوئی بھی درخواست کیش کو بائی پاس کر سکتی ہے:

```
X-OmniRoute-No-Cache: true
```

## CLIProxyAPI مینجمنٹ مطابقت

OmniRoute ان تین [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
مینجمنٹ اینڈ پوائنٹس کا جواب دیتا ہے جنہیں استعمال کے ڈیش بورڈز Claude اور Codex کی سبسکرپشن حدود
پڑھنے کے لیے کال کرتے ہیں (مثلاً T3 Code کا `cliproxy` استعمال-حد ماخذ)۔ کلائنٹ کا base URL
OmniRoute پر سیٹ کریں اور `manage` scope والی API key کو اپنی مینجمنٹ key کے طور پر استعمال کریں۔ راستے
`/v0/management/*` اور `/api/v0/management/*` پر فراہم کیے جاتے ہیں۔

| Method | Path                         | Description                                                                                                                                           |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Claude اور Codex کے OAuth کنکشنز بطور `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`۔ کوئی ٹوکن نہیں                          |
| POST   | `/v0/management/api-call`    | باڈی `{ auth_index, method, url, header?, data? }`۔ اکاؤنٹ کے ٹوکن کے ساتھ ایک allowlisted درخواست بھیجتا ہے اور `{ status_code, body }` واپس کرتا ہے |
| POST   | `/v0/management/reset-quota` | باڈی `{ auth_index }`۔ ایک اکاؤنٹ کے کنکشن کول ڈاؤن، ماڈل لاک آؤٹس اور Codex کے فی-scope کول ڈاؤنز صاف کرتا ہے                                        |

- `auth_index` OmniRoute کا کنکشن id ہے۔ `provider`، `claude` یا `codex` ہوتا ہے (صرف OAuth
  کنکشنز؛ `anthropic` API-key provider فہرست میں شامل نہیں ہے)۔ Codex کے لیے،
  `id_token.chatgpt_account_id` ذخیرہ شدہ workspace id ہے اور `plan_type` ذخیرہ شدہ plan ہے۔
- `api-call` ایک عمومی proxy نہیں ہے۔ یہ صرف Claude `GET
https://api.anthropic.com/api/oauth/usage` اور Codex `GET
https://chatgpt.com/backend-api/wham/usage`، `GET .../wham/rate-limit-reset-credits` اور
  `POST .../wham/rate-limit-reset-credits/consume` قبول کرتا ہے، اور ہر ایک صرف متعلقہ
  provider کے اکاؤنٹ کے لیے۔ کوئی بھی دوسری چیز upstream سے رابطہ کیے بغیر `403` واپس کرتی ہے۔ کالر کا
  `Authorization` ہیڈر (`$TOKEN$` placeholder سمیت) نظر انداز کیا جاتا ہے: OmniRoute کنکشن کا access token
  داخل کرتا ہے، قریباً ختم ہونے کی صورت میں پہلے اسے refresh کرتا ہے، اور صرف allowlisted headers
  (`anthropic-beta`؛ `OpenAI-Beta`، `Originator`، `Chatgpt-Account-Id`؛
  `Accept`، `Content-Type`) آگے بھیجتا ہے۔ `Chatgpt-Account-Id` نہ ہونے کی صورت میں ذخیرہ شدہ workspace id
  پہلے سے طے شدہ ہوتی ہے۔ درخواستیں 15 سیکنڈ بعد timeout ہو جاتی ہیں اور کنکشن کا proxy استعمال کرتی ہیں۔
- `reset-quota` terminal states (banned، expired، credits_exhausted) کو جوں کا توں چھوڑتا ہے۔ نامعلوم
  `auth_index`، `404` واپس کرتا ہے۔

**Auth:** ڈیش بورڈ session یا `manage`-scoped API key، login غیر فعال ہونے پر بھی لازمی ہے
(راستے `ALWAYS_PROTECTED_API_PATHS` میں شامل ہیں)۔ صرف inference والی keys کو `403` ملتا ہے۔ ماخذ:
`src/lib/cliproxyCompat/managementApi.ts`.

ہم وقت ساز/درآمد شدہ ماڈلز کے لیے، `PUT /api/provider-models`، `provider`، `modelId`، اور
`maxOutputTokenOverride` قبول کرتا ہے: ایک مثبت عدد دستی آؤٹ پٹ-ٹوکن حد مقرر کرتا ہے، جبکہ `null`
اسے صاف کر کے طے شدہ قدر بحال کرتا ہے۔ `GET /api/provider-models?provider=<provider>`، یہ اقدار
`modelOutputOverrides` میں واپس کرتا ہے، جن میں وہ ماڈلز بھی شامل ہیں جن کے لیے حسبِ ضرورت ماڈل کی
قطار موجود نہیں۔ اووررائیڈ رن ٹائم کی `max_output_tokens` صلاحیت استعمال کرتا ہے اور ماڈل کی دوبارہ
ہم وقت سازی کے بعد بھی برقرار رہتا ہے۔ OpenAI-مطابق فراہم کنندہ کا صفحہ یہی ترمیم/صاف کرنے کے
کنٹرولز فراہم کرتا ہے اور واضح بصری معاونت والے ماڈلز کی نشان دہی کرتا ہے۔

کسی مطابقت پذیر فراہم کنندہ نوڈ پر، لکھنے والے راستے (`POST`، `PUT`، `PATCH`، `DELETE` اور
`/api/provider-models/validate-and-add`) ماڈل آئی ڈی کو عین upstream آئی ڈی کے طور پر محفوظ کرتے ہیں:
کسی prefixed فہرست سے چسپاں کی گئی آئی ڈی میں نوڈ کے اپنے سابقے کی شروع میں موجود پوری تکراری
سلسلہ منہدم کر دی جاتی ہے، اور جوابات محفوظ شدہ آئی ڈی واپس کرتے ہیں۔ کینونیکل فراہم کنندگان کی
سلَیش والی آئی ڈیز (مثلاً `nvidia/nemotron-…`) جوں کی توں محفوظ کی جاتی ہیں۔
`/v1/models` کبھی بھی stacked `<prefix>/<prefix>/<model>` آئی ڈی خارج نہیں کرتا۔

حسب ضرورت Chat Completions کے کسٹم نوڈز، واضح reasoning opt-outs کو upstream بیک اینڈ کے مطابق ڈھالتے ہیں۔ کنکشن کا کامیاب ٹیسٹ خودکار طور پر ہر ایسے عین model ID کے لیے chat-template کنٹرولز منتخب کرتا ہے جس کے `/models` اندراج میں تسلیم شدہ `owned_by` قدر ثابت ہو: `vllm`، `sglang`، یا `llamacpp`۔  
شفاف OpenAI-compatible wrappers اصل model اندراج کو nested  
`openai` آبجیکٹ کے اندر برقرار رکھ سکتے ہیں؛ شناخت ایسے زیادہ سے زیادہ تین envelopes تک کی جاتی ہے۔ جن models کی ملکیت غائب، نامعلوم، یا متضاد ہو، وہ عام OpenAI رویہ برقرار رکھتے ہیں۔ شناخت موجودہ catalog request کو دوبارہ استعمال کرتی ہے، completion tokens پیدا نہیں کرتی، اور connection endpoint تبدیل ہونے پر غیر مؤثر ہو جاتی ہے۔

ایسے بیک اینڈ کے لیے یہ رویہ مقرر کرنے کے لیے جو یہ metadata ظاہر نہیں کرتا، موجودہ partial  
provider update API استعمال کریں:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

یہ body `PUT /api/providers/<connection-id>` کے ساتھ بھیجیں۔ اس connection پر `none` کی واضح  
reasoning effort کو `chat_template_kwargs.thinking=false` اور  
`chat_template_kwargs.enable_thinking=false` کے طور پر بھیجا جاتا ہے۔ واضح native template اقدار اس وقت تک بااختیار رہتی ہیں جب تک server-side reasoning rule کسی effort کو لازم نہ کرے۔ یہ ترتیب صرف اس وقت لاگو ہوتی ہے جب کوئی custom OpenAI-compatible connection، Chat Completions body کو dispatch کرے؛ Responses requests اور عام providers اپنی native request shape برقرار رکھتے ہیں۔ عام OpenAI `reasoning_effort` passthrough کو زبردستی نافذ کرنے کے لیے `reasoningControl` کو `openai` پر سیٹ کریں، یا خودکار شناخت استعمال کرنے کے لیے اسے حذف کریں/`null` پر سیٹ کریں۔

Claude Code کے auto-mode classifier requests میں جب کوئی واضح reasoning controls موجود نہ ہوں تو native thinking بطور ڈیفالٹ غیر فعال رہتی ہے۔ شناخت model names یا completion limits کے بجائے Claude-format requests میں classifier کے system marker کو استعمال کرتی ہے۔ واضح body controls، معاون effort/thinking headers، routing rules، اور resolved model effort اپنی موجودہ ترجیح برقرار رکھتے ہیں۔ دونوں classifier stages اپنے prompts، completion limits، stop sequences، اور اصل upstream permission verdicts برقرار رکھتے ہیں؛ دوسرا stage اب بھی اپنی مطلوبہ visible reasoning کو عام متن کے طور پر پیدا کر سکتا ہے۔

#### Model limit کا ماخذ

`GET /api/models?withLimits=1` (نیز `true`؛ `0`/`false` یا اسے حذف کرنے سے پہلے سے طے شدہ

| `capsSource` value                           | ماخذ                                                               |
| -------------------------------------------- | ------------------------------------------------------------------ |
| `override:context`                           | مستقل context-window override (`model_context_overrides`)          |
| `override:max_input` / `override:max_output` | مستقل `max_input_tokens` / `max_output_tokens` capability override |
| `static-authoritative:<provider>/<model>`    | Static authoritative context-window table                          |
| `synced:<provider>/<model>`                  | models.dev synced capability row                                   |
| `registry:<provider>/<model>`                | Provider registry entry                                            |
| `spec:<model>`                               | Static model spec                                                  |
| `effort-base:` prefix                        | effort-suffixed variant کے base model سے لی گئی row                |
| `none`                                       | کوئی source limit کا اعلان نہیں کرتا (value `null` ہے)             |

### ورژن اور ریلیز چینل

```bash
GET /api/system/version
```

صرف لوپ بیک کے لیے دستیاب مینجمنٹ روٹ (ایڈمن تصدیق)۔ چل رہے ورژن، تازہ ترین
شائع شدہ ورژن اور خودکار اپ ڈیٹ کی حالت واپس کرتا ہے۔ `releaseChannel` اور `channels` اضافی
فیلڈز ہیں (ریل 3.8.54)؛ `channel` کا مطلب وہی ہے — ڈیش بورڈ اپ ڈیٹر کے ذریعے
استعمال کیا جانے والا تعیناتی موڈ (`npm`، `source` یا `docker-compose`)۔

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — چلنے والی build کا npm چینل: `-nightly.*` ورژنز کے لیے `nightly`،
  دیگر پری ریلیزز (`-rc.*`، `-beta.*`، `-alpha.*`) کے لیے `next`، `channels.latest` سے
  پرانے major کے مستحکم ورژن کے لیے `lts`، بصورت دیگر `latest`۔ یہی قواعد
  `scripts/release/dist-tag.mjs` میں استعمال ہوتے ہیں، جو اشاعت کے وقت npm dist-tag منتخب کرتا ہے۔
- `channels` — ہر dist-tag کا شائع شدہ head، `npm view omniroute dist-tags` سے (رجسٹری
  HTTP fallback کے ساتھ)، اور `latest` کی طرح 10 منٹ کی TTL کے ساتھ cache کیا جاتا ہے۔ `latest`
  ہمیشہ موجود ہوتا ہے (`latest` فیلڈ پر fallback، پھر `"unavailable"`)؛ `next`، `nightly` اور
  `lts` صرف اسی وقت ظاہر ہوتے ہیں جب متعلقہ dist-tag موجود ہو۔ `Cache-Control: no-cache` کی
  درخواست دونوں lookups کو تازہ کرتی ہے۔

چینل ماڈل (`latest` = 4.0 GA تک v3، `next` = rc، `nightly` = `develop` builds،
`lts` = 4.0 GA کے بعد v3 patches) کی وضاحت `docs/ops/RELEASE_STRATEGY.md` میں کی گئی ہے۔

## آڈیو ٹرانسکرپشن

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

کسی بھی تشکیل شدہ STT فراہم کنندہ کو استعمال کرتے ہوئے آڈیو فائلوں کو ٹرانسکرائب کریں۔ پاتھ کا پہلا
حصہ مقامی فراہم کنندہ منتخب کرتا ہے (`openai/…`، `deepgram/…`)۔ ایسے گیٹ ویز جو
کسی دوسرے وینڈر کے ماڈل کو دوبارہ برآمد کرتے ہیں، ایک مکمل شناخت کنندہ استعمال کرتے ہیں
(`openrouter/deepgram/nova-3`)۔

**درخواست:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**جواب:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**مثالی ماڈل IDs:** `openai/whisper-1` (OpenAI کلید درکار ہے)،
`openrouter/deepgram/nova-3` (OpenRouter کلید درکار ہے)،
`deepgram/nova-3` (مقامی Deepgram کلید درکار ہے)۔ سادہ
`deepgram/nova-3` درخواست OpenRouter استعمال **نہیں** کرتی۔

**معاونت یافتہ فارمیٹس:** `mp3`، `wav`، `m4a`، `flac`، `ogg`، `webm`۔

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** Gemini Live
WebSocket کے ذریعے فائل موڈ ٹرانسکرپشن (Gemini API کلید درکار ہے)۔ اپ لوڈ کو `ffmpeg`
کے ذریعے 16 kHz مونو PCM میں تبدیل کیا جاتا ہے
(`PATH` پر موجود ہونا ضروری ہے، سوائے اس صورت کے جب فائل پہلے ہی 16 kHz مونو PCM WAV ہو)، سیشن میں
اسٹریم کیا جاتا ہے اور حتمی متن `{ "text": "..." }` کے طور پر واپس کیا جاتا ہے۔ اختیاری `language` اور `prompt`
فارم فیلڈز آگے بھیجے جاتے ہیں۔ حدود: 25 MiB سے بڑی اپ لوڈز یا 10 منٹ سے زیادہ طویل ڈی کوڈ شدہ آڈیو
`413` کا جواب حاصل کرتے ہیں؛ 60 سیکنڈ سے زیادہ چلنے والی تبدیلی کا عمل ختم کر دیا جاتا ہے اور `504` کا جواب
دیا جاتا ہے۔ API کلید صرف `x-goog-api-key` ہیڈر میں بھیجی جاتی ہے، WebSocket URL میں کبھی نہیں۔

## ٹوکن والے VS Code / ہیڈر کے بغیر عرف

یہ عرف اس وقت استعمال کریں جب کوئی انٹیگریشن `Authorization` ہیڈر شامل نہ کر سکے اور اسے API کلید بیس URL میں شامل کرنے کی ضرورت ہو۔

```bash
# OpenAI طرز کا کیٹلاگ عرف
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI طرز کے چیٹ عرف
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama طرز کے عرف
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

مثال:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

نوٹس:

- ٹوکن والے عرف `/v1/*` اور `/api/tags` جیسے ہی ہینڈلرز دوبارہ استعمال کرتے ہیں؛ جوابی ساختیں یکساں رہتی ہیں۔
- جب بھی کلائنٹ حسبِ ضرورت ہیڈرز کو سپورٹ کرے، `Authorization: Bearer ...` کو ترجیح دیں۔
- URL پر مبنی ٹوکنز OmniRoute سے باہر ریورس پراکسی لاگز، براؤزر ہسٹری اور ٹیلی میٹری میں ظاہر ہو سکتے ہیں۔ انہیں مطابقت کے ایک اختیار کے طور پر سمجھیں، ڈیفالٹ توثیقی طریقے کے طور پر نہیں۔

# تمام API کلیدوں کے لیے بجٹ کی حیثیت حاصل کریں

## ٹوکن کی حدود

فی API کلید **ٹوکن** بجٹس (اوپر دیے گئے USD پر مبنی بجٹ سے الگ)۔ درخواست کے راستے پر براہِ راست نافذ کیے جاتے ہیں: جب کسی کلید کے موجودہ ونڈو کے استعمال کی مقدار اپنی حد تک پہنچ جاتی ہے، تو درخواستیں `429 Too Many Requests` کے ساتھ مسترد کر دی جاتی ہیں۔ حدود کسی مخصوص `model`، `provider` تک محدود کی جا سکتی ہیں، یا پوری کلید پر `global` طور پر لاگو کی جا سکتی ہیں؛ جب متعدد حدود کسی درخواست سے مطابقت رکھتی ہوں، تو سب سے زیادہ پابندی والی حد نافذ ہوتی ہے۔

```bash
# کسی کلید کی ٹوکن حدود کی فہرست (موجودہ ونڈو کے استعمال سمیت)
GET /api/usage/token-limits?apiKeyId=key-123

# ٹوکن کی حد بنائیں یا اپ ڈیٹ کریں
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id کے ذریعے ٹوکن کی حد حذف کریں
DELETE /api/usage/token-limits?id=tl-abc
```

> **اسکیما نوٹس** (`setTokenLimitSchema`): `apiKeyId` اور `scopeType` (`model` | `provider` | `global`) درکار ہیں۔ `scopeType` اگر `global` نہ ہو تو `scopeValue` درکار ہے (مثلاً `model` اسکوپ کے لیے ماڈل id، اور `provider` اسکوپ کے لیے provider id)۔ `tokenLimit` ایک مثبت عدد صحیح ہونا چاہیے (اسٹرنگ سے تبدیل کیا جاتا ہے)۔ اختیاری: `id` (بنانے کے لیے چھوڑ دیں، اپ ڈیٹ کرنے کے لیے فراہم کریں)، `resetInterval` (`daily` | `weekly` | `monthly`، ڈیفالٹ `monthly`)، `resetTime` (`HH:MM`)، `enabled` (ڈیفالٹ `true`)۔ `GET` کے جوابات ہر حد میں `tokensUsed`، `remaining`، `windowStart`، `periodStartAt`، اور `nextResetAt` شامل کرتے ہیں۔ یہ مینجمنٹ-کلاس اینڈپوائنٹ ہے (توثیق مرکزی authz پائپ لائن کے ذریعے نافذ کی جاتی ہے)۔

## درخواست کی پراسیسنگ

1. کلائنٹ `/v1/*` کو درخواست بھیجتا ہے
2. روٹ ہینڈلر `handleChat`، `handleEmbedding`، `handleAudioTranscription`، یا `handleImageGeneration` کو کال کرتا ہے
3. ماڈل حل کیا جاتا ہے (براہِ راست provider/model یا alias/combo)
4. اکاؤنٹ کی دستیابی کی فلٹرنگ کے ساتھ مقامی DB سے اسناد منتخب کی جاتی ہیں
5. چیٹ کے لیے: `handleChatCore` semantic/signature کیش چیک کرتا ہے اور combo کی کمپریشن ترتیبات حل کرتا ہے
6. فعال ہونے کی صورت میں provider translation سے پہلے پیشگی کمپریشن چلتی ہے (`lite`، Caveman، RTK، یا stacked)
7. provider executor upstream درخواست بھیجتا ہے
8. جواب کو کلائنٹ کے فارمیٹ میں واپس تبدیل کیا جاتا ہے (چیٹ)، یا جوں کا توں واپس کیا جاتا ہے (embeddings/images/audio)
9. استعمال، کمپریشن کے تجزیات، اور درخواست کے لاگز ریکارڈ کیے جاتے ہیں
10. combo کے قواعد کے مطابق خرابیوں کی صورت میں fallback لاگو ہوتا ہے

مکمل آرکیٹیکچر حوالہ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## مینجمنٹ پراکسیز

آؤٹ باؤنڈ HTTP(S)/SOCKS پراکسیز جنہیں providers، accounts یا عالمی سطح پر تفویض کیا جا سکتا ہے۔

| Method | Path                                         | Description                                                                                                                                                                  |
| ------ | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | پراکسیز کی فہرست (اگر `?id=` دیا جائے تو ایک پراکسی واپس کرتا ہے؛ `?id=&where_used=1` کے ساتھ assignment graph واپس کرتا ہے)                                                 |
| POST   | `/api/v1/management/proxies`                 | پراکسی بنائیں — باڈی کی توثیق `createProxyRegistrySchema` سے ہوتی ہے                                                                                                         |
| PATCH  | `/api/v1/management/proxies`                 | پراکسی اپ ڈیٹ کریں — باڈی کی توثیق `updateProxyRegistrySchema` سے ہوتی ہے (`id` درکار ہے)                                                                                    |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | پراکسی حذف کریں (`force=1` استعمال کرنے سے assignments الگ ہو جاتے ہیں)                                                                                                      |
| GET    | `/api/v1/management/proxies/assignments`     | assignments کی فہرست — `proxy_id`, `scope`, `scope_id` کے ذریعے فلٹر کیا جا سکتا ہے؛ کسی connection کے لیے فعال پراکسی حل کرنے کی خاطر `resolve_connection_id=<id>` پاس کریں |
| PUT    | `/api/v1/management/proxies/assignments`     | تفویض کریں — باڈی کی توثیق `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) سے ہوتی ہے۔ dispatcher cache صاف کرتا ہے                                                  |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | بلک تفویض — باڈی کی توثیق `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) سے ہوتی ہے                                                                           |
| GET    | `/api/v1/management/proxies/health?hours=24` | مقررہ مدت کے دوران مجموعی پراکسی صحت (کامیابی/ناکامی کی تعداد، latency)                                                                                                      |

**Auth:** ہر route پر management session/API key درکار ہے (`requireManagementAuth`)۔

> ٹاسک کی تفصیل میں موجود `POST /api/v1/management/proxies/[id]/assignments` اور `POST /api/v1/management/proxies/[id]/health` اوپر دکھائے گئے flat `/assignments` اور `/health` routes کے ذریعے فراہم کیے جاتے ہیں — codebase میں فی-id subroutes موجود نہیں ہیں۔

## لچک (توسیع شدہ)

OmniRoute عارضی ناکامی کے تین آزاد میکانزم فراہم کرتا ہے؛ ذیل کے انتظامی اینڈپوائنٹس آپریٹرز کو انہیں پڑھنے اور اووررائیڈ کرنے کی اجازت دیتے ہیں:

| دائرہ کار       | حالت کا ذخیرہ                          | پڑھیں                                     | ری سیٹ / صاف کریں                                                 |
| --------------- | -------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| پرووائیڈر بریکر | `domain_circuit_breakers` + میموری میں | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                      |
| کنکشن کول ڈاؤن  | پرووائیڈر کنکشنز پر `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (سست روی سے دوبارہ فعال ہوتا ہے؛ پرووائیڈر PUT کے ذریعے صاف کریں) |
| ماڈل لاک آؤٹ    | میموری میں ماڈل دستیابی کی رجسٹری      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                          |

`PATCH /api/resilience`، `providerBreaker.oauth` اور `providerBreaker.apikey` کے تحت پرووائیڈر بریکر اووررائیڈز قبول کرتا ہے۔ ہر پروفائل `degradationThreshold`، `failureThreshold`، اور `resetTimeoutMs` کو سپورٹ کرتا ہے؛ یہی فیلڈز Dashboard → Settings → Resilience میں بھی دستیاب ہیں۔

```bash
# ایک ماڈل کا لاک آؤٹ صاف کریں
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# تمام لاک آؤٹ صاف کریں
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

مکمل تصوراتی حوالہ اور بریکر کی ڈیفالٹ قدریں: [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" اور [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) دیکھیں۔

### ریٹ-لمٹ قطار اور خودکار فعال کاری کا حفاظتی نظام

- **مجاز تحریری راستہ**: `POST /api/rate-limits`، جس کی باڈی `{"connectionId": "<id>", "enabled": true|false}` ہے، کسی کنکشن کے لیے ریٹ-لمٹ تحفظ کو ٹوگل کرنے کا مجاز انتظامی اینڈپوائنٹ ہے۔ `PUT /api/providers/[id]` جان بوجھ کر `rateLimitProtection` میں ترمیم یا اسے تبدیل نہیں کرتا (#11278)۔
- **`enabled: false` کے معانی**: `enabled: false` سیٹ کرنے سے کنکشن کے لیے واضح تحفظ ختم ہو جاتا ہے، لیکن یہ فعال API-key کنکشن کو عالمی خودکار فعال کاری کے حفاظتی نظام (`autoEnableApiKeyProviders = true`) سے خارج **نہیں** کرتا۔ `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) میں `false` اور `undefined` یکساں ہیں؛ واضح تحفظ کے بغیر فعال API-key کنکشن خودکار فعال کاری کے حفاظتی نظام کے تحت محفوظ رہتے ہیں۔
- **عالمی غیر فعال کاری**: API-key کنکشنز کو ریٹ-لمٹ قطاروں کے بغیر چلانے کے لیے، حفاظتی نظام کو عالمی سطح پر `RATE_LIMIT_AUTO_ENABLE=false` (env) کے ذریعے یا `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) کے ذریعے غیر فعال کریں۔

## MCP سرور

OmniRoute میں 3 ٹرانسپورٹس (stdio، SSE، streamable-http) اور محدود دائرہ کار والے ٹولز کے ساتھ سرایت شدہ Model Context Protocol سرور شامل ہے۔ ذیل کے ڈیش بورڈ اینڈ پوائنٹس اسٹیٹس/آڈٹ ڈیٹا پڑھتے ہیں اور HTTP ٹرانسپورٹس کے لیے پراکسی کا کام کرتے ہیں۔

| طریقہ  | راستہ                  | تفصیل                                                                                                             | -------------------- |
| ------ | ---------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------- |
| GET    | `/api/mcp/status`      | ہارٹ بیٹ، ٹرانسپورٹ، آن لائن حالت، آخری کال، نمایاں ٹولز، 24 گھنٹوں کی کامیابی کی شرح                             |
| GET    | `/api/mcp/tools`       | MCP ٹولز کی فہرست، جن میں `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` شامل ہیں      |
| GET    | `/api/mcp/sse`         | SSE ٹرانسپورٹ کے لیے SSE اسٹریم کھولیں (اگر MCP غیر فعال ہو یا ٹرانسپورٹ میں عدم مطابقت ہو تو `503` واپس کرتا ہے) |
| POST   | `/api/mcp/sse`         | SSE ٹرانسپورٹ پر JSON-RPC فریم بھیجیں                                                                             |
| GET    | `/api/mcp/stream`      | Streamable HTTP ٹرانسپورٹ کا SSE پہلو کھولیں (سرور کی جانب سے شروع کیے گئے پیغامات)                               |
| POST   | `/api/mcp/stream`      | Streamable HTTP ٹرانسپورٹ پر JSON-RPC فریم بھیجیں                                                                 |
| DELETE | `/api/mcp/stream`      | Streamable HTTP سیشن ختم کریں                                                                                     |
| GET    | `/api/mcp/audit`       | آڈٹ لاگ سے استفسار کریں — `?limit=`, `?offset=`, `?tool=`, `?success=true                                         | false`, `?apiKeyId=` |
| GET    | `/api/mcp/audit/stats` | مجموعی آڈٹ اعدادوشمار (کل تعداد، کامیابی کی شرح، اوسط دورانیہ، نمایاں ٹولز)                                       |

**توثیق:** `sse`/`stream` ٹرانسپورٹس MCP سے مخصوص توثیقی سطح (Bearer API key جس میں `mcp` scope ہو) کی پابندی کرتی ہیں؛ `status`/`tools`/`audit*` روٹس ڈیش بورڈ سے قابلِ مطالعہ ہیں (ڈیش بورڈ ہوسٹ تک رسائی کے علاوہ اضافی توثیق درکار نہیں)۔

> دونوں HTTP ٹرانسپورٹس `settings.mcpEnabled` اور `settings.mcpTransport` کے ذریعے محدود ہیں — ٹرانسپورٹ میں عدم مطابقت `400` واپس کرتی ہے، جبکہ MCP کی غیر فعال حالت `503` واپس کرتی ہے۔

## A2A سرور

OmniRoute ایک A2A (Agent-to-Agent) JSON-RPC 2.0 اینڈپوائنٹ کے علاوہ معائنہ/ڈیش بورڈ کے استعمال کے لیے ایک REST ریپر بھی فراہم کرتا ہے۔

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # اختیاری ہے، جب تک OMNIROUTE_API_KEY سیٹ نہ ہو
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

معاونت یافتہ طریقے (سبھی `settings.a2aEnabled` کے تحت فعال ہوتے ہیں):

| طریقہ            | وضاحت                                                            |
| ---------------- | ---------------------------------------------------------------- |
| `message/send`   | ہم وقت skill کا اجرا؛ `{task, artifacts, metadata}` واپس کرتا ہے |
| `message/stream` | اسی skill سیٹ کا اسٹریمنگ SSE اجرا                               |
| `tasks/get`      | `taskId` کے ذریعے task حاصل کریں                                 |
| `tasks/cancel`   | `taskId` کے ذریعے task منسوخ کریں                                |

بلٹ اِن skills: `smart-routing`، `quota-management`، `provider-discovery`، `cost-analysis`، `health-report`۔

### ایجنٹ کارڈ

```bash
GET /.well-known/agent.json
```

عوامی A2A ایجنٹ کارڈ (نام، وضاحت، صلاحیتیں، skill catalog، auth scheme) واپس کرتا ہے — 1h کے لیے عوامی طور پر کیش کیا جاتا ہے۔ auth درکار نہیں۔

### REST مددگار

| طریقہ | راستہ                        | وضاحت                                                                                                               |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A کی فعالیت + task کے اعدادوشمار + کیش شدہ ایجنٹ کارڈ کا خلاصہ                                                    |
| GET   | `/api/a2a/tasks`             | tasks کی فہرست — `?state=submitted\|working\|completed\|failed\|cancelled`، `?skill=`، `?limit=` (≤200)، `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST مددگار کے طور پر نافذ نہیں — JSON-RPC `message/send` کے ذریعے بنائیں)                                         |
| GET   | `/api/a2a/tasks/[id]`        | ایک task حاصل کریں                                                                                                  |
| POST  | `/api/a2a/tasks/[id]/cancel` | ایک task منسوخ کریں                                                                                                 |

**توثیق:** REST مددگار management auth کے بغیر چلتے ہیں (ڈیش بورڈ سے پڑھے جا سکتے ہیں)؛ JSON-RPC `/a2a` راستہ، اگر تشکیل دیا گیا ہو، تو Bearer `OMNIROUTE_API_KEY` استعمال کرتا ہے۔

## توثیق

چار اسناد کی اقسام (ڈیش بورڈ سیشن، مقامی CLI ٹوکن، `oma_live_…` رسائی ٹوکن، مینج اسکوپ والی API کلید) اور ان کے انفرنس کیز سے فرق کے لیے [مینجمنٹ توثیق](../guides/MANAGEMENT-AUTH.md) دیکھیں۔

- ڈیش بورڈ کے راستے (`/dashboard/*`) `auth_token` کوکی استعمال کرتے ہیں
- لاگ اِن محفوظ کردہ پاس ورڈ ہیش استعمال کرتا ہے؛ بصورتِ دیگر `INITIAL_PASSWORD` استعمال ہوتا ہے
- `requireLogin` کو `/api/settings/require-login` کے ذریعے فعال یا غیر فعال کیا جا سکتا ہے
- `/v1/*` راستوں کو `REQUIRE_API_KEY=true` ہونے پر اختیاری طور پر Bearer API کلید درکار ہوتی ہے
- اس حوالہ میں "مینجمنٹ ٹوکن" / "مینجمنٹ اسکوپ والی API کلید" سے مراد اس گائیڈ میں دی گئی اقسام میں سے کوئی ایک ہے — یہ کسی غیر متعین اضافی خفیہ قسم کی طرف اشارہ نہیں کرتا

> **اہم تبدیلی (v3.8.0)** — `/api/v1/agents/tasks/*` اور کول ڈاؤن مینجمنٹ کے اختتامی مقامات کے لیے اب **مینجمنٹ توثیق** (ڈیش بورڈ کی `auth_token` کوکی یا مینجمنٹ اسکوپ والی API کلید) درکار ہے۔ جو کلائنٹس پہلے ان راستوں کو بغیر توثیق کے کال کرتے تھے، انہیں `401 Unauthorized` موصول ہوگا۔ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) کمٹ دیکھیں۔
