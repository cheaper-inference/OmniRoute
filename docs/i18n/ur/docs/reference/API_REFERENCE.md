## چیٹ تکمیلات

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### حسبِ ضرورت ہیڈرز

| ہیڈر                     | سمت     | وضاحت                                                                                                                                                                                                                                |
| ------------------------ | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | درخواست | کیش کو نظرانداز کرنے کے لیے `true` مقرر کریں                                                                                                                                                                                         |
| `x-omniroute-no-memory`  | درخواست | اس درخواست کے لیے میموری + مہارتوں کی شمولیت چھوڑنے کی خاطر `true` مقرر کریں (no-cache کے مماثل؛ ہر کال کے ٹوکن/لاگت کے اضافی بوجھ سے بچاتا ہے)                                                                                      |
| `X-OmniRoute-Progress`   | درخواست | پیش رفت کے واقعات کے لیے `true` مقرر کریں                                                                                                                                                                                            |
| `X-Session-Id`           | درخواست | بیرونی سیشن وابستگی کے لیے مستقل سیشن کلید                                                                                                                                                                                           |
| `x_session_id`           | درخواست | انڈراسکور والی قسم بھی قبول کی جاتی ہے (براہِ راست HTTP)                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | درخواست | کالر کی فراہم کردہ سیشن/گفتگو ٹیگ (میموری کو بھی فراہم کرتی ہے)۔ موجود ہونے پر، فی سیشن لاگت منسوب کرنے کے لیے بعینہٖ `call_logs.session_tag` میں محفوظ کی جاتی ہے (#8249) — غیر موجود ہونے پر کبھی خودکار طور پر تخلیق نہیں کی جاتی |
| `Idempotency-Key`        | درخواست | نقل ختم کرنے کی کلید (5 سیکنڈ کی مدت)                                                                                                                                                                                                |
| `X-Request-Id`           | درخواست | نقل ختم کرنے کی متبادل کلید                                                                                                                                                                                                          |
| `x-omniroute-connection` | درخواست | کسی واحد ماڈل کی درخواست کو اس کے id کے ذریعے ایک فراہم کنندہ کنکشن (اکاؤنٹ) سے منسلک کریں — [ہر درخواست کے لیے اکاؤنٹ پننگ](#account-pinning-per-request) دیکھیں                                                                    |
| `X-OmniRoute-Cache`      | جواب    | `HIT` یا `MISS` (غیر اسٹریمنگ)                                                                                                                                                                                                       |
| `X-OmniRoute-Idempotent` | جواب    | اگر نقل ختم کی گئی ہو تو `true`                                                                                                                                                                                                      |
| `X-OmniRoute-Progress`   | جواب    | اگر پیش رفت کی ٹریکنگ فعال ہو تو `enabled`                                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | جواب    | OmniRoute کے استعمال کردہ مؤثر سیشن ID                                                                                                                                                                                               |
| `X-OmniRoute-Request-Id` | جواب    | درخواست سے باہمی تعلق کا id (جب معلوم ہو)                                                                                                                                                                                            |
| `X-OmniRoute-Version`    | جواب    | OmniRoute کا بلڈ ورژن (ہمیشہ موجود)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | جواب    | HIT کی صورت میں کیش کے ذریعے بچائی گئی USD رقم (صرف کیش ہٹس)                                                                                                                                                                         |
| `X-OmniRoute-Decision`   | جواب    | روٹنگ ٹریس: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` کومبو حکمتِ عملی ہے، یا غیر کومبو درخواست کے لیے `single`) — تکمیل کے جوابات میں ہمیشہ موجود ہوتی ہے                                                       |

> Nginx نوٹ: اگر آپ underscore headers پر انحصار کرتے ہیں (مثلاً `x_session_id`)، تو `underscores_in_headers on;` فعال کریں۔

#### ہر درخواست کے لیے اکاؤنٹ پِن کرنا

جب کسی provider کے متعدد connections (اکاؤنٹس یا keys) ہوں، تو OmniRoute عموماً اپنی
account-selection strategy کے ذریعے ان میں سے ایک منتخب کرتا ہے۔ اس کے بجائے، کوئی درخواست
`x-omniroute-connection` header کے ذریعے کسی مخصوص connection کو پِن کر سکتی ہے:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id کہاں ملے گی۔** dashboard میں provider کا صفحہ کھولیں
  (**Dashboard → Providers → <provider>**) اور کسی connection کی row میں `xxxxxxxx…` id chip پر
  کلک کریں — اس سے مکمل connection id کاپی ہو جاتی ہے۔
- **کون سی درخواستیں اسے استعمال کرتی ہیں۔** `/v1/chat/completions`، `/v1/messages` اور
  `/v1/responses` پر single-model درخواستیں (`provider/model`)۔ Combos اس header کو نظر انداز کرتے ہیں:
  اس کے بجائے ہر combo step کے لیے اکاؤنٹ کو اسی step کے اپنے connection کے ذریعے پِن کریں۔
- **پِن سخت ہے، محض ترجیح نہیں۔** صرف پِن کیا ہوا connection استعمال کیا جاتا ہے۔ درخواست
  کے اندر ناکامی اکاؤنٹ کا cooldown ریکارڈ کرتی ہے، لیکن اسی provider کے کسی دوسرے اکاؤنٹ پر
  **منتقل نہیں** ہوتی۔
- **Cooldown اور quota پِن کو ختم کر دیتے ہیں۔** جب پِن کیا ہوا connection cooldown میں ہو،
  اس کا quota ختم ہو چکا ہو، یا اسے quota policy نے بلاک کیا ہو، تو بعد کی درخواستیں بالکل
  unpinned traffic کی طرح provider کے دیگر connections استعمال کرتی ہیں۔
- **نامعلوم یا غیر فعال ids ناکام ہو جاتی ہیں۔** ایسی id جو provider کے active pool میں موجود
  نہ ہو (حذف شدہ، غیر فعال، یا کسی دوسرے provider سے متعلق) کوئی اہل اکاؤنٹ باقی نہیں چھوڑتی،
  اس لیے درخواست خاموشی سے کہیں اور route ہونے کے بجائے ناکام ہو جاتی ہے۔

Claude Code، `ANTHROPIC_CUSTOM_HEADERS` کے ذریعے custom headers بھیجتا ہے۔ اسے
`~/.claude/settings.json` کے `env` block میں رکھیں، یا ہر project کے لیے مختلف اکاؤنٹ پِن کرنے
کی غرض سے project-level `.claude/settings.json` میں رکھیں:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ماخذ: `src/sse/handlers/chat.ts` (header پڑھنا)، `src/sse/services/auth.ts` اور
`src/sse/services/sessionAffinityPin.ts` (پِن کا خاتمہ اور pool میں غیر موجودگی کی جانچ)۔

> **لاگت کے telemetry headers:** کامیاب non-streaming responses میں `X-OmniRoute-*` کے cost-telemetry headers بھی شامل ہوتے ہیں — `X-OmniRoute-Response-Cost` (USD، 10 اعشاری مقامات پر مقرر؛ مفت یا غیر قیمت شدہ کے لیے `0.0000000000`)، `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`، `X-OmniRoute-Model`، `X-OmniRoute-Provider`، `X-OmniRoute-Latency-Ms`، `X-OmniRoute-Cache-Hit`، اور `X-OmniRoute-Fallback-Attempts` (صرف جب > 0 ہو)، نیز `X-OmniRoute-Request-Id` اور `X-OmniRoute-Version`۔ یہ chat completions، `/v1/responses`، `/v1/messages`، **اور media endpoints** سے بھی خارج کیے جاتے ہیں — `/v1/embeddings`، `/v1/images/generations`، `/v1/audio/speech`، `/v1/audio/transcriptions`، `/v1/rerank`، `/v1/videos/generations`، `/v1/music/generations`، اور `/v1/moderations` (لاگت ہمیشہ `0`)۔ جب pricing دستیاب ہو تو media کی لاگت ہر modality کے لحاظ سے (فی image، فی second، فی character، فی search-unit) شمار کی جاتی ہے، ورنہ `0` ہوتی ہے (fail-open)۔

> **Cache-hit کی لاگت کے معانی:** semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) پر کوئی upstream call نہیں کی جاتی، اس لیے `X-OmniRoute-Response-Cost` کی قدر `0.0000000000` ہوتی ہے (ہِٹ فراہم کرنے کی **اضافی** لاگت)۔ اصل/ممکنہ لاگت الگ سے `X-OmniRoute-Cost-Saved` میں رپورٹ کی جاتی ہے۔ Billing consumers کو `X-OmniRoute-Response-Cost` کا مجموعہ استعمال کرنا چاہیے (hits کی کوئی لاگت نہیں)؛ cache analytics میں `X-OmniRoute-Cost-Saved` کو جمع کیا جا سکتا ہے۔

## خصوصی زیرِ انتظام سیشن لیزز

خصوصی زیرِ انتظام سیشن لیزنگ ایک اختیاری، کلائنٹ سے غیر جانب دار روٹنگ معاہدہ ہے: ایک فعال مالک
ایک اہل OmniRoute کنکشن اپنے پاس رکھتا ہے۔ یہ کسی ماڈل کو لیز نہیں کرتا، OAuth کا تقاضا نہیں کرتا، کسی
مخصوص کلائنٹ کی شناخت نہیں کرتا، اور نہ ہی کسی مخصوص فراہم کنندہ کا تقاضا کرتا ہے۔

توثیق کرنے والی API کلید کے پاس `lease:exclusive` اسکوپ اور ایک واضح غیر خالی
`allowedConnections` فہرست ہونی چاہیے۔ ڈیٹابیس میوٹیشن باؤنڈری کلید کی تخلیق اور جزوی
اپ ڈیٹس، دونوں کے دوران ان دونوں فیلڈز کو ایک ساتھ نافذ کرتی ہے۔

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

کامیاب حصول، تجدید، اور اجرا کے جوابات ٹائم اسٹیمپس، `state`، اور عین مثبت
`generation` ظاہر کرتے ہیں، لیکن منتخب کردہ کنکشن یا اسناد کبھی ظاہر نہیں کرتے۔ تجدید اور اجرا
کے لیے generation کو JSON باڈی میں فراہم کیا جاتا ہے:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

ایک فعال لیز مالک اپنی موجودہ بائنڈنگ کے لیے واضح طور پر رازداری کے لحاظ سے محفوظ ڈسپلے میٹا ڈیٹا کی درخواست کر سکتا ہے:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

اس اختیاری اسٹیٹس ایکشن کو ایک ہی ڈیٹابیس ٹرانزیکشن میں مبہم مالک، توثیق شدہ زیرِ انتظام API کلید، اور عین
فعال generation کے ذریعے فینس کیا جاتا ہے۔ `displayName` صرف تراشا گیا، تشکیل کردہ
کنکشن نام ہوتا ہے؛ جب کوئی محفوظ تشکیل کردہ نام موجود نہ ہو تو یہ `null` ہوتا ہے۔ OmniRoute کبھی بھی
ای میل یا تیار کردہ اکاؤنٹ شناخت کو بطور متبادل استعمال نہیں کرتا۔ فراہم کنندہ کی قدر ایک غیر حساس ڈسپلے لیبل ہوتی ہے اور کبھی بھی
تیار کردہ ہم آہنگ فراہم کنندہ شناخت کار نہیں ہوتی۔ اسناد، ٹوکنز، کوکیز، خام کنکشن یا API
کلید ids، مالک ہیشز، فینسنگ راز، اور داخلی روٹنگ ڈیٹا شامل نہیں کیے جاتے۔

غلط کلید، غلط مالک، فرسودہ generation، غیر موجود، میعاد ختم شدہ، جاری کردہ، اور کالعدم شدہ تلاشیں سبھی
کنکشن میٹا ڈیٹا کے بغیر یکساں `409 LEASE_FENCE_STALE` خرابی واپس کرتی ہیں۔ جس کلائنٹ کو گنجائش کے انتظار کا جواب ملا ہو، اس کے پاس معائنہ کرنے کے لیے کوئی فعال بائنڈنگ نہیں ہوتی۔ جب روٹنگ کسی فعال لیز کو منتقل کرتی ہے،
تو وہی generation معتبر رہتا ہے اور اسٹیٹس اٹامک طور پر نئی بائنڈنگ واپس کرتا ہے، پرانی کبھی نہیں۔
موجودہ کلائنٹس میں کوئی تبدیلی نہیں آتی کیونکہ حصول، تجدید، اجرا، اور انتظار کے جوابات اپنی
پچھلی ساخت برقرار رکھتے ہیں۔

یہ سرور معاہدہ اسٹاک OpenAI Codex `/status` کو تبدیل نہیں کرتا۔ اسٹاک Codex فی الحال اپنے
ماڈل فراہم کنندہ اور پہلے سے شامل توثیقی/اکاؤنٹ حالت کی اطلاع دیتا ہے، لیکن من مانا کسٹم
فراہم کنندہ اکاؤنٹ میٹا ڈیٹا رینڈر نہیں کرتا؛ مستقبل کی کلائنٹ انٹیگریشن کو یہ ایکشن کال کرنا اور یہ طے کرنا ہوگا کہ
`connection.displayName` کیسے دکھایا جائے۔

اس کے بعد ہر زیرِ انتظام انفرنس درخواست دونوں کنٹرول ہیڈرز فراہم کرتی ہے:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ہر معاونت یافتہ اپ اسٹریم کوشش سے فوراً پہلے عین مالک، generation، فعال کنکشن، اور توثیق شدہ API کلید
کو فینس کیا جاتا ہے۔ کسی دوسری کلید کے ساتھ مالک اور generation کو دوبارہ استعمال کرنا اس وقت بھی ناکام رہتا ہے
جب وہ کلید اسی کنکشن کی اجازت دیتی ہو۔ خام مالکان کو مستقل طور پر محفوظ، لاگ، درخواست کے اسنیپ شاٹ میں برقرار،
یا اپ اسٹریم فارورڈ نہیں کیا جاتا۔

عارضی مسابقت HTTP `429` کو `Retry-After` اور درج ذیل کے ساتھ واپس کرتی ہے:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

اس جواب کا مطلب صرف یہ ہے کہ معمول کا اہل مجموعہ غیر خالی تھا اور ہر دستیاب امیدوار
کسی دوسرے فعال لیز کے زیرِ قبضہ تھا۔ غیر معاونت یافتہ ماڈلز/فراہم کنندگان، پالیسی عدم مطابقت، کول ڈاؤن، کوٹا،
صحت، اور دیگر معمول کی اہلیت کی ناکامیاں اپنے موجودہ OmniRoute جوابات برقرار رکھتی ہیں۔

### `x-omniroute-compression`

کمپریشن پلان کی فی درخواست اوور رائیڈ۔ اسے سب سے زیادہ ترجیح حاصل ہے — یہ روٹنگ-کومبو
اوور رائیڈ، فعال پروفائل، خودکار ٹریگر، اور پینل Default پر فوقیت رکھتی ہے۔ اقدار:

| قدر           | اثر                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------- |
| `off`         | اس درخواست کے لیے کوئی کمپریشن نہیں۔                                                              |
| `default`     | پینل سے اخذ کردہ Default پروفائل (فعال پروفائل کو نظر انداز کرتا ہے)۔ نقصان دہ انجن بند رہتے ہیں۔ |
| `safe`        | صرف ڈی ڈپلیکیشن اور وائٹ اسپیس فولڈنگ۔                                                            |
| `allow-lossy` | اس درخواست کے لیے آپریٹر پلان برقرار رکھیں، بشمول خلاصے اور اسلوب کی دوبارہ تحریر۔                |
| `engine:<id>` | فعال ہونے پر ایک واحد انجن، مثلاً `engine:rtk`۔ اس انجن کے لیے فی درخواست اختیاری شمولیت۔         |
| `<combo>`     | ایک نام زد کومبو، پہلے نام (حروف کی نوعیت سے غیر حساس) اور پھر id سے مماثل کیا جاتا ہے۔           |

نوٹس:

- نامعلوم اقدار کو نظر انداز کر دیا جاتا ہے (درخواست کبھی مسترد نہیں ہوتی)؛ تعین معمول کی آپریٹر ترجیح کے مطابق جاری رہتا ہے۔
- اگر متعدد کومبوز کا ایک ہی نام ہو تو یقینی مماثلت کے لیے کومبو **id** فراہم کریں۔
- ایسا کومبو جس کا نام `off` یا `default` ہو، نام کے ذریعے منتخب نہیں کیا جا سکتا (ان کلیدی الفاظ کی پہلے تشریح کی جاتی ہے)؛ ایسے کومبو کا حوالہ اس کے id سے دیں۔
- ماسٹر کمپریشن سوئچ ایک قطعی رکاوٹ ہے: جب کمپریشن عالمی طور پر غیر فعال ہو، تو یہ ہیڈر اسے فعال نہیں کر سکتا۔

لاگو شدہ پلان کو رسپانس ہیڈر میں واپس دہرایا جاتا ہے:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

جہاں `<source>`، `request-header`، `routing-override`، `active-profile`، `auto-trigger`، `default`، یا `off` میں سے ایک ہوتا ہے۔

## ایمبیڈنگز

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

دستیاب فراہم کنندگان: Nebius، OpenAI، Mistral، Together AI، Fireworks، NVIDIA، **OpenRouter**، Jina AI۔

کیٹلاگ ids کی شکل `provider/model` ہے (مثال: `jina-ai/jina-embeddings-v5-omni-small`)۔ رجسٹری میں موجود صرف Jina model ids بھی resolve ہو جاتے ہیں (مثلاً `jina-embeddings-v5-text-small`، `jina-reranker-v3.5`)۔ Jina embed/rerank/classify/segment پہلے ڈیش بورڈ کے `jina-ai` credentials استعمال کرتے ہیں؛ `JINA_AI_API_KEY` صرف اس صورت میں fallback ہے جب ڈیش بورڈ key موجود نہ ہو۔ `jina-reader` کارڈ صرف Reader / `r.jina.ai` کے لیے ہے (`POST /v1/web/fetch`) اور کبھی embeddings یا rerank فراہم نہیں کرتا۔

وہ رجسٹری ماڈلز جو multimodal معاونت ظاہر کرتے ہیں، فراہم کنندہ سے غیر جانب دار زیادہ سے زیادہ 32 ساختہ
items بھی قبول کرتے ہیں۔ میڈیا item کی اقسام `text`، `image`، `audio`، `video`، اور `document` ہیں۔ ان کا میڈیا `source`
یا تو `{"type":"url","url":"https://..."}` ہوتا ہے یا
`{"type":"base64","data":"...","media_type":"..."}`۔

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`، `jina-ai/jina-embeddings-v5-omni-nano`،
اور family alias `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina کی مقامی
EmbeddingsV5Request دستاویزات بھی قبول کرتا ہے اور انہیں **بغیر کسی تبدیلی کے آگے بھیجتا ہے** `https://api.jina.ai/v1/embeddings` پر:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

مقامی `{ image | audio | video | pdf }` اقدار ایک عوامی HTTPS URL، ایک `data:` URI، یا خام
base64 ہو سکتی ہیں۔ OmniRoute ان objects کو string میں تبدیل نہیں کرتا اور نہ ہی مقامی image URLs حاصل کرتا ہے — Jina
عوامی میڈیا خود حاصل کرتا ہے۔ اضافی Jina fields (`task`، `normalized`، `truncate`، `embedding_type`) کو
آگے بھیج دیا جاتا ہے۔ صرف متن والے Jina SKUs اب بھی غیر متنی دستاویزات مسترد کرتے ہیں۔

سکیورٹی اور ترسیل کی حدود:

- ریموٹ میڈیا URLs لازماً عوامی HTTPS ہونے چاہییں۔ کینونیکل `{type,source:url}` items کو
  سرور کی جانب سے حاصل کیا جاتا ہے (redirect کی دوبارہ توثیق، timeout، حجم کی حدود، عوامی DNS، connection pinning) اور
  فراہم کنندہ کو call کرنے سے پہلے inline کر دیا جاتا ہے۔ Jina کے مقامی `{image:"https://..."}` items کو
  اسی عوامی HTTPS جانچ کے بعد جوں کا توں آگے بھیج دیا جاتا ہے؛ Jina URL حاصل کرتا ہے۔
- Inline base64 میڈیا کی حد فی item decode ہونے کے بعد 8 MiB اور پوری درخواست میں decode ہونے کے بعد 16 MiB ہے۔

فراہم کنندہ کے لیے ترجمہ (کینونیکل items کبھی بھی بغیر تبدیلی کے آگے نہیں بھیجے جاتے):

- Jina multimodal ماڈلز: ہر اعلیٰ سطحی item ایک modality-keyed object بن جاتا ہے
  (`text` / `image` / `audio` / `video` / `pdf`) جس میں inline میڈیا کے لیے data URIs استعمال ہوتے ہیں؛ ہر
  اعلیٰ سطحی item کے لیے ایک vector۔
- Gemini Embedding 2 family: ایک اعلیٰ سطحی array ایک واحد مقامی
  `models/{model}:embedContent` درخواست بن جاتی ہے، جس میں `content.parts` (`text` یا `inline_data`) ہوتے ہیں۔
- llama.cpp (`llama-cpp/<model>`، کوئی بھی ماڈل جسے مقامی سرور نے load کیا ہو): کینونیکل `text` items
  سادہ strings بن جاتے ہیں، جبکہ `image` / `audio` / `video` میں سے ہر ایک ایک
  `{"content": [part]}` object بن جاتا ہے، جو inline data کے ساتھ llama-server کے chat content parts (`image_url`،
  `input_audio` جس کا format `wav` / `mp3` / `flac` ہو، `input_video`) استعمال کرتا ہے؛ ہر اعلیٰ سطحی
  item کے لیے ایک vector۔ سرور کو `--embedding --mmproj …` کے ساتھ چلنا چاہیے؛ projector کے بغیر وہ
  میڈیا کو خود مسترد کر دیتا ہے۔ `document` معاونت یافتہ نہیں ہے۔
- واضح modality metadata کے بغیر نامعلوم/dynamic ماڈلز، ساختہ input کو HTTP 400 کے ساتھ مسترد کرتے ہیں۔

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

غیر معاون model/modality امتزاج، item کو زبردستی تبدیل کرنے کے بجائے HTTP 400 واپس کرتے ہیں۔ پرانی string/token درخواستوں کے non-input
extension fields بغیر تبدیلی کے آگے بھیجے جاتے ہیں۔

```bash
# تمام embedding ماڈلز کی فہرست دکھائیں
GET /v1/embeddings
```

```bash
}
```

دستیاب فراہم کنندگان میں OpenAI (GPT Image 2)، xAI (Grok Image)، Together AI (FLUX)، Fireworks AI، Nebius (FLUX)، Hyperbolic، NanoBanana، **OpenRouter**، **ZenMux**، SD WebUI (مقامی)، اور ComfyUI (مقامی) شامل ہیں۔

`n`، `data[]` میں `n` تصاویر واپس کرتا ہے۔ جن فراہم کنندگان کی upstream API ہر کال پر ایک تصویر واپس کرتی ہے
(Black Forest Labs، Stability AI، Leonardo، Ideogram، Haiper، Hyperbolic، Magnific/Freepik،
NVIDIA NIM، Cloudflare Workers AI)، ان کے لیے `n` الگ upstream کالز کی جاتی ہیں، جن میں زیادہ سے زیادہ 4 بیک وقت جاری رہتی ہیں۔ ایک
مقررہ `seed` کو کال انڈیکس کے مطابق offset کیا جاتا ہے (`seed`، `seed + 1`، …)، لہٰذا تصاویر مختلف ہوتی ہیں لیکن
دوبارہ اسی طرح تیار کی جا سکتی ہیں۔ `n` کی زیادہ سے زیادہ حد 10 ہے۔ اگر کوئی بھی کال ناکام ہو جائے تو پوری درخواست
ناکام ہو جاتی ہے۔ fan-out فارمیٹس کی فہرست `SINGLE_IMAGE_FANOUT_FORMATS` میں
`open-sse/handlers/imageGeneration/fanOut.ts` پر موجود ہے۔

ZenMux موجودہ API-key کنکشن کو دوبارہ استعمال کرتا ہے اور `zenmux/` یا `zm/` سابقے قبول کرتا ہے:

- `zenmux/openai/gpt-image-2`، ZenMux کی OpenAI Images API استعمال کرتا ہے۔ اختیارات میں `size`،
  `quality`، `n`، `output_format`، `output_compression`، `background`، اور `response_format` شامل ہیں۔
- دیگر پبلشرز، مثلاً `zm/meta/muse-image-1.0`، ZenMux کا Vertex AI `:predict`
  endpoint استعمال کرتے ہیں۔ `n` کو `sampleCount`، `aspect_ratio` کو `aspectRatio`، اور `image_size`
  (`1K`، `2K`، `4K`) کو `sampleImageSize` سے map کیا جاتا ہے۔ پکسل `size` صرف aspect ratio فراہم کرتا ہے،
  یقینی پکسل ابعاد نہیں۔ معاونت یافتہ ratios، resolutions، اور counts ماڈل کے لحاظ سے مختلف ہوتے ہیں۔
- `zm/inclusionai/ming-image-0.1-design` اپنے ابعاد خود منتخب کرتا ہے۔ `size`،
  `aspect_ratio`، اور `image_size` شامل نہ کریں؛ واضح اقدار HTTP 400 واپس کرتی ہیں۔ PNG، JPEG، اور WebP
  کی درخواست `output_format` کے ذریعے کی جا سکتی ہے۔

یہ integration متن سے تصویر بنانے کی معاونت کرتا ہے، reference-image editing کی نہیں۔ Vertex
output کو `data[].b64_json` میں normalize کیا جاتا ہے؛ `response_format: "url"` ایک upstream
HTTPS URL، یا صرف image bytes دستیاب ہونے کی صورت میں base64 data URL واپس کرتا ہے۔ خالی/فلٹر شدہ outputs
خالی کامیاب جواب کے بجائے ایک خرابی واپس کرتے ہیں۔ ماڈل تک رسائی ZenMux اکاؤنٹ پر منحصر ہے۔
[ZenMux کی Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) اور
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) دیکھیں۔

```bash
# تمام image models کی فہرست دکھائیں
GET /v1/images/generations
```

## دستاویز OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` ایک `provider/model` سابقے کے ذریعے OCR فراہم کنندہ منتخب کرتا ہے؛ صرف model id (مثلاً
`mistral-ocr-latest`) اپنے رجسٹرڈ فراہم کنندہ سے resolve ہوتی ہے، جبکہ `model` شامل نہ کرنے پر
Mistral (`mistral-ocr-latest`) بطور ڈیفالٹ استعمال ہوتا ہے۔ رجسٹرڈ فراہم کنندگان (`open-sse/config/ocrRegistry.ts`):

| فراہم کنندہ id                | ماڈل id              | `model` کی قدر                                             | نوٹس                                                                                                            |
| ----------------------------- | -------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (یا صرف `mistral-ocr-latest`) | Synchronous — جواب براہ راست واحد upstream کال سے واپس کیا جاتا ہے۔                                             |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                | Asynchronous upstream (`analyze` + poll) — ذیل میں دیکھیں۔                                                      |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                    | Synchronous، Vertex AI کے `openapi/chat/completions` پارٹنر endpoint کے ذریعے — auth/URL کے لیے ذیل میں دیکھیں۔ |

تینوں فراہم کنندگان ایک ہی Mistral طرز کی body میں جواب دیتے ہیں:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence کا poll flow

Azure Document Intelligence کی `analyze` API asynchronous ہے: ابتدائی درخواست body کے بجائے ایک
`Operation-Location` header واپس کرتی ہے، اور نتیجہ حاصل کرنے کے لیے polling ضروری ہے۔ handler
(`open-sse/handlers/ocr.ts`) اس URL کو ہر سیکنڈ میں، زیادہ سے زیادہ 30 کوششوں تک poll کرتا ہے، کسی non-`ok`
poll جواب یا `"failed"` status پر فوری طور پر ناکام ہو جاتا ہے (polling جاری نہیں رکھتا)، اور اگر کوششوں کی
حد ختم ہونے کے بعد بھی operation جاری ہو تو `504` واپس کرتا ہے۔ آخری Azure جواب کو caller کو واپس کرنے سے پہلے
اسی `pages`/`markdown` ساخت میں normalize کیا جاتا ہے جو Mistral استعمال کرتا ہے، لہٰذا client code کو
فراہم کنندہ کے لیے کوئی خصوصی صورت الگ سے سنبھالنے کی ضرورت نہیں ہوتی۔

### Vertex AI DeepSeek OCR کی auth اور endpoint resolution

`vertex-deepseek-ocr` وہی Vertex AI authentication دوبارہ استعمال کرتا ہے جس کی OmniRoute پہلے ہی
chat/image ٹریفک کے لیے معاونت کرتا ہے (`open-sse/executors/vertex.ts`): کنکشن کی API key یا تو
Service Account JSON credential ہوتی ہے (جسے JWT-bearer flow کے ذریعے مختصر مدت کے OAuth access token
سے تبدیل کیا جاتا ہے)، یا پہلے سے جاری کردہ OAuth access token ہوتا ہے، جسے جوں کا توں استعمال کیا جاتا ہے۔
upstream endpoint URL، Vertex کا عمومی `openapi/chat/completions` پارٹنر endpoint ہے، جو کنکشن کے project اور
region سے بنایا جاتا ہے — واضح `providerSpecificData.project`/`providerSpecificData.region` کو ہمیشہ ترجیح دی جاتی ہے؛
بصورت دیگر project، Service Account JSON کے `project_id` سے اخذ کیا جاتا ہے اور region
بطور ڈیفالٹ `us-central1` ہوتا ہے۔ دونوں resolutions، `open-sse/handlers/ocr.ts` میں انجام پاتی ہیں
(`resolveVertexOcrAccessToken`، `resolveVertexOcrBaseUrl`)، جنہیں
`src/app/api/v1/ocr/route.ts`، `handleOcr` کو dispatch کرنے سے پہلے استعمال کرتا ہے۔

## ماڈلز کی فہرست

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ تمام چیٹ، ایمبیڈنگ، اور امیج ماڈلز + کومبوز کو OpenAI فارمیٹ میں لوٹاتا ہے
```

### ماڈل کی قیمتیں (`pricing`)

جب OmniRoute کو ماڈل کی قیمت معلوم ہو تو اندراج میں ایک `pricing` آبجیکٹ شامل ہوتا ہے۔ قیمت اس پرائسنگ ٹیبل
سے آتی ہے جسے لاگت کا حساب کتاب استعمال کرتا ہے: بلٹ اِن ڈیفالٹس، مطابقت پذیر قیمتیں، اور
`/api/pricing` کے ذریعے مقرر کردہ اوور رائیڈز۔ یہ فہرستی قیمتیں ہیں، لہٰذا سبسکرپشن فراہم کنندگان بھی
فی ٹوکن قیمت دکھاتے ہیں۔

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| فیلڈز                                                           | اکائی                      | نوٹس                                                                                                                                                             |
| --------------------------------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | فی ٹوکن USD، اعشاری اسٹرنگ | OpenRouter سے ہم آہنگ، کبھی exponent notation میں نہیں۔ دونوں کیش فیلڈز صرف اس وقت ظاہر ہوتے ہیں جب کیش کی قیمت موجود ہو۔                                        |
| `input`, `output`, `cached`, `cache_creation`                   | فی 1M ٹوکنز USD، عدد       | کیٹلاگ کے سابقہ ورژنز کے فیلڈز، موجودہ کلائنٹس کے لیے برقرار رکھے گئے ہیں۔ جب پرائسنگ قطار میں `reasoning` اور `long_context` موجود ہوں تو وہ بھی ظاہر ہوتے ہیں۔ |

- **کومبوز** اپنے پہلے دکھائی دینے والے ہدف کی قیمت رکھتے ہیں۔ بلٹ اِن `auto/*` کومبوز درخواست کے وقت
  ہدف منتخب کرتے ہیں، اس لیے ان میں `pricing` نہیں ہوتا۔
- **مفت ماڈلز** کی قیمت صفر ہونے پر `"0"` (اور `0`) دکھایا جاتا ہے۔ ایسا ماڈل جس کی کوئی پرائسنگ قطار نہ ہو
  وہ بھی `"0"` دکھاتا ہے، اگر کیٹلاگ اسے مفت (`free: true`) قرار دیتا ہو یا بلٹ اِن مفت ماڈلز کے
  کیٹلاگ میں وہ شامل ہو۔
- **نامعلوم قیمت:** اندراج میں `pricing` کلید موجود نہیں ہوتی۔
- **کریڈٹ کے حساب سے میٹر کیے گئے فراہم کنندگان** (جیسے Kiro) فی ٹوکن کے بجائے فی درخواست بل کرتے ہیں۔ ان کے
  اندراجات میں پہلے سے موجود عددی فی-1M فیلڈز برقرار رہتے ہیں اور ان میں فی ٹوکن اسٹرنگ فیلڈز نہیں ہوتے۔
- **ویریئنٹس** (reasoning-effort ids، no-thinking aliases، discovery اور gateway mirrors)
  اس ماڈل کی قیمت نقل کرتے ہیں جس کی طرف وہ روٹ کرتے ہیں۔
- فیلڈز صرف بنیادی نرخ رکھتے ہیں۔ Long-context tiers (عددی `long_context` فیلڈ) اور
  service-tier multipliers (مثلاً Codex fast یا flex) `prompt` یا
  `completion` کو تبدیل نہیں کرتے۔
- یہ آبجیکٹ توثیق کے ہر انداز کے لیے یکساں ہے، بشمول Anthropic طرز کی
  `x-api-key` اور `anthropic-version` والی درخواست کے (جواب بدستور `{ "object": "list",
"data": [...] }` رہتا ہے)۔ نفاذ: `src/app/api/v1/models/catalogPricing.ts`۔

### ماڈل id کے سابقے (`?prefix=`)

زیادہ تر ماڈلز کی تشہیر ایک **فراہم کنندہ سابقے** کے تحت کی جاتی ہے۔ آپ کو کون سا سابقہ ملتا ہے، اسے
`MODELS_CATALOG_PREFIX_MODE` فیچر فلیگ کنٹرول کرتا ہے، اور اسے ایک query parameter کے ذریعے **فی درخواست**
اوور رائیڈ کیا جا سکتا ہے — یہ ایسے کلائنٹ کے لیے مفید ہے جو ہر کسی کے لیے سرور کی مجموعی
ترتیب تبدیل کیے بغیر ایک صاف فہرست چاہتا ہو:

```bash
GET /v1/models?prefix=alias        # فی ماڈل ایک id — مختصر alias سابقہ
GET /v1/models?prefix=dual         # دونوں صورتیں (سرور کا ڈیفالٹ)
GET /v1/models?prefix=canonical    # صرف مکمل provider-id سابقہ
```

| موڈ         | اخراج                                                     | نوٹس                                                                                                                                                                                                 |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **اور** `claude/claude-sonnet-4-6` | **ڈیفالٹ۔** دونوں ids ایک ہی ماڈل کی طرف روٹ کرتے ہیں؛ اسے اس لیے برقرار رکھا گیا ہے تاکہ کسی بھی صورت کو hardcode کرنے والی کلائنٹ کنفیگریشنز کام کرتی رہیں۔ یہ کیٹلاگ کو تقریباً دوگنا کر دیتا ہے۔ |
| `alias`     | `cc/claude-sonnet-4-6`                                    | فی ماڈل ایک اندراج۔ الگ alias نہ رکھنے والے فراہم کنندگان بھی اپنا اندراج خارج کرتے ہیں، اس لیے کچھ ضائع نہیں ہوتا۔                                                                                  |
| `canonical` | `claude/claude-sonnet-4-6`                                | مکمل provider-id سابقے کے تحت فی ماڈل ایک اندراج۔ الگ alias نہ رکھنے والے فراہم کنندگان (مثلاً `antigravity/…`، `agy/…`) بھی یہاں اپنا واحد id خارج کرتے ہیں، اس لیے کچھ ضائع نہیں ہوتا۔             |

`dual` موڈ کے mirror کو query parameter کے بغیر بھی پہچانا جا سکتا ہے: اس میں بنیادی id کی طرف اشارہ کرنے والا `parent`
فیلڈ ہوتا ہے۔

ماڈل چننے والا انٹرفیس رینڈر کرنے والے کلائنٹس کو `?prefix=alias` کی درخواست کرنی چاہیے — یہی کام
[OmniCopilot VS Code ایکسٹینشن](../guides/VSCODE-COPILOT.md) کرتی ہے۔

### دریافت کے فلٹرز (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` اختیاری دریافت کے فلٹرز قبول کرتا ہے۔ ان میں سے کسی کے بغیر جواب
تبدیل نہیں ہوتا۔ یہ اس کیٹلاگ کو محدود کرتے ہیں جو کالر پہلے ہی دیکھ سکتا ہے (API-key اجازتیں پہلے لاگو ہوتی ہیں)،
اور یہ OpenAI طرز کی `limit` / `after` پیجنگ سے پہلے چلتے ہیں:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # فہرست میں شامل ہر صلاحیت true ہونی چاہیے
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # کیٹلاگ `type`؛ اس کے بغیر قطاریں `chat` ہیں
GET /v1/models?q=sonnet&limit=10                           # id یا نام پر حروف کی صورت سے غیر حساس مماثلت
```

| پیرامیٹر      | اقدار                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`، `reasoning`، `structured_output`، `temperature`، `thinking`، `tool_calling`، `vision` |
| `min_context` | غیر منفی صحیح عدد، جس کا موازنہ `context_length` سے کیا جاتا ہے                                     |
| `kind`        | `chat`، `audio`، `embedding`، `image`، `moderation`، `music`، `rerank`، `video`                     |
| `q`           | 1–200 حروف                                                                                          |

کوئی نامعلوم قدر، یا ایسا `min_context` جو غیر منفی صحیح عدد نہ ہو (مثلاً `1.5`)،
HTTP `400` واپس کرتا ہے اور پیغام میں درست اقدار درج ہوتی ہیں۔ نفاذ:
`src/app/api/v1/models/catalogFilters.ts`۔

### ماڈلز کی مختصر فہرست (`POST /v1/models/query`)

`POST /v1/models/query` اسی کیٹلاگ سے ایک مختصر، قطعی فہرست واپس کرتا ہے، جس میں وہی
توثیق اور فی کلید مرئیت ہوتی ہے جو `GET /v1/models` میں ہے:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ہر فیلڈ اختیاری ہے۔ `capabilities` اور `exclude` ایک ارے یا کوما سے علیحدہ کردہ اسٹرنگ قبول کرتے ہیں؛
`max_output` کا موازنہ `max_output_tokens` سے کیا جاتا ہے۔ نتائج پہلے `owned_by`، پھر `id` کے لحاظ سے ترتیب دیے جاتے ہیں۔
`limit` کی ڈیفالٹ قدر `20` ہے اور `100` سے زیادہ اقدار کو `100` تک محدود کر دیا جاتا ہے۔ غلط JSON، کوئی نامعلوم
فیلڈ یا کوئی غلط قدر HTTP `400` واپس کرتی ہے۔

### انفرادی طور پر مخفی چیٹ ماڈلز

اپنے فراہم کنندہ کے صفحے پر **مخفی** نشان زد ماڈل کو کیٹلاگ سے خارج کر دیا جاتا ہے اور واضح طور پر
درخواست کیے جانے پر اسے HTTP `404` / `model_not_found` کے ساتھ مسترد کر دیا جاتا ہے۔ یہ جانچ طے شدہ
فراہم کنندہ اور ماڈل کو استعمال کرتی ہے، جس میں فراہم کنندہ کے عرف، ہم آہنگ فراہم کنندہ کے نوڈ سابقے، اور
کنکشن کی ڈیفالٹ اقدار شامل ہیں۔ کوئی کومبو مخفی اہداف کو چھوڑ دیتا ہے اور کسی مرئی متبادل کو استعمال کر سکتا ہے؛ جب کوئی
قابلِ عمل ہدف باقی نہ رہے تو یہ وہی خرابی کوڈ واپس کرتا ہے۔ مخفی حالت ختم کرنے کا اثر اگلی
درخواست پر ہوتا ہے۔ صرف تصویر سے متعلق مرئیت کی اوور رائیڈز اسی ID والے چیٹ ماڈل کو مخفی نہیں کرتیں۔

یہ انفرادی ماڈل ترتیب
[ماڈل کی نمائش کی اجازت/ممانعت کی فہرستوں](../routing/MODEL_EXPOSURE_LIST.md) سے الگ ہے، جو واضح ڈسپیچ برقرار رکھتے ہوئے کیٹلاگ
میں تشہیر اور خودکار روٹنگ کے امیدواروں کو فلٹر کرتی ہیں۔ API کلید کی ماڈل اجازتیں بدستور آزادانہ طور پر لاگو ہوتی ہیں۔
ڈیفالٹ کیٹلاگ سابقہ موڈ `dual` ہی رہتا ہے۔

### بغیر سوچ کے ماڈل ویریئنٹس

سوچنے کی صلاحیت رکھنے والے Claude ماڈلز کے لیے، `/v1/models` ایک **بغیر سوچ** ویریئنٹ بھی مشتہر کرتا ہے جس کی id کے شروع میں `claude-3-omniroute-no-thinking/` سابقہ لگایا جاتا ہے:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

اس id کو منتخب کرنے سے (مثلاً ایسی Claude Code کنفیگریشن میں جو ہمیشہ `thinking` بلاک منسلک کرتی ہے) یہ استدلال کو دبانے کے ساتھ حقیقی `<provider>/<model>` پر واپس ریزولو ہو جاتا ہے — `/v1/messages` پاتھ پر `thinking:{type:"disabled"}`، یا `/v1/chat/completions` پاتھ پر `reasoning`/`reasoning_effort` فیلڈز کو حذف کر کے۔ یہ ویریئنٹ صرف Claude خاندان کے ان ماڈلز کے لیے فہرست میں شامل کیا جاتا ہے جو سوچنے کی معاونت کرتے **اور** `disabled` کا احترام کرتے ہیں (لہٰذا، مثلاً صرف اڈاپٹیو ماڈلز جو `disabled` کو مسترد کرتے ہیں، خارج کر دیے جاتے ہیں)۔ آپریٹرز `ModelSpec.noThinkingAlias` کے ذریعے ہر ماڈل کے لیے اس ویریئنٹ کو فعال یا غیر فعال کرنے پر مجبور کر سکتے ہیں۔

## ElevenLabs آڈیو جنریشن

اپنی ElevenLabs API کلید کے ساتھ OmniRoute میں ایک `elevenlabs` پرووائیڈر کنکشن کنفیگر کریں۔
کلائنٹس اپنی **OmniRoute** کلید (`Authorization: Bearer $OMNIROUTE_API_KEY`) سے توثیق کرتے ہیں؛
گیٹ وے محفوظ شدہ پرووائیڈر کلید کو `xi-api-key` کے طور پر فراہم کرتا ہے۔ ElevenLabs کلید کو کبھی بھی گیٹ وے بیئرر ٹوکن کے طور پر نہ بھیجیں۔

| طریقہ | پاتھ                        | رسپانس                                 | API کلید اینڈ پوائنٹ زمرہ |
| ----- | --------------------------- | -------------------------------------- | ------------------------- |
| POST  | `/v1/sound-generation`      | مقامی آڈیو بائٹس                       | `elevenlabs`              |
| POST  | `/v1/music`                 | مقامی آڈیو بائٹس                       | `music`                   |
| POST  | `/v1/music/stream`          | اسٹریمنگ آڈیو بائٹس                    | `music`                   |
| POST  | `/v1/music/detailed`        | مقامی ملٹی پارٹ آڈیو اور کمپوزیشن پلان | `music`                   |
| POST  | `/v1/music/detailed/stream` | مقامی SSE میٹا ڈیٹا اور آڈیو چنکس      | `music`                   |
| POST  | `/v1/music/plan`            | JSON کمپوزیشن پلان                     | `music`                   |

یہ اینڈ پوائنٹس موجودہ `/v1/audio/speech`، `/v1/audio/transcriptions`،
`/v1/voices`، `/v1/text-to-speech/{voiceId}` اور `/v1/speech-to-text` روٹس کی تکمیل کرتے ہیں۔ مقامی JSON فیلڈز
اور کوئری پیرامیٹرز، جیسے `output_format` اور `enable_logging`، محفوظ رکھے جاتے ہیں۔
`/v1/music/detailed` کے رسپانسز اپنی ملٹی پارٹ حدود برقرار رکھتے ہیں؛ انہیں ملٹی پارٹ کے طور پر پارس کریں۔
`/v1/music/detailed/stream` کمپوزیشن میٹا ڈیٹا اور SSE ایونٹس میں
base64 آڈیو چنکس کے ساتھ `text/event-stream` واپس کرتا ہے۔ تمام چھ روٹس CORS پری فلائٹ کو سپورٹ کرتے ہیں۔

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# ایک مختصر صوتی اثر۔ دورانیہ: 0.5 سے 30 سیکنڈ۔
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# موسیقی کا دورانیہ ملی سیکنڈز میں ظاہر کیا جاتا ہے: 3000 سے 600000۔
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

آڈیو کی تدریجی ترسیل کے لیے اسی JSON باڈی کے ساتھ `/v1/music/stream` استعمال کریں۔ کمپوزیشن
`prompt` یا `composition_plan` میں سے ٹھیک ایک کو قبول کرتی ہے؛ `/v1/music/plan` کے لیے `prompt`
درکار ہے اور یہ اختیاری طور پر `source_composition_plan` قبول کرتا ہے۔ مقامی اسکیماز اضافی
پرووائیڈر فیلڈز محفوظ رکھتے ہیں تاکہ کمپوزیشن پلان کے ورژنز اور فائن ٹیوننگ کے اختیارات ElevenLabs تک پہنچ سکیں۔

متحد `/v1/music/generations` اینڈ پوائنٹ `elevenlabs/music_v1`،
`elevenlabs/music_v2` اور `elevenlabs/music_v2_5` بھی قبول کرتا ہے۔ فعال ElevenLabs کنکشن کے ساتھ،
یہ ماڈلز میوزک کیٹلاگ میں دستیاب ہوتے ہیں۔ یہ اینڈ پوائنٹ
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` واپس کرتا ہے۔ اس کا `duration` فیلڈ
سیکنڈز میں ہوتا ہے اور `music_length_ms` سے میپ ہوتا ہے؛ واضح طور پر دیا گیا `music_length_ms` ترجیح رکھتا ہے۔
`instrumental`، `force_instrumental` سے میپ ہوتا ہے، جبکہ مقامی فیلڈ کو ترجیح حاصل ہوتی ہے۔
اسٹریمنگ کے لیے مقامی اسٹریمنگ اینڈ پوائنٹس اور صرف کمپوزیشن پلان سے چلنے والی ریکویسٹس کے لیے مقامی کمپوزیشن اینڈ پوائنٹ استعمال کریں۔

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

اپ اسٹریم کال سے پہلے اینڈ پوائنٹ، ماڈل، بجٹ اور کنکشن کی پابندیاں لاگو ہوتی ہیں۔ مقامی
روٹس اپ اسٹریم اسٹیٹس کوڈز اور ایرر باڈیز کو بغیر تبدیلی کے واپس کرتے ہیں، جن میں پلان
کی پابندی کے لیے `402` اور کوٹا کی حد کے لیے `429` شامل ہیں۔ دستیاب ہونے پر `character-cost`، `song-id`، `request-id` اور `retry-after`
ہیڈرز محفوظ رکھے جاتے ہیں۔ مفت کریڈٹ بیلنس ہر میوزک ماڈل، آؤٹ پٹ فارمیٹ یا API فیچر تک رسائی کی ضمانت نہیں دیتا: ElevenLabs ہر ریکویسٹ کے لیے استحقاق کا فیصلہ کرتا ہے۔
متحد اینڈ پوائنٹ OmniRoute کے معمول پر لائے گئے ایرر انویلپ میں ایرر اسٹیٹس کوڈز محفوظ رکھتا ہے۔

اپ اسٹریم معاہدے: [صوتی اثرات](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)،
[میوزک کمپوزیشن](https://elevenlabs.io/docs/api-reference/music/compose) اور
[اسٹریمنگ میوزک کی تفصیلات](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)۔

تمام POST روٹس ایک ہی ساخت کی پیروی کرتے ہیں: `Bearer your-api-key` + Zod سے توثیق شدہ JSON باڈی (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` وغیرہ، `src/shared/validation/schemas.ts` دیکھیں)۔ اسکیما کی ناکامی پر 4xx واپس کیا جاتا ہے۔

جو کلائنٹس `Authorization: Bearer ...` منسلک نہیں کر سکتے، ان کے لیے OmniRoute یو آر ایل میں API کیز بھی قبول کرتا ہے، یا تو query-string مطابقت (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) کے ذریعے، یا ذیل میں دستاویزی مخصوص `/api/v1/vscode/{token}/...` اینڈ پوائنٹس کے ذریعے۔

```bash
# Rerank (کلاؤڈ رجسٹری فراہم کنندہ، یا "<prefix>/<model>" کی صورت میں OpenAI سے مطابقت رکھنے والا فراہم کنندہ نوڈ)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina classify (Foundation API اسناد)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina segmenter
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina search (s.jina.ai؛ فراہم کنندہ عرف: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Moderations
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (یا درخواست کردہ فارمیٹ) باڈی واپس کرتا ہے
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS کے لیے ایک زبان اور آواز درکار ہے: `language` کی طے شدہ قدر "en" ہے؛ غیر موجود
# آواز یا OpenAI کی معیاری آواز کا نام (alloy, nova, …) "Adrian" بن جاتا ہے
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# تصویر میں ترمیم (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# ویڈیو / موسیقی کی جنریشن (فراہم کنندہ کے سابقے والی ماڈل ID)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **ری رینک فراہم کنندہ نوڈز:** `POST /v1/rerank` کو OpenAI سے مطابقت رکھنے والے فراہم کنندہ نوڈز
> (oMLX، vLLM، Infinity، گیٹ وے کے پیچھے TEI، …) کی طرف بھی روٹ کیا جاتا ہے، جنہیں `<node-prefix>/<model>` کے طور پر ایڈریس کیا جاتا ہے۔ لوپ بیک
> نوڈز (`localhost`، `127.0.0.1`، `172.16.0.0/12`) ہمیشہ اہل ہوتے ہیں، اور وہ میزبان نام بھی اہل ہوتے ہیں جنہیں
> آپریٹر `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` میں درج کرتا ہے (مثلاً Docker/Compose سروس کا نام، جیسے
> `http://reranker:8080/v1`؛ انہیں براہِ راست کال کیا جاتا ہے، کبھی بھی `HTTP(S)_PROXY` یا کسی
> کنکشن کی پن شدہ پراکسی کے ذریعے نہیں)۔ کسی دوسرے
> میزبان پر موجود نوڈز — جیسے LAN مشین یا Tailscale پیئر — صرف اسی وقت اہل ہوتے ہیں جب آپریٹر
> `RERANK_REMOTE_PROVIDER_NODES` فیچر فلیگ فعال کرے **اور** نوڈ کا بنیادی URL فراہم کنندہ کی
> آؤٹ باؤنڈ URL پالیسی (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) پر پورا اترے۔
> میموری انجن کا ری رینک مرحلہ اس روٹ کو
> لوپ بیک کے ذریعے کال کرتا ہے، اس لیے یہی اصول Memory کی ترتیبات میں `rerankProviderModel` پر بھی لاگو ہوتا ہے۔
>
> **مقامی سرور کی ساختیں:** نوڈ کو `<base>/v1/rerank` پر اور 404 آنے کی صورت میں `<base>/rerank`
> (Infinity، TEI) پر کال کیا جاتا ہے۔ اپ اسٹریم باڈی میں Cohere/OpenAI والی املا (`documents`،
> `return_documents`) اور TEI والی املا (`texts`، `return_text`) دونوں شامل ہوتی ہیں، اور اپ اسٹریم جواب کو
> Cohere انویلپ کے مطابق معمول پر لایا جاتا ہے: TEI کا سادہ `[{index, score, text}]`، ہلکے پھلکے گیٹ ویز سے آنے والا `{results: [{index, score}]}`
> اور Voyage طرز کا `{data: [...]}`، سب کلائنٹ کو
> `{results: [{index, relevance_score, document?}]}` کی شکل میں واپس ملتے ہیں، اسکور کے لحاظ سے مرتب ہوتے ہیں اور `top_n` تک محدود کیے جاتے ہیں۔

> **فراہم کنندہ نوڈ کی دریافت:** OpenAI سے مطابقت رکھنے والے فراہم کنندہ نوڈ پر موجود ماڈلز، نوڈ کے سابقے کے تحت `GET /v1/models`
> میں ظاہر ہوتے ہیں۔ جن قطاروں میں اینڈ پوائنٹ میٹا ڈیٹا موجود نہ ہو (جو مقامی `/v1/models` فہرستوں کے لیے عام ہے)،
> وہ نوڈ کا `apiType` وراثت میں لیتی ہیں، لہٰذا `embeddings` نوڈ کے ماڈلز `type: "embedding"` اور
> `rerank` نوڈ کے ماڈلز `type: "rerank"` ہوتے ہیں، بجائے اس کے کہ وہ بطور ڈیفالٹ چیٹ بن جائیں؛ سنک کی گئی یا دستی طور پر شامل کردہ قطار پر واضح
> `supportedEndpoints` کو پھر بھی ترجیح حاصل ہوتی ہے۔

### مخصوص فراہم کنندہ روٹس

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

اگر فراہم کنندہ کا سابقہ موجود نہ ہو تو اسے خودکار طور پر شامل کر دیا جاتا ہے۔ غیر مطابق ماڈلز `400` واپس کرتے ہیں۔

**تصدیق:** بیئرر API کلید — فائلیں `getApiKeyRequestScope` کے ذریعے ہر API کلید کے دائرۂ کار تک محدود ہوتی ہیں۔ کوئی کلید
صرف اپنی فائلیں دیکھ، ڈاؤن لوڈ اور حذف کر سکتی ہے؛ کلید کے بغیر ڈیش بورڈ سیشن پوری
انسٹینس کو پڑھ سکتا ہے؛ مالک کے بغیر فائل (گمنام یا ڈیش بورڈ سیشن کے ذریعے اپ لوڈ کردہ) ہر

حل نہ ہو — `401` کے ساتھ مسترد کرتا ہے، حتیٰ کہ جب `REQUIRE_API_KEY=false` ہو، بجائے اس کے کہ ہر ٹیننٹ کی
فائلیں درج کرے (GHSA-m3hp-hq9g-fpmv، GHSA-2jm2-mpx8-6523)۔

| ----- | ---------------------- | -------------------------------------------------------------------------------------------------------- |

| POST  | `/v1/search`           | ایک سرچ استفسار چلائیں — باڈی جس کی توثیق `v1SearchSchema` نے کی ہے، caching/coalescing کو سپورٹ کرتا ہے |

**تصدیق:** بیئرر API کلید (`extractApiKey` + `isValidApiKey`)۔ تلاش کی پالیسی `enforceApiKeyPolicy` کے ذریعے نافذ کی گئی۔

### Exa اور Tavily `provider_options`

Exa اور Tavily نام کی جگہ والے بیگ سے فراہم کنندہ کے مخصوص فیلڈز کو پڑھیں: `provider_options.exa` (یا `provider_options["exa-search"]`) اور `provider_options.tavily` (یا `provider_options["tavily-search"]`)۔ صرف نیچے کی چابیاں آگے بھیجی جاتی ہیں۔ ہر ایک کو `open-sse/handlers/search/providerOptionsPassthrough.ts` میں اس کے اپنے Zod اسکیما کے خلاف چیک کیا جاتا ہے، اور غلط قسم والی کلید چھوڑ دی جاتی ہے۔ کسی بھی دوسری کلید کو نظر انداز کر دیا جاتا ہے، بشمول auth، base URL، `stream` اور `outputSchema`۔ دوسرے فراہم کنندگان (`cx`, `depth`, ...) کے ذریعے استعمال ہونے والی فلیٹ کیز پہلے کی طرح کام کرتی ہیں۔

| فراہم کرنے والا | ٹاپ لیول فیلڈز                                                                                                                                                                                                                                                                                                                                                            | نیسٹڈ                                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa             | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (فلیٹ پرائمیٹو) , `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                               | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` پہلے سے طے شدہ `{ text: true, highlights: true }` پر ضم ہوگیا۔ |
| تاویلی          | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                            |

عام فیلڈز ہمیشہ جیتتے ہیں: `query`، `max_results`، `filters` (ڈومینز)، `country` اور `search_type` سے ماخوذ موضوع۔ Exa پر، `search_type: "news"` `category: "news"` رکھتا ہے۔ Tavily `search_type: "finance"` (`topic: "finance"`) کو بھی قبول کرتا ہے۔

فائر کرال تلاش کی لاگت 10 لوٹے گئے نتائج کے فی شروع شدہ بلاک میں، $0.002 (2 کریڈٹ) ایک بلاک اور کم از کم ایک بلاک فی کال ( [فائرکرول بلنگ](https://docs.firecrawl.dev/billing) ): 11 نتائج کی لاگت $0.004 ہے۔

عام `time_range` اب دونوں فراہم کنندگان تک پہنچ جاتا ہے: Exa کو `startPublishedDate` (ISO ٹائم اسٹیمپ) اور Tavily کو `start_date` (`YYYY-MM-DD`) ملتا ہے۔ `provider_options` میں ایک واضح تاریخ میپ شدہ کو اوور رائیڈ کرتی ہے۔

Exa نتائج `id`, `highlight_scores`, `summary`, `subpages`, `entities` اور `extras` `provider_raw` میں رکھتے ہیں۔ Tavily کے نتائج `images` اور `favicon` برقرار رکھتے ہیں۔

لنک اپ کی تلاش کی قیمت `depth` `fast` اور `standard` کے لیے $0.005 اور `deep` کے لیے $0.05 ( [Linkup pricing](https://docs.linkup.so/pages/documentation/development/pricing) ) ریکارڈ کی گئی ہے، چاہے `depth` `provider_options` سے آیا ہو یا کنکشن کی ترتیبات سے۔

Exa `type: "lite"` (Exa 3.0) فیلڈز کے ایک چھوٹے سیٹ کو قبول کرتا ہے اور جب کوئی دوسرا فیلڈ سیٹ کیا جاتا ہے تو پوری درخواست کو مسترد کر دیتا ہے۔ لائٹ کے لیے، `additionalQueries`، `systemPrompt` اور `text` اور `highlights` کے علاوہ ہر `contents` کلید کال سے پہلے چھوڑ دی جاتی ہے۔ فرسودہ `subpages`، `subpageTarget`، `highlights.numSentences` اور `highlights.highlightsPerUrl` مزید آگے نہیں بھیجے جاتے ہیں۔

لاگت کا حساب کتاب فلیٹ رجسٹری `costPerQuery` ہے، Exa کے علاوہ، جو Exa کی اپنی قیمتوں کی پیروی کرتا ہے: $0.007 فی کال `auto` (اور لیگیسی `fast`) کے لیے یا $0.004 `lite` (اور لیگیسی `instant`) کے لیے، جس میں 10 نتائج شامل ہیں۔ ہر مزید نتیجے کے لیے $0.001؛ اور $0.001 فی لوٹا ہوا نتیجہ جب `contents.summary` سیٹ ہو۔ Tavily کو `search_depth` `basic`، `fast` اور `ultra-fast` کے لیے 1 کریڈٹ ($0.008) اور `advanced` ( [Tavily API کریڈٹس](https://docs.tavily.com/documentation/api-credits) ) کے لیے 2 کریڈٹ ($0.016) پر ریکارڈ کیا گیا ہے۔ `auto_parameters: true` کے ساتھ ایک کال جسے Tavily ایڈوانس میں اپ گریڈ کرتا ہے اب بھی 1 کریڈٹ پر ریکارڈ کیا جاتا ہے۔

## ویب فیچ API

ترتیب دیے گئے ویب فیچ فراہم کنندہ (Firecrawl، Jina
Reader، Tavily Extract، TinyFish Fetch، Nimble Extract، Parallel Extract) کے ذریعے URL سے مواد اخذ کریں۔

Parallel Extract (`parallel-search`، وہی API کلید جو Parallel Search کی ہے) صرف Markdown
واپس کرتا ہے — کوئی بھی دوسرا `format` ایک `400` دیتا ہے — اور مواد کو 100,000 حروف تک محدود کرتا ہے۔ جب
ہدف صفحہ بذاتِ خود اخذ نہ کیا جا سکے، تو اَپ اسٹریم اسے HTTP 200 کے اندر رپورٹ کرتا ہے؛
OmniRoute اسے ایک مقررہ پیغام کے ساتھ `422` کے طور پر ظاہر کرتا ہے۔

| طریقہ | راستہ           | تفصیل                                                             |
| ----- | --------------- | ----------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL فیچ/اسکریپ کریں — باڈی کی توثیق `v1WebFetchSchema` سے ہوتی ہے |

**توثیق:** Bearer API کلید (`extractApiKey` + `isValidApiKey`)۔ پالیسی `enforceApiKeyPolicy` کے ذریعے نافذ کی جاتی ہے۔

**کوٹہ سے آگاہ فال بیک (#8297):** جب کوئی واضح `provider` نہ دیا گیا ہو، تو پول
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) کو
مقررہ
ترجیحی ترتیب (پہلے پُر کریں) میں آزمایا جاتا ہے — شرح کی حد تک پہنچ چکے مگر ترتیب شدہ فراہم کنندہ کو درخواست فوراً ختم کرنے
کے بجائے چھوڑ دیا جاتا ہے، اور دوبارہ کوشش کے قابل/کوٹہ سے متعلق اَپ اسٹریم ناکامی
(HTTP 429 ہمیشہ؛ Firecrawl/Tavily/TinyFish کے کوٹہ طرز کے مفت درجات کے لیے 402/403 —
Jina Reader کے لیے نہیں، اور ایک سادہ 400 ناقص درخواست کے لیے کبھی نہیں) درخواست کے وقت
اگلے ایسے فراہم کنندہ کی طرف منتقل ہو جاتی ہے جسے ابھی آزمایا نہ گیا ہو اور جس کی اسناد موجود ہوں۔ جب پول کے تمام فراہم کنندگان
ختم ہو جائیں، تو اینڈ پوائنٹ سابقہ عمومی `400` کے بجائے ایک واحد `429` (`Retry-After`
ہیڈر کے ساتھ) واپس کرتا ہے۔ جب کوئی واضح `provider`
درخواست کیا جائے، تو **کوئی** خاموش فال بیک نہیں ہوتا — شرح کی حد تک پہنچا ہوا یا ناکام واضح
فراہم کنندہ اپنی ہی خرابی ظاہر کرتا ہے (شرح کی حد کی صورت میں `429`، بصورتِ دیگر اَپ اسٹریم
اسٹیٹس)۔

## WebSocket اسٹریمنگ

```bash
GET /v1/ws?handshake=1
```

WebSocket اپ گریڈ ہینڈ شیک کی توثیق کرتا ہے اور وائر پروٹوکول کے مثالی پیغامات (`request`، `cancel`) واپس کرتا ہے۔ اصل WS فریمز Next.js روٹ ٹیبل سے باہر بنڈل شدہ WS سرور کے ذریعے سنبھالے جاتے ہیں۔

**توثیق:** ہینڈ شیک کے دوران Bearer API کلید۔

### WebSocket پر Responses API (صرف codex)

```bash
# وہی host:port جو HTTP API کا ہے (ڈیفالٹ 20128)؛ کنکشن کو اپ گریڈ کریں:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (یا: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# پہلا فریم لازماً response.create ہونا چاہیے:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket پراکسی **خصوصی طور پر `codex`** (ChatGPT
بیک اینڈ) سے منسلک ہے۔ یہ API/ڈیش بورڈ کے اسی پورٹ پر `/v1/responses`،
`/responses`، اور `/api/v1/responses` راستوں پر سنتی ہے۔ پہلے `response.create` فریم پر یہ
اندرونی `codex-responses-ws` برج کے ذریعے توثیق + تیاری کرتی ہے، ایک
codex OAuth کنکشن منتخب کرتی ہے، اور `wreq-js` ٹرانسپورٹ کے ذریعے `wss://chatgpt.com/backend-api/codex/responses`
تک ٹنل بناتی ہے۔ **غیر codex ماڈلز مسترد کر دیے جاتے ہیں** (`codex_ws_provider_required`)۔
کوٹہ شیئر روٹنگ کے لیے `model: "qtSd/<group>/codex/<model>"` استعمال کریں۔ نفاذ
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` میں ہے۔

**توثیق:** ہینڈ شیک کے دوران Bearer API کلید۔ بنڈل شدہ HTTP سرور (`server-ws.mjs`)
فعال انٹری پوائنٹ ہونا چاہیے (جب `app/server-ws.mjs` موجود ہو تو ڈیفالٹ طور پر یہی ہوتا ہے)۔

#### ماڈل id: سادہ ChatGPT id استعمال کریں (`codex/` سابقے کے بغیر)

OpenAI **Codex CLI** اس وقت کلائنٹ کی جانب ماڈل کے نام کی توثیق کرتا ہے جب
`supports_websockets = true` ہو، اور `codex/gpt-5.5` جیسے
**فراہم کنندہ کے سابقے والے ids مسترد کرتا ہے** (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)۔ **سادہ** id بھیجیں (مثلاً `gpt-5.5`)۔ OmniRoute کا برج
صرف codex کے لیے ہے، اس لیے اَپ اسٹریم تک ٹنل بنانے سے پہلے یہ سادہ id کو codex ماڈل کے طور پر
(`resolveCodexWsModelInfo`) دوبارہ حل کرتا ہے — اگرچہ ایک سادہ
`gpt-5.5` بصورتِ دیگر HTTP پر کسی دوسرے فراہم کنندہ کی طرف روٹ ہوتا۔

#### OpenAI Codex CLI کی ترتیب

`~/.codex/config.toml` میں WebSocket
سپورٹ کے حامل حسبِ ضرورت فراہم کنندہ کو شامل کرکے Codex CLI کو OmniRoute کی طرف متوجہ کریں (موجودہ ترتیب کو
چھیڑنے سے بچنے کے لیے الگ `CODEX_HOME` استعمال کریں):

```toml
model = "gpt-5.5"                 # سادہ id — "codex/gpt-5.5" نہیں
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # آخر میں slash نہیں؛ WS URL اخذ کیا جاتا ہے (پروڈکشن میں https/wss استعمال کریں)
wire_api = "responses"                    # Feb 2026 سے واحد معاونت یافتہ قدر
supports_websockets = true                # Responses-over-WS ٹرانسپورٹ فعال کرتا ہے
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API کلید رکھتا ہے (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ایک OmniRoute API کلید (اگر REQUIRE_API_KEY=false ہو تو کوئی بھی کلید)
codex exec "Responda apenas: PONG"
```

CLI، `base_url + /responses` کو WebSocket میں اپ گریڈ کرتا ہے اور OmniRoute اسے
منتخب کردہ codex OAuth کنکشن تک ٹنل کرتا ہے۔ مقامی
سرور کے ساتھ ابتدا سے انتہا تک توثیق شدہ: ChatGPT، `codex.rate_limits` + `response.created` واپس کرتا ہے اور
تکمیل کو اسٹریم کرتا ہے۔

## ذاتی استعمال (`/api/usage/om-usage`)

کوئی بھی API کلید **اپنے** استعمال اور کوٹوں کو پڑھ سکتی ہے — انتظامی توثیق درکار نہیں۔ یہ وہ اینڈ پوائنٹ ہے جسے
کلائنٹ (CLI، OmniCopilot پینل) کسی کلید کے حامل شخص کو اس کے اخراجات دکھانے کے لیے استعمال کرتا ہے۔

```bash
# متنی صورت (تاریخی معاہدہ — ٹرمینل کے لیے سادہ متن)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ساختی صورت — جسے UI استعمال کرتا ہے
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

کلید کے لیے **`allowUsageCommand`** فعال ہونا ضروری ہے (یہ بطور ڈیفالٹ بند ہوتا ہے — ڈیش بورڈ کا API کلید
مینیجر اسے ہر کلید کے لیے الگ سے تبدیل کرتا ہے)۔ اس کے بغیر اینڈ پوائنٹ `403` کا جواب دیتا ہے۔

`?format=json` ایک امتیازی ساخت واپس کرتا ہے تاکہ کالر کبھی بھی انکار کی صورت میں ڈیٹا فیلڈ نہ پڑھے۔
کامیابی کی صورت میں:

```jsonc
{
  "allowed": true,
  // صرف اس وقت موجود ہوتا ہے جب کلید نے فی کلید استعمال کی حدود (یومیہ/ہفتہ وار USD) اختیار کی ہوں:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // منتخب فراہم کنندہ کے کوٹے کا اسنیپ شاٹ، یا اگر ابھی کچھ کیش نہ ہوا ہو تو null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // ہر کنکشن کا اسنیپ شاٹ، تاکہ UI متعدد فراہم کنندگان کو ساتھ ساتھ رینڈر کر سکے:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

انکار کی صورت میں (`401` غلط کلید / `403` اجازت نہیں) یہی روٹ
`{ "allowed": false, "error": { "message": "…" } }` واپس کرتا ہے — موجود مگر خالی `personal`/`provider`
(کلید کو اجازت ہے، لیکن ابھی کچھ معلوم نہیں ہوا) انکار سے مختلف حالت ہے، اور صرف JSON صورت
ان میں فرق ظاہر کرتی ہے۔

**توثیق:** کالر کی اپنی بیئرر API کلید، جس کی توثیق `isValidApiKey` سے کی جاتی ہے — یہ انتظامی
سطح (`/api/keys/…`) _نہیں_ ہے، جو `requireManagementAuth` کے پیچھے محفوظ رہتی ہے۔

### خام بمقابلہ کٹ آف کے مطابق ایڈجسٹ کردہ کوٹہ فیصد

`/api/usage/om-usage` استعمال کرتے وقت، کالرز کو **سادہ متنی آؤٹ پٹ** اور ساختی **JSON آؤٹ پٹ**
میں پیش کیے جانے والے فیصد کے درمیان فرق کو ملحوظ رکھنا چاہیے:

| پہلو              | سادہ متنی فارمیٹ (`/api/usage/om-usage` / `@@om-usage`)                                    | JSON فارمیٹ (`?format=json`)                                                   |
| :---------------- | :----------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| **آؤٹ پٹ فیلڈ**   | `NN% left` (مثلاً، `20% left`)                                                             | `provider.quotas` / `providers[].quotas`                                       |
| **پیمائش**        | **کٹ آف کے مطابق ایڈجسٹ کردہ قابلِ استعمال گنجائش**: کٹ آف حد سے اوپر باقی صلاحیت          | **خام اپ اسٹریم کوٹہ**: فراہم کنندہ کی غیر ایڈجسٹ شدہ پیمائش                   |
| **کٹ آف اسکیلنگ** | `effectiveRemainingPercent()` کے ذریعے اسکیل کیا جاتا ہے تاکہ محفوظ ذخیرہ `0% left` دکھائے | کوئی نہیں (خام اسنیپ شاٹ اقدار، جیسا کہ فراہم کنندہ نے رپورٹ کیا)              |
| **حد کا ڈیٹا**    | دکھائے گئے فیصد میں شامل ہوتا ہے                                                           | ہر کنکشن کے لیے `quotaWindowThresholds` میں محفوظ ہوتا ہے (یا سرور کے ڈیفالٹس) |
| **بنیادی صارف**   | انٹرایکٹو CLIs، ٹرمینل پرامپٹس، انسانی آپریٹرز                                             | پروگراماتی انضمام، ڈیش بورڈز، تجزیات، بلنگ ٹریکرز                              |

#### کٹ آف ایڈجسٹمنٹ کا فارمولا

OmniRoute اپ اسٹریم کوٹے کے خاتمے کو روکنے کے لیے پیشگی کوٹہ کٹ آف کی معاونت کرتا ہے (جو کنکشن
`quotaWindowThresholds`، فراہم کنندہ کے ڈیفالٹس، یا عالمی ریزیلیئنس ترتیبات کے ذریعے تشکیل دیے جاتے ہیں)۔ جب کسی کوٹہ ونڈو پر کٹ آف حد
(مثلاً، `cutoff = 25%`) فعال ہو، تو ٹیکسٹ رینڈرر باقی گنجائش کا حساب یوں لگاتا ہے:

- اگر `remaining <= cutoff` ہو: `0%` واپس کرتا ہے۔
- اگر `remaining > cutoff` ہو: `((remaining - cutoff) / (100 - cutoff)) * 100` واپس کرتا ہے۔

فارمیٹ کردہ متنی آؤٹ پٹ اسے قریب ترین صحیح عدد تک راؤنڈ کرتا ہے (`Math.round(...)`)۔

#### وضاحتی مثال

ایک فراہم کنندہ ونڈو فرض کریں جس میں **60% خام استعمال** ہو (لہٰذا **40% خام کوٹہ باقی** ہو) اور
**باقی کوٹے کے لیے 25% کٹ آف** حد تشکیل دی گئی ہو:

| نمائندگی                      | حساب                                               |  باقی   |                  اخذ کردہ استعمال                  |
| :---------------------------- | :------------------------------------------------- | :-----: | :------------------------------------------------: |
| **خام JSON (`?format=json`)** | اپ اسٹریم اسنیپ شاٹ (`quotas[window]`)             | **40%** |                      **60%**                       |
| **متنی فارمیٹ (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (اگر `100 - remaining` کا حساب لگایا جائے) |

- **متن میں 20% باقی کیوں دکھائی دیتا ہے:** اکاؤنٹ پر باقی 40% حقیقی کوٹے میں سے 25% کٹ آف
  پالیسی کے تحت محفوظ ہے۔ روٹر کے اس کنکشن کی جانب روٹنگ روکنے سے پہلے کالر کے پاس قابلِ استعمال 75% گنجائش میں سے
  صرف 15% باقی ہے۔ اسکیلنگ یقینی بناتی ہے کہ کنکشن عین اس وقت کوٹہ ختم ہونے (`0% left`) کا اشارہ دے
  جب روٹنگ بند ہو گی۔
- **JSON خام اقدار کو کیوں برقرار رکھتا ہے:** JSON پے لوڈ فراہم کنندہ کا عین اسنیپ شاٹ (`UsageSnapshot`)
  واپس کرتا ہے تاکہ بیرونی ٹولز کو حقیقی اپ اسٹریم استعمال اور کنکشن کی سطح کے
  `quotaWindowThresholds` تک سرور کی جانب سے نقصان دہ اسکیلنگ کے بغیر رسائی حاصل ہو۔

#### صارفین کی منتقلی کے لیے رہنمائی

اگر کسی بیرونی انٹیگریشن (جیسے ایڈیٹر پلگ اِن یا ایجنٹ ایکسٹینشن) نے پہلے متن والے
اینڈ پوائنٹ (`NN% left`) کو اسکریپ کیا ہو اور استعمال شدہ فیصد کا حساب `100 - NN` کے طور پر لگایا ہو، تو `?format=json` پر منتقل ہونے کا مطلب یہ ہے:

- خام JSON اقدار پڑھنے سے **اصل اَپ اسٹریم استعمال** ظاہر ہوگا (اوپر دی گئی مثال میں 60% استعمال شدہ)۔
- اگر انٹیگریشن متن والے اینڈ پوائنٹ کے قابلِ استعمال الاؤنس کے مفہوم کو برقرار رکھنا چاہتی ہے، تو وہ کنکشن کی سطح کی اوور رائیڈز کے لیے `quotaWindowThresholds` استعمال کرتے ہوئے
  مؤثر باقی ماندہ مقدار کے فارمولے کا کلائنٹ کی جانب جائزہ لے سکتی ہے۔

```json
{

    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {

  }
```

### تاخیر پر اثر

سیمنٹک کیش HIT کی صورت میں جواب کیش سے فراہم کیا جاتا ہے، **بغیر کسی اَپ اسٹریم
کال کے**، اس لیے رپورٹ کردہ `X-OmniRoute-Response-Latency` تقریباً صفر ہوتی ہے
(اصل اَپ اسٹریم تاخیر سے قطع نظر)۔ تاخیر کے حوالے سے حساس کلائنٹس
(بینچ مارکنگ، p50/p99 نگرانی) کو
`X-OmniRoute-Cache-Latency` جوابی ہیڈر چیک کرنا چاہیے:

| قدر           | مطلب                                                          |
| ------------- | ------------------------------------------------------------- |
| `synthetic`   | جواب کیش سے فراہم کیا گیا؛ تاخیر حقیقی اَپ اسٹریم وقت نہیں ہے |
| _(غیر موجود)_ | حقیقی اَپ اسٹریم کال سے موصولہ جواب                           |

### فی کلید کیش بائی پاس

API کلیدیں `cacheDefaultMode` کے ذریعے سیمنٹک کیش ریڈز سے دست بردار ہو سکتی ہیں:

| قدر      | طرزِ عمل                                                       |
| -------- | -------------------------------------------------------------- |
| `legacy` | کیش کا معمول کا طرزِ عمل (ڈیفالٹ)                              |
| `bypass` | کیش لُک اَپ مکمل طور پر چھوڑ دیں؛ ہمیشہ اَپ اسٹریم کو کال کریں |

کلید بناتے وقت (`POST /api/keys`) سیٹ کریں یا اپ ڈیٹ کریں (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### فی درخواست بائی پاس

کوئی بھی درخواست، کلید کی ترتیبات سے قطع نظر، کیش کو بائی پاس کر سکتی ہے:

```
X-OmniRoute-No-Cache: true
```

انتظامی روٹس (`/api/*`، عوامی توثیق/لاگ اِن کے علاوہ) عام اِنفرنس API کلیدوں کے ذریعے
**مجاز نہیں** ہوتے۔ اسناد کی اقسام، اسکوپس، اور curl کی مثالیں:

### توثیق

| اینڈ پوائنٹ                   | طریقہ    | تفصیل                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/auth/login`             | POST     | لاگ اِن                                                                                                                                                                                                                                                                                                          |
| `/api/auth/logout`            | POST     | لاگ آؤٹ                                                                                                                                                                                                                                                                                                          |
| `/api/settings/require-login` | GET/POST | لاگ اِن کی حالت (GET، عوامی)۔ POST پاس ورڈ سیٹ کرتا ہے / لاگ اِن کو فعال یا غیر فعال کرتا ہے: پاس ورڈ موجود ہونے کے بعد صرف آپریٹر کے لیے (ڈیش بورڈ سیشن، مقامی CLI، یا لاگ اِن غیر فعال ہو — API کلیدوں اور `oma_` ٹوکنز کو `403` ملتا ہے)؛ ڈیش بورڈ سیشن پاس ورڈ تبدیل کرنے کے لیے `currentPassword` بھیجتا ہے |

### پرووائیڈر کا انتظام

| اینڈ پوائنٹ                             | طریقہ                     | تفصیل                                                                                                                                    |
| --------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/providers`                        | GET/POST                  | فراہم کنندگان کی فہرست دکھائیں / تخلیق کریں                                                                                              |
| `/api/providers/[id]`                   | GET/PUT/DELETE            | فراہم کنندہ کا نظم کریں                                                                                                                  |

| `/api/providers/bulk`                   | POST                      | ایک فراہم کنندہ کے لیے API کلیدیں بڑی تعداد میں شامل کریں                                                                                |

| `/api/provider-models`                  | GET/POST/PUT/PATCH/DELETE | حسبِ ضرورت ماڈلز اور فی ماڈل اوور رائیڈز (شامل کرنا، اپ ڈیٹ کرنا، چھپانا/دکھانا، حذف کرنا)                                               |
| `/api/provider-models/validate-and-add` | POST                      | انتظامی توثیق کے ساتھ، اختیاری سخت کنکشن توثیق اور ایٹمی حسبِ ضرورت ماڈل رجسٹریشن؛ [ماڈل کی توثیق](../guides/MODEL-VALIDATION.md) دیکھیں |

ہم وقت ساز/درآمد شدہ ماڈلز کے لیے، `PUT /api/provider-models`، `provider`، `modelId`، اور
`maxOutputTokenOverride` قبول کرتا ہے: ایک مثبت صحیح عدد دستی آؤٹ پٹ ٹوکن حد مقرر کرتا ہے، جبکہ `null`
اسے صاف کرکے طے شدہ قدر بحال کرتا ہے۔ `GET /api/provider-models?provider=<provider>` یہ
اقدار `modelOutputOverrides` میں واپس کرتا ہے، بشمول ان ماڈلز کے جن کی حسبِ ضرورت ماڈل قطار موجود نہیں ہوتی۔ اوور رائیڈ
رن ٹائم `max_output_tokens` صلاحیت استعمال کرتا ہے اور ماڈل کی دوبارہ ہم وقت سازی کے بعد بھی برقرار رہتا ہے۔ OpenAI سے ہم آہنگ
فراہم کنندہ کا صفحہ وہی ترمیم/صاف کرنے کے کنٹرولز پیش کرتا ہے اور واضح وژن معاونت رکھنے والے ماڈلز کو نشان زد کرتا ہے۔

حسبِ ضرورت Chat Completions نوڈز، استدلال سے واضح دستبرداریوں کو اپ اسٹریم بیک اینڈ کے مطابق ڈھالتے ہیں۔ ایک
کامیاب کنکشن ٹیسٹ ہر عین ماڈل ID کے لیے خودکار طور پر چیٹ ٹیمپلیٹ کنٹرولز منتخب کرتا ہے
جس کا `/models` اندراج کوئی تسلیم شدہ `owned_by` قدر ثابت کرے: `vllm`، `sglang`، یا `llamacpp`۔
شفاف OpenAI سے ہم آہنگ ریپرز اصل ماڈل اندراج کو ایک نیسٹڈ
`openai` آبجیکٹ کے اندر محفوظ رکھ سکتے ہیں؛ شناخت زیادہ سے زیادہ ایسے تین انویلپس کی پیروی کرتی ہے۔ غائب، نامعلوم، یا
متضاد ملکیت والے ماڈلز OpenAI کا عام طرزِ عمل برقرار رکھتے ہیں۔ شناخت موجودہ کیٹلاگ درخواست کو دوبارہ استعمال کرتی ہے،
کوئی تکمیلی ٹوکن پیدا نہیں کرتی، اور کنکشن اینڈ پوائنٹ تبدیل ہونے پر منسوخ ہو جاتی ہے۔

ایسے بیک اینڈ کے لیے طرزِ عمل مقرر رکھنے کی خاطر جو یہ میٹا ڈیٹا ظاہر نہیں کرتا، موجودہ جزوی
فراہم کنندہ اپ ڈیٹ API استعمال کریں:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

وہ باڈی `PUT /api/providers/<connection-id>` کے ساتھ بھیجیں۔ اس کنکشن پر، `none` کی واضح
استدلالی کوشش `chat_template_kwargs.thinking=false` اور
`chat_template_kwargs.enable_thinking=false` کی صورت میں بھیجی جاتی ہے۔ واضح مقامی ٹیمپلیٹ اقدار بدستور حتمی رہتی ہیں
سوائے اس صورت کے جب سرور کی جانب کا کوئی استدلالی اصول کسی کوشش کو لازم کرے۔ یہ ترتیب صرف اس وقت لاگو ہوتی ہے جب کوئی حسبِ ضرورت
OpenAI سے ہم آہنگ کنکشن Chat Completions باڈی بھیجتا ہے؛ Responses درخواستیں اور عام
فراہم کنندگان اپنی مقامی درخواست کی ساخت برقرار رکھتے ہیں۔ عام OpenAI
`reasoning_effort` پاس تھرو کو لازم کرنے کے لیے `reasoningControl` کو `openai` پر مقرر کریں، یا خودکار شناخت استعمال کرنے کے لیے اسے حذف کریں/`null` پر مقرر کریں۔

Claude Code خودکار موڈ کی کلاسیفائر درخواستیں، جب ان میں کوئی واضح استدلالی کنٹرول موجود نہ ہو، تو طے شدہ طور پر
مقامی سوچ کو غیر فعال رکھتی ہیں۔ شناخت Claude فارمیٹ کی درخواستوں میں کلاسیفائر کا سسٹم مارکر استعمال کرتی ہے،
نہ کہ ماڈل کے نام یا تکمیل کی حدود۔ واضح باڈی کنٹرولز، معاون کوشش/سوچ
ہیڈرز، روٹنگ کے اصول، اور حل شدہ ماڈل کی کوشش اپنی موجودہ ترجیح برقرار رکھتے ہیں۔ کلاسیفائر کے دونوں
مراحل اپنے پرامپٹس، تکمیل کی حدود، اختتامی سلسلوں، اور حقیقی اپ اسٹریم اجازت کے
فیصلوں کو برقرار رکھتے ہیں؛ دوسرا مرحلہ اب بھی اپنی مطلوبہ قابلِ مشاہدہ استدلال عام متن کی صورت میں تیار کر سکتا ہے۔

### API کلید کی اجازتیں

`PATCH /api/keys/{id}` کسی موجودہ کلید کی اجازتوں کو اپ ڈیٹ کرتا ہے۔ ہر `/api/keys*` روٹ کی طرح، اسے انتظامی اجازت درکار ہے (دیکھیے [انتظامی توثیق](../guides/MANAGEMENT-AUTH.md))، نہ کہ انفرنس کلید۔ صرف وہ فیلڈز بھیجیں جنہیں آپ تبدیل کرنا چاہتے ہیں؛ ان میں سے کسی بھی فیلڈ کے بغیر درخواست کو `No valid fields to update` کے ساتھ مسترد کر دیا جاتا ہے۔ قابل قبول فیلڈز کی وضاحت `src/shared/validation/schemas/keys.ts` میں `updateKeyPermissionsSchema` کے ذریعے کی گئی ہے۔

| `/api/db-backups/exportAll` | GET    | مکمل بیک اپ کو .tar.gz آرکائیو کے طور پر ڈاؤن لوڈ کریں                                |

`/api/db-backups/export`، `/api/db-backups/exportAll` اور `/api/settings/export-json`
تمام محفوظ شدہ اسناد فراہم کرتے ہیں، اس لیے ان کے لیے ڈیش بورڈ سیشن یا مقامی CLI درکار ہے (یا لاگ اِن
غیر فعال ہو)۔ کسی بھی دائرۂ کار کی API keys اور `oma_` رسائی ٹوکنز کو `403` ملتا ہے۔ بحالی کی کارروائیوں پر بھی یہی
حد لاگو ہوتی ہے: `POST /api/db-backups/import` (`dryRun=true` سمیت)، `POST /api/db-backups` (id
کے ذریعے بحالی) اور `POST /api/settings/import-json` فعال ڈیٹابیس یا ترتیبات کو تبدیل کرتے ہیں، اس لیے مشینی
سند کو وہاں بھی `403` ملتا ہے؛ `omniroute sync import` مقامی CLI سند بھیجتا ہے۔ یہی اصول
`DELETE /api/db-backups` (محفوظ شدہ بیک اپس کو کم کرنا) اور `PATCH /api/db-backups` (برقرار رکھنے کی ترتیبات:
محفوظ شدہ اقدار ہر بیک اپ کے بعد خودکار کمی کو کنٹرول کرتی ہیں) پر بھی لاگو ہوتا ہے۔ فہرست دکھانے (`GET`) اور
دستی بیک اپ بنانے (`PUT`) کے لیے معمول کی انتظامی توثیق برقرار رہتی ہے۔

### ورژن اور ریلیز چینل

```bash
GET /api/system/version
```

صرف لوپ بیک کے لیے مینجمنٹ روٹ (ایڈمن توثیق)۔ یہ زیرِ استعمال ورژن، تازہ ترین
شائع شدہ ورژن اور خودکار اپ ڈیٹ کی حالت واپس کرتا ہے۔ `releaseChannel` اور `channels` اضافی
فیلڈز ہیں (ریل 3.8.54)؛ `channel` کا مفہوم برقرار رہتا ہے — یعنی وہ تعیناتی موڈ جسے ڈیش بورڈ اپ ڈیٹر
استعمال کرتا ہے (`npm`، `source` یا `docker-compose`)۔

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — زیرِ استعمال بلڈ کا npm چینل: `-nightly.*` ورژنز کے لیے `nightly`،
  دیگر پری ریلیزز (`-rc.*`، `-beta.*`، `-alpha.*`) کے لیے `next`، اور ایسے مستحکم ورژن کے لیے `lts` جو
  `channels.latest` سے پرانے میجر کا ہو، بصورتِ دیگر `latest`۔ یہ وہی اصول ہیں جو
  `scripts/release/dist-tag.mjs` میں استعمال ہوتے ہیں، جو اشاعت کے وقت npm dist-tag منتخب کرتا ہے۔
- `channels` — ہر dist-tag کا شائع شدہ تازہ ترین ورژن، جو `npm view omniroute dist-tags` سے حاصل ہوتا ہے (رجسٹری
  HTTP فال بیک)، اور `latest` کی طرح اسی 10 منٹ کی TTL کے ساتھ کیش کیا جاتا ہے۔ `latest` ہمیشہ موجود
  ہوتا ہے (پہلے `latest` فیلڈ اور پھر `"unavailable"` کو فال بیک کے طور پر استعمال کرتا ہے)؛ `next`، `nightly` اور `lts` صرف
  اسی وقت ظاہر ہوتے ہیں جب متعلقہ dist-tag موجود ہو۔ `Cache-Control: no-cache` درخواست دونوں تلاشوں کو ریفریش کرتی ہے۔

چینل ماڈل (`latest` = 4.0 GA تک v3، `next` = rc، `nightly` = `develop` بلڈز،
`lts` = 4.0 GA کے بعد v3 پیچز) کی وضاحت `docs/ops/RELEASE_STRATEGY.md` میں کی گئی ہے۔

## ٹوکنائزڈ VS Code / بغیر ہیڈر کے عرفی راستے

جب کوئی انٹیگریشن `Authorization` ہیڈر شامل نہ کر سکے اور API کلید کو بنیادی URL میں شامل کرنا ضروری ہو تو یہ عرفی راستے استعمال کریں۔

```bash
# OpenAI طرز کا کیٹلاگ عرفی راستہ
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI طرز کے چیٹ عرفی راستے
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama طرز کے عرفی راستے
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

مثال:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

نوٹس:

- ٹوکنائزڈ عرفی راستے `/v1/*` اور `/api/tags` والے ہی ہینڈلرز دوبارہ استعمال کرتے ہیں؛ جوابات کی ساخت یکساں رہتی ہے۔
- جب بھی کلائنٹ حسبِ ضرورت ہیڈرز کی معاونت کرے، `Authorization: Bearer ...` کو ترجیح دیں۔
- URL پر مبنی ٹوکنز OmniRoute سے باہر ریورس پراکسی لاگز، براؤزر ہسٹری، اور ٹیلی میٹری میں ظاہر ہو سکتے ہیں۔ انہیں مطابقت کے اختیار کے طور پر استعمال کریں، نہ کہ تصدیق کے طے شدہ طریقے کے طور پر۔

## ٹوکن کی حدود

فی API کلید **ٹوکن** بجٹس (اوپر موجود USD پر مبنی بجٹ سے مختلف)۔ درخواست کے راستے میں ہی نافذ کیے جاتے ہیں: جب کسی کلید کا موجودہ ونڈو استعمال اپنی حد تک پہنچ جاتا ہے، تو درخواستیں `429 Too Many Requests` کے ساتھ مسترد کر دی جاتی ہیں۔ حدود کو کسی مخصوص `model`، کسی `provider` تک محدود کیا جا سکتا ہے، یا پوری کلید پر `global` طور پر لاگو کیا جا سکتا ہے؛ جب ایک درخواست پر متعدد حدود لاگو ہوں، تو سب سے زیادہ پابندی والی حد کو ترجیح دی جاتی ہے۔

```bash
# کسی کلید کی ٹوکن حدود کی فہرست حاصل کریں (لائیو ونڈو استعمال سمیت)
GET /api/usage/token-limits?apiKeyId=key-123

# ٹوکن حد بنائیں یا اپ ڈیٹ کریں
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id کے ذریعے ٹوکن حد حذف کریں
DELETE /api/usage/token-limits?id=tl-abc
```

> **اسکیما کے نوٹس** (`setTokenLimitSchema`): `apiKeyId` اور `scopeType` (`model` | `provider` | `global`) لازمی ہیں۔ `scopeValue` لازمی ہے، سوائے اس صورت کے جب `scopeType`، `global` ہو (مثلاً `model` اسکوپ کے لیے ایک ماڈل id، یا `provider` اسکوپ کے لیے ایک فراہم کنندہ id)۔ `tokenLimit` لازماً ایک مثبت صحیح عدد ہونا چاہیے (اسٹرنگ سے تبدیل کیا جاتا ہے)۔ اختیاری: `id` (بنانے کے لیے شامل نہ کریں، اپ ڈیٹ کرنے کے لیے فراہم کریں)، `resetInterval` (`daily` | `weekly` | `monthly`، ڈیفالٹ `monthly`)، `resetTime` (`HH:MM`)، `enabled` (ڈیفالٹ `true`)۔ `GET` جوابات ہر حد کو `tokensUsed`، `remaining`، `windowStart`، `periodStartAt`، اور `nextResetAt` کے ساتھ مزید معلومات فراہم کرتے ہیں۔ یہ مینجمنٹ درجے کا اینڈ پوائنٹ ہے (توثیق authz پائپ لائن کے ذریعے مرکزی طور پر نافذ کی جاتی ہے)۔

## درخواست کی پروسیسنگ

1. کلائنٹ `/v1/*` کو درخواست بھیجتا ہے
2. روٹ ہینڈلر `handleChat`، `handleEmbedding`، `handleAudioTranscription`، یا `handleImageGeneration` کو کال کرتا ہے
3. ماڈل کو حل کیا جاتا ہے (براہِ راست فراہم کنندہ/ماڈل یا عرف/کومبو)
4. اکاؤنٹ کی دستیابی کی فلٹرنگ کے ساتھ مقامی DB سے اسناد منتخب کی جاتی ہیں
5. چیٹ کے لیے: `handleChatCore` سیمینٹک/سگنیچر کیش کی جانچ کرتا اور کومبو کمپریشن کی ترتیبات حل کرتا ہے
6. فعال ہونے پر فراہم کنندہ کی ترجمانی سے پہلے پیشگی کمپریشن چلتی ہے (`lite`، Caveman، RTK، یا اسٹیک شدہ)
7. فراہم کنندہ ایگزیکیوٹر اپ اسٹریم درخواست بھیجتا ہے
8. جواب کو دوبارہ کلائنٹ فارمیٹ میں ترجمہ کیا جاتا ہے (چیٹ)، یا جوں کا توں واپس کیا جاتا ہے (ایمبیڈنگز/تصاویر/آڈیو)
9. استعمال، کمپریشن تجزیات، اور درخواست کے لاگز ریکارڈ کیے جاتے ہیں
10. خرابیوں کی صورت میں کومبو قواعد کے مطابق فال بیک لاگو ہوتا ہے

مکمل آرکیٹیکچر کا حوالہ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

خودکار کلید انتظامی ذیلی نظام اسے بیکنگ فراہم کنندہ/اکاؤنٹ کے ساتھ API کلیدیں جاری کرنے اور گردش دینے کے لیے استعمال کرتا ہے، جن پر یومیہ/فی گھنٹہ کوٹے لاگو ہوتے ہیں۔

| طریقہ  | راستہ                                 | تفصیل                                                                                                                                                                                                         |
| ------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | رجسٹرڈ کلیدوں کی فہرست دکھائیں (صرف مخفی سابقہ)                                                                                                                                                               |
| POST   | `/api/v1/registered-keys`             | نئی رجسٹرڈ کلید جاری کریں — باڈی: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`۔ خام کلید **صرف ایک بار** واپس کی جاتی ہے۔ کوٹا مسترد ہونے پر `429` واپس کرتا ہے۔ |
| GET    | `/api/v1/registered-keys/[id]`        | رجسٹرڈ کلید کا میٹا ڈیٹا حاصل کریں (خام مواد کے بغیر)                                                                                                                                                         |
| DELETE | `/api/v1/registered-keys/[id]`        | رجسٹرڈ کلید منسوخ کریں                                                                                                                                                                                        |
| POST   | `/api/v1/registered-keys/[id]/revoke` | واضح منسوخی اینڈ پوائنٹ (DELETE جیسا ہی اثر)                                                                                                                                                                  |

**توثیق:** انتظامی سیشن/API کلید (`requireManagementAuth`) — وہی حفاظتی عمل جو `/api/keys` کے لیے ہے: ڈیش بورڈ سیشن، مقامی CLI ٹوکن، یا `manage`/`admin` اسکوپ والی API کلید؛ صرف انفرنس کی API کلیدوں کو `403` ملتا ہے۔ `/v1/quotas/check` اور `/v1/issues/report` بھی دیکھیں۔

## مینجمنٹ پراکسیز

آؤٹ باؤنڈ HTTP(S)/SOCKS پراکسیز جنہیں providers، accounts، یا عالمی سطح پر تفویض کیا جا سکتا ہے۔

| طریقہ  | پاتھ                                         | تفصیل                                                                                                                                                                            |
| ------ | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | پراکسیز کی فہرست (`?id=` کے ساتھ ایک پراکسی واپس کرتا ہے؛ `?id=&where_used=1` کے ساتھ assignment graph واپس کرتا ہے)                                                             |
| POST   | `/api/v1/management/proxies`                 | پراکسی بنائیں — باڈی کی توثیق `createProxyRegistrySchema` کے ذریعے کی جاتی ہے                                                                                                    |
| PATCH  | `/api/v1/management/proxies`                 | پراکسی اپ ڈیٹ کریں — باڈی کی توثیق `updateProxyRegistrySchema` کے ذریعے کی جاتی ہے (`id` درکار ہے)                                                                               |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | پراکسی حذف کریں (assignments الگ کرنے کے لیے `force=1` استعمال کریں)                                                                                                             |
| GET    | `/api/v1/management/proxies/assignments`     | assignments کی فہرست — `proxy_id`، `scope`، `scope_id` کے ذریعے فلٹر کی جا سکتی ہے؛ کسی connection کے لیے فعال پراکسی resolve کرنے کی خاطر `resolve_connection_id=<id>` پاس کریں |
| PUT    | `/api/v1/management/proxies/assignments`     | تفویض کریں — باڈی کی توثیق `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) کے ذریعے کی جاتی ہے۔ dispatcher cache صاف کرتا ہے                                             |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | ایک ساتھ تفویض کریں — باڈی کی توثیق `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) کے ذریعے کی جاتی ہے                                                            |
| GET    | `/api/v1/management/proxies/health?hours=24` | ایک دورانیے کے دوران پراکسی کی مجموعی صحت (کامیابی/ناکامی کی تعداد، latency)                                                                                                     |

**تصدیق:** ہر route پر management session/API key درکار ہے (`requireManagementAuth`)۔

> ٹاسک کی تفصیل میں موجود `POST /api/v1/management/proxies/[id]/assignments` اور `POST /api/v1/management/proxies/[id]/health` کو اوپر دکھائے گئے flat `/assignments` اور `/health` routes فراہم کرتے ہیں — codebase میں فی id کوئی subroutes موجود نہیں ہیں۔

## لچک پذیری (توسیع شدہ)

OmniRoute عارضی ناکامی سے نمٹنے کے تین آزاد طریقۂ کار فراہم کرتا ہے؛ ذیل کے انتظامی اینڈ پوائنٹس آپریٹرز کو انہیں پڑھنے اور اوور رائیڈ کرنے کی سہولت دیتے ہیں:

| دائرہ           | حالت کا ذخیرہ                          | پڑھنا                                     | ری سیٹ / صاف کرنا                                             |
| --------------- | -------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| پرووائیڈر بریکر | `domain_circuit_breakers` + اِن میموری | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                  |
| کنکشن کول ڈاؤن  | پرووائیڈر کنکشنز پر `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (بتدریج دوبارہ فعال ہوتا ہے؛ پرووائیڈر PUT کے ذریعے صاف کریں) |
| ماڈل لاک آؤٹ    | اِن میموری ماڈل دستیابی رجسٹری         | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                      |

`PATCH /api/resilience`، `providerBreaker.oauth` اور `providerBreaker.apikey` کے تحت پرووائیڈر بریکر اوور رائیڈز قبول کرتا ہے۔ ہر پروفائل `degradationThreshold`، `failureThreshold`، اور `resetTimeoutMs` کو سپورٹ کرتا ہے؛ یہی فیلڈز ڈیش بورڈ → ترتیبات → لچک پذیری میں بھی دستیاب ہیں۔

```bash
# کسی ایک ماڈل لاک آؤٹ کو صاف کریں
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# تمام لاک آؤٹس مٹا دیں
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

مکمل تصوری حوالہ اور بریکر کی ڈیفالٹ اقدار کے لیے: [`CLAUDE.md`](../../CLAUDE.md) → "لچک پذیری کی رن ٹائم حالت" اور [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) دیکھیں۔

### ریٹ لمٹ قطار اور خودکار فعال کاری کا حفاظتی جال

- **معاونت یافتہ تحریری راستہ**: باڈی `{"connectionId": "<id>", "enabled": true|false}` کے ساتھ `POST /api/rate-limits`، کسی کنکشن کے لیے ریٹ لمٹ تحفظ کو آن یا آف کرنے کا معاونت یافتہ انتظامی اینڈ پوائنٹ ہے۔ `PUT /api/providers/[id]` دانستہ طور پر `rateLimitProtection` میں ترمیم نہیں کرتا اور نہ ہی اسے پلٹتا ہے (#11278)۔
- **`enabled: false` کے مفاہیم**: `enabled: false` مقرر کرنے سے کنکشن کا واضح تحفظ ہٹ جاتا ہے، لیکن یہ کسی فعال API کلید کنکشن کو عالمی خودکار فعال کاری کے حفاظتی جال (`autoEnableApiKeyProviders = true`) سے **خارج نہیں** کرتا۔ `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) میں `false` اور `undefined` مساوی ہیں؛ واضح تحفظ کے بغیر فعال API کلید کنکشنز خودکار فعال کاری کے حفاظتی جال کے تحت محفوظ رہتے ہیں۔
- **عالمی طور پر غیر فعال کرنا**: API کلید کنکشنز کو ریٹ لمٹ قطاروں کے بغیر چلانے کے لیے، حفاظتی جال کو عالمی طور پر `RATE_LIMIT_AUTO_ENABLE=false` (ماحولیاتی متغیر) یا `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (ترتیبات → لچک پذیری / `PATCH /api/resilience`) کے ذریعے غیر فعال کریں۔

## MCP سرور

OmniRoute ایک اندرونی Model Context Protocol سرور کے ساتھ فراہم ہوتا ہے، جس میں 3 ٹرانسپورٹس (stdio، SSE، streamable-http) اور محدود دائرۂ کار والے ٹولز شامل ہیں۔ ذیل کے ڈیش بورڈ اینڈ پوائنٹس اسٹیٹس/آڈٹ ڈیٹا پڑھتے ہیں اور HTTP ٹرانسپورٹس کو پراکسی کرتے ہیں۔

| طریقہ | پاتھ | تفصیل |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ہارٹ بیٹ، ٹرانسپورٹ، آن لائن حالت، آخری کال، نمایاں ٹولز، 24 گھنٹوں کی کامیابی کی شرح |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` کے ساتھ MCP ٹولز کی فہرست |
| GET | `/api/mcp/sse` | SSE ٹرانسپورٹ کے لیے SSE اسٹریم کھولیں (اگر MCP غیر فعال ہو یا ٹرانسپورٹ مطابقت نہ رکھتا ہو تو `503` لوٹاتا ہے) |
| POST | `/api/mcp/sse` | SSE ٹرانسپورٹ پر JSON-RPC فریم بھیجیں |
| GET | `/api/mcp/stream` | Streamable HTTP ٹرانسپورٹ کا SSE رخ کھولیں (سرور کی جانب سے شروع کردہ پیغامات) |
| POST | `/api/mcp/stream` | Streamable HTTP ٹرانسپورٹ پر JSON-RPC فریم بھیجیں |
| DELETE | `/api/mcp/stream` | Streamable HTTP سیشن ختم کریں |
| GET | `/api/mcp/audit` | آڈٹ لاگ استفسار کریں — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | مجموعی آڈٹ اعدادوشمار (کل تعداد، کامیابی کی شرح، اوسط دورانیہ، نمایاں ٹولز) |

**توثیق:** `sse`/`stream` ٹرانسپورٹس MCP کے مخصوص توثیقی انٹرفیس کی پابندی کرتے ہیں (`mcp` دائرۂ کار والی Bearer API کلید)؛ `status`/`tools`/`audit*` روٹس ڈیش بورڈ سے قابلِ مطالعہ ہیں (ڈیش بورڈ ہوسٹ تک رسائی کے علاوہ کسی اضافی توثیق کی ضرورت نہیں)۔

> دونوں HTTP ٹرانسپورٹس `settings.mcpEnabled` اور `settings.mcpTransport` کے ذریعے محدود ہیں — ٹرانسپورٹ کی عدم مطابقت `400` لوٹاتی ہے، جبکہ MCP کی غیر فعال حالت `503` لوٹاتی ہے۔

## A2A سرور

OmniRoute معائنے اور ڈیش بورڈ کے استعمال کے لیے REST ریپر کے ساتھ ایک A2A (ایجنٹ سے ایجنٹ) JSON-RPC 2.0 اینڈ پوائنٹ فراہم کرتا ہے۔

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # اختیاری، الا یہ کہ OMNIROUTE_API_KEY سیٹ ہو
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

معاونت یافتہ طریقے (تمام `settings.a2aEnabled` کے ذریعے محدود ہیں):

| طریقہ            | وضاحت                                                            |
| ---------------- | ---------------------------------------------------------------- |
| `message/send`   | ہم وقت مہارت کا نفاذ؛ `{task, artifacts, metadata}` واپس کرتا ہے |
| `message/stream` | اسی مہارت کے مجموعے کا اسٹریمنگ SSE نفاذ                         |
| `tasks/get`      | `taskId` کے ذریعے ٹاسک حاصل کریں                                 |
| `tasks/cancel`   | `taskId` کے ذریعے ٹاسک منسوخ کریں                                |

بلٹ اِن مہارتیں: `smart-routing`، `quota-management`، `provider-discovery`، `cost-analysis`، `health-report`۔

### ایجنٹ کارڈ

```bash
GET /.well-known/agent.json
```

عوامی A2A ایجنٹ کارڈ (نام، وضاحت، صلاحیتیں، مہارتوں کا کیٹلاگ، تصدیقی اسکیم) واپس کرتا ہے — جسے عوامی طور پر 1 گھنٹے کے لیے کیش کیا جاتا ہے۔ کسی تصدیق کی ضرورت نہیں۔

### REST معاون ذرائع

| طریقہ | راستہ                        | وضاحت                                                                                                               |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A فعال ہونے کی حالت + ٹاسک کے اعداد و شمار + کیش شدہ ایجنٹ کارڈ کا خلاصہ                                          |
| GET   | `/api/a2a/tasks`             | ٹاسکس کی فہرست — `?state=submitted\|working\|completed\|failed\|cancelled`، `?skill=`، `?limit=` (≤200)، `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST معاون ذریعے کے طور پر نافذ نہیں کیا گیا — JSON-RPC `message/send` کے ذریعے بنائیں)                            |
| GET   | `/api/a2a/tasks/[id]`        | ایک ٹاسک حاصل کریں                                                                                                  |
| POST  | `/api/a2a/tasks/[id]/cancel` | ایک ٹاسک منسوخ کریں                                                                                                 |

**تصدیق:** REST معاون ذرائع مینجمنٹ تصدیق کے بغیر چلتے ہیں (ڈیش بورڈ سے پڑھے جا سکتے ہیں)؛ اگر کنفیگر کیا گیا ہو تو JSON-RPC `/a2a` روٹ Bearer `OMNIROUTE_API_KEY` استعمال کرتا ہے۔

## توثیق

اسناد کی چار اقسام (ڈیش بورڈ سیشن، مقامی CLI ٹوکن، `oma_live_…` ایکسیس
ٹوکن، انتظامی دائرۂ کار والی API کلید) اور ان کے استنتاجی کلیدوں سے فرق کے لیے [انتظامی توثیق](../guides/MANAGEMENT-AUTH.md) دیکھیں۔

- ڈیش بورڈ روٹس (`/dashboard/*`) `auth_token` کوکی استعمال کرتے ہیں
- لاگ اِن محفوظ کردہ پاس ورڈ ہیش استعمال کرتا ہے؛ متبادل کے طور پر `INITIAL_PASSWORD`
- `requireLogin` کو `/api/settings/require-login` کے ذریعے فعال یا غیر فعال کیا جا سکتا ہے
- جب `REQUIRE_API_KEY=true` ہو تو `/v1/*` روٹس کے لیے اختیاری طور پر بیئرر API کلید درکار ہوتی ہے
- اس حوالہ میں "انتظامی ٹوکن" / "انتظامی دائرۂ کار والی API کلید" سے مراد اس رہنما میں بیان کردہ اقسام میں سے کوئی ایک ہے — کوئی غیر متعین اضافی خفیہ قسم نہیں

> **اہم تبدیلی (v3.8.0)** — `/api/v1/agents/tasks/*` اور کول ڈاؤن کے انتظامی اینڈ پوائنٹس کے لیے اب **انتظامی توثیق** (ڈیش بورڈ `auth_token` کوکی یا انتظامی دائرۂ کار والی API کلید) درکار ہے۔ وہ کلائنٹس جو پہلے توثیق کے بغیر ان روٹس کو کال کرتے تھے، اب `401 Unauthorized` وصول کریں گے۔ کمٹ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) دیکھیں۔
