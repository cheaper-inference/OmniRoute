OmniRoute کال لاگز کا کسی بیرونی تجزیاتی اسٹور میں مسلسل، تدریجی ایکسپورٹ۔

لاگز ڈیش بورڈ کا ٹیب درخواستوں کی تاریخ SQLite (`call_logs`) میں رکھتا ہے، جو
روٹیشن اور برقرار رکھنے کی مدت کے تحت محدود ہوتی ہے۔ لاگ ایکسپورٹ اسی ریکارڈ سیٹ کو ایک شیڈول کے مطابق باہر بھیجتا ہے تاکہ وہ
مقامی ڈیٹابیس سے زیادہ عرصے تک محفوظ رہے اور اسے دوسرے ڈیٹا کے ساتھ جوڑا جا سکے۔ BigQuery پہلی منزل ہے؛
پائپ لائن ایک رجسٹری ہے، اس لیے مزید منزلیں اضافی طور پر شامل کی جا سکتی ہیں۔

## 1. یہ کیسے کام کرتا ہے

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **شیڈول** — ایک `JobRegistry` کرون جاب، `log_export`، جس کی طے شدہ ترتیب `0 * * * *` ہے (ہر گھنٹے،
  UTC)۔ یہ `src/lib/initCloudSync.ts` میں رجسٹر ہوتی ہے؛ اسے `OMNIROUTE_LOG_EXPORT_CRON` سے تبدیل کیا جا سکتا ہے۔
  ہر ٹِک پر ہر **فعال** منزل کا زیرِ التوا ڈیٹا یکے بعد دیگرے مکمل طور پر بھیجا جاتا ہے۔
- **کرسر** — SQLite کا ضمنی `call_logs.rowid`، جو ہر منزل کے لیے
  `log_export_destinations.cursor_row_id` میں محفوظ ہوتا ہے۔ جان بوجھ کر `timestamp` کو کرسر نہیں بنایا گیا: کال کرنے والے
  اپنی قدر فراہم کر سکتے ہیں، اس لیے کوئی سست درخواست ایسی تیز درخواست کے بعد لکھی جا سکتی ہے جو
  بعد میں شروع ہوئی ہو، اور ٹائم اسٹیمپ پر مبنی کرسر اسے چھوڑ دے گا۔
- **بیچ بندی** — ہر درخواست میں `batch_size` قطاریں (طے شدہ 500)، ہر اجرا میں `max_rows_per_run` قطاریں
  (طے شدہ 10000)، تاکہ بڑا بیک لاگ ایک ٹِک کو روکنے کے بجائے کئی ٹِکس میں نمٹایا جائے۔
- **ترسیل** — کرسر صرف تب آگے بڑھتا ہے جب `send()` کامیابی سے مکمل ہو۔ ناکام بیچ کی صورت میں
  کرسر وہیں رہتا ہے، اس لیے اگلے اجرا میں انہی قطاروں کے لیے دوبارہ کوشش کی جاتی ہے۔ ضمانت
  کم از کم ایک بار ترسیل اور منزل کی طرف نقل مٹانے کی ہے، حقیقی معنوں میں عین ایک بار ترسیل کی نہیں: BigQuery ہر
  قطار کی کلید کال لاگ کی آئی ڈی کو بناتا ہے، جس کا وہ نقل مٹانے کی اپنی مدت کے اندر ممکنہ حد تک لحاظ رکھتا ہے۔
- **بیک وقت اجرا سے تحفظ** — کرون ٹِک اور `POST .../run` ایک ساتھ شروع ہو سکتے ہیں۔ جس منزل کا
  ڈیٹا پہلے ہی بھیجا جا رہا ہو اسے دو بار بھیجنے کے بجائے چھوڑ دیا جاتا ہے (اجرا کے نتیجے میں `skipped: true`)،
  اس لیے بیک وقت اجرا کسی بیچ کو دوبارہ نہیں بھیج سکتا یا کرسر کو پیچھے نہیں لکھ سکتا۔
- **مکمل صفائی کے بعد بحالی** — اگر `cursor_row_id`، `MAX(rowid)` سے آگے نکل جائے (پورا ٹیبل
  صاف کر دیا گیا ہو اور rowids دوبارہ شروع ہوئے ہوں)، تو رنر مستقل طور پر نئے ریکارڈز سے بے خبر رہنے کے بجائے 0 پر واپس آ جاتا ہے۔

### الگ تھلگ رنر اور حدود

Node پر ہر منزل کا اجرا ایک الگ، مختصر مدت کا OS چائلڈ پراسیس شروع کرتا ہے (IPC کے ساتھ `child_process`،
نہ کہ `worker_threads`)۔ باڈی پڑھنا، پے لوڈ JSON کی پارسنگ/سیریلائزیشن، منزل کا
`prepare()` اور منزل کا نیٹ ورک I/O، سب وہیں چلتے ہیں، سرور کے ایونٹ لوپ پر نہیں۔
صرف کنفیگریشن اور پیش رفت کے چھوٹے پیغامات IPC سے گزرتے ہیں؛ ایکسپورٹ شدہ ریکارڈ کبھی
سرور پر واپس نہیں آتے۔ کرون جاب اور ابھی چلائیں کا روٹ وہی عوامی نتیجہ اور بیک وقت اجرا سے تحفظ برقرار رکھتے ہیں۔

چائلڈ، `node:sqlite` استعمال کرتے ہوئے سرور کی حل شدہ `DATA_DIR/storage.sqlite` کو صرف پڑھنے کے لیے کھولتا ہے،
جس میں `busy_timeout=5000` اور `query_only=ON` ہوتے ہیں۔ یہ کوئی DB سنگلٹن امپورٹ نہیں کرتا اور نہ ہی
مائیگریشن، بیک اپ یا SQLite اپ ڈیٹس کرتا ہے۔ گم شدہ/خراب آرٹی فیکٹس کا حساب کتاب (بشمول
خراب آرٹی فیکٹ کا UPDATE) صرف ڈیش بورڈ کے تفصیلی پاتھ میں رہتا ہے۔ دونوں پاتھ ایک خالص
تفصیلی ریزالور استعمال کرتے ہیں؛ ایکسپورٹ غیر ہم وقت فائل سسٹم ریڈز اور وہی آرٹی فیکٹ → پرانا
اِن لائن → پرانی ڈسک → کچھ نہیں کی تلاش کی ترتیب استعمال کرتا ہے۔ جب چائلڈ اپنا ریڈر کھولتا ہے تو اجرا زیادہ سے زیادہ اندراجی rowid کا اسنیپ شاٹ
لیتا ہے؛ بعد کے اندراجات اگلے اجرا تک انتظار کرتے ہیں۔ یہ اندراج کی
حد ہے، طویل مدت کا SQLite ٹرانزیکشن نہیں: نیٹ ورک کے انتظار کے دوران WAL رائٹرز اور چیک پوائنٹس آزاد رہتے ہیں۔
موجودہ قطاروں کی اپ ڈیٹس/حذف اس حد کے باعث منجمد نہیں ہوتے۔

ہر قبول شدہ بیچ کے بعد، چائلڈ تصدیق کا انتظار کرتا ہے۔ سرور پہلے
`advanceLogExportCursor` کے ذریعے کرسر محفوظ کرتا ہے، پھر `ack` بھیجتا ہے؛ اس سے پہلے اگلا بیچ شروع نہیں ہوتا۔
بھیجنے میں ناکامی، کریش یا ٹائم آؤٹ اس بیچ کے کرسر کو آگے بڑھائے بغیر ناکامی درج کرتا ہے۔ پہلے سے
تصدیق شدہ بیچز محفوظ رہتے ہیں؛ زیادہ سے زیادہ صرف ایک غیر تصدیق شدہ بیچ دوبارہ بھیجا جا سکتا ہے۔
کامیابی صرف `done` اور چائلڈ کے درست طور پر بند ہونے کے بعد درج ہوتی ہے۔ ناکامی کی صورت میں چائلڈ کو
SIGTERM سے بند کیا جاتا ہے، 500 ms بعد ضرورت پڑنے پر SIGKILL استعمال ہوتا ہے، اور رنر پراسیس بند ہونے کا انتظار کرتا ہے۔

| ماحولیاتی متغیر                               | طے شدہ | مقصد                                |
| --------------------------------------------- | ------ | ----------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000 | ہر منزل کے لیے حقیقی گزرے وقت کی حد |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024   | چائلڈ کی V8 old-space حد، MB میں    |

غلط/غیر مثبت/غیر صحیح عددی قدروں کی صورت میں طے شدہ قدریں استعمال ہوتی ہیں۔ ہیپ کی ترتیب مجموعی
RSS حد نہیں ہے؛ بہت بڑے بیچز اب بھی چائلڈ کی میموری ختم کر سکتے ہیں اور اجرا کو محفوظ انداز میں ناکام کر سکتے ہیں۔
1024 MB کی طے شدہ حد، باڈیز فعال ہونے پر 512 KiB آرٹی فیکٹس کے طے شدہ 500 قطاروں والے بیچ کے لیے اضافی گنجائش چھوڑتی ہے،
جس میں BigQuery کی بائٹ حصوں میں تقسیم شدہ JSON سیریلائزیشن بھی شامل ہے۔ یہ
باڈیز والے 10000 قطاروں کے بیچ کو محفوظ نہیں بناتی۔ V8 ہیپ ختم ہونے پر ایسی ناکامی درج ہوتی ہے جس پر کارروائی کی جا سکے: بیچ
کا حجم کم کریں یا `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` بڑھائیں؛ کرسر آخری
تصدیق شدہ بیچ پر رہتا ہے۔ پرانی اِن لائن/ڈسک باڈیز جدید آرٹی فیکٹ حد کے تحت نہیں آتیں۔
آپریٹرز کو RSS کے لیے الگ گنجائش مختص کرنا ہوگی، خاص طور پر محدود میموری والے کنٹینرز میں۔

چائلڈ کو وراثت میں صرف حل شدہ `DATA_DIR`، `NODE_ENV`، واضح طور پر مقرر کردہ `TZ` (پرانے طرز کے فائل نام کے
مقامی وقت کا تعین)، موجود ہونے پر `ELECTRON_RUN_AS_NODE`، اور درج ذیل آؤٹ باؤنڈ اِن پٹس ملتے ہیں:
`HTTP_PROXY`، `HTTPS_PROXY`، `ALL_PROXY`، `NO_PROXY` (اور ان کی چھوٹے حروف والی صورتیں)،
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`، `NODE_EXTRA_CA_CERTS`، `SSL_CERT_FILE`، `SSL_CERT_DIR`۔
ایک عالمی Undici ڈسپیچر سرور کے صرف ماحول پر مبنی پراکسی کے تعین اور مقامی ہوسٹ کو
بائی پاس کرنے کے قواعد، بشمول `NO_PROXY`، استعمال کرتا ہے؛ یہ `proxyFetch.ts` یا اس کے DB/فیچر فلیگز درآمد نہیں کرتا۔
آگے بھیجے گئے آؤٹ پٹ اور ریکارڈ کردہ خرابیوں سے پراکسی کی اسناد چھپا دی جاتی ہیں۔ منزل کی اسناد
صرف آغاز کے ایک IPC پیغام میں بھیجی جاتی ہیں، کبھی argv یا ماحول میں نہیں؛ آؤٹ پٹ/خرابی کو آگے بھیجتے وقت
سابقہ لگایا جاتا ہے اور حساس مواد صاف کیا جاتا ہے۔ چائلڈ کے exec آرگیومنٹس میں صرف `ExperimentalWarning` کو غیر فعال کیا جاتا ہے تاکہ
ہر cron اجرا میں Node کی SQLite تنبیہ دہرائی نہ جائے؛ تنبیہات کی دیگر اقسام نظر آتی رہتی ہیں۔

منزل کے ماڈیولز کو Next.js/server-only انحصارات کے بغیر درآمد کیا جا سکنا چاہیے۔ موجودہ
BigQuery نفاذ پہلے ہی اس تقاضے پر پورا اترتا ہے۔ رسائی ٹوکن کے کیش صرف چائلڈ کے
اجرا تک برقرار رہتے ہیں، مختلف اجرا کے درمیان نہیں۔ Node معاونت یافتہ رن ٹائم ہے (`package.json` کے engines)، لیکن README کا Bun
تنصیب کا سیکشن اور `Dockerfile.bun` بھی `bun:sqlite` (`src/lib/db/core.ts` / اڈاپٹرز) استعمال کرتے ہوئے پروڈکشن مطابقت کا راستہ
پیش کرتے ہیں۔ لہٰذا Bun کے تحت برآمدات سابقہ
اسی پروسیس میں چلنے والا طریقہ برقرار رکھتی ہیں اور ایک بار تنبیہ جاری کرتی ہیں: چائلڈ کی ہیپ/ٹائم آؤٹ علیحدگی دستیاب نہیں۔ ایونٹ لوپ اور OOM کی علیحدگی کے لیے
Node استعمال کریں؛ یہاں Bun کو صرف ڈیولپمنٹ تک محدود نہیں سمجھا جاتا۔

جب `includeBodies` فعال ہو، تو گھنٹہ وار پے لوڈ کا انبار جمع کرنے کے بجائے
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` جیسا منٹوں کی سطح کا وقفہ ترجیح دیں۔
بیچ اور قطار کی حدود پھر بھی ہر اجرا کو محدود رکھتی ہیں۔ ہر اجرا میں ہر منزل کے لیے پروسیس شروع کرنے کی لاگت آتی ہے؛
یہ سرور کے ایونٹ لوپ کی علیحدگی کے بدلے آغاز کی معمولی لاگت کا تبادلہ ہے، مجموعی CPU استعمال میں کمی نہیں۔

### پے لوڈز (پرامپٹس اور تکمیلات)

بطور طے شدہ، برآمد میں صرف وہ خلاصہ فیلڈز شامل ہوتی ہیں جو Logs کی **فہرست** میں دکھائی جاتی ہیں۔
**پرامپٹس اور جوابات برآمد کریں** (`includeBodies`) فعال کرنے سے ہر کال کے لیے وہ مواد بھی بھیجا جاتا ہے جو Logs کے **تفصیل**
پین میں دکھائی دیتا ہے:

| فیلڈ                             | اس میں کیا ہوتا ہے                                                 |
| -------------------------------- | ------------------------------------------------------------------ |
| `request_body` / `response_body` | کال کے پے لوڈز، جیسے ڈیش بورڈ انہیں دکھاتا ہے                      |
| `pipeline_route_decision`        | راؤٹر نے کون سی منزل اور ماڈل منتخب کیا                            |
| `pipeline_client_request`        | خام درخواست، بالکل اسی طرح جیسے کلائنٹ نے بھیجی                    |
| `pipeline_openai_request`        | اندرونی OpenAI ساخت میں تبدیلی کے بعد                              |
| `pipeline_provider_request`      | حقیقتاً اپ اسٹریم بھیجی گئی درخواست، فراہم کنندہ کی مخصوص ساخت میں |
| `pipeline_provider_response`     | خام اپ اسٹریم جواب                                                 |
| `pipeline_client_response`       | کال کرنے والے کو واپس دیا گیا مواد                                 |
| `pipeline_error`                 | ناکام کال کے لیے پائپ لائن کی سطح پر خرابی کی تفصیل                |
| `bodies_truncated`               | جب اوپر کی کوئی فیلڈ `maxBodyBytes` کی حد تک پہنچے تو True         |

یہ پرامپٹ کا مواد ہے، اس لیے یہ **بطور طے شدہ بند** ہوتا ہے اور دانستہ طور پر ہر منزل کے لیے الگ انتخاب ہے۔
وہی مواد بھیجا جاتا ہے جو ڈیش بورڈ دکھاتا ہے، کیونکہ برآمد اور `getCallLogById` تفصیلات کے تعین کا ایک ہی طریقہ
استعمال کرتے ہیں: پے لوڈز
لکھے جاتے وقت ہی ذاتی شناختی معلومات سے صاف اور خفیہ معلومات سے پاک کر دیے جاتے ہیں، اور
`noLog` API کلید کے ساتھ کی گئی کال کوئی پے لوڈ محفوظ نہیں کرتی، اس لیے برآمد کرنے کے لیے کچھ نہیں ہوتا۔

پے لوڈز فائل سسٹم آرٹیفیکٹ سے ہر قطار کے لیے پڑھے جاتے ہیں، لہٰذا ڈیٹا کی مکمل بازیافت صرف ان منزلوں کے لیے چلتی ہے
جنہوں نے اس کی درخواست کی ہو۔ آرٹیفیکٹ غائب یا خراب ہونے پر بیچ کو ناکام کرنے اور کرسر کو پھنسانے کے بجائے
اس کا خلاصہ null پے لوڈز کے ساتھ برآمد کیا جاتا ہے۔

`maxBodyBytes` (طے شدہ 262144) ہر فیلڈ کی حد مقرر کرتا ہے۔ طویل پے لوڈز **حذف کرنے کے بجائے
مختصر کیے جاتے ہیں** — کٹا ہوا پرامپٹ بھی یہ بتاتا ہے کہ "کیا پوچھا گیا تھا" — اور قطار کو
`bodies_truncated` سے نشان زد کیا جاتا ہے۔ اسٹریم کیے گئے، ٹکڑا بہ ٹکڑا تغیرات برآمد نہیں کیے جاتے؛ مکمل جوڑا گیا جواب
پہلے ہی `pipeline_provider_response` اور `pipeline_client_response` میں موجود ہوتا ہے۔

## 4. BigQuery منزل

ترتیب کی کلیدیں (`type: "bigquery"`):

| کلید                 | نوٹس                                                                          |
| -------------------- | ----------------------------------------------------------------------------- |
| `projectId`          | وہ GCP پروجیکٹ جس میں ڈیٹاسیٹ موجود ہے                                        |
| `datasetId`          | `[A-Za-z0-9_]+`                                                               |
| `tableId`            | `[A-Za-z0-9_]+`                                                               |
| `location`           | صرف اس وقت استعمال ہوتا ہے جب ڈیٹاسیٹ بنانا ضروری ہو (طے شدہ `EU`)            |
| `serviceAccountJson` | سروس اکاؤنٹ کی کلید۔ خفیہ: ذخیرہ شدہ حالت میں رمز شدہ، کبھی واپس نہیں کی جاتی |
| `autoCreate`         | پہلی برآمد پر ڈیٹاسیٹ اور ٹیبل بنائیں (طے شدہ `true`)                         |

سروس اکاؤنٹ کو ہدف ٹیبل پر `bigquery.tables.updateData` کی اجازت درکار ہے، اور
جب `autoCreate` فعال ہو تو `bigquery.datasets.create` / `bigquery.tables.create` کی بھی۔

ترتیب دیا گیا بیچ **کرسر** کی اکائی ہے، HTTP کی نہیں: `send()` اسے زیادہ سے زیادہ 500 قطاروں والی insertAll
کالز میں تقسیم کرتا ہے، اس لیے بڑا `batch_size` بھی BigQuery کی 10 MB فی درخواست حد سے تجاوز نہیں کر سکتا۔
عارضی اسٹیٹس (408/429/500/502/503/504) پر اسی insertIds کو دوبارہ استعمال کرتے ہوئے، تیزی سے بڑھتے
وقفے کے ساتھ تین بار تک دوبارہ کوشش کی جاتی ہے؛ توثیق اور اسکیما کی ناکامیوں پر پورا عمل ضائع کرنے کے بجائے
پہلی ہی کوشش میں استثنا پھینک دیا جاتا ہے۔

ابھی ابھی بنایا گیا ٹیبل اسٹریمنگ اینڈپوائنٹ کو فوراً نظر نہیں آتا، جو چند سیکنڈ تک
404 کا جواب دیتا ہے۔ اس 404 پر دوبارہ کوشش کی جاتی ہے، لیکن **صرف تب جب اسی عمل نے ٹیبل بنایا ہو** —
واقعی غیر موجود ٹیبل کی صورت میں اب بھی فوری ناکامی ہوتی ہے۔ یاد رہے کہ حال ہی میں حذف کیے گئے نام سے
ٹیبل دوبارہ بنانے پر BigQuery کئی منٹ تک اسٹریمنگ اندراجات قبول نہیں کرتا؛ یہ
حذف کرنے کے بعد دوبارہ بنانے کا نتیجہ ہے، اس لیے ٹیبل حذف کر کے دوبارہ شامل کرنے کے بجائے نیا نام استعمال کریں۔

**جزوی ناکامی HTTP 200 کے ساتھ آتی ہے، جس میں `insertErrors[]` خالی نہیں ہوتا۔** اسے
ناکامی سمجھ کر استثنا پھینکا جاتا ہے، اور یہی کرسر کو ان قطاروں سے آگے بڑھنے سے روکتا ہے جنہیں BigQuery نے کبھی
قبول نہیں کیا؛ `tests/unit/log-export-bigquery.test.ts` اس رویے کی تصدیق کرتا ہے۔

نقل و حمل سادہ REST کے ذریعے ہوتی ہے — خود دستخط شدہ RS256 assertion کو
`https://oauth2.googleapis.com/token` پر ایک رسائی ٹوکن کے بدلے پیش کیا جاتا ہے، پھر قطاریں `tabledata.insertAll` کو بھیجی جاتی ہیں۔ کوئی Google SDK
شامل نہیں کیا جاتا۔ رسائی ٹوکنز ہر (سروس اکاؤنٹ، اسکوپ) کے لیے اسی پراسیس میں کیش کیے جاتے ہیں۔

بنائے گئے ٹیبل میں Logs ٹیب کے ہر فیلڈ کے لیے ایک کالم، نیز `exported_at` ہوتا ہے، اور اس کی ترتیب
کال لاگز پر حقیقتاً کی جانے والی کوئریز کے مطابق ہوتی ہے:

- **`timestamp` پر یومیہ پارٹیشننگ**، تاکہ تاریخ کی حد والی کوئری صرف انہی دنوں کو اسکین کرے۔
- **`api_key_name`, `provider`, `model`, `status` کے لحاظ سے کلسٹرنگ** (اسی ترتیب میں)، تاکہ
  اسے کس نے چلایا، یہ کہاں گیا، یا آیا یہ ناکام ہوا، ان بنیادوں پر فلٹر لگانے سے ہر پارٹیشن کے اندر غیر متعلقہ بلاکس چھانٹ دیے جائیں۔ BigQuery
  زیادہ سے زیادہ چار کلسٹرنگ کالمز کی اجازت دیتا ہے اور ترتیب اہم ہے: صرف `api_key_name` پر فلٹر
  بلاکس چھانٹ دیتا ہے، جبکہ صرف `status` پر فلٹر ایسا نہیں کرتا۔
- **اختیاری پارٹیشن برقرار رکھنے کی مدت** بذریعہ `partitionExpirationDays` (0 سب کچھ برقرار رکھتا ہے)، جس کا اطلاق
  ٹیبل بناتے وقت ہوتا ہے۔

دونوں ترتیبات تخلیق کے وقت لاگو ہوتی ہیں۔ موجودہ ٹیبل اپنی پہلے سے موجود ترتیب برقرار رکھتا ہے، اس لیے
اگر آپ انہیں اپنانا چاہتے ہیں تو منزل کے لیے نئی ٹیبل آئی ڈی مقرر کریں۔

`tests/unit/log-export-bigquery.test.ts` اس بات کی تصدیق کرتا ہے کہ میپر اور ٹیبل اسکیما مکمل طور پر
ہم آہنگ رہیں، تاکہ برآمد کے دوران کال لاگ کا کوئی نیا کالم خاموشی سے حذف نہ ہو جائے۔

بیچز کو قطاروں کی تعداد اور سیریلائز شدہ بائٹس **دونوں** کے لحاظ سے حصوں میں تقسیم کیا جاتا ہے۔ پے لوڈز برآمد ہونے لگیں تو
صرف قطاروں کی تعداد کافی نہیں ہوتی: پرامپٹس پر مشتمل 500 قطاریں دسیوں میگابائٹس کی ہو سکتی ہیں، اور insertAll
10 MB سے بڑی درخواست مسترد کر دیتا ہے۔ ہر حصہ 500 قطاروں یا 9 MB پر مکمل ہو جاتا ہے، جو بھی پہلے پورا ہو۔

## 5. OTLP/HTTP ٹریسز کی منزل

ترتیب میں `type: "otlp-http"` استعمال ہوتا ہے۔ یہ محفوظ شدہ کال لاگز کی ایک طے شدہ، کرسر پر مبنی برآمد ہے،
نہ کہ `open-sse/services/routing/otel.ts` میں موجود بہترین ممکنہ کوشش کے تحت کام کرنے والا لائیو روٹنگ ایونٹ سنک۔
یہ اس سنک کے ماحولیاتی متغیرات، ٹائمرز یا بفرز کو نہ پڑھتا ہے اور نہ تبدیل کرتا ہے۔ دونوں کو فعال کرنے سے اسپینز کی دو آزاد اقسام پیدا ہو سکتی ہیں؛
ان کال لاگ اسپینز کو الگ پہچاننے کے لیے `omniroute.log-export` انسٹرومنٹیشن اسکوپ استعمال کریں۔

| کلید                     | ڈیفالٹ / مقصد                                                                  |
| ------------------------ | ------------------------------------------------------------------------------ |
| `endpoint`               | مکمل HTTP(S) ٹریسز URL درکار ہے؛ `/v1/traces` لاحقہ شامل نہیں کیا جاتا         |
| `headers`                | اختیاری `Name: value` سطریں یا سٹرنگز کا JSON آبجیکٹ؛ مرموز                    |
| `requestHeaderAllowlist` | خالی (بند)؛ اسپین خصوصیات کے طور پر محفوظ کرنے کے لیے کلائنٹ ہیڈر کے نام/سابقے |
| `serviceName`            | `omniroute`؛ ریسورس `service.name`                                             |
| `langfuseMapping`        | `false`؛ Langfuse کی جنریشن/سیشن/صارف خصوصیات شامل کرتا ہے                     |
| `identity`               | `pseudonymous`، `keyName`، یا `none`                                           |
| `paths`                  | `/v1/chat/completions`، `/v1/responses`، `/v1/messages`                        |
| `timeoutMs`              | ہر HTTP کوشش کے لیے `30000`                                                    |
| `environment`            | غیر متعین؛ اختیاری `langfuse.environment`                                      |

عمومی ڈیش بورڈ ان فیلڈز کو دکھاتا ہے۔ `paths` ایک API ارے یا ایسا متنی خانہ قبول کرتا ہے
جس میں عین پاتھ نئی سطروں/کوما سے الگ کیے گئے ہوں۔ ایمبیڈنگز، ری رینک اور دیگر پاتھ
چھوڑ دیے جاتے ہیں، جب تک انہیں واضح طور پر اجازت نہ دی جائے۔ چھوڑی گئی قطاریں بھی کرسر کو آگے بڑھاتی ہیں؛ موجودہ
رنر کے `exported`/`exportedTotal` کاؤنٹرز قبول شدہ اسپینز کے بجائے پراسیس کی گئی ماخذ قطاریں شمار کرتے ہیں،
جن میں فلٹر کی گئی قطاریں بھی شامل ہیں۔ فلٹرنگ چائلڈ میں کی جاتی ہے، اس کے
IPC/کرسر معاہدے کو تبدیل کیے بغیر۔

URL کی توثیق کے لیے `src/shared/network/outboundUrlGuard.ts` کا DB سے آزاد `parseAndValidateNonMetadataUrl` ہیلپر
استعمال ہوتا ہے: یعنی `block-metadata` پالیسی۔ اس میں میٹاڈیٹا/پروٹوکول/URL میں شامل اسناد کی وہی
غیر مشروط جانچ ہوتی ہے جو نجی URLs کی اجازت والے ویب ہک ویلیڈیٹر میں ہوتی ہے،
لیکن یہ جان بوجھ کر کسی عالمی فیچر فلیگ اووررائیڈ کے بغیر localhost/LAN اہداف کی اجازت دیتا ہے۔
اس سے خود میزبانی کردہ Langfuse، Phoenix، Tempo اور Collector
اینڈپوائنٹس، بشمول نجی HTTP اینڈپوائنٹس، استعمال کیے جا سکتے ہیں۔ کلاؤڈ میٹاڈیٹا ہوسٹس ہمیشہ مسدود رہتے ہیں۔
ری ڈائریکٹس کی پیروی نہیں کی جاتی، اس لیے کوئی کلیکٹر اسناد کو کسی دوسرے ہوسٹ پر ری ڈائریکٹ نہیں کر سکتا۔
موجودہ لغوی URL گارڈ کی طرح، یہ DNS ریزولیوشن کو مقید نہیں کرتا؛ صرف
آپریٹر کے زیرِ اختیار ہوسٹس ترتیب دیں۔ جب بھی اینڈپوائنٹ کسی قابلِ اعتماد نیٹ ورک پر نہ ہو، HTTPS کو ترجیح دیں۔

### پے لوڈ اور ترسیل

OTLP/HTTP JSON (`ExportTraceServiceRequest`، `Content-Type: application/json`) ہر اجازت یافتہ قطار کے لیے ایک
CLIENT اسپین لے جاتا ہے، جس کا نام اس کا عین درخواست پاتھ ہوتا ہے۔ پاتھ پر مبنی نام
Chat Completions، Responses اور Messages میں فرق کرتے ہیں، بغیر اس کے کہ ماڈل یا شناختی ڈیٹا
اسپین کے نام میں شامل ہو۔ ریسورس خصوصیات میں `service.name` اور پیکیج کا `service.version` شامل ہیں۔

عام چیٹ کوشش لاگر (`open-sse/handlers/chatCore/attemptLogging.ts`) تکمیل پر
`duration = Date.now() - startTime` لکھتا ہے اور ٹائم اسٹیمپ فراہم نہیں کرتا؛
`src/lib/usage/callLogs.ts` میں `saveCallLogOperation` ٹائم اسٹیمپ کو ڈیفالٹ طور پر لکھنے
(تکمیل) کے وقت پر مقرر کرتا ہے۔ لہٰذا برآمد میں اختتام = قطار کا ٹائم اسٹیمپ اور آغاز = اختتام − دورانیہ
مقرر ہوتا ہے (ملی سیکنڈز، جنہیں اعشاری نینو سیکنڈز میں تبدیل کیا جاتا ہے)۔ کال کرنے والے کے فراہم کردہ تاریخی ٹائم اسٹیمپس
بھی اختتامی وقت کے طور پر محفوظ رکھے جاتے ہیں؛ ہر قطار کے لیے آغاز/تکمیل میں فرق بتانے والا کوئی اشارہ نہیں ہے۔
null دورانیہ صفر بن جاتا ہے۔ غلط/غائب ٹائم اسٹیمپس غیر متعین اسپینز بنانے کے بجائے
بیچ کو ناکام کر دیتے ہیں۔ `ttftMs` کی قدر null ہو سکتی ہے اور یہ `omniroute.ttft_ms` سے میپ ہوتا ہے۔

خصوصیات میں `gen_ai.operation.name="chat"`، فراہم کنندہ، درخواست کردہ/جوابی ماڈل،
ان پٹ/آؤٹ پٹ ٹوکنز، اختیاری کیش ریڈ/کیش تخلیق/ریزننگ ٹوکنز، HTTP اسٹیٹس،
کومبو، کیش ماخذ، سیشن ٹیگ اور ارتباطی شناخت کنندہ شامل ہیں۔ صحیح عددی OTLP قدریں اور ٹائم اسٹیمپس
اعشاری سٹرنگز ہوتے ہیں؛ سٹرنگز، بولینز اور کسری اعداد اپنی اصل OTLP قدر کی
اقسام استعمال کرتے ہیں۔ خرابی والے اسپینز کا اسٹیٹس ERROR اور صاف کردہ اسٹیٹس پیغام ہوتا ہے۔ معیاری
ریکارڈ میں اپ اسٹریم ہوسٹ URL نہیں ہوتا، اس لیے کلیکٹر کو غلطی سے
ماڈل سرور قرار دینے کے بجائے `server.address` چھوڑ دیا جاتا ہے۔ لاگت برآمد نہیں کی جاتی۔

صرف `includeBodies=true` ہی مواد لوڈ کرتا ہے۔ `langfuseMapping=false` کے ساتھ،
`gen_ai.input.messages` / `gen_ai.output.messages` میں صاف کردہ درخواست/جواب
باڈی JSON اسی صورت میں ہوتا ہے جس میں OmniRoute نے اسے محفوظ کیا تھا (اگر پارس کرنا ممکن ہو تو معیاری صورت میں)، نہ کہ ازسرِنو تشکیل دیا گیا semconv
پیغامات کا ارے۔ کٹی ہوئی/غیر JSON باڈیز خام متن ہی رہتی ہیں۔ `langfuseMapping=true` کے ساتھ،
باڈیز صرف `langfuse.observation.input` / `langfuse.observation.output` کے طور پر بھیجی جاتی ہیں؛
`gen_ai.*.messages` خصوصیات چھوڑ دی جاتی ہیں تاکہ ہر باڈی ایک ہی بار بھیجی جائے۔ دونوں طریقے
موجودہ مواد لوڈ کرنے کے راستے سے `maxBodyBytes` وراثت میں لیتے ہیں؛
`omniroute.bodies_truncated=true` کٹاؤ کی نشان دہی کرتا ہے۔
یہ منزل کوئی اضافی پائپ لائن اسنیپ شاٹس یا غیر صاف کردہ آرٹیفیکٹس کی خواندگی شامل نہیں کرتی؛
اختیاری درخواست ہیڈر کی گرفت کے لیے ذیل میں بیان کردہ موجودہ لوڈ شدہ کلائنٹ اسنیپ شاٹ استعمال ہوتا ہے۔
باڈیز برآمد کرتے وقت، گھنٹہ وار بقایا جمع کرنے کے بجائے
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` جیسا منٹ کی سطح کا وقفہ استعمال کریں۔

### اختیاری کلائنٹ درخواست ہیڈرز

ہیڈر کی گرفت **ڈیفالٹ طور پر بند ہے**۔ منزل کی ترتیب میں `requestHeaderAllowlist` مقرر کریں
اور **پرامپٹس اور جوابات برآمد کریں** فعال کریں (منزل پر `includeBodies: true`)۔
اجازت یافتہ فہرست ایک API ارے یا نئی سطروں/کوما سے الگ کیے گئے ناموں والا متنی خانہ قبول کرتی ہے:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

ناموں کی مطابقت بڑے اور چھوٹے حروف کے فرق کے بغیر عین مطابق ہوتی ہے، سوائے اس صورت کے جب آخر میں موجود واحد `*` ہیڈر کے نام کا ایک غیر خالی سابقہ منتخب کرے۔ تنہا `*`، درمیان میں موجود وائلڈ کارڈز اور نامعتبر HTTP ہیڈر نام مسترد کر دیے جاتے ہیں۔
زیادہ سے زیادہ 64 سلیکٹرز ہو سکتے ہیں، اور ہر ایک کا نام/سابقہ زیادہ سے زیادہ 256 ASCII بائٹس کا ہو سکتا ہے۔
یہ ترتیب `headers` سے الگ ہے، جو کلیکٹر کے سامنے ایکسپورٹر کی توثیق کرتا ہے۔

کیپچر صرف `pipeline_client_request` کو پڑھتا ہے، جو محفوظ کردہ تفصیلی پائپ لائن کے
`clientRawRequest` (یا پرانے `clientRequest`) سے بھرا جاتا ہے۔ یہ کبھی متبادل کے طور پر فراہم کنندہ کی درخواست کے ہیڈرز استعمال نہیں کرتا۔
درخواست ریکارڈ ہوتے وقت تفصیلی پائپ لائن لاگنگ فعال ہونی چاہیے تھی۔ اگر
`includeBodies` غیر فعال ہو، یا کلائنٹ اسنیپ شاٹ کا JSON غائب، خراب یا کٹا ہوا ہو، تو کوئی ہیڈر
اوصاف خارج نہیں کیے جاتے۔ `maxBodyBytes` بڑھانے سے ایکسپورٹ کے وقت اسنیپ شاٹ کٹنے سے بچا جا سکتا ہے؛
یہ ایسی تفصیل بحال نہیں کر سکتا جو کبھی محفوظ ہی نہ ہوئی ہو۔ 1 MiB سے بڑا یا
256 سے زیادہ ہیڈر اندراجات رکھنے والا اسنیپ شاٹ نظر انداز کر دیا جاتا ہے۔ موجودہ پرامپٹ/جواب ایکسپورٹ ہیڈر کیپچر کے ساتھ
فعال رہتا ہے؛ اجازت یافتہ فہرست صرف ہیڈرز کی ہائیڈریشن کا موڈ فراہم نہیں کرتی۔

منتخب قدریں `http.request.header.<full lowercase header name>` کے OTLP اسٹرنگ ارے بن جاتی ہیں،
خواہ صرف ایک اسٹرنگ ہی ہو۔ مثلاً، `X-OmniRoute-Meta-Team: example-team`،
`http.request.header.x-omniroute-meta-team` بن جاتا ہے، جس کی قدر
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}` ہوتی ہے۔
مکمل سابقہ برقرار رہتا ہے: یہ عام ہیڈرز ہیں، جن پر نہ کاروباری فیلڈ کی پارسنگ ہوتی ہے اور نہ
`omniroute.metadata.*` / Langfuse میٹاڈیٹا میں تبدیلی۔ `langfuseMapping` ہیڈرز کے
مفہوم کو نہیں بدلتا۔ منتخب کردہ واحد قدر والا `User-Agent` معیاری اسکیلر
`user_agent.original` بھی مقرر کرتا ہے۔ ایک قدر کے اندر موجود کوما پر تقسیم نہیں کی جاتی۔ حروف کی بڑی/چھوٹی شکلوں والے نام محفوظ کردہ
اندراجات کی ترتیب میں ضم ہوتے ہیں؛ کسی بھی نامعتبر شکل کی موجودگی پورے ہیڈر کو خارج کر دیتی ہے۔ اوصاف چھوٹے حروف والے نام کے لحاظ سے ترتیب دیے جاتے ہیں۔

Authorization، Proxy-Authorization، Cookie، Set-Cookie، API-key ہیڈرز، ایسے نام جن میں
auth/token/secret/password/credential کی نشانیاں ہوں، اور اندرونی گیٹ وے کی اسناد ہمیشہ
خارج رہتی ہیں، چاہے منتخب کی گئی ہوں یا اسٹوریج میں جزوی طور پر چھپائی گئی ہوں۔ معلوم اسنادی نمونوں کے لیے
مشترکہ اسناد شناخت کنندہ دوبارہ استعمال ہوتا ہے؛ اخفا کی نشانیاں چھوڑ دی جاتی ہیں، انہیں محفوظ قدروں کے طور پر ایکسپورٹ نہیں کیا جاتا۔
صرف اسٹرنگز اور غیر خالی اسٹرنگ ارے قبول کیے جاتے ہیں؛ اعداد یا آبجیکٹس کو زبردستی تبدیل نہیں کیا جاتا۔
نامعتبر نام، پروٹوٹائپ کیز، کنٹرول حروف (افقی ٹیب کے سوا) اور خراب Unicode
بیچ کو ناکام کیے بغیر اور خرابیوں میں ان کا مواد ظاہر کیے بغیر نظر انداز کر دیے جاتے ہیں۔

ہر اسپین زیادہ سے زیادہ 32 ہیڈرز، فی ہیڈر 16 قدریں، فی قدر 4096 UTF-8 بائٹس،
اور کیپچر کردہ ہیڈر ناموں اور قدروں میں مجموعی طور پر 16384 UTF-8 بائٹس کیپچر کرتا ہے۔ حد سے بڑے/نامعتبر ہیڈرز
مکمل طور پر چھوڑ دیے جاتے ہیں، کاٹے نہیں جاتے۔ انتخاب آپریٹر کی رازداری سے متعلق صوابدید ہے: بظاہر محفوظ ناموں
میں بھی ذاتی ڈیٹا ہو سکتا ہے، اور یہ حدود/شناخت کنندگان عمومی PII صاف کرنے کا نظام نہیں ہیں۔

### ترسیل کی حدود

درخواستیں، لفافے سمیت، 500 اسپینز اور 4 MiB UTF-8 JSON تک محدود ہیں۔
کرسر بیچ کی پہلی درخواست سے پہلے ہر اجازت یافتہ اسپین کا حجم جانچا جاتا ہے۔ حد سے بڑا انفرادی
اسپین اس بیچ کا کوئی حصہ نہیں بھیجتا اور `maxBodyBytes` کم کرنے کی رہنمائی کے ساتھ
ناکام ہوتا ہے؛ اسے خاموشی سے چھوڑا نہیں جاتا۔ پیشگی جانچ صرف ریکارڈ کے حوالے اور
بائٹس کی تعداد برقرار رکھتی ہے، اور ہر عارضی اسپین/JSON کو حذف کر دیتی ہے؛ بیچ کی دوسری سیریلائز شدہ نقل رکھنے کے
بجائے محدود حجم کے حصوں کے لیے اسپینز دوبارہ بنائے جاتے ہیں۔ HTTP 408/429/5xx، نیٹ ورک کی ناکامیوں اور ٹائم آؤٹس پر زیادہ سے زیادہ
تین کوششیں کی جاتی ہیں، جن میں 250/500 ms کا اسّی تاخیر کا وقفہ ہوتا ہے۔ `Retry-After` میں سیکنڈز یا HTTP تاریخیں
تاخیر کو 5 سیکنڈ تک بڑھا سکتی ہیں۔ دیگر اسٹیٹس فوری ناکام ہوتے ہیں۔ OTLP 2xx کی جزوی نامنظوری بھی
ضائع شدہ اسپین کی تصدیق کرنے کے بجائے خرابی پیدا کرتی ہے؛ خالی یا درست JSON تصدیقات قبول کی جاتی ہیں، اور
جواب پڑھنے کی حد 64 KiB ہے۔

خرابیوں میں صرف ایکسپورٹر کے اپنے حقائق ہوتے ہیں: HTTP اسٹیٹس، دوبارہ کوشش کی قسم، کوششوں اور بھیجے گئے اسپینز
کی تعداد، یا تصدیق/نیٹ ورک کی ناکامی کے مقررہ الفاظ۔ کلیکٹر کے جواب کے متن،
جزوی کامیابی کی تعداد اور جواب کے ہیڈرز کبھی خرابیوں، لاگز یا
ڈیش بورڈ میں نقل نہیں کیے جاتے۔ ناکام یا جزوی طور پر قبول شدہ بیچ کی تصدیق نہیں ہوتی: منزل اس اسٹیٹس کے ساتھ
ناکامی دکھاتی ہے، کرسر آخری تصدیق شدہ بیچ پر رہتا ہے، اور اگلا اجرا
وہی قطاریں دوبارہ بھیجتا ہے۔ مستقل اسٹیٹس اس وقت تک ناکام رہتے ہیں جب تک کلیکٹر یا ترتیب
درست نہ کر دی جائے۔ جواب کی تفصیلات کے لیے کلیکٹر کے اپنے لاگز استعمال کریں۔ کال لاگ کی خرابیوں کے خلاصوں میں
ان کا الگ اخفا برقرار رہتا ہے۔
`prepare()` کچھ بھی فراہم نہیں کرتا؛ ٹیسٹ عین `{"resourceSpans":[]}` پوسٹ کرتا ہے اور
کال لاگ اسپینز لکھے بغیر HTTP اسٹیٹس بتاتا ہے۔

ٹریس آئی ڈیز اور اسپین آئی ڈیز،
`"omniroute.trace\\0" + callLogId` اور `"omniroute.span\\0" + callLogId` پر SHA-256 کے پہلے 32/16 ہیکس ہندسے ہیں۔ دوبارہ بھیجنے پر
وہی آئی ڈیز استعمال ہوتی ہیں۔ یہ نقل ختم کرنے کی ضمانت نہیں ہے: بعض بیک اینڈز، بشمول Langfuse
v4 ان جیشن، ایک ہی آئی ڈی والے اسپینز کی نقل ختم نہیں کرتے۔ کریش یا کسی حصے کی جزوی ناکامی
زیادہ سے زیادہ ایک غیر تصدیق شدہ کرسر بیچ کو دوبارہ بھیج سکتی ہے؛ وہ پورا بیچ نقل ہو سکتا ہے،
نہ کہ صرف اس کا آخری HTTP حصہ۔ اس سمجھوتے کو مدنظر رکھتے ہوئے کرسر بیچ کا حجم منتخب کریں۔

### Langfuse کی مثال

خود میزبانی کردہ Langfuse انسٹینس کے لیے یہ فیلڈز ترتیب دیں:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Authorization کی قدر مقامی طور پر لفظی `public-key:secret-key`
اسٹرنگ کی Base64 صورت میں بنائیں (مثلاً `Buffer.from(publicKey + ":" + secretKey).toString("base64")` سے)۔
حقیقی اسناد لاگز، اسکرین شاٹس یا ایشوز میں چسپاں نہ کریں۔ میپنگ خودکار طور پر
`x-langfuse-ingestion-version: 4` مقرر کرتی ہے؛ Authorization اب بھی `headers` میں فراہم کیا جاتا ہے۔
ہیڈرز اور تیار کردہ شناختی سالٹ دونوں موجودہ مرموز خفیہ فیلڈ
کے طریقۂ کار اور API پلیس ہولڈرز استعمال کرتے ہیں؛ `STORAGE_ENCRYPTION_KEY` درکار ہے۔

میپنگ میں جنریشن کی قسم/ماڈل، JSON استعمال کی تفصیلات (ان پٹ/آؤٹ پٹ/کل اور دستیاب
کیش کیز)، JSON ان پٹ/آؤٹ پٹ اسنیپ شاٹس، ERROR/DEFAULT سطح، صاف کیا گیا اسٹیٹس پیغام،
ٹریس کا نام، سیشن آئی ڈی، اختیاری ماحول اور فراہم کنندہ، درخواست کردہ ماڈل، پاتھ، کومبو، کیش
کے ماخذ اور اسٹیٹس کے لیے قابلِ فلٹر
`langfuse.observation.metadata.<key>` شامل ہوتے ہیں۔ `langfuse.observation.completion_start_time` صرف
تب آغاز + TTFT پر ISO 8601 ہوتا ہے جب TTFT معلوم ہو اور دورانیے کے اندر ہو۔ لاگت کے کوئی ایٹریبیوٹس نہیں بھیجے جاتے۔

شناخت کے موڈز `langfuse.user.id` پر لاگو ہوتے ہیں:

- `pseudonymous` (ڈیفالٹ): API کلید کی اندرونی آئی ڈی کا HMAC-SHA256، ہر منزل کے لیے ایک بے ترتیب
  32 بائٹ سالٹ کے ساتھ۔ اگر سالٹ موجود نہ ہو تو اسے تخلیق کے وقت بنایا جاتا ہے، `identitySalt`
  کے طور پر انکرپٹ کیا جاتا ہے، کبھی واپس نہیں کیا جاتا، اور ترامیم کے دوران برقرار رکھا جاتا ہے۔ کلید کی خام آئی ڈیز کبھی
  اسپین ایٹریبیوٹس میں شامل نہیں کی جاتیں۔ کسی منزل کا سالٹ دوبارہ بنانے/روٹیٹ کرنے سے شناختیں بدل جاتی ہیں۔
- `keyName`: کنفیگر کردہ API کلید کا نام، جو جان بوجھ کر آپریٹر کے اس لیبل کو ظاہر کرتا ہے۔
- `none`: کوئی صارف آئی ڈی نہیں۔ سیشن ٹیگز موجود ہوں تو پھر بھی ایکسپورٹ کیے جاتے ہیں؛ یہ موڈز
  من مانے پرامپٹ مواد یا آپریٹر کے فراہم کردہ سیشن/کوریلیشن لیبلز کو گمنام نہیں بناتے۔

### بیک فِل کے بغیر آغاز

صرف تخلیق کے وقت، **موجودہ مقام سے شروع کریں (موجودہ لاگز چھوڑ دیں)** فعال کریں یا
تخلیق کی API پے لوڈ کی بالائی سطح پر `startFromCurrentPosition: true` پاس کریں۔ یہ موجودہ کرسر
ہیلپرز استعمال کرتے ہوئے `cursor_row_id` کو محفوظ شدہ کال لاگ کے موجودہ زیادہ سے زیادہ rowid پر سیٹ کرتا ہے،
بغیر کسی مائیگریشن کے۔ ڈیفالٹ false ہے (کرسر 0 اور محفوظ شدہ ہسٹری کی بیک فِل)۔
یہ اپ ڈیٹ کے وقت کرسر ری سیٹ کرنے کی ترتیب نہیں ہے۔

مشترکہ `ttftMs` اضافے سے BigQuery میپر
اور نئے ٹیبل کے اسکیما میں ایک nullable `ttft_ms` کالم بھی شامل ہوتا ہے: اس کا اسکیما ٹیسٹ تقاضا کرتا ہے کہ ہر معیاری ریکارڈ فیلڈ کا ایک
کالم ہو۔ موجودہ ٹیبلز کی ایکسپورٹ بلا تبدیلی جاری رہتی ہے: `prepare()` ٹیبل کا اسکیما پڑھتا ہے اور
جب وہ کالم موجود نہ ہو تو صرف `ttft_ms` کو چھوڑ دیتا ہے۔ اگلی بار چلانے پر TTFT حاصل کرنے کے لیے
nullable INT64 کالم شامل کریں، یا نیا ٹیبل استعمال کریں۔ کسی PATCH، خودکار اسکیما تبدیلی یا اضافی
اجازتوں کی ضرورت نہیں؛ قطار کے باقی تمام فیلڈز کی سخت اسکیما جانچ برقرار رہتی ہے۔

## 6. منزل شامل کرنا

1. `src/lib/logExport/destinations/<name>.ts` بنائیں جو ایک `LogExportDestinationType` ایکسپورٹ کرے:
   ایک Zod `configSchema`، UI کے لیے `fields` کی وضاحتی صف، `secretFields`، اور ایک
   `createClient(config)` جو `test()` / `prepare()` / `send(records)` واپس کرے۔
2. اسے `src/lib/logExport/registry.ts` میں موجود `DESTINATIONS` صف میں شامل کریں۔
3. `tests/unit/` کے تحت ٹیسٹ لکھیں۔

بس یہی پوری تبدیلی ہے: مستقل ذخیرہ کاری، cron جاب، REST تہہ، خفیہ معلومات کی رمزکاری اور
ڈیش بورڈ فارم سب رجسٹری سے پڑھتے ہیں۔

نئی منزل کے لیے دو اصول:

- جزوی ناکامی پر `send()` **کو لازماً استثنا پھینکنا چاہیے**۔ کامیابی سے مکمل ہونے کا مطلب ہے کہ "منزل کے پاس یہ قطاریں موجود ہیں"،
  اور کرسر مستقل طور پر ان سے آگے بڑھ جاتا ہے۔
- ایسی منزل جو صارف کا فراہم کردہ URL قبول کرتی ہو، اسے درخواست بھیجنے سے پہلے
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) کے ذریعے اس کی توثیق کرنی چاہیے،
  بالکل ویسے ہی جیسے ویب ہُکس کرتے ہیں۔ BigQuery کو اس کی ضرورت نہیں: اس کے میزبان مستقل ہیں۔

## 7. اسے چلانا

- **ڈیش بورڈ**: انضمامات → لاگ ایکسپورٹ۔ ایک منزل شامل کریں، قطاریں لکھے بغیر اسناد کی جانچ کے لیے **ٹیسٹ** چلائیں،
  پھر اسے فعال کریں۔
- **زیرِ التوا کام**: ہر منزل کا کارڈ زیرِ التوا قطاریں اور کرسر دکھاتا ہے؛ `GET
/api/log-export/status` یہی اعداد و شمار اور جاب کے آخری 20 اجرا کی تفصیلات واپس کرتا ہے۔
- **ایک منزل کی ناکامی دوسری منزلوں کو ناکام نہیں کرتی** — اجرا کا خلاصہ ہر منزل کی
  حالت `last_status` / `last_error` میں درج کرتا ہے، اور جاب کے اجرا کی تاریخ مجموعی نتیجہ محفوظ رکھتی ہے۔
- **منزل کو حذف کرنے سے اس کا کرسر بھی حذف ہو جاتا ہے۔** اسے دوبارہ شامل کرنے پر آغاز سب سے پرانے محفوظ شدہ
  کال لاگ سے ہوتا ہے، جس سے وہ قطاریں دوبارہ بھیجی جاتی ہیں جو ممکن ہے منزل کے پاس پہلے ہی موجود ہوں۔ BigQuery میں ہر قطار کا
  `insertId` اس تکرار کو صرف BigQuery کی اپنی تکرار دور کرنے کی زمانی حد کے اندر ہی روکتا ہے، اس لیے
  منزل کو حذف کرنے کے بجائے غیر فعال کرنے کو ترجیح دیں۔
