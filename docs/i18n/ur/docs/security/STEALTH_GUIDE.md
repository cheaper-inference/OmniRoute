## قانونی اور اخلاقی نوٹس

اسٹیلتھ خصوصیات اس لیے موجود ہیں تاکہ OmniRoute صارف کی ملکیت والے سرکاری اکاؤنٹس (Claude Code CLI، Codex، Antigravity، Cursor، وغیرہ) اور OmniRoute کی متحد API کے درمیان مطابقتی تہہ کے طور پر کام کر سکے۔ یہ فراڈ کی شناخت سے بچنے، اسناد کا اشتراک کرنے، یا فراہم کنندہ کی سروس کی شرائط کی خلاف ورزی کے لیے **نہیں** ہیں۔ مینٹینرز آپریٹرز سے توقع کرتے ہیں کہ وہ اکاؤنٹس بناتے وقت قبول کردہ اپ اسٹریم ToS کی پابندی کریں گے۔

## TLS فنگر پرنٹنگ لیئر

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

مستقل `wreq-js` سیشنز ہر اکاؤنٹ اسکوپ اور حل شدہ پراکسی کے لیے ضرورت پڑنے پر بنائے جاتے ہیں۔
پورے پراسیس پر محیط `TlsClient` زیادہ سے زیادہ 128 سیشنز کے پول کا انتظام کرتا ہے، جو Cloudflare
کے پیچھے موجود اپ اسٹریمز کے لیے **macOS پر Chrome 124** کی نقل کرتے ہیں۔ مقامی رن ٹائم دستیاب نہ
ہونے پر `TlsClient.fetch()` بند حالت میں ناکام ہوتا ہے؛ کالر واضح طور پر اس ریپر سے باہر کوئی فال بیک
منتخب کر سکتا ہے۔

- سیشن پروفائل: `browser: "chrome_124", os: "macos"`
- پراکسی ریزولیوشن (ترجیح): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (چھوٹے حروف والی اقسام بھی)
- ٹائم آؤٹ: `TLS_CLIENT_TIMEOUT_MS` (`FETCH_TIMEOUT_MS` سے وراثت میں ملتا ہے، ڈیفالٹ 600000)
- `wreq-js` ریسپانس fetch کے ساتھ مطابقت رکھتا ہے (`headers`, `text()`, `json()`, `clone()`, `body`)۔
- پہلے بائٹ کا واچ ڈاگ (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): `TlsClient.fetch()`
  اپ اسٹریم ہیڈرز آتے ہی ریزولو ہو جاتا ہے، اس لیے صرف `TLS_CLIENT_TIMEOUT_MS` ایسی باڈی کو محدود
  نہیں کر سکتا جو کبھی پہلا بائٹ نہ دے۔ `guardTlsFirstByte()` باڈی کے پہلے `read()` اور
  `TLS_FIRST_BYTE_WATCHDOG_MS` (ڈیفالٹ `10000`، `0` اسے غیر فعال کرتا ہے) کے درمیان ریس کرواتا ہے؛
  ایک صحت مند باڈی متاثر نہیں ہوتی، جبکہ رکی ہوئی باڈی wreq ریڈر کو منسوخ کر دیتی ہے اور
  `proxyFetch` کی موجودہ TLS فال بیک منطق کو براہِ راست/پراکسی ڈسپیچر تک جانے دیتی ہے (ایسی درخواست
  جسے محفوظ طریقے سے دوبارہ نہیں چلایا جا سکتا، مثلاً باڈی والی POST، خاموشی سے دوبارہ آزمانے کے
  بجائے اب بھی خرابی پھینکتی ہے)۔

### ویب کوکی فراہم کنندہ ٹرانسپورٹ — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` ذیل میں موجود پانچ مخصوص ویب کوکی ٹرانسپورٹس کے لیے مشترکہ
اڈاپٹر ہے۔ ہر ہلکا پھلکا فراہم کنندہ ریپر ایک براؤزر/OS پروفائل منتخب کرتا ہے۔ اڈاپٹر
`open-sse/utils/tlsClient.ts` میں موجود واحد wreq رن ٹائم لوڈر اور ٹرانسپورٹ پول استعمال کرتا ہے،
جس کی کلید پروفائل + OS + حل شدہ پراکسی ہے، جبکہ ہر درخواست `cookieMode: "ephemeral"` استعمال کرتی
ہے۔ اس لیے اکاؤنٹس اور درخواستیں ٹرانسپورٹ سطح کے کنکشنز کا اشتراک کرتی ہیں، مگر کبھی بھی wreq سیشن
یا کوکی جار کا نہیں۔

| فراہم کنندہ | پروفائل       | نقل کردہ OS | اسٹریم EOF پالیسی                        |
| ----------- | ------------- | ----------- | ---------------------------------------- |
| Claude      | `chrome_146`  | Linux       | `[DONE]` شامل کریں                       |
| Perplexity  | `firefox_151` | macOS       | `event: end_of_stream` شامل کریں         |
| Grok        | `chrome_146`  | Linux       | `[DONE]` خارج کریں                       |
| Notion      | `chrome_146`  | Windows     | `[DONE]` شامل کریں                       |
| LMArena     | `chrome_146`  | Windows     | کوئی سینٹینل نہیں؛ مقامی EOF پر بند کریں |

- اسٹریمنگ مقامی ریسپانس `ReadableStream` کو براہِ راست استعمال کرتی ہے؛ کوئی عارضی فائل یا
  سائیڈ کار نہیں بنایا جاتا۔
- اسٹریم ظاہر کرنے سے پہلے ابتدائی 256 بائٹس تک کا معائنہ کیا جاتا ہے۔ SSE فراہم کنندگان غیر SSE
  خرابیوں کو بفر کرتے ہیں؛ Grok/LMArena، Cloudflare چیلنجز کو `403` اور HTML انٹرسٹیشلز کو `502`
  سے میپ کرتے ہیں۔
- مقامی درخواست کا ٹائم آؤٹ بدستور ایک قطعی JS ہارڈ ڈیڈ لائن میں لپٹا رہتا ہے۔ ہینگ ہونے کی صورت
  میں صرف متاثرہ پروفائل/OS/پراکسی ٹرانسپورٹ کو غیر مؤثر کر کے بند کیا جاتا ہے، پھر اگلی درخواست
  اسے دوبارہ بناتی ہے۔
- پراکسی ریزولیوشن کی ترجیح یہ ہے: ہر کال کا `proxyUrl` → درخواست کے دائرۂ کار والا
  اکاؤنٹ/ڈیش بورڈ سیاق → `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (چھوٹے حروف والی اقسام سمیت)۔
  ریزولیوشن کی خرابیاں براہِ راست کنکشن لیک کرنے کے بجائے بند حالت میں ناکام ہوتی ہیں۔ LMArena
  دانستہ طور پر `arena.ai` کے مقابل ریزولو کرتا ہے۔
- `byteResponse`، UTF-8 خرابی کے بغیر مواد کی قسم والا `data:` URL واپس کرتا ہے۔
- خرابیاں `TlsClientUnavailableError` (پیکیج/ایڈ آن دستیاب نہیں)، `TlsClientHangError`
  (ڈیڈ لائن تجاوز کر گئی)، اور `WreqTransportCapacityError` (مشترکہ سیشن گنجائش کا خرابی کوڈ)
  ہیں، جب تمام 128 محدود پروفائل/OS/پراکسی سلاٹس فعال ہوں یا بند ہو رہے ہوں۔

اوپر موجود عمومی `TlsClient` سیشن مستقل، براؤزر کی مدد سے چلنے والی کوکی حالت کے لیے مخصوص رہتا
ہے۔ دونوں راستے ایک ہی کیش شدہ wreq ماڈیول لوڈر اور پراسیس لائف سائیکل ہک دوبارہ استعمال کرتے ہیں؛
ان کے پول الگ رہتے ہیں کیونکہ ان کی کوکی لائف ٹائمز دانستہ طور پر مختلف ہیں۔

یہ پروفائلز پن کیے گئے پیکیج کے ذریعے معاونت یافتہ ہیں، لیکن حقیقی WAF قبولیت مقامی کنٹریکٹ ٹیسٹس
سے آزادانہ طور پر تبدیل ہو سکتی ہے۔ کسی اپ اسٹریم براؤزر کے ساتھ برابری کا دعویٰ کرنے سے پہلے
فنگر پرنٹ کی تبدیلیوں کی واضح طور پر مجاز لائیو اکاؤنٹ کے مقابل توثیق کریں۔

## Claude Code اسٹیلتھ بنڈل

جب `cliCompatMode` فعال ہو، تو OmniRoute باہر جانے والی Claude درخواستوں کو اس طرح ڈھالتا ہے کہ وہ `claude-cli` ٹریفک سے ناقابلِ امتیاز ہوں۔ تین ماڈیول باہمی تعاون کرتے ہیں:

### `claudeCodeFingerprint.ts`

بلنگ ہیڈر میں شامل 3-حرفی `cc_version` فنگرپرنٹ کا حساب لگاتا ہے:

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (ہارڈ کوڈ شدہ؛ آفیشل کلائنٹ سے مطابقت رکھتا ہے)
- اِن پٹس: پہلے صارف کے پیغام کے متن میں انڈیکس 4، 7، 20 پر موجود حروف + ورژن اسٹرنگ
- آؤٹ پٹ: 3-حرفی ہیکس سابقہ

### `claudeCodeCCH.ts` (کلائنٹ مواد ہیش)

سرور سائیڈ سالمیت کی جانچ، جسے آفیشل Claude Code CLI، Bun/Zig کے ذریعے شمار کرتا ہے۔ OmniRoute اسے `xxhash-wasm` کے ساتھ دوبارہ نافذ کرتا ہے:

1. باڈی کو `cch=00000;` پلیس ہولڈر کے ساتھ سیریلائز کریں
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. صفر سے پیڈ کردہ 5-حرفی چھوٹے حروف والا ہیکس
4. `cch=00000;` کو شمار کردہ ٹوکن سے تبدیل کریں

مستقل قدریں:

- سیڈ: `0x6e52736ac806831e`
- پیٹرن: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

"حساس" کلائنٹ ناموں کے پہلے حرف کے بعد ایک یونیکوڈ **صفر چوڑائی جوائنر** (`U+200D`) داخل کرتا ہے، تاکہ اپ اسٹریم فلٹرز انہیں grep نہ کر سکیں۔ ڈیفالٹ الفاظ کی فہرست:

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

اس پر لاگو ہوتا ہے: `system` بلاکس، تمام `messages[].content`، اور `tools[].description` / `tools[].function.description`۔ آپریٹر اسے `setSensitiveWords()` کے ذریعے تبدیل کر سکتا ہے۔

### `claudeCodeCompatible.ts` — `anthropic-compatible-cc-*` فراہم کنندگان

فریقِ ثالث کے ان Anthropic ریلے کے لیے جو صرف "حقیقی Claude Code" ٹریفک قبول کرتے ہیں:

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.280 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- ڈیفالٹ طور پر `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"`
- فی کنکشن "Enable redact-thinking beta" ٹوگل، جب کسی CC Compatible اپ اسٹریم کو خاص طور پر مخفی کردہ تھنکنگ اسٹریمز درکار ہوں، تو `redact-thinking-2026-02-12` شامل کرتا ہے
- فی کنکشن "Enable summarized thinking display" ٹوگل `providerSpecificData.requestDefaults.summarizeThinking` محفوظ کرتا ہے اور ان CC Compatible تھنکنگ درخواستوں میں `display: "summarized"` شامل کرتا ہے جن میں پہلے سے ڈسپلے موڈ مقرر نہیں کیا گیا
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (Opus/Sonnet 4.x خاندان)
- ڈیفالٹ پاتھ: `/v1/messages?beta=true`

اسی بنڈل میں موجود متعلقہ ماڈیولز:

- `claudeCodeConstraints.ts` — درجۂ حرارت + کیش کنٹرول کے قواعد
- `claudeCodeToolRemapper.ts` — ٹول ناموں کی دوبارہ میپنگ
- `claudeCodeExtraRemap.ts` — اضافی پے لوڈ کی معمول کاری

## Antigravity چپکے

Antigravity کالر ٹیکسٹ بائٹ بائٹ کے لیے محفوظ رکھنے کی درخواست کرتا ہے۔ OmniRoute IDE کلائنٹ کی نقل کرنے کے لیے پرامپٹس یا rename/inject ٹولز میں صفر چوڑائی والے حروف داخل نہیں کرتا ہے۔

### `antigravityHeaderScrub.ts`

سٹرپس سٹینلیس SDK مارکر (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`) کو آگے بھیجنے سے پہلے۔

### ⚠️ رسک: `ANTIGRAVITY_CREDITS=always` (اکاؤنٹ پر پابندی گرم جگہ)

`ANTIGRAVITY_CREDITS=always` ( `open-sse/executors/antigravity.ts` کے ذریعے استعمال کیا جاتا ہے) راستے** ہر** Google کے فری ٹائر کوٹہ گیٹ چیزوں کو دینے کی بجائے Antigravity AI کریڈٹ اووریجز (ادائیگی شدہ Google کریڈٹ) کے ذریعے درخواست کریں۔ یہ ایک خصوصیت کے طور پر دستاویزی ہے، لیکن یہ ہے** واحد سب سے عام ToS-خلاف ورزی کی رپورٹ جو ہم دیکھتے ہیں۔** — ایک سے زیادہ Google الٹرا اکاؤنٹس `=always` کے ساتھ چند گھنٹوں تک چلانے کے بعد `403 / "service disabled for ToS violation" / insufficient_quota` کے ساتھ پابندی لگا دی گئی ہے۔

اپ اسٹریم نفاذ جاری ہے۔**Google کی طرف** ، کچھ بھی نہیں OmniRoute روک سکتا ہے۔ env var نام اور موجودہ دستاویزات اسے پلٹنے کے لیے ایک محفوظ نوب کی طرح آواز دیتے ہیں۔ یہ نہیں ہے.

**کیوں یہ بدسلوکی کا پتہ لگانے کو صرف مفت درجے کے استعمال سے زیادہ جارحانہ انداز میں کھینچتا ہے:**

- ایک واحد Google اکاؤنٹ پر مستقل خودکار خرچ فری ٹائر ہٹس کوٹہ اور اسٹاپس سے مختلف ہے۔
- کریڈٹ اووریجز کی شرح کی کوئی حد نہیں ہے، اس لیے غلط کنفیگر کردہ کلائنٹ منٹوں میں کئی سو USD کے ذریعے جل سکتا ہے اور API-key کی دوبارہ فروخت یا بوٹ ٹریفک کی طرح نظر آتا ہے۔
- متعدد OmniRoute صارفین ایک ہی بیرونی IP سے متوازی طور پر زیادہ عمر کے کریڈٹ کو مارتے ہیں جو سگنل کو مرکب کرتے ہیں۔

**تجویز کردہ کرنسی:**

1. پہلے سے طے شدہ `ANTIGRAVITY_CREDITS=off` رکھیں جب تک کہ آپریٹر واضح طور پر ادا شدہ کریڈٹ اور اکاؤنٹ کے نفاذ کے خطرے کو قبول نہ کرے۔ `retry` پہلے عام درخواست بھیجتا ہے اور ایک اہل کوٹہ 429 کے بعد زیادہ سے زیادہ ایک بار کریڈٹ لگاتا ہے۔ `always` پہلی درخواست پر کریڈٹ لگاتا ہے۔
2. **آٹو کومبو کے ذریعے فراہم کنندگان میں بوجھ پھیلائیں۔** (`model: "auto"` یا `kr/glm/etc` -combo) ایک Antigravity اکاؤنٹ کو سیر کرنے کے بجائے۔
3. **فی کنکشن RPM حدیں مقرر کریں۔** Antigravity فراہم کنندہ کے ترمیمی صفحہ میں (ڈیش بورڈ → فراہم کنندہ → Antigravity → کنکشن → شرح کی حد)۔ 30-60 RPM پائیدار استعمال کے لیے ایک قابل دفاع بالائی حد ہے۔
4. **مستحکم، آپریٹر کے زیر کنٹرول اپ اسٹریم نیٹ ورکنگ کا استعمال کریں۔** اور غیر متعلقہ صارفین یا کام کے بوجھ میں ایک اکاؤنٹ کا اشتراک کرنے سے گریز کریں۔
5. **اگر پابندی لگا دی جائے۔** : `support.google.com` → کے ذریعے اپیل کریں " Workspace/Account رسائی بحال کریں" کے عین مطابق `quota_exceeded` / `service disabled` جوابی باڈی Google بھیجا گیا ہے۔ بحالی کی ضمانت نہیں ہے۔

ماحول کا حوالہ ہر کریڈٹ موڈ کے اکاؤنٹ اور خرچ کے مضمرات کو دستاویز کرتا ہے۔

#### نہ صرف `=always`: Antigravity OAuth عام طور پر روٹنگ

معطلی صرف کریڈٹ کی حد تک محدود نہیں ہے۔ نومبر 2026 (#19223, #19266) کی رپورٹیں `antigravity` اور `agy` (Antigravity CLI) فراہم کنندگان کے ذریعے روٹنگ کے دوران معطل کئی Google اکاؤنٹس کی وضاحت کرتی ہیں، اس کے ساتھ:

```
403: This service has been disabled in this account for violation of Terms of Service.
Please submit an appeal to continue using this product.
```

دونوں فراہم کنندگان Antigravity پروڈکٹ OAuth سیشن کے ساتھ تصدیق کرتے ہیں، جس کی صورت میں ڈیش بورڈ کا رسک نوٹس ("یہ فراہم کنندہ آپ کی آفیشل پروڈکٹ session/OAuth استعمال کرتا ہے، جو کہ proxy/router استعمال کے لیے مجاز نہیں ہے") کنکشن شامل کرنے سے پہلے خبردار کرتا ہے۔ مندرجہ بالا سفارشات میں سے کوئی بھی اس استعمال کو مجاز نہیں بناتا ہے۔ وہ صرف ایک اکاؤنٹ کی ٹریفک کو کم کرتے ہیں۔

**Gemini ماڈلز کے لیے مجاز API انٹرفیس۔** Google اپنے APIs کے ذریعے Gemini تک پروگرامی رسائی کی پیشکش کرتا ہے، جسے OmniRoute عام API کلیدی فراہم کنندگان کے طور پر سپورٹ کرتا ہے:

| فراہم کنندہ کی شناخت | ڈیش بورڈ کا نام            | اسناد                                                                   |
| -------------------- | -------------------------- | ----------------------------------------------------------------------- |
| `gemini`             | Gemini (Google AI اسٹوڈیو) | Gemini API کلید Google AI اسٹوڈیو سے (مفت درجے میں دستیاب)              |
| `vertex`             | Vertex AI                  | سروس اکاؤنٹ JSON, OAuth رسائی ٹوکن یا ورٹیکس ایکسپریس API کلید (Gemini) |

یہ فراہم کنندگان API تک رسائی کے لیے اسناد Google ایشوز کا استعمال کرتے ہیں، Antigravity پروڈکٹ سیشن کے برعکس۔ وہ ہر استعمال کو موافق نہیں بناتے ہیں اور نہ ہی نفاذ کے خطرے کو ختم کرتے ہیں: ہر ایک کی اپنی شرائط کے تحت حکومت ہوتی ہے، جسے آپریٹر کو ان کی تعیناتی کی جانچ کرنا ہوتی ہے۔ مثال کے طور پر، [Gemini API سروس کی اضافی شرائط](https://ai.google.dev/gemini-api/terms) صرف اس وقت ادا شدہ خدمات کی اجازت دیتی ہیں جب API کلائنٹس کو یورپی اکنامک ایریا، سوئٹزرلینڈ یا یونائیٹڈ کنگڈم میں صارفین کے لیے دستیاب کرایا جاتا ہے، اور بلا معاوضہ سروسز کو بھیجے گئے مواد کو Google کی مصنوعات کو بہتر بنانے کے لیے استعمال کیا جا سکتا ہے۔ Vertex AI اس کے بجائے Google کلاؤڈ کی شرائط کے تحت آتا ہے ( [سروس کی مخصوص شرائط](https://cloud.google.com/terms/service-terms) )۔ قیمتوں کا تعین اور کوٹہ Antigravity سبسکرپشن کے بجائے ان API شرائط کی پیروی کرتے ہیں۔

آپریٹرز جو اوپر بیان کردہ Antigravity معطلی سے بچنا چاہتے ہیں انہیں چاہیے کہ وہ Gemini ٹریفک کو `antigravity` / `agy` کے بجائے ان فراہم کنندگان میں سے کسی ایک کے ذریعے روٹ کریں، یہ چیک کرنے کے بعد کہ ان کا استعمال فراہم کنندہ کی شرائط پر پورا اترتا ہے۔

ٹچ پوائنٹس:

- `open-sse/executors/antigravity.ts` — `process.env.ANTIGRAVITY_CREDITS` پڑھتا ہے۔
- `src/lib/oauth/providers/antigravity.ts` — سندی پلمبنگ
- اصل واقعہ رپورٹ: بحث [#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## CLI فنگرپرنٹ رجسٹری — `open-sse/config/cliFingerprints.ts`

ہر فراہم کنندہ کے لیے ایک جدول جو آفیشل CLIs کے mitmproxy ٹریسز سے حاصل کردہ ہیڈر کی **عین** ترتیب اور JSON باڈی فیلڈز کی ترتیب کو مقرر کرتا ہے۔ فی الحال رجسٹرڈ: `codex`، `claude`، نیز `antigravity` اور `github` کے لیے `providerHeaderProfiles.ts` میں رن ٹائم سے اخذ کردہ پروفائلز۔

```ts
interface CliFingerprint {
  headerOrder: string[]; // حروف کی ہیئت کے لحاظ سے حساس
  bodyFieldOrder: string[]; // اعلیٰ سطح کی JSON کلیدیں
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

ہر فراہم کنندہ کے لیے env کے ذریعے فعال یا غیر فعال کریں (نیچے دیکھیں)۔ غیر فعال ہونے پر ہیڈرز/باڈی کلیدیں اسی ترتیب میں ظاہر ہوتی ہیں جس ترتیب میں Node/JSON نے انہیں فراہم کیا — جس سے فنگرپرنٹ بنانا آسان ہو جاتا ہے۔

## MITM پراکسی (Antigravity، Linux/macOS/Windows)

ان CLIs کے لیے جن کی بائنریز کو `OPENAI_BASE_URL` کے ذریعے ری ڈائریکٹ نہیں کیا جا سکتا، OmniRoute ایک مقامی TLS ختم کرنے والی پراکسی چلاتا ہے۔ اینڈ پوائنٹس `src/app/api/cli-tools/antigravity-mitm/` کے تحت موجود ہیں۔

| طریقہ  | اینڈ پوائنٹ                             | مقصد                                                 |
| ------ | --------------------------------------- | ---------------------------------------------------- |
| GET    | `/api/cli-tools/antigravity-mitm`       | حالت — چل رہا ہے، pid، dnsConfigured، certExists     |
| POST   | `/api/cli-tools/antigravity-mitm`       | MITM شروع کریں (`apiKey` + `sudoPassword` درکار ہیں) |
| DELETE | `/api/cli-tools/antigravity-mitm`       | MITM روکیں                                           |
| GET    | `/api/cli-tools/antigravity-mitm/alias` | ماڈل عرفیات کی فہرست                                 |
| PUT    | `/api/cli-tools/antigravity-mitm/alias` | کسی ٹول کے لیے ماڈل عرفیات محفوظ کریں                |

ہدف بنایا گیا میزبان: **`daily-cloudcode-pa.googleapis.com`** (Antigravity کا اپ اسٹریم)۔

### آغاز کی ترتیب (`src/mitm/manager.ts::startMitm`)

1. `selfsigned` کے ذریعے خود دستخط شدہ سرٹیفکیٹ بنائیں (RSA-2048، SHA-256، 1y) — `cert/generate.ts`
2. سرٹیفکیٹ کو سسٹم ٹرسٹ اسٹور میں انسٹال کریں — `cert/install.ts`
3. ہوسٹس اندراج `127.0.0.1 daily-cloudcode-pa.googleapis.com` شامل کریں — `dns/dnsConfig.ts`
4. `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (ڈیفالٹ `443`) کے ساتھ `src/mitm/server.cjs` کو اسپان کریں
5. PID کو `<DATA_DIR>/mitm/.mitm.pid` میں محفوظ رکھیں

### Linux کی متحرک ٹرسٹ اسٹور شناخت — `cert/install.ts`

`getLinuxCertConfig()` ترجیحی فہرست کا جائزہ لیتا ہے اور پہلی موجود ڈائریکٹری منتخب کرتا ہے:

| ڈسٹرو خاندان             | ڈائریکٹری                                   | اپ ڈیٹ کمانڈ             |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

سرٹیفکیٹ فائل کا نام: `omniroute-mitm.crt`۔ فنگرپرنٹ کی مماثلت `getCertFingerprint()` کے ذریعے (DER کا SHA-1)۔

مزید برآں، جب `certutil` دستیاب ہو تو `updateNssDatabases()` ہر صارف کے NSS DBs میں انسٹال کرتا ہے: `~/.pki/nssdb`، `~/snap/chromium/.../nssdb`، تمام Firefox پروفائلز (بشمول snap)، عرفی نام **`OmniRoute MITM Root CA`** کے تحت۔

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** اعلیٰ مراعات یافتہ PowerShell → `certutil -addstore Root`

### توثیق

تمام MITM اینڈ پوائنٹس کے لیے انتظامی توثیق (`requireCliToolsAuth`) درکار ہے۔ sudo پاس ورڈ کو ماڈیول اسکوپ میں کیش کیا جاتا ہے (کبھی بھی `globalThis` میں نہیں) اور `stopMitm()` پر صاف کر دیا جاتا ہے۔

## فراہم کنندہ کی تبدیلی پر فنگرپرنٹس اپ ڈیٹ کرنا

1. `mitmproxy` کے ذریعے آفیشل CLI ٹریفک کیپچر کریں (TLS انٹرسیپشن + ڈمپ)
2. JA3/JA4 اور ہیڈرز کی عین ترتیب اخذ کریں
3. متعلقہ `CLI_FINGERPRINTS[...]` اندراج اپ ڈیٹ کریں
4. `.env.example` میں مماثل `*_USER_AGENT` ڈیفالٹ اپ ڈیٹ کریں
5. اگر TLS ہینڈ شیک بھی تبدیل ہوا ہے، تو متعلقہ فراہم کنندہ ریپر یا wreq-js کا `browser:` آپشن اپ ڈیٹ کریں
6. فراہم کنندہ سے مخصوص TLS ٹیسٹس چلائیں اور لائیو فراہم کنندہ کے خلاف دستی کینری ٹیسٹ کریں
7. پیچ ریلیز میں جاری کریں؛ `CHANGELOG.md` میں دستاویز کریں
