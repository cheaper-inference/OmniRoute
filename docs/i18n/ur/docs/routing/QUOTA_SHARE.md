## جائزہ

کوٹہ شیئرنگ انجن کسی فراہم کنندہ کے وقت پر مبنی کوٹے (مثلاً Codex کی
5 گھنٹے کی ونڈو، Kimi کی 1500 درخواستیں فی گھنٹہ) کو ایک ہی کنکشن استعمال کرنے والی
متعدد API کلیدوں میں منصفانہ طور پر تقسیم کرتا ہے۔

**حل کیا جانے والا مسئلہ:** OmniRoute بہت سی API کلیدوں کو اسی upstream
فراہم کنندہ اکاؤنٹ کے ذریعے پراکسی کرتا ہے۔ شیئرنگ منطق کے بغیر، کلید A سے آنے والا اچانک بوجھ
فراہم کنندہ کا فی گھنٹہ کوٹہ ختم کر سکتا ہے، جس کے نتیجے میں کلیدیں B اور C ونڈو ری سیٹ ہونے تک مسدود رہتی ہیں۔
انجن درج ذیل طریقوں سے اسے روکتا ہے:

1. ہر کلید کے لیے ہر جہت (٪، درخواستیں، ٹوکنز، $) میں رولنگ کھپت کا سراغ لگانا۔
2. کام کو برقرار رکھنے والا منصفانہ تقسیم کا الگورتھم لاگو کرنا: جب تک عالمی پول
   مکمل طور پر استعمال نہ ہو، ایک کلید غیر استعمال شدہ حصوں سے مستعار لے سکتی ہے۔
3. درخواست کے upstream executor تک پہنچنے سے پہلے hot path (`chatCore.ts`) میں
   نتیجے کا نفاذ کرنا۔

## الگورتھم: فیئر شیئر ورک کنزرونگ

`src/lib/quota/fairShare.ts` میں نافذ کیا گیا۔

### موڈز

| حالت                                       | موڈ      | رویہ                                              |
| ------------------------------------------ | -------- | ------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **فیاض** | کلید عالمی حد مائنس کنسمڈ کل تک ادھار لے سکتی ہے۔ |
| `globalUsedPercent >= saturationThreshold` | **سخت**  | انفرادی منصفانہ شیئر کو سختی سے نافذ کریں۔        |

پہلے سے طے شدہ `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`)۔

یہ دو موڈز ڈیفالٹ ادھار موڈ میں ایک پول کی وضاحت کرتے ہیں، `saturation`۔ `consent` موڈ میں ایک پول ہمیشہ سخت اصولوں کا اطلاق کرتا ہے، جو بھی سنترپتی ہو۔ [رضامندی سے قرضہ (فی پول آپٹ ان)](#consented-lending-per-pool-opt-in) دیکھیں۔

### فی طول و عرض کا فیصلہ

پول میں ہر ایک فعال جہت کے لیے، انجن حساب کرتا ہے:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent` طول و عرض کے لیے، `consumed` اس کی بجائے انتساب کتاب سے آتا ہے (دیکھیں [فیصد جہت: فی کلیدی انتساب](#percent-dimensions-per-key-attribution) )۔

پھر:

- **`policy = hard`** : اگر `consumed > fairShareAllowed` اور موڈ سخت → ہے۔** بلاک** .
- **`policy = soft`** : اگر `consumed > fairShareAllowed` اور موڈ سخت → ہے۔** سزا دینا** (کومبو میں ترجیح دیں؛ کبھی ہارڈ بلاک)۔
- **`policy = burst`** : اس وقت اجازت دیں جب عالمی ہیڈ روم منصفانہ حصہ سے قطع نظر موجود ہو۔

### ٹوپی مطلق

مختص پر `capValue` + `capUnit` موڈ یا پالیسی سے آزاد ایک سخت چھت ہے۔ کوئی بھی جہت جہاں ہمیشہ `consumed >= capValue`** بلاکس** درخواست `percent` کیپ کے لیے، `consumed` صرف کلید سے منسوب حصہ ہے۔

### کثیر جہتی چیک

ایک درخواست مسدود ہے اگر** کوئی بھی** پول میں طول و عرض اسے روک دے گا. طول و عرض آزاد ہیں ایک 5h% — ہفتہ وار% طول و عرض کو متاثر نہیں کرتی ہے۔

### ادھار لینا

فراخ موڈ میں، ایک کلید جس کی مختص رقم کم استعمال کی گئی ہے وہ دیگر کلیدوں کے غیر مختص حصص سے اضافی استعمال کر سکتی ہے۔ فارمولا ہے:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

جہاں `consumedByOtherKeys = consumedTotal - consumedByThisKey` ٹیٹو گلوبل (اس جہت کے لیے پول `limit` ) ہمیشہ سخت چھت ہوتی ہے۔

### منظور شدہ قرضہ (فی پول آپٹ ان)

ہر پول میں قرض لینے کا موڈ ہوتا ہے۔ `saturation` پہلے سے طے شدہ ہے اور قواعد کو اوپر رکھتا ہے۔ `consent` موڈ میں ایک `hard` کلید اپنا حصہ صرف اس صلاحیت کے اندر منتقل کرتی ہے جسے دوسری کلیدیں قرض دینے پر راضی ہوتی ہیں۔ منتظم ہر پول کا موڈ سیٹ کرتا ہے۔ ہر کلیدی ہولڈر [قرض دینے کی رضامندی](#lending-consent) کے ذریعے اپنی رضامندی طے کرتا ہے۔

رضامندی 0 سے 100 تک کا فیصد ہے اور ایک اختیاری آخری تاریخ epoch ملی سیکنڈ میں ہے۔ کلید اپنے بیکار حصہ کا وہ فیصد قرض دیتی ہے جب کہ آخری تاریخ مستقبل میں ہے۔

ایک جہت کے لیے، `L` مؤثر حد ہے: پلان کی حد پول میں اکاؤنٹس کو گنا کرتی ہے۔ گیٹ حساب کرتا ہے، درخواست کرنے والی کلید کے لیے:

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` کلید کا وزن ہے، یا `100 / n` ہر کلید کے لیے ہے جب کوئی وزن 0 سے زیادہ نہ ہو `lend_k` درخواست کرنے والی کلید کی اپنی رضامندی کبھی شمار نہیں ہوتی۔ ایک `hard` کلید سے انکار کر دیا جاتا ہے جب اس کی کھپت اس کے حصہ تک پہنچ جاتی ہے `borrowAvailable`۔

قابلیت جس کا کوئی مختص دعویٰ نہیں کرتا (100 مائنس وزن کا مجموعہ) قابل قرض نہیں ہے۔ کوئی چابی اسے قرض دینے پر راضی نہیں ہوئی۔

**مثال۔** `L` 1000 ہے۔

| چابی | وزن | شیئر کریں۔ | استعمال | قرض دیتا ہے۔ |
| ---- | --- | ---------- | ------- | ------------ |
| اے   | 50  | 500        | 530     | 0%           |
| بی   | 30  | 300        | 100     | 50%          |
| سی   | 0   | 0          | 60      | 0%           |

- B اپنے بیکار 200 کا 50% قرض دیتا ہے، جو کہ 100 ہے۔ C پہلے ہی اپنے حصے سے 60 لے چکا ہے۔ A 40 ادھار لے سکتا ہے۔
- A کو 530 پر پیش کیا جاتا ہے اور جب اس کی کھپت 540 تک پہنچ جاتی ہے تو انکار کر دیا جاتا ہے۔
- اس سے پہلے کہ C کچھ بھی استعمال کرے، A کے ساتھ اس کے حصے پر یا اس کے نیچے، C 100 ادھار لے سکتا ہے۔
- اس سے پہلے کہ C کچھ بھی استعمال کرے، A کے ساتھ 530 پر، C 70 ادھار لے سکتا ہے۔

**صفر وزن۔** وزن 0 والی چابی میں 0 کا حصہ ہوتا ہے۔ اسے صرف اس وقت پیش کیا جاتا ہے جب اس کی کھپت دوسرے قرضے سے کم ہو۔ جب کوئی قرض نہیں دیتا تو اس کی پہلی درخواست سے انکار کر دیا جاتا ہے۔

**ڈیڈ لائنز** کسی بھی پس منظر کے کام کی رضامندی ختم نہیں ہوتی۔ ہر درخواست آخری تاریخ کا اپنے وقت سے موازنہ کرتی ہے، اور اس وقت کے برابر ایک آخری تاریخ گزر چکی ہے۔ ایک ذخیرہ شدہ آخری تاریخ جو ایک محدود تعداد نہیں ہے، یا `Date` سب سے بڑی تاریخ سے گزر چکی ہے، اسے گزرے ہوئے شمار کیا جاتا ہے۔

**`soft` اور `burst`** قرض دینا انہیں محدود نہیں کرتا۔ ایک `soft` کلید کو اس کے حصہ سے گزرنے کے بعد محروم کر دیا جاتا ہے۔ ایک `burst` کلید گزرتی ہے جب پول میں کمرہ ہوتا ہے۔ پول کی کل حد تک پہنچنے کے بعد پول کی چھت اب بھی ہر کلید سے انکار کر دیتی ہے۔

**درخواست کے راستے پر لاگت۔** `saturation` پول پہلے سے زیادہ کچھ نہیں پڑھتا ہے۔ ایک `consent` پول میں، ایک قابل شمار جہت صرف ایک `hard` کلید کے لیے اس کے حصہ پر یا اس سے اوپر دوسری کلیدوں کو پڑھتی ہے جبکہ دوسری کلید قرض دیتی ہے۔ اس کے بعد یہ متوازی طور پر ایک دوسری کلید کو پڑھتا ہے۔ ایک ناکام پڑھنے کا شمار اس کلید کے لیے 0 کی کھپت کے طور پر ہوتا ہے۔ ایک `percent` طول و عرض کوئی پڑھا نہیں ہے، کیونکہ انتساب کتاب میں ہر کلید ہوتی ہے۔

**ایک تالاب میں ترمیم کرنا۔** ایک ترمیم ان کلیدوں کی رضامندی کو برقرار رکھتی ہے جو رہتی ہیں۔ اس میں ایلوکیشن ایڈیٹس، گروپ بھر میں تبدیلی اور `ensure` کالز شامل ہیں۔ ہٹائی گئی کلید اپنی رضامندی کھو دیتی ہے، اور دوبارہ شامل کی گئی کلید 0 سے شروع ہوتی ہے۔ منتظم کے راستے ہر کلید کی رضامندی واپس کرتے ہیں اور اسے کبھی نہیں لکھتے ہیں۔ پول کو واپس `saturation` میں تبدیل کرنے سے ہر ذخیرہ شدہ رضامندی برقرار رہتی ہے، جس کا اس موڈ میں کوئی اثر نہیں ہوتا ہے۔ پول کو `consent` میں تبدیل کرنے سے ذخیرہ شدہ رضامندی دوبارہ فعال ہو جاتی ہے جن کی آخری تاریخ گزری نہیں ہے۔ کلیدی ہولڈر کسی بھی موڈ میں ذخیرہ شدہ رضامندی کو صاف کر سکتا ہے۔

**اپ گریڈ کرنا۔** اگر کالم `lending_percent` اور `lending_until` پہلے سے موجود ہیں، تو منتقلی صرف `borrow_mode` جوڑتی ہے، اور ذخیرہ شدہ فیصد وہی رہتے ہیں جیسے وہ ہیں۔ ہر پول `saturation` موڈ میں شروع ہوتا ہے۔ پول وزرڈ میں فی پول `consent` آن کریں۔ ذخیرہ شدہ اقدار سے کسی چیز کا اندازہ نہیں لگایا جاتا ہے۔

**حدود۔**

- ایک قرض دہندہ پول کو اس کی چھت پر تلاش کر سکتا ہے اس سے پہلے کہ وہ اپنا حصہ استعمال کرے۔ صلاحیت جو دوسروں نے ادھار لی ہے اس کا شمار پول کے کل میں ہوتا ہے۔
- چیک درخواست سے پہلے چلتا ہے اور کچھ بھی محفوظ نہیں رکھتا ہے۔ سمورتی درخواستیں کسی بھی ریکارڈ ہونے سے پہلے کھپت کو پڑھتی ہیں، لہذا قرض کی گنجائش ایک سے زیادہ بار خرچ کی جا سکتی ہے، پرواز میں درخواستوں کے پابند ہیں۔ `saturation` موڈ کے شیئر چیک میں ایک ہی پراپرٹی ہے۔

## سلائیڈنگ ونڈو کاؤنٹر

`src/lib/quota/sqliteQuotaStore.ts` اور `redisQuotaStore.ts` میں نافذ کیا گیا ہے۔

ہر `(apiKeyId, dimensionKey)` کے لیے دو بکٹ:

- `curr`: موجودہ بکٹ (`floor(nowMs / windowMs)`)
- `prev`: پچھلی بکٹ (`curr - 1`)

مؤثر رولنگ قدر:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**درستگی**: تقریباً 99٪ درست۔ بکٹوں کی سرحد پر غلطی زیادہ سے زیادہ ونڈو کے حجم کا 1٪
ہوتی ہے (یہ 2-بکٹ تخمینے میں فطری ہے)۔

### ہم وقتی عمل

SQLite ڈرائیور: ہر `(apiKeyId | dimensionKey)` کلید کے لیے in-memory mutex،
read-modify-write تصادم کو روکتا ہے۔ پیٹرن `src/sse/services/auth.ts` کے anti-thundering-herd کی عکاسی کرتا ہے۔

Redis ڈرائیور: atomic increment کے لیے Lua EVAL اسکرپٹ — ایک واحد Redis کمانڈ کے طور پر چلتا ہے۔

## ڈرائیورز

### SQLite (ڈیفالٹ، 0-install)

- ٹیبل: `quota_consumption` (مائیگریشن `073_quota_pools.sql` / `074_quota_consumption.sql` دیکھیں)۔
- سنگل-انسٹینس ڈیپلائمنٹس کے لیے بہترین۔
- تمام مستقل ڈیٹا موجودہ OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) میں محفوظ ہوتا ہے۔

### Redis (اختیاری، ملٹی-انسٹینس)

- `ioredis` npm پیکیج درکار ہے۔
- کاؤنٹرز Redis میں محفوظ ہوتے ہیں؛ میٹا ڈیٹا (پولز/مختصات) بدستور SQLite میں رہتا ہے۔
- ملٹی-ریپلیکا ڈیپلائمنٹس کے لیے بہترین، جہاں کاؤنٹرز کا مشترک ہونا ضروری ہو۔

### ڈرائیورز تبدیل کرنا

سیٹنگز UI (`/dashboard/settings` → Quota Store) کے ذریعے، یا env vars کے ذریعے:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB سیٹنگ کو env پر ترجیح حاصل ہے۔ اگر `driver=redis` ہو لیکن URL موجود نہ ہو یا
`ioredis` انسٹال نہ ہو، تو فیکٹری SQLite پر واپس آ جاتی ہے اور ایک انتباہ لاگ کرتی ہے۔

ڈرائیور کے انتخاب کی ترتیب:

1. DB سیٹنگ `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. ڈیفالٹ: `sqlite`

```ts
QuotaDimension {
```

**مثال: Codex منصوبہ** (5h% + ہفتہ وار%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

ایک درخواست کی اجازت کے لیے تمام جہتوں کو پورا کرنا ضروری ہے۔

### فیصد ابعاد: فی کلیدی انتساب

ایک فیصد منصوبہ فی اکاؤنٹ اور پلان ونڈو کے استعمال کے ایک اعداد و شمار کی اطلاع دیتا ہے۔ فراہم کنندہ کوئی کاؤنٹر فی API کلید نہیں دیتا ہے۔

اس اعداد و شمار کو کلیدوں کے درمیان تقسیم کرنے کے لیے، ہر پول ایک انتساب کتاب فی اکاؤنٹ اور پلان ونڈو رکھتا ہے۔ `src/lib/quota/percentLedger.ts` کتاب کے اصولوں کو رکھتا ہے۔ `src/lib/quota/percentAttribution.ts` کتاب کو ان نمبروں میں بدل دیتا ہے جو نفاذ استعمال کرتا ہے۔ نتیجہ ہر کلیدی راستوں کے ٹوکن سے بنایا گیا تخمینہ ہے۔

#### ایسی پڑھائی جو کتاب کو حرکت دیتی ہے۔

درخواست کردہ پلان ونڈو کے لیے کتاب صرف فراہم کنندہ کے اپنے اعداد و شمار پر منتقل ہوتی ہے۔ یہ کنکشن ایک رپورٹ کرتے ہیں:

| فراہم کرنے والا                  | ونڈوز پلان کریں۔ |
| -------------------------------- | ---------------- |
| Claude، ایک OAuth کنکشن کے ذریعے | `5h`, `weekly`   |
| Codex                            | `5h`, `weekly`   |

یہ پڑھنے کے طور پر شمار نہیں ہوتے ہیں:

- ایک جواب فراہم کنندہ کلائنٹ کو باسی کے طور پر نشان زد کرتا ہے۔
- ایک Claude ونڈو جس کی فیصد فراہم کنندہ نے رپورٹ نہیں کی۔
- کسی اور ونڈو کا اعداد و شمار، یا کھڑکیوں میں بدترین صورت
- شرح کی حد ہیڈر فال بیک
- ایک ناکام پڑھنا

دیگر فراہم کنندگان، بشمول Claude ایک API کلید کے ساتھ، کوئی کتاب نہیں ہے۔ ہر کلید کو ان کے فیصد کے طول و عرض پر 0 چارج کیا جاتا ہے، جیسا کہ اس تبدیلی سے پہلے تھا۔

ایک ریڈنگ سنترپتی سگنل کے 30 سیکنڈ کیشے کو شیئر کرتی ہے۔ Claude پڑھنے کی تاریخ اس وقت ہوتی ہے جب اعداد و شمار کو جوابی سرخیوں میں دیکھا گیا تھا یا استعمال کے اختتامی نقطہ سے پڑھا گیا تھا، جب وہ وقت معلوم ہوتا ہے۔ دیگر ریڈنگز کی تاریخ اس وقت کی ہے جب وہ کیش اندراج بنایا گیا تھا۔

#### کتاب کیا رکھتی ہے۔

ہر ریکارڈ شدہ درخواست اپنے ٹوکن، ایک بار، ایک کاؤنٹر فی پول، اکاؤنٹ اور کلید میں شامل کرتی ہے۔ ایک کاؤنٹر صرف بڑھتا ہے۔ کتاب تین چیزیں رکھتی ہے:

- بیس لائن: وہ اعداد و شمار جب کتاب کھلی یا کھڑکی آخری بار مڑی۔
- آخری لاگو شکل
- فی کلید، اسی لمحے اس کا ٹوکن کاؤنٹر، اس کا نشان کہلاتا ہے۔

جب نفاذ یا استعمال کا راستہ انتساب کی گنتی کرتا ہے تو کتاب کو اپ ڈیٹ کیا جاتا ہے۔ تحریروں کا ایک نظرثانی نمبر پر موازنہ اور سیٹ کیا جاتا ہے۔ ایک مصنف جو ہار جاتا ہے ایک بار تازہ پڑھنے پر دوبارہ کوشش کرتا ہے۔

#### کلید کے حصے کی گنتی کیسے کی جاتی ہے۔

جب کتاب پڑھی جاتی ہے تو ہر کلید کے حصے کی گنتی کی جاتی ہے۔ اعداد و شمار کی نمو چونکہ بیس لائن کو کلیدوں کے درمیان ٹوکن کے تناسب سے تقسیم کیا گیا ہے ہر ایک کو نشان کے بعد سے روٹ کیا گیا ہے۔

Together، وہ ٹوکن فی `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` ٹوکن (پہلے سے طے شدہ 1,000) کے اعداد و شمار کے زیادہ سے زیادہ ایک نقطہ کی وضاحت کرتے ہیں۔ وہ جس ترقی کی وضاحت نہیں کرتے وہ بیرونی ہے۔ بیس لائن بھی بیرونی ہے۔

مثال کے طور پر، ایک کتاب 0 پر کھلتی ہے۔ کلیدی A پھر 900,000 ٹوکنز اور کلیدی B روٹس 100,000 کو روٹ کرتی ہے۔ 60 کے اعداد و شمار پر، A کا حصہ 54 پوائنٹس اور B کا حصہ 6 ہے۔

اس کے کلید کے نشان کے نیچے ایک کاؤنٹر دوبارہ شروع ہو گیا ہے اور پوری گنتی ہے۔ نشان کے بغیر ایک کلید، جیسے ایک چابی جو کھڑکی کے بیچ میں موجود پول میں شامل ہوتی ہے، اس کے تمام ٹوکن شمار کرتی ہے۔ ایک اعداد و شمار جو ٹوکنز کو پیچھے چھوڑ دیتا ہے ایک غلطی کا سبب بنتا ہے جو اگلی پڑھنے میں دور ہو جاتا ہے۔ یہ جمع نہیں ہوتا۔

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` ہر انتساب پر پڑھا جاتا ہے۔ ایک قدر جو کم از کم 1 کی محدود تعداد نہیں ہے واپس 1,000 پر آتی ہے۔

#### پڑھنے سے کتاب کیسے بدل جاتی ہے۔

پہلا مماثل اصول لاگو ہوتا ہے:

1. **ابھی تک کوئی کتاب نہیں:** پڑھنے سے کتاب کھل جاتی ہے۔ اس کا فگر بیس لائن ہے اور ہر کاؤنٹر پر نشان لگا ہوا ہے۔
2. **پرانا پڑھنا:** آخری لاگو ہونے سے پہلے کی تاریخ کو نظر انداز کر دیا گیا ہے۔ اسی طرح ایک پڑھنا ہے جس کا دوبارہ ترتیب دینے کا وقت ذخیرہ شدہ سے 30 منٹ پہلے ہے۔
3. **نئی فراہم کنندہ ونڈو:** دوبارہ ترتیب دینے کا وقت 30 منٹ سے زیادہ بعد میں ذخیرہ شدہ کتاب کو موڑ دیتا ہے۔ اعداد و شمار بیس لائن بن جاتا ہے اور ہر کاؤنٹر کو دوبارہ نشان زد کیا جاتا ہے۔ کاؤنٹر کے بغیر چابیاں کتاب کو چھوڑ دیتی ہیں۔
4. **ختم شدہ ونڈو:** ایک ذخیرہ شدہ ری سیٹ ٹائم جو پڑھنے کے ڈیٹا ٹائم کے بعد نہیں ہے اس کا مطلب ہے کہ ونڈو ختم ہو گئی ہے۔ پڑھنے سے کتاب بدل جاتی ہے، خواہ اس کی شکل کچھ بھی ہو۔
5. **اعلی شخصیت:** صرف آخری اعداد و شمار چلتا ہے. بیس لائن اور نشان باقی ہیں۔
6. **ایک ہی شکل:** اعداد و شمار، بیس لائن اور نشان رہتے ہیں. کتاب کا فقدان صرف ایک ری سیٹ وقت لکھا جاتا ہے۔
7. **نچلی شکل:** نچلے اعداد و شمار کا اطلاق کبھی نہیں ہوتا ہے۔ یہ کتاب تبھی بدلتی ہے جب تین چیزیں پکڑی جاتی ہیں۔ یہ آخری لاگو پڑھنے سے کم از کم دو منٹ نیا ہے۔ کچھ نہیں کہتا کہ کھڑکی وہی کھلی ہے۔ یہ ایک سے زیادہ پوائنٹ کم ہے۔

جب تین چیزیں ہوتی ہیں تو ونڈو ایک ہی کھلی کے طور پر شمار ہوتی ہے۔ ری سیٹ کے دونوں اوقات معلوم ہیں۔ وہ ایک دوسرے کے 30 منٹ کے اندر ہیں۔ ذخیرہ شدہ ابھی بھی پڑھنے سے آگے ہے۔ اس کھڑکی کے اندر ایک نچلی شخصیت کچھ نہیں بدلتی۔

دوبارہ ترتیب دینے کا وقت صرف اس وقت ذخیرہ کیا جاتا ہے جب یہ پڑھنے کے ڈیٹا ٹائم سے آگے ہوتا ہے جو اسے لے جاتا ہے۔ ایک اعلی شخصیت اس کے پڑھنے کے ری سیٹ وقت کو ذخیرہ کرتی ہے جب وہ قابل استعمال ہوتا ہے، اور ذخیرہ شدہ کو دوسری صورت میں رکھتا ہے۔ ایک مساوی اعداد و شمار اس کے پڑھنے کے دوبارہ ترتیب دینے کا وقت صرف اس وقت ریکارڈ کرتا ہے جب کتاب میں کوئی نہ ہو۔ یہ اور کچھ نہیں بدلتا۔ ایک نچلی شخصیت جو کتاب کو تبدیل نہیں کرتی ہے اس کا کوئی ری سیٹ وقت نہیں ہے۔

#### جب کتاب استعمال ہوتی ہے۔

پڑھنے کے بعد، کتاب استعمال کی جاتی ہے جب تک کہ اس کا ذخیرہ شدہ ری سیٹ کا وقت موجودہ وقت کے بعد نہ ہو۔ یہ معاملہ اس وقت پیدا ہوتا ہے جب دوبارہ ترتیب دینے سے پہلے لی گئی پڑھائی، جیسے کہ کیشے سے پیش کی گئی، اس کے فوراً بعد دیکھی جاتی ہے۔

قابل استعمال پڑھنے کے بغیر، ذخیرہ شدہ کتاب کو صرف اس وقت استعمال کیا جاتا ہے جب یہ اب بھی موجودہ ونڈو کی کتاب ہوسکتی ہے۔ یہ دو صورتوں میں ہوتا ہے:

- اس کا دوبارہ ترتیب دینے کا وقت معلوم ہے اور ابھی آگے ہے۔
- اس کا کوئی دوبارہ ترتیب دینے کا وقت نہیں ہے، اور آخری پڑھنا جس نے اسے تبدیل کیا ہے وہ زیادہ سے زیادہ 15 منٹ پرانا ہے۔

ورنہ کچھ بھی منسوب نہیں ہوتا، جیسا کہ جب کوئی کتاب نہ ہو۔ ایک کتاب جس کا ذخیرہ شدہ ری سیٹ کا وقت گزر گیا ہے کبھی چارج نہیں کیا جاتا ہے۔

#### نفاذ

فیصد جہت پر ایک کلید کی کھپت اس کا منسوب حصہ اور بیرونی حصے کا حصہ ہے۔ بیرونی حصہ سب سے پہلے اس صلاحیت کا استعمال کرتا ہے جس کا کوئی مختص دعوی نہیں ہوتا ہے (100 مائنس وزن کا مجموعہ)۔ وزن کے لحاظ سے چابیاں کے درمیان صرف اضافی کا اشتراک کیا جاتا ہے۔

اس کھپت کا موازنہ کلید کے منصفانہ حصص سے کیا جاتا ہے جیسا کہ کسی دوسرے جہت کے لیے۔ سخت موڈ تب بھی شروع ہوتا ہے جب سنترپتی سگنل `QUOTA_SATURATION_THRESHOLD` (پہلے سے طے شدہ 0.5) تک پہنچ جاتا ہے۔ ہر نمبر کو مؤثر حد سے چھوٹا کیا جاتا ہے: فی اکاؤنٹ کی حد پول میں اکاؤنٹس کی تعداد کو گنا کرتی ہے۔

`capUnit: "percent"` کے ساتھ ایک مطلق ٹوپی صرف کلید سے منسوب حصہ شمار کرتی ہے، اسی طرح اسکیل کیا جاتا ہے۔ فی اکاؤنٹ کی حد 100 اور k اکاؤنٹس لیں۔ N کی ٹوپی تب پہنچ جاتی ہے جب سرونگ اکاؤنٹ کے اعداد و شمار کا کلید کا حصہ N/k پوائنٹس تک پہنچ جاتا ہے۔ ہر اکاؤنٹ کو اس کی اپنی کتاب کے خلاف چیک کیا جاتا ہے۔ مثال کے طور پر، دو اکاؤنٹس کے ساتھ، ایک اکاؤنٹ کے اعداد و شمار کے 5 پوائنٹس پر 10 کی کیپ پہنچ جاتی ہے۔

جب اسٹور کو پڑھا نہیں جا سکتا ہے، تو کچھ بھی منسوب نہیں کیا جاتا ہے اور ہر کلید کو اس جہت پر 0 چارج کیا جاتا ہے۔ جب کوئی کتاب لکھنے میں ناکام ہوجاتی ہے، تو وہ انتساب کتاب کا استعمال کرتا ہے جیسا کہ اسے پڑھا گیا تھا۔ ایک ناکام ٹوکن تحریر اس درخواست کے ٹوکن کو کتاب سے باہر کر دیتا ہے۔ ان میں سے کوئی بھی ناکامی کسی درخواست کو بلاک نہیں کرتی ہے۔

`consent` پول میں، قرض دینے کا فارمولہ ہر کلید کی کھپت کو فیصد کے جہت پر استعمال کرتا ہے جیسا کہ اوپر بیان کیا گیا ہے۔ جب کوئی اور کلید قرض دیتی ہے تو کتاب کو ایک بار پڑھا جاتا ہے اور ہر کلید سے منسوب کیا جاتا ہے۔ قابل استعمال کتاب کے بغیر ہر چابی 0 چارج کی جاتی ہے۔ وزن والی ایک کلید پھر گزر جاتی ہے، اور 0 وزن والی چابی صرف اس وقت گزرتی ہے جب دوسری کلید قرضہ دیتی ہے۔

#### استعمال کا راستہ

`GET /api/quota/pools/{id}/usage` ایک ہی فنکشن کے ذریعے ایک ہی نمبر کی اطلاع دیتا ہے۔ `accounts` میں فی پول کنکشن پر ایک فیصد ڈائمینشن میں ایک اندراج ہے۔ اس کے اعلیٰ درجے کے `consumedTotal` اور `perKey` پہلے اندراج کی آئینہ دار ہیں۔

روٹ موجودہ پڑھنے پر بھی لاگو ہوتا ہے، لہذا یہ کتاب کو آگے بڑھا سکتا ہے جیسا کہ درخواست کرتا ہے۔ `internal + external` `consumedTotal` سے مختلف ہو سکتا ہے جب کوئی قابل استعمال پڑھنا نہ ہو، یا جب نچلے اعداد کا اطلاق نہ ہو۔

#### ذخیرہ اور برقرار رکھنا

دونوں کوٹہ اسٹور کتاب رکھتے ہیں۔ SQLite پر، خودکار ڈیٹا بیس کلین اپ، فعال ہونے پر، 60 دنوں تک اپ ڈیٹ نہ ہونے والی قطاروں کو ہٹا دیتا ہے۔ Redis پر، پول کنکشن کی کتابیں اور کاؤنٹرز ایک کلید کا اشتراک کرتے ہیں۔ اس کی میعاد اس کے آخری ٹوکن لکھنے یا کتاب کی تبدیلی کے 60 دن بعد ختم ہو جاتی ہے۔ ایک کتاب جو تبدیل نہیں ہوتی اسے دوبارہ نہیں لکھا جاتا ہے، لہذا کٹ آف سب سے طویل پلان ونڈو کے اوپر سیٹ کیا جاتا ہے۔ دستی استعمال کی تاریخ کو دوبارہ ترتیب دینے سے SQLite پر کتابیں بھی صاف ہو جاتی ہیں (حدود دیکھیں)۔

#### حدود

## پائپ لائن انٹیگریشن

### PRE ہک (`open-sse/handlers/chatCore.ts`)

اپ اسٹریم ایگزیکیوٹر سے پہلے، تصدیق اور پالیسی کی جانچ کے بعد چلتا ہے:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**فیل کھلنا** : اگر `enforceQuotaShare` پھینکتا ہے تو، درخواست کو `pino.warn` لاگ کے ذریعے اجازت دی جاتی ہے۔ یہ کوٹہ انجن بگ کو تمام ٹریفک کو روکنے سے روکتا ہے۔

**جب صلاحیت واپس آتی ہے۔** کلید کے حصہ پر یا پول کی چھت پر انکار دو جملوں میں سے ایک کے ساتھ ختم ہوتا ہے، دونوں ادھار کے طریقوں میں:

- `percent` ونڈو: `. The <window> window resets at <time>.` فراہم کنندہ کی رپورٹ کو دوبارہ ترتیب دینے کا وقت ہے۔
- قابل شمار یونٹ: `. Enough <window> usage is expected to clear by <time>.` وقت سلائیڈنگ ونڈو سے اوپری باؤنڈ ہے، اگر کلید کچھ اور نہیں بھیجتی ہے۔

`<time>` UTC میں ایک ISO 8601 فوری ہے۔ انکار پھر `Retry-After` لے جاتا ہے : اس لمحے تک پورے سیکنڈ، جمع ایک۔ ایک کلائنٹ جو طویل انتظار کرتا ہے فوری طور پر زیادہ سے زیادہ ایک سیکنڈ کے بعد دوبارہ کوشش کرتا ہے۔ جب فوری معلوم نہ ہو تو انکار میں نہ تو جملہ ہوتا ہے نہ ہیڈر۔ ایک مطلق ٹوپی انکار کی جاتی ہے نہ ہی. عوامی کوڈ `quota_share_blocked` رہتا ہے۔

اشتراک سے انکار مشترکہ کنکشن کو نہیں چھوتا ہے۔ یہ کوئی کولڈاؤن سیٹ نہیں کرتا، کوئی ماڈل لاک اور کوئی پرووائیڈر بریکر فیل نہیں ہوتا، اور پول کی دوسری چابیاں پیش کی جاتی رہیں۔ جب کامبو کا ہر ہدف اپنے حصے کی کلید سے انکار کرتا ہے، تو کومبو انتظار کیے بغیر 429 کا جواب دیتا ہے۔ اس کا جواب `Retry-After` کے طور پر اشارہ کرتا ہے۔ سرایت کرنے کا راستہ اسی جملے کے ساتھ اپنے انکار کو ختم کرتا ہے اور کوئی `Retry-After` نہیں بھیجتا ہے۔

### POST ہک (ریکارڈ کھپت)

کامیاب جواب کے بعد:

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**بڑھے ہوئے نوٹ** : اگر `consume` جواب کے بعد ناکام ہو جاتا ہے تو رولنگ کاؤنٹر کم شمار ہوتا ہے۔ فراہم کنندہ کی طرف سے سنترپتی سگنل (مثال کے طور پر `anthropic-ratelimit-unified-5h-utilization`) اگلی درخواست پر عالمی تخمینہ کو درست کرتا ہے۔

## سیلف سروس کوٹہ API (آپٹ ان)

`GET /api/v1/me/quota/{provider}` ( `/v1/me/quota/{provider}` میں بھی پیش کیا جاتا ہے) ایک API کلید رکھنے والے کو ان کی اپنی کلید کے ساتھ یہ پڑھنے دیتا ہے کہ مشترکہ سبسکرپشن ان کی کتنی ہے اور کیا چیز انہیں روک رہی ہے۔ روٹ `src/server/selfService/quotaHandler.ts` پر ایک پتلا شیل ہے؛ منظر `src/lib/quota/selfView.ts` نے بنایا ہے اور اس کا جوابی معاہدہ `src/shared/schemas/selfQuota.ts` ( `docs/openapi.yaml` میں `SelfQuotaView` ) ہے۔

### فعال کرنا اور تصدیق کرنا

- نمایاں پرچم `QUOTA_SELF_PANEL`, ڈیفالٹ `false`. جب یہ بند ہوتا ہے، روٹ تک پہنچنے والی درخواست کو 404 مل جاتا ہے۔ `REQUIRE_API_KEY=true` کے ساتھ، کلائنٹ API پالیسی روٹ کے چلنے سے پہلے 401 کے ساتھ غائب یا غلط کلید سے انکار کرتی ہے، چاہے کوئی بھی جھنڈا ہو۔ ایک درخواست جس میں کوئی کلید نہیں ہے لیکن ایک سائن ان کردہ ڈیش بورڈ سیشن اس پالیسی کو پاس کرتا ہے اور روٹ کا اپنا جواب حاصل کرتا ہے۔ جھنڈا ہر دوسرے جھنڈے کی طرح حل ہوتا ہے (ڈیش بورڈ یا REST اوور رائڈ، پھر اسی نام کا ماحولیاتی متغیر)؛ [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md) دیکھیں۔
- ہر پول کا ڈسپلے نام اور ہر شیڈول کا لیبل پول کے کلیدی ہولڈرز کو بالکل ویسے ہی واپس کر دیا جاتا ہے جیسا کہ منتظم نے لکھا تھا۔ جھنڈا آن کرنے سے پہلے، چیک کریں کہ وہ ان کلیدی ہولڈرز کے پڑھنے کے لیے موزوں ہیں۔
- کلید صرف ہیڈرز سے پڑھی جاتی ہے: `Authorization: Bearer <key>` یا `x-api-key: <key>`۔ جب دونوں بھیجے جاتے ہیں، تو پہلا استعمال کیا جاتا ہے جس کی توثیق ہوتی ہے۔ استفسار کے سٹرنگ میں ایک کلید یا کوکی کو نظر انداز کر دیا جاتا ہے۔ سرور کی ماحولیاتی کلید سے انکار کر دیا گیا ہے (401)۔
- کلید کو `self:usage` دائرہ کار کی ضرورت ہے (اس کے بغیر 403)۔
- فراہم کنندہ کے حصے کو تراش لیا جاتا ہے، لوئر کیس کیا جاتا ہے اور `^[a-z0-9][a-z0-9._-]{0,63}$` (400 بصورت دیگر) کے خلاف جانچ پڑتال کی جاتی ہے، پھر فراہم کنندہ کی رجسٹری کے ذریعے حل کیا جاتا ہے، لہذا `cc` جیسا عرف `claude` پولز کو پڑھتا ہے۔ `claude` اور `anthropic` ایک ہی پول پڑھتے ہیں۔

| مرئیت         | کی ضرورت ہے۔                                                                            | فیلڈز                                                                                                                                                                                                                                                                           |
| ------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

- اکاؤنٹ بارز اور ماڈل ونڈوز صرف ان اکاؤنٹس کے لیے دکھائی جاتی ہیں جن کا کنکشن کلید استعمال کر سکتی ہے۔ جب کلید کے پاس اجازت شدہ کنکشنز کی فہرست ہوتی ہے، تو اس کے باہر ایک اکاؤنٹ `account` یا `modelWindows` کے بغیر اپنی `Account N` اندراج رکھتا ہے۔ خالی فہرست کا مطلب ہے کوئی پابندی نہیں، جیسا کہ `/v1/me/status`۔ پول کل (`dimensions[].total`) اس فہرست پر منحصر نہیں ہے۔
- صرف `self:usage` کے ساتھ دکھائے گئے دو اعداد و شمار دوسری کلیدوں کے استعمال سے آتے ہیں۔ شیڈول بجٹ کا `exhausted` اس شیڈول کے تحت ہر کلید کے استعمال کی عکاسی کرتا ہے۔ ایک تالاب میں جس کا وزن تمام صفر ہے، کلید کا `weight` `100 / number of members` ہے۔ دونوں وہی ہیں جو کلید پر لاگو ہوتے ہیں۔
- ایک پول کی شناخت صرف `ref` سے ہوتی ہے، کالنگ کلید سے منسلک ایک مبہم قدر۔ اس کا ڈسپلے نام (`name`) شامل ہے جیسا کہ منتظم نے لکھا ہے۔ ایک `ref` کلید اور سرور کے API- کلید راز (`API_KEY_SECRET`) کے ساتھ پول سے اخذ کیا گیا ہے۔ کلائنٹس کو اسے برقرار نہیں رکھنا چاہئے: اگر اس راز کو گھمایا جائے تو یہ بدل جاتا ہے۔
- اکاؤنٹس کو پول آرڈر میں `Account 1`، `Account 2`، … کے طور پر درج کیا گیا ہے۔ کوئی پول آئی ڈی، کنکشن آئی ڈی، اکاؤنٹ ای میل یا اکاؤنٹ کا نام واپس نہیں کیا جاتا ہے، اور جواب کنٹریکٹ اسکیما کے ذریعے جاتا ہے، جو اس کے باہر کسی بھی فیلڈ کو چھوڑ دیتا ہے۔
- قابل گنتی اکائیاں (`requests`, `tokens`, `usd`) پول بالٹی کے طور پر بتائی جاتی ہیں جو کوٹہ گیٹ نافذ کرتا ہے: `limit` = پلان پول میں × اکاؤنٹس کی حد، `fairShare` = وزن / 100 × `limit` (مساوی تقسیم جب ہر کاؤنٹر کا وزن qkz'0 میں ہوتا ہے) = اسٹور، `consumed` `remaining` = `fairShare` − `consumed` 0 پر فرش۔
- `blocks.schedules` کلید کے شیڈول ونڈوز (`open`/`closed`، `blackout` یا `outside-window`، `retryAfterSeconds`، ریزرو فلورز، اور آیا ونڈو کا بجٹ خرچ ہوا ہے) کی فہرست دیتا ہے؛ `blocks.modelCaps` اس کے فی ماڈل فی گھنٹہ کیپس کو استعمال کے ساتھ درج کرتا ہے۔
- فراہم کنندہ کے ہر پول کے باہر ایک کلید `pools: []` کے ساتھ 200 ملتی ہے۔ `availableModels` ( `qtSd/` ids جو کلید `/v1/models` میں دیکھتی ہے)، `expiresAt` اور `apiBaseUrl` ابھی بھی بھرے ہوئے ہیں۔
- `apiBaseUrl` `OMNIROUTE_PUBLIC_API_BASE_URL` ہے، پھر `OMNIROUTE_PUBLIC_BASE_URL`، ورنہ `null`۔ یہ کبھی بھی درخواست کی اپنی اصل نہیں ہے۔

| `connection_lookup_failed`        | اکاؤنٹ کا کنکشن پڑھا نہیں جا سکا۔                                                                                                        |
| `not_supported`                   | OmniRoute اکاؤنٹ کے فراہم کنندہ کے لیے استعمال کی حدیں نہیں پڑھ سکتا۔                                                                    |
| `fetch_failed`                    | کوئی ذخیرہ شدہ پڑھنا قابل استعمال نہیں تھا اور فراہم کنندہ کی حدیں ریفریش ناکام ہوگئیں۔                                                  |
| `not_available`                   | پڑھنے میں استعمال کی کوئی کھڑکی نہیں ہے، یا اکاؤنٹ میں بالکل بھی پڑھنا نہیں ہے۔                                                          |

جب کوٹہ اسٹور نہیں پڑھا جا سکتا ہے، تو `blocks` کے اسٹور سے حمایت یافتہ فیلڈز (ایک شیڈول بجٹ کا `exhausted`، ماڈل کیپ کا `consumed` اور `reached`) بھی `null` ہوتے ہیں۔

### قرض دینے کی رضامندی۔

`PATCH /api/v1/me/quota/{provider}` ایک پول کے لیے کالنگ کلید کی اپنی رضامندی کو ریکارڈ کرتا ہے۔ یہ `GET` کے جھنڈے، ہیڈرز اور فراہم کنندہ کے قواعد کا استعمال کرتا ہے۔ `self:usage` اسکوپ اس تحریر کی اجازت دیتا ہے، حالانکہ اس کا نام صرف پڑھنے کے لیے پڑھا جاتا ہے۔

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` `ref` ہے `GET` اس پول کے لیے واپس آتا ہے۔
- `lendingPercent` 0 سے 100 تک کا عدد ہے۔ 0 کی قدر رضامندی اور اس کی آخری تاریخ کو صاف کرتی ہے۔ `lendingPercent` 0 والی باڈی کسی بھی موڈ میں قبول کی جاتی ہے۔
- `lendingUntil` اختیاری ہے: epoch milliseconds، یا `null` بغیر آخری تاریخ کے۔ یہ مستقبل میں اور زیادہ سے زیادہ 8640000000000000 ہونا چاہیے۔ 1000000000000 سے نیچے کی قدر سیکنڈ کے طور پر پڑھتی ہے اور اسے مسترد کر دیا جاتا ہے۔
- کسی بھی دوسرے میدان سے انکار کر دیا جاتا ہے. 4096 بائٹس سے زیادہ لمبی باڈی سے انکار کر دیا گیا ہے۔ پڑھنا اس سائز پر رک جاتا ہے، لہذا لمبا جسم کبھی بھی مکمل نہیں ہوتا۔

چیک اس ٹیبل کی ترتیب میں چلتے ہیں۔ ہر انکار ایک مقررہ پیغام کے ساتھ معیاری ایرر باڈی کا استعمال کرتا ہے۔ ان میں سے ایک چیک سے انکار کچھ نہیں لکھتا۔

| حیثیت | پیغام                                                                                              | جب                                                                  |
| ----- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 404   | `Not found`                                                                                        | `QUOTA_SELF_PANEL` جھنڈا بند ہے۔                                    |
| 401   | `Valid API key required`                                                                           | کلید غائب یا غلط ہے، یا سرور کی ماحولیاتی کلید ہے۔                  |
| 403   | `API key lacks the self:usage scope`                                                               | کلید میں `self:usage` کمی ہے۔                                       |
| 400   | `Invalid provider`                                                                                 | فراہم کنندہ سیگمنٹ غلط ہے۔                                          |
| 429   | `Too many lending changes. Retry later.`                                                           | چابی اپنی حد سے گزر گئی۔ جواب میں `Retry-After` ہے۔                 |
| 400   | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | جسم JSON نہیں ہے، بہت لمبا ہے، یا اسکیما سے میل نہیں کھاتا ہے۔      |
| 400   | `lendingUntil must be a Unix time in milliseconds`                                                 | آخری تاریخ سیکنڈ کے طور پر پڑھتی ہے۔                                |
| 400   | `lendingUntil must be in the future`                                                               | آخری تاریخ درخواست کے وقت یا اس سے پہلے ہے۔                         |
| 404   | `Pool not found`                                                                                   | `ref` اس فراہم کنندہ کے لیے اس کلید کے کسی پول کا نام نہیں دیتا ہے۔ |
| 403   | `Lending is not enabled for this pool`                                                             | پول `saturation` موڈ میں ہے اور `lendingPercent` 0 سے اوپر ہے۔      |
| 500   | `Failed to build quota view`                                                                       | کوئی اور ناکامی۔ اس کی وجہ سرور پر لاگ ان ہے۔                       |

حد ہر کلید کے لیے 20 درخواستیں فی 60 سیکنڈ ہے۔ ہر وہ درخواست جو فراہم کنندہ کے چیک کو پاس کرتی ہے شمار ہوتی ہے، یہاں تک کہ ایک نے بعد میں انکار کر دیا یا وہ جو کچھ نہیں بدلتی۔ کلید کی درخواست کی شرح کی حد کے علاوہ، اس کا اپنا کاؤنٹر ہے۔

ایک درخواست جو ذخیرہ شدہ رضامندی کو تبدیل کرتی ہے ایک `quota.pool.lending.updated` آڈٹ ریکارڈ لکھتی ہے۔ یہ پرانی اور نئی اقدار کے ساتھ کلید کا نام دیتا ہے۔ ایک ہی باڈی دو بار بھیجتی ہے ایک بار لکھتی ہے اور ایک بار آڈٹ کرتی ہے۔ جواب 200 مکمل `GET` منظر کے ساتھ ہے، جو تحریر کے بعد بنایا گیا ہے۔

`GET` ویو قرض دینے کی رپورٹ درج ذیل ہے:

- ہر پول میں `borrowMode` (`saturation` یا `consent`) ہوتا ہے، اور کلید کا اپنا `lendingPercent` اور `lendingUntil`۔
- `lendingActive` صرف `consent` پول میں `true` ہے، جس کا فیصد 0 سے اوپر ہے اور آخری تاریخ تک نہیں پہنچی ہے۔
- ایک `consent` پول میں، ہر قابل شمار `dimensions[].yourShare` میں `borrowAvailable` ہوتا ہے۔ یہ وہی ہے جسے کلید اب اپنے حصے کے اوپر استعمال کر سکتی ہے، دوسری کلیدوں کے ذریعے دی گئی ہے۔
- `borrowAvailable` گیٹ کا فارمولا استعمال کرتا ہے۔ یہ ہر دوسری کلید کو پڑھتا ہے، اس وقت بھی جب کلید اس کے حصے کے نیچے ہو۔ ایک `hard` کلید کے لیے جو کہ ایک اضافی پڑھی ہوئی ہے فی دوسری کلید اور قابل شمار جہت، متوازی طور پر۔
- `borrowAvailable` `soft` یا `burst` کلید کے لیے `null` ہے، اور `null` جب پڑھنا ناکام ہوجاتا ہے۔
- `borrowAvailable` دیگر تمام کلیدوں کے لیے ایک شکل ہے۔ دو کلیدوں کے تالاب میں یہ دوسری کلید کی اپنی شکل ہے۔
- `borrowAvailable` کی ابھی تک `percent` windows یا `accounts[]` میں اطلاع نہیں ہے۔
- ایک `saturation` پول میں منظر `lendingActive: false` اور بغیر `borrowAvailable` کے ساتھ ذخیرہ شدہ رضامندی کی اطلاع دیتا ہے۔

### غلطیاں

Every response of this route, success or error, carries `Cache-Control: no-store`. A refusal that happens before the route runs does not carry it, for example the client API policy's 401 or the IP filter's 403. Errors of the route use the standard error body with a fixed message: 400 (invalid provider), 401 (missing or invalid key), 403 (missing `self:usage`), 404 (flag off) and 500 (`Failed to build quota view`). The 500 covers any failure once the request reaches the route, including the key lookup itself; its cause is logged on the server and never returned. The errors of the `PATCH` are listed in [Lending consent](#lending-consent).

### حدود

- `remaining` کلید کے منصفانہ حصہ کا وہ حصہ ہے جسے اس نے استعمال نہیں کیا ہے۔ یہ کوئی ضمانت نہیں ہے۔ ایک چابی اب بھی اس سے باہر پیش کی جا سکتی ہے جب کہ پول میں کمرہ ہو۔ ایک بار جب پول کا ٹوٹل `limit` تک پہنچ جاتا ہے، تو پول کی ہر چابی سے انکار کر دیا جاتا ہے، چاہے اس کی اپنی `remaining`، اور `self:account-quota` کے بغیر کوئی کلید اس کل کو نہیں دیکھ سکتی۔
- `remaining` مختص کے مطلق `cap` مدنظر نہیں رکھتا ہے۔ جب کیپ یونٹ کی کھڑکی میں اس کی اپنی کھپت ٹوپی کی قدر تک پہنچ جاتی ہے تو نفاذ کلید کو مسترد کر دیتا ہے۔
- اکاؤنٹ کی سطح کا بار فراہم کنندہ کی حد کیش سے آتا ہے اور نفاذ کے فیصلے کو چند منٹوں تک پیچھے چھوڑ سکتا ہے۔ ایک پڑھنا جس کا دوبارہ ترتیب دینے کا وقت گزر چکا ہے اسے `stale` کہا جاتا ہے۔
- فی ماڈل ونڈوز (`modelWindows`) کی اطلاع صرف ان فراہم کنندگان کے لیے دی جاتی ہے جن کے پاس پلان ونڈو میپنگ ہے: Claude اور Codex آج۔ دوسرے فراہم کنندگان کے لیے `modelWindows` تب بھی موجود ہوتا ہے جب اکاؤنٹ کا ڈیٹا خالی `windows` فہرست کے ساتھ دکھایا جاتا ہے۔
- `percent` ونڈو کی کلید کا اپنا حصہ ایک تخمینہ ہے۔ یہ انتساب کی کتاب سے آتا ہے اور اوپر "فیصد جہت: فی کلیدی انتساب" کے تحت درج ہر حد کو رکھتا ہے۔
- `consumed` وہ نمبر ہے جس کا منصفانہ حصہ سے موازنہ کیا جاتا ہے۔ یہ `attributed` پلس `external` ہے، بالکل۔ `attributed` وہ حصہ ہے جو کتاب روٹ کیے گئے ٹوکنز کی کلید دیتی ہے۔ `external` اکاؤنٹ کے استعمال کا کلید کا حصہ ہے جس کا پول کی چابیاں نہیں کرتی ہیں۔
- دونوں حصے تبھی بھیجے جاتے ہیں جب پول کا `accountVisible` درست ہو: کلید میں `self:account-quota` ہے اور فراہم کنندہ اس کے `sharedQuotaProviders` میں ہے۔ ایک کلید اس کے بغیر اکیلے `consumed` ہو جاتی ہے، اسی `status` اور `reason` کے ساتھ۔
- دونوں حصوں اور اس کے اپنے وزن کے ساتھ، ایک ہولڈر پول کے باہر بنائے گئے استعمال کو پورا کر سکتا ہے جو پول کی چابیاں سے چارج کیا جاتا ہے۔ اکاؤنٹ کے دائرہ کار کے حامل ایک ہولڈر کو اکاؤنٹ کی کل رقم پہلے ہی نظر آتی ہے۔
- ایک کلید جس نے ونڈو میں کچھ بھی نہیں روٹ کیا وہ اب بھی اپنے بیرونی چارج کو `consumed` سے پڑھ سکتی ہے، کیونکہ اس کا منسوب حصہ پھر 0 ہے۔
- مثال کے طور پر، ایک کتاب 0 پر کھلتی ہے، جس میں A اور B کیز ہر ایک کا وزن 50 ہے۔ کلیدی A روٹس 900,000 ٹوکنز اور کلید B 100,000۔ اس کے بعد اکاؤنٹ 100 کی حد کے 60% تک پہنچ جاتا ہے۔ پھر `attributed` کلید A کے لیے 54 اور کلید B کے لیے 6 ہے، اور `external` دونوں کے لیے 0 ہے۔
- نظریہ کتاب پڑھتا ہے اور اپنی حالت کبھی نہیں لکھتا۔ یہ ایک کتاب نہیں کھولتا ہے، اور یہ کبھی بھی فراہم کنندہ سے پڑھنے کے لئے نہیں پوچھتا ہے۔ Redis اسٹور کے ساتھ، ایک ریڈ بیک گراؤنڈ میں نظر ثانی شدہ فیلڈز کو ہٹاتا ہے، جیسا کہ گیٹ کے ریڈز کرتے ہیں۔
- حصہ صرف `ok` ہے جب کہ گیٹ کے کیشے میں اکاؤنٹ کی ریڈنگ ہوتی ہے۔ ایک کے بغیر یہ ہے `stale`، اس لیے کسی تالاب میں جس میں کوئی حالیہ درخواست نہیں ہے یہ ممکنہ طور پر پرانی دکھائی دیتی ہے۔
- جب تک کوئی درخواست پول میں نہیں جاتی ہے، شیئر دستیاب نہیں ہے۔ اس درخواست سے کتاب کھل جاتی ہے، اور اس وقت اکاؤنٹ کا اعداد و شمار پول کے باہر کیے گئے استعمال کے طور پر شمار ہوتا ہے۔
- متعدد اکاؤنٹس والے پول میں، ہر اکاؤنٹ کا اندراج اس اکاؤنٹ کی اپنی کتاب اور ایک اکاؤنٹ کی حد کا استعمال کرتا ہے۔ انفورسمنٹ اکاؤنٹس کی تعداد کے لحاظ سے دونوں اطراف کو پیمانہ کرتا ہے، لہذا تناسب ایک جیسا ہے۔
- فی ماڈل ونڈوز میں چابی کا کوئی حصہ نہیں ہوتا ہے۔ کتاب فی ماڈل ڈیٹا نہیں رکھتی ہے۔
- شیڈول کے ریزرو فلورز کا اندازہ اس منظر سے نہیں کیا جاتا ہے: ایک شیڈول `open` کے طور پر ظاہر ہو سکتا ہے جب کہ `schedule-reserve` کی وجہ سے درخواست مسترد کر دی جاتی ہے۔
- جب ایک ہی کلید کے دو پول ایک کنکشن کا اشتراک کرتے ہیں، انفورسمنٹ ان میں سے ایک کو لاگو کرتا ہے، اور منظر دونوں کی فہرست دیتا ہے۔
- ناکام کلیدی کوششوں پر فی ایڈریس کی کوئی حد نہیں ہے: ریورس پراکسی کال کرنے والے ایک پتے کا اشتراک کر سکتے ہیں (یہ اس بات پر منحصر ہے کہ آیا آگے بھیجے گئے کلائنٹ کے پتے پر بھروسہ ہے)، اس لیے لاک آؤٹ ہر کلید رکھنے والے کے راستے سے انکار کر سکتا ہے۔ `REQUIRE_API_KEY=true` کے ساتھ، روٹ کے چلنے سے پہلے کلائنٹ API پالیسی کی طرف سے ایک غلط کلید سے انکار کر دیا جاتا ہے، اس روٹ کی بجائے اس پالیسی کی 401 باڈی کے ساتھ۔

### ممبر کا استعمال

ایک منتظم کلیدی ہولڈرز کو یہ دیکھنے دے سکتا ہے کہ ونڈو کا استعمال پول کے اراکین کے درمیان کیسے تقسیم ہوتا ہے۔ آپشن پول کا `memberBreakdown` ہے، بطور ڈیفالٹ آف۔ یہ پول وزرڈ میں یا `PATCH /api/quota/pools/{id}` کے ساتھ سیٹ کیا گیا ہے۔ `GET /api/quota/pools` اور `GET /api/quota/pools/{id}` اس کی اطلاع دیتے ہیں۔

نقطہ نظر کی ایک جہت `members` لے جاتی ہے جب یہ سب کچھ رکھتے ہیں:

- پول کا آپشن آن ہے۔
- پول میں زیادہ سے زیادہ 20 مختص کیز ہیں، اور ان میں سے کم از کم تین درخواستیں کر سکتے ہیں: فعال، منسوخ نہیں، پابندی نہیں اور ان کی میعاد ختم نہیں ہوئی
- پول کا `accountVisible` درست ہے: کلید میں `self:account-quota` ہے اور فراہم کنندہ اس کے `sharedQuotaProviders` میں ہے
- `percent` ونڈو پر، اکاؤنٹ کا کنکشن ایک کلید ہے جسے استعمال کیا جا سکتا ہے۔
- اس ونڈو کی کلید کا اپنا حصہ پڑھا گیا تھا: اس کا `status` `unavailable` نہیں ہے۔

ورنہ `members` غائب ہے۔ یہ کبھی بھی خالی فہرست نہیں ہے۔

- ہر ٹکڑا `{ slot, consumed, isYou }` ہے۔ رسپانس اسکیما ایک سلائس پر کسی بھی دوسری پراپرٹی کو مسترد کرتا ہے، اور 20 سے زیادہ سلائسوں کی فہرست۔ سلائسیں سلاٹ آرڈر میں درج ہیں۔
- فی مختص کلید کا ایک ٹکڑا ہے، بشمول ایک کلید جو مزید درخواستیں نہیں کر سکتی۔ ایک رکن جس کا کوئی استعمال نہیں وہ حقیقی صفر دکھاتا ہے۔

### استعمال کی سیریز (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` ( `/v1/me/usage` میں بھی پیش کیا جاتا ہے) کالنگ کلید کی اپنی درخواستوں کا استعمال اور لاگت واپس کرتا ہے: کل، ایک اندراج فی UTC دن، فی دن اور ماڈل، فی ماڈل اور فی فراہم کنندہ۔ یہ پرچم، توثیق کے قواعد، `self:usage` دائرہ کار، `Cache-Control: no-store` اور اوپر کوٹہ روٹ کے خرابی کے رویے کا اشتراک کرتا ہے۔ کلید کو `range` سے پہلے چیک کیا جاتا ہے۔ غلطیاں 400 (`Invalid range`)، 401, 403, 404 اور 500 (`Failed to build usage`) ہیں۔

- `range` `1d`، `7d`، `30d` (پہلے سے طے شدہ) یا `90d` میں سے ایک ہے۔ کوئی دوسری قدر، خالی قدر یا بار بار پیرامیٹر 400 ہے۔ کال کی لاگت کو پابند کرنے کے لیے سیٹ `90d` پر رک جاتا ہے۔ یہ منظر صرف استعمال کی خام تاریخ پڑھتا ہے، روزانہ کے خلاصے کبھی نہیں ہوتے، جن میں کوئی کلید نہیں ہوتی۔
- قطاروں کا انتخاب کالنگ کی کی آئی ڈی سے کیا جاتا ہے۔ کلیدی نام کا کالم کبھی مماثل نہیں ہوتا ہے، اور کلیدی شناخت کے بغیر ریکارڈ کی گئی قطاریں کبھی شمار نہیں ہوتی ہیں۔
- سیریز بنانا ونڈو میں کلید کی قطاروں پر پانچ گروپ شدہ سوالات چلاتا ہے۔ بلٹ سیریز کو 60 سیکنڈ فی کلید اور رینج کے لیے دوبارہ استعمال کیا جاتا ہے، اور دوبارہ استعمال شدہ کال کوئی نہیں چلتی ہے۔ اس کا `generatedAt` اس کی عمر بتاتا ہے۔
- جب سیریز بنتی ہے تو ونڈو ختم ہوجاتی ہے۔ ایک قطار جو بعد میں مہر لگائی گئی ہے، مثال کے طور پر گھڑی کی ترچھی سے، شمار نہیں کی جاتی ہے۔
- `coverage.retentionDays` آپریٹر کی خام استعمال کی تاریخ برقرار رکھنے کی ترتیب ہے (ڈیٹا بیس کی ترتیبات میں `retention.usageHistory` )۔ `coverage.truncatedByRetention` درست ہے جب درخواست کی گئی حد اس ترتیب سے لمبی ہو۔ یہ دو نمبروں کا موازنہ کرتا ہے اور یہ چیک نہیں کرتا ہے کہ آیا قطاریں واقعی غائب ہیں۔
- فراہم کنندہ کو کلید کی اپنی درخواستوں کے ریکارڈ کے مطابق واپس کیا جاتا ہے۔ ماڈل اس کے آخری `/` کے بعد ریکارڈ شدہ نام ہے، اور اس کے ذریعہ قطاروں کو گروپ کیا گیا ہے۔ ایک کومبو درخواست جس کے ہر ہدف سے انکار کر دیا گیا تھا روٹنگ لیبل کے ساتھ بطور فراہم کنندہ (کومبو نام، `auto` یا `combo`) اور کلائنٹ کے بھیجے گئے ماڈل سٹرنگ کے ساتھ ریکارڈ کیا جاتا ہے۔ دیگر مسترد شدہ درخواستیں، مثال کے طور پر اوپن سرکٹ بریکر، ایک ماڈل کولڈاؤن یا کوٹہ پر رکھی گئی سکیپ، ہدف فراہم کنندہ اور ماڈل کو رکھیں۔
- شمار اور اخراجات کے علاوہ، جواب میں اوسط تاخیر، کامیابی کی شرح اور پہلی اور آخری درخواست کے اوقات ہوتے ہیں۔
- `byModel` سب سے زیادہ درخواستوں کے ساتھ فراہم کنندہ اور ماڈل کے 50 جوڑوں کی فہرست بناتا ہے۔ مزید جوڑوں کے ساتھ اس کے اندراجات `summary` میں شامل نہیں ہوتے ہیں، اور `summary.uniqueModels` ہر ریکارڈ شدہ ماڈل کے ہجے کو شمار کرتا ہے۔ `byModelTruncated` پھر سچ ہے، اور ایک ماڈل جس کے جوڑے کٹ کے دونوں طرف آتے ہیں جزوی کل دکھاتا ہے۔
- دو اخراجات کی اطلاع ہے۔ `costUsd` بل کی جانے والی لاگت ہے، جیسا کہ استعمال کے تجزیات اسے دکھاتے ہیں۔ فلیٹ ریٹ سبسکرپشن فراہم کرنے والے، جیسے Claude کوڈ پلان، وہاں $0 گنتے ہیں۔ `listPriceUsd` وہی استعمال ہے جس کی قیمت فہرست قیمت پر ہے، سبسکرپشنز شامل ہیں۔ ایک درخواست جس کے ماڈل میں قیمت کی قطار نہیں ہے اس کی ذخیرہ شدہ لاگت کا شمار ہوتا ہے: فراہم کنندہ کی طرف سے اطلاع دی گئی قیمت، یا درخواست کے ریکارڈ ہونے پر اس کا حساب لگایا جاتا ہے۔ صرف ایک درخواست جس میں کوئی 0 شمار نہیں ہوتا، بغیر مارکر کے، اس لیے کل جزوی ہو سکتا ہے۔
- جوابی معاہدہ `src/shared/schemas/selfUsage.ts` ( `docs/openapi.yaml` میں `SelfUsageSeries` ) ہے۔

### سیلف سروس پیج

`QUOTA_SELF_PANEL` آن کے ساتھ، `/quota/{provider}` ایک عوامی صفحہ ہے۔ کلیدی ہولڈر وہاں ایک API کلید ٹائپ کرتا ہے اور فراہم کنندہ کے لیے اس کلید کے پول کو دیکھتا ہے۔ ہر پول ہر ایک کے لیے پول کے استعمال اور کلید کا اپنا حصہ کے ساتھ، ہر پول ونڈو میں ایک کارڈ دکھاتا ہے۔ پول کے ہر اکاؤنٹ کے اپنے کارڈ ہوتے ہیں، اکاؤنٹ کے استعمال اور کلید کے حصے کے ساتھ۔ اکاؤنٹ کا استعمال صرف اس وقت ظاہر ہوتا ہے جب کلید اکاؤنٹ کا ڈیٹا دیکھ سکتی ہے۔ صفحہ ہر اکاؤنٹ کی فی ماڈل حدود اور کلید کے اپنے استعمال کی فہرست بھی دیتا ہے۔ ایک نوٹس ظاہر ہوتا ہے جب کوئی شیڈول ابھی کلید کو روکتا ہے۔ ایک کارڈ اس کے استعمال کے ساتھ کلید کے ہر فی ماڈل کیپ کی فہرست بناتا ہے، اور پہنچ جانے والوں کو نشان زد کرتا ہے۔ `{provider}` ایک فراہم کنندہ کی شناخت یا اس کا عرف (`/quota/claude`, `/quota/cc`) ہے۔ ایک نامعلوم فراہم کنندہ، اور جھنڈا بند ہونے کے دوران ہر `/quota/*` پاتھ کا جواب 404۔ اپنی مرضی کے مطابق OpenAI- یا Anthropic-compatible نوڈ پر موجود پولز کا کوئی صفحہ نہیں ہوتا ہے۔ API اب بھی ان کے لئے جواب دیتا ہے.

صفحہ کا کوئی سیشن نہیں ہے۔ کلید صرف `GET /api/v1/me/quota/{provider}`، `PATCH /api/v1/me/quota/{provider}` اور `GET /api/v1/me/usage` کے `Authorization` ہیڈر میں بھیجی جاتی ہے، کبھی بھی URL میں نہیں۔ ایک کلید جسے سرور قبول کرتا ہے اسے ٹیب کے `sessionStorage` میں رکھا جاتا ہے۔ "اس ڈیوائس پر یاد رکھیں" کے ساتھ اسے اس کی بجائے `localStorage` میں رکھا جاتا ہے، اور "Forget key" اسے دونوں سے ہٹا دیتا ہے۔ سرور کی جانب سے مسترد کردہ کلید کو اسٹوریج سے ہٹا دیا جاتا ہے۔

`consent` موڈ میں ایک پول قرض دینے والا کارڈ دکھاتا ہے۔ وہاں کلیدی ہولڈر قرض دینے کے لیے کلید کے بیکار حصہ کا 0 سے 100 تک پورا فیصد مقرر کرتا ہے۔ ہولڈر یہ بھی منتخب کرتا ہے کہ رضامندی کتنی دیر تک رہتی ہے: جب تک کہ بند نہ ہو، 1 گھنٹہ، 8 گھنٹے، 24 گھنٹے، 7 دن یا 30 دن۔ ایک مدت بچت کے لمحے سے شمار ہوتی ہے۔ جب ایک ڈیڈ لائن نافذ ہے، ہولڈر اس کی بجائے اسے رکھ سکتا ہے۔ اگر وہ آخری تاریخ محفوظ کرنے سے پہلے گزر جاتی ہے، تو کارڈ کچھ نہیں بھیجتا اور دوسرا انتخاب طلب کرتا ہے۔ 0% کے ساتھ کوئی آخری تاریخ نہیں بھیجی جاتی ہے۔ کارڈ اپنے ٹائم زون کے نام کے ساتھ ذخیرہ شدہ آخری تاریخ دکھاتا ہے۔ ایک رضامندی جس کی آخری تاریخ گزر چکی ہے اسے ختم کے طور پر دکھایا گیا ہے۔

`hard` کلید کے لیے کارڈ میں یہ بھی درج ہوتا ہے، فی پول ونڈو، اس وقت کون سی دوسری چابیاں کلید کو دیتی ہیں۔ ہر قطار ایک ساتھ دیگر تمام کلیدوں کے لیے ایک شکل ہے۔ دو کلیدوں کے تالاب میں یہ دوسری کلید کی اپنی شکل ہے۔ ایک اعداد و شمار جو منظر کی اطلاع نہیں دیتا ہے اسے دستیاب نہیں کے طور پر پڑھتا ہے، صفر کے طور پر نہیں۔ `soft` یا `burst` کلید کے لیے کارڈ کہتا ہے کہ کوئی اعداد و شمار لاگو نہیں ہوتے ہیں۔

`saturation` موڈ میں ایک پول جس کی کلید 0 سے اوپر فیصد ذخیرہ کرتی ہے صرف واپسی دکھاتا ہے۔ اس کا کہنا ہے کہ ذخیرہ شدہ فیصد کا وہاں کوئی اثر نہیں ہوتا ہے۔ اس کا واپس لینے کا بٹن 0 بھیجتا ہے بغیر کسی آخری تاریخ کے۔ ذخیرہ شدہ 0 کے ساتھ `saturation` موڈ میں ایک پول کوئی قرض دینے والا کارڈ نہیں دکھاتا ہے۔ محفوظ کرنے کے بعد، ایک کارڈ جس کی واپسی کی ضرورت نہیں ہے اس کے پیغام کے ساتھ اس وقت تک رہتا ہے جب تک کہ صفحہ کا منظر دوبارہ تبدیل نہ ہو جائے۔

کچھ بھی محفوظ نہیں ہوتا جب تک کہ ہولڈر محفوظ کریں یا واپس لے دبائیں۔ ہر پریس ایک `PATCH /api/v1/me/quota/{provider}` درخواست بھیجتا ہے، اور دوسرا پریس کچھ نہیں بھیجتا جب تک کہ پہلا زیر التواء ہو۔ جسم پول کے مبہم `ref` منظر، فیصد اور آخری تاریخ سے لے جاتا ہے۔ جواب دوبارہ تعمیر شدہ کوٹہ کا منظر ہے، اور صفحہ اسے بغیر پڑھے دکھاتا ہے۔ جب دو اوورلیپ کو محفوظ کرتا ہے، تو صفحہ آخری جواب کے بعد ایک بار کوٹہ پڑھتا ہے۔ صفحہ براؤزر اسٹوریج میں رضامندی نہیں رکھتا ہے۔

انکار شدہ تبدیلی کی وضاحت کارڈ پر HTTP اسٹیٹس سے منتخب کردہ متن کے ذریعے کی گئی ہے۔ ایرر باڈی نہیں پڑھی جاتی ہے۔ A 401 کہتا ہے کہ کلید قبول نہیں کی گئی اور کوٹہ کو دوبارہ لوڈ کرتا ہے۔ ایک 403 کہتا ہے کہ پول قرضے میں تبدیلیاں نہیں لے رہا ہے، اور 404 کہتا ہے کہ پول ختم ہو گیا ہے۔ دونوں ایک بٹن پیش کرتے ہیں جو کوٹہ کو دوبارہ لوڈ کرتا ہے۔ 400 یا دوسرا 4xx جواب ہولڈر سے فیصد اور آخری تاریخ چیک کرنے کو کہتا ہے۔ A 429 ہولڈر سے انتظار کرنے کو کہتا ہے، `Retry-After` کے سیکنڈز کے ساتھ جب وہ جواب دیتا ہے۔ ایک 5xx جواب، 408 یا نیٹ ورک کی ناکامی کہتی ہے کہ تبدیلی محفوظ نہیں ہوئی ہو گی، اور ٹائپ کردہ اقدار کو برقرار رکھتی ہے۔ معاہدے سے باہر کا جواب کوٹہ کو دوبارہ لوڈ کرتا ہے۔ ایک ناکام بچت کلید کو خود سے نہیں ہٹاتی ہے۔ جب اسے دوبارہ لوڈ کرنے سے انکار کر دیا جاتا ہے، تو صفحہ کلید کو ہٹا دیتا ہے جیسا کہ کسی انکار شدہ پڑھے پر ہے۔

ایک بار ایک کلید قبول ہو جانے کے بعد، صفحہ تین ٹیبز کے ساتھ "اپنے ٹولز کو سیٹ اپ کریں" کارڈ بھی دکھاتا ہے۔ "Claude کوڈ" `~/.claude/settings.json` کے لیے `env` بلاک دیتا ہے۔ "شیل" وہی متغیرات دیتا ہے جیسے `export` لائنز۔ "Claude ڈیسک ٹاپ" اپنی تیسری پارٹی کے انفرنس ونڈو کے لیے اقدار دیتا ہے۔ ماڈلز کوٹا شیئر ماڈلز ہیں جو کلید اس فراہم کنندہ کے لیے کال کر سکتی ہے۔ جب ایسی کوئی فہرست کلید کے ساتھ نہیں آتی ہے، تو اس کے بجائے بلاک گیٹ وے ماڈل کی دریافت کو آن کر دیتا ہے۔ گیٹ وے ایڈریس عوامی API اصل سرور کی رپورٹ ہے (`OMNIROUTE_PUBLIC_API_BASE_URL`، پھر `OMNIROUTE_PUBLIC_BASE_URL`)۔ جب کوئی بھی سیٹ نہیں ہوتا ہے، تو کارڈ ایک پلیس ہولڈر دکھاتا ہے اور ہولڈر سے کہتا ہے کہ وہ منتظم سے پوچھے۔ کلید کو پلیس ہولڈر کے طور پر دکھایا گیا ہے۔ "میری کلید کو شامل کریں" پوری کلید کو اسکرین پر موجود متن میں اور جس میں کاپی بٹن کاپی کرتا ہے۔ یہ اس وقت تک رہتا ہے جب تک کہ باکس صاف نہ ہو جائے، کلید بھول جائے یا اسے تبدیل کر دیا جائے، یا صفحہ چھوڑ دیا جائے۔ کارڈ کوئی درخواست نہیں بھیجتا ہے اور کوئی فائل ڈاؤن لوڈ نہیں کرتا ہے۔

API کے نشانات `stale` پڑھنا ممکنہ طور پر پرانا دکھایا گیا ہے۔ اسے پڑھنے سے `unavailable` کو اس کی وجہ کے ساتھ دکھایا گیا ہے، کبھی بھی صفر کے طور پر نہیں۔

فیصد کے منصوبوں پر صفحہ کلید کا اپنا حصہ کھینچتا ہے جب API اس کی اطلاع دیتا ہے۔ اس کا کہنا ہے کہ تعداد ایک تخمینہ ہے اور اس کے دو حصوں کو نام دیتا ہے۔ فی ماڈل کی حدیں صرف اکاؤنٹ دکھاتی ہیں۔

جب ونڈو میں `members` ہوتا ہے، تو اس کا کارڈ سلاٹ ترتیب میں فی ممبر ایک طبقہ کے ساتھ ایک بار بھی دکھاتا ہے۔ پوچھنے والی کلید کا سیگمنٹ لہجے کا رنگ استعمال کرتا ہے۔ دوسرے سیگمنٹس تھیم کے چارٹ کے رنگوں کے ذریعے چکر لگاتے ہیں۔ ٹیکسٹ لیجنڈ ہر طبقہ کو اس کی قدر کے ساتھ درج کرتا ہے، لہذا کچھ بھی رنگ پر منحصر نہیں ہوتا ہے۔ حصوں پر `You` یا `Member N` لیبل لگایا گیا ہے، جہاں N سلاٹ ہے۔

### صفحہ کے لیے وقف پورٹ

`QUOTA_PANEL_PORT` ایک دوسرے سامعین کو کھولتا ہے جو صرف سیلف سروس پیج کی خدمت کرتا ہے۔ یہ بند ہے جب تک کہ متغیر سیٹ نہ ہو۔ `QUOTA_PANEL_HOST` بائنڈ ایڈریس ہے اور `127.0.0.1` پر ڈیفالٹ ہے۔

سننے والا ان راستوں کو مرکزی بندرگاہ تک پہنچاتا ہے اور ہر دوسرے راستے کے لیے 404 کا جواب دیتا ہے:

| راستہ                                                                    | خدمت کرتا ہے۔                      |
| ------------------------------------------------------------------------ | ---------------------------------- |
| `/quota/{provider}`                                                      | صفحہ                               |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | کوٹہ صفحہ پڑھتا ہے۔                |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | استعمال کی سیریز جو صفحہ پڑھتا ہے۔ |
| `/_next/static/`                                                         | تعمیر کے اسکرپٹ، سٹائل اور فونٹس   |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | شبیہیں                             |

`GET` اور `HEAD` بغیر کسی جسم کے ریلے ہوتے ہیں۔ ایک باڈی کے ساتھ ایک درخواست بھی جاری کی جاتی ہے: کوٹہ ویو پاتھ کا ایک `PATCH` ، جسے صفحہ قرض دینے کے انتخاب کو بچانے کے لیے بھیجتا ہے۔ کوئی دوسرا طریقہ 404 کا جواب دیتا ہے، سوائے CONNECT درخواست کے، جس کا کنکشن بغیر کسی جواب کے بند ہے۔ کوئی دوسری درخواست جو باڈی کا اعلان کرتی ہے 404 کا جواب دیتی ہے اور اس کا کنکشن بند ہے۔ اپ گریڈ کی درخواستیں مسترد کر دی گئی ہیں اور ان کا کنکشن بند کر دیا گیا ہے۔ ڈاٹ سیگمنٹ یا فریگمنٹ مارکر والا راستہ انکار کر دیا گیا ہے، جیسا کہ API پورٹ پر ہے۔ اسی طرح ایک درخواست کا ہدف ہے جس میں پرنٹ ایبل ASCII سے باہر ایک کردار ہے۔ ہدف میں ایک خام کنٹرول کردار کا جواب 400 HTTP پارسر کے ذریعہ دیا جاتا ہے، اس پورٹ کی اپنی جانچ سے پہلے۔ ہیڈرز سے درخواست کریں کہ فریم ورک کے اپنے استعمال کے لیے محفوظ رکھے گئے ہیں: وہ نام جو `x-middleware-`، `x-invoke-`، `x-nextjs-`، `x-now-` یا `x-next-` سے شروع ہوتے ہیں، اور نام `x-matched-path` اور `next-resume`۔ درخواست ان کے بغیر پیش کی جاتی ہے۔ ڈیش بورڈ، لاگ ان پیج، مینجمنٹ API اور انفرنس راستوں تک اس پورٹ کے ذریعے نہیں پہنچا جا سکتا۔

`PATCH` `Content-Type: application/json` لے جانا چاہیے، بغیر کسی پیرامیٹر کے یا صرف `charset=utf-8` کے ساتھ۔ اس میں 1 سے 4096 تک ایک `Content-Length` ہونا چاہیے، سادہ ہندسوں کے طور پر لکھا جائے، اور کوئی `Transfer-Encoding` نہیں۔ ایک `PATCH` جو ان اصولوں میں سے کسی ایک کو توڑتا ہے وہ 404 کا جواب دیتا ہے۔ کچھ خراب طوالت، جیسے کہ دستخط شدہ یا دہرائی گئی، کا جواب HTTP پارسر کے ذریعے اس پورٹ کے اپنے چیک سے پہلے 400 دیا جاتا ہے۔ بندرگاہ مرکزی بندرگاہ سے رابطہ کرنے سے پہلے اعلان کردہ بائٹس کو پڑھتی ہے، اور ان کے لیے زیادہ سے زیادہ 5 سیکنڈ انتظار کرتی ہے۔ ایک جسم جو اس وقت تک مکمل نہیں ہوتا ہے 404 کا جواب دیتا ہے اور اس کا کنکشن بند ہوجاتا ہے۔ اس صورت میں مرکزی بندرگاہ تک کچھ نہیں پہنچتا، یا جب کلائنٹ پہلے چلا جاتا ہے۔ پورٹ بالکل اسی `Content-Length` کے ساتھ اعلان کردہ بائٹس کو ریلے کرتا ہے۔ ان کے بعد بائٹس کو کنکشن پر اگلی درخواست کے طور پر پڑھا جاتا ہے۔ سامنے والی TLS ریورس پراکسی کو `Content-Length` فارورڈ کرنا چاہیے اور درخواست کے باڈی کو دوبارہ نہیں بنانا چاہیے۔ مین پورٹ `Authorization` ہیڈر میں API کلید کو چیک کرتا ہے، جیسا کہ `GET` کے لیے ہے۔

404 جسم `{"error":"not_found","message":"Not found."}` ہے۔ ایک ناکام ریلے بغیر `detail` فیلڈ کے 502 (`api_bridge_unavailable`) یا 504 (`api_bridge_timeout`) کا جواب دیتا ہے۔

سننے والا `QUOTA_SELF_PANEL` نہیں پڑھتا، اور صفحہ آن نہیں کرتا۔ جھنڈا بند ہونے کے دوران، صفحہ اور اس کا API مین پورٹ پر 404 جواب دیتا ہے، اور سننے والا اس جواب کو ریلے کرتا ہے۔

ڈویلپمنٹ سرور (`next dev`) کے تحت صفحہ اس پورٹ کے ذریعے انٹرایکٹو نہیں ہوتا ہے۔ ڈویلپمنٹ ہاٹ ری لوڈ ساکٹ ایک اپ گریڈ کی درخواست ہے، اور پورٹ اس سے انکار کرتا ہے۔ ترقی کرتے وقت مین پورٹ کا استعمال کریں۔

پورٹ سادہ HTTP پیش کرتا ہے اور صفحہ API کیز بھیجتا ہے۔ ڈیفالٹ بائنڈ ایڈریس رکھیں اور اس کے سامنے TLS کے ساتھ ایک ریورس پراکسی رکھیں۔ لوپ بیک کے علاوہ ایک پابند پتہ اس نوٹس کو لاگ کرتا ہے:

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

ایک لوپ بیک پیئر جو فارورڈنگ ہیڈر نہیں بھیجتا ہے اسے مین پورٹ پر مقامی شمار کیا جاتا ہے۔ لہذا اسی میزبان پر ایک پراکسی کو `X-Forwarded-For` بھیجنا ضروری ہے۔ نجی ایڈریس پر ایک پراکسی صرف `OMNIROUTE_TRUST_PROXY=private` (یا `lan`) کے ساتھ اس ہیڈر کے لیے قابل اعتماد ہے۔ کسی بھی دوسرے ہم مرتبہ کی اطلاع اس کے کنکشن کے پتے کے ذریعے دی جاتی ہے، اور اس کے بھیجے گئے فارورڈنگ ہیڈرز کو چھوڑ دیا جاتا ہے۔

سننے والا ایک وقت میں زیادہ سے زیادہ 256 کنکشن رکھتا ہے۔ ایک کلائنٹ کے پاس درخواست ہیڈر بھیجنے کے لیے 10 سیکنڈ اور پوری درخواست بھیجنے کے لیے 30 سیکنڈ ہوتے ہیں۔ ایک غیر فعال رکھا ہوا کنکشن تقریباً 5 سیکنڈ کے بعد بند ہو جاتا ہے۔ 60 سیکنڈ تک کوئی سرگرمی نہ ہونے والا کنکشن بند ہے۔ یہ اقدار طے شدہ ہیں۔ سامنے والے ریورس پراکسی پر بھی کنکشن اور شرح کی حدیں سیٹ کریں۔ سامنے ایک ریورس پراکسی کو اپنے بیکار اپ اسٹریم کنکشن کو 5 سیکنڈ سے کم کے لیے رکھنا چاہیے، یا انہیں دوبارہ استعمال نہیں کرنا چاہیے۔ مرکزی بندرگاہ کا ریلے API پورٹ (`API_BRIDGE_*`) کے اپ اسٹریم ٹائم آؤٹ کا استعمال کرتا ہے۔

سننے والا بھی اس وقت شروع ہوتا ہے جب `API_PORT` مقرر نہ ہو۔ `QUOTA_PANEL_PORT` 1 سے 65535 تک ایک پورٹ ہونا چاہیے، صرف ہندسوں میں لکھا جائے۔ یہ ڈیش بورڈ پورٹ اور API پورٹ سے مختلف ہونا چاہیے۔ جبکہ لائیو WebSocket سرور آن ہے، یہ `LIVE_WS_PORT` (پہلے سے طے شدہ 20132) سے بھی مختلف ہونا چاہیے۔ کوئی دوسری قدر کچھ نہیں کھولتی اور ایک انتباہ لاگ کرتی ہے۔ انکار شدہ قدر کے بارے میں ایک انتباہ متغیر کا نام دیتا ہے اور قدر کو دہراتا نہیں ہے۔ ایک پورٹ جو پہلے سے استعمال میں ہے کچھ نہیں کھولتا اور اس انتباہ کو لاگ کرتا ہے:

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH` سیٹ کے ساتھ، سامع اس سابقے کے تحت اوپر والے ہر راستے کی توقع کرتا ہے۔ تعمیر کے وقت اور رن ٹائم میں ایک ہی `OMNIROUTE_BASE_PATH` استعمال کریں۔ اسے لیڈنگ سلیش کے ساتھ لکھیں اور بغیر کسی ٹریلنگ سلیش کے، مثال کے طور پر `/omniroute`۔ ایک اور شکل، بشمول `/` اور `/omniroute/`، ایک انتباہ کے ساتھ بندرگاہ کو چھوڑ دیتی ہے، حالانکہ عمارت ان شکلوں کو قبول کرتی ہے۔ اسی طرح ایک بنیادی راستہ ہے جس کا پہلا طبقہ ایپلیکیشن روٹ کا نام دیتا ہے: `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0`, یا `connect` کسی بھی صورت میں۔

حدود:

- `/quota/{provider}/` اس پورٹ پر ٹریلنگ سلیش کے ساتھ 404 کا جواب دیتا ہے۔
- سروس ورکر اور ویب ایپ مینی فیسٹ کو اس پورٹ پر پیش نہیں کیا جاتا ہے۔
- ڈیش بورڈ میں ایک حسب ضرورت فیویکن سیٹ اس پورٹ پر نہیں دکھایا گیا ہے۔
- جب ایپلیکیشن بنیادی راستے کے تحت چلتی ہے تو شبیہیں نہیں دکھائے جاتے ہیں۔
- بندرگاہ سادہ HTTP/1.1. بولتی ہے۔
- ایک پابندی جو ناکام ہوجاتی ہے اس وقت تک دوبارہ کوشش نہیں کی جاتی ہے جب تک کہ عمل دوبارہ شروع نہ ہوجائے۔
- سننے والے کے پاس فی کلائنٹ ایڈریس کا کوئی کنکشن یا شرح کی حد نہیں ہے۔
- کنٹینر سیٹ اپ اس سیکشن میں شامل نہیں ہیں۔

## مسائل کا حل

### Redis تشکیل شدہ ہے لیکن کنیکٹ نہیں ہو رہا

یقینی بنائیں کہ `ioredis` انسٹال ہے (`npm ls ioredis`) اور `QUOTA_STORE_REDIS_URL`
قابلِ رسائی ہے۔ کنکشن ناکام ہونے پر فیکٹری SQLite پر واپس چلی جاتی ہے (جس کا اندراج
`warn` پر ہوتا ہے)۔

### `peek` پرانا نتیجہ دیتا ہے / fail-open

اگر `peek` استثنا پھینکتا ہے تو `enforceQuotaShare` نتیجے کو "اجازت" (fail-open)
سمجھتا ہے۔ بنیادی وجہ معلوم کرنے کے لیے `quota:enforce` اور `quota:factory`
اندراجات کے لیے `pino` لاگز چیک کریں۔

### استعمال کے کاؤنٹر میں انحراف

اگر فراہم کنندہ کا حقیقی استعمال کاؤنٹرز سے مختلف ہو تو یہ متوقع ہے — 2-بکٹ
sliding window میں ونڈو کی حدود پر تقریباً 1% خرابی ہوتی ہے، اور `consume`
جواب کے بعد fire-and-forget انداز میں چلتا ہے۔ سیچوریشن سگنل (`saturationSignals.ts`)
30 سیکنڈ TTL کے ساتھ فراہم کنندہ کا حقیقی استعمال پڑھتا ہے اور اسی کے مطابق
`globalUsedPercent` کو ایڈجسٹ کرتا ہے۔

### پول برن ریٹ کے لیے "کوئی ڈیٹا نہیں" دکھاتا ہے

`computeBurnRate` کو کم از کم 2 تاریخی نمونے درکار ہیں۔ سابقہ `consume` کالز کے
بغیر نئے پولز `tokensPerSecond: 0` اور `timeToExhaustionMs: null` دکھائیں گے۔

## localStorage سے منتقلی

جب `/dashboard/costs/quota-share` پہلی بار لوڈ ہوتا ہے، تو ہُک `useLocalStoragePoolMigration`
درج ذیل کی جانچ کرتا ہے:

1. `localStorage.getItem("omniroute:quota-share:pools")` خالی نہ ہو۔
2. `GET /api/quota/pools` سے `[]` واپس آئے (DB خالی ہو)۔

اگر دونوں شرائط درست ہوں، تو یہ ہر پرانے پول کو بیچ کی صورت میں `POST /api/quota/pools` پر پوسٹ کرتا ہے،
پھر localStorage کلید حذف کر دیتا ہے۔ یہ منتقلی idempotent ہے: شرط 2
دوبارہ منتقلی کو روکتی ہے۔

## داخلی حکمتِ عملی کی درجہ بندی

`quota-share` ایک **صرف داخلی** روٹنگ حکمتِ عملی ہے (`src/shared/constants/routingStrategies.ts` میں
`INTERNAL_ROUTING_STRATEGY_VALUES`)۔ اسے خصوصی طور پر سسٹم کے بنائے ہوئے
`qtSd/` پول کومبوز استعمال کرتے ہیں، اور اسے جان بوجھ کر `ROUTING_STRATEGY_VALUES` سے خارج رکھا گیا ہے تاکہ یہ کبھی بھی
UI یا API میں صارف کے لیے قابلِ انتخاب اختیار کے طور پر ظاہر نہ ہو۔

## DB اسکیما کا خلاصہ

ہجرت `078`، `079` اور `085` کے ذریعے تین جدولیں شامل کی گئیں:

- `quota_pools` + `quota_allocations` — پول کی تعریفیں اور فی کلیدی مختص۔
- `quota_consumption` — رولنگ 2-بالٹی کاؤنٹر فی `(apiKeyId, dimensionKey)`۔
- `provider_plans` — مینوئل پرووائیڈر پلان اوور رائیڈز (طول و عرض JSON فی connectionId)۔

تمام جدولیں idempotent `CREATE TABLE IF NOT EXISTS` ہجرت کے ذریعے شامل کی گئیں۔

رضامندی والے قرضے میں تین کالم شامل ہوتے ہیں: `quota_allocations.lending_percent` (انٹیجر، ڈیفالٹ 0)، `quota_allocations.lending_until` (ایپوچ ملی سیکنڈز، یا `NULL` بغیر ڈیڈ لائن) اور `quota_pools.borrow_mode` (پہلے سے طے شدہ `saturation`)۔ اس کی منتقلی صرف ان کالموں کو جوڑتی ہے اور کوئی موجودہ قطار نہیں لکھتی ہے۔

فیصد انتساب کتاب میں `quota_percent_ledger` (ایک قطار فی پول، اکاؤنٹ اور پلان ونڈو) اور `quota_percent_ledger_tokens` (ایک ٹوکن کاؤنٹر فی پول، اکاؤنٹ اور API کلید) شامل کیا گیا ہے۔ `src/lib/db/quotaPercentLedger.ts` انہیں پڑھتا اور لکھتا ہے۔
