## زیرو-کنفگ آٹو-روٹنگ (`auto/` سابقہ)

> **نیا:** کومبو بنانے کی ضرورت نہیں۔ کسی بھی کلائنٹ میں براہِ راست `auto/` سابقہ استعمال کریں۔

### فوری مثالیں

| ماڈل ID        | ویریئنٹ | طرزِ عمل                                                         |
| -------------- | ------- | ---------------------------------------------------------------- |
| `auto`         | ڈیفالٹ  | تمام منسلک فراہم کنندگان، LKGP حکمتِ عملی، متوازن وزن            |
| `auto/coding`  | کوڈنگ   | معیار کو ترجیح دینے والے وزن، کوڈ بنانے کے لیے موزوں             |
| `auto/fast`    | تیز     | کم تاخیر پر مبنی وزنی انتخاب                                     |
| `auto/cheap`   | سستا    | لاگت کے لیے بہتر بنائی گئی روٹنگ (سب سے کم لاگت پہلے)            |
| `auto/offline` | آف لائن | سب سے زیادہ کوٹہ دستیابی والے فراہم کنندگان کو ترجیح دیتا ہے     |
| `auto/smart`   | اسمارٹ  | معیار کو ترجیح + بہتر ماڈل دریافت کے لیے زیادہ کھوج کی شرح (10%) |
| `auto/lkgp`    | lkgp    | واضح LKGP (ڈیفالٹ `auto` کے مساوی)                               |
| `auto/chaos`   | chaos   | متوازی fan-out، فی فراہم کنندہ ایک ماڈل (fault injection نہیں)   |

### زمرہ × درجہ تشکیل (`auto/<category>:<tier>`)

OpenRouter طرز کے لاحقے **روٹ کی نوعیت** (زمرہ) کو **اسے بہتر بنانے کے طریقے** (درجہ) سے الگ کرتے ہیں، تاکہ آپ انہیں آزادانہ طور پر یکجا کر سکیں (#4235 Phase B، `open-sse/services/autoCombo/suffixComposition.ts`):

- **زمرے** (صلاحیت کے لحاظ سے امیدواروں کے مجموعے کو فلٹر کریں): `coding` · `reasoning` · `vision` · `chat` · `multimodal`۔ `vision`/`multimodal` بصارت کی صلاحیت رکھنے والے ماڈلز برقرار رکھتے ہیں؛ `reasoning` استدلال/تفکر والے ماڈلز برقرار رکھتا ہے۔
- **درجے** (اسکورنگ کے وزن / مجموعے کا فلٹر منتخب کریں): `fast` (فوری ترسیل) · `cheap` (عرف `floor`، لاگت بچانے والا) · `reliable` (circuit-breaker کی صحت + تاخیر کا استحکام) · `free` / `pro` (`classifyTier` کے ذریعے ماڈل کے درجے کے مطابق مجموعے کو فلٹر کریں — مفت درجہ بمقابلہ پریمیم)۔

| مثال                   | نتیجہ                                                                 |
| ---------------------- | --------------------------------------------------------------------- |
| `auto/coding:fast`     | کوڈنگ کا مجموعہ، کم تاخیر والے وزن                                    |
| `auto/coding:cheap`    | کوڈنگ کا مجموعہ، لاگت کے لیے بہتر بنایا گیا (عرف `auto/coding:floor`) |
| `auto/reasoning:pro`   | صرف استدلال/تفکر والے ماڈلز، پریمیم درجہ                              |
| `auto/vision`          | بصارت کی صلاحیت رکھنے والے ماڈلز (کوئی درجہ نہیں → متوازن وزن)        |
| `auto/multimodal:free` | ملٹی موڈل صلاحیت رکھنے والے ماڈلز، صرف مفت درجہ                       |

کوئی بھی درست `auto/<category>[:<tier>]` حسبِ ضرورت resolve ہو جاتا ہے؛ ایک منتخب ذیلی مجموعہ `/v1/models` اور ڈیش بورڈ میں مشتہر کیا جاتا ہے (`open-sse/services/autoCombo/builtinCatalog.ts` میں `AUTO_SUFFIX_VARIANTS`)۔ فلٹرنگ **fail-open** ہے — اگر کوئی شرط کسی منسلک ماڈل سے مماثل نہ ہو تو مکمل مجموعہ استعمال کیا جاتا ہے، تاکہ روٹنگ کبھی ناکام نہ ہو۔ بنیادی اسکورر (`combo.ts`) میں کوئی تبدیلی نہیں کی گئی؛ زمرہ/درجہ فلٹر `buildAutoCandidates` میں لاگو ہوتا ہے۔

> **لائیو ماڈل انٹیلی جنس:** جب `ARENA_ELO_SYNC_ENABLED` فلیگ فعال ہو تو آٹو-روٹنگ کی موزونیت لائیو **Arena ELO** درجہ بندیوں + **models.dev** کے درجہ جاتی ڈیٹا سے متعین ہوتی ہے (بصورتِ دیگر جامد موزونیت میپ استعمال کیا جاتا ہے)۔

**استعمال کا طریقہ:**

```bash
# کوئی بھی IDE یا CLI ٹول جو OpenAI فارمیٹ کو سپورٹ کرتا ہو
Base URL: http://localhost:20128/v1
API Key:  <آپ کی endpoint key>

# اپنے کوڈ/config میں model کو یوں سیٹ کریں:
model: "auto"                 # متوازن ڈیفالٹ
model: "auto/coding"          # کوڈنگ کے کاموں کے لیے بہترین
model: "auto/fast"            # تیز ترین دستیاب
model: "auto/cheap"           # فی token سب سے سستا
```

**کیا ہوتا ہے:**

1. OmniRoute، `src/sse/handlers/chat.ts` میں `auto/` سابقے کا پتہ لگاتا ہے
2. ڈیٹابیس سے تمام **فعال فراہم کنندہ کنکشنز** حاصل کرتا ہے
3. درست اسناد (API key یا OAuth token) رکھنے والے کنکشنز کو فلٹر کرتا ہے
4. ہر کنکشن کے لیے ماڈل کا تعین کرتا ہے (`connection.defaultModel` یا فراہم کنندہ کا پہلا ماڈل)
5. میموری میں ایک **ورچوئل کومبو** بناتا ہے (DB میں محفوظ نہیں کیا جاتا)
6. منتخب ویریئنٹ کے weight profile + LKGP حکمتِ عملی کے ذریعے روٹ کرتا ہے

**اہم خصوصیات:**

- ✅ **ہمیشہ فعال:** کسی toggle، کومبو بنانے یا کنفگریشن کی ضرورت نہیں
- ✅ **متحرک:** موجودہ منسلک فراہم کنندگان کو خودکار طور پر ظاہر کرتا ہے
- ✅ **سیشن کی وابستگی:** LKGP یقینی بناتا ہے کہ آخری کامیاب فراہم کنندہ کو ترجیح دی جائے
- ✅ **متعدد اکاؤنٹس سے آگاہ:** ہر فراہم کنندہ کنکشن ایک علیحدہ امیدوار بن جاتا ہے
- ✅ **DB میں کوئی تحریر نہیں:** ورچوئل کومبو صرف درخواست کے دوران موجود رہتا ہے، persistence کا کوئی اضافی خرچ نہیں

### فی key امیدوار کنٹرول (#7819، سطح 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` کے بعد آنے والا لاحقہ، یا
بنیادی چینل کے لیے بعینہٖ `auto`) ایک **صرف پڑھنے کے لیے** endpoint ہے، جو
لائیو رسائی پذیری کی معلومات کے ساتھ `auto/*` چینل کے موجودہ امیدواروں کے مجموعے کی فہرست دیتا ہے اور
موجودہ resilience reads کو دوبارہ استعمال کرتا ہے (خام breaker `state` کبھی استعمال نہیں کرتا):

- فراہم کنندہ circuit breaker — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- کنکشن cooldown — resolve کی گئی `provider_connections` row پر `rateLimitedUntil` / `testStatus`
- ماڈل lockout — `isModelLocked(provider, connectionId, model)`

ہر امیدوار میں اس API key کا `excluded` فلیگ بھی شامل ہوتا ہے۔ استثنا
فی API key محفوظ کیے جاتے ہیں (`auto_candidate_overrides` ٹیبل، migration `128`) — OmniRoute
single-tenant ہے اور اس میں کوئی `users` ٹیبل نہیں، لہٰذا `apiKeyId` فی کالر
حقیقی شناخت کا قریب ترین متبادل ہے — اور انہیں
`open-sse/services/autoCombo/virtualFactory.ts` میں امیدواروں کے مجموعے کے مرکزی کنٹرول مقام پر خالص، unit-tested
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) کے ذریعے نافذ کیا جاتا ہے۔
فلٹر **fail-open** ہے: غیر متعین apiKeyId/channel یا DB lookup کی ناکامی، دونوں صورتوں میں
مجموعہ بغیر فلٹر کیے رہتا ہے، لہٰذا وہ آپریٹر جس کے لیے کوئی override کنفگر نہ ہو، اس فیچر سے پہلے جیسی
byte-identical روٹنگ دیکھتا ہے۔

**آئندہ فالو اَپ مسئلے کے لیے مؤخر:** فی امیدوار وزن + واضح ترتیب (لیول 3
— موجودہ وزن یافتہ/ترجیحی حکمتِ عملی کے راستوں میں شامل ہوتا ہے) اور ہر `auto/*`
چینل کے لیے ایک مخصوص `combo.ts` حکمتِ عملی کو پن کرنا (لیول 4)۔ اس کھلے سوال کے
لیے #7819 کا منصوبہ دیکھیں کہ آیا واحد کرایہ دار ماڈل کے پیشِ نظر اوور رائیڈز کو فی API کلید
تک محدود رہنا چاہیے یا عالمی بنا دینا چاہیے۔

**پسِ پردہ:**

```txt
درخواست: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts سابقے کا پتہ لگاتا ہے
   ↓
createVirtualAutoCombo('coding') → فعال کنکشنز سے candidatePool
   ↓
handleComboChat (وہی انجن جو مستقل محفوظ شدہ combos کے لیے استعمال ہوتا ہے)
   ↓
خودکار اسکورنگ ہر درخواست کے لیے بہترین فراہم کنندہ/ماڈل منتخب کرتی ہے
```

**نفاذ کی فائلیں:**

| فائل                                                      | مقصد                                           |
| --------------------------------------------------------- | ---------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | سابقہ پارسر (`parseAutoPrefix`)                |
| `open-sse/services/autoCombo/virtualFactory.ts`           | ورچوئل `AutoComboConfig` آبجیکٹس بناتی ہے      |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | فراہم کنندہ رجسٹری کو موک کرنے کے لیے ٹیسٹ ہُک |
| `src/sse/handlers/chat.ts`                                | انضمام: خودکار سابقے کا شارٹ سرکٹ              |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` سسٹم اندراج            |

## محفوظ کردہ آٹو کومبوز کے لیے اکاؤنٹ کی ترجیحات

ذہین آٹو ایڈیٹر ایک اختیاری پیش کرتا ہے۔** اکاؤنٹ کی ترجیحات** سیکشن ہر کنکشن کو ترجیحی، نارمل (پہلے سے طے شدہ)، ریزرو، یا خارج کیا جا سکتا ہے۔ متعدد کنکشن ایک درجے کا اشتراک کر سکتے ہیں۔ آٹو پہلے اہل درجے کے اندر منتخب کرتا ہے، وہاں اپنے scoring/router رویے کو برقرار رکھتا ہے۔ ناکام کوششیں باقی کنکریٹ اکاؤنٹس تک پہنچ جاتی ہیں، ریزرو سے پہلے معمول سے پہلے ترجیح دی جاتی ہے۔ خارج کیے گئے کنکشن اس کومبو کے ذریعہ کبھی استعمال نہیں ہوتے ہیں۔

ترتیب کو `config.accountPreferences` کے طور پر محفوظ کیا جاتا ہے، کنکشن ID کے ذریعے کلید:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

ایک چھوڑا ہوا یا خالی نقشہ موجودہ روٹنگ کو برقرار رکھتا ہے۔ ترجیحات غیر فعال کنکشنز کو فعال نہیں کرتی ہیں، API- کلید تک رسائی نہیں دیتی ہیں، کوٹہ بلاک شدہ امیدواروں کو بحال نہیں کرتی ہیں، یا بجٹ چیک کو نظرانداز نہیں کرتی ہیں۔ ہر کوشش اس کے کنکریٹ کنکشن تک محدود ہے، لہذا اکاؤنٹ فال بیک کامبو روٹر کے پیچھے ٹائر نہیں چھلانگ لگا سکتا ہے۔ موجودہ سیشن وابستگی ایک اہل اکاؤنٹ کو برقرار رکھ سکتی ہے۔ مقامی موڑ کے پابند اکاؤنٹ کو چھوڑ کر اکاؤنٹس کو خاموشی سے تبدیل کرنے کے بجائے رک جاتا ہے۔

کنفیگر شدہ ترجیحات اکاؤنٹ سے آگاہ آٹو پاتھ کا استعمال کرتی ہیں: ان باؤنڈ سیاق و سباق، سمارٹ پائپ لائن، افراتفری اور شیڈو شارٹ کٹس نہیں بھیجے جاتے ہیں۔ ان درخواستوں کے لیے قیاس آرائی پر مبنی ہیجنگ غیر فعال ہے لہذا ریزرو اکاؤنٹس ترجیحی اکاؤنٹس کی دوڑ نہیں لگا سکتے۔ دیگر کومبو حکمت عملی اس ترتیب کی ترجمانی نہیں کرتی ہیں۔ آٹو سے دور کسی کومبو کو تبدیل کرنا بعد میں واپس سوئچ کرنے کے لیے محفوظ کردہ ترجیحات کو برقرار رکھتا ہے۔

## ایسے کومبو نام جو کسی حقیقی ماڈل آئی ڈی سے مماثل ہوں

ایسا کومبو جس کا `name` کسی سادہ ماڈل آئی ڈی کے عین مطابق ہو (مثلاً `gpt-5.5` نامی کومبو)، ایک **دانستہ اور معاونت یافتہ پیٹرن** ہے، بگ نہیں: یہ فی ماڈل آئی ڈی پرووائیڈر فال بیک کا طریقۂ کار ہے، جسے [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) میں دستاویزی شکل دی گئی ہے۔ چونکہ کومبو ریزولیوشن کو سادہ ماڈل آئی ڈی ریزولیوشن سے پہلے چیک کیا جاتا ہے (`src/sse/services/model.ts` میں `getComboForModel()`)، اس لیے سادہ آئی ڈی `gpt-5.5` کی درخواست براہِ راست کسی ایک پرووائیڈر کے پاس جانے کے بجائے کومبو کے اہداف (مثلاً `acme-responses/gpt-5.5`، `backup-responses/gpt-5.5`) کے ذریعے روٹ کی جاتی ہے — یہ [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) کے لیے بنائی گئی کومبو-قبل-از-ری رائٹ ترجیح کو دوبارہ استعمال کرتا ہے، اور `tests/unit/responses-combo-resolution-3227.test.ts` اور `tests/unit/combo-name-codex-responses-rewrite.test.ts` کے ذریعے اس کی ریگریشن ٹیسٹنگ کی جاتی ہے۔

کسی ایسے کومبو کو بنانا یا اس کا نام بدلنا جو کسی حقیقی ماڈل آئی ڈی کو شیڈو کرے، **کبھی مسترد نہیں کیا جاتا** — ایسا کرنے سے یہ دستاویزی ورک فلو ٹوٹ جائے گا۔ اس کے بجائے (#8530)، جب (نیا) نام کسی حقیقی ماڈل آئی ڈی سے متصادم ہو تو `POST /api/combos` اور `PUT /api/combos/[id]` ریسپانس کے ساتھ ایک غیر مسدود کرنے والی `warning` فیلڈ منسلک کرتے ہیں:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

بوٹ کے وقت، `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ایک سطر پر مشتمل `[STARTUP]` وارننگ بھی لاگ کرتا ہے، جس میں ایسے تمام موجودہ کومبوز درج ہوتے ہیں جو کسی ماڈل آئی ڈی کو شیڈو کرتے ہیں، تاکہ جن آپریٹرز کو دانستہ طور پر، بمطابق #6940، ایسا کرنے کے بجائے حادثاتی طور پر اس صورتِ حال کا سامنا ہو، انہیں ایک اشارہ مل سکے۔ ڈیٹیکشن ہیلپر `src/lib/combos/modelNameCollision.ts` میں موجود ہے۔

## کسی کلائنٹ سے کسٹم کومبو کو کال کرنا

محفوظ شدہ کومبوز (Settings → Combos) صرف اسی وقت استعمال ہوتے ہیں جب کلائنٹ `model` فیلڈ میں کومبو کا **بالکل درست نام** بھیجے — کومبو نام کی کوئی مبہم یا جزوی میچنگ نہیں ہوتی، اور نہ ہی `auto/` پریفکس شامل ہوتا ہے۔ ریزولیوشن کی ترتیب (`src/sse/services/model.ts` میں `getComboForModel()`):

1. کومبو نام سے بالکل درست میچ (`model: "my-combo"`)،
2. `combo/<name>` پریفکس (`model: "combo/my-combo"`)،
3. ماڈل→کومبو گلوب میپنگز (`/api/model-combo-mappings`)۔

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

دو عام غلط فہمیاں:

- **`auto` آپ کے کومبوز استعمال نہیں کرتا۔** `auto`/`auto/*` اپنا زیرو-کنفیگ امیدوار پول بناتا ہے اور محفوظ شدہ کومبوز سے صرف اس صورت میں رجوع کرتا ہے جب کسی کومبو کا نام حرف بہ حرف `auto` ہو (اس کی سفارش نہیں کی جاتی)۔ کسی کومبو کے ذریعے روٹ کرنے کے لیے اس کا بالکل درست نام بھیجیں — `auto` نہیں۔
- **`openrouter/auto` ایک حقیقی، بامعاوضہ OpenRouter پراڈکٹ** ("Auto Best Available") ہے، OmniRoute کا عرف نہیں۔ یہ OpenRouter رجسٹری (`open-sse/config/providers/registry/openrouter/index.ts`) کا واحد جامد ماڈل اندراج ہے اور اس کی بلنگ الگ سے ہوتی ہے۔ اسے `auto` پولز سے خارج کرنے کے لیے Settings → Routing → Hide paid models استعمال کریں۔

اس دستاویز میں بیان کردہ اصل الجھن کے لیے [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) اور [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) دیکھیں۔

## یہ کیسے کام کرتا ہے (محفوظ شدہ Auto-Combos)

Auto-Combo Engine ہر درخواست کے لیے **16 عوامل پر مشتمل اسکورنگ فنکشن** (جس کی تعریف `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` میں ہے) استعمال کرتے ہوئے بہترین provider/model کو متحرک طور پر منتخب کرتا ہے۔ پہلے سے طے شدہ weights کا مجموعہ `1.0` ہے؛ حسبِ ضرورت weights کو `normalizeScoringWeights()` کے ذریعے دوبارہ معمول پر لایا جاتا ہے۔ سولہ میں سے دو — `cacheAffinity` اور `resetWindowAffinity` — کا پہلے سے طے شدہ weight `0` ہے؛ `reliability` کا `DEFAULT_WEIGHTS` میں `0`، عمومی packs میں `0.03`، اور `reliability-first` میں `0.04` ہے؛ جبکہ `quality` کا packs میں `0.02` (`quality-first` میں `0.03`) ہے: یہ سب ہر candidate کے لیے پھر بھی calculate کیے جاتے ہیں، اور `cacheAffinity` اسکور سے باہر prompt-cache deduplication کو کنٹرول کرتا ہے، اس لیے صفر والے default عوامل بطورِ default ووٹ نہیں دیتے، جبکہ packs ایسا کرتے ہیں۔

  - **quality-first** → taskFit 0.3524 + stability 0.1429 + quality 0.03، جو تمام پیکس میں سب سے زیادہ ہے (کام کے لیے بہترین، مستقل ماڈل)

### فی درخواست کنٹرولز (ہیڈرز) — #6023 / #6024 / #6025 / #3470

کسی `auto` کومبو کو محفوظ کردہ کنفگ میں تبدیلی کیے بغیر، تین ہیڈرز کے ذریعے **فی درخواست** کنٹرول کیا جا سکتا ہے۔ یہ صرف `auto` حکمتِ عملی اور صرف اس درخواست پر لاگو ہوتے ہیں جس میں یہ موجود ہوں؛ ہیڈر موجود نہ ہونے کی صورت میں کومبو کی محفوظ شدہ `modePack`/`budgetCap`/`budgetFallback` قدریں استعمال ہوتی ہیں۔

| ہیڈر                          | قابلِ قبول اقدار                                                                                                                                                                     | اثر                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

`config.budgetFallback` ان پٹس کو فراہم کی جاتی ہیں۔ کسی کومبو کی محفوظ شدہ `config.budgetFallback` ("strict" |
"cheapest") مستقل پالیسی متعین کرتی ہے؛ ہیڈر ایک واحد درخواست کے لیے اسے اوور رائیڈ کرتا ہے۔

### `weighted` کے مفاہیم

`weighted` **ہر درخواست کے لیے متناسب بے ترتیب انتخاب** ہے
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)، نہ کہ مساوی تقسیم کرنے والا طریقہ:

- ہر درخواست احتمال `weight / totalWeight` کے ساتھ **ایک** مرحلہ منتخب کرتی ہے؛ باقی مراحل اس درخواست کے لیے fallback chain کے طور پر وزن کی نزولی ترتیب میں رہتے ہیں۔
- جس مرحلے کا وزن `0` ہو (یا موجود نہ ہو)، اسے اس وقت **کبھی منتخب نہیں کیا جاتا** جب کسی دوسرے مرحلے کا وزن > 0 ہو — یہ صرف منتخب مرحلے کی ناکامی کے بعد fallback کے طور پر کام کر سکتا ہے۔ صرف اس صورت میں جب **تمام** وزن 0 ہوں، انتخاب uniform ہو جاتا ہے۔
- جن مراحل کے تمام targets دستیاب نہ ہوں — provider circuit breaker `OPEN`، connection cooldown، model lockout — انہیں انتخاب سے پہلے ہٹا دیا جاتا ہے
  (`open-sse/services/combo/targetResolution.ts`)، اس لیے ایک صحت مند مرحلہ عارضی طور پر ہر درخواست جیت سکتا ہے۔
- `stickyWeightedLimit` (combo config، default `1` = off) منتخب مرحلے کو دوبارہ انتخاب کرنے سے پہلے اتنی مسلسل کامیابیوں تک برقرار رکھتا ہے۔

سخت rotation کے لیے `round-robin` استعمال کریں؛ `weighted` میں مساوی weights شماریاتی — نہ کہ سخت — توازن فراہم کرتے ہیں۔

### Agentic pipeline mode

کم از کم دو models والا `pipeline` combo، `config.agenticOrchestration.enabled` کے ذریعے planner/executor routing اختیار کر سکتا ہے۔ پہلا target planning اور حتمی جوابات کا ذمہ دار ہوتا ہے؛ دوسرا target client-native tool calls جاری کرتا ہے۔ OmniRoute درخواست کے protocol سے tool-result continuations کا پتا لگاتا ہے، planner سے پوچھتا ہے کہ آیا ایک اور tool round درکار ہے، اور executor یا planner میں سے کسی ایک کو client-facing حتمی مرحلہ متحرک طور پر بناتا ہے۔

اختیاری `config.agenticOrchestration.contextCompaction` ہر planner یا executor dispatch سے پہلے الگ payload budget لاگو کرتا ہے۔ اسے واضح طور پر فعال کریں:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

یہ operator کے منتخب کردہ serialized JSON character budgets ہیں، token context windows یا upstream کی ضمانت شدہ limits نہیں۔ exact model IDs، default کو override کرتے ہیں۔ threshold سے اوپر پہنچنے پر compaction یکساں tool definitions ہٹا دیتا ہے، بڑے tool evidence کو digest کے ساتھ مختصر کرتا ہے، اور پرانے مکمل history groups کو target ratio کی جانب ہٹا دیتا ہے۔ یہ system/developer instructions، تازہ ترین user request، آخری tool round بشمول parallel calls/results، اور Gemini کی ابتدائی routing instruction محفوظ رکھتا ہے۔ top-level instructions اور tool settings برقرار رہتے ہیں۔ omission marker ہٹائی گئی history کا اندراج کرتا ہے؛ یہ semantic summary نہیں بلکہ deterministic trimming ہے۔ اگر pinned context اب بھی budget سے تجاوز کرے تو model سے رابطہ کرنے سے پہلے درخواست 413 واپس کرتی ہے۔ Compaction غیر فعال ہونے یا threshold سے کم ہونے کی صورت میں درخواست میں کوئی تبدیلی نہیں کی جاتی۔

Tool-result continuations پر، OmniRoute اس وقت execution بھی روک دیتا ہے جب مسلسل دو مکمل rounds میں وہی tool calls غیر تبدیل شدہ results کے ساتھ دہرائے جائیں، یا مسلسل دو rounds میں ہر واضح طور پر نشان زد result ناکام ہو۔ تبدیل شدہ results بار بار calls کی اجازت دیتے ہیں (مثلاً polling)۔ یہ guard نئی user request پر reset ہو جاتا ہے، parallel calls کو ایک round میں group کرتا ہے، اور Anthropic، Chat Completions، Responses اور Gemini histories کو سپورٹ کرتا ہے۔ planner کو وجہ موصول ہوتی ہے اور وہ حتمی جواب کا ذمہ دار ہوتا ہے، چاہے وہ ایک اور tool round کی درخواست کرے۔

دوسرے target کے بعد آنے والے اضافی models executor backups کی ترتیب میں ہوتے ہیں۔ ناکام HTTP response یا transport exception اگلے executor کی طرف بڑھتا ہے، جبکہ وہی planner decision اور native tools برقرار رہتے ہیں، مگر اس executor کا اپنا step prompt اور resolved connection استعمال ہوتا ہے۔ پہلی کامیاب response کو بغیر تبدیلی کے واپس کیا جاتا ہے، بشمول SSE streaming؛ کامیاب stream شروع ہونے کے بعد کی ناکامیوں کو یہاں دوبارہ آزمایا نہیں جا سکتا۔ اگر تمام executors ناکام ہو جائیں تو آخری failure واپس کی جاتی ہے۔ Client aborts dispatch روک دیتے ہیں۔

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Executor ایک ہی response میں متعدد آزاد calls جاری کر سکتا ہے۔ Dependent calls کو بعد کے client tool-result turns میں سنبھالا جاتا ہے، جبکہ planner ہر result کا جائزہ لیتا ہے۔ `maxToolRounds` کا default `8` ہے اور یہ `1`–`32` قبول کرتا ہے؛ حد تک پہنچنے کے بعد planner کو دستیاب بہترین حتمی جواب تیار کرنا ہوتا ہے۔ اندرونی planner decisions کو buffer کیا جاتا ہے، جبکہ منتخب client-facing response اصل streaming preference برقرار رکھتی ہے۔

### `round-robin` sticky batch and account expansion

Round-robin کو batch کی صورت میں چلایا جاتا ہے، ہر request کے لیے الگ step نہیں:

- `stickyRoundRobinLimit` (combo config، پھر `comboStickyRoundRobinLimit`، پھر `settings.stickyRoundRobinLimit`، default **3**) rotate کرنے سے پہلے اتنی مسلسل کامیابیوں تک وہی target برقرار رکھتا ہے۔ ایک request کے بعد rotation کے لیے combo override کو `1` پر سیٹ کریں۔ Combo editor مؤثر value اور اس کے ماخذ کی layer دکھاتا ہے۔
- `connectionAwareExpansion` (combo config، پھر settings، default **false**) rotation سے پہلے ہر provider-level step کو فی-account targets میں پھیلاتا ہے۔ Group-B strategies (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline, jev) اس option کے فعال ہونے تک provider-level view برقرار رکھتی ہیں۔ Combo editor inherit / on / off فراہم کرتا ہے؛ inherit عالمی default (off) استعمال کرتا ہے۔
- Prompt-cache locality routing (`promptCacheAffinityEnabled`, default **true**) pinned connections کو اس طرح دوبارہ ترتیب دیتی ہے کہ matching cache keys ایک ہی account پر رہیں۔ یہ pinned per-account steps کے درمیان round-robin اور weighted rotation پر ترجیح رکھتی ہے۔ اگر آپ کو strict rotation درکار ہو تو اسے Settings → Combo defaults کے تحت بند کریں۔ اس کا per-combo override موجود نہیں ہے۔

ایک model پر multi-account rotation کے لیے تین pinned `connectionId`s کے بجائے **ایک dynamic-account step** (خالی `connectionId`، پورا pool) اور sticky limit `1` کو ترجیح دیں۔ Pinned steps اور affinity ایک ہی account پر مرکوز ہو جاتے ہیں، حتیٰ کہ RR counter آگے بڑھتا رہے۔

## فیوژن حکمتِ عملی

`fusion` وہ واحد حکمتِ عملی ہے جو کسی ایک ہدف کو منتخب **نہیں** کرتی۔ یہ پرامپٹ کو
**ہر پینل ماڈل کو متوازی طور پر** بھیجتی ہے، پھر ایک قابلِ تشکیل **جج ماڈل** پینل کے
تمام جوابات سے ایک حتمی جواب مرتب کرتا ہے۔ اسے اپ اسٹریم `decolua/9router`
(OpenRouter کے Fusion ڈیزائن) سے پورٹ کیا گیا ہے؛ نفاذ `open-sse/services/fusion.ts` میں ہے۔

یہ کیسے کام کرتی ہے:

0. **ٹول والی درخواست کا بائی پاس** — ایسی درخواست جس میں ایک غیر خالی `tools` ارے ہو اور
   `tool_choice` کو واضح طور پر `"none"` مقرر نہ کیا گیا ہو، پینل کو مکمل طور پر چھوڑ دیتی ہے:
   یہ `tools`/`tool_choice` کو بغیر تبدیلی کے براہِ راست ایک ماڈل (تشکیل کردہ جج، یا `panel[0]`)
   کی طرف بھیجی جاتی ہے۔ پینل اراکین کو ٹولز تک رسائی حاصل نہیں ہوتی اور جج کی
   ترکیبی ہدایت ٹول کال پیدا کرنے کی حوصلہ شکنی کرتی ہے، اس لیے ایجنٹ پر مبنی/ٹول کال کرنے والے کلائنٹس
   کو ترکیب شدہ نثر کے بجائے حقیقی ٹول کال کا فیصلہ ملتا ہے (#6771)۔
1. **فین آؤٹ** (صرف ٹول کے بغیر درخواستوں کے لیے) — پرامپٹ کو ایک ہی وقت میں ہر پینل
   ماڈل کو بھیجا جاتا ہے، ٹولز ہٹا کر نان اسٹریمنگ کو لازمی بنایا جاتا ہے (جج کو ترکیب کے لیے
   مکمل نثر درکار ہوتی ہے)۔
2. **کورم-گریس کلیکشن** — جیسے ہی `minPanel` جوابات موصول ہوتے ہیں، پیچھے رہ جانے والوں کے لیے
   ایک مختصر گریس ٹائمر شروع ہو جاتا ہے، پھر جو کچھ جمع ہو چکا ہو اس کے ساتھ فیوژن آگے بڑھتا ہے۔
   یہ وال ٹائم پر سب سے سست ماڈل کے جرمانے کو محدود کرتا ہے، جبکہ ایک سخت ٹائم آؤٹ حتمی حد مقرر کرتا ہے۔
3. **جج کی ترکیب** — پینل کے جوابات کو گمنام بنایا جاتا ہے (`Source 1`، `Source 2`، … — تاکہ
   جج ماڈل کے برانڈ کے بجائے مواد کی اہمیت پر غور کرے) اور جج کو دے دیا جاتا ہے، جو
   اتفاقِ رائے / تضادات / جزوی احاطے / منفرد بصیرتوں / نظر انداز پہلوؤں کا تجزیہ کرتا ہے، پھر
   **ایک** مستند جواب لکھتا ہے۔ جج کال کلائنٹ کا اصل
   `stream` فلیگ + ٹولز برقرار رکھتی ہے، اس لیے اسٹریمنگ اور ڈاؤن اسٹریم ٹول کا استعمال بدستور کام کرتے ہیں۔
4. **بتدریج تنزل** — پینل کے 0 جوابات → `503`؛ صرف 1 جواب باقی بچے → وہ جواب
   براہِ راست واپس کر دیا جاتا ہے (ترکیب کرنے کے لیے کچھ نہیں)؛ ایک ماڈل والا پینل براہِ راست جواب دیتا ہے۔

پینل کا کوئی رکن `combo-ref` مرحلہ بھی ہو سکتا ہے (`{kind: "combo-ref", comboName: "..."}`) جو
کسی دوسرے کومبو کا حوالہ دیتا ہے — اسے **ایک بلیک باکس پینل آواز** کے طور پر حل کیا جاتا ہے (حوالہ دیے گئے
کومبو میں مکمل تکراری ڈسپیچ، نہ کہ اس کومبو کے اپنے اہداف کا فین آؤٹ)، اور اس میں وہی گہرائی/چکر کا تحفظ
استعمال ہوتا ہے جو پہلے سے ہر دوسری combo-ref استعمال کرنے والی حکمتِ عملی میں موجود ہے (#6764)۔

### تشکیل

کومبو کے `config` بلاب میں تشکیل کیا جاتا ہے (کسی اسکیما مائیگریشن کی ضرورت نہیں — یہ موجودہ
`combos` ٹیبل کو دوبارہ استعمال کرتا ہے):

| فیلڈ                                     | قسم      | ڈیفالٹ         | مقصد                                                                         |
| :--------------------------------------- | :------- | :------------- | :--------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | پہلا پینل ماڈل | حتمی جواب کی ترکیب کرنے والا ماڈل                                            |
| `config.fusionTuning.minPanel`           | `number` | `2`            | گریس ٹائمر شروع ہونے سے پہلے درکار کامیاب جوابات (`[2, panelSize]` تک محدود) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`         | کورم پورا ہونے کے بعد پیچھے رہ جانے والوں کا کتنی دیر انتظار کیا جائے        |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`        | حتمی مطلق حد، تاکہ ایک معلق ماڈل درخواست کو روک نہ سکے                       |

ڈیفالٹس `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) میں موجود ہیں۔

### مثال

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \

    "strategy": "fusion",
    "targets": [

    ],

      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

پھر اسے کسی بھی کومبو کی طرح کال کریں: `{"model":"fusion-panel","messages":[...]}`۔

## ورچوئل آٹو-کومبو فیکٹری

Auto Combo انجن کو پہلے سے متعین combos کی ضرورت نہیں ہوتی۔ اس کے بجائے، `open-sse/services/autoCombo/virtualFactory.ts` فوری طور پر امیدوار بناتا ہے:

1. `getProviderConnections({ isActive: true })` حاصل کرتا ہے (تمام فعال connections)
2. ان connections تک محدود کرتا ہے جن کے credentials درست ہوں (API key یا `hasUsableOAuthToken()` کے ذریعے غیر زائد المیعاد OAuth token)
3. ماڈل کی دستیابی + قیمتوں کے لیے `getProviderRegistry()` سے تقابل کرتا ہے
4. ہر tuple `(provider, model, connection)` کے لیے ایک `VirtualAutoComboCandidate` بناتا ہے
5. dispatch ہدف کے طور پر `connection.defaultModel` (یا registry کا پہلا ماڈل) منتخب کرتا ہے
6. 16 عوامل والے `scorePool()` اور variant کے weight pack کے ذریعے ہر امیدوار کو اسکور کرتا ہے
7. `handleComboChat()` کے لیے نتیجے میں بننے والا in-memory `AutoComboConfig` واپس کرتا ہے — اسے کبھی DB میں محفوظ نہیں کیا جاتا

اس کا مطلب ہے کہ **`auto/*` فعال رکھنے والا نیا provider شامل کرنے سے امیدواروں کا pool خودکار طور پر وسیع ہو جاتا ہے** — combo میں دستی ترمیم کی ضرورت نہیں ہوتی۔ ورچوئل combo ہر درخواست پر دوبارہ بنایا جاتا ہے، اس لیے نئے شامل کیے گئے یا دوبارہ صحت مند ہونے والے connections فوراً شامل کر لیے جاتے ہیں۔

## خودکار بحالی

- **عارضی اخراج**: اسکور < 0.2 → 5 منٹ کے لیے خارج (تدریجی backoff، زیادہ سے زیادہ 30 منٹ)
- **Circuit breaker سے آگاہی**: OPEN → خودکار طور پر خارج؛ HALF_OPEN → آزمائشی درخواستیں
- **حادثاتی صورتِ حال کا موڈ**: >50% OPEN → exploration غیر فعال، استحکام زیادہ سے زیادہ
- **Cooldown بحالی**: اخراج کے بعد پہلی درخواست کم timeout کے ساتھ ایک "probe" ہوتی ہے

## Bandit Exploration

5% درخواستیں (قابلِ ترتیب) exploration کے لیے بے ترتیب providers کو بھیجی جاتی ہیں۔ حادثاتی صورتِ حال کے موڈ میں یہ غیر فعال ہوتا ہے۔

## API

کوئی **مخصوص `POST /api/combos/auto` اینڈ پوائنٹ موجود نہیں ہے** — Auto-Combo کو دو طریقوں سے استعمال کیا جاتا ہے:

1. **بغیر کنفیگریشن (تجویز کردہ):** کسی بھی چیٹ کمپلیشن درخواست کو `model: "auto"` یا `model: "auto/<variant>"` کے ساتھ بھیجیں۔ ورچوئل فیکٹری ہر درخواست کے لیے کومبو بناتی ہے — کسی مستقل اسٹوریج یا API کالز کی ضرورت نہیں۔

2. **`strategy: "auto"` کے ساتھ محفوظ شدہ کومبو:** `POST /api/combos` کے ذریعے ایک عام کومبو بنائیں اور `strategy: "auto"` کے ساتھ `config.auto.weights` / `config.auto.candidatePool` سیٹ کریں۔ یہی اسکورنگ انجن استعمال ہوتا ہے؛ کومبو `combos` میں محفوظ ہو جاتا ہے اور ID کے ذریعے دوبارہ استعمال کیا جا سکتا ہے۔

دریافت کے لیے، `GET /api/combos/auto` ہر ویرینٹ کو اس کے حل شدہ امیدوار پول کے ساتھ، نیز `context_length` / `max_output_tokens` کے ساتھ فہرست کرتا ہے — یہ امیدوار پول کی ونڈوز میں سے MAX ہوتے ہیں۔ کلائنٹس (مثلاً opencode پلگ ان) کو `0` کی بجائے انہی قدروں کی تشہیر کرنی چاہیے: صفر کانٹیکسٹ opencode کی خودکار کمپیکشن کو مکمل طور پر غیر فعال کر دیتا ہے، جس سے سیشنز اس وقت تک بڑھتے رہتے ہیں جب تک گیٹ وے کی ہسٹری صفائی کانٹیکسٹ کو تباہ نہ کر دے۔ MAX کی تشہیر محفوظ ہے کیونکہ auto-combo کا کانٹیکسٹ پری فلٹر حد سے بڑی درخواستوں کو بڑی ونڈو والے امیدواروں کی طرف روٹ کرتا ہے۔

```bash
# بغیر کنفیگریشن استعمال (کومبو بنانے کی ضرورت نہیں)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# عام کومبوز اینڈ پوائنٹ کے ذریعے محفوظ شدہ آٹو کومبو
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### آٹو راؤٹر کی حکمت عملیاں

محفوظ شدہ `strategy: "auto"` کومبوز، `config.routerStrategy` (یا لیگیسی
`config.auto.routerStrategy`) کو درج ذیل میں سے کسی ایک پر سیٹ کر سکتے ہیں:

- `rules` — ڈیفالٹ وزن دار اسکورنگ
- `score` — سب سے زیادہ کنفیگر شدہ وزن دار اسکور منتخب کرتا ہے۔ عین برابر اسکور کی صورت میں کنفیگر شدہ
  امیدواروں کی ترتیب برقرار رہتی ہے؛ موجودہ `explorationRate` مکمل درجہ بند پول سے نمونہ منتخب کرتا ہے۔
- `cost` / `eco` — سب سے سستا صحت مند فراہم کنندہ
- `latency` / `fast` — قابلِ اعتماد ہونے کی پینلٹی کے ساتھ سب سے کم p95 لیٹنسی
- `sla-aware` / `sla` — ایسے امیدواروں کو ترجیح دیتا ہے جو p95 لیٹنسی، خرابی کی شرح، اور اختیاری
  لاگت کے SLOs پورے کرتے ہوں
- `lkgp` — آخری معلوم درست فراہم کنندہ پہلے
- `nadir` — [Nadir](https://getnadir.com) کے فیصلہ جاتی API سے پوچھتا ہے کہ پول میں موجود کون سا ماڈل
  پرامپٹ کے لیے درکار ہے؛ اختیاری ہے، ناکامی کی صورت میں `rules` پر کھلا فال بیک کرتا ہے
- `decision` — کنفیگرڈ فیصلہ کنندہ سے پوچھیں (TypeSafe سسٹم ون، آپ کا اپنا فیصلہ URL، یا کومبو کے اپنے ماڈلز میں سے ایک) پول میں کون سا ماڈل درخواست کے مطابق ہے؛ ڈیفالٹ آف `COMBO_DECISION_ROUTER_ENABLED` پرچم کے پیچھے، `rules` کے لیے فیل-اوپن

### راؤٹر کی حکمت عملیوں کی تفصیل

auto-combo انجن 7 قابلِ پلگ ان **RouterStrategy** امپلی مینٹیشنز فراہم کرتا ہے جنہیں
آپ `config.routerStrategy` (یا لیگیسی `config.auto.routerStrategy`) کے ذریعے تبدیل کر سکتے ہیں۔
ہر حکمت عملی دیے گئے `RoutingContext` کی بنیاد پر امیدوار پول سے ایک فراہم کنندہ منتخب کرتی ہے
(ٹاسک کی قسم، ٹول/ویژن کے اشارے، ٹوکن کا تخمینہ، اختیاری SLA پالیسی، اختیاری
آخری معلوم درست فراہم کنندہ)۔

#### 1. `rules` (ڈیفالٹ) — 16 عوامل پر مبنی وزن دار اسکورنگ

موجودہ اسکورنگ انجن کو ریپ کرتا ہے۔ `OPEN` سرکٹ بریکر والے
امیدواروں کو فلٹر کرتا ہے، پھر موجودہ ٹاسک کی قسم اور `getTaskFitness()` کے ساتھ `scorePool()`
چلاتا ہے، اور سب سے زیادہ اسکور والے فراہم کنندہ کو منتخب کرتا ہے۔

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: ڈیفالٹ۔ جب آپ تمام سگنلز کے درمیان متوازن سمجھوتا چاہتے ہوں تو اسے استعمال کریں۔

**عرف**: `rules` (کوئی عرف نہیں)

---

#### 2. `cost` / `eco` — سب سے سستا صحت مند فراہم کنندہ

امیدوار پول کو `costPer1MTokens` کے لحاظ سے (صعودی ترتیب میں) مرتب کرتا ہے اور سب سے سستا منتخب کرتا ہے۔
پہلے `OPEN` امیدواروں کو فلٹر کرتا ہے۔

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: لاگت کے لحاظ سے حساس ورک لوڈز، بیچ پروسیسنگ، یا بیک گراؤنڈ جابز۔

**عرف**: `cost`، `eco`

#### 3. `latency` / `fast` — قابلِ اعتماد ہونے کی پینلٹی کے ساتھ سب سے کم p95 لیٹنسی

`p95LatencyMs + (errorRate * 1000)` کے لحاظ سے ترتیب دیتا ہے۔ خرابی کی شرح کی پینلٹی یقینی بناتی ہے کہ
ناقابلِ اعتماد فراہم کنندگان کو کم درجہ ملے، چاہے ان کی برائے نام لیٹنسی کم ہو۔

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: لیٹنسی کے لحاظ سے حساس ورک لوڈز، جیسے ریئل ٹائم چیٹ، آٹو کمپلیٹ، یا
انٹرایکٹو کوڈنگ اسسٹنٹس۔

**عرف**: `latency`، `fast`

---

#### 4. `sla-aware` / `sla` — لیٹنسی/خرابی/لاگت کے SLO کی تعمیل

ہر امیدوار کو اس بنیاد پر اسکور کرتا ہے کہ وہ کنفیگر شدہ SLO پالیسی کو کتنی اچھی طرح پورا کرتا ہے:

| عامل             | وزن | فارمولا                                           |
| ---------------- | --- | ------------------------------------------------- |
| لیٹنسی اسکور     | 35% | `threshold / max(value, ε)`                       |
| خرابی کا اسکور   | 35% | `threshold / max(value, ε)`                       |
| صحت کا اسکور     | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| لاگت کا اسکور    | 10% | `threshold / max(value, ε)` یا معکوس نارملائزڈ    |
| استحکام کا اسکور | 5%  | لیٹنسی کے معیاری انحراف کا معکوس نارملائزڈ اسکور  |

جب `hardConstraints: true` ہو، تو امیدواروں کو بنیادی طور پر **خلاف ورزی کے اسکور**
(یعنی وہ کسی SLO سے کتنی حد تک تجاوز کرتے ہیں) کے لحاظ سے، اور پھر جامع اسکور کے لحاظ سے مرتب کیا جاتا ہے۔ بصورت دیگر صرف
جامع اسکور استعمال ہوتا ہے۔

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... پالیسی کے مقابلے میں ہر امیدوار کو اسکور کرتا ہے: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA فیلڈز** (کامبو کنفگ میں سیٹ کیے جاتے ہیں):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**کب استعمال کریں**: سخت لیٹنسی، خرابی کی شرح، یا لاگت کے بجٹ والے پروڈکشن ورک لوڈز کے لیے۔

**عرفی نام**: `sla-aware`، `sla`

#### 5. `lkgp` — آخری معلوم درست فراہم کنندہ پہلے

پہلے **آخری معلوم درست فراہم کنندہ** (اگر سیٹ ہو) کو آزماتا ہے، پھر
`rules` حکمت عملی پر واپس آ جاتا ہے۔ یہ سیشن اسٹکینیس کے لیے مفید ہے — گفتگو میں
بعد کی درخواستیں بھی وہی فراہم کنندہ سنبھالتا ہے۔

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules حکمت عملی پر واپس جائیں
    return getStrategy("rules").select(pool, context);
  }
}
```

**کب استعمال کریں**: کثیر مرحلہ گفتگوؤں میں، جہاں آپ چاہتے ہوں کہ وہی فراہم کنندہ
بعد کی درخواستیں سنبھالے (مثلاً کیشنگ، سیاق و سباق کے تسلسل، یا قیمتوں میں یکسانیت کے لیے)۔

**عرفی نام**: `lkgp` (کوئی عرفی نام نہیں)

#### 6. `nadir` — Nadir کے ذریعے پرامپٹ سے آگاہ ماڈل کا انتخاب

اوپر دی گئی ہر حکمت عملی امیدواروں کو اپنی ٹیلی میٹری کی بنیاد پر درجہ دیتی ہے؛ ان میں سے کوئی بھی
درخواست کو نہیں پڑھتی۔ `nadir` صارف کی آخری باری کے متن اور پول کے ماڈل IDs کو
[Nadir](https://getnadir.com) کے فیصلہ جاتی API (`POST /v1/bucket`) کو بھیجتا ہے اور اس مینیو میں سے Nadir کے منتخب کردہ ماڈل
کی طرف روٹ کرتا ہے (`simple` → سب سے سستا اہل ماڈل، `complex` →
فرنٹیئر ماڈل)۔ اس ماڈل کو پیش کرنے والا کنکشن پھر بھی `rules` کے ذریعے منتخب کیا جاتا ہے، اس لیے کوٹا،
صحت اور لاگت یہ فیصلہ کرتے رہتے ہیں کہ کون سا اکاؤنٹ استعمال ہوگا۔

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

دونوں اسٹرنگز کے لیے `OMNIROUTE_NADIR_API_KEY` اور `OMNIROUTE_NADIR_BASE_URL` متبادل env اقدار ہیں۔
`baseUrl` صرف خود ہوسٹ کردہ Nadir کے لیے درکار ہے (آخر میں آنے والا `/v1` قابل قبول ہے)۔
کلید کے بغیر کالز Nadir کے گمنام درجے پر جاتی ہیں، جہاں فی IP شرح کی حد عائد ہوتی ہے۔ کلید کے ساتھ
([ایک بنائیں](https://app.getnadir.com/dashboard/api-keys))، ہر فیصلہ
آپ کے Nadir ڈیش بورڈ میں لاگ کیا جاتا ہے۔ مکمل سیٹ اپ اور توثیق:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/)۔

سسٹم سے باہر جانے والا ڈیٹا: صارف کے آخری پیغام کا متن (پہلے 16k حروف)، امیدوار
ماڈل IDs اور ایک `source: "omniroute"` چینل ٹیگ۔ کوئی سسٹم پرامپٹ، ہسٹری، ٹولز یا
ہیڈرز نہیں۔

ناکامی کی صورت میں رویہ fail-open ہوتا ہے: ٹائم آؤٹ (ڈیفالٹ 2000 ms)، non-2xx، ناقابل رسائی
ہوسٹ، خراب جواب یا پول سے باہر کسی انتخاب کی صورت میں `rules`
کے فیصلے پر واپس جایا جاتا ہے اور وجہ کے شروع میں `NadirStrategy: fallback (…)` شامل کیا جاتا ہے۔ ناکام کال کے بعد
حکمت عملی 30 s تک نیٹ ورک کو چھوڑ دیتی ہے، اس لیے کسی بندش میں ہر درخواست کے بجائے
ہر 30 s میں صرف ایک ٹائم آؤٹ کی لاگت آتی ہے۔ روٹنگ ایونٹس صرف اس وقت `strategy: "nadir"` رپورٹ کرتے ہیں جب Nadir نے واقعی
انتخاب کیا ہو۔

**کب استعمال کریں**: ایسے پول پر مختلف مشکل درجات کی ٹریفک کے لیے جو ماڈل کے متعدد درجات پر مشتمل ہو (ایک چھوٹا، ایک درمیانی
اور ایک فرنٹیئر ماڈل)، جہاں آپ ہمیشہ فرنٹیئر ماڈل استعمال کرنے کی لاگت کم کرنا چاہتے ہوں۔

**عرفی نام**: `nadir` (کوئی عرفی نام نہیں)

#### 7. `decision` — پلگ ایبل فیصلہ کن ماڈل چنتا ہے۔

`decision` پوچھتا ہے a** فیصلہ کن** پول میں کون سا ماڈل درخواست پر فٹ بیٹھتا ہے، پھر پول کو اس ماڈل تک تنگ کرتا ہے اور `rules` کنکشن لینے دیتا ہے (کوٹہ، صحت اور لاگت اب بھی اکاؤنٹ کا انتخاب کرتے ہیں)۔ فیصلہ کن کو کومبو کے فیصلے بلاک — `config.decision` میں سیٹ کیا جاتا ہے جب راؤٹر نوبز `config` کے اوپر بیٹھتے ہیں (ڈیش بورڈ کیا لکھتا ہے)، یا `config.auto.routerStrategy` کے آگے `config.auto.decision` :

| `decider`     | کون جواب دیتا ہے۔                                                                                                          | ضروریات                                       |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `systemone`   | TypeSafe سسٹم ون (`POST https://api.typesafe.ai/v1/systemone`)، ڈیفالٹ ماڈل `jev-latest`                                   | ایک `typesafe` کنکشن یا env کلید              |
| `http`        | `baseUrl` پر آپ کا فیصلہ کرنے والا : `wire: "systemone"` (`{baseUrl}/v1/systemone`) یا `"openai-chat"` ( بات چیت کی تکمیل) | `baseUrl` + `model`; کلیدی اختیاری            |
| `combo-model` | آپ کے فراہم کنندہ کے ماڈلز میں سے ایک، جسے فیوژن جج کی طرح عمل میں بلایا جاتا ہے۔                                          | `model` as `provider/model` (کوئی کومبو نہیں) |

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "decision",
    "decision": {
      "decider": "http",
      "baseUrl": "https://decider.example.com",
      "wire": "openai-chat",
      "model": "qwen-small",
      "connectionId": "<stored connection id>",
      "timeoutMs": 2000,
      "minConfidence": 0.6,
      "descriptions": { "gpt-4o-mini": "Quick drafts and short answers" }
    }
  }
}
```

فیلڈز (محفوظ کرنے پر اور دوبارہ درخواست کے وقت پر سخت اسکیما کے ذریعہ تصدیق شدہ):

- `decider` — `systemone`, `http` یا `combo-model`
- `model` — TypeSafe ماڈل، آپ کے URL پر فیصلہ کرنے والا ماڈل، یا کومبو ماڈل کال کا `provider/model` (200 حروف تک)۔
- صرف `baseUrl` — `http` : ایک `http(s)` URL 500 حروف تک، بغیر اسناد، استفسار یا ٹکڑے کے۔ اس OmniRoute (loopback + `PORT`) کی طرف اشارہ کرنے والے URL سے انکار کر دیا گیا ہے۔
- `wire` — `http` صرف: `systemone` (پہلے سے طے شدہ) یا `openai-chat`۔
- `connectionId` — ذخیرہ شدہ کنکشن جس کی کلید استعمال ہوتی ہے (صرف کالنگ API کلید کے اجازت یافتہ کنکشن کے اندر)۔ اس کے بغیر، `systemone` ایک `typesafe` کنکشن پڑھتا ہے اور ہر نیٹ ورک فیصلہ کنندہ `OMNIROUTE_DECISION_API_KEY` پر واپس آتا ہے۔ کوئی `apiKey` فیلڈ نہیں ہے: ایک کلید کبھی بھی کومبو میں محفوظ نہیں ہوتی ہے۔
- `timeoutMs` — انٹیجر، 100–5000، ڈیفالٹ 2000۔
- `minConfidence` — 0-1; کم اعتماد والا جواب `rules` پر آتا ہے (ایک فیصلہ کنندہ جو عدم اعتماد کی اطلاع دیتا ہے 0 شمار ہوتا ہے)۔
- `descriptions` — 50 اندراجات تک (300 تک کی کلید، 1000 حروف تک متن)، ماڈل id یا `provider/model` کے ذریعے کلید؛ غیر ترتیب شدہ اندراجات کو لاگت کی درجہ بندی کی تفصیل ملتی ہے۔

**جھنڈا۔** `COMBO_DECISION_ROUTER_ENABLED` (پہلے سے طے شدہ `false`) ہر فیصلہ کنندہ کو گیٹ کرتا ہے۔ جب یہ آف ہوتا ہے، ایک `decision` کومبو کوئی سند نہیں پڑھتا، کوئی کال نہیں کرتا اور `rules` کے ساتھ روٹس کرتا ہے۔ لاگ `fallback (disabled)` کہتا ہے۔ اکیلے ذخیرہ شدہ کلید اسے کبھی آن نہیں کرتی ہے۔ فیصلہ بلاک کے بغیر کمبوس بالکل متاثر نہیں ہوتے ہیں۔

**باکس سے کیا نکلتا ہے۔** صرف آخری صارف کے پیغام کا متن (8000 حروف تک؛ chat/Claude `messages` یا جوابات `input`) اور ماڈل ids کا مینو ان کی تفصیل کے ساتھ۔ کبھی بھی سسٹم پرامپٹ، جوابات `instructions`، ٹولز، ہسٹری، ہیڈرز یا اکاؤنٹ کا ڈیٹا نہ دیں۔ نیٹ ورک کالز فراہم کنندہ کے آؤٹ باؤنڈ گارڈ سے گزرتی ہیں بغیر دوبارہ کوششوں کے، کوئی ری ڈائریکٹ اور 64 KB رسپانس کیپ کے بغیر۔ `combo-model` کال نان سٹریمنگ، ٹول فری، `temperature: 0` ہے، 256 ٹوکن بجٹ کے ساتھ؛ فیصلہ کال کے اندر شروع ہونے والے فیصلے سے انکار کر دیا جاتا ہے۔

**ناکامی کا رویہ** فیل کھلا ہے: کوئی بھی ناکامی `rules` فیصلے کو حل کرتی `recursion`، اور وجہ `decision(<decider>): fallback (<reason>)` `disabled`, `not_configured`, `missing_credential`, `timeout`, `http_error`, `invalid_response`, `out_of_menu`, `refused`, `cooldown`, `network_error` `low_confidence` `single_option` میں سے `<reason>` کے ساتھ پڑھتی ہے `no_user_text` ٹائم آؤٹ، HTTP ایرر یا نیٹ ورک کی خرابی کے بعد اینڈ پوائنٹ کو 30 سیکنڈ کے لیے چھوڑ دیا جاتا ہے۔ ایک کامیاب انتخاب `decision(<decider>): selected <model> from <n>; confidence <c> (<rules reason>)` پڑھتا ہے۔ کوئی URL، key، prompt یا upstream باڈی لاگ تک نہیں پہنچتی۔

کامبو بلڈر ان فیلڈز کو دکھاتا ہے جب راؤٹر کی حکمت عملی `decision` ہو، جس میں پلیس ہولڈرز اور ایک** ٹیسٹ کا فیصلہ** بٹن جو `POST /api/combos/decision-preview` ایک بار غیر محفوظ شدہ ترتیبات (ایک ہی پرچم) کے ساتھ کال کرتا ہے۔

**کب استعمال کرنا ہے۔** : مخلوط مشکل ٹریفک جہاں آپ چاہتے ہیں کہ آپ کے منتخب کردہ درجہ بندی کے ذریعہ فی درخواست درجے کا انتخاب کیا جائے، خاص طور پر نادر کے ذریعہ نہیں۔

**عرف** : `decision` (کوئی عرف نہیں)

### حسب ضرورت راؤٹر حکمت عملیاں

آپ عوامی API کے ذریعے اپنا `RouterStrategy` نفاذ رجسٹر کر سکتے ہیں:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // آپ کی روٹنگ منطق یہاں
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

پھر اسے استعمال کریں:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### راؤٹر حکمت عملی کے انتخاب کی رہنما فہرست

| استعمال کی صورت          | حکمتِ عملی  | وجہ                                       |
| ------------------------ | ----------- | ----------------------------------------- |
| متوازن کام کا بوجھ       | `rules`     | طے شدہ — تمام عوامل کو مدِنظر رکھتی ہے    |
| لاگت کم کرنا             | `cost`      | ہمیشہ سب سے کم لاگت والا انتخاب کرتی ہے   |
| تاخیر کم کرنا            | `latency`   | تیز ترین قابلِ اعتماد فراہم کنندہ چنتی ہے |
| سخت SLOs                 | `sla-aware` | p95/خرابی/لاگت کی حدود کے مطابق چھانتی ہے |
| کثیر باری چیٹ            | `lkgp`      | سیشن سے وابستگی                           |
| ملی جلی دشواری           | `nadir`     | ہر پرامپٹ کے لیے ماڈل کا درجہ چنتی ہے     |
| اپنا درجہ بندی کرنے والا | `decision`  | آپ کا فیصلہ کرنے والا ماڈل چنتا ہے۔       |

SLA سے آگاہ فیلڈز:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## ٹاسک کی موزونیت

6 ٹاسک اقسام (`coding`، `review`، `planning`، `analysis`، `debugging`، `documentation`) میں 30+ ماڈلز کو اسکور کیا گیا ہے۔ وائلڈ کارڈ پیٹرنز کی معاونت موجود ہے (مثلاً، `*-coder` → کوڈنگ کا بلند اسکور)۔

## خودکار ویریئنٹس کا خلاصہ

بنیادی `auto` (ڈیفالٹ) اور `autoPrefix.ts` میں اعلان کردہ 6 `AutoVariant` اقدار سمیت، **7 قابلِ استعمال ماڈل IDs** ہیں:

`auto`، `auto/coding`، `auto/fast`، `auto/cheap`، `auto/offline`، `auto/smart`، `auto/lkgp`

(`AutoVariant` بذاتِ خود 6 اقدار شمار کرتا ہے؛ ساتواں آپشن "کوئی ویریئنٹ نہیں" — بنیادی `auto` — ہے، جسے `parseAutoPrefix()`، `variant: undefined` کے طور پر ہینڈل کرتا ہے۔)

## ٹئیرز Auto-Combo میں کیسے فٹ ہوتے ہیں

16 عوامل پر مشتمل اسکورنگ فنکشن (`open-sse/services/autoCombo/scoring.ts`) ٹئیر کی
رکنیت کو دو سگنلز کے طور پر استعمال کرتا ہے: `tierPriority` (0.0476) اور `tierAffinity` (0.0476)۔ مکمل
`DEFAULT_WEIGHTS` سیٹ کے لیے اوپر دی گئی مستند [اسکورنگ عوامل کی جدول](#how-it-works-persisted-auto-combos) دیکھیں — ہر پیک کی مخصوص ترتیبات (ship-fast/cost-saver/quality-first/
offline-friendly) "ہر پیک کے لیے ویٹ پروفائلز" کی جدول میں درج ہیں۔

صرف ٹئیر کی بنیاد پر **لازماً** Tier 1 کو پہلی ترجیح نہیں دی جاتی — اگر Tier 1 کی لیٹنسی خراب ہو یا
لاگت بمقابلہ معیار غیر موزوں ہو، تو Tier 2 ترجیح حاصل کرتا ہے۔ ٹئیر کی ترتیب لازمی کرنے کے لیے، کومبو
حکمتِ عملی `priority` استعمال کریں اور فراہم کنندگان کو ٹئیر کے مطابق ترتیب دیں۔

Tier 1 (سبسکرپشن) کو بھرپور ترجیح دینے کے لیے، `tierPriority` کا ویٹ بڑھائیں:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ٹئیر کی تعریفوں اور فراہم کنندگان کی درجہ بندی کے لیے [`docs/guides/TIERS.md`](../guides/TIERS.md) دیکھیں۔

## ٹیسٹنگ اور کوریج

### تعیّن شدہ routing-decision میٹرکس (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` حقیقی combo pipeline کے ذریعے mocked upstream کے ساتھ end-to-end اس میں شامل عوامی strategies کے routing **decision** کو ثابت کرتا ہے۔
کوریج میں شامل ہیں:

- تمام 21 `ROUTING_STRATEGY_VALUES` strategies (ordered، weighted، cost، context، fusion، …)۔
- `quota-share` (اندرونی) end-to-end: حقیقی `selectQuotaShareTarget` seam (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) کے ذریعے DRR fairness + saturation deprioritization۔
- ہر target count میں `context-relay` universal-handoff کوریج۔

یہ suite CI (`test:integration` job) میں `--test-concurrency=1` اور
`--test-force-exit` کے ساتھ چلتا ہے، اس لیے یہ تعیّن شدہ ہے اور اسے live credentials کی ضرورت نہیں ہوتی۔

### مشروط live smoke (CI میں نہیں — حقیقی providers)

| Command                                | یہ کیا کرتا ہے                                                                                 |
| :------------------------------------- | :--------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` کے ساتھ in-process حقیقی routing؛ ایک live OmniRoute DB کا snapshot لیتا ہے |
| `npm run test:combo:live:vps`          | live OmniRoute server کے خلاف HTTP calls (`COMBO_LIVE_BASE_URL` سیٹ کریں)                      |
| `npm run test:combo:live:vps:failover` | وہی، جان بوجھ کر failover scenarios کے ساتھ                                                    |

یہ smoke tests حقیقی wire path (combo → provider → completion) کی جانچ کرتے ہیں۔ انہیں
جان بوجھ کر CI سے خارج رکھا گیا ہے کیونکہ ان کے لیے live credentials اور VPS access درکار ہے۔
