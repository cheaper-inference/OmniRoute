使用本指南，為提取請求選擇最精簡且可靠的開發迴圈。本指南並不取代下方連結的特定領域架構與安全性文件；它會將每種常見的變更類型連結至其契約、重點檢查及 CI 涵蓋範圍。

## 每項變更都遵循的流程

1. **編輯前先選擇基礎分支。** 找出最高版本且仍在使用中的 `release/v*` 分支，並從
   其頂端建立分支。將該分支設為目標，而非 `main`。若目前處於版本凍結期，請勿將已凍結的
   分支設為目標；請使用
   [分支與發布模型](BRANCHING_MODEL.md)中所述的下一個有效週期。
2. **列出契約。** 識別變更所影響的每個目錄、結構描述、產生的成品、公開 API 或使用者
   介面。下表提供最低限度的起始集合。
3. **撰寫或更新重點測試。** 對 `src/`、`open-sse/`、`electron/` 或
   `bin/` 的正式環境程式碼變更，必須在同一個 PR 中包含自動化測試。先執行能證明該
   行為的最小測試檔案集合，再執行列出的重點檢查關卡。
4. **讓 CI 執行廣泛的矩陣。** 完整的單元測試分片、Vitest、覆蓋率棘輪檢查及
   正式環境建置都會在 PR 上執行。只有當重點測試失敗顯示可能存在更廣泛的影響，或變更橫跨
   多個子系統時，才在本機執行廣泛的測試套件。
5. **在審查前完成同步。** 擷取有效的基礎分支，檢查其新增提交及您的變更與其之間的差異，
   然後依照貢獻者工作流程，將變更重定基底至基礎分支，或合併基礎分支。請從來源解決產生檔案
   與目錄的衝突，重新產生這些檔案、再次執行重點迴圈，並確認 PR 仍以有效的發布分支為目標。
6. **記錄證據。** 在 PR 範本中列出已執行的命令、每個新增或變更的測試檔案、
   遷移或功能旗標，以及任何仍待執行且僅限 CI 的驗證。

## 依變更類型分類的黃金路徑

下列命令是最低限度的重點檢查，並不代表可以略過直接涵蓋您所變更行為的測試。

### 提供者

**契約**

- `src/shared/constants/providers/` 中的提供者定義，以及其在
  `src/shared/constants/providers.ts` 中的組合方式。
- `open-sse/config/providerRegistry.ts` 或其拆分出的登錄檔案中的模型與功能。
- 執行器／轉譯器選擇、OAuth 或 API 金鑰設定、儀表板資產，以及適用時產生的
  提供者參考文件。
- 公開憑證必須使用 `resolvePublicCred()`；錯誤回應必須使用共用的淨化
  錯誤輔助函式。請參閱 `docs/security/PUBLIC_CREDS.md`（位於 git 中；不會編譯至 `/docs`）及
  [錯誤淨化](../security/ERROR_SANITIZATION.md)。

**重點迴圈**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # 當目錄變更時；提交產生的差異
npm run lint
```

也請測試每個受影響的請求系列：聊天、Responses、圖片、嵌入、音訊或影片。
請將產生的目錄與黃金差異視為契約變更進行審查；請勿盲目接受。

### 路由

**契約**

- `src/shared/constants/routingStrategies.ts` 中的公開策略值與 UI 中繼資料。
- `open-sse/services/combo.ts` 與 `open-sse/services/combo/` 下的分派及排序。
- Combo 結構描述、持久化、復原狀態、模型功能，以及 API／UI 控制項。
- 行為變更時應參閱[自動 Combo 引擎](../routing/AUTO-COMBO.md)與復原能力文件。

**重點迴圈**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # 策略或分派變更
npm run check:known-symbols      # 策略註冊變更
npm run lint
```

請在本機使用具確定性的模擬上游測試。即時 Combo 冒煙測試需要憑證，且須手動執行，
不能取代 CI。

### UI / UX

**契約**

- `src/app/` 與 `src/shared/components/` 下的 Next.js 路由／頁面及共用元件邊界。
- API 回應格式、載入／空白／錯誤狀態、鍵盤與螢幕閱讀器行為、
  回應式版面配置、主題及語系擴充。
- `src/i18n/messages/en.json` 中的英文 UI 來源字串；請勿硬編碼新的使用者可見文案。

**重點迴圈**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

若有互動或視覺變更，請執行應用程式，並檢查窄幅及寬幅視窗。CI 會執行
正式環境建置與更廣泛的測試套件；視覺行為仍需要適合該變更的重點元件測試、Playwright
測試或有記錄的手動檢查。

### i18n

**契約**

- `src/i18n/messages/en.json` 是 UI 來源；`config/i18n.json` 是語系來源。
- CLI 目錄另行存放於 `bin/cli/locales/` 下。
- 請完整保留 ICU 預留位置及標籤。請勿翻譯產品／提供者／模型名稱、
  通訊協定與標頭名稱、命令、程式碼／JSON 識別碼、URL、環境變數，或
  `OmniRoute`、`OAuth`、`MCP` 及 `A2A` 等受保護詞彙。目前的來源清單為
  `scripts/i18n/glossary/protected-terms.json`。

**重點迴圈**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # 當 CLI 字串／目錄變更時
npm run lint
```

這是現有系統的指引，並非擴充其工具或鍵模型的邀請。
在替代系統的設計期間，i18n 修補應保持精準。除非任務明確要求產生翻譯，
而且您已審查產生的差異，否則請勿執行會呼叫外部服務的翻譯命令。

### CLI

**契約**

- `bin/cli/` 中的公開命令與旗標、產生的 API 命令、結束代碼、stdout/stderr 與
  JSON 輸出結構、設定／環境行為，以及封裝的檔案。
- CLI 面向使用者的字串必須使用 CLI i18n 層，並維持 `en`/`pt-BR` 目錄同步。
- 保持 Node 為支援的執行環境，並維持已發布的二進位檔契約。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 產生／封裝的 CLI 變更
npm run check:pack-policy     # 套件介面變更
npm run lint
```

當行為取決於剖析、檔案或結束狀態時，請在暫存資料目錄中使用完全相同的命令。CI 會執行更廣泛的套件成品與生態系統檢查。

### 資料庫

**契約**

- `src/lib/db/` 下的領域模組；直接匯入特定模組（舊的 `localDb.ts` 重新匯出層已移除）。
- `src/lib/db/migrations/` 下具編號且具冪等性的 SQL 移轉、交易安全性、升級
  行為、索引，以及所有受結構描述影響的呼叫端。
- 路由與處理常式絕不可直接執行原始 SQL。

**聚焦迴圈**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

新增移轉時，請同時測試全新資料庫及從先前結構描述升級。資料庫測試必須關閉控制代碼，並在清理期間呼叫 `resetDbInstance()`。只有在盡力支援的 Bun 轉接器路徑發生變更時，才執行 `npm run test:bun:db`；Node 仍是權威基準。

### 建置／部署

**契約**

- 根目錄與工作區資訊清單／鎖定檔、`scripts/build/`、Next.js 獨立組裝、`dist/`
  套件內容、Electron 平台中繼資料、CI 工作流程，以及部署哨兵。
- 必須保持支援的 Node 版本範圍，以及 `CLAUDE.md` 中允許清單內的 Bun 用法不變。
- 建置成品維持不受追蹤；相依套件、授權、工作流程與套件政策皆適用。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 相依套件或鎖定檔變更
npm run check:pack-policy      # 已發布套件的介面變更
npm run lint
```

只有在變更會影響編譯、獨立組裝、資產或執行階段封裝時，才在本機使用 `npm run build`。僅將 `npm run build:release` 用於發布／部署驗證。CI 的建置是最終的跨平台判定依據；平台特定的 Electron 變更需要對應的聚焦建置或冒煙測試證據。

## 共用機器的開發者指令碼

兩個 `scripts/dev/` 輔助工具定義了 devbox 上其他工作階段仍在執行時的本機開發迴圈：

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD 中的檔案
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # 僅檢查這些檔案
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # 隔離的 worktree，可安全地平行執行
```

- `typecheck-touched.sh` 僅透過暫存的
  `tsconfig.touched.tmp.json`（`extends ./tsconfig.json`、`types: ["node"]`、`noEmit`、
  `incremental: false`），在 6 GB heap 限制下對異動的 `.ts/.tsx` 檔案執行類型檢查，
  因此可取代會讓高負載機器發生 OOM 的全專案 `tsc -p tsconfig.json`。它會輸出異動檔案中的
  錯誤及一行摘要；若異動檔案中有錯誤，則以 `1` 結束；若只有匯入的檔案中有錯誤，或 tsc
  在未輸出診斷資訊的情況下終止，則以 `2` 結束（請閱讀它所指出、位於
  `_artifacts/typecheck-touched/` 下的記錄檔）；若沒有錯誤，則以 `0` 結束。暫存 tsconfig
  一律會被移除；切勿提交它。
- `new-worktree.sh` 會透過 `<git-common-dir>/omniroute-new-worktree.lock`
  將並行執行序列化（預設最多等待 600 秒，並顯示提示訊息；指令碼標頭記載了覆寫方式），
  而且當 `git worktree add` 在 worktree 建立前失敗時，會回復它所建立的分支，因此重試時
  不需要手動執行 `git branch -D`。硬連結的 `node_modules` 與 `.husky/_` 副本維持不變。

## 本機候選版本迴圈

原始碼測試無法證明封裝後的成品能夠啟動：封裝清單、裁剪後的相依套件與原生二進位檔，
只有在 tarball 安裝並啟動後才會暴露問題。`npm run dev:candidate`
（`scripts/dev/candidate.mjs`）是 RFC #8084 中「建置一次 / 驗證 / 推廣」流程的本機端：
它會建置一個候選版本、驗證該確切成品、透過目錄重新命名進行推廣，並在推廣後的槽位未通過
健康檢查時將其回復。

```bash
npm run dev:candidate -- run --dry-run --json  # 輸出計畫，不進行任何變更
npm run dev:candidate -- run                   # 建置 + 驗證 + 推廣，自動回復
npm run dev:candidate -- build                 # npm pack + 安裝至 _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # 在可用連接埠啟動，檢查 /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current，current → previous
npm run dev:candidate -- rollback              # 交換 current 與 previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # 重複使用在其他地方（CI）建置的 tarball
```

- **僅建置一次。** `build` 會封裝目前的工作樹（它需要 `dist/server.js`，因此請先執行
  `npm run build:release`），或複製 `--from-tarball`，接著將 tarball 安裝至隔離的 npm
  prefix，因為 tarball 不包含 `node_modules`。id 是簡短的 `HEAD` sha（當工作樹有本機變更時
  會加上 `-dirty`），若為 tarball，則是 `tgz-<sha256>`。若未帶 dirty 標記的 id 已完成建置，
  便會直接重複使用，而不會重新建置；傳入 `--force` 可強制重新建置。
- **驗證套件，而非原始碼。** `validate` 會使用全新的
  `DATA_DIR=<candidate>/data`、虛假密鑰來啟動已安裝的 CLI（`serve --port <free port>`），
  並從環境中移除操作者的 `OMNIROUTE_API_KEY`、`STORAGE_ENCRYPTION_KEY` 與
  `INITIAL_PASSWORD`，藉此檢查全新安裝在無金鑰情況下的 loopback 安全態勢。它會等待
  `GET /api/health` 回傳 200，要求 `GET /v1/models` 回傳 200，停止處理程序群組，並將判定結果
  連同 tarball 雜湊值記錄於 `validation.json`。
- **推廣同一個成品。** 若候選版本未針對目前的 tarball 雜湊值通過驗證，`promote` 將拒絕
  推廣。預設的作用中槽位是 `_artifacts/candidate/current`；`--target <dir>` 可選取同一
  檔案系統中的其他目錄，其前一個槽位則為 `<dir>.previous`。每次重新命名都是不可分割的；
  若過程中途失敗，已執行的重新命名都會被反向復原。
- **回復。** `run` 會再次驗證推廣後的槽位；若該檢查失敗，便會交換 `current` 與
  `previous` 以回復原狀。未通過第一次驗證的候選版本絕不會被推廣。

所有內容都會寫入已由 git 忽略的 `_artifacts/candidate/`；現有的 OmniRoute 安裝及其資料目錄
絕不會受到影響。推廣後的 CLI 位於 `_artifacts/candidate/current/prefix/bin/omniroute`；
使用時請以您自己的 `DATA_DIR` 啟動它。結束代碼：`0` 表示成功，`1` 表示驗證或推廣失敗，
`2` 表示用法錯誤或缺少建置成品。

## 本地迴圈與 CI 的比較

| 每次修補皆於本地執行                               | CI 提供廣泛的訊號                                |
| -------------------------------------------------- | ------------------------------------------------ |
| 上述的直接行為測試與類別閘門                       | 分片的完整單元測試套件與序列測試                 |
| `npm run lint`                                     | Vitest 測試套件與覆蓋率／品質棘輪機制            |
| 僅在受影響的契約有所要求時，才執行類型檢查或建置   | 生產環境建置、安全性、文件、相依性與 PR 政策閘門 |
| 僅在自動化無法證明行為時，才執行手動互動／即時檢查 | 工作流程所設定的跨作業整合與平台檢查             |

聚焦迴圈通過，代表受變更契約已有相關佐證，並不表示無關的 CI 檢查
也一定會通過。反之，也不要讓每次本地編輯都必須等待完整的儲存庫矩陣執行完畢。

## 協調檢查清單

請求審查前：

- 確認 PR 的基底仍為最高版本且使用中的 `release/v*` 分支。
- 擷取該基底，並審查自建立分支以來新增的提交。
- 檢查 `git diff <active-base>...HEAD`，確認是否有意外或由產生程序造成的變動。
- 更新來源並重新產生輸出，以解決目錄與產生文件的衝突。
- 完成協調後，重新執行 PR 說明中列出的每項聚焦測試／閘門。
- 絕不可僅為了配合已變動的基底，而弱化斷言或移除必要測試。

如需了解發布凍結與重新設定目標的規則，請參閱
[分支與發布模型](BRANCHING_MODEL.md)。如需完整的 CI 項目清單，請參閱
[品質閘門參考](../architecture/QUALITY_GATES.md)。
