## 概述

所有 OmniRoute 管理 API 路由均歸類為三種保護層級之一。分類是靜態的，定義於 `src/server/authz/routeGuard.ts`，並會在執行任何其他驗證分支之前進行評估。

## 層級

### 層級 1 — LOCAL_ONLY

**強制執行方式：** `isLocalOnlyPath(path)` → 回送主機檢查  
**繞過方式：** 預設無法繞過。當請求攜帶具有 `manage` 範圍的有效 API 金鑰時，針對
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路徑提供範圍有限的例外
（請參閱[管理範圍例外](#manage-scope-carve-out)）。

這些路由會產生子程序或執行執行階段程式碼。若將它們暴露給非回送流量，
取得有效 JWT 的攻擊者（例如透過 Cloudflared/Ngrok 通道）便能觸發程序產生——
這是一種已知的 CVE 類別
（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 的含義（攻擊類別）：** 管理／代理伺服器公開了一個
會啟動子程序（`npm install`、`node`、瀏覽器、代理伺服器、`git`、`tar`、……）
的端點。如果該端點可從主機外部存取——例如操作者將 OmniRoute 放在
nginx/Cloudflare/Tailscale 通道後方，而 JWT 遭到洩漏，或驗證設定錯誤——
攻擊者便能將「呼叫 API」轉變為「在主機上執行命令」（遠端程式碼執行）。
OmniRoute 透過在每個具備產生程序能力的路由上，**無條件地在任何驗證檢查之前
強制執行回送主機檢查**，來封鎖此類攻擊：即使權杖透過通道洩漏，仍無法存取
程序產生功能。

**完整的 LOCAL_ONLY 集合。** 權威來源是
`src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES` /
`LOCAL_ONLY_API_PATTERNS`；下表反映目前的狀態。`check-route-guard-membership`
閘門會列舉具備程序產生能力之前綴下的每個 `route.ts`，若其中任何一個未被
分類為僅限本機，CI 就會失敗。

#### 管理範圍例外

部分 LOCAL_ONLY 路徑亦可從非迴路位址存取，但前提是且僅限於請求攜帶 `Authorization: Bearer <api-key>`，且其詮釋資料包含 `manage` 範圍（或 `admin`）。此例外會透過 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 明確地針對各路徑啟用，因此任何新的 LOCAL_ONLY 路徑預設仍會嚴格限制為迴路位址。未經驗證的請求，以及使用不具管理範圍金鑰的請求，仍會被拒絕並回傳 `403 LOCAL_ONLY`。

目前唯一可略過限制的前綴是 `/api/mcp/`。`/api/cli-tools/runtime/` 和 `/api/services/` 被刻意排除，因為它們可以產生任意子處理程序（`npm install`、`node`），而這正是 LOCAL_ONLY 層級旨在防範的 CVE 類型。

**#7895 — `mcp:connect` 狹義範圍：** `/api/mcp/` 例外「亦」接受持有狹義 `mcp:connect` 範圍的 Bearer 金鑰（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`），並透過 `src/server/authz/policies/management.ts` 中的 `hasMcpConnectOrManageScope()` 進行檢查。此範圍「僅」適用於 `/api/mcp/` — `mcp:connect` 不會授予任何其他管理路由的權限（包括未來可能新增的所有其他 LOCAL_ONLY 略過前綴），且刻意未將其納入 `MANAGEMENT_API_KEY_SCOPES`。持有 `manage`/`admin` 的金鑰仍可如以往一樣通過此例外；對於只需遠端呼叫 MCP、而不應具有廣泛管理存取權的呼叫者，`mcp:connect` 是權限較低的替代方案。

| 請求                                             | 路徑                       | 結果             |
| ------------------------------------------------ | -------------------------- | ---------------- |
| 非迴路位址，無 Bearer                            | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `manage` 範圍            | `/api/mcp/*`               | 允許             |
| 非迴路位址，Bearer 具有 `mcp:connect` 範圍       | `/api/mcp/*`               | 允許             |
| 非迴路位址，Bearer 不具有 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `mcp:connect` 範圍       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `manage` 範圍            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 迴路位址，有任何 Bearer／無 Bearer               | 任何 LOCAL_ONLY            | 允許（通過閘門） |

#### 營運者指引與稽核

若您在反向代理或通道（nginx、Caddy、Cloudflare Tunnel、Tailscale、Ngrok）後方執行 OmniRoute，迴路檢查仍會保護上述可產生處理程序的路由 — 用戶端位址為非迴路位址的請求會在**執行驗證前**遭到拒絕並回傳 `403 LOCAL_ONLY`，因此外洩的 JWT 無法觸及處理程序的產生。營運者仍需承擔兩項責任：

- **請勿透過將用戶端 IP 偽造成回送位址來「修正」403。** 設定
  `X-Forwarded-For: 127.0.0.1`，或使用將來源位址改寫為回送位址的 Proxy，
  會重新引入此層級所封堵的同類 RCE 弱點。請透過 Proxy 公開
  儀表板/API——絕不可公開具備產生程序能力的路由。
- **將管理範圍繞過維持在最低限度。** 只有 `/api/mcp/` 可被繞過，而且
  僅限使用具 `manage` 範圍的 API 金鑰。`SPAWN_CAPABLE_PREFIXES` 永遠不能
  加入繞過清單——zod schema 會拒絕它們，且
  `isLocalOnlyBypassableByManageScope` 會在執行階段拒絕它們（縱深防禦），
  這正是儀表板中「無法設為可繞過」的含義。同一份拒絕清單也包含少數不會
  產生程序、但也絕不能從遠端存取的 LOCAL_ONLY 路由——`/api/oauth/kiro/auto-import`
  （讀取主機本機的 Kiro 認證檔案）、`/api/discovery/` 以及 `/api/issue-agent/`。
  執行階段快照載入器也會從儲存的設定資料列中移除這類項目，而舊版 JSON 匯入
  （`/api/settings/import-json`）絕不會寫入繞過金鑰。每個
  `LOCAL_ONLY_API_PREFIXES` 項目都必須位於拒絕清單中，或已通過可繞過資格審查
  （`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`）。位於
  `/api/providers/` 下、具有動態區段與靜態路徑且可產生程序的路由（例如 `/login`、
  `/refresh-cursor`），由
  `src/shared/constants/spawnCapablePrefixes.ts` 中以正規表示式為基礎的
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套項目涵蓋，
  而不是由扁平的 `SPAWN_CAPABLE_PREFIXES` 陣列涵蓋——若要讓扁平陣列捕捉到它們，
  就必須涵蓋整個 `/api/providers/` 前綴，這會過度擴大限制範圍，影響遠端儀表板
  合法用於提供者 CRUD 的路由樹。

**稽核存取**——若要確認沒有任何主機外部流量觸及這些路由：

- 在 `/dashboard/settings/security` 開啟 **授權清冊**：其中會呈現即時
  LOCAL_ONLY 前綴清單、哪些前綴可被繞過，以及編譯時期的可產生程序
  （「無法設為可繞過」）集合。
- 在反向 Proxy／存取日誌中搜尋上述前綴，並比對非回送用戶端位址。任何這類請求
  若回傳 `200` 而非 `403 LOCAL_ONLY`，表示 Proxy 正在遮蔽真實用戶端 IP——請修正
  Proxy。
- OmniRoute 日誌中針對這些路徑之一出現的 `403 LOCAL_ONLY`，表示防護機制正按預期
  運作，而不是應被抑制的錯誤。

#### 具有呼叫點探測閘門、可從遠端存取的路由

某些路由必須讓遠端儀表板持續可存取，但會為本機呼叫者執行主機端探測
（`which <binary>`、`<binary> --version`、`tailscale status --json`）。
它們的 `GET` 並非 LOCAL_ONLY；處理常式會使用
`getRequestPeerLocality()`（`src/shared/utils/apiAuth.ts`）讀取受信任的對等端判定，
而且只為 `loopback`／`lan` 呼叫者執行探測。`remote` 呼叫者會取得相同的回應結構，
但其內容來自不產生程序的來源（持久化狀態、設定、檔案系統檢查），並標記為
`probed: false`。

| 路由                                                             | 對遠端呼叫者略過的探測                                            |
| ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI 執行階段探測（`allowLocalRuntimeProbe`）與 CLI 後援程序產生   |
| `GET /api/headroom/status`                                       | `which headroom` 與 python `--version` 探測                       |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`、`tailscale status/funnel --json`、`which brew` |
| `GET /api/tunnels/cloudflared`（`GET` 豁免於 LOCAL_ONLY）        | `which cloudflared` PATH 查詢                                     |

任何會探測主機的新讀取路由都應遵循相同模式，否則就直接歸類為 LOCAL_ONLY。

### 第 2 層級 — ALWAYS_PROTECTED

**強制執行方式：** `isAlwaysProtectedPath(path)` → 略過 `requireLogin=false` 繞過  
**繞過：** 當 `requireLogin=false` 時亦無法繞過；始終需要 JWT

這些路由具有破壞性或不可逆。若在「無密碼」安裝環境中允許存取，就表示同一
LAN 上的任何人都能清除資料庫或終止伺服器程序。

| 路徑                                      | 原因                                            |
| ----------------------------------------- | ----------------------------------------------- |
| `/api/shutdown`                           | 終止伺服器程序                                  |
| `/api/settings/database`                  | 資料庫匯出、匯入與清除                          |
| `/api/db-backups`                         | 完整資料庫備份封存檔存取                        |
| `/api/settings/export-json`               | 匯出完整設定資料塊（包括機密資料）              |
| `/api/settings/import-json`               | 取代完整設定資料塊                              |
| `/api/providers/health-autopilot/actions` | 執行 autopilot 修復動作                         |
| `/api/settings/obsidian`                  | 為任何 Vault 根目錄簽發可重複使用的 WebDAV 認證 |
| `/api/relay/tokens`                       | Mints, lists, edits and revokes relay tokens    |

**違規時的回應：** `401 Authentication required`

`/api/settings/obsidian` 涵蓋其 `/webdav` 子路徑：`POST` 會將 WebDAV 檔案服務——
由自訂 Node 層在 Next.js 之前提供，位於此管線之外——指向由呼叫者選擇的根目錄，
並回傳新簽發的 Basic 認證；`DELETE` 會輪替這些認證，而父層 `POST` 會儲存
Obsidian REST API token。GHSA-62vw 僅遮蔽了 `GET` 密碼洩露；認證簽發仍位於
失效時開放的層級（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 還會拒絕
本身即為資料目錄、位於資料目錄內，或包含資料目錄的 Vault。

#### 認證匯出僅限操作員使用

上一層級僅決定是否需要_某種_憑證。下載已儲存憑證的路由會在處理常式中加入第二項檢查：`GET /api/settings/export-json`（已解密的提供者連線與原始 API 金鑰）、`GET /api/db-backups/export`（SQLite 檔案）以及
`GET /api/db-backups/exportAll`（完整封存檔）會呼叫 `requireOperatorCredential()`
（`src/lib/api/operatorCredential.ts`）。它接受儀表板工作階段、本機 CLI 主體，或
已停用登入的執行個體；對任何範圍的 API 金鑰（包括 `manage`
與 `admin`）以及 `oma_` 存取權杖皆回應 `403`。同步權杖核發（`POST /api/sync/tokens`）使用
相同的輔助函式，並額外接受受信任的回送內部服務權杖。

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### 全新安裝的啟動程序僅限回送連線——依據真實對等端，而非 `Host`

若未設定管理密碼（且沒有 `INITIAL_PASSWORD`），
`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` **只會對回送對等端**保持匿名啟動程序開放。
回送連線會依序根據下列受信任的對等端訊號判定：由權杖標記的真實 TCP 對等端
（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，即原則所見的資訊）、管線自身的
`AUTHZ_HEADER_PEER_LOCALITY` 判定結果（即路由處理常式所見的資訊，且僅在
已設定 `OMNIROUTE_PEER_STAMP_TOKEN` 時才受信任），或直接呼叫端的真實通訊端對等端。絕不會參考 `Host` /
`nextUrl.hostname`，而首次密碼寫入
（`POST /api/settings/require-login`）也受相同限制，而非向每個
網路對等端開放（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 會明確向下傳遞其自身的 `peerContext` 判定結果，
因此原始（剝除前）請求的標頭絕不會決定此結果。

### 第 3 層級 — 管理（預設）

所有其他管理路由。除非已設定 `requireLogin=false`，否則需要驗證。
CLI 權杖可驗證這些路由（回送連線 + 有效的 HMAC）。

## 評估順序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → 繼續執行
     → 非 loopback、具 manage 範圍的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允許 (management_key)
     → 否則                                      → 拒絕 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允許 (system)
  3. hasValidCliToken(headers)?
     → 允許 (cli) [loopback + timingSafeEqual HMAC 檢查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允許 (dashboard_session)
     → 在不可繞過路徑上具 manage 範圍的 Bearer？
        → 允許 (management_key)
     → 拒絕 401/403
  5. requireLogin=false?
     → 允許 (anonymous)
```

步驟 1 的 manage 範圍分支，是唯一能滿足 LOCAL_ONLY 路由的已驗證路徑；驗證後端失敗時會傳回 503（而非 403），因此過期的 DB 不會在無提示的情況下降級為「拒絕」。

## 新增可啟動程序的路由

1. 將路徑前綴新增至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中新增測試，斷言
   `isLocalOnlyPath()` 對新前綴傳回 true
3. **絕不可略過此步驟** — 請參閱 `CLAUDE.md` 中的硬性規則 #15
4. 決定：此路由是否也應納入 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   預設答案為**否**。僅當該路由能安全地公開給 manage 範圍持有者時，才選擇加入（亦即不會啟動任意由使用者控制的程式碼）。

## 新增可由 manage 範圍繞過的路徑

1. 確認該路由不會執行使用者提供的程式碼或命令。如果會，請停止 — 此例外機制並不適用。
2. 將前綴附加至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中，針對所有四種請求形式新增測試涵蓋：無 Bearer（403）、manage Bearer（允許）、非 manage Bearer（403），以及每個前綴的迴歸測試，確保 `/api/cli-tools/runtime/*` 即使帶有 manage Bearer，仍嚴格限制為 loopback。

## 在 OpenAPI 中記錄安全層級

將新路由新增至 `docs/openapi.yaml` 時，若該路由由 `routeGuard.ts` 分類，請套用對應的提供者擴充欄位：

| routeGuard.ts 分類           | YAML 註記                  | 強制執行方式                          |
| ---------------------------- | -------------------------- | ------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 無條件封鎖來自非 loopback 的請求      |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 仍要求驗證  |
| 內部管理員／偵錯路由         | `x-internal: true`         | 預設不顯示於 /dashboard/api-endpoints |
| 無（公開／標準驗證）         | （不需要註記）             | 由標準 `requireLogin` 控制的存取      |

### 驗證

有兩個指令碼會強制確保 YAML 註記與 `routeGuard.ts` 之間的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 若涵蓋率低於 99%，則執行失敗
- `scripts/check/check-openapi-security-tiers.mjs` — 若 `x-loopback-only` 或
  `x-always-protected` 註記與編譯期常數不一致，則執行失敗

這兩個指令碼都會在 pre-commit hook 和 CI 中執行。

### 誤判規則

若某個路由標有 `x-always-protected` 或 `x-loopback-only`，但未列於
`routeGuard.ts` 常數中，涵蓋率指令碼將會失敗。修正方式一律是讓 YAML 與
`routeGuard.ts` 實際強制執行的內容保持一致，而不是在尚未實作強制執行邏輯的情況下，逕自將路由新增至 `routeGuard.ts`。
