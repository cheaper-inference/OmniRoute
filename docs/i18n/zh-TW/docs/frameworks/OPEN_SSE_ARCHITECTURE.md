> **簡而言之**：`open-sse/` 是為 OmniRoute 中每個 LLM 請求提供支援的核心串流引擎。它包含約 1,400 個檔案，實作了請求管線、執行器、服務、MCP 伺服器與轉譯層。本指南將說明這些元件如何協同運作。

**原始碼：** `open-sse/`（工作區套件，約 1,440 個非測試 `.ts` 檔案）

---

## 為什麼要使用獨立的工作區套件？

基於以下幾個原因，`open-sse/` 是 OmniRoute monorepo 中的一個**獨立工作區**：

1. **可重複使用性** — `open-sse` 以 `@omniroute/open-sse` 的名稱發佈至 npm，因此其他專案可以獨立使用它
2. **清晰的邊界** — 串流引擎與 OmniRoute 專屬的 UI/DB 層解耦
3. **效能** — 此引擎沒有 Next.js 相依性，因而可在 CLI／無伺服器環境中更快地冷啟動
4. **版本控制** — `open-sse` 可以按照自己的節奏發佈版本

```json
// package.json
"workspaces": ["open-sse"]
```

## 請求管線

每個 LLM 請求都會流經一個**五階段管線**：

```
                              ┌──────────────┐
   HTTP 請求                   │  1. 路由      │   組合解析、模型選擇
   （Next.js 路由）             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. 轉譯     │   格式轉換（OpenAI ↔ Claude ↔ Gemini）
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. 執行     │   提供者執行器、HTTP、重試、斷路器
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. 串流     │   SSE 轉換、背壓
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. 記錄     │   使用量追蹤、呼叫日誌、錯誤分類
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP 回應（SSE 或 JSON）
```

### 階段 1：路由（services/combo.ts）

**進入點**：`services/combo.ts` 中的 `handleComboChat()`

將請求解析為具體的 `(provider, model, account, credentials)` 元組：

- 依 ID 查詢組合（或為 `auto/*` 模型建立虛擬組合）
- 套用路由策略（優先順序、權重、輪詢等）
- 篩除狀態不健康的提供者（斷路器）
- 選擇下一個可用的目標

對於 `auto/*` 模型，此階段還會：

- 執行**十六因素評分**演算法（`services/autoCombo/`）
- 根據健康狀態、成本、延遲等因素選擇一組 `provider+model`

### 階段 2：轉譯（translator/）

如果來源格式（例如 OpenAI）與目標格式（例如 Claude）不同，請求將會被**轉譯**：

- 系統提示詞 → 系統訊息
- 工具定義 → 提供者專屬的工具格式
- 推理／思考參數 → 提供者專屬的對應參數
- 訊息角色正規化（對非 OpenAI 提供者將 `developer` → `system`）

`translator/index.ts` 公開以下項目：

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 階段 3：執行（executors/）

**進入點**：`getExecutor(providerId).execute(request, options)`

所有提供者都會透過 `getExecutor()` 工廠的後備機制使用 `DefaultExecutor`（`executors/default.ts`）。執行器會：

- 建構上游 URL（`buildUrl()`）
- 新增提供者專屬的標頭（`buildHeaders()`）
- 轉換請求主體（`transformRequest()`）
- 傳送 HTTP 請求，並支援重試及指數退避
- 必要時處理身分驗證重新整理（OAuth 提供者）

所有執行器都會擴充 `BaseExecutor`（`executors/base.ts`，1170 LOC），其提供：

- 通用重試邏輯
- Proxy 整合
- 斷路器整合
- 使用量記錄掛鉤

### 階段 4：串流（utils/stream.ts）

對於串流回應，執行器會傳回一個 **ReadableStream**。處理常式會：

- 透過 SSE 轉換器進行管線傳輸（`createSSETransformStreamWithLogger`）
- 套用心跳 ping 以偵測失效的連線
- 妥善處理用戶端中斷連線（`pipeWithDisconnect`）
- 對非串流用戶端將 SSE → JSON

對於非串流回應，執行器會傳回已剖析的 JSON 物件，並將其原封不動地傳遞下去。

### 階段 5：記錄（services/usage.ts）

回應後（無論成功或失敗），都會記錄使用情況：

- 回應中的 `prompt_tokens`、`completion_tokens`、`cached_tokens`
- 根據定價資料計算的 `cost_usd`
- `latency_ms`、`status`，以及失敗時的 `error_class`
- 持久儲存至 `usage_history` 資料表

呼叫日誌成品（若已啟用）會寫入 `${DATA_DIR}/call_logs/`。

## 關鍵文件深入探討

### chatCore.ts （5977 行）

這**主請求處理程序**。儘管它的規模很大，但它具有清晰的結構：

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

儘管它是一項龐大的功能，但它被組織成**評論部分**映射到 5 級管道。

### combo.ts (4456 LOC)

這**路由引擎**將組合解析為有序目標。

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

支援**22種路由策略**（參見`src/shared/constants/routingStrategies.ts`）：

| 策略                | 行為                                                       |
| ------------------- | ---------------------------------------------------------- |
| `priority`          | 第一目標有序列表                                           |
| `weighted`          | 按每個目標權重的機率                                       |
| `round-robin`       | 按順序循環瀏覽目標                                         |
| `context-relay`     | 跨目標傳遞上下文                                           |
| `fill-first`        | 在進入下一步之前先填滿配額                                 |
| `p2c`               | 兩種選擇的力量                                             |
| `random`            | 均勻隨機                                                   |
| `least-used`        | 選擇最近使用次數最少的一個                                 |
| `cost-optimized`    | 最便宜的健康目標優先                                       |
| `reset-aware`       | 了解提供者重置窗口                                         |
| `reset-window`      | 重置基於視窗的路由                                         |
| `expiry-first`      | 先使用額度到期未使用的帳戶                                 |
| `headroom`          | 最剩餘的配額空間優先                                       |
| `quota-weighted`    | 跳過耗盡的帳戶，然後按剩餘配額提取÷飛行負載                |
| `strict-random`     | 真正統一（無品質加權）                                     |
| `auto`              | 使用 16 個因素評分 (`autoCombo/`)                          |
| `lkgp`              | 最後已知的良好提供者優先                                   |
| `context-optimized` | 最適合長上下文請求                                         |
| `cache-optimized`   | 將每個可重複使用的提示前綴固定到同一帳戶（提示快取命中）   |
| `fusion`            | 並行扇出到面板，然後透過法官進行合成（`fusion.ts`）        |
| `pipeline`          | 鍊式步驟—每個目標的輸出都會饋送到下一個目標                |
| `jev`               | 選擇加入： TypeSafe Jev 承認哪些排名條目運行；否則你的訂單 |

### base.ts (1170 LOC)

這**抽象執行者**每個執行器類別都擴展（直接或透過`DefaultExecutor`和其他子類別）。它包含：

- `buildUrl()` —預設URL構造（子類別覆蓋自訂）
- `buildHeaders()` —預設標頭（auth、內容類型）
- `transformRequest()` —預設透傳
- `execute()` —與retry/backoff/breaker的主HTTP循環

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

特定於提供者的行為（auth 標頭、基本URL、版本標頭）是透過提供者註冊表配置的，而不是單獨的執行程序類別。

## 執行器（150 個模組）

大多數情況下每個提供者一個文件。執行器類別都擴展了`BaseExecutor`並覆蓋了不同的部分；其他模組是每個提供者的幫助程式（工具模式、 fetch/TTS適配器、怪異處理程序）。

### 常見模式

提供者透過`getExecutor(providerId)`解析，它會傳回配置的執行器。 OpenAI/Anthropic-compatible提供者使用`DefaultExecutor` (`executors/default.ts`)。特定於提供者的行為（基本URL、驗證標頭、 API版本）在`open-sse/config/providers/`中配置，而請求正文轉換在`open-sse/translator/`中處理。

**客製化URL**透過提供者配置設定：

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**自訂授權**透過提供者註冊表的身份驗證設定（API金鑰、 OAuth、標頭設定檔）進行處理。

**自訂請求正文**轉換（例如， Anthropic將`system`與`messages`分開）在`open-sse/translator/`中按提供者註冊。

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

解析透過`ExecutorRegistry` (`executors/registry.ts`)：每個專用執行器都在`executors/index.ts`的內建表中聲明，並在模組載入時透過`registerExecutor(alias, instance)`註冊； `getExecutor()`查閱註冊表，並為沒有專門條目的任何提供者回退到記憶的`DefaultExecutor` 。完整別名→執行器映射的特徵是黃金測試`tests/unit/executor-map-golden.test.ts`。

## 轉譯器

在 **3 種格式**之間進行轉譯：OpenAI、Anthropic、Gemini，以及新的 Responses API。

### 何時進行轉譯

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

常見轉譯：

- `OpenAI → Anthropic`：獨立的 `system` 欄位、`x-api-key` 標頭
- `OpenAI → Gemini`：使用 `contents` 取代 `messages`，以及 `systemInstruction`
- `OpenAI → Responses API`：`input` 陣列、`previous_response_id` 狀態

### 已處理的邊緣情況

- `developer` 角色 → 對非 OpenAI 轉換為 `system`
- `system` 角色 → 對 GLM/ERNIE 合併至第一則使用者訊息
- `json_schema` → Gemini 的 `responseMimeType` + `responseSchema`
- `tools` → 提供者特定的工具格式
- 思考參數（o1、Claude）→ 提供者特定的對應項目

## MCP 伺服器

`open-sse/mcp-server/` 實作了 **Model Context Protocol** 伺服器：

- **110 項工具**（提供者管理、組合、記憶體、快取、壓縮、代理、技能、遊戲化、外掛程式、Notion、Obsidian、本機語料庫）
- **3 種傳輸方式**：stdio、SSE、Streamable HTTP
- **33 個範圍**，用於細粒度授權

### 工具註冊

工具會以獨立檔案的形式註冊於 `open-sse/mcp-server/tools/`，每個檔案都會匯出名稱、結構描述、處理常式及範圍：

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### 傳輸方式

```ts
// stdio（CLI 用法）
startMcpStdio(server);

// SSE（以 HTTP 為基礎的串流）
startMcpSse(server, port);

// Streamable HTTP（現代 MCP）
startMcpStreamable(server, port);
```

### 授權

每次工具呼叫都會經過範圍檢查（`open-sse/mcp-server/auth/`）：

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## 轉換器

`open-sse/transformer/` 會在 **Chat Completions** 與 **Responses API** 格式之間進行轉換。

### 為什麼需要獨立的轉換器？

Responses API 是 OpenAI 的新格式，支援**具狀態的對話**（`previous_response_id`）。當用戶端傳送 Responses 請求時，OmniRoute 會：

1. 在內部將 Responses → Chat Completions
2. 傳送至提供者（任何支援 Chat Completions 的提供者）
3. 將回應轉換回 Responses 格式
4. 將轉換後的回應以串流方式傳送至用戶端

轉換器（`transformer/responsesTransformer.ts`）提供：

```ts
createResponsesApiTransformStream(): TransformStream
```

這會處理：

- `response.output_item.added` 事件
- `response.output_text.delta` 事件
- `response.completed` 事件
- 工具呼叫對應（`function_call` ↔ `tool_calls`）

## 配置

`open-sse/config/`持有配置層：

| 文件                          | 目的                               |
| ----------------------------- | ---------------------------------- |
| `providerRegistry.ts`         | 394 個提供者目錄上的聊天模型註冊表 |

### 提供者註冊架構

```ts
interface ProviderConfig {

```

模組載入時的Zod驗證可確保所有提供者配置均有效。

## 效能限制

路由引擎有嚴格的效能預算：

| 操作                             | 目標  | 測量條件           |
| -------------------------------- | ----- | ------------------ |
| 組合解析                         | <10ms | 針對 50 個目標     |
| 速率限制檢查                     | <1ms  | 記憶體內權杖桶     |
| 模型系列備援                     | <5ms  | 已快取的系列定義   |
| 請求路由分派                     | <2ms  | 熱路徑             |
| **路由熱路徑中不得有阻塞式 I/O** | —     | 全部採用非同步處理 |

## 反模式

❌ **在 `combo.ts` 中進行同步資料庫呼叫** — 預先計算並快取
❌ **在處理常式中實作重試邏輯** — 使用韌性服務提供的 `retry()`
❌ **直接存取提供者設定** — 使用 `providerRegistry` 的 getter
❌ **硬編碼備援鏈** — 在 `modelFamilyFallback.ts` 中定義
❌ **在並行請求之間變更狀態** — 僅使用請求範圍的上下文

## 新增元件

### 新增服務

1. 建立職責明確的 `open-sse/services/[serviceName].ts`
2. 匯出主要處理函式及所有常數
3. 在 `tests/unit/services/[serviceName].test.mjs` 中新增單元測試
4. 整合至 `handlers/chatCore.ts` 中的請求管線（若與路由相關）

3. 新增至 `executors/index.ts` 工廠
4. 為執行器新增單元測試

3. 在 `mcp-server/index.ts` 中註冊工具

5. 新增單元測試
