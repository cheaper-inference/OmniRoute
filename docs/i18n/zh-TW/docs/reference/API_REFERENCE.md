## 聊天補全

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### 自訂標頭

| 標頭                     | 方向 | 說明                                                                                                                                                   |
| ------------------------ | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | 請求 | 設為 `true` 以略過快取                                                                                                                                 |
| `x-omniroute-no-memory`  | 請求 | 設為 `true`，為此請求略過記憶體與技能注入（行為與停用快取相同；可避免每次呼叫的權杖／成本額外負擔）                                                    |
| `X-OmniRoute-Progress`   | 請求 | 設為 `true` 以接收進度事件                                                                                                                             |
| `X-Session-Id`           | 請求 | 用於外部工作階段親和性的黏著工作階段金鑰                                                                                                               |
| `x_session_id`           | 請求 | 也接受底線變體（直接 HTTP）                                                                                                                            |
| `X-OmniRoute-Session-Id` | 請求 | 呼叫端提供的工作階段／對話標籤（也會提供給記憶體）。若存在，將逐字保存至 `call_logs.session_tag`，以便依工作階段歸屬成本 (#8249)；若缺少，絕不自動產生 |
| `Idempotency-Key`        | 請求 | 去重金鑰（5 秒視窗）                                                                                                                                   |
| `X-Request-Id`           | 請求 | 替代去重金鑰                                                                                                                                           |
| `x-omniroute-connection` | 請求 | 依 ID 將單一模型請求固定至一個提供者連線（帳戶）— 請參閱[依請求固定帳戶](#account-pinning-per-request)                                                 |
| `X-OmniRoute-Cache`      | 回應 | `HIT` 或 `MISS`（非串流）                                                                                                                              |
| `X-OmniRoute-Idempotent` | 回應 | 若已去重則為 `true`                                                                                                                                    |
| `X-OmniRoute-Progress`   | 回應 | 若已開啟進度追蹤則為 `enabled`                                                                                                                         |
| `X-OmniRoute-Session-Id` | 回應 | OmniRoute 使用的實際工作階段 ID                                                                                                                        |
| `X-OmniRoute-Request-Id` | 回應 | 請求關聯 ID（若已知）                                                                                                                                  |
| `X-OmniRoute-Version`    | 回應 | OmniRoute 建置版本（始終存在）                                                                                                                         |
| `X-OmniRoute-Cost-Saved` | 回應 | 快取命中所避免的美元成本（僅限快取命中）                                                                                                               |
| `X-OmniRoute-Decision`   | 回應 | 路由追蹤：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` 是組合策略；若為非組合請求則為 `single`）— 完成回應中始終存在                  |

> Nginx 注意事項：如果您依賴含底線的標頭（例如 `x_session_id`），請啟用 `underscores_in_headers on;`。

#### 針對每個請求釘選帳戶

當提供者有多個連線（帳戶或金鑰）時，OmniRoute 通常會透過其帳戶選擇策略挑選其中一個。
請求也可以改用 `x-omniroute-connection` 標頭，釘選某個特定連線：

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **如何找到 id。** 在儀表板中開啟提供者頁面
  （**儀表板 → 提供者 → <provider>**），然後按一下連線資料列上的 `xxxxxxxx…` id 標籤，
  即可複製完整的連線 id。
- **哪些請求會採用它。** `/v1/chat/completions`、`/v1/messages` 和 `/v1/responses`
  上的單一模型請求（`provider/model`）。組合會忽略此標頭：請改為透過各組合步驟本身的連線，
  為每個步驟釘選帳戶。
- **釘選是嚴格指定，而非偏好設定。** 系統只會使用被釘選的連線。請求中的失敗會記錄該帳戶的冷卻狀態，
  但**不會**輪替至同一提供者的其他同層級帳戶。
- **冷卻和配額狀態會解除釘選。** 當被釘選的連線正處於冷卻狀態、配額已用盡，
  或遭配額政策封鎖時，後續請求會改用該提供者的其他連線，其行為與未釘選的流量完全相同。
- **未知或已停用的 id 會導致失敗。** 如果某個 id 不在提供者的有效集區中（已刪除、
  已停用，或屬於其他提供者），就不會有符合資格的帳戶，因此請求將會失敗，
  而不會悄悄路由至其他地方。

Claude Code 透過 `ANTHROPIC_CUSTOM_HEADERS` 傳送自訂標頭。請將它放入
`~/.claude/settings.json` 的 `env` 區塊中，或放入專案層級的 `.claude/settings.json`，
以便針對每個專案釘選不同的帳戶：

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

來源：`src/sse/handlers/chat.ts`（讀取標頭）、`src/sse/services/auth.ts` 和
`src/sse/services/sessionAffinityPin.ts`（解除釘選及不在集區中的檢查）。

> **成本遙測標頭：** 非串流的成功回應也會包含 `X-OmniRoute-*` 成本遙測標頭集——`X-OmniRoute-Response-Cost`（美元，固定為小數點後 10 位；免費或未定價時為 `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit` 和 `X-OmniRoute-Fallback-Attempts`（僅在 > 0 時包含），以及 `X-OmniRoute-Request-Id` 和 `X-OmniRoute-Version`。這些標頭會由聊天補全、`/v1/responses`、`/v1/messages`，**以及媒體端點**發出——`/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations` 和 `/v1/moderations`（成本一律為 `0`）。若有可用的定價資料，媒體成本會依模態計算（每張圖片、每秒、每個字元、每個搜尋單位）；否則為 `0`（開放式失敗）。

> **快取命中的成本語意：** 發生語意快取命中時（`X-OmniRoute-Cache-Hit: true`），不會進行上游呼叫，因此 `X-OmniRoute-Response-Cost` 為 `0.0000000000`（提供此次快取命中服務的**增量**成本）。原始／原本會產生的成本會另行記錄於 `X-OmniRoute-Cost-Saved`。計費系統應加總 `X-OmniRoute-Response-Cost`（快取命中不產生成本）；快取分析則可以彙總 `X-OmniRoute-Cost-Saved`。

## 獨佔式受管理工作階段租約

獨佔式受管理工作階段租用是一項選擇加入、與用戶端無關的路由契約：一個作用中的擁有者會持有一個符合資格的 OmniRoute 連線。它不會租用模型、不要求 OAuth、不識別特定用戶端，也不要求特定提供者。

用於驗證身分的 API 金鑰必須具有 `lease:exclusive` 範圍，以及明確且非空的 `allowedConnections` 清單。資料庫異動邊界會在建立金鑰和部分更新時，同時強制執行這兩個欄位的要求。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

成功的取得、續約和釋放回應會公開時間戳記、`state`，以及確切的正整數 `generation`，但絕不公開選取的連線或憑證。續約和釋放會在 JSON 主體中提供 generation：

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

作用中的租約擁有者可以明確請求其目前繫結的隱私安全顯示中繼資料：

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

這項選擇加入的狀態操作會在單一資料庫交易中，由不透明的擁有者、已驗證身分的受管理 API 金鑰，以及確切的作用中 generation 共同設置防護。`displayName` 僅為經過修剪的已設定連線名稱；若不存在安全的已設定名稱，則為 `null`。OmniRoute 絕不會以電子郵件或產生的帳戶身分取代它。提供者值是非敏感的顯示標籤，絕不會是產生的相容提供者識別碼。憑證、權杖、Cookie、原始連線或 API 金鑰 ID、擁有者雜湊、防護密鑰，以及內部路由資料均會排除。

使用錯誤金鑰、錯誤擁有者、過時 generation、缺少、已到期、已釋放及已失效的查詢，全都會回傳相同的 `409 LEASE_FENCE_STALE` 錯誤，且不包含連線中繼資料。收到容量等待回應的用戶端沒有可供檢查的作用中繫結。當路由轉換作用中的租約時，相同的 generation 會維持有效，而狀態會以不可分割方式回傳新的繫結，絕不回傳舊的繫結。現有用戶端不受影響，因為取得、續約、釋放和等待回應會維持其原有格式。

此伺服器契約不會變更原版 OpenAI Codex 的 `/status`。原版 Codex 目前會報告其模型提供者及內建的驗證／帳戶狀態，但不會呈現任意自訂提供者帳戶中繼資料；未來的用戶端整合必須呼叫此操作，並決定如何顯示 `connection.displayName`。

之後，每個受管理的推論請求都會提供這兩個控制標頭：

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

在每次支援的上游嘗試之前，會立即對確切的擁有者、generation、作用中連線和已驗證身分的 API 金鑰進行防護檢查。即使另一個金鑰允許相同的連線，使用該金鑰重播擁有者和 generation 仍會失敗。原始擁有者值不會被持久保存、不會記錄於日誌、不會保留在請求快照中，也不會轉送至上游。

暫時性競用會回傳 HTTP `429`、`Retry-After`，以及：

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

此回應僅表示一般的合格集合並非空集合，且每個可用候選連線都由其他擁有者的作用中租約持有。不支援的模型／提供者、原則不符、冷卻、配額、健康狀態及其他一般資格失敗，會維持其現有的 OmniRoute 回應。

### `x-omniroute-compression`

針對單一請求覆寫壓縮計畫。其優先順序最高——高於路由組合覆寫、作用中設定檔、自動觸發，以及面板的預設值。可用值：

| 值            | 效果                                                              |
| ------------- | ----------------------------------------------------------------- |
| `off`         | 此請求不進行壓縮。                                                |
| `default`     | 由面板衍生的預設設定檔（忽略作用中設定檔）。有損引擎會保持關閉。  |
| `safe`        | 僅進行重複內容刪除和空白摺疊。                                    |
| `allow-lossy` | 此請求保留操作人員的計畫，包括摘要和樣式重寫。                    |
| `engine:<id>` | 啟用時使用單一引擎，例如 `engine:rtk`。針對該引擎依請求選擇加入。 |
| `<combo>`     | 具名組合；先依名稱比對（不區分大小寫），再依 ID 比對。            |

注意事項：

- 未知的值會被忽略（絕不會因此拒絕請求）；解析程序會回退至一般的操作人員優先順序。
- 如果多個組合使用相同名稱，請傳遞組合的 **id**，以確保比對結果明確。
- 名稱為 `off` 或 `default` 的組合無法透過名稱選取（會先解讀這些關鍵字）；請使用其 ID 參照這類組合。
- 壓縮主開關是硬性閘門：全域停用壓縮時，此標頭無法啟用壓縮。

套用的計畫會在回應標頭中回顯：

```
X-OmniRoute-Compression: <mode>; source=<source>
```

其中 `<source>` 為 `request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default` 或 `off` 其中之一。

## 嵌入

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

可用的提供者：Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

目錄 ID 的格式為 `provider/model`（範例：`jina-ai/jina-embeddings-v5-omni-small`）。登錄檔中出現的不含提供者前綴的 Jina 模型 ID（例如 `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）也可解析。Jina 的嵌入／重排序／分類／分段功能會優先使用儀表板中的 `jina-ai` 憑證；只有在不存在儀表板金鑰時，才會改用 `JINA_AI_API_KEY`。`jina-reader` 卡片僅供 Reader／`r.jina.ai` 使用（`POST /v1/web/fetch`），絕不提供嵌入或重排序服務。

宣告支援多模態的登錄檔模型也接受最多 32 個提供者中立的結構化
項目。媒體項目類型為 `text`、`image`、`audio`、`video` 和 `document`。其媒體 `source`
可以是 `{"type":"url","url":"https://..."}`，或
`{"type":"base64","data":"...","media_type":"..."}`。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`
以及系列別名 `jina-ai/jina-embeddings-v5-omni` → omni-small）也接受 Jina 原生的
EmbeddingsV5Request 文件，並將其**完整轉送**至 `https://api.jina.ai/v1/embeddings`：

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

原生的 `{ image | audio | video | pdf }` 值可以是公開的 HTTPS URL、`data:` URI，或原始
base64。OmniRoute 不會將這些物件字串化，也不會擷取原生圖片 URL——Jina 會自行擷取
公開媒體。額外的 Jina 欄位（`task`、`normalized`、`truncate`、`embedding_type`）會被
轉送。僅支援文字的 Jina SKU 仍會拒絕非文字文件。

安全性與傳輸限制：

- 遠端媒體 URL 必須是公開的 HTTPS。標準 `{type,source:url}` 項目會在伺服器端擷取
  （重新驗證重新導向、逾時、大小限制、公開 DNS、連線固定），並在呼叫提供者前
  內嵌。Jina 原生的 `{image:"https://..."}` 項目會在經過相同的公開 HTTPS 檢查後
  原樣轉送；Jina 會擷取該 URL。
- 內嵌 base64 媒體的限制為每個項目解碼後 8 MiB，整個請求解碼後合計 16 MiB。

提供者轉換（標準項目絕不會原樣轉送）：

- Jina 多模態模型：每個頂層項目都會變成一個以模態為鍵的物件
  （`text`／`image`／`audio`／`video`／`pdf`），內嵌媒體使用資料 URI；每個
  頂層項目產生一個向量。
- Gemini Embedding 2 系列：一個頂層陣列會變成單一原生
  `models/{model}:embedContent` 請求，並使用 `content.parts`（`text` 或 `inline_data`）。
- llama.cpp（`llama-cpp/<model>`，本機伺服器載入的任何模型）：標準 `text` 項目
  會變成純字串，而 `image`／`audio`／`video` 各自會變成一個
  `{"content": [part]}` 物件，使用 llama-server 的聊天內容部分（`image_url`、
  `input_audio`，格式為 `wav`／`mp3`／`flac`，以及 `input_video`）並內嵌資料；每個
  頂層項目產生一個向量。伺服器必須使用 `--embedding --mmproj …` 執行；若沒有投影器，
  伺服器本身會拒絕媒體。不支援 `document`。
- 沒有明確模態中繼資料的未知／動態模型會以 HTTP 400 拒絕結構化輸入。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

不支援的模型／模態組合會傳回 HTTP 400，而不會強制轉換項目。舊版字串／權杖請求中的
非輸入擴充欄位會繼續原樣傳遞。

```bash
# 列出所有嵌入模型
GET /v1/embeddings
```

## 圖片生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

可用的提供者包括 OpenAI (GPT Image 2)、xAI (Grok Image)、Together AI (FLUX)、Fireworks AI、Nebius (FLUX)、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（本機）、ComfyUI（本機）。

`n` 會在 `data[]` 中傳回 `n` 張圖片。若提供者的上游 API 每次呼叫僅傳回一張圖片
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI），系統會分別發出 `n` 次上游呼叫，最多同時處理 4 次。
固定的 `seed` 會依呼叫索引遞增（`seed`、`seed + 1`、…），因此圖片會有所不同，同時仍可
重現。`n` 的上限為 10。只要任何呼叫失敗，整個請求就會失敗。扇出格式清單為
`open-sse/handlers/imageGeneration/fanOut.ts` 中的 `SINGLE_IMAGE_FANOUT_FORMATS`。

ZenMux 會重複使用現有的 API 金鑰連線，並接受 `zenmux/` 或 `zm/` 前綴：

- `zenmux/openai/gpt-image-2` 使用 ZenMux 的 OpenAI Images API。選項包括 `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background` 及 `response_format`。
- 其他發行商（例如 `zm/meta/muse-image-1.0`）會使用 ZenMux 的 Vertex AI `:predict`
  端點。`n` 對應至 `sampleCount`，`aspect_ratio` 對應至 `aspectRatio`，而 `image_size`
  （`1K`、`2K`、`4K`）對應至 `sampleImageSize`。像素 `size` 僅提供長寬比，
  不保證像素尺寸。支援的比例、解析度和數量會依模型而異。
- `zm/inclusionai/ming-image-0.1-design` 會自行選擇尺寸。請省略 `size`、
  `aspect_ratio` 和 `image_size`；明確指定這些值會傳回 HTTP 400。可透過 `output_format`
  請求 PNG、JPEG 和 WebP。

此整合支援文字生成圖片，不支援參考圖片編輯。Vertex
輸出會正規化為 `data[].b64_json`；當只有圖片位元組可用時，`response_format: "url"` 會傳回上游
HTTPS URL 或 base64 資料 URL。空白或遭篩選的輸出會傳回錯誤，而不是空白的成功回應。模型存取權限取決於 ZenMux 帳戶。
請參閱 [ZenMux 的 Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) 和
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)。

```bash
# 列出所有圖片模型
GET /v1/images/generations
```

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` 會透過 `provider/model` 前綴選取 OCR 提供者；不含前綴的模型 ID（例如
`mistral-ocr-latest`）會解析至其已註冊的提供者，而省略 `model` 時則預設使用
Mistral（`mistral-ocr-latest`）。已註冊的提供者（`open-sse/config/ocrRegistry.ts`）：

| 提供者 ID                     | 模型 ID              | `model` 值                                                        | 備註                                                                                   |
| ----------------------------- | -------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（或不含前綴的 `mistral-ocr-latest`） | 同步——直接傳回單次上游呼叫的回應。                                                     |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                       | 非同步上游（`analyze` + 輪詢）——請參閱下文。                                           |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                           | 同步，透過 Vertex AI 的 `openapi/chat/completions` 合作夥伴端點——驗證/URL 請參閱下文。 |

三個提供者都會以相同的 Mistral 格式回應本文：

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence 輪詢流程

Azure Document Intelligence 的 `analyze` API 是非同步的：初始請求會傳回
`Operation-Location` 標頭而非本文，因此必須輪詢結果。處理常式
（`open-sse/handlers/ocr.ts`）會每秒輪詢該 URL，最多嘗試 30 次；若輪詢回應不是 `ok`
或狀態為 `"failed"`，則會快速失敗（不會繼續輪詢）；如果作業在用盡嘗試次數後仍在執行，
則會傳回 `504`。最終的 Azure 回應會先正規化為 Mistral 使用的相同 `pages`/`markdown`
格式，再傳回給呼叫端，因此用戶端程式碼不需要針對該提供者進行特殊處理。

### Vertex AI DeepSeek OCR 驗證與端點解析

`vertex-deepseek-ocr` 會重複使用 OmniRoute 已支援用於聊天/圖片流量的相同 Vertex AI 驗證
（`open-sse/executors/vertex.ts`）：連線的 API 金鑰可以是服務帳戶 JSON 憑證
（透過 JWT-bearer 流程交換為短期 OAuth 存取權杖），也可以是直接使用的既有 OAuth 存取權杖。
上游端點 URL 是 Vertex 的通用 `openapi/chat/completions` 合作夥伴端點，並根據連線的專案和
區域建構——明確指定的 `providerSpecificData.project`/`providerSpecificData.region` 一律優先；
否則專案會從服務帳戶 JSON 的 `project_id` 衍生，而區域預設為 `us-central1`。這兩項解析都在
`open-sse/handlers/ocr.ts`（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`）中進行，
並由 `src/app/api/v1/ocr/route.ts` 在分派至 `handleOcr` 前使用。

## 列出模型

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ 以 OpenAI 格式傳回所有聊天、嵌入與圖片模型及組合
```

### 模型價格（`pricing`）

當 OmniRoute 知道模型的價格時，項目會包含 `pricing` 物件。價格來自成本核算所使用的定價表：內建預設值、同步的價格，以及透過 `/api/pricing` 設定的覆寫值。這些是牌價，因此訂閱制提供者也會顯示每個 token 的價格。

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| 欄位                                                            | 單位                               | 備註                                                                                                        |
| --------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | 每個 token 的美元價格，十進位字串  | 與 OpenRouter 相容，絕不使用指數表示法。兩個快取欄位僅在有快取價格時才會出現。                              |
| `input`, `output`, `cached`, `cache_creation`                   | 每 100 萬個 token 的美元價格，數值 | 來自較早目錄版本的欄位，為現有用戶端保留。當定價列包含 `reasoning` 和 `long_context` 時，也會顯示這些欄位。 |

- **組合**會採用其第一個可見目標的價格。內建的 `auto/*` 組合會在請求時選擇
  目標，因此不包含 `pricing`。
- **免費模型**的價格為零時會顯示 `"0"`（以及 `0`）。若模型沒有定價列，
  但目錄將其標記為免費（`free: true`），或內建免費模型目錄中列出了該模型，
  也會顯示 `"0"`。
- **未知價格：**該項目沒有 `pricing` 鍵。
- **按額度計費的提供者**（例如 Kiro）按請求計費，而不是按 token 計費。其
  項目會保留先前已有的每 100 萬 token 數值欄位，且不包含每個 token 的字串欄位。
- **變體**（推理強度 ID、停用思考的別名、探索與閘道鏡像）
  會複製其路由目標模型的價格。
- 這些欄位只包含基礎費率。長上下文級距（數值型 `long_context` 欄位）與
  服務級別乘數（例如 Codex fast 或 flex）不會變更 `prompt` 或
  `completion`。
- 對所有驗證方式而言，此物件都相同，包括使用 `x-api-key` 與
  `anthropic-version` 的 Anthropic 風格請求（回應仍為 `{ "object": "list",
"data": [...] }`）。實作位置：`src/app/api/v1/models/catalogPricing.ts`。

### 模型 ID 前綴（`?prefix=`）

大多數模型都會以**提供者前綴**呈現。所取得的前綴由
`MODELS_CATALOG_PREFIX_MODE` 功能旗標控制，也可以透過查詢參數針對**每個請求**覆寫——這對於希望取得簡潔清單、但又不想變更所有使用者共用的伺服器全域設定之用戶端很有用：

```bash
GET /v1/models?prefix=alias        # 每個模型一個 ID——簡短別名前綴
GET /v1/models?prefix=dual         # 兩種形式（伺服器預設值）
GET /v1/models?prefix=canonical    # 僅使用完整提供者 ID 前綴
```

| 模式        | 輸出                                                     | 備註                                                                                                                                           |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **與** `claude/claude-sonnet-4-6` | **預設值。** 兩個 ID 都會路由至同一個模型；保留兩者是為了讓硬編碼任一形式的用戶端設定繼續運作。目錄大小大約會增加一倍。                        |
| `alias`     | `cc/claude-sonnet-4-6`                                   | 每個模型一個項目。沒有不同別名的提供者仍會輸出其項目，因此不會遺漏任何內容。                                                                   |
| `canonical` | `claude/claude-sonnet-4-6`                               | 每個模型在完整提供者 ID 前綴下各有一個項目。沒有不同別名的提供者（例如 `antigravity/…`、`agy/…`）也會在此輸出其唯一 ID，因此不會遺漏任何內容。 |

即使沒有查詢參數，也可以辨識 `dual` 模式的鏡像：它會包含一個指向主要 ID 的 `parent`
欄位。

呈現模型選擇器的用戶端應請求 `?prefix=alias`——這也是
[OmniCopilot VS Code 擴充功能](../guides/VSCODE-COPILOT.md)所採用的方式。

### 探索篩選器（`?capability=`、`?min_context=`、`?kind=`、`?q=`）

`GET /v1/models` 接受選擇啟用的探索篩選器。若未使用任何篩選器，回應
不會改變。這些篩選器會縮小呼叫端原本可見的目錄範圍（會先套用 API 金鑰權限），
而且會在 OpenAI 風格的 `limit` / `after` 分頁之前執行：

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 列出的每項能力都必須為 true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # 目錄的 `type`；沒有此欄位的列視為 `chat`
GET /v1/models?q=sonnet&limit=10                           # 對 ID 或名稱進行不區分大小寫的比對
```

| 參數          | 值                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | 非負整數，會與 `context_length` 比較                                                                |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1–200 個字元                                                                                        |

未知的值，或不是非負整數的 `min_context`（例如 `1.5`），
會傳回 HTTP `400`，且訊息會列出有效值。實作位置：
`src/app/api/v1/models/catalogFilters.ts`。

### 模型候選清單（`POST /v1/models/query`）

`POST /v1/models/query` 會從同一個目錄傳回簡短且具確定性的清單，其驗證與每個金鑰的可見性皆與 `GET /v1/models` 相同：

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

每個欄位皆為選填。`capabilities` 與 `exclude` 可接受陣列或以逗號分隔的字串；
`max_output` 會與 `max_output_tokens` 比較。結果會先依 `owned_by` 排序，再依 `id` 排序。
`limit` 預設為 `20`，高於 `100` 的值會被限制為 `100`。無效的 JSON、未知欄位或無效值會傳回 HTTP `400`。

### 個別隱藏的聊天模型

在提供者頁面上標示為 **隱藏** 的模型會從目錄中排除，且在明確要求該模型時，
會以 HTTP `404` / `model_not_found` 拒絕請求。此檢查會使用解析後的
提供者與模型，包括提供者別名、相容提供者的節點前綴，以及
連線預設值。組合模型會略過隱藏的目標，並可使用可見的同層模型；當沒有
可執行的目標時，會傳回相同的錯誤代碼。取消隱藏會在下一個
請求時生效。僅限影像的可見性覆寫不會隱藏具有相同 ID 的聊天模型。

這項個別模型設定獨立於
[模型公開允許／拒絕清單](../routing/MODEL_EXPOSURE_LIST.md)；後者會篩選目錄中
公開的模型與自動路由候選項目，同時保留明確分派功能。API 金鑰的模型
權限仍會獨立套用。預設的目錄前綴模式仍為 `dual`。

### 無思考模型變體

對於支援思考功能的 Claude 模型，`/v1/models` 也會公開一個 **無思考** 變體，其 ID 會加上 `claude-3-omniroute-no-thinking/` 前綴：

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

選取此 ID（例如在一律附加 `thinking` 區塊的 Claude Code 設定中）時，會解析回實際的 `<provider>/<model>`，並停用推理——在 `/v1/messages` 路徑上使用 `thinking:{type:"disabled"}`，或在 `/v1/chat/completions` 路徑上移除 `reasoning`／`reasoning_effort` 欄位。此變體只會列出支援思考功能**且**接受 `disabled` 的 Claude 系列模型（因此，例如會拒絕 `disabled` 且僅支援自適應模式的模型會被排除）。營運人員可透過 `ModelSpec.noThinkingAlias`，針對每個模型強制啟用或停用此變體。

## ElevenLabs 音訊生成

使用您的 ElevenLabs API 金鑰，在 OmniRoute 中設定 `elevenlabs` 提供者連線。
用戶端使用其 **OmniRoute** 金鑰進行驗證（`Authorization: Bearer $OMNIROUTE_API_KEY`）；
閘道會以 `xi-api-key` 提供已儲存的提供者金鑰。切勿將 ElevenLabs 金鑰當作閘道 Bearer 權杖傳送。

| 方法 | 路徑                        | 回應                          | API 金鑰端點類別 |
| ---- | --------------------------- | ----------------------------- | ---------------- |
| POST | `/v1/sound-generation`      | 原生音訊位元組                | `elevenlabs`     |
| POST | `/v1/music`                 | 原生音訊位元組                | `music`          |
| POST | `/v1/music/stream`          | 串流音訊位元組                | `music`          |
| POST | `/v1/music/detailed`        | 原生 multipart 音訊與作曲計畫 | `music`          |
| POST | `/v1/music/detailed/stream` | 原生 SSE 中繼資料與音訊區塊   | `music`          |
| POST | `/v1/music/plan`            | JSON 作曲計畫                 | `music`          |

這些端點補充了現有的 `/v1/audio/speech`、`/v1/audio/transcriptions`、
`/v1/voices`、`/v1/text-to-speech/{voiceId}` 及 `/v1/speech-to-text` 路由。原生 JSON 欄位
與查詢參數（例如 `output_format` 和 `enable_logging`）會予以保留。
`/v1/music/detailed` 回應會保留其 multipart 邊界；請將其解析為 multipart。
`/v1/music/detailed/stream` 會傳回 `text/event-stream`，其中包含作曲中繼資料及
SSE 事件中的 base64 音訊區塊。全部六條路由皆支援 CORS 預檢。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 簡短音效。持續時間：0.5 至 30 秒。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 音樂持續時間以毫秒表示：3000 至 600000。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

若要以增量方式傳送音訊，請使用具有相同 JSON 主體的 `/v1/music/stream`。作曲功能
僅接受 `prompt` 或 `composition_plan` 其中之一；`/v1/music/plan` 必須提供 `prompt`，
並可選擇接受 `source_composition_plan`。原生結構描述會保留其他提供者欄位，
讓作曲計畫版本及微調選項能夠傳遞至 ElevenLabs。

統一的 `/v1/music/generations` 端點也接受 `elevenlabs/music_v1`、
`elevenlabs/music_v2` 及 `elevenlabs/music_v2_5`。當 ElevenLabs 連線處於作用中時，
這些模型會顯示於音樂目錄中。此端點會傳回
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`。其 `duration` 欄位的單位為
秒，並會對應至 `music_length_ms`；明確指定的 `music_length_ms` 具有優先權。
`instrumental` 會對應至 `force_instrumental`，且原生欄位具有優先權。
若需要串流，請使用原生串流端點；若請求僅由作曲計畫驅動，請使用原生作曲端點。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

在進行上游呼叫之前，會先套用端點、模型、預算及連線限制。原生
路由會原封不動地傳回上游狀態碼與錯誤主體，包括代表方案限制的 `402`
及代表配額限制的 `429`。若存在 `character-cost`、`song-id`、`request-id` 及 `retry-after`
標頭，則會予以保留。免費點數餘額並不保證可存取每個
音樂模型、輸出格式或 API 功能：ElevenLabs 會決定每項請求的使用資格。
統一端點會在 OmniRoute 的標準化錯誤封裝中保留錯誤狀態碼。

上游合約：[音效](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音樂創作](https://elevenlabs.io/docs/api-reference/music/compose)及
[串流音樂詳細資料](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。

```bash
# 重新排序（雲端登錄提供者，或以 "<prefix>/<model>" 表示的 OpenAI 相容提供者節點）
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina 分類（Foundation API 憑證）
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina 分段器
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina 搜尋（s.jina.ai；提供者別名：jina-search、jina-ai、jina）
POST /v1/search      { "query": "...", "provider": "jina-search" }

# 內容審核
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — 傳回 audio/mpeg（或所要求格式）的本文
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS 需要語言和語音：`language` 預設為 "en"；若缺少
# 語音，或使用 OpenAI 內建語音名稱（alloy、nova、…），則會改用 "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# 圖片編輯（multipart）
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# 影片／音樂生成（含提供者前綴的模型 ID）
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **重新排序提供者節點：** `POST /v1/rerank` 也會路由至以 `<node-prefix>/<model>` 定址的 OpenAI 相容提供者節點
> （oMLX、vLLM、Infinity、位於閘道後方的 TEI 等）。迴路
> 節點（`localhost`、`127.0.0.1`、`172.16.0.0/12`）一律符合資格，此外，營運者在
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` 中列出的主機名稱亦符合資格（例如 Docker/Compose 服務名稱，
> 如 `http://reranker:8080/v1`；系統會直接呼叫這些節點，絕不透過 `HTTP(S)_PROXY` 或
> 連線所固定的 Proxy）。位於任何其他
> 主機上的節點（例如區域網路中的機器或 Tailscale 對等節點），只有在營運者啟用
> `RERANK_REMOTE_PROVIDER_NODES` 功能旗標，**且**節點的基礎 URL 通過提供者
> 對外 URL 原則（`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）時才符合資格。
> 記憶體引擎的重新排序步驟會透過
> 迴路呼叫此路由，因此相同規則也適用於 Memory 設定中的 `rerankProviderModel`。
>
> **本機伺服器形式：** 系統會在 `<base>/v1/rerank` 呼叫節點；若傳回 404，則改為呼叫 `<base>/rerank`
> （Infinity、TEI）。上游本文會同時包含 Cohere/OpenAI 拼法（`documents`、
> `return_documents`）與 TEI 拼法（`texts`、`return_text`），而上游回應會
> 正規化為 Cohere 封裝格式：TEI 的裸露 `[{index, score, text}]`、精簡閘道傳回的 `{results: [{index, score}]}`
> ，以及 Voyage 風格的 `{data: [...]}`，都會以
> `{results: [{index, relevance_score, document?}]}` 的形式傳回用戶端，並依分數排序，且最多保留 `top_n` 筆。
>
> **提供者節點探索：** OpenAI 相容提供者節點上的模型會以該節點前綴顯示於 `GET /v1/models`
> 中。不含端點中繼資料的資料列（常見於本機 `/v1/models` 清單）
> 會繼承節點的 `apiType`，因此 `embeddings` 節點的模型會是 `type: "embedding"`，而
> `rerank` 節點的模型會是 `type: "rerank"`，而非預設為聊天；同步或手動新增的資料列若明確指定
> `supportedEndpoints`，仍會具有優先權。


## Files API

與 OpenAI 相容的檔案端點，用於批次輸入／輸出及依檔案用途上傳。

| 方法   | 路徑                     | 說明                                                                                                        |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | 上傳檔案（multipart：`file`、`purpose`、`expires_after[anchor]`、`expires_after[seconds]`）— 上限為 512 MiB |
| GET    | `/v1/files`              | 列出已驗證 API 金鑰的檔案                                                                                   |
| GET    | `/v1/files/[id]`         | 取得檔案的中繼資料                                                                                          |
| DELETE | `/v1/files/[id]`         | 刪除檔案                                                                                                    |
| GET    | `/v1/files/[id]/content` | 以串流方式傳回原始檔案內容                                                                                  |

**驗證：** Bearer API 金鑰 — 檔案會透過 `getApiKeyRequestScope` 依 API 金鑰劃分範圍。金鑰
只能查看、下載及刪除自己的檔案；沒有金鑰的儀表板工作階段可讀取
整個執行個體；沒有擁有者的檔案（匿名或透過儀表板工作階段上傳）會拒絕所有
非工作階段呼叫者存取。即使 `REQUIRE_API_KEY=false`，`GET /v1/files` 仍會對匿名呼叫者
以及無法解析的已提供金鑰傳回 `401`，而不會列出所有租戶的
檔案（GHSA-m3hp-hq9g-fpmv、GHSA-2jm2-mpx8-6523）。

## Batches API

與 OpenAI 相容的批次處理。

### Exa 和 Tavily `provider_options`

Exa 和 Tavily 從命名空間包中讀取特定於提供者的欄位： `provider_options.exa` （或`provider_options["exa-search"]`）和`provider_options.tavily` （或`provider_options["tavily-search"]`）。僅轉送以下密鑰。每個金鑰都會根據`open-sse/handlers/search/providerOptionsPassthrough.ts`中自己的Zod模式進行檢查，並刪除類型錯誤的金鑰。任何其他鍵都會被忽略，包括 auth、base URL、 `stream`和`outputSchema`。其他提供者（`cx`、 `depth`等）使用的平面密鑰與以前一樣工作。

| 提供者 | 頂級字段                                                                                                                                                                                                                                                                                                                                                                  | 嵌套                                                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 艾克薩 | `type`、 `category`、 `userLocation`、 `moderation`、 `additionalQueries`、 `objective`、 `systemPrompt`、 `compliance` （平面基元）、 `startPublishedDate`、 `endPublishedDate`                                                                                                                                                                                          | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}`合併到預設的`{ text: true, highlights: true }`上 |
| 塔維利 | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                             |

通用欄位總是獲勝： `query`、 `max_results`、 `filters` （域）、 `country`和從`search_type`派生的主題。在 Exa 上， `search_type: "news"`保留`category: "news"`。 Tavily 也接受`search_type: "finance"` (`topic: "finance"`)。

Firecrawl 搜尋成本記錄為每個啟動區塊（包含 10 個返回結果），每個區塊為 0.002 美元（2 個積分），每次呼叫至少一個區塊（ [Firecrawl 計費](https://docs.firecrawl.dev/billing)）：11 個結果的成本為 0.004 美元。

通用`time_range`現在到達兩個提供者：Exa 取得`startPublishedDate` （ISO時間戳記），Tavily 取得`start_date` （`YYYY-MM-DD`）。 `provider_options`中的明確日期會覆蓋映射的日期。

Exa 結果將`id`、 `highlight_scores`、 `summary`、 `subpages`、 `entities`和`extras`保留在`provider_raw`。整體結果保留`images`和`favicon`。

Linkup search cost is recorded at $0.005 for `depth` `fast` and `standard` and $0.05 for `deep` ([Linkup pricing](https://docs.linkup.so/pages/documentation/development/pricing)), whether `depth` comes from `provider_options` or the connection's settings.

Exa `type: "lite"` (Exa 3.0) 接受較小的欄位集，並在設定任何其他欄位時拒絕整個請求。對於 lite， `additionalQueries`、 `systemPrompt`和除`text`和`highlights`之外的每個`contents`鍵在呼叫之前都會被刪除。已棄用的`subpages`、 `subpageTarget`、 `highlights.numSentences`和`highlights.highlightsPerUrl`不再轉發。

Cost accounting is the flat registry `costPerQuery`, except for Exa, which follows Exa's own pricing: $0.007 per call for `auto` (and the legacy `fast`) or $0.004 for `lite` (and the legacy `instant`), covering 10 results; $0.001 for each further result; and $0.001 per returned result when `contents.summary` is set. Tavily is recorded at 1 credit ($0.008) for `search_depth` `basic`, `fast` and `ultra-fast`, and 2 credits ($0.016) for `advanced` ([Tavily API credits](https://docs.tavily.com/documentation/api-credits)). A call with `auto_parameters: true` that Tavily upgrades to advanced is still recorded at 1 credit.

## Web Fetch API

透過已設定的網頁擷取提供者（Firecrawl、Jina Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）從 URL 擷取內容。

Parallel Extract（`parallel-search`，使用與 Parallel Search 相同的 API 金鑰）僅傳回 Markdown——任何其他 `format` 都會產生 `400`——且內容上限為 100,000 個字元。當目標頁面本身無法擷取時，上游會在 HTTP 200 回應中回報此情況；OmniRoute 會將其呈現為帶有固定訊息的 `422`。

| 方法 | 路徑            | 說明                                               |
| ---- | --------------- | -------------------------------------------------- |
| POST | `/v1/web/fetch` | 擷取／抓取 URL——請求主體由 `v1WebFetchSchema` 驗證 |

**驗證：** Bearer API 金鑰（`extractApiKey` + `isValidApiKey`）。透過 `enforceApiKeyPolicy` 強制執行政策。

**配額感知備援（#8297）：** 未明確指定 `provider` 時，系統會依固定優先順序（優先填滿）巡覽提供者池（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search`）——已設定但受速率限制的提供者會被略過，而不會直接中止請求；若上游發生可重試／配額相關失敗（HTTP 429 一律適用；402/403 適用於 Firecrawl/Tavily/TinyFish 的免費方案配額類型錯誤——不適用於 Jina Reader，且一般的 400 錯誤請求絕不適用），則會在請求執行期間依序改用下一個尚未嘗試且已設定憑證的提供者。當提供者池中的每個提供者都已耗盡時，端點會傳回單一 `429`（含 `Retry-After` 標頭），而不再傳回先前的一般性 `400`。明確指定 `provider` 時，**不會**進行靜默備援——受速率限制或失敗的明確指定提供者會直接呈現其自身錯誤（若受速率限制則為 `429`，否則為上游狀態碼）。

## WebSocket 串流

```bash
GET /v1/ws?handshake=1
```

驗證 WebSocket 升級交握，並傳回線路通訊協定的範例訊息（`request`、`cancel`）。實際的 WS 訊框由 Next.js 路由表之外隨附的 WS 伺服器處理。

**驗證：** 在交握期間使用 Bearer API 金鑰。

### 透過 WebSocket 使用 Responses API（僅限 codex）

```bash
# 與 HTTP API 使用相同的主機和連接埠（預設為 20128）；升級連線：
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （或：-H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 第一個訊框必須是 response.create：
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket Proxy **僅連接至 `codex`**（ChatGPT 後端）。它會在與 API／儀表板相同的連接埠上，監聽路徑 `/v1/responses`、`/responses` 和 `/api/v1/responses`。收到第一個 `response.create` 訊框時，它會透過內部 `codex-responses-ws` 橋接進行驗證與準備、選取 codex OAuth 連線，並使用 `wreq-js` 傳輸層建立通往 `wss://chatgpt.com/backend-api/codex/responses` 的通道。**非 codex 模型會被拒絕**（`codex_ws_provider_required`）。若要使用配額共享路由，請使用 `model: "qtSd/<group>/codex/<model>"`。實作位於 `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`。

**驗證：** 在交握期間使用 Bearer API 金鑰。隨附的 HTTP 伺服器（`server-ws.mjs`）必須是作用中的進入點（存在 `app/server-ws.mjs` 時，預設即為如此）。

#### 模型 ID：使用不含 `codex/` 前綴的 ChatGPT 原始 ID

當 `supports_websockets = true` 時，OpenAI **Codex CLI** 會在用戶端驗證模型名稱，並且**拒絕帶有提供者前綴的 ID**，例如 `codex/gpt-5.5`（`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`）。請傳送**不含前綴**的 ID（例如 `gpt-5.5`）。OmniRoute 的橋接僅支援 codex，因此在建立上游通道之前，它會將不含前綴的 ID 重新解析為 codex 模型（`resolveCodexWsModelInfo`）——即使不含前綴的 `gpt-5.5` 原本會透過 HTTP 路由至其他提供者。

#### 設定 OpenAI Codex CLI

若要讓 Codex CLI 指向 OmniRoute，請在 `~/.codex/config.toml` 中新增支援 WebSocket 的自訂提供者（請使用獨立的 `CODEX_HOME`，以免更動現有設定）：

```toml
model = "gpt-5.5"                 # 不含前綴的 ID——不是 "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 不含結尾斜線；WS URL 會由此衍生（正式環境請使用 https/wss）
wire_api = "responses"                    # 自 2026 年 2 月起唯一支援的值
supports_websockets = true                # 啟用 Responses-over-WS 傳輸
env_key = "OMNIROUTE_API_KEY"             # 儲存 OmniRoute API 金鑰（Bearer）
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API 金鑰（若 REQUIRE_API_KEY=false，則可使用任何金鑰）
codex exec "Responda apenas: PONG"
```

CLI 會將 `base_url + /responses` 升級為 WebSocket，而 OmniRoute 會將其轉送至所選的 codex OAuth 連線。已針對本機伺服器完成端對端驗證：ChatGPT 會傳回 `codex.rate_limits` + `response.created`，並以串流方式傳送完成結果。

## 自助式用量查詢（`/api/usage/om-usage`）

任何 API 金鑰都可以讀取**自身的**用量與配額，無需管理驗證。這是用戶端（CLI、OmniCopilot 面板）用來向金鑰持有者顯示其支出的端點。

```bash
# 文字格式（歷史沿用的契約——供終端機使用的純文字）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 結構化格式——供 UI 使用
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

該金鑰必須啟用 **`allowUsageCommand`**（預設關閉——儀表板的 API 金鑰管理器可針對各個金鑰切換此設定）。若未啟用，端點會回應 `403`。

`?format=json` 會傳回可辨識的資料結構，讓呼叫端絕不會從拒絕回應中讀取資料欄位。成功時：

```jsonc
{
  "allowed": true,
  // 僅當金鑰選擇啟用每金鑰用量限制（每日／每週美元）時才會出現：
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 所選提供者的配額快照；若尚未快取任何資料，則為 null：
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // 每個連線的快照，讓 UI 能夠並排呈現多個提供者：
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

遭拒絕時（`401` 金鑰無效／`403` 不允許），同一路由會傳回
`{ "allowed": false, "error": { "message": "…" } }`——存在但為空的 `personal`/`provider`
（允許該金鑰，但尚未取得任何資訊）與遭拒絕是不同的狀態，且只有 JSON 格式能區分兩者。

**驗證：** 呼叫端自身的 Bearer API 金鑰，使用 `isValidApiKey` 驗證——這_不是_
管理介面（`/api/keys/…`），後者仍受 `requireManagementAuth` 保護。

### 原始配額百分比與截止值調整後的配額百分比

使用 `/api/usage/om-usage` 時，呼叫端應注意**純文字輸出**與結構化 **JSON 輸出**所呈現百分比之間的差異：

| 面向           | 純文字格式（`/api/usage/om-usage` / `@@om-usage`）                          | JSON 格式（`?format=json`）                                     |
| :------------- | :-------------------------------------------------------------------------- | :-------------------------------------------------------------- |
| **輸出欄位**   | `NN% left`（例如 `20% left`）                                               | `provider.quotas` / `providers[].quotas`                        |
| **衡量方式**   | **經截止值調整的可用額度**：高於截止門檻的剩餘容量                          | **原始上游配額**：未經調整的提供者測量值                        |
| **截止值縮放** | 透過 `effectiveRemainingPercent()` 縮放，使受保護的保留額度顯示為 `0% left` | 無（提供者所回報的原始快照值）                                  |
| **門檻資料**   | 已納入顯示的百分比                                                          | 儲存在各連線的 `quotaWindowThresholds` 中（或使用伺服器預設值） |
| **主要使用者** | 互動式 CLI、終端機提示、人工作業人員                                        | 程式化整合、儀表板、分析、帳務追蹤工具                          |

#### 截止值調整公式

OmniRoute 支援主動式配額截止值，以避免上游配額耗盡（透過連線的
`quotaWindowThresholds`、提供者預設值或全域韌性設定進行配置）。當某個配額視窗啟用截止門檻
（例如 `cutoff = 25%`）時，文字轉譯器會依下列方式計算剩餘額度：

- 若 `remaining <= cutoff`：傳回 `0%`。
- 若 `remaining > cutoff`：傳回 `((remaining - cutoff) / (100 - cutoff)) * 100`。

格式化文字輸出會將此值四捨五入至最接近的整數（`Math.round(...)`）。

#### 說明範例

假設某個提供者視窗的**原始用量為 60%**（因此**原始剩餘配額為 40%**），且設定了
**剩餘配額 25% 的截止**門檻：

| 表示方式                        | 計算                                               |  剩餘   |                推算已用                |
| :------------------------------ | :------------------------------------------------- | :-----: | :------------------------------------: |
| **原始 JSON（`?format=json`）** | 上游快照（`quotas[window]`）                       | **40%** |                **60%**                 |
| **文字格式（`NN% left`）**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%**（若以 `100 - remaining` 計算） |

- **為何文字顯示剩餘 20%：** 帳戶實際剩餘的 40% 配額中，有 25% 由截止政策保留。在路由器停止將流量路由至此連線之前，呼叫端僅剩 75% 可用餘裕中的 15%。縮放可確保連線正好在路由停止時發出配額耗盡訊號（`0% left`）。
- **為何 JSON 保留原始值：** JSON 承載資料會傳回確切的提供者快照（`UsageSnapshot`），讓外部工具能存取真實的上游使用率，以及連線層級的 `quotaWindowThresholds`，避免伺服器端有損縮放。

#### 使用端遷移指南

如果外部整合（例如編輯器外掛程式或代理擴充功能）先前擷取文字
端點（`NN% left`），並以 `100 - NN` 計算已使用的百分比，則遷移至 `?format=json` 意味著：

- 讀取原始 JSON 值將反映**實際的上游用量**（以上述範例而言，已使用 60%）。
- 如果整合希望保留文字端點的可用配額語意，可以在用戶端使用 `quotaWindowThresholds` 評估
  有效的剩餘量公式，以處理連線層級的覆寫。

## 語意快取

```bash
# 取得快取統計資料
GET /api/cache/stats

# 清除所有快取
DELETE /api/cache/stats
```

回應範例：

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### 延遲影響

語意快取命中時，會直接從快取提供回應，**而不會呼叫上游
服務**，因此回報的 `X-OmniRoute-Response-Latency` 接近零
（無論原始上游延遲為何）。對延遲敏感的用戶端
（基準測試、p50/p99 監控）應檢查
`X-OmniRoute-Cache-Latency` 回應標頭：

| 值          | 意義                                       |
| ----------- | ------------------------------------------ |
| `synthetic` | 回應由快取提供；延遲並非真實的上游處理時間 |
| _(不存在)_  | 回應來自真實的上游呼叫                     |

### 依金鑰略過快取

API 金鑰可透過 `cacheDefaultMode` 選擇不讀取語意快取：

| 值       | 行為                               |
| -------- | ---------------------------------- |
| `legacy` | 一般快取行為（預設）               |
| `bypass` | 完全略過快取查詢；一律呼叫上游服務 |

可在建立金鑰時（`POST /api/keys`）設定，或透過（`PATCH /api/keys/[id]`）更新：

```json
{ "cacheDefaultMode": "bypass" }
```

### 依請求略過快取

無論金鑰設定為何，任何請求都可以略過快取：

```
X-OmniRoute-No-Cache: true
```

對於已同步／匯入的模型，`PUT /api/provider-models` 接受 `provider`、`modelId` 和
`maxOutputTokenOverride`：正整數會設定手動輸出權杖上限，而 `null`
會將其清除以還原預設值。`GET /api/provider-models?provider=<provider>` 會在
`modelOutputOverrides` 中傳回這些值，包括沒有自訂模型資料列的模型。此覆寫設定
使用執行階段的 `max_output_tokens` 能力，並會在模型重新同步後保留。OpenAI 相容
提供者頁面提供相同的編輯／清除控制項，並會標記明確支援視覺功能的模型。

自訂 Chat Completions 節點會將明確停用推理的設定調整為上游後端適用的格式。
連線測試成功後，會針對 `/models` 項目證明具有下列可辨識 `owned_by` 值的每個精確模型 ID，
自動選取聊天範本控制項：`vllm`、`sglang` 或 `llamacpp`。
透明的 OpenAI 相容包裝器可能會將原始模型項目保留在巢狀
`openai` 物件內；偵測最多會追蹤三層此類封裝。所有權資訊缺失、未知或
衝突的模型會保留一般的 OpenAI 行為。偵測會重複使用現有的目錄請求，
不會產生任何完成權杖，並會在連線端點變更時失效。

若要為未公開該中繼資料的後端固定此行為，請使用現有的部分
提供者更新 API：

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

將該本文與 `PUT /api/providers/<connection-id>` 一起傳送。在該連線上，明確設為
`none` 的推理強度會以 `chat_template_kwargs.thinking=false` 和
`chat_template_kwargs.enable_thinking=false` 傳送。除非伺服器端推理規則強制指定強度，
否則明確的原生範本值仍具權威性。此設定僅在自訂
OpenAI 相容連線分派 Chat Completions 本文時套用；Responses 請求與一般
提供者會保留其原生請求格式。將 `reasoningControl` 設為 `openai`，可強制直接傳遞一般 OpenAI
`reasoning_effort`；或者省略此設定／將其設為 `null`，以使用自動偵測。

Claude Code 自動模式分類器請求在不含
任何明確推理控制項時，預設會停用原生思考。偵測會使用 Claude 格式
請求中的分類器系統標記，而非模型名稱或完成限制。明確的本文控制項、受支援的強度／思考
標頭、路由規則，以及解析後的模型強度，會維持其現有優先順序。兩個分類器
階段都會保留其提示、完成限制、停止序列及真正的上游權限
判定；第二階段仍可將其要求的可見推理產生為一般文字。

### 版本與發布通道

```bash
GET /api/system/version
```

僅限迴路介面的管理路由（需要管理員驗證）。回傳目前執行中的版本、最新發布版本及自動更新狀態。`releaseChannel` 與 `channels` 是新增欄位（3.8.54 軌）；`channel` 保留其原有含義——儀表板更新程式所使用的部署模式（`npm`、`source` 或 `docker-compose`）。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 目前執行組建的 npm 通道：版本為 `-nightly.*` 時是 `nightly`，
  其他預發布版本（`-rc.*`、`-beta.*`、`-alpha.*`）為 `next`；若為比 `channels.latest`
  更舊主要版本的穩定版，則為 `lts`；其他情況則為 `latest`。規則與
  `scripts/release/dist-tag.mjs` 相同，該指令碼會在發布時選擇 npm dist-tag。
- `channels` — 各 dist-tag 已發布的最新版本，資料來自 `npm view omniroute dist-tags`
  （以登錄檔 HTTP 作為備援），並使用與 `latest` 相同的 10 分鐘 TTL 快取。`latest`
  一定會存在（依序備援至 `latest` 欄位，然後是 `"unavailable"`）；`next`、`nightly`
  和 `lts` 僅在該 dist-tag 存在時才會出現。帶有 `Cache-Control: no-cache`
  的請求會重新整理這兩項查詢。

通道模型（`latest` = 4.0 正式發布前的 v3、`next` = rc、`nightly` = `develop`
組建、`lts` = 4.0 正式發布後的 v3 修補版本）說明於 `docs/ops/RELEASE_STRATEGY.md`。

## Token 限制

每個 API 金鑰的 **token** 預算（不同於上述以 USD 為基礎的預算）。限制會在請求路徑上即時強制執行：當金鑰在目前時段的使用量達到其上限時，請求將遭到拒絕並回傳 `429 Too Many Requests`。限制可以限定於特定 `model`、`provider`，或套用至整個金鑰的 `global` 範圍；當一個請求符合多項限制時，將採用最嚴格的限制。

```bash
# 列出金鑰的 token 限制（包括目前時段的即時使用量）
GET /api/usage/token-limits?apiKeyId=key-123

# 建立或更新 token 限制
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# 依 id 刪除 token 限制
DELETE /api/usage/token-limits?id=tl-abc
```

> **結構描述注意事項**（`setTokenLimitSchema`）：`apiKeyId` 和 `scopeType`（`model` | `provider` | `global`）為必填。除非 `scopeType` 為 `global`，否則 `scopeValue` 為必填（例如，`model` 範圍使用模型 id，`provider` 範圍使用提供者 id）。`tokenLimit` 必須是正整數（可從字串強制轉換）。選填：`id`（建立時省略，更新時提供）、`resetInterval`（`daily` | `weekly` | `monthly`，預設為 `monthly`）、`resetTime`（`HH:MM`）、`enabled`（預設為 `true`）。`GET` 回應會為每項限制補充 `tokensUsed`、`remaining`、`windowStart`、`periodStartAt` 和 `nextResetAt`。這是管理類端點（由授權管線集中強制執行驗證）。

## 請求處理

1. 用戶端將請求傳送至 `/v1/*`
2. 路由處理常式呼叫 `handleChat`、`handleEmbedding`、`handleAudioTranscription` 或 `handleImageGeneration`
3. 解析模型（直接指定提供者/模型，或使用別名/組合）
4. 從本機資料庫選取憑證，並依帳戶可用性進行篩選
5. 對於聊天：`handleChatCore` 會檢查語意/簽章快取，並解析組合壓縮設定
6. 啟用時，會在提供者格式轉換前執行主動壓縮（`lite`、Caveman、RTK 或堆疊模式）
7. 提供者執行器傳送上游請求
8. 將回應轉換回用戶端格式（聊天），或依原樣回傳（嵌入/圖片/音訊）
9. 記錄用量、壓縮分析與請求日誌
10. 發生錯誤時，依組合規則套用備援機制

完整架構參考：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 韌性（擴充）

OmniRoute 提供三種彼此獨立的暫時性故障處理機制；下列管理端點可讓操作人員讀取及覆寫這些機制：

| 範圍         | 狀態儲存                             | 讀取                                      | 重設／清除                               |
| ------------ | ------------------------------------ | ----------------------------------------- | ---------------------------------------- |
| 提供者斷路器 | `domain_circuit_breakers` + 記憶體內 | `/api/monitoring/health`                  | `POST /api/resilience/reset`             |
| 連線冷卻     | 提供者連線上的 `rateLimitedUntil`    | `/api/rate-limits`, `/api/providers/[id]` | （延遲重新啟用；可透過提供者 PUT 清除）  |
| 模型鎖定     | 記憶體內的模型可用性登錄檔           | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns` |

`PATCH /api/resilience` 接受位於 `providerBreaker.oauth` 和 `providerBreaker.apikey` 下的提供者斷路器覆寫設定。每個設定檔都支援 `degradationThreshold`、`failureThreshold` 和 `resetTimeoutMs`；相同欄位也會顯示於「儀表板 → 設定 → 韌性」中。

```bash
# 清除單一模型鎖定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# 清除所有鎖定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

如需完整的概念參考與斷路器預設值，請參閱 [`CLAUDE.md`](../../CLAUDE.md) →「韌性執行階段狀態」及 [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)。

### 速率限制佇列與自動啟用安全網

- **支援的寫入路徑**：使用本文 `{"connectionId": "<id>", "enabled": true|false}` 呼叫 `POST /api/rate-limits`，是切換連線速率限制保護的受支援管理端點。`PUT /api/providers/[id]` 刻意不會修改或切換 `rateLimitProtection` (#11278)。
- **`enabled: false` 的語意**：設定 `enabled: false` 會移除該連線的明確保護，但**不會**讓作用中的 API 金鑰連線退出全域自動啟用安全網（`autoEnableApiKeyProviders = true`）。在 `reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）中，`false` 與 `undefined` 等效；沒有明確保護的作用中 API 金鑰連線，在自動啟用安全網下仍會受到保護。
- **全域停用**：若要讓 API 金鑰連線在沒有速率限制佇列的情況下執行，請透過 `RATE_LIMIT_AUTO_ENABLE=false`（環境變數）或 `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（設定 → 韌性／`PATCH /api/resilience`）在全域停用安全網。

| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |

## A2A 伺服器

OmniRoute 提供一個 A2A（代理對代理）JSON-RPC 2.0 端點，以及供檢查／儀表板使用的 REST 包裝介面。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # 選用，除非已設定 OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

支援的方法（全部受 `settings.a2aEnabled` 控制）：

| 方法             | 說明                                             |
| ---------------- | ------------------------------------------------ |
| `message/send`   | 同步執行技能；回傳 `{task, artifacts, metadata}` |
| `message/stream` | 透過 SSE 串流執行相同的技能集                    |
| `tasks/get`      | 依 `taskId` 擷取任務                             |
| `tasks/cancel`   | 依 `taskId` 取消任務                             |

內建技能：`smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### 代理卡片

```bash
GET /.well-known/agent.json
```

回傳公開的 A2A 代理卡片（名稱、說明、功能、技能目錄、驗證機制）— 公開快取 1 小時。不需要驗證。

### REST 輔助端點

| 方法 | 路徑                         | 說明                                                                                                           |
| ---- | ---------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/a2a/status`            | A2A 啟用狀態 + 任務統計資料 + 已快取的代理卡片摘要                                                             |
| GET  | `/api/a2a/tasks`             | 列出任務 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST | `/api/a2a/tasks`             | （未實作為 REST 輔助端點 — 請透過 JSON-RPC `message/send` 建立）                                               |
| GET  | `/api/a2a/tasks/[id]`        | 擷取單一任務                                                                                                   |
| POST | `/api/a2a/tasks/[id]/cancel` | 取消任務                                                                                                       |

**驗證：**REST 輔助端點不需要管理驗證即可執行（可由儀表板讀取）；如果已設定 Bearer `OMNIROUTE_API_KEY`，JSON-RPC `/a2a` 路由便會使用它。

## 驗證

請參閱[管理驗證](../guides/MANAGEMENT-AUTH.md)，以瞭解四種憑證類別（儀表板工作階段、本機 CLI 權杖、`oma_live_…` 存取權杖、具管理範圍的 API 金鑰），以及它們與推論金鑰的差異。

- 儀表板路由（`/dashboard/*`）使用 `auth_token` Cookie
- 登入使用已儲存的密碼雜湊；若無法使用，則回退至 `INITIAL_PASSWORD`
- `requireLogin` 可透過 `/api/settings/require-login` 切換
- 當 `REQUIRE_API_KEY=true` 時，`/v1/*` 路由可選擇要求 Bearer API 金鑰
- 本參考文件中的「管理權杖」／「具管理範圍的 API 金鑰」是指該指南中的其中一種憑證類別，而不是未定義的其他密鑰類型

> **重大變更（v3.8.0）** — `/api/v1/agents/tasks/*` 與冷卻時間管理端點現在需要**管理驗證**（儀表板 `auth_token` Cookie 或具管理範圍的 API 金鑰）。先前未經驗證即呼叫這些路由的用戶端將收到 `401 Unauthorized`。請參閱提交 `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）。
