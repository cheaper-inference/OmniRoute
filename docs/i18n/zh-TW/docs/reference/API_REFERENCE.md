## 聊天完成

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### 自訂標頭

| Header                   | Direction | Description                                                                                                                                                   |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Request   | 設為 `true` 以略過快取                                                                                                                                        |
| `x-omniroute-no-memory`  | Request   | 設為 `true` 以略過此請求的記憶 + 技能注入（與 no-cache 相同；避免每次呼叫的權杖／成本額外負擔）                                                               |
| `X-OmniRoute-Progress`   | Request   | 設為 `true` 以啟用進度事件                                                                                                                                    |
| `X-Session-Id`           | Request   | 用於外部工作階段親和性的黏著工作階段金鑰                                                                                                                      |
| `x_session_id`           | Request   | 也接受底線變體（直接 HTTP）                                                                                                                                   |
| `X-OmniRoute-Session-Id` | Request   | 呼叫端提供的工作階段／對話標籤（也會饋送至記憶體）。提供時，會原樣持久化至 `call_logs.session_tag`，用於每個工作階段的成本歸屬（#8249）— 未提供時絕不自動產生 |
| `Idempotency-Key`        | Request   | 去重金鑰（5 秒視窗）                                                                                                                                          |
| `X-Request-Id`           | Request   | 替代去重金鑰                                                                                                                                                  |
| `x-omniroute-connection` | Request   | 依其 ID 將單一模型請求固定至一個提供者連線（帳戶）— 請參閱[每個請求的帳戶固定](#account-pinning-per-request)                                                  |
| `X-OmniRoute-Cache`      | Response  | `HIT` 或 `MISS`（非串流）                                                                                                                                     |
| `X-OmniRoute-Idempotent` | Response  | 若已去重則為 `true`                                                                                                                                           |
| `X-OmniRoute-Progress`   | Response  | 若已啟用進度追蹤則為 `enabled`                                                                                                                                |
| `X-OmniRoute-Session-Id` | Response  | OmniRoute 使用的有效工作階段 ID                                                                                                                               |
| `X-OmniRoute-Request-Id` | Response  | 請求關聯 ID（若已知）                                                                                                                                         |
| `X-OmniRoute-Version`    | Response  | OmniRoute 建置版本（始終存在）                                                                                                                                |
| `X-OmniRoute-Cost-Saved` | Response  | 快取在命中時避免的美元成本（僅限快取命中）                                                                                                                    |
| `X-OmniRoute-Decision`   | Response  | 路由追蹤：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` 是組合策略；對於非組合請求則為 `single`）— 完成回應中始終存在                         |

> Nginx 注意事項：如果依賴底線標頭（例如 `x_session_id`），請啟用 `underscores_in_headers on;`。

#### 每個請求的帳戶固定

當提供者有多個連線（帳戶或金鑰）時，OmniRoute 通常會透過其帳戶選擇策略來選取其中一個。請求也可以改用 `x-omniroute-connection` 標頭固定至特定連線：

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **在哪裡尋找 id。** 在儀表板中開啟提供者頁面
  （**Dashboard → Providers → <provider>**），然後點擊連線列上的 `xxxxxxxx…` id 晶片 — 系統會複製完整的連線 id。
- **哪些請求會遵循它。** `/v1/chat/completions`、`/v1/messages` 和
  `/v1/responses` 上的單一模型請求（`provider/model`）。組合請求會忽略此標頭：請透過每個組合步驟自己的連線，為該步驟固定指定帳戶。
- **固定指定是嚴格限制，而非偏好設定。** 系統只會使用固定的連線。請求內部發生失敗時，會記錄該帳戶的冷卻狀態，但**不會**切換至同一提供者的其他帳戶。
- **冷卻和配額會解除固定指定。** 當固定的連線正在冷卻、配額已耗盡，或遭配額政策封鎖時，後續請求會改用提供者的其他連線，行為與未固定指定的流量完全相同。
- **未知或已停用的 id 會導致失敗。** 不在提供者有效連線池中的 id（已刪除、已停用，或屬於其他提供者）會使請求沒有可用帳戶，因此請求會失敗，而不是默默地改路由至其他位置。

Claude Code 會透過 `ANTHROPIC_CUSTOM_HEADERS` 傳送自訂標頭。請將它放在
`~/.claude/settings.json` 的 `env` 區塊中，或放在專案層級的 `.claude/settings.json` 中，以便為每個專案固定指定不同的帳戶：

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

來源：`src/sse/handlers/chat.ts`（讀取標頭）、`src/sse/services/auth.ts` 和
`src/sse/services/sessionAffinityPin.ts`（固定指定的解除與從連線池中缺失的檢查）。

> **成本遙測標頭：** 非串流成功回應也會攜帶 `X-OmniRoute-*` 成本遙測集合 — `X-OmniRoute-Response-Cost`（USD，固定 10 位小數；免費／未定價時為 `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit` 和 `X-OmniRoute-Fallback-Attempts`（僅在大於 0 時提供），以及 `X-OmniRoute-Request-Id` 和 `X-OmniRoute-Version`。這些標頭會由聊天完成、`/v1/responses`、`/v1/messages` **以及媒體端點**提供 — `/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations` 和 `/v1/moderations`（成本一律為 `0`）。媒體成本會在定價可用時依各種模態計算（每張影像、每秒、每個字元、每個搜尋單位），否則為 `0`（失敗開放）。

> **快取命中成本語意：** 在語意快取命中（`X-OmniRoute-Cache-Hit: true`）時，不會發出上游呼叫，因此 `X-OmniRoute-Response-Cost` 為 `0.0000000000`（提供此次命中的**增量**成本）。原始／原本可能產生的成本會另外記錄在 `X-OmniRoute-Cost-Saved` 中。計費消費者應加總 `X-OmniRoute-Response-Cost`（命中不產生成本）；快取分析則可以彙總 `X-OmniRoute-Cost-Saved`。

## 專屬受管理工作階段租約

專屬受管理工作階段租約是一種選擇加入、與用戶端無關的路由合約：一個作用中的擁有者
持有一個符合資格的 OmniRoute 連線。它不會租用模型、不要求 OAuth、不識別特定用戶端，
也不要求特定提供者。

進行驗證的 API 金鑰必須具備 `lease:exclusive` 範圍，以及明確的非空
`allowedConnections` 清單。資料庫變更邊界會在建立金鑰和部分更新時，強制同時具備這兩個欄位。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

成功的取得、續租和釋放回應會公開時間戳記、`state`，以及確切的正數
`generation`，但絕不會公開選取的連線或認證憑證。續租和釋放會在 JSON 本文中提供
generation：

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

作用中的租約擁有者可以明確要求其目前繫結的隱私安全顯示中繼資料：

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

此選擇加入的狀態動作會在一個資料庫交易中，由不透明擁有者、經驗證的受管理 API 金鑰，
以及確切的作用中 generation 共同設限。`displayName` 僅是經過修剪的已設定連線名稱；
若不存在安全的已設定名稱，則為 `null`。OmniRoute 絕不會以電子郵件或產生的帳戶身分
取代它。提供者值是不敏感的顯示標籤，絕不是產生的相容提供者識別碼。系統會排除認證、
權杖、Cookie、原始連線或 API 金鑰識別碼、擁有者雜湊、設限密碼，以及內部路由資料。

錯誤金鑰、錯誤擁有者、過時 generation、遺失、已過期、已釋放和已失效的查詢，全部都會
在不包含連線中繼資料的情況下，回傳相同的 `409 LEASE_FENCE_STALE` 錯誤。收到容量等待
回應的用戶端沒有可供檢查的作用中繫結。當路由在作用中的租約之間轉換時，相同的 generation
仍然有效，而狀態會以原子方式回傳新的繫結，絕不會回傳舊的繫結。現有用戶端不會受到變更，
因為取得、續租、釋放和等待回應仍保留先前的結構。

此伺服器合約不會變更標準 OpenAI Codex `/status`。目前的標準 Codex 會回報其模型提供者
及內建的驗證／帳戶狀態，但不會呈現任意自訂提供者的帳戶中繼資料；未來的用戶端整合必須
呼叫此動作，並決定如何顯示 `connection.displayName`。

之後，每個受管理的推論請求都會提供這兩個控制標頭：

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

在每次受支援的上游嘗試之前，系統會立即對確切的擁有者、generation、作用中連線和經驗證
的 API 金鑰進行設限。即使另一個金鑰允許使用相同連線，以該金鑰重播擁有者和 generation
仍會失敗。原始擁有者不會被持久化、記錄、保留在請求快照中，或轉送至上游。

暫時性的競爭會回傳 HTTP `429`、`Retry-After`，以及：

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

此回應僅表示一般符合資格的集合並非空集合，且每個可用的候選項目都由其他作用中的租約
持有。模型／提供者不受支援、原則不符、冷卻、配額、健康狀態及其他一般符合資格失敗，
仍會保留其現有的 OmniRoute 回應。

### `x-omniroute-compression`

每個請求的壓縮計畫覆寫。優先順序最高——高於路由組合覆寫、作用中設定檔、自動觸發條件
和面板的 Default。值：

| Value         | Effect                                                                |
| ------------- | --------------------------------------------------------------------- |
| `off`         | 此請求不進行壓縮。                                                    |
| `default`     | 面板衍生的 Default 設定檔（忽略作用中的設定檔）。有損引擎會保持關閉。 |
| `safe`        | 僅進行去重和空白摺疊。                                                |
| `allow-lossy` | 此請求保留操作員計畫，包括摘要和樣式重寫。                            |
| `engine:<id>` | 啟用時使用單一引擎，例如 `engine:rtk`。此引擎的每個請求選擇加入。     |
| `<combo>`     | 具名組合，優先按名稱（不區分大小寫）比對，然後按 id 比對。            |

注意：

- 未知值會被忽略（請求絕不會因此遭到拒絕）；解析會回到一般操作員優先順序。
- 如果多個組合共用同一名稱，請傳遞組合 **id** 以進行確定性比對。
- 名稱為 `off` 或 `default` 的組合無法按名稱選取（這些關鍵字會先被解讀）；請改用其 id 參照此類組合。
- 主要壓縮開關是硬性閘門：當壓縮功能在全域停用時，此標頭無法將其啟用。

套用的計畫會在回應標頭中回傳：

```
X-OmniRoute-Compression: <mode>; source=<source>
```

其中 `<source>` 會是 `request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default`
或 `off` 其中之一。

## 嵌入

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

可用的提供者：Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

目錄 ID 的格式為 `provider/model`（例如：`jina-ai/jina-embeddings-v5-omni-small`）。註冊表中出現的純 Jina 模型 ID（例如 `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）也能解析。Jina embed/rerank/classify/segment 優先使用儀表板中的 `jina-ai` 憑證；只有在不存在儀表板金鑰時，才會將 `JINA_AI_API_KEY` 作為後備。`jina-reader` 卡片僅適用於 Reader / `r.jina.ai`（`POST /v1/web/fetch`），不會提供嵌入或重新排序服務。

宣告支援多模態的註冊表模型，也接受最多 32 個與提供者無關的結構化項目。媒體項目類型包括 `text`、`image`、`audio`、`video` 和 `document`。其媒體 `source`
可以是 `{"type":"url","url":"https://..."}` 或
`{"type":"base64","data":"...","media_type":"..."}`。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`
以及系列別名 `jina-ai/jina-embeddings-v5-omni` → omni-small）也接受 Jina 原生的
EmbeddingsV5Request 文件，並將其**完整轉送**至 `https://api.jina.ai/v1/embeddings`：

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

原生的 `{ image | audio | video | pdf }` 值可以是公開的 HTTPS URL、`data:` URI 或原始
base64。OmniRoute 不會將這些物件轉換為字串，也不會擷取原生影像 URL — Jina 會自行擷取
公開媒體。額外的 Jina 欄位（`task`、`normalized`、`truncate`、`embedding_type`）會被轉送。僅限文字的 Jina SKU 仍會拒絕非文字文件。

安全性與傳輸限制：

- 遠端媒體 URL 必須是公開的 HTTPS。標準 `{type,source:url}` 項目會在伺服器端擷取
  （重新導向重新驗證、逾時、大小限制、公開 DNS、連線釘選），並在呼叫提供者前內嵌。Jina 原生的 `{image:"https://..."}` 項目在通過相同的公開 HTTPS 檢查後會原樣轉送；Jina 會擷取該 URL。
- 內嵌的 base64 媒體每個項目解碼後上限為 8 MiB，整個要求解碼後上限為 16 MiB。

提供者轉換（標準項目不會原樣轉送）：

- Jina 多模態模型：每個頂層項目會轉換為一個以模態為鍵的物件
  （`text` / `image` / `audio` / `video` / `pdf`），內嵌媒體使用 data URI；每個
  頂層項目產生一個向量。
- Gemini Embedding 2 系列：一個頂層陣列會轉換為單一原生
  `models/{model}:embedContent` 要求，其中包含 `content.parts`（`text` 或 `inline_data`）。
- llama.cpp（`llama-cpp/<model>`，以及本機伺服器已載入的任何模型）：標準的 `text` 項目
  會轉換為純字串，而 `image` / `audio` / `video` 則各自轉換為一個
  `{"content": [part]}` 物件，使用 llama-server 的聊天內容部分（`image_url`、
  `input_audio`，格式為 `wav` / `mp3` / `flac`，以及 `input_video`），並使用內嵌資料；每個頂層項目產生一個向量。伺服器必須以 `--embedding --mmproj …` 執行；沒有投影器時，伺服器本身會拒絕媒體。`document` 不受支援。
- 沒有明確模態中繼資料的未知／動態模型會以 HTTP 400 拒絕結構化輸入。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

不支援的模型／模態組合會回傳 HTTP 400，而不是強制轉換項目。舊版字串／權杖要求中的非輸入
擴充欄位會繼續原樣傳遞。

```bash
# 列出所有嵌入模型
GET /v1/embeddings
```

## 影像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

可用的提供者包括 OpenAI（GPT Image 2）、xAI（Grok Image）、Together AI（FLUX）、Fireworks AI、Nebius（FLUX）、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（本機）、ComfyUI（本機）。

`n` 會在 `data[]` 中傳回 `n` 張影像。上游 API 每次呼叫只傳回一張影像的提供者
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI）會分別進行 `n` 次上游呼叫，同時最多執行 4 次。固定的
`seed` 會依呼叫索引偏移（`seed`、`seed + 1`、…），因此影像會有所不同，但仍可重現。
`n` 的上限為 10。如果任何一次呼叫失敗，整個請求就會失敗。扇出格式清單位於
`open-sse/handlers/imageGeneration/fanOut.ts` 中的 `SINGLE_IMAGE_FANOUT_FORMATS`。

ZenMux 會重複使用現有的 API 金鑰連線，並接受 `zenmux/` 或 `zm/` 前綴：

- `zenmux/openai/gpt-image-2` 使用 ZenMux 的 OpenAI Images API。選項包括 `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background` 和 `response_format`。
- 其他發布者（例如 `zm/meta/muse-image-1.0`）使用 ZenMux 的 Vertex AI `:predict`
  端點。`n` 對應至 `sampleCount`，`aspect_ratio` 對應至 `aspectRatio`，而 `image_size`
  （`1K`、`2K`、`4K`）對應至 `sampleImageSize`。像素 `size` 僅提供外觀比例，
  不保證像素尺寸。支援的比例、解析度和數量會因模型而異。
- `zm/inclusionai/ming-image-0.1-design` 會自行選擇尺寸。請省略 `size`、
  `aspect_ratio` 和 `image_size`；明確指定這些值會傳回 HTTP 400。透過
  `output_format` 可要求 PNG、JPEG 和 WebP。

此整合支援文字轉影像生成，不支援參考影像編輯。Vertex 輸出會正規化為
`data[].b64_json`；`response_format: "url"` 會傳回上游 HTTPS URL，或在只有影像位元組
可用時傳回 base64 資料 URL。空的／經篩選的輸出會傳回錯誤，而不是空白的成功回應。
模型存取權取決於 ZenMux 帳戶。請參閱 [ZenMux 的 Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) 和
[OpenAI 影像 API](https://docs.zenmux.ai/api/openai/generate-an-image)。

Microsoft 365 Copilot 登入連線會透過 Copilot 內建的影像工具提供
`copilot-m365-web/m365-copilot-image`：每張影像進行一次 Copilot 回合（`n` 為 1–4），
`size` 僅用於引導方向，影像會以內嵌方式傳回（`b64_json`，或在
`response_format: "url"` 時傳回資料 URL）。請參閱 [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation)。

```bash
# 列出所有影像模型
GET /v1/images/generations
```

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` 會透過 `provider/model` 前綴選取 OCR 提供者；單獨的模型 ID（例如
`mistral-ocr-latest`）會解析至其已註冊的提供者，而省略 `model` 時預設使用
Mistral（`mistral-ocr-latest`）。已註冊的提供者（`open-sse/config/ocrRegistry.ts`）：

| 提供者 ID                     | 模型 ID              | `model` 值                                                    | 備註                                                                                    |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（或單獨的 `mistral-ocr-latest`） | 同步——回應會直接從單次上游呼叫返回。                                                    |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | 非同步上游（`analyze` + 輪詢）——請參閱下文。                                            |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | 同步，透過 Vertex AI 的 `openapi/chat/completions` 合作夥伴端點——驗證／URL 請參閱下文。 |

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence 輪詢流程

Azure Document Intelligence 的 `analyze` API 是非同步的：初始請求會返回
`Operation-Location` 標頭，而非本文，且必須輪詢結果。處理常式
（`open-sse/handlers/ocr.ts`）每秒輪詢該 URL，最多嘗試 30 次；如果輪詢回應不是
`ok` 或狀態為 `"failed"`，則會立即失敗（不會繼續輪詢）；如果在嘗試次數用盡後操作仍在執行，
則返回 `504`。最終的 Azure 回應會先正規化為與 Mistral 相同的
`pages`/`markdown` 結構，再返回給呼叫端，因此用戶端程式碼不需要針對提供者進行特殊處理。

### Vertex AI DeepSeek OCR 驗證與端點解析

`vertex-deepseek-ocr` 會重複使用 OmniRoute 已支援的相同 Vertex AI 驗證機制來處理
聊天／圖像流量（`open-sse/executors/vertex.ts`）：連線的 API 金鑰可以是服務帳戶 JSON
憑證（透過 JWT bearer 流程交換為短期 OAuth 存取權杖），也可以是已簽發且直接使用的 OAuth
存取權杖。上游端點 URL 是 Vertex 的一般
`openapi/chat/completions` 合作夥伴端點，根據連線的專案和區域建立——明確指定的
`providerSpecificData.project`／`providerSpecificData.region` 一律優先；否則會從服務帳戶
JSON 的 `project_id` 推導專案，而區域預設為 `us-central1`。這兩種解析都發生在
`open-sse/handlers/ocr.ts`（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`），
並由 `src/app/api/v1/ocr/route.ts` 在分派至 `handleOcr` 前使用。

## 列出模型

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ 傳回 OpenAI 格式的所有聊天、嵌入和影像模型及組合
```

### 模型價格 (`pricing`)

當 OmniRoute 知道模型價格時，項目會帶有 `pricing` 物件。價格來自成本計算所使用的價格表：內建預設值、同步的價格，以及透過 `/api/pricing` 設定的覆寫值。這些是牌價，因此訂閱型提供者也會顯示每 token 的價格。

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| 欄位                                                            | 單位                    | 備註                                                                                                      |
| --------------------------------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | 每 token 美元，小數字串 | 相容於 OpenRouter，永不使用指數表示法。兩個快取欄位只有在存在快取價格時才會出現。                         |
| `input`, `output`, `cached`, `cache_creation`                   | 每 1M token 美元，數字  | 來自較早版本型錄的欄位，為現有用戶端保留。當定價列包含 `reasoning` 和 `long_context` 時，這兩者也會出現。 |

- **組合**會帶有其第一個可見目標的價格。內建的 `auto/*` 組合會在請求時選擇目標，因此不會有 `pricing`。
- **免費模型**的價格為零時會顯示 `"0"`（以及 `0`）。沒有定價列的模型，若型錄將其標記為免費（`free: true`），或內建的免費模型型錄列有該模型，也會顯示 `"0"`。
- **未知價格：**項目不會有 `pricing` 金鑰。
- **按額度計費的提供者**（例如 Kiro）會按請求而非按 token 計費。其項目會保留先前已有的每 1M 數字欄位，且不帶有每 token 的字串欄位。
- **變體**（推理強度 ID、無思考別名、探索和閘道鏡像）會複製其路由到的模型價格。
- 欄位只帶有基本費率。長內容層級（數字型的 `long_context` 欄位）和服務層級乘數（例如 Codex fast 或 flex）不會變更 `prompt` 或 `completion`。
- 對於所有驗證方式，物件都相同，包括帶有 `x-api-key` 和 `anthropic-version` 的 Anthropic 風格請求（回應仍為 `{ "object": "list", "data": [...] }`）。實作位置：`src/app/api/v1/models/catalogPricing.ts`。

### 模型 ID 前綴 (`?prefix=`)

大多數模型都會以**提供者前綴**發布。取得哪個前綴由 `MODELS_CATALOG_PREFIX_MODE` 功能旗標控制，也可以透過查詢參數針對**每個請求**覆寫——這對希望取得簡潔清單、但不想變更伺服器全域設定的用戶端很有用：

```bash
GET /v1/models?prefix=alias        # 每個模型一個 ID — 短別名前綴
GET /v1/models?prefix=dual         # 兩種形式（伺服器預設值）
GET /v1/models?prefix=canonical    # 僅完整的提供者 ID 前綴
```

| 模式        | 產出                                                     | 備註                                                                                                                                               |
| ----------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **和** `claude/claude-sonnet-4-6` | **預設值。**兩個 ID 都會路由至相同模型；予以保留，以便硬編碼任一形式的用戶端設定仍能正常運作。型錄大小約會加倍。                                   |
| `alias`     | `cc/claude-sonnet-4-6`                                   | 每個模型一個項目。沒有不同別名的提供者仍會產出其項目，因此不會遺漏任何內容。                                                                       |
| `canonical` | `claude/claude-sonnet-4-6`                               | 每個模型都使用完整的提供者 ID 前綴產出一個項目。沒有不同別名的提供者（例如 `antigravity/…`、`agy/…`）也會在此產出其單一 ID，因此不會遺漏任何內容。 |

`dual` 模式的鏡像也可以不使用查詢參數來辨識：它會帶有指向主要 ID 的 `parent` 欄位。

呈現模型選擇器的用戶端應請求 `?prefix=alias`——[OmniCopilot VS Code 擴充功能](../guides/VSCODE-COPILOT.md)就是這麼做的。

### 探索篩選條件 (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` 接受選擇性探索篩選條件。不使用任何篩選條件時，回應不變。這些篩選條件會縮小呼叫端原本可見的型錄範圍（先套用 API 金鑰權限），並且會在 OpenAI 風格的 `limit` / `after` 分頁之前執行：

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 列出的每項能力都必須為 true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # 型錄中的 `type`；沒有該欄位的列為 `chat`
GET /v1/models?q=sonnet&limit=10                           # 不區分大小寫地比對 ID 或名稱
```

| Param         | Values                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | 非負整數，與 `context_length` 比較                                                                  |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 個字元                                                                                        |

未知值，或不是非負整數的 `min_context`（例如 `1.5`），
會傳回 HTTP `400`，且訊息會列出有效值。實作位置：
`src/app/api/v1/models/catalogFilters.ts`。

### 模型候選清單 (`POST /v1/models/query`)

`POST /v1/models/query` 會從相同的目錄傳回簡短且具確定性的清單，並具有與
`GET /v1/models` 相同的驗證與每個金鑰的可見性：

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

所有欄位皆為選用。`capabilities` 和 `exclude` 可接受陣列或以逗號分隔的字串；
`max_output` 會與 `max_output_tokens` 比較。結果依 `owned_by`，再依 `id` 排序。
`limit` 預設為 `20`，高於 `100` 的值會限制為 `100`。無效的 JSON、未知欄位或無效值
會傳回 HTTP `400`。

### 個別隱藏的聊天模型

在其提供者頁面上標記為**隱藏**的模型會從目錄中排除，且在明確要求時會以 HTTP `404` /
`model_not_found` 拒絕。檢查會使用解析後的提供者與模型，包括提供者別名、
相容提供者節點前綴，以及連線預設值。組合會略過隱藏目標，並可使用可見的同類模型；
若沒有剩餘的可執行目標，則會傳回相同的錯誤代碼。取消隱藏會在下一個請求時生效。
僅限影像的可見性覆寫不會隱藏具有相同 ID 的聊天模型。

此個別模型設定與
[模型公開允許／拒絕清單](../routing/MODEL_EXPOSURE_LIST.md)分開；後者會篩選目錄
廣告與自動路由候選項目，同時保留明確派送。API 金鑰的模型權限仍會獨立套用。預設的目錄前綴模式仍為
`dual`。

### 無思考模型變體

對於支援思考功能的 Claude 模型，`/v1/models` 也會提供一個**無思考**變體，其 ID 會加上
`claude-3-omniroute-no-thinking/` 前綴：

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

選取此 ID（例如在總是附加 `thinking` 區塊的 Claude Code 設定中）會解析回真正的
`<provider>/<model>`，並停用推理——在 `/v1/messages` 路徑上使用
`thinking:{type:"disabled"}`，或在 `/v1/chat/completions` 路徑上捨棄
`reasoning`／`reasoning_effort` 欄位。只有支援思考功能**且**遵循 `disabled` 的 Claude 系列模型
才會列出此變體（因此，會拒絕 `disabled` 的僅支援自適應模式模型等不會列出）。操作人員可以透過
每個模型的 `ModelSpec.noThinkingAlias` 強制啟用或停用此變體。

## ElevenLabs 音訊生成

在 OmniRoute 中設定 `elevenlabs` provider 連線，並提供您的 ElevenLabs API 金鑰。
用戶端使用其 **OmniRoute** 金鑰進行驗證（`Authorization: Bearer $OMNIROUTE_API_KEY`）；
閘道會將儲存的 provider 金鑰以 `xi-api-key` 提供。請勿將 ElevenLabs 金鑰
作為閘道 bearer token 傳送。

| 方法 | 路徑                        | 回應                          | API 金鑰端點類別 |
| ---- | --------------------------- | ----------------------------- | ---------------- |
| POST | `/v1/sound-generation`      | 原生音訊位元組                | `elevenlabs`     |
| POST | `/v1/music`                 | 原生音訊位元組                | `music`          |
| POST | `/v1/music/stream`          | 串流音訊位元組                | `music`          |
| POST | `/v1/music/detailed`        | 原生 multipart 音訊與編曲計畫 | `music`          |
| POST | `/v1/music/detailed/stream` | 原生 SSE 中繼資料與音訊區塊   | `music`          |
| POST | `/v1/music/plan`            | JSON 編曲計畫                 | `music`          |

這些端點可補充現有的 `/v1/audio/speech`、`/v1/audio/transcriptions`、
`/v1/voices`、`/v1/text-to-speech/{voiceId}` 及 `/v1/speech-to-text` 路由。原生 JSON 欄位
及 `output_format`、`enable_logging` 等查詢參數均會保留。
`/v1/music/detailed` 回應會保留其 multipart 邊界；請將其解析為 multipart。
`/v1/music/detailed/stream` 會以 `text/event-stream` 傳回包含編曲中繼資料及
SSE 事件中 base64 音訊區塊的內容。全部六個路由都支援 CORS 預檢請求。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# A short sound effect. Duration: 0.5 to 30 seconds.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Music duration is expressed in milliseconds: 3000 to 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

使用 `/v1/music/stream` 搭配相同的 JSON 內容，以逐步傳送音訊。編曲內容
必須正好接受 `prompt` 或 `composition_plan` 其中一項；`/v1/music/plan` 需要 `prompt`
，並可選擇接受 `source_composition_plan`。原生結構描述會保留其他
provider 欄位，因此編曲計畫版本及微調選項都能傳送至 ElevenLabs。

統一的 `/v1/music/generations` 端點也接受
`elevenlabs/music_v1`、`elevenlabs/music_v2` 及 `elevenlabs/music_v2_5`。具備作用中的 ElevenLabs 連線時，
這些模型會由音樂目錄公開。此端點會傳回
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`。其 `duration` 欄位以
秒為單位，並對應至 `music_length_ms`；明確指定的 `music_length_ms` 具有優先權。
`instrumental` 對應至 `force_instrumental`，而原生欄位具有優先權。
串流請使用原生串流端點，僅由編曲計畫驅動的請求則請使用原生編曲端點。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

端點、模型、預算及連線限制會在呼叫上游之前套用。原生
路由會原樣傳回上游狀態碼及錯誤內容，包括計畫限制的 `402` 以及配額限制的 `429`。
存在時，`character-cost`、`song-id`、`request-id` 及 `retry-after`
標頭也會保留。免費額度餘額不保證能存取每個
音樂模型、輸出格式或 API 功能：ElevenLabs 會針對每個請求決定授權狀態。
統一端點會在 OmniRoute 的標準化錯誤封裝中保留錯誤狀態碼。

上游契約：[音效](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音樂編曲](https://elevenlabs.io/docs/api-reference/music/compose) 及
[串流音樂詳細資料](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。

```bash
# 重新排序（雲端註冊表提供者，或以 "<prefix>/<model>" 表示的 OpenAI 相容提供者節點）
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina 分類（Foundation API 憑證）
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina 分段器
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina 搜尋（s.jina.ai；提供者別名：jina-search、jina-ai、jina）
POST /v1/search      { "query": "...", "provider": "jina-search" }

# 審核
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — 回傳 audio/mpeg（或要求的格式）內容
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS 需要語言和語音：`language` 預設為 "en"；缺少
# 語音，或使用 OpenAI 預設語音名稱（alloy、nova、…）時，會變成 "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# 圖片編輯（multipart）
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# 影片／音樂生成（以提供者為前綴的模型 ID）
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **重新排序提供者節點：** `POST /v1/rerank` 也會路由至 OpenAI 相容的提供者節點
> (oMLX、vLLM、Infinity、閘道後的 TEI，……)，其位址格式為 `<node-prefix>/<model>`。迴路
> 節點 (`localhost`、`127.0.0.1`、`172.16.0.0/12`) 一律符合資格，操作者在
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` 中列出的主機名稱也同樣符合資格 (例如 Docker/Compose 服務名稱，
> 如 `http://reranker:8080/v1`；這些節點會直接呼叫，絕不透過 `HTTP(S)_PROXY` 或連線固定的
> Proxy)。位於任何其他主機上的節點 — LAN 電腦或 Tailscale 對等節點 — 只有在操作者啟用
> `RERANK_REMOTE_PROVIDER_NODES` 功能旗標，**且**節點的基礎 URL 通過提供者對外連線 URL 政策
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) 時才符合資格。
> 記憶體引擎的重新排序步驟會透過迴路呼叫此路由，因此相同規則也適用於記憶體設定中的
> `rerankProviderModel`。
>
> **本機伺服器形式：** 節點會呼叫 `<base>/v1/rerank`，若回應 404，則呼叫 `<base>/rerank`
> (Infinity、TEI)。上游主體同時包含 Cohere/OpenAI 拼法 (`documents`、
> `return_documents`) 和 TEI 拼法 (`texts`、`return_text`)，而上游回應會正規化為 Cohere
> 封裝格式：TEI 的裸 `[{index, score, text}]`、精簡閘道傳回的 `{results: [{index, score}]}`
> 以及 Voyage 風格的 `{data: [...]}`，都會以
> `{results: [{index, relevance_score, document?}]}` 的形式傳回用戶端，按分數排序並限制為 `top_n`。

> **提供者節點探索：** OpenAI 相容提供者節點上的模型會以節點前綴顯示於 `GET /v1/models`
> 中。未帶有端點中繼資料的列 (本機 `/v1/models` 清單通常如此) 會繼承節點的
> `apiType`，因此 `embeddings` 節點的模型其 `type: "embedding"`，而 `rerank` 節點的模型其
> `type: "rerank"`，不會預設為聊天；同步或手動新增的列若明確指定
> `supportedEndpoints`，仍優先採用該值。


如果缺少提供者前綴，系統會自動新增。模型不相符時會回傳 `400`。

## 檔案 API

相容於 OpenAI 的檔案端點，用於批次輸入/輸出和檔案用途上傳。

| 方法   | 路徑                     | 說明                                                                                                      |
| ------ | ------------------------ | --------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | 上傳檔案（multipart：`file`、`purpose`、`expires_after[anchor]`、`expires_after[seconds]`）— 最大 512 MiB |
| GET    | `/v1/files`              | 列出已驗證 API 金鑰的檔案                                                                                 |
| GET    | `/v1/files/[id]`         | 擷取檔案的中繼資料                                                                                        |
| DELETE | `/v1/files/[id]`         | 刪除檔案                                                                                                  |
| GET    | `/v1/files/[id]/content` | 串流傳回原始檔案內容                                                                                      |

**驗證：** Bearer API 金鑰 — 檔案會透過 `getApiKeyRequestScope` 依 API 金鑰進行範圍限定。金鑰
只能查看、下載及刪除其自身的檔案；沒有金鑰的儀表板工作階段可讀取整個執行個體；沒有擁有者的
檔案（匿名上傳或儀表板工作階段上傳）會拒絕所有非工作階段呼叫者的存取。即使
`REQUIRE_API_KEY=false`，`GET /v1/files` 仍會以 `401` 拒絕匿名呼叫者，以及無法解析的已提供金鑰，
而不會列出所有租戶的檔案（GHSA-m3hp-hq9g-fpmv、GHSA-2jm2-mpx8-6523）。

## 批次 API

相容於 OpenAI 的批次處理。

| 方法   | 路徑                      | 說明                                                                                             |
| ------ | ------------------------- | ------------------------------------------------------------------------------------------------ |

## 搜尋 API

Web／搜尋提供者抽象層（Tavily、Brave、Exa、Serper 等）。

| 方法 | 路徑                   | 描述                                                                |
| ---- | ---------------------- | ------------------------------------------------------------------- |
| GET  | `/v1/search`           | 列出已設定的搜尋提供者及其功能                                      |
| POST | `/v1/search`           | 執行搜尋查詢 — 要求內容由 `v1SearchSchema` 驗證，支援快取／合併請求 |
| GET  | `/v1/search/analytics` | 各提供者的命中率／延遲／快取統計                                    |

**驗證：** Bearer API 金鑰（`extractApiKey` + `isValidApiKey`）。搜尋政策透過 `enforceApiKeyPolicy` 強制執行。

**自動選擇：** 未指定 `provider` 時，會先使用已設定連線中最便宜的提供者，下一個最便宜的提供者則作為故障轉移。免費的最終備援提供者（`duckduckgo-free`）只會在沒有設定其他提供者時使用。自架的 SearXNG 一旦其連線儲存了實際的 `baseUrl`（而非目錄預設值 `http://localhost:8888/search`），就會被視為已設定；接著它會以 $0 提供者的身分排在具金鑰提供者之前，並以最便宜的具金鑰提供者作為故障轉移，即使 SearXNG 回應 400、401、403 或 404 也是如此。不是有效 `http(s)` URL 或指向雲端中繼資料位址的 `baseUrl` 不會被視為已設定。儲存了權杖的 SearXNG 連線只有在使用 `https://` 或迴路 `http://` 時才會以此方式排序。對遠端純 `http://` 而言，它永遠不會作為故障轉移，並維持為最終備援；只有在未設定其他提供者或按名稱要求時才會使用，因此在這兩種情況下確實會以明文傳送權杖。

### Exa 和 Tavily 的 `provider_options`

Exa 和 Tavily 會從具命名空間的資料袋讀取提供者專用欄位：
`provider_options.exa`（或 `provider_options["exa-search"]`）以及 `provider_options.tavily`
（或 `provider_options["tavily-search"]`）。只有下列金鑰會被轉送。每個金鑰都會在
`open-sse/handlers/search/providerOptionsPassthrough.ts` 中針對其自身的 Zod schema 進行檢查，類型錯誤的金鑰會被捨棄。任何其他金鑰都會被忽略，包括驗證、基底 URL、`stream` 和 `outputSchema`。其他提供者使用的扁平金鑰（`cx`、`depth`……）維持原有運作方式。

| 提供者 | 頂層欄位                                                                                                                                                                                                                                                                                                                                                                  | 巢狀欄位                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Exa    | `type`、`category`、`userLocation`、`moderation`、`additionalQueries`、`objective`、`systemPrompt`、`compliance`（扁平基本值）、`startPublishedDate`、`endPublishedDate`                                                                                                                                                                                                  | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` 合併於預設值 `{ text: true, highlights: true }` 之上 |
| Tavily | `search_depth`、`chunks_per_source`、`time_range`、`start_date`、`end_date`、`include_published_date`、`filter_by_published_date`、`include_answer`、`include_raw_content`、`include_images`、`include_image_descriptions`、`include_favicon`、`include_domains_mode`、`language`、`filter_by_language`、`auto_parameters`、`exact_match`、`include_usage`、`safe_search` | —                                                                                                                                  |

通用欄位一律優先：`query`、`max_results`、`filters`（網域）、`country`，以及從 `search_type` 衍生的主題。在 Exa 中，`search_type: "news"` 會保留 `category: "news"`。Tavily 也接受 `search_type: "finance"`（`topic: "finance"`）。

Firecrawl 搜尋費用會按照每開始一個包含 10 個傳回結果的區塊來記錄，每個區塊費用為 $0.002（2 個點數），且每次呼叫至少計費一個區塊
（[Firecrawl 計費](https://docs.firecrawl.dev/billing)）：11 個結果的費用為 $0.004。

通用的 `time_range` 現在會傳送至兩個提供者：Exa 取得 `startPublishedDate`（ISO 時間戳記），Tavily 取得 `start_date`（`YYYY-MM-DD`）。`provider_options` 中明確指定的日期會覆寫映射後的日期。

Exa 結果會在 `provider_raw` 中保留 `id`、`highlights`（每個 highlight，而不只是作為 `snippet` 使用的第一個）、`highlight_scores`、`summary`、`subpages`、`entities` 和 `extras`。Tavily 結果會保留 `images` 和 `favicon`。

Linkup 搜尋費用會記錄為：`depth` 為 `fast` 和 `standard` 時為 $0.005，`deep` 時為 $0.05（[Linkup 定價](https://docs.linkup.so/pages/documentation/development/pricing)），無論 `depth` 來自 `provider_options` 還是連線設定。

Exa `type: "lite"`（Exa 3.0）接受的欄位集合較小，若設定了任何其他欄位，則會拒絕整個要求。對 lite 而言，呼叫前會捨棄 `additionalQueries`、`systemPrompt` 以及除 `text` 和 `highlights` 之外的所有 `contents` 金鑰。已棄用的 `subpages`、`subpageTarget`、`highlights.numSentences` 和 `highlights.highlightsPerUrl` 不再轉送。

成本計算採用固定登錄表 `costPerQuery`，但 Exa 例外，依循 Exa 自身的定價：`auto`（以及舊版的 `fast`）每次呼叫 $0.007，或 `lite`（以及舊版的 `instant`）每次呼叫 $0.004，均涵蓋 10 筆結果；每增加一筆結果則為 $0.001；設定 `contents.summary` 時，每筆回傳結果為 $0.001。Tavily 對 `search_depth` 為 `basic`、`fast` 和 `ultra-fast` 的請求記錄為 1 點數（$0.008），對 `advanced` 則記錄為 2 點數（$0.016）
（[Tavily API 點數](https://docs.tavily.com/documentation/api-credits)）。使用
`auto_parameters: true` 的請求若 Tavily 升級為 advanced，仍記錄為 1 點數。

## Web Fetch API

透過已設定的 Web 擷取提供者（Firecrawl、Jina
Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）從 URL 擷取內容。

Parallel Extract（`parallel-search`，與 Parallel Search 使用相同的 API 金鑰）僅回傳 Markdown — 任何其他 `format` 都會產生 `400`，且內容上限為 100,000 個字元。當目標頁面本身無法擷取時，上游會在 HTTP 200 中回報此狀況；OmniRoute 會將其呈現為帶有固定訊息的 `422`。

| Method | Path            | Description                                      |
| ------ | --------------- | ------------------------------------------------ |
| POST   | `/v1/web/fetch` | 擷取／抓取 URL — body 由 `v1WebFetchSchema` 驗證 |

**驗證：** Bearer API 金鑰（`extractApiKey` + `isValidApiKey`）。透過 `enforceApiKeyPolicy` 強制執行原則。

**配額感知回退（#8297）：** 未明確提供 `provider` 時，會依固定優先順序（先填滿）遍歷提供者池（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`）：遭到速率限制但已設定的提供者會被跳過，而不會使請求提前結束；可重試／配額相關的上游失敗（HTTP 429 一律如此；對 Firecrawl／Tavily／TinyFish 的配額型免費層級而言，402/403 也屬於此類 — Jina Reader 不適用，普通的 400 錯誤請求也永遠不適用）會在請求執行期間繼續嘗試下一個尚未嘗試且具憑證的提供者。當提供者池中的所有提供者都耗盡時，端點會回傳單一 `429`（並附帶 `Retry-After` 標頭），而非先前的通用 `400`。明確請求 `provider` 時，**不會**進行靜默回退 — 遭到速率限制或失敗的明確提供者會呈現自身的錯誤（遭到速率限制時為 `429`，否則為上游狀態）。

## WebSocket 串流

```bash
GET /v1/ws?handshake=1
```

驗證 WebSocket 升級交握，並回傳線上協定範例訊息（`request`、`cancel`）。實際的 WS frame 由內建的 WS 伺服器在 Next.js 路由表之外處理。

**驗證：** 交握期間使用 Bearer API 金鑰。

### WebSocket 上的 Responses API（僅限 codex）

```bash
# 與 HTTP API 使用相同的主機埠號（預設為 20128）；升級連線：
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （或：-H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 第一個 frame 必須是 response.create：
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket 代理**僅連接至 `codex`**（ChatGPT 後端）。它會在與 API／儀表板相同的埠號上，於 `/v1/responses`、`/responses` 和 `/api/v1/responses` 路徑監聽。在第一個 `response.create` frame 上，它會透過內部 `codex-responses-ws` bridge 進行驗證與準備工作，選取 codex OAuth 連線，然後透過 `wreq-js` 傳輸通道建立隧道連線至 `wss://chatgpt.com/backend-api/codex/responses`。**非 codex 模型會被拒絕**（`codex_ws_provider_required`）。若要使用配額共享路由，請使用 `model: "qtSd/<group>/codex/<model>"`。實作位於 `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`。

**驗證：** 交握期間使用 Bearer API 金鑰。內建 HTTP 伺服器（`server-ws.mjs`）必須是作用中的進入點（當 `app/server-ws.mjs` 存在時，預設即是如此）。

#### 模型 id：使用不帶前綴的 ChatGPT id（不要使用 `codex/` 前綴）

當 `supports_websockets = true` 時，OpenAI **Codex CLI** 會在用戶端驗證模型名稱，並拒絕類似 `codex/gpt-5.5` 的提供者前綴 id（`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`）。請傳送**不帶前綴**的 id（例如 `gpt-5.5`）。OmniRoute 的 bridge 僅限 codex，因此會在建立上游隧道前，將不帶前綴的 id 重新解析為 codex 模型（`resolveCodexWsModelInfo`）— 即使不帶前綴的 `gpt-5.5` 在 HTTP 上原本會路由至其他提供者。

#### 設定 OpenAI Codex CLI

將自訂提供者與 WebSocket 支援新增至 `~/.codex/config.toml`，即可將 Codex CLI 指向 OmniRoute（使用獨立的 `CODEX_HOME`，以避免修改現有設定）：

```toml
model = "gpt-5.5"                 # 不帶前綴的 id — NOT "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 不含結尾斜線；WS URL 會從此衍生（正式環境請使用 https/wss）
wire_api = "responses"                    # 自 2026 年 2 月起唯一支援的值
supports_websockets = true                # 啟用 Responses-over-WS 傳輸
env_key = "OMNIROUTE_API_KEY"             # 儲存 OmniRoute API 金鑰（Bearer）
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API 金鑰（當 REQUIRE_API_KEY=false 時可使用任何金鑰）
codex exec "Responda apenas: PONG"
```

CLI 會將 `base_url + /responses` 升級為 WebSocket，而 OmniRoute 會將其建立隧道連線至選取的 codex OAuth 連線。已針對本機伺服器完成端對端驗證：ChatGPT 會回傳 `codex.rate_limits` + `response.created` 並串流完成結果。

## 自助式使用量（`/api/usage/om-usage`）

任何 API 金鑰都可以讀取**自己的**使用量與配額，不需要管理驗證。這是用戶端（CLI、OmniCopilot 面板）用來向金鑰持有者顯示其支出的端點。

```bash
# 文字格式（歷史合約 — 終端機使用的純文字）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 結構化格式 — UI 使用的格式
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

金鑰必須啟用 **`allowUsageCommand`**（預設關閉 — 儀表板的 API 金鑰管理器可逐一切換此設定）。若未啟用，端點會回應 `403`。

`?format=json` 會回傳具辨識性的結構，因此呼叫端不會從拒絕回應中讀取資料欄位。成功時：

```jsonc
{
  "allowed": true,
  // 僅在金鑰選擇啟用每金鑰使用量限制（日／週 USD）時存在：
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 所選提供者的配額快照；尚未快取任何資料時為 null：
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // 每個連線的快照，讓 UI 可以並排呈現多個提供者：
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

拒絕時（`401` 金鑰無效／`403` 未獲允許），相同路由會回傳
`{ "allowed": false, "error": { "message": "…" } }` — 存在但為空的 `personal`／`provider`
（已允許金鑰，但尚未取得任何資料）與拒絕是不同狀態，只有 JSON 格式能區分這兩者。

**驗證：** 呼叫端自己的 Bearer API 金鑰，使用 `isValidApiKey` 驗證 — 這**不是**管理介面（`/api/keys/…`），後者仍受 `requireManagementAuth` 保護。

### 原始配額百分比與截止值調整後的配額百分比

使用 `/api/usage/om-usage` 時，呼叫端應注意**純文字輸出**與結構化 **JSON 輸出**所呈現的百分比之間的差異：

| 面向           | 純文字格式（`/api/usage/om-usage` / `@@om-usage`）                            | JSON 格式（`?format=json`）                                |
| :------------- | :---------------------------------------------------------------------------- | :--------------------------------------------------------- |
| **輸出欄位**   | `NN% left`（例如 `20% left`）                                                 | `provider.quotas` / `providers[].quotas`                   |
| **測量方式**   | **截止值調整後的可用額度**：截止值門檻以上的剩餘容量                          | **上游原始配額**：未調整的提供者測量值                     |
| **截止值縮放** | 透過 `effectiveRemainingPercent()` 進行縮放，使受保護的保留額顯示為 `0% left` | 無（提供者回報的原始快照值）                               |
| **門檻資料**   | 納入所顯示的百分比                                                            | 依連線儲存於 `quotaWindowThresholds`（或使用伺服器預設值） |
| **主要使用者** | 互動式 CLI、終端機提示、操作人員                                              | 程式化整合、儀表板、分析、計費追蹤器                       |

#### 截止值調整公式

OmniRoute 支援主動式配額截止值，以防止上游配額耗盡（可透過連線的
`quotaWindowThresholds`、提供者預設值或全域恢復能力設定進行設定）。當配額視窗啟用截止值門檻（例如 `cutoff = 25%`）時，文字轉譯器會依以下方式計算剩餘額度：

- 若 `remaining <= cutoff`：回傳 `0%`。
- 若 `remaining > cutoff`：回傳 `((remaining - cutoff) / (100 - cutoff)) * 100`。

格式化的文字輸出會將結果四捨五入至最接近的整數（`Math.round(...)`）。

#### 說明性範例

考量一個具有 **60% 原始使用量**（因此剩餘 **40% 原始配額**）且設定
**25% 剩餘配額截止**閾值的提供者視窗：

| 表示方式                       | 計算方式                                           |  剩餘   |             隱含使用量              |
| :----------------------------- | :------------------------------------------------- | :-----: | :---------------------------------: |
| **原始 JSON (`?format=json`)** | 上游快照（`quotas[window]`）                       | **40%** |               **60%**               |
| **文字格式 (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%**（若計算 `100 - remaining`） |

- **為什麼文字顯示剩餘 20%：** 在帳戶實際剩餘的 40% 配額中，25% 由截止政策保留。呼叫端在路由器停止將流量
  路由至此連線前，實際上只剩下 75% 可用餘裕中的 15%。進行縮放可確保連線在路由停止時，恰好顯示耗盡
  （剩餘 `0% left`）。
- **為什麼 JSON 保留原始值：** JSON payload 會傳回確切的提供者快照（`UsageSnapshot`），因此外部工具可以存取
  真實的上游使用量，以及連線層級的 `quotaWindowThresholds`，不受伺服器端有損縮放影響。

#### 消費者遷移指南

如果外部整合（例如編輯器外掛程式或代理程式擴充功能）過去會擷取文字端點（`NN% left`），並將已使用百分比計算為 `100 - NN`，
遷移至 `?format=json` 表示：

- 讀取原始 JSON 值將反映**實際的上游使用量**（上述範例中已使用 60%）。
- 如果整合希望保留文字端點的可用額度語意，可以使用連線層級覆寫的 `quotaWindowThresholds`，在用戶端評估有效剩餘量公式。

## 語意快取

```bash
# 取得快取統計資料
GET /api/cache/stats

# 清除所有快取
DELETE /api/cache/stats
```

回應範例：

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### 延遲影響

語意快取命中會直接從快取提供回應，**不會呼叫上游**，因此回報的 `X-OmniRoute-Response-Latency` 接近零（無論原始上游延遲為何）。對延遲敏感的用戶端（基準測試、p50/p99 監控）應檢查 `X-OmniRoute-Cache-Latency` 回應標頭：

| 值          | 意義                                   |
| ----------- | -------------------------------------- |
| `synthetic` | 回應由快取提供；延遲不是真實的上游時間 |
| _(不存在)_  | 回應來自真實的上游呼叫                 |

### 依金鑰略過快取

API 金鑰可以透過 `cacheDefaultMode` 選擇略過語意快取讀取：

| 值       | 行為                           |
| -------- | ------------------------------ |
| `legacy` | 一般快取行為（預設）           |
| `bypass` | 完全略過快取查詢；一律命中上游 |

在建立金鑰時（`POST /api/keys`）或更新金鑰時（`PATCH /api/keys/[id]`）設定：

```json
{ "cacheDefaultMode": "bypass" }
```

### 依請求略過快取

任何請求都可以略過快取，不受金鑰設定影響：

```
X-OmniRoute-No-Cache: true
```

## CLIProxyAPI 管理相容性

OmniRoute 會回應三個 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) 管理端點，供使用量儀表板讀取 Claude 和 Codex 訂閱限制（例如 T3 Code 的 `cliproxy` 使用量限制來源）。將用戶端的基底 URL 指向 OmniRoute，並使用具有 `manage` 範圍的 API 金鑰作為管理金鑰。這些路由提供於 `/v0/management/*` 和 `/api/v0/management/*`。

| 方法 | 路徑                         | 說明                                                                                                                         |
| ---- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GET  | `/v0/management/auth-files`  | Claude 和 Codex OAuth 連線，格式為 `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`。不包含權杖        |
| POST | `/v0/management/api-call`    | 主體為 `{ auth_index, method, url, header?, data? }`。使用帳戶的權杖傳送一個允許清單中的請求，並回傳 `{ status_code, body }` |
| POST | `/v0/management/reset-quota` | 主體為 `{ auth_index }`。清除一個帳戶的連線冷卻時間、模型鎖定和 Codex 各範圍冷卻時間                                         |

- `auth_index` 是 OmniRoute 連線 ID。`provider` 為 `claude` 或 `codex`（僅限 OAuth
  連線；`anthropic` API 金鑰提供者不會列出）。對 Codex 而言，
  `id_token.chatgpt_account_id` 是儲存的工作區 ID，而 `plan_type` 是儲存的方案。
- `api-call` 不是通用代理。它只接受 Claude 的 `GET
https://api.anthropic.com/api/oauth/usage`，以及 Codex 的 `GET
https://chatgpt.com/backend-api/wham/usage`、`GET .../wham/rate-limit-reset-credits` 和
  `POST .../wham/rate-limit-reset-credits/consume`，且每個請求只能針對相符提供者的帳戶。其他任何請求都會回傳 `403`，且不會聯絡上游。呼叫端的
  `Authorization` 標頭（包括 `$TOKEN$` 預留位置）會被忽略：OmniRoute 會注入連線的存取權杖，在權杖即將過期時先重新整理，並且只轉送
  允許清單中的標頭（`anthropic-beta`；`OpenAI-Beta`、`Originator`、`Chatgpt-Account-Id`；
  `Accept`、`Content-Type`）。缺少 `Chatgpt-Account-Id` 時，會預設使用儲存的工作區 ID。
  請求會在 15 秒後逾時，並使用連線的代理。
- `reset-quota` 不會變更終端狀態（banned、expired、credits_exhausted）。未知的
  `auth_index` 會回傳 `404`。

**驗證：**即使停用登入，也需要儀表板工作階段或具有 `manage` 範圍的 API 金鑰（這些路徑位於 `ALWAYS_PROTECTED_API_PATHS`）。僅限推論的金鑰會得到 `403`。來源：`src/lib/cliproxyCompat/managementApi.ts`。

對於同步／匯入的模型，`PUT /api/provider-models` 接受 `provider`、`modelId` 與
`maxOutputTokenOverride`：正整數會設定手動輸出 token 上限，而 `null`
會清除該設定並恢復預設值。`GET /api/provider-models?provider=<provider>` 會在
`modelOutputOverrides` 中傳回這些值，包括沒有自訂模型資料列的模型。此覆寫使用執行階段的
`max_output_tokens` 功能，並且在模型重新同步後仍會保留。OpenAI 相容的
提供者頁面提供相同的編輯／清除控制項，並標示具有明確視覺支援的模型。

在相容的提供者節點上，寫入路徑（`POST`、`PUT`、`PATCH`、`DELETE` 與
`/api/provider-models/validate-and-add`）會將模型 ID 儲存為不帶前綴的上游 ID：從帶前綴的清單貼上的 ID，其開頭連續的節點自身前綴會被合併，而回應會回傳儲存的 ID。規範提供者的斜線 ID（例如 `nvidia/nemotron-…`）會原樣儲存。`/v1/models` 絕不會產生堆疊的 `<prefix>/<prefix>/<model>` ID。

自訂 Chat Completions 節點會將明確的推理停用要求轉換為上游後端可用的格式。成功的連線測試會自動為每個確切的模型 ID 選取聊天範本控制項，前提是其 `/models` 項目證明具有可識別的 `owned_by` 值：`vllm`、`sglang` 或 `llamacpp`。透明的 OpenAI 相容包裝器可能會在巢狀的 `openai` 物件中保留原始模型項目；偵測最多會沿著三層此類封裝進行。缺少、未知或相互衝突的擁有者資訊的模型，會維持一般的 OpenAI 行為。偵測會重用現有的目錄要求，不會產生任何完成 token，且連線端點變更時會失效。

若要為不公開此中繼資料的後端固定行為，請使用現有的部分提供者更新 API：

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

將該內容與 `PUT /api/providers/<connection-id>` 一起傳送。在該連線上，明確的推理努力程度 `none` 會以 `chat_template_kwargs.thinking=false` 和 `chat_template_kwargs.enable_thinking=false` 傳送。除非伺服器端的推理規則強制指定某個努力程度，否則明確的原生範本值仍具有優先權。此設定僅在自訂 OpenAI 相容連線分派 Chat Completions 主體時套用；Responses 要求和一般提供者會維持其原生要求格式。將 `reasoningControl` 設為 `openai` 可強制一般 OpenAI `reasoning_effort` 直通，或省略它／將其設為 `null` 以使用自動偵測。

Claude Code 自動模式分類器要求在未包含明確推理控制項時，預設會停用原生思考功能。偵測會使用 Claude 格式要求中的分類器系統標記，而不是模型名稱或完成限制。明確的主體控制項、受支援的努力程度／思考標頭、路由規則和已解析的模型努力程度，會維持其既有優先順序。兩個分類器階段都會保留其提示、完成限制、停止序列，以及上游實際的權限判定；第二階段仍可能將其要求的可見推理產生為一般文字。

### 影片影格深入檢視

`GET /api/v1/video-bridge/drilldown` 會讀取在明確獲得同意的 Video Bridge 請求後，
於 `x-omniroute-video-drilldown` 中傳回、與租戶綁定的不透明控制代碼。
讀取與 `DELETE` 一律需要有效的 API 金鑰，以及操作員個別的
`modalityBridgeVideoDrilldownRemoteEnabled` 權限。正式環境的保留功能另外需要
`modalityBridgeVideoDrilldownEnabled`，且每個部分都必須嚴格設定 `drilldown: true`。
如果金鑰具有非空的端點允許清單，則無論呼叫端使用 `/v1` 或 `/api/v1`，
GET 與 DELETE 都必須包含 `video`。

GET 查詢：必要的 `handle`；選用的 `variant`（`preview`、`standard`、`detail`）、
`limit`（1–8；接受舊版 `frames`，但不可與 `limit` 一併使用）、
從零開始計算的 `page`，以及以秒為單位的 `start`/`end`。如果同時提供兩個焦點界限，
`end` 必須大於 `start`。重複或未知的查詢鍵會遭拒。成功的回應包含
`derivation`、`durationSeconds`、`frames`、`hasMore`、`page`、`variant`，以及選用的
`focusWindow`；no-store JSON（包括 Base64）上限為 32 MiB。輸出過大時會回傳 413；
請求較少的影格。

`DELETE /api/v1/video-bridge/drilldown?handle=...` 會回傳 `{ "removed": 0|1 }`。
未知、已過期及跨金鑰的 GET 都會回傳無法區分的 404；跨金鑰 DELETE 無法移除擁有者的項目。
停用的存取會回傳 403，缺少或無效的驗證會回傳 401，無效查詢會回傳 400，
取消會回傳 499，暫時性錯誤會回傳 503。控制代碼僅限處理程序內使用，十分鐘後過期，
且重新啟動後不會保留。新控制代碼使用 `v1.` 加上 32 位元組的隨機 Base64URL 權杖；
僅會保留權杖雜湊。為保持相容性，舊版 64 位十六進位權杖仍可依語法讀取。
請參閱[Video Bridge 防護措施](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets)，
以取得同意、配額及變體衍生的詳細資訊。

### 版本與發布頻道

```bash
GET /api/system/version
```

僅限迴路介面的管理路由（管理員驗證）。回傳執行中的版本、最新發布版本以及自動更新狀態。`releaseChannel` 和 `channels` 是新增欄位（rail 3.8.54）；`channel` 維持其原有意義，即儀表板更新程式所使用的部署模式（`npm`、`source` 或 `docker-compose`）。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 執行中建置的 npm 頻道：對於 `-nightly.*` 版本為 `nightly`，對於其他預發布版本（`-rc.*`、`-beta.*`、`-alpha.*`）為 `next`，對於比 `channels.latest` 更早主要版本的穩定版本為 `lts`，否則為 `latest`。規則與 `scripts/release/dist-tag.mjs` 相同，該檔案會在發布時選擇 npm dist-tag。
- `channels` — 每個 dist-tag 的已發布最新版本，來源為 `npm view omniroute dist-tags`（註冊表 HTTP 備援），並與 `latest` 使用相同的 10 分鐘 TTL 進行快取。`latest` 一定存在（依序退回 `latest` 欄位，然後是 `"unavailable"`）；只有在該 dist-tag 存在時，才會出現 `next`、`nightly` 和 `lts`。`Cache-Control: no-cache` 請求會重新整理兩項查詢。

頻道模型（4.0 GA 之前，`latest` = v3；`next` = rc；`nightly` = `develop` 建置；4.0 GA 之後，`lts` = v3 修補版本）詳述於 `docs/ops/RELEASE_STRATEGY.md`。

## 音訊轉錄

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

使用任何已設定的 STT 提供者轉錄音訊檔案。第一個路徑片段會選取原生提供者（`openai/…`、`deepgram/…`）。重新匯出其他廠商模型的閘道會使用限定識別碼
（`openrouter/deepgram/nova-3`）。

**請求：**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**回應：**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**模型 ID 範例：** `openai/whisper-1`（需要 OpenAI 金鑰）、
`openrouter/deepgram/nova-3`（需要 OpenRouter 金鑰）、
`deepgram/nova-3`（需要原生 Deepgram 金鑰）。單獨使用
`deepgram/nova-3` 的請求**不會**使用 OpenRouter。

**支援的格式：** `mp3`、`wav`、`m4a`、`flac`、`ogg`、`webm`。

**Gemini Live（`gemini/gemini-3.5-transcribe-live`）：** 透過 Gemini Live
WebSocket 以檔案模式進行轉錄（需要 Gemini API 金鑰）。上傳內容會使用 `ffmpeg`
轉換為 16 kHz 單聲道 PCM（除非檔案已是 16 kHz 單聲道 PCM WAV，否則 `ffmpeg` 必須位於
`PATH` 中），串流至工作階段後，會以 `{ "text": "..." }` 的形式傳回最終文字。選用的
`language` 和 `prompt` 表單欄位會被轉送。限制：超過 25 MiB 的上傳檔案或解碼後長度超過 10 分鐘的音訊會回應
`413`；執行時間超過 60 秒的轉換程序會被終止，並回應 `504`。API 金鑰只會透過
`x-goog-api-key` 標頭傳送，絕不會放在 WebSocket URL 中。

當整合無法注入 `Authorization` 標頭，且需要將 API 金鑰嵌入基底 URL 時，請使用這些別名。

## 權杖限制

每個 API 金鑰的 **權杖** 預算（不同於上述以 USD 為基礎的預算）。在請求路徑上直接強制執行：當金鑰在目前視窗中的使用量達到其限制時，請求會遭拒並回傳 `429 Too Many Requests`。限制可以限定於特定的 `model`、`provider`，或套用至跨金鑰的 `global`；當多個限制符合請求時，以限制最嚴格者為準。

```bash
# 列出金鑰的權杖限制（包含即時視窗使用量）
GET /api/usage/token-limits?apiKeyId=key-123

# 建立或更新權杖限制
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# 依 ID 刪除權杖限制
DELETE /api/usage/token-limits?id=tl-abc
```

> **結構描述注意事項** (`setTokenLimitSchema`)：`apiKeyId` 和 `scopeType` (`model` | `provider` | `global`) 為必要欄位。除非 `scopeType` 為 `global`，否則 `scopeValue` 為必要欄位（例如，`model` 範圍的模型 ID、`provider` 範圍的提供者 ID）。`tokenLimit` 必須是正整數（會從字串強制轉型）。選用欄位：`id`（建立時省略，更新時提供）、`resetInterval`（`daily` | `weekly` | `monthly`，預設為 `monthly`）、`resetTime`（`HH:MM`）、`enabled`（預設為 `true`）。`GET` 回應會為每項限制補充 `tokensUsed`、`remaining`、`windowStart`、`periodStartAt` 和 `nextResetAt`。這是管理類別端點（由授權管線集中強制執行驗證）。

## 請求處理

1. 用戶端將請求傳送至 `/v1/*`
2. 路由處理常式呼叫 `handleChat`、`handleEmbedding`、`handleAudioTranscription` 或 `handleImageGeneration`
3. 解析模型（直接指定的提供者／模型，或別名／組合）
4. 從本機資料庫選取憑證，並篩選可用帳戶
5. 對於聊天請求：`handleChatCore` 檢查語意／簽章快取，並解析組合壓縮設定
6. 啟用時，在提供者轉譯之前執行主動壓縮（`lite`、Caveman、RTK 或堆疊模式）
7. 提供者執行器傳送上游請求
8. 將回應轉譯回用戶端格式（聊天），或原樣回傳（嵌入／圖片／音訊）
9. 記錄使用量、壓縮分析資料和請求記錄
10. 發生錯誤時，依據組合規則套用備援

完整架構參考：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 彈性（延伸）

OmniRoute 提供三種彼此獨立的暫時性失敗機制；以下管理端點可讓操作人員讀取並覆寫這些機制：

| 範圍            | 狀態儲存                             | 讀取                                      | 重設／清除                                   |
| --------------- | ------------------------------------ | ----------------------------------------- | -------------------------------------------- |
| Provider 斷路器 | `domain_circuit_breakers` + 記憶體內 | `/api/monitoring/health`                  | `POST /api/resilience/reset`                 |
| 連線冷卻        | Provider 連線上的 `rateLimitedUntil` | `/api/rate-limits`、`/api/providers/[id]` | （會延遲重新啟用；可透過 Provider PUT 清除） |
| 模型鎖定        | 記憶體內的模型可用性登錄             | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`     |

`PATCH /api/resilience` 接受位於 `providerBreaker.oauth` 和 `providerBreaker.apikey` 下的 Provider 斷路器覆寫設定。每個設定檔都支援 `degradationThreshold`、`failureThreshold` 和 `resetTimeoutMs`；相同欄位也會在 Dashboard → Settings → Resilience 中公開。

```bash
# 清除單一模型鎖定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# 清除所有鎖定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

完整的概念參考與斷路器預設值，請參閱 [`CLAUDE.md`](../../CLAUDE.md) → 「Resilience 執行階段狀態」以及 [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)。

### 速率限制佇列與自動啟用安全網

- **支援的寫入路徑**：`POST /api/rate-limits` 搭配本文 `{"connectionId": "<id>", "enabled": true|false}`，是切換連線速率限制防護功能的支援管理端點。`PUT /api/providers/[id]` 刻意不會修改或切換 `rateLimitProtection`（#11278）。
- **`enabled: false` 的語意**：設定 `enabled: false` 會移除該連線的明確防護，但**不會**讓啟用中的 API 金鑰連線退出全域自動啟用安全網（`autoEnableApiKeyProviders = true`）。在 `reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）中，`false` 與 `undefined` 等價；沒有明確防護的啟用中 API 金鑰連線仍會受到自動啟用安全網的防護。
- **全域停用**：若要在沒有速率限制佇列的情況下執行 API 金鑰連線，請透過 `RATE_LIMIT_AUTO_ENABLE=false`（環境變數）或 `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（Settings → Resilience / `PATCH /api/resilience`）全域停用安全網。

## A2A 伺服器

OmniRoute 提供 A2A（Agent-to-Agent）JSON-RPC 2.0 端點，以及用於檢查／儀表板的 REST 包裝器。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # 除非已設定 OMNIROUTE_API_KEY，否則為選用
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

支援的方法（全部受 `settings.a2aEnabled` 控制）：

| Method           | Description                                      |
| ---------------- | ------------------------------------------------ |
| `message/send`   | 同步技能執行；傳回 `{task, artifacts, metadata}` |
| `message/stream` | 對相同技能集執行串流 SSE                         |
| `tasks/get`      | 依 `taskId` 擷取工作                             |
| `tasks/cancel`   | 依 `taskId` 取消工作                             |

內建技能：`smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### Agent Card

```bash
GET /.well-known/agent.json
```

傳回公開的 A2A 代理卡片（名稱、描述、功能、技能目錄、驗證配置）—公開快取 1 小時。無需驗證。

### REST 輔助端點

| Method | Path                         | Description                                                                                                    |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A 是否啟用 + 工作統計 + 已快取的代理卡片摘要                                                                 |
| GET    | `/api/a2a/tasks`             | 列出工作 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST   | `/api/a2a/tasks`             | （未實作為 REST 輔助端點 — 請透過 JSON-RPC `message/send` 建立）                                               |
| GET    | `/api/a2a/tasks/[id]`        | 擷取單一工作                                                                                                   |
| POST   | `/api/a2a/tasks/[id]/cancel` | 取消工作                                                                                                       |

**驗證：** REST 輔助端點不需要管理驗證（儀表板可讀取）；JSON-RPC `/a2a` 路由在已設定時使用 Bearer `OMNIROUTE_API_KEY`。

## 驗證

請參閱[管理驗證](../guides/MANAGEMENT-AUTH.md)，瞭解四種認證資訊類別（儀表板工作階段、本機 CLI 權杖、`oma_live_…` 存取權杖、管理範圍 API 金鑰）以及它們與推論金鑰的差異。

- 儀表板路由（`/dashboard/*`）使用 `auth_token` Cookie
- 登入使用已儲存的密碼雜湊；若無則回退至 `INITIAL_PASSWORD`
- 可透過 `/api/settings/require-login` 切換 `requireLogin`
- 當 `REQUIRE_API_KEY=true` 時，`/v1/*` 路由可選擇要求 Bearer API 金鑰
- 本參考資料中的「管理權杖」／「管理範圍 API 金鑰」是指該指南中的其中一種類別，而非未定義的額外密碼類型

> **重大變更（v3.8.0）** — `/api/v1/agents/tasks/*` 和冷卻管理端點現在需要**管理驗證**（儀表板 `auth_token` Cookie 或管理範圍 API 金鑰）。先前未經驗證呼叫這些路由的用戶端將收到 `401 Unauthorized`。請參閱提交 `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）。
