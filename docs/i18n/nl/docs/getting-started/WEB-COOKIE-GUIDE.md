Met webcookieproviders kan OmniRoute een AI-service gebruiken via je bestaande browsersessie in plaats van via een API-sleutel. Ze zijn handig wanneer je via de website van een service al toegang hebt en je wilt dat OmniRoute dezelfde geauthenticeerde sessie gebruikt.

In tegenstelling tot providers met een API-sleutel verifiëren webcookieproviders je identiteit met de inloggegevens die je browser naar de website verzendt.

---

# Voordat je begint

> **Belangrijk:** Kopieer inloggegevens altijd uit een **live netwerkverzoek**, **niet** uit de cookieopslag van je browser.

Veel verificatieproblemen worden veroorzaakt doordat cookies vanaf de verkeerde locatie worden gekopieerd.

## Kopieer NIET uit de cookieopslag

In de meeste browsers kun je opgeslagen cookies vinden via:

```
Ontwikkelaarstools
→ Toepassing (of Opslag)
→ Cookies
```

Hoewel deze cookies er correct uitzien, kunnen ze:

- verouderd zijn
- onvolledig zijn
- cookies missen die alleen bij geauthenticeerde verzoeken worden verzonden

Het gebruik van deze waarden kan verificatiefouten veroorzaken, zelfs als ze geldig lijken.

## Kopieer uit een live verzoek

Gebruik in plaats daarvan de cookies uit een geslaagd verzoek:

```
Ontwikkelaarstools
→ Netwerk
→ Vernieuw de pagina
→ Open een chat- of gespreksverzoek
→ Verzoekheaders
→ Cookie
```

De `Cookie`-verzoekheader bevat exact de verificatiegegevens die je browser met succes heeft gebruikt.

Voor de meeste webcookieproviders is dit de waarde die je in OmniRoute moet plakken.

# Algemene configuratie

Het configuratieproces is voor de meeste webcookieproviders hetzelfde.

1. Meld je aan op de website van de provider.
2. Open de ontwikkelaarstools van de browser.
3. Open het tabblad **Netwerk**.
4. Vernieuw de pagina.
5. Open een geauthenticeerd chat- of gespreksverzoek.
6. Kopieer de vereiste verificatiegegevens.
7. Open OmniRoute.
8. Ga naar **Providers → Provider toevoegen**.
9. Selecteer je webcookieprovider.
10. Plak de inloggegevens.
11. Klik op **Verbinding testen**.
12. Sla de provider op.

Welke inloggegevens precies vereist zijn, is afhankelijk van de provider.

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) is een gratis chatplatform voor consumenten waarvoor geen registratie vereist is — de sessie wordt bij het eerste bezoek anoniem aangemaakt en blijft behouden via drie cookies: `uid`, `si_usr_id` en `si_ses_id`. OmniRoute proxyt hetzelfde `/api/dispatch`-eindpunt via één model-id (`notrack-c`, alias `ntw`).

### Stappen om verbinding te maken

1. Open [notrack.ai](https://notrack.ai) in je browser en laat de anonieme sessiecookie instellen.
2. Open **DevTools → Network**, vernieuw de pagina en klik op een willekeurig `/api`-verzoek.
3. Kopieer onder **Request Headers** de volledige waarde van de `Cookie`-header.
4. Ga in OmniRoute naar **Providers → Add Provider → NoTrack Web (Free)**.
5. Plak de cookietekenreeks in het veld `apiKey` en klik op **Save**.

OmniRoute extraheert `uid`, `si_usr_id` en `si_ses_id` uit de geplakte tekenreeks en bouwt een schone `Cookie`-header opnieuw op met uitsluitend die paren — plus `nt_session` (het `ntk_…`-token dat voor ingelogde accounts wordt ingesteld), indien aanwezig. Als een van de drie ontbreekt, wordt de onbewerkte geplakte tekenreeks ongewijzigd doorgestuurd, zodat beheerders met alternatieve indelingen kunnen experimenteren.

### Model-id's

| Model-id    | Weergavenaam | Opmerkingen                                                |
| ----------- | ------------ | ---------------------------------------------------------- |
| `notrack-c` | NoTrack C    | Standaard — het upstream-dispatchmodel `C`.                |
| `C`         | NoTrack C    | Alias voor `notrack-c` (onbewerkte upstream-dispatchcode). |
| `notrack`   | NoTrack C    | Alias voor `notrack-c`.                                    |
| `ntw`       | NoTrack C    | Korte alias voor `notrack-c`.                              |

Alle vier de model-id's verwijzen naar hetzelfde upstream-dispatchmodel (`C`).

### Verzoekopties

De executor accepteert deze optionele velden in de requestbody:

| Bodyveld              | Standaard | Doel                                                                                      |
| --------------------- | --------- | ----------------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`   | Dispatchmodus (vrije tekenreeks; de upstream accepteert `usual`, …)                       |
| `notrack_max_turns`   | `6`       | Aantal interne beurten dat de upstream mag uitvoeren voordat deze antwoordt.              |
| `notrack_chat_id`     | `null`    | Hervat een bestaande upstream-chat (weglaten voor een nieuwe chat).                       |
| `notrack_attachments` | `[]`      | Pass-through-array van upstream-bijlagebeschrijvingen.                                    |
| `notrack_regenerate`  | `false`   | Stel in op `true` om een opnieuw gegenereerd antwoord voor de vorige beurt aan te vragen. |

### Mogelijkheden

- **Streamende en niet-streamende** chatvoltooiingen.
- **Tool-calling** — stel `tools: [...]` in voor het verzoek; de executor serialiseert deze naar een tool-call-envelopecontract en parseert de antwoorden van het model terug naar OpenAI-`tool_calls`.
- **`response_format`** — `json_object` en `json_schema` worden ondersteund. De executor extraheert het eerste JSON-object uit het antwoord van het model en zet dit vóór retournering om naar een tekenreeks.
- **Redeneerhint** — de executor verzendt een `reasoning`-delta wanneer de upstream een `thinking`-event verzendt.

### Beperkingen

- De upstream legt gebruikslimieten op voor anoniem gebruik — wanneer die worden overschreden, retourneert de executor een 429 met een duidelijke melding.
- Alle model-id's verwijzen naar hetzelfde upstream-dispatchmodel; er is geen schakeloptie per model.
- De executor roept het `/api/chats`-eindpunt van de upstream niet aan, waardoor chatgeschiedenis en sessies niet automatisch worden beheerd. Gebruik `notrack_chat_id` om een bestaande upstream-chat te hervatten.

# Wat webcookieproviders wel en niet kunnen

Webcookieproviders hergebruiken de chatinterface van een website. Ze bieden **niet** dezelfde mogelijkheden als officiële API's.

## Ondersteund

- Authenticeren met uw bestaande browsersessie
- Toegang tot modellen die via uw account beschikbaar zijn
- Chatreacties streamen
- Geen API-sleutel vereist

## Niet ondersteund

- Functies aanroepen
- Hulpmiddelen aanroepen
- Automatische bestandsbewerking
- Agentische IDE-workflows
- Functies die alleen via de API beschikbaar zijn

Dit is verwacht gedrag en is **geen** bug.

Als u uitvoering van hulpmiddelen, automatische bestandsbewerking of andere agentworkflows nodig hebt, gebruikt u een **API-sleutelprovider** in plaats van een Web Cookie-provider.

# Kanttekening bij validatie

Een geslaagde **Verbinding testen** of cookievalidatie controleert alleen of de opgegeven referenties de verwachte indeling lijken te hebben.

Totdat Issue #7857 is opgelost, biedt een geslaagde validatie **geen garantie** dat de provider zich met succes kan authenticeren.

Als de authenticatie nog steeds mislukt, controleer dan of u de referenties uit een actieve netwerkaanvraag hebt gekopieerd en niet uit de cookieopslag van de browser.

---

# Problemen oplossen

## Authenticatie mislukt

Controleer of de referenties zijn gekopieerd uit:

```
Netwerk
→ Aanvraagheaders
→ Cookie
```

en **niet** uit:

```
Toepassing
→ Cookies
```

---

## Cookie werkt in de browser, maar niet in OmniRoute

Sommige providers bevatten cookies die alleen tijdens geauthenticeerde aanvragen worden verzonden.

Kopieer de referenties opnieuw uit een nieuwe netwerkaanvraag nadat u met succes een gesprek hebt geopend.

---

## Sessie verlopen

Web Cookie-providers gebruiken uw bestaande browsersessie.

Als uw browsersessie verloopt of u zich afmeldt, moet u een nieuwe set referenties kopiëren. Raadpleeg voor het automatiseren van cookievernieuwing voor ondersteunde webproviders het bijbehorende hulpmiddel [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md).

---

## Verbindingstest slaagt, maar aanvragen mislukken

Totdat Issue #7857 is opgelost, biedt een geslaagde validatie geen garantie dat de authenticatieaanvraag zal slagen.

Kopieer uw referenties opnieuw uit een nieuwe geauthenticeerde aanvraag voordat u het probleem verder onderzoekt.

---

## ChatGPT Web mislukt met "Unsupported ChatGPT integrity dependency"

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

De referentie is in orde — die fout is afkomstig van de bridge, niet van de sessie. chatgpt.com wijst zijn
module-id's per implementatie toe en de bridge zette voorheen het id van de Sentinel-helper die wordt geïnstantieerd vast, waardoor een
nieuwe build van chatgpt.com waarin de helper werd hernoemd elke beurt liet mislukken terwijl de cookie geldig bleef. Het opnieuw autoriseren
van de verbinding kan dit niet oplossen.

Builds die de module via de eigen runtime van de pagina oplossen, zetten geen id vast en hebben hier geen last van. Als u de
fout ziet, upgrade dan OmniRoute en voer de verbindingscontrole opnieuw uit.

# Aanbevolen werkwijzen

- Kopieer referenties uit een nieuwe geauthenticeerde aanvraag.
- Vermijd het hergebruiken van oude cookies.
- Houd uw browsersessie actief wanneer u Web Cookie-providers gebruikt.
- Behandel gekopieerde cookies als gevoelige referenties.
- Gebruik API-sleutelproviders wanneer u functies wilt aanroepen of agentworkflows nodig hebt.
