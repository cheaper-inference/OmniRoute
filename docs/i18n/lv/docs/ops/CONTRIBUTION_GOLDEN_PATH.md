Izmantojiet šo rokasgrāmatu, lai izvēlētos mazāko uzticamo izstrādes ciklu izmaiņu pieprasījumam. Tā
neaizstāj tālāk norādītos konkrēto jomu arhitektūras un drošības dokumentus; tā sasaista katru izplatīto
izmaiņu veidu ar tā līgumiem, mērķētajām pārbaudēm un CI tvērumu.

## Ceļš, ko veic katra izmaiņa

1. **Pirms rediģēšanas izvēlieties bāzes zaru.** Atrodiet jaunāko aktīvo `release/v*` zaru un izveidojiet zaru no
   tā galotnes. Kā mērķi norādiet šo zaru, nevis `main`. Ja ir spēkā laidiena iesaldēšana, nenorādiet kā mērķi iesaldēto
   zaru; izmantojiet nākamo aktīvo ciklu, kas aprakstīts dokumentā
   [Zarošanas un laidienu modelis](BRANCHING_MODEL.md).
2. **Nosauciet līgumus.** Identificējiet katru katalogu, shēmu, ģenerēto artefaktu, publisko API vai lietotāja
   saskarni, ko izmaiņa ietekmē. Tālāk esošajā tabulā norādīts minimālais sākuma kopums.
3. **Rakstiet vai atjauniniet mērķētus testus.** Produkcijas izmaiņām direktorijās `src/`, `open-sse/`, `electron/` vai
   `bin/` tajā pašā PR ir nepieciešams automatizēts tests. Palaidiet mazāko testu failu kopu, kas pierāda
   darbību, un pēc tam norādītās mērķētās pārbaudes.
4. **Ļaujiet CI izpildīt plašo matricu.** PR ietvaros tiek izpildītas visas vienību testu daļas, Vitest, pārklājuma sliekšņa
   pārbaude un produkcijas būvējums. Plašu testu kopu lokāli palaidiet tikai tad, ja mērķētas pārbaudes kļūme norāda uz
   plašāku ietekmi vai izmaiņa aptver vairākas apakšsistēmas.
5. **Pirms pārskatīšanas saskaņojiet izmaiņas.** Iegūstiet aktīvo bāzes zaru, pārbaudiet tā jaunos komitus un savas izmaiņas attiecībā
   pret to, pēc tam pārnesiet komitus vai sapludiniet bāzes zaru atbilstoši līdzstrādnieku darbplūsmai. Ģenerēto failu
   un katalogu konfliktus atrisiniet to avotā, ģenerējiet tos no jauna, atkārtoti izpildiet mērķēto ciklu un pārliecinieties, ka
   PR mērķis joprojām ir aktīvais laidiena zars.
6. **Dokumentējiet pierādījumus.** PR veidnē norādiet izpildītās komandas, katru pievienoto vai mainīto testa failu,
   migrācijas vai funkcionalitātes karogus un visas vēl neizpildītās pārbaudes, kas veicamas tikai CI.

## Standarta ceļi pēc izmaiņas veida

Tālāk norādītās komandas ir minimālās mērķētās pārbaudes, nevis atļauja izlaist testu, kas tieši pārbauda
jūsu mainīto darbību.

### Pakalpojumu sniedzējs

**Līgumi**

- Pakalpojumu sniedzēja definīcija direktorijā `src/shared/constants/providers/` un tās kompozīcija failā
  `src/shared/constants/providers.ts`.
- Modeļi un iespējas failā `open-sse/config/providerRegistry.ts` vai tā nodalītajos reģistra failos.
- Izpildītāja/tulkotāja atlase, OAuth vai API atslēgas konfigurācija, informācijas paneļa resursi un ģenerētā
  pakalpojumu sniedzēja atsauce, ja piemērojams.
- Publiskajiem akreditācijas datiem jāizmanto `resolvePublicCred()`; kļūdu atbildēm jāizmanto koplietotie sanitizētie
  kļūdu palīgrīki. Skatiet `docs/security/PUBLIC_CREDS.md` (git; netiek kompilēts direktorijā `/docs`) un
  [Kļūdu sanitizēšana](../security/ERROR_SANITIZATION.md).

**Mērķētais cikls**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kad katalogs mainās; iekļaujiet ģenerētās izmaiņas komitā
npm run lint
```

Pārbaudiet arī katru ietekmēto pieprasījumu saimi: tērzēšanu, Responses, attēlus, iegulumus, audio vai video.
Pārskatiet ģenerētā kataloga un etalona izmaiņas kā līgumu izmaiņas; nepieņemiet tās akli.

### Maršrutēšana

**Līgumi**

- Publiskās stratēģiju vērtības un UI metadati failā `src/shared/constants/routingStrategies.ts`.
- Nosūtīšana un secība failā `open-sse/services/combo.ts` un direktorijā `open-sse/services/combo/`.
- Combo shēmas, saglabāšana, noturības stāvoklis, modeļu iespējas un API/UI vadīklas.
- [Auto-Combo dzinis](../routing/AUTO-COMBO.md) un noturības dokumentācija, ja mainās darbība.

**Mērķētais cikls**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # stratēģijas vai nosūtīšanas izmaiņas
npm run check:known-symbols      # stratēģijas reģistrācijas izmaiņas
npm run lint
```

Lokāli izmantojiet deterministiskus testus ar imitētiem augšupstraumes pakalpojumiem. Darbspējas pārbaudēm ar aktīvu combo ir nepieciešami akreditācijas dati, un tās
veic manuāli; tās neaizstāj CI.

### UI / UX

**Līgumi**

- Next.js maršruta/lapas un koplietoto komponentu robežas direktorijās `src/app/` un
  `src/shared/components/`.
- API atbilžu formas, ielādes/tukšie/kļūdu stāvokļi, tastatūras un ekrāna lasītāja darbība,
  responsīvais izkārtojums, motīvi un lokalizāciju paplašināšana.
- Angļu valodas UI avota virknes failā `src/i18n/messages/en.json`; neiekodējiet jaunu lietotājam redzamu tekstu tieši kodā.

**Mērķētais cikls**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Mijiedarbības vai vizuālu izmaiņu gadījumā palaidiet lietotni un pārbaudiet gan šaurus, gan platus skata laukumus. CI izpilda
produkcijas būvējumu un plašākas testu kopas; vizuālajai darbībai joprojām nepieciešams izmaiņai atbilstošs mērķēts komponenta tests, Playwright tests
vai dokumentēta manuāla pārbaude.

### i18n

**Līgumi**

- `src/i18n/messages/en.json` ir UI avots; `config/i18n.json` ir lokalizāciju avots.
- CLI katalogi atrodas atsevišķi direktorijā `bin/cli/locales/`.
- Precīzi saglabājiet ICU vietturus un tagus. Netulkojiet produktu/pakalpojumu sniedzēju/modeļu nosaukumus,
  protokolu un galveņu nosaukumus, komandas, koda/JSON identifikatorus, URL, vides mainīgos vai
  aizsargātus terminus, piemēram, `OmniRoute`, `OAuth`, `MCP` un `A2A`. Pašreizējais avota saraksts ir
  `scripts/i18n/glossary/protected-terms.json`.

**Mērķētais cikls**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kad mainās CLI virknes/katalogi
npm run lint
```

Šie ir norādījumi esošajai sistēmai, nevis aicinājums paplašināt tās rīkus vai atslēgu modeli.
Kamēr tiek izstrādāta aizstājošā sistēma, veiciet tikai precīzi mērķētas i18n izmaiņas. Nepalaidiet tulkošanas
komandas, kas izsauc ārējus pakalpojumus, ja vien uzdevums skaidri nepieprasa ģenerētus tulkojumus un
neesat pārskatījis iegūtās izmaiņas.

### CLI

**Līgumi**

- Publiskās komandas un karodziņi direktorijā `bin/cli/`, ģenerētās API komandas, izejas kodi, stdout/stderr un
  JSON izvades struktūras, konfigurācijas/vides darbība un pakotnē iekļautie faili.
- CLI lietotājiem paredzētajām virknēm jāizmanto CLI i18n slānis, un `en`/`pt-BR` katalogiem jābūt savstarpēji saskaņotiem.
- Saglabājiet Node kā atbalstīto izpildvidi un publicētā binārā faila līgumu.

**Fokusētais cikls**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ģenerētās/apvienotās CLI izmaiņas
npm run check:pack-policy     # pakotnes publiskās virsmas izmaiņas
npm run lint
```

Izmantojiet precīzo komandu pagaidu datu direktorijā, ja darbība ir atkarīga no parsēšanas, failiem vai izejas
statusa. CI veic plašākas pakotnes artefaktu un ekosistēmas pārbaudes.

### Datubāze

**Līgumi**

- Domēna moduļi atrodas direktorijā `src/lib/db/`; importējiet konkrētos moduļus tieši (vecais `localDb.ts` atkārtotas eksportēšanas slānis tika noņemts).
- Numurētas, idempotentas SQL migrācijas direktorijā `src/lib/db/migrations/`, transakciju drošība, jaunināšanas
  darbība, indeksi un visi izsaucēji, kurus ietekmē shēma.
- Maršruti un apstrādātāji nekad tieši neizpilda neapstrādātu SQL.

**Fokusētais cikls**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Pievienojot migrāciju, pārbaudiet gan jaunu datubāzi, gan jaunināšanu no iepriekšējās shēmas. Datubāzes testiem
tīrīšanas laikā jāaizver savienojumi un jāizsauc `resetDbInstance()`. Izpildiet `npm run test:bun:db` tikai tad, ja
mainās eksperimentālais Bun adaptera ceļš; Node joprojām ir noteicošā izpildvide.

### Būvēšana / izvietošana

**Līgumi**

- Saknes un darbvietu manifesti/bloķēšanas fails, `scripts/build/`, Next.js savrupās versijas komplektēšana, `dist/`
  pakotnes saturs, Electron platformu metadati, CI darbplūsmas un izvietošanas kontrolatzīmes.
- Atbalstītajiem Node versiju diapazoniem un `CLAUDE.md` atļauto Bun lietojumu sarakstam jāpaliek neskartiem.
- Būvējuma artefakti netiek izsekoti; ir spēkā atkarību, licenču, darbplūsmu un pakotņu politikas.

**Fokusētais cikls**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # atkarību vai bloķēšanas faila izmaiņas
npm run check:pack-policy      # publicētās pakotnes publiskās virsmas izmaiņas
npm run lint
```

Izmantojiet `npm run build` lokāli tikai tad, ja izmaiņas ietekmē kompilēšanu, savrupās versijas komplektēšanu, resursus
vai izpildlaika apvienošanu. Izmantojiet `npm run build:release` tikai laidiena/izvietošanas validācijai. CI būvējums ir
galīgais starpplatformu signāls; platformai specifiskām Electron izmaiņām nepieciešams atbilstošs fokusētais būvējums
vai ātrās pārbaudes apliecinājums.

## Izstrādātāju skripti koplietojamai iekārtai

Divi `scripts/dev/` palīgrīki nodrošina lokālo darba ciklu izstrādes iekārtā, kurā ir aktīvas arī citas sesijas:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # faili no merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # tieši šie faili
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # izolēts worktree, drošs paralēlai lietošanai
```

- `typecheck-touched.sh` veic tipu pārbaudi tikai mainītajiem `.ts/.tsx` failiem, izmantojot pagaidu
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ar 6 GB atmiņas apjomu, tādējādi aizstājot visa projekta `tsc -p tsconfig.json`,
  kam noslogotā iekārtā nepietiek atmiņas. Tas izvada kļūdas mainītajos failos kopā ar vienu kopsavilkuma rindu un beidz darbu
  ar kodu `1`, ja kļūdas ir mainītajos failos, ar `2`, ja kļūdas ir tikai importētajos failos vai tsc pārtrauca darbu
  bez diagnostikas (izlasiet tā norādīto žurnālu direktorijā `_artifacts/typecheck-touched/`), un ar `0`, ja
  kļūdu nav. Pagaidu tsconfig vienmēr tiek noņemts; nekad neiekļaujiet to commit.
- `new-worktree.sh` secīgi izpilda vienlaicīgus palaišanas mēģinājumus, izmantojot `<git-common-dir>/omniroute-new-worktree.lock`
  (pēc noklusējuma gaida līdz 600 s, parādot ziņojumu; skripta galvene dokumentē
  iestatījuma pārrakstīšanu), un atsauc
  izveidoto zaru, ja `git worktree add` neizdodas pirms worktree izveides, tādēļ atkārtotam mēģinājumam
  nav manuāli jāizpilda `git branch -D`. Ar cietajām saitēm piesaistītais `node_modules` un `.husky/_` kopija netiek mainīta.

## Lokālais kandidāta darba cikls

Avota testi nevar pierādīt, ka pakotnes artefakts tiek palaists: pakotnē iekļaujamo failu sarakstu, atmesto atkarību
un natīvo bināro failu problēmas parādās tikai pēc tarball instalēšanas un palaišanas. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ir RFC #8084 vienreizējas būvēšanas / validēšanas / paaugstināšanas plūsmas
lokālā daļa: tas izveido vienu kandidātu, validē tieši šo artefaktu, paaugstina to, pārdēvējot direktorijus,
un atritina to, ja paaugstinātā slota darbspējas pārbaude neizdodas.

```bash
npm run dev:candidate -- run --dry-run --json  # izvadīt plānu, neko nemainot
npm run dev:candidate -- run                   # būvēt + validēt + paaugstināt, automātiski atritinot
npm run dev:candidate -- build                 # npm pack + instalēt direktorijā _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # palaist brīvā portā, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # samainīt vietām current un previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # atkārtoti izmantot citur (CI) izveidotu tarball
```

- **Būvējiet vienreiz.** `build` iepako pašreizējo koku (tam nepieciešams `dist/server.js`, tādēļ vispirms izpildiet
  `npm run build:release`) vai kopē `--from-tarball`, pēc tam instalē tarball izolētā npm prefiksā,
  jo tarball nesatur `node_modules`. Id ir saīsinātais `HEAD`
  sha (`-dirty`, ja kokā ir lokālas izmaiņas) vai `tgz-<sha256>` tarball gadījumā. Tīrs id, kas
  jau ir uzbūvēts, tiek izmantots atkārtoti, nevis būvēts vēlreiz; lai to pārbūvētu, norādiet `--force`.
- **Validējiet pakotni, nevis avotu.** `validate` palaiž instalēto CLI
  (`serve --port <free port>`) ar jaunu `DATA_DIR=<candidate>/data`, viltotiem noslēpumiem un no
  vides noņemtiem operatora `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` un `INITIAL_PASSWORD`,
  tādēļ tiek pārbaudīts jaunas instalācijas lokālā savienojuma režīms bez atslēgām. Tas gaida, līdz
  `GET /api/health` atgriež 200, pieprasa, lai `GET /v1/models` atgrieztu 200, aptur procesu grupu
  un ieraksta rezultātu failā `validation.json` kopā ar tarball jaucējvērtību.
- **Paaugstiniet to pašu artefaktu.** `promote` noraida kandidātu, kuram nav sekmīgas validācijas tā
  pašreizējai tarball jaucējvērtībai. Noklusējuma aktīvais slots ir `_artifacts/candidate/current`; `--target <dir>`
  atlasa citu direktoriju tajā pašā failu sistēmā, un tā iepriekšējais slots ir `<dir>.previous`.
  Katra pārdēvēšana ir atomāra, un kļūme procesa vidū atsauc jau izpildītās pārdēvēšanas.
- **Atritiniet.** `run` vēlreiz validē paaugstināto slotu un samaina `current` un `previous` atpakaļ, ja
  šī pārbaude neizdodas. Kandidāts, kam neizdodas pirmā validācija, nekad netiek paaugstināts.

Viss tiek ierakstīts git ignorētajā `_artifacts/candidate/`; esoša OmniRoute
instalācija un tās datu direktorijs nekad netiek mainīts. Paaugstinātais CLI atrodas
`_artifacts/candidate/current/prefix/bin/omniroute`; lietojot to, palaidiet to ar savu `DATA_DIR`.
Izejas kodi: `0` — sekmīgi, `1` — validācija vai paaugstināšana neizdevās, `2` — lietojuma kļūda vai trūkst būvējuma.

## Lokālais cikls salīdzinājumā ar CI

| Palaist lokāli katram labojumam                                                             | CI nodrošina plašu pārbaudes tvērumu                                               |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Iepriekš minētie tiešās darbības testi un kategoriju kontroles                              | Sadalīts pilnais vienībtestu komplekts un secīgie testi                            |
| `npm run lint`                                                                              | Vitest testu komplekti un pārklājuma/kvalitātes sliekšņi                           |
| Tipu pārbaude vai būvēšana tikai tad, ja to prasa skartais kontrakts                        | Produkcijas būvējums, drošības, dokumentācijas, atkarību un PR politikas kontroles |
| Manuālas mijiedarbības/tiešās pārbaudes tikai tad, ja automatizācija nevar pierādīt darbību | Darbplūsmā konfigurētās starpuzdevumu integrācijas un platformu pārbaudes          |

Sekmīgs fokusētais cikls ir pierādījums par mainīto kontraktu, nevis apliecinājums, ka nesaistītās CI pārbaudes
būs sekmīgas. Un otrādi — nelieciet katram lokālajam labojumam gaidīt pilnas repozitorija matricas izpildi.

## Saskaņošanas kontrolsaraksts

Pirms pārskatīšanas pieprasīšanas:

- Pārliecinieties, ka PR bāze joprojām ir augstākais aktīvais `release/v*` zars.
- Iegūstiet šo bāzi un pārskatiet iesniegumus, kas tajā nonākuši kopš jūsu zara izveides.
- Pārskatiet `git diff <active-base>...HEAD`, lai atrastu nejaušas vai ģenerētas izmaiņas.
- Atrisiniet katalogu un ģenerēto dokumentu konfliktus, atjauninot avotu un no jauna ģenerējot izvadi.
- Pēc saskaņošanas atkārtoti palaidiet katru PR aprakstā norādīto fokusēto testu/kontroli.
- Nekad nevājiniet pārbaudes apgalvojumus un neizlaidiet obligātos testus tikai tādēļ, lai pielāgotos pārvietotai bāzei.

Informāciju par laidiena iesaldēšanas un mērķa maiņas noteikumiem skatiet dokumentā
[Zarošanas un laidienu modelis](BRANCHING_MODEL.md). Pilnu CI pārbaužu sarakstu skatiet dokumentā
[Kvalitātes kontroļu atsauce](../architecture/QUALITY_GATES.md).
