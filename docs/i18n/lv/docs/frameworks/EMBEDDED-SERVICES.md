- OmniRoute instalē tos zem `DATA_DIR/services/{name}/` (izolēts no paša OmniRoute `package.json`)

### Pārvaldīti starpniekservera kodoli

Pielāgota starpniekservera resursdatora lauks pieņem arī V2Ray avota saiti. Izvēlieties** dziedāt kaste** vai** Rentgens** skaidri norādīts, pēc tam noklikšķiniet uz Saglabāt. Rakstīšana nekad nelejupielādē un nesāk kodolu. Saglabāt pārbauda oficiālo laidienu arhīvu, apstiprina sākotnējo konfigurāciju, sāk atsevišķu localhost SOCKS klausītāju un tikai pēc tam raksta starpniekservera reģistra piešķiršanu. Neveiksmīga aktivizēšana atjauno iepriekšējo pārvaldīto konfigurāciju un procesu. `STORAGE_ENCRYPTION_KEY` ir nepieciešams; avota saites ir šifrētas.

Pārvaldītie faili atrodas `DATA_DIR/services/managed-proxy/`, atsevišķi no TPROXY. Katram atlasītajam kodolam ir viens īpašums, līdz 100 klausītājiem. Autostartēšana vai globālā maršrutēšanas noklusējuma iestatījumi netiek mainīti. Veiksmīga saglabāšana atceras aktivizēšanu tikai šim pārvaldītajam kodolam; Lietojumprogrammas startēšana atjauno iespējotos saglabātos kodolus, izmantojot jau pārbaudīto bināro failu, nekad neveicot lejupielādi sāknēšanas laikā. Skaidra apturēšana notīra šo aktivizācijas karogu. Trūkstošam vai bojātam bināram ir nepieciešams atkārtoti saglabāt avotu. Reģistra dzēšana noņem avotu un klausītāju lokāli; parastie galapunkta labojumi pārvaldītajām rindām tiek noraidīti, tāpēc saglabātais avots nevar klusi novirzīties no maršrutētā klausītāja.

| Avota formāts                               | dziedāt kaste                                                                       | Rentgens                                                                            |
| ------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| VLESS, VMess, Trojas zirgs, Shadowsocks URI | Atbalstīta konversija                                                               | Atbalstīta konversija                                                               |
| Hysteria2/hy2, TUIC, AnyTLS URI             | Atbalstīta konversija                                                               | Noraidīts; izmantojiet saderīgu kodolu                                              |
| TCP/raw, WebSocket, gRPC, HTTPUpgrade       | Atbalstīts VLESS/VMess/Trojan                                                       | Atbalstīts VLESS/VMess/Trojan                                                       |
| XHTTP URI transports                        | Noraidīts                                                                           | Atbalstīta konversija                                                               |
| Vietējā izejošā JSON                        | Atlasītā kodola atļautais starpniekserveris protocols/options, pārbaudīts sākotnēji | Atlasītā kodola atļautais starpniekserveris protocols/options, pārbaudīts sākotnēji |

Nezināmas vadu opcijas, nedroši TLS karodziņi, ārējie spraudņi, lokālo failu ceļu opcijas un neatbalstītas kombinācijas tiek noraidītas, nevis klusi izmestas. Vietējie objekti ir izejošās definīcijas, nevis visa kodola konfigurācijas; control/direct/bypass izejošās ziņas netiek pieņemtas. WireGuard uz sing-box 1.14 izmanto beigu punktus, tāpēc tas netiek pieņemts kā vietējais izejošs. Šis nav visu formātu pārveidotājs; SSR, mantotajām whole-base64 Shadowsocks saitēm, patvaļīgiem Clash objektiem un transporta variantiem, kas nav tabulā, ir nepieciešams atsevišķi atbalstīts avota formāts.

`/api/services/managed-proxy` ir autentificēts un ir tikai atpakaļcilpas: GET uzskaita rediģētos metadatus, POST saglabā `{core,name,sourceLink,id?,assignment?}`, PATCH pieņem `{core,action:"start"|"stop"}`. Jābūt resursdatora uzticamam vienādranga zīmoga konveijeram. Vietējā pamata diagnostika tiek apspiesta, jo tajā var būt akreditācijas dati; dzīves cikla notikumi izmanto esošo strukturēto lietojumprogrammu failu reģistrētāju bez avota saitēm vai augšupējās slodzes. Lai saņemtu atbalstu, pievienojiet tikai sanitizētus lietojumprogrammu žurnālus. Oficiālās versijas ir piespraustas sing-box 1.14.3 un Xray 26.3.27 ar release-asset SHA-256 manifestiem; turpmākajiem atjauninājumiem ir jāmaina versija un visi pārbaudītie īssavilkumi kopā.

│    Re-looks up port and API key per-request (no caching).          │

│    Returns 503 service_not_running if supervisor not in "running". │
│                                                                    │
│  src/shared/constants/providers.ts                                 │
│    Entry for "9router": isEmbeddedService: true                    │
│                                                                    │
│  open-sse/config/providerRegistry.ts                               │
│    Models stored as "9router/{sub}/{model}" (prefixed).            │
│    Synced every 5 min by modelSync.ts.                             │
│                                                                    │
│  Mux is lifecycle-managed ONLY (Layers 1-3) — it is an agent-       │
│  orchestration daemon, not an LLM proxy, so it has no Layer 4      │
│  executor/provider entry and is never a routing target.            │
└────────────────────────────────────────────────────────────────────┘
```

## 3. Dzīves cikla stāvokļu automāts

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
             veselības pārbaude OK  │         avārija / SIGTERM │
                               ┌────▼─────┐  (izeja 5 s laikā)  │
                               │ running  │──── avārija ────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Stāvokļi tiek glabāti DB tabulā `version_manager` (`status` kolonnā) un atspoguļoti
`ServiceSupervisor` stāvoklī atmiņā. Darbojošam procesam noteicošais ir stāvoklis
atmiņā; DB stāvoklis ir noturīgā rezerves vērtība sistēmas palaišanas laikā.

### Stāvokļu pārejas

| No              | Notikums                          | Uz                     |
| --------------- | --------------------------------- | ---------------------- |
| `not_installed` | `install()` ir sekmīgs            | `stopped`              |
| `stopped`       | izsaukts `start()`                | `starting`             |
| `starting`      | veselības pārbaude atgriež 200    | `running`              |
| `starting`      | process beidzas pirms gatavības   | `error`                |
| `running`       | izsaukts `stop()`                 | `stopping` → `stopped` |
| `running`       | process negaidīti beidzas (< 5 s) | `error` (ātra avārija) |
| `running`       | process negaidīti beidzas (> 5 s) | `error`                |
| `error`         | izsaukts `start()`                | `starting`             |
| jebkurš         | `stop()`, kamēr ir `stopping`     | bez darbības           |

### Operāciju bloķētājs

`ServiceSupervisor` izpilda dzīves cikla operācijas secīgi, izmantojot asinhronu operāciju bloķētāju
(`withLock()`). Vienlaicīgi `start()` izsaukumi vienam un tam pašam pārraugam izraisa tieši
viena procesa palaišanu; otrais izsaucējs gaida un atgriež esošo statusu. Tas novērš
sacensības apstākļus, piemēram, ja automātiskā palaišana un lietotāja saskarnes poga tiek aktivizētas vienlaikus.

### 4.9. Reversais starpniekserveris (9 maršrutētāja informācijas paneļa iegulšana)

Informācijas panelis iegulst 9Router web UI iframe iekšpusē, izmantojot iekšējo apgriezto starpniekserveri vietnē:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Šis starpniekserveris:

- Pārsūta pieprasījumu uz `http://127.0.0.1:{port}/{path}` (tikai cilpa)
- Noņem ienākošās `cookie` un `authorization` galvenes (nav OmniRoute sesijas noplūdes)
- Ievada `Authorization: Bearer {apiKey}` 9maršrutētāja autentifikācijai
- Izņem no atbildes `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*`
- Pārraksta HTML atbildes, lai ievadītu `<base href>` un normalizētu absolūtos ceļus (`/foo` → `/dashboard/.../embed/foo`)

WebSocket jauninājumus iegultajam informācijas panelim apstrādā pavadošais serveris speciālā portā (skatiet `src/lib/services/embedWsProxy.ts`).

**Drošība:** Iegulšanas starpniekservera maršruti ir klasificēti zem `LOCAL_ONLY_API_PREFIXES`, un tos var sasniegt tikai no atpakaļcilpas. Uzbrucējs, kurš iegūst JWT izmantojot Cloudflare/Ngrok tuneli, nevar izmantot starpniekserveri iegultos pakalpojumos.

pieprasījums pienāk
  → isLocalOnlyPath(path)?
      → nav atgriezeniskā cilpa → 403 LOCAL_ONLY (vienmēr, pirms autentifikācijas pārbaudes)
      → atgriezeniskā cilpa     → turpināt ar parasto autentifikāciju
```

Tas neļauj nopludinātam JWT (piemēram, izmantojot tuneli) aktivizēt `npm install` vai
procesa palaišanu. Pilnu līmeņu matricu skatiet
`docs/security/ROUTE_GUARD_TIERS.md`.

### API atslēgas ievietošana

9Router un Mux saviem HTTP galapunktiem pieprasa API atslēgu/nesēja pilnvaru.
OmniRoute:

1. Ģenerē atslēgu, izmantojot `crypto.randomBytes(32).toString("base64url")`, ar
   pakalpojumam specifisku prefiksu (`nr_` — 9Router, `mx_` — Mux).
2. Šifrē to glabāšanas laikā, izmantojot AES-256-GCM (to pašu šifru, kas tiek izmantots pakalpojumu sniedzēju akreditācijas datiem).
3. Atšifrē un procesa palaišanas laikā ievieto to kā vides mainīgo —
   `NINEROUTER_API_KEY` pakalpojumam 9Router, `MUX_SERVER_AUTH_TOKEN` pakalpojumam Mux (nekad kā CLI
   karodziņu, tādēļ pilnvara nekad neparādās `ps`/procesu sarakstos).
4. Nekad neatgriež atklātā teksta atslēgu nevienā HTTP atbildē.

CLIProxyAPI saņem īpašu datu plaknes atslēgu, kas tiek ievietota procesa palaišanas laikā
(`needsApiKey: true` — tiek izmantota modeļu sinhronizācijai ar adapteri).

### Aizsardzība pret SSRF

Reversais HTTP starpniekserveris (`/dashboard/.../embed/[...path]`) ir stingri ieprogrammēts pārsūtīt
pieprasījumus tikai uz `http://127.0.0.1:{port}`. Tas nekad neseko novirzīšanām uz mērķiem,
kas nav atgriezeniskajā cilpā. Bibliotēka `ssrf-req-filter` tiek izmantota, lai noraidītu jebkuru augšupstraumes URL, kas
tiek atrisināts uz adresi ārpus atgriezeniskās cilpas diapazona.

### Čaulas drošība (stingrais noteikums #13)

`npm install` tiek izsaukts, izmantojot `execFile('npm', ['install', pkg, '--prefix', dir])` —
bez veidņu literāļiem, čaulas un ārējo ceļu interpolācijas komandas
virknē. Izpildlaika vērtības (porti, API atslēgas) tiek nodotas, izmantojot bērnprocesa `env` objektu.

### Kļūdu sanitizācija (stingrais noteikums #12)

Visas kļūdu atbildes no `/api/services/*` tiek apstrādātas ar `buildErrorBody()` vai
`sanitizeErrorMessage()`. Neapstrādātas `err.stack` un `err.message` vērtības nekad netiek
burtiski atgrieztas izsaucējam.

#### Pievienojams pakalpojumu sniedzēja spraudņa kontrakts (1. fāze, #7333)

`src/lib/services/providerPlugins/` ievieš `ServiceProviderPlugin` kontraktu, kas
vienā objektā apvieno aizmugursistēmas `bootstrap.ts` lauka `ServiceEntry` vērtības un
`serviceBackends.ts` manifesta veidnes laukus, nevis apraksta vienas un tās pašas
aizmugursistēmas struktūru atsevišķi divos nesaistītos failos. Šī dokumenta rakstīšanas brīdī
**migrēts ir tikai `9router`** — `bootstrap.ts` iegūst tā `SERVICES[]` ierakstu no
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`),
izraisot palaišanas kļūdu, ja spraudņa kādreiz trūkst. `cliproxy`, `mux` un `bifrost`

Failam `open-sse/config/providerPluginManifest.ts` ir pievienota arī papildinoša
`createServiceBackendManifestEntry(pluginId, template)` palīgfunkcija, kas izveido korekti
noformētu `ProviderPluginManifestEntry` no `SERVICE_BACKEND_MANIFEST_TEMPLATE` ieraksta — tā
**vēl nav** pieslēgta nevienam aktīvam pieprasījuma ceļam (ne `generateProviderPluginManifestFromRegistry()`,
ne `/v1/providers/[provider]/models`); tas paliek kā turpmāks uzdevums pēc kontrakta
pārbaudīšanas ar otru aizmugursistēmu.

Atlikts turpmākiem PR un izsekots problēmā #7333: `cliproxyapi` migrēšana, izmantojot to pašu
reģistru, `mux`/`bifrost` vispārināšana savienojuma tipā `ServiceBackendPluginId`,
izpildītāja maršrutēšanas īpašo gadījumu (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) iekļaušana spraudņa kontraktā un
`createServiceBackendManifestEntry()` pieslēgšana aktīvam manifesta/modeļu koda ceļam.

## 7. Problēmu novēršana

### Pakalpojums netiek palaists

**Pazīmes:** Poga Start atgriež 503, un stāvoklis paliek `"error"` vai `"starting"`.

**Pārbaudes saraksts:**

1. Pārbaudiet `GET /api/services/{name}/logs` (vai informācijas paneļa sadaļu Logs). Meklējiet
   tādas rindas kā `Error: ENOENT`, `address already in use` vai `Cannot find module`.
2. Pārbaudiet, vai `npm` ir pieejams PATH: izpildiet `which npm` no tā paša lietotāja konta, kas palaiž OmniRoute.
3. Pārbaudiet, vai pakalpojums ir instalēts: skatiet `GET /api/services/{name}/status`
   lauku `installedVersion`. Ja tā vērtība ir `null`, vispirms veiciet instalēšanu.
4. Pārbaudiet, vai `DATA_DIR/services/{name}/node_modules/` pastāv un nav tukšs.
5. Statusa atbildes laukā `lastError` pārbaudiet drošā formā attēloto procesa izbeigšanas iemeslu.

---

### Aukstā palaišana ir lēna (> 10 s līdz stāvoklim `running`)

**Pazīmes:** Stāvoklis ilgu laiku paliek `"starting"`, pirms tas mainās uz `"running"` vai `"error"`.

**Skaidrojums:** 9Router aukstā palaišana ietver lielu atkarību koku importēšanu (DNS,
tuneļa un MITM moduļus). Noklusējuma darbspējas pārbaudes intervāls ir 2 s ar 3 mēģinājumiem, pirms
uzraugs paziņo par noildzi (taču turpina aptauju).

**Risinājums:** `healthIntervalMs` un `waitForHealthy` noildzi
(`healthIntervalMs * 3`) var konfigurēt failā `bootstrap.ts`. Pakalpojumiem ar ilgāku
palaišanas laiku palieliniet `healthIntervalMs` līdz 5000 un `stopTimeoutMs` līdz 30 000.

---

### Porta konflikts (`EADDRINUSE`)

**Pazīmes:** Žurnālos redzams `address already in use :::20130`.

**Cēloņi:**

- Cits process jau izmanto portu 20130.
- Iepriekšējais 9Router process netika pilnībā apturēts (zombijprocess ar PID).

**Risinājums:**

1. Mainiet noklusējuma portu, izmantojot vides mainīgo `NINEROUTER_PORT` failā `.env`.
2. Atrodiet un pārtrauciet konfliktējošo procesu: `lsof -ti :20130 | xargs kill -9`.
3. Portu katram pakalpojumam var konfigurēt failā `bootstrap.ts`, izmantojot lauku `port`.

**Piezīme:** 9Router pēc noklusējuma izmanto tieši portu 20130, lai izvairītos no konflikta ar
OmniRoute noklusējuma portu 20128.

---

### Instalēšanas laikā liegta piekļuve (EACCES)

**Pazīmes:** Instalēšana atgriež 500, un žurnālos redzams `EACCES` vai `permission denied`.

**Cēloņi:**

- OmniRoute procesam nav rakstīšanas tiesību direktorijā `DATA_DIR` vai tā vecākdirektorijā.
- Sistēma darbojas bezsaknes Docker vidē bez rakstīšanas piekļuves piesaistītajam sējumam.

**Risinājums:**

1. Pārbaudiet `DATA_DIR` (noklusējums: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. Pārliecinieties, ka direktorijs pieder lietotājam, kurš palaiž OmniRoute procesu: `chown -R $USER ~/.omniroute/`
3. Docker vidē pārliecinieties, ka sējuma montējumam ir pareizās atļaujas konteinera lietotājam.

---

### Atjaunināšana neizdodas (`npm install` noildze vai tīkla kļūda)

**Pazīmes:** Atjaunināšana atgriež 500 ar `InstallError`, un žurnālos redzama tīkla noildze.

**Pārbaudes saraksts:**

1. Pārliecinieties, ka npm reģistrs ir sasniedzams: `npm ping`.
2. Pārbaudiet, vai tiek izmantots uzņēmuma starpniekserveris: `npm config get proxy`, `npm config get https-proxy`.
3. Mēģiniet veikt instalēšanu manuāli: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. Ja sistēma ir izolēta no tīkla, iepriekš lejupielādējiet tarball arhīvu un izmantojiet `npm install /path/to/tarball.tgz`.

---

### Pakalpojums uzreiz pēc palaišanas parāda stāvokli `"error"` (ātra avārija)

**Pazīmes:** Stāvoklis no `"starting"` mainās uz `"error"` mazāk nekā 5 sekunžu laikā.
Laukā `lastError` redzams `"Fast crash (exited with code 1)"`.

**Pārbaudes saraksts:**

1. Izlasiet pilnu žurnāla beigu daļu: `GET /api/services/{name}/logs?tail=500`.
2. Bieži sastopams cēlonis: trūkst pakalpojumam nepieciešamo vides mainīgo.
3. 9Router gadījumā pārbaudiet, vai palaišanas laikā nodotajā vidē ir iestatīti
   `NINEROUTER_DISABLE_MITM=true` un `NINEROUTER_DISABLE_TUNNEL=true` (skatiet
   `installers/ninerouter.ts` `resolveSpawnArgs`).

## 8. Bieži uzdotie jautājumi

**J: Vai iegulto pakalpojumu galapunktus varu padarīt pieejamus klientiem ārpus atgriezeniskās cilpas?**

Nē. LOCAL_ONLY līmenis ir ieviests apzināti (stingrais noteikums Nr. 17). Maršruti, kas var izsaukt
`npm install` vai palaist `node` procesus, nedrīkst būt sasniedzami datplūsmai, kas nav no atgriezeniskās
cilpas, jo pretējā gadījumā caur tuneli (Cloudflare, Ngrok, Tailscale) nopludināts JWT
ļautu patvaļīgi palaist procesus. Attiecībā uz
`/api/services/` nav nekādu iespēju atteikties no šī ierobežojuma — atšķirībā no `/api/mcp/` tas nav iekļauts pārvaldības tvēruma apiešanas
sarakstā. Skatiet `docs/security/ROUTE_GUARD_TIERS.md`.

---

**J: Vai 9Router un CLIProxyAPI būs pieejami produkcijas/mākoņa izvietojumos?**

Jā. Abi pakalpojumi izmanto to pašu lokāli orientēto modeli kā pats OmniRoute. Tie darbojas
tajā pašā iekārtā un sazinās, izmantojot atgriezenisko cilpu. Šeit „produkcija” nozīmē VPS
vai lokālo serveri, kurā ir izvietots OmniRoute, nevis attālinātu mākoņpakalpojumu sniedzēju.

---

**J: Kā atkļūdot pārraugu?**

1. Sekojiet SSE žurnāla straumei: `curl -N http://localhost:20128/api/services/9router/logs`.
2. Pārbaudiet strukturētos žurnālus OmniRoute pino izvadē, filtrējot pēc
   `service:supervisor` nosaukumvietas.
3. Pārbaudiet DB rindu: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. Izmantojiet `GET /api/services/9router/status`, lai vienā izsaukumā skatītu pašreizējo aktīvo stāvokli, PID, darbspēju
   un `lastError`.

---

**J: Pārraugs rāda `health: "degraded"` vai `health: "unknown"`, bet stāvoklis ir `"running"`. Vai tā ir problēma?**

`"degraded"` nozīmē, ka darbspējas pārbaude atgrieza atbildi, kas nav 200. `"unknown"` nozīmē, ka vēl nav
pabeigta neviena pārbaude (sacensības situācija ar pirmo aptauju). Abi stāvokļi palaišanas laikā ir pārejoši.
Ja darbspēja saglabājas `"degraded"` ilgāk par `healthIntervalMs * 3` ms pēc
`"running"`, iegultais pakalpojums darbojas, taču tā HTTP API neatbild. Statusa
atbildē pārbaudiet, vai ports ir pareizs un vai pakalpojums šajā portā patiešām
klausās.

---

**J: Vai varu mainīt 9Router API atslēgu bez pilnīgas restartēšanas?**

Nē. API atslēga procesa palaišanas laikā tiek nodota 9Router, izmantojot vides mainīgo.
Vides mainīgos nevar mainīt procesā, kas jau darbojas. `POST .../rotate-key`
automātiski aptur un restartē pakalpojumu, lai lietotu jauno atslēgu. Atslēgas rotācija
stājas spēkā pakalpojuma `stopTimeoutMs` laikā (pēc noklusējuma 15 s), kam pieskaitīts tā palaišanas
laiks.

---

**J: Kāds ir gredzenbufera ierobežojums, un kas notiek, kad tas tiek aizpildīts?**

Katram pakalpojumam ir atsevišķs 5 MB gredzenbuferis. Kad buferis ir pilns, vecākās
žurnāla rindas tiek izmestas, lai atbrīvotu vietu jaunām. SSE `snapshot` notikums atgriež
jaunākās rindas `tail` ierobežojuma ietvaros. Žurnāli netiek saglabāti diskā, ja vien
DB rindā nav iestatīts `logsBufferPath`.
