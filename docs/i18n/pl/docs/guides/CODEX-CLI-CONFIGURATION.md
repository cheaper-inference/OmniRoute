Kompletny przewodnik dotyczący używania Codex CLI skonfigurowanego tak, aby korzystał z OmniRoute jako backendu zgodnego z OpenAI.

---

> **TOML jest jedynym obsługiwanym formatem.** Współczesny Codex odczytuje wyłącznie
> `~/.codex/config.toml` (zweryfikowano z codex-cli 0.147.0: `codex --help` dokumentuje
> nadpisania `-c/--config` jako „wczytywane z `~/.codex/config.toml`”). Stary plik
> `~/.codex/config.yaml` należał do starszej wersji CLI instalowanej przez npm i jest po cichu ignorowany.
> Generator w panelu (`/api/cli-tools/apply`, narzędzie `codex`) zapisuje TOML,
> ostrożnie scalając konfigurację — istniejące klucze i bloki innych dostawców są zachowywane,
> klucz API pozostaje w `OMNIROUTE_API_KEY` (nigdy w pliku), a pozostały starszy plik
> `config.yaml` jest zgłaszany jako uwaga dotycząca migracji, bez jego modyfikowania.

## Gotowy do wklejenia plik config.toml

Zastąp `<YOUR_HOST>` i `<YOUR_KEY>` własnymi wartościami:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # limit przechowywania historii dla pojedynczego wywołania narzędzia

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc lub ~/.zshrc — rzeczywista wartość klucza, nigdy w config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex dołączony do aplikacji ChatGPT

Jeśli Codex został zainstalowany za pośrednictwem aplikacji komputerowej ChatGPT, plik binarny `codex` może
znajdować się wyłącznie wewnątrz pakietu aplikacji i nie być jeszcze dostępny w zmiennej `PATH` powłoki. Dodaj
katalog zasobów do pliku uruchamianego przy starcie powłoki:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Otwórz nową powłokę, a następnie sprawdź:

```bash
command -v codex
codex --version
```

### Lokalny OmniRoute bez uwierzytelniania: wystarczy klucz zastępczy

Codex sprawdza, czy zmienna środowiskowa wskazana przez `env_key` istnieje,
**zanim** pierwsze żądanie opuści CLI. Jeśli Twoja **lokalna** instancja OmniRoute
nie wymaga uwierzytelniania, wystarczy dowolna niepusta wartość zastępcza:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Jeśli serwer OmniRoute jest chroniony lub zdalny, użyj zamiast tego prawdziwego klucza.

> **Typowe opcje hosta**
>
> | Dostęp        | URL                           |
> | ------------- | ----------------------------- |
> | Sieć lokalna  | `http://192.168.0.1:20128/v1` |
> | Tailscale     | `http://100.x.x.x:20128/v1`   |
> | Pętla zwrotna | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — dlaczego działa ze wszystkimi modelami

Codex CLI wycofał obsługę `wire_api = "chat"` (Chat Completions) w lutym 2026 roku i obecnie **wymaga** ustawienia `wire_api = "responses"` (OpenAI Responses API). Ustawienie `wire_api = "chat"` powoduje natychmiastową awarię podczas uruchamiania od wersji v0.138.

Wielu dostawców, w tym GLM i Kimi, nadal udostępnia wyłącznie punkt końcowy Chat Completions. DeepSeek V4 udostępnia obecnie natywne Responses API, a także punkt końcowy zgodny z Anthropic; OmniRoute domyślnie używa Responses i pozwala każdemu połączeniu DeepSeek wybrać zgodność z Anthropic.

**OmniRoute rozwiązuje to w sposób całkowicie transparentny:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute wybiera natywny protokół dostawcy i w razie potrzeby wykonuje translację
    → POST /responses (DeepSeek V4) lub /chat/completions (Mistral / GLM / Kimi / inni)
```

Podczas korzystania z OmniRoute nigdy nie potrzebujesz osobnego proxy translacyjnego. **Wszystkie modele używają `wire_api = "responses"`** — OmniRoute zajmuje się resztą.

> **`wire_api` jest ustawieniem domyślnym** — pole ma domyślną wartość `"responses"` i może zostać całkowicie pominięte w `config.toml`. Ustawiaj je jawnie tylko wtedy, gdy chcesz udokumentować zamierzoną konfigurację.

## Okno kontekstu i kompaktowanie

### Pola konfiguracji tokenów

| Pole                             | Opis                                                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Całkowity budżet tokenów dla aktywnego modelu. Ustaw na limit deklarowany dla modelu.                                                                                                                                                                   |
| `model_auto_compact_token_limit` | Próg wyzwalający automatyczne kompaktowanie historii. **Maksymalnie: 90% wartości `model_context_window`** — wartości powyżej 90% są po cichu ignorowane.                                                                                               |
| `tool_output_token_limit`        | Limit tokenów przechowywanych w historii dla wyniku pojedynczego wywołania narzędzia. Zapobiega zapełnieniu okna przez jedną dużą odpowiedź narzędzia. **Nie jest to maksymalny rozmiar danych wyjściowych** — jest to limit przechowywania w historii. |
| `compact_prompt`                 | Bezpośrednie nadpisanie monitu systemowego używanego podczas kompaktowania (v0.138+).                                                                                                                                                                   |

> **Uwaga dotycząca `model_max_output_tokens`**: To pole **nie jest częścią schematu konfiguracji Codex CLI** (nie występuje w bazie kodu Codex napisanej w języku Rust). Jeśli zostanie ustawione, jest po cichu ignorowane. Nie polegaj na nim — użyj `tool_output_token_limit`, aby kontrolować ilość danych wyjściowych narzędzi przechowywanych w historii.

## Nakład rozumowania

Określa, jak dużo model „myśli” przed udzieleniem odpowiedzi.

| Wartość  | Zastosowanie                                              |
| -------- | --------------------------------------------------------- |
| `none`   | Bez rozumowania — bezpośrednia odpowiedź                  |
| `low`    | Trywialne zadania (zmiana nazwy, formatowanie)            |
| `medium` | **Domyślna wartość serwera**, jeśli jej nie podano        |
| `high`   | Zadania średniozaawansowane (refaktoryzacja, debugowanie) |
| `xhigh`  | Architektura, dogłębna analiza, złożone problemy          |

```bash
# Nadpisanie dla pojedynczego wywołania
codex -c model_reasoning_effort=low "zmień nazwę zmiennej x na count"
codex -c model_reasoning_effort=xhigh "zaprojektuj moduł uwierzytelniania"
```

Ustaw także **podsumowanie** rozumowania, aby aplikacja Desktop mogła wyświetlać tekst procesu myślowego (a nie tylko zaszyfrowane bloki):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # lub ultra, jeśli jest obsługiwane
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Budżet myślenia OmniRoute (ustawienie serwera)

Na hoście OmniRoute ustawienie **Settings → AI → Thinking Budget** musi mieć wartość **`passthrough`**, aby ustawienia nakładu/podsumowania Codex docierały do dostawcy nadrzędnego. Tryb **`auto` usuwa** wszystkie pola klienta `reasoning` / `reasoning_effort`, przez co panele procesu myślowego pozostają puste, nawet gdy Codex jest poprawnie skonfigurowany.

Pełny przewodnik: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Kompresja i pamięć podręczna promptów są niezależne i nadal działają w trybie `passthrough`.

## Profile — nazwane konfiguracje dla poszczególnych modeli/przepływów pracy

Profile umożliwiają zmianę modelu i okna kontekstu za pomocą jednej flagi. Każdy profil to płaski plik
`~/.codex/<name>.config.toml`, którego ustawienia są nakładane na bazowy plik `config.toml`.

> **Reguła nazewnictwa (Codex CLI v0.137+):** plik musi mieć nazwę `~/.codex/<name>.config.toml` — **bez prefiksu `profile-`**.
> CLI przekształca `-p kimi-k27` na `~/.codex/kimi-k27.config.toml`. Jeśli plik nie zostanie znaleziony, bez ostrzeżenia zastosowane zostaną ustawienia domyślne.

```bash
codex --profile kimi-k27 "przeanalizuj 10 tys. wierszy tej bazy kodu"
codex -p glm52 "przegląd architektury"
codex --profile deepseek-flash "zmień nazwę zmiennej"   # szybko, tanio
```

### Profile nakładu (ten sam model, różny nakład)

```bash
codex -p low      # cx/gpt-5.5, nakład=low
codex -p medium   # cx/gpt-5.5, nakład=medium
codex -p high     # cx/gpt-5.5, nakład=high
codex -p xhigh    # cx/gpt-5.5, nakład=xhigh (domyślnie)
codex -p chat     # cx/gpt-5.5, nakład nieustawiony (wartość domyślna serwera)
```

## Automatyczne generowanie profili za pomocą `omniroute setup-codex`

Jeśli uruchamiasz OmniRoute na serwerze VPS, możesz automatycznie wygenerować pliki profili na podstawie aktualnego katalogu modeli:

```bash
# Z serwera VPS (używa lokalnego OmniRoute na porcie 20128)
omniroute setup-codex

# Z dowolnego komputera — wskaż swój serwer VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Podgląd bez zapisywania plików
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Wygeneruj tylko profile GLM i Kimi
omniroute setup-codex --only glm,kimi

# Zapisz w niestandardowym katalogu
omniroute setup-codex --codex-home /path/to/.codex
```

Polecenie pobiera `/v1/models`, używa dostrojonych profili dla znanych modeli, w przypadku innych zgodnych modeli tekstowych korzysta z metadanych katalogu i zapisuje `~/.codex/<name>.config.toml` dla każdego z nich. Operacja jest idempotentna — można ją bezpiecznie uruchamiać ponownie.

Jeśli bazowy plik `config.toml` nie zawiera definicji `model_providers.omniroute`, jawne uruchomienie
`setup-codex` dołącza tę definicję do każdej wygenerowanej nakładki, używając wybranego
lokalnego lub zdalnego punktu końcowego. Plik bazowy pozostaje niezmieniony. Istniejąca definicja
dostawcy jest dziedziczona wraz z jej punktem końcowym i ustawieniami uwierzytelniania. Nieprawidłowy
bazowy plik TOML zatrzymuje generowanie przed zapisaniem profili.

Po podaniu `--api-key` lub `OMNIROUTE_API_KEY` nowo zdefiniowany dostawca odwołuje się do
`env_key = "OMNIROUTE_API_KEY"`; sam klucz nigdy nie jest zapisywany ani wyświetlany w
podglądzie. Ustaw tę zmienną w środowisku, w którym uruchamiasz Codex. Bez
podanego klucza nowa definicja nie wymaga klucza, co jest przeznaczone dla instancji OmniRoute
skonfigurowanej do akceptowania nieuwierzytelnionych żądań.

Opisana poniżej opcjonalna automatyczna synchronizacja katalogu zachowuje definicje dostawców już
istniejące w nakładce, ale nie tworzy nowych ustawień dostawcy; najpierw skonfiguruj dostawcę
za pomocą jawnej konfiguracji lub panelu. Istniejące ustawienia dostawcy są pomijane
w podglądach próbnych, ponieważ mogą zawierać dane uwierzytelniające zarządzane przez operatora.

OmniRoute może również **automatycznie synchronizować** te same pliki profili po tym, jak pomyślne wykrycie lub zaimportowanie modeli dostawcy zmieni aktualny katalog. Jest to funkcja **opcjonalna i domyślnie wyłączona**: włącz ją w **panelu CLI Code** („CLI profile auto-sync” → Codex) albo ustaw `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (uwzględnia również `CLI_ALLOW_CONFIG_WRITES`, które jest domyślnie włączone). Po włączeniu zapisuje wyłącznie oddzielne pliki profili `~/.codex/*.config.toml`; nigdy nie zmienia aktywnego/domyślnego pliku `~/.codex/config.toml`, ustawień Codex-lb, uwierzytelniania ani wyboru dostawcy.

## Uruchamianie Codex za pomocą `omniroute launch-codex`

Przed uruchomieniem Codex sprawdza stan instancji OmniRoute:

```bash
# Uruchom z lokalnym OmniRoute (domyślny port 20128)
omniroute launch-codex

# Uruchom z określonym profilem
omniroute launch-codex --profile kimi-k27

# Uruchom ze zdalnym serwerem VPS
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# Przekaż dodatkowe argumenty do codex
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex jest również obsługiwany przez dwa ogólne punkty wejścia oparte na manifeście
(`bin/cli/cli-manifest.mjs`):

```bash
# Interaktywny wybór modelu → zapisuje ~/.codex/<name>.config.toml (TOML, env_key)
omniroute configure codex

# Uruchom codex z dostawcą omniroute wstrzykniętym za pomocą flag -c (bez zapisywania konfiguracji)
omniroute run codex
```

## Zadania długotrwałe

Dwie wartości domyślne OmniRoute mogą po cichu sabotować wielogodzinne sesje Codex CLI. Obydwa ustawienia Codex CLI — nie są aktywne po stronie OmniRoute. Użytkownicy migrujący konfigurację z zewnętrznych serwerów proxy, które przypinają konta i wyłączają przerwy w bezczynności, często trafiają na oba i dochodzą do wniosku, OmniRoute „nie jest w stanie wytrzymać długiej sesji”.

| Objaw                                                                                                 | Prawdopodobna przyczyna                                                                                     | Pokrętło                 |
| ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------ |
| Sesja ciągle przełącza konta/ciągłość pamięci podręcznej podpowiedzi zostaje utracona pomiędzy turami | Powinowactwo sesji TTL to `0` (wyłączone)                                                                   | `sessionAffinityTtlMs`   |
| Połączenie zamiera w połowie rozumowania, bez monitu skierowanego do klienta                          | Watchdog bezczynności strumienia został uruchomiony po 10 minutach bez fragmentu przesyłania strumieniowego | `STREAM_IDLE_TIMEOUT_MS` |

Powiązane dyskusje: [#7126](https://github.com/cheaper-inference/OmniRoute/discussions/7126) (długie usuwanie zadań), [#5718](https://github.com/cheaper-inference/OmniRoute/discussions/5718) (dlaczego powinowactwo jest domyślnie wyłączone). Śledzenie: [#7287](https://github.com/cheaper-inference/OmniRoute/issues/7287).

### 1. Powinowactwo sesji — przypina jedną rozmowę do jednego konta

**Domyślny:** `sessionAffinityTtlMs = 0` (wyłączony).

**Gdzie to ustawić**

- Deska rozdzielcza →** Ustawienia → Routing** →** Powinowactwo sesji** →** Powinowactwo TTL (sekundy)** (`ComboDefaultsTab`)
- Lub ustawienia PATCH z wejściem `sessionAffinityTtlMs`** milisekundy** (zakres Zod `0`–`86_400_000`, czyli do 24 godzin)

> Zmieniono nazwę na #7274 z `codexSessionAffinityTtlMs` dostępnego wyłącznie w Kodeksie. Starszy klucz jest nadal akceptowany jako alias tylko do odczytu; nowe konfiguracje powinny używać `sessionAffinityTtlMs`. Powinowactwo ma teraz zastosowanie do** każdy** dostawca, gdy TTL znajdzie się powyżej `0`, nie tylko Codex — zobacz [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Powinowactwo sesji.

**Co się psuje, gdy pozostaje na poziomie 0**

Każda tura wieloturowej rozmowy Codex jest kierowana niezależnie przez aktywną strategię kombi i może wylądować na** inne konto na turę** . To przerywa ciągłość sesji/pamięci podręcznej monitu. OmniRoute konsultuje tylko nagłówki sesji Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) i pola treści, takie jak `prompt_cache_key` / `session_id` gdy TTL jest większe niż `0` (`extractSessionAffinityKey` w `src/sse/services/auth.ts`).

**Zalecany do wielogodzinnego pojedynczego zadania**

Ustaw TTL** powyżej oczekiwanej długości zadania** (UI max to** 86400 sekund** = 24 godziny):

| Oczekiwana długość zadania | Powinowactwo TTL (UI, sekundy) | `sessionAffinityTtlMs` |
| -------------------------- | ------------------------------ | ---------------------- |
| Kilka godzin               | `14400` (4h)                   | `14400000`             |
| Nocleg / ~ 12h             | `43200` (12h)                  | `43200000`             |
| Cały dzień                 | `86400` (24h, maksymalnie)     | `86400000`             |

Wyrażenie zgody jest celowe: wyłączenie koligacji sprzyja równoważeniu obciążenia między kontami; włączenie tej opcji sprzyja ciągłości przez jedną długą sesję agenta. Ten przewodnik to robi** nie** zmień domyślnych operatorów — wykonujących długie zadania Codex, musisz się zgodzić.

### 2. Limit czasu bezczynności strumienia — nie zabijaj cichych tur rozumowania

**Domyślny:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minut). Dziedziczy po `REQUEST_TIMEOUT_MS`, gdy nie jest ustawiony; wspólna linia bazowa wynosi również 600000. Zobacz limity czasu [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) →.

**Co psuje się domyślnie**

Rozumowanie Codex / obrót narzędzia, który pozostaje cichy przez ponad 10 minut** nie ma prawdziwego kawałka w górę** jest zamykany na siłę przez watchdog bezczynności SSE (`open-sse/utils/stream.ts`). Klient często widzi, że zerwanie połączenia, dopasowanie — „zatrzymuje się automatycznie bez żadnego powiadomienia”.

Krytyczny szczegół: syntetyczny OmniRoute firmy SSE** bicie serca nie resetuje się** bezczynny zegar. Tylko prawdziwy fragment treści nadrzędnej aktualizuje `lastChunkTime`. Cichy model, który wciąż „myśli”, z punktu widzenia nadzorcy wygląda identycznie jak model, który utknął w górnym biegu rzeki.

Powiązana brak aktywności ciała Undici: `FETCH_BODY_TIMEOUT_MS` (również domyślnie ustawiona jest ta sama 10-minutowa linia bazowa; `0` ją wyłącza). W przypadku przesyłania strumieniowego `FETCH_TIMEOUT_MS` obejmuje tylko konfigurację połączenia/pierwsze nagłówki — gdy strumień jest aktywny, straganami zarządzają `STREAM_IDLE_TIMEOUT_MS` i `FETCH_BODY_TIMEOUT_MS`.

**Zalecany do wielogodzinnego pojedynczego zadania**

W środowisku procesowym OmniRoute (`.env` / compose / systemd):

```bash
# Disable stream idle + body inactivity cutoffs for long reasoning turns
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Lub podnieś je powyżej najdłuższej oczekiwanej cichej przerwy (wartości podano w milisekundach):

```bash
# Example: allow up to 2 hours of silence between upstream chunks
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Uruchom ponownie OmniRoute po zmianie tych zmiennych środowiskowych.

### Przepis betonowy — wielogodzinne zadanie Codex

1. **Przypnij konto:** Pulpit nawigacyjny → Ustawienia → Routing → Powinowactwo sesji → Powinowactwo TTL = `43200` (12h) lub `86400` (maks. 24h).
2. **Podnieś/wyłącz wartości odcięcia biegu jałowego** w środowisku OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Zachowaj zwykłe Codex `config.toml` (`wire_api = "responses"`, popraw `base_url`, `OMNIROUTE_API_KEY`) — nie istnieją pokrętła affinity/idle po stronie Kodeksu dla tych dwóch zachowań.
4. Uruchom ponownie OmniRoute, a następnie rozpocznij długie zadanie Codex.

### Decyzja domyślna (#7287)

| Pokrętło                 | Wysyłka domyślna  | Zmiany w tym przewodniku?                                                                        |
| ------------------------ | ----------------- | ------------------------------------------------------------------------------------------------ |
| `sessionAffinityTtlMs`   | `0` (wyłączone)   | **NIE** — pozostaje opcjonalna (równoważenie obciążenia a ciągłość; zobacz Dyskusja #5718)       |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min) | **NIE** — pozostaje 10 minut dla ruchu ogólnego; operatorzy long Codex podnoszą go lub wyłączają |

Globalne odwrócenie dowolnego ustawienia domyślnego zmieniłoby zachowanie każdego klienta instancji, nie tylko Codex. Udokumentuj pokrętła; pozostaw ustawienia domyślne w spokoju, dopóki wyraźna decyzja operatora nie powie inaczej.

### Diagnozowanie cięć jałowych

Kiedy uruchamia się watchdog bezczynności, OmniRoute rejestruje linię w kształcie:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Grep dla `Idle timeout: no data from` (lub kod `stream_idle_timeout` / nazwa błędu `StreamIdleTimeoutError`). Segment dostawcy to dowolny element OmniRoute użyty w tym żądaniu (`codex`, identyfikator innego dostawcy lub `provider`, jeśli nieznany). — nie zawsze jest to dosłowny ciąg znaków `codex`.

## Rozwiązywanie problemów

**`Error: wire_api = "chat" is no longer supported`**
Usuń `wire_api = "chat"` z konfiguracji. Ustaw `wire_api = "responses"` lub pomiń to pole (od wersji v0.138 wartością domyślną jest `"responses"`).

**`Error: model not found`**
Sprawdź, czy model istnieje w OmniRoute i ma prawidłowy prefiks. Użyj `omniroute models list` lub otwórz `/dashboard/providers/<provider>`.

**`Authentication error`**
Upewnij się, że zmienna `OMNIROUTE_API_KEY` jest wyeksportowana: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex sprawdza przed wysłaniem pierwszego żądania, czy zmienna środowiskowa istnieje. Wyeksportuj
prawdziwy klucz dla chronionych serwerów lub niepustą wartość zastępczą, taką jak
`OMNIROUTE_API_KEY=local`, jeśli Twoja **lokalna** instancja OmniRoute nie
wymaga uwierzytelniania. Uruchom ponownie powłokę, jeśli zmienna została dodana do `~/.bashrc` lub `~/.zshrc`.

**`Connection refused`**
Sprawdź, czy OmniRoute jest uruchomiony oraz czy host i port w `base_url` są prawidłowe dla Twojej sieci (lokalnej, Tailscale lub VPS).

**Sesja ulega awarii w pobliżu limitu kontekstu**
Ustaw jawnie `model_context_window` i `model_auto_compact_token_limit`. Zobacz powyższą tabelę okna kontekstu.

**Kompaktowanie uruchamia się zbyt późno**
Zmniejsz `model_auto_compact_token_limit` do 80–85% rozmiaru okna. Nigdy nie ustawiaj wartości powyżej 90%.

**Profil nie jest wczytywany (`-p <name>` jest po cichu ignorowane)**
Upewnij się, że plik istnieje pod ścieżką `~/.codex/<name>.config.toml` (bez prefiksu `profile-`). Uruchom `ls ~/.codex/*.config.toml`.

**Długotrwałe zadanie Codex zostaje przerwane / przełącza konta między turami**
Zobacz [Długotrwałe zadania](#long-running-tasks). Włącz przypisanie sesji (TTL dłuższy niż czas trwania zadania) oraz zwiększ lub wyłącz `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Przeszukaj logi OmniRoute pod kątem `Idle timeout: no data from`.
