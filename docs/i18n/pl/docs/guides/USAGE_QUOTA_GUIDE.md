# Użycie, limity i śledzenie wydatków

> **TL;DR**: OmniRoute śledzi zużycie tokenów każdego żądania, liczy koszt, egzekwuje limity per klucz API i pokazuje analitykę na dashboardzie. Ten przewodnik wyjaśnia, jak to działa.

**Źródła:**

- `open-sse/services/usage.ts` (~70KB) — główne śledzenie użycia
- `src/lib/usageAnalytics.ts` (~10KB) — agregacja na dashboard
- `src/lib/db/quotaSnapshots.ts` — historyczne dane limitów
- `src/lib/db/usage*.ts` — wiele modułów DB związanych z użyciem

---

## Przegląd

Każde żądanie przechodzące przez OmniRoute generuje **rekord użycia**, który rejestruje:

- **Tożsamość**: który klucz API, provider, model, combo
- **Tokeny**: tokeny promptu, completion, cache, łącznie
- **Koszt**: kwota w USD (liczona z danych cenowych)
- **Czas**: opóźnienie, znaczniki start/end
- **Status**: sukces, błąd, rate-limited itd.

Te rekordy są agregowane w **analitykę**, zapisywane jako **snapshoty limitów** i służą do egzekwowania **limitów budżetu per klucz**.

```
Request ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    analytics  quota   billing
                    (dashboard) (enforce) (export)
```

## Co jest rejestrowane

Usługa `usage.ts` rejestruje **zdarzenie użycia** dla każdego żądania:

| Pole               | Typ     | Źródło                                                                    |
| ------------------ | ------- | ------------------------------------------------------------------------- |
| `id`               | string  | UUID generowany podczas zapisu                                            |
| `apiKeyId`         | string  | Klucz API, który zainicjował żądanie                                      |
| `provider`         | string  | Identyfikator dostawcy (openai, anthropic itp.)                           |
| `model`            | string  | Identyfikator modelu (gpt-5, claude-opus-4-6 itp.)                        |
| `comboId`          | string? | Identyfikator kombinacji, jeśli żądanie skierowano przez kombinację       |
| `promptTokens`     | number  | Z odpowiedzi dostawcy nadrzędnego                                         |
| `completionTokens` | number  | Z odpowiedzi dostawcy nadrzędnego                                         |
| `cachedTokens`     | number  | Tokeny trafień w pamięci podręcznej (buforowanie promptów Anthropic itp.) |
| `totalTokens`      | number  | prompt + odpowiedź                                                        |
| `costUsd`          | number  | Obliczany na podstawie danych cenowych                                    |
| `latencyMs`        | number  | Całkowity czas trwania żądania                                            |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                |
| `errorClass`       | string? | Klasa błędu, jeśli status jest inny niż success                           |
| `timestamp`        | string  | ISO 8601 UTC                                                              |
| `metadata`         | object  | Niestandardowe dane wstrzyknięte przez wtyczkę                            |

### Skąd pochodzą tokeny

Tokeny są wyodrębniane z odpowiedzi dostawcy nadrzędnego w **module obsługi odpowiedzi**:

```ts
// Z open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

W przypadku dostawców, którzy nie zwracają danych o użyciu (niektórzy dostawcy korzystający z plików cookie przeglądarki), OmniRoute **szacuje** liczbę tokenów za pomocą heurystyki `~4 chars per token` (zobacz `open-sse/services/autoCombo/pipelineRouter.ts`).

### Tokeny w pamięci podręcznej

OmniRoute śledzi `cached_tokens` oddzielnie od `prompt_tokens`, ponieważ:

- Buforowanie promptów Anthropic wiąże się z obniżoną stawką za tokeny w pamięci podręcznej (10% standardowej stawki)
- Niektórzy dostawcy zwracają `cache_read_input_tokens`, które należy wyceniać inaczej
- Analityka może pokazywać **współczynnik trafień w pamięci podręcznej** = `cached_tokens / prompt_tokens`

### Diagnostyka poziomów zapisu do pamięci podręcznej

Panel kondycji pamięci podręcznej promptów na pulpicie analitycznym rozróżnia zgłaszane przez dostawcę
zapisy do pamięci podręcznej na 5 minut i 1 godzinę. Pola Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` i
`usage.cache_creation.ephemeral_1h_input_tokens` są zachowywane podczas przekształcania danych o użyciu w trybie strumieniowym i
niestrumieniowym oraz zapisywane wraz z podsumowaniami dziennika wywołań. Łączna
liczba tokenów zapisanych do pamięci podręcznej nie jest ponownie dodawana do tych kategorii.

Wywołania zawierające wyłącznie łączny licznik zapisu, w tym starsze rekordy, mają nieznany
poziom. Przy częściowym podziale nieprzypisana reszta pozostaje nieznana; nieprawidłowe lub
sprzeczne liczniki są oznaczane, zamiast otrzymywać po cichu przypisany TTL. Znaczniki
TTL po stronie żądania nie stanowią dowodu naliczenia opłaty za dany poziom.

Prezentowane w panelu oszacowanie kosztu zapisu odpowiadającego opłatom API obejmuje tylko zgłoszone poziomy ze znaną ceną, a nie
całe żądanie. W przypadku natywnego cennika modeli Claude/Anthropic stosuje ono 1,25-krotność
stawki wejściowej dla zapisów na 5 minut i dwukrotność stawki wejściowej dla zapisów na 1 godzinę. Brak
ceny oznacza niedostępność danych, a nie zero. Ceny są zapisywane podczas rejestrowania każdego nowego wywołania;
rekordy historyczne nie są ponownie wyceniane. Konta subskrypcyjne mogą więc mieć
oszacowanie odpowiadające opłatom API bez ponoszenia tej kwoty jako wydatku pieniężnego lub zużycia
limitu subskrypcji. Dotychczasowe obliczenia limitów, budżetu i kosztów zgodnych z rozliczeniami dostawcy pozostają bez zmian.

Ta diagnostyka korzysta z istniejącego podsumowania kondycji pamięci podręcznej o ograniczonym zakresie oraz zasad przechowywania dziennika
wywołań. Nie zmienia domyślnych wartości TTL żądań, routingu ani wyboru konta.
Rejestrowanie wartości TTL żądanej przez klienta oraz faktycznej wartości TTL wysyłanej do dostawcy
w punkcie wysyłania odłożono na później; ten panel przedstawia poziomy z potwierdzeń rozliczeniowych, a nie faktyczną wychodzącą wartość TTL.

Implementacja: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` oraz `open-sse/utils/cacheWriteUsage.ts`.

## Obliczanie kosztu

Koszty są liczone z **danych cenowych** synchronizowanych z LiteLLM (`src/lib/pricingSync.ts`):

| Model             | Input $/1M | Output $/1M | Cached $/1M |
| ----------------- | ---------- | ----------- | ----------- |
| gpt-5             | $2.50      | $10.00      | —           |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50       |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30       |
| gemini-2.5-pro    | $1.25      | $10.00      | —           |

Formuła kosztu (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Dlaczego odejmować cached od prompt?** Część z cache ma osobną cenę; naliczanie input price na cały prompt zawyżyłoby koszt.

### Synchronizacja cen

Dane cenowe są automatycznie synchronizowane z LiteLLM przez endpoint `/api/pricing/sync` (uruchamiany wbudowanym zadaniem cron, nie przez env var widoczne dla użytkownika):

```bash
# Manual trigger
curl -X POST http://localhost:20128/api/pricing/sync
```

Dla modeli bez danych cenowych OmniRoute przechodzi na **szacowanie kosztu** wewnętrznymi średnimi stawkami (źródło: dane cenowe LiteLLM).

## Agregacja według zakresu dat

Moduł `usageAnalytics.ts` oblicza dane widżetów panelu na podstawie surowych danych o użyciu. Obsługuje 7 zakresów czasu:

| Zakres   | Okno czasowe                                  | Zastosowanie                          |
| -------- | --------------------------------------------- | ------------------------------------- |
| `1d`     | Ostatnie 24 godziny                           | Wykrywanie godzinowych skoków kosztów |
| `7d`     | Ostatnie 7 dni                                | Przegląd tygodniowy                   |
| `30d`    | Ostatnie 30 dni                               | Rozliczenia miesięczne                |
| `90d`    | Ostatnie 90 dni                               | Analiza kwartalna                     |
| `ytd`    | Od 1 stycznia bieżącego roku                  | Śledzenie rocznego budżetu            |
| `all`    | Cały okres                                    | Statystyki za cały okres              |
| `custom` | Początek i koniec określone przez użytkownika | Audyty, zapytania ad hoc              |

### Obliczane widżety panelu

Dla dowolnego zakresu dat warstwa analityczna oblicza:

| Widżet                       | Opis                                                                       |
| ---------------------------- | -------------------------------------------------------------------------- |
| **Karty podsumowania**       | Łączna liczba żądań, łączny koszt, łączna liczba tokenów, odsetek sukcesów |
| **Wykres trendu dziennego**  | Koszt + tokeny dziennie, skumulowane według modelu                         |
| **Mapa cieplna aktywności**  | Siatka godzina dnia × dzień tygodnia, kolor = liczba żądań                 |
| **Podział według modeli**    | Wykres kołowy kosztów według modelu                                        |
| **Podział według dostawców** | Wykres słupkowy żądań według dostawcy                                      |
| **Najważniejsze klucze API** | Tabela 10 kluczy o najwyższych kosztach                                    |
| **Analiza błędów**           | Odsetek błędów w czasie, najczęstsze klasy błędów                          |

### Dostęp programistyczny

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // rekordy historii użycia
  "7d",                 // zakres czasu: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // mapa połączeń dostawców (connectionId → nazwa konta)
  {
    startDate: "2025-01-01",  // opcjonalnie: dla zakresu "custom"
    endDate: "2025-06-01",   // opcjonalnie: dla zakresu "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (centy)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Egzekwowanie limitów

Limit dla każdego klucza API jest egzekwowany w dwóch miejscach:

1. **Limit miękki** (`quotaWarnAt`): ostrzeżenie w panelu, gdy użycie przekroczy próg
2. **Limit twardy** (`quotaLimit`): po przekroczeniu żądanie jest odrzucane z kodem HTTP 429

### Konfiguracja

```ts
// Dla każdego klucza API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — wyświetl ostrzeżenie
  quotaLimit: 10_00,    // $10.00 — zablokuj dalsze żądania
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Przebieg egzekwowania limitów

```
Żądanie ──▶ quotaCheck()
              │
              ├── W granicach limitu?  ──▶ zezwól
              │
              └── Limit przekroczony?  ──▶ 429 Too Many Requests
                                   z nagłówkiem Retry-After
```

### Migawki limitów

Tabela `quotaSnapshots` przechowuje **historyczny stan limitów** na potrzeby analizy trendów:

| Pole | Opis |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Śledzony klucz |
| `window` | "day" | "week" | "month" |
| `used` | Koszt wykorzystany w tym oknie (centy) |
| `limit` | Limit (centy) |
| `resetAt` | Moment resetowania okna |
| `createdAt` | Moment utworzenia migawki |

Migawki są tworzone **przy każdym żądaniu**, którego koszt wynosi > 0, i służą do:

- Wyświetlania paska wykorzystania limitu w panelu
- Pokazywania wykresów trendów wykorzystania limitu z 30 dni
- Wyzwalania alertów, gdy użycie zbliża się do limitu

## Retencja i czyszczenie

Dane o użyciu przyrastają o ~1–10 KB na żądanie. Przy dużej skali może to mieć istotne znaczenie.

### Ustawienia retencji

Retencję historii użycia konfiguruje się w ustawieniach bazy danych w interfejsie użytkownika lub za pośrednictwem `/api/settings/database`.

Domyślnie historia użycia jest przechowywana przez **90 dni**.

### Czyszczenie

Stare rekordy są usuwane przez `src/lib/db/cleanup.ts`:

- Uruchamiane przez proces cron działający w tle
- Usuwa z `usage_history` rekordy starsze niż okres retencji skonfigurowany w ustawieniu `usageHistory`

### Szacowane zapotrzebowanie na przestrzeń dyskową

| Liczba żądań        | Przestrzeń na 30 dni | Przestrzeń na 90 dni |
| ------------------- | -------------------- | -------------------- |
| 100 żądań/dzień     | ~3MB                 | ~9MB                 |
| 1 000 żądań/dzień   | ~30MB                | ~90MB                |
| 10 000 żądań/dzień  | ~300MB               | ~900MB               |
| 100 000 żądań/dzień | ~3GB                 | ~9GB                 |

Przy bardzo dużym ruchu rozważ:

- Skrócenie okresu retencji w ustawieniach bazy danych
- Używanie `aggregated_metrics` zamiast surowych rekordów (wyłącznie do analityki)

## Wskazówki dotyczące optymalizacji kosztów

### 1. Używaj odpowiedniego modelu

```bash
# Szybka odpowiedź — wybierz tanio i szybko
curl -d '{"model":"auto/fast","messages":[...]}'

# Złożone zadanie — postaw na jakość
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Włącz buforowanie

Buforowanie promptów Anthropic pozwala zaoszczędzić **90% na powtarzającym się kontekście**:

```ts
// Buforowanie jest automatyczne — wystarczy dołączyć ten sam obszerny prompt systemowy
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Zostanie automatycznie zapisany w pamięci podręcznej
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Używaj kompresji

Kompresja RTK + Caveman pozwala zaoszczędzić **15-95% w sesjach intensywnie korzystających z narzędzi**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Ustaw limity dla poszczególnych kluczy

Zawsze ustawiaj `quotaLimit`, aby zapobiec niekontrolowanemu wzrostowi kosztów:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Limit 10 USD/miesiąc
```

### 5. Sprawdzaj największych użytkowników zasobów

Użyj panelu lub **`/api/usage/analytics`**, aby grupować według klucza API i sortować według kosztu:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Rozwiązywanie problemów

### „Koszt jest wyższy niż oczekiwano”

1. Sprawdź **`/api/usage/analytics?groupBy=model`** — znajdź kosztowny model
2. Sprawdź **`/api/usage/analytics?groupBy=apiKey`** — znajdź użytkownika zużywającego dużo zasobów
3. Sprawdź, czy dane cenowe są aktualne: `POST /api/pricing/sync`

### „Brakujące rekordy”

- Sprawdź ustawienia retencji bazy danych w Panel → Baza danych → Czyszczenie — stare rekordy są usuwane przez okresowe zadanie czyszczenia (`src/lib/db/cleanup.ts`)
- Sprawdź błędy w `src/lib/db/usage*.ts` — błędy zapisu do bazy danych są rejestrowane w logach, ale nie są wyświetlane użytkownikowi
- Sprawdź, czy żądanie rzeczywiście dotarło do `chatCore` — sprawdź routing combo

### „Limit nie jest egzekwowany”

- Sprawdź ustawienie `quotaLimit` klucza
- Sprawdź, czy `quotaWindow` jest ustawione poprawnie
- Poszukaj rekordów `quotaSnapshots` — powinny być tworzone przy każdym żądaniu
