Ten dokument stanowi wiążący materiał referencyjny dla wszystkich bramek jakości CI w OmniRoute.
Opisuje każdą bramkę, zakres jej weryfikacji, zadanie CI, w którym jest uruchamiana, to, czy
wykorzystuje bazową wartość mechanizmu zapadkowego, czy zasady zaliczenia/niezaliczenia, oraz to,
czy blokuje kompilację, czy ma charakter doradczy.

Krótkie podsumowanie i zasady listy dozwolonych wyjątków znajdują się w sekcji „Quality Gates & Ratchets”
w pliku `AGENTS.md`. Krytyczną ocenę, klasyfikację dojrzałości oraz niezależny od narzędzi
plan odtworzenia tego samego systemu zawiera
[Podręcznik bramek jakości](../ops/QUALITY_GATE_PLAYBOOK.md).

## Profile inwentaryzacji i wykonania bramy

### Przyjęcie kandydata

Przepływy pracy CI i Quality Gates wydają stabilny werdykt: `Gate / CI` i `Gate / Quality`. Ich wersjonowane zasady przyjmowania wyliczają każde stanowisko wyższego szczebla jako wymagane lub doradcze. Odpowiednie wymagane zadanie musi zakończyć się pomyślnie: brakujące, anulowane, pominięte, oczekujące i nieznane wyniki nie mogą ustalić PASS. Ważna klasyfikacja obejmująca wyłącznie dokumenty lub tylko katalog może spowodować, że pas kodowy nie będzie miał zastosowania; projekt PR nie jest zaakceptowanym kandydatem. Etykieta `hotfix` nie zrzeka się dowodów.

Obydwa przepływy pracy obejmują PRs do gałęzi main/release, wypychanie do `main`, ręczne wysyłanie i zdarzenia łączenia grup. Wypychanie, wysyłanie i łączenie grup uruchamiają pełny wybór. Naciski na `release/**` nie uruchamiają ich (2026-10-18): każda zmiana uruchomiła już macierz na swoim PR, a połączona kombinacja jest zadaniem Release-Green (`docs/ops/RUNNER_BOX.md` → Hosted lane). Forki i grupy scalone wykorzystują hostowane moduły uruchamiające do zadań, które w innym przypadku wybierałyby samodzielnie hostowane moduły uruchamiające; przed wdrożeniem należy sprawdzić wystarczającą pojemność hosta.

Zwykły PR uruchamia szybką selekcję. Ścieżki `full-code` i `full-code-e2e` polityki dostępu (E2E, integracja, artefakt pakietu, Electron smoke, Bun SQLite, klienci ekosystemu i protokołu) działają tylko w wersji roboczej kolejki Mergify lub przy pełnym uruchomieniu: `gh workflow run ci.yml --ref <branch>`.

Każdy paragon JSON identyfikuje wyewidencjonowane SHA, przebieg przepływu pracy i próbę. CLI odrzuca niedopasowanie checkout/event SHA. Testy przepływu pracy wiążą członkostwo w zasadach z listą `needs` zadania werdyktowego, dzięki czemu nowy lub usunięty pas nie może po cichu zniknąć. Potwierdzenia obejmują własny przepływ pracy, a nie publikację, wdrożenie lub elementy wewnętrzne istniejącego skanera doradczego. Aktywacja obu nazw czeków w regułach oddziałów jest osobną zmianą administracyjną; dodanie tych zadań samo w sobie nie chroni gałęzi.

### Połącz kolejkę

Etykieta `queue` wysyła PR do kolejki Mergify (`.mergify.yml`). Mergify otwiera wersję roboczą PR w gałęzi `mergify/merge-queue/`, CI uruchamia tam pełny wybór, a oryginalny PR łączy się, gdy przechodzą `Gate / CI`, `Gate / Quality` i `Merge integrity (changelog + generated skills)`.

Mergify zapisuje podsumowanie swojej kolejki w opisie wersji roboczej, a inne aplikacje również mogą je edytować. Zdarzenie `pull_request` `edited` w takiej wersji roboczej przyjmuje własną grupę współbieżności (`-queue-edit-<run_id>`), więc nie może anulować rzeczywistego przebiegu wersji roboczej i pomija bramkę i macierz. Tylko `Merge integrity` nadal działa. Pominięte zadanie bramki nosi inną nazwę czeku, ponieważ Mergify odczytuje pominięte `Gate / CI` jako czek zakończony niepowodzeniem i usuwa z PR.

Po usunięciu z kolejki push nie zawsze powoduje ponowne kolejkowanie PR. Skomentuj to `@mergifyio queue`.

### Zachowany dowód w reduktorze odbioru

`scripts/quality/validate-release-acceptance.mjs` redukuje dostarczony plan i jego manifesty; nie ustala, że plan obejmuje cały proces wydań. Jego raporty wyraźnie ustawiają `releaseAcceptance: false`, nawet jeśli tym planem jest `VERIFIED`. Przepływ pracy `release-acceptance.yml` w dalszym ciągu wykorzystuje urządzenia cieniowe, a nie prawdziwe potwierdzenia kompilacji, pakietów, rozruchu lub promocji.

CLI wymaga od `--evidence-root` weryfikacji zatrzymanych dowodów. Pliki są rozpoznawane jako `<evidence-root>/<artifact_id>/<member>` i haszowane jako SHA-256. Rekord PASS bez dowodów, brakujący lub zmieniony plik, niebezpieczna ścieżka lub dowiązanie symboliczne uniemożliwiają weryfikację. Brakujące pliki nie są równoznaczne z pustymi pomyślnymi dziennikami. Istniejące kontrole SHA/run/attempt pozostają niezależne: pasujące bajty nie mogą uratować nieaktualnego paragonu. Integralność pliku nie jest dowodem autentyczności wykonania ani promowania artefaktów.

### Inwentaryzacja skanowania statycznego

Wersjonowany inwentarz npm-alias i członkostwo w trybie static-scan są dostępne w `config/quality/gate-manifest.json`. Uruchom `npm run check:gate-manifest`, aby sprawdzić nazwy skryptów i dokładne polecenia względem `package.json`; dodawanie, usuwanie i dryf poleceń kończą się niepowodzeniem zarówno w przypadku lokalnego przechwytywania, jak i zadań klasyfikacji zmian w CI. Alias nie jest zadaniem przepływu pracy, instancją macierzy ani przypadkiem testowym: liczby te nie mogą być przedstawiane jako zamienne.

Użyj `npm run quality:scan -- --list` lub `npm run quality:scan:fast -- --list`, aby sprawdzić wybrane aliasy bez ich wykonywania. Moduł uruchamiający wywołuje punkt wejściowy npm, więc jego czas działania (w tym Bun jeśli jest skonfigurowany) zostaje zachowany. Manifest rejestruje aliasy poza tymi profilami, które są wywoływane oddzielnie, a polecenia konserwacji są zabronione w profilach skanowania tylko do odczytu.

Profile te obejmują tylko skanowanie statyczne. Nie poświadczają testów produktów, zakresu, opakowania, kontroli zewnętrznych ani pełnej akceptacji kandydata na wydanie. Przyjmowanie przepływu pracy wykorzystuje połączone `config/quality/admission-policy.json` i `scripts/quality/admission-verdict.mjs`. Profile obserwatorów wydania pozostają oddzielne; niezależnie sprawdzają obowiązujące czeki i pokwitowania. Polecenia statyczne pełnego obserwatora są deklarowane w `config/quality/release-green-static-profile.json`, włączając `audit:deps`, wybór testu mutacji i kontrolę translacji. Program ładujący sprawdza poprawność poleceń npm względem deklaracji package.json i modelowanego CI/Quality ; odrzuca dryf zamiast wykonywać tokeny powłoki jako argumenty. Wymagane wyjście skanera SKIP/INCOMPLETE nie może ustanowić PASS. Profil rejestruje swoje zewnętrzne wykluczenia i nie zastępuje hostowanego zasięgu, macierzy testowych, pakietu ani dowodów wdrożenia. Poniższy spis prozy jest odniesieniem, a nie dowodem na to, że brama rzeczywiście działała.

Skrypty działają pod `scripts/check/` (bramy polityk) i `scripts/quality/` (silnik zapadkowy). Źródłem prawdy CI jest `.github/workflows/ci.yml`.

### Zwolnij szybką ścieżkę PR (`quality.yml`)

`.github/workflows/quality.yml` uzupełnia CI na main/release PRs, wypycha do `main`, wysyła i łączy grupy. PRs używa szybkich kontroli filtrowanych według ścieżki. Usunięto trwale wyłączoną zduplikowaną kompilację; prawdziwe czeki build/package/boot pozostają w CI. Zestaw jednostek i vitest działają tylko w CI (`Unit Tests (N/8)` i `Vitest`).

| Stanowisko                                       | Zakres                                                                                                                                                      | Bloking                  |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API dokumenty referencyjne i dokumenty-wszystko                                                                                              | Tak                      |
| `Fast Quality Gates`                             | Kod PRs; kontrole statyczne, sprawdzanie typu, sprawdzanie typu dashboardu, testy jednostkowe, na które ma to wpływ, zapomniane testy rodzeństwa (doradcze) |
| `No new ESLint warnings`                         | Kod PRs; Osłona chroniąca przed kłaczkami                                                                                                                   | Tak, łącznie z widelcami |
| `Merge integrity (changelog + generated skills)` | Bez przeciągu PRs; dziennik zmian i wygenerowana synchronizacja umiejętności                                                                                | Tak, łącznie z widelcami |

#### Zapomniany raport z testów rodzeństwa

`npm run check:forgotten-sibling-tests` działa jako krok doradczy `Fast Quality Gates` i ponownie wykorzystuje moduł rozpoznawania importu za mapą wpływu testu. Dla każdego zmienionego modułu produkcyjnego raportuje deterministyczne łańcuchy `changed module/symbol -> static consumer -> candidate sibling test`, gdy w różnicowym żądaniu ściągnięcia nie ma testu kandydującego. Podsumowanie Markdown i wynik JSON są zachowywane jako artefakt przepływu pracy `forgotten-sibling-tests` do kalibracji przed jakimkolwiek wdrożeniem blokującym.

Reeksport beczek i import dynamiczny służą wyłącznie do diagnostyki rozdzielczości; nigdy nie powodują ustalenia blokującego. Recenzowane wyjątki żyją w `config/quality/forgotten-sibling-allowlist.json`. Każdy wpis musi zawierać nazwę testu konsumenta i kandydata, podać konkretne uzasadnienie i powiązać problem GitHub lub żądanie ściągnięcia. Źle sformułowane wpisy nie są zamykane. Wyjątki nie mogą pomijać usuniętego testu kandydata ani różnicy, która dodaje `.skip`/`.todo`; osłabienie asercji i inne maskowanie pozostają własnością niezależnie blokującej bramki `check:test-masking`.

#### Lustra tłumaczeń są plikami pochodnymi (tryb PR vs tryb zwolnienia)

Funkcja PR edytuje wyłącznie źródła angielskie. Lustra `docs/i18n/<locale>/**` (w tym 66 kopii `llm.txt` i przetłumaczone pliki `CHANGELOG.md` ) i `.i18n-state.json` są przepisywane w jednym kroku przez falę tłumaczeń (gałęzie `docs/i18n-*` / `chore/i18n-*`, zaplanowane `i18n-mirror-refresh.yml`) i wydanie (`npm run release:sync-changelog-i18n`). Bramy lustrzane działają zatem w dwóch trybach, rozpoznawanych przez `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`, następnie `OMNIROUTE_GATE_MODE`, a następnie zdarzenie Actions; uruchomienie lokalne to `release`):

- `check:docs-sync` — release mode uruchamia każdą kontrolę. Tryb PR przechowuje wersję package.json/OpenAPI, główne nagłówki CHANGELOG i osłonę zastąpionych dokumentów oraz wypisuje `SKIP reason=pr-mode` dla kopii lustrzanych `llm.txt` i przetłumaczonych sekcji CHANGELOG — chyba że PR zapisuje kopie lustrzane: gałąź główna zadeklarowana jako moduł piszący rodziny `docs/i18n/**` w `config/quality/derived-paths/*.json` przeprowadza obie kontrole ściśle, a gdy baza różnic zostanie rozwiązana, zmiana, której własny diff edytuje `docs/i18n/<locale>/llm.txt` lub `CHANGELOG.md` ściśle to sprawdza. Baza różnicowa nie jest rozpoznawana w poleceniu depth-1 (zadanie `docs-sync-strict` ), więc tryb PR uruchamia również jedną kontrolę, która nie potrzebuje bazy: każde lustro `llm.txt` musi istnieć, zachować swój separator `---` i przenosić treść główną lub treść współdzieloną przez większość serwerów lustrzanych. Baza, która się poruszyła, pozostawia wszystkie lustra równie nieświeże i przechodzi; ręczna edycja jednego lustra kończy się niepowodzeniem. Przetłumaczone pliki `CHANGELOG.md` nie mają takiej kontroli w kasie depth-1 PR.
- Hak przed zatwierdzeniem uruchamia `check-docs-sync.mjs --mode=pr`: zatwierdzenie jest oceniane na podstawie tego, co robi. Bez flagi uruchomienie lokalne jest trybem zwolnienia, a jeden scalony PR, który edytuje główny plik `llm.txt`, blokowałby każde późniejsze zatwierdzenie w tej bazie, aż do uruchomienia fali. Ta sama zasada obowiązuje dla każdej bramki obsługującej tryb, na której działa hak Husky: hak przechodzi `--mode=pr`, a ścisły werdykt pozostaje przy uruchamianiu w trybie zwolnienia (wydanie PR, wypychanie do `main`, zwykłe uruchomienie lokalne).
- Testy jednostkowe zawartości lustrzanej (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) Tryb wydania — potwierdza każde ustawienie regionalne. Tryb PR potwierdza tylko te serwery lustrzane, które są aktualne w źródle angielskim zgodnie z `.i18n-state.json` (hasz całego pliku lub skrót nagranej sekcji sekcji, piny testowe) i pomija nieaktualne nie bez powodu. Sprawdzanie pochodzenia `target_hash` jest przeprowadzane dla każdej lokalizacji w obu trybach. Świeżość jest podana w sekcji `## `, jednostka skrótu `run-translation.mjs` ; długa sekcja (inwentarz bramek tego pliku zajmuje około połowy) oznacza, że jakakolwiek edycja w nim zawarta powoduje, że te serwery lustrzane są przestarzałe, a ich twierdzenia w trybie PR przechodzą do następnej fali. Kotwica, której źródło angielskie już nie zawiera, opiera się na porównaniu całego pliku.
- `i18n translation drift` — porada dotycząca PRs, ścisła w przypadku wypychania, co noc i wersja wydawana, więc nieaktualne lustro nie może być dostarczane w wydaniu.

`scripts/i18n/sync-llm-mirrors.mjs` (również eksportowany jako `syncLlmMirrors()`, z `--dry-run`) przepisuje kopie lustrzane `llm.txt` ; odświeżenie wydania, fala tłumaczeń i zaplanowane `i18n-mirror-refresh.yml` uruchamiają je (odświeżanie wykrywa nieaktualne serwery lustrzane `llm.txt` podczas pracy próbnej, ponieważ raport dryfu nie zawiera ich listy i synchronizuje je przed `check:docs-all`).

Generowanych jest dwanaście README SVGs pod `docs/diagrams/` (`scripts/docs/gen-readme-<name>.mjs`; `npm run docs:readme-diagrams` regeneruje je wszystkie). Każdy z nich ma test jednostkowy porównania bajtów (`tests/unit/docs/readme-*-svg.test.ts`, zadanie `test-unit`), który kończy się niepowodzeniem, gdy zatwierdzony plik jest nieaktualny w trybie zwolnienia; w PR, `check:generated-artifacts` ocenia SVG które PR edytuje, a dryf bazy pozostawia się do odświeżenia wydania (zobacz [Wygenerowane pliki i wyprowadzone linie bazowe](#generated-files-and-derived-baselines-written-at-release) ). — i `check:docs-counts` odczytują liczby kanoniczne ze swoich węzłów `<text>` — dlatego krok tworzenia konspektu sprawia, że każdy zarysowany ciąg znaków w pliku jest niewidoczny `<text>`. ### Wartości pochodne: tryby bramek `pr` i `release`

Funkcja PR nigdy nie zapisuje wartości zależnej od stanu jej bazy: dostawcy, migracji, liczników narzędzi MCP i strategii, liczb SVG README, migawki faktów. W jednym kroku przeliczane są wszystkie z nich, `npm run release:refresh-derived`, uruchamiane przez wydanie i przez nocne odświeżanie PR. Więc** pomiędzy wydaniami podstawa z założenia stoi za żywym kodem** , a bramka lub test porównujący drzewo z aktywnym kodem byłby czerwony na każdym PR po dodaniu dostawcy przez rodzeństwo. Bramki oceniające wartości pochodne działają zatem w jednym z dwóch trybów rozstrzyganych przez `scripts/check/lib/gateMode.mjs` (wygrywa pierwszy mecz):

1. `--mode=pr|release` w wierszu poleceń;
2. zmienna środowiskowa `OMNIROUTE_GATE_MODE` (`pr` lub `release`);
3. automatycznie, ze zdarzenia GitHub Actions: `pull_request`, którego głową nie jest `release/v*`, `merge_group` lub push do `omni-queue/**` → `pr`; wszystko inne (wypychanie, harmonogram, wysyłka, wydanie PR `release/v* → main`, dowolne uruchomienie lokalne) → `release`.

Co `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) zawodzi w każdym trybie:

| Tryb      | Nie udaje się                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Potrzebuje żywych faktów |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `release` | Każde sprawdzenie, ścisła równość z faktami zebranymi z drzewa (zachowanie, jakie zawsze miała brama): nieaktualna liczba, wersja, poziom zasięgu lub numer SVG to dryf STRICT                                                                                                                                                                                                                                                                                  | Tak                      |
| `pr`      | Jedynie to, co spowodowała zmiana, różniło się od bazy PR z tymi samymi ekstraktorami roszczeń: (1) wartość zarządzana, która nie istniała w bazie dla tego czeku i pliku („PR edytował numer zarządzany — przywracał linię do tekstu podstawowego”); (2) wymagane roszczenie o przenoszenie podstawy i utratę głowy. Niezmienniki treści, które nie wymagają faktów, działają jak w trybie wydania; kontrole dotyczące tylko wydania są wymienione i pominięte | NIE                      |

Pliki instrukcji agenta zawierają** NIE** w ogóle pochodna liczba: `AGENTS.md`, `llm.txt` (i jego kopie `docs/i18n/*/llm.txt` ), fork bs `AGENTS.md`, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` i każde `skills/*/SKILL.md` wskazują na źródło (na przykład `ROUTING_STRATEGY_VALUES` w `src/shared/constants/routingStrategies.ts`) i zamiast tego na `npm run facts`. Niezmiennik „Brak pochodnych zliczeń (plik instrukcji agenta…)” nie zlicza w tym przypadku (dostawcy, migracje, narzędzia i zakresy MCP, strategie routingu, współczynniki punktacji, pakiety trybów) w obu trybach, więc odświeżanie wersji nigdy nie musi przepisywać pliku instrukcji.

W trybie `pr` gałęzie piszące mogą edytować zarządzane wartości: `chore/derived-*` (nocne odświeżanie PR), `release/v*` oraz fale translacyjne `docs/i18n-*` i `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). Partie kolejki (`merge_group`, Mergify drafts , `omni-queue/**`) nie są ponownie oceniane: sumują PRs bramkę już ocenioną, jedną po drugiej.

Kody wyjścia: `0` clean · `1` STRICT dryf (lub miękki dryf z `--strict`) lub naruszenie wartości zarządzanej · `2` infrastruktura — nie można zebrać faktów o kodzie (awaria sondy tsx lub przekroczono limit czasu; limit czasu wynosi `OMNIROUTE_FACTS_TIMEOUT_MS`, domyślnie 600000 ms) lub w przypadku CI nie można rozwiązać bazy różnicowej PR. Wyjście 2 nigdy nie oznacza rozbieżności w dokumentacji: uruchom ponownie zadanie lub napraw środowisko.

Polecenia, które za nim stoją:

- `npm run facts` wypisuje każdą liczbę pochodną jako JSON (`scripts/release/facts.mjs`). `--key=code.mcpTools` wypisuje jedną wartość, `--snapshot` czyta zatwierdzoną migawkę zamiast aktywnego drzewa. Wyjście 2, gdy nie można zebrać faktów.
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) ponownie oblicza wyprowadzone pliki w jednym przebiegu, w następującej kolejności (identyfikatory kroków dla `--only=`): `provider-reference` (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (migawka), `numbers` (plan przepisywania bramki zliczającej zastosowany do dokumentów, a następnie przeniesiony do ich serwerów lustrzanych `docs/i18n/` ), `readme-diagrams`, `skills` (wygenerowany `SKILL.md`), `e2e-timings` (pominięty do momentu wysłania drzewa `syncE2eTimings`), `ui-keys` (przycina klucze `en.json` i, przy domyślnym `--rewritten-since=<ref>` — `origin/main` — ponownie ustawia w kolejce angielskie wartości przepisane od ostatniej wersji), `llm-mirrors` i `verify-generated` (po zapisie, `check:generated-artifacts` i `check:agent-skills-sync` w trybie zwolnienia muszą przejść; pominięte w `--check` i gdy `--only` je opuszcza; niepowodzenie to wyjście 2). Krok `changelog` polega na wyrażeniu zgody (`--with-changelog`, tylko profil wydania). `--profile=nightly` nigdy nie dotyka żądania wersji. W przypadku `-- --check` nic nie zapisuje i wychodzi z 1, gdy jakikolwiek plik ulegnie zmianie lub zarządzana wartość wymaga ręcznej edycji (wyszczególnia oba); wyjście 2 w przypadku awarii infrastruktury. `--json` wypisuje wynik jako JSON.
- `docs/reference/derived-facts.json` to migawka faktów, której użyto podczas ostatniego odświeżenia. Tylko odświeżenie to zapisuje. Generatory README SVG czytają to, a testy jednostkowe czasu PR porównują zatwierdzone dokumenty i wygenerowane za ich pomocą pliki — Never z aktywnym kodem. Pojedyncze porównanie pakietu na żywo to „odświeżenie wydania zamyka cykl” w `tests/unit/check-docs-counts-sync.test.ts`: w przypadku faktów na żywo plan przepisywania odświeżenia zastosowany w pamięci nie pozostawia żadnego dryfu STRICT, którego nie raportuje, a ponowne planowanie niczego nie zmienia.

Aby odtworzyć lokalnie (domyślnie uruchomienie lokalne to `release`):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

Bez rozpoznawalnej bazy (bez `BASE_SHA`/`BASE_REF`, bez lokalnego `origin/release/v<version>`) lokalne uruchomienie `pr` wyświetla ostrzeżenie i pomija różnicę zamiast kończyć się niepowodzeniem.

**Dwa tryby (od 2026-11-13).** Funkcja PR dodaje lub przepisuje klucze w `en.json` (i `bin/cli/locales/en.json`) i nie dotyczy żadnych innych ustawień regionalnych; `check:pr-derived-paths` (zadanie `pr-test-policy`, rodzina `config/quality/derived-paths/translation.json`) nie spełnia funkcji PR która to robi. Pozostałe ustawienia regionalne są uzupełniane raz na wydanie przez `release:refresh-derived`, które wywołuje `syncUiKeys()` w `scripts/i18n/sync-ui-keys.mjs` (dodaj brakujące klucze, usuń pominięte, zaznacz tłumaczenia przepisanego języka angielskiego za pomocą `rewrittenSinceRef`, przetłumacz) lub przez falę tłumaczeń. Bramki odczytują tryb z `scripts/check/lib/gateMode.mjs`: w trybie `pr` (cecha PRs, `merge_group`, `omni-queue/**`) bramki trybu zwolnienia powyżej drukują `SKIP reason=pr-mode` i wychodzą 0; w trybie `release` (wydanie PR, wypychanie do `main`, `workflow_dispatch`, uruchamianie lokalne) są rygorystyczne jak poprzednio, a w wydaniu PR osoby świadome różnic dostają `BASE_REF=origin/main`, więc oceniają każdy klucz dodany lub przepisany przez cykl. Przejrzyj werdykt dotyczący funkcji PR lokalnie za pomocą `--mode=pr`.

PR, która nadal zmienia katalogi regionalne w trybie `pr` (fala tłumaczenia, odświeżenie wydania, poprawka dotycząca tylko tłumaczenia) nie jest pomijana: `check-key-completeness` ocenia każdy zmieniony katalog względem tego samego katalogu w bazie scalania (`scripts/i18n/lib/touched-catalogs.mjs`) i kończy się niepowodzeniem w przypadku klucza utraconego katalogu, braku klucza `en.json`, prawdziwego tłumaczenia zamienionego na znacznik `__MISSING__:` lub na tekst angielski lub wartości, która nie interpoluje już placeholders/tags angielskiego ciągu, którego nie zrobiło PR dotknąć. Katalog nowy w PR musi zawierać cały zestaw kluczy `en.json`. Obejmuje to, w przypadku katalogów, których dotyka PR, to, co zobaczyłyby bramki współczynnika i parzystości CLI.

Testy jednostkowe parzystości ustawień regionalnych (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) działają w tych samych trybach poprzez `tests/_helpers/localeParityMode.ts`: w trybie `pr` pomijają potwierdzenia parzystości kluczy i pozostawiają wydaniu odświeżenie symbolu zastępczego parzystości kluczy, których angielski zmienił się od czasu połączenia bazowego (każdy klucz, gdy płytkie sprawdzenie zadania testu jednostkowego nie może go odczytać). Tym pomocnikiem jest** tylko** usankcjonowane pominięcie warunkowe trybu: `check:test-masking` zlicza `.skip(` i `{ skip: true }`, ale nie obliczone `{ skip: "<reason>" }` które zwraca, więc `tests/unit/locale-parity-mode.test.ts` przypina listę testów, które mogą z niego korzystać — dodanie jednego jest sprawdzoną edycją tej listy.

#### `check-ui-value-drift` — bramka do nieaktualnych tłumaczeń

Łapie tę regresję i18n, której inne bramki strukturalnie nie widzą: angielska wartość jest przepisana, a tłumaczenia wywodzące się z _poprzedniego_ angielskiego pozostają w tyle, więc użytkownicy nieanglojęzyczni nadal czytają pewnie sformułowaną, teraz błędną kopię.

To zostało wysłane naprawdę. `oauthModal.googleOAuthWarning` zostało przepisane po wylądowaniu pomocnika logowania Antigravity (#5203);** 39 z 43 lokalizacji** zachował tekst informujący operatorów, aby „skopiowali pełny URL i wkleili go poniżej” — przepływ, którego nie można ukończyć dla tego dostawcy. Pozostało to niezauważone aż do #8463 ponieważ:

- `sync-ui-keys` uzupełnia tylko klucze, które są** nieobecny** , nigdy takie, które są** nieświeży** ;
- `check-ui-keys-coverage` zlicza klucz _obecność_, więc nieaktualne tłumaczenie jest uznawane za uwzględnione;
- `check-translation-drift` śledzi dokumentację `docs/i18n/<locale>/**.md` odzwierciedlającą — nigdy nie czyta `src/i18n/messages/*.json`. Działa w zadaniu `docs-sync-strict`: doradztwo w zakresie PRs, ścisłe w trybie push i co noc; fala tłumaczeń odświeża lustra, a nie funkcja PR.

**Świadomość różnic, a nie wsparcie bazowe.** Porównuje `en.json` w bazie scalania z drzewem roboczym; dla każdego klucza, którego angielska wartość uległa zmianie, każde ustawienie regionalne, w którym nadal znajduje się nietknięte tłumaczenie, jest nieaktualne. To celowo** zamraża istniejące zadłużenie** — a diff nie może ujawnić, z jakiego staroangielskiego pochodzi dane tłumaczenie, więc bramka ocenia tylko to, czego dotyka bieżąca zmiana. Alternatywa (linia bazowa skrótu dla każdego klucza) kosztowałaby wygenerowany plik ~ 600 KB, 3 × największej istniejącej linii bazowej, zmieniającej się przy każdym i18n PR.

Zaspokoić to można na dwa sposoby:

1. zaktualizować tłumaczenia, których to dotyczy, lub
2. ustaw je na `__MISSING__:<new english>` — środowisko wykonawcze obsługuje następnie poprawiony język angielski (`src/i18n/request.ts::deepMergeFallback`, #7258) i kluczowe kolejki do tłumaczenia.

Jeśli ciąg znaków** oznaczający** zmienione, wolę** zmiana nazwy klucza** : nowy klucz nie może odziedziczyć nieaktualnego tłumaczenia. To jest wzór, którego użyto #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Wychodzi 0 z `SKIP reason=base-unresolved` gdy nie można odczytać katalogu podstawowego (płytki klon bez podstawowego ref), kopiując `check-openapi-breaking`. Tylko tryb wydania: funkcja PR przepisuje język angielski i na tym się zatrzymuje; odświeżenie wydania oznacza pozostawione tłumaczenia (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, to samo `findStaleTranslations`).

- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` — mierzy każdą bramkę numeryczną w sposób CI i wypisuje pozostały zapas na bramkę (`scripts/quality/baseline-headroom.mjs`). Conocne zadanie `baseline-headroom` publikuje tabelę w podsumowaniu przebiegu przepływu pracy i przesyła swój raport JSON/Markdown jako `baseline-headroom-<run_id>`, przechowywany przez 90 dni. Wiersze ostrzegawcze i krytyczne identyfikują bramki w granicach 10% limitu lub już powyżej niego. Przejrzyj te raporty jako wczesne ostrzeżenie o wyczerpaniu budżetów; sprawdź notatki `_rebaseline_*` naruszającej bramy. Zadanie nie tworzy już ani nie aktualizuje stałego problemu; #12149 zachowuje wcześniejszą historię raportów.

**Tryb nowego kodu (Clean-as-You-Code) — od 2026-08-30, tylko szybka ścieżka PR**

Podczas zdarzeń `pull_request` `quality.yml` przekazuje `--base-ref <PR base SHA>` do `check:file-size`, `check:complexity-ratchets` i `check:dead-code`. Dla `check:complexity-ratchets` i `check:dead-code` bramka porównuje HEAD z bazą scalającą** ograniczone do plików, których dotknął PR** (`scripts/check/newCodeMode.mjs`: baza łączenia jest materializowana w jednorazowym `git worktree`, uruchamia się tam ESLint/knip, a na HEAD liczba plików jest różna):

- **bloking** — PR dodał naruszenia cyclomatic/cognitive lub martwy eksport w plikach, które zmienił (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` w logu);
- **doradczy** — suma globalna w porównaniu z zamrożoną wartością bazową. Dziedziczony dryf nigdy nie szkodzi niewinnemu PR; dryf jest ponownie zamrażany podczas uzgadniania zwolnienia i obserwowany przez zadanie dotyczące zapasu.

`check:file-size` używa bazowego ref na własnych warunkach (`scripts/check/check-file-size.mjs`, #8522): sprawdza każdy plik źródłowy i testowy w drzewie, odczytuje liczbę linii każdego z nich w bazie PR za pomocą `git show` i kończy się niepowodzeniem pliku tylko wtedy, gdy przekroczy większy z jego bazowego pułapu (`frozen` / `testFrozen` lub `cap` / `testCap` w przypadku pliku poza linią bazową) i jego podstawowego rozmiaru. Dlatego plik, który już dryfował w bazie, nigdy nie powoduje czerwonego niewinnego PR.

`check:boundary:ratchet` stosuje tę samą regułę do swojej pojedynczej liczby (`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): w zdarzeniach PR zarówno szybkie bramki `quality.yml`, jak i zadanie `ci.yml` lint przekazują PR base SHA, zatwierdzenie bazowe jest mierzone na podstawie eksportu `git archive`, a PR kończy się niepowodzeniem tylko wtedy, gdy liczba krawędzi `open-sse → src` przekracza większą z `metrics.boundaryOpenSseToSrc` i liczbę w bazie. Zgłaszany jest dryft bazowy nad sufitem (`base drift herdado`), ale nigdy nie powoduje to czerwonego niewinnego PR; push → main utrzymuje absolutny pułap, a nierozwiązywalna baza SHA wraca do niego z ostrzeżeniem.

Kandydat z omnikolejką (wypychanie do `omni-queue/**`, zobacz [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ) jest traktowany tak samo jak żądanie ściągnięcia: oba przepływy pracy przekazują bazę kandydatów (`needs.changes.outputs.candidateBase`) jako `--base-ref` i `check:ts7-diagnostics-ratchet` również działa przeciwko niej. W przypadku dwóch bramek nowego kodu podstawą porównania jest samo SHA, a nie pierwszy rodzic najwyższego zatwierdzenia scalania, więc oceniane jest każde żądanie ściągnięcia partii.

`workflow_dispatch` działa, zielone wydanie i zadanie nocnego zapasu nie mają podstawy PR i zachowują absolutne (globalne) porównanie. Zasięg, powielanie i pokrycie typów pozostają na razie globalne (ich narzędzia nie tworzą tanio różnic między plikami) kandydaci — do tego samego leczenia.

**Zamknięcie fazy na v4.0 (LTS = mocniej niż wcześniej, a nie „powrót do normalności”)**

1. Na czystej końcówce `release/v4.0.0` : `npm run quality:headroom --json` dla rekordu, następnie `npm run quality:ratchet -- --update`, `check:file-size --update`, `check:complexity-ratchets --update`, `check:dead-code --update`, — każdej bramki kontroli typu `--update` każda linia bazowa spada do zmierzonej wartości.
2. Usuń `_policy` z `quality-baseline.json` (przezbrojenie `--require-tighten` i nocne bankowanie), przywróć `THRESHOLD = 36` (lub wyższe) w `check-openapi-coverage.mjs`.
3. Zwiększ ponad miarę tam, gdzie modularyzacja się opłaciła: rozmiar pliku `cap` z powrotem do 1000 (lub 800), pokrycie minimalne + 5, martwy eksport 0 dla modułowych pakietów.

### CodeQL Ratchet: odświeżanie rytmu i ręczne wyzwalanie

`check:codeql-ratchet` czyta** stan repo, odświeżany zgodnie z harmonogramem — a nie per PR.** `gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` raportuje `state: configured`, `schedule: weekly`: skanowanie domyślnej konfiguracji GitHub, a nie analiza per-push. Konsekwencja: po połączeniu PR, o którym powiadamia FIXES, mechanizm zapadkowy odczytuje starą, wyższą liczbę do czasu uruchomienia następnego zaplanowanego skanowania —, więc raportuje regresję dla każdego otwartego PR, w tym naprawianie własnych obserwacji PR, dopóki skanowanie nie zostanie nadrobione.

**Odświeżanie ręczne** : `gh workflow run codeql.yml --ref release/vX.Y.Z` ponownie przeprowadza analizę i ponownie publikuje alerty w ciągu kilku minut. Przeczytaj najpierw `.github/workflows/codeql.yml` — jego nagłówek wyjaśnia, że jest to `workflow_dispatch` -only** ponieważ jest to sprzeczne z „domyślną konfiguracją” GitHub** (`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`). Przywracanie wyzwalaczy `push`/`pull_request`/ `schedule` wymaga** najpierw działanie właściciela** : Ustawienia → Code security → CodeQL: Domyślne → Zaawansowane. Nie dodawaj wyzwalacza `schedule:` bez tego przełącznika — spowoduje to tylko niepowodzenie.

**Zaostrz linię bazową po spadku liczby** — `node scripts/check/check-codeql-ratchet.mjs --update` zapisuje nową zmierzoną liczbę do `quality-baseline.json` → `metrics.codeqlAlerts.value`, więc mechanizm zapadkowy nie pozwala po cichu na cofnięcie się do starego sufitu. Sprawdzony przykład (2026-09-02/03): PR #12502 naprawiono 7 rzeczywistych alertów (13 → 6 zmierzonych otwartych); PR #12530 dokręcił zamrożoną linię bazową 11 → 6, aby dopasować; pozostałe 6 odrzucono następnie z uzasadnieniem dla poszczególnych alertów do 0 otwartych.

**Zwolnienia są decyzją operatora (Twarda zasada #14)** — nigdy nie odrzuca alertu CodeQL bez zapisania technicznego uzasadnienia w komentarzu o zwolnieniu: `won't fix` dla wymagań protokołu wyższego szczebla, `used in tests` dla urządzenia testowego, `false positive` dla środka dezynfekującego, CodeQL nie widzi (precedens: `docs/security/ERROR_SANITIZATION.md`).

## Utrwalanie obniżeń limitów zapadkowych — kierunek w dół (#8584)

Mechanizm zapadkowy jest automatyczny tylko w połowie — i to w niewłaściwej połowie. **Podniesienie** limitu to
ręczna edycja JSON, która zajmuje dziesięć sekund i jest najszybszym sposobem na odblokowanie PR z błędem.
**Obniżenie** limitu wymaga uruchomienia `--update` i zatwierdzenia wyniku przez kogoś — a do czasu
wdrożenia zadania `bank-ratchet-shrinks` żaden workflow tego nie wykonywał. Zmierzony skutek
(2026-07-25): 18 zamrożonych plików miało już nie więcej niż limit 800 wierszy dla nowych plików, przy czym najgorszy
przypadek wynosił 132× (`src/shared/validation/schemas.ts`, 19 wierszy z limitem 2 523); pułap
złożoności wzrósł z `1794 → 2169` w około 37 notatkach o ponownym ustawieniu wartości bazowej, przy dokładnie jednym
obniżeniu (−1); a zapis „zaostrz przez `--update` w następnym cyklu” pojawił się 31 razy i został
zrealizowany raz. Limit, który pozostaje po usunięciu kodu będącego jego przyczyną, po cichu zamienia każdy ukończony
podział kodu w przyzwolenie na jego rozrost dla kolejnej osoby edytującej dany plik.

`nightly-release-green.yml` → zadanie **`bank-ratchet-shrinks`** zamyka tę pętlę:

|              |                                                                                                                       |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| Uruchamianie | `schedule` (3× dziennie) + `workflow_dispatch` — celowo **bez** `push`                                                |
| Pomiar       | najwyższa gałąź `release/vX.Y.Z`, z taką samą metodą rozstrzygania i ochroną przed wstrzyknięciem jak `release-green` |
| Zapis        | `check:file-size --update` i `check:complexity-ratchets --update` (oba z założenia mogą wyłącznie obniżać wartości)   |
| Weryfikacja  | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                              |
| Dostarczanie | jeden zawsze aktualny PR kierowany do gałęzi wydania — aktualizowany wymuszeniem, bez tworzenia spamu                 |

Utrwalanie odbywa się partiami, a nie przy każdym pushu, ponieważ nie ma wymagań dotyczących opóźnienia (obniżenie
utrwalone w ciągu 8 godzin jest wystarczające), natomiast uruchamianie po każdym scaleniu wielokrotnie przebudowywałoby gałąź PR
podczas serii scaleń i za każdym razem ponosiłoby koszt pełnego przebiegu ESLint. Wykrywanie nadal odbywa się
przy pushu (`release-green`); partiami wykonywane jest wyłącznie utrwalanie.

### Weryfikator bezpieczeństwa

Zadanie zapisuje zmiany w wartościach bazowych bez nadzoru, dlatego `verify-ratchet-bank.mjs` zapewnia
bezpieczeństwo tego procesu. Porównuje drzewo po wykonaniu `--update` z `HEAD` i **przerywa zadanie
przed utworzeniem jakiegokolwiek commita** — bez otwierania PR — chyba że każda zmiana jest jednym z poniższych przypadków:

- wartość liczbowa `frozen` / `testFrozen` została **obniżona** lub **usunięta**
- `complexity-baseline.json` → `count` została **obniżona**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` została **obniżona**

Wszystko inne powoduje błąd: podniesienie liczby, dodanie wpisu, zmiana `cap`/`testCap` lub
usunięcie/przepisanie notatki `_rebaseline_*` (notatki te stanowią ślad audytowy wyjaśniający, dlaczego każdy
pułap istnieje, i są przechowywane w tym samym obiekcie `frozen` co wpisy plików).
Bot, który mógłby podnieść limit, byłby zdecydowanie gorszy niż obecny stan. Zabezpieczenie przed regresją:
`tests/unit/verify-ratchet-bank.test.ts`.

Zadanie nigdy nie wykonuje pushu do `release/*` — PR scala człowiek, więc błędny pomiar
nie może zostać wdrożony bez przeglądu.

## Zasady dotyczące listy dozwolonych

Każda bramka, która nie może zawieść w przypadku istniejących wcześniej naruszeń, korzysta z zablokowanej listy dozwolonych (np. `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). Polityka jest następująca:

**Napraw pierwotną przyczynę; korzystaj z listy dozwolonych tylko wtedy, gdy naruszenie już istniało i nie można go naprawić w tym samym PR.**

Podczas dodawania wpisu do listy dozwolonych:

1. Dołącz komentarz z uzasadnieniem.
2. Odwołaj się do problemu ze śledzeniem (np. `// #3498 — Phase 2 feature, not yet implemented`).
3. Usuń wpis w tym samym PR, który naprawia naruszenie — nieaktualny wpis, który nie powstrzymuje już aktywnego naruszenia, sam w sobie jest wadą (po wdrożeniu wymuszenie przedawnienia 6A.3 nie przejdzie przez bramkę dla osieroconego wpisu na liście dozwolonych).

Do** nie** dodaj wpisy do listy dozwolonych, aby testy przebiegały szybciej. Zielona brama z rosnącą listą dozwolonych to fałszywe poczucie jakości.

### Kiedy brama zawiedzie na twoim PR

1. **Przeczytaj uważnie wyjście bramki** — mówi dokładnie, który plik lub symbol naruszył regułę.
2. **Napraw naruszenie** — większość bramek to deterministyczne kontrole systemu plików, które przechodzą pomyślnie, gdy tylko kod jest poprawny.
3. **Jeśli naruszenie istniało wcześniej** (tzn. nie wprowadziłeś go, ale bramka go teraz zakrywa): dodaj wpis na liście dozwolonych z komentarzem uzasadniającym i problemem ze śledzeniem.
4. **Jeśli brama jest zapadkowa** (zasięg, ostrzeżenia ESLint, powielanie, złożoność): Twoja zmiana pogorszyła wskaźnik. Napraw podstawowy problem lub (rzadko) uruchom `npm run quality:ratchet -- --update` jeśli zmiana jest zamierzona, a degradacja metryki jest akceptowalna — ale udokumentuj przyczynę w opisie PR.
5. **Bramki doradcze** (`continue-on-error: true`) mają charakter informacyjny — nie blokują scalania, ale pojawiają się w podsumowaniu CI. Napraw je mimo to.
