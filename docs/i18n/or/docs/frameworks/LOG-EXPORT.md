OmniRoute କଲ୍ ଲଗ୍ଗୁଡ଼ିକୁ ଏକ ବାହ୍ୟ ଆନାଲିଟିକ୍ସ ଷ୍ଟୋର୍କୁ ନିରନ୍ତର, କ୍ରମବର୍ଦ୍ଧିଷ୍ଣୁ ଭାବରେ ରପ୍ତାନି କରେ।

Logs ଡ୍ୟାଶବୋର୍ଡ ଟ୍ୟାବ୍ ଅନୁରୋଧ ଇତିହାସକୁ SQLite (`call_logs`)ରେ ରଖେ, ଯାହା
ରୋଟେସନ୍ ଏବଂ ରିଟେନସନ୍ ଦ୍ୱାରା ସୀମିତ। ଲଗ୍ ରପ୍ତାନି ସମାନ ରେକର୍ଡ ସେଟ୍କୁ ଏକ ସମୟସୂଚୀ ଅନୁଯାୟୀ ବାହାରକୁ ପଠାଏ, ଯାହାଦ୍ୱାରା ଏହା
ସ୍ଥାନୀୟ ଡାଟାବେସ୍ଠାରୁ ଅଧିକ ସମୟ ରହିପାରିବ ଏବଂ ଅନ୍ୟ ଡାଟା ସହ ଯୋଡ଼ାଯାଇପାରିବ। BigQuery ହେଉଛି ପ୍ରଥମ ଗନ୍ତବ୍ୟସ୍ଥଳ;
ଏହି ପାଇପଲାଇନ୍ ଏକ ରେଜିଷ୍ଟ୍ରି ହୋଇଥିବାରୁ ଅଧିକ ଗନ୍ତବ୍ୟସ୍ଥଳ ଯୋଡ଼ିହେବ।

## 1. ଏହା କିପରି କାମ କରେ

```
ସର୍ଭର୍ (କନଫିଗ୍ ଡିକ୍ରିପ୍ଟ + ବୈଧତା ଯାଞ୍ଚ, କର୍ସର୍ ସମନ୍ୱୟ)
  → IPC ଆରମ୍ଭ → ପୃଥକ exportChild OS ପ୍ରକ୍ରିୟା
    → କେବଳ-ପଠନୀୟ storage.sqlite → ଅଂଶୀଦାରୀ call-log କ୍ୱେରୀ/ମ୍ୟାପିଂ
      → ଅସିଙ୍କ୍ରୋନସ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟ ହାଇଡ୍ରେସନ୍ → ଗନ୍ତବ୍ୟ prepare()/send()
        → ବ୍ୟାଚ୍ IPC → ସର୍ଭର୍ କର୍ସର୍ ସଂରକ୍ଷଣ କରେ → ack IPC
          → ପରବର୍ତ୍ତୀ ବ୍ୟାଚ୍; done IPC → ସର୍ଭର୍ ସଫଳତା ରେକର୍ଡ କରେ
```

- **ସମୟସୂଚୀ** — ଗୋଟିଏ `JobRegistry` cron ଜବ୍, `log_export`, ଯାହାର ଡିଫଲ୍ଟ ହେଉଛି `0 * * * *` (ପ୍ରତି ଘଣ୍ଟାରେ,
  UTC)। `src/lib/initCloudSync.ts`ରେ ପଞ୍ଜୀକୃତ; `OMNIROUTE_LOG_EXPORT_CRON` ଦ୍ୱାରା ଓଭର୍ରାଇଡ୍ କରାଯାଇପାରିବ।
  ପ୍ରତ୍ୟେକ ଟିକ୍ କ୍ରମାନୁସାରେ ପ୍ରତ୍ୟେକ **ସକ୍ଷମ** ଗନ୍ତବ୍ୟକୁ ନିଷ୍କାସନ କରେ।
- **କର୍ସର୍** — SQLiteର ଅନ୍ତର୍ନିହିତ `call_logs.rowid`, ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ପାଇଁ
  `log_export_destinations.cursor_row_id`ରେ ସଂରକ୍ଷିତ। `timestamp`କୁ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ କର୍ସର୍ କରାଯାଇନାହିଁ: କଲ୍କାରୀମାନେ
  ନିଜର ମୂଲ୍ୟ ଯୋଗାଇପାରନ୍ତି, ତେଣୁ ଏକ ଧୀର ଅନୁରୋଧ ପରେ ଆରମ୍ଭ ହୋଇଥିବା ଏକ ଦ୍ରୁତ ଅନୁରୋଧ ପରେ
  ଲେଖାଯାଇପାରେ, ଏବଂ ଏକ ଟାଇମ୍ଷ୍ଟାମ୍ପ କର୍ସର୍ ଏହାକୁ ଛାଡ଼ିଦେବ।
- **ବ୍ୟାଚିଂ** — ପ୍ରତ୍ୟେକ ଅନୁରୋଧରେ `batch_size` ଧାଡ଼ି (ଡିଫଲ୍ଟ 500), ପ୍ରତ୍ୟେକ ରନ୍ରେ
  `max_rows_per_run` ଧାଡ଼ି (ଡିଫଲ୍ଟ 10000), ଯାହାଦ୍ୱାରା ଏକ ବଡ଼ ବ୍ୟାକ୍ଲଗ୍ ଗୋଟିଏ ରନ୍କୁ ଅବରୋଧ କରିବା ପରିବର୍ତ୍ତେ
  ଅନେକ ଟିକ୍ରେ ନିଷ୍କାସିତ ହୁଏ।
- **ବିତରଣ** — `send()` ସମାଧାନ ହେବା ପରେ ହିଁ କର୍ସର୍ ଆଗକୁ ବଢ଼େ। ଏକ ବିଫଳ ବ୍ୟାଚ୍
  କର୍ସର୍କୁ ପୂର୍ବ ସ୍ଥାନରେ ରଖେ, ତେଣୁ ସେହି ଧାଡ଼ିଗୁଡ଼ିକୁ ପରବର୍ତ୍ତୀ ରନ୍ରେ ପୁଣି ଚେଷ୍ଟା କରାଯାଏ। ଏହି ନିଶ୍ଚୟତା
  ହେଉଛି ଅତିକମରେ-ଥରେ ବିତରଣ ସହିତ ଗନ୍ତବ୍ୟ-ପାର୍ଶ୍ୱ ଡି-ଡୁପ୍ଲିକେସନ୍, ପ୍ରକୃତ ଠିକ୍-ଥରେ ନୁହେଁ: BigQuery ପ୍ରତ୍ୟେକ
  ଧାଡ଼ିକୁ call-log id ଦ୍ୱାରା କୀ କରେ, ଯାହାକୁ ଏହା ନିଜର ଡିଡୁପ୍ ୱିଣ୍ଡୋ ମଧ୍ୟରେ ସର୍ବୋତ୍ତମ-ପ୍ରୟାସ ଆଧାରରେ ସମ୍ମାନ କରେ।
- **ଓଭର୍ଲାପ୍ ଗାର୍ଡ୍** — cron ଟିକ୍ ଏବଂ `POST .../run` ଏକାସାଙ୍ଗରେ ଚାଲୁ ହୋଇପାରେ। ପୂର୍ବରୁ
  ନିଷ୍କାସନ ହେଉଥିବା ଏକ ଗନ୍ତବ୍ୟକୁ ଦୁଇଥର ନିଷ୍କାସନ କରିବା ପରିବର୍ତ୍ତେ ଛାଡ଼ିଦିଆଯାଏ (ରନ୍ ଫଳାଫଳରେ `skipped: true`),
  ତେଣୁ ଏକ ସମକାଳୀନ ରନ୍ କୌଣସି ବ୍ୟାଚ୍ ପୁଣି ପଠାଇପାରିବ ନାହିଁ କିମ୍ବା କର୍ସର୍କୁ ପଛକୁ ଲେଖିପାରିବ ନାହିଁ।
- **ପର୍ଜ୍ ପୁନରୁଦ୍ଧାର** — ଯଦି `cursor_row_id`, `MAX(rowid)`ଠାରୁ ଉପରକୁ ଚାଲିଯାଏ (ସମ୍ପୂର୍ଣ୍ଣ ଟେବୁଲ୍
  ପର୍ଜ୍ କରାଯାଇଛି ଏବଂ rowidଗୁଡ଼ିକ ପୁଣି ଆରମ୍ଭ ହୋଇଛି), ତେବେ ରନର୍ ସ୍ଥାୟୀ ଭାବେ ଅଦୃଶ୍ୟ ହୋଇଯିବା ପରିବର୍ତ୍ତେ 0କୁ ରିୱାଇଣ୍ଡ କରେ।

### ପୃଥକ ରନର୍ ଏବଂ ସୀମାଗୁଡ଼ିକ

Nodeରେ ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ରନ୍ ଏକ ପୃଥକ, ସ୍ୱଳ୍ପ-ସ୍ଥାୟୀ OS ଚାଇଲ୍ଡ ପ୍ରକ୍ରିୟା ଆରମ୍ଭ କରେ (`child_process`
ସହିତ IPC, `worker_threads` ନୁହେଁ)। ବଡି ପଠନ, ପେଲୋଡ୍ JSON ପାର୍ସିଂ/ସିରିଆଲାଇଜେସନ୍, ଗନ୍ତବ୍ୟ
`prepare()` ଏବଂ ଗନ୍ତବ୍ୟ ନେଟୱର୍କ I/O—ସବୁ ସର୍ଭର୍ର ଇଭେଣ୍ଟ ଲୁପ୍ରେ ନୁହେଁ, ସେଠାରେ ଚାଲେ।
କେବଳ କନଫିଗରେସନ୍ ଏବଂ ଛୋଟ ପ୍ରଗତି ସନ୍ଦେଶଗୁଡ଼ିକ IPC ଅତିକ୍ରମ କରେ; ଏକ୍ସପୋର୍ଟ ହୋଇଥିବା ରେକର୍ଡଗୁଡ଼ିକ କେବେବି
ସର୍ଭର୍କୁ ଫେରେ ନାହିଁ। cron ଜବ୍ ଏବଂ Run now ରୁଟ୍ ସମାନ ସାର୍ବଜନୀନ ଫଳାଫଳ ଓ ଓଭର୍ଲାପ୍ ଗାର୍ଡ୍ ବଜାୟ ରଖେ।

ଚାଇଲ୍ଡଟି ସର୍ଭର୍ର ସମାଧାନ ହୋଇଥିବା `DATA_DIR/storage.sqlite`କୁ `node:sqlite` ବ୍ୟବହାର କରି କେବଳ-ପଠନୀୟ ଭାବେ ଖୋଲେ,
ଯେଉଁଥିରେ `busy_timeout=5000` ଏବଂ `query_only=ON` ଥାଏ। ଏହା କୌଣସି DB ସିଙ୍ଗଲ୍ଟନ୍ ଇମ୍ପୋର୍ଟ କରେ ନାହିଁ ଏବଂ
କୌଣସି ମାଇଗ୍ରେସନ୍, ବ୍ୟାକଅପ୍ କିମ୍ବା SQLite ଅପଡେଟ୍ କରେ ନାହିଁ। ଅନୁପସ୍ଥିତ/ଦୁର୍ନୀତିଗ୍ରସ୍ତ ଆର୍ଟିଫ୍ୟାକ୍ଟ ବୁକ୍କିପିଂ (ଦୁର୍ନୀତିଗ୍ରସ୍ତ-ଆର୍ଟିଫ୍ୟାକ୍ଟ
UPDATE ସମେତ) କେବଳ ଡ୍ୟାସ୍ବୋର୍ଡ ବିବରଣୀ ପଥରେ ରହେ। ଉଭୟ ପଥ ଏକ ଶୁଦ୍ଧ

ଏହା ପ୍ରମ୍ପ୍ଟ ବିଷୟବସ୍ତୁ, ତେଣୁ ଏହା **ଡିଫଲ୍ଟ ଭାବେ ବନ୍ଦ** ଏବଂ ଜାଣିଶୁଣି ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ପାଇଁ ଏକ ସ୍ୱତନ୍ତ୍ର ପସନ୍ଦ।
ଯାହା ପଠାଯାଏ ତାହା ହେଉଛି ଡ୍ୟାସ୍ବୋର୍ଡ ଯାହା ଦେଖାଏ, କାରଣ ରପ୍ତାନି ଏବଂ `getCallLogById` ସମାନ ବିବରଣୀ
ରିଜୋଲ୍ୟୁସନ୍ ସେୟାର୍ କରନ୍ତି: ପେଲୋଡ୍ଗୁଡ଼ିକୁ
ଲେଖାଯିବା ସମୟରେ ପୂର୍ବରୁ PII-ପରିଷ୍କୃତ ଏବଂ ଗୁପ୍ତ ତଥ୍ୟ-ରିଡାକ୍ଟ କରାଯାଇଥାଏ, ଏବଂ ଏକ
`noLog` API କୀ ସହିତ କରାଯାଇଥିବା କଲ୍ କୌଣସି ପେଲୋଡ୍ ସଂରକ୍ଷଣ କରେ ନାହିଁ, ତେଣୁ ରପ୍ତାନି କରିବା ପାଇଁ କିଛି ନଥାଏ।

ପେଲୋଡ୍ଗୁଡ଼ିକୁ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟରୁ ପ୍ରତି ଧାଡ଼ି ଆଧାରରେ ପଢ଼ାଯାଏ, ତେଣୁ ହାଇଡ୍ରେସନ୍ କେବଳ ସେହି ଗନ୍ତବ୍ୟଗୁଡ଼ିକ ପାଇଁ ଚାଲେ
ଯେଉଁମାନେ ଏହା ଚାହିଁଥିଲେ। ଏକ ଅନୁପସ୍ଥିତ କିମ୍ବା ଦୁର୍ନୀତ ଆର୍ଟିଫ୍ୟାକ୍ଟ, ବ୍ୟାଚ୍କୁ ବିଫଳ କରି କର୍ସର୍କୁ ଅଟକାଇବା ପରିବର୍ତ୍ତେ,
null ପେଲୋଡ୍ ସହିତ ତାହାର ସାରାଂଶକୁ ରପ୍ତାନି କରେ।

`maxBodyBytes` (ଡିଫଲ୍ଟ 262144) ପ୍ରତ୍ୟେକ ଫିଲ୍ଡକୁ ସୀମିତ କରେ। ଅଧିକ ଲମ୍ବା ପେଲୋଡ୍ଗୁଡ଼ିକୁ **ବାଦ ଦେବା ପରିବର୍ତ୍ତେ
ଛୋଟ କରାଯାଏ** — ଏକ କଟାଯାଇଥିବା ପ୍ରମ୍ପ୍ଟ ତଥାପି "କ’ଣ ପଚରାଯାଇଥିଲା"ର ଉତ୍ତର ଦିଏ — ଏବଂ ଧାଡ଼ିଟିକୁ
`bodies_truncated` ସହିତ ଚିହ୍ନିତ କରାଯାଏ। ଷ୍ଟ୍ରିମ୍ ହୋଇଥିବା ଖଣ୍ଡ-ପରେ-ଖଣ୍ଡ ଡେଲ୍ଟାଗୁଡ଼ିକ ରପ୍ତାନି କରାଯାଏ ନାହିଁ; ସଂଯୋଜିତ ପ୍ରତିକ୍ରିୟା
ପୂର୍ବରୁ `pipeline_provider_response` ଏବଂ `pipeline_client_response`ରେ ରହିଛି।

ଯେଉଁ ପ୍ରକାରର ଗନ୍ତବ୍ୟସ୍ଥଳ ପାଇଁ ଗୋପନୀୟ ତଥ୍ୟ ଘୋଷିତ ହୋଇଛି, ତାହାକୁ ସୃଷ୍ଟି କିମ୍ବା ଅପଡେଟ୍ କରିବା ପାଇଁ **`STORAGE_ENCRYPTION_KEY`
ଆବଶ୍ୟକ**। ଏହା ବିନା `encrypt()` ନିରବରେ ତଥ୍ୟକୁ ଅପରିବର୍ତ୍ତିତ ଭାବେ ପାର କରାଏ, ତେଣୁ SQLiteରେ ଏକ ପ୍ରମାଣପତ୍ରକୁ

ସର୍ଭିସ୍ ଆକାଉଣ୍ଟକୁ ଲକ୍ଷ୍ୟ ଟେବୁଲ୍ରେ `bigquery.tables.updateData` ଆବଶ୍ୟକ, ଏବଂ
`autoCreate` ସକ୍ରିୟ ଥିବାବେଳେ `bigquery.datasets.create` / `bigquery.tables.create` ମଧ୍ୟ ଆବଶ୍ୟକ।

ଏକ କନଫିଗର୍ କରାଯାଇଥିବା ବ୍ୟାଚ୍ ହେଉଛି ଏକ **କର୍ସର୍** ଏକକ, HTTP ଏକକ ନୁହେଁ: `send()` ଏହାକୁ ସର୍ବାଧିକ 500 ଧାଡ଼ି ବିଶିଷ୍ଟ
insertAll କଲ୍ଗୁଡ଼ିକରେ ବିଭକ୍ତ କରେ, ତେଣୁ ଏକ ବଡ଼ `batch_size` BigQueryର 10 MB ଅନୁରୋଧ ସୀମା ଅତିକ୍ରମ କରିପାରେ ନାହିଁ।
ଅସ୍ଥାୟୀ ସ୍ଥିତିଗୁଡ଼ିକ (408/429/500/502/503/504) ପାଇଁ ସମାନ insertIds ପୁନଃବ୍ୟବହାର କରି ଏକ୍ସପୋନେନ୍ସିଆଲ୍
ବ୍ୟାକ୍ଅଫ୍ ସହିତ ସର୍ବାଧିକ ତିନିଥର ପୁନଃଚେଷ୍ଟା କରାଯାଏ; ପ୍ରାମାଣିକରଣ ଏବଂ ସ୍କିମା ବିଫଳତା ରନ୍କୁ ଅନାବଶ୍ୟକ ଭାବେ ବ୍ୟୟ
ନକରି ପ୍ରଥମ ପ୍ରୟାସରେ ହିଁ ତ୍ରୁଟି ନିକ୍ଷେପ କରେ।

କିଛି କ୍ଷଣ ପୂର୍ବରୁ ସୃଷ୍ଟି ହୋଇଥିବା ଏକ ଟେବୁଲ୍ ଏପର୍ଯ୍ୟନ୍ତ ଷ୍ଟ୍ରିମିଂ ଏଣ୍ଡପଏଣ୍ଟକୁ ଦୃଶ୍ୟମାନ ହୁଏ ନାହିଁ, ଯାହା
କିଛି ସେକେଣ୍ଡ ପର୍ଯ୍ୟନ୍ତ 404 ଉତ୍ତର ଦିଏ। ସେହି 404 ପାଇଁ ପୁନଃଚେଷ୍ଟା କରାଯାଏ, କିନ୍ତୁ **କେବଳ ଯେତେବେଳେ ଏହି ରନ୍ ଟେବୁଲ୍ଟି ସୃଷ୍ଟି କରିଥାଏ** —
ପ୍ରକୃତରେ ଅନୁପସ୍ଥିତ ଟେବୁଲ୍ ତଥାପି ତୁରନ୍ତ ବିଫଳ ହୁଏ। ଧ୍ୟାନ ଦିଅନ୍ତୁ, ନିକଟରେ ବିଲୋପ ହୋଇଥିବା ନାମରେ ଏକ ଟେବୁଲ୍କୁ
ପୁନଃସୃଷ୍ଟି କଲେ BigQuery କିଛି ମିନିଟ୍ ପାଇଁ ଷ୍ଟ୍ରିମିଂ ଇନ୍ସର୍ଟଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ; ଏହା ବିଲୋପ-ପରେ-ପୁନଃସୃଷ୍ଟିର
ଏକ ଗୁଣଧର୍ମ, ତେଣୁ ଗୋଟିଏ ଟେବୁଲ୍କୁ ଡ୍ରପ୍ କରି ପୁଣି ଯୋଡ଼ିବା ପରିବର୍ତ୍ତେ ଏକ ନୂଆ ଟେବୁଲ୍ ନାମ ବ୍ୟବହାର କରନ୍ତୁ।

**ଏକ ଆଂଶିକ ବିଫଳତା ଖାଲି ନଥିବା `insertErrors[]` ସହିତ HTTP 200 ଭାବେ ଆସେ।** ଏହାକୁ ଏକ
ବିଫଳତା ଭାବେ ଗ୍ରହଣ କରାଯାଇ ତ୍ରୁଟି ନିକ୍ଷେପ କରାଯାଏ, ଯାହା BigQuery କେବେବି ଗ୍ରହଣ କରିନଥିବା ଧାଡ଼ିଗୁଡ଼ିକୁ ଅତିକ୍ରମ କରି
କର୍ସର୍କୁ ଆଗକୁ ବଢ଼ିବାରୁ ରୋକେ; `tests/unit/log-export-bigquery.test.ts` ଏହି ଆଚରଣକୁ ସ୍ଥିର କରେ।

ପରିବହନ ହେଉଛି ସାଧାରଣ REST — ଏକ ସ୍ୱୟଂ-ସ୍ୱାକ୍ଷରିତ RS256 ଆସର୍ସନ୍କୁ
`https://oauth2.googleapis.com/token`ରେ ଏକ ଆକ୍ସେସ୍ ଟୋକେନ୍ ସହିତ ବିନିମୟ କରାଯାଏ, ତା’ପରେ ଧାଡ଼ିଗୁଡ଼ିକ `tabledata.insertAll`କୁ ଯାଏ। କୌଣସି Google SDK
ଅନ୍ତର୍ଭୁକ୍ତ କରାଯାଇନାହିଁ। ପ୍ରତ୍ୟେକ (ସର୍ଭିସ୍ ଆକାଉଣ୍ଟ, ସ୍କୋପ୍) ପାଇଁ ଆକ୍ସେସ୍ ଟୋକେନ୍ଗୁଡ଼ିକୁ ପ୍ରକ୍ରିୟା ମଧ୍ୟରେ କ୍ୟାଶ୍ କରାଯାଏ।

ସୃଷ୍ଟି ହୋଇଥିବା ଟେବୁଲ୍ରେ ପ୍ରତ୍ୟେକ Logs-ଟ୍ୟାବ୍ ଫିଲ୍ଡ ପାଇଁ ଗୋଟିଏ କଲମ୍ ସହିତ `exported_at` ରହେ, ଏବଂ
କଲ୍ ଲଗ୍ଗୁଡ଼ିକୁ ପ୍ରକୃତରେ ଯେପରି କ୍ୱେରି କରାଯାଏ ସେହି ଅନୁଯାୟୀ ଏହାର ବିନ୍ୟାସ କରାଯାଇଛି:

- **`timestamp` ଉପରେ ଦିନ-ଅନୁଯାୟୀ ପାର୍ଟିସନ୍ କରାଯାଇଛି**, ତେଣୁ ତାରିଖ ଦ୍ୱାରା ସୀମିତ ଏକ କ୍ୱେରି କେବଳ ସେହି ଦିନଗୁଡ଼ିକୁ ସ୍କାନ୍ କରେ।
- **`api_key_name`, `provider`, `model`, `status` ଦ୍ୱାରା କ୍ଲଷ୍ଟର୍ କରାଯାଇଛି** (ସେହି କ୍ରମରେ), ତେଣୁ
  କିଏ ଏହାକୁ ଚଳାଇଲା, ଏହା କେଉଁଠାକୁ ଗଲା, କିମ୍ବା ଏହା ବିଫଳ ହେଲା କି ନାହିଁ—ଏଗୁଡ଼ିକ ଆଧାରରେ ଫିଲ୍ଟର୍ କଲେ ପ୍ରତ୍ୟେକ ପାର୍ଟିସନ୍ର ଭିତରେ ବ୍ଲକ୍ଗୁଡ଼ିକ ଛାଣି ହୋଇଯାଏ। BigQuery
  ସର୍ବାଧିକ ଚାରୋଟି କ୍ଲଷ୍ଟରିଂ କଲମ୍କୁ ଅନୁମତି ଦିଏ ଏବଂ କ୍ରମ ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ: କେବଳ `api_key_name` ଉପରେ ଏକ ଫିଲ୍ଟର୍
  ବ୍ଲକ୍ଗୁଡ଼ିକୁ ଛାଣିଦିଏ, କିନ୍ତୁ କେବଳ `status` ଉପରେ ଏକ ଫିଲ୍ଟର୍ ତାହା କରେ ନାହିଁ।
- **`partitionExpirationDays` ମାଧ୍ୟମରେ ଇଚ୍ଛାଧୀନ ପାର୍ଟିସନ୍ ଧାରଣ ଅବଧି** (0 ସବୁକିଛି ରଖେ), ଯାହା
  ଟେବୁଲ୍ ସୃଷ୍ଟି ସମୟରେ ପ୍ରୟୋଗ କରାଯାଏ।

ଉଭୟ ସେଟିଂ ସୃଷ୍ଟି ସମୟରେ ପ୍ରୟୋଗ ହୁଏ। ଏକ ବିଦ୍ୟମାନ ଟେବୁଲ୍ ତାହାର ପୂର୍ବରୁ ଥିବା ଲେଆଉଟ୍କୁ ବଜାୟ ରଖେ, ତେଣୁ
ଆପଣ ସେଗୁଡ଼ିକୁ ଗ୍ରହଣ କରିବାକୁ ଚାହୁଁଥିଲେ ଗନ୍ତବ୍ୟକୁ ଏକ ନୂଆ ଟେବୁଲ୍ id ପ୍ରତି ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ।

`tests/unit/log-export-bigquery.test.ts` ସୁନିଶ୍ଚିତ କରେ ଯେ ମ୍ୟାପର୍ ଏବଂ ଟେବୁଲ୍ ସ୍କିମା ସମନ୍ୱିତ ରହେ,
ଯାହାଦ୍ୱାରା ବାହାରକୁ ପଠାଇବା ସମୟରେ ଏକ ନୂଆ କଲ୍-ଲଗ୍ କଲମ୍ ନିରବରେ ବାଦ ପଡ଼ିପାରିବ ନାହିଁ।

ବ୍ୟାଚ୍ଗୁଡ଼ିକୁ **ଉଭୟ** ଧାଡ଼ି ସଂଖ୍ୟା ଏବଂ କ୍ରମିକୀକୃତ ବାଇଟ୍ ଅନୁଯାୟୀ ଖଣ୍ଡିତ କରାଯାଏ। ପେଲୋଡ୍ଗୁଡ଼ିକ ରପ୍ତାନି ହେବା ପରେ କେବଳ ଧାଡ଼ି ସଂଖ୍ୟା ଯଥେଷ୍ଟ ନୁହେଁ:
ପ୍ରମ୍ପ୍ଟ ବହନ କରୁଥିବା 500ଟି ଧାଡ଼ିର ଆକାର ଦଶେଇ ମେଗାବାଇଟ୍ ହୋଇପାରେ, ଏବଂ insertAll
10 MB ଠାରୁ ଅଧିକ ଆକାରର ଅନୁରୋଧକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। 500ଟି ଧାଡ଼ି କିମ୍ବା 9 MB—ଯାହା ପ୍ରଥମେ ପୂରଣ ହୁଏ—ସେଠାରେ ଖଣ୍ଡଗୁଡ଼ିକ ବନ୍ଦ ହୁଏ।

## 5. ଏକ ଗନ୍ତବ୍ୟସ୍ଥଳ ଯୋଡ଼ିବା

1. `LogExportDestinationType` ରପ୍ତାନି କରୁଥିବା `src/lib/logExport/destinations/<name>.ts` ସୃଷ୍ଟି କରନ୍ତୁ:
   ଏକ Zod `configSchema`, UI ପାଇଁ ଏକ `fields` ବର୍ଣ୍ଣନାକାରୀ ଆରେ, `secretFields`, ଏବଂ
   `test()` / `prepare()` / `send(records)` ଫେରାଉଥିବା `createClient(config)`।
2. ଏହାକୁ `src/lib/logExport/registry.ts` ରେ ଥିବା `DESTINATIONS` ଆରେରେ ଯୋଡ଼ନ୍ତୁ।
3. `tests/unit/` ଅଧୀନରେ ପରୀକ୍ଷଣଗୁଡ଼ିକ ଲେଖନ୍ତୁ।

ଏତିକି ହେଉଛି ସମ୍ପୂର୍ଣ୍ଣ ପରିବର୍ତ୍ତନ: ସ୍ଥାୟୀ ସଂରକ୍ଷଣ, cron ଜବ୍, REST ସ୍ତର, ଗୁପ୍ତ ତଥ୍ୟର ଏନ୍କ୍ରିପ୍ସନ୍ ଏବଂ
ଡ୍ୟାଶବୋର୍ଡ ଫର୍ମ—ସମସ୍ତେ ରେଜିଷ୍ଟ୍ରିରୁ ପଢ଼ନ୍ତି।

ଏକ ନୂଆ ଗନ୍ତବ୍ୟସ୍ଥଳ ପାଇଁ ଦୁଇଟି ନିୟମ:

- ଆଂଶିକ ବିଫଳତା ହେଲେ `send()` **ନିଶ୍ଚିତ ଭାବରେ ଏକ ତ୍ରୁଟି ଥ୍ରୋ କରିବା ଆବଶ୍ୟକ**। ସଫଳତାର ସହ ସମାଧାନ ହେବାର ଅର୍ଥ ହେଉଛି, "ଗନ୍ତବ୍ୟସ୍ଥଳରେ ଏହି ଧାଡ଼ିଗୁଡ଼ିକ ଅଛି",
  ଏବଂ କର୍ସର୍ ସ୍ଥାୟୀ ଭାବରେ ସେଗୁଡ଼ିକୁ ଅତିକ୍ରମ କରି ଆଗକୁ ବଢ଼ିଯାଏ।
- ବ୍ୟବହାରକାରୀଙ୍କ ଦ୍ୱାରା ଯୋଗାଇ ଦିଆଯାଇଥିବା URL ଗ୍ରହଣ କରୁଥିବା ଗନ୍ତବ୍ୟସ୍ଥଳ, fetch କରିବା ପୂର୍ବରୁ
  ୱେବ୍ହୁକ୍ଗୁଡ଼ିକ ଭଳି ସମାନ ପ୍ରକ୍ରିୟାରେ `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) ମାଧ୍ୟମରେ ତାହାକୁ ବୈଧ କରିବା ଆବଶ୍ୟକ।
  BigQuery ପାଇଁ ଏହା ଆବଶ୍ୟକ ନୁହେଁ: ଏହାର ହୋଷ୍ଟଗୁଡ଼ିକ ଧ୍ରୁବକ।

## 6. ଏହାକୁ ପରିଚାଳନା କରିବା

- **ଡ୍ୟାଶବୋର୍ଡ**: Integrations → Log export। ଏକ ଗନ୍ତବ୍ୟସ୍ଥଳ ଯୋଡ଼ନ୍ତୁ, ଧାଡ଼ିଗୁଡ଼ିକୁ ଲେଖିବା ବିନା ପରିଚୟପତ୍ରଗୁଡ଼ିକ ଯାଞ୍ଚ କରିବା ପାଇଁ **Test** ଚଳାନ୍ତୁ,
  ତା'ପରେ ଏହାକୁ ସକ୍ଷମ କରନ୍ତୁ।
- **ବ୍ୟାକ୍ଲଗ୍**: ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟସ୍ଥଳ କାର୍ଡ ବିଚାରାଧୀନ ଧାଡ଼ିଗୁଡ଼ିକ ଏବଂ କର୍ସର୍ ଦେଖାଏ; `GET
/api/log-export/status` ସମାନ ପରିସଂଖ୍ୟାନ ସହ ଶେଷ 20ଟି ଜବ୍ ରନ୍ ଫେରାଏ।
- **ଏକ ବିଫଳ ଗନ୍ତବ୍ୟସ୍ଥଳ ଅନ୍ୟଗୁଡ଼ିକୁ ବିଫଳ କରେ ନାହିଁ** — ରନ୍ ସାରାଂଶ `last_status` / `last_error` ରେ ପ୍ରତି-ଗନ୍ତବ୍ୟସ୍ଥଳ
  ସ୍ଥିତି ରେକର୍ଡ କରେ, ଏବଂ ଜବ୍ ରନ୍ ଇତିହାସ ସାମଗ୍ରିକ ସ୍ଥିତିକୁ ରଖେ।
- **ଏକ ଗନ୍ତବ୍ୟସ୍ଥଳ ବିଲୋପ କଲେ ତାହାର କର୍ସର୍ ମଧ୍ୟ ବିଲୋପ ହୁଏ।** ଏହାକୁ ପୁଣି ଯୋଡ଼ିଲେ ସବୁଠାରୁ ପୁରୁଣା ସଂରକ୍ଷିତ
  କଲ୍ ଲଗ୍ରୁ ଆରମ୍ଭ ହୁଏ, ଯାହା ଗନ୍ତବ୍ୟସ୍ଥଳରେ ପୂର୍ବରୁ ଥାଇପାରୁଥିବା ଧାଡ଼ିଗୁଡ଼ିକୁ ପୁଣି ପଠାଏ। BigQuery ରେ ପ୍ରତି-ଧାଡ଼ି
  `insertId` କେବଳ BigQuery ର ନିଜସ୍ୱ ଡି-ଡୁପ୍ଲିକେସନ୍ ୱିଣ୍ଡୋ ମଧ୍ୟରେ ଏହାକୁ ସମ୍ଭାଳେ, ତେଣୁ ଗନ୍ତବ୍ୟସ୍ଥଳକୁ ବିଲୋପ କରିବା ପରିବର୍ତ୍ତେ
  ଅକ୍ଷମ କରିବାକୁ ପ୍ରାଧାନ୍ୟ ଦିଅନ୍ତୁ।
