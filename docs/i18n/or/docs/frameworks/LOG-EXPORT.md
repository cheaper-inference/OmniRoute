OmniRoute କଲ୍ ଲଗ୍‌ଗୁଡ଼ିକୁ ଏକ ବାହ୍ୟ ଆନାଲିଟିକ୍ସ ଷ୍ଟୋର୍‌କୁ ନିରନ୍ତର, କ୍ରମବର୍ଦ୍ଧିତ ଭାବେ ରପ୍ତାନି।

ଲଗ୍ ଡ୍ୟାସବୋର୍ଡ ଟ୍ୟାବ୍ ଅନୁରୋଧ ଇତିହାସକୁ SQLite (`call_logs`) ରେ ରଖେ, ଯାହା
ରୋଟେସନ୍ ଓ ରିଟେନ୍ସନ୍ ଦ୍ୱାରା ସୀମିତ। ଲଗ୍ ରପ୍ତାନି ଏକ ସମୟସୂଚୀ ଅନୁସାରେ ସେହି ରେକର୍ଡ ସମୂହକୁ ବାହାରକୁ ପଠାଏ, ଯାହାଫଳରେ ଏହା
ସ୍ଥାନୀୟ ଡାଟାବେସ୍‌ଠାରୁ ଅଧିକ ସମୟ ରହିପାରିବ ଏବଂ ଅନ୍ୟ ଡାଟା ସହିତ ଯୋଡ଼ାଯାଇପାରିବ। BigQuery ହେଉଛି ପ୍ରଥମ ଗନ୍ତବ୍ୟ;
ପାଇପଲାଇନ୍ ଏକ ରେଜିଷ୍ଟ୍ରି ହୋଇଥିବାରୁ, ଆହୁରି ଗନ୍ତବ୍ୟ ଯୋଡ଼ାଯାଇପାରିବ।

## 1. ଏହା କିପରି କାମ କରେ

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **ସମୟସୂଚୀ** — ଗୋଟିଏ `JobRegistry` cron ଜବ୍, `log_export`, ଯାହାର ଡିଫଲ୍ଟ ହେଉଛି `0 * * * *` (ପ୍ରତି ଘଣ୍ଟାରେ,
  UTC)। ଏହା `src/lib/initCloudSync.ts` ରେ ପଞ୍ଜୀକୃତ; `OMNIROUTE_LOG_EXPORT_CRON` ଦ୍ୱାରା ବଦଳାଯାଇପାରିବ।
  ପ୍ରତ୍ୟେକ ଟିକ୍‌ରେ ପ୍ରତ୍ୟେକ **ସକ୍ଷମ** ଗନ୍ତବ୍ୟର ଅପେକ୍ଷାରତ ରେକର୍ଡଗୁଡ଼ିକ କ୍ରମାନୁସାରେ ରପ୍ତାନି ହୁଏ।
- **କର୍ସର୍** — SQLite ର ଅନ୍ତର୍ନିହିତ `call_logs.rowid`, ଯାହା ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ପାଇଁ
  `log_export_destinations.cursor_row_id` ରେ ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ ହୁଏ। ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ `timestamp` କୁ କର୍ସର୍ କରାଯାଇନାହିଁ: କଲ୍ କରୁଥିବା ପକ୍ଷ
  ନିଜର ମୂଲ୍ୟ ଦେଇପାରନ୍ତି, ତେଣୁ ପରେ ଆରମ୍ଭ ହୋଇଥିବା ଏକ ଦ୍ରୁତ ଅନୁରୋଧ ପରେ ଏକ ଧୀର ଅନୁରୋଧ ଲେଖାଯାଇପାରେ,
  ଏବଂ ଟାଇମ୍‌ଷ୍ଟାମ୍ପ କର୍ସର୍ ତାହାକୁ ଛାଡ଼ିଦେବ।
- **ବ୍ୟାଚିଂ** — ପ୍ରତି ଅନୁରୋଧରେ `batch_size` ଧାଡ଼ି (ଡିଫଲ୍ଟ 500), ପ୍ରତି ରନ୍‌ରେ `max_rows_per_run` ଧାଡ଼ି
  (ଡିଫଲ୍ଟ 10000), ଯାହାଫଳରେ ଏକ ବଡ଼ ବ୍ୟାକଲଗ୍ ଗୋଟିଏ ଟିକ୍‌କୁ ଅବରୋଧ କରିବା ପରିବର୍ତ୍ତେ ଅନେକ ଟିକ୍‌ରେ ରପ୍ତାନି ହୁଏ।
- **ବିତରଣ** — `send()` ସଫଳ ଭାବେ ସମାପ୍ତ ହେବା ପରେ ହିଁ କର୍ସର୍ ଆଗକୁ ବଢ଼େ। ଏକ ବ୍ୟାଚ୍ ବିଫଳ ହେଲେ
  କର୍ସର୍ ପୂର୍ବ ସ୍ଥାନରେ ରହେ, ତେଣୁ ପରବର୍ତ୍ତୀ ରନ୍‌ରେ ସେହି ଧାଡ଼ିଗୁଡ଼ିକୁ ପୁଣି ଚେଷ୍ଟା କରାଯାଏ। ଏହାର ଗ୍ୟାରେଣ୍ଟି ହେଉଛି
  ଅତିକମରେ ଥରେ ବିତରଣ ସହିତ ଗନ୍ତବ୍ୟ ପାର୍ଶ୍ୱରେ ଡୁପ୍ଲିକେଟ୍ ଅପସାରଣ, ପ୍ରକୃତରେ ଠିକ୍ ଥରେ ବିତରଣ ନୁହେଁ: BigQuery ପ୍ରତ୍ୟେକ
  ଧାଡ଼ି ପାଇଁ କଲ୍-ଲଗ୍ id କୁ କୀ ଭାବେ ବ୍ୟବହାର କରେ, ଯାହାକୁ ଏହା ନିଜର ଡୁପ୍ଲିକେଟ୍ ଅପସାରଣ ସମୟସୀମା ମଧ୍ୟରେ ସର୍ବୋତ୍ତମ ପ୍ରୟାସ ଭିତ୍ତିରେ ମାନେ।
- **ଓଭରଲାପ୍ ସୁରକ୍ଷା** — cron ଟିକ୍ ଓ `POST .../run` ଏକାସାଙ୍ଗରେ ଆରମ୍ଭ ହୋଇପାରନ୍ତି। ଯେଉଁ ଗନ୍ତବ୍ୟରେ
  ରପ୍ତାନି ଆଗରୁ ଚାଲିଛି, ତାହାକୁ ଦୁଇଥର ରପ୍ତାନି କରିବା ପରିବର୍ତ୍ତେ ଛାଡ଼ିଦିଆଯାଏ (ରନ୍ ଫଳାଫଳରେ `skipped: true`),
  ତେଣୁ ଏକ ସମକାଳୀନ ରନ୍ ବ୍ୟାଚ୍‌କୁ ପୁଣି ପଠାଇପାରିବ ନାହିଁ କିମ୍ବା କର୍ସର୍‌କୁ ପଛକୁ ଲେଖିପାରିବ ନାହିଁ।
- **ସମ୍ପୂର୍ଣ୍ଣ ବିଲୋପ ପରେ ପୁନରୁଦ୍ଧାର** — ଯଦି `cursor_row_id`, `MAX(rowid)` ଠାରୁ ଅଧିକ ହୋଇଯାଏ (ସମ୍ପୂର୍ଣ୍ଣ ଟେବୁଲ୍
  ବିଲୋପ ହୋଇ rowid ଗୁଡ଼ିକ ପୁନର୍ବାର ଆରମ୍ଭ ହୋଇଥିଲେ), ରନର୍ ସ୍ଥାୟୀ ଭାବେ ରେକର୍ଡ ଦେଖିବାରେ ଅସମର୍ଥ ହେବା ପରିବର୍ତ୍ତେ 0 କୁ ଫେରେ।

### ପୃଥକ ରନର୍ ଏବଂ ସୀମା

Node ରେ ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ରନ୍ ଏକ ପୃଥକ, ସ୍ୱଳ୍ପସ୍ଥାୟୀ OS ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ଆରମ୍ଭ କରେ (IPC ସହିତ `child_process`,
`worker_threads` ନୁହେଁ)। ବଡି ପଢ଼ିବା, ପେଲୋଡ୍ JSON ପାର୍ସିଂ/ସିରିଆଲାଇଜେସନ୍, ଗନ୍ତବ୍ୟର
`prepare()` ଏବଂ ଗନ୍ତବ୍ୟ ନେଟୱର୍କ I/O ସବୁ ସେଠାରେ ଚାଲେ, ସର୍ଭର୍‌ର ଇଭେଣ୍ଟ ଲୁପ୍‌ରେ ନୁହେଁ।
କେବଳ କନଫିଗରେସନ୍ ଓ ଛୋଟ ପ୍ରଗତି ବାର୍ତ୍ତାଗୁଡ଼ିକ IPC ଦେଇ ଯାଆନ୍ତି; ରପ୍ତାନି ହୋଇଥିବା ରେକର୍ଡଗୁଡ଼ିକ କେବେ ବି
ସର୍ଭର୍‌କୁ ଫେରନ୍ତି ନାହିଁ। cron ଜବ୍ ଏବଂ ଏବେ ଚଲାନ୍ତୁ ରୁଟ୍ ସମାନ ସାର୍ବଜନୀନ ଫଳାଫଳ ଓ ଓଭରଲାପ୍ ସୁରକ୍ଷା ବଜାୟ ରଖନ୍ତି।

ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ସର୍ଭର୍‌ର ନିର୍ଦ୍ଧାରିତ `DATA_DIR/storage.sqlite` କୁ `node:sqlite` ବ୍ୟବହାର କରି କେବଳ-ପଠନ ମୋଡ୍‌ରେ ଖୋଲେ,
ଯେଉଁଥିରେ `busy_timeout=5000` ଏବଂ `query_only=ON` ରହେ। ଏହା କୌଣସି DB ସିଙ୍ଗଲଟନ୍ ଇମ୍ପୋର୍ଟ କରେ ନାହିଁ ଏବଂ କୌଣସି
ମାଇଗ୍ରେସନ୍, ବ୍ୟାକଅପ୍ କିମ୍ବା SQLite ଅପଡେଟ୍ କରେ ନାହିଁ। ଅନୁପସ୍ଥିତ/କ୍ଷତିଗ୍ରସ୍ତ ଆର୍ଟିଫାକ୍ଟର ହିସାବରକ୍ଷଣ (କ୍ଷତିଗ୍ରସ୍ତ ଆର୍ଟିଫାକ୍ଟର
UPDATE ସମେତ) କେବଳ ଡ୍ୟାସବୋର୍ଡ ବିବରଣୀ ପଥରେ ରହେ। ଉଭୟ ପଥ ଏକ ଶୁଦ୍ଧ
ବିବରଣୀ ରିଜଲଭର୍ ସେୟାର କରନ୍ତି; ରପ୍ତାନି ଅସିଙ୍କ୍ରୋନସ୍ ଫାଇଲସିଷ୍ଟମ୍ ପଠନ ଏବଂ ସମାନ ଆର୍ଟିଫାକ୍ଟ → ପୁରୁଣା

ଏହା ପ୍ରମ୍ପ୍ଟ ବିଷୟବସ୍ତୁ, ତେଣୁ ଏହା **ଡିଫଲ୍ଟ ଭାବେ ବନ୍ଦ** ରହେ ଏବଂ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ପାଇଁ ଅଲଗା ପସନ୍ଦ ଅଟେ।
ଡ୍ୟାସ୍‌ବୋର୍ଡରେ ଯାହା ଦେଖାଯାଏ ତାହାହିଁ ପଠାଯାଏ, କାରଣ ରପ୍ତାନି ଏବଂ `getCallLogById` ସମାନ ବିବରଣୀ
ନିର୍ଣ୍ଣୟ ବ୍ୟବହାର କରନ୍ତି: ପେଲୋଡ୍‌ଗୁଡ଼ିକ
ଲେଖାଯିବା ସମୟରେ ହିଁ PII-ମୁକ୍ତ ଏବଂ ଗୋପନ ତଥ୍ୟ ଲୁଚାଯାଇଥିବା ଅବସ୍ଥାରେ ଥାଏ, ଏବଂ
`noLog` API କି ସହିତ କରାଯାଇଥିବା କଲ୍ କୌଣସି ପେଲୋଡ୍ ସଂରକ୍ଷଣ କରେ ନାହିଁ, ତେଣୁ ରପ୍ତାନି କରିବାକୁ କିଛି ନଥାଏ।

ପେଲୋଡ୍‌ଗୁଡ଼ିକ ଫାଇଲ୍‌ସିଷ୍ଟମ୍ ଆର୍ଟିଫାକ୍ଟରୁ ପ୍ରତ୍ୟେକ ଧାଡ଼ି ଅନୁସାରେ ପଢ଼ାଯାଏ, ତେଣୁ ହାଇଡ୍ରେସନ୍ କେବଳ ଏହାକୁ ଅନୁରୋଧ କରିଥିବା
ଗନ୍ତବ୍ୟଗୁଡ଼ିକ ପାଇଁ ଚାଲେ। ଆର୍ଟିଫାକ୍ଟ ଅନୁପସ୍ଥିତ କିମ୍ବା ନଷ୍ଟ ହୋଇଥିଲେ, ବ୍ୟାଚ୍‌କୁ ବିଫଳ କରି କର୍ସର୍‌କୁ ଅଟକାଇବା
ପରିବର୍ତ୍ତେ ତାହାର ସାରାଂଶକୁ ନଲ୍ ପେଲୋଡ୍ ସହିତ ରପ୍ତାନି କରାଯାଏ।

`maxBodyBytes` (ଡିଫଲ୍ଟ 262144) ପ୍ରତ୍ୟେକ ଫିଲ୍ଡର ସୀମା ଧାର୍ଯ୍ୟ କରେ। ଅଧିକ ଲମ୍ବା ପେଲୋଡ୍‌ଗୁଡ଼ିକୁ **ବାଦ ଦେବା ପରିବର୍ତ୍ତେ
ଛୋଟ କରାଯାଏ** — କଟାଯାଇଥିବା ପ୍ରମ୍ପ୍ଟ ମଧ୍ୟ "କ’ଣ ପଚରାଯାଇଥିଲା" ତାହାର ଉତ୍ତର ଦିଏ — ଏବଂ ଧାଡ଼ିଟିକୁ
`bodies_truncated` ସହିତ ଚିହ୍ନିତ କରାଯାଏ। ଷ୍ଟ୍ରିମ୍ ହୋଇଥିବା ଖଣ୍ଡ-ଖଣ୍ଡ ଡେଲ୍ଟାଗୁଡ଼ିକ ରପ୍ତାନି କରାଯାଏ ନାହିଁ; ଏକତ୍ରିତ ପ୍ରତିକ୍ରିୟା
ପୂର୍ବରୁ `pipeline_provider_response` ଏବଂ `pipeline_client_response`ରେ ରହିଛି।

## 3. REST API

ସମସ୍ତ ରୁଟ୍ ପାଇଁ ପରିଚାଳନା ପ୍ରମାଣୀକରଣ କରାଯାଏ (`requireManagementAuth`)। ଗୁପ୍ତ ତଥ୍ୟ କେବେ ଫେରାଯାଏ ନାହିଁ:
ସଂରକ୍ଷିତ ଗୁପ୍ତ ତଥ୍ୟ ଆକ୍ଷରିକ ମୂଲ୍ୟ `__stored__` ଭାବରେ ଫେରେ, ଏବଂ ଅଦ୍ୟତନ ସମୟରେ ସେହି ମୂଲ୍ୟକୁ ପୁଣି ପଠାଇଲେ
ସଂରକ୍ଷିତ ପ୍ରମାଣପତ୍ର ଅପରିବର୍ତ୍ତିତ ରହେ।

ଯେଉଁ ଗନ୍ତବ୍ୟର ପ୍ରକାର ଏକ ଗୁପ୍ତ ତଥ୍ୟ ଘୋଷଣା କରେ, ତାହା ସୃଷ୍ଟି କିମ୍ବା ଅଦ୍ୟତନ କରିବା ପାଇଁ **`STORAGE_ENCRYPTION_KEY`
ଆବଶ୍ୟକ**। ଏହା ବିନା `encrypt()` ନିରବରେ ତଥ୍ୟକୁ ଅପରିବର୍ତ୍ତିତ ଭାବେ ପାସ୍ କରେ, ତେଣୁ ପ୍ରମାଣପତ୍ରକୁ
SQLite ରେ ସାଧାରଣ ପାଠ୍ୟ ଭାବେ ରଖିବା ପରିବର୍ତ୍ତେ 400 ସହିତ ଲେଖନକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ (Telegram webhook

## 4. BigQuery ଗନ୍ତବ୍ୟ

ବିନ୍ୟାସ କୀଗୁଡ଼ିକ (`type: "bigquery"`):

| କୀ                   | ଟିପ୍ପଣୀ                                                                         |
| -------------------- | ------------------------------------------------------------------------------- |
| `projectId`          | ଡାଟାସେଟ୍ ଥିବା GCP ପ୍ରୋଜେକ୍ଟ                                                     |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                 |
| `tableId`            | `[A-Za-z0-9_]+`                                                                 |
| `location`           | କେବଳ ଡାଟାସେଟ୍ ସୃଷ୍ଟି କରିବାକୁ ପଡ଼ିଲେ ବ୍ୟବହୃତ ହୁଏ (ଡିଫଲ୍ଟ `EU`)                   |
| `serviceAccountJson` | ସେବା-ଆକାଉଣ୍ଟ କୀ। ଗୋପନୀୟ: ସଂରକ୍ଷିତ ଅବସ୍ଥାରେ ଏନକ୍ରିପ୍ଟ କରାଯାଏ, କେବେ ଫେରାଯାଏ ନାହିଁ |
| `autoCreate`         | ପ୍ରଥମ ରପ୍ତାନି ସମୟରେ ଡାଟାସେଟ୍ ଓ ଟେବୁଲ୍ ସୃଷ୍ଟି କରନ୍ତୁ (ଡିଫଲ୍ଟ `true`)             |

ସେବା ଆକାଉଣ୍ଟ ପାଇଁ ଲକ୍ଷ୍ୟ ଟେବୁଲ୍‌ରେ `bigquery.tables.updateData` ଅନୁମତି ଆବଶ୍ୟକ, ଏବଂ
`autoCreate` ସକ୍ରିୟ ଥିଲେ `bigquery.datasets.create` / `bigquery.tables.create` ମଧ୍ୟ ଆବଶ୍ୟକ।

ଏକ ବିନ୍ୟାସିତ ବ୍ୟାଚ୍ ହେଉଛି ଏକ **କର୍ସର୍** ଏକକ, HTTP ଏକକ ନୁହେଁ: `send()` ଏହାକୁ ସର୍ବାଧିକ 500 ଧାଡ଼ି ବିଶିଷ୍ଟ insertAll
କଲ୍‌ରେ ଭାଗ କରେ, ତେଣୁ ବଡ଼ `batch_size` ଯୋଗୁଁ BigQueryର 10 MB ଅନୁରୋଧ ସୀମା ଅତିକ୍ରମ ହୁଏ ନାହିଁ।
ସାମୟିକ ସ୍ଥିତିଗୁଡ଼ିକ (408/429/500/502/503/504) ପାଇଁ ସମାନ insertIds ପୁନଃବ୍ୟବହାର କରି, ଘାତାଙ୍କୀୟ ଭାବେ
ବଢ଼ୁଥିବା ବିରତି ସହ ସର୍ବାଧିକ ତିନିଥର ପୁନଃଚେଷ୍ଟା କରାଯାଏ; ପ୍ରମାଣୀକରଣ ଓ ସ୍କିମା ବିଫଳତା କ୍ଷେତ୍ରରେ ରନ୍‌କୁ
ଅଯଥା ଚାଲୁ ରଖିବା ପରିବର୍ତ୍ତେ ପ୍ରଥମ ପ୍ରୟାସରେ ହିଁ ତ୍ରୁଟି ଉତ୍ପନ୍ନ କରାଯାଏ।

v4 ଇନଜେସନ୍ ସମେତ କେତେକ ବ୍ୟାକଏଣ୍ଡ ସମାନ-ID ସ୍ପାନ୍‌ର ନକଲ ଅପସାରଣ କରନ୍ତି ନାହିଁ। କ୍ରାଶ୍ କିମ୍ବା ଆଂଶିକ ଖଣ୍ଡ ବିଫଳତା
ସର୍ବାଧିକ ସେହି ଗୋଟିଏ ଅସ୍ୱୀକୃତ କର୍ସର୍ ବ୍ୟାଚ୍ ପୁନଃପଠାଇପାରେ; କେବଳ ଏହାର ଶେଷ HTTP ଖଣ୍ଡ ନୁହେଁ,
ସମ୍ପୂର୍ଣ୍ଣ ବ୍ୟାଚ୍‌ର ନକଲ ସୃଷ୍ଟି ହୋଇପାରେ। ଏହି ଲାଭ-କ୍ଷତିକୁ ଧ୍ୟାନରେ ରଖି କର୍ସର୍ ବ୍ୟାଚ୍ ଆକାର ବାଛନ୍ତୁ।

### Langfuse ଉଦାହରଣ

ଏକ ସ୍ୱ-ହୋଷ୍ଟେଡ୍ Langfuse ଇନଷ୍ଟାନ୍ସ ପାଇଁ ଏହି ଫିଲ୍ଡଗୁଡ଼ିକ ବିନ୍ୟାସ କରନ୍ତୁ:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

ଆକ୍ଷରିକ `public-key:secret-key`
ଷ୍ଟ୍ରିଙ୍ଗ୍‌ର Base64 ଭାବେ ସ୍ଥାନୀୟ ଭାବରେ Authorization ମୂଲ୍ୟ ତିଆରି କରନ୍ତୁ (ଉଦାହରଣ ସ୍ୱରୂପ `Buffer.from(publicKey + ":" + secretKey).toString("base64")` ସହିତ)।
ପ୍ରକୃତ ପ୍ରମାଣପତ୍ର ଲଗ୍, ସ୍କ୍ରିନଶଟ୍ କିମ୍ବା ଇସ୍ୟୁରେ ପେଷ୍ଟ କରନ୍ତୁ ନାହିଁ। ମ୍ୟାପିଂ ସ୍ୱୟଂଚାଳିତ ଭାବେ
`x-langfuse-ingestion-version: 4` ସେଟ୍ କରେ; Authorization ତଥାପି `headers` ରେ ପ୍ରଦାନ କରାଯାଏ।
ଉଭୟ ହେଡର୍ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା ପରିଚୟ ସଲ୍ଟ ବିଦ୍ୟମାନ ଏନକ୍ରିପ୍ଟ ହୋଇଥିବା ଗୁପ୍ତ-ଫିଲ୍ଡ
ବ୍ୟବସ୍ଥା ଏବଂ API ପ୍ଲେସହୋଲ୍ଡର୍ ବ୍ୟବହାର କରନ୍ତି; `STORAGE_ENCRYPTION_KEY` ଆବଶ୍ୟକ।

ମ୍ୟାପିଂ ଜେନେରେସନ୍ ପ୍ରକାର/ମଡେଲ୍, JSON ବ୍ୟବହାର ବିବରଣୀ (ଇନପୁଟ୍/ଆଉଟପୁଟ୍/ମୋଟ ଏବଂ ଉପଲବ୍ଧ
କ୍ୟାଶ୍ କିଗୁଡ଼ିକ), JSON ଇନପୁଟ୍/ଆଉଟପୁଟ୍ ସ୍ନାପଶଟ୍, ERROR/DEFAULT ସ୍ତର, ସମ୍ବେଦନଶୀଳ ତଥ୍ୟ ଅପସାରିତ ସ୍ଥିତି ସନ୍ଦେଶ,
ଟ୍ରେସ୍ ନାମ, ସେସନ୍ ଆଇଡି, ଇଚ୍ଛାଧୀନ ପରିବେଶ ଏବଂ ପ୍ରଦାନକାରୀ, ଅନୁରୋଧ କରାଯାଇଥିବା ମଡେଲ୍, ପାଥ୍, କମ୍ବୋ, କ୍ୟାଶ୍
ଉତ୍ସ ଓ ସ୍ଥିତି ପାଇଁ ଫିଲ୍ଟର୍ କରିହେଉଥିବା
`langfuse.observation.metadata.<key>` ଯୋଡ଼େ। `langfuse.observation.completion_start_time` କେବଳ TTFT ଜଣାଥିଲେ ଏବଂ ଅବଧି ମଧ୍ୟରେ ଥିଲେ
ଆରମ୍ଭ ସମୟ + TTFT ଭାବରେ ISO 8601 ରେ ରହେ। କୌଣସି ଖର୍ଚ୍ଚ ଆଟ୍ରିବ୍ୟୁଟ୍ ପଠାଯାଏ ନାହିଁ।

ପରିଚୟ ମୋଡ୍‌ଗୁଡ଼ିକ `langfuse.user.id` ପାଇଁ ପ୍ରଯୁଜ୍ୟ:

- `pseudonymous` (ଡିଫଲ୍ଟ): ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ ପାଇଁ ଏକ ଯାଦୃଚ୍ଛିକ
  32-ବାଇଟ୍ ସଲ୍ଟ ସହିତ API କିର ଆଭ୍ୟନ୍ତରୀଣ ଆଇଡିର HMAC-SHA256। ସଲ୍ଟ ଅନୁପସ୍ଥିତ ଥିଲେ ସୃଷ୍ଟି ସମୟରେ ତିଆରି ହୁଏ, `identitySalt` ଭାବରେ ଏନକ୍ରିପ୍ଟ କରାଯାଏ,
  କେବେବି ଫେରସ୍ତ ଦିଆଯାଏ ନାହିଁ, ଏବଂ ସମ୍ପାଦନା ସମୟରେ ରଖାଯାଏ। ମୂଳ କି ଆଇଡିଗୁଡ଼ିକ କେବେବି
  ସ୍ପାନ୍ ଆଟ୍ରିବ୍ୟୁଟ୍‌ରେ ରଖାଯାଏ ନାହିଁ। କୌଣସି ଗନ୍ତବ୍ୟର ସଲ୍ଟ ପୁନଃସୃଷ୍ଟି/ପରିବର୍ତ୍ତନ କଲେ ପରିଚୟଗୁଡ଼ିକ ବଦଳିଯାଏ।
- `keyName`: ବିନ୍ୟାସିତ API କି ନାମ, ଯାହା ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ ସେହି ଅପରେଟର୍ ଲେବେଲ୍ ପ୍ରକାଶ କରେ।
- `none`: କୌଣସି ବ୍ୟବହାରକାରୀ ଆଇଡି ନାହିଁ। ସେସନ୍ ଟ୍ୟାଗ୍ ଥିଲେ ସେଗୁଡ଼ିକ ତଥାପି ରପ୍ତାନି ହୁଏ; ଏହି ମୋଡ୍‌ଗୁଡ଼ିକ
  ଯେକୌଣସି ପ୍ରମ୍ପ୍ଟ ବିଷୟବସ୍ତୁ କିମ୍ବା ଅପରେଟର୍‌ଙ୍କ ଦ୍ୱାରା ପ୍ରଦତ୍ତ ସେସନ୍/ସହସମ୍ପର୍କ ଲେବେଲ୍‌କୁ ଅଜ୍ଞାତ କରନ୍ତି ନାହିଁ।

### ବ୍ୟାକଫିଲ୍ ବିନା ଆରମ୍ଭ କରିବା

କେବଳ ସୃଷ୍ଟି ସମୟରେ, **ବର୍ତ୍ତମାନ ସ୍ଥାନରୁ ଆରମ୍ଭ କରନ୍ତୁ (ବିଦ୍ୟମାନ ଲଗ୍‌ଗୁଡ଼ିକୁ ଛାଡ଼ନ୍ତୁ)** ସକ୍ଷମ କରନ୍ତୁ କିମ୍ବା
ସୃଷ୍ଟି API ପେଲୋଡ୍‌ର ଶୀର୍ଷ ସ୍ତରରେ `startFromCurrentPosition: true` ପଠାନ୍ତୁ। ଏହା ବିଦ୍ୟମାନ କର୍ସର୍
ସହାୟକଗୁଡ଼ିକ ବ୍ୟବହାର କରି, କୌଣସି ମାଇଗ୍ରେସନ୍ ବିନା, `cursor_row_id` କୁ ବର୍ତ୍ତମାନ ସଂରକ୍ଷିତ କଲ୍-ଲଗ୍‌ର ସର୍ବାଧିକ rowid ରେ
ପ୍ରାରମ୍ଭ କରେ। ଡିଫଲ୍ଟ ହେଉଛି false (କର୍ସର୍ 0 ଏବଂ ସଂରକ୍ଷିତ ଇତିହାସର ବ୍ୟାକଫିଲ୍)।
ଏହା ଅଦ୍ୟତନ ସମୟରେ କର୍ସର୍ ପୁନଃସେଟ୍ କରିବାର ସେଟିଂ ନୁହେଁ।

ସାଧାରଣ `ttftMs` ସଂଯୋଜନ BigQuery ମ୍ୟାପର୍
ଏବଂ ନୂତନ-ଟେବୁଲ୍ ସ୍କିମାରେ ଏକ ନଲ୍ ମୂଲ୍ୟ ଗ୍ରହଣ କରିପାରୁଥିବା `ttft_ms` ସ୍ତମ୍ଭ ମଧ୍ୟ ଯୋଡ଼େ: ଏହାର ସ୍କିମା ପରୀକ୍ଷଣରେ ପ୍ରତ୍ୟେକ କାନୋନିକାଲ୍ ରେକର୍ଡ ଫିଲ୍ଡ ପାଇଁ ଏକ
ସ୍ତମ୍ଭ ରହିବା ଆବଶ୍ୟକ। ବିଦ୍ୟମାନ ଟେବୁଲ୍‌ଗୁଡ଼ିକ ଅପରିବର୍ତ୍ତିତ ଭାବରେ ରପ୍ତାନି ଜାରି ରଖନ୍ତି: `prepare()` ଟେବୁଲ୍ ସ୍କିମା ପଢ଼େ ଏବଂ
ସେହି ସ୍ତମ୍ଭ ଅନୁପସ୍ଥିତ ଥିଲେ କେବଳ `ttft_ms` କୁ ବାଦ୍ ଦିଏ। ପରବର୍ତ୍ତୀ ରନ୍‌ରେ TTFT ପାଇବାକୁ
ନଲ୍ ମୂଲ୍ୟ ଗ୍ରହଣ କରିପାରୁଥିବା INT64 ସ୍ତମ୍ଭ ଯୋଡ଼ନ୍ତୁ, କିମ୍ବା ଏକ ନୂତନ ଟେବୁଲ୍ ବ୍ୟବହାର କରନ୍ତୁ। କୌଣସି PATCH, ସ୍ୱୟଂଚାଳିତ ସ୍କିମା ପରିବର୍ତ୍ତନ କିମ୍ବା ଅତିରିକ୍ତ
ଅନୁମତି ଆବଶ୍ୟକ ନାହିଁ; ଅନ୍ୟ ସମସ୍ତ ଧାଡ଼ି ଫିଲ୍ଡ ପାଇଁ କଠୋର ସ୍କିମା ଯାଞ୍ଚ ବଜାୟ ରହେ।

  ଏବଂ କର୍ସର ସ୍ଥାୟୀ ଭାବେ ସେଗୁଡ଼ିକୁ ଅତିକ୍ରମ କରି ଆଗକୁ ବଢ଼େ।

  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) ମାଧ୍ୟମରେ ଏହାକୁ ଯାଞ୍ଚ କରିବା ଆବଶ୍ୟକ,

## 7. ଏହାକୁ ପରିଚାଳନା କରିବା

- **ଡ୍ୟାଶବୋର୍ଡ**: ଏକୀକରଣ → ଲଗ୍ ଏକ୍ସପୋର୍ଟ। ଏକ ଗନ୍ତବ୍ୟ ଯୋଡ଼ନ୍ତୁ, ଧାଡ଼ି ନ ଲେଖି ପ୍ରମାଣପତ୍ର ଯାଞ୍ଚ କରିବାକୁ **ପରୀକ୍ଷା** ଚଲାନ୍ତୁ,
  ତା’ପରେ ଏହାକୁ ସକ୍ରିୟ କରନ୍ତୁ।
- **ବକେୟା କାର୍ଯ୍ୟ**: ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟ କାର୍ଡରେ ବିଚାରାଧୀନ ଧାଡ଼ି ଏବଂ କର୍ସର ଦେଖାଯାଏ; `GET
/api/log-export/status` ସେହି ସମାନ ସଂଖ୍ୟା ସହିତ ଶେଷ 20ଟି ଜବ୍ ରନ୍ ଫେରାଏ।
- **ଗୋଟିଏ ଗନ୍ତବ୍ୟର ବିଫଳତା ଅନ୍ୟଗୁଡ଼ିକୁ ବିଫଳ କରେ ନାହିଁ** — ରନ୍ ସାରାଂଶ ପ୍ରତ୍ୟେକ ଗନ୍ତବ୍ୟର
  ସ୍ଥିତିକୁ `last_status` / `last_error` ରେ ରେକର୍ଡ କରେ, ଏବଂ ଜବ୍ ରନ୍ ଇତିହାସ ସାମଗ୍ରିକ ତଥ୍ୟ ରଖେ।
- **ଏକ ଗନ୍ତବ୍ୟ ବିଲୋପ କଲେ ଏହାର କର୍ସର ମଧ୍ୟ ବିଲୋପ ହୁଏ।** ଏହାକୁ ପୁଣି ଯୋଡ଼ିଲେ ସଂରକ୍ଷିତ ସବୁଠାରୁ ପୁରୁଣା
  କଲ୍ ଲଗ୍‌ରୁ ଆରମ୍ଭ ହୁଏ, ଯାହା ଗନ୍ତବ୍ୟରେ ପୂର୍ବରୁ ଥାଇପାରୁଥିବା ଧାଡ଼ିଗୁଡ଼ିକୁ ପୁଣି ପଠାଏ। BigQuery ରେ ପ୍ରତ୍ୟେକ ଧାଡ଼ିର
  `insertId` କେବଳ BigQuery ର ନିଜସ୍ୱ ଡୁପ୍ଲିକେଟ୍ ଅପସାରଣ ସମୟସୀମା ମଧ୍ୟରେ ଏହି ପୁନରାବୃତ୍ତିକୁ ସମ୍ଭାଳେ, ତେଣୁ
  ଗନ୍ତବ୍ୟକୁ ବିଲୋପ କରିବା ପରିବର୍ତ୍ତେ ନିଷ୍କ୍ରିୟ କରିବାକୁ ପସନ୍ଦ କରନ୍ତୁ।
