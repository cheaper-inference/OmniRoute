ଏକ pull request ପାଇଁ ସବୁଠାରୁ ଛୋଟ ବିଶ୍ୱସନୀୟ development loop ବାଛିବାକୁ ଏହି ମାର୍ଗଦର୍ଶିକା ବ୍ୟବହାର କରନ୍ତୁ। ଏହା ନିମ୍ନରେ ଲିଙ୍କ୍ କରାଯାଇଥିବା କ୍ଷେତ୍ର-ନିର୍ଦ୍ଦିଷ୍ଟ architecture ଏବଂ security ଦଲିଲଗୁଡ଼ିକୁ
ବଦଳାଏ ନାହିଁ; ଏହା ପ୍ରତ୍ୟେକ ସାଧାରଣ change typeକୁ ତାହାର contracts, focused checks, ଏବଂ CI coverage ସହିତ ସଂଯୋଗ କରେ।

## ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ଅନୁସରଣ କରୁଥିବା ପଥ

1. **ସମ୍ପାଦନା ପୂର୍ବରୁ base ବାଛନ୍ତୁ।** ସର୍ବୋଚ୍ଚ ସକ୍ରିୟ `release/v*` branch ଖୋଜନ୍ତୁ ଏବଂ
   ତାହାର tipରୁ branch ସୃଷ୍ଟି କରନ୍ତୁ। `main`କୁ ନୁହେଁ, ସେହି branchକୁ target କରନ୍ତୁ। ଯଦି ଏକ release freeze ସକ୍ରିୟ ଅଛି, frozen
   branchକୁ target କରନ୍ତୁ ନାହିଁ; [Branching & Release Model](BRANCHING_MODEL.md)ରେ
   ବର୍ଣ୍ଣିତ ପରବର୍ତ୍ତୀ ସକ୍ରିୟ cycle ବ୍ୟବହାର କରନ୍ତୁ।
2. **Contractsଗୁଡ଼ିକର ନାମ ଦିଅନ୍ତୁ।** ପରିବର୍ତ୍ତନଟି ପ୍ରଭାବିତ କରୁଥିବା ପ୍ରତ୍ୟେକ catalog, schema, generated artifact, public API, କିମ୍ବା user
   interface ଚିହ୍ନଟ କରନ୍ତୁ। ନିମ୍ନର table ସର୍ବନିମ୍ନ ପ୍ରାରମ୍ଭିକ set ପ୍ରଦାନ କରେ।
3. **Focused tests ଲେଖନ୍ତୁ କିମ୍ବା update କରନ୍ତୁ।** `src/`, `open-sse/`, `electron/`, କିମ୍ବା
   `bin/`ର production ପରିବର୍ତ୍ତନ ପାଇଁ ସେହି PRରେ ଏକ automated test ଆବଶ୍ୟକ। ଆଚରଣକୁ ପ୍ରମାଣିତ କରୁଥିବା ସବୁଠାରୁ ଛୋଟ test files ଚଲାନ୍ତୁ,
   ତା'ପରେ ତାଲିକାଭୁକ୍ତ focused gates ଚଲାନ୍ତୁ।
4. **CIକୁ ବ୍ୟାପକ matrix ଚଲାଇବାକୁ ଦିଅନ୍ତୁ।** ସମ୍ପୂର୍ଣ୍ଣ unit shards, Vitest, coverage ratchet, ଏବଂ
   production build PRରେ ଚାଲେ। କେବଳ ଯେତେବେଳେ focused failure ଅଧିକ ବ୍ୟାପକ ପ୍ରଭାବ ସୂଚାଏ
   କିମ୍ବା ପରିବର୍ତ୍ତନଟି ଅନେକ subsystemsକୁ ବ୍ୟାପେ, ସେତେବେଳେ ସ୍ଥାନୀୟ ଭାବେ ଏକ broad suite ଚଲାନ୍ତୁ।
5. **Review ପୂର୍ବରୁ ସମନ୍ୱୟ କରନ୍ତୁ।** ସକ୍ରିୟ base fetch କରନ୍ତୁ, ତାହାର ନୂତନ commits ଏବଂ ତାହା ବିପକ୍ଷରେ ଆପଣଙ୍କ diff ଯାଞ୍ଚ କରନ୍ତୁ,
   ତା'ପରେ contributor workflow ଅନୁଯାୟୀ baseକୁ rebase କିମ୍ବା merge କରନ୍ତୁ। Generated-file
   ଏବଂ catalog conflictsକୁ ସେମାନଙ୍କ sourceରୁ ସମାଧାନ କରନ୍ତୁ, ସେଗୁଡ଼ିକୁ ପୁନଃ generate କରନ୍ତୁ, focused loop ପୁନର୍ବାର ଚଲାନ୍ତୁ, ଏବଂ
   PRଟି ଏପର୍ଯ୍ୟନ୍ତ ସକ୍ରିୟ release branchକୁ target କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।
6. **ପ୍ରମାଣ ଲିପିବଦ୍ଧ କରନ୍ତୁ।** PR templateରେ ଚଲାଯାଇଥିବା commands, ଯୋଡ଼ାଯାଇଥିବା କିମ୍ବା ପରିବର୍ତ୍ତିତ ପ୍ରତ୍ୟେକ test file,
   migrations କିମ୍ବା feature flags, ଏବଂ ଏପର୍ଯ୍ୟନ୍ତ pending ଥିବା ଯେକୌଣସି CI-only validation ତାଲିକାଭୁକ୍ତ କରନ୍ତୁ।

## Change type ଅନୁଯାୟୀ Golden paths

ନିମ୍ନର commandsଗୁଡ଼ିକ ସର୍ବନିମ୍ନ focused checks ଅଟେ, ଆପଣ ପରିବର୍ତ୍ତନ କରିଥିବା ଆଚରଣକୁ ସିଧାସଳଖ cover କରୁଥିବା
testକୁ ଛାଡ଼ିଦେବା ପାଇଁ ଅନୁମତି ନୁହେଁ।

### Provider

**Contracts**

- `src/shared/constants/providers/`ରେ Provider definition ଏବଂ
  `src/shared/constants/providers.ts`ରେ ତାହାର composition।
- `open-sse/config/providerRegistry.ts` କିମ୍ବା ଏଥିରୁ extract କରାଯାଇଥିବା registry filesରେ models ଏବଂ capabilities।
- ପ୍ରଯୋଜ୍ୟ ହେଲେ Executor/translator selection, OAuth କିମ୍ବା API-key configuration, dashboard assets, ଏବଂ generated
  provider reference।
- Public credentials ନିଶ୍ଚିତ ଭାବେ `resolvePublicCred()` ବ୍ୟବହାର କରିବା ଉଚିତ; error responses ନିଶ୍ଚିତ ଭାବେ shared sanitized
  error helpers ବ୍ୟବହାର କରିବା ଉଚିତ। `docs/security/PUBLIC_CREDS.md` (git; `/docs`ରେ compile କରାଯାଇନାହିଁ) ଏବଂ
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ଦେଖନ୍ତୁ।

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ପରିବର୍ତ୍ତନ ହେଲେ; generated diffକୁ commit କରନ୍ତୁ
npm run lint
```

ପ୍ରଭାବିତ ପ୍ରତ୍ୟେକ request familyକୁ ମଧ୍ୟ test କରନ୍ତୁ: chat, Responses, images, embeddings, audio, କିମ୍ବା video।
Generated catalog ଏବଂ golden diffsକୁ contract changes ଭାବରେ review କରନ୍ତୁ; ସେଗୁଡ଼ିକୁ ଅନ୍ଧ ଭାବରେ ଗ୍ରହଣ କରନ୍ତୁ ନାହିଁ।

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts`ରେ Public strategy values ଏବଂ UI metadata।
- `open-sse/services/combo.ts` ଏବଂ `open-sse/services/combo/` ଅଧୀନରେ dispatch ଏବଂ ordering।
- Combo schemas, persistence, resilience state, model capabilities, ଏବଂ API/UI controls।
- ଆଚରଣ ପରିବର୍ତ୍ତନ ହେଲେ [Auto-Combo Engine](../routing/AUTO-COMBO.md) ଏବଂ resilience documentation।

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy କିମ୍ବା dispatch ପରିବର୍ତ୍ତନ
npm run check:known-symbols      # strategy registration ପରିବର୍ତ୍ତନ
npm run lint
```

ସ୍ଥାନୀୟ ଭାବେ deterministic mocked-upstream tests ବ୍ୟବହାର କରନ୍ତୁ। Live combo smokes ପାଇଁ credentials ଆବଶ୍ୟକ ଏବଂ ସେଗୁଡ଼ିକ
manual, CIର ବିକଳ୍ପ ନୁହେଁ।

### UI / UX

**Contracts**

- `src/app/` ଏବଂ `src/shared/components/` ଅଧୀନରେ Next.js route/page ଏବଂ shared component boundaries।
- API response shapes, loading/empty/error states, keyboard ଏବଂ screen-reader ଆଚରଣ,
  responsive layout, theming, ଏବଂ locale expansion।
- `src/i18n/messages/en.json`ରେ English UI source strings; ନୂତନ user-facing copyକୁ hard-code କରନ୍ତୁ ନାହିଁ।

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction କିମ୍ବା visual ପରିବର୍ତ୍ତନ ପାଇଁ app ଚଲାନ୍ତୁ ଏବଂ ଉଭୟ narrow ଓ wide viewports ଯାଞ୍ଚ କରନ୍ତୁ। CI
production build ଏବଂ broader suites ଚଲାଏ; visual ଆଚରଣ ପାଇଁ ତଥାପି ପରିବର୍ତ୍ତନ ଅନୁଯାୟୀ ଏକ focused component, Playwright,
କିମ୍ବା ଲିପିବଦ୍ଧ manual check ଆବଶ୍ୟକ।

### i18n

**Contracts**

- `src/i18n/messages/en.json` ହେଉଛି UI source; `config/i18n.json` ହେଉଛି locale source।
- CLI catalogs ପୃଥକ ଭାବରେ `bin/cli/locales/` ଅଧୀନରେ ରହେ।
- ICU placeholders ଏବଂ tagsକୁ ଅବିକଳ ସଂରକ୍ଷଣ କରନ୍ତୁ। Product/provider/model names,
  protocol ଏବଂ header names, commands, code/JSON identifiers, URLs, environment variables, କିମ୍ବା
  `OmniRoute`, `OAuth`, `MCP`, ଏବଂ `A2A` ପରି protected termsକୁ ଅନୁବାଦ କରନ୍ତୁ ନାହିଁ। ବର୍ତ୍ତମାନର source list ହେଉଛି
  `scripts/i18n/glossary/protected-terms.json`।

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs ପରିବର୍ତ୍ତନ ହେଲେ
npm run lint
```

ଏହା ବିଦ୍ୟମାନ system ପାଇଁ ମାର୍ଗଦର୍ଶନ, ତାହାର tooling କିମ୍ବା key model ବିସ୍ତାର କରିବା ପାଇଁ ଆମନ୍ତ୍ରଣ ନୁହେଁ।
Replacement systemର design ଚାଲିଥିବା ସମୟରେ i18n patchesକୁ ଅତ୍ୟନ୍ତ ସୀମିତ ରଖନ୍ତୁ। Taskଟି ସ୍ପଷ୍ଟ ଭାବରେ generated translations ଆବଶ୍ୟକ ନକରିଲେ ଏବଂ
ଆପଣ resulting diffକୁ review କରିନଥିଲେ, external servicesକୁ call କରୁଥିବା translation
commands ଚଲାନ୍ତୁ ନାହିଁ।

### CLI

**Contracts**

- `bin/cli/` ଭିତରେ ଥିବା ସାର୍ବଜନୀନ କମାଣ୍ଡ ଏବଂ ଫ୍ଲାଗ୍, ଉତ୍ପାଦିତ API କମାଣ୍ଡ, exit code, stdout/stderr ଏବଂ
  JSON ଆଉଟପୁଟ୍ ଆକୃତି, config/environment ଆଚରଣ, ଏବଂ ପ୍ୟାକେଜ୍ ହୋଇଥିବା ଫାଇଲ୍ଗୁଡ଼ିକ।
- CLI ବ୍ୟବହାରକାରୀଙ୍କୁ ଦୃଶ୍ୟମାନ ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକ ନିଶ୍ଚିତ ଭାବେ CLI i18n ସ୍ତର ବ୍ୟବହାର କରିବା ଉଚିତ ଏବଂ `en`/`pt-BR` କ୍ୟାଟାଲଗ୍ଗୁଡ଼ିକୁ ସମନ୍ୱିତ ରଖିବା ଉଚିତ।
- ସମର୍ଥିତ runtime ଭାବରେ Node ଏବଂ ପ୍ରକାଶିତ binary contract କୁ ସଂରକ୍ଷିତ ରଖନ୍ତୁ।

**କେନ୍ଦ୍ରିତ ଲୁପ୍**

```bash

npm run check:cli-i18n
npm run build:cli             # ଉତ୍ପାଦିତ/ବଣ୍ଡଲ୍ ହୋଇଥିବା CLI ପରିବର୍ତ୍ତନ
npm run check:pack-policy     # ପ୍ୟାକେଜ୍ର ସାର୍ବଜନୀନ ପୃଷ୍ଠର ପରିବର୍ତ୍ତନ

```

ଯେତେବେଳେ ଆଚରଣ parsing, ଫାଇଲ୍ କିମ୍ବା exit status ଉପରେ ନିର୍ଭର କରେ, ସେତେବେଳେ ଏକ ଅସ୍ଥାୟୀ data directory ମଧ୍ୟରେ ଠିକ୍ ସେହି କମାଣ୍ଡ ବ୍ୟବହାର କରନ୍ତୁ। CI ଅଧିକ ବ୍ୟାପକ package artifact ଏବଂ ecosystem ଯାଞ୍ଚଗୁଡ଼ିକ ସମ୍ପାଦନ କରେ।

### ଡାଟାବେସ୍

**ଚୁକ୍ତିଗୁଡ଼ିକ**

## ସହଭାଗୀ ମେସିନ୍ ପାଇଁ ଡେଭେଲପର୍ ସ୍କ୍ରିପ୍ଟଗୁଡ଼ିକ

ଅନ୍ୟ ସେସନ୍ଗୁଡ଼ିକ ସକ୍ରିୟ ଥିବା ଏକ devbox ଉପରେ ସ୍ଥାନୀୟ ଲୁପ୍କୁ ଦୁଇଟି `scripts/dev/` ସହାୟକ ଏନ୍କୋଡ୍ କରନ୍ତି:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD ରୁ ଫାଇଲ୍ଗୁଡ଼ିକ
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ଠିକ୍ ଏହି ଫାଇଲ୍ଗୁଡ଼ିକ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # ପୃଥକ worktree, ସମାନ୍ତରାଳ ଭାବେ ସୁରକ୍ଷିତ
```

- `typecheck-touched.sh` ଏକ ଅସ୍ଥାୟୀ
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ମାଧ୍ୟମରେ କେବଳ ସ୍ପର୍ଶ କରାଯାଇଥିବା `.ts/.tsx` ଫାଇଲ୍ଗୁଡ଼ିକୁ 6 GB heap ଅଧୀନରେ typecheck କରେ, ତେଣୁ ଏହା ଅଧିକ ଲୋଡ୍ ଥିବା ମେସିନ୍ରେ OOM ହେଉଥିବା ପ୍ରକଳ୍ପ-ବ୍ୟାପୀ `tsc -p tsconfig.json`କୁ ପ୍ରତିସ୍ଥାପନ କରେ।
  ଏହା ସ୍ପର୍ଶ କରାଯାଇଥିବା ଫାଇଲ୍ଗୁଡ଼ିକର ତ୍ରୁଟି ସହିତ ଗୋଟିଏ ସାରାଂଶ ଧାଡ଼ି ପ୍ରିଣ୍ଟ କରେ ଏବଂ ସ୍ପର୍ଶ କରାଯାଇଥିବା ଫାଇଲ୍ଗୁଡ଼ିକରେ ତ୍ରୁଟି ପାଇଁ
  `1`, କେବଳ ଆମଦାନୀ କରାଯାଇଥିବା ଫାଇଲ୍ଗୁଡ଼ିକରେ ତ୍ରୁଟି ଥିଲେ କିମ୍ବା ଡାଇଗ୍ନୋଷ୍ଟିକ୍ ବିନା tsc ବନ୍ଦ ହୋଇଗଲେ
  `2` (ଏହା `_artifacts/typecheck-touched/` ଅଧୀନରେ ଉଲ୍ଲେଖ କରୁଥିବା ଲଗ୍ଟି ପଢ଼ନ୍ତୁ), ଏବଂ ତ୍ରୁଟିମୁକ୍ତ ହେଲେ
  `0` ସହିତ ପ୍ରସ୍ଥାନ କରେ। ଅସ୍ଥାୟୀ tsconfigକୁ ସର୍ବଦା ଅପସାରଣ କରାଯାଏ; କେବେ ମଧ୍ୟ ଏହାକୁ commit କରନ୍ତୁ ନାହିଁ।
- `new-worktree.sh`, `<git-common-dir>/omniroute-new-worktree.lock` ଉପରେ ସମସାମୟିକ ରନ୍ଗୁଡ଼ିକୁ କ୍ରମିକ କରେ
  (ଡିଫଲ୍ଟ ଭାବେ 600 s ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରେ, ଏକ ଦୃଶ୍ୟମାନ ସନ୍ଦେଶ ସହିତ; ସ୍କ୍ରିପ୍ଟ ହେଡର୍ରେ
  ଓଭରରାଇଡ୍ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଛି) ଏବଂ worktreeଟି ଅବସ୍ଥିତ ହେବା ପୂର୍ବରୁ `git worktree add` ବିଫଳ ହେଲେ ଏହା ସୃଷ୍ଟି କରିଥିବା branchକୁ
  ପଛକୁ ଫେରାଏ, ତେଣୁ ପୁନଃଚେଷ୍ଟା ପାଇଁ ହସ୍ତକୃତ `git branch -D` ଆବଶ୍ୟକ ହୁଏ ନାହିଁ। hard-linked `node_modules` ଏବଂ `.husky/_` କପି ଅପରିବର୍ତ୍ତିତ ରହେ।

## ସ୍ଥାନୀୟ candidate ଲୁପ୍

ସୋର୍ସ ପରୀକ୍ଷାଗୁଡ଼ିକ ପ୍ୟାକେଜ୍ ହୋଇଥିବା artifact ଚାଲୁ ହୁଏ ବୋଲି ପ୍ରମାଣ କରିପାରିବ ନାହିଁ: packaging ତାଲିକା, ବାଦ୍ ଦିଆଯାଇଥିବା dependencyଗୁଡ଼ିକ,
ଏବଂ native binaryଗୁଡ଼ିକ କେବଳ tarballଟି ଇନ୍ଷ୍ଟଲ୍ ଏବଂ ଆରମ୍ଭ ହେବା ପରେ ବିଫଳ ହୁଅନ୍ତି। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ହେଉଛି RFC #8084ର build-once / validate / promote ପ୍ରବାହର ସ୍ଥାନୀୟ ପାର୍ଶ୍ୱ: ଏହା ଗୋଟିଏ candidate build କରେ, ସେହି ନିର୍ଦ୍ଦିଷ୍ଟ artifactକୁ validate କରେ, directory
rename ମାଧ୍ୟମରେ ଏହାକୁ promote କରେ, ଏବଂ promoted slot ତାହାର health checkରେ ବିଫଳ ହେଲେ ଏହାକୁ rollback କରେ।

```bash
npm run dev:candidate -- run --dry-run --json  # ଯୋଜନା ପ୍ରିଣ୍ଟ କରନ୍ତୁ, କିଛି ପରିବର୍ତ୍ତନ କରନ୍ତୁ ନାହିଁ
npm run dev:candidate -- run                   # build + validate + promote, ସ୍ୱୟଂଚାଳିତ rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ଭିତରେ ଇନ୍ଷ୍ଟଲ୍ କରନ୍ତୁ
npm run dev:candidate -- validate --id <id>    # ଏକ ଖାଲି portରେ boot କରନ୍ତୁ, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current ଏବଂ previousକୁ ଅଦଳବଦଳ କରନ୍ତୁ
npm run dev:candidate -- run --from-tarball <file.tgz>  # ଅନ୍ୟତ୍ର (CI) build ହୋଇଥିବା tarballକୁ ପୁନଃବ୍ୟବହାର କରନ୍ତୁ
```

- **ଥରେ ମାତ୍ର build କରନ୍ତୁ।** `build` ବର୍ତ୍ତମାନର treeକୁ pack କରେ (ଏଥିପାଇଁ `dist/server.js` ଆବଶ୍ୟକ, ତେଣୁ ପ୍ରଥମେ
  `npm run build:release` ଚଲାନ୍ତୁ) କିମ୍ବା `--from-tarball`କୁ କପି କରେ, ତା’ପରେ tarballଟିକୁ ଏକ
  ପୃଥକ npm prefixରେ ଇନ୍ଷ୍ଟଲ୍ କରେ, କାରଣ tarballରେ `node_modules` ନଥାଏ। id ହେଉଛି ସଂକ୍ଷିପ୍ତ `HEAD`
  sha (treeରେ ସ୍ଥାନୀୟ ପରିବର୍ତ୍ତନ ଥିଲେ `-dirty`) କିମ୍ବା ଏକ tarball ପାଇଁ `tgz-<sha256>`। ପୂର୍ବରୁ build ହୋଇଥିବା ଏକ clean idକୁ ପୁନଃ build କରିବା ପରିବର୍ତ୍ତେ ପୁନଃବ୍ୟବହାର କରାଯାଏ; ଏହାକୁ ପୁନଃ build କରିବା ପାଇଁ `--force` ପାସ୍ କରନ୍ତୁ।
- **ସୋର୍ସକୁ ନୁହେଁ, ପ୍ୟାକେଜ୍କୁ validate କରନ୍ତୁ।** `validate` ଇନ୍ଷ୍ଟଲ୍ ହୋଇଥିବା CLIକୁ
  (`serve --port <free port>`) ଏକ ନୂଆ `DATA_DIR=<candidate>/data`, ନକଲି secretଗୁଡ଼ିକ ସହିତ ଏବଂ operatorଙ୍କ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ଓ `INITIAL_PASSWORD`କୁ
  environmentରୁ ଅପସାରଣ କରି ଆରମ୍ଭ କରେ, ଯାହାଦ୍ୱାରା ଏହା ଏକ ନୂଆ installର keyless loopback postureକୁ ଯାଞ୍ଚ କରେ। ଏହା
  `GET /api/health`ର 200 ଫେରାଇବା ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରେ, `GET /v1/models`ର 200 ଫେରାଇବା ଆବଶ୍ୟକ କରେ, process groupକୁ ବନ୍ଦ କରେ,
  ଏବଂ tarball hash ସହିତ `validation.json`ରେ verdict ରେକର୍ଡ କରେ।
- **ସେହି ଏକା artifactକୁ promote କରନ୍ତୁ।** `promote` ତାହାର
  ବର୍ତ୍ତମାନର tarball hash ପାଇଁ ଏକ ସଫଳ validation ନଥିବା candidateକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଡିଫଲ୍ଟ active slot ହେଉଛି `_artifacts/candidate/current`; `--target <dir>`
  ସେହି filesystem ଉପରେ ଅନ୍ୟ directory ଚୟନ କରେ, ଏବଂ ତାହାର previous slot ହେଉଛି `<dir>.previous`।
  ପ୍ରତ୍ୟେକ rename atomic ଅଟେ, ଏବଂ ମଝିରେ ବିଫଳତା ହେଲେ ପୂର୍ବରୁ ଚାଲିଥିବା renameଗୁଡ଼ିକୁ ଓଲଟାଇ ଦିଏ।
- **Rollback କରନ୍ତୁ।** `run` promoted slotକୁ ପୁଣି validate କରେ ଏବଂ ସେହି ଯାଞ୍ଚ ବିଫଳ ହେଲେ
  `current` ଏବଂ `previous`କୁ ପୁନଃ ଅଦଳବଦଳ କରେ। ପ୍ରଥମ validationରେ ବିଫଳ ହେଉଥିବା candidateକୁ କେବେ ମଧ୍ୟ promote କରାଯାଏ ନାହିଁ।

ସବୁକିଛି gitignored `_artifacts/candidate/` ଅଧୀନରେ ଲେଖାଯାଏ; ଏକ ବିଦ୍ୟମାନ OmniRoute
installation ଏବଂ ତାହାର data directoryକୁ କେବେ ମଧ୍ୟ ସ୍ପର୍ଶ କରାଯାଏ ନାହିଁ। promoted CLI ହେଉଛି
`_artifacts/candidate/current/prefix/bin/omniroute`; ଏହାକୁ ବ୍ୟବହାର କରିବାବେଳେ ନିଜ `DATA_DIR` ସହିତ ଆରମ୍ଭ କରନ୍ତୁ।
Exit codeଗୁଡ଼ିକ: ସଫଳତା ପାଇଁ `0`, ବିଫଳ validation କିମ୍ବା promotion ପାଇଁ `1`, usage error କିମ୍ବା build ନଥିଲେ `2`।

| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| ଉପରୋକ୍ତ ପ୍ରତ୍ୟକ୍ଷ ଆଚରଣ ପରୀକ୍ଷା ଏବଂ ବର୍ଗ ଗେଟ୍ଗୁଡ଼ିକ                            | ଖଣ୍ଡିତ ସମ୍ପୂର୍ଣ୍ଣ ୟୁନିଟ୍ ସୁଇଟ୍ ଏବଂ କ୍ରମିକ ପରୀକ୍ଷାଗୁଡ଼ିକ                       |

| ପ୍ରଭାବିତ କଣ୍ଟ୍ରାକ୍ଟ ଆବଶ୍ୟକ କଲେ ମାତ୍ର ଟାଇପ୍ ଯାଞ୍ଚ କିମ୍ବା ବିଲ୍ଡ୍                | ପ୍ରଡକ୍ସନ୍ ବିଲ୍ଡ୍, ସୁରକ୍ଷା, ଡକ୍ୟୁମେଣ୍ଟେସନ୍, ନିର୍ଭରଶୀଳତା ଏବଂ PR-ନୀତି ଗେଟ୍ଗୁଡ଼ିକ |

ଏକ ସଫଳ କେନ୍ଦ୍ରିତ ଲୁପ୍ ପରିବର୍ତ୍ତିତ କଣ୍ଟ୍ରାକ୍ଟ ବିଷୟରେ ପ୍ରମାଣ ଅଟେ, ଅସମ୍ପର୍କିତ CI ଯାଞ୍ଚଗୁଡ଼ିକ
ସଫଳ ହେବାର ପ୍ରମାଣ ନୁହେଁ। ଅନ୍ୟପକ୍ଷରେ, ପ୍ରତ୍ୟେକ ସ୍ଥାନୀୟ ସମ୍ପାଦନାକୁ ସମ୍ପୂର୍ଣ୍ଣ ରିପୋଜିଟୋରି ମ୍ୟାଟ୍ରିକ୍ସ ପାଇଁ ଅପେକ୍ଷା କରାନ୍ତୁ ନାହିଁ।

## ସମନ୍ୱୟ ଯାଞ୍ଚତାଲିକା

ସମୀକ୍ଷା ଅନୁରୋଧ କରିବା ପୂର୍ବରୁ:

- PR ବେସ୍ ଏବେ ମଧ୍ୟ ସର୍ବୋଚ୍ଚ ସକ୍ରିୟ `release/v*` ବ୍ରାଞ୍ଚ୍ ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।
- ସେହି ବେସ୍କୁ ଫେଚ୍ କରନ୍ତୁ ଏବଂ ଆପଣ ବ୍ରାଞ୍ଚ୍ ସୃଷ୍ଟି କରିବା ପରଠାରୁ ଯୋଡ଼ାଯାଇଥିବା କମିଟ୍ଗୁଡ଼ିକୁ ସମୀକ୍ଷା କରନ୍ତୁ।
- ଅନିଚ୍ଛାକୃତ କିମ୍ବା ସୃଷ୍ଟି ହୋଇଥିବା ଅପ୍ରୟୋଜନୀୟ ପରିବର୍ତ୍ତନ ପାଇଁ `git diff <active-base>...HEAD` ସମୀକ୍ଷା କରନ୍ତୁ।
- ଉତ୍ସକୁ ଅପଡେଟ୍ କରି ଏବଂ ଆଉଟପୁଟ୍କୁ ପୁନଃ ସୃଷ୍ଟି କରି କ୍ୟାଟାଲଗ୍ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା ଡକ୍ୟୁମେଣ୍ଟ୍ର ଦ୍ୱନ୍ଦ୍ୱ ସମାଧାନ କରନ୍ତୁ।
- ସମନ୍ୱୟ ପରେ PR ବର୍ଣ୍ଣନାରେ ତାଲିକାଭୁକ୍ତ ପ୍ରତ୍ୟେକ କେନ୍ଦ୍ରିତ ପରୀକ୍ଷା/ଗେଟ୍କୁ ପୁଣି ଚଲାନ୍ତୁ।
- ସ୍ଥାନାନ୍ତରିତ ବେସ୍ ସହ ମେଳ କରିବା ପାଇଁ କେବଳ ଆସର୍ସନ୍ଗୁଡ଼ିକୁ କେବେବି ଦୁର୍ବଳ କରନ୍ତୁ ନାହିଁ କିମ୍ବା ଆବଶ୍ୟକ ପରୀକ୍ଷାଗୁଡ଼ିକୁ ବାଦ ଦିଅନ୍ତୁ ନାହିଁ।
