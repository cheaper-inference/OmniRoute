## SQLite କାହିଁକି?

OmniRoute ବିଭିନ୍ନ କାରଣରୁ PostgreSQL/MySQL ପରିବର୍ତ୍ତେ SQLite ବାଛିଛି:

| ବିଷୟ                | SQLite                                | PostgreSQL                              |
| ------------------- | ------------------------------------- | --------------------------------------- |
| **ନିୟୋଜନ**          | ଏମ୍ବେଡେଡ୍ — ପୃଥକ ସର୍ଭର୍ ଆବଶ୍ୟକ ନୁହେଁ  | ସର୍ଭର୍ ସେଟଅପ୍ ଆବଶ୍ୟକ                    |
| **ଏନ୍କ୍ରିପ୍ସନ୍**    | ଆପ୍ଲିକେସନ୍ ସ୍ତରୀୟ (AES-256-GCM)       | ଅନ୍ତର୍ନିର୍ମିତ TDE                       |
| **କାର୍ଯ୍ୟଦକ୍ଷତା**   | କ୍ଷୁଦ୍ର/ମଧ୍ୟମ କାର୍ଯ୍ୟଭାର ପାଇଁ ଦ୍ରୁତତର | ଅତ୍ୟଧିକ ସମକାଳୀନ ଲେଖନ ପାଇଁ ଉତ୍ତମ         |
| **ସମକାଳୀନତା**       | WAL ମୋଡ୍ ସମକାଳୀନ ପଠନକୁ ଅନୁମତି ଦିଏ     | ପୂର୍ଣ୍ଣ MVCC                            |
| **ବ୍ୟାକଅପ୍**        | ଏକକ-ଫାଇଲ୍ କପି                         | `pg_dump` କିମ୍ବା ଫାଇଲ୍ସିଷ୍ଟମ୍ ସ୍ନାପ୍ସଟ୍ |
| **ବ୍ୟବହାର କ୍ଷେତ୍ର** | ପ୍ରତି-ବ୍ୟବହାରକାରୀ ଇନ୍ଷ୍ଟଲ୍, ଏମ୍ବେଡେଡ୍ | ମଲ୍ଟି-ଟେନାଣ୍ଟ SaaS                      |

**ଏକକ-ବ୍ୟବହାରକାରୀ, ଏକକ-ଇନ୍ଷ୍ଟାନ୍ସ** ନିୟୋଜନଗୁଡ଼ିକ ପାଇଁ (OmniRouteର ପ୍ରାଥମିକ ବ୍ୟବହାର କ୍ଷେତ୍ର), SQLite ଅଧିକ ସରଳ ଏବଂ ଦ୍ରୁତ।

### WAL ଜର୍ଣ୍ଣାଲିଂ

`core.ts` ଡାଟାବେସ୍କୁ **WAL (Write-Ahead Logging) ମୋଡ୍**ରେ ଖୋଲେ:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL ଲେଖନ ସମୟରେ **ସମକାଳୀନ ପଠନ**କୁ ଅନୁମତି ଦିଏ — ଅନୁରୋଧଗୁଡ଼ିକ ରେକର୍ଡ ହେଉଥିବା ସମୟରେ କ୍ୱେରି କରୁଥିବା ଡ୍ୟାସ୍ବୋର୍ଡ ପାଇଁ ଏହା ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ।

ଡିଫଲ୍ଟ କ୍ୟାଶ୍ ଆକାର ହେଉଛି **65,536 KiB (64 MiB)**। SQLite ଏକ ଋଣାତ୍ମକ
`cache_size`କୁ KiBରେ ଆନୁମାନିକ ସର୍ବୋଚ୍ଚ ସୀମା ଭାବରେ ବ୍ୟାଖ୍ୟା କରେ ଏବଂ ଆବଶ୍ୟକତାନୁସାରେ ପେଜ୍ ଆବଣ୍ଟନ କରେ।
**Settings > System & Storage > Cache Size**ରେ **1ରୁ
1,000,000 KiB** ପର୍ଯ୍ୟନ୍ତ ପୂର୍ଣ୍ଣସଂଖ୍ୟା ମୂଲ୍ୟ ଗ୍ରହଣ କରାଯାଏ; ସେଟିଂ ସଂରକ୍ଷଣ କଲେ ଏହା ସକ୍ରିୟ ଡାଟାବେସ୍ ସଂଯୋଗରେ ପ୍ରୟୋଗ ହୁଏ,
ଏବଂ ଆରମ୍ଭ ସମୟରେ OmniRoute ସଂରକ୍ଷିତ ମୂଲ୍ୟକୁ ପୁନଃସ୍ଥାପନ କରେ।

## ଡାଟାବେସ୍ର ଅବସ୍ଥାନ

SQLite ଫାଇଲ୍ଟି ନିମ୍ନ ସ୍ଥାନରେ ସଂରକ୍ଷିତ ହୁଏ:

| OS      | ପଥ                                                            |
| ------- | ------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                 |
| macOS   | `~/.omniroute/storage.sqlite`                                 |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                     |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` ମାଧ୍ୟମରେ ବିନ୍ୟାସଯୋଗ୍ୟ) |

ସହଯୋଗୀ ଫାଇଲ୍ଗୁଡ଼ିକ:

- `storage.sqlite-wal` — ରାଇଟ୍-ଏହେଡ୍ ଲଗ୍
- `storage.sqlite-shm` — ସହଭାଗୀ ମେମୋରି ଫାଇଲ୍
- `call_logs/` — ଅନୁରୋଧ ପେଲୋଡ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟଗୁଡ଼ିକ (ସକ୍ଷମ ଥିଲେ)

**ଅବସ୍ଥାନକୁ ଓଭର୍ରାଇଡ୍ କରନ୍ତୁ:**

```bash
DATA_DIR=/custom/path omniroute
```

## ଡୋମେନ୍ ମଡ୍ୟୁଲ୍ ଆର୍କିଟେକ୍ଚର୍

OmniRouteର ଡାଟାବେସ୍ରେ `src/lib/db/` ମଧ୍ୟରେ **110ଟି ଶୀର୍ଷ-ସ୍ତରୀୟ TypeScript ମଡ୍ୟୁଲ୍** ଅଛି। ପ୍ରତ୍ୟେକ ଡୋମେନ୍ ମଡ୍ୟୁଲ୍:

- ଗୋଟିଏ କିମ୍ବା ଅଧିକ ନିର୍ଦ୍ଦିଷ୍ଟ ଟେବୁଲ୍ର ଦାୟିତ୍ୱ ନିଏ
- ଟାଇପ୍ଯୁକ୍ତ CRUD ଫଙ୍କସନ୍ଗୁଡ଼ିକୁ ଏକ୍ସପୋର୍ଟ କରେ
- ଅନ୍ୟ କୌଣସି ମଡ୍ୟୁଲ୍ର ଟେବୁଲ୍କୁ କେବେ ମଧ୍ୟ ସ୍ପର୍ଶ କରେ ନାହିଁ
- DBକୁ ଆକ୍ସେସ୍ କରିବା ପାଇଁ `core.ts`ରୁ `getDbInstance()` ବ୍ୟବହାର କରେ

### ମଡ୍ୟୁଲ୍ ସୀମା

ଏକ ମୁଖ୍ୟ ଆର୍କିଟେକ୍ଚରାଲ୍ ନିୟମ: **ମଡ୍ୟୁଲ୍ଗୁଡ଼ିକ ପରସ୍ପରର ଟେବୁଲ୍କୁ ସିଧାସଳଖ ଆକ୍ସେସ୍ କରନ୍ତି ନାହିଁ**। ଅନ୍ୟ ଏକ ମଡ୍ୟୁଲ୍ର ଡାଟା ସହିତ କାମ କରିବା ପାଇଁ, ସେହି ମଡ୍ୟୁଲ୍ରୁ ଫଙ୍କସନ୍ଟି ଇମ୍ପୋର୍ଟ କରନ୍ତୁ।

```ts
// ❌ ଭୁଲ୍: ଅନ୍ୟ ଏକ ମଡ୍ୟୁଲ୍ରୁ ସିଧାସଳଖ SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ଠିକ୍: providers ମଡ୍ୟୁଲ୍ର ଫଙ୍କସନ୍ ବ୍ୟବହାର କରନ୍ତୁ
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

ଏହି ନିୟମ କୋଡ୍ ସମୀକ୍ଷା ମାଧ୍ୟମରେ ପ୍ରବର୍ତ୍ତନ କରାଯାଏ — ଏଥିପାଇଁ କୌଣସି ସ୍ଥିର ଯାଞ୍ଚ ନାହିଁ, କିନ୍ତୁ ଉଲ୍ଲଂଘନଗୁଡ଼ିକୁ ଚିହ୍ନିତ କରାଯାଏ।

OmniRoute ବ୍ୟବହାର କରେ।** ସଂସ୍କରଣ, ଅପାରଗ ସ୍ଥାନାନ୍ତରଣ।** `src/lib/db/migrations/` ରେ ପ୍ରତ୍ୟେକ ସ୍ଥାନାନ୍ତରଣ ହେଉଛି ଗୋଟିଏ SQL ଫାଇଲ୍। ଦୁଇଟି ନାମକରଣ ଫର୍ମାଟ୍ ମିଳିତ; `_omniroute_migrations` ରେ ରେକର୍ଡ ହୋଇଥିବା ସଂସ୍କରଣ ହେଉଛି ସାଂଖ୍ୟିକ ଉପସର୍ଗ।

- ସମାନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ସହିତ ଦୁଇଟି ଫାଇଲ୍ ହେଉଛି ଏକ ନକଲ।
- ନୋ-ଫାଙ୍କ ନିୟମ କେବଳ ପୁରୁଣା କ୍ରମରେ ପ୍ରଯୁଜ୍ୟ: `001` ରୁ `241` ପର୍ଯ୍ୟନ୍ତ ପ୍ରତ୍ୟେକ ସଂଖ୍ୟା ନିଶ୍ଚିତ ରହିବା ଆବଶ୍ୟକ, ଜଣାଶୁଣା ଫାଙ୍କଗୁଡିକ `026`, `055` ଏବଂ `121` ବ୍ୟତୀତ। `241` (କିମ୍ବା କ old ଣସି ପୁରୁଣା ଫାଇଲ) ଡିଲିଟ୍ କରିବା ଦ୍ gate ାରା ଗେଟ୍ ବିଫଳ ହୁଏ। `001` ଏବଂ `241` `KNOWN_GAPS` ଅନୁମତି ତାଲିକାରେ କେବେବି ଯୋଗ କରାଯାଇପାରିବ ନାହିଁ। ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ହୋଇଥିବା ଫାଇଲଗୁଡ଼ିକ କଦାପି ଫାଙ୍କ ସୃଷ୍ଟି କରେ ନାହିଁ।
- `src/lib/db/migrations/` ର ପ୍ରତ୍ୟେକ ଏଣ୍ଟ୍ରି ଏକ ବ valid ଧ ଲୋୟର କେସ୍ `.sql` ନାମ ସହିତ ଏକ ନିୟମିତ ଫାଇଲ୍ ହେବା ଜରୁରୀ। ଏକ ଡିରେକ୍ଟୋରୀ, ଏକ ସିମ୍ଲିଙ୍କ୍, `.SQL` କିମ୍ବା `.sql.bak` ଫାଇଲ୍, ଏକ ଲୁକ୍କାୟିତ ଫାଇଲ୍ କିମ୍ବା ଏକ ସ୍ପେସ୍ ସହିତ ନାମ ଗେଟ୍ ବିଫଳ ହୁଏ, କାରଣ ରନର୍ ଏହାକୁ ଚୁପଚାପ୍ ଛାଡିଦେବେ କିମ୍ବା ବୁଟରେ କ୍ରାସ୍ କରିବେ।

**ଅର୍ଡର ପ୍ରୟୋଗ କରନ୍ତୁ।** ଉପସର୍ଗର ସାଂଖ୍ୟିକ ମୂଲ୍ୟ ଅନୁଯାୟୀ ରନର୍ ସର୍ଟ କରେ, ପାଠ୍ୟ ଦ୍ୱାରା ନୁହେଁ: ପ୍ରଥମେ ପୁରୁଣା `001`-`241` ଫାଇଲଗୁଡ଼ିକ, ତା’ପରେ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ କ୍ରମରେ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ହୋଇଥିବା ଫାଇଲଗୁଡ଼ିକ, ତାପରେ `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ସହିତ ପଞ୍ଜୀକୃତ ଯେକ names ଣସି ନାମ ସ୍ଥାନ ଡିରେକ୍ଟୋରୀ ( `ee-001` ପରି ସଂସ୍କରଣ)। ଏକ ବିଚାରାଧୀନ ସ୍ଥାନାନ୍ତରଣ ହେଉଛି ଯେକ file ଣସି ଫାଇଲ ଯାହାର ସଂସ୍କରଣ `_omniroute_migrations` ରେ ନାହିଁ, ତେଣୁ ଏକ ପୁରୁଣା ଶାଖାରୁ ସ୍ଥାନାନ୍ତରଣ ଯାହା ଏକ ନୂତନ ପରେ ମିଶ୍ରଣ ହୁଏ ତଥାପି ବିଦ୍ୟମାନ ଡାଟାବେସରେ ପ୍ରଯୁଜ୍ୟ।

**ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ହେଉଛି ସୃଷ୍ଟି କ୍ରମ, ମିଶ୍ରଣ କ୍ରମ ନୁହେଁ।** ଯଦି ଆପଣଙ୍କର ସ୍ଥାନାନ୍ତରଣ a ସହିତ ସ୍ଥାନାନ୍ତରଣ ଦ୍ୱାରା ସୃଷ୍ଟି ହୋଇଥିବା ଏକ ସାରଣୀ କିମ୍ବା ସ୍ତମ୍ଭ ଉପରେ ନିର୍ଭର କରେ।** ନୂତନ** ଟାଇମଷ୍ଟ୍ୟାମ୍ପ (ଉଦାହରଣ ସ୍ୱରୂପ, ଅନ୍ୟ PR ରୁ ଗୋଟିଏ ଯାହା ପ୍ରଥମେ ମିଶ୍ରିତ ହେଲା), ଏକ ନୂତନ ଡାଟାବେସ୍ ପ୍ରଥମେ ତୁମକୁ ଚଲାଇବ ଏବଂ ବିଫଳ ହେବ। ଯେତେବେଳେ ଆପଣଙ୍କର PR ଖୋଲା ଅଛି, `npm run db:new-migration` ସହିତ ଫାଇଲ୍ ନାମକୁ ପୁନ ener ନିର୍ମାଣ କରନ୍ତୁ ଯାହା ଦ୍ it ାରା ଏହା ଏକ ନୂତନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ପାଇବ, କିମ୍ବା ଏହାକୁ ସ୍ independent ାଧୀନ କର। `npm run test:migrations:fresh` ପ୍ରତ୍ୟେକ ସ୍ଥାନାନ୍ତରଣକୁ ଏକ ଖାଲି ଡାଟାବେସରେ ପ୍ରୟୋଗ କରିଥାଏ ଏବଂ ଏହାକୁ ଧରିଥାଏ।

### ଏକ ମିଶ୍ରିତ ସ୍ଥାନାନ୍ତରଣ କଦାପି ବିଲୋପ ହୁଏ ନାହିଁ କିମ୍ବା ନାମ ପରିବର୍ତ୍ତନ ହୁଏ ନାହିଁ।

ଥରେ ଏକ ସ୍ଥାନାନ୍ତରଣ ଫାଇଲ ଏକ ରିଲିଜ୍ ଶାଖା କିମ୍ବା `main` ରେ ଥଲା, ଏହା ହୋମୋଲୋଜି ଏବଂ ଡେଭଲପର୍ ଡାଟାବେସରେ, VPS ସଂସ୍ଥାଗୁଡ଼ିକରେ ଏବଂ ଏଣ୍ଟରପ୍ରାଇଜ୍ ସିଙ୍କରେ ଚାଲିସାରିଛି। ସେବେଠାରୁ:

- **ଏହାକୁ କେବେ ବିଲୋପ କରନ୍ତୁ ନାହିଁ।** ସତେଜ ସଂସ୍ଥାଗୁଡ଼ିକ ଏହାର ସ୍କିମା ହରାଇବ ଯେତେବେଳେ ଅପଗ୍ରେଡ୍ ଡାଟାବେସ୍ ଏହାକୁ ରଖିବ।
- **ଏହାକୁ କେବେବି ନାମ ପରିବର୍ତ୍ତନ କରନ୍ତୁ ନାହିଁ।** `_omniroute_migrations` ରେ ଥିବା ସଂସ୍କରଣ ଆଉ ଏକ ଫାଇଲ ସହିତ ମେଳ ହେବ ନାହିଁ, ତେଣୁ ଏହାକୁ ପ୍ରୟୋଗ କରିଥିବା ପ୍ରତ୍ୟେକ ଡାଟାବେସ୍ ଏହାକୁ ପୁନର୍ବାର ଚଲାଇବ। ଅଣ-କ୍ଷମତାହୀନ SQL ତାପରେ ତଥ୍ୟ ନକଲ କରେ କିମ୍ବା ବୁଟକୁ ବନ୍ଦ କରିଦିଏ।
- **ଏକ ଭିନ୍ନ ଯୋଜନା ଆବଶ୍ୟକ କରନ୍ତି କି?** `npm run db:new-migration` ସହିତ ଏକ ନୂତନ ସ୍ଥାନାନ୍ତରଣ ସୃଷ୍ଟି କରନ୍ତୁ।

କେବଳ ଏକ ଫାଇଲ୍ ପାଇଁ ପୁନ am ନାମକରଣ ନିରାପଦ ଅଟେ ଯାହା ଏପର୍ଯ୍ୟନ୍ତ ମିଶ୍ରିତ ହୋଇନାହିଁ, ଯାହା ଫାଟକର ସୂଚକକୁ ଦର୍ଶାଏ। ଏକ ରିଲିଜ୍ ଟ୍ୟାଗ୍ ଏଠାରେ କିଛି ପରିବର୍ତ୍ତନ କରେ ନାହିଁ: `release/v*` ଶାଖାର ପ୍ରତ୍ୟେକ ଧକ୍କା Docker `:next` ପ୍ରତିଛବି ପ୍ରକାଶ କରେ ଏବଂ ହୋମୋଲୋଜ୍, VPS ସଂସ୍ଥାପନ ଏବଂ ଏଣ୍ଟରପ୍ରାଇଜ୍ ସିଙ୍କରେ ଚାଲିଥାଏ, ତେଣୁ କ z ଣସି `vX.Y.Z` ଟ୍ୟାଗ୍ ପୂର୍ବରୁ ଏକ ମିଶ୍ରିତ ସ୍ଥାନାନ୍ତରଣ ପ୍ରକୃତ ଡାଟାବେସରେ ଚାଲିଥାଏ। ଗେଟ୍ ଏକ ବେସ୍ ଫାଇଲ୍ ର ଅପସାରଣରେ ବିଫଳ ହୁଏ, ଟ୍ୟାଗ୍ ହୋଇଛି କି ନାହିଁ।

- **ଏକ ମିଶ୍ରିତ ସ୍ଥାନାନ୍ତରଣକୁ ପ୍ରତ୍ୟାବର୍ତ୍ତନ।** ଏକ `git revert` ଯାହା ଫାଇଲ୍ ଡିଲିଟ୍ କରେ ଗେଟ୍ ବିଫଳ ହୁଏ। ଫାଇଲକୁ ରଖନ୍ତୁ ଏବଂ ଏହାର ସ୍କିମାକୁ ଏକ ନୂତନ ସ୍ଥାନାନ୍ତରଣରେ ପୂର୍ବବତ୍ କରନ୍ତୁ: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` ଇତ୍ୟାଦି ସହିତ। ଅପଗ୍ରେଡ୍ ଏବଂ ତାଜା ଡାଟାବେସ୍ ତାପରେ ସମାନ ସ୍କିମା ସହିତ ଶେଷ ହୁଏ।
- **ଗୋଟିଏ ଗ୍ରହଣ କରାଯାଇଥିବା ନାମ: ଏକ ସୁସଙ୍ଗତତା ପ୍ରବେଶ ଏବଂ ସମାନ ବିଷୟବସ୍ତୁ।** ଯଦି ଏକ ମିଶ୍ରିତ ଫାଇଲ୍ ନିଶ୍ଚିତ ଭାବରେ ଘୁଞ୍ଚିବ (ଉଦାହରଣ ସ୍ୱରୂପ, ଦୁଇଟି ମିଶ୍ରିତ ଫାଇଲ୍ ଏକ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ଅଂଶୀଦାର କରେ ଏବଂ ରନର୍ ଏକ ସଂସ୍କରଣ ଧକ୍କା ସହିତ ବନ୍ଦ ହୋଇଯାଏ), ଏହାର SQL ସ୍ପର୍ଶ ନକରି ପରବର୍ତ୍ତୀ ନାମର ନାମ ପରିବର୍ତ୍ତନ କରନ୍ତୁ ଏବଂ `src/lib/db/migrationRunner/constants.ts` ରେ `{ fromVersion, fromName, toVersion, toName }` କୁ `RENAMED_MIGRATION_COMPATIBILITY` ରେ ଯୋଗ କରନ୍ତୁ। ପୁରୁଣା ସଂସ୍କରଣକୁ ପ୍ରୟୋଗ କରିଥିବା ଡାଟାବେସ୍ ପୁନର୍ବାର ଫାଇଲ୍ ଚଲାଇବା ପରିବର୍ତ୍ତେ ସେମାନଙ୍କର `_omniroute_migrations` ଧାଡି ଘୁଞ୍ଚାଏ। ଗେଟ୍ ଏପରି ନାମକରଣ ବିଷୟରେ ଚେତାବନୀ ଦେଇଥାଏ ଏବଂ ସର୍ବଦା ଏହା ଉପରେ ଯାତାୟାତ ଯାଞ୍ଚ କରିଥାଏ, ନୂତନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ଯାହା ହେଉନା କାହିଁକି: ତାଜା ସଂସ୍ଥାଗୁଡ଼ିକ ଫାଇଲକୁ ଏହାର ନୂତନ ସ୍ଥିତିରେ ପ୍ରୟୋଗ କରେ, ଅପଗ୍ରେଡ୍ ଡାଟାବେସ୍ କରେ ନାହିଁ, ତେଣୁ ପୁରୁଣା ନିକଟରେ ଏକ ନୂତନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ବାଛ। ଯଦି ବିଷୟବସ୍ତୁ ବଦଳିଯାଏ (ଏକ ସ୍କିମା ପରିବର୍ତ୍ତନ ଏକ ନୂତନ ସ୍ଥାନାନ୍ତରଣରେ ଚାଲିଥାଏ), କିମ୍ବା ଯଦି ପ୍ରବେଶର ଲକ୍ଷ୍ୟ ଫାଇଲ ଡିସ୍କରେ ନଥାଏ ତେବେ ଗେଟ୍ ନାମ ପରିବର୍ତ୍ତନ କରିବାରେ ବିଫଳ ହୁଏ।
- **ସମାନ ସମୟ ସୀମା ମଧ୍ୟରେ କେବେବି ନାମ ପରିବର୍ତ୍ତନ କରନ୍ତୁ ନାହିଁ।** ଏକ ପୁନ ame ନାମ ଯାହା ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ରଖେ ଏବଂ କେବଳ ବର୍ଣ୍ଣନା ପରିବର୍ତ୍ତନ କରେ, ପ୍ରବେଶ କିମ୍ବା ବିନା ପ୍ରବେଶ ଦ୍ୱାର ବିଫଳ ହୁଏ। ଏକ ଏଣ୍ଟ୍ରି ସହିତ ଯାହାର `toVersion` ଏହାର `fromVersion` ସହିତ ସମାନ, ରନର୍ ପୁରୁଣା `_omniroute_migrations` ଧାଡି ଡିଲିଟ୍ କରେ ଏବଂ ଫାଇଲ୍ ଚଲାଇଥିବା ପ୍ରତ୍ୟେକ ଡାଟାବେସରେ ପୁନର୍ବାର ପ୍ରୟୋଗ କରେ। ଏକ ଏଣ୍ଟ୍ରି ବିନା, ରନର୍ କେବଳ ସଂସ୍କରଣକୁ ଟ୍ରାକ୍ କରେ: ଏହା ସେହି ଡାଟାବେସରେ ଫାଇଲକୁ ଛାଡିଦିଏ (ନୂତନ ବିଷୟବସ୍ତୁ ସେଠାରେ କେବେବି ଚାଲିବ ନାହିଁ) ଏବଂ ପ୍ରତ୍ୟେକ ବୁଟରେ ପୁନ umber ନାମକରଣ ତ୍ରୁଟି ଲଗ୍ କରେ। ଅନ୍ୟ ଏକ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ଏବଂ ଏକ ସୁସଙ୍ଗତତା ପ୍ରବିଷ୍ଟ ବ୍ୟବହାର କରନ୍ତୁ, କିମ୍ବା ନାମ ରଖନ୍ତୁ।
- **ଗେଟ୍ ଯାଞ୍ଚ କରେ ଯେ ନାମ ପରିବର୍ତ୍ତନ ହୋଇଥିବା ଫାଇଲ ଆଉ ଚାଲୁ ନାହିଁ।** ପ୍ରତ୍ୟେକ ଆଚ୍ଛାଦିତ ନାମ ପାଇଁ, ଗେଟ୍ ନୂତନ ଫାଇଲ୍ ନାମକୁ `--must-not-apply` ସହିତ ଯାତାୟାତ ଯାଞ୍ଚକୁ ପଠାଇଥାଏ। ଚେକ୍ ଅପଗ୍ରେଡ୍ ଡାଟାବେସ୍ କୁ ପ୍ରକୃତ ରନର୍ ସହିତ ବୁଟ୍ କରେ, ଏବଂ ଯଦି ରନର୍ ସେହି ଫାଇଲ୍ କୁ ପୁନର୍ବାର ପ୍ରୟୋଗ କରେ (ଉଦାହରଣ ସ୍ୱରୂପ, କାରଣ ଏଣ୍ଟ୍ରିର ଭୁଲ ସଂସ୍କରଣ କିମ୍ବା ନାମ ଅଛି, କିମ୍ବା ଗେଟ୍ ର ଟେକ୍ସଟ୍ ପାର୍ସର୍ `constants.ts` TypeScript ଭିନ୍ନ ଭାବରେ ପ read ଼ିଥାଏ), ଗେଟ୍ `migration renomeada rodaria de novo` ସହିତ ବିଫଳ ହୁଏ ଏବଂ ପ୍ରବେଶର ପୁରୁଣା ଏବଂ ନୂତନ ସଂସ୍କରଣ ଏବଂ ନାମ ଯାଞ୍ଚ କରିବାକୁ କହିଥାଏ।

### ଗେଟ୍ ବେସ୍ ବିରୁଦ୍ଧରେ କଣ ଯାଞ୍ଚ କରେ।

ଟାଣ ଅନୁରୋଧ ଏବଂ ମିଶ୍ରଣ-ଧାଡ଼ି ଚାଲିବା ଉପରେ, `npm run check:migration-numbering` ଡିସ୍କରେ `src/lib/db/migrations/` ଆଧାର ଶାଖାରେ ସମାନ ଡିରେକ୍ଟୋରୀ ସହିତ ତୁଳନା କରେ। ଆଧାର ହେଉଛି, ଏହି କ୍ରମରେ: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` ଭେରିଏବଲ୍, କିମ୍ବା, ଯେତେବେଳେ `GITHUB_EVENT_NAME` ହେଉଛି `pull_request`, `pull_request_target` କିମ୍ବା `merge_group`, ମିଶ୍ରଣ ପ୍ରତିଶ୍ରୁତିର ପ୍ରଥମ ପିତାମାତା, ଇଭେଣ୍ଟ ପେଲୋଡ୍ ର `merge_group.base_sha`, କିମ୍ବା `git merge-base HEAD origin/$GITHUB_BASE_REF`। କ pull ଣସି ସମାଧାନଯୋଗ୍ୟ ଆଧାର ସହିତ ଏକ ଟାଣ ଅନୁରୋଧ କିମ୍ବା ମିଶ୍ରଣ-ଧାଡିରେ ଗେଟ୍ ବିଫଳ ହୁଏ। `--base` ବିନା CI ବାହାରେ ଏହା `comparação com a base: pulada (sem --base)` ପ୍ରିଣ୍ଟ କରେ ଏବଂ ଏହି ନିୟମକୁ ଛାଡିଦିଏ।

`--base-latest-tag` ନୂତନ ରିଲିଜ୍ ଟ୍ୟାଗ୍ ସହିତ ତୁଳନା କରେ (`vX.Y.Z` ସେମର୍ କ୍ରମରେ; ସଫିକ୍ସଡ୍ ଟ୍ୟାଗ୍ ଯେପରିକି ନାଇଟ୍ଲି ଗଣନା କରେ ନାହିଁ) ଯାହାକି `HEAD` ଇତିହାସରେ ଅଛି, `--base` ସହିତ ସମାନ ନିୟମ ସହିତ। ରିଲିଜ୍-ଗ୍ରୀନ୍ (`scripts/quality/validate-release-green.mjs`) ଏହିପରି ଗେଟ୍ ଚଲାଇଥାଏ, କାରଣ ପୁସ୍ ଏବଂ ନିର୍ଧାରିତ ରନ୍ଗୁଡ଼ିକର କ pull ଣସି ଟାଣ ଅନୁରୋଧ ଆଧାର ନାହିଁ ଏବଂ ଏକ ମିଶ୍ରଣ ଏକ ନୂତନ CI ରନ୍ ବିନା ଅବତରଣ କରିପାରିବ। ଇତିହାସରେ କ release ଣସି ରିଲିଜ୍ ଟ୍ୟାଗ୍ ସହିତ ଗେଟ୍ ବିଫଳ ହୁଏ; `git fetch --tags` ଚଲାନ୍ତୁ ( CI ରେ, `fetch-depth: 0` ସହିତ `actions/checkout` ଟ୍ୟାଗ୍ ଆଣିଥାଏ)।

ଯାତାୟାତ ଯାଞ୍ଚ (`scripts/check/migration-commutation.ts`) ପ୍ରକୃତ ସଂସ୍ଥାପନ ପଥ ସହିତ ଦୁଇଟି ଅସ୍ଥାୟୀ ଡାଟାବେସ୍ ନିର୍ମାଣ କରେ: an** ନବୀକରଣ** ଗୋଟିଏ (ଆଧାର ସ୍ଥାନାନ୍ତରଣ ସହିତ ବୁଟ କରନ୍ତୁ, ତାପରେ ପୁନର୍ବାର ସମାନ ଫାଇଲରେ ଟାଣ ଅନୁରୋଧର ସ୍ଥାନାନ୍ତରଣ ସହିତ ବୁଟ କରନ୍ତୁ) ଏବଂ a** ସତେଜ** ଗୋଟିଏ (ଟାଣ ଅନୁରୋଧର ସ୍ଥାନାନ୍ତରଣ ସହିତ ଗୋଟିଏ ବୁଟ୍)। ଏହା ଫଳାଫଳ ହୋଇଥିବା ସ୍କିମାଗୁଡ଼ିକୁ ତୁଳନା କରେ: ଟେବୁଲ୍ ଏବଂ ସ୍ତମ୍ଭଗୁଡିକ (ସ୍ତମ୍ଭ କ୍ରମକୁ ଅଣଦେଖା କରି), UNIQUE / PRIMARY KEY ଏବଂ FOREIGN KEY ପ୍ରତିବନ୍ଧକ, ପ୍ରତ୍ୟେକ ଟେବୁଲର ସାଧାରଣ `CREATE TABLE` ପାଠ୍ୟ (ଯାହାକି CHECK ପ୍ରତିବନ୍ଧକ, ସଂଗ୍ରହ, ଉତ୍ପାଦିତ ସ୍ତମ୍ଭ ଏବଂ ଟେବୁଲ୍ ବିକଳ୍ପଗୁଡ଼ିକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ), ସୂଚକାଙ୍କ, ଟ୍ରିଗର ଏବଂ ଦୃଶ୍ୟ। ଧାଡି ତଥ୍ୟ ତୁଳନା କରାଯାଏ ନାହିଁ। ଯଦି ସେମାନେ ମେଳ କରନ୍ତି, ଗେଟ୍ ପ୍ରିଣ୍ଟ୍ କରେ ଯେ ଫାଇଲ୍ ଅର୍ଡର ଅଛି କିନ୍ତୁ ଯାତାୟାତ କରେ, ଏବଂ ପାସ୍ କରେ। ଯଦି ସେମାନେ ଭିନ୍ନ ହୁଅନ୍ତି, ଗେଟ୍ ପାର୍ଥକ୍ୟ ଏବଂ ମାମଲା ପାଇଁ ଏକ ସୂଚନା ସହିତ ବିଫଳ ହୁଏ: ଏକ ଅର୍ଡର ଫାଇଲ୍ ପାଇଁ, `npm run db:new-migration` ସହିତ ଏହାର ନାମ ପୁନ ener ନିର୍ମାଣ କରନ୍ତୁ, ଯାହା ସୁରକ୍ଷିତ କାରଣ ଫାଇଲ ଏପର୍ଯ୍ୟନ୍ତ ମିଶ୍ରିତ ହୋଇନାହିଁ; ଏକ ସଂପାଦିତ ଆଧାର ଫାଇଲ ପାଇଁ, ମୂଳ ବିଷୟବସ୍ତୁକୁ ପୁନ restore ସ୍ଥାପନ କରନ୍ତୁ ଏବଂ ଏକ ନୂତନ ସ୍ଥାନାନ୍ତରଣରେ ପରିବର୍ତ୍ତନ ରଖନ୍ତୁ; ପୁନ ren ନାମିତ ଫାଇଲ ପାଇଁ, ପୁନ ame ନାମକୁ ପୂର୍ବବତ୍ କରନ୍ତୁ କିମ୍ବା ଅନ୍ୟ ଏକ ନୂତନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ବାଛନ୍ତୁ ଯେଉଁଠାରେ ଏହା ଯାତାୟାତ କରେ, ଅନ୍ୟ ନାମ ସହିତ ସମାନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ କେବେବି ନୁହେଁ। ଯଦି ଚେକ୍ ନିଜେ ଚାଲିପାରିବ ନାହିଁ, ଗେଟ୍ CI ରେ ବିଫଳ ହୁଏ ଏବଂ କେବଳ ସ୍ଥାନୀୟ ଭାବରେ ଚେତାବନୀ ଦେଇଥାଏ। ଏକ ଏଡିଟ୍ ହୋଇଥିବା ବେସ୍ ଫାଇଲ୍ ପାଇଁ, ଅପଗ୍ରେଡ୍ ଡାଟାବେସ୍ ସେହି ଫାଇଲର ଆଧାରର ବିଷୟବସ୍ତୁ ସହିତ ନିର୍ମିତ ହୋଇଛି ଏବଂ ଦ୍ୱିତୀୟ ବୁଟ୍ ଏହାକୁ ଛାଡିଦିଏ କାରଣ ଏହାର ସଂସ୍କରଣ ପୂର୍ବରୁ ରେକର୍ଡ ହୋଇସାରିଛି। ପୁନ ren ନାମିତ ଫାଇଲ୍ ପାଇଁ, ଅପଗ୍ରେଡ୍ ଡାଟାବେସ୍ ଏହାର ପୁରୁଣା ନାମରେ ଫାଇଲ୍ ସହିତ ନିର୍ମିତ ହୋଇଛି ଏବଂ ଦ୍ୱିତୀୟ ବୁଟ୍ ଏହାର `_omniroute_migrations` ଧାଡିକୁ ପୁନର୍ବାର ଚଲାଇବା ପରିବର୍ତ୍ତେ ସୁସଙ୍ଗତତା ଏଣ୍ଟ୍ରି ମାଧ୍ୟମରେ ଘୁଞ୍ଚାଏ। ଗେଟ୍ `--must-not-apply` ସହିତ ନୂତନ ନାମ ପାସ୍ କରେ, ତେଣୁ ଦ୍ୱିତୀୟ ବୁଟ୍ ଏହାକୁ ପ୍ରୟୋଗ କଲେ ଚେକ୍ ବିଫଳ ହୁଏ। ଯଦି ଏକ ଟାଣ ଅନୁରୋଧ ସ୍ଥାନାନ୍ତରଣ ଅପଗ୍ରେଡ୍ ପଥରେ ପ୍ରୟୋଗ କରିବାରେ ବିଫଳ ହୁଏ, ଅର୍ଥାତ୍ ପ୍ରତ୍ୟେକ ଆଧାର ସ୍ଥାନାନ୍ତରଣ ପରେ (ଏହା ମଧ୍ୟ ଏକ ନୂତନ ସଂସ୍ଥାପନାରେ ବିଫଳ ହୁଏ କି ନାହିଁ), ଗେଟ୍ `migration do PR não aplica` ରିପୋର୍ଟ କରେ ଏବଂ ଆଧାରର ସାମ୍ପ୍ରତିକ ସ୍କିମା ବିରୁଦ୍ଧରେ SQL ଠିକ୍ କରିବାକୁ କହିଥାଏ; ଯଦି ଫାଇଲ୍ ପରବର୍ତ୍ତୀ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ସହିତ ଅନ୍ୟ ଏକ ଟାଣ ଅନୁରୋଧ ସ୍ଥାନାନ୍ତରଣ ଉପରେ ନିର୍ଭର କରେ, `npm run db:new-migration` ସହିତ ଏହାର ନାମ ପୁନ ener ନିର୍ମାଣ କରନ୍ତୁ।

ସ୍ଥାନୀୟ ଭାବରେ ସମାନ ତୁଳନାକୁ ଚଲାଇବା ପାଇଁ, ଆଧାରକୁ ସ୍ପଷ୍ଟ ଭାବରେ ପାସ୍ କରନ୍ତୁ, ଉଦାହରଣ ସ୍ୱରୂପ `npm run check:migration-numbering -- --base origin/<base-branch>`, କିମ୍ବା `npm run check:migration-numbering -- --base-latest-tag` ସର୍ବଶେଷ ପ୍ରକାଶନ ସହିତ ତୁଳନା କରିବାକୁ।

1. **ବର୍ଣ୍ଣନାକୁ ରଖି ଜେନେରେଟର ସହିତ ଫାଇଲର ନାମ ପରିବର୍ତ୍ତନ କରନ୍ତୁ।** ନୂତନ ନାମ ପାଇବା ପାଇଁ `npm run db:new-migration -- <same description>` ଚଲାନ୍ତୁ, SQL କୁ ଏଥିରେ ଘୁଞ୍ଚାନ୍ତୁ ଏବଂ ପୁରୁଣା `NNN_` ଫାଇଲକୁ ବିଲୋପ କରନ୍ତୁ। ବର୍ଣ୍ଣନା ନିଶ୍ଚିତ ଭାବରେ ସମାନ ରହିବ: ନିମ୍ନରେ ଥିବା ସୁସଙ୍ଗତତା ଏଣ୍ଟ୍ରି ଏଥିରେ ମେଳ ଖାଉଛି।
2. **ଯଦି ଏକ ସ୍ଥାୟୀ ଡାଟାବେସ୍ ପୁରୁଣା ସଂଖ୍ୟା ଚଲାଇଥାଏ ତେବେ ଏକ ସୁସଙ୍ଗତତା ଏଣ୍ଟ୍ରି ଯୋଡନ୍ତୁ।** ଯଦି କ database ଣସି ଡାଟାବେସ୍ ରଖାଯାଏ (ହୋମୋଲୋଜ୍, ଏକ VPS, ଜଣେ ଅବଦାନକାରୀଙ୍କ ନିଜସ୍ୱ ସଂସ୍ଥାପନ) `NNN_` ଫାଇଲ୍ ସହିତ PR ର ଏକ ବିଲ୍ଡ ଚଲାଇଥାଏ, `src/lib/db/migrationRunner/constants.ts` ରେ `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` କୁ `RENAMED_MIGRATION_COMPATIBILITY` ରେ ଯୋଗ କର। ଏହା ହେଉଛି** `237` ରୁ `241` ପାଇଁ ଆବଶ୍ୟକ।** : ସେହି ସ୍ଲଟ୍ ଗୁଡିକ ବର୍ତ୍ତମାନ କାନୋନିକାଲ୍ `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` ଏବଂ `241_seen_models.sql` ଧାରଣ କରିଥାଏ, ଏବଂ ଏଣ୍ଟ୍ରି ବିନା ଏହିପରି ଏକ ଡାଟାବେସ୍ କାନୋନିକାଲ୍ ସ୍ଥାନାନ୍ତରଣକୁ ସବୁଦିନ ପାଇଁ ଛାଡିଦିଏ ଏବଂ ରୂପାନ୍ତରିତକୁ ପୁଣି ଚଲାଇଥାଏ। ଏହା ଏକ ସ୍ଲଟ୍ ପାଇଁ ମଧ୍ୟ କାମ କରେ ଯାହା ଖାଲି ରହିଥାଏ, ଯେପରିକି `242`, ଯେତେବେଳେ ଗନ୍ତବ୍ୟସ୍ଥଳ ଏକ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ଅଟେ। ସନ୍ଦେହ ହେଲେ, ଏଣ୍ଟ୍ରି ଯୋଡନ୍ତୁ। ଯେଉଁଠାରେ ଆପଣ ଏହାକୁ ଆରେରେ ଯୋଡନ୍ତି ସେଥିରେ କିଛି ଫରକ ପଡ଼େ ନାହିଁ: ଯେତେବେଳେ ଏକ ଏଣ୍ଟ୍ରିର ଟାର୍ଗେଟ୍ ସ୍ଲଟ୍ ଏକ ଧାଡି ଧରିଥାଏ ଯାହାକି ଅନ୍ୟ ଏକ ଏଣ୍ଟ୍ରି ଦୂରକୁ ଚାଲିଯାଏ (ଉଦାହରଣ ସ୍ୱରୂପ `237` ଏକ PR ଧାଡି ଧରିଥିବାବେଳେ ଏକ ପୁରୁଣା `usage_history_calculated_cost` ଧାଡି `237` କୁ ଯିବା ପାଇଁ ଅପେକ୍ଷା କରିଥାଏ), ରନର୍ ସେହି ପ୍ରବେଶକୁ ସ୍ଲଟ୍ ମୁକ୍ତ ହେବା ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରିବାକୁ ଦେଇଥାଏ। କେବଳ ଏକ ପ୍ରକୃତ ଦ୍ୱନ୍ଦ, ଯେପରିକି ଧାଡିରେ ଧରାଯାଇଥିବା ଏକ ସ୍ଲଟ୍, କ entry ଣସି ଏଣ୍ଟ୍ରି ମୁଭ୍ ନାହିଁ, କିମ୍ବା ଦୁଇଟି ଏଣ୍ଟ୍ରି ଯାହା ସ୍ଲଟ୍ ଅଦଳବଦଳ କରେ, `Cannot reconcile ...` ସହିତ ବୁଟକୁ ବନ୍ଦ କରିଥାଏ।
3. **SQL idempotent ରଖନ୍ତୁ।** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), କାରଣ ରୂପାନ୍ତରିତ ସ୍ଥାନାନ୍ତରଣ ଏକ ଡାଟାବେସ୍ ପୂରଣ କରିପାରିବ ଯେଉଁଠାରେ ଏହାର ସ୍କିମ୍ ପୂର୍ବରୁ ବିଦ୍ୟମାନ ଅଛି।
4. **ସଂସ୍କରଣ-କିଡ୍ ସ୍ special ତନ୍ତ୍ର କେସ୍ ଘୁଞ୍ଚାନ୍ତୁ।** ଯଦି PR ଏହାର ପୁରୁଣା ସଂଖ୍ୟା ପାଇଁ `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) କିମ୍ବା `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) ରେ ଏକ ମାମଲା ଯୋଡିଥାଏ, ତେବେ ନୂତନ ଟାଇମଷ୍ଟ୍ୟାମ୍ପର ଚାବିକୁ ପରିବର୍ତ୍ତନ କରନ୍ତୁ।

`tests/unit/db/codex-fence-migration-rename.test.ts` ଏକ ନାମକରଣ ସ୍ଥାନାନ୍ତରଣ ପାଇଁ ଏକ ପରୀକ୍ଷଣର ଏକ କାର୍ଯ୍ୟର ଉଦାହରଣ।

### ସୁଇଚ୍ ପୂର୍ବରୁ ଶାଖାଗୁଡ଼ିକୁ ବ୍ୟାକପୋର୍ଟ।

କ z ଣସି `YYYYMMDDHHMMSS_` ଫାଇଲକୁ ଏକ ଶାଖାରେ ଚେରି-ପିକ୍ କିମ୍ବା ବ୍ୟାକପୋର୍ଟ କରନ୍ତୁ ନାହିଁ ଯାହାକି ସୁଇଚ୍ ପୂର୍ବାନୁମାନ କରେ (ଉଦାହରଣ ସ୍ୱରୂପ ଏକ ପୁରୁଣା `release/v*` ଶାଖା)। ସେଠାରେ ଥିବା ରନର୍ ଫାଇଲ୍ ନାମଗୁଡ଼ିକୁ ପାଠ୍ୟ ଭାବରେ ସଜାଇଥାଏ, ତେଣୁ ଏକ ଟାଇମଷ୍ଟ୍ୟାମ୍ପଡ୍ ଫାଇଲ୍ ଏକ ନୂତନ ଡାଟାବେସରେ `201_` ଏବଂ `202_` ମଧ୍ୟରେ ଚାଲିବ, ଏବଂ ସେଠାରେ ଥିବା ପୁରୁଣା ଗେଟ୍ 14 ଅଙ୍କ ବିଶିଷ୍ଟ ଉପସର୍ଗ ବୁ understand ିପାରିବ ନାହିଁ। ଏହିପରି ଏକ ଶାଖାରେ, ପରିବର୍ତ୍ତନକୁ ସେହି ଶାଖାର ନିଜସ୍ୱ ପରବର୍ତ୍ତୀ `NNN_` ଫାଇଲ୍, idempotent ଭାବରେ ଲେଖ, ତେଣୁ ଟାଇମଷ୍ଟ୍ୟାମ୍ପଡ୍ ସଂସ୍କରଣ ପରେ ଆସିବା ଏହା ଏକ ନୋ-ଅପ୍ ଅଟେ।

### ସ୍ଥାନାନ୍ତରଣ କିପରି ଚାଲିଥାଏ।

ଆରମ୍ଭ ସମୟରେ, `migrationRunner.ts`:

1. ଯଦି ନାହିଁ ତେବେ `_omniroute_migrations` ଟେବୁଲ୍ ସୃଷ୍ଟି କରେ।
2. ପୂର୍ବରୁ ପ୍ରୟୋଗ ହୋଇଥିବା ସ୍ଥାନାନ୍ତରଣ ପାଇଁ ପ୍ରଶ୍ନଗୁଡିକ।
3. ପ୍ରତ୍ୟେକ କାରବାରରେ କ new ଣସି ନୂତନ ସ୍ଥାନାନ୍ତରଣ ପ୍ରୟୋଗ କରନ୍ତି।
4. ପ୍ରତ୍ୟେକ ପ୍ରୟୋଗ ସ୍ଥାନାନ୍ତରଣକୁ ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ସହିତ ରେକର୍ଡ କରେ।

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### ଅଜ୍ଞତା।

ସ୍ଥାନାନ୍ତରଣ ହେବା ଜରୁରୀ।** idempotent** — ସେମାନଙ୍କୁ ଦୁଇଥର ଚଲାଇବା ଏକ ନୋ-ଅପ୍ ହେବା ଉଚିତ:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

ଉଦାର ଭାବରେ `IF NOT EXISTS`, `IF EXISTS`, ଏବଂ `OR IGNORE` / `OR REPLACE` ଧାରା ବ୍ୟବହାର କରନ୍ତୁ।

### ଏକ ନୂତନ ସ୍ଥାନାନ୍ତରଣ ଯୋଗ କରିବା।

1. **ଜେନେରେଟର ସହିତ ଫାଇଲ୍ ସୃଷ୍ଟି କରନ୍ତୁ।** : `npm run db:new-migration -- <description>` (ଉଦାହରଣ ସ୍ୱରୂପ `npm run db:new-migration -- add combo priority`)। ଏହା ସାମ୍ପ୍ରତିକ UTC ସମୟ ଏବଂ ଏକ ମନ୍ତବ୍ୟ ହେଡର୍ ସହିତ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` ଲେଖେ, ଯଦି ସେହି ଟାଇମଷ୍ଟ୍ୟାମ୍ପ ନିଆଯାଏ ତେବେ ଗୋଟିଏ ସେକେଣ୍ଡ ଆଗକୁ ବ, େ, ଏବଂ କ never ଣସି ଫାଇଲକୁ ଓଭର୍ ରାଇଟ୍ କରେ ନାହିଁ। ହାତରେ ଏକ ନମ୍ବର ବାଛନ୍ତୁ ନାହିଁ।
2. **ସୁରକ୍ଷିତ DDL ବ୍ୟବହାର କରନ୍ତୁ।** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **ତଥ୍ୟକୁ ଯତ୍ନର ସହିତ ବ୍ୟାକଫିଲ୍ କରନ୍ତୁ।** : ବିଦ୍ୟମାନ ଧାଡିଗୁଡିକ ପରିଚାଳନା କରିବାକୁ `UPDATE ... WHERE ...` ବ୍ୟବହାର କରନ୍ତୁ।
4. **କ୍ରମ ଏବଂ ନାମକରଣ ଯାଞ୍ଚ କରନ୍ତୁ।** : `npm run test:migrations:fresh` (ଏକ ଖାଲି ଡାଟାବେସରେ ସମସ୍ତ ସ୍ଥାନାନ୍ତରଣ) ଏବଂ `npm run check:migration-numbering`
5. **ଏକ କପି ଉପରେ ପରୀକ୍ଷା କରନ୍ତୁ।** : ଉତ୍ପାଦନରେ କଦାପି ପରୀକ୍ଷିତ ସ୍ଥାନାନ୍ତରଣ ଚଲାନ୍ତୁ ନାହିଁ।

ଉଦାହରଣ:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **ପଛୁଆ-ଅସଙ୍ଗତ ପରିବର୍ତ୍ତନ।** (ଉଦାହରଣ ସ୍ୱରୂପ, ସ୍ତମ୍ଭଗୁଡିକ ପକାଇବା) ଚତୁର ଅଟେ। OmniRoute ଏକ ସ୍ଥାନାନ୍ତରଣ ପ୍ରୟୋଗ ହେବା ପରେ NOT ଡାଉନଗ୍ରେଡ୍ — କୁ ସମର୍ଥନ କରେ, ସ୍କିମା ପରିବର୍ତ୍ତନ ସ୍ଥାୟୀ ଅଟେ। ସେହି ଅନୁଯାୟୀ ଯୋଜନା କରନ୍ତୁ।

## ସଂରକ୍ଷିତ ଅବସ୍ଥାରେ ଏନ୍କ୍ରିପ୍ସନ୍

ସମ୍ବେଦନଶୀଳ ଫିଲ୍ଡଗୁଡ଼ିକ (API କୀ, OAuth ଟୋକନ୍, କନେକ୍ସନ୍ ଷ୍ଟ୍ରିଙ୍ଗ୍) ସଂରକ୍ଷିତ ଅବସ୍ଥାରେ **AES-256-GCM** ବ୍ୟବହାର କରି ଏନ୍କ୍ରିପ୍ଟ କରାଯାଏ।

### ଏହା କିପରି କାମ କରେ

```ts
// src/lib/db/encryption.ts (ସରଳୀକୃତ)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

- `provider_connections.api_key` — ଆପ୍ଲିକେସନ୍ ସ୍ତରରେ ଏନ୍କ୍ରିପ୍ଟ କରାଯାଏ
- `provider_connections.access_token`, `refresh_token`, `id_token` — ଆପ୍ଲିକେସନ୍ ସ୍ତରରେ ଏନ୍କ୍ରିପ୍ଟ କରାଯାଏ
- `namespace = "secrets"` ଥିବା `key_value` ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ — ଆପ୍ଲିକେସନ୍ ସ୍ତରରେ ଏନ୍କ୍ରିପ୍ଟ କରାଯାଏ
- `proxy_registry.auth` — ଉପସ୍ଥିତ ଥିଲେ ଆପ୍ଲିକେସନ୍ ସ୍ତରରେ ଏନ୍କ୍ରିପ୍ଟ କରାଯାଏ

### ଏନ୍କ୍ରିପ୍ସନ୍ କୀ

ଏନ୍କ୍ରିପ୍ସନ୍ କୀ ଏକ **ପାସ୍ଫ୍ରେଜ୍** (`STORAGE_ENCRYPTION_KEY` env var ମାଧ୍ୟମରେ ସେଟ୍ କରାଯାଏ) ଏବଂ ଏକ **ସଲ୍ଟ** (DB ରେ ସଂରକ୍ଷିତ) ଠାରୁ ଉତ୍ପନ୍ନ କରାଯାଏ। ଡାଟା ଡିକ୍ରିପ୍ଟ କରିବା ପାଇଁ ଉଭୟ ଆବଶ୍ୟକ।

```bash
# ଏକ ସୁରକ୍ଷିତ ପାସ୍ଫ୍ରେଜ୍ ସୃଷ୍ଟି କରନ୍ତୁ
openssl rand -hex 32

# .env ରେ ସେଟ୍ କରନ୍ତୁ
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ**: ଏନ୍କ୍ରିପ୍ସନ୍ କୀ ହରାଇବାର ଅର୍ଥ ହେଉଛି ସମସ୍ତ ଏନ୍କ୍ରିପ୍ଟ ହୋଇଥିବା ଡାଟାକୁ ପ୍ରବେଶ ହରାଇବା। **ଡାଟାବେସ୍ଠାରୁ ଅଲଗା ଭାବରେ କୀର ବ୍ୟାକ୍ଅପ୍ ରଖନ୍ତୁ**।

### କେଉଁଗୁଡ଼ିକ ଏନ୍କ୍ରିପ୍ଟ ହୁଏ ନାହିଁ

କାର୍ଯ୍ୟଦକ୍ଷତାଜନିତ କାରଣରୁ, ନିମ୍ନଲିଖିତଗୁଡ଼ିକୁ ପ୍ଲେନ୍ଟେକ୍ସ୍ଟରେ ସଂରକ୍ଷଣ କରାଯାଏ:

- ପ୍ରଦାନକାରୀଙ୍କ ପ୍ରଦର୍ଶିତ ନାମ
- ମଡେଲ୍ ସଂଜ୍ଞାଗୁଡ଼ିକ (ପୂର୍ବରୁ ସାର୍ବଜନୀନ)
- ରାଉଟିଂ ନିୟମଗୁଡ଼ିକ
- ବ୍ୟବହାର ରେକର୍ଡଗୁଡ଼ିକ (କୌଣସି PII ନାହିଁ)

## କାର୍ଯ୍ୟଦକ୍ଷତା ଟ୍ୟୁନିଂ।

### WAL ମୋଡ୍।

WAL ଡିଫଲ୍ଟ ଭାବରେ ସକ୍ଷମ ହୋଇଛି। ଉଚ୍ଚ-ଲେଖା କାର୍ଯ୍ୟଭାର ପାଇଁ, ବିଚାର କରନ୍ତୁ:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` ସେଟ୍ କରେ ନାହିଁ। ଏକ ଚେକପଏଣ୍ଟ WAL ଫ୍ରେମଗୁଡ଼ିକୁ ମୁଖ୍ୟ ଫାଇଲକୁ ଘୁଞ୍ଚାଏ, କିନ୍ତୁ WAL ଫାଇଲ ଏହାର ସର୍ବ ବୃହତ ଆବଣ୍ଟିତ ଆକାର ରଖେ। `OMNIROUTE_WAL_GUARD_MAX_MB` ରାକ୍ଷୀ କେବଳ `wal_checkpoint(RESTART)` ଚେତାବନୀ ଦେଇଥାଏ। ଏହା ଏକ ଡିସ୍କ ଆକାରର କ୍ୟାପ୍ ନୁହେଁ।

### ସୂଚକାଙ୍କ

କାର୍ଯ୍ୟଦକ୍ଷତା ପାଇଁ ମୁଖ୍ୟ ସୂଚକାଙ୍କ (ସ୍ଥାନାନ୍ତରଣ ଦ୍ୱାରା ସ୍ auto ତ - ସୃଷ୍ଟି):

- ପ୍ରଦାନକାରୀ ଦ୍ୱାରା`idx_models_provider` — ମଡେଲ୍ ସନ୍ଧାନ।
- `idx_combo_targets_combo_id` — କମ୍ବୋ ଲକ୍ଷ୍ୟ ବିସ୍ତାର।
- `idx_usage_history_api_key_timestamp` — ବ୍ୟବହାର ଆନାଲିଟିକ୍ସ।
- `idx_quota_snapshots_api_key_window` — କୋଟା ଟ୍ରାକିଂ।
- `idx_call_logs_timestamp` — କଲ୍ ଲଗ ପ୍ରଶ୍ନଗୁଡ଼ିକ।

ଏକ ନୂତନ ସୂଚକାଙ୍କ ଯୋଡିବାକୁ, ଏକ ସ୍ଥାନାନ୍ତରଣ ସୃଷ୍ଟି କରନ୍ତୁ:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

ବହୁତ ବଡ ଡାଟାବେସ୍ (> 10GB) ପାଇଁ, SQLite pragma ମାଧ୍ୟମରେ ମେମୋରୀ ମ୍ୟାପିଂ ଆଡଜଷ୍ଟ ହୋଇପାରିବ:

| ଫିଲ୍ଡ             | ଅର୍ଥ                                                                                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `issues` ଖାଲି ଥିଲେ `true`। `driver` ଏହାକୁ କେବେ ମଧ୍ୟ ପ୍ରଭାବିତ କରେ ନାହିଁ।                                                                                  |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` ମଧ୍ୟରୁ ଗୋଟିଏ।                                                            |
| `repairedCount`   | ଏହି ଚାଳନ ସମୟରେ ମରାମତି ହୋଇଥିବା ଧାଡ଼ିଗୁଡ଼ିକ; `autoRepair` false ଥିଲେ ସର୍ବଦା `0`।                                                                           |

| `driver.degraded` | ରାଇଟ୍ଗୁଡ଼ିକ ଡାଟାବେସ୍ ଫାଇଲ୍ ଦ୍ୱାରା ସ୍ଥାୟୀ ଭାବେ ସମର୍ଥିତ ନଥିଲେ `true` — `sql.js` WASM ଫଲ୍ବ୍ୟାକ୍ (ସମ୍ପୂର୍ଣ୍ଣ-ଫାଇଲ୍ ସ୍ଥାୟୀକରଣ) କିମ୍ବା ଏକ ଇନ୍-ମେମୋରି ଡାଟାବେସ୍। |

ସମାନ ପେଲୋଡ୍ `omniroute_db_health_check` MCP ଟୁଲ୍ ଦ୍ୱାରା ଫେରାଯାଏ।

କରପ୍ସନ୍ ଚିହ୍ନଟ କରିବା ପାଇଁ `PRAGMA integrity_check` ଚଲାନ୍ତୁ:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ଏହା ପ୍ରିଣ୍ଟ୍ ହେବା ଉଚିତ: ok
```

ଯଦି ଏହା `ok` ବ୍ୟତୀତ ଅନ୍ୟ କିଛି ଫେରାଏ, **ତୁରନ୍ତ ଡାଟାବେସ୍ ବ୍ୟବହାର ବନ୍ଦ କରନ୍ତୁ** ଏବଂ ବ୍ୟାକ୍ଅପ୍ରୁ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ।

## ବିପର୍ଯ୍ୟୟ ପୁନରୁଦ୍ଧାର

### ପରିସ୍ଥିତି 1: WAL ଫାଇଲ୍ ହଜିଯାଇଛି

`-wal` ଫାଇଲ୍ଟି ନାହିଁ, କିନ୍ତୁ `-shm` ଏବଂ ମୁଖ୍ୟ DB ଅକ୍ଷୁଣ୍ଣ ଅଛି:

```bash
# ପରବର୍ତ୍ତୀ ଥର ଖୋଲିଲେ ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନରୁଦ୍ଧାର ହୁଏ
omniroute
```

ଯଦି SQLite ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନରୁଦ୍ଧାର କରିପାରେ ନାହିଁ:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### ପରିସ୍ଥିତି 2: ମୁଖ୍ୟ DB ଫାଇଲ୍ ଦୂଷିତ ହୋଇଛି

ବ୍ୟାକଅପ୍ରୁ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` କେବଳ ଚାଲୁଥିବା ସର୍ଭରରୁ ଏକ ସମ୍ପୂର୍ଣ୍ଣ `.tar.gz` ଆର୍କାଇଭ୍ ଡାଉନଲୋଡ୍ କରେ
(`GET /api/db-backups/exportAll`, ଅପରେଟର୍ ପରିଚୟପତ୍ର ଆବଶ୍ୟକ); ଏହା କିଛି ମଧ୍ୟ ପୁନଃସ୍ଥାପନ କରେ ନାହିଁ।

### ପରିସ୍ଥିତି 3: ଏନ୍କ୍ରିପ୍ସନ୍ କୀ ହଜିଯାଇଛି

କୀ ବିନା **ପୁନରୁଦ୍ଧାର ସମ୍ଭବ ନୁହେଁ**। ଏନ୍କ୍ରିପ୍ଟ ହୋଇଥିବା ଫିଲ୍ଡଗୁଡ଼ିକ ପଢ଼ାଯାଇପାରିବ ନାହିଁ। ନୂତନ ପରିଚୟପତ୍ର ସହିତ ସମସ୍ତ ପ୍ରଦାନକାରୀଙ୍କୁ ମାନୁଆଲ୍ ଭାବେ ପୁନଃ ଯୋଡ଼ନ୍ତୁ।

> **ପ୍ରତିକାର**: ଏନ୍କ୍ରିପ୍ସନ୍ କୀକୁ ସର୍ବଦା ପୃଥକ ଭାବେ ବ୍ୟାକଅପ୍ କରନ୍ତୁ, ଆଦର୍ଶ ଭାବେ ଏକ ପାସୱାର୍ଡ ମ୍ୟାନେଜର୍ କିମ୍ବା KMSରେ।

### ପରିସ୍ଥିତି 4: ଡିସ୍କ ପୂର୍ଣ୍ଣ

SQLite `SQLITE_FULL` ତ୍ରୁଟି ଫେରାଇବ। ଡିସ୍କ ସ୍ଥାନ ଖାଲି କରନ୍ତୁ, ତା’ପରେ:

```bash
# ସ୍ଥାନ ଖାଲି କରିବା ପାଇଁ WAL ଚେକ୍ପଏଣ୍ଟ କରନ୍ତୁ
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## ସାଧାରଣ କାର୍ଯ୍ୟଗୁଡ଼ିକ

### ଏକ ଟେବୁଲ୍ ଯାଞ୍ଚ କରନ୍ତୁ

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### ସମସ୍ତ ଟେବୁଲ୍ରେ ଧାଡ଼ି ସଂଖ୍ୟା ଗଣନା କରନ୍ତୁ

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### ସମସ୍ତ ତଥ୍ୟ ରିସେଟ୍ (ମୋଛି) କରନ୍ତୁ

```bash
# ପ୍ରଥମେ OmniRoute ବନ୍ଦ କରନ୍ତୁ
omniroute stop

# DB ଫାଇଲ୍ ବିଲୋପ କରନ୍ତୁ
rm ~/.omniroute/storage.sqlite*

# ପୁନରାରମ୍ଭ କରନ୍ତୁ (ଖାଲି DB ପୁନଃ ସୃଷ୍ଟି ହେବ)
omniroute
```

ଏକ **ଚୟନାତ୍ମକ** ରିସେଟ୍ ପାଇଁ (ପ୍ରଦାନକାରୀଙ୍କୁ ରଖି, ବ୍ୟବହାର ତଥ୍ୟ ମୋଛନ୍ତୁ):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### ଗୋଟିଏ ଟେବୁଲ୍ ରପ୍ତାନି କରନ୍ତୁ

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## ସମସ୍ୟା ନିବାରଣ

### "ଡାଟାବେସ୍ ଲକ୍ ହୋଇଛି"

ଅନ୍ୟ ଏକ ପ୍ରକ୍ରିୟା ରାଇଟ୍ ଲକ୍ ଧରି ରଖିଛି। ନିମ୍ନଲିଖିତ ମଧ୍ୟରୁ ଗୋଟିଏ କରନ୍ତୁ:

- ଅନ୍ୟ ପ୍ରକ୍ରିୟା ସମାପ୍ତ ହେବା ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରନ୍ତୁ (`lsof | grep storage.sqlite` ଯାଞ୍ଚ କରନ୍ତୁ)
- ଅନ୍ୟ ପ୍ରକ୍ରିୟାକୁ ବନ୍ଦ କରନ୍ତୁ
- ସମସ୍ୟା ଜାରି ରହିଲେ, OmniRoute ପୁନରାରମ୍ଭ କରନ୍ତୁ

### "ଫରେନ୍ କୀ ସୀମାବଦ୍ଧତା ବିଫଳ ହୋଇଛି"

ଏକ ଡୋମେନ୍ ମଡ୍ୟୁଲ୍ ରେଫରେନ୍ସିଆଲ୍ ଇଣ୍ଟେଗ୍ରିଟି ଉଲ୍ଲଂଘନ କରୁଛି। ଯାଞ୍ଚ କରନ୍ତୁ:

- ନିର୍ଭରଶୀଳ ଟେବୁଲ୍ଗୁଡ଼ିକରେ ଅନାଥ ଧାଡ଼ି
- ପ୍ରସାରିତ ହୋଇନଥିବା କ୍ୟାସ୍କେଡିଂ ବିଲୋପ
- ଏକ ଫରେନ୍ କୀ ପରିବର୍ତ୍ତନ କରିଥିବା ସାମ୍ପ୍ରତିକ ମାଇଗ୍ରେସନ୍

ଉଲ୍ଲଂଘନଗୁଡ଼ିକ ଖୋଜିବା ପାଇଁ `PRAGMA foreign_key_check;` ଚଲାନ୍ତୁ।

### "ମେମୋରି ଶେଷ ହୋଇଛି"

SQLiteର ମେମୋରି-ମ୍ୟାପ୍ଡ୍ I/O, OS ସୀମା ଅତିକ୍ରମ କରୁଛି। SQLite pragma ମାଧ୍ୟମରେ ଏହାକୁ ହ୍ରାସ କରନ୍ତୁ:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB ପରିବର୍ତ୍ତେ 128MB
```

କିମ୍ବା ଅକ୍ଷମ କରନ୍ତୁ:

```sql
PRAGMA mmap_size = 0;
```

### "ମାଇଗ୍ରେସନ୍ ମଝିରେ ବିଫଳ ହୋଇଛି"

ମାଇଗ୍ରେସନ୍ଟି ଏକ ଟ୍ରାଞ୍ଜାକ୍ସନ୍ରେ ଚାଲିଥିଲା, ତେଣୁ ଏହା ରୋଲ୍ବ୍ୟାକ୍ ହୋଇଥିବା ଉଚିତ। ଯଦି ହୋଇନାହିଁ:

1. **OmniRoute ବନ୍ଦ କରନ୍ତୁ** (ପରବର୍ତ୍ତୀ ପ୍ରୟାସଗୁଡ଼ିକୁ ରୋକନ୍ତୁ)
2. `sqlite3` ସହିତ **DBର ସ୍ଥିତି ଯାଞ୍ଚ କରନ୍ତୁ**
3. ଆଂଶିକ ମାଇଗ୍ରେସନ୍କୁ **ମାନୁଆଲ୍ ଭାବେ ଠିକ୍ କରନ୍ତୁ**
4. OmniRouteକୁ **ପୁନଃ ଚଲାନ୍ତୁ** (ମାଇଗ୍ରେସନ୍ ପୁଣି ପ୍ରୟାସ କରାଯିବ)

ଏହାକୁ ରୋକିବା ପାଇଁ, ସର୍ବଦା ପ୍ରଥମେ ଏକ କପିରେ ମାଇଗ୍ରେସନ୍ ପରୀକ୍ଷା କରନ୍ତୁ।
