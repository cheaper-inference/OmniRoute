OmniRoute ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ ଏକ 5-ପଦକ୍ଷେପ ବିଶିଷ୍ଟ ଫଲ୍ବ୍ୟାକ୍ ଶୃଙ୍ଖଳା ମାଧ୍ୟମରେ ଏହାର SQLite ଡ୍ରାଇଭର୍ ସମାଧାନ କରେ:

1. **ବଣ୍ଡଲ୍ କରାଯାଇଥିବା `better-sqlite3`** (`package.json`ରେ ଥିବା `dependencies` ମାଧ୍ୟମରେ)
   — ସବୁଠାରୁ ଦ୍ରୁତ, ନେଟିଭ୍ ବାଇନେରୀ, ବିଲ୍ଡ ଟୁଲ୍ ଉପଲବ୍ଧ ଥିଲେ `npm install` ଦ୍ୱାରା ଇନ୍ଷ୍ଟଲ୍ ହୁଏ।

2. **ରନ୍ଟାଇମ୍ରେ ଇନ୍ଷ୍ଟଲ୍ ହୋଇଥିବା `better-sqlite3`** (`~/.omniroute/runtime/`ରେ)
   — ପ୍ରଥମ ଥର ଚାଲିବାବେଳେ ଆବଶ୍ୟକତାନୁସାରେ **କିମ୍ବା** `scripts/build/postinstall.mjs → scripts/postinstall.mjs` ଦ୍ୱାରା ଇନ୍ଷ୍ଟଲ୍ ହୁଏ।
   ଲୋଡ୍ କରିବା ପୂର୍ବରୁ ନେଟିଭ୍ `.node` ମ୍ୟାଜିକ୍ ବାଇଟ୍ଗୁଡ଼ିକୁ (ELF / Mach-O / PE) ବୈଧ କରେ,
   ଯାହା ଦୂଷିତ କିମ୍ବା ଭୁଲ୍ ପ୍ଲାଟଫର୍ମର ବାଇନେରୀଠାରୁ ସୁରକ୍ଷା ଦିଏ।

3. **`node:sqlite`** (Node ≥22.5 stdlib) — କୌଣସି ନେଟିଭ୍ ବିଲ୍ଡ ଆବଶ୍ୟକ ନୁହେଁ; ଉଭୟ
   better-sqlite3 ପଥ ବିଫଳ ହେଲେ ଏହା ବ୍ୟବହୃତ ହୁଏ। ଏହାର ବୈଶିଷ୍ଟ୍ୟ ସେଟ୍ ସୀମିତ।

4. **`sql.js`** (WASM) — ଅନ୍ତିମ ଫଲ୍ବ୍ୟାକ୍। ସବୁଠାରେ କାମ କରେ, କିନ୍ତୁ ଧୀର
   ଏବଂ ସମକାଳୀନ ଭାବେ ଲେଖିବା ପରିବର୍ତ୍ତେ ନିର୍ଦ୍ଦିଷ୍ଟ ବ୍ୟବଧାନରେ ଡାଟା ଲେଖେ।

## ଏତେ ଜଟିଳତା କାହିଁକି?

- **Windows EBUSY**: ଯଦି ପୂର୍ବ ସଂସ୍କରଣର `better_sqlite3.node` କୌଣସି ଚାଲୁଥିବା
  ପ୍ରକ୍ରିୟା ଦ୍ୱାରା ଲକ୍ ହୋଇଥାଏ, ତେବେ `npm install -g omniroute@latest` ବିଫଳ ହୋଇପାରେ। `~/.omniroute/runtime/`ରେ ଥିବା ରନ୍ଟାଇମ୍
  ଇନ୍ଷ୍ଟଲେସନ୍ ଗ୍ଲୋବାଲ୍ npm କ୍ୟାଶ୍କୁ ଏଡ଼ାଇଯାଏ।
- **କୌଣସି ବିଲ୍ଡ ଟୁଲ୍ ନାହିଁ**: କିଛି ପରିବେଶ (VS Build
  Tools ବିନା କର୍ପୋରେଟ୍ Windows, ନ୍ୟୂନତମ Docker ଇମେଜ୍ଗୁଡ଼ିକ) `better-sqlite3` କମ୍ପାଇଲ୍ କରିପାରନ୍ତି ନାହିଁ। ରନ୍ଟାଇମ୍
  ଇନ୍ଷ୍ଟଲର୍ npm ରେଜିଷ୍ଟ୍ରିରୁ ଏକ ପୂର୍ବରୁ ବିଲ୍ଡ ହୋଇଥିବା ବାଇନେରୀ ସମାଧାନ କରେ; ଏହା ବିଫଳ ହେଲେ ମଧ୍ୟ
  ଫଲ୍ବ୍ୟାକ୍ ଡ୍ରାଇଭର୍ଗୁଡ଼ିକ OmniRoute ବୁଟ୍ ହେବା ସୁନିଶ୍ଚିତ କରନ୍ତି।
- **ଏୟାର୍-ଗ୍ୟାପ୍ଡ ସିଷ୍ଟମ୍ଗୁଡ଼ିକ**: npm ରେଜିଷ୍ଟ୍ରି ଉପଲବ୍ଧ ନ ହେଲେ, `node:sqlite`
  କିମ୍ବା `sql.js` ମୌଳିକ କାର୍ଯ୍ୟକ୍ଷମତାର ନିଶ୍ଚିତତା ଦିଏ।

## ମ୍ୟାଜିକ୍-ବାଇଟ୍ ବୈଧତା ଯାଞ୍ଚ

ରନ୍ଟାଇମ୍ରେ ଇନ୍ଷ୍ଟଲ୍ ହୋଇଥିବା `.node` ଫାଇଲ୍କୁ ଲୋଡ୍ କରିବା ପୂର୍ବରୁ OmniRoute ପ୍ରଥମ 8
ବାଇଟ୍ ପଢ଼େ ଏବଂ ଜଣାଶୁଣା ପ୍ଲାଟଫର୍ମ ମ୍ୟାଜିକ୍ଗୁଡ଼ିକ ସହିତ ମେଳ କରେ:

| ପ୍ଲାଟଫର୍ମ             | ବାଇଟ୍ (hex)   | ଲେବଲ୍       |
| --------------------- | ------------- | ----------- |
| Linux                 | `7F 45 4C 46` | `elf`       |
| macOS 64-bit BE       | `FE ED FA CF` | `macho`     |
| macOS 64-bit LE       | `CF FA ED FE` | `macho-le`  |
| macOS fat (universal) | `CA FE BA BE` | `macho-fat` |
| Windows               | `4D 5A` (MZ)  | `pe`        |

ମ୍ୟାଜିକ୍ ମେଳ ନ ଖାଇଲେ → ଫାଇଲ୍ଟିକୁ ଅଣଦେଖା କରାଯାଏ ଏବଂ ଫଲ୍ବ୍ୟାକ୍ ପରବର୍ତ୍ତୀ ପଦକ୍ଷେପକୁ ଜାରି ରହେ।

## ମାନୁଆଲ୍ ନିୟନ୍ତ୍ରଣ

```bash
# ଦ୍ରୁତ CI ଇନ୍ଷ୍ଟଲେସନ୍ ପାଇଁ postinstall ୱାର୍ମ-ଅପ୍ ଏଡ଼ାନ୍ତୁ
OMNIROUTE_SKIP_POSTINSTALL=1 npm install -g omniroute

# ରନ୍ଟାଇମ୍ better-sqlite3କୁ ବାଧ୍ୟତାମୂଳକ ଭାବେ ପୁନଃ-ଇନ୍ଷ୍ଟଲ୍ କରନ୍ତୁ
rm -rf ~/.omniroute/runtime
omniroute  # ପରବର୍ତ୍ତୀ ଥର ଆରମ୍ଭ ହେବାବେଳେ ପୁନଃ-ଇନ୍ଷ୍ଟଲ୍ ହେବ

# କେଉଁ ଡ୍ରାଇଭର୍ ସକ୍ରିୟ ଅଛି ଯାଞ୍ଚ କରନ୍ତୁ
omniroute config db-info  # (ଯଦି CLI କମାଣ୍ଡ ଉପଲବ୍ଧ ଅଛି)
```

## ସମକାଳୀନ ସ୍ଥଗିତତା ନିର୍ଣ୍ଣୟ କରିବା

`better-sqlite3` ସହିତ ସମକାଳୀନ ଆଡାପ୍ଟର୍ ଟାଇମିଂକୁ ସକ୍ରିୟ କରିବା ପାଇଁ ଷ୍ଟାର୍ଟଅପ୍ ପୂର୍ବରୁ `OMNIROUTE_SQLITE_SLOW_MS=200` ସେଟ୍ କରନ୍ତୁ।
ଡିଫଲ୍ଟ ଭାବରେ ଏହା ବନ୍ଦ ଥାଏ। ଅତି କମରେ ସେତିକି ମିଲିସେକେଣ୍ଡ ସମୟ ନେଇଥିବା ଏକ ସମ୍ପୂର୍ଣ୍ଣ ଅପରେସନ୍
ପ୍ରତ୍ୟେକ ଆଡାପ୍ଟର୍ ପାଇଁ ପ୍ରତି ଦଶ ସେକେଣ୍ଡରେ ସର୍ବାଧିକ ଥରେ ଗୋଟିଏ `[SQLITE-SLOW]` ଚେତାବନୀ ନିର୍ଗତ କରେ।
ଚେତାବନୀରେ କେବଳ ଡ୍ରାଇଭର୍, ଅପରେସନ୍ ଶ୍ରେଣୀ
(`prepare`, `get`, `all`, `run`, `exec`, `pragma`, ଟ୍ରାଞ୍ଜାକ୍ସନ୍ କିମ୍ବା ରକ୍ଷଣାବେକ୍ଷଣ), ଏବଂ
ବିତିଥିବା ମିଲିସେକେଣ୍ଡ ରହେ: କୌଣସି SQL, ବାଇଣ୍ଡିଂ, ଧାଡ଼ି, ପଥ କିମ୍ବା ଏକ୍ସେପ୍ସନ୍ ଟେକ୍ସଟ୍ ନୁହେଁ।

ଏହା ଏକ ନିଦାନ ସହାୟତା, କୌଣସି ଟାଇମ୍ଆଉଟ୍ କିମ୍ବା କ୍ୱେରୀ ଅପ୍ଟିମାଇଜେସନ୍ ନୁହେଁ। ଏହା କେବେ ମଧ୍ୟ ଫେରୁ ନଥିବା
ଅପରେସନ୍ର ରିପୋର୍ଟ କରିପାରିବ ନାହିଁ, CPU କାର୍ଯ୍ୟକୁ ଡିସ୍କ ଅପେକ୍ଷାଠାରୁ ପୃଥକ କରିପାରିବ ନାହିଁ, ସଠିକ୍
SQL ଚିହ୍ନଟ କରିପାରିବ ନାହିଁ, କିମ୍ବା କଞ୍ଚା ଡ୍ରାଇଭର୍ ହ୍ୟାଣ୍ଡଲ୍ ମାଧ୍ୟମରେ କରାଯାଇଥିବା ଅପରେସନ୍ଗୁଡ଼ିକୁ ନିରୀକ୍ଷଣ କରିପାରିବ ନାହିଁ।
ଅସମକାଳୀନ ବ୍ୟାକଅପ୍ର ଅବଧିକୁ ଜାଣିଶୁଣି ବାଦ ଦିଆଯାଇଛି; ଅନ୍ୟ SQLite ଡ୍ରାଇଭର୍ଗୁଡ଼ିକୁ
ଏହି ଇଚ୍ଛାଧୀନ ବିକଳ୍ପ ଦ୍ୱାରା ଇନ୍ଷ୍ଟ୍ରୁମେଣ୍ଟ କରାଯାଏ ନାହିଁ। ଭେରିଏବଲ୍କୁ ଅକ୍ଷମ କଲେ ଟାଇମିଂ
ରାପର୍ ବିନା ମୂଳ ଆଡାପ୍ଟର୍ ପୁନଃସ୍ଥାପିତ ହୁଏ। ଡାଟାବେସ୍ ସ୍କିମା କିମ୍ବା ସଞ୍ଚିତ କନଫିଗରେସନ୍ରେ କୌଣସି ପରିବର୍ତ୍ତନ ହୁଏ ନାହିଁ।

`/healthz` ଲ୍ୟାଗ୍ ଚେତାବନୀ ପୂର୍ବ ନମୁନାଠାରୁ ଏପର୍ଯ୍ୟନ୍ତ ଘଟିଥିବା ଇଭେଣ୍ଟ-ଲୁପ୍ର ସର୍ବୋଚ୍ଚ ମାନ ରିପୋର୍ଟ କରେ,
ସମଗ୍ର ଜୀବନକାଳର ହାରାହାରି ନୁହେଁ। କୌଣସି ସ୍ଥଗିତତାକୁ SQLite କିମ୍ବା ଡିସ୍କ ବିଫଳତା ଭାବେ ଦାୟୀ କରିବା ପୂର୍ବରୁ,
ଏହାର ଟାଇମ୍ଷ୍ଟାମ୍ପଗୁଡ଼ିକୁ ଧୀର ଅପରେସନ୍ ଚେତାବନୀ ଏବଂ ହୋଷ୍ଟ/ଷ୍ଟୋରେଜ୍ ମେଟ୍ରିକ୍ସ ସହିତ ସମ୍ପର୍କିତ କରନ୍ତୁ।

## ସନ୍ଦର୍ଭ

କାର୍ଯ୍ୟାନ୍ୱୟନ:

- `bin/cli/runtime/magicBytes.mjs` — ବାଇନେରୀ ମ୍ୟାଜିକ୍-ବାଇଟ୍ ବୈଧତା ଯାଞ୍ଚ ସହାୟକ
- `bin/cli/runtime/sqliteRuntime.mjs` — 5-ପଦକ୍ଷେପ ରନ୍ଟାଇମ୍ ରିଜଲ୍ଭର୍ + ଲେଜି ଇନ୍ଷ୍ଟଲର୍
- `bin/cli/runtime/index.mjs` — ଷ୍ଟାର୍ଟଅପ୍ ଅର୍କେଷ୍ଟ୍ରେଟର୍ (`warmUpRuntimes()`)
- `scripts/postinstall.mjs` — npm ପୋଷ୍ଟ-ଇନ୍ଷ୍ଟଲ୍ ହୁକ୍ (ବିଫଳତା-ଘାତକ ନୁହେଁ ଏପରି ୱାର୍ମ-ଅପ୍)
- `src/lib/db/core.ts` — `ensureDbInitialized()` / `getDriverInfo()` ଏକ୍ସପୋର୍ଟଗୁଡ଼ିକ

## ଏକକ-ଲେଖକ ଟୋପୋଲୋଜି (HA ସମର୍ଥିତ ନୁହେଁ)

ଉପରୋକ୍ତ ଡ୍ରାଇଭର୍ ଫଲ୍ବ୍ୟାକ୍ ଶୃଙ୍ଖଳା ଏବେ ମଧ୍ୟ **ଗୋଟିଏ ପ୍ରକ୍ରିୟା**ରେ ଚାଲେ। ଡିଫଲ୍ଟ SQLite
OmniRoute ହେଉଛି ଏକ **ଏକକ ଲେଖକ**:

- ଏକେ `storage.sqlite` ଫାଇଲ୍ରେ ଦୁଇଟି OmniRoute ରେପ୍ଲିକା ସଂଯୁକ୍ତ କରନ୍ତୁ ନାହିଁ।
- କଣ୍ଟେନର୍ ପୁନଃଚାଳନ, Recreate ଡିପ୍ଲୟ, OOM କିଲ୍, କିମ୍ବା HEALTHCHECK ପୁନଃଚାଳନ
  ପ୍ରଗତିରେ ଥିବା ପ୍ରତ୍ୟେକ SSE ସେସନ୍କୁ ବନ୍ଦ କରିଦିଏ। ଷ୍ଟକ୍ ପଥରେ କୌଣସି ସେସନ୍ ଡ୍ରେନ୍ ନାହିଁ।
- ଧୀର `/healthz`କୁ ମୃତ ଭାବେ ବିବେଚନା କରୁଥିବା ଅର୍କେଷ୍ଟ୍ରେଟର୍ ଲାଇଭ୍ନେସ୍ ଏକମାତ୍ର
  ରେପ୍ଲିକାକୁ ବନ୍ଦ କରିଦେବ। TCP ଲାଇଭ୍ନେସ୍ + HTTP `/healthz` ରେଡିନେସ୍କୁ ପ୍ରାଧାନ୍ୟ ଦିଅନ୍ତୁ। ଦେଖନ୍ତୁ
