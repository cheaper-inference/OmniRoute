ଏହା ପ୍ରତ୍ୟେକ ଗେଟ୍, ଏହା କ’ଣ ଯାଞ୍ଚ କରେ, କେଉଁ CI ଜବ୍ରେ ଏହା ଚାଲେ, ଏହା
ଏକ ରାଚେଟ୍ ବେସ୍ଲାଇନ୍ କିମ୍ବା ଏକ ପାସ୍/ଫେଲ୍ ନୀତି ବ୍ୟବହାର କରେ କି ନାହିଁ, ଏବଂ ଏହା ବିଲ୍ଡ୍କୁ ଅବରୋଧ କରେ କିମ୍ବା କେବଳ ପରାମର୍ଶମୂଳକ—ତାହା ବର୍ଣ୍ଣନା କରେ।

ଏକ ସଂକ୍ଷିପ୍ତ ସାରାଂଶ ଏବଂ ଅନୁମତି-ତାଲିକା ନୀତି ପାଇଁ, `AGENTS.md` ରେ ଥିବା
"ଗୁଣବତ୍ତା ଗେଟ୍ ଏବଂ ରାଚେଟ୍" ବିଭାଗ ଦେଖନ୍ତୁ। ସେହି ସିଷ୍ଟମ୍ର ସମାଲୋଚନାମୂଳକ ମୂଲ୍ୟାଙ୍କନ,
ପରିପକ୍ୱତା ବର୍ଗୀକରଣ ଏବଂ ଟୁଲ୍-ନିରପେକ୍ଷ ପ୍ରତିରୂପଣ ଯୋଜନା ପାଇଁ,
[ଗୁଣବତ୍ତା ଗେଟ୍ ପ୍ଲେବୁକ୍](../ops/QUALITY_GATE_PLAYBOOK.md) ଦେଖନ୍ତୁ।

## ଗେଟ୍ ଇନଭେଣ୍ଟରି ଏବଂ ନିଷ୍ପାଦନ ପ୍ରୋଫାଇଲ୍

### ପ୍ରାର୍ଥୀ ଗ୍ରହଣ

CI ଏବଂ Quality Gates ୱର୍କଫ୍ଲୋ ପ୍ରତ୍ୟେକ ଏକ ସ୍ଥିର ରାୟ ନିର୍ଗତ କରେ: `Gate / CI` ଏବଂ
`Gate / Quality`। ସେମାନଙ୍କର ସଂସ୍କରଣଭିତ୍ତିକ ଗ୍ରହଣ ନୀତି ପ୍ରତ୍ୟେକ ଅପ୍ଷ୍ଟ୍ରିମ୍ ଜବ୍କୁ
ଆବଶ୍ୟକ କିମ୍ବା ପରାମର୍ଶମୂଳକ ଭାବେ ତାଲିକାଭୁକ୍ତ କରେ। ଏକ ପ୍ରଯୁଜ୍ୟ ଆବଶ୍ୟକ ଜବ୍ ସଫଳ ହେବା ଆବଶ୍ୟକ:
ଅନୁପସ୍ଥିତ, ବାତିଲ, ଏଡ଼ାଇ ଦିଆଯାଇଥିବା, ବିଚାରାଧୀନ ଏବଂ ଅଜଣା ଫଳାଫଳ PASS ପ୍ରତିଷ୍ଠା କରିପାରିବ ନାହିଁ। ଏକ ବୈଧ
କେବଳ-ଡକ୍ସ କିମ୍ବା କେବଳ-କ୍ୟାଟାଲଗ୍ ବର୍ଗୀକରଣ ଏକ କୋଡ୍ ଲେନ୍କୁ ଅପ୍ରଯୁଜ୍ୟ କରିପାରେ;
ଏକ ଡ୍ରାଫ୍ଟ PR ଗ୍ରହଣୀୟ ପ୍ରାର୍ଥୀ ନୁହେଁ। ଏକ `hotfix` ଲେବଲ୍ ପ୍ରମାଣ ଆବଶ୍ୟକତାକୁ ଛାଡ଼ କରେ ନାହିଁ।

ଉଭୟ ୱର୍କଫ୍ଲୋ main/release ବ୍ରାଞ୍ଚକୁ ଆସୁଥିବା PR, `main`କୁ ପୁଶ୍, ମାନୁଆଲ୍ ଡିସ୍ପାଚ୍
ଏବଂ ମର୍ଜ୍-ଗ୍ରୁପ୍ ଇଭେଣ୍ଟକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ। ପୁଶ୍, ଡିସ୍ପାଚ୍ ଏବଂ ମର୍ଜ୍-ଗ୍ରୁପ୍ ସମ୍ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାଏ। `release/**`କୁ
ହୋଇଥିବା ପୁଶ୍ ସେଗୁଡ଼ିକୁ ଆରମ୍ଭ କରେ ନାହିଁ (2026-10-18): ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ତାହାର PRରେ ପୂର୍ବରୁ ମ୍ୟାଟ୍ରିକ୍ସ ଚଲାଇସାରିଛି
ଏବଂ ମର୍ଜ୍ ହୋଇଥିବା ସଂଯୋଜନ Release-Greenର କାର୍ଯ୍ୟ (`docs/ops/RUNNER_BOX.md` → ହୋଷ୍ଟେଡ୍ ଲେନ୍)। ଫୋର୍କ୍
ଏବଂ ମର୍ଜ୍ ଗ୍ରୁପ୍ଗୁଡ଼ିକ ସେହି ଜବ୍ ପାଇଁ ହୋଷ୍ଟେଡ୍ ରନର୍ ବ୍ୟବହାର କରନ୍ତି, ଯେଉଁଗୁଡ଼ିକ ଅନ୍ୟଥା ସେଲ୍ଫ୍-ହୋଷ୍ଟେଡ୍
ରନର୍ ଚୟନ କରିଥାନ୍ତା; ରୋଲ୍ଆଉଟ୍ ପୂର୍ବରୁ ପର୍ଯ୍ୟାପ୍ତ ହୋଷ୍ଟେଡ୍ କ୍ଷମତା ଯାଞ୍ଚ କରିବା ଆବଶ୍ୟକ।

ଏକ ସାଧାରଣ PR ଦ୍ରୁତ ଚୟନ ଚଲାଏ। ଗ୍ରହଣ ନୀତିର `full-code` ଏବଂ `full-code-e2e` ଲେନ୍ଗୁଡ଼ିକ
(E2E, ଇଣ୍ଟିଗ୍ରେସନ୍, ପ୍ୟାକେଜ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟ, Electron ସ୍ମୋକ୍, Bun SQLite, ଇକୋସିଷ୍ଟମ୍
ଏବଂ ପ୍ରୋଟୋକଲ୍ କ୍ଲାଏଣ୍ଟ) କେବଳ ଏକ Mergify କ୍ୟୁ ଡ୍ରାଫ୍ଟରେ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ରନ୍ରେ ଚାଲେ:
`gh workflow run ci.yml --ref <branch>`।

### ମର୍ଜ୍ କ୍ୟୁ

`queue` ଲେବଲ୍ ଏକ PRକୁ Mergify କ୍ୟୁ (`.mergify.yml`)କୁ ପଠାଏ। Mergify ଏକ
`mergify/merge-queue/` ବ୍ରାଞ୍ଚରେ ଡ୍ରାଫ୍ଟ PR ଖୋଲେ, CI ସେଠାରେ ସମ୍ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାଏ, ଏବଂ
`Gate / CI`, `Gate / Quality` ଓ `Merge integrity (changelog + generated skills)` ପାସ୍ ହେଲେ ମୂଳ PR ମର୍ଜ୍ ହୁଏ।

Mergify ତାହାର କ୍ୟୁ ସାରାଂଶକୁ ଡ୍ରାଫ୍ଟର ବର୍ଣ୍ଣନାରେ ଲେଖେ, ଏବଂ ଅନ୍ୟ ଆପ୍ଗୁଡ଼ିକ ମଧ୍ୟ ଏହାକୁ ସମ୍ପାଦନ କରିପାରନ୍ତି।
ଏପରି ଡ୍ରାଫ୍ଟରେ ଏକ `pull_request` `edited` ଇଭେଣ୍ଟ ନିଜସ୍ୱ କନ୍କରେନ୍ସି ଗ୍ରୁପ୍
(`-queue-edit-<run_id>`) ନିଏ, ଯାହାଫଳରେ ଏହା ଡ୍ରାଫ୍ଟର ପ୍ରକୃତ ରନ୍କୁ ବାତିଲ କରିପାରେ ନାହିଁ, ଏବଂ ଏହା ଗେଟ୍ ଓ
ମ୍ୟାଟ୍ରିକ୍ସକୁ ଏଡ଼ାଇ ଦିଏ। କେବଳ `Merge integrity` ଏପର୍ଯ୍ୟନ୍ତ ଚାଲେ। ଏଡ଼ାଇ ଦିଆଯାଇଥିବା ଗେଟ୍ ଜବ୍ର ଏକ ଭିନ୍ନ ଚେକ୍ ନାମ ଥାଏ,
କାରଣ Mergify ଏଡ଼ାଇ ଦିଆଯାଇଥିବା `Gate / CI`କୁ ବିଫଳ ଚେକ୍ ଭାବେ ପଢ଼େ ଏବଂ PRକୁ କ୍ୟୁରୁ ବାହାର କରେ।

କ୍ୟୁରୁ ବାହାର ହେବା ପରେ, ଏକ ପୁଶ୍ ସବୁବେଳେ PRକୁ ପୁନଃ କ୍ୟୁରେ ରଖେ ନାହିଁ। ଏଥିରେ `@mergifyio queue` ମନ୍ତବ୍ୟ କରନ୍ତୁ।

ପ୍ରତ୍ୟେକ JSON ରସିଦ୍ ଚେକ୍ଆଉଟ୍ ହୋଇଥିବା SHA, ୱର୍କଫ୍ଲୋ ରନ୍ ଏବଂ ପ୍ରୟାସକୁ ଚିହ୍ନଟ କରେ।
CLI ଏକ ଚେକ୍ଆଉଟ୍/ଇଭେଣ୍ଟ SHA ଅମେଳକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ୱର୍କଫ୍ଲୋ ପରୀକ୍ଷାଗୁଡ଼ିକ ନୀତି ସଦସ୍ୟତାକୁ
ରାୟ ଜବ୍ର `needs` ତାଲିକା ସହ ବାନ୍ଧିଥାଏ, ଯାହାଫଳରେ ଏକ ନୂତନ କିମ୍ବା ଅପସାରିତ ଲେନ୍ ନିରବରେ ଅଦୃଶ୍ୟ ହୋଇପାରେ ନାହିଁ।
ରସିଦ୍ଗୁଡ଼ିକ ନିଜ ୱର୍କଫ୍ଲୋକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ, ପ୍ରକାଶନ, ଡିପ୍ଲୟମେଣ୍ଟ କିମ୍ବା ଏକ ବିଦ୍ୟମାନ
ପରାମର୍ଶମୂଳକ ସ୍କାନର୍ର ଆଭ୍ୟନ୍ତରୀଣ କାର୍ଯ୍ୟକୁ ନୁହେଁ। ବ୍ରାଞ୍ଚ ନିୟମରେ ଉଭୟ ଚେକ୍ ନାମ ସକ୍ରିୟ କରିବା
ଏକ ପୃଥକ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ; ଏହି ଜବ୍ଗୁଡ଼ିକ ଯୋଡ଼ିବା ନିଜେ କୌଣସି ବ୍ରାଞ୍ଚକୁ ସୁରକ୍ଷିତ କରେ ନାହିଁ।

### ସ୍ଥିର ସ୍କାନ୍ ଇନଭେଣ୍ଟରି

ସଂସ୍କରଣଭିତ୍ତିକ npm-ଉପନାମ ଇନଭେଣ୍ଟରି ଏବଂ ସ୍ଥିର-ସ୍କାନ୍ ସଦସ୍ୟତା
`config/quality/gate-manifest.json`ରେ ରହିଛି। `package.json` ସହିତ ସ୍କ୍ରିପ୍ଟ ନାମ ଏବଂ ସଠିକ୍ କମାଣ୍ଡ

#### ଦୁଇଟି ଟାଇପ୍ଚେକ୍ ପ୍ରୋଗ୍ରାମ୍ ଭିନ୍ନ ଉତ୍ତର ଦିଅନ୍ତି

`typecheck:core` ଏବଂ `check:build-typecheck` ଭିନ୍ନ ବିକଳ୍ପ ଅଧୀନରେ ଭିନ୍ନ

ଏଣ୍ଟ୍ରିର ଇମ୍ପୋର୍ଟ ଗ୍ରାଫ୍ ଅନୁସରଣ କରେ, ତେଣୁ ବିଲ୍ଡ ପ୍ରୋଗ୍ରାମ୍ରେ କେବେ ଦେଖାଯାଉ ନଥିବା ଫାଇଲ୍ଗୁଡ଼ିକୁ ମଧ୍ୟ

ର ଅର୍ଥ ଶୂନ୍ୟ ନୁହେଁ**। 26ଟି ଫାଇଲ୍ରୁ `@ts-nocheck` ହଟାଇବା ପରେ
ସେଗୁଡ଼ିକ ମଧ୍ୟରୁ 23ଟି ବିଲ୍ଡ ପ୍ରୋଗ୍ରାମ୍ରେ ତ୍ରୁଟିମୁକ୍ତ ଦେଖାଗଲା; ସେଥିରୁ ଷୋହଳଟିରେ

#### `check-ui-value-drift` — ପୁରୁଣା-ଅନୁବାଦ ଗେଟ୍

ଅନ୍ୟ ଗେଟ୍ଗୁଡ଼ିକ ଗଠନାତ୍ମକ ଭାବେ ଦେଖିପାରୁ ନଥିବା ଏକମାତ୍ର i18n ରିଗ୍ରେସନ୍କୁ ଏହା ଧରେ: ଗୋଟିଏ ଇଂରାଜୀ ମୂଲ୍ୟ
ପୁନଃଲିଖିତ ହୁଏ ଏବଂ _ପୂର୍ବବର୍ତ୍ତୀ_ ଇଂରାଜୀରୁ ପ୍ରସ୍ତୁତ ଅନୁବାଦଗୁଡ଼ିକ ସେହିପରି ରହିଯାଆନ୍ତି, ଫଳରେ
ଅଣ-ଇଂରାଜୀ ବ୍ୟବହାରକାରୀମାନେ ଆତ୍ମବିଶ୍ୱାସପୂର୍ଣ୍ଣ ଭାଷାରେ ଲିଖିତ, କିନ୍ତୁ ଏବେ ଭୁଲ୍ ଥିବା ପାଠ୍ୟ ପଢ଼ିଚାଲନ୍ତି।

ଏହା ବାସ୍ତବରେ ରିଲିଜ୍ ହୋଇଥିଲା। Antigravity ଲଗଇନ୍ ସହାୟକ ଯୋଡ଼ାଯିବା ସମୟରେ (#5203) `oauthModal.googleOAuthWarning` ପୁନଃଲିଖିତ
ହୋଇଥିଲା; **43ଟି ମଧ୍ୟରୁ 39ଟି ଲୋକେଲ୍**ରେ ଅପରେଟର୍ମାନଙ୍କୁ "ସମ୍ପୂର୍ଣ୍ଣ URL କପି କରି ତଳେ ପେଷ୍ଟ କରନ୍ତୁ" ବୋଲି କହୁଥିବା ପାଠ୍ୟ ରହିଯାଇଥିଲା — ଏପରି ଏକ ପ୍ରବାହ ଯାହା ସେହି ପ୍ରଦାତା ପାଇଁ ସମ୍ପୂର୍ଣ୍ଣ ହୋଇପାରେ ନାହିଁ। #8463 ପର୍ଯ୍ୟନ୍ତ ଏହା ଅଲକ୍ଷିତ ରହିଥିଲା, କାରଣ:

- `sync-ui-keys` କେବଳ **ଅନୁପସ୍ଥିତ** କୀଗୁଡ଼ିକୁ ବ୍ୟାକ୍ଫିଲ୍ କରେ, **ପୁରୁଣା** କୀଗୁଡ଼ିକୁ କେବେ ନୁହେଁ;
- `check-ui-keys-coverage` କୀର _ଉପସ୍ଥିତି_ ଗଣନା କରେ, ତେଣୁ ଏକ ପୁରୁଣା ଅନୁବାଦକୁ ଅନ୍ତର୍ଭୁକ୍ତ ବୋଲି ସ୍କୋର୍ କରାଯାଏ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ଡକ୍ୟୁମେଣ୍ଟେସନ୍ ପ୍ରତିରୂପଗୁଡ଼ିକୁ ଟ୍ରାକ୍ କରେ —
  ଏହା କେବେ ମଧ୍ୟ `src/i18n/messages/*.json` ପଢ଼େ ନାହିଁ। 2026-09 ପୁନଃ-ସିଙ୍କ୍ ପରଠାରୁ ଜବ୍ `docs-sync-strict`ରେ ବ୍ଲକିଂ: ଏକ ମୂଳ ଡକ୍ୟୁମେଣ୍ଟ ସମ୍ପାଦନା କରନ୍ତୁ → `npm run i18n:run -- --files=<doc>` (ବିଭାଗ-ସ୍ତରୀୟ, କମ୍ ଖର୍ଚ୍ଚସାଧ୍ୟ)।

**ଡିଫ୍-ସଚେତନ, ବେସ୍ଲାଇନ୍-ସମର୍ଥିତ ନୁହେଁ।** ଏହା ମର୍ଜ୍ ବେସ୍ରେ ଥିବା `en.json`କୁ
ୱର୍କିଂ ଟ୍ରି ସହିତ ତୁଳନା କରେ; ଯେଉଁ ପ୍ରତ୍ୟେକ କୀର ଇଂରାଜୀ ମୂଲ୍ୟ ବଦଳିଛି, ସେଥିପାଇଁ ଯେକୌଣସି ଲୋକେଲ୍ରେ ଅପରିବର୍ତ୍ତିତ
ଅନୁବାଦ ରହିଥିଲେ ତାହା ପୁରୁଣା। ଏହା ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ **ପୂର୍ବରୁ ଥିବା ବକେୟାକୁ ସ୍ଥିର କରେ** — ଦୀର୍ଘକାଳ ଧରି ଥିବା ଏକ ଅନୁବାଦ କେଉଁ ପୁରୁଣା ଇଂରାଜୀରୁ ଆସିଥିଲା, ତାହା ଡିଫ୍ ପ୍ରକାଶ କରିପାରେ ନାହିଁ; ତେଣୁ ଗେଟ୍ କେବଳ ବର୍ତ୍ତମାନର ପରିବର୍ତ୍ତନ ଯାହାକୁ ସ୍ପର୍ଶ କରେ ତାହାକୁ ବିଚାର କରେ। ବିକଳ୍ପଟି (ପ୍ରତି-କୀ ହ୍ୟାଶ୍ ବେସ୍ଲାଇନ୍) ପାଇଁ ପ୍ରାୟ 600 KBର ଏକ ଜେନେରେଟେଡ୍ ଫାଇଲ୍ ଦରକାର ହେବ, ଯାହା ସର୍ବବୃହତ୍ ବିଦ୍ୟମାନ ବେସ୍ଲାଇନ୍ର 3× ଏବଂ ପ୍ରତ୍ୟେକ i18n PRରେ ବଦଳିବ।

## ଅନୁମୋଦିତ-ତାଲିକା ନୀତି

ପୂର୍ବରୁ ଥିବା ଉଲ୍ଲଂଘନ ଯୋଗୁଁ ବିଫଳ ହୋଇପାରୁ ନଥିବା ପ୍ରତ୍ୟେକ ଗେଟ୍ ଏକ ଅପରିବର୍ତ୍ତନୀୟ ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରେ
(ଯଥା, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ନୀତିଟି ହେଉଛି:

**ମୂଳ କାରଣଟି ସମାଧାନ କରନ୍ତୁ; ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲେ ଏବଂ ସେହି PRରେ
ସମାଧାନ କରାଯାଇପାରୁ ନଥିଲେ ମାତ୍ର ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରନ୍ତୁ।**

ଏକ ଅନୁମୋଦିତ-ତାଲିକାରେ ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବାବେଳେ:

1. ଯଥାର୍ଥତାର କାରଣ ସହିତ ଏକ ମନ୍ତବ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ କରନ୍ତୁ।
2. ଟ୍ରାକିଂ ଇସ୍ୟୁକୁ ଉଲ୍ଲେଖ କରନ୍ତୁ (ଯଥା, `// #3498 — ପର୍ଯ୍ୟାୟ 2 ବୈଶିଷ୍ଟ୍ୟ, ଏପର୍ଯ୍ୟନ୍ତ କାର୍ଯ୍ୟକାରୀ କରାଯାଇନାହିଁ`)।
3. ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରୁଥିବା ସେହି PRରେ ଏଣ୍ଟ୍ରିଟି ହଟାନ୍ତୁ — ଆଉ କୌଣସି ସକ୍ରିୟ ଉଲ୍ଲଂଘନକୁ
   ଦମନ କରୁ ନଥିବା ଏକ ଅଚଳ ଏଣ୍ଟ୍ରି ନିଜେ ଏକ ତ୍ରୁଟି (କାର୍ଯ୍ୟକାରୀ ହେବା ପରେ 6A.3 ଅଚଳ-ପ୍ରବର୍ତ୍ତନ
   ଏକ ଅନାଥ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ପାଇଁ ଗେଟ୍କୁ ବିଫଳ କରିବ)।

ପରୀକ୍ଷାଗୁଡ଼ିକୁ ଶୀଘ୍ର ପାସ୍ କରାଇବା ପାଇଁ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ **ନାହିଁ**। ବଢ଼ୁଥିବା
ଅନୁମୋଦିତ-ତାଲିକା ସହିତ ଏକ ସବୁଜ ଗେଟ୍ ଗୁଣବତ୍ତାର ଏକ ମିଥ୍ୟା ଆଶ୍ୱାସନ।

### ଆପଣଙ୍କ PRରେ ଏକ ଗେଟ୍ ବିଫଳ ହେଲେ

1. **ଗେଟ୍ର ଆଉଟପୁଟ୍ ଯତ୍ନର ସହ ପଢ଼ନ୍ତୁ** — କେଉଁ ଫାଇଲ୍ କିମ୍ବା ସିମ୍ବଲ୍ ନିୟମଟି ଉଲ୍ଲଂଘନ କରିଛି, ଏହା ଆପଣଙ୍କୁ ଠିକ୍ ଭାବରେ କହିଥାଏ।
2. **ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରନ୍ତୁ** — ଅଧିକାଂଶ ଗେଟ୍ ନିର୍ଦ୍ଧାରଣାତ୍ମକ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଯାଞ୍ଚ, ଯାହା କୋଡ୍
   ସଠିକ୍ ହେବାମାତ୍ରେ ପାସ୍ ହୋଇଯାଏ।
3. **ଯଦି ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲା** (ଅର୍ଥାତ୍, ଆପଣ ଏହାକୁ ସୃଷ୍ଟି କରିନାହାନ୍ତି, କିନ୍ତୁ ଗେଟ୍ ବର୍ତ୍ତମାନ
   ଏହାକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରୁଛି): ଯଥାର୍ଥତାର ମନ୍ତବ୍ୟ ଏବଂ ଏକ ଟ୍ରାକିଂ ଇସ୍ୟୁ ସହିତ ଏକ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ।
4. **ଯଦି ଗେଟ୍ଟି ଏକ ରାଚେଟ୍ ଅଟେ** (କଭରେଜ୍, ESLint ଚେତାବନୀ, ପୁନରାବୃତ୍ତି, ଜଟିଳତା):
   ଆପଣଙ୍କ ପରିବର୍ତ୍ତନ ମେଟ୍ରିକ୍କୁ ଆହୁରି ଖରାପ କରିଛି। ଅନ୍ତର୍ନିହିତ ସମସ୍ୟାଟି ସମାଧାନ କରନ୍ତୁ, କିମ୍ବା (କ୍ୱଚିତ୍) ପରିବର୍ତ୍ତନଟି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଏବଂ ମେଟ୍ରିକ୍ର
   ଅବନତି ଗ୍ରହଣଯୋଗ୍ୟ ହେଲେ `npm run quality:ratchet -- --update` ଚଲାନ୍ତୁ — କିନ୍ତୁ PR ବିବରଣୀରେ ଏହାର କାରଣ ଲିପିବଦ୍ଧ କରନ୍ତୁ।
5. **ପରାମର୍ଶମୂଳକ ଗେଟ୍ଗୁଡ଼ିକ** (`continue-on-error: true`) କେବଳ ସୂଚନାମୂଳକ — ସେଗୁଡ଼ିକ ମର୍ଜ୍କୁ ଅବରୋଧ
   କରେନାହିଁ, କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଏ। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ 2026-06-17 ରେ ସକ୍ରିୟ ଗେଟ୍ ସ୍ଥିତି ସହିତ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ବିଶ୍ୱାସ କରନ୍ତୁ, କିନ୍ତୁ ଯାଞ୍ଚ ମଧ୍ୟ କରନ୍ତୁ);
ଅନେକ "ସ୍ପଷ୍ଟ" ମର୍ଜ ଋଣ ଲୁଚାଇ ରଖିଥିବା ଜଣାପଡ଼ିଲା ଏବଂ ସେଗୁଡ଼ିକ **ସିଧାସଳଖ ପ୍ରତିସ୍ଥାପନଯୋଗ୍ୟ ନୁହେଁ**।

- **`check:docs-sync` ଦୁଇଥର ଚାଲେ** — `lint` ଜବ୍ରେ ସ୍ୱତନ୍ତ୍ର ଭାବେ ଏବଂ ପୁଣି `check:docs-all` (`docs-sync-strict`) ଭିତରେ ଓ husky pre-commit hook ରେ। ✅ **ସମ୍ପୂର୍ଣ୍ଣ** — ସ୍ୱତନ୍ତ୍ର `lint` ଆହ୍ୱାନ ହଟାଯାଇଛି।
- **CVE ସ୍କାନିଂ** — ❌ **ଏକ ସ୍ୱଚ୍ଛ ମର୍ଜ ନୁହେଁ।** ଯେକୌଣସି high/critical CVE ଥିଲେ `audit:deps` ନିଶ୍ଚିତ ଭାବେ ବିଫଳ ହୁଏ; `check:vuln-ratchet` (osv) କେବଳ ବେସ୍ଲାଇନ୍ ତୁଳନାରେ ଏକ _ଅବନତି_ ହେଲେ ବିଫଳ ହୁଏ (ବର୍ତ୍ତମାନ 1 MODERATE)। ଅର୍ଥବିଜ୍ଞାନ ଭିନ୍ନ — `audit:deps` ବାଦ ଦେଲେ ସମ୍ପୂର୍ଣ୍ଣ high/critical ଗେଟ୍ ହରାଇଯିବ। ଉଭୟକୁ ରଖନ୍ତୁ।
- **ଚକ୍ର ଚିହ୍ନଟ** — ✅ **ସମ୍ପୂର୍ଣ୍ଣ** (#15159 G-01/G-02)। ଏଠାରେ ଥିବା ପୁରୁଣା ପାଠ୍ୟ `check:cycles` କୁ "ସବୁଜ, ସୁବ୍ୟବସ୍ଥିତ" ଗେଟ୍ ବୋଲି କହିଥିଲା ଏବଂ `check:circular-deps` (dpdm) 91ଟି ଚକ୍ର ରିପୋର୍ଟ କରିଥିବାରୁ ଏହାକୁ ବ୍ଲକିଂ ଭାବେ ରଖିବା ଯୁକ୍ତିସଙ୍ଗତ ବୋଲି ଦର୍ଶାଇଥିଲା। ସେହି ସବୁଜ ସ୍ଥିତି ଏକ **ଭୁଲ ସବୁଜ** ଥିଲା: `check:cycles` 5ଟି ସବ୍ଡିରେକ୍ଟୋରୀ (450ଟି ଫାଇଲ୍) ସ୍କାନ୍ କରୁଥିଲା, କେବଳ ସ୍ଥିର `import|export … from` ସହିତ ମେଳ କରୁଥିଲା, ଏବଂ ପ୍ରତ୍ୟେକ `@/` ଓ `@omniroute/open-sse/` ସ୍ପେସିଫାୟର୍କୁ ବାଦ ଦେଉଥିଲା, ତେଣୁ ରିପୋଜିଟୋରୀରେ ପ୍ରାଧାନ୍ୟ ରଖିଥିବା ଡାଇନାମିକ୍-import + alias ଚକ୍ରଗୁଡ଼ିକୁ ଏହା ଦେଖିପାରୁ ନଥିଲା। ସମାଧାନ କରାଯାଇଛି: ଗେଟ୍ଟି ବର୍ତ୍ତମାନ `src` + `open-sse` (5023ଟି ଫାଇଲ୍) ପରିକ୍ରମା କରେ, TypeScript AST ରୁ ସ୍ପେସିଫାୟର୍ଗୁଡ଼ିକ ସଂଗ୍ରହ କରେ (ଫଳରେ `import("…")` ଗଣାଯାଏ ଏବଂ type-position `typeof import("…")` ଗଣାଯାଏ ନାହିଁ), ଏବଂ tsconfig `paths` ସମାଧାନ କରେ। ଏହା 0 ନୁହେଁ, **14**ଟି ଚକ୍ର ଚିହ୍ନଟ କରେ। ଏକ ଗେଟ୍ PR ରେ ପୂର୍ବରୁ ଥିବା 14ଟି ଚକ୍ର ସମାଧାନ କରାଯାଇପାରିବ ନାହିଁ ବୋଲି, `check:cycles` ବର୍ତ୍ତମାନ ଏକ **ରାଚେଟ୍** (`--ratchet`, `quality-baseline.json` ରେ ସୀମା `metrics.cycles.value = 14`, `direction: down`) — ଏହା ଯେକୌଣସି _ଅବନତି_କୁ ଅବରୋଧ କରେ ଏବଂ ଗଣନା କେବଳ କମିପାରେ। CI `npm run check:cycles:ratchet` ଚଲାଏ। କ୍ରମଶଃ ହ୍ରାସ **A-01** ସହିତ ଚାଲିବ। ବ୍ୟାପକ ଦ୍ୱିତୀୟ ମତାମତ ଭାବେ `check:circular-deps` (dpdm) ପରାମର୍ଶମୂଳକ ରହିବ।
- **ଜଟିଳତା** — ✅ **ସମ୍ପୂର୍ଣ୍ଣ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ଗୋଟିଏ ESLint ପରିକ୍ରମା, ruleId ଅନୁଯାୟୀ ଗଣନା କରେ ଯାହାଦ୍ୱାରା cyclomatic+max-lines ଏବଂ cognitive ବେସ୍ଲାଇନ୍ଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହେ; ସ୍ଥାନୀୟ `--update` ପାଇଁ ବ୍ୟକ୍ତିଗତ `check:complexity` / `check:cognitive-complexity` ରହିବ।
- **`/api` ଭ୍ରମବିରୋଧୀ ବ୍ୟବସ୍ଥା** — ✅ **ସମ୍ପୂର୍ଣ୍ଣ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ର ଗୋଟିଏ FS ଇନ୍ଭେଣ୍ଟରୀ, openapi-routes + docs-symbols ଏବେ ମଧ୍ୟ ସ୍ୱାଧୀନ ଭାବେ ରିପୋର୍ଟ କରେ; ସ୍ଥାନୀୟ ଚାଳନା ପାଇଁ ବ୍ୟକ୍ତିଗତଗୁଡ଼ିକ ରହିବ।
- **`check:node-runtime` 11ଟି ଜବ୍ରେ ଚାଲେ** — ⚠️ **କମ୍ ROI।** ପ୍ରତ୍ୟେକଟି ଏକ ପୃଥକ ରନର୍ ଏବଂ ଯାଞ୍ଚଟି <1s; ମୋଟ ସଞ୍ଚୟ ~10s, କିନ୍ତୁ ଏହା ବଦଳରେ ପ୍ରତି-ଜବ୍ର ଏକ ଶସ୍ତା ସୁରକ୍ଷା ବ୍ୟବସ୍ଥା ହରାଇବାକୁ ପଡ଼ିବ। ଏହି ପରିବର୍ତ୍ତନଜନିତ ଅସ୍ଥିରତା ଯୋଗ୍ୟ ନୁହେଁ।
- **CI lint ରେ `typecheck:noimplicit:core`** — ✅ **lint ଜବ୍ରୁ ହଟାଯାଇଛି** (ପୂର୍ବରୁ ପରାମର୍ଶମୂଳକ `continue-on-error` ଥିଲା); ବ୍ଲକିଂ ଟାଇପ୍ ସର୍ଫେସ୍ ହେଉଛି `typecheck:core` + `check:type-coverage`। ସ୍ଥାନୀୟ ସ୍କ୍ରିପ୍ଟ ରଖାଯାଇଛି।

### ଫ୍ଲିପ୍ / ନିଷ୍ପତ୍ତି ନିଅନ୍ତୁ (ଅପରେଟର୍ ନୀତି)

- `check:openapi-security-tiers` (ପରାମର୍ଶମୂଳକ) — ❌ **ସ୍ୱଚ୍ଛ ଭାବେ ଫ୍ଲିପ୍ କରାଯାଇପାରିବ ନାହିଁ।** ଏହା 0 ସହିତ ପ୍ରସ୍ଥାନ କରେ, କିନ୍ତୁ ସତର୍କ କରେ ଯେ `LOCAL_ONLY_API_PREFIXES` ଅଧୀନରେ ଥିବା ଅନେକ `traffic-inspector` ରୁଟ୍ରେ `x-loopback-only: true` ଟୀକା ନାହିଁ। ଏହାକୁ ବାଧ୍ୟତାମୂଳକ କରିବା ପାଇଁ ପ୍ରଥମେ `openapi.yaml` ରେ ସେହି ଟୀକାଗୁଡ଼ିକ ଯୋଡ଼ିବା ଆବଶ୍ୟକ।

- `test:vitest:ui` (ବର୍ତ୍ତମାନ **ବ୍ଲକିଂ**) — ପୂର୍ବରୁ ଥିବା ବିଫଳତାଗୁଡ଼ିକୁ `vitest.config.ts` ରେ `// #8618` ଟ୍ରାକିଂ ମନ୍ତବ୍ୟ ସହିତ ସ୍ପଷ୍ଟ ଭାବେ ବାଦ ଦିଆଯାଇଛି; ନୂତନ ବିଫଳତା ଜବ୍କୁ ବିଫଳ କରେ।
- `check:secrets` (gitleaks, 3ଟି ଡକ୍ୟୁମେଣ୍ଟେଡ୍ false-positive ରେ ସ୍ଥିରୀକୃତ ବ୍ଲକିଂ ରାଚେଟ୍) — 0 ରେ ପହଞ୍ଚିବା ପାଇଁ ସେହି 3ଟିକୁ allowlist କରନ୍ତୁ, କିମ୍ବା ପରାମର୍ଶମୂଳକ ସ୍ତରକୁ ଅବନମିତ କରନ୍ତୁ। GitHub ର ନେଟିଭ୍ secret-scanning + `check:public-creds` ସହିତ ଏହାର ଆଂଶିକ ପୁନରାବୃତ୍ତି ଅଛି।
- `check:pr-evidence` (ବ୍ଲକିଂ, PR-body ଗଦ୍ୟକୁ grep କରେ) — false-positive ହେବାର ଉଚ୍ଚ ବିପଦ; ବାଦ ଦିଆଗଲେ Hard Rule #18 ର ପ୍ରବର୍ତ୍ତନ ଦୁର୍ବଳ ହୁଏ, ତେଣୁ ଏହା ଏକ ପ୍ରକୃତ ନୀତିଗତ ନିଷ୍ପତ୍ତି।
- `semgrep` (ପରାମର୍ଶମୂଳକ ସ୍ୱତନ୍ତ୍ର) — OWASP ପରିବାରଗୁଡ଼ିକ ପାଇଁ CodeQL ସହିତ ପୁନରାବୃତ୍ତି ଅଛି; ଏହାର ବେସ୍ଲାଇନ୍କୁ ଏକ ରାଚେଟ୍ ସହିତ ସଂଯୋଗ କରନ୍ତୁ କିମ୍ବା ବାଦ ଦିଅନ୍ତୁ।
