ପରିପକ୍ୱତା ବର୍ଗୀକରଣ ଏବଂ ଟୁଲ୍-ନିରପେକ୍ଷ ପ୍ରତିରୂପଣ ଯୋଜନା ପାଇଁ,

## ଗେଟ୍ ଇନ୍ଭେଣ୍ଟରି ଏବଂ ନିଷ୍ପାଦନ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ

### ପ୍ରାର୍ଥୀ ଆଡମିଶନ।

CI ଏବଂ କ୍ୱାଲିଟି ଗେଟ୍ସ ୱାର୍କଫ୍ଲୋ ପ୍ରତ୍ୟେକ ଏକ ସ୍ଥିର ରାୟ ନିର୍ଗତ କରେ: `Gate / CI` ଏବଂ `Gate / Quality`। ସେମାନଙ୍କର ସଂସ୍କରଣ ଆଡମିଶନ ନୀତି ପ୍ରତ୍ୟେକ ଅପଷ୍ଟ୍ରିମ କାର୍ଯ୍ୟକୁ ଆବଶ୍ୟକ କିମ୍ବା ପରାମର୍ଶଦାତା ଭାବରେ ଗଣନା କରେ। ଏକ ପ୍ରଯୁଜ୍ୟ ଆବଶ୍ୟକୀୟ କାର୍ଯ୍ୟ ନିଶ୍ଚିତ ଭାବରେ ସଫଳ ହେବ: ନିଖୋଜ, ବାତିଲ୍, ଛାଡି, ବିଚାରାଧୀନ ଏବଂ ଅଜ୍ଞାତ ଫଳାଫଳ PASS ପ୍ରତିଷ୍ଠା କରିପାରିବ ନାହିଁ। ଏକ ବ valid ଧ ଡକସ୍-କେବଳ କିମ୍ବା କାଟାଲଗ୍-କେବଳ ବର୍ଗୀକରଣ ଏକ କୋଡ୍ ଗାଡ଼ି ଅନୁପଯୁକ୍ତ କରିପାରେ। ଏକ ସାଧାରଣ ଡ୍ରାଫ୍ଟ PR ଏକ ଗ୍ରହଣୀୟ ପ୍ରାର୍ଥୀ ନୁହେଁ। ଏକ `hotfix` ଲେବଲ୍ ପ୍ରମାଣ ଛାଡ କରେ ନାହିଁ।

ଉଭୟ ୱାର୍କଫ୍ଲୋ PRs main/release ଶାଖାରେ ଆବୃତ କରେ, `main` କୁ ଠେଲିଥାଏ, ମାନୁଆଲ୍ ପଠାଇବା ଏବଂ ମିଶ୍ରଣ-ଗୋଷ୍ଠୀ ଇଭେଣ୍ଟଗୁଡିକ। ପୁସ୍, ପଠାଇବା ଏବଂ ମିଶ୍ରଣ-ଗୋଷ୍ଠୀ ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାନ୍ତୁ। ଏକ ବିଶ୍ୱସ୍ତ Mergify କ୍ୟୁ ଡ୍ରାଫ୍ଟ ମଧ୍ୟ ପ୍ରଯୁଜ୍ୟ `full-code`/`full-code-e2e` କାର୍ଯ୍ୟଗୁଡିକ ଚଲାଇଥାଏ। ସାଧାରଣ PRs ସେମାନଙ୍କୁ ଛାଡିଦିଅ। ଏକ ମାନୁଆଲ୍ ମିଶ୍ରଣ ପୂର୍ବରୁ, ସଠିକ୍ ପ୍ରାର୍ଥୀଙ୍କ ଉପରେ ସମ୍ପୂର୍ଣ୍ଣ ପଠାନ୍ତୁ। `release/**` କୁ ଠେଲିବା ଏହି କାର୍ଯ୍ୟ ପ୍ରବାହ ଆରମ୍ଭ କରେ ନାହିଁ; ରିଲିଜ୍-ଗ୍ରୀନ୍ ମିଶ୍ରିତ ଆଧାରକୁ ପୃଥକ ଭାବରେ ଦେଖେ (`docs/ops/RUNNER_BOX.md` → ହୋଷ୍ଟେଡ୍ ଗାଡ଼ି)। ଫର୍କସ୍ ଏବଂ ମିଶ୍ରଣ ଗୋଷ୍ଠୀଗୁଡିକ ଚାକିରି ପାଇଁ ହୋଷ୍ଟ ରନର୍ସ ବ୍ୟବହାର କରନ୍ତି ଯାହା ଅନ୍ୟଥା ସ୍ୱ-ହୋଷ୍ଟ ରନର୍ସ ଚୟନ କରେ। ଯଥେଷ୍ଟ ହୋଷ୍ଟ କ୍ଷମତା ରୋଲଆଉଟ୍ ପୂର୍ବରୁ ଯାଞ୍ଚ ହେବା ଜରୁରୀ।

ଏକ ସାଧାରଣ PR ଦ୍ରୁତ ଚୟନ ଚଳାଇଥାଏ। ଆଡମିଶନ ପଲିସିର `full-code` ଏବଂ `full-code-e2e` ଗାଡ଼ିଗୁଡ଼ିକ (E2E, ଏକୀକରଣ, ପ୍ୟାକେଜ୍ ଆର୍ଟିଫାକ୍ଟ, Electron ଧୂଆଁ, Bun SQLite, ଇକୋସିଷ୍ଟମ୍ ଏବଂ ପ୍ରୋଟୋକଲ୍ କ୍ଲାଏଣ୍ଟ) କେବଳ ଏକ ମର୍ଜିଫ୍ କ୍ୟୁ ଡ୍ରାଫ୍ଟରେ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ଚାଲିବାରେ ଚାଲିଥାଏ: `gh workflow run ci.yml --ref <branch>`।

ପ୍ରତ୍ୟେକ JSON ରସିଦ ଯାଞ୍ଚ ହୋଇଥିବା SHA, ୱାର୍କଫ୍ଲୋ ଚଲାଇବା ଏବଂ ପ୍ରୟାସକୁ ଚିହ୍ନଟ କରେ। CLI ଏକ checkout/event SHA ଅସଙ୍ଗତିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ୱାର୍କଫ୍ଲୋ ପରୀକ୍ଷଣ ନୀତି ସଦସ୍ୟତାକୁ ବିଚାରର `needs` ତାଲିକାରେ ବାନ୍ଧେ ତେଣୁ ଏକ ନୂତନ କିମ୍ବା ଅପସାରିତ ଗାଡ଼ି ଚୁପଚାପ୍ ଅଦୃଶ୍ୟ ହୋଇପାରିବ ନାହିଁ। ରସିଦଗୁଡିକ ସେମାନଙ୍କର ନିଜସ୍ୱ କାର୍ଯ୍ୟ ପ୍ରବାହକୁ ଆବୃତ୍ତି କରେ, ପ୍ରକାଶନ, ନିୟୋଜନ କିମ୍ବା ଏକ ବିଦ୍ୟମାନ ପରାମର୍ଶଦାତା ସ୍କାନରର ଆଭ୍ୟନ୍ତରୀଣ ନୁହେଁ। ଶାଖା ନିୟମରେ ଆବଶ୍ୟକ ପ୍ରଯୁଜ୍ୟ ଯାଞ୍ଚ କରିବା ଏକ ପୃଥକ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ; ସେମାନଙ୍କର ଚାକିରୀକୁ ବ୍ୟାଖ୍ୟା କରିବା ନିଜେ ଏକ ଶାଖା ରକ୍ଷା କରେ ନାହିଁ।

`API Route Typecheck` ହେଉଛି ଏକ ସ୍ independent ାଧୀନ କାର୍ଯ୍ୟଧାରା ଯାଞ୍ଚ, ଉଭୟ ଏଗ୍ରିମେଣ୍ଟ୍ ରାୟ ଏବଂ ସ୍ଥାନୀୟ ପୂର୍ଣ୍ଣ ପର୍ଯ୍ୟବେକ୍ଷକଙ୍କ ଷ୍ଟାଟିକ୍ ପ୍ରୋଫାଇଲ୍ ବାହାରେ। ପ୍ରକୃତ ପ୍ରାର୍ଥୀଙ୍କ ପାଇଁ ଏହାର ଫଳାଫଳକୁ ପୃଥକ ଭାବରେ ଯାଞ୍ଚ କରନ୍ତୁ। `.github/workflows/api-route-typecheck.yml` PRs ରେ `main` କିମ୍ବା `release/**` ରେ ଚାଲିଥାଏ, ଶାଖା ପରିବାରକୁ, ମାନୁଆଲ ପଠାଇବା, ଏବଂ `checks_requested` ପ୍ରକାରର `merge_group` ଇଭେଣ୍ଟକୁ ଠେଲିଥାଏ। ଏହାର କ path ଣସି ପଥ ଫିଲ୍ଟର ନାହିଁ। ଗୋଷ୍ଠୀଗୁଡିକ `merge_group.head_sha` ଯାଞ୍ଚ କରନ୍ତୁ; ଅନ୍ୟାନ୍ୟ ଘଟଣା `github.sha` ଯାଞ୍ଚ କରନ୍ତୁ। ସମସ୍ତ ଇଭେଣ୍ଟ ସମାନ API ଡାଇଗ୍ନୋଷ୍ଟିକ୍ ଗେଟ୍ ଏବଂ ଗେଟ୍ ୟୁନିଟ୍ ପରୀକ୍ଷା ବ୍ୟବହାର କରନ୍ତି। PR base retargets ଏକ ନୂତନ ଯାଞ୍ଚ ପାଇଁ ଅନୁରୋଧ କରେ; body/title ସମ୍ପାଦନା କେବଳ ପର୍ଯ୍ୟବେକ୍ଷଣ-ନାମ `Admission not requested / API Route Typecheck` ବ୍ୟବହାର କରେ ଏବଂ ଆଡମିଶନ ଯାଞ୍ଚକୁ ବଦଳାଇ ପାରିବ ନାହିଁ।

### ଗ୍ରହଣ ରିଡ୍ୟୁସର୍ରେ ସଂରକ୍ଷିତ ପ୍ରମାଣ

### ଯାଞ୍ଚ ହୋଇଥିବା CI build କୁ DAST ବ୍ୟବହାର କରେ

ବାଧ୍ୟତାମୂଳକ `dast-smoke` CI job, `build` ପରେ `.github/workflows/dast-smoke.yml` କୁ ଡାକେ। ସମର୍ଥିତ fork PR, release ଲକ୍ଷ୍ୟ କରୁଥିବା PR ଓ merge group ସହିତ build ଅନୁସରଣ କରୁଥିବା ସମାନ code/draft ଚୟନକୁ ଏହା ଅନୁସରଣ କରେ। DAST job ନଥିଲେ, ବିଫଳ କିମ୍ବା ବାତିଲ ହେଲେ, ଅଥବା ଅପ୍ରତ୍ୟାଶିତ ଭାବେ ଛାଡ଼ି ଦିଆଗଲେ `Gate / CI` ଅବରୋଧ ହୁଏ। ପୁନଃବ୍ୟବହାରଯୋଗ୍ୟ workflow-ର ସ୍ୱତନ୍ତ୍ର PR/dispatch trigger ନାହିଁ; manual validation ପାଇଁ CI dispatch ବ୍ୟବହୃତ ହୁଏ, ଯାହା ଫଳରେ build ଓ consumer ଏକେ run ଭିତରେ ରହନ୍ତି।

`scripts/ci/next-build-provenance.mjs`, ସମ୍ପୂର୍ଣ୍ଣ Next artifact କୁ ତାହାର tar digest, repository/event/run, producer attempt, head/base/checkout/tree, workflow ପରିଚୟ, lockfile, ସଠିକ୍ Node version/ABI, platform ଓ bundler ସହିତ ବାନ୍ଧି ପ୍ରମାଣିତ କରେ। DAST, `needs.build.outputs` ରୁ ଅପରିବର୍ତ୍ତନୀୟ artifact ID ବାଛେ ଓ download digest ଯାଞ୍ଚ ବାଧ୍ୟତାମୂଳକ କରେ। ଅନୁମତି ତାଲିକାର ଦୁଇଟି ସଦସ୍ୟକୁ `scripts/ci/unpack-ci-build.py` ମାଧ୍ୟମରେ ବାହାର କରିବା ପୂର୍ବରୁ ZIP hash ସ୍ୱତନ୍ତ୍ର ଭାବେ ଗଣନା କରି producer digest ସହ ମେଳାଏ। Next tree ବାହାର କରିବା ପୂର୍ବରୁ manifest ଓ tar archive ମଧ୍ୟ ସ୍ୱତନ୍ତ୍ର producer output ସହିତ ମେଳ ଖାଇବା ଆବଶ୍ୟକ। Branch-ର ସର୍ବଶେଷ ସଫଳ build କୁ ଏହା କେବେ ଖୋଜେ ନାହିଁ। ID ଓ ସବୁ input ଏବେ ମଧ୍ୟ ମେଳ ଖାଉଥିଲେ partial rerun ସେହି producer attempt କୁ ପୁଣି ବ୍ୟବହାର କରିପାରେ; receipt ଦୁଇଟି attempt କୁ ରେକର୍ଡ କରେ।

Consumer କେବଳ repository ପଢ଼ିବା ଅନୁମତି ଥିବା hosted Linux runner ରେ ଚାଲେ; repository secret ନଥାଏ। Producer ବ୍ୟବହାର କରିଥିବା ସଠିକ୍ Node version ସ୍ଥାପନ କରି, `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` ସହ CLI ତିଆରି କରେ। ଯେକୌଣସି fallback build ପୂର୍ବରୁ standalone server ନଥିବା ସ୍ଥିତିକୁ `scripts/build/standaloneInput.mjs` ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ; ସାଧାରଣ ସ୍ଥାନୀୟ CLI build ସେମାନଙ୍କ ପୂର୍ବ fallback ରଖନ୍ତି। Server readiness, Schemathesis ଓ promptfoo ସବୁ ଅପରିବର୍ତ୍ତିତ 25 ମିନିଟ୍ job ସୀମା ମଧ୍ୟରେ ସଫଳ ହେବା ଦରକାର। Provenance receipt input ପରିଚୟ ଓ bytes ପ୍ରମାଣ କରେ, ସଫଳ DAST scan ନୁହେଁ। Artifact ଅବଧି ଶେଷ, runner ବାଧା କିମ୍ବା scanner ବିଫଳତା ଅସମ୍ପୂର୍ଣ୍ଣ କିମ୍ବା ବିଫଳ ପ୍ରମାଣ ହୋଇ ରହେ; advisory wrapper ମାଧ୍ୟମରେ ଏହାକୁ PASS କରାଯାଇପାରିବ ନାହିଁ।

CI JSONL ଫାଇଲଗୁଡ଼ିକୁ `unit-progress-ci-<run>-<attempt>-<shard>` ନାମରେ ସଂରକ୍ଷଣ କରେ। ଏକ ଜବ୍ ଟାଇମ୍ଆଉଟ୍ ପରବର୍ତ୍ତୀ ଅପଲୋଡ୍କୁ ବାଧା ଦେଇପାରେ; ପୂର୍ବରୁ ନିର୍ଗତ ହୋଇଥିବା ହାର୍ଟବିଟ୍ଗୁଡ଼ିକ ନିଦାନମୂଳକ ପ୍ରମାଣ ଭାବରେ ରହିଥାଏ। ହାର୍ଟବିଟ୍ ଅନୁପସ୍ଥିତ ରହିବା ଏକ ଅବରୋଧିତ କିମ୍ବା ସମାପ୍ତ କରାଯାଇଥିବା ରନର୍ ପ୍ରକ୍ରିୟାକୁ ମଧ୍ୟ ସୂଚାଇପାରେ। ଏହି ରସିଦଗୁଡ଼ିକ ବର୍ତ୍ତମାନର ପରୀକ୍ଷା ଚୟନ, ସମକାଳୀନତା, ସମୟସୀମା ଏବଂ ପ୍ରସ୍ଥାନ ସ୍ଥିତିକୁ ଅପରିବର୍ତ୍ତିତ ରଖେ; ଏଗୁଡ଼ିକ ପ୍ରାର୍ଥୀ-ଗ୍ରହଣ ସମ୍ବନ୍ଧୀୟ ନିଷ୍ପତ୍ତି ନୁହେଁ।

### Merge queue

`queue` ଲେବଲ୍ ଗୋଟିଏ PRକୁ Mergify queue (`.mergify.yml`)କୁ ପଠାଏ। Mergify
ଗୋଟିଏ `mergify/merge-queue/` branchରେ draft PR ଖୋଲେ, CI ସେଠାରେ ସମ୍ପୂର୍ଣ୍ଣ selection ଚଲାଏ, ଏବଂ
`Gate / CI`, `Gate / Quality` ଏବଂ `Merge integrity (changelog + generated skills)` pass ହେଲେ ମୂଳ PR merge ହୁଏ।

Mergify ଏହାର queue summaryକୁ draftର descriptionରେ ଲେଖେ, ଏବଂ ଅନ୍ୟ appଗୁଡ଼ିକ ମଧ୍ୟ ଏହାକୁ edit କରିପାରନ୍ତି।
ଏପରି draftରେ ଗୋଟିଏ `pull_request` `edited` event ନିଜସ୍ୱ concurrency group
(`-queue-edit-<run_id>`) ନିଏ, ତେଣୁ ଏହା draftର ପ୍ରକୃତ runକୁ cancel କରିପାରେ ନାହିଁ, ଏବଂ ଏହା gate ଓ
matrixକୁ skip କରେ। କେବଳ `Merge integrity` ତଥାପି ଚାଲେ। Skip ହୋଇଥିବା gate jobର check name ଅଲଗା,
କାରଣ Mergify ଗୋଟିଏ skip ହୋଇଥିବା `Gate / CI`କୁ failed check ଭାବେ ପଢ଼େ ଏବଂ PRକୁ dequeue କରେ।

ଗୋଟିଏ dequeue ପରେ, push ସର୍ବଦା PRକୁ ପୁନଃ queue କରେ ନାହିଁ। ଏଥିରେ `@mergifyio queue` comment କରନ୍ତୁ।

### ସ୍ଥିର ସ୍କାନ୍ ଇନଭେଣ୍ଟରି

ସଂସ୍କରଣଭିତ୍ତିକ npm-ଆଲିଆସ୍ ଇନଭେଣ୍ଟରି ଏବଂ ଷ୍ଟାଟିକ୍-ସ୍କାନ୍ ସଦସ୍ୟତା
`config/quality/gate-manifest.json`ରେ ରହେ। `package.json` ବିପକ୍ଷରେ ସ୍କ୍ରିପ୍ଟ ନାମ ଏବଂ ସଠିକ୍ କମାଣ୍ଡ
ଯାଞ୍ଚ କରିବା ପାଇଁ `npm run check:gate-manifest` ଚଲାନ୍ତୁ; ଯୋଗ, ଅପସାରଣ ଏବଂ
କମାଣ୍ଡ ଡ୍ରିଫ୍ଟ ଉଭୟ ସ୍ଥାନୀୟ ହୁକ୍ ଏବଂ CIର ପରିବର୍ତ୍ତନ-ବର୍ଗୀକରଣ ଜବ୍ଗୁଡ଼ିକୁ ବିଫଳ କରେ।
ଏକ ଆଲିଆସ୍ ୱର୍କଫ୍ଲୋ ଜବ୍, ମ୍ୟାଟ୍ରିକ୍ସ ଇନ୍ଷ୍ଟାନ୍ସ କିମ୍ବା ପରୀକ୍ଷା କେସ୍ ନୁହେଁ: ଏହି ଗଣନାଗୁଡ଼ିକୁ
ପରସ୍ପର ବଦଳଯୋଗ୍ୟ ଭାବେ ଉପସ୍ଥାପନ କରାଯିବା ଉଚିତ୍ ନୁହେଁ।

ଚୟନିତ ଆଲିଆସ୍ଗୁଡ଼ିକୁ ନିଷ୍ପାଦନ ନକରି ଯାଞ୍ଚ କରିବା ପାଇଁ `npm run quality:scan -- --list` କିମ୍ବା `npm run quality:scan:fast -- --list`
ବ୍ୟବହାର କରନ୍ତୁ। ରନର୍ଟି
npm ଏଣ୍ଟ୍ରିପଏଣ୍ଟକୁ ଆହ୍ୱାନ କରେ, ତେଣୁ ଏହାର ରନ୍ଟାଇମ୍ (ବିନ୍ୟାସିତ ସ୍ଥାନରେ Bun ସହିତ) ସଂରକ୍ଷିତ ରହେ।
ମାନିଫେଷ୍ଟ ସେହି ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ ବାହାରର ଆଲିଆସ୍ଗୁଡ଼ିକୁ ପୃଥକ ଭାବେ ଆହ୍ୱାନ କରାଯାଇଥିବା ଭାବେ ରେକର୍ଡ କରେ, ଏବଂ
କେବଳ-ପଠନୀୟ ସ୍କାନ୍ ପ୍ରୋଫାଇଲ୍ରେ ରକ୍ଷଣାବେକ୍ଷଣ କମାଣ୍ଡଗୁଡ଼ିକ ନିଷିଦ୍ଧ।

ଏହି ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ କେବଳ ଷ୍ଟାଟିକ୍ ସ୍କାନ୍କୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ। ସେଗୁଡ଼ିକ ପ୍ରଡକ୍ଟ ପରୀକ୍ଷା,
କଭରେଜ୍, ପ୍ୟାକେଜିଂ, ବାହ୍ୟ ଯାଞ୍ଚ କିମ୍ବା ଏକ ପ୍ରାର୍ଥୀର ସମ୍ପୂର୍ଣ୍ଣ ରିଲିଜ୍ ଗ୍ରହଣକୁ ପ୍ରମାଣିତ କରେ ନାହିଁ।
ୱର୍କଫ୍ଲୋ ଗ୍ରହଣ ଲିଙ୍କ୍ ହୋଇଥିବା `config/quality/admission-policy.json` ଏବଂ
`scripts/quality/admission-verdict.mjs` ବ୍ୟବହାର କରେ। ରିଲିଜ୍-ଅବଜର୍ଭର୍ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ ପୃଥକ ରହେ;
ସେମାନଙ୍କର ପ୍ରଯୁଜ୍ୟ ଯାଞ୍ଚ ଏବଂ ରସିଦ୍ଗୁଡ଼ିକୁ ସ୍ୱାଧୀନ ଭାବେ ପରୀକ୍ଷା କରନ୍ତୁ। ସମ୍ପୂର୍ଣ୍ଣ ଅବଜର୍ଭର୍ର ଷ୍ଟାଟିକ୍
କମାଣ୍ଡଗୁଡ଼ିକ `config/quality/release-green-static-profile.json`ରେ ଘୋଷିତ, ଯେଉଁଥିରେ
`audit:deps`, ମ୍ୟୁଟେସନ୍-ଟେଷ୍ଟ ଚୟନ ଏବଂ ଅନୁବାଦ ଯାଞ୍ଚ ସାମିଲ। ଲୋଡର୍ଟି npm
କମାଣ୍ଡଗୁଡ଼ିକୁ package.json ଏବଂ ମଡେଲ୍ କରାଯାଇଥିବା CI/Quality ଘୋଷଣା ବିପକ୍ଷରେ ଯାଞ୍ଚ କରେ; ଏହା ଶେଲ୍ ଟୋକେନ୍ଗୁଡ଼ିକୁ ଆର୍ଗୁମେଣ୍ଟ ଭାବରେ ନିଷ୍ପାଦନ କରିବା ପରିବର୍ତ୍ତେ
ଡ୍ରିଫ୍ଟକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଆବଶ୍ୟକ ସ୍କାନର୍ SKIP/INCOMPLETE ଆଉଟ୍ପୁଟ୍
PASS ପ୍ରତିଷ୍ଠା କରିପାରିବ ନାହିଁ। ପ୍ରୋଫାଇଲ୍ଟି ଏହାର ବାହ୍ୟ ବହିଷ୍କରଣଗୁଡ଼ିକୁ ରେକର୍ଡ କରେ ଏବଂ
ହୋଷ୍ଟେଡ୍ କଭରେଜ୍, ପରୀକ୍ଷା ମ୍ୟାଟ୍ରିକ୍ସ, ପ୍ୟାକେଜ୍ କିମ୍ବା ଡିପ୍ଲୟମେଣ୍ଟ ପ୍ରମାଣକୁ ପ୍ରତିସ୍ଥାପିତ କରେ ନାହିଁ। ନିମ୍ନରେ ଥିବା ଗଦ୍ୟ ଇନଭେଣ୍ଟରି
ଏକ ସନ୍ଦର୍ଭ, କୌଣସି ଗେଟ୍ ପ୍ରକୃତରେ ଚାଲିଥିଲା ବୋଲି ପ୍ରମାଣ ନୁହେଁ।

ସ୍କ୍ରିପ୍ଟଗୁଡ଼ିକ `scripts/check/` (ନୀତି ଗେଟ୍ଗୁଡ଼ିକ) ଏବଂ `scripts/quality/` (ରାଚେଟ୍ ଇଞ୍ଜିନ୍) ଅଧୀନରେ ରହେ।
CIର ପ୍ରାମାଣିକ ଉତ୍ସ ହେଉଛି `.github/workflows/ci.yml`।

### ପ୍ରକାଶିତ-ଆଧାର ଡକ୍ୟୁମେଣ୍ଟେସନ୍ର ସ୍ୱାସ୍ଥ୍ୟ

`.github/workflows/i18n-base-health.yml` ଚୟନିତ `main` ଏବଂ `release/v*` ପୁଷ୍ଗୁଡ଼ିକ ପରେ ଓ ମାନୁଆଲ୍ ଡିସ୍ପାଚ୍ ସମୟରେ ଡକ୍ୟୁମେଣ୍ଟେସନ୍ର ସ୍ୱାସ୍ଥ୍ୟ ନିରୀକ୍ଷଣ କରେ। ଏହାର ଫିଲ୍ଟର୍ଗୁଡ଼ିକ ଡକ୍ୟୁମେଣ୍ଟେସନ୍, ରୁଟ୍ Markdown, `llm.txt`, ଅନୁବାଦ ସ୍ଥିତି/ବିନ୍ୟାସ ଏବଂ ପ୍ରାସଙ୍ଗିକ i18n ଟୁଲିଂକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ। ଏକମାତ୍ର `Published base documentation health` ଜବ୍ ହୋଷ୍ଟ କରାଯାଇଥିବା Ubuntu ଏବଂ ପାଞ୍ଚ-ମିନିଟ୍ ସମୟସୀମା ବ୍ୟବହାର କରେ। ଏହା କେବଳ-ପଠନୀୟ ବୈଧୀକରଣ କରେ ଏବଂ ନିର୍ଭରଶୀଳତା ଇନ୍ଷ୍ଟଲେସନ୍, ଅନୁବାଦ କିମ୍ବା ସ୍ଥିତି ଗ୍ରହଣ ବିନା ଏକ ଡାୟାଗ୍ନୋଷ୍ଟିକ୍ ରସିଦ ଲେଖେ।

`scripts/i18n/check-base-health.mjs` ପାଇଁ source-hash, missing-target, target-hash, stale-translation ଏବଂ section-cache ଅସଙ୍ଗତି ଶୂନ୍ୟ ହେବା ଆବଶ୍ୟକ। ଏହା ବର୍ତ୍ତମାନର ମୂଳ ଡକ୍ୟୁମେଣ୍ଟ/ଲୋକେଲ୍ ପରିସର ଏବଂ ତାହାର ରେକର୍ଡ କରାଯାଇଥିବା ଉତ୍ପତ୍ତିକୁ ମଧ୍ୟ ବୈଧ କରେ। ଅବୈଧ ପ୍ରସଙ୍ଗ, ଅସମ୍ପୂର୍ଣ୍ଣ କଭରେଜ୍ କିମ୍ବା ବାଧାପ୍ରାପ୍ତ ଚେକର୍ `INCOMPLETE` ଉତ୍ପନ୍ନ କରେ; ସୁନିଶ୍ଚିତ ଡ୍ରିଫ୍ଟ `FAIL` ଉତ୍ପନ୍ନ କରେ। ଉଭୟ ଏକ ବିଫଳ ପ୍ରସ୍ଥାନ ସ୍ଥିତି ଫେରାନ୍ତି। ରସିଦଟି checkout SHA, workflow, run ଏବଂ attempt ସହିତ ବାନ୍ଧି ରଖାଯାଏ ଏବଂ `i18n-base-health-<sha>-<run>-<attempt>` ଭାବେ ସଂରକ୍ଷିତ ହୁଏ।

ଏହା ପ୍ରକାଶିତ ଆଧାରର ଏକ ସ୍ୱାଧୀନ ପର୍ଯ୍ୟବେକ୍ଷଣ। ଏହା ଏକ PR କିମ୍ବା merge-group ଇଭେଣ୍ଟ, ଆବଶ୍ୟକ PR ଯାଞ୍ଚ, npm ଉପନାମ କିମ୍ବା static-scan ପ୍ରୋଫାଇଲ୍ ସଦସ୍ୟ ଯୋଡ଼େ ନାହିଁ। ବିଦ୍ୟମାନ ଭିନ୍ନତାମୂଳକ PR ନୀତି ଏବଂ ଅନ୍ତର୍ନିହିତ ଚେକର୍ର ପରାମର୍ଶମୂଳକ ବର୍ଗୀକରଣଗୁଡ଼ିକ ପୃଥକ ରହେ। ଏକ ସଫଳ ଅପଲୋଡ୍ ବିଫଳ ସ୍ୱାସ୍ଥ୍ୟ ଫଳାଫଳକୁ PASSରେ ପରିବର୍ତ୍ତନ କରିପାରିବ ନାହିଁ।

#### ଭୁଲିଯାଇଥିବା ଭାଇଭଉଣୀ ପରୀକ୍ଷା ରିପୋର୍ଟ।

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ର ଏକ ପରାମର୍ଶଦାତା ପଦକ୍ଷେପ ଭାବରେ ଚାଲିଥାଏ ଏବଂ ପରୀକ୍ଷା-ପ୍ରଭାବ ମାନଚିତ୍ର ପଛରେ ଆମଦାନୀ ସମାଧାନକାରୀକୁ ପୁନ uses ବ୍ୟବହାର କରେ। ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତିତ ଉତ୍ପାଦନ ମଡ୍ୟୁଲ୍ ପାଇଁ, ଏହା ନିର୍ଣ୍ଣୟକାରୀ `changed module/symbol -> static consumer -> candidate sibling test` ଶୃଙ୍ଖଳା ରିପୋର୍ଟ କରେ ଯେତେବେଳେ ପ୍ରାର୍ଥୀ ପରୀକ୍ଷା ଟାଣ-ଅନୁରୋଧ ଭିନ୍ନରୁ ଅନୁପସ୍ଥିତ ଥାଏ। ମାର୍କଡାଉନ୍ ସାରାଂଶ ଏବଂ JSON ଫଳାଫଳ କ any ଣସି ଅବରୋଧ ରୋଲଆଉଟ୍ ପୂର୍ବରୁ କାଲିବ୍ରେସନ୍ ପାଇଁ `forgotten-sibling-tests` ୱାର୍କଫ୍ଲୋ ଆର୍ଟିଫାକ୍ଟ ଭାବରେ ରଖାଯାଇଛି।

ବ୍ୟାରେଲ୍ ପୁନ - ରପ୍ତାନି ଏବଂ ଗତିଶୀଳ ଆମଦାନୀ କେବଳ ରେଜୋଲୁସନ ଡାଇଗ୍ନୋଷ୍ଟିକ୍ ଅଟେ; ସେମାନେ କଦାପି ଏକ ଅବରୋଧକାରୀ ସନ୍ଧାନ ସୃଷ୍ଟି କରନ୍ତି ନାହିଁ। ସମୀକ୍ଷା ହୋଇଥିବା ବ୍ୟତିକ୍ରମଗୁଡ଼ିକ `config/quality/forgotten-sibling-allowlist.json` ରେ ରୁହନ୍ତି। ପ୍ରତ୍ୟେକ ଏଣ୍ଟ୍ରି ନିଶ୍ଚିତ ଭାବରେ ଗ୍ରାହକ ଏବଂ ପ୍ରାର୍ଥୀ ପରୀକ୍ଷଣର ନାମ ଦେବା, ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ଯୁକ୍ତିଯୁକ୍ତତା ଦେବା, ଏବଂ ଏକ GitHub ଇସୁ କିମ୍ବା ଟାଣ ଅନୁରୋଧକୁ ଲିଙ୍କ୍ କରିବା ଜରୁରୀ। ବିକୃତ ଏଣ୍ଟ୍ରିଗୁଡିକ ବନ୍ଦ ହୋଇଗଲା। ବ୍ୟତିକ୍ରମଗୁଡିକ ଏକ ବିଲୋପିତ ପ୍ରାର୍ଥୀ ପରୀକ୍ଷା କିମ୍ବା ଏକ ଭିନ୍ନତାକୁ ଦମନ କରିପାରିବ ନାହିଁ ଯାହାକି `.skip`/`.todo` ଯୋଗ କରେ। ଧାରଣା ଦୁର୍ବଳ ହେବା ଏବଂ ଅନ୍ୟାନ୍ୟ ମାସ୍କିଂ ସ୍ q ାଧୀନ ଭାବରେ `check:test-masking` ଗେଟକୁ ଅବରୋଧ କରିଥାଏ।

### CodeQL ratchet: candidate admission ଓ repository inventory

ସ୍ପଷ୍ଟ dependency ଶୃଙ୍ଖଳ ମାଧ୍ୟମରେ candidate CodeQL admission ର ଦାୟିତ୍ୱ CI ନିଏ: `codeql-scan`, `codeql.yml` ର ଚାରିଟି ଭାଷା matrix କୁ ଡାକେ; ତାପରେ `codeql-admission`, `node scripts/check/check-codeql-ratchet.mjs --candidate` ଚଲାଏ। `Gate / CI` ଦୁଇଟି ଫଳାଫଳ ଆବଶ୍ୟକ କରେ। Quality ନିଜ ସଂଖ୍ୟାଭିତ୍ତିକ ଯାଞ୍ଚ ରଖେ, କିନ୍ତୁ producer ସମାପ୍ତ ହେବା ପୂର୍ବରୁ scanner କୁ ପଚାରେ ନାହିଁ; କେବଳ `Gate / Quality` ସମ୍ପୂର୍ଣ୍ଣ candidate admission ନୁହେଁ। କେବଳ documentation ବଦଳୁଥିବା candidate ପାଇଁ ମଧ୍ୟ CodeQL ବାଧ୍ୟତାମୂଳକ ରହେ।

`config/quality/codeql-admission-policy.json` ର policy Actions, C/C++, JavaScript/TypeScript ଓ Python ବାଛେ; query suite default, threat model remote ଓ build mode none ମଧ୍ୟ ବାଛେ। Producer preflight ଅପେକ୍ଷାରତ activation ରେକର୍ଡ ଏବଂ ସ୍ପଷ୍ଟ target ତାଲିକା ବାହାରର branch କୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ପ୍ରାରମ୍ଭିକ target ହେଉଛି main ଓ release/v3.8.53; ପରବର୍ତ୍ତୀ release ପାଇଁ ସମୀକ୍ଷିତ onboarding ଆବଶ୍ୟକ। CI ର ବର୍ତ୍ତମାନ ବିସ୍ତୃତ release PR trigger ରହିବ, କିନ୍ତୁ onboarding ହୋଇନଥିବା target ମାପ ନହୋଇଥିବା PASS ପାଇବା ବଦଳରେ extraction ପୂର୍ବରୁ HOLD ଜଣାଏ।

ପ୍ରତ୍ୟେକ matrix job ନିଜ ପ୍ରକୃତ SARIF upload ID, ଭାଷା, category, run ଓ attempt, caller workflow ପରିଚୟ, event ref/head/base/merge SHA ଓ policy hash ରେକର୍ଡ କରେ। ନିର୍ଭରଶୀଳ job କେବଳ ଏହି run ର receipt download କରି artifact digest ଯାଞ୍ଚ କରେ। ସମସ୍ତ ଚାରିଟି category, ସଫଳ producer ଓ ପ୍ରତ୍ୟେକ ନିର୍ଦ୍ଦିଷ୍ଟ upload ର ସମାପ୍ତ processing ଦରକାର। Branch ରେ ସର୍ବଶେଷ ମିଳିଥିବା analysis ବଦଳରେ API ର sarif_id filter ବ୍ୟବହାର କରେ। Partial rerun ଗୁଡ଼ିକ ସମାନ run ଓ candidate ର ପୂର୍ବ attempt ର ସଫଳ category କୁ, ଉତ୍ପାଦନ କରିଥିବା attempt ପରିଚୟ ରଖି, ପୁଣି ବ୍ୟବହାର କରିପାରନ୍ତି; ବର୍ତ୍ତମାନ producer ବିଫଳ ହେଲେ ପୁରୁଣା ସବୁଜ ପ୍ରମାଣ ବ୍ୟବହାର କରିପାରିବ ନାହିଁ।

CodeQL action processing ପାଇଁ ଅପେକ୍ଷା କରେ, କିନ୍ତୁ pin କରାଯାଇଥିବା implementation status ପଢ଼ା ବିଫଳ ହେଲେ କିମ୍ବା ଅପେକ୍ଷା ସୀମା ସରିଲେ ଚେତାବନୀ ଦେଇ ଆଗକୁ ଚାଲିପାରେ। ତେଣୁ admission processing ପୁଣି ଯାଞ୍ଚ କରେ। Category ନଥିବା, processing ଅପେକ୍ଷାରତ ରହିବା, job ବିଫଳ କିମ୍ବା ବାତିଲ ହେବା, ପୁରୁଣା ପରିଚୟ, ଅସମ୍ପୂର୍ଣ୍ଣ pagination କିମ୍ବା API ଉପଲବ୍ଧ ନଥିବା ହେଲେ HOLD ଓ exit 2 ମିଳେ। ସ୍ୱତନ୍ତ୍ର scanner workflow ପାଇଁ ନିର୍ଦ୍ଧାରିତ ଅପେକ୍ଷା ଆଉ ନାହିଁ। Alert query 0 ଦେଇଥିବା ମାତ୍ରେ scan ହୋଇନଥିବା PR ପାସ୍ ହୋଇପାରିବ ନାହିଁ। ମାପିଥିବା ସଂଖ୍ୟା `metrics.codeqlAlerts.value` ଠାରୁ ଅଧିକ ହେଲେ exit 1 ହୁଏ; ଅନ୍ୟ branch ର alert କୁ ଗ୍ରହଣ କରିବା ପାଇଁ baseline ବଢ଼ାଯାଏ ନାହିଁ। [Upload ସ୍ଥିତି ଓ analysis ସନ୍ଧାନ](https://docs.github.com/en/rest/code-scanning/code-scanning).

Receipt upload ଓ analysis ID, category, tool version, ref/SHA, baseline ଓ alert ସଂଖ୍ୟା ରେକର୍ଡ କରେ। SARIF ପରିଚୟ/result ସଂଖ୍ୟା, ସର୍ବନିମ୍ନ rule ସଂଖ୍ୟା ଓ ସଠିକ୍ alert instance ବାଧ୍ୟତାମୂଳକ ରହେ। ଗ୍ରହଣ କରିବା ପୂର୍ବରୁ PR/analysis ପରିଚୟ ପୁଣି ଯାଞ୍ଚ ହୁଏ। ଏହି ଯାଞ୍ଚ ବିନ୍ୟାସ କରାଯାଇଥିବା category coverage ନିଶ୍ଚିତ କରେ, ବାହାର କରାଯାଇଥିବା ପ୍ରତ୍ୟେକ source file ର inventory ନୁହେଁ। C/C++ no-build extraction ଭିତରେ project build ସମୟରେ ଉତ୍ପାଦିତ code ରହେ ନାହିଁ। Source exclusion ର ସମୀକ୍ଷା ଏବେ ମଧ୍ୟ ଦରକାର; contributor attribution ପାଇଁ ତୁଳନାଯୋଗ୍ୟ ସଠିକ୍ base ପ୍ରମାଣ ଆବଶ୍ୟକ।

`codeql-maintenance.yml`, PR/main producer କୁ ନକଲ ନକରି active release push scan ଓ ସାପ୍ତାହିକ schedule ଦିଏ। `nightly-codeql-inventory.yml`, `--strict-measurement` ସହ repository ବ୍ୟାପୀ baseline ଅଲଗା ରଖେ ଏବଂ ମାପ ଉପଲବ୍ଧ ନଥିଲେ ବିଫଳ ହୁଏ। ସ୍ଥାନୀୟ ପୁରୁଣା collector ତ୍ରୁଟି ବିନା ଛାଡ଼ିଦେବା candidate admission ନୁହେଁ। ଯାଞ୍ଚ ହୋଇଥିବା କମ୍ ସମଗ୍ର ସଂଖ୍ୟା ପରେ ସ୍ପଷ୍ଟ `--update` ମାଧ୍ୟମରେ ସୀମା କଠୋର କରାଯାଏ।

Default Setup ବିନ୍ୟାସ ହୋଇଥିବା ବେଳେ Advanced workflow ପ୍ରକାଶ କରିବା ଉଚିତ ନୁହେଁ: GitHub ଏହି ସଂଯୋଗ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ସମୀକ୍ଷିତ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ ପୁଣି ପଢ଼ି ନିଶ୍ଚିତ ହେବା ପର୍ଯ୍ୟନ୍ତ version କରାଯାଇଥିବା policy ଅପେକ୍ଷାରତ ରହେ। ପ୍ରକାଶ ପୂର୍ବରୁ operator repository, head/base/tree, policy/patch/rollback hash ଓ ଦେଖାଯାଇଥିବା setup ସ୍ଥିତିକୁ ନିର୍ଦ୍ଦିଷ୍ଟ କରନ୍ତି; `node scripts/quality/codeql-producer.mjs verify-admin-readback` ଦିଆଯାଇଥିବା expected ଓ actual JSON ରେକର୍ଡ ଯାଞ୍ଚ କରେ। ଏହା ଏକ ବୈଷୟିକ ସୁରକ୍ଷା, operator ଅନୁମୋଦନ କିମ୍ବା ତାଜା readback ଆଣିବାର ବିକଳ୍ପ ନୁହେଁ। PR token କେବେ Administration access ମାଗେ ନାହିଁ। Rollout ଓ ଯେକୌଣସି scanner ପରିବର୍ତ୍ତନ ପାଇଁ ସେହି ଅଲଗା readback ସହ ପ୍ରକୃତ PR, fork ଓ merge-group compatibility ପ୍ରମାଣ ଦରକାର।

Fork ଗୁଡ଼ିକ hosted runner ଓ credential ସଞ୍ଚୟ ନକରୁଥିବା checkout ବ୍ୟବହାର କରନ୍ତି; producer ରେ project install/build ନଥାଏ ଓ repository secret ଉତ୍ତରାଧିକାରରେ ମିଳେ ନାହିଁ। କମ୍ ଅଧିକାର ଥିବା fork token ସହ pull_request ଘଟଣାରେ SARIF upload କୁ GitHub ସମର୍ଥନ କରେ; ପ୍ରଥମ contribution ଚଲାଇବା ପାଇଁ ଅନୁମୋଦନ GitHub policy ହୋଇ ରହେ। ଅବିଶ୍ୱସନୀୟ code ଚଲାଇବାକୁ pull_request_target କେବେ ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ। Migration ସମ୍ପୂର୍ଣ୍ଣ ବୋଲି ଧରିବା ପୂର୍ବରୁ ନିୟନ୍ତ୍ରିତ canary ରେ ପ୍ରକୃତ token permission, analysis_key ଓ ସବୁ category environment ନିଶ୍ଚିତ କରନ୍ତୁ। [Fork upload ନିୟମ](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible),
[ପରସ୍ପର ବିରୋଧୀ setup ପ୍ରଣାଳୀ](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows).

**ଖାରଜ କରିବା ଅପରେଟର୍ଙ୍କ ନିଷ୍ପତ୍ତି (କଠୋର ନିୟମ #14)** — ଖାରଜ ମନ୍ତବ୍ୟରେ ପ୍ରାଯୁକ୍ତିକ
ଯଥାର୍ଥତା ରେକର୍ଡ ନକରି କେବେବି କୌଣସି CodeQL ଆଲର୍ଟ ଖାରଜ କରନ୍ତୁ ନାହିଁ: ଅପ୍ଷ୍ଟ୍ରିମ୍-ପ୍ରୋଟୋକଲ୍

| ଲେଖେ      | `check:file-size --update` ଏବଂ `check:complexity-ratchets --update` (ଉଭୟ ନିର୍ମାଣଗତ ଭାବେ କେବଳ-ହ୍ରାସକାରୀ) |
| ଯାଞ୍ଚ କରେ | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                |
| ପଠାଏ      | release branch ବିରୁଦ୍ଧରେ ସଦା ଅଦ୍ୟତନ ଥିବା ଗୋଟିଏ PR — ବଳପୂର୍ବକ ଅଦ୍ୟତନ ହୁଏ, କେବେବି spam ହୁଏ ନାହିଁ          |

ବ୍ୟାଙ୍କିଙ୍ଗ ପ୍ରତି-push ପରିବର୍ତ୍ତେ batchରେ କରାଯାଏ, କାରଣ ଏଥିରେ କୌଣସି latency ଆବଶ୍ୟକତା ନାହିଁ (8h ମଧ୍ୟରେ
ବ୍ୟାଙ୍କ ହୋଇଥିବା ହ୍ରାସ ଗ୍ରହଣୀୟ), ଯେତେବେଳେ ପ୍ରତି-merge run, merge campaign ସମୟରେ PR branchକୁ ବାରମ୍ବାର
ପୁନଃନିର୍ମାଣ କରିବ ଏବଂ ପ୍ରତ୍ୟେକ ଥର ସମ୍ପୂର୍ଣ୍ଣ ESLint walk ପାଇଁ ମୂଲ୍ୟ ଦେବ। ଚିହ୍ନଟକରଣ pushରେ ଜାରି ରହେ
(`release-green`); କେବଳ ବ୍ୟାଙ୍କିଙ୍ଗକୁ batch କରାଯାଏ।

### ସୁରକ୍ଷା ଯାଞ୍ଚକାରୀ

jobଟି ବିନା ତଦାରଖରେ baselineଗୁଡ଼ିକରେ ଲେଖେ, ତେଣୁ `verify-ratchet-bank.mjs` ହିଁ ଏହାକୁ
ଗ୍ରହଣୀୟ କରେ। ଏହା `HEAD` ବିରୁଦ୍ଧରେ `--update` ପରବର୍ତ୍ତୀ treeର diff କରେ ଏବଂ **କୌଣସି commit ସୃଷ୍ଟି ହେବା
ପୂର୍ବରୁ jobକୁ ବାତିଲ କରେ** — କୌଣସି PR ଖୋଲେ ନାହିଁ — ଯଦି ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ନିମ୍ନୋକ୍ତ ମଧ୍ୟରୁ ଗୋଟିଏ ନୁହେଁ:

- ଗୋଟିଏ `frozen` / `testFrozen` ସାଂଖ୍ୟିକ ଏଣ୍ଟ୍ରି **କମାଯାଇଛି** କିମ୍ବା **ଅପସାରିତ ହୋଇଛି**
- `complexity-baseline.json` → `count` **କମାଯାଇଛି**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **କମାଯାଇଛି**

ଅନ୍ୟ ସବୁକିଛି ବିଫଳ ହୁଏ: ଗୋଟିଏ ସଂଖ୍ୟା ବଢ଼ାଇବା, ଗୋଟିଏ ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବା, `cap`/`testCap` ପରିବର୍ତ୍ତନ କରିବା, କିମ୍ବା
ଗୋଟିଏ `_rebaseline_*` note ବିଲୋପ/ପୁନର୍ଲିଖନ କରିବା (ସେହି noteଗୁଡ଼ିକ ପ୍ରତ୍ୟେକ ceiling କାହିଁକି ଅଛି ତାହାର audit trail
ଏବଂ file entryଗୁଡ଼ିକ ସହିତ ସମାନ `frozen` object ମଧ୍ୟରେ ସଂରକ୍ଷିତ)। ଗୋଟିଏ cap ବଢ଼ାଇପାରୁଥିବା bot
ବର୍ତ୍ତମାନର ସ୍ଥିତିଠାରୁ ନିଶ୍ଚିତ ଭାବେ ଅଧିକ ଖରାପ ହେବ। ରିଗ୍ରେସନ୍
guard: `tests/unit/verify-ratchet-bank.test.ts`।

jobଟି କେବେବି `release/*`କୁ push କରେ ନାହିଁ — ଜଣେ ମଣିଷ PRଟିକୁ merge କରନ୍ତି, ତେଣୁ ଏକ ଖରାପ measurement
ସମୀକ୍ଷା ବିନା land କରିପାରିବ ନାହିଁ।

## ଅନୁମୋଦିତ-ତାଲିକା ନୀତି

ପୂର୍ବରୁ ଥିବା ଉଲ୍ଲଂଘନଗୁଡ଼ିକ ଯୋଗୁଁ ବିଫଳ ହୋଇପାରିବ ନାହିଁ ଏପରି ପ୍ରତ୍ୟେକ ଗେଟ୍ ଏକ ଅପରିବର୍ତ୍ତନୀୟ ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରେ
(ଯଥା, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ନୀତିଟି ହେଉଛି:

**ମୂଳ କାରଣକୁ ସମାଧାନ କରନ୍ତୁ; ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲେ ଏବଂ ସେହି PRରେ
ସମାଧାନ କରାଯାଇପାରୁ ନଥିଲେ ମାତ୍ର ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରନ୍ତୁ।**

ଏକ ଅନୁମୋଦିତ-ତାଲିକାରେ ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବା ବେଳେ:

1. ଯଥାର୍ଥତା ବ୍ୟାଖ୍ୟା କରୁଥିବା ଏକ ମନ୍ତବ୍ୟ ସାମିଲ କରନ୍ତୁ।
2. ଟ୍ରାକିଂ ଇସ୍ୟୁକୁ ଉଲ୍ଲେଖ କରନ୍ତୁ (ଯଥା, `// #3498 — Phase 2 feature, not yet implemented`)।
3. ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରୁଥିବା ସେହି PRରେ ଏଣ୍ଟ୍ରିଟିକୁ ହଟାନ୍ତୁ — ଆଉ କୌଣସି ସକ୍ରିୟ
   ଉଲ୍ଲଂଘନକୁ ଦମନ କରୁ ନଥିବା ଏକ ଅଚଳ ଏଣ୍ଟ୍ରି ନିଜେ ଏକ ତ୍ରୁଟି (6A.3 ଅଚଳ-ପ୍ରବର୍ତ୍ତନ
   କାର୍ଯ୍ୟକାରୀ ହେବା ପରେ ଏକ ଅନାଥ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଗୁଁ ଗେଟ୍ ବିଫଳ ହେବ)।

ପରୀକ୍ଷାଗୁଡ଼ିକୁ ଶୀଘ୍ର ପାସ୍ କରାଇବା ପାଇଁ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି **ଯୋଡ଼ନ୍ତୁ ନାହିଁ**। କ୍ରମଶଃ ବଢ଼ୁଥିବା
ଅନୁମୋଦିତ-ତାଲିକା ସହିତ ଏକ ସଫଳ ଗେଟ୍ ଗୁଣବତ୍ତାର ଏକ ମିଥ୍ୟା ଆଶ୍ୱାସନ।

### ଆପଣଙ୍କ PRରେ ଏକ ଗେଟ୍ ବିଫଳ ହେଲେ

1. **ଗେଟ୍ ଆଉଟପୁଟ୍କୁ ଧ୍ୟାନପୂର୍ବକ ପଢ଼ନ୍ତୁ** — କେଉଁ ଫାଇଲ୍ କିମ୍ବା ସିମ୍ବଲ୍ ନିୟମଟିକୁ ଉଲ୍ଲଂଘନ
   କରିଛି ତାହା ଏହା ଆପଣଙ୍କୁ ସଠିକ୍ ଭାବେ ଜଣାଏ।
2. **ଉଲ୍ଲଂଘନଟିକୁ ସମାଧାନ କରନ୍ତୁ** — ଅଧିକାଂଶ ଗେଟ୍ ନିର୍ଦ୍ଧାରଣାତ୍ମକ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଯାଞ୍ଚ, ଯାହା କୋଡ୍
   ଠିକ୍ ହେବା ମାତ୍ରେ ପାସ୍ ହୁଏ।
3. **ଯଦି ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲା** (ଅର୍ଥାତ୍, ଆପଣ ଏହାକୁ ଆଣି ନଥିଲେ କିନ୍ତୁ ଗେଟ୍ ଏବେ
   ଏହାକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରୁଛି): ଯଥାର୍ଥତା ବ୍ୟାଖ୍ୟା କରୁଥିବା ମନ୍ତବ୍ୟ ଏବଂ ଏକ ଟ୍ରାକିଂ ଇସ୍ୟୁ ସହିତ ଅନୁମୋଦିତ-ତାଲିକାରେ ଏକ ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ।
4. **ଯଦି ଗେଟ୍ଟି ଏକ ରାଚେଟ୍ ଅଟେ** (କଭରେଜ୍, ESLint ଚେତାବନୀ, ନକଲିକରଣ, ଜଟିଳତା):
   ଆପଣଙ୍କ ପରିବର୍ତ୍ତନ ମେଟ୍ରିକ୍କୁ ଆହୁରି ଖରାପ କରିଛି। ମୂଳ ସମସ୍ୟାଟିକୁ ସମାଧାନ କରନ୍ତୁ, କିମ୍ବା (ବିରଳ ପରିସ୍ଥିତିରେ)
   ପରିବର୍ତ୍ତନଟି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଏବଂ ମେଟ୍ରିକ୍ର ଅବନତି ଗ୍ରହଣୀୟ ହୋଇଥିଲେ `npm run quality:ratchet -- --update` ଚଲାନ୍ତୁ — କିନ୍ତୁ PR ବର୍ଣ୍ଣନାରେ ଏହାର କାରଣ ଲିପିବଦ୍ଧ କରନ୍ତୁ।
5. **ପରାମର୍ଶମୂଳକ ଗେଟ୍ଗୁଡ଼ିକ** (`continue-on-error: true`) କେବଳ ସୂଚନା ପାଇଁ — ସେଗୁଡ଼ିକ
   ମର୍ଜ୍କୁ ଅବରୋଧ କରନ୍ତି ନାହିଁ, କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଆନ୍ତି। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

## ଏକ ନୂତନ ଗେଟ୍ ଯୋଡ଼ିବା

1. `scripts/check/check-<name>.mjs` (କିମ୍ବା `.ts`) ସୃଷ୍ଟି କରନ୍ତୁ। ନୀତି ଗେଟ୍ଗୁଡ଼ିକ 0/1 ଏକ୍ସିଟ୍ କରନ୍ତି।
   ରାଚେଟ୍-ଶୈଳୀର ଗେଟ୍ଗୁଡ଼ିକ `collect-metrics.mjs` ମାଧ୍ୟମରେ `quality-metrics.json`କୁ ଏକ ମେଟ୍ରିକ୍ ନିର୍ଗତ କରନ୍ତି।
2. `package.json`ରେ `"check:<name>": "node scripts/check/check-<name>.mjs"` ଯୋଡ଼ନ୍ତୁ, ଏବଂ
   `config/quality/gate-manifest.json`ରେ ଉପନାମ ଓ ଏହାର ସଠିକ୍ କମାଣ୍ଡକୁ ସମନ୍ୱୟ କରନ୍ତୁ।
   କୌଣସି ବିଦ୍ୟମାନ ବୈଧତା ଯାଞ୍ଚ ଉପନାମକୁ ପରିବର୍ତ୍ତନ କିମ୍ବା ଅପସାରଣ କରିବା ସମୟରେ ମଧ୍ୟ ସମାନ ସମନ୍ୱୟ ପ୍ରୟୋଗ କରନ୍ତୁ।
   `npm run check:gate-manifest` ଚଲାନ୍ତୁ; pre-commit hook ଏବଂ CI ପରିବର୍ତ୍ତନ ବର୍ଗୀକରଣ
   ଏହି ଚୁକ୍ତିକୁ ବାଧ୍ୟତାମୂଳକ କରେ।
3. ଉପଯୁକ୍ତ ଜବ୍ର ଅଧୀନରେ `.github/workflows/ci.yml`ରେ ଏହାକୁ ସଂଯୋଗ କରନ୍ତୁ
   (ନୀତି → `lint` କିମ୍ବା `docs-sync-strict`; ରାଚେଟ୍ → `quality-gate`)।
4. ଯଦି ଏହାର ଏକ ଅନୁମୋଦିତ-ତାଲିକା ଅଛି, ତେବେ ଅଚଳ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବେ ଚିହ୍ନଟ ହେବା ପାଇଁ
   `scripts/check/lib/allowlist.mjs`ରୁ `reportStaleEntries()` ପ୍ରୟୋଗ କରନ୍ତୁ।
5. ଗେଟ୍ର ଚିହ୍ନଟ ତର୍କକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରି `tests/unit/build/`ରେ ଏକ ପରୀକ୍ଷା ଲେଖନ୍ତୁ।
6. ଏହି ଡକ୍ୟୁମେଣ୍ଟ୍କୁ ଅଦ୍ୟତନ କରନ୍ତୁ (ସମ୍ପର୍କିତ ଜବ୍ ଟେବୁଲ୍ରେ ଏକ ଧାଡ଼ି ଯୋଡ଼ନ୍ତୁ)।

### ମର୍ଜ / ଡିଡ୍ୟୁପ୍ (ଯାନ୍ତ୍ରିକ, କମ୍ ବିପଦ)

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ 2026-06-17 ରେ ସକ୍ରିୟ ଗେଟ୍ ସ୍ଥିତି ବିପକ୍ଷରେ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ବିଶ୍ୱାସ କରନ୍ତୁ, କିନ୍ତୁ ଯାଞ୍ଚ ମଧ୍ୟ କରନ୍ତୁ);
ଅନେକ “ସ୍ପଷ୍ଟ” ମର୍ଜ ଋଣ ଲୁଚାଇଥିବା ଜଣାପଡ଼ିଲା ଏବଂ ସେଗୁଡ଼ିକ **ସିଧାସଳଖ ପ୍ରତିସ୍ଥାପନଯୋଗ୍ୟ ନୁହେଁ**।

- **`check:docs-sync` ଦୁଇଥର ଚାଲେ** — `lint` ଜବ୍ରେ ସ୍ୱତନ୍ତ୍ର ଭାବେ ଏବଂ ପୁଣି `check:docs-all` (`docs-sync-strict`) ଭିତରେ ଓ husky pre-commit hook ରେ। ✅ **ସମ୍ପନ୍ନ** — ସ୍ୱତନ୍ତ୍ର `lint` ଆହ୍ୱାନ ଅପସାରିତ।
- **CVE ସ୍କାନିଂ** — ❌ **ଏକ ସ୍ୱଚ୍ଛ ମର୍ଜ ନୁହେଁ।** `audit:deps` ସମସ୍ତ ପାଞ୍ଚଟି lockfile ମଧ୍ୟରେ ଗୁରୁତର ପରାମର୍ଶ ଏବଂ ଅସମ୍ପୂର୍ଣ୍ଣ ଅଡିଟ୍କୁ ବ୍ଲକ୍ କରେ, ଯେତେବେଳେ ବର୍ତ୍ତମାନର ନୀତି ଅନୁଯାୟୀ ଉଚ୍ଚ-ଗୁରୁତ୍ୱର ପରାମର୍ଶଗୁଡ଼ିକୁ ଚେତାବନୀ ଭାବେ ରିପୋର୍ଟ କରେ; `check:vuln-ratchet` (osv) କେବଳ ଚେକ୍-ଇନ୍ ହୋଇଥିବା ବେସ୍ଲାଇନ୍ ତୁଳନାରେ ଏକ _ଅବନତି_ ହେଲେ ବିଫଳ ହୁଏ ଏବଂ ଆବଶ୍ୟକ ସମୟରେ ଅନୁପସ୍ଥିତ ମାପକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଅର୍ଥବିଜ୍ଞାନ ଭିନ୍ନ — `audit:deps` କୁ ଡ୍ରପ୍ କଲେ ପରମ ଗୁରୁତର ଗେଟ୍ ଏବଂ ସ୍ୱାଧୀନ ପ୍ୟାକେଜ୍ ଅଡିଟ୍ ପ୍ରମାଣ ହରାଇବ। ଉଭୟକୁ ରଖନ୍ତୁ।
- **ଚକ୍ର ଚିହ୍ନଟ** — ✅ **ସମ୍ପନ୍ନ** (#15159 G-01/G-02)। ଏଠାରେ ଥିବା ପୁରୁଣା ପାଠ୍ୟ `check:cycles` କୁ “ସବୁଜ, ସୁନିର୍ବାଚିତ” ଗେଟ୍ ବୋଲି କହିଥିଲା ଏବଂ `check:circular-deps` (dpdm) 91ଟି ଚକ୍ର ରିପୋର୍ଟ କରିଥିବାରୁ ଏହାକୁ ବ୍ଲକିଂ ରଖିବାକୁ ଯୁକ୍ତିସଙ୍ଗତ କରିଥିଲା। ସେହି ସବୁଜ ସ୍ଥିତି ଏକ **ମିଥ୍ୟା ସବୁଜ** ଥିଲା: `check:cycles` 5ଟି ସବ୍ଡିରେକ୍ଟୋରି (450ଟି ଫାଇଲ୍) ସ୍କାନ୍ କରିଥିଲା, କେବଳ ସ୍ଥିର `import|export … from` ସହିତ ମେଳ କରିଥିଲା, ଏବଂ ପ୍ରତ୍ୟେକ `@/` ଓ `@omniroute/open-sse/` ସ୍ପେସିଫାୟର୍କୁ ବାଦ ଦେଇଥିଲା, ତେଣୁ ଏହା ରିପୋଜିଟୋରିରେ ପ୍ରାଧାନ୍ୟ ବିସ୍ତାର କରିଥିବା ଡାଇନାମିକ୍-ଇମ୍ପୋର୍ଟ + ଆଲିଆସ୍ ଚକ୍ରଗୁଡ଼ିକୁ ଦେଖିପାରୁନଥିଲା। ସମାଧାନ କରାଗଲା: ଗେଟ୍ ବର୍ତ୍ତମାନ `src` + `open-sse` (5023ଟି ଫାଇଲ୍) ମଧ୍ୟରେ ବିଚରଣ କରେ, TypeScript AST ରୁ ସ୍ପେସିଫାୟର୍ ସଂଗ୍ରହ କରେ (ଫଳରେ `import("…")` ଗଣାଯାଏ ଏବଂ ଟାଇପ୍-ସ୍ଥିତିର `typeof import("…")` ଗଣାଯାଏ ନାହିଁ), ଏବଂ tsconfig `paths` କୁ ସମାଧାନ କରେ। ଏହା 0 ନୁହେଁ, **14**ଟି ଚକ୍ର ଖୋଜେ। ଏକ ଗେଟ୍ PR ରେ ପୂର୍ବରୁ ଥିବା 14ଟି ଚକ୍ରକୁ ସମାଧାନ କରାଯାଇପାରିବ ନାହିଁ ବୋଲି `check:cycles` ବର୍ତ୍ତମାନ ଏକ **ରାଚେଟ୍** (`--ratchet`, `quality-baseline.json` ରେ ସୀମା `metrics.cycles.value = 14`, `direction: down`) — ଏହା ଯେକୌଣସି _ଅବନତି_ କୁ ବ୍ଲକ୍ କରେ ଏବଂ ସଂଖ୍ୟା କେବଳ କମିପାରିବ। CI `npm run check:cycles:ratchet` ଚଲାଏ। କ୍ରମାଗତ ହ୍ରାସ **A-01** ସହିତ ଚାଲିବ। `check:circular-deps` (dpdm) ଏକ ବ୍ୟାପକ ଦ୍ୱିତୀୟ ମତ ଭାବେ ପରାମର୍ଶମୂଳକ ରହିବ।
- **ଜଟିଳତା** — ✅ **ସମ୍ପନ୍ନ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ଗୋଟିଏ ESLint ବିଚରଣ, ruleId ଅନୁଯାୟୀ ଗଣନା କରେ ଯାହାଦ୍ୱାରା cyclomatic+max-lines ଏବଂ cognitive ବେସ୍ଲାଇନ୍ଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହେ; ପୃଥକ `check:complexity` / `check:cognitive-complexity` ସ୍ଥାନୀୟ `--update` ପାଇଁ ରହିଥାଏ।
