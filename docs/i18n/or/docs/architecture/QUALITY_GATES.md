ଏହି ଡକ୍ୟୁମେଣ୍ଟଟି OmniRoute ର ସମସ୍ତ CI ଗୁଣବତ୍ତା ଗେଟ୍ ପାଇଁ ପ୍ରାମାଣିକ ସନ୍ଦର୍ଭ।
ଏହା ପ୍ରତ୍ୟେକ ଗେଟ୍, ଏହା କ’ଣ ଯାଞ୍ଚ କରେ, କେଉଁ CI ଜବ୍ରେ ଏହା ଚାଲେ, ଏହା
ଏକ ରାଚେଟ୍ ବେସ୍ଲାଇନ୍ କିମ୍ବା ଏକ ପାସ୍/ଫେଲ୍ ନୀତି ବ୍ୟବହାର କରେ କି ନାହିଁ, ଏବଂ ଏହା ବିଲ୍ଡ୍କୁ ଅବରୋଧ କରେ କିମ୍ବା କେବଳ ପରାମର୍ଶମୂଳକ—ତାହା ବର୍ଣ୍ଣନା କରେ।

ଏକ ସଂକ୍ଷିପ୍ତ ସାରାଂଶ ଏବଂ ଅନୁମତି-ତାଲିକା ନୀତି ପାଇଁ, `AGENTS.md` ରେ ଥିବା
"ଗୁଣବତ୍ତା ଗେଟ୍ ଏବଂ ରାଚେଟ୍" ବିଭାଗ ଦେଖନ୍ତୁ। ସେହି ସିଷ୍ଟମ୍ର ସମାଲୋଚନାମୂଳକ ମୂଲ୍ୟାଙ୍କନ,
ପରିପକ୍ୱତା ବର୍ଗୀକରଣ ଏବଂ ଟୁଲ୍-ନିରପେକ୍ଷ ପ୍ରତିରୂପଣ ଯୋଜନା ପାଇଁ,
[ଗୁଣବତ୍ତା ଗେଟ୍ ପ୍ଲେବୁକ୍](../ops/QUALITY_GATE_PLAYBOOK.md) ଦେଖନ୍ତୁ।

## ଗେଟ୍ ଇନଭେଣ୍ଟରି ଏବଂ ଏକ୍ଜିକ୍ୟୁସନ୍ ପ୍ରୋଫାଇଲ୍

### ପ୍ରାର୍ଥୀ ଭର୍ତ୍ତି

CI ଏବଂ Quality Gates ୱର୍କଫ୍ଲୋ ପ୍ରତ୍ୟେକଟି ଏକ ସ୍ଥିର ନିଷ୍ପତ୍ତି ପ୍ରକାଶ କରେ: `Gate / CI` ଏବଂ
`Gate / Quality`। ସେମାନଙ୍କର ସଂସ୍କରଣ-ନିୟନ୍ତ୍ରିତ ଭର୍ତ୍ତି ନୀତି ପ୍ରତ୍ୟେକ ଅପ୍ଷ୍ଟ୍ରିମ୍ ଜବ୍କୁ ଆବଶ୍ୟକ କିମ୍ବା ପରାମର୍ଶମୂଳକ ଭାବେ ତାଲିକାଭୁକ୍ତ କରେ। ପ୍ରୟୋଜ୍ୟ ଆବଶ୍ୟକ ଜବ୍ ସଫଳ ହେବା ଦରକାର: ଅନୁପସ୍ଥିତ, ବାତିଲ, ସ୍କିପ୍, ଅପେକ୍ଷାରତ ଏବଂ ଅଜଣା ଫଳାଫଳ PASS ସ୍ଥାପନ କରିପାରେ ନାହିଁ। ବୈଧ docs-only କିମ୍ବା catalog-only ବର୍ଗୀକରଣ ଏକ code lane କୁ ପ୍ରୟୋଜ୍ୟ ନୁହେଁ ବୋଲି ଦର୍ଶାଇପାରେ; draft PR ଗ୍ରହଣଯୋଗ୍ୟ ପ୍ରାର୍ଥୀ ନୁହେଁ। `hotfix` ଲେବଲ୍ ପ୍ରମାଣକୁ ଛାଡ଼ ଦେଇନଥାଏ।

ଉଭୟ ୱର୍କଫ୍ଲୋ main/release ବ୍ରାଞ୍ଚକୁ ଯାଉଥିବା PR, `main` କୁ push, manual dispatch
ଏବଂ merge-group ଇଭେଣ୍ଟକୁ ଆବୃତ କରେ। Push, dispatch ଏବଂ merge-group ସମ୍ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାଏ। `release/**` କୁ push ଏଗୁଡ଼ିକୁ ଆରମ୍ଭ କରେ ନାହିଁ (2026-10-18): ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ତାହାର PR ରେ ପୂର୍ବରୁ matrix ଚଲାଇସାରିଛି ଏବଂ ମର୍ଜ୍ ହୋଇଥିବା ସଂଯୋଜନ Release-Green ର ଦାୟିତ୍ୱ (`docs/ops/RUNNER_BOX.md` → Hosted lane)।
Fork ଏବଂ merge group ଗୁଡ଼ିକ ସେହି ଜବ୍ଗୁଡ଼ିକ ପାଇଁ hosted runner ବ୍ୟବହାର କରେ ଯେଉଁଗୁଡ଼ିକ ଅନ୍ୟଥା self-hosted
runner ଚୟନ କରିଥାନ୍ତା; rollout ପୂର୍ବରୁ ପର୍ଯ୍ୟାପ୍ତ hosted କ୍ଷମତା ଯାଞ୍ଚ କରିବା ଆବଶ୍ୟକ।

ଏକ ସାଧାରଣ PR ଦ୍ରୁତ ଚୟନ ଚଲାଏ। ଭର୍ତ୍ତି ନୀତିର `full-code` ଏବଂ `full-code-e2e` lane
(E2E, integration, package artifact, Electron smoke, Bun SQLite, ecosystem ଏବଂ protocol clients) କେବଳ Mergify queue draft ରେ କିମ୍ବା ଏକ ସମ୍ପୂର୍ଣ୍ଣ run ରେ ଚଲେ:
`gh workflow run ci.yml --ref <branch>`।

ପ୍ରତ୍ୟେକ JSON receipt ଯାଞ୍ଚ କରାଯାଇଥିବା SHA, workflow run ଏବଂ attempt ଚିହ୍ନଟ କରେ।
CLI checkout/event SHA ଅମେଳକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ୱର୍କଫ୍ଲୋ ପରୀକ୍ଷାଗୁଡ଼ିକ ନୀତି ସଦସ୍ୟତାକୁ verdict job ର `needs` ତାଲିକା ସହିତ ବାନ୍ଧିଥାଏ, ଯାହାଫଳରେ ନୂଆ କିମ୍ବା ହଟାଯାଇଥିବା lane ନିରବରେ ଅଦୃଶ୍ୟ ହୋଇପାରେ ନାହିଁ। Receipt ଗୁଡ଼ିକ ନିଜସ୍ୱ workflow କୁ ଆବୃତ କରେ, ପ୍ରକାଶନ, deployment କିମ୍ବା ବର୍ତ୍ତମାନର ପରାମର୍ଶମୂଳକ scanner ର ଆଭ୍ୟନ୍ତରୀଣ କାର୍ଯ୍ୟକୁ ନୁହେଁ। Branch rules ରେ ଉଭୟ check name ସକ୍ରିୟ କରିବା ଏକ ପୃଥକ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ; ଏହି job ଗୁଡ଼ିକୁ ଯୋଡ଼ିବା ନିଜେ କୌଣସି branch କୁ ସୁରକ୍ଷିତ କରେ ନାହିଁ।

### ମର୍ଜ୍ କ୍ୟୁ

`queue` ଲେବଲ୍ ଏକ PR କୁ Mergify queue (`.mergify.yml`) କୁ ପଠାଏ। Mergify ଏକ
`mergify/merge-queue/` ବ୍ରାଞ୍ଚରେ draft PR ଖୋଲେ, ସେଠାରେ CI ସମ୍ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାଏ, ଏବଂ
`Gate / CI`, `Gate / Quality` ଏବଂ `Merge integrity (changelog + generated skills)` ପାସ୍ ହେଲେ ମୂଳ PR ମର୍ଜ୍ ହୁଏ।

Mergify draft ର description ରେ ନିଜ queue summary ଲେଖେ, ଏବଂ ଅନ୍ୟ app ଗୁଡ଼ିକ ମଧ୍ୟ ଏହାକୁ ସମ୍ପାଦନ କରିପାରନ୍ତି।
ଏପରି draft ଉପରେ `pull_request` `edited` ଇଭେଣ୍ଟ ନିଜସ୍ୱ concurrency group
(`-queue-edit-<run_id>`) ନିଏ, ଯାହାଫଳରେ ଏହା draft ର ପ୍ରକୃତ run କୁ ବାତିଲ କରିପାରେ ନାହିଁ, ଏବଂ gate ଓ
matrix କୁ ସ୍କିପ୍ କରେ। କେବଳ `Merge integrity` ଏବେ ମଧ୍ୟ ଚଲେ। ସ୍କିପ୍ ହୋଇଥିବା gate job ଏକ ଭିନ୍ନ check name ବହନ କରେ,
କାରଣ Mergify ସ୍କିପ୍ ହୋଇଥିବା `Gate / CI` କୁ ବିଫଳ check ଭାବେ ପଢ଼େ ଏବଂ PR କୁ queue ରୁ ବାହାର କରିଦିଏ।

Queue ରୁ ବାହାରିବା ପରେ, push ସବୁବେଳେ PR କୁ ପୁନଃ queue କରେ ନାହିଁ। ଏଥିରେ `@mergifyio queue` comment କରନ୍ତୁ।

### ଗ୍ରହଣ reducer ରେ ସଂରକ୍ଷିତ ପ୍ରମାଣ

`scripts/quality/validate-release-acceptance.mjs` ଦିଆଯାଇଥିବା plan ଏବଂ ତାହାର
manifests କୁ reduce କରେ; ଏହା plan ଟି ସମ୍ପୂର୍ଣ୍ଣ release pipeline କୁ ଆବୃତ କରୁଛି ବୋଲି ସ୍ଥାପନ କରେ ନାହିଁ।
ଏହାର report ଗୁଡ଼ିକ ସ୍ପଷ୍ଟ ଭାବେ `releaseAcceptance: false` ସେଟ୍ କରେ, ଯଦିଓ ସେହି plan
`VERIFIED` ହୋଇଥାଏ। `release-acceptance.yml` workflow ଏବେ ମଧ୍ୟ ପ୍ରକୃତ build, package, boot କିମ୍ବା promotion receipt ବଦଳରେ shadow fixture ବ୍ୟବହାର କରେ।

CLI retained evidence ଯାଞ୍ଚ କରିବା ପାଇଁ `--evidence-root` ଆବଶ୍ୟକ କରେ। File ଗୁଡ଼ିକ `<evidence-root>/<artifact_id>/<member>` ଭାବେ resolve ହୁଏ ଏବଂ SHA-256 ଭାବେ hash କରାଯାଏ। Evidence ବିନା PASS record, ଅନୁପସ୍ଥିତ କିମ୍ବା ପରିବର୍ତ୍ତିତ file, ଅସୁରକ୍ଷିତ path କିମ୍ବା symlink verification କୁ ରୋକେ। ଅନୁପସ୍ଥିତ file ଗୁଡ଼ିକ ଖାଲି ସଫଳ log ସହିତ ସମାନ ନୁହେଁ। ପୂର୍ବରୁ ଥିବା SHA/run/attempt ଯାଞ୍ଚଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହେ: ମେଳ ଖାଉଥିବା byte ଗୁଡ଼ିକ ପୁରୁଣା receipt କୁ ସଠିକ୍ କରିପାରେ ନାହିଁ। File integrity ହେଉଛି execution authenticity କିମ୍ବା artifact promotion ର ପ୍ରମାଣ ନୁହେଁ।

### Static scan ଇନଭେଣ୍ଟରି

ସଂସ୍କରଣ-ନିୟନ୍ତ୍ରିତ npm-alias ଇନଭେଣ୍ଟରି ଏବଂ static-scan membership
`config/quality/gate-manifest.json` ରେ ରହିଛି। `npm run check:gate-manifest` ଚଲାଇ
`package.json` ବିରୁଦ୍ଧରେ script name ଏବଂ ସଠିକ୍ command ଯାଞ୍ଚ କରନ୍ତୁ; addition, removal ଏବଂ
command drift ଉଭୟ local hook ଏବଂ CI ର change-classification job ଗୁଡ଼ିକୁ ବିଫଳ କରେ।
ଏକ alias workflow job, matrix instance କିମ୍ବା test case ନୁହେଁ: ଏହି ସଂଖ୍ୟାଗୁଡ଼ିକୁ ପରସ୍ପର ବଦଳାଯୋଗ୍ୟ ଭାବେ ପ୍ରଦର୍ଶନ କରିବା ଉଚିତ୍ ନୁହେଁ।

ଚଲାଇବା ବିନା ଚୟନ ହୋଇଥିବା alias ଗୁଡ଼ିକୁ ଯାଞ୍ଚ କରିବା ପାଇଁ `npm run quality:scan -- --list` କିମ୍ବା `npm run quality:scan:fast -- --list`
ବ୍ୟବହାର କରନ୍ତୁ। Runner npm entrypoint କୁ invoke କରେ, ତେଣୁ ଏହାର runtime (ଯେଉଁଠାରେ configured ଅଛି ସେଠାରେ Bun ସମେତ) ସଂରକ୍ଷିତ ରହେ।
Manifest ସେହି profile ବାହାରର alias ଗୁଡ଼ିକୁ ପୃଥକ ଭାବେ invoke କରାଯାଇଥିବା ବୋଲି ରେକର୍ଡ କରେ, ଏବଂ
maintenance command ଗୁଡ଼ିକୁ read-only scan profile ରେ ନିଷେଧ କରେ।

ଏହି profile ଗୁଡ଼ିକ କେବଳ static scan କୁ ଆବୃତ କରେ। ଏଗୁଡ଼ିକ product test,
coverage, packaging, external check କିମ୍ବା ଏକ candidate ର ସମ୍ପୂର୍ଣ୍ଣ release acceptance କୁ ପ୍ରମାଣିତ କରେ ନାହିଁ।
Workflow admission ଲିଙ୍କ୍ ହୋଇଥିବା `config/quality/admission-policy.json` ଏବଂ `scripts/quality/admission-verdict.mjs` ବ୍ୟବହାର କରେ। Release-observer profile ଗୁଡ଼ିକ ପୃଥକ ରହେ;
ସେମାନଙ୍କର ପ୍ରୟୋଜ୍ୟ check ଏବଂ receipt ଗୁଡ଼ିକୁ ସ୍ୱାଧୀନ ଭାବେ ଯାଞ୍ଚ କରନ୍ତୁ। Full observer ର static
command ଗୁଡ଼ିକ `config/quality/release-green-static-profile.json` ରେ ଘୋଷିତ, ଯେଉଁଥିରେ
`audit:deps`, mutation-test selection ଏବଂ translation check ଅନ୍ତର୍ଭୁକ୍ତ। Loader package.json ବିରୁଦ୍ଧରେ npm
command ଏବଂ modeled CI/Quality declaration ଯାଞ୍ଚ କରେ; shell token ଗୁଡ଼ିକୁ argument ଭାବେ execute କରିବା ପରିବର୍ତ୍ତେ drift କୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଆବଶ୍ୟକ scanner ର SKIP/INCOMPLETE output PASS ସ୍ଥାପନ କରିପାରେ ନାହିଁ। Profile ଏହାର external exclusion ଗୁଡ଼ିକୁ record କରେ ଏବଂ hosted coverage, test matrix, package କିମ୍ବା deployment evidence କୁ ପ୍ରତିସ୍ଥାପନ କରେ ନାହିଁ। ତଳେ ଥିବା prose inventory ଏକ reference, ପ୍ରକୃତରେ କୌଣସି gate ଚଲିଛି ବୋଲି ପ୍ରମାଣ ନୁହେଁ।

Script ଗୁଡ଼ିକ `scripts/check/` (policy gate) ଏବଂ `scripts/quality/` (ratchet engine) ଅଧୀନରେ ରହିଛି।
CI ର source of truth ହେଉଛି `.github/workflows/ci.yml`।

### Release PR fast-path (`quality.yml`)

`.github/workflows/quality.yml` main/release PR, `main` କୁ push,
dispatch ଏବଂ merge group ସମୟରେ CI କୁ ପୂରକ କରେ। PR ଗୁଡ଼ିକ path-filtered fast check ବ୍ୟବହାର କରେ।

#### ଭୁଲିଯାଇଥିବା ସହୋଦର ଟେଷ୍ଟ ରିପୋର୍ଟ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates`-ର ଏକ ପରାମର୍ଶମୂଳକ ପଦକ୍ଷେପ ଭାବେ ଚାଲେ ଏବଂ ଟେଷ୍ଟ-ଇମ୍ପାକ୍ଟ ମ୍ୟାପ୍ ପଛରେ ଥିବା ଇମ୍ପୋର୍ଟ ରିଜଲ୍ଭରକୁ ପୁନଃବ୍ୟବହାର କରେ।
ପରିବର୍ତ୍ତିତ ପ୍ରତ୍ୟେକ ପ୍ରୋଡକ୍ସନ୍ ମଡ୍ୟୁଲ୍ ପାଇଁ, ପ୍ରାର୍ଥୀ ଟେଷ୍ଟ ପୁଲ୍-ରିକ୍ୱେଷ୍ଟ ଡିଫ୍ରେ ନଥିଲେ, ଏହା ନିର୍ଦ୍ଧାରିତ
`changed module/symbol -> static consumer -> candidate sibling test` ଚେନ୍ ରିପୋର୍ଟ କରେ। ମାର୍କଡାଉନ୍ ସାରାଂଶ ଏବଂ JSON ଫଳାଫଳକୁ
କ୍ୟାଲିବ୍ରେସନ୍ ପାଇଁ କୌଣସି ବ୍ଲକିଂ ରୋଲ୍ଆଉଟ୍ ପୂର୍ବରୁ `forgotten-sibling-tests` ୱର୍କଫ୍ଲୋ ଆର୍ଟିଫ୍ୟାକ୍ଟ ଭାବେ ସଂରକ୍ଷିତ ରଖାଯାଏ।

ବ୍ୟାରେଲ୍ ରି-ଏକ୍ସପୋର୍ଟ ଏବଂ ଡାଇନାମିକ୍ ଇମ୍ପୋର୍ଟଗୁଡ଼ିକ କେବଳ ରିଜଲ୍ୟୁସନ୍ ଡାଏଗ୍ନୋଷ୍ଟିକ୍ସ; ସେଗୁଡ଼ିକ କେବେ ମଧ୍ୟ ବ୍ଲକିଂ ଫାଇଣ୍ଡିଂ ସୃଷ୍ଟି କରନ୍ତି ନାହିଁ। ସମୀକ୍ଷିତ ବ୍ୟତିକ୍ରମଗୁଡ଼ିକ
`config/quality/forgotten-sibling-allowlist.json`-ରେ ରହେ। ପ୍ରତ୍ୟେକ ଏଣ୍ଟ୍ରିରେ କନ୍ଜ୍ୟୁମର୍ ଏବଂ ପ୍ରାର୍ଥୀ
ଟେଷ୍ଟର ନାମ, ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ଯୁକ୍ତି, ଏବଂ ଏକ GitHub ଇସ୍ୟୁ କିମ୍ବା ପୁଲ୍ ରିକ୍ୱେଷ୍ଟର ଲିଙ୍କ୍ ଥିବା ଆବଶ୍ୟକ। ଭୁଲ୍ ଫର୍ମାଟ୍ର ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ ବିଫଳ ହୋଇ ସୁରକ୍ଷିତ ଭାବେ ବନ୍ଦ ହୁଅନ୍ତି। ବ୍ୟତିକ୍ରମଗୁଡ଼ିକ ଡିଲିଟ୍ ହୋଇଥିବା ପ୍ରାର୍ଥୀ ଟେଷ୍ଟ କିମ୍ବା `.skip`/`.todo` ଯୋଡ଼ୁଥିବା ଡିଫ୍କୁ ଦମନ କରିପାରିବ ନାହିଁ;
ଆସର୍ସନ୍ ଦୁର୍ବଳକରଣ ଏବଂ ଅନ୍ୟାନ୍ୟ ମାସ୍କିଂ ସ୍ୱାଧୀନ ଭାବେ ବ୍ଲକିଂ କରୁଥିବା `check:test-masking` ଗେଟ୍ର ଦାୟିତ୍ୱରେ ରହେ।

`llm.txt` copies ଏବଂ ଅନୁବାଦିତ `CHANGELOG.md` files ସହିତ) ଏବଂ `.i18n-state.json` translation wave (`docs/i18n-*` / `chore/i18n-*` branches, scheduled
`i18n-mirror-refresh.yml`) ଦ୍ୱାରା ଏବଂ release (`npm run release:sync-changelog-i18n`) ଦ୍ୱାରା ଗୋଟିଏ ପଦକ୍ଷେପରେ ପୁନଃଲିଖିତ ହୁଏ। ତେଣୁ mirror gates ଦୁଇଟି ମୋଡ୍ରେ ଚାଲେ, ଯାହା `scripts/check/lib/gateMode.mjs` ଦ୍ୱାରା ସମାଧାନ ହୁଏ (`--mode=pr|release`,
ତାପରେ `OMNIROUTE_GATE_MODE`, ତାପରେ Actions event; local run ହେଉଛି `release`):

- `check:docs-sync` — ରିଲିଜ୍ ମୋଡ୍ରେ ପ୍ରତ୍ୟେକ ଯାଞ୍ଚ ଚାଲେ। PR ମୋଡ୍ରେ package.json/OpenAPI ସଂସ୍କରଣ,
  ରୁଟ୍ CHANGELOG ଶୀର୍ଷକଗୁଡ଼ିକ ଏବଂ superseded-docs ଗାର୍ଡ୍ ରଖାଯାଏ, ଏବଂ
  `SKIP reason=pr-mode` ପ୍ରିଣ୍ଟ୍ କରି `llm.txt` ମିରର୍ କପିଗୁଡ଼ିକ ଓ ଅନୁବାଦିତ CHANGELOG ଅଂଶଗୁଡ଼ିକୁ
  ଛାଡ଼ିଦିଏ — ଯଦିଓ PR ମିରର୍ ଲେଖେ: `config/quality/derived-paths/*.json` ରେ
  `docs/i18n/**` ପରିବାରର ଲେଖକ ଭାବେ ଘୋଷିତ ଏକ head branch ଉଭୟ ଯାଞ୍ଚକୁ କଠୋରଭାବେ ଚଲାଏ,
  ଏବଂ, ଯେତେବେଳେ diff base ନିର୍ଣ୍ଣୟ ହୁଏ, ନିଜ diff ରେ `docs/i18n/<locale>/llm.txt` କିମ୍ବା
  `CHANGELOG.md` ସମ୍ପାଦନ କରୁଥିବା ପରିବର୍ତ୍ତନ ସେହି ଯାଞ୍ଚକୁ କଠୋରଭାବେ ଚଲାଏ। diff base
  depth-1 checkout (`docs-sync-strict` job) ରେ ନିର୍ଣ୍ଣୟ ହୁଏ ନାହିଁ, ତେଣୁ PR ମୋଡ୍ରେ ଏକ
  base ଆବଶ୍ୟକ ନଥିବା ଯାଞ୍ଚ ମଧ୍ୟ ଚାଲେ: ପ୍ରତ୍ୟେକ `llm.txt` ମିରର୍ ଅବଶ୍ୟ ରହିବା ଦରକାର, ଏହାର
  `---` ବିଭାଜକକୁ ରଖିବା ଦରକାର ଏବଂ ରୁଟ୍ body କିମ୍ବା ଅଧିକାଂଶ ମିରର୍ରେ ସାଧାରଣ ଥିବା body
  ବହନ କରିବା ଦରକାର। ଏକ base ସ୍ଥାନାନ୍ତରିତ ହେଲେ ସମସ୍ତ ମିରର୍ ସମାନ ଭାବରେ ପୁରୁଣା ହୋଇଯାଏ
  ଏବଂ ଯାଞ୍ଚ ପାସ୍ କରେ; ଗୋଟିଏ ମିରର୍ରେ ହାତରେ କରାଯାଇଥିବା ସମ୍ପାଦନ ବିଫଳ ହୁଏ। depth-1 PR
  checkout ରେ ଅନୁବାଦିତ `CHANGELOG.md` ଫାଇଲ୍ଗୁଡ଼ିକ ପାଇଁ ଏପରି କୌଣସି ଯାଞ୍ଚ ନାହିଁ।
- pre-commit hook `check-docs-sync.mjs --mode=pr` ଚଲାଏ: ଏକ commit ଏହା କ’ଣ କରୁଛି ତାହା ଆଧାରରେ
  ମୂଲ୍ୟାୟିତ ହୁଏ। flag ବିନା local run release mode ହୁଏ, ଏବଂ root `llm.txt` ସମ୍ପାଦନ କରୁଥିବା
  ଗୋଟିଏ merged PR ପରବର୍ତ୍ତୀ ପ୍ରତ୍ୟେକ commit କୁ ସେହି base ଉପରେ wave ଚାଲିବା ପର୍ଯ୍ୟନ୍ତ
  ଅଟକାଇଦେଇଥାନ୍ତା। Husky hook ଚଲାଉଥିବା ଯେକୌଣସି mode-aware gate ପାଇଁ ମଧ୍ୟ ସମାନ ନିୟମ
  ଲାଗୁ ହୁଏ: hook `--mode=pr` ପାସ୍ କରେ, ଏବଂ strict verdict release-mode runଗୁଡ଼ିକ ସହିତ
  ରହେ (release PR, `main` କୁ push, ସାଧାରଣ local run)।
- Mirror-content unit tests (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`,
  `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`,
  `docs/*-locales`) — release mode ପ୍ରତ୍ୟେକ locale କୁ ଯାଞ୍ଚ କରେ। PR mode କେବଳ ସେହି
  ମିରର୍ଗୁଡ଼ିକୁ ଯାଞ୍ଚ କରେ ଯେଉଁଗୁଡ଼ିକ `.i18n-state.json` ଅନୁଯାୟୀ ଇଂରାଜୀ source ସହିତ
  ସମକାଳୀନ (ସମ୍ପୂର୍ଣ୍ଣ-ଫାଇଲ୍ hash, କିମ୍ବା test pin କରୁଥିବା sectionର ରେକର୍ଡ୍ ହୋଇଥିବା
  section hash) ଏବଂ ପୁରୁଣାଗୁଡ଼ିକୁ ଏକ କାରଣ ସହିତ ଛାଡ଼ିଦିଏ। `target_hash` provenance ଯାଞ୍ଚ
  ଉଭୟ modeରେ ପ୍ରତ୍ୟେକ locale ପାଇଁ ଚାଲେ। Freshness ପ୍ରତ୍ୟେକ `## ` section ପାଇଁ ଅଲଗା,
  unit `run-translation.mjs` hash କରେ; ଏକ ଦୀର୍ଘ section (ଏହି ଫାଇଲ୍ର gate inventory ଏହାର
  ପ୍ରାୟ ଅଧା) ଅର୍ଥ ହେଉଛି ଏଥିରେ ଯେକୌଣସି ସମ୍ପାଦନ ସେହି ମିରର୍ଗୁଡ଼ିକୁ ପୁରୁଣା କରିଦିଏ,
  ଏବଂ ପରବର୍ତ୍ତୀ wave ପର୍ଯ୍ୟନ୍ତ ସେମାନଙ୍କର PR-mode assertions ଛାଡ଼ିଦିଏ। ଇଂରାଜୀ source
  ଆଉ ଧାରଣ ନକରୁଥିବା ଏକ anchor ସମ୍ପୂର୍ଣ୍ଣ-ଫାଇଲ୍ ତୁଳନାକୁ fallback କରେ।

### Derived values: the `pr` and `release` gate modes

ଏକ feature PR ଏହାର baseର state ଉପରେ ନିର୍ଭର କରୁଥିବା କୌଣସି value ଲେଖେ ନାହିଁ: provider, migration,
MCP-tool ଏବଂ strategy counts, README SVG numbers, facts snapshot। ଏକ step ସେଗୁଡ଼ିକୁ ସମସ୍ତଙ୍କୁ
ପୁନଃଗଣନା କରେ, `npm run release:refresh-derived` ଦ୍ୱାରା, ଯାହା release ଏବଂ nightly
derived-refresh PR ଚଲାଏ। ତେଣୁ **releases ମଧ୍ୟରେ base ଇଚ୍ଛାକୃତ ଭାବେ live code ଠାରୁ ପଛରେ
ରହେ**, ଏବଂ sibling ଗୋଟିଏ provider ଯୋଡ଼ିବା ପରେ tree କୁ live code ସହିତ ତୁଳନା କରୁଥିବା
gate କିମ୍ବା test ପ୍ରତ୍ୟେକ PR ରେ red ହୋଇଥାନ୍ତା। Derived valuesକୁ ମୂଲ୍ୟାୟନ କରୁଥିବା
gates ତେଣୁ ଦୁଇଟି mode ମଧ୍ୟରୁ ଗୋଟିଏରେ ଚାଲେ, ଯାହା `scripts/check/lib/gateMode.mjs` ଦ୍ୱାରା
ନିର୍ଣ୍ଣୟ ହୁଏ (ପ୍ରଥମ match ପ୍ରୟୋଗ ହୁଏ):

1. command line ରେ `--mode=pr|release`;
2. `OMNIROUTE_GATE_MODE` environment variable (`pr` କିମ୍ବା `release`);
3. GitHub Actions event ରୁ ସ୍ୱୟଂଚାଳିତ: ଯେଉଁ `pull_request` ର head `release/v*` ନୁହେଁ,
   ଏକ `merge_group`, କିମ୍ବା `omni-queue/**` କୁ push → `pr`; ଅନ୍ୟ ସବୁ (push, schedule,
   dispatch, release PR `release/v* → main`, ଯେକୌଣସି local run) → `release`।

ପ୍ରତ୍ୟେକ modeରେ `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) କ’ଣ ବିଫଳ କରେ:

| Mode      | Fails                                                                                                                                                                                                                                                                                                                                                                                                                       | Needs the live facts |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| `release` | ପ୍ରତ୍ୟେକ ଯାଞ୍ଚରେ ଟ୍ରିରୁ ସଂଗ୍ରହ କରାଯାଇଥିବା ତଥ୍ୟ ସହିତ strict equality (ଗେଟ୍ରେ ସଦା ଥିବା ବ୍ୟବହାର): ଏକ ପୁରୁଣା count, version, coverage floor କିମ୍ବା SVG number ହେଉଛି ଏକ STRICT drift                                                                                                                                                                                                                                             | ହଁ                   |
| `pr`      | କେବଳ ପରିବର୍ତ୍ତନ ଯାହା କରିଛି, ସେହିଟିକୁ ସମାନ claim extractors ସହିତ PR base ବିରୋଧରେ diff କରାଯାଏ: (1) ସେହି check ଏବଂ file ପାଇଁ base-ରେ ନଥିବା ଏକ managed value ("PR edited a managed number — restore the line to the base text"); (2) base-ରେ ଥିବା ଏକ required claim ଯାହା head-ରୁ ହରାଇଯାଇଛି। ଯେଉଁ content invariants ପାଇଁ facts ଆବଶ୍ୟକ ନୁହେଁ, ସେଗୁଡ଼ିକ release mode ପରି ଚାଲେ; release-only checks ତାଲିକାଭୁକ୍ତ କରାଯାଇ skip କରାଯାଏ | ନା                   |

Agent-instruction files-ରେ କୌଣସି derived count ନାହିଁ: `AGENTS.md`, `llm.txt` (ଏବଂ ଏହାର
`docs/i18n/*/llm.txt` copies), bs `AGENTS.md` fork, `open-sse/services/AGENTS.md`,
`src/shared/constants/agentSkills.ts`, `skills/README.md` ଏବଂ ପ୍ରତ୍ୟେକ `skills/*/SKILL.md` source କୁ (ଉଦାହରଣ ସ୍ୱରୂପ
`ROUTING_STRATEGY_VALUES` in `src/shared/constants/routingStrategies.ts`) ଏବଂ `npm run facts` ପ୍ରତି ନିର୍ଦ୍ଦେଶ କରେ। ଉଭୟ mode-ରେ invariant "No derived counts (agent-instruction file …)" ସେଠାରେ ଏକ count (providers, migrations, MCP tools ଏବଂ scopes, routing strategies, scoring factors, mode packs) ପାଇଲେ ବିଫଳ ହୁଏ, ତେଣୁ release refresh-କୁ କୌଣସି instruction file ପୁନଃଲେଖନ କରିବାକୁ ପଡ଼େ ନାହିଁ।

`pr` mode-ରେ writer branches managed values ସମ୍ପାଦନ କରିପାରନ୍ତି: `chore/derived-*` (nightly refresh
PR), `release/v*`, ଏବଂ translation waves `docs/i18n-*` ଏବଂ `chore/i18n-*`
(`scripts/check/lib/derivedClaimsDiff.mjs`)। Queue batches (`merge_group`, Mergify drafts,
`omni-queue/**`) ପୁନର୍ବାର ବିଚାର କରାଯାଏ ନାହିଁ: gate ପୂର୍ବରୁ ଯେଉଁ PRଗୁଡ଼ିକୁ ଗୋଟିଏ ପରେ ଗୋଟିଏ ବିଚାର କରିଛି, ସେଗୁଡ଼ିକୁ ଏହା ସମୁଦାୟ କରେ।

Exit codes: `0` clean · `1` STRICT drift (କିମ୍ବା `--strict` ସହିତ soft drift) କିମ୍ବା ଏକ managed-value
violation · `2` infrastructure — code facts ସଂଗ୍ରହ କରାଯାଇପାରିଲା ନାହିଁ (tsx probe ବିଫଳ ହେଲା କିମ୍ବା
timeout ହେଲା; timeout ହେଉଛି `OMNIROUTE_FACTS_TIMEOUT_MS`, default 600000 ms) କିମ୍ବା CI-ରେ PR diff
base resolve କରାଯାଇପାରିଲା ନାହିଁ। Exit 2 କେବେ documentation divergence ନୁହେଁ: job ପୁନଃଚାଲନ୍ତୁ କିମ୍ବା
environment ଠିକ୍ କରନ୍ତୁ।

ପ୍ରତ୍ୟେକ mode କେଉଁଠାରେ ଚାଲେ:

| Where                                                                                          | Mode                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

ଏହା ପଛରେ ଥିବା commands:

- `npm run facts` ପ୍ରତ୍ୟେକ ଉତ୍ପନ୍ନ ସଂଖ୍ୟାକୁ JSON ଭାବେ ପ୍ରିଣ୍ଟ କରେ (`scripts/release/facts.mjs`)।
  `--key=code.mcpTools` ଗୋଟିଏ ମୂଲ୍ୟ ପ୍ରିଣ୍ଟ କରେ, `--snapshot` ସଜୀବ ଟ୍ରି ପରିବର୍ତ୍ତେ କମିଟ୍ ହୋଇଥିବା ସ୍ନାପସଟ୍ ପଢ଼େ। ତଥ୍ୟ ସଂଗ୍ରହ କରିହେବ ନାହିଁ ହେଲେ Exit 2।
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) ଗୋଟିଏ ପାସ୍ରେ ଏହି କ୍ରମରେ ଉତ୍ପନ୍ନ ଫାଇଲଗୁଡ଼ିକୁ ପୁନଃଗଣନା କରେ (`--only=` ପାଇଁ ପଦକ୍ଷେପ IDଗୁଡ଼ିକ): `provider-reference`
  (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (ସ୍ନାପସଟ୍), `numbers` (counts gateର rewrite planକୁ ଡକ୍ୟୁମେଣ୍ଟଗୁଡ଼ିକରେ ପ୍ରୟୋଗ କରେ, ପରେ ତାହାକୁ ସେମାନଙ୍କର `docs/i18n/` ମିରରଗୁଡ଼ିକୁ ନେଇଯାଏ),
  `readme-diagrams`, `skills` (ଉତ୍ପନ୍ନ `SKILL.md`), `e2e-timings` (ଟ୍ରିରେ `syncE2eTimings` ଆସିବା ପର୍ଯ୍ୟନ୍ତ ଛାଡ଼ିଦିଆଯାଏ), `ui-keys` (`en.json`ରୁ ବାଦ ପଡ଼ିଥିବା keyଗୁଡ଼ିକୁ ଛାଟେ ଏବଂ, `--rewritten-since=<ref>` ସହ — ଡିଫଲ୍ଟ `origin/main` — ଶେଷ release ପରଠାରୁ ପୁନଃଲିଖିତ English ମୂଲ୍ୟଗୁଡ଼ିକୁ ପୁଣି କ୍ୟୁରେ ରଖେ), `llm-mirrors` ଏବଂ `verify-generated` (ଲେଖା ପରେ, release modeରେ `check:generated-artifacts` ଏବଂ `check:agent-skills-sync` ସଫଳ ହେବା ଆବଶ୍ୟକ; `--check`ରେ ଏବଂ `--only` ଏହାକୁ ବାଦ ଦେଲେ ଛାଡ଼ିଦିଆଯାଏ; ବିଫଳତା ହେଲେ exit 2)। `changelog` ପଦକ୍ଷେପଟି opt-in (`--with-changelog`, କେବଳ release profileରେ)। `--profile=nightly` କେବେ version claimକୁ ସ୍ପର୍ଶ କରେ ନାହିଁ। `-- --check` ସହିତ ଏହା କିଛି ଲେଖେ ନାହିଁ ଏବଂ କୌଣସି ଫାଇଲ ବଦଳିବାକୁ ଥିଲେ କିମ୍ବା କୌଣସି managed valueରେ ମାନୁଆଲ୍ edit ଆବଶ୍ୟକ ହେଲେ exit 1 ଦିଏ (ଉଭୟକୁ ତାଲିକାଭୁକ୍ତ କରି); infrastructure failure ହେଲେ exit 2। `--json` ଫଳାଫଳକୁ JSON ଭାବେ ପ୍ରିଣ୍ଟ କରେ।
- `docs/reference/derived-facts.json` ହେଉଛି ଶେଷ refresh ଦ୍ୱାରା ବ୍ୟବହୃତ factsର ସ୍ନାପସଟ୍। କେବଳ refresh ଏହାକୁ ଲେଖେ। README SVG generatorଗୁଡ଼ିକ ଏହାକୁ ପଢ଼ନ୍ତି, ଏବଂ PR ସମୟର unit testଗୁଡ଼ିକ committed docs ଏବଂ generated filesକୁ ଏହା ସହିତ ତୁଳନା କରନ୍ତି — live code ସହିତ କେବେ ନୁହେଁ। suiteର ଏକମାତ୍ର live comparison ହେଉଛି `tests/unit/check-docs-counts-sync.test.ts`ର “the release refresh closes the cycle”: live facts ସହିତ, refreshର rewrite planକୁ memoryରେ ପ୍ରୟୋଗ କଲେ ଏହା ରିପୋର୍ଟ ନକରିଥିବା କୌଣସି STRICT drift ରହେ ନାହିଁ, ଏବଂ ପୁଣିଥରେ planning କଲେ କିଛି ବଦଳେ ନାହିଁ।

ସ୍ଥାନୀୟ ଭାବେ ପୁନରୁତ୍ପାଦନ କରିବାକୁ (ସ୍ଥାନୀୟ run ଡିଫଲ୍ଟ ଭାବେ `release` ବ୍ୟବହାର କରେ):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

ସମାଧାନଯୋଗ୍ୟ base ନଥିଲେ (`BASE_SHA`/`BASE_REF` ନାହିଁ, କିମ୍ବା ସ୍ଥାନୀୟ `origin/release/v<version>` ନାହିଁ), ସ୍ଥାନୀୟ
`pr` run ଏକ ସତର୍କବାର୍ତ୍ତା ପ୍ରିଣ୍ଟ କରେ ଏବଂ ବିଫଳ ହେବା ପରିବର୍ତ୍ତେ diffକୁ ଛାଡ଼ିଦିଏ।

**ଦୁଇଟି mode (2026-11-13 ଠାରୁ)।** ଏକ feature PR `en.json` (ଏବଂ
`bin/cli/locales/en.json`)ରେ key ଯୋଡ଼େ କିମ୍ବା ପୁନଃଲେଖେ ଏବଂ ଅନ୍ୟ କୌଣସି localeକୁ ସ୍ପର୍ଶ କରେ ନାହିଁ; `check:pr-derived-paths` (`pr-test-policy` job,
`config/quality/derived-paths/translation.json` family) ଏହା କରୁଥିବା feature PRକୁ ବିଫଳ କରେ। ଅନ୍ୟ localeଗୁଡ଼ିକ ପ୍ରତ୍ୟେକ releaseରେ ଥରେ `release:refresh-derived` ଦ୍ୱାରା ସମ୍ପୂର୍ଣ୍ଣ ହୁଅନ୍ତି, ଯାହା
`scripts/i18n/sync-ui-keys.mjs`ରେ `syncUiKeys()`କୁ କଲ୍ କରେ (missing key ଯୋଡ଼େ, ବାଦ ପଡ଼ିଥିବା key ଛାଟେ, ପୁନଃଲିଖିତ Englishର translationଗୁଡ଼ିକୁ `rewrittenSinceRef` ସହିତ ଚିହ୍ନଟ କରେ, translate କରେ), କିମ୍ବା translation wave ଦ୍ୱାରା। Gateଗୁଡ଼ିକ `scripts/check/lib/gateMode.mjs`ରୁ mode ପଢ଼ନ୍ତି: `pr` modeରେ (feature PR,
`merge_group`, `omni-queue/**`) ଉପରୋକ୍ତ release-mode gateଗୁଡ଼ିକ `SKIP reason=pr-mode` ପ୍ରିଣ୍ଟ କରି
0 ଦିଅନ୍ତି; `release` modeରେ (release PR, `main`କୁ pushes, `workflow_dispatch`, ସ୍ଥାନୀୟ run) ସେଗୁଡ଼ିକ ପୂର୍ବବତ୍ strict ରହନ୍ତି, ଏବଂ release PRରେ diff-aware gateଗୁଡ଼ିକ `BASE_REF=origin/main` ପାଆନ୍ତି, ତେଣୁ ସେମାନେ cycle ଦ୍ୱାରା ଯୋଡ଼ା କିମ୍ବା ପୁନଃଲିଖା ପ୍ରତ୍ୟେକ keyକୁ ଯାଞ୍ଚ କରନ୍ତି। `--mode=pr` ସହିତ feature-PR verdictକୁ ସ୍ଥାନୀୟ ଭାବେ preview କରନ୍ତୁ।

ଏକ PR ଯାହା `pr` ମୋଡ୍ରେ ମଧ୍ୟ locale catalog-ଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରେ (ଏକ translation wave, release refresh, କିମ୍ବା translation-only fix), ତାହାକୁ ଛାଡ଼ାଯାଏ ନାହିଁ: `check-key-completeness` merge base-ରେ ଥିବା ସମାନ catalog (`scripts/i18n/lib/touched-catalogs.mjs`)-ସହିତ ଏହା ପରିବର୍ତ୍ତନ କରିଥିବା ପ୍ରତ୍ୟେକ catalog-କୁ ତୁଳନା କରେ ଏବଂ catalog ହରାଇଥିବା key, `en.json`-ରେ ନଥିବା key, ପ୍ରକୃତ ଅନୁବାଦ `__MISSING__:` marker କିମ୍ବା ଇଂରାଜୀ ପାଠ୍ୟରେ ପରିଣତ ହେବା, କିମ୍ବା PR ଯାହାକୁ ସ୍ପର୍ଶ କରିନାହିଁ ସେହି ଇଂରାଜୀ string-ର placeholders/tags-କୁ ଆଉ interpolate ନକରୁଥିବା value ଉପରେ ବିଫଳ ହୁଏ। PR-ରେ ନୂଆ ଥିବା catalog-ରେ ସମ୍ପୂର୍ଣ୍ଣ `en.json` key set ଥିବା ଆବଶ୍ୟକ। ଏହା PR ଯେଉଁ catalog-ଗୁଡ଼ିକୁ ସ୍ପର୍ଶ କରେ, ସେଗୁଡ଼ିକ ପାଇଁ ratio ଏବଂ CLI-parity gate-ଗୁଡ଼ିକ କ’ଣ ଦେଖିବେ ତାହା ଆବରଣ କରେ।

Locale-parity unit test-ଗୁଡ଼ିକ (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) ମଧ୍ୟ `tests/_helpers/localeParityMode.ts` ମାଧ୍ୟମରେ ସମାନ mode ଅନୁସରଣ କରେ: `pr` mode-ରେ ସେଗୁଡ଼ିକ key-parity assertion-ଗୁଡ଼ିକୁ skip କରେ ଏବଂ merge base ପରଠାରୁ ଇଂରାଜୀ ପରିବର୍ତ୍ତିତ ହୋଇଥିବା key-ଗୁଡ଼ିକର placeholder parity-କୁ release refresh ପାଇଁ ଛାଡ଼ିଦିଏ (unit-test job-ର shallow checkout ଏହା ପଢ଼ିପାରିବା ନଥିଲେ ପ୍ରତ୍ୟେକ key)। ସେହି helper ହେଉଛି ଅନୁମୋଦିତ mode-conditional skip-ର **ଏକମାତ୍ର** ଉତ୍ସ: `check:test-masking` `.skip(` ଏବଂ `{ skip: true }` ଗଣନା କରେ, କିନ୍ତୁ ଏହା ଫେରାଉଥିବା computed `{ skip: "<reason>" }`-କୁ ଗଣନା କରେ ନାହିଁ, ତେଣୁ `tests/unit/locale-parity-mode.test.ts` ଏହା ବ୍ୟବହାର କରିବାକୁ ଅନୁମତିପ୍ରାପ୍ତ test-ଗୁଡ଼ିକର ତାଲିକାକୁ ସ୍ଥିର କରେ — ଏଥିରେ ଗୋଟିଏ ଯୋଡ଼ିବା ହେଉଛି ସେହି ତାଲିକାର ସମୀକ୍ଷିତ ସମ୍ପାଦନ।

#### `check-ui-value-drift` — ପୁରୁଣା-ଅନୁବାଦ gate

ଅନ୍ୟ gate-ଗୁଡ଼ିକ ଗଠନାତ୍ମକ ଭାବେ ଦେଖିପାରୁନଥିବା ଏକମାତ୍ର i18n regression-କୁ ଧରେ: ଏକ ଇଂରାଜୀ value ପୁନଃଲିଖାଯାଏ ଏବଂ _ପୂର୍ବତନ_ ଇଂରାଜୀରୁ ଉତ୍ପନ୍ନ ହୋଇଥିବା ଅନୁବାଦଗୁଡ଼ିକ ପଛରେ ରହିଯାଏ, ତେଣୁ ଅଣ-ଇଂରାଜୀ ଉପଭୋକ୍ତାମାନେ ଆତ୍ମବିଶ୍ୱାସଜନକ ଭାବରେ ଲେଖାଯାଇଥିବା, କିନ୍ତୁ ଏବେ ଭୁଲ copy ପଢ଼ିଚାଲନ୍ତି।

ଏହା ପ୍ରକୃତରେ ଶିପ୍ ହୋଇଥିଲା। Antigravity login helper ଯୋଡ଼ାଯିବା ସମୟରେ `oauthModal.googleOAuthWarning` ପୁନଃଲିଖାଯାଇଥିଲା (#5203); **43ଟି locale ମଧ୍ୟରୁ 39ଟି** operator-ମାନଙ୍କୁ “ସମ୍ପୂର୍ଣ୍ଣ URL କପି କରି ତଳେ paste କରନ୍ତୁ” ବୋଲି କହୁଥିବା ପାଠ୍ୟ ରଖିଥିଲା — ଏହି provider ପାଇଁ ଯେଉଁ flow ସମ୍ପୂର୍ଣ୍ଣ ହୋଇପାରେ ନାହିଁ। #8463 ପର୍ଯ୍ୟନ୍ତ ଏହା ଅଦୃଶ୍ୟ ରହିଥିଲା, କାରଣ:

- `sync-ui-keys` କେବଳ **ଅନୁପସ୍ଥିତ** key-ଗୁଡ଼ିକୁ ପୂରଣ କରେ, ପୁରୁଣା ହୋଇଯାଇଥିବା key-ଗୁଡ଼ିକୁ କେବେ ନୁହେଁ;
- `check-ui-keys-coverage` key _ଉପସ୍ଥିତି_ ଗଣନା କରେ, ତେଣୁ ପୁରୁଣା ଅନୁବାଦକୁ covered ଭାବେ ଗଣାଯାଏ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` documentation mirror-ଗୁଡ଼ିକୁ track କରେ — ଏହା କେବେ `src/i18n/messages/*.json` ପଢ଼େ ନାହିଁ। ଏହା `docs-sync-strict` job-ରେ ଚାଲେ: PR-ରେ advisory, push ଏବଂ nightly-ରେ strict; translation wave mirror-ଗୁଡ଼ିକୁ refresh କରେ, feature PR-କୁ ନୁହେଁ।

**Diff-aware, baseline-backed ନୁହେଁ।** ଏହା merge base-ରେ ଥିବା `en.json`-କୁ working tree-ସହିତ ତୁଳନା କରେ; ଯେଉଁ key-ଗୁଡ଼ିକର ଇଂରାଜୀ value ପରିବର୍ତ୍ତିତ ହୋଇଛି, ସେଗୁଡ଼ିକ ପାଇଁ ଏପର୍ଯ୍ୟନ୍ତ ଅସ୍ପର୍ଶିତ ଅନୁବାଦ ରଖିଥିବା ଯେକୌଣସି locale ପୁରୁଣା ଅଟେ। ଏହା ଇଚ୍ଛାକୃତ ଭାବେ ପୂର୍ବରୁ ଥିବା debt-କୁ **ସ୍ଥିର କରେ** — କୌଣସି ପୁରୁଣା ଅନୁବାଦ କେଉଁ ଇଂରାଜୀ ପାଠ୍ୟରୁ ଆସିଥିଲା, diff ତାହା ପ୍ରକାଶ କରିପାରେ ନାହିଁ, ତେଣୁ gate କେବଳ ବର୍ତ୍ତମାନ ପରିବର୍ତ୍ତନ ଯାହାକୁ ସ୍ପର୍ଶ କରେ ତାହାକୁ ହିଁ ନିର୍ଣ୍ଣୟ କରେ। ବିକଳ୍ପ (ପ୍ରତି-key hash baseline) ପାଇଁ ପ୍ରାୟ 600 KB-ର ଏକ generated file ଲାଗିଥାନ୍ତା, ଯାହା ବର୍ତ୍ତମାନର ସବୁଠାରୁ ବଡ଼ baseline-ଠାରୁ 3× ଏବଂ ପ୍ରତ୍ୟେକ i18n PR-ରେ ପରିବର୍ତ୍ତନ ହୋଇଥାନ୍ତା।

ଏହା ପୂରଣ କରିବାର ଦୁଇଟି ଉପାୟ:

1. ପ୍ରଭାବିତ ଅନୁବାଦଗୁଡ଼ିକୁ update କରନ୍ତୁ, କିମ୍ବା
2. ସେଗୁଡ଼ିକୁ `__MISSING__:<new english>` ଭାବେ ସେଟ୍ କରନ୍ତୁ — runtime ତା’ପରେ ସଂଶୋଧିତ ଇଂରାଜୀକୁ serve କରେ (`src/i18n/request.ts::deepMergeFallback`, #7258) ଏବଂ key-ଟି translation ପାଇଁ queue ହୁଏ।

ଯଦି string-ର **ଅର୍ଥ** ପରିବର୍ତ୍ତିତ ହୋଇଥାଏ, ତେବେ **key-ର ନାମ ବଦଳାଇବାକୁ** ପସନ୍ଦ କରନ୍ତୁ: ଏକ ନୂଆ key ପୁରୁଣା ଅନୁବାଦ inherit କରିପାରେ ନାହିଁ। #8463 ଏହି pattern ବ୍ୟବହାର କରିଥିଲା।

```bash
npm run i18n:check-value-drift          # strict (CI ଯାହା ଚଲାଏ)
npm run i18n:check-value-drift:warn     # କେବଳ report
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Base catalog ପଢ଼ିହେବା ନଥିଲେ (base ref ବିନା shallow clone), `check-openapi-breaking`-କୁ ଅନୁକରଣ କରି `SKIP reason=base-unresolved` ସହିତ 0 exit କରେ। କେବଳ release mode: ଏକ feature PR ଇଂରାଜୀକୁ ପୁନଃଲିଖି ସେଠାରେ ଥମିଯାଏ; release refresh ତାହା ପଛରେ ରଖିଯାଇଥିବା ଅନୁବାଦଗୁଡ଼ିକୁ mark କରେ (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, ସମାନ `findStaleTranslations`)।

## ଅନୁମୋଦିତ ତାଲିକା ନୀତି

ପୂର୍ବରୁ ଥିବା ଉଲ୍ଲଂଘନଗୁଡ଼ିକ ଉପରେ ବିଫଳ ହୋଇପାରୁନଥିବା ପ୍ରତ୍ୟେକ ଗେଟ୍ ଏକ ଫ୍ରୋଜେନ୍ ଅନୁମୋଦିତ ତାଲିକା ବ୍ୟବହାର କରେ
(ଯଥା, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ନୀତିଟି ହେଉଛି:

**ମୂଳ କାରଣ ସମାଧାନ କରନ୍ତୁ; ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲେ ଏବଂ ସେହି PR ରେ
ସମାଧାନ କରିହେବ ନାହିଁ କେବଳ ସେତେବେଳେ ଅନୁମୋଦିତ ତାଲିକା ବ୍ୟବହାର କରନ୍ତୁ।**

ଅନୁମୋଦିତ ତାଲିକାରେ ଏକ ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବା ସମୟରେ:

2. ଟ୍ରାକିଂ ଇସ୍ୟୁକୁ ଉଲ୍ଲେଖ କରନ୍ତୁ (ଯଥା, `// #3498 — Phase 2 feature, not yet implemented`)।
3. ଉଲ୍ଲଂଘନ ସମାଧାନ କରୁଥିବା ସେହି PR ରେ ଏଣ୍ଟ୍ରିଟି ହଟାନ୍ତୁ — ଆଉ ସକ୍ରିୟ ଉଲ୍ଲଂଘନକୁ
   ଦମନ ନକରୁଥିବା ଏକ ପୁରୁଣା ଏଣ୍ଟ୍ରି ନିଜେ ଏକ ତ୍ରୁଟି ଅଟେ (କାର୍ଯ୍ୟକାରୀ ହେବା ପରେ
   6A.3 stale-enforcement ଏକ ଅନାଥ ଅନୁମୋଦିତ ତାଲିକା ଏଣ୍ଟ୍ରି ଥିଲେ ଗେଟ୍ରେ
   ବିଫଳ ହେବ)।

ପରୀକ୍ଷାଗୁଡ଼ିକୁ ଶୀଘ୍ର ପାସ୍ କରାଇବା ପାଇଁ ଅନୁମୋଦିତ ତାଲିକାରେ ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ ନାହିଁ। ବଢ଼ୁଥିବା
ଅନୁମୋଦିତ ତାଲିକା ସହିତ ସବୁଜ ଗେଟ୍ ଗୁଣବତ୍ତାର ଏକ ମିଥ୍ୟା ଧାରଣା ଅଟେ।

### ଆପଣଙ୍କ PR ରେ ଏକ ଗେଟ୍ ବିଫଳ ହେଲେ

1. **ଗେଟ୍ର ଆଉଟପୁଟ୍କୁ ସାବଧାନତାର ସହିତ ପଢ଼ନ୍ତୁ** — ନିୟମ ଉଲ୍ଲଂଘନ କରିଥିବା କେଉଁ ଫାଇଲ୍ କିମ୍ବା ସିମ୍ବଲ୍ ତାହା ଏହା ସଠିକ୍ ଭାବେ କହିଥାଏ।
2. **ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରନ୍ତୁ** — ଅଧିକାଂଶ ଗେଟ୍ ନିର୍ଦ୍ଧାରିତ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଯାଞ୍ଚ ଅଟେ, ତେଣୁ କୋଡ୍ ସଠିକ୍ ହେବା ମାତ୍ରେ ସେଗୁଡ଼ିକ ପାସ୍ ହୋଇଯାଏ।
3. **ଯଦି ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲା** (ଅର୍ଥାତ୍, ଆପଣ ଏହାକୁ ଯୋଡ଼ିନଥିଲେ କିନ୍ତୁ ଗେଟ୍ ବର୍ତ୍ତମାନ ଏହାକୁ ଆବୃତ କରୁଛି): ଯୁକ୍ତିସହ ଏକ ମନ୍ତବ୍ୟ ଏବଂ ଟ୍ରାକିଂ ଇସ୍ୟୁ ସହିତ ଏକ ଅନୁମୋଦିତ ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ।
4. **ଯଦି ଗେଟ୍ଟି ଏକ ରାଚେଟ୍** (କଭରେଜ୍, ESLint ସତର୍କତା, ଡୁପ୍ଲିକେସନ୍, ଜଟିଳତା): ଆପଣଙ୍କ ପରିବର୍ତ୍ତନ ମେଟ୍ରିକ୍କୁ ଅଧିକ ଖରାପ କରିଛି। ମୂଳ ସମସ୍ୟା ସମାଧାନ କରନ୍ତୁ, କିମ୍ବା (ବିରଳ କ୍ଷେତ୍ରରେ) ପରିବର୍ତ୍ତନଟି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଏବଂ ମେଟ୍ରିକ୍ର ଅବନତି ଗ୍ରହଣଯୋଗ୍ୟ ହେଲେ `npm run quality:ratchet -- --update` ଚଲାନ୍ତୁ — କିନ୍ତୁ PR ବର୍ଣ୍ଣନାରେ ଏହାର କାରଣ ଲେଖନ୍ତୁ।
5. **ପରାମର୍ଶମୂଳକ ଗେଟ୍ଗୁଡ଼ିକ** (`continue-on-error: true`) ସୂଚନାମୂଳକ — ସେଗୁଡ଼ିକ ମର୍ଜ୍କୁ ଅଟକାଇନଥାଏ କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଏ। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

### ମର୍ଜ / ଡିଡ୍ୟୁପ୍ (ଯାନ୍ତ୍ରିକ, କମ୍ ଝୁମ୍ପ)

- **`check:docs-sync` ଦୁଇଥର ଚାଲେ** — `lint` ଜବ୍ରେ ସ୍ୱତନ୍ତ୍ର ଭାବେ ଏବଂ ପୁଣି `check:docs-all` (`docs-sync-strict`) ଭିତରେ ଓ husky ପ୍ରି-କମିଟ୍ ହୁକ୍ରେ। ✅ **ସମ୍ପନ୍ନ** — ସ୍ୱତନ୍ତ୍ର `lint` ଇନଭୋକେସନ୍ ହଟାଯାଇଛି।
- **CVE ସ୍କାନିଂ** — ❌ **ସଫା ମର୍ଜ ନୁହେଁ।** `audit:deps` ସମସ୍ତ ପାଞ୍ଚଟି ଲକଫାଇଲ୍ରେ ଗୁରୁତର ଆଡଭାଇଜରୀ ଏବଂ ଅସମ୍ପୂର୍ଣ୍ଣ ଅଡିଟ୍କୁ ବ୍ଲକ୍ କରେ, ଯେତେବେଳେ ବର୍ତ୍ତମାନର ନୀତି ଅନୁସାରେ ଉଚ୍ଚ-ସ୍ତରୀୟ ଆଡଭାଇଜରୀଗୁଡ଼ିକୁ ସତର୍କତା ଭାବେ ରିପୋର୍ଟ କରେ; `check:vuln-ratchet` (osv) କେବଳ ଚେକ୍-ଇନ୍ ହୋଇଥିବା ବେସଲାଇନ୍ ବିରୋଧରେ _ରିଗ୍ରେସନ୍_ ହେଲେ ବିଫଳ ହୁଏ ଏବଂ ଆବଶ୍ୟକ ସମୟରେ ମାପ ଅନୁପସ୍ଥିତିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଅର୍ଥ ଭିନ୍ନ — `audit:deps` ହଟାଇଲେ ନିରପେକ୍ଷ ଗୁରୁତର ଗେଟ୍ ଏବଂ ସ୍ୱତନ୍ତ୍ର ପ୍ୟାକେଜ୍ ଅଡିଟ୍ ରସିଦଗୁଡ଼ିକ ହରାଇଯିବ। ଉଭୟକୁ ରଖନ୍ତୁ।
- **ସାଇକେଲ୍ ଚିହ୍ନଟ** — ✅ **ସମ୍ପନ୍ନ** (#15159 G-01/G-02)। ଏଠାରେ ପୁରୁଣା ଲେଖା `check:cycles` କୁ "ଗ୍ରୀନ୍, କ୍ୟୁରେଟେଡ୍" ଗେଟ୍ ଭାବେ ଉଲ୍ଲେଖ କରିଥିଲା ଏବଂ `check:circular-deps` (dpdm) 91ଟି ସାଇକେଲ୍ ରିପୋର୍ଟ କରିଥିବାରୁ ଏହାକୁ ବ୍ଲକିଂ ରଖିବାର ଯୁକ୍ତି ଦେଇଥିଲା। ସେହି ଗ୍ରୀନ୍ ଏକ **ଭୁଲ୍ ଗ୍ରୀନ୍** ଥିଲା: `check:cycles` 5ଟି ସବ୍ଡାଇରେକ୍ଟୋରୀ (450 ଫାଇଲ୍) ସ୍କାନ୍ କରୁଥିଲା, କେବଳ ସ୍ଥିର `import|export … from` ସହିତ ମେଳ କରୁଥିଲା, ଏବଂ ପ୍ରତ୍ୟେକ `@/` ଓ `@omniroute/open-sse/` ସ୍ପେସିଫାୟର୍କୁ ଛାଡ଼ି ଦେଉଥିଲା; ତେଣୁ ରେପୋକୁ ପ୍ରଭାବିତ କରୁଥିବା ଡାଇନାମିକ୍-ଇମ୍ପୋର୍ଟ + ଏଲିଆସ୍ ସାଇକେଲ୍ଗୁଡ଼ିକୁ ଏହା ଦେଖିପାରୁନଥିଲା। ସମାଧାନ କରାଯାଇଛି: ଗେଟ୍ ବର୍ତ୍ତମାନ `src` + `open-sse` (5023 ଫାଇଲ୍) ମାଧ୍ୟମରେ ଚାଲେ, TypeScript AST ରୁ ସ୍ପେସିଫାୟର୍ ସଂଗ୍ରହ କରେ (ତେଣୁ `import("…")` ଗଣନା ହୁଏ ଏବଂ type-position `typeof import("…")` ହୁଏ ନାହିଁ), ଏବଂ tsconfig `paths` ରିଜଲ୍ଭ କରେ। ଏହା 0 ନୁହେଁ, **14**ଟି ସାଇକେଲ୍ ଖୋଜେ। ଗେଟ୍ PR ରେ ପୂର୍ବରୁ ଥିବା 14ଟି ସାଇକେଲ୍ ସମାଧାନ କରାଯାଇପାରିବ ନାହିଁ ବୋଲି, `check:cycles` ବର୍ତ୍ତମାନ ଏକ **ରାଚେଟ୍** (`--ratchet`, `quality-baseline.json` ରେ ceiling `metrics.cycles.value = 14`, `direction: down`) — ଏହା ଯେକୌଣସି _ରିଗ୍ରେସନ୍_କୁ ବ୍ଲକ୍ କରେ ଏବଂ ଗଣନା କେବଳ କମିପାରିବ। CI `npm run check:cycles:ratchet` ଚଲାଏ। ବର୍ନ୍-ଡାଉନ୍ **A-01** ସହିତ ଚାଲିବ। `check:circular-deps` (dpdm) ବ୍ୟାପକ ଦ୍ୱିତୀୟ ମତ ଭାବେ ପରାମର୍ଶମୂଳକ ରହିବ।
