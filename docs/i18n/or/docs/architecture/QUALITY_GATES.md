## ଗେଟ୍ ଇନଭେଣ୍ଟରି ଏବଂ ନିଷ୍ପାଦନ ପ୍ରୋଫାଇଲ୍

### ପ୍ରାର୍ଥୀ ଗ୍ରହଣ

CI ଏବଂ Quality Gates ୱର୍କଫ୍ଲୋ ପ୍ରତ୍ୟେକ ଏକ ସ୍ଥିର ନିଷ୍ପତ୍ତି ନିର୍ଗତ କରେ: `Gate / CI` ଏବଂ
`Gate / Quality`। ସେମାନଙ୍କର ସଂସ୍କରଣଭିତ୍ତିକ ଗ୍ରହଣ ନୀତି ପ୍ରତ୍ୟେକ ଅପ୍ଷ୍ଟ୍ରିମ୍ ଜବ୍କୁ
ଆବଶ୍ୟକ କିମ୍ବା ପରାମର୍ଶମୂଳକ ଭାବେ ତାଲିକାଭୁକ୍ତ କରେ। ଏକ ପ୍ରଯୁଜ୍ୟ ଆବଶ୍ୟକ ଜବ୍ ନିଶ୍ଚିତ ଭାବେ ସଫଳ ହେବା ଦରକାର: ଅନୁପସ୍ଥିତ,
ବାତିଲ୍ ହୋଇଥିବା, ଏଡ଼ାଇ ଦିଆଯାଇଥିବା, ବିଚାରାଧୀନ ଏବଂ ଅଜଣା ଫଳାଫଳ PASS ପ୍ରତିଷ୍ଠା କରିପାରିବ ନାହିଁ। ଏକ ବୈଧ
କେବଳ-ଡକ୍ସ କିମ୍ବା କେବଳ-କ୍ୟାଟାଲଗ୍ ବର୍ଗୀକରଣ ଏକ କୋଡ୍ ଲେନ୍କୁ ଅପ୍ରଯୁଜ୍ୟ କରିପାରେ;
ଏକ ଡ୍ରାଫ୍ଟ PR ଗ୍ରହଣଯୋଗ୍ୟ ପ୍ରାର୍ଥୀ ନୁହେଁ। ଏକ `hotfix` ଲେବଲ୍ ପ୍ରମାଣର ଆବଶ୍ୟକତାକୁ ଛାଡ଼ କରେ ନାହିଁ।

ଉଭୟ ୱର୍କଫ୍ଲୋ main/release ବ୍ରାଞ୍ଚକୁ ଆସୁଥିବା PR, `main`କୁ ପୁଶ୍, ମାନୁଆଲ୍ ଡିସ୍ପାଚ୍
ଏବଂ ମର୍ଜ୍-ଗ୍ରୁପ୍ ଇଭେଣ୍ଟକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ। ପୁଶ୍, ଡିସ୍ପାଚ୍ ଏବଂ ମର୍ଜ୍-ଗ୍ରୁପ୍ ସମ୍ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାଏ।
`release/**`କୁ ପୁଶ୍ ସେଗୁଡ଼ିକୁ ଆରମ୍ଭ କରେ ନାହିଁ (2026-10-18): ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ତାହାର PRରେ ପୂର୍ବରୁ ମ୍ୟାଟ୍ରିକ୍ସ ଚଲାଇସାରିଛି
ଏବଂ ମର୍ଜ୍ ହୋଇଥିବା ସଂଯୋଜନ Release-Greenର ଜବ୍ (`docs/ops/RUNNER_BOX.md` → ହୋଷ୍ଟେଡ୍ ଲେନ୍)। ଫର୍କ
ଏବଂ ମର୍ଜ୍ ଗ୍ରୁପ୍ ସେହି ଜବ୍ଗୁଡ଼ିକ ପାଇଁ ହୋଷ୍ଟେଡ୍ ରନର୍ ବ୍ୟବହାର କରେ, ଯେଉଁଗୁଡ଼ିକ ଅନ୍ୟଥା ସେଲ୍ଫ-ହୋଷ୍ଟେଡ୍
ରନର୍ ବାଛନ୍ତି; ରୋଲଆଉଟ୍ ପୂର୍ବରୁ ପର୍ଯ୍ୟାପ୍ତ ହୋଷ୍ଟେଡ୍ କ୍ଷମତା ଯାଞ୍ଚ କରାଯିବା ଆବଶ୍ୟକ।

ପ୍ରତ୍ୟେକ JSON ରସିଦ ଚେକ୍ଆଉଟ୍ ହୋଇଥିବା SHA, ୱର୍କଫ୍ଲୋ ରନ୍ ଏବଂ ପ୍ରୟାସକୁ ଚିହ୍ନଟ କରେ।
CLI ଏକ ଚେକ୍ଆଉଟ୍/ଇଭେଣ୍ଟ SHA ଅମେଳକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ୱର୍କଫ୍ଲୋ ପରୀକ୍ଷାଗୁଡ଼ିକ ନୀତି ସଦସ୍ୟତାକୁ
ନିଷ୍ପତ୍ତି ଜବ୍ର `needs` ତାଲିକା ସହ ବାନ୍ଧିଥାଏ, ଯାହାଦ୍ୱାରା ଏକ ନୂଆ କିମ୍ବା ଅପସାରିତ ଲେନ୍ ନିରବରେ ଅଦୃଶ୍ୟ ହୋଇପାରିବ ନାହିଁ।
ରସିଦଗୁଡ଼ିକ କେବଳ ସେମାନଙ୍କ ନିଜସ୍ୱ କାର୍ଯ୍ୟପ୍ରବାହକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ, ପ୍ରକାଶନ, ଡିପ୍ଲୟମେଣ୍ଟ କିମ୍ବା ଏକ ବିଦ୍ୟମାନ ଆଡଭାଇଜରି ସ୍କାନର୍ର ଆଭ୍ୟନ୍ତରୀଣ ବିଷୟକୁ ନୁହେଁ। ପ୍ରଯୁଜ୍ୟ ଯାଞ୍ଚଗୁଡ଼ିକୁ ବ୍ରାଞ୍ଚ ନିୟମରେ ଆବଶ୍ୟକୀୟ କରିବା ଏକ ପୃଥକ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ; ସେମାନଙ୍କ ଜବ୍ଗୁଡ଼ିକୁ ପରିଭାଷିତ କରିବା ମାତ୍ର ଦ୍ୱାରା କୌଣସି ବ୍ରାଞ୍ଚ ସୁରକ୍ଷିତ ହୁଏ ନାହିଁ।

`API Route Typecheck` ହେଉଛି ଏକ ସ୍ୱାଧୀନ କାର୍ଯ୍ୟପ୍ରବାହ ଯାଞ୍ଚ, ଯାହା ଉଭୟ ସମନ୍ୱିତ ନିଷ୍କର୍ଷ ଏବଂ ସ୍ଥାନୀୟ ପୂର୍ଣ୍ଣ ପର୍ଯ୍ୟବେକ୍ଷକଙ୍କ ଷ୍ଟାଟିକ୍ ପ୍ରୋଫାଇଲ୍ର ବାହାରେ ଅଛି। ସଠିକ୍ ପ୍ରାର୍ଥୀ ପାଇଁ ଏହାର ଫଳାଫଳକୁ ପୃଥକ ଭାବରେ ଯାଞ୍ଚ କରନ୍ତୁ। `.github/workflows/api-route-typecheck.yml` `main` କିମ୍ବା `release/**`କୁ ଲକ୍ଷ୍ୟ କରୁଥିବା PR, ଉଭୟ ବ୍ରାଞ୍ଚ ପରିବାରକୁ କରାଯାଉଥିବା ପୁଶ୍ ଏବଂ ମାନୁଆଲ୍ ଡିସ୍ପାଚ୍ରେ ଚାଲେ। ଏଥିରେ କୌଣସି ପାଥ୍ ଫିଲ୍ଟର୍ ନାହିଁ। PR ବେସ୍କୁ ପୁନଃଲକ୍ଷ୍ୟ କରିବା ଏକ ନୂତନ ଯାଞ୍ଚର ଅନୁରୋଧ କରେ; ବଡି/ଟାଇଟଲ୍ ସମ୍ପାଦନାଗୁଡ଼ିକ କେବଳ-ପର୍ଯ୍ୟବେକ୍ଷଣ ନାମ `Admission not requested / API Route Typecheck` ବ୍ୟବହାର କରେ ଏବଂ ଆଡମିସନ୍ ଯାଞ୍ଚକୁ ପ୍ରତିସ୍ଥାପନ କରିପାରେ ନାହିଁ। କାର୍ଯ୍ୟପ୍ରବାହଟି କୌଣସି ମର୍ଜ୍-ଗ୍ରୁପ୍ ଟ୍ରିଗର୍ ଘୋଷଣା କରେ ନାହିଁ। ଏହି ଯାଞ୍ଚକୁ ଆବଶ୍ୟକ କରୁଥିବା ଯେକୌଣସି ମର୍ଜ୍-କ୍ୟୁ ରୋଲଆଉଟ୍କୁ ପ୍ରଥମେ ସେହି ଇଭେଣ୍ଟ ପାଇଁ ଏହାର ନିଷ୍ପାଦନ ସୁନିଶ୍ଚିତ କରିବାକୁ ପଡ଼ିବ।

### UI ନିଷ୍ପାଦନ କ୍ଷମତା

CI ସମ୍ପୂର୍ଣ୍ଣ UI ଇନଭେଣ୍ଟରିକୁ ଚାରିଟି `test-vitest` ମ୍ୟାଟ୍ରିକ୍ସ ଶାର୍ଡ ଭାବେ ଚଲାଏ, ପ୍ରତ୍ୟେକରେ ସର୍ବାଧିକ
ଦୁଇଟି ୱର୍କର୍ ଏବଂ ବିଦ୍ୟମାନ 15-ମିନିଟ୍ ଜବ୍ ସମୟସୀମା ରହେ। ପ୍ରଥମ ଶାର୍ଡ MCP/autoCombo Vitest ସୁଟ୍କୁ ମଧ୍ୟ ଚଲାଏ।

ସହଭାଗୀ `test:unit:ci:shard` କମାଣ୍ଡ୍ଟି `scripts/ci/unit-progress-reporter.mjs` ମାଧ୍ୟମରେ `primary`, `dashboard` ଏବଂ `serial` ପର୍ଯ୍ୟାୟଗୁଡ଼ିକୁ ରେକର୍ଡ କରେ। ସାଧାରଣ ପରୀକ୍ଷା ରିପୋର୍ଟ ଉପଲବ୍ଧ ରହେ। ଏକ ପୃଥକ, କେବଳ-ମେଟାଡାଟା ରସିଦ ପ୍ରତ୍ୟେକ ଫାଇଲ୍ର ଆରମ୍ଭ ଏବଂ ସମାପ୍ତିକୁ ରେକର୍ଡ କରେ, ଏବଂ 30-ସେକେଣ୍ଡର ହାର୍ଟବିଟ୍ ଏବେ ମଧ୍ୟ ସକ୍ରିୟ ଥିବା ଫାଇଲ୍ଗୁଡ଼ିକ ଓ ସେଗୁଡ଼ିକର ବିତିଥିବା ସମୟକୁ ତାଲିକାଭୁକ୍ତ କରେ। ଏହା କେବଳ ଅନୁମୋଦିତ ତାଲିକାରେ ଥିବା ନିଷ୍ପାଦନ ମେଟାଡାଟାକୁ ରେକର୍ଡ କରେ; ପରୀକ୍ଷା ବର୍ଣ୍ଣନା, ଆଉଟ୍ପୁଟ୍, ତ୍ରୁଟିର ବିସ୍ତୃତ ବିବରଣୀ ଏବଂ ସମ୍ପୂର୍ଣ୍ଣ ପରିବେଶକୁ ସିରିଆଲାଇଜ୍ କରାଯାଏ ନାହିଁ।

CI ଏବଂ Quality, JSONL ଫାଇଲ୍ଗୁଡ଼ିକୁ `unit-progress-ci-<run>-<attempt>-<shard>` ଏବଂ `unit-progress-quality-<run>-<attempt>-<shard>` ଭାବରେ ସଂରକ୍ଷଣ କରନ୍ତି। ଏକ ଜବ୍ ଟାଇମ୍ଆଉଟ୍ ପରବର୍ତ୍ତୀ ଅପଲୋଡ୍କୁ ବାଧା ଦେଇପାରେ; ପୂର୍ବରୁ ନିର୍ଗତ ହୋଇଥିବା ହାର୍ଟବିଟ୍ଗୁଡ଼ିକ ନିଦାନମୂଳକ ପ୍ରମାଣ ଭାବରେ ରହିଥାଏ। ହାର୍ଟବିଟ୍ ଅନୁପସ୍ଥିତ ରହିବା ଏକ ଅବରୋଧିତ କିମ୍ବା ସମାପ୍ତ କରାଯାଇଥିବା ରନର୍ ପ୍ରକ୍ରିୟାକୁ ମଧ୍ୟ ସୂଚାଇପାରେ। ଏହି ରସିଦଗୁଡ଼ିକ ବର୍ତ୍ତମାନର ପରୀକ୍ଷା ଚୟନ, ସମକାଳୀନତା, ସମୟସୀମା ଏବଂ ପ୍ରସ୍ଥାନ ସ୍ଥିତିକୁ ଅପରିବର୍ତ୍ତିତ ରଖେ; ଏଗୁଡ଼ିକ ପ୍ରାର୍ଥୀ-ଗ୍ରହଣ ସମ୍ବନ୍ଧୀୟ ନିଷ୍ପତ୍ତି ନୁହେଁ।

### ସ୍ୱୀକୃତି ଫଳାଫଳ ସଂକଳନକାରୀରେ ସଂରକ୍ଷିତ ପ୍ରମାଣ

`scripts/quality/validate-release-acceptance.mjs` ଦିଆଯାଇଥିବା ଯୋଜନା ଏବଂ ଏହାର ମାନିଫେଷ୍ଟଗୁଡ଼ିକୁ ସଂକଳନ କରେ; ଯୋଜନାଟି ସମ୍ପୂର୍ଣ୍ଣ ରିଲିଜ୍ ପାଇପଲାଇନ୍କୁ ଆବରଣ କରେ ବୋଲି ଏହା ପ୍ରତିଷ୍ଠା କରେ ନାହିଁ। ଯୋଜନା `VERIFIED` ହେଲେ ମଧ୍ୟ ଏହାର ରିପୋର୍ଟଗୁଡ଼ିକ ସ୍ପଷ୍ଟ ଭାବେ `releaseAcceptance: false` ସେଟ୍ କରନ୍ତି। `release-acceptance.yml` ୱର୍କଫ୍ଲୋ ଏବେ ବି shadow ପରୀକ୍ଷା ଫିକ୍ସଚର୍ ବ୍ୟବହାର କରେ, ପ୍ରକୃତ build, package, boot କିମ୍ବା promotion ରସିଦ ନୁହେଁ।

ସଂରକ୍ଷିତ ପ୍ରମାଣ ଯାଞ୍ଚ କରିବାକୁ CLI ପାଇଁ `--evidence-root` ଆବଶ୍ୟକ। ଫାଇଲଗୁଡ଼ିକ `<evidence-root>/<artifact_id>/<member>` ପଥରେ ଖୋଜାଯାଏ ଏବଂ ସେଗୁଡ଼ିକର SHA-256 ହ୍ୟାଶ୍ ଗଣନା କରାଯାଏ। ପ୍ରମାଣ ବିନା PASS ରେକର୍ଡ, ନିଖୋଜ କିମ୍ବା ବଦଳିଥିବା ଫାଇଲ୍, ଅସୁରକ୍ଷିତ ପଥ କିମ୍ବା ସିମଲିଙ୍କ୍ ଯାଞ୍ଚକୁ ଅଟକାଏ। ନିଖୋଜ ଫାଇଲଗୁଡ଼ିକ ସଫଳ ରନ୍ର ଖାଲି ଲଗ୍ ସହିତ ସମାନ ନୁହେଁ। ବିଦ୍ୟମାନ SHA/run/attempt ଯାଞ୍ଚଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହେ: ବାଇଟ୍ ମେଳ ହେଲେ ବି ପୁରୁଣା ରସିଦ ବୈଧ ହୁଏ ନାହିଁ। ଫାଇଲ୍ର ଅଖଣ୍ଡତା କାର୍ଯ୍ୟନିର୍ବାହର ପ୍ରାମାଣିକତା କିମ୍ବା ଆର୍ଟିଫ୍ୟାକ୍ଟର promotion ର ପ୍ରମାଣ ନୁହେଁ।

### ପ୍ରକାଶିତ-ଆଧାର ଡକ୍ୟୁମେଣ୍ଟେସନ୍ର ସ୍ୱାସ୍ଥ୍ୟ

`.github/workflows/i18n-base-health.yml` ଚୟନିତ `main` ଏବଂ `release/v*` ପୁଷ୍ଗୁଡ଼ିକ ପରେ ଓ ମାନୁଆଲ୍ ଡିସ୍ପାଚ୍ ସମୟରେ ଡକ୍ୟୁମେଣ୍ଟେସନ୍ର ସ୍ୱାସ୍ଥ୍ୟ ନିରୀକ୍ଷଣ କରେ। ଏହାର ଫିଲ୍ଟର୍ଗୁଡ଼ିକ ଡକ୍ୟୁମେଣ୍ଟେସନ୍, ରୁଟ୍ Markdown, `llm.txt`, ଅନୁବାଦ ସ୍ଥିତି/ବିନ୍ୟାସ ଏବଂ ପ୍ରାସଙ୍ଗିକ i18n ଟୁଲିଂକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ। ଏକମାତ୍ର `Published base documentation health` ଜବ୍ ହୋଷ୍ଟ କରାଯାଇଥିବା Ubuntu ଏବଂ ପାଞ୍ଚ-ମିନିଟ୍ ସମୟସୀମା ବ୍ୟବହାର କରେ। ଏହା କେବଳ-ପଠନୀୟ ବୈଧୀକରଣ କରେ ଏବଂ ନିର୍ଭରଶୀଳତା ଇନ୍ଷ୍ଟଲେସନ୍, ଅନୁବାଦ କିମ୍ବା ସ୍ଥିତି ଗ୍ରହଣ ବିନା ଏକ ଡାୟାଗ୍ନୋଷ୍ଟିକ୍ ରସିଦ ଲେଖେ।

`scripts/i18n/check-base-health.mjs` ପାଇଁ source-hash, missing-target, target-hash, stale-translation ଏବଂ section-cache ଅସଙ୍ଗତି ଶୂନ୍ୟ ହେବା ଆବଶ୍ୟକ। ଏହା ବର୍ତ୍ତମାନର ମୂଳ ଡକ୍ୟୁମେଣ୍ଟ/ଲୋକେଲ୍ ପରିସର ଏବଂ ତାହାର ରେକର୍ଡ କରାଯାଇଥିବା ଉତ୍ପତ୍ତିକୁ ମଧ୍ୟ ବୈଧ କରେ। ଅବୈଧ ପ୍ରସଙ୍ଗ, ଅସମ୍ପୂର୍ଣ୍ଣ କଭରେଜ୍ କିମ୍ବା ବାଧାପ୍ରାପ୍ତ ଚେକର୍ `INCOMPLETE` ଉତ୍ପନ୍ନ କରେ; ସୁନିଶ୍ଚିତ ଡ୍ରିଫ୍ଟ `FAIL` ଉତ୍ପନ୍ନ କରେ। ଉଭୟ ଏକ ବିଫଳ ପ୍ରସ୍ଥାନ ସ୍ଥିତି ଫେରାନ୍ତି। ରସିଦଟି checkout SHA, workflow, run ଏବଂ attempt ସହିତ ବାନ୍ଧି ରଖାଯାଏ ଏବଂ `i18n-base-health-<sha>-<run>-<attempt>` ଭାବେ ସଂରକ୍ଷିତ ହୁଏ।

ଏହା ପ୍ରକାଶିତ ଆଧାରର ଏକ ସ୍ୱାଧୀନ ପର୍ଯ୍ୟବେକ୍ଷଣ। ଏହା ଏକ PR କିମ୍ବା merge-group ଇଭେଣ୍ଟ, ଆବଶ୍ୟକ PR ଯାଞ୍ଚ, npm ଉପନାମ କିମ୍ବା static-scan ପ୍ରୋଫାଇଲ୍ ସଦସ୍ୟ ଯୋଡ଼େ ନାହିଁ। ବିଦ୍ୟମାନ ଭିନ୍ନତାମୂଳକ PR ନୀତି ଏବଂ ଅନ୍ତର୍ନିହିତ ଚେକର୍ର ପରାମର୍ଶମୂଳକ ବର୍ଗୀକରଣଗୁଡ଼ିକ ପୃଥକ ରହେ। ଏକ ସଫଳ ଅପଲୋଡ୍ ବିଫଳ ସ୍ୱାସ୍ଥ୍ୟ ଫଳାଫଳକୁ PASSରେ ପରିବର୍ତ୍ତନ କରିପାରିବ ନାହିଁ।

   ମର୍ଜ୍କୁ ଅବରୋଧ କରନ୍ତି ନାହିଁ, କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଆନ୍ତି। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ 2026-06-17 ରେ ସକ୍ରିୟ ଗେଟ୍ ସ୍ଥିତି ବିପକ୍ଷରେ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ବିଶ୍ୱାସ କରନ୍ତୁ, କିନ୍ତୁ ଯାଞ୍ଚ ମଧ୍ୟ କରନ୍ତୁ);
ଅନେକ “ସ୍ପଷ୍ଟ” ମର୍ଜ ଋଣ ଲୁଚାଇଥିବା ଜଣାପଡ଼ିଲା ଏବଂ ସେଗୁଡ଼ିକ **ସିଧାସଳଖ ପ୍ରତିସ୍ଥାପନଯୋଗ୍ୟ ନୁହେଁ**।

- **`check:docs-sync` ଦୁଇଥର ଚାଲେ** — `lint` ଜବ୍ରେ ସ୍ୱତନ୍ତ୍ର ଭାବେ ଏବଂ ପୁଣି `check:docs-all` (`docs-sync-strict`) ଭିତରେ ଓ husky pre-commit hook ରେ। ✅ **ସମ୍ପନ୍ନ** — ସ୍ୱତନ୍ତ୍ର `lint` ଆହ୍ୱାନ ଅପସାରିତ।
- **CVE ସ୍କାନିଂ** — ❌ **ଏକ ସ୍ୱଚ୍ଛ ମର୍ଜ ନୁହେଁ।** `audit:deps` ସମସ୍ତ ପାଞ୍ଚଟି lockfile ମଧ୍ୟରେ ଗୁରୁତର ପରାମର୍ଶ ଏବଂ ଅସମ୍ପୂର୍ଣ୍ଣ ଅଡିଟ୍କୁ ବ୍ଲକ୍ କରେ, ଯେତେବେଳେ ବର୍ତ୍ତମାନର ନୀତି ଅନୁଯାୟୀ ଉଚ୍ଚ-ଗୁରୁତ୍ୱର ପରାମର୍ଶଗୁଡ଼ିକୁ ଚେତାବନୀ ଭାବେ ରିପୋର୍ଟ କରେ; `check:vuln-ratchet` (osv) କେବଳ ଚେକ୍-ଇନ୍ ହୋଇଥିବା ବେସ୍ଲାଇନ୍ ତୁଳନାରେ ଏକ _ଅବନତି_ ହେଲେ ବିଫଳ ହୁଏ ଏବଂ ଆବଶ୍ୟକ ସମୟରେ ଅନୁପସ୍ଥିତ ମାପକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଅର୍ଥବିଜ୍ଞାନ ଭିନ୍ନ — `audit:deps` କୁ ଡ୍ରପ୍ କଲେ ପରମ ଗୁରୁତର ଗେଟ୍ ଏବଂ ସ୍ୱାଧୀନ ପ୍ୟାକେଜ୍ ଅଡିଟ୍ ପ୍ରମାଣ ହରାଇବ। ଉଭୟକୁ ରଖନ୍ତୁ।
