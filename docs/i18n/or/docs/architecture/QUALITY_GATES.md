ଏହି ଡକ୍ୟୁମେଣ୍ଟଟି OmniRoute ର ସମସ୍ତ CI ଗୁଣବତ୍ତା ଗେଟ୍ ପାଇଁ ପ୍ରାମାଣିକ ସନ୍ଦର୍ଭ।
ଏହା ପ୍ରତ୍ୟେକ ଗେଟ୍, ଏହା କ’ଣ ଯାଞ୍ଚ କରେ, କେଉଁ CI ଜବ୍ରେ ଏହା ଚାଲେ, ଏହା
ଏକ ରାଚେଟ୍ ବେସ୍ଲାଇନ୍ କିମ୍ବା ଏକ ପାସ୍/ଫେଲ୍ ନୀତି ବ୍ୟବହାର କରେ କି ନାହିଁ, ଏବଂ ଏହା ବିଲ୍ଡ୍କୁ ଅବରୋଧ କରେ କିମ୍ବା କେବଳ ପରାମର୍ଶମୂଳକ—ତାହା ବର୍ଣ୍ଣନା କରେ।

ଏକ ସଂକ୍ଷିପ୍ତ ସାରାଂଶ ଏବଂ ଅନୁମତି-ତାଲିକା ନୀତି ପାଇଁ, `AGENTS.md` ରେ ଥିବା
"ଗୁଣବତ୍ତା ଗେଟ୍ ଏବଂ ରାଚେଟ୍" ବିଭାଗ ଦେଖନ୍ତୁ। ସେହି ସିଷ୍ଟମ୍ର ସମାଲୋଚନାମୂଳକ ମୂଲ୍ୟାଙ୍କନ,
ପରିପକ୍ୱତା ବର୍ଗୀକରଣ ଏବଂ ଟୁଲ୍-ନିରପେକ୍ଷ ପ୍ରତିରୂପଣ ଯୋଜନା ପାଇଁ,
[ଗୁଣବତ୍ତା ଗେଟ୍ ପ୍ଲେବୁକ୍](../ops/QUALITY_GATE_PLAYBOOK.md) ଦେଖନ୍ତୁ।

## Gate ଇନଭେଣ୍ଟରୀ ଏବଂ ଏକ୍ସିକ୍ୟୁସନ୍ ପ୍ରୋଫାଇଲ୍

### ପ୍ରାର୍ଥୀ ଗ୍ରହଣ

CI ଏବଂ Quality Gates ୱର୍କଫ୍ଲୋ ପ୍ରତ୍ୟେକଟି ଏକ ସ୍ଥିର ନିଷ୍ପତ୍ତି ପ୍ରକାଶ କରେ: `Gate / CI` ଏବଂ
`Gate / Quality`। ସେମାନଙ୍କର ସଂସ୍କରଣଭିତ୍ତିକ ଗ୍ରହଣ ନୀତି ପ୍ରତ୍ୟେକ upstream jobକୁ
ଆବଶ୍ୟକ କିମ୍ବା ପରାମର୍ଶମୂଳକ ଭାବେ ତାଲିକାଭୁକ୍ତ କରେ। ପ୍ରୟୋଜ୍ୟ ଆବଶ୍ୟକ job ସଫଳ ହେବା
ଦରକାର: ଅନୁପସ୍ଥିତ, ବାତିଲ, skip, pending ଏବଂ ଅଜଣା ଫଳାଫଳ PASS ସ୍ଥାପନ କରିପାରେ ନାହିଁ। ଏକ ବୈଧ
docs-only କିମ୍ବା catalog-only ଶ୍ରେଣୀକରଣ ଏକ code laneକୁ ଅପ୍ରୟୋଜ୍ୟ କରିପାରେ;
draft PR ଗ୍ରହଣଯୋଗ୍ୟ ପ୍ରାର୍ଥୀ ନୁହେଁ। `hotfix` label ପ୍ରମାଣକୁ ଛାଡ଼ ଦେଉନାହିଁ।

ଉଭୟ ୱର୍କଫ୍ଲୋ main/release branchକୁ ଯାଉଥିବା PR, `main`କୁ push, manual dispatch
ଏବଂ merge-group eventଗୁଡ଼ିକୁ ଆବୃତ କରେ। Push, dispatch ଏବଂ merge-group ସମ୍ପୂର୍ଣ୍ଣ
selection ଚଳାଏ। `release/**`କୁ push ଏଗୁଡ଼ିକୁ ଆରମ୍ଭ କରେ ନାହିଁ (2026-10-18): ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ
ନିଜ PRରେ matrix ଚଳାଇସାରିଛି ଏବଂ merged combination ହେଉଛି Release-Greenର କାମ
(`docs/ops/RUNNER_BOX.md` → Hosted lane)। Fork ଏବଂ merge groupଗୁଡ଼ିକ ସାଧାରଣତଃ self-hosted
runner ବାଛୁଥିବା jobଗୁଡ଼ିକ ପାଇଁ hosted runner ବ୍ୟବହାର କରେ; rollout ପୂର୍ବରୁ ପର୍ଯ୍ୟାପ୍ତ hosted
capacity ଯାଞ୍ଚ କରିବା ଆବଶ୍ୟକ।

ଏକ ସାଧାରଣ PR fast selection ଚଳାଏ। admission policyର `full-code` ଏବଂ `full-code-e2e` lane
(E2E, integration, package artifact, Electron smoke, Bun SQLite, ecosystem
ଏବଂ protocol client) କେବଳ ଏକ Mergify queue draft କିମ୍ବା full runରେ ଚାଲେ:
`gh workflow run ci.yml --ref <branch>`।

ପ୍ରତ୍ୟେକ JSON receipt ଯାଞ୍ଚ କରାଯାଇଥିବା SHA, workflow run ଏବଂ attempt ଚିହ୍ନଟ କରେ।
CLI checkout/event SHA ମେଳ ନଥିଲେ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। Workflow testଗୁଡ଼ିକ policy membershipକୁ
verdict jobର `needs` ତାଲିକା ସହିତ ବାନ୍ଧିଥାଏ, ଯାହାଦ୍ୱାରା ନୂତନ କିମ୍ବା ଅପସାରିତ lane ନିରବରେ
ଅଦୃଶ୍ୟ ହୋଇପାରେ ନାହିଁ। Receiptଗୁଡ଼ିକ ନିଜ workflowକୁ ଆବୃତ କରେ, publication, deployment କିମ୍ବା
ବର୍ତ୍ତମାନର advisory scannerର ଆଭ୍ୟନ୍ତରୀଣ ଅଂଶଗୁଡ଼ିକୁ ନୁହେଁ। Branch ruleରେ ଉଭୟ check name
ସକ୍ରିୟ କରିବା ଏକ ପୃଥକ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ; ଏହି jobଗୁଡ଼ିକ ଯୋଡ଼ିବା ନିଜେ ଏକ branchକୁ
ସୁରକ୍ଷିତ କରେ ନାହିଁ।

### Merge queue

`queue` label ଏକ PRକୁ Mergify queue (`.mergify.yml`)କୁ ପଠାଏ। Mergify ଏକ
`mergify/merge-queue/` branchରେ draft PR ଖୋଲେ, ସେଠାରେ CI ସମ୍ପୂର୍ଣ୍ଣ selection ଚଳାଏ, ଏବଂ
`Gate / CI`, `Gate / Quality` ଏବଂ `Merge integrity (changelog + generated skills)` pass
କଲେ ମୂଳ PR merge ହୁଏ।

Mergify draftର descriptionରେ ତାହାର queue summary ଲେଖେ, ଏବଂ ଅନ୍ୟ appଗୁଡ଼ିକ ମଧ୍ୟ ଏହାକୁ
ସମ୍ପାଦନ କରିପାରନ୍ତି। ଏପରି draft ଉପରେ `pull_request` `edited` event ନିଜସ୍ୱ concurrency group
(`-queue-edit-<run_id>`) ନିଏ, ଯାହାଦ୍ୱାରା ଏହା draftର ପ୍ରକୃତ runକୁ cancel କରିପାରେ ନାହିଁ,
ଏବଂ gate ଓ matrixକୁ skip କରେ। କେବଳ `Merge integrity` ଚାଲିଥାଏ। Skipped gate job ଏକ
ଭିନ୍ନ check name ବହନ କରେ, କାରଣ Mergify skipped `Gate / CI`କୁ failed check ଭାବେ ପଢ଼ି
PRକୁ queueରୁ ବାହାର କରିଦିଏ।

Dequeue ପରେ push ସବୁବେଳେ PRକୁ ପୁନଃ queue କରେ ନାହିଁ। ଏଥିରେ `@mergifyio queue` comment କରନ୍ତୁ।

### Acceptance reducerରେ ସଂରକ୍ଷିତ ପ୍ରମାଣ

`scripts/quality/validate-release-acceptance.mjs` ଦିଆଯାଇଥିବା plan ଏବଂ ତାହାର
manifestଗୁଡ଼ିକୁ reduce କରେ; ଏହା planଟି ସମ୍ପୂର୍ଣ୍ଣ release pipelineକୁ ଆବୃତ କରୁଛି ବୋଲି
ସ୍ଥାପନ କରେ ନାହିଁ। ଏହାର reportଗୁଡ଼ିକ ସ୍ପଷ୍ଟ ଭାବରେ `releaseAcceptance: false` ସେଟ୍ କରେ,
ଏପରିକି ସେହି plan `VERIFIED` ହେଲେ ମଧ୍ୟ। `release-acceptance.yml` workflow ଏପର୍ଯ୍ୟନ୍ତ
ପ୍ରକୃତ build, package, boot କିମ୍ବା promotion receipt ପରିବର୍ତ୍ତେ shadow fixture ବ୍ୟବହାର କରେ।

Retained evidence ଯାଞ୍ଚ କରିବା ପାଇଁ CLI `--evidence-root` ଆବଶ୍ୟକ କରେ। Fileଗୁଡ଼ିକୁ
`<evidence-root>/<artifact_id>/<member>` ଭାବେ resolve କରାଯାଏ ଏବଂ SHA-256 ଭାବେ hash କରାଯାଏ।
Evidence ବିନା PASS record, ଅନୁପସ୍ଥିତ କିମ୍ବା ପରିବର୍ତ୍ତିତ file, ଅସୁରକ୍ଷିତ path କିମ୍ବା symlink
verificationକୁ ବାଧା ଦିଏ। ଅନୁପସ୍ଥିତ file ଖାଲି ସଫଳ log ସହିତ ସମାନ ନୁହେଁ। ବର୍ତ୍ତମାନର
SHA/run/attempt ଯାଞ୍ଚଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହେ: ମେଳ ଖାଉଥିବା bytes ଏକ ପୁରୁଣା receiptକୁ ଉଦ୍ଧାର
କରିପାରେ ନାହିଁ। File integrity execution authenticity କିମ୍ବା artifact promotionର ପ୍ରମାଣ ନୁହେଁ।

### Static scan ଇନଭେଣ୍ଟରୀ

ସଂସ୍କରଣଭିତ୍ତିକ npm-alias ଇନଭେଣ୍ଟରୀ ଏବଂ static-scan membership
`config/quality/gate-manifest.json`ରେ ରହେ। `npm run check:gate-manifest` ଚଳାଇ
`package.json` ବିରୋଧରେ script name ଏବଂ ସଠିକ command ଯାଞ୍ଚ କରନ୍ତୁ; addition, removal ଏବଂ
command drift ଉଭୟ local hook ଏବଂ CIର change-classification jobଗୁଡ଼ିକୁ fail କରେ।
ଏକ alias workflow job, matrix instance କିମ୍ବା test case ନୁହେଁ: ଏହି countଗୁଡ଼ିକୁ
ପରସ୍ପର ବଦଳାଯୋଗ୍ୟ ଭାବେ ପ୍ରସ୍ତୁତ କରାଯିବା ଉଚିତ୍ ନୁହେଁ।

ଚଳାଇବା ବିନା ଚୟନ ହୋଇଥିବା aliasଗୁଡ଼ିକୁ ଦେଖିବା ପାଇଁ `npm run quality:scan -- --list` କିମ୍ବା
`npm run quality:scan:fast -- --list` ବ୍ୟବହାର କରନ୍ତୁ। Runner npm entrypointକୁ invoke କରେ,
ତେଣୁ ଏହାର runtime (configured ଥିଲେ Bun ସହିତ) ଅବିକୃତ ରହେ। Manifest ସେହି profileଗୁଡ଼ିକ
ବାହାରର aliasଗୁଡ଼ିକୁ separately invoked ଭାବେ ରେକର୍ଡ କରେ, ଏବଂ read-only scan profileରେ
maintenance command ନିଷିଦ୍ଧ।

ଏହି profileଗୁଡ଼ିକ କେବଳ static scanକୁ ଆବୃତ କରେ। ଏଗୁଡ଼ିକ product test, coverage, packaging,
external check କିମ୍ବା ଏକ ପ୍ରାର୍ଥୀର ସମ୍ପୂର୍ଣ୍ଣ release acceptanceକୁ certify କରେ ନାହିଁ।
Workflow admission ସଂଯୁକ୍ତ `config/quality/admission-policy.json` ଏବଂ

test ନଥିଲେ, ଏହା ନିର୍ଦ୍ଧାରଣାତ୍ମକ

### Derived values: `pr` ଏବଂ `release` gate modes

ଏକ feature PR କେବେ ମଧ୍ୟ ତାହାର baseର state ଉପରେ ନିର୍ଭର କରୁଥିବା value ଲେଖେନାହିଁ: provider,
migration, MCP-tool ଏବଂ strategy counts, README SVG numbers, facts snapshot। ଗୋଟିଏ step
ସେଗୁଡ଼ିକୁ ସମସ୍ତଙ୍କୁ ପୁନଃଗଣନା କରେ, `npm run release:refresh-derived` ଦ୍ୱାରା, ଯାହା release
ଏବଂ nightly derived-refresh PR ଚଲାଏ। ତେଣୁ **releases ମଧ୍ୟରେ base ଜାଣିଶୁଣି live code
ଠାରୁ ପଛରେ ରହେ**, ଏବଂ live code ସହିତ treeକୁ ତୁଳନା କରୁଥିବା gate କିମ୍ବା test, sibling
ଦ୍ୱାରା provider ଯୋଡ଼ାଯିବା ପରେ ପ୍ରତ୍ୟେକ PRରେ red ହୋଇଯିବ। ତେଣୁ derived valuesକୁ
ମୂଲ୍ୟାୟନ କରୁଥିବା gates `scripts/check/lib/gateMode.mjs` ଦ୍ୱାରା ନିର୍ଣ୍ଣୟ ହେଉଥିବା
ଦୁଇଟି mode ମଧ୍ୟରୁ ଗୋଟିଏରେ ଚାଲନ୍ତି (ପ୍ରଥମ match ପ୍ରୟୋଗ ହୁଏ):

1. command lineରେ `--mode=pr|release`;
2. `OMNIROUTE_GATE_MODE` environment variable (`pr` କିମ୍ବା `release`);
3. GitHub Actions eventରୁ automatic: ଯେଉଁ `pull_request`ର head `release/v*` ନୁହେଁ,
   `merge_group`, କିମ୍ବା `omni-queue/**` କୁ push → `pr`; ଅନ୍ୟ ସବୁ (push, schedule,
   dispatch, release PR `release/v* → main`, ଯେକୌଣସି local run) → `release`।

ପ୍ରତ୍ୟେକ modeରେ `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) କ’ଣ ବିଫଳ କରେ:

| ମୋଡ୍      | ବିଫଳ ହୁଏ                                                                                                                                                                                                                                                                                                                                                                                                   | ଲାଇଭ୍ ତଥ୍ୟ ଆବଶ୍ୟକ |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `release` | ପ୍ରତ୍ୟେକ ଯାଞ୍ଚ, ଟ୍ରିରୁ ସଂଗ୍ରହ କରାଯାଇଥିବା ତଥ୍ୟ ବିରୋଧରେ କଠୋର ସମାନତା (ଗେଟ୍ରେ ସର୍ବଦା ଥିବା ବ୍ୟବହାର): ପୁରୁଣା count, version, coverage floor କିମ୍ବା SVG number ହେଉଛି ଏକ STRICT drift                                                                                                                                                                                                                              | ହଁ                |
| `pr`      | କେବଳ ପରିବର୍ତ୍ତନ ଯାହା କରିଛି, ସମାନ claim extractors ସହିତ PR base ବିରୋଧରେ diff କରାଯାଏ: (1) ସେହି ଯାଞ୍ଚ ଏବଂ ଫାଇଲ୍ ପାଇଁ base ରେ ନଥିବା ଏକ managed value ("PR ଏକ managed number ସମ୍ପାଦନ କରିଛି — ଲାଇନ୍ଟିକୁ base text କୁ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ"); (2) base ରେ ଥିବା ଏକ required claim ଯାହା head ରୁ ହରାଇଯାଇଛି। ତଥ୍ୟ ଆବଶ୍ୟକ ନଥିବା content invariants release mode ପରି ଚାଲେ; release-only checks ତାଲିକାଭୁକ୍ତ ହୋଇ skip କରାଯାଏ | ନା                |

`docs/i18n/*/llm.txt` କପିଗୁଡ଼ିକ), bs `AGENTS.md` fork, `open-sse/services/AGENTS.md`,

source ଦିଗରେ (ଉଦାହରଣ ସ୍ୱରୂପ `src/shared/constants/routingStrategies.ts` ରେ
`ROUTING_STRATEGY_VALUES`) ଏବଂ ଏହା ପରିବର୍ତ୍ତେ `npm run facts` ଦିଗରେ ନିର୍ଦ୍ଦେଶ କରେ। Invariant "No derived counts (agent-instruction file …)" ଉଭୟ mode ରେ ସେଠାରେ ଏକ count (providers, migrations, MCP tools ଏବଂ scopes, routing strategies, scoring factors, mode packs) ପାଇଲେ ବିଫଳ ହୁଏ, ତେଣୁ release refresh କେବେ ମଧ୍ୟ instruction file ପୁନଃଲେଖନ କରିବାକୁ ପଡ଼େ ନାହିଁ।

`pr` mode ରେ writer branches managed values ସମ୍ପାଦନ କରିପାରନ୍ତି: `chore/derived-*` (nightly refresh
PR), `release/v*`, ଏବଂ translation waves `docs/i18n-*` ଏବଂ `chore/i18n-*`
(`scripts/check/lib/derivedClaimsDiff.mjs`)। Queue batches (`merge_group`, Mergify drafts,
`omni-queue/**`) ପୁନଃବିଚାର କରାଯାଏ ନାହିଁ: gate ପୂର୍ବରୁ ଗୋଟିଏ ପରେ ଗୋଟିଏ ଯେଉଁ PR ଗୁଡ଼ିକୁ ବିଚାର କରିଛି, ସେଗୁଡ଼ିକୁ ଏହା ସମୁଦାୟ କରେ।

Exit codes: `0` clean · `1` STRICT drift (କିମ୍ବା `--strict` ସହିତ soft drift) କିମ୍ବା managed-value
violation · `2` infrastructure — code facts ସଂଗ୍ରହ କରାଯାଇପାରିଲା ନାହିଁ (tsx probe ବିଫଳ ହେଲା କିମ୍ବା timeout ହେଲା; timeout ହେଉଛି `OMNIROUTE_FACTS_TIMEOUT_MS`, default 600000 ms) କିମ୍ବା CI ରେ PR diff
base resolve କରାଯାଇପାରିଲା ନାହିଁ। Exit 2 କେବେ ମଧ୍ୟ documentation divergence ନୁହେଁ: job ପୁନଃଚାଲନ୍ତୁ କିମ୍ବା environment ଠିକ୍ କରନ୍ତୁ।

ଏହା ପଛରେ ଥିବା commands:

- `npm run facts` ଉତ୍ପନ୍ନ ପ୍ରତ୍ୟେକ ସଂଖ୍ୟାକୁ JSON ଭାବରେ ପ୍ରିଣ୍ଟ କରେ (`scripts/release/facts.mjs`)।
  `--key=code.mcpTools` ଗୋଟିଏ ମୂଲ୍ୟ ପ୍ରିଣ୍ଟ କରେ, `--snapshot` ସଜୀବ ଟ୍ରି ପରିବର୍ତ୍ତେ କମିଟ୍ ହୋଇଥିବା ସ୍ନାପସଟ୍ ପଢ଼େ। facts ସଂଗ୍ରହ କରାଯାଇପାରିବ ନାହିଁ ହେଲେ Exit 2।
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) ଗୋଟିଏ ପାସ୍ରେ ଉତ୍ପନ୍ନ ଫାଇଲଗୁଡ଼ିକୁ ଏହି କ୍ରମରେ ପୁନଃଗଣନା କରେ (`--only=` ପାଇଁ ଷ୍ଟେପ୍ IDଗୁଡ଼ିକ): `provider-reference`
  (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (ସ୍ନାପସଟ୍), `numbers` (counts gateର ପୁନଃଲେଖନ ଯୋଜନାକୁ docs ଉପରେ ପ୍ରୟୋଗ କରି, ପରେ ସେଗୁଡ଼ିକୁ ସେମାନଙ୍କର `docs/i18n/` ମିରର୍ଗୁଡ଼ିକୁ ନେଇଯାଏ),
  `readme-diagrams`, `skills` (ଉତ୍ପନ୍ନ `SKILL.md`), `e2e-timings` (ଟ୍ରିରେ `syncE2eTimings` ଆସିବା ପର୍ଯ୍ୟନ୍ତ ଛାଡ଼ିଦିଆଯାଏ), `ui-keys` (`en.json`ରୁ ବିଲୋପ ହୋଇଥିବା କୀଗୁଡ଼ିକୁ ବାଦ୍ ଦିଏ ଏବଂ, `--rewritten-since=<ref>` ସହିତ — ଡିଫଲ୍ଟ `origin/main` — ଶେଷ ରିଲିଜ୍ ପରଠାରୁ ପୁନଃଲିଖିତ ଇଂରାଜୀ ମୂଲ୍ୟଗୁଡ଼ିକୁ ପୁନଃ ଧାରାରେ ରଖେ), `llm-mirrors` ଏବଂ `verify-generated` (ଲେଖିବା ପରେ, release modeରେ `check:generated-artifacts` ଏବଂ `check:agent-skills-sync` ପାସ୍ ହେବା ଆବଶ୍ୟକ; `--check`ରେ ଏବଂ `--only` ଏହାକୁ ବାଦ୍ ଦେଲେ ଛାଡ଼ିଦିଆଯାଏ; ବିଫଳତା ହେଲେ exit 2)। `changelog` ଷ୍ଟେପ୍ଟି opt-in (`--with-changelog`, କେବଳ release profileରେ)। `--profile=nightly` କେବେବି version claimକୁ ସ୍ପର୍ଶ କରେ ନାହିଁ। `-- --check` ସହିତ ଏହା କିଛି ଲେଖେ ନାହିଁ ଏବଂ କୌଣସି ଫାଇଲ୍ ବଦଳିବାକୁ ଥିଲେ କିମ୍ବା କୌଣସି ପରିଚାଳିତ ମୂଲ୍ୟ ପାଇଁ ମାନୁଆଲ୍ ସମ୍ପାଦନ ଆବଶ୍ୟକ ହେଲେ exit 1 କରେ (ଉଭୟକୁ ତାଲିକାଭୁକ୍ତ କରି); infrastructure ବିଫଳତା ହେଲେ exit 2। `--json` ଫଳାଫଳକୁ JSON ଭାବରେ ପ୍ରିଣ୍ଟ କରେ।
- `docs/reference/derived-facts.json` ହେଉଛି ଶେଷ refresh ଦ୍ୱାରା ବ୍ୟବହୃତ factsର ସ୍ନାପସଟ୍। କେବଳ refresh ଏହାକୁ ଲେଖେ। README SVG generatorଗୁଡ଼ିକ ଏହାକୁ ପଢ଼ନ୍ତି, ଏବଂ PR ସମୟର unit tests କମିଟ୍ ହୋଇଥିବା docs ଓ ଉତ୍ପନ୍ନ ଫାଇଲଗୁଡ଼ିକୁ ଏହା ସହିତ ତୁଳନା କରନ୍ତି — ସଜୀବ code ସହିତ କେବେ ନୁହେଁ। suiteର ଏକମାତ୍ର ସଜୀବ ତୁଳନା ହେଉଛି `tests/unit/check-docs-counts-sync.test.ts`ର “the release refresh closes the cycle”: ସଜୀବ facts ସହିତ, refreshର rewrite planକୁ memoryରେ ପ୍ରୟୋଗ କଲେ ଏହା ରିପୋର୍ଟ ନ କରିଥିବା କୌଣସି STRICT drift ରଖେ ନାହିଁ, ଏବଂ ପୁନଃ-ଯୋଜନା କଲେ କିଛି ବଦଳେ ନାହିଁ।

ସ୍ଥାନୀୟ ଭାବରେ ପୁନରୁତ୍ପାଦନ କରିବାକୁ (ସ୍ଥାନୀୟ run ଡିଫଲ୍ଟ ଭାବରେ `release` ବ୍ୟବହାର କରେ):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

ସମାଧାନଯୋଗ୍ୟ base ନଥିଲେ (`BASE_SHA`/`BASE_REF` ନାହିଁ, କିମ୍ବା ସ୍ଥାନୀୟ `origin/release/v<version>` ନାହିଁ), ସ୍ଥାନୀୟ
`pr` run ଏକ ସତର୍କବାର୍ତ୍ତା ପ୍ରିଣ୍ଟ କରେ ଏବଂ ବିଫଳ ହେବା ପରିବର୍ତ୍ତେ diffକୁ ଛାଡ଼ିଦିଏ।

ଏକ PR ଯାହା `pr` ମୋଡ୍ରେ ମଧ୍ୟ ଲୋକେଲ୍ କ୍ୟାଟାଲଗ୍ଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରେ (ଏକ ଅନୁବାଦ ତରଙ୍ଗ, ରିଲିଜ୍ ରିଫ୍ରେଶ୍, କିମ୍ବା କେବଳ-ଅନୁବାଦ ଫିକ୍ସ), ତାହାକୁ ସ୍କିପ୍ କରାଯାଏ ନାହିଁ: `check-key-completeness` ପରିବର୍ତ୍ତିତ ପ୍ରତ୍ୟେକ କ୍ୟାଟାଲଗ୍କୁ ମର୍ଜ୍ ବେସ୍ରେ ଥିବା ସେହି କ୍ୟାଟାଲଗ୍ (`scripts/i18n/lib/touched-catalogs.mjs`) ସହିତ ତୁଳନା କରେ ଏବଂ କ୍ୟାଟାଲଗ୍ରୁ ହଟିଯାଇଥିବା କୀ, `en.json`-ରେ ନଥିବା କୀ, ପ୍ରକୃତ ଅନୁବାଦ `__MISSING__:` ମାର୍କରରେ କିମ୍ବା ଇଂରାଜୀ ଟେକ୍ସ୍ଟରେ ପରିଣତ ହୋଇଥିବା ସ୍ଥିତି, କିମ୍ବା PR ଦ୍ୱାରା ସ୍ପର୍ଶ ନହୋଇଥିବା ଏକ ଇଂରାଜୀ ଷ୍ଟ୍ରିଙ୍ଗ୍ର placeholder/tagଗୁଡ଼ିକୁ ଆଉ interpolate ନକରୁଥିବା ମୂଲ୍ୟ ମିଳିଲେ ବିଫଳ ହୁଏ। PR-ରେ ନୂଆ ଥିବା ଏକ କ୍ୟାଟାଲଗ୍ରେ ସମ୍ପୂର୍ଣ୍ଣ `en.json` କୀ ସେଟ୍ ଥିବା ଆବଶ୍ୟକ। ଏହା PR ଯେଉଁ କ୍ୟାଟାଲଗ୍ଗୁଡ଼ିକୁ ସ୍ପର୍ଶ କରେ, ସେଗୁଡ଼ିକ ପାଇଁ ratio ଏବଂ CLI-parity gateଗୁଡ଼ିକ ଯାହା ଦେଖିବେ ତାହାକୁ ଆବରଣ କରେ।

ଲୋକେଲ୍-ପ୍ୟାରିଟି ୟୁନିଟ୍ ଟେଷ୍ଟଗୁଡ଼ିକ (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) `tests/_helpers/localeParityMode.ts` ମାଧ୍ୟମରେ ସେହି ମୋଡ୍ଗୁଡ଼ିକୁ ଅନୁସରଣ କରେ: `pr` ମୋଡ୍ରେ ସେଗୁଡ଼ିକ key-parity assertionଗୁଡ଼ିକୁ ସ୍କିପ୍ କରେ ଏବଂ ମର୍ଜ୍ ବେସ୍ଠାରୁ ଇଂରାଜୀ ପରିବର୍ତ୍ତିତ ହୋଇଥିବା କୀଗୁଡ଼ିକର placeholder parity ରିଲିଜ୍ ରିଫ୍ରେଶ୍କୁ ଛାଡ଼ିଦିଏ (ୟୁନିଟ୍-ଟେଷ୍ଟ jobର shallow checkout ଏହାକୁ ପଢ଼ିପାରିବା ନଥିଲେ ପ୍ରତ୍ୟେକ କୀ)। ସେହି helper-ଟି ହେଉଛି ଏକମାତ୍ର ଅନୁମୋଦିତ mode-conditional skip:
`check:test-masking` `.skip(` ଏବଂ `{ skip: true }` ଗଣନା କରେ, କିନ୍ତୁ ଏହା ଫେରାଇଥିବା computed `{ skip: "<reason>" }` ଗଣନା କରେ ନାହିଁ, ତେଣୁ `tests/unit/locale-parity-mode.test.ts` ଏହାକୁ ବ୍ୟବହାର କରିବାକୁ ଅନୁମତିପ୍ରାପ୍ତ ଟେଷ୍ଟଗୁଡ଼ିକର ତାଲିକାକୁ ସ୍ଥିର କରେ — ଏଥିରେ ଆଉ ଗୋଟିଏ ଯୋଡ଼ିବା ସେହି ତାଲିକାରେ review କରାଯାଇଥିବା ସମ୍ପାଦନା ଅଟେ।

#### `check-ui-value-drift` — ପୁରୁଣା-ଅନୁବାଦ gate

ଅନ୍ୟ gateଗୁଡ଼ିକ ଗଠନାତ୍ମକ ଭାବେ ଦେଖିପାରୁନଥିବା ଏକମାତ୍ର i18n regressionକୁ ଧରେ: ଏକ ଇଂରାଜୀ ମୂଲ୍ୟ ପୁନଃଲେଖାଯାଏ ଏବଂ ପୂର୍ବତନ ଇଂରାଜୀ ଉପରେ ଆଧାରିତ ଅନୁବାଦଗୁଡ଼ିକ ପଛରେ ରହିଯାଏ, ଫଳରେ ଅଣ-ଇଂରାଜୀ ବ୍ୟବହାରକାରୀମାନେ ନିଶ୍ଚିତ ଭାବରେ ଲେଖାଯାଇଥିବା, କିନ୍ତୁ ବର୍ତ୍ତମାନ ଭୁଲ୍, କପି ପଢ଼ିଚାଲନ୍ତି।

ଏହା ପ୍ରକୃତରେ ship ହୋଇଥିଲା। Antigravity login helper ଆସିବାବେଳେ `oauthModal.googleOAuthWarning` ପୁନଃଲେଖାଯାଇଥିଲା (#5203); **43ଟି locale ମଧ୍ୟରୁ 39ଟି** ଅପରେଟରମାନଙ୍କୁ "ସମ୍ପୂର୍ଣ୍ଣ URL କପି କରି ତଳେ paste କରନ୍ତୁ" ବୋଲି କହୁଥିବା ଟେକ୍ସ୍ଟ ରଖିଥିଲା — ସେହି provider ପାଇଁ ଯାହା ଦ୍ୱାରା flow ସମ୍ପୂର୍ଣ୍ଣ ହୋଇପାରେ ନାହିଁ। #8463 ପର୍ଯ୍ୟନ୍ତ ଏହା ଧରାପଡ଼ିନଥିଲା, କାରଣ:

- `sync-ui-keys` କେବଳ **ଅନୁପସ୍ଥିତ** କୀଗୁଡ଼ିକୁ ପଛକୁ ଭରେ, ପୁରୁଣା କୀଗୁଡ଼ିକୁ ନୁହେଁ;
- `check-ui-keys-coverage` କୀ _ଉପସ୍ଥିତି_ ଗଣନା କରେ, ତେଣୁ ପୁରୁଣା ଅନୁବାଦ covered ଭାବେ ଗଣାଯାଏ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` documentation mirrorଗୁଡ଼ିକୁ track କରେ —
  ଏହା କେବେ `src/i18n/messages/*.json` ପଢ଼େ ନାହିଁ। ଏହା `docs-sync-strict` jobରେ ଚାଲେ: PRଗୁଡ଼ିକରେ advisory, push ଏବଂ nightlyରେ strict; translation wave mirrorଗୁଡ଼ିକୁ refresh କରେ, feature PRକୁ ନୁହେଁ।

**Diff-aware, baseline-backed ନୁହେଁ।** ଏହା merge baseରେ ଥିବା `en.json`କୁ working tree ସହିତ ତୁଳନା କରେ; ଯେଉଁ କୀର ଇଂରାଜୀ ମୂଲ୍ୟ ପରିବର୍ତ୍ତିତ ହୋଇଛି, ସେଠାରେ ଏପର୍ଯ୍ୟନ୍ତ ଅସ୍ପର୍ଶିତ ଅନୁବାଦ ରଖିଥିବା ଯେକୌଣସି locale ପୁରୁଣା ଅଟେ। ଏହା ଇଚ୍ଛାକୃତ ଭାବେ ପୂର୍ବରୁ ଥିବା debtକୁ **freeze** କରେ — ଏକ diff ଦୀର୍ଘ ସମୟ ଧରି ଥିବା ଅନୁବାଦ କେଉଁ ପୁରୁଣା ଇଂରାଜୀରୁ ଆସିଛି ତାହା ପ୍ରକାଶ କରିପାରେ ନାହିଁ, ତେଣୁ gate କେବଳ ବର୍ତ୍ତମାନ ପରିବର୍ତ୍ତନ ଯାହାକୁ ସ୍ପର୍ଶ କରେ ତାହାକୁ ମୂଲ୍ୟାୟନ କରେ। ବିକଳ୍ପଟି (ପ୍ରତ୍ୟେକ କୀ ପାଇଁ hash baseline) ପାଇଁ ପ୍ରାୟ 600 KBର ଏକ generated file ଦରକାର ହେବ, ଯାହା ବର୍ତ୍ତମାନର ସବୁଠାରୁ ବଡ଼ baselineଠାରୁ 3× ବଡ଼ ଏବଂ ପ୍ରତ୍ୟେକ i18n PRରେ churn ସୃଷ୍ଟି କରିବ।

ଏହାକୁ ପୂରଣ କରିବାର ଦୁଇଟି ଉପାୟ:

1. ପ୍ରଭାବିତ ଅନୁବାଦଗୁଡ଼ିକୁ update କରନ୍ତୁ, କିମ୍ବା
2. ସେଗୁଡ଼ିକୁ `__MISSING__:<new english>` ଭାବେ ସେଟ୍ କରନ୍ତୁ — runtime ତାହାପରେ ସଠିକ୍ ଇଂରାଜୀ (`src/i18n/request.ts::deepMergeFallback`, #7258) ପ୍ରଦାନ କରେ ଏବଂ କୀଟି ଅନୁବାଦ ପାଇଁ queue ହୁଏ।

ଯଦି ଷ୍ଟ୍ରିଙ୍ଗ୍ର **ଅର୍ଥ** ବଦଳିଛି, ତେବେ କୀର ନାମ ପରିବର୍ତ୍ତନ କରିବାକୁ ପସନ୍ଦ କରନ୍ତୁ: ଏକ ନୂଆ କୀ ପୁରୁଣା ଅନୁବାଦ inherit କରିପାରେ ନାହିଁ। #8463 ଏହି pattern ବ୍ୟବହାର କରିଥିଲା।

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Base catalog ପଢ଼ିହେବା ନଥିଲେ (base ref ବିନା shallow clone) `SKIP reason=base-unresolved` ସହିତ 0 exit କରେ, ଯାହା `check-openapi-breaking`କୁ ଅନୁକରଣ କରେ। କେବଳ release mode: ଏକ feature PR ଇଂରାଜୀକୁ ପୁନଃଲେଖେ ଏବଂ ସେଠାରେ ଥାମେ; release refresh ଏହା ପଛରେ ରଖିଯାଇଥିବା ଅନୁବାଦଗୁଡ଼ିକୁ ଚିହ୍ନଟ କରେ (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, ସେହି `findStaleTranslations`)।

   ଦମନ ନକରୁଥିବା ଏକ ପୁରୁଣା ଏଣ୍ଟ୍ରି ନିଜେ ଏକ ତ୍ରୁଟି ଅଟେ (କାର୍ଯ୍ୟକାରୀ ହେବା ପରେ
   6A.3 stale-enforcement ଏକ ଅନାଥ ଅନୁମୋଦିତ ତାଲିକା ଏଣ୍ଟ୍ରି ଥିଲେ ଗେଟ୍ରେ
   ବିଫଳ ହେବ)।

### ଆପଣଙ୍କ PR ରେ ଏକ ଗେଟ୍ ବିଫଳ ହେଲେ

1. **ଗେଟ୍ର ଆଉଟପୁଟ୍କୁ ସାବଧାନତାର ସହିତ ପଢ଼ନ୍ତୁ** — ନିୟମ ଉଲ୍ଲଂଘନ କରିଥିବା କେଉଁ ଫାଇଲ୍ କିମ୍ବା ସିମ୍ବଲ୍ ତାହା ଏହା ସଠିକ୍ ଭାବେ କହିଥାଏ।
2. **ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରନ୍ତୁ** — ଅଧିକାଂଶ ଗେଟ୍ ନିର୍ଦ୍ଧାରିତ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଯାଞ୍ଚ ଅଟେ, ତେଣୁ କୋଡ୍ ସଠିକ୍ ହେବା ମାତ୍ରେ ସେଗୁଡ଼ିକ ପାସ୍ ହୋଇଯାଏ।
3. **ଯଦି ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲା** (ଅର୍ଥାତ୍, ଆପଣ ଏହାକୁ ଯୋଡ଼ିନଥିଲେ କିନ୍ତୁ ଗେଟ୍ ବର୍ତ୍ତମାନ ଏହାକୁ ଆବୃତ କରୁଛି): ଯୁକ୍ତିସହ ଏକ ମନ୍ତବ୍ୟ ଏବଂ ଟ୍ରାକିଂ ଇସ୍ୟୁ ସହିତ ଏକ ଅନୁମୋଦିତ ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ।
4. **ଯଦି ଗେଟ୍ଟି ଏକ ରାଚେଟ୍** (କଭରେଜ୍, ESLint ସତର୍କତା, ଡୁପ୍ଲିକେସନ୍, ଜଟିଳତା): ଆପଣଙ୍କ ପରିବର୍ତ୍ତନ ମେଟ୍ରିକ୍କୁ ଅଧିକ ଖରାପ କରିଛି। ମୂଳ ସମସ୍ୟା ସମାଧାନ କରନ୍ତୁ, କିମ୍ବା (ବିରଳ କ୍ଷେତ୍ରରେ) ପରିବର୍ତ୍ତନଟି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଏବଂ ମେଟ୍ରିକ୍ର ଅବନତି ଗ୍ରହଣଯୋଗ୍ୟ ହେଲେ `npm run quality:ratchet -- --update` ଚଲାନ୍ତୁ — କିନ୍ତୁ PR ବର୍ଣ୍ଣନାରେ ଏହାର କାରଣ ଲେଖନ୍ତୁ।
5. **ପରାମର୍ଶମୂଳକ ଗେଟ୍ଗୁଡ଼ିକ** (`continue-on-error: true`) ସୂଚନାମୂଳକ — ସେଗୁଡ଼ିକ ମର୍ଜ୍କୁ ଅଟକାଇନଥାଏ କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଏ। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

### ମର୍ଜ / ଡିଡ୍ୟୁପ୍ (ଯାନ୍ତ୍ରିକ, କମ୍ ଝୁମ୍ପ)

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ 2026-06-17 ରେ ଲାଇଭ୍ ଗେଟ୍ ଅବସ୍ଥା ବିରୋଧରେ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ଭରସା କରନ୍ତୁ, କିନ୍ତୁ ଯାଞ୍ଚ କରନ୍ତୁ);
କିଛି "ସ୍ପଷ୍ଟ" ମର୍ଜ ମଧ୍ୟରେ ଲୁକାଇଥିବା ଋଣ ମିଳିଲା ଏବଂ ସେଗୁଡ଼ିକ **ସଫା ଡ୍ରପ୍-ଇନ୍ ନୁହେଁ**।

- **`check:docs-sync` ଦୁଇଥର ଚାଲେ** — `lint` ଜବ୍ରେ ସ୍ୱତନ୍ତ୍ର ଭାବେ ଏବଂ ପୁଣି `check:docs-all` (`docs-sync-strict`) ଭିତରେ ଓ husky ପ୍ରି-କମିଟ୍ ହୁକ୍ରେ। ✅ **ସମ୍ପନ୍ନ** — ସ୍ୱତନ୍ତ୍ର `lint` ଇନଭୋକେସନ୍ ହଟାଯାଇଛି।
- **CVE ସ୍କାନିଂ** — ❌ **ସଫା ମର୍ଜ ନୁହେଁ।** `audit:deps` ସମସ୍ତ ପାଞ୍ଚଟି ଲକଫାଇଲ୍ରେ ଗୁରୁତର ଆଡଭାଇଜରୀ ଏବଂ ଅସମ୍ପୂର୍ଣ୍ଣ ଅଡିଟ୍କୁ ବ୍ଲକ୍ କରେ, ଯେତେବେଳେ ବର୍ତ୍ତମାନର ନୀତି ଅନୁସାରେ ଉଚ୍ଚ-ସ୍ତରୀୟ ଆଡଭାଇଜରୀଗୁଡ଼ିକୁ ସତର୍କତା ଭାବେ ରିପୋର୍ଟ କରେ; `check:vuln-ratchet` (osv) କେବଳ ଚେକ୍-ଇନ୍ ହୋଇଥିବା ବେସଲାଇନ୍ ବିରୋଧରେ _ରିଗ୍ରେସନ୍_ ହେଲେ ବିଫଳ ହୁଏ ଏବଂ ଆବଶ୍ୟକ ସମୟରେ ମାପ ଅନୁପସ୍ଥିତିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଅର୍ଥ ଭିନ୍ନ — `audit:deps` ହଟାଇଲେ ନିରପେକ୍ଷ ଗୁରୁତର ଗେଟ୍ ଏବଂ ସ୍ୱତନ୍ତ୍ର ପ୍ୟାକେଜ୍ ଅଡିଟ୍ ରସିଦଗୁଡ଼ିକ ହରାଇଯିବ। ଉଭୟକୁ ରଖନ୍ତୁ।
- **ସାଇକେଲ୍ ଚିହ୍ନଟ** — ✅ **ସମ୍ପନ୍ନ** (#15159 G-01/G-02)। ଏଠାରେ ପୁରୁଣା ଲେଖା `check:cycles` କୁ "ଗ୍ରୀନ୍, କ୍ୟୁରେଟେଡ୍" ଗେଟ୍ ଭାବେ ଉଲ୍ଲେଖ କରିଥିଲା ଏବଂ `check:circular-deps` (dpdm) 91ଟି ସାଇକେଲ୍ ରିପୋର୍ଟ କରିଥିବାରୁ ଏହାକୁ ବ୍ଲକିଂ ରଖିବାର ଯୁକ୍ତି ଦେଇଥିଲା। ସେହି ଗ୍ରୀନ୍ ଏକ **ଭୁଲ୍ ଗ୍ରୀନ୍** ଥିଲା: `check:cycles` 5ଟି ସବ୍ଡାଇରେକ୍ଟୋରୀ (450 ଫାଇଲ୍) ସ୍କାନ୍ କରୁଥିଲା, କେବଳ ସ୍ଥିର `import|export … from` ସହିତ ମେଳ କରୁଥିଲା, ଏବଂ ପ୍ରତ୍ୟେକ `@/` ଓ `@omniroute/open-sse/` ସ୍ପେସିଫାୟର୍କୁ ଛାଡ଼ି ଦେଉଥିଲା; ତେଣୁ ରେପୋକୁ ପ୍ରଭାବିତ କରୁଥିବା ଡାଇନାମିକ୍-ଇମ୍ପୋର୍ଟ + ଏଲିଆସ୍ ସାଇକେଲ୍ଗୁଡ଼ିକୁ ଏହା ଦେଖିପାରୁନଥିଲା। ସମାଧାନ କରାଯାଇଛି: ଗେଟ୍ ବର୍ତ୍ତମାନ `src` + `open-sse` (5023 ଫାଇଲ୍) ମାଧ୍ୟମରେ ଚାଲେ, TypeScript AST ରୁ ସ୍ପେସିଫାୟର୍ ସଂଗ୍ରହ କରେ (ତେଣୁ `import("…")` ଗଣନା ହୁଏ ଏବଂ type-position `typeof import("…")` ହୁଏ ନାହିଁ), ଏବଂ tsconfig `paths` ରିଜଲ୍ଭ କରେ। ଏହା 0 ନୁହେଁ, **14**ଟି ସାଇକେଲ୍ ଖୋଜେ। ଗେଟ୍ PR ରେ ପୂର୍ବରୁ ଥିବା 14ଟି ସାଇକେଲ୍ ସମାଧାନ କରାଯାଇପାରିବ ନାହିଁ ବୋଲି, `check:cycles` ବର୍ତ୍ତମାନ ଏକ **ରାଚେଟ୍** (`--ratchet`, `quality-baseline.json` ରେ ceiling `metrics.cycles.value = 14`, `direction: down`) — ଏହା ଯେକୌଣସି _ରିଗ୍ରେସନ୍_କୁ ବ୍ଲକ୍ କରେ ଏବଂ ଗଣନା କେବଳ କମିପାରିବ। CI `npm run check:cycles:ratchet` ଚଲାଏ। ବର୍ନ୍-ଡାଉନ୍ **A-01** ସହିତ ଚାଲିବ। `check:circular-deps` (dpdm) ବ୍ୟାପକ ଦ୍ୱିତୀୟ ମତ ଭାବେ ପରାମର୍ଶମୂଳକ ରହିବ।
- **ଜଟିଳତା** — ✅ **ସମ୍ପନ୍ନ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ଗୋଟିଏ ESLint ୱାକ୍, ruleId ଅନୁସାରେ ଗଣନା କରେ ଯାହାଦ୍ୱାରା cyclomatic+max-lines ଏବଂ cognitive ବେସଲାଇନ୍ଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହନ୍ତି; ବ୍ୟକ୍ତିଗତ `check:complexity` / `check:cognitive-complexity` ସ୍ଥାନୀୟ `--update` ପାଇଁ ରହିଛି।
- **`/api` ଆଣ୍ଟି-ହାଲୁସିନେସନ୍** — ✅ **ସମ୍ପନ୍ନ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ର ଗୋଟିଏ FS ଇନଭେଣ୍ଟରୀ; openapi-routes + docs-symbols ସ୍ୱାଧୀନ ଭାବେ ରିପୋର୍ଟ କରନ୍ତି; ବ୍ୟକ୍ତିଗୁଡ଼ିକ ସ୍ଥାନୀୟ ରନ୍ ପାଇଁ ରହିଛନ୍ତି।
- **`check:node-runtime` 11ଟି ଜବ୍ରେ ଚାଲେ** — ⚠️ **କମ୍ ROI।** ପ୍ରତ୍ୟେକଟି ଅଲଗା ରନର୍ ଏବଂ ଚେକ୍ଟି <1s; ଏକ ଶସ୍ତା ପ୍ରତି-ଜବ୍ ଗାର୍ଡ ହରାଇବା ବଦଳରେ ମୋଟ ସଞ୍ଚୟ ପ୍ରାୟ ~10s। ଏହି ପରିବର୍ତ୍ତନର ଝଞ୍ଜଟ ଯୋଗ୍ୟ ନୁହେଁ।
