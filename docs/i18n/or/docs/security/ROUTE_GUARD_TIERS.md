## ସାରାଂଶ

ସମସ୍ତ OmniRoute ପରିଚାଳନା API ରୁଟ୍କୁ ତିନୋଟି ସୁରକ୍ଷା
ସ୍ତର ମଧ୍ୟରୁ ଗୋଟିଏରେ ବର୍ଗୀକୃତ କରାଯାଇଛି। ବର୍ଗୀକରଣ ସ୍ଥିର, ଯାହା `src/server/authz/routeGuard.ts`ରେ
ପରିଭାଷିତ ହୋଇଛି, ଏବଂ ଅନ୍ୟ କୌଣସି ପ୍ରମାଣୀକରଣ ଶାଖା ଚାଲିବା ପୂର୍ବରୁ ଏହାର ମୂଲ୍ୟାଙ୍କନ କରାଯାଏ।

## ସ୍ତରଗୁଡ଼ିକ

### ସ୍ତର 1 — LOCAL_ONLY

**ଏହା ଦ୍ୱାରା ବଳବତ୍ତର କରାଯାଏ:** `isLocalOnlyPath(path)` → ଲୁପବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ  
**ବାଇପାସ୍:** ଡିଫଲ୍ଟ ଭାବେ କିଛି ନାହିଁ। ଯେତେବେଳେ ଅନୁରୋଧରେ `manage` ସ୍କୋପ୍ ଥିବା ଏକ ବୈଧ
API କି ରହିଥାଏ, ସେତେବେଳେ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ମଧ୍ୟରେ ଥିବା ପଥଗୁଡ଼ିକ ପାଇଁ
ଏକ ସୀମିତ ବ୍ୟତିକ୍ରମ ରହିଛି ([Manage-scope carve-out](#manage-scope-carve-out) ଦେଖନ୍ତୁ)।

ଏହି ରୁଟ୍ଗୁଡ଼ିକ ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ଆରମ୍ଭ କରନ୍ତି କିମ୍ବା ରନ୍ଟାଇମ୍ କୋଡ୍ ନିଷ୍ପାଦନ କରନ୍ତି। ସେଗୁଡ଼ିକୁ
ନନ୍-ଲୁପବ୍ୟାକ୍ ଟ୍ରାଫିକ୍ ପାଇଁ ଉନ୍ମୁକ୍ତ କରିବା ଦ୍ୱାରା ଏକ ବୈଧ JWT ପାଇଥିବା ଆକ୍ରମଣକାରୀ (ଉଦାହରଣସ୍ୱରୂପ,
ଏକ Cloudflared/Ngrok ଟନେଲ୍ ମାଧ୍ୟମରେ) ପ୍ରୋସେସ୍ ଆରମ୍ଭକୁ ଟ୍ରିଗର୍ କରିପାରିବେ — ଯାହା ଏକ ଜଣାଶୁଣା CVE
ଶ୍ରେଣୀ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))।

**GHSA-fhh6-4qxv-rpqj କ’ଣ (ଆକ୍ରମଣର ଶ୍ରେଣୀ):** ଏକ ପରିଚାଳନା/ଏଜେଣ୍ଟ ସର୍ଭର୍
ଏପରି ଏକ ଏଣ୍ଡପଏଣ୍ଟ ଉନ୍ମୁକ୍ତ କରେ ଯାହା ଏକ ସବ୍ପ୍ରୋସେସ୍ (`npm install`, `node`, ଏକ ବ୍ରାଉଜର୍,
ଏକ ପ୍ରକ୍ସି, `git`, `tar`, …) ଆରମ୍ଭ କରେ। ଯଦି ସେହି ଏଣ୍ଡପଏଣ୍ଟକୁ ହୋଷ୍ଟ ବାହାରୁ ପହଞ୍ଚିହୁଏ — କାରଣ
ଅପରେଟର୍ OmniRouteକୁ ଏକ nginx/Cloudflare/Tailscale ଟନେଲ୍ ପଛରେ ରଖିଛନ୍ତି ଏବଂ ଏକ JWT
ଲିକ୍ ହୋଇଛି, କିମ୍ବା ପ୍ରମାଣୀକରଣ ଭୁଲ୍ ଭାବେ ବିନ୍ୟାସ କରାଯାଇଛି — ତେବେ ଆକ୍ରମଣକାରୀ "ଏକ APIକୁ କଲ୍ କରିବା"କୁ
"ହୋଷ୍ଟରେ ଏକ କମାଣ୍ଡ ଚଲାଇବା"ରେ ପରିଣତ କରିଦିଅନ୍ତି (ରିମୋଟ୍ କୋଡ୍ ନିଷ୍ପାଦନ)। OmniRoute ପ୍ରତ୍ୟେକ
ପ୍ରୋସେସ୍-ଆରମ୍ଭ-ସକ୍ଷମ ରୁଟ୍ରେ **କୌଣସି ପ୍ରମାଣୀକରଣ ଯାଞ୍ଚ ପୂର୍ବରୁ, ବିନା ସର୍ତ୍ତରେ ଏକ ଲୁପବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ**
ବଳବତ୍ତର କରି ଏହାକୁ ବନ୍ଦ କରେ: ଏକ ଟନେଲ୍ ମାଧ୍ୟମରେ ଲିକ୍ ହୋଇଥିବା ଟୋକେନ୍ ମଧ୍ୟ ପ୍ରୋସେସ୍ ଆରମ୍ଭ ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ।

**ସମ୍ପୂର୍ଣ୍ଣ LOCAL_ONLY ସେଟ୍।** ପ୍ରାମାଣିକ ଉତ୍ସ ହେଉଛି
`src/server/authz/routeGuard.ts` ମଧ୍ୟରେ ଥିବା `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`;
ନିମ୍ନର ସାରଣୀ ବର୍ତ୍ତମାନର ସ୍ଥିତିକୁ ପ୍ରତିଫଳିତ କରେ। `check-route-guard-membership` ଗେଟ୍
ପ୍ରୋସେସ୍-ଆରମ୍ଭ-ସକ୍ଷମ ପ୍ରିଫିକ୍ସଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା ପ୍ରତ୍ୟେକ `route.ts`କୁ ଗଣନା କରେ ଏବଂ ଯଦି କୌଣସିଟିକୁ
କେବଳ-ଲୋକାଲ୍ ଭାବେ ଶ୍ରେଣୀଭୁକ୍ତ କରାଯାଇନାହିଁ, ତେବେ CIକୁ ବିଫଳ କରେ।

#### Manage-scope ବ୍ୟତିକ୍ରମ

LOCAL_ONLY pathଗୁଡ଼ିକର ଏକ ଉପସମୁଚ୍ଚୟକୁ non-loopbackରୁ ମଧ୍ୟ access କରାଯାଇପାରିବ, ଯଦି ଏବଂ
କେବଳ ଯଦି requestଟିରେ ଏକ `Authorization: Bearer <api-key>` ଥାଏ, ଯାହାର
metadataରେ `manage` scope (କିମ୍ବା `admin`) ସାମିଲ ଅଛି। ଏହି ବ୍ୟତିକ୍ରମକୁ
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ମାଧ୍ୟମରେ ପ୍ରତ୍ୟେକ path ପାଇଁ ସ୍ପଷ୍ଟ ଭାବେ ନିୟନ୍ତ୍ରଣ କରାଯାଏ, ଯାହାଦ୍ୱାରା
ଯେକୌଣସି ନୂତନ LOCAL_ONLY path ପାଇଁ defaultଟି strict-loopback ହୋଇ ରହେ। Unauthenticated
request ଏବଂ non-manage key ଥିବା requestଗୁଡ଼ିକ ଏବେ ମଧ୍ୟ
`403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ।

ବର୍ତ୍ତମାନ ଏକମାତ୍ର bypass କରାଯୋଗ୍ୟ prefix ହେଉଛି `/api/mcp/`। `/api/cli-tools/runtime/` ଏବଂ
`/api/services/`କୁ ଜାଣିଶୁଣି ବାଦ ଦିଆଯାଇଛି, କାରଣ ସେଗୁଡ଼ିକ arbitrary
subprocess (`npm install`, `node`) ସୃଷ୍ଟି କରିପାରନ୍ତି, ଯାହା ଠିକ୍ ସେହି CVE ଶ୍ରେଣୀ ଯାହାକୁ
LOCAL_ONLY ସ୍ତର ପ୍ରତିରୋଧ କରିବା ପାଇଁ ରହିଛି।

#### Operator ମାର୍ଗଦର୍ଶନ ଏବଂ auditing

ଯଦି ଆପଣ OmniRouteକୁ ଏକ reverse proxy କିମ୍ବା tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ପଛରେ ଚଳାନ୍ତି, loopback ଯାଞ୍ଚ ତଥାପି ଉପରୋକ୍ତ spawn-ସକ୍ଷମ
routeଗୁଡ଼ିକୁ ସୁରକ୍ଷିତ ରଖେ — ଯେଉଁ requestର client address non-loopback, ତାହାକୁ
**auth ଚାଲିବା ପୂର୍ବରୁ** `403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ, ତେଣୁ ଏକ leaked JWT spawn ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ। ଦୁଇଟି
operator ଦାୟିତ୍ୱ ଅବଶିଷ୍ଟ ରହେ:

- **କ୍ଲାଏଣ୍ଟ IPକୁ loopback ଭାବେ ଜାଲିଆତି କରି 403କୁ "ଠିକ୍" କରନ୍ତୁ ନାହିଁ।**
  `X-Forwarded-For: 127.0.0.1` ସେଟ୍ କରିବା, କିମ୍ବା ଉତ୍ସ ଠିକଣାକୁ
  loopback ଭାବେ ପୁନଃଲିଖନ କରୁଥିବା proxy ବ୍ୟବହାର କରିବା, ଏହି ସ୍ତର ବନ୍ଦ କରୁଥିବା ଠିକ୍ ସେହି RCE ଶ୍ରେଣୀକୁ ପୁଣି ଖୋଲିଦିଏ।
  proxy ମାଧ୍ୟମରେ dashboard/APIକୁ ପ୍ରକାଶ କରନ୍ତୁ — spawn-ସକ୍ଷମ routeଗୁଡ଼ିକୁ କେବେ ନୁହେଁ।
- **manage-scope bypassକୁ ସର୍ବନିମ୍ନ ରଖନ୍ତୁ।** କେବଳ `/api/mcp/`କୁ bypass କରାଯାଇପାରିବ, ଏବଂ
  ତାହା ମଧ୍ୟ କେବଳ ଏକ `manage`-scoped API key ସହିତ। `SPAWN_CAPABLE_PREFIXES`କୁ
  bypass ତାଲିକାରେ କେବେ ମଧ୍ୟ ଯୋଡ଼ାଯାଇପାରିବ ନାହିଁ — zod schema ସେଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ ଏବଂ
  `isLocalOnlyBypassableByManageScope` runtimeରେ ସେଗୁଡ଼ିକୁ ଅସ୍ୱୀକାର କରେ (ବହୁ-ସ୍ତରୀୟ ପ୍ରତିରକ୍ଷା),
  dashboardରେ "bypass-ଯୋଗ୍ୟ କରାଯାଇପାରିବ ନାହିଁ" ବୋଲି କହିବାର ଅର୍ଥ ଏହାହିଁ। ସେହି
  deny-listରେ କିଛି LOCAL_ONLY route ମଧ୍ୟ ରହିଛି, ଯେଉଁଗୁଡ଼ିକ spawn କରନ୍ତି ନାହିଁ, କିନ୍ତୁ କେବେ ମଧ୍ୟ
  ଦୂରରୁ ପହଞ୍ଚଯୋଗ୍ୟ ହେବା ଉଚିତ ନୁହେଁ — `/api/oauth/kiro/auto-import` (host-local Kiro
  credential fileଗୁଡ଼ିକ ପଢ଼େ), `/api/discovery/` ଏବଂ `/api/issue-agent/`। runtime
  snapshot loader ମଧ୍ୟ ସଂରକ୍ଷିତ settings rowରୁ ଏପରି entryଗୁଡ଼ିକୁ ବାଦ ଦିଏ, ଏବଂ
  legacy JSON import (`/api/settings/import-json`) କେବେ ମଧ୍ୟ bypass keyଗୁଡ଼ିକୁ ଲେଖେ ନାହିଁ।
  ପ୍ରତ୍ୟେକ `LOCAL_ONLY_API_PREFIXES` entry deny-listରେ ଥିବା ଉଚିତ କିମ୍ବା
  bypass-ଯୋଗ୍ୟ ଭାବେ ସମୀକ୍ଷିତ ହେବା ଉଚିତ (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)। `/api/providers/` ଅଧୀନରେ ଥିବା dynamic-segment
  ଏବଂ static-path spawn-ସକ୍ଷମ routeଗୁଡ଼ିକ (ଯଥା `/login`,
  `/refresh-cursor`) flat
  `SPAWN_CAPABLE_PREFIXES` array ଦ୍ୱାରା ନୁହେଁ, ବରଂ `src/shared/constants/spawnCapablePrefixes.ts`ରେ ଥିବା regex-ଆଧାରିତ `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ସହଯୋଗୀ ଦ୍ୱାରା ଅନ୍ତର୍ଭୁକ୍ତ — ସେଗୁଡ଼ିକୁ ଧରିବା ପାଇଁ flat arrayକୁ
  ସମ୍ପୂର୍ଣ୍ଣ `/api/providers/` prefix ଅନ୍ତର୍ଭୁକ୍ତ କରିବାକୁ ପଡ଼ିବ, ଯାହା provider CRUD ପାଇଁ
  remote dashboardଗୁଡ଼ିକ ବୈଧ ଭାବେ ବ୍ୟବହାର କରୁଥିବା route treeକୁ ଅତ୍ୟଧିକ ବ୍ୟାପକ କରିଦେବ।

**ପ୍ରବେଶ ଅଡିଟ୍ କରିବା** — host ବାହାରୁ କୌଣସି ଅନୁରୋଧ ଏହି routeଗୁଡ଼ିକରେ ପହଞ୍ଚୁନାହିଁ ବୋଲି ଯାଞ୍ଚ କରିବା ପାଇଁ:

- `/dashboard/settings/security`ରେ **Authorization Inventory** ଖୋଲନ୍ତୁ: ଏହା
  live LOCAL_ONLY prefix ତାଲିକା, କେଉଁ prefixଗୁଡ଼ିକ bypass-ଯୋଗ୍ୟ, ଏବଂ compile-time
  spawn-ସକ୍ଷମ ("bypass-ଯୋଗ୍ୟ କରାଯାଇପାରିବ ନାହିଁ") ସେଟ୍ ପ୍ରଦର୍ଶନ କରେ।
- ଉପରୋକ୍ତ prefixଗୁଡ଼ିକ ସହ non-loopback client address ଯୋଡ଼ି ଆପଣଙ୍କ reverse-proxy / access logଗୁଡ଼ିକୁ Grep କରନ୍ତୁ।
  ଏପରି କୌଣସି hit `403 LOCAL_ONLY` ପରିବର୍ତ୍ତେ `200` ଫେରାଇଥିଲେ,
  proxy ପ୍ରକୃତ client IPକୁ ଲୁଚାଉଛି — proxyକୁ ଠିକ୍ କରନ୍ତୁ।
- ଏହି pathଗୁଡ଼ିକ ମଧ୍ୟରୁ ଗୋଟିଏ ପାଇଁ OmniRouteର logରେ ଥିବା `403 LOCAL_ONLY` ହେଉଛି guard
  ଉଦ୍ଦେଶ୍ୟାନୁସାରେ କାମ କରୁଥିବାର ସୂଚନା, ଦମନ କରିବାକୁ ଥିବା error ନୁହେଁ।

#### call-site probe gate ସହିତ remote-reachable routeଗୁଡ଼ିକ

କିଛି routeକୁ remote dashboardରୁ ପହଞ୍ଚଯୋଗ୍ୟ ରଖିବା ଆବଶ୍ୟକ, କିନ୍ତୁ local callerମାନଙ୍କ ପାଇଁ
host-side probe (`which <binary>`, `<binary> --version`, `tailscale status --json`) ଚଲାଇବାକୁ ପଡ଼େ।
ସେଗୁଡ଼ିକ `GET` ପାଇଁ LOCAL_ONLY ନୁହେଁ; ତାହା ପରିବର୍ତ୍ତେ handler
`getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) ମାଧ୍ୟମରେ trusted peer verdict ପଢ଼େ ଏବଂ କେବଳ
`loopback` / `lan` callerମାନଙ୍କ ପାଇଁ probe ଚଲାଏ। ଏକ `remote` caller
non-spawning sourceଗୁଡ଼ିକରୁ (ସ୍ଥାୟୀ state, settings, fs check) ନିର୍ମିତ ସମାନ response shape ପାଏ,
ଯାହା `probed: false` ଭାବେ ଚିହ୍ନିତ।

| Route                                                            | remote callerମାନଙ୍କ ପାଇଁ ଛାଡ଼ି ଦିଆଯାଉଥିବା probe                     |
| ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI runtime probe (`allowLocalRuntimeProbe`) ଏବଂ CLI-fallback spawn |
| `GET /api/headroom/status`                                       | `which headroom` ଏବଂ python `--version` probeଗୁଡ଼ିକ                 |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`   |
| `GET /api/tunnels/cloudflared` (LOCAL_ONLYରୁ GET-exempt)         | `which cloudflared` PATH lookup                                     |

hostକୁ probe କରୁଥିବା ଏକ ନୂତନ read route ସମାନ pattern ଅନୁସରଣ କରେ, କିମ୍ବା ସିଧାସଳଖ
LOCAL_ONLY ଭାବେ ବର୍ଗୀକୃତ ହୁଏ।

### ସ୍ତର 2 — ALWAYS_PROTECTED

**ବାଧ୍ୟତାମୂଳକ କରେ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` bypassକୁ ଛାଡ଼ିଦିଅ
**Bypass:** `requireLogin=false` ଥିବାବେଳେ କିଛି ନାହିଁ; JWT ସର୍ବଦା ଆବଶ୍ୟକ

ଏହି routeଗୁଡ଼ିକ ବିନାଶକାରୀ କିମ୍ବା ଅପରିବର୍ତ୍ତନୀୟ। ଏକ "no-password"
installationରେ ସେଗୁଡ଼ିକୁ ଅନୁମତି ଦେବାର ଅର୍ଥ, ସମାନ LANରେ ଥିବା ଯେକୌଣସି ବ୍ୟକ୍ତି databaseକୁ ସମ୍ପୂର୍ଣ୍ଣ ମିଟାଇପାରିବେ କିମ୍ବା
server processକୁ ବନ୍ଦ କରିପାରିବେ।

| Path                                      | କାରଣ                                                                |
| ----------------------------------------- | ------------------------------------------------------------------- |
| `/api/shutdown`                           | server processକୁ ସମାପ୍ତ କରେ                                         |
| `/api/settings/database`                  | Database export, import, ଏବଂ wipe                                   |
| `/api/db-backups`                         | ସମ୍ପୂର୍ଣ୍ଣ database backup archive access                           |
| `/api/settings/export-json`               | ସମ୍ପୂର୍ଣ୍ଣ settings blob export କରେ (secret ସମେତ)                   |
| `/api/settings/import-json`               | ସମ୍ପୂର୍ଣ୍ଣ settings blobକୁ ବଦଳାଇଦିଏ                                 |
| `/api/providers/health-autopilot/actions` | autopilot remediation actionଗୁଡ଼ିକୁ execute କରେ                     |
| `/api/settings/obsidian`                  | ଯେକୌଣସି vault root ପାଇଁ ପୁନଃବ୍ୟବହାରଯୋଗ୍ୟ WebDAV credential ଜାରି କରେ |

**ଉଲ୍ଲଂଘନ ସମୟରେ response:** `401 Authentication required`

`/api/settings/obsidian` ଏହାର `/webdav` childକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ: `POST`, Next.js ପୂର୍ବରୁ custom Node layer ଦ୍ୱାରା
serve ହେଉଥିବା ଏବଂ ଏହି pipeline ବାହାରେ ଥିବା WebDAV file serviceକୁ caller ବାଛିଥିବା root ଦିଗରେ ନିର୍ଦ୍ଦେଶ କରେ
ଏବଂ ନୂତନ ଭାବେ ଜାରି ହୋଇଥିବା Basic credentialକୁ ପ୍ରତିଧ୍ୱନିତ କରେ, `DELETE` ସେଗୁଡ଼ିକୁ rotate କରେ, ଏବଂ parent `POST`
Obsidian REST API tokenକୁ ସଂରକ୍ଷଣ କରେ। GHSA-62vw କେବଳ `GET` password ପ୍ରକାଶକୁ ଲୁଚାଇଥିଲା; credential ଜାରି କରିବା
ତଥାପି fail-open ସ୍ତରରେ ଥିଲା (GHSA-7pq4-8pvv-rx7r)। `enableObsidianVaultSync()` ଅତିରିକ୍ତ ଭାବେ
data directory ସହ ସମାନ, ତାହା ଭିତରେ ଥିବା, କିମ୍ବା ତାହାକୁ ଧାରଣ କରୁଥିବା vaultକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

#### Credential exportଗୁଡ଼ିକ କେବଳ operatorଙ୍କ ପାଇଁ

ଉପରୋକ୍ତ ସ୍ତରଟି କେବଳ _କୌଣସି_ ପ୍ରମାଣପତ୍ର ଆବଶ୍ୟକ କି ନାହିଁ ନିର୍ଣ୍ଣୟ କରେ। ସଂରକ୍ଷିତ ପ୍ରମାଣପତ୍ର
ଡାଉନଲୋଡ୍ କରୁଥିବା ରୁଟ୍ଗୁଡ଼ିକ ହ୍ୟାଣ୍ଡଲର୍ରେ ଏକ ଦ୍ୱିତୀୟ ଯାଞ୍ଚ ଯୋଗ କରନ୍ତି: `GET /api/settings/export-json` (ଡିକ୍ରିପ୍ଟ କରାଯାଇଥିବା
ପ୍ରଦାନକାରୀ ସଂଯୋଗ ଏବଂ କଞ୍ଚା API କୀଗୁଡ଼ିକ), `GET /api/db-backups/export` (SQLite ଫାଇଲ୍) ଏବଂ
`GET /api/db-backups/exportAll` (ସମ୍ପୂର୍ଣ୍ଣ ଆର୍କାଇଭ୍) `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`)କୁ କଲ୍ କରନ୍ତି। ଏହା ଏକ ଡ୍ୟାସ୍ବୋର୍ଡ ସେସନ୍, ସ୍ଥାନୀୟ CLI ସବ୍ଜେକ୍ଟ, କିମ୍ବା
ଲଗଇନ୍ ଅକ୍ଷମ ଥିବା ଏକ ଇନ୍ଷ୍ଟାନ୍ସକୁ ଗ୍ରହଣ କରେ ଏବଂ ଯେକୌଣସି ସ୍କୋପ୍ର API କୀଗୁଡ଼ିକୁ (`manage`
ଏବଂ `admin` ସମେତ) ଏବଂ `oma_` ଆକ୍ସେସ୍ ଟୋକନ୍ଗୁଡ଼ିକୁ `403` ଉତ୍ତର ଦିଏ। ସିଙ୍କ୍ ଟୋକନ୍ ଜାରିକରଣ (`POST /api/sync/tokens`) ସେହି
ସହାୟକକୁ, ଏବଂ ତା’ ସହିତ ବିଶ୍ୱସ୍ତ ଲୁପ୍ବ୍ୟାକ୍ ଆଭ୍ୟନ୍ତରୀଣ-ସେବା ଟୋକନ୍କୁ ବ୍ୟବହାର କରେ।

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### ନୂତନ-ଇନ୍ଷ୍ଟଲ୍ ବୁଟ୍ଷ୍ଟ୍ରାପ୍ କେବଳ ଲୁପ୍ବ୍ୟାକ୍ ପାଇଁ — `Host` ନୁହେଁ, ପ୍ରକୃତ ପିଅର୍ ଆଧାରରେ

କୌଣସି ପରିଚାଳନା ପାସ୍ୱାର୍ଡ ବିନ୍ୟାସ ହୋଇନଥିଲେ (ଏବଂ କୌଣସି `INITIAL_PASSWORD` ନଥିଲେ),
`src/shared/utils/apiAuth.ts`ର `isAuthRequired()` ଅଜ୍ଞାତ ବୁଟ୍ଷ୍ଟ୍ରାପ୍କୁ **କେବଳ ଲୁପ୍ବ୍ୟାକ୍ ପିଅର୍ମାନଙ୍କ ପାଇଁ** ଖୋଲା ରଖେ।
ବିଶ୍ୱସ୍ତ ପିଅର୍ ସଙ୍କେତଗୁଡ଼ିକ ଆଧାରରେ, ନିମ୍ନ କ୍ରମରେ, ଲୁପ୍ବ୍ୟାକ୍ ନିର୍ଣ୍ଣୟ କରାଯାଏ: ଟୋକନ୍-ଷ୍ଟାମ୍ପ୍ ହୋଇଥିବା ପ୍ରକୃତ TCP ପିଅର୍
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ଯାହା ପଲିସି ଦେଖେ), ପାଇପ୍ଲାଇନ୍ର ନିଜସ୍ୱ
`AUTHZ_HEADER_PEER_LOCALITY` ନିଷ୍ପତ୍ତି (ଯାହା ରୁଟ୍ ହ୍ୟାଣ୍ଡଲର୍ଗୁଡ଼ିକ ଦେଖନ୍ତି, କେବଳ
`OMNIROUTE_PEER_STAMP_TOKEN` ସେଟ୍ ଥିବାବେଳେ ବିଶ୍ୱସ୍ତ), କିମ୍ବା ସିଧାସଳଖ କଲର୍ମାନଙ୍କ ପାଇଁ ଏକ ପ୍ରକୃତ ସକେଟ୍ ପିଅର୍। `Host` /
`nextUrl.hostname`କୁ କେବେ ମଧ୍ୟ ବିଚାର କରାଯାଏ ନାହିଁ, ଏବଂ ପ୍ରଥମ-ପାସ୍ୱାର୍ଡ ଲେଖା
(`POST /api/settings/require-login`) ପ୍ରତ୍ୟେକ ନେଟ୍ୱର୍କ ପିଅର୍ ପାଇଁ ଖୋଲା ନ ରହି, ସମାନ
ପ୍ରତିବନ୍ଧକ ଅଧୀନରେ ରହେ (GHSA-7pq4-8pvv-rx7r)। `managementPolicy` ନିଜର `peerContext` ନିଷ୍ପତ୍ତିକୁ
ସ୍ପଷ୍ଟ ଭାବରେ ନିମ୍ନକୁ ପଠାଏ, ତେଣୁ ORIGINAL (ଷ୍ଟ୍ରିପ୍ କରିବା ପୂର୍ବରୁ) ଅନୁରୋଧର ହେଡର୍ଗୁଡ଼ିକ ଏହାକୁ କେବେ ନିର୍ଣ୍ଣୟ କରନ୍ତି ନାହିଁ।

### ସ୍ତର 3 — ପରିଚାଳନା (ଡିଫଲ୍ଟ)

ଅନ୍ୟ ସମସ୍ତ ପରିଚାଳନା ରୁଟ୍। `requireLogin=false` ବିନ୍ୟାସ କରାଯାଇନଥିଲେ
ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ। CLI ଟୋକନ୍ଗୁଡ଼ିକ ଏହି ରୁଟ୍ଗୁଡ଼ିକୁ ପ୍ରମାଣୀକୃତ କରିପାରିବେ (ଲୁପ୍ବ୍ୟାକ୍ + ବୈଧ HMAC)।

## ମୂଲ୍ୟାଙ୍କନ କ୍ରମ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ପରବର୍ତ୍ତୀ ପଦକ୍ଷେପକୁ ଯାଆନ୍ତୁ
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → ଅନ୍ୟଥା                                    → 403 LOCAL_ONLY ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  2. isInternalModelSyncRequest(ctx)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (system)
  3. hasValidCliToken(headers)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (cli) [loopback + timingSafeEqual HMAC ଯାଞ୍ଚ]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ଅନୁମତି ଦିଅନ୍ତୁ (dashboard_session)
     → bypass କରିହେଉ ନଥିବା ପଥରେ manage-scope Bearer?
        → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → 401/403 ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  5. requireLogin=false?
     → ଅନୁମତି ଦିଅନ୍ତୁ (anonymous)
```

ପଦକ୍ଷେପ 1ର manage-scope ଶାଖା ହେଉଛି ଏକମାତ୍ର ପ୍ରମାଣୀକୃତ ପଥ ଯାହା ଏକ
LOCAL_ONLY ରୁଟ୍କୁ ସନ୍ତୁଷ୍ଟ କରିପାରେ; auth-backend ବିଫଳତା ମୋଡ୍ 503 ଫେରାଏ
(403 ନୁହେଁ), ଯାହାଫଳରେ ଏକ ମିଆଦ ଶେଷ ହୋଇଥିବା DB ନିରବରେ "deny"କୁ
ଡାଉନ୍ଗ୍ରେଡ୍ ହୁଏ ନାହିଁ।

4. ନିଷ୍ପତ୍ତି ନିଅନ୍ତୁ: ଏହି ରୁଟ୍ଟି କ’ଣ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ
   ମଧ୍ୟ ରହିବା ଉଚିତ? ଡିଫଲ୍ଟ ଉତ୍ତର ହେଉଛି **ନା**। କେବଳ ସେତେବେଳେ opt-in କରନ୍ତୁ,
   ଯେତେବେଳେ ରୁଟ୍ଟିକୁ ଏକ manage-scope ଧାରକଙ୍କ ପାଇଁ ଉନ୍ମୁକ୍ତ କରିବା ସୁରକ୍ଷିତ
   (ଅର୍ଥାତ୍, ଏହା ଇଚ୍ଛାମତେ ବ୍ୟବହାରକାରୀ-ନିୟନ୍ତ୍ରିତ କୋଡ୍ spawn କରେ **ନାହିଁ**)।

## ଏକ manage-scope-bypassable ପଥ ଯୋଡ଼ିବା

1. ରୁଟ୍ଟି ବ୍ୟବହାରକାରୀ-ପ୍ରଦତ୍ତ କୋଡ୍ କିମ୍ବା କମାଣ୍ଡ ଚାଲୁ କରେ ନାହିଁ ବୋଲି
   ନିଶ୍ଚିତ କରନ୍ତୁ। ଯଦି କରେ, ଅଟକି ଯାଆନ୍ତୁ — ଏହି ବ୍ୟତିକ୍ରମ ଏଥିପାଇଁ ଉପଯୁକ୍ତ
   ଉପକରଣ ନୁହେଁ।
2. ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
3. ସମସ୍ତ ଚାରିଟି ଅନୁରୋଧ ରୂପ ପାଇଁ `tests/unit/authz/management-policy.test.ts`ରେ
   କଭରେଜ୍ ଯୋଡ଼ନ୍ତୁ: Bearer ନାହିଁ (403), manage Bearer (ଅନୁମତି), non-manage Bearer
   (403), ଏବଂ manage Bearer ଥିଲେ ମଧ୍ୟ `/api/cli-tools/runtime/*`
   strict-loopback ରହୁଥିବା ପ୍ରତି-ପ୍ରିଫିକ୍ସ ରିଗ୍ରେସନ୍।

## OpenAPIରେ ସୁରକ୍ଷା ଟିଅର୍ଗୁଡ଼ିକୁ ଡକ୍ୟୁମେଣ୍ଟ କରିବା

`docs/openapi.yaml`ରେ ଏକ ନୂତନ ରୁଟ୍ ଯୋଡ଼ିବାବେଳେ, ଯଦି ରୁଟ୍ଟି
`routeGuard.ts` ଦ୍ୱାରା ବର୍ଗୀକୃତ ହୋଇଛି, ତେବେ ସମ୍ପର୍କିତ vendor extension
ପ୍ରୟୋଗ କରନ୍ତୁ:

| routeGuard.ts ବର୍ଗୀକରଣ             | YAML ଆନୋଟେସନ୍                 | ପ୍ରବର୍ତ୍ତନ                                       |
| ---------------------------------- | ----------------------------- | ------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`          | `x-loopback-only: true`       | non-loopbackରୁ ନିଃସର୍ତ୍ତ ଭାବେ ଅବରୋଧିତ            |
| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true`    | `requireLogin=false` ଥିଲେ ମଧ୍ୟ ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ |
| ଆଭ୍ୟନ୍ତରୀଣ admin/debug ରୁଟ୍        | `x-internal: true`            | ଡିଫଲ୍ଟ ଭାବେ /dashboard/api-endpointsରୁ ଲୁକ୍କାୟିତ |
| କିଛି ନୁହେଁ (ସାର୍ବଜନୀନ / ମାନକ auth) | (କୌଣସି ଆନୋଟେସନ୍ ଆବଶ୍ୟକ ନାହିଁ) | ମାନକ `requireLogin`-ନିୟନ୍ତ୍ରିତ ପ୍ରବେଶ            |

### ବୈଧତା ଯାଞ୍ଚ

ଦୁଇଟି ସ୍କ୍ରିପ୍ଟ YAML ଆନୋଟେସନ୍ ଏବଂ `routeGuard.ts` ମଧ୍ୟରେ ସମନ୍ୱୟକୁ
ବାଧ୍ୟତାମୂଳକ କରେ:

- `scripts/check/check-openapi-coverage.mjs` — କଭରେଜ୍ < 99% ହେଲେ ବିଫଳ ହୁଏ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` କିମ୍ବା
  `x-always-protected` ଆନୋଟେସନ୍ଗୁଡ଼ିକ compile-time କନ୍ଷ୍ଟାଣ୍ଟଠାରୁ ଭିନ୍ନ ହେଲେ ବିଫଳ ହୁଏ

ଉଭୟ ସ୍କ୍ରିପ୍ଟ pre-commit hook ଏବଂ CIରେ ଚାଲେ।

### ଭୁଲ୍ ସକାରାତ୍ମକ ନିୟମ

ଯଦି `routeGuard.ts` କନ୍ଷ୍ଟାଣ୍ଟରେ ନଥିବା ଏକ ରୁଟ୍ରେ `x-always-protected`
କିମ୍ବା `x-loopback-only` ଆନୋଟେଟ୍ କରାଯାଏ, ତେବେ କଭରେଜ୍ ସ୍କ୍ରିପ୍ଟ ବିଫଳ ହୁଏ।
ସମାଧାନ ହେଉଛି ସର୍ବଦା YAMLକୁ `routeGuard.ts` ପ୍ରକୃତରେ ଯାହା ପ୍ରବର୍ତ୍ତନ କରେ
ତାହା ସହିତ ସମନ୍ୱିତ କରିବା — ପ୍ରବର୍ତ୍ତନ ଲଜିକ୍ ମଧ୍ୟ କାର୍ଯ୍ୟକାରୀ ନକରି କେବଳ
`routeGuard.ts`ରେ ରୁଟ୍ ଯୋଡ଼ିବା ନୁହେଁ।
