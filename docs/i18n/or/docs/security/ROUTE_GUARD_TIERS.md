## ସମୀକ୍ଷା

ସମସ୍ତ OmniRoute ପରିଚାଳନା API ରୁଟ୍ଗୁଡ଼ିକୁ ତିନୋଟି ସୁରକ୍ଷା ସ୍ତର ମଧ୍ୟରୁ ଗୋଟିଏରେ ବର୍ଗୀକୃତ କରାଯାଇଛି। ବର୍ଗୀକରଣଟି ସ୍ଥିର, ଯାହା `src/server/authz/routeGuard.ts` ରେ ପରିଭାଷିତ, ଏବଂ ଅନ୍ୟ କୌଣସି auth ଶାଖା ଚାଲିବା ପୂର୍ବରୁ ମୂଲ୍ୟାୟନ କରାଯାଏ।

## ସ୍ତରଗୁଡ଼ିକ

### ସ୍ତର 1 — LOCAL_ONLY

**ପ୍ରବର୍ତ୍ତନ କରେ:** `isLocalOnlyPath(path)` → ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ  
**ବାଇପାସ୍:** ଡିଫଲ୍ଟ ଭାବେ କୌଣସିଟି ନାହିଁ। `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ରେ ଥିବା ପଥଗୁଡ଼ିକ ପାଇଁ ସୀମିତ ବ୍ୟତିକ୍ରମ ରହିଛି, ଯେତେବେଳେ ଅନୁରୋଧଟି `manage` ସ୍କୋପ୍ ସହିତ ଏକ ବୈଧ API କୀ ବହନ କରେ ([Manage-scope carve-out](#manage-scope-carve-out) ଦେଖନ୍ତୁ)।

ଏହି ରୁଟ୍ଗୁଡ଼ିକ ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ଆରମ୍ଭ କରେ କିମ୍ବା ରନ୍ଟାଇମ୍ କୋଡ୍ ଚାଲାଏ। ଏଗୁଡ଼ିକୁ ଲୁପ୍ବ୍ୟାକ୍ ନୁହେଁ ଏପରି ଟ୍ରାଫିକ୍ ପାଇଁ ଉନ୍ମୁକ୍ତ କଲେ, ଜଣେ ଆକ୍ରମଣକାରୀ ବୈଧ JWT ହାସଲ କରିଥିଲେ (ଉଦାହରଣସ୍ୱରୂପ, Cloudflared/Ngrok ଟନେଲ୍ ମାଧ୍ୟମରେ) ପ୍ରୋସେସ୍ ଆରମ୍ଭ କରାଇପାରିବ — ଏହା ଏକ ପରିଚିତ CVE ଶ୍ରେଣୀ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))।

**GHSA-fhh6-4qxv-rpqj କ’ଣ (ଆକ୍ରମଣ ଶ୍ରେଣୀ):** ଏକ ପରିଚାଳନା/ଏଜେଣ୍ଟ ସର୍ଭର୍ ଏପରି ଏକ ଏଣ୍ଡପଏଣ୍ଟ୍ ଉନ୍ମୋଚନ କରେ ଯାହା ଏକ ସବ୍ପ୍ରୋସେସ୍ (`npm install`, `node`, ଏକ ବ୍ରାଉଜର୍, ଏକ ପ୍ରକ୍ସି, `git`, `tar`, …) ଆରମ୍ଭ କରେ। ଯଦି ସେହି ଏଣ୍ଡପଏଣ୍ଟ୍ ହୋଷ୍ଟ୍ ବାହାରୁ ପହଞ୍ଚଯୋଗ୍ୟ ହୁଏ — କାରଣ ଅପରେଟର୍ OmniRoute କୁ ଏକ nginx/Cloudflare/Tailscale ଟନେଲ୍ ପଛରେ ରଖିଛନ୍ତି ଏବଂ ଏକ JWT ଲିକ୍ ହୋଇଛି, କିମ୍ବା auth ଭୁଲ୍ଭାବେ ବିନ୍ୟାସିତ ହୋଇଛି — ତେବେ ଆକ୍ରମଣକାରୀ "call an API" କୁ "run a command on the host" ରେ ପରିଣତ କରିଦିଏ (ରିମୋଟ୍ କୋଡ୍ ଏକ୍ସିକ୍ୟୁସନ୍)। OmniRoute ପ୍ରତ୍ୟେକ spawn-capable ରୁଟ୍ରେ ଯେକୌଣସି auth ଯାଞ୍ଚ ପୂର୍ବରୁ **ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ ସର୍ତ୍ତହୀନ ଭାବରେ ପ୍ରବର୍ତ୍ତନ କରି** ଏହାକୁ ବନ୍ଦ କରେ: ଟନେଲ୍ ମାଧ୍ୟମରେ ଲିକ୍ ହୋଇଥିବା ଟୋକେନ୍ ଥିଲେ ମଧ୍ୟ spawn ପହଞ୍ଚଯୋଗ୍ୟ ହୁଏ ନାହିଁ।

**ସମ୍ପୂର୍ଣ୍ଣ LOCAL_ONLY ସେଟ୍।** ପ୍ରାମାଣିକ ଉତ୍ସ ହେଉଛି `src/server/authz/routeGuard.ts` ରେ ଥିବା `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`; ନିମ୍ନସ୍ଥ ସାରଣୀ ବର୍ତ୍ତମାନର ସ୍ଥିତିକୁ ପ୍ରତିଫଳିତ କରେ। `check-route-guard-membership` ଗେଟ୍ spawn-capable ପ୍ରିଫିକ୍ସଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା ପ୍ରତ୍ୟେକ `route.ts` କୁ ଗଣନା କରେ ଏବଂ ଯଦି କୌଣସିଟି local-only ଭାବେ ବର୍ଗୀକୃତ ହୋଇନଥାଏ, ତେବେ CI ବିଫଳ କରେ।

#### ପରିଚାଳନା-ସ୍କୋପ୍ ବ୍ୟତିକ୍ରମ

LOCAL_ONLY ପଥଗୁଡ଼ିକର ଏକ ଉପସମୁଚ୍ଚୟ non-loopback ଠାରୁ ମଧ୍ୟ ଆକ୍ସେସ୍ କରାଯାଇପାରେ, କିନ୍ତୁ କେବଳ ସେତେବେଳେ ଯଦି ଅନୁରୋଧରେ ଏକ `Authorization: Bearer <api-key>` ଥାଏ, ଯାହାର ମେଟାଡାଟାରେ `manage` ସ୍କୋପ୍ (କିମ୍ବା `admin`) ଅନ୍ତର୍ଭୁକ୍ତ ଥାଏ। ଏହି ବ୍ୟତିକ୍ରମଟି `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ମାଧ୍ୟମରେ ପ୍ରତ୍ୟେକ ପଥ ପାଇଁ ସ୍ପଷ୍ଟ ଭାବେ ନିୟନ୍ତ୍ରିତ, ତେଣୁ ଯେକୌଣସି ନୂତନ LOCAL_ONLY ପଥ ପାଇଁ ଡିଫଲ୍ଟ ଭାବରେ strict-loopback ରହେ। ଅପ୍ରମାଣିତ ଅନୁରୋଧ ଏବଂ non-manage କୀ ସହିତ ଅନୁରୋଧଗୁଡ଼ିକୁ ଏପର୍ଯ୍ୟନ୍ତ `403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ।

ବର୍ତ୍ତମାନ ଏକମାତ୍ର bypass କରାଯାଇପାରୁଥିବା prefix ହେଉଛି `/api/mcp/`। `/api/cli-tools/runtime/` ଏବଂ `/api/services/` କୁ ଜାଣିଶୁଣି ବାଦ ଦିଆଯାଇଛି, କାରଣ ସେଗୁଡ଼ିକ ଇଚ୍ଛାମତେ subprocess (`npm install`, `node`) ସ୍ପନ୍ କରିପାରନ୍ତି, ଯାହା LOCAL_ONLY tier ରୋକିବା ପାଇଁ ଥିବା ସଠିକ୍ CVE ଶ୍ରେଣୀ ଅଟେ।

**#7895 — `mcp:connect` ସଂକୀର୍ଣ୍ଣ ସ୍କୋପ୍:** `/api/mcp/` carve-out ଏକ Bearer କୀକୁ ମଧ୍ୟ ଗ୍ରହଣ କରେ, ଯଦି ତାହାରେ ସଂକୀର୍ଣ୍ଣ `mcp:connect` ସ୍କୋପ୍ ଥାଏ (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), ଯାହାକୁ `src/server/authz/policies/management.ts` ରେ `hasMcpConnectOrManageScope()` ମାଧ୍ୟମରେ ଯାଞ୍ଚ କରାଯାଏ। ଏହା କେବଳ `/api/mcp/` ପାଇଁ ସୀମିତ — `mcp:connect` ଅନ୍ୟ କୌଣସି management route ରେ କିଛି ଅନୁମତି ଦେଉନାହିଁ (ଭବିଷ୍ୟତରେ ଯୋଡ଼ାଯାଇପାରୁଥିବା ଅନ୍ୟ ସମସ୍ତ LOCAL_ONLY bypass prefix ସମେତ), ଏବଂ ଏହାକୁ `MANAGEMENT_API_KEY_SCOPES` ଠାରୁ ଜାଣିଶୁଣି ବାଦ ଦିଆଯାଇଛି। `manage`/`admin` ଧାରଣ କରୁଥିବା କୀ ପୂର୍ବବତ୍ carve-out ପାସ୍ କରେ; ବ୍ୟାପକ management ଆକ୍ସେସ୍ ଆବଶ୍ୟକ ନଥିବା remote MCP-only caller ମାନଙ୍କ ପାଇଁ `mcp:connect` ଏକ କମ୍-ଅଧିକାର ବିକଳ୍ପ ଅଟେ।

#### ଅପରେଟର୍ ନିର୍ଦ୍ଦେଶନା ଏବଂ ଅଡିଟିଂ

ଆପଣ ଯଦି OmniRoute କୁ reverse proxy କିମ୍ବା tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ପଛରେ ଚଲାନ୍ତି, ତଥାପି loopback ଯାଞ୍ଚ ଉପରୋକ୍ତ spawn-capable ପଥଗୁଡ଼ିକୁ ସୁରକ୍ଷା ଦିଏ — ଯେଉଁ ଅନୁରୋଧର client address non-loopback, ତାହାକୁ auth ଚାଲିବା **ପୂର୍ବରୁ** `403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ, ତେଣୁ ଲିକ୍ ହୋଇଥିବା JWT ମଧ୍ୟ spawn ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରେ ନାହିଁ। ଅପରେଟର୍ଙ୍କର ଆହୁରି ଦୁଇଟି ଦାୟିତ୍ୱ ରହିଥାଏ:

- **ଲୁପ୍ବ୍ୟାକ୍ ଭାବେ କ୍ଲାଏଣ୍ଟ IP ଜାଲିଆତି କରି 403କୁ “ଠିକ” କରନ୍ତୁ ନାହିଁ।** `X-Forwarded-For: 127.0.0.1` ସେଟ୍ କରିବା, କିମ୍ବା ସୋର୍ସ ଠିକଣାକୁ ଲୁପ୍ବ୍ୟାକ୍କୁ ପୁନଃଲେଖନ କରୁଥିବା ପ୍ରକ୍ସି ବ୍ୟବହାର କରିବା, ଏହି ଟିଅର୍ ବନ୍ଦ କରୁଥିବା ସେହି RCE ଶ୍ରେଣୀକୁ ପୁନଃ ଖୋଲିଦିଏ। ପ୍ରକ୍ସି ମାଧ୍ୟମରେ ଡ୍ୟାସ୍ବୋର୍ଡ/API ଏକ୍ସପୋଜ୍ କରନ୍ତୁ — spawn-ସକ୍ଷମ ରୁଟ୍ଗୁଡ଼ିକୁ କେବେ ନୁହେଁ।
- **manage-scope ବାଇପାସ୍କୁ ସର୍ବନ୍ୟୁନ ରଖନ୍ତୁ।** କେବଳ `/api/mcp/` ବାଇପାସ୍ଯୋଗ୍ୟ, ଏବଂ କେବଳ `manage`-ସ୍କୋପ୍ଡ୍ API କୀ ସହିତ। `SPAWN_CAPABLE_PREFIXES`କୁ କେବେ ମଧ୍ୟ ବାଇପାସ୍ ତାଲିକାରେ ଯୋଡ଼ାଯାଇପାରିବ ନାହିଁ — zod ସ୍କିମା ଏଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ ଏବଂ `isLocalOnlyBypassableByManageScope` ରନ୍ଟାଇମ୍ରେ ଏଗୁଡ଼ିକୁ ଅସ୍ୱୀକାର କରେ (defence-in-depth), ଯାହା ଡ୍ୟାସ୍ବୋର୍ଡର “cannot be made bypassable” ଅର୍ଥ କରେ। ସେହି deny-listରେ କିଛି LOCAL_ONLY ରୁଟ୍ ମଧ୍ୟ ରହିଛି, ଯେଉଁଗୁଡ଼ିକ spawn କରେ ନାହିଁ କିନ୍ତୁ ଦୂରସ୍ଥ ଭାବେ କେବେ ମଧ୍ୟ ପହଞ୍ଚଯୋଗ୍ୟ ହେବା ଉଚିତ୍ ନୁହେଁ — `/api/oauth/kiro/auto-import` (ହୋଷ୍ଟ-ଲୋକାଲ୍ Kiro credential ଫାଇଲ୍ଗୁଡ଼ିକ ପଢ଼େ), `/api/discovery/` ଏବଂ `/api/issue-agent/`। ରନ୍ଟାଇମ୍ snapshot loader ମଧ୍ୟ ସଂରକ୍ଷିତ settings rowରୁ ଏପରି ଏଣ୍ଟ୍ରିଗୁଡ଼ିକୁ ବାହାର କରେ, ଏବଂ legacy JSON import (`/api/settings/import-json`) କେବେ ମଧ୍ୟ bypass କୀଗୁଡ଼ିକୁ ଲେଖେ ନାହିଁ। ପ୍ରତ୍ୟେକ `LOCAL_ONLY_API_PREFIXES` ଏଣ୍ଟ୍ରି deny-listରେ ଥିବା ଦରକାର କିମ୍ବା bypass-ଯୋଗ୍ୟ ଭାବେ ସମୀକ୍ଷା କରାଯାଇଥିବା ଦରକାର (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)। `/api/providers/` ଅଧୀନରେ ଥିବା dynamic-segment ଏବଂ static-path spawn-ସକ୍ଷମ ରୁଟ୍ଗୁଡ଼ିକ (ଯଥା `/login`, `/refresh-cursor`) flat `SPAWN_CAPABLE_PREFIXES` array ଦ୍ୱାରା ନୁହେଁ, ବରଂ `src/shared/constants/spawnCapablePrefixes.ts`ର regex-ଆଧାରିତ `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` companion ଦ୍ୱାରା ଆବୃତ — ଏଗୁଡ଼ିକୁ ଧରିବା ପାଇଁ flat arrayକୁ ସମଗ୍ର `/api/providers/` prefixକୁ ଆବୃତ କରିବାକୁ ପଡ଼ିବ, ଯାହା provider CRUD ପାଇଁ remote dashboardଗୁଡ଼ିକ ଯଥାର୍ଥ ଭାବେ ବ୍ୟବହାର କରୁଥିବା ଏକ route treeକୁ ଅତ୍ୟଧିକ ବ୍ୟାପକ କରିଦେବ।

**ପ୍ରବେଶ ଅଡିଟ୍ କରିବା** — ଅଫ୍-ହୋଷ୍ଟରୁ କେହି ଏହି ରୁଟ୍ଗୁଡ଼ିକୁ ପହଞ୍ଚୁନାହାନ୍ତି ବୋଲି ଯାଞ୍ଚ କରିବା ପାଇଁ:

- `/dashboard/settings/security`ରେ ଥିବା **Authorization Inventory** ଖୋଲନ୍ତୁ: ଏହା live LOCAL_ONLY prefix ତାଲିକା, କେଉଁ prefixଗୁଡ଼ିକ bypass-ଯୋଗ୍ୟ, ଏବଂ compile-time spawn-ସକ୍ଷମ (“cannot be made bypassable”) ସେଟ୍କୁ ଦେଖାଏ।
- ଉପରୋକ୍ତ prefixଗୁଡ଼ିକ ସହିତ non-loopback client address ଯୋଡ଼ି reverse-proxy / access logsରେ grep କରନ୍ତୁ। ଏପରି କୌଣସି hit ଯଦି `403 LOCAL_ONLY` ପରିବର୍ତ୍ତେ `200` ଫେରାଇଥାଏ, ତେବେ ତାହାର ଅର୍ଥ proxy ପ୍ରକୃତ client IPକୁ ଲୁଚାଉଛି — proxyକୁ ଠିକ କରନ୍ତୁ।
- ଏହି ପଥଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସି ଗୋଟିଏ ପାଇଁ OmniRouteର logsରେ ଥିବା `403 LOCAL_ONLY` ହେଉଛି guard ଆଶା କରାଯାଇଥିବା ଭାବେ କାମ କରୁଥିବାର ସଙ୍କେତ, suppress କରିବାକୁ ପଡ଼ିବା ଏକ ତ୍ରୁଟି ନୁହେଁ।

#### call-site probe gate ସହିତ ଦୂରସ୍ଥ ଭାବେ ପହଞ୍ଚଯୋଗ୍ୟ ରୁଟ୍ଗୁଡ଼ିକ

କିଛି ରୁଟ୍ ଦୂରସ୍ଥ dashboardରୁ ପହଞ୍ଚଯୋଗ୍ୟ ରହିବା ଦରକାର, କିନ୍ତୁ ସ୍ଥାନୀୟ callerମାନଙ୍କ ପାଇଁ ହୋଷ୍ଟ-ସାଇଡ୍ probe

`GET` ପାଇଁ ଏଗୁଡ଼ିକ LOCAL_ONLY ନୁହେଁ; ତାହା ପରିବର୍ତ୍ତେ handler `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) ସହିତ trusted peer verdict ପଢ଼େ ଏବଂ କେବଳ `loopback` / `lan` callerମାନଙ୍କ ପାଇଁ probe ଚଲାଏ। ଏକ `remote` caller non-spawning sources (persisted state, settings, fs checks)ରୁ ନିର୍ମିତ ସମାନ response shape ପାଏ, ଯେଉଁଥିରେ `probed: false` flag ଥାଏ।

କଲର୍ ଚୟନ କରିଥିବା ରୁଟ୍ରେ ପଏଣ୍ଟ୍ କରେ ଏବଂ ନୂତନ ଭାବେ ସୃଷ୍ଟି ହୋଇଥିବା Basic ପ୍ରମାଣପତ୍ରଗୁଡ଼ିକୁ ପୁନର୍ବାର ଦିଏ, `DELETE` ସେଗୁଡ଼ିକୁ ରୋଟେଟ୍ କରେ, ଏବଂ ପ୍ୟାରେଣ୍ଟ୍ `POST` Obsidian REST API ଟୋକେନ୍ ସଂରକ୍ଷଣ କରେ। GHSA-62vw କେବଳ `GET` ପାସୱାର୍ଡ ପ୍ରକାଶକୁ ଆଡ଼କରିଥିଲା; ଇସ୍ୟୁଆନ୍ସ ତଥାପି fail-open ସ୍ତରରେ ଥିଲା (GHSA-7pq4-8pvv-rx7r)। `enableObsidianVaultSync()` ଏହାସହିତ ଡାଟା ଡିରେକ୍ଟୋରୀ ଥିବା, ତାହାର ଭିତରେ ଥିବା କିମ୍ବା ତାହାକୁ ଧାରଣ କରୁଥିବା ଭଲ୍ଟ୍କୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

#### ପ୍ରମାଣପତ୍ର ରପ୍ତାନି ଏବଂ ପୁନଃସ୍ଥାପନ କେବଳ ଅପରେଟର୍ମାନଙ୍କ ପାଇଁ

ଉପରୋକ୍ତ ସ୍ତର କେବଳ _କିଛି_ ପ୍ରମାଣପତ୍ର ଆବଶ୍ୟକ କି ନାହିଁ ତାହା ନିର୍ଣ୍ଣୟ କରେ। ସଂରକ୍ଷିତ ପ୍ରମାଣପତ୍ର ଡାଉନଲୋଡ୍ କରୁଥିବା ରୁଟ୍ଗୁଡ଼ିକ ହ୍ୟାଣ୍ଡଲର୍ରେ ଦ୍ୱିତୀୟ ଯାଞ୍ଚ ଯୋଡ଼ନ୍ତି: `GET /api/settings/export-json` (ଡିକ୍ରିପ୍ଟ୍ କରାଯାଇଥିବା ପ୍ରୋଭାଇଡର୍ ସଂଯୋଗ ଏବଂ କଞ୍ଚା API କୀ), `GET /api/db-backups/export` (SQLite ଫାଇଲ୍) ଏବଂ `GET /api/db-backups/exportAll` (ସମ୍ପୂର୍ଣ୍ଣ ଆର୍କାଇଭ୍) `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`) କଲ୍ କରନ୍ତି। ଏହା ଏକ ଡ୍ୟାସ୍ବୋର୍ଡ୍ ସେସନ୍, ସ୍ଥାନୀୟ CLI ସବ୍ଜେକ୍ଟ୍, କିମ୍ବା ଲଗଇନ୍ ନିଷ୍କ୍ରିୟ ଥିବା ଏକ ଇନ୍ଷ୍ଟାନ୍ସକୁ ଗ୍ରହଣ କରେ, ଏବଂ ଯେକୌଣସି ସ୍କୋପ୍ର API କୀ (ଏଥିରେ `manage` ଏବଂ `admin` ସମେତ) ଏବଂ `oma_` ଆକ୍ସେସ୍ ଟୋକେନ୍ଗୁଡ଼ିକୁ `403` ଉତ୍ତର ଦିଏ। ବିନାଶକାରୀ ପ୍ରତିପକ୍ଷଗୁଡ଼ିକ ମଧ୍ୟ ସମାନ ସୀମା ଅଧୀନରେ ରହନ୍ତି: `POST /api/db-backups/import` (ଅପଲୋଡ୍ ହୋଇଥିବା `.sqlite`, `dryRun=true` ସମେତ), `POST /api/db-backups` (id ଦ୍ୱାରା ସଂରକ୍ଷିତ ବ୍ୟାକଅପ୍ ପୁନଃସ୍ଥାପନ) ଏବଂ `POST /api/settings/import-json` (ପୁରୁଣା JSON ପୁନଃସ୍ଥାପନ) ଲାଇଭ୍ ଡାଟାବେସ୍ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ସେଟିଂସ୍/ସଂଯୋଗ/API-କୀ ସେଟ୍କୁ ପ୍ରତିସ୍ଥାପନ କରନ୍ତି, ତେଣୁ ଏକ ମେସିନ୍ ପ୍ରମାଣପତ୍ର ମଧ୍ୟ ସେଗୁଡ଼ିକୁ ଟ୍ରିଗର୍ କରିପାରେ ନାହିଁ। ପୁନଃସ୍ଥାପନ ପଏଣ୍ଟ୍ ଧ୍ୱଂସ କରିବା ମଧ୍ୟ ସମାନ ସୀମା ଅଧୀନରେ ରହେ: `DELETE /api/db-backups` (କ୍ଲିନଅପ୍ — ସର୍ବଶେଷ N ରଖିବା / D ଦିନରୁ ପୁରୁଣାଗୁଡ଼ିକୁ ଛାଡ଼ିବା) ଏବଂ `PATCH /api/db-backups` (ରିଟେନ୍ସନ୍ ସେଟିଂସ୍), କାରଣ ସଂରକ୍ଷିତ ରିଟେନ୍ସନ୍ ହିଁ ପ୍ରତ୍ୟେକ ସ୍ୱୟଂଚାଳିତ ବ୍ୟାକଅପ୍ ପରେ `cleanupDbBackups()` (`src/lib/db/backup.ts`) ପ୍ରୟୋଗ କରୁଥିବା ନୀତି, ତେଣୁ `keepLatest: 1` ସଂରକ୍ଷଣ କରିପାରୁଥିବା ଏକ ମେସିନ୍ ପ୍ରମାଣପତ୍ର ପରବର୍ତ୍ତୀ ସ୍ନାପ୍ଶଟ୍ରେ ସବୁକିଛି ପ୍ରୁନ୍ କରିଦେଇପାରେ। ବ୍ୟାକଅପ୍ ତାଲିକାଭୁକ୍ତ କରିବା ଏବଂ ସୃଷ୍ଟି କରିବା (`GET`/`PUT /api/db-backups`) ସାଧାରଣ ମ୍ୟାନେଜମେଣ୍ଟ୍ ପ୍ରମାଣୀକରଣକୁ ରଖେ। ସିଙ୍କ୍ ଟୋକେନ୍ ଇସ୍ୟୁଆନ୍ସ (`POST /api/sync/tokens`) ସମାନ ହେଲ୍ପର୍ ସହିତ ବିଶ୍ୱସ୍ତ loopback ଆଭ୍ୟନ୍ତରୀଣ-ସେବା ଟୋକେନ୍ ବ୍ୟବହାର କରେ।

### ନୂତନ ଇନ୍ଷ୍ଟଲେସନ୍ ବୁଟ୍ଷ୍ଟ୍ରାପ୍ କେବଳ loopback — ପ୍ରକୃତ peer ଦ୍ୱାରା, `Host` ନୁହେଁ

କୌଣସି ମ୍ୟାନେଜମେଣ୍ଟ୍ ପାସୱାର୍ଡ୍ କନ୍ଫିଗର୍ କରାଯାଇନଥିଲେ (ଏବଂ କୌଣସି `INITIAL_PASSWORD` ନଥିଲେ), `src/shared/utils/apiAuth.ts` ରେ ଥିବା `isAuthRequired()` ଅଜ୍ଞାତନାମା ବୁଟ୍ଷ୍ଟ୍ରାପ୍କୁ **କେବଳ loopback peer** ପାଇଁ ଖୋଲା ରଖେ। ବିଶ୍ୱସ୍ତ peer ସିଗ୍ନାଲ୍ଗୁଡ଼ିକରୁ କ୍ରମାନୁସାରେ loopback ନିର୍ଣ୍ଣୟ କରାଯାଏ: ଟୋକେନ୍-ଷ୍ଟାମ୍ପ୍ କରାଯାଇଥିବା ପ୍ରକୃତ TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ନୀତି ଯାହା ଦେଖେ), ପାଇପ୍ଲାଇନ୍ର ନିଜସ୍ୱ `AUTHZ_HEADER_PEER_LOCALITY` ରାୟ (ରୁଟ୍ ହ୍ୟାଣ୍ଡଲର୍ଗୁଡ଼ିକ ଯାହା ଦେଖନ୍ତି, କେବଳ `OMNIROUTE_PEER_STAMP_TOKEN` ସେଟ୍ ଥିବାବେଳେ ବିଶ୍ୱସ୍ତ), କିମ୍ବା ସିଧାସଳଖ କଲର୍ମାନଙ୍କ ପାଇଁ ପ୍ରକୃତ ସକେଟ୍ peer। `Host` / `nextUrl.hostname` କେବେବି ପରାମର୍ଶ କରାଯାଏ ନାହିଁ, ଏବଂ ପ୍ରଥମ-ପାସୱାର୍ଡ୍ ଲେଖା (`POST /api/settings/require-login`) ପ୍ରତ୍ୟେକ ନେଟୱର୍କ୍ peer ପାଇଁ ଖୋଲା ନରଖି ସମାନ ନିୟମ ଅଧୀନରେ ରହେ (GHSA-7pq4-8pvv-rx7r)। `managementPolicy` ନିଜସ୍ୱ `peerContext` ରାୟକୁ ସ୍ପଷ୍ଟ ଭାବରେ ତଳକୁ ପଠାଏ, ତେଣୁ ORIGINAL (ଷ୍ଟ୍ରିପ୍ ପୂର୍ବର) ଅନୁରୋଧର ହେଡର୍ଗୁଡ଼ିକ ଏହାକୁ କେବେ ନିର୍ଣ୍ଣୟ କରନ୍ତି ନାହିଁ।

### ସ୍ତର 3 — MANAGEMENT (ଡିଫଲ୍ଟ)

ଅନ୍ୟ ସମସ୍ତ ମ୍ୟାନେଜମେଣ୍ଟ୍ ରୁଟ୍। `requireLogin=false` କନ୍ଫିଗର୍ କରାଯାଇନଥିଲେ ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ। CLI ଟୋକେନ୍ଗୁଡ଼ିକ ଏହି ରୁଟ୍ଗୁଡ଼ିକୁ ପ୍ରମାଣୀକରଣ କରିପାରନ୍ତି (loopback + ବୈଧ HMAC)।

## ମୂଲ୍ୟାୟନ କ୍ରମ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → fall through
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → allow (management_key)
     → otherwise                                  → reject 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → allow (system)
  3. hasValidCliToken(headers)?
     → allow (cli) [loopback + timingSafeEqual HMAC check]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → allow (dashboard_session)
     → manage-scope Bearer on a non-bypassable path?
        → allow (management_key)
     → reject 401/403
  5. requireLogin=false?
     → allow (anonymous)
```

LOCAL_ONLY ରୁଟ୍କୁ ସନ୍ତୁଷ୍ଟ କରିପାରୁଥିବା ଏକମାତ୍ର ପ୍ରମାଣୀକୃତ ପଥ ହେଉଛି ପଦକ୍ରମ 1ର manage-scope ଶାଖା; auth-backend ବିଫଳତା ମୋଡ୍ 503 ଫେରାଏ (403 ନୁହେଁ), ଯାହାଦ୍ୱାରା ମেয়ାଦ ଶେଷ ହୋଇଥିବା DB ନିରବରେ "deny" କୁ downgrade ହୁଏ ନାହିଁ।

## ଏକ ନୂତନ spawn-capable ରୁଟ୍ ଯୋଡ଼ିବା

1. `src/server/authz/routeGuard.ts` ରେ `LOCAL_ONLY_API_PREFIXES` କୁ path prefix ଯୋଡ଼ନ୍ତୁ
2. `tests/unit/authz/routeGuard.test.ts` ରେ ଏକ test ଯୋଡ଼ନ୍ତୁ, ଯାହା ନୂତନ prefix ପାଇଁ `isLocalOnlyPath()` true ଫେରାଏ ବୋଲି ନିଶ୍ଚିତ କରେ
3. **ଏହି ପଦକ୍ରମକୁ କେବେବି ଛାଡ଼ନ୍ତୁ ନାହିଁ** — `CLAUDE.md` ର Hard Rule #15 ଦେଖନ୍ତୁ
4. ନିର୍ଣ୍ଣୟ କରନ୍ତୁ: ଏହି ରୁଟ୍ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ରେ ମଧ୍ୟ ରହିବ କି?
   ଡିଫଲ୍ଟ ଉତ୍ତର ହେଉଛି **ନା**। କେବଳ ସେତେବେଳେ opt-in କରନ୍ତୁ, ଯେତେବେଳେ ରୁଟ୍ଟି manage-scope ଧାରକଙ୍କ ପାଇଁ ପ୍ରକାଶ କରିବାକୁ ସୁରକ୍ଷିତ ହୁଏ (ଅର୍ଥାତ୍ ଏହା ଇଚ୍ଛାଧୀନ user-controlled code spawn କରେ ନାହିଁ)।

## ଏକ manage-scope-bypassable path ଯୋଡ଼ିବା

1. ନିଶ୍ଚିତ କରନ୍ତୁ ଯେ ରୁଟ୍ଟି user-supplied code କିମ୍ବା commands ଚଲାଏ ନାହିଁ। ଯଦି ଚଲାଏ, ତେବେ ଥମ୍କନ୍ତୁ — ଏହି carve-out ହେଉଛି ଭୁଲ ଉପକରଣ।
2. `src/server/authz/routeGuard.ts` ରେ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` କୁ prefix ଯୋଡ଼ନ୍ତୁ
3. `tests/unit/authz/management-policy.test.ts` ରେ ସମସ୍ତ ଚାରିଟି request shape ପାଇଁ coverage ଯୋଡ଼ନ୍ତୁ: Bearer ନଥିଲେ (403), manage Bearer (allow), non-manage Bearer (403), ଏବଂ ପ୍ରତ୍ୟେକ prefix ପାଇଁ regression ଯେ `/api/cli-tools/runtime/*` manage Bearer ଥିଲେ ମଧ୍ୟ strict-loopback ରହିଥାଏ।

## OpenAPI ରେ Security Tier ଡକ୍ୟୁମେଣ୍ଟ କରିବା

`docs/openapi.yaml` ରେ ଏକ ନୂତନ ରୁଟ୍ ଯୋଡ଼ିବା ସମୟରେ, ଯଦି ରୁଟ୍ଟି `routeGuard.ts` ଦ୍ୱାରା ବର୍ଗୀକୃତ ହୋଇଥାଏ, ତେବେ ସମ୍ପର୍କିତ vendor extension ପ୍ରୟୋଗ କରନ୍ତୁ:

| routeGuard.ts ବର୍ଗୀକରଣ        | YAML annotation                 | Enforcement                                      |
| ----------------------------- | ------------------------------- | ------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`     | `x-loopback-only: true`         | Non-loopback ରୁ ନିରପେକ୍ଷ ଭାବରେ ବ୍ଲକ୍ କରାଯାଏ      |
| `ALWAYS_PROTECTED_API_PATHS`  | `x-always-protected: true`      | `requireLogin=false` ଥିଲେ ମଧ୍ୟ Auth ଆବଶ୍ୟକ       |
| Internal admin/debug route    | `x-internal: true`              | ଡିଫଲ୍ଟ ଭାବରେ /dashboard/api-endpoints ରୁ ଲୁଚାଯାଏ |
| None (public / standard auth) | (କୌଣସି annotation ଆବଶ୍ୟକ ନାହିଁ) | Standard `requireLogin`-ନିୟନ୍ତ୍ରିତ access        |

### ବୈଧତା ଯାଞ୍ଚ

YAML annotations ଏବଂ `routeGuard.ts` ମଧ୍ୟରେ ସମନ୍ୱୟ ଯାଞ୍ଚ କରିବା ପାଇଁ ଦୁଇଟି script ରହିଛି:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% ହେଲେ ବିଫଳ ହୁଏ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` କିମ୍ବା
  `x-always-protected` annotations compile-time constants ଠାରୁ ଭିନ୍ନ ହେଲେ ବିଫଳ ହୁଏ

ଉଭୟ script pre-commit hook ଏବଂ CI ରେ ଚାଲେ।

### False Positive ନିୟମ

ଯଦି `routeGuard.ts` constant ରେ ନଥିବା ଏକ ରୁଟ୍ରେ `x-always-protected` କିମ୍ବା `x-loopback-only` annotate କରାଯାଇଥାଏ, ତେବେ coverage script ବିଫଳ ହୁଏ। ସମାଧାନ ସବୁବେଳେ YAML କୁ `routeGuard.ts` ପ୍ରକୃତରେ ଯାହା enforce କରେ ତାହା ସହିତ ସମନ୍ୱୟ କରିବା — enforcement logic ମଧ୍ୟ implement ନକରି `routeGuard.ts` ରେ ରୁଟ୍ ଯୋଡ଼ିବା ନୁହେଁ।
