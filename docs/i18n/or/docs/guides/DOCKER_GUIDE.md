## ଶୀଘ୍ର ଚାଳନ

> **ଗୋଟିଏ କମାଣ୍ଡରେ ସ୍ୱୟଂ-ହୋଷ୍ଟ କରିବେ?**
> [ସ୍ୱୟଂ-ହୋଷ୍ଟ ଗାଇଡ୍](../getting-started/SELF_HOST_GUIDE.md) ଦେଖନ୍ତୁ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ପ୍ରକାଶିତ ଇମେଜ୍ +
> Redis, କେବଳ loopback, କୌଣସି ପ୍ରୋଫାଇଲ୍ ବିକଳ୍ପ ନାହିଁ)। ନିମ୍ନରେ ଥିବା ଶୀଘ୍ର ଚାଳନଟି
> ଅନ୍ୟତ୍ର ପୂର୍ବରୁ Redis ଚଳାଉଥିବା ବ୍ୟବହାରକାରୀଙ୍କ ପାଇଁ
> ଏକକ-କଣ୍ଟେନର୍ ପଥ ଅଟେ।

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## ପରିବେଶ ଫାଇଲ୍ ସହିତ

# ପ୍ରଥମେ .env କପି ଏବଂ ସମ୍ପାଦନା କରନ୍ତୁ

## Docker Compose

```bash
# ମୂଳ ପ୍ରୋଫାଇଲ୍ (କୌଣସି CLI ଟୁଲ୍ ନାହିଁ)
docker compose --profile base up -d

# CLI ପ୍ରୋଫାଇଲ୍ (Claude Code, Codex, OpenClaw ଅନ୍ତର୍ନିହିତ)
docker compose --profile cli up -d

# ହୋଷ୍ଟ ପ୍ରୋଫାଇଲ୍ (Linux-ପ୍ରଥମ; ହୋଷ୍ଟ CLI ବାଇନାରିଗୁଡ଼ିକୁ କେବଳ-ପଠନୀୟ ଭାବେ ମାଉଣ୍ଟ କରେ)
docker compose --profile host up -d

# ୱେବ୍ ପ୍ରୋଫାଇଲ୍ (ୱେବ୍-ସେସନ୍ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI ସାଇଡକାର୍କୁ ଏକତ୍ର କରନ୍ତୁ
docker compose --profile cli --profile cliproxyapi up -d
```

## ଉପଲବ୍ଧ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ

ମୁଖ୍ୟ ଡିପ୍ଲୟମେଣ୍ଟ ଆକୃତିଗୁଡ଼ିକ ପାଇଁ OmniRoute ସହିତ Compose ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ ଉପଲବ୍ଧ। ଆପଣଙ୍କ ପରିବେଶ ସହ ମେଳ ଖାଉଥିବା ପ୍ରୋଫାଇଲ୍ଟି ବାଛନ୍ତୁ।

| ପ୍ରୋଫାଇଲ୍       | ସେବା             | କେବେ ବ୍ୟବହାର କରିବେ                                                                                                                                        | କମାଣ୍ଡ                                       |
| --------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ଡିଫଲ୍ଟ) | `omniroute-base` | ହେଡ୍ଲେସ୍ ସର୍ଭର୍ / ସର୍ବନିମ୍ନ ରନ୍ଟାଇମ୍, କୌଣସି ପ୍ରଦାନକାରୀ CLI ସଂଲଗ୍ନ ନାହିଁ                                                                                   | `docker compose --profile base up -d`        |
| `cli`           | `omniroute-cli`  | `omniroute providers/setup/doctor` ଏବଂ ସଂଲଗ୍ନ CLIଗୁଡ଼ିକୁ (Codex, Claude Code, Droid, OpenClaw) ଡାକୁଥିବା ଏଜେଣ୍ଟିକ୍ ୱାର୍କଫ୍ଲୋଗୁଡ଼ିକ                         | `docker compose --profile cli up -d`         |
| `host`          | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` ଇତ୍ୟାଦିକୁ କେବଳ-ପଠନୀୟ ଭାବେ ମାଉଣ୍ଟ କରି ହୋଷ୍ଟ CLIଗୁଡ଼ିକ ପାଇଁ `network_mode`-ସଦୃଶ ଆକ୍ସେସ୍ ଚାହୁଁଥିବା Linux ହୋଷ୍ଟଗୁଡ଼ିକ | `docker compose --profile host up -d`        |
| `cliproxyapi`   | `cliproxyapi`    | ଅପ୍ଷ୍ଟ୍ରିମ୍ CLI ପ୍ରକ୍ସିଂ ପାଇଁ ପୋର୍ଟ `8317`ରେ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ସାଇଡକାର୍ ଚଲାନ୍ତୁ                                 | `docker compose --profile cliproxyapi up -d` |
| `web`           | `omniroute-web`  | ବ୍ରାଉଜର୍ ଆବଶ୍ୟକ କରୁଥିବା ୱେବ୍-ସେସନ୍ ପ୍ରଦାନକାରୀଗୁଡ଼ିକ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ବିଲ୍ଡ କରେ, Chromium ଅନ୍ତର୍ଭୁକ୍ତ)        | `docker compose --profile web up -d`         |

> ଏକାଧିକ ପ୍ରୋଫାଇଲ୍କୁ ଏକତ୍ର କରାଯାଇପାରେ: `docker compose --profile cli --profile cliproxyapi up -d`।

## OmniRoute Dockerରେ ଚାଲୁଥିବାବେଳେ host CLI ଟୁଲ୍ଗୁଡ଼ିକୁ ବିନ୍ୟାସ କରିବା

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ଏବଂ dashboardର
**ବିନ୍ୟାସ ସଂରକ୍ଷଣ କରନ୍ତୁ** ବଟନ୍—ସମସ୍ତେ `~/.codex/*.config.toml` ପରି ଫାଇଲ୍ ଲେଖନ୍ତି। ସେହି ପଥଗୁଡ଼ିକ
କେବଳ CLI ପ୍ରକୃତରେ ଚାଲୁଥିବା ମେସିନ୍ରେ ହିଁ ଅର୍ଥପୂର୍ଣ୍ଣ। ସେଗୁଡ଼ିକୁ
container ଭିତରେ ଚଲାଇଲେ, ଲେଖାଟି containerର ନିଜସ୍ୱ home (`/home/node` —
imageଟି `USER node` ଭାବେ ଚାଲେ)ରେ ସଂରକ୍ଷିତ ହୁଏ, ଯାହାକୁ କୌଣସି host CLI କେବେ ପଢ଼ିବ ନାହିଁ ଏବଂ containerଟି
ପୁନଃସୃଷ୍ଟି ହେବା ମାତ୍ରେ ଯାହା ବିଲୋପ ହୋଇଯାଏ।

OmniRoute ଏହାକୁ ଚିହ୍ନଟ କରେ ଏବଂ ଆପଣ ବ୍ୟବହାର କରିପାରିବେ ନାହିଁ ଏପରି ସଫଳତା ସୂଚନା ଦେବା ପରିବର୍ତ୍ତେ
ନିର୍ଦ୍ଦେଶ ସହିତ ଲେଖାକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ: CLI `2` ସହିତ ବନ୍ଦ ହୁଏ ଏବଂ API
`containerEphemeralTarget: true` ସହିତ `422` ଉତ୍ତର ଦିଏ।

### ସୁପାରିସକୃତ: CLIକୁ hostରେ ଏବଂ OmniRouteକୁ Dockerରେ ଚଲାନ୍ତୁ

containerଟି API ପ୍ରଦାନ କରେ; CLI ଆପଣଙ୍କ host ଟୁଲ୍ଗୁଡ଼ିକୁ ବିନ୍ୟାସ କରେ।

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLIକୁ container ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ
omniroute setup-codex                      # ଆପଣଙ୍କ hostରେ ପ୍ରକୃତ ~/.codex ଲେଖେ
```

Codex, Claude Code, Cursor କିମ୍ବା ସମାନ ଟୁଲ୍ ଆପଣଙ୍କ
laptopରେ ଚାଲୁଥିବାବେଳେ ଏହା ହେଉଛି ଉଚିତ ବିକଳ୍ପ — ଏବଂ ଏହା ହିଁ ସାଧାରଣ ବ୍ୟବସ୍ଥା।

### ବିକଳ୍ପ: host config ଡିରେକ୍ଟୋରିଗୁଡ଼ିକୁ bind-mount କରନ୍ତୁ (`host` profile)

ଯଦି ଆପଣ containerକୁ ହିଁ ନିଜ host config ଲେଖିବାକୁ ଦେବାକୁ ଚାହାନ୍ତି, ତେବେ
ଡିରେକ୍ଟୋରିଗୁଡ଼ିକୁ mount କରନ୍ତୁ ଏବଂ `CLI_CONFIG_HOME`କୁ mount root ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ। `host` profile
ପୂର୍ବରୁ ଏହା କରେ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

bind mount ହିଁ ପଥଟିକୁ ବିଶ୍ୱସନୀୟ କରେ: OmniRoute
`/proc/self/mountinfo` ପଢ଼େ ଏବଂ mounted ପଥଗୁଡ଼ିକରେ (ଏବଂ ଯେଉଁ ଡିରେକ୍ଟୋରିର
childଗୁଡ଼ିକ mount ହୋଇଛି, ଯାହା ଉପରୋକ୍ତ `/host-home` ଗଠନ ସହିତ ଠିକ୍ ମେଳ ଖାଏ) ଲେଖିବାକୁ ଅନୁମତି ଦିଏ, ଏବଂ
ତଥାପି unmounted ପଥଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

### ଜରୁରୀ ବିକଳ୍ପ: containerର ନିଜସ୍ୱ CLIଗୁଡ଼ିକୁ ବିନ୍ୟାସ କରନ୍ତୁ (ସୀମିତ ଭାବେ ବ୍ୟବହାର କରନ୍ତୁ)

CLIଗୁଡ଼ିକ ପ୍ରକୃତରେ container ଭିତରେ ଥିବାବେଳେ (`cli` profile), ଲେଖାଟି
ଉଦ୍ଦେଶ୍ୟମୂଳକ ଅଟେ। ଯେକୌଣସି `setup-*` commandକୁ `--allow-container-write` ପ୍ରଦାନ କରନ୍ତୁ, କିମ୍ବା server ପାଇଁ
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ସେଟ୍ କରନ୍ତୁ। ଏହା container ପରେ ଅବିକଳ ରହିବ ନାହିଁ ବୋଲି
ଏକ ଚେତାବନୀ ସହିତ ଲେଖା ଜାରି ରହେ।

> **ସୁରକ୍ଷା ଚେତାବନୀ — `cli` profile + `docker.sock` mount।**
> container ଭିତରର auto-updater ଯେପରି host daemonରୁ stackକୁ ପୁନଃସୃଷ୍ଟି କରିପାରିବ, ସେଥିପାଇଁ `cli` profile
> `/var/run/docker.sock`କୁ bind-mount କରେ
> (`src/lib/system/autoUpdate.ts` ସେହି socketକୁ ଯାଞ୍ଚ କରେ ଏବଂ ଏହା
> ଉପସ୍ଥିତ ନଥିଲେ Docker ପଥକୁ ଏଡ଼ାଇଯାଏ)। ସେହି socketଟି **ଏକ host-root ବିଶ୍ୱାସ
> ସୀମା**: ଏହା ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରୁଥିବା ଯେକୌଣସି ଜିନିଷ root ଭାବେ host Docker daemonକୁ
> ନିୟନ୍ତ୍ରଣ କରିପାରେ — ଏହା hostରେ ଥିବା ଯେକୌଣସି container ସୃଷ୍ଟି, ଯାଞ୍ଚ, ବନ୍ଦ ଏବଂ ଅପସାରଣ କରିପାରେ।
> ଏହାର ପ୍ରଭାବ:
>
> 1. **`cli` profileର portକୁ କେବେ ମଧ୍ୟ networkରେ ପ୍ରକାଶ କରନ୍ତୁ ନାହିଁ।** ଏହାକୁ
>    `127.0.0.1`ରେ publish କରନ୍ତୁ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LANରୁ ପହଞ୍ଚଯୋଗ୍ୟ `cli` profile ଯେକୌଣସି dashboard-ସ୍ତରୀୟ RCEକୁ
>    hostର ସମ୍ପୂର୍ଣ୍ଣ ନିୟନ୍ତ୍ରଣ ହରାଇବାରେ ପରିଣତ କରେ।
> 2. **`cli` profileରେ କୌଣସି ଅତିରିକ୍ତ host ଡିରେକ୍ଟୋରି bind କରନ୍ତୁ ନାହିଁ।**
>    Docker socket ସହ ଅନ୍ୟ କୌଣସି mount containerକୁ ଆପଣଙ୍କ filesystem ଏବଂ host configରେ
>    ସମ୍ପୂର୍ଣ୍ଣ read/write ଅଧିକାର ଦିଏ। ଯଦି କୌଣସି ଟୁଲ୍କୁ ଏକ project ଦେଖିବା ଆବଶ୍ୟକ, ତେବେ CLI binary ସହିତ ତାହାକୁ
>    ସ୍ଥାନୀୟ ଭାବେ ଚଲାନ୍ତୁ — ତାହାକୁ `cli` container ଭିତରେ mount କରନ୍ତୁ ନାହିଁ।
>
> ଯଦି ଆପଣଙ୍କୁ container ଭିତରର auto-update ଆବଶ୍ୟକ ନାହିଁ, ତେବେ `cli` profileକୁ ବନ୍ଦ ରଖନ୍ତୁ
> (`COMPOSE_PROFILES=core,redis` କିମ୍ବା ଏହାଠାରୁ ଛୋଟ)। ଅନ୍ୟ profileଗୁଡ଼ିକ
> Docker socketକୁ mount କରନ୍ତି ନାହିଁ।
>
> MITM ସମ୍ବନ୍ଧିତ threat model ପାଇଁ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`ରେ compile କରାଯାଇନାହିଁ) ଦେଖନ୍ତୁ,
> ଏବଂ `codex`/`claude-code`/`droid`/`openclaw` binaryର ଉତ୍ପତ୍ତି ଶୃଙ୍ଖଳ ପାଇଁ
> `docs/security/SUPPLY_CHAIN.md` ଦେଖନ୍ତୁ।

## Redis ସାଇଡକାର୍

OmniRoute ବିତରିତ ରେଟ୍ ଲିମିଟର୍ ଏବଂ ଅଂଶୀଦାର କ୍ୟାଶ୍କୁ ସମର୍ଥନ କରିବା ପାଇଁ Redis ଉପରେ ନିର୍ଭର କରେ। `redis` ସେବାଟି `docker-compose.yml`ରେ **ସର୍ବଦା ପରିଭାଷିତ** ଥାଏ (ଏଥିରେ କୌଣସି ପ୍ରୋଫାଇଲ୍ ଗେଟ୍ ନାହିଁ) ଏବଂ ଅନ୍ୟ ଯେକୌଣସି ପ୍ରୋଫାଇଲ୍ ସହିତ ଆରମ୍ଭ ହୁଏ।

| ବିବରଣୀ                    | ମୂଲ୍ୟ                                       |
| ------------------------- | ------------------------------------------- |
| ଇମେଜ୍                     | `redis:7-alpine`                            |
| କଣ୍ଟେନର୍ ନାମ              | `omniroute-redis`                           |
| ଆଭ୍ୟନ୍ତରୀଣ ପୋର୍ଟ          | `6379`                                      |
| ହୋଷ୍ଟ ପୋର୍ଟ (ଓଭର୍ରାଇଡ୍)   | `REDIS_PORT` (ଡିଫଲ୍ଟ ଭାବେ `6379`)           |
| ହୋଷ୍ଟ ବାଇଣ୍ଡ୍ (ଓଭର୍ରାଇଡ୍) | `REDIS_BIND_HOST` (ଡିଫଲ୍ଟ ଭାବେ `127.0.0.1`) |
| ଭଲ୍ୟୁମ୍                   | `omniroute-redis-data` → `/data`            |
| ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ           | `redis-cli ping` (10s ବ୍ୟବଧାନ)              |

ସମ୍ପର୍କିତ ପରିବେଶ ଭେରିଏବଲ୍ଗୁଡ଼ିକ:

- `REDIS_URL` — ଆପ୍ରେ ଇଞ୍ଜେକ୍ଟ କରାଯାଉଥିବା ସଂଯୋଗ ଷ୍ଟ୍ରିଙ୍ଗ୍ (ଡିଫଲ୍ଟ ଭାବେ `redis://redis:6379`)।
- `REDIS_PORT` — Redis କଣ୍ଟେନର୍ ପାଇଁ ହୋଷ୍ଟ-ପାର୍ଶ୍ୱ ପୋର୍ଟ ମ୍ୟାପିଂ।
- `REDIS_BIND_HOST` — ଯେଉଁ ହୋଷ୍ଟ ଇଣ୍ଟରଫେସ୍ରେ ପୋର୍ଟଟି ପ୍ରକାଶିତ ହୁଏ। ଡିଫଲ୍ଟ ଭାବେ `127.0.0.1`।

> **ଡିଫଲ୍ଟ ଭାବେ ଲୁପ୍ବ୍ୟାକ୍ କାହିଁକି:** ସାଇଡକାର୍ଟି `requirepass` ବିନା ଚାଲେ, ଏବଂ ଆପ୍
> କଣ୍ଟେନର୍ଗୁଡ଼ିକ compose ନେଟୱର୍କ (`redis:6379`) ମାଧ୍ୟମରେ ଏହା ସହିତ ସଂଯୋଗ କରନ୍ତି — ପ୍ରକାଶିତ ପୋର୍ଟଟି
> କେବଳ ହୋଷ୍ଟ-ପାର୍ଶ୍ୱ ଟୁଲିଂ (`redis-cli`, ଏକ ସ୍ଥାନୀୟ `npm run dev`) ପାଇଁ ରହିଛି। `0.0.0.0`ରେ ପ୍ରକାଶ କଲେ
> ଆପଣଙ୍କ LANର ପ୍ରତ୍ୟେକ ହୋଷ୍ଟ ପାଇଁ ଏକ ଅପ୍ରମାଣିତ Redis ଉନ୍ମୁକ୍ତ ହୋଇଯିବ। ଯଦି ଆପଣ
> `REDIS_BIND_HOST=0.0.0.0` ସେଟ୍ କରନ୍ତି, ତେବେ ସେବାର `command:`ରେ ମଧ୍ୟ `--requirepass` ଯୋଗ କରନ୍ତୁ।

**Redis ନିଷ୍କ୍ରିୟ କରିବା** ସୁପାରିସ କରାଯାଏ ନାହିଁ (ରେଟ୍ ଲିମିଟର୍ ଇନ୍-ମେମୋରି ଫଲ୍ବ୍ୟାକ୍କୁ ଅବନମିତ ହେବ)। ଯଦି ଆପଣଙ୍କୁ ଏହା କରିବାକୁ ହିଁ ପଡ଼େ, ତେବେ `docker-compose.yml`ରେ ଥିବା `redis:` ସେବା ବ୍ଲକ୍କୁ ହଟାନ୍ତୁ/କମେଣ୍ଟ କରନ୍ତୁ କିମ୍ବା ଏହାକୁ ଶୂନ୍ୟକୁ ସ୍କେଲ୍ କରନ୍ତୁ:

```bash
docker compose up -d --scale redis=0
```

## ପ୍ରଡକ୍ସନ୍ Compose

ଡେଭ୍ ସହିତ ସମାନ୍ତରାଳ ଭାବେ ଚାଲୁଥିବା ଏକ ପୃଥକ ପ୍ରଡକ୍ସନ୍ ସ୍ନାପ୍ସଟ୍ ପାଇଁ `docker-compose.prod.yml` ବ୍ୟବହାର କରନ୍ତୁ।

| ବିବରଣୀ                   | ମୂଲ୍ୟ                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------- |
| ଫାଇଲ୍                    | `docker-compose.prod.yml`                                                                         |
| ଡିଫଲ୍ଟ ଡ୍ୟାସ୍ବୋର୍ଡ ପୋର୍ଟ | `PROD_DASHBOARD_PORT=20130` (ଆଭ୍ୟନ୍ତରୀଣ `${DASHBOARD_PORT:-20128}`କୁ ମ୍ୟାପ୍ କରାଯାଇଛି)             |
| ଡିଫଲ୍ଟ API ପୋର୍ଟ         | `PROD_API_PORT=20131`                                                                             |
| ଇମେଜ୍                    | `omniroute:prod` (`runner-cli` ଟାର୍ଗେଟ୍ରୁ ବିଲ୍ଡ୍ ହୋଇଛି)                                           |
| Redis କଣ୍ଟେନର୍           | `omniroute-redis-prod` (`redis:8.6.2`, ଉତ୍ସର୍ଗୀକୃତ `redis-prod-data` ଭଲ୍ୟୁମ୍)                     |
| ଡାଟା ଭଲ୍ୟୁମ୍             | `omniroute-prod-data` (ନାମିତ, ପୁନଃବିଲ୍ଡ୍ଗୁଡ଼ିକ ମଧ୍ୟରେ ସ୍ଥାୟୀ ରହେ)                                 |
| ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚଗୁଡ଼ିକ    | `node healthcheck.mjs` + `redis-cli ping`, Redisର ସ୍ୱାସ୍ଥ୍ୟ ଆଧାରରେ ଗେଟ୍ ହୋଇଥିବା `depends_on` ସହିତ |

ବ୍ୟବହାର କରିବା ପ୍ରଣାଳୀ:

```bash
# ପ୍ରଡକ୍ସନ୍ ଷ୍ଟାକ୍ ବିଲ୍ଡ୍ ଏବଂ ଆରମ୍ଭ କରନ୍ତୁ
docker compose -f docker-compose.prod.yml up -d --build

# ଲଗ୍ଗୁଡ଼ିକୁ ଷ୍ଟ୍ରିମ୍ କରନ୍ତୁ
docker compose -f docker-compose.prod.yml logs -f

# ବନ୍ଦ କରନ୍ତୁ (ଭଲ୍ୟୁମ୍ଗୁଡ଼ିକୁ ରଖନ୍ତୁ)
docker compose -f docker-compose.prod.yml down
```

ପ୍ରଡକ୍ସନ୍ ଷ୍ଟାକ୍ଟି ଡେଭ୍ compose ସହିତ ସମାନ୍ତରାଳ ଭାବେ ଚାଲେ (ଭିନ୍ନ କଣ୍ଟେନର୍ ନାମ, ପୋର୍ଟ ଏବଂ ଭଲ୍ୟୁମ୍), ତେଣୁ ପ୍ରଡକ୍ସନ୍ ଚାଲୁ ରହିଥିବାବେଳେ ଆପଣ ସ୍ଥାନୀୟ ଭାବେ ପୁନରାବୃତ୍ତିମୂଳକ ବିକାଶ ଜାରି ରଖିପାରିବେ।

## Dockerfile ପର୍ଯ୍ୟାୟଗୁଡ଼ିକ

ରିପୋଜିଟୋରୀଟି ଏକ ବହୁ-ପର୍ଯ୍ୟାୟ Dockerfile (`Dockerfile`) ସହିତ ଆସେ। ଚାରିଟି ପର୍ଯ୍ୟାୟ ଉପଲବ୍ଧ କରାଯାଇଛି; ଆପଣଙ୍କ ବ୍ୟବହାର ପାଇଁ ଉପଯୁକ୍ତ `target` ବାଛନ୍ତୁ।

| ପର୍ଯ୍ୟାୟ      | ମୂଳ ଇମେଜ୍             | ଉଦ୍ଦେଶ୍ୟ                                                                                                                                                                                                                                                                                                |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ନିର୍ଭରତାଗୁଡ଼ିକ ସଂସ୍ଥାପନ କରେ (`npm ci --legacy-peer-deps`) ଏବଂ `npm run build` ଚଲାଏ (ଡିଫଲ୍ଟ ଭାବରେ Turbopack — ନିମ୍ନରେ ଥିବା ବିଲ୍ଡ-ସମୟ ସମ୍ବଳଗୁଡ଼ିକ ଦେଖନ୍ତୁ)                                                                                                                                                |
| `runner-base` | `node:26-trixie-slim` | Next.js-ର ସ୍ୱତନ୍ତ୍ର ଆଉଟପୁଟ୍ ସହିତ ପ୍ରଡକ୍ସନ୍ ରନ୍ଟାଇମ୍। **କୌଣସି ପ୍ରଦାତା CLI ବଣ୍ଡଲ୍ କରାଯାଇନାହିଁ।**                                                                                                                                                                                                          |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ଏବଂ ଗ୍ଲୋବାଲ୍ CLI-ଗୁଡ଼ିକ ଯୋଡ଼େ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`। **ଏଜେଣ୍ଟିକ୍ କାର୍ଯ୍ୟପ୍ରବାହ ପାଇଁ ଏହା ବାଛନ୍ତୁ।**                                                                                                                    |
| `runner-web`  | `runner-base`         | ୱେବ୍-ସେସନ୍ ପ୍ରଦାତାମାନଙ୍କ ପାଇଁ Playwright + ଏକ Chromium ବ୍ରାଉଜର୍ (`--with-deps`) ଯୋଡ଼େ: `gemini-web`, `claude-web`, `claude-turnstile`। **ଆପଣ ସେହି ପ୍ରଦାତାଗୁଡ଼ିକ ବ୍ୟବହାର କରୁଥିଲେ ଏହା ବାଛନ୍ତୁ** — ଏହା ବିନା ସାଧାରଣ ଇମେଜ୍ ଅନୁରୋଧ ସମୟରେ ବିଫଳ ହୁଏ (ରିଲିଜ୍ ଚ୍ୟାନେଲ୍ଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା `-web` ଟିପ୍ପଣୀ ଦେଖନ୍ତୁ)। |

ନିର୍ଦ୍ଦିଷ୍ଟ ଏକ ଟାର୍ଗେଟ୍କୁ ହସ୍ତକୃତ ଭାବରେ ବିଲ୍ଡ କରନ୍ତୁ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ବିଲ୍ଡ-ସମୟ ସମ୍ବଳଗୁଡ଼ିକ

ତିନୋଟି ବିଲ୍ଡ ଆର୍ଗୁମେଣ୍ଟ୍ `builder` ପର୍ଯ୍ୟାୟର ସମ୍ବଳ ବ୍ୟୟକୁ ନିୟନ୍ତ୍ରଣ କରେ। ସେଗୁଡ଼ିକ କେବଳ ବିଲ୍ଡ-ସମୟ ପାଇଁ —
`OMNIROUTE_MEMORY_MB` (ନିମ୍ନରେ) ଏକ ପୃଥକ ରନ୍ଟାଇମ୍ ନିୟନ୍ତ୍ରକ।

| ବିଲ୍ଡ ଆର୍ଗୁମେଣ୍ଟ୍           | ଡିଫଲ୍ଟ | ପ୍ରଭାବ                                                                                                   |
| --------------------------- | ------ | -------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`    | `0` webpack ସହିତ ବିଲ୍ଡ କରେ: ସର୍ବାଧିକ ମେମୋରି ବ୍ୟବହାର କମ୍, କିନ୍ତୁ ଧୀର। `1` Turbopack ବ୍ୟବହାରକୁ ସକ୍ରିୟ କରେ। |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144` | ଆରମ୍ଭ କରାଯାଇଥିବା `next build` ପାଇଁ V8 heap ସୀମା (`--max-old-space-size`)।                                |
| `OMNIROUTE_BUILD_WORKERS`   | `2`    | `CIRCLE_NODE_TOTAL`କୁ ମୂଲ୍ୟ ପ୍ରଦାନ କରେ; ପୃଷ୍ଠା-ଡାଟା ସଂଗ୍ରହ ପାଇଁ Next `workers = N - 1` ନିର୍ଦ୍ଧାରଣ କରେ।   |

ଏକ ବଡ଼ builder-ରେ `OMNIROUTE_BUILD_WORKERS` ହେଉଛି ବୃଦ୍ଧି କରିବାକୁ ଥିବା ପାରାମିଟର୍ ଏବଂ ସୀମିତ ସମ୍ବଳର ବିଲ୍ଡ `✓ Compiled successfully` **ପରେ** ବନ୍ଦ ହୋଇଗଲେ ପ୍ରଥମେ ଏହାକୁ ସନ୍ଦେହ କରିବା ଉଚିତ। ପ୍ରତ୍ୟେକ ପୃଷ୍ଠା-ଡାଟା worker ଏକ ସ୍ୱତନ୍ତ୍ର ପ୍ରକ୍ରିୟା, ଏବଂ ମୂଳ `next build` ମଧ୍ୟ ସେହିପରି; ଏକ ସକ୍ରିୟ VPS ପୁନରୁତ୍ପାଦନରେ (issue #7518) `NODE_OPTIONS` heap ଫ୍ଲାଗ୍ଠାରୁ ସ୍ୱାଧୀନ ଭାବରେ ପ୍ରତ୍ୟେକ ପ୍ରକ୍ରିୟାର ସର୍ବାଧିକ RSS ~4.5 GB ମାପ କରାଯାଇଥିଲା (Turbopack V8 heap ବାହାରେ native/Rust ମେମୋରିରେ କମ୍ପାଇଲ୍ କରେ)। `2`-ର ଡିଫଲ୍ଟ (→ 1 worker, ମୋଟ 2ଟି ପ୍ରକ୍ରିୟା) ପ୍ରକାଶନ ପାଇପ୍ଲାଇନ୍ ବ୍ୟବହାର କରୁଥିବା 16 GB / 4 vCPU GitHub-hosted runner ପାଇଁ ନିର୍ଦ୍ଧାରିତ। `8`ରେ (→ 7 workers) ସେହି runner-ର ମେମୋରି ଶେଷ ହୋଇଗଲା ଏବଂ buildkit `ResourceExhausted: ... cannot allocate memory` ସହିତ ପଦକ୍ଷେପଟିକୁ ବିଫଳ କଲା; ପ୍ରତି-ପ୍ରକ୍ରିୟା RSSକୁ ଅନୁମାନ କରିବା ପରିବର୍ତ୍ତେ ସିଧାସଳଖ ମାପିବା ପରେ `3` (→ 2 workers) ମଧ୍ୟ ଉପଲବ୍ଧ ମେମୋରିରେ ଫିଟ୍ ହେଲା ନାହିଁ। `tests/unit/docker-build-memory-budget.test.ts` ମାପ କରାଯାଇଥିବା ମୂଲ୍ୟ ଆଧାରରେ ହିସାବ କରେ ଏବଂ ଯେକୌଣସି ନିୟନ୍ତ୍ରକ runner-ର କ୍ଷମତା ଅତିକ୍ରମ କଲେ ବିଫଳ ହୁଏ।

Turbopack V8 heap-ର **ବାହାରେ** ଅବସ୍ଥିତ native Rust ମେମୋରିରେ କମ୍ପାଇଲ୍ କରେ, ତେଣୁ `OMNIROUTE_BUILD_MEMORY_MB` ଏହାକୁ ସୀମିତ କରେନାହିଁ। ମେମୋରି ସୀମା ଥିବା ଏକ ହୋଷ୍ଟ୍ରେ ବିଲ୍ଡଟି କୌଣସି ତ୍ରୁଟି ସନ୍ଦେଶ ବିନା OOM killer ଦ୍ୱାରା SIGKILL କରାଯାଏ — ଏହା କେବଳ `Creating an optimized production build` ମଝିରେ ବନ୍ଦ ହୋଇଯାଏ, ଯାହା ମେମୋରି ଶେଷ ହେବା ପରିବର୍ତ୍ତେ ହ୍ୟାଙ୍ଗ୍ ହୋଇଥିବା ଭଳି ଦେଖାଯାଏ। ଏହି କାରଣରୁ `npm run dev` / `npm run build`ରେ Turbopack କୋଡ୍ ଡିଫଲ୍ଟ ହୋଇଥିଲେ ମଧ୍ୟ `Dockerfile` webpack (`OMNIROUTE_USE_TURBOPACK=0`)କୁ ଡିଫଲ୍ଟ କରେ: କୌଣସି ବିଲ୍ଡ ଆର୍ଗୁମେଣ୍ଟ୍ ବିନା ଏକ ସାଧାରଣ `docker build .` (ଯାହା Railway ଏବଂ ଅନ୍ୟ ଏକ-କ୍ଲିକ୍ ହୋଷ୍ଟ୍ଗୁଡ଼ିକ ଚଲାନ୍ତି) ମେମୋରି-ସୀମିତ builder-ରେ ନିରବରେ ବନ୍ଦ ହେବା ଉଚିତ୍ ନୁହେଁ। ପ୍ରକାଶିତ ଇମେଜ୍ଗୁଡ଼ିକ ପୂର୍ବରୁ `docker-publish.yml`ରେ ସ୍ପଷ୍ଟ ଭାବରେ `OMNIROUTE_USE_TURBOPACK=0` ପାସ୍ କରନ୍ତି। ପ୍ରଚୁର RAM ଥିବା builder-ରେ ଦ୍ରୁତ ବିଲ୍ଡ ପାଇଁ Turbopack ସକ୍ରିୟ କରନ୍ତୁ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ସକ୍ରିୟ ଅଛି, ତେଣୁ `next build` ଏକ ମୂଳ ପ୍ରକ୍ରିୟା **ଏବଂ** ଏକ worker ପ୍ରକ୍ରିୟା ଚଲାଏ ଏବଂ ପ୍ରତ୍ୟେକଟି ପୃଥକ ଭାବରେ `OMNIROUTE_BUILD_MEMORY_MB`କୁ ସମ୍ମାନ କରେ। କଣ୍ଟେନର୍ ସୀମାକୁ ସେହି ମୂଲ୍ୟର ପ୍ରାୟ ଦୁଇଗୁଣାଠାରୁ ଅଧିକ ରଖନ୍ତୁ, କେବଳ ଥରେ ନୁହେଁ।

ଏହି ଟ୍ରିରେ ମାପ କରାଯାଇଛି (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ବଣ୍ଡଲର୍   | କଣ୍ଟେନର୍ ସୀମା  | ଫଳାଫଳ                                   |
| --------- | -------------- | --------------------------------------- |
| Turbopack | 8 GiB / 16 GiB | ଉଭୟରେ ନିରବରେ OOM-killed ହୋଇଛି           |
| webpack   | 8 GiB          | build worker SIGKILLed ହୋଇଛି            |
| webpack   | 12 GiB         | ସଫଳ ହୋଇଛି, ସର୍ବାଧିକ 11.1 GiBରେ ପହଞ୍ଚିଛି |

### ରନ୍ଟାଇମ୍ ଡିଫଲ୍ଟଗୁଡ଼ିକ

`runner-base` ଦ୍ୱାରା ଏକ୍ସପୋର୍ଟ୍ କରାଯାଇଥିବା ଡିଫଲ୍ଟଗୁଡ଼ିକ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`।

Dockerରେ ମେମୋରି ଆଚରଣ:

- ଇମେଜ୍ଟି `OMNIROUTE_MEMORY_MB=1024` ସେଟ୍ କରେ ଏବଂ ଏଥିରୁ `NODE_OPTIONS=--max-old-space-size=1024` ନିର୍ଦ୍ଧାରଣ କରେ।
- ପ୍ରକୃତ ସର୍ଭର ପ୍ରକ୍ରିୟାଟି standalone launcher ଦ୍ୱାରା ଆରମ୍ଭ ହୁଏ, ଯାହା `OMNIROUTE_MEMORY_MB` ପଢ଼େ ଏବଂ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ଯୋଡ଼େ।
- Node ପୁନରାବୃତ୍ତ `--max-old-space-size` ମୂଲ୍ୟଗୁଡ଼ିକ ମଧ୍ୟରୁ ଶେଷ ମୂଲ୍ୟଟି ବ୍ୟବହାର କରେ, ତେଣୁ `OMNIROUTE_MEMORY_MB` ସେଟ୍ କରିବା ଦ୍ୱାରା କାର୍ଯ୍ୟକାରୀ Docker heap ସୀମା ନିୟନ୍ତ୍ରିତ ହୁଏ।
- ଇମେଜ୍ଟି ଏହାକୁ ସର୍ବଦା ସେଟ୍ କରୁଥିବାରୁ, Docker ଅଧୀନରେ launcher-ର ନିଜସ୍ୱ RAM-ଅନୁକୂଳିତ fallback କେବେ ଲାଗୁ ହୁଏନାହିଁ। କାର୍ଯ୍ୟଭାର ପାଇଁ ଏହାକୁ ସ୍ପଷ୍ଟ ଭାବରେ ବଢ଼ାନ୍ତୁ (ତଳେ ଥିବା ସାରଣୀ)। coding-agent `/v1/responses` ପାଇଁ `2048` ଏବେ ମଧ୍ୟ ଅତ୍ୟନ୍ତ କମ୍।

### coding agent-ମାନଙ୍କ ପାଇଁ runtime RAM

1 GiB Docker ଡିଫଲ୍ଟ ହେଉଛି dashboard/ହାଲୁକା chat ପାଇଁ ସର୍ବନିମ୍ନ ସୀମା, production ଆକାର ନୁହେଁ। ଦୀର୍ଘ `POST /v1/responses` body-ଗୁଡ଼ିକ (ଶତାଧିକ message, ଦଶ-ଦଶଟି tool) compression ସମୟରେ ଏକାଧିକ in-memory graph ଧରି ରଖନ୍ତି। ପରସ୍ପରକୁ overlap କରୁଥିବା ପ୍ରାୟ ~3 MiB / ~750k-token ର ଦୁଇଟି request **12 GiB** old-space-ରେ V8 କୁ ବନ୍ଦ କରିଦେଇଛି (`FATAL ERROR: Reached heap limit`) ଏବଂ 16 GiB cgroup OOM ମଧ୍ୟ ସୃଷ୍ଟି କରିଛି। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ଦେଖନ୍ତୁ।

**heap ଠାରୁ ଅଧିକ cgroup `--memory` ଆକାର ନିର୍ଦ୍ଧାରଣ କରନ୍ତୁ** — native buffer, SQLite ଏବଂ compression intermediate-ଗୁଡ଼ିକ V8 ବାହାରେ ରହେ।

| କାର୍ଯ୍ୟଭାର                             | `OMNIROUTE_MEMORY_MB`         | Container / cgroup          | ଟିପ୍ପଣୀ                                                                                                          |
| -------------------------------------- | ----------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Dashboard, ଗୋଟିଏ ହାଲୁକା chat           | `1024` (ଇମେଜ୍ ଡିଫଲ୍ଟ)         | ≥2 GiB                      |                                                                                                                  |
| ଗୋଟିଏ coding agent (Claude/Codex/Grok) | `8192`                        | ≥10 GiB                     | ସାଧାରଣ single-session `/v1/responses`                                                                            |
| ଦୁଇଟି ସମକାଳୀନ ଦୀର୍ଘ `/v1/responses`    | `10240`–`12288`               | ≥12–16 GiB                  | ~12 GiB heap-ରେ V8 ବନ୍ଦ ହେବା ମାପ କରାଯାଇଛି                                                                        |
| ତିନି କିମ୍ବା ଅଧିକ ସମକାଳୀନ ଦୀର୍ଘ context | ଗୋଟିଏ process-ରେ କରନ୍ତୁ ନାହିଁ | serialize କରନ୍ତୁ / ଅଧିକ RAM | ଡିଫଲ୍ଟ heavyweight admission ହେଉଛି 1 in-flight; RAM ବଢ଼ାଇବା ବିନା ଏହାକୁ ବଢ଼ାଇଲେ ପୁଣି ବନ୍ଦ ହେବାର ସମସ୍ୟା ସୃଷ୍ଟି ହୁଏ |

bare metal-ରେ `omniroute serve`, `OMNIROUTE_MEMORY_MB` **ସେଟ୍ ହୋଇନଥିବା** ସମୟରେ RAM-ର ପ୍ରାୟ ~35% ଅନୁକୂଳନ କରେ (`[512, 4096]` ମଧ୍ୟରେ ସୀମିତ)। Docker ସର୍ବଦା `1024` ସେଟ୍ କରେ, ତେଣୁ official image-ରେ ସେହି ଅନୁକୂଳନ କେବେ ଚାଲେନାହିଁ।

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ଉପପଥରେ Reverse Proxy (Traefik / nginx)

Next.js `basePath` standalone bundle ମଧ୍ୟରେ କମ୍ପାଇଲ୍ ହୋଇଥାଏ। OmniRoute ଆପ୍ ରୁଟ୍ରେ ଥିବା ଏକ sentinel ଫାଇଲ୍ରେ ଅନ୍ତର୍ନିହିତ
ମୂଲ୍ୟକୁ ରେକର୍ଡ କରେ (`npm run build` ସମୟରେ ଲେଖାଯାଏ; `scripts/docker/ensure-docker-base-path.mjs` ଦ୍ୱାରା
ପଢ଼ାଯାଏ) ଏବଂ କଣ୍ଟେନର୍ ଆରମ୍ଭ ହେବାବେଳେ ଏହାକୁ
`OMNIROUTE_BASE_PATH` ସହିତ ତୁଳନା କରେ। ସେଗୁଡ଼ିକ ଭିନ୍ନ ହେଲେ ଏବଂ imageଟି
ଡୋମେନ୍ ରୁଟ୍ ପାଇଁ build ହୋଇଥିଲେ, entrypoint standalone manifests,
ଅନ୍ତର୍ନିହିତ `basePath`/`assetPrefix` literals (Next 16 କେବଳ
`assetPrefix`ରୁ SSR asset URLଗୁଡ଼ିକୁ render କରେ — patcher ଉପପଥଟିକୁ ଏଥିରେ ମଧ୍ୟ ପ୍ରତିଫଳିତ କରେ),
ଅନ୍ତର୍ନିହିତ `/_next/static` asset URLଗୁଡ଼ିକ (client-reference manifests, media imports, prerendered
error pages) ଏବଂ client `process.env` shimକୁ ପୁନଃଲେଖନ କରେ, ତା’ପରେ `node dev/run-standalone.mjs`
ଚାଲେ।

### Compose build (ସୁପାରିଶକୃତ)

`.env`ରେ ଉଭୟ variable ସେଟ୍ କରନ୍ତୁ, ତା’ପରେ image ଏବଂ runtime ମେଳ ଖାଇବା ପାଇଁ ପୁନଃ build କରନ୍ତୁ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH`କୁ Docker build-arg ଏବଂ
runtime environment variable ଭାବରେ ପଠାଏ।

### ପୂର୍ବରୁ build ହୋଇଥିବା root image + runtime ଉପପଥ

ପ୍ରକାଶିତ `diegosouzapw/omniroute:*` imageଗୁଡ଼ିକ ଡୋମେନ୍ ରୁଟ୍ ପାଇଁ build ହୋଇଛି। ତଥାପି ଆପଣ
runtimeରେ `OMNIROUTE_BASE_PATH` ସେଟ୍ କରିପାରିବେ; କଣ୍ଟେନର୍ startup ସମୟରେ bundleକୁ ଥରେ patch କରେ।
ଏହା ସହିତ ମେଳ ଖାଉଥିବା public originକୁ ଯୋଡ଼ନ୍ତୁ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

**ସମ୍ପୂର୍ଣ୍ଣ** ବାହ୍ୟ pathକୁ forward କରିବା ପାଇଁ reverse proxyକୁ configure କରନ୍ତୁ (prefixକୁ
ହଟାନ୍ତୁ ନାହିଁ)। Traefik, `StripPrefix` ବିନା `PathPrefix(`/omniroute`)`କୁ କଣ୍ଟେନର୍କୁ
route କରିବା ଉଚିତ୍, ଯାହାଦ୍ୱାରା Next.js `/omniroute/...` ଗ୍ରହଣ କରିବ ଏବଂ
`/omniroute/_next/...`ରୁ assets ପରିବେଷଣ କରିବ।

Docker healthcheck, ସକ୍ରିୟ `OMNIROUTE_BASE_PATH` prefix ଥିବା ହାଲୁକା
`/healthz` lifecycle endpointକୁ probe କରେ। ମାନବ/dashboard diagnostics ପାଇଁ
`/api/monitoring/health` ଉପଲବ୍ଧ ରହେ; କଣ୍ଟେନର୍ HEALTHCHECKକୁ ପୁଣି ସେହି pathକୁ ନିର୍ଦ୍ଦେଶ କରିବାକୁ
(ଉଦାହରଣ ସ୍ୱରୂପ deep health enforcement ପାଇଁ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health`
ସେଟ୍ କରନ୍ତୁ। ସେହି path ଏକ **ଗଭୀର** ଯାଞ୍ଚ (DB + monitoring summary) — ଆପଣ ପୁଣି ଏହାକୁ ସକ୍ରିୟ କଲେ
Dockerର ବିରଳ `HEALTHCHECK` ପାଇଁ ଉପଯୁକ୍ତ, କିନ୍ତୁ Kubernetes `livenessProbe`
intervals ପାଇଁ **ନୁହେଁ**।

orchestratorଗୁଡ଼ିକ ପାଇଁ (Kubernetes, Nomad, ଇତ୍ୟାଦି):

| Probe           | ପସନ୍ଦ କରନ୍ତୁ                                                         | ଏଡ଼ାନ୍ତୁ                                                |
| --------------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| Liveness        | HTTP `GET /livez`, କିମ୍ବା ମୁଖ୍ୟ portରେ TCP (`PORT`, default `20128`) | liveness ଭାବରେ `/api/monitoring/health`                 |
| Readiness       | HTTP `GET /healthz`                                                  | event-loop ବ୍ୟସ୍ତ ଥିବାକୁ ବନ୍ଦ ଭାବେ ଧରୁଥିବା କଠୋର timeout |
| Deep / blackbox | `/api/monitoring/health`                                             | —                                                       |

`/healthz` process lifecycle (`ok` / `starting` / `stopping`) ରିପୋର୍ଟ କରେ। `/livez` କେବଳ
processଟି ସଚଳ ଅଛି କି ନାହିଁ ଜଣାଏ (handler ଚାଲିପାରିଲେ ସର୍ବଦା 200; ଏହା
readiness ପାଇଁ ଅପେକ୍ଷା କରେ ନାହିଁ)। ଉଭୟ ଏବେ ମଧ୍ୟ request handling ସହିତ ସମାନ Node event loopରେ
ଚାଲେ, ତେଣୁ CPU-bound catalog କିମ୍ବା compression କାର୍ଯ୍ୟ ସେଗୁଡ଼ିକୁ ବିଳମ୍ବିତ କରିପାରେ — ବ୍ୟସ୍ତ ≠ ବନ୍ଦ।
HTTP probeଗୁଡ଼ିକ time out ହେଲେ TCP livenessକୁ ପସନ୍ଦ କରନ୍ତୁ। ସମ୍ପୂର୍ଣ୍ଣ probe ମାର୍ଗଦର୍ଶନ:
[Monitoring ମାର୍ଗଦର୍ଶିକା — Kubernetes probe ସୁପାରିଶଗୁଡ଼ିକ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Caddy ସହିତ Docker Compose (HTTPS Auto-TLS)

Caddyର ସ୍ୱୟଂଚାଳିତ SSL ବ୍ୟବସ୍ଥା ବ୍ୟବହାର କରି OmniRouteକୁ ସୁରକ୍ଷିତ ଭାବରେ ପ୍ରକାଶ କରାଯାଇପାରେ। ଆପଣଙ୍କ ଡୋମେନ୍ର DNS A ରେକର୍ଡ ଆପଣଙ୍କ ସର୍ଭର୍ର IPକୁ ସୂଚିତ କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth କଲ୍ବ୍ୟାକ୍, ଡ୍ୟାସ୍ବୋର୍ଡ ଲିଙ୍କ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା ସାର୍ବଜନୀନ URLଗୁଡ଼ିକ ପାଇଁ ବ୍ରାଉଜର୍ମୁଖୀ ଉତ୍ସ।
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ନିର୍ଦ୍ଧାରିତ କାର୍ଯ୍ୟ / ସ୍ୱୟଂ-ଫେଚ୍ ପାଇଁ ଆଭ୍ୟନ୍ତରୀଣ ସର୍ଭର୍ରୁ-ସର୍ଭର୍ URL।
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy ଅପ୍ଷ୍ଟ୍ରିମ୍ କଣ୍ଟେନର୍ ପାଇଁ ମାନକ ଫରୱାର୍ଡିଂ ହେଡର୍ଗୁଡ଼ିକ ସେଟ୍ କରେ। OAuth କଲ୍ବ୍ୟାକ୍ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା ସାର୍ବଜନୀନ ଲିଙ୍କଗୁଡ଼ିକ ପାଇଁ OmniRoute

ସୁରକ୍ଷା ବ୍ୟବହାର କରେ। କେବଳ ଉନ୍ନତ ଡିପ୍ଲୟମେଣ୍ଟଗୁଡ଼ିକ ପାଇଁ `OMNIROUTE_TRUST_PROXY` ସକ୍ଷମ କରନ୍ତୁ, ଯେଉଁଠାରେ ଆପଣ ସ୍ପଷ୍ଟ
ବିନ୍ୟାସ ପରିବର୍ତ୍ତେ ବିଶ୍ୱସ୍ତ ଫରୱାର୍ଡ ହେଡର୍ଗୁଡ଼ିକରୁ ସାର୍ବଜନୀନ ଉତ୍ସ ନିର୍ଣ୍ଣୟ କରିବାକୁ OmniRouteକୁ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବରେ ଚାହାନ୍ତି।

## Cloudflare Quick Tunnel

Docker ଡିପ୍ଲୟମେଣ୍ଟଗୁଡ଼ିକ ପାଇଁ ଡ୍ୟାସ୍ବୋର୍ଡ ସମର୍ଥନରେ `Dashboard → Endpoints`ରେ ଏକ-କ୍ଲିକ୍ **Cloudflare Quick Tunnel** ଅନ୍ତର୍ଭୁକ୍ତ ଅଛି। ପ୍ରଥମ ଥର ସକ୍ଷମ କଲେ, କେବଳ ଆବଶ୍ୟକ ସମୟରେ `cloudflared` ଡାଉନ୍ଲୋଡ୍ ହୁଏ, ଆପଣଙ୍କ ବର୍ତ୍ତମାନର `/v1` ଏଣ୍ଡପଏଣ୍ଟକୁ ଏକ ଅସ୍ଥାୟୀ ଟନେଲ୍ ଆରମ୍ଭ ହୁଏ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା `https://*.trycloudflare.com/v1` URL ଆପଣଙ୍କ ସାଧାରଣ ସାର୍ବଜନୀନ URLର ଠିକ୍ ତଳେ ଦେଖାଯାଏ।

ସକ୍ରିୟ ଟନେଲ୍ର ସ୍ଥିତି ପରିବର୍ତ୍ତନ ନକରି `Settings → Appearance`ରୁ ଏଣ୍ଡପଏଣ୍ଟ ଟନେଲ୍ ପ୍ୟାନେଲ୍ଗୁଡ଼ିକ (Cloudflare, Tailscale, ngrok) ଦେଖାଯାଇପାରେ କିମ୍ବା ଲୁଚାଯାଇପାରେ।

### ଟନେଲ୍ ସମ୍ବନ୍ଧୀୟ ଟିପ୍ପଣୀ

- Quick Tunnel URLଗୁଡ଼ିକ ଅସ୍ଥାୟୀ ଏବଂ ପ୍ରତ୍ୟେକ ପୁନଃଚାଳନ ପରେ ପରିବର୍ତ୍ତିତ ହୁଏ।
- OmniRoute କିମ୍ବା କଣ୍ଟେନର୍ ପୁନଃଚାଳନ ପରେ Quick Tunnelଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନଃସ୍ଥାପିତ ହୁଏ ନାହିଁ। ଆବଶ୍ୟକ ହେଲେ ଡ୍ୟାସ୍ବୋର୍ଡରୁ ସେଗୁଡ଼ିକୁ ପୁନଃସକ୍ଷମ କରନ୍ତୁ।
- ପରିଚାଳିତ ଇନ୍ଷ୍ଟଲ୍ ବର୍ତ୍ତମାନ `x64` / `arm64`ରେ Linux, macOS ଏବଂ Windowsକୁ ସମର୍ଥନ କରେ।
- ସୀମିତ କଣ୍ଟେନର୍ ପରିବେଶଗୁଡ଼ିକରେ କୋଳାହଳପୂର୍ଣ୍ଣ QUIC UDP ବଫର୍ ଚେତାବନୀ ଏଡ଼ାଇବାକୁ ପରିଚାଳିତ Quick Tunnelଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବରେ HTTP/2 ପରିବହନ ବ୍ୟବହାର କରନ୍ତି। ଆପଣ ଏକ ଭିନ୍ନ ପରିବହନ ଚାହୁଁଥିଲେ `CLOUDFLARED_PROTOCOL=quic` କିମ୍ବା `auto` ସେଟ୍ କରନ୍ତୁ।
- Docker ଇମେଜ୍ଗୁଡ଼ିକ ସିଷ୍ଟମ୍ CA ରୁଟ୍ଗୁଡ଼ିକୁ ବଣ୍ଡଲ୍ କରି ପରିଚାଳିତ `cloudflared`କୁ ପ୍ରଦାନ କରେ, ଯାହା କଣ୍ଟେନର୍ ଭିତରେ ଟନେଲ୍ ବୁଟ୍ଷ୍ଟ୍ରାପ୍ ହେବା ସମୟରେ TLS ବିଶ୍ୱାସ ବିଫଳତାକୁ ଏଡ଼ାଇଥାଏ।
- OmniRoute ଡାଉନ୍ଲୋଡ୍ କରିବା ପରିବର୍ତ୍ତେ ଏକ ବିଦ୍ୟମାନ ବାଇନାରି ବ୍ୟବହାର କରୁ ବୋଲି ଚାହୁଁଥିଲେ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ସେଟ୍ କରନ୍ତୁ।

#### ୱେବ୍-ସେସନ୍ ପ୍ରଦାନକାରୀ: `-web` ଇମେଜ୍ଗୁଡ଼ିକ

ଉପରୋକ୍ତ ପ୍ରତ୍ୟେକ ଚ୍ୟାନେଲ୍ ଏକ `-web` ଟ୍ୟାଗ୍ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ଭାବରେ ମଧ୍ୟ ଉପଲବ୍ଧ, ଯାହା `runner-web` ଷ୍ଟେଜ୍ରୁ ନିର୍ମିତ — Playwright ଏବଂ ଏକ Chromium ବ୍ରାଉଜର୍ ସହିତ ସମାନ ଇମେଜ୍। ସାଧାରଣ ଇମେଜ୍ Chromium **ବିନା** ପ୍ରଦାନ କରାଯାଏ; `gemini-web`, `claude-web` ଏବଂ `claude-turnstile` ପାଇଁ ଏହା ଆବଶ୍ୟକ।

ବିଫଳତା ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ ନୁହେଁ, ପରେ ଘଟେ: ସେହି ପ୍ରଦାନକାରୀମାନେ ସେମାନଙ୍କ ମଡେଲ୍ଗୁଡ଼ିକୁ ତାଲିକାଭୁକ୍ତ କରନ୍ତି ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡରେ ସଂଯୁକ୍ତ ଭାବେ ଦେଖାଯାନ୍ତି, ଏବଂ କେବଳ ପ୍ରଥମ ଅନୁରୋଧ ଏହି ସନ୍ଦେଶ ସହିତ ବିଫଳ ହୁଏ

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ଆପଣ ସେହି ପ୍ରଦାନକାରୀମାନଙ୍କୁ ବ୍ୟବହାର କରୁଥିଲେ, ଆପଣ ବର୍ତ୍ତମାନ ବ୍ୟବହାର କରୁଥିବା ଚ୍ୟାନେଲ୍ର `-web` ଟ୍ୟାଗ୍ ପୁଲ୍ କରନ୍ତୁ — ଅନ୍ୟ କିଛି ପରିବର୍ତ୍ତନ ହୁଏ ନାହିଁ। ଏକ npm/CLI ଇନ୍ଷ୍ଟଲ୍ରେ (Docker ଇମେଜ୍ ବିନା), ସମତୁଲ୍ୟ ଅନୁପସ୍ଥିତ ଅଂଶ ହେଉଛି ବ୍ରାଉଜର୍ ବାଇନାରି: ହୋଷ୍ଟରେ `npx playwright install chromium` ଚଲାନ୍ତୁ।

#### ପ୍ରି-ରିଲିଜ୍ ଚ୍ୟାନେଲ୍ର ବ୍ୟବହାର

`next` ଚ୍ୟାନେଲ୍ଟି ବର୍ତ୍ତମାନର ଡିଫଲ୍ଟ `release/v*` ବ୍ରାଞ୍ଚକୁ ପ୍ରତ୍ୟେକ push ସମୟରେ ପୁନଃନିର୍ମାଣ କରାଯାଏ ଏବଂ AMD64 ଓ ARM64 ଉଭୟ ପାଇଁ ପ୍ରକାଶିତ ହୁଏ। ପୁରୁଣା maintenance ବ୍ରାଞ୍ଚଗୁଡ଼ିକ ଏହାକୁ overwrite କରିପାରିବେ ନାହିଁ। ପରବର୍ତ୍ତୀ stable tag ସୃଷ୍ଟି ହେବା ପୂର୍ବରୁ ସକ୍ରିୟ release ବ୍ରାଞ୍ଚରେ merge ହୋଇଥିବା ସଂଶୋଧନଗୁଡ଼ିକ ପାଇଁ ଏହି ଚ୍ୟାନେଲ୍ ଗୋଟିଏ pull କରାଯୋଗ୍ୟ image ପ୍ରଦାନ କରେ।

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ପାଇଁ, ଚୟନିତ profile ଦ୍ୱାରା ବ୍ୟବହୃତ image tagକୁ override କରନ୍ତୁ, ତା’ପରେ serviceକୁ pull କରି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ସୁରକ୍ଷା ଏବଂ rollback

`next` ହେଉଛି ଏକ ପରିବର୍ତ୍ତନଶୀଳ pre-release ଚ୍ୟାନେଲ୍। ସକ୍ରିୟ release ବ୍ରାଞ୍ଚକୁ ହେଉଥିବା ଯେକୌଣସି pushରେ ଏହା ପରିବର୍ତ୍ତିତ ହୋଇପାରେ ଏବଂ ଏହା **production ବ୍ୟବହାର ପାଇଁ ସମର୍ଥିତ ନୁହେଁ**। ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ buildର ମୂଲ୍ୟାୟନ କରୁଥିବାବେଳେ image digestକୁ pin କରନ୍ତୁ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ପରୀକ୍ଷା କରିବା ପୂର୍ବରୁ OmniRoute data volume କିମ୍ବା bind-mounted data directoryର backup ନିଅନ୍ତୁ। rollback କରିବା ପାଇଁ, ପୂର୍ବରୁ ବ୍ୟବହୃତ stable version କିମ୍ବା digestକୁ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ ଏବଂ containerକୁ ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

ଏକ release-branch build କେବେବି `latest`କୁ ଆଗକୁ ବଢ଼ାଇପାରିବ ନାହିଁ; କେବଳ ଏକ ଯୋଗ୍ୟ stable semantic version ହିଁ stable pointerକୁ promote କରିପାରିବ। `next` imagesରେ release image inspection ଏବଂ CRITICAL vulnerabilityକୁ ଅବରୋଧ କରୁଥିବା gate ବଜାୟ ରହେ।

**`latest`, git ପାଇଁ ସଦ୍ୟତାର କୌଣସି ନିଶ୍ଚିତତା ନୁହେଁ।** `main` କିମ୍ବା ସକ୍ରିୟ `release/v*` ବ୍ରାଞ୍ଚରେ merge ହୋଇଥିବା ସଂଶୋଧନଗୁଡ଼ିକ ଏକ stable SemVer image ପ୍ରକାଶିତ ହୋଇ publish job ଦ୍ୱାରା `:latest` promote ନହେବା ପର୍ଯ୍ୟନ୍ତ `:latest`ରେ ରହିବେ **ନାହିଁ** (ସେହି SemVer ସହ ସମାନ digest)। GitHubରେ ସଂଶୋଧନଟି ପୂର୍ବରୁ ଦେଖାଯାଉଥିବା ସତ୍ତ୍ୱେ `latest` ସ୍ଥିର ଥିବା ପରି ଦେଖାଗଲେ, release ବ୍ରାଞ୍ଚକୁ ପରୀକ୍ଷା କରିବା ପାଇଁ `:next` pull କରନ୍ତୁ କିମ୍ବା SemVer tag ପାଇଁ ଅପେକ୍ଷା କରନ୍ତୁ।

| ଆପଣ ଯାହା ଚାହୁଁଛନ୍ତି                                                                 | ବ୍ୟବହାର କରନ୍ତୁ                                |
| ----------------------------------------------------------------------------------- | --------------------------------------------- |
| ବିଚ୍ୟୁତ ହେବା ଅନୁଚିତ ଥିବା GitOps / production                                        | `:X.Y.Z`କୁ pin କରନ୍ତୁ (କିମ୍ବା image digestକୁ) |
| ପ୍ରକାଶିତ stableଗୁଡ଼ିକୁ ଅନୁସରଣ କରିବା ଏବଂ ପ୍ରତ୍ୟେକ releaseରେ ପୁନଃସୃଷ୍ଟିକୁ ଗ୍ରହଣ କରିବା | `:latest`                                     |
| ଅପ୍ରକାଶିତ `release/v*` commitଗୁଡ଼ିକୁ ପରୀକ୍ଷା କରିବା                                  | `:next` (production ନୁହେଁ)                    |
| `main`କୁ ପରୀକ୍ଷା କରିବା                                                              | `:main` (production ନୁହେଁ)                    |

## Dockerରେ ଡ୍ୟାସବୋର୍ଡ ଅପଡେଟ୍

ଏକ ପ୍ରକାଶିତ-ଇମେଜ୍ କଣ୍ଟେନର୍ ନିଜକୁ ନିଜେ ପ୍ରତିସ୍ଥାପନ କରିପାରେ ନାହିଁ। OmniRoute ଯେତେବେଳେ ଚିହ୍ନଟ କରେ ଯେ ଏହା ଏକ
କଣ୍ଟେନର୍ ଭିତରେ ଚାଲୁଛି (`.git` checkout ନାହିଁ, npm install ନୁହେଁ), ସେତେବେଳେ ହୋମ୍ ଡ୍ୟାସବୋର୍ଡର ଅପଡେଟ୍ ବ୍ୟାନର୍ npm/git ନିର୍ଦ୍ଦେଶ ବଦଳରେ
ଚଲାଇବାକୁ ଥିବା ହୋଷ୍ଟ କମାଣ୍ଡକୁ ଏକ କପି ବଟନ୍ ସହ ଦେଖାଏ:

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

ସେବାର ନାମ `AUTO_UPDATE_SERVICE`ରୁ ଆସେ (ଡିଫଲ୍ଟ `omniroute`, ଯାହା
`docker-compose.selfhost.yml`ରେ ଥିବା ସେବା)। `pull` କେବଳ ଏକ ପରିବର୍ତ୍ତନଶୀଳ ଟ୍ୟାଗ୍କୁ (`latest`, `next`) ଆଗକୁ ନେଇଥାଏ; ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ
`:X.Y.Z` ଟ୍ୟାଗ୍ ଥିଲେ, ପ୍ରଥମେ ଟ୍ୟାଗ୍ଟି ସମ୍ପାଦନ କରନ୍ତୁ।

### ଏକ ହୋଷ୍ଟ ଟ୍ରିଗର୍ ଫାଇଲ୍ ସହ ଏକ-କ୍ଲିକ୍ ଅପଡେଟ୍

`/var/run/docker.sock` ମାଉଣ୍ଟ୍ ନକରି **Update Now**କୁ କାର୍ଯ୍ୟକ୍ଷମ ରଖିବା ପାଇଁ (ଏହା କଣ୍ଟେନର୍କୁ
ହୋଷ୍ଟରେ root ଅଧିକାର ଦିଏ — ଉପରେ ଥିବା `cli` ପ୍ରୋଫାଇଲ୍ ଚେତାବନୀ ଦେଖନ୍ତୁ), OmniRoute ସେବାରେ `DOCKER_UPDATE_TRIGGER_FILE` ସେଟ୍ କରନ୍ତୁ
ଏବଂ ହୋଷ୍ଟରେ ଏକ ୱାଚର୍ ଚଲାନ୍ତୁ:

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

ପଥଟି `DATA_DIR` ଭିତରେ ଥିବା ଆବଶ୍ୟକ (ଆପେକ୍ଷିକ ମୂଲ୍ୟଗୁଡ଼ିକ ଏହାକୁ ଆଧାର କରି ସମାଧାନ ହୁଏ); ଅନ୍ୟ ଯେକୌଣସି ପଥ
ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ। ତା’ପରେ **Update Now** ସେହି ଫାଇଲ୍ରେ `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }` ଲେଖେ,
`202` ଉତ୍ତର ଦିଏ, ଏବଂ ନୂତନ ସଂସ୍କରଣ ସକ୍ରିୟ ହୋଇ ପୁନଃଲୋଡ୍ ହେବା ପର୍ଯ୍ୟନ୍ତ ଡ୍ୟାସବୋର୍ଡ `/api/system/version`କୁ ପୋଲ୍ କରେ।
ଏହି ମୋଡ୍ରେ OmniRoute କେବେ ମଧ୍ୟ କୌଣସି shell କିମ୍ବା Docker କମାଣ୍ଡ ଚଲାଏ ନାହିଁ। ପ୍ରତ୍ୟେକ ଅପଡେଟ୍
କାର୍ଯ୍ୟ ପରି, ଅନୁରୋଧଟି କେବଳ loopback/LAN କ୍ଲାଏଣ୍ଟ୍ମାନଙ୍କଠାରୁ ଗ୍ରହଣ କରାଯାଏ।

ଏକ bind-mounted ଡାଟା ଡିରେକ୍ଟୋରୀ ହୋଷ୍ଟକୁ ନିରୀକ୍ଷଣ କରିବା ପାଇଁ ଏକ ସ୍ଥିର ପଥ ଦିଏ। ନମୁନା `systemd` ୟୁନିଟ୍ଗୁଡ଼ିକ
(`/srv/omniroute`କୁ ଆପଣଙ୍କ compose ଫାଇଲ୍ ଏବଂ `data/` ଥିବା ଡିରେକ୍ଟୋରୀ ଅନୁଯାୟୀ ସମନ୍ୱୟ କରନ୍ତୁ):

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=OmniRoute ଡ୍ୟାସବୋର୍ଡ ଅପଡେଟ୍ ଅନୁରୋଧଗୁଡ଼ିକୁ ନିରୀକ୍ଷଣ କରନ୍ତୁ

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=OmniRoute କଣ୍ଟେନର୍କୁ pull କରି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

ସେବାଟି pull କରିବା ପୂର୍ବରୁ ଅନୁରୋଧକୁ ହଟାଏ, ଯାହାଦ୍ୱାରା ଏକ ବିଫଳ ରନ୍ ପୁନରାବୃତ୍ତି ହୁଏ ନାହିଁ।
`DOCKER_UPDATE_TRIGGER_FILE` ନଥିଲେ ଡ୍ୟାସବୋର୍ଡ ମାନୁଆଲ୍ କମାଣ୍ଡ ପ୍ରବାହକୁ ବଜାୟ ରଖେ।

## ଉପଲବ୍ଧତା: ଡିଫଲ୍ଟ SQLite ହେଉଛି single-replica

ମାନକ Docker / Kubernetes OmniRoute ହେଉଛି **ଗୋଟିଏ Node ପ୍ରକ୍ରିୟା + ଗୋଟିଏ SQLite writer**। ଏହି topologyରେ high availability **ସମର୍ଥିତ ନୁହେଁ**।

| ସୀମାବଦ୍ଧତା                                | ପରିଣାମ                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ଏକକ writer                                | ସମାନ SQLite ଫାଇଲ୍ ପାଇଁ ଏକାଧିକ replica **ଚଲାନ୍ତୁ ନାହିଁ**। ଏହା DBକୁ କ୍ଷତିଗ୍ରସ୍ତ କରେ।                                                                                                                                                                                                                                                         |
| ପୁନଃସୃଷ୍ଟି / ପୁନଃଆରମ୍ଭ / HEALTHCHECK kill | ଚାଲୁଥିବା SSE, ଡ୍ୟାସବୋର୍ଡ session ଏବଂ in-memory stateର **ସମ୍ପୂର୍ଣ୍ଣ ବିଭ୍ରାଟ**। ପ୍ରତ୍ୟେକ ସଂଯୁକ୍ତ କ୍ଲାଏଣ୍ଟ୍ର ସଂଯୋଗ ବିଚ୍ଛିନ୍ନ ହୁଏ। endpoint ଖାଲି ଥିବା ସମୟରେ ଆସୁଥିବା ନୂତନ ଅନୁରୋଧଗୁଡ଼ିକ OmniRoute JSON ବଦଳରେ reverse-proxy **`502 Bad Gateway: Unknown error`** ପାଆନ୍ତି — କ୍ଲାଏଣ୍ଟ୍ମାନେ ଏହାକୁ provider ବିଫଳତାରୁ ପୃଥକ୍ କରିପାରନ୍ତି ନାହିଁ (#11015)। |
| `/healthz` ସହ ସମାନ event loop             | ଏକ ବ୍ୟସ୍ତ catalog କିମ୍ବା compression tick probeଗୁଡ଼ିକୁ ବିଳମ୍ବ କରିପାରେ; ତା’ପରେ ଏକ ଛୋଟ timeout **ଏକମାତ୍ର** replicaକୁ ପୁନଃଆରମ୍ଭ କରେ।                                                                                                                                                                                                          |

**Probe matrix** ([Kubernetes probe ସୁପାରିସଗୁଡ଼ିକ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ମଧ୍ୟ ଦେଖନ୍ତୁ):

| Probe       | ଲକ୍ଷ୍ୟ                                                     | ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ                                    |
| ----------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| Liveness    | `PORT`ରେ TCP (ଡିଫଲ୍ଟ `20128`), କିମ୍ବା soft HTTP `/healthz` | `/api/monitoring/health`                                |
| Readiness   | HTTP `GET /healthz`                                        | event-loop ବ୍ୟସ୍ତ ଥିବାକୁ dead ବୋଲି ଧରୁଥିବା କଠୋର timeout |
| Deep / ମଣିଷ | `/api/monitoring/health`                                   | ସ୍ୱୟଂଚାଳିତ kubelet liveness                             |

**ଅପଗ୍ରେଡ୍:** ପ୍ରତ୍ୟେକ session ବିଚ୍ଛିନ୍ନ ହେବ ବୋଲି ଆଶା କରନ୍ତୁ। ସମ୍ଭବ ହେଲେ କ୍ଲାଏଣ୍ଟ୍ମାନଙ୍କୁ drain କରନ୍ତୁ; ଡିଫଲ୍ଟ SQLiteରେ rolling update ନାହିଁ। Compose `restart: unless-stopped` ସହ Docker `HEALTHCHECK` ମଧ୍ୟ କଣ୍ଟେନର୍ Unhealthy ହେଲେ ଏକମାତ୍ର ପ୍ରକ୍ରିୟାକୁ ପ୍ରତିସ୍ଥାପନ କରିବ — ସମାନ ପ୍ରଭାବ କ୍ଷେତ୍ର।

ଏକ **single replica** ପାଇଁ Kubernetes ସ୍ନିପେଟ୍ (Recreate ଆବଶ୍ୟକ; ଗୋଟିଏ SQLite ଫାଇଲ୍ ପାଇଁ `replicas` ବଢ଼ାନ୍ତୁ ନାହିଁ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` sleep ଫଳରେ SIGTERM ପୂର୍ବରୁ kube Service endpointଗୁଡ଼ିକୁ ବାଦ ଦେଇପାରେ, ଯାହାଦ୍ୱାରା **ନୂତନ** traffic ବନ୍ଦ ହେଉଥିବା processକୁ ଆସିବା ବନ୍ଦ କରେ। ଚାଲୁଥିବା `/v1/responses` SSEକୁ heavyweight admission leaseଗୁଡ଼ିକ (#11015) ମାଧ୍ୟମରେ `SHUTDOWN_TIMEOUT_MS` (ଡିଫଲ୍ଟ 30s) ପର୍ଯ୍ୟନ୍ତ ସମୟ ଦେଇ ସମାପ୍ତ କରାଯାଏ। ତଥାପି process ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚୁଥିବା ନୂତନ requestଗୁଡ଼ିକ `503` + `Retry-After: 5` ପାଆନ୍ତି। ପ୍ରତିସ୍ଥାପନ Ready ହେବା ପର୍ଯ୍ୟନ୍ତ Recreateର ଖାଲି-endpoint ବ୍ୟବଧାନ ଏକ ସମ୍ପୂର୍ଣ୍ଣ outage ଭାବେ ରହେ — ଏହା SQLite topology, କୌଣସି probeର ଭୁଲ configuration ନୁହେଁ।

External Postgres / multi-writer HA ଏକ ନଥିଭୁକ୍ତ stock path **ନୁହେଁ**। ଯଦି ଆପଣଙ୍କୁ HA ଦରକାର, ଗୋଟିଏ replica ରଖନ୍ତୁ କିମ୍ବା project ଅଲଗା ଭାବରେ ପରୀକ୍ଷା ଏବଂ ନଥିଭୁକ୍ତ କରିଥିବା topology ଚଲାନ୍ତୁ। Postgres/MySQL କାର୍ଯ୍ୟ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)ରେ ଅଛି। ଏହା ପ୍ରକାଶିତ ହେବା ପର୍ଯ୍ୟନ୍ତ, **ବଡ଼** `/v1/responses` କ୍ଷମତା ବଢ଼ାଇବାର ଏକମାତ୍ର ସମର୍ଥିତ ଉପାୟ ହେଉଛି Nଟି ସ୍ୱାଧୀନ process (ପରବର୍ତ୍ତୀ ବିଭାଗ), ଗୋଟିଏ volumeରେ `replicas > 1` ନୁହେଁ।

## ସ୍କେଲ୍-ଆଉଟ୍: N ସ୍ୱାଧୀନ ପ୍ରକ୍ରିୟା

ଗୋଟିଏ Node ପ୍ରକ୍ରିୟା ହେଉଛି **ଗୋଟିଏ V8 heap**। ପରସ୍ପରକୁ ଓଭରଲାପ୍ କରୁଥିବା ଦୁଇଟି ~3 MiB / ~750k-token coding-agent `POST /v1/responses` (RTK + Caveman) ପ୍ରାୟ ~12 Gi ଠାରେ ସେହି heapକୁ ବନ୍ଦ କରିଦିଏ (`FATAL ERROR: Reached heap limit`) ଏବଂ ଏକ 16 Gi cgroupକୁ OOM କରିପାରେ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ଦେଖନ୍ତୁ। ସେହି ମାପ ଏକ **ମେମୋରି-ବଜେଟ୍** ଚେତାବନୀ, ଦୁଇଟି ସମକାଳୀନ ଦୀର୍ଘ `/v1/responses` ପାଇଁ ପ୍ରଡକ୍ଟର ହାର୍ଡ-ମ୍ୟାକ୍ସ ନୁହେଁ। ହେଭିୱେଟ୍ ଚାଟ୍ ଆଡମିଶନ୍ ଏକ ସ୍ୱୟଂକ୍ରିୟ ଭାବେ ନିର୍ଦ୍ଧାରିତ ଇନଜେଷ୍ଟ୍ ବାଇଟ୍ ବଜେଟ୍ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ଦ୍ୱାରା ନିୟନ୍ତ୍ରିତ, ଯାହାକୁ ସେହି V8/cgroup ସୀମାରୁ ଆକାର ଦିଆଯାଇଛି — ପୂର୍ବରୁ ଆକାରିତ ପ୍ରକ୍ରିୟାରେ ଏହାକୁ ଅଧିକ ମୂଲ୍ୟରେ ଓଭରରାଇଡ୍ କରିବା (କିମ୍ବା ପୁରୁଣା `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ଅନୁରୋଧ-ଗଣନା ସୀମା ସେଟ୍ କରିବା) ପୁନର୍ବାର ସେହି ଅବର୍ଟ୍ ସୃଷ୍ଟି କରେ। ଛୋଟ ଚାଟ୍, `/healthz`, `/v1/models`, ଏବଂ MCP ସେହି ସୀମାରେ **ଅନ୍ତର୍ଭୁକ୍ତ ନୁହେଁ**।

### ଏକକ ପ୍ରକ୍ରିୟା: ଦୁଇଟିରୁ ଅଧିକ ଦୀର୍ଘ `/v1/responses`

ଏକ **ସୁସ୍ଥ** ପ୍ରକ୍ରିୟା (heap `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ଠାରୁ କମ୍, ଡିଫଲ୍ଟ `0.75`) ଦୁଇଟିରୁ ଅଧିକ ସମକାଳୀନ ଦୀର୍ଘ `POST /v1/responses` ଚଳାଇ **ପାରେ**, ଯେତେବେଳେ ପ୍ରକ୍ରିୟା-ବ୍ୟାପୀ ଇନଫ୍ଲାଇଟ୍-ବାଇଟ୍ ବଜେଟ୍ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110)ରେ ଏପର୍ଯ୍ୟନ୍ତ ସ୍ଥାନ ଥାଏ। `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (ଡିଫଲ୍ଟ 256 KiB) କିମ୍ବା ତାଠାରୁ ଅଧିକ ଆକାରର ବଡିଗୁଡ଼ିକ ଗଠନ-ଭାରୀ ଅନୁରୋଧ ପରି ସମାନ ହେଭିୱେଟ୍ ଲିଜ୍ ନିଅନ୍ତି ଏବଂ ସମାନ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` ଏସ୍କେପ୍ (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ବ୍ୟବହାର କରନ୍ତି। ଦଶଦଶ ସମକାଳୀନ ଦୀର୍ଘ SSE କ୍ଲାଏଣ୍ଟ୍ (ଅପରେଟରମାନଙ୍କୁ ପ୍ରାୟତଃ 40–50 ଆବଶ୍ୟକ ହୁଏ) ଏକ **ମେମୋରି-ବଜେଟ୍** ପ୍ରଶ୍ନ — heap + ପ୍ରାଇମେରି/ହେଡ୍ରୁମ୍ ସ୍ଲଟ୍ + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`କୁ ଉପଯୁକ୍ତ ଆକାର ଦିଅନ୍ତୁ — ଏହା ପ୍ରଡକ୍ଟର ହାର୍ଡ “ସର୍ବାଧିକ 2” ସୀମା ନୁହେଁ। ଚାପଗ୍ରସ୍ତ heap ତଥାପି ପୁନଃଚେଷ୍ଟାଯୋଗ୍ୟ `503` ସହିତ ଲୋଡ୍ କମାଏ, ଯାହାଦ୍ୱାରା #7849 ପୁନର୍ବାର ନ ଫେରେ।

ପୁଣି କରନ୍ତୁ। ଏହା ରାଉଟିଂ ପରିବର୍ତ୍ତନକୁ ସେହି ସଂଯୋଗ ମଧ୍ୟରେ ସୀମିତ ରଖେ। ପ୍ରକ୍ସିଟି
କଣ୍ଟେନର୍ରୁ ପହଞ୍ଚଯୋଗ୍ୟ ଏବଂ ସଂଯୋଗଟି ପ୍ରକୃତରେ ତାହାକୁ ଚୟନ କରୁଛି ବୋଲି ଯାଞ୍ଚ କରନ୍ତୁ।
ରୁଟ୍ ପରିବର୍ତ୍ତନ କରିବା ଅପ୍ଷ୍ଟ୍ରିମ୍ ଆଞ୍ଚଳିକ ଯୋଗ୍ୟତାର ନିଶ୍ଚିତତା ଦିଏ ନାହିଁ।

### ହୋଷ୍ଟ ଏବଂ କଣ୍ଟେନର୍ ନେଟୱର୍କିଂ ତୁଳନା କରନ୍ତୁ

ପ୍ରମାଣୀକୃତ ଫଳାଫଳ ତୁଳନା କରିବାବେଳେ key, ମଡେଲ୍ ଏବଂ ଅନୁରୋଧକୁ ସମାନ ରଖନ୍ତୁ; କୌଣସି
issueରେ କେବେବି ପରିଚୟପତ୍ର, ପ୍ରକ୍ସି ପାସୱାର୍ଡ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ଅଥରାଇଜେସନ୍ ହେଡର୍ ପେଷ୍ଟ କରନ୍ତୁ ନାହିଁ।
ପ୍ରଥମେ ହୋଷ୍ଟରେ ଏବଂ କଣ୍ଟେନର୍ ଭିତରେ ସମାନ କମାଣ୍ଡ ବ୍ୟବହାର କରି, OS ରିଜଲ୍ଭର୍ କେଉଁ
ଆଡ୍ରେସ୍ ଫ୍ୟାମିଲି ପ୍ରଦାନ କରୁଛି ତାହା ଯାଞ୍ଚ କରନ୍ତୁ:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute`କୁ ଆପଣ ଚଳାଉଥିବା ସେବାଦ୍ୱାରା ବଦଳାନ୍ତୁ (ଉଦାହରଣ ସ୍ୱରୂପ, `omniroute-web`)। ଏହି
କମାଣ୍ଡଗୁଡ଼ିକ ପରିଚୟପତ୍ର କିମ୍ବା IP ଠିକଣା ବିନା ଆଡ୍ରେସ୍ ଫ୍ୟାମିଲିଗୁଡ଼ିକୁ ପ୍ରିଣ୍ଟ କରେ। ଫେରିଥିବା `6`
କେବଳ ଏକ IPv6 DNS ଫଳାଫଳ ଦର୍ଶାଏ: ଏହା ବ୍ୟବହାରଯୋଗ୍ୟ IPv6 ରୁଟ୍ କିମ୍ବା API ଆକ୍ସେସ୍କୁ
ପ୍ରମାଣ କରେ **ନାହିଁ**। ଯେଉଁଠାରେ `curl` ଇନ୍ଷ୍ଟଲ୍ ହୋଇଛି, ଉଭୟ ପରିବେଶରେ
`curl -4 -I https://generativelanguage.googleapis.com`କୁ
`curl -6 -I https://generativelanguage.googleapis.com` ସହିତ ତୁଳନା କରନ୍ତୁ।
ଏକ HTTP ପ୍ରତିକ୍ରିୟା ସେହି ପ୍ରୋବ୍ ପାଇଁ ସଂଯୋଗକୁ ପ୍ରମାଣ କରେ, ଯଦିଓ ଏହା ଏକ ଅପ୍ରମାଣୀକୃତ
ତ୍ରୁଟି ହୋଇଥାଏ; କେବଳ ପ୍ରମାଣୀକୃତ ମଡେଲ୍ ଅନୁରୋଧ Gemini ଯୋଗ୍ୟତାକୁ ପରୀକ୍ଷା କରେ।

### ହୋଷ୍ଟ-ସ୍ତରୀୟ ବିକଳ୍ପ: କାର୍ଯ୍ୟକ୍ଷମ IPv6 ଏବଂ ରିଜଲ୍ଭର୍ ନୀତି

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762)ର ରିପୋର୍ଟକାରୀ
କଣ୍ଟେନର୍ IPv6 ସକ୍ଷମ କରି ଏବଂ glibc ଆଡ୍ରେସ୍ ଚୟନ ପରିବର୍ତ୍ତନ କରି ନିଜ ପରିବେଶରେ
ଆକ୍ସେସ୍ ପୁନଃସ୍ଥାପନ କରିଥିଲେ। ଏହାକୁ ଏକ ପରିବେଶ-ନିର୍ଦ୍ଦିଷ୍ଟ ବିକଳ୍ପ ଭାବରେ ବିବେଚନା କରନ୍ତୁ।
ରିଜଲ୍ଭର୍ ପ୍ରାଥମିକତା ସମନ୍ୱୟ କରିବା ପୂର୍ବରୁ କାର୍ଯ୍ୟକ୍ଷମ ହୋଷ୍ଟ IPv6, କଣ୍ଟେନର୍ ଇଗ୍ରେସ୍/ରାଉଟିଂ
ଏବଂ ଫାୟାରୱାଲ୍ ନିୟମଗୁଡ଼ିକ ନିଶ୍ଚିତ କରନ୍ତୁ। ନିଜେ ଏକ ପ୍ରାଇଭେଟ୍ ULA ଠିକଣା ସାର୍ବଜନୀନ
IPv6 ସଂଯୋଗ ସ୍ଥାପିତ କରେ ନାହିଁ।

Composeର ଡିଫଲ୍ଟ ନେଟୱର୍କ ସହିତ ପୂର୍ବରୁ ସଂଲଗ୍ନ ସେବାଗୁଡ଼ିକ ପାଇଁ, ଏହି ଖଣ୍ଡଟି
ସେହି ନେଟୱର୍କରେ IPv6 ସକ୍ଷମ କରେ; ଆପଣଙ୍କ ସେବା, ପୋର୍ଟ, ଭଲ୍ୟୁମ୍ ଏବଂ କନଫିଗରେସନ୍ର
ଅବଶିଷ୍ଟ ଅଂଶକୁ ଅପରିବର୍ତ୍ତିତ ରଖନ୍ତୁ:

```yaml
networks:
  default:
    enable_ipv6: true
```

ଏକ ନାମିତ ନେଟୱର୍କ ପାଇଁ, ସେବାଟି ପ୍ରକୃତରେ ଯେଉଁ ନେଟୱର୍କରେ ଯୋଗ ଦେଉଛି ସେଠାରେ ଏହାକୁ
ସକ୍ଷମ କରନ୍ତୁ। Docker ଏକ ULA ସବ୍ନେଟ୍ ବଣ୍ଟନ କରିପାରେ; କେବଳ ଆପଣଙ୍କ ନେଟୱର୍କରେ
ଆବଶ୍ୟକ ହେଲେ ଏକ ସ୍ପଷ୍ଟ, ଓଭରଲାପ୍ ନକରୁଥିବା ସବ୍ନେଟ୍ ଚୟନ କରନ୍ତୁ।
[Docker IPv6 ନେଟୱର୍କିଂ](https://docs.docker.com/engine/daemon/ipv6/)
ଏବଂ [Compose ନେଟୱର୍କ ବିକଳ୍ପଗୁଡ଼ିକ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ଦେଖନ୍ତୁ।

ଏକ **glibc-ଆଧାରିତ ଇମେଜ୍**ରେ, `/etc/gai.conf` ଆଡ୍ରେସ୍ ଚୟନ ପରିବର୍ତ୍ତନ କରିପାରେ। ବର୍ତ୍ତମାନର
ରିପୋଜିଟୋରି Dockerfile Debian ବ୍ୟବହାର କରେ; କଷ୍ଟମ୍ musl-ଆଧାରିତ ଇମେଜ୍ଗୁଡ଼ିକରେ ଏହି
ପ୍ରକ୍ରିୟା ନାହିଁ। ରିପୋର୍ଟ କରାଯାଇଥିବା ସମନ୍ୱୟ ULA ଲେବଲ୍କୁ `label fc00::/7 6`ରୁ
`label fc00::/7 1`କୁ ପରିବର୍ତ୍ତନ କରେ। ଇମେଜ୍ର ସମ୍ପୂର୍ଣ୍ଣ ନୀତି ସାରଣୀରୁ ଆରମ୍ଭ କରନ୍ତୁ ଏବଂ
ଏହାର ଅନ୍ୟ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକୁ ସଂରକ୍ଷଣ କରନ୍ତୁ: ଏକ `label` କିମ୍ବା `precedence` ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବା
ସେହି ଡିଫଲ୍ଟ ସାରଣୀକୁ ବଦଳାଇଦିଏ, ତେଣୁ କେବଳ ପରିବର୍ତ୍ତିତ ଲାଇନ୍ ଥିବା ଏକ ଫାଇଲ୍ ଯଥେଷ୍ଟ ନୁହେଁ।
[glibc କନଫିଗରେସନ୍ ସନ୍ଦର୍ଭ](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ସେହି ଆଚରଣଗୁଡ଼ିକୁ ଦଲିଲଭୁକ୍ତ କରେ। ସମୀକ୍ଷା କରାଯାଇଥିବା ଫାଇଲ୍କୁ `/etc/gai.conf`ରେ
କେବଳ-ପଠନୀୟ ଭାବେ bind-mount କରନ୍ତୁ ଏବଂ ଏହା ପ୍ରୟୋଗ କରିବା ପାଇଁ ସେବାଟି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ।

ଏହା **ସେହି କଣ୍ଟେନର୍ର ସମସ୍ତ ଆଉଟ୍ବାଉଣ୍ଡ ଟ୍ରାଫିକ୍** ପାଇଁ OS ଆଡ୍ରେସ୍ ଚୟନ ପରିବର୍ତ୍ତନ କରେ।
ଏହା ପ୍ରତ୍ୟେକ ଆପ୍ଲିକେସନ୍କୁ IPv6 ଚୟନ କରିବାକୁ ବାଧ୍ୟ କରେ ନାହିଁ: Nodeର DNS କ୍ରମ ଏବଂ
ସଂଯୋଗ ଚୟନ ମଧ୍ୟ ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ। ବିଶେଷତଃ, `--dns-result-order=ipv4first` IPv4କୁ
ପ୍ରାଧାନ୍ୟ ଦିଏ ଏବଂ କେବଳ IPv4-ସମ୍ବନ୍ଧୀୟ ବିଫଳତା ପାଇଁ ଏହା ଏକ ସମାଧାନ ନୁହେଁ।
[Node DNS କ୍ରମ](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ଦେଖନ୍ତୁ।

ହୋଷ୍ଟ-ସ୍ତରୀୟ କୌଣସି ପରିବର୍ତ୍ତନ ପରେ Gemini ଏବଂ ଆପଣଙ୍କ ଅନ୍ୟ ପ୍ରଦାତାମାନଙ୍କୁ ପୁଣି ପରୀକ୍ଷା କରନ୍ତୁ।
ପଛକୁ ଫେରାଇବା ପାଇଁ, କଷ୍ଟମ୍ `gai.conf` ମାଉଣ୍ଟ ହଟାନ୍ତୁ, ପୂର୍ବ ନେଟୱର୍କ କନଫିଗରେସନ୍
ପୁନଃସ୍ଥାପନ କରନ୍ତୁ ଏବଂ ଏକ ରକ୍ଷଣାବେକ୍ଷଣ ସମୟସୀମା ମଧ୍ୟରେ ପ୍ରଭାବିତ ସେବା/ନେଟୱର୍କକୁ
ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ। ଏକ ନେଟୱର୍କ ପୁନଃସୃଷ୍ଟି କରିବା ଏଥିରେ ସଂଲଗ୍ନ ଅନ୍ୟ କଣ୍ଟେନର୍ଗୁଡ଼ିକୁ
ବାଧା ଦେଇପାରେ; ସ୍ଥାୟୀ ଡାଟା ଭଲ୍ୟୁମ୍କୁ ଡିଲିଟ୍ କରନ୍ତୁ ନାହିଁ।

## ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ଟିପ୍ପଣୀ

- **SQLite WAL ମୋଡ୍:** OmniRoute ଯେପରି ସର୍ବଶେଷ ପରିବର୍ତ୍ତନଗୁଡ଼ିକୁ `storage.sqlite` ମଧ୍ୟରେ ଚେକପଏଣ୍ଟ କରିପାରିବ, ସେଥିପାଇଁ `docker stop`କୁ ସମ୍ପୂର୍ଣ୍ଣ ହେବାକୁ ଦିଅନ୍ତୁ। ସହିତ ଦିଆଯାଇଥିବା Compose ଫାଇଲଗୁଡ଼ିକରେ ପୂର୍ବରୁ 40s ଷ୍ଟପ୍ ଗ୍ରେସ୍ ପିରିୟଡ୍ ସେଟ୍ କରାଯାଇଛି। ଯଦି ଆପଣ ଇମେଜ୍ଟିକୁ ସିଧାସଳଖ ଚଲାନ୍ତି, ତେବେ `--stop-timeout 40` ରଖନ୍ତୁ।
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ଯଦି ନିୟମିତ/ଲେଖିବା-ପୂର୍ବ ବ୍ୟାକଅପ୍ଗୁଡ଼ିକ ବାହ୍ୟ ଭାବରେ ପରିଚାଳିତ ହୁଏ, ତେବେ ଏହାକୁ `true` ଭାବେ ସେଟ୍ କରନ୍ତୁ। ବିଦ୍ୟମାନ ଡାଟାବେସ୍ ମାଇଗ୍ରେସନ୍ଗୁଡ଼ିକ ପାଇଁ ତଥାପି ସେମାନଙ୍କର ନିଜସ୍ୱ ସ୍ଥାୟୀ ସୁରକ୍ଷା ସ୍ନାପସଟ୍ ଏବଂ ବ୍ୟାପକ ମାଇଗ୍ରେସନ୍ ସୁରକ୍ଷା ବ୍ୟବସ୍ଥା ଆବଶ୍ୟକ।
- **ଡାଟା ସ୍ଥାୟିତ୍ୱ:** କଣ୍ଟେନର୍ ପୁନଃଚାଳନଗୁଡ଼ିକ ମଧ୍ୟରେ ଆପଣଙ୍କ ଡାଟାବେସ୍, କୀ ଏବଂ ବିନ୍ୟାସଗୁଡ଼ିକୁ ସ୍ଥାୟୀ ରଖିବା ପାଇଁ ସର୍ବଦା `/app/data`ରେ ଏକ ଭଲ୍ୟୁମ୍ ମାଉଣ୍ଟ କରନ୍ତୁ।
- **ପୋର୍ଟ ବିନ୍ୟାସ:** ଡିଫଲ୍ଟ `20128` ପୋର୍ଟ ପରିବର୍ତ୍ତନ କରିବା ପାଇଁ `PORT` ପରିବେଶ ଭେରିଏବଲ୍କୁ ଓଭରରାଇଡ୍ କରନ୍ତୁ।
