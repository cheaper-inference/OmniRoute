## ଶୂନ୍ୟ-କନଫିଗ୍ ସ୍ୱୟଂଚାଳିତ ରାଉଟିଂ (`auto/` ପ୍ରିଫିକ୍ସ)

> **ନୂଆ:** କମ୍ବୋ ସୃଷ୍ଟି କରିବା ଆବଶ୍ୟକ ନାହିଁ। ଯେକୌଣସି କ୍ଲାଏଣ୍ଟରେ ସିଧାସଳଖ `auto/` ପ୍ରିଫିକ୍ସ ବ୍ୟବହାର କରନ୍ତୁ।

### ଦ୍ରୁତ ଉଦାହରଣ

| ମଡେଲ୍ ID       | ଭାରିଆଣ୍ଟ | ଆଚରଣ                                                                         |
| -------------- | -------- | ---------------------------------------------------------------------------- |
| `auto`         | ଡିଫଲ୍ଟ   | ସମସ୍ତ ସଂଯୁକ୍ତ ପ୍ରଦାତା, LKGP କୌଶଳ, ସନ୍ତୁଳିତ ଓଜନ                               |
| `auto/coding`  | କୋଡିଂ    | ଗୁଣବତ୍ତା-ପ୍ରଥମ ଓଜନ, କୋଡ୍ ଜେନେରେସନ୍ ପାଇଁ ଉପଯୁକ୍ତ                              |
| `auto/fast`    | ଦ୍ରୁତ    | କମ୍-ବିଳମ୍ବତା ଓଜନଯୁକ୍ତ ଚୟନ                                                    |
| `auto/cheap`   | ଶସ୍ତା    | ଖର୍ଚ୍ଚ-ଅନୁକୂଳିତ ରାଉଟିଂ (ସର୍ବନିମ୍ନ ଖର୍ଚ୍ଚ ପ୍ରଥମେ)                             |
| `auto/offline` | ଅଫଲାଇନ୍  | ସର୍ବାଧିକ କୋଟା ଉପଲବ୍ଧତା ଥିବା ପ୍ରଦାତାଙ୍କୁ ପ୍ରାଧାନ୍ୟ ଦିଏ                        |
| `auto/smart`   | ସ୍ମାର୍ଟ  | ଉନ୍ନତ ମଡେଲ୍ ଆବିଷ୍କାର ପାଇଁ ଗୁଣବତ୍ତା-ପ୍ରଥମ + ଅଧିକ ଅନ୍ୱେଷଣ ହାର (10%)            |
| `auto/lkgp`    | lkgp     | ସ୍ପଷ୍ଟ LKGP (ଡିଫଲ୍ଟ `auto` ସହ ସମାନ)                                          |
| `auto/chaos`   | chaos    | ସମାନ୍ତରାଳ ଫ୍ୟାନ୍-ଆଉଟ୍, ପ୍ରତି ପ୍ରଦାତାରେ ଗୋଟିଏ ମଡେଲ୍ (ତ୍ରୁଟି ଇଞ୍ଜେକ୍ସନ୍ ନୁହେଁ) |

### ବର୍ଗ × ସ୍ତର ସଂଯୋଜନ (`auto/<category>:<tier>`)

OpenRouter-ଶୈଳୀର ସଫିକ୍ସଗୁଡ଼ିକ **କେଉଁ ପ୍ରକାରର ରୁଟ୍** (ବର୍ଗ)କୁ **କିପରି ଅନୁକୂଳିତ କରାଯିବ** (ସ୍ତର)ଠାରୁ ପୃଥକ କରେ, ଯାହାଦ୍ୱାରା ଆପଣ ସେଗୁଡ଼ିକୁ ସ୍ୱାଧୀନ ଭାବରେ ସଂଯୋଜନ କରିପାରିବେ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ବର୍ଗଗୁଡ଼ିକ** (କ୍ଷମତା ଅନୁଯାୟୀ ପ୍ରାର୍ଥୀ ପୁଲ୍ ଫିଲ୍ଟର୍ କରେ): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍ଗୁଡ଼ିକୁ ରଖେ; `reasoning` ରିଜନିଂ/ଥିଙ୍କିଂ ମଡେଲ୍ଗୁଡ଼ିକୁ ରଖେ।
- **ସ୍ତରଗୁଡ଼ିକ** (ସ୍କୋରିଂ ଓଜନ / ପୁଲ୍ ଫିଲ୍ଟର୍ ବାଛେ): `fast` (ଶୀଘ୍ର ପ୍ରେରଣ) · `cheap` (ଉପନାମ `floor`, ଖର୍ଚ୍ଚ-ସଞ୍ଚୟକାରୀ) · `reliable` (ସର୍କିଟ୍-ବ୍ରେକର୍ ସ୍ୱାସ୍ଥ୍ୟ + ବିଳମ୍ବତା ସ୍ଥିରତା) · `free` / `pro` (`classifyTier` ମାଧ୍ୟମରେ ମଡେଲ୍ ସ୍ତର ଅନୁଯାୟୀ ପୁଲ୍ ଫିଲ୍ଟର୍ କରେ — ମାଗଣା ସ୍ତର ବନାମ ପ୍ରିମିୟମ୍)।

| ଉଦାହରଣ                 | ଏଥିରେ ରିଜଲ୍ଭ ହୁଏ                                        |
| ---------------------- | ------------------------------------------------------- |
| `auto/coding:fast`     | କୋଡିଂ ପୁଲ୍, କମ୍-ବିଳମ୍ବତା ଓଜନ                            |
| `auto/coding:cheap`    | କୋଡିଂ ପୁଲ୍, ଖର୍ଚ୍ଚ-ଅନୁକୂଳିତ (ଉପନାମ `auto/coding:floor`) |
| `auto/reasoning:pro`   | କେବଳ ରିଜନିଂ/ଥିଙ୍କିଂ ମଡେଲ୍, ପ୍ରିମିୟମ୍ ସ୍ତର               |
| `auto/vision`          | ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍ (କୌଣସି ସ୍ତର ନାହିଁ → ସନ୍ତୁଳିତ ଓଜନ)     |
| `auto/multimodal:free` | ମଲ୍ଟିମୋଡାଲ୍-ସକ୍ଷମ ମଡେଲ୍, କେବଳ ମାଗଣା ସ୍ତର                |

ଯେକୌଣସି ବୈଧ `auto/<category>[:<tier>]` ଚାହିଦା ଅନୁସାରେ ରିଜଲ୍ଭ ହୁଏ; `/v1/models` ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡରେ ଏକ କ୍ୟୁରେଟ୍ କରାଯାଇଥିବା ଉପସେଟ୍ର ପ୍ରଚାର କରାଯାଏ (`open-sse/services/autoCombo/builtinCatalog.ts`ରେ `AUTO_SUFFIX_VARIANTS`)। ଫିଲ୍ଟରିଂ **ଫେଲ୍-ଓପନ୍** ଅଟେ — ଯଦି କୌଣସି ସୀମାବନ୍ଧନ ସହ କୌଣସି ସଂଯୁକ୍ତ ମଡେଲ୍ ମେଳ ନ ଖାଏ, ତେବେ ସମ୍ପୂର୍ଣ୍ଣ ପୁଲ୍ ବ୍ୟବହୃତ ହୁଏ, ଯାହାଦ୍ୱାରା ରାଉଟିଂ କେବେ ଭଙ୍ଗ ହୁଏ ନାହିଁ। ମୂଳ ସ୍କୋରର୍ (`combo.ts`) ଅପରିବର୍ତ୍ତିତ ରହେ; ବର୍ଗ/ସ୍ତର ଫିଲ୍ଟର୍ `buildAutoCandidates`ରେ ପ୍ରୟୋଗ କରାଯାଏ।

> **ଲାଇଭ୍ ମଡେଲ୍ ଇଣ୍ଟେଲିଜେନ୍ସ:** `ARENA_ELO_SYNC_ENABLED` ଫ୍ଲାଗ୍ ଚାଲୁ ଥିବାବେଳେ ସ୍ୱୟଂଚାଳିତ ରାଉଟିଂ ଉପଯୁକ୍ତତା ଲାଇଭ୍ **Arena ELO** ର୍ୟାଙ୍କିଂ + **models.dev** ସ୍ତର ଡାଟା ଦ୍ୱାରା ନିର୍ଦ୍ଧାରିତ ହୁଏ (ଅନ୍ୟଥା ସ୍ଥିର ଉପଯୁକ୍ତତା ମ୍ୟାପ୍କୁ ଫେରିଯାଏ)।

**କିପରି ବ୍ୟବହାର କରିବେ:**

```bash
# OpenAI ଫର୍ମାଟ୍ ସମର୍ଥନ କରୁଥିବା ଯେକୌଣସି IDE କିମ୍ବା CLI ଟୁଲ୍
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ଆପଣଙ୍କ କୋଡ୍/କନଫିଗ୍ରେ ମଡେଲ୍କୁ ଏପରି ସେଟ୍ କରନ୍ତୁ:
model: "auto"                 # ସନ୍ତୁଳିତ ଡିଫଲ୍ଟ
model: "auto/coding"          # କୋଡିଂ କାର୍ଯ୍ୟ ପାଇଁ ସର୍ବୋତ୍ତମ
model: "auto/fast"            # ଉପଲବ୍ଧ ମଧ୍ୟରେ ସବୁଠାରୁ ଦ୍ରୁତ
model: "auto/cheap"           # ପ୍ରତି ଟୋକେନ୍ରେ ସବୁଠାରୁ ଶସ୍ତା
```

**କ’ଣ ଘଟେ:**

1. OmniRoute `src/sse/handlers/chat.ts`ରେ `auto/` ପ୍ରିଫିକ୍ସ ଚିହ୍ନଟ କରେ
2. ଡାଟାବେସ୍ରୁ ସମସ୍ତ **ସକ୍ରିୟ ପ୍ରଦାତା ସଂଯୋଗ** କ୍ୱେରି କରେ
3. ବୈଧ ପରିଚୟପତ୍ର (API କୀ କିମ୍ବା OAuth ଟୋକେନ୍) ଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ଫିଲ୍ଟର୍ କରେ
4. ପ୍ରତ୍ୟେକ ସଂଯୋଗ ପାଇଁ ମଡେଲ୍ ନିର୍ଦ୍ଧାରଣ କରେ (`connection.defaultModel` କିମ୍ବା ପ୍ରଦାତାଙ୍କ ପ୍ରଥମ ମଡେଲ୍)
5. ମେମୋରିରେ ଏକ **ଭର୍ଚୁଆଲ୍ କମ୍ବୋ** ତିଆରି କରେ (DBରେ ସଂରକ୍ଷିତ ହୁଏ ନାହିଁ)
6. ଚୟନିତ ଭାରିଆଣ୍ଟର ଓଜନ ପ୍ରୋଫାଇଲ୍ + LKGP କୌଶଳ ବ୍ୟବହାର କରି ରାଉଟ୍ କରେ

**ମୁଖ୍ୟ ଗୁଣଧର୍ମ:**

- ✅ **ସର୍ବଦା-ଚାଲୁ:** କୌଣସି ଟଗଲ୍, କମ୍ବୋ ସୃଷ୍ଟି କିମ୍ବା କନଫିଗରେସନ୍ ଆବଶ୍ୟକ ନାହିଁ
- ✅ **ଡାଇନାମିକ୍:** ବର୍ତ୍ତମାନ ସଂଯୁକ୍ତ ପ୍ରଦାତାଗୁଡ଼ିକୁ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ପ୍ରତିଫଳିତ କରେ
- ✅ **ସେସନ୍ ସ୍ଥିରତା:** LKGP ଶେଷ ସଫଳ ପ୍ରଦାତାଙ୍କୁ ପ୍ରାଥମିକତା ଦେବା ସୁନିଶ୍ଚିତ କରେ
- ✅ **ବହୁ-ଆକାଉଣ୍ଟ ସଚେତନ:** ପ୍ରତ୍ୟେକ ପ୍ରଦାତା ସଂଯୋଗ ଏକ ପୃଥକ ପ୍ରାର୍ଥୀ ହୁଏ
- ✅ **କୌଣସି DB ଲେଖନ ନାହିଁ:** ଭର୍ଚୁଆଲ୍ କମ୍ବୋ କେବଳ ଅନୁରୋଧ ପାଇଁ ଅବସ୍ଥିତ ରହେ, ସ୍ଥାୟୀକରଣ ଓଭରହେଡ୍ ଶୂନ୍ୟ

### ପ୍ରତି-କୀ ପ୍ରାର୍ଥୀ ନିୟନ୍ତ୍ରଣ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` ପରେ ଥିବା ସଫିକ୍ସ, କିମ୍ବା

ସହନଶୀଳତା ପଠନଗୁଡ଼ିକୁ ପୁନଃବ୍ୟବହାର କରି ଲାଇଭ୍ ପହଞ୍ଚଯୋଗ୍ୟତା ସହ ସଜ୍ଜିତ ଏକ `auto/*` ଚ୍ୟାନେଲ୍ର
ବର୍ତ୍ତମାନର ପ୍ରାର୍ଥୀ ପୁଲ୍ ତାଲିକାଭୁକ୍ତ କରେ (କେବେ ମଧ୍ୟ କଚ୍ଚା ବ୍ରେକର୍ `state` ନୁହେଁ):

- ମଡେଲ୍ ଲକ୍ଆଉଟ୍ — `isModelLocked(provider, connectionId, model)`

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ଏହି API କୀର `excluded` ଫ୍ଲାଗ୍ ମଧ୍ୟ ବହନ କରେ। ବହିଷ୍କରଣଗୁଡ଼ିକ
ପ୍ରତି-API-କୀ ଆଧାରରେ ସଂରକ୍ଷିତ ହୁଏ (`auto_candidate_overrides` ଟେବୁଲ୍, ମାଇଗ୍ରେସନ୍ `128`) — OmniRoute
କୌଣସି `users` ଟେବୁଲ୍ ନଥିବା ଏକକ-ଟେନାଣ୍ଟ ପ୍ରଣାଳୀ, ତେଣୁ `apiKeyId` ହେଉଛି ସର୍ବନିକଟ ପ୍ରକୃତ ପ୍ରତି-କଲର୍
ପରିଚୟ — ଏବଂ ଶୁଦ୍ଧ, ୟୁନିଟ୍-ପରୀକ୍ଷିତ
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) ମାଧ୍ୟମରେ

ଫିଲ୍ଟର୍ଟି **ଫେଲ୍-ଓପନ୍** ଅଟେ: ଏକ ଅସେଟ୍ apiKeyId/channel କିମ୍ବା ଏକ DB ଲୁକଅପ୍ ବିଫଳତା, ଉଭୟ

## ସଞ୍ଚିତ ଅଟୋ କମ୍ବୋ ପାଇଁ ଖାତା ପସନ୍ଦ।

ଇଣ୍ଟେଲିଜେଣ୍ଟ୍ ଅଟୋ ଏଡିଟର୍ ଏକ ଇଚ୍ଛାଧୀନ ପ୍ରଦାନ କରେ।** ଖାତା ପସନ୍ଦ** ବିଭାଗ ପ୍ରତ୍ୟେକ ସଂଯୋଗକୁ ଅଗ୍ରାଧିକାର ଦିଆଯାଇପାରେ, ସାଧାରଣ (ଡିଫଲ୍ଟ), ରିଜର୍ଭ, କିମ୍ବା ବାଦ ଦିଆଯାଇପାରେ। ଏକାଧିକ ସଂଯୋଗ ଏକ ସ୍ତର ଅଂଶୀଦାର କରିପାରିବ। ପ୍ରଥମ ଯୋଗ୍ୟ ସ୍ତର ମଧ୍ୟରେ ଅଟୋ ଚୟନ କରେ, ସେଠାରେ ଏହାର scoring/router ଆଚରଣକୁ ବଜାୟ ରଖେ; ବିଫଳ ପ୍ରୟାସ ଅବଶିଷ୍ଟ କଂକ୍ରିଟ୍ ଆକାଉଣ୍ଟକୁ ଖସିଯାଏ, ସଂରକ୍ଷଣ ପୂର୍ବରୁ ସାଧାରଣ ପୂର୍ବରୁ ପସନ୍ଦ କରାଯାଏ। ବାଦ ଦିଆଯାଇଥିବା ସଂଯୋଗଗୁଡ଼ିକ ଏହି କମ୍ବୋ ଦ୍ୱାରା କେବେବି ବ୍ୟବହୃତ ହୁଏ ନାହିଁ।

ସେଟିଂ `config.accountPreferences` ଭାବରେ ଗଚ୍ଛିତ ହୋଇଛି, ସଂଯୋଗ ID ଦ୍ୱାରା କି:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

ଏକ ବାଦ ଦିଆଯାଇଥିବା କିମ୍ବା ଖାଲି ମାନଚିତ୍ର ବିଦ୍ୟମାନ ମାର୍ଗଦର୍ଶନକୁ ବଜାୟ ରଖେ। ଅଗ୍ରାଧିକାରଗୁଡିକ ଅକ୍ଷମ ସଂଯୋଗକୁ ସକ୍ଷମ କରେ ନାହିଁ, API- କି ପ୍ରବେଶ ଅନୁମତି, କୋଟା-ଅବରୋଧିତ ପ୍ରାର୍ଥୀଙ୍କୁ ପୁନ restore ସ୍ଥାପନ କିମ୍ବା ବଜେଟ୍ ଯାଞ୍ଚ ବାଇପାସ୍ କରେ ନାହିଁ। ପ୍ରତ୍ୟେକ ପ୍ରୟାସ ଏହାର କଂକ୍ରିଟ୍ ସଂଯୋଗରେ ସୀମିତ, ତେଣୁ ଆକାଉଣ୍ଟ୍ ଫଲବ୍ୟାକ୍ କମ୍ବୋ ରାଉଟର ପଛରେ ସ୍ତରଗୁଡିକ ଡେଇଁ ପାରିବ ନାହିଁ। ବିଦ୍ୟମାନ ଅଧିବେଶନ ସମ୍ବନ୍ଧ ଏକ ଯୋଗ୍ୟ ଖାତା ବଜାୟ ରଖିପାରେ; ଏକ ଦେଶୀ ଟର୍ନରେ ବନ୍ଧା ହୋଇଥିବା ଆକାଉଣ୍ଟକୁ ବାଦ୍ ଦେଇ ଚୁପଚାପ୍ ଖାତା ବଦଳାଇବା ପରିବର୍ତ୍ତେ ଟର୍ନ୍।

ବିନ୍ୟାସିତ ପସନ୍ଦଗୁଡ଼ିକ ଖାତା-ସଚେତନ ଅଟୋ ପଥ ବ୍ୟବହାର କରନ୍ତି: ଅନ୍-ସୀମା ପ୍ରସଙ୍ଗ-କ୍ୟାଚ୍, ସ୍ମାର୍ଟ-ପାଇପଲାଇନ, ବିଶୃଙ୍ଖଳା ଏବଂ ଛାୟା ସର୍ଟକଟ୍ ପଠାଯାଏ ନାହିଁ। ଏହି ଅନୁରୋଧଗୁଡିକ ପାଇଁ କଳ୍ପନାକାରୀ ହେଡିଂ ଅକ୍ଷମ ହୋଇଛି ତେଣୁ ରିଜର୍ଭ ଆକାଉଣ୍ଟଗୁଡିକ ପସନ୍ଦିତ ଦ race ଡ଼କୁଦ କରିପାରିବ ନାହିଁ। ଅନ୍ୟ କମ୍ବୋ ରଣନୀତି ଏହି ସେଟିଂକୁ ବ୍ୟାଖ୍ୟା କରେ ନାହିଁ। ଅଟୋ ଠାରୁ ଏକ କମ୍ବୋ ପରିବର୍ତ୍ତନ କରିବା, ପରବର୍ତ୍ତୀ ସୁଇଚ୍ ପାଇଁ ସଞ୍ଚିତ ପସନ୍ଦଗୁଡ଼ିକୁ ରଖେ।

## ଏକ Clientରୁ Custom Comboକୁ Call କରିବା

Persisted combos (Settings → Combos) କେବଳ ସେତେବେଳେ ବ୍ୟବହୃତ ହୁଏ, ଯେତେବେଳେ client `model` fieldରେ comboର **ଅବିକଳ ନାମ** ପଠାଏ — combo ନାମର କୌଣସି fuzzy କିମ୍ବା partial matching ନାହିଁ, ଏବଂ କୌଣସି `auto/` prefix ମଧ୍ୟ ସମ୍ପୃକ୍ତ ନୁହେଁ। Resolution କ୍ରମ (`src/sse/services/model.ts`ରେ `getComboForModel()`):

1. ଅବିକଳ combo-name match (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ଦୁଇଟି ସାଧାରଣ ଭୁଲ:

- **`auto` ଆପଣଙ୍କ combos ବ୍ୟବହାର କରେ ନାହିଁ।** `auto`/`auto/*` ନିଜର zero-config candidate pool ନିର୍ମାଣ କରେ ଏବଂ କେବଳ ଯଦି କୌଣସି comboର ନାମ ଆକ୍ଷରିକ ଭାବରେ `auto` ଥାଏ, ତେବେ persisted combosକୁ ବିଚାର କରେ (ଏହା ସୁପାରିସ କରାଯାଏ ନାହିଁ)। ଏକ combo ମାଧ୍ୟମରେ route କରିବାକୁ, ଏହାର ଅବିକଳ ନାମ ପଠାନ୍ତୁ — `auto` ନୁହେଁ।
- **`openrouter/auto` ହେଉଛି ଏକ ପ୍ରକୃତ paid OpenRouter product** ("Auto Best Available"), OmniRoute alias ନୁହେଁ। ଏହା OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`)ର ଏକମାତ୍ର static model entry ଏବଂ ଏଥିପାଇଁ ପୃଥକ ଭାବରେ bill କରାଯାଏ। ଏହାକୁ `auto` poolsରୁ ବାଦ ଦେବା ପାଇଁ Settings → Routing → Hide paid models ବ୍ୟବହାର କରନ୍ତୁ।

ଏଠାରେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ମୂଳ ଦ୍ୱନ୍ଦ୍ୱ ପାଇଁ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) ଏବଂ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) ଦେଖନ୍ତୁ।

## ଏହା କିପରି କାମ କରେ (ସ୍ଥାୟୀ ଅଟୋ-କମ୍ବୋସ୍)

ଅଟୋ-କମ୍ବୋ ଇଞ୍ଜିନ୍ ଗତିଶୀଳ ଭାବରେ a ବ୍ୟବହାର କରି ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ସର୍ବୋତ୍ତମ provider/model ଚୟନ କରେ।**16-ଫ୍ୟାକ୍ଟର୍ ସ୍କୋରିଂ ଫଙ୍କସନ୍।** ( `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` ରେ ବ୍ୟାଖ୍ୟା କରାଯାଇଛି) `1.0` କୁ ଡିଫଲ୍ଟ ଓଜନ ରାଶି; କଷ୍ଟମ୍ ଓଜନ `normalizeScoringWeights()` ଦ୍ୱାରା ପୁନ orn ନିର୍ମାଣ କରାଯାଏ। ଷୋହଳ — `cacheAffinity` ଏବଂ `resetWindowAffinity` — ମଧ୍ୟରୁ ଦୁଇଟି `0` ର ଏକ ଡିଫଲ୍ଟ ଓଜନ ବହନ କରେ; `reliability` `DEFAULT_WEIGHTS` ରେ `0` ବହନ କରେ କିନ୍ତୁ ଜେନେରିକ୍ ପ୍ୟାକ୍ ରେ `0.03` ଏବଂ `reliability-first` ରେ `0.04`, ଏବଂ `quality` ପ୍ୟାକ୍ ରେ `0.02` ବହନ କରେ ( `quality-first` ରେ`0.03` ): ସେଗୁଡିକ ଏପର୍ଯ୍ୟନ୍ତ ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀଙ୍କ ପାଇଁ ଗଣନା କରାଯାଇଥାଏ, ଏବଂ `cacheAffinity` ଗେଟ୍ ସ୍କୋର ବାହାରେ ପ୍ରମ୍ପ୍ଟ-କ୍ୟାଚ୍ ଡିପ୍ଲିକେସନ୍, ତେଣୁ ଶୂନ-ଡିଫଲ୍ଟ କାରକଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବରେ ଭୋଟ୍ କରନ୍ତି ନାହିଁ।

### `weighted` ସେମାଣ୍ଟିକ୍ସ।

`weighted` ହେଉଛି a **ଅନୁରୋଧ ପାଇଁ ଆନୁପାତିକ ରାଣ୍ଡମ ଡ୍ର।** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ସମାନତା ନୁହେଁ:

- ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ଅଙ୍କନ କରେ।**ଗୋଟିଏ।** ସମ୍ଭାବ୍ୟତା `weight / totalWeight` ସହିତ ପଦକ୍ଷେପ; ଅବଶିଷ୍ଟ ପଦକ୍ଷେପଗୁଡିକ ସେହି ଅନୁରୋଧ ପାଇଁ ଫଲବ୍ୟାକ୍ ଚେନ୍ ଭାବରେ ଓଜନ ହ୍ରାସ କରି ଅର୍ଡର ହୋଇଛି।
- ଏକ ପଦକ୍ଷେପ ଯାହାର ଓଜନ `0` (କିମ୍ବା ନିଖୋଜ) ଅଟେ।**କଦାପି ଅଙ୍କିତ ନୁହେଁ।** ଯେତେବେଳେ ଅନ୍ୟ କ step ଣସି ପଦକ୍ଷେପର ଓଜନ > 0 — ଥାଏ, ଏହା କେବଳ ଡ୍ରପ୍ ଷ୍ଟେପ୍ ବିଫଳ ହେବା ପରେ ଏକ ଫଲବ୍ୟାକ୍ ଭାବରେ କାର୍ଯ୍ୟ କରିପାରିବ। କେବଳ ଯେତେବେଳେ**ସମସ୍ତ** ଓଜନ 0 ହେଉଛି ଚୟନ ଏକକ ହୋଇଯାଏ।
- ଷ୍ଟେପଗୁଡିକ ଯାହାର ଲକ୍ଷ୍ୟ ସବୁ ଉପଲବ୍ଧ ନାହିଁ — ପ୍ରଦାନକାରୀ ସର୍କିଟ ବ୍ରେକର୍ `OPEN`, ସଂଯୋଗ କୁଲଡାଉନ୍, ମଡେଲ୍ ଲକଆଉଟ୍ — ଏହା ଘଟିବା ପୂର୍ବରୁ ଡ୍ରରୁ ଅପସାରିତ ହୋଇଛି (`open-sse/services/combo/targetResolution.ts`), ତେଣୁ ଗୋଟିଏ ସୁସ୍ଥ ପଦକ୍ଷେପ ପ୍ରତ୍ୟେକ ଅନୁରୋଧକୁ ସାମୟିକ ଭାବରେ ଜିତାଇପାରେ।
- `stickyWeightedLimit` (କମ୍ବୋ ବିନ୍ୟାସ, ଡିଫଲ୍ଟ `1` = ବନ୍ଦ) ପୁନ - ଚିତ୍ରାଙ୍କନ ପୂର୍ବରୁ କ୍ରମାଗତ ଅନେକ ସଫଳତା ପାଇଁ ଅଙ୍କିତ ପଦକ୍ଷେପକୁ ପିନ୍ କରେ।

କଠୋର ଘୂର୍ଣ୍ଣନ ପାଇଁ `round-robin` ବ୍ୟବହାର କରନ୍ତୁ; `weighted` ରେ ସମାନ ଓଜନ ପରିସଂଖ୍ୟାନ — ପ୍ରଦାନ କରେ କଠୋର — ସନ୍ତୁଳନ ନୁହେଁ।

### ଏଜେଣ୍ଟ ପାଇପଲାଇନ ମୋଡ୍।

ଅତିକମରେ ଦୁଇଟି ମଡେଲ ସହିତ ଏକ `pipeline` କମ୍ବୋ `config.agenticOrchestration.enabled` ସହିତ planner/executor ରାଉଟିଙ୍ଗକୁ ଚୟନ କରିପାରିବ। ପ୍ରଥମ ଲକ୍ଷ୍ୟ ଯୋଜନା ଏବଂ ଅନ୍ତିମ ଉତ୍ତରଗୁଡିକର ମାଲିକ; ଦ୍ୱିତୀୟ ଟାର୍ଗେଟ୍ କ୍ଲାଏଣ୍ଟ-ଦେଶୀ ଟୁଲ୍ କଲ୍ ନିର୍ଗତ କରେ। OmniRoute ଅନୁରୋଧ ପ୍ରୋଟୋକଲରୁ ସାଧନ-ଫଳାଫଳ ନିରନ୍ତର ଚିହ୍ନଟ କରେ, ଯୋଜନାକାରୀଙ୍କୁ ପଚାରିଥାଏ ଯେ ଅନ୍ୟ ଏକ ଉପକରଣ ରାଉଣ୍ଡ ଆବଶ୍ୟକ କି, ଏବଂ ଗତିଶୀଳ ଭାବରେ ଏକଜେକ୍ୟୁଟର କିମ୍ବା ପ୍ଲାନର୍ କ୍ଲାଏଣ୍ଟ ମୁହାଁମୁହିଁ ଚୂଡ଼ାନ୍ତ ପଦକ୍ଷେପ କରିଥାଏ।

ବ plan କଳ୍ପିକ `config.agenticOrchestration.contextCompaction` ପ୍ରତ୍ୟେକ ଯୋଜନାକାରୀ କିମ୍ବା ନିର୍ବାହୀ ପଠାଇବା ପୂର୍ବରୁ ଏକ ପୃଥକ ପେଲୋଡ୍ ବଜେଟ୍ ପ୍ରୟୋଗ କରେ। ଏହାକୁ ସ୍ପଷ୍ଟ ଭାବରେ ସକ୍ଷମ କରନ୍ତୁ:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

ଏଗୁଡ଼ିକ କ୍ରମିକ JSON ବର୍ଣ୍ଣ ବଜେଟ୍ ଅପରେଟର୍ ଦ୍ୱାରା ମନୋନୀତ ହୋଇଛି, ଟୋକେନ୍ ପ୍ରସଙ୍ଗ ୱିଣ୍ଡୋ କିମ୍ବା ଗ୍ୟାରେଣ୍ଟି ଅପଷ୍ଟ୍ରିମ୍ ସୀମା ନୁହେଁ। ପ୍ରକୃତ ମଡେଲ୍ IDs ଡିଫଲ୍ଟକୁ ନବଲିଖନ କରେ। ଥ୍ରେସହୋଲ୍ଡ ଉପରେ, ସଙ୍କୋଚନ ସମାନ ଉପକରଣ ପରିଭାଷାକୁ ଅପସାରଣ କରେ, ଏକ ହଜମ ସହିତ ଓଭରସାଇଜଡ୍ ଟୁଲ୍ ପ୍ରମାଣକୁ ଟ୍ରିମ୍ କରେ ଏବଂ ଲକ୍ଷ୍ୟ ଅନୁପାତରେ ପୁରୁଣା ସମ୍ପୂର୍ଣ୍ଣ ଇତିହାସ ଗୋଷ୍ଠୀକୁ ଅପସାରଣ କରେ। ଏହା system/developer ନିର୍ଦ୍ଦେଶାବଳୀ, ସର୍ବଶେଷ ଉପଭୋକ୍ତା ଅନୁରୋଧ, ସମାନ୍ତରାଳ calls/results ଅନ୍ତର୍ଭୂକ୍ତ କରି ଶେଷ ଉପକରଣ ରାଉଣ୍ଡ, ଏବଂ Gemini ର ଅଗ୍ରଣୀ ମାର୍ଗଦର୍ଶନ ନିର୍ଦ୍ଦେଶକୁ ବଜାୟ ରଖେ। ଶୀର୍ଷ ସ୍ତରୀୟ ନିର୍ଦ୍ଦେଶାବଳୀ ଏବଂ ଉପକରଣ ସେଟିଙ୍ଗ୍ ସଂରକ୍ଷିତ। ଏକ ବର୍ଜନ ମାର୍କର ରେକର୍ଡ ଇତିହାସ ଅପସାରଣ କଲା; ଏହା ଏକ ସ୍ଥିରିକୃତ ଟ୍ରିମିଂ, ଏକ ଅର୍ଥଗତ ସାରାଂଶ ନୁହେଁ। ଯଦି ପିନ୍ ହୋଇଥିବା ପ୍ରସଙ୍ଗ ତଥାପି ବଜେଟ୍ ଅତିକ୍ରମ କରେ, ମଡେଲ୍ ସହିତ ଯୋଗାଯୋଗ କରିବା ପୂର୍ବରୁ ଅନୁରୋଧ 413 ଫେରସ୍ତ କରେ। ସଙ୍କୋଚନ ଅକ୍ଷମ କିମ୍ବା ଥ୍ରେସହୋଲ୍ଡ ତଳେ ଅନୁରୋଧ ଅପରିବର୍ତ୍ତିତ ହୋଇଯାଏ।

ଟୁଲ୍-ଫଳାଫଳ ଜାରିରଖିବା ଉପରେ, OmniRoute ଏକଜେକ୍ୟୁଶନ୍ ମଧ୍ୟ ବନ୍ଦ କରେ ଯେତେବେଳେ କ୍ରମାଗତ ଦୁଇଟି ସମାପ୍ତ ରାଉଣ୍ଡ ସମାନ ଉପକରଣ କଲ୍ କୁ ଅପରିବର୍ତ୍ତିତ ଫଳାଫଳ ସହିତ ପୁନରାବୃତ୍ତି କରେ, କିମ୍ବା ଯେତେବେଳେ କ୍ରମାଗତ ଦୁଇଟି ରାଉଣ୍ଡରେ ପ୍ରତ୍ୟେକ ସ୍ପଷ୍ଟ ଭାବରେ ଚିହ୍ନିତ ଫଳାଫଳ ବିଫଳ ହେଲା। ପରିବର୍ତ୍ତିତ ଫଳାଫଳ ବାରମ୍ବାର କଲ୍ ଅନୁମତି ଦେଇଥାଏ (ଉଦାହରଣ ସ୍ୱରୂପ, ମତଦାନ)। ରାକ୍ଷୀ ଏକ ନୂତନ ଉପଭୋକ୍ତା ଅନୁରୋଧ ଉପରେ ପୁନ res ସେଟ୍ କରେ, ସମାନ୍ତରାଳ କଲ୍ଗୁଡ଼ିକୁ ଗୋଟିଏ ରାଉଣ୍ଡରେ ଗୋଷ୍ଠୀ କରେ, ଏବଂ Anthropic, ଚାଟ୍ ସମାପ୍ତି, ପ୍ରତିକ୍ରିୟା ଏବଂ Gemini ଇତିହାସକୁ ସମର୍ଥନ କରେ। ଯୋଜନାକାରୀ ଏହାର କାରଣ ଗ୍ରହଣ କରନ୍ତି ଏବଂ ଅନ୍ୟ ଏକ ଟୁଲ୍ ରାଉଣ୍ଡ ଅନୁରୋଧ କଲେ ମଧ୍ୟ ଅନ୍ତିମ ଉତ୍ତରର ମାଲିକ ଅଟନ୍ତି।

ଦ୍ୱିତୀୟ ଟାର୍ଗେଟ୍ ପରେ ଅତିରିକ୍ତ ମଡେଲଗୁଡିକ ନିର୍ବାହୀ ବ୍ୟାକଅପ୍ ଅର୍ଡର ହୋଇଛି। ଏକ ବିଫଳ HTTP ପ୍ରତିକ୍ରିୟା କିମ୍ବା ପରିବହନ ବ୍ୟତିକ୍ରମ ପରବର୍ତ୍ତୀ କାର୍ଯ୍ୟନିର୍ବାହୀକୁ ଅଗ୍ରଗତି କରେ, ସମାନ ଯୋଜନାକାରୀ ନିଷ୍ପତ୍ତି ଏବଂ ଦେଶୀ ଉପକରଣଗୁଡ଼ିକୁ ବହନ କରେ କିନ୍ତୁ ସେହି ନିର୍ବାହକଙ୍କ ନିଜସ୍ୱ ଷ୍ଟେପ୍ ପ୍ରମ୍ପ୍ଟ ଏବଂ ସଂଯୋଗ ସମାଧାନ ହେଲା। ପ୍ରଥମ ସଫଳ ପ୍ରତିକ୍ରିୟା SSE ଷ୍ଟ୍ରିମିଂ ସହିତ ଅପରିବର୍ତ୍ତିତ ଭାବରେ ଫେରି ଆସେ। ଏକ ସଫଳ ଷ୍ଟ୍ରିମ୍ ଆରମ୍ଭ ହେବା ପରେ ବିଫଳତା ଏଠାରେ ପୁନ ry ଚେଷ୍ଟା କରାଯାଇପାରିବ ନାହିଁ। ଯଦି ସମସ୍ତ ନିର୍ବାହକାରୀ ବିଫଳ ହୁଅନ୍ତି, ଶେଷ ବିଫଳତା ଫେରସ୍ତ ହେବ। ଗ୍ରାହକ ଗର୍ଭପାତ ବନ୍ଦ କରିବା ବନ୍ଦ କରନ୍ତି।

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

ଏକ ପ୍ରତିକ୍ରିୟାରେ କାର୍ଯ୍ୟନିର୍ବାହୀ ଏକାଧିକ ସ୍ independent ାଧୀନ କଲ୍ ନିର୍ଗତ କରିପାରନ୍ତି। ପରବର୍ତ୍ତୀ କ୍ଲାଏଣ୍ଟ ଟୁଲ୍-ଫଳାଫଳ ଟର୍ନରେ ନିର୍ଭରଶୀଳ କଲ୍ ଗୁଡିକ ନିୟନ୍ତ୍ରଣ କରାଯାଏ, ଯୋଜନାକାରୀ ପ୍ରତ୍ୟେକ ଫଳାଫଳକୁ ସମୀକ୍ଷା କରନ୍ତି। `maxToolRounds` ଡିଫଲ୍ଟ `8` ଏବଂ `1`-`32` ଗ୍ରହଣ କରେ; ଥରେ ପହଞ୍ଚିବା ପରେ, ଯୋଜନାକାରୀ ସର୍ବୋତ୍ତମ ଉପଲବ୍ଧ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ଉତ୍ପାଦନ କରିବା ଜରୁରୀ। ଆଭ୍ୟନ୍ତରୀଣ ଯୋଜନାକାରୀ ନିଷ୍ପତ୍ତିଗୁଡିକ ବଫର୍ କରାଯାଏ, ଯେତେବେଳେ ମନୋନୀତ କ୍ଲାଏଣ୍ଟ-ମୁହାଁ ପ୍ରତିକ୍ରିୟା ମୂଳ ଷ୍ଟ୍ରିମିଂ ପସନ୍ଦକୁ ସଂରକ୍ଷଣ କରେ।

### `round-robin` ଷ୍ଟିକି ବ୍ୟାଚ୍ ଏବଂ ଆକାଉଣ୍ଟ୍ ବିସ୍ତାର।

ରାଉଣ୍ଡ-ରୋବିନ୍ ବ୍ୟାଚ୍ ହୋଇଛି, ପ୍ରତି-ପ୍ରତି-ଅନୁରୋଧ ନୁହେଁ:

- `stickyRoundRobinLimit` (କମ୍ବୋ ବିନ୍ୟାସ, ତାପରେ `comboStickyRoundRobinLimit`, ତାପରେ `settings.stickyRoundRobinLimit`, ଡିଫଲ୍ଟ।**3** ) ଘୂର୍ଣ୍ଣନ କରିବା ପୂର୍ବରୁ କ୍ରମାଗତ ଅନେକ ସଫଳତା ପାଇଁ ସମାନ ଲକ୍ଷ୍ୟ ରଖେ। ଗୋଟିଏ ଅନୁରୋଧ ଘୂର୍ଣ୍ଣନ ପାଇଁ କମ୍ବୋକୁ `1` ରେ ଓଭରବାଇଡ୍ ସେଟ୍ କରନ୍ତୁ। କମ୍ବୋ ଏଡିଟର୍ ପ୍ରଭାବଶାଳୀ ମୂଲ୍ୟ ଏବଂ କେଉଁ ସ୍ତରରୁ ଆସିଛି ତାହା ଦର୍ଶାଏ।
- `connectionAwareExpansion` (କମ୍ବୋ ବିନ୍ୟାସ, ତାପରେ ସେଟିଂସମୂହ, ଡିଫଲ୍ଟ।**ମିଥ୍ୟା** ) ପ୍ରତ୍ୟେକ ପ୍ରଦାନକାରୀ-ସ୍ତରର ପଦକ୍ଷେପକୁ ଘୂର୍ଣ୍ଣନ ପୂର୍ବରୁ ପ୍ରତି-ଆକାଉଣ୍ଟ ଟାର୍ଗେଟରେ ବିସ୍ତାର କରେ। ଗ୍ରୁପ୍-ବି ରଣନୀତି (ପ୍ରାଥମିକତା, ଓଜନ, ରାଉଣ୍ଡ-ରୋବିନ୍, ରାଣ୍ଡମ୍, p2c, ସର୍ବନିମ୍ନ ବ୍ୟବହୃତ, ମୂଲ୍ୟ-ଅପ୍ଟିମାଇଜ୍, lkgp, ଫିଲ୍-ପ୍ରଥମ, କଠୋର-ରାଣ୍ଡମ, ପ୍ରସଙ୍ଗ-ଅପ୍ଟିମାଇଜ୍, କ୍ୟାଚ୍-ଅପ୍ଟିମାଇଜ୍, ପ୍ରସଙ୍ଗ-ରିଲେ, ଫ୍ୟୁଜନ୍, ପାଇପଲାଇନ) ଏହା ନହେବା ପର୍ଯ୍ୟନ୍ତ ଏକ ପ୍ରଦାନକାରୀ ସ୍ତରର ଦୃଶ୍ୟ ରଖେ। କମ୍ବୋ ଏଡିଟର୍ ଉତ୍ତରାଧିକାରୀ / ଅନ / ଅଫ୍ ପ୍ରକାଶ କରେ; ଉତ୍ତରାଧିକାରୀ ଗ୍ଲୋବାଲ୍ ଡିଫଲ୍ଟ (ଅଫ୍) ବ୍ୟବହାର କରେ।
- ପ୍ରମ୍ପ୍ଟ-କ୍ୟାଚ୍ ଲୋକାଲ୍ ରାଉଟିଙ୍ଗ୍ (`promptCacheAffinityEnabled`, ଡିଫଲ୍ଟ।**ସତ** ) ପିନ୍ ହୋଇଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ପୁନ order ରେକର୍ଡ କରେ ତେଣୁ ମେଳ ଖାଉଥିବା କ୍ୟାଚ୍ କିଗୁଡ଼ିକ ଗୋଟିଏ ଆକାଉଣ୍ଟରେ ରହିଥାଏ। ଏହା ପ୍ରତି-ଆକାଉଣ୍ଟ୍ ପଦାଙ୍କରେ ରାଉଣ୍ଡ-ରୋବିନ ଏବଂ ଓଜନିଆ ଘୂର୍ଣ୍ଣନ ଉପରେ ପ୍ରାଧାନ୍ୟ ଦେଇଥାଏ। ଯଦି ଆପଣ କଠୋର ଘୂର୍ଣ୍ଣନ ଆବଶ୍ୟକ କରନ୍ତି ସେଟିଂସମୂହ → କମ୍ବୋ ଡିଫଲ୍ଟ ଅଧୀନରେ ଏହାକୁ ବନ୍ଦ କରନ୍ତୁ। କ per ଣସି କମ୍ବୋ ଓଭରବ୍ରିଡ୍ ନାହିଁ।

ଗୋଟିଏ ମଡେଲରେ ମଲ୍ଟି ଆକାଉଣ୍ଟ୍ ଘୂର୍ଣ୍ଣନ ପାଇଁ, ପସନ୍ଦ କରନ୍ତୁ।**ଗୋଟିଏ ଡାଇନାମିକ୍ ଆକାଉଣ୍ଟ୍ ଷ୍ଟେପ୍।** (ଖାଲି `connectionId`, ପୁରା ପୁଲ୍) ଷ୍ଟିକି ସୀମା `1` ସହିତ, ତିନୋଟି ପିନ୍ ହୋଇଥିବା `connectionId` s ନୁହେଁ। RR କାଉଣ୍ଟର ଅଗ୍ରଗତି କଲାବେଳେ ସମାନ ଆକାଉଣ୍ଟରେ ପିନଡ୍ ଷ୍ଟେପ୍ ଏବଂ ଆଫିନିଟି ଭୁଶୁଡ଼ି ପଡ଼େ।

## ଫ୍ୟୁଜନ୍ କୌଶଳ

`fusion` ହେଉଛି ଏକମାତ୍ର କୌଶଳ ଯାହା ଗୋଟିଏ ଲକ୍ଷ୍ୟ ଚୟନ କରେ **ନାହିଁ**। ଏହା ପ୍ରମ୍ପ୍ଟକୁ
**ପ୍ରତ୍ୟେକ ପ୍ୟାନେଲ୍ ମଡେଲ୍‌କୁ ସମାନ୍ତରାଳ ଭାବରେ** ପଠାଏ, ତା'ପରେ ଏକ ବିନ୍ୟାସଯୋଗ୍ୟ **ବିଚାରକ ମଡେଲ୍**
ସମସ୍ତ ପ୍ୟାନେଲ୍ ପ୍ରତିକ୍ରିୟାରୁ ଗୋଟିଏ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ସଂଶ୍ଳେଷଣ କରେ। ଏହାକୁ ଅପ୍‌ଷ୍ଟ୍ରିମ୍ `decolua/9router`
(OpenRouterର Fusion ଡିଜାଇନ୍)ରୁ ପୋର୍ଟ କରାଯାଇଛି; ଏହାର କାର୍ଯ୍ୟାନ୍ୱୟନ `open-sse/services/fusion.ts`ରେ ଅଛି।

ଏହା କିପରି କାମ କରେ:

0. **ଟୁଲ୍-ଯୁକ୍ତ ବାଇପାସ୍** — ଏକ ଅନୁରୋଧରେ ଖାଲି ନଥିବା `tools` ଆରେ ଥିଲେ ଏବଂ
   `tool_choice` ସ୍ପଷ୍ଟ ଭାବରେ `"none"` ନଥିଲେ, ଏହା ପ୍ୟାନେଲ୍‌କୁ ସମ୍ପୂର୍ଣ୍ଣ ଏଡ଼ାଇଯାଏ: ଏହା ସିଧାସଳଖ
   ଗୋଟିଏ ମଡେଲ୍‌କୁ (ବିନ୍ୟାସିତ ବିଚାରକ କିମ୍ବା `panel[0]`) ରୂଟ୍ ହୁଏ ଏବଂ `tools`/`tool_choice`
   କୌଣସି ପରିବର୍ତ୍ତନ ବିନା ପଠାଯାଏ। ପ୍ୟାନେଲ୍ ସଦସ୍ୟମାନଙ୍କ ପାଖରେ ଟୁଲ୍ ଆକ୍ସେସ୍ ନଥାଏ ଏବଂ ବିଚାରକର
   ସଂଶ୍ଳେଷଣ ନିର୍ଦ୍ଦେଶ ଟୁଲ୍-କଲ୍ ନିର୍ଗମନକୁ ନିରୁତ୍ସାହିତ କରେ, ତେଣୁ ଏଜେଣ୍ଟିକ୍/ଟୁଲ୍-କଲିଂ କ୍ଲାଏଣ୍ଟମାନେ
   ସଂଶ୍ଳେଷିତ ଗଦ୍ୟ ପରିବର୍ତ୍ତେ ଏକ ପ୍ରକୃତ ଟୁଲ୍-କଲ୍ ନିଷ୍ପତ୍ତି ପାଆନ୍ତି (#6771)।
1. **ଫ୍ୟାନ୍-ଆଉଟ୍** (କେବଳ ଟୁଲ୍-ବିହୀନ ଅନୁରୋଧ) — ପ୍ରମ୍ପ୍ଟଟିକୁ ଏକାସାଙ୍ଗରେ ପ୍ରତ୍ୟେକ ପ୍ୟାନେଲ୍
   ମଡେଲ୍‌କୁ ପଠାଯାଏ, ଟୁଲ୍‌ଗୁଡ଼ିକୁ ବାଦ ଦେଇ ବାଧ୍ୟତାମୂଳକ ଭାବେ ନନ୍-ଷ୍ଟ୍ରିମିଂ କରାଯାଏ (ସଂଶ୍ଳେଷଣ ପାଇଁ
   ବିଚାରକକୁ ସମ୍ପୂର୍ଣ୍ଣ ଗଦ୍ୟ ଆବଶ୍ୟକ)।
2. **କୋରମ୍-ଗ୍ରେସ୍ ସଂଗ୍ରହ** — `minPanel`ଟି ଉତ୍ତର ପହଞ୍ଚିବା ମାତ୍ରେ ପଛରେ ପଡ଼ିଥିବା
   ମଡେଲ୍‌ଗୁଡ଼ିକ ପାଇଁ ଏକ ସ୍ୱଳ୍ପ ଗ୍ରେସ୍ ଟାଇମର୍ ଆରମ୍ଭ ହୁଏ, ତା'ପରେ ଯାହା ସଂଗ୍ରହ ହୋଇଛି ତାହା ସହିତ
   ଫ୍ୟୁଜନ୍ ଆଗକୁ ବଢ଼େ। ଏହା ୱାଲ୍ ଟାଇମ୍‌ରେ ସବୁଠାରୁ ଧୀର ମଡେଲ୍‌ର ବିଳମ୍ବ ପ୍ରଭାବକୁ ସୀମିତ କରେ,
   ଯାହା ଏକ ହାର୍ଡ ଟାଇମ୍‌ଆଉଟ୍‌ରେ ବାନ୍ଧିତ।
3. **ବିଚାରକ ସଂଶ୍ଳେଷଣ** — ପ୍ୟାନେଲ୍ ଉତ୍ତରଗୁଡ଼ିକୁ ଅଜ୍ଞାତକୃତ କରାଯାଏ (`Source 1`, `Source 2`, … — ଯାହାଦ୍ୱାରା
   ବିଚାରକ ମଡେଲ୍ ବ୍ରାଣ୍ଡ ପରିବର୍ତ୍ତେ ବିଷୟବସ୍ତୁକୁ ଗୁରୁତ୍ୱ ଦିଏ) ଏବଂ ବିଚାରକକୁ ଦିଆଯାଏ, ଯିଏ
   ସହମତି / ବିରୋଧାଭାସ / ଆଂଶିକ ପରିସର / ଅନନ୍ୟ ଅନ୍ତର୍ଦୃଷ୍ଟି / ଅଦୃଶ୍ୟ ଦିଗଗୁଡ଼ିକୁ ବିଶ୍ଳେଷଣ କରି,
   **ଗୋଟିଏ** ପ୍ରାମାଣିକ ଉତ୍ତର ଲେଖେ। ବିଚାରକ କଲ୍ କ୍ଲାଏଣ୍ଟର ମୂଳ `stream` ଫ୍ଲାଗ୍ + ଟୁଲ୍‌ଗୁଡ଼ିକୁ
   ଅପରିବର୍ତ୍ତିତ ରଖେ, ଫଳରେ ଷ୍ଟ୍ରିମିଂ ଏବଂ ଡାଉନ୍‌ଷ୍ଟ୍ରିମ୍ ଟୁଲ୍ ବ୍ୟବହାର ଏବେ ମଧ୍ୟ କାମ କରେ।
4. **ସୁଗମ ଅବନତି** — 0ଟି ପ୍ୟାନେଲ୍ ଉତ୍ତର → `503`; ଠିକ୍ 1ଟି ଉତ୍ତର ରହିଲେ → ସେହି ଉତ୍ତର
   ସିଧାସଳଖ ଫେରାଯାଏ (ସଂଯୋଜନ କରିବାକୁ କିଛି ନାହିଁ); ଗୋଟିଏ-ମଡେଲ୍ ପ୍ୟାନେଲ୍ ସିଧାସଳଖ ଉତ୍ତର ଦିଏ।

ଜଣେ ପ୍ୟାନେଲ୍ ସଦସ୍ୟ ଅନ୍ୟ ଏକ କମ୍ବୋକୁ ସନ୍ଦର୍ଭ କରୁଥିବା `combo-ref` ପଦକ୍ଷେପ
(`{kind: "combo-ref", comboName: "..."}`) ମଧ୍ୟ ହୋଇପାରେ — ଏହା **ଗୋଟିଏ ବ୍ଲାକ୍-ବକ୍ସ ପ୍ୟାନେଲ୍ ସ୍ୱର** ଭାବେ
ସମାଧାନ ହୁଏ (ସନ୍ଦର୍ଭିତ କମ୍ବୋର ନିଜସ୍ୱ ଲକ୍ଷ୍ୟଗୁଡ଼ିକର ଫ୍ୟାନ୍-ଆଉଟ୍ ନୁହେଁ, ବରଂ ସେହି କମ୍ବୋ ମଧ୍ୟକୁ
ଏକ ସମ୍ପୂର୍ଣ୍ଣ ପୁନରାବୃତ୍ତିଶୀଳ ଡିସ୍ପାଚ୍), ଏବଂ ଏଥିରେ ପୂର୍ବରୁ ଅନ୍ୟ ସମସ୍ତ combo-ref-ବ୍ୟବହାରକାରୀ
କୌଶଳ ବ୍ୟବହାର କରୁଥିବା ସମାନ ଗଭୀରତା/ଚକ୍ର ସୁରକ୍ଷା ରହିଛି (#6764)।

| `config.fusionTuning.minPanel`           | `number` | `2`                  | ଗ୍ରେସ୍ ଟାଇମର୍ ଆରମ୍ଭ ହେବା ପୂର୍ବରୁ ଆବଶ୍ୟକ ସଫଳ ଉତ୍ତର ସଂଖ୍ୟା (`[2, panelSize]`ରେ ସୀମିତ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`               | କୋରମ୍ ପୂରଣ ହେବା ପରେ ପଛରେ ପଡ଼ିଥିବା ମଡେଲ୍‌ଗୁଡ଼ିକ ପାଇଁ କେତେ ସମୟ ଅପେକ୍ଷା କରାଯିବ         |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`              | ଗୋଟିଏ ଅଟକିଥିବା ମଡେଲ୍ ଯେପରି ଅନୁରୋଧକୁ ଅଟକାଇ ନପାରେ, ସେଥିପାଇଁ ସର୍ବାଧିକ ସମୟସୀମା          |

ଡିଫଲ୍ଟଗୁଡ଼ିକ `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)ରେ ରହିଛି।

## ଭର୍ଚୁଆଲ୍ ଅଟୋ-କମ୍ବୋ ଫ୍ୟାକ୍ଟରୀ

ଅଟୋ କମ୍ବୋ ଇଞ୍ଜିନ୍‌କୁ ପୂର୍ବ-ନିର୍ଦ୍ଧାରିତ କମ୍ବୋ ଆବଶ୍ୟକ ହୁଏ ନାହିଁ। ଏହା ପରିବର୍ତ୍ତେ, `open-sse/services/autoCombo/virtualFactory.ts` ତତ୍କ୍ଷଣାତ୍ ପ୍ରାର୍ଥୀଗୁଡ଼ିକ ତିଆରି କରେ:

1. `getProviderConnections({ isActive: true })` (ସମସ୍ତ ସକ୍ରିୟ ସଂଯୋଗ) ଆଣେ
2. ବୈଧ ପ୍ରମାଣପତ୍ର ଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ଫିଲ୍ଟର୍ କରେ (API କୀ କିମ୍ବା `hasUsableOAuthToken()` ମାଧ୍ୟମରେ ମିଆଦ ଶେଷ ହୋଇନଥିବା OAuth ଟୋକେନ୍)
3. ମଡେଲ୍ ଉପଲବ୍ଧତା + ମୂଲ୍ୟ ନିର୍ଦ୍ଧାରଣ ପାଇଁ `getProviderRegistry()` ସହିତ କ୍ରସ୍-ରେଫରେନ୍ସ କରେ
4. ପ୍ରତ୍ୟେକ `(provider, model, connection)` ଟ୍ୟୁପଲ୍ ପାଇଁ ଏକ `VirtualAutoComboCandidate` ତିଆରି କରେ
5. ଡିସ୍ପାଚ୍ ଲକ୍ଷ୍ୟ ଭାବରେ `connection.defaultModel` (କିମ୍ବା ରେଜିଷ୍ଟ୍ରିର ପ୍ରଥମ ମଡେଲ୍) ବାଛେ
6. 16-ଫ୍ୟାକ୍ଟର୍ `scorePool()` ଏବଂ ଭାରିଆଣ୍ଟର ୱେଟ୍ ପ୍ୟାକ୍ ବ୍ୟବହାର କରି ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ ସ୍କୋର୍ କରେ
7. `handleComboChat()` ପାଇଁ ଫଳସ୍ୱରୂପ ମିଳିଥିବା ଇନ୍-ମେମୋରୀ `AutoComboConfig` ଫେରାଏ — ଏହା କେବେବି DBରେ ସ୍ଥାୟୀ ଭାବରେ ସଂରକ୍ଷିତ ହୁଏ ନାହିଁ

ଏହାର ଅର୍ଥ ହେଉଛି **`auto/*` ସକ୍ରିୟ ଥିବା ଏକ ନୂଆ ପ୍ରଦାନକାରୀ ଯୋଡ଼ିଲେ ପ୍ରାର୍ଥୀ ପୁଲ୍ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ବିସ୍ତାରିତ ହୁଏ** — ମାନୁଆଲ୍ କମ୍ବୋ ସମ୍ପାଦନା ଆବଶ୍ୟକ ନୁହେଁ। ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ଭର୍ଚୁଆଲ୍ କମ୍ବୋ ପୁନଃନିର୍ମାଣ ହୁଏ, ତେଣୁ ନୂତନ ଭାବେ ଯୋଡ଼ାଯାଇଥିବା କିମ୍ବା ନୂତନ ଭାବେ ସୁସ୍ଥ ହୋଇଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ତୁରନ୍ତ ବାଛାଯାଏ।

## ସ୍ୱୟଂ-ପୁନରୁଦ୍ଧାର

- **ଅସ୍ଥାୟୀ ବହିଷ୍କାର**: ସ୍କୋର୍ < 0.2 → 5 ମିନିଟ୍ ପାଇଁ ବହିଷ୍କୃତ (କ୍ରମବର୍ଦ୍ଧିଷ୍ଣୁ ବ୍ୟାକ୍‌ଅଫ୍, ସର୍ବାଧିକ 30 ମିନିଟ୍)
- **ସର୍କିଟ୍ ବ୍ରେକର୍ ସଚେତନତା**: OPEN → ସ୍ୱୟଂଚାଳିତ ଭାବରେ ବହିଷ୍କୃତ; HALF_OPEN → ପ୍ରୋବ୍ ଅନୁରୋଧ
- **ଘଟଣା ମୋଡ୍**: >50% OPEN → ଅନ୍ୱେଷଣ ଅକ୍ଷମ କରି ସ୍ଥିରତାକୁ ସର୍ବାଧିକ କରେ
- **କୁଲ୍‌ଡାଉନ୍ ପୁନରୁଦ୍ଧାର**: ବହିଷ୍କାର ପରେ, ପ୍ରଥମ ଅନୁରୋଧଟି ହ୍ରାସକୃତ ଟାଇମ୍‌ଆଉଟ୍ ସହିତ ଏକ "ପ୍ରୋବ୍" ହୁଏ

## ବ୍ୟାଣ୍ଡିଟ୍ ଅନ୍ୱେଷଣ

5% ଅନୁରୋଧ (ବିନ୍ୟାସଯୋଗ୍ୟ) ଅନ୍ୱେଷଣ ପାଇଁ ଯାଦୃଚ୍ଛିକ ପ୍ରଦାନକାରୀଙ୍କ ନିକଟକୁ ରାଉଟ୍ କରାଯାଏ। ଘଟଣା ମୋଡ୍‌ରେ ଏହା ଅକ୍ଷମ ରହେ।

## API

ଏଠାରେ **କୌଣସି ସ୍ୱତନ୍ତ୍ର `POST /api/combos/auto` ଏଣ୍ଡପଏଣ୍ଟ ନାହିଁ** — Auto-Comboକୁ ଦୁଇଟି ଉପାୟରେ ବ୍ୟବହାର କରାଯାଏ:

1. **ଶୂନ୍ୟ-କନଫିଗ୍ (ସୁପାରିଶକୃତ):** `model: "auto"` କିମ୍ବା `model: "auto/<variant>"` ସହିତ ଯେକୌଣସି ଚାଟ୍ କମ୍ପ୍ଲିସନ୍ ଅନୁରୋଧ ପଠାନ୍ତୁ। ଭର୍ଚୁଆଲ୍ ଫ୍ୟାକ୍ଟରି ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ କମ୍ବୋ ନିର୍ମାଣ କରେ — କୌଣସି ସ୍ଥାୟୀ ସଂରକ୍ଷଣ କିମ୍ବା API କଲ୍ର ଆବଶ୍ୟକତା ନାହିଁ।

2. **`strategy: "auto"` ସହିତ ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ କମ୍ବୋ:** `POST /api/combos` ମାଧ୍ୟମରେ ଏକ ନିୟମିତ କମ୍ବୋ ସୃଷ୍ଟି କରନ୍ତୁ ଏବଂ `config.auto.weights` / `config.auto.candidatePool` ସହିତ `strategy: "auto"` ସେଟ୍ କରନ୍ତୁ। ସମାନ ସ୍କୋରିଂ ଇଞ୍ଜିନ୍ ବ୍ୟବହୃତ ହୁଏ; କମ୍ବୋଟି `combos`ରେ ସଂରକ୍ଷିତ ହୁଏ ଏବଂ ID ଦ୍ୱାରା ପୁନଃବ୍ୟବହାର କରାଯାଇପାରେ।

ଅନ୍ୱେଷଣ ପାଇଁ, `GET /api/combos/auto` ପ୍ରତ୍ୟେକ ଭାରିଆଣ୍ଟକୁ ତାହାର ସମାଧାନ ହୋଇଥିବା ପ୍ରାର୍ଥୀ ପୁଲ୍ ସହିତ, ଏବଂ `context_length` / `max_output_tokens` — ପ୍ରାର୍ଥୀ ପୁଲ୍ର ୱିଣ୍ଡୋଗୁଡ଼ିକ ମଧ୍ୟରୁ ସର୍ବାଧିକ ମୂଲ୍ୟ — ତାଲିକାଭୁକ୍ତ କରେ। କ୍ଲାଏଣ୍ଟଗୁଡ଼ିକୁ (ଉଦାହରଣସ୍ୱରୂପ opencode ପ୍ଲଗଇନ୍) `0` ପରିବର୍ତ୍ତେ ଏହି ମୂଲ୍ୟଗୁଡ଼ିକ ପ୍ରଚାର କରିବା ଆବଶ୍ୟକ: ଶୂନ୍ୟ କଣ୍ଟେକ୍ସ୍ଟ opencodeର ସ୍ୱୟଂଚାଳିତ କମ୍ପାକ୍ସନ୍କୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ଅକ୍ଷମ କରିଦିଏ, ଫଳରେ ଗେଟୱେର ହିଷ୍ଟ୍ରି ପର୍ଜ୍ କଣ୍ଟେକ୍ସ୍ଟକୁ ନଷ୍ଟ କରିବା ପର୍ଯ୍ୟନ୍ତ ସେସନ୍ଗୁଡ଼ିକ ବଢ଼ିଚାଲେ। ସର୍ବାଧିକ ମୂଲ୍ୟ ପ୍ରଚାର କରିବା ସୁରକ୍ଷିତ, କାରଣ auto-combo କଣ୍ଟେକ୍ସ୍ଟ ପ୍ରି-ଫିଲ୍ଟର୍ ଅତ୍ୟଧିକ ବଡ଼ ଅନୁରୋଧଗୁଡ଼ିକୁ ବଡ଼-ୱିଣ୍ଡୋ ପ୍ରାର୍ଥୀମାନଙ୍କ ନିକଟକୁ ରୁଟ୍ କରେ।

```bash
# ଶୂନ୍ୟ-କନଫିଗ୍ ବ୍ୟବହାର (କମ୍ବୋ ସୃଷ୍ଟି ବିନା)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ନିୟମିତ କମ୍ବୋ ଏଣ୍ଡପଏଣ୍ଟ ମାଧ୍ୟମରେ ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ ଅଟୋ କମ୍ବୋ
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ଅଟୋ ରାଉଟର୍ କୌଶଳଗୁଡ଼ିକ

ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ `strategy: "auto"` କମ୍ବୋଗୁଡ଼ିକ `config.routerStrategy` (କିମ୍ବା ପୁରୁଣା
`config.auto.routerStrategy`)କୁ ନିମ୍ନଲିଖିତ ମଧ୍ୟରୁ ଗୋଟିଏରେ ସେଟ୍ କରିପାରିବେ:

- `rules` — ଡିଫଲ୍ଟ ଭାରିତ ସ୍କୋରିଂ
- `score` — ସର୍ବାଧିକ କନଫିଗର୍ ହୋଇଥିବା ଭାରିତ ସ୍କୋର୍କୁ ଚୟନ କରେ। ସଠିକ୍ ସମାନ ସ୍କୋର୍ କନଫିଗର୍ ହୋଇଥିବା
  ପ୍ରାର୍ଥୀ କ୍ରମକୁ ବଜାୟ ରଖେ; ବିଦ୍ୟମାନ `explorationRate` ସମ୍ପୂର୍ଣ୍ଣ ର୍ୟାଙ୍କ୍ ହୋଇଥିବା ପୁଲ୍ରୁ ନମୁନା ଚୟନ କରେ।
- `cost` / `eco` — ସବୁଠାରୁ ଶସ୍ତା ସୁସ୍ଥ ପ୍ରଦାନକାରୀ
- `latency` / `fast` — ବିଶ୍ୱସନୀୟତା ଦଣ୍ଡ ସହିତ ସର୍ବନିମ୍ନ p95 ବିଳମ୍ବତା
- `sla-aware` / `sla` — p95 ବିଳମ୍ବତା, ତ୍ରୁଟି ହାର ଏବଂ ଇଚ୍ଛାଧୀନ
  ଖର୍ଚ୍ଚ SLOଗୁଡ଼ିକ ପୂରଣ କରୁଥିବା ପ୍ରାର୍ଥୀଙ୍କୁ ପ୍ରାଥମିକତା ଦିଏ
- `lkgp` — ସର୍ବଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରଦାନକାରୀ ପ୍ରଥମେ
- `nadir` — ପୁଲ୍ର କେଉଁ ମଡେଲ୍ର ଆବଶ୍ୟକତା ପ୍ରମ୍ପ୍ଟକୁ ଅଛି, ତାହା [Nadir](https://getnadir.com)ର ନିଷ୍ପତ୍ତି APIକୁ ପଚାରେ;
  ଏହା ଅପ୍ଟ-ଇନ୍ ଏବଂ ବିଫଳ ହେଲେ `rules`କୁ ଖୋଲା ଭାବେ ଫେରେ

### ରାଉଟର୍ କୌଶଳଗୁଡ଼ିକର ବିସ୍ତୃତ ବିବରଣୀ

auto-combo ଇଞ୍ଜିନ୍ 7ଟି ପ୍ଲଗ୍ କରାଯାଇପାରୁଥିବା **RouterStrategy** ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ପ୍ରଦାନ କରେ, ଯାହାକୁ
ଆପଣ `config.routerStrategy` (କିମ୍ବା ପୁରୁଣା `config.auto.routerStrategy`) ମାଧ୍ୟମରେ ବଦଳାଇପାରିବେ।
ପ୍ରତ୍ୟେକ କୌଶଳ ଏକ `RoutingContext` (ଟାସ୍କ ପ୍ରକାର, ଟୁଲ୍/ଭିଜନ୍ ସଙ୍କେତ, ଟୋକନ୍ ଆକଳନ, ଇଚ୍ଛାଧୀନ SLA ନୀତି, ଇଚ୍ଛାଧୀନ
ସର୍ବଶେଷ-ଜଣାଶୁଣା-ଭଲ ପ୍ରଦାନକାରୀ) ଆଧାରରେ ପ୍ରାର୍ଥୀ ପୁଲ୍ରୁ ଗୋଟିଏ ପ୍ରଦାନକାରୀ ଚୟନ କରେ।

#### 1. `rules` (ଡିଫଲ୍ଟ) — 16-ଫ୍ୟାକ୍ଟର୍ ଭାରିତ ସ୍କୋରିଂ

ବିଦ୍ୟମାନ ସ୍କୋରିଂ ଇଞ୍ଜିନ୍କୁ ଆବୃତ କରେ। `OPEN` ସର୍କିଟ୍-ବ୍ରେକର୍
ପ୍ରାର୍ଥୀମାନଙ୍କୁ ବାଦ ଦିଏ, ତାପରେ ବର୍ତ୍ତମାନର ଟାସ୍କ ପ୍ରକାର ଏବଂ `getTaskFitness()` ସହିତ `scorePool()` ଚଲାଇ,
ସର୍ବାଧିକ ସ୍କୋର୍ ପାଇଥିବା ପ୍ରଦାନକାରୀକୁ ଚୟନ କରେ।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ଡିଫଲ୍ଟ। ସମସ୍ତ ସଙ୍କେତ ମଧ୍ୟରେ ଏକ ସନ୍ତୁଳିତ ସମନ୍ୱୟ ଚାହୁଁଥିଲେ ବ୍ୟବହାର କରନ୍ତୁ।

**ଉପନାମ**: `rules` (କୌଣସି ଉପନାମ ନାହିଁ)

---

#### 2. `cost` / `eco` — ସବୁଠାରୁ ଶସ୍ତା ସୁସ୍ଥ ପ୍ରଦାନକାରୀ

ପ୍ରାର୍ଥୀ ପୁଲ୍କୁ `costPer1MTokens` (ଆରୋହୀ କ୍ରମରେ) ଅନୁସାରେ ସଜାଇ ସବୁଠାରୁ ଶସ୍ତାଟିକୁ ଚୟନ କରେ।
ପ୍ରଥମେ `OPEN` ପ୍ରାର୍ଥୀମାନଙ୍କୁ ବାଦ ଦିଏ।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ଖର୍ଚ୍ଚ-ସମ୍ବେଦନଶୀଳ ୱର୍କଲୋଡ୍, ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ କିମ୍ବା ବ୍ୟାକଗ୍ରାଉଣ୍ଡ ଜବ୍ଗୁଡ଼ିକ ପାଇଁ।

**ଉପନାମଗୁଡ଼ିକ**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ବିଶ୍ୱସନୀୟତା ଦଣ୍ଡ ସହିତ ସର୍ବନିମ୍ନ p95 ବିଳମ୍ବତା

`p95LatencyMs + (errorRate * 1000)` ଅନୁସାରେ ସଜାଏ। ତ୍ରୁଟି-ହାର ଦଣ୍ଡ ଏହା ସୁନିଶ୍ଚିତ କରେ ଯେ,
ଅବିଶ୍ୱସନୀୟ ପ୍ରଦାନକାରୀଙ୍କ ନାମମାତ୍ର ବିଳମ୍ବତା କମ୍ ଥିଲେ ମଧ୍ୟ ସେମାନଙ୍କୁ ନିମ୍ନ ସ୍ଥାନ ଦିଆଯାଏ।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ରିଅଲ୍-ଟାଇମ୍ ଚାଟ୍, ଅଟୋକମ୍ପ୍ଲିଟ୍ କିମ୍ବା
ଇଣ୍ଟରଆକ୍ଟିଭ୍ କୋଡିଂ ସହାୟକ ଭଳି ବିଳମ୍ବତା-ସମ୍ବେଦନଶୀଳ ୱର୍କଲୋଡ୍ ପାଇଁ।

**ଉପନାମଗୁଡ଼ିକ**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ବିଳମ୍ବତା/ତ୍ରୁଟି/ଖର୍ଚ୍ଚ SLO ଅନୁପାଳନ

କନଫିଗର୍ ହୋଇଥିବା SLO ନୀତିକୁ ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ କେତେ ଭଲ ଭାବେ ପୂରଣ କରେ, ସେହି ଆଧାରରେ ସ୍କୋର୍ କରେ:

| କାରକ             | ଓଜନ | ସୂତ୍ର                                                 |
| ---------------- | --- | ----------------------------------------------------- |
| ଲେଟେନ୍ସି ସ୍କୋର୍  | 35% | `threshold / max(value, ε)`                           |
| ତ୍ରୁଟି ସ୍କୋର୍    | 35% | `threshold / max(value, ε)`                           |
| ସ୍ୱାସ୍ଥ୍ୟ ସ୍କୋର୍ | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)     |
| ଖର୍ଚ୍ଚ ସ୍କୋର୍    | 10% | `threshold / max(value, ε)` କିମ୍ବା ବିପରୀତ ସାମାନ୍ୟୀକୃତ |
| ସ୍ଥିରତା ସ୍କୋର୍   | 5%  | ବିପରୀତ ସାମାନ୍ୟୀକୃତ ଲେଟେନ୍ସି ମାନକ ବିଚ୍ୟୁତି             |

ଯେତେବେଳେ `hardConstraints: true` ଥାଏ, ପ୍ରାର୍ଥୀମାନଙ୍କୁ ପ୍ରଥମେ **ଉଲ୍ଲଂଘନ ସ୍କୋର୍**
(ସେମାନେ କୌଣସି SLOକୁ କେତେ ଅତିକ୍ରମ କରନ୍ତି) ଏବଂ ତା’ପରେ ସଂଯୁକ୍ତ ସ୍କୋର୍ ଅନୁସାରେ
ସଜାଯାଏ। ଅନ୍ୟଥା, କେବଳ ସଂଯୁକ୍ତ ସ୍କୋର୍ ବ୍ୟବହୃତ ହୁଏ।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ନୀତି ଅନୁସାରେ ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀଙ୍କ ସ୍କୋର୍ ନିର୍ଣ୍ଣୟ କରେ: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ଫିଲ୍ଡଗୁଡ଼ିକ** (କମ୍ବୋ କନଫିଗ୍ରେ ସେଟ୍ କରନ୍ତୁ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**କେତେବେଳେ ବ୍ୟବହାର କରିବେ**: କଠୋର ଲେଟେନ୍ସି, ତ୍ରୁଟି-ହାର କିମ୍ବା ଖର୍ଚ୍ଚ ବଜେଟ୍ ଥିବା ପ୍ରଡକ୍ସନ୍ ୱାର୍କଲୋଡ୍ ପାଇଁ।

**ଉପନାମଗୁଡ଼ିକ**: `sla-aware`, `sla`

#### 5. `lkgp` — ଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରଦାତା ପ୍ରଥମେ

ପ୍ରଥମେ **ଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରଦାତାଙ୍କୁ** (ଯଦି ସେଟ୍ ହୋଇଥାଏ) ଚେଷ୍ଟା କରେ, ତା’ପରେ
`rules` ରଣନୀତିକୁ ଫଲ୍ବ୍ୟାକ୍ କରେ। ସେସନ୍ ସ୍ଥିରତା ପାଇଁ ଏହା ଉପଯୋଗୀ — ଏକେ ପ୍ରଦାତା
କଥୋପକଥନର ପରବର୍ତ୍ତୀ ଅନୁରୋଧଗୁଡ଼ିକ ପରିଚାଳନା କରନ୍ତି।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules ରଣନୀତିକୁ ଫଲ୍ବ୍ୟାକ୍ କରନ୍ତୁ
    return getStrategy("rules").select(pool, context);
  }
}
```

**କେତେବେଳେ ବ୍ୟବହାର କରିବେ**: ଯେଉଁ ମଲ୍ଟି-ଟର୍ଣ୍ଣ କଥୋପକଥନରେ ଆପଣ ଏକେ ପ୍ରଦାତାଙ୍କ ଦ୍ୱାରା
ପରବର୍ତ୍ତୀ ଅନୁରୋଧଗୁଡ଼ିକ ପରିଚାଳିତ କରାଇବାକୁ ଚାହାନ୍ତି (ଯେପରିକି କ୍ୟାସିଂ, ପ୍ରସଙ୍ଗ ନିରନ୍ତରତା କିମ୍ବା ମୂଲ୍ୟ ସ୍ଥିରତା ପାଇଁ)।

**ଉପନାମ**: `lkgp` (କୌଣସି ଉପନାମ ନାହିଁ)

#### 6. `nadir` — Nadir ମାଧ୍ୟମରେ ପ୍ରମ୍ପ୍ଟ-ସଚେତନ ମଡେଲ୍ ଚୟନ

ଉପରୋକ୍ତ ପ୍ରତ୍ୟେକ ରଣନୀତି ନିଜସ୍ୱ ଟେଲିମେଟ୍ରି ଆଧାରରେ ପ୍ରାର୍ଥୀମାନଙ୍କୁ କ୍ରମବଦ୍ଧ କରେ; ସେଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସିଟି
ଅନୁରୋଧକୁ ପଢ଼େ ନାହିଁ। `nadir` ଶେଷ ବ୍ୟବହାରକାରୀ ଟର୍ଣ୍ଣ ସହିତ ପୁଲ୍ର ମଡେଲ୍ IDଗୁଡ଼ିକୁ
[Nadir](https://getnadir.com)ର ନିଷ୍ପତ୍ତି API (`POST /v1/bucket`)କୁ ପଠାଏ ଏବଂ ସେହି ତାଲିକାରୁ Nadir
ଚୟନ କରିଥିବା ମଡେଲ୍କୁ ରାଉଟ୍ କରେ (`simple` → ସବୁଠାରୁ ଶସ୍ତା ସକ୍ଷମ ମଡେଲ୍, `complex` → ଫ୍ରଣ୍ଟିୟର୍
ମଡେଲ୍)। ସେହି ମଡେଲ୍କୁ ସେବା ଦେଉଥିବା ସଂଯୋଗ ତଥାପି `rules` ଦ୍ୱାରା ଚୟନ କରାଯାଏ, ତେଣୁ କୋଟା,
ସ୍ୱାସ୍ଥ୍ୟ ଏବଂ ଖର୍ଚ୍ଚ ଆଧାରରେ କେଉଁ ଆକାଉଣ୍ଟ ବ୍ୟବହୃତ ହେବ ତାହା ନିର୍ଦ୍ଧାରିତ ହୋଇଥାଏ।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

ଏହି ଦୁଇଟି ଷ୍ଟ୍ରିଙ୍ଗ୍ ପାଇଁ `OMNIROUTE_NADIR_API_KEY` ଏବଂ `OMNIROUTE_NADIR_BASE_URL` ପରିବେଶ ଫଲ୍ବ୍ୟାକ୍
ଅଟେ। `baseUrl` କେବଳ ସ୍ୱୟଂ-ହୋଷ୍ଟ କରାଯାଇଥିବା Nadir ପାଇଁ ଆବଶ୍ୟକ (ଶେଷରେ ଥିବା `/v1` ଗ୍ରହଣୀୟ)।
କି ବିନା କରାଯାଇଥିବା କଲ୍ଗୁଡ଼ିକ Nadirର ଅଜ୍ଞାତ ଟିଅର୍କୁ ଯାଏ, ଯାହା ପ୍ରତ୍ୟେକ IP ପାଇଁ ରେଟ୍-ଲିମିଟ୍ ହୋଇଥାଏ। ଏକ କି ସହିତ
([ଗୋଟିଏ ସୃଷ୍ଟି କରନ୍ତୁ](https://app.getnadir.com/dashboard/api-keys)), ପ୍ରତ୍ୟେକ ନିଷ୍ପତ୍ତି
ଆପଣଙ୍କ Nadir ଡ୍ୟାସ୍ବୋର୍ଡରେ ଲଗ୍ ହୁଏ। ସମ୍ପୂର୍ଣ୍ଣ ସେଟ୍ଅପ୍ ଏବଂ ଯାଞ୍ଚ:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/)।

ବକ୍ସରୁ ବାହାରକୁ ଯାଉଥିବା ତଥ୍ୟ: ଶେଷ ବ୍ୟବହାରକାରୀ ସନ୍ଦେଶର ପାଠ୍ୟ (ପ୍ରଥମ 16k ଅକ୍ଷର), ପ୍ରାର୍ଥୀ
ମଡେଲ୍ IDଗୁଡ଼ିକ ଏବଂ ଏକ `source: "omniroute"` ଚ୍ୟାନେଲ୍ ଟ୍ୟାଗ୍। କୌଣସି ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ, ଇତିହାସ, ଟୁଲ୍ କିମ୍ବା
ହେଡର୍ ପଠାଯାଏ ନାହିଁ।

ବିଫଳତା ସମୟର ଆଚରଣ ହେଉଛି ଫେଲ୍-ଓପନ୍: ଟାଇମ୍ଆଉଟ୍ (ଡିଫଲ୍ଟ 2000 ms), non-2xx, ପହଞ୍ଚି ହେଉନଥିବା
ହୋଷ୍ଟ, ବିକୃତ ପ୍ରତିକ୍ରିୟା କିମ୍ବା ପୁଲ୍ ବାହାରର ଚୟନ ହେଲେ `rules`
ନିଷ୍ପତ୍ତି ବ୍ୟବହୃତ ହୁଏ ଏବଂ କାରଣର ଆରମ୍ଭରେ `NadirStrategy: fallback (…)` ଯୋଡ଼ାଯାଏ। ଏକ କଲ୍ ବିଫଳ ହେବା ପରେ
ରଣନୀତି 30 s ପର୍ଯ୍ୟନ୍ତ ନେଟ୍ୱର୍କକୁ ଏଡ଼ାଇଯାଏ, ଫଳରେ କୌଣସି ବିଭ୍ରାଟ ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ଗୋଟିଏ ଟାଇମ୍ଆଉଟ୍ ପରିବର୍ତ୍ତେ
ପ୍ରତ୍ୟେକ 30 sରେ ଗୋଟିଏ ଟାଇମ୍ଆଉଟ୍ର ମୂଲ୍ୟ ଦିଏ। କେବଳ Nadir ପ୍ରକୃତରେ
ଚୟନ କରିଥିଲେ ରାଉଟିଂ ଇଭେଣ୍ଟଗୁଡ଼ିକ `strategy: "nadir"` ରିପୋର୍ଟ କରେ।

**କେତେବେଳେ ବ୍ୟବହାର କରିବେ**: ବିଭିନ୍ନ ମଡେଲ୍ ଟିଅର୍ (ଏକ ଛୋଟ, ଏକ ମଧ୍ୟମ
ଏବଂ ଏକ ଫ୍ରଣ୍ଟିୟର୍ ମଡେଲ୍) ଥିବା ପୁଲ୍ରେ ମିଶ୍ରିତ-କଠିନତା ଟ୍ରାଫିକ୍ ପାଇଁ, ଯେଉଁଠାରେ ସବୁବେଳେ ଫ୍ରଣ୍ଟିୟର୍ ମଡେଲ୍ ବ୍ୟବହାରର ଖର୍ଚ୍ଚକୁ ଆପଣ କମାଇବାକୁ ଚାହାନ୍ତି।

**ଉପନାମ**: `nadir` (କୌଣସି ଉପନାମ ନାହିଁ)

### କଷ୍ଟମ୍ ରାଉଟର୍ ରଣନୀତିଗୁଡ଼ିକ

ଆପଣ ସାର୍ବଜନୀନ API ମାଧ୍ୟମରେ ନିଜର `RouterStrategy` ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ପଞ୍ଜୀକୃତ କରିପାରିବେ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ଆପଣଙ୍କ ରାଉଟିଂ ଲଜିକ୍ ଏଠାରେ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ତା’ପରେ ଏହାକୁ ବ୍ୟବହାର କରନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## କାର୍ଯ୍ୟ ଉପଯୁକ୍ତତା

6ଟି କାର୍ଯ୍ୟ ପ୍ରକାର (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) ମଧ୍ୟରେ 30+ ମଡେଲ୍‌କୁ ସ୍କୋର୍ କରାଯାଇଛି। ୱାଇଲ୍ଡକାର୍ଡ ପ୍ୟାଟର୍ନଗୁଡ଼ିକୁ ସମର୍ଥନ କରେ (ଉଦାହରଣ ସ୍ୱରୂପ, `*-coder` → ଉଚ୍ଚ କୋଡିଂ ସ୍କୋର୍)।

## Auto ଭାରିଆଣ୍ଟଗୁଡ଼ିକର ସାରାଂଶ

ଡିଫଲ୍ଟ ଖାଲି `auto` ସହିତ `autoPrefix.ts`ରେ ଘୋଷିତ 6ଟି `AutoVariant` ମୂଲ୍ୟକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରି, **7ଟି ଆହ୍ୱାନଯୋଗ୍ୟ ମଡେଲ୍ ID** ଅଛି:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ନିଜେ 6ଟି ମୂଲ୍ୟ ଗଣନା କରେ; 7ମ ବିକଳ୍ପଟି ହେଉଛି "କୌଣସି ଭାରିଆଣ୍ଟ ନାହିଁ" — ଖାଲି `auto` — ଯାହାକୁ `parseAutoPrefix()` ଦ୍ୱାରା `variant: undefined` ଭାବେ ପରିଚାଳନା କରାଯାଏ।)

## ଟିୟରଗୁଡ଼ିକ Auto-Combo ସହିତ କିପରି ଖାପ ଖାଆନ୍ତି

16-ଫ୍ୟାକ୍ଟର ସ୍କୋରିଂ ଫଙ୍କସନ୍ (`open-sse/services/autoCombo/scoring.ts`) ଟିୟର
ସଦସ୍ୟତାକୁ ଦୁଇଟି ସିଗ୍ନାଲ୍ ଭାବେ ବିବେଚନା କରେ: `tierPriority` (0.0476) ଏବଂ `tierAffinity` (0.0476)। ସମ୍ପୂର୍ଣ୍ଣ
`DEFAULT_WEIGHTS` ସେଟ୍ ପାଇଁ ଉପରେ ଥିବା ପ୍ରାମାଣିକ [ସ୍କୋରିଂ ଫ୍ୟାକ୍ଟର୍ ସାରଣୀ](#how-it-works-persisted-auto-combos) ଦେଖନ୍ତୁ —
ପ୍ରତି-ପ୍ୟାକ୍ ଓଭରରାଇଡ୍ଗୁଡ଼ିକ (ship-fast/cost-saver/quality-first/
offline-friendly) "ପ୍ରତି ପ୍ୟାକ୍ର ଓଜନ ପ୍ରୋଫାଇଲ୍" ସାରଣୀରେ ତାଲିକାଭୁକ୍ତ ହୋଇଛି।

କେବଳ ଟିୟର୍ **Tier 1**କୁ ପ୍ରଥମ ସ୍ଥାନରେ ରଖିବାକୁ ବାଧ୍ୟ କରେ ନାହିଁ — ଯଦି Tier 1ର ବିଳମ୍ବତା ଖରାପ ଥାଏ କିମ୍ବା
ମୂଲ୍ୟ-ତୁଳନାରେ-ଗୁଣବତ୍ତା ସର୍ବୋତ୍ତମ ନ ହୁଏ, ତେବେ Tier 2 ବିଜୟୀ ହୁଏ। ଟିୟର୍ କ୍ରମକୁ ବାଧ୍ୟତାମୂଳକ କରିବା ପାଇଁ, କମ୍ବୋ
ଷ୍ଟ୍ରାଟେଜି `priority` ବ୍ୟବହାର କରନ୍ତୁ ଏବଂ ପ୍ରଦାତାମାନଙ୍କୁ ଟିୟର୍ ଅନୁସାରେ ସଜାନ୍ତୁ।

Tier 1 (ସବ୍ସ୍କ୍ରିପ୍ସନ୍)କୁ ଦୃଢ଼ ଭାବରେ ପ୍ରାଧାନ୍ୟ ଦେବା ପାଇଁ, `tierPriority`ର ଓଜନ ବଢ଼ାନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ଟିୟର୍ର ସଂଜ୍ଞା ଏବଂ ପ୍ରଦାତାଙ୍କ ବର୍ଗୀକରଣ ପାଇଁ [`docs/guides/TIERS.md`](../guides/TIERS.md) ଦେଖନ୍ତୁ।

## ପରୀକ୍ଷଣ ଏବଂ କଭରେଜ୍

### ନିର୍ଦ୍ଧାରିତ ରାଉଟିଂ-ନିଷ୍ପତ୍ତି ମ୍ୟାଟ୍ରିକ୍ସ (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ଏକ ମକ୍ କରାଯାଇଥିବା ଅପ୍‌ଷ୍ଟ୍ରିମ୍ ସହିତ ବାସ୍ତବ କମ୍ବୋ ପାଇପ୍‌ଲାଇନ୍ ମାଧ୍ୟମରେ ସମସ୍ତ 19ଟି
ସାର୍ବଜନୀନ କୌଶଳର ଏଣ୍ଡ-ଟୁ-ଏଣ୍ଡ ରାଉଟିଂ **ନିଷ୍ପତ୍ତି**କୁ ପ୍ରମାଣ କରେ।
କଭରେଜ୍‌ରେ ଅନ୍ତର୍ଭୁକ୍ତ:

- ସମସ୍ତ 19ଟି `ROUTING_STRATEGY_VALUES` କୌଶଳ (କ୍ରମବଦ୍ଧ, ଓଜନଯୁକ୍ତ, ମୂଲ୍ୟ, ପ୍ରସଙ୍ଗ, ଫ୍ୟୁଜନ୍, …)।
- `quota-share` (ଆଭ୍ୟନ୍ତରୀଣ) ଏଣ୍ଡ-ଟୁ-ଏଣ୍ଡ: ବାସ୍ତବ `selectQuotaShareTarget` ସିମ୍ ମାଧ୍ୟମରେ DRR ନିରପେକ୍ଷତା + ସାଚୁରେସନ୍ ପ୍ରାଥମିକତା ହ୍ରାସ
  (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)।
- ପ୍ରତ୍ୟେକ ଟାର୍ଗେଟ୍ ସଂଖ୍ୟାରେ `context-relay` ସାର୍ବଜନୀନ-ହ୍ୟାଣ୍ଡଅଫ୍ କଭରେଜ୍।

ଏହି ସୁଇଟ୍ CIରେ (`test:integration` ଜବ୍) `--test-concurrency=1` ଏବଂ
`--test-force-exit` ସହିତ ଚାଲେ, ତେଣୁ ଏହା ନିର୍ଦ୍ଧାରିତ ଏବଂ ଲାଇଭ୍ କ୍ରେଡେନ୍ସିଆଲ୍‌ର ଆବଶ୍ୟକତା ନାହିଁ।
