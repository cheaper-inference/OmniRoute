> ଯୋଗ୍ୟ କଣ୍ଟେକ୍ସ୍ଟରେ ସ୍ୱୟଂଚାଳିତ ଭାବେ 15-95% ସଞ୍ଚୟ କରନ୍ତୁ। ଏକ ଦ୍ରୁତ ସାରାଂଶ ପାଇଁ [README କମ୍ପ୍ରେସନ୍ ବିଭାଗ](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) ଦେଖନ୍ତୁ।

## ସାରାଂଶ

OmniRoute ଏକ ମଡ୍ୟୁଲାର୍ ପ୍ରମ୍ପ୍ଟ କମ୍ପ୍ରେସନ୍ ପାଇପ୍ଲାଇନ୍ କାର୍ଯ୍ୟକାରୀ କରେ, ଯାହା ଅନୁରୋଧଗୁଡ଼ିକ ଅପ୍ଷ୍ଟ୍ରିମ୍ ପ୍ରଦାନକାରୀଙ୍କ ପାଖରେ ପହଞ୍ଚିବା ପୂର୍ବରୁ **ସକ୍ରିୟ ଭାବେ** ଚାଲେ। ଏହାର ଅର୍ଥ ଆପଣଙ୍କ ଟୋକନ୍ ସଞ୍ଚୟ ସ୍ୱଚ୍ଛ ଭାବେ ହୁଏ — ଆପଣଙ୍କ କାର୍ଯ୍ୟପ୍ରବାହରେ କୌଣସି ପରିବର୍ତ୍ତନ ଆବଶ୍ୟକ ନାହିଁ।

```
କ୍ଲାଏଣ୍ଟ ଅନୁରୋଧ
  → କମ୍ପ୍ରେସନ୍ କୌଶଳ ଚୟନକର୍ତ୍ତା
    → Combo ଓଭର୍ରାଇଡ୍? → Combo ସେଟିଂ ବ୍ୟବହାର କରନ୍ତୁ
    → ସ୍ୱୟଂଚାଳିତ-ଟ୍ରିଗର୍ ଥ୍ରେସ୍ହୋଲ୍ଡ? → ସ୍ୱୟଂଚାଳିତ ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
    → ଡିଫଲ୍ଟ ମୋଡ୍? → ଗ୍ଲୋବାଲ୍ ସେଟିଂ ବ୍ୟବହାର କରନ୍ତୁ
    → ବନ୍ଦ? → କମ୍ପ୍ରେସନ୍ ଛାଡ଼ିଦିଅନ୍ତୁ
  → ଚୟନିତ କମ୍ପ୍ରେସନ୍ ମୋଡ୍
    → ବନ୍ଦ: କୌଣସି କମ୍ପ୍ରେସନ୍ ନାହିଁ
    → ଲାଇଟ୍: ସୁରକ୍ଷିତ ହ୍ୱାଇଟ୍ସ୍ପେସ୍/ଫର୍ମାଟିଂ ସଫେଇ (~15%)
    → ଷ୍ଟାଣ୍ଡାର୍ଡ: Caveman-ଶୈଳୀର ଅନାବଶ୍ୟକ ଶବ୍ଦ ଅପସାରଣ (~30%)
    → ଆଗ୍ରେସିଭ୍: ଇତିହାସ ଏଜିଂ + ସାରାଂଶକରଣ (~50%)
    → ଅଲ୍ଟ୍ରା: ହ୍ୟୁରିଷ୍ଟିକ୍ ପ୍ରୁନିଂ + କୋଡ୍-ବ୍ଲକ୍ ଥିନିଂ (~75%)
    → RTK: କମାଣ୍ଡ-ସଚେତନ ଟର୍ମିନାଲ୍/ଟୁଲ୍-ଆଉଟ୍ପୁଟ୍ ଫିଲ୍ଟରିଂ (60-90% ଅପ୍ଷ୍ଟ୍ରିମ୍ ପରିସର)
    → ଷ୍ଟାକ୍ଡ୍: କ୍ରମବଦ୍ଧ ମଲ୍ଟି-ଇଞ୍ଜିନ୍ ପାଇପ୍ଲାଇନ୍, ସାଧାରଣତଃ ପ୍ରଥମେ RTK ଓ ପରେ Caveman (78-95% ଯୋଗ୍ୟ ପରିସର)
  → କମ୍ପ୍ରେସ୍ ହୋଇଥିବା ଅନୁରୋଧ → ପ୍ରଦାନକାରୀ
```

## ସଙ୍କୋଚନ ମୋଡ୍ଗୁଡ଼ିକ

### ବନ୍ଦ

କୌଣସି ସଙ୍କୋଚନ ପ୍ରୟୋଗ ହୁଏ ନାହିଁ। ସମସ୍ତ ସନ୍ଦେଶ ଅପରିବର୍ତ୍ତିତ ଭାବେ ପାର ହୁଏ।

### Lite ମୋଡ୍ (~15% ସଞ୍ଚୟ, <1ms ବିଳମ୍ବତା)

ସବୁଠାରୁ ସୁରକ୍ଷିତ ମୋଡ୍ — ଫର୍ମାଟିଂ ପରିଷ୍କାର। ଏହାର ଟୁଲ୍-ଫଳାଫଳ ଛୋଟ କରିବା ପ୍ରକ୍ରିୟାରେ ତଥ୍ୟ ହ୍ରାସ ହୁଏ, ତେଣୁ ଡିଫଲ୍ଟ
ପଥ (`allow-lossy`, `engine:lite` କିମ୍ବା ନାମିତ-କମ୍ବୋ ଅପ୍ଟ-ଇନ୍ ନଥିଲେ) `compressToolResults: false` ସହିତ lite ଚଲାଏ:
ପୂର୍ବର ଟୁଲ୍ ଫଳାଫଳଗୁଡ଼ିକ ଅପରିବର୍ତ୍ତିତ ଭାବେ ପ୍ରୋଭାଇଡର୍କୁ ପହଞ୍ଚେ।

| କୌଶଳ                     | ବର୍ଣ୍ଣନା                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | ପରସ୍ପରକ୍ରମିକ ଖାଲି ଲାଇନ୍ ଏବଂ ଶେଷର ସ୍ପେସ୍ଗୁଡ଼ିକୁ ଏକତ୍ର କରେ                                     |
| `dedupSystemPrompt`      | ପୁନରାବୃତ୍ତ ସିଷ୍ଟମ୍ ସନ୍ଦେଶଗୁଡ଼ିକୁ ଅପସାରଣ କରେ                                                  |
| `compressToolResults`    | ପୂର୍ବର ଟୁଲ୍ ଫଳାଫଳଗୁଡ଼ିକୁ lite ସୀମା ପର୍ଯ୍ୟନ୍ତ ଛୋଟ କରେ (ତଥ୍ୟ ହ୍ରାସ: କେବଳ ଅନୁରୋଧ ଅପ୍ଟ-ଇନ୍ ସହିତ) |
| `removeRedundantContent` | ପୁନରାବୃତ୍ତ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ ହଟାଏ                                                             |
| `replaceImageUrls`       | base64 ଇମେଜ୍ ଡାଟା URIଗୁଡ଼ିକୁ ସଂକ୍ଷିପ୍ତ କରେ                                                   |

**ଏଥିପାଇଁ ଉତ୍ତମ:** ସର୍ବଦା-ଚାଲୁ ବ୍ୟବହାର, ସୁରକ୍ଷା-ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ୱର୍କଫ୍ଲୋ।

### Standard ମୋଡ୍ (~30% ସଞ୍ଚୟ)

[Caveman](https://github.com/JuliusBrussee/caveman) ଠାରୁ ପ୍ରେରିତ — ଅର୍ଥ ଅକ୍ଷୁଣ୍ଣ ରଖି ଅତିରିକ୍ତ ଶବ୍ଦ ଏବଂ ଦୀର୍ଘ ବାକ୍ୟରଚନାକୁ ଅପସାରଣ କରେ:

- ଅତିରିକ୍ତ ଶବ୍ଦ ଅପସାରଣ କରେ ("please", "I think", "basically", "actually")
- ଦୀର୍ଘ ବାକ୍ୟାଂଶଗୁଡ଼ିକୁ ସଂକ୍ଷିପ୍ତ କରେ ("in order to" → "to", "as a result of" → "because")
- ଭଦ୍ର ଦ୍ୱିଧା ପ୍ରକାଶକୁ ହଟାଏ ("Would you mind...", "If you could possibly...")
- କୋଡିଂ ପ୍ରମ୍ପ୍ଟ ପାଇଁ ସୁସଜ୍ଜିତ 30+ regex ନିୟମ

**ଏଥିପାଇଁ ଉତ୍ତମ:** ଦୈନିକ କୋଡିଂ ୱର୍କଫ୍ଲୋ, ଖର୍ଚ୍ଚ-ସଚେତନ ଟିମ୍ଗୁଡ଼ିକ।

### Aggressive ମୋଡ୍ (~50% ସଞ୍ଚୟ)

ଦୀର୍ଘ ସେସନ୍ ପାଇଁ ସ୍ମାର୍ଟ ଇତିହାସ ପରିଚାଳନା:

- **ସନ୍ଦେଶ ବୟସ୍କୀକରଣ** — ପୁରୁଣା ସନ୍ଦେଶଗୁଡ଼ିକୁ କ୍ରମେ ଅଧିକ ସଙ୍କୋଚିତ କରାଯାଏ
- **ଟୁଲ୍ ଫଳାଫଳ ସଙ୍କୋଚନ** — ଦୀର୍ଘ ଟୁଲ୍ ଆଉଟପୁଟ୍କୁ ଛୋଟ କିମ୍ବା ଅଦୃଶ୍ୟ କରାଯାଏ (ପ୍ରଥମ/ଶେଷ ଲାଇନ୍,
  ମ୍ୟାଚ୍-ଲାଇନ୍ ଫିଲ୍ଟରିଂ, JSON କି ଅପ୍ଟିମାଇଜେସନ୍)
- **ଗଠନାତ୍ମକ ଅଖଣ୍ଡତା ଗାର୍ଡ୍ଗୁଡ଼ିକ** — `tool_use` + `tool_result` ଯୁଗଳଗୁଡ଼ିକ ସୁସଙ୍ଗତ ରହିବା ସୁନିଶ୍ଚିତ କରେ
- **କଣ୍ଟେକ୍ସଟ୍ ୱିଣ୍ଡୋ ସଚେତନତା** — ପ୍ରତ୍ୟେକ ମଡେଲ୍ର ଟୋକେନ୍ ସୀମାକୁ ସମ୍ମାନ କରେ

**ଏଥିପାଇଁ ଉତ୍ତମ:** ଦୀର୍ଘ ଡିବଗିଂ ସେସନ୍, ବଡ଼ କୋଡ୍ବେସ୍।

### Ultra ମୋଡ୍ (~75% ସଞ୍ଚୟ)

ଟୋକେନ୍-ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ପରିସ୍ଥିତି ପାଇଁ ସର୍ବାଧିକ ସଙ୍କୋଚନ:

- **ହ୍ୟୁରିଷ୍ଟିକ୍ ପ୍ରୁନିଂ** — ସ୍କୋର୍-ଆଧାରିତ ଭାବେ ପ୍ରୋଜ୍ର ଟୋକେନ୍ ଛାଟେ
- **ଗଠନ ସଂରକ୍ଷଣ** — ଫେନ୍ସ୍ଡ୍ କୋଡ୍ ବ୍ଲକ୍, ଇନ୍ଲାଇନ୍ କୋଡ୍, URL ଏବଂ ଆଇଡେଣ୍ଟିଫାୟର୍ଗୁଡ଼ିକୁ
  ଟମ୍ବ୍ଷ୍ଟୋନ୍ କରି ଅପରିବର୍ତ୍ତିତ ଭାବେ ପୁନଃ ଯୋଡ଼ାଯାଏ, କେବେ ଛାଟାଯାଏ ନାହିଁ
- **ଇଚ୍ଛାଧୀନ SLM ସ୍ତର** — କନ୍ଫିଗର୍ କରାଗଲେ ଏକ ଛୋଟ ଲୋକାଲ୍ ମଡେଲ୍ ପ୍ରୁନ୍କୁ ସୁଧାରିପାରେ
- Aggressive ମୋଡ୍ଠାରୁ ସ୍ୱାଧୀନ: ଏହା ସନ୍ଦେଶ ବୟସ୍କୀକରଣ, ଟୁଲ୍-ଫଳାଫଳ ସଙ୍କୋଚନ
  କିମ୍ବା ଫଲବ୍ୟାକ୍ ସାରାଂଶକାରୀ ଚଲାଏ ନାହିଁ (କେବଳ SLM-ସ୍ତର ବିଫଳତା ହେଲେ ଏକ ଫଲବ୍ୟାକ୍ ପାସ୍କୁ
  aggressive ମାଧ୍ୟମରେ ପଠାଇପାରେ)

**ଏଥିପାଇଁ ଉତ୍ତମ:** ଯେତେବେଳେ ଆପଣ ପୁନଃପୁନି କଣ୍ଟେକ୍ସଟ୍ ସୀମାରେ ପହଞ୍ଚୁଛନ୍ତି।

### RTK ମୋଡ୍ (60-90% upstream ପରିସର)

କୋଡିଂ-ଏଜେଣ୍ଟ ସେସନ୍ରେ ଦେଖାଯାଉଥିବା ଦୀର୍ଘ ଟୁଲ୍ ଆଉଟପୁଟ୍ ପାଇଁ RTK ମୋଡ୍ ଅପ୍ଟିମାଇଜ୍ କରାଯାଇଛି:

- `git status`, `git diff`, `git log`, ଟେଷ୍ଟ ରନର୍, TypeScript/Vite/Webpack ବିଲ୍ଡ୍, ESLint/Biome/Prettier, npm audit/install, Docker ଲଗ୍, ଇନ୍ଫ୍ରା ଆଉଟପୁଟ୍ ଏବଂ ସାଧାରଣ shell ଆଉଟପୁଟ୍ ପରି କମାଣ୍ଡ୍/ଆଉଟପୁଟ୍ ଶ୍ରେଣୀ ଚିହ୍ନଟ କରେ
- `open-sse/services/compression/engines/rtk/filters/` ଠାରୁ JSON ଫିଲ୍ଟର୍ ପ୍ୟାକ୍ ପ୍ରୟୋଗ କରେ
- ପ୍ରୋଜେକ୍ଟ କିମ୍ବା ଗ୍ଲୋବାଲ୍ `filters.toml` ଫାଇଲ୍ଠାରୁ RTK TOML ସ୍କିମା v1 ଫିଲ୍ଟର୍ ଆମଦାନି କରେ, ଇନ୍ଲାଇନ୍-ଟେଷ୍ଟ
  ଭ୍ୟାଲିଡେସନ୍ ଏବଂ ପ୍ରୋଜେକ୍ଟ ଫାଇଲ୍ ପାଇଁ trust-gating ସହିତ
- ଇନ୍ଲାଇନ୍ ଭେରିଫାଇ ସାମ୍ପଲ୍ ସହିତ 56ଟି ବିଲ୍ଟ-ଇନ୍ ଫିଲ୍ଟର୍ ଯୋଗାଇଥାଏ
- ANSI କଣ୍ଟ୍ରୋଲ୍ ସିକ୍ୱେନ୍ସ, ପ୍ରୋଗ୍ରେସ୍ ବାର୍, ପୁନରାବୃତ୍ତ ଲାଇନ୍ ଏବଂ କାର୍ଯ୍ୟ-ଅପ୍ରାସଙ୍ଗିକ ଶବ୍ଦ ହଟାଏ
- ବିଫଳତା, ତ୍ରୁଟି, ସତର୍କତା, ପରିବର୍ତ୍ତିତ ଫାଇଲ୍, ସାରାଂଶ ଏବଂ ଦୀର୍ଘ ଆଉଟପୁଟ୍ର ଶେଷ ଅଂଶ ସଂରକ୍ଷଣ କରେ
- trust-gated ପ୍ରୋଜେକ୍ଟ ଫିଲ୍ଟର୍, ଗ୍ଲୋବାଲ୍ ଫିଲ୍ଟର୍ ଏବଂ ଇଚ୍ଛାଧୀନ redacted raw-output recovery ସମର୍ଥନ କରେ

**ଏଥିପାଇଁ ଉତ୍ତମ:** shell, build, test, git, grep ଏବଂ file-output ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ୍ ସହିତ ଏଜେଣ୍ଟ ସେସନ୍।

### Stacked ମୋଡ୍ (78-95% ଯୋଗ୍ୟ ପରିସର)

Stacked ମୋଡ୍ ଏକ ନିର୍ଦ୍ଧାରିତ କ୍ରମରେ ଏକାଧିକ ସଙ୍କୋଚନ ଇଞ୍ଜିନ୍ ଚଲାଏ। ଡିଫଲ୍ଟ ପାଇପ୍ଲାଇନ୍ ହେଉଛି:

```txt
RTK -> Caveman
```

ଏହି କ୍ରମ ପ୍ରଥମେ ଟର୍ମିନାଲ୍/ଟୁଲ୍ ଆଉଟପୁଟ୍କୁ ସଂକ୍ଷିପ୍ତ ରଖେ, ତାପରେ ଅବଶିଷ୍ଟ ପ୍ରାକୃତିକ-ଭାଷା ପ୍ରମ୍ପ୍ଟରେ Caveman ସେମାଣ୍ଟିକ୍ ସଙ୍କୋଚନ ପ୍ରୟୋଗ କରେ। Stacked ପାଇପ୍ଲାଇନ୍ଗୁଡ଼ିକୁ ଗ୍ଲୋବାଲ୍ ଭାବେ କିମ୍ବା
ରାଉଟିଂ କମ୍ବୋଗୁଡ଼ିକୁ ନିଯୁକ୍ତ ସଙ୍କୋଚନ କମ୍ବୋ ମାଧ୍ୟମରେ କନ୍ଫିଗର୍ କରାଯାଇପାରେ।

**ଏଥିପାଇଁ ଉତ୍ତମ:** ବଡ଼ ଟୁଲ୍ ଲଗ୍ ସହିତ ମାନବ ନିର୍ଦ୍ଦେଶ କିମ୍ବା ଆସିଷ୍ଟାଣ୍ଟ ସାରାଂଶ ଥିବା ମିଶ୍ରିତ କଣ୍ଟେକ୍ସଟ୍।

## ଅପ୍ଷ୍ଟ୍ରିମ୍ ସଞ୍ଚୟ ଗଣନା

OmniRoute ଦୁଇଟି ଉତ୍ସରୁ ମିଳୁଥିବା କମ୍ପ୍ରେସନ୍ ସଞ୍ଚୟକୁ ଡକ୍ୟୁମେଣ୍ଟ କରେ: ଅପ୍ଷ୍ଟ୍ରିମ୍ ପ୍ରୋଜେକ୍ଟ ବେଞ୍ଚମାର୍କ ଏବଂ
OmniRoute-ର ନିଜସ୍ୱ ଇଞ୍ଜିନ୍ ସଂଯୋଜନ।

| ଉତ୍ସ    | ଏଠାରେ ବ୍ୟବହୃତ ଅପ୍ଷ୍ଟ୍ରିମ୍ README ସଂଖ୍ୟା                                                                              |
| ------- | -------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` କମ୍ ଆଉଟପୁଟ୍ ଟୋକନ୍, `65%` ବେଞ୍ଚମାର୍କ ହାରାହାରି ଆଉଟପୁଟ୍ ସଞ୍ଚୟ, `22-87%` ପରିସର, ଏବଂ `~46%` ଇନପୁଟ୍ କମ୍ପ୍ରେସନ୍ ଟୁଲ୍ |
| RTK     | କମାଣ୍ଡ-ଆଉଟପୁଟ୍ରେ `60-90%` ସଞ୍ଚୟ; ନମୁନା ସେସନ୍ରେ `~118,000 -> ~23,900` ଟୋକନ୍, କିମ୍ବା `79.7%` ସଞ୍ଚୟ (`~80%`)            |

ପରସ୍ପରକୁ ଆବୃତ କରୁଥିବା ଟୁଲ୍/କଣ୍ଟେକ୍ସ୍ଟ ପେଲୋଡ୍ଗୁଡ଼ିକ ପାଇଁ, ଡିଫଲ୍ଟ OmniRoute କମ୍ବୋ ଇଞ୍ଜିନ୍ଗୁଡ଼ିକୁ କ୍ରମବଦ୍ଧ ଭାବେ ଯୋଡ଼େ:

```txt
RTK -> Caveman
```

ମିଳିତ ସଞ୍ଚୟ ଗୁଣାତ୍ମକ, ଯୋଗାତ୍ମକ ନୁହେଁ:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ଯେତେବେଳେ RTK ଏବଂ Caveman ଉଭୟ ସମାନ ଇନପୁଟ୍/କଣ୍ଟେକ୍ସ୍ଟ ପେଲୋଡ୍କୁ ହ୍ରାସ କରିପାରନ୍ତି, ସେତେବେଳେ ସେହି `78-95%` ସଂଖ୍ୟା ପ୍ରଯୁଜ୍ୟ।
Caveman ରେସ୍ପନ୍ସ ଆଉଟପୁଟ୍ ମୋଡ୍ ପୃଥକ: ସକ୍ଷମ କରାଯାଇଥିଲେ, Caveman-ର ନିଜସ୍ୱ ଆଉଟପୁଟ୍ ସଞ୍ଚୟ (`65%`
ହାରାହାରି, `~75%` ମୁଖ୍ୟ ଆକଳନ, `22-87%` ପରିସର) ବ୍ୟବହାର କରନ୍ତୁ। ମୋଟ ବିଲିଂ ସଞ୍ଚୟ ଆପଣଙ୍କ ପ୍ରମ୍ପ୍ଟ/ଆଉଟପୁଟ୍ ମିଶ୍ରଣ ଉପରେ ନିର୍ଭର କରେ।

### "ଯୋଗ୍ୟ"ର ପ୍ରକୃତ ଅର୍ଥ କ’ଣ

15-95% ମୁଖ୍ୟ ପରିସରଟି ବାସ୍ତବ, କିନ୍ତୁ ଏହା କେବଳ **ଅନାବଶ୍ୟକ କିମ୍ବା ଅତ୍ୟଧିକ ବିସ୍ତୃତ** ବିଷୟବସ୍ତୁ ପାଇଁ ପ୍ରଯୁଜ୍ୟ — ପୁନରାବୃତ୍ତ
ତ୍ରୁଟି ଲାଇନ୍, ସମାନ ଚେତାବନୀକୁ ବାରମ୍ବାର ଦେଖାଉଥିବା ଏକ ବିଲ୍ଡ ଲଗ୍, ଏକ ଅତ୍ୟଧିକ ବଡ଼ `grep`/ଫାଇଲ୍-ରିଡ୍ ଡମ୍ପ୍। ଏହାର ଅର୍ଥ
**ଏହା ନୁହେଁ** ଯେ ପ୍ରତ୍ୟେକ ଅନୁରୋଧରେ ଏତେ ସଞ୍ଚୟ ହୁଏ।

ପ୍ରୟୋଗମୂଳକ ଭାବେ ଯାଞ୍ଚ କରାଯାଇଛି (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300ଟି ସମାନ
ତ୍ରୁଟି ଲାଇନ୍ ଥିବା ଏକ Anthropic-ଆକୃତିର `tool_result` ବ୍ଲକ୍ରେ ଚାଲିଥିବା ଏକ `stacked` (RTK + Caveman)
ରନ୍ରେ **95.93% ଟୋକନ୍ ସଞ୍ଚୟ / 96.26% ଅକ୍ଷର ସଞ୍ଚୟ** ହୋଇଥିଲା — ଯାହା ବିଜ୍ଞାପିତ
ପରିସର ମଧ୍ୟରେ ସଠିକ୍ ଭାବେ ରହିଛି। କିନ୍ତୁ ସାଧାରଣ, ଅନାବଶ୍ୟକ ପୁନରାବୃତ୍ତି ନଥିବା ଟୁଲ୍ ଆଉଟପୁଟ୍ରେ (ଏକ ସ୍ୱଚ୍ଛ `grep` ମ୍ୟାଚ୍ ତାଲିକା,
ଏକ ଛୋଟ ଫାଇଲ୍ ରିଡ୍, ସାଧାରଣ କଥୋପକଥନମୂଳକ ପାଠ୍ୟ) ସମାନ ପାଇପ୍ଲାଇନ୍ ଚଲାଇଲେ ଯଥାର୍ଥ ଭାବେ **ପ୍ରାୟ-ଶୂନ୍ୟ ସଞ୍ଚୟ** ହୁଏ, କାରଣ
ଅପସାରଣ କରିବା ପାଇଁ କୌଣସି ପୁନରାବୃତ୍ତି ନାହିଁ ଏବଂ `validateCompression()` (`validation.ts`) କୋଡ୍ ବ୍ଲକ୍, URL, ଶୀର୍ଷକ, ସଂସ୍କରଣ କିମ୍ବା ALL-CAPS ସ୍ଥିରାଙ୍କ ପରିଚୟକଗୁଡ଼ିକୁ ଛାଡ଼ିଦେବା କିମ୍ବା ପରିବର୍ତ୍ତନ କରିଦେବା ଭଳି
କୌଣସି ପୁନର୍ଲିଖନ ପଠାଇବାକୁ ମନା କରେ।

ଏହା ଆଶାକରାଯାଉଥିବା, ସୁରକ୍ଷିତ ଆଚରଣ, କୌଣସି ବଗ୍ ନୁହେଁ: ମୁଖ୍ୟତଃ ସ୍ୱଚ୍ଛ ଫାଇଲ୍ଗୁଡ଼ିକୁ ପଢ଼ୁଥିବା/grep କରୁଥିବା ଏକ କୋଡିଂ ସେସନ୍ରେ
କମ୍ପ୍ରେସନ୍ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ସକ୍ଷମ ଥିଲେ ମଧ୍ୟ ସାମାନ୍ୟ ମୋଟ ସଞ୍ଚୟ ଦେଖାଯିବ, ଯେତେବେଳେ ବିଫଳ ହେଉଥିବା ଏକ
ଲୁପ୍ କିମ୍ବା ଅତ୍ୟଧିକ ଆଉଟପୁଟ୍ ଦେଉଥିବା ଏକ ଲିଣ୍ଟର୍ର ସମ୍ମୁଖୀନ ହେଉଥିବା ସେସନ୍ରେ ସେହି ଟ୍ରାଫିକ୍ରେ ସମ୍ପୂର୍ଣ୍ଣ 78-95% ପରିସର ଦେଖାଯିବ। କମ୍ପ୍ରେସନ୍ ଭୁଲ ଭାବେ ବିନ୍ୟାସ ହୋଇଛି ବୋଲି ପ୍ରମାଣ ଭାବେ ଗୋଟିଏ ସେସନ୍ର
କମ୍ ସମଗ୍ର ସଞ୍ଚୟ ପ୍ରତିଶତକୁ ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ — ପ୍ରଥମେ ମୂଳ ଟୁଲ୍ ଆଉଟପୁଟ୍ ପ୍ରକୃତରେ ଅନାବଶ୍ୟକ ଭାବେ ପୁନରାବୃତ୍ତ ଥିଲା କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ।

Aggressive ସହିତ:        24K ଟୋକନ୍ ପଠାଯାଇଛି          (50% ସଞ୍ଚୟ — ବୟସ୍କୀକରଣ + ସାରାଂଶୀକରଣ)
Ultra ସହିତ:             12K ଟୋକନ୍ ପଠାଯାଇଛି          (75% ସଞ୍ଚୟ — ହ୍ୟୁରିଷ୍ଟିକ୍ ଛଟେଇ)
RTK ସହିତ:               19K-5K ଟୋକନ୍ ପଠାଯାଇଛି       (କମାଣ୍ଡ/ଟୁଲ୍ ଆଉଟପୁଟ୍ରେ 60-90% ସଞ୍ଚୟ)
Stacked ସହିତ:           10K-2.5K ଟୋକନ୍ ପଠାଯାଇଛି     (ଯୋଗ୍ୟ RTK+Caveman ପରିସରରେ 78-95%)

## ବିନ୍ୟାସ

### ଡ୍ୟାଶବୋର୍ଡ

`Dashboard → Context & Cache` କୁ ଯାଆନ୍ତୁ:

- **Caveman** — ମୋଡ୍ ଚୟନ, ଭାଷା ପ୍ୟାକ୍, ପ୍ରିଭ୍ୟୁ ଏବଂ ଗ୍ଲୋବାଲ୍ ଡିଫଲ୍ଟଗୁଡ଼ିକ
- **RTK** — କମାଣ୍ଡ-ଫିଲ୍ଟର୍ ପ୍ରିଭ୍ୟୁ, RTK ସୁରକ୍ଷା ସେଟିଂଗୁଡ଼ିକ ଏବଂ ଫିଲ୍ଟର୍ କ୍ୟାଟାଲଗ୍
- **Compression Combos** — ରାଉଟିଂ କମ୍ବୋଗୁଡ଼ିକୁ ନିର୍ଦ୍ଦିଷ୍ଟ ଇଞ୍ଜିନ୍ ପାଇପଲାଇନ୍ ଆବଣ୍ଟନ
- **Auto-Trigger Threshold** — ଟୋକେନ୍ ସଂଖ୍ୟା ଥ୍ରେଶହୋଲ୍ଡ ଅତିକ୍ରମ କଲେ ସ୍ୱୟଂଚାଳିତ ଭାବେ କମ୍ପ୍ରେସନ୍ ସକ୍ରିୟ କରେ

### ପ୍ରତି-କମ୍ବୋ ଓଭରରାଇଡ୍

`Dashboard → Context & Cache → Compression Combos` ରେ ଏକ ରାଉଟିଂ
କମ୍ବୋକୁ ଏକ କମ୍ପ୍ରେସନ୍ କମ୍ବୋ ଆବଣ୍ଟନ କରନ୍ତୁ:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ଏହା ଦ୍ୱାରା ଆପଣ ମାଗଣା/କୋଡିଂ ପ୍ରଦାନକାରୀମାନଙ୍କରେ ଷ୍ଟାକ୍ଡ କମ୍ପ୍ରେସନ୍ ବ୍ୟବହାର କରିପାରିବେ, ଯେତେବେଳେ ପେଡ୍
ସବସ୍କ୍ରିପସନ୍ଗୁଡ଼ିକରେ ଲାଇଟ୍ ମୋଡ୍ ରଖିପାରିବେ।

ଏହି "Per-Combo Override" ଆସାଇନମେଣ୍ଟ, **routing-combo compression
mode** ଓଭରରାଇଡ୍ (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ଫିଲ୍ଡର ସ୍କିମା
`rtk`, `stacked` ଏବଂ `omniglyph` ମଧ୍ୟ ଗ୍ରହଣ କରେ) ଠାରୁ ଏକ ଭିନ୍ନ ନିୟନ୍ତ୍ରଣ — ସେହି ଓଭରରାଇଡ୍ କୌଣସି ନାମିତ
କମ୍ପ୍ରେସନ୍-କମ୍ବୋ ପାଇପଲାଇନ୍ ଚୟନ କରେ ନାହିଁ; ଏହା କେବଳ
`resolveCompressionPlan` ଦ୍ୱାରା ପରାମର୍ଶ କରାଯାଉଥିବା `compressionMode` ଫିଲ୍ଡ ସେଟ୍ କରେ। ଏହା କମ୍ବୋ କାର୍ଡରେ
(`Dashboard → Combos`) କିମ୍ବା #6760 ପରଠାରୁ, ଉପରେ
ଦଲିଲଭୁକ୍ତ ପାଇପଲାଇନ୍-ଆସାଇନମେଣ୍ଟ ଚେକବକ୍ସ ପାଖରେ ଥିବା
`Dashboard → Context & Cache → Compression Combos` ର "Assign to routing" ତାଲିକାରେ ପ୍ରତି ରାଉଟିଂ କମ୍ବୋ ପାଇଁ
ସେଟ୍ କରାଯାଇପାରେ। ଉଭୟ ସ୍ଥାନ ସମାନ `PUT /api/combos/{id}` ଏଣ୍ଡପଏଣ୍ଟ ମାଧ୍ୟମରେ ପର୍ସିଷ୍ଟ ହୁଏ।

### ପ୍ରତି-ଅନୁରୋଧ ଓଭରରାଇଡ୍

ଏକକ ଅନୁରୋଧ ପାଇଁ କମ୍ପ୍ରେସନ୍ ପ୍ଲାନ୍ ଓଭରରାଇଡ୍ କରିବାକୁ
`x-omniroute-compression` ଅନୁରୋଧ ହେଡର୍ ପଠାନ୍ତୁ। ଏହାର ସର୍ବାଧିକ ପ୍ରାଥମିକତା ରହେ — ଏହା ରାଉଟିଂ-କମ୍ବୋ ଓଭରରାଇଡ୍, ସକ୍ରିୟ ପ୍ରୋଫାଇଲ୍,
ଅଟୋ-ଟ୍ରିଗର୍ ଏବଂ ପ୍ୟାନେଲ୍ ଡିଫଲ୍ଟକୁ ଅତିକ୍ରମ କରେ। ଅଜଣା ମୂଲ୍ୟଗୁଡ଼ିକୁ ଅଣଦେଖା କରାଯାଏ (ଅନୁରୋଧ କେବେ ବି ପ୍ରତ୍ୟାଖ୍ୟାନ ହୁଏ ନାହିଁ) ଏବଂ
ଗ୍ଲୋବାଲ୍ ମାଷ୍ଟର୍ ସ୍ୱିଚ୍ ସବୁକିଛି ନିୟନ୍ତ୍ରଣ କରେ: କମ୍ପ୍ରେସନ୍ ଗ୍ଲୋବାଲ୍ ଭାବେ ବନ୍ଦ ଥିଲେ ହେଡର୍ ଏହାକୁ
ଚାଲୁ କରିପାରେ ନାହିଁ। ମୂଲ୍ୟଗୁଡ଼ିକ:

| ମୂଲ୍ୟ         | ପ୍ରଭାବ                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `off`         | ଏହି ଅନୁରୋଧ ପାଇଁ କୌଣସି କମ୍ପ୍ରେସନ୍ ନାହିଁ।                                                             |
| `default`     | ପ୍ୟାନେଲ୍ରୁ ଉତ୍ପନ୍ନ Default ପ୍ରୋଫାଇଲ୍ (ସକ୍ରିୟ ପ୍ରୋଫାଇଲ୍କୁ ଅଣଦେଖା କରେ)। Lossy ଇଞ୍ଜିନ୍ଗୁଡ଼ିକ ବନ୍ଦ ରହେ। |
| `safe`        | ହେଡର୍ ନ ପଠାଇବା ସହିତ ସମାନ।                                                                           |
| `allow-lossy` | ସାରାଂଶ, ପ୍ରାସଙ୍ଗିକତା ଫିଲ୍ଟର୍ ଏବଂ ଷ୍ଟାଇଲ୍ ରିରାଇଟ୍ ସହିତ ଏହି ଅନୁରୋଧର ଅପରେଟର୍ ପ୍ଲାନ୍କୁ ରଖେ।             |
| `engine:<id>` | ସକ୍ଷମ ଥିବାବେଳେ ଏକକ ଇଞ୍ଜିନ୍, ଯଥା `engine:rtk`। ଏହା ସେହି ଇଞ୍ଜିନ୍ ପାଇଁ ପ୍ରତି-ଅନୁରୋଧ ଅପ୍ଟ-ଇନ୍।          |
| `<combo>`     | ନାମ ଅନୁସାରେ (କେସ୍-ଇନସେନ୍ସିଟିଭ୍) ପ୍ରଥମେ, ପରେ id ଅନୁସାରେ ମେଳ ହେଉଥିବା ଏକ ନାମିତ କମ୍ବୋ।                  |

`allow-lossy`, `engine:<id>` କିମ୍ବା ଏକ ନାମିତ କମ୍ବୋ ନଥିଲେ, lossy ଇଞ୍ଜିନ୍ଗୁଡ଼ିକ ପ୍ରୟୋଗ ହୁଏ ନାହିଁ। ଯେତେବେଳେ ଏକ
lossy Default, auto-trigger କିମ୍ବା routing override ଡାଉନଗ୍ରେଡ୍ ହୁଏ, OmniRoute କନଫିଗର୍ କରାଯାଇଥିବା stacked ପାଇପଲାଇନ୍ରୁ ଚିହ୍ନଟ ହୋଇଥିବା
lossless ପଦକ୍ଷେପଗୁଡ଼ିକୁ କନଫିଗର୍ କରାଯାଇଥିବା କ୍ରମରେ ରଖେ। କୌଣସି କନଫିଗର୍ କରାଯାଇଥିବା lossless ପଦକ୍ଷେପ ବଞ୍ଚି ନଥିଲେ ମାତ୍ର ଏହା
`session-dedup → lite` କୁ ଫେରିଯାଏ।

Settings ପ୍ୟାନେଲ୍ର **Effective pipeline** ପ୍ରିଭ୍ୟୁ ସାଧାରଣ at-rest ପ୍ଲାନ୍ ଦେଖାଏ। ଯେତେବେଳେ ଏକ
auto-trigger ଚାଲିପାରେ, ସେହି ପ୍ରିଭ୍ୟୁ ଏହାର conditional effective pipeline ମଧ୍ୟ ଦେଖାଏ, ଯାହା ଦ୍ୱାରା ପ୍ୟାନେଲ୍ ଏବଂ ହେଡର୍-ବିହୀନ runtime resolution ସମନ୍ୱିତ ରହେ।

ପ୍ରୟୋଗ କରାଯାଇଥିବା ପ୍ଲାନ୍କୁ `X-OmniRoute-Compression: <mode>; source=<source>` ରେସପନ୍ସ
ହେଡର୍ରେ ପୁନଃ ପଠାଯାଏ, ଯେଉଁଠାରେ `<source>` ନିମ୍ନଲିଖିତ ମଧ୍ୟରୁ ଗୋଟିଏ:
`request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` କିମ୍ବା `off`।

## ସ୍ୱୀକୃତି

ଷ୍ଟାଣ୍ଡାର୍ଡ ମୋଡ୍ କମ୍ପ୍ରେସନ୍ ନିୟମଗୁଡ଼ିକ **[JuliusBrussee](https://github.com/JuliusBrussee)**ଙ୍କ **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ — ଭାଇରାଲ୍ "କମ୍ ଟୋକେନ୍ରେ କାମ ହେଉଥିବା ବେଳେ ଅଧିକ ଟୋକେନ୍ କାହିଁକି ବ୍ୟବହାର କରିବେ" ପ୍ରକଳ୍ପ। Caveman `~75%` କମ୍ ଆଉଟପୁଟ୍ ଟୋକେନ୍, ବେଞ୍ଚମାର୍କରେ ହାରାହାରି `65%` ଆଉଟପୁଟ୍ ସଞ୍ଚୟ, `22-87%` ଆଉଟପୁଟ୍ ପରିସର ଏବଂ ଏକ `~46%` ଇନ୍ପୁଟ୍-କମ୍ପ୍ରେସନ୍ ଟୁଲ୍ ରିପୋର୍ଟ କରେ।

RTK ମୋଡ୍ **[RTK AI](https://github.com/rtk-ai)**ର **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ — ଟର୍ମିନାଲ୍, ବିଲ୍ଡ, ଟେଷ୍ଟ, git ଏବଂ ଟୁଲ୍-ଆଉଟପୁଟ୍ ଫିଲ୍ଟରିଂ ପାଇଁ ଉଚ୍ଚ-କାର୍ଯ୍ୟକ୍ଷମତାସମ୍ପନ୍ନ କମାଣ୍ଡ-ଆଉଟପୁଟ୍ କମ୍ପ୍ରେସନ୍ ପ୍ରକଳ୍ପ। RTK `60-90%` ସଞ୍ଚୟ ରିପୋର୍ଟ କରେ, ଏବଂ ଏହାର README ନମୁନା ସେସନ୍ରେ `~80%` ସଞ୍ଚୟ ଦେଖାଯାଇଛି।

## ଉନ୍ନତ ସଙ୍କୋଚନ ପ୍ରଣାଳୀ।

ଉପରୋକ୍ତ ବର୍ଣ୍ଣିତ 7 ଟି ମୋଡ୍ ବାହାରେ (ଉତ୍ସ `codex-responses` ଏବଂ `omniglyph` ମୋଡ୍ ମଧ୍ୟ ଗ୍ରହଣ କରେ, ଯାହା ଏହି ଗାଇଡ୍ କଭର୍ କରେ ନାହିଁ), ନିମ୍ନରେ ଥିବା ବିଭାଗଗୁଡ଼ିକ ସେହି ମୋଡ୍ ଭିତରେ କିମ୍ବା ଏହା ସହିତ କାମ କରୁଥିବା ବ features ଶିଷ୍ଟ୍ୟଗୁଡିକ କଭର୍ କରେ: ଟୁଲ୍ ରେଜଲ୍ଟ ସଙ୍କୋଚନ ଏବଂ ପ୍ରଗତିଶୀଳ ବୟସ ହେଉଛି ଆକ୍ରମଣାତ୍ମକ ଇଞ୍ଜିନର ଷ୍ଟେପ୍ 1 ଏବଂ 2 (ଆକ୍ରମଣାତ୍ମକ ମୋଡ୍ ଏବଂ ଏକ ଷ୍ଟାକ୍ ପାଇପଲାଇନର ଏକ `aggressive` ଷ୍ଟେପ୍), `aggressive` ପାଇପଲାଇନ କିପରି ଷ୍ଟାକ୍ ପାଇପ୍ `standard` ସଙ୍କୋଚନ ଚାଲୁଥିବା ସମୟରେ କ୍ୟାଚିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ, ଏବଂ କ୍ୟାଭମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍ ଏବଂ ଆଉଟପୁଟ୍ ଶ `ultra` ଳୀଗୁଡ଼ିକ ଅପ୍ଟ-ଇନ୍ ସିଷ୍ଟମ୍-ପ୍ରମ୍ପ୍ଟ ନିର୍ଦ୍ଦେଶାବଳୀ ଅଟେ, ଡିଫଲ୍ଟ ଭାବରେ ଅଫ୍, ଯାହା ଅନୁରୋଧକୁ ସଙ୍କୋଚନ କରିବା ପରିବର୍ତ୍ତେ ମଡେଲର ଆଉଟପୁଟ୍ ଆକୃତି କରିଥାଏ।

### କ୍ୟାଚ୍-ସଚେତନ ସଙ୍କୋଚନ।

କିଛି ପ୍ରଦାନକାରୀ (ପ୍ରମ୍ପ୍ଟ କ୍ୟାଚିଂ ସହିତ Anthropic ପରି) ସମର୍ଥନ କରନ୍ତି।** ତୁରନ୍ତ କ୍ୟାଚିଂ।** , ଯାହା ସେମାନଙ୍କୁ ଖର୍ଚ୍ଚ ଏବଂ ବିଳମ୍ବତା ହ୍ରାସ କରିବାକୁ ପ୍ରମ୍ପ୍ଟର କିଛି ଅଂଶ କ୍ୟାଚ୍ କରିବାକୁ ଦିଏ। ଯେତେବେଳେ କ୍ୟାଚିଂ ସକ୍ଷମ ହୁଏ, ଆକ୍ରମଣାତ୍ମକ ସଙ୍କୋଚନ ପ୍ରକୃତରେ ହୋଇପାରେ।** ଆଘାତ** କାର୍ଯ୍ୟଦକ୍ଷତା କାରଣ ଏହା କ୍ୟାଚ୍ ଅବ alid ଧ କରି କ୍ୟାଚ୍ ଟୋକେନ୍ଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରେ।

`cachingAware.ts` ମଡ୍ୟୁଲ୍ ଏହାକୁ ସମାଧାନ କରିଥାଏ।** କ୍ୟାଚିଂ ପ୍ରସଙ୍ଗ ଚିହ୍ନଟ କରିବା।** ଏବଂ** ସଙ୍କୋଚନ ରଣନୀତି** ସେହି ଅନୁଯାୟୀ।

#### ଏହା କିପରି କାମ କରେ।

1. **କ୍ୟାଚିଂ ପ୍ରସଙ୍ଗ ଚିହ୍ନଟ କରନ୍ତୁ।** — `cache_control` ମାର୍କର ପାଇଁ ଅନୁରୋଧ ଶରୀରକୁ ସ୍କାନ୍ କରେ।
2. **କ୍ୟାଚିଂ ପ୍ରଦାନକାରୀଙ୍କୁ ଚିହ୍ନଟ କରନ୍ତୁ।** — ଲକ୍ଷ୍ୟ ପ୍ରଦାନକାରୀ କ୍ୟାଚିଂକୁ ସମର୍ଥନ କରନ୍ତି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ।
3. **ରଣନୀତି ଆଡଜଷ୍ଟ କରନ୍ତୁ।** — କ୍ୟାସିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ `aggressive`/`ultra` କୁ `standard` କୁ ଡାଉନଗ୍ରେଡ୍ କରେ।
4. **ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟକୁ ଏଡ଼ାଇଦିଅ।** — ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟଗୁଡିକ ସାଧାରଣତ c କ୍ୟାଚ୍ ହୋଇଥାଏ, ତେଣୁ ସେଗୁଡ଼ିକୁ ସଙ୍କୋଚନ କରନ୍ତୁ ନାହିଁ।

ଷ୍ଟ୍ରାଟେଜୀ ହେଲପର ମଧ୍ୟ ଏକ `deterministicOnly` ପତାକା ଫେରସ୍ତ କରେ, କିନ୍ତୁ ଯୋଜନା ବିଲ୍ଡର୍ କେବଳ କ strategy ଶଳ — ଖାଏ ଯାହା ଆଜି ଡାଉନ୍ଷ୍ଟ୍ରିମ୍ ପତାକା ପ read େ ନାହିଁ।

#### କୋଡ୍ ଉଦାହରଣ।

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ।

କ୍ୟାଚ୍-ସଚେତନ ସଙ୍କୋଚନ ହେଉଛି।** ସର୍ବଦା ଅନ୍** — config ଣସି ବିନ୍ୟାସ ଆବଶ୍ୟକ ନାହିଁ। ଯେତେବେଳେ ବି ସଙ୍କୋଚନ ଚାଲିଥାଏ ଏବଂ ଟାର୍ଗେଟ୍ ପ୍ରଦାନକାରୀ ପ୍ରମ୍ପ୍ଟ କ୍ୟାଚିଂ (Anthropic, OpenAI, ଇତ୍ୟାଦି) କୁ ସମର୍ଥନ କରେ। ସ୍ପଷ୍ଟ `cache_control` ମାର୍କରଗୁଡିକ ଆବଶ୍ୟକ ନୁହେଁ — ଏକ କ୍ୟାଚିଂ ପ୍ରଦାନକାରୀ କେବଳ ଡାଉନଗ୍ରେଡ୍ ଟ୍ରିଗର କରନ୍ତି, ଏବଂ ମାର୍କରମାନେ କେବଳ କରନ୍ତି ନାହିଁ (ମାର୍କର ଚିହ୍ନଟ କ୍ୟାଚ୍ ଟେଲିମେଟ୍ରି ଫିଡ୍ କରେ, ରଣନୀତି ନିଷ୍ପତ୍ତି ନୁହେଁ)।

OpenRouter କେବଳ `anthropic/*` ମଡେଲଗୁଡିକ ପାଇଁ ଏକ କ୍ୟାଚିଂ ପ୍ରଦାନକାରୀ ଭାବରେ ଗଣନା କରେ: Claude କୋଡ୍ ଅନୁରୋଧଗୁଡିକ ସେମାନଙ୍କର `cache_control` ବ୍ରେକପଏଣ୍ଟଗୁଡିକ (ସର୍ବାଧିକ 4) ରଖେ ଏବଂ ରାକ୍ଷୀ ଉପସର୍ଗକୁ ସୁରକ୍ଷା ଦେଇଥାଏ, ଯେତେବେଳେ ଅନ୍ୟ ସମସ୍ତ OpenRouter ପରିବାର (`openai/`, `google/`, `qwen/`,…) ଛଡ଼ାଯାଇଥାଏ ଏବଂ ଅସୁରକ୍ଷିତ ରହିଥାଏ।

### ପ୍ରଗତିଶୀଳ ବାର୍ଦ୍ଧକ୍ୟ।

ଲମ୍ବା ବାର୍ତ୍ତାଳାପ ଅନେକ ବାର୍ତ୍ତା ଟର୍ନ୍ ସଂଗ୍ରହ କରେ, କିନ୍ତୁ ପୁରାତନ ମୋଡ଼ କମ୍ ପ୍ରାସଙ୍ଗିକ ହୋଇଯାଏ। `progressiveAging.ts` ମଡ୍ୟୁଲ୍** ବାର୍ତ୍ତା ଦୂରତାକୁ ଦୂର କରେ।** (ବାର୍ତ୍ତାଳାପର ଶେଷରୁ ଦୂରତା ମାପ କରାଯାଏ)। ପଠାଯାଇଥିବା ଡିଫଲ୍ଟ ସହିତ (`verbatim: 2, light: 2, moderate: 3`):

- **ଶେଷ 2 ଟର୍ନ୍ (ଦୂରତା ≤ 2)** : ଭର୍ବାଟିମ୍ ରଖାଯାଇଛି।
- **ଦୂରତା 3** : ଗୁମ୍ଫା ସଙ୍କୋଚନ (ଫିଲର୍ ଅପସାରଣ)
- **ଦୂରତା 4 +** : ସହାୟକ ବାର୍ତ୍ତାଗୁଡ଼ିକ ସଂକ୍ଷିପ୍ତ; ଉପଭୋକ୍ତା ବାର୍ତ୍ତାଗୁଡ଼ିକ ସେମାନଙ୍କର ପ୍ରଥମ ଧାଡିରେ ହ୍ରାସ ହୋଇଛି, 120 ଅକ୍ଷରରେ କ୍ୟାପ୍ ହୋଇଛି; ଅନ୍ୟାନ୍ୟ ଭୂମିକା ଅସ୍ପୃଶ୍ୟ। ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ, ପୂର୍ବରୁ ବୟସ ହୋଇଥିବା ବାର୍ତ୍ତା ଏବଂ ସର୍ବଶେଷ ଉପଭୋକ୍ତା ବାର୍ତ୍ତା ଦୂରତାକୁ ଖାତିର ନକରି ସର୍ବଦା ଭର୍ବାଟିମ୍ ରଖାଯାଏ। କ othing ଣସି ଜିନିଷକୁ ସିଧା ସଳଖ ଡ୍ରପ୍ କରାଯାଏ ନାହିଁ, ଏବଂ `light` ବ୍ୟାଣ୍ଡ ପଠାଯାଇଥିବା ଡିଫଲ୍ଟ ସହିତ ଉପଲବ୍ଧ ନୁହେଁ (`light` `verbatim` ସହିତ ସମାନ)।

#### କୋଡ୍ ଉଦାହରଣ।

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ।

ପ୍ରଗତିଶୀଳ ବାର୍ଦ୍ଧକ୍ୟ ହେଉଛି।** ସର୍ବଦା ଅନ୍** `aggressive` ମୋଡ୍ — ପାଇଁ ଏହା `compressAggressive()` ର ଷ୍ଟେପ୍ 2। ଅଲ୍ଟ୍ରା ମୋଡ୍ ଏହାକୁ ଚଲାଇ ନଥାଏ। ଏହା ବିଶେଷ ଭାବରେ ପ୍ରଭାବଶାଳୀ:

- ଦୀର୍ଘ ଚାଲୁଥିବା କୋଡିଂ ଅଧିବେଶନ।
- ବହୁ ଦିନର ବାର୍ତ୍ତାଳାପ।
- ଅନେକ ଟୁଲ୍ କଲ୍ ସହିତ ଏଜେଣ୍ଟ୍ ୱାର୍କଫ୍ଲୋ।

### ଗୁମ୍ଫା ଆଉଟପୁଟ୍ ମୋଡ୍।

ଗୁମ୍ଫା ଆଉଟପୁଟ୍ ମୋଡ୍ ଯୋଗ କରେ।** ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ନିର୍ଦ୍ଦେଶାବଳୀ।** ଟେର୍ସ ଆଉଟପୁଟ୍ — ପାଇଁ ମଡେଲକୁ ନିଜେ ପଚାରିଥାଏ `lite` ସ୍ତର ସଂକ୍ଷିପ୍ତ ଉତ୍ତର ମାଗେ ଯାହା ପୂର୍ଣ୍ଣ ବାକ୍ୟ ରଖେ, `full` ଏହାକୁ "ସ୍ମାର୍ଟ ଗୁମ୍ଫା ପରି ଟେର୍ସକୁ ଜବାବ ଦେବାକୁ" କହିଥାଏ, ଏବଂ `ultra` ଟେଲିଗ୍ରାଫିକ୍ ଆଉଟପୁଟ୍ ମାଗେ। ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକ କେବଳ ପଚାର, ସେମାନେ ଏହାକୁ ଗ୍ୟାରେଣ୍ଟି କରିପାରିବେ ନାହିଁ। ଅନୁରୋଧ ସେମାନଙ୍କୁ `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ମାଧ୍ୟମରେ ଗ୍ରହଣ କରେ: `open-sse/handlers/chatCore.ts` ପ୍ରଥମେ ବ୍ୟାକ୍-କମ୍ପିଟ୍ ଶିମ୍ ( `open-sse/services/compression/outputStyles/backCompat.ts` ରେ`resolveOutputStyleSelection()` ) ସହିତ ଚୟନକୁ ସମାଧାନ କରେ, ଯାହାକି `outputStyles` ଖାଲି ଥିବାବେଳେ `cavemanOutputMode.intensity` ରେ `terse-prose` ଆଉଟପୁଟ୍ ଶ style ଳୀରେ ଏକ ସକ୍ଷମ `cavemanOutputMode` ମାନଚିତ୍ର କରେ (ନିମ୍ନରେ ବ୍ୟାକ୍-କମ୍ପିଟ୍ ଦେଖନ୍ତୁ); ଏକ ଖାଲି `outputStyles` ଚୟନ ଯେପରି ବ୍ୟବହାର କରାଯାଏ, ଏବଂ `cavemanOutputMode.enabled` ଏବଂ `intensity` ତା’ପରେ କ effect ଣସି ପ୍ରଭାବ ପକାଇବ ନାହିଁ, ଯେତେବେଳେ କି ଏହାର `autoClarity` ଟୋଗଲ୍ ପ୍ରଯୁଜ୍ୟ। `outputMode.ts` ନିର୍ଦ୍ଦେଶ ପାଠ୍ୟ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), ବିଷୟବସ୍ତୁ ବାଇପାସ୍ ଏବଂ ଇଞ୍ଜେକ୍ସନ୍ ବ୍ୟବହାର କରୁଥିବା ପ୍ଲେସମେଣ୍ଟ ହେଲପର୍ ଧାରଣ କରେ। ଏହାର ନିଜସ୍ୱ `applyCavemanOutputMode()` ଇଞ୍ଜେକ୍ଟରର କ production ଣସି ଉତ୍ପାଦନ କଲର୍ ନାହିଁ।

#### ଏହା କିପରି କାମ କରେ।

ଏହି ମୋଡ୍ ଇନପୁଟ୍ କୁ ସଙ୍କୋଚନ କରେ ନାହିଁ। ଏହା ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟରେ ଏକ ନିର୍ଦ୍ଦେଶନାମା ଯୋଗ କରିଥାଏ (ନିମ୍ନରେ ଇଞ୍ଜେକ୍ସନ୍ କିପରି କାମ କରେ ଦେଖନ୍ତୁ), ଏବଂ ଅନୁରୋଧ ପାଇଁ ମନୋନୀତ ଯେକ input ଣସି ଇନପୁଟ୍ ସଙ୍କୋଚନ ମୋଡ୍ ବର୍ତ୍ତମାନ ପର୍ଯ୍ୟନ୍ତ ଚାଲିଥାଏ, ଯାହା ବର୍ତ୍ତମାନ ବ୍ଲକ୍ ବହନ କରେ। ଅଂଶୀଦାର ସୀମା ଧାରା ଆଗରେ ଯାହା ପ୍ରତ୍ୟେକ ସ୍ତର ସହିତ ଶେଷ ହୁଏ, ଇଂରାଜୀ `full` ସ୍ତର ପ s ଼ିଥାଏ:

> URLs ସ୍ମାର୍ଟ ଗୁମ୍ଫା ଭଳି ଟେର୍ସକୁ ଜବାବ ଦିଅ। ପ୍ରବନ୍ଧଗୁଡିକ (a/an/the), ଫିଲର୍ (just/really/basically/actually/simply), ପ୍ରସନ୍ନତା, ହେଡିଂ OK ଖଣ୍ଡଗୁଡ଼ିକ

ଏହା ବିଶେଷ ଭାବରେ ଭଲ କାମ କରେ:

- କୋଡ୍ ଉତ୍ପାଦନ (ଟର୍ସର୍ ଆଉଟପୁଟ୍ = କମ୍ ଟୋକେନ୍)
- ଦ୍ରୁତ ପ୍ରଶ୍ନ ଏବଂ ଉତ୍ତର (ବିସ୍ତୃତ ବ୍ୟାଖ୍ୟା ପାଇଁ କ need ଣସି ଆବଶ୍ୟକତା ନାହିଁ)
- ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ (ସର୍ବାଧିକ ଥ୍ରୋପପୁଟ୍)

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ।

ଗୁମ୍ଫା ଆଉଟପୁଟ୍ ମୋଡ୍ ହେଉଛି।** ଅପ୍ଟ-ଇନ୍** । ସଙ୍କୋଚନ ସହିତ (`enabled: true`, ସଙ୍କୋଚନ ସେଟିଂସମୂହ ପୃଷ୍ଠାରେ ମାଷ୍ଟର ଟୋଗଲ୍), ଏହାକୁ `cavemanOutputMode.enabled` ସହିତ ଟର୍ନ୍ ଅନ୍ କରନ୍ତୁ। `intensity` `lite`, `full` କିମ୍ବା `ultra` ବାଛିଥାଏ:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ଏକ ସଙ୍କୋଚନ କମ୍ବୋ।** ଆଉଟପୁଟ୍ ମୋଡ୍** ଟୋଗଲ୍ (`outputMode`, `outputModeIntensity` ରେ ସ୍ତର) ଅନୁରୋଧ ପାଇଁ ସମାନ ସୁଇଚ୍ ସେଟ୍ କରେ ଯାହା କମ୍ବୋ ପ୍ରଯୁଜ୍ୟ, ଏବଂ `omniroute_set_compression_engine` MCP ସାଧନ ଏହାକୁ ଏହାର ବୁଲିଅନ୍ `outputMode` ଆର୍ଗୁମେଣ୍ଟ ମାଧ୍ୟମରେ ଲେଖେ। ଏକ ଖାଲି ନଥିବା `outputStyles` ଚୟନ ଏହି ସୁଇଚ୍ ଉପରେ ପ୍ରାଧାନ୍ୟ ଦେଇଥାଏ। ଡ୍ୟାସବୋର୍ଡରେ, ସକ୍ଷମ କରିବା।** ଟେର୍ ଗଦ୍ୟ।** ଆଉଟପୁଟ୍ ଶ style ଳୀ ସମାନ ବ୍ଲକକୁ ଇଞ୍ଜେକ୍ସନ୍ କରେ (ନିମ୍ନରେ ଆଉଟପୁଟ୍ ଶ yles ଳୀ ଦେଖନ୍ତୁ)।

ପ୍ରତ୍ୟେକ ଶ style ଳୀ ତିନୋଟି ତୀବ୍ରତା ସ୍ତର — `lite`, `full`, `ultra` — ପଠାଇଥାଏ ଏବଂ ପ୍ରତ୍ୟେକ ସ୍ତର ଅଂଶୀଦାର ସୀମା ଧାରା ( `outputMode.ts` ରେ`SHARED_BOUNDARIES` ) ସହିତ ସମାପ୍ତ ହୁଏ, ଯାହାକି କୋଡ୍ ବ୍ଲକ୍, ଫାଇଲ୍ ପଥ, ନିର୍ଦ୍ଦେଶ, ତ୍ରୁଟି ଏବଂ URLs ସଠିକ୍ ରଖେ। `terse-prose` ଏବଂ `terse-cjk` ସ୍ତରର ପାଠ୍ୟ ସେହି ତାଲିକାରେ ପରିଚାୟକ ଯୋଗ କରେ।

`terse-cjk` ଦୁଇଟି ସ୍ଥାନରେ `zh` କୁ ଲୋକାଲ୍-ଗେଟେଡ୍। ସଙ୍କୋଚନ ସେଟିଂସମୂହ ପୃଷ୍ଠା ଏହାର ଧାଡି ତାଲିକାଭୁକ୍ତ କରେ ଯେତେବେଳେ ଡ୍ୟାସବୋର୍ଡ UI ଭାଷା ଚାଇନିଜ୍ (`zh-CN` କିମ୍ବା `zh-TW`), ଏବଂ `applyOutputStyles()` ଯେତେବେଳେ ଇଞ୍ଜେକ୍ସନ ଦେଇଥାଏ ଯେତେବେଳେ ଅନୁରୋଧର ସମାଧାନ ହୋଇଥିବା ଭାଷା (ନିମ୍ନରେ ଭାଷା ଚୟନ ଦେଖନ୍ତୁ) `zh` ଅଟେ। ଧାଡି ଲୁଚାଇବା ଏକ ସଞ୍ଚିତ `terse-cjk` ଚୟନକୁ ସଫା କରେ ନାହିଁ: API ସେଟିଂସମୂହ ଯେକ style ଣସି ଶ style ଳୀ id କୁ ଗ୍ରହଣ କରେ, ଏବଂ ପୃଷ୍ଠାରେ ଅନ୍ୟ ଶ yles ଳୀଗୁଡ଼ିକୁ ସଂରକ୍ଷଣ କରିବା ଏହାକୁ ରଖେ। ଅନୁରୋଧ ସମୟରେ, `applyOutputStyles()` ଭାଷା ଯାଞ୍ଚ ହେଉଛି ଏକମାତ୍ର ଲୋକାଲ୍ ଗେଟ୍।

#### ଇଞ୍ଜେକ୍ସନ୍ କିପରି କାମ କରେ।

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) କାଟାଲଗ୍ ବିରୁଦ୍ଧରେ ଚୟନକୁ ସମାଧାନ କରେ (ଅଜ୍ଞାତ id ଏବଂ ଲୋକାଲ୍-ମେଳ ଖାଇ ନଥିବା ଶ yles ଳୀଗୁଡିକ ଡ୍ରପ୍ ହୁଏ, କଦାପି ତ୍ରୁଟି ହୁଏ ନାହିଁ; ଏକ ଚୟନ ଯାହା ଶରୀରକୁ ଅପରିବର୍ତ୍ତିତ ରଖେ ନାହିଁ, `no_styles` ଭାବରେ ଛାଡି ଦିଆଯାଏ), ମନୋନୀତ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ କାଟାଲଗ୍ କ୍ରମରେ ଯୋଡିଥାଏ, ସୀମା ଧାରାକୁ ଯୋଡିଥାଏ।** ଥରେ।** `SAFETY_BOUNDARIES` `less-code` `ponytail` `[OmniRoute Output Styles]` ଯେତେବେଳେ ସମାଧାନ ହୋଇଥିବା ଭାଷା (ନିମ୍ନରେ ଭାଷା ଚୟନ ଦେଖନ୍ତୁ) ର ଏକ ଅନୁବାଦ ଅଛି, ସ୍ଥାନୀୟ ପରିବର୍ତ୍ତେ ଇଂରାଜୀ ପରିବର୍ତ୍ତେ ଇଞ୍ଜେକ୍ସନ ଦିଆଯାଏ।

ଖାଲି ନଥିବା `messages` ଆରେ ଥିବା ଏକ ଶରୀର ଉପରେ, idempotency ଯାଞ୍ଚ ବିଷୟବସ୍ତୁ ବାଇପାସ୍ ପୂର୍ବରୁ ଚାଲିଥାଏ: ଯେତେବେଳେ `[OmniRoute Output Styles]` ମାର୍କର ଟପ୍-ଲେଭଲ୍ `system` ଫିଲ୍ଡରେ (ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ କିମ୍ବା କଣ୍ଟେଣ୍ଟ୍-ବ୍ଲକ୍ ଆରେ) କିମ୍ବା ଷ୍ଟ୍ରିଙ୍ଗ୍ କଣ୍ଟେଣ୍ଟ୍ ସହିତ ସିଷ୍ଟମ୍ ମେସେଜ୍ ରେ, ଶରୀର `already_applied` ଭାବରେ ଅପରିବର୍ତ୍ତିତ ରହିଥାଏ ଏବଂ କ key ଣସି କୀୱାର୍ଡ ଯାଞ୍ଚ ଚାଲିନଥାଏ। ଅନ୍ୟଥା, ଏକ ବିଷୟବସ୍ତୁ ବାଇପାସ୍ ( `open-sse/services/compression/outputMode.ts` ରେ`shouldBypassCavemanOutputMode()` ) ଶେଷ ତିନୋଟି ସନ୍ଦେଶର ପାଠ୍ୟ ଯାଞ୍ଚ କରେ, ସେମାନଙ୍କର ଭୂମିକା ଯାହା ହେଉ, ଏବଂ ସେହି ପାଠ୍ୟ ଯେତେବେଳେ ଏହାର ସୁରକ୍ଷା, ଅଦୃଶ୍ୟ-କ୍ରିୟା କିମ୍ବା ସ୍ପଷ୍ଟୀକରଣ `migrate` ଶବ୍ଦ, କିମ୍ବା ଏକ କ୍ରମ-ସମ୍ବେଦନଶୀଳ କ୍ରମ ସହିତ ମେଳ `drop` ସେତେବେଳେ ଶ yles ଳୀକୁ ଛାଡିଦିଏ: `first`, `then`, `after that`, `before`, `rollback` କିମ୍ବା `backup` `delete` `release` `deploy` ବାଇପାସ୍ ଚାଲିଥିବାବେଳେ** ଅଟୋ-କ୍ଲିରିଟି ବାଇପାସ୍।** ଟୋଗଲ୍ (`cavemanOutputMode.autoClarity`, ଡିଫଲ୍ଟ ଭାବରେ) ଅନ୍ ଅଛି; ଟୋଗଲ୍ ବନ୍ଦ କରିବା କୀୱାର୍ଡ ଯାଞ୍ଚକୁ ଛାଡିଦିଏ।

ଯେତେବେଳେ ବାଇପାସ୍ ଟର୍ନ୍ ଦେଇ ଦିଏ, `placeSystemInstruction()` (ସମାନ ଫାଇଲ୍), ଯାହାକି କ z ଣସି ନୂତନ `messages[0]` ସୃଷ୍ଟି କରେ ନାହିଁ, ବ୍ଲକକୁ ଏହା ମଧ୍ୟରୁ ପ୍ରଥମରେ ସ୍ଥାନିତ କରେ:

1. ଷ୍ଟ୍ରିଙ୍ଗ୍ ବିଷୟବସ୍ତୁ ସହିତ ଏକ ଅଗ୍ରଣୀ ସିଷ୍ଟମ୍ ବାର୍ତ୍ତା: ବ୍ଲକ୍ ଏହାର ପାଠ୍ୟ ପରେ ଯୋଡା ଯାଇଛି।
2. ଶୀର୍ଷ-ସ୍ତରୀୟ `system` କ୍ଷେତ୍ର: ଏକ ଷ୍ଟ୍ରିଙ୍ଗର ପାଠ୍ୟ ପରେ ବ୍ଲକଟି ଯୋଡା ଯାଇଥାଏ, କିମ୍ବା ଏକ ବିଷୟବସ୍ତୁ-ବ୍ଲକ ଆରେ ଏକ ନୂତନ ପାଠ୍ୟ ବ୍ଲକ ଭାବରେ ଯୋଡା ଯାଇଥାଏ।
3. ଷ୍ଟ୍ରିଙ୍ଗ୍ ବିଷୟବସ୍ତୁ ସହିତ ପ୍ରଥମ ପରବର୍ତ୍ତୀ ସିଷ୍ଟମ୍ ବାର୍ତ୍ତା: ଏହାର ପାଠ୍ୟ ପରେ ବ୍ଲକ୍ ଯୋଡା ଯାଇଛି।
4. ଉପରୋକ୍ତ ମଧ୍ୟରୁ କ None ଣସିଟି ନୁହେଁ: `messages` ଶେଷରେ ବ୍ଲକ ଏକ ନୂତନ ସିଷ୍ଟମ ସନ୍ଦେଶକୁ ଯାଏ।

`messages` ଆରେ ବିନା ଶରୀରରେ (କିମ୍ବା ଏକ ଖାଲି ସହିତ), କ content ଣସି ବିଷୟବସ୍ତୁ ବାଇପାସ୍ ଚାଲିବ ନାହିଁ ଏବଂ ଏକ ଶୀର୍ଷ ସ୍ତରୀୟ `system` କ୍ଷେତ୍ର ପରାମର୍ଶ କରାଯାଏ ନାହିଁ। ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ `instructions` ଫିଲ୍ଡର ଟେକ୍ସଟ୍ ପରେ ବ୍ଲକ୍ ଯୋଡା ଯାଇଥାଏ, ଯେପର୍ଯ୍ୟନ୍ତ ସେହି ଫିଲ୍ଡରେ `[OmniRoute Output Styles]` ମାର୍କର୍ ଥାଏ, ଯେଉଁ କ୍ଷେତ୍ରରେ ଶରୀର `already_applied` ଭାବରେ ଅପରିବର୍ତ୍ତିତ ରହିଥାଏ। ଯେତେବେଳେ ଶରୀରର କ string ଣସି ଷ୍ଟ୍ରିଙ୍ଗ୍ `instructions` ଫିଲ୍ଡ ନାହିଁ କିନ୍ତୁ `input` (ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ କିମ୍ବା ଏକ ଆରେ) ବହନ କରେ, ସେହି କ୍ଷେତ୍ରଟି ଯେକ any ଣସି ଅଣ-ଷ୍ଟ୍ରିଙ୍ଗ୍ ମୂଲ୍ୟକୁ ବଦଳାଇ `instructions` ହୋଇଯାଏ। ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ `instructions` ଫିଲ୍ଡ କିମ୍ବା ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ କିମ୍ବା ଆରେ `input` ସହିତ ଏକ ଶରୀର ଅପରିବର୍ତ୍ତିତ ରହି `no_messages` ଭାବରେ ଛାଡି ଦିଆଯାଏ।

#### କିପରି ସକ୍ଷମ କରିବେ।

ଡ୍ୟାସବୋର୍ଡରେ:** ସଙ୍କୋଚନ ପ୍ରସଙ୍ଗ → ସଙ୍କୋଚନ ସେଟିଂସମୂହ।** (`/dashboard/context/settings`), ଆଉଟପୁଟ୍ ଶ yles ଳୀ ବିଭାଗ: on/off ଟୋଗଲ୍ ଏବଂ ଏକ ସ୍ତର ଚୟନକର୍ତ୍ତା ସହିତ ଶ style ଳୀ ପ୍ରତି ଗୋଟିଏ ଧାଡି। ସଙ୍କୋଚନ ନିଜେ ଥିବାବେଳେ ଶ yles ଳୀଗୁଡିକ ଇଞ୍ଜେକ୍ସନ ଦିଅନ୍ତି (ପୃଷ୍ଠାର ମାଷ୍ଟର ଟୋଗଲ୍, `enabled`)। The** ଅଟୋ-କ୍ଲିରିଟି ବାଇପାସ୍।** ଟୋଗଲ୍ ହେଉଛି** ଗୁମ୍ଫା** ପୃଷ୍ଠା (`/dashboard/context/caveman`), ଏଥିରେ।** ଆଉଟପୁଟ୍ ମୋଡ୍** କାର୍ଡ ପ୍ରୋଗ୍ରାମେଟିକ୍ ଭାବରେ, ସଙ୍କୋଚନ ବିନ୍ୟାସ ଚୟନକୁ ସ୍ଥିର କରିଥାଏ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ବ୍ୟାକ୍-ସୁସଙ୍ଗତ: ଯେତେବେଳେ `outputStyles` ଖାଲି ଅଛି, ପୁରୁଣା `cavemanOutputMode.enabled` `cavemanOutputMode.intensity` ରେ `terse-prose` କୁ ମାନଚିତ୍ର ସେଟିଂ କରୁଛି। ବ୍ଲକଟି `[OmniRoute Output Styles]` ମାର୍କର୍ ସହିତ ଆରମ୍ଭ ହୁଏ, ଯେଉଁଠାରେ ପୁରୁଣା `applyCavemanOutputMode()` ଇଞ୍ଜେକ୍ଟର `[OmniRoute Caveman Output Mode]` ଲେଖିଥିଲେ। ମାର୍କର ତଳେ, ପାଠ୍ୟ en, pt-BR, es, de, fr, it, ru, id ଏବଂ vi ରେ ପୁରୁଣା ଇଞ୍ଜେକ୍ସନ୍ ସହିତ ମେଳ ହୁଏ। ja ଏବଂ zh ରେ ଏହା ସୀମା ଧାରା ପୂର୍ବରୁ ଗୋଟିଏ ଅତିରିକ୍ତ ସ୍ଥାନ ବହନ କରେ। `terse-prose` pt-BR, es, de, fr, it, ru, zh, ja, id ଏବଂ vi ରେ ଅନୁବାଦ କରେ, ତେଣୁ ଏକ ଅନୁରୋଧ ଯାହାର ସମାଧାନ ଭାଷା `hu` ଇଂରାଜୀ ପାଠ ପାଇଥାଏ ଯେଉଁଠାରେ ଉତ୍ତରାଧିକାରୀ ଇଞ୍ଜେକ୍ଟର ଏହାର ହଙ୍ଗେରୀ ଭାଷା ବ୍ୟବହାର କରିଥିଲେ।

ଆଉଟପୁଟ୍-ଷ୍ଟାଇଲ୍ ଭାଷା ଚୟନ ( `outputStyles/apply.ts` ରେ`resolveOutputStyleLanguage()` ): `languageConfig.enabled` ସହିତ, `autoDetect` ନମୁନାଗୁଡ଼ିକର ଅନୁରୋଧର `messages` ଆରେରେ ସର୍ବଶେଷ ଉପଭୋକ୍ତା ବାର୍ତ୍ତା ଯାହାର ପାଠ୍ୟ (ଷ୍ଟ୍ରିଙ୍ଗ୍ ବିଷୟବସ୍ତୁ, କିମ୍ବା ଏହାର ବିଷୟବସ୍ତୁ ଅଂଶଗୁଡ଼ିକର `text` ) ଅଛି ଏବଂ ଏହା ଉପରେ କ୍ୟାଭମ୍ୟାନ୍ ଇଞ୍ଜିନର ଡିଟେକ୍ଟର (`detectCompressionLanguage()`) ଚଲାଇଥାଏ। ଡିଟେକ୍ଟର ହାନ ଅକ୍ଷର ସହିତ ପାଠ୍ୟ ପାଇଁ `zh` ଫେରସ୍ତ କରେ ଏବଂ କ no ଣସି କାନା ନାହିଁ; ଅନ୍ୟଥା ଏହା `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` ଏବଂ `id` ର ସର୍ବାଧିକ ସୂଚକ ମେଳକ ଥାଏ, ଏବଂ `en` ଯେତେବେଳେ — ପାଠ୍ୟ ସହିତ ମେଳ ହୁଏ ନାହିଁ ତାହା ଇଂରାଜୀ ପାଇଥାଏ, `defaultLanguage`, ଏବଂ `vi` କେବେବି ଚିହ୍ନଟ ହୁଏ ନାହିଁ ଯଦିଓ ଶ yles ଳୀ `vi` ପାଠ୍ୟ ପଠାଏ। ଏକ ପ୍ରତିକ୍ରିୟା API ଶରୀର `input` ରେ ଏହାର ମୋଡ ରଖେ, ଯାହା ନମୁନା ହୋଇନଥାଏ, ତେଣୁ ଏହା `defaultLanguage`, ତା’ପରେ ଇଂରାଜୀ ପାଇଥାଏ। ଯେତେବେଳେ `messages` ରେ କ user ଣସି ଉପଭୋକ୍ତା ସନ୍ଦେଶର ପାଠ୍ୟ ନାହିଁ, କିମ୍ବା `autoDetect` ବନ୍ଦ ସହିତ, `defaultLanguage` ପ୍ରଯୁଜ୍ୟ, ତେବେ ଇଂରାଜୀ। `languageConfig.enabled` ବନ୍ଦ ସହିତ, ଭାଷା ହେଉଛି ଇଂରାଜୀ — ଯେପର୍ଯ୍ୟନ୍ତ ଏକ ସଙ୍କୋଚନ କମ୍ବୋ ଅନୁରୋଧରେ ପ୍ରଯୁଜ୍ୟ ନହୁଏ (ଅନୁରୋଧର ରାଉଟିଙ୍ଗ୍ କମ୍ବୋକୁ ଦିଆଯାଇଥିବା ଏକ କମ୍ବୋ, କିମ୍ବା ଡିଫଲ୍ଟ ସଙ୍କୋଚନ କମ୍ବୋ chatCore ବିଲ୍ଟ-ଇନ୍ ଷ୍ଟାକ୍ ପାଇପଲାଇନ ପାଇଁ ଫେରିଯାଏ): ଏକ କମ୍ବୋ ପ୍ରୟୋଗ କରିବା ସେହି ଅନୁରୋଧ ପାଇଁ `languageConfig.enabled` ଟର୍ନ୍ କରେ ଏବଂ କମ୍ବୋ ର ଭାଷା ପ୍ୟାକ୍ ମଧ୍ୟରୁ `defaultLanguage` ସେଟ୍ କରେ, ଯଦି ଏହା କମ୍ବୋ ଭାଷା ପ୍ୟାକ୍ ଅଟେ, ତେବେ ଏହା କମ୍ବୋ ଭାଷାର ପ୍ୟାକ୍ ଅଟେ। `en` କୁ), ଯେତେବେଳେ ସଞ୍ଚିତ `autoDetect` (ଡିଫଲ୍ଟ ଭାବରେ) ତଥାପି ପ୍ରଯୁଜ୍ୟ। କ୍ୟାଭମ୍ୟାନ୍ ଇନପୁଟ୍ ଇଞ୍ଜିନ୍ ଏହାର ନିୟମ-ପ୍ୟାକ୍ ଭାଷାକୁ ଟେକ୍ସଟ୍ ଅଂଶରେ ଭିନ୍ନ ଭାବରେ — ବାଛିଥାଏ ଏବଂ, ଅଟୋ-ଡିଟେକ୍ଟ ଅଫ୍ ସହିତ, `enabledPacks` ରେ ଗେଟ୍ ହୋଇଥିଲା।

× ଭାଷା ମ୍ୟାଟ୍ରିକ୍ସ ଶ style ଳୀ `tests/unit/compression/output-styles-i18n-matrix.test.ts` ଦ୍ୱାରା ପିନ୍ ହୋଇଛି: ପ୍ରତ୍ୟେକ କାଟାଲଗ୍ ଶ style ଳୀ ପରୀକ୍ଷଣର `BASELINE_LANGUAGES` ରେ ଏକ ପ୍ରବେଶ ଆବଶ୍ୟକ କରେ। ଏକ ଶ style ଳୀ ଯାହା ଲୋକାଲ୍-ଗେଟେଡ୍ ନୁହେଁ, ନିଶ୍ଚିତ ଭାବରେ ଏକ pt-BR ଅନୁବାଦ ପଠାଇବ (ଲୋକାଲ୍-ଗେଟେଡ୍ `terse-cjk` ଏହି ନିୟମରୁ ମୁକ୍ତ) ଯଦି ଏହା `KNOWN_ENGLISH_ONLY` ରେ ତାଲିକାଭୁକ୍ତ ନହୁଏ, ଯାହାକି ସମସ୍ତ — ରେ କ translations ଣସି ଅନୁବାଦ ବିନା ଶ yles ଳୀ ଧାରଣ କରିପାରିବ ଯାହା ଏକ ତାଲିକାଭୁକ୍ତ ଶ style ଳୀରେ କ translation ଣସି ଅନୁବାଦ ପରୀକ୍ଷା ବିଫଳ ହେବ। ଏବଂ ଏକ ଶ style ଳୀ ପରୀକ୍ଷଣରେ ବିଫଳ ହୁଏ ଯେତେବେଳେ ଏହା ଏକ ଭାଷା ହରାଇଥାଏ ଯାହା ଏହାର `BASELINE_LANGUAGES` ପ୍ରବେଶ ତାଲିକା ଅଟେ। ଏକ ଶ style ଳୀ ଯୋଡିବାକୁ, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) ଦେଖନ୍ତୁ।

### ସାଧନ ଫଳାଫଳ ସଙ୍କୋଚନ।

`open-sse/services/compression/toolResultCompressor.ts` ରେ`compressToolResult()` ସାଧନ-ଫଳାଫଳ ପାଠ୍ୟ ସହିତ ସଙ୍କୋଚନ କରେ।** 5 ରଣନୀତି।** । ଏହା ସେମାନଙ୍କୁ ଏହି କ୍ରମରେ ଚେଷ୍ଟା କରେ, ଏବଂ ପ୍ରଥମ ସକ୍ଷମ ରଣନୀତି ଯାହାର ଯାଞ୍ଚ ବିଷୟବସ୍ତୁ ସହିତ ମେଳ ହୁଏ ଫଳାଫଳ ନିର୍ଣ୍ଣୟ କରେ:

1. **`fileContent`** : 3 କିମ୍ବା ଅଧିକ ଧାଡିର ବିଷୟବସ୍ତୁ ଯେଉଁଥିରେ ଅନ୍ତତ least ପକ୍ଷେ ଗୋଟିଏ ଧାଡି, ଅଗ୍ରଣୀ ଇଣ୍ଡେଣ୍ଟେସନ୍ କୁ ଅଣଦେଖା କରି `import `, `export `, `function `, `class `, `const `, `let `, `var ` କିମ୍ବା `return ` (କୀୱାର୍ଡ ପ୍ଲସ୍ ସ୍ପେସ୍) ସହିତ ଆରମ୍ଭ ହୁଏ, କିମ୍ବା `if`, `for` କିମ୍ବା `while` ଦ୍ z ାରା `(` କିମ୍ବା ` (` ଦ୍ first ାରା ଏହାର ପ୍ରଥମ 20 ଏବଂ ଶେଷ 5 ଧାଡି ଚିହ୍ନିତ ହୁଏ।
2. **`grepSearch`** : `<path>:<digits>:` ଫର୍ମର ଅତି କମରେ ଗୋଟିଏ ଧାଡି ସହିତ ବିଷୟବସ୍ତୁ, ଯେଉଁଠାରେ ପ୍ରଥମ କୋଲନ୍ ପୂର୍ବରୁ ପାଠ୍ୟର କ ites ଣସି ଧଳା ସ୍ଥାନ ନାହିଁ, କେବଳ ସେହି ରେଖାଗୁଡ଼ିକୁ ରଖେ, ସର୍ବାଧିକ 30, ତା’ପରେ ଅନ୍ୟ କ matches ଣସି ମେଳ ଗଣନା ଏବଂ ମେଳ ହୋଇଥିବା ଫାଇଲଗୁଡ଼ିକର ତାଲିକା; ଅନ୍ୟ ସମସ୍ତ ରେଖା ଡ୍ରପ୍ ହୋଇଛି। ରଣନୀତିକୁ ଟ୍ରିଗର କରିବା ପାଇଁ ଏହିପରି ଗୋଟିଏ ରେଖା ଯଥେଷ୍ଟ, ତେଣୁ `12:30:45` ପରି ଏକ ଟାଇମଷ୍ଟ୍ୟାମ୍ପରୁ ଆରମ୍ଭ ହୋଇଥିବା ଏକ ଲଗ୍ ଲାଇନ୍ ମଧ୍ୟ ଗଣନା କରେ।
3. **`shellOutput`** : ଆଉଟପୁଟ୍ ଯାହାକି ଏକ ANSI CSI କ୍ରମ ଧାରଣ କରିଥାଏ (`ESC[` ତାପରେ ଅଙ୍କ କିମ୍ବା ସେମିକଲନ୍ ତାପରେ ଏକ ଅକ୍ଷର, ରଙ୍ଗ ସଂକେତ ପରି) କିମ୍ବା ପାଠ୍ୟର ଯେକ anywhere ଣସି ସ୍ଥାନରେ ହ୍ ites ାଇଟସ୍ପେସ୍ ଦ୍ by ାରା ଏକ `$` ସେହି କ୍ରମଗୁଡିକ ହରାଇଥାଏ (ଅନ୍ୟ ପଳାୟନ ଯେପରିକି `ESC[?25l` କିମ୍ବା OSC ୱିଣ୍ଡୋ-ଟାଇଟଲ୍ କ୍ରମ, ରଖାଯାଇଥାଏ) ଏବଂ ଏହାର ଶେଷ 50 ଧାଡିଗୁଡିକ କ୍ରମାଗତ ବାରମ୍ବାର ଧାଡିଗୁଡିକ ନଷ୍ଟ ହୋଇଯାଏ। କାରଣ ଏହି ଚେକ୍ `json` ଏବଂ `errorMessage`, JSON କିମ୍ବା ତ୍ରୁଟି ଆଉଟପୁଟ୍ ପୂର୍ବରୁ ଚାଲିଥାଏ ଯାହାକି `shellOutput` ଚାଲୁଥିବା ସମୟରେ ଏପରି `$` ଧାରଣ କରିଥାଏ।
4. **`json`** : `{` କିମ୍ବା `[` (ଇଚ୍ଛାଧୀନ ହ୍ ites ାଇଟସ୍ପେସ୍ ପରେ) ଏବଂ ପାର୍ସରୁ ଆରମ୍ଭ ହୋଇଥିବା 2,000 ଅକ୍ଷରରୁ ଅଧିକ JSON ପେଲୋଡ୍ ସଂକ୍ଷେପରେ ସଂକ୍ଷିପ୍ତ ହୋଇଛି: 7 ରୁ ଅଧିକ ଆଇଟମ୍ ର ଏକ ଆରେ ଏହାର ପ୍ରଥମ 5 ଏବଂ ଶେଷ 2 ଆଇଟମ୍ ଏବଂ ଏହାର ସମୁଦାୟ ଗଣନାକୁ ରଖେ, ଏବଂ ଏକ ବସ୍ତୁ ଏହାର ପ୍ରଥମ 20 କିଗୁଡ଼ିକୁ ରଖେ, ପ୍ରତ୍ୟେକ ନେଷ୍ଟେଡ୍ ବସ୍ତୁ କିମ୍ବା ଆରେ ମୂଲ୍ୟ `{…N keys}` ପ୍ଲେସହୋଲ୍ଡର୍ ଦ୍ୱାରା ବଦଳାଯାଇଥାଏ (N ଆରେ ଏହାର ଲମ୍ବ)। ସମ୍ପୁର୍ଣ୍ଣ, ତେଣୁ କ keys ଣସି ନଷ୍ଟ ହୋଇଥିବା ମୂଲ୍ୟ ସହିତ 20 କି କିମ୍ବା ତା’ଠାରୁ କମ୍ ବସ୍ତୁ କେବଳ `_remaining_<N>_keys` — ପୁନ - ଇଣ୍ଡେଣ୍ଟ କରାଯାଇଥାଏ, ଏକ କ୍ଷୁଦ୍ର ଅକ୍ଷର ହାସଲ କରେ ଏବଂ ଅପରିବର୍ତ୍ତିତ ରହିଥାଏ।
5. **`errorMessage`** : ଆଉଟପୁଟ୍, ଯେକ anywhere ଣସି ସ୍ଥାନରେ ଏବଂ ଯେକ any ଣସି ଅକ୍ଷର କ୍ଷେତ୍ରରେ, `error:`, `error ` (ଶବ୍ଦଟି ଏକ ସ୍ପେସ୍ ଦ୍ୱାରା ଅନୁସରଣ ହୁଏ, ଯେପରି `no error found` ପରି), `[error]`, `exception:`, `exception `, `[exception]` କିମ୍ବା `traceback` ଏହାର ପ୍ରଥମ ଧାଡି, ପରବର୍ତ୍ତୀ 10 ଧାଡି ଏବଂ ଶେଷ 3, ସେମାନଙ୍କ ମଧ୍ୟରେ ରେଖା ସ୍ଥାନରେ `… [N frames elided] …` ମାର୍କର ସହିତ ରଖେ। ମାର୍କରଟି ଦୃଶ୍ୟମାନ ହୁଏ ଯେତେବେଳେ 13 ରୁ ଅଧିକ ଧାଡି ପ୍ରଥମ ଧାଡି ଅନୁସରଣ କରେ, ତେଣୁ 14 ଧାଡି କିମ୍ବା ତା’ଠାରୁ କମ୍ ତ୍ରୁଟି ଆଉଟପୁଟ୍ ଛୋଟ ହୋଇନଥାଏ (12 କିମ୍ବା 13 ଧାଡିରେ ଶେଷ 3 ପୁନରାବୃତ୍ତି ଧାଡି ପୂର୍ବରୁ ରଖାଯାଇଥିଲା)।

ଏକ ରଣନୀତି ମେଳ ହେବା ପରେ, ଯାହାକି କିଛି ସଞ୍ଚୟ କରେ ନାହିଁ, ପରବର୍ତ୍ତୀ ରଣନୀତି ଚେଷ୍ଟା କରାଯାଏ ନାହିଁ। ଯେତେବେଳେ ମେଳଣ କ strategy ଶଳ କ estimated ଣସି ଆନୁମାନିକ ଟୋକେନ୍ (ଦ length ର୍ଘ୍ୟ ÷ 4, ଗୋଲାକାର) — ସଞ୍ଚୟ କରେ ନାହିଁ ଉଦାହରଣ ସ୍ୱରୂପ 25 ଧାଡି କିମ୍ବା ତା’ଠାରୁ କମ୍ କୋଡ୍ ପରି ଫାଇଲ୍, କିମ୍ବା 7 ଟି ଆଇଟମ୍ କିମ୍ବା କମ୍ — ସହିତ 2000 ଅକ୍ଷରରୁ ଅଧିକ JSON ଆରେ ମୂଳ ଉପକରଣ ଫଳାଫଳକୁ ରଖେ: ଉଭୟ କଲ୍ କରୁଥିବା ବ୍ୟକ୍ତି (`compressAggressive()` ଏବଂ `compressAnthropicToolResultBlock()`) ଯେତେବେଳେ `saved` 0 କିମ୍ବା ତା’ଠାରୁ କମ୍, ସେତେବେଳେ `compressToolResult()` ନିଜେ ଆଉଟପୁଟ୍ ଫେରାଇଥାଏ। ଟୁଲ୍-ଫଳାଫଳ ପଦକ୍ଷେପ ହେଉଛି ଶେଷ ଶବ୍ଦ ନୁହେଁ: ଇଞ୍ଜିନ୍ ର ଫଲବ୍ୟାକ୍ ସାରାଂଶାଇଜର୍ ଏପର୍ଯ୍ୟନ୍ତ ଏକ `tool` କିମ୍ବା `function` ସନ୍ଦେଶକୁ 8,192 ଅକ୍ଷରରୁ ଅଧିକ କ୍ଷୁଦ୍ର କରିପାରେ (`maxTokensPerMessage`, 2,048, 4 ଥର)।

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ।

ସାଧନ ଫଳାଫଳ ସଙ୍କୋଚନ ହେଉଛି ଆକ୍ରମଣାତ୍ମକ ଇଞ୍ଜିନର ପ୍ରଥମ ପଦକ୍ଷେପ ( `open-sse/services/compression/aggressive.ts` ରେ`compressAggressive()` ), ତେଣୁ ଏହା ଆକ୍ରମଣାତ୍ମକ ମୋଡରେ ଏବଂ ଏକ ଷ୍ଟାକ୍ ପାଇପଲାଇନର `aggressive` ପଦକ୍ଷେପରେ ଚାଲିଥାଏ। ଏହା OpenAI- ଆକୃତି `tool` ଏବଂ `function` ସନ୍ଦେଶ ଏବଂ Anthropic `tool_result` ବ୍ଲକ ଭିତରେ ଥିବା ପାଠ୍ୟକୁ ସଙ୍କୋଚନ କରେ। ପ୍ରତ୍ୟେକ କ strategy ଶଳର `aggressive.toolStrategies` ଅଧୀନରେ ନିଜସ୍ୱ ସୁଇଚ୍ ଅଛି, ସମସ୍ତ ଡିଫଲ୍ଟ ଭାବରେ। ଡ୍ୟାସବୋର୍ଡରେ, ସୁଇଚ୍ ଗୁଡିକ କେଭମ୍ୟାନ୍ ପୃଷ୍ଠାର ଅଛି।** ଉନ୍ନତ** ସଙ୍କୋଚନ ଚାଲିଥିବାବେଳେ ଦେଖନ୍ତୁ ଏବଂ ଡିଫଲ୍ଟ ମୋଡ୍ ଆକ୍ରମଣାତ୍ମକ ଅଟେ।

### ଷ୍ଟାକ୍ ପାଇପ୍ ଲାଇନ୍।

ଷ୍ଟାକଡ୍ ମୋଡ୍ ଚାଲିଥାଏ।** କ୍ରମରେ ଏକାଧିକ ଇଞ୍ଜିନ୍।** — ସାଧାରଣତ z ପ୍ରଥମେ RTK (ଟୁଲ୍ ଆଉଟପୁଟ୍ ଉପରେ 60-90% ସଞ୍ଚୟ), ତାପରେ ଅବଶିଷ୍ଟ ପାଠ୍ୟ ଉପରେ କେଭମ୍ୟାନ୍ (~ 46% ଇନପୁଟ୍ ସଞ୍ଚୟ)। ରଚନା, ତାହା ହେଉଛି** 78-95% ଯୋଗ୍ୟ ପରିସର।** (ଉପର ଅପଷ୍ଟ୍ରିମ୍ ସଞ୍ଚୟ ଗଣିତ ଦେଖନ୍ତୁ): `1 - (1 - 0.60..0.90) × (1 - 0.46)` ହାରାହାରି ≈ 89%।

#### ଏହା କିପରି କାମ କରେ।

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ।

ପାଇଁ ଷ୍ଟାକ୍ଡ୍ ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ:

- ସାଧନ-ଭାରୀ କାର୍ଯ୍ୟ ପ୍ରବାହ (ଏଜେଣ୍ଟିକ୍ କୋଡିଂ, ଅନୁସନ୍ଧାନ)
- ମୂଲ୍ୟ ସମ୍ବେଦନଶୀଳ ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ।
- ଯେତେବେଳେ ଆପଣ ସର୍ବାଧିକ ଟୋକନ୍ ସଞ୍ଚୟ ଆବଶ୍ୟକ କରନ୍ତି।

ଷ୍ଟାକ୍ ପାଇପଲାଇନଗୁଡିକ ଗ୍ଲୋବାଲ୍ `stackedPipeline` ସଙ୍କୋଚନ ସେଟିଂ ମାଧ୍ୟମରେ କିମ୍ବା ଏକ ରାଉଟିଙ୍ଗ୍ କମ୍ବୋକୁ ଦିଆଯାଇଥିବା ଏକ ନାମିତ ସଙ୍କୋଚନ କମ୍ବୋ ମାଧ୍ୟମରେ (ଉପରେ ପେ-କମ୍ବୋ ଓଭରବାଇଡ୍ ଦେଖନ୍ତୁ) — ଏକ ଅଟୋ-କମ୍ବୋ `modePack` ମାଧ୍ୟମରେ ନୁହେଁ (ସେହି କ୍ଷେତ୍ର କେବଳ ଅଟୋ-କମ୍ବୋ ମଡେଲ ଚୟନକୁ ପୁନ re ଓଜନ କରେ, ଏବଂ `stacked` ଏକ ବ valid ଧ ପ୍ୟାକ୍ ନାମ ନୁହେଁ)।

## କମ୍ପ୍ରେସନ୍ କମ୍ବୋ ଓଭରରାଇଡ୍

ବିଭିନ୍ନ ବ୍ୟବହାର ପରିସ୍ଥିତି ପାଇଁ ଆଚରଣକୁ ସୂକ୍ଷ୍ମ ଭାବରେ ସମନ୍ୱୟ କରିବାକୁ ଆପଣ **ପ୍ରତ୍ୟେକ କମ୍ବୋ ପାଇଁ** ଗ୍ଲୋବାଲ୍ କମ୍ପ୍ରେସନ୍ ମୋଡ୍କୁ ଓଭରରାଇଡ୍ କରିପାରିବେ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ଏହା ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରରେ ଉପଯୋଗୀ:

- **କୋଡିଂ କମ୍ବୋ**: ଦୀର୍ଘ ସେସନ୍ ପାଇଁ `aggressive` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ଦ୍ରୁତ ପ୍ରଶ୍ନୋତ୍ତର କମ୍ବୋ**: ଦ୍ରୁତ ପ୍ରତିକ୍ରିୟା ପାଇଁ `lite` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ଅଧିକ ଟୁଲ୍-ଆଧାରିତ କମ୍ବୋ**: ସର୍ବାଧିକ ସଞ୍ଚୟ ପାଇଁ `stacked` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ପ୍ରୋଡକ୍ସନ୍ କମ୍ବୋ**: କ୍ୟାସିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ ଓଭରରାଇଡ୍ ବନ୍ଦ ରଖନ୍ତୁ — ସର୍ବଦା ସକ୍ରିୟ
  କ୍ୟାସ୍-ସଚେତନ ସମନ୍ୱୟ `aggressive`/`ultra`କୁ ସ୍ୱୟଂଚାଳିତ ଭାବରେ `standard`କୁ ଡାଉନ୍ଗ୍ରେଡ୍ କରେ
  (ଚୟନଯୋଗ୍ୟ `cache-aware` ମୋଡ୍ ନାହିଁ)
