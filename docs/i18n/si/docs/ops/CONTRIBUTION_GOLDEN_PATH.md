මෙම මාර්ගෝපදේශය භාවිත කර pull request එකක් සඳහා විශ්වාසදායක කුඩාම සංවර්ධන චක්රය තෝරන්න. මෙය පහත සබැඳි කර ඇති ක්ෂේත්ර-විශේෂිත නිර්මාණ ශිල්පීය සහ ආරක්ෂක ලේඛන ප්රතිස්ථාපනය නොකරයි; එය සෑම පොදු වෙනස්කම් වර්ගයක්ම එහි ගිවිසුම්, ඉලක්කගත පරීක්ෂණ සහ CI ආවරණය සමඟ සම්බන්ධ කරයි.

## සෑම වෙනස්කමක්ම අනුගමනය කරන මාර්ගය

1. **සංස්කරණය කිරීමට පෙර පාදකය තෝරන්න.** ඉහළම සක්රිය `release/v*` ශාඛාව සොයා එහි අග්රයෙන් නව ශාඛාවක් සාදන්න. `main` නොව, එම ශාඛාව ඉලක්ක කරන්න. නිකුතු අත්හිටුවීමක් සක්රිය නම්, අත්හිටුවා ඇති ශාඛාව ඉලක්ක නොකරන්න; [ශාඛාකරණ සහ නිකුතු ආකෘතිය](BRANCHING_MODEL.md) හි විස්තර කර ඇති ඊළඟ සක්රිය චක්රය භාවිත කරන්න.
2. **ගිවිසුම් නම් කරන්න.** වෙනස්කම බලපාන සෑම නාමාවලියක්, යෝජනා ක්රමයක්, ජනනය කළ කෘතියක්, පොදු API එකක් හෝ පරිශීලක අතුරුමුහුණතක්ම හඳුනා ගන්න. පහත වගුව අවම ආරම්භක කට්ටලය සපයයි.
3. **ඉලක්කගත පරීක්ෂණ ලියන්න හෝ යාවත්කාලීන කරන්න.** `src/`, `open-sse/`, `electron/`, හෝ `bin/` තුළ ඇති නිෂ්පාදන වෙනස්කම් සඳහා එම PR එක තුළම ස්වයංක්රීය පරීක්ෂණයක් අවශ්ය වේ. හැසිරීම තහවුරු කරන කුඩාම පරීක්ෂණ ගොනු පළමුව ධාවනය කර, ඉන්පසු ලැයිස්තුගත කර ඇති ඉලක්කගත ද්වාර ධාවනය කරන්න.
4. **පුළුල් අනුකෘතිය CI මඟින් ධාවනය වීමට ඉඩ දෙන්න.** සම්පූර්ණ ඒකක කොටස්, Vitest, ආවරණ ratchet එක සහ නිෂ්පාදන build එක PR එක මත ධාවනය වේ. ඉලක්කගත අසාර්ථක වීමක් පුළුල් බලපෑමක් පෙන්වන විට හෝ වෙනස්කම උපපද්ධති කිහිපයක් පුරා විහිදෙන විට පමණක් පුළුල් පරීක්ෂණ කට්ටලයක් දේශීයව ධාවනය කරන්න.
5. **සමාලෝචනයට පෙර සමථයකට පත් කරන්න.** සක්රිය පාදකය fetch කර, එහි නව commits සහ එයට සාපේක්ෂව ඔබේ diff එක පරීක්ෂා කර, ඉන්පසු දායකත්ව කාර්ය ප්රවාහයට අනුව පාදකය rebase හෝ merge කරන්න. ජනනය කළ ගොනු සහ නාමාවලි ගැටුම් ඒවායේ මූලාශ්රයෙන් විසඳා, ඒවා නැවත ජනනය කර, ඉලක්කගත චක්රය නැවත ධාවනය කර, PR එක තවමත් සක්රිය නිකුතු ශාඛාව ඉලක්ක කරන බව තහවුරු කරන්න.
6. **සාක්ෂි සටහන් කරන්න.** PR අච්චුවෙහි, ධාවනය කළ විධාන, එක් කළ හෝ වෙනස් කළ සෑම පරීක්ෂණ ගොනුවක්ම, migrations හෝ feature flags, සහ තවමත් බලාපොරොත්තුවෙන් ඇති CI-පමණක් වලංගුකරණය ලැයිස්තුගත කරන්න.

## වෙනස්කම් වර්ගය අනුව ප්රධාන මාර්ග

පහත විධාන අවම ඉලක්කගත පරීක්ෂණ වන අතර, ඔබ වෙනස් කළ හැසිරීම සෘජුවම ආවරණය කරන පරීක්ෂණයක් මඟහැරීමට අවසරයක් නොවේ.

### සපයන්නා

**ගිවිසුම්**

- `src/shared/constants/providers/` තුළ ඇති සපයන්නාගේ නිර්වචනය සහ `src/shared/constants/providers.ts` තුළ එහි සංයුතිය.
- `open-sse/config/providerRegistry.ts` හෝ එයින් වෙන් කළ registry ගොනු තුළ ඇති models සහ capabilities.
- අදාළ වන විට executor/translator තේරීම, OAuth හෝ API-key වින්යාසය, dashboard සම්පත් සහ ජනනය කළ provider reference.
- පොදු අක්තපත්ර `resolvePublicCred()` භාවිත කළ යුතුය; දෝෂ ප්රතිචාර හවුල් sanitized error helpers භාවිත කළ යුතුය. `docs/security/PUBLIC_CREDS.md` (git; `/docs` තුළට compile නොකෙරේ) සහ [දෝෂ සනීපාරක්ෂාව](../security/ERROR_SANITIZATION.md) බලන්න.

**ඉලක්කගත චක්රය**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # නාමාවලිය වෙනස් වන විට; ජනනය කළ diff එක commit කරන්න
npm run lint
```

බලපෑමට ලක් වූ සෑම request family එකක්ම ද පරීක්ෂා කරන්න: chat, Responses, images, embeddings, audio, හෝ video. ජනනය කළ catalog සහ golden diffs ගිවිසුම් වෙනස්කම් ලෙස සමාලෝචනය කරන්න; ඒවා අන්ධ ලෙස පිළි නොගන්න.

```bash
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # හුදකලා worktree එකක්, සමාන්තරව භාවිත කිරීමට ආරක්ෂිතයි
```

- `typecheck-touched.sh`, තාවකාලික `tsconfig.touched.tmp.json` එකක් (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`, `incremental: false`) හරහා වෙනස් කළ `.ts/.tsx` ගොනු පමණක්, 6 GB heap එකක් යටතේ type-check කරයි. එම නිසා, බර වැඩි යන්ත්රයක OOM වන ව්යාපෘතිය පුරා ක්රියාත්මක වන `tsc -p tsconfig.json` වෙනුවට මෙය භාවිත වේ. එය වෙනස් කළ ගොනුවල දෝෂ සහ එක් සාරාංශ පේළියක් මුද්රණය කරයි. වෙනස් කළ ගොනුවල දෝෂ සඳහා `1`, එකම දෝෂ import කළ ගොනුවල තිබේ නම් හෝ diagnostics නොමැතිව tsc නතර වූ විට `2` (එය `_artifacts/typecheck-touched/` යටතේ නම් කරන log එක කියවන්න), සහ දෝෂ නොමැති විට `0` සමඟ පිටවෙයි. තාවකාලික tsconfig එක සැමවිටම ඉවත් කරනු ලැබේ; කිසිවිටෙක එවැන්නක් commit නොකරන්න.
- `new-worktree.sh`, `<git-common-dir>/omniroute-new-worktree.lock` මත සමකාලීන ධාවන අනුක්රමික කරයි (පෙරනිමියෙන් 600 s දක්වා, පෙනෙන පණිවිඩයක් සමඟ රැඳී සිටියි; වෙනස් කිරීම පිළිබඳව ස්ක්රිප්ට් ශීර්ෂයේ ලේඛනගත කර ඇත). worktree එක පැවතීමට පෙර `git worktree add` අසාර්ථක වුවහොත්, එය නිර්මාණය කළ branch එක ආපසු හරවයි. එම නිසා නැවත උත්සාහ කිරීමට අතින් `git branch -D` ක්රියාත්මක කිරීම අවශ්ය නොවේ. hard-link කළ `node_modules` සහ `.husky/_` පිටපත නොවෙනස්ව පවතී.

## දේශීය candidate ක්රියා චක්රය

ඇසුරුම් කළ artifact එක ආරම්භ වන බව source tests මඟින් තහවුරු කළ නොහැක: ඇසුරුම් ලැයිස්තු, ඉවත් කළ dependencies සහ native binaries අසාර්ථක වන්නේ tarball එක ස්ථාපනය කර ආරම්භ කළ පසුව පමණි. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) යනු RFC #8084 හි එක් වරක් build කිරීම / වලංගු කිරීම / ප්රවර්ධනය කිරීමේ ප්රවාහයේ දේශීය පැත්තයි: එය එක් candidate එකක් build කර, එම නිශ්චිත artifact එක වලංගු කර, directory rename කිරීමෙන් එය ප්රවර්ධනය කර, ප්රවර්ධනය කළ slot එකේ health check එක අසාර්ථක වුවහොත් එය ආපසු හරවයි.

```bash
npm run dev:candidate -- run --dry-run --json  # සැලැස්ම මුද්රණය කරන්න, කිසිවක් වෙනස් නොකරන්න
npm run dev:candidate -- run                   # build + validate + promote, ස්වයංක්රීයව ආපසු හරවන්න
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ තුළට ස්ථාපනය කරන්න
npm run dev:candidate -- validate --id <id>    # නිදහස් port එකක ආරම්භ කර, /api/health + /v1/models පරීක්ෂා කරන්න
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current සහ previous හුවමාරු කරන්න
npm run dev:candidate -- run --from-tarball <file.tgz>  # වෙනත් තැනක (CI) build කළ tarball එකක් නැවත භාවිත කරන්න
```

- **එක් වරක් build කරන්න.** `build`, වත්මන් tree එක pack කරයි (එයට `dist/server.js` අවශ්ය බැවින් පළමුව `npm run build:release` ධාවනය කරන්න), නැතහොත් `--from-tarball` පිටපත් කරයි. ඉන්පසු tarball එකේ `node_modules` නොමැති බැවින්, එය හුදකලා npm prefix එකකට tarball එක ස්ථාපනය කරයි. id එක කෙටි `HEAD` sha එකයි (tree එකේ දේශීය වෙනස්කම් ඇති විට `-dirty`) හෝ tarball එකක් සඳහා `tgz-<sha256>` වේ. දැනටමත් build කර ඇති පිරිසිදු id එකක් නැවත build කිරීම වෙනුවට නැවත භාවිත කරයි; එය නැවත build කිරීමට `--force` යොදන්න.
- **source එක නොව package එක වලංගු කරන්න.** `validate`, නැවුම් `DATA_DIR=<candidate>/data` එකක් සහ ව්යාජ secrets සමඟ ස්ථාපිත CLI එක (`serve --port <free port>`) ආරම්භ කරයි. එසේම operatorගේ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` සහ `INITIAL_PASSWORD` environment එකෙන් ඉවත් කරයි. එමඟින් නැවුම් ස්ථාපනයක key රහිත loopback ආකාරය පරීක්ෂා කරයි. එය `GET /api/health` වෙතින් 200 ලැබෙන තෙක් රැඳී සිට, `GET /v1/models` වෙතින් 200 ලැබීම අනිවාර්ය කර, process group එක නවතා, tarball hash එක සමඟ තීන්දුව `validation.json` තුළ සටහන් කරයි.
- **එම artifact එකම ප්රවර්ධනය කරන්න.** වත්මන් tarball hash එක සඳහා සාර්ථක validation එකක් නොමැති candidate එකක් `promote` විසින් ප්රතික්ෂේප කරයි. පෙරනිමි සක්රිය slot එක `_artifacts/candidate/current` වේ; `--target <dir>` මඟින් එම filesystem එකේ වෙනත් directory එකක් තෝරන අතර, එහි පෙර slot එක `<dir>.previous` වේ. සෑම rename එකක්ම atomic වන අතර, අතරමඟදී අසාර්ථක වුවහොත් දැනටමත් සිදු කළ rename ආපසු හරවයි.
- **ආපසු හරවන්න.** `run`, ප්රවර්ධනය කළ slot එක නැවත වලංගු කරන අතර එම පරීක්ෂාව අසාර්ථක වූ විට `current` සහ `previous` නැවත හුවමාරු කරයි. පළමු validation එක අසාර්ථක වන candidate එකක් කිසිවිටෙක ප්රවර්ධනය නොකෙරේ.

සෑම දෙයක්ම gitignore කර ඇති `_artifacts/candidate/` යටතේ ලියනු ලැබේ; පවතින OmniRoute ස්ථාපනයක් සහ එහි data directory එක කිසිවිටෙක වෙනස් නොකෙරේ. ප්රවර්ධනය කළ CLI එක `_artifacts/candidate/current/prefix/bin/omniroute` වේ; එය භාවිත කරන විට ඔබේම `DATA_DIR` සමඟ ආරම්භ කරන්න. පිටවීමේ කේත: සාර්ථකත්වය සඳහා `0`, අසාර්ථක validation හෝ promotion සඳහා `1`, usage error එකක් හෝ build එක නොමැති වීම සඳහා `2`.

## ප්රතිසන්ධාන පිරික්සුම් ලැයිස්තුව

සමාලෝචනය ඉල්ලා සිටීමට පෙර:

- PR පදනම තවමත් ඉහළම සක්රිය `release/v*` ශාඛාව බව තහවුරු කරන්න.
- එම පදනම ලබාගෙන, ඔබ ශාඛාව නිර්මාණය කළ පසු ඇතුළත් වූ commits සමාලෝචනය කරන්න.
- අහඹු හෝ ජනනය කළ අනවශ්ය වෙනස්කම් සඳහා `git diff <active-base>...HEAD` සමාලෝචනය කරන්න.
- මූලාශ්රය යාවත්කාලීන කර ප්රතිදානය නැවත ජනනය කිරීමෙන් නාමාවලි සහ ජනනය කළ-ලේඛන ගැටුම් විසඳන්න.
- ප්රතිසන්ධානයෙන් පසු PR විස්තරයේ ලැයිස්තුගත කර ඇති සෑම ඉලක්කගත පරීක්ෂණයක්/ද්වාරයක්ම නැවත ධාවනය කරන්න.
- වෙනස් වූ පදනමකට ගැළපීම සඳහා පමණක් assertions කිසිවිටෙක දුර්වල නොකරන්න හෝ අවශ්ය පරීක්ෂණ ඉවත් නොකරන්න.
