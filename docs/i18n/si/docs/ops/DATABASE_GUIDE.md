## SQLite භාවිත කරන්නේ ඇයි?

OmniRoute විසින් PostgreSQL/MySQL වෙනුවට SQLite තෝරාගත්තේ හේතු කිහිපයක් නිසාය:

| සාධකය             | SQLite                                   | PostgreSQL                           |
| ----------------- | ---------------------------------------- | ------------------------------------ |
| **යෙදවීම**        | අන්තර්ගතයි — වෙනම server එකක් අවශ්ය නොවේ | server සැකසීමක් අවශ්ය වේ             |
| **සංකේතනය**       | යෙදුම් මට්ටමේ (AES-256-GCM)              | අන්තර්ගත TDE                         |
| **කාර්යසාධනය**    | කුඩා/මධ්යම වැඩ ප්රමාණ සඳහා වේගවත්ය       | අතිවිශාල සමගාමී ලිවීම් සඳහා වඩා හොඳය |
| **සමගාමීත්වය**    | WAL mode සමගාමී කියවීම් සඳහා ඉඩ දෙයි     | සම්පූර්ණ MVCC                        |
| **Backup**        | තනි-ගොනු පිටපත                           | `pg_dump` හෝ filesystem snapshot     |
| **භාවිත අවස්ථාව** | එක් පරිශීලකයෙකු සඳහා ස්ථාපනය, අන්තර්ගත   | බහු-tenant SaaS                      |

**තනි-පරිශීලක, තනි-instance** යෙදවීම් සඳහා (OmniRoute හි ප්රධාන භාවිත අවස්ථාව), SQLite වඩා සරල සහ වේගවත් වේ.

### WAL ජර්නලකරණය

`core.ts` විසින් database එක **WAL (Write-Ahead Logging) mode** සමඟ විවෘත කරයි:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL මඟින් ලිවීම් අතරතුර **සමගාමී කියවීම්** සඳහා ඉඩ ලැබේ — requests වාර්තා කෙරෙන අතරතුර queries ක්රියාත්මක කරන dashboard එක සඳහා මෙය වැදගත් වේ.

පෙරනිමි cache ප්රමාණය **65,536 KiB (64 MiB)** වේ. SQLite විසින් ඍණ
`cache_size` අගයක් KiB ඒකකයෙන් දළ උපරිම සීමාවක් ලෙස අර්ථකථනය කර අවශ්යතාව අනුව pages වෙන් කරයි.
**Settings > System & Storage > Cache Size** තුළ **1 සිට
1,000,000 KiB** දක්වා පූර්ණ සංඛ්යා අගයන් පිළිගනී; සැකසුම සුරැකීමෙන් එය සජීවී database connection එකට යෙදෙන අතර,
OmniRoute ආරම්භයේදී සුරැකි අගය ප්රතිසාධනය කරයි.

## Database පිහිටීම

SQLite ගොනුව මෙහි ගබඩා කර ඇත:

| OS      | Path                                                        |
| ------- | ----------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                               |
| macOS   | `~/.omniroute/storage.sqlite`                               |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                   |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` හරහා වින්යාස කළ හැක) |

අනුබද්ධ ගොනු:

- `storage.sqlite-wal` — write-ahead log
- `storage.sqlite-shm` — shared memory ගොනුව
- `call_logs/` — request payload කලාකෘති (සක්රීය කර ඇත්නම්)

**පිහිටීම අභිබවා සකසන්න:**

```bash
DATA_DIR=/custom/path omniroute
```

```ts
// ❌ වැරදියි: වෙනත් මොඩියුලයකින් සෘජු SQL
db.prepare("SELECT * FROM provider_connections").all();

import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

මෙම රීතිය කේත සමාලෝචනය මඟින් බලාත්මක කෙරේ — ස්ථිතික පරීක්ෂාවක් නොමැති නමුත්, උල්ලංඝන සලකුණු කෙරේ.

### ඒකාබද්ධ කළ සංක්‍රමණය කිසිවිටක මකාදැමීම හෝ නැවත නම් කිරීම සිදු නොවේ

සංක්‍රමණ ගොනුවක් නිකුතු ශාඛාවක හෝ `main` මත වූ පසු, එය දැනටමත් homolog සහ සංවර්ධක දත්ත සමුදායන් මත, VPS ස්ථාපනයන්හි සහ ව්‍යවසාය සමමුහුර්තකරණයේ ධාවනය වී ඇත. එතැන් සිට:

- **ඒක කවදාවත් මකන්න එපා.** නවීකරණය කරන ලද දත්ත සමුදායන් එය තබා ගන්නා අතරතුර නැවුම් ස්ථාපනයන් එහි යෝජනා ක්‍රමය නැති කර ගනී.
- **කිසිවිටෙක එය නැවත නම් නොකරන්න.** `_omniroute_migrations` හි අනුවාදය තවදුරටත් ගොනුවකට නොගැලපේ, එබැවින් එය දැනටමත් යෙදී ඇති සෑම දත්ත සමුදායක්ම එය නැවත ධාවනය කරනු ඇත. Idempotent නොවන SQL පසුව දත්ත අනුපිටපත් කරයි හෝ ඇරඹුම නතර කරයි.
- **වෙනස් සැලැස්මක් අවශ්‍යද?** `npm run db:new-migration` සමඟින් නව සංක්‍රමණයක් සාදන්න.

නැවත නම් කිරීම ආරක්ෂිත වන්නේ තවමත් ඒකාබද්ධ කර නොමැති ගොනුවක් සඳහා පමණි, එය ගේට්ටුවේ ඉඟි සඳහන් වේ. නිකුතු ටැගයක් මෙහි කිසිවක් වෙනස් නොකරයි: `release/v*` ශාඛාවකට සෑම තල්ලුවක්ම Docker `:next` රූපය ප්‍රකාශනය කරන අතර homolog, VPS ස්ථාපනයන් සහ ව්‍යවසාය සමමුහුර්තකරණය මත ධාවනය වේ, එබැවින් ඒකාබද්ධ සංක්‍රමණයක් ඕනෑම `vX.Y.Z` ටැගයක් පැවතීමට පෙර සැබෑ දත්ත සමුදායන් මත ක්‍රියාත්මක වේ. ගේට්ටුව ටැග් කළ හෝ නොකළ මූලික ගොනුවක් ඉවත් කිරීම අසාර්ථක වේ.

- **ඒකාබද්ධ සංක්‍රමණයක් ප්‍රතිවර්තනය කිරීම.** ගොනුව මකා දැමූ `git revert` ගේට්ටුව අසමත් වේ. ගොනුව තබා නව සංක්‍රමණයකින් එහි යෝජනා ක්‍රමය අහෝසි කරන්න: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS` සමඟ , `DROP INDEX IF EXISTS` සහ යනාදිය. උත්ශ්‍රේණි කළ සහ නැවුම් දත්ත සමුදායන් පසුව එකම ක්‍රමයෙන් අවසන් වේ.
- **පිළිගත් නැවත නම් කිරීම: ගැළපුම් ඇතුළත් කිරීමක් සහ සමාන අන්තර්ගතයක්.** ඒකාබද්ධ කළ ගොනුවක් චලනය විය යුතු නම් (උදාහරණයක් ලෙස, ඒකාබද්ධ කළ ගොනු දෙකක් වේලා මුද්‍රාවක් බෙදා ගන්නා අතර ධාවකය අනුවාද ගැටීමකින් නතර වේ), එහි SQL ස්පර්ශ නොකර පසු කාලීන එක නැවත නම් කර `src/lib/db/migrationRunner/constants.ts` හි `RENAMED_MIGRATION_COMPATIBILITY` වෙත `{ fromVersion, fromName, toVersion, toName }` එකතු කරන්න. පැරණි අනුවාදය යෙදූ දත්ත සමුදායන් ගොනුව නැවත ධාවනය කරනවා වෙනුවට ඔවුන්ගේ `_omniroute_migrations` පේළිය ගෙන යයි. ගේට්ටුව එවැනි නැවත නම් කිරීමක් ගැන අනතුරු අඟවන අතර නව වේලා මුද්‍රාව කුමක් වුවත් සෑම විටම එය මත සංක්‍රමණ පරීක්ෂාව ක්‍රියාත්මක කරයි: නැවුම් ස්ථාපනයන් ගොනුව එහි නව ස්ථානයට යොදයි, යාවත්කාලීන කළ දත්ත සමුදායන් එසේ නොවේ, එබැවින් පැරණි එක අසල නව වේලා මුද්‍රාවක් තෝරන්න. අන්තර්ගතය වෙනස් වුවහොත් (අලුත් සංක්‍රමණයකදී ක්‍රමලේඛන වෙනසක් තවමත් සිදුවේ) හෝ ඇතුල්වීමේ ඉලක්ක ගොනුව තැටියේ නොමැති නම් ගේට්ටුව නැවත නම් කිරීම අසාර්ථක වේ.
- **එකම වේලා මුද්දරය තුළ කිසිවිටෙක නැවත නම් නොකරන්න.** වේලා මුද්‍රාව තබා විස්තරය පමණක් වෙනස් කරන නැවත නම් කිරීමක් ඇතුල්වීමක් ඇතිව හෝ රහිතව ගේට්ටුව අසාර්ථක වේ. `toVersion` එහි `fromVersion` ට සමාන ප්‍රවේශයක් සමඟින්, ධාවකයා පැරණි `_omniroute_migrations` පේළිය මකා එය දැනටමත් ධාවනය කර ඇති සෑම දත්ත සමුදායකම නැවත ගොනුව යොදයි. ප්‍රවේශයකින් තොරව, ධාවකය ලුහුබඳින්නේ අනුවාදය පමණි: එය එම දත්ත සමුදායේ ගොනුව මඟ හරියි (නව අන්තර්ගතය කිසි විටෙකත් එහි ධාවනය නොවේ) සහ සෑම ඇරඹුමකම නැවත අංකනය කිරීමේ දෝෂයක් සටහන් කරයි. වෙනත් වේලා මුද්දරයක් සහ ගැළපුම් ප්‍රවේශයක් භාවිතා කරන්න, නැතහොත් නම තබා ගන්න.
- **නැවත නම් කරන ලද ගොනුව නැවත ක්‍රියාත්මක නොවන බව ගේට්ටුව පරීක්ෂා කරයි.** ආවරණය කරන ලද එක් එක් නැවත නම් කිරීම සඳහා, ගේට්ටුව නව ගොනු නාමය `--must-not-apply` සමඟ සංක්‍රමණ පරීක්ෂාවට යවයි. චෙක්පත උත්ශ්‍රේණිගත දත්ත සමුදාය නියම ධාවකය සමඟින් ආරම්භ කරන අතර, ධාවකය නැවත එම ගොනුව යොදන්නේ නම් (උදාහරණයක් ලෙස, ඇතුල්වීමේ වැරදි අනුවාදයක් හෝ නමක් ඇති නිසා හෝ ගේට්ටුවේ පෙළ විග්‍රහකය TypeScript ට වඩා වෙනස් ලෙස `constants.ts` කියවන නිසා), ගේට්ටුව `migration renomeada rodaria de novo` සමඟ අසාර්ථක වන අතර ප්‍රවේශයේ පැරණි සහ නව අනුවාදය පරීක්ෂා කිරීමට ඔබෙන් අසයි.

### ගේට්ටුව පදනමට එරෙහිව පරීක්ෂා කරන දේ

ඇදීමේ ඉල්ලීම සහ ඒකාබද්ධ පෝලිම් ධාවනයේදී, `npm run check:migration-numbering` තැටියේ ඇති `src/lib/db/migrations/` මූලික ශාඛාවේ ඇති නාමාවලිය සමඟ සංසන්දනය කරයි. පදනම වන්නේ, මෙම අනුපිළිවෙලෙහි: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` විචල්‍යය, හෝ, `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` හෝ `merge_group` වූ විට , ඒකාබද්ධ කිරීමේ පළමු මාපිය, සිදුවීම් ගෙවීමේ `merge_group.base_sha`, හෝ `git merge-base HEAD origin/$GITHUB_BASE_REF`. විසඳිය හැකි පදනමක් නොමැතිව ඇදීමේ ඉල්ලීමක හෝ ඒකාබද්ධ පෝලිම් ධාවනයකදී ගේට්ටුව අසාර්ථක වේ. `--base` නොමැතිව CI පිටත එය `comparação com a base: pulada (sem --base)` මුද්‍රණය කර මෙම නීති මඟ හරියි.

`--base-latest-tag` නවතම නිකුතු ටැගය සමඟ සංසන්දනය කරයි (සෙම්වර් අනුපිළිවෙලෙහි`vX.Y.Z` ; නයිට්ලීස් වැනි උපසර්ග ටැග් ගණන් නොගනී) එය `HEAD` ඉතිහාසයේ ඇති, `--base` හා සමාන නීති සමඟ. සංක්‍රමණ පරීක්ෂාව (`scripts/check/migration-commutation.ts`) සැබෑ ස්ථාපන මාර්ගය සමඟ තාවකාලික දත්ත සමුදායන් දෙකක් ගොඩනඟයි: a** වැඩිදියුණු කරන ලදී** එකක් (පාදක සංක්‍රමණයන් සමඟ ආරම්භ කරන්න, ඉන්පසු ඇදීමේ ඉල්ලීමේ සංක්‍රමණය සමඟ එකම ගොනුව මත නැවත ආරම්භ කරන්න) සහ a** නැවුම්** එකක් (ඇදීමේ ඉල්ලීමේ සංක්‍රමණය සමඟ එක් ඇරඹුමක්). එය ප්‍රතිඵලයක් ලෙස ලැබෙන යෝජනා ක්‍රම සංසන්දනය කරයි: වගු සහ තීරු (තීරු අනුපිළිවෙල නොසලකා හැරීම), UNIQUE / PRIMARY KEY සහ FOREIGN KEY සීමාවන්, එක් එක් වගුවේ සාමාන්‍යකරණය කළ `CREATE TABLE` පෙළ ( CHECK සීමා කිරීම්, එකතු කිරීම්, ජනනය කළ තීරු සහ වගු විකල්ප ආවරණය කරයි), දර්ශක, ප්‍රේරක සහ බැලීම. පේළි දත්ත සංසන්දනය නොකෙරේ. ඒවා ගැළපෙන්නේ නම්, ගොනුව ක්‍රියා විරහිත බව ගේට්ටුව මුද්‍රණය කරයි, නමුත් ගමන් කරයි, සහ සමත් වේ. ඒවා වෙනස් නම්, ගේට්ටුව වෙනස හා නඩුව සඳහා ඉඟියක් සමඟ අසමත් වේ: නියෝගයෙන් බැහැර ගොනුවක් සඳහා, එහි නම `npm run db:new-migration` සමඟ නැවත උත්පාදනය කරන්න, ගොනුව තවමත් ඒකාබද්ධ කර නොමැති නිසා ආරක්ෂිතයි; සංස්කරණය කරන ලද පාදක ගොනුවක් සඳහා, මූලික අන්තර්ගතය ප්‍රතිසාධනය කර වෙනස් කිරීම නව සංක්‍රමණයකට දමන්න; නැවත නම් කරන ලද ගොනුවක් සඳහා, නැවත නම් කිරීම අහෝසි කරන්න හෝ එය ගමන් කරන වෙනත් නව වේලා මුද්‍රාවක් තෝරන්න, වෙනත් නමක් සමඟ එකම වේලා මුද්‍රාව කිසිවිටෙකත් නොකරන්න. චෙක්පතම ධාවනය කළ නොහැකි නම්, CI හි ගේට්ටුව අසාර්ථක වන අතර දේශීය වශයෙන් පමණක් අනතුරු අඟවයි. සංස්කරණය කරන ලද පාදක ගොනුවක් සඳහා, උත්ශ්‍රේණිගත කළ දත්ත සමුදාය එම ගොනුවේ මූලික අන්තර්ගතය සමඟ ගොඩනගා ඇති අතර, එහි අනුවාදය දැනටමත් වාර්තා කර ඇති බැවින් දෙවන ඇරඹුම එය මඟ හරියි. නැවත නම් කරන ලද ගොනුවක් සඳහා, නවීකරණය කරන ලද දත්ත සමුදාය එහි පැරණි නම යටතේ ගොනුව සමඟ ගොඩනගා ඇති අතර, දෙවන ඇරඹුම් එය නැවත ධාවනය කිරීම වෙනුවට එහි `_omniroute_migrations` පේළිය ගැළපෙන ප්‍රවේශය හරහා ගෙන යයි; ගේට්ටුව `--must-not-apply` සමඟ නව නම පසු කරයි, එබැවින් දෙවන ඇරඹුම එය යෙදුවහොත් චෙක්පත අසාර්ථක වේ. උත්ශ්‍රේණිගත කළ මාර්ගයෙහි ඇදීමේ ඉල්ලීම් සංක්‍රමණයක් යෙදීමට අපොහොසත් වන්නේ නම්, එනම්, සෑම මූලික සංක්‍රමණයකටම පසුව (නැවුම් ස්ථාපනයකදී එය අසාර්ථක වුවත් නැතත්), ද්වාරය `migration do PR não aplica` වාර්තා කර පදනමේ වත්මන් ක්‍රමයට එරෙහිව SQL සවි කරන ලෙස ඔබෙන් අසයි; ගොනුව පසුකාලීන වේලා මුද්‍රාවක් සමඟ වෙනත් ඇදීමේ ඉල්ලීමක් සංක්‍රමණයක් මත රඳා පවතී නම්, එහි නම `npm run db:new-migration` සමඟ නැවත උත්පාදනය කරන්න.

එකම සංසන්දනය දේශීයව ක්‍රියාත්මක කිරීමට, පාදම පැහැදිලිව ලබා දෙන්න, උදාහරණයක් ලෙස `npm run check:migration-numbering -- --base origin/<base-branch>`, හෝ නවතම නිකුතුව සමඟ සංසන්දනය කිරීමට `npm run check:migration-numbering -- --base-latest-tag`.

### විවෘත PR හි `NNN` සංක්‍රමණයක් පරිවර්තනය කිරීම

1. **විස්තරය තබා, උත්පාදක යන්ත්රය සමඟ ගොනුව නැවත නම් කරන්න.** නව නම ලබා ගැනීමට `npm run db:new-migration -- <same description>` ධාවනය කරන්න, SQL එය තුළට ගෙන යන්න, සහ පැරණි `NNN_` ගොනුව මකා දමන්න. විස්තරය එක හා සමානව පැවතිය යුතුය: පහත අනුකූලතා ඇතුළත් කිරීම එයට ගැලපේ.

```ts
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {

    })();
  }
}
```

## ගබඩා කර ඇති දත්ත සංකේතනය

සංවේදී ක්ෂේත්ර (API යතුරු, OAuth tokens, connection strings) ගබඩා කර ඇති විට **AES-256-GCM** භාවිතයෙන් සංකේතනය කෙරේ.

### එය ක්රියා කරන ආකාරය

```ts
// src/lib/db/encryption.ts (සරල කළ)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### එය භාවිත වන ස්ථාන

- `provider_connections.api_key` — යෙදුම් මට්ටමේදී සංකේතනය කෙරේ
- `provider_connections.access_token`, `refresh_token`, `id_token` — යෙදුම් මට්ටමේදී සංකේතනය කෙරේ
- `namespace = "secrets"` සහිත `key_value` ඇතුළත් කිරීම් — යෙදුම් මට්ටමේදී සංකේතනය කෙරේ
- `proxy_registry.auth` — පවතී නම් යෙදුම් මට්ටමේදී සංකේතනය කෙරේ

### සංකේතන යතුර

සංකේතන යතුර **passphrase** එකකින් (`STORAGE_ENCRYPTION_KEY` env var හරහා සකසන) සහ **salt** එකකින් (DB තුළ ගබඩා කරන) ව්යුත්පන්න කෙරේ. දත්ත විකේතනය කිරීමට දෙකම අවශ්ය වේ.

```bash
# ආරක්ෂිත passphrase එකක් ජනනය කරන්න
openssl rand -hex 32

# .env තුළ සකසන්න
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **අතිශයින් වැදගත්**: සංකේතන යතුර නැතිවීමෙන් සියලුම සංකේතනය කළ දත්ත වෙත ඇති ප්රවේශය අහිමි වේ. **යතුර database එකෙන් වෙන්ව backup කරන්න**.

### සංකේතනය නොකරන දෑ

කාර්ය සාධන හේතු මත, පහත දෑ plaintext ලෙස ගබඩා කෙරේ:

- Provider දර්ශන නාම
- Model අර්ථ දැක්වීම් (දැනටමත් පොදුය)
- Routing නීති
- භාවිත වාර්තා (PII නොමැත)

### SQLite සජීවී උපස්ථය

ක්රියාත්මක DB එකක් සේවා අක්රියතාවකින් තොරව උපස්ථ කිරීමට:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

මෙය SQLite හි මාර්ගගත උපස්ථ API භාවිත කරයි — OmniRoute ක්රියාත්මක වන අතරතුර ධාවනය කිරීම ආරක්ෂිතය.

### WAL මාදිලිය

WAL පෙරනිමියෙන් සක්රිය කර ඇත. ඉහළ ලිවීමේ වැඩ බර සඳහා, සලකා බලන්න:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` සකසන්නේ නැත. මුරපොලක් WAL රාමු ප්‍රධාන ගොනුවට ගෙන යයි, නමුත් WAL ගොනුව එහි විශාලතම වෙන් කළ ප්‍රමාණය තබා ගනී. `OMNIROUTE_WAL_GUARD_MAX_MB` ආරක්ෂකයා අනතුරු අඟවා `wal_checkpoint(RESTART)` පමණක් ධාවනය කරයි; එය තැටි ප්‍රමාණයේ පියනක් නොවේ.

### දර්ශක

කාර්ය සාධනය සඳහා ප්‍රධාන දර්ශක (සංක්‍රමණ මගින් ස්වයංක්‍රීයව සාදනු ලැබේ):

- සපයන්නා විසින්`idx_models_provider` — ආකෘති සෙවීම්
- `idx_combo_targets_combo_id` — combo ඉලක්ක පුළුල් කිරීම
- `idx_usage_history_api_key_timestamp` — භාවිත විශ්ලේෂණ
- `idx_quota_snapshots_api_key_window` — කෝටා ලුහුබැඳීම
- `idx_call_logs_timestamp` — ඇමතුම් ලඝු විමසුම්

නව දර්ශකයක් එක් කිරීමට, සංක්‍රමණයක් සාදන්න:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### මතක සිතියම්ගත I/O

ඉතා විශාල දත්ත සමුදායන් සඳහා (> 10GB), මතක සිතියම්කරණය SQLite ප්‍රයෝගය හරහා සකස් කළ හැක:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

## සෞඛ්ය පරීක්ෂාව

`src/lib/db/healthCheck.ts` මඟින් **දත්ත සමුදා මට්ටමේ සෞඛ්ය නිර්ණය** සපයයි:

ක්රියාපද දෙකටම සත්යාපනය අවශ්ය වේ (එසේ නොමැති නම් `401`). `GET` නිර්ණය පමණක් සිදු කරයි; `POST` මඟින්
`autoRepair` සක්රීය කර එම පරීක්ෂාවම ධාවනය කරයි.

```bash
GET  /api/db/health   # නිර්ණය කරන්න
POST /api/db/health   # නිර්ණය කරන්න + අලුත්වැඩියා කරන්න
```

### අවස්ථාව 1: WAL ගොනුව නැතිවීම

`-wal` ගොනුව නොමැති නමුත් `-shm` සහ ප්රධාන DB ගොනුව හානි නොවී පවතී:

```bash
# ඊළඟ වර විවෘත කිරීමේදී ස්වයංක්රීයව ප්රතිසාධනය වේ
omniroute
```

SQLite හට ස්වයංක්රීයව ප්රතිසාධනය කළ නොහැකි නම්:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### අවස්ථාව 2: ප්රධාන DB ගොනුව දූෂිත වීම

උපස්ථ පිටපතකින් ප්රතිසාධනය කරන්න:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` මඟින් සිදු කරන්නේ ක්රියාත්මක සේවාදායකයකින් සම්පූර්ණ `.tar.gz` සංරක්ෂිතයක් බාගැනීම පමණි
(`GET /api/db-backups/exportAll`, ක්රියාකරු අක්තපත්ර අවශ්ය වේ); එය කිසිවක් ප්රතිසාධනය නොකරයි.

### අවස්ථාව 3: සංකේතන යතුර නැතිවීම

යතුර නොමැතිව **ප්රතිසාධනය කළ නොහැක**. සංකේතනය කළ ක්ෂේත්ර කියවිය නොහැක. නව අක්තපත්ර භාවිතයෙන් සියලුම සැපයුම්කරුවන් අතින් නැවත එක් කරන්න.

> **අවදානම අවම කිරීම**: සංකේතන යතුර සෑම විටම වෙනම උපස්ථ කරන්න, වඩාත් සුදුසු වන්නේ මුරපද කළමනාකරුවක හෝ KMS එකකය.

### අවස්ථාව 4: තැටිය පිරී යාම

SQLite මඟින් `SQLITE_FULL` දෝෂ ලබා දෙනු ඇත. තැටි ඉඩ නිදහස් කර, ඉන්පසු:

```bash
# ඉඩ නිදහස් කිරීමට WAL පරීක්ෂණ ලක්ෂ්යයක් සාදන්න
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## පොදු මෙහෙයුම්

### වගුවක් පරීක්ෂා කිරීම

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### සියලු වගුවල පේළි ගණන ගණනය කිරීම

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### සියලු දත්ත යළි සැකසීම (මකා දැමීම)

```bash
# පළමුව OmniRoute නවත්වන්න
omniroute stop

# DB ගොනුව මකන්න
rm ~/.omniroute/storage.sqlite*

# නැවත ආරම්භ කරන්න (හිස් DB එකක් නැවත සාදනු ඇත)
omniroute
```

**තෝරාගත්** යළි සැකසීමක් සඳහා (සැපයුම්කරුවන් තබාගෙන, භාවිත දත්ත මකා දැමීමට):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
```

## දෝෂ නිරාකරණය

### "දත්ත සමුදාය අගුළු දමා ඇත"

වෙනත් ක්රියාවලියක් ලිවීමේ අගුලක් රඳවාගෙන සිටී. පහත විකල්පවලින් එකක් භාවිත කරන්න:

- අනෙක් ක්රියාවලිය අවසන් වන තෙක් රැඳී සිටින්න (`lsof | grep storage.sqlite` පරීක්ෂා කරන්න)
- අනෙක් ක්රියාවලිය බලහත්කාරයෙන් අවසන් කරන්න
- ගැටලුව දිගටම පවතී නම්, OmniRoute නැවත ආරම්භ කරන්න

### "විදේශීය යතුරු සීමාව අසාර්ථක විය"

වසම් මොඩියුලයක් යොමු අඛණ්ඩතාව උල්ලංඝනය කරයි. පහත දෑ පරීක්ෂා කරන්න:

- පරායත්ත වගුවල මව් පේළියක් නොමැති පේළි
- ප්රචාරණය නොවූ අනුක්රමික මකා දැමීම්
- විදේශීය යතුරක් වෙනස් කළ මෑතකාලීන සංක්රමණයක්

උල්ලංඝනයන් සොයා ගැනීමට `PRAGMA foreign_key_check;` ධාවනය කරන්න.

### "මතකය ප්රමාණවත් නොවේ"

SQLite හි මතකයට සිතියම්ගත කළ I/O මෙහෙයුම් පද්ධතියේ සීමාව ඉක්මවා යයි. SQLite pragma එක හරහා එය අඩු කරන්න:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB වෙනුවට 128MB
```

නැතහොත් අක්රීය කරන්න:

```sql
PRAGMA mmap_size = 0;
```

### "සංක්රමණය අතරමඟ අසාර්ථක විය"

සංක්රමණය ගනුදෙනුවක් තුළ ධාවනය වූ බැවින්, එය ආපසු පෙරළී තිබිය යුතුය. එසේ නොමැති නම්:

1. **OmniRoute නවත්වන්න** (තවදුරටත් උත්සාහ කිරීම වැළැක්වීමට)
2. `sqlite3` සමඟ **DB තත්ත්වය පරීක්ෂා කරන්න**
3. අර්ධ වශයෙන් සිදු වූ සංක්රමණය **අතින් නිවැරදි කරන්න**
4. OmniRoute **නැවත ධාවනය කරන්න** (සංක්රමණය නැවත උත්සාහ කරනු ඇත)

මෙය වළක්වා ගැනීමට, සෑම විටම පළමුව පිටපතක් මත සංක්රමණ පරීක්ෂා කරන්න.
