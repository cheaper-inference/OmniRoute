## දළ විශ්ලේෂණය

OmniRoute විසින් ඉල්ලීම් upstream සැපයුම්කරුවන් වෙත ළඟා වීමට **පෙර ක්රියාකාරීව** ධාවනය වන මොඩියුලර් prompt සම්පීඩන නල මාර්ගයක් ක්රියාත්මක කරයි. මෙයින් අදහස් වන්නේ ඔබේ token ඉතිරිකිරීම් විනිවිද පෙනෙන ආකාරයෙන් සිදුවන බවයි — ඔබේ කාර්ය ප්රවාහයට කිසිදු වෙනසක් අවශ්ය නොවේ.

```
සේවාලාභී ඉල්ලීම
  → සම්පීඩන උපායමාර්ග තේරීම්කරු
    → Combo අභිබවා යාමක්ද? → Combo සැකසුම භාවිත කරන්න
    → ස්වයංක්රීය-ප්රේරක සීමාවක්ද? → ස්වයංක්රීය ප්රකාරය භාවිත කරන්න
    → පෙරනිමි ප්රකාරයද? → ගෝලීය සැකසුම භාවිත කරන්න
    → ක්රියාවිරහිතද? → සම්පීඩනය මඟ හරින්න
  → තෝරාගත් සම්පීඩන ප්රකාරය
    → Off: සම්පීඩනයක් නැත
    → Lite: ආරක්ෂිත හිස් ඉඩ/ආකෘතිකරණ පිරිසිදු කිරීම (~15%)
    → Standard: Caveman-ශෛලියේ පිරවුම් වචන ඉවත් කිරීම (~30%)
    → Aggressive: ඉතිහාසය වයස්ගත කිරීම + සාරාංශකරණය (~50%)
    → Ultra: හියුරිස්ටික් කප්පාදු කිරීම + කේත-බ්ලොක් තුනී කිරීම (~75%)
    → RTK: විධාන-සංවේදී terminal/tool-output පෙරීම (upstream පරාසය 60-90%)
    → Stacked: අනුපිළිවෙළට සැකසූ බහු-engine නල මාර්ගය, සාමාන්යයෙන් RTK පසුව Caveman (සුදුසුකම් ලබන පරාසය 78-95%)
  → සම්පීඩිත ඉල්ලීම → සැපයුම්කරු
```

## සම්පීඩන ප්රකාර

### Off

කිසිදු සම්පීඩනයක් යොදනු නොලැබේ. සියලුම පණිවිඩ වෙනස් නොකරම යවනු ලැබේ.

### Lite ප්රකාරය (~15% ඉතිරියක්, <1ms ප්රමාදයක්)

ආරක්ෂිතම ප්රකාරය — අර්ථයට කිසිදු වෙනසක් සිදු නොකර, ආකෘතිකරණය පමණක් පිරිසිදු කරයි:

| ශිල්පක්රමය               | විස්තරය                                             |
| ------------------------ | --------------------------------------------------- |
| `collapseWhitespace`     | අනුක්රමික හිස් පේළි සහ පේළි අග හිස් ඉඩ ඒකාබද්ධ කරයි |
| `dedupSystemPrompt`      | අනුපිටපත් system පණිවිඩ ඉවත් කරයි                   |
| `compressToolResults`    | දීර්ඝ tool/function ප්රතිදාන සම්පීඩනය කරයි          |
| `removeRedundantContent` | නැවත නැවත සඳහන් වන උපදෙස් ඉවත් කරයි                 |
| `replaceImageUrls`       | base64 රූප දත්ත URI කෙටි කරයි                       |

**වඩාත් සුදුසු වන්නේ:** සැමවිටම සක්රීය භාවිතයට සහ ආරක්ෂාව-අතිශය-වැදගත් කාර්ය ප්රවාහ සඳහාය.

### Standard ප්රකාරය (~30% ඉතිරියක්)

[Caveman](https://github.com/JuliusBrussee/caveman) වෙතින් ආභාසය ලබා ඇත — අර්ථය සුරකිමින් පිරවුම් වචන සහ අනවශ්ය ලෙස දීර්ඝ යෙදුම් ඉවත් කරයි:

- පිරවුම් වචන ඉවත් කරයි ("කරුණාකර", "මම සිතන්නේ", "මූලික වශයෙන්", "ඇත්තෙන්ම")
- අනවශ්ය ලෙස දීර්ඝ වාක්ය ඛණ්ඩ සංක්ෂිප්ත කරයි ("කිරීම සඳහා" → "කිරීමට", "ප්රතිඵලයක් ලෙස" → "නිසා")
- ආචාරශීලී අවිනිශ්චිත යෙදුම් ඉවත් කරයි ("ඔබට අපහසු නැත්නම්...", "ඔබට හැකි නම්...")
- coding prompt සඳහා සකස් කළ regex රීති 30කට වැඩි ගණනක්

**වඩාත් සුදුසු වන්නේ:** දෛනික coding කාර්ය ප්රවාහ සහ පිරිවැය පිළිබඳ සැලකිලිමත් කණ්ඩායම් සඳහාය.

### Aggressive ප්රකාරය (~50% ඉතිරියක්)

දිගු සැසි සඳහා බුද්ධිමත් ඉතිහාස කළමනාකරණය:

- **පණිවිඩ වයස්ගත කිරීම** — පැරණි පණිවිඩ ක්රමයෙන් වැඩි වශයෙන් සම්පීඩනය කෙරේ
- **Tool ප්රතිඵල සම්පීඩනය** — දිගු tool ප්රතිදාන කෙටි කර හෝ ඉවත් කරයි (පළමු/අවසාන පේළි,
  ගැළපෙන පේළි පෙරීම, JSON key සංක්ෂිප්ත කිරීම)
- **ව්යුහාත්මක අඛණ්ඩතා ආරක්ෂක** — `tool_use` + `tool_result` යුගල අනුකූලව පවතින බව සහතික කරයි
- **Context Window පිළිබඳ දැනුවත්භාවය** — එක් එක් model සඳහා වන token සීමාවන්ට අනුකූල වේ

**වඩාත් සුදුසු වන්නේ:** දීර්ඝ debugging සැසි සහ විශාල codebase සඳහාය.

### Stacked ප්රකාරය (සුදුසුකම් ලබන පරාසය 78-95%)

```txt

```

එම අනුපිළිවෙළ පළමුව terminal/tool ප්රතිදානය සංක්ෂිප්තව තබාගෙන, ඉන්පසු ඉතිරි ස්වාභාවික-භාෂා prompt එකට Caveman අර්ථමය සංක්ෂිප්තකරණය යොදයි. Stacked නල මාර්ග ගෝලීයව හෝ routing combo වෙත පවරා ඇති සම්පීඩන combo හරහා වින්යාස කළ හැක.

## Upstream ඉතිරිකිරීම් ගණිතය

OmniRoute සම්පීඩන ඉතිරිකිරීම් මූලාශ්ර දෙකක් මත පදනම්ව ලේඛනගත කරයි: upstream ව්යාපෘති මිණුම් සලකුණු සහ
OmniRoute හිම engine සංයෝජනය.

| මූලාශ්රය | මෙහි භාවිත කරන Upstream README අගය                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Caveman  | ප්රතිදාන ටෝකන `~75%`ක් අඩුය, මිණුම් සලකුණු සාමාන්ය ප්රතිදාන ඉතිරිය `65%`කි, පරාසය `22-87%`කි, සහ ආදාන සම්පීඩන මෙවලම `~46%`කි |
| RTK      | විධාන ප්රතිදාන ඉතිරිය `60-90%`කි; නියැදි සැසියක ටෝකන `~118,000 -> ~23,900`කි, නැතහොත් `79.7%`ක (`~80%`) ඉතිරියකි             |

එකිනෙක අතිච්ඡාදනය වන මෙවලම්/සන්දර්භ payload සඳහා, පෙරනිමි OmniRoute සංයෝජනය engine එක මත එක ලෙස යොදයි:

```txt
RTK -> Caveman
```

ඒකාබද්ධ ඉතිරිකිරීම් ආකලනීය නොව, ගුණාකාර වේ:

```txt
combined = 1 - (1 - RTK ඉතිරිකිරීම්) * (1 - Caveman ආදාන ඉතිරිකිරීම්)
සාමාන්යය = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
පරාසය    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK සහ Caveman යන දෙකටම එකම ආදාන/සන්දර්භ payload එක අඩු කළ හැකි විට එම `78-95%` අගය අදාළ වේ.
Caveman ප්රතිචාර ප්රතිදාන මාදිලිය වෙනම වේ: එය සක්රීය කර ඇති විට, Caveman හිම ප්රතිදාන ඉතිරිකිරීම් (සාමාන්යය `65%`,
ප්රධාන අගය `~75%`, පරාසය `22-87%`) භාවිත කරන්න. සමස්ත බිල්පත් ඉතිරිකිරීම් ඔබේ prompt/ප්රතිදාන මිශ්රණය මත රඳා පවතී.

### "සුදුසු" යන්නෙන් සැබවින්ම අදහස් කරන්නේ කුමක්ද

සෑම ඉල්ලීමක්ම එතරම් ඉතිරියක් ලබා දෙන බව **අදහස් නොවේ**.

අනුභූතිකව සත්යාපනය කර ඇත (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): සමාන

ක්රියාවලියක් **95.93% ටෝකන ඉතිරියක් / 96.26% අක්ෂර ඉතිරියක්** ලබා දුන්නේය — එය ප්රචාරණය කළ

## වින්යාසය

### උපකරණ පුවරුව

`උපකරණ පුවරුව → සන්දර්භය සහ හැඹිලිය` වෙත යන්න:

- **Caveman** — ප්රකාර තේරීම, භාෂා පැකේජ, පෙරදසුන සහ ගෝලීය පෙරනිමි
- **RTK** — විධාන-පෙරහන් පෙරදසුන, RTK ආරක්ෂක සැකසුම් සහ පෙරහන් නාමාවලිය
- **සම්පීඩන සංයෝජන** — මාර්ගගත කිරීමේ සංයෝජන වෙත පවරන ලද, නම් කළ එන්ජින් නලමාලා
- **ස්වයංක්රීය-ප්රේරක සීමාව** — ටෝකන ගණන සීමාව ඉක්මවන විට ස්වයංක්රීයව සම්පීඩනය සක්රිය කරයි

### එක් එක් සංයෝජනය සඳහා අතික්රමණය

`උපකරණ පුවරුව → සන්දර්භය සහ හැඹිලිය → සම්පීඩන සංයෝජන` තුළ, මාර්ගගත කිරීමේ
සංයෝජනයකට සම්පීඩන සංයෝජනයක් පවරන්න:

```txt
සංයෝජනය: "free-tier-fallback"
  සම්පීඩන සංයෝජනය: "coding-agent-stack"
  නලමාලාව: RTK -> Caveman
  ඉලක්ක:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

මෙමගින් ගෙවීම් සහිත දායකත්ව සඳහා ලයිට් ප්රකාරය පවත්වා ගනිමින්, නොමිලේ/කේතකරණ සැපයුම්කරුවන් මත
ස්තරගත සම්පීඩනය භාවිත කිරීමට ඔබට හැකියාව ලැබේ.

මෙම "එක් එක් සංයෝජනය සඳහා අතික්රමණය" පැවරීම **මාර්ගගත කිරීමේ-සංයෝජන සම්පීඩන
ප්රකාර** අතික්රමණයට (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — එම ක්ෂේත්රයේ
schema මඟින් `rtk`, `stacked` සහ `omniglyph` ද පිළිගනී) වඩා වෙනස් පාලනයකි — එම අතික්රමණය නම් කළ
සම්පීඩන-සංයෝජන නලමාලාවක් තෝරා නොගනී; එය හුදෙක් `resolveCompressionPlan` විසින් සලකා බලන
`compressionMode` ක්ෂේත්රය සකසයි. එය සංයෝජන කාඩ්පතේ (`උපකරණ පුවරුව → සංයෝජන`) හෝ, #6760 සිට,
ඉහත ලේඛනගත කළ නලමාලා-පැවරුම් සලකුණු කොටුවට යාබදව
`උපකරණ පුවරුව → සන්දර්භය සහ හැඹිලිය → සම්පීඩන සංයෝජන` තුළ ඇති "මාර්ගගත කිරීමට පවරන්න" ලැයිස්තුවේ
එක් එක් මාර්ගගත කිරීමේ සංයෝජනය සඳහා සැකසිය හැක. අතුරුමුහුණත් දෙකම එකම `PUT /api/combos/{id}` අන්ත ලක්ෂ්යය හරහා ස්ථිරව සුරැකේ.

### එක් එක් ඉල්ලීම සඳහා අතික්රමණය

එක් ඉල්ලීමක් සඳහා සම්පීඩන සැලැස්ම අතික්රමණය කිරීමට `x-omniroute-compression` ඉල්ලීම් ශීර්ෂය

ගෝලීය ප්රධාන ස්විචය තවමත් සියල්ල පාලනය කරයි: සම්පීඩනය ගෝලීයව අක්රිය කර ඇති විට, ශීර්ෂයට

| `safe`        | ශීර්ෂය ඉවත් කිරීම හා සමානය: අනුපිටපත් ඉවත් කිරීම සහ හිස් ඉඩ හැකිළීම පමණි.                                |
| `allow-lossy` | සාරාංශ, අදාළතා පෙරහන් සහ ශෛලීය නැවත ලිවීම් ඇතුළුව මෙම ඉල්ලීමේ ක්රියාකරු සැලැස්ම තබා ගනී.                 |
| `engine:<id>` | සක්රිය කර ඇති විට එක් එන්ජිමක්, උදා. `engine:rtk`. මෙය එම එන්ජිම සඳහා එක්-ඉල්ලීම් සක්රිය තේරීමයි.        |
| `<combo>`     | නමින් (අකුරු විශාලත්වය නොසලකා) පළමුවත්, පසුව id මඟිනුත් ගැළපෙන නම් කළ සංයෝජනයක්.                         |

`allow-lossy`, `engine:<id>`, හෝ නම් කළ සංයෝජනයක් නොමැතිව, දත්ත-හානි සහිත එන්ජින් යොදනු නොලැබේ.
සම්පීඩනය සක්රියව ඇති විට ඉල්ලීමට තවමත් සැසි අනුපිටපත් ඉවත් කිරීම සහ හිස් ඉඩ හැකිළීම ලැබේ.

යෙදූ සැලැස්ම `X-OmniRoute-Compression: <mode>; source=<source>` ප්රතිචාර
ශීර්ෂය තුළ නැවත දක්වනු ලැබේ, මෙහි `<source>` යනු `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default`, හෝ `off` අතරින් එකකි.

### API

```bash
# සම්පීඩන සැකසුම් ලබා ගන්න
curl http://localhost:20128/api/settings/compression

# සම්පීඩන සැකසුම් යාවත්කාලීන කරන්න
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# නිශ්චිත RTK/stacked දත්ත භාරයක පෙරදසුනක් බලන්න
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK පෙරහන් පැකේජ ලැයිස්තුගත කරන්න
curl http://localhost:20128/api/context/rtk/filters

# විකල්ප විධාන පාරදත්ත සමඟ RTK සෘජුවම පරීක්ෂා කරන්න
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

Caveman විසින් `~75%` අඩු ප්රතිදාන ටෝකන, මිණුම් ලකුණු පරීක්ෂණවල සාමාන්ය ප්රතිදාන ඉතිරිය `65%`, ප්රතිදාන පරාසය `22-87%`, සහ `~46%` ආදාන-සම්පීඩන මෙවලමක් වාර්තා කරයි.

සමහර සපයන්නන් (ප්රේරක හැඹිලිකරණය සහිත Anthropic වැනි) **ප්රේරක හැඹිලිකරණය** සඳහා සහාය දක්වන අතර,
එමඟින් පිරිවැය සහ ප්රමාදය අඩු කිරීම සඳහා ප්රේරකයේ කොටස් හැඹිලිගත කිරීමට ඔවුන්ට හැකි වේ.
හැඹිලිකරණය සක්රිය කර ඇති විට, ආක්රමණශීලී සම්පීඩනය හැඹිලිගත ටෝකන වෙනස් කර
හැඹිලිය අවලංගු කරන බැවින් කාර්යසාධනයට සැබැවින්ම **හානි** කළ හැකිය.

`cachingAware.ts` මොඩියුලය මෙය විසඳන්නේ **හැඹිලිකරණ සන්දර්භය හඳුනාගෙන**
ඒ අනුව **සම්පීඩන උපායමාර්ගය සීරුමාරු කිරීමෙන්** ය.

#### එය ක්රියා කරන ආකාරය

1. **හැඹිලිකරණ සන්දර්භය හඳුනාගැනීම** — `cache_control` සලකුණු සඳහා ඉල්ලීම් බඳ පරිලෝකනය කරයි
2. **හැඹිලිකරණ සපයන්නන් හඳුනාගැනීම** — ඉලක්ක සපයන්නා හැඹිලිකරණයට සහාය දක්වන්නේ දැයි පරීක්ෂා කරයි
3. **උපායමාර්ගය සීරුමාරු කිරීම** — හැඹිලිකරණ සපයන්නන් සඳහා `aggressive`/`ultra` යන්න `standard` වෙත පහත හෙළයි
4. **පද්ධති ප්රේරකය මඟහැරීම** — පද්ධති ප්රේරක සාමාන්යයෙන් හැඹිලිගත කර ඇති බැවින් ඒවා සම්පීඩනය නොකරයි

උපායමාර්ග සහායකය `deterministicOnly` සලකුණක් ද ආපසු ලබා දෙන නමුත්, සැලසුම් සාදනය භාවිත කරන්නේ
උපායමාර්ගය පමණි — අද වන විට පසු ප්රවාහයේ කිසිවක් එම සලකුණ කියවන්නේ නැත.

#### කේත උදාහරණය

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← හැඹිලි සලකුණ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### භාවිත කළ යුත්තේ කවදාද

හැඹිලි-සංවේදී සම්පීඩනය **සැමවිටම සක්රියයි** — කිසිදු වින්යාසයක් අවශ්ය නොවේ. සම්පීඩනය
සක්රියව ඇති සෑම අවස්ථාවකම සහ ඉලක්ක සපයන්නා ප්රේරක හැඹිලිකරණයට (Anthropic, OpenAI,
ආදිය) සහාය දක්වන විට එය ක්රියාත්මක වේ; පැහැදිලි `cache_control` සලකුණු අවශ්ය නොවේ — හැඹිලිකරණ සපයන්නෙකු පමණක් වුවද
පහත හෙළීම ක්රියාත්මක කරන අතර, සලකුණු පමණක් එසේ නොකරයි (සලකුණු හඳුනාගැනීම හැඹිලි
දුරමිතිකයට දත්ත සපයනවා මිස උපායමාර්ග තීරණයට නොවේ).

### ප්රගතිශීලී වියපත් කිරීම

දිගු සංවාදවල බොහෝ පණිවිඩ වාර එකතු වන නමුත්, පැරණි වාරවල අදාළත්වය
අඩු වේ. `progressiveAging.ts` මොඩියුලය **වාර දුර අනුව පණිවිඩවල විස්තරාත්මකභාවය අඩු කරයි**
(දුර මනිනු ලබන්නේ සංවාදයේ අවසානයේ සිටය). නිකුත් කළ පෙරනිමි සමඟ
(`verbatim: 2, light: 2, moderate: 3`):

- **අවසන් වාර 2 (දුර ≤ 2)**: වචනානුසාරයෙන් තබා ගනී
- **දුර 3**: Caveman සම්පීඩනය (පිරවුම් ඉවත් කිරීම)
- **දුර 4+**: සහායක පණිවිඩ සාරාංශගත කරයි; පරිශීලක පණිවිඩ ඒවායේ පළමු
  පේළියට සීමා කර, අක්ෂර 120ක උපරිමයකට යටත් කරයි; අනෙකුත් භූමිකා වෙනස් නොකරයි. පද්ධති ප්රේරක, දැනටමත් වියපත් කළ
  පණිවිඩ සහ නවතම පරිශීලක පණිවිඩය දුර නොසලකා සැමවිටම වචනානුසාරයෙන් තබා ගනී.
  කිසිවක් සම්පූර්ණයෙන්ම ඉවත් නොකරන අතර, නිකුත් කළ පෙරනිමි සමඟ (`light` යන්න `verbatim` ට සමාන බැවින්)
  `light`
  පරාසයට ළඟා විය නොහැක.

#### කේත උදාහරණය

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... තවත් වාර 50ක් ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // අවසන් වාර 3: වචනානුසාරයෙන්
  light: 8, // දුර <= 8: සැහැල්ලු සම්පීඩනය
  moderate: 20, // දුර <= 20: caveman සම්පීඩනය
  fullSummary: 5, // වර්ගයට අවශ්ය නමුත් පරාසකරණ කේතයෙන් කියවනු නොලැබේ
  // දුර > 20: සාරාංශගත කරයි (සහායක) / පළමු පේළිය තබා ගනී (පරිශීලක)
});

// saved = ඉතිරි කළ ටෝකන ගණන
```

#### භාවිත කළ යුත්තේ කවදාද

ප්රගතිශීලී වියපත් කිරීම `aggressive` මාදිලිය සඳහා **සැමවිටම සක්රියයි** — එය
`compressAggressive()` හි පියවර 2 වේ. Ultra මාදිලිය එය ක්රියාත්මක නොකරයි. එය
විශේෂයෙන් ඵලදායී වන්නේ:

- දිගුකාලීන කේතකරණ සැසි
- දින කිහිපයක් පුරා දිවෙන සංවාද
- බොහෝ මෙවලම් ඇමතුම් සහිත නියෝජිතමය කාර්ය ප්රවාහ

### Caveman ප්රතිදාන මාදිලිය

Caveman ප්රතිදාන මාදිලිය සංක්ෂිප්ත ප්රතිදානයක් ලබා දෙන ලෙස ආකෘතියෙන්ම ඉල්ලා සිටින
**පද්ධති ප්රේරක උපදෙස්** එක් කරයි — `lite` මට්ටම සම්පූර්ණ වාක්ය තබා ගන්නා සංක්ෂිප්ත පිළිතුරු ඉල්ලයි, `full`
මට්ටම එයට "බුද්ධිමත් ගුහා මිනිසෙකු මෙන් කෙටියෙන් ප්රතිචාර දක්වන්න" යැයි ඉල්ලයි, සහ `ultra` මට්ටම විදුලි පණිවුඩ ආකාරයේ ප්රතිදානයක් ඉල්ලයි;
උපදෙස් ඉල්ලීමක් පමණක් කරන අතර, ඒවාට එය සහතික කළ නොහැක. ඉල්ලීම්වලට ඒවා ලැබෙන්නේ

#### එය ක්රියා කරන ආකාරය

මෙම ප්රකාරය ආදානය සම්පීඩනය නොකරයි. එය පද්ධති ප්රේරකයට උපදෙස් කොටසක් එක් කරයි

තවමත් ඉන්පසු, දැන් එම කොටස අඩංගු අන්තර්ගතය මත ක්රියාත්මක වේ. සෑම මට්ටමක්ම අවසන් වන හවුල්
සීමා වගන්තියට පෙර, ඉංග්රීසි `full` මට්ටම මෙසේ සඳහන් කරයි:

> "බුද්ධිමත් ගුහා මිනිසෙකු මෙන් කෙටියෙන් පිළිතුරු දෙන්න. නිපාත (a/an/the), අනවශ්ය පිරවුම් වචන (just/really/basically/actually/simply), ආචාරශීලී ප්රකාශ, සැක සහිත මෘදු ප්රකාශ ඉවත් කරන්න. වාක්ය ඛණ්ඩ ප්රමාණවත්. කෙටි සමානාර්ථ පද භාවිත කරන්න (extensive වෙනුවට big, implement වෙනුවට fix). සියලු තාක්ෂණික කරුණු, කේත, දෝෂ, URLs, identifiers හරියටම තබාගන්න."

මෙය පහත අවස්ථා සඳහා විශේෂයෙන් හොඳින් ක්රියා කරයි:

#### භාවිත කළ යුතු අවස්ථා

Caveman ප්රතිදාන ප්රකාරය **තෝරා සක්රිය කළ යුතු** එකකි. සම්පීඩනය සක්රියව තිබෙන විට (`enabled: true`, Compression Settings පිටුවේ

මඟින් `lite`, `full` හෝ `ultra` තෝරයි:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

`omniroute_set_compression_engine` MCP මෙවලම එහි බූලීය `outputMode`

**Terse prose** ප්රතිදාන ශෛලිය සක්රිය කිරීමෙන් එම කොටසම එන්නත් කරයි (පහත ප්රතිදාන
ශෛලී බලන්න).

3. **`shellOutput`**: ANSI CSI අනුක්රමයක් (`ESC[` පසු ඉලක්කම් හෝ අර්ධවිරාම සහ පසුව අකුරක්, වර්ණ කේතවල මෙන්) හෝ පෙළේ ඕනෑම තැනක හිස්තැනක් පසුපස ඇති `$` අඩංගු ප්රතිදානයකින් එම අනුක්රම ඉවත් කරයි (වෙනත් escape අනුක්රම, `ESC[?25l` හෝ OSC කවුළු-මාතෘකා අනුක්රමයක් වැනි දෑ, තබා ගනී) සහ අඛණ්ඩව නැවත නැවත එන පේළි ඒකාබද්ධ කරමින් අවසාන පේළි 50 තබා ගනී. මෙම පරීක්ෂාව `json` සහ `errorMessage` වලට පෙර ධාවනය වන බැවින්, එවැනි `$` එකක් අඩංගු JSON හෝ දෝෂ ප්රතිදානයක් `shellOutput` සක්රීයව ඇති විට ඒවා වෙත කිසිවිටෙක ළඟා නොවේ.
4. **`json`**: විකල්ප හිස්තැන්වලින් පසු `{` හෝ `[` සමඟ ආරම්භ වන, අක්ෂර 2,000කට වැඩි සහ සාර්ථකව parse වන JSON payload එකක් සාරාංශ කරයි: අයිතම 7කට වැඩි array එකක් එහි පළමු අයිතම 5, අවසාන අයිතම 2 සහ මුළු ගණන තබා ගනී; object එකක් එහි පළමු keys 20 තබා ගන්නා අතර, එක් එක් nested object හෝ array අගය `{…N keys}` placeholder එකකින් ප්රතිස්ථාපනය කරයි (array එකක් සඳහා N යනු එහි දිගයි), සහ පළමු 20ට පසු ඉවත් කළ keys ගණනය කරන `_remaining_<N>_keys` සලකුණක් එක් කරයි. Scalar අගයන් සම්පූර්ණයෙන්ම පිටපත් කරනු ලැබේ. එබැවින් nested අගයන් නොමැති keys 20ක් හෝ ඊට අඩු object එකක් නැවත indentation කිරීම පමණක් සිදු වේ — minified object එකක අක්ෂර ගණන වැඩි වන බැවින් එය නොවෙනස්ව පවතී.
5. **`errorMessage`**: ඕනෑම ස්ථානයක සහ ඕනෑම අකුරු case එකකින් `error:`,
   `error ` (`no error found` හි මෙන්, පසුව හිස්තැනක් ඇති වචනය), `[error]`,
   `exception:`, `exception `, `[exception]` හෝ `traceback` අඩංගු ප්රතිදානයක් එහි පළමු පේළිය, ඊළඟ පේළි 10 සහ අවසාන පේළි 3 තබා ගන්නා අතර, ඒවා අතර ඇති පේළි වෙනුවට `… [N frames elided] …` සලකුණක් යොදයි. පළමු පේළියට පසු පේළි 13කට වැඩි ගණනක් ඇති විට පමණක් මෙම සලකුණ දිස් වේ. එබැවින් පේළි 14ක් හෝ ඊට අඩු දෝෂ ප්රතිදානයක් කෙටි නොවේ (පේළි 12ක් හෝ 13ක් ඇති විට අවසාන පේළි 3, දැනටමත් තබා ඇති පේළි නැවත දක්වයි).

උපායමාර්ගයක් ගැළපුණු පසු, එය කිසිවක් ඉතිරි නොකළත්, පසුකාලීන උපායමාර්ග උත්සාහ නොකෙරේ. ගැළපෙන උපායමාර්ගය ඇස්තමේන්තුගත tokens කිසිවක් ඉතිරි නොකරන විට (දිග ÷ 4, ඉහළට වටකළ) — උදාහරණයක් ලෙස පේළි 25ක් හෝ ඊට අඩු code-සමාන ගොනුවක්, හෝ අක්ෂර 2,000කට වැඩි නමුත් අයිතම 7ක් හෝ ඊට අඩු JSON array එකක් — aggressive engine එක මුල් මෙවලම් ප්රතිඵලය තබා ගනී: callers දෙකම (`compressAggressive()` සහ `compressAnthropicToolResultBlock()`) `saved` 0 හෝ ඊට අඩු වූ විට මුල් අගය තබා ගන්නා අතර, `compressToolResult()` මඟින් තවමත් එම උපායමාර්ගයේ ප්රතිදානය ආපසු ලබා දෙයි. මෙවලම්-ප්රතිඵල පියවර අවසාන තීරණය නොවේ: engine එකේ fallback summarizer එකට තවමත් අක්ෂර 8,192කට වඩා දිගු `tool` හෝ `function` පණිවිඩයක් (`maxTokensPerMessage`, 2,048, ගුණ කිරීම 4) කෙටි කළ හැක.

#### භාවිත කළ යුත්තේ කවදාද

මෙවලම් ප්රතිඵල සම්පීඩනය aggressive engine එකේ පළමු පියවරයි (`open-sse/services/compression/aggressive.ts` තුළ `compressAggressive()`), එබැවින් එය Aggressive ප්රකාරයේ සහ stacked pipeline එකක `aggressive` පියවරක ධාවනය වේ. එය OpenAI-හැඩයේ `tool` සහ `function` පණිවිඩ මෙන්ම Anthropic `tool_result` blocks තුළ ඇති පෙළ ද සම්පීඩනය කරයි. සෑම උපායමාර්ගයකටම `aggressive.toolStrategies` යටතේ තමන්ගේම switch එකක් ඇති අතර, පෙරනිමියෙන් සියල්ල සක්රීයය. dashboard එකේ, compression සක්රීයව ඇති විට සහ පෙරනිමි ප්රකාරය Aggressive වන විට, switches Caveman පිටුවේ **Advanced** දසුන තුළ ඇත.

### අට්ටිගත Pipeline එක

stacked ප්රකාරය **engines කිහිපයක් අනුක්රමයෙන්** ධාවනය කරයි — සාමාන්යයෙන් පළමුව RTK (මෙවලම් ප්රතිදානයෙන් 60-90%ක ඉතිරියක්), ඉන්පසු ඉතිරි පෙළ මත Caveman (~46%ක ආදාන ඉතිරියක්). ඒවා සංයුක්ත කළ විට, එය **78-95%ක සුදුසු පරාසයයි** (ඉහත Upstream Savings Math බලන්න): `1 - (1 - 0.60..0.90) × (1 - 0.46)` හි සාමාන්යය ≈89%කි.

#### එය ක්රියා කරන ආකාරය

```
ආදානය (tokens 1000)
  → RTK (විධාන-දැනුවත් පෙරහන) → tokens 200
    → Caveman (අතිරික්ත කොටස් ඉවත් කිරීම) → tokens 108
  → ප්රතිදානය (tokens 108, ~89%ක ඉතිරියක්)
```

#### භාවිත කළ යුත්තේ කවදාද

පහත අවස්ථා සඳහා stacked ප්රකාරය භාවිත කරන්න:

- මෙවලම්-බහුල workflows (agentic coding, පර්යේෂණ)
- පිරිවැය-සංවේදී batch processing
- ඔබට උපරිම token ඉතිරියක් අවශ්ය විට

Stacked pipelines වින්යාස කරන්නේ ගෝලීය `stackedPipeline` compression සැකසුම හරහා හෝ routing combo එකකට පැවරූ නම් කළ compression combo එකක් හරහාය (ඉහත Per-Combo Override බලන්න) — auto-combo `modePack` එකක් හරහා නොවේ (එම field එක auto-combo model තේරීමේ weights නැවත සකසනවා පමණක් වන අතර, `stacked` වලංගු pack නාමයක් නොවේ).

## සම්පීඩන සංයෝජන අභිබැවීම්

විවිධ භාවිත අවස්ථා සඳහා හැසිරීම සියුම්ව සකස් කිරීමට, ගෝලීය සම්පීඩන ප්රකාරය **එක් එක් සංයෝජනය සඳහා** අභිබවා යා හැකිය:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

මෙය පහත අවස්ථා සඳහා ප්රයෝජනවත් වේ:

- **කේතකරණ සංයෝජන**: දිගු සැසි සඳහා `aggressive` ප්රකාරය භාවිත කරන්න
- **ඉක්මන් ප්රශ්නෝත්තර සංයෝජන**: වේගවත් ප්රතිචාර සඳහා `lite` ප්රකාරය භාවිත කරන්න
- **මෙවලම් බහුල සංයෝජන**: උපරිම ඉතිරි කිරීම් සඳහා `stacked` ප්රකාරය භාවිත කරන්න
- **නිෂ්පාදන සංයෝජන**: හැඹිලිගත කිරීමේ සැපයුම්කරුවන් සඳහා අභිබැවීම අක්රියව තබන්න — සැමවිටම සක්රිය
  හැඹිලි-දැනුවත් ගැළපීම මඟින් `aggressive`/`ultra` ස්වයංක්රීයව `standard` දක්වා පහත හෙළයි
  (තෝරාගත හැකි `cache-aware` ප්රකාරයක් නොමැත)
