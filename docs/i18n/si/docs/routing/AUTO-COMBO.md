## ශුන්ය-වින්යාස ස්වයංක්රීය මාර්ගගත කිරීම (`auto/` උපසර්ගය)

> **නව:** combo සෑදීම අවශ්ය නොවේ. ඕනෑම client එකක සෘජුවම `auto/` උපසර්ගය භාවිත කරන්න.

### ඉක්මන් උදාහරණ

| Model ID       | ප්රභේදය | හැසිරීම                                                                            |
| -------------- | ------- | ---------------------------------------------------------------------------------- |
| `auto`         | පෙරනිමි | සම්බන්ධිත සියලු providers, LKGP උපායමාර්ගය, සමතුලිත weights                        |
| `auto/coding`  | coding  | ගුණාත්මකභාවයට ප්රමුඛත්වය දෙන weights, code ජනනය සඳහා සුදුසුය                       |
| `auto/fast`    | fast    | අඩු-ප්රමාද weighted තේරීම                                                          |
| `auto/cheap`   | cheap   | පිරිවැය-ප්රශස්ත කළ මාර්ගගත කිරීම (අඩුම පිරිවැය පළමුව)                              |
| `auto/offline` | offline | ඉහළම quota ලබාගත හැකි providers වෙත ප්රමුඛත්වය දෙයි                                |
| `auto/smart`   | smart   | වඩා හොඳ model සොයාගැනීම සඳහා ගුණාත්මකභාවයට ප්රමුඛත්වය + ඉහළ exploration rate (10%) |
| `auto/lkgp`    | lkgp    | පැහැදිලි LKGP (පෙරනිමි `auto` හා සමානයි)                                           |
| `auto/chaos`   | chaos   | සමාන්තර fan-out, එක් provider එකකට එක් model එකක් (fault injection නොවේ)           |

### ප්රවර්ගය × ස්තර සංයෝජනය (`auto/<category>:<tier>`)

OpenRouter-ශෛලියේ suffix මඟින් **කුමන ආකාරයේ මාර්ගයක්ද** (category) යන්න **එය ප්රශස්ත කරන්නේ කෙසේද** (tier) යන්නෙන් වෙන් කරයි, එබැවින් ඒවා නිදහසේ සංයෝජනය කළ හැකිය (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ප්රවර්ග** (හැකියාව අනුව candidate pool එක පෙරහන් කරන්න): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` මඟින් vision හැකියාව ඇති models තබා ගනී; `reasoning` මඟින් reasoning/thinking models තබා ගනී.
- **ස්තර** (scoring weights / pool filter එක තෝරන්න): `fast` (ඉක්මනින් නිකුත් කිරීම) · `cheap` (`floor` යන alias එක, පිරිවැය ඉතිරි කිරීම) · `reliable` (circuit-breaker සෞඛ්යය + latency ස්ථායීතාව) · `free` / `pro` (`classifyTier` හරහා model tier අනුව pool එක පෙරහන් කිරීම — free-tier එදිරිව premium).

| උදාහරණය                | විසඳෙන්නේ                                                         |
| ---------------------- | ----------------------------------------------------------------- |
| `auto/coding:fast`     | coding pool, අඩු-ප්රමාද weights                                   |
| `auto/coding:cheap`    | coding pool, පිරිවැය-ප්රශස්ත කළ (`auto/coding:floor` යන alias එක) |
| `auto/reasoning:pro`   | reasoning/thinking models පමණි, premium tier                      |
| `auto/vision`          | vision හැකියාව ඇති models (tier එකක් නැත → සමතුලිත weights)       |
| `auto/multimodal:free` | multimodal හැකියාව ඇති models, free tier පමණි                     |

වලංගු ඕනෑම `auto/<category>[:<tier>]` එකක් ඉල්ලුම අනුව resolve වේ; තෝරා සැකසූ subset එකක් `/v1/models` සහ dashboard එකෙහි ප්රචාරණය කෙරේ (`open-sse/services/autoCombo/builtinCatalog.ts` හි `AUTO_SUFFIX_VARIANTS`). Filtering **fail-open** වේ — constraint එකක් කිසිදු සම්බන්ධිත model එකකට නොගැළපෙන්නේ නම්, routing කිසි විටෙකත් බිඳ නොවැටෙන ලෙස සම්පූර්ණ pool එක භාවිත කෙරේ. මූලික scorer එක (`combo.ts`) වෙනස් කර නැත; category/tier filter එක `buildAutoCandidates` තුළ යොදනු ලැබේ.

> **සජීවී model බුද්ධිය:** `ARENA_ELO_SYNC_ENABLED` flag එක ක්රියාත්මක විට, auto-routing යෝග්යතාව සජීවී **Arena ELO** ශ්රේණිගත කිරීම් + **models.dev** tier දත්ත මඟින් දැනුවත් කෙරේ (එසේ නොමැති විට static fitness map එක වෙත ආපසු යයි).

**භාවිත කරන ආකාරය:**

```bash
# OpenAI ආකෘතියට සහාය දක්වන ඕනෑම IDE හෝ CLI මෙවලමක්
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ඔබේ code/config තුළ model එක මෙසේ සකසන්න:
model: "auto"                 # සමතුලිත පෙරනිමිය
model: "auto/coding"          # coding කාර්ය සඳහා වඩාත් සුදුසුයි
model: "auto/fast"            # ලබාගත හැකි වේගවත්ම එක
model: "auto/cheap"           # token එකකට ලාභම එක
```

**සිදුවන්නේ කුමක්ද:**

1. OmniRoute විසින් `src/sse/handlers/chat.ts` තුළ `auto/` උපසර්ගය හඳුනා ගනී
2. database එකෙන් සියලු **සක්රිය provider connections** විමසයි
3. වලංගු credentials (API key හෝ OAuth token) ඇති ඒවාට පෙරහන් කරයි
4. connection එකකට model එක තීරණය කරයි (`connection.defaultModel` හෝ providerගේ පළමු model එක)
5. memory තුළ **virtual combo** එකක් ගොඩනඟයි (DB එකෙහි ගබඩා නොකෙරේ)
6. තෝරාගත් variant එකේ weight profile + LKGP උපායමාර්ගය භාවිතයෙන් මාර්ගගත කරයි

**ප්රධාන ගුණාංග:**

- ✅ **සැමවිටම ක්රියාත්මකයි:** toggle එකක්, combo සෑදීමක් හෝ configuration එකක් අවශ්ය නොවේ
- ✅ **ගතිකයි:** දැනට සම්බන්ධිත providers ස්වයංක්රීයව පිළිබිඹු කරයි
- ✅ **Session stickiness:** LKGP මඟින් අවසන් වරට සාර්ථක වූ provider වෙත ප්රමුඛත්වය දීම සහතික කරයි
- ✅ **බහු-account පිළිබඳ දැනුවත්:** එක් එක් provider connection එක වෙනම candidate එකක් බවට පත්වේ

## සුරකින ලද ස්වයංක්‍රීය සංයෝජන සඳහා ගිණුම් මනාප

බුද්ධිමය ස්වයංක්‍රීය සංස්කාරකය විකල්පයක් ඉදිරිපත් කරයි** ගිණුම් මනාප** කොටස. සෑම සම්බන්ධතාවයක්ම මනාප, සාමාන්‍ය (පෙරනිමිය), රක්ෂිතය හෝ බැහැර කළ හැක. බහු සම්බන්ධතාවලට ස්ථරයක් බෙදා ගත හැක. ස්වයංක්‍රීයව එහි scoring/router හැසිරීම රඳවා ගනිමින් පළමු සුදුසුකම් ලත් ස්ථරය තුළ තෝරා ගනී; අසාර්ථක උත්සාහයන් ඉතිරි සංයුක්ත ගිණුම් වලට වැටේ, රක්ෂිතයට පෙර සාමාන්‍යයට පෙර කැමති වේ. මෙම සංයෝජනයෙන් බැහැර කළ සම්බන්ධතා කිසි විටෙක භාවිතා නොවේ.

සැකසුම `config.accountPreferences` ලෙස ගබඩා කර ඇත, ID සම්බන්ධතාවයෙන් යතුරු කර ඇත:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

අත්හැර දැමූ හෝ හිස් සිතියමක් දැනට පවතින මාර්ගගත කිරීම් රඳවා තබා ගනී. මනාපයන් අබල කළ සම්බන්ධතා සබල නොකරයි, API-යතුරු ප්‍රවේශය ලබා දෙන්නේ නැත, කෝටාව-අවහිර කළ අපේක්ෂකයින් ප්‍රතිසාධනය කරයි, හෝ අයවැය චෙක්පත් මඟ හරින්නේ නැත. සෑම උත්සාහයක්ම එහි සංයුක්ත සම්බන්ධතාවයට සීමා කර ඇත, එබැවින් ගිණුම් ආපසු හැරීමට සංයුක්ත රවුටරය පිටුපසින් ස්ථර පැනිය නොහැක. පවතින සැසි සම්බන්ධතාව සුදුසුකම් ලත් ගිණුමක් තබා ගත හැක; නිශ්ශබ්දව ගිණුම් වෙනස් කිරීම වෙනුවට හැරෙන ස්වදේශීය හැරීමකට බැඳී ඇති ගිණුම හැර.

වින්‍යාස කළ මනාපයන් ගිණුම්-දැනුවත් ස්වයංක්‍රීය මාර්ගය භාවිතා කරයි: නොබැඳි සන්දර්භය-හැඹිලිය, ස්මාර්ට්-පයිප්ලයින්, අවුල් සහ සෙවනැලි කෙටිමං යවා නැත. මෙම ඉල්ලීම් සඳහා සමපේක්ෂන හෙජිං අක්‍රිය කර ඇති නිසා සංචිත ගිණුම්වලට මනාප අය කළ නොහැක. වෙනත් සංයෝජන උපාය මාර්ග මෙම සැකසුම අර්ථ නිරූපණය නොකරයි. ස්වයංක්‍රීයව සිට සංයෝජනයක් වෙනස් කිරීම පසුකාලීන ස්විචයක් සඳහා සුරකින ලද මනාපයන් තබා ගනී.

## සැබෑ Model Id එකකට ගැළපෙන Combo නම්

හිස් model id එකකට සමාන `name` එකක් ඇති combo එකක් (උදා. `gpt-5.5` නමින් ඇති combo එකක්) යනු දෝෂයක් නොව, **හිතාමතාම සපයන සහය දක්වන රටාවකි**: එය [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) හි ලේඛනගත කර ඇති එක් එක් model id සඳහා provider fallback යාන්ත්රණයයි. හිස්-model-id විසඳීමට පෙර combo විසඳීම පරීක්ෂා කරන බැවින් (`src/sse/services/model.ts` හි `getComboForModel()`), හිස් id එක වන `gpt-5.5` සඳහා ඉල්ලීමක් සෘජුවම තනි provider කෙනෙකු වෙත යැවීම වෙනුවට combo එකේ targets හරහා (උදා. `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) යොමු කරයි — මෙය [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) සඳහා ගොඩනැගූ combo-before-rewrite ප්රමුඛතාව නැවත භාවිත කරන අතර `tests/unit/responses-combo-resolution-3227.test.ts` සහ `tests/unit/combo-name-codex-responses-rewrite.test.ts` මඟින් regression පරීක්ෂාවට ලක් කර ඇත.

සැබෑ model id එකක් සඟවන නමකට combo එකක් සෑදීම හෝ නැවත නම් කිරීම **කිසිවිටෙක ප්රතික්ෂේප නොකෙරේ** — එසේ කිරීමෙන් මෙම ලේඛනගත workflow එක බිඳ වැටෙනු ඇත. ඒ වෙනුවට (#8530), (නව) නම සැබෑ model id එකක් සමඟ ගැටෙන විට `POST /api/combos` සහ `PUT /api/combos/[id]` response එකට ක්රියාකාරිත්වය අවහිර නොකරන `warning` field එකක් එක් කරයි:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Boot වන අවස්ථාවේදී, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ද model id එකක් සඟවන සෑම පවතින combo එකක්ම ලැයිස්තුගත කරමින් එක් පේළියක `[STARTUP]` අනතුරු ඇඟවීමක් log කරයි. එමඟින් #6940 අනුව හිතාමතා කරනවාට වඩා අහම්බෙන් මෙයට මුහුණ දෙන operators හට සංඥාවක් ලැබේ. හඳුනාගැනීමේ helper එක `src/lib/combos/modelNameCollision.ts` හි ඇත.

## Client එකකින් Custom Combo එකක් ඇමතීම

Persist කර ඇති combos (Settings → Combos) භාවිත වන්නේ client එක `model` field එකෙහි combo එකේ **නිශ්චිත නම** යවන විට පමණි — combo නම සඳහා fuzzy හෝ partial matching නොමැති අතර `auto/` prefix එකක්ද සම්බන්ධ නොවේ. විසඳීමේ අනුපිළිවෙළ (`src/sse/services/model.ts` හි `getComboForModel()`):

1. නිශ්චිත combo-name ගැළපීම (`model: "my-combo"`),
2. `combo/<name>` prefix එක (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

පොදු වැරදි අවබෝධ දෙකක්:

- **`auto` ඔබගේ combos භාවිත නොකරයි.** `auto`/`auto/*` තමන්ගේම zero-config candidate pool එකක් ගොඩනඟන අතර, `auto` යන නමම ඇති combo එකක් තිබේ නම් පමණක් persist කර ඇති combos සලකා බලයි (නිර්දේශ නොකෙරේ). Combo එකක් හරහා යොමු කිරීමට, `auto` නොව එහි නිශ්චිත නම යවන්න.
- **`openrouter/auto` යනු සැබෑ ගෙවීම් සහිත OpenRouter නිෂ්පාදනයකි** ("Auto Best Available"), OmniRoute alias එකක් නොවේ. එය OpenRouter registry එකේ (`open-sse/config/providers/registry/openrouter/index.ts`) ඇති එකම static model entry එක වන අතර ඒ සඳහා වෙනම ගාස්තු අය කෙරේ. එය `auto` pools වෙතින් ඉවත් කිරීමට Settings → Routing → Hide paid models භාවිත කරන්න.

මෙහි ලේඛනගත කර ඇති මුල් ව්යාකූලතාව සඳහා [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) සහ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) බලන්න.

## එය ක්‍රියා කරන ආකාරය (පසුගිය ස්වයංක්‍රීය සංයෝජන)

ඔටෝ-කොම්බෝ එන්ජිම ගතිකව එක් එක් ඉල්ලීම සඳහා හොඳම provider/model තෝරා ගනී**16-සාධක ලකුණු කිරීමේ කාර්යය** ( `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` හි අර්ථ දක්වා ඇත). පෙරනිමි බර එකතුව `1.0` වෙත; අභිරුචි බර `normalizeScoringWeights()` මගින් නැවත යථා තත්ත්වයට පත් කෙරේ. — `cacheAffinity` සහ `resetWindowAffinity` — දහසයෙන් දෙකක් `0` හි පෙරනිමි බරක් දරයි; `reliability` `DEFAULT_WEIGHTS` හි `0` දරයි නමුත් `0.03` සාමාන්‍ය ඇසුරුම්වල සහ `0.04` `reliability-first` වලදී සහ `quality` ඇසුරුම්වල `0.02` දරයි ( `quality-first` හි`0.03` ): ඒවා තවමත් සෑම අපේක්ෂකයෙකු සඳහාම ගණනය කර ඇත, සහ `cacheAffinity` ගේට්ටු ප්‍රමාද-හැඹිලි අඩුකිරීම ලකුණු වලින් පිටත, එබැවින් පෙරනිමියෙන් පැකේජයක් නොවන අතර, පෙරනිමි සාධක ඇසුරුම් නොකරයි.

### `weighted` අර්ථ ශාස්ත්‍රය

`weighted` යනු a **ඉල්ලීමකට සමානුපාතික අහඹු ඇඳීම** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), සමකරනයක් නොවේ:

- සෑම ඉල්ලීමක්ම ඇද ගනී**එකක්** සම්භාවිතාව සමග පියවර `weight / totalWeight`; ඉතිරි පියවර එම ඉල්ලීම සඳහා පසුබැසීම දාමය ලෙස බර අවරෝහණ මගින් ඇණවුම් කර ඇත.
- `0` (හෝ අතුරුදහන්) බර ඇති පියවරකි**කවදාවත් ඇදලා නැහැ** වෙනත් ඕනෑම පියවරක් බර > 0 — ඇති අතර, එය පසුබැසීමක් ලෙස ක්‍රියා කළ හැක්කේ අඳින ලද පියවර අසාර්ථක වූ පසුව පමණි. විට පමණි**සියලු** බර 0 යි තේරීම ඒකාකාර වේ.
- ඉලක්ක සියල්ල ලබා ගත නොහැකි පියවර — සැපයුම්කරු පරිපථ කඩනය `OPEN`, සම්බන්ධතා සිසිලනය, ආදර්ශ අගුලු දැමීම — එය සිදුවීමට පෙර දිනුම් ඇදීමෙන් ඉවත් කරනු ලැබේ (`open-sse/services/combo/targetResolution.ts`), එබැවින් එක් සෞඛ්‍ය සම්පන්න පියවරකට සෑම ඉල්ලීමක්ම තාවකාලිකව දිනා ගත හැක.
- `stickyWeightedLimit` (combo config, default `1` = off) නැවත ඇඳීමට පෙර එම අඛණ්ඩ සාර්ථකත්වයන් සඳහා අඳින ලද පියවර සම්බන්ධ කරයි.

දැඩි භ්රමණය සඳහා `round-robin` භාවිතා කරන්න ; `weighted` මත සමාන බරක් සංඛ්‍යානමය — ලබා දෙන්නේ දැඩි — ශේෂයක් නොවේ.

මේවා ක්‍රියාකරු විසින් තෝරන ලද අනුක්‍රමික JSON අනුලකුණු අයවැය, සංකේත සන්දර්භ කවුළු හෝ සහතික කළ උඩුගං සීමාවන් නොවේ. නිශ්චිත මාදිලිය IDs පෙරනිමිය අභිබවා යයි. එළිපත්තට ඉහළින්, සංයුක්ත කිරීම සමාන මෙවලම් නිර්වචන ඉවත් කරයි, විශාල මෙවලම් සාක්‍ෂි දිරවීමකින් කප්පාදු කරයි, සහ ඉලක්ක අනුපාතය දෙසට පැරණි සම්පූර්ණ ඉතිහාස කණ්ඩායම් ඉවත් කරයි. එය system/developer උපදෙස්, නවතම පරිශීලක ඉල්ලීම, සමාන්තර calls/results ඇතුළු අවසාන මෙවලම් වටය සහ Gemini හි ප්‍රමුඛ මාර්ගගත උපදෙස් රඳවා ගනී. ඉහළ මට්ටමේ උපදෙස් සහ මෙවලම් සැකසුම් සංරක්ෂණය කර ඇත. අතපසුවීම් සලකුණක් ඉවත් කළ ඉතිහාසය වාර්තා කරයි; මෙය නිර්ණායක කප්පාදුවක් මිස අර්ථ සාරාංශයක් නොවේ. අමුණන ලද සන්දර්භය තවමත් අයවැය ඉක්මවා ඇත්නම්, ආකෘතිය සම්බන්ධ කර ගැනීමට පෙර ඉල්ලීම 413 ලබා දෙයි. සංයුක්ත අක්‍රිය හෝ එළිපත්තට පහළින් ඉල්ලීම නොවෙනස්ව ගමන් කරයි.

මෙවලම්-ප්‍රතිඵල අඛණ්ඩව, OmniRoute අඛණ්ඩව සම්පූර්ණ කරන ලද වට දෙකක් එකම මෙවලම් ඇමතුම් නොවෙනස් වූ ප්‍රතිඵල සමඟ පුනරුච්චාරණය කරන විට හෝ අඛණ්ඩව වට දෙකකදී පැහැදිලිව සලකුණු කළ සෑම ප්‍රතිඵලයක්ම අසාර්ථක වූ විටද ක්‍රියාත්මක වීම නතර කරයි. වෙනස් කළ ප්‍රතිඵල නැවත නැවත ඇමතුම්වලට අවසර දෙයි (උදාහරණයක් ලෙස, ඡන්ද විමසීම). ආරක්‍ෂකය නැවුම් පරිශීලක ඉල්ලීමක් මත යළි සකසයි, සමාන්තරව ඇමතුම් එක් වටයකට සමූහගත කරයි, සහ Anthropic, කතාබස් සම්පූර්ණ කිරීම්, ප්‍රතිචාර සහ Gemini ඉතිහාසය සඳහා සහය දක්වයි. සැලසුම්කරුට හේතුව ලැබෙන අතර එය වෙනත් මෙවලම් වටයක් ඉල්ලා සිටියද අවසාන පිළිතුර හිමිවේ.

දෙවන ඉලක්කයෙන් පසු අතිරේක ආකෘති ක්රියාත්මක කරන්නාගේ උපස්ථ ඇණවුම් කරනු ලැබේ. අසාර්ථක HTTP ප්‍රතිචාරයක් හෝ ප්‍රවාහන ව්‍යතිරේකයක් ඊළඟ ක්‍රියාත්මක කරන්නා වෙත ඉදිරියට යයි, එම සැලසුම්කරුගේ තීරණයම සහ ස්වදේශීය මෙවලම් ද රැගෙන නමුත් එම ක්‍රියාත්මක කරන්නාගේම පියවර කඩිනම් සහ විසඳන ලද සම්බන්ධතාවය. - `connectionAwareExpansion` (combo config, පසුව සැකසුම්, පෙරනිමිය **බොරු** ) භ්‍රමණය වීමට පෙර එක් එක් සැපයුම්කරු මට්ටමේ පියවර එක් ගිණුමකට ඉලක්ක වෙත පුළුල් කරයි. B කාණ්ඩයේ උපාය මාර්ග (ප්‍රමුඛත්වය, බර, රවුම්-රොබින්, අහඹු, p2c, අවම වශයෙන් භාවිත කළ, පිරිවැය-ප්‍රශස්ත, lkgp, පුරවන්න-පළමු, දැඩි-අහඹු, සන්දර්භය-ප්‍රශස්ත, හැඹිලි-ප්‍රශස්ත, සන්දර්භය-රිලේ, විලයන, නල මාර්ගය) මෙය ක්‍රියාත්මක වන තෙක් සැපයුම්කරු මට්ටමේ දසුනක් තබා ගන්න. සංයෝජන සංස්කාරකය හෙලිදරව් කරයි inherit / on / off; inherit ගෝලීය පෙරනිමි (අක්‍රිය) භාවිතා කරයි.
- ක්ෂණික-හැඹිලි ප්‍රාදේශීය මාර්ගගත කිරීම (`promptCacheAffinityEnabled`, පෙරනිමිය **ඇත්ත** ) අමුණන ලද සම්බන්ධතා නැවත ඇණවුම් කරයි, එවිට ගැලපෙන හැඹිලි යතුරු එක ගිණුමක පවතී. එය රවුන්ඩ් රොබින් සහ එක් ගිණුමකට අමුණන ලද පියවර හරහා බර භ්‍රමණයට වඩා ප්‍රමුඛත්වය ගනී. ඔබට දැඩි භ්‍රමණය අවශ්‍ය නම් Settings → Combo defaults යටතේ එය අක්‍රිය කරන්න. එක්-කොම්බෝ අභිබවා යාමක් නොමැත.

එක් ආකෘතියක් මත බහු ගිණුම් භ්රමණය සඳහා, කැමති**එක් ගතික-ගිණුම් පියවරක්** (හිස් `connectionId`, සම්පූර්ණ තටාකය) ඇලෙන සුළු සීමාවක් සහිත `1`, අමුණන ලද `connectionId` s තුනක් නොවේ. RR කවුන්ටරය ඉදිරියට යන අතරතුරේදී පවා ඇලවූ පියවර සහ සම්බන්ධතාවය එකම ගිණුමට කඩා වැටේ.

## Fusion Strategy

`fusion` යනු එක් උපාය මාර්ගයකි**නැත** තනි ඉලක්කයක් තෝරන්න. එය විමසුමට රසිකයි**සෑම පැනල් ආකෘතියක්ම සමාන්තරව** , පසුව වින්යාසගත කළ හැකි**විනිශ්චය ආකෘතිය** සියලුම පැනල ප්‍රතිචාර වලින් තනි අවසාන පිළිතුරක් සංස්ලේෂණය කරයි. උඩු ගංවතුර `decolua/9router` (OpenRouter's Fusion design) වෙතින් පෝර්ට් කර ඇත; `open-sse/services/fusion.ts` හි ක්රියාත්මක කිරීම.

එය ක්රියා කරන ආකාරය:

0. **මෙවලම් සහිත බයිපාස්** — `tool_choice` සමඟ හිස් නොවන `tools` අරාවක් ගෙන යන ඉල්ලීමක් පැහැදිලිවම `"none"` පැනලය සම්පූර්ණයෙන්ම මග හරියි: එය වෙනස් නොකළ `tools`/`tool_choice` සමඟින් තනි මාදිලියකට (වින්‍යාස කළ විනිසුරු හෝ `panel[0]`) සෘජුවම ගමන් කරයි. පැනල් සාමාජිකයින්ට මෙවලම් ප්‍රවේශයක් නොමැති අතර විනිශ්චයකරුගේ සංශ්ලේෂණ විධානය මෙවලම්-ඇමතුම් විමෝචනය අධෛර්යමත් කරයි, එබැවින් agentic/tool-calling සේවාදායකයින්ට සංස්ලේෂණය කළ ගද්‍ය (#6771) වෙනුවට සැබෑ මෙවලම් ඇමතුම් තීරණයක් ලැබේ.
1. **Fan-out** (මෙවලම් දරණ නොවන ඉල්ලීම් පමණි) — ප්‍රේරකය සෑම පැනල් මාදිලියකටම එකවර යවනු ලැබේ, මෙවලම් ඉවත් කර ප්‍රවාහ නොකිරීමට බල කෙරේ (විනිසුරුවරයාට සංස්ලේෂණය කිරීමට සම්පූර්ණ ගද්‍ය අවශ්‍ය වේ).
2. **ගණපූරණය-කරුණා එකතුව** — `minPanel` පිළිතුරු පැමිණි විගස, ස්ට්රැග්ලර් සඳහා කෙටි වරප්රසාද ටයිමරයක් ආරම්භ වේ, පසුව එකතු කරන ලද ඕනෑම දෙයක් සමඟ විලයනය සිදු වේ. මෙය බිත්ති කාලය මත මන්දගාමී මාදිලියේ දඩය සීමා කරයි, දුෂ්කර කල් ඉකුත්වීමකින් සීමා වේ.
3. **විනිසුරු සංශ්ලේෂණය** — පැනලයේ පිළිතුරු නිර්නාමික කර ඇත (`Source 1`, `Source 2`, … — එබැවින් විනිසුරුවරයා ද්‍රව්‍ය කිරා මැන බලයි, ආකෘති සන්නාමය නොවේ) සහ විනිසුරුවරයාට භාර දෙන අතර, එය සම්මුතිය / ප්‍රතිවිරෝධතා / අර්ධ ආවරණය / අද්විතීය තීක්ෂ්ණ බුද්ධිය / අන්ධ ස්ථාන විශ්ලේෂණය කරයි.**එකක්** බලයලත් පිළිතුර. විනිසුරු ඇමතුම සේවාලාභියාගේ මුල් `stream` ධජය + මෙවලම් තබා ගනී, එබැවින් ප්‍රවාහ සහ පහළ මෙවලම් භාවිතය තවමත් ක්‍රියාත්මක වේ.
4. **අලංකාර පිරිහීම** — 0 පැනලය පිළිතුරු → `503`; හරියටම 1 දිවි ගලවා ගත් → පිළිතුර සෘජුවම ආපසු ලබා දෙයි (ෆියුස් කිරීමට කිසිවක් නැත); තනි මාදිලි පුවරුවක් සෘජුවම පිළිතුරු දෙයි.

පැනල සාමාජිකයෙකු එය විසඳන — තවත් සංයෝජනයක් වන `combo-ref` පියවරක් (`{kind: "combo-ref", comboName: "..."}`) විය හැකිය **එක් කළු පෙට්ටි පැනල් හඬක්** (යොමු කරන ලද කොම්බෝ වෙත සම්පූර්ණ පුනරාවර්තන යැවීමක්, එම කොම්බෝගේම ඉලක්ක වලින් රසිකයෙක් නොවේ), එකම depth/cycle ආරක්ෂාව සමඟම අනෙකුත් සෑම කොම්බෝ-රෙෆ්-පරිභෝජන උපායමාර්ගය දැනටමත් භාවිතා කරයි (#6764).

## අතථ්ය Auto-Combo කර්මාන්තශාලාව

Auto Combo එන්ජිමට පෙර-නිර්වචිත combos අවශ්ය නොවේ. ඒ වෙනුවට, `open-sse/services/autoCombo/virtualFactory.ts` මඟින් අවශ්ය අවස්ථාවේදීම අපේක්ෂකයන් ගොඩනඟයි:

1. `getProviderConnections({ isActive: true })` (සක්රීය කර ඇති සියලු සම්බන්ධතා) ලබාගනී
2. වලංගු අක්තපත්ර ඇති ඒවාට පෙරහන් කරයි (API යතුරක් හෝ `hasUsableOAuthToken()` හරහා කල් ඉකුත් නොවූ OAuth ටෝකනයක්)
3. ආකෘති ලබාගත හැකි බව සහ මිලකරණය සඳහා `getProviderRegistry()` සමඟ හරස්-යොමු කරයි
4. සෑම `(provider, model, connection)` ටියුපලයක් සඳහාම `VirtualAutoComboCandidate` එකක් ගොඩනඟයි
5. යැවීමේ ඉලක්කය ලෙස `connection.defaultModel` (හෝ රෙජිස්ට්රියේ පළමු ආකෘතිය) තෝරයි
6. සාධක 16කින් යුත් `scorePool()` සහ ප්රභේදයේ බර පැකේජය භාවිතයෙන් සෑම අපේක්ෂකයෙකුටම ලකුණු ලබාදෙයි
7. `handleComboChat()` සඳහා ප්රතිඵලයක් ලෙස ලැබෙන මතකය තුළ පවතින `AutoComboConfig` ආපසු ලබාදෙයි — කිසිවිටෙක DB වෙත ස්ථිරව සුරකින්නේ නැත

මෙයින් අදහස් වන්නේ **`auto/*` සක්රීය කර ඇති නව සැපයුම්කරුවෙකු එක් කිරීමෙන් අපේක්ෂක සංචිතය ස්වයංක්රීයව පුළුල් වන බවයි** — combos අතින් සංස්කරණය කිරීමට අවශ්ය නොවේ. එක් එක් ඉල්ලීම සඳහා අතථ්ය combo එක නැවත ගොඩනඟන බැවින්, අලුතින් එක් කළ හෝ නැවත සෞඛ්ය සම්පන්න වූ සම්බන්ධතා වහාම භාවිතයට ගැනේ.

## API

**කැපවූ `POST /api/combos/auto` endpoint එකක් නොමැත** — Auto-Combo පහත ආකාර දෙකෙන් භාවිත කෙරේ:

1. **ශුන්ය-වින්යාසය (නිර්දේශිතයි):** `model: "auto"` හෝ `model: "auto/<variant>"` සහිත ඕනෑම chat completion ඉල්ලීමක් යවන්න. අතථ්ය factory එක එක් එක් ඉල්ලීම සඳහා combo එක ගොඩනඟයි — persistence හෝ API ඇමතුම් අවශ්ය නොවේ.

2. **`strategy: "auto"` සහිත ස්ථිරව සුරැකි combo එකක්:** `POST /api/combos` හරහා සාමාන්ය combo එකක් සාදා, `strategy: "auto"` සමඟ `config.auto.weights` / `config.auto.candidatePool` සකසන්න. එම scoring engine එකම භාවිත කෙරේ; combo එක `combos` තුළ ගබඩා කර ID එක අනුව නැවත භාවිත කළ හැක.

සොයාගැනීම සඳහා, `GET /api/combos/auto` මඟින් විසඳන ලද candidate pool එක සහ candidate pool එකේ windows සියල්ල අතරින් උපරිම අගයන් වන `context_length` / `max_output_tokens` සමඟ සෑම variant එකක්ම ලැයිස්තුගත කරයි. Clients (උදා. opencode plugin එක) `0` වෙනුවට මෙම අගයන් ප්රචාරය කළ යුතුය: ශුන්ය context එකක් opencode හි auto-compaction සම්පූර්ණයෙන්ම අක්රිය කරයි; එවිට gateway හි history purge කිරීමෙන් context එක විනාශ වන තෙක් sessions වර්ධනය වේ. MAX අගය ප්රචාරය කිරීම ආරක්ෂිතය, මන්ද auto-combo context pre-filter එක අතිවිශාල ඉල්ලීම් විශාල-window candidates වෙත route කරන බැවිනි.

### Auto router උපායමාර්ග

ස්ථිරව සුරැකි `strategy: "auto"` combos සඳහා `config.routerStrategy` (හෝ පැරණි
`config.auto.routerStrategy`) පහත අගයන්ගෙන් එකකට සැකසිය හැක:

- `rules` — පෙරනිමි weighted scoring
- `score` — වින්යාස කර ඇති ඉහළම weighted score එක තෝරයි. සම්පූර්ණයෙන් සමාන ලකුණු ඇති විට වින්යාස කර ඇති
  candidate අනුපිළිවෙළ සුරැකේ; පවතින `explorationRate` එක සම්පූර්ණ ranked pool එකෙන් නියැදි ලබා ගනී.
- `cost` / `eco` — අඩුම මිල සහිත සෞඛ්ය සම්පන්න provider
- `latency` / `fast` — reliability penalty එකක් සමඟ අඩුම p95 latency
- `sla-aware` / `sla` — p95 latency, error-rate සහ විකල්ප
  cost SLOs සපුරාලන candidates වෙත ප්රමුඛත්වය දෙයි
- `lkgp` — අවසන් වරට හොඳ තත්ත්වයේ තිබූ provider පළමුව
- `nadir` — prompt එකට අවශ්ය pool එකේ කුමන model එකදැයි [Nadir](https://getnadir.com) හි decision API එකෙන් විමසයි;
  මෙය opt-in වන අතර, අසමත් වුවහොත් විවෘත ආකාරයෙන් `rules` වෙත මාරු වේ

### Router උපායමාර්ග සවිස්තරව

Auto-combo engine එක, `config.routerStrategy` (හෝ පැරණි `config.auto.routerStrategy`) හරහා
මාරු කළ හැකි, plug කළ හැකි **RouterStrategy** implementations 7ක් සපයයි.
සෑම strategy එකක්ම `RoutingContext` එකක් (task type, tool/vision ඉඟි, token ඇස්තමේන්තුව, විකල්ප SLA policy එකක්, විකල්ප
last-known-good provider එකක්) ලබා දුන් විට candidate pool එකෙන් එක් provider කෙනෙකු තෝරයි.

#### 1. `rules` (පෙරනිමි) — සාධක 16ක weighted scoring

පවතින scoring engine එක wrap කරයි. `OPEN` circuit-breaker
candidates ඉවත් කර, වත්මන් task type එක සහ `getTaskFitness()` සමඟ `scorePool()` ධාවනය කරමින්
ඉහළම ලකුණු ලබාගත් provider තෝරයි.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: පෙරනිමි විකල්පයයි. සියලු signals අතර සමබර trade-off එකක් අවශ්ය විට භාවිත කරන්න.

**අන්වර්ථ නාමය**: `rules` (අන්වර්ථ නාමයක් නොමැත)

#### 2. `cost` / `eco` — අඩුම මිල සහිත සෞඛ්ය සම්පන්න provider

Candidate pool එක `costPer1MTokens` අනුව (ආරෝහණ අනුපිළිවෙළට) සකසා අඩුම මිල සහිත එක තෝරයි.
පළමුව `OPEN` candidates ඉවත් කරයි.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: පිරිවැයට සංවේදී workloads, batch processing හෝ background jobs සඳහා.

**අන්වර්ථ නාම**: `cost`, `eco`

---

#### 3. `latency` / `fast` — reliability penalty එකක් සමඟ අඩුම p95 latency

`p95LatencyMs + (errorRate * 1000)` අනුව සකසයි. Error-rate penalty එක නිසා,
නාමික latency අඩු වුවද විශ්වාස කළ නොහැකි providers පහළින් rank වේ.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: real-time chat, autocomplete හෝ
interactive coding assistants වැනි latency-sensitive workloads සඳහා.

**අන්වර්ථ නාම**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO අනුකූලතාව

වින්යාස කර ඇති SLO policy එක එක් එක් candidate විසින් කෙතරම් හොඳින් සපුරාලන්නේද යන්න අනුව ලකුණු ලබා දෙයි:

| සාධකය          | බර  | සූත්රය                                              |
| -------------- | --- | --------------------------------------------------- |
| ප්රමාද ලකුණු   | 35% | `threshold / max(value, ε)`                         |
| දෝෂ ලකුණු      | 35% | `threshold / max(value, ε)`                         |
| සෞඛ්ය ලකුණු    | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)   |
| පිරිවැය ලකුණු  | 10% | `threshold / max(value, ε)` හෝ ප්රතිලෝම සාමාන්යකරණය |
| ස්ථායීතා ලකුණු | 5%  | ප්රතිලෝම සාමාන්යකරණය කළ ප්රමාද සම්මත අපගමනය         |

`hardConstraints: true` වන විට, අපේක්ෂකයන් ප්රධාන වශයෙන් **උල්ලංඝන ලකුණු**
(ඔවුන් කිසියම් SLO එකක් කොපමණ ප්රමාණයකින් ඉක්මවා යන්නේද යන්න) අනුවත්, ඉන්පසු සංයුක්ත ලකුණු අනුවත් අනුපිළිවෙළට සකසනු ලැබේ. එසේ නොමැති නම්,
සංයුක්ත ලකුණු පමණක් භාවිත වේ.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ප්රතිපත්තියට සාපේක්ෂව එක් එක් අපේක්ෂකයාට ලකුණු ලබා දෙයි: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ක්ෂේත්ර** (සංයෝජන වින්යාසය මත සකසන්න):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: දැඩි ප්රමාද, දෝෂ අනුපාත හෝ පිරිවැය සීමා සහිත නිෂ්පාදන කාර්යභාර සඳහා.

**අන්වර්ථ නාම**: `sla-aware`, `sla`

#### 5. `lkgp` — අවසන් වරට යහපත් බව දන්නා සැපයුම්කරු පළමුව

පළමුව **අවසන් වරට යහපත් බව දන්නා සැපයුම්කරු** (සකසා ඇත්නම්) උත්සාහ කර, ඉන්පසු
`rules` උපායමාර්ගය වෙත පසුබසී. සැසි ඇලී සිටීම සඳහා මෙය ප්රයෝජනවත් වේ — සංවාදයක
පසු විමසුම් එකම සැපයුම්කරු විසින් හසුරුවනු ලැබේ.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules උපායමාර්ගය වෙත පසුබසින්න
    return getStrategy("rules").select(pool, context);
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: පසු විමසුම් හැසිරවීමට එකම සැපයුම්කරු අවශ්ය වන
බහු-වාර සංවාදවලදී (උදා., හැඹිලිගත කිරීම, සන්දර්භ අඛණ්ඩතාව හෝ මිලකරණ අනුකූලතාව සඳහා).

**අන්වර්ථ නාමය**: `lkgp` (අන්වර්ථ නාමයක් නැත)

#### 6. `nadir` — Nadir හරහා ප්රේරකය පිළිබඳ දැනුවත් ආකෘති තේරීම

ඉහත සෑම උපායමාර්ගයක්ම අපේක්ෂකයන් ඔවුන්ගේම දුරමිතිය අනුව ශ්රේණිගත කරයි; ඒ කිසිවක්
ඉල්ලීම කියවන්නේ නැත. `nadir`, අවසන් පරිශීලක වාරය සහ සංචිතයේ ආකෘති හැඳුනුම්
[Nadir](https://getnadir.com) හි තීරණ API වෙත (`POST /v1/bucket`) යවා, එම මෙනුවෙන්
Nadir තෝරන ආකෘතිය වෙත මාර්ගගත කරයි (`simple` → හැකියාව ඇති ලාභම ආකෘතිය, `complex` →
අතිනවීන ආකෘතිය). එම ආකෘතිය සපයන සම්බන්ධතාව තවමත් `rules` මඟින් තෝරනු ලබන බැවින්, කෝටාව,
සෞඛ්යය සහ පිරිවැය යන කරුණු කුමන ගිණුම තෝරාගත යුතුද යන්න දිගටම තීරණය කරයි.

```json
{

    "routerStrategy": "nadir",
```

### අභිරුචි රවුටර් උපායමාර්ග

පොදු API හරහා ඔබේම `RouterStrategy` ක්රියාත්මක කිරීම ලියාපදිංචි කළ හැකිය:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ඔබේ මාර්ගගත කිරීමේ තර්කනය මෙහි යොදන්න
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ඉන්පසු එය භාවිත කරන්න:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` විසින්ම අගයන් 6ක් ලැයිස්තුගත කරයි; 7 වන විකල්පය "ප්රභේදයක් නැත" යන්නයි — හිස් `auto` — එය `parseAutoPrefix()` මඟින් `variant: undefined` ලෙස හසුරුවයි.)

## Auto-Combo සමඟ ස්තර ගැළපෙන ආකාරය

සාධක 16ක ලකුණුකරණ ශ්රිතය (`open-sse/services/autoCombo/scoring.ts`) ස්තර
සාමාජිකත්වය සංඥා දෙකක් ලෙස සලකයි: `tierPriority` (0.0476) සහ `tierAffinity` (0.0476). සම්පූර්ණ
`DEFAULT_WEIGHTS` කට්ටලය සඳහා ඉහත ඇති සම්මත [ලකුණුකරණ සාධක වගුව](#how-it-works-persisted-auto-combos) බලන්න —
එක් එක් පැකේජයට අදාළ අතික්රමණ (ship-fast/cost-saver/quality-first/
offline-friendly) "එක් එක් පැකේජය සඳහා බර පැතිකඩ" වගුවේ දක්වා ඇත.

ස්තරය පමණක් **Tier 1** පළමුව තැබීමට බල නොකරයි — Tier 1 ප්රමාදය අයහපත් නම් හෝ
පිරිවැයට සාපේක්ෂ ගුණාත්මකභාවය ප්රශස්ත නොවේ නම්, Tier 2 ජය ගනී. ස්තර අනුපිළිවෙළ බලෙන් යෙදීමට,
`priority` සංයෝජන උපායමාර්ගය භාවිත කර සැපයුම්කරුවන් ස්තරය අනුව සකසන්න.

Tier 1 (දායකත්වය) දැඩි ලෙස ප්රිය කිරීමට, `tierPriority` බර වැඩි කරන්න:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ස්තර නිර්වචන සහ සැපයුම්කරු වර්ගීකරණය සඳහා [`docs/guides/TIERS.md`](../guides/TIERS.md) බලන්න.

## පරීක්ෂණ සහ ආවරණය

### නිශ්චිත routing-තීරණ අනුකෘතිය (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` විසින් mock කළ upstream එකක් සමඟ සැබෑ combo pipeline එක හරහා පොදු උපායමාර්ග 19ම සඳහා routing **තීරණය** ආරම්භයේ සිට අවසානය දක්වා තහවුරු කරයි. ආවරණයට පහත දෑ ඇතුළත් වේ:

- `ROUTING_STRATEGY_VALUES` උපායමාර්ග 19ම (ordered, weighted, cost, context, fusion, …).
- `quota-share` (අභ්යන්තර) ආරම්භයේ සිට අවසානය දක්වා: සැබෑ `selectQuotaShareTarget` seam එක (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`) හරහා DRR සාධාරණත්වය + සංතෘප්ති ප්රමුඛතාව අඩු කිරීම.
- සෑම target සංඛ්යාවක් පුරාම `context-relay` සාර්වත්රික-handoff ආවරණය.

මෙම suite එක CI තුළ (`test:integration` job) `--test-concurrency=1` සහ `--test-force-exit` සමඟ ධාවනය වන බැවින් එය නිශ්චිත වන අතර සජීවී අක්තපත්ර අවශ්ය නොවේ.

### Gated සජීවී smoke පරීක්ෂණ (CI තුළ නොවේ — සැබෑ සපයන්නන්)

| විධානය                                 | එයින් සිදු වන්නේ කුමක්ද                                                                  |
| :------------------------------------- | :--------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` සමඟ in-process සැබෑ routing; සජීවී OmniRoute DB එකක snapshot එකක් ගනී |
| `npm run test:combo:live:vps`          | සජීවී OmniRoute server එකකට එරෙහි HTTP calls (`COMBO_LIVE_BASE_URL` සකසන්න)              |
| `npm run test:combo:live:vps:failover` | එයම, හිතාමතා සැලසුම් කළ failover අවස්ථා සමඟ                                              |

මෙම smoke පරීක්ෂණ සැබෑ wire මාර්ගය (combo → provider → completion) ක්රියාත්මක කරයි. ඒවාට සජීවී අක්තපත්ර සහ VPS ප්රවේශය අවශ්ය වන බැවින්, හිතාමතාම CI වෙතින් බැහැර කර ඇත.
