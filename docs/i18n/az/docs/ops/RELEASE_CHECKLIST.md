## npm Trusted Publishing (v3.8.51-dən etibarən standart) — sorğu əsasında mərhələli, ehtiyat variant kimi birbaşa

`npm-publish.yml` defolt olaraq **npm Trusted Publishing (OIDC)** vasitəsilə yayımlayır: `stage-npm` işi (GitHub tərəfindən yerləşdirilən) həmin icra üçün GitHub-ın id-token-ını qısaömürlü npm etimadnaməsinə çevirir — repozitoriyanın sirlərində uzunömürlü npm tokeni yoxdur, 2FA sorğusu yoxdur, provenance əlavə olunur.
Bu, 2FA-nı keçən tokenlər artıq istifadədən çıxarıldığı üçün npm sanksiyalarından yan keçən üsuldur;
o, layihənin v3.8.48-ə qədər malik olduğu tam avtomatik axını bərpa edir və WS1.3 zəmanətini qoruyur (sızdırılmış token təkbaşına yayımlaya bilməz — token yoxdur).

**Birdəfəlik quraşdırma (sahib):** npmjs.com → `omniroute` paketi → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). Bu quraşdırılana qədər avtomatik addım `ENEEDAUTH` xətası ilə uğursuz olur:
`publish_mode=staged` (aşağıda) və ya `direct` ilə yenidən göndərin.

### Mərhələli yayımlama (sorğu əsasında — `publish_mode=staged`)

npm-publish iş axını artıq birbaşa yayımlamır: o, paketlənmiş tarball-u
(`check:pack-boot`) başladır və sonra `npm stage publish` icra edir — dəqiq baytlar reyestrdə
saxlanılır, **sahib təsdiqləyənədək quraşdırıla bilməz**. İnsan tərəfindən həyata keçirilən 2FA qapısı
sübutdan ƏVVƏL deyil, SONRA yerləşdirilib.

**İş axını uğurla tamamlandıqdan sonra sahibin görəcəyi addımlar:**

1. `npm stage list omniroute` — mərhələ identifikatorunu tapın (o, iş axınının xülasəsində də çap olunur).
2. Mərhələləndirilmiş baytları yoxlayın (tövsiyə olunur): `npm stage download <id>`, sonra yüklənmiş
   tarball-u müvəqqəti prefiksə quraşdırın və başladın (`npm run check:pack-boot` CI-də eyni
   paketlə→quraşdır→başlat hökmünü avtomatlaşdırır).
3. `npm stage approve <id>` — 2FA sorğusu yayımlamanın ÖZÜDÜR. `npm stage reject <id>` mərhələni silir.
4. Yayımdan sonrakı şəbəkə yoxlaması (v3.8.49 planının WS1.4-ü) yayımlanmış
   versiyanı təmiz konteynerdə ictimai reyestrdən quraşdırır və başladır.

**Təcili ehtiyat variant:** `workflow_dispatch` ilə `publish_mode=direct` köhnə dərhal `npm publish`
üsulunu bərpa edir (yalnız mərhələləndirmənin özündə problem yaranarsa istifadə edin; səbəbi qeyd edin).

**Birdəfəlik sərtləşdirmə (sahib, npmjs.com):** `omniroute` üçün Trusted Publisher-ı
yalnız mərhələləndirmə rejimində konfiqurasiya edin ki, sızdırılmış uzunömürlü token
istənilən yerdən birbaşa `npm publish` icra edə bilməsin — CI yalnız mərhələləndirə bilər;
yalnız sahibin 2FA-sı buraxılış edir.

**Qüsurlu artefaktlar üzrə təlimat (dəyişməz):** defolt ilkin tədbir kimi
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` istifadə edin
(dəqiqələr ərzində, geri qaytarıla bilər); `npm unpublish` yalnız 72 saatlıq/asılılıqların olmadığı
pəncərədə istifadə edilməli və heç vaxt ilk addım olmamalıdır. Docker: versiya teqini heç vaxt yenidən yazmayın —
geri qaytarma `latest` teqinin sonuncu işlək digest-ə yönləndirilməsidir.

**Docker Hub `latest` (hər stabil SemVer yayımlamasında məcburidir):** `docker-publish` iş axını həm
**`X.Y.Z`**, həm də `should-promote-latest.sh` bunun ən yüksək stabil SemVer olduğunu təsdiqlədikdə `:latest`
teqini **eyni digest** ilə teqləməlidir. İşdən sonra: Hub-dakı `latest` digest-i yeni SemVer digest-inə bərabər olmalı və `last_updated` dəyişməlidir. Buraxılış qeydlərində yalnız git-də mövcud olan düzəlişlərdən bəhs edilərkən `:latest` teqini köhnə
qurulmada saxlamayın. Compose sürətli başlanğıcları `:latest` istifadə edir; GitOps isə
`X.Y.Z` teqini sabit saxlamalıdır. [Docker buraxılış kanalları](../guides/DOCKER_GUIDE.md#release-channels) bölməsinə və #10317-yə baxın.

**Docker Hub təşkilat repozitoriyası (`cheaperinference/omniroute`):** Docker Hub
repozitoriyanı ad məkanları arasında köçürə bilmədiyi üçün `diegosouzapw/omniroute` öz yükləmə tarixçəsini
və hər buraxılışı saxlayır, `docker-publish` iş axınının `mirror-org-dockerhub` işi isə
hər buraxılmış versiyanı (və təşviq edildikdə `:latest` teqini)
`ghcr.io/cheaper-inference/omniroute` ünvanından təşkilat repozitoriyasına köçürür. Bunun üçün
`DOCKERHUB_ORG_USERNAME` /
`DOCKERHUB_ORG_TOKEN` sirləri tələb olunur; onlar olmadıqda iş “Docker Hub org
mirror skipped” xəbərdarlığı ilə uğurlu qalır və digər reyestrlər normal şəkildə yayımlayır. Buraxılmış versiyanı sonradan orada yayımlamaq üçün **Actions → Mirror Docker image to the Docker Hub org → Run
workflow** bölməsində `version=X.Y.Z` (və ən yüksək stabil versiya üçün
`promote_latest`) göstərin: bu, mövcud təsvirləri köçürür, yenidən qurmur.

## Hotfix Fast-Lane (label `hotfix`)

`hotfix` etiketi ilə işarələnmiş PR ağır CI matrisini (9-parçalı E2E, coverage ratchet,
quality-gate, quality-extended) ötürür və sürətli, yüksək siqnallı yoxlamaları saxlayır: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
və tarball boot-smoke (`check:pack-boot`). Məqsəd: təxminən 33 dəqiqə əvəzinə ≤15 dəqiqəyə
uğurlu nəticə əldə etməkdir.

**Giriş siyasəti — dördünün də yerinə yetirilməsi tələb olunur (Chromium/VS Code/Node emergency lane-ləri əsasında):**

1. **Ciddilik**: production işlək deyil — yayımlanmış artifact yüklənmə zamanı çökür / təhlükəsizlik düzəlişi tələb olunur / buraxılışın bütün istifadəçiləri təsirlənir. "Vacib" sözü "işlək deyil" demək deyil.
2. **Səlahiyyət**: `hotfix` etiketini yalnız repository sahibi tətbiq edir. Etiket təsdiqin ÖZÜDÜR — campaign PR üzərində heç vaxt özünüz tətbiq etməyin.
3. **Sübut**: PR mətnində əvvəlki tam yaşıl heavy run-a (ötürülmüş job-ların yenidən təsdiq etməli olduğu suite) və düzəlişin özünün əvvəlcə uğursuz, sonra uğurlu olan testinə keçid verilir.
4. **Əhatə dairəsi**: yalnız cherry-pick — minimal düzəliş, refaktorinq və əlavə dəyişikliklər yoxdur.

Ötürülmüş coverage/ratchet səthi release branch-də növbəti tam run tərəfindən yenidən yoxlanılır
(davamlı release-green) — bu lane WAITING mərhələsini ötürür, validasiyanı deyil.
Yalnız testlərə aid diff-lər (`tests/` altındakı bütün fayllar, `tests/e2e/` altında heç bir fayl yoxdur)
E2E matrisini avtomatik ötürür, heç bir etiket tələb olunmur.

### Hook-lar (Husky ilə yoxlanılıb)

Husky hook-ları `.husky/` qovluğunda yerləşir və git əməliyyatları zamanı avtomatik icra olunur.

Hook uğursuz olarsa: əsas problemi düzəldin, `--no-verify` ilə yan keçməyin.

### Build düzülüşü

Repozitoridə üç ayrı çıxış qovluğundan istifadə olunur — onları heç vaxt qarışdırmayın:

| Qovluq    | Təyinat                                                              | İzlənilir?                          |
| --------- | -------------------------------------------------------------------- | ----------------------------------- |
| `src/`    | Tətbiq mənbə kodu (TypeScript / TSX)                                 | Bəli                                |
| `.build/` | Build aralıq faylları — `next build` çıxışı (`distDir`)              | Xeyr (gitignore ilə istisna edilib) |
| `dist/`   | Göndərilə bilən npm paketi — `assembleStandalone` tərəfindən yığılır | Xeyr (gitignore ilə istisna edilib) |

> **Operator qeydi:** uzaq VPS image qovluğu `/usr/lib/node_modules/omniroute/app/` olaraq qalır.
> Yalnız **repozitoriyadaxili** build çıxışı dəyişib (`app/` → `dist/`). Deploy skill-ləri
> `dist/` məzmununu uzaqdakı `app/` qovluğuna rsync edir — VPS yollarında dəyişiklik tələb olunmur.

**Tək build axını:**

```
npm run build:release
  └─ rm -rf .build dist          (təmizləmə)
  └─ next build → .build/next/   (aralıq fayllar)
  └─ assembleStandalone          (standalone + static + public + natives → dist/ qovluğuna köçürür)
  └─ dist/BUILD_SHA yazır         (HEAD sentinel-i)
```

Deploy üçün `npm run build` əmrindən sonra ayrıca `npm run build:cli` icra ETMƏYİN — bir əmrdə təmiz yenidən build və sentinel həyata keçirən `npm run build:release` istifadə edin.

### PR önizləmə artefaktı (bir dəfə qurun, eyni baytları yayımlayın)

`.github/workflows/preview-artifact.yml` PR head-dən bir production tarball qurur və həmin dəqiq build-i
doğrulayır (#8084 dilimi (a)). Yalnız eyni repozitoriyadakı PR-lər; heç nə yayımlanmır.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # və ya `preview-artifact` etiketini əlavə edin
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # önizləmə quraşdırması
```

İcra `npm ci`, `npm run build:release`, `npm run check:pack-artifact` əməliyyatlarını yerinə yetirir, tarball-ı
paketləyir, `npm run check:pack-boot` işlədir (saxta secret-lər, müvəqqəti data qovluğu), yenidən paketləyir
və digest eyni olmadıqda uğursuz olur; sonra `artifact-identity.json` faylını (head SHA, base
SHA, lockfile heşi, platforma, arxitektura, node ABI, bundler, build siyasəti —
`scripts/release/artifact-identity.mjs`) qeyd edir və ayrıca job-da tarball üçün attestasiya yaradır.
Önizləməni yayımlamaq həmin tarball-ı quraşdırmaq deməkdir: mənbədən heç vaxt yenidən build etməyin.

### Kəsim (3.9.0, GO-dan sonra)

1. GO [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) faylında qeyd edilir.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` `RESULT: READY` çap edir.
3. Budaqları `origin` üzərində sınaq icrasının çap etdiyi əmrlərlə əl ilə yaradın —
   skript `origin`-ə push etməyi rədd edir. Yoxlanılmış develop commit-ini yenidən istifadə etmək üçün
   əvvəlcə 3.9.0 tip-i üzərində `--execute` məşqini fork-unuzda başladın; skript hər iki SHA-nı çap edir və
   eyni commit-lər push edilə bilər:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. İlk PR birləşdirilməzdən əvvəl `stable/v3` və `develop` qollarını qoruyun (qayda dəstləri + birləşdirmə növbəsi).
5. Aktiv olmayan workflow-lar budağın mövcudluğuna görə aktivləşir: `forward-port.yml` (`stable/v3`-ə push), `validate-stable-pr.yml` (`stable/v3`-ə yönələn PR-lər) və `nightly-v4-build.yml`
   (`develop` qolu ilə build-lər). Go-live-dan əvvəl repository secret-i `secrets.FORWARD_PORT_TOKEN` təyin edin (beləliklə CI
   forward-port PR-lərində işləyəcək); nightly publishing owner repository
   variable-ını `vars.NIGHTLY_PUBLISH` dəyərinə `true` təyin edənə və npm Trusted Publishing `nightly-v4-build.yml` faylını qəbul edənə qədər
   aktiv olmayacaq. Kanalın təyini `scripts/release/dist-tag.mjs` faylındadır və `npm-publish.yml` də eyni
   resolver-dən istifadə edir.
6. Kanalları yoxlayın: `npm view omniroute dist-tags --json` nəticəsində `latest` = 3.9.0 göstərilməli və v4 yayımlanana qədər `next` / `nightly` olmamalıdır.
7. Lazım gələrsə geri qaytarma: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   və `npm dist-tag add omniroute@3.8.59 latest`.

## Geri qaytarma

Buraxılışda kritik problem varsa:

1. `gh release edit vX.Y.Z --prerelease` (ən son buraxılış kimi işarələnməsin)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (yalnız istifadəçilər tərəfindən hələ qəbul edilməyibsə)
3. Və ya: `release/vX.Y.0` üzərində hotfix → patch buraxılışı `vX.Y.(Z+1)`
4. GitHub Discussions və Discord-da dərhal məlumat verin

## Sərt qaydalar

- Heç vaxt birbaşa `main` budağına commit etməyin
- Heç vaxt `main` və ya `release/*` budaqlarında `git push --force` istifadə etməyin
- Heç vaxt Husky hook-larını (`--no-verify`) ötürməyin
- Heç vaxt məxfi məlumatları, giriş məlumatlarını və ya `.env` fayllarını commit etməyin
- Coverage ≥60/60/60/60 səviyyəsində qalmalıdır (ifadələr/sətirlər/funksiyalar/budaqlar)
- `src/`, `open-sse/`, `electron/` və ya `bin/` daxilində production kodunu dəyişdirərkən həmişə testlər əlavə edin və ya mövcud testləri yeniləyin
