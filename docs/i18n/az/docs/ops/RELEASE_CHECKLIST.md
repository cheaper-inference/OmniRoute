## npm Trusted Publishing (v3.8.51-dən etibarən standart) — sorğu əsasında mərhələli, ehtiyat variant kimi birbaşa

`npm-publish.yml` standart olaraq **npm Trusted Publishing (OIDC)** vasitəsilə dərc edir:
`stage-npm` işi (GitHub tərəfindən host edilir) həmin icra üçün GitHub id-token-i qısamüddətli npm
etimadnaməsi ilə dəyişdirir — repozitoriyanın məxfi məlumatlarında uzunmüddətli npm tokeni yoxdur, 2FA sorğusu yoxdur, mənşə məlumatı əlavə olunur.
2FA-dan yayınan tokenlər dövriyyədən çıxarıldığı üçün bu, npm-in indi icazə verdiyi yan keçmə üsuludur;
WS1.3 təminatını qoruyaraq layihənin v3.8.48-ə qədər malik olduğu tam avtomatik prosesi bərpa edir
(sızdırılmış token təkbaşına dərc edə bilməz — çünki token yoxdur).

**Birdəfəlik quraşdırma (sahib):** npmjs.com → `omniroute` paketi → Settings → _Trusted
Publisher_ → GitHub: sahib `diegosouzapw`, repo `OmniRoute`, iş axını `npm-publish.yml`
(mühit: yoxdur). Bu mövcud olana qədər avtomatik addım `ENEEDAUTH` xətası ilə uğursuz olacaq:
`publish_mode=staged` (aşağıda) və ya `direct` ilə yenidən başladın.

### Mərhələli dərc (sorğu əsasında — `publish_mode=staged`)

npm-publish iş axını artıq birbaşa dərc etmir: paketlənmiş tarball-ı işə salır
(`check:pack-boot`) və sonra `npm stage publish` icra edir — həmin dəqiq baytlar reyestrdə saxlanılır,
lakin sahib təsdiqləyənədək **quraşdırıla bilməz**. İnsan tərəfindən həyata keçirilən 2FA keçidi
sübutdan əvvələ deyil, SONRAYA keçirilib.

**İş axını uğurla tamamlandıqdan sonra sahibin icra edəcəyi proses:**

1. `npm stage list omniroute` — mərhələ ID-sini tapın (iş axınının xülasəsində də göstərilir).
2. Mərhələlənmiş baytları yoxlayın (tövsiyə olunur): `npm stage download <id>`, sonra endirilmiş
   tarball-ı müvəqqəti prefiksə quraşdırın və işə salın (`npm run check:pack-boot` CI daxilində
   eyni paketlə→quraşdır→işə sal hökmünü avtomatlaşdırır).
3. `npm stage approve <id>` — 2FA sorğusu elə dərc prosesinin ÖZÜDÜR. `npm stage reject <id>` ləğv edir.
4. Dərcdən sonrakı qoruma: dərcdən sonrakı yoxlayıcı (v3.8.49 planının WS1.4 hissəsi) dərc edilmiş
   versiyanı təmiz konteynerdə ictimai reyestrdən quraşdırır və işə salır.

**Fövqəladə ehtiyat variant:** `publish_mode=direct` ilə `workflow_dispatch` köhnə
dərhal `npm publish` davranışını bərpa edir (yalnız mərhələləmənin özündə problem olduqda istifadə edin; səbəbini qeyd edin).

**Birdəfəlik sərtləşdirmə (sahib, npmjs.com):** `omniroute` üçün Trusted Publisher-i
yalnız mərhələləmə rejimində konfiqurasiya edin ki, sızdırılmış uzunmüddətli token heç bir yerdən
birbaşa `npm publish` edə bilməsin — CI yalnız mərhələləyə bilər; yalnız sahibin 2FA-sı buraxılışı həyata keçirir.

**Pozulmuş artefakt üzrə təlimat (dəyişməyib):** standart ilkin reaksiya kimi
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` istifadə edin (dəqiqələr çəkir, geri qaytarıla bilər);
`npm unpublish` yalnız 72 saatlıq/asılılığı olmayanlar pəncərəsi daxilində və heç vaxt ilk addım kimi deyil.
Docker: versiya teqini heç vaxt yenidən yazmayın — geriyə qaytarma `latest` teqinin sonuncu işlək digest-ə yönləndirilməsidir.

**Docker Hub `latest` (hər stabil SemVer dərcində tələb olunur):**
`docker-publish` iş axını **həm** `X.Y.Z` teqini, həm də
`should-promote-latest.sh` bunun ən yüksək stabil SemVer olduğu ilə razılaşdıqda `:latest`
teqini **eyni digest** ilə işarələməlidir. İşdən sonra: Hub-dakı `latest` digest-i yeni
SemVer digest-inə bərabər olmalı və `last_updated` yenilənməlidir. Buraxılış qeydlərində
yalnız git-də mövcud olan düzəlişlərdən danışıldığı halda `:latest` teqini köhnə yığmada
saxlamayın. Compose sürətli başlanğıcları `:latest` istifadə edir; GitOps isə `X.Y.Z` versiyasını sabitləməyə davam etməlidir.
[Docker buraxılış kanalları](../guides/DOCKER_GUIDE.md#release-channels) və #10317-yə baxın.

## Təcili Düzəliş üçün Sürətli Xətt (`hotfix` etiketi)

`hotfix` etiketi verilmiş PR ağır CI matrisini (9 hissəli E2E, əhatə dairəsi ratchet-i,
quality-gate, quality-extended) ötürür və sürətli, yüksək siqnallı yoxlamaları saxlayır: build,
unit hissələri, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
və tarball açılış tüstü testi (`check:pack-boot`). Hədəf: ~33 dəqiqə əvəzinə ≤15 dəqiqə ərzində uğurlu nəticə.

**Giriş siyasəti — dördünün də yerinə yetirilməsi tələb olunur (Chromium/VS Code/Node fövqəladə xətləri əsasında modelləşdirilib):**

1. **Ciddilik**: production işləmir — dərc edilmiş artefakt açılış zamanı çökür /
   təhlükəsizlik düzəlişidir / buraxılışın hər bir istifadəçisi təsirlənir. "Vacib" olmaq "işləməmək" demək deyil.
2. **Səlahiyyət**: `hotfix` etiketini yalnız repozitoriya sahibi tətbiq edir. Etiket
   təsdiqin ÖZÜDÜR — kampaniya PR-ında heç vaxt özbaşına istifadə edilməməlidir.
3. **Sübut**: PR təsvirində əvvəlki tam uğurlu ağır işə salınmaya (ötürülən işlərin
   yenidən təsdiqləyəcəyi dəstə), həmçinin düzəlişin əvvəlcə uğursuz, sonra uğurlu olan testinə keçid verilir.
4. **Əhatə dairəsi**: yalnız cherry-pick — minimal düzəliş, refaktorinq və əlavə dəyişikliklər yoxdur.

Ötürülmüş əhatə/ratchet səthi release budağındakı növbəti tam işə salınma ilə yenidən
təsdiqlənir (davamlı uğurlu release) — xətt yoxlamanı deyil, yalnız GÖZLƏMƏNİ ötürür.
Yalnız testlərdən ibarət dəyişikliklər (`tests/` altındakı bütün fayllar, `tests/e2e/` altında heç bir fayl olmamaqla)
heç bir etiket olmadan E2E matrisini avtomatik ötürür.

### Quraşdırma Planı

Repozitoriya üç fərqli çıxış kataloqundan istifadə edir — onları heç vaxt qarışdırmır:

| kataloq   | Məqsəd                                                                   | İzlənildi?           |
| --------- | ------------------------------------------------------------------------ | -------------------- |
| `src/`    | Tətbiq mənbəyi (TypeScript / TSX)                                        | Bəli                 |
| `.build/` | Aralıq — `next build` çıxışı qurun (`distDir`)                           | Xeyr (götürülmüşdür) |
| `dist/`   | Göndərilə bilən npm paketi — `assembleStandalone` tərəfindən yığılmışdır | Xeyr (götürülmüşdür) |

> **Operator qeydi:** uzaq VPS şəkil kataloqu `/usr/lib/node_modules/omniroute/app/` olaraq qalır. Yalnız** in-repo** qurma çıxışı köçürüldü (`app/` → `dist/`). Yerləşdirmə bacarıqları rsync `dist/` məzmununu uzaq `app/` dir — a VPS yolunda dəyişikliklər tələb etmir.

**Tək quruluşlu axın:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

NOT run `npm run build` ardınca ayrıca `npm run build:cli` — üçün `npm run build:release` istifadə edin, hansı ki, bir komandada + sentinel-in təmiz yenidən qurulmasını həyata keçirir.

### PR önizləmə artefaktı (bir dəfə qurun, eyni baytları təşviq edin)

`.github/workflows/preview-artifact.yml` PR-ın son kommitindən bir istehsal tarball-u qurur və
məhz həmin quruluşu doğrulayır (#8084 hissə (a)). Yalnız eyni repozitoriyadan olan PR-lar; heç nə dərc edilmir.

```bash

gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview

gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # önizləmə quraşdırması
```

İcra `npm ci`, `npm run build:release`, `npm run check:pack-artifact` əmrlərini yerinə yetirir, tarball-u
paketləyir, `npm run check:pack-boot` əmrini icra edir (saxta məxfi məlumatlar, müvəqqəti məlumat kataloqu), yenidən paketləyir və
həzm eyni olmadıqda uğursuz olur, sonra `artifact-identity.json` faylını (son kommit SHA-sı, baza
SHA-sı, kilid faylının heşi, platforma, arxitektura, node ABI-si, paketləyici, qurma siyasəti —
`scripts/release/artifact-identity.mjs`) qeydə alır və ayrıca işdə tarball-u attestasiya edir. Önizləməni
təşviq etmək həmin tarball-u quraşdırmaq deməkdir: heç vaxt mənbədən yenidən qurmayın.

### Ayırma (3.9.0, GO-dan sonra)

1. GO qərarı [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) sənədində qeydə alınıb.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` əmri `RESULT: READY` çap edir.
3. Sınaq icrasının çap etdiyi əmrlərlə `origin` üzərində budaqları əl ilə yaradın —
   skript `origin`-ə göndərməkdən imtina edir. Nəzərdən keçirilmiş develop kommitini təkrar istifadə etmək üçün əvvəlcə
   3.9.0 son kommitində fork-unuz üzərində `--execute` sınağını başladın; o, hər iki SHA-nı çap edir və
   eyni kommitlər göndərilə bilər:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. İlk PR birləşdirilməzdən əvvəl `stable/v3` və `develop` budaqlarını qoruyun (qaydalar dəstləri + birləşdirmə növbəsi).
5. Qeyri-aktiv iş axınları budağın mövcudluğuna əsasən işə düşür: `forward-port.yml` (`stable/v3`
   budağına push), `validate-stable-pr.yml` (`stable/v3` budağına PR-lər) və `nightly-v4-build.yml`
   (`develop` budağını qurur). İstifadəyə verməzdən əvvəl `secrets.FORWARD_PORT_TOKEN` repozitoriya məxfisini təyin edin (beləliklə, CI
   forward-port PR-lərində işləyəcək); sahib `vars.NIGHTLY_PUBLISH` repozitoriya
   dəyişənini `true` olaraq təyin edənə və npm Trusted Publishing
   `nightly-v4-build.yml` faylını qəbul edənə qədər gecəlik dərc deaktiv qalır. Kanalın müəyyənləşdirilməsi `scripts/release/dist-tag.mjs` tərəfindən həyata keçirilir; bu,
   `npm-publish.yml` faylının istifadə etdiyi eyni müəyyənləşdiricidir.
6. Kanalları yoxlayın: `npm view omniroute dist-tags --json` əmri `latest` = 3.9.0 göstərir və v4 dərc edilənədək
   `next` / `nightly` mövcud deyil.
7. Lazım gələrsə, geri qaytarma: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   və `npm dist-tag add omniroute@3.8.59 latest`.

## Geri qaytarma

Relizdə kritik problem varsa:

1. `gh release edit vX.Y.Z --prerelease` (ən son reliz kimi işarələnməsini ləğv edir)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (yalnız istifadəçilər tərəfindən hələ mənimsənilməyibsə)
3. Və ya: `release/vX.Y.0` üzərində təcili düzəliş → `vX.Y.(Z+1)` yamaq relizi
4. Dərhal GitHub Discussions və Discord vasitəsilə məlumat verin

## Qəti qaydalar

- Heç vaxt birbaşa `main` budağına commit etməyin
- Heç vaxt `main` və ya `release/*` budaqları üçün `git push --force` istifadə etməyin
- Heç vaxt Husky hook-larını (`--no-verify`) ötürməyin
- Heç vaxt məxfi məlumatları, giriş məlumatlarını və ya `.env` fayllarını commit etməyin
- Örtük ≥60/60/60/60 (ifadələr/sətirlər/funksiyalar/budaqlar) səviyyəsində qalmalıdır
- `src/`, `open-sse/`, `electron/` və ya `bin/` daxilindəki istehsal kodunu dəyişdirərkən həmişə testlər əlavə edin və ya yeniləyin
