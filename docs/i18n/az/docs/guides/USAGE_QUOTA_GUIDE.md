> **Qısa xülasə**: OmniRoute hər sorğunun token istifadəsini izləyir, xərci hesablayır, hər API açarı üzrə kvotanı tətbiq edir və analitik məlumatları idarəetmə panelində göstərir. Bu təlimat bütün bunların necə işlədiyini izah edir.

**Mənbələr:**

- `open-sse/services/usage.ts` (~70KB) — əsas istifadə izləmə xidməti
- `src/lib/usageAnalytics.ts` (~10KB) — idarəetmə paneli üçün aqreqasiya
- `src/lib/db/quotaSnapshots.ts` — tarixi kvota məlumatları
- `src/lib/db/usage*.ts` — istifadə ilə əlaqəli bir neçə DB modulu

## Ümumi baxış

OmniRoute üzərindən keçən hər sorğu aşağıdakı məlumatları əhatə edən **istifadə qeydi** yaradır:

- **İdentifikasiya**: hansı API açarı, provayder, model və kombinasiya
- **Tokenlər**: prompt tokenləri, tamamlama tokenləri, keşlənmiş tokenlər, ümumi say
- **Xərc**: USD məbləği (qiymət məlumatlarından hesablanır)
- **Vaxt göstəriciləri**: gecikmə, başlama/bitmə vaxt nişanları
- **Status**: uğurlu, xəta, sürət məhdudiyyətinə məruz qalmış və s.

Bu qeydlər **analitika** şəklində aqreqasiya olunur, **kvota anlıq görüntüləri** kimi saxlanılır və **hər açar üzrə büdcə limitlərini** tətbiq etmək üçün istifadə edilir.

```
Sorğu ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    analitika  kvota   hesablaşma
                    (panel)    (tətbiq) (ixrac)
```

## Nələr qeydə alınır

`usage.ts` xidməti hər sorğu üçün bir **istifadə hadisəsi** qeydə alır:

| Sahə               | Tip     | Mənbə                                                              |
| ------------------ | ------- | ------------------------------------------------------------------ |
| `id`               | string  | Qeyd zamanı yaradılan UUID                                         |
| `apiKeyId`         | string  | Sorğunu başladan API açarı                                         |
| `provider`         | string  | Provayder ID-si (openai, anthropic və s.)                          |
| `model`            | string  | Model ID-si (gpt-5, claude-opus-4-6 və s.)                         |
| `comboId`          | string? | Kombo vasitəsilə yönləndirilibsə, kombo ID-si                      |
| `promptTokens`     | number  | Yuxarı axın cavabından                                             |
| `completionTokens` | number  | Yuxarı axın cavabından                                             |
| `cachedTokens`     | number  | Keşdən oxunan tokenlər (Anthropic sorğu mətninin keşlənməsi və s.) |
| `totalTokens`      | number  | Sorğu mətni + tamamlanma                                           |
| `costUsd`          | number  | Qiymət məlumatlarından hesablanır                                  |
| `latencyMs`        | number  | Sorğunun başdan sona müddəti                                       |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`         |
| `errorClass`       | string? | Status success deyilsə, xəta sinfi                                 |
| `timestamp`        | string  | ISO 8601 UTC                                                       |
| `metadata`         | object  | Plagin tərəfindən əlavə edilən fərdi məlumatlar                    |

### Tokenlər haradan alınır

Tokenlər **cavab emaledicisində** yuxarı axın provayderinin cavabından çıxarılır:

```ts
// Mənbə: open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

İstifadə məlumatlarını qaytarmayan provayderlər (bəzi veb-kuki provayderləri) üçün OmniRoute `~4 chars per token` evristikasından istifadə edərək tokenləri **təxmin edir** (bax: `open-sse/services/autoCombo/pipelineRouter.ts`).

### Keşlənmiş tokenlər

OmniRoute `cached_tokens` göstəricisini `prompt_tokens` göstəricisindən ayrı izləyir, çünki:

- Anthropic sorğu mətninin keşlənməsi zamanı keşlənmiş tokenlər üçün endirimli tarif tətbiq edir (adi tarifin 10%-i)
- Bəzi provayderlər fərqli qiymətləndirilməli olan `cache_read_input_tokens` göstəricisini qaytarır
- Analitika **keşə düşmə nisbətini** = `cached_tokens / prompt_tokens` göstərə bilər

### Keşə yazma səviyyələrinin diaqnostikası

Analitika idarəetmə panelinin sorğu mətni keşinin vəziyyəti paneli provayder tərəfindən bildirilən
5 dəqiqəlik və 1 saatlıq keşə yazmaları fərqləndirir. Anthropic-in
`usage.cache_creation.ephemeral_5m_input_tokens` və
`usage.cache_creation.ephemeral_1h_input_tokens` göstəriciləri axınlı və
axınsız istifadə məlumatlarının çevrilməsi zamanı qorunur və çağırış jurnalı xülasələri ilə birlikdə saxlanılır. Ümumi
keşə yazma sayı bu kateqoriyalara ikinci dəfə əlavə edilmir.

Yalnız ümumi yazma sayğacı olan çağırışların, o cümlədən köhnə qeydlərin səviyyəsi
naməlumdur. Qismən bölgüdə təyin edilməmiş qalıq naməlum olaraq qalır; etibarsız və ya
ziddiyyətli sayğaclara səssizcə TTL təyin etmək əvəzinə, onlar işarələnir. Sorğu tərəfindəki
TTL markerləri ödənişə cəlb olunan səviyyənin sübutu deyil.

Panelin API-ekvivalent yazma təxmini bütün sorğunu deyil, yalnız
bildirilmiş və qiyməti müəyyən edilmiş səviyyələri əhatə edir. Birbaşa Claude/Anthropic model qiymətləndirməsində 5 dəqiqəlik yazmalar üçün
giriş tarifinin 1.25 misli, 1 saatlıq yazmalar üçün isə giriş tarifinin iki misli istifadə olunur. Çatışmayan
qiymət sıfır deyil, mövcud olmayan qiymət kimi qəbul edilir. Hər yeni çağırış jurnala yazılarkən qiymətlər qeydə alınır;
tarixi qeydlər yenidən qiymətləndirilmir. Buna görə abunə hesabları həmin məbləğ pul xərci və ya abunə
kvotası kimi tutulmadan API-ekvivalent təxminə malik ola bilər.
Mövcud kvota, büdcə və provayderin dəqiq xərc hesablamaları dəyişmir.

Bu diaqnostika mövcud məhdud ölçülü keş vəziyyəti xülasəsindən və çağırış jurnalının
saxlanma mexanizmindən istifadə edir. Sorğunun standart TTL dəyərlərini, yönləndirməni və ya hesab seçimini dəyişmir.
Provayderə göndərilmə nöqtəsində müştərinin tələb etdiyi TTL ilə faktiki çıxış TTL-sinin
qeydə alınması sonraya saxlanılıb; bu panel faktiki çıxış TTL-sini deyil, qəbzlərdəki səviyyələri göstərir.

Reallaşdırma: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` və `open-sse/utils/cacheWriteUsage.ts`.

## Xərcin Hesablanması

Xərclər LiteLLM-dən sinxronlaşdırılan **qiymət məlumatları** əsasında hesablanır (`src/lib/pricingSync.ts`):

| Model             | Giriş $/1M | Çıxış $/1M | Keşlənmiş $/1M |
| ----------------- | ---------- | ---------- | -------------- |
| gpt-5             | $2.50      | $10.00     | —              |
| claude-opus-4-6   | $15.00     | $75.00     | $1.50          |
| claude-sonnet-4-5 | $3.00      | $15.00     | $0.30          |
| gemini-2.5-pro    | $1.25      | $10.00     | —              |

Xərc düsturu (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Keşlənmiş tokenlər niyə sorğudan çıxılır?** Keşlənmiş hissə ayrıca qiymətləndirilir; bütün sorğu üçün giriş qiymətinin tətbiq edilməsi xərcin artıq hesablanmasına səbəb olardı.

### Qiymətlərin Sinxronlaşdırılması

Qiymət məlumatları LiteLLM-dən `/api/pricing/sync` son nöqtəsi vasitəsilə avtomatik sinxronlaşdırılır (istifadəçiyə təqdim olunan mühit dəyişəni ilə deyil, daxili cron tapşırığı ilə başladılır):

```bash
# Əl ilə başladılma
curl -X POST http://localhost:20128/api/pricing/sync
```

Qiymət məlumatları olmayan modellər üçün OmniRoute daxili orta tariflərdən (LiteLLM-in qiymət məlumatlarından əldə edilən) istifadə edərək **xərci təxmini hesablayır**.

## Tarix aralığı üzrə aqreqasiya

`usageAnalytics.ts` modulu xam istifadə məlumatlarından idarəetmə paneli vidcetlərini hesablayır. O, 7 vaxt aralığını dəstəkləyir:

| Aralıq   | Zaman intervalı                          | İstifadə halı                             |
| -------- | ---------------------------------------- | ----------------------------------------- |
| `1d`     | Son 24 saat                              | Saatlıq xərc sıçrayışlarının aşkarlanması |
| `7d`     | Son 7 gün                                | Həftəlik icmal                            |
| `30d`    | Son 30 gün                               | Aylıq hesablaşma                          |
| `90d`    | Son 90 gün                               | Rüblük təhlil                             |
| `ytd`    | Cari ilin 1 yanvarından etibarən         | İllik büdcənin izlənməsi                  |
| `all`    | Bütün dövr                               | Bütün dövr üzrə statistika                |
| `custom` | İstifadəçinin təyin etdiyi başlanğıc/son | Auditlər, birdəfəlik sorğular             |

### Hesablanan idarəetmə paneli vidcetləri

İstənilən tarix aralığı üçün analitika qatı aşağıdakıları hesablayır:

| Vidcet                               | Təsvir                                                     |
| ------------------------------------ | ---------------------------------------------------------- |
| **Xülasə kartları**                  | Ümumi sorğu sayı, ümumi xərc, ümumi token sayı, uğur faizi |
| **Gündəlik tendensiya qrafiki**      | Modellər üzrə yığılmış gündəlik xərc + tokenlər            |
| **Fəaliyyətin istilik xəritəsi**     | Günün saatı × həftənin günü şəbəkəsi, rəng = sorğu sayı    |
| **Model üzrə bölgü**                 | Model üzrə xərclərin dairəvi diaqramı                      |
| **Provayder üzrə bölgü**             | Provayder üzrə sorğuların sütun diaqramı                   |
| **Ən çox xərc yaradan API açarları** | Xərcə görə ilk 10 açarın cədvəli                           |
| **Xətaların təhlili**                | Zaman ərzində xəta faizi, əsas xəta sinifləri              |

### Proqram vasitəsilə giriş

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // istifadə tarixçəsinin qeydləri
  "7d",                 // vaxt aralığı: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // provayder bağlantılarının xəritəsi (connectionId → hesab adı)
  {
    startDate: "2025-01-01",  // istəyə bağlı: "custom" aralığı üçün
    endDate: "2025-06-01",   // istəyə bağlı: "custom" aralığı üçün
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (sent)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Kvotanın tətbiqi

Hər API açarı üzrə kvota iki yerdə tətbiq olunur:

1. **Yumşaq hədd** (`quotaWarnAt`): istifadə həddi aşdıqda idarəetmə panelində xəbərdarlıq
2. **Sərt hədd** (`quotaLimit`): hədd aşıldıqda sorğu HTTP 429 ilə rədd edilir

### Konfiqurasiya

```ts
// Hər API açarı üçün
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — xəbərdarlıq göstər
  quotaLimit: 10_00,    // $10.00 — tam dayandır
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Tətbiq axını

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### Kvotanın ani görüntüləri

`quotaSnapshots` cədvəli tendensiyaların təhlili üçün **kvotanın tarixi vəziyyətini** saxlayır:

| Sahə | Təsvir |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | İzlənən açar |
| `window` | "gün" | "həftə" | "ay" |
| `used` | Bu intervalda istifadə edilmiş xərc (sent) |
| `limit` | Hədd (sent) |
| `resetAt` | İntervalın sıfırlandığı vaxt |
| `createdAt` | Ani görüntünün qeydə alındığı vaxt |

Ani görüntülər xərci > 0 olan **hər sorğuda** qeydə alınır və aşağıdakılar üçün istifadə olunur:

- İdarəetmə panelində kvotanın gedişat zolağını göstərmək
- 30 günlük kvota tendensiyası qrafiklərini göstərmək
- İstifadə həddə yaxınlaşdıqda xəbərdarlıqları işə salmaq

## REST API

### İstifadə qeydlərinin siyahısını əldə edin

```bash
GET /api/usage?range=7d&limit=100
GET /api/usage?apiKeyId=key-123&range=30d

```

### İstifadə analitikasını sorğulayın

İstifadə məlumatlarına birbaşa REST ixrac son nöqtələri ilə deyil, idarəetmə paneli və ya MCP alətləri vasitəsilə daxil olunur. Mövcud analitika imkanları:

- **`/api/usage/analytics`** — ümumiləşdirilmiş istifadə göstəriciləri (model, provayder, açar üzrə qruplaşdırma)
- **`/api/usage/quota`** — hər API açarı üzrə cari kvota vəziyyəti
- **`/api/usage/history`** — sorğu tarixçəsi jurnalları

| `omniroute_cost_report` | Verilmiş dövr üçün hər açar üzrə xərc hesabatı yaradır |
| `omniroute_check_quota` | API açarı üçün cari kvota vəziyyətini qaytarır         |

Agent çağırışı nümunəsi:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## Saxlama və təmizləmə

İstifadə məlumatlarının həcmi hər sorğu üçün ~1-10KB artır. Böyük miqyasda bu, əhəmiyyətli həcmə çata bilər.

### Saxlama parametrləri

İstifadə tarixçəsinin saxlanması istifadəçi interfeysindəki Verilənlər bazası parametrləri və ya `/api/settings/database` vasitəsilə tənzimlənir.

Standart olaraq, istifadə tarixçəsi **90 gün** saxlanılır.

### Təmizləmə

Köhnə qeydlər `src/lib/db/cleanup.ts` tərəfindən təmizlənir:

- Arxa planda işləyən cron prosesi tərəfindən başladılır
- `usage_history` cədvəlindən yaşı konfiqurasiya edilmiş `usageHistory` saxlama müddətini keçən qeydləri silir

### Saxlama həcminin hesablanması

| Sorğu tezliyi     | 30 günlük saxlama həcmi | 90 günlük saxlama həcmi |
| ----------------- | ----------------------- | ----------------------- |
| 100 sorğu/gün     | ~3MB                    | ~9MB                    |
| 1,000 sorğu/gün   | ~30MB                   | ~90MB                   |
| 10,000 sorğu/gün  | ~300MB                  | ~900MB                  |
| 100,000 sorğu/gün | ~3GB                    | ~9GB                    |

Çox yüksək trafik zamanı aşağıdakıları nəzərdən keçirin:

- Verilənlər bazası parametrləri vasitəsilə saxlama müddətini azaltmaq
- Xam qeydlər əvəzinə `aggregated_metrics` istifadə etmək (yalnız analitika üçün)

## Xərclərin optimallaşdırılması üçün məsləhətlər

### 1. Düzgün modeldən istifadə edin

```bash
# Sürətli cavab — ucuz və sürətli modeldən istifadə edin
curl -d '{"model":"auto/fast","messages":[...]}'

# Mürəkkəb tapşırıq — keyfiyyətli modeldən istifadə edin
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Keşləməni aktivləşdirin

Anthropic prompt keşləməsi **təkrarlanan kontekstdə 90% qənaət** təmin edir:

```ts
// Keşləmə avtomatikdir — sadəcə eyni böyük sistem promptunu daxil edin
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Avtomatik keşlənəcək
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Sıxılmadan istifadə edin

RTK + Caveman sıxılması **alətlərdən intensiv istifadə olunan sessiyalarda 15-95% qənaət** təmin edir:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Hər açar üçün kvota təyin edin

Nəzarətsiz xərclərin qarşısını almaq üçün həmişə `quotaLimit` təyin edin:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Ayda $10 limiti
```

### 5. Ən çox istifadə edənləri yoxlayın

API açarına görə qruplaşdırmaq və xərcə görə sıralamaq üçün idarəetmə panelindən və ya **`/api/usage/analytics`** ünvanından istifadə edin:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Problemlərin aradan qaldırılması

### "Xərc gözləniləndən yüksəkdir"

1. **`/api/usage/analytics?groupBy=model`** ünvanını yoxlayın — bahalı modeli tapın
2. **`/api/usage/analytics?groupBy=apiKey`** ünvanını yoxlayın — ən çox istifadə edəni tapın
3. Qiymət məlumatlarının aktual olduğunu yoxlayın: `POST /api/pricing/sync`

### "Qeydlər çatışmır"

- İdarəetmə paneli → Verilənlər bazası → Təmizləmə bölməsində verilənlər bazasının saxlama parametrlərini yoxlayın — köhnə qeydlər dövri təmizləmə tapşırığı (`src/lib/db/cleanup.ts`) tərəfindən silinir
- `src/lib/db/usage*.ts` daxilində xətaları yoxlayın — verilənlər bazasına yazma xətaları jurnala yazılır, lakin istifadəçiyə göstərilmir
- Sorğunun həqiqətən `chatCore` funksiyasına çatdığını yoxlayın — kombo marşrutlaşdırmasını yoxlayın

### "Kvota tətbiq edilmir"

- Açarın `quotaLimit` parametrini yoxlayın
- `quotaWindow` parametrinin düzgün təyin olunduğunu yoxlayın
- `quotaSnapshots` qeydlərini axtarın — onlar hər sorğuda yaradılmalıdır
