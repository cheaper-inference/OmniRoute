## Ümumi baxış

Bütün OmniRoute idarəetmə API marşrutları üç qoruma səviyyəsindən birinə aid edilir. Təsnifat statikdir, `src/server/authz/routeGuard.ts` faylında müəyyən edilir və hər hansı digər autentifikasiya şaxəsi işə düşməzdən əvvəl qiymətləndirilir.

## Səviyyələr

### Səviyyə 1 — LOCAL_ONLY

**Tətbiq edən:** `isLocalOnlyPath(path)` → loopback host yoxlaması
**Yan keçmə:** Varsayılan olaraq yoxdur.
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` daxilindəki yollar üçün məhdud istisna — sorğu `manage` əhatə dairəsinə malik etibarlı API açarı daşıdıqda (bax: [Manage-scope istisnası](#manage-scope-carve-out)).

Bu marşrutlar uşaq proseslər yaradır və ya icra vaxtı kodu işlədir. Onları qeyri-loopback trafikinə açmaq, etibarlı JWT əldə etmiş hücumçuya (məsələn, Cloudflared/Ngrok tuneli vasitəsilə) proses yaratmağa başlamağa imkan verərdi — bu, məlum bir CVE sinfidir ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj nədir (hücum sinfi):** idarəetmə/agent serveri alt proses işə salan bir endpoint açır (`npm install`, `node`, brauzer, proksi, `git`, `tar`, …). Əgər bu endpoint hostdan kənardan əlçatandırsa — operator OmniRoute-u nginx/Cloudflare/Tailscale tunelinin arxasına qoyduğu və JWT sızdığı və ya autentifikasiya səhv konfiqurasiya edildiyi üçün — hücumçu "API çağırışı"nı "hostda əmr icrası"na çevirir (uzaqdan kod icrası). OmniRoute bunu, proses yarada bilən hər marşrutda **hər hansı autentifikasiya yoxlamasından əvvəl, şərtsiz olaraq loopback host yoxlaması** tətbiq etməklə bağlayır: tunel üzərindən sızmış token belə proses yaratma nöqtəsinə çata bilmir.

**Tam LOCAL_ONLY dəsti.** Səlahiyyətli mənbə
`src/server/authz/routeGuard.ts` faylındakı
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`-dir; aşağıdakı cədvəl cari vəziyyəti əks etdirir.
`check-route-guard-membership` qapısı proses yarada bilən prefikslər altındakı hər bir `route.ts` faylını sadalayır və hər hansı biri local-only kimi təsnif edilməyibsə, CI-ni uğursuz edir.

#### Manage-scope istisnası

LOCAL_ONLY yollarının bir alt dəstinə qeyri-loopback ünvandan yalnız və yalnız
sorğunun metadata-sında `manage` scope-u (və ya `admin`) olan bir
`Authorization: Bearer <api-key>` daşıdığı halda daxil olmaq OLAR. İstisna
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` vasitəsilə hər yol üzrə açıq şəkildə
idarə olunur ki, hər hansı yeni LOCAL_ONLY yolu üçün standart davranış
ciddi-loopback olaraq qalsın. Autentifikasiyasız sorğular və manage-olmayan
açarlarla sorğular yenə də `403 LOCAL_ONLY` ilə rədd edilir.

Bu gün keçid verilə bilən yeganə prefiks `/api/mcp/`-dir. `/api/cli-tools/runtime/`
və `/api/services/` qəsdən istisna edilib, çünki onlar ixtiyari alt proseslər
(`npm install`, `node`) işə sala bilər — bu da məhz LOCAL_ONLY səviyyəsinin
qarşısını almaq üçün mövcud olduğu CVE sinfidir.

**#7895 — `mcp:connect` dar scope-u:** `/api/mcp/` istisnası HƏMÇİNİN dar
`mcp:connect` scope-u daşıyan Bearer açarını qəbul edir
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), bu isə
`src/server/authz/policies/management.ts`-dəki `hasMcpConnectOrManageScope()`
vasitəsilə yoxlanılır. Bu, YALNIZ `/api/mcp/` ilə məhdudlaşır — `mcp:connect`
başqa heç bir idarəetmə marşrutunda (gələcəkdə əlavə edilsə belə, hər hansı digər
LOCAL_ONLY keçid prefiksi daxil olmaqla) heç nə vermir və qəsdən
`MANAGEMENT_API_KEY_SCOPES`-dən kənarda saxlanılıb. `manage`/`admin` daşıyan
açar istisnadan əvvəlki kimi keçir; `mcp:connect` geniş idarəetmə girişinə ehtiyacı
olmayan uzaq yalnız-MCP çağıranları üçün daha aşağı səlahiyyətli alternativdir.

| Sorğu                                                 | Yol                        | Nəticə                 |
| ----------------------------------------------------- | -------------------------- | ---------------------- |
| Qeyri-loopback, Bearer yoxdur                         | `/api/mcp/*`               | 403 LOCAL_ONLY         |
| Qeyri-loopback, `manage` scope-lu Bearer              | `/api/mcp/*`               | İcazə ver              |
| Qeyri-loopback, `mcp:connect` scope-lu Bearer         | `/api/mcp/*`               | İcazə ver              |
| Qeyri-loopback, `manage`/`mcp:connect` olmayan Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY         |
| Qeyri-loopback, `mcp:connect` scope-lu Bearer         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY         |
| Qeyri-loopback, `manage` scope-lu Bearer              | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY         |
| Loopback, istənilən/Bearer yoxdur                     | istənilən LOCAL_ONLY       | İcazə ver (qapı keçir) |

#### Operator təlimatları və audit

OmniRoute-u tərs proksi və ya tunel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) arxasında işlədirsinizsə, loopback yoxlaması yuxarıdakı
spawn qabiliyyətli marşrutları yenə də qoruyur — müştəri ünvanı qeyri-loopback
olan sorğu **auth işləməzdən əvvəl** `403 LOCAL_ONLY` ilə rədd edilir, buna görə də
sızmış JWT spawn-a çata bilməz. Operatorun iki öhdəliyi qalır:

- **403-ü müştəri IP-sini loopback kimi saxtalaşdırmaqla "düzəltməyin".**
  `X-Forwarded-For: 127.0.0.1` təyin etmək və ya mənbə ünvanını loopback-ə
  yenidən yazan bir proksi, məhz bu səviyyənin bağladığı RCE sinfini yenidən
  açır. İdarə panelini/API-ni proksi vasitəsilə açın — spawn qabiliyyətli
  marşrutları heç vaxt yox.
- **Manage-scope keçidini minimal saxlayın.** Yalnız `/api/mcp/` keçid edilə
  bilər və yalnız `manage` əhatəli API açarı ilə. `SPAWN_CAPABLE_PREFIXES`
  heç vaxt keçid siyahısına əlavə edilə bilməz — zod sxemi onları rədd edir və
  `isLocalOnlyBypassableByManageScope` iş vaxtında onları qadağan edir
  (dərin müdafiə), idarə panelinin "keçid edilə bilməz" ilə nəzərdə tutduğu
  məhz budur. Eyni qadağa siyahısı həmçinin spawn etməyən, lakin uzaqdan da
  heç vaxt əlçatan olmamalı olan bir neçə LOCAL_ONLY marşrutunu saxlayır —
  `/api/oauth/kiro/auto-import` (host-yerli Kiro etimadnamə fayllarını oxuyur),
  `/api/discovery/` və `/api/issue-agent/`. Runtime snapshot yükləyicisi də
  belə qeydləri saxlanılmış parametrlər sətrindən atır və köhnə JSON idxalı
  (`/api/settings/import-json`) heç vaxt keçid açarlarını yazmır. Hər
  `LOCAL_ONLY_API_PREFIXES` qeydi ya qadağa siyahısında olmalı, ya da keçidə
  uyğun kimi nəzərdən keçirilməlidir (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`).
  `/api/providers/` altındakı dinamik seqmentli və statik yollu spawn
  qabiliyyətli marşrutlar (məs. `/login`, `/refresh-cursor`) düz
  `SPAWN_CAPABLE_PREFIXES` massivi ilə yox,
  `src/shared/constants/spawnCapablePrefixes.ts`-dəki regex-əsaslı
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` müşayiətçisi
  ilə əhatə olunur — düz massiv onları tutmaq üçün bütün `/api/providers/`
  prefiksini əhatə etməli olardı ki, bu da uzaq idarə panellərinin provayder
  CRUD üçün qanuni istifadə etdiyi marşrut ağacını həddindən artıq
  genişləndirərdi.

**Girişin auditı** — hostdan kənar heç nənin bu marşrutlara çatmadığını
yoxlamaq üçün:

- `/dashboard/settings/security`-dəki **Authorization Inventory** bölməsini açın:
  o, canlı LOCAL_ONLY prefiks siyahısını, hansı prefikslərin keçid edilə
  biləcəyini və tərtib zamanı spawn qabiliyyətli ("keçid edilə bilməz")
  dəstini göstərir.
- Geriyə proksi / giriş jurnallarınızda yuxarıdakı prefiksləri qeyri-loopback
  müştəri ünvanı ilə birlikdə axtarın. `403 LOCAL_ONLY` əvəzinə `200` qaytaran
  istənilən belə nəticə proksinin real müştəri IP-sini maskaladığını bildirir —
  proksini düzəldin.
- OmniRoute-un jurnallarında bu yollardan biri üçün `403 LOCAL_ONLY` qeydi
  qoruyucunun nəzərdə tutulduğu kimi işlədiyini göstərir, yatırılması lazım
  olan bir xəta deyil.

#### Zəng yerində yoxlama qapısı olan uzaqdan əlçatan marşrutlar

Bəzi marşrutlar uzaq idarə panelindən əlçatan qalmalı, lakin yerli çağıranlar
üçün host tərəfində yoxlama (`which <binary>`, `<binary> --version`,
`tailscale status --json`) icra etməlidir. Onlar `GET` üçün LOCAL_ONLY deyil;
əvəzində işləyici etibarlı tərəfin qərarını `getRequestPeerLocality()`
(`src/shared/utils/apiAuth.ts`) ilə oxuyur və yoxlamanı yalnız `loopback` /
`lan` çağıranları üçün icra edir. `remote` çağıranı spawn etməyən mənbələrdən
(saxlanılmış vəziyyət, parametrlər, fs yoxlamaları) qurulan eyni cavab formasını
alır, `probed: false` kimi işarələnmiş halda.

| Marşrut                                                          | Uzaq çağıranlar üçün ötürülən yoxlama                                  |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI runtime yoxlaması (`allowLocalRuntimeProbe`) və CLI-fallback spawn |
| `GET /api/headroom/status`                                       | `which headroom` və python `--version` yoxlamaları                     |

Hostu yoxlayan yeni bir oxuma marşrutu eyni nümunəyə əməl edir və ya birbaşa
LOCAL_ONLY kimi təsnif edilir.

### Səviyyə 2 — ALWAYS_PROTECTED

parol açıqlanmasını maskaladı; verilmə hələ də fail-open səviyyəsində idi (GHSA-7pq4-8pvv-rx7r).

#### Etimadnamə ixracı və bərpası yalnız operator üçündür

Yuxarıdakı səviyyə yalnız _hansısa_ etimadnamənin tələb olunub-olunmadığına qərar verir. Saxlanmış
etimadnamələri yükləyən marşrutlar handler-də ikinci yoxlama əlavə edir:
`GET /api/settings/export-json` (deşifrə edilmiş provayder bağlantıları və xam API açarları),
`GET /api/db-backups/export` (SQLite faylı) və `GET /api/db-backups/exportAll` (tam arxiv)
`requireOperatorCredential()` funksiyasını çağırır (`src/lib/api/operatorCredential.ts`). O,
dashboard sessiyasını, yerli CLI subyektini və ya girişi söndürülmüş instansiyanı qəbul edir və
istənilən əhatə dairəsinə malik API açarlarına (`manage` və `admin` daxil olmaqla), həmçinin `oma_`
giriş tokenlərinə `403` ilə cavab verir. Dağıdıcı əks variantlar eyni sərhədi saxlayır:
`POST /api/db-backups/import` (yüklənmiş `.sqlite`, `dryRun=true` daxil olmaqla),
`POST /api/db-backups` (saxlanmış ehtiyat nüsxəni id ilə bərpa etmək) və
`POST /api/settings/import-json` (köhnə JSON bərpası) canlı verilənlər bazasını və ya bütün
parametrlər/bağlantılar/API açarı dəstini əvəz edir, buna görə maşın etimadnaməsi də onları işə
sala bilməz. Bərpa nöqtələrinin məhv edilməsi eyni sərhədi saxlayır: `DELETE /api/db-backups`
(təmizləmə — son N-i saxla / D gündən köhnələri sil) və `PATCH /api/db-backups` (saxlanma
parametrləri), çünki davamlı saxlanma məhz hər avtomatik ehtiyat nüsxədən sonra
`cleanupDbBackups()` funksiyasının tətbiq etdiyi şeydir (`src/lib/db/backup.ts`), buna görə
`keepLatest: 1` dəyərini saxlaya bilən maşın etimadnaməsi növbəti snapshot-da hər şeyi budayardı.
Ehtiyat nüsxələrin siyahıya alınması və yaradılması (`GET`/`PUT /api/db-backups`) adi idarəetmə
autentifikasiyasını saxlayır. Sync token verilməsi (`POST /api/sync/tokens`) eyni köməkçidən,
üstəlik etibarlı loopback daxili xidmət tokenindən istifadə edir.

### Yeni quraşdırma bootstrap-i yalnız loopback üçündür — real peer ilə, `Host` ilə yox

İdarəetmə parolu konfiqurasiya edilmədikdə (və `INITIAL_PASSWORD` olmadıqda),
`src/shared/utils/apiAuth.ts` faylındakı `isAuthRequired()` anonim bootstrap-i **yalnız loopback
peer-ləri üçün** açıq saxlayır. Loopback etibarlı peer siqnallarından, bu ardıcıllıqla müəyyən
edilir: token-möhürlü real TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, siyasətin gördüyü),
pipeline-ın öz `AUTHZ_HEADER_PEER_LOCALITY` qərarı (marşrut handler-lərinin gördüyü, yalnız
`OMNIROUTE_PEER_STAMP_TOKEN` təyin edilmişkən etibarlıdır) və ya birbaşa çağıranlar üçün real
socket peer. `Host` / `nextUrl.hostname` heç vaxt nəzərə alınmır və ilk parol yazısı
(`POST /api/settings/require-login`) hər şəbəkə peer-inə açıq olmaq əvəzinə eyni məhdudiyyət
altındadır (GHSA-7pq4-8pvv-rx7r). `managementPolicy` öz `peerContext` qərarını açıq şəkildə aşağı
ötürür, buna görə ORİJİNAL (strip-dən əvvəlki) sorğunun başlıqları bunu heç vaxt müəyyən etmir.

### Səviyyə 3 — İDARƏETMƏ (standart)

Bütün digər idarəetmə marşrutları. `requireLogin=false` konfiqurasiya edilmədikcə autentifikasiya
tələb olunur. CLI tokenləri bu marşrutlar üçün autentifikasiya edə bilər (loopback + etibarlı HMAC).

## Qiymətləndirmə ardıcıllığı

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → davam et
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → icazə ver (management_key)
     → əks halda                                 → rədd et 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → icazə ver (system)
  3. hasValidCliToken(headers)?
     → icazə ver (cli) [loopback + timingSafeEqual HMAC yoxlaması]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → icazə ver (dashboard_session)
     → keçilməsi mümkün olmayan yolda manage-scope Bearer?
        → icazə ver (management_key)
     → rədd et 401/403
  5. requireLogin=false?
     → icazə ver (anonymous)
```

1-ci addımın manage-scope şaxəsi LOCAL_ONLY marşrutunu təmin edə bilən yeganə autentifikasiya edilmiş yoldur; auth-backend nasazlığı halında 503 (403 deyil) qaytarılır ki, vaxtı bitmiş DB səssizcə "rədd et" rejiminə keçməsin.
