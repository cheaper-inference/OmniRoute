Pomocou tejto príručky vyberte najmenší spoľahlivý vývojový cyklus pre pull request. Nenahrádza
dokumenty o architektúre a zabezpečení konkrétnych oblastí, na ktoré sa odkazuje nižšie; prepája každý bežný
typ zmeny s jeho kontraktmi, cielenými kontrolami a pokrytím v CI.

## Postup, ktorým prechádza každá zmena

1. **Pred úpravami vyberte základnú vetvu.** Nájdite najvyššiu aktívnu vetvu `release/v*` a vytvorte vetvu z
   jej najnovšieho commitu. Zacieľte na túto vetvu, nie na `main`. Ak je aktívne zmrazenie vydania, necielite na zmrazenú
   vetvu; použite nasledujúci aktívny cyklus opísaný v dokumente
   [Model vetvenia a vydávania](BRANCHING_MODEL.md).
2. **Pomenujte kontrakty.** Identifikujte každý katalóg, schému, generovaný artefakt, verejné API alebo používateľské
   rozhranie, ktoré zmena ovplyvňuje. Tabuľka nižšie uvádza minimálnu počiatočnú množinu.
3. **Napíšte alebo aktualizujte cielené testy.** Zmeny produkčného kódu v `src/`, `open-sse/`, `electron/` alebo
   `bin/` vyžadujú automatizovaný test v tom istom PR. Spustite najmenšie testovacie súbory, ktoré preukazujú
   dané správanie, a potom uvedené cielené kontroly.
4. **Nechajte CI spustiť širokú maticu.** Kompletné segmenty jednotkových testov, Vitest, kontrola pokrytia a
   produkčné zostavenie sa spúšťajú v PR. Širokú sadu spúšťajte lokálne iba vtedy, keď cielené zlyhanie poukazuje na
   širší dosah alebo keď zmena zasahuje viacero podsystémov.
5. **Pred kontrolou zosúlaďte zmeny.** Stiahnite aktívnu základnú vetvu, skontrolujte jej nové commity a rozdiely vašej vetvy
   voči nej a potom vykonajte rebase alebo zlúčenie základnej vetvy podľa pracovného postupu pre prispievateľov. Konflikty v generovaných súboroch
   a katalógoch vyriešte v ich zdroji, znova ich vygenerujte, opätovne spustite cielený cyklus a potvrďte, že
   PR stále cieli na aktívnu vetvu vydania.
6. **Zaznamenajte dôkazy.** V šablóne PR uveďte spustené príkazy, každý pridaný alebo zmenený testovací súbor,
   migrácie alebo príznaky funkcií a všetky validácie vykonávané iba v CI, ktoré ešte čakajú na spustenie.

## Odporúčané postupy podľa typu zmeny

Príkazy nižšie predstavujú minimálne cielené kontroly, nie povolenie vynechať test, ktorý priamo pokrýva
správanie, ktoré ste zmenili.

### Poskytovateľ

**Kontrakty**

- Definícia poskytovateľa v `src/shared/constants/providers/` a jej zostavenie v
  `src/shared/constants/providers.ts`.
- Modely a možnosti v `open-sse/config/providerRegistry.ts` alebo v jeho vyčlenených súboroch registra.
- Výber vykonávacieho modulu/prekladača, konfigurácia OAuth alebo API kľúča, prostriedky ovládacieho panela a generovaná
  referencia poskytovateľa, ak je to relevantné.
- Verejné prihlasovacie údaje musia používať `resolvePublicCred()`; chybové odpovede musia používať zdieľané pomocné funkcie
  na sanitizáciu chýb. Pozrite si `docs/security/PUBLIC_CREDS.md` (git; nekompiluje sa do `/docs`) a
  [Sanitizácia chýb](../security/ERROR_SANITIZATION.md).

**Cielený cyklus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # keď sa katalóg zmení; commitnite vygenerovaný rozdiel
npm run lint
```

Otestujte tiež každú ovplyvnenú skupinu požiadaviek: chat, Responses, obrázky, embeddings, zvuk alebo video.
Vygenerované rozdiely katalógu a referenčných výstupov kontrolujte ako zmeny kontraktov; neprijímajte ich bez overenia.

### Smerovanie

**Kontrakty**

- Verejné hodnoty stratégií a metadáta používateľského rozhrania v `src/shared/constants/routingStrategies.ts`.
- Distribúcia a poradie v `open-sse/services/combo.ts` a `open-sse/services/combo/`.
- Schémy kombinácií, perzistencia, stav odolnosti, možnosti modelov a ovládacie prvky API/používateľského rozhrania.
- [Modul automatických kombinácií](../routing/AUTO-COMBO.md) a dokumentácia odolnosti, keď sa mení správanie.

**Cielený cyklus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # zmeny stratégie alebo distribúcie
npm run check:known-symbols      # zmeny registrácie stratégie
npm run lint
```

Lokálne používajte deterministické testy so simulovanými nadradenými službami. Živé rýchle testy kombinácií vyžadujú prihlasovacie údaje a sú
manuálne; nenahrádzajú CI.

### UI / UX

**Kontrakty**

- Hranice trás/stránok Next.js a zdieľaných komponentov v `src/app/` a
  `src/shared/components/`.
- Tvary odpovedí API, stavy načítavania/prázdneho obsahu/chýb, správanie klávesnice a čítačky obrazovky,
  responzívne rozloženie, motívy a rozšírenie lokalizácií.
- Anglické zdrojové reťazce používateľského rozhrania v `src/i18n/messages/en.json`; nový text zobrazovaný používateľom nevkladajte priamo do kódu.

**Cielený cyklus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Pri zmenách interakcie alebo vzhľadu spustite aplikáciu a skontrolujte úzke aj široké zobrazenie. CI spúšťa
produkčné zostavenie a širšie sady testov; vizuálne správanie stále vyžaduje cielený test komponentu, Playwright
alebo zdokumentovanú manuálnu kontrolu primeranú danej zmene.

### i18n

**Kontrakty**

- `src/i18n/messages/en.json` je zdrojom používateľského rozhrania; `config/i18n.json` je zdrojom lokalizácií.
- Katalógy CLI sa nachádzajú samostatne v `bin/cli/locales/`.
- Zástupné symboly a značky ICU zachovajte presne. Neprekladajte názvy produktov/poskytovateľov/modelov,
  názvy protokolov a hlavičiek, príkazy, identifikátory kódu/JSON, adresy URL, premenné prostredia ani
  chránené výrazy, ako sú `OmniRoute`, `OAuth`, `MCP` a `A2A`. Aktuálny zdrojový zoznam je
  `scripts/i18n/glossary/protected-terms.json`.

**Cielený cyklus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # keď sa menia reťazce/katalógy CLI
npm run lint
```

Toto je usmernenie pre existujúci systém, nie výzva na rozširovanie jeho nástrojov alebo modelu kľúčov.
Kým sa navrhuje náhradný systém, udržiavajte opravy i18n presne zacielené. Nespúšťajte prekladové
príkazy, ktoré volajú externé služby, pokiaľ úloha výslovne nevyžaduje generované preklady a
neskontrolovali ste výsledný rozdiel.

### CLI

**Kontrakty**

- Verejné príkazy a príznaky v `bin/cli/`, generované príkazy API, návratové kódy, stdout/stderr a
  štruktúry výstupu JSON, správanie konfigurácie/prostredia a súbory v balíku.
- Reťazce CLI určené používateľom musia používať vrstvu i18n CLI a katalógy `en`/`pt-BR` musia zostať zosúladené.
- Zachovajte Node ako podporované behové prostredie a zmluvu publikovaného binárneho súboru.

**Cielený cyklus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # zmeny generovaného/zbaleného CLI
npm run check:pack-policy     # zmeny verejného rozhrania balíka
npm run lint
```

Ak správanie závisí od syntaktickej analýzy, súborov alebo návratového
stavu, použite presný príkaz v dočasnom dátovom adresári. CI vykonáva širšie kontroly artefaktov balíka a ekosystému.

### Databáza

**Zmluvy**

- Doménové moduly v `src/lib/db/`; importujte konkrétne moduly priamo (stará vrstva opätovného exportu `localDb.ts` bola odstránená).
- Číslované, idempotentné migrácie SQL v `src/lib/db/migrations/`, bezpečnosť transakcií, správanie pri
  inovácii, indexy a každý volajúci ovplyvnený schémou.
- Trasy a obslužné rutiny nikdy priamo nevykonávajú nespracované SQL.

**Cielený cyklus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Pri pridávaní migrácie otestujte novú databázu aj inováciu z predchádzajúcej schémy. Databázové testy
musia zatvoriť prostriedky a počas čistenia zavolať `resetDbInstance()`. Príkaz `npm run test:bun:db` spúšťajte iba vtedy, keď
sa zmení nezaručená cesta adaptéra Bun; Node zostáva smerodajný.

### Zostavenie / nasadenie

**Zmluvy**

- Koreňové manifesty, manifesty pracovných priestorov a uzamykací súbor, `scripts/build/`, samostatné zostavenie Next.js, obsah balíka `dist/`,
  metadáta platformy Electron, pracovné postupy CI a kontrolné prvky nasadenia.
- Podporované rozsahy Node a používanie Bun povolené zoznamom v `CLAUDE.md` musia zostať zachované.
- Artefakty zostavenia zostávajú nesledované; uplatňujú sa zásady pre závislosti, licencie, pracovné postupy a balíky.

**Cielený cyklus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # zmeny závislostí alebo uzamykacieho súboru
npm run check:pack-policy      # zmeny verejného rozhrania publikovaného balíka
npm run lint
```

Príkaz `npm run build` používajte lokálne iba vtedy, keď zmena ovplyvňuje kompiláciu, samostatné zostavenie, prostriedky
alebo zbaľovanie pre behové prostredie. Príkaz `npm run build:release` používajte iba na overenie vydania/nasadenia. Zostavenie v CI je
konečným signálom pre viaceré platformy; zmeny Electron špecifické pre platformu vyžadujú zodpovedajúce cielené zostavenie
alebo dôkaz zo základného testu.

## Vývojárske skripty pre zdieľaný počítač

Dva pomocné skripty v `scripts/dev/` implementujú lokálny cyklus na vývojovom počítači, na ktorom sú aktívne ďalšie relácie:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # súbory z merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # presne tieto súbory
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # izolovaný pracovný strom, bezpečný pri paralelnom použití
```

- `typecheck-touched.sh` typovo kontroluje iba zmenené súbory `.ts/.tsx` prostredníctvom dočasného
  súboru `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) s pamäťou heap obmedzenou na 6 GB, takže nahrádza projektový príkaz `tsc -p tsconfig.json`,
  ktorý na zaťaženom počítači zlyháva pre nedostatok pamäte. Vypíše chyby v zmenených súboroch spolu s jedným súhrnným riadkom a skončí
  s kódom `1` pri chybách v zmenených súboroch, `2`, ak sú jediné chyby v importovaných súboroch alebo tsc zlyhal
  bez diagnostiky (prečítajte si pomenovaný protokol v `_artifacts/typecheck-touched/`), a `0`, ak
  sa nenašli žiadne chyby. Dočasný tsconfig sa vždy odstráni; nikdy ho necommitujte.
- `new-worktree.sh` serializuje súbežné spustenia pomocou `<git-common-dir>/omniroute-new-worktree.lock`
  (predvolene čaká až 600 s a zobrazuje pritom správu; hlavička skriptu dokumentuje spôsob
  prepísania tejto hodnoty) a vráti
  späť ním vytvorenú vetvu, keď `git worktree add` zlyhá pred vytvorením pracovného stromu, takže opakovaný pokus
  nevyžaduje manuálne spustenie `git branch -D`. Pevne prepojený adresár `node_modules` a kópia `.husky/_` zostávajú nezmenené.

## Lokálny cyklus kandidáta

Testy zdrojového kódu nedokážu preukázať, že sa zostavený artefakt spustí: zoznamy balených súborov, orezané závislosti
a natívne binárne súbory zlyhajú až po nainštalovaní a spustení tarballu. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) predstavuje lokálnu časť postupu zostaviť raz / overiť / nasadiť z
RFC #8084: zostaví jedného kandidáta, overí presne tento artefakt, nasadí ho premenovaním
adresárov a vráti zmenu späť, keď nasadený slot neprejde kontrolou stavu.

```bash
npm run dev:candidate -- run --dry-run --json  # vypíše plán bez vykonania zmien
npm run dev:candidate -- run                   # zostavenie + overenie + nasadenie, automatické vrátenie pri zlyhaní
npm run dev:candidate -- build                 # npm pack + inštalácia do _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # spustenie na voľnom porte, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # výmena current a previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # opätovné použitie tarballu zostaveného inde (CI)
```

- **Zostaviť raz.** `build` zabalí aktuálny strom (vyžaduje `dist/server.js`, preto najskôr spustite
  `npm run build:release`) alebo skopíruje `--from-tarball` a potom nainštaluje tarball do
  izolovaného prefixu npm, pretože tarball neobsahuje `node_modules`. Identifikátorom je skrátený hash `HEAD`
  sha (`-dirty`, keď strom obsahuje lokálne zmeny) alebo `tgz-<sha256>` pre tarball. Čistý identifikátor, ktorý
  už bol zostavený, sa namiesto opätovného zostavenia znovu použije; na jeho opätovné zostavenie použite `--force`.
- **Overujte balík, nie zdrojový kód.** `validate` spustí nainštalované CLI
  (`serve --port <free port>`) s novým `DATA_DIR=<candidate>/data`, falošnými tajnými údajmi a odstránenými
  premennými `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` a `INITIAL_PASSWORD` z prostredia
  operátora, čím overí režim spätnej slučky bez kľúča čerstvej inštalácie. Čaká, kým
  `GET /api/health` vráti 200, vyžaduje, aby `GET /v1/models` vrátil 200, zastaví skupinu procesov
  a zaznamená výsledok do `validation.json` spolu s hashom tarballu.
- **Nasaďte rovnaký artefakt.** `promote` odmietne kandidáta bez úspešného overenia jeho
  aktuálneho hashu tarballu. Predvoleným aktívnym slotom je `_artifacts/candidate/current`; `--target <dir>`
  vyberie iný adresár v rovnakom súborovom systéme a jeho predchádzajúcim slotom je `<dir>.previous`.
  Každé premenovanie je atomické a zlyhanie počas procesu vráti späť už vykonané premenovania.
- **Vrátenie späť.** `run` znova overí nasadený slot a pri zlyhaní
  tejto kontroly znovu vymení `current` a `previous`. Kandidát, ktorý neprejde prvým overením, sa nikdy nenasadí.

Všetko sa zapisuje do adresára `_artifacts/candidate/`, ktorý git ignoruje; existujúca inštalácia OmniRoute
ani jej dátový adresár sa nikdy nemenia. Nasadené CLI sa nachádza v
`_artifacts/candidate/current/prefix/bin/omniroute`; pri jeho použití ho spustite s vlastným `DATA_DIR`.
Návratové kódy: `0` úspech, `1` neúspešné overenie alebo nasadenie, `2` chyba použitia alebo chýbajúce zostavenie.

## Lokálny cyklus verzus CI

| Spúšťajte lokálne pre každú úpravu                                                       | CI poskytuje širší signál                                                                 |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Priame testy správania a vyššie uvedené kontroly kategórií                               | Rozdelený úplný súbor jednotkových testov a sériové testy                                 |
| `npm run lint`                                                                           | Súbory testov Vitest a postupne sprísňované požiadavky na pokrytie/kvalitu                |
| Kontrola typov alebo zostavenie iba vtedy, keď to vyžaduje dotknutý kontrakt             | Produkčné zostavenie, bezpečnostné kontroly, dokumentácia, závislosti a kontroly zásad PR |
| Manuálne interakcie/živé kontroly iba vtedy, keď automatizácia nedokáže overiť správanie | Kontroly integrácie medzi úlohami a platforiem nakonfigurované pracovným postupom         |

Úspešný cielený cyklus je dôkazom o zmenenom kontrakte, nie potvrdením, že nesúvisiace kontroly CI
prejdú. Zároveň nenechávajte každú lokálnu úpravu čakať na úplnú maticu repozitára.

## Kontrolný zoznam zosúladenia

Pred požiadaním o kontrolu:

- Potvrďte, že základom PR je stále najvyššia aktívna vetva `release/v*`.
- Načítajte tento základ a skontrolujte commity, ktoré boli začlenené od vytvorenia vašej vetvy.
- Skontrolujte `git diff <active-base>...HEAD`, či neobsahuje náhodné alebo vygenerované zmeny.
- Konflikty v katalógoch a generovaných dokumentoch riešte aktualizáciou zdroja a opätovným vygenerovaním výstupu.
- Po zosúladení znova spustite každý cielený test a kontrolu uvedenú v popise PR.
- Nikdy nezmierňujte asercie ani neodstraňujte povinné testy len preto, aby zodpovedali posunutému základu.

Pravidlá zmrazenia vydania a zmeny cieľovej vetvy nájdete v dokumente
[Model vetvenia a vydávania](BRANCHING_MODEL.md). Úplný zoznam kontrol CI nájdete v dokumente
[Referenčná príručka kontrol kvality](../architecture/QUALITY_GATES.md).
