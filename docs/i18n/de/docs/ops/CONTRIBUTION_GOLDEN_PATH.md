Verwenden Sie diesen Leitfaden, um die kleinste zuverlässige Entwicklungsschleife für einen Pull Request auszuwählen. Er
ersetzt nicht die unten verlinkten bereichsspezifischen Architektur- und Sicherheitsdokumente, sondern verknüpft jeden gängigen
Änderungstyp mit seinen Verträgen, gezielten Prüfungen und seiner CI-Abdeckung.

## Der Ablauf für jede Änderung

1. **Wählen Sie vor der Bearbeitung die Basis aus.** Ermitteln Sie den höchsten aktiven `release/v*`-Branch und erstellen Sie Ihren Branch
   ausgehend von dessen Spitze. Verwenden Sie diesen Branch und nicht `main` als Ziel. Wenn ein Release Freeze aktiv ist, verwenden Sie nicht den eingefrorenen
   Branch als Ziel, sondern den nächsten aktiven Zyklus, der im
   [Branching- und Release-Modell](BRANCHING_MODEL.md) beschrieben ist.
2. **Benennen Sie die Verträge.** Ermitteln Sie jeden Katalog, jedes Schema, jedes generierte Artefakt, jede öffentliche API und jede
   Benutzeroberfläche, die von der Änderung betroffen sind. Die folgende Tabelle enthält die mindestens zu berücksichtigende Ausgangsmenge.
3. **Schreiben oder aktualisieren Sie gezielte Tests.** Produktionsänderungen in `src/`, `open-sse/`, `electron/` oder
   `bin/` erfordern einen automatisierten Test im selben PR. Führen Sie zunächst die kleinstmöglichen Testdateien aus, die das
   Verhalten nachweisen, und anschließend die aufgeführten gezielten Prüfungen.
4. **Lassen Sie CI die umfassende Matrix ausführen.** Die vollständigen Unit-Shards, Vitest, die Coverage-Ratchet-Prüfung und
   der Produktions-Build werden für den PR ausgeführt. Führen Sie eine umfassende Suite lokal nur dann aus, wenn ein gezielter Fehler auf
   weiterreichende Auswirkungen hindeutet oder wenn die Änderung mehrere Subsysteme betrifft.
5. **Gleichen Sie vor dem Review ab.** Rufen Sie die aktive Basis ab, prüfen Sie deren neue Commits und Ihren Diff gegenüber
   dieser Basis und führen Sie anschließend gemäß dem Contributor-Workflow einen Rebase durch oder mergen Sie die Basis. Lösen Sie Konflikte bei generierten Dateien
   und Katalogen ausgehend von deren Quelle, generieren Sie sie neu, führen Sie die gezielte Schleife erneut aus und bestätigen Sie, dass der
   PR weiterhin auf den aktiven Release-Branch zielt.
6. **Dokumentieren Sie die Nachweise.** Führen Sie in der PR-Vorlage die ausgeführten Befehle, jede hinzugefügte oder geänderte Testdatei,
   Migrationen oder Feature Flags sowie alle noch ausstehenden, ausschließlich in CI möglichen Validierungen auf.

## Empfohlene Abläufe nach Änderungstyp

Die folgenden Befehle sind die mindestens erforderlichen gezielten Prüfungen und keine Erlaubnis, einen Test zu überspringen, der das
von Ihnen geänderte Verhalten direkt abdeckt.

### Provider

**Verträge**

- Provider-Definition in `src/shared/constants/providers/` und deren Zusammenstellung in
  `src/shared/constants/providers.ts`.
- Modelle und Fähigkeiten in `open-sse/config/providerRegistry.ts` oder den daraus extrahierten Registry-Dateien.
- Auswahl von Executor/Translator, OAuth- oder API-Key-Konfiguration, Dashboard-Assets und generierte
  Provider-Referenz, sofern zutreffend.
- Öffentliche Anmeldedaten müssen `resolvePublicCred()` verwenden; Fehlerantworten müssen die gemeinsamen bereinigten
  Fehlerhilfsfunktionen verwenden. Siehe `docs/security/PUBLIC_CREDS.md` (git; wird nicht nach `/docs` kompiliert) und
  [Fehlerbereinigung](../security/ERROR_SANITIZATION.md).

**Gezielte Schleife**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # wenn sich der Katalog ändert; den generierten Diff committen
npm run lint
```

Testen Sie außerdem jede betroffene Anfragefamilie: chat, Responses, images, embeddings, audio oder video.
Prüfen Sie generierte Katalog- und Golden-Diffs als Vertragsänderungen; akzeptieren Sie sie nicht ungeprüft.

### Routing

**Verträge**

- Öffentliche Strategiewerte und UI-Metadaten in `src/shared/constants/routingStrategies.ts`.
- Dispatch und Reihenfolge unter `open-sse/services/combo.ts` und `open-sse/services/combo/`.
- Combo-Schemas, Persistenz, Resilienzstatus, Modellfähigkeiten und API-/UI-Steuerelemente.
- [Auto-Combo-Engine](../routing/AUTO-COMBO.md) und Resilienzdokumentation, wenn sich das Verhalten ändert.

**Gezielte Schleife**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # Änderungen an Strategie oder Dispatch
npm run check:known-symbols      # Änderungen an der Strategieregistrierung
npm run lint
```

Verwenden Sie lokal deterministische Tests mit gemockten Upstream-Diensten. Live-Combo-Smoke-Tests benötigen Anmeldedaten und werden
manuell ausgeführt; sie sind kein Ersatz für CI.

### UI / UX

**Verträge**

- Grenzen von Next.js-Routen/-Seiten und gemeinsam genutzten Komponenten unter `src/app/` und
  `src/shared/components/`.
- API-Antwortstrukturen, Lade-/Leer-/Fehlerzustände, Verhalten für Tastatur und Screenreader,
  responsives Layout, Themes und Erweiterung der Locales.
- Englische UI-Quelltexte in `src/i18n/messages/en.json`; neue benutzerseitig sichtbare Texte dürfen nicht hartcodiert werden.

**Gezielte Schleife**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Führen Sie die Anwendung bei Interaktions- oder visuellen Änderungen aus und prüfen Sie sowohl schmale als auch breite Viewports. CI führt den
Produktions-Build und umfassendere Suites aus; visuelles Verhalten benötigt weiterhin eine für die Änderung geeignete gezielte Komponentenprüfung,
einen Playwright-Test oder eine dokumentierte manuelle Prüfung.

### i18n

**Verträge**

- `src/i18n/messages/en.json` ist die UI-Quelle; `config/i18n.json` ist die Locale-Quelle.
- CLI-Kataloge befinden sich separat unter `bin/cli/locales/`.
- Bewahren Sie ICU-Platzhalter und Tags exakt. Übersetzen Sie keine Produkt-/Provider-/Modellnamen,
  Protokoll- und Header-Namen, Befehle, Code-/JSON-Bezeichner, URLs, Umgebungsvariablen oder
  geschützte Begriffe wie `OmniRoute`, `OAuth`, `MCP` und `A2A`. Die aktuelle Quellliste befindet sich unter
  `scripts/i18n/glossary/protected-terms.json`.

**Gezielte Schleife**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # wenn sich CLI-Texte/-Kataloge ändern
npm run lint
```

Dies ist eine Anleitung für das bestehende System und keine Aufforderung, dessen Tooling oder Schlüsselmodell zu erweitern.
Halten Sie i18n-Patches gezielt und minimal, während das Ersatzsystem entworfen wird. Führen Sie keine Übersetzungsbefehle
aus, die externe Dienste aufrufen, es sei denn, die Aufgabe erfordert ausdrücklich generierte Übersetzungen und
Sie haben den resultierenden Diff geprüft.

### CLI

**Verträge**

- Öffentliche Befehle und Flags in `bin/cli/`, generierte API-Befehle, Exit-Codes, stdout/stderr und
  JSON-Ausgabeformate, Konfigurations-/Umgebungsverhalten sowie paketierte Dateien.
- Benutzerseitig sichtbare CLI-Zeichenfolgen müssen die CLI-i18n-Schicht verwenden, und die Kataloge `en`/`pt-BR` müssen synchron gehalten werden.
- Node muss als unterstützte Laufzeitumgebung und der veröffentlichte Binärvertrag müssen erhalten bleiben.

**Fokussierter Durchlauf**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generierte/gebündelte CLI-Änderungen
npm run check:pack-policy     # Änderungen an der Paketoberfläche
npm run lint
```

Verwenden Sie den exakten Befehl in einem temporären Datenverzeichnis, wenn das Verhalten vom Parsen, von Dateien oder vom Exit-
Status abhängt. CI führt die umfassenderen Prüfungen von Paketartefakten und des Ökosystems durch.

### Datenbank

**Verträge**

- Domänenmodule unter `src/lib/db/`; importieren Sie bestimmte Module direkt (die alte Re-Export-Schicht `localDb.ts` wurde entfernt).
- Nummerierte, idempotente SQL-Migrationen unter `src/lib/db/migrations/`, Transaktionssicherheit, Upgrade-
  Verhalten, Indizes und jeder vom Schema betroffene Aufrufer.
- Routen und Handler führen niemals direkt rohes SQL aus.

**Fokussierter Durchlauf**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Testen Sie beim Hinzufügen einer Migration sowohl eine neue Datenbank als auch ein Upgrade vom vorherigen Schema. Datenbanktests
müssen Handles schließen und während der Bereinigung `resetDbInstance()` aufrufen. Führen Sie `npm run test:bun:db` nur aus, wenn
sich der nach Best-Effort-Prinzip unterstützte Bun-Adapterpfad ändert; Node bleibt maßgeblich.

### Build / Bereitstellung

**Verträge**

- Root- und Workspace-Manifeste/Lockfile, `scripts/build/`, eigenständige Next.js-Assemblierung, `dist/`-
  Paketinhalte, Electron-Plattformmetadaten, CI-Workflows und Bereitstellungs-Sentinels.
- Unterstützte Node-Bereiche und die in `CLAUDE.md` freigegebene Bun-Nutzung müssen unverändert bleiben.
- Build-Artefakte bleiben unversioniert; Richtlinien für Abhängigkeiten, Lizenzen, Workflows und Pakete gelten.

**Fokussierter Durchlauf**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # Änderungen an Abhängigkeiten oder Lockfile
npm run check:pack-policy      # Änderungen an der veröffentlichten Paketoberfläche
npm run lint
```

Verwenden Sie `npm run build` lokal nur, wenn die Änderung die Kompilierung, eigenständige Assemblierung, Assets
oder Laufzeitbündelung betrifft. Verwenden Sie `npm run build:release` nur für die Release-/Bereitstellungsvalidierung. Der Build
von CI ist das endgültige plattformübergreifende Signal; plattformspezifische Electron-Änderungen benötigen den entsprechenden fokussierten Build
oder Smoke-Test-Nachweis.

## Entwicklerskripte für eine gemeinsam genutzte Maschine

Zwei Hilfsskripte unter `scripts/dev/` bilden den lokalen Arbeitsablauf auf einer Devbox ab, auf der andere Sitzungen aktiv sind:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # Dateien aus merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # genau diese Dateien
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # isolierter Worktree, sicher parallel ausführbar
```

- `typecheck-touched.sh` führt die Typprüfung nur für die betroffenen `.ts/.tsx`-Dateien über eine temporäre
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) mit einem 6-GB-Heap durch und ersetzt damit das projektweite `tsc -p tsconfig.json`,
  das auf einer ausgelasteten Maschine wegen Speichermangels abbricht. Es gibt die Fehler in den betroffenen Dateien sowie eine Zusammenfassungszeile aus und beendet sich
  mit `1` bei Fehlern in betroffenen Dateien, mit `2`, wenn die einzigen Fehler in importierten Dateien liegen oder tsc
  ohne Diagnoseausgabe beendet wurde (lesen Sie das angegebene Protokoll unter `_artifacts/typecheck-touched/`), und mit `0`, wenn
  keine Fehler vorliegen. Die temporäre tsconfig wird immer entfernt; committen Sie sie niemals.
- `new-worktree.sh` serialisiert gleichzeitig ausgeführte Instanzen über `<git-common-dir>/omniroute-new-worktree.lock`
  (wartet standardmäßig bis zu 600 s und zeigt dabei eine Meldung an; der Skript-Header dokumentiert die
  Überschreibung) und macht
  die erstellte Branch rückgängig, wenn `git worktree add` fehlschlägt, bevor der Worktree existiert, sodass für einen erneuten Versuch
  kein manuelles `git branch -D` erforderlich ist. Die hart verknüpften `node_modules` und die Kopie von `.husky/_` bleiben unverändert.

## Lokaler Kandidatenzyklus

Quellcodetests können nicht beweisen, dass das paketierte Artefakt startet: Paketierungslisten, bereinigte Abhängigkeiten
und native Binärdateien schlagen erst fehl, wenn der Tarball installiert und gestartet wird. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ist die lokale Seite des Ablaufs „einmal bauen / validieren / hochstufen“ aus
RFC #8084: Es erstellt einen Kandidaten, validiert genau dieses Artefakt, stuft es durch Umbenennen von Verzeichnissen hoch
und setzt es zurück, wenn der hochgestufte Slot seine Zustandsprüfung nicht besteht.

```bash
npm run dev:candidate -- run --dry-run --json  # Plan ausgeben, nichts ändern
npm run dev:candidate -- run                   # bauen + validieren + hochstufen, automatische Rücksetzung
npm run dev:candidate -- build                 # npm pack + Installation unter _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # auf einem freien Port starten, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current und previous vertauschen
npm run dev:candidate -- run --from-tarball <file.tgz>  # einen andernorts erstellten Tarball wiederverwenden (CI)
```

- **Einmal bauen.** `build` paketiert den aktuellen Arbeitsbaum (es benötigt `dist/server.js`; führen Sie daher zuerst
  `npm run build:release` aus) oder kopiert `--from-tarball` und installiert den Tarball anschließend in ein
  isoliertes npm-Präfix, da der Tarball keine `node_modules` enthält. Die ID ist der kurze `HEAD`-SHA
  (`-dirty`, wenn der Arbeitsbaum lokale Änderungen enthält) oder `tgz-<sha256>` für einen Tarball. Eine saubere ID, die
  bereits erstellt wurde, wird wiederverwendet, statt erneut erstellt zu werden; übergeben Sie `--force`, um sie neu zu erstellen.
- **Das Paket validieren, nicht den Quellcode.** `validate` startet die installierte CLI
  (`serve --port <free port>`) mit einem neuen `DATA_DIR=<candidate>/data`, Platzhaltergeheimnissen und ohne die
  Variablen `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` und `INITIAL_PASSWORD` des Operators in der
  Umgebung, sodass die schlüssellose Loopback-Konfiguration einer Neuinstallation geprüft wird. Es wartet, bis
  `GET /api/health` den Status 200 zurückgibt, verlangt, dass `GET /v1/models` den Status 200 zurückgibt, beendet die Prozessgruppe
  und zeichnet das Ergebnis zusammen mit dem Tarball-Hash in `validation.json` auf.
- **Dasselbe Artefakt hochstufen.** `promote` lehnt einen Kandidaten ab, der für seinen
  aktuellen Tarball-Hash keine erfolgreiche Validierung aufweist. Der aktive Standardslot ist `_artifacts/candidate/current`; `--target <dir>`
  wählt ein anderes Verzeichnis auf demselben Dateisystem aus, und dessen vorheriger Slot ist `<dir>.previous`.
  Jede Umbenennung ist atomar, und bei einem Fehler während des Vorgangs werden die bereits ausgeführten Umbenennungen rückgängig gemacht.
- **Zurücksetzen.** `run` validiert den hochgestuften Slot erneut und vertauscht `current` und `previous` wieder, wenn
  diese Prüfung fehlschlägt. Ein Kandidat, der die erste Validierung nicht besteht, wird niemals hochgestuft.

Alles wird unter dem von Git ignorierten Verzeichnis `_artifacts/candidate/` gespeichert; eine vorhandene OmniRoute-
Installation und ihr Datenverzeichnis werden niemals verändert. Die hochgestufte CLI befindet sich unter
`_artifacts/candidate/current/prefix/bin/omniroute`; starten Sie sie mit Ihrem eigenen `DATA_DIR`, wenn Sie sie verwenden.
Exit-Codes: `0` Erfolg, `1` fehlgeschlagene Validierung oder Hochstufung, `2` Anwendungsfehler oder fehlender Build.

## Lokale Schleife im Vergleich zu CI

| Für jeden Patch lokal ausführen                                                                         | CI liefert das umfassende Signal                                                               |
| ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Direkte Verhaltenstests und die oben genannten Kategorie-Gates                                          | Aufgeteilte vollständige Unit-Test-Suite und serielle Tests                                    |
| `npm run lint`                                                                                          | Vitest-Suites und Schwellenwerte für Abdeckung/Qualität                                        |
| Typprüfung oder Build nur, wenn der betroffene Vertrag dies erfordert                                   | Produktions-Build sowie Sicherheits-, Dokumentations-, Abhängigkeits- und PR-Richtlinien-Gates |
| Manuelle Interaktions-/Live-Prüfungen nur, wenn die Automatisierung das Verhalten nicht nachweisen kann | Workflow-konfigurierte jobübergreifende Integrations- und Plattformprüfungen                   |

Eine erfolgreiche fokussierte Schleife ist ein Beleg für den geänderten Vertrag, aber kein Nachweis dafür, dass nicht damit zusammenhängende CI-Prüfungen
bestanden werden. Umgekehrt sollte nicht jede lokale Änderung auf die vollständige Repository-Matrix warten müssen.

## Checkliste für den Abgleich

Vor dem Anfordern einer Review:

- Bestätigen, dass die PR-Basis weiterhin der höchste aktive `release/v*`-Branch ist.
- Diese Basis abrufen und die Commits prüfen, die seit dem Erstellen des Branches übernommen wurden.
- `git diff <active-base>...HEAD` auf unbeabsichtigte oder generierte Änderungen prüfen.
- Konflikte bei Katalogen und generierten Dokumenten beheben, indem die Quelle aktualisiert und die Ausgabe neu generiert wird.
- Nach dem Abgleich jeden in der PR-Beschreibung aufgeführten fokussierten Test bzw. jedes Gate erneut ausführen.
- Niemals Assertions abschwächen oder erforderliche Tests entfernen, nur um sie an eine verschobene Basis anzupassen.

Regeln zu Release-Freezes und Retargeting finden sich unter
[Branching- und Release-Modell](BRANCHING_MODEL.md). Das vollständige CI-Inventar befindet sich in der
[Referenz zu Qualitäts-Gates](../architecture/QUALITY_GATES.md).
