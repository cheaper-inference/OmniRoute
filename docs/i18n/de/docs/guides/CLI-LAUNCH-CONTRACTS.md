Der neutrale `config/cli-tools-manifest.json` Vertrag deklariert kanonisches IDs, Aliase, binäre Kandidaten, Setup-Rezepte, Modellargumente und Fähigkeiten. Der einfache Node-Adapter in `bin/cli/cli-manifest.mjs` und der TypeScript Adapter in `src/shared/constants/cliIntegrationManifest.ts` lesen dieselbe Datei. Laufzeit, Katalog, Konfiguration, Vervollständigung, Generatoren und Backend-Registrierung werden gemeinsam von `tests/unit/cli/cli-manifest-drift.test.ts` überprüft. Die Katalogisierung bedeutet nicht, dass ein Tool gestartet oder konfiguriert werden kann. Insbesondere bleibt 5dive weiterhin konfigurierbar.

## Umgebung und Lebenszyklus des Kindes

`omniroute run`, `omniroute launch` und `omniroute launch-codex` erben eine OS/terminal Kompatibilitäts-Zulassungsliste und fügen die Anmeldeinformationen des ausgewählten Ziels ein. Unabhängige Anbieter- und Datenbankgeheimnisse werden standardmäßig nicht vererbt. `--inherit-env` stellt explizit die vollständige Vererbung der übergeordneten Umgebung wieder her; Verwenden Sie es nur, wenn der ausgewählte Drittanbieterprozess diese Werte erhalten soll. Hierbei handelt es sich um eine Umgebungsfilterung, nicht um eine OS Sandbox: Der Prozess wird weiterhin mit den Dateisystemberechtigungen des Aufrufers ausgeführt.

Unterbrechungs- und Beendigungssignale werden an das Kind weitergeleitet. Der Launcher wartet auf das Schließereignis des untergeordneten Elements, bevor er die temporäre Konfiguration entfernt. `OMNIROUTE_CHILD_SIGNAL_TIMEOUT_MS` steuert den Kulanzzeitraum vor der erzwungenen Beendigung (Standard 5000 Millisekunden).

## Gemini Persistenz-Setup

```bash
omniroute setup-gemini --remote https://omni.example --model provider/model --yes
omniroute configure gemini --model provider/model --yes
omniroute run gemini --model provider/model --dry-run --json
```

Die ersten beiden Befehle konfigurieren diesen Computer für den ausgewählten lokalen oder Remote-Server. Das Setup behält nicht verwandte JSON Einstellungen bei, wählt Gemini -API-Schlüsselauthentifizierung aus und schreibt den Endpunkt und die Anmeldeinformationen in eine private `.gemini/.env` Datei. Es lehnt ungültiges JSON ab, anstatt es zu überschreiben. Endpunkt URLs muss HTTP(S) sein, ohne eingebettete Anmeldeinformationen, Abfrageparameter oder Fragmente. Der Probelauf druckt Pfade, keine Anmeldedatenwerte.

`GEMINI_CLI_HOME` oder `--gemini-home` wählt den persistenten Home-Root aus. Ein tatsächlicher `run gemini` erstellt und entfernt später sein eigenes temporäres Zuhause. Keiner der Modi umgeht die Workspace-Trust-Prüfungen von Gemini.

## Codex Profile

`configure codex` schreibt ein privates `<name>.config.toml` mit einem Modell und seinem OmniRoute -Provider-Endpunkt. Anmeldeinformationen werden über `OMNIROUTE_API_KEY` referenziert und niemals eingebettet. Der Startbefehl legt das ausgewählte Modell auf der `model` -Taste der obersten Ebene fest, nicht innerhalb `model_providers`.

Separate Profildateien sind der aktuell dokumentierte Codex Vertrag; Sie überlagern die Benutzerkonfiguration, wenn sie mit `codex --profile <name>` ausgewählt werden. Sehen Sie sich [die offizielle Profilreferenz](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) und [den OmniRoute Codex -Leitfaden](./CODEX-CLI-CONFIGURATION.md) an.

## Hermetische Befehlsausführung

Mit einem expliziten `DATA_DIR` verhindert die Einstellung `OMNIROUTE_CLI_SKIP_DEFAULT_DATA_ENV=1`, dass der Startvorgang in die Anmeldeinformationsumgebung des Standardbenutzerdatenverzeichnisses übergeht. Dies ist für isolierte Tests nützlich. Andere explizit ausgewählte Umgebungsdateien werden dadurch nicht deaktiviert.

## Arbeitsverzeichnis `.env`

Der CLI liest `.env` Dateien in dieser Reihenfolge, und die erste Datei, die einen Schlüssel festlegt, gewinnt: der explizite `DATA_DIR`, das Standarddatenverzeichnis, das aktuelle Arbeitsverzeichnis und dann das Paketverzeichnis. Shell-Variablen gewinnen immer.

Das Arbeitsverzeichnis kann jemand anderem gehören (einem geklonten Repository, einem entpackten Archiv), und `omniroute serve` übergibt die CLI Umgebung an den Server und an jedes Tool, das der Server ausführt. Ein `.env` darf dort also nur diese Schlüssel festlegen, die in `bin/cli/utils/untrustedCwdEnv.mjs` aufgeführt sind:

| Schlüssel                       | Akzeptierte Werte                                                               |
| ------------------------------- | ------------------------------------------------------------------------------- |
| `REQUIRE_API_KEY`               | `true`, `1` oder `yes` in jedem Fall die Werte, die der Server als on behandelt |
| `LANG`, `LC_ALL`, `LC_MESSAGES` | bis zu 64 Buchstaben, Ziffern, `_`, `.`, `@` oder `-`                           |
| `LANGUAGE`                      | das gleiche, plus `:`                                                           |
| `TZ`                            | bis zu 64 Buchstaben, Ziffern, `_`, `+`, `-` oder `/`, nicht beginnend mit `/`  |
| `NO_COLOR`, `FORCE_COLOR`       | bis zu 16 Buchstaben und Ziffern                                                |

Jeder Wert, `REQUIRE_API_KEY` akzeptiert, aktiviert die Prüfung, sodass die Datei die Prüfung nicht selbst deaktivieren kann. Es entscheidet jedoch nicht über das Ergebnis: Der Server liest eine in der Datenbank gespeicherte `REQUIRE_API_KEY` Überschreibung vor der Umgebung, während die Startwarnung zum Abhören aller Schnittstellen ohne API -Schlüssel nur die Umgebung liest. Bei einer gespeicherten Überschreibung von `false` lässt ein Arbeitsverzeichnis- `REQUIRE_API_KEY=true` das API offen und verbirgt diese Warnung. Die `TZ` Regel ist enger gefasst als POSIX: Sie lehnt `.`, `:`, `,` und `<>` ab, daher müssen die `:Area/City` Form und Regeln wie `EST5EDT,M3.2.0,M11.1.0` in der Shell oder in `<DATA_DIR>/.env` festgelegt werden.

Die Namen müssen exakt übereinstimmen und in Großbuchstaben geschrieben werden. Alle anderen Zeilen, ein Wert, der die Prüfung nicht besteht, und ein Name, der nicht aus einfachen ASCII Buchstaben, Ziffern und `_` besteht (z. B. eine mit einem NUL Byte oder einem ähnlichen Buchstaben), werden übersprungen. Der CLI gibt eine Warnung aus, die die Schlüssel benennt, die er nicht festlegen kann, und eine, die die erlaubten Schlüssel benennt, die er ignoriert hat, jeweils mit dem, was geändert werden soll (`TZ (expected a zone name such as Europe/Berlin)`, `lang (write the name as LANG)`). Weder werden die Werte gedruckt. Dateipfade in diesen Nachrichten und die `.env` Pfad `omniroute doctor` -Berichte werden maskiert, wenn sie Steuer- oder Bidi-Zeichen enthalten. Die Einschränkung gilt nicht, wenn das Arbeitsverzeichnis das Datenverzeichnis oder das Paketverzeichnis ist.

`PORT`, `API_PORT` und `DASHBOARD_PORT` sind nicht auf der Liste. Ohne einen Basis URL von einer Quelle mit höherer Priorität kommuniziert der CLI mit `localhost:<PORT>`, und was auch immer dort lauscht, empfängt den API Schlüssel des CLI, das Kontext-Token und den CLI Maschinen-Token (`x-omniroute-cli-token`, siehe [CLI_TOKEN.md](../security/CLI_TOKEN.md) ), den der lokale Server für Verwaltungsaufrufe vom Loopback akzeptiert. Ein Port aus dem Arbeitsverzeichnis würde es dieser Datei ermöglichen, den Listener auszuwählen. Legen Sie die Ports daher in der Shell, in `<DATA_DIR>/.env` oder mit der `--port` Option von Befehlen fest, die einen solchen haben (`serve`, `launch`, `run`).

Der Parser hat keine `export` Syntax. Eine Zeile wie `export LD_PRELOAD=...` benennt eine Variable `export LD_PRELOAD`; Aus dem Arbeitsverzeichnis wird es übersprungen und in anderen `.env` -Dateien wird dieser Literalname festgelegt, der nichts liest.

Der CLI koppelt das gespeicherte Token eines Kontexts (Zugriffstoken oder Legacy- API -Schlüssel) nur mit dem eigenen Ursprung dieses Kontexts: Schema, Host und Port, verglichen mit `URL.origin`. Dies gilt für Anfragen, die über den HTTP Client von CLI(`--base-url`, `OMNIROUTE_BASE_URL`, `omniroute connect <new-url>`) gestellt werden, sowie für die Befehle `launch`, `launch codex`, `configure` und `setup-*`, die einen Basis URL und -schlüssel in die Konfiguration eines anderen Tools schreiben. Wenn sie mit `--remote` auf einen anderen Server verweisen, verwenden sie ein explizites `--api-key` oder `OMNIROUTE_API_KEY` sofern eines festgelegt ist, und kein Kontext-Token. Der Vergleich ist genau, daher gelten `localhost` und `127.0.0.1` oder ein Host mit und ohne abschließendem Punkt als unterschiedliche Server und erhalten kein Kontexttoken. Ein URL mit Benutzerinformationen, einem Backslash oder Leerzeichen stimmt nie überein, da andere URL Parser (zum Beispiel `urllib` und `httpx` von Python) einen anderen Host daraus lesen können. Bei Anfragen, die das CLI selbst sendet, deckt diese Prüfung nur das Schema und die Autorität ab, sodass eine ID mit einem Leerzeichen im Pfad oder in der Abfrage das Token behält.
