`copilot-m365-web` (alias `m365copilot`) sendet Chatanfragen im OpenAI-Format über eine authentifizierte Microsoft 365 Copilot Sitzung bei `m365.cloud.microsoft/chat`. Dies ist eine inoffizielle native Integration: Es ist kein separater Proxy-Prozess oder Localhost-Upstream erforderlich. Der Anbieter ID, Alias und bestehende importierte Verbindungen bleiben unverändert. `copilot-web` ist ein anderer Anbieter für den Verbraucherservice bei `copilot.microsoft.com`.

> **Neu bei Web-Cookie-Anbietern?**
>
> Lesen**`docs/getting-started/WEB-COOKIE-GUIDE.md`** Informieren Sie sich über den allgemeinen Einrichtungsprozess, Anleitungen zur Authentifizierung, Einschränkungen und Fehlerbehebung, bevor Sie dieser anbieterspezifischen Anleitung folgen.
>
> **Für Legacy-Importe:** Die Anmeldeinformationen für diesen Anbieter sind** kein Keks** . Kopieren Sie keine Cookies von `m365.cloud.microsoft`. Bei den Anmeldeinformationen handelt es sich um einen WebSocket URL -Abfrageparameter und ein Pfadsegment, die beide aus der DevTools Registerkarte „Netzwerk“ gelesen werden.

## Voraussetzungen

- Ein Microsoft 365-Konto mit Zugriff auf Copilot unter `m365.cloud.microsoft/chat`
- Ein Chromium-basierter Browser (Chrome, Edge) für DevTools WebSocket Inspektion
- Zugriff auf das angeforderte Modell über dieses Konto; Die Verfügbarkeit variiert je nach Mieter und Lizenz

## Native Anmeldung (Arbeits- oder Schulkonten)

Wählen**Microsoft 365 Copilot → Connect** und bereiten Sie einen Anmeldeversuch vor. Das Dashboard verwendet einen Autorisierungscode-Flow mit PKCE; Es wird nicht nach Ihrem Microsoft Passwort oder MFA Code gefragt.

1. Öffnen Sie ein** leere Browser-Registerkarte** , dann öffnen**DevTools → Netzwerk** und ermöglichen** Protokoll aufbewahren** . Tun Sie dies, bevor Sie zu Microsoft navigieren: Windows SSO wird möglicherweise sofort beendet.
2. Kopieren Sie die im Verbindungsdialog angezeigte Autorisierungs- URL und navigieren Sie in der vorbereiteten Registerkarte dorthin. Vervollständigen Sie die Kontoauswahl von Microsoft oder MFA, falls erforderlich.
3. Suchen Sie im erhaltenen Netzwerkprotokoll nach der Anfrage an `https://login.microsoftonline.com/common/oauth2/nativeclient` und kopieren Sie sie vollständig** Fordern Sie URL** .
4. Fügen Sie diesen URL in den Verbindungsdialog ein und stellen Sie eine Verbindung her. Fügen Sie keinen Rohcode oder die endgültige `wrongplace` -Adressleiste URL ein: Der erforderliche Rückruf ist eine vorübergehende Navigation.

Jeder Versuch verfällt nach zehn Minuten und kann nur einmal verwendet werden. Der Server überprüft seinen Status, PKCE Verifizierer und das erneute Authentifizierungsziel, bevor er den Code austauscht. Starten Sie nach Ablauf oder einem Umtauschfehler einen neuen Versuch. Ein Versuch kann einen Serverneustart nicht überleben.

Token verwenden den vorhandenen Speicher für Verbindungsanmeldeinformationen und den Aktualisierungspfad. Für die erneute Authentifizierung einer Verbindung ist dieselbe Microsoft tenant/object Identität erforderlich, nicht nur dieselbe E-Mail. Es behält den Operator naming/settings bei und ersetzt veraltete importierte Anmeldeinformationen. Die native Anmeldung gilt für work/school -Konten. Der Legacy-Importpfad bleibt für bestehende Verbindungen und unterstützte Tier-Konfigurationen verfügbar.

Bei der vollständigen Rückruf- URL handelt es sich um eine einmalige Berechtigung. Fügen Sie es niemals in Screenshots, Protokolle, Supportnachrichten oder Commits ein. Dieser Ablauf öffnet keinen Browser auf dem Server, prüft Ihren Browserverlauf nicht und startet keinen lokalen Rückrufserver.

## Erfassung von Anmeldeinformationen (WebSocket Methode)

1. Melden Sie sich bei `https://m365.cloud.microsoft/chat` an und beginnen Sie ein Gespräch.
2. Offen**DevTools → Netzwerk** .
3. Filtern nach**WS** (WebSocket).
4. Klicken Sie auf die Chathub- WebSocket -Verbindung. Suchen Sie nach einem URL das mit `wss://substrate.office.com/m365Copilot/Chathub/` beginnt.
5. Von ihm** Fordern Sie URL** , kopieren:
   - Der `access_token` -Abfrageparameterwert (ein kurzlebiger JWT).
   - Das Chathub-Pfadsegment nach `/Chathub/` (z. B. `<oid>@<tenant>`).

Die vollständige URL hat die Form:

```
wss://substrate.office.com/m365Copilot/Chathub/<oid>@<tenant>?...&access_token=<jwt>
```

6. Wählen Sie in OmniRoute aus**Microsoft 365 Copilot** , wählen Sie die Legacy- API-key/import Option und fügen Sie die Anmeldeinformationen im folgenden Format ein:

```
access_token=<jwt>; chathubPath=<oid>@<tenant>
```

7. Klicken** Testverbindung** Und** Speichern** .

## Anmeldeinformationserfassung (HAR -Import)

Anstatt Werte manuell aus WebSocket URL zu kopieren, können Sie eine DevTools HAR Datei exportieren:

1. Offen**DevTools → Netzwerk** .
2. Starten oder setzen Sie ein Microsoft 365 Copilot -Gespräch fort (dies löst die WebSocket Verbindung aus).
3. Klicken Sie mit der rechten Maustaste in das Netzwerkfenster und wählen Sie aus** Alles als HAR mit Inhalt speichern** .
4. Verwenden Sie in OmniRoute die** .har-Datei importieren** Schaltfläche im Provider-Verbindungsdialog.

OmniRoute durchsucht das HAR nach dem Chathub WebSocket URL, extrahiert `access_token` und `chathubPath` und füllt die Anmeldeinformationsfelder automatisch aus. Der HAR Import dekodiert den JWT Ablauf und zeigt die verbleibende Token-Lebensdauer an.

> **Führen Sie niemals einen echten HAR Export, Zugriffstoken oder Aktualisierungstoken durch.** Test- und Dokumentationswerte müssen immer Platzhalter sein.

## Lebensdauer und Aktualisierung des Tokens

Die `access_token` ist von kurzer Dauer (typischerweise).**~ 75 Minuten** ). Ohne ein verwendbares Aktualisierungstoken müssen Sie die Anmeldeinformationen nach Ablauf erneut erfassen.

### Automatische Aktualisierung mit `refreshToken`

Im Microsoft 365 Anbieter** Verbindung hinzufügen** oder** Verbindung bearbeiten** Dialog, öffnen** Erweiterte Einstellungen → -Aktualisierungstoken (optional)** . Fügen Sie ein Microsoft OAuth Aktualisierungstoken für den `substrate.office.com/sydney` -Bereich ein und speichern Sie es. Die Eingabe wird maskiert und niemals mit dem gespeicherten Token vorbefüllt. Lassen Sie das Feld beim Bearbeiten leer, um das vorhandene Token beizubehalten. Fügen Sie einen neuen Token ein, um ihn zu ersetzen.

Die native Anmeldung ruft das Aktualisierungstoken ab, wenn Microsoft eines zurückgibt. Verwenden Sie für Legacy-Importe eine vorhandene kompatible Microsoft -Autorisierungscode-Gewährung. Dieser Anbieter implementiert oder verspricht keinen Gerätecodefluss. Wenn ein Aktualisierungstoken konfiguriert ist, überprüft OmniRoute den `access_token` vor Anfragen und aktualisiert ihn nur, wenn eine Aktualisierung erforderlich ist. Bei einer erfolgreichen Aktualisierung bleibt auch das rotierte Aktualisierungstoken erhalten, wodurch eine manuelle erneute Erfassung vermieden wird, während das Aktualisierungstoken gültig bleibt.

Wenn `refreshToken` nicht festgelegt ist, müssen Sie die WebSocket Anmeldeinformationen nach jedem Ablauf manuell erneut erfassen.

## Modelle und Routing

Der native Katalog umfasst alle dokumentierten eigenständigen IDs sowie die vier ursprünglichen nativen IDs. Der Katalog ist statisch und kontounabhängig und stellt keine Prüfung der Kontoberechtigung dar: Bezahlte Routen und Kompatibilitätsaliase bleiben auch dann aufgeführt, wenn ein verbundenes Konto sie nicht verwenden kann. Bei den Modellanzeigebezeichnungen werden der Name des Anbieters und die Boilerplate für die Verfügbarkeit pro Modell weggelassen. Der Anbieter bleibt bestehen**Microsoft 365 Copilot** . Etiketten markiert** Alias** oder** Vermächtnis** behalten ihre bestehenden Identifikatoren und Protokollzuordnungen bei, keine Garantie für eine historische Modellversion. Die eigenständigen Proxys** Import aus /models** Anweisungen gelten nicht für diesen nativen WebSocket Anbieter.

| ----------------- | ------------------------------------------------------------------------------------------------ |
| Automatisch       | `m365-copilot`                                                                                   |
| GPT-5.5 / GPT-5.6 | `gpt-5.5`, `gpt-5.5-think-deeper`, `gpt-5.6`, `gpt-5.6-think-deeper`                             |
| Früher GPT        | `gpt-5.4`, `gpt-5.4-quick`, `gpt-5.3`, `gpt-5.3-think-deeper`, `gpt-5.2`, `gpt-5.2-think-deeper` |

Aliase wie `auto`, `quick`, `think-deeper` und Versionsaliase werden ebenfalls registriert. Die vorhandenen `copilot-m365`, `copilot-m365-claude-opus`, `copilot-m365-gpt-5-6-reasoning` und `copilot-m365-gpt-5-5-chat` bleiben gültig. Die dokumentierten IDs benötigen das Provider-Präfix (`copilot-m365-web/claude-opus` oder `m365copilot/claude-opus`): Viele sind generische Wörter oder Modellnamen anderer Anbieter, sodass ein bloßes `claude-opus` das Routing genauso fortsetzt wie ohne diesen Provider. Die Registrierung ist kein Versprechen, dass Microsoft dieses Modell für jedes Konto bereitstellt. Die eigenständigen IDs folgen dem öffentlichen [Protokollkatalog](https://github.com/cramt/m365-copilot-proxy/blob/main/packages/core/src/copilot.ts) (der exportierten Model-to-Tone-Map und ihren modellbewussten Szenario-Metadaten). Alle nativen Profile behalten `availability: "unverified"` bei; Die Aufnahme in den Katalog ist kein erfolgreicher Account-Test.

- Es erfolgt eine explizite Modelllizenzverweigerung** 403** `m365_model_not_licensed`, nicht 502. Routing sperrt das connection/model Paar, sodass lizenzierte Modelle auf der Verbindung verwendbar bleiben.
- `InvalidCopilotLicense` handelt es sich um eine Lizenzverweigerung auf Kontoebene, die separat als `m365_account_not_licensed` gemeldet wird.
- Es wird eine Drosselung pro Benutzer zurückgegeben** 429** `m365_throttled` und kühlt die Verbindung ab. Erschöpfungsrückgaben mit vorrangigem Zugriff** 429** `priority_access_exhausted` und ist modellbezogen. Ein Ergebnis von `OutOfCredits` mit `errorCode: "ReasoningTurnExhausted"` wird zurückgegeben** 429** stattdessen `reasoning_turns_exhausted`, ebenfalls modellbezogen, ohne beanspruchte Rücksetzzeit. Es wurde berichtet, dass ein Arbeitsmieter die „Think deeper“-Töne begrenzte, während die Quick-Töne weiter dienten; Dieser Umfang ist eine Verbraucherbeobachtung und nicht etwas, das dieses Repository reproduziert hat. Durch das Routing werden daher auch die anderen dokumentierten Think Deeper-Modelle von `gpt-5.5` und `gpt-5.6` für die gleiche Abklingzeit auf dieser Verbindung aus der Rotation genommen und die Schnelltöne und alle anderen Fehler auf ihrem eigenen Modell belassen. Die bereitgestellten Wiederholungshinweise bleiben erhalten. Ein fehlender Reset wird nicht als bekannte Reset-Zeit angekündigt.
- Eine Copilot Sicherheitsverweigerung (`Disengaged`) kehrt zurück** 400** `provider_safety_rejection`, das gemeinsame Sicherheitsstopp-Label des Anbieters. Es wird nie auf den Zustand der Verbindung angerechnet, der Client SDKs versucht es nicht erneut mit 400, und bei aktiviertem `PROVIDER_SAFETY_STOPS_TERMINAL` stoppt das Combo-Routing dort, anstatt die Anfrage für ein anderes Ziel erneut abzuspielen.
- Anforderungen an eine Verbindung werden über das vorhandene Kontosemaphor serialisiert. Bevorzugen Sie Prioritäts-Fallback gegenüber parallelen Panels; Durch die Serialisierung allein werden die Konversationsgeschwindigkeitsbeschränkungen von Microsoft nicht beseitigt.

## Fordern Sie Verhalten und Grenzen an

- Werkzeuge sind** prompt-emuliert** , keine nativen Microsoft -Funktionsaufrufe. Eine durch ein Tool aktivierte Anfrage verwendet eine gepufferte Generation. Es verbringt keine weitere Generation mit der Auswahl von Werkzeugen. Als Aufrufe werden nur deklarierte Werkzeuge mit gültigen unterstützten Argumentformen zurückgegeben.
- Eine lange strukturierte Antwort mit einem einzelnen abschließenden Beispiel bleibt als Prosa erhalten. Dies ist eine Heuristik, kein Absichtsbeweis; Anwendungen müssen weiterhin ihre eigenen Tool-Berechtigungen erzwingen.
- Die Bildeingabe funktioniert so, wie der Webclient sie sendet. Jeder Bildteil (`image_url` als Daten- URL oder öffentlicher HTTPS URL oder Antwort- `input_image`) wird mit dem Chat-Token in `/m365Copilot/UploadFile` in die Konversation des Turns hochgeladen, und die Nachricht zeigt darauf mit einer `ImageFile` -Anmerkung; Der Text markiert die Stelle, an der er sich befand (`[image 1]`, …). Bei einer neuen Konversation werden alle Bilder im Verlauf hochgeladen, bei einer fortgesetzten Konversation werden nur die Bilder der neuen Nachrichten hochgeladen. Bis zu 10 PNG, JPEG, GIF oder WebP Bilder mit jeweils höchstens 10 MiB (40 MiB pro Anfrage); Das Format wird aus den Bytes gelesen. HTTPS URLs werden über den nur öffentlichen, DNS-angehefteten Remote Image Guard abgerufen. Bei einem fehlgeschlagenen Upload schlägt die Anfrage fehl (** 502** `m365_image_upload_failed`,** 400** `m365_image_rejected` oder `m365_image_invalid`); Eine Runde geht nie ohne ein Bild weiter, das ihr gegeben wurde. Andere Nicht-Text-Teile (Audio, Dateien) werden explizit abgelehnt und nicht stillschweigend gelöscht.
- Eine Folgeanfrage setzt die gleiche Upstream-Konversation fort und sendet nur die Nachrichten nach der vorherigen Antwort. Diese Antwort muss genau erweitert werden: gleiche Verbindung, gleiches Modellprofil und gleicher Werkzeugsatz; ein unveränderter Verlauf (eine sha256-Kette über jede Nachricht); und die Tool-Call-IDs der Antwort oder deren Text bis auf Leerzeichen. Alles andere (ein bearbeiteter Verlauf, eine andere Sitzung mit derselben ersten Nachricht, eine andere Antwort, eine Konversation, die 30 Minuten lang inaktiv war oder in der Nähe der 600-Nachrichten-Grenze von Copilot liegt, eine Verbindung ohne ID) startet eine neue Konversation mit dem gesamten Verlauf. Eine fehlgeschlagene Runde wird nie wieder aufgenommen und ein inhaltsloser `InternalError` wird einmal in einer neuen Konversation erneut gesendet (** 502** `m365_internal_error` wenn es erneut fehlschlägt). Fortsetzungen werden im Prozessspeicher gehalten: Ein Neustart startet neue Konversationen.
- Jede Runde läuft im temporären Chat von Copilot(`disableMemory=1`): Die Konversation behält während der Ausführung ihren Kontext und erscheint nie im Chat-Verlauf des Kontos. Modelltests, Test-Alles und Kombinationstests können diesen Anbieter daher testen, ohne Gespräche zu hinterlassen.
- Eine Runde hat eine Leerlaufzeit von 120 Sekunden und eine begrenzte Gesamtfrist. Nur endgültige Antworten, Fortschrittsfilterung und Abbruch werden vom nativen transport/composer. verwaltet
- Webbasierte Antworten behalten ihre Quellen. Copilot markiert ein Zitat inline mit Steuerzeichen für den privaten Gebrauch und sendet die Quellen als `references`; Jeder Marker wird zu einem nummerierten Markdown-Link (`[1](https://…)` oder der bloße URL wenn Copilot den Marker als Linkziel verwendet hat) mit einer passenden `url_citation` Annotation (`message.annotations` oder `delta.annotations` auf dem Block, der den Link trägt). Eine Quelle, die nie eintrifft, wird verworfen, sodass die Markierungen den Client nie erreichen. Beim Streaming wartet der Text nach einem Zitat, bis die Quelle eingetroffen ist.
- Die Argumentationszusammenfassung von Copilot(`ChainOfThoughtSummary`) wird, wenn das Modell eine sendet, als `reasoning_content` zurückgegeben, niemals als Teil der Antwort. Eine Zusammenfassung, die sich selbst neu schreibt, stoppt das Streaming, ohne dass die Runde fehlschlägt.
- Vor jeglichem Inhalt behalten licence/throttle Fehler HTTP 403/429 bei, selbst wenn Streaming angefordert wurde. Nach dem Start des Inhalts handelt es sich bei Fehlern um SSE Fehlerereignisse, niemals um einen erfolgreichen Abschluss. Ein Upstream-Umschreiben, das nicht durch reines Anhängen-Streaming dargestellt werden kann, ist ein expliziter Stream-Fehler. Nicht gestreamte und gepufferte Tool-Antworten behalten den endgültigen Text.
- Wenn Copilot die Verbindung selbst ablehnt, wird seine Antwort wie folgt gemeldet:** 401** `m365_unauthorized` für eine abgelehnte oder abgelaufene Anmeldung (erneut anmelden),** 429** mit seinem `Retry-After` zur Drosselung und andernfalls einem Handshake-Fehler, niemals einem generischen Verbindungsfehler.

## Bilderzeugung

`POST /v1/images/generations` mit `model: "copilot-m365-web/m365-copilot-image"` (alias `m365copilot/m365-copilot-image`) zeichnet wie der Webclient mit dem integrierten Bildtool von Copilot. Jedes Bild ist eine Copilot Runde: Es wird mit den Bildoptionssätzen des Web-Clients aktiviert und `GenerateGraphicArt` deklariert, und das Bild kommt in einem Fortschrittseintrag an, der auf ein Artefakt im Designer-Dienst von Microsoft verweist. Dieses Artefakt lehnt das Chat-Token ab, also prägt OmniRoute ein Designer-Token aus dem Aktualisierungstoken der Verbindung und lädt die Bytes herunter; Der Token wird immer nur an `designerapp.officeapps.live.com` gesendet.

- Benötigt eine native Anmeldeverbindung (ein Aktualisierungstoken); Ein eingefügtes Token schlägt fehl** 400** bevor eine Runde beendet ist.
- `n` ist 1–4, jeweils eine Runde. `size` steuert nur die Ausrichtung (breiter, höher oder quadratisch), was Copilot aus der Eingabeaufforderung liest; Copilot wählt die Rendergröße aus.
- Bilder werden inline zurückgegeben: standardmäßig `b64_json`, Daten URL für `response_format: "url"`.
- Für die generierten Bilder wird unabhängig vom Chat ein kleines Tagesbudget benötigt. Wenn es aufgebraucht ist, schlägt die Anfrage fehl** 429** . Ein Zug, der ohne Bild antwortet, schlägt mit fehl** 502** (oder** 400** /** 503** wenn sich der Text von Copilot als Ablehnung oder Kapazitätsproblem liest); Die Nachricht sagt welche.

## Sicherheitsmodell

- **Inoffizielle Integration.** Dieser Anbieter entwickelt das BizChat WebSocket Protokoll zurück. Es kann ohne Vorankündigung abbrechen, wenn Microsoft den Endpunkt ändert.
- Das `subscriptionRisk: true` Flag spiegelt wider, dass die Integration auf einem undokumentierten Endpunkt basiert. Kontobeschränkungen sind möglich, aber nicht bestätigt.
- Das Zugriffstoken ist ein kurzlebiges JWT. Behandeln Sie es wie ein Passwort: Übernehmen, protokollieren oder teilen Sie es nicht.
- Das Aktualisierungstoken gewährt fortlaufenden Zugriff auf die Microsoft 365-Oberfläche. Bewahren Sie ihn mit der gleichen Sorgfalt auf wie einen API -Schlüssel.

## Fehlerbehebung

### Die Authentifizierung schlägt sofort fehl

- Stellen Sie sicher, dass Sie von kopiert haben**WebSocket URL** , nicht aus einer XHR/Fetch Anfrage. Die Anmeldeinformationen befinden sich im `access_token` Abfrageparameter der Chathub WebSocket Verbindung — nicht in einem `Authorization: Bearer` Header.
- Stellen Sie sicher, dass die `chathubPath` das vollständige `<oid>@<tenant>` Segment aus dem URL Pfad enthält.

### Der Token läuft nach ~ 75 Minuten ab

Dies wird erwartet. Ohne `refreshToken` ist das Zugriffstoken nur von kurzer Dauer. Entweder:

- Erfassen Sie die Anmeldeinformationen erneut von DevTools oder
- Konfigurieren** Erweiterte Einstellungen → Aktualisierungstoken (optional)** im Dialogfeld „Verbindung hinzufügen oder bearbeiten“ für die automatische Aktualisierung.

### Die Testverbindung ist erfolgreich, aber der Chat gibt 401 zurück

Für eine Verbindung erstellt mit** Melden Sie sich mit Microsoft an** , Test Connection überprüft den Ablauf des Zugriffstokens und erneuert einen abgelaufenen Token mit dem gespeicherten Aktualisierungstoken, sodass ein bestandener Test auch beweist, dass der Aktualisierungstoken noch funktioniert.

Bei eingefügten Anmeldeinformationen überprüft Test Connection die Form der Anmeldeinformationen und stellt, wenn das Token ein Ablaufdatum aufweist, sicher, dass das Token, das der Anbieter verwenden würde, nicht abgelaufen ist (das gespeicherte Token der Verbindung gewinnt ein veraltetes Einfügen; ein Aktualisierungstoken gilt als erneuerbar). Ein Token, der vor Ablauf widerrufen wird, besteht den Test dennoch; Der Chat kehrt dann zurück** 401** `m365_unauthorized`. Verwenden** Melden Sie sich mit Microsoft an** erneut oder erfassen Sie einen neuen Ausweis erneut.

### Copilot erscheint nicht in der Anbieterliste

Stellen Sie sicher, dass `copilot-m365-web` aktiviert ist** Dashboard → Anbieter** . Der Anbieter ist in einigen Ebenen möglicherweise standardmäßig ausgeblendet.
