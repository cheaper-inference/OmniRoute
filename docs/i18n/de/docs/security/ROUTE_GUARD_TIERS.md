## Übersicht

Alle Routen der OmniRoute-Verwaltungs-API sind einer von drei Schutzstufen zugeordnet. Die Klassifizierung ist statisch, wird in `src/server/authz/routeGuard.ts` definiert und ausgewertet, bevor ein anderer Authentifizierungszweig ausgeführt wird.

## Ebenen

### Tier 1 — LOCAL_ONLY

**Durchgesetzt durch:** Überprüfung `isLocalOnlyPath(path)` → -Loopback-Hosts** Bypass:** Standardmäßig keine. Enge Ausgliederung für Pfade in `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` wenn die Anfrage einen gültigen API Schlüssel mit dem `manage` Bereich enthält (siehe [Ausgliederung des Bereichs verwalten](#manage-scope-carve-out) ).

Diese Routen erzeugen untergeordnete Prozesse oder führen Laufzeitcode aus. Wenn man sie dem Nicht-Loopback-Verkehr aussetzt, kann ein Angreifer, der ein gültiges JWT erhalten hat (z. B. über einen Cloudflared/Ngrok Tunnel), einen Prozess auslösen, der eine bekannte CVE Klasse ( [GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj) ) — erzeugt.

**Was GHSA-fhh6-4qxv-rpqj ist (die Angriffsklasse):** Ein management/agent Server stellt einen Endpunkt bereit, der einen Unterprozess startet (`npm install`, `node`, ein Browser, ein Proxy, `git`, `tar`, …). Wenn dieser Endpunkt von — außerhalb des Hosts erreichbar ist, weil der Betreiber OmniRoute hinter einen nginx/Cloudflare/Tailscale Tunnel gelegt hat und ein JWT durchgesickert ist oder die Authentifizierung falsch konfiguriert wurde — wandelt der Angreifer „einen API aufrufen“ in „einen Befehl auf dem Host ausführen“ um (Remote-Code-Ausführung). OmniRoute schließt dies, indem es a erzwingt** Loopback-Hostprüfung bedingungslos vor jeder Authentifizierungsprüfung** , auf jeder Spawn-fähigen Route: Ein über einen Tunnel durchgesickerter Token kann den Spawn immer noch nicht erreichen.

**Das komplette LOCAL_ONLY Set.** Die maßgebliche Quelle ist `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` in `src/server/authz/routeGuard.ts`; Die folgende Tabelle spiegelt den aktuellen Stand wider. Das `check-route-guard-membership` Gate listet jedes `route.ts` unter den spawnfähigen Präfixen auf und schlägt CI fehl, wenn eines davon nicht nur lokal klassifiziert ist.

**Reaktion auf Verstoß:** `403 LOCAL_ONLY`

#### Ausgliederung des Umfangs verwalten

Auf eine Teilmenge der LOCAL_ONLY -Pfade MAY kann auch von Nicht-Loopback genau dann zugegriffen werden, wenn die Anforderung einen `Authorization: Bearer <api-key>` enthält, dessen Metadaten den `manage` Bereich (oder `admin`) enthalten. Die Ausgliederung wird explizit pro Pfad über `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` gesteuert, sodass die Standardeinstellung für jeden neuen LOCAL_ONLY Pfad weiterhin der strikte Loopback ist. Nicht authentifizierte Anfragen und Anfragen mit nicht verwalteten Schlüsseln werden weiterhin mit `403 LOCAL_ONLY` abgelehnt.

Heute ist `/api/mcp/` das einzige umgehbare Präfix. `/api/cli-tools/runtime/` und `/api/services/` werden absichtlich ausgeschlossen, da sie beliebige Unterprozesse (`npm install`, `node`) erzeugen können. Dies ist genau die CVE Klasse, die die LOCAL_ONLY Ebene verhindern soll.

**#7895 — `mcp:connect` enger Geltungsbereich:** Die `/api/mcp/` -Ausgliederung ALSO akzeptiert einen Bearer-Schlüssel, der den engen `mcp:connect` Bereich (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`) enthält und über `hasMcpConnectOrManageScope()` in `src/server/authz/policies/management.ts` überprüft wird. Dies gilt für `/api/mcp/` ONLY — `mcp:connect` gewährt auf keiner anderen Verwaltungsroute (einschließlich aller anderen LOCAL_ONLY -Bypass-Präfixe, falls jemals eines hinzugefügt werden sollte) nichts und wird absichtlich von `MANAGEMENT_API_KEY_SCOPES` ausgeschlossen. Ein Schlüssel, der `manage`/`admin` hält, durchläuft die Ausgliederung immer noch genau wie zuvor; `mcp:connect` ist eine Alternative mit geringeren Berechtigungen für Remote-MCP-Anrufer, die keinen umfassenden Verwaltungszugriff benötigen sollten.

| Anfrage                                            | Weg                        | Ergebnis              |
| -------------------------------------------------- | -------------------------- | --------------------- |
| Kein Loopback, kein Träger                         | `/api/mcp/*`               | 403 LOCAL_ONLY        |
| Nicht-Loopback, Träger mit `manage` Bereich        | `/api/mcp/*`               | Erlauben              |
| Nicht-Loopback, Träger mit `mcp:connect` Bereich   | `/api/mcp/*`               | Erlauben              |
| Nicht-Loopback, Träger ohne `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY        |

| Nicht-Loopback, Träger mit `manage` Bereich        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY        |
| Loopback, any/no Bearer                            | LOCAL_ONLY                 | Zulassen (Gate-Pässe) |

#### Bedienerführung und Auditierung

Wenn Sie OmniRoute hinter einem Reverse-Proxy oder Tunnel (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok) ausführen, schützt die Loopback-Prüfung weiterhin die Spawn-fähigen Routen über — Eine Anfrage, deren Client-Adresse kein Loopback ist, wird mit `403 LOCAL_ONLY` abgelehnt** bevor die Authentifizierung ausgeführt wird** , sodass ein durchgesickertes JWT keinen Spawn erreichen kann. Es bleiben zwei Betreiberpflichten bestehen:

- **Reparieren Sie einen 403-Fehler nicht, indem Sie die Client- IP als Loopback fälschen.** Durch das Festlegen `X-Forwarded-For: 127.0.0.1` oder eines Proxys, der die Quelladresse in Loopback umschreibt, wird genau die RCE Klasse erneut geöffnet, die diese Ebene schließt. Stellen Sie den dashboard/API über den Proxy- — niemals den Spawn-fähigen Routen zur Verfügung.
- **Halten Sie die Umgehung des Verwaltungsbereichs minimal.** Nur `/api/mcp/` kann umgangen werden, und zwar nur mit einem `manage` -scoped API -Schlüssel. Die `SPAWN_CAPABLE_PREFIXES` können niemals zur Umgehungsliste — hinzugefügt werden, da das ZOD-Schema sie ablehnt und `isLocalOnlyBypassableByManageScope` sie zur Laufzeit ablehnt (Defense-in-Depth), was das Dashboard mit „kann nicht umgehbar gemacht werden“ meint. Die gleiche Verweigerungsliste enthält auch einige LOCAL_ONLY Routen, die nicht erzeugt werden, aber niemals aus der Ferne erreichbar sein dürfen, — `/api/oauth/kiro/auto-import` (liest hostlokale Kiro Anmeldeinformationen), `/api/discovery/` und `/api/issue-agent/`. Der Runtime-Snapshot-Loader löscht solche Einträge auch aus einer Zeile mit gespeicherten Einstellungen, und der alte JSON -Import (`/api/settings/import-json`) schreibt niemals die Umgehungsschlüssel. Jeder `LOCAL_ONLY_API_PREFIXES` Eintrag muss entweder in der Verweigerungsliste enthalten sein oder als umgehbar (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`) überprüft werden. Spawn-fähige Routen für dynamische Segmente und statische Pfade unter `/api/providers/` (z. B. `/login`, `/refresh-cursor`) werden durch den Regex-basierten `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` -Begleiter in `src/shared/constants/spawnCapablePrefixes.ts` abgedeckt, nicht durch das flache `SPAWN_CAPABLE_PREFIXES` Array — Das flache Array müsste das gesamte `/api/providers/` Präfix abdecken, um sie abzufangen, wodurch ein Routenbaum, den Remote-Dashboards rechtmäßig für den Anbieter CRUD verwenden, übermäßig erweitert wird.

**Prüfzugriff** —, um sicherzustellen, dass nichts außerhalb des Hosts diese Routen erreicht:

- Öffnen Sie die** Autorisierungsinventar** auf `/dashboard/settings/security`: Es rendert die Live- LOCAL_ONLY -Präfixliste, welche Präfixe umgangen werden können, und legt die Spawn-Fähigkeit zur Kompilierungszeit fest („kann nicht umgehbar gemacht werden“).
- Suchen Sie in Ihren Reverse-Proxy-/Zugriffsprotokollen nach den oben genannten Präfixen gepaart mit einer Nicht-Loopback-Client-Adresse. Jeder Treffer, der `200` anstelle von `403 LOCAL_ONLY` zurückgibt, bedeutet, dass der Proxy den echten Client maskiert. IP — repariert den Proxy.
- Ein `403 LOCAL_ONLY` in den Protokollen von OmniRoute für einen dieser Pfade bedeutet, dass der Wächter wie vorgesehen funktioniert, kein Fehler, der unterdrückt werden muss.

#### Aus der Ferne erreichbare Routen mit einem Call-Site-Probe-Gate

Einige Routen müssen von einem Remote-Dashboard aus erreichbar bleiben, aber eine hostseitige Prüfung (`which <binary>`, `<binary> --version`, `tailscale status --json`) für lokale Anrufer ausführen. Sie sind nicht LOCAL_ONLY für `GET`; Stattdessen liest der Handler das Urteil über den vertrauenswürdigen Peer mit `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) und führt die Prüfung nur für `loopback` / `lan` Aufrufer aus. Ein `remote` Aufrufer erhält die gleiche Antwortform, die aus nicht-spawnenden Quellen (persistenter Status, Einstellungen, FS-Prüfungen) erstellt wurde, markiert mit `probed: false`.

| Route                                                            | Probe für Remote-Anrufer übersprungen                               |
| ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI Laufzeitprobe (`allowLocalRuntimeProbe`) und CLI-Fallback-Spawn |
| `GET /api/headroom/status`                                       | `which headroom` und die Python- `--version` Sonden                 |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`   |
| `GET /api/tunnels/cloudflared` (GET-ausgenommen von LOCAL_ONLY)  | `which cloudflared` PATH                                            |

Eine neue Leseroute, die den Host prüft, folgt demselben Muster oder wird direkt LOCAL_ONLY klassifiziert.

GHSA-62vw hat nur die Enthüllung `GET` -Passworts maskiert; Die Emission befand sich immer noch auf der Fail-Open-Stufe (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` lehnt außerdem einen Tresor ab, der sich darin befindet oder das Datenverzeichnis enthält.

#### Das Exportieren und Wiederherstellen von Anmeldeinformationen ist nur dem Bediener vorbehalten

Die darüber liegende Ebene entscheidet nur, ob _irgendeine_ Anmeldeinformationen erforderlich sind. Die Routen, die gespeicherte Anmeldeinformationen herunterladen, fügen eine zweite Prüfung im Handler hinzu: `GET /api/settings/export-json` (entschlüsselte Anbieterverbindungen und rohe API Schlüssel), `GET /api/db-backups/export` (die SQLite Datei) und `GET /api/db-backups/exportAll` (das vollständige Archiv) rufen `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`) auf. Es akzeptiert eine Dashboard-Sitzung, das lokale CLI Subjekt oder eine Instanz mit deaktivierter Anmeldung und antwortet `403` auf API Schlüssel eines beliebigen Bereichs (einschließlich `manage` und `admin`) und auf `oma_` Zugriffstokens. Die destruktiven Gegenstücke haben die gleiche Grenze: `POST /api/db-backups/import` (hochgeladenes `.sqlite`, einschließlich `dryRun=true` ), `POST /api/db-backups` (ein gespeichertes Backup nach ID wiederherstellen) und `POST /api/settings/import-json` (alte JSON -Wiederherstellung) ersetzen die Live-Datenbank oder den gesamten settings/connections/API-key Satz, sodass sie auch nicht durch Anmeldeinformationen eines Computers ausgelöst werden können. Für das Zerstören von Wiederherstellungspunkten gilt die gleiche Grenze: `DELETE /api/db-backups` (Bereinigung — hält die neuesten N/Drops älter als D Tage) und `PATCH /api/db-backups` (Aufbewahrungseinstellungen), da die dauerhafte Aufbewahrung genau das ist, was `cleanupDbBackups()` nach jeder automatischen Sicherung anwendet (`src/lib/db/backup.ts`), sodass eine Maschinenanmeldeinformation, die `keepLatest: 1` speichern könnte, beim nächsten Snapshot alles bereinigen würde. Beim Auflisten und Erstellen von Backups (`GET`/`PUT /api/db-backups`) bleibt die normale Verwaltungsauthentifizierung erhalten. Die Ausstellung des Synchronisierungstokens (`POST /api/sync/tokens`) verwendet denselben Helfer sowie das vertrauenswürdige Loopback-Token für den internen Dienst.

### Beim Neuinstallations-Bootstrap handelt es sich um ein reines Loopback- — von einem echten Peer, nicht `Host`

Wenn kein Verwaltungskennwort konfiguriert ist (und kein `INITIAL_PASSWORD`), hält `isAuthRequired()` in `src/shared/utils/apiAuth.ts` den anonymen Bootstrap offen** nur für Loopback-Peers** . Loopback wird anhand der vertrauenswürdigen Peer-Signale entschieden, in der Reihenfolge: der mit einem Token versehene echte TCP Peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, was die Richtlinie sieht), das eigene `AUTHZ_HEADER_PEER_LOCALITY` -Urteil der Pipeline (was Routenhandler sehen, nur vertrauenswürdig, solange `OMNIROUTE_PEER_STAMP_TOKEN` festgelegt ist) oder ein echter Socket-Peer für direkte Aufrufer. `Host` / `nextUrl.hostname` werden nie konsultiert, und das Schreiben des ersten Passworts (`POST /api/settings/require-login`) unterliegt derselben Einschränkung und ist nicht für jeden Netzwerk-Peer (GHSA-7pq4-8pvv-rx7r) offen. `managementPolicy` gibt sein eigenes `peerContext` -Urteil explizit weiter, sodass die Header der ORIGINAL Anfrage (Pre-Strip) niemals darüber entscheiden.

### Tier 3 — MANAGEMENT (Standard)

Alle anderen Verwaltungsrouten. Authentifizierung erforderlich, es sei denn, `requireLogin=false` ist konfiguriert. CLI -Tokens können diese Routen authentifizieren (Loopback + valid HMAC).

## Auswertungsreihenfolge

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → Loopback                                   → weiter
     → kein Loopback, Bearer mit manage-Berechtigungsumfang
        UND isLocalOnlyBypassableByManageScope    → zulassen (management_key)
     → andernfalls                               → ablehnen 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → zulassen (system)
  3. hasValidCliToken(headers)?
     → zulassen (cli) [Loopback + timingSafeEqual-HMAC-Prüfung]
  4. isAlwaysProtectedPath(path) oder requireLogin=true?
     → isDashboardSessionAuthenticated?
        → zulassen (dashboard_session)
     → Bearer mit manage-Berechtigungsumfang auf einem nicht umgehbaren Pfad?
        → zulassen (management_key)
     → ablehnen 401/403
  5. requireLogin=false?
     → zulassen (anonymous)
```

Der Zweig für den manage-Berechtigungsumfang in Schritt 1 ist der einzige authentifizierte Pfad, der eine
LOCAL_ONLY-Route erfüllen kann; der Fehlermodus des Authentifizierungs-Backends gibt 503 (nicht 403) zurück, damit eine
abgelaufene DB nicht stillschweigend auf „ablehnen“ zurückfällt.

## Hinzufügen einer neuen Spawn-fähigen Route

1. Fügen Sie das Pfadpräfix zu `LOCAL_ONLY_API_PREFIXES` in `src/server/authz/routeGuard.ts` hinzu
2. Fügen Sie in `tests/unit/authz/routeGuard.test.ts` einen Test hinzu, der bestätigt, dass `isLocalOnlyPath()` für das neue Präfix „true“ zurückgibt
3. **Überspringen Sie diesen Schritt niemals** — siehe Hard Rule #15 in `CLAUDE.md`
4. Entscheiden Sie: Gehört diese Route ALSO zu `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`? Die Standardantwort lautet** NEIN** . Melden Sie sich nur an, wenn die Route sicher einem Inhaber des Verwaltungsbereichs zugänglich gemacht werden kann (z. B. generiert NOT beliebigen benutzergesteuerten Code).

## Hinzufügen eines Pfads, der mit manage-Berechtigungsumfang umgangen werden kann

1. Stelle sicher, dass die Route keinen vom Benutzer bereitgestellten Code oder entsprechende Befehle ausführt. Falls doch,
   brich ab — diese Ausnahme ist dafür das falsche Werkzeug.
2. Hänge das Präfix an `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` in
   `src/server/authz/routeGuard.ts` an
3. Füge in `tests/unit/authz/management-policy.test.ts` Testabdeckung für alle vier
   Anfragevarianten hinzu: kein Bearer (403), manage-Bearer (zulassen), Nicht-manage-Bearer
   (403) sowie den präfixspezifischen Regressionstest, dass `/api/cli-tools/runtime/*` selbst
   mit einem manage-Bearer strikt auf Loopback beschränkt bleibt.

## Dokumentieren von Sicherheitsstufen in OpenAPI

Wende beim Hinzufügen einer neuen Route zu `docs/openapi.yaml` die entsprechende
Herstellererweiterung an, wenn die Route durch `routeGuard.ts` klassifiziert wird:

| routeGuard.ts-Klassifizierung                  | YAML-Annotation                 | Durchsetzung                                                 |
| ---------------------------------------------- | ------------------------------- | ------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                      | `x-loopback-only: true`         | Von Nicht-Loopback-Verbindungen bedingungslos blockiert      |
| `ALWAYS_PROTECTED_API_PATHS`                   | `x-always-protected: true`      | Authentifizierung auch bei `requireLogin=false` erforderlich |
| Interne Admin-/Debug-Route                     | `x-internal: true`              | Standardmäßig vor /dashboard/api-endpoints verborgen         |
| Keine (öffentlich / Standardauthentifizierung) | (keine Annotation erforderlich) | Standardzugriff, gesteuert durch `requireLogin`              |

### Validierung

Zwei Skripte erzwingen die Konsistenz zwischen YAML-Annotationen und `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — schlägt fehl, wenn die Abdeckung < 99% ist
- `scripts/check/check-openapi-security-tiers.mjs` — schlägt fehl, wenn `x-loopback-only`- oder
  `x-always-protected`-Annotationen von den Konstanten zur Kompilierzeit abweichen

Beide Skripte werden im Pre-Commit-Hook und in CI ausgeführt.

### Regel für falsch-positive Ergebnisse

Wenn `x-always-protected` oder `x-loopback-only` für eine Route annotiert ist, die NICHT in
der `routeGuard.ts`-Konstante enthalten ist, schlägt das Abdeckungsskript fehl. Die Lösung besteht immer darin, das
YAML an die tatsächliche Durchsetzung durch `routeGuard.ts` anzupassen — nicht darin, Routen zu `routeGuard.ts`
hinzuzufügen, ohne zugleich die Durchsetzungslogik zu implementieren.
