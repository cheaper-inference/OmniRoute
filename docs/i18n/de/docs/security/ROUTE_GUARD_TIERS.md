## Übersicht

Alle Routen der OmniRoute-Verwaltungs-API sind einer von drei Schutzstufen zugeordnet. Die Klassifizierung ist statisch, wird in `src/server/authz/routeGuard.ts` definiert und ausgewertet, bevor ein anderer Authentifizierungszweig ausgeführt wird.

## Stufen

### Stufe 1 — LOCAL_ONLY

**Durchgesetzt durch:** `isLocalOnlyPath(path)` → Loopback-Host-Prüfung
**Umgehung:** Standardmäßig keine. Eng gefasste Ausnahme für Pfade in
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, wenn die Anfrage einen gültigen
API-Schlüssel mit dem Scope `manage` enthält (siehe [Manage-Scope-Ausnahme](#manage-scope-carve-out)).

Diese Routen starten Kindprozesse oder führen Laufzeitcode aus. Würden sie für
Nicht-Loopback-Verkehr geöffnet, könnte ein Angreifer, der ein gültiges JWT
erlangt hat (z. B. über einen Cloudflared/Ngrok-Tunnel), das Starten von
Prozessen auslösen — eine bekannte CVE-Klasse
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Was GHSA-fhh6-4qxv-rpqj ist (die Angriffsklasse):** Ein Management-/Agent-Server
stellt einen Endpunkt bereit, der einen Unterprozess startet (`npm install`, `node`,
einen Browser, einen Proxy, `git`, `tar`, …). Ist dieser Endpunkt von außerhalb des
Hosts erreichbar — etwa weil der Betreiber OmniRoute hinter einen
nginx/Cloudflare/Tailscale-Tunnel gestellt hat und ein JWT durchgesickert ist oder
die Authentifizierung falsch konfiguriert war — verwandelt der Angreifer „eine API
aufrufen" in „einen Befehl auf dem Host ausführen" (Remote Code Execution).
OmniRoute schließt diese Lücke, indem es auf jeder spawn-fähigen Route
**unbedingt und vor jeder Authentifizierungsprüfung eine Loopback-Host-Prüfung**
erzwingt: Ein über einen Tunnel durchgesickertes Token erreicht den Prozessstart
dennoch nicht.

**Der vollständige LOCAL_ONLY-Satz.** Die maßgebliche Quelle sind
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` in
`src/server/authz/routeGuard.ts`; die folgende Tabelle bildet den aktuellen Stand
ab. Das Gate `check-route-guard-membership` zählt jede `route.ts` unter den
spawn-fähigen Präfixen auf und lässt die CI fehlschlagen, falls eine davon nicht
als local-only klassifiziert ist.

#### Ausnahme für den Manage-Scope

Eine Teilmenge der LOCAL_ONLY-Pfade DARF auch von Nicht-Loopback-Adressen aus
aufgerufen werden, wenn und nur wenn die Anfrage einen
`Authorization: Bearer <api-key>` enthält, dessen Metadaten den Scope `manage`
(oder `admin`) umfassen. Die Ausnahme wird explizit pro Pfad über
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` gesteuert, sodass die Vorgabe für jeden
neuen LOCAL_ONLY-Pfad strikt Loopback bleibt. Nicht authentifizierte Anfragen
und Anfragen mit Schlüsseln ohne manage-Scope werden weiterhin mit
`403 LOCAL_ONLY` abgelehnt.

Derzeit ist `/api/mcp/` das einzige umgehbare Präfix. `/api/cli-tools/runtime/`
und `/api/services/` sind bewusst ausgeschlossen, da sie beliebige Subprozesse
starten können (`npm install`, `node`) — genau die CVE-Klasse, deren Verhinderung
die LOCAL_ONLY-Stufe dient.

**#7895 — `mcp:connect` als eingeschränkter Scope:** Die `/api/mcp/`-Ausnahme
akzeptiert AUSSERDEM einen Bearer-Schlüssel mit dem engen Scope `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), geprüft über
`hasMcpConnectOrManageScope()` in `src/server/authz/policies/management.ts`.
Dies gilt NUR für `/api/mcp/` — `mcp:connect` gewährt keinerlei Zugriff auf
andere Management-Routen (einschließlich aller anderen
LOCAL_ONLY-Bypass-Präfixe, sollten jemals welche hinzukommen) und ist bewusst
aus `MANAGEMENT_API_KEY_SCOPES` ausgenommen. Ein Schlüssel mit `manage`/`admin`
passiert die Ausnahme weiterhin genau wie zuvor; `mcp:connect` ist eine
Alternative mit geringeren Rechten für reine Remote-MCP-Aufrufer, die keinen
weitreichenden Management-Zugriff benötigen sollten.

| Anfrage                                            | Pfad                       | Ergebnis                 |
| -------------------------------------------------- | -------------------------- | ------------------------ |
| Nicht-Loopback, kein Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY           |
| Nicht-Loopback, Bearer mit Scope `manage`          | `/api/mcp/*`               | Zulässig                 |
| Nicht-Loopback, Bearer mit Scope `mcp:connect`     | `/api/mcp/*`               | Zulässig                 |
| Nicht-Loopback, Bearer ohne `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY           |
| Nicht-Loopback, Bearer mit Scope `mcp:connect`     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY           |
| Nicht-Loopback, Bearer mit Scope `manage`          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY           |
| Loopback, beliebiger/kein Bearer                   | beliebiger LOCAL_ONLY-Pfad | Zulässig (Gate passiert) |

#### Hinweise für Betreiber & Auditing

Wenn Sie OmniRoute hinter einem Reverse-Proxy oder Tunnel betreiben (nginx,
Caddy, Cloudflare Tunnel, Tailscale, Ngrok), schützt die Loopback-Prüfung die
oben genannten spawn-fähigen Routen weiterhin — eine Anfrage, deren
Client-Adresse nicht Loopback ist, wird mit `403 LOCAL_ONLY` abgelehnt, **bevor
die Authentifizierung läuft**, sodass ein kompromittiertes JWT keinen Spawn
erreichen kann. Zwei Verantwortlichkeiten des Betreibers bleiben bestehen:

- **„Beheben“ Sie einen 403 nicht, indem Sie die Client-IP als Loopback fälschen.** Das Setzen von
  `X-Forwarded-For: 127.0.0.1` oder ein Proxy, der die Quelladresse auf
  Loopback umschreibt, öffnet genau die RCE-Klasse wieder, die diese Stufe schließt. Exponieren Sie das
  Dashboard/die API über den Proxy — niemals die spawn-fähigen Routen.
- **Halten Sie die Umgehung per `manage`-Scope minimal.** Nur `/api/mcp/` ist umgehbar, und
  nur mit einem API-Schlüssel mit `manage`-Scope. Die `SPAWN_CAPABLE_PREFIXES` können niemals
  zur Umgehungsliste hinzugefügt werden — das Zod-Schema lehnt sie ab und
  `isLocalOnlyBypassableByManageScope` verweigert sie zur Laufzeit (Defence-in-Depth);
  das ist es, was das Dashboard mit „kann nicht umgehbar gemacht werden“ meint. Dieselbe
  Deny-Liste enthält außerdem einige LOCAL_ONLY-Routen, die nichts spawnen, aber ebenfalls niemals
  aus der Ferne erreichbar sein dürfen — `/api/oauth/kiro/auto-import` (liest host-lokale Kiro-
  Anmeldedateien), `/api/discovery/` und `/api/issue-agent/`. Der
  Laufzeit-Snapshot-Loader verwirft solche Einträge ebenfalls aus einer gespeicherten Einstellungszeile, und der
  Legacy-JSON-Import (`/api/settings/import-json`) schreibt die Umgehungsschlüssel niemals.
  Jeder `LOCAL_ONLY_API_PREFIXES`-Eintrag muss entweder in der Deny-Liste stehen oder
  als umgehungsfähig geprüft worden sein (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Spawn-fähige
  Routen mit dynamischen Segmenten und statischen Pfaden unter `/api/providers/` (z. B. `/login`,
  `/refresh-cursor`) werden durch den regex-basierten Begleiter `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` in
  `src/shared/constants/spawnCapablePrefixes.ts` abgedeckt, nicht durch das flache
  `SPAWN_CAPABLE_PREFIXES`-Array — das flache Array müsste das gesamte
  `/api/providers/`-Präfix abdecken, um sie zu erfassen, und würde damit einen Routenbaum
  zu weit fassen, den entfernte Dashboards legitim für Provider-CRUD nutzen.

**Zugriffe auditieren** — um zu prüfen, dass nichts von außerhalb des Hosts diese Routen erreicht:

- Öffnen Sie das **Authorization Inventory** unter `/dashboard/settings/security`: Es zeigt die
  Live-Liste der LOCAL_ONLY-Präfixe, welche Präfixe umgehbar sind, und die zur Compile-Zeit
  festgelegte spawn-fähige Menge („kann nicht umgehbar gemacht werden“).
- Durchsuchen Sie Ihre Reverse-Proxy-/Access-Logs mit grep nach den obigen Präfixen in Kombination mit einer
  Nicht-Loopback-Client-Adresse. Jeder solche Treffer, der `200` statt
  `403 LOCAL_ONLY` zurückgab, bedeutet, dass der Proxy die echte Client-IP maskiert — korrigieren Sie den Proxy.
- Ein `403 LOCAL_ONLY` in den Logs von OmniRoute für einen dieser Pfade ist der Guard,
  der wie vorgesehen arbeitet — kein Fehler, den man unterdrücken sollte.

#### Aus der Ferne erreichbare Routen mit Probe-Gate am Aufrufort

Einige Routen müssen von einem entfernten Dashboard aus erreichbar bleiben, führen aber für lokale Aufrufer
eine host-seitige Probe aus (`which <binary>`, `<binary> --version`, `tailscale status --json`).
Sie sind für `GET` nicht LOCAL_ONLY; stattdessen liest der Handler die vertrauenswürdige Peer-Einstufung
mit `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) und führt die Probe
nur für `loopback`-/`lan`-Aufrufer aus. Ein `remote`-Aufrufer erhält dieselbe Antwortstruktur,
aufgebaut aus nicht-spawnenden Quellen (persistierter Zustand, Einstellungen, Dateisystemprüfungen), gekennzeichnet mit `probed: false`.

| Route                                                               | Für Remote-Aufrufer übersprungene Probe                              |
| ------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`        | CLI-Laufzeit-Probe (`allowLocalRuntimeProbe`) und CLI-Fallback-Spawn |
| `GET /api/headroom/status`                                          | `which headroom` und die Python-`--version`-Probes                   |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check`    | `which tailscale`, `tailscale status/funnel --json`, `which brew`    |
| `GET /api/tunnels/cloudflared` (für GET von LOCAL_ONLY ausgenommen) | `which cloudflared`-PATH-Lookup                                      |

Eine neue Leseroute, die den Host prüft, folgt demselben Muster oder wird direkt als
LOCAL_ONLY klassifiziert.

### Stufe 2 — ALWAYS_PROTECTED

**Durchgesetzt durch:** `isAlwaysProtectedPath(path)` → überspringt die `requireLogin=false`-Umgehung
**Umgehung:** Keine bei `requireLogin=false`; JWT immer erforderlich

Diese Routen sind destruktiv oder irreversibel. Sie in einer Installation „ohne Passwort“
zuzulassen, würde bedeuten, dass jeder im selben LAN die Datenbank löschen oder den

`/api/settings/obsidian` deckt sein `/webdav`-Kind ab: `POST` richtet den WebDAV-Dateidienst —
der von der benutzerdefinierten Node-Schicht vor Next.js bereitgestellt wird, außerhalb dieser Pipeline —

`DELETE` rotiert sie, und das übergeordnete `POST` speichert das Obsidian-REST-API-Token.
GHSA-62vw hat nur die Passwort-Preisgabe per `GET` kaschiert; die Ausstellung befand sich weiterhin
auf der Fail-open-Stufe (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` verweigert zusätzlich
einen Vault, der das Datenverzeichnis ist, darin liegt oder es enthält.

#### Exporte und Wiederherstellungen von Zugangsdaten sind nur für Operatoren zulässig

Die obige Stufe entscheidet nur, ob _irgendein_ Credential erforderlich ist. Die Routen, die
gespeicherte Zugangsdaten herunterladen, fügen im Handler eine zweite Prüfung hinzu:
`GET /api/settings/export-json` (entschlüsselte Provider-Verbindungen und rohe API-Schlüssel),
`GET /api/db-backups/export` (die SQLite-Datei) und `GET /api/db-backups/exportAll` (das
vollständige Archiv) rufen `requireOperatorCredential()` auf
(`src/lib/api/operatorCredential.ts`). Es akzeptiert eine Dashboard-Sitzung, das lokale
CLI-Subjekt oder eine Instanz mit deaktiviertem Login und antwortet API-Schlüsseln jedes
Geltungsbereichs (einschließlich `manage` und `admin`) sowie `oma_`-Zugriffstoken mit `403`.
Die destruktiven Gegenstücke halten dieselbe Grenze ein: `POST /api/db-backups/import`
(hochgeladene `.sqlite`, einschließlich `dryRun=true`), `POST /api/db-backups` (Wiederherstellung
eines gespeicherten Backups anhand der ID) und `POST /api/settings/import-json`
(Legacy-JSON-Wiederherstellung) ersetzen die Live-Datenbank oder den gesamten Satz aus
Einstellungen/Verbindungen/API-Schlüsseln, sodass ein maschinelles Credential sie ebenfalls nicht
auslösen kann. Das Löschen von Wiederherstellungspunkten hält dieselbe Grenze ein:
`DELETE /api/db-backups` (Aufräumen — die letzten N behalten / ältere als D Tage verwerfen) und
`PATCH /api/db-backups` (Aufbewahrungseinstellungen), denn die persistierte Aufbewahrung ist genau
das, was `cleanupDbBackups()` nach jedem automatischen Backup anwendet
(`src/lib/db/backup.ts`), sodass ein maschinelles Credential, das `keepLatest: 1` speichern
könnte, beim nächsten Snapshot alles kürzen würde. Auflisten und Erstellen von Backups
(`GET`/`PUT /api/db-backups`) behalten die gewöhnliche Management-Authentifizierung. Die
Ausstellung von Sync-Tokens (`POST /api/sync/tokens`) verwendet denselben Helfer, plus das
vertrauenswürdige Loopback-Internal-Service-Token.

### Der Bootstrap einer Neuinstallation ist nur per Loopback möglich — anhand des echten Peers, nicht `Host`

Wenn kein Management-Passwort konfiguriert ist (und kein `INITIAL_PASSWORD`), hält
`isAuthRequired()` in `src/shared/utils/apiAuth.ts` den anonymen Bootstrap **nur für
Loopback-Peers** offen. Loopback wird aus den vertrauenswürdigen Peer-Signalen entschieden, in
dieser Reihenfolge: der mit Token gestempelte echte TCP-Peer (`PEER_IP_HEADER` +
`VIA_PROXY_HEADER`, was die Policy sieht), das eigene `AUTHZ_HEADER_PEER_LOCALITY`-Urteil der
Pipeline (was die Routen-Handler sehen, nur vertrauenswürdig, solange
`OMNIROUTE_PEER_STAMP_TOKEN` gesetzt ist) oder ein echter Socket-Peer für direkte Aufrufer.
`Host` / `nextUrl.hostname` werden niemals herangezogen, und das Schreiben des ersten Passworts
(`POST /api/settings/require-login`) unterliegt derselben Einschränkung, statt für jeden
Netzwerk-Peer offen zu sein (GHSA-7pq4-8pvv-rx7r). `managementPolicy` gibt sein eigenes
`peerContext`-Urteil explizit nach unten weiter, sodass die Header des ORIGINAL-Requests
(vor dem Entfernen) es niemals entscheiden.

### Stufe 3 — MANAGEMENT (Standard)

Alle anderen Management-Routen. Authentifizierung erforderlich, es sei denn, `requireLogin=false`
ist konfiguriert. CLI-Tokens können diese Routen authentifizieren (Loopback + gültiger HMAC).

## Auswertungsreihenfolge

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → Loopback                                   → weiter
     → kein Loopback, Bearer mit manage-Berechtigungsumfang
        UND isLocalOnlyBypassableByManageScope    → zulassen (management_key)
     → andernfalls                               → ablehnen 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → zulassen (system)
  3. hasValidCliToken(headers)?
     → zulassen (cli) [Loopback + timingSafeEqual-HMAC-Prüfung]
  4. isAlwaysProtectedPath(path) oder requireLogin=true?
     → isDashboardSessionAuthenticated?
        → zulassen (dashboard_session)
     → Bearer mit manage-Berechtigungsumfang auf einem nicht umgehbaren Pfad?
        → zulassen (management_key)
     → ablehnen 401/403
  5. requireLogin=false?
     → zulassen (anonymous)
```

Der Zweig für den manage-Berechtigungsumfang in Schritt 1 ist der einzige authentifizierte Pfad, der eine
LOCAL_ONLY-Route erfüllen kann; der Fehlermodus des Authentifizierungs-Backends gibt 503 (nicht 403) zurück, damit eine
abgelaufene DB nicht stillschweigend auf „ablehnen“ zurückfällt.

## Hinzufügen einer neuen Route mit Spawn-Fähigkeit

1. Füge das Pfadpräfix zu `LOCAL_ONLY_API_PREFIXES` in
   `src/server/authz/routeGuard.ts` hinzu
2. Füge einen Test in `tests/unit/authz/routeGuard.test.ts` hinzu, der sicherstellt, dass
   `isLocalOnlyPath()` für das neue Präfix true zurückgibt
3. **Überspringe diesen Schritt niemals** — siehe Strikte Regel Nr. 15 in `CLAUDE.md`
4. Entscheide: Gehört diese Route AUCH zu `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Die Standardantwort lautet **nein**. Aktiviere dies nur ausdrücklich, wenn die Route sicher für einen
   Inhaber des manage-Berechtigungsumfangs freigegeben werden kann (d. h. KEINEN beliebigen benutzergesteuerten Code startet).

## Hinzufügen eines Pfads, der mit manage-Berechtigungsumfang umgangen werden kann

1. Stelle sicher, dass die Route keinen vom Benutzer bereitgestellten Code oder entsprechende Befehle ausführt. Falls doch,
   brich ab — diese Ausnahme ist dafür das falsche Werkzeug.
2. Hänge das Präfix an `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` in
   `src/server/authz/routeGuard.ts` an
3. Füge in `tests/unit/authz/management-policy.test.ts` Testabdeckung für alle vier
   Anfragevarianten hinzu: kein Bearer (403), manage-Bearer (zulassen), Nicht-manage-Bearer
   (403) sowie den präfixspezifischen Regressionstest, dass `/api/cli-tools/runtime/*` selbst
   mit einem manage-Bearer strikt auf Loopback beschränkt bleibt.

## Dokumentieren von Sicherheitsstufen in OpenAPI

Wende beim Hinzufügen einer neuen Route zu `docs/openapi.yaml` die entsprechende
Herstellererweiterung an, wenn die Route durch `routeGuard.ts` klassifiziert wird:

| routeGuard.ts-Klassifizierung                  | YAML-Annotation                 | Durchsetzung                                                 |
| ---------------------------------------------- | ------------------------------- | ------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                      | `x-loopback-only: true`         | Von Nicht-Loopback-Verbindungen bedingungslos blockiert      |
| `ALWAYS_PROTECTED_API_PATHS`                   | `x-always-protected: true`      | Authentifizierung auch bei `requireLogin=false` erforderlich |
| Interne Admin-/Debug-Route                     | `x-internal: true`              | Standardmäßig vor /dashboard/api-endpoints verborgen         |
| Keine (öffentlich / Standardauthentifizierung) | (keine Annotation erforderlich) | Standardzugriff, gesteuert durch `requireLogin`              |

### Validierung

Zwei Skripte erzwingen die Konsistenz zwischen YAML-Annotationen und `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — schlägt fehl, wenn die Abdeckung < 99% ist
- `scripts/check/check-openapi-security-tiers.mjs` — schlägt fehl, wenn `x-loopback-only`- oder
  `x-always-protected`-Annotationen von den Konstanten zur Kompilierzeit abweichen

Beide Skripte werden im Pre-Commit-Hook und in CI ausgeführt.

### Regel für falsch-positive Ergebnisse

Wenn `x-always-protected` oder `x-loopback-only` für eine Route annotiert ist, die NICHT in
der `routeGuard.ts`-Konstante enthalten ist, schlägt das Abdeckungsskript fehl. Die Lösung besteht immer darin, das
YAML an die tatsächliche Durchsetzung durch `routeGuard.ts` anzupassen — nicht darin, Routen zu `routeGuard.ts`
hinzuzufügen, ohne zugleich die Durchsetzungslogik zu implementieren.
