## Chat-Vervollständigungen

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Benutzerdefinierte Header

| Header                   | Richtung | Beschreibung                                                                                                                                                                                                                                              |
| ------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Anfrage  | Auf `true` setzen, um den Cache zu umgehen                                                                                                                                                                                                                |
| `x-omniroute-no-memory`  | Anfrage  | Auf `true` setzen, um für diese Anfrage die Einspeisung von Speicher + Skills zu überspringen (entspricht „kein Cache“; vermeidet den Token-/Kostenaufwand pro Aufruf)                                                                                    |
| `X-OmniRoute-Progress`   | Anfrage  | Für Fortschrittsereignisse auf `true` setzen                                                                                                                                                                                                              |
| `X-Session-Id`           | Anfrage  | Persistenter Sitzungsschlüssel für externe Sitzungsaffinität                                                                                                                                                                                              |
| `x_session_id`           | Anfrage  | Variante mit Unterstrichen wird ebenfalls akzeptiert (direktes HTTP)                                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | Anfrage  | Vom Aufrufer bereitgestelltes Sitzungs-/Konversations-Tag (wird auch dem Speicher zugeführt). Falls vorhanden, wird es unverändert in `call_logs.session_tag` gespeichert, um Kosten pro Sitzung zuzuordnen (#8249) — bei Abwesenheit wird es nie erzeugt |
| `Idempotency-Key`        | Anfrage  | Deduplizierungsschlüssel (5-Sekunden-Fenster)                                                                                                                                                                                                             |
| `X-Request-Id`           | Anfrage  | Alternativer Deduplizierungsschlüssel                                                                                                                                                                                                                     |
| `x-omniroute-connection` | Anfrage  | Eine Einzelmodellanfrage anhand ihrer ID an eine Anbieter-Verbindung (Konto) binden — siehe [Kontobindung pro Anfrage](#account-pinning-per-request)                                                                                                      |
| `X-OmniRoute-Cache`      | Antwort  | `HIT` oder `MISS` (ohne Streaming)                                                                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | Antwort  | `true`, falls dedupliziert                                                                                                                                                                                                                                |
| `X-OmniRoute-Progress`   | Antwort  | `enabled`, wenn die Fortschrittsverfolgung aktiviert ist                                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | Antwort  | Effektive, von OmniRoute verwendete Sitzungs-ID                                                                                                                                                                                                           |
| `X-OmniRoute-Request-Id` | Antwort  | ID zur Anfragekorrelation (falls bekannt)                                                                                                                                                                                                                 |
| `X-OmniRoute-Version`    | Antwort  | OmniRoute-Build-Version (immer vorhanden)                                                                                                                                                                                                                 |
| `X-OmniRoute-Cost-Saved` | Antwort  | Durch den Cache bei einem HIT vermiedene Kosten in USD (nur Cache-Treffer)                                                                                                                                                                                |
| `X-OmniRoute-Decision`   | Antwort  | Routing-Ablaufverfolgung: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` ist die Combo-Strategie oder `single` bei einer Nicht-Combo-Anfrage) — in Abschlussantworten immer vorhanden                                                      |

> Nginx-Hinweis: Wenn Sie Header mit Unterstrichen verwenden (zum Beispiel `x_session_id`), aktivieren Sie `underscores_in_headers on;`.

#### Kontofixierung pro Anfrage

Wenn ein Anbieter über mehrere Verbindungen (Konten oder Schlüssel) verfügt, wählt OmniRoute normalerweise eine davon über seine Kontenauswahlstrategie aus. Stattdessen kann eine Anfrage mit dem Header `x-omniroute-connection` auf eine bestimmte Verbindung festgelegt werden:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Wo Sie die ID finden.** Öffnen Sie die Anbieterseite im Dashboard
  (**Dashboard → Anbieter → <provider>**) und klicken Sie in einer Verbindungszeile auf den ID-Chip `xxxxxxxx…` — dadurch wird die vollständige Verbindungs-ID kopiert.
- **Welche Anfragen sie berücksichtigen.** Einzelmodell-Anfragen (`provider/model`) an
  `/v1/chat/completions`, `/v1/messages` und `/v1/responses`. Kombinationen ignorieren den Header: Legen Sie stattdessen für jeden Kombinationsschritt über die eigene Verbindung des Schritts ein Konto fest.
- **Die Festlegung ist strikt und keine Präferenz.** Ausschließlich die festgelegte Verbindung wird verwendet. Ein Fehler innerhalb der Anfrage erfasst die Abklingzeit des Kontos, führt jedoch **nicht** zu einem Wechsel auf ein anderes Konto desselben Anbieters.
- **Abklingzeit und Kontingent heben die Festlegung auf.** Während für die festgelegte Verbindung eine Abklingzeit gilt, ihr Kontingent ausgeschöpft ist oder sie durch eine Kontingentrichtlinie blockiert wird, greifen spätere Anfragen auf die anderen Verbindungen des Anbieters zurück, genau wie nicht festgelegter Datenverkehr.
- **Unbekannte oder deaktivierte IDs führen zu einem Fehler.** Eine ID, die sich nicht im aktiven Pool des Anbieters befindet (weil sie gelöscht oder deaktiviert wurde oder zu einem anderen Anbieter gehört), lässt kein berechtigtes Konto übrig. Daher schlägt die Anfrage fehl, anstatt unbemerkt an eine andere Stelle weitergeleitet zu werden.

Claude Code sendet benutzerdefinierte Header über `ANTHROPIC_CUSTOM_HEADERS`. Fügen Sie die Variable im `env`-Block von `~/.claude/settings.json` oder in einer `.claude/settings.json` auf Projektebene ein, um für jedes Projekt ein anderes Konto festzulegen:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Quelle: `src/sse/handlers/chat.ts` (Auslesen des Headers), `src/sse/services/auth.ts` und
`src/sse/services/sessionAffinityPin.ts` (Aufheben der Festlegung und Prüfung auf Nichtvorhandensein im Pool).

> **Header für die Kostentelemetrie:** Erfolgreiche Antworten ohne Streaming enthalten außerdem den Kostentelemetriesatz `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, fest auf 10 Dezimalstellen; `0.0000000000` bei kostenlosen Angeboten oder fehlenden Preisangaben), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` und `X-OmniRoute-Fallback-Attempts` (nur wenn > 0) sowie `X-OmniRoute-Request-Id` und `X-OmniRoute-Version`. Diese werden von Chatvervollständigungen, `/v1/responses`, `/v1/messages` **und den Medienendpunkten** ausgegeben — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` und `/v1/moderations` (Kosten immer `0`). Sofern Preisangaben verfügbar sind, werden die Medienkosten je nach Modalität berechnet (pro Bild, Sekunde, Zeichen oder Sucheinheit), andernfalls betragen sie nach dem Fail-open-Prinzip `0`.

> **Kostensemantik bei Cache-Treffern:** Bei einem Treffer im semantischen Cache (`X-OmniRoute-Cache-Hit: true`) erfolgt kein vorgelagerter Aufruf. Daher beträgt `X-OmniRoute-Response-Cost` `0.0000000000` (die **inkrementellen** Kosten für die Bereitstellung des Treffers). Die ursprünglichen beziehungsweise andernfalls angefallenen Kosten werden separat in `X-OmniRoute-Cost-Saved` ausgewiesen. Abrechnungssysteme sollten `X-OmniRoute-Response-Cost` summieren (Treffer verursachen keine Kosten); für Cache-Analysen kann `X-OmniRoute-Cost-Saved` aggregiert werden.

## Exklusive verwaltete Sitzungs-Leases

Exklusive verwaltete Sitzungs-Leases sind ein optionaler, clientneutraler Routing-Vertrag: Ein aktiver Eigentümer
hält eine geeignete OmniRoute-Verbindung. Dabei wird weder ein Modell geleast noch OAuth vorausgesetzt, ein
bestimmter Client identifiziert oder ein bestimmter Anbieter verlangt.

Der authentifizierende API-Schlüssel muss über den Scope `lease:exclusive` und eine explizite, nicht leere
`allowedConnections`-Liste verfügen. Die Mutationsgrenze der Datenbank erzwingt beide Felder gemeinsam bei der
Schlüsselerstellung und bei partiellen Aktualisierungen.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Erfolgreiche Antworten auf Erwerb, Erneuerung und Freigabe enthalten Zeitstempel, `state` und die exakte positive
`generation`, jedoch niemals die ausgewählte Verbindung oder Anmeldedaten. Bei Erneuerung und Freigabe wird die
Generation im JSON-Body angegeben:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Ein aktiver Lease-Eigentümer kann explizit datenschutzkonforme Anzeigemetadaten für seine aktuelle Bindung anfordern:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Diese optionale Statusaktion wird innerhalb einer einzigen Datenbanktransaktion durch den undurchsichtigen Eigentümer,
den authentifizierten verwalteten API-Schlüssel und die exakte aktive Generation abgesichert. `displayName` ist
ausschließlich der getrimmte konfigurierte Verbindungsname; er ist `null`, wenn kein sicherer konfigurierter Name
vorhanden ist. OmniRoute verwendet niemals ersatzweise eine E-Mail-Adresse oder eine generierte Kontoidentität.
Der Anbieterwert ist eine nicht vertrauliche Anzeigebezeichnung und niemals eine generierte Kennung eines kompatiblen
Anbieters. Anmeldedaten, Token, Cookies, unformatierte Verbindungs- oder API-Schlüssel-IDs, Eigentümer-Hashes,
Fencing-Geheimnisse und interne Routing-Daten sind ausgeschlossen.

Abfragen mit falschem Schlüssel, falschem Eigentümer, veralteter Generation sowie fehlende, abgelaufene, freigegebene
und ungültig gemachte Abfragen geben alle denselben Fehler `409 LEASE_FENCE_STALE` ohne Verbindungsmetadaten zurück.
Ein Client, der die Antwort zum Warten auf Kapazität erhalten hat, verfügt über keine aktive Bindung, die geprüft
werden könnte. Wenn das Routing eine aktive Lease auf eine andere Verbindung umstellt, bleibt dieselbe Generation
gültig und der Status gibt atomar die neue Bindung zurück, niemals die alte. Bestehende Clients bleiben unverändert,
da die Antworten für Erwerb, Erneuerung, Freigabe und Warten ihre bisherigen Strukturen beibehalten.

Dieser Serververtrag ändert den standardmäßigen OpenAI-Codex-Endpunkt `/status` nicht. Der standardmäßige Codex meldet
derzeit seinen Modellanbieter sowie den integrierten Authentifizierungs- und Kontostatus, stellt jedoch keine beliebigen
Kontometadaten benutzerdefinierter Anbieter dar. Eine spätere Clientintegration muss diese Aktion aufrufen und
entscheiden, wie `connection.displayName` angezeigt werden soll.

Jede verwaltete Inferenzanfrage übermittelt anschließend beide Steuerungs-Header:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Der exakte Eigentümer, die Generation, die aktive Verbindung und der authentifizierte API-Schlüssel werden unmittelbar
vor jedem unterstützten Upstream-Versuch durch Fencing abgesichert. Das erneute Verwenden von Eigentümer und Generation
mit einem anderen Schlüssel schlägt selbst dann fehl, wenn dieser Schlüssel dieselbe Verbindung zulässt. Unformatierte
Eigentümerwerte werden weder dauerhaft gespeichert noch protokolliert, im Anfrage-Snapshot aufbewahrt oder an den
Upstream weitergeleitet.

Vorübergehende Konkurrenz um Ressourcen gibt HTTP `429` mit `Retry-After` und Folgendem zurück:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Diese Antwort bedeutet lediglich, dass die reguläre Menge geeigneter Verbindungen nicht leer war und jeder freie
Kandidat von einer fremden aktiven Lease belegt wurde. Nicht unterstützte Modelle oder Anbieter, Richtlinienkonflikte,
Abklingzeiten, Kontingente, Integritätszustände und andere reguläre Fehler bei der Eignungsprüfung behalten ihre
bestehenden OmniRoute-Antworten bei.

### `x-omniroute-compression`

Anfragespezifische Außerkraftsetzung des Komprimierungsplans. Höchste Priorität — hat Vorrang vor der
Routing-Kombinationsüberschreibung, dem aktiven Profil, dem automatischen Auslöser und der Standardeinstellung des
Panels. Werte:

| Wert          | Wirkung                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Keine Komprimierung für diese Anfrage.                                                                                         |
| `default`     | Das vom Panel abgeleitete Standardprofil (ignoriert das aktive Profil). Verlustbehaftete Engines bleiben deaktiviert.          |
| `safe`        | Nur Deduplizierung und Zusammenfassung von Leerraum.                                                                           |
| `allow-lossy` | Behält den Betreiberplan für diese Anfrage bei, einschließlich Zusammenfassungen und Stilumschreibungen.                       |
| `engine:<id>` | Eine einzelne Engine, sofern aktiviert, z. B. `engine:rtk`. Anfragespezifische Aktivierung dieser Engine.                      |
| `<combo>`     | Eine benannte Kombination, die zuerst nach Namen (ohne Beachtung der Groß-/Kleinschreibung) und dann nach ID abgeglichen wird. |

Hinweise:

- Unbekannte Werte werden ignoriert (die Anfrage wird niemals abgelehnt); die Auflösung greift auf die normale Betreiberpriorität zurück.
- Wenn mehrere Kombinationen denselben Namen haben, übergeben Sie für eine deterministische Übereinstimmung die **ID** der Kombination.
- Eine Kombination mit dem Namen `off` oder `default` kann nicht anhand ihres Namens ausgewählt werden (diese Schlüsselwörter werden zuerst interpretiert); referenzieren Sie eine solche Kombination anhand ihrer ID.
- Der Hauptschalter für die Komprimierung ist eine feste Sperre: Wenn die Komprimierung global deaktiviert ist, kann dieser Header sie nicht aktivieren.

Der angewendete Plan wird im Antwort-Header zurückgegeben:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

Dabei ist `<source>` einer der Werte `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` oder `off`.

## Einbettungen

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Verfügbare Anbieter: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog-IDs haben das Format `provider/model` (Beispiel: `jina-ai/jina-embeddings-v5-omni-small`). Reine Jina-Modell-IDs, die in der Registry erscheinen (zum Beispiel `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), werden ebenfalls aufgelöst. Jina-Einbettungs-, Reranking-, Klassifizierungs- und Segmentierungsmodelle verwenden zuerst die `jina-ai`-Anmeldedaten aus dem Dashboard; `JINA_AI_API_KEY` dient nur als Fallback, wenn kein Dashboard-Schlüssel vorhanden ist. Die Karte `jina-reader` ist ausschließlich für Reader / `r.jina.ai` (`POST /v1/web/fetch`) vorgesehen und stellt niemals Einbettungs- oder Reranking-Funktionen bereit.

Registry-Modelle, die multimodale Unterstützung angeben, akzeptieren außerdem bis zu 32 anbieterneutrale strukturierte
Elemente. Die Medienelementtypen sind `text`, `image`, `audio`, `video` und `document`. Ihre Medienquelle `source`
ist entweder `{"type":"url","url":"https://..."}` oder
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
und der Familienalias `jina-ai/jina-embeddings-v5-omni` → omni-small) akzeptiert auch Jinas native
EmbeddingsV5Request-Dokumente und **leitet sie unverändert** an `https://api.jina.ai/v1/embeddings` weiter:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Native Werte für `{ image | audio | video | pdf }` können eine öffentliche HTTPS-URL, eine `data:`-URI oder rohe
Base64-Daten sein. OmniRoute konvertiert diese Objekte nicht in Zeichenfolgen und ruft native Bild-URLs nicht ab — Jina ruft
öffentliche Medien selbst ab. Zusätzliche Jina-Felder (`task`, `normalized`, `truncate`, `embedding_type`) werden
weitergeleitet. Reine Text-SKUs von Jina lehnen Nicht-Text-Dokumente weiterhin ab.

Sicherheits- und Übertragungsgrenzen:

- Remote-Medien-URLs müssen öffentliches HTTPS verwenden. Kanonische `{type,source:url}`-Elemente werden
  serverseitig abgerufen (erneute Validierung von Weiterleitungen, Zeitüberschreitung, Größenbeschränkungen, öffentliches DNS, Verbindungs-Pinning) und
  vor dem Anbieteraufruf inline eingebettet. Jina-native `{image:"https://..."}`-Elemente werden nach
  derselben Prüfung auf öffentliches HTTPS unverändert weitergeleitet; Jina ruft die URL ab.
- Inline-Base64-Medien sind auf 8 MiB dekodiert pro Element und 16 MiB dekodiert für die gesamte Anfrage begrenzt.

Anbieterübersetzung (kanonische Elemente werden niemals unverändert weitergeleitet):

- Multimodale Jina-Modelle: Jedes Element der obersten Ebene wird zu einem nach Modalität benannten Objekt
  (`text` / `image` / `audio` / `video` / `pdf`), wobei Daten-URIs für Inline-Medien verwendet werden; ein Vektor pro
  Element der obersten Ebene.
- Gemini Embedding 2-Familie: Ein Array der obersten Ebene wird zu einer einzigen nativen
  `models/{model}:embedContent`-Anfrage mit `content.parts` (`text` oder `inline_data`).
- llama.cpp (`llama-cpp/<model>`, jedes vom lokalen Server geladene Modell): Kanonische `text`-Elemente
  werden zu einfachen Zeichenfolgen, und `image` / `audio` / `video` werden jeweils zu einem
  `{"content": [part]}`-Objekt. Dabei werden die Chat-Inhaltsteile des llama-Servers (`image_url`,
  `input_audio` mit dem Format `wav` / `mp3` / `flac`, `input_video`) mit Inline-Daten verwendet; ein Vektor
  pro Element der obersten Ebene. Der Server muss mit `--embedding --mmproj …` ausgeführt werden; ohne Projektor
  lehnt er Medien selbst ab. `document` wird nicht unterstützt.
- Unbekannte/dynamische Modelle ohne explizite Modalitätsmetadaten lehnen strukturierte Eingaben mit HTTP 400 ab.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Nicht unterstützte Modell-/Modalitätskombinationen geben HTTP 400 zurück, anstatt das Element zu konvertieren. Erweiterungsfelder
außerhalb der Eingabe werden bei älteren Zeichenfolgen-/Token-Anfragen weiterhin unverändert weitergeleitet.

```bash
# Alle Einbettungsmodelle auflisten
GET /v1/embeddings
```

## Bilderzeugung

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Zu den verfügbaren Anbietern gehören OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokal), ComfyUI (lokal).

`n` gibt `n` Bilder in `data[]` zurück. Bei Anbietern, deren vorgelagerte API pro Aufruf ein Bild zurückgibt
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), werden `n` separate vorgelagerte Aufrufe ausgeführt, davon höchstens 4 gleichzeitig. Ein
fester `seed` wird um den Aufrufindex versetzt (`seed`, `seed + 1`, …), sodass sich die Bilder unterscheiden, aber
reproduzierbar bleiben. `n` ist auf 10 begrenzt. Die gesamte Anfrage schlägt fehl, wenn ein Aufruf fehlschlägt. Die Liste
der Fan-out-Formate befindet sich unter `SINGLE_IMAGE_FANOUT_FORMATS` in
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux verwendet die bestehende API-Schlüssel-Verbindung erneut und akzeptiert die Präfixe `zenmux/` oder `zm/`:

- `zenmux/openai/gpt-image-2` verwendet die OpenAI Images API von ZenMux. Zu den Optionen gehören `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` und `response_format`.
- Andere Publisher, etwa `zm/meta/muse-image-1.0`, verwenden den Vertex-AI-Endpunkt `:predict`
  von ZenMux. `n` wird `sampleCount`, `aspect_ratio` wird `aspectRatio` und `image_size`
  (`1K`, `2K`, `4K`) wird `sampleImageSize` zugeordnet. Eine pixelbasierte Angabe für `size` legt nur ein Seitenverhältnis fest,
  keine garantierten Pixelabmessungen. Unterstützte Seitenverhältnisse, Auflösungen und Anzahlen variieren je nach Modell.
- `zm/inclusionai/ming-image-0.1-design` wählt seine Abmessungen selbst. Lassen Sie `size`,
  `aspect_ratio` und `image_size` weg; explizite Werte führen zu HTTP 400. PNG, JPEG und WebP
  können mit `output_format` angefordert werden.

Diese Integration unterstützt die Text-zu-Bild-Erzeugung, jedoch nicht die Bearbeitung von Referenzbildern. Die Vertex-Ausgabe
wird zu `data[].b64_json` normalisiert; `response_format: "url"` gibt eine vorgelagerte
HTTPS-URL oder eine Base64-Daten-URL zurück, wenn nur Bildbytes verfügbar sind. Leere/gefilterte Ausgaben
führen zu einem Fehler statt zu einer leeren erfolgreichen Antwort. Der Modellzugriff hängt vom ZenMux-Konto ab.
Siehe [Vertex API von ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) und
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Alle Bildmodelle auflisten
GET /v1/images/generations
```

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
```

`model` wählt den OCR-Anbieter über ein Präfix im Format `provider/model` aus; eine reine Modell-ID (z. B.
`mistral-ocr-latest`) wird dem registrierten Anbieter zugeordnet, und wenn `model` weggelassen wird, wird standardmäßig
Mistral (`mistral-ocr-latest`) verwendet. Registrierte Anbieter (`open-sse/config/ocrRegistry.ts`):

| Anbieter-ID                   | Modell-ID            | Wert für `model`                                             | Hinweise                                                                                                                     |
| ----------------------------- | -------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (oder nur `mistral-ocr-latest`) | Synchron — die Antwort wird direkt vom einzelnen vorgelagerten Aufruf zurückgegeben.                                         |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                  | Asynchroner vorgelagerter Dienst (`analyze` + Abfrage) — siehe unten.                                                        |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                      | Synchron, über den Partner-Endpunkt `openapi/chat/completions` von Vertex AI — Details zu Authentifizierung/URL siehe unten. |

Alle drei Anbieter antworten mit demselben an Mistral angelehnten Antworttext:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Abfrageablauf von Azure Document Intelligence

Die `analyze`-API von Azure Document Intelligence ist asynchron: Die ursprüngliche Anfrage gibt einen
`Operation-Location`-Header anstelle eines Antworttexts zurück, und das Ergebnis muss wiederholt abgefragt werden. Der Handler
(`open-sse/handlers/ocr.ts`) fragt diese URL bis zu 30-mal im Abstand von jeweils einer Sekunde ab, bricht bei einer nicht erfolgreichen
`ok`-Abfrageantwort oder dem Status `"failed"` sofort mit einem Fehler ab (ohne weitere Abfragen) und gibt `504` zurück, wenn der
Vorgang nach Ausschöpfung der maximalen Anzahl von Versuchen noch läuft. Die endgültige Azure-Antwort wird
vor der Rückgabe an den Aufrufer in dieselbe von Mistral verwendete `pages`-/`markdown`-Struktur normalisiert,
sodass der Clientcode den Anbieter nicht gesondert behandeln muss.

### Authentifizierung und Endpunktauflösung für Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` verwendet dieselbe Vertex-AI-Authentifizierung, die OmniRoute bereits für
Chat-/Bilddatenverkehr unterstützt (`open-sse/executors/vertex.ts`): Der API-Schlüssel der Verbindung ist entweder eine
Service-Account-JSON-Anmeldeinformation (die über den JWT-Bearer-Ablauf gegen ein kurzlebiges OAuth-Zugriffstoken
ausgetauscht wird) oder ein bereits ausgestelltes OAuth-Zugriffstoken, das unverändert verwendet wird. Die URL des vorgelagerten Endpunkts ist der
generische Vertex-Partner-Endpunkt `openapi/chat/completions`, der anhand des Projekts und der
Region der Verbindung erstellt wird — explizite Angaben für `providerSpecificData.project`/`providerSpecificData.region` haben immer Vorrang;
andernfalls wird das Projekt aus `project_id` im Service-Account-JSON abgeleitet und für die Region
standardmäßig `us-central1` verwendet. Beide Auflösungen erfolgen in `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) und werden von
`src/app/api/v1/ocr/route.ts` verwendet, bevor die Anfrage an `handleOcr` weitergeleitet wird.

### Modellpreise (`pricing`)

Ein Eintrag enthält ein `pricing`-Objekt, wenn OmniRoute den Preis des Modells kennt. Der Preis stammt
aus der Preistabelle, die für die Kostenabrechnung verwendet wird: integrierte Standardwerte, synchronisierte Preise und
über `/api/pricing` festgelegte Überschreibungen. Dabei handelt es sich um Listenpreise, sodass auch Abonnementanbieter
einen Preis pro Token anzeigen.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Felder                                                          | Einheit                            | Hinweise                                                                                                                                                                     |
| --------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD pro Token, Dezimalzeichenfolge | OpenRouter-kompatibel, niemals in Exponentialschreibweise. Die beiden Cache-Felder erscheinen nur, wenn ein Cache-Preis vorhanden ist.                                       |
| `input`, `output`, `cached`, `cache_creation`                   | USD pro 1 Mio. Token, Zahl         | Felder aus früheren Katalogversionen, die für bestehende Clients beibehalten werden. `reasoning` und `long_context` erscheinen ebenfalls, wenn die Preiszeile diese enthält. |

- **Kombinationen** übernehmen den Preis ihres ersten sichtbaren Ziels. Integrierte `auto/*`-Kombinationen wählen ein
  Ziel zum Zeitpunkt der Anfrage aus und haben daher kein `pricing`.
- **Kostenlose Modelle** zeigen `"0"` (und `0`) an, wenn ihr Preis null ist. Ein Modell ohne Preiszeile
  zeigt ebenfalls `"0"` an, wenn der Katalog es als kostenlos kennzeichnet (`free: true`) oder es im integrierten Katalog
  kostenloser Modelle aufgeführt ist.
- **Unbekannter Preis:** Der Eintrag hat keinen `pricing`-Schlüssel.
- **Nach Guthaben abgerechnete Anbieter** (wie Kiro) rechnen pro Anfrage statt pro Token ab. Ihre
  Einträge behalten die numerischen Felder pro 1 Mio. Token bei, die sie zuvor hatten, und enthalten keine Zeichenfolgenfelder für Preise pro Token.
- **Varianten** (IDs für Reasoning-Aufwand, No-Thinking-Aliase sowie Discovery- und Gateway-Spiegelungen)
  kopieren den Preis des Modells, an das sie weiterleiten.
- Die Felder enthalten nur die Basistarife. Tarife für lange Kontexte (das numerische Feld `long_context`) und
  Service-Tier-Multiplikatoren (zum Beispiel Codex Fast oder Flex) ändern `prompt` oder
  `completion` nicht.
- Das Objekt ist für jeden Authentifizierungsstil identisch, einschließlich einer Anfrage im Anthropic-Stil
  mit `x-api-key` und `anthropic-version` (die Antwort bleibt `{ "object": "list",
"data": [...] }`). Implementierung: `src/app/api/v1/models/catalogPricing.ts`.

### Modell-ID-Präfixe (`?prefix=`)

Die meisten Modelle werden unter einem **Anbieterpräfix** angeboten. Welches Präfix verwendet wird, wird durch
das Feature-Flag `MODELS_CATALOG_PREFIX_MODE` gesteuert und kann **pro Anfrage** mit einem
Abfrageparameter überschrieben werden — nützlich für einen Client, der eine übersichtliche Liste benötigt, ohne die serverweite
Einstellung für alle anderen zu ändern:

```bash
GET /v1/models?prefix=alias        # eine ID pro Modell — das kurze Aliaspräfix
GET /v1/models?prefix=dual         # beide Formen (Serverstandard)
GET /v1/models?prefix=canonical    # nur das vollständige Anbieter-ID-Präfix
```

| Modus       | Gibt aus                                                  | Hinweise                                                                                                                                                                                                                  |
| ----------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **und** `claude/claude-sonnet-4-6` | **Standard.** Beide IDs leiten an dasselbe Modell weiter; dies wird beibehalten, damit Clientkonfigurationen, in denen eine der beiden Formen fest codiert ist, weiterhin funktionieren. Verdoppelt den Katalog ungefähr. |
| `alias`     | `cc/claude-sonnet-4-6`                                    | Ein Eintrag pro Modell. Anbieter ohne einen eigenen Alias geben ihren Eintrag dennoch aus, sodass nichts verloren geht.                                                                                                   |
| `canonical` | `claude/claude-sonnet-4-6`                                | Ein Eintrag pro Modell unter dem vollständigen Anbieter-ID-Präfix. Anbieter ohne einen eigenen Alias (z. B. `antigravity/…`, `agy/…`) geben auch hier ihre einzelne ID aus, sodass nichts verloren geht.                  |

Eine Spiegelung im `dual`-Modus kann auch ohne den Abfrageparameter erkannt werden: Sie enthält ein `parent`-Feld,
das auf die primäre ID verweist.

Clients, die eine Modellauswahl anzeigen, sollten `?prefix=alias` anfordern — dies wird auch von der
[OmniCopilot-Erweiterung für VS Code](../guides/VSCODE-COPILOT.md) verwendet.

### Discovery-Filter (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` akzeptiert optionale Discovery-Filter. Ohne diese bleibt die Antwort
unverändert. Sie schränken den Katalog ein, den der Aufrufer bereits sehen kann (API-Schlüssel-Berechtigungen werden zuerst angewendet),
und werden vor der OpenAI-kompatiblen Paginierung mit `limit` / `after` ausgeführt:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # jede aufgeführte Fähigkeit muss wahr sein
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` des Katalogs; Zeilen ohne Angabe gelten als `chat`
GET /v1/models?q=sonnet&limit=10                           # Übereinstimmung ohne Beachtung der Groß-/Kleinschreibung bei ID oder Name
```

| Parameter     | Werte                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | nicht negative Ganzzahl, wird mit `context_length` verglichen                                       |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 Zeichen                                                                                       |

Ein unbekannter Wert oder ein `min_context`, das keine nicht negative Ganzzahl ist (zum Beispiel `1.5`),
führt zu HTTP `400`; die Meldung listet die gültigen Werte auf. Implementierung:
`src/app/api/v1/models/catalogFilters.ts`.

### Modellauswahl (`POST /v1/models/query`)

`POST /v1/models/query` gibt eine kurze, deterministische Liste aus demselben Katalog zurück, mit derselben
Authentifizierung und derselben schlüsselspezifischen Sichtbarkeit wie `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Jedes Feld ist optional. `capabilities` und `exclude` akzeptieren ein Array oder eine durch Kommas getrennte Zeichenfolge;
`max_output` wird mit `max_output_tokens` verglichen. Die Ergebnisse werden zuerst nach `owned_by` und dann nach `id` sortiert.
Der Standardwert für `limit` ist `20`; Werte über `100` werden auf `100` begrenzt. Ungültiges JSON, ein unbekanntes
Feld oder ein ungültiger Wert führt zu HTTP `400`.

### Einzeln ausgeblendete Chatmodelle

Ein Modell, das auf seiner Anbieterseite als **Ausgeblendet** markiert ist, wird aus dem Katalog ausgeschlossen und
bei einer expliziten Anfrage mit HTTP `404` / `model_not_found` abgelehnt. Bei der Prüfung werden der aufgelöste
Anbieter und das aufgelöste Modell berücksichtigt, einschließlich Anbieter-Aliasen, Knotenpräfixen kompatibler Anbieter und
Verbindungsstandardwerten. Eine Kombination überspringt ausgeblendete Ziele und kann ein sichtbares gleichgeordnetes Modell verwenden; wenn kein
ausführbares Ziel verbleibt, wird derselbe Fehlercode zurückgegeben. Das Aufheben der Ausblendung wird bei der nächsten
Anfrage wirksam. Sichtbarkeitsüberschreibungen ausschließlich für Bilder blenden das Chatmodell mit derselben ID nicht aus.

Diese individuelle Modelleinstellung ist von den
[Zulassungs-/Sperrlisten für die Modellbereitstellung](../routing/MODEL_EXPOSURE_LIST.md) getrennt, die die
Anzeige im Katalog und Kandidaten für automatisches Routing filtern, während die explizite Weiterleitung erhalten bleibt. Modellberechtigungen
für API-Schlüssel gelten weiterhin unabhängig davon. Der standardmäßige Präfixmodus des Katalogs bleibt `dual`.

### Modellvarianten ohne Thinking

Für Thinking-fähige Claude-Modelle zeigt `/v1/models` außerdem eine **No-Thinking**-Variante an, deren ID das Präfix `claude-3-omniroute-no-thinking/` trägt:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Die Auswahl dieser ID (z. B. in einer Claude-Code-Konfiguration, die immer einen `thinking`-Block anhängt) wird wieder zum tatsächlichen `<provider>/<model>` aufgelöst, wobei Reasoning unterdrückt wird — `thinking:{type:"disabled"}` im `/v1/messages`-Pfad oder das Entfernen der Felder `reasoning`/`reasoning_effort` im `/v1/chat/completions`-Pfad. Die Variante wird nur für Modelle der Claude-Familie aufgeführt, die Thinking unterstützen **und** `disabled` berücksichtigen (adaptive Modelle, die `disabled` ablehnen, sind beispielsweise ausgeschlossen). Betreiber können die Variante pro Modell über `ModelSpec.noThinkingAlias` erzwingen oder deaktivieren.

## ElevenLabs-Audiogenerierung

Konfigurieren Sie in OmniRoute eine `elevenlabs`-Provider-Verbindung mit Ihrem ElevenLabs-API-Schlüssel.
Clients authentifizieren sich mit ihrem **OmniRoute**-Schlüssel (`Authorization: Bearer $OMNIROUTE_API_KEY`);
das Gateway stellt den gespeicherten Provider-Schlüssel als `xi-api-key` bereit. Senden Sie niemals einen
ElevenLabs-Schlüssel als Bearer-Token des Gateways.

| Methode | Pfad                        | Antwort                                      | API-Schlüssel-Endpunktkategorie |
| ------- | --------------------------- | -------------------------------------------- | ------------------------------- |
| POST    | `/v1/sound-generation`      | Native Audiobytes                            | `elevenlabs`                    |
| POST    | `/v1/music`                 | Native Audiobytes                            | `music`                         |
| POST    | `/v1/music/stream`          | Gestreamte Audiobytes                        | `music`                         |
| POST    | `/v1/music/detailed`        | Natives Multipart-Audio und Kompositionsplan | `music`                         |
| POST    | `/v1/music/detailed/stream` | Native SSE-Metadaten und Audio-Chunks        | `music`                         |
| POST    | `/v1/music/plan`            | JSON-Kompositionsplan                        | `music`                         |

Diese Endpunkte ergänzen die vorhandenen Routen `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` und `/v1/speech-to-text`. Native JSON-Felder
und Abfrageparameter wie `output_format` und `enable_logging` bleiben erhalten.
Antworten von `/v1/music/detailed` behalten ihre Multipart-Begrenzungen bei; parsen Sie sie als Multipart.
`/v1/music/detailed/stream` gibt `text/event-stream` mit Kompositionsmetadaten und
Base64-Audio-Chunks in SSE-Ereignissen zurück. Alle sechs Routen unterstützen CORS-Preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Ein kurzer Soundeffekt. Dauer: 0,5 bis 30 Sekunden.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Die Musikdauer wird in Millisekunden angegeben: 3000 bis 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Verwenden Sie `/v1/music/stream` mit demselben JSON-Body für die inkrementelle Audioübertragung. Die Komposition
akzeptiert genau eines von `prompt` oder `composition_plan`; `/v1/music/plan` erfordert `prompt`
und akzeptiert optional `source_composition_plan`. Die nativen Schemas behalten zusätzliche
Provider-Felder bei, sodass Versionen von Kompositionsplänen und Feinabstimmungsoptionen ElevenLabs erreichen.

Der einheitliche Endpunkt `/v1/music/generations` akzeptiert außerdem `elevenlabs/music_v1`,
`elevenlabs/music_v2` und `elevenlabs/music_v2_5`. Bei einer aktiven ElevenLabs-Verbindung
werden diese Modelle im Musikkatalog bereitgestellt. Dieser Endpunkt gibt
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` zurück. Sein Feld `duration` wird in
Sekunden angegeben und `music_length_ms` zugeordnet; ein explizites `music_length_ms` hat Vorrang.
`instrumental` wird `force_instrumental` zugeordnet, wobei das native Feld Vorrang hat.
Verwenden Sie die nativen Streaming-Endpunkte für Streaming und den nativen Kompositionsendpunkt
für Anfragen, die ausschließlich durch einen Kompositionsplan gesteuert werden.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Endpunkt-, Modell-, Budget- und Verbindungseinschränkungen werden vor einem Upstream-Aufruf angewendet. Native
Routen geben Upstream-Statuscodes und Fehler-Bodys unverändert zurück, einschließlich `402` bei einer
Tarifeinschränkung und `429` bei einem Kontingentlimit. Die Header `character-cost`, `song-id`, `request-id` und `retry-after`
bleiben erhalten, sofern sie vorhanden sind. Ein kostenloses Guthaben garantiert keinen Zugriff auf jedes
Musikmodell, Ausgabeformat oder API-Feature: ElevenLabs entscheidet für jede Anfrage über die Berechtigung.
Der einheitliche Endpunkt behält Fehlerstatuscodes im normalisierten Fehler-Umschlag von OmniRoute bei.

Upstream-Verträge: [Soundeffekte](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[Musikkomposition](https://elevenlabs.io/docs/api-reference/music/compose) und
[Streaming-Musikdetails](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# Neusortierung (Cloud-Registry-Anbieter oder ein OpenAI-kompatibler Anbieterknoten als "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Soniox TTS erfordert eine Sprache und eine Stimme: `language` verwendet standardmäßig "en"; eine fehlende
# Stimme oder der Name einer Standardstimme von OpenAI (alloy, nova, …) wird zu "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }
```

> **Knoten von Rerank-Anbietern:** `POST /v1/rerank` leitet Anfragen auch an OpenAI-kompatible Anbieterknoten
> (oMLX, vLLM, Infinity, TEI hinter einem Gateway, …) weiter, die als `<node-prefix>/<model>` adressiert werden. Loopback-
> Knoten (`localhost`, `127.0.0.1`, `172.16.0.0/12`) sind immer zulässig, ebenso wie Hostnamen, die der
> Betreiber in `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` aufführt (z. B. ein Docker-/Compose-Dienstname wie
> `http://reranker:8080/v1`; diese werden direkt aufgerufen, niemals über `HTTP(S)_PROXY` oder den
> fest zugewiesenen Proxy einer Verbindung). Knoten auf jedem anderen
> Host – etwa einem Rechner im LAN oder einem Tailscale-Peer – sind nur zulässig, wenn der Betreiber das
> Feature-Flag `RERANK_REMOTE_PROVIDER_NODES` aktiviert **und** die Basis-URL des Knotens die Richtlinie für
> ausgehende Anbieter-URLs (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)
> erfüllt. Der Rerank-Schritt der Memory-Engine ruft diese Route über
> Loopback auf, sodass dieselbe Regel für `rerankProviderModel` in den Memory-Einstellungen gilt.
>
> **Schnittstellenformen lokaler Server:** Der Knoten wird unter `<base>/v1/rerank` und bei einer 404-Antwort unter `<base>/rerank`
> (Infinity, TEI) aufgerufen. Der Upstream-Body enthält sowohl die Cohere-/OpenAI-Schreibweise (`documents`,
> `return_documents`) als auch die TEI-Schreibweise (`texts`, `return_text`), und die Upstream-Antwort wird
> auf das Cohere-Format normalisiert: Das reine TEI-Format `[{index, score, text}]`, `{results: [{index, score}]}`
> von schlanken Gateways und das Voyage-Format `{data: [...]}` werden alle als
> `{results: [{index, relevance_score, document?}]}` an den Client zurückgegeben, nach Score sortiert und auf `top_n` begrenzt.

> **Erkennung von Anbieterknoten:** Modelle auf einem OpenAI-kompatiblen Anbieterknoten erscheinen in `GET /v1/models`
> unter dem Knotenpräfix. Einträge ohne Endpunktmetadaten (typisch für lokale `/v1/models`-Auflistungen)
> übernehmen den `apiType` des Knotens, sodass die Modelle eines `embeddings`-Knotens `type: "embedding"` und die
> Modelle eines `rerank`-Knotens `type: "rerank"` erhalten, anstatt standardmäßig als Chatmodelle behandelt zu werden; explizite
> `supportedEndpoints` in einem synchronisierten oder manuell hinzugefügten Eintrag haben weiterhin Vorrang.

## Search-API

Abstraktion für Web-/Suchanbieter (Tavily, Brave, Exa, Serper usw.).

| Methode | Pfad                   | Beschreibung                                                                                                 |
| ------- | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| GET     | `/v1/search`           | Konfigurierte Suchanbieter und deren Funktionen auflisten                                                    |
| POST    | `/v1/search`           | Eine Suchanfrage ausführen — Body wird durch `v1SearchSchema` validiert, unterstützt Caching/Zusammenführung |
| GET     | `/v1/search/analytics` | Anbieterbezogene Treffer-/Latenz-/Cache-Statistiken                                                          |

**Authentifizierung:** Bearer-API-Schlüssel (`extractApiKey` + `isValidApiKey`). Die Suchrichtlinie wird über `enforceApiKeyPolicy` durchgesetzt.

### Exa- und Tavily-`provider_options`

Exa und Tavily lesen anbieterspezifische Felder aus einem namensraumgebundenen Container:
`provider_options.exa` (oder `provider_options["exa-search"]`) und `provider_options.tavily`
(oder `provider_options["tavily-search"]`). Nur die unten aufgeführten Schlüssel werden weitergegeben. Jeder davon wird
anhand seines eigenen Zod-Schemas in `open-sse/handlers/search/providerOptionsPassthrough.ts`
geprüft; ein Schlüssel mit dem falschen Typ wird verworfen. Alle anderen Schlüssel werden ignoriert, einschließlich Authentifizierung, Basis-URL,
`stream` und `outputSchema`. Die von anderen Anbietern verwendeten flachen Schlüssel (`cx`, `depth`, ...) funktionieren
weiterhin wie zuvor.

| Anbieter | Felder auf oberster Ebene                                                                                                                                                                                                                                                                                                                                                 | Verschachtelt                                                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flache primitive Werte), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                       | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` wird über dem Standardwert `{ text: true, highlights: true }` zusammengeführt |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                                    |

Die generischen Felder haben immer Vorrang: `query`, `max_results`, `filters` (Domains), `country` und das
aus `search_type` abgeleitete Thema. Bei Exa behält `search_type: "news"` den Wert `category: "news"` bei.
Tavily akzeptiert außerdem `search_type: "finance"` (`topic: "finance"`).

Das generische `time_range` erreicht nun beide Anbieter: Exa erhält `startPublishedDate` (ISO-
Zeitstempel) und Tavily erhält `start_date` (`YYYY-MM-DD`). Ein explizites Datum in `provider_options`
überschreibt den zugeordneten Wert.

Exa-Ergebnisse behalten `id`, `highlight_scores`, `summary`, `subpages`, `entities` und `extras` in
`provider_raw`. Tavily-Ergebnisse behalten `images` und `favicon`.

Die Kostenabrechnung verwendet weiterhin die flache Registry `costPerQuery`. Tavily berechnet für
`search_depth: "advanced"` mehr Credits pro Aufruf; dieser Unterschied wird in
`usage.search_cost_usd` nicht berücksichtigt.

## Web-Fetch-API

Extrahiert Inhalte von einer URL über einen konfigurierten Web-Fetch-Anbieter (Firecrawl, Jina

Parallel Extract (`parallel-search`, derselbe API-Schlüssel wie bei Parallel Search) gibt ausschließlich Markdown

die Zielseite selbst nicht extrahiert werden kann, meldet der Upstream-Dienst dies innerhalb einer HTTP-200-Antwort;
OmniRoute gibt dies als `422` mit einer festen Meldung aus.

| Methode | Pfad            | Beschreibung                                                       |
| ------- | --------------- | ------------------------------------------------------------------ |
| POST    | `/v1/web/fetch` | URL abrufen/scrapen — Body wird durch `v1WebFetchSchema` validiert |

**Authentifizierung:** Bearer-API-Schlüssel (`extractApiKey` + `isValidApiKey`). Die Richtlinie wird über `enforceApiKeyPolicy` durchgesetzt.

**Kontingentberücksichtigender Fallback (#8297):** Wenn kein expliziter `provider` angegeben ist, wird der Pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) in einer festen
Prioritätsreihenfolge durchlaufen (Fill-first) — ein ratenbegrenzter, aber konfigurierter Anbieter wird übersprungen,
anstatt die Anfrage sofort abzubrechen, und bei einem wiederholbaren Upstream-/Kontingentfehler
(HTTP 429 immer; 402/403 bei kontingentbedingten kostenlosen Tarifen von Firecrawl/Tavily/TinyFish —
nicht bei Jina Reader und niemals bei einer einfachen fehlerhaften 400-Anfrage) wird zur Laufzeit auf den
nächsten noch nicht versuchten Anbieter mit hinterlegten Zugangsdaten zurückgegriffen. Wenn alle Anbieter im
Pool ausgeschöpft sind, gibt der Endpunkt statt des bisherigen generischen `400` eine einzelne `429`-Antwort
(mit einem `Retry-After`-Header) zurück. Wenn ein expliziter `provider` angefordert
wird, gibt es **keinen** stillen Fallback — bei einem ratenbegrenzten oder fehlerhaften expliziten
Anbieter wird dessen eigener Fehler ausgegeben (`429` bei Ratenbegrenzung, andernfalls der
Upstream-Status).

## WebSocket-Streaming

```bash
GET /v1/ws?handshake=1
```

Validiert einen WebSocket-Upgrade-Handshake und gibt die Beispielnachrichten des Wire-Protokolls (`request`, `cancel`) zurück. Die eigentlichen WS-Frames werden vom mitgelieferten WS-Server außerhalb der Next.js-Routentabelle verarbeitet.

**Authentifizierung:** Bearer-API-Schlüssel während des Handshakes.

### Responses API über WebSocket (nur codex)

```bash
# Derselbe Host und Port wie bei der HTTP-API (standardmäßig 20128); Verbindung upgraden:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (oder: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Der erste Frame MUSS response.create sein:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Ein Responses-API-over-WebSocket-Proxy ist **ausschließlich mit `codex`** (ChatGPT-
Backend) verbunden. Er lauscht auf demselben Port wie die API/das Dashboard unter den Pfaden `/v1/responses`,
`/responses` und `/api/v1/responses`. Beim ersten `response.create`-Frame
authentifiziert und initialisiert er über die interne `codex-responses-ws`-Bridge, wählt eine
codex-OAuth-Verbindung aus und tunnelt über den `wreq-js`-Transport zu `wss://chatgpt.com/backend-api/codex/responses`.
**Nicht-codex-Modelle werden abgelehnt** (`codex_ws_provider_required`).
Verwenden Sie für Kontingentanteil-Routing `model: "qtSd/<group>/codex/<model>"`. Implementiert in
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Authentifizierung:** Bearer-API-Schlüssel während des Handshakes. Der mitgelieferte HTTP-Server (`server-ws.mjs`)
muss der aktive Einstiegspunkt sein (was standardmäßig der Fall ist, wenn `app/server-ws.mjs` vorhanden ist).

#### Modell-ID: die reine ChatGPT-ID verwenden (ohne `codex/`-Präfix)

Die OpenAI **Codex CLI** validiert den Modellnamen clientseitig, wenn
`supports_websockets = true` festgelegt ist, und **lehnt IDs mit Anbieterpräfix** wie
`codex/gpt-5.5` ab (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Senden Sie die **reine** ID (z. B. `gpt-5.5`). Die Bridge von OmniRoute ist
ausschließlich für codex bestimmt und löst daher eine reine ID vor dem Tunneln zum Upstream-Dienst erneut als codex-Modell auf
(`resolveCodexWsModelInfo`) — obwohl ein reines
`gpt-5.5` über HTTP andernfalls an einen anderen Anbieter weitergeleitet würde.

#### Konfigurieren der OpenAI Codex CLI

Richten Sie die Codex CLI auf OmniRoute aus, indem Sie `~/.codex/config.toml` einen benutzerdefinierten Anbieter mit WebSocket-

vorhandene Konfiguration nicht zu verändern):

```toml

[model_providers.omniroute]
name = "OmniRoute (WS)"
```

```bash

codex exec "Responda apenas: PONG"
```

Server validiert: ChatGPT gibt `codex.rate_limits` + `response.created` zurück und streamt die

## Self-Service-Nutzung (`/api/usage/om-usage`)

Jeder API-Schlüssel kann **seine eigene** Nutzung und seine Kontingente abrufen — ohne Verwaltungsauthentifizierung. Dies ist der Endpunkt, den ein
Client (CLI, das OmniCopilot-Panel) verwendet, um einem Schlüsselinhaber seine Ausgaben anzuzeigen.

```bash
# Textformat (der historische Vertrag — Klartext für ein Terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Strukturiertes Format — wird von einer Benutzeroberfläche verwendet
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Für den Schlüssel muss **`allowUsageCommand`** aktiviert sein (standardmäßig deaktiviert — der API-Schlüsselmanager
des Dashboards schaltet dies für jeden Schlüssel einzeln um). Andernfalls antwortet der Endpunkt mit `403`.

`?format=json` gibt eine diskriminierte Struktur zurück, sodass ein Aufrufer niemals ein Datenfeld aus einer
Ablehnungsantwort liest. Bei Erfolg:

```jsonc
{
  "allowed": true,
  // nur vorhanden, wenn für den Schlüssel schlüsselspezifische Nutzungslimits aktiviert wurden (täglich/wöchentlich in USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // der ausgewählte Snapshot des Anbieterkontingents oder null, wenn noch nichts zwischengespeichert wurde:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // der Snapshot jeder Verbindung, damit eine Benutzeroberfläche mehrere Anbieter nebeneinander darstellen kann:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Bei einer Ablehnung (`401` ungültiger Schlüssel / `403` nicht erlaubt) gibt dieselbe Route
`{ "allowed": false, "error": { "message": "…" } }` zurück — ein vorhandenes, aber leeres `personal`/`provider`
(Schlüssel erlaubt, aber noch keine Daten ermittelt) ist ein anderer Zustand als eine Ablehnung, und nur das JSON-Format
unterscheidet diese Zustände.

**Authentifizierung:** der eigene Bearer-API-Schlüssel des Aufrufers, validiert mit `isValidApiKey` — dies ist _nicht_ die
Verwaltungsoberfläche (`/api/keys/…`), die weiterhin durch `requireManagementAuth` geschützt ist.

### Unveränderte vs. um Schwellenwerte bereinigte Kontingentprozentsätze

Bei der Nutzung von `/api/usage/om-usage` sollten Aufrufer den Unterschied zwischen den Prozentsätzen in der
**Klartextausgabe** und denen in der strukturierten **JSON-Ausgabe** beachten:

| Aspekt                      | Klartextformat (`/api/usage/om-usage` / `@@om-usage`)                                                         | JSON-Format (`?format=json`)                                                     |
| :-------------------------- | :------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------- |
| **Ausgabefeld**             | `NN% left` (z. B. `20% left`)                                                                                 | `provider.quotas` / `providers[].quotas`                                         |
| **Messgröße**               | **Um den Schwellenwert bereinigtes nutzbares Kontingent**: verbleibende Kapazität oberhalb des Schwellenwerts | **Unverändertes Upstream-Kontingent**: nicht angepasster Messwert des Anbieters  |
| **Schwellenwertskalierung** | Mittels `effectiveRemainingPercent()` skaliert, sodass die geschützte Reserve als `0% left` angezeigt wird    | Keine (unveränderte Snapshot-Werte, wie vom Anbieter gemeldet)                   |
| **Schwellenwertdaten**      | In den angezeigten Prozentsatz einbezogen                                                                     | Pro Verbindung in `quotaWindowThresholds` gespeichert (oder Serverstandardwerte) |
| **Hauptnutzer**             | Interaktive CLIs, Terminal-Eingabeaufforderungen, menschliche Bediener                                        | Programmatische Integrationen, Dashboards, Analysen, Abrechnungs-Tracker         |

#### Die Formel zur Schwellenwertbereinigung

OmniRoute unterstützt proaktive Kontingent-Schwellenwerte, um eine Erschöpfung der Upstream-Ressourcen zu verhindern (konfiguriert über
`quotaWindowThresholds` der Verbindung, Anbietervorgaben oder globale Resilienz-Einstellungen). Wenn für ein Kontingentfenster ein Schwellenwert
(z. B. `cutoff = 25%`) aktiv ist, berechnet der Text-Renderer das verbleibende Kontingent wie folgt:

- Wenn `remaining <= cutoff`: gibt `0%` zurück.
- Wenn `remaining > cutoff`: gibt `((remaining - cutoff) / (100 - cutoff)) * 100` zurück.

Die formatierte Textausgabe rundet dies auf die nächste Ganzzahl (`Math.round(...)`).

#### Veranschaulichendes Beispiel

Betrachten Sie ein Anbieterfenster mit **60 % unveränderter Nutzung** (also **40 % unverbleibendem Rohkontingent**) und einem konfigurierten
**Schwellenwert von 25 % des verbleibenden Kontingents**:

| Darstellung                             | Berechnung                                         | Verbleibend |                Implizit genutzt                 |
| :-------------------------------------- | :------------------------------------------------- | :---------: | :---------------------------------------------: |
| **Unverändertes JSON (`?format=json`)** | Upstream-Snapshot (`quotas[window]`)               |  **40 %**   |                    **60 %**                     |
| **Textformat (`NN% left`)**             | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20 %**   | **80 %** (bei Berechnung von `100 - remaining`) |

- **Warum der Text 20 % verbleibend anzeigt:** Von den 40 % des physischen Kontingents, die für das Konto verbleiben, sind 25 % durch die
  Schwellenwertrichtlinie reserviert. Dem Aufrufer verbleiben nur 15 % von 75 % nutzbarem Spielraum, bevor der Router das Routing
  zu dieser Verbindung einstellt. Durch die Skalierung signalisiert die Verbindung genau dann Erschöpfung (`0% left`), wenn
  das Routing eingestellt wird.
- **Warum JSON die unveränderten Werte beibehält:** Die JSON-Nutzlast gibt den exakten Anbieter-Snapshot (`UsageSnapshot`) zurück,
  sodass externe Tools ohne verlustbehaftete serverseitige Skalierung Zugriff auf die tatsächliche Upstream-Auslastung und die
  verbindungsspezifischen `quotaWindowThresholds` haben.

#### Migrationshinweise für Nutzer

Wenn eine externe Integration (wie etwa ein Editor-Plugin oder eine Agent-Erweiterung) zuvor den Textendpunkt (`NN% left`) ausgelesen und den verbrauchten Prozentsatz als `100 - NN` berechnet hat, bedeutet die Migration zu `?format=json` Folgendes:

- Das Auslesen der JSON-Rohwerte spiegelt den **tatsächlichen Upstream-Verbrauch** wider (im obigen Beispiel wurden 60 % verbraucht).
- Wenn die Integration die Semantik des nutzbaren Kontingents des Textendpunkts beibehalten möchte, kann sie die Formel für den effektiven Restwert clientseitig auswerten und dabei `quotaWindowThresholds` für Überschreibungen auf Verbindungsebene verwenden.

### Auswirkungen auf die Latenz

Bei einem Treffer im semantischen Cache wird die Antwort **ohne einen
Upstream-Aufruf** aus dem Cache bereitgestellt, sodass die gemeldete
`X-OmniRoute-Response-Latency` nahezu null beträgt (unabhängig von der
ursprünglichen Upstream-Latenz). Latenzempfindliche Clients (Benchmarking,
p50/p99-Überwachung) sollten den Antwort-Header
`X-OmniRoute-Cache-Latency` prüfen:

| Wert        | Bedeutung                                                       |
| ----------- | --------------------------------------------------------------- |
| `synthetic` | Antwort aus dem Cache; die Latenz ist keine reale Upstream-Zeit |
| _(fehlend)_ | Antwort aus einem tatsächlichen Upstream-Aufruf                 |

### Cache-Umgehung pro Schlüssel

API-Schlüssel können über `cacheDefaultMode` das Lesen aus dem semantischen Cache deaktivieren:

| Wert     | Verhalten                                                       |
| -------- | --------------------------------------------------------------- |
| `legacy` | Normales Cache-Verhalten (Standard)                             |
| `bypass` | Cache-Abfrage vollständig überspringen; immer Upstream aufrufen |

Bei der Schlüsselerstellung (`POST /api/keys`) festlegen oder aktualisieren (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Umgehung pro Anfrage

Jede Anfrage kann den Cache unabhängig von den Schlüsseleinstellungen umgehen:

```
X-OmniRoute-No-Cache: true
```

Für synchronisierte/importierte Modelle akzeptiert `PUT /api/provider-models` die Felder `provider`, `modelId` und
`maxOutputTokenOverride`: Eine positive Ganzzahl legt die manuelle Begrenzung der Ausgabetoken fest, und `null`

verwendet die Laufzeitfunktion `max_output_tokens` und bleibt nach einer erneuten Modellsynchronisierung erhalten. Die Seite für OpenAI-kompatible
Anbieter bietet dieselben Steuerelemente zum Bearbeiten/Entfernen und kennzeichnet Modelle mit expliziter Vision-Unterstützung.

Benutzerdefinierte Chat-Completions-Knoten passen explizite Deaktivierungen des Reasonings an das Upstream-Backend an. Ein
erfolgreicher Verbindungstest wählt automatisch Chat-Template-Steuerelemente für jede exakte Modell-ID aus,
deren `/models`-Eintrag einen anerkannten `owned_by`-Wert nachweist: `vllm`, `sglang` oder `llamacpp`.
Transparente OpenAI-kompatible Wrapper können den ursprünglichen Modelleintrag innerhalb eines verschachtelten
`openai`-Objekts beibehalten; die Erkennung folgt bis zu drei solchen Hüllen. Modelle mit fehlenden, unbekannten oder
widersprüchlichen Eigentümerangaben behalten das gewöhnliche OpenAI-Verhalten bei. Die Erkennung verwendet die vorhandene Kataloganfrage erneut,
erzeugt keine Completion-Token und wird ungültig, wenn sich der Verbindungsendpunkt ändert.

Um das Verhalten für ein Backend festzulegen, das diese Metadaten nicht bereitstellt, verwenden Sie die vorhandene API
für partielle Anbieteraktualisierungen:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Senden Sie diesen Body mit `PUT /api/providers/<connection-id>`. Bei dieser Verbindung wird ein expliziter
Reasoning-Aufwand von `none` als `chat_template_kwargs.thinking=false` und
`chat_template_kwargs.enable_thinking=false` gesendet. Explizite native Template-Werte bleiben maßgeblich,
sofern nicht eine serverseitige Reasoning-Regel einen Aufwand erzwingt. Die Einstellung gilt nur, wenn eine benutzerdefinierte
OpenAI-kompatible Verbindung einen Chat-Completions-Body weiterleitet; Responses-Anfragen und gewöhnliche
Anbieter behalten ihre native Anfragestruktur bei. Setzen Sie `reasoningControl` auf `openai`, um die gewöhnliche OpenAI-
Weitergabe von `reasoning_effort` zu erzwingen, oder lassen Sie es weg bzw. setzen Sie es auf `null`, um die automatische Erkennung zu verwenden.

Bei Anfragen des Claude-Code-Automodus-Klassifikators ist natives Thinking standardmäßig deaktiviert, wenn sie
keine expliziten Reasoning-Steuerelemente enthalten. Die Erkennung verwendet die Systemmarkierung des Klassifikators in Anfragen
im Claude-Format, nicht Modellnamen oder Completion-Limits. Explizite Body-Steuerelemente, unterstützte Aufwand-/Thinking-
Header, Routing-Regeln und der aufgelöste Modellaufwand behalten ihre bestehende Priorität bei. Beide Klassifikator-
Stufen behalten ihre Prompts, Completion-Limits, Stoppsequenzen und tatsächlichen Upstream-Berechtigungsentscheidungen
bei; die zweite Stufe kann ihr angefordertes sichtbares Reasoning weiterhin als gewöhnlichen Text ausgeben.

### Version und Veröffentlichungskanal

```bash
GET /api/system/version
```

Nur über Loopback erreichbare Verwaltungsroute (Admin-Authentifizierung). Gibt die ausgeführte Version, die neueste
veröffentlichte Version und den Status der automatischen Aktualisierung zurück. `releaseChannel` und `channels` sind additive
Felder (Zweig 3.8.54); `channel` behält seine Bedeutung bei — den Bereitstellungsmodus, den das Dashboard-Aktualisierungsprogramm
verwendet (`npm`, `source` oder `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-Kanal des ausgeführten Builds: `nightly` für `-nightly.*`-Versionen,
  `next` für andere Vorabversionen (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` für eine stabile Version einer
  älteren Hauptversion als `channels.latest`, andernfalls `latest`. Es gelten dieselben Regeln wie in
  `scripts/release/dist-tag.mjs`, das bei der Veröffentlichung das npm-Dist-Tag auswählt.
- `channels` — veröffentlichter Spitzenstand jedes Dist-Tags aus `npm view omniroute dist-tags` (HTTP-Fallback
  der Registry), zwischengespeichert mit derselben TTL von 10 Minuten wie `latest`. `latest` ist immer vorhanden
  (greift ersatzweise auf das Feld `latest` und anschließend auf `"unavailable"` zurück); `next`, `nightly` und `lts` werden
  nur angezeigt, wenn das jeweilige Dist-Tag vorhanden ist. Eine `Cache-Control: no-cache`-Anfrage aktualisiert beide Abfragen.

Das Kanalmodell (`latest` = v3 bis zur allgemeinen Verfügbarkeit von 4.0, `next` = RC, `nightly` = Builds aus `develop`,
`lts` = v3-Patches nach der allgemeinen Verfügbarkeit von 4.0) wird in `docs/ops/RELEASE_STRATEGY.md` beschrieben.

## Audiotranskription

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transkribieren Sie Audiodateien mit einem beliebigen konfigurierten STT-Anbieter. Das erste Pfadsegment
wählt den nativen Anbieter aus (`openai/…`, `deepgram/…`). Gateways, die das
Modell eines anderen Anbieters erneut bereitstellen, verwenden eine qualifizierte ID
(`openrouter/deepgram/nova-3`).

**Anfrage:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Antwort:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Beispiele für Modell-IDs:** `openai/whisper-1` (erfordert einen OpenAI-Schlüssel),
`openrouter/deepgram/nova-3` (erfordert einen OpenRouter-Schlüssel),
`deepgram/nova-3` (erfordert einen nativen Deepgram-Schlüssel). Eine einfache
`deepgram/nova-3`-Anfrage verwendet **nicht** OpenRouter.

**Unterstützte Formate:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Tokenisierte VS-Code-Aliasse / Aliasse ohne Header

Verwenden Sie diese Aliasse, wenn eine Integration keinen `Authorization`-Header einfügen kann und der API-Schlüssel in die Basis-URL eingebettet werden muss.

```bash
# Katalog-Alias im OpenAI-Stil
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Chat-Aliasse im OpenAI-Stil
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Aliasse im Ollama-Stil
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Beispiel:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Hinweise:

- Die tokenisierten Aliasse verwenden dieselben Handler wie `/v1/*` und `/api/tags`; die Antwortstrukturen bleiben identisch.
- Verwenden Sie nach Möglichkeit `Authorization: Bearer ...`, wenn der Client benutzerdefinierte Header unterstützt.
- URL-basierte Token können in Reverse-Proxy-Protokollen, im Browserverlauf und in Telemetriedaten außerhalb von OmniRoute erscheinen. Betrachten Sie sie als Kompatibilitätsoption, nicht als standardmäßigen Authentifizierungsmodus.

## Budget

```bash

```

> **Schemahinweise** (`setBudgetSchema`): `apiKeyId` ist erforderlich; mindestens einer der Werte `dailyLimitUsd`, `weeklyLimitUsd` oder `monthlyLimitUsd` muss größer als null sein. Optionale Felder: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Das veraltete Format `{keyId, limit, period}` gibt `400 Bad Request` zurück.

## Token-Limits

**Token**-Budgets pro API-Schlüssel (unabhängig vom oben beschriebenen USD-basierten Budget). Sie werden direkt im Anfragepfad durchgesetzt: Sobald die Nutzung eines Schlüssels im aktuellen Zeitfenster sein Limit erreicht, werden Anfragen mit `429 Too Many Requests` abgelehnt. Limits können auf ein bestimmtes `model`, einen `provider` oder `global` für den gesamten Schlüssel festgelegt werden. Wenn mehrere Limits auf eine Anfrage zutreffen, gilt das restriktivste.

```bash
# Token-Limits eines Schlüssels auflisten (einschließlich der aktuellen Nutzung im Zeitfenster)
GET /api/usage/token-limits?apiKeyId=key-123

# Token-Limit erstellen oder aktualisieren
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Token-Limit anhand der ID löschen
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schemahinweise** (`setTokenLimitSchema`): `apiKeyId` und `scopeType` (`model` | `provider` | `global`) sind erforderlich. `scopeValue` ist erforderlich, sofern `scopeType` nicht `global` ist (z. B. eine Modell-ID für den Gültigkeitsbereich `model` oder eine Anbieter-ID für den Gültigkeitsbereich `provider`). `tokenLimit` muss eine positive Ganzzahl sein (wird aus einer Zeichenfolge konvertiert). Optional: `id` (zum Erstellen weglassen, zum Aktualisieren angeben), `resetInterval` (`daily` | `weekly` | `monthly`, Standardwert `monthly`), `resetTime` (`HH:MM`), `enabled` (Standardwert `true`). `GET`-Antworten ergänzen jedes Limit um `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` und `nextResetAt`. Dies ist ein Verwaltungsendpunkt (die Authentifizierung wird zentral durch die Autorisierungspipeline durchgesetzt).

## Anfrageverarbeitung

1. Der Client sendet eine Anfrage an `/v1/*`
2. Der Routen-Handler ruft `handleChat`, `handleEmbedding`, `handleAudioTranscription` oder `handleImageGeneration` auf
3. Das Modell wird aufgelöst (direkter Anbieter/direktes Modell oder Alias/Combo)
4. Anmeldedaten werden aus der lokalen Datenbank ausgewählt, wobei die Kontoverfügbarkeit berücksichtigt wird
5. Für Chat-Anfragen prüft `handleChatCore` den semantischen/Signatur-Cache und löst die Komprimierungseinstellungen der Combo auf
6. Wenn aktiviert, wird vor der Anbieterübersetzung eine proaktive Komprimierung ausgeführt (`lite`, Caveman, RTK oder gestapelt)
7. Der Anbieter-Executor sendet die Upstream-Anfrage
8. Die Antwort wird zurück in das Clientformat übersetzt (Chat) oder unverändert zurückgegeben (Embeddings/Bilder/Audio)
9. Nutzung, Komprimierungsanalysen und Anfrageprotokolle werden aufgezeichnet
10. Bei Fehlern wird gemäß den Combo-Regeln ein Fallback angewendet

Vollständige Architekturreferenz: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resilienz (erweitert)

OmniRoute stellt drei unabhängige Mechanismen für vorübergehende Fehler bereit; über die nachfolgenden Verwaltungsendpunkte können Betreiber deren Status abrufen und überschreiben:

| Geltungsbereich          | Statusspeicher                               | Abrufen                                   | Zurücksetzen / löschen                                        |
| ------------------------ | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| Provider-Circuit-Breaker | `domain_circuit_breakers` + In-Memory        | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                  |
| Verbindungs-Cooldown     | `rateLimitedUntil` für Provider-Verbindungen | `/api/rate-limits`, `/api/providers/[id]` | (wird bei Bedarf erneut aktiviert; Löschen über Provider-PUT) |
| Modellsperre             | In-Memory-Register der Modellverfügbarkeit   | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                      |

`PATCH /api/resilience` akzeptiert Überschreibungen für Provider-Circuit-Breaker unter `providerBreaker.oauth` und `providerBreaker.apikey`. Jedes Profil unterstützt `degradationThreshold`, `failureThreshold` und `resetTimeoutMs`; dieselben Felder sind unter Dashboard → Einstellungen → Resilienz verfügbar.

```bash
# Eine einzelne Modellsperre löschen
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Alle Sperren löschen
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Vollständige konzeptionelle Referenz und Circuit-Breaker-Standardwerte: siehe [`CLAUDE.md`](../../CLAUDE.md) → „Resilienz-Laufzeitstatus“ und [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Ratenbegrenzungswarteschlange und Sicherheitsnetz zur automatischen Aktivierung

- **Unterstützter Schreibpfad**: `POST /api/rate-limits` mit dem Body `{"connectionId": "<id>", "enabled": true|false}` ist der unterstützte Verwaltungsendpunkt, um den Ratenbegrenzungsschutz für eine Verbindung umzuschalten. `PUT /api/providers/[id]` ändert oder invertiert `rateLimitProtection` absichtlich nicht (#11278).
- **Semantik von `enabled: false`**: Durch das Setzen von `enabled: false` wird der explizite Schutz für die Verbindung entfernt, eine aktive API-Schlüsselverbindung wird dadurch jedoch **nicht** vom globalen Sicherheitsnetz zur automatischen Aktivierung (`autoEnableApiKeyProviders = true`) ausgenommen. In `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) sind `false` und `undefined` gleichwertig; aktive API-Schlüsselverbindungen ohne expliziten Schutz bleiben durch das Sicherheitsnetz zur automatischen Aktivierung geschützt.
- **Globale Deaktivierung**: Um API-Schlüsselverbindungen ohne Ratenbegrenzungswarteschlangen auszuführen, deaktivieren Sie das Sicherheitsnetz global über `RATE_LIMIT_AUTO_ENABLE=false` (Umgebungsvariable) oder `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Einstellungen → Resilienz / `PATCH /api/resilience`).

## Authentifizierung

Siehe [Management-Authentifizierung](../guides/MANAGEMENT-AUTH.md) für die vier
Anmeldedatenfamilien (Dashboard-Sitzung, lokales CLI-Token, `oma_live_…`-Zugriffs-
Token, API-Schlüssel mit Management-Berechtigung) und ihre Unterschiede zu Inferenzschlüsseln.

- Dashboard-Routen (`/dashboard/*`) verwenden das `auth_token`-Cookie
- Die Anmeldung verwendet den gespeicherten Passwort-Hash; ersatzweise wird `INITIAL_PASSWORD` verwendet
- `requireLogin` kann über `/api/settings/require-login` umgeschaltet werden
- `/v1/*`-Routen erfordern optional einen Bearer-API-Schlüssel, wenn `REQUIRE_API_KEY=true` gilt
- „Management-Token“ / „API-Schlüssel mit Management-Berechtigung“ bezeichnet in dieser Referenz eine der Familien aus diesem Leitfaden — nicht einen zusätzlichen, undefinierten Geheimnistyp

> **Inkompatible Änderung (v3.8.0)** — `/api/v1/agents/tasks/*` und die Endpunkte zur Cooldown-Verwaltung erfordern jetzt eine **Management-Authentifizierung** (`auth_token`-Cookie des Dashboards oder einen API-Schlüssel mit Management-Berechtigung). Clients, die diese Routen zuvor ohne Authentifizierung aufgerufen haben, erhalten nun `401 Unauthorized`. Siehe Commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
