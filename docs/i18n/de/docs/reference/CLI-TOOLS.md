| --------------- | ----------------------- | -------------------------------------------------------------------------------------- | -------------- |

## Funktionsweise

```
CLI-Codes / CLI-Agenten (Nutzungsablauf):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (alle verweisen auf OmniRoute)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute leitet an den richtigen Anbieter weiter)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP-Agenten (umgekehrter Startablauf):
    Client-Anfrage → OmniRoute → startet CLI über stdio/ACP → Antwort
```

**Vorteile:**

- Ein API-Schlüssel zur Verwaltung aller Tools
- Kostenverfolgung für alle CLIs im Dashboard
- Modellwechsel, ohne jedes Tool neu konfigurieren zu müssen
- Funktioniert lokal und auf Remote-Servern (VPS, Docker, Akamai, Cloudflare Tunnel)

## Automatische Konfiguration mit `setup-*`

Sie müssen die Konfiguration jedes Tools nicht manuell schreiben. OmniRoute liefert einen `setup-*` -Befehl pro unterstütztem CLI der das liest** live** Modellkatalog von einem laufenden OmniRoute (lokal oder remote) und schreibt die eigene Konfiguration des Tools auf Ihren Computer:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
omniroute setup-whycodes
```

Jeder akzeptiert `--remote <url> --api-key <key>` (ein lokales Tool für ein entferntes OmniRoute konfigurieren), `--dry-run` (Vorschau ohne Schreiben) und `--port`. Werkzeuge ohne automatische Modellerkennung (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive, WhyCodes) verwenden `--model <id>` (und `--yes` für nicht interaktive Läufe). `setup-5dive` ist das einzige Rezept, das nicht unter `$HOME` schreibt: Es konfiguriert eine 5dive-Agentenflotte, indem es ein Root-eigenes Authentifizierungsprofil auf dem Flottenhost schreibt, sodass es über `sudo` erneut ausgeführt wird und keinen eigenen Remote-Modus hat. Um einen CLI mit der richtigen eingefügten Umgebung und ohne geschriebene Konfiguration zu starten, verwenden Sie den generischen `omniroute run <target>` Launcher (Claude, Codex, Aider, Goose, Opencode, Qwen, Gemini, Whycodes – Ziele und Aliase stammen von `bin/cli/cli-manifest.mjs`). Die veralteten pro-Tool-Launcher `omniroute launch` (Claude Code) und `omniroute launch-codex` (Codex) bleiben verfügbar. Gemini CLI ist nur für den Start gedacht: Es ist ein `omniroute run` Ziel, hat aber kein `setup-*`/`configure` -Rezept.

> **Vollständige Referenz:** Die Master-Tabelle – was jeder Befehl schreibt, jedes Flag, lokal oder remote und welche Tools ein `/v1` Suffix benötigen – lebt darin** [CLI Integrationen](../guides/CLI-INTEGRATIONS.md)** .

### Führen Sie diese in einem Container aus

Ein im OmniRoute Container ausgeführter `setup-*` -Befehl schreibt in das eigene Home des Containers, das kein Host CLI liest und das mit dem Container verschwindet. OmniRoute erkennt dies und beendet `2` mit Anweisungen, anstatt zu schreiben. Zwei unterstützte Möglichkeiten für die Zukunft: Installieren Sie CLI auf dem Host und `omniroute connect` im Container oder mounten Sie die Konfigurationsverzeichnisse per Bind-Mount und legen Sie `CLI_CONFIG_HOME` (das Compose- `host` Profil) fest. Jeder `setup-*` Befehl sowie `omniroute configure` und `omniroute config set` akzeptiert `--allow-container-write`, wenn Sie den eigenen CLIs des Containers konfigurieren, was Sie eigentlich gemeint haben; `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` macht dasselbe für den Server. Siehe [Docker Anleitung → Konfigurieren von Host- CLI Tools](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker).

Das Dashboard** Endpunkt anwenden** (`POST /api/cli-tools/apply`) erzwingt denselben Schutz: In einem Container antwortet ein Schreibvorgang, dessen Ziel nicht vom Host gebunden ist**`422`** mit `containerEphemeralTarget: true`, dem sicheren Fehlertext und – für die Tools mit einem Host-Rezept (claude, codex, opencode, cline, kilo, continue) – einem `hostSetupCommand` (z. B. `omniroute setup-opencode`), das stattdessen auf dem Host ausgeführt wird; nichts ist geschrieben. `dryRun: true` arbeitet weiterhin im Containermodus und gibt einen geschwärzten Vorschau- + Zielpfad zurück, ohne die Festplatte zu berühren. Bei Vorschauinhalten handelt es sich nicht um eine Konfiguration mit Anmeldeinformationen, die kopiert oder importiert werden kann. Wenden Sie es mit den ursprünglichen tool/base URL/API key/model Eingaben auf dem Host an oder verwenden Sie den angegebenen hostseitigen Setup-Befehl. Informationen zum Vorschau-Header und Anforderungsvertrag finden Sie unter [CLI -Konfigurationssicherheit](../security/CLI-CONFIGURATION.md). Dieses Verhalten ist beabsichtigt und wird von `tests/unit/api/cli-tools/apply-container-guard.test.ts` durch Regression geschützt – „reparieren“ Sie niemals einen 422-Fehler, indem Sie den Schutz entfernen.

## Maßgebliche Quelle

Der vereinheitlichte Katalog befindet sich in `src/shared/constants/cliTools.ts` als `CLI_TOOLS: Record<string, CliCatalogEntry>`.

Jeder Eintrag enthält diese Felder (definiert in `src/shared/schemas/cliCatalog.ts`):

| Feld                                            | Typ                                                          | Beschreibung                                                                  |
| ----------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `category`                                      | `"code" \| "agent"`                                          | Auf welcher Seite das Tool erscheint                                          |
| `vendor`                                        | `string`                                                     | Herkunft des Tools ("Anthropic", "OSS (P. Gauthier)")                         |
| `acpSpawnable`                                  | `boolean`                                                    | Auch als ACP-Agent verwendbar (Badge wird angezeigt)                          |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | Unterstützungsstufe für benutzerdefinierte Endpunkte. `"none"` = MITM-Backlog |
| `configType`                                    | `"env" \| "custom" \| "guide" \| "custom-builder" \| "mitm"` | Konfigurationsmechanismus                                                     |
| `id`, `name`, `color`, `description`, `docsUrl` | Standard                                                     | Zentrale Anzeigefelder                                                        |

Einträge mit `baseUrlSupport: "none"` werden auf den Dashboard-Seiten **nicht angezeigt** – sie sind im MITM-Backlog für Plan 11 registriert (siehe `_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md`).

### Funktionsstufen (katalogisiert × erkennbar × konfigurierbar × startbar)

Nicht jedes katalogisierte Tool ist erkennbar, konfigurierbar oder startbar. Für jede Stufe gibt es genau
eine deklarierende Quelle, und ein Drift-Test stellt sicher, dass sie aufeinander abgestimmt bleiben:

| Stufe              | Bedeutung                                                                              | Deklariert in                                                     |
| ------------------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **Katalogisiert**  | Erscheint im Dashboard-Katalog (Name, Anbieter, Dokumentation, Konfigurationstyp)      | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                  |
| **Erkennbar**      | Binärdatei-/Konfigurationserkennung, Integritätsprüfungen, Konfigurationspfade         | `src/shared/services/cliRuntime.ts` (`CLI_TOOLS`-Laufzeitkatalog) |
| **Konfigurierbar** | Wird von `omniroute configure <cli>` unterstützt (Einrichtungsrezept vorhanden)        | `bin/cli/cli-manifest.mjs` (`configure: true`)                    |
| **Startbar**       | Wird von `omniroute run <target>` unterstützt (Umgebungs-/Argumentinjektion definiert) | `bin/cli/cli-manifest.mjs` (`run: true`)                          |

`bin/cli/cli-manifest.mjs` ist das kanonische ausführbare Manifest für die Oberflächen der CLI-Befehle:
`run`, `configure` und die Generatoren für die Shell-Vervollständigung leiten daraus jeweils ihre
Ziellisten, die Aliasauflösung (zum Beispiel `kilocode`/`kilo-code`/`kilo_cli` → `kilo`)
und die Einbindung des Flags `--model` ab. Die Drift-Schutzprüfung
`tests/unit/cli/cli-manifest-drift.test.ts` stellt sicher, dass das Manifest, der Laufzeitkatalog,
der UI-Katalog und alle konsumierenden Oberflächen synchron bleiben – ein Ziel, das nur einer
Oberfläche hinzugefügt wird, führt zum Fehlschlagen der Testsuite, anstatt unbemerkt abzuweichen.

## 5. API zur Batch-Erkennung

Die gesamte Tool-Erkennung wird über einen einzigen Endpunkt aggregiert:

**`GET /api/cli-tools/all-statuses`**

- Authentifizierung: `requireCliToolsAuth(request)` (wie bei anderen `/api/cli-tools/`-Routen)
- Rückgabe: `Record<toolId, ToolBatchStatus>` (Typ: `src/shared/types/cliBatchStatus.ts`)
- Strategie: `Promise.all` über alle Tools, Zeitüberschreitung von 5 Sekunden pro Tool
- Cache: In-Memory-LRU, indiziert nach `mtime` der Konfigurationsdatei. Der Cache wird bei einer Änderung von `mtime` invalidiert. Zurücksetzung bei einem Serverneustart.

Antwortstruktur pro Tool:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // bereinigt, keine Stacktraces
}
```

## 10. Interne OmniRoute-CLI

Das Binärprogramm `omniroute` stellt Befehle für den Serverlebenszyklus, die Einrichtung, Diagnose und Providerverwaltung bereit. Einstiegspunkt: `bin/omniroute.mjs`.

```bash
omniroute                              # Server starten (Standardport 20128)
omniroute setup                        # Interaktiver Einrichtungsassistent
omniroute doctor                       # Konfiguration, DB, Ports und Laufzeit prüfen
omniroute providers list               # Konfigurierte Providerverbindungen
omniroute providers test-all           # Jede aktive Verbindung testen
omniroute reset-password               # Administratorpasswort zurücksetzen
omniroute logs                         # Anforderungsprotokolle streamen
omniroute health                       # Detaillierter Zustand (Unterbrecher, Cache, Arbeitsspeicher)
omniroute --version                    # Version ausgeben
omniroute --help                       # Alle Befehle anzeigen
```

### Einrichtung & Initialisierung

```bash
omniroute setup                        # Interaktiver Einrichtungsassistent
omniroute setup --non-interactive      # CI-/Automatisierungsmodus (liest Umgebungsvariablen + Flags)
omniroute setup --password '<value>'   # Administratorpasswort direkt festlegen
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # Einen Provider in einem Schritt hinzufügen und testen
```

Erkannte Umgebungsvariablen für die nicht interaktive Einrichtung:

| Variable            | Zweck                                                                    |
| ------------------- | ------------------------------------------------------------------------ |
| `OMNIROUTE_API_KEY` | Provider-API-Schlüssel (über Commander `.env()` an `--api-key` gebunden) |
| `DATA_DIR`          | OmniRoute-Datenverzeichnis überschreiben                                 |

Alle anderen nicht interaktiven Eingaben werden als Flags und nicht als Umgebungsvariablen übergeben:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(siehe die Optionen von `omniroute setup` oben).

### Diagnose

```bash
omniroute doctor                       # Konfiguration, DB, Ports, Laufzeit, Arbeitsspeicher und Erreichbarkeit prüfen
omniroute doctor --json                # Maschinenlesbares JSON
omniroute doctor --no-liveness         # HTTP-Zustandsprüfung überspringen
omniroute doctor --host 0.0.0.0        # Host für die Erreichbarkeitsprüfung überschreiben
omniroute doctor --liveness-url <url>  # Vollständige URL des Zustandsendpunkts überschreiben
```

Der Doctor führt folgende Prüfungen aus: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` und `Server liveness`. Er wird mit einem Exit-Code ungleich null beendet, wenn eine Prüfung den Status `fail` aufweist.

### Providerverwaltung

```bash
omniroute providers available                       # OmniRoute-Providerkatalog
omniroute providers available --search openai       # Katalog nach ID/Name/Alias/Kategorie filtern
omniroute providers available --category api-key    # Nach Kategorie filtern (api-key, oauth, free, ...)
omniroute providers available --json                # Maschinenlesbares JSON

omniroute providers list                            # Konfigurierte Providerverbindungen
omniroute providers list --json

omniroute providers test <id|name>                  # Eine konfigurierte Verbindung testen
omniroute providers test-all                        # Jede aktive Verbindung testen
omniroute providers validate                        # Rein lokale Strukturvalidierung
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # Bestehender OAuth-Ablauf
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` sind API-orientiert und funktionieren daher mit
dem aktiven lokalen oder entfernten Kontext. Anmeldedaten sollten über
`--credential-stdin` oder `--credential-env` eingegeben werden; `--dry-run --json` meldet nur
redigierte Angaben zu Vorhandensein und Struktur. `providers available` liest den OmniRoute-Katalog;
`providers list/test/test-all/validate` behalten ihr lokales SQLite-Verhalten bei und
erfordern keinen laufenden Server.

Hängen Sie für einen benutzerdefinierten OpenAI- oder Anthropic-kompatiblen Knoten Anmeldedaten an
die von `omniroute nodes add` zurückgegebene Knoten-ID an, indem Sie `omniroute keys add "$NODE_ID" --stdin` verwenden.
Dies erfordert einen laufenden Server und eine Verwaltungsauthentifizierung für den aktiven Kontext.
Die CLI verwendet `POST /api/providers`, wodurch der Knoten validiert und dessen Endpunkteinstellungen
in die Verbindung kopiert werden. Bei einem fehlenden Knoten, einer fehlgeschlagenen Autorisierung oder einem nicht verfügbaren
Server wird ein Fehler zurückgegeben, ohne lokale Ersatzanmeldedaten zu erstellen.

`nodes add --base-url` legt den Knotenendpunkt fest; dieser unterscheidet sich von der Serveradresse
in `OMNIROUTE_BASE_URL`. Verwenden Sie für OpenAPI-Dateien
`omniroute openapi dump --format json --out ./openapi.json`; das globale `--output`
bestimmt die Anzeigeformatierung der CLI und nicht den Namen einer Zieldatei.

### Wiederherstellung & Zurücksetzen

```bash
omniroute reset-password                # Administratorpasswort zurücksetzen (auch: omniroute-reset-password)
omniroute reset-encrypted-columns       # Warnung + Testlauf für das Zurücksetzen verschlüsselter Anmeldedaten anzeigen
omniroute reset-encrypted-columns --force  # Verschlüsselte Anmeldedaten in SQLite tatsächlich auf null setzen
```

### Export von Anmeldedaten (⚠ mit Vorsicht behandeln)

```bash
omniroute auth export                                 # Warnung + Bestätigungsabfrage anzeigen — kein DB-Zugriff
omniroute auth export --force                          # ENTSCHLÜSSELTE Anmeldedaten ALLER Verbindungen als JSON auf stdout exportieren
omniroute auth export --force --id <id>                 # Nur die übereinstimmende Verbindung exportieren
omniroute auth export --force --format env               # Zeilen im Format OMNIROUTE_<PROVIDER>_<FIELD>=<value> ausgeben
omniroute auth export --force --out creds.json           # In eine Datei schreiben (mit Berechtigungen 0600 erstellt)
```

`auth export` funktioniert **nur lokal** (direkter SQLite-Lesezugriff, keine HTTP-Route) und gibt absichtlich
**unverschlüsselte** `apiKey`-/`accessToken`-/`refreshToken`-/`idToken`-Werte aus bzw. schreibt sie — das ist eine Funktion und kein
Fehler. Ohne `--force` wird nichts aus der Datenbank gelesen und nichts entschlüsselt. Bevor unverschlüsselte Daten ausgegeben werden, erscheint auf stderr
immer ein Warnhinweis. Erfordert, dass `STORAGE_ENCRYPTION_KEY`
gesetzt ist. Bei einem Feld, das nicht entschlüsselt werden kann (veralteter Schlüssel, beschädigter Geheimtext), wird
`<field>DecryptFailed: true` gemeldet, statt den gesamten Export abzubrechen oder den zugrunde liegenden Fehler offenzulegen.

## Richtlinie für Inferenzschlüssel mit der OmniRoute CLI verwalten

Verwenden Sie einen authentifizierten Verwaltungskontext (siehe [Remote-Modus](../guides/REMOTE-MODE.md)),
um einen vorhandenen Inferenzschlüssel anhand seiner ID zu überprüfen oder zu aktualisieren:

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted` ist ein Alias für `--model-access-mode all`. Durch die Aktualisierung wird die
Modell-Zulassungsliste gelöscht. Gültigkeitsbereiche, Verbindungsregeln, gesperrte Modelle, Ratenbegrenzungen
und Kostenlimits bleiben erhalten, sodass diese anderen Kontrollen eine Anfrage weiterhin ablehnen können. Ein explizites
`--allowed-models ""` wählt ebenfalls `all`; kombinieren Sie es mit
`--model-access-mode restricted`, um einen eingeschränkten Schlüssel ohne zulässige Modelle beizubehalten.
Eine nicht leere, durch Kommas getrennte Liste wählt `restricted`, sofern nicht ausdrücklich anders angegeben.
Die widersprüchliche Kombination aus `all` und einer nicht leeren Zulassungsliste wird vor dem Senden einer Anfrage abgelehnt.

`--rate-limit 30` legt die Anzahl der Anfragen pro Minute fest und behält Regeln für andere
Zeitfenster bei. `--max-cost 5` aktiviert die tägliche Obergrenze in USD, ohne die wöchentliche Obergrenze zu ändern;
`--max-cost 0` entfernt die tägliche Obergrenze und behält den vorhandenen Schalter für das
Nutzungslimit sowie die wöchentliche Obergrenze bei. Nicht angegebene Richtlinienfelder bleiben unverändert. Bei Änderungen der Ratenbegrenzung wird
zunächst die aktuelle Richtlinie gelesen; vermeiden Sie gleichzeitige Änderungen am Ratenbegrenzungs-Array desselben Schlüssels.

Richtlinienbefehle verwenden authentifizierte `GET`/`PATCH /api/keys/{id}`-Anfragen und berücksichtigen den aktiven
Kontext sowie die globale Option `--api-key`. Die JSON-Ausgabe enthält ausschließlich Richtlinienfelder,
nicht den gespeicherten Schlüssel oder dessen maskierte Darstellung. Eine ausschließlich für Inferenz vorgesehene Anmeldeinformation
kann keine Verwaltungsänderungen autorisieren. Bei einem 401/403-Fehler müssen die Verwaltungsanmeldeinformationen
und der Kontext überprüft werden; dies ist kein Nachweis für einen Fehler des lokalen CLI-Tokens oder Salts.
Informationen zum separaten lokalen Authentifizierungsvertrag finden Sie unter [CLI-Token](../security/CLI_TOKEN.md).
