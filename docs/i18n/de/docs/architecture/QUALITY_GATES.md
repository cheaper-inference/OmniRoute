Dieses Dokument ist die verbindliche Referenz für alle CI-Qualitätsprüfungen in OmniRoute.
Es beschreibt jede Prüfung, was sie validiert, in welchem CI-Job sie ausgeführt wird, ob sie
eine Ratchet-Baseline oder eine Bestanden/Nicht-bestanden-Richtlinie verwendet und ob sie den Build blockiert oder nur informativen Charakter hat.

Eine kurze Zusammenfassung und die Allowlist-Richtlinie finden Sie im Abschnitt „Quality Gates & Ratchets“
in `AGENTS.md`. Die kritische Bewertung, Reifegradklassifizierung und den werkzeugunabhängigen
Replikationsplan desselben Systems finden Sie im
[Quality Gate Playbook](../ops/QUALITY_GATE_PLAYBOOK.md).

## Torbestands- und Ausführungsprofile

### Kandidatenzulassung

Die Workflows CI und Quality Gates geben jeweils ein stabiles Urteil aus: `Gate / CI` und `Gate / Quality`. Ihre versionierte Zulassungsrichtlinie listet jeden Upstream-Job nach Bedarf oder Empfehlung auf. Ein anwendbarer erforderlicher Job muss erfolgreich sein: Fehlende, abgebrochene, übersprungene, ausstehende und unbekannte Ergebnisse können PASS nicht ermitteln. Eine gültige Nur-Dokumente- oder Nur-Katalog-Klassifizierung kann dazu führen, dass eine Codespur nicht anwendbar ist. Ein PR -Entwurf ist kein akzeptierter Kandidat. Ein `hotfix` -Label verzichtet nicht auf Beweise.

Beide Workflows decken PRs in main/release Zweige, Push-Vorgänge zu `main`, manuelles Versenden und Merge-Group-Ereignisse ab. Push, Dispatch und Merge-Group führen die vollständige Auswahl aus. Pushs an `release/**` starten sie nicht (18.10.2026): Bei jeder Änderung wurde die Matrix bereits auf ihrem PR ausgeführt, und die zusammengeführte Kombination ist die Aufgabe von Release-Green (`docs/ops/RUNNER_BOX.md` → Hosted Lane). Forks und Merge-Gruppen verwenden gehostete Läufer für Jobs, die ansonsten selbstgehostete Läufer auswählen; Vor der Einführung muss eine ausreichende gehostete Kapazität überprüft werden.

Ein gewöhnlicher PR führt die schnelle Auswahl aus. Die `full-code` und `full-code-e2e` Spuren der Zulassungsrichtlinie (E2E, Integration, Paketartefakt, Electron Smoke, Bun SQLite, Ökosystem- und Protokoll-Clients) werden nur bei einem Mergify-Warteschlangenentwurf oder bei einem vollständigen Lauf ausgeführt: `gh workflow run ci.yml --ref <branch>`.

Jeder JSON -Beleg identifiziert den ausgecheckten SHA, die Workflow-Ausführung und den Versuch. Der CLI lehnt eine checkout/event SHA Nichtübereinstimmung ab. Workflow-Tests binden die Richtlinienmitgliedschaft an die `needs` -Liste des Verdict-Jobs, sodass eine neue oder entfernte Spur nicht stillschweigend verschwinden kann. Die Belege decken ihren eigenen Arbeitsablauf ab, nicht die Veröffentlichung, Bereitstellung oder die Interna eines vorhandenen Beratungsscanners. Die Aktivierung beider Prüfnamen in Verzweigungsregeln ist eine separate administrative Änderung; Durch das Hinzufügen dieser Jobs wird ein Zweig nicht geschützt.

### Warteschlange zusammenführen

> **19.11.2026: Die Mergify-Merge-Warteschlange wird eingestellt** (Entscheidung des Eigentümers). `.mergify.yml` definiert keine Warteschlange mehr und lehnt die Mergify-Befehle ab, die eine Pull-Anfrage zusammenführen oder neu schreiben. Release- PRs werden manuell unter dem Repository-Regelsatz „Erfordern grüne Gates für das aktive Release“ (`Gate / CI` + `Gate / Quality`) zusammengeführt, bis Omni-Queue im Live-Modus ausgeführt wird, und danach über Omni-Queue ( [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ). Die unten beschriebene Workflow-Verarbeitung von Mergify-Entwürfen ist weiterhin in `ci.yml` und `quality.yml` vorhanden, es wird jedoch kein Mergify-Entwurf mehr geöffnet.

Das `queue` Label sendet einen PR an die Mergify-Warteschlange (`.mergify.yml`). Mergify öffnet einen PR -Entwurf in einem `mergify/merge-queue/` Zweig, CI führt dort die vollständige Auswahl aus und der ursprüngliche PR wird zusammengeführt, wenn `Gate / CI`, `Gate / Quality` und `Merge integrity (changelog + generated skills)` übergeben werden.

Mergify schreibt seine Warteschlangenzusammenfassung in die Beschreibung des Entwurfs und andere Apps können sie auch bearbeiten. Ein `pull_request` `edited` -Ereignis für einen solchen Entwurf benötigt eine eigene Parallelitätsgruppe (`-queue-edit-<run_id>`), sodass es die tatsächliche Ausführung des Entwurfs nicht abbrechen kann und das Gate und die Matrix überspringt. Nur `Merge integrity` läuft noch. Der übersprungene Gate-Job trägt einen anderen Prüfnamen, da Mergify einen übersprungenen `Gate / CI` als fehlgeschlagene Prüfung liest und den PR aus der Warteschlange entfernt.

Nach einem Auszug aus der Warteschlange wird der PR durch einen Push nicht immer erneut in die Warteschlange gestellt. Kommentiere `@mergifyio queue` dazu.

### Beweissicherung im Akzeptanzminderer

`scripts/quality/validate-release-acceptance.mjs` reduziert einen bereitgestellten Plan und seine Manifeste; Es wird nicht festgestellt, dass der Plan die gesamte Release-Pipeline abdeckt. Seine Berichte legen `releaseAcceptance: false` explizit fest, auch wenn dieser Plan `VERIFIED` ist. Der `release-acceptance.yml` Workflow verwendet weiterhin Schatten-Fixtures, keine echten Build-, Paket-, Boot- oder Promotion-Belege.

Die CLI verpflichtet `--evidence-root` zur Überprüfung der aufbewahrten Beweise. Dateien werden als `<evidence-root>/<artifact_id>/<member>` aufgelöst und als SHA-256 gehasht. Ein PASS Eintrag ohne Beweise, eine fehlende oder geänderte Datei, ein unsicherer Pfad oder ein symbolischer Link verhindern die Überprüfung. Fehlende Dateien sind nicht gleichbedeutend mit leeren erfolgreichen Protokollen. Bestehende SHA/run/attempt -Prüfungen bleiben unabhängig: Übereinstimmende Bytes können eine veraltete Quittung nicht retten. Die Dateiintegrität ist kein Beweis für die Authentizität der Ausführung oder die Förderung von Artefakten.

### Statisches Scan-Inventar

Das versionierte npm-alias-Inventar und die Static-Scan-Mitgliedschaft sind in `config/quality/gate-manifest.json` verfügbar. Führen Sie `npm run check:gate-manifest` aus, um Skriptnamen und genaue Befehle anhand von `package.json` zu validieren. Hinzufügungen, Entfernungen und Befehlsdrift schlagen sowohl beim lokalen Hook als auch bei den Änderungsklassifizierungsjobs in CI fehl. Ein Alias ist kein Workflow-Job, keine Matrixinstanz oder kein Testfall: Diese Zählungen dürfen nicht als austauschbar dargestellt werden.

Verwenden Sie `npm run quality:scan -- --list` oder `npm run quality:scan:fast -- --list` um die ausgewählten Aliase zu überprüfen, ohne sie auszuführen. Der Läufer ruft den NPM-Einstiegspunkt auf, sodass seine Laufzeit (einschließlich Bun sofern konfiguriert) erhalten bleibt. Das Manifest zeichnet Aliase außerhalb dieser Profile als separat aufgerufen auf, und Wartungsbefehle sind in schreibgeschützten Scanprofilen verboten.

Diese Profile decken nur den statischen Scan ab. Sie zertifizieren keine Produkttests, Abdeckung, Verpackung, externe Prüfungen oder die vollständige Freigabeabnahme eines Kandidaten. Für die Workflow-Zulassung werden die verknüpften Elemente `config/quality/admission-policy.json` und `scripts/quality/admission-verdict.mjs` verwendet. Release-Beobachter-Profile bleiben getrennt; die entsprechenden Schecks und Quittungen selbstständig prüfen. Die statischen Befehle des vollständigen Beobachters werden in `config/quality/release-green-static-profile.json` deklariert, einschließlich `audit:deps`, Mutationstestauswahl und Übersetzungsprüfungen. Der Loader validiert npm-Befehle anhand von package.json und modellierten CI/Quality Deklarationen. Es lehnt Drift ab, anstatt Shell-Token als Argumente auszuführen. Die erforderliche Scanner- SKIP/INCOMPLETE Ausgabe kann PASS nicht herstellen. Das Profil zeichnet seine externen Ausschlüsse auf und ersetzt nicht die gehostete Abdeckung, Testmatrizen, Paket- oder Bereitstellungsnachweise. Die folgende Prosainventur ist eine Referenz und kein Beweis dafür, dass tatsächlich ein Tor geöffnet war.

Skripte laufen unter `scripts/check/` (Policy Gates) und `scripts/quality/` (Ratchet Engine). Die CI Quelle der Wahrheit ist `.github/workflows/ci.yml`.

### Geben Sie PR -Fast-Path (`quality.yml`) frei.

`.github/workflows/quality.yml` ergänzt CI auf main/release PRs, pusht auf `main`, versendet und führt Gruppen zusammen. PRs verwendet pfadgefilterte Schnellprüfungen. Der dauerhaft deaktivierte Duplikat-Build wurde entfernt; Die echten build/package/boot -Prüfungen verbleiben in CI. Die Unit Suite und vitest laufen nur in CI (`Unit Tests (N/8)` und `Vitest`).

#### Bericht über vergessene Geschwistertests

`npm run check:forgotten-sibling-tests` wird als Beratungsschritt von `Fast Quality Gates` ausgeführt und verwendet den Import-Resolver hinter der Test-Impact-Map wieder. Für jedes geänderte Produktionsmodul werden deterministische `changed module/symbol -> static consumer -> candidate sibling test` Ketten gemeldet, wenn der Kandidatentest im Pull-Request-Diff fehlt. Die Markdown-Zusammenfassung und JSON Ergebnis werden als `forgotten-sibling-tests` -Workflow-Artefakt zur Kalibrierung vor einem blockierenden Rollout beibehalten.

Bei Fass-Reexporten und dynamischen Importen handelt es sich lediglich um Auflösungsdiagnosen. Sie erstellen niemals einen blockierenden Befund. Überprüfte Ausnahmen leben in `config/quality/forgotten-sibling-allowlist.json`. Jeder Eintrag muss den Verbraucher- und Kandidatentest benennen, eine spezifische Begründung angeben und einen GitHub -Issue- oder Pull-Request verlinken. Fehlerhafte Einträge können nicht geschlossen werden. Ausnahmen können einen gelöschten Kandidatentest oder einen Diff, der `.skip`/`.todo` hinzufügt, nicht unterdrücken. Behauptungsschwächung und andere Maskierungen verbleiben im Besitz des unabhängig blockierenden `check:test-masking` Gates.

#### Übersetzungsspiegel sind abgeleitete Dateien (PR Modus vs. Release-Modus)

Eine Funktion PR bearbeitet nur englische Quellen. Die `docs/i18n/<locale>/**` Spiegel (einschließlich der 66 `llm.txt` Kopien und der übersetzten `CHANGELOG.md` Dateien) und `.i18n-state.json` werden in einem Schritt durch die Übersetzungswelle (`docs/i18n-*` / `chore/i18n-*` Zweige, das geplante `i18n-mirror-refresh.yml`) und durch die Veröffentlichung (`npm run release:sync-changelog-i18n`) neu geschrieben. Die Spiegelgatter laufen daher in zwei Modi, aufgelöst durch `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`, dann `OMNIROUTE_GATE_MODE`, dann das Actions-Ereignis; ein lokaler Lauf ist `release`):

- `check:docs-sync` — Release-Modus führt jede Prüfung durch. PR Modus behält die package.json/OpenAPI Version, die Root CHANGELOG Überschriften und den Superseded-Docs-Guard bei und gibt `SKIP reason=pr-mode` für die `llm.txt` -Spiegelkopien und die übersetzten CHANGELOG Abschnitte — aus, es sei denn, der PR schreibt Spiegel: Ein als Writer der `docs/i18n/**` Familie in `config/quality/derived-paths/*.json` deklarierter Hauptzweig führt beide Prüfungen strikt durch, und wenn die Diff-Basis aufgelöst wird, führt eine Änderung, deren eigenes Diff `docs/i18n/<locale>/llm.txt` oder `CHANGELOG.md` bearbeitet, diese Prüfung strikt aus. Die Diff-Basis wird bei einem depth-1 -Checkout (dem `docs-sync-strict` Job) nicht aufgelöst, daher führt PR Modus auch eine Prüfung aus, die keine Basis benötigt: Jeder `llm.txt` Spiegel muss vorhanden sein, sein `---` Trennzeichen behalten und entweder den Stammkörper oder den Körper tragen, den die meisten Spiegel gemeinsam nutzen. Eine Basis, die sich bewegt hat, hinterlässt alle Spiegel gleichermaßen veraltet und geht durch; Eine manuelle Bearbeitung eines Spiegels schlägt fehl. Die übersetzten `CHANGELOG.md` Dateien haben keine solche Prüfung in einem depth-1 PR Checkout.
- Der Pre-Commit-Hook führt `check-docs-sync.mjs --mode=pr` aus: Ein Commit wird danach beurteilt, was es tut. Ohne das Flag befindet sich ein lokaler Lauf im Release-Modus, und ein zusammengeführter PR, der den Root- `llm.txt` bearbeitet, würde jeden späteren Commit auf dieser Basis blockieren, bis die Wave ausgeführt wird. Die gleiche Regel gilt für jedes modusbewusste Gate, das ein Husky-Hook ausführt: Der Hook übergibt `--mode=pr` und das strenge Urteil bleibt bei den Release-Modus-Läufen (das Release PR schiebt auf `main`, ein einfacher lokaler Lauf).
- Unit-Tests mit gespiegeltem Inhalt (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) — Release-Modus bestätigt jedes Gebietsschema. PR Modus bestätigt nur die Spiegelungen, die mit der englischen Quelle gemäß `.i18n-state.json` (Whole-File-Hash oder der aufgezeichnete Abschnitts-Hash des Abschnitts, den die Test-Pins darstellen) aktuell sind, und überspringt die veralteten Spiegelungen mit einem Grund. Die `target_hash` Herkunftsprüfungen werden für jedes Gebietsschema in beiden Modi ausgeführt. Die Frische gilt pro `## ` Abschnitt, die Einheit `run-translation.mjs` Hashes; Ein langer Abschnitt (das Gate-Inventar dieser Datei beträgt etwa die Hälfte davon) bedeutet, dass jede Bearbeitung darin diese Spiegel veraltet lässt und ihre PR-Modus-Behauptungen bis zur nächsten Welle überspringen. Ein Anker, der in der englischen Quelle nicht mehr enthalten ist, greift auf den Vergleich der gesamten Datei zurück.
- `i18n translation drift` — -Hinweis zu PRs, strikt bei Push, Nightly und dem Release-Cut, sodass ein veralteter Mirror nicht in einem Release ausgeliefert werden kann.

`scripts/i18n/sync-llm-mirrors.mjs` (auch als `syncLlmMirrors()` exportiert, mit `--dry-run`) schreibt die `llm.txt` Spiegel neu; die Release-Aktualisierung, die Übersetzungswelle und die geplante `i18n-mirror-refresh.yml` -Ausführung (die Aktualisierung erkennt veraltete `llm.txt` Spiegel mit einem Probelauf, da der Driftbericht sie nicht auflistet, und synchronisiert sie vor `check:docs-all`).

Die zwölf README SVGs unter `docs/diagrams/` werden generiert (`scripts/docs/gen-readme-<name>.mjs`; `npm run docs:readme-diagrams` regeneriert sie alle). Jeder verfügt über einen Byte-Vergleichs-Einheitentest (`tests/unit/docs/readme-*-svg.test.ts`, Job `test-unit`), der fehlschlägt, wenn die festgeschriebene Datei im Release-Modus veraltet ist; In einem PR beurteilt `check:generated-artifacts` und SVG die PR -Änderungen und die Drift der Basis bleibt der Aktualisierung der Version überlassen (siehe [Generierte Dateien und abgeleitete Baselines](#generated-files-and-derived-baselines-written-at-release) ). — und `check:docs-counts` lesen kanonische Zahlen aus ihren `<text>` Knoten — weshalb der Outlining-Schritt jede umrissene Zeichenfolge in der Datei als unsichtbares `<text>` behält. Die SVG -Prüfung auf kanonische Zahlen liest die in `SVG_DIAGRAM_FILES` (`scripts/check/check-docs-counts-sync.mjs`) aufgeführten Dateien: `docs/diagrams/readme-hero.svg`, `free-tier-budget.svg`, `promise-pillars.svg`, `comparison-table.svg`, `cli-terminal.svg`, `tier-cascade.svg` sowie `public/images/tier-flow-dark.svg` und `tier-flow-light.svg`; Die Ansprüche „Für immer kostenlos“, „Katalogeintrag“, „Wiederkehrender Pool“ und „Bewertungsfaktoren“ lauten auch `promise-pillars.svg`, `free-tier-budget.svg` und `strategies-grid.svg`. Die von diesen Generatoren ermittelten Zahlen (Anbieter-Gesamtzahl, MCP Tools, Routing-Strategien, für immer kostenlose Anbieter usw.) stammen aus dem Fakten-Snapshot `docs/reference/derived-facts.json` bis `scripts/docs/readmeFacts.mjs` und nicht aus Literalen. Daher wird bei der Neugenerierung eines Diagramms in einem Zweig die festgeschriebene Datei reproduziert. `free-tier-budget.svg` bezieht seine Zeilen aus demselben Snapshot (`code.freeTierBudget`, die Katalogzusammenfassung, die die Faktenprobe aufzeichnet), sodass eine Änderung an `FREE_MODEL_BUDGETS` die Karte bei der nächsten Aktualisierung erreicht, anstatt CI rot zu färben.

### Abgeleitete Werte: die Gate-Modi `pr` und `release`

Ein Feature- PR schreibt niemals einen Wert, der vom Status seiner Basis abhängt: Anbieter, Migration, MCP-Tool und Strategieanzahl, die README SVG Nummern, der Fakten-Snapshot. In einem Schritt werden sie alle neu berechnet, `npm run release:refresh-derived`, ausgeführt von der Veröffentlichung und von der nächtlichen abgeleiteten Aktualisierung PR. Also** Zwischen den Veröffentlichungen befindet sich die Basis konstruktionsbedingt hinter dem Live-Code** , und ein Gate oder Test, der den Baum mit dem Live-Code vergleicht, würde bei jedem PR rot sein, nachdem ein Geschwister einen Anbieter hinzugefügt hat. Die Tore, die abgeleitete Werte beurteilen, laufen daher in einem von zwei Modi, gelöst durch `scripts/check/lib/gateMode.mjs` (erste Übereinstimmung gewinnt):

1. `--mode=pr|release` in der Befehlszeile;
2. die `OMNIROUTE_GATE_MODE` Umgebungsvariable (`pr` oder `release`);
3. automatisch, aus dem GitHub Actions-Ereignis: ein `pull_request` dessen Kopf nicht `release/v*`, ein `merge_group` oder ein Push to `omni-queue/**` → `pr` ist; alles andere (Push, Schedule, Dispatch, die Freigabe PR `release/v* → main`, jede lokale Ausführung) → `release`.

Was `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) in jedem Modus fehlschlägt:

| Modus     | Scheitert                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Benötigt die Live-Fakten |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `release` | Jede Prüfung, strikte Gleichheit mit den vom Baum gesammelten Fakten (das Verhalten, das das Tor immer hatte): Eine veraltete Anzahl, Version, Abdeckungsuntergrenze oder SVG Nummer ist eine STRICT Drift                                                                                                                                                                                                                                                                                                                        | Ja                       |
| `pr`      | Lediglich das, was die Änderung bewirkte, unterschied sich von der PR Basis mit den gleichen Anspruchsextraktoren: (1) ein verwalteter Wert, der in der Basis für diese Prüfung und Datei nicht vorhanden war („PR bearbeitete eine verwaltete Nummer — stellte die Zeile im Basistext wieder her“); (2) Bei einem erforderlichen Anspruch wurde die Basis getragen und der Kopf verloren. Inhaltsinvarianten, die keine Fakten benötigen, laufen wie im Release-Modus; Nur-Release-Prüfungen werden aufgelistet und übersprungen | NEIN                     |

Die Agent-Anweisungsdateien enthalten** NEIN** abgeleitete Anzahl überhaupt: `AGENTS.md`, `llm.txt` (und seine `docs/i18n/*/llm.txt` Kopien), die bs `AGENTS.md` Gabel, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` und jedes `skills/*/SKILL.md` zeigen auf die Quelle (zum Beispiel `ROUTING_STRATEGY_VALUES` in `src/shared/constants/routingStrategies.ts`) und stattdessen auf `npm run facts`. Die Invariante „Keine abgeleiteten Zählungen (Agent-Anweisungsdatei …)“ schlägt dort (Anbieter, Migrationen, MCP Tools und -Bereiche, Routing-Strategien, Bewertungsfaktoren, Moduspakete) in beiden Modi fehl, sodass bei der Release-Aktualisierung nie eine Anweisungsdatei neu geschrieben werden muss.

Im `pr` Modus können die Writer-Zweige verwaltete Werte bearbeiten: `chore/derived-*` (die nächtliche Aktualisierung PR), `release/v*` und die Übersetzungswellen `docs/i18n-*` und `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). Warteschlangenstapel (`merge_group`, Mergify Drafts, `omni-queue/**`) werden nicht erneut beurteilt: Sie summieren PRs das bereits beurteilte Gate nacheinander.

Exit-Codes: `0` clean · `1` STRICT Drift (oder Soft Drift mit `--strict`) oder eine Verletzung verwalteter Werte · `2` Infrastructure — Die Codefakten konnten nicht erfasst werden (die tsx-Probe ist fehlgeschlagen oder es kam zu einer Zeitüberschreitung; die Zeitüberschreitung ist `OMNIROUTE_FACTS_TIMEOUT_MS`, Standard 600000 ms) oder in CI konnte die PR -Diff-Basis nicht aufgelöst werden. Ein Exit 2 stellt niemals eine Dokumentationsabweichung dar: Führen Sie den Job erneut aus oder reparieren Sie die Umgebung.

- `npm run facts` gibt jede abgeleitete Zahl als JSON (`scripts/release/facts.mjs`) aus. `--key=code.mcpTools` gibt einen Wert aus, `--snapshot` liest den festgeschriebenen Snapshot anstelle des Live-Baums. Ausgang 2, wenn die Fakten nicht erfasst werden können.

#### `check-ui-value-drift` — veraltetes Übersetzungstor

Fängt die eine i18n-Regression ab, die die anderen Tore strukturell nicht sehen können: Ein englischer Wert wird umgeschrieben und die aus dem _vorherigen_ Englisch abgeleiteten Übersetzungen bleiben erhalten, sodass nicht-englische Benutzer weiterhin sicher formulierte, jetzt falsche Kopien lesen.

Das wurde echt geliefert. `oauthModal.googleOAuthWarning` wurde neu geschrieben, als der Antigravity -Anmeldehelfer landete (#5203);** 39 von 43 Orten** Behalten Sie den Text bei, der die Bediener auffordert, „den vollständigen URL zu kopieren und unten einzufügen“ — einen Fluss, der für diesen Anbieter nicht abgeschlossen werden kann. Es blieb bis #8463 unbemerkt, weil:

- `sync-ui-keys` füllt nur Schlüssel auf, die vorhanden sind** abwesend** , niemals diejenigen, die es sind** abgestanden** ;
- `check-ui-keys-coverage` zählt die _Präsenz_ des Schlüssels, sodass eine veraltete Übersetzung als abgedeckt gilt;
- `check-translation-drift` verfolgt die `docs/i18n/<locale>/**.md` -Dokumentation und spiegelt — wider, es liest niemals `src/i18n/messages/*.json`. Es läuft im Job `docs-sync-strict`: Advisory auf PRs, strikt bei Push und nächtlich; Die Übersetzungswelle aktualisiert die Spiegel, nicht die Funktion PR.

**Differenzbewusst, nicht baseline-unterstützt.** Es vergleicht `en.json` an der Zusammenführungsbasis mit dem Arbeitsbaum; Für jeden Schlüssel, dessen englischer Wert sich geändert hat, ist jedes Gebietsschema, das noch eine unberührte Übersetzung enthält, veraltet. Dies bewusst** Friert bereits bestehende Schulden ein** — a diff kann nicht offenbaren, aus welchem alten Englisch eine langjährige Übersetzung stammt, daher beurteilt das Gate nur, was die aktuelle Änderung betrifft. Die Alternative (eine Pro-Schlüssel-Hash-Baseline) würde eine generierte Datei ~ 600 KB kosten, 3 × die größte existierende Baseline, die bei jedem i18n PR abwandert.

Zwei Möglichkeiten, es zu befriedigen:

1. die betroffenen Übersetzungen aktualisieren, oder
2. Setzen Sie sie auf `__MISSING__:<new english>` — Die Laufzeit stellt dann das korrigierte Englisch (`src/i18n/request.ts::deepMergeFallback`, #7258) und die Schlüsselwarteschlangen zur Übersetzung bereit.

Wenn die Zeichenfolge** Bedeutung** geändert, lieber** Umbenennen des Schlüssels** : Ein neuer Schlüssel kann keine veraltete Übersetzung erben. Das ist das Muster, #8463 verwendet hat.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Beendet 0 mit `SKIP reason=base-unresolved`, wenn der Basiskatalog nicht gelesen werden kann (flacher Klon ohne Basisreferenz), was `check-openapi-breaking` widerspiegelt. Nur Release-Modus: Eine Funktion PR schreibt das Englische neu und stoppt dort; Die Release-Aktualisierung markiert die Übersetzungen, die sie hinterlassen hat (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, dasselbe `findStaleTranslations`).

Bei `pull_request` -Ereignissen übergibt `quality.yml` `--base-ref <PR base SHA>` an `check:file-size`, `check:complexity-ratchets` und `check:dead-code`. Für `check:complexity-ratchets` und `check:dead-code` vergleicht das Gate HEAD mit der Merge-Basis** auf die Dateien beschränkt, die der PR berührt hat** (`scripts/check/newCodeMode.mjs`: Die Zusammenführungsbasis wird in einem Wegwerf `git worktree` materialisiert, ESLint/knip läuft dort und auf HEAD sind die Zählungen pro Datei unterschiedlich):

- **Blockierung** — der PR hat cyclomatic/cognitive -Verstöße oder tote Exporte in den von ihm geänderten Dateien hinzugefügt (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` im Protokoll);
- **beratend** — die globale Gesamtsumme im Vergleich zur eingefrorenen Basislinie. Vererbte Drift macht niemals einen unschuldigen PR rot; Die Abweichung wird bei der Freigabeabstimmung erneut eingefroren und vom Headroom-Job überwacht.

`check:file-size` verwendet die Basisreferenz zu seinen eigenen Bedingungen (`scripts/check/check-file-size.mjs`, #8522): Es überprüft jede Quell- und Testdatei im Baum, liest die Zeilenanzahl jeder einzelnen an der PR Basis mit `git show` und lässt eine Datei nur dann fehlschlagen, wenn sie über den größeren Wert ihrer Basislinienobergrenze (`frozen` / `testFrozen` oder `cap` / `testCap` für eine Datei außerhalb der Basislinie) und ihrer Basisgröße hinauswächst. Eine Datei, die bereits auf der Basis gedriftet ist, löscht daher niemals einen unschuldigen PR.

`check:boundary:ratchet` wendet die gleiche Regel auf seine einzelne Zahl (`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`) an: Bei PR Ereignissen passieren sowohl `quality.yml` Fast-Gates als auch der `ci.yml` Lint-Job die PR Basis SHA, der Basis-Commit wird anhand eines `git archive` Exports gemessen und PR schlägt nur fehl, wenn seine `open-sse → src` Kantenanzahl den größeren von `metrics.boundaryOpenSseToSrc` und der Anzahl auf der Basis überschreitet. Eine Basisdrift über der Decke wird gemeldet (`base drift herdado`), aber niemals ein unschuldiger PR; push → main behält die absolute Obergrenze bei und ein nicht auflösbarer Basis SHA greift mit einer Warnung darauf zurück.

Ein Omni-Queue-Kandidat (ein Push an `omni-queue/**`, siehe [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ) wird genauso behandelt wie eine Pull-Anfrage: Beide Workflows übergeben die Kandidatenbasis (`needs.changes.outputs.candidateBase`) als `--base-ref` und `check:ts7-diagnostics-ratchet` wird auch dagegen ausgeführt. Für die beiden neuen Code-Gates ist die Vergleichsbasis das SHA selbst, nicht das erste übergeordnete Element des obersten Merge-Commits, sodass jede Pull-Anfrage des Stapels beurteilt wird.

`workflow_dispatch` Läufe, der Release-Green-Sweep und der Nightly-Headroom-Job haben keine PR Basis und behalten den absoluten (globalen) Vergleich bei. Abdeckung, Duplizierung und Typabdeckung bleiben vorerst global (ihre Tools erzeugen keinen kostengünstigen Unterschied pro Datei). — -Kandidaten für die gleiche Behandlung.

| `coverage.lines`      | `up`     | Die Leitungsabdeckung darf nicht sinken            |
| `coverage.functions`  | `up`     | Die Funktionsabdeckung darf nicht sinken           |
| `coverage.branches`   | `up`     | Die Filialabdeckung darf nicht sinken              |

So aktualisieren Sie die Basislinie nach einer echten Verbesserung:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

Das Flag `--update` schreibt die aktuellen Messwerte in `quality-baseline.json`. Das Bankieren einer Verbesserung ist release/nightly Arbeit, keine Funktion von PR: `--require-tighten` (Fase 6A.5) schlägt bei einer nicht-bankierten Verbesserung nur im Release-Modus fehl (Push, Zeitplan, Release- PR, lokale Ausführung). In einer Funktion PR (`pr` Gate-Modus) wird die Verbesserung als Information gedruckt und übergeben; Eine Regression schlägt in beiden Modi fehl. Während der Geschwindigkeitsphase ist es überall beratend (`_policy.requireTighten: false`). Siehe [Generierte Dateien und abgeleitete Baselines](#generated-files-and-derived-baselines-written-at-release).

### CodeQL -Ratsche: Aktualisierung der Trittfrequenz und manueller Auslöser

`check:codeql-ratchet` liest** Repo-Status, aktualisiert nach einem Zeitplan — nicht nach PR.** `gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` meldet den Standard-Setup-Scan von `state: configured`, `schedule: weekly`: GitHub, keine Per-Push-Analyse. Konsequenz: Nachdem ein PR, das FIXES warnt, zusammengeführt wird, liest der Ratchet weiterhin die alte, höhere Anzahl, bis der nächste geplante Scan — ausführt, sodass er bei jedem offenen PR eine Regression meldet, einschließlich der eigenen Nachverfolgungen des reparierenden PR, bis der Scan aufholt.

**Manuelle Aktualisierung** : `gh workflow run codeql.yml --ref release/vX.Y.Z` führt die Analyse erneut aus und veröffentlicht Warnungen innerhalb von Minuten erneut. Lesen Sie zuerst `.github/workflows/codeql.yml` — Der Header erklärt, dass es sich `workflow_dispatch` -only handelt** weil es mit dem „Standard-Setup“ von GitHub in Konflikt steht** (`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`). Das Wiederherstellen von `push`/`pull_request`/ `schedule` -Triggern erfordert eine** Eigentümeraktion zuerst** : Einstellungen → Codesicherheit → CodeQL: Standard → Erweitert. Fügen Sie keinen `schedule:` Trigger ohne diesen Schalter — hinzu, da dies nur zu fehlgeschlagenen Läufen führt.

**Ziehen Sie die Grundlinie fest, nachdem die Zählung gesunken ist** — `node scripts/check/check-codeql-ratchet.mjs --update` schreibt die neue gemessene Anzahl in `quality-baseline.json` → `metrics.codeqlAlerts.value`, sodass die Ratsche nicht stillschweigend eine Regression zurück zur alten Obergrenze zulässt. Arbeitsbeispiel (2026-09-02/03): PR #12502 hat 7 echte Alarme behoben (13 → 6 gemessene offene); PR #12530 verschärfte die eingefrorene Grundlinie 11 → 6 entsprechend; Die restlichen 6 wurden dann mit einer Begründung pro Warnung auf 0 offene Stellen abgewiesen.

**Entlassungen sind Sache des Betreibers (harte Regel #14)** — lehnt eine CodeQL Warnung niemals ab, ohne die technische Begründung im Ablehnungskommentar anzugeben: `won't fix` für eine Upstream-Protokollanforderung, `used in tests` für eine Testvorrichtung, `false positive` für ein Desinfektionsmittel, CodeQL nicht sehen kann (Präzedenzfall: `docs/security/ERROR_SANITIZATION.md`).

## Richtlinie für Testwiederholungen (WS5.4, v3.8.49)

Wiederholungen werden pro Runner konfiguriert, niemals pauschal global — eine pauschale Wiederholung macht aus echten Regressionen unsichtbare Flakes:

| Runner           | Richtlinie                                                                                                                                    | Begründung                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Playwright (e2e) | `retries: 1` nur in CI, mit `trace: on-first-retry`                                                                                           | Browser-/Netzwerk-Timing ist tatsächlich nicht deterministisch; eine Wiederholung mit einem Trace macht aus einem Flake ein diagnostizierbares Artefakt |
| Vitest           | KEINE globale Wiederholung. Ein nachweislich instabiler Test erhält eine explizite Wiederholung pro Test (im Diff sichtbar und im PR geprüft) | So bleibt die Quarantäneliste im Repository und ist niemals undurchsichtig                                                                              |
| node:test (Unit) | NIEMALS Wiederholungen                                                                                                                        | Ein instabiler Unit-Test ist ein Fehler im Test — beheben, nicht erneut ausführen                                                                       |

Ziel-SLOs, sobald die Flake-Telemetrie verfügbar ist (WS5.2/5.3): <1 % Flake-Rate pro Test
(Schwellenwert für „sofort beheben“), ≥95 % Erfolgsrate pro Pipeline. Branchenübliche Referenzwerte —
anhand unserer eigenen Messungen neu kalibrieren.

## Drift der Ratchets auf Release-Ebene (WS5.5, v3.8.49)

Wenn sich ein Ratchet (Dateigröße, Komplexität, eslint-Warnungen) am REINEN Release-
Tip verschlechtert — d. h., die KOMBINATION der Merges hat die Verschlechterung verursacht und kein einzelner PR reproduziert sie
in seinem eigenen Branch — obliegt die Behebung **einmalig dem Release Captain auf dem
Release-Branch**: Extraktion/Refactoring bevorzugen; die Baseline nur mit dem dokumentierten
Begründungseintrag neu setzen. Kombinationsbedingte Drift niemals auf einen Contributor-PR abwälzen und niemals
pro PR neu baselinen (das verbirgt echte Regressionen). Zuerst differenzieren: Den
roten Status in einem Probe-Worktree gegen den reinen Tip reproduzieren, bevor angenommen wird, dass der eigene PR ihn verursacht hat.

## Ratchet-Absenkungen übernehmen — die Abwärtsrichtung (#8584)

Das Ratchet ist nur zur Hälfte automatisiert, und zwar zur falschen Hälfte. Das **Anheben** eines Limits ist eine
manuelle JSON-Bearbeitung, die zehn Sekunden dauert und der schnellste Weg ist, einen roten PR wieder freizugeben.
Das **Absenken** erfordert, dass jemand `--update` ausführt und das Ergebnis committet — und bis
der Job `bank-ratchet-shrinks` eingeführt wurde, führte kein Workflow diesen Vorgang aus. Die gemessene Folge
(2026-07-25): 18 eingefrorene Dateien lagen bereits bei oder unter dem Limit von 800 Zeilen für neue Dateien, im schlimmsten
Fall beim 132-Fachen (`src/shared/validation/schemas.ts`, 19 Zeilen bei einem Limit von 2.523); die
Komplexitätsobergrenze stieg über etwa 37 Rebaseline-Hinweise hinweg von `1794 → 2169`, bei genau einer
Absenkung (−1); und „im nächsten Zyklus über `--update` verschärfen“ wurde 31-mal geschrieben und
einmal umgesetzt. Ein Limit, das länger bestehen bleibt als der Code, durch den es begründet wurde, verwandelt
jede abgeschlossene Zerlegung stillschweigend in zusätzlichen Wachstumsspielraum für die Person, die die Datei als Nächstes bearbeitet.

`nightly-release-green.yml` → Job **`bank-ratchet-shrinks`** schließt diesen Regelkreis:

|             |                                                                                                                           |
| ----------- | ------------------------------------------------------------------------------------------------------------------------- |
| Läuft bei   | `schedule` (3×/Tag) + `workflow_dispatch` — bewusst **nicht** bei `push`                                                  |
| Misst       | den höchsten `release/vX.Y.Z`, mit derselben Auflösung und demselben Injection Guard wie `release-green`                  |
| Schreibt    | `check:file-size --update` und `check:complexity-ratchets --update` (beide konstruktionsbedingt ausschließlich absenkend) |
| Verifiziert | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                  |
| Liefert aus | einen stets aktuellen PR gegen den Release-Branch — per Force-Update aktualisiert, niemals als Spam                       |

Die Übernahme erfolgt gebündelt statt bei jedem Push, da es keine Latenzanforderung gibt (eine innerhalb von
8 Stunden übernommene Absenkung ist ausreichend), während eine Ausführung bei jedem Merge den PR-Branch während
Merge-Kampagnen wiederholt neu erstellen und jedes Mal einen vollständigen ESLint-Durchlauf verursachen würde. Die Erkennung erfolgt weiterhin bei
`push` (`release-green`); nur die Übernahme wird gebündelt.

### Der Sicherheitsprüfer

Der Job schreibt unbeaufsichtigt in die Baselines, daher sorgt `verify-ratchet-bank.mjs` dafür,
dass dies vertretbar ist. Er vergleicht den Baum nach `--update` mit `HEAD` und **bricht den Job ab,
bevor ein Commit existiert** — ohne einen PR zu öffnen —, sofern nicht jede Änderung einer der folgenden Kategorien entspricht:

- ein numerischer `frozen`- / `testFrozen`-Eintrag wurde **abgesenkt** oder **entfernt**
- `complexity-baseline.json` → `count` wurde **abgesenkt**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` wurde **abgesenkt**

Alles andere schlägt fehl: das Anheben einer Zahl, das Hinzufügen eines Eintrags, das Ändern von `cap`/`testCap` oder
das Löschen/Umschreiben eines `_rebaseline_*`-Hinweises (diese Hinweise bilden den Audit-Trail dafür, warum die jeweilige
Obergrenze existiert, und werden innerhalb desselben `frozen`-Objekts wie die Dateieinträge gespeichert).
Ein Bot, der ein Limit anheben könnte, wäre eindeutig schlechter als der Status quo. Regressions-
Guard: `tests/unit/verify-ratchet-bank.test.ts`.

Der Job pusht niemals nach `release/*` — ein Mensch mergt den PR, sodass eine fehlerhafte Messung
nicht ungeprüft übernommen werden kann.

## Richtlinie zur Zulassungsliste

Jedes Gate, das bei bereits bestehenden Verstößen nicht fehlschlagen kann, verwendet eine eingefrorene Zulassungsliste (z. B. `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). Die Richtlinie lautet:

**Beheben Sie die Grundursache. Verwenden Sie die Zulassungsliste nur, wenn der Verstoß bereits besteht und nicht im selben PR behoben werden kann.**

Beim Hinzufügen eines Eintrags zu einer Zulassungsliste:

1. Fügen Sie der Begründung einen Kommentar bei.
2. Verweisen Sie auf das Tracking-Problem (z. B. `// #3498 — Phase 2 feature, not yet implemented`).
3. Entfernen Sie den Eintrag in demselben PR, der den Verstoß behebt — Ein veralteter Eintrag, der einen aktiven Verstoß nicht mehr unterdrückt, ist selbst ein Fehler (6A.3 Stale-Enforcement führt dazu, dass das Gate bei einem verwaisten Zulassungslisteneintrag scheitert, sobald er implementiert ist).

Tun** nicht** Fügen Sie Zulassungslisteneinträge hinzu, um das Bestehen von Tests zu beschleunigen. Ein grünes Tor mit einer wachsenden Zulassungsliste ist ein falsches Qualitätsgefühl.

### Wenn ein Tor an Ihrem PR ausfällt

1. **Lesen Sie die Gate-Ausgabe sorgfältig durch** — sagt Ihnen genau, welche Datei oder welches Symbol gegen die Regel verstoßen hat.
2. **Beheben Sie den Verstoß** — den meisten Gates handelt es sich um deterministische Dateisystemprüfungen, die bestanden werden, sobald der Code korrekt ist.
3. **Wenn der Verstoß bereits vorliegt** (d. h. Sie haben es nicht eingeführt, aber das Tor deckt es jetzt ab): Fügen Sie einen Zulassungslisteneintrag mit einem Begründungskommentar und einem Tracking-Problem hinzu.
4. **Wenn das Tor eine Ratsche ist** (Abdeckung, ESLint Warnungen, Duplizierung, Komplexität): Ihre Änderung hat die Metrik verschlechtert. Beheben Sie das zugrunde liegende Problem oder führen Sie (selten) `npm run quality:ratchet -- --update` aus, wenn die Änderung beabsichtigt ist und die Metrikverschlechterung akzeptabel ist. —, aber dokumentieren Sie den Grund in der PR -Beschreibung.
5. **Beratungstore** (`continue-on-error: true`) sind Informations- — sie blockieren die Zusammenführung nicht, erscheinen aber in der CI Zusammenfassung. Repariere sie trotzdem.

#### `check-key-completeness` — Schlüsselsatz-Paritätsgatter

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, Job `i18n-ui-coverage`). Vergleicht den Blattschlüsselsatz jedes `src/i18n/messages/<locale>.json` mit `en.json` und schlägt bei jedem fehlenden oder zusätzlichen Blatt fehl, unabhängig davon, wann der Schlüssel hinzugefügt wurde. `__MISSING__:` Platzhalter gelten als vorhanden (ihr Inhalt ist Sache des Ratio-Gates). Es ist die absolute Ergänzung der beiden diff-based/percentage Gatter: `check-ui-keys-coverage` erzwingt eine Untergrenze von 80 % pro Gebietsschema (43 fehlende Schlüssel von 13.000 ~ lesen immer noch 99,7 %) und `check-new-key-coverage` beurteilt nur die Schlüssel, die ein PR zu `en.json` hinzufügt. Ein Locale-Batch wird aus dem `en.json` des Tages generiert, an dem sein Zweig geschnitten wird, und tagelang übersetzt, während die Basis weiterhin Schlüssel hinzufügt. Der Batch PR fügt selbst keinen Schlüssel hinzu, daher schwiegen beide Geschwister, als Batch 1 (#13044) in neun Lokalisierungen 43 Schlüssel fehlte und Batch 2 (#13660) in acht Lokalisierungen 10 Schlüssel fehlte (15.09.2026). Repariere ein Rot mit `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`; ein `extra` Blatt bedeutet, dass die Quelle es gelöscht hat — `sync-ui-keys` es gelöscht hat (`--prune-extra`, die Standardeinstellung). `--warn` berichtet ohne Fehler. `--catalog=cli` führt den gleichen Vergleich über `bin/cli/locales` (`npm run i18n:check-keys:cli`) durch; Beide Schritte leben im Job `i18n-ui-coverage`. Die absolute Prüfung erfolgt nur im Release-Modus: Ein Feature- PR sieht `SKIP reason=pr-mode` und der Fix wird in der Release-Aktualisierung oder einer Übersetzungswelle ausgeführt, niemals in einem Feature- PR; Bei einem PR, der Gebietsschemakataloge ändert, wird stattdessen jeder von ihnen anhand der Zusammenführungsbasis beurteilt (siehe „Zwei Modi“ unter Job `i18n-ui-coverage`).

#### `check-new-key-coverage` — neuer Schlüssel i18n Gate

Geschwister von `check-ui-value-drift`. Das fängt einen englischen Wert ein, der war** umgeschrieben** während seine Übersetzungen zurückgelassen wurden; Dieser fängt einen englischen Schlüssel ein** hinzugefügt** während einige Orte es nie erhalten haben.

`check-ui-keys-coverage` kann diese Klasse nicht sehen: Sie erzwingt eine prozentuale Untergrenze pro Gebietsschema, und elf fehlende Schlüssel von ~ 13.000 belassen die Abdeckung bei 99,9 %. Ein Prozentsatz pro Sprache kann nicht ausdrücken, dass „diese Funktion unübersetzt ausgeliefert wurde“, — eine ganze Funktion kann in einem neuen Gebietsschema ohne Text landen und die Zahl nie verschieben.

Der Vorfall, den es kodiert: Phase 3 des Orchestration Canvas übersetzte seine elf Schlüssel in die 42 zu diesem Zeitpunkt existierenden Gebietsschemas. Stunden später brachte die EU-Sprachgruppe (#13044) das Repo auf 51 Standorte, und die neun Neuankömmlinge (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) erhielten sie nie. `deepMergeFallback` ersetzt einen fehlenden Schlüssel durch Englisch, daher war der Fehlermodus unübersetztes UI statt leeres UI — real und konstruktionsbedingt still.

Wie sein Geschwister ist es** diff-bewusst** Dabei wird Englisch an der Zusammenführungsbasis mit dem Arbeitsbaum verglichen, sodass bereits vorhandene Lücken eingefroren bleiben und das Gate keine Migration zum Einschalten benötigt.

**Ein `__MISSING__:<english>` Marker erfüllt dies nicht (seit 17.09.2026).** Früher war es die dokumentierte Verzögerung — bei der die Laufzeit auf korrektes englisches — zurückgreift, bis acht Feature PRs am 16.09.2026 61 Schlüssel hinzufügten und die Markierung in alle 65 Gebietsschemas einprägten, anstatt zu übersetzen: Dieses Gate akzeptierte alle, nichts blockierte das PRs, und das blockierende Real-Translation-Ratio-Gate schlug dann bei der Veröffentlichungsspitze für alle fehl (pt-BR 3,2 % > 2,5 % + 0,5). Eine Markierung wird nun als fehlende Übersetzung gewertet. Release-Modus erst seit dem 13.11.2026: Ein Feature PR sieht `SKIP reason=pr-mode`, und beim Release PR (`BASE_REF=origin/main`) beurteilt das Gate jeden Schlüssel, den der Zyklus hinzugefügt hat. Beheben Sie ein Rot in der Release-Aktualisierung oder eine Übersetzungswelle mit `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` oder allen Gebietsschemas parallel mit `npm run i18n:translate-new-keys` (`scripts/i18n/translate-new-keys.sh`, tached-safe, weigert sich, ohne die `OMNIROUTE_TRANSLATION_*` Umgebung zu starten). Ein Schlüssel, der englisch bleiben muss (ein angehefteter product/engine/flag Name), gehört in `scripts/i18n/untranslatable-keys.json` und niemals hinter eine Markierung. `vi` verbietet Marker komplett (`tests/unit/i18n-vi-completeness.test.ts`).

#### `check-vitest-exclusions` — geparktes Testtor

Eine Datei in der `exclude` Liste von `vitest.config.ts` ist ein Test, der nicht ausgeführt wird, und sieht für denjenigen, der den Baum liest, wie eine Abdeckung aus. Hinter dem Kommentar `// #8618 — pre-existing failure; remove this exclusion when fixed` haben sich 62 Dateien angesammelt. Die Ausgabe #8618 wurde am 11.08.2026 geschlossen, während die von ihr verfolgte Liste von 45 Einträgen auf 62 anwuchs, wobei jeder neue Eintrag einen Kommentar erbte, der auf eine tote Ausgabe verwies. Als die Liste schließlich Datei für Datei vermessen wurde (#13204),** 51 der 62 wurden ohne Quelländerung an den aktuellen Baum übergeben** .

Das Gate erfordert, dass jeder Ausschluss, der sich in eine echte Datei auflöst, (a) ein Tracking-Problem benennt und (b) mit seinem gemessenen Status in `config/quality/vitest-exclusions.json` erscheint. Das Hinzufügen eines solchen Ausschlusses ist also ein überprüfbarer Unterschied in einer dedizierten Datei und nicht eine weitere Zeile in einem Array mit 60 Einträgen. Die ausgeschlossenen Tests — werden absichtlich nicht erneut ausgeführt, was ~ 10 Minuten kostet und zu einem periodischen Job gehört; Die Bestandsaufzeichnungen zeigen, wann jeweils das letzte Mal gemessen wurde.
