> **Status:** Das Dashboard basiert auf dem **Keak CI UI Kit** (`@keak/cheaper-inference-ui-kit`), das per
> Vendoring als Workspace `packages/ui-kit` eingebunden ist (`@omniroute/ui-kit`; der Upstream-Snapshot ist in
> `packages/ui-kit/UPSTREAM.md` festgehalten und durch `npm run check:ui-kit-snapshot` abgesichert). Light ist das
> kanonische Theme; die Standardvoreinstellung ist `system`. Die Akzentfarbe ist Keak Lime (`--ci-color-accent`).
> Inter (letter-spacing 0, `--ci-letter-spacing-ui`) ist die UI-Schriftfamilie, Instrument Serif nur für große,
> sparsam eingesetzte Display-Texte (`.ci-dashboard-display`), IBM Plex Mono für Code — alle selbst gehostet über
> die `@fontsource/*`-Imports am Anfang von `src/app/globals.css`. Jedes Icon ist eine Lucide-Glyphe.

## 1. Wo sich alles befindet

- **Kit.** `packages/ui-kit/src` ist eine Byte-für-Byte-Kopie des Upstream-`src/` am Commit, der in
  `packages/ui-kit/UPSTREAM.md` gepinnt ist (das auch die Lizenzautorisierung festhält); `PATCHES.md`
  listet lokale Patches auf (keine). Es wird als Quellcode eingebunden, ohne Build: `next.config.mjs`
  transpiliert es, und `tsconfig.json` mappt `@omniroute/ui-kit` → `packages/ui-kit/src` und
  `@omniroute/ui-kit/*` → `packages/ui-kit/src/*` (`vitest.config.ts` und `vitest.mcp.config.ts` tragen
  denselben Alias). Eine Kit-Komponente wird über ihren Subpath importiert (`@omniroute/ui-kit/table`,
  `@omniroute/ui-kit/page-header`…), niemals über das `@omniroute/ui-kit`-Barrel: Das Barrel zieht jede
  Komponente (einschließlich des Date-Pickers) in jede importierende Datei. Das Kit-Stylesheet kommt über
  `src/app/globals.css` herein (`@import "../../packages/ui-kit/src/ci-ui.css"`).
- **Tokens.** `packages/ui-kit/src/ci-tokens.css` deklariert die `--ci-*`-Tokens; `src/app/globals.css`
  brückt sie zu den Legacy-OmniRoute-Namen (`--color-*`, `--radius-*`, `--font-sans`/`--font-mono`,
  `--table-*`, `--orch-status-*`, `--color-fd-*`), sodass die bestehenden `var(--color-*)`-Zugriffe und
  Tailwind-Utilities weiterhin funktionieren. Neuer Code verwendet die Tailwind-Utilities (`bg-surface`,
  `text-text-muted`, `border-border`, `text-success`, `bg-success-bg`, `bg-chart-1`…) oder Kit-Klassen —
  niemals einen Hex-Wert (`tests/unit/design-kit-bridge.test.ts` erzwingt die Bridge). `text-primary`
  löst über `--text-color-primary` zu `--color-primary-ink` auf (lime-800 im Light-Modus, das
  Lime-Accent im Dark-Modus), sodass primärer Text lesbar bleibt, während `bg-primary`/`border-primary`
  die Lime-Oberfläche behalten. Chart-Serien verwenden `--color-chart-1` … `--color-chart-5`.
- **Themes.** `<html className="ci-theme">` (`src/app/layout.tsx`) aktiviert das Kit-Theme für das
  Dokument. Die Präferenz ist `light`, `dark` oder `system` (`THEME_CONFIG.defaultTheme = "system"` in
  `src/shared/constants/appConfig.ts`; `system` folgt `prefers-color-scheme`). `applyTheme()` in
  `src/store/themeStore.ts` (gespiegelt durch das Inline-Bootstrap-Skript in `src/app/layout.tsx`, das
  vor der Hydration läuft) setzt `data-theme="dark"|"light"` und toggelt gemeinsam damit die
  `.dark`-Klasse auf `<html>`. Das Dark-Token-Set des Kits hängt an `data-theme="dark"`
  (`packages/ui-kit/src/ci-tokens.css`); OmniRoutes eigene Dark-Overrides (der `.dark`-Block in
  `globals.css`) und die Legacy-Tailwind-`dark:`-Utilities hängen an der `.dark`-Klasse. Es gibt keine
  Akzentfarb-Presets: Der Akzent kommt immer vom Kit, und ein persistiertes Preset aus einem älteren
  Build wird beim Laden des Stores verworfen.
- **Komponenten (Adapter).** `src/shared/components/index.tsx` behält die OmniRoute-Komponenten-API bei
  (gleiche Namen, Default-Exports und Props), und die Primitiven dahinter sind Adapter über dem Kit:
  Formulare (`Button`, `Input`, `Textarea`, `Checkbox`, `Select`, `Toggle`, `Badge`, `Card`), Overlays
  und Feedback (`Modal`/`ConfirmModal`, `Tooltip`/`InfoTooltip`, `NotificationToast`, `EmptyState`,
  `Loading`), Struktur (`Collapsible`, `CollapsibleSection`, `SegmentedControl`, `Breadcrumbs`,
  `Avatar`) und Tabellen (`DataTable`, `FilterBar`, `ColumnToggle`, `FilterPills`, `PresetSlider`). Ein
  Adapter importiert die Kit-Komponente per Subpath und bildet die Legacy-Props darauf ab — zum Beispiel
  ist `Button variant="primary"` der Kit-`default`-Button (`--ci-button-primary-*`: die inverse
  Oberfläche im Light-Modus, der Akzent mit seiner `--ci-color-accent-foreground`-Ink im Dark-Modus),
  `danger` ist `destructive`, und `warning` ist `outline` plus die `.ci-button--warning`-Erweiterung. Die
  `.ci-button--warning`- und `.ci-badge[data-tone]`-Regeln am Ende von `globals.css`
  (`@layer components`) sind OmniRoute-Erweiterungen auf den Kit-Klassen.
  `tests/unit/ui/adapters/*.test.tsx` pinnt jeden Adapter.
- **Shell.** `src/app/(dashboard)/layout.tsx` rendert `DashboardLayout`, das
  `src/shared/components/layouts/DashboardShell.tsx` rendert: das Kit-`SidebarProvider` / `Sidebar` /
  `SidebarInset` (`packages/ui-kit/src/sidebar.tsx`), mit OmniRoutes Navigationslogik in
  `src/shared/components/Sidebar.tsx`. Ein „Zum Inhalt springen"-Link zu `#main-content` ist das erste
  fokussierbare Element. `src/shared/components/Header.tsx` enthält den Kit-`SidebarTrigger` (den
  einzigen Sidebar-Toggle der Shell), den Keak-`ProductSwitcher` und den Öffner der Befehlspalette; er
  zeigt den Routentitel nur an, solange kein Kit-`PageHeader` (`.ci-page-header`) innerhalb von
  `#main-content` gemountet ist, sodass eine Seite mit eigenem `PageHeader` nur ein einziges `h1` hat.
  `src/shared/components/CommandPalette.tsx` ist ein Kit-`Dialog`.
- **Icons.** `<Icon name="material_name">` (`src/shared/components/Icon.tsx`) löst den Namen (das
  Material-Symbols-Vokabular, das die Screens verwenden) über `ICON_MAP`
  (`src/shared/constants/iconMap.ts`) zu einem Lucide-Glyph auf. Die Material-Symbols-Schriftart und das
  Paket wurden entfernt: Ein Name, der in der Map fehlt, rendert ein neutrales Platzhalter-Glyph
  (`data-icon-missing="true"`) und loggt außerhalb der Produktion eine Konsolenwarnung.
  `npm run gen:icon-map` gibt die verwendeten Namen aus, die in der Map fehlen
  (`tests/unit/icon-map-coverage.test.ts` schlägt bei jedem Namen ohne Lucide-Icon fehl;
  `tests/unit/icon-map-object-values.test.ts` deckt Namen ab, die in Lookup-Objekten gespeichert sind);
  `scripts/dev/codemod-material-icons.mjs <dir|file>... [--write]` schreibt literale
  `<span className="material-symbols-outlined">`-Spans zu `<Icon>` um.
- **Branding.** `src/shared/components/OmniRouteLogo.tsx` wrappt das Kit: Der Default-Export
  `OmniRouteLogo` rendert `ProductIcon product="omniroute" variant="glyph"` (Inline-SVG,
  `basePath`-sicher) und `OmniRouteLockup` rendert `ProductLockup product="omniroute"` (zugänglicher Name
  "Keak OmniRoute") oder, für White-Label-Betreiber, deren eigene `name`/`logoSrc`. Die Ziele des
  Product-Switchers liegen in `src/shared/constants/keakProducts.ts` (`KEAK_PRODUCT_LINKS`,
  `KEAK_ACTIVE_PRODUCT`). Die eigenständigen Screens — `src/app/login/page.tsx`,
  `src/app/status/page.tsx`, `src/app/maintenance/page.tsx`, `src/app/offline/page.tsx`,
  `src/app/not-found.tsx` und `src/shared/components/ErrorPageScaffold.tsx` — zeigen das Lockup;
  `tests/unit/brand-pages-static.test.ts` sichert es ab.

## 2. Regeln

1. Tokens, niemals Literale. Ausnahmen werden absichtlich beibehalten: das immer dunkle
   Konsolen-Terminal, ReactFlow-SVG-Striche über `STATUS_HEX` (`src/shared/constants/statusColors.ts`)
   sowie die kategorialen Paletten `STRATEGY_COLORS`
   (`src/app/(dashboard)/dashboard/combos/live/nodes/StrategyNode.tsx`) und
   `LAYER_COLORS` (`src/app/(dashboard)/dashboard/compression/studio/nodes/EngineNode.tsx`).
2. Niemals `packages/ui-kit/src` von Hand patchen: mit `scripts/dev/sync-ui-kit.sh <commit>`
   synchronisieren; das Pre-Commit-Gate `npm run check:ui-kit-snapshot` (`.husky/pre-commit`)
   schlägt bei jedem Byte fehl, das vom gepinnten Upstream-Commit abweicht (es wird mit einer
   Warnung übersprungen, wenn der Upstream-Klon, `UI_KIT_CLONE` oder
   `_references/cheaper-inference-ui-kit`, fehlt). Wenn dem Kit etwas fehlt, im Adapter oder im
   Screen umgehen und upstream danach fragen.
3. Die Standardtexte des Kits sind Englisch (`label = "Loading"`, `loadingLabel = "Loading table"`…) —
   übergib übersetzte Strings aus `useTranslations(...)`, wann immer eine Kit-Komponente Text rendert.
4. Tailwind-Utilities haben Vorrang vor Kit-Komponentenklassen (das Kit deklariert
   `@layer theme, base, components, utilities` und seine Regeln liegen in `components`) — Utilities
   für Abstände und Layout verwenden, nicht, um Kit-Komponenten umzufärben.
5. Überschriften: `.ci-heading` (Inter, ohne Tracking) für Seiten- und Abschnittstitel;
   `.ci-dashboard-display` (Instrument Serif) nur für großen, sparsamen Display-Text wie den
   Statuscode der Fehlerseite.
6. `tests/unit/dashboard-kit-sweep.test.ts` sichert die Kit-Einführung ab: keine
   Material-Ligatur-Spans unter `src/app` oder `src/shared/components`; im Dashboard-Baum
   (`src/app/(dashboard)` und `src/shared/components`) keine rohen `<select>`, `<textarea>` oder
   `<table>` und kein handgeschriebenes `role="dialog"` außerhalb der aufgeführten Ausnahmen (der
   native Zweig des `Select`-Adapters, `RequestLoggerDetail`); jedes rohe `<button>` oder `<input>`
   dort braucht einen Kommentar mit `kit-exception:` (mit der Begründung), der höchstens 3 Zeilen
   darüber endet; Palettentöne und `dark:`-Varianten nur in den Dateien, die der Test auflistet.
7. Vor einem PR beide Themes und den 390-px-Viewport prüfen (Screenshots); `tests/e2e/a11y.spec.ts`
   führt axe aus.

## 3. Einen Screen hinzufügen

1. Die Seite mit dem Kit-`PageHeader` (`@omniroute/ui-kit/page-header`, `compact` innerhalb des
   Dashboards) eröffnen — Titel, Beschreibung und `actions`. Der Shell-Header lässt dann seinen
   eigenen Titel fallen.
2. Steuerelemente aus `@/shared/components` (den Adaptern) bauen und Kit-Komponenten per Subpath
   verwenden, wo kein Adapter existiert (`Table`/`TableScrollArea`/`DataTableShell`, `Field`,
   `Alert`, `Tabs`, `RadioGroup`, `Slider`…).
3. Icons: `<Icon name="…" />`. Ein neuer Name kommt mit der semantisch passenden
   Lucide-Komponente in `ICON_MAP`; `npm run gen:icon-map` listet die noch fehlenden Namen.
4. Farben: semantische Utilities (`text-success`, `bg-warning-bg`, `border-border`…) und
   `var(--color-chart-N)` für Chart-Serien; keine Hex-Werte und keine `dark:`-Varianten, die nur
   eine Farbe wiederholen.
5. Text: jeder String, einschließlich der Labels, die an Kit-Komponenten übergeben werden, kommt
   aus `useTranslations`. Neue Schlüssel kommen in `src/i18n/messages/en.json`, `pt-BR.json` und
   `vi.json` (der vietnamesische Paritätstest pinnt jeden englischen Schlüssel); die anderen
   Locales werden vom i18n-Sync gefüllt.
6. Vor dem PR die Guards laufen lassen: `tests/unit/dashboard-kit-sweep.test.ts`,
   `tests/unit/icon-map-coverage.test.ts`, `tests/unit/icon-map-object-values.test.ts`,
   `npm run check:dashboard-typecheck` (die einzige Prüfung, die einen doppelten Import in
   `iconMap.ts` erkennt), `npm run check:ui-icu` und die eigenen Tests des Screens.

## 4. Hinzufügen oder Ändern eines Adapters

1. Die öffentliche API von `src/shared/components/index.tsx` beibehalten: gleiche Exportnamen, Default-Exports und
   akzeptierte Props. Legacy-Props im Adapter auf das Kit mappen (siehe `Button.tsx`: `VARIANT_TO_KIT`,
   `SIZE_TO_KIT`).
2. Das Kit über den Unterpfad importieren (`@omniroute/ui-kit/<component>`).
3. Workarounds für Kit-Lücken gehören in den Adapter (oder in `globals.css` `@layer components`, wenn die Korrektur
   ein Style ist), niemals in `packages/ui-kit/src`.
4. `tests/unit/ui/adapters/<name>.test.tsx` hinzufügen oder aktualisieren. Bei einem Adapter mit vielen Aufrufern
   das gerenderte Markup vor und nach der Änderung vergleichen — Änderungen an Padding oder Wrappern wirken sich
   auf jede Ansicht aus.

## 5. Aktualisieren des Kits

`scripts/dev/sync-ui-kit.sh <commit> [clone]` kopiert das Upstream-`src/` des angegebenen Commits nach
`packages/ui-kit/src` und wendet die einzige erlaubte Transformation an (das Suffix `.js` wird aus relativen
Imports entfernt). Anschließend: `git diff packages/ui-kit` prüfen, eine visuelle Kontrolle von Providers,
Settings, Combos, Usage und Endpoint in beiden Themes durchführen, `npm run check:ui-kit-snapshot` und
`npm run test:vitest:ui` ausführen und den PR mit dem Upstream-Changelog öffnen.
