## ခြုံငုံသုံးသပ်ချက်

Quota Sharing Engine သည် ချိတ်ဆက်မှုတစ်ခုတည်းကို မျှဝေသုံးစွဲသည့် API key အများအပြားအကြား provider ၏ အချိန်အခြေပြု quota (ဥပမာ Codex ၏ 5 နာရီ window၊ Kimi ၏ တစ်နာရီလျှင် request 1500) ကို မျှတစွာ ခွဲဝေပေးသည်။

**ဖြေရှင်းပေးသည့် ပြဿနာ:** OmniRoute သည် upstream provider account တစ်ခုတည်းသို့ API key အများအပြားကို proxy ပြုလုပ်ပေးသည်။ မျှဝေခြင်းဆိုင်ရာ logic မရှိပါက key A မှ ရုတ်တရက်များပြားလာသော အသုံးပြုမှုသည် တစ်နာရီအတွက် provider quota ကို ကုန်ဆုံးစေနိုင်ပြီး window ပြန်လည်သတ်မှတ်ချိန်အထိ key B နှင့် C တို့ကို ပိတ်ဆို့ထားစေနိုင်သည်။ Engine သည် အောက်ပါနည်းလမ်းများဖြင့် ယင်းကို ကာကွယ်သည်-

1. Dimension တစ်ခုချင်းစီ (ရာခိုင်နှုန်း၊ request များ၊ token များ၊ $) အလိုက် key တစ်ခုချင်းစီ၏ rolling consumption ကို ခြေရာခံခြင်း။
2. Work-conserving fair-share algorithm ကို အသုံးပြုခြင်း- global pool ပြည့်နှက်မနေသေးသရွေ့ key တစ်ခုသည် အသုံးမပြုထားသော share များမှ ချေးယူနိုင်သည်။
3. Request သည် upstream executor သို့ မရောက်ရှိမီ hot path (`chatCore.ts`) တွင် ရလဒ်ကို မဖြစ်မနေလိုက်နာစေခြင်း။

## အယ်လဂိုရီသမ်- တရားမျှတ-မျှဝေ အလုပ်-ထိန်းသိမ်းခြင်း

`src/lib/quota/fairShare.ts` တွင်အကောင်အထည်ဖော်ခဲ့သည်။

### မုဒ်များ

| အခြေအနေ                                    | မုဒ်          | အနေအထိုင်                                                                          |
| ------------------------------------------ | ------------- | ---------------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **စေတနာ**     | သော့သည် ကမ္ဘာလုံးဆိုင်ရာ ကန့်သတ်ချက်အနှုတ် သုံးစွဲမှုစုစုပေါင်းအထိ ချေးယူနိုင်သည်။ |
| `globalUsedPercent >= saturationThreshold` | **မထွက်ဘူး။** | တစ်ဦးချင်း မျှမျှတတ မျှဝေခြင်းကို တင်းတင်းကျပ်ကျပ် ကျင့်သုံးပါ။                    |

မူရင်း `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`)။

ဤမုဒ်နှစ်ခုသည် မူရင်းအငှားမုဒ် `saturation` တွင် ရေကူးကန်ကို ဖော်ပြသည်။ `consent` မုဒ်ရှိ ရေကူးကန်သည် တင်းကျပ်သော စည်းမျဉ်းများကို အမြဲတမ်း ကျင့်သုံးသည် [သဘောတူညီချက်ဖြင့် ချေးငှားခြင်း (အစုအလိုက် ရွေးချယ်မှု) ကို](#consented-lending-per-pool-opt-in) ကြည့်ပါ။

### အတိုင်းအတာ တစ်ခုချင်း ဆုံးဖြတ်ချက်

ရေကူးကန်အတွင်းရှိ တက်ကြွသောအတိုင်းအတာတစ်ခုစီအတွက် အင်ဂျင်က တွက်ချက်သည်-

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent` အတိုင်းအတာများအတွက်၊ `consumed` ၎င်းအစား ရည်ညွှန်းချက်စာအုပ်မှ လာပါသည် ( [ရာခိုင်နှုန်းအတိုင်းအတာများကိုကြည့်ပါ- သော့တစ်ခုချင်းထည့်တွက်မှုကို](#percent-dimensions-per-key-attribution) ကြည့်ပါ)။

ထို့နောက်-

- **`policy = hard`** `consumed > fairShareAllowed` နှင့် မုဒ်သည် တင်းကျပ်သော → ဖြစ်လျှင်** ဘလောက်** .
- **`policy = soft`** `consumed > fairShareAllowed` နှင့် မုဒ်သည် တင်းကျပ်သော → ဖြစ်လျှင်** အပြစ်ပေး** (ပေါင်းစပ်မှုတွင် ဦးစားပေးလုပ်ပါ၊ ခက်ခက်ခဲခဲပိတ်ဆို့ခြင်းမျိုး ဘယ်သောအခါမှ မလုပ်ပါ)။
- **`policy = burst`** : မျှမျှတတ မျှဝေမှု မခွဲခြားဘဲ ကမ္ဘာလုံးဆိုင်ရာ အကြီးအကဲ တည်ရှိနေချိန်တွင် ခွင့်ပြုပါ။

### ဦးထုပ်အကြွင်းမဲ့

ခွဲဝေချထားမှုတွင်`capValue` + `capUnit` သည် မုဒ် သို့မဟုတ် မူဝါဒနှင့် ကင်းသော ခိုင်မာသော မျက်နှာကျက်တစ်ခုဖြစ်သည်။ ဘယ်အတိုင်းအတာမဆို `consumed >= capValue` အမြဲတမ်း** တုံး** တောင်းဆိုချက်။ `percent` cap တစ်ခုအတွက်၊ `consumed` သော့၏ အစိတ်အပိုင်းတစ်ခုသာဖြစ်သည်။

### ဘက်စုံစစ်ဆေးပါ။

တောင်းဆိုမှုတစ်ခုကို ပိတ်ဆို့ထားလျှင်** တစ်ခုခု** ရေကူးကန်အတွင်းရှိ dimension သည် ၎င်းကိုပိတ်ဆို့မည်ဖြစ်သည်။ Dimensions များသည် သီးခြား — a 5h% ကုန်ဆုံးမှုသည် အပတ်စဉ်% dimension ကို မထိခိုက်စေပါ။

### ငွေချေးခြင်း။

ရက်ရောသောမုဒ်တွင်၊ ခွဲဝေသုံးစွဲမှုနည်းသောသော့သည် အခြားသော့များ၏ ခွဲဝေမထားသောရှယ်ယာများမှ ပိုငွေကို သုံးနိုင်သည်။ ဖော်မြူလာမှာ-

```
maxAllowed = globalLimit - consumedByOtherKeys
```

`consumedByOtherKeys = consumedTotal - consumedByThisKey` ဘယ်မှာလဲ teto global (ထိုအတိုင်းအတာအတွက် pool `limit` ) သည် အမြဲတမ်း မာကျောသော မျက်နှာကျက်ဖြစ်သည်။

### ချေးငွေခွင့်ပြုချက် (အစုအလိုက် ရွေးချယ်မှု)

ရေကူးကန်တစ်ခုစီတွင် အငှားမုဒ်ရှိသည်။ `saturation` သည် ပုံသေဖြစ်ပြီး အထက်ဖော်ပြပါ စည်းကမ်းများကို ထိန်းထားသည်။ `consent` မုဒ်တွင် `hard` သော့သည် အခြားသော့များကို ချေးရန် သဘောတူထားသည့် ပမာဏအတွင်းသာ ၎င်း၏ရှယ်ယာကို ဖြတ်သန်းသည်။ စီမံခန့်ခွဲသူက ရေကူးကန်တစ်ခုစီ၏ မုဒ်ကို သတ်မှတ်ပေးသည်။ သော့ကိုင်ဆောင်သူတိုင်းသည် [Lending consent](#lending-consent) ဖြင့် ၎င်းတို့၏ကိုယ်ပိုင်သဘောတူညီချက်ကို သတ်မှတ်သည်။

သဘောတူညီချက်သည် 0 မှ 100 ရာခိုင်နှုန်းဖြစ်ပြီး အချိန်မီလီစက္ကန့်အတွင်း ရွေးချယ်နိုင်သော နောက်ဆုံးရက်ဖြစ်သည်။ နောက်ဆုံးသတ်မှတ်ရက်သည် အနာဂတ်တွင် ရှိနေစဉ် သော့သည် ၎င်း၏ idle ရှယ်ယာ၏ ရာခိုင်နှုန်းကို ချေးငှားသည်။

အတိုင်းအတာတစ်ခုအတွက်၊ `L` သည် ထိရောက်သောကန့်သတ်ချက်ဖြစ်သည်- အစီအစဉ်ကန့်သတ်ချက်သည် ရေကူးကန်ရှိအကောင့်များကို အဆများသည်။ တောင်းဆိုသည့်သော့အတွက် ဂိတ်သည် တွက်ချက်သည်-

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` သည် သော့၏အလေးချိန်၊ သို့မဟုတ် အလေးချိန် 0 အထက်မရှိသည့်အခါ သော့တိုင်းအတွက် `100 / n` ဖြစ်သည်။ `lend_k` သည် သော့၏တက်ကြွသောရာခိုင်နှုန်းဖြစ်ပြီး ၎င်း၏နောက်ဆုံးရက်ကျော်လွန်သည်နှင့် 0 ။ တောင်းဆိုနေသောသော့၏ကိုယ်ပိုင်သဘောတူညီချက်ကို ဘယ်တော့မှ ထည့်မတွက်ပါ။ ၎င်း၏သုံးစွဲမှုသည် ၎င်း၏ရှယ်ယာပေါင်း `borrowAvailable` သို့ရောက်ရှိသည်နှင့် `hard` သော့ကို ငြင်းပယ်သည်။

ခွဲဝေပေးရန် တောင်းဆိုခြင်းမရှိသော စွမ်းရည် (အလေးများပေါင်းလဒ် 100 အနှုတ်) ကို ချေးငှား၍မရပါ။ သော့မရှိလို့ ချေးဖို့ သဘောတူတယ်။

**ဥပမာ။** `L` သည် 1000 ဖြစ်သည်။

| သော့ | အလေးချိန် | မျှဝေပါ။ | လောင်တယ်။ | ချေးတယ်။ |
| ---- | --------- | -------- | --------- | -------- |
| တစ်  | 50        | 500      | 530       | 0%       |
| ခ    | 30        | 300      | 100       | 50%      |
| ဂ    | 0         | 0        | 60        | 0%       |

- B သည် ၎င်း၏ idle 200 ၏ 50% ကို ချေးငှားပြီး 100 ဖြစ်သည့် C သည် ၎င်း၏ ရှယ်ယာ 60 နှင့် အထက်ကို ရယူထားပြီးဖြစ်သည်။ A ၄၀ ချေးနိုင်တယ်။
- A ကို 530 တွင် ဆောင်ရွက်ပေးပြီး ၎င်း၏ စားသုံးမှု 540 သို့ ရောက်သည်နှင့် ငြင်းဆန်သည်။
- C သည် မည်သည့်အရာကိုမျှ အသုံးမပြုမီ၊ A တွင် သို့မဟုတ် ၎င်း၏ရှယ်ယာအောက်တွင် C သည် 100 ချေးနိုင်သည်။
- C က ဘာမှမသုံးခင် A မှာ 530 နဲ့ C က 70 ချေးနိုင်တယ်။

**သုညအလေးချိန်။** အလေးချိန် 0 ပါသောသော့သည် 0 ၏ဝေစုရှိသည်။ ၎င်းကို အခြားသူများချေးသည့်ပမာဏထက် စားသုံးမှုအောက်တွင်သာ ဆောင်ရွက်ပေးသည်။ ဘယ်သူကမှ မချေးတဲ့အခါ သူ့ရဲ့ ပထမတောင်းဆိုမှုကနေ ငြင်းပယ်ခံရတယ်။

**သတ်မှတ်ရက်။** နောက်ခံလုပ်ဆောင်စရာတစ်ခုမှ ခွင့်ပြုချက်သက်တမ်းကုန်ဆုံးခြင်းမရှိပါ။ တောင်းဆိုမှုတစ်ခုစီသည် နောက်ဆုံးရက်အား ၎င်း၏ကိုယ်ပိုင်အချိန်နှင့် နှိုင်းယှဉ်ကာ၊ ထိုအချိန်နှင့် တူညီသော နောက်ဆုံးရက်ကို ကျော်လွန်သွားပါသည်။ ကန့်သတ်နံပါတ်မဟုတ်သော သိမ်းဆည်းထားသည့် နောက်ဆုံးရက်၊ သို့မဟုတ် `Date` လုပ်နိုင်သည့် အကြီးဆုံးရက်စွဲကို ကျော်သွားပါက ကျော်လွန်သွားသည်ဟု ရေတွက်သည်။

**`soft` နှင့် `burst`။** ချေးငွေကို ကန့်သတ်မထားဘူး။ `soft` သော့ကို ၎င်း၏ရှယ်ယာကို ကျော်ပြီးသည်နှင့် ဦးစားပေးလုပ်ထားသည်။ ရေကူးကန်တွင် နေရာလွတ်ရှိစဉ် `burst` သော့တစ်ခု ဖြတ်သန်းသွားသည်။ ရေကူးကန်၏ စုစုပေါင်း ကန့်သတ်ချက် ပြည့်သွားသည်နှင့် ရေကူးကန်မျက်နှာကျက်သည် သော့တိုင်းကို ငြင်းဆိုဆဲဖြစ်သည်။

**တောင်းဆိုမှုလမ်းကြောင်းပေါ်တွင်ကုန်ကျစရိတ်။** `saturation` ရေကူးကန်သည် ယခင်ကထက်စာလျှင် ဘာမှပိုမဖတ်ပါ။ `consent` ရေကူးကန်တွင်၊ အခြားသော့က ချေးနေစဉ်တွင် အခြားသော့များကို `hard` ကီးတစ်ခု သို့မဟုတ် ၎င်း၏အထက်တွင်သာ ရေတွက်နိုင်သောအတိုင်းအတာတစ်ခုက ဖတ်သည်။ ၎င်းသည် အခြားသော့တစ်ခုအား အပြိုင်ဖတ်စေသည်။ မအောင်မြင်သောဖတ်ခြင်းသည် ထိုသော့အတွက် 0 သုံးစွဲမှုအဖြစ် ရေတွက်သည်။ ရည်ညွှန်းချက်စာအုပ်တွင် သော့တိုင်းကို ကိုင်ဆောင်ထားသောကြောင့် `percent` အတိုင်းအတာသည် ဖတ်ရန်မထည့်ပါ။

**ရေကူးကန်ကို တည်းဖြတ်ခြင်း။** တည်းဖြတ်မှုတစ်ခုသည် တည်ရှိနေသောသော့များ၏ သဘောတူညီချက်ကို သိမ်းဆည်းထားသည်။ ၎င်းသည် ခွဲဝေတည်းဖြတ်မှုများ၊ အုပ်စုလိုက် အစားထိုးမှုများနှင့် `ensure` ခေါ်ဆိုမှုများအတွက် ထိန်းသိမ်းထားသည်။ ဖယ်ရှားထားသောသော့တစ်ခုသည် ၎င်း၏သဘောဆန္ဒကို ဆုံးရှုံးသွားပြီး၊ ပြန်ထည့်ထားသောသော့သည် 0 တွင်စတင်သည်။ စီမံခန့်ခွဲသူလမ်းကြောင်းများသည် သော့တစ်ခုစီ၏သဘောတူညီချက်ကို ပြန်ပေးကာ မည်သည့်အခါမျှ မရေးပါ။ ရေကူးကန်ကို `saturation` သို့ ပြန်ပြောင်းခြင်းဖြင့် ထိုမုဒ်တွင် သက်ရောက်မှုမရှိသော သိမ်းဆည်းထားသော သဘောတူညီချက်တိုင်းကို သိမ်းဆည်းထားသည်။ ရေကူးကန်အား `consent` သို့ ထပ်မံပြောင်းခြင်းသည် နောက်ဆုံးရက်ကျော်လွန်ခြင်းမရှိသော သိမ်းဆည်းထားသော သဘောတူညီချက်များကို ပြန်လည်အသက်သွင်းသည်။ သော့ကိုင်ဆောင်သူသည် မုဒ်နှစ်ခုစလုံးတွင် သိမ်းဆည်းထားသော သဘောတူညီချက်ကို ရှင်းလင်းနိုင်သည်။

**အဆင့်မြှင့်တင်ခြင်း။** `lending_percent` နှင့် `lending_until` ကော်လံများ ရှိနှင့်ပြီးဖြစ်ပါက၊ ရွှေ့ပြောင်းခြင်းသည် `borrow_mode` သာ ပေါင်းထည့်မည်ဖြစ်ပြီး သိမ်းဆည်းထားသော ရာခိုင်နှုန်းများသည် ၎င်းတို့အတိုင်း ဆက်ရှိနေမည်ဖြစ်သည်။ ရေကူးကန်တိုင်းသည် `saturation` မုဒ်တွင် စတင်သည်။ pool wizard ရှိ ရေကူးကန်အလိုက် `consent` ဖွင့်ပါ။ သိမ်းဆည်းထားသော တန်ဖိုးများမှ မည်သည့်အရာကိုမျှ ကောက်ချက်မချပါ။

**ကန့်သတ်ချက်များ။**

- ငွေချေးသူတစ်ဦးသည် ၎င်း၏ကိုယ်ပိုင်ဝေစုကို အသုံးမပြုမီ ၎င်း၏မျက်နှာကျက်တွင် ရေကန်ကို ရှာဖွေနိုင်သည်။ အခြားသူများ ချေးထားသော ပမာဏသည် ရေကူးကန်၏ စုစုပေါင်းအပေါ် တွက်ချက်သည်။
- ချက်လက်မှတ်သည် တောင်းဆိုမှုမတိုင်မီ လုပ်ဆောင်ပြီး မည်သည့်အရာကိုမျှ သိမ်းဆည်းထားသည်။ တစ်ပြိုင်နက်တည်း တောင်းဆိုမှုများကို မှတ်တမ်းတင်ခြင်းမပြုမီ သုံးစွဲမှုကို ဖတ်ရှုနိုင်သောကြောင့် ချေးငွေပမာဏကို တစ်ကြိမ်ထက်ပို၍ သုံးစွဲနိုင်ပြီး လေယာဉ်ပျံသန်းမှု တောင်းဆိုချက်များနှင့် ကန့်သတ်ထားသည်။ `saturation` မုဒ်၏မျှဝေမှုစစ်ဆေးမှုတွင် တူညီသောပိုင်ဆိုင်မှုရှိသည်။

## Sliding Window Counter

`src/lib/quota/sqliteQuotaStore.ts` နှင့် `redisQuotaStore.ts` တို့တွင် အကောင်အထည်ဖော်ထားသည်။

`(apiKeyId, dimensionKey)` တစ်ခုလျှင် bucket နှစ်ခုရှိသည်-

- `curr`: လက်ရှိ bucket (`floor(nowMs / windowMs)`)
- `prev`: ယခင် bucket (`curr - 1`)

ထိရောက်သော rolling value-

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**တိကျမှု**: ~99% တိကျသည်။ Bucket များအကြား နယ်နိမိတ်တွင် အမှားပမာဏသည် window အရွယ်အစား၏ အများဆုံး 1% ဖြစ်သည် (bucket 2 ခုဖြင့် ခန့်မှန်းခြင်းတွင် ပင်ကိုအားဖြင့် ရှိနေသည့် အမှားဖြစ်သည်)။

### တစ်ပြိုင်နက်လုပ်ဆောင်မှု

SQLite driver: `(apiKeyId | dimensionKey)` key တစ်ခုချင်းစီအတွက် in-memory mutex သည် read-modify-write race ကို ကာကွယ်ပေးသည်။ Pattern သည် `src/sse/services/auth.ts` ၏ anti-thundering-herd ပုံစံအတိုင်း ဖြစ်သည်။

Redis driver: atomic increment အတွက် Lua EVAL script ကို အသုံးပြုသည် — Redis command တစ်ခုတည်းအဖြစ် လုပ်ဆောင်သည်။

## Driver များ

### SQLite (မူလသတ်မှတ်ချက်၊ ထည့်သွင်းရန်မလို)

- Table: `quota_consumption` (migration `073_quota_pools.sql` / `074_quota_consumption.sql` ကို ကြည့်ပါ)။
- Instance တစ်ခုတည်း အသုံးပြုသည့် deployment များအတွက် အသင့်တော်ဆုံးဖြစ်သည်။
- Persistence အားလုံးကို လက်ရှိ OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) တွင် သိမ်းဆည်းထားသည်။

### Redis (ရွေးချယ်နိုင်၊ instance အများအပြား)

- `ioredis` npm package လိုအပ်သည်။
- Counter များကို Redis တွင် သိမ်းဆည်းပြီး metadata (pool/allocation များ) ကို SQLite တွင် ဆက်လက်သိမ်းဆည်းသည်။
- Counter များကို အတူမျှဝေရန်လိုအပ်သည့် replica အများအပြားပါသော deployment များအတွက် အသင့်တော်ဆုံးဖြစ်သည်။

### Driver များ ပြောင်းလဲခြင်း

Settings UI (`/dashboard/settings` → Quota Store) မှတစ်ဆင့် သို့မဟုတ် env var များမှတစ်ဆင့် ပြောင်းလဲနိုင်သည်-

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB setting သည် env ထက် ဦးစားပေးသည်။ `driver=redis` ဖြစ်သော်လည်း URL မရှိလျှင် သို့မဟုတ်
`ioredis` ကို ထည့်သွင်းမထားလျှင် factory သည် SQLite သို့ ပြန်လည်အသုံးပြုပြီး သတိပေးချက်တစ်ခုကို log မှတ်တမ်းတင်သည်။

Driver ရွေးချယ်မှုအစဉ်-

1. DB setting `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. မူလသတ်မှတ်ချက်- `sqlite`

## Multi-Dimension

ရေကူးကန်တစ်ခုသည် အတိုင်းအတာများစွာရှိနိုင်သည်။ အတိုင်းအတာတစ်ခုစီသည် လွတ်လပ်သည်-

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**ဥပမာ- Codex အစီအစဉ်** (5h% + အပတ်စဉ်%)-

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

တောင်းဆိုချက်တစ်ခုသည် ခွင့်ပြုရန် အတိုင်းအတာအားလုံးကို ကျေနပ်ရပါမည်။

### ရာခိုင်နှုန်းအတိုင်းအတာ- သော့တစ်ခုချင်းထည့်တွက်ခြင်း။

ရာခိုင်နှုန်းအစီအစဉ်တစ်ခုသည် အကောင့်တစ်ခုလျှင် အသုံးပြုမှုကိန်းဂဏန်းတစ်ခုနှင့် အစီအစဉ်ဝင်းဒိုးကို အစီရင်ခံသည်။ ဝန်ဆောင်မှုပေးသူက API သော့တစ်ခုအတွက် ကောင်တာမပေးပါ။

ထိုကိန်းဂဏန်းကို သော့များကြားတွင် ပိုင်းခြားရန် ရေကူးကန်တစ်ခုစီသည် အကောင့်တစ်ခုစီအတွက် ရည်ညွှန်းချက်စာအုပ်တစ်အုပ်နှင့် အစီအစဉ်ဝင်းဒိုးကို သိမ်းဆည်းထားသည်။ `src/lib/quota/percentLedger.ts` သည် စာအုပ်၏စည်းကမ်းများကို ကိုင်ဆောင်ထားသည်။ `src/lib/quota/percentAttribution.ts` စာအုပ်ကို ပြဋ္ဌာန်းထားသော ကိန်းဂဏန်းများအဖြစ် ပြောင်းလဲပေးသည်။ ရလဒ်သည် အဓိကလမ်းကြောင်းတစ်ခုစီမှ တိုကင်များမှ တည်ဆောက်ထားသော ခန့်မှန်းချက်ဖြစ်သည်။

#### စာအုပ်ကို ရွေ့လျားစေသော ဖတ်ရှုမှုများ

စာအုပ်သည် တောင်းဆိုထားသော အစီအစဉ်ဝင်းဒိုးအတွက် ပံ့ပိုးပေးသူ၏ ကိုယ်ပိုင်ကိန်းဂဏန်းပေါ်တွင်သာ ရွေ့လျားသည်။ ဤချိတ်ဆက်မှုများသည် တစ်ခုအစီရင်ခံသည်-

| ပံ့ပိုးပေးသူ                     | ပြတင်းပေါက်များကို စီစဉ်ပါ။ |
| -------------------------------- | --------------------------- |
| Claude၊ OAuth ချိတ်ဆက်မှုမှတဆင့် | `5h`, `weekly`              |
| Codex                            | `5h`, `weekly`              |

ဤအရာများကို စာဖတ်ခြင်းအဖြစ် မရေတွက်ပါ။

- တုံ့ပြန်မှုတစ်ခုသည် ဝန်ဆောင်မှုပေးသူအား ဖောက်သည်က ပျက်သွားသည်ဟု အမှတ်အသားပြုသည်။
- ပံ့ပိုးပေးသူ၏ ရာခိုင်နှုန်းကို အစီရင်ခံခြင်းမရှိသော Claude ဝင်းဒိုးတစ်ခု
- အခြားဝင်းဒိုး၏ပုံသဏ္ဍာန် သို့မဟုတ် ပြတင်းပေါက်များတွင် အဆိုးဆုံးအခြေအနေ
- နှုန်းကန့်သတ်ချက် ခေါင်းစီးနောက်ပြန်
- မအောင်မြင်ဘူး

API သော့ပါသော Claude အပါအဝင် အခြားဝန်ဆောင်မှုပေးသူများသည် စာအုပ်မရှိပါ။ ဤပြောင်းလဲမှုမတိုင်မီကဲ့သို့ သော့တစ်ခုစီကို ၎င်းတို့၏ ရာခိုင်နှုန်းအတိုင်းအတာများပေါ်တွင် 0 ကောက်ခံပါသည်။

စာဖတ်ခြင်းသည် saturation signal ၏ 30-second cache ကိုမျှဝေသည်။ Claude ဖတ်ခြင်းသည် ကိန်းဂဏန်းကို တုံ့ပြန်မှု ခေါင်းစီးများတွင် တွေ့ရှိသည့်အခါ သို့မဟုတ် ထိုအချိန်ကို သိရှိသည့်အခါ အသုံးပြုမှုအဆုံးမှတ်မှ ဖတ်သည့်နေ့စွဲဖြင့် ရက်စွဲတပ်ထားသည်။ အဆိုပါ cache entry ကိုတည်ဆောက်သည့်အခါအခြားစာဖတ်ခြင်းများကိုရက်စွဲပါရှိသည်။

#### စာအုပ်သိမ်းထားတာ ဘာလဲ။

မှတ်တမ်းတင်ထားသော တောင်းဆိုမှုတစ်ခုစီသည် ၎င်း၏ တိုကင်များ၊ တစ်ကြိမ်၊ ကောင်တာတစ်ခုစီသို့ ပေါင်းကူးကန်တစ်ခု၊ အကောင့်နှင့် သော့တို့ကို ပေါင်းထည့်သည်။ ကောင်တာတစ်ခုသာ ပေါက်သည်။ စာအုပ်တွင် အချက်သုံးချက်ကို သိမ်းဆည်းထားသည်။

- အခြေခံမျဉ်း- စာအုပ်ဖွင့်ချိန် သို့မဟုတ် ပြတင်းပေါက်နောက်ဆုံးလှည့်သည့်ပုံ
- နောက်ဆုံးအသုံးချပုံ
- သော့တစ်ခု၊ တစ်ချိန်တည်းမှာပင် ၎င်း၏ တိုကင်ကောင်တာကို ၎င်း၏ အမှတ်အသားဟု ခေါ်သည်။

ပြဋ္ဌာန်းချက် သို့မဟုတ် အသုံးပြုမှုလမ်းကြောင်းက ရည်ညွှန်းချက်ကို တွက်ချက်သည့်အခါ စာအုပ်ကို အပ်ဒိတ်လုပ်သည်။ ရေးထားသည်များကို ပြန်လည်ပြင်ဆင်မှုနံပါတ်ပေါ်တွင် နှိုင်းယှဉ်သတ်မှတ်ထားသည်။ အသစ်ပြန်ဖတ်ပြီး တခါပြန်ကြိုးစားမှု ရှုံးတဲ့ စာရေးဆရာ။

#### သော့အပိုင်းကို ဘယ်လိုတွက်ချက်မလဲ။

စာအုပ်ဖတ်သည့်အခါ သော့တစ်ပိုင်းစီကို တွက်ချက်သည်။ အခြေခံလိုင်းကို တိုကင်များ အချိုးအစားအလိုက် သော့များကြားတွင် ပိုင်းခြားထားသောကြောင့် ကိန်းဂဏန်း ကြီးထွားလာခြင်း။

Together၊ ထိုတိုကင်များသည် `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` တိုကင်တစ်ခုလျှင် ပုံသေတစ်မှတ် (ပုံသေ 1,000) ဖြင့် ရှင်းပြသည်။ ကြီးပွားခြင်းဆိုတာ ပြင်ပက မရှင်းပြတတ်ဘူး။ အခြေခံအချက်က ပြင်ပလည်းဖြစ်တယ်။

ဥပမာအားဖြင့်၊ စာအုပ်တစ်အုပ်သည် 0 တွင်ဖွင့်သည်။ Key A သည် တိုကင် 900,000 နှင့် သော့ B လမ်းကြောင်း 100,000 ကို လမ်းကြောင်းပေးသည်။ ကိန်းဂဏန်း 60 တွင် A အပိုင်းသည် 54 မှတ်ဖြစ်ပြီး B အပိုင်းသည် 6 မှတ်ဖြစ်သည်။

၎င်း၏သော့အမှတ်အသားအောက်ရှိ ကောင်တာတစ်ခုသည် ပြန်လည်စတင်ပြီး အပြည့်အဝရေတွက်ပါသည်။ ပြတင်းပေါက်အလယ်ရှိ ရေကူးကန်ကို ချိတ်ဆက်ထားသည့် သော့ကဲ့သို့သော အမှတ်အသားမပါသောသော့သည် ၎င်း၏တိုကင်များအားလုံးကို ရေတွက်သည်။ တိုကင်များကို နောက်ကျစေသော ကိန်းဂဏန်းသည် နောက်ဖတ်ခြင်းတွင် အမှားဖြစ်သွားသည်။ မစုပြုံပါဘူး။

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` သည် ရည်ညွှန်းချက်တိုင်းတွင် ဖတ်သည်။ အနည်းဆုံး 1 ၏ ကန့်သတ်နံပါတ်မဟုတ်သော တန်ဖိုးသည် 1,000 သို့ ပြန်ရောက်သွားသည်။

#### စာဖတ်ခြင်းသည် စာအုပ်ကို မည်သို့ပြောင်းလဲစေသနည်း။

ပထမကိုက်ညီသော စည်းမျဉ်းသည် အကျုံးဝင်သည်-

1. **စာအုပ်မရှိသေးပါ-** စာဖတ်ခြင်းသည် စာအုပ်ကိုဖွင့်သည်။ ၎င်း၏ပုံသည် အခြေခံမျဉ်းဖြစ်ပြီး ကောင်တာတိုင်းကို အမှတ်အသားပြုထားသည်။
2. **အသက်ကြီးသောစာဖတ်ခြင်း-** နောက်ဆုံးအသုံးမပြုမီ ရက်စွဲပါစာဖတ်ခြင်းကို လျစ်လျူရှုထားသည်။ ထို့ကြောင့် ပြန်လည်သတ်မှတ်ချိန်သည် သိမ်းဆည်းထားသည့်စာထက် မိနစ် 30 ကျော်စောသော စာဖတ်ခြင်းဖြစ်ပါသည်။
3. **ဝန်ဆောင်မှုပေးဝင်းဒိုးအသစ်-** ပြန်လည်သတ်မှတ်ချိန်ထက် မိနစ် 30 ကျော်နောက်ကျပြီးမှ စာအုပ်ကို လှည့်ပါ။ ပုံသည် အခြေခံလိုင်းဖြစ်လာပြီး ကောင်တာတိုင်းကို ထပ်မံအမှတ်အသားပြုသည်။ ကောင်တာမပါသောသော့များ စာအုပ်ကို ချန်ထားခဲ့သည်။
4. **ပြီးဆုံးသည့်ဝင်းဒိုး-** သိမ်းဆည်းထားသော ပြန်လည်သတ်မှတ်ချိန်သည် ဖတ်ရှုခြင်း၏ဒေတာအချိန်ပြီးနောက်မဟုတ်သော ဝင်းဒိုးကုန်ဆုံးသွားခြင်းကို ဆိုလိုသည်။ စာဖတ်ခြင်းသည် စာအုပ်ကို ပုံသဏ္ဍန်အတိုင်း လှည့်သည်။
5. **ပိုမြင့်သောရုပ်ပုံ-** နောက်ဆုံးပုံမျှသာ ရွေ့သည်။ အခြေခံမျဥ်းများနှင့် အမှတ်အသားများသည် တည်ရှိနေပါသည်။
6. **တူညီသောရုပ်ပုံ** ပုံ၊ အခြေခံမျဥ်းနှင့် အမှတ်များ ရှိနေသည်။ စာအုပ်မရှိလို့ ပြန်လည်သတ်မှတ်ချိန်သာ ရေးတာပါ။
7. **အောက်ပုံ-** အောက်ပုံသဏ္ဍန်ကို ဘယ်တော့မှ မသုံးပါဘူး။ အချက်သုံးချက် ကိုင်ထားမှသာ စာအုပ်ကို လှည့်ပါ။ ၎င်းသည် နောက်ဆုံးအသုံးပြုထားသောဖတ်ခြင်းထက် အနည်းဆုံး နှစ်မိနစ် ပိုအသစ်ဖြစ်သည်။ ပြတင်းပေါက်က ဖွင့်ထားတယ်လို့ ဘာမှ မပြောပါဘူး။ ၎င်းသည် တစ်မှတ်ထက် ပိုနိမ့်သည်။

အရာသုံးခုကို ကိုင်ထားသည့်အခါ ပြတင်းပေါက်သည် တူညီသောအဖွင့်တစ်ခုအဖြစ် ရေတွက်သည်။ ပြန်လည်သတ်မှတ်ချိန် နှစ်ခုစလုံးကို သိပါသည်။ သူတို့အချင်းချင်း မိနစ် 30 အတွင်း သိမ်းဆည်းထားသည့်အရာသည် စာဖတ်ခြင်းထက်သာလွန်နေသေးသည်။ ထိုပြတင်းပေါက်အတွင်းရှိ အောက်ပုံသည် ဘာမှမပြောင်းလဲပါ။

ပြန်လည်သတ်မှတ်ချိန်သည် ၎င်းကိုသယ်ဆောင်သောဖတ်ရှုခြင်း၏ဒေတာအချိန်မတိုင်မီတွင်သာ သိမ်းဆည်းထားသည်။ မြင့်မားသောကိန်းဂဏန်းသည် ၎င်းကိုအသုံးပြု၍ရသည့်အခါတွင် ၎င်း၏ပြန်လည်သတ်မှတ်ချိန်ကို သိမ်းဆည်းထားပြီး အခြားနည်းဖြင့် သိမ်းဆည်းထားသည်။ စာအုပ်တွင်မရှိမှသာ တူညီသောကိန်းဂဏန်းတစ်ခုသည် ၎င်း၏စာဖတ်ခြင်း၏ပြန်လည်သတ်မှတ်ချိန်ကို မှတ်တမ်းတင်သည်။ အခြားဘာမှမပြောင်းလဲပါ။ စာအုပ်အခွေကို မလှန်နိုင်သော အောက်ပုံသည် ပြန်လည်သတ်မှတ်ချိန်မရှိပါ။

#### စာအုပ်ကိုသုံးတဲ့အခါ

စာဖတ်ပြီးနောက်၊ ၎င်း၏သိမ်းဆည်းထားသည့် ပြန်လည်သတ်မှတ်ချိန်သည် လက်ရှိအချိန်ထက် မကျော်လွန်ပါက စာအုပ်ကို အသုံးပြုမည်ဖြစ်သည်။ ကက်ရှ်မှ ပေးဆောင်ထားသည့်အရာကဲ့သို့ ပြန်လည်သတ်မှတ်ခြင်းမပြုမီလေးတွင် ပြုလုပ်ခဲ့သော ဖတ်ရှုမှုတစ်ခုကို ၎င်းပြီးနောက်တွင် တွေ့ရှိသောအခါ ယင်းအခြေအနေ ဖြစ်ပေါ်လာသည်။

အသုံးပြု၍ရနိုင်သော စာဖတ်ခြင်းမရှိဘဲ၊ သိမ်းဆည်းထားသောစာအုပ်ကို လက်ရှိဝင်းဒိုးစာအုပ်အဖြစ် တည်ရှိနေချိန်တွင်သာ အသုံးပြုပါသည်။ ၎င်းသည် ကိစ္စနှစ်ခုတွင် ရှိနေသည်-

- ၎င်း၏ပြန်လည်သတ်မှတ်ချိန်ကို သိပြီး ရှေ့တွင်ရှိနေဆဲဖြစ်သည်။
- ၎င်းတွင်ပြန်လည်သတ်မှတ်ချိန်မရှိပါ၊ ၎င်းကိုပြောင်းလဲခဲ့သောနောက်ဆုံးဖတ်ခြင်းသည်အများဆုံး 15 မိနစ်ဖြစ်သည်။

မဟုတ်ရင် စာအုပ်မရှိတဲ့အခါ ဘာမှမသတ်မှတ်ပါဘူး။ ပြန်လည်သတ်မှတ်ချိန်ကျော်လွန်သွားသော သိမ်းဆည်းထားသည့် စာအုပ်ကို မည်သည့်အခါမှ ငွေမကောက်ခံပါ။

#### ပြဋ္ဌာန်းသည်။

ရာခိုင်နှုန်းအတိုင်းအတာတစ်ခုတွင် သော့အသုံးပြုမှုသည် ၎င်း၏သတ်မှတ်ထားသောအပိုင်းနှင့် ပြင်ပအပိုင်း၏ဝေစုဖြစ်သည်။ ပြင်ပအစိတ်အပိုင်းသည် ခွဲဝေပေးခြင်းမရှိကြောင်း အခိုင်အမာဆိုထားသည့် စွမ်းရည်ကို ဦးစွာအသုံးပြုသည် (အလေးချိန်၏ပေါင်းလဒ် 100 အနှုတ်)။ အလေးချိန်အလိုက် သော့များကြားတွင် ပိုလျှံမှုများကိုသာ မျှဝေပါသည်။

ထိုစားသုံးမှုသည် အခြားအတိုင်းအတာတစ်ခုအတွက် သော့၏တရားမျှတသောရှယ်ယာနှင့် နှိုင်းယှဉ်ပါသည်။ saturation signal သည် `QUOTA_SATURATION_THRESHOLD` (မူလ 0.5) သို့ရောက်ရှိသောအခါ တင်းကျပ်သောမုဒ်သည် စတင်ဆဲဖြစ်သည်။ နံပါတ်တိုင်းကို ထိရောက်သောကန့်သတ်ချက်ဖြင့် တိုင်းတာသည်- အကောင့်တစ်ခုချင်းကန့်သတ်ချက်သည် အစုအဝေးရှိ အကောင့်အရေအတွက်ထက် အဆများသည်။

`capUnit: "percent"` ပါသော အကြွင်းမဲ့ ဦးထုပ်သည် သော့နှင့် သက်ဆိုင်သည့် အစိတ်အပိုင်းကိုသာ ရေတွက်သည်၊ ထိုနည်းအတိုင်း အတိုင်းအတာ။ အကောင့်တစ်ခုလျှင် 100 နှင့် k အကောင့်ကန့်သတ်ချက်ကို ယူပါ။ ဝန်ဆောင်မှုပေးသည့်အကောင့်၏ကိန်းဂဏန်း၏ သော့အစိတ်အပိုင်းသည် N/k အမှတ်များရောက်ရှိသောအခါ N ၏ဦးထုပ်ကိုရောက်ရှိသည်။ အကောင့်တစ်ခုစီသည် ၎င်း၏ကိုယ်ပိုင်စာအုပ်ကို စစ်ဆေးပါသည်။ ဥပမာအားဖြင့်၊ အကောင့်နှစ်ခုဖြင့်၊ အကောင့်တစ်ခု၏ကိန်းဂဏန်းတစ်ခု၏ 5 မှတ်တွင် 10 ဦးထုပ်ကို ရောက်သည်။

စတိုးဆိုင်ကို မဖတ်နိုင်သောအခါတွင် မည်သည့်အရာမှ မပါ၀င်ဘဲ သော့တိုင်းကို ထိုအတိုင်းအတာတွင် 0 ကောက်ခံပါသည်။ စာအုပ်တစ်အုပ်ရေးရန် ပျက်ကွက်သောအခါ၊ ထိုရည်ညွှန်းချက်ကို ဖတ်ပြီးသည့်အတိုင်း စာအုပ်ကို အသုံးပြုသည်။ မအောင်မြင်သော တိုကင်တစ်ခုသည် တောင်းဆိုချက်၏ တိုကင်များကို စာအုပ်ထဲမှ ချန်ထားခဲ့သည် ။ ဤမအောင်မြင်မှုတစ်ခုမှ တောင်းဆိုချက်တစ်ခုကို ပိတ်ပင်ထားသည်။

`consent` ရေကူးကန်တွင်၊ ချေးငွေဖော်မြူလာသည် အထက်တွင်ဖော်ပြထားသည့်အတိုင်း သော့တစ်ခုစီ၏ သုံးစွဲမှုရာခိုင်နှုန်းအတိုင်းအတာကို အသုံးပြုသည်။ အခြားသော့ငှားသည့်အခါ စာအုပ်ကို တစ်ကြိမ်ဖတ်ပြီး သော့တိုင်းအတွက် သတ်မှတ်သည်။ အသုံးပြုနိုင်သောစာအုပ်မရှိပါက သော့တိုင်းသည် 0 ကောက်ခံပါသည်။ အလေးချိန်ရှိသောသော့သည် ဖြတ်သန်းသွားမည်ဖြစ်ပြီး အလေးချိန် 0 ရှိသောသော့သည် အခြားသော့အားချေးသည့်အခါမှသာ ဖြတ်သန်းပါသည်။

#### အသုံးပြုမှုလမ်းကြောင်း

`GET /api/quota/pools/{id}/usage` တူညီသောလုပ်ဆောင်ချက်မှတစ်ဆင့် တူညီသောနံပါတ်များကို အစီရင်ခံသည်။ ရာခိုင်နှုန်းအတိုင်းအတာတစ်ခုသည် `accounts` တွင် pool ချိတ်ဆက်မှုတစ်ခုလျှင် ဝင်ပေါက်တစ်ခုရှိသည်။ ၎င်း၏ ထိပ်တန်းအဆင့် `consumedTotal` နှင့် `perKey` ပထမဆုံး entry ကို ထင်ဟပ်စေသည်။

လမ်းကြောင်းသည် လက်ရှိဖတ်ရှုခြင်းကိုလည်း အကျုံးဝင်သောကြောင့် ၎င်းသည် တောင်းဆိုမှုအတိုင်း စာအုပ်ကို ကြိုပေးနိုင်သည်။ အသုံးပြု၍မရသောစာဖတ်ခြင်း မရှိသည့်အခါ သို့မဟုတ် အောက်ခြေပုံသဏ္ဍာန်ကို အသုံးမပြုသည့်အခါ `internal + external` `consumedTotal` နှင့် ကွဲပြားနိုင်သည်။

#### သိမ်းဆည်းခြင်းနှင့် ထိန်းသိမ်းခြင်း။

ခွဲတမ်းဆိုင် နှစ်ခုစလုံးက စာအုပ်ကို သိမ်းထားတယ်။ SQLite တွင်၊ အလိုအလျောက်ဒေတာဘေ့စ်ရှင်းလင်းခြင်းကိုဖွင့်သောအခါ၊ ရက် 60 ကြာမွမ်းမံမွမ်းမံထားသောအတန်းများကိုဖယ်ရှားသည်။ Redis တွင်၊ ရေကူးကန်ချိတ်ဆက်မှု၏ စာအုပ်များနှင့် ကောင်တာများသည် သော့တစ်ချောင်းကို မျှဝေထားသည်။ ၎င်း၏နောက်ဆုံးတိုကင်ရေးခြင်း သို့မဟုတ် စာအုပ်အပြောင်းအလဲပြီးနောက် ရက် 60 တွင် သက်တမ်းကုန်ဆုံးသည်။ မပြောင်းလဲသောစာအုပ်ကို ပြန်လည်ရေးသားခြင်းမပြုသောကြောင့် ဖြတ်တောက်ခြင်းကို အရှည်ဆုံးအစီအစဉ်ဝင်းဒိုးအထက်တွင် သတ်မှတ်ထားပါသည်။ ကိုယ်တိုင်အသုံးပြုမှု-မှတ်တမ်းကို ပြန်လည်သတ်မှတ်ခြင်းသည် SQLite ရှိ စာအုပ်များကိုလည်း ရှင်းလင်းပေးသည် (ကန့်သတ်ချက်များကို ကြည့်ပါ)။

#### ကန့်သတ်ချက်များ

- အခြေခံလိုင်းကို တိုကင်များဖြင့် ပိုင်းခြားထားသောကြောင့် ထိုအချိန်မှစ၍ လမ်းကြောင်းပေါ်ရှိ သော့တစ်ခုစီဖြင့် အကောင့်၏တိုးတက်မှုအားလုံးကို။ ကြီးထွားလာတဲ့အခါ အရေးမကြီးပါဘူး။
- ထို့ကြောင့် OmniRoute ပြင်ပတွင်ပြုလုပ်သောအသုံးပြုမှုကို ၎င်းတို့၏တိုကင်များခွင့်ပြုသည့်အထိ သော့များတွင် ကောက်ခံပါသည်။ စာအုပ်ကိုဖွင့်ထားပြီးဖြစ်သည့်အချိန်၊ ဝင်းဒိုး၏ သော့တစ်ခု၏ပထမဆုံးတောင်းဆိုမှုမတိုင်မီ ပြုလုပ်ထားသည့်အသုံးပြုမှု ပါဝင်သည်။

- သိမ်းဆည်းထားသည့် ပြန်လည်သတ်မှတ်ချိန်ပြီးနောက်တွင် အသုံးပြု၍မရသောစာဖတ်ခြင်းသို့ ရောက်ရှိလာသည့်အခါ၊ သော့တစ်ရာခိုင်နှုန်းမျှဝေမှုများနှင့် ရာခိုင်နှုန်းစာထုပ်များကို ဖတ်ရှုခြင်းပြန်မလာမချင်း အတင်းအကြပ်လုပ်ဆောင်မည်မဟုတ်ပါ။ ပြန်လည်သတ်မှတ်ချိန်မရှိဘဲ၊ ၎င်းသည် စာအုပ်ကိုပြောင်းလဲစေသည့် နောက်ဆုံးအကြိမ်ဖတ်ပြီးနောက် 15 မိနစ်တွင် စတင်သည်။
- Redis စတိုးတွင်၊ စာရေးဆရာတစ်ဦး၏ချက်လက်မှတ်နှင့်၎င်း၏ရေးမှုအကြားရက်ပေါင်း 60 ကြာအလုပ်မလုပ်သောစာအုပ်သည်သက်တမ်းကုန်ဆုံးနိုင်သည်။ ထို့နောက် မှန်ကန်သောအခြေအနေဖြစ်သည့် 1 အထက်တည်းဖြတ်မှုတွင် ၎င်းကို ပြန်လည်ဖန်တီးသည်။

## ပိုက်လိုင်းပေါင်းစည်းခြင်း။

### PRE ချိတ် (`open-sse/handlers/chatCore.ts`)

အထောက်အထားနှင့် မူဝါဒစစ်ဆေးမှုများအပြီးတွင် အထက်ရေစီးကြောင်း စီမံဆောင်ရွက်သူရှေ့တွင် လုပ်ဆောင်သည်-

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**ပျက်ကွက်** `enforceQuotaShare` ချလိုက်ပါက၊ တောင်းဆိုချက်ကို `pino.warn` မှတ်တမ်းဖြင့် ဖြတ်သန်းခွင့်ပြုသည်။ ၎င်းသည် အသွားအလာအားလုံးကို ပိတ်ဆို့ခြင်းမှ ခွဲတမ်းအင်ဂျင် ချွတ်ယွင်းချက်မှ တားဆီးပေးသည်။

**စွမ်းရည်ပြန်တက်လာတဲ့အခါ။** သော့၏ရှယ်ယာတွင် သို့မဟုတ် ရေကူးကန်မျက်နှာကျက်တွင် ငြင်းဆိုမှုသည် အငှားမုဒ်နှစ်ခုစလုံးတွင် ဝါကျနှစ်ကြောင်းအနက်တစ်ခုဖြင့် အဆုံးသတ်သည်-

- `percent` window: `. The <window> window resets at <time>.` အချိန်သည် ဝန်ဆောင်မှုပေးသူ အစီရင်ခံစာများကို ပြန်လည်သတ်မှတ်ခြင်း ဖြစ်သည်။
- ရေတွက်နိုင်သော ယူနစ်- `. Enough <window> usage is expected to clear by <time>.` အချိန်သည် အခြားဘာမှ ပေးပို့ခြင်းမရှိပါက လျှောပြတင်းပေါက်မှ အပေါ်ဘက်တွင် ချည်နှောင်ထားသည်။

`<time>` သည် UTC တွင် ISO 8601 လက်ငင်းဖြစ်သည်။ ထို့နောက် ငြင်းဆိုချက်သည် `Retry-After`: ထိုခဏအထိ စက္ကန့်တစ်ခုလုံး၊ အပေါင်းတစ်ခုဖြစ်သည်။ အကြာကြီးစောင့်ရသော ကလိုင်းယင့်သည် ချက်ခြင်းပြီးနောက် တစ်စက္ကန့်တွင် အများဆုံး ပြန်ကြိုးစားသည်။ လက်ငင်းကို မသိသောအခါ၊ ငြင်းဆိုမှုသည် ဝါကျနှင့် ခေါင်းစီးကို မဆောင်ပါ။ အကြွင်းမဲ့ ငြင်းဆိုချက်သည် အကျုံးဝင်သည် မဟုတ်ပေ။ အများသူငှာကုဒ်သည် `quota_share_blocked` ရှိနေသည်။

မျှဝေရန်ငြင်းဆိုမှုသည် မျှဝေထားသောချိတ်ဆက်မှုကို မထိပါ။ ၎င်းသည် cooldown မသတ်မှတ်ထားဘဲ၊ မော်ဒယ်လော့ခ်မရှိခြင်းနှင့် ဝန်ဆောင်မှုပေးသူ ဘရိတ်ကာများ ချို့ယွင်းမှုမရှိခြင်းနှင့် ရေကူးကန်၏အခြားသော့များကို ဆက်လက်လုပ်ဆောင်နေပါသည်။ ကွန်ဘိုတစ်ခု၏ပစ်မှတ်တိုင်းသည် ၎င်း၏ရှယ်ယာအတွက်သော့ကိုငြင်းဆိုသောအခါ၊ ကွန်ဘိုသည် စောင့်ဆိုင်းစရာမလိုဘဲ 429 ကိုအဖြေပေးသည်။ ၎င်း၏အဖြေသည် `Retry-After` အဖြစ် အရိပ်အမြွက်ကို ဆောင်သည်။ ထည့်သွင်းမှုလမ်းကြောင်းသည် ၎င်း၏ငြင်းဆိုချက်ကို တူညီသောဝါကျဖြင့် အဆုံးသတ်ပြီး `Retry-After` မရှိပါ။

### POST ချိတ် (စားသုံးမှုမှတ်တမ်း)

အောင်မြင်သော တုံ့ပြန်မှုပြီးနောက်

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**ရေစုန်မျောမှုမှတ်စု** : `consume` တုံ့ပြန်မှုအပြီးတွင် ပျက်ကွက်ပါက၊ လှိမ့်သောကောင်တာသည် အရေအတွက်နည်းပါးသည်။ ပံ့ပိုးပေးသူထံမှ ပြည့်ဝသောအချက်ပြမှု (ဥပမာ `anthropic-ratelimit-unified-5h-utilization`) သည် လာမည့်တောင်းဆိုမှုတွင် ကမ္ဘာလုံးဆိုင်ရာ ခန့်မှန်းချက်ကို မှန်ကန်စေသည်။

### ပေါင်းစပ်အပျော့စား ပြစ်ဒဏ် (`open-sse/services/combo.ts`)

`decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

အခြားအမှတ်ပေးအချက်များအားလုံးပြီးနောက် ပင်နယ်တီကို သက်ရောက်သည်။ ၎င်းသည် ခက်ခက်ခဲခဲပိတ်ဆို့ခြင်းမရှိဘဲ saturated key ကိုရွေးချယ်ခြင်း၏ အလိုအလျောက်ပေါင်းစပ်နိုင်ခြေကို လျှော့ချပေးသည်။

pool wizard ၏သော့အဆင့်တွင် `Show usage by member to key holders` box တစ်ခုရှိသည်။ ၎င်းသည် pool ၏ `memberBreakdown` ရွေးချယ်မှုကို သတ်မှတ်ပေးသည် ( [အဖွဲ့ဝင်အသုံးပြုမှုကို](#member-usage) ကြည့်ပါ)။ ၎င်းအောက်တွင် အသုံးပြုထားသော သော့တစ်ခုသည် ဘားတစ်ခုအား ထိုသော့နှင့် ကိုက်ညီနိုင်သည်ကို သိရှိသူတစ်ဦးမှ သတိပေးသည်။ အကွက်ကို အမှတ်ခြစ်ထားခြင်းဖြင့်၊ အဆင့်သည် သော့သုံးခုထက်နည်းသော သို့မဟုတ် 20 ထက်နည်းသောစာရင်းများကို ဖော်ပြသည့်အခါ၊ ဘားများကို ဝှက်ထားသကဲ့သို့ ဖြစ်နေသည်။ ၎င်းသည် ခြေလှမ်းရှိ သော့များကို ရေတွက်ပြီး ၎င်းတို့ထဲမှ မည်သည့်တောင်းဆိုမှုများကို ပြုလုပ်နိုင်သည်ကို မပြောနိုင်ပါ။

### `/dashboard/costs/quota-share/plans` — ဝန်ဆောင်မှုပေးသူ အစီအစဉ် config

## Self-Service Quota API (ရွေးချယ်မှု)

`GET /api/v1/me/quota/{provider}` ( `/v1/me/quota/{provider}` တွင်လည်း ဝန်ဆောင်မှုပေးသည်) သည် API သော့ကိုင်ဆောင်သူတစ်ဦးအား ၎င်းတို့၏ကိုယ်ပိုင်သော့၊ မျှဝေထားသော စာရင်းသွင်းမှုပမာဏကို ၎င်းတို့၏ မည်မျှနှင့် ၎င်းတို့ကို ပိတ်ဆို့ထားသည်ကို ဖတ်နိုင်စေပါသည်။ လမ်းကြောင်းသည် `src/server/selfService/quotaHandler.ts` အပေါ်မှ ပါးလွှာသော အခွံတစ်ခုဖြစ်သည်။ မြင်ကွင်းကို `src/lib/quota/selfView.ts` ဖြင့်တည်ဆောက်ထားပြီး ၎င်း၏တုံ့ပြန်မှုစာချုပ်မှာ `src/shared/schemas/selfQuota.ts` (`SelfQuotaView` in `docs/openapi.yaml`) ဖြစ်သည်။

### ဖွင့်ခြင်းနှင့် စစ်မှန်ကြောင်းအထောက်အထားပြခြင်း။

- အင်္ဂါရပ်အလံ `QUOTA_SELF_PANEL`၊ မူရင်း `false`။ ပိတ်ထားစဉ်တွင်၊ လမ်းကြောင်းသို့ရောက်ရှိသော တောင်းဆိုချက်သည် 404 ကိုရရှိမည်ဖြစ်သည်။ `REQUIRE_API_KEY=true` ဖြင့်၊ client API မူဝါဒသည် လမ်းကြောင်းမလည်ပတ်မီ 401 နှင့် လွဲမှားနေသောသော့ကို ငြင်းဆိုသည်။ သော့မပါရှိဘဲ တောင်းဆိုချက်တစ်ခုသည် လက်မှတ်ထိုးဝင်ထားသည့် ဒက်ရှ်ဘုတ်ဆက်ရှင်သည် ထိုမူဝါဒကို ဖြတ်သန်းပြီး လမ်းကြောင်း၏ ကိုယ်ပိုင်အဖြေကို ရရှိသည်။ အလံသည် အခြားအလံတိုင်းကဲ့သို့ ဖြေရှင်းသည် (ဒက်ရှ်ဘုတ် သို့မဟုတ် REST တွင် ထပ်ရေးသည်၊ ထို့နောက် အမည်တူ၏ ပတ်၀န်းကျင်ကို ပြောင်းလဲနိုင်သော) [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md) ကြည့်ပါ။
- ရေကူးကန်တစ်ခုစီ၏ ဖော်ပြမှုအမည်နှင့် အချိန်ဇယားတစ်ခုစီ၏ အညွှန်းကို အက်ဒမင်က ၎င်းတို့ရေးထားသည့်အတိုင်း အတိအကျရေကူးကန်၏ သော့ကိုင်ဆောင်သူများထံ ပြန်ပေးသည်။ အလံကိုမဖွင့်မီ၊ ထိုသော့ကိုင်ဆောင်ထားသူများ ဖတ်ရန် သင့်လျော်မှုရှိမရှိ စစ်ဆေးပါ။
- သော့ကို ခေါင်းစီးများသာ ဖတ်သည်- `Authorization: Bearer <key>` သို့မဟုတ် `x-api-key: <key>`။ နှစ်ခုလုံးကို ပို့သောအခါ၊ တရားဝင်အောင်ပြုလုပ်သော ပထမတစ်ခုကို အသုံးပြုသည်။ စုံစမ်းရေးစာကြောင်းရှိ သော့တစ်ခု သို့မဟုတ် ကွက်ကီးတစ်ခုကို လျစ်လျူရှုထားသည်။ ဆာဗာ၏ ပတ်ဝန်းကျင်သော့သည် (401) ကို ငြင်းဆိုထားသည်။
- သော့သည် `self:usage` နယ်ပယ် (၎င်းမပါဘဲ 403) လိုအပ်သည်။
- ဝန်ဆောင်မှုပေးသည့်အပိုင်းကို ဖြတ်ညှပ်ကပ်၊ အသေးအသေးဖြင့် စစ်ဆေးပြီး `^[a-z0-9][a-z0-9._-]{0,63}$` (400 မဟုတ်ရင်) ကို စစ်ဆေးပြီးနောက် ဝန်ဆောင်မှုပေးသူ မှတ်ပုံတင်ခြင်းမှတစ်ဆင့် ဖြေရှင်းလိုက်သည်၊ ထို့ကြောင့် `cc` ကဲ့သို့သော alias သည် `claude` pools များကို ဖတ်သည်။ `claude` နှင့် `anthropic` တူညီသော ရေကန်များကို ဖတ်သည်။

### မြင်နိုင်စွမ်းတစ်ခုစီက ဘာကိုပြသလဲ။

| မြင်နိုင်စွမ်း  | လိုအပ်ပါသည်။                                                                         | လယ်ကွင်းများ                                                                                                                                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ကိုယ်ပိုင် ရှယ် | `self:usage`                                                                         | `pools[]` (ကိုးကား၊ အမည်၊ ဝန်ဆောင်မှုပေးသူ၊ မူဝါဒ၊ အလေးချိန်၊ ဦးထုပ်)၊ `dimensions[].yourShare`၊ `yourShare` နှင့် `accounts[]` ( `attributed` နှင့် `external` မပါရှိသော `percent` ဝင်းဒိုးတွင်) `blocks`, `availableModels`, `expiresAt`, `apiBaseUrl`                                                      |

- `sharedQuotaProviders` သည် per-key ဆက်တင်တစ်ခု (`PUT /api/keys/[id]/self-service`) : `null`၊ ပုံသေသည် သော့ရောက်သည့်ဝန်ဆောင်မှုပေးသူတိုင်းကို ဆိုလိုသည်။ `[]` သည် အဓိပ္ပါယ်မရှိပါ။ ရေကူးကန်တစ်ခုစီ၏ `accountVisible` ၎င်းနှင့်သက်ဆိုင်သည့် မြင်နိုင်စွမ်းကို ပြောပြသည်။
- အကောင့်ဘားများနှင့် မော်ဒယ်ဝင်းဒိုးများကို သော့ချိတ်ဆက်မှု အသုံးပြုနိုင်သော အကောင့်များအတွက်သာ ပြသထားသည်။ သော့တွင် ခွင့်ပြုထားသောချိတ်ဆက်မှုများစာရင်းရှိသောအခါ၊ ပြင်ပအကောင့်တစ်ခုသည် `account` သို့မဟုတ် `modelWindows` မပါဘဲ ၎င်း၏ `Account N` ဝင်ရောက်မှုကို သိမ်းဆည်းထားသည်။ အလွတ်စာရင်းသည် `/v1/me/status` ကဲ့သို့ ကန့်သတ်ချက်မရှိဟု ဆိုလိုသည်။ ရေကူးကန် စုစုပေါင်း (`dimensions[].total`) သည် ထိုစာရင်းပေါ်တွင် မမူတည်ပါ။
- `self:usage` တစ်ခုတည်းဖြင့် ပြထားသည့် ကိန်းဂဏန်းနှစ်ခုသည် အခြားသော့အသုံးပြုမှုမှ ဆင်းသက်လာသည်။ အချိန်ဇယားဘတ်ဂျက်၏ `exhausted` ထိုအချိန်ဇယားအောက်ရှိ သော့တိုင်း၏သုံးစွဲမှုကို ထင်ဟပ်စေသည်။ အလေးချိန်အားလုံး သုညရှိသော ရေကန်တစ်ခုတွင် သော့၏ `weight` သည် `100 / number of members` ဖြစ်သည်။ နှစ်ခုစလုံးသည် အဓိကအကျဆုံးဖြစ်သည့် ပြဋ္ဌာန်းချက်ဖြစ်သည်။
- ရေကူးကန်ကို `ref` ဖြင့်သာ ခွဲခြားသတ်မှတ်သည်၊ ခေါ်ဆိုမှုသော့နှင့် တွဲထားသော အလင်းရောင်တန်ဖိုး။ အက်ဒမင်က ၎င်းကို ရေးသားထားသည့်အတိုင်း ၎င်း၏ ဖော်ပြအမည် (`name`) ပါဝင်သည်။ `ref` သည် သော့နှင့် ဆာဗာ၏ API သော့လျှို့ဝှက်ချက် (`API_KEY_SECRET`) တို့မှ ဆင်းသက်လာသည်။ ဖောက်သည်များက ၎င်းကို စွဲမြဲစွာမထားရပါ။ ၎င်းလျှို့ဝှက်ချက်ကို လှည့်ပတ်ပါက ပြောင်းလဲပါသည်။
- အကောင့်များကို `Account 1`, `Account 2`, … အစုအဝေးတွင် စာရင်းသွင်းထားသည်။ ရေကူးကန်အိုင်ဒီ၊ ချိတ်ဆက်မှုအိုင်ဒီ၊ အကောင့်အီးမေးလ် သို့မဟုတ် အကောင့်အမည်ကို ပြန်မပေးဘဲ၊ တုံ့ပြန်ချက်သည် ၎င်းအပြင်ဘက်ရှိ မည်သည့်အကွက်ကိုမဆို ချပေးသည့် စာချုပ်ပုံစံစနစ်မှတစ်ဆင့် ရောက်သွားပါသည်။
- Countable units (`requests`, `tokens`, `usd`) are reported as the pool bucket the quota gate enforces: `limit` = plan limit × accounts in the pool, `fairShare` = weight / 100 × `limit` (equal split when every weight is 0), `consumed` = the key's own counter in the quota store, `remaining` = `fairShare` − `consumed`, floored at 0.
- `blocks.schedules` သည် သော့၏အချိန်ဇယား windows (`open`/`closed`, `blackout` သို့မဟုတ် `outside-window`, `retryAfterSeconds`, reserve floors နှင့် window's budget ကိုသုံးစွဲသည်ဖြစ်စေ၊ `blocks.modelCaps` သည် ၎င်း၏ မော်ဒယ်အလိုက် နာရီအလိုက် ဦးထုပ်များကို စားသုံးမှုဖြင့် စာရင်းပြုစုထားသည်။
- ဝန်ဆောင်မှုပေးသူ၏ ရေကန်တိုင်းအပြင်ဘက်တွင် သော့တစ်ခု `pools: []` နှင့် 200 ရရှိသည်။ `availableModels` ( `/v1/models` တွင်မြင်ရသောသော့ `qtSd/` ids ) ၊ `expiresAt` နှင့် `apiBaseUrl` ဖြည့်ဆဲဖြစ်သည်။
- `apiBaseUrl` သည် `OMNIROUTE_PUBLIC_API_BASE_URL`၊ ထို့နောက် `OMNIROUTE_PUBLIC_BASE_URL`၊ အခြား `null` ဖြစ်သည်။ တောင်းဆိုမှုရဲ့ မူလဇာစ်မြစ်က ဘယ်တော့မှ မဟုတ်ပါဘူး။

### ချေးငွေသဘောတူညီချက်

`PATCH /api/v1/me/quota/{provider}` ရေကန်တစ်ခုအတွက် ခေါ်ဆိုမှုသော့၏ကိုယ်ပိုင်သဘောတူညီချက်ကို မှတ်တမ်းတင်သည်။ ၎င်းသည် `GET`၏အလံ၊ ခေါင်းစီးများနှင့် ဝန်ဆောင်မှုပေးသူစည်းမျဉ်းများကို အသုံးပြုသည်။ `self:usage` နယ်ပယ်သည် ၎င်း၏အမည်ကို ဖတ်ရန်သာအဖြစ်ဖတ်သော်လည်း၊ ဤတစ်ခုရေးရန်ခွင့်ပြုသည်။

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` သည် `ref` ဖြစ်ပြီး `GET` ထိုရေကန်အတွက် ပြန်ပေးသည်။
- `lendingPercent` သည် 0 မှ 100 မှ ကိန်းပြည့်တစ်ခုဖြစ်သည်။ 0 တန်ဖိုးသည် သဘောတူညီမှုနှင့် ၎င်း၏နောက်ဆုံးရက်ကို ရှင်းလင်းသည်။ `lendingPercent` 0 ပါသော ကိုယ်ထည်ကို မုဒ်နှစ်ခုလုံးတွင် လက်ခံသည်။
- `lendingUntil` သည် ရွေးချယ်နိုင်သည်- epoch milliseconds သို့မဟုတ် နောက်ဆုံးရက်အတွက် `null` ။ ၎င်းသည် အနာဂတ်တွင်ဖြစ်ပြီး အများဆုံး 8640000000000000 ဖြစ်ရပါမည်။ 100000000000 အောက်တန်ဖိုးသည် စက္ကန့်အဖြစ်ဖတ်ပြီး ငြင်းဆိုထားသည်။
- အခြားနယ်ပယ်တစ်ခုခုကို ငြင်းဆိုထားသည်။ 4096 bytes ထက် ပိုရှည်သော ကိုယ်ထည်ကို ငြင်းဆိုထားသည်။ စာဖတ်ခြင်းသည် ထိုအရွယ်တွင် ရပ်တန့်သွားသောကြောင့် တစ်ကိုယ်လုံး ပိုရှည်သည်ဟူ၍ မရှိပါ။

စစ်ဆေးမှုများသည် ဤဇယား၏ အစီအစဥ်အတိုင်း လုပ်ဆောင်သည်။ ငြင်းဆိုမှုတိုင်းသည် ပုံသေမက်ဆေ့ချ်ဖြင့် စံအမှားကိုယ်ထည်ကို အသုံးပြုသည်။ ဤချက်လက်မှတ်များအနက်မှ ငြင်းဆိုခြင်းသည် ဘာမှမရေးပါ။

သိမ်းဆည်းထားသော သဘောတူညီချက်ကို ပြောင်းလဲသည့် တောင်းဆိုချက်တစ်ခုသည် `quota.pool.lending.updated` စာရင်းစစ်မှတ်တမ်းတစ်ခုကို ရေးသားသည်။ ၎င်းသည် သော့ကို အဟောင်းနှင့် တန်ဖိုးအသစ်များဖြင့် အမည်ပေးသည်။ တူညီတဲ့ကိုယ်ထည်ကို နှစ်ကြိမ် ရေးပြီး တစ်ကြိမ် စစ်ဆေးတယ်။ အဖြေသည် 200 ကိုရေးပြီးနောက်တည်ဆောက်ထားသော `GET` မြင်ကွင်းအပြည့်ဖြစ်သည်။

`GET` အောက်ပါအတိုင်း ချေးငွေထုတ်ချေးခြင်း အစီရင်ခံစာကို ကြည့်ရှုသည်-

- ရေကူးကန်တစ်ခုစီသည် `borrowMode` (`saturation` သို့မဟုတ် `consent`) ပါရှိပြီး သော့၏ကိုယ်ပိုင် `lendingPercent` နှင့် `lendingUntil` ပါဝင်သည်။
- `lendingActive` သည် `true` တွင်သာ `consent` pool တွင်သာဖြစ်ပြီး 0 အထက်ရာခိုင်နှုန်းရှိပြီး နောက်ဆုံးရက်ကို မရောက်ပါ။
- `consent` ရေကန်တွင်၊ ရေတွက်နိုင်သော `dimensions[].yourShare` တစ်ခုစီသည် `borrowAvailable` ကို သယ်ဆောင်သည်။ ၎င်းသည် အခြားသော့များမှ ထုတ်ချေးထားသော ၎င်း၏ရှယ်ယာအထက်တွင် ယခုအသုံးပြုနိုင်သည့် သော့ဖြစ်သည်။
- `borrowAvailable` ဂိတ်၏ဖော်မြူလာကို အသုံးပြုသည်။ သော့သည် ၎င်း၏မျှဝေမှုအောက်တွင်ရှိသော်လည်း အခြားသော့တိုင်းကိုလည်း ဖတ်သည်။ အခြားသော့တစ်ခုနှင့် countable dimension တစ်ခုလျှင် အပိုတစ်ခုဖတ်နိုင်သော `hard` သော့တစ်ခုအတွက်၊ အပြိုင်ဖြစ်သည်။
- `borrowAvailable` သည် `soft` သို့မဟုတ် `burst` သော့တစ်ခုအတွက် `null` ဖြစ်ပြီး ဖတ်မရသောအခါ `null` ဖြစ်သည်။
- `borrowAvailable` သည် အခြားသော့များအားလုံးအတွက် ပုံတစ်ပုံဖြစ်သည်။ သော့နှစ်လုံးပါသော ရေကန်တစ်ခုတွင် ၎င်းသည် အခြားသော့၏ကိုယ်ပိုင်ပုံဖြစ်သည်။
- `borrowAvailable` `percent` windows အတွက် သို့မဟုတ် `accounts[]` တွင် အစီရင်ခံခြင်းမရှိသေးပါ။
- `saturation` ရေကူးကန်တွင် မြင်ကွင်းသည် `lendingActive: false` နှင့် `borrowAvailable` မရှိသော သိမ်းဆည်းထားသော သဘောတူညီချက်ကို အစီရင်ခံသည်။

### အဆင်ပြေကြပါစေ

Every response of this route, success or error, carries `Cache-Control: no-store`. A refusal that happens before the route runs does not carry it, for example the client API policy's 401 or the IP filter's 403. Errors of the route use the standard error body with a fixed message: 400 (invalid provider), 401 (missing or invalid key), 403 (missing `self:usage`), 404 (flag off) and 500 (`Failed to build quota view`). The 500 covers any failure once the request reaches the route, including the key lookup itself; its cause is logged on the server and never returned. The errors of the `PATCH` are listed in [Lending consent](#lending-consent).

### ကန့်သတ်ချက်များ

- `remaining` သည် အသုံးမပြုရသေးသော သော့၏မျှတသောမျှဝေမှု၏ အစိတ်အပိုင်းဖြစ်သည်။ အာမခံချက် မဟုတ်ပါ။ ရေကူးကန်တွင် နေရာလွတ်ရှိသော်လည်း သော့ကို ၎င်းထက်ကျော်လွန်၍ ဆောင်ရွက်ပေးနိုင်ပါသေးသည်။ pool ၏စုစုပေါင်း `limit` သို့ရောက်သည်နှင့်၊ pool ၏သော့တိုင်း၊ ၎င်း၏ကိုယ်ပိုင် `remaining` မှန်သမျှကို ငြင်းပယ်ပြီး `self:account-quota` မရှိသောသော့သည် ထိုစုစုပေါင်းကို မမြင်နိုင်ပါ။
- `remaining` ခွဲဝေမှု၏ အကြွင်းမဲ့ `cap` ထည့်သွင်းစဉ်းစားခြင်းမရှိပါ။ ဦးထုပ်၏ယူနစ်ပြတင်းပေါက်တွင် ၎င်း၏ကိုယ်ပိုင်သုံးစွဲမှုသည် ဦးထုပ်၏တန်ဖိုးသို့ရောက်သည်နှင့်တစ်ပြိုင်နက် အာဏာတည်မြဲရေးသည် သော့ကို ငြင်းပယ်သည်။
- အကောင့်အဆင့်ဘားသည် ဝန်ဆောင်မှုပေးသူကန့်သတ်ထားသော ကက်ရှ်မှ ဆင်းသက်လာပြီး ပြဋ္ဌာန်းသည့်ဆုံးဖြတ်ချက်ကို မိနစ်အနည်းငယ်ကြာအောင် နောက်ကျစေနိုင်သည်။ ပြန်လည်သတ်မှတ်ချိန်လွန်သွားသော စာဖတ်ခြင်းကို `stale` အဖြစ် အစီရင်ခံပါသည်။
- မော်ဒယ်အလိုက် ပြတင်းပေါက်များ (`modelWindows`) ကို အစီအစဉ်-ဝင်းဒိုးမြေပုံရေးဆွဲသည့် ဝန်ဆောင်မှုပေးသူများအတွက်သာ အစီရင်ခံသည်- ယနေ့တွင် Claude နှင့် Codex ။ အခြားဝန်ဆောင်မှုပေးသူများအတွက် `modelWindows` သည် `windows` စာရင်းအလွတ်တစ်ခုဖြင့် အကောင့်ဒေတာကိုပြသသောအခါတွင် ရှိနေသေးသည်။
- `percent` window တစ်ခု၏ သော့၏ကိုယ်ပိုင်ဝေစုသည် ခန့်မှန်းချက်တစ်ခုဖြစ်သည်။ ၎င်းသည် ရည်ညွှန်းချက်စာအုပ်မှ ဆင်းသက်လာပြီး အထက်ဖော်ပြပါ "ရာခိုင်နှုန်းအတိုင်းအတာများ- သော့ထည့်တွက်ခြင်း" အောက်တွင် ဖော်ပြထားသော ကန့်သတ်ချက်တိုင်းကို ထည့်သွင်းထားသည်။
- `consumed` သည် တရားမျှတသော ရှယ်ယာနှင့် နှိုင်းယှဉ်ထားသော ကိန်းဂဏန်းများ စိုးမိုးရေးဖြစ်သည်။ `attributed` အပေါင်း `external`၊ အတိအကျ။ `attributed` သည် ၎င်းကို ဖြတ်သွားသော တိုကင်များအတွက် သော့ပေးသော အပိုင်းဖြစ်သည်။ `external` သည် pool ၏သော့များမပါဝင်သည့်အကောင့်အသုံးပြုမှု၏သော့အစိတ်အပိုင်းဖြစ်သည်။
- pool ၏ `accountVisible` မှန်မှသာ အစိတ်အပိုင်းနှစ်ခုလုံးကို ပေးပို့သည်- သော့မှာ `self:account-quota` ရှိပြီး ပံ့ပိုးသူသည် ၎င်း၏ `sharedQuotaProviders` တွင် ရှိနေသည်။ ၎င်းမပါသောသော့သည် `consumed` တစ်ခုတည်း၊ `status` နှင့် `reason` အတူတူဖြစ်သည်။
- အစိတ်အပိုင်းနှစ်ခုလုံးနှင့် ၎င်း၏ကိုယ်ပိုင်အလေးချိန်ဖြင့်၊ ကိုင်ဆောင်ထားသူသည် ရေကူးကန်၏သော့များကို အားသွင်းထားသည့် ရေကူးကန်အပြင်ဘက်တွင် ပြုလုပ်ထားသည့် အသုံးပြုမှုကို အကောင်အထည်ဖော်နိုင်သည်။ အကောင့်နယ်ပယ်ရှိ ကိုင်ဆောင်ထားသူသည် အကောင့်စုစုပေါင်းကို မြင်ပြီးဖြစ်သည်။
- ဝင်းဒိုးတွင် မည်သည့်အရာကိုမျှ လမ်းကြောင်းလွဲသွားသော သော့သည် ၎င်း၏ ပြင်ပအားသွင်းမှုကို `consumed` မှ ဖတ်နိုင်ဆဲဖြစ်သည်၊ ၎င်း၏ ရည်ညွှန်းချက်မှာ 0 ဖြစ်သောကြောင့် ဖြစ်သည်။
- ဥပမာအားဖြင့်၊ စာအုပ်တစ်အုပ်ကို 0 တွင်ဖွင့်ပြီး သော့များ A နှင့် B တစ်ခုစီကိုအလေးချိန် 50 ဖြင့်ဖွင့်သည်။ ကီး A သည် တိုကင် 900,000 နှင့် သော့ B 100,000 ကို လမ်းကြောင်းပေးသည်။ ထို့နောက် အကောင့်သည် ကန့်သတ်ချက် 100 ၏ 60% သို့ ရောက်ရှိသွားသည်။ ထို့နောက် `attributed` သည် သော့ A အတွက် 54 နှင့် သော့ B အတွက် 6 ဖြစ်ပြီး `external` နှစ်ခုလုံးအတွက် 0 ဖြစ်သည်။
- မြင်ကွင်းက စာအုပ်ကိုဖတ်ပြီး သူ့အခြေအနေကို ဘယ်တော့မှ မရေးဘူး။ ၎င်းသည် စာအုပ်တစ်အုပ်ကို မဖွင့်ဘဲ စာဖတ်ရန် ပံ့ပိုးသူကို ဘယ်သောအခါမှ မတောင်းဆိုပါ။ Redis စတိုးဖြင့်၊ ဂိတ်၏ဖတ်ပြသည့်အတိုင်း နောက်ခံတွင် အစားထိုးထားသော ပြန်လည်ပြင်ဆင်မှုအကွက်များကို ဖတ်ရှုခြင်းဖြင့် ဖယ်ရှားသည်။
- ဂိတ်၏ ကက်ရှ်တွင် အကောင့်ကို ဖတ်နေချိန်တွင်သာ မျှဝေမှုသည် `ok` ဖြစ်သည်။ တစ်ခုမှမရှိလျှင် `stale` ဖြစ်သည်၊ ထို့ကြောင့် မကြာသေးမီက တောင်းဆိုချက်မရှိသော ရေကန်တစ်ခုတွင် ၎င်းသည် ခေတ်နောက်ကျနေနိုင်သည်ဟု ဖော်ပြသည်။
- တောင်းဆိုမှုတစ်ခုသည် ရေကူးကန်မှတစ်ဆင့် မျှဝေမှု မရရှိနိုင်ပါ။ ထိုတောင်းဆိုချက်သည် စာအုပ်ကိုဖွင့်ပြီး ထိုအချိန်တွင် အကောင့်၏ကိန်းဂဏန်းသည် ရေကန်အပြင်ဘက်တွင် ပြုလုပ်ထားသည့် အသုံးပြုမှုအဖြစ် ရေတွက်သည်။
- အကောင့်များစွာပါသော အစုအဝေးတစ်ခုတွင်၊ အကောင့်ဝင်ရောက်မှုတစ်ခုစီသည် ထိုအကောင့်၏ကိုယ်ပိုင်စာအုပ်နှင့် အကောင့်တစ်ခု၏ ကန့်သတ်ချက်ကို အသုံးပြုသည်။ အကောင့်အရေအတွက်ဖြင့် နှစ်ဖက်စလုံးကို အတိုင်းအတာဖြင့် တိုင်းတာထားသောကြောင့် အချိုးအစားမှာ တူညီပါသည်။
- မော်ဒယ်အလိုက် windows များသည် သော့အတွက် မျှဝေခြင်းမရှိပါ။ စာအုပ်သည် မော်ဒယ်အလိုက် အချက်အလက်ကို မသိမ်းဆည်းပါ။
- အချိန်ဇယားတစ်ခု၏ အရန်ကြမ်းပြင်များကို ကြည့်ရှုခြင်းဖြင့် အကဲဖြတ်မည်မဟုတ်ပါ- တောင်းဆိုမှုကို `schedule-reserve` ဖြင့် ငြင်းဆိုထားချိန်တွင် အချိန်ဇယားတစ်ခုသည် `open` အဖြစ် ပြနိုင်သည် ။
- တူညီသောသော့နှစ်ခု၏ ချိတ်ဆက်မှုတစ်ခုကို မျှဝေသောအခါ၊ ပြဋ္ဌာန်းချက်သည် ၎င်းတို့ထဲမှ တစ်ခုကို သက်ရောက်မှုရှိပြီး ကြည့်ရှုမှုစာရင်းနှစ်ခုစလုံးကို ဖော်ပြသည်။
- မအောင်မြင်သောသော့ကြိုးပမ်းမှုများအတွက် လိပ်စာကန့်သတ်ချက်မရှိပါ- ပြောင်းပြန်ပရောက်စီခေါ်ဆိုသူများသည် လိပ်စာတစ်ခုမျှဝေနိုင်သည် (၎င်းသည် ထပ်ဆင့်ပေးပို့ထားသောဖောက်သည်လိပ်စာများကို ယုံကြည်ခြင်းရှိမရှိအပေါ် မူတည်သည်) ထို့ကြောင့် လော့ခ်ချခြင်းသည် သော့ကိုင်ဆောင်သူတိုင်းအတွက် လမ်းကြောင်းကို ငြင်းပယ်နိုင်သည်။ `REQUIRE_API_KEY=true` ဖြင့်၊ လမ်းကြောင်းမလည်ပတ်မီ ကလိုင်းယင့် API မူဝါဒက မမှန်ကန်သောသော့ကို ငြင်းဆိုသည်၊ ထိုမူဝါဒ၏ 401 ကိုယ်ထည်သည် ဤလမ်းကြောင်း၏အစား၊

### အဖွဲ့ဝင်အသုံးပြုမှု

စီမံခန့်ခွဲသူတစ်ဦးသည် ကီးကိုင်ဆောင်သူများကို ဝင်းဒိုးတစ်ခု၏အသုံးပြုမှုကို ရေကူးကန်အဖွဲ့ဝင်များကြားတွင် မည်သို့ခွဲထားသည်ကို မြင်နိုင်စေပါသည်။ ရွေးချယ်ခွင့်သည် ပုံမှန်အားဖြင့် pool's `memberBreakdown` ဖြစ်သည် ။ ၎င်းကို pool wizard သို့မဟုတ် `PATCH /api/quota/pools/{id}` ဖြင့်သတ်မှတ်ထားသည်။ `GET /api/quota/pools` နှင့် `GET /api/quota/pools/{id}` သတင်းပို့ပါ။

ဤအရာအားလုံးကို ထိန်းထားသည့်အခါမှသာ မြင်ကွင်း၏အတိုင်းအတာတစ်ခုသည် `members` ကို သယ်ဆောင်သည်-

- ရေကူးကန်၏ ရွေးချယ်ခွင့်ကို ဖွင့်ထားသည်။
- ရေကူးကန်တွင် အများဆုံးခွဲဝေချထားပေးသည့်သော့ 20 ခုရှိပြီး ၎င်းတို့ထဲမှ အနည်းဆုံး 3 ခုသည် တောင်းဆိုမှုများပြုလုပ်နိုင်သည်- အသက်ဝင်သည်၊ ရုတ်သိမ်းမခံရ၊ တားမြစ်မထားသည့်အပြင် ၎င်းတို့၏ သက်တမ်းကုန်ဆုံးရက်ကို မကျော်လွန်နိုင်ပါ။
- pool ၏ `accountVisible` အမှန်ဖြစ်သည်- သော့တွင် `self:account-quota` ရှိပြီး ပံ့ပိုးသူသည် ၎င်း၏ `sharedQuotaProviders` တွင်ရှိသည်။
- `percent` ဝင်းဒိုးတွင်၊ အကောင့်၏ချိတ်ဆက်မှုသည် အသုံးပြုနိုင်သည့်သော့တစ်ခုဖြစ်သည်။
- ထိုဝင်းဒိုး၏ သော့ဝေစုကို ဖတ်ရသည်- ၎င်း၏ `status` သည် `unavailable` မဟုတ်ပါ။

မဟုတ်ရင် `members` မရှိတော့ပါ။ ဘယ်တော့မှ အလွတ်စာရင်းမဟုတ်ဘူး။

- အချပ်တစ်ခုစီသည် `{ slot, consumed, isYou }` ဖြစ်သည်။ တုံ့ပြန်မှုအစီအစဉ်သည် အစိပ်အပိုင်းတစ်ခုပေါ်ရှိ အခြားပိုင်ဆိုင်မှုများနှင့် အချပ် 20 ကျော်စာရင်းကို ငြင်းပယ်သည်။ အချပ်များကို အထိုင်အစီအစဥ်တွင် ဖော်ပြထားပါသည်။
- တောင်းဆိုမှုများပြုလုပ်၍မရတော့သောသော့အပါအဝင် ခွဲဝေပေးထားသောသော့တစ်ခုလျှင် တစ်ချပ် ရှိပါသည်။ အသုံးမဝင်သော အဖွဲ့ဝင်သည် အစစ်အမှန် သုညကို ပြသည်။
- အပေါက် 1 သည် `isYou` true ဖြင့် အမြဲမေးနေသော သော့ဖြစ်သည်။ အခြား slot နံပါတ်များသည် keyed hash ၏အဆင့်များဖြစ်သည်။ ၎င်းကို `API_KEY_SECRET` ဖြင့် သော့ခတ်ထားပြီး ရေကူးကန်၊ မေးသော့နှင့် အဖွဲ့ဝင်ကို ဖုံးအုပ်ထားသည်။
- ထို့ကြောင့် နံပါတ်များသည် ကိုင်ဆောင်သူများကြားတွင် မညီပါ။ ကိုင်ဆောင်ထားသူ တစ်ဦးအတွက် လည်ပတ်မှုကြားတွင် တူညီကြသည်။ သော့တစ်ခုသည် ရေကန်ထဲသို့ ထွက်သွားသည့်အခါ သို့မဟုတ် လျှို့ဝှက်လှည့်သွားသည့်အခါတွင် ၎င်းတို့သည် ပြောင်းလဲနိုင်သည်။
- ရေတွက်နိုင်သောဝင်းဒိုးတစ်ခုတွင် အစိပ်အပိုင်းသည် ၎င်း၏ကိုယ်ပိုင် `consumed` နှင့် တူညီသောကောင်တာခွဲတမ်းစတိုးရှိ အဖွဲ့ဝင်၏ကောင်တာဖြစ်သည်။
- `percent` ဝင်းဒိုးတွင် အစိပ်အပိုင်းသည် သော့၏ကိုယ်ပိုင်မျှဝေမှုအဖြစ် ဖတ်ထားသည့် စာအုပ်တစ်ခုတည်းမှ အဖွဲ့ဝင်၏ `attributed` အပိုင်းဖြစ်သည်။ ရေကူးကန်အပြင်ဘက်တွင် ပြုလုပ်ထားသည့် အသုံးပြုမှုကို ဘယ်တော့မှ အချပ်မခွဲပါ။ ထိုအားသွင်းမှုကို အလေးချိန်ဖြင့် ပိုင်းခြားထားသောကြောင့် ၎င်းကိုသယ်ဆောင်သော အချပ်များသည် အလေးများကို ပြသမည်ဖြစ်သည်။
- ကြည့်ရှုမှုတစ်ခုစီသည် အခြားအဖွဲ့ဝင်တစ်ဦးနှင့် ရေတွက်နိုင်သောဝင်းဒိုးတစ်ခုစီကို အပြိုင်ဖတ်သည်။ `percent` ပြတင်းပေါက်တစ်ခုတွင် အချပ်များသည် မျှဝေသူ၏ကိုယ်ပိုင်စာအုပ်ကို ကျော်လွန်၍ မဖတ်ရပါ။ တန်ဖိုးတစ်ခုအား ဖတ်၍မရသောအခါ၊ ထိုဝင်းဒိုးတွင် `members` မရှိတော့ဘဲ သော့၏ကိုယ်ပိုင်မျှဝေမှုသည် ဆက်ရှိနေမည်ဖြစ်သည်။
- ရွေးချယ်ခွင့်နှင့် အသုံးပြုနိုင်သော သော့အရေအတွက်ကို အစုတစ်ခုလျှင် တစ်ကြိမ်ဖတ်ပြီး အကောင့်ဒေတာကို မြင်နိုင်သည့် သော့တစ်ခုအတွက်သာ ဖြစ်သည်။ ရွေးချယ်စရာ သို့မဟုတ် အသုံးပြုနိုင်သော သော့အရေအတွက်ကို ဖတ်ရှု၍မရပါက ထိုရေကူးကန်အတွက် ဘားများကို ပိတ်ပစ်လိုက်သည်။ ဆာဗာသည် သတိပေးချက်တစ်ခုကို မှတ်တမ်းတင်ထားပြီး ကျန်မြင်ကွင်းကို တည်ဆောက်ထားသည်။

အရက်ဆိုင်များတွင် နာမည် သို့မဟုတ် ID မပါရှိပါ။ ၎င်းတို့သည် အခြားအဖွဲ့ဝင်များအကြောင်း သော့ကိုင်ထားသူအား ပြောပြဆဲဖြစ်သည်။

- ကိုင်ဆောင်သူများသည် ၎င်းတို့၏တန်ဖိုးများဖြင့် အချပ်များကို ယှဉ်နိုင်သေးသည်။
- တည်ငြိမ်သောနံပါတ်သတ်မှတ်ခြင်းသည် ကိုင်ဆောင်ထားသူအား အဖွဲ့ဝင်တစ်ဦးကို အချိန်နှင့်အမျှ လိုက်နိုင်စေပါသည်။
- အချပ်အရေအတွက်သည် ရေကူးကန်တွင် သော့မည်မျှခွဲဝေထားသည်ကို ပြသသည်။
- သော့သုံးချောင်းပါသော ရေကန်တစ်ခုတွင် သော့တစ်ချောင်းက ဘာကိုအသုံးပြုထားသည်ကို သိရှိသူတစ်ဦးသည် နောက်ဆုံးသော့ကို အသုံးပြုထားသည်ကို ပြောပြနိုင်သည်။
- ရေကူးကန်တစ်ခုသည် အသုံးပြုနိုင်သော သော့သုံးခုအောက်တွင် ကျဆင်းသွားသောအခါ၊ ဘားများ ပျောက်သွားသည်။ အစောပိုင်းက ရိုက်ကူးခဲ့သော ကြည့်ရှုမှုများသည် အဖွဲ့ဝင်တစ်ဦးစီ အသုံးပြုခဲ့သည့်အရာကို ပြသနေဆဲဖြစ်သည်။
- ရေတွက်နိုင်သော ဝင်းဒိုးတစ်ခုတွင်၊ အစုအဝေးမှ ခွဲဝေမပေးတော့သော သော့များအသုံးပြုမှုကို ပြသနိုင်သည်။
- အကောင့်တစ်ခုတွင် သုညကိုပြသပြီး အခြားတစ်ခုတွင်အသုံးပြုသည့်အဖွဲ့ဝင်တစ်ဦးသည် မည်သည့်အဖွဲ့ဝင်က မည်သည့်အကောင့်ကိုအသုံးပြုသည်ကို ပြသနိုင်သည်။
- `hard` ပေါ်လစီပါရှိသော ရေတွက်နိုင်သောရေကန်တစ်ခုတွင်၊ အဖွဲ့ဝင်တစ်ဦး၏မျှတသောမျှဝေမှုတွင် ကြီးထွားမှုရပ်တန့်သွားသည့်အစိပ်အပိုင်းသည် ထိုအဖွဲ့ဝင်၏အလေးချိန်ကို အရိပ်အမြွက်ဖော်ပြသည်။

### အသုံးပြုမှုစီးရီး (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` ( `/v1/me/usage` တွင်လည်း ဆောင်ရွက်ပေးသည်) သည် ဖုန်းခေါ်ဆိုမှုသော့၏ ကိုယ်ပိုင်တောင်းဆိုမှုများ၏ အသုံးပြုမှုနှင့် ကုန်ကျစရိတ်ကို ပြန်ပေးသည်- စုစုပေါင်း၊ UTC တစ်ရက်လျှင် တစ်ကြိမ်၊ တစ်ရက်နှင့် မော်ဒယ်၊ မော်ဒယ်တစ်ခုနှင့် ဝန်ဆောင်မှုပေးသူတစ်ဦးစီ။ ၎င်းသည် အလံ၊ အထောက်အထားစိစစ်ခြင်းစည်းမျဉ်းများ၊ `self:usage` နယ်ပယ်၊ `Cache-Control: no-store` နှင့် အထက်ခွဲတမ်းလမ်းကြောင်း၏ အမှားအယွင်းများကို မျှဝေပါသည်။ သော့ကို `range` မတိုင်မီ စစ်ဆေးပါ။ အမှားများသည် 400 (`Invalid range`) ၊ 401 ၊ 403 ၊ 404 နှင့် 500 (`Failed to build usage`) ဖြစ်သည်။

- `range` သည် `1d`၊ `7d`၊ `30d` (မူလ) သို့မဟုတ် `90d` တို့မှ တစ်ခုဖြစ်သည်။ အခြားတန်ဖိုး၊ ဗလာတန်ဖိုး သို့မဟုတ် ထပ်ခါတလဲလဲ ကန့်သတ်ချက်တစ်ခုသည် 400 ဖြစ်သည်။ သတ်မှတ်မှုသည် ခေါ်ဆိုမှုတစ်ခု၏ကုန်ကျစရိတ်ကို ကန့်သတ်ရန် `90d` တွင် ရပ်သည်။ မြင်ကွင်းသည် သော့မပါသော နေ့စဉ်အကျဉ်းချုပ်များကိုသာ ဖတ်သည် ။
- ခေါ်ဆိုမှုကီး၏ ID ဖြင့် အတန်းများကို ရွေးချယ်ထားသည်။ သော့အမည်ကော်လံကို ဘယ်တော့မှ မတိုက်ဆိုင်ပါ၊ သော့ ID မပါဘဲ မှတ်တမ်းတင်ထားသော အတန်းများကို ဘယ်တော့မှ ရေတွက်မည်မဟုတ်ပါ။
- စီးရီးတစ်ခုတည်ဆောက်ခြင်းသည် ဝင်းဒိုးရှိ သော့တန်းများပေါ်တွင် အုပ်စုဖွဲ့ထားသော မေးခွန်းငါးခုကို လုပ်ဆောင်သည်။ တည်ဆောက်ထားသောစီးရီးကို သော့နှင့်အကွာအဝေးတစ်ခုလျှင် စက္ကန့် 60 ကြာ ပြန်သုံးထားပြီး ပြန်သုံးထားသောခေါ်ဆိုမှုတစ်ခုမှ လုပ်ဆောင်မည်မဟုတ်ပါ။ ၎င်း၏ `generatedAt` ၎င်း၏အသက်ကိုပေးသည်။
- စီးရီးတည်ဆောက်သည့်အခါ ပြတင်းပေါက်သည် ပြီးဆုံးသည်။ ဥပမာ နာရီ လှည့်၍ နောက်မှ ရိုက်သော အတန်းကို ရေတွက်မည်မဟုတ်ပါ။
- `coverage.retentionDays` သည် အော်ပရေတာ၏ ကုန်ကြမ်းအသုံးပြုမှု-မှတ်တမ်းထိန်းသိမ်းခြင်း ဆက်တင် (ဒေတာဘေ့စ်ဆက်တင်များတွင်`retention.usageHistory` ) ဖြစ်သည်။ တောင်းဆိုထားသော အပိုင်းအခြားသည် ထိုဆက်တင်ထက် ပိုရှည်သောအခါ `coverage.truncatedByRetention` သည် မှန်ပါသည်။ ၎င်းသည် နံပါတ်နှစ်ခုကို နှိုင်းယှဉ်ပြီး အတန်းများ အမှန်တကယ်ပျောက်ဆုံးနေခြင်းရှိမရှိ စစ်ဆေးပေးပါသည်။
- သော့၏ကိုယ်ပိုင်တောင်းဆိုမှုများကို မှတ်တမ်းတင်ထားသည့်အတိုင်း ဝန်ဆောင်မှုပေးသူကို ပြန်ပေးသည်။ မော်ဒယ်သည် ၎င်း၏နောက်ဆုံး `/` ပြီးနောက် မှတ်တမ်းတင်ထားသော အမည်ဖြစ်ပြီး အတန်းများကို ၎င်းဖြင့် အုပ်စုဖွဲ့ထားသည်။ ပစ်မှတ်တိုင်းကို ငြင်းဆိုခံရသည့် ပေါင်းစပ်တောင်းဆိုမှုတစ်ခုအား ပံ့ပိုးသူအဖြစ် လမ်းကြောင်းသတ်မှတ်တံဆိပ် (ပေါင်းစပ်အမည်၊ `auto` သို့မဟုတ် `combo`) နှင့် ကလိုင်းယင့်ပေးပို့သည့် မော်ဒယ်စာကြောင်းတို့ဖြင့် မှတ်တမ်းတင်ထားသည်။ အခြားသော ငြင်းဆိုမှုများ၊ ဥပမာအားဖြင့် အဖွင့် circuit breaker၊ model cooldown သို့မဟုတ် quota-parked skip၊ target provider နှင့် model ကို သိမ်းဆည်းပါ။
- အရေအတွက်နှင့် ကုန်ကျစရိတ်များအပြင်၊ တုံ့ပြန်မှုသည် ပျမ်းမျှကြာချိန်၊ အောင်မြင်မှုနှုန်းနှင့် ပထမနှင့် နောက်ဆုံးတောင်းဆိုမှု၏ အချိန်များကို သယ်ဆောင်ပေးပါသည်။
- `byModel` တောင်းဆိုမှုအများဆုံးဖြင့် ပံ့ပိုးသူနှင့် မော်ဒယ်အတွဲ 50 ကို စာရင်းပြုစုထားသည်။ နောက်ထပ်အတွဲများနှင့်အတူ ၎င်း၏ထည့်သွင်းမှုများကို `summary` အထိ ပေါင်းမထည့်ဘဲ `summary.uniqueModels` မှတ်တမ်းတင်ထားသော မော်ဒယ်စာလုံးပေါင်းတိုင်းကို ရေတွက်သည်။ `byModelTruncated` သည် အမှန်ဖြစ်ပြီး၊ ဖြတ်တောက်မှု၏ နှစ်ဖက်စလုံးတွင် အတွဲများကျနေသော မော်ဒယ်သည် တစ်စိတ်တစ်ပိုင်း စုစုပေါင်းကို ပြသသည်။
- ကုန်ကျစရိတ် နှစ်မျိုးရှိကြောင်း သိရသည်။ `costUsd` သည် အသုံးပြုမှုပိုင်းခြားစိတ်ဖြာချက်တွင်ပြသထားသည့်အတိုင်း ကောက်ခံထားသောကုန်ကျစရိတ်ဖြစ်သည်။ Claude ကုဒ်အစီအစဉ်ကဲ့သို့သော နှုန်းထားစာရင်းသွင်းဝန်ဆောင်မှုပေးသူများသည် ထိုနေရာတွင် $0 ကိုရေတွက်ပါ။ `listPriceUsd` သည် စာရင်းသွင်းထားသောစျေးနှုန်း၊ စာရင်းသွင်းမှုများပါ၀င်သော အသုံးပြုမှုစျေးနှုန်းနှင့် တူညီပါသည်။ မော်ဒယ်တွင် စျေးနှုန်းအတန်းမရှိသော တောင်းဆိုချက်တစ်ခုသည် ၎င်း၏ သိမ်းဆည်းထားသည့် ကုန်ကျစရိတ်ကို ရေတွက်သည်- ဝန်ဆောင်မှုပေးသူမှ အစီရင်ခံထားသည့် ကုန်ကျစရိတ်တစ်ခု သို့မဟုတ် တောင်းဆိုချက်ကို မှတ်တမ်းတင်သည့်အခါ တွက်ချက်ထားသည့် တစ်ခု။ အမှတ်အသားမပါသော၊ ရေတွက်ခြင်း မရှိသော တောင်းဆိုချက်တစ်ခုသာ ဖြစ်သောကြောင့် စုစုပေါင်း တစ်စိတ်တစ်ပိုင်းဖြစ်နိုင်ပါသည်။
- တုံ့ပြန်မှုစာချုပ်သည် `src/shared/schemas/selfUsage.ts` (`SelfUsageSeries` in `docs/openapi.yaml`) ဖြစ်သည်။

### ကိုယ်ပိုင်ဝန်ဆောင်မှုစာမျက်နှာ

`QUOTA_SELF_PANEL` ဖွင့်ထားခြင်းဖြင့် `/quota/{provider}` သည် အများသူငှာ စာမျက်နှာတစ်ခုဖြစ်သည်။ သော့ကိုင်ဆောင်သူသည် ထိုနေရာတွင် API သော့ကို ရိုက်ထည့်ကာ ပံ့ပိုးပေးသူအတွက် ထိုသော့အုပ်စုများကို မြင်သည်။ ရေကူးကန်တစ်ခုစီသည် ရေကူးကန်ဝင်းဒိုးတစ်ခုစီတွင် လူတိုင်းအတွက်အသုံးပြုမှုနှင့် သော့၏ကိုယ်ပိုင်မျှဝေမှုတို့နှင့်အတူ ကတ်တစ်ခုစီပြသည်။ ရေကူးကန်၏အကောင့်တစ်ခုစီတွင် အကောင့်အသုံးပြုမှုနှင့် သော့ခွဲဝေမှုတို့နှင့်အတူ ၎င်း၏ကိုယ်ပိုင်ကတ်များရှိသည်။ သော့သည် အကောင့်ဒေတာကို မြင်နိုင်မှသာ အကောင့်၏အသုံးပြုမှုသည် ပေါ်လာပါသည်။ စာမျက်နှာသည် အကောင့်တစ်ခုစီ၏ မော်ဒယ်ကန့်သတ်ချက်များနှင့် သော့၏ကိုယ်ပိုင်အသုံးပြုမှုတို့ကိုလည်း စာရင်းပြုစုထားသည်။ အချိန်ဇယားတစ်ခုက သော့ကို ပိတ်ဆို့လိုက်သောအခါ သတိပေးချက်တစ်ခု ပေါ်လာသည်။ ကတ်တစ်ခုသည် သော့တစ်ခုစီ၏ မော်ဒယ်ဦးထုပ်တိုင်းကို ၎င်း၏အသုံးပြုမှုနှင့်အတူ စာရင်းပြုစုပြီး ရောက်ရှိလာသည့်အရာများကို အမှတ်အသားပေးသည်။ `{provider}` သည် ဝန်ဆောင်မှုပေးသူ id သို့မဟုတ် ၎င်း၏ နံပတ် (`/quota/claude`, `/quota/cc`) ဖြစ်သည်။ အမည်မသိဝန်ဆောင်မှုပေးသူနှင့် အလံပိတ်ထားစဉ် `/quota/*` လမ်းကြောင်းတိုင်း၊ 404 ကိုဖြေဆိုပါ။ စိတ်ကြိုက် OpenAI- သို့မဟုတ် Anthropic-compatible node ပေါ်ရှိ အစုများသည် စာမျက်နှာမရှိပါ။ API သူတို့အတွက် အဖြေပေးနေတုန်းပဲ။

စာမျက်နှာတွင် စက်ရှင်မရှိပါ။ သော့ကို `GET /api/v1/me/quota/{provider}`၊ `PATCH /api/v1/me/quota/{provider}` နှင့် `GET /api/v1/me/usage`၏ `Authorization` ခေါင်းစီးတွင်သာ ပေးပို့သည်၊ URL တွင် ဘယ်တော့မှ မပို့ပါ။ ဆာဗာလက်ခံသောသော့ကို တက်ဘ်၏ `sessionStorage` တွင် သိမ်းဆည်းထားသည်။ "ဤစက်ပစ္စည်းပေါ်တွင် သတိရပါ" ဖြင့် ၎င်းကို ၎င်းအစား `localStorage` တွင် သိမ်းဆည်းထားပြီး "Forget key" သည် ၎င်းကို နှစ်ခုစလုံးမှ ဖယ်ရှားမည်ဖြစ်သည်။ ဆာဗာမှ ငြင်းပယ်သောသော့ကို သိုလှောင်မှုမှ ဖယ်ရှားသည်။

`consent` မုဒ်ရှိ ရေကူးကန်တစ်ခုသည် ချေးငွေကတ်ကို ပြသသည်။ အဲဒီမှာ သော့ကိုင်ထားသူက ချေးဖို့ သော့ရဲ့ idle share ရဲ့ 0 မှ 100 ရာခိုင်နှုန်းတစ်ခုလုံးကို သတ်မှတ်ပေးတယ်။ သဘောတူညီချက်သည် မည်မျှကြာမည်ကို ကိုင်ဆောင်ထားသူသည် ပိတ်ထားချိန်အထိ၊ 1 နာရီ၊ 8 နာရီ၊ 24 နာရီ၊ 7 ရက် သို့မဟုတ် 30 ရက်အထိဖြစ်သည်။ သိမ်းဆည်းသည့်အချိန်မှ ကြာချိန်ကို ရေတွက်သည်။ နောက်ဆုံးသတ်မှတ်ရက်သည် အသက်ဝင်နေချိန်တွင် ကိုင်ဆောင်ထားသူက ၎င်းကို သိမ်းဆည်းထားနိုင်သည်။ Save မတိုင်မီ နောက်ဆုံးရက်ကျော်လွန်ပါက၊ ကတ်သည် မည်သည့်အရာကိုမျှ ပေးပို့ပြီး အခြားရွေးချယ်မှုတစ်ခုကို တောင်းဆိုပါသည်။ 0% ဖြင့် နောက်ဆုံးရက်ကို မပို့ပါ။ ကတ်သည် ၎င်း၏ အချိန်ဇုန်အမည်ဖြင့် သိမ်းဆည်းထားသည့် နောက်ဆုံးရက်ကို ပြသသည်။ နောက်ဆုံးရက်ကျော်လွန်သွားသော သဘောတူညီချက်ကို ပြီးဆုံးသည့်အတိုင်း ပြထားသည်။

`hard` သော့တစ်ခုအတွက် ကတ်သည် ရေကူးကန်ဝင်းဒိုးတစ်ခုလျှင် အခြားသော့များကို ယခုသော့ထံ ချေးငှားပေးသည်ကိုလည်း ဖော်ပြပါသည်။ အတန်းတစ်ခုစီသည် အခြားသော့များအားလုံးအတွက် ပုံတစ်ပုံဖြစ်သည်။ သော့နှစ်လုံးပါသော ရေကန်တစ်ခုတွင် ၎င်းသည် အခြားသော့၏ကိုယ်ပိုင်ပုံဖြစ်သည်။ ရှုမြင်ပုံသည် သုညကဲ့သို့ မရရှိနိုင်သကဲ့သို့ မဖတ်ရဟု အစီရင်ခံမည်မဟုတ်ပါ။ `soft` သို့မဟုတ် `burst` သော့တစ်ခုအတွက် ကတ်သည် ပုံသဏ္ဍာန်နှင့် မသက်ဆိုင်ကြောင်း ဖော်ပြထားသည် ။

0 အထက်ရာခိုင်နှုန်းကို သော့သိမ်းဆည်းထားသည့် `saturation` မုဒ်ရှိ ရေကန်တစ်ခုသည် ငွေထုတ်ခြင်းကိုသာ ပြသသည်။ သိမ်းဆည်းထားသော ရာခိုင်နှုန်းသည် ထိုနေရာတွင် သက်ရောက်မှုမရှိဟု ဆိုသည်။ ၎င်း၏ ငွေထုတ်ခလုတ်သည် နောက်ဆုံးရက်မရှိဘဲ 0 ကို ပေးပို့သည်။ သိမ်းဆည်းထားသည့် 0 ပါသော `saturation` မုဒ်ရှိ ရေကူးကန်သည် ချေးငွေကတ်ကို ပြမည်မဟုတ်ပါ။ သိမ်းဆည်းပြီးနောက်၊ စာမျက်နှာ၏ကြည့်ရှုမှု ထပ်မံမပြောင်းလဲမီအထိ ပြန်ကြည့်ရန် မလိုအပ်တော့သည့် ကတ်တစ်ခုသည် ၎င်း၏စာနှင့်အတူ ရှိနေမည်ဖြစ်သည်။

ကိုင်ဆောင်ထားသူက Save သို့မဟုတ် Withdraw ကိုမနှိပ်မချင်း မည်သည့်အရာကိုမျှ မသိမ်းဆည်းပါ။ စာနယ်ဇင်းတစ်ခုစီသည် `PATCH /api/v1/me/quota/{provider}` တောင်းဆိုချက်တစ်ခု ပေးပို့ပြီး ပထမအကြိမ်တွင် ဆိုင်းငံ့ထားစဉ် ဒုတိယ စာနယ်ဇင်းက ဘာမျှမပေးပို့ပါ။ ကိုယ်ထည်သည် ရေကူးကန်၏ အလင်းပြသော `ref` မြင်ကွင်း၊ ရာခိုင်နှုန်းနှင့် နောက်ဆုံးရက်တို့မှ သယ်ဆောင်သည်။ အဖြေမှာ ပြန်လည်တည်ဆောက်ထားသော ခွဲတမ်းမြင်ကွင်းဖြစ်ပြီး စာမျက်နှာတွင် ၎င်းကို ဒုတိယမဖတ်ဘဲ ပြသထားသည်။ သိမ်းဆည်းမှုနှစ်ခု ထပ်နေသောအခါ၊ စာမျက်နှာသည် နောက်ဆုံးအဖြေပြီးနောက် တစ်ကြိမ် ခွဲတမ်းကို ဖတ်သည်။ စာမျက်နှာသည် ဘရောက်ဆာသိုလှောင်မှုတွင် သဘောတူညီချက်ကို မသိမ်းဆည်းပါ။

HTTP အခြေအနေမှ ရွေးချယ်ထားသော စာသားဖြင့် ကတ်ပေါ်တွင် ငြင်းဆိုထားသောပြောင်းလဲမှုကို ရှင်းပြသည်။ error body က မဖတ်ဘူး။ A 401 က သော့ကို လက်မခံဘဲ ခွဲတမ်းကို ပြန်လည်စတင်သည်ဟု ဆိုသည်။ A 403 က ရေကူးကန်သည် ချေးငွေအပြောင်းအလဲများကို မယူတော့ကြောင်း နှင့် 404 က ရေကူးကန် မရှိတော့ဟု ဆိုသည်။ နှစ်ခုလုံးသည် ခွဲတမ်းကို ပြန်လည်စတင်သည့် ခလုတ်တစ်ခု ကမ်းလှမ်းသည်။ 400 သို့မဟုတ် အခြား 4xx အဖြေတစ်ခုသည် ရာခိုင်နှုန်းနှင့် နောက်ဆုံးရက်ကို စစ်ဆေးရန် ကိုင်ဆောင်ထားသူအား တောင်းဆိုသည်။ အဖြေပေးသောအခါ 429 သည် ကိုင်ဆောင်ထားသူအား `Retry-After` စက္ကန့်ဖြင့် စောင့်ခိုင်းသည်။ 5xx အဖြေ၊ 408 သို့မဟုတ် ကွန်ရက် ချို့ယွင်းမှုတစ်ခုသည် ပြောင်းလဲမှုအား မသိမ်းဆည်းနိုင်ဘဲ ရိုက်ထည့်ထားသော တန်ဖိုးများကို သိမ်းဆည်းထားသည်ဟု ဆိုသည်။ စာချုပ်ပြင်ပ အဖြေတစ်ခုသည် ခွဲတမ်းကို ပြန်လည်စတင်သည်။ မအောင်မြင်သောသိမ်းဆည်းခြင်းသည် သော့ကို သူ့ဘာသာသူ မဖယ်ရှားပါ။ ငြင်းဆိုပြီးနောက် ပြန်လည်စတင်သောအခါ၊ စာမျက်နှာသည် ငြင်းဆိုထားသည့်စာဖတ်သည့်အတိုင်း သော့ကို ဖယ်ရှားသည်။

သော့တစ်ခုကို လက်ခံပြီးသည်နှင့်၊ စာမျက်နှာတွင် တက်ဘ်သုံးခုပါသည့် "သင်၏ကိရိယာများကို စနစ်ထည့်သွင်းပါ" ကတ်ကိုလည်း ပြသထားသည်။ "Claude Code" သည် `env` ဘလောက်ကို `~/.claude/settings.json` အတွက်ပေးသည်။ "Shell" သည် `export` လိုင်းများကဲ့သို့တူညီသော variable များကိုပေးသည်။ "Claude Desktop" သည် ၎င်း၏ ပြင်ပအဖွဲ့အစည်း အနုမာနဝင်းဒိုးအတွက် တန်ဖိုးများကို ပေးသည်။ မော်ဒယ်များသည် ပံ့ပိုးပေးသူအတွက် သော့ခေါ်နိုင်သည့် ခွဲတမ်းခွဲဝေမှု မော်ဒယ်များဖြစ်သည်။ ထိုစာရင်းတွင် သော့မပါလာသောအခါ၊ ဘလောက်သည် ၎င်းအစား တံခါးပေါက်ပုံစံရှာဖွေမှုကို ဖွင့်သည်။ ဂိတ်ဝေးလိပ်စာသည် ဆာဗာအစီရင်ခံတင်ပြသည့် အများသူငှာ API မူရင်းဖြစ်သည် (`OMNIROUTE_PUBLIC_API_BASE_URL`၊ ထို့နောက် `OMNIROUTE_PUBLIC_BASE_URL`)။ နှစ်ခုကို မသတ်မှတ်သည့်အခါ၊ ကတ်သည် နေရာယူထားသည့်နေရာကို ပြသပြီး ကိုင်ဆောင်ထားသူအား စီမံခန့်ခွဲသူကို မေးမြန်းရန် ပြောထားသည်။ သော့ကို နေရာယူသူအဖြစ် ပြထားသည်။ "ကျွန်ုပ်၏သော့ကို ထည့်သွင်းပါ" သည် ကီးတစ်ခုလုံးကို မျက်နှာပြင်ပေါ်တွင် စာသားနှင့် မိတ္တူခလုတ်ကို မိတ္တူကူးသည်။ ၎င်းသည် ဘောက်စ်ကို ရှင်းပြီးသည်အထိ ကြာရှည်သည်၊ သော့ကို မေ့သွားသည် သို့မဟုတ် အစားထိုးလိုက်သည်၊ သို့မဟုတ် စာမျက်နှာ ကျန်နေသေးသည် ။ ကတ်သည် တောင်းဆိုချက်မပို့ဘဲ ဖိုင်ဒေါင်းလုဒ်လုပ်ရန် ကမ်းလှမ်းခြင်းမရှိပါ။

API အမှတ်အသား `stale` ကိုဖတ်ခြင်းသည် ခေတ်နောက်ကျနေပြီဟု ပြသည်။ `unavailable` အမှတ်အသားပြုထားသည့် ဖတ်ခြင်းသည် သုညအဖြစ် မည်သည့်အခါမျှ ၎င်း၏ အကြောင်းပြချက်ဖြင့် ပြသည်။

ရာခိုင်နှုန်းအစီအစဥ်တွင် API ၎င်းကို သတင်းပို့သောအခါတွင် စာမျက်နှာသည် သော့၏ကိုယ်ပိုင်မျှဝေမှုကို ဆွဲယူသည်။ ကိန်းဂဏန်းသည် ခန့်မှန်းချက်တစ်ခုဖြစ်ပြီး ၎င်း၏ အပိုင်းနှစ်ပိုင်းကို အမည်ပေးထားသည်။ မော်ဒယ်အလိုက် ကန့်သတ်ချက်များသည် အကောင့်ကိုသာ ပြသသည်။

ဝင်းဒိုးတစ်ခုသည် `members` သယ်ဆောင်လာသောအခါ ၎င်း၏ကတ်သည် အထိုင်အစီအစဥ်အရ အဖွဲ့ဝင်တစ်ဦးလျှင် အပိုင်းတစ်ခုပါသည့် ဘားတစ်ခုကိုလည်း ပြသသည်။ မေးသော့၏အပိုင်းသည် လေယူလေသိမ်းအရောင်ကို အသုံးပြုသည်။ အခြားအပိုင်းများသည် အပြင်အဆင်၏ဇယားအရောင်များမှတဆင့် လည်ပတ်သည်။ စာသားဒဏ္ဍာရီတစ်ခုသည် အပိုင်းတိုင်းကို ၎င်း၏တန်ဖိုးဖြင့် စာရင်းပြုစုထားသောကြောင့် အရောင်ပေါ်တွင်မူတည်ခြင်းမရှိပါ။ N သည် အပေါက်နေရာတွင် `You` သို့မဟုတ် `Member N` ဟု တံဆိပ်တပ်ထားသည်။

### စာမျက်နှာအတွက် သီးသန့်ဆိပ်ကမ်း

`QUOTA_PANEL_PORT` ကိုယ်တိုင်ဝန်ဆောင်မှု စာမျက်နှာကိုသာ ဆောင်ရွက်ပေးသည့် ဒုတိယနားဆင်သူကို ဖွင့်သည်။ variable ကို သတ်မှတ်မထားပါက ၎င်းကို ပိတ်ထားသည်။ `QUOTA_PANEL_HOST` သည် bind address ဖြစ်ပြီး `127.0.0.1` တွင် ပုံသေဖြစ်သည်။

နားထောင်သူသည် ဤလမ်းကြောင်းများကို ပင်မဆိပ်ကမ်းသို့ ပြန်ပို့ပေးပြီး အခြားလမ်းကြောင်းတိုင်းအတွက် 404 ကို အဖြေပေးသည်-

`GET` နှင့် `HEAD` သည် ကိုယ်ခန္ဓာမပါဘဲ လက်ဆင့်ကမ်းသည်။ စာကိုယ်ပါ တောင်းဆိုချက်တစ်ခုကိုလည်း ထပ်ဆင့်ပေးပို့သည်- ချေးငွေရွေးချယ်မှုတစ်ခုကို သိမ်းဆည်းရန် စာမျက်နှာမှ ပေးပို့သည့် ခွဲတမ်းကြည့်ရှုမှုလမ်းကြောင်း၏ `PATCH` ။ CONNECT တောင်းဆိုချက်မှလွဲ၍ အခြားနည်းလမ်း 404 ကို အဖြေမပေးဘဲ ဆက်သွယ်မှုအား ပိတ်ထားသည်။ အဖွဲ့အစည်းတစ်ခုအား ကြေငြာသည့် အခြားတောင်းဆိုမှုတိုင်းသည် 404 ကိုဖြေကြားပြီး ၎င်း၏ချိတ်ဆက်မှုကို ပိတ်ထားသည်။ အဆင့်မြှင့်တင်ရန် တောင်းဆိုမှုများကို ငြင်းဆိုထားပြီး ၎င်းတို့၏ ချိတ်ဆက်မှုကို ပိတ်ထားသည်။ API ဆိပ်ကမ်းတွင်ကဲ့သို့ အစက်အပိုင်း သို့မဟုတ် အပိုင်းအစ အမှတ်အသားပါသော လမ်းကြောင်းကို ငြင်းဆိုထားသည်။ ထို့ကြောင့် ပုံနှိပ်နိုင်သော ASCII ပြင်ပတွင် စာလုံးတစ်လုံးပါသော တောင်းဆိုချက်ပစ်မှတ်တစ်ခုဖြစ်သည်။ ဤပို့တ်၏ကိုယ်ပိုင်စစ်ဆေးခြင်းမပြုမီ၊ ပစ်မှတ်ရှိ အကြမ်းထည်ထိန်းချုပ်မှုဇာတ်ကောင်တစ်ခုကို HTTP parser မှ အဖြေ 400 ကိုဖြေကြားသည်။ မူဘောင်အား ၎င်း၏ကိုယ်ပိုင်အသုံးပြုမှုအတွက် သိမ်းဆည်းထားသည့် ခေါင်းစီးများကို ဆင့်ခေါ်ခြင်းမပြုပါ- `x-middleware-`၊ `x-invoke-`၊ `x-nextjs-`၊ `x-now-` သို့မဟုတ် `x-next-`၊ နှင့် `x-matched-path` နှင့် `next-resume` အမည်များ . ၎င်းတို့မပါဘဲ တောင်းဆိုချက်ကို ထပ်ဆင့်ပို့သည်။ ဒက်ရှ်ဘုတ်၊ လော့ဂ်အင်စာမျက်နှာ၊ စီမံခန့်ခွဲမှု API နှင့် အနုမာနလမ်းကြောင်းများကို ဤဆိပ်ကမ်းမှတဆင့် မရောက်နိုင်ပါ။

`PATCH` `Content-Type: application/json`၊ ဘောင်မပါသော သို့မဟုတ် `charset=utf-8` ဖြင့်သာ ဆောင်ထားရမည်။ ၎င်းသည် `Content-Length` တစ်ခုမှ 1 မှ 4096 အထိ၊ ရိုးရိုးဂဏန်းများအဖြစ် ရေးသားထားကာ `Transfer-Encoding` မရှိပါ။ ဤစည်းမျဥ်းများထဲမှ တစ်ခုကို ချိုးဖောက်သော `PATCH` သည် 404 ကို အဖြေပေးပါသည်။ လက်မှတ်ထိုးထားသော သို့မဟုတ် ထပ်ခါတလဲလဲ ပြုလုပ်ခြင်းကဲ့သို့ ပုံစံမမှန်သော အရှည်အချို့ကို ဤ port ၏ကိုယ်ပိုင်မစစ်ဆေးမီ HTTP parser မှ 400 ကို အဖြေပေးပါသည်။ ဆိပ်ကမ်းသည် ပင်မပို့တ်ကို မဆက်သွယ်မီ ကြေငြာထားသော ဘိုက်များကို ဖတ်ပြီး ၎င်းတို့အတွက် အများဆုံး 5 စက္ကန့် စောင့်သည်။ ထို့နောက် 404 အဖြေမပြီးသေးသော ကောင်က ၎င်း၏ချိတ်ဆက်မှုကို ပိတ်ထားသည်။ ထိုအခြေအနေမျိုးတွင် ပင်မဆိပ်ကမ်းသို့ မည်သည့်အရာမှ မရောက်ပါ၊ သို့မဟုတ် ဖောက်သည်သည် ဦးစွာထွက်ခွာသောအခါတွင် မည်သည့်အရာမှ မရောက်ပါ။ port relay သည် တူညီသော `Content-Length` ဖြင့် ကြေညာထားသော bytes အတိအကျကို ဖော်ပြသည်။ ၎င်းတို့ပြီးနောက် ဘိုက်များကို ချိတ်ဆက်မှုတွင် နောက်လာမည့် တောင်းဆိုချက်အဖြစ် ဖတ်သည်။ ရှေ့ရှိ TLS ပြောင်းပြန်ပရောက်စီတစ်ခုသည် `Content-Length` ပေးပို့ရမည်ဖြစ်ပြီး တောင်းဆိုချက်ကိုယ်ထည်ကို ပြန်မရိုက်ရပါ။ ပင်မအပေါက်သည် `Authorization` ခေါင်းစီးရှိ API ကီးကို စစ်ဆေးသည်၊ `GET`.

404 ကိုယ်ထည်သည် `{"error":"not_found","message":"Not found."}` ဖြစ်သည်။ မအောင်မြင်သော relay သည် `detail` အကွက်မရှိသော 502 (`api_bridge_unavailable`) သို့မဟုတ် 504 (`api_bridge_timeout`) ကို အဖြေပေးသည်။

နားထောင်သူသည် `QUOTA_SELF_PANEL` မဖတ်ဘဲ၊ စာမျက်နှာကိုဖွင့်မထားပါ။ အလံပိတ်နေစဉ်၊ စာမျက်နှာနှင့် ၎င်း၏ API သည် ပင်မပို့တ်တွင် 404 အဖြေရှိပြီး နားထောင်သူက ထိုအဖြေကို ထပ်ဆင့်ပို့သည်။

ဖွံ့ဖြိုးတိုးတက်မှုဆာဗာ (`next dev`) အောက်တွင် စာမျက်နှာသည် ဤပို့တ်မှတစ်ဆင့် အပြန်အလှန်တုံ့ပြန်မှုဖြစ်လာမည်မဟုတ်ပါ။ ဖွံ့ဖြိုးတိုးတက်မှု hot-reload socket သည် အဆင့်မြှင့်ရန် တောင်းဆိုချက်ဖြစ်ပြီး ဆိပ်ကမ်းက ၎င်းကို ငြင်းပယ်သည်။ ဖွံ့ဖြိုးတိုးတက်နေချိန်တွင် ပင်မဆိပ်ကမ်းကို အသုံးပြုပါ။

ဆိပ်ကမ်းသည် ရိုးရိုး HTTP ဆောင်ရွက်ပေးပြီး စာမျက်နှာသည် API သော့များကို ပေးပို့သည်။ မူရင်း bind လိပ်စာကို သိမ်းထားပြီး ၎င်းရှေ့တွင် TLS ဖြင့် ပြောင်းပြန် proxy ကို ထည့်ပါ။ loopback မှလွဲ၍ အခြားစည်းလိပ်စာတစ်ခုသည် ဤသတိပေးချက်ကို မှတ်တမ်းတင်သည်-

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

ပင်မပို့တ်တွင် စက်တွင်းအဖြစ် ထပ်ဆင့်ပို့ခြင်း ခေါင်းစီးရေတွက်ခြင်း မရှိသော လှည့်ကွက်မျိုးတူ။ ထို့ကြောင့် တူညီသော host ရှိ proxy သည် `X-Forwarded-For` ပေးပို့ရပါမည်။ သီးသန့်လိပ်စာရှိ proxy ကို `OMNIROUTE_TRUST_PROXY=private` (သို့မဟုတ် `lan`) ဖြင့်သာ ထိုခေါင်းစီးအတွက် ယုံကြည်ပါသည်။ အခြားမျိုးတူချင်းများကို ၎င်း၏ချိတ်ဆက်မှုလိပ်စာဖြင့် အစီရင်ခံထားပြီး ၎င်းပေးပို့သည့် ထပ်ဆင့်ခေါင်းစီးများကို ပြုတ်ကျစေသည်။

နားထောင်သူသည် တစ်ကြိမ်လျှင် ချိတ်ဆက်မှု အများဆုံး 256 ခုရှိသည်။ ဖောက်သည်တစ်ဦးသည် တောင်းဆိုချက်ခေါင်းစီးများကို ပေးပို့ရန် 10 စက္ကန့်နှင့် တောင်းဆိုချက်တစ်ခုလုံးကို ပေးပို့ရန် စက္ကန့် 30 ရှိသည်။ 5 စက္ကန့်ခန့်ကြာပြီးနောက် idle Keep-alive ချိတ်ဆက်မှု ပိတ်သွားသည်။ စက္ကန့် 60 ကြာ လှုပ်ရှားမှုမရှိသော ချိတ်ဆက်မှုကို ပိတ်ထားသည်။ ဤတန်ဖိုးများသည် ပုံသေဖြစ်သည်။ ရှေ့ရှိ ပြောင်းပြန် proxy တွင်လည်း ချိတ်ဆက်မှုနှင့် နှုန်းကန့်သတ်ချက်များကို သတ်မှတ်ပါ။ ရှေ့ရှိ ပြောင်းပြန် proxy သည် ၎င်း၏ idle upstream ချိတ်ဆက်မှုများကို 5 စက္ကန့်ထက်နည်းအောင် ထိန်းသိမ်းထားသင့်သည်၊ သို့မဟုတ် ၎င်းတို့ကို ပြန်မသုံးသင့်ပါ။ ပင်မဆိပ်ကမ်းသို့ relay သည် API port (`API_BRIDGE_*`) ၏ အထက်ရေစီးကြောင်း အချိန်ကုန်ခြင်းကို အသုံးပြုသည်။

`API_PORT` သတ်မှတ်မထားသည့်အချိန်တွင် နားထောင်သူသည်လည်း စတင်သည်။ `QUOTA_PANEL_PORT` ဂဏန်းများဖြင့်သာ ရေးသားထားသော 1 မှ 65535 အထိ ဖြစ်ရပါမည်။ ၎င်းသည် dashboard port နှင့် API port တို့မှ ကွဲပြားရပါမည်။ တိုက်ရိုက် WebSocket ဆာဗာကို ဖွင့်ထားစဉ်၊ ၎င်းသည် `LIVE_WS_PORT` (မူလ 20132) နှင့်လည်း ကွဲပြားရပါမည်။ အခြားတန်ဖိုးများသည် မည်သည့်အရာကိုမျှ မဖွင့်ဘဲ သတိပေးချက်တစ်ခုကို မှတ်တမ်းတင်ထားသည်။ ငြင်းဆိုထားသည့်တန်ဖိုးအကြောင်း သတိပေးချက်သည် ကိန်းရှင်ကို အမည်ပေးကာ တန်ဖိုးကို ထပ်၍မပေးပါ။ အသုံးပြုပြီးသား ဆိပ်ကမ်းတစ်ခုသည် မည်သည့်အရာကိုမျှ မဖွင့်ဘဲ ဤသတိပေးချက်ကို မှတ်တမ်းတင်သည်-

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH` အစုံဖြင့်၊ နားထောင်သူသည် ထိုရှေ့ဆက်အောက်တွင် အထက်လမ်းတိုင်းကို မျှော်လင့်သည်။ တည်ဆောက်ချိန်နှင့် လုပ်ဆောင်သည့်အချိန်၌ တူညီသော `OMNIROUTE_BASE_PATH` အသုံးပြုပါ။ ၎င်းကို ဦးဆောင်မျဉ်းစောင်းဖြင့် ရေးပါ၊ ဥပမာ `/omniroute`၊ `/` နှင့် `/omniroute/` အပါအဝင် အခြားပုံသဏ္ဍာန်တစ်ခုသည် အဆိုပါပုံစံများကို လက်ခံသော်လည်း တည်ဆောက်မှုမှ သတိပေးချက်ဖြင့် ဆိပ်ကမ်းကို ပိတ်ထားသည်။ ပထမအပိုင်းသည် အပလီကေးရှင်းလမ်းကြောင်းကို အမည်ပေးသည့် အခြေခံလမ်းကြောင်းဖြစ်သည်- `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0` သို့မဟုတ် `connect`, မည်သို့ပင်ဆိုစေ။

ကန့်သတ်ချက်များ-

- နောက်မှ မျဥ်းစောင်းဖြင့်`/quota/{provider}/` ဤပို့တ်တွင် 404 ကို အဖြေပေးသည်။
- ဝန်ဆောင်မှုဝန်ထမ်းနှင့် ဝဘ်အက်ပ်မန်နီးဖက်စ်ကို ဤဆိပ်ကမ်းတွင် ဆောင်ရွက်ပေးခြင်းမရှိပါ။
- ဒက်ရှ်ဘုတ်တွင် သတ်မှတ်ထားသော စိတ်ကြိုက် Favicon တစ်ခုကို ဤအပေါက်တွင် မပြပါ။
- အပလီကေးရှင်းသည် အခြေခံလမ်းကြောင်းတစ်ခုအောက်တွင် အလုပ်လုပ်သည့်အခါ အိုင်ကွန်များကို ပြသမည်မဟုတ်ပါ။
- ဆိပ်ကမ်းသည် ဗြောင် HTTP/1.1. ပြောသည်
- လုပ်ငန်းစဉ်ပြန်လည်စတင်မချင်း ပျက်ကွက်သောစည်းကို ပြန်မစမ်းပါ။
- နားထောင်သူသည် သုံးစွဲသူလိပ်စာတစ်ခုအတွက် ချိတ်ဆက်မှု သို့မဟုတ် နှုန်းထားကန့်သတ်ချက်မရှိပါ။
- ကွန်တိန်နာ စနစ်ထည့်သွင်းမှုများကို ဤကဏ္ဍတွင် မပါဝင်ပါ။

## ပြဿနာဖြေရှင်းခြင်း

### Redis ကို စီစဉ်သတ်မှတ်ထားသော်လည်း ချိတ်ဆက်၍မရခြင်း

`ioredis` ကို ထည့်သွင်းထားကြောင်း (`npm ls ioredis`) နှင့် `QUOTA_STORE_REDIS_URL`
ကို ဆက်သွယ်နိုင်ကြောင်း စစ်ဆေးပါ။ ချိတ်ဆက်မှု မအောင်မြင်ပါက factory သည် SQLite သို့ ပြန်လည်အသုံးပြုမည် (`warn`
အဆင့်ဖြင့် log မှတ်တမ်းတင်သည်)။

### `peek` က ဒေတာဟောင်းကို ပြန်ပေးခြင်း / fail-open ဖြစ်ခြင်း

`peek` က error ပစ်ပါက `enforceQuotaShare` သည် ရလဒ်ကို "ခွင့်ပြုသည်" (fail-open) ဟု သတ်မှတ်သည်။
အခြေခံအကြောင်းရင်းကို ဖော်ထုတ်ရန် `pino` log များထဲရှိ `quota:enforce` နှင့် `quota:factory` entry များကို
စစ်ဆေးပါ။

### သုံးစွဲမှု counter ကွာဟခြင်း

Provider ၏ အမှန်တကယ်အသုံးပြုမှုသည် counter များနှင့် ကွာခြားပါက မျှော်လင့်ထားသည့် အခြေအနေဖြစ်သည် —
2-bucket sliding window တွင် window နယ်နိမိတ်များ၌ ~1% အမှားရှိပြီး `consume` ကို
response ပြန်ပေးပြီးနောက် fire-and-forget ပုံစံဖြင့် လုပ်ဆောင်သည်။ Saturation signal (`saturationSignals.ts`)
သည် အမှန်တကယ် provider အသုံးပြုမှုကို 30 စက္ကန့် TTL ဖြင့် ဖတ်ရှုပြီး `globalUsedPercent`
ကို လိုက်လျောညီထွေ ချိန်ညှိသည်။

### Pool တွင် burn rate အတွက် "ဒေတာမရှိ" ဟု ပြခြင်း

`computeBurnRate` သည် အနည်းဆုံး သမိုင်းဆိုင်ရာ sample 2 ခု လိုအပ်သည်။ ယခင်
`consume` call မရှိသော pool အသစ်များတွင် `tokensPerSecond: 0` နှင့် `timeToExhaustionMs: null` ဟု ပြမည်။

## localStorage မှ ရွှေ့ပြောင်းခြင်း

`/dashboard/costs/quota-share` ကို ပထမဆုံး ဖွင့်သည့်အခါ hook ဖြစ်သော `useLocalStoragePoolMigration` က အောက်ပါတို့ကို စစ်ဆေးသည်-

1. `localStorage.getItem("omniroute:quota-share:pools")` သည် ဗလာမဟုတ်ပါ။
2. `GET /api/quota/pools` က `[]` ကို ပြန်ပေးသည် (DB သည် ဗလာဖြစ်သည်)။

နှစ်ချက်စလုံး မှန်ကန်ပါက legacy pool တစ်ခုစီကို batch အဖြစ် `POST /api/quota/pools` သို့ ပို့ပြီးနောက်
localStorage key ကို ဖယ်ရှားသည်။ ဤရွှေ့ပြောင်းမှုသည် idempotent ဖြစ်သည်- အခြေအနေ 2 က
ထပ်မံရွှေ့ပြောင်းခြင်းကို တားဆီးပေးသည်။

## အတွင်းပိုင်း Strategy အမျိုးအစားခွဲခြားခြင်း

option အဖြစ် မည်သည့်အခါမျှ မပေါ်စေရန် `ROUTING_STRATEGY_VALUES` မှ တမင်ဖယ်ထုတ်ထားသည်။

## DB Schema အကျဉ်းချုပ်

ရွှေ့ပြောင်းခြင်း `078`၊ `079` နှင့် `085` ဖြင့် ထည့်ထားသော ဇယားသုံးခု

- `quota_pools` + `quota_allocations` — pool အဓိပ္ပါယ်ဖွင့်ဆိုချက်များနှင့် သော့တစ်ခုစီခွဲဝေမှု။
- `quota_consumption` — `(apiKeyId, dimensionKey)` တစ်ခုလျှင် 2-ပုံးကောင်တာများ လှိမ့်နေသည်။
- `provider_plans` — လက်စွဲ ပံ့ပိုးပေးသူ အစီအစဉ်ကို ထပ်ရေးသည် (အတိုင်းအတာ JSON per connectionId)။

idempotent `CREATE TABLE IF NOT EXISTS` ရွှေ့ပြောင်းမှုများမှတစ်ဆင့် ဇယားအားလုံးကို ထည့်သွင်းထားသည်။

သဘောတူခွင့်ပြုထားသော ချေးငွေသည် ကော်လံသုံးခုကို ပေါင်းထည့်သည်- `quota_allocations.lending_percent` (ကိန်းပြည့်၊ ပုံသေ 0)၊ `quota_allocations.lending_until` (epoch milliseconds၊ သို့မဟုတ် နောက်ဆုံးရက်အတွက် `NULL` ) နှင့် `quota_pools.borrow_mode` (မူလ `saturation`)။ ၎င်း၏ ပြောင်းရွှေ့ခြင်းသည် ဤကော်လံများကိုသာ ထည့်သွင်းပြီး ရှိပြီးသားအတန်းကို မရေးပါ။

ရာခိုင်နှုန်းထည့်ဝင်မှုစာအုပ်တွင် `quota_percent_ledger` (တစ်တန်း၊ အကောင့်နှင့် အစီအစဉ်ဝင်းဒိုးတစ်ခုစီ) နှင့် `quota_percent_ledger_tokens` (ရေကူးကန်တစ်ခုလျှင် တိုကင်ကောင်တာတစ်ခု၊ အကောင့်နှင့် API သော့) တို့ကို ပေါင်းထည့်သည်။ `src/lib/db/quotaPercentLedger.ts` သူတို့ကို ဖတ်ပြီး ရေးတယ်။
