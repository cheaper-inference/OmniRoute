## Zero-Config အလိုအလျောက် လမ်းကြောင်းရွေးချယ်ခြင်း (`auto/` ရှေ့ဆက်)

> **အသစ်:** combo ဖန်တီးရန် မလိုအပ်ပါ။ မည်သည့် client တွင်မဆို `auto/` ရှေ့ဆက်ကို တိုက်ရိုက်အသုံးပြုပါ။

### အမြန်နမူနာများ

| -------------- | ------- | ----------------------------------------------------------------------------------------------------- |

| `auto/coding`  | coding  | အရည်အသွေးဦးစားပေး weights၊ code ထုတ်လုပ်ခြင်းအတွက် သင့်လျော်သည်                                       |

| `auto/cheap`   | cheap   | ကုန်ကျစရိတ်အကောင်းဆုံးဖြစ်အောင် လမ်းကြောင်းရွေးချယ်ခြင်း (အနည်းဆုံးကုန်ကျစရိတ်ကို ဦးစွာရွေးသည်)       |
| `auto/offline` | offline | quota ရရှိနိုင်မှု အမြင့်ဆုံး provider များကို ဦးစားပေးသည်                                            |
| `auto/smart`   | smart   | ပိုမိုကောင်းမွန်သော model ရှာဖွေမှုအတွက် အရည်အသွေးဦးစားပေး + ပိုမြင့်သော စမ်းသပ်ရှာဖွေမှုနှုန်း (10%) |
| `auto/lkgp`    | lkgp    | တိကျစွာသတ်မှတ်ထားသော LKGP (မူလ `auto` နှင့် တူညီသည်)                                                  |
| `auto/chaos`   | chaos   | အပြိုင် fan-out၊ provider တစ်ခုလျှင် model တစ်ခု (ချို့ယွင်းချက်ထည့်သွင်းခြင်း မဟုတ်ပါ)               |

### Category × Tier ပေါင်းစပ်မှု (`auto/<category>:<tier>`)

OpenRouter ပုံစံ suffix များသည် **မည်သည့်လမ်းကြောင်းအမျိုးအစားဖြစ်သည်** (category) ကို **မည်သို့ အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်မည်** (tier) နှင့် ခွဲခြားပေးသောကြောင့် ၎င်းတို့ကို လွတ်လပ်စွာ ပေါင်းစပ်နိုင်သည် (#4235 Phase B၊ `open-sse/services/autoCombo/suffixComposition.ts`)：

- **Categories** (စွမ်းဆောင်ရည်အလိုက် ရွေးချယ်နိုင်သော pool ကို စစ်ထုတ်သည်): `coding` · `reasoning` · `vision` · `chat` · `multimodal`။ `vision`/`multimodal` သည် vision စွမ်းရည်ရှိသော model များကို ထိန်းသိမ်းထားပြီး `reasoning` သည် reasoning/thinking model များကို ထိန်းသိမ်းထားသည်။
- **Tiers** (အမှတ်ပေး weights / pool filter ကို ရွေးချယ်သည်): `fast` (လျင်မြန်စွာ ထုတ်ပေးခြင်း) · `cheap` (`floor` ၏ alias၊ ကုန်ကျစရိတ်ချွေတာမှု) · `reliable` (circuit-breaker ကျန်းမာရေး + latency တည်ငြိမ်မှု) · `free` / `pro` (`classifyTier` မှတစ်ဆင့် model tier အလိုက် pool ကို စစ်ထုတ်သည် — free-tier နှင့် premium)။

| နမူနာ                  | ဖြေရှင်းသတ်မှတ်ပုံ                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `auto/coding:fast`     | coding pool၊ latency နည်းသော weights                                                     |
| `auto/coding:cheap`    | coding pool၊ ကုန်ကျစရိတ်အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်ထားသည် (`auto/coding:floor` ၏ alias) |
| `auto/reasoning:pro`   | reasoning/thinking model များသာ၊ premium tier                                            |
| `auto/vision`          | vision စွမ်းရည်ရှိသော model များ (tier မရှိ → ချိန်ညှိထားသော weights)                    |
| `auto/multimodal:free` | multimodal စွမ်းရည်ရှိသော model များ၊ free tier သာ                                       |

တရားဝင်သော `auto/<category>[:<tier>]` မှန်သမျှကို လိုအပ်သည့်အချိန်တွင် ဖြေရှင်းသတ်မှတ်ပေးသည်။ စီစဉ်ရွေးချယ်ထားသော အစုခွဲတစ်ခုကို `/v1/models` နှင့် dashboard တွင် ဖော်ပြထားသည် (`open-sse/services/autoCombo/builtinCatalog.ts` ရှိ `AUTO_SUFFIX_VARIANTS`)။ စစ်ထုတ်ခြင်းသည် **fail-open** ဖြစ်သည် — constraint တစ်ခုနှင့် ကိုက်ညီသော ချိတ်ဆက်ထားသည့် model မရှိပါက လမ်းကြောင်းရွေးချယ်မှု မပျက်စေရန် pool အပြည့်အစုံကို အသုံးပြုသည်။ အဓိက scorer (`combo.ts`) သည် မပြောင်းလဲဘဲ category/tier filter ကို `buildAutoCandidates` တွင် အသုံးချထားသည်။

> **တိုက်ရိုက် model အသိဉာဏ်:** `ARENA_ELO_SYNC_ENABLED` flag ဖွင့်ထားသည့်အခါ အလိုအလျောက်လမ်းကြောင်းရွေးချယ်မှု၏ သင့်လျော်မှုကို တိုက်ရိုက် **Arena ELO** အဆင့်သတ်မှတ်ချက်များ + **models.dev** tier data တို့ဖြင့် ဆုံးဖြတ်သည် (မဟုတ်ပါက static fitness map ကို ပြန်လည်အသုံးပြုသည်)။

**အသုံးပြုနည်း:**

```bash
# OpenAI format ကို ပံ့ပိုးသော မည်သည့် IDE သို့မဟုတ် CLI tool မဆို
Base URL: http://localhost:20128/v1
API Key:  <သင့်-endpoint-key>

# သင့် code/config တွင် model ကို အောက်ပါအတိုင်း သတ်မှတ်ပါ:
model: "auto"                 # ချိန်ညှိထားသော မူလရွေးချယ်မှု
model: "auto/coding"          # coding လုပ်ငန်းများအတွက် အကောင်းဆုံး
model: "auto/fast"            # ရရှိနိုင်သည့်အထဲတွင် အမြန်ဆုံး
model: "auto/cheap"           # token တစ်ခုလျှင် ဈေးအသက်သာဆုံး
```

**ဖြစ်ပျက်ပုံ:**

1. OmniRoute သည် `src/sse/handlers/chat.ts` တွင် `auto/` ရှေ့ဆက်ကို ရှာဖွေသိရှိသည်
2. database မှ **အသုံးပြုနေသော provider ချိတ်ဆက်မှုများ** အားလုံးကို query ပြုလုပ်သည်
3. တရားဝင် credentials (API key သို့မဟုတ် OAuth token) ရှိသည့်အရာများကို စစ်ထုတ်သည်
4. ချိတ်ဆက်မှုတစ်ခုစီအတွက် model ကို ဆုံးဖြတ်သည် (`connection.defaultModel` သို့မဟုတ် provider ၏ ပထမဆုံး model)
5. memory အတွင်း **virtual combo** တစ်ခုကို တည်ဆောက်သည် (DB တွင် မသိမ်းဆည်းပါ)
6. ရွေးချယ်ထားသော မူကွဲ၏ weight profile + LKGP နည်းဗျူဟာကို အသုံးပြု၍ လမ်းကြောင်းရွေးချယ်သည်

**အဓိကဂုဏ်သတ္တိများ:**

- ✅ **အမြဲဖွင့်ထားသည်:** toggle မလို၊ combo ဖန်တီးရန် မလို၊ configuration မလိုအပ်ပါ
- ✅ **Dynamic:** လက်ရှိချိတ်ဆက်ထားသော provider များကို အလိုအလျောက် ထင်ဟပ်ပေးသည်
- ✅ **Session stickiness:** LKGP သည် နောက်ဆုံးအောင်မြင်ခဲ့သော provider ကို ဦးစားပေးရန် သေချာစေသည်
- ✅ **အကောင့်အများအပြားကို သိရှိစီမံနိုင်သည်:** provider ချိတ်ဆက်မှုတစ်ခုစီသည် သီးခြား candidate တစ်ခု ဖြစ်လာသည်
- ✅ **DB ရေးသားမှုမရှိ:** Virtual combo သည် request အတွက်သာ တည်ရှိပြီး persistence overhead လုံးဝမရှိပါ

### Key တစ်ခုချင်းစီအလိုက် candidate ထိန်းချုပ်မှု (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` နောက်ရှိ suffix သို့မဟုတ်
အခြေခံ channel အတွက် တိုက်ရိုက် `auto`) သည် ရှိပြီးသား resilience reads များကို
ပြန်လည်အသုံးပြုကာ တိုက်ရိုက် reachability ဖြင့် ဖြည့်စွက်ဖော်ပြထားသည့် `auto/*` channel ၏
လက်ရှိ candidate pool ကို စာရင်းပြုစုသော **ဖတ်ရှုရန်သီးသန့်** endpoint ဖြစ်သည် (breaker `state` အကြမ်းကို မည်သည့်အခါမျှ မသုံးပါ):

- provider circuit breaker — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ချိတ်ဆက်မှု cooldown — ဖြေရှင်းသတ်မှတ်ထားသော `provider_connections` row ရှိ
  `rateLimitedUntil` / `testStatus`
- model lockout — `isModelLocked(provider, connectionId, model)`

Candidate တစ်ခုစီတွင် ဤ API key ၏ `excluded` flag လည်း ပါဝင်သည်။ ဖယ်ထုတ်မှုများကို
API key တစ်ခုချင်းစီအလိုက် သိမ်းဆည်းထားသည် (`auto_candidate_overrides` table၊ migration `128`) — OmniRoute သည်
`users` table မရှိသော single-tenant ဖြစ်သောကြောင့် `apiKeyId` သည် တကယ့် caller တစ်ဦးချင်းစီ၏
identity နှင့် အနီးစပ်ဆုံးဖြစ်သည် — ထို့ပြင် သီးခြားယူနစ်စမ်းသပ်ထားသော
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) မှတစ်ဆင့်
`open-sse/services/autoCombo/virtualFactory.ts` ရှိ candidate-pool chokepoint တွင် အတင်းအကျပ် အသုံးချသည်။
Filter သည် **fail-open** ဖြစ်သည်: apiKeyId/channel ကို မသတ်မှတ်ထားခြင်း သို့မဟုတ် DB lookup ပျက်ကွက်ခြင်း နှစ်မျိုးစလုံးတွင်
pool ကို စစ်ထုတ်ခြင်းမပြုဘဲ ထားရှိသောကြောင့် override များ မစီစဉ်ထားသည့် operator တစ်ဦးသည် ဤ feature မတိုင်မီကနှင့်
byte အဆင့်အထိ တစ်ပုံစံတည်းဖြစ်သော လမ်းကြောင်းရွေးချယ်မှုကို တွေ့မြင်ရသည်။

**နောက်ဆက်တွဲ issue တစ်ခုသို့ ရွှေ့ဆိုင်းထားသည်:** candidate တစ်ခုချင်းစီအလိုက် weight များ + တိကျစွာ သတ်မှတ်ထားသော အစီအစဉ် (Level 3
— လက်ရှိ weighted/priority strategy လမ်းကြောင်းများသို့ ထည့်သွင်းပေးသည်) နှင့် `auto/*` channel တစ်ခုချင်းစီအတွက် သတ်မှတ်ထားသော
`combo.ts` strategy တစ်ခုကို pin လုပ်ခြင်း (Level 4)။ single-tenant model ကို ထည့်သွင်းစဉ်းစားလျှင် override များကို API key တစ်ခုချင်းစီအလိုက် ဆက်လက်ထားရှိသင့်သလား သို့မဟုတ် global အဖြစ် ပြောင်းလဲသင့်သလားဆိုသည့် အဖြေမရှိသေးသော
မေးခွန်းအတွက် #7819 plan ကို ကြည့်ပါ။

**နောက်ကွယ်ရှိ လုပ်ငန်းစဉ်:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**အကောင်အထည်ဖော်မှုဆိုင်ရာ ဖိုင်များ:**

| ဖိုင်                                                     | ရည်ရွယ်ချက်                                        |
| --------------------------------------------------------- | -------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Prefix parser (`parseAutoPrefix`)                  |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Virtual `AutoComboConfig` object များကို ဖန်တီးသည် |

## သိမ်းဆည်းထားသော Auto ပေါင်းစပ်မှုများအတွက် အကောင့်ဦးစားပေးများ

Intelligent Auto တည်းဖြတ်သူသည် ရွေးချယ်ခွင့်တစ်ခု ပေးထားသည်။** အကောင့်ဦးစားပေးများ** အပိုင်း။ ချိတ်ဆက်မှုတစ်ခုစီတိုင်းကို ဦးစားပေး၊ ပုံမှန် (မူလ)၊ သီးသန့် သို့မဟုတ် ဖယ်ထုတ်နိုင်သည်။ ချိတ်ဆက်မှုများစွာသည် အဆင့်တစ်ခုကို မျှဝေနိုင်သည်။ သတ်မှတ်ချက်ပြည့်မီသော ပထမအဆင့်အတွင်း အလိုအလျောက်ရွေးချယ်ပြီး ၎င်း၏ scoring/router အပြုအမူကို ထိုနေရာတွင် ထိန်းသိမ်းထားရန်၊ မအောင်မြင်သော ကြိုးပမ်းမှုများသည် ပုံမှန်အရန်မထားရှိမီ ဦးစားပေးရမည့် ကျန်ခိုင်မာသော အကောင့်များသို့ ရောက်သွားပါသည်။ ဖယ်ထုတ်ထားသော ချိတ်ဆက်မှုများကို ဤပေါင်းစပ်မှုတွင် ဘယ်တော့မှ အသုံးမပြုပါ။

ဆက်တင်ကို `config.accountPreferences` အဖြစ် သိမ်းဆည်းထားပြီး ID ချိတ်ဆက်မှုဖြင့် သော့ခတ်ထားသည်။

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

ချန်လှပ်ထားသည့် သို့မဟုတ် အလွတ်မြေပုံတစ်ခုသည် လက်ရှိလမ်းကြောင်းကို ထိန်းသိမ်းထားသည်။ ဦးစားပေးများသည် ပိတ်ထားရသော ချိတ်ဆက်မှုများကို ဖွင့်မပေးပါ၊ API ကီးအသုံးပြုခွင့်ကို ပေးသည်၊ ခွဲတမ်း-ပိတ်ဆို့ထားသော ကိုယ်စားလှယ်လောင်းများကို ပြန်လည်ရယူခြင်း သို့မဟုတ် ဘတ်ဂျက်စစ်ဆေးမှုများကို ကျော်ဖြတ်ပါ။ ကြိုးပမ်းမှုတိုင်းသည် ၎င်း၏ခိုင်မာသောချိတ်ဆက်မှုကို ကန့်သတ်ထားသောကြောင့် အကောင့်ပြန်လည်ရယူမှုသည် ပေါင်းစပ်ရောက်တာနောက်တွင် အဆင့်များမတက်နိုင်ပါ။ လက်ရှိ စက်ရှင်၏ ရင်းနှီးမှုသည် အရည်အချင်းပြည့်မီသော အကောင့်ကို ထိန်းသိမ်းထားနိုင်သည်။ တိတ်တဆိတ် အကောင့်ပြောင်းမည့်အစား ဇာတိအလှည့်တွင် ချိတ်ထားသည့် အကောင့်မှလွဲ၍ အခြားရပ်တန့်မှုများ၊

ပြင်ဆင်သတ်မှတ်ထားသော ဦးစားပေးများသည် အကောင့်-သတိပြုမိသော အော်တိုလမ်းကြောင်းကို အသုံးပြုသည်- unbound context-cache၊ smart-pipeline၊ chaos နှင့် shadow shortcuts များကို ပေးပို့ခြင်းမပြုပါ။ ဤတောင်းဆိုမှုများအတွက် မှန်းဆငွေချေးခြင်းအား ပိတ်ထားသောကြောင့် ကြိုတင်စာရင်းများ နှစ်သက်ရာများကို ယှဉ်ပြိုင်၍မရပါ။ အခြားပေါင်းစပ်နည်းဗျူဟာများသည် ဤဆက်တင်ကို အဓိပ္ပါယ်မဖော်ပါ။ အော်တိုနှင့်ဝေးသော ပေါင်းစပ်တစ်ခုကို ပြောင်းခြင်းက နောက်ပိုင်းတွင် ခလုတ်တစ်ခုအတွက် သိမ်းဆည်းထားသော စိတ်ကြိုက်များကို သိမ်းထားမည်ဖြစ်သည်။

## အမှန်တကယ်ရှိသော Model Id နှင့် ကိုက်ညီသည့် Combo အမည်များ

`name` သည် bare model id တစ်ခုနှင့် တူညီနေသော combo (ဥပမာ `gpt-5.5` ဟု အမည်ပေးထားသည့် combo) သည် bug မဟုတ်ဘဲ **ရည်ရွယ်ချက်ရှိရှိ ပံ့ပိုးထားသော ပုံစံတစ်ခု** ဖြစ်သည်။ ၎င်းသည် [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) တွင် မှတ်တမ်းတင်ထားသည့် model-id တစ်ခုချင်းအလိုက် provider fallback ပြုလုပ်ရန် ယန္တရားဖြစ်သည်။ Bare-model-id resolution မတိုင်မီ combo resolution ကို စစ်ဆေးသောကြောင့် (`src/sse/services/model.ts` ရှိ `getComboForModel()`) bare id `gpt-5.5` အတွက် request ကို provider တစ်ခုတည်းထံ တိုက်ရိုက်ပို့မည့်အစား combo ၏ targets များ (ဥပမာ `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) မှတစ်ဆင့် route လုပ်သည် — ဤလုပ်ဆောင်ချက်သည် [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) အတွက် တည်ဆောက်ထားသော combo-before-rewrite ဦးစားပေးအစီအစဉ်ကို ပြန်လည်အသုံးပြုထားပြီး `tests/unit/responses-combo-resolution-3227.test.ts` နှင့် `tests/unit/combo-name-codex-responses-rewrite.test.ts` တို့ဖြင့် regression test ပြုလုပ်ထားသည်။

အမှန်တကယ်ရှိသော model id ကို ဖုံးကွယ်သည့် အမည်တစ်ခုဖြင့် combo ဖန်တီးခြင်း သို့မဟုတ် အမည်ပြောင်းခြင်းကို **မည်သည့်အခါမျှ ငြင်းပယ်မည်မဟုတ်ပါ** — ထိုသို့ပြုလုပ်ပါက မှတ်တမ်းတင်ထားသော ဤ workflow ကို ပျက်စီးစေမည်ဖြစ်သည်။ ထိုအစား (#8530)၊ (အသစ်သတ်မှတ်ထားသော) အမည်သည် အမှန်တကယ်ရှိသော model id နှင့် တိုက်ဆိုင်သည့်အခါ `POST /api/combos` နှင့် `PUT /api/combos/[id]` တို့သည် request ကို ပိတ်ဆို့ခြင်းမရှိသော `warning` field တစ်ခုကို response တွင် ထည့်သွင်းပေးသည်-

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

စနစ်စတင်ချိန်တွင် `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) သည် model id ကို ဖုံးကွယ်နေသည့် လက်ရှိ combo တိုင်းကို စာရင်းပြုစုထားသော တစ်ကြောင်းတည်းပါ `[STARTUP]` သတိပေးချက်ကိုလည်း log လုပ်ပေးသည်။ ထို့ကြောင့် #6940 အရ ရည်ရွယ်ချက်ရှိရှိ ပြုလုပ်ခြင်းမဟုတ်ဘဲ မတော်တဆ ကြုံတွေ့ရသော operator များအတွက် သတိပြုနိုင်သည့် အချက်ပြမှုတစ်ခု ရရှိစေသည်။ Detection helper သည် `src/lib/combos/modelNameCollision.ts` တွင် ရှိသည်။

## Client မှ Custom Combo တစ်ခုကို ခေါ်ယူခြင်း

သိမ်းဆည်းထားသော combo များ (Settings → Combos) ကို client က combo ၏ **အမည်အတိအကျ** ကို `model` field တွင် ပို့သည့်အခါမှသာ အသုံးပြုသည် — combo အမည်အတွက် fuzzy သို့မဟုတ် partial matching မရှိသည့်အပြင် `auto/` prefix လည်း မပါဝင်ပါ။ Resolution အစီအစဉ် (`src/sse/services/model.ts` ရှိ `getComboForModel()`)-

1. combo အမည်နှင့် အတိအကျကိုက်ညီမှု (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)။

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

အဖြစ်များသော သတိပြုရမည့်အချက်နှစ်ခု-

- **`auto` သည် သင့် combo များကို အသုံးမပြုပါ။** `auto`/`auto/*` သည် ၎င်းကိုယ်ပိုင် zero-config candidate pool ကို တည်ဆောက်ပြီး `auto` ဟု အမည်အတိအကျ ပေးထားသည့် combo ရှိမှသာ သိမ်းဆည်းထားသော combo များကို အသုံးပြုသည် (မအကြံပြုပါ)။ Combo မှတစ်ဆင့် route လုပ်ရန် `auto` ကို မပို့ဘဲ ၎င်း၏ အမည်အတိအကျကို ပို့ပါ။
- **`openrouter/auto` သည် အမှန်တကယ်ရှိသော အခပေး OpenRouter product** ("Auto Best Available") ဖြစ်ပြီး OmniRoute alias မဟုတ်ပါ။ ၎င်းသည် OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) ၏ တစ်ခုတည်းသော static model entry ဖြစ်ပြီး သီးခြားငွေတောင်းခံသည်။ ၎င်းကို `auto` pools များမှ ဖယ်ထုတ်ရန် Settings → Routing → Hide paid models ကို အသုံးပြုပါ။

ဤမှတ်တမ်းတွင် ရှင်းလင်းထားသော မူလရှုပ်ထွေးမှုအကြောင်းကို [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) နှင့် [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) တို့တွင် ကြည့်ပါ။

Auto-Combo Engine သည် a ကိုအသုံးပြု၍ တောင်းဆိုမှုတစ်ခုစီအတွက် အကောင်းဆုံး provider/model dynamically ရွေးချယ်သည်။** 16-အချက် အမှတ်ပေး လုပ်ဆောင်ချက်** ( `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` တွင် သတ်မှတ်ထားသည်။ မူရင်းအလေးသည် `1.0` သို့ ပေါင်းလဒ်ဖြစ်သည် ; စိတ်ကြိုက်အလေးချိန်များကို `normalizeScoringWeights()` ဖြင့် ပြန်လည်သတ်မှတ်ထားသည်။ တစ်ဆယ့်ခြောက် — `cacheAffinity` နှင့် `resetWindowAffinity` — နှစ်ခုသည် `0`၏ ပုံသေအလေးချိန်ကို သယ်ဆောင်သည်။ `reliability` `DEFAULT_WEIGHTS` တွင် `0` သယ်ဆောင်သော်လည်း `0.03` generic packs နှင့် `reliability-first` တွင် `0.04` ၊ `quality` `0.02` packs ထဲတွင် သယ်ဆောင်သည် (`0.03` in `quality-first`): ၎င်းတို့ကို ကိုယ်စားလှယ်တိုင်းအတွက် တွက်ချက်နေဆဲဖြစ်ပြီး `cacheAffinity` gates သည် အမှတ်အပြင်ဘက်တွင် prompt-cache deduplication ဖြစ်သောကြောင့် zero-default Factors များသည် ပုံမှန်အားဖြင့် မဲမပေးရပါ။

> **မဖတ်နိုင်သော ခွဲတမ်း (#15347)** ဝန်ဆောင်မှုပေးသူတစ်ဦးတွင် ခွဲတမ်းရယူသူရှိသော်လည်း ၎င်းသည် ဖတ်ရှု၍ရနိုင်သော မည်သည့်အရာကိုမျှ ပြန်မပေးသည့်အခါ (ထုတ်ယူမှုမအောင်မြင်ခြင်း၊ အထောက်အထားများ ပျောက်ဆုံးနေခြင်း၊ မက်ဆေ့ချ်သီးသန့်အသုံးပြုမှု သို့မဟုတ် ခွဲခြမ်းစိပ်ဖြာနိုင်သော `windows` နှင့် `percentUsed: null` အပါအဝင် အကန့်အသတ်မရှိ `percentUsed` မပါသော ပုံမမှန်သော) ယှဉ်ပြိုင်သူက `0` ရမှတ်ကို `quota` ဝင်ရိုးပေါ်တွင် အမှတ်ပေးပြီး ၎င်း၏နောက်ဆုံးရမှတ်သည် `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` နှင့် 5 ( `autoStrategy.ts`) တူညီပါသည်။ ပုံသဏ္ဍာန်ချိတ်ဆက်မှု-အခြေအနေဒါဏ်အဖြစ်။ မအောင်မြင်သောအသုံးပြုမှုဖတ်ခြင်းသည် ပံ့ပိုးပေးသူမဟုတ်ဘဲ telemetry နှင့်ပတ်သက်သော အထောက်အထားဖြစ်သောကြောင့် ၎င်းသည် အတည်ပြုထားသော 100%-used တစ်ခုအပါအဝင် မည်သည့်စစ်မှန်သောဖတ်ရှုမှုအောက်တွင်မဆို တင်းကြပ်စွာ အဆင့်သတ်မှတ်ထားသော်လည်း မည်သည့်အခါမျှ ခက်ခက်ခဲခဲပိတ်ဆို့ခြင်း သို့မဟုတ် နှင်ထုတ်ခြင်းမဟုတ်ပါ။ ဦးထုပ်မပါသော ဝန်ဆောင်မှုပေးသူတစ်ဦးသည် `unlimited: true` နှင့် ရမှတ်များကို ခွဲတမ်းအပြည့်အဖြစ် ဖော်ပြသည်။ စာရင်းသွင်းထားသော quota fetcher မရှိသော ဝန်ဆောင်မှုပေးသူတွင် telemetry အရင်းအမြစ် လုံးဝမရှိသည့်အပြင် `100`၏ ပုံသေကို ထိန်းသိမ်းထားသည်။

**ရလဒ်-** `DEFAULT_WEIGHTS` တွင်ကြေငြာထားသည့်အတိုင်း `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` အသုံးပြုသူ-ပြင်ဆင်ထားသော အလေးချိန်များကို အမှတ်မဖြတ်မီ `normalizeScoringWeights()` ဖြင့် ဖြန့်ဖြူးမှုတစ်ခုအဖြစ် ပြန်လည်သတ်မှတ်ထားသည်။

- **Pack များတွင် `quality` နှင့် `reliability` ပါဝင်သည်** (`quality 0.02`, `quality-first 0.03`; `reliability 0.03`, `reliability-first 0.04`) ဖြစ်ပြီး weight map ကို တစ်ခုလုံး အစားထိုးသည် (`weights = pack` ဖြစ်ပြီး merge မဟုတ်ပါ)။ `DEFAULT_WEIGHTS` တွင် `quality 0.03 / reliability 0` ပါဝင်သည်။ `balanced`/`default` ကို ရွေးချယ်ပါက အဆိုပါ မူလ value များကို ဆက်လက်အသုံးပြုပြီး pack တစ်ခုကို ရွေးချယ်ပါက အထက်ပါ pack ၏ value များကို အသုံးပြုသည်။ Cold pool တစ်ခုတွင် (လေ့လာမှတ်တမ်းများ မရှိသေးသဖြင့် `quality 0.5` နှင့် `reliability 1` ဖြစ်နေချိန်) ဤအချက်နှစ်ခုသည် သာမန် pack တစ်ခုအောက်တွင် `+0.04` (`0.03 + 0.01`)၊ `quality-first` အောက်တွင် `+0.045` နှင့် `reliability-first` အောက်တွင် `+0.05` ထပ်ပေါင်းပေးသည်။
- `tierAffinity`, `specificityMatch` နှင့် `resetWindowAffinity` တို့ကို pack အားလုံးတွင် `0` ဟု အတိအလင်း သတ်မှတ်ထားသည်။
- Pack တစ်ခုစီ၏ အဓိကဦးစားပေးမှုကို အကျဉ်းချုပ်ကြည့်လျှင်:
  - **ship-fast** → latencyInv 0.3048 + health 0.2667 (latency နည်းပြီး အခြေအနေကောင်းသော connection များ)
  - **cost-saver** → costInv 0.3324 (စျေးအသက်သာဆုံး token များကို ရွေးချယ်သည်)
  - **quality-first** → taskFit 0.3524 + stability 0.1429 + quality 0.03၊ pack အားလုံးအနက် အမြင့်ဆုံးဖြစ်သည် (လုပ်ငန်းအတွက် အသင့်တော်ဆုံးနှင့် တသမတ်တည်းရှိသော model)
  - **offline-friendly** → quota 0.3324 + health 0.2667 (အမြန်နှုန်း/ကုန်ကျစရိတ်ကို မစဉ်းစားဘဲ အများဆုံး headroom)
  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04၊ pack အားလုံးအနက် အမြင့်ဆုံးဖြစ်သည် (မမျှော်လင့်ထားသော အခြေအနေ အနည်းဆုံး)
  - **chaos-mode** → health 0.4000 + taskFit 0.1905 (`auto/chaos` weight pack က ၎င်း၏ panel member များအတွက် သတ်မှတ်ပေးထားသည့် weight ဖြစ်သည်။ Parallel fan-out သည် ဤ weight များကို မဖတ်သည့်အပြင် ၎င်းသည် fault-injection profile တစ်ခုလည်း မဟုတ်ပါ၊ [CHAOS-MODE.md](../guides/CHAOS-MODE.md#autochaos-parallel-fan-out) ကို ကြည့်ပါ)

### `weighted` ဝေါဟာရ

`weighted` သည် a** တောင်းဆိုမှုအလိုက် အချိုးကျကျပန်းဆွဲပါ။** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`) ချေပခြင်းမဟုတ်ပါ

- တောင်းဆိုမှုတိုင်းက ဆွဲတယ်။** တစ်ခု** ဖြစ်နိုင်ခြေ `weight / totalWeight` နှင့် အဆင့် ကျန်အဆင့်များကို ထိုတောင်းဆိုချက်အတွက် ကျောရိုးကွင်းဆက်အဖြစ် အလေးချိန်အနိမ့်ဆင်းဖြင့် အမိန့်ပေးသည်။
- `0` အလေးချိန် (သို့မဟုတ်ပျောက်ဆုံးနေသည်) ၏ခြေလှမ်း** ဘယ်တော့မှ မဆွဲဘူး။** အခြားအဆင့်တစ်ဆင့်တွင် > 0 — အလေးချိန်ရှိသော်လည်း ဆွဲသည့်အဆင့်မအောင်မြင်ပြီးနောက်တွင် ဆုတ်ကိုင်မှုအဖြစ်သာ လုပ်ဆောင်နိုင်သည်။ အခါသာ** အားလုံး** အလေးချိန်များသည် ၀တ်စုံသည် ရွေးချယ်မှု တူညီသည်။
- — ပံ့ပိုးပေးသူ circuit breaker `OPEN`၊ ချိတ်ဆက်မှု cooldown ၊ model လော့ခ်ချခြင်း — အားလုံးကို မရရှိနိုင်သည့်အဆင့်များ (`open-sse/services/combo/targetResolution.ts`) မဖြစ်ပေါ်မီ မဲနှိုက်ခြင်းမှ ဖယ်ရှားလိုက်သောကြောင့် ကျန်းမာသောအဆင့်တစ်ခုသည် တောင်းဆိုမှုတိုင်းကို ယာယီအနိုင်ရနိုင်သည်။
- `stickyWeightedLimit` (combo config၊ default `1` = off) သည် ပြန်လည်မဆွဲမီ ဆက်တိုက်အောင်မြင်မှုများအတွက် ရေးဆွဲထားသော အဆင့်ကို ပင်ထိုးထားသည်။

တင်းကျပ်သောလည်ပတ်မှုအတွက် `round-robin` အသုံးပြုပါ။ `weighted` ပေါ်ရှိ တူညီသောအလေးချိန်များသည် ကိန်းဂဏန်း — တင်းကျပ်သော — ချိန်ခွင်လျှာကိုပေးသည် ။

### အေးဂျင့်ပိုက်လိုင်းမုဒ်

အနည်းဆုံးမော်ဒယ်နှစ်ခုပါသော `pipeline` ပေါင်းစပ်မှုတစ်ခုသည် planner/executor လမ်းကြောင်းကို `config.agenticOrchestration.enabled` ဖြင့် ရွေးချယ်နိုင်သည်။ ပထမပစ်မှတ်သည် အစီအစဉ်ဆွဲခြင်းနှင့် နောက်ဆုံးအဖြေများကို ပိုင်ဆိုင်သည်။ ဒုတိယပစ်မှတ်သည် client-native tool ခေါ်ဆိုမှုများကို ထုတ်လွှတ်သည်။ OmniRoute တောင်းဆိုမှုပရိုတိုကောမှ တူးလ်-ရလဒ်ဆက်ကြောင်းများကို ရှာဖွေတွေ့ရှိပြီး အခြားကိရိယာဝိုင်းများ လိုအပ်ခြင်းရှိမရှိ စီစဉ်သူကိုမေးကာ executor သို့မဟုတ် စီစဉ်သူအား client-facing နောက်ဆုံးအဆင့်အဖြစ် dynamically ပြုလုပ်ပေးသည်။

စိတ်ကြိုက်ရွေးချယ်နိုင်သော `config.agenticOrchestration.contextCompaction` အစီအစဉ်ရေးဆွဲသူ သို့မဟုတ် စီစစ်ရေးမှူးတစ်ဦးစီထံ ပေးပို့ခြင်းမပြုမီ သီးခြား payload ဘတ်ဂျက်ကို အသုံးပြုသည်။ ၎င်းကို အတိအလင်း ဖွင့်ပါ-

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

၎င်းတို့သည် အော်ပရေတာမှ ရွေးချယ်ထားသော နံပါတ်စဉ်အလိုက် JSON စာလုံးဘတ်ဂျက်များဖြစ်သည်၊ တိုကင်အကြောင်းအရာပြတင်းပေါက်များ သို့မဟုတ် အာမခံထားသော ရေစီးကြောင်းကန့်သတ်ချက်များ မဟုတ်ပါ။ မော်ဒယ်အတိအကျ IDs သည် မူရင်းကို ထပ်ရေးသည်။ ကန့်သတ်ချက်ထက်၊ ကြိတ်ခွဲခြင်းသည် တူညီသော တူးလ်အဓိပ္ပါယ်ဖွင့်ဆိုချက်များကို ဖယ်ရှားပေးသည်၊ အရွယ်အစားကြီးသော ကိရိယာအထောက်အထားများကို အချေအတင်ဖြင့် ဖြတ်တောက်ကာ ပစ်မှတ်အချိုးဆီသို့ ဦးတည်သည့် အချိုးအစားဆီသို့ ပြီးပြည့်စုံသော သမိုင်းအုပ်စုဟောင်းများကို ဖယ်ရှားသည်။ ၎င်းသည် system/developer လမ်းညွှန်ချက်များ၊ နောက်ဆုံးအသုံးပြုသူတောင်းဆိုချက်၊ အပြိုင် calls/results နှင့် Gemini၏ ဦးဆောင်လမ်းကြောင်းလမ်းညွှန်အပါအဝင် နောက်ဆုံးတူးလ်ဝိုင်းကို ထိန်းသိမ်းထားသည်။ ထိပ်တန်းအဆင့် ညွှန်ကြားချက်များနှင့် ကိရိယာဆက်တင်များကို ထိန်းသိမ်းထားသည်။ ပျက်ကွက်မှု အမှတ်အသားတစ်ခုသည် ဖယ်ရှားထားသော မှတ်တမ်းကို မှတ်တမ်းတင်သည်။ ၎င်းသည် အဆုံးအဖြတ်ဖြတ်တောက်ခြင်းဖြစ်ပြီး ဝေါဟာရအကျဉ်းချုပ်မဟုတ်ပါ။ ပင်ထိုးထားသော အကြောင်းအရာသည် ဘတ်ဂျက်ထက် ကျော်လွန်နေပါက၊ တောင်းဆိုချက်သည် မော်ဒယ်ကို မဆက်သွယ်မီ 413 ကို ပြန်ပေးသည်။ ကျဉ်းမြောင်းမှုကို ပိတ်ထားသည် သို့မဟုတ် သတ်မှတ်ချက်ဘောင်အောက်တွင် တောင်းဆိုချက်သည် မပြောင်းလဲဘဲ ဖြတ်သန်းသွားပါသည်။

On tool-result continuations, OmniRoute also stops execution when two consecutive completed rounds repeat the same tool calls with unchanged results, or when every explicitly marked result in two consecutive rounds failed. Changed results permit repeated calls (for example, polling). The guard resets on a fresh user request, groups parallel calls into one round, and supports Anthropic, Chat Completions, Responses and Gemini histories. The planner receives the reason and owns the final answer even if it requests another tool round.

ဒုတိယပစ်မှတ်ပြီးနောက် ထပ်လောင်းမော်ဒယ်များသည် executor အရန်များကို အမိန့်ပေးသည်။ မအောင်မြင်သော HTTP တုံ့ပြန်မှု သို့မဟုတ် သယ်ယူပို့ဆောင်ရေး ခြွင်းချက်တစ်ခုသည် တူညီသော အစီအစဉ်ရေးဆွဲသူ၏ ဆုံးဖြတ်ချက်နှင့် မူရင်းကိရိယာများကို သယ်ဆောင်သွားသော်လည်း အဆိုပါ executor ၏ကိုယ်ပိုင်ခြေလှမ်းဖြင့် အချက်ပြပြီး ချိတ်ဆက်မှုကို ဖြေရှင်းပြီးသည့်နောက် executor သို့ ရောက်ရှိလာပါသည်။ SSE streaming အပါအဝင် ပထမဆုံးအောင်မြင်သောတုံ့ပြန်မှုကို မပြောင်းလဲဘဲ ပြန်ပေးပါသည်။ အောင်မြင်သော ထုတ်လွှင့်မှုစတင်ပြီးနောက် ပျက်ကွက်မှုများကို ဤနေရာတွင် ပြန်ကြည့်၍မရပါ။ စီစစ်ရေးမှူးများအားလုံး ပျက်ကွက်ပါက နောက်ဆုံးကျရှုံးမှုကို ပြန်လည်ရရှိမည်ဖြစ်သည်။ ဖောက်သည် ပျက်သွားသည် ပေးပို့ခြင်းကို ရပ်လိုက်သည် ။

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

executor သည် တုံ့ပြန်မှုတစ်ခုတွင် သီးခြားလွတ်လပ်သောခေါ်ဆိုမှုများစွာကို ထုတ်လွှတ်နိုင်သည်။ အစီအစဉ်ရေးဆွဲသူမှ ရလဒ်တိုင်းကို ပြန်လည်သုံးသပ်ခြင်းဖြင့် နောက်ပိုင်းတွင် အသုံးပြုသူ ကိရိယာ-ရလဒ်အလှည့်တွင် မှီခိုခေါ်ဆိုမှုများကို ကိုင်တွယ်ဆောင်ရွက်ပါသည်။ `maxToolRounds` `8` သို့ ပုံသေသတ်မှတ်ထားပြီး `1`–`32` ကို လက်ခံသည်။ ပြီးသည်နှင့်၊ အစီအစဉ်ရေးဆွဲသူသည် အကောင်းဆုံးရရှိနိုင်သော နောက်ဆုံးအဖြေကို ထုတ်ပြန်ရမည်ဖြစ်သည်။ ရွေးချယ်ထားသော ကလိုင်းယင့်ရင်ဆိုင်သည့် တုံ့ပြန်မှုသည် မူရင်း တိုက်ရိုက်ထုတ်လွှင့်မှု ဦးစားပေးမှုကို ထိန်းသိမ်းထားသော်လည်း အတွင်းပိုင်း အစီအစဉ်ရေးဆွဲသူ ဆုံးဖြတ်ချက်များ ဖြတ်တောက်ထားသည်။

### `round-robin` စေးကပ်သောအသုတ်နှင့် အကောင့်ချဲ့ထွင်ခြင်း။

Round-robin ကို တစ်စုတစ်စည်းတည်း မဟုတ်ဘဲ တစ်လှမ်းချင်း တောင်းဆိုသည်-

- `stickyRoundRobinLimit` (combo config၊ ထို့နောက် `comboStickyRoundRobinLimit`၊ ထို့နောက် `settings.stickyRoundRobinLimit`၊ မူရင်း** ၃** ) အလှည့်မရောက်မီ ထိုဆက်တိုက်အောင်မြင်မှုများအတွက် တူညီသောပစ်မှတ်ကို ထားရှိပါ။ တောင်းဆိုချက်တစ်ခု လည်ပတ်မှုအတွက် ပေါင်းစပ်မှုအား `1` သို့ သတ်မှတ်ပါ။ ပေါင်းစပ်တည်းဖြတ်သူသည် ထိရောက်သောတန်ဖိုးနှင့် မည်သည့်အလွှာမှ ထွက်လာသည်ကို ပြသသည်။
- `connectionAwareExpansion` (combo config၊ ထို့နောက် ဆက်တင်များ၊ မူရင်း** အတုအယောင်** ) လည်ပတ်ခြင်းမပြုမီ ပံ့ပိုးပေးသူအဆင့်အဆင့်တစ်ခုစီကို အကောင့်တစ်ခုချင်းပစ်မှတ်များသို့ ချဲ့ထွင်သည်။ Group-B ဗျူဟာများ (ဦးစားပေး၊ အလေးချိန်၊ အလှည့်ကျ၊ ကျပန်း၊ p2c၊ အသုံးအနည်းဆုံး၊ ကုန်ကျစရိတ်-အကောင်းဆုံးဖြစ်အောင်၊ lkgp၊ ပထမဆုံး၊ တင်းကျပ်သောကျပန်း၊ ဆက်စပ်-ပိုကောင်းအောင်၊ ကက်ရှ်-ပိုကောင်းအောင်ပြုလုပ်ထားသော၊ context-relay၊ ပေါင်းစည်းမှု၊ ပိုက်လိုင်း၊ jev) တို့ကို မဖွင့်မချင်း ပံ့ပိုးသူအဆင့်မြင်ကွင်းကို ထားရှိပါ။ ပေါင်းစပ်အယ်ဒီတာသည် အမွေဆက်ခံ/ဖွင့်/ပိတ် ဖော်ထုတ်ပေးသည်။ inherit သည် global default (off) ကိုအသုံးပြုသည်။
- Prompt-cache တည်နေရာလမ်းကြောင်း (`promptCacheAffinityEnabled`၊ မူရင်း** အမှန်** ) ပင်ချိတ်ထားသော ချိတ်ဆက်မှုများကို ပြန်လည်မှာယူသည် ထို့ကြောင့် ကိုက်ညီသော ကက်ရှ်ကီးများကို အကောင့်တစ်ခုတည်းတွင် ဆက်လက်ထားရှိပါ။ ပင်ထိုးထားသောအကောင့်တစ်ခုခြင်းစီအဆင့်များတစ်လျှောက် အဝိုင်းစက်နှင့် အလေးချိန်လှည့်ပတ်မှုတို့ထက် သာလွန်သည်။ တင်းကျပ်သောလည်ပတ်မှုလိုအပ်ပါက ဆက်တင်များ → Combo ပုံသေများအောက်တွင် ၎င်းကိုပိတ်ပါ။ ပေါင်းစည်းမှုတစ်ခုချင်း ထပ်ရေးခြင်း မရှိပါ။

မော်ဒယ်တစ်ခုတွင် အကောင့်ပေါင်းများစွာလှည့်ခြင်းအတွက်၊ ပိုကြိုက်သည်။** dynamic-account အဆင့်တစ်ခု** (ဗလာ `connectionId`၊ ရေကန်တစ်ခုလုံး) ကပ်စေးနဲသောကန့်သတ်ချက် `1`၊ ချိတ်ထားသော `connectionId` s သုံးခုမဟုတ်ပါ။ RR ကောင်တာ တိုးတက်လာနေချိန်တွင်ပင် ပင်ထိုးထားသည့် အဆင့်များ နှင့် ရင်းနှီးမှု တူညီသော အကောင့်ပေါ်သို့ ပြိုကျသွားသည်။

## Fusion မဟာဗျူဟာ

`fusion` သည် ပစ်မှတ်တစ်ခုတည်းကို **မရွေးချယ်သည့်** တစ်ခုတည်းသော မဟာဗျူဟာဖြစ်သည်။ ၎င်းသည် prompt ကို
**panel model အားလုံးထံ တစ်ပြိုင်နက်တည်း** ဖြန့်ပို့ပြီးနောက် ပြင်ဆင်သတ်မှတ်နိုင်သော **judge model** က
panel တုံ့ပြန်ချက်အားလုံးမှ နောက်ဆုံးအဖြေတစ်ခုတည်းကို ပေါင်းစပ်ထုတ်ပေးသည်။ မူရင်း `decolua/9router`
(OpenRouter ၏ Fusion ဒီဇိုင်း) မှ ပြောင်းရွှေ့ယူထားပြီး အကောင်အထည်ဖော်မှုမှာ `open-sse/services/fusion.ts` တွင်ရှိသည်။

အလုပ်လုပ်ပုံ-

0. **Tool ပါဝင်သော တောင်းဆိုမှုကို ကျော်လွှားခြင်း** — အလွတ်မဟုတ်သော `tools` array ပါဝင်ပြီး
   `tool_choice` ကို `"none"` ဟု တိတိကျကျ မသတ်မှတ်ထားသော တောင်းဆိုမှုသည် panel ကို လုံးဝကျော်သွားသည်။ ၎င်းကို
   model တစ်ခုတည်း (ပြင်ဆင်သတ်မှတ်ထားသော judge သို့မဟုတ် `panel[0]`) ထံသို့ `tools`/`tool_choice`
   ကို မပြောင်းလဲဘဲ တိုက်ရိုက်လမ်းကြောင်းပေးသည်။ Panel အဖွဲ့ဝင်များသည် tool အသုံးပြုခွင့်မရှိသည့်အပြင် judge ၏
   ပေါင်းစပ်ရေးသားမှု ညွှန်ကြားချက်က tool-call ထုတ်လွှတ်ခြင်းကို အားမပေးသောကြောင့် agentic/tool-calling client များသည်
   ပေါင်းစပ်ရေးသားထားသော စာသားအစား တကယ့် tool-call ဆုံးဖြတ်ချက်ကို ရရှိသည် (#6771)။
1. **ဖြန့်ခွဲပို့ခြင်း** (tool မပါသော တောင်းဆိုမှုများသာ) — prompt ကို panel
   model အားလုံးထံ တစ်ပြိုင်နက်တည်း ပို့ပြီး tools များကို ဖယ်ရှားကာ non-streaming ဖြစ်ရန် အတင်းသတ်မှတ်သည် (judge သည်
   ပေါင်းစပ်ရေးသားရန် စာသားအပြည့်အစုံ လိုအပ်သည်)။
2. **Quorum-grace စုဆောင်းခြင်း** — `minPanel` အဖြေများ ရောက်လာသည်နှင့် ကျန်နေသူများအတွက်
   grace timer အတိုတစ်ခု စတင်ပြီးနောက် ရရှိစုဆောင်းထားသမျှဖြင့် fusion ကို ဆက်လက်လုပ်ဆောင်သည်။
   ဤနည်းဖြင့် အနှေးဆုံး model ကြောင့် wall time တွင် ဖြစ်ပေါ်သော နှောင့်နှေးမှုကို ကန့်သတ်ပေးပြီး hard timeout ဖြင့် အမြင့်ဆုံးကန့်သတ်ထားသည်။
3. **Judge ဖြင့် ပေါင်းစပ်ရေးသားခြင်း** — panel အဖြေများကို အမည်မဖော်ဘဲ (`Source 1`, `Source 2`, … — ထို့ကြောင့်
   judge သည် model အမှတ်တံဆိပ်မဟုတ်ဘဲ အကြောင်းအရာကို အလေးထားသည်) judge ထံ လွှဲပေးသည်။ ထို့နောက် judge က
   သဘောတူညီချက် / ဆန့်ကျင်ကွဲလွဲချက်များ / တစ်စိတ်တစ်ပိုင်းသာ ခြုံငုံမိမှု / ထူးခြားသော ထိုးထွင်းသိမြင်မှုများ / မမြင်မိသော အချက်များကို ခွဲခြမ်းစိတ်ဖြာပြီး
   ယုံကြည်အားထားရသော အဖြေ **တစ်ခုတည်း** ကို ရေးသားသည်။ Judge call သည် client ၏ မူလ
   `stream` flag နှင့် tools များကို ဆက်လက်ထိန်းသိမ်းထားသောကြောင့် streaming နှင့် downstream tool အသုံးပြုမှုတို့ ဆက်လက်အလုပ်လုပ်သည်။
4. **ချောမွေ့စွာ အဆင့်လျှော့လုပ်ဆောင်ခြင်း** — panel အဖြေ 0 ခု → `503`; အဖြေ 1 ခုတည်းသာ ကျန်ရှိခြင်း → ထိုအဖြေကို
   တိုက်ရိုက်ပြန်ပေးသည် (ပေါင်းစပ်စရာမရှိပါ); model တစ်ခုတည်းပါသော panel သည် တိုက်ရိုက်ဖြေဆိုသည်။

Panel အဖွဲ့ဝင်တစ်ခုသည် အခြား combo ကို ရည်ညွှန်းသော `combo-ref` အဆင့် (`{kind: "combo-ref", comboName: "..."}`) လည်း ဖြစ်နိုင်သည် —
၎င်းကို **black-box panel အသံတစ်ခုတည်း** အဖြစ် ဖြေရှင်းသည် (ရည်ညွှန်းထားသော combo သို့ အပြည့်အဝ recursive dispatch လုပ်ခြင်းဖြစ်ပြီး
ထို combo ၏ ကိုယ်ပိုင်ပစ်မှတ်များကို ဖြန့်ခွဲပို့ခြင်းမဟုတ်ပါ)။ ထို့ပြင် အခြား combo-ref အသုံးပြုသည့် မဟာဗျူဟာတိုင်းတွင် ရှိပြီးသား
တူညီသော depth/cycle ကာကွယ်မှုကို အသုံးပြုသည် (#6764)။

### ပြင်ဆင်သတ်မှတ်မှု

Combo ၏ `config` blob တွင် ပြင်ဆင်သတ်မှတ်သည် (schema migration မလိုအပ်ပါ — ရှိပြီးသား
`combos` table ကို ပြန်လည်အသုံးပြုသည်)-

| Field                                    | Type     | Default         | Purpose                                                                                                |
| :--------------------------------------- | :------- | :-------------- | :----------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ပထမ panel model | နောက်ဆုံးအဖြေကို ပေါင်းစပ်ရေးသားသည့် model                                                             |
| `config.fusionTuning.minPanel`           | `number` | `2`             | grace timer မစတင်မီ လိုအပ်သော အောင်မြင်သည့်အဖြေ အရေအတွက် (`[2, panelSize]` အတွင်း ကန့်သတ်ထားသည်)       |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`          | quorum ပြည့်ပြီးနောက် နောက်ကျနေသူများကို စောင့်ဆိုင်းမည့်ကြာချိန်                                      |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`         | model တစ်ခု ရပ်တန့်နေခြင်းကြောင့် တောင်းဆိုမှု တစ်ခုလုံး မနှောင့်နှေးစေရန် အကြွင်းမဲ့အချိန်ကန့်သတ်ချက် |

မူလတန်ဖိုးများကို `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) တွင် ထည့်သွင်းထားသည်။

### ဥပမာ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

ထို့နောက် မည်သည့် combo ကိုမဆို ခေါ်သကဲ့သို့ ၎င်းကို ခေါ်ပါ- `{"model":"fusion-panel","messages":[...]}`။

## Virtual Auto-Combo Factory

Auto Combo အင်ဂျင်သည် ကြိုတင်သတ်မှတ်ထားသော combo များကို မလိုအပ်ပါ။ ယင်းအစား `open-sse/services/autoCombo/virtualFactory.ts` သည် candidate များကို လိုအပ်သည့်အချိန်တွင် ချက်ချင်းတည်ဆောက်သည်-

1. `getProviderConnections({ isActive: true })` (ဖွင့်ထားသော connection အားလုံး) ကို ရယူသည်
2. မှန်ကန်သော credential များရှိသည့် connection များကို စစ်ထုတ်သည် (API key သို့မဟုတ် `hasUsableOAuthToken()` မှတစ်ဆင့် သက်တမ်းမကုန်သေးသော OAuth token)
3. Model ရရှိနိုင်မှုနှင့် ဈေးနှုန်းအတွက် `getProviderRegistry()` နှင့် အပြန်အလှန်တိုက်ဆိုင်စစ်ဆေးသည်
4. `(provider, model, connection)` tuple တစ်ခုစီအတွက် `VirtualAutoComboCandidate` တစ်ခု တည်ဆောက်သည်
5. Dispatch target အဖြစ် `connection.defaultModel` (သို့မဟုတ် registry ၏ ပထမဆုံး model) ကို ရွေးချယ်သည်
6. 16-factor `scorePool()` နှင့် variant ၏ weight pack ကို အသုံးပြု၍ candidate တစ်ခုစီကို အမှတ်ပေးသည်
7. `handleComboChat()` အတွက် ရရှိလာသော memory အတွင်းရှိ `AutoComboConfig` ကို ပြန်ပေးသည် — DB ထဲသို့ မည်သည့်အခါမျှ သိမ်းဆည်းထားခြင်းမရှိပါ

ဆိုလိုသည်မှာ **`auto/*` ဖွင့်ထားသော provider အသစ်တစ်ခုကို ထည့်သွင်းခြင်းသည် candidate pool ကို အလိုအလျောက်ချဲ့ထွင်ပေးသည်** — combo ကို ကိုယ်တိုင်ပြင်ဆင်ရန် မလိုအပ်ပါ။ Virtual combo ကို request တစ်ခုစီအတွက် ပြန်လည်တည်ဆောက်သောကြောင့် အသစ်ထည့်ထားသော သို့မဟုတ် ပြန်လည်ကျန်းမာလာသော connection များကို ချက်ချင်းရွေးချယ်နိုင်သည်။

## ကိုယ်တိုင်ပြန်လည်ပြုပြင်ခြင်း

- **ယာယီဖယ်ထုတ်ခြင်း**: Score < 0.2 → 5 min ကြာ ဖယ်ထုတ်မည် (တဖြည်းဖြည်းတိုးလာသော backoff၊ အများဆုံး 30 min)
- **Circuit breaker အခြေအနေကို သိရှိခြင်း**: OPEN → အလိုအလျောက်ဖယ်ထုတ်မည်၊ HALF_OPEN → စမ်းသပ် request များ
- **Incident mode**: >50% OPEN → exploration ကို ပိတ်ပြီး တည်ငြိမ်မှုကို အမြင့်ဆုံးဖြစ်စေမည်
- **Cooldown ပြီးနောက် ပြန်လည်ကောင်းမွန်ခြင်း**: ဖယ်ထုတ်မှုအပြီး ပထမဆုံး request သည် timeout လျှော့ထားသော "probe" တစ်ခုဖြစ်သည်

## Bandit Exploration

Request များ၏ 5% (ပြင်ဆင်သတ်မှတ်နိုင်သည်) ကို exploration အတွက် ကျပန်း provider များထံ လမ်းကြောင်းပြောင်းပို့သည်။ Incident mode တွင် ပိတ်ထားသည်။

## API

**သီးသန့် `POST /api/combos/auto` endpoint မရှိပါ** — Auto-Combo ကို နည်းလမ်းနှစ်မျိုးဖြင့် အသုံးပြုနိုင်သည်-

1. **ပြင်ဆင်သတ်မှတ်မှုမလို (အကြံပြုထားသည်)-** `model: "auto"` သို့မဟုတ် `model: "auto/<variant>"` ပါဝင်သော မည်သည့် chat completion request ကိုမဆို ပေးပို့ပါ။ Virtual factory သည် request တစ်ခုချင်းစီအတွက် combo ကို တည်ဆောက်ပေးသည် — အမြဲတမ်းသိမ်းဆည်းထားရန်မလိုသလို API call များလည်း မလိုအပ်ပါ။

2. **`strategy: "auto"` ဖြင့် အမြဲတမ်းသိမ်းဆည်းထားသော combo-** `POST /api/combos` မှတစ်ဆင့် ပုံမှန် combo တစ်ခုဖန်တီးပြီး `strategy: "auto"` နှင့်အတူ `config.auto.weights` / `config.auto.candidatePool` ကို သတ်မှတ်ပါ။ တူညီသော scoring engine ကို အသုံးပြုမည်ဖြစ်ပြီး combo ကို `combos` ထဲတွင် သိမ်းဆည်းကာ ID ဖြင့် ပြန်လည်အသုံးပြုနိုင်သည်။

ရှာဖွေကြည့်ရှုရန် `GET /api/combos/auto` သည် variant အားလုံးကို ၎င်းတို့၏ ဖြေရှင်းသတ်မှတ်ပြီးသော candidate pool နှင့်အတူ `context_length` / `max_output_tokens` တို့ဖြင့် စာရင်းပြုစုပေးသည် — ၎င်းတို့သည် candidate pool အတွင်းရှိ context window များထဲမှ အများဆုံးတန်ဖိုးဖြစ်သည်။ Client များ (ဥပမာ opencode plugin) သည် `0` အစား ဤတန်ဖိုးများကို အသိပေးကြေညာရမည်။ Context သုညဖြစ်ပါက opencode ၏ အလိုအလျောက်ချုံ့ခြင်းကို လုံးဝပိတ်ပစ်ပြီး gateway ၏ history purge က context ကို ဖျက်ဆီးသည့်အထိ session များကို ကြီးထွားခွင့်ပြုထားမည်ဖြစ်သည်။ Auto-combo ၏ context pre-filter က အရွယ်အစားကျော်လွန်သော request များကို context window ကြီးသည့် candidate များထံ route လုပ်ပေးသောကြောင့် အများဆုံးတန်ဖိုးကို အသိပေးကြေညာခြင်းသည် ဘေးကင်းသည်။

```bash
# ပြင်ဆင်သတ်မှတ်မှုမလိုဘဲ အသုံးပြုခြင်း (combo ဖန်တီးရန်မလို)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ပုံမှန် combos endpoint မှတစ်ဆင့် အမြဲတမ်းသိမ်းဆည်းထားသော auto combo
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router မဟာဗျူဟာများ

အမြဲတမ်းသိမ်းဆည်းထားသော `strategy: "auto"` combo များသည် `config.routerStrategy` (သို့မဟုတ် အဟောင်းပုံစံ
`config.auto.routerStrategy`) ကို အောက်ပါတို့ထဲမှ တစ်ခုအဖြစ် သတ်မှတ်နိုင်သည်-

- `rules` — မူလ weighted scoring
- `score` — ပြင်ဆင်သတ်မှတ်ထားသည့် weighted score အမြင့်ဆုံးကို ရွေးချယ်သည်။ Score အတိအကျတူညီပါက ပြင်ဆင်သတ်မှတ်ထားသည့်
  candidate အစဉ်ကို ထိန်းသိမ်းထားပြီး လက်ရှိ `explorationRate` သည် အဆင့်စီထားသော pool အပြည့်အစုံမှ နမူနာရွေးချယ်သည်။
- `cost` / `eco` — ကျန်းမာရေးကောင်းမွန်သည့် provider များအနက် စရိတ်အနည်းဆုံး
- `latency` / `fast` — ယုံကြည်စိတ်ချရမှု penalty ပါဝင်သော အနိမ့်ဆုံး p95 latency
- `sla-aware` / `sla` — p95 latency၊ error rate နှင့် ထည့်သွင်းနိုင်သည့်
  cost SLO များကို ဖြည့်ဆည်းသော candidate များကို ဦးစားပေးသည်
- `lkgp` — နောက်ဆုံးကောင်းမွန်ခဲ့ကြောင်း သိရှိထားသော provider ကို ဦးစွာရွေးချယ်သည်
- `nadir` — pool ထဲရှိ မည်သည့် model ကို prompt က လိုအပ်ကြောင်း [Nadir](https://getnadir.com) ၏ ဆုံးဖြတ်ချက် API ကို
  မေးမြန်းသည်။ ကိုယ်တိုင်ဖွင့်သုံးရပြီး မအောင်မြင်ပါက `rules` သို့ ပြန်သွားသည်

### Router မဟာဗျူဟာများ၏ အသေးစိတ်

Auto-combo engine တွင် `config.routerStrategy` (သို့မဟုတ် အဟောင်းပုံစံ `config.auto.routerStrategy`) မှတစ်ဆင့်
အစားထိုးအသုံးပြုနိုင်သော ပေါင်းစပ်တပ်ဆင်နိုင်သည့် **RouterStrategy** implementation ၇ ခု ပါဝင်သည်။
မဟာဗျူဟာတစ်ခုစီသည် `RoutingContext`
(task အမျိုးအစား၊ tool/vision အချက်ပြမှုများ၊ ခန့်မှန်း token အရေအတွက်၊ ထည့်သွင်းနိုင်သည့် SLA policy နှင့် ထည့်သွင်းနိုင်သည့်
နောက်ဆုံးကောင်းမွန်ခဲ့ကြောင်း သိရှိထားသော provider) ကို အခြေခံ၍ candidate pool မှ provider တစ်ခုကို ရွေးချယ်သည်။

#### 1. `rules` (မူလ) — အချက် ၁၆ ချက်ပါ weighted scoring

လက်ရှိ scoring engine ကို အထုပ်အပိုးပြုထားသည်။ `OPEN` circuit-breaker ဖြစ်နေသော
candidate များကို စစ်ထုတ်ပြီးနောက် လက်ရှိ task အမျိုးအစားနှင့် `getTaskFitness()` ကို အသုံးပြု၍ `scorePool()` ကို လုပ်ဆောင်ကာ
score အမြင့်ဆုံး provider ကို ရွေးချယ်သည်။

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**- အခြေခံရွေးချယ်မှုဖြစ်သည်။ Signal အားလုံးအကြား ဟန်ချက်ညီသည့် အပေးအယူကို လိုချင်သောအခါ အသုံးပြုပါ။

**အခြားအမည်**- `rules` (အခြားအမည်မရှိ)

---

#### 2. `cost` / `eco` — ကျန်းမာရေးကောင်းမွန်သည့် provider များအနက် စရိတ်အနည်းဆုံး

Candidate pool ကို `costPer1MTokens` အလိုက် (ငယ်စဉ်ကြီးလိုက်) စီပြီး စရိတ်အနည်းဆုံးကို ရွေးချယ်သည်။
`OPEN` ဖြစ်နေသော candidate များကို ဦးစွာ စစ်ထုတ်သည်။

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**- စရိတ်ကို အလေးထားသော workload များ၊ batch processing သို့မဟုတ် နောက်ခံ job များအတွက်။

**အခြားအမည်များ**- `cost`, `eco`

---

#### 3. `latency` / `fast` — ယုံကြည်စိတ်ချရမှု penalty ပါဝင်သော အနိမ့်ဆုံး p95 latency

`p95LatencyMs + (errorRate * 1000)` ဖြင့် စီသည်။ Error rate penalty ကြောင့်
ပုံမှန် latency နည်းသော်လည်း ယုံကြည်စိတ်ချ၍မရသော provider များကို အဆင့်နိမ့်စေသည်။

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**- အချိန်နှင့်တစ်ပြေးညီ chat၊ autocomplete သို့မဟုတ်
အပြန်အလှန်တုံ့ပြန်နိုင်သော coding assistant များကဲ့သို့ latency ကို အလေးထားသည့် workload များအတွက်။

**အခြားအမည်များ**- `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO လိုက်နာမှု

Candidate တစ်ခုစီသည် ပြင်ဆင်သတ်မှတ်ထားသော SLO policy ကို မည်မျှကောင်းမွန်စွာ ဖြည့်ဆည်းနိုင်သည်ဆိုသည့်အပေါ် မူတည်၍ score ပေးသည်-

| အချက်           | အလေးချိန် | ဖော်မြူလာ                                                                  |
| --------------- | --------- | -------------------------------------------------------------------------- |
| Latency ရမှတ်   | 35%       | `threshold / max(value, ε)`                                                |
| Error ရမှတ်     | 35%       | `threshold / max(value, ε)`                                                |
| Health ရမှတ်    | 15%       | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)                          |
| Cost ရမှတ်      | 10%       | `threshold / max(value, ε)` သို့မဟုတ် ပြောင်းပြန် ပုံမှန်ပြုထားသည့်တန်ဖိုး |
| Stability ရမှတ် | 5%        | ပြောင်းပြန် ပုံမှန်ပြုထားသည့် latency စံသွေဖည်မှု                          |

`hardConstraints: true` ဖြစ်သည့်အခါ candidate များကို အဓိကအားဖြင့် **ချိုးဖောက်မှုရမှတ်**
(SLO တစ်ခုခုကို မည်မျှကျော်လွန်သည်ကို တိုင်းတာသည့်ရမှတ်) အလိုက် စီပြီး၊ ထို့နောက် composite ရမှတ်အလိုက် စီသည်။ သို့မဟုတ်ပါက
composite ရမှတ်တစ်ခုတည်းကိုသာ အသုံးပြုသည်။

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // candidate တစ်ခုစီကို မူဝါဒနှင့် နှိုင်းယှဉ်၍ ရမှတ်ပေးသည်: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA field များ** (combo config တွင် သတ်မှတ်ပါ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: latency၊ error-rate သို့မဟုတ် ကုန်ကျစရိတ် budget များကို တင်းကျပ်စွာ သတ်မှတ်ထားသည့် production workload များ။

**Alias များ**: `sla-aware`, `sla`

#### 5. `lkgp` — နောက်ဆုံး အခြေအနေကောင်းခဲ့သည့် provider ကို ဦးစွာအသုံးပြုခြင်း

သတ်မှတ်ထားပါက **နောက်ဆုံး အခြေအနေကောင်းခဲ့သည့် provider** ကို ဦးစွာစမ်းသပ်ပြီး၊ ထို့နောက်
`rules` strategy သို့ fallback လုပ်သည်။ Session stickiness အတွက် အသုံးဝင်ပြီး စကားဝိုင်းတစ်ခုရှိ
နောက်ဆက်တွဲ request များကို တူညီသည့် provider က ကိုင်တွယ်ပေးသည်။

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules strategy သို့ fallback လုပ်သည်
    return getStrategy("rules").select(pool, context);
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: နောက်ဆက်တွဲ request များကို တူညီသည့် provider က
ကိုင်တွယ်ပေးစေလိုသော အလှည့်များစွာပါသည့် စကားဝိုင်းများ (ဥပမာ caching၊ context ဆက်လက်တည်တံ့မှု သို့မဟုတ် ဈေးနှုန်း တသမတ်တည်းဖြစ်မှုအတွက်)။

**Alias**: `lkgp` (အခြား alias မရှိပါ)

#### 6. `nadir` — Nadir မှတစ်ဆင့် prompt ကိုအခြေခံသည့် model ရွေးချယ်မှု

အထက်ပါ strategy တစ်ခုစီသည် candidate များကို ၎င်းတို့၏ telemetry ကိုသာ အခြေခံ၍ အဆင့်သတ်မှတ်ပြီး request ကို မဖတ်ပါ။
`nadir` သည် နောက်ဆုံး user turn နှင့် pool ၏ model id များကို
[Nadir](https://getnadir.com) ၏ decision API (`POST /v1/bucket`) သို့ ပေးပို့ပြီး ထိုစာရင်းထဲမှ Nadir
ရွေးချယ်သည့် model သို့ route လုပ်သည် (`simple` → လိုအပ်ချက်ကို ဖြည့်ဆည်းနိုင်သည့် ဈေးအသက်သာဆုံး model၊ `complex` →
စွမ်းဆောင်ရည်အမြင့်ဆုံး model)။ ထို model ကို ဝန်ဆောင်မှုပေးသည့် connection ကို `rules` က ဆက်လက်ရွေးချယ်သဖြင့် quota၊
health နှင့် ကုန်ကျစရိတ်တို့က မည်သည့် account ကို အသုံးပြုမည်ကို ဆက်လက်ဆုံးဖြတ်ပေးသည်။

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

String နှစ်ခုအတွက် `OMNIROUTE_NADIR_API_KEY` နှင့် `OMNIROUTE_NADIR_BASE_URL` ကို env fallback များအဖြစ် အသုံးပြုသည်။
`baseUrl` သည် self-hosted Nadir အတွက်သာ လိုအပ်သည် (နောက်ဆုံးတွင် `/v1` ပါရှိခြင်းကိုလည်း လက်ခံသည်)။
Key မပါသည့် call များသည် IP တစ်ခုချင်းစီအလိုက် rate limit သတ်မှတ်ထားသော Nadir ၏ anonymous tier သို့ ရောက်ရှိသည်။ Key တစ်ခုရှိပါက
([တစ်ခုဖန်တီးရန်](https://app.getnadir.com/dashboard/api-keys)) decision တစ်ခုစီကို သင်၏ Nadir dashboard တွင်
မှတ်တမ်းတင်ထားမည်။ အပြည့်အစုံ setup ပြုလုပ်ခြင်းနှင့် အတည်ပြုခြင်းအတွက်:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/)။

ပြင်ပသို့ ပေးပို့သည့်အရာများမှာ နောက်ဆုံး user message ၏ စာသား (ပထမဆုံး စာလုံးရေ 16k)၊ candidate
model id များနှင့် `source: "omniroute"` channel tag တို့ဖြစ်သည်။ System prompt၊ history၊ tool သို့မဟုတ်
header များကို မပေးပို့ပါ။

Failure ဖြစ်သည့်အခါ fail-open နည်းလမ်းဖြင့် ဆောင်ရွက်သည်။ timeout (မူလသတ်မှတ်ချက် 2000 ms)၊ non-2xx response၊ ဆက်သွယ်၍မရသည့်
host၊ ပုံစံမမှန်သည့် response သို့မဟုတ် pool ပြင်ပမှ selection တစ်ခု ဖြစ်ပေါ်ပါက `rules`
decision သို့ ပြောင်းလဲပြီး အကြောင်းပြချက်၏ အစတွင် `NadirStrategy: fallback (…)` ကို ထည့်သွင်းသည်။ Call တစ်ခု မအောင်မြင်ပြီးနောက်
strategy သည် network ကို 30 s ကြာ ကျော်သွားမည်ဖြစ်သဖြင့် outage တစ်ခုတွင် request တစ်ခုစီအတွက် timeout ဖြစ်မည့်အစား
30 s တိုင်းတွင် timeout တစ်ကြိမ်သာ ဖြစ်ပေါ်သည်။ Nadir က အမှန်တကယ် ရွေးချယ်မှုပြုလုပ်ခဲ့သည့်အခါမှသာ routing event များက
`strategy: "nadir"` ဟု report လုပ်သည်။

**အသုံးပြုသင့်သည့်အချိန်**: model tier အမျိုးမျိုး (အသေးစား model တစ်ခု၊ အလယ်အလတ် model တစ်ခုနှင့်
စွမ်းဆောင်ရည်အမြင့်ဆုံး model တစ်ခု) ပါဝင်သော pool ပေါ်ရှိ ခက်ခဲမှုအဆင့် မတူညီသည့် traffic များတွင် အမြဲတမ်း စွမ်းဆောင်ရည်အမြင့်ဆုံး model ကို သုံးစွဲခြင်းကြောင့် ဖြစ်ပေါ်သည့် ကုန်ကျစရိတ်ကို လျှော့ချလိုသည့်အခါ။

**Alias**: `nadir` (အခြား alias မရှိပါ)

### စိတ်ကြိုက် router strategy များ

Public API မှတစ်ဆင့် သင့်ကိုယ်ပိုင် `RouterStrategy` implementation ကို register လုပ်နိုင်သည်:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // သင့် routing logic ကို ဤနေရာတွင် ထည့်ပါ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ထို့နောက် အောက်ပါအတိုင်း အသုံးပြုပါ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## လုပ်ဆောင်ချက်နှင့် ကိုက်ညီမှု

လုပ်ဆောင်ချက်အမျိုးအစား 6 မျိုး (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) အလိုက် မော်ဒယ် 30 ကျော်ကို အမှတ်ပေးထားသည်။ Wildcard pattern များကို ပံ့ပိုးသည် (ဥပမာ၊ `*-coder` → coding အမှတ်မြင့်)။

## Auto Variant များ အကျဉ်းချုပ်

မူရင်းဖြစ်သည့် သီးသန့် `auto` နှင့် `autoPrefix.ts` တွင် ကြေညာထားသော `AutoVariant` တန်ဖိုး 6 ခုအပါအဝင်၊ **ခေါ်ယူအသုံးပြုနိုင်သော model ID 7 ခု** ရှိသည်-

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ကိုယ်တိုင်သည် တန်ဖိုး 6 ခုကို စာရင်းပြုထားသည်။ 7 ခုမြောက်ရွေးချယ်စရာမှာ "variant မရှိခြင်း" — သီးသန့် `auto` — ဖြစ်ပြီး `parseAutoPrefix()` က `variant: undefined` အဖြစ် ကိုင်တွယ်သည်။)

## အဆင့်များသည် Auto-Combo နှင့် မည်သို့ ကိုက်ညီသနည်း

အချက် 16 ချက်ပါ အမှတ်ပေးလုပ်ဆောင်ချက် (`open-sse/services/autoCombo/scoring.ts`) သည် အဆင့်အဖွဲ့ဝင်ဖြစ်မှုကို အချက်ပြမှုနှစ်ခုအဖြစ် သတ်မှတ်သည်- `tierPriority` (0.0476) နှင့် `tierAffinity` (0.0476) တို့ဖြစ်သည်။ `DEFAULT_WEIGHTS` အစုအပြည့်အစုံအတွက် အထက်ပါ စံသတ်မှတ်ထားသော [အမှတ်ပေးအချက်ဇယား](#how-it-works-persisted-auto-combos) ကို ကြည့်ပါ — pack တစ်ခုချင်းစီအလိုက် အစားထိုးသတ်မှတ်ချက်များ (ship-fast/cost-saver/quality-first/
offline-friendly) ကို "Pack တစ်ခုချင်းစီအလိုက် Weight profile များ" ဇယားတွင် ဖော်ပြထားသည်။

အဆင့်တစ်ခုတည်းကြောင့် Tier 1 ကို ဦးစွာအသုံးပြုရန် **အတင်းအကျပ် မသတ်မှတ်ပါ** — Tier 1 ၏ တုံ့ပြန်ကြာချိန် မကောင်းပါက သို့မဟုတ် ကုန်ကျစရိတ်နှင့် အရည်အသွေး အချိုးအစား မသင့်တော်ပါက Tier 2 က ရွေးချယ်ခံရမည်ဖြစ်သည်။ အဆင့်အစဉ်ကို အတင်းအကျပ်သတ်မှတ်ရန် combo မဟာဗျူဟာ `priority` ကို အသုံးပြုပြီး provider များကို အဆင့်အလိုက် စီစဉ်ပါ။

Tier 1 (subscription) ကို အထူးဦးစားပေးရန် `tierPriority` weight ကို တိုးမြှင့်ပါ-

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

အဆင့်သတ်မှတ်ချက်များနှင့် provider အမျိုးအစားခွဲခြားမှုအတွက် [`docs/guides/TIERS.md`](../guides/TIERS.md) ကို ကြည့်ပါ။

## စမ်းသပ်ခြင်းနှင့် လွှမ်းခြုံမှု

### Deterministic routing-decision matrix (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` လမ်းကြောင်းကို သက်သေပြသည်။** ဆုံးဖြတ်ချက်** အများသူငှာ မဟာဗျူဟာ 21 ခုစလုံး၏ အစစ်အမှန် ပေါင်းစပ်ပိုက်လိုင်းမှတဆင့် အဆုံးမှ အဆုံးအထိ လှောင်ပြောင်ထားသော ရေစီးကြောင်းအတိုင်း။ အကျုံးဝင်သည်-

- `ROUTING_STRATEGY_VALUES` နည်းဗျူဟာ 21 ခုစလုံး (မှာယူသည်၊ တွက်ဆသည်၊ ကုန်ကျစရိတ်၊ အကြောင်းအရာ၊ ပေါင်းစပ်မှု၊ …)။
- `quota-share` (အတွင်းပိုင်း) အဆုံးမှအဆုံး- DRR မျှတမှု + saturation deprioritization အစစ်အမှန် `selectQuotaShareTarget` ချုပ်ရိုး (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`) ။
- ပစ်မှတ်တိုင်းအတွက်`context-relay` universal-handoff လွှမ်းခြုံမှု။

ဤ suite သည် CI (`test:integration` job) တွင် `--test-concurrency=1` နှင့် `--test-force-exit` ဖြင့် အလုပ်လုပ်သောကြောင့် ၎င်းသည် အဆုံးအဖြတ်ရှိပြီး တိုက်ရိုက်အထောက်အထားများ မလိုအပ်ပါ။
