**ရင်းမြစ်များ:**

- `open-sse/services/usage.ts` (~70KB) — အဓိက usage ခြေရာခံမှု
- `src/lib/usageAnalytics.ts` (~10KB) — dashboard အတွက် စုစည်းတွက်ချက်မှု
- `src/lib/db/quotaSnapshots.ts` — ယခင် quota ဒေတာ
- `src/lib/db/usage*.ts` — usage နှင့်သက်ဆိုင်သော DB module အများအပြား

## အနှစ်ချုပ်

OmniRoute မှတစ်ဆင့် ဖြတ်သန်းသော request တစ်ခုချင်းစီသည် အောက်ပါတို့ကို မှတ်တမ်းတင်သည့် **usage record** တစ်ခုကို ထုတ်ပေးသည်-

- **အထောက်အထား**: မည်သည့် API key၊ provider၊ model နှင့် combo ဖြစ်သည်
- **Token များ**: prompt token များ၊ completion token များ၊ cache လုပ်ထားသော token များနှင့် စုစုပေါင်း
- **ကုန်ကျစရိတ်**: USD ပမာဏ (pricing ဒေတာမှ တွက်ချက်ထားသည်)
- **အချိန်ဆိုင်ရာအချက်အလက်**: latency၊ စတင်/ပြီးဆုံး timestamp များ
- **အခြေအနေ**: အောင်မြင်မှု၊ error၊ rate limit သတ်မှတ်ခံရမှု စသည်တို့

ဤ record များကို **analytics** အဖြစ် စုစည်းတွက်ချက်ပြီး **quota snapshot** များအဖြစ် အမြဲတမ်းသိမ်းဆည်းကာ **key တစ်ခုချင်းစီ၏ budget limit** ကို သတ်မှတ်ကျင့်သုံးရန် အသုံးပြုသည်။

```
Request ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    analytics  quota   billing
                    (dashboard) (သတ်မှတ်ကျင့်သုံး) (ထုတ်ယူရန်)
```

## မှတ်တမ်းတင်ထားသည့် အချက်အလက်များ

`usage.ts` ဝန်ဆောင်မှုသည် တောင်းဆိုမှုတိုင်းအတွက် **အသုံးပြုမှုဖြစ်ရပ်** တစ်ခုကို မှတ်တမ်းတင်သည်-

| အကွက်              | အမျိုးအစား | ရင်းမြစ်                                                                    |
| ------------------ | ---------- | --------------------------------------------------------------------------- |
| `id`               | string     | မှတ်တမ်းတင်ချိန်တွင် ထုတ်ပေးသော UUID                                        |
| `apiKeyId`         | string     | တောင်းဆိုမှုကို စတင်ခဲ့သည့် API သော့                                        |
| `provider`         | string     | ဝန်ဆောင်မှုပေးသူ ID (openai, anthropic စသည်)                                |
| `model`            | string     | မော်ဒယ် ID (gpt-5, claude-opus-4-6 စသည်)                                    |
| `comboId`          | string?    | combo မှတစ်ဆင့် လမ်းကြောင်းပို့ထားလျှင် ထို combo ၏ ID                      |
| `promptTokens`     | number     | အထက်ဆင့်ဝန်ဆောင်မှု၏ တုံ့ပြန်ချက်မှ                                         |
| `completionTokens` | number     | အထက်ဆင့်ဝန်ဆောင်မှု၏ တုံ့ပြန်ချက်မှ                                         |
| `cachedTokens`     | number     | ကက်ရှ်တွင် တွေ့ရှိသော တိုကင်များ (Anthropic prompt ကက်ရှ်သိမ်းဆည်းမှု စသည်) |
| `totalTokens`      | number     | prompt + ဖြည့်စွက်ထုတ်ပေးမှု                                                |
| `costUsd`          | number     | ဈေးနှုန်းဒေတာမှ တွက်ချက်ထားခြင်း                                            |
| `latencyMs`        | number     | တောင်းဆိုမှု အစမှအဆုံး ကြာချိန်                                             |
| `status`           | enum       | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                  |
| `errorClass`       | string?    | အခြေအနေသည် အောင်မြင်မှုမဟုတ်ပါက အမှားအမျိုးအစား                             |
| `timestamp`        | string     | ISO 8601 UTC                                                                |
| `metadata`         | object     | ပလပ်အင်က ထည့်သွင်းပေးသော စိတ်ကြိုက်ဒေတာ                                     |

### တိုကင်များ၏ ရင်းမြစ်

တိုကင်များကို **တုံ့ပြန်ချက် ကိုင်တွယ်သည့် အစိတ်အပိုင်း** တွင် အထက်ဆင့်ဝန်ဆောင်မှုပေးသူ၏ တုံ့ပြန်ချက်မှ ထုတ်ယူသည်-

```ts
// open-sse/handlers/chatCore.ts မှ
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

အသုံးပြုမှုအချက်အလက်ကို ပြန်မပေးသော ဝန်ဆောင်မှုပေးသူများ (web-cookie ဝန်ဆောင်မှုပေးသူအချို့) အတွက် OmniRoute သည် `~4 chars per token` အနီးစပ်ဆုံးတွက်ချက်နည်းကို အသုံးပြု၍ တိုကင်များကို **ခန့်မှန်းသည်** (`open-sse/services/autoCombo/pipelineRouter.ts` ကို ကြည့်ပါ)။

### ကက်ရှ်သိမ်းထားသော တိုကင်များ

OmniRoute သည် `cached_tokens` ကို `prompt_tokens` နှင့် သီးခြား ခြေရာခံသည်။ အကြောင်းရင်းများမှာ-

- Anthropic prompt ကက်ရှ်သိမ်းဆည်းမှုသည် ကက်ရှ်သိမ်းထားသော တိုကင်များအတွက် လျှော့ချထားသည့် နှုန်းထား (ပုံမှန်၏ 10%) ဖြင့် ကောက်ခံသည်
- ဝန်ဆောင်မှုပေးသူအချို့သည် မတူညီသော ဈေးနှုန်းဖြင့် တွက်သင့်သည့် `cache_read_input_tokens` ကို ပြန်ပေးသည်
- ခွဲခြမ်းစိတ်ဖြာမှုတွင် **ကက်ရှ်တွင် တွေ့ရှိမှုနှုန်း** = `cached_tokens / prompt_tokens` ကို ပြသနိုင်သည်

### ကက်ရှ်ရေးသွင်းမှု အဆင့်အလိုက် စစ်ဆေးချက်များ

ခွဲခြမ်းစိတ်ဖြာမှု ဒက်ရှ်ဘုတ်၏ prompt ကက်ရှ်အခြေအနေပြကွက်သည် ဝန်ဆောင်မှုပေးသူက အစီရင်ခံသော
5 မိနစ်နှင့် 1 နာရီ ကက်ရှ်ရေးသွင်းမှုများကို ခွဲခြားပြသည်။ Anthropic ၏
`usage.cache_creation.ephemeral_5m_input_tokens` နှင့်
`usage.cache_creation.ephemeral_1h_input_tokens` တို့ကို streaming နှင့်
non-streaming အသုံးပြုမှုအချက်အလက် ပြောင်းလဲဖော်ပြရာတွင် ဆက်လက်ထိန်းသိမ်းထားပြီး ခေါ်ဆိုမှုမှတ်တမ်း အနှစ်ချုပ်များနှင့်အတူ သိမ်းဆည်းသည်။ ပေါင်းစပ်ထားသော
ကက်ရှ်ရေးသွင်းမှု စုစုပေါင်းကို ထိုအုပ်စုများထဲသို့ ဒုတိယအကြိမ် ထပ်မပေါင်းပါ။

မှတ်တမ်းဟောင်းများအပါအဝင် ပေါင်းစပ်ရေးသွင်းမှု ကောင်တာတစ်ခုသာ ပါရှိသော ခေါ်ဆိုမှုများ၏
အဆင့်ကို မသိရှိဟု သတ်မှတ်သည်။ တစ်စိတ်တစ်ပိုင်းသာ ခွဲခြားဖော်ပြထားလျှင် မသတ်မှတ်ရသေးသော လက်ကျန်ကို မသိရှိအဖြစ် ထားရှိသည်။ မမှန်ကန်သော သို့မဟုတ်
အချင်းချင်းကွဲလွဲနေသော ကောင်တာများကို TTL တစ်ခု တိတ်တဆိတ် သတ်မှတ်ပေးမည့်အစား သတိပေးအမှတ်အသား ပြုလုပ်သည်။ တောင်းဆိုမှုဘက်မှ
TTL အမှတ်အသားများသည် ငွေကောက်ခံထားသော အဆင့်၏ အထောက်အထား မဟုတ်ပါ။

ပြကွက်၏ API နှင့် ညီမျှသော ရေးသွင်းမှုကုန်ကျစရိတ် ခန့်မှန်းချက်သည် အစီရင်ခံထားပြီး ဈေးနှုန်းရှိသော အဆင့်များကိုသာ အကျုံးဝင်ပြီး
တောင်းဆိုမှုတစ်ခုလုံးကို မလွှမ်းခြုံပါ။ မူရင်း Claude/Anthropic မော်ဒယ်ဈေးနှုန်းများအတွက် 5 မိနစ် ရေးသွင်းမှုများကို
အဝင်နှုန်းထား၏ 1.25 ဆ၊ 1 နာရီ ရေးသွင်းမှုများကို အဝင်နှုန်းထား၏ နှစ်ဆဖြင့် တွက်ချက်သည်။ ဈေးနှုန်း
မရှိပါက မရရှိနိုင်ဟု သတ်မှတ်ပြီး သုညဟု မသတ်မှတ်ပါ။ ခေါ်ဆိုမှုအသစ်တစ်ခုစီကို မှတ်တမ်းတင်ချိန်တွင် ဈေးနှုန်းများကို သိမ်းဆည်းသည်။
ယခင်မှတ်တမ်းများ၏ ဈေးနှုန်းကို ပြန်မတွက်ပါ။ ထို့ကြောင့် စာရင်းသွင်းအသုံးပြုသည့် အကောင့်များတွင်
ထိုပမာဏကို ငွေသားအသုံးစရိတ် သို့မဟုတ် စာရင်းသွင်းမှု
ခွဲတမ်းမှ ကုန်ကျခြင်းမရှိဘဲ API နှင့် ညီမျှသော ခန့်မှန်းချက် ရှိနိုင်သည်။ လက်ရှိ ခွဲတမ်း၊ ဘတ်ဂျက်နှင့် ဝန်ဆောင်မှုပေးသူ၏ အတိအကျ ကုန်ကျစရိတ်တွက်ချက်မှုများမှာ မပြောင်းလဲပါ။

ဤစစ်ဆေးချက်များသည် လက်ရှိ အကန့်အသတ်ရှိသော ကက်ရှ်အခြေအနေ အနှစ်ချုပ်နှင့် ခေါ်ဆိုမှုမှတ်တမ်း
ထိန်းသိမ်းမှုကို အသုံးပြုသည်။ ၎င်းတို့သည် တောင်းဆိုမှု TTL မူလသတ်မှတ်ချက်များ၊ လမ်းကြောင်းပို့မှု သို့မဟုတ် အကောင့်ရွေးချယ်မှုကို မပြောင်းလဲပါ။
ဝန်ဆောင်မှုပေးသူထံ ပေးပို့သည့် နယ်နိမိတ်တွင် ကလိုင်းယင့်တောင်းဆိုထားသော TTL နှင့် အမှန်တကယ် အထွက် TTL တို့ကို
နှိုင်းယှဉ်မှတ်တမ်းတင်ခြင်းကို နောက်ပိုင်းသို့ ရွှေ့ဆိုင်းထားသည်။ ဤပြကွက်သည် လက်ခံဖြတ်ပိုင်းပါ အဆင့်များကိုသာ အစီရင်ခံပြီး အမှန်တကယ် အထွက် TTL ကို မဖော်ပြပါ။

အကောင်အထည်ဖော်ထားသည့်နေရာ: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` နှင့် `open-sse/utils/cacheWriteUsage.ts`။

## ကုန်ကျစရိတ် တွက်ချက်ခြင်း

ကုန်ကျစရိတ်များကို LiteLLM မှ စင့်ခ်လုပ်ထားသော **ဈေးနှုန်းဒေတာ** (`src/lib/pricingSync.ts`) ကို အသုံးပြု၍ တွက်ချက်သည်-

| မော်ဒယ်           | ထည့်သွင်းမှု $/1M | ထုတ်ပေးမှု $/1M | ကက်ရှ်လုပ်ထားမှု $/1M |
| ----------------- | ----------------- | --------------- | --------------------- |
| gpt-5             | $2.50             | $10.00          | —                     |
| claude-opus-4-6   | $15.00            | $75.00          | $1.50                 |
| claude-sonnet-4-5 | $3.00             | $15.00          | $0.30                 |
| gemini-2.5-pro    | $1.25             | $10.00          | —                     |

ကုန်ကျစရိတ် ဖော်မြူလာ (`src/lib/usage/costCalculator.ts`)-

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **ကက်ရှ်လုပ်ထားသည့် ပမာဏကို prompt မှ အဘယ်ကြောင့် နုတ်သနည်း။** ကက်ရှ်လုပ်ထားသည့် အပိုင်းအတွက် ဈေးနှုန်းကို သီးခြားတွက်ချက်သောကြောင့် prompt တစ်ခုလုံးအပေါ် ထည့်သွင်းမှုဈေးနှုန်း ကောက်ခံပါက ထပ်တိုးတွက်ချက်မိမည်ဖြစ်သည်။

### ဈေးနှုန်း စင့်ခ်လုပ်ခြင်း

ဈေးနှုန်းဒေတာကို `/api/pricing/sync` endpoint မှတစ်ဆင့် LiteLLM ထံမှ အလိုအလျောက် စင့်ခ်လုပ်သည် (အသုံးပြုသူအတွက် ရည်ရွယ်ထားသော env var ဖြင့်မဟုတ်ဘဲ ထည့်သွင်းပေးထားသည့် cron task ဖြင့် အစပျိုးသည်)-

```bash
# ကိုယ်တိုင် အစပျိုးခြင်း
curl -X POST http://localhost:20128/api/pricing/sync
```

ဈေးနှုန်းဒေတာမရှိသည့် မော်ဒယ်များအတွက် OmniRoute သည် အတွင်းပိုင်း ပျမ်းမျှနှုန်းထားများ (LiteLLM ၏ ဈေးနှုန်းဒေတာမှ ရယူထားသည်) ကို အသုံးပြု၍ **ကုန်ကျစရိတ် ခန့်မှန်းခြင်း** သို့ ပြန်လည်အသုံးပြုသည်။

## ခွဲတမ်း ကန့်သတ်ချက်များကို အကောင်အထည်ဖော်ခြင်း

API သော့တစ်ခုချင်းစီ၏ ခွဲတမ်းကို နေရာနှစ်ခုတွင် ကန့်သတ်ထားသည်။

1. **အပျော့စား ကန့်သတ်ချက်** (`quotaWarnAt`): အသုံးပြုမှုသည် သတ်မှတ်အဆင့်ကို ကျော်လွန်သောအခါ ဒက်ရှ်ဘုတ်တွင် သတိပေးခြင်း
2. **တင်းကျပ်သော ကန့်သတ်ချက်** (`quotaLimit`): ကျော်လွန်သောအခါ တောင်းဆိုမှုကို HTTP 429 ဖြင့် ငြင်းပယ်ခြင်း

### ပြင်ဆင်သတ်မှတ်ခြင်း

```ts
// API သော့တစ်ခုချင်းစီအတွက်
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — သတိပေးချက် ပြသရန်
  quotaLimit: 10_00,    // $10.00 — လုံးဝ ရပ်တန့်ရန်
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### ကန့်သတ်ချက် အကောင်အထည်ဖော်မှု လုပ်ငန်းစဉ်

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### ခွဲတမ်းအခြေအနေ လျှပ်တစ်ပြက်မှတ်တမ်းများ

`quotaSnapshots` ဇယားသည် လမ်းကြောင်းခွဲခြမ်းစိတ်ဖြာမှုအတွက် **ယခင် ခွဲတမ်းအခြေအနေများ** ကို သိမ်းဆည်းထားသည်။

| အကွက် | ဖော်ပြချက် |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ခြေရာခံနေသော သော့ |
| `window` | "day" | "week" | "month" |
| `used` | ဤကာလအတွင်း အသုံးပြုပြီးသော ကုန်ကျစရိတ် (ဆင့်) |
| `limit` | ကန့်သတ်ပမာဏ (ဆင့်) |
| `resetAt` | ကာလကို ပြန်လည်သတ်မှတ်မည့် အချိန် |
| `createdAt` | လျှပ်တစ်ပြက်မှတ်တမ်းကို ရယူခဲ့သည့် အချိန် |

ကုန်ကျစရိတ် > 0 ရှိသော **တောင်းဆိုမှုတိုင်းတွင်** လျှပ်တစ်ပြက်မှတ်တမ်းများကို ရယူပြီး အောက်ပါတို့အတွက် အသုံးပြုသည်။

- ဒက်ရှ်ဘုတ်တွင် ခွဲတမ်းအသုံးပြုမှု တိုးတက်ပြဘားကို ဖော်ပြရန်
- ရက် 30 ခွဲတမ်းလမ်းကြောင်းပြဇယားများကို ပြသရန်
- အသုံးပြုမှုသည် ကန့်သတ်ပမာဏသို့ နီးကပ်လာသောအခါ သတိပေးချက်များ ထုတ်ပေးရန်

### အသုံးပြုမှုခွဲခြမ်းစိတ်ဖြာချက်များကို မေးမြန်းခြင်း

အသုံးပြုမှုဒေတာကို တိုက်ရိုက် REST ထုတ်ယူမှု endpoint များမှတစ်ဆင့် မဟုတ်ဘဲ ဒက်ရှ်ဘုတ် သို့မဟုတ် MCP ကိရိယာများမှတစ်ဆင့် ရယူနိုင်သည်။ ရရှိနိုင်သော ခွဲခြမ်းစိတ်ဖြာချက်များ:

- **`/api/usage/analytics`** — စုစည်းထားသော အသုံးပြုမှုတိုင်းတာချက်များ (မော်ဒယ်၊ ဝန်ဆောင်မှုပေးသူ၊ သော့အလိုက် အုပ်စုဖွဲ့ထားသည်)
- **`/api/usage/quota`** — API သော့တစ်ခုစီအတွက် လက်ရှိခွဲတမ်းအခြေအနေ
- **`/api/usage/history`** — တောင်းဆိုမှုမှတ်တမ်းများ

## MCP ကိရိယာများ

MCP ကိရိယာနှစ်ခုက အေးဂျင့်များအတွက် အသုံးပြုမှုဒေတာကို ရယူနိုင်စေသည် (`open-sse/mcp-server/tools/` ကို ကြည့်ပါ):

| ကိရိယာ                  | ဖော်ပြချက်                                                                      |
| ----------------------- | ------------------------------------------------------------------------------- |
| `omniroute_cost_report` | သတ်မှတ်ကာလတစ်ခုအတွက် သော့တစ်ခုချင်းစီအလိုက် ကုန်ကျစရိတ်အစီရင်ခံစာကို ထုတ်ပေးသည် |
| `omniroute_check_quota` | API သော့တစ်ခုအတွက် လက်ရှိခွဲတမ်းအခြေအနေကို ပြန်ပေးသည်                           |

အေးဂျင့်မှ ခေါ်သုံးမှု ဥပမာ:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## ထိန်းသိမ်းခြင်းနှင့် ရှင်းလင်းခြင်း

အသုံးပြုမှုဒေတာသည် တောင်းဆိုမှုတစ်ခုလျှင် ~1-10KB တိုးပွားသည်။ အသုံးပြုမှုပမာဏ များလာသည့်အခါ ဤပမာဏသည် သိသာထင်ရှားလာနိုင်သည်။

### ထိန်းသိမ်းမှုဆိုင်ရာ ဆက်တင်များ

အသုံးပြုမှုမှတ်တမ်း ထိန်းသိမ်းခြင်းကို UI ရှိ ဒေတာဘေ့စ်ဆက်တင်များမှတစ်ဆင့် သို့မဟုတ် `/api/settings/database` မှတစ်ဆင့် ပြင်ဆင်သတ်မှတ်နိုင်သည်။

မူလသတ်မှတ်ချက်အရ အသုံးပြုမှုမှတ်တမ်းကို **ရက် 90** ကြာ ထိန်းသိမ်းထားသည်။

### ရှင်းလင်းခြင်း

မှတ်တမ်းဟောင်းများကို `src/lib/db/cleanup.ts` က ရှင်းလင်းပေးသည်:

- နောက်ခံ cron လုပ်ငန်းစဉ်က စတင်လုပ်ဆောင်စေသည်
- သတ်မှတ်ထားသော `usageHistory` ထိန်းသိမ်းမှုကာလထက် ပိုဟောင်းသည့် မှတ်တမ်းများကို `usage_history` မှ ဖျက်ပစ်သည်

### သိုလှောင်မှုပမာဏ ခန့်မှန်းခြင်း

| တောင်းဆိုမှုနှုန်း               | ရက် 30 သိုလှောင်မှုပမာဏ | ရက် 90 သိုလှောင်မှုပမာဏ |
| -------------------------------- | ----------------------- | ----------------------- |
| တစ်ရက်လျှင် တောင်းဆိုမှု 100     | ~3MB                    | ~9MB                    |
| တစ်ရက်လျှင် တောင်းဆိုမှု 1,000   | ~30MB                   | ~90MB                   |
| တစ်ရက်လျှင် တောင်းဆိုမှု 10,000  | ~300MB                  | ~900MB                  |
| တစ်ရက်လျှင် တောင်းဆိုမှု 100,000 | ~3GB                    | ~9GB                    |

အသုံးပြုမှုပမာဏ အလွန်များပါက အောက်ပါတို့ကို စဉ်းစားပါ:

- ဒေတာဘေ့စ်ဆက်တင်များမှတစ်ဆင့် ထိန်းသိမ်းမှုကာလကို လျှော့ချခြင်း
- မူရင်းမှတ်တမ်းများအစား `aggregated_metrics` ကို အသုံးပြုခြင်း (ခွဲခြမ်းစိတ်ဖြာမှုအတွက်သာ)

## ကုန်ကျစရိတ် လျှော့ချရန် အကြံပြုချက်များ

### 1. သင့်လျော်သော မော်ဒယ်ကို အသုံးပြုပါ

```bash
# အမြန်အဖြေ — စျေးသက်သာပြီး မြန်ဆန်သော မော်ဒယ်ကို သုံးပါ
curl -d '{"model":"auto/fast","messages":[...]}'

# ရှုပ်ထွေးသော အလုပ် — အရည်အသွေးမြင့် မော်ဒယ်ကို သုံးပါ
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. ကက်ရှ်သိမ်းဆည်းခြင်းကို ဖွင့်ပါ

Anthropic ၏ prompt ကက်ရှ်သိမ်းဆည်းခြင်းသည် **ထပ်တလဲလဲ အသုံးပြုသော နောက်ခံအကြောင်းအရာအတွက် ကုန်ကျစရိတ်ကို 90% သက်သာစေသည်**:

```ts
// ကက်ရှ်သိမ်းဆည်းခြင်းသည် အလိုအလျောက်ဖြစ်သည် — တူညီသော ရှည်လျားသည့် system prompt ကို ထည့်သွင်းရုံသာ လိုအပ်သည်
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // အလိုအလျောက် ကက်ရှ်သိမ်းဆည်းမည်
  messages: [{ role: "user", content: "..." }],
});
```

### 3. ချုံ့ခြင်းကို အသုံးပြုပါ

RTK + Caveman ချုံ့ခြင်းသည် **ကိရိယာများကို များစွာအသုံးပြုသော ဆက်ရှင်များတွင် ကုန်ကျစရိတ်ကို 15-95% သက်သာစေသည်**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. ကီးတစ်ခုချင်းစီအတွက် ခွဲတမ်းများ သတ်မှတ်ပါ

ကုန်ကျစရိတ် ထိန်းမနိုင်သိမ်းမရ မြင့်တက်ခြင်းကို ကာကွယ်ရန် `quotaLimit` ကို အမြဲသတ်မှတ်ပါ:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // တစ်လလျှင် အများဆုံး $10
```

### 5. အသုံးပြုမှု အများဆုံးသူများကို စစ်ဆေးပါ

API ကီးအလိုက် အုပ်စုဖွဲ့ပြီး ကုန်ကျစရိတ်အလိုက် စီရန် ဒက်ရှ်ဘုတ် သို့မဟုတ် **`/api/usage/analytics`** ကို အသုံးပြုပါ:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## ပြဿနာဖြေရှင်းခြင်း

### "ကုန်ကျစရိတ်သည် မျှော်မှန်းထားသည်ထက် ပိုများနေသည်"

1. **`/api/usage/analytics?groupBy=model`** ကို စစ်ဆေးပါ — ကုန်ကျစရိတ်များသော မော်ဒယ်ကို ရှာပါ
2. **`/api/usage/analytics?groupBy=apiKey`** ကို စစ်ဆေးပါ — အသုံးပြုမှုများသောသူကို ရှာပါ
3. စျေးနှုန်းဒေတာသည် နောက်ဆုံးအခြေအနေဖြစ်ကြောင်း အတည်ပြုပါ: `POST /api/pricing/sync`

### "မှတ်တမ်းများ ပျောက်နေသည်"

- ဒက်ရှ်ဘုတ် → ဒေတာဘေ့စ် → ရှင်းလင်းခြင်း အောက်ရှိ DB မှတ်တမ်းထိန်းသိမ်းမှု ဆက်တင်များကို စစ်ဆေးပါ — မှတ်တမ်းဟောင်းများကို အချိန်မှန် ရှင်းလင်းရေးလုပ်ငန်း (`src/lib/db/cleanup.ts`) က ဖျက်ပစ်သည်
- `src/lib/db/usage*.ts` တွင် အမှားများ ရှိမရှိ စစ်ဆေးပါ — DB သို့ ရေးသားမှု မအောင်မြင်ခြင်းများကို မှတ်တမ်းတင်ထားသော်လည်း အသုံးပြုသူထံ ဖော်ပြခြင်းမရှိပါ
- တောင်းဆိုချက်သည် `chatCore` သို့ အမှန်တကယ် ရောက်ရှိခဲ့ကြောင်း အတည်ပြုပါ — combo လမ်းကြောင်းသတ်မှတ်မှုကို စစ်ဆေးပါ

### "ခွဲတမ်းကန့်သတ်ချက် အလုပ်မလုပ်ပါ"

- ကီး၏ `quotaLimit` ဆက်တင်ကို စစ်ဆေးပါ
- `quotaWindow` ကို မှန်ကန်စွာ သတ်မှတ်ထားကြောင်း အတည်ပြုပါ
- `quotaSnapshots` မှတ်တမ်းများကို ရှာပါ — တောင်းဆိုချက်တိုင်းတွင် ၎င်းတို့ကို ဖန်တီးထားသင့်သည်
