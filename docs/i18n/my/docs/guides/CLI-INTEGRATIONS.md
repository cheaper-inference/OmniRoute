မျှဝေထားသော executable manifest၊ ကန့်သတ်ထားသော ကလေးပတ်ဝန်းကျင်များနှင့် ဆက်တိုက် Gemini စနစ်ထည့်သွင်းခြင်းအတွက် [CLI စတင်ခြင်းစာချုပ်များကို](./CLI-LAUNCH-CONTRACTS.md) ကြည့်ပါ။

OmniRoute OmniRoute ၎င်း၏နောက်ကွယ်မှအဖြစ်အသုံးပြုရန် CLI (Codex, Claude Code, OpenCode, Cline, …) ကို configure လုပ်သည့် `setup-*` command မိသားစုတစ်စုကို ပေးပို့သည် — ထို့ကြောင့် tool နှင့် စကားပြောသည်** တစ်ခု** အဆုံးမှတ်နှင့် OmniRoute လမ်းကြောင်းများသည် အလိုအလျောက်ပြန်ယူခြင်းဖြင့် မှန်ကန်သောဝန်ဆောင်မှုပေးသူထံ လမ်းကြောင်းများ။ အမိန့်တစ်ခုစီသည် စာကိုဖတ်သည်။** အသက်ရှင်** လည်ပတ်နေသည့် OmniRoute (ဒေသခံ သို့မဟုတ် အဝေးထိန်း) မှ မော်ဒယ်ကတ်တလောက်ကို တူးလ်၏ ကိုယ်ပိုင် config ဖိုင်ပေါ်တွင် ရေးသားသည်။** သင်၏** စက်။ API သော့ကို ကိရိယာက ပံ့ပိုးပေးသည့် နေရာတိုင်းတွင် ပတ်ဝန်းကျင် ကိန်းရှင်တစ်ခုက ရည်ညွှန်းသည်။ ကိရိယာ-စက်တွင်းပတ်ဝန်းကျင် ဖိုင်ကို ဆက်ရှိနေစေသည့် အမိန့်များကို အောက်တွင် မှတ်သားထားသည်။

မည်သည့် config ကိုမျှ မရေးဘဲ `claude`, `codex`, zqd , `aider`, `goose`, `opencode`, `qwen`, `gemini` သို့မဟုတ် `whycodes` တို့ကို မှန်ကန်သော env ထိုးသွင်းထားသည့် ယေဘုယျ launcher — `omniroute run <target>` — လည်း ရှိပါသည်။ ပစ်မှတ်များ နှင့် ၎င်းတို့၏ နာမည်တူများသည် canonical manifest `bin/cli/cli-manifest.mjs` (`claude-code|cc|anthropic`, `codex-cli|openai-codex|openai`, `goose-cli`, `open-code`, `qwen-code`, `gemini-cli`, `why-codes|why`) နှင့် `omniroute completion` တူညီသော ထင်ရှားပေါ်လွင်သည့် ပစ်မှတ်စကားလုံးများကို ပေးဆောင်သည်။ တူးလ်တစ်ခုချင်းပစ်လွှတ်သည့် အမွေအနှစ်များ— `omniroute launch` (Claude Code) နှင့် `omniroute launch-codex` (Codex) — ရရှိနိုင်ဆဲဖြစ်သည်။

ဝန်ဆောင်မှုပေးသူ စတင်အသုံးပြုခြင်းကို တူညီသော local/remote အကြောင်းအရာမှ ရရှိနိုင်သည်။ အောက်ဖော်ပြပါ API-ပထမညွှန်ကြားချက်များသည် စီမံခန့်ခွဲမှုအထောက်အထားစိစစ်ခြင်းအား ပံ့ပိုးပေးသူအထောက်အထားများနှင့် သီးခြားခွဲထားကာ ဖွဲ့စည်းတည်ဆောက်ထားသည့်အထွက်တွင် အထောက်အထားကို ဘယ်သောအခါမှ မပုံနှိပ်ပါ-

```bash
omniroute providers add glm --credential-env GLM_API_KEY --name work
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth openai
omniroute providers edit <connection-id> --default-model glm/glm-5.2
omniroute providers remove <connection-id> --yes
```

script များအတွက် `--credential-stdin` သို့မဟုတ် `--credential-env` ကို နှစ်သက်သည်။ `--credential` ထိန်းချုပ်ထားသော ဒေသတွင်းအသုံးပြုမှုအတွက် ထိန်းသိမ်းထားသည်။ `providers remove` အပြန်အလှန်အကျိုးသက်ရောက်မှုမရှိသော terminal တွင် `--yes` လိုအပ်ပြီး ညွှန်ကြားချက်ငါးခုစလုံးသည် တက်ကြွသောအကြောင်းအရာ သို့မဟုတ် ကမ္ဘာလုံးဆိုင်ရာ `--base-url`/`--api-key` ရွေးချယ်မှုများကို ဂုဏ်ပြုပါသည်။

ပံ့ပိုးပေးသူရွေးချယ်သူများသည် မရှင်းလင်းသော ID ရှေ့ဆက်များ၊ အမည်များ သို့မဟုတ် ဝန်ဆောင်မှုပေးသူအမည်များကို ငြင်းပယ်သည်၊ ချိတ်ဆက်မှုများစွာနှင့် ကိုက်ညီသောအခါတွင် အပြည့်အဝချိတ်ဆက်မှု ID အသုံးပြုပါ။ သိမ်းဆည်းထားသော ချိတ်ဆက်မှုကို ပြန်ဖတ်ပြီး ညွှန်ကြားချက်များကို ဖန်တီးပြီး တည်းဖြတ်ခြင်းဖြင့် ၎င်းကို ဖတ်ရှု၍မရတော့ကြောင်း ဖယ်ရှားကြောင်း အတည်ပြုသည်။ တင်သွင်းမှုသည် ရှိပြီးသား provider/name အတွဲကို ကျော်သွားသည်။ တင်သွင်းထားသည့်အရာများသည် CLI သို့ပေးဆောင်သော စီမံခန့်ခွဲမှုအဆုံးမှတ်၊ အကြောင်းအရာ သို့မဟုတ် စီမံခန့်ခွဲမှုအထောက်အထားများကို အစားထိုး၍မရပါ။

## မာစတာစားပွဲ

အမိန့်တိုင်းကို လေးစားတယ်။** တက်ကြွသောအကြောင်းအရာ** ( `omniroute connect` ဖြင့်သတ်မှတ်ပါ၊ [အဝေးထိန်းမုဒ်ကို](./REMOTE-MODE.md) ကြည့်ပါ) သို့မဟုတ် ပြတ်သားသော `--remote <url> --api-key <key>` အလံများ။ အောက်ဖော်ပြပါ "Local vs remote" ဆိုသည်မှာ `http://localhost:20128` ပစ်မှတ်ထားခြင်းမရှိသော အလံမရှိသော၊ `--remote` (သို့မဟုတ် အသက်ဝင်နေသော အဝေးထိန်းအကြောင်းအရာ) ဖြင့် ၎င်းသည် ထိုဆာဗာမှ ကတ်တလောက်ကို ရယူပြီး config ကို စက်တွင်း၌ ရေးသားသည်။

အလံများအတွက် မှတ်စုများ (အမိန့်တော်ရင်းမြစ်တွင် အတည်ပြုထားသည်)

- `--remote <url>` — အဝေးထိန်း OmniRoute မှ ကတ်တလောက်ကို ရယူပါ ( `--port` နှင့် တက်ကြွသော အကြောင်းအရာကို အစားထိုးသည်)။ `--api-key <key>` ထိုဆာဗာအတွက် အထောက်အထားကို ပံ့ပိုးပေးသည် ( `OMNIROUTE_API_KEY` env var သို့ ပုံသေများ သို့မဟုတ် အသက်ဝင်နေသော အကြောင်းအရာ၏ တိုကင်)။
- `--only <patterns>` — ကော်မာ-ခြားထားသော စာကြောင်းများ; ကိုက်ညီသော မော်ဒယ် IDs သာ ထားရှိပါ (ဥပမာ `--only glm,kimi`)။ `setup-codex`, `setup-claude`, `setup-opencode`, `setup-continue`, `setup-cursor`, `setup-crush`, `setup-zed` တွင်ရနိုင်သည်။
- `--dry-run` — ဖိုင်စနစ်ကို မထိဘဲ ရေးထားမည့်အရာကို အတိအကျ print ထုတ်ပါ။ `setup-*` အမိန့်တိုင်းတွင် ရနိုင်သည်။** မှလွဲ၍** `setup-cursor` (ဖိုင်ကို ဘယ်တော့မှ မရေးဘူး)။
- `--model <id>` — မော်ဒယ် အလိုအလျောက် ရှာဖွေတွေ့ရှိခြင်းမရှိသော ကိရိယာများအတွက် လိုအပ်သည် (သို့မဟုတ် အပြန်အလှန်အားဖြင့် ရွေးသည်) − Cline၊ Kilo ၊ Roo ၊ Goose ၊ Qwen၊ Aider ၊ 5dive ၊ WhyCodes. ထိုကိရိယာများသည် အပြန်အလှန်အကျိုးသက်ရောက်မှုမရှိသောလုပ်ဆောင်မှုများအတွက် `--yes` ကိုလည်းလက်ခံသည် (ထို့နောက် `--model` လိုအပ်သည်)။ `setup-opencode` သည် မူရင်း ထိပ်တန်းအဆင့် မော်ဒယ်ကို သတ်မှတ်ရန် `--model` ယူသည်။
- `omniroute run` ပေါ်ရှိ`--model <id>` သည် မန်နီးဖက်စ်၏ ပစ်မှတ်တစ်ခုစီ ဝိုင်ယာကြိုး (`bin/cli/cli-manifest.mjs`) ကို လိုက်နာသည်။** ကူညီသူ** `--model openai/<id>` နှင့် လက်ခံသည်။** opencode** `--model omniroute/<id>` (id သည် ၎င်းကို မသယ်ဆောင်ရသေးသည့်အချိန်တွင်သာ ရှေ့ဆက်ကို ပေါင်းထည့်သည်);** qwen** နှင့်** မေထုန်** id verbatim ကိုလက်ခံပါ။** လော့ဒ်** `ANTHROPIC_MODEL` မှတဆင့်ရယူပါ** ဘဲငန်း** `GOOSE_MODEL` မှတဆင့်၊** အဘယ်ကြောင့်ကုဒ်များ** `-P omniroute -m <id>` မှတဆင့်၊ နှင့်** codex** `-c model_providers.omniroute.*` args မှတဆင့်။**Qwen သည် `--model` လိုအပ်သော တစ်ခုတည်းသော ပြေးပစ်မှတ်ဖြစ်သည်။** — ၎င်းမပါဘဲ `omniroute run qwen` ပြတ်သားသောအမှားတစ်ခုဖြင့် `2` မှထွက်သည်။
- `--port <port>` — ဒေသတွင်း OmniRoute ဆိပ်ကမ်း (မူလ `20128`၊ `--remote` ကို သတ်မှတ်သည့်အခါ လျစ်လျူရှုထားသည်)။ `setup-*` နှင့် launchers နှစ်ခုစလုံးတွင် တင်ပြပါ။
- `omniroute run` ထွက်ပေါက်ကုဒ်များ- ကလေး CLI၏ကိုယ်ပိုင်ထွက်ပေါက်ကုဒ်ကို စကားလုံးဖြင့် ဖြန့်ဝေထားသည်။ `2` = မမှန်ကန်သော အကြောင်းပြချက်များ (ပံ့ပိုးမထားသော ပစ်မှတ်၊ လိုအပ်သော `--model` ပျောက်နေခြင်း၊ ကွန်တိန်နာစောင့်); `127` = ပစ်မှတ် binary သည် `PATH` တွင်မရှိပါ။ ပစ်လွှတ်ခြင်းကို `SIGINT`/`143`/`SIGHUP` ဖြင့် အဆုံးသတ်သောအခါ `130`/`SIGTERM`/`129` ; `1` = အခြား runtime လွှင့်တင်မှု မအောင်မြင်ပါ။
- အရင်းခံ `claude` / `codex` binary အတွက် `setup-claude` / `setup-codex` မှ ရေးသားထားသော ပရိုဖိုင်ကို ရွေးချယ်ရန် launchers နှစ်ခု (`launch`, `launch-codex`) သည် `--profile <name>` လက်ခံသည်။

အပြန်အလှန်အကျိုးသက်ရောက်မှုရွေးချယ်မှုအား စနစ်ထည့်သွင်းမှုချက်ပြုတ်နည်းများမှလည်း မျှဝေထားသည်-

```bash
# Pick from the active local or remote model catalog and configure the target.
omniroute configure claude
omniroute configure opencode --provider glm
omniroute configure qwen --model qwen/qwen3.8-max-preview --yes
```

`configure` `codex`, `claude`, `opencode`, `qwen`, `aider`, `goose`, `cline`, `continue`, `kilo`, နှင့် `5dive` အတွက် စမ်းသပ်ထားသော ချက်ပြုတ်နည်းများကို လက်ရှိတွင် ကိုယ်စားလှယ်လွှဲအပ်ထားသည်။ IDE သီးသန့်၊ MITM နှင့် လမ်းညွှန်-သီးသန့် ကက်တလောက်ထည့်သွင်းမှုများသည် တိကျပြတ်သားသော `setup-*`/manual flows များအဖြစ် ဆက်လက်တည်ရှိနေပြီး ပစ်မှတ်များအဖြစ် မဖော်ပြပါ။

> `setup-opencode` သည်** ပေါ့ပါးသော openai နှင့်လိုက်ဖက်သည်။** OpenCode ပေါင်းစပ်မှု။ `@omniroute/opencode-plugin` ကို ထည့်သွင်းပေးသည့် ပိုမိုကြွယ်ဝသော ပလပ်အင်ပေါင်းစည်းမှု - `omniroute setup opencode` လည်း ရှိပါသည်။ ၎င်းတို့သည် မတူညီသော အမိန့်များဖြစ်သည်။ အပေါ်က ဇယားက စာရွက်စာတမ်း `setup-opencode`။
>
> ပလပ်အင်သည် OpenCode အဓိကတစ်ခုလျှင် ပက်ကေ့ခ်ျနှစ်ခုဖြင့် လာပါသည်။ loader နှစ်ခုသည် မတူညီသော entrypoints များကို မျှော်လင့်ထားသောကြောင့်ဖြစ်သည်- `@omniroute/opencode-plugin` for OpenCode v1 နှင့် OpenCode v2 အတွက် `@omniroute/opencode-plugin-v2` ။ v2 ပက်ကေ့ဂျ်သည် အသစ် (`0.1.0`) ဖြစ်ပြီး ရွေ့လျားနေဆဲဖြစ်သော အိမ်ရှင်စာချုပ်ကို လိုက်နာသောကြောင့် ၎င်းသည် တစ်ခုယူဆရမည့်အစား OpenCode အစေ့များကို ကတ်တလောက်အကြမ်းထဲသို့ ဖတ်ပြသည်။ `plugins` entry ကို `opencode.json` တွင်ထည့်ခြင်းဖြင့် ၎င်းကို install လုပ်ပါ။ `omniroute setup opencode` v1 အထုပ်ကို ထည့်သွင်းနေသေးသည်။ ရွေးချယ်စရာများနှင့် အထောက်အထားရှာဖွေမှုအမှာစာ README အထုပ်တွင်ရှိသည်။

## စက်တွင်း အသုံးပြုမှု

OmniRoute ကို `localhost:20128` တွင် လည်ပတ်ထားပြီး သင့်ကိရိယာအတွက် setup command ကိုသာ run ပါ။ catalog ကို local server မှ ရယူပါမည်။

```bash
# Codex: ကိုက်ညီသော model တစ်ခုစီအတွက် profile တစ်ခုကို ~/.codex/ ထဲသို့ ရေးပါ
omniroute setup-codex
codex --profile glm52            # ထုတ်ပေးထားသော profile ကို အသုံးပြုပါ

# Claude Code: model တစ်ခုစီအတွက် profile များကို ရေးပြီးနောက် တစ်ခုကို စတင်ပါ
omniroute setup-claude
omniroute launch --profile glm52

# OpenCode: catalog model အားလုံးပါဝင်သည့် openai-compatible provider ကို ရေးပါ
omniroute setup-opencode
export OMNIROUTE_API_KEY=sk-...  # {env:OMNIROUTE_API_KEY} မှတစ်ဆင့် ရည်ညွှန်းပြီး disk ပေါ်တွင် လုံးဝမသိမ်းပါ
opencode -m omniroute/glm/glm-5.2 "..."

# အလိုအလျောက်ရှာဖွေခြင်း မရှိသော ကိရိယာများတွင် model ကို အတိအကျ သတ်မှတ်ရန် လိုအပ်သည်-
omniroute setup-aider --model glm/glm-5.2
omniroute setup-qwen --model qwen/qwen3.8-max-preview

# မည်သည့်အရာကိုမျှ မရေးဘဲ အစမ်းကြည့်ရန်-
omniroute setup-continue --dry-run
```

မည်သည့် config ကိုမျှ မရေးဘဲ စတင်ပါ (env-injection သီးသန့်)-

```bash
omniroute launch                 # Claude Code → local OmniRoute
omniroute launch-codex           # Codex CLI → local OmniRoute
omniroute launch-codex --profile glm52
omniroute run claude --model openai/gpt-5.4
omniroute run codex --model openai/gpt-5.4 --dry-run --json
omniroute run aider --model glm/glm-5.2 -- --message "reply OK"
omniroute run goose --model glm/glm-5.2
omniroute run opencode --model glm/glm-5.2 -- run "reply OK"
omniroute run qwen --model glm/glm-5.2 -- -p "reply OK"
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "reply OK"

omniroute run claude -- --print-system-prompt "review this diff"
```

## အဝေးမှ အသုံးပြုမှု

မည်သည့် setup command ကိုမဆို `--remote` + `--api-key` ဖြင့် အဝေးရှိ OmniRoute သို့ ညွှန်ပါ။ catalog ကို remote မှ ရယူပြီး config ကို သင့် local machine ပေါ်တွင် ရေးပါမည်။

```bash
# Remote VPS ရှိ OpenCode အတွက် glm/kimi model များကိုသာ ထားပါ
omniroute setup-opencode --remote http://192.168.0.15:20128 --api-key oma_live_xxx \
  --only glm,kimi
opencode -m omniroute/glm/glm-5.2 "..."   # OMNIROUTE_API_KEY ကို ဦးစွာ export လုပ်ပါ

# Remote catalog မှ Codex profile များ
omniroute setup-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx

# CLI တစ်ခုကို remote နှင့် တိုက်ရိုက်ချိတ်ဆက်၍ စတင်ပါ
omniroute launch       --remote http://192.168.0.15:20128 --api-key oma_live_xxx
omniroute launch-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx
```

အကြိမ်တိုင်း `--remote`/`--api-key` ပေးမည့်အစား တစ်ကြိမ် login ဝင်ပြီး **လက်ရှိအသုံးပြုနေသော context** က ၎င်းတို့ကို အလိုအလျောက် ဖြည့်ပေးစေပါ-

```bash
omniroute connect 192.168.0.15        # scope ကန့်သတ်ထားသော token တစ်ခုကို ထုတ်ပေးပြီး context ကို သိမ်းဆည်းသည်
omniroute setup-codex                 # ← ယခု remote catalog ကို အသုံးပြုသည်
omniroute setup-opencode              # ← အတူတူပင်
omniroute launch                      # ← Remote နှင့် ချိတ်ဆက်ထားသော Claude Code
```

Context များ၊ scope များနှင့် token စီမံခန့်ခွဲမှုအတွက် [Remote Mode](./REMOTE-MODE.md) ကို ကြည့်ပါ။

## 5dive agent အုပ်စုများ

[5dive](https://5dive.ai) သည် အချိန်ကြာမြင့်စွာ အလုပ်လုပ်နေသော coding agent အုပ်စုတစ်ခုကို လည်ပတ်ပေးပြီး agent တစ်ခုစီသည် ၎င်း၏ကိုယ်ပိုင် Unix user အောက်ရှိ systemd unit တစ်ခုဖြစ်သည်။ ၎င်းကိုယ်တိုင်က coding CLI မဟုတ်သောကြောင့် `omniroute run` ဖြင့် စတင်ရန် မည်သည့်အရာမျှ မရှိပါ — `5dive` သည် **configure-only** target တစ်ခုဖြစ်သည်။

```bash
omniroute configure 5dive --model failover-demo --yes
omniroute setup-5dive --model failover-demo --auth-profile omniroute --agent worker1
```

ပုံစံနှစ်မျိုးလုံးသည် 5dive **auth profile** တစ်ခုကို ရေးပေးပြီး ထို profile နှင့် ချိတ်ထားသော `claude` seat အားလုံးသည် ထို့နောက် OmniRoute နှင့် ဆက်သွယ်ပါမည်။ ဤ target အတွက် သီးခြားဖြစ်သော အချက်သုံးချက်ရှိသည်-

- **၎င်းသည် fleet host ပေါ်တွင် root အဖြစ် လည်ပတ်သည်။** 5dive ၏ verb များသည် local systemd unit များနှင့် root ပိုင်ဆိုင်သော state dir တစ်ခုအပေါ် လုပ်ဆောင်သောကြောင့် remote mode မရှိပါ။ root မဖြစ်သေးသည့်အခါ recipe သည် `sudo` မှတစ်ဆင့် ပြန်လည် execute လုပ်သည် (`--no-sudo` သည် ယင်းကို ပိတ်ပြီး အစားထိုးအနေဖြင့် command ကို ထုတ်ပြသည်)။
- **Loopback မဟုတ်ပါက endpoint သည် `https://` ဖြစ်ရမည်။** Agent ၏ API key သည် request တိုင်းတွင် ထို URL မှတစ်ဆင့် ပါသွားပြီး 5dive သည် စက်ပြင်ပသို့ plaintext ဖြင့် ဆက်သွယ်သည့် endpoint ကို လက်မခံပါ။ Private LAN address သည်လည်း ခြွင်းချက်မဟုတ်ပါ။
- **Seat တစ်ခုစီ၏ ကိုယ်ပိုင် model pin သည် profile ထက် ဦးစားပေးအဆင့်မြင့်သည်။** Profile တွင် `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` ပါဝင်သော်လည်း stock model id တစ်ခုနှင့် pin လုပ်ထားဆဲ seat သည် ၎င်း၏ ပထမဆုံး turn တွင် _"ရွေးချယ်ထားသော model တွင် ပြဿနာရှိနေသည်"_ ဟူသော စာသားဖြင့် မအောင်မြင်ပါ။ Seat များကိုပါ pin လုပ်ရန် `--agent <name>` (ထပ်ခါတလဲလဲ သုံးနိုင်သည်) ကို ပေးပါ၊ မပေးပါက recipe သည် command ကို ထုတ်ပြပါမည်။

API key ကို **stdin** (`--api-key=-`) မှတစ်ဆင့် 5dive ထံ လွှဲပေးသောကြောင့် ၎င်းသည် `ps` output တွင် လုံးဝပေါ်လာမည်မဟုတ်ပါ။

Profile ကို model တစ်ခုတည်းအစား OmniRoute **combo** တစ်ခုသို့ ညွှန်ခြင်းဖြင့် fleet provider failover ကို ရရှိစေသည်။ [#11578](https://github.com/diegosouzapw/OmniRoute/issues/11578) တွင် မှတ်တမ်းတင်ထားသော run အတွင်း primary endpoint သည် turn တစ်ခု၏ အလယ်တွင် လုံးဝ ရပ်တန့်သွားသောအခါ agent သည် ကျန်ရှိသော အဆင့်များကို fallback ပေါ်တွင် ပြီးဆုံးစေခဲ့ပြီး ပြတ်တောက်မှုကို အသုံးပြုသူထံ မဖော်ပြခဲ့ပါ။

## Update လုပ်စဉ် native dependencies များကို ထိန်းသိမ်းထားခြင်း: `--include=optional`

`omniroute update` ဖြင့် update လုပ်သည့်အခါ (အတည်ပြုပြီးနောက် သို့မဟုတ် `--apply` ဖြင့်)
OmniRoute သည် `--include=optional` ကို မူလကတည်းက ထည့်သွင်းထားသော install command ကို လုပ်ဆောင်သည်။

```bash
npm install -g omniroute@latest --include=optional
```

၎င်းသည် `omniroute update` သို့ သင်ပေးပို့ရမည့် flag **မဟုတ်ပါ** — updater က
အမြဲတမ်း အလိုအလျောက် အသုံးပြုသည်။ သင်၏ npm config တွင် `omit=optional` သတ်မှတ်ထားလျှင်ပင်
`optionalDependencies` (`better-sqlite3`, `keytar`, `tls-client`,
LLMLingua SLM stack) များသည် update အပြီးတွင် ဆက်လက်ရှိနေမည်ဟု အာမခံပေးသည်။
မဟုတ်ပါက native SQLite driver နှင့် OS-keyring binding တို့ကို မည်သည့်သတိပေးချက်မျှမရှိဘဲ
ဖယ်ရှားသွားမည်ဖြစ်သည်။ အမှန်တကယ် မလုပ်ဆောင်ဘဲ command အတိအကျကို ကြိုတင်ကြည့်ရှုရန်-

```bash
omniroute update --dry-run
# [DRY RUN] လုပ်ဆောင်မည့် command: npm install -g omniroute@latest --include=optional
```

အခြား `omniroute update` flag များ (source တွင် အတည်ပြုပြီးဖြစ်သည်)- `--check` (ဗားရှင်းဟောင်းနေပါက
exit 1 ပြန်ပေးသည်)၊ `--apply` (အတည်ပြုချက်မတောင်းဘဲ install လုပ်သည်)၊ `--changelog`၊ `--no-backup`၊
`--yes`။

## `omniroute run gemini` မှတစ်ဆင့် Google Gemini CLI အသုံးပြုခြင်း

`@google/gemini-cli` 0.50.0 နှင့် တိုက်ဆိုင်စစ်ဆေး၍ contract ကို အတည်ပြုပြီးဖြစ်သည်။ CLI သည်
`GOOGLE_GEMINI_BASE_URL` ကို လိုက်နာပြီး ၎င်းထံသို့
`POST /v1beta/models/<model>:generateContent`
(နှင့် `:streamGenerateContent?alt=sse`) ကို ပေးပို့သည် — OmniRoute ၏ native
Gemini surface (`/v1beta`) နှင့် အတိအကျပင် ဖြစ်သည်။ `omniroute run gemini` က
၎င်းကို အလိုအလျောက် ချိတ်ဆက်သတ်မှတ်ပေးသည်-

- `GOOGLE_GEMINI_BASE_URL` → လက်ရှိအသုံးပြုနေသော OmniRoute base URL (root၊ `/v1` မပါ)၊
- `GEMINI_API_KEY` → ဆုံးဖြတ်ရရှိထားသော OmniRoute credential (option/env/context)၊
- `gemini-api-key` auth ကို ရွေးချယ်ထားသည့် `.gemini/settings.json` ပါဝင်သော
  **ယာယီ သီးခြားခွဲထားသည့် `GEMINI_CLI_HOME`**၊ ထို့ကြောင့် သိမ်းဆည်းထားသော Google OAuth session
  (Code Assist) က OmniRoute သို့ ဦးတည်ထားသည့် launch ကို မည်သည့်အခါမျှ ကျော်လွှားအစားထိုးမည်မဟုတ်ပါ —
  exit ပြီးနောက် ဖယ်ရှားပစ်သည်၊
- **env သန့်ရှင်းရေး**- child env မှ `GOOGLE_API_KEY`,
  `GOOGLE_GENAI_USE_VERTEXAI` နှင့် `GOOGLE_GENAI_USE_GCA` (auth ကို Vertex/Code Assist သို့
  လမ်းကြောင်းပြောင်းစေနိုင်သည့် variable များ) ကို ဖယ်ရှားပြီး၊ အရန်ကာကွယ်မှုအဖြစ်
  `GEMINI_DEFAULT_AUTH_TYPE=gemini-api-key` ကို သတ်မှတ်သည် — အခြား `run` target များအတွက်လည်း
  ၎င်းတို့နှင့် သက်ဆိုင်သော ပဋိပက္ခဖြစ်စေနိုင်သည့် variable များကို အလားတူ ကိုင်တွယ်ပေးသည်၊
- `--provider`/`--model` မှ `--model <id>` ကို ထည့်သွင်းပေးခြင်း။

```bash
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "hello"
```

Gemini ၏ workspace-trust အကာအကွယ်သည် headless mode တွင်လည်း ဆက်လက်သက်ရောက်သည် —
`--skip-trust` ကို သင်ကိုယ်တိုင် ပေးပို့ပါ (သို့မဟုတ် directory ကို interactive နည်းဖြင့် trust လုပ်ပါ)။
launcher သည် ၎င်းကို ရည်ရွယ်ချက်ရှိရှိ ကျော်လွှားခြင်းမပြုပါ။ ဤ launcher သည်
**ACP registration** (`src/lib/acp/registry.ts`, `gemini --acp`) နှင့် သီးခြားဖြစ်ပြီး၊
ACP registration သည် `/dashboard/acp-agents` အတွက် agent-protocol integration အဖြစ်
ဆက်လက်တည်ရှိနေသည်။

## လက်တွေ့ smoke sweep (ရွေးချယ်ဖွင့်သုံးနိုင်သည်)

တိကျသေချာစွာ ထပ်တလဲလဲလုပ်ဆောင်နိုင်သော launch-plan regression ကို CI (`tests/unit/cli/run-command.test.ts`,
`tests/unit/cli/run-execution.test.ts`) တွင် လုပ်ဆောင်ပါသည်။ လက်တွေ့ OmniRoute server နှင့် လက်တွေ့ binary များကို စစ်ဆေးအတည်ပြုရန် ရွေးချယ်ဖွင့်သုံးနိုင်သော harness ကို
`tests/integration/upstream-cli-smoke.int.test.ts` တွင် ထည့်သွင်းထားပါသည်။ ၎င်းသည် အလိုအလျောက် မည်သည့်အခါမျှ မလုပ်ဆောင်ပါ
(`RUN_CLI_SMOKE=1` မသတ်မှတ်ထားလျှင် sub-test တစ်ခုစီကို ကျော်သွားမည်)၊ အထောက်အထားကို တန်ဖိုးဖြင့်မဟုတ်ဘဲ env-var
အမည်ဖြင့် ပေးပို့သည်၊ မှတ်တမ်းတင်ထားသော output များမှ key ပုံစံ string များကို ဖုံးကွယ်သည်၊
binary ထည့်သွင်းမထားသော target များကို ကျော်သွားပြီး failure များကို boolean တန်ဖိုးသက်သက်အစား
auth / upstream / config ဟူ၍ အမျိုးအစားခွဲခြားသည်-

```bash
RUN_CLI_SMOKE=1 \
OMNIROUTE_SMOKE_BASE_URL="http://localhost:20128" \
OMNIROUTE_SMOKE_MODEL="<provider/model>" \
OMNIROUTE_SMOKE_API_KEY_ENV="OMNIROUTE_API_KEY" \
node --import tsx/esm --test tests/integration/upstream-cli-smoke.int.test.ts
```

ရွေးချယ်နိုင်သည်- `OMNIROUTE_SMOKE_TARGETS="codex,opencode,qwen"` သည် sweep ၏ နယ်ပယ်ကို ကန့်သတ်ပေးသည်၊
`OMNIROUTE_SMOKE_TIMEOUT_MS` သည် target တစ်ခုစီအတွက် သတ်မှတ်ထားသော 120s timeout ကို အစားထိုးသတ်မှတ်သည်။
