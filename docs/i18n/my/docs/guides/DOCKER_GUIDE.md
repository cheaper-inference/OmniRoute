## အမြန် လုပ်ဆောင်ခြင်း

> **Command တစ်ခုတည်းဖြင့် ကိုယ်တိုင် Host လုပ်မည်လား။**
> [ကိုယ်တိုင် Host လုပ်ခြင်း လမ်းညွှန်](../getting-started/SELF_HOST_GUIDE.md) ကို ကြည့်ပါ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ထုတ်ဝေထားသော Image +
> Redis၊ Loopback သီးသန့်၊ Profile ရွေးချယ်စရာ မရှိပါ)။ အောက်ပါ အမြန်လုပ်ဆောင်နည်းသည်
> အခြားနေရာတွင် Redis ကို လုပ်ဆောင်ထားပြီးသား အသုံးပြုသူများအတွက်
> Container တစ်ခုတည်း အသုံးပြုသည့် နည်းလမ်းဖြစ်သည်။

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Environment File ဖြင့်

```bash
# ဦးစွာ .env ကို မိတ္တူကူးပြီး တည်းဖြတ်ပါ
cp .env.example .env

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Docker Compose

```bash
# အခြေခံ Profile (CLI Tool မပါဝင်ပါ)
docker compose --profile base up -d

# CLI Profile (Claude Code၊ Codex၊ OpenClaw တို့ ထည့်သွင်းပြီးသား)
docker compose --profile cli up -d

# Host Profile (Linux ကို ဦးစားပေးသည်၊ Host CLI Binary များကို ဖတ်ရှုခွင့်သာဖြင့် Mount လုပ်သည်)
docker compose --profile host up -d

# Web Profile (Web-session Provider များအတွက် Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI Sidecar ကို ပေါင်းစပ်ပါ
docker compose --profile cli --profile cliproxyapi up -d
```

## ရရှိနိုင်သော Profile များ

OmniRoute တွင် အဓိက ဖြန့်ချမှုပုံစံများအတွက် Compose Profile များ ပါဝင်သည်။ သင့်ပတ်ဝန်းကျင်နှင့် ကိုက်ညီသည့် Profile ကို ရွေးချယ်ပါ။

| Profile       | Service          | အသုံးပြုသင့်သည့်အချိန်                                                                                                                                            | Command                                      |
| ------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (မူလ)  | `omniroute-base` | Headless Server / အနည်းဆုံး Runtime၊ Provider CLI များ ထည့်သွင်းမထားပါ                                                                                            | `docker compose --profile base up -d`        |
| `cli`         | `omniroute-cli`  | `omniroute providers/setup/doctor` နှင့် ထည့်သွင်းပြီးသား CLI များ (Codex၊ Claude Code၊ Droid၊ OpenClaw) ကို ခေါ်သုံးသည့် Agentic Workflow များ                   | `docker compose --profile cli up -d`         |
| `host`        | `omniroute-host` | `~/.local/bin`၊ `~/.codex`၊ `~/.claude` စသည်တို့ကို ဖတ်ရှုခွင့်သာဖြင့် Mount လုပ်ကာ Host CLI များထံ `network_mode` ကဲ့သို့ ဝင်ရောက်အသုံးပြုလိုသော Linux Host များ | `docker compose --profile host up -d`        |
| `cliproxyapi` | `cliproxyapi`    | Upstream CLI Proxy ပြုလုပ်ရန် Port `8317` ပေါ်တွင် [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) Sidecar ကို လုပ်ဆောင်ရန်                           | `docker compose --profile cliproxyapi up -d` |
| `web`         | `omniroute-web`  | Browser လိုအပ်သော Web-session Provider များ — `gemini-web`၊ `claude-web`၊ `claude-turnstile` (`runner-web` ကို Build လုပ်ပြီး Chromium ပါဝင်သည်)                  | `docker compose --profile web up -d`         |

> Profile များစွာကို ပေါင်းစပ်အသုံးပြုနိုင်သည် — `docker compose --profile cli --profile cliproxyapi up -d`။

## OmniRoute ကို Docker တွင် လုပ်ဆောင်နေစဉ် host CLI ကိရိယာများကို စီစဉ်သတ်မှတ်ခြင်း

`omniroute setup-codex`၊ `setup-claude`၊ `config set <tool>` နှင့် dashboard ၏
**စီစဉ်သတ်မှတ်ချက်ကို သိမ်းဆည်းရန်** ခလုတ်တို့သည် `~/.codex/*.config.toml` ကဲ့သို့သော ဖိုင်များကို ရေးသားသည်။ ထိုလမ်းကြောင်းများသည်
CLI အမှန်တကယ် လုပ်ဆောင်နေသည့် စက်ပေါ်တွင်သာ အဓိပ္ပာယ်ရှိသည်။ ၎င်းတို့ကို container အတွင်း
လုပ်ဆောင်ပါက ရေးသားမှုသည် container ၏ ကိုယ်ပိုင် home (`/home/node` —
image သည် `USER node` ဖြင့် လုပ်ဆောင်သည်) ထဲသို့ ရောက်ရှိသွားမည်ဖြစ်ပြီး မည်သည့် host CLI ကမျှ ထိုနေရာမှ ဖတ်မည်မဟုတ်သည့်အပြင်
container ကို ပြန်လည်ဖန်တီးသည့်အချိန်တွင်လည်း ပယ်ဖျက်ခံရမည်ဖြစ်သည်။

OmniRoute သည် ဤအခြေအနေကို ရှာဖွေသိရှိပြီး သင် အသုံးမပြုနိုင်သည့် အောင်မြင်မှုကို အစီရင်ခံမည့်အစား
ညွှန်ကြားချက်များနှင့်အတူ ရေးသားမှုကို ငြင်းပယ်သည်- CLI သည် `2` ဖြင့် ထွက်ပြီး API သည် `422`
နှင့် `containerEphemeralTarget: true` ကို ပြန်လည်ဖြေကြားသည်။

### အကြံပြုထားသည့်နည်းလမ်း- CLI ကို host ပေါ်တွင် လုပ်ဆောင်ပြီး OmniRoute ကို Docker တွင် လုပ်ဆောင်ပါ

Container သည် API ကို ဝန်ဆောင်မှုပေးပြီး CLI သည် သင့် host ကိရိယာများကို စီစဉ်သတ်မှတ်ပေးသည်။

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI ကို container သို့ ချိတ်ဆက်ရန် ညွှန်ပါ
omniroute setup-codex                      # သင့် host ပေါ်ရှိ အမှန်တကယ် ~/.codex ထဲသို့ ရေးသားသည်
```

Codex၊ Claude Code၊ Cursor သို့မဟုတ် အလားတူကိရိယာများကို သင့်
laptop ပေါ်တွင် လုပ်ဆောင်ပါက ဤနည်းလမ်းသည် မှန်ကန်သော ရွေးချယ်မှုဖြစ်သည် — ပုံမှန် စီစဉ်အသုံးပြုမှုမှာလည်း ဤအတိုင်းဖြစ်သည်။

### အခြားနည်းလမ်း- host config directory များကို bind-mount လုပ်ပါ (`host` profile)

Container ကိုယ်တိုင်က သင့် host config ကို ရေးသားစေလိုပါက directory များကို
mount လုပ်ပြီး `CLI_CONFIG_HOME` ကို mount root သို့ ညွှန်ပါ။ `host` profile တွင်
၎င်းကို ပြုလုပ်ပြီးသားဖြစ်သည်-

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

Bind mount ကြောင့်သာ ထိုလမ်းကြောင်းကို ယုံကြည်စိတ်ချနိုင်ခြင်းဖြစ်သည်- OmniRoute သည်
`/proc/self/mountinfo` ကို ဖတ်ပြီး mount လုပ်ထားသည့် လမ်းကြောင်းများ (နှင့် child များက mount များဖြစ်သော
directory များကိုလည်း ခွင့်ပြုသည်၊ ၎င်းသည် အထက်ပါ `/host-home` ပုံစံနှင့် အတိအကျ ကိုက်ညီသည်) သို့
ရေးသားခြင်းကို ခွင့်ပြုကာ mount မလုပ်ထားသော လမ်းကြောင်းများကို ဆက်လက်ငြင်းပယ်ထားသည်။

### နောက်ဆုံးရွေးချယ်စရာ- container ၏ ကိုယ်ပိုင် CLI များကို စီစဉ်သတ်မှတ်ပါ (လိုအပ်မှသာ အသုံးပြုပါ)

CLI များသည် container အတွင်း၌ အမှန်တကယ် ရှိနေပါက (`cli` profile) ရေးသားမှုသည်
ရည်ရွယ်ထားသည့် လုပ်ဆောင်ချက်ဖြစ်သည်။ မည်သည့် `setup-*` command တွင်မဆို `--allow-container-write` ကို ထည့်သွင်းပါ၊ သို့မဟုတ် server အတွက်
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ကို သတ်မှတ်ပါ။ Container ရှိနေသည့်ကာလထက် ကျော်လွန်၍
ထိုရေးသားမှု မတည်ရှိနိုင်ကြောင်း သတိပေးချက်နှင့်အတူ ရေးသားမှုကို ဆက်လက်လုပ်ဆောင်မည်ဖြစ်သည်။

> **လုံခြုံရေး သတိပေးချက် — `cli` profile + `docker.sock` mount။**
> Container အတွင်းရှိ auto-updater က host daemon မှ stack ကို ပြန်လည်ဖန်တီးနိုင်စေရန်
> `cli` profile သည် `/var/run/docker.sock` ကို bind-mount လုပ်သည်
> (`src/lib/system/autoUpdate.ts` သည် ထို socket ရှိမရှိ စစ်ဆေးပြီး
> မရှိပါက Docker လမ်းကြောင်းကို ကျော်သွားသည်)။ ထို socket သည် **host-root ယုံကြည်မှု
> နယ်နိမိတ်** ဖြစ်သည်- ၎င်းကို အသုံးပြုနိုင်သည့် မည်သည့်အရာမဆို host Docker daemon ကို
> root အဖြစ် ထိန်းချုပ်နိုင်သည် — host ပေါ်ရှိ မည်သည့် container ကိုမဆို ဖန်တီးခြင်း၊ စစ်ဆေးခြင်း၊ ရပ်တန့်ခြင်းနှင့် ဖယ်ရှားခြင်းတို့ ပြုလုပ်နိုင်သည်။
> သက်ရောက်မှုများ-
>
> 1. **`cli` profile ၏ port ကို network သို့ ဘယ်တော့မှ မဖွင့်ပါနှင့်။**
>    ၎င်းကို `127.0.0.1` တွင် publish လုပ်ပါ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN မှ ဝင်ရောက်နိုင်သော `cli` profile သည် dashboard အဆင့် RCE တစ်ခုခုကို
>    host အပြည့်အဝ ထိန်းချုပ်ခံရမှုအဖြစ် ပြောင်းလဲစေသည်။
> 2. **`cli` profile ထဲသို့ နောက်ထပ် host directory များကို bind မလုပ်ပါနှင့်။**
>    Docker socket နှင့် ထပ်ဆောင်း mount တစ်ခုခု ပေါင်းစပ်ခြင်းသည် container ကို သင့် filesystem နှင့် host config အား
>    အပြည့်အဝ ဖတ်ရှု/ရေးသားခွင့် ပေးလိုက်ခြင်းဖြစ်သည်။ ကိရိယာတစ်ခုက project တစ်ခုကို
>    မြင်ရန်လိုအပ်ပါက CLI binary ဖြင့် local တွင် လုပ်ဆောင်ပါ — ၎င်းကို
>    `cli` container ထဲသို့ mount မလုပ်ပါနှင့်။
>
> Container အတွင်း auto-update ကို မလိုအပ်ပါက `cli` profile ကို ပိတ်ထားပါ
> (`COMPOSE_PROFILES=core,redis` သို့မဟုတ် ပိုတိုသော သတ်မှတ်ချက်)။ အခြား profile များသည်
> Docker socket ကို mount မလုပ်ပါ။
>
> MITM နှင့် သက်ဆိုင်သော ခြိမ်းခြောက်မှုပုံစံအတွက် `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` ထဲသို့ compile မလုပ်ထားပါ) ကို
> ကြည့်ရှုပါ၊ ထို့ပြင် `codex`/`claude-code`/`droid`/`openclaw` binary မူလရင်းမြစ်ကွင်းဆက်အတွက်
> `docs/security/SUPPLY_CHAIN.md` ကို ကြည့်ရှုပါ။

## Redis Sidecar

OmniRoute သည် ဖြန့်ဝေထားသော rate limiter နှင့် မျှဝေထားသော cache အတွက် Redis ကို အသုံးပြုသည်။ `redis` service ကို `docker-compose.yml` ထဲတွင် **အမြဲတမ်း သတ်မှတ်ထားသည်** (၎င်းတွင် profile gate မရှိပါ)၊ ထို့ပြင် အခြားမည်သည့် profile နှင့်မဆို အတူတကွ စတင်သည်။

| အသေးစိတ်                        | တန်ဖိုး                                         |
| ------------------------------- | ----------------------------------------------- |
| Image                           | `redis:7-alpine`                                |
| Container အမည်                  | `omniroute-redis`                               |
| အတွင်းပိုင်း port               | `6379`                                          |
| Host port (အစားထိုးသတ်မှတ်ချက်) | `REDIS_PORT` (ပုံမှန်အားဖြင့် `6379`)           |
| Host bind (အစားထိုးသတ်မှတ်ချက်) | `REDIS_BIND_HOST` (ပုံမှန်အားဖြင့် `127.0.0.1`) |
| Volume                          | `omniroute-redis-data` → `/data`                |
| Healthcheck                     | `redis-cli ping` (10s ကြားကာလ)                  |

ဆက်စပ် environment variable များ-

- `REDIS_URL` — app ထဲသို့ ထည့်သွင်းပေးသော connection string (ပုံမှန်အားဖြင့် `redis://redis:6379`)။
- `REDIS_PORT` — Redis container အတွက် host ဘက်ရှိ port mapping။
- `REDIS_BIND_HOST` — port ကို publish လုပ်မည့် host interface။ ပုံမှန်အားဖြင့် `127.0.0.1` ဖြစ်သည်။

> **ပုံမှန်အားဖြင့် loopback ကို အသုံးပြုရသည့်အကြောင်းရင်း-** sidecar သည် `requirepass` မပါဘဲ အလုပ်လုပ်ပြီး app
> container များက compose network (`redis:6379`) မှတစ်ဆင့် ၎င်းထံ ဆက်သွယ်ကြသည် — publish လုပ်ထားသော port သည်
> host ဘက်ရှိ tooling (`redis-cli`၊ local `npm run dev`) အတွက်သာ ဖြစ်သည်။ `0.0.0.0` တွင် publish လုပ်ခြင်းက
> authentication မပါသော Redis ကို သင့် LAN ရှိ host အားလုံးထံ ဖွင့်ပေးလိုက်မည်ဖြစ်သည်။ `REDIS_BIND_HOST=0.0.0.0` ဟု သတ်မှတ်ပါက
> service `command:` ထဲတွင် `--requirepass` ကိုလည်း ထည့်ပါ။

**Redis ကို ပိတ်ထားခြင်း** အား မထောက်ခံပါ (rate limiter သည် in-memory fallback ကို အသုံးပြုရသဖြင့် စွမ်းဆောင်ရည် ကျဆင်းမည်)။ မဖြစ်မနေ လုပ်ဆောင်ရမည်ဆိုပါက `docker-compose.yml` ထဲရှိ `redis:` service block ကို ဖယ်ရှား/မှတ်ချက်အဖြစ် ပြောင်းပါ သို့မဟုတ် zero အထိ scale လုပ်ပါ-

```bash
docker compose up -d --scale redis=0
```

## Production Compose

Dev နှင့်အတူ သီးခြားခွဲထုတ်ထားသော production snapshot တစ်ခုကို လည်ပတ်ရန် `docker-compose.prod.yml` ကို အသုံးပြုပါ။

| အသေးစိတ်               | တန်ဖိုး                                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| File                   | `docker-compose.prod.yml`                                                                      |
| ပုံမှန် dashboard port | `PROD_DASHBOARD_PORT=20130` (အတွင်းပိုင်း `${DASHBOARD_PORT:-20128}` သို့ mapped လုပ်ထားသည်)   |
| ပုံမှန် API port       | `PROD_API_PORT=20131`                                                                          |
| Image                  | `omniroute:prod` (`runner-cli` target မှ build လုပ်ထားသည်)                                     |
| Redis container        | `omniroute-redis-prod` (`redis:8.6.2`၊ သီးခြား `redis-prod-data` volume)                       |
| Data volume            | `omniroute-prod-data` (အမည်ပေးထားပြီး rebuild များအကြား ဆက်လက်သိမ်းဆည်းထားသည်)                 |
| Healthcheck များ       | `node healthcheck.mjs` + `redis-cli ping`၊ `depends_on` ကို Redis health ဖြင့် gate လုပ်ထားသည် |

အသုံးပြုပုံ-

```bash
# Production stack ကို build လုပ်ပြီး စတင်ပါ
docker compose -f docker-compose.prod.yml up -d --build

# Log များကို ဆက်တိုက်ကြည့်ရှုပါ
docker compose -f docker-compose.prod.yml logs -f

# ရပ်တန့်ဖယ်ရှားပါ (volume များကို ဆက်လက်သိမ်းထားပါ)
docker compose -f docker-compose.prod.yml down
```

Prod stack သည် dev compose နှင့် တစ်ပြိုင်နက် လည်ပတ်သည် (container အမည်များ၊ port များနှင့် volume များ မတူညီပါ)။ ထို့ကြောင့် production ကို ဆက်လက်လည်ပတ်စေထားစဉ် local တွင် ဆက်လက်ပြင်ဆင်စမ်းသပ်နိုင်သည်။

## Dockerfile အဆင့်များ

Repository တွင် multi-stage Dockerfile (`Dockerfile`) တစ်ခု ပါဝင်သည်။ အဆင့်လေးခုကို အသုံးပြုနိုင်ပြီး မိမိအသုံးပြုမည့်အခြေအနေနှင့် ကိုက်ညီသော `target` ကို ရွေးချယ်ပါ။

| အဆင့်         | Base image            | ရည်ရွယ်ချက်                                                                                                                                                                                                                                                                                                                                                  |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `builder`     | `node:26-trixie-slim` | Dependencies များကို ထည့်သွင်းပြီး (`npm ci --legacy-peer-deps`) `npm run build` ကို လုပ်ဆောင်သည် (ပုံသေအားဖြင့် Turbopack — အောက်ရှိ Build-time resources ကို ကြည့်ပါ)                                                                                                                                                                                      |
| `runner-base` | `node:26-trixie-slim` | Next.js standalone output ပါဝင်သော production runtime ဖြစ်သည်။ **မည်သည့် provider CLI မျှ ထည့်သွင်းပေးထားခြင်း မရှိပါ။**                                                                                                                                                                                                                                     |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` နှင့် global CLI များဖြစ်သော `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw` တို့ကို ထည့်သွင်းပေးသည်။ **Agentic workflow များအတွက် ၎င်းကို ရွေးချယ်ပါ။**                                                                                                                                              |
| `runner-web`  | `runner-base`         | Web-session provider များဖြစ်သော `gemini-web`, `claude-web`, `claude-turnstile` အတွက် Playwright နှင့် Chromium browser (`--with-deps`) ကို ထည့်သွင်းပေးသည်။ **အဆိုပါ provider များကို အသုံးပြုသည့်အခါ ၎င်းကို ရွေးချယ်ပါ** — ၎င်းမပါဝင်သော ရိုးရိုး image သည် request ပြုလုပ်ချိန်တွင် အလုပ်မလုပ်ပါ (Release Channels အောက်ရှိ `-web` မှတ်ချက်ကို ကြည့်ပါ)။ |

သတ်မှတ်ထားသော target တစ်ခုကို ကိုယ်တိုင် build လုပ်ရန်-

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### Build လုပ်ချိန် အရင်းအမြစ်များ

Build arg သုံးခုက `builder` အဆင့်အတွက် လိုအပ်သော resource ပမာဏကို ထိန်းချုပ်သည်။ ၎င်းတို့သည် build လုပ်ချိန်အတွက်သာ ဖြစ်သည် —
`OMNIROUTE_MEMORY_MB` (အောက်တွင်ဖော်ပြထားသည်) သည် runtime အတွက် သီးခြားထိန်းချုပ်မှုတစ်ခု ဖြစ်သည်။

| Build arg                   | ပုံသေတန်ဖိုး | သက်ရောက်မှု                                                                                                                 |
| --------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`          | `0` သည် webpack ဖြင့် build လုပ်သည်- peak memory ပိုနည်းသော်လည်း ပိုနှေးသည်။ `1` သည် Turbopack ကို အသုံးပြုရန် ရွေးချယ်သည်။ |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`       | စတင်ထားသော `next build` အတွက် V8 heap အများဆုံးကန့်သတ်ချက် (`--max-old-space-size`) ဖြစ်သည်။                                |
| `OMNIROUTE_BUILD_WORKERS`   | `2`          | `CIRCLE_NODE_TOTAL` သို့ တန်ဖိုးပေးသည်။ Next သည် page-data စုဆောင်းရန် `workers = N - 1` ဟု ဆုံးဖြတ်သည်။                    |

ကြီးမားသော builder ပေါ်တွင် မြှင့်တင်သင့်သည်မှာ `OMNIROUTE_BUILD_WORKERS` ဖြစ်ပြီး၊ resource ကန့်သတ်ထားသော build တစ်ခုသည် `✓ Compiled successfully` **ပြီးနောက်** ရပ်တန့်သွားပါက သံသယထားသင့်သည်မှာလည်း ၎င်းပင်ဖြစ်သည်။ Page-data worker တစ်ခုစီသည် သီးခြား process တစ်ခုဖြစ်သကဲ့သို့ parent `next build` ကိုယ်တိုင်လည်း သီးခြား process တစ်ခုဖြစ်သည်။ လက်တွေ့ VPS ပေါ်တွင် ပြန်လည်စမ်းသပ်မှု (issue #7518) အရ process တစ်ခုစီ၏ peak RSS သည် `NODE_OPTIONS` heap flag နှင့် မသက်ဆိုင်ဘဲ ~4.5 GB ရှိကြောင်း တိုင်းတာတွေ့ရှိခဲ့သည် (Turbopack သည် V8 heap ပြင်ပရှိ native/Rust memory တွင် compile လုပ်သည်)။ ပုံသေတန်ဖိုး `2` (→ worker 1 ခု၊ စုစုပေါင်း process 2 ခု) ကို publish pipeline အသုံးပြုသည့် 16 GB / 4 vCPU GitHub-hosted runner များအတွက် သတ်မှတ်ထားသည်။ `8` (→ worker 7 ခု) ထားသောအခါ ထို runner သည် memory ကုန်သွားပြီး buildkit က အဆင့်ကို `ResourceExhausted: ... cannot allocate memory` ဖြင့် မအောင်မြင်ခဲ့သည်။ Process တစ်ခုချင်းစီ၏ RSS ကို ခန့်မှန်းခြင်းအစား တိုက်ရိုက်တိုင်းတာသောအခါ `3` (→ worker 2 ခု) သည်ပင် မလုံလောက်သေးပါ။ `tests/unit/docker-build-memory-budget.test.ts` သည် တိုင်းတာထားသော ကိန်းဂဏန်းနှင့် နှိုင်းယှဉ်တွက်ချက်ပြီး ထိန်းချုပ်မှုနှစ်ခုအနက် တစ်ခုခုက runner ၏ စွမ်းရည်ထက် ကျော်လွန်ပါက မအောင်မြင်စေသည်။

Turbopack သည် V8 heap ၏ **ပြင်ပ** တွင်ရှိသော native Rust memory ကို အသုံးပြု၍ compile လုပ်သောကြောင့် `OMNIROUTE_BUILD_MEMORY_MB` ဖြင့် ၎င်းကို ကန့်သတ်၍ မရပါ။ Memory အများဆုံးပမာဏ ကန့်သတ်ထားသော host တစ်ခုတွင် build ကို OOM killer က error စာသားလုံးဝမပြဘဲ SIGKILL လုပ်သွားမည်ဖြစ်သည် — `Creating an optimized production build` အလယ်တွင် ရိုးရိုးရပ်သွားသဖြင့် memory မလုံလောက်ခြင်းထက် ရပ်တန့်စောင့်ဆိုင်းနေသကဲ့သို့ ထင်ရသည်။ ထို့ကြောင့် `npm run dev` / `npm run build` တွင် Turbopack သည် code ၏ ပုံသေဖြစ်သော်လည်း `Dockerfile` က webpack (`OMNIROUTE_USE_TURBOPACK=0`) ကို ပုံသေအဖြစ် သတ်မှတ်ထားခြင်းဖြစ်သည်။ မည်သည့် build arg မျှ မပါသော `docker build .` (Railway နှင့် အခြား one-click host များ လုပ်ဆောင်သည့်ပုံစံ) သည် memory ကန့်သတ်ထားသော builder ပေါ်တွင် အကြောင်းကြားချက်မရှိဘဲ ပျက်သွားခြင်း မဖြစ်ရပါ။ Publish လုပ်ထားသော image များသည် `docker-publish.yml` တွင် `OMNIROUTE_USE_TURBOPACK=0` ကို အတိအလင်း ပေးထားပြီးဖြစ်သည်။ RAM များစွာရှိသော builder တစ်ခုတွင် ပိုမိုမြန်ဆန်စွာ build လုပ်ရန် Turbopack ကို ရွေးချယ်အသုံးပြုနိုင်သည်-

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ကို ဖွင့်ထားသောကြောင့် `next build` သည် parent process **နှင့်** worker process နှစ်ခုလုံးကို လုပ်ဆောင်ပြီး process တစ်ခုစီက `OMNIROUTE_BUILD_MEMORY_MB` ကို သီးခြားလိုက်နာသည်။ ထို့ကြောင့် container ၏ အများဆုံးကန့်သတ်ပမာဏကို ထိုတန်ဖိုး၏ တစ်ဆမဟုတ်ဘဲ အကြမ်းဖျင်း နှစ်ဆထက်ပို၍ သတ်မှတ်ပါ။

ဤ tree ပေါ်တွင် တိုင်းတာထားသော ရလဒ်များ (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`)-

| Bundler   | Container အများဆုံးကန့်သတ်ပမာဏ | ရလဒ်                                                      |
| --------- | ------------------------------ | --------------------------------------------------------- |
| Turbopack | 8 GiB / 16 GiB                 | နှစ်မျိုးလုံးတွင် အကြောင်းကြားချက်မရှိဘဲ OOM-kill ဖြစ်သည် |
| webpack   | 8 GiB                          | Build worker ကို SIGKILL လုပ်ခံရသည်                       |
| webpack   | 12 GiB                         | အောင်မြင်ပြီး peak ပမာဏသည် 11.1 GiB ရှိသည်                |

### Runtime ပုံသေတန်ဖိုးများ

`runner-base` က export လုပ်ထားသော ပုံသေတန်ဖိုးများ- `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`။

Docker အတွင်းရှိ memory အပြုအမူ-

- Image သည် `OMNIROUTE_MEMORY_MB=1024` ကို သတ်မှတ်ပြီး ၎င်းမှ `NODE_OPTIONS=--max-old-space-size=1024` ကို ရယူသတ်မှတ်သည်။
- အမှန်တကယ် server process ကို standalone launcher က စတင်ပေးပြီး၊ ၎င်းသည် `OMNIROUTE_MEMORY_MB` ကို ဖတ်ကာ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ကို ထပ်ပေါင်းသည်။
- Node သည် ထပ်တလဲလဲပါရှိသော `--max-old-space-size` တန်ဖိုးများအနက် နောက်ဆုံးတန်ဖိုးကို အသုံးပြုသောကြောင့် `OMNIROUTE_MEMORY_MB` ကို သတ်မှတ်ခြင်းဖြင့် အမှန်တကယ်သက်ရောက်မည့် Docker heap ကန့်သတ်ချက်ကို ထိန်းချုပ်နိုင်သည်။
- Image က ၎င်းကို အမြဲသတ်မှတ်ထားသောကြောင့် launcher ၏ RAM ပမာဏအလိုက် ချိန်ညှိသည့် မူလ fallback သည် Docker အောက်တွင် မည်သည့်အခါမျှ အသုံးမဝင်ပါ။ Workload အတွက် ၎င်းကို တိတိကျကျ မြှင့်သတ်မှတ်ပါ (အောက်ပါဇယားကို ကြည့်ပါ)။ Coding-agent `/v1/responses` အတွက် `2048` သည်ပင် မလုံလောက်သေးပါ။

### Coding agent များအတွက် runtime RAM

Docker ၏ မူလ 1 GiB သတ်မှတ်ချက်သည် dashboard/ပေါ့ပါးသော chat အတွက် အနိမ့်ဆုံးပမာဏသာဖြစ်ပြီး production အတွက် သင့်တော်သောပမာဏ မဟုတ်ပါ။ ရှည်လျားသော `POST /v1/responses` body များ (message ရာပေါင်းများစွာ၊ tool ဆယ်ဂဏန်းများစွာ) သည် compression လုပ်နေစဉ်အတွင်း in-memory graph အများအပြားကို ဆက်လက်ထိန်းသိမ်းထားသည်။ တစ်ခုလျှင် ~3 MiB / ~750k-token ခန့်ရှိပြီး တစ်စိတ်တစ်ပိုင်း အချိန်ထပ်နေသော request နှစ်ခုသည် **12 GiB** old-space တွင် V8 ကို ရပ်တန့်စေခဲ့သည် (`FATAL ERROR: Reached heap limit`)။ ထို့အပြင် 16 GiB cgroup OOM ကိုလည်း ကြုံတွေ့ခဲ့သည်။ [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ကို ကြည့်ပါ။

**cgroup `--memory` ကို heap ထက် ပိုများအောင်** သတ်မှတ်ပါ — native buffer များ၊ SQLite နှင့် compression intermediate များသည် V8 ပြင်ပတွင် ရှိနေသည်။

| Workload                                                           | `OMNIROUTE_MEMORY_MB`              | Container / cgroup                   | မှတ်ချက်များ                                                                                                                       |
| ------------------------------------------------------------------ | ---------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard၊ ပေါ့ပါးသော chat တစ်ခု                                   | `1024` (image မူလတန်ဖိုး)          | ≥2 GiB                               |                                                                                                                                    |
| Coding agent တစ်ခု (Claude/Codex/Grok)                             | `8192`                             | ≥10 GiB                              | ပုံမှန် single-session `/v1/responses`                                                                                             |
| တစ်ပြိုင်နက်တည်း လုပ်ဆောင်သော ရှည်လျားသည့် `/v1/responses` နှစ်ခု  | `10240`–`12288`                    | ≥12–16 GiB                           | ~12 GiB heap တွင် V8 ရပ်တန့်မှုကို တိုင်းတာတွေ့ရှိခဲ့သည်                                                                           |
| တစ်ပြိုင်နက်တည်း လုပ်ဆောင်သော ရှည်လျားသည့် context သုံးခုနှင့်အထက် | process တစ်ခုတည်းတွင် မလုပ်ပါနှင့် | အစဉ်လိုက်လုပ်ဆောင်ပါ / RAM ပိုထည့်ပါ | မူလ heavyweight admission တွင် in-flight 1 ခုသာ ခွင့်ပြုသည်။ RAM မတိုးဘဲ ၎င်းကို မြှင့်ခြင်းသည် ရပ်တန့်မှုကို ပြန်လည်ဖြစ်ပေါ်စေသည် |

Bare metal ပေါ်ရှိ `omniroute serve` သည် `OMNIROUTE_MEMORY_MB` ကို **မသတ်မှတ်ထားသည့်အခါ** RAM ၏ ~35% ခန့်ကို ချိန်ညှိအသုံးပြုသည် (`[512, 4096]` အတွင်း ကန့်သတ်ထားသည်)။ Docker သည် `1024` ကို အမြဲသတ်မှတ်ထားသောကြောင့် တရားဝင် image တွင် အဆိုပါ ချိန်ညှိမှုသည် မည်သည့်အခါမျှ အလုပ်မလုပ်ပါ။

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

| `OMNIROUTE_BASE_PATH`         | App ကို reverse proxy နောက်တွင် လွှင့်တင်ထားသောအခါ အသုံးပြုသည့် URL subpath (ဥပမာ `/omniroute`)                                                                                                                                                                                                          | _(အလွတ် = root)_                 |
| `NEXT_PUBLIC_BASE_URL`        | Subpath ပါဝင်သော အများသုံး browser origin (ဥပမာ `https://host/omniroute`)                                                                                                                                                                                                                                | မသတ်မှတ်ထားပါ                    |
| `PROD_DASHBOARD_PORT`         | `docker-compose.prod.yml` အတွက် host ဘက်ခြမ်း dashboard port                                                                                                                                                                                                                                             | `20130`                          |
| `CLIPROXYAPI_PORT`            | `cliproxyapi` sidecar အတွက် host ဘက်ခြမ်း port                                                                                                                                                                                                                                                           | `8317`                           |

## လမ်းကြောင်းခွဲတစ်ခုပေါ်ရှိ Reverse Proxy (Traefik / nginx)

Next.js `basePath` ကို standalone bundle အတွင်းသို့ compile လုပ်ထားသည်။ OmniRoute သည် ထည့်သွင်းထားသော တန်ဖိုးကို app root ရှိ sentinel file တစ်ခုတွင် မှတ်တမ်းတင်ပြီး (`npm run build` ပြုလုပ်စဉ် ရေးသားကာ `scripts/docker/ensure-docker-base-path.mjs` က ဖတ်သည်) container စတင်ချိန်တွင် ၎င်းကို `OMNIROUTE_BASE_PATH` နှင့် နှိုင်းယှဉ်သည်။ တန်ဖိုးများ မတူညီဘဲ image ကို domain root အတွက် build လုပ်ထားပါက entrypoint သည် `node dev/run-standalone.mjs` မလုပ်ဆောင်မီ standalone manifests များ၊ ထည့်သွင်းထားသော `basePath`/`assetPrefix` literals များ (Next 16 သည် SSR asset URL များကို `assetPrefix` တစ်ခုတည်းမှ render လုပ်သောကြောင့် patcher က လမ်းကြောင်းခွဲကို ၎င်းထဲသို့ပါ တူညီစွာ ထည့်ပေးသည်)၊ ထည့်သွင်းထားသော `/_next/static` asset URL များ (client-reference manifests၊ media imports၊ ကြိုတင် render လုပ်ထားသော error pages) နှင့် client `process.env` shim တို့ကို ပြန်လည်ရေးသားသည်။

### Compose ဖြင့် build လုပ်ခြင်း (အကြံပြုထားသည်)

Image နှင့် runtime တို့ ကိုက်ညီစေရန် variable နှစ်ခုလုံးကို `.env` တွင် သတ်မှတ်ပြီးနောက် ပြန်လည် build လုပ်ပါ-

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml` သည် `OMNIROUTE_BASE_PATH` ကို Docker build-arg အဖြစ်နှင့် runtime environment variable အဖြစ် လွှဲပို့ပေးသည်။

### ကြိုတင် build လုပ်ထားသော root image + runtime လမ်းကြောင်းခွဲ

ဖြန့်ချိထားသော `diegosouzapw/omniroute:*` image များကို domain root အတွက် build လုပ်ထားသည်။ Runtime တွင် `OMNIROUTE_BASE_PATH` ကို သတ်မှတ်နိုင်ဆဲဖြစ်ပြီး container စတင်ချိန်တွင် bundle ကို တစ်ကြိမ် patch လုပ်ပေးမည်။ ၎င်းကို ကိုက်ညီသော public origin နှင့် တွဲဖက်သတ်မှတ်ပါ-

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

Reverse proxy ကို ပြင်ပလမ်းကြောင်း **အပြည့်အစုံ** လွှဲပို့ရန် စီစဉ်သတ်မှတ်ပါ (prefix ကို မဖြုတ်ပါနှင့်)။ Traefik သည် `StripPrefix` မသုံးဘဲ `PathPrefix(`/omniroute`)` ကို container သို့ route လုပ်သင့်သည်။ သို့မှသာ Next.js က `/omniroute/...` ကို လက်ခံရရှိပြီး asset များကို `/omniroute/_next/...` မှ ပေးပို့မည်ဖြစ်သည်။

Docker healthcheck သည် အသုံးပြုနေသော `OMNIROUTE_BASE_PATH` prefix ထည့်ထားသည့် ပေါ့ပါးသော `/healthz` lifecycle endpoint ကို စစ်ဆေးသည်။ လူကိုယ်တိုင်/ဒက်ရှ်ဘုတ်မှ ရောဂါရှာဖွေစစ်ဆေးရန် `/api/monitoring/health` ကို ဆက်လက်အသုံးပြုနိုင်သည်။ Container HEALTHCHECK ကို ထို endpoint သို့ ပြန်ညွှန်လိုပါက (ဥပမာ နက်ရှိုင်းသော ကျန်းမာရေးစစ်ဆေးမှုကို တင်းကျပ်စွာ အသုံးချရန်) `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ဟု သတ်မှတ်ပါ။ ထိုလမ်းကြောင်းသည် **နက်ရှိုင်းသော** စစ်ဆေးမှု (DB + monitoring အနှစ်ချုပ်) ဖြစ်သည်။ ပြန်လည်အသုံးပြုရန် ရွေးချယ်ပါက မကြာခဏ မလုပ်ဆောင်သော Docker `HEALTHCHECK` အတွက် သင့်လျော်သော်လည်း Kubernetes `livenessProbe` interval များအတွက်မူ **မသင့်လျော်ပါ**။

Orchestrator များ (Kubernetes၊ Nomad စသည်) အတွက်-

| Probe           | ဦးစားပေးရန်                                                                    | ရှောင်ရန်                                                                                     |
| --------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Liveness        | HTTP `GET /livez` သို့မဟုတ် ပင်မ port (`PORT`၊ မူလတန်ဖိုး `20128`) ပေါ်ရှိ TCP | `/api/monitoring/health` ကို liveness အဖြစ် အသုံးပြုခြင်း                                     |
| Readiness       | HTTP `GET /healthz`                                                            | event loop အလုပ်များနေခြင်းကို process သေသွားသည်ဟု သတ်မှတ်သော အလွန်တိုတောင်းသည့် timeout များ |
| Deep / blackbox | `/api/monitoring/health`                                                       | —                                                                                             |

`/healthz` သည် process lifecycle (`ok` / `starting` / `stopping`) ကို အစီရင်ခံသည်။ `/livez` သည် process အသက်ရှင်နေခြင်းကိုသာ စစ်ဆေးသည် (handler အလုပ်လုပ်နိုင်သည့်အခါတိုင်း 200 ပြန်ပေးပြီး readiness ကို မစောင့်ပါ)။ နှစ်ခုလုံးသည် request handling နှင့် တူညီသော Node event loop ပေါ်တွင် ဆက်လက်အလုပ်လုပ်သောကြောင့် CPU အဓိကအသုံးပြုသည့် catalog သို့မဟုတ် compression အလုပ်များက ၎င်းတို့ကို နှောင့်နှေးစေနိုင်သည် — အလုပ်များနေခြင်း ≠ သေဆုံးနေခြင်း။ HTTP probe များ timeout ဖြစ်ပါက TCP liveness ကို ဦးစားပေးပါ။ Probe ဆိုင်ရာ လမ်းညွှန်ချက်အပြည့်အစုံ-
[Monitoring လမ်းညွှန် — Kubernetes probe အကြံပြုချက်များ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)။

## Caddy ဖြင့် Docker Compose (HTTPS Auto-TLS)

Caddy ၏ အလိုအလျောက် SSL စီစဉ်ပေးမှုကို အသုံးပြု၍ OmniRoute ကို လုံခြုံစွာ ပြင်ပသို့ ဖွင့်ပေးနိုင်သည်။ သင့်ဒိုမိန်း၏ DNS A record သည် သင့်ဆာဗာ၏ IP ကို ညွှန်ထားကြောင်း သေချာပါစေ။

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth callback များ၊ dashboard လင့်ခ်များနှင့် ထုတ်လုပ်ထားသော အများသုံး URL များအတွက် browser တွင် အသုံးပြုမည့် origin။
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # အချိန်ဇယားသတ်မှတ်ထားသော job များ / self-fetch များအတွက် ဆာဗာအချင်းချင်း အသုံးပြုမည့် အတွင်းပိုင်း URL။
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy သည် upstream container အတွက် စံသတ်မှတ်ထားသော forwarding header များကို သတ်မှတ်ပေးသည်။ OmniRoute သည် OAuth callback များနှင့် ထုတ်လုပ်ထားသော အများသုံး
လင့်ခ်များအတွက် `NEXT_PUBLIC_BASE_URL` ကို တရားဝင်အများသုံး origin အဖြစ် အသုံးပြုသည်။
အထောက်အထားစစ်ဆေးပြီးသော dashboard write လုပ်ဆောင်ချက်များသည် same-origin request များနှင့် session ချိတ်ဆက်ထားသော CSRF
ကာကွယ်မှုကို အသုံးပြုသည်။ တိကျစွာသတ်မှတ်ထားသော configuration အစား ယုံကြည်ရသော forwarded header များမှ အများသုံး origin ကို
OmniRoute အား ရယူစေလိုသည့် အဆင့်မြင့် deployment များတွင်သာ `OMNIROUTE_TRUST_PROXY` ကို ဖွင့်ပါ။

## Cloudflare Quick Tunnel

Docker deployment များအတွက် dashboard ပံ့ပိုးမှုတွင် `Dashboard → Endpoints` ၌ တစ်ချက်နှိပ်ရုံဖြင့် အသုံးပြုနိုင်သော **Cloudflare Quick Tunnel** ပါဝင်သည်။ ပထမဆုံးဖွင့်သည့်အခါ လိုအပ်မှသာ `cloudflared` ကို ဒေါင်းလုဒ်လုပ်ပြီး သင့်လက်ရှိ `/v1` endpoint သို့ ယာယီ tunnel တစ်ခု စတင်ကာ ထုတ်လုပ်ထားသော `https://*.trycloudflare.com/v1` URL ကို သင်၏ ပုံမှန်အများသုံး URL အောက်တွင် တိုက်ရိုက်ပြသပေးသည်။

Endpoint tunnel panel များကို (Cloudflare၊ Tailscale၊ ngrok) အသုံးပြုနေသော tunnel ၏ အခြေအနေကို မပြောင်းလဲဘဲ `Settings → Appearance` မှ ပြသနိုင်သလို ဖျောက်ထားနိုင်သည်။

### Tunnel မှတ်ချက်များ

- Quick Tunnel URL များသည် ယာယီဖြစ်ပြီး restart လုပ်တိုင်း ပြောင်းလဲသည်။
- OmniRoute သို့မဟုတ် container ကို restart လုပ်ပြီးနောက် Quick Tunnel များကို အလိုအလျောက် ပြန်လည်ဖွင့်ပေးမည် မဟုတ်ပါ။ လိုအပ်သည့်အခါ dashboard မှ ပြန်လည်ဖွင့်ပါ။
- Managed install သည် လက်ရှိတွင် `x64` / `arm64` ရှိသော Linux၊ macOS နှင့် Windows ကို ပံ့ပိုးသည်။
- အရင်းအမြစ်ကန့်သတ်ထားသော container environment များတွင် အနှောင့်အယှက်ဖြစ်စေသော QUIC UDP buffer သတိပေးချက်များကို ရှောင်ရှားရန် Managed Quick Tunnel များသည် HTTP/2 transport ကို မူလသတ်မှတ်ချက်အဖြစ် အသုံးပြုသည်။ မတူညီသော transport ကို အသုံးပြုလိုပါက `CLOUDFLARED_PROTOCOL=quic` သို့မဟုတ် `auto` ဟု သတ်မှတ်ပါ။
- Docker image များတွင် system CA root များ ပါဝင်ပြီး managed `cloudflared` သို့ လွှဲပေးထားသောကြောင့် container အတွင်း tunnel စတင်ချိန်၌ TLS ယုံကြည်မှုဆိုင်ရာ ချို့ယွင်းချက်များကို ရှောင်ရှားနိုင်သည်။
- OmniRoute အား ဒေါင်းလုဒ်လုပ်မည့်အစား ရှိပြီးသား binary ကို အသုံးပြုစေလိုပါက `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ဟု သတ်မှတ်ပါ။

| ------------------------------- | ------------------------------------------------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `:<version>` / `:<version>-web` | လက်မှတ်ရေးထိုးပြီး/version သတ်မှတ်ထားသော release | ပြောင်းလဲမရ                           | release အတိအကျတစ်ခုကို ပုံသေသတ်မှတ်ထားသော production deployment များ                                                                                 |
| `:latest` / `:latest-web`       | **ထုတ်ဝေထားပြီးသော** အမြင့်ဆုံး stable SemVer    | ပြောင်းလဲနိုင်သော stable pointer      | SemVer publish job လုပ်ဆောင်ပြီးနောက် stable release များကို လိုက်နာသည် — `main` သို့မဟုတ် မထုတ်ဝေရသေးသော `release/v*` commit များကို **မလိုက်နာပါ** |
| `:next` / `:next-web`           | လက်ရှိ မူလ `release/v*` branch                   | ပြောင်းလဲနိုင်သော pre-release pointer | အသုံးပြုနေသော release branch သို့ ထည့်သွင်းပြီးသော်လည်း stable release တွင် မပါဝင်သေးသည့် ပြင်ဆင်ချက်များကို စမ်းသပ်ရန်                              |
| `:main` / `:main-web`           | `main` branch                                    | ပြောင်းလဲနိုင်သော development pointer | Development နှင့် integration စမ်းသပ်မှုအတွက်သာ                                                                                                      |

#### Web-session provider များ: `-web` image များ

အထက်ပါ channel တစ်ခုစီတွင် `runner-web` stage မှ တည်ဆောက်ထားသော `-web` tag (`:latest-web`၊ `:<version>-web`၊ `:next-web`၊ `:main-web`) လည်း ရှိသည် — ၎င်းသည် တူညီသော image တွင် Playwright နှင့် Chromium browser ကို ထည့်သွင်းထားခြင်းဖြစ်သည်။ ပုံမှန် image တွင် Chromium **မပါဝင်ပါ**။ `gemini-web`၊ `claude-web` နှင့် `claude-turnstile` တို့သည် ၎င်းကို လိုအပ်သည်။

ချို့ယွင်းချက်သည် startup အချိန်တွင် မဖြစ်ဘဲ နောက်ပိုင်းမှ ဖြစ်ပေါ်သည်။ အဆိုပါ provider များသည် ၎င်းတို့၏ model များကို စာရင်းပြုစုပြီး dashboard တွင် ချိတ်ဆက်ထားသည့်အဖြစ် ပြသသော်လည်း ပထမဆုံး request တွင်သာ အောက်ပါအမှားဖြင့် မအောင်မြင်ပါ။

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

အဆိုပါ provider များကို အသုံးပြုပါက သင်လက်ရှိအသုံးပြုနေသော channel ၏ `-web` tag ကို pull လုပ်ပါ — အခြားမည်သည့်အရာမျှ ပြောင်းလဲမည်မဟုတ်ပါ။ npm/CLI install တစ်ခုတွင် (Docker image မပါဘဲ) အလားတူ ပျောက်နေသောအစိတ်အပိုင်းမှာ browser binary ဖြစ်သည်။ host ပေါ်တွင် `npx playwright install chromium` ကို လုပ်ဆောင်ပါ။

#### Pre-release channel ကို အသုံးပြုခြင်း

`next` ချန်နယ်ကို လက်ရှိ မူလ `release/v*` branch သို့ push ပြုလုပ်တိုင်း ပြန်လည်တည်ဆောက်ပြီး AMD64 နှင့် ARM64 နှစ်မျိုးလုံးအတွက် ထုတ်ဝေသည်။ အဟောင်း maintenance branch များက ၎င်းကို overwrite မလုပ်နိုင်ပါ။ နောက်ထပ် stable tag မထုတ်မီ လက်ရှိအသုံးပြုနေသော release branch သို့ merge လုပ်ပြီးသည့် ပြင်ဆင်ချက်များပါဝင်သော pull လုပ်နိုင်သည့် image ကို ဤချန်နယ်က ပံ့ပိုးပေးသည်။

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose အတွက် ရွေးချယ်ထားသော profile က အသုံးပြုသည့် image tag ကို override လုပ်ပြီးနောက် service ကို pull လုပ်၍ ပြန်လည်ဖန်တီးပါ။

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ဘေးကင်းလုံခြုံမှုနှင့် ပြန်လည်နောက်ဆုတ်ခြင်း

`next` သည် ပြောင်းလဲနေသော pre-release ချန်နယ်တစ်ခုဖြစ်သည်။ လက်ရှိအသုံးပြုနေသော release branch သို့ push ပြုလုပ်သည့်အခါတိုင်း ပြောင်းလဲနိုင်ပြီး **production တွင် အသုံးပြုရန် ပံ့ပိုးမထားပါ**။ သတ်မှတ်ထားသော build တစ်ခုကို အကဲဖြတ်နေစဉ် image digest ကို pin လုပ်ထားပါ။

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

စမ်းသပ်ခြင်းမပြုမီ OmniRoute data volume သို့မဟုတ် bind-mounted data directory ကို backup ပြုလုပ်ထားပါ။ နောက်သို့ပြန်သွားရန် ယခင်အသုံးပြုခဲ့သော stable version သို့မဟုတ် digest ကို ပြန်လည်အသုံးပြုပြီး container ကို ပြန်လည်ဖန်တီးပါ။

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

release-branch build တစ်ခုသည် `latest` ကို မည်သည့်အခါမျှ ရွှေ့ပြောင်းနိုင်မည်မဟုတ်ပါ။ သတ်မှတ်ချက်နှင့် ကိုက်ညီသော stable semantic version တစ်ခုသာ stable pointer ကို မြှင့်တင်နိုင်သည်။ `next` image များတွင် release image စစ်ဆေးခြင်းနှင့် CRITICAL အဆင့် အားနည်းချက်များကို တားဆီးသည့် gate ကို ဆက်လက်ထားရှိသည်။

**`latest` သည် git အတွက် နောက်ဆုံးပေါ်ဖြစ်ကြောင်း အာမခံချက်မဟုတ်ပါ။** `main` သို့မဟုတ် လက်ရှိအသုံးပြုနေသော `release/v*` branch တွင် merge လုပ်ထားသော ပြင်ဆင်ချက်များသည် stable SemVer image ကို ထုတ်ဝေပြီး publish job က `:latest` ကို မြှင့်တင်သည်အထိ `:latest` တွင် **မပါဝင်ပါ** (ထို SemVer နှင့် digest တူညီသည်)။ GitHub တွင် ပြင်ဆင်ချက်ကို ပြသထားပြီးဖြစ်သော်လည်း `latest` က မပြောင်းလဲဘဲ ရှိနေပါက release branch ကို စမ်းသပ်ရန် `:next` ကို pull လုပ်ပါ၊ သို့မဟုတ် SemVer tag ကို စောင့်ပါ။

| သင်လိုချင်သည့်အရာ                                                                          | အသုံးပြုရန်                                      |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| ပြောင်းလဲမှုမဖြစ်ရမည့် GitOps / production                                                 | `:X.Y.Z` (သို့မဟုတ် image digest) ကို pin လုပ်ပါ |
| ထုတ်ဝေထားသော stable များကို လိုက်နာပြီး release တစ်ခုစီတွင် ပြန်လည်ဖန်တီးခြင်းကို လက်ခံရန် | `:latest`                                        |
| မထုတ်ဝေရသေးသော `release/v*` commit များကို စမ်းသပ်ရန်                                      | `:next` (production မဟုတ်ပါ)                     |
| `main` ကို စမ်းသပ်ရန်                                                                      | `:main` (production မဟုတ်ပါ)                     |

## Docker ရှိ Dashboard အပ်ဒိတ်များ

ထုတ်ဝေထားသော image ကို အသုံးပြုသည့် container သည် မိမိကိုယ်တိုင် အစားထိုး၍ မရပါ။ OmniRoute က container တစ်ခုအတွင်း လည်ပတ်နေကြောင်း (`.git` checkout မရှိခြင်း၊ npm ဖြင့် ထည့်သွင်းထားခြင်း မဟုတ်ခြင်း) သိရှိသည့်အခါ ပင်မ dashboard ၏ အပ်ဒိတ် banner တွင် npm/git လမ်းညွှန်ချက်များအစား host ပေါ်တွင် လုပ်ဆောင်ရမည့် command ကို copy ခလုတ်နှင့်အတူ ပြသသည်-

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

Service အမည်ကို `AUTO_UPDATE_SERVICE` မှ ရယူသည် (မူလတန်ဖိုးမှာ `omniroute` ဖြစ်ပြီး `docker-compose.selfhost.yml` ထဲရှိ service ဖြစ်သည်)။ `pull` သည် ပြောင်းလဲနိုင်သော tag (`latest`, `next`) ကိုသာ ရွှေ့ပေးသည်။ သတ်မှတ်ထားသော `:X.Y.Z` tag ကို အသုံးပြုထားပါက tag ကို ဦးစွာ ပြင်ဆင်ပါ။

### Host trigger ဖိုင်ဖြင့် တစ်ချက်နှိပ် အပ်ဒိတ်များ

Container ကို host ပေါ်တွင် root အခွင့်အရေးပေးသည့် `/var/run/docker.sock` ကို mount မလုပ်ဘဲ **Update Now** ကို ဆက်လက်အသုံးပြုနိုင်ရန် (အထက်ရှိ `cli` profile သတိပေးချက်ကို ကြည့်ပါ) OmniRoute service တွင် `DOCKER_UPDATE_TRIGGER_FILE` ကို သတ်မှတ်ပြီး host ပေါ်တွင် watcher တစ်ခု လုပ်ဆောင်ပါ-

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

Path သည် `DATA_DIR` အတွင်း ရှိရမည် (relative တန်ဖိုးများကို ၎င်းနှင့် နှိုင်းယှဉ်၍ ဖြေရှင်းသည်)။ အခြားနေရာများကို ငြင်းပယ်မည်။ ထို့နောက် **Update Now** သည် `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }` ကို ထိုဖိုင်ထဲသို့ ရေးသားပြီး `202` ဖြင့် တုံ့ပြန်ကာ ဗားရှင်းအသစ် အလုပ်လုပ်သည်အထိ dashboard က `/api/system/version` ကို အကြိမ်ကြိမ် စစ်ဆေးပြီး ပြန်လည် load လုပ်သည်။ ဤ mode တွင် OmniRoute သည် shell သို့မဟုတ် Docker command တစ်ခုခုကို မည်သည့်အခါမျှ လုပ်ဆောင်ခြင်းမရှိပါ။ အခြားအပ်ဒိတ် လုပ်ဆောင်ချက်တိုင်းကဲ့သို့ပင် request ကို loopback/LAN client များထံမှသာ လက်ခံသည်။

Bind-mount လုပ်ထားသော data directory သည် host အတွက် စောင့်ကြည့်ရန် တည်ငြိမ်သော path တစ်ခုကို ပေးသည်။ နမူနာ `systemd` unit များ (`/srv/omniroute` ကို သင်၏ compose ဖိုင်နှင့် `data/` ပါရှိသည့် directory သို့ ပြင်ဆင်ပါ)-

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=OmniRoute dashboard အပ်ဒိတ် request များကို စောင့်ကြည့်ရန်

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=OmniRoute container ကို pull လုပ်ပြီး ပြန်လည်ဖန်တီးရန်

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

မအောင်မြင်သော လုပ်ဆောင်မှုတစ်ခု ထပ်ခါတလဲလဲ မဖြစ်စေရန် service သည် pull မလုပ်မီ request ကို ဖယ်ရှားသည်။ `DOCKER_UPDATE_TRIGGER_FILE` မရှိပါက dashboard သည် manual command လုပ်ငန်းစဉ်ကို ဆက်လက်အသုံးပြုသည်။

## အသုံးပြုနိုင်မှု- မူလ SQLite သည် replica တစ်ခုတည်းသာဖြစ်သည်

ပုံမှန် Docker / Kubernetes OmniRoute သည် **Node process တစ်ခု + SQLite writer တစ်ခု** ဖြစ်သည်။ ဤ topology တွင် high availability ကို **ပံ့ပိုးမထားပါ**။

| ကန့်သတ်ချက်                                     | အကျိုးဆက်                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Writer တစ်ခုတည်း                                | SQLite ဖိုင်တစ်ခုတည်းကို အသုံးပြု၍ replica အများအပြားကို **မလုပ်ဆောင်ပါနှင့်**။ ထိုသို့လုပ်ပါက DB ပျက်စီးမည်။                                                                                                                                                                                                                                                                                    |
| ပြန်လည်ဖန်တီးခြင်း / restart / HEALTHCHECK kill | လက်ရှိလုပ်ဆောင်နေသော SSE၊ dashboard session များနှင့် memory အတွင်းရှိ state အားလုံး **လုံးဝပြတ်တောက်မည်**။ ချိတ်ဆက်ထားသော client အားလုံး ပြတ်တောက်မည်။ Endpoint မရှိသည့် အချိန်ကာလအတွင်း request အသစ်များသည် OmniRoute JSON မဟုတ်ဘဲ reverse-proxy **`502 Bad Gateway: Unknown error`** ကို ရရှိမည်ဖြစ်သောကြောင့် client များသည် ၎င်းကို provider ချို့ယွင်းမှုနှင့် ခွဲခြားမသိနိုင်ပါ (#11015)။ |
| `/healthz` နှင့် event loop တစ်ခုတည်း           | အလုပ်များနေသော catalog သို့မဟုတ် compression tick တစ်ခုက probe များကို နှောင့်နှေးစေနိုင်ပြီး timeout တိုတောင်းပါက **တစ်ခုတည်းသော** replica ကို restart လုပ်မည်။                                                                                                                                                                                                                                 |

**Probe ဇယား** ([Kubernetes probe အကြံပြုချက်များ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ကိုလည်း ကြည့်ပါ)-

| Probe             | ပစ်မှတ်                                                                | မသုံးရမည့်အရာ                                                                        |
| ----------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Liveness          | `PORT` ပေါ်ရှိ TCP (မူလတန်ဖိုး `20128`) သို့မဟုတ် soft HTTP `/healthz` | `/api/monitoring/health`                                                             |
| Readiness         | HTTP `GET /healthz`                                                    | Event loop အလုပ်များနေခြင်းကို ရပ်တန့်သွားသည်ဟု သတ်မှတ်သော တင်းကျပ်သည့် timeout များ |
| အသေးစိတ် / လူများ | `/api/monitoring/health`                                               | အလိုအလျောက် kubelet liveness                                                         |

**အဆင့်မြှင့်တင်မှုများ-** session တိုင်း ပြတ်တောက်မည်ဟု မျှော်မှန်းထားပါ။ ဖြစ်နိုင်ပါက client များကို ကြိုတင်ရွှေ့ပြောင်းပါ။ မူလ SQLite တွင် rolling update မရှိပါ။ Compose `restart: unless-stopped` နှင့် Docker `HEALTHCHECK` တို့သည် container က Unhealthy ဖြစ်သည့်အခါ တစ်ခုတည်းသော process ကိုလည်း အစားထိုးမည်ဖြစ်ပြီး သက်ရောက်မှု အတိုင်းအတာမှာ အတူတူပင်ဖြစ်သည်။

**Replica တစ်ခုတည်း** အတွက် Kubernetes snippet (`Recreate` လိုအပ်သည်။ SQLite ဖိုင်တစ်ခုတည်းကို အသုံးပြုနေစဉ် `replicas` ကို မတိုးပါနှင့်)-

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` sleep သည် SIGTERM မတိုင်မီ kube က Service endpoint များကို ဖယ်ရှားနိုင်စေသောကြောင့် **အသစ်ဝင်လာသော** traffic များသည် ရပ်ဆိုင်းနေသည့် process သို့ ဆက်လက်မရောက်ရှိတော့ပါ။ လက်ရှိလုပ်ဆောင်နေဆဲ `/v1/responses` SSE များကို heavyweight admission lease များ (#11015) မှတစ်ဆင့် `SHUTDOWN_TIMEOUT_MS` (မူလသတ်မှတ်ချက် 30s) အထိ ပြီးဆုံးအောင် စောင့်ပေးပါသည်။ Process သို့ ရောက်ရှိနေဆဲ request အသစ်များသည် `503` + `Retry-After: 5` ကို ရရှိပါမည်။ အစားထိုး process က Ready ဖြစ်လာသည်အထိ Recreate ကြောင့် endpoint မရှိဘဲ ဖြစ်နေသည့်ကာလသည် ဝန်ဆောင်မှု လုံးဝပြတ်တောက်မှုအဖြစ် ဆက်လက်ရှိနေမည်ဖြစ်ပြီး — ၎င်းသည် SQLite topology ကြောင့်ဖြစ်ကာ probe သတ်မှတ်ချက်မှားယွင်းမှု မဟုတ်ပါ။

External Postgres / multi-writer HA သည် မှတ်တမ်းတင်ထားသော ပုံမှန်အသုံးပြုနိုင်သည့် လမ်းကြောင်းတစ်ခု **မဟုတ်ပါ**။ HA လိုအပ်ပါက replica တစ်ခုတည်းကို ထားရှိပါ သို့မဟုတ် project က သီးခြားစမ်းသပ်ပြီး မှတ်တမ်းတင်ထားသည့် topology တစ်ခုကို အသုံးပြုပါ။ Postgres/MySQL ဆိုင်ရာ လုပ်ဆောင်မှုများကို [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) တွင် ကြည့်ရှုနိုင်ပါသည်။ ၎င်းမထွက်ရှိမီအထိ **ကြီးမားသော** `/v1/responses` capacity ကို တိုးမြှင့်ရန် တစ်ခုတည်းသော ပံ့ပိုးထားသည့်နည်းလမ်းမှာ volume တစ်ခုတည်းပေါ်တွင် `replicas > 1` အသုံးပြုခြင်းမဟုတ်ဘဲ သီးခြားလွတ်လပ်သော process N ခု (နောက်အပိုင်း) ကို အသုံးပြုခြင်းဖြစ်သည်။

## အလျားလိုက်တိုးချဲ့ခြင်း: အမှီအခိုကင်းသော process N ခု

Node process တစ်ခုသည် **V8 heap တစ်ခု** ဖြစ်သည်။ တစ်ခုနှင့်တစ်ခု ထပ်နေသော ~3 MiB / ~750k-token coding-agent `POST /v1/responses` နှစ်ခု (RTK + Caveman) သည် ~12 Gi တွင် ထို heap ကို ရပ်တန့်စေပြီး (`FATAL ERROR: Reached heap limit`) 16 Gi cgroup တစ်ခုတွင် OOM ဖြစ်စေနိုင်သည်။ [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ကို ကြည့်ပါ။ ထိုတိုင်းတာချက်သည် **memory-budget** သတိပေးချက်ဖြစ်ပြီး တစ်ပြိုင်နက်လုပ်ဆောင်နိုင်သော ကြာမြင့်သည့် `/v1/responses` နှစ်ခုဟူသည့် ထုတ်ကုန်၏ အမြင့်ဆုံးကန့်သတ်ချက် မဟုတ်ပါ။ Heavyweight chat လက်ခံမှုကို ထို V8/cgroup အမြင့်ဆုံးကန့်သတ်ချက်တစ်ခုတည်းမှ အလိုအလျောက်တွက်ချက်ရရှိသော ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ဖြင့် ထိန်းချုပ်ထားသည် — အရွယ်အစားသတ်မှတ်ပြီးသား process တစ်ခုတွင် ၎င်းကို ပိုမြင့်အောင် override လုပ်ခြင်း (သို့မဟုတ် အဟောင်းဖြစ်သော `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` request-count cap ကို သတ်မှတ်ခြင်း) သည် ရပ်တန့်မှုကို ပြန်လည်ဖြစ်ပေါ်စေသည်။ အသေးစား chat များ၊ `/healthz`၊ `/v1/models` နှင့် MCP တို့သည် ထို cap ထဲတွင် **မပါဝင်ပါ**။

### Process တစ်ခုတည်း: ကြာမြင့်သည့် `/v1/responses` နှစ်ခုထက်ပို၍

**ကောင်းမွန်သည့် အခြေအနေရှိသော** process တစ်ခု (heap သည် `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` အောက်တွင်ရှိခြင်း၊ မူလတန်ဖိုး `0.75`) သည် process တစ်ခုလုံးအတွက် inflight-byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) တွင် နေရာရှိနေသေးပါက တစ်ပြိုင်နက်လုပ်ဆောင်သည့် ကြာမြင့်သော `POST /v1/responses` နှစ်ခုထက်ပို၍ လုပ်ဆောင်နိုင်သည်။ `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (မူလတန်ဖိုး 256 KiB) နှင့် ညီမျှသော သို့မဟုတ် ထိုထက်ကြီးသော body များသည် ဖွဲ့စည်းပုံရှုပ်ထွေးသော request များကဲ့သို့ တူညီသည့် heavyweight lease ကို ရယူပြီး တူညီသော [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` လွတ်မြောက်လမ်းကြောင်း (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ကို အသုံးပြုသည်။ တစ်ပြိုင်နက် ချိတ်ဆက်ထားသည့် ကြာမြင့်သော SSE client ဆယ်ဂဏန်းများ (operator များအနေဖြင့် 40–50 အထိ လိုအပ်လေ့ရှိသည်) သည် **memory-budget** ဆိုင်ရာ မေးခွန်းဖြစ်သည် — heap + primary/headroom slot များ + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ကို အရွယ်အစားသတ်မှတ်ရမည် — ထုတ်ကုန်၏ “အများဆုံး 2 ခု” ဟူသော တင်းကျပ်သည့် ကန့်သတ်ချက် မဟုတ်ပါ။ ဖိအားများနေသော heap သည် #7849 ပြန်မဖြစ်စေရန် retry လုပ်နိုင်သည့် `503` ဖြင့် request များကို ဆက်လက်လျှော့ချမည်။

**Heap များကို ပွားရန်** (အမှီအခိုကင်းသော V8 old-space များ) **လက်ရှိတွင်**:

| လုပ်ဆောင်ရန်                                                                                                                                                                                     | မလုပ်ဆောင်ရန်                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| **Container/pod N ခု** ကို တစ်ခုစီ၏ **ကိုယ်ပိုင်** `DATA_DIR` / volume ဖြင့် လုပ်ဆောင်ပါ                                                                                                         | SQLite file တစ်ခုတည်းအတွက် `replicas > 1` ဟု သတ်မှတ်ခြင်း                             |
| Heavy in-flight + healthy-headroom ကို heap / inflight-byte budget အရ အရွယ်အစားသတ်မှတ်ပါ။ 1–2 သည် ရှေးရိုးစွဲသော #7849 မူလတန်ဖိုးသာဖြစ်ပြီး ထုတ်ကုန်၏ တင်းကျပ်သည့် အမြင့်ဆုံးကန့်သတ်ချက် မဟုတ်ပါ | Process တစ်ခုတည်းအား RAM 8× နှင့် အကန့်အသတ်မရှိသော count cap ပေးခြင်း                 |
| ရွေးချယ်နိုင်သည်: **မျှဝေထားသော quota counter များ** အတွက် `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                                  | Redis ကို မျှဝေထားသော SQLite အဖြစ် သတ်မှတ်ယူဆခြင်း — ၎င်းသည် မဟုတ်ပါ                  |
| Provider secret များကို instance တစ်ခုစီသို့ မိတ္တူပွားပါ (သို့မဟုတ် အပိုင်းပိုင်းခွဲထားသော dashboard များကို လက်ခံပါ)                                                                           | Instance များအကြား dashboard တစ်ခုတည်း / call-log တစ်ခုတည်း ရရှိမည်ဟု မျှော်လင့်ခြင်း |
| မည်သည့် load balancer ကိုမဆို ရှေ့တွင်ထားနိုင်သည်။ API key သို့မဟုတ် session အလိုက် sticky ဖြစ်ရုံဖြင့် လုံလောက်သည်                                                                              | Vendor တစ်ခုနှင့်သာသက်ဆိုင်သော size-aware middleware ကို မဖြစ်မနေလိုအပ်သည်ဟု ယူဆခြင်း |

Hardware: instance တစ်ခုစီတွင် တစ်ပြိုင်နက်လုပ်ဆောင်သည့် ကြာမြင့်သော `/v1/responses` အရေအတွက်သည် **memory-budget** ဆိုင်ရာ မေးခွန်းဖြစ်သည် (heap + inflight-byte / #10110)။ အမှီအခိုကင်းသော `DATA_DIR` N ခုသည် heap များကိုလည်း ပွားပေးသည်။ ထို့ကြောင့် host RAM သည် “N=8 ပါသည့် 16 Gi pod တစ်ခု” မဟုတ်ဘဲ `N × cgroup` ကို လုံလောက်စွာ ပံ့ပိုးနိုင်ရမည်။ SQLite file တစ်ခုတည်းတွင် `replicas > 1` ကို မည်သည့်အခါမျှ မသုံးပါနှင့်။

Compose နမူနာ (heap နှစ်ခု၊ volume နှစ်ခု — `deploy.replicas: 2` မဟုတ်ပါ):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

In-process သိပ်သည်းဆ (HTTP isolate ပြင်ပတွင် compression လုပ်ခြင်း) ကို [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) တွင် ကြည့်ပါ။ မျှဝေထားသော တည်တံ့သည့် state ပေါ်ရှိ logical cluster တစ်ခုအကြောင်းကို [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) တွင် ကြည့်ပါ။

## Docker အတွင်းရှိ Gemini ဒေသဆိုင်ရာ အမှားများ

Google AI Studio / Gemini API သည် FAILED_PRECONDITION နှင့်အတူ HTTP 400 ကို ပြန်ပေးနိုင်ပြီး
`User location is not supported for the API use.` ဟု ဖော်ပြနိုင်သည်။ Host ပေါ်တွင် request အောင်မြင်ခြင်းက
container သည် တူညီသော outbound route ကို အသုံးပြုနေကြောင်း သက်သေမပြနိုင်ပါ။ DNS အစီအစဉ်၊
IPv4/IPv6 ချိတ်ဆက်နိုင်မှု၊ VPN routing နှင့် သတ်မှတ်ထားသော proxy များသည် ကွဲပြားနိုင်သည်။
[Google ၏ ပံ့ပိုးထားသော ဒေသများ](https://ai.google.dev/gemini-api/docs/available-regions) နှင့်
အမှန်တကယ် အသုံးပြုနေသော ချိတ်ဆက်မှုလမ်းကြောင်းကိုပါ စစ်ဆေးပါ။ ဤအမှားတစ်ခုတည်းဖြင့် API key မှားယွင်းနေသည်ဟု မသတ်မှတ်နိုင်ပါ။

### ချိတ်ဆက်မှုတစ်ခုချင်းအလိုက် proxy ကို ဦးစားပေးပါ

သက်ရောက်မှုရှိသော Gemini ချိတ်ဆက်မှုအတွက် OmniRoute ၏ [ချိတ်ဆက်မှုတစ်ခုချင်းအလိုက် proxy သတ်မှတ်ချက်](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ကို အသုံးပြုပြီးနောက် တူညီသော model ဖြင့် **Test Connection** နှင့် request အသေးစားတစ်ခုကို
ထပ်မံလုပ်ဆောင်ပါ။ ဤနည်းဖြင့် routing ပြောင်းလဲမှုကို ထိုချိတ်ဆက်မှုတစ်ခုတည်းအတွင်း ကန့်သတ်ထားနိုင်သည်။ Proxy ကို
container အတွင်းမှ ဆက်သွယ်နိုင်ကြောင်းနှင့် ချိတ်ဆက်မှုက ၎င်းကို အမှန်တကယ် ရွေးချယ်အသုံးပြုကြောင်း
စစ်ဆေးပါ။ Route ကို ပြောင်းလဲခြင်းက upstream ဒေသဆိုင်ရာ အသုံးပြုခွင့်ရှိမည်ဟု အာမမခံပါ။

### Host နှင့် container ကွန်ရက်ချိတ်ဆက်မှုကို နှိုင်းယှဉ်ပါ

Authentication ပြုလုပ်ထားသော ရလဒ်များကို နှိုင်းယှဉ်ရာတွင် key၊ model နှင့် request ကို တူညီစွာထားပါ။ Credential များ၊
proxy password များ သို့မဟုတ် authorization header အပြည့်အစုံကို issue တစ်ခုအတွင်း မည်သည့်အခါမျှ
မထည့်ပါနှင့်။ ဦးစွာ OS resolver က မည်သည့် address family များကို ပေးထားသည်ကို host နှင့်
container အတွင်း နှစ်နေရာစလုံးတွင် တူညီသော command ကို အသုံးပြု၍ စစ်ဆေးပါ။

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` ကို သင်အသုံးပြုနေသော service ဖြင့် အစားထိုးပါ (ဥပမာ `omniroute-web`)။ ဤ
command များသည် credential သို့မဟုတ် IP address များမပါဘဲ address family များကို ဖော်ပြသည်။ `6` ပြန်ရခြင်းသည်
IPv6 DNS ရလဒ်ရှိကြောင်းကိုသာ ပြသသည်။ အသုံးပြုနိုင်သော IPv6 route သို့မဟုတ် API access ရှိကြောင်းကို
သက်သေမပြနိုင်ပါ။ `curl` ကို ထည့်သွင်းထားသည့်နေရာတွင် environment နှစ်ခုလုံး၌
`curl -4 -I https://generativelanguage.googleapis.com` နှင့် `curl -6 -I https://generativelanguage.googleapis.com` ကို နှိုင်းယှဉ်ပါ။
Authentication မပြုထားသော အမှားဖြစ်နေသော်လည်း HTTP response တစ်ခုရခြင်းက ထို probe အတွက် ချိတ်ဆက်နိုင်ကြောင်း သက်သေပြသည်။
Authentication ပြုလုပ်ထားသော model request တစ်ခုကသာ Gemini အသုံးပြုခွင့်ရှိမရှိကို စမ်းသပ်နိုင်သည်။

### Host အဆင့် အခြားရွေးချယ်စရာ- အလုပ်လုပ်သော IPv6 နှင့် resolver policy

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) ကို တင်ပြသူသည် မိမိ၏ environment တွင်
container IPv6 ကို ဖွင့်ပြီး glibc address selection ကို ပြောင်းလဲခြင်းဖြင့် အသုံးပြုခွင့်ကို ပြန်လည်ရရှိခဲ့သည်။
၎င်းကို environment တစ်ခုချင်းအလိုက် အသုံးပြုရမည့် အခြားရွေးချယ်စရာအဖြစ်သာ သတ်မှတ်ပါ။ Resolver preference များကို
မပြင်ဆင်မီ host IPv6 အလုပ်လုပ်ကြောင်း၊ container egress/routing နှင့် firewall rule များကို စစ်ဆေးအတည်ပြုပါ။
Private ULA address တစ်ခုရှိရုံဖြင့် public IPv6 ချိတ်ဆက်နိုင်ကြောင်း မသတ်မှတ်နိုင်ပါ။

Compose ၏ default network နှင့် ချိတ်ဆက်ထားပြီးဖြစ်သော service များအတွက် အောက်ပါ fragment သည်
ထို network ပေါ်တွင် IPv6 ကို ဖွင့်ပေးသည်။ သင်၏ အခြား service၊ port၊ volume နှင့် configuration များကို ဆက်လက်ထိန်းသိမ်းထားပါ။

```yaml
networks:
  default:
    enable_ipv6: true
```

Named network တစ်ခုအတွက် service က အမှန်တကယ် ချိတ်ဆက်ထားသော network ပေါ်တွင် ၎င်းကို ဖွင့်ပါ။ Docker သည်
ULA subnet တစ်ခုကို သတ်မှတ်ပေးနိုင်သည်။ သင့် network က လိုအပ်သည့်အခါမှသာ အခြား subnet များနှင့် မထပ်သော subnet ကို
အတိအလင်း ရွေးချယ်ပါ။ [Docker IPv6 networking](https://docs.docker.com/engine/daemon/ipv6/)
နှင့် [Compose network options](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ကို ကြည့်ပါ။

**glibc-based image** တစ်ခုတွင် `/etc/gai.conf` သည် address selection ကို ပြောင်းလဲနိုင်သည်။ လက်ရှိ
repository Dockerfile သည် Debian ကို အသုံးပြုထားသည်။ စိတ်ကြိုက် musl-based image များတွင် ဤယန္တရားကို အသုံးမပြုနိုင်ပါ။
တင်ပြထားသော ပြင်ဆင်မှုသည် ULA label ကို `label fc00::/7 6` မှ
`label fc00::/7 1` သို့ ပြောင်းလဲသည်။ Image ၏ policy table အပြည့်အစုံမှ စတင်ပြီး ၎င်းရှိ အခြား
entry များကို ဆက်လက်ထိန်းသိမ်းပါ။ `label` သို့မဟုတ် `precedence` entry တစ်ခု ထည့်ခြင်းက မူလ default table ကို အစားထိုးသဖြင့်
ပြောင်းလဲထားသော စာကြောင်းတစ်ကြောင်းသာ ပါသည့် file သည် မလုံလောက်ပါ။
[glibc configuration reference](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
တွင် အဆိုပါ လုပ်ဆောင်ပုံကို မှတ်တမ်းတင်ထားသည်။ စစ်ဆေးပြီးသော file ကို `/etc/gai.conf` တွင် read-only အဖြစ် bind-mount လုပ်ပြီး
၎င်းကို အသုံးချရန် service ကို ပြန်လည်ဖန်တီးပါ။

ဤပြောင်းလဲမှုသည် **ထို container အတွင်းရှိ outbound traffic အားလုံး** အတွက် OS address selection ကို ပြောင်းလဲသည်။
၎င်းသည် application တိုင်းကို IPv6 ရွေးချယ်ရန် အတင်းအကျပ် မပြုလုပ်ပါ။ Node ၏ DNS order နှင့် connection
selection တို့သည်လည်း သက်ရောက်မှုရှိသည်။ အထူးသဖြင့် `--dns-result-order=ipv4first` သည် IPv4 ကို ဦးစားပေးပြီး
IPv4-only failure အတွက် ဖြေရှင်းနည်းမဟုတ်ပါ။ [Node DNS ordering](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ကို ကြည့်ပါ။

Host အဆင့် ပြောင်းလဲမှုတစ်ခုခု ပြုလုပ်ပြီးတိုင်း Gemini နှင့် သင့်အခြား provider များကို ပြန်လည်စမ်းသပ်ပါ။ မူလအခြေအနေသို့ ပြန်သွားရန်
စိတ်ကြိုက် `gai.conf` mount ကို ဖယ်ရှားပါ၊ ယခင် network configuration ကို ပြန်လည်ထားရှိပြီး
maintenance window အတွင်း သက်ရောက်မှုရှိသော service/network ကို ပြန်လည်ဖန်တီးပါ။ Network တစ်ခုကို ပြန်လည်ဖန်တီးခြင်းက
၎င်းနှင့် ချိတ်ဆက်ထားသော အခြား container များကို အနှောင့်အယှက်ဖြစ်စေနိုင်သည်။ Persistent data volume ကို မဖျက်ပါနှင့်။

## အရေးကြီးသော မှတ်ချက်များ

- **SQLite WAL Mode:** OmniRoute က နောက်ဆုံးပြောင်းလဲမှုများကို `storage.sqlite` ထဲသို့ checkpoint ပြန်လုပ်နိုင်စေရန် `docker stop` ကို ပြီးဆုံးသည်အထိ လုပ်ဆောင်ခွင့်ပြုသင့်သည်။ ပူးတွဲပါရှိသော Compose ဖိုင်များတွင် ရပ်တန့်ရန် အချိန်ပိုကာလ 40s ကို သတ်မှတ်ထားပြီးဖြစ်သည်။ image ကို တိုက်ရိုက် run ပါက `--stop-timeout 40` ကို ဆက်လက်ထားရှိပါ။
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ပုံမှန်/ရေးသားမှုမပြုမီ backup များကို ပြင်ပစနစ်ဖြင့် စီမံထားပါက `true` ဟု သတ်မှတ်ပါ။ ရှိပြီးသား database များ၏ migration များအတွက်မူ ၎င်းတို့ကိုယ်ပိုင် ရေရှည်ခံသော ဘေးကင်းရေး snapshot နှင့် အစုလိုက် migration ကာကွယ်မှု လိုအပ်ဆဲဖြစ်သည်။
- **ဒေတာ ရေရှည်သိမ်းဆည်းမှု:** container ပြန်လည်စတင်မှုများကြားတွင် သင့် database၊ key များနှင့် configuration များကို ဆက်လက်သိမ်းဆည်းထားရန် volume တစ်ခုကို `/app/data` သို့ အမြဲတမ်း mount လုပ်ပါ။
- **Port သတ်မှတ်မှု:** မူလ `20128` port ကို ပြောင်းလဲရန် `PORT` environment variable ကို override လုပ်ပါ။
