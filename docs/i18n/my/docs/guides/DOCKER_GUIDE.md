## အမြန်ပြေးပါ။

> **အမိန့်တစ်ခုတည်းတွင် ကိုယ်ပိုင်အိမ်ရှင်ရှိပါသလား။** [Self-Host လမ်းညွှန်](../getting-started/SELF_HOST_GUIDE.md) — `docker compose -f docker-compose.selfhost.yml up -d` (ထုတ်ဝေထားသော ပုံ + Redis၊ အလှည့်ကျသီးသန့်၊ ပရိုဖိုင်ရွေးချယ်စရာမရှိ) ကိုကြည့်ပါ။ အောက်ဖော်ပြပါ Quick Run သည် အခြားနေရာမှ Redis သုံးထားပြီး အသုံးပြုသူများအတွက် ကွန်တိန်နာတစ်ခုတည်းလမ်းကြောင်းဖြစ်သည်။

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  cheaperinference/omniroute:latest
```

## ပတ်ဝန်းကျင် ဖိုင်ဖြင့်

```bash
# Copy and edit .env first

```

## Docker Compose

```bash
# အခြေခံ Profile (CLI Tool မပါဝင်ပါ)
docker compose --profile base up -d

# CLI Profile (Claude Code၊ Codex၊ OpenClaw တို့ ထည့်သွင်းပြီးသား)
docker compose --profile cli up -d

# Host Profile (Linux ကို ဦးစားပေးသည်၊ Host CLI Binary များကို ဖတ်ရှုခွင့်သာဖြင့် Mount လုပ်သည်)
docker compose --profile host up -d

# Web Profile (Web-session Provider များအတွက် Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI Sidecar ကို ပေါင်းစပ်ပါ
docker compose --profile cli --profile cliproxyapi up -d
```

## ရရှိနိုင်သော Profile များ

OmniRoute တွင် အဓိက ဖြန့်ချမှုပုံစံများအတွက် Compose Profile များ ပါဝင်သည်။ သင့်ပတ်ဝန်းကျင်နှင့် ကိုက်ညီသည့် Profile ကို ရွေးချယ်ပါ။

| Profile       | Service          | အသုံးပြုသင့်သည့်အချိန်                                                                                                                                            | Command                                      |
| ------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (မူလ)  | `omniroute-base` | Headless Server / အနည်းဆုံး Runtime၊ Provider CLI များ ထည့်သွင်းမထားပါ                                                                                            | `docker compose --profile base up -d`        |
| `cli`         | `omniroute-cli`  | `omniroute providers/setup/doctor` နှင့် ထည့်သွင်းပြီးသား CLI များ (Codex၊ Claude Code၊ Droid၊ OpenClaw) ကို ခေါ်သုံးသည့် Agentic Workflow များ                   | `docker compose --profile cli up -d`         |
| `host`        | `omniroute-host` | `~/.local/bin`၊ `~/.codex`၊ `~/.claude` စသည်တို့ကို ဖတ်ရှုခွင့်သာဖြင့် Mount လုပ်ကာ Host CLI များထံ `network_mode` ကဲ့သို့ ဝင်ရောက်အသုံးပြုလိုသော Linux Host များ | `docker compose --profile host up -d`        |
| `cliproxyapi` | `cliproxyapi`    | Upstream CLI Proxy ပြုလုပ်ရန် Port `8317` ပေါ်တွင် [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) Sidecar ကို လုပ်ဆောင်ရန်                           | `docker compose --profile cliproxyapi up -d` |
| `web`         | `omniroute-web`  | Browser လိုအပ်သော Web-session Provider များ — `gemini-web`၊ `claude-web`၊ `claude-turnstile` (`runner-web` ကို Build လုပ်ပြီး Chromium ပါဝင်သည်)                  | `docker compose --profile web up -d`         |

> Profile များစွာကို ပေါင်းစပ်အသုံးပြုနိုင်သည် — `docker compose --profile cli --profile cliproxyapi up -d`။

## ကွန်တိန်နာတင်းမာခြင်း။

`base`၊ `web`၊ `cli` နှင့် `host` အက်ပ်ဝန်ဆောင်မှုများသည် `docker-compose.yml` နှင့် `no-new-privileges:true` လုံခြုံရေးရွေးချယ်မှုကို အသုံးပြုသည် `cap_drop: [ALL]` ပုံသည် root မဟုတ်သောအသုံးပြုသူ `node` အဖြစ်လည်ပတ်ပြီး မြင့်မားသော port များပေါ်တွင် နားထောင်သောကြောင့် Linux စွမ်းရည်များမလိုအပ်ပါ။ လုံခြုံရေးရွေးချယ်မှုသည် setuid binaries မှတဆင့် လုပ်ငန်းစဉ်များကို အခွင့်ထူးများရရှိခြင်းမှ တားဆီးပေးသည်။

`cli` ပရိုဖိုင်မှသာလျှင် အလိုအလျောက်အပ်ဒိတ်လုပ်ခြင်းအတွက် Docker ပေါက်ပေါက်ကို တပ်ဆင်သည်။ [Escape hatch ကိုကြည့်ပါ- လုံခြုံရေးသက်ရောက်မှုများအတွက် ကွန်တိန်နာ၏ကိုယ်ပိုင် CLIs စီစဉ်သတ်မှတ်ပါ](#escape-hatch-configure-the-containers-own-clis-use-sparingly) ။

root ဖိုင်စနစ်သည် မူရင်းအတိုင်း ဆက်လက်ရေးသားနိုင်သည်။ `cli` ပရိုဖိုင်သည် CLI ဖွဲ့စည်းမှုပုံစံနှင့် ကက်ရှ်များကို ကွန်တိန်နာ၏ပင်မလမ်းညွှန်တွင် ရေးသားသည်၊ `web` ပရိုဖိုင်သည် Chromium စက်ရှင်အခြေအနေအား သိမ်းဆည်းထားပြီး Next.js runtime သည် `/app/data` အပြင်ဘက်တွင် ကက်ရှ်များကို ရေးသားနိုင်သည်။

`base` ပရိုဖိုင်ဖြင့် ဖတ်ရန်-သီးသန့် root ဖိုင်စနစ်ကို စမ်းကြည့်ရန်၊ ၎င်းကို `docker-compose.yml` ဘေးရှိ `docker-compose.override.yml` အဖြစ် သိမ်းဆည်းပါ။ စာစီကုံးသည် အလိုအလျောက် ထပ်လောင်းဖတ်သည်။

```yaml
services:
  omniroute-base:
    read_only: true
    tmpfs:
      - /tmp
```

```bash
docker compose --profile base up -d
```

ရှိပြီးသား `/app/data` mount သည် ဆက်၍ရေးနိုင်သည်။ အခြားလမ်းကြောင်းများသို့ စာရေးရန် လိုအပ်နိုင်သောကြောင့် ဤ override ကို ထုတ်လုပ်မှုတွင် အသုံးမပြုမီ သင့်လုပ်ငန်းတာဝန်ကို စမ်းသပ်ပါ။

## OmniRoute ကို Docker တွင် လုပ်ဆောင်နေစဉ် host CLI ကိရိယာများကို စီစဉ်သတ်မှတ်ခြင်း

`omniroute setup-codex`၊ `setup-claude`၊ `config set <tool>` နှင့် dashboard ၏
**စီစဉ်သတ်မှတ်ချက်ကို သိမ်းဆည်းရန်** ခလုတ်တို့သည် `~/.codex/*.config.toml` ကဲ့သို့သော ဖိုင်များကို ရေးသားသည်။ ထိုလမ်းကြောင်းများသည်
CLI အမှန်တကယ် လုပ်ဆောင်နေသည့် စက်ပေါ်တွင်သာ အဓိပ္ပာယ်ရှိသည်။ ၎င်းတို့ကို container အတွင်း
လုပ်ဆောင်ပါက ရေးသားမှုသည် container ၏ ကိုယ်ပိုင် home (`/home/node` —
image သည် `USER node` ဖြင့် လုပ်ဆောင်သည်) ထဲသို့ ရောက်ရှိသွားမည်ဖြစ်ပြီး မည်သည့် host CLI ကမျှ ထိုနေရာမှ ဖတ်မည်မဟုတ်သည့်အပြင်
container ကို ပြန်လည်ဖန်တီးသည့်အချိန်တွင်လည်း ပယ်ဖျက်ခံရမည်ဖြစ်သည်။

OmniRoute သည် ဤအခြေအနေကို ရှာဖွေသိရှိပြီး သင် အသုံးမပြုနိုင်သည့် အောင်မြင်မှုကို အစီရင်ခံမည့်အစား
ညွှန်ကြားချက်များနှင့်အတူ ရေးသားမှုကို ငြင်းပယ်သည်- CLI သည် `2` ဖြင့် ထွက်ပြီး API သည် `422`
နှင့် `containerEphemeralTarget: true` ကို ပြန်လည်ဖြေကြားသည်။

### အကြံပြုထားသည့်နည်းလမ်း- CLI ကို host ပေါ်တွင် လုပ်ဆောင်ပြီး OmniRoute ကို Docker တွင် လုပ်ဆောင်ပါ

Container သည် API ကို ဝန်ဆောင်မှုပေးပြီး CLI သည် သင့် host ကိရိယာများကို စီစဉ်သတ်မှတ်ပေးသည်။

```bash
docker compose --profile base up -d

npm install -g omniroute
```

### အခြားနည်းလမ်း- host config directory များကို bind-mount လုပ်ပါ (`host` profile)

Container ကိုယ်တိုင်က သင့် host config ကို ရေးသားစေလိုပါက directory များကို
mount လုပ်ပြီး `CLI_CONFIG_HOME` ကို mount root သို့ ညွှန်ပါ။ `host` profile တွင်
၎င်းကို ပြုလုပ်ပြီးသားဖြစ်သည်-

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

Bind mount ကြောင့်သာ ထိုလမ်းကြောင်းကို ယုံကြည်စိတ်ချနိုင်ခြင်းဖြစ်သည်- OmniRoute သည်
`/proc/self/mountinfo` ကို ဖတ်ပြီး mount လုပ်ထားသည့် လမ်းကြောင်းများ (နှင့် child များက mount များဖြစ်သော
directory များကိုလည်း ခွင့်ပြုသည်၊ ၎င်းသည် အထက်ပါ `/host-home` ပုံစံနှင့် အတိအကျ ကိုက်ညီသည်) သို့
ရေးသားခြင်းကို ခွင့်ပြုကာ mount မလုပ်ထားသော လမ်းကြောင်းများကို ဆက်လက်ငြင်းပယ်ထားသည်။

### နောက်ဆုံးရွေးချယ်စရာ- container ၏ ကိုယ်ပိုင် CLI များကို စီစဉ်သတ်မှတ်ပါ (လိုအပ်မှသာ အသုံးပြုပါ)

CLI များသည် container အတွင်း၌ အမှန်တကယ် ရှိနေပါက (`cli` profile) ရေးသားမှုသည်
ရည်ရွယ်ထားသည့် လုပ်ဆောင်ချက်ဖြစ်သည်။ မည်သည့် `setup-*` command တွင်မဆို `--allow-container-write` ကို ထည့်သွင်းပါ၊ သို့မဟုတ် server အတွက်
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ကို သတ်မှတ်ပါ။ Container ရှိနေသည့်ကာလထက် ကျော်လွန်၍
ထိုရေးသားမှု မတည်ရှိနိုင်ကြောင်း သတိပေးချက်နှင့်အတူ ရေးသားမှုကို ဆက်လက်လုပ်ဆောင်မည်ဖြစ်သည်။

> **လုံခြုံရေး သတိပေးချက် — `cli` profile + `docker.sock` mount။**
> Container အတွင်းရှိ auto-updater က host daemon မှ stack ကို ပြန်လည်ဖန်တီးနိုင်စေရန်
> `cli` profile သည် `/var/run/docker.sock` ကို bind-mount လုပ်သည်
> (`src/lib/system/autoUpdate.ts` သည် ထို socket ရှိမရှိ စစ်ဆေးပြီး
> မရှိပါက Docker လမ်းကြောင်းကို ကျော်သွားသည်)။ ထို socket သည် **host-root ယုံကြည်မှု
> နယ်နိမိတ်** ဖြစ်သည်- ၎င်းကို အသုံးပြုနိုင်သည့် မည်သည့်အရာမဆို host Docker daemon ကို
> root အဖြစ် ထိန်းချုပ်နိုင်သည် — host ပေါ်ရှိ မည်သည့် container ကိုမဆို ဖန်တီးခြင်း၊ စစ်ဆေးခြင်း၊ ရပ်တန့်ခြင်းနှင့် ဖယ်ရှားခြင်းတို့ ပြုလုပ်နိုင်သည်။
> သက်ရောက်မှုများ-
>
> 1. **`cli` profile ၏ port ကို network သို့ ဘယ်တော့မှ မဖွင့်ပါနှင့်။**
>    ၎င်းကို `127.0.0.1` တွင် publish လုပ်ပါ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN မှ ဝင်ရောက်နိုင်သော `cli` profile သည် dashboard အဆင့် RCE တစ်ခုခုကို
>    host အပြည့်အဝ ထိန်းချုပ်ခံရမှုအဖြစ် ပြောင်းလဲစေသည်။
> 2. **`cli` profile ထဲသို့ နောက်ထပ် host directory များကို bind မလုပ်ပါနှင့်။**
>    Docker socket နှင့် ထပ်ဆောင်း mount တစ်ခုခု ပေါင်းစပ်ခြင်းသည် container ကို သင့် filesystem နှင့် host config အား
>    အပြည့်အဝ ဖတ်ရှု/ရေးသားခွင့် ပေးလိုက်ခြင်းဖြစ်သည်။ ကိရိယာတစ်ခုက project တစ်ခုကို
>    မြင်ရန်လိုအပ်ပါက CLI binary ဖြင့် local တွင် လုပ်ဆောင်ပါ — ၎င်းကို
>    `cli` container ထဲသို့ mount မလုပ်ပါနှင့်။
>
> Container အတွင်း auto-update ကို မလိုအပ်ပါက `cli` profile ကို ပိတ်ထားပါ
> (`COMPOSE_PROFILES=core,redis` သို့မဟုတ် ပိုတိုသော သတ်မှတ်ချက်)။ အခြား profile များသည်
> Docker socket ကို mount မလုပ်ပါ။
>
> MITM နှင့် သက်ဆိုင်သော ခြိမ်းခြောက်မှုပုံစံအတွက် `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` ထဲသို့ compile မလုပ်ထားပါ) ကို
> ကြည့်ရှုပါ၊ ထို့ပြင် `codex`/`claude-code`/`droid`/`openclaw` binary မူလရင်းမြစ်ကွင်းဆက်အတွက်
> `docs/security/SUPPLY_CHAIN.md` ကို ကြည့်ရှုပါ။

## Redis Sidecar

OmniRoute သည် ဖြန့်ဝေထားသော rate limiter နှင့် မျှဝေထားသော cache အတွက် Redis ကို အသုံးပြုသည်။ `redis` service ကို `docker-compose.yml` ထဲတွင် **အမြဲတမ်း သတ်မှတ်ထားသည်** (၎င်းတွင် profile gate မရှိပါ)၊ ထို့ပြင် အခြားမည်သည့် profile နှင့်မဆို အတူတကွ စတင်သည်။

| အသေးစိတ်                        | တန်ဖိုး                                         |
| ------------------------------- | ----------------------------------------------- |
| Image                           | `redis:7-alpine`                                |
| Container အမည်                  | `omniroute-redis`                               |
| အတွင်းပိုင်း port               | `6379`                                          |
| Host port (အစားထိုးသတ်မှတ်ချက်) | `REDIS_PORT` (ပုံမှန်အားဖြင့် `6379`)           |
| Host bind (အစားထိုးသတ်မှတ်ချက်) | `REDIS_BIND_HOST` (ပုံမှန်အားဖြင့် `127.0.0.1`) |
| Volume                          | `omniroute-redis-data` → `/data`                |
| Healthcheck                     | `redis-cli ping` (10s ကြားကာလ)                  |

ဆက်စပ် environment variable များ-

- `REDIS_URL` — app ထဲသို့ ထည့်သွင်းပေးသော connection string (ပုံမှန်အားဖြင့် `redis://redis:6379`)။
- `REDIS_PORT` — Redis container အတွက် host ဘက်ရှိ port mapping။
- `REDIS_BIND_HOST` — port ကို publish လုပ်မည့် host interface။ ပုံမှန်အားဖြင့် `127.0.0.1` ဖြစ်သည်။

> **ပုံမှန်အားဖြင့် loopback ကို အသုံးပြုရသည့်အကြောင်းရင်း-** sidecar သည် `requirepass` မပါဘဲ အလုပ်လုပ်ပြီး app
> container များက compose network (`redis:6379`) မှတစ်ဆင့် ၎င်းထံ ဆက်သွယ်ကြသည် — publish လုပ်ထားသော port သည်
> host ဘက်ရှိ tooling (`redis-cli`၊ local `npm run dev`) အတွက်သာ ဖြစ်သည်။ `0.0.0.0` တွင် publish လုပ်ခြင်းက
> authentication မပါသော Redis ကို သင့် LAN ရှိ host အားလုံးထံ ဖွင့်ပေးလိုက်မည်ဖြစ်သည်။ `REDIS_BIND_HOST=0.0.0.0` ဟု သတ်မှတ်ပါက
> service `command:` ထဲတွင် `--requirepass` ကိုလည်း ထည့်ပါ။

**Redis ကို ပိတ်ထားခြင်း** အား မထောက်ခံပါ (rate limiter သည် in-memory fallback ကို အသုံးပြုရသဖြင့် စွမ်းဆောင်ရည် ကျဆင်းမည်)။ မဖြစ်မနေ လုပ်ဆောင်ရမည်ဆိုပါက `docker-compose.yml` ထဲရှိ `redis:` service block ကို ဖယ်ရှား/မှတ်ချက်အဖြစ် ပြောင်းပါ သို့မဟုတ် zero အထိ scale လုပ်ပါ-

```bash
docker compose up -d --scale redis=0
```

## Production Compose

Dev နှင့်အတူ သီးခြားခွဲထုတ်ထားသော production snapshot တစ်ခုကို လည်ပတ်ရန် `docker-compose.prod.yml` ကို အသုံးပြုပါ။

| အသေးစိတ်               | တန်ဖိုး                                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| File                   | `docker-compose.prod.yml`                                                                      |
| ပုံမှန် dashboard port | `PROD_DASHBOARD_PORT=20130` (အတွင်းပိုင်း `${DASHBOARD_PORT:-20128}` သို့ mapped လုပ်ထားသည်)   |
| ပုံမှန် API port       | `PROD_API_PORT=20131`                                                                          |
| Image                  | `omniroute:prod` (`runner-cli` target မှ build လုပ်ထားသည်)                                     |
| Redis container        | `omniroute-redis-prod` (`redis:8.6.2`၊ သီးခြား `redis-prod-data` volume)                       |
| Data volume            | `omniroute-prod-data` (အမည်ပေးထားပြီး rebuild များအကြား ဆက်လက်သိမ်းဆည်းထားသည်)                 |
| Healthcheck များ       | `node healthcheck.mjs` + `redis-cli ping`၊ `depends_on` ကို Redis health ဖြင့် gate လုပ်ထားသည် |

အသုံးပြုပုံ-

```bash
# Production stack ကို build လုပ်ပြီး စတင်ပါ
docker compose -f docker-compose.prod.yml up -d --build

# Log များကို ဆက်တိုက်ကြည့်ရှုပါ
docker compose -f docker-compose.prod.yml logs -f

# ရပ်တန့်ဖယ်ရှားပါ (volume များကို ဆက်လက်သိမ်းထားပါ)
docker compose -f docker-compose.prod.yml down
```

Prod stack သည် dev compose နှင့် တစ်ပြိုင်နက် လည်ပတ်သည် (container အမည်များ၊ port များနှင့် volume များ မတူညီပါ)။ ထို့ကြောင့် production ကို ဆက်လက်လည်ပတ်စေထားစဉ် local တွင် ဆက်လက်ပြင်ဆင်စမ်းသပ်နိုင်သည်။

## Dockerfile အဆင့်များ

repository သည် multi-stage Dockerfile (`Dockerfile`) ကို ပေးပို့သည်။ အဆင့် လေးဆင့်ကို ဖော်ထုတ်ထားသည်။ သင့်အသုံးပြုမှုအတွက် မှန်ကန်သော `target` ရွေးချယ်ပါ။

| ဇာတ်ခုံ       | အခြေခံပုံ             | ရည်ရွယ်ချက်                                                                                                                                                                                                                                                                                                                              |
| ------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | deps (`npm ci --legacy-peer-deps`) ကို ထည့်သွင်းပြီး `npm run build` (Turbopack မူရင်း — ဖြင့် လုပ်ဆောင်သည် အောက်တွင် တည်ဆောက်ချိန်အရင်းအမြစ်များကို ကြည့်ပါ)                                                                                                                                                                            |
| `runner-base` | `node:26-trixie-slim` | Next.js standalone output ဖြင့် ထုတ်လုပ်သည့် runtime** ပံ့ပိုးပေးသူ CLIs စုစည်းထားခြင်းမရှိပါ။**                                                                                                                                                                                                                                         |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` နှင့် global CLIs: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw` တို့ကို ပေါင်းထည့်သည်။** အေးဂျင့်အလုပ်အသွားအလာများအတွက် ၎င်းကို ရွေးပါ။**                                                                                                                                      |
| `runner-web`  | `runner-base`         | ဝဘ်စက်ရှင်ဝန်ဆောင်မှုပေးသူများအတွက် Playwright + Chromium ဘရောက်ဆာ (`--with-deps`) ကို ပေါင်းထည့်သည်- `gemini-web`, `claude-web`, `claude-turnstile`.** အဆိုပါဝန်ဆောင်မှုပေးသူများကို သင်အသုံးပြုသည့်အခါ ၎င်းကိုရွေးချယ်ပါ။** — ရိုးရိုးပုံသည် တောင်းဆိုမှုမရှိဘဲ ပျက်ကွက်သည် (ဖြန့်ချိရေးချန်နယ်များအောက်ရှိ `-web` မှတ်စုကို ကြည့်ပါ)။ |

တိကျသောပစ်မှတ်ကို ကိုယ်တိုင်ဖန်တီးပါ-

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### အချိန်အရင်းအမြစ်များတည်ဆောက်ခြင်း။

တည်ဆောက်မှု args သုံးခုသည် `builder` အဆင့်ကုန်ကျစရိတ်ကို ထိန်းချုပ်သည်။ ၎င်းတို့သည် build-time only — `OMNIROUTE_MEMORY_MB` (အောက်တွင်) သီးခြား runtime knob ဖြစ်သည်။

| arg ကိုတည်ဆောက်ပါ။          | ပုံသေ  | သက်ရောက်မှု                                                                                                |
| --------------------------- | ------ | ---------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`    | `0` webpack ဖြင့်တည်ဆောက်သည်- အထွတ်အထိပ်မှတ်ဉာဏ်နိမ့်၊ ပိုနှေးသည်။ `1` သည် Turbopack သို့ရွေးချယ်သည်။      |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144` | မွေးမြူထားသော `next build` အတွက် V8 အမှိုက်ပုံမျက်နှာကျက် (`--max-old-space-size`)                         |
| `OMNIROUTE_BUILD_WORKERS`   | `2`    | `CIRCLE_NODE_TOTAL` ကျွေးသည် ; နောက်တစ်ခုသည် စာမျက်နှာဒေတာစုဆောင်းမှုအတွက် `workers = N - 1` ဆင်းသက်လာသည်။ |

`OMNIROUTE_BUILD_WORKERS` is the one to raise on a big builder and the one to suspect when a constrained build dies **after** `✓ Compiled successfully`. Each page-data worker is its own process, and so is the parent `next build` itself; a live VPS reproduction (issue #7518) measured each process's peak RSS at ~4.5 GB independent of the `NODE_OPTIONS` heap flag (Turbopack compiles in native/Rust memory outside the V8 heap). The default of `2` (→ 1 worker, 2 processes total) is sized for the 16 GB / 4 vCPU GitHub-hosted runners the publish pipeline uses. At `8` (→ 7 workers) that runner ran out of memory and buildkit failed the step with `ResourceExhausted: ... cannot allocate memory`; `3` (→ 2 workers) still didn't fit once the per-process RSS was measured directly instead of inferred. `tests/unit/docker-build-memory-budget.test.ts` does the arithmetic against the measured figure and fails if either knob outgrows the runner.

Turbopack compiles in native Rust memory that lives **outside** the V8 heap, so `OMNIROUTE_BUILD_MEMORY_MB` does not bound it. On a host with a memory ceiling the build is then SIGKILLed by the OOM killer with no error text at all — it simply stops mid-`Creating an optimized production build`, which reads like a hang rather than an out-of-memory. That is why the `Dockerfile` defaults to webpack (`OMNIROUTE_USE_TURBOPACK=0`), unlike `npm run dev` / `npm run build`, where Turbopack is the code default: a bare `docker build .` with no build args (what Railway and other one-click hosts run) must not die silently on a memory-capped builder. The published images already pass `OMNIROUTE_USE_TURBOPACK=0` explicitly in `docker-publish.yml`. On a builder with plenty of RAM, opt into Turbopack for a faster build:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ကို ဖွင့်ထားသောကြောင့် `next build` သည် မိဘကို လုပ်ဆောင်သည်။** နှင့်** အလုပ်သမားလုပ်ငန်းစဉ်တစ်ခုနှင့် တစ်ခုစီသည် `OMNIROUTE_BUILD_MEMORY_MB` သီးခြားစီ ဂုဏ်ပြုပါသည်။ အပေါ်က ကွန်တိန်နာမျက်နှာကျက်ကို အကြမ်းဖျင်းအားဖြင့် တစ်ကြိမ်မဟုတ်ဘဲ အဲဒီတန်ဖိုးထက် နှစ်ဆလောက် အရွယ်အစားပေးပါ။

ဤသစ်ပင်ပေါ်တွင် တိုင်းတာခြင်း (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| Bundler   | ကွန်တိန်နာ မျက်နှာကျက် | ရလဒ်                                                  |
| --------- | ---------------------- | ----------------------------------------------------- |
| Turbopack | 8 GiB / 16 GiB         | OOM - နှစ်ယောက်စလုံးကို တိတ်တဆိတ် သတ်ပစ်လိုက်တယ်။     |
| ဝဘ်အိတ်   | 8 GiB                  | ဆောက်လုပ်ရေးလုပ်သား SIGKILLed                         |
| ဝဘ်အိတ်   | 12 GiB                 | အောင်မြင်ခဲ့ပြီး 11.1 GiB တွင် အထွတ်အထိပ်ရောက်ခဲ့သည်။ |

### Runtime မူရင်းများ

`runner-base` ဖြင့် တင်ပို့သော ပုံသေများ : `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Docker ရှိ မှတ်ဉာဏ်အပြုအမူ

- ပုံသည် `OMNIROUTE_MEMORY_MB=1024` သတ်မှတ်ပြီး ၎င်းမှ `NODE_OPTIONS=--max-old-space-size=1024` ဆင်းသက်သည်။
- အမှန်တကယ်ဆာဗာလုပ်ငန်းစဉ်ကို `OMNIROUTE_MEMORY_MB` ဖတ်ပြီး `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ကိုထည့်သွင်းပေးသော standalone launcher မှစတင်ပါသည်။
- Node သည် နောက်ဆုံးအကြိမ် `--max-old-space-size` တန်ဖိုးကို အသုံးပြုသည်၊ ထို့ကြောင့် `OMNIROUTE_MEMORY_MB` ဆက်တင်သည် ထိရောက်သော Docker heap ကန့်သတ်ချက်ကို ထိန်းချုပ်သည်။
- ပုံသည် ၎င်းကို အမြဲတမ်း သတ်မှတ်ပေးသောကြောင့်၊ launcher ၏ ကိုယ်ပိုင် RAM-ချိန်ကိုက်နိုင်သော လှည့်ကွက်သည် Docker အောက်တွင် မည်သည့်အခါမှ သက်ရောက်မှုမရှိပါ။ အလုပ်တာဝန်အတွက် အထူးတလည် မြှင့်တင်ပါ (အောက်ပါဇယား)။ `2048` သည် coding-agent `/v1/responses` အတွက် အလွန်သေးငယ်ပါသည်။

### coding အေးဂျင့်များအတွက် runtime RAM

1 GiB Docker မူရင်းသည် ထုတ်လုပ်မှုအရွယ်အစားမဟုတ်ဘဲ dashboard/light-chat ကြမ်းခင်းဖြစ်သည်။ ရှည်လျားသော `POST /v1/responses` ကောင်များ (မက်ဆေ့ချ် ရာနှင့်ချီ၊ ကိရိယာ ဆယ်ဂဏန်း) သည် ချုံ့နေစဉ်အတွင်း မမ်မိုရီဂရပ်အများအပြားကို ထိန်းသိမ်းထားသည်။ ထပ်နေသော ~ 3 MiB / ~ 750k-တိုကင် တောင်းဆိုချက်နှစ်ခုသည် V8 ကို ဖျက်သိမ်းလိုက်သည်** 12 GiB** old-space (`FATAL ERROR: Reached heap limit`) နှင့် 16 GiB cgroup OOM ကို လည်း ရိုက်သည် ။ [#7849](https://github.com/cheaper-inference/OmniRoute/issues/7849) ကြည့်ပါ။

အရွယ်အစား** အမှိုက်ပုံအထက် cgroup `--memory`** — ဇာတိ buffers၊ SQLite နှင့် compression ကြားခံများသည် V8 အပြင်ဘက်တွင် ထိုင်သည်။

| အလုပ်ဝန်                                           | `OMNIROUTE_MEMORY_MB`             | ကွန်တိန်နာ / cgroup  | မှတ်စုများ                                                                                                     |
| -------------------------------------------------- | --------------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------- |
| ဒက်ရှ်ဘုတ်၊ အလင်းစကားပြောခန်းတစ်ခု                 | `1024` (ပုံသေပုံသေ)               | ≥2 GiB               |                                                                                                                |
| ကုဒ်နံပါတ် အေးဂျင့်တစ်ခု (Claude/Codex/Grok)       | `8192`                            | ≥10 GiB              | ရိုးရိုးတစ်ဆက်ရှင် `/v1/responses`                                                                             |
| နှစ်ခုပြိုင်တူ `/v1/responses` အရှည်               | `10240`–`12288`                   | ≥12–16 GiB           | ~ 12 GiB အမှိုက်ပုံတွင် တိုင်းတာထားသော V8 ကို ဖျက်သိမ်းသည်။                                                    |
| + သုံးခု တစ်ပြိုင်တည်း ရှည်လျားသော အကြောင်းအရာများ | လုပ်ငန်းစဉ်တစ်ခုတည်းတွင် မလုပ်ပါ။ | serialize / more RAM | မူရင်း ဟဲဗီးဝိတ် ဝင်ခွင့်သည် 1 in-flight; RAM မပါဘဲ မွေးမြူခြင်းသည် ကိုယ်ဝန်ဖျက်ခြင်းကို ပြန်လည်မိတ်ဆက်ပေးသည်။ |

သတ္တုဗလာရှိ`omniroute serve` ~၏ 35% RAM ( `[512, 4096]`) ကို `OMNIROUTE_MEMORY_MB` ဖြစ်သောအခါ ချိန်ညှိသည်** သတ်မှတ်မထားပါ။** . Docker `1024` အမြဲတမ်း သတ်မှတ်ပေးသည်၊ ထို့ကြောင့် ချိန်ညှိခြင်းကို တရားဝင်ပုံတွင် ဘယ်တော့မှ မလည်ပတ်ပါ။

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data cheaperinference/omniroute:latest
```

## Subpath (Traefik / nginx) ပေါ်ရှိ Reverse Proxy

Next.js `basePath` ကို သီးခြားအစုအဝေးတွင် စုစည်းထားသည်။ OmniRoute app root ရှိ sentinel ဖိုင်တွင် ဖုတ်ထားသောတန်ဖိုးကို မှတ်တမ်းတင်သည် ( `npm run build` တွင် ; `scripts/docker/ensure-docker-base-path.mjs` ဖြင့်ဖတ်သည် ) နှင့် ကွန်တိန်နာစတင်သည့်အခါ `OMNIROUTE_BASE_PATH` နှင့် နှိုင်းယှဉ်သည်။ ၎င်းတို့ ကွဲပြားပြီး ပုံအား domain root အတွက် တည်ဆောက်သောအခါ၊ entrypoint သည် standalone manifests များကို ပြန်လည်ရေးသားသည်၊ မြှုပ်ထားသော `basePath`/`assetPrefix` literals (Next 16 သည် SSR asset URLs `assetPrefix` တစ်ခုတည်းမှ — မှ patcher သည် subpath အတွင်းသို့ mirror လုပ်ထားသည်)၊ဖုတ်ထားသော `/_next/static` asset- URLs (တင်သွင်းသည်)၊ အမှားစာမျက်နှာများ) နှင့် `node dev/run-standalone.mjs` မလည်ပတ်မီ client `process.env` shim ။

### တည်ဆောက်ရေးရေးပါ (အကြံပြုထားသည်)

`.env` တွင် variable နှစ်ခုလုံးကို သတ်မှတ်ပါ၊ ထို့နောက် image နှင့် runtime ကသဘောတူသည်-

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml` `OMNIROUTE_BASE_PATH` Docker build-arg အဖြစ်နှင့် runtime environment variable အဖြစ် ပေးပို့သည်။

### ကြိုတင်တည်ဆောက်ထားသော root image + runtime subpath

ထုတ်ဝေထားသော `cheaperinference/omniroute:*` ပုံများကို domain root အတွက် တည်ဆောက်ထားသည်။ သင် runtime တွင် `OMNIROUTE_BASE_PATH` သတ်မှတ်နိုင်သေးသည်။ ကွန်တိန်နာသည် စတင်ချိန်တွင် အစုအစည်းကို ဖာထေးပေးသည်။ ၎င်းကို ကိုက်ညီသော အများသူငှာ မူရင်းနှင့် တွဲချိတ်ပါ-

```yaml
services:
  omniroute:
    image: cheaperinference/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

ပေးပို့ရန် reverse proxy ကို configure လုပ်ပါ။** အပြည့်** ပြင်ပလမ်းကြောင်း (ရှေ့ဆက်ကို မချွတ်ပါနှင့်)။ Traefik သည် `PathPrefix(`/omniroute `)` `StripPrefix` မပါဘဲ ကွန်တိန်နာသို့ လမ်းကြောင်းပေးသင့်သည်၊ ထို့ကြောင့် Next.js `/omniroute/...` လက်ခံပြီး `/omniroute/_next/...` မှ ပိုင်ဆိုင်မှုများကို ဆောင်ရွက်ပေးပါသည်။

Docker ကျန်းမာရေးစစ်ဆေးမှုသည် တက်ကြွသော `OMNIROUTE_BASE_PATH` နှင့် ရှေ့ဆက်ထားသော ပေါ့ပါးသော `/healthz` ဘဝသံသရာအဆုံးမှတ်ကို စစ်ဆေးသည်။ `/api/monitoring/health` human/dashboard ရောဂါရှာဖွေခြင်းအတွက် ရနိုင်သေးသည်။ ကွန်တိန်နာ HEALTHCHECK ၎င်းကို ပြန်ညွှန်ရန် (ဥပမာ နက်ရှိုင်းသော ကျန်းမာရေး ထိန်းသိမ်းရေးအတွက်) `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ကို သတ်မှတ်ပါ။ အဲဒီလမ်းက တစ်ကြောင်း** နက်နဲသည်။** check (DB + စောင့်ကြည့်ရေးအကျဉ်းချုပ်) — သင်ပြန်ရွေးချယ်ပါက Docker's ခဏခဏ `HEALTHCHECK` အတွက်သင့်လျော်သော်လည်း၊** မဟုတ်ဘူး** Kubernetes `livenessProbe` ကြားကာလများအတွက်။

သံစုံတီးဝိုင်းများအတွက် (Kubernetes၊ Nomad စသည်ဖြင့်)။

| ထိုးဆွ                   | ဦးစားပေး                                                                | ရှောင်ပါ။                                                                                          |
| ------------------------ | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| ရှင်သန်မှု               | HTTP `GET /livez` သို့မဟုတ် ပင်မပို့တ်တွင် TCP (`PORT`၊ မူရင်း `20128`) | `/api/monitoring/health` အသက်ရှင်ခြင်းအဖြစ်                                                        |
| စေတနာ                    | HTTP `GET /healthz`                                                     | အဖြစ်အပျက်-ကွင်းဆက် အလုပ်ရှုပ်ခြင်းကို သေသည်အဖြစ် သတ်မှတ်ပေးသည့် တင်းကျပ်သော အချိန်ကုန်ဆုံးမှုများ |
| နက်ရှိုင်းသော / blackbox | `/api/monitoring/health`                                                | —                                                                                                  |

`/healthz` အစီရင်ခံစာသည် လုပ်ငန်းစဉ်ဘဝသံသရာ (`ok` / `starting` / `stopping`)။ `/livez` သည် process-alive သာဖြစ်သည် (ကိုင်တွယ်သူသည် run သည့်အခါတိုင်း 200; အဆင်သင့်မစောင့်ဘဲ)။ နှစ်ခုစလုံးသည် တောင်းဆိုမှုကိုင်တွယ်ခြင်းကဲ့သို့ တူညီသော Node event loop တွင်လည်ပတ်နေသေးသည်၊ ထို့ကြောင့် CPU-bound catalog သို့မဟုတ် compression အလုပ်သည် ၎င်းတို့အား — busy ≠ dead ဖြင့်နှောင့်နှေးစေနိုင်သည်။ HTTP စစ်ဆေးမှုများ အချိန်ကုန်သွားပါက TCP အသက်ရှင်မှုကို ဦးစားပေးပါ။ စုံစမ်းစစ်ဆေးရေးလမ်းညွှန်ချက် အပြည့်အစုံ- [စောင့်ကြည့်ရေးလမ်းညွှန် — Kubernetes စုံစမ်းစစ်ဆေးရေး အကြံပြုချက်များ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ။

## Docker Caddy ဖြင့်ရေးပါ (HTTPS Auto-TLS)

OmniRoute Caddy ၏ အလိုအလျောက် SSL စီမံဆောင်ရွက်ပေးမှုကို အသုံးပြု၍ လုံခြုံစွာ ဖော်ထုတ်နိုင်သည်။ သင့်ဒိုမိန်း၏ DNS A မှတ်တမ်းအမှတ်သည် သင့်ဆာဗာ၏ IP သို့ သေချာပါစေ။

```yaml
services:
  omniroute:
    image: cheaperinference/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # Browser-facing origin for OAuth callbacks, dashboard links, and generated public URLs.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # Internal server-to-server URL for scheduled jobs / self-fetches.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy သည် upstream container အတွက် စံသတ်မှတ်ထားသော forwarding header များကို သတ်မှတ်ပေးသည်။ OmniRoute သည် OAuth callback များနှင့် ထုတ်လုပ်ထားသော အများသုံး
လင့်ခ်များအတွက် `NEXT_PUBLIC_BASE_URL` ကို တရားဝင်အများသုံး origin အဖြစ် အသုံးပြုသည်။
အထောက်အထားစစ်ဆေးပြီးသော dashboard write လုပ်ဆောင်ချက်များသည် same-origin request များနှင့် session ချိတ်ဆက်ထားသော CSRF
ကာကွယ်မှုကို အသုံးပြုသည်။ တိကျစွာသတ်မှတ်ထားသော configuration အစား ယုံကြည်ရသော forwarded header များမှ အများသုံး origin ကို
OmniRoute အား ရယူစေလိုသည့် အဆင့်မြင့် deployment များတွင်သာ `OMNIROUTE_TRUST_PROXY` ကို ဖွင့်ပါ။

## Cloudflare Quick Tunnel

Docker deployment များအတွက် dashboard ပံ့ပိုးမှုတွင် `Dashboard → Endpoints` ၌ တစ်ချက်နှိပ်ရုံဖြင့် အသုံးပြုနိုင်သော **Cloudflare Quick Tunnel** ပါဝင်သည်။ ပထမဆုံးဖွင့်သည့်အခါ လိုအပ်မှသာ `cloudflared` ကို ဒေါင်းလုဒ်လုပ်ပြီး သင့်လက်ရှိ `/v1` endpoint သို့ ယာယီ tunnel တစ်ခု စတင်ကာ ထုတ်လုပ်ထားသော `https://*.trycloudflare.com/v1` URL ကို သင်၏ ပုံမှန်အများသုံး URL အောက်တွင် တိုက်ရိုက်ပြသပေးသည်။

Endpoint tunnel panel များကို (Cloudflare၊ Tailscale၊ ngrok) အသုံးပြုနေသော tunnel ၏ အခြေအနေကို မပြောင်းလဲဘဲ `Settings → Appearance` မှ ပြသနိုင်သလို ဖျောက်ထားနိုင်သည်။

### Tunnel မှတ်ချက်များ

- Quick Tunnel URL များသည် ယာယီဖြစ်ပြီး restart လုပ်တိုင်း ပြောင်းလဲသည်။
- OmniRoute သို့မဟုတ် container ကို restart လုပ်ပြီးနောက် Quick Tunnel များကို အလိုအလျောက် ပြန်လည်ဖွင့်ပေးမည် မဟုတ်ပါ။ လိုအပ်သည့်အခါ dashboard မှ ပြန်လည်ဖွင့်ပါ။
- Managed install သည် လက်ရှိတွင် `x64` / `arm64` ရှိသော Linux၊ macOS နှင့် Windows ကို ပံ့ပိုးသည်။
- အရင်းအမြစ်ကန့်သတ်ထားသော container environment များတွင် အနှောင့်အယှက်ဖြစ်စေသော QUIC UDP buffer သတိပေးချက်များကို ရှောင်ရှားရန် Managed Quick Tunnel များသည် HTTP/2 transport ကို မူလသတ်မှတ်ချက်အဖြစ် အသုံးပြုသည်။ မတူညီသော transport ကို အသုံးပြုလိုပါက `CLOUDFLARED_PROTOCOL=quic` သို့မဟုတ် `auto` ဟု သတ်မှတ်ပါ။
- Docker image များတွင် system CA root များ ပါဝင်ပြီး managed `cloudflared` သို့ လွှဲပေးထားသောကြောင့် container အတွင်း tunnel စတင်ချိန်၌ TLS ယုံကြည်မှုဆိုင်ရာ ချို့ယွင်းချက်များကို ရှောင်ရှားနိုင်သည်။
- OmniRoute အား ဒေါင်းလုဒ်လုပ်မည့်အစား ရှိပြီးသား binary ကို အသုံးပြုစေလိုပါက `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ဟု သတ်မှတ်ပါ။

အထက်တွင်ရှိသောချန်နယ်တိုင်းသည် `-web` tag (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) အဖြစ် `runner-web` အဆင့်မှ တည်ဆောက်ထားသော — တူညီသောပုံပေါင်း Playwright နှင့် Chromium ဘရောက်ဆာတစ်ခုဖြစ်သည်။ မြေပြန့်ပုံသဏ္ဍာန် သင်္ဘောများ** မပါဘဲ** ခရိုမီယမ်၊ `gemini-web`၊ `claude-web` နှင့် `claude-turnstile` လိုအပ်သည်။

ပျက်ကွက်မှုကို ရွှေ့ဆိုင်းထားသည်၊ စတင်ချိန်မဟုတ်ပါ- ထိုဝန်ဆောင်မှုပေးသူများသည် ၎င်းတို့၏မော်ဒယ်များကို စာရင်းပြုစုပြီး ဒက်ရှ်ဘုတ်တွင် ချိတ်ဆက်ထားသည့်အတိုင်း ပြသကာ ပထမတောင်းဆိုချက်တစ်ခုတည်းသာ ပျက်ကွက်သည်

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

အကယ်၍ သင်သည် အဆိုပါဝန်ဆောင်မှုပေးသူများကိုအသုံးပြုပါက၊ သင် — တွင်ရှိပြီးသားချန်နယ်၏ `-web` tag ကိုဆွဲယူပါ။ npm/CLI ထည့်သွင်းမှုတွင် ( Docker ပုံမရှိ) နှင့်ညီမျှသော ပျောက်ဆုံးနေသောအပိုင်းသည် ဘရောက်ဆာ binary ဖြစ်သည်- host ပေါ်တွင် `npx playwright install chromium` run သည်။

#### အကြိုထုတ်လွှင့်မှုချန်နယ်ကို အသုံးပြုခြင်း။

#### ဘေးကင်းရေးနှင့် နောက်ပြန်ဆုတ်ခြင်း။

`next` သည် ရေပေါ်ကြိုတင်ဖြန့်ချိသည့်ချန်နယ်တစ်ခုဖြစ်သည်။ ၎င်းသည် တက်ကြွသော ဖြန့်ချိရေးဌာနခွဲသို့ တွန်းအားပေးမှုအပေါ် ပြောင်းလဲနိုင်သည်။** ထုတ်လုပ်မှုအတွက် အသုံးမပြုပါ။** . သတ်မှတ်ထားသော တည်ဆောက်မှုကို အကဲဖြတ်နေစဉ် ပုံ၏ အနှစ်ချုပ်ကို ပင်ထိုးပါ-

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

စမ်းသပ်ခြင်းမပြုမီ၊ OmniRoute ဒေတာပမာဏ သို့မဟုတ် bind-mounted data directory ကို အရန်ကူးပါ။ ပြန်လှည့်ရန်၊ ယခင်အသုံးပြုထားသော တည်ငြိမ်သောဗားရှင်းကို ပြန်ယူပါ သို့မဟုတ် ချေဖျက်ပြီး ကွန်တိန်နာကို ပြန်လည်ဖန်တီးပါ-

```bash
docker pull cheaperinference/omniroute:<stable-version>
docker compose up -d
```

လွတ်မြောက်ရေးဌာနခွဲတည်ဆောက်မှုတစ်ခုသည် `latest` ဘယ်တော့မှမရွှေ့နိုင်ပါ။ အရည်အချင်းပြည့်မီသော တည်ငြိမ်သော အခေါ်အဝေါ်ဗားရှင်းတစ်ခုသာလျှင် တည်ငြိမ်သောညွှန်ပြချက်ကို မြှင့်တင်နိုင်သည်။ `next` ပုံများသည် ထွက်ရှိလာသော ပုံစစ်ဆေးခြင်းကို ထိန်းသိမ်းထားပြီး CRITICAL-vulnerability gate ကို ပိတ်ဆို့ထားသည်။

**`latest` သည် git အတွက်ငွေကြေးအာမခံချက်မဟုတ်ပါ။** `main` တွင် သို့မဟုတ် တက်ကြွသော `release/v*` ဌာနခွဲတွင် ပေါင်းစပ်ပြင်ဆင်မှုများ** မဟုတ်ဘူး** `:latest` တွင် တည်ငြိမ်သော SemVer ပုံတစ်ပုံကို လွှင့်တင်ပြီး ထုတ်ဝေခြင်းအလုပ်သည် `:latest` အားပေးသည် (ထို SemVer နှင့် တူညီသော အနှစ်ချုပ် )။ `latest` သည် fix ကိုပြသပြီးဖြစ်သော်လည်း GitHub သည်အေးခဲနေပါက၊ ထုတ်ဝေမှုဌာနခွဲကိုစမ်းသပ်ရန် `:next` ဆွဲထုတ်ပါ သို့မဟုတ် SemVer tag ကိုစောင့်ပါ။

| လိုချင်တယ်။                                                                          | သုံးပါ။                                      |
| ------------------------------------------------------------------------------------ | -------------------------------------------- |

| ထုတ်ဝေထားသော တဲများကို လိုက်နာပြီး ထုတ်ဝေမှုတစ်ခုစီတွင် ပြန်လည်ဖန်တီးမှုကို လက်ခံပါ။ | `:latest`                                    |
| မထုတ်ဝေရသေးသော `release/v*` ကတိကဝတ်များကို စမ်းသပ်သည်။                               | `:next` (ထုတ်လုပ်မှုမဟုတ်ပါ)                 |

## Docker ရှိ Dashboard အပ်ဒိတ်များ

ထုတ်ဝေထားသော image ကို အသုံးပြုသည့် container သည် မိမိကိုယ်တိုင် အစားထိုး၍ မရပါ။ OmniRoute က container တစ်ခုအတွင်း လည်ပတ်နေကြောင်း (`.git` checkout မရှိခြင်း၊ npm ဖြင့် ထည့်သွင်းထားခြင်း မဟုတ်ခြင်း) သိရှိသည့်အခါ ပင်မ dashboard ၏ အပ်ဒိတ် banner တွင် npm/git လမ်းညွှန်ချက်များအစား host ပေါ်တွင် လုပ်ဆောင်ရမည့် command ကို copy ခလုတ်နှင့်အတူ ပြသသည်-

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

Service အမည်ကို `AUTO_UPDATE_SERVICE` မှ ရယူသည် (မူလတန်ဖိုးမှာ `omniroute` ဖြစ်ပြီး `docker-compose.selfhost.yml` ထဲရှိ service ဖြစ်သည်)။ `pull` သည် ပြောင်းလဲနိုင်သော tag (`latest`, `next`) ကိုသာ ရွှေ့ပေးသည်။ သတ်မှတ်ထားသော `:X.Y.Z` tag ကို အသုံးပြုထားပါက tag ကို ဦးစွာ ပြင်ဆင်ပါ။

### Host trigger ဖိုင်ဖြင့် တစ်ချက်နှိပ် အပ်ဒိတ်များ

Container ကို host ပေါ်တွင် root အခွင့်အရေးပေးသည့် `/var/run/docker.sock` ကို mount မလုပ်ဘဲ **Update Now** ကို ဆက်လက်အသုံးပြုနိုင်ရန် (အထက်ရှိ `cli` profile သတိပေးချက်ကို ကြည့်ပါ) OmniRoute service တွင် `DOCKER_UPDATE_TRIGGER_FILE` ကို သတ်မှတ်ပြီး host ပေါ်တွင် watcher တစ်ခု လုပ်ဆောင်ပါ-

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

Path သည် `DATA_DIR` အတွင်း ရှိရမည် (relative တန်ဖိုးများကို ၎င်းနှင့် နှိုင်းယှဉ်၍ ဖြေရှင်းသည်)။ အခြားနေရာများကို ငြင်းပယ်မည်။ ထို့နောက် **Update Now** သည် `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }` ကို ထိုဖိုင်ထဲသို့ ရေးသားပြီး `202` ဖြင့် တုံ့ပြန်ကာ ဗားရှင်းအသစ် အလုပ်လုပ်သည်အထိ dashboard က `/api/system/version` ကို အကြိမ်ကြိမ် စစ်ဆေးပြီး ပြန်လည် load လုပ်သည်။ ဤ mode တွင် OmniRoute သည် shell သို့မဟုတ် Docker command တစ်ခုခုကို မည်သည့်အခါမျှ လုပ်ဆောင်ခြင်းမရှိပါ။ အခြားအပ်ဒိတ် လုပ်ဆောင်ချက်တိုင်းကဲ့သို့ပင် request ကို loopback/LAN client များထံမှသာ လက်ခံသည်။

Bind-mount လုပ်ထားသော data directory သည် host အတွက် စောင့်ကြည့်ရန် တည်ငြိမ်သော path တစ်ခုကို ပေးသည်။ နမူနာ `systemd` unit များ (`/srv/omniroute` ကို သင်၏ compose ဖိုင်နှင့် `data/` ပါရှိသည့် directory သို့ ပြင်ဆင်ပါ)-

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=OmniRoute dashboard အပ်ဒိတ် request များကို စောင့်ကြည့်ရန်

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=OmniRoute container ကို pull လုပ်ပြီး ပြန်လည်ဖန်တီးရန်

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

မအောင်မြင်သော လုပ်ဆောင်မှုတစ်ခု ထပ်ခါတလဲလဲ မဖြစ်စေရန် service သည် pull မလုပ်မီ request ကို ဖယ်ရှားသည်။ `DOCKER_UPDATE_TRIGGER_FILE` မရှိပါက dashboard သည် manual command လုပ်ငန်းစဉ်ကို ဆက်လက်အသုံးပြုသည်။

## ရရှိနိုင်မှု- မူရင်း SQLite သည် တစ်ခုတည်းသော ပုံစံတူဖြစ်သည်။

စတော့ခ် Docker / Kubernetes OmniRoute သည်** one Node process + one SQLite စာရေးဆရာ** . ရရှိနိုင်မှုမြင့်မားသည်။** မထောက်ခံပါ။** အဲဒီ topology ပေါ်မှာ။

| ကန့်သတ်ချက်                           | အကျိုးဆက်                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| လူပျို စာရေးဆရာ                       | လုပ်ပါ။** မဟုတ်ဘူး** တူညီသော SQLite ဖိုင်နှင့် ပုံစံတူများစွာကို လုပ်ဆောင်ပါ။ အဲဒါက DB ကို ပျက်စီးစေတယ်။                                                                                                                                                                                                                                                      |
| ပြန်လုပ် / restart / HEALTHCHECK kill | **ပြတ်တောက်မှု အပြည့်** in-flight SSE၊ dashboard sessions နှင့် in-memory state တို့။ ချိတ်ဆက်ထားသော သုံးစွဲသူတိုင်း ကျဆင်းသွားသည်။ အလွတ်မှတ်တိုင်ဝင်းဒိုးအတွင်း တောင်းဆိုချက်အသစ်များသည် ပြောင်းပြန်-ပရောက်စီကို ရယူပါ။**`502 Bad Gateway: Unknown error`** OmniRoute JSON — ဖောက်သည်များသည် ၎င်းကို ပံ့ပိုးပေးသူ ပျက်ကွက်ခြင်း (#11015) နှင့် ခွဲခြား၍မရပါ။ |
| `/healthz` နှင့် အလားတူဖြစ်ရပ်မျိုး   | အလုပ်များသောကက်တလောက် သို့မဟုတ် ဖိသိပ်မှုအမှတ်အသားသည် စုံစမ်းစစ်ဆေးမှုများကို နှောင့်နှေးစေနိုင်သည်။ ခဏတာ ကုန်ဆုံးပြီးနောက် ၎င်းကို ပြန်လည်စတင်သည်။** သာ** ပုံတူ။                                                                                                                                                                                             |

**လေ့လာဆန်းစစ်မှု matrix** ( [Kubernetes စုံစမ်းစစ်ဆေးရေး အကြံပြုချက်များကို](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ကြည့်ပါ )

| ထိုးဆွ         | ပစ်မှတ်                                                      | မသုံးပါနဲ့။                                                                                        |
| -------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| ရှင်သန်မှု     | TCP တွင် `PORT` (မူလ `20128`) သို့မဟုတ် Soft HTTP `/healthz` | `/api/monitoring/health`                                                                           |
| စေတနာ          | HTTP `GET /healthz`                                          | အဖြစ်အပျက်-ကွင်းဆက် အလုပ်ရှုပ်ခြင်းကို သေသည်အဖြစ် သတ်မှတ်ပေးသည့် တင်းကျပ်သော အချိန်ကုန်ဆုံးမှုများ |
| နက်နဲသော/လူသား | `/api/monitoring/health`                                     | အလိုအလျောက် kubelet အသက်ရှင်မှု                                                                    |

**အဆင့်မြှင့်တင်မှုများ** session တိုင်းကို drop ဖို့မျှော်လင့်တယ်။ သင်တတ်နိုင်လျှင်ဖောက်သည်များကိုထုတ်ပယ်; default SQLite တွင် rolling update မရှိပါ။ `restart: unless-stopped` အပေါင်း Docker `HEALTHCHECK` သည် ကွန်တိန်နာသည် ကျန်းမာရေးနှင့်မညီညွတ်သော — တူညီသောပေါက်ကွဲမှုအချင်းဝက်ရှိမှသာ လုပ်ငန်းစဉ်ကို အစားထိုးပါမည်။

အဆင်သင့်လုပ်ထားသော manifest များနှင့် Helm ဇယားကို `deploy/kubernetes/` နှင့် `deploy/helm/omniroute/` — တွင် တိုက်ရိုက်ဖော်ပြထားသော [Kubernetes အသုံးချခြင်းလမ်းညွှန်ကို](../ops/KUBERNETES_DEPLOYMENT_GUIDE.md) ကြည့်ပါ။

Kubernetes အတိုအထွာတစ်ခုအတွက်** ပုံတူတစ်ခုတည်း** (ပြန်လည်ဖန်တီးရန် လိုအပ်သည်၊ `replicas` SQLite ဖိုင်တစ်ခုမှ မတင်ပါနှင့်)

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` sleep သည် SIGTERM မတိုင်မီ kube သည် ဝန်ဆောင်မှု အဆုံးမှတ်များကို ချပေးနိုင်သည်။** အသစ်** ယာဉ်ကြောပိတ်ဆို့မှုသည် သေလုမြောပါးဖြစ်စဉ်ကို ထိခိုက်စေသည်။ လေယာဉ်တွင်း `/v1/responses` SSE ဟဲဗီးဝိတ်ဝင်ခွင့်ရငှားရမ်းမှုများ (#11015) မှတစ်ဆင့် `SHUTDOWN_TIMEOUT_MS` (မူလ 30 နှစ်များ) အထိ ကုန်ဆုံးသည်။ လုပ်ငန်းစဉ်သို့ရောက်ရှိဆဲ တောင်းဆိုချက်အသစ်များကို `503` + `Retry-After: 5` ရယူပါ။ အစားထိုးခြင်း အဆင်သင့်မဖြစ်မချင်း ပြန်လည်ဖန်တီးခြင်းသည် ခက်ခဲသော — ပြတ်တောက်မှုတစ်ခုဖြစ်ပြီး၊ probe misconfig မဟုတ်ဘဲ SQLite topology ဖြစ်သည်။

External Postgres / multi-writer HA is** မဟုတ်ဘူး** မှတ်တမ်းတင်ထားသော စတော့လမ်းကြောင်း။ အကယ်၍ သင်သည် HA လိုအပ်ပါက၊ တစ်ခုတည်းသော ပုံတူတစ်ခုကို သိမ်းဆည်းထားပါ သို့မဟုတ် သီးခြားစီပြုလုပ်ထားသော ပရောဂျက်မှ စမ်းသပ်ပြီး မှတ်တမ်းတင်ထားသော topology ကို လုပ်ဆောင်ပါ။ Postgres/MySQL အလုပ်သည် [#8075](https://github.com/cheaper-inference/OmniRoute/issues/8075) တွင်နေထိုင်သည်။ ထိုသင်္ဘောများ မရောက်မချင်း ပွားများရန် တစ်ခုတည်းသော နည်းလမ်းမှာ အထောက်အကူ ဖြစ်သည်။** ကြီးမားသော** `/v1/responses` စွမ်းရည်သည် Volume တစ်ခုတွင် `replicas > 1` မဟုတ်ဘဲ N အမှီအခိုကင်းသော လုပ်ငန်းစဉ်များ (နောက်အပိုင်း) ဖြစ်သည်။

## အတိုင်းအတာ- N သီးခြား လုပ်ငန်းစဉ်များ

### Codex တိုကင်လည်ပတ်မှုပိုင်ဆိုင်မှု

Codex အကောင့်တစ်ခု၏ မိတ္တူများသည် ၎င်း၏ တစ်ခါသုံး ပြန်လည်ဆန်းသစ်မှု တိုကင်ကို လွတ်လပ်စွာ သုံးစွဲခြင်းမပြုရပါ။ ထပ်တူပြုထားသည့် အထောက်အထားများကိုသာ အသုံးပြုသည့် သာဓကများတွင် `OMNIROUTE_TOKEN_REFRESH_PASSIVE_PROVIDERS=codex` (alias `cx`) ကို သတ်မှတ်ပါ။ လှည့်ခြင်းပိုင်ရှင်တစ်ခုတည်းတွင် ၎င်းကို မသတ်မှတ်ထားပါ။ လုပ်ငန်းစဉ်တစ်ခုစီသည် ၎င်း၏ကိုယ်ပိုင် `DATA_DIR` လိုအပ်ပါသေးသည်။ ဤရွေးချယ်မှုသည် SQLite မျှဝေခြင်းမရှိသလို တိုကင်ထပ်တူပြုခြင်း သို့မဟုတ် ဖြန့်ဝေသောသော့ကို ပေးဆောင်မည်မဟုတ်ပါ။

ပြန်လည်ဆန်းသစ်ရန် လိုအပ်သောအခါတွင် passive instance သည် ချိတ်ဆက်မှုကို ပြန်လည်ဖတ်ရှုပြီး မတူညီသော၊ သက်တမ်းမကုန်သေးသော အသုံးပြုခွင့်တိုကင်တစ်ခုကိုသာ လက်ခံပါသည်။ သို့မဟုတ်ပါက ပြန်လည်စတင်ခြင်းအား သက်တမ်းကုန်ဆုံးခြင်း သို့မဟုတ် ချိတ်ဆက်မှုကို ပိတ်ခြင်း သို့မဟုတ် ပြန်လည်စတင်ခြင်းဆိုင်ရာ ချို့ယွင်းမှုတို့ကို ရေတွက်ခြင်းမရှိဘဲ ပြန်လည်စတင်ခြင်းကို ပိတ်ထားသည်။ စစ်မှန်သော အထက်ပိုင်း စစ်မှန်ကြောင်း အထောက်အထား မခိုင်လုံသော ချို့ယွင်းချက်များသည် ပုံမှန် ပျက်ကွက်မှု စာရင်းအင်း၊ ကိန်းဂဏန်း အအေးခံစနစ် နှင့် ပုံမှန် ဖောက်သည် အမှားကို ဆက်လက် အသုံးပြုနေဆဲ ဖြစ်သည်။ အကောင့်ပိတ်ခြင်းသည် အမြဲတမ်းရှိနေပါသည်။ အသုံးပြုခွင့် တိုကင်များ သက်တမ်းမကုန်မီ ပိုင်ရှင်၏ အလှည့်ကျ တိုကင်များကို စင့်ခ်လုပ်ပါ (မူရင်း တက်ကြွသော ပြန်လည်ဆန်းသစ်မှု ဦးဆောင်မှုမှာ ငါးမိနစ်ဖြစ်သည်) သို့မဟုတ် Codex auth ဖိုင်ကို ပြန်လည်တင်သွင်းပါ။ Passive တင်သွင်းမှုများသည် တိုကင်အမှတ်အသားတွင် ၎င်းတို့ကို သက်သေမပြဘဲ ပေးထားသော တိုကင်များကို သိမ်းဆည်းထားသည်။ လူကိုယ်တိုင် dashboard/API refresh သည် `409 refresh_disabled` ကို ပြန်ပေးသည် ; OAuth အကောင့်အသစ်များသည် မပြောင်းလဲပါ။ [ပတ်ဝန်းကျင်ကို ကိုးကား](../reference/ENVIRONMENT.md#passive-codex-token-refresh) ကြည့်ပါ။

Node ဖြစ်စဉ်တစ်ခုဖြစ်ပါတယ်။** V8 အမှိုက်ပုံတစ်ခု** . ထပ်နေသော ~ 3 MiB / ~ 750k-တိုကင် ကုတ်ဒ်-အေးဂျင့် `POST /v1/responses` (RTK + Caveman) နှစ်ခုသည် ~ 12 Gi (`FATAL ERROR: Reached heap limit`) တွင် ထိုအမှိုက်ပုံအား ဖျက်သိမ်းလိုက်ပြီး OOM a 16 Gi cgroup လုပ်နိုင်သည် ။ [#7849](https://github.com/cheaper-inference/OmniRoute/issues/7849) ကြည့်ပါ။ ထိုအတိုင်းအတာသည် တစ်ခုဖြစ်သည်။** မှတ်ဉာဏ်-ဘတ်ဂျက်** သတိပေးချက်၊ တစ်ပြိုင်တည်း ရှည်လျားသော `/v1/responses` နှစ်ခု၏ hard-max မဟုတ်ပါ။ Heavyweight ချတ်ဝင်ခွင့်ကို အလိုအလျောက်ရရှိသော စားသုံးလိုက်သော ဘိုက်ဘတ်ဂျက် (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) သည် ၎င်းကို အပေါ်မှ ဖုံးအုပ်ထားသော အဆိုပါ V8/cgroup မျက်နှာကျက် — မှ အရွယ်အစား (သို့မဟုတ် အမွေဆက်ခံ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` တောင်းဆိုမှု-အရေအတွက်ထုပ်ကို သတ်မှတ်ခြင်း) ဖြင့် တံခါးပိတ်သည် အရွယ်အစားရှိ လုပ်ငန်းစဉ်တစ်ခုတွင် ဖျက်ချခြင်းကို ပြန်လည်မိတ်ဆက်သည်။ ချတ်အသေးများ၊ `/healthz`၊ `/v1/models` နှင့် MCP ဖြစ်သည်။** မဟုတ်ဘူး** ထိုဦးထုပ်၌။

### လုပ်ငန်းစဉ်တစ်ခု- ရှည်လျားသော `/v1/responses` နှစ်ခုထက်ပိုသည်။

တစ်** ကျန်းမာသည်။** လုပ်ငန်းစဉ် ( `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` အောက်တွင် အစုအပုံ၊ မူရင်း `0.75`)** မေ** လုပ်ငန်းစဉ်ကျယ်ပြန့်သော inflight-byte ဘတ်ဂျက် (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) တွင် နေရာလွတ်ကျန်နေချိန်တွင် တစ်ပြိုင်တည်း long `POST /v1/responses` နှစ်ခုထက်ပို၍ လုပ်ဆောင်ပါ။ `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (မူလ 256 KiB) တွင် သို့မဟုတ် အထက်တွင်ရှိသော ကောင်များသည် တူညီသော ဟဲဗီးဝိတ် ငှားရမ်းခကို ဖွဲ့စည်းပုံ-လေးလံသော တောင်းဆိုမှုများအတိုင်း ရယူပြီး တူညီသော [#10437](https://github.com/cheaper-inference/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` escape (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ကို အသုံးပြုပါ။ တစ်ပြိုင်တည်း SSE ဖောက်သည် ဆယ်ဂဏန်း (အော်ပရေတာများ မကြာခဏ 40-50 လိုအပ်သည်) သည် တစ်ခုဖြစ်သည်။** မှတ်ဉာဏ်-ဘတ်ဂျက်** မေးခွန်း — အရွယ်အစား အမှိုက်ပုံ + primary/headroom အကွက်များ + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` — ခက်ခဲသော “max 2” ထုတ်ကုန်ကန့်သတ်ချက်မဟုတ်ပါ။ ဖိအားပေးထားသော အမှိုက်ပုံသည် ပြန်စမ်းနိုင်သော `503` ပါနေသေးသောကြောင့် #7849 ပြန်မလာပါ။

ကိုက်ညီသည့်အထောက်အထားနှင့် မက်တာဒေတာရှိသော OAuth အကောင့်များတွင် ကိုက်ညီသောချိတ်ဆက်မှု IDs မလိုအပ်ပါ။ လူသိများသော အကောင့်အထောက်အထားများသည် ပင်ထိုးဆုံးဖြတ်ချက်နှင့် အစောင့်အကြပ်ထုတ်ပယ်ခြင်းတွင် ဆန့်ကျင်ဘက်ဖြစ်သော ဒေသန္တရ IDs ထက် ဦးစားပေးပါသည်။ အထောက်အထားမရှိဘဲ မှတ်တမ်းများ (သို့မဟုတ် အထောက်အထားမရှိဘဲ နှင်ထုတ်ခံရသူများ) သည် ID အစောင့်အရှောက်ကို ထိန်းသိမ်းထားသည်။ တည်ငြိမ်သောအသုံးပြုမှုအထောက်အထားမရှိသောအကောင့်များသည် ကိုက်ညီသော IDs လိုအပ်ဆဲဖြစ်သည်။ Redis အမှားအယွင်းများ သို့မဟုတ် 100 ms ထက်ကျော်လွန်သောခေါ်ဆိုမှုများသည် local SQLite သို့ ပြန်ရောက်သွားသည်။ Redis ရင်းနှီးမှုစတိုးတစ်ခုစီသည် 8 တွင် ထူးထူးခြားခြားလုပ်ဆောင်မှုများကို ကန့်သတ်ထားကာ၊ ပြည့်သည့်အခါ Redis ချက်ချင်းကျော်သွားကာ ခေါ်ဆိုသူနောက်ဆုံးရက်တွင်မဟုတ်ဘဲ အရင်းခံအလုပ်ပြေလည်သွားသည့်အခါမှသာ slot များကို ထုတ်ပေးပါသည်။ Redis ပြတ်တောက်မှုတစ်ခုအတွင်း မျှဝေထားသောအမှန်တရားမရှိပါ- instance တစ်ခုစီသည် ၎င်း၏စက်တွင်းရင်းနှီးမှုသို့ ပြန်ကျသွားသည်၊ session များသည် instance တစ်ခုလျှင် တစ်ကြိမ်ပြန်လည် pin နိုင်ပြီး၊ instance ကွဲပြားနိုင်သည်။ ပြန်လည်ကောင်းမွန်လာသောအခါတွင် ကပ်စေးမှုသည် Redis မှတဆင့် ပြန်လည်ရောက်ရှိသွားပါသည်။ အချိန်လွန်သည် စောင့်ဆိုင်းနေသည်၊ ပေးပို့သည့် EVAL မဟုတ်ဘဲ၊ နောက်ပြန်ဆုတ်ပြီးနောက် ပြန်ဆင်းလာနိုင်သည်။ Routing သည် အသစ်သော ပြောင်းလဲမှု-အချိန်ကို ဖတ်ရှုခြင်းမဟုတ်ဘဲ လမ်းကြောင်းဆုံးဖြတ်ခြင်းမှ သတိပြုမိသည့် အတိအကျတန်ဖိုးကို နှိုင်းယှဉ်ရေးသားသည်။ မှတ်သားထားသော miss သို့မဟုတ် SQLite အမှားအယွင်းတစ်ခုအား ပျက်ကွက် Redis သော့တစ်ခုအဖြစ် နှိုင်းယှဉ်သည်။ အသုံးမပြုတော့သော ပင်နံပါတ်များကို CAS တစ်ခုတွင် အစားထိုးထားသည်၊ ထို့ကြောင့် နောက်ကျသောအမိန့်ပေးမှုတစ်ခုသည် ပိုသစ်ပြီး မတူညီသော pin တစ်ခုကို အစားထိုး သို့မဟုတ် ဖျက်၍မရပါ။ Redis အက်တမ်တန်ဖိုးကို ပြန်ပေးသည်နှင့် ကျန်ဆာဗာ TTL ကို ဖတ်သည် ; အပြုသဘော PTTL (သို့မဟုတ် သက်တမ်းကုန်ဆုံးခြင်းမရှိ) သည် စာရေးဆရာ၏ JSON အချိန်တံဆိပ် သို့မဟုတ် စာဖတ်သူ၏နာရီကို မဟုတ်ဘဲ အသက်ရှင်သန်မှုကို ဆုံးဖြတ်သည်။ ဒေသဆိုင်ရာ လျှပ်တစ်ပြက်ရိုက်ချက်များသည် ကျန်ရှိနေသော TTL ကို ဒေသဆိုင်ရာ နောက်ဆုံးရက်အဖြစ် မြေပုံဆွဲပါ။ ရှိပြီးသား JSON သော့များသည် ဆက်လက်ဖတ်ရှုနိုင်မည်ဖြစ်ပြီး ၎င်းတို့၏ အကြမ်းဘိုက်များကို CAS အတွက် ထိန်းသိမ်းထားသည်။ Redis သည် အဖြေရှိစဉ်တွင် အမှန်တရား၏ တစ်ခုတည်းသောအရင်းအမြစ်ဖြစ်သည်။ အတည်ပြုထားသော မျှဝေထားသော တင်ပြချက်များ၊ ထိခြင်းနှင့် ဖျက်ခြင်းများသည် စက်တွင်းထည့်သွင်းမှုကို ဖယ်ရှားပါ၊ ၎င်းကို မည်သည့်အခါမျှ ထည့်သွင်းခြင်း သို့မဟုတ် ပြန်လည်စတင်ပါ။ Redis လမ်းကြောင်းပေါ်ရှိ SQLite Redis အမှားအယွင်းများ၊ အချိန်ကုန်သွားခြင်း သို့မဟုတ် ဝင်ခွင့်ပြည့်ဝခြင်းမှ ဤဥပမာ၏ကိုယ်ပိုင်ပြန်လည်သုံးသပ်ဆုံးဖြတ်ချက်များကိုသာ ကိုင်ဆောင်ထားခြင်းဖြစ်သည်။ နောက်ပိုင်း ပြတ်တောက်မှုတွင် ပျောက်ဆုံးနေသော စက်တွင်းပင်နံပါတ်သည် အသစ်ရွေးချယ်မှုတစ်ခု (တစ်ချက်တည်း-ကက်ရှ်လွတ်သွားသည်)၊ မှားယွင်းသော သို့မဟုတ် ဖယ်ရှားခံရသော အကောင့်ကို မပေးချေပါ။ ငြင်းဆိုထားသော အကြံပြုချက်များသည် မျှဝေထားသော အနိုင်ရရှိသူနှင့် ၎င်း၏ကျန်ရှိသော TTL အက်တမ်အဖြစ် ပြန်ပေးသည်- သာမာန်ရွေးချယ်မှုသည် မြေပုံထုတ်ထားသော ဒေသန္တရနောက်ဆုံးရက်ကို ပြန်လည်စစ်ဆေးပြီး အခြားမျှဝေထားသောစာမရေးဘဲ အကောင့်အတွက် အသုံးပြုမှုနှင့် လော့ဂ်အင်ကို ထိပြီး အသက်ရှင်ဆဲ အရည်အချင်းပြည့်မီသူအား အသုံးပြုသည်။ မရရှိနိုင်ပါက၊ ရွေးချယ်မှုသည် ဒေသတွင်း ကိုယ်စားလှယ်ကို ထိန်းသိမ်းထားပြီး မျှဝေထားသော ပင်နံပါတ်ကို မပြောင်းလဲဘဲ ချန်ထားခဲ့ကာ အမှားရှာပြင်သည့် မက်ဆေ့ချ်တစ်ခု ထုတ်ပေးသည်။ ပယ်ချခံရသော CAS SQLite မရေးပါ။ Redis အမှားအယွင်းများ၊ အချိန်ကုန်သွားခြင်း သို့မဟုတ် ဝင်ခွင့် ရွှဲရွှဲသည် အစား လက်ရှိ စက်တွင်းလုပ်ဆောင်ချက်ကို အသုံးပြုပါသည်။ အချိန်လွန်ပြီးနောက် ပေးပို့ထားသော ပြောင်းလဲမှု၏ အကြောင်းပြန်ချက်သည် (လက်ခံသည်၊ ငြင်းပယ်သည် သို့မဟုတ် အမှားအယွင်း) ရောက်ရှိလာပါက၊ ထပ်တူကျသည့် အတိအကျ အမှတ်စဉ်အလိုက်-တန်ဖိုး နှိုင်းယှဉ်-နှင့်-ဖျက်ခြင်းသည် ဘိုက်-ထပ်တူ အချိန်ကုန်သွားသည့် နောက်တန်းအတန်းကိုသာ ဖယ်ရှားသည်။ ထိုနှိုင်းယှဉ်မှုနှင့် ဖျက်ခြင်းကြားတွင် စောင့်မျှော်စရာမရှိပါ။ ပြတ်တောက်မှုအသစ်ကို သိမ်းဆည်းထားသည်။ လုံခြုံရေးတင်းကြပ်ထားသော နှင်ထုတ်ခြင်းသည် မအောင်မြင်သောအကောင့်၏ ကိုယ်ပိုင်စက်တွင်းပင်နံပါတ်ကို Redis နှင့်ပင် ဖယ်ရှားပြီး မျှဝေထားသည်ကို အတည်ပြုပြီးနောက် ၎င်းအား ထပ်မံရှင်းလင်းသည်။ မျှဝေထားသော အောင်မြင်မှုများသည် SQLite ဘယ်သောအခါမှ မရေးထားသောကြောင့် ဆိုင်းငံ့ထားသော အစောပိုင်းက မျှဝေထားသော ပြန်စာများသည် ဖယ်ရှားခံထားရသော စက်တွင်းပင်ပင်ကို ပြန်ယူ၍မရပါ။ နောက်ပိုင်းတွင် ပြတ်တောက်သွားခြင်းသည် အကောင့်တစ်ခုအား ပြန်လည်စတင်နိုင်သည်၊ နောက်ပိုင်းလက်ခံထားသော မျှဝေရေးစာသည် Redis တွင်သာ ရှိနေသည်။ Redis လွမ်းဆွတ်မှုများသည် ဒေသန္တရ ဆုတ်ယုတ်မှုအခြေအနေကို မတိုင်ပင်ပါ။ ယာဉ်မောင်းကို ပိတ်လိုက်ခြင်းဖြင့်၊ အသစ်ရွေးချယ်ထားသော ပင်နံပါတ်များသည် အမွေအနှစ် SQLite JSON ပုံသဏ္ဍာန်ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ Redis လမ်းကြောင်းပေးခြင်းဖြင့်သာလျှင် hashed အကောင့်အထောက်အထားကို ပေါင်းထည့်သည်။ ကြိုတင်ထုတ်ယူထားသော ပင်နံပါတ်များကို ၎င်းတို့၏ သက်တမ်းကုန်ဆုံးသည့်နယ်နိမိတ်တွင် ပြန်လည်စစ်ဆေးပါသည်။ Redis ငှားရမ်းခြင်းမဟုတ်သော ရွေးချယ်မှုသည် စတိုးဆိုင်ကို ပြန်လည်ဖတ်ရှုသော်လည်း ထပ်တူကျသော အငှားချစီစဉ်ခြင်းတွင် ကြိုတင်ထုတ်ယူခြင်းနှင့် စီစဉ်ခြင်းကြားမှ ဖယ်ရှားထားသော ပင်နံပါတ်ကို ဆက်လက်အသုံးပြုနိုင်ပါသေးသည်။ အငှားချမှုတစ်ခုသည် တာရှည်ခံတောင်းဆိုမှုတစ်ခုပြီးနောက် အကောင့်များကိုပြောင်း၍မရပါ- ငြင်းဆိုထားသည့်အခါတွင် ၎င်းသည် တောင်းဆိုချက်အတွက် တောင်းဆိုထားသည့် ကိုယ်စားလှယ်လောင်းကိုသာ သိမ်းဆည်းထားပြီး မျှဝေထားသောအနိုင်ရရှိသူကို မထိမခိုက်စေသောကြောင့် ဖြစ်ရပ်များတစ်လျှောက် သဘောတူညီချက်သည် ထိုလမ်းကြောင်းပေါ်တွင် ကန့်သတ်ထားသည်။ ကျန်ဇယား၏ကျန်ရှိနေသေးသည်- ၎င်းသည် ပေါင်းစည်းဆက်ရှင်တင်းကျပ်မှု၊ မူရင်း Codex အလှည့် pins၊ အကောင့် semaphores၊ လော့ခ်ချမှုများ၊ သုံးစွဲမှုကန့်သတ်ချက်များ၊ ဖွဲ့စည်းမှု သို့မဟုတ် ခေါ်ဆိုမှုမှတ်တမ်းများကို မျှဝေထားခြင်းမရှိပါ။

ဟာ့ဒ်ဝဲ- instance တစ်ခုချင်း ပြိုင်တူ ရှည်လျားသော `/v1/responses` သည် a** မှတ်ဉာဏ်-ဘတ်ဂျက်** မေးခွန်း ( heap + inflight-byte / #10110)။ `N` အမှီအခိုကင်းသော `DATA_DIR` s သည် အစုများကို များပြားနေဆဲဖြစ်သည်- host RAM `N × cgroup` ဖုံးအုပ်ထားရမည်ဖြစ်ပြီး "16 Gi pod တစ်ခုသည် N = 8" ဖြင့် မဟုတ်ဘဲ 16 Gi pod တစ်ခုဖြစ်သည်။ SQLite ဖိုင်တစ်ခုတွင် ဘယ်တော့မှ မ `replicas > 1` ။

ပုံကြမ်းရေးပါ (ပုံနှစ်ပုံ၊ အတွဲနှစ်တွဲ — မဟုတ် `deploy.replicas: 2`)

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

လုပ်ငန်းစဉ်အတွင်း သိပ်သည်းဆ ( HTTP isolate ကို ဖယ်ထုတ်ခြင်း) သည် [#11023](https://github.com/cheaper-inference/OmniRoute/issues/11023) ဖြစ်သည်။ မျှဝေထားသော တာရှည်ခံအခြေအနေရှိ ယုတ္တိဗေဒအစုအဝေးတစ်ခုသည် [#8075](https://github.com/cheaper-inference/OmniRoute/issues/8075) ဖြစ်သည်။

## Docker အတွင်းရှိGemini အမှားများ

Google AI Studio / Gemini API HTTP 400 ကို FAILED_PRECONDITION နှင့် `User location is not supported for the API use.` ဖြင့် ပြန်ပေးနိုင်သည်မှာ လက်ခံသူပေါ်ရှိ အောင်မြင်သောတောင်းဆိုချက်တစ်ခုသည် ကွန်တိန်နာသည် တူညီသောအထွက်လမ်းကြောင်းကို အသုံးပြုကြောင်း သက်သေမပြပါ။ DNS မှာယူခြင်း၊ IPv4/IPv6 ချိတ်ဆက်မှု၊ VPN လမ်းကြောင်းသတ်မှတ်ခြင်းနှင့် စီစဉ်သတ်မှတ်ထားသော ပရောက်စီများသည် ကွဲပြားနိုင်သည်။ [Google၏ပံ့ပိုးပေးထားသောဒေသများ](https://ai.google.dev/gemini-api/docs/available-regions) အပြင် အမှန်တကယ်ချိတ်ဆက်မှုလမ်းကြောင်းကိုစစ်ဆေးပါ။ ဤအမှားတစ်ခုတည်းကြောင့် မကောင်းတဲ့ API သော့ကို မဖော်ထုတ်နိုင်ပါ။

### ချိတ်ဆက်မှုဆိုင်ရာ ပရောက်စီကို ဦးစားပေးပါ။

ထိခိုက်နေသော Gemini ချိတ်ဆက်မှုအတွက် OmniRoute၏ [per-connection proxy configuration ကို](../ops/PROXY_GUIDE.md#4-level-proxy-system) သုံးပါ၊ ထို့နောက် ပြန်လုပ်ပါ။** စမ်းသပ်ချိတ်ဆက်မှု** တူညီသောမော်ဒယ်နှင့်အတူတောင်းဆိုမှုအသေးစား။ ၎င်းသည် လမ်းကြောင်းပြောင်းခြင်းကို ထိုချိတ်ဆက်မှုတွင် အတိုင်းအတာတစ်ခုအထိ ထိန်းသိမ်းထားသည်။ ပရောက်စီကို ကွန်တိန်နာမှ လှမ်းယူနိုင်ကြောင်း၊ ချိတ်ဆက်မှုသည် ၎င်းကို အမှန်တကယ် ရွေးချယ်ကြောင်း စစ်ဆေးပါ။ လမ်းကြောင်းပြောင်းခြင်းသည် အထက်ပိုင်းဒေသဆိုင်ရာ အရည်အချင်းပြည့်မီမှုကို အာမမခံနိုင်ပါ။

### လက်ခံသူနှင့် ကွန်တိန်နာကွန်ရက်ကို နှိုင်းယှဉ်ပါ။

စစ်မှန်သောရလဒ်များကို နှိုင်းယှဉ်သည့်အခါ သော့၊ မော်ဒယ်နှင့် တောင်းဆိုချက် တူညီနေပါစေ။ အထောက်အထားများ၊ ပရောက်စီစကားဝှက်များ သို့မဟုတ် ပြီးပြည့်စုံသော ခွင့်ပြုချက်ခေါင်းစီးများကို ပြဿနာတစ်ခုအဖြစ် ဘယ်သောအခါမှ မထည့်ပါ။ လက်ခံသူနှင့် ကွန်တိန်နာအတွင်းတွင် တူညီသော command ကို အသုံးပြု၍ OS ဖြေရှင်းသူ ကမ်းလှမ်းသည့် မိသားစုများ၏ လိပ်စာကို စစ်ဆေးပါ။

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

သင်အသုံးပြုသည့်ဝန်ဆောင်မှုဖြင့် `omniroute` အစားထိုးပါ (ဥပမာ `omniroute-web`)။ ဤအမိန့်တော်များသည် အထောက်အထားများ သို့မဟုတ် IP လိပ်စာများမပါဘဲ မိသားစုလိပ်စာများကို ထုတ်ယူသည်။ ပြန်လာသော `6` IPv6 DNS ရလဒ်ကိုသာ ပြသသည်- ၎င်းသည် လုပ်ဆောင်သည်။** မဟုတ်ဘူး** အသုံးပြုနိုင်သော IPv6 လမ်းကြောင်း သို့မဟုတ် API ဝင်ရောက်မှုကို သက်သေပြပါ။ `curl` ထည့်သွင်းသည့်နေရာတွင်၊ ပတ်ဝန်းကျင်နှစ်ခုလုံးတွင် `curl -4 -I https://generativelanguage.googleapis.com` နှင့် `curl -6 -I https://generativelanguage.googleapis.com` နှိုင်းယှဉ်ပါ။ HTTP တုံ့ပြန်မှုသည် ၎င်းသည် အထောက်အထားမခိုင်လုံသော အမှားဖြစ်လျှင်ပင် ထိုစုံစမ်းစစ်ဆေးမှုအတွက် ချိတ်ဆက်မှုကို သက်သေပြသည်။ စစ်မှန်သော မော်ဒယ် တောင်းဆိုမှု စမ်းသပ်မှုများ Gemini အရည်အချင်းပြည့်မီမှုကိုသာ။

### လက်ခံသူအဆင့် အခြားရွေးချယ်စရာ- IPv6 နှင့် ဖြေရှင်းသူမူဝါဒကို လုပ်ဆောင်သည်။

[#12762](https://github.com/cheaper-inference/OmniRoute/issues/12762) ၏သတင်းထောက်သည် ကွန်တိန်နာ IPv6 ကိုဖွင့်ကာ glibc လိပ်စာရွေးချယ်မှုကို ပြောင်းလဲခြင်းဖြင့် ၎င်းတို့၏ပတ်ဝန်းကျင်တွင် ဝင်ရောက်ကြည့်ရှုခွင့်ကို ပြန်လည်ရယူခဲ့သည်။ ဒါကို ပတ်ဝန်းကျင်ဆိုင်ရာ သီးခြားရွေးချယ်စရာအဖြစ် သဘောထားပါ။ ဖြေရှင်းသူဦးစားပေးများကို မချိန်ညှိမီ အလုပ်လက်ခံသူ IPv6၊ container egress/routing နှင့် firewall စည်းမျဉ်းများကို အတည်ပြုပါ။ သီးသန့် ULA လိပ်စာသည် အများသူငှာ IPv6 ချိတ်ဆက်မှုကို မသတ်မှတ်ပါ။

Compose ၏မူလကွန်ရက်တွင် ချိတ်ဆက်ထားပြီးသော ဝန်ဆောင်မှုများအတွက်၊ ဤအပိုင်းသည် IPv6 ထိုကွန်ရက်ပေါ်တွင် ဖွင့်ပေးသည်။ ကျန်ရှိသော သင်၏ဝန်ဆောင်မှု၊ ဆိပ်ကမ်းများ၊ ထုထည်များနှင့် ဖွဲ့စည်းမှုပုံစံများကို ထိန်းသိမ်းထားပါ-

```yaml
networks:
  default:
    enable_ipv6: true
```

အမည်ပေးထားသော ကွန်ရက်တစ်ခုအတွက်၊ ဝန်ဆောင်မှု အမှန်တကယ်ပါဝင်သည့် ကွန်ရက်ပေါ်တွင် ၎င်းကို ဖွင့်ပါ။ Docker ULA subnet ကိုခွဲဝေပေးနိုင်သည်။ သင့်ကွန်ရက်လိုအပ်သည့်အခါမှသာ တိကျပြတ်သားသော၊ ထပ်နေခြင်းမရှိသော subnet တစ်ခုကို ရွေးချယ်ပါ။ [Docker IPv6 ကွန်ရက်ချိတ်ဆက်မှုကို](https://docs.docker.com/engine/daemon/ipv6/) ကြည့်ပါနှင့် [ကွန်ရက်ရွေးချယ်စရာများကို ရေးဖွဲ့ပါ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ။

ဂရန်** glibc-အခြေခံပုံ** , `/etc/gai.conf` လိပ်စာရွေးချယ်မှုကို ပြောင်းလဲနိုင်သည်။ လက်ရှိသိမ်းဆည်းထားသော Dockerfile သည် Debian ကိုအသုံးပြုသည်။ စိတ်ကြိုက် musl အခြေခံပုံများသည် ဤယန္တရားကို မမျှဝေပါ။ အစီရင်ခံထားသော ချိန်ညှိမှုသည် ULA အညွှန်းကို `label fc00::/7 6` မှ `label fc00::/7 1` သို့ ပြောင်းသည်။ ပုံ၏ ပြီးပြည့်စုံသော မူဝါဒဇယားမှ စတင်ပြီး ၎င်း၏ အခြားထည့်သွင်းမှုများကို ထိန်းသိမ်းပါ- `label` သို့မဟုတ် `precedence` ထည့်သွင်းမှုသည် အဆိုပါ ပုံသေဇယားကို အစားထိုးသည်၊ ထို့ကြောင့် ပြောင်းလဲထားသော စာကြောင်းတစ်ခုသာပါရှိသော ဖိုင်သည် မလုံလောက်ပါ။ [glibc configuration ရည်ညွှန်းချက်သည်](https://github.com/bminor/glibc/blob/master/posix/gai.conf) ထိုဝေါဟာရများကို မှတ်တမ်းတင်သည်။ `/etc/gai.conf` တွင် ပြန်လည်သုံးသပ်ထားသော ဖိုင်ကို ဖတ်ရန်-သပ်သပ် ချိတ်တွဲပြီး ၎င်းကို အသုံးပြုရန် ဝန်ဆောင်မှုကို ပြန်လည်ဖန်တီးပါ။

၎င်းသည် OS လိပ်စာရွေးချယ်မှုကို ပြောင်းလဲသည်။** ထိုကွန်တိန်နာအတွင်းမှ အထွက်အသွားအလာအားလုံး** . IPv6 ရွေးချယ်ရန် အပ DNS ကေးရှင်းတိုင်းကို အတင်းအကျပ် မခိုင်းစေရပါ။ အထူးသဖြင့်၊ `--dns-result-order=ipv4first` IPv4 ပိုနှစ်သက်ပြီး IPv4-only ကျရှုံးမှုအတွက် ကုစားမဟုတ်ပါ။ [Node DNS အမိန့်ကို](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ကြည့်ပါ။

လက်ခံသူအဆင့် ပြောင်းလဲမှုတစ်ခုခုပြီးနောက် Gemini နှင့် သင်၏အခြားဝန်ဆောင်မှုပေးသူများကို ပြန်လည်စမ်းသပ်ပါ။ ပြန်လှည့်ရန်၊ စိတ်ကြိုက် `gai.conf` mount ကို ဖယ်ရှားပါ၊ ယခင် ကွန်ရက်ဖွဲ့စည်းပုံကို ပြန်ယူကာ ပြုပြင်ထိန်းသိမ်းမှုဝင်းဒိုးအတွင်း ထိခိုက်နေသော service/network ပြန်လည်ဖန်တီးပါ။ ကွန်ရက်တစ်ခုကို ပြန်လည်ဖန်တီးခြင်းသည် ၎င်းနှင့် ချိတ်ဆက်ထားသော အခြားကွန်တိန်နာများကို အနှောင့်အယှက်ဖြစ်စေနိုင်သည်။ persistent data volume ကို မဖျက်ပါနှင့်။

## အရေးကြီးသော မှတ်ချက်များ

- **SQLite WAL Mode:** OmniRoute က နောက်ဆုံးပြောင်းလဲမှုများကို `storage.sqlite` ထဲသို့ checkpoint ပြန်လုပ်နိုင်စေရန် `docker stop` ကို ပြီးဆုံးသည်အထိ လုပ်ဆောင်ခွင့်ပြုသင့်သည်။ ပူးတွဲပါရှိသော Compose ဖိုင်များတွင် ရပ်တန့်ရန် အချိန်ပိုကာလ 40s ကို သတ်မှတ်ထားပြီးဖြစ်သည်။ image ကို တိုက်ရိုက် run ပါက `--stop-timeout 40` ကို ဆက်လက်ထားရှိပါ။
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ပုံမှန်/ရေးသားမှုမပြုမီ backup များကို ပြင်ပစနစ်ဖြင့် စီမံထားပါက `true` ဟု သတ်မှတ်ပါ။ ရှိပြီးသား database များ၏ migration များအတွက်မူ ၎င်းတို့ကိုယ်ပိုင် ရေရှည်ခံသော ဘေးကင်းရေး snapshot နှင့် အစုလိုက် migration ကာကွယ်မှု လိုအပ်ဆဲဖြစ်သည်။
- **ဒေတာ ရေရှည်သိမ်းဆည်းမှု:** container ပြန်လည်စတင်မှုများကြားတွင် သင့် database၊ key များနှင့် configuration များကို ဆက်လက်သိမ်းဆည်းထားရန် volume တစ်ခုကို `/app/data` သို့ အမြဲတမ်း mount လုပ်ပါ။
- **Port သတ်မှတ်မှု:** မူလ `20128` port ကို ပြောင်းလဲရန် `PORT` environment variable ကို override လုပ်ပါ။
