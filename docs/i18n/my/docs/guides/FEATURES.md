## ✨ v3.8.0 ၏ အထူးအချက်များ

v3.7.x → v3.8.0 အဆင့်မြှင့်တင်မှုစက်ဝန်းတွင် စီစဉ်သတ်မှတ်ရန်မလိုသော အလိုအလျောက်လမ်းကြောင်းရွေးချယ်မှု၊ provider အသစ်များ၊ OAuth လုပ်ငန်းစဉ်များ၊ ပိုမိုနက်ရှိုင်းသော ခံနိုင်ရည်ရှိမှုနှင့် ပိုမိုပြည့်စုံကြွယ်ဝသော CLI အသုံးပြုမှုအတွေ့အကြုံတို့ကို ထည့်သွင်းထားသည်။ အဓိကအင်္ဂါရပ်များကို အောက်တွင်ဖော်ပြထားပြီး အသေးစိတ်အပြည့်အစုံကို ဤစာတမ်း၏ နောက်ပိုင်းအပိုင်းများနှင့် ချိတ်ဆက်ထားသော သတ်မှတ်ချက်စာတမ်းများတွင် ကြည့်ရှုနိုင်သည်။

- 🤖 **အလိုအလျောက် ပေါင်းစပ်မှု / စီစဉ်သတ်မှတ်ရန်မလိုသော အလိုအလျောက်လမ်းကြောင်းရွေးချယ်မှု** — prefix များဖြစ်သော `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`, `auto/chaos` ကို အသုံးပြုပါ။ အချက် 16 ချက်ပါ အမှတ်ပေးအင်ဂျင်နှင့် စနစ်တကျရွေးချယ်ထားသော **mode pack** 6 ခု (ship-fast, cost-saver, quality-first, offline-friendly, reliability-first, chaos-mode) က ပံ့ပိုးထားသည်
- 🆕 **Command Code provider** (#2199) — model catalog နှင့် quota ခြေရာခံမှုပါဝင်သော ပထမတန်းစား မှတ်ပုံတင်မှု
- 🆕 **Z.AI provider** — quota အညွှန်းများပါဝင်သည့် အခမဲ့အဆင့် provider အသစ်
- 🎬 **KIE မီဒီယာ တိုးချဲ့မှု** — ဗီဒီယိုဖန်တီးသည့် model များအပါအဝင် catalog ကို တိုးချဲ့ထားသည်
- 🔐 **Devin စစ်မှန်ကြောင်းအတည်ပြုမှု** — Desktop သည် ရှိပြီးသား Devin API key ကို ထည့်သွင်းအသုံးပြုသည်၊ CLI ကမူ စက်တွင်းရှိ `devin auth login` အထောက်အထားများကို အသုံးပြုသည်
- 🆓 **အခမဲ့ provider အသစ် 8 ခု** — LLM7, Lepton, UncloseAI, BazaarLink, Completions, Enally, FreeTheAi, Command Code
- 🎯 **Manifest ကိုထည့်သွင်းစဉ်းစားသော W1–W4 အဆင့်လိုက်လမ်းကြောင်းရွေးချယ်မှု** — provider manifest များက အလေးချိန်ပေးထားသော အဆင့်ရွေးချယ်မှုကို ထိန်းချုပ်သည်
- 🎨 **Cursor ၏ OpenAI နှင့် အပြည့်အဝတန်းတူညီမှု** — tool call များ၊ streaming နှင့် session စီမံခန့်ခွဲမှုတို့ကို အစမှအဆုံး ပံ့ပိုးထားသည်
- 📊 **Cursor Pro အစီအစဉ် အသုံးပြုမှု** — quota နှင့် စက်ဝန်းဒေတာကို provider ကန့်သတ်ချက် dashboard တွင် ဖော်ပြထားသည်
- ⚡ **ဝန်ဆောင်မှုအဆင့် ခွဲခြမ်းဖော်ပြမှု / Codex အမြန်အဆင့် ခွဲခြမ်းစိတ်ဖြာမှု** — အဆင့်တစ်ခုချင်းအလိုက် သုံးစွဲမှုကို မြင်နိုင်သည်
- 📌 **Session တစ်ခုချင်းအလိုက် တည်ငြိမ်သောလမ်းကြောင်းရွေးချယ်မှု** — Codex session များကို အပြန်အလှန်ဆက်သွယ်မှုတစ်ကြိမ်နှင့်တစ်ကြိမ်ကြား တူညီသော account တွင် ချိတ်ဆက်ထားသည်
- 🔊 **Inworld TTS မြှင့်တင်မှုများ** — အသံ catalog များ၊ streaming နှင့် တုံ့ပြန်ချိန် မြှင့်တင်မှုများ
- 🔑 **Kiro headless စစ်မှန်ကြောင်းအတည်ပြုမှု** — browser မလိုဘဲ စက်တွင်း `kiro-cli` SQLite သိုလှောင်မှုမှတစ်ဆင့် login ဝင်နိုင်သည်
- 📉 **DeepSeek quota နှင့် ကန့်သတ်ချက် စောင့်ကြည့်မှု** — နေ့စဉ်/လစဉ် အသုံးပြုမှုကို dashboard မှတစ်ဆင့် ဖော်ပြထားသည်
- 🔄 **ပြန်လည်သတ်မှတ်ချိန်ကို ထည့်သွင်းစဉ်းစားသော လမ်းကြောင်းရွေးချယ်မှု မဟာဗျူဟာ** — ပေါင်းစပ်မှုများသည် quota ကာလ အစောဆုံးပြန်လည်သတ်မှတ်မည့် account များကို ယခု ဦးစားပေးသည်
- ⏱️ **`fallbackDelayMs`** နှင့် **dynamic tool ကန့်သတ်ချက် ရှာဖွေသတ်မှတ်မှု** — fallback အချိန်ကို ပိုမိုအသေးစိတ်ချိန်ညှိနိုင်ခြင်း + provider တစ်ခုချင်းအလိုက် tool အရေအတွက် ကန့်သတ်ချက်များ
- 🔧 **နောက်ခံမုဒ် အဆင့်လျှော့ချမှု (Responses API)** — အထက်စီးဝန်ဆောင်မှုတစ်ခုက နောက်ခံ polling ကို မပံ့ပိုးပါက ဖွဲ့စည်းပုံတကျ သတိပေးချက်တစ်ခုနှင့်အတူ synchronous mode သို့ fallback လုပ်သည်
- 🚦 **Provider တစ်ခုချင်းအလိုက် 429 အမျိုးအစားခွဲခြားမှု** + `useUpstream429BreakerHints` အဖွင့်အပိတ် — အထက်စီး rate-limit အချက်ပြမှုများကို အသုံးပြု၍ breaker အပြုအမူကို ပိုမိုအသေးစိတ်ထိန်းချုပ်နိုင်သည်
- 🩺 **Model cooldown dashboard** — model တစ်ခုချင်းအလိုက် ယာယီပိတ်ထားမှုများကို စောင့်ကြည့်ပြီး UI မှ ကိုယ်တိုင်ပြန်လည်ဖွင့်နိုင်သည်
- 🔒 **MITM ၏ ပြောင်းလဲနိုင်သော Linux လက်မှတ် ရှာဖွေသတ်မှတ်မှု** — Debian/Ubuntu, Fedora/RHEL, Arch နှင့် အခြား distro များတွင် အလုပ်လုပ်သည်
- 💻 **CLI မြှင့်တင်မှု အစုံအလင်** — `omniroute providers`, `omniroute combos`, `omniroute doctor`, `omniroute setup` အပါအဝင် command 20 ကျော်
- 🔍 **Qdrant embedding model ရှာဖွေတွေ့ရှိမှု** — vector-store model ကို အလိုအလျောက် စမ်းသပ်စစ်ဆေးသည်
- 🔑 **`manage` scope ပါသော API Key များ / Bearer key များ** — API မှတစ်ဆင့် စီမံခန့်ခွဲရေးလုပ်ဆောင်ချက်များကို ပရိုဂရမ်ဖြင့် လုပ်ဆောင်နိုင်သည်
- 🏥 **ပေါင်းစပ်မှု ပစ်မှတ် ကျန်းမာရေး ခွဲခြမ်းစိတ်ဖြာမှု** + **ဖွဲ့စည်းပုံတကျ ပေါင်းစပ်မှုတည်ဆောက်ကိရိယာ** — ပစ်မှတ်တစ်ခုချင်းအလိုက် ကျန်းမာရေးအခြေအနေနှင့် `(provider, model, connection)` အဆင့်များကို စုစည်းတည်ဆောက်ရန် UI တည်ဆောက်ကိရိယာ

## 🎨 Combos

အများသူငှာ မဟာဗျူဟာ 22 ခုဖြင့် မော်ဒယ်လမ်းကြောင်းသတ်မှတ်ခြင်း ပေါင်းစပ်မှုများ ဖန်တီးပါ- ဦးစားပေး၊ အလေးချိန်၊ အဝိုင်း-ရော်ဘင်၊ ဆက်စပ်-ထပ်ဆင့်ပို့မှု၊ ပထမဦးစွာ ဖြည့်စွက်မှု၊ p2c (ရွေးချယ်မှုနှစ်ခု၏ ပါဝါ)၊ ကျပန်း၊ အသုံးအနည်းဆုံး၊ ကုန်ကျစရိတ်-အကောင်းဆုံး၊ ပြန်လည်သတ်မှတ်မှု-သတိပြုမှု၊ ပြန်လည်သတ်မှတ်မှု-ဝင်းဒိုး၊ သက်တမ်းကုန်-ပထမ၊ ကန့်သတ်ချက်၊ ကန့်သတ်ချက်၊ (နောက်ဆုံး-သိ-ကောင်း-ပံ့ပိုးပေးသူ)၊ ဆက်စပ်-အကောင်းဆုံးဖြစ်အောင်၊ ကက်ရှ်-အကောင်းဆုံးဖြစ်အောင်၊** ပေါင်းစပ်မှု** (အပြိုင် မော်ဒယ်များ အကန့်ကို အားပေးပါ၊ ထို့နောက် တရားသူကြီးမှတစ်ဆင့် အဖြေတစ်ခုကို ပေါင်းစပ်ပါ)၊** ပိုက်လိုင်း** , နှင့်** jev** (သင်၏အဆင့်သတ်မှတ်ချက်စာရင်းထက် TypeSafe Jev ဝင်ခွင့်ကို ရွေးချယ်ပါ။) ပေါင်းစပ်မှုတစ်ခုစီတွင် မော်ဒယ်များစွာကို အလိုအလျောက် တုံ့ပြန်မှုဖြင့် ချိတ်ဆက်ထားပြီး အမြန်ပုံစံများနှင့် အဆင်သင့်စစ်ဆေးမှုများ ပါဝင်သည်။

လတ်တလော ပေါင်းစပ်တိုးတက်မှုများ-

- **ဖွဲ့စည်းတည်ဆောက်ထားသော ပေါင်းစပ်တည်ဆောက်သူ** ဝန်ဆောင်မှုပေးသူ၊ မော်ဒယ်နှင့် account/connection အတိအကျကို ရွေးချယ်ခြင်းဖြင့် — အဆင့်တစ်ခုစီကို ဖန်တီးပါ။
- **ထပ်ခါတလဲလဲ ပံ့ပိုးပေးသူ** — tuple သည် ထူးခြားသရွေ့ တူညီသောဝန်ဆောင်မှုပေးသူကို ပေါင်းစပ်မှုတစ်ခုတွင် အကြိမ်များစွာ ပြန်သုံးပါ `(provider, model, connection)`
- **Combo ပစ်မှတ်ကျန်းမာရေး** — ခွဲခြမ်းစိတ်ဖြာချက်များနှင့် ကျန်းမာရေးမျက်နှာပြင်များသည် အရာအားလုံးကို မော်ဒယ်ကြိုးများအဖြစ် ပြိုကျမည့်အစား တစ်ဦးချင်းစီ ပေါင်းစပ် targets/steps ကို ခွဲခြားနိုင်ပါပြီ
- **ပေါင်းစပ်အဆင့် အော်ဒါမှာသည်။** — `defaultTier -> fallbackTier` ထိပ်တန်းအဆင့် ပေါင်းစပ်အဆင့်များအတွက် ယခု runtime execution/fallback အစီအစဉ်ကို လွှမ်းမိုးထားသည်။
- **စနစ်ပုံစံ နမူနာများ** — combo `system_message` server-side `{{MODEL_ID}}`, `{{PROVIDER_ID}}`, `{{ACCOUNT}}` နှင့် `{{FINGERPRINT}}` placeholder များကို ပံ့ပိုးပေးသည်၊ ခွင့်ပြုထားသောစာရင်းနှင့် ထပ်တူမကျသော၊ အမည်မသိနေရာကိုင်ဆောင်သူများသည် ပကတိအတိုင်းတည်ရှိနေပါသည်။ ဗလာတန်ဖိုးများကို ဗလာအဖြစ် ချဲ့ထွင်သည်။ client system prompts တွေကို ဘယ်တော့မှ ပြန်မရေးပါဘူး။ `{{FINGERPRINT}}` — ထိုးထားသော သို့မဟုတ် အလိုအလျောက်လှည့်ထားသော လက်ဗွေဖြင့် လက်ဗွေအခြေခံ အခမဲ့ဝန်ဆောင်မှုပေးသူများအတွက်သာ ဖြေရှင်းပေးသည် (ဥပမာ- လက်ဗွေတစ်ခုတည်းချိတ်ဆက်မှုများ၊ fp မဟုတ်သောဝန်ဆောင်မှုပေးသူများ)။ ချဲ့ထွင်မှုသည် စံ dispatch loop၊ round-robin နှင့် pinned context-cache sessions များကို အကျုံးဝင်ပါသည်။ ပေါင်းစပ်မှု၊ ပရမ်းပတာမှု၊ ပိုက်လိုင်းနှင့် nested-execute မဟာဗျူဟာများသည် နေရာချထားသူများကို မချဲ့ထွင်သေးပါ။

- **အသွင်အပြင်** — Theme ရွေးချယ်ကိရိယာ (dark/light/system)၊ အရောင် theme ကြိုတင်သတ်မှတ်ချက်များနှင့် စိတ်ကြိုက်အရောင်များ၊ health log မြင်နိုင်မှု၊ sidebar item နှင့် group separator မြင်နိုင်မှု ထိန်းချုပ်ချက်များ၊ Endpoint tunnel မြင်နိုင်မှု ထိန်းချုပ်ချက်များ
- **AI** — AI assistant လုပ်ဆောင်ချက်များ၊ မူလ routing ကြိုတင်သတ်မှတ်ချက်များ (Auto Combo `auto/coding`, `auto/fast`, `auto/cheap`, `auto/smart`)၊ reasoning replay cache နှင့် skill/memory အဖွင့်အပိတ်များ
- **လုံခြုံရေး** — API endpoint ကာကွယ်မှု၊ စိတ်ကြိုက် provider ပိတ်ဆို့ခြင်း၊ IP စစ်ထုတ်ခြင်း၊ session အချက်အလက်
- **Routing** — Model alias များ၊ နောက်ခံ task အဆင့်လျှော့ချခြင်း၊ manifest ကို အခြေခံသော tier routing (W1–W4)၊ `fallbackDelayMs`၊ session တစ်ခုချင်းစီအလိုက် sticky routing
- **ခံနိုင်ရည်** — Rate limit အမြဲတမ်းထိန်းသိမ်းမှု၊ circuit breaker ချိန်ညှိမှု၊ ပိတ်ပင်ခံထားရသော account များကို အလိုအလျောက်ပိတ်ခြင်း၊ provider သက်တမ်းကုန်ဆုံးမှု စောင့်ကြည့်ခြင်း၊ **Context Relay** လွှဲပြောင်းမှု threshold နှင့် summary model ဖွဲ့စည်းသတ်မှတ်မှု၊ provider တစ်ခုချင်းစီအလိုက် 429 အမျိုးအစားခွဲခြားမှုနှင့် `useUpstream429BreakerHints` အဖွင့်အပိတ်၊ model cooldown များ
- **အဆင့်မြင့်** — Configuration override များ၊ configuration စစ်ဆေးမှတ်တမ်း၊ fallback အဆင့်လျှော့ချမှု mode၊ Responses API အတွက် နောက်ခံ mode အဆင့်လျှော့ချမှု

## 🗜️ Prompt ချုံ့ခြင်း _(v3.7.9+)_

Context & Cache တွင် ယခု Caveman၊ RTK နှင့် Compression Combos တို့အတွက် သီးသန့်စာမျက်နှာများ ပါဝင်လာသည်-

- **Caveman** — ဘာသာစကားကို သိရှိနားလည်သော စည်းမျဉ်းအစုများ၊ အကြိုကြည့်ရှုမှု၊ output mode ထိန်းချုပ်မှုများနှင့် ခွဲခြမ်းစိတ်ဖြာချက်များ
- **RTK** — shell၊ git၊ test၊ build၊ package၊ Docker၊ infra၊ JSON နှင့် stack-trace output များအတွက် command ကို သိရှိနားလည်သော ချုံ့ခြင်း
- **Compression Combos** — routing combo များတွင် သတ်မှတ်အသုံးပြုသည့် `rtk -> caveman` ကဲ့သို့သော အမည်ပေးထားသည့် pipeline များ၊ engine နှစ်ခုစလုံး အလုပ်လုပ်သည့်အခါ မူလအဆင့်ဆင့်တွက်ချက်မှုအရ ပျမ်းမျှ `~89%` နှင့် ချုံ့နိုင်သော ဆက်စပ်အကြောင်းအရာတွင် `78-95%` အထိ သက်သာမှု ရရှိသည်
- **မူရင်း output ပြန်လည်ရယူခြင်း** — ချုံ့ခြင်းဆိုင်ရာ ချို့ယွင်းမှုများကို debugging ပြုလုပ်ရန် ရွေးချယ်အသုံးပြုနိုင်သော အရေးကြီးအချက်အလက်များ ဖျောက်ထားသည့် RTK မူရင်း output ညွှန်းချက်များ

[ချုံ့ခြင်း လမ်းညွှန်](../compression/COMPRESSION_GUIDE.md)၊ [RTK ချုံ့ခြင်း](../compression/RTK_COMPRESSION.md) နှင့်

## 🛡️ Proxy လုံခြုံရေး မြှင့်တင်ခြင်း _(v3.5.5+)_

တောင်းဆိုမှု pipeline တစ်ခုလုံးတွင် ပြည့်စုံသော proxy configuration ကို မဖြစ်မနေ အသုံးပြုစေသည်-

- **Token အခြေအနေ စစ်ဆေးခြင်း** — နောက်ခံ OAuth refresh သည် ယခု connection တစ်ခုချင်းစီအလိုက် proxy config ကို ရှာဖွေဖြေရှင်းပေးသဖြင့် proxy မဖြစ်မနေလိုအပ်သော environment များတွင် ချို့ယွင်းမှုများ မဖြစ်ပေါ်စေရန် ကာကွယ်ပေးသည်
- **API Key အတည်ပြုခြင်း** — Provider key အတည်ပြုခြင်း (`POST /api/providers/validate`) ကို `runWithProxyContext` မှတစ်ဆင့် route လုပ်ပြီး provider အဆင့်နှင့် global proxy ဆက်တင်များကို လိုက်နာအသုံးပြုသည်
- **undici Dispatcher ပြင်ဆင်ချက်** — Proxy dispatcher များသည် Node ၏ built-in fetch အစား undici ၏ ကိုယ်ပိုင် fetch implementation ကို အသုံးပြုသဖြင့် Node.js 22 တွင် ဖြစ်ပေါ်သော `invalid onRequestStart method` error များကို ဖြေရှင်းပေးသည်
- **Node.js Version ရှာဖွေစစ်ဆေးခြင်း** — Login စာမျက်နှာသည် ကိုက်ညီမှုမရှိသော Node.js version များ (24+) ကို ကြိုတင်ရှာဖွေစစ်ဆေးပြီး Node 22 LTS အသုံးပြုရန် ညွှန်ကြားချက်များပါဝင်သော သတိပေး banner တစ်ခုကို ပြသသည်

## 🖥️ Desktop Application

Windows၊ macOS နှင့် Linux အတွက် native Electron desktop app။ System tray ပေါင်းစပ်မှု၊ offline ပံ့ပိုးမှု၊ အလိုအလျောက် update နှင့် တစ်ချက်နှိပ် install လုပ်ဆောင်ချက်တို့ဖြင့် OmniRoute ကို သီးခြား application တစ်ခုအဖြစ် အသုံးပြုနိုင်သည်။

အဓိကလုပ်ဆောင်ချက်များ-

- Server အဆင်သင့်ဖြစ်မှုကို အကြိမ်ကြိမ် စစ်ဆေးခြင်း (စတင်ဖွင့်ချိန်တွင် မျက်နှာပြင်အလွတ် မပေါ်စေပါ)
- Port စီမံခန့်ခွဲမှုပါဝင်သည့် system tray
- အကြောင်းအရာ လုံခြုံရေးမူဝါဒ
- Instance တစ်ခုတည်းသာ အသုံးပြုနိုင်ရန် lock
- ပြန်လည်စတင်ချိန်တွင် အလိုအလျောက် update
- Platform အလိုက် သတ်မှတ်ထားသော UI (macOS traffic light များ၊ Windows/Linux မူလ titlebar)
- ပိုမိုလုံခြုံခိုင်မာသော Electron build packaging — သီးခြား bundle အတွင်း symlink ပြုလုပ်ထားသည့် `node_modules` ကို packaging မပြုလုပ်မီ ရှာဖွေပြီး ပယ်ချသဖြင့် runtime တွင် build machine ကို မှီခိုရခြင်းမှ ကာကွယ်ပေးသည် (v2.5.5+)
- **စနစ်တကျ ပိတ်သိမ်းခြင်း** — Electron `before-quit` သည် Next.js ကို စနစ်တကျ ပိတ်သိမ်းပေးပြီး SQLite WAL database lock များ ဖြစ်ပေါ်ခြင်းကို ကာကွယ်ပေးသည် (v3.6.2+)

## 🌐 V1 WebSocket Bridge _(v3.6.6+)_

ယခုအခါ OmniRoute သည် `/v1/ws` upgrade endpoint မှတစ်ဆင့် **OpenAI နှင့် တွဲဖက်အသုံးပြုနိုင်သော WebSocket client များ** ကို ပံ့ပိုးပေးသည်။ စိတ်ကြိုက် `scripts/dev/v1-ws-bridge.mjs` server သည် Next.js ကို wrapper ပြုလုပ်ပြီး WS connection များကို အပြည့်အဝ နှစ်ဖက်သွား streaming session များအဖြစ် upgrade ပြုလုပ်ပေးသည်။ Authentication အတွက် HTTP request များကဲ့သို့ တူညီသော API key သို့မဟုတ် session cookie ကို အသုံးပြုသည်။

အဓိကလုပ်ဆောင်ပုံများ-

- Connection မတည်ဆောက်မီ WS upgrade ကို `src/lib/ws/handshake.ts` ဖြင့် စစ်ဆေးအတည်ပြုသည်
- Session ပိတ်သိမ်းချိန် သို့မဟုတ် upstream error ဖြစ်ပေါ်ချိန်တွင် stream များကို စနစ်တကျ ရပ်တန့်သည်
- ရှိပြီးသား HTTP+SSE streaming လမ်းကြောင်းနှင့် တစ်ပြိုင်နက်တည်း တွဲဖက်အလုပ်လုပ်သည်

## 🔑 Sync Token များနှင့် Config Bundle _(v3.6.6+)_

ယခုအခါ **နယ်ပယ်သတ်မှတ်ထားသော sync token များ** မှတစ်ဆင့် စက်အများအပြားနှင့် ပြင်ပ operator များမှ အသုံးပြုနိုင်ပါသည်-

- **`POST /api/sync/tokens`** — sync token အသစ်တစ်ခု ထုတ်ပေးသည် (နယ်ပယ်သတ်မှတ်ထားပြီး သက်တမ်းကုန်ဆုံးချိန်ကို ရွေးချယ်သတ်မှတ်နိုင်သည်)
- **`DELETE /api/sync/tokens/:id`** — token တစ်ခုကို ပြန်လည်ရုပ်သိမ်းသည်
- **`GET /api/sync/bundle`** — config ၏ version သတ်မှတ်ထားပြီး ETag ဖြင့် key သတ်မှတ်ထားသော JSON snapshot ကို ဒေါင်းလုဒ်လုပ်သည် (sync token တစ်ခုတည်းဖြင့်သာ အထောက်အထားစိစစ်သည်)။ Dashboard password ကဲ့သို့သော auth setting များကို ဖယ်ရှားထားသော်လည်း provider credential များနှင့် API key များ ပါဝင်သောကြောင့် ဤဖိုင်ကို လျှို့ဝှက်ဖိုင်အဖြစ် ကိုင်တွယ်ပါ

Config bundle ကို `src/lib/sync/bundle.ts` က တည်ဆောက်သည်။ Payload အပြည့်အစုံကို ထပ်မံဒေါင်းလုဒ်မလုပ်ဘဲ ပြောင်းလဲမှုများကို ရှာဖွေရန် အသုံးပြုသူများသည် `ETag` response header ကို နှိုင်းယှဉ်ကြသည်။ CLI မှ `omniroute sync bundle <outPath> --token <syncToken>` (သို့မဟုတ် `OMNIROUTE_SYNC_TOKEN`) ကို အသုံးပြုပါက ၎င်းကို ပိုင်ရှင်သာ အသုံးပြုနိုင်သော ဖိုင်အဖြစ် သိမ်းဆည်းသည်။

## 🛡️ ဘေးကင်းသော ပြင်ပသို့ ဆွဲယူမှု & SSRF Guard _(v3.6.6 +)_

ဝန်ဆောင်မှုပေးသူ၏ တရားဝင်အတည်ပြုချက်နှင့် မော်ဒယ်ရှာဖွေတွေ့ရှိမှုခေါ်ဆိုမှုအားလုံးသည် ယခုအခါ အပြင်ဘက်အလွှာနှစ်ခုမှ အကာအကွယ်တစ်ခုဖြင့် သွားကြသည်-

1. **URL ကိုယ်ရံတော်** (`src/shared/network/outboundUrlGuard.ts`) — ပထမဦးစွာရေးသားထားသည့်အတိုင်း ပစ်မှတ်၏ hostname သို့မဟုတ် IP literal ကိုစစ်ဆေးပါ။ အများသူငှာ သီးသန့်မုဒ်တွင် လုံခြုံစွာယူဆောင်မှု ထုပ်ပိုးခြင်းသည်လည်း အမည်ကို ဖြေရှင်းပေးပြီး သီးသန့်အဖြေများကို ငြင်းပယ်သည်။ မူရင်းအားဖြင့် ၎င်းသည် cloud-metadata အဆုံးမှတ်များ — အားလုံးကို 169.254.0.0/16 နှင့် သိထားသော metadata hostnames များကိုပိတ်ဆို့သည်။ `OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS=false` သီးသန့် နှင့် loopback host များကိုလည်း ပိတ်ဆို့ထားသည်။ `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS=true` (သို့မဟုတ် `OUTBOUND_SSRF_GUARD_ENABLED=false` အမွေအနှစ်) စစ်ဆေးမှုများကို ပိတ်သည်။ အလံတစ်ခု၏ ဒက်ရှ်ဘုတ်အဖွင့်အပိတ်မှ သိမ်းဆည်းထားသော တန်ဖိုးသည် ၎င်း၏ variable ထက် သာလွန်ပြီး သော့အတည်ပြုချက်တွင် ထည့်သွင်းထားသော ပြည်တွင်းဝန်ဆောင်မှုပေးသူများသည် အစောင့်ကို ကျော်သွားပါသည်။ `docs/reference/ENVIRONMENT.md` ကြည့်ပါ။
2. **ဘေးကင်းသော ထုပ်ပိုးမှု** (`src/shared/network/safeOutboundFetch.ts`) — URL အစောင့်အကြပ်ကို အသုံးပြုကာ အချိန်ကုန်မှုများကို ပုံမှန်ဖြစ်စေပြီး ကိန်းဂဏန်းများကို နောက်ပြန်ပိတ်ခြင်းဖြင့် ယာယီအမှားများကို ထပ်လုပ်သည်။

`getSafeOutboundFetchErrorStatus` (မော်ဒယ်ရှာဖွေမှုလမ်းကြောင်းတွင် 400) မှတဆင့် `URL_GUARD_BLOCKED` — HTTP 503 အဖြစ်အပေါ်ယံချိုးဖောက်မှုများသည် — နှင့် စစ်မှန်သော SSRF တုံးများကို `provider.validation.ssrf_blocked` ဖြစ်ရပ်များအဖြစ် စာရင်းစစ်မှတ်တမ်းတွင် ရေးသားထားသည်။

## 🔄 Cooldown ကို ထည့်သွင်းစဉ်းစားသော ပြန်လည်ကြိုးစားမှုများ _(v3.6.6+)_

Upstream provider တစ်ခုက model အလိုက်သတ်မှတ်ထားသော cooldown ကို ပြန်ပေးသည့်အခါ ယခုအခါ chat request များသည် **အလိုအလျောက် ပြန်လည်ကြိုးစားသည်**။ `REQUEST_RETRY` (ပုံသေ- 2) နှင့် `MAX_RETRY_INTERVAL_SEC` (ပုံသေ- 30 s) တို့မှတစ်ဆင့် ပြင်ဆင်သတ်မှတ်နိုင်သည်။ `x-ratelimit-reset-requests`၊ `x-ratelimit-reset-tokens` နှင့် `Retry-After` တို့တစ်လျှောက် rate-limit header ကို လေ့လာသိရှိမှု ပိုမိုကောင်းမွန်လာပြီး model တစ်ခုချင်းစီ၏ cooldown အခြေအနေကို Resilience dashboard တွင် မြင်တွေ့နိုင်သည်။

Audit log ကို cursor အခြေပြု စာမျက်နှာခွဲခြင်း၊ request context ဖြည့်စွက်ခြင်း (request ID၊ user agent၊ IP)၊ ဖွဲ့စည်းပုံကျသော auth event များ၊ ကွာခြားချက် context ပါဝင်သည့် provider CRUD event များနှင့် SSRF ကြောင့် ပိတ်ဆို့ထားသော အတည်ပြုမှု logging တို့ဖြင့် တိုးချဲ့ထားသည်။ Event အသစ်များကို `src/lib/compliance/providerAudit.ts` က ထုတ်လွှတ်သည်။
