## 1. အရာများ ရှိသည့်နေရာ

- **Kit။** `packages/ui-kit/src` သည် `packages/ui-kit/UPSTREAM.md` တွင် pin လုပ်ထားသည့် commit ရှိ upstream `src/` ကို byte-for-byte ကူးယူထားခြင်းဖြစ်သည် (`packages/ui-kit/UPSTREAM.md` တွင် license authorization ကိုလည်း မှတ်တမ်းတင်ထားသည်)။ `PATCHES.md` တွင် local patch များကို စာရင်းပြုစုထားသည် (မရှိပါ)။ ၎င်းကို build မလုပ်ဘဲ source အဖြစ် တိုက်ရိုက်အသုံးပြုသည်။ `next.config.mjs` က ၎င်းကို transpile လုပ်ပြီး
  `tsconfig.json` က `@omniroute/ui-kit` → `packages/ui-kit/src` နှင့် `@omniroute/ui-kit/*` →
  `packages/ui-kit/src/*` ဟု map လုပ်ထားသည် (`vitest.config.ts` နှင့် `vitest.mcp.config.ts` တို့တွင်လည်း တူညီသော alias ရှိသည်)။ Kit component တစ်ခုကို ၎င်း၏ subpath (`@omniroute/ui-kit/table`, `@omniroute/ui-kit/page-header`…) မှတစ်ဆင့် import လုပ်ပါ။ `@omniroute/ui-kit` barrel မှတစ်ဆင့် မည်သည့်အခါမျှ import မလုပ်ပါနှင့်။ Barrel သည် component အားလုံးကို (date picker အပါအဝင်) importer တစ်ခုစီထဲသို့ ဆွဲသွင်းမည်ဖြစ်သည်။ Kit stylesheet ကို `src/app/globals.css`
  (`@import "../../packages/ui-kit/src/ci-styles.css"`, ပြီးပြည့်စုံသော sheet ဖြစ်ပြီး core `ci-ui.css` နှင့် pattern family အားလုံး ပါဝင်သည်) မှတစ်ဆင့် ထည့်သွင်းထားသည်။
- **Token များ။** `packages/ui-kit/src/ci-tokens.css` က `--ci-*` token များကို ကြေညာသည်။ `src/app/globals.css`
  က ၎င်းတို့ကို အဟောင်း OmniRoute အမည်များ (`--color-*`, `--radius-*`, `--font-sans`/`--font-mono`,
  `--table-*`, `--orch-status-*`, `--color-fd-*`) နှင့် ချိတ်ဆက်ပေးထားသောကြောင့် ရှိပြီးသား `var(--color-*)` ဖတ်ယူမှုများနှင့် Tailwind utility များ ဆက်လက်အလုပ်လုပ်သည်။ Code အသစ်များတွင် Tailwind utility များ (`bg-surface`, `text-text-muted`,
  `border-border`, `text-success`, `bg-success-bg`, `bg-chart-1`…) သို့မဟုတ် kit class များကို အသုံးပြုပြီး hex value ကို မည်သည့်အခါမျှ မသုံးပါနှင့်
  (`tests/unit/design-kit-bridge.test.ts` က bridge ကို enforce လုပ်ထားသည်)။ `text-primary` သည်
  `--text-color-primary` မှတစ်ဆင့် `--color-primary-ink` သို့ resolve လုပ်သောကြောင့် primary text ကို ဖတ်ရှုရလွယ်ကူစေပြီး
  `bg-primary`/`border-primary` က accent surface ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ Editions အောက်တွင် ၎င်းသည် kit ၏
  `--ci-color-accent-active` (light တွင် ကြေးနီရောင်ရင့် `#99562f`၊ dark တွင် ကြေးနီ accent) ဖြစ်ပြီး Classic အောက်တွင်မူ
  light တွင် lime-800 နှင့် dark တွင် lime accent ဖြစ်သည်။ Chart series များသည်
  `--color-chart-1` … `--color-chart-5` ကို အသုံးပြုသည်။
- **Theme များ။** `<html className="ci-theme">` (`src/app/layout.tsx`) က document ကို kit theme ထဲသို့ ထည့်သွင်းသည်။
  Preference သည် `light`, `dark` သို့မဟုတ် `system` ဖြစ်သည် (`src/shared/constants/appConfig.ts` ရှိ
  `THEME_CONFIG.defaultTheme = "system"`၊ `system` သည် `prefers-color-scheme` ကို လိုက်နာသည်)။ `src/store/themeStore.ts` ရှိ
  `applyTheme()` သည် (`src/app/layout.tsx` ထဲတွင် inline လုပ်ထားပြီး hydration မတိုင်မီ run သော `THEME_BOOT_SCRIPT` ကလည်း အလားတူလုပ်ဆောင်သည်)
  `data-theme="dark"|"light"` ကို သတ်မှတ်ပြီး `<html>` ပေါ်ရှိ `.dark` class ကိုလည်း တစ်ပြိုင်နက် toggle လုပ်သည်။
  Kit ၏ dark token set ကို `data-theme="dark"` အပေါ် အခြေခံထားသည် (`packages/ui-kit/src/ci-tokens.css`)။
  OmniRoute ၏ ကိုယ်ပိုင် dark override များ (`globals.css` ရှိ `.dark` block) နှင့် အဟောင်း Tailwind `dark:`
  utility များကို `.dark` class အပေါ် အခြေခံထားသည်။ Accent color preset များ မရှိပါ။ Accent သည် kit မှ အမြဲလာပြီး
  အဟောင်း build တစ်ခုမှ persist လုပ်ထားသည့် preset ကို store load လုပ်သည့်အခါ ဖယ်ရှားသည်။
- **Palette များ။** နှစ်ခုရှိပြီး နှစ်ခုစလုံး kit မှလာသည် (`src/shared/constants/appearancePalette.ts`)။ Default ဖြစ်သည့် `editions` နှင့်
  `classic` တို့ဖြစ်သည်။ Editions သည် `<html>` ပေါ်ရှိ kit ၏ `data-ci-appearance="editions"` attribute ဖြစ်ပြီး
  `ci-editions.css` (`ci-ui.css` က import လုပ်ထားသည်) က ၎င်းကို `data-theme` နှင့် ပေါင်းစပ်အသုံးပြုသည်။ Classic သည် ထို attribute မရှိခြင်းဖြစ်သည်။
  Root layout က attribute ကို server-render လုပ်သောကြောင့် သိမ်းဆည်းထားသည့်အရာမရှိသော visitor (သို့မဟုတ် JS မရှိသော visitor) သည်
  dashboard၊ login၊ `/status`၊ error page များ၊ `/docs` နှင့် PWA အပါအဝင် surface အားလုံးတွင် Editions ကို ရရှိသည်။ ရွေးချယ်မှုကို
  theme နှင့်အတူ တူညီသော `theme` store ထဲတွင် persist လုပ်ထားပြီး (`src/store/themeStore.ts` ရှိ `palette`, `setPalette()`, `applyPalette()`)
  `THEME_BOOT_SCRIPT` က paint မတိုင်မီ အသုံးချသည်
  (`src/shared/utils/themeBootScript.ts`၊ layout ၏ `<head>` ထဲတွင် inline လုပ်ထားသည်)။ သိမ်းဆည်းထားသော palette သည် `"classic"` ဖြစ်သည့်အခါမှသာ
  attribute ကို ဖယ်ရှားသည်။ Root layout အပြင်ဘက်ရှိ `src/app/global-error.tsx` ကလည်း တူညီသော store မှ ၎င်းကို အသုံးချသည်။
  `data-ci-appearance` ကို အခြားမည်သည့် element ပေါ်တွင်မျှ မထည့်ပါနှင့်။ Kit က ၎င်းကို
  `html:root:has([data-ci-appearance="editions"])` ဖြင့် match လုပ်သောကြောင့် descendant တစ်ခုတည်းက document တစ်ခုလုံးကို ပြောင်းလဲစေမည်ဖြစ်သည်။
  Editions ၏ `data-ci-editions-variant="landing"` variant သည် marketing page များအတွက်ဖြစ်ပြီး dashboard အတွက် မဟုတ်ပါ။
  Browser chrome အတွက် server က default ဖြစ်သည့် Editions ကို `viewport.themeColor` တွင် render လုပ်သည် (`prefers-color-scheme` တစ်ခုစီအတွက် tag တစ်ခု)၊ web manifest တွင်လည်း render လုပ်သည် — `src/shared/constants/pwaThemeColors.ts` ရှိ
  `PWA_THEME_COLORS` သည် Editions ၏ `--ci-color-background`
  (`#f3f1e9` / `#11120f`) ကို mirror လုပ်ထားသည့် တစ်ခုတည်းသောနေရာဖြစ်ပြီး `tests/unit/pwa-theme-colors.test.ts` က ၎င်းကို `ci-editions.css` နှင့် pin လုပ်ထားသည်။ ထို့နောက် live
  `<meta name="theme-color">` သည် သိမ်းဆည်းထားသော palette နှင့် mode ကို လိုက်နာသည်။ `THEME_BOOT_SCRIPT` က paint မတိုင်မီ tag များကို ပြန်ရေးပြီး
  theme store ၏ action များက ပြောင်းလဲမှုတိုင်းတွင် ထိုသို့လုပ်ဆောင်သည် (`src/shared/utils/themeColorMeta.ts` ရှိ `resolveThemeColor()` /
  `applyThemeColor()`၊ kit ၏ `ciTokens` မှ `CLASSIC_PAGE_BACKGROUND` ကို ဖတ်ယူသည်)။ Light/dark theme ကို အတိအလင်း သတ်မှတ်ထားပါက tag အားလုံးကို ထို mode သို့ သတ်မှတ်သည်။ `system` သည်
  scheme တစ်ခုစီအတွက် colour တစ်ခုစီကို ထိန်းသိမ်းထားသည်။ Manifest သည် Editions အဖြစ် ဆက်ရှိနေသည်။ ၎င်းကို install တစ်ခုလျှင် တစ်ကြိမ်သာ fetch လုပ်ပြီး
  preference မပါဝင်ပါ။ Monaco သည် probe တစ်ခုမှ ၎င်း၏ colour များကို ဖတ်ယူသည် (`monacoKitTheme.ts`)။

## 2. စည်းကမ်းများ

1. တိုကင်များ၊ စာလုံးများကို ဘယ်တော့မှ မရေးပါ။ ခြွင်းချက်များ- ပကတိ hex လိုအပ်သောခေါ်ဆိုသူများအတွက် kit status palette ၏ ဖြေရှင်းထားသော-hex မှန်၊ အမြဲတမ်း-မှောင်နေသော ကွန်ဆိုးလ်ဂိတ်နှင့် `STATUS_HEX` (`src/shared/constants/statusColors.ts`) တို့ဖြစ်သည်။ အမျိုးအစားအလိုက် palettes များသည် ခြွင်းချက်မရှိတော့သည်- ၎င်းတို့သည် `src/shared/utils/categoricalPalette.ts` မှတဆင့် kit ၏ ဇယားတိုကင်ငါးခု (`--color-chart-1..5`) နှင့်၊ လမ်းကြောင်းသတ်မှတ်ခြင်းဗျူဟာများအတွက် `src/app/(dashboard)/dashboard/combos/strategyPalette.ts`; ReactFlow အစွန်းများနှင့် တီးမှုတ်ခြင်း ကင်းဗတ်စသည် ဆောင်ပုဒ်-သတိပြုမိသော `--orch-status-*` ကိန်းရှင်များ (`src/shared/components/flow/edgeStyles.ts`) ကို ဖတ်သည်။
2. `packages/ui-kit/src` လက်ဖြင့် မပြင်ပါနှင့်။ `scripts/dev/sync-ui-kit.sh <commit>` နှင့် ထပ်တူပြုပါ။ pre-commit gate `npm run check:ui-kit-snapshot` (`.husky/pre-commit`) သည် pinned upstream commit နှင့် မတူသည့် မည်သည့် byte တွင်မဆို ကျရှုံးသည် (အထက်ပိုင်း clone, `UI_KIT_CLONE` သို့မဟုတ် `_references/cheaper-inference-ui-kit`, မရှိသည့်အခါ သတိပေးချက်ဖြင့် ကျော်သွားသည်)။ ပစ္စည်းတစ်ခုခု ချို့တဲ့သောအခါ၊ ၎င်းကို adapter သို့မဟုတ် စခရင်တွင် ပတ်ပြီး ၎င်းကို ရေအထက်သို့ တောင်းပါ။
3. Kit စာသား မူရင်းများသည် အင်္ဂလိပ် (`label = "Loading"`, `loadingLabel = "Loading table"`… ) — kit အစိတ်အပိုင်းမှ စာသားကို ပြန်ဆိုသည့်အခါတိုင်း `useTranslations(...)` မှ ဘာသာပြန်ထားသော စာကြောင်းများကို ဖြတ်သန်းပါ။
4. Tailwind utilities သည် kit အစိတ်အပိုင်း အတန်းများကို ကျော်ပြီး အနိုင်ရသည် (kit သည် `@layer theme, base, components, utilities` နှင့် ၎င်း၏ စည်းမျဉ်းများကို `components` တွင် ကြေငြာထားသည်) — kit အစိတ်အပိုင်းများကို အရောင်ပြန်မဖော်ရန်၊ အကွာအဝေးနှင့် အပြင်အဆင်အတွက် အသုံးအဆောင်များကို အသုံးပြုပါ။
5. ခေါင်းစဉ်များ- စာမျက်နှာနှင့် ကဏ္ဍခေါင်းစဉ်များအတွက် `.ci-heading` ; `.ci-dashboard-display` error-page status code ကဲ့သို့သော ကြီးမားပြီး ကျဲကျဲသော display စာသားအတွက်သာ။ Switzer ကိုသုံးပါတယ်။
6. `tests/unit/dashboard-kit-sweep.test.ts` kit မွေးစားခြင်းကို အကာအကွယ်ပေးသည်- `src/app` သို့မဟုတ် `src/shared/components` အောက်တွင် Material ligature span မရှိပါ။ ဒက်ရှ်ဘုတ်သစ်ပင် (`src/app/(dashboard)` နှင့် `src/shared/components`) တွင် အကြမ်းထည် `<select>`၊ `<textarea>` သို့မဟုတ် `<table>` နှင့် စာရင်းသွင်းထားသော ခြွင်းချက်ပြင်ပတွင် လက်ဖြင့်လှိမ့်ထားသော `role="dialog"` မရှိပါ ( `Select` adapter ၏ မူရင်းဌာနခွဲ၊ `RequestLoggerDetail`); `<button>` သို့မဟုတ် `<input>` အကြမ်းတိုင်းတွင် ၎င်း၏အထက်စာကြောင်း 3 ခုတွင် အများဆုံးအဆုံးသတ်သည့် `kit-exception:` (အကြောင်းပြချက်ဖြင့်) ပါရှိသော မှတ်ချက်တစ်ခု လိုအပ်ပါသည်။ စမ်းသပ်စာရင်းဖိုင်များတွင်သာ palette hues နှင့် `dark:` မျိုးကွဲများ။
7. PR (ဖန်သားပြင်ဓာတ်ပုံများ) မတိုင်မီ အပြင်အဆင်နှင့် 390 px မြင်ကွင်းပို့တ်ကို စစ်ဆေးပါ။ `tests/e2e/a11y.spec.ts` ပုဆိန်ဖြင့် အလုပ်လုပ်သည်။

1. `src/shared/components/index.tsx` ၏ public API ကို ထိန်းသိမ်းထားပါ — export အမည်များ၊ default export များနှင့် လက်ခံသည့် props များ အတူတူဖြစ်ရမည်။ legacy props များကို adapter အတွင်းတွင် kit ပေါ်သို့ map လုပ်ပါ (`Button.tsx` ကို ကြည့်ပါ: `VARIANT_TO_KIT`,
   `SIZE_TO_KIT`)။
2. kit ကို subpath ဖြင့် import လုပ်ပါ (`@omniroute/ui-kit/<component>`)။
3. kit ၏ လစ်လပ်ချက်များအတွက် workaround များကို adapter အတွင်းတွင် (သို့မဟုတ် ပြင်ဆင်ချက်က style ဖြစ်လျှင် `globals.css` `@layer components` အတွင်းတွင်) ထားရှိပါ၊ `packages/ui-kit/src` အတွင်းတွင် လုံးဝ မဟုတ်ပါ။
4. `tests/unit/ui/adapters/<name>.test.tsx` ကို ထည့်ပါ သို့မဟုတ် update လုပ်ပါ။ caller များ များစွာရှိသော adapter တစ်ခုအတွက် ပြောင်းလဲမှုမပြုလုပ်မီနှင့် ပြုလုပ်ပြီးနောက် render လုပ်ထားသော markup ကို နှိုင်းယှဉ်ပါ — padding သို့မဟုတ် wrapper ပြောင်းလဲမှုများသည် screen တိုင်းသို့ ပျံ့နှံ့သွားသည်။

## 5. ပစ္စည်းအစုံကို အပ်ဒိတ်လုပ်ခြင်း။

`npm run check:ui-kit-upstream` `packages/ui-kit/UPSTREAM.md` တွင်ထိုးထားသောဗားရှင်းကို upstream repo ၏နောက်ဆုံးထွက် `v*` tag နှင့် နှိုင်းယှဉ်ပြီး ထွက်ရှိလာသောအခါတွင် ထပ်တူကျသည့်အမိန့်ကို ပရင့်ထုတ်သည်။

နေ့စဉ် `UI Kit upstream watch` အလုပ်အသွားအလာ (`.github/workflows/ui-kit-upstream-watch.yml`) သည် တူညီသောစစ်ဆေးမှုကို လုပ်ဆောင်သည်။ ပင်နံပါတ်နောက်တွင်၊ `scripts/ci/ui-kit-sync-pr.sh` အမြင့်ဆုံး `release/vX.Y.Z` အကိုင်းအခက်နှင့် အဖွင့်တစ်ပြိုင်တည်းဖြစ်သော PR တစ်ခုကို လှိမ့်လိုက်သောကိုင်းဆက် `chore/ui-kit-sync-latest` တွင် ထားရှိထားသည်။ ၎င်းသည် ဘယ်တော့မှ ပေါင်းစပ်မည်မဟုတ်ပါ- အစုံလိုက်ထုတ်လွှတ်မှုတိုင်းသည် local VPS တွင် အမြင်အာရုံစစ်ဆေးမှု လိုအပ်နေသေးသည်။ အသစ်ထွက်ပြီး အခြားနည်းဖြင့် အထီးကျန်နေချိန်တွင် ဌာနခွဲကို ပြန်လည်တည်ဆောက်ပါသည်။ လက်ဖြင့်တွန်းထားသော ကတိကဝတ်များပါသော အဖွင့် PR ထပ်မရေးဘဲ၊ ပြုပြင်ထိန်းသိမ်းသူမှ ပိတ်ထားသော ပေါင်းစပ်မထားသော ဗားရှင်းအတွက် PR အသစ်ထွက်သည့်အချိန်အထိ ပိတ်ထားသည်။

PR ကိုဖွင့်၍မရသောအခါ (ပစ်မှတ်ထုတ်လွှတ်မှုကို အေးခဲသွားသည်၊ PR လက်ဖြင့်တွန်းထုတ်သည်၊ PR ပိတ်ထားသည်၊ သို့မဟုတ် PR တိုကင်ကိုမသတ်မှတ်ထားပါ) အလုပ်အသွားအလာသည် အဘယ်ကြောင့်ဆိုသော် ခြေရာခံခြင်းပြဿနာကို ဖွင့်ထားစေသည်။

အလုပ်အသွားအလာတွင် လျှို့ဝှက်ချက်နှစ်ခုကို အသုံးပြုသည်-

- `secrets.UI_KIT_READ_TOKEN`: သီးသန့် upstream repo အတွက် ဖတ်ရန်-သီးသန့် တိုကင်။ အလုပ်အသွားအလာကို အထက်စီးကြောင်းကို မဖတ်နိုင်သောအခါ (တိုကင်မရှိ၊ အလုပ်မလုပ်တော့သည့် သို့မဟုတ် GitHub မရနိုင်ပါ) run သည် အစိမ်းရောင်ရှိနေသော်လည်း သတိပေးချက်တစ်ခုရေးသားပြီး သီးခြားပြဿနာတစ်ခုကို ဖွင့်ထားကာ ၎င်းသည် နောက်မှပြေးပြီးသည်နှင့် ၎င်းကိုယ်တိုင်ပိတ်သွားပါက အထက်သို့ပြန်ဖတ်နိုင်သည်။
- `secrets.UI_KIT_SYNC_PR_TOKEN`: Contents and Pull Requests ဖြင့် ဝင်ရောက်ရေးသားခွင့် တောင်းဆိုချက်များပါရှိသော ဤသိုလှောင်ခန်းရှိ အနုစိတ်သော တိုကင်တစ်ခု။ မူရင်း `GITHUB_TOKEN` ဤနေရာတွင် PRs ဖန်တီး၍မရပါ၊ ၎င်းကိုဖွင့်ထားသော PR CI အစပျိုးမည်မဟုတ်ပါ။ ဤသင်္ကေတမပါဘဲ အလုပ်အသွားအလာသည် ဌာနခွဲကိုသာ တွန်းပို့သည်။

`scripts/dev/sync-ui-kit.sh <commit|latest> [clone]` `src/` commit တွင် (`latest` = the newest `v*` tag) ကို `packages/ui-kit/src` သို့ ကူးယူသည်၊ ခွင့်ပြုထားသော အသွင်ပြောင်းမှုကို အသုံးပြုသည် (၎င်းသည် `.js` ၏ နောက်ဆက်တွဲကို ဆက်စပ်တင်သွင်းမှုများမှ ရုပ်သိမ်းသွားသည်) နှင့် `packages/ui-kit/package.json` နှင့် `package-lock.json` တွင် workspace ဗားရှင်းကို upstream တစ်ခုသို့ သတ်မှတ်သည်။ ထို့နောက်- `git diff packages/ui-kit` ပြန်လည်သုံးသပ်ပါ၊ ပံ့ပိုးပေးသူများ၊ ဆက်တင်များ၊ ပေါင်းစပ်မှုများ၊ အသုံးပြုမှုနှင့် အဆုံးမှတ်ကို အပြင်အဆင်နှစ်ခုလုံးတွင် ပြုလုပ်ပါ၊ `npm run check:ui-kit-snapshot` နှင့် `npm run test:vitest:ui` ကိုဖွင့်ပါ၊ နှင့် PR ကို upstream changelog ဖြင့်ဖွင့်ပါ။

- **အရွယ်အစားကန့်သတ်ချက်။** ဖိုင်တစ်ဖိုင်လျှင် 200 KB အောက်ရှိရမည် (staleness test တစ်ခုစီက စစ်ဆေးသည်)။ README
  ပုံတစ်ပုံအတွက် 500 KB သည် အမြင့်ဆုံးသတ်မှတ်ချက်ဖြစ်သည် (SVG studio validator ၏ စည်းမျဉ်း)။
- **စာသားကို မပြောင်းလဲပါနှင့်၊ အရေအတွက်များကို gate မှ ရယူပါ။** Rebrand သည် type နှင့် palette ကိုသာ ပြောင်းလဲခဲ့ပြီး စာလုံးများကို မပြောင်းလဲခဲ့ပါ။ Generator တစ်ခုစီတွင်
  ၎င်း၏ဒိုင်ယာဂရမ်စာသားကို `*_COPY` constant တစ်ခုအဖြစ် ထည့်သွင်းထားသည် (သို့မဟုတ် လက်ရှိ catalog မှ တည်ဆောက်သည်)။ ၎င်းသည်
  ရေးဆွဲထားသော စာသားလည်းဖြစ်သလို outlining အဆင့်၏ input လည်းဖြစ်သည်။ Canonical ကိန်းဂဏန်းများကို `<text>` node များတွင် ဆက်လက်ထားရှိသည် (outline ပြောင်းပြီးနောက်
  `fill-opacity:0` ဖြင့် မမြင်ရတော့ပါ)၊ ၎င်းတို့ကို `check:docs-counts`
  (`scripts/check/check-docs-counts-sync.mjs`) က ဖတ်သည်။ ထို gate က ဖတ်ရှုသော ဒိုင်ယာဂရမ်များ၏ staleness test များသည်လည်း
  generate လုပ်ထားသောဖိုင်ပေါ်တွင် ၎င်း၏ validator များကို run သဖြင့် ကိန်းဂဏန်းတစ်ခုက code နှင့် ကွဲလွဲသွားပါက test မအောင်မြင်ပါ — generator ထဲရှိ
  နံပါတ်ကို မပြင်ဘဲ gate က ဖတ်သည့် source ကိုသာ ပြင်ပါ။
