## ဂိတ်စာရင်းနှင့် အကောင်အထည်ဖော်မှု ပရိုဖိုင်များ

### ကိုယ်စားလှယ်လောင်း ဝင်ခွင့်

CI နှင့် Quality Gates အလုပ်အသွားအလာတစ်ခုစီသည် တည်ငြိမ်သောစီရင်ချက်တစ်ခုစီကို ထုတ်လွှတ်သည်- `Gate / CI` နှင့် `Gate / Quality`. ၎င်းတို့၏ ဗားရှင်းဖြင့် ဝင်ခွင့်မူဝါဒသည် လိုအပ်သည့် သို့မဟုတ် အကြံပေးချက်အဖြစ် အထက်ပိုင်းအလုပ်တိုင်းကို ရေတွက်ပါသည်။ သက်ဆိုင်ရာ လိုအပ်သော အလုပ်တစ်ခု အောင်မြင်ရပါမည်- ပျောက်ဆုံးနေသော၊ ပယ်ဖျက်လိုက်၊ ကျော်သွားသည်၊ ဆိုင်းငံ့ထားပြီး မသိသောရလဒ်များကို PASS သတ်မှတ်၍မရပါ။ မှန်ကန်သော docs-only သို့မဟုတ် catalog-only အမျိုးအစားခွဲခြင်းသည် ကုဒ်လမ်းကြောင်းကို အသုံးချ၍မရပေ။ PR မူကြမ်းသည် လက်ခံထားသော ကိုယ်စားလှယ်မဟုတ်ပါ။ `hotfix` အညွှန်းသည် သက်သေအထောက်အထား မလွတ်ပါ။

အလုပ်အသွားအလာနှစ်ခုလုံးသည် PRs main/release အကိုင်းအခက်များအဖြစ် ဖုံးလွှမ်းကာ၊ `main` သို့ တွန်းပို့သည်၊ လူကိုယ်တိုင် ပေးပို့ခြင်းနှင့် အုပ်စုလိုက်ဖြစ်ရပ်များကို ပေါင်းစည်းသည်။ ရွေးချယ်မှု အပြည့်အစုံကို တွန်းပို့ခြင်း၊ ပေးပို့ခြင်းနှင့် ပေါင်းစည်းခြင်းတို့ကို လုပ်ဆောင်ပါ။ `release/**` သို့ တွန်းပို့ခြင်းများ မစတင် → ( PR )`docs/ops/RUNNER_BOX.md` Forks နှင့် အဖွဲ့များ ပေါင်းစည်းထားသော အလုပ်များအတွက် လက်ခံထားသော အပြေးသမားများကို အသုံးပြုသည်၊ ဖြန့်ချိခြင်းမပြုမီ လုံလောက်သော လက်ခံနိုင်သော စွမ်းရည်ကို စစ်ဆေးရပါမည်။

သာမန် PR သည် အမြန်ရွေးချယ်မှုကို လုပ်ဆောင်သည်။ ဝင်ခွင့်မူဝါဒ၏ `full-code` နှင့် `full-code-e2e` လမ်းကြောများ (E2E၊ ပေါင်းစပ်မှု၊ ပက်ကေ့ဂျ်အနုပညာ၊ Electron မီးခိုး၊ Bun SQLite၊ ဂေဟစနစ်နှင့် ပရိုတိုကောဖောက်သည်များ) သည် ပေါင်းစည်းထားသော တန်းစီမူကြမ်း သို့မဟုတ် အပြည့်အဝလည်ပတ်မှုတွင်သာ လုပ်ဆောင်သည်- `gh workflow run ci.yml --ref <branch>`.

JSON ပြေစာတစ်ခုစီသည် check-out SHA၊ workflow run နှင့် ကြိုးစားမှုကို ခွဲခြားသတ်မှတ်သည်။ CLI သည် checkout/event SHA မကိုက်ညီမှုကို ငြင်းပယ်သည်။ အလုပ်အသွားအလာ စမ်းသပ်မှုများသည် စီရင်ချက်ချသည့်အလုပ်၏ `needs` စာရင်းနှင့် မူဝါဒအဖွဲ့ဝင်ခြင်းကို ချိတ်ဆက်ထားသောကြောင့် လမ်းအသစ် သို့မဟုတ် ဖယ်ရှားထားသော လမ်းကြောသည် တိတ်တဆိတ် ပျောက်ကွယ်သွားမည်မဟုတ်ပေ။ ပြေစာများသည် ထုတ်ဝေခြင်း၊ ဖြန့်ကျက်ခြင်း သို့မဟုတ် လက်ရှိအကြံပေးစကင်နာတစ်ခု၏ အတွင်းပိုင်းများကို ထုတ်ဝေခြင်းမဟုတ်ဘဲ ၎င်းတို့၏လုပ်ငန်းအသွားအလာကို အကျုံးဝင်ပါသည်။ ဌာနခွဲစည်းမျဥ်းစည်းကမ်းများတွင် စစ်ဆေးမှုအမည်နှစ်ခုလုံးကို အသက်သွင်းခြင်းသည် သီးခြားစီမံခန့်ခွဲရေးဆိုင်ရာ ပြောင်းလဲမှုတစ်ခုဖြစ်သည်။ ဤအလုပ်များကို ပေါင်းထည့်ခြင်းသည် အကိုင်းအခက်ကို မကာကွယ်နိုင်ပါ။

### တန်းစီခြင်းကို ပေါင်းစည်းပါ။

`queue` အညွှန်းသည် PR တစ်ခုကို ပေါင်းစည်းထားသော တန်းစီ (`.mergify.yml`) သို့ ပို့ပေးသည်။ Mergify သည် `mergify/merge-queue/` အကိုင်းအခက်တစ်ခုပေါ်တွင် PR မူကြမ်းကိုဖွင့်သည်၊ CI ထိုနေရာတွင် ရွေးချယ်မှုအပြည့်အစုံကို လုပ်ဆောင်ပြီး `Gate / CI`၊ `Gate / Quality` နှင့် `Merge integrity (changelog + generated skills)` ကျော်သွားသောအခါ မူရင်း PR ပေါင်းစည်းသွားသည်။

Mergify သည် မူကြမ်း၏ဖော်ပြချက်တွင် ၎င်း၏တန်းစီဇယားအနှစ်ချုပ်ကို ရေးသားပြီး အခြားအက်ပ်များက ၎င်းကို တည်းဖြတ်နိုင်သည်။ ထိုကဲ့သို့ မူကြမ်းတွင် `pull_request` `edited` ဖြစ်ရပ်သည် ၎င်း၏ကိုယ်ပိုင်ငွေကြေးအုပ်စု (`-queue-edit-<run_id>`) ကို ယူသောကြောင့် ၎င်းသည် မူကြမ်း၏ တကယ့်လည်ပတ်မှုကို မပယ်ဖျက်နိုင်ဘဲ ၎င်းသည် ဂိတ်နှင့် မက်ထရစ်ကို ကျော်သွားပါသည်။ `Merge integrity` သာ လည်ပတ်နေသေးသည်။ Mergify သည် မအောင်မြင်သောစစ်ဆေးချက်တစ်ခုအဖြစ် ကျော်သွားသော `Gate / CI` ဖတ်ပြီး PR စီစစ်ပေးသောကြောင့် skiped gate အလုပ်တွင် မတူညီသောစစ်ဆေးမှုအမည်တစ်ခုပါရှိသည်။

ခေတ္တရပ်ဆိုင်းပြီးနောက်၊ တွန်းအားသည် PR ကို အမြဲတမ်း queue လုပ်မည်မဟုတ်ပါ။ `@mergifyio queue` ကို မှတ်ချက်ပေးလိုက်ပါ။

### လက်ခံမှုလျော့ပါးရေးတွင် အထောက်အထားများ သိမ်းဆည်းထားသည်။

`scripts/quality/validate-release-acceptance.mjs` ထောက်ပံ့ပေးထားသော အစီအစဉ်နှင့် ၎င်း၏ဖော်ပြချက်များကို လျှော့ချပေးသည်။ ပြီးပြည့်စုံသော ပိုက်လိုင်းကို အကျုံးဝင်စေမည့် အစီအစဥ်ကို မသတ်မှတ်ထားပေ။ ၎င်းအစီအစဥ်သည် `VERIFIED` ဖြစ်သည့်အခါ၌ပင် ၎င်း၏အစီရင်ခံစာများသည် `releaseAcceptance: false` အတိအလင်းသတ်မှတ်ထားသည်။ `release-acceptance.yml` အလုပ်အသွားအလာသည် အစစ်အမှန်တည်ဆောက်မှု၊ ပက်ကေ့ချ်၊ boot သို့မဟုတ် ပရိုမိုးရှင်းဖြတ်ပိုင်းများကို မဟုတ်ဘဲ အရိပ်တွဲများကို အသုံးပြုနေဆဲဖြစ်သည်။

CLI သည် သိမ်းဆည်းထားသော အထောက်အထားများကို စစ်ဆေးရန် `--evidence-root` လိုအပ်သည်။ ဖိုင်များကို `<evidence-root>/<artifact_id>/<member>` အဖြစ် ဖြေရှင်းပြီး SHA-256 အဖြစ် hash လုပ်ထားသည်။ အထောက်အထားမရှိဘဲ PASS မှတ်တမ်းတစ်ခု၊ ပျောက်ဆုံးနေသော သို့မဟုတ် ပြောင်းလဲထားသော ဖိုင်၊ မလုံခြုံသောလမ်းကြောင်း သို့မဟုတ် symlink သည် အတည်ပြုခြင်းကို တားဆီးသည်။ ပျောက်ဆုံးနေသောဖိုင်များသည် အောင်မြင်သောမှတ်တမ်းအလွတ်များနှင့် ညီမျှသည်မဟုတ်ပါ။ လက်ရှိ SHA/run/attempt စစ်ဆေးမှုများသည် အမှီအခိုကင်းဆဲဖြစ်သည်- ကိုက်ညီသော bytes သည် ဟောင်းနွမ်းနေသောပြေစာအား ကယ်တင်နိုင်မည်မဟုတ်ပေ။ ဖိုင်ခိုင်မာမှုသည် စစ်မှန်သောစစ်မှန်မှု သို့မဟုတ် ပစ္စည်းပရိုမိုးရှင်း၏ သက်သေမဟုတ်ပါ။

### Static scan စာရင်း

ဗားရှင်းသတ်မှတ်ထားသော npm-alias စာရင်းနှင့် static-scan အဖွဲ့ဝင်မှုသည် `config/quality/gate-manifest.json` တွင်နေထိုင်သည်။ script အမည်များနှင့် `package.json` နှင့် ပတ်သက်သည့် တိကျသော command များကို အတည်ပြုရန် `npm run check:gate-manifest` ကို ဖွင့်ပါ။ ထပ်တိုးမှုများ၊ ဖယ်ရှားခြင်းနှင့် အမိန့်ပေးထားသော ဒရုန်းများသည် ဒေသတွင်းချိတ်နှင့် CI ရှိ ပြောင်းလဲမှုအမျိုးအစားခွဲခြားခြင်းအလုပ်များ နှစ်ခုစလုံးတွင် မအောင်မြင်ပါ။ နာမည်တူတစ်ခုသည် အလုပ်အသွားအလာအလုပ်၊ မက်ထရစ်ဥပမာ သို့မဟုတ် စမ်းသပ်မှုကိစ္စမဟုတ်ပါ- ဤအရေအတွက်များကို အပြန်အလှန်ဖလှယ်နိုင်သောအဖြစ် မဖော်ပြရပါ။

၎င်းတို့ကို လုပ်ဆောင်ခြင်းမရှိဘဲ ရွေးချယ်ထားသော နာမည်တူများကို စစ်ဆေးရန် `npm run quality:scan -- --list` သို့မဟုတ် `npm run quality:scan:fast -- --list` အသုံးပြုပါ။ အပြေးသမားသည် npm entrypoint ကို ခေါ်ဆိုသည်၊ ထို့ကြောင့် ၎င်း၏ runtime (configured လုပ်ထားသော Bun အပါအဝင်) ကို ထိန်းသိမ်းထားသည်။ မန်နီးဖက်စ်သည် သီးခြားခေါ်ဆိုထားသည့်အတိုင်း အဆိုပါပရိုဖိုင်များအပြင်ဘက်တွင် နာမည်တူများကို မှတ်တမ်းတင်ပြီး ပြုပြင်ထိန်းသိမ်းမှုအမိန့်များကို ဖတ်သာစကင်န်ပရိုဖိုင်များတွင် တားမြစ်ထားသည်။

ဤပရိုဖိုင်များသည် static scan ကိုသာ အကျုံးဝင်ပါသည်။ ၎င်းတို့သည် ထုတ်ကုန်စစ်ဆေးမှုများ၊ အကျုံးဝင်မှု၊ ထုပ်ပိုးမှု၊ ပြင်ပစစ်ဆေးမှုများ သို့မဟုတ် ကိုယ်စားလှယ်တစ်ဦး၏ အပြည့်အဝလက်ခံမှုကို အသိအမှတ်ပြုခြင်းမပြုပါ။ Workflow ဝင်ခွင့်သည် ချိတ်ဆက်ထားသော `config/quality/admission-policy.json` နှင့် `scripts/quality/admission-verdict.mjs` ကို အသုံးပြုသည်။ ထုတ်ဝေသူ-လေ့လာသူ ပရိုဖိုင်များသည် သီးခြားကျန်ရှိနေသည်။ ၎င်းတို့၏ သက်ဆိုင်ရာ ချက်လက်မှတ်များနှင့် ပြေစာများကို လွတ်လပ်စွာ စစ်ဆေးပါ။ လေ့လာသူ၏ static command အပြည့်အစုံကို `audit:deps`၊ mutation-test ရွေးချယ်မှုနှင့် ဘာသာပြန်စစ်ဆေးမှုများအပါအဝင် `config/quality/release-green-static-profile.json` တွင် ကြေငြာထားသည်။ loader သည် package.json နှင့် စံပြထားသော CI/Quality ကြေငြာချက်များကို ဆန့်ကျင်သည့် npm ညွှန်ကြားချက်များကို တရားဝင်စေပါသည်။ အကြောင်းပြချက်များအဖြစ် shell တိုကင်များကို လုပ်ဆောင်မည့်အစား drift ကို ငြင်းပယ်သည်။ လိုအပ်သော စကင်နာ SKIP/INCOMPLETE အထွက်သည် PASS သတ်မှတ်၍ မရပါ။ ပရိုဖိုင်သည် ၎င်း၏ ပြင်ပ ချန်လှပ်ခြင်းများကို မှတ်တမ်းတင်ပြီး လက်ခံထားသော လွှမ်းခြုံမှု၊ စမ်းသပ်မှု မက်ထရစ်များ၊ ပက်ကေ့ခ်ျ သို့မဟုတ် အသုံးချမှု အထောက်အထားများကို အစားထိုးမထားပါ။ အောက်ဖော်ပြပါ စကားပြေစာရင်းသည် ဂိတ်တစ်ခု အမှန်တကယ်ထွက်ကြောင်း အထောက်အထားမဟုတ်ဘဲ ကိုးကားချက်ဖြစ်သည်။

Script များသည် `scripts/check/` (မူဝါဒတံခါးများ) နှင့် `scripts/quality/` (ratchet engine) အောက်တွင် နေထိုင်ပါသည်။ CI အမှန်တရား၏အရင်းအမြစ်သည် `.github/workflows/ci.yml` ဖြစ်သည်။

### PR အမြန်လမ်း (`quality.yml`) ကို လွှတ်ပေးပါ

`.github/workflows/quality.yml` main/release PRs တွင် CI ဖြည့်စွက်သည်၊ `main` သို့တွန်းသည်၊ ပေးပို့ပြီးအုပ်စုများကိုပေါင်းစည်းသည်။ PRs လမ်းကြောင်းကို စစ်ထုတ်သည့် အမြန်စစ်ဆေးမှုများကို အသုံးပြုပါ။ အပြီးအပိုင်ပိတ်ထားသော ထပ်နေသောတည်ဆောက်မှုကို ဖယ်ရှားခဲ့သည်။ အစစ်အမှန် build/package/boot စစ်ဆေးမှုများသည် CI တွင်ရှိနေပါသည်။ ယူနစ်အစုံနှင့် vitest သည် CI (`Unit Tests (N/8)` နှင့် `Vitest`) တွင်သာလည်ပတ်သည်။

#### ပေါက်ဖော် စာမေးပွဲတွေ မေ့သွားပြီ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ၏ အကြံပေးအဆင့်အဖြစ် လုပ်ဆောင်ပြီး စမ်းသပ်သက်ရောက်မှုမြေပုံနောက်ကွယ်ရှိ တင်သွင်းမှုဖြေရှင်းချက်ကို ပြန်လည်အသုံးပြုသည်။ ပြောင်းလဲထားသော ထုတ်လုပ်မှု module တစ်ခုစီအတွက်၊ လျှောက်ထားသူ၏စမ်းသပ်မှုသည် ဆွဲငင်တောင်းဆိုချက်ကွဲပြားမှုမှ ပျက်ပြယ်သွားသောအခါတွင် ၎င်းသည် တိကျသော `changed module/symbol -> static consumer -> candidate sibling test` ကွင်းဆက်များကို အစီရင်ခံသည်။ Markdown အနှစ်ချုပ်နှင့် JSON ရလဒ်အား ပိတ်ဆို့ခြင်းမပြုလုပ်မီ ချိန်ညှိခြင်းအတွက် `forgotten-sibling-tests` အလုပ်အသွားအလာကို ဆက်လက်ထိန်းသိမ်းထားသည်။

စည်ပိုင်းပြန်လည်တင်ပို့မှုနှင့် ရွေ့လျားတင်သွင်းမှုများသည် ကြည်လင်ပြတ်သားသောရောဂါရှာဖွေခြင်းသာဖြစ်သည်။ ပိတ်ဆို့ရှာဖွေမှုကို ဘယ်တော့မှ မဖန်တီးကြဘူး။ သုံးသပ်ထားသောခြွင်းချက်များသည် `config/quality/forgotten-sibling-allowlist.json` တွင်နေထိုင်သည်။ ဝင်ရောက်မှုတစ်ခုစီသည် စားသုံးသူနှင့် ကိုယ်စားလှယ်လောင်း စမ်းသပ်မှုအား အမည်ပေး၍ တိကျသော ကျိုးကြောင်းဆီလျော်မှုတစ်ခုပေးကာ GitHub ပြဿနာကို လင့်ခ် သို့မဟုတ် တောင်းဆိုချက် ဆွဲထုတ်ရပါမည်။ ပုံမမှန်သော ထည့်သွင်းမှုများ မအောင်မြင်ပါ။ ခြွင်းချက်များသည် ဖျက်လိုက်သော ကိုယ်စားလှယ်လောင်း စမ်းသပ်မှု သို့မဟုတ် `.skip`/`.todo` ပေါင်းထည့်သည့် ကွဲပြားမှုကို ဖိနှိပ်၍ မရပါ။ အခိုင်အမာပြောဆိုမှု အားနည်းခြင်းနှင့် အခြားမျက်နှာဖုံးစွပ်ခြင်းကို သီးခြား `check:test-masking` ဂိတ်က ပိုင်ဆိုင်သည်။

#### စာရိုက်စစ်ဆေးသည့် ပရိုဂရမ်နှစ်ခုသည် ကွဲပြားစွာ အဖြေပေးသည်။

`typecheck:core` နှင့် `check:build-typecheck` မတူညီသောရွေးချယ်မှုများအောက်တွင် မတူညီသောပရိုဂရမ်များကို စုစည်းထားပြီး တူညီသောဖိုင်သည် တစ်ခုနှင့်တစ်ခုတွင် သန့်ရှင်းနိုင်ပြီး အခြားတစ်ခုတွင် အမှားအယွင်းများနှင့် ပြည့်နေပါသည်။

`tsconfig.build.json` `"strict": false` သတ်မှတ်ပေးသည်၊ ထို့ကြောင့် `noImplicitAny` ပိတ်ထားသည်။ core config သည် တင်းကျပ်သောရွေးချယ်မှုများဖြင့် စုစည်းထားသော 27-ဖိုင်ခွင့်ပြုစာရင်းကိုစုစည်းပြီး entry ၏တင်သွင်းမှုဂရပ်တစ်ခုစီကိုလိုက်နာသောကြောင့် build program တွင်ဘယ်တော့မှမပေါ်သောဖိုင်များကိုထိုနေရာတွင်စစ်ဆေးနေဆဲဖြစ်သည်။

ဖိုင်ကို ရိုက်ထည့်ခြင်း ရှိ၊ မရှိ ဆုံးဖြတ်သည့်အခါ အကျိုးဆက်သည် အရေးကြီးသည်-** `check:build-typecheck` အောက်တွင် သုညရောဂါရှာဖွေခြင်းသည် သုညဟု မဆိုလိုပါ။** . ဖိုင် ၂၆ ဖိုင်မှ `@ts-nocheck` ဖယ်ထုတ်ခြင်းတွင် ၎င်းတို့ထဲမှ ၂၃ ခုကို build ပရိုဂရမ်တွင် ရှင်းလင်းပြသခဲ့သည်။ အဲဒီအထဲက ဆယ့်ခြောက်ခုဟာ သွယ်ဝိုက်သောနည်းနဲ့ အမှားအယွင်းပေါင်း 120 လောက် ပေါ်ထွက်နေပါတယ်။ ဖိုင်ကို clean မခေါ်ခင် နှစ်ခုလုံးကို စစ်ကြည့်ပါ။

#### ဘာသာပြန်မှန်များသည် ဆင်းသက်လာသောဖိုင်များ (PR mode နှင့် release mode)

PR လုပ်ဆောင်ချက်သည် အင်္ဂလိပ်ရင်းမြစ်များကိုသာ တည်းဖြတ်သည်။ `docs/i18n/<locale>/**` mirrors ( `llm.txt` မိတ္တူ 66 ခုနှင့် ဘာသာပြန်ထားသော `CHANGELOG.md` ဖိုင်များ အပါအဝင်) နှင့် `.i18n-state.json` ဘာသာပြန်လှိုင်း (`docs/i18n-*` / `chore/i18n-*` အကိုင်းအခက်များ၊ စီစဉ်ထားသော `i18n-mirror-refresh.yml`) နှင့် ထုတ်ဝေမှု (`npm run release:sync-changelog-i18n`) တို့ဖြင့် တစ်လှမ်းချင်း ပြန်လည်ရေးသားထားပါသည်။ ထို့ကြောင့် မှန်တံခါးများသည် `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`၊ ထို့နောက် `OMNIROUTE_GATE_MODE`၊ ထို့နောက် လုပ်ဆောင်ချက်များ ဖြစ်ရပ် ၊ ဒေသန္တရ လည်ပတ်မှုမှာ `release`) ဖြင့် ဖြေရှင်းသော မုဒ်နှစ်ခုဖြင့် လုပ်ဆောင်သည်။

- `check:docs-sync` — ထုတ်ဝေမှုမုဒ်သည် စစ်ဆေးမှုတိုင်းကို လုပ်ဆောင်သည်။ PR မုဒ်သည် package.json/OpenAPI ဗားရှင်း၊ အမြစ် CHANGELOG ခေါင်းစဉ်များနှင့် အစားထိုးထားသော-docs အစောင့်ကို သိမ်းထားပြီး `llm.txt` မှန်ချပ်များနှင့် ဘာသာပြန်ထားသော CHANGELOG အပိုင်းများကို — အတွက် `SKIP reason=pr-mode` ကြေးမုံကိုမရေးပါက PR ကြေးမုံမရေးပါက- `docs/i18n/**` မိသားစု၏ စာရေးဆရာတစ်ဦးအဖြစ် ကြေငြာထားသည့် ဌာနခွဲတစ်ခုသည် `config/quality/derived-paths/*.json` တွင် စစ်ဆေးမှု၊ အပြောင်းအလဲများကို တင်းကြပ်စွာဖြေရှင်းသောအခါတွင် ကိုယ်ပိုင်၊ တင်းကြပ်စွာစစ်ဆေးသော `docs/i18n/<locale>/llm.txt` သို့မဟုတ် `CHANGELOG.md` အလုပ်လုပ်သည်။ diff base သည် depth-1 checkout ( `docs-sync-strict` အလုပ်) တွင် မဖြေရှင်းနိုင်သောကြောင့် PR mode သည် အခြေခံမလိုအပ်သည့် check တစ်ခုကိုလည်း run သည်- `llm.txt` mirror တစ်ခုစီရှိရမည်၊ ၎င်း၏ `---` ခြားနားခြင်းကို သိမ်းဆည်းထားပြီး root body သို့မဟုတ် mirror အများစုပါဝင်သည့် body ကို သယ်ဆောင်သွားမည်ဖြစ်သည်။ ရွေ့သွားသော အခြေသည် မှန်များအားလုံးကို အညီအမျှ ဆိတ်သုဉ်းစေပြီး ဖြတ်သန်းသွားစေသည်။ မှန်တစ်ချပ်ကို လက်ဖြင့်တည်းဖြတ်ရန် အဆင်မပြေပါ။ ဘာသာပြန်ထားသော `CHANGELOG.md` ဖိုင်များတွင် depth-1 PR ငွေရှင်းခြင်းတွင် ထိုသို့သော စစ်ဆေးမှုမရှိပါ။
- pre-commit hook သည် `check-docs-sync.mjs --mode=pr` run သည် : commit သည် ၎င်းလုပ်ဆောင်သည့်အရာကို ဆုံးဖြတ်သည်။ အလံမပါဘဲ local run သည် release mode ဖြစ်ပြီး၊ root `llm.txt` ကို တည်းဖြတ်သည့် ပေါင်းစည်းထားသော PR တစ်ခုသည် wave ပြေးသည်အထိ ထို base ပေါ်တွင် commit လုပ်ခြင်းကို ပိတ်ဆို့သွားမည်ဖြစ်သည်။ တူညီသောစည်းမျဉ်းသည် Husky ချိတ်တစ်ခုလည်ပတ်သည့်မည်သည့်မုဒ်-အသိတံခါးအတွက်ဖြစ်သည်- ချိတ်သည် `--mode=pr` ကျော်သွားကာ တင်းကျပ်သောစီရင်ချက်သည် လွှတ်-မုဒ်လည်ပတ်မှုနှင့်အတူရှိနေသည် (လွှတ်ပေးရန် PR၊ `main`၊ ရိုးရိုးဒေသတွင်းပြေးခြင်း)။
- Mirror-content ယူနစ်စမ်းသပ်မှုများ (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) — release mode သည် နေရာတိုင်းကို အတည်ပြုသည်။ PR မုဒ်သည် `.i18n-state.json` (ဖိုင်တစ်ခုလုံး ဟက်ရှ် သို့မဟုတ် အပိုင်း၏ စမ်းသပ်မှုပင်များ အပိုင်း၏ မှတ်သားထားသော အပိုင်း hash) အရ အင်္ဂလိပ်ရင်းမြစ်နှင့် လက်ရှိရှိသော မှန်များကိုသာ အခိုင်အမာ အတည်ပြုပြီး ဟောင်းနွမ်းနေသော အရာများကို အကြောင်းပြချက်ဖြင့် ကျော်သွားသည်။ `target_hash` သက်သေစစ်ဆေးမှုများသည် မုဒ်နှစ်ခုစလုံးတွင် နေရာတိုင်းအတွက် လုပ်ဆောင်သည်။ လတ်ဆတ်မှုသည် `## ` ကဏ္ဍအလိုက်၊ ယူနစ် `run-translation.mjs` hashes; ရှည်လျားသော အပိုင်း (ဤဖိုင်၏ ဂိတ်စာရင်းသည် ၎င်း၏ ထက်ဝက်ခန့်ဖြစ်သည်) ဆိုလိုသည်မှာ ၎င်းတွင် တည်းဖြတ်မှုတိုင်းသည် ထိုကြေးမုံများကို ပျက်သွားစေပြီး ၎င်းတို့၏ PR-မုဒ် အခိုင်အမာ ပြောဆိုမှုများသည် နောက်လှိုင်းအထိ ကျော်သွားမည်ဖြစ်သည်။ အင်္ဂလိပ်ရင်းမြစ်တွင် မပါဝင်တော့သော ဖိုင်တွဲတစ်ခုလုံးကို နှိုင်းယှဉ်ခြင်းသို့ ပြန်ရောက်သွားပါသည်။
- `i18n translation drift` — အကြံပေးချက် PRs၊ တွန်းအား ၊ ညစဉ်ညတိုင်း နှင့် ထုတ်လွှတ်မှု ဖြတ်တောက်ခြင်း ၊ ထို့ကြောင့် ဟောင်းနွမ်းနေသော မှန်တစ်ချပ်ကို လွှတ်တင်ခြင်းတွင် ပို့ဆောင်၍ မရပါ။

`scripts/i18n/sync-llm-mirrors.mjs` ( `syncLlmMirrors()`၊ `--dry-run` ဖြင့်လည်း တင်ပို့ထားသည်) `llm.txt` မှန်များကို ပြန်ရေးသည်။ ထုတ်ဝေမှု ပြန်လည်ဆန်းသစ်ခြင်း၊ ဘာသာပြန်လှိုင်းနှင့် စီစဉ်ထားသည့် `i18n-mirror-refresh.yml` ၎င်းကို လုပ်ဆောင်သည် (ပြန်လည်ဆန်းသစ်ခြင်းသည် ၎င်းတို့ကို စာရင်းမသွင်းထားသောကြောင့် ၎င်းတို့ကို ရပ်တန့်နေသော `llm.txt` မှန်များကို ခြောက်သွေ့သောအပြေးဖြင့် ထောက်လှမ်းသိရှိနိုင်ပြီး `check:docs-all` မတိုင်မီ ၎င်းတို့ကို ထပ်တူကျစေသည်)။

### ရရှိသောတန်ဖိုးများ- `pr` နှင့် `release` ဂိတ်မုဒ်များ

PR အင်္ဂါရပ်တစ်ခုသည် ၎င်း၏အခြေခံအခြေအနေအပေါ် မူတည်သည်- ဝန်ဆောင်မှုပေးသူ၊ ရွှေ့ပြောင်းနေထိုင်မှု၊ MCP-tool နှင့် ဗျူဟာအရေအတွက်၊ README SVG နံပါတ်များ၊ အချက်အလက်လျှပ်တစ်ပြက်ရိုက်ချက်အပေါ် မူတည်ပါသည်။ အဆင့်တစ်ဆင့်သည် ၎င်းတို့အားလုံးကို `npm run release:refresh-derived`၊ ထုတ်ဝေမှုမှ လုပ်ဆောင်ပြီး ညစဉ်ရရှိသည့်-ပြန်လည်ဆန်းသစ်သည့် PR ဖြင့် ပြန်လည်တွက်ချက်သည်။ ဒါကြောင့်** ထုတ်ဝေမှုများကြားတွင် အခြေခံသည် ဒီဇိုင်းဖြင့် တိုက်ရိုက်ကုဒ်နောက်တွင် ရှိနေသည်။** နှင့် သစ်ပင်ကို တိုက်ရိုက်ကုဒ်နှင့် နှိုင်းယှဉ်သည့် ဂိတ်ပေါက် သို့မဟုတ် စမ်းသပ်မှုတစ်ခုသည် မောင်နှမတစ်ဦးမှ ပံ့ပိုးပေးသူတစ်ဦးကို ထည့်ပြီးနောက် PR တိုင်းတွင် အနီရောင်ဖြစ်လိမ့်မည်။ ထို့ကြောင့် ဆင်းသက်လာသောတန်ဖိုးများကို ဆုံးဖြတ်သည့် ဂိတ်များသည် `scripts/check/lib/gateMode.mjs` (ပထမပွဲအနိုင်ရသည်) ဖြင့် ဖြေရှင်းသော မုဒ်နှစ်ခုအနက်တစ်ခုတွင် အလုပ်လုပ်သည်။

1. command line တွင်`--mode=pr|release` ;
2. `OMNIROUTE_GATE_MODE` ပတ်ဝန်းကျင် ပြောင်းလဲနိုင်သော (`pr` သို့မဟုတ် `release`);
3. GitHub လုပ်ဆောင်ချက်များ ဖြစ်ရပ်မှ အလိုအလျောက်ဖြစ်သည်- `pull_request` ဦးခေါင်းမဟုတ်သည့် `release/v*`၊ a `merge_group` သို့မဟုတ် `omni-queue/**` → `pr` သို့ တွန်းချက်တစ်ခု။ အခြားအရာအားလုံး (တွန်းသည်၊ အချိန်ဇယား၊ ပေးပို့မှု PR `release/v* → main`၊ မည်သည့်ဒေသထွက်ပြေးမှုမဆို) → `release`။

မုဒ်တစ်ခုစီတွင် `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) ကျရှုံးသည် ။

အေးဂျင့်-ညွန်ကြားချက်ဖိုင်တွေ ဆောင်ထား** မဟုတ်ဘူး** အားလုံးမှဆင်းသက်လာသောရေတွက်- `AGENTS.md`၊ `llm.txt` (နှင့် ၎င်း၏ `docs/i18n/*/llm.txt` ကော်ပီများ)၊ bs `AGENTS.md` ခက်ရင်း၊ `open-sse/services/AGENTS.md`၊ `src/shared/constants/agentSkills.ts`၊ `skills/README.md` နှင့် `skills/*/SKILL.md` တိုင်းသည် အရင်းအမြစ် (ဥပမာ `ROUTING_STRATEGY_VALUES` တွင် `src/shared/constants/routingStrategies.ts`) နှင့် `npm run facts` အစား။ မုဒ်နှစ်ခုလုံးတွင် "ထုတ်လုပ်ထားသော အရေအတွက်များ (ကိုယ်စားလှယ်-ညွှန်ကြားချက်ဖိုင် …)" သည် (ဝန်ဆောင်မှုပေးသူ၊ ရွှေ့ပြောင်းမှုများ၊ MCP ကိရိယာများနှင့် နယ်ပယ်များ၊ လမ်းပြနည်းဗျူဟာများ၊ အမှတ်ပေးအချက်များ

`pr` မုဒ်တွင် စာရေးဆရာအကိုင်းအခက်များက စီမံထားသောတန်ဖိုးများကို တည်းဖြတ်နိုင်သည်- `chore/derived-*` (ညစဉ်ပြန်လည်ဆန်းသစ်သည့် PR)၊ `release/v*` နှင့် ဘာသာပြန်လှိုင်း `docs/i18n-*` နှင့် `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`)။ Queue batches (`merge_group`၊ Mergify drafts ၊ `omni-queue/**`) ကို ထပ်ပြီး မဆုံးဖြတ်ပါ ။ ၎င်းတို့သည် PRs ဂိတ်မှ တစ်ခုပြီးတစ်ခု စီစစ်ပြီးဖြစ်သည်။

ထွက်ကုဒ်များ- `0` clean · `1` STRICT drift (သို့မဟုတ် `--strict` ဖြင့် soft drift ) သို့မဟုတ် စီမံထားသော တန်ဖိုးချိုးဖောက်မှု · `2` အခြေခံအဆောက်အအုံ — ကုဒ်အချက်အလက်ကို စုဆောင်း၍မရပါ (tsx probe မအောင်မြင်ပါ သို့မဟုတ် အချိန်ကုန်သွားသည်၊ အချိန်ကုန်သည် `OMNIROUTE_FACTS_TIMEOUT_MS` ဖြစ်သည်၊ ပုံသေ PR ms) သို့မဟုတ် CI အခြေခံတွင် ဖြေရှင်း၍မရပါ။ ထွက်ပေါက် 2 သည် စာရွက်စာတမ်းကွဲပြားခြင်းမဟုတ်ပါ- အလုပ်ကို ပြန်လည်လုပ်ဆောင်ပါ သို့မဟုတ် ပတ်ဝန်းကျင်ကို ပြင်ဆင်ပါ။

- `docs/reference/derived-facts.json` သည် နောက်ဆုံးအသုံးပြုခဲ့သော ပြန်လည်ဆန်းသစ်မှုဆိုင်ရာ အချက်အလက်များ၏ လျှပ်တစ်ပြက်ဓာတ်ပုံဖြစ်သည်။ ပြန်လည်ဆန်းသစ်မှုသာ ရေးသည်။ README SVG ဂျင်နရေတာများသည် ၎င်းကိုဖတ်ပြီး PR-time ယူနစ်စမ်းသပ်မှုများသည် ကျူးလွန်ထားသော docs နှင့်ထုတ်ပေးသောဖိုင်များကို — နှင့် တိုက်ရိုက်ကုဒ်ဖြင့် ဘယ်သောအခါမှ မနှိုင်းယှဉ်ပါ။ suite ၏တစ်ခုတည်းသောတိုက်ရိုက်ထုတ်လွှနှိုင်းယှဉ်ချက်မှာ `tests/unit/check-docs-counts-sync.test.ts` တွင် "ပြန်လည်စတင်ခြင်းသည် သံသရာကိုပိတ်သည်" ဖြစ်သည်- တိုက်ရိုက်အချက်အလက်များနှင့်အတူ၊ memory တွင်အသုံးပြုထားသည့် refresh ၏ပြန်လည်ရေးသားမှုအစီအစဉ်သည် ၎င်းကိုအစီရင်ခံခြင်းမပြုဘဲ STRICT ပျံ့လွင့်သွားခြင်းမရှိသည့်အပြင် ပြန်လည်စီစဉ်ခြင်းမှာလည်းဘာမှမပြောင်းလဲပါ။

စက်တွင်းတွင် ပြန်ထုတ်ရန် (စက်တွင်းသုံး defaults သည် `release` ဖြစ်သည်):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

ဖြေရှင်းနိုင်သော အခြေခံ (no `BASE_SHA`/`BASE_REF`၊ local `origin/release/v<version>`) မရှိဘဲ local `pr` run သည် သတိပေးချက်ကို print ထုတ်ပြီး ပျက်ကွက်မည့်အစား diff ကို ကျော်သွားပါသည်။

`fetch-depth: 0` — သည် value-drift gate သည် merge base နှင့် `en.json` ကွဲပြားသည်။

**Two modes (since 2026-11-13).** A feature PR adds or rewrites keys in `en.json` (and `bin/cli/locales/en.json`) and touches no other locale; `check:pr-derived-paths` (job `pr-test-policy`, family `config/quality/derived-paths/translation.json`) fails a feature PR that does. The other locales are completed once per release by `release:refresh-derived`, which calls `syncUiKeys()` in `scripts/i18n/sync-ui-keys.mjs` (add missing keys, prune dropped ones, mark translations of rewritten English with `rewrittenSinceRef`, translate), or by a translation wave. The gates read the mode from `scripts/check/lib/gateMode.mjs`: in `pr` mode (feature PRs, `merge_group`, `omni-queue/**`) the release-mode gates above print `SKIP reason=pr-mode` and exit 0; in `release` mode (the release PR, pushes to `main`, `workflow_dispatch`, local runs) they are strict as before, and on the release PR the diff-aware ones get `BASE_REF=origin/main`, so they judge every key the cycle added or rewrote. Preview the feature-PR verdict locally with `--mode=pr`.

`pr` မုဒ်တွင် ဒေသဆိုင်ရာ ကတ်တလောက်များကို ပြောင်းလဲဆဲဖြစ်သော PR (ဘာသာပြန်လှိုင်း၊ ထုတ်ဝေမှု ပြန်လည်ဆန်းသစ်မှု၊ ဘာသာပြန်ဆိုမှုသာ ပြုပြင်မှု) ကို ကျော်သွားမည်မဟုတ်ပါ- `check-key-completeness` သည် ပေါင်းစည်းမှုအခြေခံရှိ ကတ်တလောက်တစ်ခုစီကို တူညီသောကက်တလောက် (`scripts/i18n/lib/touched-catalogs.mjs`) နှင့် ပြောင်းထားသော ကက်တလောက်တစ်ခုစီတွင် ပျက်ကွက်ပြီး ကတ်တလောက်ပျောက်ဆုံးသွားသောသော့၊ `en.json` ချို့တဲ့သော၊ တကယ့်ဘာသာပြန်ဆိုချက်သည် `__MISSING__:` အမှတ်အသားမဟုတ်တော့ဘဲ အင်္ဂလိပ်ဘာသာအဖြစ်သို့ ပြောင်းသွားသည်၊ PR မထိ placeholders/tags အင်္ဂလိပ်စာတန်းတစ်ခု။ PR ရှိ ကတ်တလောက်အသစ်တစ်ခုသည် `en.json` သော့အစုံတစ်ခုလုံးကို သယ်ဆောင်ရမည်ဖြစ်သည်။ ၎င်းသည် PR ထိသော ကက်တလောက်များအတွက်၊ အချိုးနှင့် CLI-parity ဂိတ်များက မြင်ရမည့်အရာဖြစ်သည်။

locale-parity ယူနစ်စမ်းသပ်မှုများ (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) သည် `tests/_helpers/localeParityMode.ts` မှတဆင့် တူညီသောမုဒ်များကို လိုက်နာသည် : `pr` မုဒ်တွင် ၎င်းတို့သည် သော့-ညီမျှခြင်း အခိုင်အမာပြောဆိုချက်များကိုကျော်သွားကာ ထုတ်ဝေမှုတွင် ထွက်ခွာသွားသော ပေါင်းစပ်အခြေမှ အင်္ဂလိပ်ပြောင်းလဲသွားသော သော့များ၏ ညီမျှခြင်း (placeholder parity) ကို ပြန်လည်စတင်ခြင်း (ယူနစ်စမ်းသပ်မှုအလုပ်၏ သော့တိုင်းသည် ၎င်းကိုဖတ်မရသည့်အခါ) တိမ်ကောသွားပါသည်။ ထိုအကူအညီသည်** သာ** ဒဏ်ခတ်ထားသောမုဒ်-သတ်မှတ်ချက်အတိုင်း ကျော်သွားခြင်း- `check:test-masking` `.skip(` နှင့် `{ skip: true }` ကိုရေတွက်သော်လည်း ၎င်းသည် တွက်ချက်ထားသော `{ skip: "<reason>" }` ပြန်မလာသောကြောင့် `tests/unit/locale-parity-mode.test.ts` ၎င်းကိုအသုံးပြုရန်ခွင့်ပြုထားသောစမ်းသပ်မှုများစာရင်းကို — တွင်ထိုးထည့်ခြင်းသည် ထိုစာရင်းသို့ပြန်လည်သုံးသပ်ထားသောတည်းဖြတ်မှုတစ်ခုဖြစ်သည်။

#### `check-ui-value-drift` — stale-ဘာသာပြန်ဂိတ်

အခြားဂိတ်များ၏ တည်ဆောက်ပုံအရ မမြင်နိုင်သော i18n ဆုတ်ယုတ်မှုကို ဖမ်းစားသည်- အင်္ဂလိပ်တန်ဖိုးကို ပြန်လည်ပြင်ဆင်ပြီး _previous_ အင်္ဂလိပ်မှ ဆင်းသက်လာသော ဘာသာပြန်များသည် နောက်တွင်ရှိနေသောကြောင့် အင်္ဂလိပ်မဟုတ်သော အသုံးပြုသူများသည် စိတ်ချလက်ချ-စကားလုံးဖြင့် ယခုမှားနေသော ကော်ပီကို ဆက်လက်ဖတ်ရှုနေပါသည်။

ဒါက တကယ်ကို ပို့ပေးတာပါ။ Antigravity login helper #5203 `oauthModal.googleOAuthWarning` ;** ဒေသ ၄၃ ခုအနက် ၃၉ ခု** " URL အပြည့်အစုံကို ကော်ပီကူးပြီး အောက်တွင် ကူးထည့်ပါ" ဟု အော်ပရေတာများအား စာသား — တွင် ထားရှိ၍ ထိုဝန်ဆောင်မှုပေးသူအတွက် မပြီးမြောက်နိုင်ပါ။ #8463 မရောက်ခင်အထိ သတိမထားမိခဲ့တာမို့၊

- `sync-ui-keys` backfills သော့များသာဖြစ်သည်။** ပျက်ကွက်** ဘယ်တော့မှ မဖြစ်ဘူး။** သိုးသိုး** ;
- `check-ui-keys-coverage` သည် သော့ _presence_ ကို ရေတွက်သည်၊ ထို့ကြောင့် ဟောင်းနွမ်းသော ဘာသာပြန်ဆိုမှု ရမှတ်သည် အကျုံးဝင်သည် ။
- `check-translation-drift` သည် `docs/i18n/<locale>/**.md` documentation mirrors — ဘယ်တော့မှ `src/i18n/messages/*.json` မဖတ်တတ်ပါ။ အလုပ် `docs-sync-strict` တွင်အလုပ်လုပ်သည် : PRs တွင်အကြံပေးခြင်း၊ တွန်းအားပေးခြင်းနှင့်ညစဉ်ညတိုင်း၊ ဘာသာပြန်လှိုင်းသည် PR အင်္ဂါရပ်မဟုတ်ဘဲ မှန်များကို ပြန်လည်ဆန်းသစ်စေသည်။

**အခြေအမြစ် ကျောထောက်နောက်ခံပြုထားခြင်း မဟုတ်ဘဲ ကွဲပြားစွာ သိရှိမှု။** ၎င်းသည် အလုပ်လုပ်သောသစ်ပင်နှင့် ပေါင်းစည်းထားသော အခြေခံတွင် `en.json` နှိုင်းယှဉ်သည်။ အင်္ဂလိပ်တန်ဖိုး ပြောင်းလဲသွားသော သော့တိုင်းအတွက်၊ မထိမခိုက်ရသေးသော ဘာသာပြန်ခြင်းကို ကိုင်ဆောင်ထားဆဲ မည်သည့်နေရာမဆို ပျက်ယွင်းနေပါသည်။ ဒါက တမင်တကာ** နဂိုရှိရင်းစွဲကြွေးမြီများကို ရပ်တန့်စေသည်။** — a diff သည် မည်သည့်အင်္ဂလိပ်စကားဟောင်းမှ နှစ်ရှည်လများ ဘာသာပြန်ခြင်းမှ ထွက်လာသည်ကို မဖော်ပြနိုင်သောကြောင့် ဂိတ်သည် လက်ရှိပြောင်းလဲမှုနှင့် ထိတွေ့မှုကိုသာ ဆုံးဖြတ်သည်။ အခြားရွေးချယ်စရာ (သော့တစ်ခုစီ hash အခြေခံလိုင်းတစ်ခု) သည် ~ 600 KB ထုတ်ပေးသည့်ဖိုင်တစ်ခု၊ 3 × သည် အကြီးဆုံးအခြေခံလိုင်းဖြစ်ပြီး i18n PR တိုင်းတွင် လည်ပတ်နေမည်ဖြစ်သည်။

ကျေနပ်စေရန် နည်းလမ်းနှစ်ခု

1. ထိခိုက်ထားသော ဘာသာပြန်များကို အပ်ဒိတ်လုပ်ပါ။ သို့မဟုတ်
2. ၎င်းတို့ကို `__MISSING__:<new english>` — ဟု သတ်မှတ်ပြီး runtime တွင် ပြုပြင်ထားသော အင်္ဂလိပ် (`src/i18n/request.ts::deepMergeFallback`, #7258) နှင့် ဘာသာပြန်ရန်အတွက် သော့တန်းစီများကို ဆောင်ရွက်ပေးသည်။

ကြိုးတစ်ချောင်းရဲ့ ရင်ကို** အဓိပ္ပါယ်** ပြောင်းတယ်၊ ပိုကြိုက်တယ်။** သော့ကို အမည်ပြောင်းခြင်း။** - သော့အသစ်သည် ဟောင်းနွမ်းသောဘာသာပြန်ခြင်းကို အမွေဆက်ခံ၍မရပါ။ အဲဒါကတော့ #8463 သုံးတဲ့ ပုံစံပါ။

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Base catalog ကို ဖတ်၍မရသောအခါ (အခြေခံ ref မပါဘဲ တိမ်ပိုင်းကိုယ်ပွား) `check-openapi-breaking` ကို ထင်ဟပ်ပြနေသောအခါတွင် `SKIP reason=base-unresolved` ဖြင့် 0 မှ ထွက်သည်။ ဖြန့်ချိသည့်မုဒ်သာ- PR အင်္ဂါရပ်တစ်ခုသည် အင်္ဂလိပ်ကို ပြန်လည်ရေးသားပြီး ထိုနေရာတွင် ရပ်သည်။ ထုတ်ဝေမှု ပြန်လည်ဆန်းသစ်ခြင်းသည် နောက်ကျကျန်ခဲ့သော ဘာသာပြန်ဆိုချက်များကို အမှတ်အသားပြုသည် (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`၊ အလားတူ `findStaleTranslations`)။

ခွင့်ပြုစာရင်းများ (`eslint-suppressions.json`, `test-masking-allowlist.json`, `test-discovery-baseline.json`,
…) သည် **ဘတ်ဂျက်များမဟုတ်သောကြောင့်** မပြင်ဆင်ထားပါ။ Pass/fail policy gates (secrets, SQL rules,
docs/env contract, i18n parity, unit tests) မပြောင်းလဲပါ — test အနီရောင်ဖြစ်ပါက အနီရောင်အတိုင်းပင် ဖြစ်သည်။

**Tooling**

- `npm run quality:relax-baselines -- --pct 20 --note velocity_YYYY_MM_DD [--dry-run]` — တစ်ကြိမ်တည်းလုပ်ဆောင်သည့်
  ဖြေလျှော့မှု (`scripts/quality/relax-baselines.mjs`) ဖြစ်ပြီး note တစ်ခုတည်းဖြင့် နှစ်ကြိမ်လုပ်ဆောင်ရန် ငြင်းပယ်သည်။
- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` —
  CI လုပ်ဆောင်သည့်နည်းလမ်းအတိုင်း ဂဏန်းတန်ဖိုးပါသော gate တိုင်းကို တိုင်းတာပြီး gate တစ်ခုချင်းစီအတွက် ကျန်ရှိသည့် headroom ကို
  ပြသသည် (`scripts/quality/baseline-headroom.mjs`)။ nightly `baseline-headroom` job သည်
  workflow run summary တွင် ဇယားကို ထုတ်ဝေပြီး JSON/Markdown အစီရင်ခံစာကို
  `baseline-headroom-<run_id>` အဖြစ် upload လုပ်ကာ 90 ရက်ကြာ ထိန်းသိမ်းထားသည်။ Warning နှင့် critical row များသည်
  cap နှင့် 10% အတွင်းရောက်နေသော သို့မဟုတ် cap ကို ကျော်လွန်ပြီးဖြစ်သော gate များကို ဖော်ပြသည်။ ဘတ်ဂျက်များ
  သုံးစွဲနေမှုအတွက် အစောပိုင်းသတိပေးချက်အဖြစ် ဤအစီရင်ခံစာများကို ပြန်လည်သုံးသပ်ပြီး ပြဿနာဖြစ်စေသော gate ၏
  `_rebaseline_*` မှတ်ချက်များကို စစ်ဆေးပါ။ Job သည် အမြဲတမ်း issue တစ်ခုကို ဖန်တီးခြင်း သို့မဟုတ် အပ်ဒိတ်လုပ်ခြင်း မပြုတော့ပါ၊
  #12149 သည် ယခင်အစီရင်ခံစာမှတ်တမ်းကို ထိန်းသိမ်းထားသည်။

**ကုဒ်အသစ်မုဒ် (Clean-as-You-Code) — 2026-08-30 မှစ၍၊ PR fast-path အတွက်သာ**

`pull_request` event များတွင် `quality.yml` သည် `check:file-size`၊
`check:complexity-ratchets` နှင့် `check:dead-code` သို့ `--base-ref <PR base SHA>` ကို ပေးပို့သည်။ `check:complexity-ratchets` နှင့်
`check:dead-code` အတွက် gate သည် merge-base နှင့် HEAD ကို **PR က ပြင်ဆင်ခဲ့သည့်ဖိုင်များအတွင်းသာ ကန့်သတ်၍**
နှိုင်းယှဉ်သည် (`scripts/check/newCodeMode.mjs`: merge-base ကို ယာယီအသုံးပြုသည့်
`git worktree` တွင် materialize လုပ်ပြီး ESLint/knip ကို ထိုနေရာနှင့် HEAD နှစ်ခုစလုံးတွင် run ကာ ဖိုင်တစ်ဖိုင်ချင်းအလိုက်
အရေအတွက်များကို diff လုပ်သည်):

- **ပိတ်ဆို့သည့်အရာ** — PR က ပြင်ဆင်ထားသောဖိုင်များတွင် cyclomatic/cognitive violation များ သို့မဟုတ် dead export များကို ထည့်သွင်းခဲ့ခြင်း
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` ကို log တွင် တွေ့ရမည်);
- **အကြံပြုချက်** — frozen baseline နှင့် နှိုင်းယှဉ်ထားသော global total။ အမွေဆက်ခံလာသည့် drift ကြောင့်
  အပြစ်မရှိသော PR ကို အနီရောင်မပြစေပါ။ ထို drift ကို release reconciliation အချိန်တွင် ပြန်လည် frozen လုပ်ပြီး headroom job က စောင့်ကြည့်သည်။

`check:file-size` သည် base ref ကို ၎င်း၏ကိုယ်ပိုင်စည်းမျဉ်းများအတိုင်း အသုံးပြုသည် (`scripts/check/check-file-size.mjs`, #8522):
၎င်းသည် tree အတွင်းရှိ source နှင့် test ဖိုင်တိုင်းကို စစ်ဆေးပြီး၊ `git show` ဖြင့် PR base ရှိ ဖိုင်တစ်ဖိုင်ချင်းစီ၏
လိုင်းအရေအတွက်ကို ဖတ်သည်။ ထို့နောက် ဖိုင်တစ်ဖိုင်သည် ၎င်း၏ baseline ceiling
(`frozen` / `testFrozen` သို့မဟုတ် baseline ပြင်ပရှိဖိုင်အတွက် `cap` / `testCap`) နှင့် base size တို့အနက် ပိုကြီးသည့်တန်ဖိုးကို
ကျော်လွန်သည့်အခါမှသာ fail ဖြစ်စေသည်။ Base တွင် drift ဖြစ်ပြီးသားဖိုင်တစ်ဖိုင်သည် ထိုအကြောင်းကြောင့် အပြစ်မရှိသော PR ကို
အနီရောင်မပြစေတော့ပါ။

`check:boundary:ratchet` သည် ၎င်း၏ တစ်ခုတည်းသော နံပါတ်အတွက်လည်း တူညီသော စည်းမျဉ်းကို အသုံးပြုသည်
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR event များတွင်
`quality.yml` fast-gates နှင့် `ci.yml` lint job နှစ်ခုစလုံးက PR base SHA ကို ပေးပို့သည်၊ base commit ကို
`git archive` export မှ တိုင်းတာသည်၊ ထို့အပြင် ၎င်း၏ `open-sse → src` edge
အရေအတွက်သည် `metrics.boundaryOpenSseToSrc` နှင့် base ပေါ်ရှိ အရေအတွက်တို့အနက် ပိုကြီးသောတန်ဖိုးထက် ကျော်လွန်မှသာ PR မအောင်မြင်ပါ။ မျက်နှာကျက်တန်ဖိုးထက် ကျော်လွန်သော base drift ကို (`base drift herdado`) အစီရင်ခံသော်လည်း အပြစ်မရှိသော PR ကို မအောင်မြင်စေပါ။ push → main သည် absolute ceiling ကို ဆက်လက်အသုံးပြုပြီး ဖြေရှင်း၍မရသော base SHA ဖြစ်ပါက သတိပေးချက်ဖြင့် ၎င်းထံသို့ fallback ပြုလုပ်သည်။

Omni-queue candidate တစ်ခု (`omni-queue/**` သို့ push ပြုလုပ်ခြင်း၊ [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ကို ကြည့်ပါ) သည် pull request တစ်ခုကဲ့သို့ပင် ကိုင်တွယ်ခံရသည်။ workflow နှစ်ခုစလုံးက candidate base
(`needs.changes.outputs.candidateBase`) ကို `--base-ref` အဖြစ် ပေးပို့ပြီး `check:ts7-diagnostics-ratchet` ကိုလည်း
၎င်းအပေါ်တွင် run ပြုလုပ်သည်။ code အသစ်အတွက် gate နှစ်ခုတွင် comparison base သည် ထို SHA ကိုယ်တိုင်ဖြစ်ပြီး ထိပ်ဆုံး merge commit ၏ first parent မဟုတ်သောကြောင့် batch အတွင်းရှိ pull request တစ်ခုချင်းစီကို စစ်ဆေးနိုင်သည်။

`workflow_dispatch` run များ၊ release-green sweep နှင့် nightly headroom job တို့တွင် PR base မရှိသဖြင့် absolute (global) comparison ကို ဆက်လက်အသုံးပြုသည်။ Coverage၊ duplication နှင့် type-coverage တို့သည် လောလောဆယ် global အဖြစ် ဆက်ရှိနေသည် (၎င်းတို့၏ tools များသည် file တစ်ခုချင်းစီအလိုက် diff ကို ကုန်ကျစရိတ်နည်းစွာဖြင့် မထုတ်ပေးနိုင်သေးသောကြောင့်) — တူညီသော ကိုင်တွယ်မှုအတွက် candidate များဖြစ်သည်။

**v4.0 တွင် phase ကို ပိတ်ခြင်း (LTS = ယခင်ထက် ပိုမိုတင်းကျပ်ခြင်း၊ "ပုံမှန်အခြေအနေသို့ ပြန်သွားခြင်း" မဟုတ်ပါ)**

1. သန့်ရှင်းသော `release/v4.0.0` tip ပေါ်တွင်: မှတ်တမ်းအတွက် `npm run quality:headroom --json` ကို run ပြီးနောက်
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update` နှင့် typecheck gate တစ်ခုချင်းစီ၏
   `--update` ကို run ပြုလုပ်ပါ — baseline တိုင်းသည် တိုင်းတာရရှိသောတန်ဖိုးသို့ လျော့ကျသွားရမည်။
2. `quality-baseline.json` ထဲမှ `_policy` ကို ဖျက်ပါ (`--require-tighten` နှင့် nightly
   banking ကို ပြန်လည်အသက်သွင်းရန်)၊ ထို့နောက် `check-openapi-coverage.mjs` ထဲတွင်
   `THRESHOLD = 36` (သို့မဟုတ် ထိုထက်မြင့်သောတန်ဖိုး) ကို ပြန်လည်ထားရှိပါ။
3. modularization ကြောင့် အကျိုးရှိလာသောနေရာများတွင် တိုင်းတာရရှိသောတန်ဖိုးထက် ပိုမိုတင်းကျပ်အောင် ပြုလုပ်ပါ: file-size `cap` ကို 1000

## Ratchet အခြေခံတန်ဖိုး (`quality-baseline.json`)

Ratchet engine (`scripts/quality/check-quality-ratchet.mjs`) သည် `quality-baseline.json` ကိုဖတ်ပြီး
အသစ်စုဆောင်းထားသော `quality-metrics.json` နှင့် နှိုင်းယှဉ်သည်။ မည်သည့် metric မဆို
၎င်း၏ epsilon ထက်ကျော်လွန်၍ ဆုတ်ယုတ်ပါက build မအောင်မြင်ပါ။

လက်ရှိခြေရာခံနေသော metrics များမှာ-

| Metric                | Direction | အဓိပ္ပာယ်                          |
| --------------------- | --------- | ---------------------------------- |
| `eslintWarnings`      | `down`    | ESLint သတိပေးချက်အရေအတွက် မတိုးရပါ |
| `coverage.statements` | `up`      | Statement coverage မကျရပါ          |
| `coverage.lines`      | `up`      | Line coverage မကျရပါ               |
| `coverage.functions`  | `up`      | Function coverage မကျရပါ           |
| `coverage.branches`   | `up`      | Branch coverage မကျရပါ             |

အမှန်တကယ်တိုးတက်မှုရှိပြီးနောက် baseline ကို အပ်ဒိတ်လုပ်ရန်-

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` flag သည် လက်ရှိတိုင်းတာထားသော တန်ဖိုးများကို `quality-baseline.json` ထဲသို့ ရေးသားသည်။
တိုးတက်မှုကို baseline ထဲတွင် မှတ်တမ်းတင်ခြင်းသည် release/nightly အလုပ်ဖြစ်ပြီး feature PR ၏ အလုပ်မဟုတ်ပါ။ `--require-tighten`
(Fase 6A.5) သည် baseline ထဲသို့ မသွင်းရသေးသော တိုးတက်မှုကို release mode (push, schedule, release PR၊
local runs) တွင်သာ မအောင်မြင်စေသည်။ Feature PR (`pr` gate mode) တွင်မူ တိုးတက်မှုကို အချက်အလက်အဖြစ် ပြသပြီး
အောင်မြင်စေသည်။ ဆုတ်ယုတ်မှုဖြစ်ပါက mode နှစ်ခုလုံးတွင် မအောင်မြင်ပါ။ Velocity phase အတွင်းတွင်မူ နေရာတိုင်း၌
အကြံပြုချက်အဖြစ်သာ သတ်မှတ်ထားသည် (`_policy.requireTighten: false`)။ [Generated files and derived baselines](#generated-files-and-derived-baselines-written-at-release) တွင် ကြည့်ပါ။

### CodeQL ratchet: ပြန်လည်စစ်ဆေးသည့်အကြိမ်နှုန်းနှင့် ကိုယ်တိုင်စတင်ခြင်း

`check:codeql-ratchet` သည် **PR တိုင်းအလိုက် မဟုတ်ဘဲ အချိန်ဇယားအတိုင်း ပြန်လည်မွမ်းမံထားသော repo အခြေအနေကို ဖတ်သည်။**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` သည်

ဆန်းစစ်ခြင်းမဟုတ်ဘဲ GitHub ၏ default-setup scan ဖြစ်သည်။ ထို့ကြောင့် alert များကို FIX လုပ်သည့် PR merge
ဖြစ်ပြီးနောက် ratchet သည် နောက်တစ်ကြိမ် schedule အတိုင်း scan မလုပ်မချင်း အဟောင်းဖြစ်သော အရေအတွက်မြင့်ကို ဆက်လက်ဖတ်နေမည်ဖြစ်သည်။
ထို့ကြောင့် scan က အခြေအနေကို မသိမ်းဆည်းမချင်း ဖွင့်ထားသော PR တိုင်းတွင်၊ alert များကို ပြင်ဆင်သည့် PR ၏
နောက်ဆက်တွဲများတွင်ပင် regression ကို အစီရင်ခံမည်ဖြစ်သည်။

**ကိုယ်တိုင် refresh လုပ်ရန်**: `gh workflow run codeql.yml --ref release/vX.Y.Z` သည်
ဆန်းစစ်မှုကို ပြန်လည်လုပ်ဆောင်ပြီး မိနစ်အနည်းငယ်အတွင်း alert များကို ပြန်လည်ထုတ်ပြန်သည်။ `.github/workflows/codeql.yml` ကို
အရင်ဖတ်ပါ။ ၎င်း၏ header တွင် GitHub ၏ **"default setup" နှင့် ပဋိပက္ခဖြစ်သောကြောင့်**
`workflow_dispatch`-only ဖြစ်ကြောင်း ရှင်းပြထားသည် (`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`)။ `push`/`pull_request`/
`schedule` triggers များကို ပြန်လည်ထည့်သွင်းရန် **ပိုင်ရှင်ဘက်မှ ဦးစွာ လုပ်ဆောင်ချက်လိုအပ်သည်**: Settings → Code security →
CodeQL: Default → Advanced။ ထို switch ကို မပြောင်းဘဲ `schedule:` trigger ထည့်မထားပါနှင့် — ၎င်းသည်
မအောင်မြင်သော runs များကိုသာ ထုတ်ပေးမည်ဖြစ်သည်။

**အရေအတွက်ကျဆင်းပြီးနောက် baseline ကို တင်းကျပ်ပါ** — `node scripts/check/check-codeql-ratchet.mjs
--update` သည် တိုင်းတာရရှိသော အရေအတွက်အသစ်ကို `quality-baseline.json` → `metrics.codeqlAlerts.value` ထဲသို့ ရေးသားသဖြင့်
ratchet သည် အရင်ကန့်သတ်ချက်အထိ ပြန်တက်သွားသော regression ကို တိတ်တဆိတ် ခွင့်မပြုနိုင်တော့ပါ။ လုပ်ဆောင်ထားသော ဥပမာ (2026-09-02/03): PR #12502 သည်
အမှန်တကယ်ဖြစ်သော alerts ၇ ခုကို ပြင်ဆင်ခဲ့သည် (တိုင်းတာရရှိသော open အရေအတွက် 13 → 6)၊ PR #12530 သည် frozen baseline ကို 11 → 6 သို့
တင်းကျပ်ပြီး ကိုက်ညီစေခဲ့သည်။ ထို့နောက် ကျန်ရှိသော 6 ခုကို alert တစ်ခုချင်းစီအတွက် အကြောင်းပြချက်ဖြင့် dismiss လုပ်ကာ open အရေအတွက်ကို 0 သို့ လျှော့ချခဲ့သည်။

**Dismissal များသည် operator ၏ ဆုံးဖြတ်ချက်ဖြစ်သည် (Hard Rule #14)** — CodeQL alert တစ်ခုကို
dismissal comment ထဲတွင် နည်းပညာဆိုင်ရာ အကြောင်းပြချက် မှတ်တမ်းတင်ခြင်းမရှိဘဲ မည်သည့်အခါမျှ dismiss မလုပ်ပါနှင့်:
upstream-protocol လိုအပ်ချက်အတွက် `won't fix`၊ test fixture အတွက် `used in tests`၊ CodeQL မမြင်နိုင်သော sanitizer အတွက်
`false positive` ကို အသုံးပြုပါ (နမူနာအဖြစ်: `docs/security/ERROR_SANITIZATION.md`)။

## Release အဆင့် Ratchet Drift (WS5.5, v3.8.49)

PURE release tip ပေါ်တွင် ratchet တစ်ခု (ဖိုင်အရွယ်အစား၊ ရှုပ်ထွေးမှု၊ eslint သတိပေးချက်များ) regression ဖြစ်လာသောအခါ —
ဆိုလိုသည်မှာ merge များ၏ ပေါင်းစပ်မှုကြောင့် regression ဖြစ်ပြီး PR တစ်ခုတည်းက ၎င်း၏
ကိုယ်ပိုင် branch ပေါ်တွင် ထို regression ကို ပြန်လည်ဖြစ်ပေါ်စေနိုင်ခြင်းမရှိသောအခါ — ပြင်ဆင်မှုသည် **release captain က release
branch ပေါ်တွင် တစ်ကြိမ်သာ** လုပ်ဆောင်ရန် တာဝန်ရှိသည်- extraction/refactor ကို ဦးစားပေးပါ၊ မှတ်တမ်းတင်ထားသော
အကြောင်းပြချက် entry ရှိမှသာ baseline ကို ပြန်လည်သတ်မှတ်ပါ။ ပေါင်းစပ်မှုကြောင့်ဖြစ်သည့် drift ကို contributor PR ပေါ်သို့ မည်သည့်အခါမျှ
မတွန်းပို့ပါနှင့်၊ PR တစ်ခုချင်းစီအလိုက်လည်း baseline ကို မည်သည့်အခါမျှ ပြန်လည်မသတ်မှတ်ပါနှင့် (ထိုသို့လုပ်ခြင်းသည် အမှန်တကယ်ဖြစ်သော regression များကို ဖုံးကွယ်သည်)။ ဦးစွာ ခွဲခြားစစ်ဆေးပါ- သင်၏ PR ကြောင့် ဖြစ်သည်ဟု မယူဆမီ
probe worktree တစ်ခုထဲရှိ pure tip ကို အသုံးပြု၍ မအောင်မြင်မှုကို ပြန်လည်ဖြစ်ပေါ်စေပါ။

## Ratchet လျှော့ချမှုများကို စုဆောင်းသိမ်းဆည်းခြင်း — အောက်သို့ ဦးတည်ချက် (#8584)

ratchet သည် တစ်ဝက်သာ အလိုအလျောက်ဖြစ်ပြီး၊ အလိုအလျောက်ဖြစ်နေသည့်အပိုင်းကလည်း မှားယွင်းသည့်အပိုင်းဖြစ်သည်။ cap ကို **မြှင့်တင်ခြင်း** သည်
ဆယ်စက္ကန့်သာကြာသော manual JSON ပြင်ဆင်မှုဖြစ်ပြီး မအောင်မြင်နေသော PR ကို အမြန်ဆုံး ပြန်လည်လုပ်ဆောင်နိုင်စေသည့် နည်းလမ်းဖြစ်သည်။
cap တစ်ခုကို **လျှော့ချခြင်း** အတွက်မူ တစ်စုံတစ်ဦးက `--update` ကို run ပြီး ရလဒ်ကို commit လုပ်ရန်လိုသည် — ထို့အပြင်
`bank-ratchet-shrinks` job မပေါ်ပေါက်မီအထိ မည်သည့် workflow ကမျှ ထိုသို့ run မလုပ်ခဲ့ပါ။ တိုင်းတာတွေ့ရှိရသော အကျိုးဆက်
(2026-07-25)- frozen file 18 ခုသည် file အသစ်အတွက် သတ်မှတ်ထားသော လိုင်း 800 cap အောက် သို့မဟုတ် ၎င်းနှင့်ညီမျှသော အခြေအနေသို့ ရောက်ရှိပြီးဖြစ်သော်လည်း၊ အဆိုးဆုံးမှာ
132× (`src/shared/validation/schemas.ts` တွင် လိုင်း 19 သာရှိသော်လည်း cap 2,523 ထားရှိခြင်း) ဖြစ်သည်၊
complexity ceiling သည် rebaseline မှတ်စု ~37 ခုအတွင်း `1794 → 2169` သို့ တက်သွားပြီး လျှော့ချမှုမှာ တိတိကျကျ တစ်ကြိမ်သာ
(−1) ရှိခဲ့သည်၊ ထို့အပြင် "နောက် cycle တွင် `--update` ဖြင့် တင်းကျပ်မည်" ဟု 31 ကြိမ်ရေးသားခဲ့သော်လည်း တစ်ကြိမ်သာ
အကောင်အထည်ဖော်ခဲ့သည်။ ၎င်းကို ဖြစ်ပေါ်စေခဲ့သော code ထက် ပို၍ကြာရှည်တည်ရှိသည့် cap သည် ပြီးစီးသွားသော
decomposition တစ်ခုစီကို ထို file ကို နောက်တစ်ကြိမ် ပြင်ဆင်သူအတွက် တိုးချဲ့ခွင့်အဖြစ် တိတ်တဆိတ် ပြောင်းလဲပေးသည်။

### ဘေးကင်းရေး အတည်ပြုကိရိယာ

job သည် လူကိုယ်တိုင် ကြီးကြပ်ခြင်းမရှိဘဲ baseline များသို့ ရေးသားသောကြောင့် `verify-ratchet-bank.mjs` ကသာ
ထိုလုပ်ဆောင်ချက်ကို လက်ခံနိုင်စေသည်။ ၎င်းသည် `--update` ပြီးနောက် tree ကို `HEAD` နှင့် diff လုပ်ပြီး၊ ပြောင်းလဲမှုတိုင်းသည်
အောက်ပါအမျိုးအစားများထဲမှ တစ်ခုမဟုတ်ပါက **မည်သည့် commit မျှ မရှိမီ job ကို ရပ်တန့်ကာ**
PR လုံးဝ မဖွင့်ပါ-

- `frozen` / `testFrozen` numeric entry တစ်ခုကို **လျှော့ချခြင်း** သို့မဟုတ် **ဖယ်ရှားခြင်း**
- `complexity-baseline.json` → `count` ကို **လျှော့ချခြင်း**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ကို **လျှော့ချခြင်း**

အခြားမည်သည့်အရာမဆို မအောင်မြင်ပါ- ကိန်းဂဏန်းတစ်ခုကို မြှင့်တင်ခြင်း၊ entry တစ်ခုထည့်ခြင်း၊ `cap`/`testCap` ကို ပြောင်းလဲခြင်း သို့မဟုတ်
`_rebaseline_*` မှတ်စုတစ်ခုကို ဖျက်ခြင်း/ပြန်လည်ရေးသားခြင်း (ထိုမှတ်စုများသည် ceiling တစ်ခုစီ ရှိနေရသည့်အကြောင်းရင်းအတွက် audit trail ဖြစ်ပြီး
file entry များနှင့်အတူ တူညီသော `frozen` object ထဲတွင် သိမ်းဆည်းထားသည်)။ cap ကို မြှင့်တင်နိုင်သော bot သည် လက်ရှိအခြေအနေထက်
ပိုဆိုးမည်မှာ သေချာသည်။ Regression guard- `tests/unit/verify-ratchet-bank.test.ts`။

job သည် `release/*` သို့ မည်သည့်အခါမျှ push မလုပ်ပါ — လူတစ်ဦးက PR ကို merge လုပ်ရသောကြောင့် မှားယွင်းသည့် တိုင်းတာမှုတစ်ခုသည်
ပြန်လည်သုံးသပ်ခြင်းမရှိဘဲ အတည်မဖြစ်နိုင်ပါ။

## Allowlist မူဝါဒ

ရှိပြီးသား ချိုးဖောက်မှုများကြောင့် မအောင်မြင်နိုင်သော gate တိုင်းတွင် frozen allowlist တစ်ခုကို အသုံးပြုထားသည်
(ဥပမာ `KNOWN_STALE_DOC_REFS`၊ `KNOWN_MISSING`၊ `KNOWN_RAW_SQL`)။ မူဝါဒမှာ -

**အမြစ်ခံအကြောင်းရင်းကို ပြင်ဆင်ပါ။ ချိုးဖောက်မှုသည် ရှိပြီးသားဖြစ်ပြီး
တစ်ခုတည်းသော PR အတွင်း မပြင်ဆင်နိုင်သည့်အခါမှသာ allowlist ကို အသုံးပြုပါ။**

Allowlist ထဲသို့ entry တစ်ခု ထည့်သွင်းသည့်အခါ -

1. အကြောင်းပြချက်ပါဝင်သော comment တစ်ခု ထည့်ပါ။
2. လိုက်လံခြေရာခံမည့် issue ကို ရည်ညွှန်းပါ (ဥပမာ `// #3498 — Phase 2 feature, not yet implemented`)။
3. ချိုးဖောက်မှုကို ပြင်ဆင်သည့် PR တစ်ခုတည်းအတွင်း entry ကို ဖယ်ရှားပါ — လက်ရှိဖြစ်နေသော ချိုးဖောက်မှုကို
   မဖိနှိပ်တော့သည့် stale entry သည် ကိုယ်တိုင် defect တစ်ခုဖြစ်သည် (အကောင်အထည်ဖော်ပြီးသည့်အခါ
   6A.3 stale-enforcement သည် orphaned allowlist entry ကြောင့် gate ကို fail လိမ့်မည်)။

Tests များ မြန်မြန်အောင်မြင်စေရန် allowlist entry များ မထည့်ပါနှင့်။ တိုးပွားလာသော allowlist နှင့်အတူ
အောင်မြင်နေသော gate သည် အရည်အသွေးကောင်းမွန်သည်ဟု မှားယွင်းစွာ ယူဆစေခြင်းသာ ဖြစ်သည်။

### သင့် PR တွင် gate မအောင်မြင်သည့်အခါ

1. **Gate output ကို သေချာဖတ်ပါ** — မည်သည့် file သို့မဟုတ် symbol က စည်းမျဉ်းကို ချိုးဖောက်ထားသည်ကို အတိအကျ ဖော်ပြပေးသည်။
2. **ချိုးဖောက်မှုကို ပြင်ဆင်ပါ** — gate အများစုသည် deterministic filesystem check များဖြစ်သောကြောင့် code မှန်ကန်သည်နှင့် တစ်ပြိုင်နက် အောင်မြင်သွားမည်။
3. **ချိုးဖောက်မှုသည် ရှိပြီးသားဖြစ်ပါက** (ဆိုလိုသည်မှာ သင်က မထည့်သွင်းခဲ့သော်လည်း gate က ယခုမှ လွှမ်းခြုံစစ်ဆေးခြင်းဖြစ်ပါက) justification comment နှင့် tracking issue ပါဝင်သော allowlist entry တစ်ခု ထည့်ပါ။
4. **Gate သည် ratchet ဖြစ်ပါက** (coverage၊ ESLint warnings၊ duplication၊ complexity) သင့်ပြောင်းလဲမှုက metric ကို ပိုမိုဆိုးရွားစေခြင်းဖြစ်သည်။ အခြေခံပြဿနာကို ပြင်ဆင်ပါ၊ သို့မဟုတ် (ရှားပါးစွာ) ပြောင်းလဲမှုသည် ရည်ရွယ်ချက်ရှိပြီး metric ကျဆင်းမှုကို လက်ခံနိုင်ပါက `npm run quality:ratchet -- --update` ကို လုပ်ဆောင်ပါ — သို့သော် PR description ထဲတွင် အကြောင်းရင်းကို မှတ်တမ်းတင်ပါ။
5. **အကြံပြုချက်ပေးသည့် gate များ** (`continue-on-error: true`) သည် အချက်အလက်ပေးရန်သာဖြစ်ပြီး merge ကို မတားဆီးပါ၊ သို့သော် CI summary ထဲတွင် ပေါ်လာမည်။ ထို gate များကိုလည်း မဖြစ်မနေ ပြင်ဆင်ပါ။

## Gate အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `scripts/check/check-<name>.mjs` (သို့မဟုတ် `.ts`) ကို ဖန်တီးပါ။ မူဝါဒ gate များသည် 0/1 ဖြင့် ထွက်သည်။
   Ratchet ပုံစံ gate များသည် `collect-metrics.mjs` မှတစ်ဆင့် တိုင်းတာချက်တစ်ခုကို `quality-metrics.json` သို့ ထုတ်ပေးသည်။
2. `"check:<name>": "node scripts/check/check-<name>.mjs"` ကို `package.json` တွင် ထည့်ပါ။
3. `.github/workflows/ci.yml` အတွင်း သင့်လျော်သော job အောက်တွင် ၎င်းကို ချိတ်ဆက်ပါ
   (မူဝါဒ → `lint` သို့မဟုတ် `docs-sync-strict`; ratchet → `quality-gate`)။
4. ၎င်းတွင် ခွင့်ပြုစာရင်းတစ်ခု ပါဝင်ပါက ခေတ်မမီတော့သော entry များကို အလိုအလျောက် ရှာဖွေနိုင်စေရန်
   `scripts/check/lib/allowlist.mjs` မှ `reportStaleEntries()` ကို အသုံးပြုပါ။
5. gate ၏ ရှာဖွေစစ်ဆေးမှု logic ကို လွှမ်းခြုံသည့် စမ်းသပ်မှုတစ်ခုကို `tests/unit/build/` တွင် ရေးပါ။
6. ဤစာတမ်းကို အပ်ဒိတ်လုပ်ပါ (သက်ဆိုင်ရာ job ဇယားတွင် row တစ်ခု ထည့်ပါ)။

## Agent ကိရိယာများ- LSP-in-the-loop (ရွေးချယ်အသုံးပြုနိုင်)

CI gate များအပြင် OmniRoute တွင် **ရွေးချယ်အသုံးပြုနိုင်သော** `agent-lsp` scaffold
(project အဆင့် `.mcp.json`၊ Fase 7 Task 15) ပါရှိသည်။ coding agent များအတွက် TypeScript language server ကို ဖော်ထုတ်ပေးရန် `.mcp.json`
ကို ဖန်တီးပါ။ ထိုသို့ဖြင့် ၎င်းတို့သည် code မရေးမီ symbol များ /
diagnostic များကို ဖြေရှင်းနိုင်မည်ဖြစ်သည် — ၎င်းသည် မရှိသည့် symbol များကို ဖန်တီးမိခြင်းကြောင့် ဖြစ်သော error များကို အရင်းအမြစ်မှ လျှော့ချပေးသည့်
`typecheck:core` ၏ compile-before-claim တွဲဖက်တစ်ခုဖြစ်သည်။ ၎င်းကို ရည်ရွယ်ချက်ရှိရှိ
အလိုအလျောက် မတင်ထားပါ (MCP↔LSP bridge ကို သင်ကိုယ်တိုင် ရွေးချယ်ပြီး အတည်ပြုရမည်)။ ပျက်နေသော entry တစ်ခုသည်
ချိတ်ဆက်မှု error ကိုသာ log လုပ်ပြီး session များကို မည်သည့်အခါမျှ မပျက်စေပါ။

## Rationalization Backlog (ROI ပြန်လည်သုံးသပ်ချက် — အဆင့် 9 လှိုင်း 3)

ဤစာရင်းကို 2026-06-17 တွင် `ci.yml` နှင့် တိုက်ဆိုင်စစ်ဆေးပြီး ပြန်လည်ညှိနှိုင်းထားသည် (ယခင်ဗားရှင်းတွင်
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` တို့ မပါဝင်ခဲ့ပါ)။ ပြန်လည်ညှိနှိုင်းထားသောအစုကို ROI ပြန်လည်သုံးသပ်ရာမှ
အောက်ပါ rationalization ကိုယ်စားလှယ်များကို ဖော်ထုတ်ခဲ့သည်။ **ပေါင်းစည်းမှုများသည် CI ၏ စက်ပိုင်းဆိုင်ရာ
ပြောင်းလဲမှုများဖြစ်ပြီး၊ flip/drop များသည် operator အတွက်သာ သီးသန့်ထားသော မူဝါဒဆုံးဖြတ်ချက်များဖြစ်သည်။** အောက်ပါအရာများထဲမှ
မည်သည့်အရာမျှ လက်ရှိတွင် အသုံးမချရသေးပါ။

**အထက်တွင်လည်း မှတ်တမ်းမတင်ရသေးသောအရာများ** (အကြံပြုချက်သာ၊ signal နည်းပါး): `docs-lint` job
(markdownlint + Vale၊ job တစ်ခုလုံး `continue-on-error`) နှင့် သီးခြား scanner workflows များဖြစ်သော
`semgrep.yml` / `codeql.yml` / `scorecard.yml` တို့ဖြစ်သည်။ `semgrepFindings: 0` သည်
`quality-baseline.json` တွင် ပါရှိသော်လည်း `ci.yml` အတွင်း blocking ratchet နှင့် ချိတ်ဆက်ထားခြင်း မရှိသေးပါ — metric သည်
လက်ရှိတွင် သီးခြားကျန်နေသည်။

### ပေါင်းစည်းခြင်း / ထပ်တူဖယ်ရှားခြင်း (စက်ပိုင်းဆိုင်ရာ၊ အန္တရာယ်နည်း)

ကိုယ်စားလှယ်တစ်ခုချင်းစီကို 2026-06-17 တွင် live gate state နှင့် တိုက်ဆိုင်စစ်ဆေးခဲ့သည် (ယုံကြည်သော်လည်း အတည်ပြုစစ်ဆေးပါ)၊
“သိသာသော” ပေါင်းစည်းမှုအချို့တွင် အကြွေးများ ဖုံးကွယ်နေကြောင်း တွေ့ရှိရပြီး **သန့်ရှင်းသော drop-in ပြောင်းလဲမှုများ မဟုတ်ပါ**။

- **`check:docs-sync` ကို နှစ်ကြိမ် run သည်** — `lint` job တွင် သီးခြား run ပြီး `check:docs-all` (`docs-sync-strict`) အတွင်းနှင့် husky pre-commit hook တွင် ထပ်မံ run သည်။ ✅ **ပြီးစီး** — သီးခြား `lint` invocation ကို ဖယ်ရှားပြီးဖြစ်သည်။
- **CVE scanning** — ❌ **သန့်ရှင်းစွာ ပေါင်းစည်း၍ မရပါ။** `audit:deps` သည် lockfile ငါးခုလုံးရှိ critical advisories နှင့် မပြည့်စုံသော audits များကို block လုပ်ပြီး၊ လက်ရှိမူဝါဒအရ high advisories များကို warnings အဖြစ် report လုပ်သည်။ `check:vuln-ratchet` (osv) သည် check-in လုပ်ထားသော baseline နှင့် နှိုင်းယှဉ်ရာတွင် _regression_ ဖြစ်မှသာ fail လုပ်ပြီး၊ လိုအပ်သည့်အခါ measurement မရှိခြင်းကိုလည်း reject လုပ်သည်။ အဓိပ္ပာယ်ဖွင့်ဆိုချက်များ မတူညီသောကြောင့် `audit:deps` ကို ဖယ်ရှားခြင်းသည် absolute critical gate နှင့် သီးခြား package audit receipts များကို ဆုံးရှုံးစေမည်။ နှစ်ခုလုံးကို ဆက်ထားပါ။

- **Complexity** — ✅ **ပြီးစီး** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ESLint walk တစ်ခုတည်းကို အသုံးပြုပြီး cyclomatic နှင့် max-lines baseline များ သီးခြားတည်ရှိစေရန် ruleId အလိုက် count လုပ်သည်။ တစ်ဦးချင်း `check:complexity` / `check:cognitive-complexity` များကို local `--update` အတွက် ဆက်ထားသည်။

#### `check-key-completeness` — key-set တူညီမှု gate

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, job `i18n-ui-coverage`)။
`src/i18n/messages/<locale>.json` တိုင်း၏ leaf key set ကို `en.json` နှင့် နှိုင်းယှဉ်ပြီး key ထည့်သည့်အချိန် မည်သည့်အချိန်ဖြစ်စေ မရှိသော သို့မဟုတ် အပိုဖြစ်သော leaf တစ်ခုခုရှိလျှင် fail ဖြစ်စေသည်။ `__MISSING__:` placeholder များကို ရှိသည်ဟု သတ်မှတ်သည် (၎င်းတို့၏အကြောင်းအရာကို ratio gate က ကိုင်တွယ်သည်)။ ၎င်းသည် diff အပေါ်အခြေခံသော/ရာခိုင်နှုန်းအပေါ်အခြေခံသော gate နှစ်ခုနှင့် လုံးဝဆန့်ကျင်ဘက်ဖြစ်သည်။ `check-ui-keys-coverage` သည် locale တစ်ခုစီအတွက် 80 % အနိမ့်ဆုံးသတ်မှတ်ချက်ကို စစ်ဆေးသည် (key ~13,000 ထဲမှ 43 ခု မရှိသော်လည်း 99.7 % အဖြစ် ဖတ်ရသည်)။ `check-new-key-coverage` က `en.json` ထဲသို့ PR က ထည့်သည့် key များကိုသာ အကဲဖြတ်သည်။ Locale batch တစ်ခုကို ၎င်း၏ branch ဖြတ်သည့်နေ့တွင်ရှိသော `en.json` မှ ထုတ်လုပ်ပြီး ရက်များစွာ ဘာသာပြန်နေစဉ် base တွင် key များ ဆက်လက်ထည့်သွင်းနေသည်။ batch PR ကိုယ်တိုင်က key မထည့်သဖြင့် sibling နှစ်ခုစလုံးသည် batch 1 (#13044) က locale ကိုးခုတွင် key 43 ခု လိုအပ်နေပြီး ရောက်လာချိန်နှင့် batch 2 (#13660) က locale ရှစ်ခုတွင် key 10 ခု လိုအပ်နေပြီး ရောက်လာချိန်တွင် တိတ်ဆိတ်နေခဲ့သည် (2026-09-15)။ အနီရောင်ရလဒ်ကို `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` ဖြင့် ပြင်ဆင်နိုင်သည်။ `extra` leaf ဆိုသည်မှာ source က ၎င်းကို ဖယ်ရှားလိုက်သည်ဟု ဆိုလိုပြီး `sync-ui-keys` က ၎င်းကို ဖယ်ရှားပစ်သည် (`--prune-extra` သည် default ဖြစ်သည်)။ `--warn` သည် fail မဖြစ်စေဘဲ report ပြုလုပ်သည်။

#### `check-new-key-coverage` — new-key i18n gate

`check-ui-value-drift` ၏ sibling ဖြစ်သည်။ ထို gate သည် English value တစ်ခုကို **ပြန်လည်ရေးသား** ထားသော်လည်း ၎င်း၏ ဘာသာပြန်များကို မပြင်ဆင်ထားခြင်းကို ဖမ်းယူသည်။ ဤ gate ကမူ English key တစ်ခုကို **ထည့်သွင်း** ထားသော်လည်း locale အချို့တွင် မရရှိသေးခြင်းကို ဖမ်းယူသည်။

`check-ui-keys-coverage` သည် ဤအမျိုးအစားကို မမြင်နိုင်ပါ။ ၎င်းသည် locale တစ်ခုစီအတွက် ရာခိုင်နှုန်းအနိမ့်ဆုံးသတ်မှတ်ချက်ကိုသာ စစ်ဆေးပြီး leaf ~13,000 ထဲမှ key 11 ခု မရှိလျှင် coverage သည် 99.9% အထိ ရှိနေသည်။ ဘာသာစကားတစ်ခုစီအတွက် ရာခိုင်နှုန်းတစ်ခုတည်းဖြင့် "ဤ feature ကို ဘာသာမပြန်ဘဲ ထုတ်လွှင့်လိုက်သည်" ကို ဖော်ပြ၍မရပါ။ Feature တစ်ခုလုံးသည် စာသားမပါဘဲ locale အသစ်တစ်ခုတွင် ပါဝင်လာနိုင်ပြီး ကိန်းဂဏန်းကို မည်သည့်အခါမျှ မရွှေ့စေနိုင်ပါ။

၎င်းက encode လုပ်ထားသော incident မှာ ဤသို့ဖြစ်သည်။ Orchestration Canvas ၏ Phase 3 သည် ထိုအချိန်တွင် ရှိပြီးသား locale 42 ခုအတွက် ၎င်း၏ key 11 ခုကို ဘာသာပြန်ခဲ့သည်။ နာရီအနည်းငယ်အကြာတွင် EU-language batch (#13044) က repo ကို locale 51 ခုအထိ တိုးမြှင့်ခဲ့ပြီး အသစ်ဝင်လာသော locale ကိုးခု (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) သည် ထို key များကို မရရှိခဲ့ပါ။ `deepMergeFallback` သည် မရှိသော key အတွက် English ကို အစားထိုးပေးသောကြောင့် failure mode သည် UI အလွတ်ဖြစ်ခြင်းမဟုတ်ဘဲ ဘာသာမပြန်ရသေးသော UI ဖြစ်ခဲ့သည် — အမှန်တကယ် ဖြစ်ပေါ်ခဲ့ပြီး ဒီဇိုင်းအရ တိတ်ဆိတ်နေခဲ့သည်။

၎င်း၏ sibling ကဲ့သို့ပင် ဤ gate သည် **diff-aware** ဖြစ်ပြီး merge base ရှိ English နှင့် working tree ရှိ English ကို နှိုင်းယှဉ်သည်။ ထို့ကြောင့် ယခင်ကတည်းက ရှိနေသော gap များကို မပြောင်းလဲဘဲ ထားနိုင်ပြီး ဖွင့်ရန် migration မလိုအပ်ခဲ့ပါ။

**`__MISSING__:<english>` marker သည် 2026-09-17 မှစ၍ ၎င်းကို မဖြည့်ဆည်းနိုင်တော့ပါ။** ယခင်က ၎င်းကို document လုပ်ထားသော deferral အဖြစ် အသုံးပြုခဲ့သည် — runtime သည် မှန်ကန်သော English သို့ fallback ပြုလုပ်သည် — သို့သော် 2026-09-16 တွင် feature PR ရှစ်ခုက key 61 ခုကို ထည့်သွင်းပြီး ဘာသာပြန်မည့်အစား locale 65 ခုစလုံးတွင် marker ကို ထည့်သွင်းခဲ့သည်။ ဤ gate က အားလုံးကို လက်ခံခဲ့ပြီး PR များကို မည်သည့်အရာကမျှ မတားဆီးခဲ့ပါ။ ထို့နောက် blocking real-translation ratio gate သည် release tip တွင် လူတိုင်းအတွက် fail ဖြစ်ခဲ့သည် (pt-BR 3.2 % > 2.5 % + 0.5)။ ယခု marker ကို မရှိသော ဘာသာပြန်မှုအဖြစ် အကဲဖြတ်သည်။ Release mode တွင်သာ 2026-11-13 မှစ၍ အလုပ်လုပ်သည်။ Feature PR တစ်ခုက `SKIP reason=pr-mode` ကို တွေ့ရပြီး release PR (`BASE_REF=origin/main`) တွင်မူ cycle က ထည့်သွင်းခဲ့သမျှ key တိုင်းကို gate က အကဲဖြတ်သည်။ အနီရောင်ရလဒ်ကို release refresh သို့မဟုတ် ဘာသာပြန် wave တွင် `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` ဖြင့် ပြင်ဆင်နိုင်သည်။ သို့မဟုတ် locale အားလုံးကို တပြိုင်နက်တည်း `npm run i18n:translate-new-keys` (`scripts/i18n/translate-new-keys.sh`, detached-safe ဖြစ်ပြီး `OMNIROUTE_TRANSLATION_*` env များမရှိပါက စတင်ရန် ငြင်းပယ်သည်) ဖြင့် လုပ်ဆောင်နိုင်သည်။ English အဖြစ် မပြောင်းလဲဘဲ ထားရမည့် key (pinned product/engine/flag name) သည် `scripts/i18n/untranslatable-keys.json` ထဲတွင် ပါဝင်ရမည်ဖြစ်ပြီး marker နောက်ကွယ်တွင် မထားရပါ။ `vi` သည် marker များကို လုံးဝပိတ်ပင်ထားသည် (`tests/unit/i18n-vi-completeness.test.ts`)။

#### `check-vitest-exclusions` — parked-test gate

`vitest.config.ts` ၏ `exclude` list ထဲရှိ file တစ်ခုသည် မလုပ်ဆောင်ရသော test တစ်ခုဖြစ်ပြီး tree ကို ဖတ်သူအတွက် coverage ရှိသကဲ့သို့ ထင်ရစေသည်။ `// #8618 — pre-existing failure; remove this exclusion when fixed` ဟူသော comment နောက်ကွယ်တွင် file 62 ခု စုဝေးလာခဲ့သည်။ Issue #8618 ကို 2026-08-11 တွင် ပိတ်ခဲ့သော်လည်း ၎င်းက ခြေရာခံထားသော list သည် entry 45 ခုမှ 62 ခုအထိ တိုးလာခဲ့ပြီး အသစ်ထည့်သွင်းသည့် entry တစ်ခုချင်းစီသည် ပိတ်သိမ်းပြီးသား issue ကို ညွှန်ပြသော comment ကို အမွေဆက်ခံခဲ့သည်။ List ကို နောက်ဆုံးတွင် file တစ်ခုချင်းစီတိုင်း တိုင်းတာခဲ့ချိန် (#13204) တွင် **62 ခုထဲမှ 51 ခုသည် source မပြောင်းလဲဘဲ လက်ရှိ tree အပေါ် pass ဖြစ်ခဲ့သည်**။

Gate သည် real file တစ်ခုသို့ resolve ဖြစ်သော exclusion တိုင်းအတွက် (a) tracking issue တစ်ခုကို ဖော်ပြရန်နှင့် (b) တိုင်းတာထားသော status ဖြင့် `config/quality/vitest-exclusions.json` ထဲတွင် ပါဝင်ရန် လိုအပ်သည်။ ထို့ကြောင့် ထည့်သွင်းမှုတစ်ခုသည် entry 60 ခုပါသော array ထဲသို့ နောက်ထပ်တစ်ကြောင်း ထည့်ခြင်းမဟုတ်ဘဲ သီးခြား file တစ်ခုထဲရှိ review ပြုလုပ်နိုင်သော diff ဖြစ်လာသည်။ Excluded test များကို တမင်တကာ ပြန်လည်မလုပ်ဆောင်ပါ။ ၎င်းသည် ~10 မိနစ် ကြာမြင့်ပြီး periodic job တွင်သာ သက်ဆိုင်သောကြောင့် ဖြစ်သည်။ Inventory တွင် တစ်ခုချင်းစီကို နောက်ဆုံးတိုင်းတာခဲ့သည့်အချိန်ကို မှတ်တမ်းတင်ထားသည်။
