## ဂိတ်စာရင်းနှင့် အကောင်အထည်ဖော်မှု ပရိုဖိုင်များ

### ကိုယ်စားလှယ်လောင်း ဝင်ခွင့်

CI နှင့် Quality Gates အလုပ်အသွားအလာတစ်ခုစီသည် တည်ငြိမ်သောစီရင်ချက်တစ်ခုစီကို ထုတ်လွှတ်သည်- `Gate / CI` နှင့် `Gate / Quality`။ ၎င်းတို့၏ ဗားရှင်းဖြင့် ဝင်ခွင့်မူဝါဒသည် လိုအပ်သည့် သို့မဟုတ် အကြံပေးချက်အဖြစ် အထက်ပိုင်းအလုပ်တိုင်းကို ရေတွက်ပါသည်။ သက်ဆိုင်ရာ လိုအပ်သော အလုပ်တစ်ခု အောင်မြင်ရမည်- ပျောက်ဆုံးနေသော၊ ပယ်ဖျက်လိုက်သည်၊ ကျော်သွားသည်၊ ဆိုင်းငံ့ထားပြီး မသိသောရလဒ်များ PASS မတည်ထောင်နိုင်ပါ။ မှန်ကန်သော docs-only သို့မဟုတ် catalog-only အမျိုးအစားခွဲခြင်းသည် ကုဒ်လမ်းကြောင်းကို အသုံးချ၍မရပေ။ သာမန် PR မူကြမ်းသည် လက်ခံထားသော ကိုယ်စားလှယ်မဟုတ်ပါ။ `hotfix` တံဆိပ်သည် သက်သေအထောက်အထား မလွတ်ပါ။

အလုပ်အသွားအလာ နှစ်ခုစလုံးသည် PRs main/release အကိုင်းအခက်များအဖြစ် ဖုံးအုပ်ထားပြီး `main` သို့ တွန်းပို့သည်၊ လူကိုယ်တိုင် ပေးပို့ခြင်းနှင့် အဖွဲ့ပေါင်းခြင်း အစီအစဉ်များ။ ရွေးချယ်မှု အပြည့်အစုံကို တွန်းပို့ခြင်း၊ ပေးပို့ခြင်းနှင့် ပေါင်းစည်းခြင်းတို့ကို လုပ်ဆောင်ပါ။ ယုံကြည်ရသော Mergify တန်းစီစာမူကြမ်းသည် သက်ဆိုင်ရာ `full-code`/`full-code-e2e` အလုပ်များကို လုပ်ဆောင်ပါသည်။ သာမာန် PRs ၎င်းတို့ကို ကျော်သွားသည်။ လူကိုယ်တိုင် ပေါင်းစည်းခြင်းမပြုမီ၊ ကိုယ်စားလှယ်လောင်း အတိအကျအပေါ် အပြည့်အဝပေးပို့မှုကို လုပ်ဆောင်ပါ။ `release/**` သို့ တွန်းပို့ခြင်းသည် ဤလုပ်ငန်းအသွားအလာများကို မစတင်ပါ။ Release-Green သည် သီးခြားခွဲထားသော အခြေစိုက်စခန်း (`docs/ops/RUNNER_BOX.md` → Hosted lane) ကို စောင့်ကြည့်သည်။ Forks နှင့် အဖွဲ့များ ပေါင်းစည်းထားသော အလုပ်များအတွက် လက်ခံထားသော အပြေးသမားများကို အသုံးပြုသည်၊ ဖြန့်ချိခြင်းမပြုမီ လုံလောက်သော လက်ခံနိုင်သော စွမ်းရည်ကို စစ်ဆေးရပါမည်။

သာမန် PR သည် အမြန်ရွေးချယ်မှုကို လုပ်ဆောင်သည်။ ဝင်ခွင့်မူဝါဒ၏ `full-code` နှင့် `full-code-e2e` လမ်းကြောများ (E2E၊ ပေါင်းစည်းမှု၊ ထုပ်ပိုးမှု ၊ Electron မီးခိုး ၊ Bun SQLite၊ ဂေဟစနစ် နှင့် ပရိုတိုကော ဖောက်သည်များ ) သည် ပေါင်းစည်းထားသော တန်းစီမူကြမ်း သို့မဟုတ် အပြည့်အဝ လည်ပတ်မှုတွင်သာ လုပ်ဆောင်သည်- `gh workflow run ci.yml --ref <branch>`.

JSON ပြေစာတစ်ခုစီသည် ထုတ်ယူထားသော SHA၊ အလုပ်အသွားအလာ လည်ပတ်မှုနှင့် ကြိုးစားမှုကို ခွဲခြားသတ်မှတ်သည်။ CLI သည် checkout/event SHA မကိုက်ညီမှုကို ငြင်းပယ်သည်။ အလုပ်အသွားအလာ စမ်းသပ်မှုများသည် စီရင်ချက်ချသည့်အလုပ်၏ `needs` စာရင်းနှင့် မူဝါဒအဖွဲ့ဝင်ခြင်းကို ချိတ်ဆက်ထားသောကြောင့် လမ်းအသစ် သို့မဟုတ် ဖယ်ရှားလိုက်သည့်လမ်းသည် တိတ်တဆိတ် ပျောက်ကွယ်သွားမည်မဟုတ်ပေ။ ပြေစာများသည် ထုတ်ဝေခြင်း၊ ဖြန့်ကျက်ခြင်း သို့မဟုတ် လက်ရှိအကြံပေးစကင်နာတစ်ခု၏ အတွင်းပိုင်းများကို ထုတ်ဝေခြင်းမဟုတ်ဘဲ ၎င်းတို့၏လုပ်ငန်းအသွားအလာကို အကျုံးဝင်ပါသည်။ ဌာနခွဲစည်းမျဥ်းများတွင် လိုအပ်သော သက်ဆိုင်ရာ စစ်ဆေးမှုများကို ပြုလုပ်ခြင်းသည် သီးခြား စီမံခန့်ခွဲရေး အပြောင်းအလဲ ဖြစ်သည်။ ၎င်းတို့၏ အလုပ်အကိုင်များကို သတ်မှတ်ခြင်းသည် အကိုင်းအခက်ကို မကာကွယ်ပေးပေ။

`API Route Typecheck` စုစည်းစီရင်ချက်များနှင့် ပြည်တွင်းလေ့လာသူ၏ တည်ငြိမ်ပရိုဖိုင် နှစ်ခုစလုံးအပြင် လွတ်လပ်သောအလုပ်အသွားအလာစစ်ဆေးချက်တစ်ခုဖြစ်သည်။ ကိုယ်စားလှယ်လောင်း အတိအကျအတွက် ၎င်း၏ရလဒ်ကို သီးခြားစစ်ဆေးပါ။ `.github/workflows/api-route-typecheck.yml` PRs တွင် `main` သို့မဟုတ် `release/**` သို့ လုပ်ဆောင်သည်၊၊ ဌာနခွဲမိသားစု၊ လူကိုယ်တိုင် ပေးပို့ခြင်းနှင့် `merge_group` အမျိုးအစား `checks_requested` ဖြစ်ရပ်များသို့ တွန်းပို့သည်။ ၎င်းတွင်လမ်းကြောင်း filter မရှိပါ။ `merge_group.head_sha` စစ်ဆေးရန် အဖွဲ့များကို ပေါင်းစည်းပါ။ အခြားဖြစ်ရပ်များ `github.sha` စစ်ဆေးပါ။ ဖြစ်ရပ်များအားလုံးသည် တူညီသော API ရောဂါရှာဖွေရေးဂိတ်နှင့် ဂိတ်ယူနစ်စစ်ဆေးမှုများကို အသုံးပြုသည်။ PR အခြေခံ ပြန်လည်ပစ်မှတ်များသည် စစ်ဆေးမှုအသစ်တစ်ခု တောင်းဆိုသည်။ body/title တည်းဖြတ်မှုများသည် လေ့လာရေးသီးသန့်အမည် `Admission not requested / API Route Typecheck` ကိုအသုံးပြုပြီး ဝင်ခွင့်စစ်ဆေးမှုကို အစားထိုး၍မရပါ။

### လက်ခံမှုလျော့ပါးရေးတွင် အထောက်အထားများ သိမ်းဆည်းထားသည်။

`scripts/quality/validate-release-acceptance.mjs` ထောက်ပံ့ပေးထားသော အစီအစဉ်နှင့် ၎င်း၏ဖော်ပြချက်များကို လျှော့ချပေးသည်။ ပြီးပြည့်စုံသော ပိုက်လိုင်းကို အကျုံးဝင်စေမည့် အစီအစဥ်ကို မသတ်မှတ်ထားပေ။ ၎င်းအစီအစဥ်သည် `VERIFIED` ဖြစ်သည့်အခါ၌ပင် ၎င်း၏အစီရင်ခံစာများသည် `releaseAcceptance: false` အတိအလင်းသတ်မှတ်ထားသည်။ `release-acceptance.yml` အလုပ်အသွားအလာသည် အစစ်အမှန်တည်ဆောက်မှု၊ ပက်ကေ့ချ်၊ ဘွတ်ဖိနပ် သို့မဟုတ် ပရိုမိုးရှင်းဖြတ်ပိုင်းများကို မဟုတ်ဘဲ အရိပ်တွဲများကို အသုံးပြုနေဆဲဖြစ်သည်။

CLI သည် ထိန်းသိမ်းထားသော အထောက်အထားများကို စစ်ဆေးရန် `--evidence-root` လိုအပ်သည်။ ဖိုင်များကို `<evidence-root>/<artifact_id>/<member>` အဖြစ် ဖြေရှင်းပြီး SHA-256 အဖြစ် hash လုပ်ထားသည်။ အထောက်အထားမရှိဘဲ PASS မှတ်တမ်းတစ်ခု၊ ပျောက်ဆုံးနေသော သို့မဟုတ် ပြောင်းလဲထားသော ဖိုင်၊ မလုံခြုံသောလမ်းကြောင်း သို့မဟုတ် symlink သည် အတည်ပြုခြင်းကို တားဆီးသည်။ ပျောက်ဆုံးနေသောဖိုင်များသည် အောင်မြင်သောမှတ်တမ်းအလွတ်များနှင့် ညီမျှသည်မဟုတ်ပါ။ လက်ရှိ SHA/run/attempt စစ်ဆေးမှုများသည် အမှီအခိုကင်းဆဲဖြစ်သည်- ကိုက်ညီသော bytes သည် ဟောင်းနွမ်းနေသောပြေစာကို ကယ်တင်နိုင်မည်မဟုတ်ပေ။ ဖိုင်ခိုင်မာမှုသည် စစ်မှန်သောစစ်မှန်မှု သို့မဟုတ် ပစ္စည်းပရိုမိုးရှင်း၏ သက်သေမဟုတ်ပါ။

### DAST အတည်ပြုထားသော CI တည်ဆောက်မှုကို အသုံးပြုသည်။

လိုအပ်သော `dast-smoke` CI အလုပ်သည် `build` ပြီးနောက် `.github/workflows/dast-smoke.yml` ခေါ်ဆိုသည်။ ၎င်းသည် ပံ့ပိုးထားသော လမ်းဆုံလမ်းခွ PRs၊ ဖြန့်ချိရေးပစ်မှတ် PRs နှင့် အဖွဲ့များကို ပေါင်းစည်းခြင်းအပါအဝင် တည်ဆောက်မှုကဲ့သို့တူညီသော code/draft ရွေးချယ်မှုကို လိုက်နာသည်။ ပျောက်ဆုံးနေသော၊ မအောင်မြင်သော၊ ပယ်ဖျက်ထားသည် သို့မဟုတ် မမျှော်လင့်ဘဲ ကျော်သွားခြင်းသည် DAST အလုပ်အား `Gate / CI` ပိတ်ဆို့သည်။ ပြန်သုံးနိုင်သော အလုပ်အသွားအလာတွင် သီးခြား PR/dispatch အစပျိုး မရှိပါ။ manual validation သည် CI၏ dispatch ကိုအသုံးပြုသောကြောင့် build နှင့် consumer သည် run တစ်ခုတည်းတွင်ရှိနေပါသည်။

`scripts/ci/next-build-provenance.mjs` ၎င်း၏ ကတ္တရာစေးချေဖျက်မှုဖြင့် နောက်တစ်ခု အပြည့်အစုံကို တံဆိပ်ခတ်ခြင်း၊ repository/event/runထုတ်လုပ်သူကြိုးစားမှု၊ head/base/checkout/tree၊ အလုပ်အသွားအလာ အထောက်အထားများ၊ သော့ခတ်ဖိုင်၊ အတိအကျ Node version/ABIပလပ်ဖောင်းနှင့် အစုအဝေး။ DAST မပြောင်းလဲနိုင်သော ရှေးဟောင်းပစ္စည်းကို ရွေးသည်။ ID ထံမှ `needs.build.outputs`၊ ဒေါင်းလုဒ်အနှစ်ချုပ်အတည်ပြုချက်လိုအပ်ပြီး ၎င်းကို သီးခြားခွဲထုတ်သည်။ ZIP ၎င်း၏ခွင့်ပြုထားသောစာရင်းဝင်အဖွဲ့ဝင်နှစ်ဦးကို မထုတ်ယူမီ ထုတ်လုပ်သူအချေအတင်နှင့် ဆန့်ကျင်သည်။ `scripts/ci/unpack-ci-build.py`. နောက်သစ်ပင်ကို မထုတ်ယူမီ မန်နီးဖက်စ်နှင့် ကတ္တရာစေးမှတ်တမ်းသည် လွတ်လပ်သော ထုတ်လုပ်သူ ရလဒ်များနှင့်လည်း ကိုက်ညီရပါမည်။ ၎င်းသည် နောက်ဆုံးအောင်မြင်သော ဌာနခွဲတည်ဆောက်မှုကို ဘယ်သောအခါမှ ရှာဖွေမည်မဟုတ်ပါ။ တစ်စိတ်တစ်ပိုင်း ပြန် run သည့်အခါ ထိုထုတ်လုပ်သူ ကြိုးပမ်းမှုကို ပြန်လည်အသုံးပြုနိုင်ပါသည်။ ID သွင်းအားစုများအားလုံး တူညီနေသေးသည်။ ပြေစာသည် ကြိုးစားမှုနှစ်ခုလုံးကို မှတ်တမ်းတင်ထားသည်။

သုံးစွဲသူသည် ဖတ်ရှုရန်သီးသန့်သိုလှောင်မှုခွင့်ပြုချက်ဖြင့် လက်ခံကျင်းပထားသည့် Linux အပြေးသမားတွင် ဆက်လက်ရှိနေမည်ဖြစ်ပြီး သိုလှောင်မှုလျှို့ဝှက်ချက်များမရှိပါ။ ၎င်းသည် ထုတ်လုပ်သူ၏ Node ဗားရှင်းအတိအကျကို ထည့်သွင်းပြီး CLI ကို `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` ဖြင့် စုစည်းသည်။ `scripts/build/standaloneInput.mjs` လွဲမှားနေသော သီးသန့်ဆာဗာကို ငြင်းပယ်သည် ။ ပုံမှန်ပြည်တွင်း CLI တည်ဆောက်မှုများသည် ၎င်းတို့၏ ရှိပြီးသား ဆုတ်ယုတ်မှုကို ထိန်းသိမ်းထားသည်။ ဆာဗာအဆင်သင့်၊ Schemathesis နှင့် promptfoo အားလုံးသည် မပြောင်းလဲသော 25 မိနစ်အလုပ်ကန့်သတ်ချက်အတွင်း အောင်မြင်ရပါမည်။ သက်သေပြပြေစာသည် အောင်မြင်သော DAST စကင်န်မဟုတ်ဘဲ ထည့်သွင်းအထောက်အထားနှင့် ဘိုက်များကို သက်သေပြသည်။ ပစ္စည်းများ သက်တမ်းကုန်ခြင်း၊ အပြေးသမား ပြတ်တောက်ခြင်း သို့မဟုတ် မအောင်မြင်သော စကင်နာသည် မပြည့်စုံသော သို့မဟုတ် မအောင်မြင်သော အထောက်အထားများ ရှိနေပါသည်။ အကြံပေးချက်ထုပ်ပိုးမှုမှတဆင့် PASS မဖြစ်လာနိုင်ပါ။

### UI ကွပ်မျက်မှုစွမ်းရည်

CI UI စာရင်းအပြည့်အစုံကို `test-vitest` matrix shards လေးခုအဖြစ် လုပ်ဆောင်ပြီး၊ တစ်ခုစီတွင် အလုပ်သမားနှစ်ဦး အများဆုံးပါဝင်ပြီး လက်ရှိ 15 မိနစ်အလုပ်နောက်ဆုံးရက်။ ပထမ shard သည် MCP/autoCombo Vitest suite ကိုလည်း လုပ်ဆောင်သည်။ လိုအပ်သောအလုပ်ရလဒ်သည် matrix ခြေထောက်တိုင်းကို အကျုံးဝင်သည်။ shard တစ်ခု၏ ပျက်ကွက်ခြင်း သို့မဟုတ် ပယ်ဖျက်ခြင်းသည် ကိုယ်စားလှယ်လောင်းဝင်ခွင့်ကို မသတ်မှတ်နိုင်ပါ။

ညစဉ်လေ့လာသူသည် UI shard တစ်ခုစီအတွက် သီးခြားပြေစာတစ်ခုစီအတွက် MCP ကွပ်မျက်ခြင်းအပါအဝင် သီးခြားအတိအကျ- ကိုယ်စားလှယ်လောင်းပြေစာကို ထိန်းသိမ်းထားသည်။ ပြေစာ၊ မှတ်တမ်းများနှင့် ကိုက်ညီသော အကောင်အထည်ဖော်မှု အထောက်အထား လေးခုစလုံး လိုအပ်ပါသည်။ Local `npm run test:vitest:ui` ပြီးပြည့်စုံသော suite ကို ရွေးချယ်ဆဲဖြစ်သည်။ `--shard` run သည် တစ်စိတ်တစ်ပိုင်းသာဓကဖြစ်သည်။

### ယူနစ်လွှမ်းခြုံစုဆောင်းခြင်း။

ယူနစ် ၁၂ ခုသည် ၎င်းတို့၏ လက်ရှိစမ်းသပ်လုပ်ဆောင်မှုအတွင်း V8 လွှမ်းခြုံမှုကို စုဆောင်းသည်။ အောင်မြင်သော shard တစ်ခုသည် အလယ်အလတ် Istanbul အစီရင်ခံစာကို မထုတ်ဘဲ မူရင်းဖိုင်များကို ချုံ့ရန် `scripts/ci/compact-v8-coverage.mjs` လုပ်ဆောင်သည်။ နောက်ဆုံးအကျုံးဝင်သည့်အလုပ်သည် ကိုယ်စားလှယ်လောင်း SHA၊ runtime၊ source root နှင့် data hashes ဆယ့်နှစ်ခုစလုံးကို စိစစ်ပြီး c8 ၏ သတင်းထောက်များနှင့် လက်ရှိလွှမ်းခြုံမှုအဆင့်များကို လုပ်ဆောင်သည်။ ထည့်သွင်းမှုများသည် c8 ၏ ကမ္ဘာလုံးဆိုင်ရာ ဖိုင်အမည်အစီအစဥ်ကို ထိန်းသိမ်းထားသည်။ per-shard ကြိုတင်ပေါင်းစည်းခြင်းသည် function/block လွှမ်းခြုံမှုအတွက် မလုံခြုံပါ။ ပျောက်ဆုံးနေသော၊ ပုံစံမမှန်သော သို့မဟုတ် သဟဇာတမဖြစ်သော အပိုင်းများသည် ဝင်ခွင့်မရပါ။ မအောင်မြင်သော စမ်းသပ်မှု shard များသည် အကြမ်းရောဂါရှာဖွေရေး အကျုံးဝင်မှုကို သီးခြားစီ ထိန်းသိမ်းထားသည်၊ နောက်ဆုံး ပေါင်းစည်းခြင်းသို့ မဝင်နိုင်ပါ။

### ယူနစ်လုပ်ဆောင်မှု တိုးတက်မှုပြေစာများ

မျှဝေထားသော `test:unit:ci:shard` အမိန့်သည် `primary`၊ `dashboard` နှင့် `serial` အဆင့်များကို `scripts/ci/unit-progress-reporter.mjs` မှတဆင့် မှတ်တမ်းတင်သည်။ ပုံမှန်စမ်းသပ်မှုအစီရင်ခံစာကို ဆက်လက်ရရှိနိုင်ပါသည်။ သီးခြား မက်တာဒေတာ-သပ်သပ် လက်ခံပြေစာသည် ဖိုင်တစ်ခုစီ၏ အစနှင့် ပြီးဆုံးမှုကို မှတ်တမ်းတင်ပြီး စက္ကန့် 30-ကြာ နှလုံးခုန်သံသည် အသက်ဝင်နေသေးသော ဖိုင်များနှင့် ၎င်းတို့၏ ကုန်ဆုံးသွားသော အချိန်တို့ကို စာရင်းပြုစုပါသည်။ ၎င်းသည် ခွင့်ပြုစာရင်းသွင်းထားသော လုပ်ဆောင်မှု မက်တာဒေတာကိုသာ မှတ်တမ်းတင်သည်။ စမ်းသပ်ဖော်ပြချက်များ၊ အထွက်၊ အမှားအယွင်းများနှင့် ပတ်ဝန်းကျင် အပြည့်အစုံကို အမှတ်စဉ်မထားပါ။

CI JSONL ဖိုင်များကို `unit-progress-ci-<run>-<attempt>-<shard>` အဖြစ် ထိန်းသိမ်းထားသည်။ အလုပ်အချိန်ကုန်ခြင်းသည် နောက်ပိုင်းတွင် အပ်လုဒ်လုပ်ခြင်းကို တားဆီးနိုင်သည်။ ထုတ်လွှတ်ပြီးသား နှလုံးခုန်သံများသည် ရောဂါရှာဖွေရေး အထောက်အထားများ ရှိနေသေးသည်။ ပျောက်ဆုံးနေသော နှလုံးခုန်သံများသည် ပိတ်ဆို့ခြင်း သို့မဟုတ် ရပ်တန့်ထားသော အပြေးသမား လုပ်ငန်းစဉ်ကို ထင်ဟပ်စေနိုင်သည်။ ဤလက်ခံဖြတ်ပိုင်းများသည် လက်ရှိစမ်းသပ်ရွေးချယ်မှု၊ ပေါင်းစပ်ငွေကြေး၊ နောက်ဆုံးရက်များနှင့် ထွက်ပေါက်အခြေအနေတို့ကို ထိန်းသိမ်းထားသည်။ ၎င်းတို့သည် ကိုယ်စားလှယ်လောင်း ဝင်ခွင့် စီရင်ချက် မဟုတ်ပါ။

### တန်းစီခြင်းကို ပေါင်းစည်းပါ။

`queue` အညွှန်းသည် PR တစ်ခုကို ပေါင်းစည်းထားသော တန်းစီ (`.mergify.yml`) သို့ ပေးပို့သည်။ Mergify သည် `mergify/merge-queue/` ဌာနခွဲတစ်ခုတွင် PR မူကြမ်းကိုဖွင့်သည်၊ CI ထိုနေရာတွင် ရွေးချယ်မှုအပြည့်အစုံကို လုပ်ဆောင်ပြီး `Gate / CI`၊ `Gate / Quality` နှင့် `Merge integrity (changelog + generated skills)` ကျော်သွားသောအခါ မူရင်း PR ပေါင်းစည်းသွားသည်။

Mergify သည် မူကြမ်း၏ဖော်ပြချက်တွင် ၎င်း၏ တန်းစီဇယားအနှစ်ချုပ်ကို ရေးသားသည်။ Body/title-only `pull_request` `edited` ဖြစ်ရပ်များသည် အမျိုးအစားခွဲခြင်း၊ စမ်းသပ်မှုမက်ထရစ်များ၊ သမာဓိပေါင်းစည်းခြင်း သို့မဟုတ် ဝင်ခွင့်စီရင်ချက်တို့ကို ပြန်လည်လုပ်ဆောင်ခြင်းမပြုပါနှင့်။ Observation-only check အမည်များသည် `Gate / CI` သို့မဟုတ် `Gate / Quality` ကို အစားထိုး၍မရပါ။ ပစ်မှတ်အခြေခံကို ပြောင်းလဲစေသော တည်းဖြတ်မှုတစ်ခုသည် အသစ်သော ကိုယ်စားလှယ်လောင်း အတည်ပြုချက်ကို တောင်းဆိုပါသည်။

ဇယားတစ်ခုပြီးနောက်၊ တွန်းအားသည် PR အမြဲတမ်း တောင်းခံမည်မဟုတ်ပါ။ ၎င်းကို `@mergifyio queue` တွင် မှတ်ချက်ပေးပါ။

### Static scan စာရင်း

ဗားရှင်းသတ်မှတ်ထားသော npm-alias စာရင်းနှင့် static-scan အဖွဲ့ဝင်မှုသည် `config/quality/gate-manifest.json` တွင် နေထိုင်သည်။ `package.json` နှင့် ဆန့်ကျင်သည့် ဇာတ်ညွှန်းအမည်များနှင့် တိကျသောအမိန့်တော်များကို အတည်ပြုရန် `npm run check:gate-manifest` ကိုဖွင့်ပါ။ ထပ်တိုးမှုများ၊ ဖယ်ရှားခြင်းနှင့် အမိန့်ပေးထားသော ဒရုန်းများသည် ဒေသတွင်းချိတ်နှင့် CI ရှိ အပြောင်းအလဲ-အမျိုးအစားခွဲခြားခြင်းအလုပ်များ နှစ်ခုစလုံးတွင် မအောင်မြင်ပါ။ နာမည်တူတစ်ခုသည် အလုပ်အသွားအလာအလုပ်၊ မက်ထရစ်စံနမူနာ သို့မဟုတ် စမ်းသပ်မှုကိစ္စမဟုတ်ပါ- ဤအရေအတွက်များကို လဲလှယ်နိုင်သောအဖြစ် မဖော်ပြရပါ။

၎င်းတို့ကို လုပ်ဆောင်ခြင်းမရှိဘဲ ရွေးချယ်ထားသော နာမည်တူများကို စစ်ဆေးရန် `npm run quality:scan -- --list` သို့မဟုတ် `npm run quality:scan:fast -- --list` အသုံးပြုပါ။ အပြေးသမားသည် npm entrypoint ကို ခေါ်ဆိုသည်၊ ထို့ကြောင့် ၎င်း၏ runtime (configured လုပ်ထားသည့် Bun အပါအဝင်) ကို ထိန်းသိမ်းထားသည်။ မန်နီးဖက်စ်သည် သီးခြားခေါ်ဆိုထားသည့်အတိုင်း အဆိုပါပရိုဖိုင်များအပြင်ဘက်တွင် နာမည်တူများကို မှတ်တမ်းတင်ပြီး ပြုပြင်ထိန်းသိမ်းမှုအမိန့်များကို ဖတ်သာစကင်န်ပရိုဖိုင်များတွင် တားမြစ်ထားသည်။

ဤပရိုဖိုင်များသည် static scan ကိုသာ အကျုံးဝင်ပါသည်။ ၎င်းတို့သည် ထုတ်ကုန်စစ်ဆေးမှုများ၊ အကျုံးဝင်မှု၊ ထုပ်ပိုးမှု၊ ပြင်ပစစ်ဆေးမှုများ သို့မဟုတ် ကိုယ်စားလှယ်လောင်း၏ အပြည့်အဝလက်ခံမှုကို အသိအမှတ်ပြုခြင်းမပြုပါ။ Workflow ဝင်ခွင့်သည် ချိတ်ဆက်ထားသော `config/quality/admission-policy.json` နှင့် `scripts/quality/admission-verdict.mjs` အသုံးပြုသည်။ ထုတ်ဝေသူ-လေ့လာသူ ပရိုဖိုင်များသည် သီးခြားကျန်ရှိနေသည်။ ၎င်းတို့၏ သက်ဆိုင်ရာ ချက်လက်မှတ်များနှင့် ပြေစာများကို လွတ်လပ်စွာ စစ်ဆေးပါ။ လေ့လာသူ၏ တည်ငြိမ်သော ညွှန်ကြားချက်များ အပြည့်အစုံကို `audit:deps`၊ ပြောင်းလဲမှု-စမ်းသပ်ရွေးချယ်မှုနှင့် ဘာသာပြန်စစ်ဆေးမှုများအပါအဝင် `config/quality/release-green-static-profile.json` တွင် ကြေငြာထားသည်။ loader သည် package.json နှင့် CI/Quality ကြေငြာချက်များကို စံနမူနာပြုထားသော npm ညွှန်ကြားချက်များကို တရားဝင်စေပါသည်။ အကြောင်းပြချက်များအဖြစ် shell တိုကင်များကို လုပ်ဆောင်မည့်အစား drift ကို ငြင်းပယ်သည်။ လိုအပ်သော စကင်နာ SKIP/INCOMPLETE အထွက်သည် PASS မတည်ထောင်နိုင်ပါ။ ပရိုဖိုင်သည် ၎င်း၏ ပြင်ပ ချန်လှပ်မှုများကို မှတ်တမ်းတင်ထားပြီး လက်ခံထားသော လွှမ်းခြုံမှု၊ စမ်းသပ်မှု မက်ထရစ်များ၊ ပက်ကေ့ခ်ျ သို့မဟုတ် အသုံးချမှု အထောက်အထားများကို အစားထိုးမထားပါ။ အောက်ဖော်ပြပါ စကားပြေစာရင်းသည် ဂိတ်တစ်ခု အမှန်တကယ်ထွက်ကြောင်း အထောက်အထားမဟုတ်ဘဲ ကိုးကားချက်ဖြစ်သည်။

Script များသည် `scripts/check/` (မူဝါဒတံခါးများ) နှင့် `scripts/quality/` (ratchet engine) အောက်တွင် နေထိုင်ပါသည်။ CI အမှန်တရား၏အရင်းအမြစ်သည် `.github/workflows/ci.yml` ဖြစ်သည်။

### ထုတ်ဝေ-အခြေခံစာရွက်စာတမ်းကျန်းမာရေး

`.github/workflows/i18n-base-health.yml` `main` နှင့် `release/v*` သို့ ရွေးချယ်ထားသော တွန်းပို့ပြီးနောက် နှင့် လူကိုယ်တိုင်ပေးပို့ခြင်းတွင် စာရွက်စာတမ်းကျန်းမာရေးကို စောင့်ကြည့်သည်။ ၎င်း၏စစ်ထုတ်မှုများသည် စာရွက်စာတမ်းပြုစုခြင်း၊ အမြစ် Markdown၊ `llm.txt`၊ ဘာသာပြန်ဆိုခြင်း state/configuration နှင့် သက်ဆိုင်ရာ i18n ကိရိယာတန်ဆာပလာများ ပါဝင်သည်။ `Published base documentation health` အလုပ်တစ်ခုတည်းက Ubuntu ကို လက်ခံကျင်းပပြီး ငါးမိနစ်စာ နောက်ဆုံးရက်ကို အသုံးပြုပါတယ်။ ၎င်းသည် ဖတ်ရှုခြင်းအတွက်သာ တရားဝင်မှုကို လုပ်ဆောင်ပြီး မှီခိုမှုထည့်သွင်းခြင်း၊ ဘာသာပြန်ခြင်း သို့မဟုတ် ပြည်နယ်မွေးစားခြင်းမရှိဘဲ ရောဂါရှာဖွေရေးပြေစာတစ်စောင်ကို ရေးပေးသည်။

`scripts/i18n/check-base-health.mjs` သုညအရင်းအမြစ်-hash၊ ပျောက်နေသော-ပစ်မှတ်၊ ပစ်မှတ်-hash၊ stale-translation နှင့် section-cache ကွဲလွဲမှုများ လိုအပ်သည်။ ၎င်းသည် လက်ရှိ core document/locale နယ်ပယ်နှင့် ၎င်း၏ မှတ်တမ်းတင်ထားသော သက်သေကိုလည်း စစ်ဆေးသည်။ မမှန်ကန်သော အကြောင်းအရာ၊ မပြည့်စုံသော လွှမ်းခြုံမှု သို့မဟုတ် အနှောက်အယှက်ဖြစ်စေသော စစ်ဆေးသူသည် `INCOMPLETE` ထုတ်လုပ်သည်။ အတည်ပြုထားသော drift သည် `FAIL` ထုတ်လုပ်သည်။ နှစ်ခုစလုံးသည် မအောင်မြင်သော ထွက်ပေါက်အခြေအနေကို ပြန်ပေးသည်။ ပြေစာသည် SHA၊ အလုပ်အသွားအလာ၊ လည်ပတ်မှုနှင့် ကြိုးစားမှုတို့နှင့် ဆက်စပ်နေပြီး `i18n-base-health-<sha>-<run>-<attempt>` အဖြစ် ထိန်းသိမ်းထားသည်။

ဤသည်မှာ ထုတ်ဝေမှုအခြေခံ၏ သီးခြားလွတ်လပ်သော လေ့လာတွေ့ရှိချက်ဖြစ်သည်။ ၎င်းသည် PR သို့မဟုတ် အဖွဲ့ပေါင်းစည်းခြင်းကိစ္စ၊ လိုအပ်သော PR စစ်ဆေးမှု၊ npm alias သို့မဟုတ် static-scan ပရိုဖိုင်အဖွဲ့ဝင်ကို မထည့်ပါ။ အရင်းခံ checker သည် အတန်းငါးခုလုံးကို absolute mode တွင် ပိတ်ဆို့ထားသည်။ သာမန် PR ပြင်ဆင်မှုသည် ဝင်ခွင့်နှင့် သီးခြားဖြစ်သည်။ အောင်မြင်စွာ အပ်လုဒ်လုပ်ခြင်းသည် မအောင်မြင်သော ကျန်းမာရေးရလဒ်ကို PASS အဖြစ်သို့ ပြောင်းလဲ၍မရပါ။

သာမန် PR တစ်ခုသည် `--baseline-evidence` မှထုတ်ပေးသော အခြေခံအစီရင်ခံစာနှင့်အတူ `--preflight` အသုံးပြုသည်။ ပြီးပြည့်စုံသောဘာသာပြန်မှတ်တမ်းနှင့် အမှန်တကယ်ပစ်မှတ်ဘိုက်များကို ထိုအတိအကျအခြေခံမှမပြောင်းလဲသည့်အခါတွင် အင်္ဂလိပ်ရင်းမြစ်တစ်ခုကို ဆိုင်းငံ့ထားနိုင်သည်။ ပစ်မှတ်အသစ် သို့မဟုတ် အပိုင်း-ကက်ရှ် မကိုက်ညီမှုများကို ပိတ်ဆို့ထားဆဲဖြစ်ပြီး မပြည့်စုံသော အထောက်အထားများသည် ပြင်ဆင်မှုကို အခွင့်အာဏာမပေးနိုင်ပါ။ အစီရင်ခံစာသည် `preparationPending` နှင့် `mergeReady` သီးခြားစီဖော်ပြသည်- အောင်မြင်သောပြင်ဆင်မှုသည် ဆိုင်းငံ့ထားသောဘာသာပြန်များကို ပေါင်းစည်းရန်အဆင်သင့်ဖြစ်စေမည်မဟုတ်ပါ။ ဝင်ခွင့်မပြုမီ ဖွဲ့စည်းထားသည့် ကိုယ်စားလှယ်လောင်းရှိ ထိခိုက်မိသောမှန်များကို ပြန်လည်စတင်ပါ။ ယုံကြည်ရသော Mergify တန်းစီကိုယ်စားလှယ်လောင်း၊ `merge_group`၊ အကိုင်းအခက်တွန်းပို့မှုများနှင့် လက်စွဲ CI လုပ်ဆောင်မှုများသည် `--warn` သို့မဟုတ် အမွေဆက်ခံ-ပျက်ကွက်မှုကို ခွင့်လွှတ်ခြင်းမရှိဘဲ အကြွင်းမဲ့စစ်ဆေးခြင်းကို အသုံးပြုပါသည်။ ပျောက်နေသောပစ်မှတ် hashes နှင့် ဖျက်လိုက်သော core ဖိုင်များဖြင့် လျှော့ချထားသော အတိုင်းအတာသည် အောင်မြင်သော လုံးဝစီရင်ချက်မထုတ်နိုင်ပါ။

#### ပေါက်ဖော် စာမေးပွဲတွေ မေ့သွားပြီ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ၏ အကြံပေးအဆင့်အဖြစ် လုပ်ဆောင်ပြီး စမ်းသပ်သက်ရောက်မှုမြေပုံနောက်ကွယ်ရှိ တင်သွင်းမှုဖြေရှင်းချက်ကို ပြန်လည်အသုံးပြုသည်။ ပြောင်းလဲထားသော ထုတ်လုပ်မှု module တစ်ခုစီအတွက်၊ လျှောက်ထားသူ၏စမ်းသပ်မှုအား ဆွဲယူတောင်းဆိုမှုကွာခြားမှုမှ ပျက်ပြယ်သွားသောအခါတွင် ၎င်းသည် တိကျသော `changed module/symbol -> static consumer -> candidate sibling test` ကွင်းဆက်များကို အစီရင်ခံပါသည်။ Markdown အနှစ်ချုပ်နှင့် JSON ရလဒ်အား ပိတ်ဆို့ခြင်းမပြုလုပ်မီ ချိန်ညှိခြင်းအတွက် `forgotten-sibling-tests` အလုပ်အသွားအလာကို ဆက်လက်ထိန်းသိမ်းထားသည်။

စည်ပိုင်းပြန်လည်တင်ပို့မှုနှင့် ရွေ့လျားတင်သွင်းမှုများသည် ကြည်လင်ပြတ်သားသောရောဂါရှာဖွေခြင်းသာဖြစ်သည်။ ပိတ်ဆို့ရှာဖွေမှုကို ဘယ်တော့မှ မဖန်တီးကြဘူး။ သုံးသပ်ထားသောခြွင်းချက်များသည် `config/quality/forgotten-sibling-allowlist.json` တွင်နေထိုင်သည်။ ဝင်ရောက်မှုတစ်ခုစီသည် စားသုံးသူနှင့် ကိုယ်စားလှယ်လောင်း စမ်းသပ်မှုအား အမည်ပေးကာ၊ တိကျသော ကျိုးကြောင်းဆီလျော်မှုတစ်ခုပေးကာ GitHub ပြဿနာကို လင့်ခ်ချိတ်ခြင်း သို့မဟုတ် တောင်းဆိုချက်ဆွဲရန် လိုအပ်သည်။ ပုံစံမမှန်သော ထည့်သွင်းမှုများ မအောင်မြင်ပါ။ ခြွင်းချက်များသည် ဖျက်လိုက်သော ကိုယ်စားလှယ်လောင်း စမ်းသပ်မှု သို့မဟုတ် `.skip`/`.todo` တို့ကို ပေါင်းထည့်သည့် ကွဲပြားမှုကို ဖိနှိပ်၍ မရပါ။ အခိုင်အမာပြောဆိုမှုအားနည်းခြင်းနှင့် အခြားမျက်နှာဖုံးစွပ်ခြင်းကို သီးခြား `check:test-masking` ဂိတ်က ပိုင်ဆိုင်ထားသည်။

#### စာရိုက်စစ်ဆေးသည့် ပရိုဂရမ်နှစ်ခုသည် ကွဲပြားစွာ အဖြေပေးသည်။

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) နှင့် `check:build-typecheck` မတူညီသောရွေးချယ်မှုများအောက်တွင် မတူညီသောပရိုဂရမ်များကို စုစည်းကြပြီး တူညီသောဖိုင်သည် တစ်ခုနှင့်တစ်ခုတွင် သန့်ရှင်းနိုင်ပြီး အခြားတစ်ခုတွင် အမှားအယွင်းများနှင့် ပြည့်နေပါသည်။

`tsconfig.build.json` သည် `"strict": false` သတ်မှတ်ပေးသည်၊ ထို့ကြောင့် `noImplicitAny` ပိတ်ထားသည်။ core config သည် တင်းကျပ်သောရွေးချယ်မှုများဖြင့် စုစည်းထားသော 27-ဖိုင်ခွင့်ပြုစာရင်းကိုစုစည်းပြီး entry ၏တင်သွင်းမှုဂရပ်တစ်ခုစီကိုလိုက်နာသောကြောင့် build program တွင်ဘယ်တော့မှမပေါ်သောဖိုင်များကိုထိုနေရာတွင်စစ်ဆေးနေဆဲဖြစ်သည်။

ဖိုင်ကို ရိုက်ထည့်ခြင်း ရှိ၊ မရှိ ဆုံးဖြတ်သည့်အခါ အကျိုးဆက်သည် အရေးကြီးသည်-**`check:build-typecheck` အောက်တွင် သုညရောဂါရှာဖွေခြင်းများသည် သုညကိုမဆိုလိုပါ။** . ဖိုင် ၂၆ ဖိုင်မှ `@ts-nocheck` ဖယ်ထုတ်ခြင်းတွင် ၎င်းတို့ထဲမှ ၂၃ ခုကို တည်ဆောက်မှုပရိုဂရမ်တွင် ရှင်းလင်းပြသခဲ့သည်။ အဲဒီအထဲက ဆယ့်ခြောက်ခုမှာ သွယ်ဝိုက်သော အမှားအယွင်း 120 လောက် ပေါ်နေပါတယ်။ ဖိုင်ကို clean မခေါ်ခင် နှစ်ခုလုံးကို စစ်ကြည့်ပါ။

#### `check-ui-value-drift` — stale-ဘာသာပြန်ဂိတ်

အခြားဂိတ်များ၏ တည်ဆောက်ပုံအရ မမြင်နိုင်သော i18n ဆုတ်ယုတ်မှုကို ဖမ်းစားသည်- အင်္ဂလိပ်တန်ဖိုးကို ပြန်လည်ပြင်ဆင်ပြီး _previous_ အင်္ဂလိပ်မှ ဆင်းသက်လာသော ဘာသာပြန်များသည် နောက်တွင်ရှိနေသောကြောင့် အင်္ဂလိပ်မဟုတ်သော အသုံးပြုသူများသည် စိတ်ချလက်ချ-စကားလုံးဖြင့် ယခုမှားနေသော ကော်ပီကို ဆက်လက်ဖတ်ရှုနေပါသည်။

ဒါက တကယ်ကို ပို့ပေးတာပါ။ `oauthModal.googleOAuthWarning` အကောင့်ဝင်ကူညီသူ ( Antigravity )#5203**ဒေသ ၄၃ ခုအနက် ၃၉ ခု** " URL အပြည့်အစုံကို ကော်ပီကူးပြီး အောက်တွင် ကူးထည့်ပါ" ဟု အော်ပရေတာများအား စာသား — က ဆက်လက်ပြောပြနေပါသည်။ အဘယ်ကြောင့်ဆိုသော် #8463 အထိ သတိမပြုမိခဲ့ပါ။

- `sync-ui-keys` backfills သော့များသာဖြစ်သည်။**ပျက်ကွက်** ဘယ်တော့မှ မဖြစ်ဘူး။**သိုးသိုး** ;
- `check-ui-keys-coverage` သည် သော့ _presence_ ကို ရေတွက်သည်၊ ထို့ကြောင့် ဟောင်းနွမ်းသော ဘာသာပြန်ဆိုမှု ရမှတ်သည် အကျုံးဝင်သည် ။
- `check-translation-drift` သည် `docs/i18n/<locale>/**.md` စာရွက်စာတမ်းကိုကြည့်၍ — ကို ဘယ်တော့မှ `src/i18n/messages/*.json` မဖတ်ပါ။ 2026-09 ခုနှစ်မှ ပြန်လည်စင့်ခ်လုပ်ချိန်မှစ၍ အလုပ် `docs-sync-strict` တွင် ပိတ်ဆို့ခြင်း- core doc → `npm run i18n:run -- --files=<doc>` (ကဏ္ဍအဆင့်၊ စျေးပေါ) ကို တည်းဖြတ်ပါ။

**အခြေအမြစ် ကျောထောက်နောက်ခံပြုထားခြင်း မဟုတ်ဘဲ ကွဲပြားစွာ သိရှိမှု။** ၎င်းသည် အလုပ်လုပ်သောသစ်ပင်နှင့် ပေါင်းစည်းထားသော အခြေခံတွင် `en.json` နှိုင်းယှဉ်သည်။ အင်္ဂလိပ်တန်ဖိုး ပြောင်းလဲသွားသော သော့တိုင်းအတွက်၊ မထိမခိုက်ရသေးသော ဘာသာပြန်ခြင်းကို ကိုင်ဆောင်ထားဆဲ မည်သည့်နေရာမဆို ဟောင်းနွမ်းနေပါသည်။ ဒါက တမင်တကာ**နဂိုရှိရင်းစွဲကြွေးမြီများကို ရပ်တန့်စေသည်။** — ကွဲပြားမှုသည် မည်သည့်အင်္ဂလိပ်စကားဟောင်းမှ နှစ်ရှည်လများ ဘာသာပြန်ခြင်းမှ ထွက်လာသည်ကို မဖော်ပြနိုင်သောကြောင့် ဂိတ်သည် လက်ရှိပြောင်းလဲမှုနှင့် ထိတွေ့မှုကိုသာ အကဲဖြတ်ပါသည်။ အခြားရွေးချယ်စရာ (သော့တစ်ခုစီ hash အခြေခံလိုင်း) သည် ~ 600 KB ထုတ်ပေးသည့်ဖိုင်တစ်ခု၊ 3 × သည် အကြီးဆုံးအခြေခံလိုင်းဖြစ်ပြီး i18n PR တိုင်းတွင် လည်ပတ်နေမည်ဖြစ်သည်။

ကျေနပ်စေရန် နည်းလမ်းနှစ်ခု

1. ထိခိုက်ထားသော ဘာသာပြန်များကို အပ်ဒိတ်လုပ်ပါ။ သို့မဟုတ်
2. ၎င်းတို့ကို `__MISSING__:<new english>` — သို့ သတ်မှတ်ပြီးနောက် ပြုပြင်ထားသော အင်္ဂလိပ် (`src/i18n/request.ts::deepMergeFallback`၊ #7258) နှင့် ဘာသာပြန်ခြင်းအတွက် သော့တန်းစီများကို လုပ်ဆောင်ပေးသည်။

ကြိုးတစ်ချောင်းရဲ့ ရင်ဘက်**အဓိပ္ပါယ်** ပြောင်းတယ်၊ ပိုကြိုက်တယ်။**သော့ကို အမည်ပြောင်းခြင်း။** - သော့အသစ်သည် ဟောင်းနွမ်းသောဘာသာပြန်ခြင်းကို အမွေဆက်ခံ၍မရပါ။ ဒါက #8463 သုံးတဲ့ ပုံစံပါ။

value-drift နှင့် new-key gates များသည် `scripts/i18n/resolve-ui-diff-base.mjs` မှ မပြောင်းလဲနိုင်သော နှိုင်းယှဉ်ချက်တစ်ခုကို မျှဝေပါသည်။ အလုပ်အသွားအလာသည် တူညီသောအခြေခံ၊ အခြေခံ-အစွန်အဖျားနှင့် ကိုယ်စားလှယ်လောင်း SHAs စစ်ဆေးချက်နှစ်ခုလုံးသို့ ဖြတ်သန်းသည်။ PR/base-retarget၊ push နှင့် ပေါင်းစည်းခြင်းများသည် ၎င်းတို့၏ event context ကို အသုံးပြုသည်။ ကိုယ်စားလှယ်လောင်းဌာနခွဲကို ပေးပို့ခြင်းတွင် ၎င်း၏တိကျသော PR သို့မဟုတ် တိကျပြတ်သားသော `i18n_base_sha` ထည့်သွင်းမှု လိုအပ်သည်။ ထည့်သွင်းခြင်းမရှိဘဲ `main` သို့မဟုတ် `release/vX.Y.Z` ကို ပေးပို့ခြင်း သို့မဟုတ် စောင့်ကြည့်လေ့လာရန် စီစဉ်ထားခြင်းသည် ၎င်း၏ပထမမိဘနှင့် နောက်ဆုံးကတိကဝတ်ကို နှိုင်းယှဉ်ပါသည်။ အမွေဆက်ခံ ဘာသာပြန်ကြွေးမြီအားလုံး၏ စာရင်းစစ်မဟုတ်ပါ။ ဒေသဆိုင်ရာ ဖိတ်ခေါ်ချက်သည် အထက်ဖော်ပြပါ `BASE_REF` ညွှန်ကြားချက်ကို တိကျပြတ်သားစွာ နှိုင်းယှဉ်မှု အခြေခံတစ်ခု လိုအပ်သည်။

ပျောက်ဆုံးနေသော သို့မဟုတ် မရှင်းလင်းသော နှိုင်းယှဉ်မှုအကြောင်းအရာ၊ ဖတ်မရသော သို့မဟုတ် မမှန်ကန်သော လိုအပ်သောကတ်တလောက်တစ်ခုနှင့် ပြောင်းလဲထားသော ကိုယ်စားလှယ်တစ်ဦးသည် `INCOMPLETE` ထွက်ကုဒ်ဖြင့် ထုတ်လုပ်သည်**၂** သတိပေးမုဒ်တွင် အပါအဝင်။ ကက်တလောက်ဖတ်သော `scripts/i18n/read-ui-catalog.mjs` သုံးပါ။ ဖတ်ရန် ပျက်ကွက်မှုများကို အရာဝတ္တုအလွတ်များဖြင့် အစားထိုးမထားပါ။ မရရှိနိုင်သော အခြေခံ သို့မဟုတ် မပြည့်စုံသော ထည့်သွင်းမှုသည် PASS မဖြစ်ပေါ်စေပါ။

**Tooling**

- `npm run quality:relax-baselines -- --pct 20 --note velocity_YYYY_MM_DD [--dry-run]` — တစ်ကြိမ်တည်း
  လျှော့ပေါ့ပေးသည့် လုပ်ဆောင်မှု (`scripts/quality/relax-baselines.mjs`) ဖြစ်ပြီး တူညီသော
  note ဖြင့် နှစ်ကြိမ် run လုပ်ရန် ငြင်းပယ်သည်။
- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` —
  CI တိုင်းတာသည့် နည်းလမ်းအတိုင်း ကိန်းဂဏန်းဆိုင်ရာ gate တိုင်းကို တိုင်းတာပြီး gate တစ်ခုချင်းစီအတွက်
  ကျန်ရှိသော headroom ကို ထုတ်ပြသည် (`scripts/quality/baseline-headroom.mjs`)။ ညစဉ်
  `baseline-headroom` job သည် workflow run summary တွင် ဇယားကို ထုတ်ပြန်ပြီး ၎င်း၏
  JSON/Markdown report ကို `baseline-headroom-<run_id>` အဖြစ် upload လုပ်ကာ ရက် 90 ကြာ
  ထိန်းသိမ်းထားသည်။ Warning နှင့် critical row များသည် ၎င်းတို့၏ cap ၏ 10% အတွင်း
  ရောက်နေသော သို့မဟုတ် cap ကို ကျော်လွန်ပြီးသား gate များကို ဖော်ပြသည်။ Budget များ
  အသုံးပြုခံနေရကြောင်း ကြိုတင်သတိပေးချက်အဖြစ် ဤ report များကို စစ်ဆေးပြီး ပြဿနာဖြစ်နေသော
  gate ၏ `_rebaseline_*` မှတ်ချက်များကို ကြည့်ရှုပါ။ ယခု job သည် အမြဲတမ်း issue တစ်ခုကို
  ဖန်တီးခြင်း သို့မဟုတ် update လုပ်ခြင်း မရှိတော့ပါ။ #12149 တွင် ယခင် report history ကို

**New-code mode (Clean-as-You-Code) — 2026-08-30 မှစ၍ PR fast-path အတွက်သာ**

`pull_request` event များတွင် `quality.yml` က `--base-ref <PR base SHA>` ကို
`check:file-size`၊ `check:complexity-ratchets` နှင့် `check:dead-code` သို့ ပေးပို့သည်။
`check:complexity-ratchets` နှင့် `check:dead-code` အတွက် gate သည် HEAD ကို merge-base နှင့်
**PR က ပြင်ဆင်ထားသော ဖိုင်များကိုသာ ကန့်သတ်၍** နှိုင်းယှဉ်သည်
(`scripts/check/newCodeMode.mjs`: merge-base ကို ယာယီ `git worktree` တစ်ခုတွင် ဖန်တီးထားပြီး၊
ESLint/knip ကို ထိုနေရာနှင့် HEAD နှစ်ခုလုံးတွင် run ကာ ဖိုင်တစ်ခုချင်းစီ၏ အရေအတွက်များကို
diff လုပ်သည်)-

- **ပိတ်ပင်ခြင်း** — PR က ၎င်းပြင်ဆင်ထားသော ဖိုင်များတွင် cyclomatic/cognitive ချိုးဖောက်မှုများ
  သို့မဟုတ် dead export များ ထည့်သွင်းခဲ့သည်
  (log ထဲရှိ `complexityNewCode=`၊ `cognitiveComplexityNewCode=`၊ `deadExportsNewCode=`);
- **အကြံပြုချက်** — ကမ္ဘာလုံးဆိုင်ရာ စုစုပေါင်းနှင့် အေးခဲထားသော အခြေခံမျဉ်းတို့ကို နှိုင်းယှဉ်ခြင်း ဖြစ်သည်။ အမွေဆက်ခံလာသော ကွာဟမှုကြောင့်
  အပြစ်မရှိသော PR ကို မည်သည့်အခါမျှ အနီရောင်အဖြစ် မသတ်မှတ်ပါ။ ယင်းကွာဟမှုကို ထုတ်ဝေမှု ပြန်လည်ညှိနှိုင်းချိန်တွင် ပြုပြင်ရန် ခြေရာခံထားပြီး
  headroom job က စောင့်ကြည့်သည်။

`check:file-size` သည် base ref ကို ၎င်း၏ကိုယ်ပိုင်စည်းမျဉ်းများအတိုင်း အသုံးပြုသည်
(`scripts/check/check-file-size.mjs`, #8522): tree ထဲရှိ source နှင့် test file တိုင်းကို
စစ်ဆေးပြီး PR base ရှိ ဖိုင်တစ်ခုချင်းစီ၏ စာကြောင်းအရေအတွက်ကို `git show` ဖြင့် ဖတ်ကာ၊
၎င်း၏ baseline ceiling (`frozen` / `testFrozen` သို့မဟုတ် baseline ပြင်ပရှိ ဖိုင်အတွက်
`cap` / `testCap`) နှင့် base size တို့အနက် ပိုကြီးသောတန်ဖိုးကို ကျော်လွန်သည်အထိ
ကြီးလာမှသာ ထိုဖိုင်ကို မအောင်မြင်စေသည်။ ထို့ကြောင့် base တွင် drift ဖြစ်ပြီးသား ဖိုင်တစ်ခုက
သက်ဆိုင်မှုမရှိသည့် PR တစ်ခုကို မည်သည့်အခါမျှ မအောင်မြင်စေပါ။

`check:boundary:ratchet` သည် ၎င်း၏ တစ်ခုတည်းသော ကိန်းဂဏန်းအပေါ် တူညီသည့် စည်းမျဉ်းကို အသုံးပြုသည်
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`)။ PR event များတွင်
`quality.yml` ၏ fast-gate များနှင့် `ci.yml` ၏ lint job နှစ်ခုစလုံးက PR base SHA ကို ပေးပို့ပြီး၊ base commit ကို
`git archive` export တစ်ခုမှ တိုင်းတာကာ PR ၏ `open-sse → src` edge အရေအတွက်သည်
`metrics.boundaryOpenSseToSrc` နှင့် base ရှိ အရေအတွက်တို့အနက် ပိုကြီးသည့်တန်ဖိုးကို ကျော်လွန်မှသာ
PR ကျရှုံးသည်။ သတ်မှတ်အမြင့်ဆုံးတန်ဖိုးထက် ကျော်လွန်နေသော base drift ကို (`base drift herdado`) အဖြစ် အစီရင်ခံသော်လည်း အပြစ်မရှိသော PR ကို မည်သည့်အခါမျှ အနီရောင်ဖြစ်စေမည်မဟုတ်ပါ။ push → main သည်
အကြွင်းမဲ့အမြင့်ဆုံးတန်ဖိုးကို ဆက်လက်ထိန်းသိမ်းပြီး၊ ဖြေရှင်း၍မရသော base SHA ဖြစ်ပါက သတိပေးချက်တစ်ခုနှင့်အတူ ထိုတန်ဖိုးကို ပြန်လည်အသုံးပြုသည်။

`workflow_dispatch` run များ၊ release-green sweep နှင့် nightly headroom job တို့တွင် PR base မရှိသဖြင့်
အကြွင်းမဲ့ (global) နှိုင်းယှဉ်မှုကို ဆက်လက်အသုံးပြုသည်။ Coverage၊ duplication နှင့် type-coverage တို့သည် လက်ရှိအချိန်တွင် global အဖြစ် ဆက်ရှိနေသည်
(၎င်းတို့၏ tool များက ဖိုင်တစ်ခုချင်းစီအလိုက် diff ကို ကုန်ကျစရိတ်နည်းနည်းဖြင့် မထုတ်ပေးနိုင်ပါ) — တူညီသည့် ကိုင်တွယ်မှုကို အသုံးပြုရန် အလားအလာရှိသည့် ကိုယ်စားလှယ်များဖြစ်သည်။

   `npm run quality:ratchet -- --update`၊ `check:file-size --update`၊

   `--update` ကို run ပါ — baseline အားလုံးသည် တိုင်းတာရရှိသည့်တန်ဖိုးအထိ လျော့ကျသွားမည်။
2. `quality-baseline.json` မှ `_policy` ကို ဖျက်ပါ (`--require-tighten` နှင့် nightly

3. Modularization ကြောင့် အကျိုးရှိခဲ့သည့်နေရာများတွင် တိုင်းတာရရှိသည့်တန်ဖိုးထက် ပိုတင်းကျပ်စွာ သတ်မှတ်ပါ — file-size `cap` ကို 1000
   (သို့မဟုတ် 800) သို့ ပြန်ထားခြင်း၊ coverage floor များကို +5 တိုးခြင်း၊ modularize လုပ်ထားသည့် package များအတွက် dead export ကို 0 သတ်မှတ်ခြင်း။

## Ratchet အခြေခံမျဉ်း (`quality-baseline.json`)

Ratchet အင်ဂျင် (`scripts/quality/check-quality-ratchet.mjs`) သည် `quality-baseline.json`
ကို ဖတ်ပြီး အသစ်စုဆောင်းထားသော `quality-metrics.json` နှင့် နှိုင်းယှဉ်သည်။ သတ်မှတ်ထားသော
epsilon ထက်ကျော်လွန်၍ နောက်ပြန်ဆုတ်သွားသည့် မည်သည့်မက်ထရစ်မဆို build ကို ကျရှုံးစေသည်။

လက်ရှိ ခြေရာခံထားသော မက်ထရစ်များ-

| မက်ထရစ်               | ဦးတည်ချက် | အဓိပ္ပာယ်                          |
| --------------------- | --------- | ---------------------------------- |
| `eslintWarnings`      | `down`    | ESLint သတိပေးချက်အရေအတွက် မတိုးရပါ |
| `coverage.statements` | `up`      | Statement coverage မကျဆင်းရပါ      |
| `coverage.lines`      | `up`      | Line coverage မကျဆင်းရပါ           |
| `coverage.functions`  | `up`      | Function coverage မကျဆင်းရပါ       |
| `coverage.branches`   | `up`      | Branch coverage မကျဆင်းရပါ         |

အမှန်တကယ် တိုးတက်မှုတစ်ခု ဖြစ်ပေါ်ပြီးနောက် အခြေခံမျဉ်းကို အပ်ဒိတ်လုပ်ရန်-

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` flag သည် လက်ရှိတိုင်းတာထားသော တန်ဖိုးများကို `quality-baseline.json` ထဲသို့ ရေးသားသည်။
မက်ထရစ်ကို တိုးတက်စေခဲ့သော ပြောင်းလဲမှုနှင့်အတူ ဤဖိုင်ကို commit လုပ်ပါ။ မက်ထရစ်တစ်ခုကို
တိုးတက်စေသော်လည်း အခြေခံမျဉ်းကို အပ်ဒိတ်မလုပ်ထားသော PR ကို `--require-tighten` က
ဖမ်းမိမည်ဖြစ်သည် (အဆင့် 6A.5၊ အကောင်အထည်ဖော်ရန် ကျန်ရှိနေသေးသည်)။

### CodeQL ratchet- ကိုယ်စားလှယ်လောင်း ဝင်ခွင့်နှင့် သိုလှောင်မှု စာရင်း

CI တိကျပြတ်သားသော မှီခိုမှုကွင်းဆက်တစ်ခုမှတစ်ဆင့် ကိုယ်စားလှယ်လောင်း CodeQL ဝင်ခွင့်ကို ပိုင်ဆိုင်သည်- `codeql-scan` `codeql.yml` တွင် လေးဘာသာစကားမက်ထရစ်ကို ခေါ်သည်၊ ထို့နောက် `codeql-admission` `node scripts/check/check-codeql-ratchet.mjs --candidate` လုပ်ဆောင်သည်။ `Gate / CI` ရလဒ်နှစ်ခုစလုံး လိုအပ်သည်။ အရည်အသွေးသည် ၎င်း၏ကိုယ်ပိုင် ဂဏန်းစစ်ဆေးမှုများကို ထိန်းသိမ်းထားသော်လည်း ထုတ်လုပ်သူ မပြီးဆုံးမီ စကင်နာကို မေးမြန်းခြင်းမပြုပါ။ `Gate / Quality` တစ်ခုတည်းသည် လျှောက်ထားသူ၏ ဝင်ခွင့် အပြည့်အစုံမဟုတ်ပါ။ CodeQL docs သီးသန့် ကိုယ်စားလှယ်လောင်းများအတွက် လိုအပ်ပါသည်။

`config/quality/codeql-admission-policy.json` ရှိ မူဝါဒသည် လုပ်ဆောင်ချက်များ၊ C/C++၊ JavaScript/TypeScript နှင့် Python၊ query suite မူရင်း၊ အဝေးထိန်း ခြိမ်းခြောက်မှု မော်ဒယ်နှင့် တည်ဆောက်မှုမုဒ်ကို ရွေးချယ်သည်။ ထုတ်လုပ်သူ preflight သည် ဆိုင်းငံ့ထားသော activation မှတ်တမ်းကို ငြင်းပယ်ပြီး တိကျပြတ်သားသော ပစ်မှတ်စာရင်းအပြင်ဘက်တွင် အကိုင်းအခက်များရှိသည်။ လက်ရှိပစ်မှတ်များသည် အဓိကဖြစ်ပြီး release/v3.8.54. စာချုပ်စမ်းသပ်မှုများသည် ဤကန့်သတ်စာရင်းနှင့် ပက်ကေ့ဂျ်ဗားရှင်းနှင့် ပြုပြင်ထိန်းသိမ်းမှုတွန်းအားကို နှိုင်းယှဉ်ပါ။ နောက်ထွက်ရှိမှုတွင် စတင်အသုံးပြုခြင်းကို ပြန်လည်သုံးသပ်ရန် လိုအပ်သည်။ CI၏ လက်ရှိပိုမိုကျယ်ပြန့်သောထုတ်လွှတ်မှု PR အစပျိုးမှုကို ဆက်လက်ထိန်းသိမ်းထားသော်လည်း မတိုင်းတာရသေးသော PASS ရယူမည့်အစား ထုတ်ယူခြင်းမပြုမီ ပစ်မှတ်က HOLD ကို အစီရင်ခံသည်။

matrix အလုပ်တစ်ခုစီသည် ၎င်း၏အမှန်တကယ် SARIF အပ်လုဒ် ID၊ ဘာသာစကား၊ အမျိုးအစား၊ ပြေးခြင်းနှင့် ကြိုးစားမှု၊ ခေါ်ဆိုသူအလုပ်အသွားအလာအထောက်အထား၊ ဖြစ်ရပ် ref/head/base/merge SHA နှင့် မူဝါဒ hash တို့ကို မှတ်တမ်းတင်ပါသည်။ မှီခိုနေသောအလုပ်သည် ဤလုပ်ငန်းလည်ပတ်မှု၏ပြေစာများကိုသာ ဒေါင်းလုဒ်လုပ်ကာ ရှေးဟောင်းပစ္စည်းအချေအတင်များကို အတည်ပြုသည်။ ၎င်းသည် အမျိုးအစား လေးခုစလုံး၊ အောင်မြင်သော ထုတ်လုပ်သူနှင့် အတိအကျ အပ်လုဒ်တစ်ခုစီကို အပြီးသတ်လုပ်ဆောင်ခြင်း လိုအပ်ပါသည်။ ၎င်းသည် ဌာနခွဲတစ်ခုပေါ်ရှိ နောက်ဆုံးခွဲခြမ်းစိတ်ဖြာမှုမဟုတ်ဘဲ API၏ sarif_id စစ်ထုတ်မှုကို အသုံးပြုသည်။ တစ်စိတ်တစ်ပိုင်း ပြန်လည်လုပ်ဆောင်မှုများသည် တူညီသောအပြေးနှင့် ကိုယ်စားလှယ်လောင်း၏ အစောပိုင်းကြိုးပမ်းမှုမှ အောင်မြင်သောအမျိုးအစားများကို ပြန်လည်အသုံးပြုနိုင်ပြီး ထုတ်လုပ်ရေးကြိုးပမ်းမှုကို ထိန်းသိမ်းထားနိုင်သည်၊ မအောင်မြင်သော လက်ရှိထုတ်လုပ်သူသည် ယခင်အစိမ်းရောင်အထောက်အထားများကို ပြန်သုံး၍မရပါ။

CodeQL လုပ်ဆောင်ချက်သည် လုပ်ဆောင်ခြင်းအတွက် စောင့်ဆိုင်းနေသော်လည်း ၎င်း၏ ပင်ထိုးထားသော အကောင်အထည်ဖော်မှုသည် အခြေအနေကို ဖတ်ရန် ပျက်ကွက်ခြင်း သို့မဟုတ် စောင့်ဆိုင်းမှု ကုန်ဆုံးပြီးနောက် သတိပေးပြီး ဆက်လက်လုပ်ဆောင်နိုင်သည်။ ထို့ကြောင့် ဝင်ခွင့်ကို ထပ်မံစစ်ဆေးပါသည်။ အမျိုးအစားများ ပျောက်ဆုံးနေခြင်း၊ ဆိုင်းငံ့ထားသော လုပ်ဆောင်ခြင်း၊ မအောင်မြင်သော သို့မဟုတ် ပယ်ဖျက်ထားသော အလုပ်များ၊ ဟောင်းနွမ်းနေသော အထောက်အထား၊ မပြည့်စုံသော မျက်နှာဖုံးစွပ်ခြင်း သို့မဟုတ် မရရှိနိုင်သော APIs HOLD နှင့် ထွက်ပေါက် 2 ကို ထုတ်လုပ်သည်။ သီးခြားလွတ်လပ်သော စကင်နာလုပ်ဆောင်မှုအသွားအလာအတွက် ပုံသေစောင့်ဆိုင်းခြင်းမရှိပါ။ မစကင်န်မထားသော PR သတိပေးချက်တစ်ခု 0 သို့ပြန်လာသောကြောင့် မဖြတ်သန်းနိုင်ပါ။ `metrics.codeqlAlerts.value` အပေါ်မှ တိုင်းတာသောရေတွက်သည် 1 မှ ထွက်သည်; အခြားဌာနခွဲ၏သတိပေးချက်များကို စုပ်ယူရန် အခြေခံမျဉ်းအား မမြှင့်တင်ပါ။ [အခြေအနေနှင့် ခွဲခြမ်းစိတ်ဖြာမှု ရှာဖွေမှုကို အပ်လုဒ်လုပ်ပါ](https://docs.github.com/en/rest/code-scanning/code-scanning) ။

ပြေစာတွင် အပ်လုဒ်နှင့် ခွဲခြမ်းစိတ်ဖြာခြင်း IDs၊ အမျိုးအစားများ၊ ကိရိယာဗားရှင်းများ၊ ref/SHA၊ အခြေခံလိုင်းနှင့် သတိပေးချက်နံပါတ်များကို မှတ်တမ်းတင်ထားသည်။ SARIF identity/result အရေအတွက်၊ အနိမ့်ဆုံး စည်းမျဉ်းအရေအတွက်များနှင့် တိကျသောသတိပေးချက် ဖြစ်ရပ်များသည် မဖြစ်မနေ ကျန်ရှိနေပါသည်။ လက်ခံခြင်းမပြုမီ PR/analysis အထောက်အထားများကို ပြန်လည်စစ်ဆေးပါသည်။ ဤစစ်ဆေးမှုများသည် ထုတ်ယူထားသော အရင်းအမြစ်ဖိုင်တိုင်း၏ စာရင်းတစ်ခုမဟုတ်ဘဲ အမျိုးအစားအလိုက် အကျုံးဝင်မှုကို တည်ဆောက်ပေးပါသည်။ C/C++ no-build ထုတ်ယူခြင်းတွင် ပရောဂျက်တည်ဆောက်စဉ်အတွင်း ထုတ်ပေးသည့်ကုဒ်များ မပါဝင်ပါ။ ရင်းမြစ်ကို ချန်လှပ်ထားမှုများသည် ပြန်လည်သုံးသပ်ရန် လိုအပ်ဆဲဖြစ်ပြီး ပံ့ပိုးသူ၏ ထည့်တွက်မှုသည် နှိုင်းယှဉ်နိုင်သော အတိအကျ အခြေခံအထောက်အထားများ လိုအပ်ပါသည်။

`codeql-maintenance.yml` တက်ကြွစွာထုတ်လွှတ်သော တွန်းအားစကင်ဖတ်စစ်ဆေးချက်များနှင့် PR/main ထုတ်လုပ်သူများကို မပွားဘဲ အပတ်စဉ်အချိန်ဇယားကို ပံ့ပိုးပေးပါသည်။ `nightly-codeql-inventory.yml` သိုလှောင်မှု ကျယ်ပြန့်သော အခြေခံလိုင်းအား `--strict-measurement` ဖြင့် သီးခြား ထားရှိကာ တိုင်းတာမှု မရရှိနိုင်သောအခါ ပျက်ကွက်မှုကို သိမ်းဆည်းထားသည်။ ဒေသတွင်း အမွေအနှစ်စုဆောင်းသူ၏ လှပသော ကျော်သွားမှုသည် ကိုယ်စားလှယ်လောင်း ဝင်ခွင့်မဟုတ်ပါ။ ကမ္ဘာလုံးဆိုင်ရာ အရေအတွက်ကို စိစစ်ပြီးနောက် တင်းကျပ်ခြင်းသည် ပြတ်သားသော `--update` တစ်ခုအဖြစ် ကျန်ရှိနေပါသည်။

ပုံသေသတ်မှတ်မှုအား စီစဉ်သတ်မှတ်ထားချိန်တွင် အဆင့်မြင့်လုပ်ငန်းအသွားအလာကို မထုတ်ဝေရပါမည်- GitHub ထိုပေါင်းစပ်မှုကို ငြင်းပယ်သည်။ ပြန်လည်သုံးသပ်ထားသော စီမံခန့်ခွဲရေးအကူးအပြောင်းကို ပြန်မဖတ်မချင်း ၎င်း၏မူကွဲမူဝါဒကို ဆိုင်းငံ့ထားဆဲဖြစ်သည်။ ထုတ်ဝေခြင်းမပြုမီ၊ အော်ပရေတာတစ်ခုသည် သိုလှောင်ရာနေရာ၊ head/base/tree၊ policy/patch/rollback ဟက်ရှ်များနှင့် တပ်ဆင်မှုအခြေအနေကို စောင့်ကြည့်လေ့လာသည်။ `node scripts/quality/codeql-producer.mjs verify-admin-readback` ပံ့ပိုးပေးထားသည့် မျှော်လင့်ထားသည့် နှင့် အမှန်တကယ် JSON မှတ်တမ်းများကို စစ်ဆေးသည်။ ၎င်းသည် အော်ပရေတာခွင့်ပြုချက် သို့မဟုတ် အသစ်ပြန်ဖတ်ခြင်းများကို ရယူခြင်းအတွက် အစားထိုးခြင်းမဟုတ်ဘဲ နည်းပညာဆိုင်ရာ အစောင့်အကြပ်တစ်ခုဖြစ်သည်။ PR တိုကင်သည် စီမံခန့်ခွဲခွင့်ကို ဘယ်သောအခါမှ မတောင်းဆိုပါ။ ဖြန့်ချိခြင်းနှင့် မည်သည့်စကင်နာပြောင်းလဲမှုမဆို သီးခြားဖတ်ရှုခြင်းအပြင် အစစ်အမှန် PR၊ လမ်းဆုံလမ်းခွနှင့် ပေါင်းစည်းခြင်းဆိုင်ရာ အထောက်အထားများ လိုအပ်ပါသည်။

Forks သည် လက်ခံထားသော အပြေးသမားများကို အသုံးပြုသည်၊ ဆက်ရှိနေသော အထောက်အထားများမပါဘဲ ငွေရှင်းရန်၊ ထုတ်လုပ်သူတွင် ပရောဂျက် install/build မရှိ၊ နှင့် အမွေဆက်ခံသော သိုလှောင်မှုလျှို့ဝှက်ချက်များ မရှိပေ။ GitHub ၎င်း၏လျှော့ချထားသော fork တိုကင်ဖြင့် pull_request ဖြစ်ရပ်အတွက် SARIF အပ်လုဒ်ကို ပံ့ပိုးပေးသည်။ ပထမအကြိမ် ပံ့ပိုးကူညီမှု အကောင်အထည်ဖော်မှု အတည်ပြုချက်သည် GitHub မူဝါဒတွင် ကျန်ရှိနေပါသည်။ စိတ်မချရသောကုဒ်ကို လုပ်ဆောင်ရန် pull_request_target ကို ဘယ်တော့မှ မသုံးပါနှင့်။ ရွှေ့ပြောင်းခြင်းမပြီးမီတွင် အမှန်တကယ် တိုကင်ခွင့်ပြုချက်များ၊ analysis_key နှင့် ထိန်းချုပ်ထားသော canary ရှိ အမျိုးအစားပတ်ဝန်းကျင်အားလုံးကို အတည်ပြုပါ။ [Fork အပ်လုဒ်စည်းမျဉ်းများ](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible) ၊ [ကွဲလွဲနေသော စနစ်ထည့်သွင်းမှုမုဒ်များ](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows) ။

**ထုတ်ပယ်မှုများသည် အော်ပရေတာ၏ခေါ်ဆိုမှု (Hard Rule #14)** — ထုတ်ပယ်ခြင်းဆိုင်ရာ မှတ်ချက်တွင် နည်းပညာဆိုင်ရာ ကျိုးကြောင်းဆီလျော်မှုကို မှတ်တမ်းတင်ခြင်းမရှိဘဲ CodeQL သတိပေးချက်ကို ဘယ်သောအခါမှ မပယ်ပါ- ရေစီးကြောင်း-ပရိုတိုကော လိုအပ်ချက်အတွက် `won't fix` ၊ စမ်းသပ်မှုတစ်ခုအတွက် `used in tests` ၊ သန့်စင်ဆေး CodeQL အတွက် `false positive` မမြင်နိုင် (ဥပမာ- `docs/security/ERROR_SANITIZATION.md`)။

### ဘေးကင်းရေး အတည်ပြုကိရိယာ

job သည် လူကိုယ်တိုင် ကြီးကြပ်ခြင်းမရှိဘဲ baseline များသို့ ရေးသားသောကြောင့် `verify-ratchet-bank.mjs` ကသာ
ထိုလုပ်ဆောင်ချက်ကို လက်ခံနိုင်စေသည်။ ၎င်းသည် `--update` ပြီးနောက် tree ကို `HEAD` နှင့် diff လုပ်ပြီး၊ ပြောင်းလဲမှုတိုင်းသည်
အောက်ပါအမျိုးအစားများထဲမှ တစ်ခုမဟုတ်ပါက **မည်သည့် commit မျှ မရှိမီ job ကို ရပ်တန့်ကာ**
PR လုံးဝ မဖွင့်ပါ-

- `frozen` / `testFrozen` numeric entry တစ်ခုကို **လျှော့ချခြင်း** သို့မဟုတ် **ဖယ်ရှားခြင်း**
- `complexity-baseline.json` → `count` ကို **လျှော့ချခြင်း**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ကို **လျှော့ချခြင်း**

အခြားမည်သည့်အရာမဆို မအောင်မြင်ပါ- ကိန်းဂဏန်းတစ်ခုကို မြှင့်တင်ခြင်း၊ entry တစ်ခုထည့်ခြင်း၊ `cap`/`testCap` ကို ပြောင်းလဲခြင်း သို့မဟုတ်
`_rebaseline_*` မှတ်စုတစ်ခုကို ဖျက်ခြင်း/ပြန်လည်ရေးသားခြင်း (ထိုမှတ်စုများသည် ceiling တစ်ခုစီ ရှိနေရသည့်အကြောင်းရင်းအတွက် audit trail ဖြစ်ပြီး
file entry များနှင့်အတူ တူညီသော `frozen` object ထဲတွင် သိမ်းဆည်းထားသည်)။ cap ကို မြှင့်တင်နိုင်သော bot သည် လက်ရှိအခြေအနေထက်
ပိုဆိုးမည်မှာ သေချာသည်။ Regression guard- `tests/unit/verify-ratchet-bank.test.ts`။

job သည် `release/*` သို့ မည်သည့်အခါမျှ push မလုပ်ပါ — လူတစ်ဦးက PR ကို merge လုပ်ရသောကြောင့် မှားယွင်းသည့် တိုင်းတာမှုတစ်ခုသည်
ပြန်လည်သုံးသပ်ခြင်းမရှိဘဲ အတည်မဖြစ်နိုင်ပါ။

## Allowlist မူဝါဒ

ယခင်ကတည်းက ရှိနေသော ချိုးဖောက်မှုများကြောင့် မအောင်မြင်နိုင်သည့် gate တိုင်းသည် အပြောင်းအလဲမရှိအောင် သတ်မှတ်ထားသော allowlist တစ်ခုကို အသုံးပြုသည်
(ဥပမာ၊ `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)။ မူဝါဒမှာ-

**မူလအကြောင်းရင်းကို ဖြေရှင်းပါ။ ချိုးဖောက်မှုသည် ယခင်ကတည်းက ရှိနေပြီး တူညီသော PR အတွင်း မပြင်ဆင်နိုင်သည့်အခါမှသာ allowlist ကို အသုံးပြုပါ။**

Allowlist တစ်ခုထဲသို့ entry တစ်ခု ထည့်သွင်းသည့်အခါ-

1. အကြောင်းပြချက်ပါသော comment တစ်ခု ထည့်သွင်းပါ။
2. ခြေရာခံ issue ကို ကိုးကားပါ (ဥပမာ၊ `// #3498 — Phase 2 feature, not yet implemented`)။
3. ချိုးဖောက်မှုကို ပြင်ဆင်သည့် PR တစ်ခုတည်းတွင်ပင် entry ကို ဖယ်ရှားပါ — လက်ရှိဖြစ်ပေါ်နေသော ချိုးဖောက်မှုကို မတားဆီးတော့သည့် ခေတ်မမီသော entry သည်လည်း ချို့ယွင်းချက်တစ်ခု ဖြစ်သည် (6A.3 stale-enforcement ကို အကောင်အထည်ဖော်ပြီးသည်နှင့် မည်သည့်ချိုးဖောက်မှုနှင့်မျှ မသက်ဆိုင်တော့သော allowlist entry ကြောင့် gate မအောင်မြင်ပါလိမ့်မည်)။

စမ်းသပ်မှုများကို ပိုမိုမြန်ဆန်စွာ အောင်မြင်စေရန် allowlist entry များကို **မထည့်ပါနှင့်**။ အစိမ်းရောင် gate တစ်ခုနှင့်အတူ ဆက်လက်ကြီးထွားနေသော allowlist တစ်ခုသည် အရည်အသွေးနှင့်ပတ်သက်၍ မှားယွင်းသော ယုံကြည်စိတ်ချမှုကို ဖြစ်စေသည်။

### သင်၏ PR တွင် gate တစ်ခု မအောင်မြင်သည့်အခါ

1. **Gate output ကို ဂရုတစိုက်ဖတ်ပါ** — မည်သည့်ဖိုင် သို့မဟုတ် symbol က စည်းမျဉ်းကို ချိုးဖောက်ခဲ့သည်ကို အတိအကျ ဖော်ပြပေးထားသည်။
2. **ချိုးဖောက်မှုကို ပြင်ဆင်ပါ** — gate အများစုသည် code မှန်ကန်သည်နှင့် အောင်မြင်သွားမည့် အတိအကျ ရလဒ်တူညီသော filesystem စစ်ဆေးမှုများ ဖြစ်သည်။
3. **ချိုးဖောက်မှုသည် ယခင်ကတည်းက ရှိနေခဲ့ပါက** (ဆိုလိုသည်မှာ သင်က စတင်ဖြစ်ပေါ်စေခဲ့ခြင်းမဟုတ်ဘဲ gate က ယခုမှ ၎င်းကို လွှမ်းခြုံစစ်ဆေးခြင်းဖြစ်ပါက)- အကြောင်းပြချက် comment နှင့် ခြေရာခံ issue တို့ပါဝင်သော allowlist entry တစ်ခု ထည့်သွင်းပါ။
4. **Gate သည် ratchet တစ်ခုဖြစ်ပါက** (coverage၊ ESLint warnings၊ duplication၊ complexity)- သင်၏ ပြောင်းလဲမှုကြောင့် metric ပိုဆိုးသွားခြင်း ဖြစ်သည်။ အခြေခံပြဿနာကို ပြင်ဆင်ပါ၊ သို့မဟုတ် ပြောင်းလဲမှုသည် ရည်ရွယ်ချက်ရှိပြီး metric ကျဆင်းမှုကို လက်ခံနိုင်ပါက (အလွန်ရှားပါးစွာ) `npm run quality:ratchet -- --update` ကို run ပါ — သို့သော် PR description တွင် အကြောင်းရင်းကို မှတ်တမ်းတင်ပါ။
5. **အကြံပြုချက်ပေးသည့် gate များ** (`continue-on-error: true`) သည် အချက်အလက်ပေးရန်သာ ဖြစ်သည် — ၎င်းတို့သည် merge လုပ်ခြင်းကို မတားဆီးသော်လည်း CI summary တွင် ပေါ်လာမည်ဖြစ်သည်။ သို့သော်လည်း ၎င်းတို့ကို ပြင်ဆင်ပါ။

## Gate အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `scripts/check/check-<name>.mjs` (သို့မဟုတ် `.ts`) ကို ဖန်တီးပါ။ မူဝါဒ gate များသည် 0/1 ဖြင့် ထွက်သည်။
   Ratchet ပုံစံ gate များသည် `collect-metrics.mjs` မှတစ်ဆင့် တိုင်းတာချက်တစ်ခုကို `quality-metrics.json` သို့ ထုတ်ပေးသည်။
2. `package.json` တွင် `"check:<name>": "node scripts/check/check-<name>.mjs"` ကို ထည့်သွင်းပြီး
   alias နှင့် ၎င်း၏ command အတိအကျကို `config/quality/gate-manifest.json` တွင် တစ်ပြိုင်တည်း ကိုက်ညီအောင် ပြင်ဆင်ပါ။
   ရှိပြီးသား validation alias တစ်ခုကို ပြောင်းလဲခြင်း သို့မဟုတ် ဖယ်ရှားခြင်း ပြုလုပ်သည့်အခါတွင်လည်း အလားတူ တစ်ပြိုင်တည်း ကိုက်ညီအောင် ပြင်ဆင်ပါ။
   `npm run check:gate-manifest` ကို run ပါ။ pre-commit hook နှင့် CI change classification တို့က
   ဤ contract ကို မဖြစ်မနေ လိုက်နာစေသည်။
3. `.github/workflows/ci.yml` အတွင်း သင့်လျော်သော job အောက်တွင် ၎င်းကို ချိတ်ဆက်ပါ
   (မူဝါဒ → `lint` သို့မဟုတ် `docs-sync-strict`; ratchet → `quality-gate`)။
4. ၎င်းတွင် ခွင့်ပြုစာရင်းတစ်ခု ပါဝင်ပါက ခေတ်မမီတော့သော entry များကို အလိုအလျောက် ရှာဖွေနိုင်စေရန်
   `scripts/check/lib/allowlist.mjs` မှ `reportStaleEntries()` ကို အသုံးပြုပါ။
5. gate ၏ ရှာဖွေစစ်ဆေးမှု logic ကို လွှမ်းခြုံသည့် စမ်းသပ်မှုတစ်ခုကို `tests/unit/build/` တွင် ရေးပါ။
6. ဤစာတမ်းကို အပ်ဒိတ်လုပ်ပါ (သက်ဆိုင်ရာ job ဇယားတွင် row တစ်ခု ထည့်ပါ)။

## Agent ကိရိယာများ- LSP-in-the-loop (ရွေးချယ်အသုံးပြုနိုင်)

CI gate များအပြင် OmniRoute တွင် **ရွေးချယ်အသုံးပြုနိုင်သော** `agent-lsp` scaffold
(project အဆင့် `.mcp.json`၊ Fase 7 Task 15) ပါရှိသည်။ coding agent များအတွက် TypeScript language server ကို ဖော်ထုတ်ပေးရန် `.mcp.json`
ကို ဖန်တီးပါ။ ထိုသို့ဖြင့် ၎င်းတို့သည် code မရေးမီ symbol များ /
diagnostic များကို ဖြေရှင်းနိုင်မည်ဖြစ်သည် — ၎င်းသည် မရှိသည့် symbol များကို ဖန်တီးမိခြင်းကြောင့် ဖြစ်သော error များကို အရင်းအမြစ်မှ လျှော့ချပေးသည့်
`typecheck:core` ၏ compile-before-claim တွဲဖက်တစ်ခုဖြစ်သည်။ ၎င်းကို ရည်ရွယ်ချက်ရှိရှိ
အလိုအလျောက် မတင်ထားပါ (MCP↔LSP bridge ကို သင်ကိုယ်တိုင် ရွေးချယ်ပြီး အတည်ပြုရမည်)။ ပျက်နေသော entry တစ်ခုသည်
ချိတ်ဆက်မှု error ကိုသာ log လုပ်ပြီး session များကို မည်သည့်အခါမျှ မပျက်စေပါ။

## ကျိုးကြောင်းညီညွတ်အောင် ပြန်လည်စီစဉ်ရန် ကျန်ရှိစာရင်း (ROI ပြန်လည်သုံးသပ်မှု — အဆင့် 9 လှိုင်း 3)

ဤစာရင်းကို 2026-06-17 တွင် `ci.yml` နှင့် တိုက်ဆိုင်စစ်ဆေးထားသည် (ယခင်ဗားရှင်းတွင်
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` တို့ မပါဝင်ခဲ့ပါ)။ တိုက်ဆိုင်စစ်ဆေးပြီးသော အစုကို
ROI ပြန်လည်သုံးသပ်ရာတွင် အောက်ပါ ကျိုးကြောင်းညီညွတ်အောင် ပြန်လည်စီစဉ်နိုင်မည့် အရာများကို
ဖော်ထုတ်နိုင်ခဲ့သည်။ **ပေါင်းစည်းမှုများသည် စက်ပိုင်းဆိုင်ရာ CI အပြောင်းအလဲများဖြစ်ပြီး၊
ပြောင်းလဲဖွင့်ခြင်း/ဖယ်ရှားခြင်းများသည် အော်ပရေတာအတွက် သီးသန့်ထားသည့် မူဝါဒဆိုင်ရာ ဆုံးဖြတ်ချက်များဖြစ်သည်။** အောက်ပါအရာများထဲမှ
မည်သည့်အရာကိုမျှ ယခုအချိန်အထိ အသုံးမချရသေးပါ။

**အထက်တွင်လည်း မမှတ်တမ်းတင်ထားသေးသော အရာများ** (အကြံပေးအဆင့်၊ အသုံးဝင်သော signal နည်း): `docs-lint` job (markdownlint + Vale၊ job တစ်ခုလုံး `continue-on-error`) နှင့် သီးခြား scanner workflow များဖြစ်သော `semgrep.yml` / `scorecard.yml` တို့ဖြစ်သည်။ CodeQL တွင် ယခု `Gate / CI` အောက်၌ မဖြစ်မနေလိုအပ်သော producer နှင့် လက်ခံခွင့် job များရှိပြီး အထက်ဖော်ပြပါ activation လိုအပ်ချက်များကို လိုက်နာရသည်။ `semgrepFindings: 0` သည် `quality-baseline.json` တွင် ရှိသော်လည်း `ci.yml` ရှိ ပိတ်ဆို့နိုင်သော ratchet နှင့် မချိတ်ဆက်ထားပါ — ယခုဤ metric တွင် တကယ်လိုက်နာစစ်ဆေးပေးသည့် လုပ်ငန်း မရှိသေးပါ။

### ပေါင်းစည်းခြင်း / ထပ်နေမှုဖယ်ရှားခြင်း (စက်ပိုင်းဆိုင်ရာ၊ အန္တရာယ်ပိုနည်း)

အရာတစ်ခုစီကို 2026-06-17 ရှိ အမှန်တကယ် အသုံးပြုနေသော gate အခြေအနေနှင့် တိုက်ဆိုင်အတည်ပြုထားသည် (ယုံကြည်သော်လည်း ပြန်လည်စစ်ဆေးသည်)။
"သိသာထင်ရှားသည့်" ပေါင်းစည်းမှုအချို့တွင် ဖုံးကွယ်နေသော နည်းပညာကြွေးမြီများ ရှိနေကြောင်း တွေ့ရှိခဲ့ရပြီး ၎င်းတို့သည် **တိုက်ရိုက်အစားထိုးအသုံးပြုနိုင်သည့် သန့်ရှင်းသော အပြောင်းအလဲများ မဟုတ်ပါ**။

- **`check:docs-sync` ကို နှစ်ကြိမ် လုပ်ဆောင်သည်** — `lint` job အတွင်း သီးခြားလုပ်ဆောင်ပြီး `check:docs-all` (`docs-sync-strict`) နှင့် husky pre-commit hook အတွင်း၌လည်း ထပ်မံလုပ်ဆောင်သည်။ ✅ **ပြီးပါပြီ** — သီးခြား `lint` ခေါ်ယူလုပ်ဆောင်မှုကို ဖယ်ရှားပြီးဖြစ်သည်။
- **CVE စစ်ဆေးခြင်း** — ❌ **သန့်ရှင်းသော ပေါင်းစည်းမှု မဟုတ်ပါ။** `audit:deps` သည် lockfile ငါးခုလုံးအတွက် အလွန်ပြင်းထန်သော သတိပေးချက်များနှင့် မပြည့်စုံသော audit များကို ပိတ်ဆို့ပြီး၊ လက်ရှိမူဝါဒအရ ပြင်းထန်မှုမြင့်သော သတိပေးချက်များကို warning အဖြစ် အစီရင်ခံသည်။ သို့သော် `check:vuln-ratchet` (osv) သည် repository ထဲသို့ ထည့်သွင်းထားသော baseline နှင့် နှိုင်းယှဉ်ရာတွင် _နောက်ဆုတ်မှု_ ရှိမှသာ ကျရှုံးပြီး၊ လိုအပ်သည့်အခါ တိုင်းတာချက် ပျောက်ဆုံးနေခြင်းကို ငြင်းပယ်သည်။ အဓိပ္ပာယ်ဖွင့်ဆိုမှုများ မတူညီပါ — `audit:deps` ကို ဖယ်ရှားပါက အလွန်ပြင်းထန်မှုအဆင့်အတွက် ပကတိ gate နှင့် သီးခြား package audit အထောက်အထားများ ဆုံးရှုံးသွားမည်ဖြစ်သည်။ နှစ်ခုလုံးကို ဆက်လက်ထားရှိပါ။
- **Cycle ရှာဖွေခြင်း** — ✅ **ပြီးပါပြီ** (#15159 G-01/G-02)။ ဤနေရာရှိ စာသားဟောင်းတွင် `check:cycles` ကို "အောင်မြင်နေသော၊ ရွေးချယ်ပြင်ဆင်ထားသည့်" gate ဟု ခေါ်ဆိုခဲ့ပြီး `check:circular-deps` (dpdm) က cycle 91 ခု အစီရင်ခံခဲ့သောကြောင့် ၎င်းကို ပိတ်ဆို့သည့် gate အဖြစ် ဆက်ထားရန် အကြောင်းပြခဲ့သည်။ ထိုအောင်မြင်မှုသည် **မှားယွင်းသော အောင်မြင်မှု** ဖြစ်သည်။ `check:cycles` သည် subdirectory 5 ခု (ဖိုင် 450 ခု) ကိုသာ စစ်ဆေးခဲ့ပြီး static `import|export … from` နှင့်သာ ကိုက်ညီစစ်ဆေးကာ `@/` နှင့် `@omniroute/open-sse/` specifier အားလုံးကို ဖယ်ထုတ်ခဲ့သည်။ ထို့ကြောင့် repository ကို လွှမ်းမိုးနေသော dynamic-import + alias cycle များကို မမြင်နိုင်ခဲ့ပါ။ ပြင်ဆင်ပြီးဖြစ်သည်။ ယခု gate သည် `src` + `open-sse` (ဖိုင် 5023 ခု) ကို လှည့်လည်စစ်ဆေးပြီး TypeScript AST မှ specifier များကို စုဆောင်းသည် (ထို့ကြောင့် `import("…")` ကို ထည့်တွက်သော်လည်း type-position ရှိ `typeof import("…")` ကို မထည့်တွက်ပါ)၊ ထို့အပြင် tsconfig `paths` ကိုလည်း ဖြေရှင်းသည်။ 0 ခုမဟုတ်ဘဲ cycle **14** ခုကို တွေ့ရှိသည်။ ယခင်ကတည်းကရှိနေသော cycle 14 ခုကို gate PR တစ်ခုအတွင်း မပြင်ဆင်နိုင်သောကြောင့် `check:cycles` သည် ယခု **ratchet** (`--ratchet`၊ `quality-baseline.json` ရှိ အများဆုံးကန့်သတ်ချက် `metrics.cycles.value = 14`၊ `direction: down`) ဖြစ်လာသည် — ၎င်းသည် မည်သည့် _နောက်ဆုတ်မှု_ ကိုမဆို ပိတ်ဆို့ပြီး အရေအတွက်သည် လျော့ကျရန်သာ ခွင့်ပြုသည်။ CI သည် `npm run check:cycles:ratchet` ကို လုပ်ဆောင်သည်။ တဖြည်းဖြည်း လျှော့ချဖြေရှင်းမှုကို **A-01** နှင့်အတူ ဆောင်ရွက်မည်။ `check:circular-deps` (dpdm) ကို ပိုမိုကျယ်ပြန့်သော ဒုတိယအမြင်အဖြစ် အကြံပြုအဆင့်တွင် ဆက်ထားမည်။
- **ရှုပ်ထွေးမှု** — ✅ **ပြီးပါပြီ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`)။ ESLint ဖြင့် တစ်ကြိမ်သာ လှည့်လည်စစ်ဆေးပြီး ruleId အလိုက် ရေတွက်သဖြင့် cyclomatic+max-lines နှင့် cognitive baseline များသည် သီးခြားလွတ်လပ်စွာ ရှိနေသည်။ `check:complexity` / `check:cognitive-complexity` တစ်ခုချင်းစီကို local `--update` အတွက် ဆက်လက်ထားရှိသည်။
- **`/api` မှားယွင်းဖန်တီးမှု တားဆီးခြင်း** — ✅ **ပြီးပါပြီ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`)။ `src/app/api` ကို FS inventory တစ်ကြိမ်သာ ပြုလုပ်ပြီး openapi-routes + docs-symbols တို့သည် သီးခြားစီ ဆက်လက်အစီရင်ခံသည်။ တစ်ခုချင်းစီကို local လုပ်ဆောင်မှုများအတွက် ဆက်လက်ထားရှိသည်။
- **`check:node-runtime` ကို job 11 ခုတွင် လုပ်ဆောင်သည်** — ⚠️ **ROI နည်းပါးသည်။** တစ်ခုစီသည် သီးခြား runner ဖြစ်ပြီး စစ်ဆေးမှုမှာ <1s သာ ကြာသည်။ စုစုပေါင်း ချွေတာနိုင်မှုမှာ ~10s ဖြစ်ပြီး၊ job တစ်ခုချင်းစီအတွက် ကုန်ကျစရိတ်နည်းသော အကာအကွယ်တစ်ခု ဆုံးရှုံးရမည်ဖြစ်သည်။ အပြောင်းအလဲကြောင့် ဖြစ်လာမည့် အရှုပ်အရှင်းနှင့် မတန်ပါ။
- **CI lint ရှိ `typecheck:noimplicit:core`** — ✅ **lint job မှ ဖယ်ရှားပြီးဖြစ်သည်** (ယခင်က အကြံပြုအဆင့် `continue-on-error` ဖြစ်သည်)။ ပိတ်ဆို့သည့် type မျက်နှာပြင်မှာ `typecheck:core` + `check:type-coverage` ဖြစ်သည်။ Local script ကို ဆက်လက်ထားရှိသည်။

### ပြောင်းလဲဖွင့်ရန် / ဆုံးဖြတ်ရန် (အော်ပရေတာမူဝါဒ)

- `check:openapi-security-tiers` (အကြံပြုအဆင့်) — ❌ **တိုက်ရိုက် ပြောင်းလဲဖွင့်၍ မရပါ။** ၎င်းသည် 0 ဖြင့် ထွက်သော်လည်း `LOCAL_ONLY_API_PREFIXES` အောက်ရှိ `traffic-inspector` route အချို့တွင် `x-loopback-only: true` annotation မရှိကြောင်း သတိပေးသည်။ ၎င်းကို မဖြစ်မနေလိုက်နာစေရန် ဦးစွာ ထို annotation များကို `openapi.yaml` သို့ ထည့်သွင်းရန် လိုအပ်သည်။
- `typecheck:noimplicit:core` (အကြံပြုအဆင့်) — ပိတ်ဆို့သည့် `check:type-coverage` ratchet က အများစုကို လွှမ်းခြုံပြီးဖြစ်သည်။ ratchet အဖြစ် ပြောင်းလဲဖွင့်ပါ သို့မဟုတ် ထပ်နေသော ဒုတိယ `tsc` pass ကို ဖယ်ရှားပါ။
