ဤစာတမ်းသည် OmniRoute ရှိ CI အရည်အသွေးဂိတ်အားလုံးအတွက် အတည်ပြုကိုးကားရမည့် မူရင်းရင်းမြစ်ဖြစ်သည်။

ratchet baseline သို့မဟုတ် pass/fail policy ကို အသုံးပြုခြင်းရှိမရှိနှင့် build ကို ပိတ်ဆို့ခြင်းရှိမရှိ သို့မဟုတ် အကြံပြုချက်အဖြစ်သာ ရှိမရှိတို့ကို ဖော်ပြထားသည်။

အကျဉ်းချုပ်နှင့် allowlist policy အတွက် `AGENTS.md` ရှိ "Quality Gates & Ratchets" အပိုင်းကို
ကြည့်ပါ။ တူညီသည့်စနစ်၏ အရေးပါသော အကဲဖြတ်ချက်၊ ရင့်ကျက်မှုအဆင့်သတ်မှတ်ချက်နှင့် tool တစ်ခုတည်းအပေါ် မမှီခိုသည့်
ပြန်လည်အကောင်အထည်ဖော်ရေးအစီအစဉ်အတွက်
[Quality Gate Playbook](../ops/QUALITY_GATE_PLAYBOOK.md) ကို ကြည့်ပါ။

## Gate စာရင်းနှင့် လုပ်ဆောင်မှု ပရိုဖိုင်များ

### Candidate လက်ခံခြင်း

CI နှင့် Quality Gates workflow တစ်ခုစီသည် တည်ငြိမ်သော ဆုံးဖြတ်ချက်တစ်ခုကို ထုတ်ပေးသည်- `Gate / CI` နှင့်
`Gate / Quality`။ ၎င်းတို့၏ ဗားရှင်းသတ်မှတ်ထားသော လက်ခံမှုမူဝါဒတွင် upstream job တစ်ခုစီကို
မဖြစ်မနေလိုအပ်သော သို့မဟုတ် အကြံပြုအဆင့်အဖြစ် စာရင်းပြုစုထားသည်။ သက်ဆိုင်သော မဖြစ်မနေလိုအပ်သည့် job သည် အောင်မြင်ရမည်-
ပျောက်ဆုံးနေခြင်း၊ ပယ်ဖျက်ထားခြင်း၊ ကျော်ထားခြင်း၊ ဆိုင်းငံ့ထားခြင်းနှင့် အမည်မသိရလဒ်များဖြင့် PASS ဟု သတ်မှတ်၍မရပါ။ အကျုံးဝင်သော
docs-only သို့မဟုတ် catalog-only အမျိုးအစားခွဲခြားမှုသည် code lane တစ်ခုကို မသက်ဆိုင်စေနိုင်သည်၊
draft PR ကိုမူ လက်ခံနိုင်သော candidate အဖြစ် မသတ်မှတ်ပါ။ `hotfix` label တစ်ခုသည် အထောက်အထားလိုအပ်ချက်ကို မပယ်ဖျက်ပေးပါ။

Workflow နှစ်ခုစလုံးသည် main/release branch များသို့ ဝင်လာသော PR များ၊ `main` သို့ push များ၊ manual dispatch
နှင့် merge-group event များကို လွှမ်းခြုံသည်။ Push၊ dispatch နှင့် merge-group တို့သည် ရွေးချယ်မှုအပြည့်အစုံကို လုပ်ဆောင်သည်။
`release/**` သို့ push များက ၎င်းတို့ကို စတင်မလုပ်ဆောင်ပါ (2026-10-18)- ပြောင်းလဲမှုတစ်ခုစီသည် ၎င်း၏ PR တွင် matrix ကို
လုပ်ဆောင်ပြီးဖြစ်ကာ ပေါင်းစည်းထားသော ပေါင်းစပ်ရလဒ်သည် Release-Green ၏ တာဝန်ဖြစ်သည်
(`docs/ops/RUNNER_BOX.md` → Hosted lane)။ Fork များနှင့် merge group များသည် ပုံမှန်အားဖြင့် self-hosted
runner များကို ရွေးချယ်မည့် job များအတွက် hosted runner များကို အသုံးပြုသည်။ rollout မလုပ်မီ
လုံလောက်သော hosted capacity ရှိကြောင်း စစ်ဆေးအတည်ပြုရမည်။

JSON receipt တစ်ခုစီသည် checkout လုပ်ထားသော SHA၊ workflow run နှင့် attempt ကို သတ်မှတ်ဖော်ပြသည်။
CLI သည် checkout/event SHA မကိုက်ညီမှုကို ငြင်းပယ်သည်။ Workflow test များသည် policy membership ကို
verdict job ၏ `needs` စာရင်းနှင့် ချိတ်ဆက်ထားသောကြောင့် lane အသစ်တစ်ခု သို့မဟုတ် ဖယ်ရှားထားသော lane တစ်ခုသည်
တိတ်တဆိတ် ပျောက်ကွယ်သွားနိုင်မည်မဟုတ်ပါ။ အထောက်အထားမှတ်တမ်းများသည် ၎င်းတို့၏ ကိုယ်ပိုင် workflow ကိုသာ အကျုံးဝင်ပြီး publication၊ deployment သို့မဟုတ် လက်ရှိ advisory scanner တစ်ခု၏ အတွင်းပိုင်းလုပ်ဆောင်ချက်များကို အကျုံးမဝင်ပါ။ သက်ဆိုင်ရာ စစ်ဆေးမှုများကို branch rules များတွင် မဖြစ်မနေလိုအပ်ချက်အဖြစ် သတ်မှတ်ခြင်းသည် သီးခြား စီမံခန့်ခွဲမှုဆိုင်ရာ ပြောင်းလဲမှုတစ်ခုဖြစ်သည်။ ၎င်းတို့၏ job များကို သတ်မှတ်ရုံဖြင့် branch တစ်ခုကို ကာကွယ်ပေးမည်မဟုတ်ပါ။

`API Route Typecheck` သည် စုပေါင်းဆုံးဖြတ်ချက်နှစ်ခုလုံးနှင့် local full observer ၏ static profile တို့၏ ပြင်ပတွင်ရှိသော သီးခြား workflow စစ်ဆေးမှုတစ်ခုဖြစ်သည်။ အတိအကျ candidate အတွက် ၎င်း၏ရလဒ်ကို သီးခြားစစ်ဆေးပါ။ `.github/workflows/api-route-typecheck.yml` သည် `main` သို့မဟုတ် `release/**` သို့ ဝင်ရောက်မည့် PR များ၊ ထို branch မိသားစုနှစ်ခုထဲမှ တစ်ခုခုသို့ push လုပ်မှုများနှင့် manual dispatch တို့တွင် အလုပ်လုပ်သည်။ ၎င်းတွင် path filter မရှိပါ။ PR base ကို retarget လုပ်ခြင်းသည် စစ်ဆေးမှုအသစ်တစ်ခုကို တောင်းဆိုသည်။ body/title ပြင်ဆင်မှုများသည် observation-only အမည်ဖြစ်သည့် `Admission not requested / API Route Typecheck` ကို အသုံးပြုပြီး admission စစ်ဆေးမှုကို အစားမထိုးနိုင်ပါ။ Workflow သည် merge-group trigger တစ်ခုကို ကြေညာထားခြင်းမရှိပါ။ ဤစစ်ဆေးမှုကို မဖြစ်မနေလိုအပ်သည့် merge-queue rollout မည်သည့်အရာမဆို ထို event အတွက် ၎င်း၏ execution ကို ဦးစွာ ထူထောင်ရမည်။

### UI လုပ်ဆောင်မှုစွမ်းရည်

CI သည် UI စာရင်းအပြည့်အစုံကို `test-vitest` matrix shard လေးခုအဖြစ် လုပ်ဆောင်ပြီး တစ်ခုစီတွင် အများဆုံး
worker နှစ်ခုနှင့် ရှိပြီးသား 15 မိနစ် job deadline ကို အသုံးပြုသည်။ ပထမ shard သည်
MCP/autoCombo Vitest suite ကိုလည်း လုပ်ဆောင်သည်။ မဖြစ်မနေလိုအပ်သော job ရလဒ်သည် matrix leg အားလုံးကို
လွှမ်းခြုံသည်။ Shard တစ်ခု ပျက်ကွက်ခြင်း သို့မဟုတ် ပယ်ဖျက်ခြင်းဖြင့် candidate လက်ခံမှုကို သတ်မှတ်၍မရပါ။

Nightly observer သည် UI shard တစ်ခုစီအတွက် သီးခြား exact-candidate receipt တစ်ခုကို ဆက်လက်ထိန်းသိမ်းထားပြီး
ပထမ receipt တွင် MCP လုပ်ဆောင်မှုကိုပါ ထည့်သွင်းထားသည်။ Receipt လေးခုစလုံး၊ log များနှင့် ကိုက်ညီသော
execution identity များအားလုံး လိုအပ်သည်။ Local `npm run test:vitest:ui` သည် suite အပြည့်အစုံကို
ဆက်လက်ရွေးချယ်သည်။ `--shard` run တစ်ခုတည်းသည် တစ်စိတ်တစ်ပိုင်း အထောက်အထားသာဖြစ်သည်။

### Unit coverage စုဆောင်းခြင်း

Unit shard ဆယ့်နှစ်ခုသည် ၎င်းတို့၏ ရှိပြီးသား test လုပ်ဆောင်မှုအတွင်း V8 coverage ကို စုဆောင်းသည်။ အောင်မြင်သော
shard တစ်ခုသည် ကြားခံ Istanbul report မထုတ်လုပ်ဘဲ မူရင်းဖိုင်များကို ချုံ့ရန်
`scripts/ci/compact-v8-coverage.mjs` ကို လုပ်ဆောင်သည်။ နောက်ဆုံး Coverage job သည် manifest ဆယ့်နှစ်ခုစလုံးကို
candidate SHA၊ runtime၊ source root နှင့် data hash များနှင့် တိုက်ဆိုင်စစ်ဆေးပြီးနောက် c8 ၏ reporter များနှင့်
ရှိပြီးသား coverage threshold များကို လုပ်ဆောင်သည်။ Input များသည် c8 ၏ global filename အစီအစဉ်ကို
ဆက်လက်ထိန်းသိမ်းထားသည်။ Function/block coverage ရောနှောထားသောအခါ shard တစ်ခုချင်းအလိုက် ကြိုတင်ပေါင်းစည်းခြင်းသည်
မလုံခြုံပါ။ ပျောက်ဆုံးနေသော၊ ပုံစံမမှန်သော သို့မဟုတ် ကိုက်ညီမှုမရှိသော shard များသည် လက်ခံမှုကို ပျက်ကွက်စေသည်။
ပျက်ကွက်သော test shard များ၏ raw diagnostic coverage ကို သီးခြားထိန်းသိမ်းထားပြီး ၎င်းကို နောက်ဆုံးပေါင်းစည်းမှုတွင်
ထည့်သွင်း၍မရပါ။

### Unit လုပ်ဆောင်မှုတိုးတက်ရေး မှတ်တမ်းများ

မျှဝေအသုံးပြုသည့် `test:unit:ci:shard` command သည် `scripts/ci/unit-progress-reporter.mjs` မှတစ်ဆင့် `primary`, `dashboard` နှင့် `serial` အဆင့်များကို မှတ်တမ်းတင်သည်။ ပုံမှန်စမ်းသပ်မှုအစီရင်ခံစာကို ဆက်လက်ရရှိနိုင်သည်။ မက်တာဒေတာသီးသန့် မှတ်တမ်းတစ်ခုက ဖိုင်တစ်ခုစီ၏ စတင်ချိန်နှင့် ပြီးဆုံးချိန်ကို မှတ်တမ်းတင်ပြီး၊ 30 စက္ကန့်တစ်ကြိမ် heartbeat က လက်ရှိလုပ်ဆောင်နေဆဲဖိုင်များနှင့် ၎င်းတို့၏ ကြာမြင့်ချိန်ကို စာရင်းပြုစုသည်။ ခွင့်ပြုစာရင်းတွင် ပါဝင်သော လုပ်ဆောင်မှုမက်တာဒေတာကိုသာ မှတ်တမ်းတင်ပြီး စမ်းသပ်မှုဖော်ပြချက်များ၊ output၊ error body များနှင့် environment အပြည့်အစုံကို serialize မပြုလုပ်ပါ။

CI နှင့် Quality တို့သည် JSONL ဖိုင်များကို `unit-progress-ci-<run>-<attempt>-<shard>` နှင့် `unit-progress-quality-<run>-<attempt>-<shard>` အဖြစ် ထိန်းသိမ်းထားသည်။ Job timeout ဖြစ်ပါက နောက်ပိုင်း upload ပြုလုပ်မှုကို တားဆီးနိုင်သော်လည်း ထုတ်လွှတ်ပြီးသား heartbeat များသည် ပြဿနာရှာဖွေရေးအထောက်အထားအဖြစ် ကျန်ရှိနေမည်ဖြစ်သည်။ Heartbeat များ ပျောက်ဆုံးနေခြင်းသည် runner process ပိတ်ဆို့နေခြင်း သို့မဟုတ် ရပ်စဲသွားခြင်းကိုလည်း ညွှန်ပြနိုင်သည်။ ဤမှတ်တမ်းများသည် လက်ရှိစမ်းသပ်မှုရွေးချယ်ခြင်း၊ တစ်ပြိုင်နက်လုပ်ဆောင်မှု၊ သတ်မှတ်ပြီးဆုံးချိန်များနှင့် exit status တို့ကို မပြောင်းလဲဘဲ ထိန်းသိမ်းထားသည်။ ၎င်းတို့သည် candidate ကို လက်ခံရန် ဆုံးဖြတ်ချက်များမဟုတ်ပါ။

### လက်ခံမှုရလဒ် စုစည်းကိရိယာရှိ သိမ်းဆည်းထားသော အထောက်အထား

`scripts/quality/validate-release-acceptance.mjs` သည် ပေးထားသော အစီအစဉ်နှင့် ၎င်း၏ manifest များကို စုစည်းသည်။ အစီအစဉ်သည် release pipeline တစ်ခုလုံးကို လွှမ်းခြုံကြောင်း မသက်သေပြပါ။ အစီအစဉ်က `VERIFIED` ဖြစ်နေလျှင်ပင် ၎င်း၏ အစီရင်ခံစာများသည် `releaseAcceptance: false` ဟု အတိအလင်း သတ်မှတ်သည်။ `release-acceptance.yml` workflow သည် shadow စမ်းသပ် fixture များကိုသာ ဆက်လက်အသုံးပြုပြီး အမှန်တကယ် build၊ package၊ boot သို့မဟုတ် promotion မှတ်တမ်းများကို အသုံးမပြုသေးပါ။

သိမ်းဆည်းထားသော အထောက်အထားကို စစ်ဆေးရန် CLI သည် `--evidence-root` ကို လိုအပ်သည်။ ဖိုင်များကို `<evidence-root>/<artifact_id>/<member>` လမ်းကြောင်းဖြင့် ရှာပြီး SHA-256 hash တွက်ချက်သည်။ အထောက်အထားမရှိသော PASS မှတ်တမ်း၊ ပျောက်ဆုံးနေသော သို့မဟုတ် ပြောင်းလဲသွားသော ဖိုင်၊ မလုံခြုံသော လမ်းကြောင်း သို့မဟုတ် symlink ရှိလျှင် အတည်ပြုမှု မရနိုင်ပါ။ ပျောက်ဆုံးနေသော ဖိုင်များသည် အောင်မြင်သော run များ၏ အလွတ် log များနှင့် မတူပါ။ ရှိပြီးသား SHA/run/attempt စစ်ဆေးမှုများသည် သီးခြားဖြစ်နေဆဲဖြစ်ပြီး bytes များ ကိုက်ညီနေခြင်းက ဟောင်းနွမ်းနေသော မှတ်တမ်းကို တရားဝင် မဖြစ်စေနိုင်ပါ။ ဖိုင်၏ ပြည့်စုံမှန်ကန်မှုသည် လုပ်ဆောင်မှု၏ အစစ်အမှန်ဖြစ်မှု သို့မဟုတ် artifact promotion ကို သက်သေမပြပါ။

### Static scan စာရင်း

ဗားရှင်းသတ်မှတ်ထားသော npm-alias စာရင်းနှင့် static-scan membership တို့သည်
`config/quality/gate-manifest.json` တွင် ရှိသည်။ Script name များနှင့် command အတိအကျကို
`package.json` နှင့် တိုက်ဆိုင်စစ်ဆေးရန် `npm run check:gate-manifest` ကို လုပ်ဆောင်ပါ။ ထည့်သွင်းမှု၊
ဖယ်ရှားမှုနှင့် command ကွဲလွဲမှုများသည် local hook နှင့် CI ရှိ change-classification job နှစ်မျိုးစလုံးကို
ပျက်ကွက်စေသည်။ Alias တစ်ခုသည် workflow job၊ matrix instance သို့မဟုတ် test case မဟုတ်ပါ။ ဤအရေအတွက်များကို
အပြန်အလှန်ဖလှယ်နိုင်သကဲ့သို့ မဖော်ပြရပါ။

ရွေးချယ်ထားသော alias များကို မလုပ်ဆောင်ဘဲ စစ်ဆေးကြည့်ရှုရန် `npm run quality:scan -- --list` သို့မဟုတ်
`npm run quality:scan:fast -- --list` ကို အသုံးပြုပါ။ Runner သည် npm entrypoint ကို ခေါ်ယူသောကြောင့်
၎င်း၏ runtime ကို ဆက်လက်ထိန်းသိမ်းထားသည်၊ စီစဉ်ထားသည့်နေရာတွင် Bun လည်း ပါဝင်သည်။
Manifest သည် ထို profile များပြင်ပရှိ alias များကို သီးခြားခေါ်ယူထားသည့်အဖြစ် မှတ်တမ်းတင်ပြီး
read-only scan profile များတွင် maintenance command များကို တားမြစ်ထားသည်။

ဤ profile များသည် static scan ကိုသာ လွှမ်းခြုံသည်။ ၎င်းတို့သည် product test များ၊ coverage၊ packaging၊
external check များ သို့မဟုတ် candidate တစ်ခု၏ release လက်ခံမှုအပြည့်အစုံကို အတည်ပြုမပေးပါ။
Workflow လက်ခံမှုသည် ချိတ်ဆက်ထားသော `config/quality/admission-policy.json` နှင့်
`scripts/quality/admission-verdict.mjs` ကို အသုံးပြုသည်။ Release-observer profile များသည် သီးခြားအဖြစ်
ဆက်လက်တည်ရှိသည်။ ၎င်းတို့နှင့်သက်ဆိုင်သော check များနှင့် receipt များကို သီးခြားစစ်ဆေးပါ။ Observer အပြည့်အစုံ၏
static command များကို `config/quality/release-green-static-profile.json` တွင် ကြေညာထားပြီး
`audit:deps`၊ mutation-test ရွေးချယ်မှုနှင့် translation check များ ပါဝင်သည်။ Loader သည် npm
command များကို package.json နှင့် ပုံစံချထားသော CI/Quality ကြေညာချက်များနှင့် တိုက်ဆိုင်စစ်ဆေးသည်။
Shell token များကို argument အဖြစ် လုပ်ဆောင်မည့်အစား ကွဲလွဲမှုကို ငြင်းပယ်သည်။ မဖြစ်မနေလိုအပ်သော scanner ၏
SKIP/INCOMPLETE output ဖြင့် PASS ဟု သတ်မှတ်၍မရပါ။ Profile သည် ၎င်း၏ ပြင်ပချန်လှပ်ချက်များကို မှတ်တမ်းတင်ထားပြီး
hosted coverage၊ test matrix များ၊ package သို့မဟုတ် deployment အထောက်အထားများကို အစားမထိုးပါ။
အောက်ပါ စာသားဖြင့်ဖော်ပြထားသော စာရင်းသည် ကိုးကားရန်သာဖြစ်ပြီး gate တစ်ခု အမှန်တကယ် လုပ်ဆောင်ခဲ့ကြောင်း
သက်သေမပြပါ။

Script များသည် `scripts/check/` (policy gate များ) နှင့် `scripts/quality/` (ratchet engine) အောက်တွင် ရှိသည်။
CI အတွက် တစ်ခုတည်းသော အမှန်ရင်းမြစ်မှာ `.github/workflows/ci.yml` ဖြစ်သည်။

### ထုတ်ဝေထားသော အခြေခံစာရွက်စာတမ်း၏ ကျန်းမာရေးအခြေအနေ

`.github/workflows/i18n-base-health.yml` သည် ရွေးချယ်ထားသော `main` နှင့် `release/v*` သို့ push လုပ်မှုများပြီးနောက်နှင့် ကိုယ်တိုင်စတင်လုပ်ဆောင်သည့်အခါ စာရွက်စာတမ်း၏ ကျန်းမာရေးအခြေအနေကို စောင့်ကြည့်သည်။ ၎င်း၏ စစ်ထုတ်မှုများတွင် စာရွက်စာတမ်းများ၊ root Markdown၊ `llm.txt`၊ ဘာသာပြန်ဆိုမှုအခြေအနေ/ဖွဲ့စည်းပုံနှင့် သက်ဆိုင်ရာ i18n ကိရိယာများ ပါဝင်သည်။ တစ်ခုတည်းသော `Published base documentation health` အလုပ်သည် hosted Ubuntu ကို အသုံးပြုပြီး အချိန်ကန့်သတ်ချက်မှာ ငါးမိနစ်ဖြစ်သည်။ ၎င်းသည် ဖတ်ရှုရန်သက်သက် အတည်ပြုစစ်ဆေးမှုကို လုပ်ဆောင်ပြီး dependency ထည့်သွင်းခြင်း၊ ဘာသာပြန်ဆိုခြင်း သို့မဟုတ် အခြေအနေကို လက်ခံအသုံးပြုခြင်းမရှိဘဲ ရောဂါရှာဖွေရေးမှတ်တမ်းတစ်ခုကို ရေးသားသည်။

`scripts/i18n/check-base-health.mjs` သည် source-hash မကိုက်ညီမှု၊ target ပျောက်ဆုံးမှု၊ target-hash ပြဿနာ၊ ခေတ်နောက်ကျနေသော ဘာသာပြန်ဆိုမှုနှင့် section-cache မကိုက်ညီမှုတို့ လုံးဝမရှိရန် လိုအပ်သည်။ ၎င်းသည် လက်ရှိ core document/locale နယ်ပယ်နှင့် မှတ်တမ်းတင်ထားသော မူလရင်းမြစ်ဆိုင်ရာ အချက်အလက်ကိုလည်း အတည်ပြုစစ်ဆေးသည်။ မမှန်ကန်သော context၊ မပြည့်စုံသော coverage သို့မဟုတ် စစ်ဆေးကိရိယာ လုပ်ဆောင်မှု ပြတ်တောက်ခြင်းသည် `INCOMPLETE` ကို ဖြစ်ပေါ်စေပြီး၊ drift ရှိကြောင်း အတည်ပြုနိုင်ပါက `FAIL` ကို ဖြစ်ပေါ်စေသည်။ နှစ်ခုစလုံးသည် မအောင်မြင်သော exit status ကို ပြန်ပေးသည်။ မှတ်တမ်းကို checkout SHA၊ workflow၊ run နှင့် attempt တို့နှင့် ချိတ်ဆက်ထားပြီး `i18n-base-health-<sha>-<run>-<attempt>` အဖြစ် ထိန်းသိမ်းထားသည်။

ဤသည်မှာ ထုတ်ဝေထားသော အခြေခံ၏ သီးခြားလွတ်လပ်သည့် စောင့်ကြည့်ချက်ဖြစ်သည်။ ၎င်းသည် PR သို့မဟုတ် merge-group event၊ မဖြစ်မနေလိုအပ်သော PR check၊ npm alias သို့မဟုတ် static-scan profile member တစ်ခုကို မထည့်သွင်းပါ။ ရှိပြီးသား differential PR မူဝါဒနှင့် အခြေခံစစ်ဆေးကိရိယာ၏ အကြံပြုသဘောထားရှိသော အမျိုးအစားခွဲခြားမှုများသည် သီးခြားစီ ဆက်ရှိနေသည်။ အောင်မြင်သော upload တစ်ခုသည် မအောင်မြင်သည့် ကျန်းမာရေးရလဒ်ကို PASS အဖြစ် မပြောင်းလဲနိုင်ပါ။

### Release PR အမြန်လမ်းကြောင်း (`quality.yml`)

`.github/workflows/quality.yml` သည် main/release PR များ၊ `main` သို့ push များ၊
dispatch နှင့် merge group များတွင် CI ကို ဖြည့်စွက်ပေးသည်။ PR များသည် path-filter လုပ်ထားသော
အမြန်စစ်ဆေးမှုများကို အသုံးပြုသည်။ အမြဲတမ်းပိတ်ထားသော ထပ်နေသည့် build ကို ဖယ်ရှားထားပြီးဖြစ်သည်။
အမှန်တကယ် build/package/boot စစ်ဆေးမှုများသည် CI တွင် ဆက်လက်ရှိနေသည်။

#### မေ့လျော့နေသော sibling test များ၏ အစီရင်ခံစာ

`npm run check:forgotten-sibling-tests` သည် test-impact map နောက်ကွယ်ရှိ import resolver ကို ပြန်လည်အသုံးပြုသည်။
ပြောင်းလဲထားသော production module တစ်ခုစီအတွက် ဖြစ်နိုင်ခြေရှိသော test သည် pull-request diff တွင်
မပါရှိပါက တသမတ်တည်းဖြစ်သော `changed module/symbol -> static consumer -> candidate sibling test`
ကွင်းဆက်များကို အစီရင်ခံသည်။ ပိတ်ဆို့သည့် rollout တစ်ခုခုမပြုလုပ်မီ ချိန်ညှိနိုင်ရန် Markdown အနှစ်ချုပ်နှင့်
JSON ရလဒ်ကို `forgotten-sibling-tests` workflow artifact အဖြစ် ထိန်းသိမ်းထားသည်။

Barrel re-export များနှင့် dynamic import များသည် resolution diagnostic များသာဖြစ်ပြီး ပိတ်ဆို့သည့်
တွေ့ရှိချက်ကို မည်သည့်အခါမျှ မဖန်တီးပါ။ ပြန်လည်သုံးသပ်ပြီးသော ခြွင်းချက်များကို
`config/quality/forgotten-sibling-allowlist.json` တွင် ထားရှိသည်။ Entry တစ်ခုစီတွင် consumer နှင့် ဖြစ်နိုင်ခြေရှိသော
test ကို အမည်ဖော်ပြရမည်၊ တိကျသော အကြောင်းပြချက်ပေးရမည်၊ ထို့ပြင် GitHub issue သို့မဟုတ် pull request တစ်ခုကို link ချိတ်ရမည်။ ပုံစံမမှန်သော entry များကို
လက်မခံဘဲ ပိတ်ဆို့သည်။ ခြွင်းချက်များသည် ဖျက်ထားသော ဖြစ်နိုင်ခြေရှိသည့် test သို့မဟုတ် `.skip`/`.todo` ထည့်သွင်းသည့် diff ကို ဖုံးကွယ်၍မရပါ;
assertion အားနည်းအောင်လုပ်ခြင်းနှင့် အခြား masking များကို သီးခြားလွတ်လပ်စွာ ပိတ်ဆို့သည့်
`check:test-masking` gate က ဆက်လက်တာဝန်ယူသည်။

ကို ပြန်လည်ရေးသားလိုက်သော်လည်း _ယခင်_ အင်္ဂလိပ်မှ ဆင်းသက်လာသော ဘာသာပြန်ချက်များ ကျန်ရှိနေခြင်းကြောင့်
အင်္ဂလိပ်မဟုတ်သော ဘာသာစကားအသုံးပြုသူများသည် ယုံကြည်စိတ်ချဖွယ် ရေးသားထားသော်လည်း ယခုအခါ မှားယွင်းနေသော စာသားကို ဆက်လက်ဖတ်ရှုနေရသည်။

၎င်းသည် အမှန်တကယ် release လုပ်သွားခဲ့ဖူးသည်။ Antigravity login helper ထည့်သွင်းချိန် (#5203) တွင်
`oauthModal.googleOAuthWarning` ကို ပြန်လည်ရေးသားခဲ့သော်လည်း **locale 43 ခုအနက် 39 ခု** တွင် operator များအား "URL အပြည့်အစုံကို
ကူးယူပြီး အောက်တွင် paste လုပ်ပါ" ဟု ပြောထားသည့် စာသား ကျန်ရှိနေခဲ့သည် — ထို provider အတွက် ပြီးမြောက်နိုင်ခြင်းမရှိသော flow ဖြစ်သည်။ အောက်ပါအကြောင်းရင်းများကြောင့်
#8463 မတိုင်မီ သတိမပြုမိခဲ့ပါ။

- `sync-ui-keys` သည် **မရှိသေးသော** key များကိုသာ backfill လုပ်ပြီး **ခေတ်မမီတော့သော** key များကို လုံးဝမလုပ်ပါ။
- `check-ui-keys-coverage` သည် key _ရှိ/မရှိ_ ကို ရေတွက်သဖြင့် ခေတ်မမီသော ဘာသာပြန်ချက်တစ်ခုကို လွှမ်းခြုံထားသည်ဟု သတ်မှတ်သည်။
- `check-translation-drift` သည် `docs/i18n/<locale>/**.md` documentation mirror များကို ခြေရာခံသည် —
  `src/i18n/messages/*.json` ကို လုံးဝမဖတ်ပါ။ 2026-09 re-sync မှစ၍ job `docs-sync-strict` တွင် ပိတ်ဆို့ထားသည်။

**Diff ကို အခြေခံပြီး baseline ကို မအခြေခံပါ။** ၎င်းသည် merge base ရှိ `en.json` ကို
working tree နှင့် နှိုင်းယှဉ်သည်။ အင်္ဂလိပ် value ပြောင်းလဲခဲ့သော key တိုင်းအတွက် locale တစ်ခုခုတွင်
မပြင်ဆင်ထားသော ဘာသာပြန်ချက်ကို ဆက်လက်ထားရှိပါက ယင်းသည် ခေတ်မမီတော့ပါ။ ဤနည်းလမ်းသည် **ယခင်ကတည်းကရှိသော အကြွေးကို ရည်ရွယ်ချက်ရှိရှိ မပြောင်းလဲအောင်ထားသည်** — ကာလကြာရှည်စွာရှိနေသော ဘာသာပြန်ချက်တစ်ခုသည် မည်သည့် အင်္ဂလိပ်အဟောင်းမှ ဆင်းသက်လာသည်ကို diff တစ်ခုဖြင့် မဖော်ထုတ်နိုင်သဖြင့်
gate သည် လက်ရှိပြောင်းလဲမှုက ထိတွေ့သောအရာကိုသာ အကဲဖြတ်သည်။ အခြားရွေးချယ်စရာဖြစ်သည့် key တစ်ခုချင်းစီအတွက် hash baseline သည်
~600 KB generated file တစ်ခု လိုအပ်မည်ဖြစ်ပြီး လက်ရှိအကြီးဆုံး baseline ထက် 3× ကြီးကာ i18n PR တိုင်းတွင် ထပ်ခါတလဲလဲ ပြောင်းလဲနေမည်ဖြစ်သည်။

၎င်းကို ကျော်ဖြတ်ရန် နည်းလမ်းနှစ်ခုရှိသည်။

1. သက်ရောက်မှုရှိသော ဘာသာပြန်ချက်များကို ပြင်ဆင်ပါ၊ သို့မဟုတ်
2. ၎င်းတို့ကို `__MISSING__:<new english>` ဟု သတ်မှတ်ပါ — ထို့နောက် runtime သည် ပြင်ဆင်ပြီးသော အင်္ဂလိပ်စာသားကို ပေးမည်
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ဖြစ်ပြီး key ကို ဘာသာပြန်ရန် queue ထဲ ထည့်ပေးမည်။

စာကြောင်း၏ **အဓိပ္ပာယ်** ပြောင်းလဲခဲ့ပါက **key ကို အမည်ပြောင်းခြင်း** ကို ဦးစားပေးပါ။ key အသစ်တစ်ခုသည်
ခေတ်မမီသော ဘာသာပြန်ချက်ကို ဆက်ခံနိုင်ခြင်းမရှိပါ။ ယင်းသည် #8463 တွင် အသုံးပြုခဲ့သော ပုံစံဖြစ်သည်။

```bash
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

context ကို အသုံးပြုသည်။ candidate branch တစ်ခုကို dispatch လုပ်ရန် ၎င်းနှင့် အတိအကျသက်ဆိုင်သော ဖွင့်ထားဆဲ PR သို့မဟုတ် အတိအလင်းသတ်မှတ်ထားသော

candidate ပြောင်းလဲသွားခြင်းတို့သည် warn mode အပါအဝင် exit code **2** ဖြင့် `INCOMPLETE` ကို ဖြစ်ပေါ်စေသည်။

**New-code mode (Clean-as-You-Code) — 2026-08-30 မှစ၍ PR fast-path အတွက်သာ**

`pull_request` event များတွင် `quality.yml` က `--base-ref <PR base SHA>` ကို
`check:file-size`၊ `check:complexity-ratchets` နှင့် `check:dead-code` သို့ ပေးပို့သည်။
`check:complexity-ratchets` နှင့် `check:dead-code` အတွက် gate သည် HEAD ကို merge-base နှင့်
**PR က ပြင်ဆင်ထားသော ဖိုင်များကိုသာ ကန့်သတ်၍** နှိုင်းယှဉ်သည်
(`scripts/check/newCodeMode.mjs`: merge-base ကို ယာယီ `git worktree` တစ်ခုတွင် ဖန်တီးထားပြီး၊
ESLint/knip ကို ထိုနေရာနှင့် HEAD နှစ်ခုလုံးတွင် run ကာ ဖိုင်တစ်ခုချင်းစီ၏ အရေအတွက်များကို
diff လုပ်သည်)-

- **ပိတ်ပင်ခြင်း** — PR က ၎င်းပြင်ဆင်ထားသော ဖိုင်များတွင် cyclomatic/cognitive ချိုးဖောက်မှုများ
  သို့မဟုတ် dead export များ ထည့်သွင်းခဲ့သည်
  (log ထဲရှိ `complexityNewCode=`၊ `cognitiveComplexityNewCode=`၊ `deadExportsNewCode=`);
- **အကြံပြုချက်** — ကမ္ဘာလုံးဆိုင်ရာ စုစုပေါင်းနှင့် အေးခဲထားသော အခြေခံမျဉ်းတို့ကို နှိုင်းယှဉ်ခြင်း ဖြစ်သည်။ အမွေဆက်ခံလာသော ကွာဟမှုကြောင့်
  အပြစ်မရှိသော PR ကို မည်သည့်အခါမျှ အနီရောင်အဖြစ် မသတ်မှတ်ပါ။ ယင်းကွာဟမှုကို ထုတ်ဝေမှု ပြန်လည်ညှိနှိုင်းချိန်တွင် ပြုပြင်ရန် ခြေရာခံထားပြီး
  headroom job က စောင့်ကြည့်သည်။

`check:file-size` သည် base ref ကို ၎င်း၏ကိုယ်ပိုင်စည်းမျဉ်းများအတိုင်း အသုံးပြုသည်

စစ်ဆေးပြီး PR base ရှိ ဖိုင်တစ်ခုချင်းစီ၏ စာကြောင်းအရေအတွက်ကို `git show` ဖြင့် ဖတ်ကာ၊
၎င်း၏ baseline ceiling (`frozen` / `testFrozen` သို့မဟုတ် baseline ပြင်ပရှိ ဖိုင်အတွက်
`cap` / `testCap`) နှင့် base size တို့အနက် ပိုကြီးသောတန်ဖိုးကို ကျော်လွန်သည်အထိ
ကြီးလာမှသာ ထိုဖိုင်ကို မအောင်မြင်စေသည်။ ထို့ကြောင့် base တွင် drift ဖြစ်ပြီးသား ဖိုင်တစ်ခုက
သက်ဆိုင်မှုမရှိသည့် PR တစ်ခုကို မည်သည့်အခါမျှ မအောင်မြင်စေပါ။

`check:boundary:ratchet` သည် ၎င်း၏ တစ်ခုတည်းသော ကိန်းဂဏန်းအပေါ် တူညီသည့် စည်းမျဉ်းကို အသုံးပြုသည်
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`)။ PR event များတွင်
`quality.yml` ၏ fast-gate များနှင့် `ci.yml` ၏ lint job နှစ်ခုစလုံးက PR base SHA ကို ပေးပို့ပြီး၊ base commit ကို
`git archive` export တစ်ခုမှ တိုင်းတာကာ PR ၏ `open-sse → src` edge အရေအတွက်သည်
`metrics.boundaryOpenSseToSrc` နှင့် base ရှိ အရေအတွက်တို့အနက် ပိုကြီးသည့်တန်ဖိုးကို ကျော်လွန်မှသာ
PR ကျရှုံးသည်။ သတ်မှတ်အမြင့်ဆုံးတန်ဖိုးထက် ကျော်လွန်နေသော base drift ကို (`base drift herdado`) အဖြစ် အစီရင်ခံသော်လည်း အပြစ်မရှိသော PR ကို မည်သည့်အခါမျှ အနီရောင်ဖြစ်စေမည်မဟုတ်ပါ။ push → main သည်
အကြွင်းမဲ့အမြင့်ဆုံးတန်ဖိုးကို ဆက်လက်ထိန်းသိမ်းပြီး၊ ဖြေရှင်း၍မရသော base SHA ဖြစ်ပါက သတိပေးချက်တစ်ခုနှင့်အတူ ထိုတန်ဖိုးကို ပြန်လည်အသုံးပြုသည်။

`workflow_dispatch` run များ၊ release-green sweep နှင့် nightly headroom job တို့တွင် PR base မရှိသဖြင့်
အကြွင်းမဲ့ (global) နှိုင်းယှဉ်မှုကို ဆက်လက်အသုံးပြုသည်။ Coverage၊ duplication နှင့် type-coverage တို့သည် လက်ရှိအချိန်တွင် global အဖြစ် ဆက်ရှိနေသည်
(၎င်းတို့၏ tool များက ဖိုင်တစ်ခုချင်းစီအလိုက် diff ကို ကုန်ကျစရိတ်နည်းနည်းဖြင့် မထုတ်ပေးနိုင်ပါ) — တူညီသည့် ကိုင်တွယ်မှုကို အသုံးပြုရန် အလားအလာရှိသည့် ကိုယ်စားလှယ်များဖြစ်သည်။

**v4.0 တွင် အဆင့်ကို ပိတ်သိမ်းခြင်း (LTS = ယခင်ထက် ပိုတင်းကျပ်ခြင်း၊ "ပုံမှန်အတိုင်း ပြန်သွားခြင်း" မဟုတ်ပါ)**

1. ရိုးရိုး `release/v4.0.0` tip တွင် မှတ်တမ်းအတွက် `npm run quality:headroom --json` ကို run ပြီးနောက်
   `npm run quality:ratchet -- --update`၊ `check:file-size --update`၊
   `check:complexity-ratchets --update`၊ `check:dead-code --update` နှင့် typecheck gate တစ်ခုချင်းစီ၏
   `--update` ကို run ပါ — baseline အားလုံးသည် တိုင်းတာရရှိသည့်တန်ဖိုးအထိ လျော့ကျသွားမည်။
2. `quality-baseline.json` မှ `_policy` ကို ဖျက်ပါ (`--require-tighten` နှင့် nightly
   banking ကို ပြန်လည်အသက်သွင်းသည်)၊ `check-openapi-coverage.mjs` ရှိ `THRESHOLD = 36` (သို့မဟုတ် ပိုမြင့်သောတန်ဖိုး) ကို ပြန်ထားပါ။
3. Modularization ကြောင့် အကျိုးရှိခဲ့သည့်နေရာများတွင် တိုင်းတာရရှိသည့်တန်ဖိုးထက် ပိုတင်းကျပ်စွာ သတ်မှတ်ပါ — file-size `cap` ကို 1000
   (သို့မဟုတ် 800) သို့ ပြန်ထားခြင်း၊ coverage floor များကို +5 တိုးခြင်း၊ modularize လုပ်ထားသည့် package များအတွက် dead export ကို 0 သတ်မှတ်ခြင်း။

## Ratchet အခြေခံမျဉ်း (`quality-baseline.json`)

Ratchet အင်ဂျင် (`scripts/quality/check-quality-ratchet.mjs`) သည် `quality-baseline.json`
ကို ဖတ်ပြီး အသစ်စုဆောင်းထားသော `quality-metrics.json` နှင့် နှိုင်းယှဉ်သည်။ သတ်မှတ်ထားသော
epsilon ထက်ကျော်လွန်၍ နောက်ပြန်ဆုတ်သွားသည့် မည်သည့်မက်ထရစ်မဆို build ကို ကျရှုံးစေသည်။

လက်ရှိ ခြေရာခံထားသော မက်ထရစ်များ-

| မက်ထရစ်               | ဦးတည်ချက် | အဓိပ္ပာယ်                          |
| --------------------- | --------- | ---------------------------------- |
| `eslintWarnings`      | `down`    | ESLint သတိပေးချက်အရေအတွက် မတိုးရပါ |
| `coverage.statements` | `up`      | Statement coverage မကျဆင်းရပါ      |
| `coverage.lines`      | `up`      | Line coverage မကျဆင်းရပါ           |
| `coverage.functions`  | `up`      | Function coverage မကျဆင်းရပါ       |
| `coverage.branches`   | `up`      | Branch coverage မကျဆင်းရပါ         |

အမှန်တကယ် တိုးတက်မှုတစ်ခု ဖြစ်ပေါ်ပြီးနောက် အခြေခံမျဉ်းကို အပ်ဒိတ်လုပ်ရန်-

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` flag သည် လက်ရှိတိုင်းတာထားသော တန်ဖိုးများကို `quality-baseline.json` ထဲသို့ ရေးသားသည်။
မက်ထရစ်ကို တိုးတက်စေခဲ့သော ပြောင်းလဲမှုနှင့်အတူ ဤဖိုင်ကို commit လုပ်ပါ။ မက်ထရစ်တစ်ခုကို
တိုးတက်စေသော်လည်း အခြေခံမျဉ်းကို အပ်ဒိတ်မလုပ်ထားသော PR ကို `--require-tighten` က
ဖမ်းမိမည်ဖြစ်သည် (အဆင့် 6A.5၊ အကောင်အထည်ဖော်ရန် ကျန်ရှိနေသေးသည်)။

### CodeQL ratchet: ပြန်လည်ဆန်းသစ်သည့် အကြိမ်နှုန်းနှင့် ကိုယ်တိုင်အစပျိုးခြင်း

`check:codeql-ratchet` သည် **အချိန်ဇယားအတိုင်း ပြန်လည်ဆန်းသစ်ထားသော repo အခြေအနေကို ဖတ်သည် — PR တစ်ခုချင်းအလိုက် မဟုတ်ပါ။**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` သည်
`state: configured`, `schedule: weekly` ဟု အစီရင်ခံသည်- ၎င်းသည် GitHub ၏ default-setup scan ဖြစ်ပြီး push တစ်ခုချင်းအလိုက်
လုပ်ဆောင်သော analysis မဟုတ်ပါ။ အကျိုးဆက်အနေဖြင့် alert များကို ပြင်ဆင်ထားသော PR တစ်ခု merge ဖြစ်ပြီးနောက်တွင်
ratchet သည် နောက်တစ်ကြိမ် အချိန်ဇယားအတိုင်း scan မလုပ်ဆောင်မချင်း အဟောင်းဖြစ်သည့် ပိုများသော အရေအတွက်ကို ဆက်လက်ဖတ်နေမည် —
ထို့ကြောင့် scan က အခြေအနေသစ်ကို ဖမ်းမိသည်အထိ ပြင်ဆင်သည့် PR ၏ နောက်ဆက်တွဲ PR များအပါအဝင် ဖွင့်ထားသော PR အားလုံးတွင်
နောက်ပြန်ဆုတ်မှုအဖြစ် အစီရင်ခံမည်ဖြစ်သည်။

**ကိုယ်တိုင် ပြန်လည်ဆန်းသစ်ခြင်း**: `gh workflow run codeql.yml --ref release/vX.Y.Z` သည်
analysis ကို ပြန်လည်လုပ်ဆောင်ပြီး မိနစ်ပိုင်းအတွင်း alert များကို ပြန်လည်ထုတ်ပြန်သည်။ `.github/workflows/codeql.yml`
ကို ဦးစွာဖတ်ပါ — GitHub ၏ "default setup" နှင့် ပဋိပက္ခဖြစ်သောကြောင့်
(`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`) ၎င်းသည် `workflow_dispatch` သီးသန့်သာဖြစ်ကြောင်း
၎င်း၏ header တွင် ရှင်းပြထားသည်။ `push`/`pull_request`/
`schedule` trigger များကို ပြန်လည်ထည့်သွင်းရန် ဦးစွာ **owner ၏ လုပ်ဆောင်မှု** လိုအပ်သည်- Settings → Code security →
CodeQL: Default → Advanced။ ထိုပြောင်းလဲမှုမပြုလုပ်ဘဲ `schedule:` trigger ကို မထည့်ပါနှင့် — ထိုသို့ပြုလုပ်ပါက
ကျရှုံးသော run များသာ ဖြစ်ပေါ်စေမည်။

**အရေအတွက် ကျဆင်းပြီးနောက် အခြေခံမျဉ်းကို တင်းကျပ်ပါ** — `node scripts/check/check-codeql-ratchet.mjs
--update` သည် အသစ်တိုင်းတာထားသော အရေအတွက်ကို `quality-baseline.json` →
`metrics.codeqlAlerts.value` ထဲသို့ ရေးသားသောကြောင့် ratchet က အဟောင်းဖြစ်သည့် အမြင့်ဆုံးကန့်သတ်ချက်အထိ
ပြန်လည်မြင့်တက်သွားခြင်းကို မသိမသာ ခွင့်ပြုမည်မဟုတ်ပါ။ လက်တွေ့ဥပမာ (2026-09-02/03)- PR #12502 က အမှန်တကယ် alert 7 ခုကို
ပြင်ဆင်ခဲ့သည် (တိုင်းတာထားသော ဖွင့်ထားသည့် alert 13 → 6); PR #12530 က ကိုက်ညီစေရန် ပုံသေထားသော အခြေခံမျဉ်းကို 11 → 6 သို့
တင်းကျပ်ခဲ့သည်; ထို့နောက် ကျန်ရှိသည့် 6 ခုကို alert တစ်ခုချင်းအလိုက် အကြောင်းပြချက်ပေး၍ ပယ်ဖျက်ခဲ့ပြီး ဖွင့်ထားသည့် alert အရေအတွက်ကို 0 အထိ လျှော့ချခဲ့သည်။

**ပယ်ဖျက်ခြင်းများသည် operator ၏ ဆုံးဖြတ်ချက်ဖြစ်သည် (တင်းကျပ်သော စည်းမျဉ်း #14)** — ပယ်ဖျက်မှုမှတ်ချက်တွင်
နည်းပညာဆိုင်ရာ အကြောင်းပြချက်ကို မှတ်တမ်းမတင်ဘဲ CodeQL alert တစ်ခုကို မည်သည့်အခါမျှ မပယ်ဖျက်ပါနှင့်- upstream-protocol
လိုအပ်ချက်အတွက် `won't fix`၊ test fixture အတွက် `used in tests`၊ CodeQL က မမြင်နိုင်သော sanitizer
အတွက် `false positive` (ရှေ့နမူနာ- `docs/security/ERROR_SANITIZATION.md`)။

## Release အဆင့် Ratchet Drift (WS5.5, v3.8.49)

PURE release tip ပေါ်တွင် ratchet တစ်ခု (ဖိုင်အရွယ်အစား၊ ရှုပ်ထွေးမှု၊ eslint သတိပေးချက်များ) regression ဖြစ်လာသောအခါ —
ဆိုလိုသည်မှာ merge များ၏ ပေါင်းစပ်မှုကြောင့် regression ဖြစ်ပြီး PR တစ်ခုတည်းက ၎င်း၏
ကိုယ်ပိုင် branch ပေါ်တွင် ထို regression ကို ပြန်လည်ဖြစ်ပေါ်စေနိုင်ခြင်းမရှိသောအခါ — ပြင်ဆင်မှုသည် **release captain က release
branch ပေါ်တွင် တစ်ကြိမ်သာ** လုပ်ဆောင်ရန် တာဝန်ရှိသည်- extraction/refactor ကို ဦးစားပေးပါ၊ မှတ်တမ်းတင်ထားသော
အကြောင်းပြချက် entry ရှိမှသာ baseline ကို ပြန်လည်သတ်မှတ်ပါ။ ပေါင်းစပ်မှုကြောင့်ဖြစ်သည့် drift ကို contributor PR ပေါ်သို့ မည်သည့်အခါမျှ
မတွန်းပို့ပါနှင့်၊ PR တစ်ခုချင်းစီအလိုက်လည်း baseline ကို မည်သည့်အခါမျှ ပြန်လည်မသတ်မှတ်ပါနှင့် (ထိုသို့လုပ်ခြင်းသည် အမှန်တကယ်ဖြစ်သော regression များကို ဖုံးကွယ်သည်)။ ဦးစွာ ခွဲခြားစစ်ဆေးပါ- သင်၏ PR ကြောင့် ဖြစ်သည်ဟု မယူဆမီ
probe worktree တစ်ခုထဲရှိ pure tip ကို အသုံးပြု၍ မအောင်မြင်မှုကို ပြန်လည်ဖြစ်ပေါ်စေပါ။

## Ratchet လျှော့ချမှုများကို စုဆောင်းသိမ်းဆည်းခြင်း — အောက်သို့ ဦးတည်ချက် (#8584)

ratchet သည် တစ်ဝက်သာ အလိုအလျောက်ဖြစ်ပြီး၊ အလိုအလျောက်ဖြစ်နေသည့်အပိုင်းကလည်း မှားယွင်းသည့်အပိုင်းဖြစ်သည်။ cap ကို **မြှင့်တင်ခြင်း** သည်
ဆယ်စက္ကန့်သာကြာသော manual JSON ပြင်ဆင်မှုဖြစ်ပြီး မအောင်မြင်နေသော PR ကို အမြန်ဆုံး ပြန်လည်လုပ်ဆောင်နိုင်စေသည့် နည်းလမ်းဖြစ်သည်။
cap တစ်ခုကို **လျှော့ချခြင်း** အတွက်မူ တစ်စုံတစ်ဦးက `--update` ကို run ပြီး ရလဒ်ကို commit လုပ်ရန်လိုသည် — ထို့အပြင်
`bank-ratchet-shrinks` job မပေါ်ပေါက်မီအထိ မည်သည့် workflow ကမျှ ထိုသို့ run မလုပ်ခဲ့ပါ။ တိုင်းတာတွေ့ရှိရသော အကျိုးဆက်
(2026-07-25)- frozen file 18 ခုသည် file အသစ်အတွက် သတ်မှတ်ထားသော လိုင်း 800 cap အောက် သို့မဟုတ် ၎င်းနှင့်ညီမျှသော အခြေအနေသို့ ရောက်ရှိပြီးဖြစ်သော်လည်း၊ အဆိုးဆုံးမှာ
132× (`src/shared/validation/schemas.ts` တွင် လိုင်း 19 သာရှိသော်လည်း cap 2,523 ထားရှိခြင်း) ဖြစ်သည်၊
complexity ceiling သည် rebaseline မှတ်စု ~37 ခုအတွင်း `1794 → 2169` သို့ တက်သွားပြီး လျှော့ချမှုမှာ တိတိကျကျ တစ်ကြိမ်သာ
(−1) ရှိခဲ့သည်၊ ထို့အပြင် "နောက် cycle တွင် `--update` ဖြင့် တင်းကျပ်မည်" ဟု 31 ကြိမ်ရေးသားခဲ့သော်လည်း တစ်ကြိမ်သာ
အကောင်အထည်ဖော်ခဲ့သည်။ ၎င်းကို ဖြစ်ပေါ်စေခဲ့သော code ထက် ပို၍ကြာရှည်တည်ရှိသည့် cap သည် ပြီးစီးသွားသော
decomposition တစ်ခုစီကို ထို file ကို နောက်တစ်ကြိမ် ပြင်ဆင်သူအတွက် တိုးချဲ့ခွင့်အဖြစ် တိတ်တဆိတ် ပြောင်းလဲပေးသည်။

### ဘေးကင်းရေး အတည်ပြုကိရိယာ

job သည် လူကိုယ်တိုင် ကြီးကြပ်ခြင်းမရှိဘဲ baseline များသို့ ရေးသားသောကြောင့် `verify-ratchet-bank.mjs` ကသာ
ထိုလုပ်ဆောင်ချက်ကို လက်ခံနိုင်စေသည်။ ၎င်းသည် `--update` ပြီးနောက် tree ကို `HEAD` နှင့် diff လုပ်ပြီး၊ ပြောင်းလဲမှုတိုင်းသည်
အောက်ပါအမျိုးအစားများထဲမှ တစ်ခုမဟုတ်ပါက **မည်သည့် commit မျှ မရှိမီ job ကို ရပ်တန့်ကာ**
PR လုံးဝ မဖွင့်ပါ-

- `frozen` / `testFrozen` numeric entry တစ်ခုကို **လျှော့ချခြင်း** သို့မဟုတ် **ဖယ်ရှားခြင်း**
- `complexity-baseline.json` → `count` ကို **လျှော့ချခြင်း**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ကို **လျှော့ချခြင်း**

အခြားမည်သည့်အရာမဆို မအောင်မြင်ပါ- ကိန်းဂဏန်းတစ်ခုကို မြှင့်တင်ခြင်း၊ entry တစ်ခုထည့်ခြင်း၊ `cap`/`testCap` ကို ပြောင်းလဲခြင်း သို့မဟုတ်
`_rebaseline_*` မှတ်စုတစ်ခုကို ဖျက်ခြင်း/ပြန်လည်ရေးသားခြင်း (ထိုမှတ်စုများသည် ceiling တစ်ခုစီ ရှိနေရသည့်အကြောင်းရင်းအတွက် audit trail ဖြစ်ပြီး
file entry များနှင့်အတူ တူညီသော `frozen` object ထဲတွင် သိမ်းဆည်းထားသည်)။ cap ကို မြှင့်တင်နိုင်သော bot သည် လက်ရှိအခြေအနေထက်
ပိုဆိုးမည်မှာ သေချာသည်။ Regression guard- `tests/unit/verify-ratchet-bank.test.ts`။

job သည် `release/*` သို့ မည်သည့်အခါမျှ push မလုပ်ပါ — လူတစ်ဦးက PR ကို merge လုပ်ရသောကြောင့် မှားယွင်းသည့် တိုင်းတာမှုတစ်ခုသည်
ပြန်လည်သုံးသပ်ခြင်းမရှိဘဲ အတည်မဖြစ်နိုင်ပါ။

## Allowlist မူဝါဒ

ယခင်ကတည်းက ရှိနေသော ချိုးဖောက်မှုများကြောင့် မအောင်မြင်နိုင်သည့် gate တိုင်းသည် အပြောင်းအလဲမရှိအောင် သတ်မှတ်ထားသော allowlist တစ်ခုကို အသုံးပြုသည်
(ဥပမာ၊ `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)။ မူဝါဒမှာ-

**မူလအကြောင်းရင်းကို ဖြေရှင်းပါ။ ချိုးဖောက်မှုသည် ယခင်ကတည်းက ရှိနေပြီး တူညီသော PR အတွင်း မပြင်ဆင်နိုင်သည့်အခါမှသာ allowlist ကို အသုံးပြုပါ။**

Allowlist တစ်ခုထဲသို့ entry တစ်ခု ထည့်သွင်းသည့်အခါ-

1. အကြောင်းပြချက်ပါသော comment တစ်ခု ထည့်သွင်းပါ။
2. ခြေရာခံ issue ကို ကိုးကားပါ (ဥပမာ၊ `// #3498 — Phase 2 feature, not yet implemented`)။
3. ချိုးဖောက်မှုကို ပြင်ဆင်သည့် PR တစ်ခုတည်းတွင်ပင် entry ကို ဖယ်ရှားပါ — လက်ရှိဖြစ်ပေါ်နေသော ချိုးဖောက်မှုကို မတားဆီးတော့သည့် ခေတ်မမီသော entry သည်လည်း ချို့ယွင်းချက်တစ်ခု ဖြစ်သည် (6A.3 stale-enforcement ကို အကောင်အထည်ဖော်ပြီးသည်နှင့် မည်သည့်ချိုးဖောက်မှုနှင့်မျှ မသက်ဆိုင်တော့သော allowlist entry ကြောင့် gate မအောင်မြင်ပါလိမ့်မည်)။

စမ်းသပ်မှုများကို ပိုမိုမြန်ဆန်စွာ အောင်မြင်စေရန် allowlist entry များကို **မထည့်ပါနှင့်**။ အစိမ်းရောင် gate တစ်ခုနှင့်အတူ ဆက်လက်ကြီးထွားနေသော allowlist တစ်ခုသည် အရည်အသွေးနှင့်ပတ်သက်၍ မှားယွင်းသော ယုံကြည်စိတ်ချမှုကို ဖြစ်စေသည်။

### သင်၏ PR တွင် gate တစ်ခု မအောင်မြင်သည့်အခါ

1. **Gate output ကို ဂရုတစိုက်ဖတ်ပါ** — မည်သည့်ဖိုင် သို့မဟုတ် symbol က စည်းမျဉ်းကို ချိုးဖောက်ခဲ့သည်ကို အတိအကျ ဖော်ပြပေးထားသည်။
2. **ချိုးဖောက်မှုကို ပြင်ဆင်ပါ** — gate အများစုသည် code မှန်ကန်သည်နှင့် အောင်မြင်သွားမည့် အတိအကျ ရလဒ်တူညီသော filesystem စစ်ဆေးမှုများ ဖြစ်သည်။
3. **ချိုးဖောက်မှုသည် ယခင်ကတည်းက ရှိနေခဲ့ပါက** (ဆိုလိုသည်မှာ သင်က စတင်ဖြစ်ပေါ်စေခဲ့ခြင်းမဟုတ်ဘဲ gate က ယခုမှ ၎င်းကို လွှမ်းခြုံစစ်ဆေးခြင်းဖြစ်ပါက)- အကြောင်းပြချက် comment နှင့် ခြေရာခံ issue တို့ပါဝင်သော allowlist entry တစ်ခု ထည့်သွင်းပါ။
4. **Gate သည် ratchet တစ်ခုဖြစ်ပါက** (coverage၊ ESLint warnings၊ duplication၊ complexity)- သင်၏ ပြောင်းလဲမှုကြောင့် metric ပိုဆိုးသွားခြင်း ဖြစ်သည်။ အခြေခံပြဿနာကို ပြင်ဆင်ပါ၊ သို့မဟုတ် ပြောင်းလဲမှုသည် ရည်ရွယ်ချက်ရှိပြီး metric ကျဆင်းမှုကို လက်ခံနိုင်ပါက (အလွန်ရှားပါးစွာ) `npm run quality:ratchet -- --update` ကို run ပါ — သို့သော် PR description တွင် အကြောင်းရင်းကို မှတ်တမ်းတင်ပါ။
5. **အကြံပြုချက်ပေးသည့် gate များ** (`continue-on-error: true`) သည် အချက်အလက်ပေးရန်သာ ဖြစ်သည် — ၎င်းတို့သည် merge လုပ်ခြင်းကို မတားဆီးသော်လည်း CI summary တွင် ပေါ်လာမည်ဖြစ်သည်။ သို့သော်လည်း ၎င်းတို့ကို ပြင်ဆင်ပါ။

## Gate အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `scripts/check/check-<name>.mjs` (သို့မဟုတ် `.ts`) ကို ဖန်တီးပါ။ မူဝါဒ gate များသည် 0/1 ဖြင့် ထွက်သည်။
   Ratchet ပုံစံ gate များသည် `collect-metrics.mjs` မှတစ်ဆင့် တိုင်းတာချက်တစ်ခုကို `quality-metrics.json` သို့ ထုတ်ပေးသည်။
2. `package.json` တွင် `"check:<name>": "node scripts/check/check-<name>.mjs"` ကို ထည့်သွင်းပြီး
   alias နှင့် ၎င်း၏ command အတိအကျကို `config/quality/gate-manifest.json` တွင် တစ်ပြိုင်တည်း ကိုက်ညီအောင် ပြင်ဆင်ပါ။
   ရှိပြီးသား validation alias တစ်ခုကို ပြောင်းလဲခြင်း သို့မဟုတ် ဖယ်ရှားခြင်း ပြုလုပ်သည့်အခါတွင်လည်း အလားတူ တစ်ပြိုင်တည်း ကိုက်ညီအောင် ပြင်ဆင်ပါ။
   `npm run check:gate-manifest` ကို run ပါ။ pre-commit hook နှင့် CI change classification တို့က
   ဤ contract ကို မဖြစ်မနေ လိုက်နာစေသည်။
3. `.github/workflows/ci.yml` အတွင်း သင့်လျော်သော job အောက်တွင် ၎င်းကို ချိတ်ဆက်ပါ
   (မူဝါဒ → `lint` သို့မဟုတ် `docs-sync-strict`; ratchet → `quality-gate`)။
4. ၎င်းတွင် ခွင့်ပြုစာရင်းတစ်ခု ပါဝင်ပါက ခေတ်မမီတော့သော entry များကို အလိုအလျောက် ရှာဖွေနိုင်စေရန်
   `scripts/check/lib/allowlist.mjs` မှ `reportStaleEntries()` ကို အသုံးပြုပါ။
5. gate ၏ ရှာဖွေစစ်ဆေးမှု logic ကို လွှမ်းခြုံသည့် စမ်းသပ်မှုတစ်ခုကို `tests/unit/build/` တွင် ရေးပါ။
6. ဤစာတမ်းကို အပ်ဒိတ်လုပ်ပါ (သက်ဆိုင်ရာ job ဇယားတွင် row တစ်ခု ထည့်ပါ)။

## Agent ကိရိယာများ- LSP-in-the-loop (ရွေးချယ်အသုံးပြုနိုင်)

CI gate များအပြင် OmniRoute တွင် **ရွေးချယ်အသုံးပြုနိုင်သော** `agent-lsp` scaffold
(project အဆင့် `.mcp.json`၊ Fase 7 Task 15) ပါရှိသည်။ coding agent များအတွက် TypeScript language server ကို ဖော်ထုတ်ပေးရန် `.mcp.json`
ကို ဖန်တီးပါ။ ထိုသို့ဖြင့် ၎င်းတို့သည် code မရေးမီ symbol များ /
diagnostic များကို ဖြေရှင်းနိုင်မည်ဖြစ်သည် — ၎င်းသည် မရှိသည့် symbol များကို ဖန်တီးမိခြင်းကြောင့် ဖြစ်သော error များကို အရင်းအမြစ်မှ လျှော့ချပေးသည့်
`typecheck:core` ၏ compile-before-claim တွဲဖက်တစ်ခုဖြစ်သည်။ ၎င်းကို ရည်ရွယ်ချက်ရှိရှိ
အလိုအလျောက် မတင်ထားပါ (MCP↔LSP bridge ကို သင်ကိုယ်တိုင် ရွေးချယ်ပြီး အတည်ပြုရမည်)။ ပျက်နေသော entry တစ်ခုသည်
ချိတ်ဆက်မှု error ကိုသာ log လုပ်ပြီး session များကို မည်သည့်အခါမျှ မပျက်စေပါ။

## ကျိုးကြောင်းညီညွတ်အောင် ပြန်လည်စီစဉ်ရန် ကျန်ရှိစာရင်း (ROI ပြန်လည်သုံးသပ်မှု — အဆင့် 9 လှိုင်း 3)

ဤစာရင်းကို 2026-06-17 တွင် `ci.yml` နှင့် တိုက်ဆိုင်စစ်ဆေးထားသည် (ယခင်ဗားရှင်းတွင်
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` တို့ မပါဝင်ခဲ့ပါ)။ တိုက်ဆိုင်စစ်ဆေးပြီးသော အစုကို
ROI ပြန်လည်သုံးသပ်ရာတွင် အောက်ပါ ကျိုးကြောင်းညီညွတ်အောင် ပြန်လည်စီစဉ်နိုင်မည့် အရာများကို
ဖော်ထုတ်နိုင်ခဲ့သည်။ **ပေါင်းစည်းမှုများသည် စက်ပိုင်းဆိုင်ရာ CI အပြောင်းအလဲများဖြစ်ပြီး၊
ပြောင်းလဲဖွင့်ခြင်း/ဖယ်ရှားခြင်းများသည် အော်ပရေတာအတွက် သီးသန့်ထားသည့် မူဝါဒဆိုင်ရာ ဆုံးဖြတ်ချက်များဖြစ်သည်။** အောက်ပါအရာများထဲမှ
မည်သည့်အရာကိုမျှ ယခုအချိန်အထိ အသုံးမချရသေးပါ။

**အထက်တွင် မှတ်တမ်းမတင်ထားသေးသည့်အရာများလည်း ရှိသည်** (အကြံပြုအဆင့်၊ အချက်ပြမှုနည်းပါးသည်)။ ၎င်းတို့မှာ `docs-lint` job
(markdownlint + Vale၊ job တစ်ခုလုံးတွင် `continue-on-error`) နှင့် သီးခြား scanner workflow များဖြစ်သော
`semgrep.yml` / `codeql.yml` / `scorecard.yml` တို့ဖြစ်သည်။ `semgrepFindings: 0` သည်
`quality-baseline.json` တွင် ပါဝင်သော်လည်း `ci.yml` ရှိ ပိတ်ဆို့တားဆီးသည့် ratchet နှင့် ချိတ်ဆက်ထားခြင်းမရှိပါ — ယင်း metric သည်
လက်ရှိတွင် အထီးကျန်နေသည်။

### ပေါင်းစည်းခြင်း / ထပ်နေမှုဖယ်ရှားခြင်း (စက်ပိုင်းဆိုင်ရာ၊ အန္တရာယ်ပိုနည်း)

အရာတစ်ခုစီကို 2026-06-17 ရှိ အမှန်တကယ် အသုံးပြုနေသော gate အခြေအနေနှင့် တိုက်ဆိုင်အတည်ပြုထားသည် (ယုံကြည်သော်လည်း ပြန်လည်စစ်ဆေးသည်)။
"သိသာထင်ရှားသည့်" ပေါင်းစည်းမှုအချို့တွင် ဖုံးကွယ်နေသော နည်းပညာကြွေးမြီများ ရှိနေကြောင်း တွေ့ရှိခဲ့ရပြီး ၎င်းတို့သည် **တိုက်ရိုက်အစားထိုးအသုံးပြုနိုင်သည့် သန့်ရှင်းသော အပြောင်းအလဲများ မဟုတ်ပါ**။

- **`check:docs-sync` ကို နှစ်ကြိမ် လုပ်ဆောင်သည်** — `lint` job အတွင်း သီးခြားလုပ်ဆောင်ပြီး `check:docs-all` (`docs-sync-strict`) နှင့် husky pre-commit hook အတွင်း၌လည်း ထပ်မံလုပ်ဆောင်သည်။ ✅ **ပြီးပါပြီ** — သီးခြား `lint` ခေါ်ယူလုပ်ဆောင်မှုကို ဖယ်ရှားပြီးဖြစ်သည်။
- **CVE စစ်ဆေးခြင်း** — ❌ **သန့်ရှင်းသော ပေါင်းစည်းမှု မဟုတ်ပါ။** `audit:deps` သည် lockfile ငါးခုလုံးအတွက် အလွန်ပြင်းထန်သော သတိပေးချက်များနှင့် မပြည့်စုံသော audit များကို ပိတ်ဆို့ပြီး၊ လက်ရှိမူဝါဒအရ ပြင်းထန်မှုမြင့်သော သတိပေးချက်များကို warning အဖြစ် အစီရင်ခံသည်။ သို့သော် `check:vuln-ratchet` (osv) သည် repository ထဲသို့ ထည့်သွင်းထားသော baseline နှင့် နှိုင်းယှဉ်ရာတွင် _နောက်ဆုတ်မှု_ ရှိမှသာ ကျရှုံးပြီး၊ လိုအပ်သည့်အခါ တိုင်းတာချက် ပျောက်ဆုံးနေခြင်းကို ငြင်းပယ်သည်။ အဓိပ္ပာယ်ဖွင့်ဆိုမှုများ မတူညီပါ — `audit:deps` ကို ဖယ်ရှားပါက အလွန်ပြင်းထန်မှုအဆင့်အတွက် ပကတိ gate နှင့် သီးခြား package audit အထောက်အထားများ ဆုံးရှုံးသွားမည်ဖြစ်သည်။ နှစ်ခုလုံးကို ဆက်လက်ထားရှိပါ။
- **Cycle ရှာဖွေခြင်း** — ✅ **ပြီးပါပြီ** (#15159 G-01/G-02)။ ဤနေရာရှိ စာသားဟောင်းတွင် `check:cycles` ကို "အောင်မြင်နေသော၊ ရွေးချယ်ပြင်ဆင်ထားသည့်" gate ဟု ခေါ်ဆိုခဲ့ပြီး `check:circular-deps` (dpdm) က cycle 91 ခု အစီရင်ခံခဲ့သောကြောင့် ၎င်းကို ပိတ်ဆို့သည့် gate အဖြစ် ဆက်ထားရန် အကြောင်းပြခဲ့သည်။ ထိုအောင်မြင်မှုသည် **မှားယွင်းသော အောင်မြင်မှု** ဖြစ်သည်။ `check:cycles` သည် subdirectory 5 ခု (ဖိုင် 450 ခု) ကိုသာ စစ်ဆေးခဲ့ပြီး static `import|export … from` နှင့်သာ ကိုက်ညီစစ်ဆေးကာ `@/` နှင့် `@omniroute/open-sse/` specifier အားလုံးကို ဖယ်ထုတ်ခဲ့သည်။ ထို့ကြောင့် repository ကို လွှမ်းမိုးနေသော dynamic-import + alias cycle များကို မမြင်နိုင်ခဲ့ပါ။ ပြင်ဆင်ပြီးဖြစ်သည်။ ယခု gate သည် `src` + `open-sse` (ဖိုင် 5023 ခု) ကို လှည့်လည်စစ်ဆေးပြီး TypeScript AST မှ specifier များကို စုဆောင်းသည် (ထို့ကြောင့် `import("…")` ကို ထည့်တွက်သော်လည်း type-position ရှိ `typeof import("…")` ကို မထည့်တွက်ပါ)၊ ထို့အပြင် tsconfig `paths` ကိုလည်း ဖြေရှင်းသည်။ 0 ခုမဟုတ်ဘဲ cycle **14** ခုကို တွေ့ရှိသည်။ ယခင်ကတည်းကရှိနေသော cycle 14 ခုကို gate PR တစ်ခုအတွင်း မပြင်ဆင်နိုင်သောကြောင့် `check:cycles` သည် ယခု **ratchet** (`--ratchet`၊ `quality-baseline.json` ရှိ အများဆုံးကန့်သတ်ချက် `metrics.cycles.value = 14`၊ `direction: down`) ဖြစ်လာသည် — ၎င်းသည် မည်သည့် _နောက်ဆုတ်မှု_ ကိုမဆို ပိတ်ဆို့ပြီး အရေအတွက်သည် လျော့ကျရန်သာ ခွင့်ပြုသည်။ CI သည် `npm run check:cycles:ratchet` ကို လုပ်ဆောင်သည်။ တဖြည်းဖြည်း လျှော့ချဖြေရှင်းမှုကို **A-01** နှင့်အတူ ဆောင်ရွက်မည်။ `check:circular-deps` (dpdm) ကို ပိုမိုကျယ်ပြန့်သော ဒုတိယအမြင်အဖြစ် အကြံပြုအဆင့်တွင် ဆက်ထားမည်။
- **ရှုပ်ထွေးမှု** — ✅ **ပြီးပါပြီ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`)။ ESLint ဖြင့် တစ်ကြိမ်သာ လှည့်လည်စစ်ဆေးပြီး ruleId အလိုက် ရေတွက်သဖြင့် cyclomatic+max-lines နှင့် cognitive baseline များသည် သီးခြားလွတ်လပ်စွာ ရှိနေသည်။ `check:complexity` / `check:cognitive-complexity` တစ်ခုချင်းစီကို local `--update` အတွက် ဆက်လက်ထားရှိသည်။

- **`check:node-runtime` ကို job 11 ခုတွင် လုပ်ဆောင်သည်** — ⚠️ **ROI နည်းပါးသည်။** တစ်ခုစီသည် သီးခြား runner ဖြစ်ပြီး စစ်ဆေးမှုမှာ <1s သာ ကြာသည်။ စုစုပေါင်း ချွေတာနိုင်မှုမှာ ~10s ဖြစ်ပြီး၊ job တစ်ခုချင်းစီအတွက် ကုန်ကျစရိတ်နည်းသော အကာအကွယ်တစ်ခု ဆုံးရှုံးရမည်ဖြစ်သည်။ အပြောင်းအလဲကြောင့် ဖြစ်လာမည့် အရှုပ်အရှင်းနှင့် မတန်ပါ။
- **CI lint ရှိ `typecheck:noimplicit:core`** — ✅ **lint job မှ ဖယ်ရှားပြီးဖြစ်သည်** (ယခင်က အကြံပြုအဆင့် `continue-on-error` ဖြစ်သည်)။ ပိတ်ဆို့သည့် type မျက်နှာပြင်မှာ `typecheck:core` + `check:type-coverage` ဖြစ်သည်။ Local script ကို ဆက်လက်ထားရှိသည်။

`src/i18n/messages/<locale>.json` တစ်ခုစီ၏ နောက်ဆုံးအဆင့်ကီးအစုကို `en.json` နှင့် နှိုင်းယှဉ်ပြီး

ရှိနေသည်ဟု သတ်မှတ်သည် (၎င်းတို့၏ အကြောင်းအရာသည် အချိုးစစ်ဆေးရေးဂိတ်၏ တာဝန်ဖြစ်သည်)။ ၎င်းသည်

အဆင့်နှစ်ခုလုံးသည် အလုပ် `i18n-ui-coverage` တွင် ပါဝင်သည်။

#### `check-new-key-coverage` — i18n ကီးအသစ် စစ်ဆေးရေးဂိတ်

`check-ui-value-drift` ၏ ညီအစ်ကိုစစ်ဆေးမှုဖြစ်သည်။ ထိုစစ်ဆေးမှုသည် အင်္ဂလိပ်တန်ဖိုးတစ်ခုကို **ပြန်လည်ရေးသား**
ထားသော်လည်း ၎င်း၏ဘာသာပြန်ချက်များကို မပြောင်းဘဲ ထားခဲ့ခြင်းကို ဖမ်းယူပြီး၊ ဤစစ်ဆေးမှုက အင်္ဂလိပ်ကီးတစ်ခုကို **ထည့်သွင်း**
ထားသော်လည်း အချို့ locale များက ၎င်းကို လုံးဝမရရှိခဲ့ခြင်းကို ဖမ်းယူသည်။

`check-ui-keys-coverage` သည် ဤအခြေအနေမျိုးကို မမြင်နိုင်ပါ။ ၎င်းသည် locale တစ်ခုစီအတွက် ရာခိုင်နှုန်းအနည်းဆုံးတန်ဖိုးကို သတ်မှတ်ပြီး
~13,000 နောက်ဆုံးအဆင့်ကီးအနက် ဆယ့်တစ်ခု ပျောက်နေသော်လည်း လွှမ်းခြုံမှုမှာ 99.9% ဖြစ်နေသည်။ ဘာသာစကားတစ်ခုချင်းစီအလိုက် ရာခိုင်နှုန်းတစ်ခုဖြင့်
"ဤလုပ်ဆောင်ချက်ကို ဘာသာမပြန်ဘဲ ထုတ်ဝေခဲ့သည်" ဟူသည်ကို မဖော်ပြနိုင်ပါ — လုပ်ဆောင်ချက်တစ်ခုလုံးသည် စာသားတစ်ခုမျှမပါဘဲ
locale အသစ်တစ်ခုသို့ ရောက်ရှိနိုင်ပြီး ကိန်းဂဏန်းမှာ လုံးဝမပြောင်းနိုင်ပါ။

၎င်းက မှတ်တမ်းတင်ထားသော ဖြစ်ရပ်မှာ Orchestration Canvas ၏ Phase 3 က ထိုအချိန်က ရှိနေသော locale 42 ခုလုံးအတွက်
ကီး ဆယ့်တစ်ခုကို ဘာသာပြန်ခဲ့ခြင်းဖြစ်သည်။ နာရီအနည်းငယ်အကြာတွင် EU-language batch (#13044) က repo ကို
locale 51 ခုအထိ တိုးစေခဲ့ပြီး အသစ်ဝင်လာသော ကိုးခု (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) သည်
၎င်းတို့ကို လုံးဝမရရှိခဲ့ပါ။ `deepMergeFallback` သည် ပျောက်နေသောကီးအတွက် အင်္ဂလိပ်စာသားကို အစားထိုးပေးသဖြင့်
ပျက်ကွက်မှုပုံစံမှာ UI အလွတ်မဟုတ်ဘဲ ဘာသာမပြန်ထားသော UI ဖြစ်ခဲ့သည် — အမှန်တကယ်ဖြစ်ပြီး ဒီဇိုင်းအရ အသံတိတ်နေခဲ့သည်။

၎င်း၏ ညီအစ်ကိုစစ်ဆေးမှုကဲ့သို့ပင် ၎င်းသည် **diff-aware** ဖြစ်ပြီး merge base ရှိ အင်္ဂလိပ်စာသားကို လက်ရှိအလုပ်လုပ်နေသော
tree နှင့် နှိုင်းယှဉ်သဖြင့် ယခင်ကတည်းက ရှိနေသော ကွက်လပ်များသည် မပြောင်းလဲဘဲ ကျန်ရှိကာ စစ်ဆေးရေးဂိတ်ကို ဖွင့်ရန် migration မလိုခဲ့ပါ။

**`__MISSING__:<english>` marker တစ်ခုက ၎င်း၏လိုအပ်ချက်ကို မဖြည့်ဆည်းပါ (2026-09-17 မှစ၍)။** ယခင်က ၎င်းသည်
မှတ်တမ်းတင်ထားသော ရွှေ့ဆိုင်းနည်းဖြစ်ခဲ့သည် — runtime က မှန်ကန်သော အင်္ဂလိပ်စာသားသို့ fallback လုပ်သည် — သို့သော်
2026-09-16 တွင် feature PR ရှစ်ခုက ကီး 61 ခု ထည့်ပြီး ဘာသာပြန်မည့်အစား locale 65 ခုလုံးတွင် marker ကို
ထည့်သွင်းခဲ့သည်။ ဤစစ်ဆေးရေးဂိတ်က ၎င်းတို့အားလုံးကို လက်ခံခဲ့ပြီး PR များကို မည်သည့်အရာကမျှ မတားဆီးခဲ့သဖြင့်
ပိတ်ဆို့မှုလုပ်သော ဘာသာပြန်ချက်အစစ် အချိုးစစ်ဆေးရေးဂိတ်သည် release tip တွင် လူတိုင်းအတွက် မအောင်မြင်ခဲ့သည်
(pt-BR 3.2 % > 2.5 % + 0.5)။ ယခု marker တစ်ခုကို ပျောက်နေသော ဘာသာပြန်ချက်အဖြစ် ဆုံးဖြတ်သည်။ မအောင်မြင်မှုကို

#### `check-vitest-exclusions` — ရပ်နားထားသော စမ်းသပ်မှု စစ်ဆေးရေးဂိတ်

`vitest.config.ts` ၏ `exclude` စာရင်းထဲရှိ ဖိုင်တစ်ခုသည် မလည်ပတ်သော စမ်းသပ်မှုတစ်ခုဖြစ်ပြီး tree ကို ဖတ်ရှုသူအတွက်မူ
လွှမ်းခြုံမှုရှိသကဲ့သို့ မြင်ရသည်။ ဖိုင် ခြောက်ဆယ့်နှစ်ခုသည် မှတ်ချက်
`// #8618 — pre-existing failure; remove this exclusion when fixed` နောက်ကွယ်တွင် စုပုံလာခဲ့သည်။ Issue #8618 ကို
2026-08-11 တွင် ပိတ်ခဲ့သော်လည်း ၎င်းက ခြေရာခံသည့်စာရင်းမှာ entry 45 ခုမှ 62 ခုအထိ တိုးလာခဲ့ပြီး အသစ်တစ်ခုစီသည်
ပိတ်သွားသော issue ကို ညွှန်းသည့် မှတ်ချက်ကို ဆက်ခံခဲ့သည်။ နောက်ဆုံးတွင် စာရင်းကို ဖိုင်တစ်ခုချင်းစီအလိုက် တိုင်းတာသောအခါ (#13204)၊ **62 ခုအနက် 51 ခုသည်
မူရင်းကုဒ်ကို မပြောင်းလဲဘဲ လက်ရှိ tree ပေါ်တွင် အောင်မြင်ခဲ့သည်**။

ဤစစ်ဆေးရေးဂိတ်သည် တကယ့်ဖိုင်တစ်ခုသို့ ဖြေရှင်းရောက်ရှိသော exclusion တစ်ခုစီအား (a) ခြေရာခံ issue တစ်ခုကို အမည်ဖော်ပြရန်နှင့်
(b) ၎င်း၏ တိုင်းတာထားသော အခြေအနေနှင့်အတူ `config/quality/vitest-exclusions.json` တွင် ပါဝင်ရန် လိုအပ်စေသည်။ ထို့ကြောင့်
exclusion တစ်ခု ထည့်ခြင်းသည် entry 60 ပါသော array ထဲတွင် နောက်ထပ်စာကြောင်းတစ်ကြောင်း ထည့်ခြင်းမဟုတ်ဘဲ သီးသန့်ဖိုင်တစ်ခုထဲရှိ
ပြန်လည်သုံးသပ်နိုင်သော diff တစ်ခုဖြစ်လာသည်။ ၎င်းသည် ဖယ်ထုတ်ထားသော စမ်းသပ်မှုများကို ရည်ရွယ်ချက်ရှိရှိ ပြန်မလည်ပတ်ပါ —
