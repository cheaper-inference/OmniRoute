## ဂိတ်စာရင်းနှင့် အကောင်အထည်ဖော်မှု ပရိုဖိုင်များ

### ကိုယ်စားလှယ်လောင်း ဝင်ခွင့်

CI နှင့် Quality Gates အလုပ်အသွားအလာတစ်ခုစီသည် တည်ငြိမ်သောစီရင်ချက်တစ်ခုစီကို ထုတ်လွှတ်သည်- `Gate / CI` နှင့် `Gate / Quality`. ၎င်းတို့၏ ဗားရှင်းဖြင့် ဝင်ခွင့်မူဝါဒသည် လိုအပ်သည့် သို့မဟုတ် အကြံပေးချက်အဖြစ် အထက်ပိုင်းအလုပ်တိုင်းကို ရေတွက်ပါသည်။ သက်ဆိုင်ရာ လိုအပ်သော အလုပ်တစ်ခု အောင်မြင်ရပါမည်- ပျောက်ဆုံးနေသော၊ ပယ်ဖျက်လိုက်၊ ကျော်သွားသည်၊ ဆိုင်းငံ့ထားပြီး မသိသောရလဒ်များကို PASS သတ်မှတ်၍မရပါ။ မှန်ကန်သော docs-only သို့မဟုတ် catalog-only အမျိုးအစားခွဲခြင်းသည် ကုဒ်လမ်းကြောင်းကို အသုံးချ၍မရပေ။ PR မူကြမ်းသည် လက်ခံထားသော ကိုယ်စားလှယ်မဟုတ်ပါ။ `hotfix` အညွှန်းသည် သက်သေအထောက်အထား မလွတ်ပါ။

အလုပ်အသွားအလာနှစ်ခုလုံးသည် PRs main/release အကိုင်းအခက်များအဖြစ် ဖုံးလွှမ်းကာ၊ `main` သို့ တွန်းပို့သည်၊ လူကိုယ်တိုင် ပေးပို့ခြင်းနှင့် အုပ်စုလိုက်ဖြစ်ရပ်များကို ပေါင်းစည်းသည်။ ရွေးချယ်မှု အပြည့်အစုံကို တွန်းပို့ခြင်း၊ ပေးပို့ခြင်းနှင့် ပေါင်းစည်းခြင်းတို့ကို လုပ်ဆောင်ပါ။ `release/**` သို့ တွန်းပို့ခြင်းများ မစတင် → ( PR )`docs/ops/RUNNER_BOX.md` Forks နှင့် အဖွဲ့များ ပေါင်းစည်းထားသော အလုပ်များအတွက် လက်ခံထားသော အပြေးသမားများကို အသုံးပြုသည်၊ ဖြန့်ချိခြင်းမပြုမီ လုံလောက်သော လက်ခံနိုင်သော စွမ်းရည်ကို စစ်ဆေးရပါမည်။

သာမန် PR သည် အမြန်ရွေးချယ်မှုကို လုပ်ဆောင်သည်။ ဝင်ခွင့်မူဝါဒ၏ `full-code` နှင့် `full-code-e2e` လမ်းကြောများ (E2E၊ ပေါင်းစပ်မှု၊ ပက်ကေ့ဂျ်အနုပညာ၊ Electron မီးခိုး၊ Bun SQLite၊ ဂေဟစနစ်နှင့် ပရိုတိုကောဖောက်သည်များ) သည် ပေါင်းစည်းထားသော တန်းစီမူကြမ်း သို့မဟုတ် အပြည့်အဝလည်ပတ်မှုတွင်သာ လုပ်ဆောင်သည်- `gh workflow run ci.yml --ref <branch>`.

JSON ပြေစာတစ်ခုစီသည် check-out SHA၊ workflow run နှင့် ကြိုးစားမှုကို ခွဲခြားသတ်မှတ်သည်။ CLI သည် checkout/event SHA မကိုက်ညီမှုကို ငြင်းပယ်သည်။ အလုပ်အသွားအလာ စမ်းသပ်မှုများသည် စီရင်ချက်ချသည့်အလုပ်၏ `needs` စာရင်းနှင့် မူဝါဒအဖွဲ့ဝင်ခြင်းကို ချိတ်ဆက်ထားသောကြောင့် လမ်းအသစ် သို့မဟုတ် ဖယ်ရှားထားသော လမ်းကြောသည် တိတ်တဆိတ် ပျောက်ကွယ်သွားမည်မဟုတ်ပေ။ ပြေစာများသည် ထုတ်ဝေခြင်း၊ ဖြန့်ကျက်ခြင်း သို့မဟုတ် လက်ရှိအကြံပေးစကင်နာတစ်ခု၏ အတွင်းပိုင်းများကို ထုတ်ဝေခြင်းမဟုတ်ဘဲ ၎င်းတို့၏လုပ်ငန်းအသွားအလာကို အကျုံးဝင်ပါသည်။ ဌာနခွဲစည်းမျဥ်းများတွင် စစ်ဆေးမှုအမည်နှစ်ခုလုံးကို အသက်သွင်းခြင်းသည် သီးခြားစီမံခန့်ခွဲရေးဆိုင်ရာ ပြောင်းလဲမှုတစ်ခုဖြစ်သည်။ ဤအလုပ်များကို ပေါင်းထည့်ခြင်းသည် အကိုင်းအခက်ကို မကာကွယ်နိုင်ပါ။

### တန်းစီခြင်းကို ပေါင်းစည်းပါ။

`queue` အညွှန်းသည် PR တစ်ခုကို ပေါင်းစည်းထားသော တန်းစီ (`.mergify.yml`) သို့ ပို့ပေးသည်။ Mergify သည် `mergify/merge-queue/` အကိုင်းအခက်တစ်ခုပေါ်တွင် PR မူကြမ်းကိုဖွင့်သည်၊ CI ထိုနေရာတွင် ရွေးချယ်မှုအပြည့်အစုံကို လုပ်ဆောင်ပြီး `Gate / CI`၊ `Gate / Quality` နှင့် `Merge integrity (changelog + generated skills)` ကျော်သွားသောအခါ မူရင်း PR ပေါင်းစည်းသွားသည်။

Mergify သည် မူကြမ်း၏ဖော်ပြချက်တွင် ၎င်း၏တန်းစီဇယားအနှစ်ချုပ်ကို ရေးသားပြီး အခြားအက်ပ်များက ၎င်းကို တည်းဖြတ်နိုင်သည်။ ထိုကဲ့သို့ မူကြမ်းတွင် `pull_request` `edited` ဖြစ်ရပ်သည် ၎င်း၏ကိုယ်ပိုင်ငွေကြေးအုပ်စု (`-queue-edit-<run_id>`) ကို ယူသောကြောင့် ၎င်းသည် မူကြမ်း၏ တကယ့်လည်ပတ်မှုကို မပယ်ဖျက်နိုင်ဘဲ ၎င်းသည် ဂိတ်နှင့် မက်ထရစ်ကို ကျော်သွားပါသည်။ `Merge integrity` သာ လည်ပတ်နေသေးသည်။ Mergify သည် မအောင်မြင်သောစစ်ဆေးချက်တစ်ခုအဖြစ် ကျော်သွားသော `Gate / CI` ဖတ်ပြီး PR စီစစ်ပေးသောကြောင့် skiped gate အလုပ်တွင် မတူညီသောစစ်ဆေးမှုအမည်တစ်ခုပါရှိသည်။

ခေတ္တရပ်ဆိုင်းပြီးနောက်၊ တွန်းအားသည် PR ကို အမြဲတမ်း queue လုပ်မည်မဟုတ်ပါ။ `@mergifyio queue` ကို မှတ်ချက်ပေးလိုက်ပါ။

### လက်ခံမှုလျော့ပါးရေးတွင် အထောက်အထားများ သိမ်းဆည်းထားသည်။

`scripts/quality/validate-release-acceptance.mjs` ထောက်ပံ့ပေးထားသော အစီအစဉ်နှင့် ၎င်း၏ဖော်ပြချက်များကို လျှော့ချပေးသည်။ ပြီးပြည့်စုံသော ပိုက်လိုင်းကို အကျုံးဝင်စေမည့် အစီအစဥ်ကို မသတ်မှတ်ထားပေ။ ၎င်းအစီအစဥ်သည် `VERIFIED` ဖြစ်သည့်အခါ၌ပင် ၎င်း၏အစီရင်ခံစာများသည် `releaseAcceptance: false` အတိအလင်းသတ်မှတ်ထားသည်။ `release-acceptance.yml` အလုပ်အသွားအလာသည် အစစ်အမှန်တည်ဆောက်မှု၊ ပက်ကေ့ချ်၊ boot သို့မဟုတ် ပရိုမိုးရှင်းဖြတ်ပိုင်းများကို မဟုတ်ဘဲ အရိပ်တွဲများကို အသုံးပြုနေဆဲဖြစ်သည်။

CLI သည် သိမ်းဆည်းထားသော အထောက်အထားများကို စစ်ဆေးရန် `--evidence-root` လိုအပ်သည်။ ဖိုင်များကို `<evidence-root>/<artifact_id>/<member>` အဖြစ် ဖြေရှင်းပြီး SHA-256 အဖြစ် hash လုပ်ထားသည်။ အထောက်အထားမရှိဘဲ PASS မှတ်တမ်းတစ်ခု၊ ပျောက်ဆုံးနေသော သို့မဟုတ် ပြောင်းလဲထားသော ဖိုင်၊ မလုံခြုံသောလမ်းကြောင်း သို့မဟုတ် symlink သည် အတည်ပြုခြင်းကို တားဆီးသည်။ ပျောက်ဆုံးနေသောဖိုင်များသည် အောင်မြင်သောမှတ်တမ်းအလွတ်များနှင့် ညီမျှသည်မဟုတ်ပါ။ လက်ရှိ SHA/run/attempt စစ်ဆေးမှုများသည် အမှီအခိုကင်းဆဲဖြစ်သည်- ကိုက်ညီသော bytes သည် ဟောင်းနွမ်းနေသောပြေစာအား ကယ်တင်နိုင်မည်မဟုတ်ပေ။ ဖိုင်ခိုင်မာမှုသည် စစ်မှန်သောစစ်မှန်မှု သို့မဟုတ် ပစ္စည်းပရိုမိုးရှင်း၏ သက်သေမဟုတ်ပါ။

### Static scan စာရင်း

ဗားရှင်းသတ်မှတ်ထားသော npm-alias စာရင်းနှင့် static-scan အဖွဲ့ဝင်မှုသည် `config/quality/gate-manifest.json` တွင်နေထိုင်သည်။ script အမည်များနှင့် `package.json` နှင့် ပတ်သက်သည့် တိကျသော command များကို အတည်ပြုရန် `npm run check:gate-manifest` ကို ဖွင့်ပါ။ ထပ်တိုးမှုများ၊ ဖယ်ရှားခြင်းနှင့် အမိန့်ပေးထားသော ဒရုန်းများသည် ဒေသတွင်းချိတ်နှင့် CI ရှိ ပြောင်းလဲမှုအမျိုးအစားခွဲခြားခြင်းအလုပ်များ နှစ်ခုစလုံးတွင် မအောင်မြင်ပါ။ နာမည်တူတစ်ခုသည် အလုပ်အသွားအလာအလုပ်၊ မက်ထရစ်ဥပမာ သို့မဟုတ် စမ်းသပ်မှုကိစ္စမဟုတ်ပါ- ဤအရေအတွက်များကို အပြန်အလှန်ဖလှယ်နိုင်သောအဖြစ် မဖော်ပြရပါ။

၎င်းတို့ကို လုပ်ဆောင်ခြင်းမရှိဘဲ ရွေးချယ်ထားသော နာမည်တူများကို စစ်ဆေးရန် `npm run quality:scan -- --list` သို့မဟုတ် `npm run quality:scan:fast -- --list` အသုံးပြုပါ။ အပြေးသမားသည် npm entrypoint ကို ခေါ်ဆိုသည်၊ ထို့ကြောင့် ၎င်း၏ runtime (configured လုပ်ထားသော Bun အပါအဝင်) ကို ထိန်းသိမ်းထားသည်။ မန်နီးဖက်စ်သည် သီးခြားခေါ်ဆိုထားသည့်အတိုင်း အဆိုပါပရိုဖိုင်များအပြင်ဘက်တွင် နာမည်တူများကို မှတ်တမ်းတင်ပြီး ပြုပြင်ထိန်းသိမ်းမှုအမိန့်များကို ဖတ်သာစကင်န်ပရိုဖိုင်များတွင် တားမြစ်ထားသည်။

ဤပရိုဖိုင်များသည် static scan ကိုသာ အကျုံးဝင်ပါသည်။ ၎င်းတို့သည် ထုတ်ကုန်စစ်ဆေးမှုများ၊ အကျုံးဝင်မှု၊ ထုပ်ပိုးမှု၊ ပြင်ပစစ်ဆေးမှုများ သို့မဟုတ် ကိုယ်စားလှယ်တစ်ဦး၏ အပြည့်အဝလက်ခံမှုကို အသိအမှတ်ပြုခြင်းမပြုပါ။ Workflow ဝင်ခွင့်သည် ချိတ်ဆက်ထားသော `config/quality/admission-policy.json` နှင့် `scripts/quality/admission-verdict.mjs` ကို အသုံးပြုသည်။ ထုတ်ဝေသူ-လေ့လာသူ ပရိုဖိုင်းများသည် သီးခြားတည်ရှိနေပါသည်။ ၎င်းတို့၏ သက်ဆိုင်ရာ ချက်လက်မှတ်များနှင့် ပြေစာများကို လွတ်လပ်စွာ စစ်ဆေးပါ။ လေ့လာသူ၏ static command အပြည့်အစုံကို `audit:deps`၊ mutation-test ရွေးချယ်မှုနှင့် ဘာသာပြန်စစ်ဆေးမှုများအပါအဝင် `config/quality/release-green-static-profile.json` တွင် ကြေငြာထားသည်။ loader သည် package.json နှင့် စံပြထားသော CI/Quality ကြေငြာချက်များကို ဆန့်ကျင်သည့် npm ညွှန်ကြားချက်များကို တရားဝင်စေပါသည်။ အကြောင်းပြချက်များအဖြစ် shell တိုကင်များကို လုပ်ဆောင်မည့်အစား drift ကို ငြင်းပယ်သည်။ လိုအပ်သော စကင်နာ SKIP/INCOMPLETE အထွက်သည် PASS သတ်မှတ်၍ မရပါ။ ပရိုဖိုင်သည် ၎င်း၏ ပြင်ပ ချန်လှပ်ခြင်းများကို မှတ်တမ်းတင်ပြီး လက်ခံထားသော လွှမ်းခြုံမှု၊ စမ်းသပ်မှု မက်ထရစ်များ၊ ပက်ကေ့ခ်ျ သို့မဟုတ် အသုံးချမှု အထောက်အထားများကို အစားထိုးမထားပါ။ အောက်ဖော်ပြပါ စကားပြေစာရင်းသည် ဂိတ်တစ်ခု အမှန်တကယ်ထွက်ကြောင်း အထောက်အထားမဟုတ်ဘဲ ကိုးကားချက်ဖြစ်သည်။

Script များသည် `scripts/check/` (မူဝါဒတံခါးများ) နှင့် `scripts/quality/` (ratchet engine) အောက်တွင် နေထိုင်ပါသည်။ CI အမှန်တရား၏အရင်းအမြစ်သည် `.github/workflows/ci.yml` ဖြစ်သည်။

### PR အမြန်လမ်း (`quality.yml`) ကို လွှတ်ပေးပါ

`.github/workflows/quality.yml` main/release PRs တွင် CI ဖြည့်စွက်သည်၊ `main` သို့တွန်းသည်၊ ပေးပို့ပြီးအုပ်စုများကိုပေါင်းစည်းသည်။ PRs လမ်းကြောင်းကို စစ်ထုတ်သည့် အမြန်စစ်ဆေးမှုများကို အသုံးပြုပါ။ အပြီးအပိုင်ပိတ်ထားသော ထပ်နေသောတည်ဆောက်မှုကို ဖယ်ရှားခဲ့သည်။ အစစ်အမှန် build/package/boot စစ်ဆေးမှုများသည် CI တွင်ရှိနေပါသည်။ ယူနစ်အစုံနှင့် vitest သည် CI (`Unit Tests (N/8)` နှင့် `Vitest`) တွင်သာလည်ပတ်သည်။

#### ပေါက်ဖော် စာမေးပွဲတွေ မေ့သွားပြီ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ၏ အကြံပေးအဆင့်အဖြစ် လုပ်ဆောင်ပြီး စမ်းသပ်သက်ရောက်မှုမြေပုံနောက်ကွယ်ရှိ တင်သွင်းမှုဖြေရှင်းချက်ကို ပြန်လည်အသုံးပြုသည်။ ပြောင်းလဲထားသော ထုတ်လုပ်မှု မော်ဂျူးတိုင်းအတွက်၊ လျှောက်ထားသူ၏ စမ်းသပ်မှုအား ဆွဲယူတောင်းဆိုမှု ကွာခြားမှုမှ ပျက်ပြယ်သောအခါတွင် ၎င်းသည် တိကျသော `changed module/symbol -> static consumer -> candidate sibling test` ကွင်းဆက်များကို အစီရင်ခံသည်။ Markdown အနှစ်ချုပ်နှင့် JSON ရလဒ်အား ပိတ်ဆို့ခြင်းမပြုလုပ်မီ ချိန်ညှိခြင်းအတွက် `forgotten-sibling-tests` အလုပ်အသွားအလာကို ထိန်းသိမ်းထားရှိပါသည်။

စည်ပိုင်းပြန်လည်တင်ပို့မှုနှင့် ရွေ့လျားတင်သွင်းမှုများသည် ကြည်လင်ပြတ်သားသော ရောဂါရှာဖွေခြင်းသာဖြစ်သည်။ ပိတ်ဆို့ရှာဖွေမှုကို ဘယ်တော့မှ မဖန်တီးကြဘူး။ သုံးသပ်ထားသောခြွင်းချက်များသည် `config/quality/forgotten-sibling-allowlist.json` တွင်နေထိုင်သည်။ ဝင်ရောက်မှုတစ်ခုစီသည် စားသုံးသူနှင့် ကိုယ်စားလှယ်လောင်း စမ်းသပ်မှုအား အမည်ပေးကာ၊ တိကျသော ကျိုးကြောင်းဆီလျော်မှုတစ်ခုပေးကာ GitHub ပြဿနာကို လင့်ခ်ချိတ်ရန် သို့မဟုတ် တောင်းဆိုချက်ကို ဆွဲထုတ်ရမည်ဖြစ်သည်။ ပုံစံမမှန်သော ထည့်သွင်းမှုများ မအောင်မြင်ပါ။ ခြွင်းချက်များသည် ဖျက်လိုက်သော ကိုယ်စားလှယ်လောင်း စမ်းသပ်မှု သို့မဟုတ် `.skip`/`.todo` ပေါင်းထည့်သည့် ကွဲပြားမှုကို ဖိနှိပ်၍ မရပါ။ အခိုင်အမာပြောဆိုမှု အားနည်းခြင်းနှင့် အခြားမျက်နှာဖုံးစွပ်ခြင်းကို သီးခြား `check:test-masking` ဂိတ်က ပိုင်ဆိုင်သည်။

#### စာရိုက်စစ်ဆေးသည့် ပရိုဂရမ်နှစ်ခုသည် ကွဲပြားစွာ အဖြေပေးသည်။

`typecheck:core` နှင့် `check:build-typecheck` မတူညီသောရွေးချယ်မှုများအောက်တွင် မတူညီသောပရိုဂရမ်များကို စုစည်းထားပြီး တူညီသောဖိုင်သည် တစ်ခုနှင့်တစ်ခုတွင် သန့်ရှင်းနိုင်ပြီး အခြားတစ်ခုတွင် အမှားအယွင်းများနှင့် ပြည့်နေပါသည်။

`tsconfig.build.json` `"strict": false` သတ်မှတ်ပေးသည်၊ ထို့ကြောင့် `noImplicitAny` ပိတ်ထားသည်။ core config သည် တင်းကျပ်သောရွေးချယ်မှုများဖြင့် စုစည်းထားသော 27-ဖိုင်ခွင့်ပြုစာရင်းကိုစုစည်းပြီး entry ၏တင်သွင်းမှုဂရပ်တစ်ခုစီကိုလိုက်နာသောကြောင့် build program တွင်ဘယ်တော့မှမပေါ်သောဖိုင်များကိုထိုနေရာတွင်စစ်ဆေးနေဆဲဖြစ်သည်။

ဖိုင်ကို ရိုက်ထည့်ခြင်း ရှိ၊ မရှိ ဆုံးဖြတ်သည့်အခါ အကျိုးဆက်သည် အရေးကြီးသည်-** `check:build-typecheck` အောက်တွင် သုညရောဂါရှာဖွေခြင်းသည် သုညဟု မဆိုလိုပါ။** . ဖိုင် ၂၆ ဖိုင်မှ `@ts-nocheck` ဖယ်ထုတ်ခြင်းတွင် ၎င်းတို့ထဲမှ ၂၃ ခုကို build ပရိုဂရမ်တွင် ရှင်းလင်းပြသခဲ့သည်။ အဲဒီအထဲက ဆယ့်ခြောက်ခုဟာ သွယ်ဝိုက်သောနည်းနဲ့ အမှားအယွင်းပေါင်း 120 လောက် ပေါ်ထွက်နေပါတယ်။ ဖိုင်ကို clean မခေါ်ခင် နှစ်ခုလုံးကို စစ်ကြည့်ပါ။

#### `check-ui-value-drift` — stale-ဘာသာပြန်ဂိတ်

အခြားဂိတ်များ၏ တည်ဆောက်ပုံအရ မမြင်နိုင်သော i18n ဆုတ်ယုတ်မှုကို ဖမ်းစားသည်- အင်္ဂလိပ်တန်ဖိုးကို ပြန်လည်ပြင်ဆင်ပြီး _previous_ အင်္ဂလိပ်မှ ဆင်းသက်လာသော ဘာသာပြန်များသည် နောက်တွင်ရှိနေသောကြောင့် အင်္ဂလိပ်မဟုတ်သော အသုံးပြုသူများသည် စိတ်ချလက်ချ-စကားလုံးဖြင့် ယခုမှားနေသော ကော်ပီကို ဆက်လက်ဖတ်ရှုနေပါသည်။

ဒါက တကယ်ကို ပို့ပေးတာပါ။ `oauthModal.googleOAuthWarning` အကောင့်ဝင်ကူညီသူ#5203Antigravity ;** ဒေသ ၄၃ ခုအနက် ၃၉ ခု** " URL အပြည့်အစုံကို ကော်ပီကူးပြီး အောက်တွင် ကူးထည့်ပါ" ဟု အော်ပရေတာများအား စာသားအား ထားရှိ၍ — ထိုဝန်ဆောင်မှုပေးသူအတွက် မပြီးမြောက်နိုင်သော စီးဆင်းမှုတစ်ခုဖြစ်သည်။ #8463 မတိုင်ခင်အထိ သတိမထားမိတဲ့အတွက်၊

- `sync-ui-keys` backfills သော့များသာဖြစ်သည်။** ပျက်ကွက်** ဘယ်တော့မှ မဖြစ်ဘူး။** သိုးသိုး** ;
- `check-ui-keys-coverage` သည် သော့ _presence_ ကို ရေတွက်သည်၊ ထို့ကြောင့် ဟောင်းနွမ်းသော ဘာသာပြန်ဆိုမှု ရမှတ်သည် အကျုံးဝင်သည် ။
- `check-translation-drift` သည် `docs/i18n/<locale>/**.md` documentation mirrors — ဘယ်တော့မှ `src/i18n/messages/*.json` မဖတ်တတ်ပါ။ 2026-09 ခုနှစ်မှ ပြန်လည်စင့်ခ်လုပ်ချိန်မှစ၍ အလုပ် `docs-sync-strict` တွင် ပိတ်ဆို့ခြင်း- core doc → `npm run i18n:run -- --files=<doc>` (ကဏ္ဍအဆင့်၊ စျေးပေါ) ကို တည်းဖြတ်ပါ။

**အခြေအမြစ် ကျောထောက်နောက်ခံပြုထားခြင်း မဟုတ်ဘဲ ကွဲပြားစွာ သိရှိမှု။** ၎င်းသည် အလုပ်လုပ်သောသစ်ပင်နှင့် ပေါင်းစည်းထားသော အခြေခံတွင် `en.json` နှိုင်းယှဉ်သည်။ အင်္ဂလိပ်တန်ဖိုး ပြောင်းလဲသွားသော သော့တိုင်းအတွက်၊ မထိမခိုက်ရသေးသော ဘာသာပြန်ခြင်းကို ကိုင်ဆောင်ထားဆဲ မည်သည့်နေရာမဆို ပျက်ယွင်းနေပါသည်။ ဒါက တမင်တကာ** နဂိုရှိရင်းစွဲကြွေးမြီများကို ရပ်တန့်စေသည်။** — a diff သည် မည်သည့်အင်္ဂလိပ်စကားဟောင်းမှ နှစ်ရှည်လများ ဘာသာပြန်ခြင်းမှ ထွက်လာသည်ကို မဖော်ပြနိုင်သောကြောင့် ဂိတ်သည် လက်ရှိပြောင်းလဲမှုနှင့် ထိတွေ့မှုကိုသာ ဆုံးဖြတ်သည်။ အခြားရွေးချယ်စရာ (သော့တစ်ခုစီ hash အခြေခံလိုင်း) သည် ~ 600 KB ထုတ်ပေးသော ဖိုင်တစ်ခု၊ 3 × အကြီးဆုံးသော အခြေခံလိုင်းဖြစ်ပြီး i18n PR တိုင်းတွင် လည်ပတ်နေမည်ဖြစ်သည်။

ကျေနပ်စေရန် နည်းလမ်းနှစ်ခု

1. ထိခိုက်ထားသော ဘာသာပြန်များကို အပ်ဒိတ်လုပ်ပါ။ သို့မဟုတ်
2. ၎င်းတို့ကို `__MISSING__:<new english>` — ဟု သတ်မှတ်ပြီး runtime တွင် ပြုပြင်ထားသော အင်္ဂလိပ် (`src/i18n/request.ts::deepMergeFallback`, #7258) နှင့် ဘာသာပြန်ရန်အတွက် သော့တန်းစီများကို ဆောင်ရွက်ပေးသည်။

ကြိုးတစ်ချောင်းရဲ့ ရင်ဘက်** အဓိပ္ပါယ်** ပြောင်းတယ်၊ ပိုကြိုက်တယ်။** သော့ကို အမည်ပြောင်းခြင်း။** - သော့အသစ်သည် ဟောင်းနွမ်းသောဘာသာပြန်ခြင်းကို အမွေဆက်ခံ၍မရပါ။ အဲဒါကတော့ #8463 သုံးတဲ့ ပုံစံပါ။

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

**New-code mode (Clean-as-You-Code) — 2026-08-30 မှစ၍ PR fast-path အတွက်သာ**

`pull_request` event များတွင် `quality.yml` က `--base-ref <PR base SHA>` ကို
`check:file-size`၊ `check:complexity-ratchets` နှင့် `check:dead-code` သို့ ပေးပို့သည်။
`check:complexity-ratchets` နှင့် `check:dead-code` အတွက် gate သည် HEAD ကို merge-base နှင့်
**PR က ပြင်ဆင်ထားသော ဖိုင်များကိုသာ ကန့်သတ်၍** နှိုင်းယှဉ်သည်
(`scripts/check/newCodeMode.mjs`: merge-base ကို ယာယီ `git worktree` တစ်ခုတွင် ဖန်တီးထားပြီး၊
ESLint/knip ကို ထိုနေရာနှင့် HEAD နှစ်ခုလုံးတွင် run ကာ ဖိုင်တစ်ခုချင်းစီ၏ အရေအတွက်များကို
diff လုပ်သည်)-

- **ပိတ်ပင်ခြင်း** — PR က ၎င်းပြင်ဆင်ထားသော ဖိုင်များတွင် cyclomatic/cognitive ချိုးဖောက်မှုများ
  သို့မဟုတ် dead export များ ထည့်သွင်းခဲ့သည်
  (log ထဲရှိ `complexityNewCode=`၊ `cognitiveComplexityNewCode=`၊ `deadExportsNewCode=`);
- **အကြံပြုချက်** — global စုစုပေါင်းကို ရပ်တန့်ထားသော baseline နှင့် နှိုင်းယှဉ်ခြင်းဖြစ်သည်။
  အမွေဆက်ခံထားသော drift ကြောင့် သက်ဆိုင်မှုမရှိသည့် PR တစ်ခုကို မည်သည့်အခါမျှ
  မအောင်မြင်စေပါ။ ထို drift ကို release reconciliation တွင် ပြန်လည်ရပ်တန့်သတ်မှတ်ပြီး
  headroom job ဖြင့် စောင့်ကြည့်သည်။

`check:file-size` သည် base ref ကို ၎င်း၏ကိုယ်ပိုင်စည်းမျဉ်းများအတိုင်း အသုံးပြုသည်
(`scripts/check/check-file-size.mjs`, #8522): tree ထဲရှိ source နှင့် test file တိုင်းကို
စစ်ဆေးပြီး PR base ရှိ ဖိုင်တစ်ခုချင်းစီ၏ စာကြောင်းအရေအတွက်ကို `git show` ဖြင့် ဖတ်ကာ၊
၎င်း၏ baseline ceiling (`frozen` / `testFrozen` သို့မဟုတ် baseline ပြင်ပရှိ ဖိုင်အတွက်
`cap` / `testCap`) နှင့် base size တို့အနက် ပိုကြီးသောတန်ဖိုးကို ကျော်လွန်သည်အထိ
ကြီးလာမှသာ ထိုဖိုင်ကို မအောင်မြင်စေသည်။ ထို့ကြောင့် base တွင် drift ဖြစ်ပြီးသား ဖိုင်တစ်ခုက
သက်ဆိုင်မှုမရှိသည့် PR တစ်ခုကို မည်သည့်အခါမျှ မအောင်မြင်စေပါ။

`check:boundary:ratchet` သည် ၎င်း၏ တစ်ခုတည်းသော ကိန်းဂဏန်းအပေါ် တူညီသည့် စည်းမျဉ်းကို အသုံးပြုသည်
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`)။ PR event များတွင်
`quality.yml` ၏ fast-gate များနှင့် `ci.yml` ၏ lint job နှစ်ခုစလုံးက PR base SHA ကို ပေးပို့ပြီး၊ base commit ကို
`git archive` export တစ်ခုမှ တိုင်းတာကာ PR ၏ `open-sse → src` edge အရေအတွက်သည်
`metrics.boundaryOpenSseToSrc` နှင့် base ရှိ အရေအတွက်တို့အနက် ပိုကြီးသည့်တန်ဖိုးကို ကျော်လွန်မှသာ
PR ကျရှုံးသည်။ သတ်မှတ်အမြင့်ဆုံးတန်ဖိုးထက် ကျော်လွန်နေသော base drift ကို (`base drift herdado`) အဖြစ် အစီရင်ခံသော်လည်း အပြစ်မရှိသော PR ကို မည်သည့်အခါမျှ အနီရောင်ဖြစ်စေမည်မဟုတ်ပါ။ push → main သည်
အကြွင်းမဲ့အမြင့်ဆုံးတန်ဖိုးကို ဆက်လက်ထိန်းသိမ်းပြီး၊ ဖြေရှင်း၍မရသော base SHA ဖြစ်ပါက သတိပေးချက်တစ်ခုနှင့်အတူ ထိုတန်ဖိုးကို ပြန်လည်အသုံးပြုသည်။

`workflow_dispatch` run များ၊ release-green sweep နှင့် nightly headroom job တို့တွင် PR base မရှိသဖြင့်
အကြွင်းမဲ့ (global) နှိုင်းယှဉ်မှုကို ဆက်လက်အသုံးပြုသည်။ Coverage၊ duplication နှင့် type-coverage တို့သည် လက်ရှိအချိန်တွင် global အဖြစ် ဆက်ရှိနေသည်
(၎င်းတို့၏ tool များက ဖိုင်တစ်ခုချင်းစီအလိုက် diff ကို ကုန်ကျစရိတ်နည်းနည်းဖြင့် မထုတ်ပေးနိုင်ပါ) — တူညီသည့် ကိုင်တွယ်မှုကို အသုံးပြုရန် အလားအလာရှိသည့် ကိုယ်စားလှယ်များဖြစ်သည်။

**v4.0 တွင် အဆင့်ကို ပိတ်သိမ်းခြင်း (LTS = ယခင်ထက် ပိုတင်းကျပ်ခြင်း၊ "ပုံမှန်အတိုင်း ပြန်သွားခြင်း" မဟုတ်ပါ)**

1. ရိုးရိုး `release/v4.0.0` tip တွင် မှတ်တမ်းအတွက် `npm run quality:headroom --json` ကို run ပြီးနောက်
   `npm run quality:ratchet -- --update`၊ `check:file-size --update`၊
   `check:complexity-ratchets --update`၊ `check:dead-code --update` နှင့် typecheck gate တစ်ခုချင်းစီ၏
   `--update` ကို run ပါ — baseline အားလုံးသည် တိုင်းတာရရှိသည့်တန်ဖိုးအထိ လျော့ကျသွားမည်။
2. `quality-baseline.json` မှ `_policy` ကို ဖျက်ပါ (`--require-tighten` နှင့် nightly
   banking ကို ပြန်လည်အသက်သွင်းသည်)၊ `check-openapi-coverage.mjs` ရှိ `THRESHOLD = 36` (သို့မဟုတ် ပိုမြင့်သောတန်ဖိုး) ကို ပြန်ထားပါ။
3. Modularization ကြောင့် အကျိုးရှိခဲ့သည့်နေရာများတွင် တိုင်းတာရရှိသည့်တန်ဖိုးထက် ပိုတင်းကျပ်စွာ သတ်မှတ်ပါ — file-size `cap` ကို 1000
   (သို့မဟုတ် 800) သို့ ပြန်ထားခြင်း၊ coverage floor များကို +5 တိုးခြင်း၊ modularize လုပ်ထားသည့် package များအတွက် dead export ကို 0 သတ်မှတ်ခြင်း။

## Ratchet အခြေခံမျဉ်း (`quality-baseline.json`)

Ratchet အင်ဂျင် (`scripts/quality/check-quality-ratchet.mjs`) သည် `quality-baseline.json`
ကို ဖတ်ပြီး အသစ်စုဆောင်းထားသော `quality-metrics.json` နှင့် နှိုင်းယှဉ်သည်။ သတ်မှတ်ထားသော
epsilon ထက်ကျော်လွန်၍ နောက်ပြန်ဆုတ်သွားသည့် မည်သည့်မက်ထရစ်မဆို build ကို ကျရှုံးစေသည်။

လက်ရှိ ခြေရာခံထားသော မက်ထရစ်များ-

| မက်ထရစ်               | ဦးတည်ချက် | အဓိပ္ပာယ်                          |
| --------------------- | --------- | ---------------------------------- |
| `eslintWarnings`      | `down`    | ESLint သတိပေးချက်အရေအတွက် မတိုးရပါ |
| `coverage.statements` | `up`      | Statement coverage မကျဆင်းရပါ      |
| `coverage.lines`      | `up`      | Line coverage မကျဆင်းရပါ           |
| `coverage.functions`  | `up`      | Function coverage မကျဆင်းရပါ       |
| `coverage.branches`   | `up`      | Branch coverage မကျဆင်းရပါ         |

အမှန်တကယ် တိုးတက်မှုတစ်ခု ဖြစ်ပေါ်ပြီးနောက် အခြေခံမျဉ်းကို အပ်ဒိတ်လုပ်ရန်-

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` flag သည် လက်ရှိတိုင်းတာထားသော တန်ဖိုးများကို `quality-baseline.json` ထဲသို့ ရေးသားသည်။
မက်ထရစ်ကို တိုးတက်စေခဲ့သော ပြောင်းလဲမှုနှင့်အတူ ဤဖိုင်ကို commit လုပ်ပါ။ မက်ထရစ်တစ်ခုကို
တိုးတက်စေသော်လည်း အခြေခံမျဉ်းကို အပ်ဒိတ်မလုပ်ထားသော PR ကို `--require-tighten` က
ဖမ်းမိမည်ဖြစ်သည် (အဆင့် 6A.5၊ အကောင်အထည်ဖော်ရန် ကျန်ရှိနေသေးသည်)။

### CodeQL ratchet: ပြန်လည်ဆန်းသစ်သည့် အကြိမ်နှုန်းနှင့် ကိုယ်တိုင်အစပျိုးခြင်း

`check:codeql-ratchet` သည် **အချိန်ဇယားအတိုင်း ပြန်လည်ဆန်းသစ်ထားသော repo အခြေအနေကို ဖတ်သည် — PR တစ်ခုချင်းအလိုက် မဟုတ်ပါ။**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` သည်
`state: configured`, `schedule: weekly` ဟု အစီရင်ခံသည်- ၎င်းသည် GitHub ၏ default-setup scan ဖြစ်ပြီး push တစ်ခုချင်းအလိုက်
လုပ်ဆောင်သော analysis မဟုတ်ပါ။ အကျိုးဆက်အနေဖြင့် alert များကို ပြင်ဆင်ထားသော PR တစ်ခု merge ဖြစ်ပြီးနောက်တွင်
ratchet သည် နောက်တစ်ကြိမ် အချိန်ဇယားအတိုင်း scan မလုပ်ဆောင်မချင်း အဟောင်းဖြစ်သည့် ပိုများသော အရေအတွက်ကို ဆက်လက်ဖတ်နေမည် —
ထို့ကြောင့် scan က အခြေအနေသစ်ကို ဖမ်းမိသည်အထိ ပြင်ဆင်သည့် PR ၏ နောက်ဆက်တွဲ PR များအပါအဝင် ဖွင့်ထားသော PR အားလုံးတွင်
နောက်ပြန်ဆုတ်မှုအဖြစ် အစီရင်ခံမည်ဖြစ်သည်။

**ကိုယ်တိုင် ပြန်လည်ဆန်းသစ်ခြင်း**: `gh workflow run codeql.yml --ref release/vX.Y.Z` သည်
analysis ကို ပြန်လည်လုပ်ဆောင်ပြီး မိနစ်ပိုင်းအတွင်း alert များကို ပြန်လည်ထုတ်ပြန်သည်။ `.github/workflows/codeql.yml`
ကို ဦးစွာဖတ်ပါ — GitHub ၏ "default setup" နှင့် ပဋိပက္ခဖြစ်သောကြောင့်
(`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`) ၎င်းသည် `workflow_dispatch` သီးသန့်သာဖြစ်ကြောင်း
၎င်း၏ header တွင် ရှင်းပြထားသည်။ `push`/`pull_request`/
`schedule` trigger များကို ပြန်လည်ထည့်သွင်းရန် ဦးစွာ **owner ၏ လုပ်ဆောင်မှု** လိုအပ်သည်- Settings → Code security →
CodeQL: Default → Advanced။ ထိုပြောင်းလဲမှုမပြုလုပ်ဘဲ `schedule:` trigger ကို မထည့်ပါနှင့် — ထိုသို့ပြုလုပ်ပါက
ကျရှုံးသော run များသာ ဖြစ်ပေါ်စေမည်။

**အရေအတွက် ကျဆင်းပြီးနောက် အခြေခံမျဉ်းကို တင်းကျပ်ပါ** — `node scripts/check/check-codeql-ratchet.mjs
--update` သည် အသစ်တိုင်းတာထားသော အရေအတွက်ကို `quality-baseline.json` →
`metrics.codeqlAlerts.value` ထဲသို့ ရေးသားသောကြောင့် ratchet က အဟောင်းဖြစ်သည့် အမြင့်ဆုံးကန့်သတ်ချက်အထိ
ပြန်လည်မြင့်တက်သွားခြင်းကို မသိမသာ ခွင့်ပြုမည်မဟုတ်ပါ။ လက်တွေ့ဥပမာ (2026-09-02/03)- PR #12502 က အမှန်တကယ် alert 7 ခုကို
ပြင်ဆင်ခဲ့သည် (တိုင်းတာထားသော ဖွင့်ထားသည့် alert 13 → 6); PR #12530 က ကိုက်ညီစေရန် ပုံသေထားသော အခြေခံမျဉ်းကို 11 → 6 သို့
တင်းကျပ်ခဲ့သည်; ထို့နောက် ကျန်ရှိသည့် 6 ခုကို alert တစ်ခုချင်းအလိုက် အကြောင်းပြချက်ပေး၍ ပယ်ဖျက်ခဲ့ပြီး ဖွင့်ထားသည့် alert အရေအတွက်ကို 0 အထိ လျှော့ချခဲ့သည်။

**ပယ်ဖျက်ခြင်းများသည် operator ၏ ဆုံးဖြတ်ချက်ဖြစ်သည် (တင်းကျပ်သော စည်းမျဉ်း #14)** — ပယ်ဖျက်မှုမှတ်ချက်တွင်
နည်းပညာဆိုင်ရာ အကြောင်းပြချက်ကို မှတ်တမ်းမတင်ဘဲ CodeQL alert တစ်ခုကို မည်သည့်အခါမျှ မပယ်ဖျက်ပါနှင့်- upstream-protocol
လိုအပ်ချက်အတွက် `won't fix`၊ test fixture အတွက် `used in tests`၊ CodeQL က မမြင်နိုင်သော sanitizer
အတွက် `false positive` (ရှေ့နမူနာ- `docs/security/ERROR_SANITIZATION.md`)။

## Release အဆင့် Ratchet Drift (WS5.5, v3.8.49)

PURE release tip ပေါ်တွင် ratchet တစ်ခု (ဖိုင်အရွယ်အစား၊ ရှုပ်ထွေးမှု၊ eslint သတိပေးချက်များ) regression ဖြစ်လာသောအခါ —
ဆိုလိုသည်မှာ merge များ၏ ပေါင်းစပ်မှုကြောင့် regression ဖြစ်ပြီး PR တစ်ခုတည်းက ၎င်း၏
ကိုယ်ပိုင် branch ပေါ်တွင် ထို regression ကို ပြန်လည်ဖြစ်ပေါ်စေနိုင်ခြင်းမရှိသောအခါ — ပြင်ဆင်မှုသည် **release captain က release
branch ပေါ်တွင် တစ်ကြိမ်သာ** လုပ်ဆောင်ရန် တာဝန်ရှိသည်- extraction/refactor ကို ဦးစားပေးပါ၊ မှတ်တမ်းတင်ထားသော
အကြောင်းပြချက် entry ရှိမှသာ baseline ကို ပြန်လည်သတ်မှတ်ပါ။ ပေါင်းစပ်မှုကြောင့်ဖြစ်သည့် drift ကို contributor PR ပေါ်သို့ မည်သည့်အခါမျှ
မတွန်းပို့ပါနှင့်၊ PR တစ်ခုချင်းစီအလိုက်လည်း baseline ကို မည်သည့်အခါမျှ ပြန်လည်မသတ်မှတ်ပါနှင့် (ထိုသို့လုပ်ခြင်းသည် အမှန်တကယ်ဖြစ်သော regression များကို ဖုံးကွယ်သည်)။ ဦးစွာ ခွဲခြားစစ်ဆေးပါ- သင်၏ PR ကြောင့် ဖြစ်သည်ဟု မယူဆမီ
probe worktree တစ်ခုထဲရှိ pure tip ကို အသုံးပြု၍ မအောင်မြင်မှုကို ပြန်လည်ဖြစ်ပေါ်စေပါ။

## Ratchet လျှော့ချမှုများကို စုဆောင်းသိမ်းဆည်းခြင်း — အောက်သို့ ဦးတည်ချက် (#8584)

ratchet သည် တစ်ဝက်သာ အလိုအလျောက်ဖြစ်ပြီး၊ အလိုအလျောက်ဖြစ်နေသည့်အပိုင်းကလည်း မှားယွင်းသည့်အပိုင်းဖြစ်သည်။ cap ကို **မြှင့်တင်ခြင်း** သည်
ဆယ်စက္ကန့်သာကြာသော manual JSON ပြင်ဆင်မှုဖြစ်ပြီး မအောင်မြင်နေသော PR ကို အမြန်ဆုံး ပြန်လည်လုပ်ဆောင်နိုင်စေသည့် နည်းလမ်းဖြစ်သည်။
cap တစ်ခုကို **လျှော့ချခြင်း** အတွက်မူ တစ်စုံတစ်ဦးက `--update` ကို run ပြီး ရလဒ်ကို commit လုပ်ရန်လိုသည် — ထို့အပြင်
`bank-ratchet-shrinks` job မပေါ်ပေါက်မီအထိ မည်သည့် workflow ကမျှ ထိုသို့ run မလုပ်ခဲ့ပါ။ တိုင်းတာတွေ့ရှိရသော အကျိုးဆက်
(2026-07-25)- frozen file 18 ခုသည် file အသစ်အတွက် သတ်မှတ်ထားသော လိုင်း 800 cap အောက် သို့မဟုတ် ၎င်းနှင့်ညီမျှသော အခြေအနေသို့ ရောက်ရှိပြီးဖြစ်သော်လည်း၊ အဆိုးဆုံးမှာ
132× (`src/shared/validation/schemas.ts` တွင် လိုင်း 19 သာရှိသော်လည်း cap 2,523 ထားရှိခြင်း) ဖြစ်သည်၊
complexity ceiling သည် rebaseline မှတ်စု ~37 ခုအတွင်း `1794 → 2169` သို့ တက်သွားပြီး လျှော့ချမှုမှာ တိတိကျကျ တစ်ကြိမ်သာ
(−1) ရှိခဲ့သည်၊ ထို့အပြင် "နောက် cycle တွင် `--update` ဖြင့် တင်းကျပ်မည်" ဟု 31 ကြိမ်ရေးသားခဲ့သော်လည်း တစ်ကြိမ်သာ
အကောင်အထည်ဖော်ခဲ့သည်။ ၎င်းကို ဖြစ်ပေါ်စေခဲ့သော code ထက် ပို၍ကြာရှည်တည်ရှိသည့် cap သည် ပြီးစီးသွားသော
decomposition တစ်ခုစီကို ထို file ကို နောက်တစ်ကြိမ် ပြင်ဆင်သူအတွက် တိုးချဲ့ခွင့်အဖြစ် တိတ်တဆိတ် ပြောင်းလဲပေးသည်။

`nightly-release-green.yml` → job **`bank-ratchet-shrinks`** သည် ထို loop ကို ပိတ်ပေးသည်-

|                |                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Run သည့်အချိန် | `schedule` (တစ်ရက်လျှင် 3×) + `workflow_dispatch` — ရည်ရွယ်ချက်ရှိရှိ **`push` မဟုတ်ပါ**                                  |
| တိုင်းတာမှု    | အမြင့်ဆုံး `release/vX.Y.Z`၊ `release-green` နှင့် တူညီသော resolution + injection guard                                   |
| ရေးသားမှု      | `check:file-size --update` နှင့် `check:complexity-ratchets --update` (နှစ်ခုစလုံးသည် ဖွဲ့စည်းပုံအရ လျှော့ချရန်သာဖြစ်သည်) |
| အတည်ပြုမှု     | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                  |
| ပေးပို့မှု     | release branch ကို ရည်ညွှန်းသည့် အမြဲတမ်း လက်ရှိအခြေအနေဖြစ်သော PR တစ်ခု — force-update လုပ်ပြီး၊ ထပ်ခါတလဲလဲ မဖန်တီးပါ     |

Banking ကို push တစ်ခုချင်းစီအလိုက် မလုပ်ဘဲ batch အလိုက် လုပ်ဆောင်ခြင်းမှာ latency လိုအပ်ချက်မရှိသောကြောင့်ဖြစ်သည် (လျှော့ချမှုကို
8h အတွင်း bank လုပ်နိုင်လျှင် လုံလောက်သည်)။ merge campaign များအတွင်း merge တစ်ခုချင်းစီအလိုက် run လျှင် PR branch ကို အကြိမ်ကြိမ်
ပြန်လည်တည်ဆောက်ရပြီး အကြိမ်တိုင်း ESLint အပြည့်အစုံ scan လုပ်ရသည့် ကုန်ကျစရိတ်ရှိမည်။ Detection ကို
push (`release-green`) ပေါ်တွင် ဆက်ထားပြီး banking ကိုသာ batch လုပ်သည်။

### ဘေးကင်းရေး အတည်ပြုကိရိယာ

job သည် လူကိုယ်တိုင် ကြီးကြပ်ခြင်းမရှိဘဲ baseline များသို့ ရေးသားသောကြောင့် `verify-ratchet-bank.mjs` ကသာ
ထိုလုပ်ဆောင်ချက်ကို လက်ခံနိုင်စေသည်။ ၎င်းသည် `--update` ပြီးနောက် tree ကို `HEAD` နှင့် diff လုပ်ပြီး၊ ပြောင်းလဲမှုတိုင်းသည်
အောက်ပါအမျိုးအစားများထဲမှ တစ်ခုမဟုတ်ပါက **မည်သည့် commit မျှ မရှိမီ job ကို ရပ်တန့်ကာ**
PR လုံးဝ မဖွင့်ပါ-

- `frozen` / `testFrozen` numeric entry တစ်ခုကို **လျှော့ချခြင်း** သို့မဟုတ် **ဖယ်ရှားခြင်း**
- `complexity-baseline.json` → `count` ကို **လျှော့ချခြင်း**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ကို **လျှော့ချခြင်း**

အခြားမည်သည့်အရာမဆို မအောင်မြင်ပါ- ကိန်းဂဏန်းတစ်ခုကို မြှင့်တင်ခြင်း၊ entry တစ်ခုထည့်ခြင်း၊ `cap`/`testCap` ကို ပြောင်းလဲခြင်း သို့မဟုတ်
`_rebaseline_*` မှတ်စုတစ်ခုကို ဖျက်ခြင်း/ပြန်လည်ရေးသားခြင်း (ထိုမှတ်စုများသည် ceiling တစ်ခုစီ ရှိနေရသည့်အကြောင်းရင်းအတွက် audit trail ဖြစ်ပြီး
file entry များနှင့်အတူ တူညီသော `frozen` object ထဲတွင် သိမ်းဆည်းထားသည်)။ cap ကို မြှင့်တင်နိုင်သော bot သည် လက်ရှိအခြေအနေထက်
ပိုဆိုးမည်မှာ သေချာသည်။ Regression guard- `tests/unit/verify-ratchet-bank.test.ts`။

job သည် `release/*` သို့ မည်သည့်အခါမျှ push မလုပ်ပါ — လူတစ်ဦးက PR ကို merge လုပ်ရသောကြောင့် မှားယွင်းသည့် တိုင်းတာမှုတစ်ခုသည်
ပြန်လည်သုံးသပ်ခြင်းမရှိဘဲ အတည်မဖြစ်နိုင်ပါ။

## ခွင့်ပြုစာရင်းမူဝါဒ

နဂိုရှိပြီးသား ချိုးဖောက်မှုများတွင် မအောင်မြင်နိုင်သော ဂိတ်တိုင်းသည် အေးခဲထားသော ခွင့်ပြုစာရင်း (ဥပမာ၊ `KNOWN_STALE_DOC_REFS`၊ `KNOWN_MISSING`၊ `KNOWN_RAW_SQL`) ကို အသုံးပြုသည်။ မူဝါဒမှာ-

**မူလအကြောင်းအရင်းကို ဖြေရှင်းပါ။ ချိုးဖောက်မှုသည် နဂိုရှိပြီးသားဖြစ်ပြီး တူညီသော PR တွင် မပြင်နိုင်သည့်အခါမှသာ ခွင့်ပြုစာရင်းကို အသုံးပြုပါ။**

ခွင့်ပြုစာရင်းသို့ ထည့်သွင်းသည့်အခါ-

1. တရားမျှတမှုနှင့်အတူ မှတ်ချက်တစ်ခု ထည့်သွင်းပါ။
2. ခြေရာခံခြင်းပြဿနာ (ဥပမာ `// #3498 — Phase 2 feature, not yet implemented`) ကိုကိုးကားပါ။
3. ချိုးဖောက်မှု — ကိုပြင်ပေးသည့် တူညီသော PR တွင် ဝင်ရောက်မှုကို ဖယ်ရှားလိုက်ပါက အသက်ဝင်သောချိုးဖောက်မှုတစ်ခုကို ဖိနှိပ်ထားတော့မည့် ဟောင်းနွမ်းသောဝင်ရောက်မှုမှာ ၎င်းကိုယ်တိုင် ချို့ယွင်းချက်တစ်ခုဖြစ်သည် (6A.3 ဖောက်ဖျက်ခြင်းအား အကောင်အထည်ဖော်ပြီးသည်နှင့် မိဘမဲ့စာရင်းသွင်းမှုတွင် ဂိတ်ပေါက်ကျမည်မဟုတ်ပါ)။

လုပ်ပါ။** မဟုတ်ဘူး** စာမေးပွဲများ ပိုမိုမြန်ဆန်စေရန်အတွက် ခွင့်ပြုစာရင်းများကို ထည့်သွင်းပါ။ တိုးလာနေသော ခွင့်ပြုစာရင်းပါသော အစိမ်းရောင်တံခါးသည် အရည်အသွေး၏ လွဲမှားသောသဘောဖြစ်သည်။

### သင့် PR တွင် ဂိတ်တစ်ခုပျက်သောအခါ

1. **ဂိတ်ထွက်ပေါက်ကို သေချာဖတ်ပါ။** — သည် မည်သည့်ဖိုင် သို့မဟုတ် သင်္ကေတသည် စည်းကမ်းကို ချိုးဖောက်ကြောင်း အတိအကျပြောပြသည်။
2. **ချိုးဖောက်မှုကို ပြင်ပါ။** — ဂိတ်အများစုသည် ကုဒ်မှန်သည်နှင့် အဆုံးအဖြတ်ပေးသော ဖိုင်စနစ်စစ်ဆေးမှုများဖြစ်သည်။
3. **အကယ်၍ ချိုးဖောက်မှုမှာ နဂိုရှိပြီးသား** (ဆိုလိုသည်မှာ သင်သည် ၎င်းကို မမိတ်ဆက်ခဲ့ဘဲ ယခု တံခါးသည် ၎င်းကို ဖုံးလွှမ်းထားသည်)။ မျှတသောမှတ်ချက်နှင့် ခြေရာခံခြင်းပြဿနာတစ်ခုပါရှိသော ခွင့်ပြုစာရင်းတစ်ခု ထည့်သွင်းပါ။
4. **အကယ်၍ တံခါးသည် ကတုတ်၊** (လွှမ်းခြုံမှု၊ ESLint သတိပေးချက်များ၊ ပွားမှု၊ ရှုပ်ထွေးမှု- သင်၏ပြောင်းလဲမှုသည် မက်ထရစ်ကို ပိုဆိုးစေသည်။ အရင်းခံပြဿနာကို ဖြေရှင်းပါ၊ သို့မဟုတ် အပြောင်းအလဲသည် ရည်ရွယ်ချက်ရှိရှိဖြစ်ပြီး မက်ထရစ်ကျဆင်းခြင်းသည် — လက်ခံနိုင်သော်လည်း PR ဖော်ပြချက်တွင် အကြောင်းရင်းကို မှတ်တမ်းတင်ထားပါက `npm run quality:ratchet -- --update` (ရှားရှားပါးပါး) လုပ်ဆောင်ပါ။
5. **အကြံပေးဂိတ်များ** (`continue-on-error: true`) သည် အချက်အလက်ဆိုင်ရာ — ဖြစ်ပြီး ၎င်းတို့သည် ပေါင်းစည်းခြင်းကို မပိတ်ပင်ထားသော်လည်း CI အကျဉ်းချုပ်တွင် ပေါ်လာသည်။ သူတို့ကို ပြင်ပါ။

   Ratchet ပုံစံ gate များသည် `collect-metrics.mjs` မှတစ်ဆင့် တိုင်းတာချက်တစ်ခုကို `quality-metrics.json` သို့ ထုတ်ပေးသည်။
2. `"check:<name>": "node scripts/check/check-<name>.mjs"` ကို `package.json` တွင် ထည့်ပါ။
3. `.github/workflows/ci.yml` အတွင်း သင့်လျော်သော job အောက်တွင် ၎င်းကို ချိတ်ဆက်ပါ
   (မူဝါဒ → `lint` သို့မဟုတ် `docs-sync-strict`; ratchet → `quality-gate`)။
4. ၎င်းတွင် ခွင့်ပြုစာရင်းတစ်ခု ပါဝင်ပါက ခေတ်မမီတော့သော entry များကို အလိုအလျောက် ရှာဖွေနိုင်စေရန်
   `scripts/check/lib/allowlist.mjs` မှ `reportStaleEntries()` ကို အသုံးပြုပါ။
5. gate ၏ ရှာဖွေစစ်ဆေးမှု logic ကို လွှမ်းခြုံသည့် စမ်းသပ်မှုတစ်ခုကို `tests/unit/build/` တွင် ရေးပါ။
6. ဤစာတမ်းကို အပ်ဒိတ်လုပ်ပါ (သက်ဆိုင်ရာ job ဇယားတွင် row တစ်ခု ထည့်ပါ)။

## Agent ကိရိယာများ- LSP-in-the-loop (ရွေးချယ်အသုံးပြုနိုင်)

CI gate များအပြင် OmniRoute တွင် **ရွေးချယ်အသုံးပြုနိုင်သော** `agent-lsp` scaffold
(project အဆင့် `.mcp.json`၊ Fase 7 Task 15) ပါရှိသည်။ coding agent များအတွက် TypeScript language server ကို ဖော်ထုတ်ပေးရန် `.mcp.json`
ကို ဖန်တီးပါ။ ထိုသို့ဖြင့် ၎င်းတို့သည် code မရေးမီ symbol များ /
diagnostic များကို ဖြေရှင်းနိုင်မည်ဖြစ်သည် — ၎င်းသည် မရှိသည့် symbol များကို ဖန်တီးမိခြင်းကြောင့် ဖြစ်သော error များကို အရင်းအမြစ်မှ လျှော့ချပေးသည့်
`typecheck:core` ၏ compile-before-claim တွဲဖက်တစ်ခုဖြစ်သည်။ ၎င်းကို ရည်ရွယ်ချက်ရှိရှိ
အလိုအလျောက် မတင်ထားပါ (MCP↔LSP bridge ကို သင်ကိုယ်တိုင် ရွေးချယ်ပြီး အတည်ပြုရမည်)။ ပျက်နေသော entry တစ်ခုသည်
ချိတ်ဆက်မှု error ကိုသာ log လုပ်ပြီး session များကို မည်သည့်အခါမျှ မပျက်စေပါ။

## Rationalization Backlog (ROI ပြန်လည်သုံးသပ်ချက် — Fase 9 Onda 3)

ဤစာရင်းကို 2026-06-17 တွင် `ci.yml` နှင့် ပြန်လည်ညှိနှိုင်းခဲ့သည် (ယခင်ဗားရှင်းသည် `audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`, `check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`, `check:codeql-ratchet`, `check:pr-evidence`)။ ပြန်လည်သင့်မြတ်ရေး အစုံ၏ ROI ပြန်လည်သုံးသပ်မှုတွင် အောက်ပါ ကျိုးကြောင်းဆီလျော်မှုဆိုင်ရာ ကိုယ်စားလှယ်လောင်းများကို ဖော်ထုတ်ခဲ့သည်။** ပေါင်းစည်းမှုသည် စက်ပိုင်းဆိုင်ရာ CI အပြောင်းအလဲများဖြစ်သည်။ flips/drops သည် အော်ပရေတာအတွက် သီးသန့် မူဝါဒဆိုင်ရာ ဆုံးဖြတ်ချက်များဖြစ်သည်။** အောက်တွင် မည်သည့်အရာမှ မသက်ရောက်သေးပါ။

**အထောက်အထားမဲ့လည်း အထက်မှာ** (အကြံပေး၊ အချက်ပြနည်း)- `docs-lint` အလုပ် (markdownlint + Vale၊ အလုပ်တစ်ခုလုံး `continue-on-error`) နှင့် သီးသန့်စကင်နာ၏ အလုပ်အသွားအလာများသည် `semgrep.yml` / `codeql.yml` / `scorecard.yml` ဖြစ်သည် ။ `semgrepFindings: 0` သည် `quality-baseline.json` တွင်ရှိသော်လည်း `ci.yml` — ရှိ မက်ထရစ်သည် လက်ရှိတွင် မိဘမဲ့ဖြစ်နေသော ပိတ်ဆို့ထားသော ratchet သို့ ကြိုးမတပ်ပါ။

### ပေါင်းစည်းခြင်း / dedup (စက်ပိုင်းဆိုင်ရာ၊ အန္တရာယ်နည်းပါးသည်)

- `check:secrets` (gitleaks၊ မှတ်တမ်းတင်ထားသော မှားယွင်းသောအပြုသဘောဆောင်သည့် 3 ခုတွင် အေးခဲနေသော ratchet ကိုပိတ်ဆို့ခြင်း) — 3 ကို 0 သို့ရောက်ရှိရန် ခွင့်ပြုစာရင်း သို့မဟုတ် အကြံပေးမှုအဖြစ် အဆင့်သတ်မှတ်ထားသည်။ GitHub ဇာတိလျှို့ဝှက်စကင်န်ဖတ်ခြင်း + `check:public-creds` ကို ထပ်နေသည်။
- `check:pr-evidence` (ပိတ်ဆို့ခြင်း၊ greps PR-ကိုယ်ထည် စကားပြေ) — မြင့်မားသော မှားယွင်းသောအပြုသဘောအန္တရာယ်၊ ပြုတ်ကျပါက Hard Rule #18 ကျင့်သုံးမှုကို အားနည်းစေသောကြောင့် ၎င်းသည် စစ်မှန်သော မူဝါဒခေါ်ဆိုမှုဖြစ်သည်။
- `semgrep` (အကြံပေးသီးသန့်) — သည် OWASP မိသားစုများအတွက် CodeQL ထပ်နေပါသည်။ ၎င်း၏အခြေခံလိုင်းကို ratchet သို့မဟုတ် drop သို့ပြောင်းပါ။

#### `check-key-completeness` — key-set parity ဂိတ်

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`၊ အလုပ် `i18n-ui-coverage`)။ `src/i18n/messages/<locale>.json` တစ်ခုစီ၏ အရွက်သော့အစုံကို `en.json` နှင့် နှိုင်းယှဉ်ပြီး သော့ထည့်လိုက်သောအခါတွင် ပျက်ကွက်ခြင်း သို့မဟုတ် အပိုရွက်များတွင် ပျက်ကွက်သည်။ `__MISSING__:` နေရာကိုင်ဆောင်သူများသည် လက်ရှိအဖြစ်ရေတွက်သည် (၎င်းတို့၏အကြောင်းအရာသည် အချိုးဂိတ်၏လုပ်ငန်းဖြစ်သည်)။ ၎င်းသည် diff-based/percentage ဂိတ်နှစ်ခု၏ အကြွင်းမဲ့ ဖြည့်စွက်ချက်ဖြစ်သည်- `check-ui-keys-coverage` နေရာတစ်ခုလျှင် 80% ကြမ်းပြင်ကို တွန်းအားပေးသည် ( ~ 13,000 တွင် ပျက်နေသောသော့ 43 ခုမှ 99.7 %) ကိုဖတ်ပြီး `check-new-key-coverage` PR မှထည့်သောသော့များကိုသာ `en.json` တွင်စီရင်သည်။ အကိုင်းအခက်ဖြတ်သည့်နေ့၏ `en.json` မှ ဒေသဆိုင်ရာအသုတ်ကို အရင်းမှ သော့များထပ်ထည့်နေချိန်တွင် ရက်ပေါင်းများစွာ ဘာသာပြန်ဆိုသည်။ batch PR သော့ကိုယ်နှိုက်မထည့်သောကြောင့် batch 1 (#13044) တွင် သော့ 43 ခု တိုတောင်းသော ကိုးခုနှင့် batch 2 (#13660) 10 keys ရှစ်ခု (2026-09-15) တွင် အတိုချုံး၍ ထွက်လာသောအခါ မောင်နှမနှစ်ယောက်လုံး နှုတ်ဆိတ်နေကြပါသည်။ `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` ဖြင့် အနီရောင်ကို ပြင်ပါ။ `extra` အရွက်ဆိုသည်မှာ အရင်းအမြစ်မှ ပြုတ်ကျပြီး — ၎င်းကို locale မှ ဖျက်ခြင်းဖြစ်သည်။ `--warn` သည် မအောင်မြင်ဘဲ အစီရင်ခံသည်။ `--catalog=cli` သည် `bin/cli/locales` (`npm run i18n:check-keys:cli`); အဆင့်နှစ်ဆင့်စလုံးသည် အလုပ် `i18n-ui-coverage` တွင် နေထိုင်ကြသည်။

#### `check-new-key-coverage` — new-key i18n ဂိတ်

`check-ui-value-drift`၏မွေးချင်း။ အဲဒါက အင်္ဂလိပ်တန်ဖိုးကို ဖမ်းတယ်။** ပြန်ရေးသည်။** ဘာသာပြန်ဆိုမှုများ နောက်ကျကျန်နေခဲ့သည်။ ဒီတစ်ခုက အင်္ဂလိပ်ကီးကို ဖမ်းတယ်။** ထပ်ပြောသည်။** အချို့ဒေသခံများက လက်မခံကြပေ။

`check-ui-keys-coverage` ဤအတန်းအစားကို မမြင်နိုင်ပေ- ၎င်းသည် နေရာဒေသတစ်ခုစီအတွက် ကြမ်းပြင်ကို တွန်းအားပေးပြီး ~ 13,000 မှ ပျက်ကွက်သော့ 11 ခုကို 99.9% ဖြင့် ဖုံးအုပ်ထားသည်။ ဘာသာစကားတစ်ခုလျှင် ရာခိုင်နှုန်းတစ်ခုသည် "ဤအင်္ဂါရပ်ကို ဘာသာပြန်မထားဘဲ ပို့ဆောင်လိုက်သည်" — အင်္ဂါရပ်တစ်ခုလုံးသည် စာသားမပါဘဲ နေရာအသစ်တစ်ခုသို့ ဆင်းသက်နိုင်ပြီး နံပါတ်ကို ဘယ်သောအခါမှ မရွှေ့နိုင်ပါ။

အဖြစ်အပျက်ကို ကုဒ်ဖော်ပြသည်- Orchestration Canvas ၏ အဆင့် 3 သည် ထိုအချိန်က ရှိခဲ့သော ဒေသ 42 ခုတွင် ၎င်း၏ သော့ဆယ့်တစ်ခုကို ဘာသာပြန်ဆိုပါသည်။ နာရီအကြာတွင် EU ဘာသာစကားအသုတ် (#13044) သည် ဒေသန္တရ ၅၁ ခုသို့ repo ကိုယူခဲ့ပြီး အသစ်ရောက်ရှိလာသူ ကိုးဦး (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) ၎င်းတို့ကို လုံးဝလက်မခံပါ။ `deepMergeFallback` ပျက်ကွက်သော့ကို အင်္ဂလိပ်လို အစားထိုးသည်၊ ထို့ကြောင့် ကျရှုံးမှုမုဒ် UI အလွတ် UI — အစစ်မဟုတ်ဘဲ၊ တည်ဆောက်မှုဖြင့် အသံတိတ်သွားပါသည်။

မောင်နှမလိုပါပဲ။** diff-aware** အလုပ်လုပ်သောသစ်ပင်နှင့် ပေါင်းစည်းထားသည့် အခြေခံမှ အင်္ဂလိပ်ကို နှိုင်းယှဉ်ထားသောကြောင့် ယခင်ရှိပြီးသား ကွာဟချက်များ အေးခဲနေပြီး တံခါးကို ဖွင့်ရန် ရွှေ့ပြောင်းရန် မလိုအပ်ပါ။

**`__MISSING__:<english>` အမှတ်အသားသည် ၎င်းကို မကျေနပ်ပါ (2026-09-17) ကတည်းက။** 2026-09-16 တွင် — အင်္ဂါရပ်ရှစ်ခု PRs — အင်္ဂါရပ်ရှစ်ခုထည့်သွင်းပြီး 61 တွင် ဘာသာပြန်ခြင်းအစား locales 65 လုံးသို့ အမှတ်အသားပြုလုပ်ထားသည်- ဤတံခါးသည် တစ်ခုစီတိုင်းကို လက်ခံခဲ့ပြီး PRs ကို မည်သည့်အရာကမှ ပိတ်ပင်ထားခြင်းမရှိပဲ၊ နှင့် မှန်ကန်သောဘာသာပြန်ဆိုမှုအချိုးအစား BR မှ 2% တိုင်းကို ပိတ်ဆို့ခြင်း မအောင်မြင်ပါ။ > 2.5 % + 0.5)။ အမှတ်အသားတစ်ခုအား ပျက်ကွက်ဘာသာပြန်အဖြစ် သတ်မှတ်သည်။ `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` ဖြင့် အနီရောင်ကို ပြင်ပါ၊ သို့မဟုတ် `npm run i18n:translate-new-keys` နှင့်အပြိုင် (`scripts/i18n/translate-new-keys.sh`၊ သီးသန့်-ဘေးကင်းသော၊ `OMNIROUTE_TRANSLATION_*` env မပါဘဲ စတင်ရန်ငြင်းဆန်သည်)။ အင်္ဂလိပ် (ပင်ထိုးထားသည့် product/engine/flag အမည်) သည် `scripts/i18n/untranslatable-keys.json` တွင်ရှိနေရမည်၊ အမှတ်အသားတစ်ခု၏နောက်တွင် ဘယ်တော့မှ မပါဝင်ပါ။ `vi` အမှတ်အသားများကို အပြတ်အသတ် တားမြစ်သည် (`tests/unit/i18n-vi-completeness.test.ts`)။

#### `check-vitest-exclusions` — ရပ်ထား-စမ်းသပ်ဂိတ်

`vitest.config.ts`'s `exclude` စာရင်းရှိ ဖိုင်သည် မပြေးနိုင်သော စမ်းသပ်ချက်ဖြစ်ပြီး သစ်ပင်ကိုဖတ်သူတိုင်းအား လွှမ်းခြုံထားပုံရသည်။ မှတ်ချက် `// #8618 — pre-existing failure; remove this exclusion when fixed`၏ နောက်ကွယ်တွင် စုစည်းထားသော ဖိုင်ခြောက်ဆယ့်နှစ်ဖိုင်။ ၎င်းကို ခြေရာခံလိုက်သည့်စာရင်းသည် 45 entry မှ 62 သို့ တိုးလာစဉ် စာစောင် #8618 2026-08-11 တွင် ပိတ်ခဲ့ပြီး၊ အသစ်တစ်ခုစီသည် သေနေသောပြဿနာကို ညွှန်ပြသော မှတ်ချက်တစ်ခုကို အမွေဆက်ခံထားသည်။ စာရင်းကို ဖိုင် (#13204) ဖြင့် တိုင်းတာသောအခါ၊** ၆၂ ခုအနက် ၅၁ ခုသည် အရင်းအမြစ်ပြောင်းလဲမှုမရှိဘဲ လက်ရှိသစ်ပင်ကို ကျော်သွားခဲ့သည်။** .

ဂိတ်သည် (က) ခြေရာခံခြင်းပြဿနာကို အမည်ပေးခြင်းနှင့် (ခ) ၎င်း၏တိုင်းတာမှုအခြေအနေဖြင့် `config/quality/vitest-exclusions.json` တွင် အစစ်အမှန်ဖိုင်တစ်ခုသို့ ဖြေရှင်းပေးသည့် ဖယ်ထုတ်မှုတိုင်း လိုအပ်သည်၊ ထို့ကြောင့် တစ်ခုထည့်သွင်းခြင်းသည် 60-entry array တွင်တစ်ခုထက်ပိုသောစာကြောင်းမဟုတ်ဘဲ သီးခြားဖိုင်တစ်ခုတွင် ပြန်လည်သုံးသပ်နိုင်သော ကွာခြားချက်ဖြစ်သည်။ ၎င်းသည် ~ 10 မိနစ်ကုန်ကျပြီး အချိန်အပိုင်းအခြားအလိုက် အလုပ်တစ်ခုတွင်ပါဝင်သည့် ဖယ်ထုတ်ထားသော — စာမေးပွဲများကို တမင်ပြန်မလုပ်ဆောင်ပါ။ တစ်ခုချင်းစီကို နောက်ဆုံးတိုင်းတာသည့်အခါ စာရင်းမှတ်တမ်းများ။
