> Compression စသည်တို့) ကို အသေးစိတ်လေ့လာရန် ဤ `docs/` directory ရှိ ၎င်းတို့အတွက် သီးသန့်ဖိုင်များကို ကြည့်ပါ။

ဤဖိုင်သည် **ယနေ့ repository ထဲတွင် အမှန်တကယ်ရှိနေသောအရာများ** ကို ဖော်ပြထားပြီး၊ အင်ဂျင်နီယာအသစ်တစ်ဦးအနေဖြင့်
tree အတွင်း လမ်းညွှန်ရှာဖွေနိုင်ရန်၊ runtime layering ကို နားလည်နိုင်ရန်နှင့် module အသစ်များ
မဖန်တီးဘဲ code ကို မည်သည့်နေရာတွင် ထည့်သွင်းရမည်ကို သိရှိနိုင်ရန် ရည်ရွယ်သည်။

### 3.1 `src/app/` — အက်ပ် Router

App Router သည် ဒက်ရှ်ဘုတ် UI နှင့် public/management HTTP API နှစ်ခုလုံးကို ဖော်ထုတ်ပေးသည်။ ရှိသည်** global middleware မရှိပါ။** — ကြားဖြတ်ပေးခြင်းကို လမ်းကြောင်းတစ်ခုချင်း လုပ်ဆောင်သည်။

`src/app/` အောက်ရှိ ထိပ်တန်းအဆင့် အပိုင်းများ

| မဂ်                                                                           | ရည်ရွယ်ချက်                                                    |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `api/`                                                                        | HTTP API လမ်းကြောင်းများအားလုံး (အသေးစိတ်အား အောက်တွင်ကြည့်ပါ) |

#### 3.1.2a `src/app/api/services/` — Embedded Services စီမံခန့်ခွဲမှု

ထည့်သွင်းခြင်း၊ စတင်ခြင်း၊ ရပ်တန့်ခြင်းနှင့် 9Router နှင့် CLIProxyAPI စောင့်ကြည့်ခြင်းအတွက် လမ်းကြောင်းများ။ လမ်းကြောင်းအားလုံးကို ခွဲခြားထားသည်။**LOCAL_ONLY** (loopback သာလျှင်၊ hard rule #17) ၎င်းတို့သည် `npm install` နှင့် spawn child လုပ်ငန်းစဉ်များကို ခေါ်ဆိုနိုင်သောကြောင့် ဖြစ်သည်။

```

├── 9router/
│   ├── _lib.ts             getOrInitSupervisor() helper
│   ├── install/route.ts    POST — npm install via execFile
│   ├── start/route.ts      POST — supervisor.start()
│   ├── stop/route.ts       POST — supervisor.stop()
│   ├── restart/route.ts    POST — supervisor.restart()
│   ├── update/route.ts     POST — npm install newer version

│   ├── status/route.ts     GET  — live + DB status + version metadata
│   └── auto-start/route.ts POST — toggle auto_start flag
├── cliproxy/
│   ├── _lib.ts             getOrInitSupervisor() helper
│   ├── install/route.ts    POST — npm install
│   ├── start/route.ts      POST — supervisor.start()

│   ├── update/route.ts     POST — npm install newer version
```

သက်ဆိုင်သည့် ဒက်ရှ်ဘုတ် UI: `src/app/(dashboard)/dashboard/providers/services/` — နှစ်-တဘ် စာမျက်နှာ (CLIProxyAPI + 9Router)။ 9Router တွင် ထည့်သွင်းထားသော UI: `src/app/(dashboard)/dashboard/providers/services/[name]/embed/[[...path]]/route.ts` အတွက် ပြောင်းပြန်ပရောက်စီ

## 10. ပါဝင်ကူညီနည်း

### Provider အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `src/shared/constants/providers.ts` တွင် မှတ်ပုံတင်ပါ (load လုပ်ချိန်တွင် Zod ဖြင့် အတည်ပြုစစ်ဆေးသည်)။
2. စိတ်ကြိုက် logic လိုအပ်ပါက `open-sse/executors/` တွင် executor တစ်ခု ထည့်ပါ
   (`BaseExecutor` ကို တိုးချဲ့ပါ)။
3. OpenAI format ကို အသုံးမပြုပါက `open-sse/translator/` တွင် translator တစ်ခု ထည့်ပါ။
4. OAuth အခြေခံဖြစ်ပါက `src/lib/oauth/providers/` နှင့်
   `src/lib/oauth/services/` အောက်တွင် config ထည့်ပါ။
5. Model များကို `open-sse/config/providerRegistry.ts` (သို့မဟုတ် `open-sse/config/`
   အောက်ရှိ format အလိုက် registry) တွင် မှတ်ပုံတင်ပါ။
6. `tests/unit/` အောက်တွင် test များ ရေးပါ။

### API route အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `src/app/api/your-route/route.ts` ကို ဖန်တီးပါ။
2. CORS → Zod body validation → auth → handler delegation ပုံစံကို လိုက်နာပါ။

4. Management အတွက်သာဖြစ်ပါက path ကို `src/shared/constants/publicApiRoutes.ts`
   (အများသုံး API မျက်နှာပြင်အတွက် denylist) တွင် ထည့်ပါ။
5. `tests/unit/` အောက်တွင် test များ ထည့်ပါ။
6. `docs/reference/API_REFERENCE.md` နှင့် `docs/openapi.yaml` ကို အပ်ဒိတ်လုပ်ပါ။

### DB module အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `src/lib/db/yourModule.ts` ကို ဖန်တီးပြီး `./core.ts` မှ `getDbInstance()` ကို import လုပ်ပါ။

## 11. သတ်မှတ်စည်းမျဉ်းများ

- **Code style**: 2-space indent၊ double quotes၊ စာလုံး 100 အကျယ်၊ semicolon များနှင့်
  `es5` trailing comma များ — `lint-staged` မှတစ်ဆင့် Prettier ဖြင့် မဖြစ်မနေ လိုက်နာစေသည်။
- **Import များ**: external → internal (`@/`, `@omniroute/open-sse`) → relative။
- **အမည်ပေးပုံ**: File များအတွက် `camelCase` သို့မဟုတ် `kebab-case`၊ component များအတွက် `PascalCase`၊
  constant များအတွက် `UPPER_SNAKE`။
- **ESLint**: `no-eval`, `no-implied-eval`, `no-new-func` = နေရာတိုင်းတွင် `error`၊
  `no-explicit-any` = `open-sse/` နှင့် `tests/` တွင် `warn`၊ အခြားနေရာများတွင် error။
- **TypeScript**: `strict: false` (legacy အနေအထား)။ Module များကြား boundary များအတွက်
  inference ထက် explicit type များကို ဦးစားပေးပါ။
- **Database**: Route သို့မဟုတ် handler များတွင် raw SQL ကို မည်သည့်အခါမျှ မရေးပါနှင့် — အမြဲတမ်း
  `src/lib/db/` module များမှတစ်ဆင့် လုပ်ဆောင်ပါ။ Barrel-import ကို မည်သည့်အခါမျှ မလုပ်ပါနှင့် — သီးခြား `src/lib/db/*` module များကို တိုက်ရိုက်အသုံးပြုပါ။
- **DB entity typing (#3512)**: DB table တစ်ခု၏ row ပုံသဏ္ဌာန်ကို ရေးသားခြင်း သို့မဟုတ် ဖတ်ရှုခြင်းပြုသည့်
  function သည် ခေါ်ဆိုသည့်နေရာရှိ `any` သို့မဟုတ် inline anonymous type မဟုတ်ဘဲ ထို table ၏
  column များကို 1:1 ထင်ဟပ်သည့် အမည်ပေးထားသော TS interface ကို လက်ခံ/ပြန်ပေးရမည်။ Interface ကို
  function အနီးတွင် ထားပါ (ဥပမာ `saveRequestUsage` အပေါ်ရှိ
  `src/lib/usage/usageHistory.ts` ထဲမှ `export interface UsageEntry`)၊ မတူညီသော writer များက row ကို
  တဖြည်းဖြည်း ဖြည့်သွင်းသည့်အခါ field တစ်ခုချင်းစီကို optional/nullable အဖြစ် ထားပါ၊ ခေါ်ဆိုသူအလိုက် ပုံသဏ္ဌာန်
  ကွဲပြားသော field အတွက် `any` ထက် `unknown` ကို ဦးစားပေးပါ (field ပေါ်တွင် မှတ်တမ်းတင်ထားရမည်၊ ဥပမာ `UsageEntry.tokens`
  သည် မူရင်း provider ပုံသဏ္ဌာန်ရှိ usage နှင့် normalized ပုံသဏ္ဌာန် နှစ်မျိုးလုံးကို လက်ခံသည်)။ ဤနည်းဖြင့်
  file တစ်ခု၏ `any` အရေအတွက် သုညသို့ရောက်သည်နှင့် ပြန်လည်ဆုတ်ယုတ်မသွားစေရန် ၎င်းကို
  `check:any-budget:t11` allowlist (`scripts/check/check-t11-any-budget.mjs`,
  `maxAny: 0`) သို့ ထည့်ပါ။ ဤသည်မှာ ပထမအဆင့်ပိုင်းဆိုင်ရာ သတ်မှတ်ချက်ဖြစ်ပြီး ပိုမိုကျယ်ပြန့်သော “anonymous `any` မသုံးရ”
  ရှင်းလင်းရေးကို ကျန် codebase တစ်လျှောက် အဆင့်ဆင့် ဆောင်ရွက်သွားမည်ဖြစ်သည်။
- **Error များ**: သီးခြား error type များဖြင့် try/catch လုပ်ပြီး pino context ဖြင့် log မှတ်တမ်းတင်ပါ။ SSE stream များတွင်
  error များကို အသံတိတ် လျစ်လျူမရှုပါနှင့်၊ cleanup အတွက် abort signal များကို အသုံးပြုပါ။
- **လုံခြုံရေး**: `eval()` / `new Function()` / implied eval ကို မည်သည့်အခါမျှ မသုံးပါနှင့်။ Input အားလုံးကို
  Zod ဖြင့် အတည်ပြုစစ်ဆေးပါ။ သိမ်းဆည်းထားသော credential များကို encrypt လုပ်ပါ (AES-256-GCM)။
  `src/shared/constants/upstreamHeaders.ts` denylist ကို sanitize/validation layer နှင့် ကိုက်ညီအောင် ထားပါ။
- **Commit များ**: Conventional Commits — `feat(scope): subject`။ ခွင့်ပြုထားသော scope များမှာ
  `db`, `sse`, `oauth`, `dashboard`, `api`, `cli`, `docker`, `ci`, `mcp`,
  `a2a`, `memory`, `skills` ဖြစ်သည်။
- **Branch များ**: Prefix များမှာ `feat/`, `fix/`, `refactor/`, `docs/`, `test/`,
  `chore/` ဖြစ်သည်။ `main` သို့ မည်သည့်အခါမျှ တိုက်ရိုက် commit မလုပ်ပါနှင့်။
- **Husky**: pre-commit တွင် `lint-staged` + `check:docs-sync` +
  `check:any-budget:t11` ကို run သည်၊ pre-push တွင် `check:any-budget:t11` + `check:tracked-artifacts` ကို run သည် (မြန်ဆန်သော gate များဖြစ်ပြီး `test:unit` မပါဝင်ပါ)။

## 12. မဖြစ်မနေလိုက်နာရမည့် စည်းမျဉ်းများ (`CLAUDE.md` မှ)

1. လျှို့ဝှက်ချက်များ သို့မဟုတ် အထောက်အထားများကို မည်သည့်အခါမျှ commit မလုပ်ရ။
2. Barrel import ကို မည်သည့်အခါမျှ မသုံးရ — သီးခြား `src/lib/db/*` module များကို တိုက်ရိုက်အသုံးပြုရမည်။
3. `eval()` / `new Function()` / သွယ်ဝိုက်သော eval ကို မည်သည့်အခါမျှ မသုံးရ။
4. `main` သို့ မည်သည့်အခါမျှ တိုက်ရိုက် commit မလုပ်ရ။
5. Route များတွင် raw SQL ကို မည်သည့်အခါမျှ မရေးရ — `src/lib/db/` module များမှတစ်ဆင့် အမြဲလုပ်ဆောင်ရမည်။
6. SSE stream များရှိ error များကို အသိပေးခြင်းမရှိဘဲ မည်သည့်အခါမျှ လျစ်လျူမရှုရ။
7. Input များကို Zod schema များဖြင့် အမြဲ validate လုပ်ရမည်။
8. Production code ကို ပြောင်းလဲသည့်အခါ test များကို အမြဲထည့်သွင်းရမည်။
9. Coverage သည် ≥ 60% (statement များ၊ line များ၊ function များ၊ branch များ) ကို ဆက်လက်ထိန်းထားရမည်။
