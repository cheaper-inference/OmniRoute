> **အသုံးပြုသူများအတွက်**: ရိုးရှင်းသော လမ်းညွှန်ကို ရှာဖွေနေပါသလား။ အခမဲ့ AI ရယူရန် အဆင့်ဆင့်ညွှန်ကြားချက်များအတွက် [အခမဲ့အဆင့်များ လမ်းညွှန်](../getting-started/FREE-TIERS-GUIDE.md) ကို ကြည့်ပါ။

> **နောက်ဆုံး သုတေသနပြုခဲ့သည့်ရက်:** 2026-06-17 — အခမဲ့အဆင့် quota နှင့် ToS အားလုံးကို ပြန်လည်ဆန်းသစ်ထားသည့် provider တစ်ခုချင်းအလိုက် ဝဘ်သုတေသန (တရားဝင်စာရွက်စာတမ်းများ + နောက်ဆုံး 7 ရက်အတွင်း သတင်းများ၊ ဆန့်ကျင်ဘက်စိစစ်အတည်ပြုမှုပါဝင်သော agent 50 ခုဖြင့် စစ်ဆေးမှု)။ **တစ်စိတ်တစ်ပိုင်း ပြန်လည်စစ်ဆေးသည့်ရက် 2026-09-02** (`gemini`, `ollama-cloud`, `groq`, `nara`, `mistral` — အောက်ပါ ရက်စွဲပါမှတ်ချက်ကို ကြည့်ပါ)။
> **အမှန်တရားအတွက် အဓိကရင်းမြစ် (catalog):** `open-sse/config/freeModelCatalog.ts` (MODEL တစ်ခုချင်းစီအလိုက် budget များ၊ pool ထပ်နေမှုများကို ဖယ်ရှားထားသည်)။ အောက်ပါ token-budget ကိန်းဂဏန်းများသည် တိုက်ရိုက်ဝဘ်သုတေသနမှ ရရှိထားပြီး **ခန့်မှန်းခြေ** ဖြစ်သည် — [နည်းလမ်းနှင့် သတိပြုရန်အချက်များ](#methodology--caveats) ကို ကြည့်ပါ။

## TL;DR — OmniRoute က အမှန်တကယ် အခမဲ့ inference ဘယ်လောက်အထိ စုစည်းပေးသလဲ?

ဤကိန်းဂဏန်းများသည် catalog တစ်လျှောက်ရှိ သီးခြား third-party အကောင့်များနှင့် အကျုံးဝင်မှုအခြေအနေများကို ဖော်ပြထားခြင်းဖြစ်သည်။ OmniRoute က ဤဘတ်ဂျက်ကို ပေးအပ်ခြင်းမရှိပါ။ လိုအပ်သော အကောင့်များ သို့မဟုတ် credentials များကို သင်ကိုယ်တိုင် ရယူရမည်ဖြစ်ပြီး၊ အကျုံးဝင်သော provider များကို ချိတ်ဆက်ကာ ၎င်းတို့၏ ကန့်သတ်ချက်များကို လိုက်နာရမည်ဖြစ်သည်။ အမှန်တကယ် အသုံးပြုနိုင်သော capacity သည် လျော့နည်းနိုင်ပြီး၊ အကျုံးဝင်သော route မရှိသည့် fresh installation တွင် သုညပင် ဖြစ်နိုင်သည်။ `tos: avoid` ဟု သတ်မှတ်ထားသော provider များကို default အနေဖြင့် အလိုအလျောက် routing ပြုလုပ်ရာတွင် ဖယ်ထုတ်ထားသည်။

**စစ်ဆေးခဲ့သည့်ရက်စွဲ 2026-10-08:** [Cerebras](https://www.cerebras.ai/pricing) က payment method လိုအပ်ပြီး ရက် 30 အကြာတွင် သက်တမ်းကုန်ဆုံးမည့် တစ်ကြိမ်သုံး $5 promotional credit ကို ပေးထားသည်။ [Gemini](https://ai.google.dev/gemini-api/docs/rate-limits) က project/model/tier အလိုက် rate limit များကို ထုတ်ပြန်ထားပြီး၊ တစ်လစာ အဓိကကိန်းဂဏန်းတွင် မထည့်သွင်းထားပါ။

## 2026-10-18 SiliconFlow အခမဲ့ model ပြင်ဆင်ချက် (#17028)

ထုတ်ပြန်ထားသော token တစ်ခုချင်းစီအလိုက် အပေါင်းတန်ဖိုးရှိသည့် ဈေးနှုန်းများပါဝင်သော SiliconFlow ထိပ်တန်း model ဆယ်ခုကို `recurring-uncapped` အခမဲ့အသုံးပြုခွင့်အဖြစ် မှားယွင်းထည့်သွင်းဖြန့်ချိခဲ့သည်။ ထိုအတန်းဆယ်ခုကို static catalog မှ **ဖယ်ရှားပြီး** ဖြစ်သဖြင့် ယခု catalog တွင် **entry 467 ခု** ရှိသည်။ SiliconFlow သည် static စုစုပေါင်းကိန်းဂဏန်းများတွင် ခြွင်းချက်မရှိသော အခမဲ့ model အတန်း သို့မဟုတ် အမြဲတမ်းအခမဲ့ provider တစ်ခုအဖြစ် ပါဝင်ပံ့ပိုးခြင်း မရှိတော့ပါ။

ယင်းသည် SiliconFlow တွင် အခမဲ့ model လုံးဝမရှိဟု **မဆိုလိုပါ**။ အခမဲ့ model များသာ ထည့်သွင်းမှုနှင့် Free badge တို့အတွက် ယခုအခါ **တိုက်ရိုက် provider model payload မှ model တစ်ခုချင်းစီအတွက် အတည်ပြုနိုင်သော အထောက်အထား** လိုအပ်သည်။ ဥပမာ၊ အခမဲ့ဖြစ်ကြောင်း ရှင်းလင်းစွာညွှန်ပြထားသည့် boolean marker သို့မဟုတ် token ဈေးနှုန်းနှစ်ခုစလုံး သုညဖြစ်ခြင်းတို့ဖြစ်သည်။ ပေးချေရသည့် model ဖြစ်ကြောင်း ရှင်းလင်းစွာညွှန်ပြထားသော flag သို့မဟုတ် အပေါင်းတန်ဖိုးရှိသည့် ကိန်းဂဏန်းဈေးနှုန်းတစ်ခုခုသည် အခမဲ့ဖြစ်နိုင်ကြောင်း အကောင်းမြင်ဖော်ပြထားသော marker ထက် ဦးစားပေးသည်။ ရရှိနိုင်သော တိုက်ရိုက်အထောက်အထားမရှိသည့် model ကို အခမဲ့ဟု **မယူဆပါ**။ အကောင့်အသစ်အတွက် တစ်ကြိမ်သာရရှိသည့် credit သည် ထပ်တလဲလဲရရှိသော အခမဲ့ခွင့်ပြုချက်ဖြစ်ကြောင်း သက်သေမပြနိုင်ပါ။ လက်ရှိ provider API က model အဆင့်ရှိ ယုံကြည်စိတ်ချရသော ဈေးနှုန်းအချက်အလက်ကို မပေးနိုင်ပါက routing မလုပ်မီ provider console တွင် အတည်ပြုပါ။ ဤသတိထားသည့် ရွေးချယ်မှုက အခမဲ့ model များသာ ထည့်သွင်းခြင်းနှင့် အလိုအလျောက်ပေါင်းစပ်မှုများမှတစ်ဆင့် မမျှော်လင့်ထားသော ကုန်ကျစရိတ်များ ဖြစ်ပေါ်ခြင်းကို တားဆီးပေးသည်။

အောက်ပါ သမိုင်းမှတ်တမ်း provider ဇယားသည် လက်ရှိရရှိနိုင်မှုအတွက် ကတိပြုချက်မဟုတ်ပါ။ ၎င်း၏ ယခင် SiliconFlow အကန့်အသတ်မရှိ/10-model entry ကို ရည်ရွယ်ချက်ရှိရှိ မထည့်သွင်းထားခြင်းမှာ အဆိုပါ entry က အတည်ပြုပြီးဖြစ်သည့် ထပ်တလဲလဲရရှိသော အခမဲ့ခွင့်ပြုချက်ကို ကိုယ်စားမပြုတော့သောကြောင့် ဖြစ်သည်။

ဤခွဲခြားမှုကို ရည်ရွယ်ချက်ရှိရှိ ထိန်းသိမ်းထားသည်။

## နည်းလမ်းနှင့် သတိပြုရန်အချက်များ

- ဂဏန်းများသည် ဝန်ဆောင်မှုပေးသူတစ်ခုချင်းစီ၏ မှတ်တမ်းတင်ထားသော အခမဲ့အဆင့် ကန့်သတ်ချက်များကို အခြေခံထားသည့် **အမြင့်ဆုံးကန့်သတ်ချက် ခန့်မှန်းချက်များ** ဖြစ်ပြီး **2026-06-17** အထိ ဝဘ်သုတေသနပြုစုထားခြင်း ဖြစ်သည်။ အခမဲ့အဆင့်များသည် အမြဲပြောင်းလဲနေသောကြောင့် ဂဏန်းတစ်ခုကို အားကိုးအသုံးမပြုမီ ပြန်လည်စစ်ဆေးပါ။
- **Entry တစ်ခုက အမှန်တကယ် ဘာကို အာမခံပေးသလဲ။** Entry တစ်ခုချင်းစီတွင် row အလိုက် ယုံကြည်စိတ်ချရမှုအဆင့် သတ်မှတ်ချက် မရှိသကဲ့သို့ API ကလည်း မပေးပါ — အထက်ပါဂဏန်းတိုင်းကို အမည်မဖော်ပြထားသည့် အရည်အသွေးတူ ခန့်မှန်းချက်တစ်ခုအဖြစ်သာ သတ်မှတ်ပါ။ အချက်နှစ်ချက်မှာ လက်ဖြင့် စုစည်းထားခြင်းဖြစ်၍ ခန့်မှန်းထားခြင်းမဟုတ်သောကြောင့် ကွဲပြားသည် — Entry 44 ခုတွင် သီးခြားမှတ်တမ်းတင်ထားသည့် hard stop ပါရှိပြီး (ထိုအထဲမှ 39 ခုမှာ တူညီသော နေ့စဉ်ခွင့်ပြုချက်ကို မျှဝေသုံးစွဲသည့် xKiro rows များဖြစ်သည်)၊ Entry 22 ခုတွင် prompt လေ့ကျင့်ရေးဆိုင်ရာ ဖော်ပြချက် ပါရှိသည်။ `hardStopGuaranteed` ကို ဝန်ဆောင်မှုပေးသူ၏ ကိုယ်ပိုင်စည်းမျဉ်းများတွင် အခမဲ့ခွင့်ပြုချက်ကို ကျော်လွန်သုံးစွဲပါက တိတ်တဆိတ် ငွေကောက်ခံမှု စတင်မည့်အစား request ကို ငြင်းပယ်မည်ဟု ဖော်ပြထားသည့်အခါတွင်သာ သတ်မှတ်ပြီး၊ ထိုအချက်၏ ရင်းမြစ်ကို Entry ဘေးရှိ comment တွင် ထည့်သွင်းထားသည်။ ၎င်းကို `true` သို့ ပုံသေသတ်မှတ်ခြင်း မရှိသကဲ့သို့ မည်သူမျှ အတည်မပြုရသေးသည့် Entry ကိုလည်း သတ်မှတ်မထားပါ။ ထို့ကြောင့် hard-stop flag မရှိခြင်းသည် "မသတ်မှတ်ရသေးခြင်း" ကို ဆိုလိုပြီး "ငွေကောက်ခံမည်ဟု သိရှိထားခြင်း" ကို မဆိုလိုပါ။ **STRICT mode** (ရွေးချယ်အသုံးပြုနိုင်သော `freeAccessPolicy=strict` routing guard) သည် flag ပါရှိသည့် Entry များကိုသာ ယုံကြည်သည်။ အခြား free tier အားလုံးကို `no-hard-stop` အဖြစ် ဖယ်ရှားထားသည် (ကြည့်ရန် `open-sse/services/autoCombo/strictZeroCostFilter.ts`)။ Guard က pool တစ်ခုကို filter လုပ်သည့်အခါ operator မြင်နိုင်သည့် log တွင် ဖယ်ရှားထားသည့်အရေအတွက်နှင့် ၎င်းတို့အနက် `no-hard-stop` ဖြစ်သည့် အချိုးအစား နှစ်ခုလုံးကို ဖော်ပြသည်။
- `estMonthlyFreeTokens` = လစဉ် ထပ်တလဲလဲရရှိသော token များသာ ဖြစ်သည်။ **တစ်ကြိမ်သာရရှိသော signup credits များသည် ထပ်မရရှိသည့်အတွက်** 0 အဖြစ်တွက်သည်။ ရပ်ဆိုင်းထားသည့် tier များကိုလည်း 0 အဖြစ်တွက်သည်။
- နေ့စဉ် token cap → `monthly = daily × 30`။ RPD ကိုသာ မှတ်တမ်းတင်ထားပါက → `RPD × ~800 output tokens × 30`။ RPM/TPM ကိုသာ (နေ့စဉ် cap မရှိဘဲ) မှတ်တမ်းတင်ထားပါက → **ကန့်သတ်မရှိ** (အောက်တွင်ကြည့်ပါ)။
- **အခမဲ့အသုံးပြုခွင့်ရှိသော်လည်း ထုတ်ပြန်ထားသော token cap မရှိခြင်း** (`glm-cn`, `tencent`, `baidu`, `kilo-gateway`, `opencode-zen`, `gemini`, `nvidia`) — ၎င်းတို့ကို rate/concurrency ကန့်သတ်ထားသည်။ ၎င်းတို့ကို `recurring-uncapped` အဖြစ် သတ်မှတ်ပြီး **မည်သည့်အခါမျှ ပေါင်းမတွက်ပါ** — `RPM × 24/7 × 30d` ဖြင့် မြှောက်ခြင်းသည် စိတ်ကူးယဉ်အမြင့်ဆုံးပမာဏကို ဖြစ်ပေါ်စေမည်ဖြစ်သောကြောင့် (ကျွန်ုပ်တို့ ပယ်ချသည့် ဖောင်းပွမှု) ဖြစ်သည်။ NVIDIA ၏ API သည် စမ်းသပ်အသုံးပြုရန်အတွက်သာ ဖြစ်သည်။ အောက်ပါ ToS သတိပြုရန်အချက်ကို ကြည့်ပါ။
- **Deposit-unlock boost:** တစ်ကြိမ်သာ အနည်းငယ်ငွေဖြည့်ခြင်းဖြင့် အခမဲ့ quota ကို အမြဲတမ်းမြှင့်တင်ပေးသည် (OpenRouter: $10 → 1000 req/day ≈ +24M/mo)။ ၎င်းကို သီးခြားဂဏန်းအဖြစ် ဖော်ပြပြီး ပုံမှန် headline ထဲတွင် မထည့်ပါ။
- **Eligibility-gated quotas** (`eligibilityGate: "regional-identity"`): ဒေသအလိုက် သတ်မှတ်ထားသော identity စစ်ဆေးမှု (လက်ရှိတွင် တရုတ်ပြည်မကြီး၏ အမည်ရင်းအတည်ပြုမှု) ပြီးဆုံးမှသာ ရရှိနိုင်သည့် အမှန်တကယ် ထပ်တလဲလဲရရှိသော quota ဖြစ်သည်။ ၎င်းကို pool-dedupe rule တူညီစွာ အသုံးပြုပြီး သီးခြားဂဏန်း (`gatedRecurringTokens`) ထဲတွင်သာ တွက်ချက်ကာ ပုံမှန် headline ထဲသို့ မည်သည့်အခါမျှ မထည့်ပါ။ စနစ် (`freeType`) သည် မပြောင်းလဲသောကြောင့် routing လည်း မပြောင်းလဲပါ။
- **အထောက်အထားအမျိုးအစားများ။** စည်းမျဉ်းမှာ catalog ထဲရှိ ဂဏန်းတစ်ခု၏ အရင်းအမြစ်ကို Entry ဘေးရှိ `// evidence:` comment တွင် ကိုးကားရမည် — `public-page` (မည်သူမဆို ဖတ်ရှုနိုင်သည့် ဝန်ဆောင်မှုပေးသူ၏ စာမျက်နှာ)၊ `api-public` (ဥပမာ router.bynara.id ရှိ NaraRouter ၏ public plans endpoint ကဲ့သို့ ဝန်ဆောင်မှုပေးသူ၏ authentication မလိုသော endpoint) သို့မဟုတ် `console-verified <date> por <who>` (ဂဏန်းကို account console အတွင်းတွင်သာ မြင်နိုင်ပြီး comment တွင် ၎င်းကို မည်သူက မည်သည့်အချိန်တွင် မြင်တွေ့ခဲ့သည်နှင့် cap ရှိကြောင်း ဖော်ပြသည့် public page ကို မှတ်တမ်းတင်ထားသည်) ဖြစ်သည်။ ယနေ့အခြေအနေမှာ 2026-09-02 တွင် ပြန်လည်စစ်ဆေးထားသော block ငါးခု (`gemini`, `groq`, `mistral`, `ollama-cloud`, `nara`) တွင် ၎င်းကို ထည့်သွင်းထားသည်။ 2026-09-02 ပြန်လည်စစ်ဆေးမှု မတိုင်မီရှိခဲ့သော Entry များသည် ပြန်လည်ပြင်ဆင်မခံရမချင်း ယခင်သုတေသနအထောက်အထားကို ဆက်လက်အသုံးပြုသည်။ **အသစ်ထည့်သွင်းထားသော သို့မဟုတ် ပြောင်းလဲထားသော** ဂဏန်းတစ်ခုတွင် evidence comment မပါရှိပါက ၎င်းသည် bug ဖြစ်သည်။ ယနေ့အချိန်တွင် `mistral` တစ်ခုတည်းသာ console-verified ဖြစ်သည်။

## ကျွန်ုပ်တို့၏ နံပါတ်သည် အခြား aggregator များ၏ နံပါတ်များထက် အဘယ်ကြောင့် ပိုနည်းသနည်း

ဤနယ်ပယ်ရှိ "တစ်လလျှင် အခမဲ့ token များ" ဟူသော ကိန်းဂဏန်းအများစုသည် model တစ်ခုချင်းစီ၏ label များကို ပေါင်းထားခြင်းဖြစ်သည်။ ကျွန်ုပ်တို့၏ ကိန်းဂဏန်းမှာမူ ရည်ရွယ်ချက်ရှိရှိ ထိုသို့မဟုတ်ပါ-

- **မျှဝေသုံးစွဲသည့် pool တစ်ခုစီကို တစ်ကြိမ်သာ ရေတွက်သည်။** Mistral ၏ အခမဲ့အစီအစဉ်သည် organization တစ်ခုလျှင် တစ်လ 1B သုံးစွဲခွင့်တစ်ခုဖြစ်သည်။ ၎င်းကို model ငါးခုအောက်တွင် စာရင်းသွင်းထားခြင်းကြောင့် 5B ဖြစ်မသွားပါ။ Model တစ်ခုချင်းစီအလိုက် ပေါင်းပါက ကျွန်ုပ်တို့၏ ကိုယ်ပိုင် catalog သည် **~7.4B** ဟု ပြမည် (2026-09-03 တွင် ပြန်လည်တွက်ချက်ထားသည်။ ဤကိန်းဂဏန်းကို CI ဖြင့် ထိန်းချုပ်ထားခြင်းမရှိသောကြောင့် catalog ပြောင်းလဲသည့်အခါတိုင်း ပြန်လည်တိုင်းတာပါ) — ခေါင်းစီးတွင် **~1.47B** ဟု ဖော်ပြထားခြင်းမှာ provider တစ်ခုစီ၏ account တစ်ခုက အမှန်တကယ် သုံးစွဲနိုင်သည့်ပမာဏ ဖြစ်သောကြောင့်ဖြစ်သည်။
- **နေ့စဉ်ကန့်သတ်ချက်များကို ပြောင်းလဲတွက်ချက်သော်လည်း rate များကို မတွက်ချက်ပါ။** မှတ်တမ်းတင်ဖော်ပြထားသော tokens/day ကန့်သတ်ချက်ကို `× 30` အဖြစ် ပြောင်းလဲသည်။ မှတ်တမ်းတင်ဖော်ပြထားသော requests/day ကန့်သတ်ချက်ကို `RPD × ~800 tokens × 30` အဖြစ် ပြောင်းလဲသည်။ Requests-per-minute ကိုသာ ထုတ်ပြန်သည့် provider တွင် လစဉ်ကိန်းဂဏန်း **မရှိဘဲ** _uncapped_ အဖြစ် စာရင်းသွင်းထားကာ ပေါင်းလဒ်ထဲသို့ လုံးဝမထည့်ပါ။ Rate limit ကို 24/7 ဖြင့် မြှောက်ကာ ကိန်းဂဏန်းဖောင်းပွစေခြင်းကို ကျွန်ုပ်တို့ လက်မခံပါ။
- **ဒေသအလိုက် အထောက်အထားစစ်ဆေးမှုနောက်ကွယ်ရှိ quota များကို သီးခြားဖော်ပြထားသည်** (`+~6M behind regional identity verification`)၊ အဘယ်ကြောင့်ဆိုသော် ဖတ်ရှုသူအများစုက ၎င်းတို့ကို အသုံးမပြုနိုင်သောကြောင့်ဖြစ်သည်။
- **Signup credit များသည် ပထမလအတွက်သာဖြစ်ပြီး** ပုံမှန်တည်ငြိမ်သော ကိန်းဂဏန်းထဲသို့ မရောနှောဘဲ ဒုတိယကိန်းဂဏန်းအဖြစ်သာ အစီရင်ခံထားသည်။
- **ဤကိန်းဂဏန်းကို CI ဖြင့် အတည်ပြုထိန်းချုပ်ထားသည်။** `npm run check:docs-counts` သည် catalog မှ စုစုပေါင်းများကို ပြန်လည်တွက်ချက်ပြီး ဤဖိုင်၊ README သို့မဟုတ် budget card ရှိ ကိန်းဂဏန်းများနှင့် ကွာဟလာပါက build ကို ကျရှုံးစေသည်။

## ToS သတိပြုရန် ဇယား

> **ToS အလံသည် အကြံပြုချက်သာဖြစ်ပြီး လမ်းကြောင်းသတ်မှတ်မှု တံခါးကာမဟုတ်ပါ။** `tos` ဟု မှတ်သားထားသော Provider များကို မူလသတ်မှတ်ချက်အရ routing နှင့် combo/fallback တွင် ဆက်လက်ထည့်သွင်းထားသည်။ ဤအလံသည် `/dashboard/free-tiers` နှင့် `/api/free-tier/summary` တွင်သာ ဖော်ပြပေးသည်။ `excludeTosAvoid` query parameter သည် summary မြင်ကွင်းကိုသာ သက်ရောက်ပြီး အထွေထွေ routing ကို မသက်ရောက်ပါ။ ဆုံးဖြတ်ချက်သည် `open-sse/config/freeTierCatalog.ts` တွင် ရှိသည် (အချက်အလက်ပေးရန်သာဖြစ်ပြီး routing engine များက ဖတ်ရှုအသုံးမပြုပါ)။

> ကိုယ်တိုင် host လုပ်ထားသော၊ အသုံးပြုသူတစ်ဦးတည်းအတွက် ကိုယ်ပိုင် proxy အဖြစ် အသုံးပြုရာတွင် Provider တစ်ခုချင်းစီ၏ စည်းမျဉ်းများကို အမြန်ဖတ်ရှုရန်။ `caution` = ကိုယ်ပိုင်အသုံးပြုမှု သို့မဟုတ် proxy ဆိုင်ရာ စစ်ဆေးသင့်သော စည်းကမ်းချက်ရှိသည်; `ambiguous` = မရှင်းလင်းပါ; `ok` = ခွင့်ပြုထားကြောင်း အတိအလင်း ဖော်ပြထားသည်။ အချက်အလက်ပေးရန်သာဖြစ်ပြီး ဥပဒေရေးရာ အကြံဉာဏ်မဟုတ်ပါ — ဆုံးဖြတ်ချက်ကို သင်ကိုယ်တိုင် ချမှတ်ရမည်။
