## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### စိတ်ကြိုက် Header များ

| Header                   | ဦးတည်ချက် | ဖော်ပြချက်                                                                                                                                                                                                                                                        |
| ------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Request   | Cache ကို ကျော်လွှားရန် `true` ဟု သတ်မှတ်ပါ                                                                                                                                                                                                                       |
| `x-omniroute-no-memory`  | Request   | ဤ request အတွက် memory နှင့် skills ထည့်သွင်းမှုကို ကျော်ရန် `true` ဟု သတ်မှတ်ပါ (no-cache နှင့် တူညီပြီး call တစ်ခုစီ၏ token/ကုန်ကျစရိတ် overhead ကို ရှောင်ရှားပေးသည်)                                                                                          |
| `X-OmniRoute-Progress`   | Request   | တိုးတက်မှု event များအတွက် `true` ဟု သတ်မှတ်ပါ                                                                                                                                                                                                                    |
| `X-Session-Id`           | Request   | ပြင်ပ session affinity အတွက် sticky session key                                                                                                                                                                                                                   |
| `x_session_id`           | Request   | Underscore ပုံစံကိုလည်း လက်ခံသည် (တိုက်ရိုက် HTTP)                                                                                                                                                                                                                |
| `X-OmniRoute-Session-Id` | Request   | ခေါ်ဆိုသူက ပေးပို့သော session/conversation tag (memory ကိုလည်း ဖြည့်သွင်းပေးသည်)။ ပါရှိသည့်အခါ session တစ်ခုစီအလိုက် ကုန်ကျစရိတ်သတ်မှတ်နိုင်ရန် `call_logs.session_tag` ထဲသို့ မူရင်းအတိုင်း သိမ်းဆည်းသည် (#8249) — မပါရှိပါက မည်သည့်အခါမျှ အလိုအလျောက် မဖန်တီးပါ |
| `Idempotency-Key`        | Request   | ထပ်တူများဖယ်ရှားရန် key (၅ စက္ကန့်ကြာ window)                                                                                                                                                                                                                     |
| `X-Request-Id`           | Request   | အစားထိုးအသုံးပြုနိုင်သော ထပ်တူဖယ်ရှားရေး key                                                                                                                                                                                                                      |
| `x-omniroute-connection` | Request   | Model တစ်ခုတည်းပါသော request ကို ၎င်း၏ id ဖြင့် provider connection (account) တစ်ခုတွင် ပုံသေချိတ်ထားပါ — [Request တစ်ခုစီအတွက် account ပုံသေချိတ်ခြင်း](#account-pinning-per-request) ကို ကြည့်ပါ                                                                |
| `X-OmniRoute-Cache`      | Response  | `HIT` သို့မဟုတ် `MISS` (streaming မဟုတ်သည့်အခါ)                                                                                                                                                                                                                   |
| `X-OmniRoute-Idempotent` | Response  | ထပ်တူဖယ်ရှားထားပါက `true`                                                                                                                                                                                                                                         |
| `X-OmniRoute-Progress`   | Response  | တိုးတက်မှုခြေရာခံခြင်း ဖွင့်ထားပါက `enabled`                                                                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | Response  | OmniRoute အသုံးပြုခဲ့သည့် အကျိုးသက်ရောက်သော session ID                                                                                                                                                                                                            |
| `X-OmniRoute-Request-Id` | Response  | Request ဆက်စပ်ဖော်ထုတ်ရေး id (သိရှိသည့်အခါ)                                                                                                                                                                                                                       |
| `X-OmniRoute-Version`    | Response  | OmniRoute build version (အမြဲပါရှိသည်)                                                                                                                                                                                                                            |
| `X-OmniRoute-Cost-Saved` | Response  | HIT တစ်ခုတွင် cache ကြောင့် ရှောင်ရှားနိုင်ခဲ့သော USD ကုန်ကျစရိတ် (cache hit များအတွက်သာ)                                                                                                                                                                         |
| `X-OmniRoute-Decision`   | Response  | Routing trace: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` သည် combo strategy ဖြစ်ပြီး combo မဟုတ်သော request အတွက် `single` ဖြစ်သည်) — ပြီးစီးမှု response များတွင် အမြဲပါရှိသည်                                                               |

> Nginx မှတ်ချက်- underscore ပါဝင်သည့် header များ (ဥပမာ `x_session_id`) ကို အသုံးပြုထားပါက `underscores_in_headers on;` ကို ဖွင့်ထားပါ။

#### တောင်းဆိုမှုတစ်ခုချင်းအလိုက် အကောင့်ကို ပင်တွဲသတ်မှတ်ခြင်း

ပံ့ပိုးသူတစ်ခုတွင် ချိတ်ဆက်မှုများ (အကောင့်များ သို့မဟုတ် key များ) အများအပြားရှိသည့်အခါ OmniRoute သည် ပုံမှန်အားဖြင့် ၎င်း၏ အကောင့်ရွေးချယ်မှု နည်းဗျူဟာမှတစ်ဆင့် ချိတ်ဆက်မှုတစ်ခုကို
ရွေးချယ်သည်။ သို့သော် တောင်းဆိုမှုတစ်ခုသည် `x-omniroute-connection` header ကို အသုံးပြု၍
သီးခြားချိတ်ဆက်မှုတစ်ခုကို ပင်တွဲသတ်မှတ်နိုင်သည်-

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id ကို ရှာရန်နေရာ။** dashboard ရှိ ပံ့ပိုးသူစာမျက်နှာ
  (**Dashboard → Providers → <provider>**) ကို ဖွင့်ပြီး ချိတ်ဆက်မှု row တစ်ခုရှိ `xxxxxxxx…` id chip ကို နှိပ်ပါ
  — ၎င်းသည် ချိတ်ဆက်မှု id အပြည့်အစုံကို ကူးယူပေးသည်။
- **၎င်းကို လိုက်နာသည့် တောင်းဆိုမှုများ။** `/v1/chat/completions`, `/v1/messages` နှင့် `/v1/responses` ရှိ
  မော်ဒယ်တစ်ခုတည်းသုံး တောင်းဆိုမှုများ (`provider/model`)။ Combo များသည် header ကို လျစ်လျူရှုသည်- ယင်းအစား
  combo အဆင့်တစ်ခုစီ၏ ကိုယ်ပိုင်ချိတ်ဆက်မှုမှတစ်ဆင့် အကောင့်တစ်ခုကို ပင်တွဲသတ်မှတ်ပါ။
- **ပင်တွဲသတ်မှတ်မှုသည် ဦးစားပေးချက်မျှမဟုတ်ဘဲ တင်းကျပ်စွာ အကျုံးဝင်သည်။** ပင်တွဲသတ်မှတ်ထားသည့် ချိတ်ဆက်မှုကိုသာ သီးသန့်အသုံးပြုသည်။
  တောင်းဆိုမှုအတွင်း ချို့ယွင်းမှုတစ်ခု ဖြစ်ပေါ်ပါက အကောင့်၏ cooldown ကို မှတ်တမ်းတင်သော်လည်း တူညီသည့် ပံ့ပိုးသူ၏
  အခြားအကောင့်သို့ **ပြောင်းလဲအသုံးပြုမည် မဟုတ်ပါ**။
- **Cooldown နှင့် quota က ပင်တွဲသတ်မှတ်မှုကို ဖြေလွှတ်သည်။** ပင်တွဲသတ်မှတ်ထားသည့် ချိတ်ဆက်မှုသည် cooldown ဖြစ်နေစဉ်၊
  quota ကုန်ဆုံးနေစဉ် သို့မဟုတ် quota မူဝါဒကြောင့် ပိတ်ဆို့ခံထားရစဉ်တွင် နောက်ပိုင်းတောင်းဆိုမှုများသည် ပင်တွဲမသတ်မှတ်ထားသော traffic ကဲ့သို့ပင်
  ပံ့ပိုးသူ၏ အခြားချိတ်ဆက်မှုများကို ပြန်လည်အသုံးပြုသည်။
- **မသိရှိသော သို့မဟုတ် ပိတ်ထားသော id များသည် မအောင်မြင်ပါ။** ပံ့ပိုးသူ၏ active pool ထဲတွင် မရှိသည့် id တစ်ခု (ဖျက်ထားသော၊
  အသက်မဝင်အောင် ပြုလုပ်ထားသော သို့မဟုတ် အခြားပံ့ပိုးသူတစ်ခုနှင့် သက်ဆိုင်သော id) ကြောင့် အသုံးပြုနိုင်သည့် အကောင့်မရှိတော့သဖြင့် တောင်းဆိုမှုကို
  အခြားနေရာသို့ တိတ်တဆိတ် လမ်းကြောင်းပြောင်းပေးမည့်အစား မအောင်မြင်စေသည်။

Claude Code သည် စိတ်ကြိုက် header များကို `ANTHROPIC_CUSTOM_HEADERS` မှတစ်ဆင့် ပေးပို့သည်။ ပရောဂျက်တစ်ခုချင်းစီအတွက်
မတူညီသည့် အကောင့်တစ်ခုကို ပင်တွဲသတ်မှတ်ရန် ၎င်းကို `~/.claude/settings.json` ၏ `env` block ထဲတွင် သို့မဟုတ်
ပရောဂျက်အဆင့် `.claude/settings.json` ထဲတွင် ထည့်ပါ-

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ရင်းမြစ်- `src/sse/handlers/chat.ts` (header ဖတ်ရှုခြင်း)၊ `src/sse/services/auth.ts` နှင့်
`src/sse/services/sessionAffinityPin.ts` (ပင်တွဲသတ်မှတ်မှုကို ဖြေလွှတ်ခြင်းနှင့် pool ထဲတွင် မရှိကြောင်း စစ်ဆေးခြင်း)။

> **ကုန်ကျစရိတ် telemetry header များ-** streaming မဟုတ်သော အောင်မြင်သည့် response များတွင် `X-OmniRoute-*` ကုန်ကျစရိတ် telemetry အစုလည်း ပါဝင်သည် — `X-OmniRoute-Response-Cost` (USD၊ ဒဿမ ၁၀ နေရာဖြင့် ပုံသေဖော်ပြသည်၊ အခမဲ့/ဈေးနှုန်းမသတ်မှတ်ထားပါက `0.0000000000`)၊ `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`၊ `X-OmniRoute-Model`၊ `X-OmniRoute-Provider`၊ `X-OmniRoute-Latency-Ms`၊ `X-OmniRoute-Cache-Hit` နှင့် `X-OmniRoute-Fallback-Attempts` (> 0 ဖြစ်မှသာ)၊ ထို့အပြင် `X-OmniRoute-Request-Id` နှင့် `X-OmniRoute-Version` တို့ဖြစ်သည်။ ၎င်းတို့ကို chat completions၊ `/v1/responses`၊ `/v1/messages` **နှင့် media endpoint များအားလုံး** — `/v1/embeddings`၊ `/v1/images/generations`၊ `/v1/audio/speech`၊ `/v1/audio/transcriptions`၊ `/v1/rerank`၊ `/v1/videos/generations`၊ `/v1/music/generations` နှင့် `/v1/moderations` (ကုန်ကျစရိတ် အမြဲတမ်း `0`) — က ထုတ်ပေးသည်။ ဈေးနှုန်းအချက်အလက် ရရှိနိုင်ပါက media ကုန်ကျစရိတ်ကို modality တစ်မျိုးချင်းအလိုက် (ပုံတစ်ပုံလျှင်၊ စက္ကန့်တစ်စက္ကန့်လျှင်၊ စာလုံးတစ်လုံးလျှင်၊ search-unit တစ်ခုလျှင်) တွက်ချက်ပြီး၊ မရရှိနိုင်ပါက `0` (fail-open) အဖြစ် သတ်မှတ်သည်။

> **Cache-hit ကုန်ကျစရိတ် သဘောတရား-** semantic-cache HIT တစ်ခု (`X-OmniRoute-Cache-Hit: true`) ဖြစ်သည့်အခါ upstream call ပြုလုပ်ခြင်းမရှိသောကြောင့် `X-OmniRoute-Response-Cost` သည် `0.0000000000` ဖြစ်သည် (hit ကို ဝန်ဆောင်မှုပေးခြင်း၏ **ထပ်တိုး** ကုန်ကျစရိတ်)။ မူလ/ဖြစ်လာနိုင်ခဲ့သည့် ကုန်ကျစရိတ်ကို `X-OmniRoute-Cost-Saved` တွင် သီးခြားအစီရင်ခံသည်။ Billing အသုံးပြုသူများသည် `X-OmniRoute-Response-Cost` ကို စုစုပေါင်းတွက်ချက်သင့်သည် (hit များအတွက် ကုန်ကျစရိတ်မရှိပါ)၊ cache analytics များအတွက်မူ `X-OmniRoute-Cost-Saved` ကို စုစည်းတွက်ချက်နိုင်သည်။

## သီးသန့် စီမံခန့်ခွဲထားသော စက်ရှင် ငှားရမ်းခွင့်များ

သီးသန့် စီမံခန့်ခွဲထားသော စက်ရှင် ငှားရမ်းခြင်းသည် အသုံးပြုရန် ကိုယ်တိုင်ရွေးချယ်ရပြီး client နှင့်မသက်ဆိုင်သော routing သဘောတူညီချက်တစ်ခုဖြစ်သည်။ လက်ရှိအသုံးပြုနေသော ပိုင်ရှင်တစ်ဦးသည် သတ်မှတ်ချက်ပြည့်မီသော OmniRoute ချိတ်ဆက်မှုတစ်ခုကို ကိုင်ထားသည်။ ၎င်းသည် model တစ်ခုကို ငှားရမ်းခြင်းမဟုတ်သကဲ့သို့ OAuth ကိုလည်း မလိုအပ်ပါ၊ သီးခြား client တစ်ခုကိုလည်း သတ်မှတ်ဖော်ထုတ်ခြင်းမရှိပါ၊ သီးခြား provider တစ်ခုကိုလည်း မလိုအပ်ပါ။

စစ်မှန်ကြောင်းအတည်ပြုရာတွင် အသုံးပြုသော API key တွင် `lease:exclusive` scope နှင့် ပြတ်သားစွာ သတ်မှတ်ထားသော ဗလာမဟုတ်သည့် `allowedConnections` စာရင်း ရှိရမည်။ Database mutation boundary သည် key ဖန်တီးချိန်နှင့် တစ်စိတ်တစ်ပိုင်း update လုပ်ချိန် နှစ်ခုစလုံးတွင် အဆိုပါ field နှစ်ခုကို တွဲဖက်၍ မဖြစ်မနေ လိုက်နာစေသည်။

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

အောင်မြင်သော acquire၊ renew နှင့် release response များတွင် timestamp များ၊ `state` နှင့် တိကျသော အပေါင်းကိန်း `generation` တို့ကို ဖော်ပြသော်လည်း ရွေးချယ်ထားသော connection သို့မဟုတ် credential များကို မည်သည့်အခါမျှ မဖော်ပြပါ။ Renew နှင့် release တို့သည် JSON body အတွင်း generation ကို ပေးပို့ရသည်-

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

လက်ရှိအသုံးပြုနေသော lease ပိုင်ရှင်သည် ၎င်း၏ လက်ရှိ binding အတွက် ကိုယ်ရေးအချက်အလက်လုံခြုံသည့် display metadata ကို ပြတ်သားစွာ တောင်းဆိုနိုင်သည်-

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ဤကိုယ်တိုင်ရွေးချယ်အသုံးပြုရသော status action ကို ခွဲခြားမသိနိုင်သည့် owner၊ စစ်မှန်ကြောင်း အတည်ပြုထားသော managed API key နှင့် တိကျသော လက်ရှိအသုံးပြုနေသည့် generation တို့ဖြင့် database transaction တစ်ခုတည်းအတွင်း ကန့်သတ်ထားသည်။ `displayName` သည် အစနှင့်အဆုံးရှိ whitespace များကို ဖယ်ရှားထားသော သတ်မှတ်ချိတ်ဆက်မှုအမည်သာဖြစ်ပြီး လုံခြုံစွာ သတ်မှတ်ထားသော အမည်မရှိပါက `null` ဖြစ်သည်။ OmniRoute သည် email သို့မဟုတ် စနစ်က ထုတ်လုပ်ထားသော account identity ကို မည်သည့်အခါမျှ အစားထိုးအသုံးမပြုပါ။ Provider value သည် အရေးကြီးအချက်အလက် မပါဝင်သော display label တစ်ခုဖြစ်ပြီး စနစ်က ထုတ်လုပ်ထားသော compatible-provider identifier လုံးဝမဟုတ်ပါ။ Credential များ၊ token များ၊ cookie များ၊ မပြုပြင်ရသေးသော connection သို့မဟုတ် API key id များ၊ owner hash များ၊ fencing secret များနှင့် အတွင်းပိုင်း routing data တို့ကို ဖယ်ထုတ်ထားသည်။

မှားယွင်းသော key၊ မှားယွင်းသော owner၊ သက်တမ်းမမီတော့သော generation၊ မရှိသော၊ သက်တမ်းကုန်သော၊ release လုပ်ထားသောနှင့် invalid ဖြစ်သွားသော lookup များအားလုံးသည် connection metadata မပါဘဲ တူညီသော `409 LEASE_FENCE_STALE` error ကို ပြန်ပေးသည်။ Capacity-wait response ကို လက်ခံရရှိထားသော client တွင် စစ်ဆေးနိုင်သည့် လက်ရှိ binding မရှိပါ။ Routing က လက်ရှိအသုံးပြုနေသော lease တစ်ခုကို ပြောင်းလဲပေးသောအခါ တူညီသည့် generation သည် ဆက်လက်အကျုံးဝင်ပြီး status သည် binding အသစ်ကို atomic နည်းလမ်းဖြင့် ပြန်ပေးကာ အဟောင်းကို မည်သည့်အခါမျှ ပြန်မပေးပါ။ Acquire၊ renew၊ release နှင့် waiting response များသည် ၎င်းတို့၏ ယခင်ဖွဲ့စည်းပုံများအတိုင်း ဆက်ရှိနေသောကြောင့် ရှိပြီးသား client များမှာ မပြောင်းလဲပါ။

ဤ server သဘောတူညီချက်သည် မူလ OpenAI Codex `/status` ကို မပြောင်းလဲပါ။ မူလ Codex သည် လက်ရှိတွင် ၎င်း၏ model provider နှင့် ပါရှိပြီးသား authentication/account state ကို အစီရင်ခံသော်လည်း စိတ်ကြိုက် provider account metadata ကို ဖော်ပြပေးခြင်းမရှိပါ။ နောင်တွင်ပြုလုပ်မည့် client integration သည် ဤ action ကို ခေါ်ယူပြီး `connection.displayName` ကို မည်သို့ပြသမည်ကို ဆုံးဖြတ်ရမည်။

ထို့နောက် စီမံခန့်ခွဲထားသော inference request တိုင်းသည် control header နှစ်ခုစလုံးကို ပေးပို့ရသည်-

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ပံ့ပိုးထားသော upstream attempt တစ်ခုစီမတိုင်မီ တိကျသော owner၊ generation၊ လက်ရှိအသုံးပြုနေသော connection နှင့် စစ်မှန်ကြောင်းအတည်ပြုထားသော API key တို့ကို ချက်ချင်း fencing လုပ်သည်။ အခြား key တစ်ခုက တူညီသော connection ကို ခွင့်ပြုထားလျှင်ပင် owner နှင့် generation ကို ထို key ဖြင့် ပြန်လည်အသုံးပြုခြင်း မအောင်မြင်ပါ။ မပြုပြင်ရသေးသော owner များကို သိမ်းဆည်းခြင်း၊ log မှတ်တမ်းတင်ခြင်း၊ request snapshot ထဲတွင် ထိန်းသိမ်းထားခြင်း သို့မဟုတ် upstream သို့ လွှဲပို့ခြင်း မပြုပါ။

ယာယီအရင်းအမြစ်ယှဉ်ပြိုင်မှု ဖြစ်ပေါ်ပါက HTTP `429` ကို `Retry-After` နှင့်အတူ အောက်ပါအတိုင်း ပြန်ပေးသည်-

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ဤ response သည် ပုံမှန်အကျုံးဝင်သောအစုမှာ ဗလာမဟုတ်ဘဲ လွတ်နေသော candidate အားလုံးကို အခြားသူပိုင် လက်ရှိအသုံးပြုနေသည့် lease များက ကိုင်ထားကြောင်းကိုသာ ဆိုလိုသည်။ ပံ့ပိုးမထားသော model/provider များ၊ policy မကိုက်ညီမှု၊ cooldown၊ quota၊ health နှင့် အခြားပုံမှန် eligibility failure များသည် ၎င်းတို့၏ ရှိပြီးသား OmniRoute response များကို ဆက်လက်ထိန်းသိမ်းထားသည်။

### `x-omniroute-compression`

Request တစ်ခုချင်းစီအတွက် compression plan ကို override လုပ်ခြင်းဖြစ်သည်။ ဦးစားပေးအဆင့် အမြင့်ဆုံးဖြစ်ပြီး routing-combo override၊ လက်ရှိအသုံးပြုနေသော profile၊ auto-trigger နှင့် panel ၏ မူလသတ်မှတ်ချက်တို့ထက် ဦးစားပေးသည်။ Value များ-

| Value         | သက်ရောက်မှု                                                                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | ဤ request အတွက် compression မလုပ်ပါ။                                                                                                                       |
| `default`     | Panel မှ ဆင်းသက်လာသော မူလ profile ဖြစ်သည်၊ လက်ရှိအသုံးပြုနေသော profile ကို လျစ်လျူရှုသည်။ Lossy engine များကို ပိတ်ထားသည်။                                 |
| `safe`        | Dedup နှင့် whitespace folding ကိုသာ ပြုလုပ်သည်။                                                                                                           |
| `allow-lossy` | Summary နှင့် style rewrite များအပါအဝင် ဤ request အတွက် operator plan ကို ဆက်လက်အသုံးပြုသည်။                                                               |
| `engine:<id>` | Enable လုပ်ထားပါက engine တစ်ခုတည်းကို အသုံးပြုသည်၊ ဥပမာ `engine:rtk`။ ထို engine အတွက် request တစ်ခုချင်းစီအလိုက် ကိုယ်တိုင်ရွေးချယ်အသုံးပြုခြင်း ဖြစ်သည်။ |
| `<combo>`     | အမည်သတ်မှတ်ထားသော combo တစ်ခုဖြစ်ပြီး ပထမဦးစွာ အမည်ဖြင့် စာလုံးအကြီးအသေးမခွဲဘဲ တိုက်ဆိုင်စစ်ဆေးပြီးနောက် id ဖြင့် တိုက်ဆိုင်စစ်ဆေးသည်။                     |

မှတ်ချက်များ-

- မသိသော value များကို လျစ်လျူရှုသည်၊ request ကို မည်သည့်အခါမျှ ငြင်းပယ်ခြင်းမရှိပါ။ Resolution သည် ပုံမှန် operator ဦးစားပေးအစီအစဉ်သို့ ဆက်လက်ကျသွားသည်။
- Combo များစွာသည် အမည်တူနေပါက တိကျသေချာစွာ တိုက်ဆိုင်စေရန် combo **id** ကို ပေးပို့ပါ။
- အမည်မှာ `off` သို့မဟုတ် `default` ဖြစ်သော combo ကို အမည်ဖြင့် ရွေးချယ်၍မရပါ၊ အကြောင်းမှာ အဆိုပါ keyword များကို ဦးစွာ အဓိပ္ပာယ်ကောက်ယူသောကြောင့်ဖြစ်သည်။ ထိုကဲ့သို့သော combo ကို ၎င်း၏ id ဖြင့် ရည်ညွှန်းပါ။
- Master compression switch သည် မဖြစ်မနေဖြတ်သန်းရသည့် gate ဖြစ်သည်။ Compression ကို တစ်စုံလုံးအတွက် disable လုပ်ထားပါက ဤ header ဖြင့် enable လုပ်၍မရပါ။

အသုံးချထားသော plan ကို response header တွင် အောက်ပါအတိုင်း ပြန်လည်ဖော်ပြသည်-

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ဤနေရာတွင် `<source>` သည် `request-header`၊ `routing-override`၊ `active-profile`၊ `auto-trigger`၊ `default` သို့မဟုတ် `off` တို့အနက် တစ်ခုဖြစ်သည်။

## Embedding များ

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ရရှိနိုင်သော provider များမှာ Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI တို့ဖြစ်သည်။

Catalog ID များသည် `provider/model` ပုံစံဖြစ်သည် (ဥပမာ- `jina-ai/jina-embeddings-v5-omni-small`)။ Registry တွင် ပါဝင်သော prefix မပါသည့် Jina model ID များ (ဥပမာ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ကိုလည်း ဖြေရှင်းအသုံးပြုနိုင်သည်။ Jina embed/rerank/classify/segment သည် dashboard ရှိ `jina-ai` အထောက်အထားများကို ဦးစွာအသုံးပြုသည်။ Dashboard key မရှိသည့်အခါမှသာ `JINA_AI_API_KEY` ကို အရန်အဖြစ် အသုံးပြုသည်။ `jina-reader` card သည် Reader / `r.jina.ai` အတွက်သာဖြစ်ပြီး (`POST /v1/web/fetch`) embeddings သို့မဟုတ် rerank ကို မည်သည့်အခါမျှ မပံ့ပိုးပါ။

Multimodal ပံ့ပိုးမှုရှိကြောင်း ဖော်ပြထားသည့် registry model များသည် provider နှင့် မသက်ဆိုင်သော ဖွဲ့စည်းပုံပါ item ၃၂ ခုအထိကိုလည်း လက်ခံသည်။
Media item အမျိုးအစားများမှာ `text`, `image`, `audio`, `video` နှင့် `document` တို့ဖြစ်သည်။ ၎င်းတို့၏ media `source`
သည် `{"type":"url","url":"https://..."}` သို့မဟုတ်
`{"type":"base64","data":"...","media_type":"..."}` ဖြစ်သည်။

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
နှင့် family alias `jina-ai/jina-embeddings-v5-omni` → omni-small) သည် Jina ၏ မူရင်း
EmbeddingsV5Request document များကိုလည်း လက်ခံပြီး `https://api.jina.ai/v1/embeddings` သို့ **မပြောင်းလဲဘဲ တိုက်ရိုက်ပေးပို့သည်**-

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

မူရင်း `{ image | audio | video | pdf }` တန်ဖိုးများသည် အများပြည်သူ အသုံးပြုနိုင်သော HTTPS URL၊ `data:` URI သို့မဟုတ် မူရင်း
base64 ဖြစ်နိုင်သည်။ OmniRoute သည် ထို object များကို string အဖြစ် မပြောင်းသကဲ့သို့ မူရင်း image URL များကိုလည်း ရယူခြင်းမပြုပါ — Jina က
အများပြည်သူ အသုံးပြုနိုင်သော media ကို ကိုယ်တိုင်ရယူသည်။ ထပ်ဆောင်း Jina field များ (`task`, `normalized`, `truncate`, `embedding_type`) ကို
တိုက်ရိုက်ပေးပို့သည်။ Text-only Jina SKU များသည် text မဟုတ်သော document များကို ဆက်လက်ငြင်းပယ်သည်။

လုံခြုံရေးနှင့် ပို့ဆောင်မှုဆိုင်ရာ ကန့်သတ်ချက်များ-

- အဝေးရှိ media URL များသည် အများပြည်သူ အသုံးပြုနိုင်သော HTTPS ဖြစ်ရမည်။ Canonical `{type,source:url}` item များကို
  server ဘက်တွင် ရယူပြီး (redirect ကို ပြန်လည်စစ်ဆေးခြင်း၊ timeout၊ အရွယ်အစားကန့်သတ်ချက်များ၊ public DNS၊ connection pinning)
  provider ကို မခေါ်ဆိုမီ inline အဖြစ် ထည့်သွင်းသည်။ Jina ၏ မူရင်း `{image:"https://..."}` item များကို တူညီသော public-HTTPS စစ်ဆေးမှု ပြုလုပ်ပြီးနောက်
  မပြောင်းလဲဘဲ ပေးပို့သည်။ Jina က URL ကို ရယူသည်။
- Inline base64 media ကို item တစ်ခုလျှင် decode လုပ်ပြီး 8 MiB အထိနှင့် request တစ်ခုလုံးတွင် decode လုပ်ပြီး 16 MiB အထိ ကန့်သတ်ထားသည်။

Provider အလိုက် ပြောင်းလဲခြင်း (canonical item များကို မပြောင်းလဲဘဲ မည်သည့်အခါမျှ ပေးပို့ခြင်းမပြုပါ)-

- Jina multimodal model များ- ထိပ်ဆုံးအဆင့် item တစ်ခုစီကို modality key ပါသော object တစ်ခု
  (`text` / `image` / `audio` / `video` / `pdf`) အဖြစ် ပြောင်းပြီး inline media အတွက် data URI များကို အသုံးပြုသည်။ ထိပ်ဆုံးအဆင့်
  item တစ်ခုလျှင် vector တစ်ခု ရရှိသည်။
- Gemini Embedding 2 family- ထိပ်ဆုံးအဆင့် array တစ်ခုကို `content.parts` (`text` သို့မဟုတ် `inline_data`) ပါသော မူရင်း
  `models/{model}:embedContent` request တစ်ခုအဖြစ် ပြောင်းသည်။
- llama.cpp (`llama-cpp/<model>`၊ local server က load လုပ်ထားသော မည်သည့် model မဆို)- canonical `text` item များကို
  ရိုးရိုး string များအဖြစ် ပြောင်းပြီး `image` / `audio` / `video` တစ်ခုစီကို
  `{"content": [part]}` object တစ်ခုစီအဖြစ် ပြောင်းသည်။ ထိုသို့ပြောင်းရာတွင် inline data နှင့်အတူ llama-server ၏ chat content part များ (`image_url`,
  format `wav` / `mp3` / `flac` ပါသော `input_audio`, `input_video`) ကို အသုံးပြုသည်။ ထိပ်ဆုံးအဆင့်
  item တစ်ခုလျှင် vector တစ်ခု ရရှိသည်။ Server ကို `--embedding --mmproj …` ဖြင့် run ရမည်။ Projector မရှိပါက
  server ကိုယ်တိုင်က media ကို ငြင်းပယ်သည်။ `document` ကို မပံ့ပိုးပါ။
- တိကျသော modality metadata မပါသည့် မသိသော/dynamic model များသည် ဖွဲ့စည်းပုံပါ input ကို HTTP 400 ဖြင့် ငြင်းပယ်သည်။

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

မပံ့ပိုးသော model/modality ပေါင်းစပ်မှုများတွင် item ကို အတင်းအကျပ်ပြောင်းလဲမည့်အစား HTTP 400 ကို ပြန်ပေးသည်။ ယခင် string/token request များရှိ input နှင့် မသက်ဆိုင်သော
extension field များကို မပြောင်းလဲဘဲ ဆက်လက်ပေးပို့သည်။

```bash
# Embedding model အားလုံးကို စာရင်းပြုစုရန်
GET /v1/embeddings
```

## ပုံဖန်တီးခြင်း

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",

```

ရရှိနိုင်သော provider များတွင် OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local), ComfyUI (local) တို့ ပါဝင်သည်။

`n` သည် `data[]` အတွင်း ပုံ `n` ပုံကို ပြန်ပေးသည်။ Upstream API က ခေါ်ဆိုမှုတစ်ခုလျှင် ပုံတစ်ပုံသာ ပြန်ပေးသော provider များ
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) အတွက် သီးခြား upstream ခေါ်ဆိုမှု `n` ခု ပြုလုပ်ပြီး တစ်ပြိုင်နက် လုပ်ဆောင်မှု အများဆုံး 4 ခု ရှိမည်။ ပုံသေ
`seed` ကို ခေါ်ဆိုမှုအညွှန်းအလိုက် တိုးပေးသည် (`seed`, `seed + 1`, …)၊ ထို့ကြောင့် ပုံများ ကွဲပြားသော်လည်း
ရလဒ်များကို ပြန်လည်ဖန်တီးနိုင်စွမ်း ရှိနေသည်။ `n` ကို အများဆုံး 10 အထိ ကန့်သတ်ထားသည်။ ခေါ်ဆိုမှုတစ်ခုခု မအောင်မြင်ပါက request
တစ်ခုလုံး မအောင်မြင်ပါ။ Fan-out format များ၏ စာရင်းမှာ
`open-sse/handlers/imageGeneration/fanOut.ts` အတွင်းရှိ `SINGLE_IMAGE_FANOUT_FORMATS` ဖြစ်သည်။

ZenMux သည် ရှိပြီးသား API-key connection ကို ပြန်လည်အသုံးပြုပြီး `zenmux/` သို့မဟုတ် `zm/` prefix များကို လက်ခံသည်-

- `zenmux/openai/gpt-image-2` သည် ZenMux ၏ OpenAI Images API ကို အသုံးပြုသည်။ Option များတွင် `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` နှင့် `response_format` တို့ ပါဝင်သည်။
- `zm/meta/muse-image-1.0` ကဲ့သို့သော အခြား publisher များသည် ZenMux ၏ Vertex AI `:predict`
  endpoint ကို အသုံးပြုသည်။ `n` ကို `sampleCount`၊ `aspect_ratio` ကို `aspectRatio`၊ `image_size`
  (`1K`, `2K`, `4K`) ကို `sampleImageSize` နှင့် ချိတ်ဆက်သတ်မှတ်သည်။ Pixel `size` သည် aspect ratio ကိုသာ ပေးပြီး
  pixel dimension အတိအကျကို အာမမခံပါ။ ပံ့ပိုးထားသော ratio၊ resolution နှင့် အရေအတွက်တို့သည် model အလိုက် ကွဲပြားသည်။
- `zm/inclusionai/ming-image-0.1-design` သည် ၎င်း၏ dimension များကို ကိုယ်တိုင် ရွေးချယ်သည်။ `size`,
  `aspect_ratio` နှင့် `image_size` တို့ကို ချန်လှပ်ပါ၊ တန်ဖိုးများ အတိအလင်း ထည့်သွင်းပါက HTTP 400 ကို ပြန်ပေးသည်။ PNG, JPEG နှင့် WebP
  တို့ကို `output_format` ဖြင့် တောင်းဆိုနိုင်သည်။

ဤ integration သည် စာသားမှ ပုံဖန်တီးခြင်းကို ပံ့ပိုးသော်လည်း reference-image တည်းဖြတ်ခြင်းကို မပံ့ပိုးပါ။ Vertex
output ကို `data[].b64_json` ပုံစံသို့ စံညှိပေးသည်။ `response_format: "url"` သည် upstream
HTTPS URL ကို ပြန်ပေးပြီး ပုံ byte များသာ ရရှိနိုင်ပါက base64 data URL ကို ပြန်ပေးသည်။ Output မရှိခြင်း သို့မဟုတ် စစ်ထုတ်ခံထားရသော output များသည်
အောင်မြင်မှုအလွတ်တစ်ခုအစား error တစ်ခုကို ပြန်ပေးသည်။ Model အသုံးပြုခွင့်သည် ZenMux account ပေါ် မူတည်သည်။
[ZenMux's Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) နှင့်
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) ကို ကြည့်ပါ။


## စာရွက်စာတမ်း OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` သည် `provider/model` prefix မှတစ်ဆင့် OCR provider ကို ရွေးချယ်သည်။ Provider မပါသော model id (ဥပမာ
`mistral-ocr-latest`) သည် ၎င်းအတွက် မှတ်ပုံတင်ထားသော provider သို့ ဖြေရှင်းသတ်မှတ်ပြီး `model` ကို ချန်လှပ်ထားပါက မူလသတ်မှတ်ချက်အဖြစ်
Mistral (`mistral-ocr-latest`) ကို အသုံးပြုသည်။ မှတ်ပုံတင်ထားသော provider များ (`open-sse/config/ocrRegistry.ts`)-

| Provider id                   | Model id             | `model` တန်ဖိုး                                                               | မှတ်ချက်များ                                                                                                                   |
| ----------------------------- | -------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (သို့မဟုတ် provider မပါသော `mistral-ocr-latest`) | Synchronous — upstream ခေါ်ဆိုမှုတစ်ခုတည်းမှ response ကို တိုက်ရိုက် ပြန်ပေးသည်။                                               |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                                   | Asynchronous upstream (`analyze` + poll) — အောက်တွင် ကြည့်ပါ။                                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                       | Vertex AI ၏ `openapi/chat/completions` partner endpoint မှတစ်ဆင့် synchronous လုပ်ဆောင်သည် — auth/URL အတွက် အောက်တွင် ကြည့်ပါ။ |

Provider သုံးခုလုံးသည် Mistral နှင့် ပုံစံတူသော body ဖြင့် response ပြန်ပေးသည်-

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence poll လုပ်ငန်းစဉ်

Azure Document Intelligence ၏ `analyze` API သည် asynchronous ဖြစ်သည်။ ကနဦး request သည် body အစား
`Operation-Location` header တစ်ခုကို ပြန်ပေးပြီး ရလဒ်အတွက် poll လုပ်ရသည်။ Handler
(`open-sse/handlers/ocr.ts`) သည် ထို URL ကို တစ်စက္ကန့်လျှင် တစ်ကြိမ်ဖြင့် အများဆုံး ကြိုးပမ်းမှု 30 အထိ poll လုပ်သည်။ `ok` မဟုတ်သော poll response သို့မဟုတ် `"failed"` status ရရှိပါက ချက်ချင်း မအောင်မြင်ကြောင်း သတ်မှတ်ပြီး (ဆက်လက်
poll မလုပ်ပါ)၊ သတ်မှတ်ထားသော ကြိုးပမ်းမှုအရေအတွက် ကုန်ဆုံးပြီးနောက် operation လည်ပတ်နေဆဲဖြစ်ပါက `504` ကို ပြန်ပေးသည်။ နောက်ဆုံး Azure response ကို
ခေါ်ဆိုသူထံ မပြန်ပေးမီ Mistral အသုံးပြုသည့် တူညီသော `pages`/`markdown` ပုံစံသို့
စံညှိပေးထားသောကြောင့် client code တွင် provider အလိုက် သီးခြားကိုင်တွယ်ရန် မလိုပါ။

### Vertex AI DeepSeek OCR auth နှင့် endpoint ဖြေရှင်းသတ်မှတ်ခြင်း

`vertex-deepseek-ocr` သည် chat/image traffic အတွက် OmniRoute က ပံ့ပိုးထားပြီးဖြစ်သော တူညီသည့် Vertex AI authentication
(`open-sse/executors/vertex.ts`) ကို ပြန်လည်အသုံးပြုသည်။ Connection ၏ API key သည်
Service Account JSON credential (JWT-bearer
flow မှတစ်ဆင့် သက်တမ်းတို OAuth access token တစ်ခုနှင့် လဲလှယ်သည်) သို့မဟုတ် အသင့်ထုတ်ပေးပြီးသား OAuth access token တစ်ခုဖြစ်ပြီး ထိုအတိုင်း အသုံးပြုသည်။ Upstream endpoint URL သည် Vertex ၏
ယေဘုယျ `openapi/chat/completions` partner endpoint ဖြစ်ပြီး connection ၏ project နှင့်
region တို့မှ တည်ဆောက်ထားသည်။ အတိအလင်း သတ်မှတ်ထားသော `providerSpecificData.project`/`providerSpecificData.region` ကို အမြဲ ဦးစားပေးသည်။
ထိုသို့ မသတ်မှတ်ထားပါက project ကို Service Account JSON ၏ `project_id` မှ ရယူပြီး region
ကို မူလသတ်မှတ်ချက်အဖြစ် `us-central1` သတ်မှတ်သည်။ ဖြေရှင်းသတ်မှတ်မှု နှစ်ခုလုံးကို `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) တွင် လုပ်ဆောင်ပြီး
`handleOcr` သို့ လွှဲပြောင်းမပို့မီ `src/app/api/v1/ocr/route.ts` က အသုံးပြုသည်။

### မော်ဒယ်စျေးနှုန်းများ (`pricing`)

OmniRoute က မော်ဒယ်၏စျေးနှုန်းကို သိရှိထားသည့်အခါ entry တစ်ခုတွင် `pricing` object ပါဝင်သည်။ စျေးနှုန်းသည် ကုန်ကျစရိတ်စာရင်းကိုင်ရာတွင် အသုံးပြုသည့် pricing table မှ ရရှိသည်- built-in မူလသတ်မှတ်ချက်များ၊ sync လုပ်ထားသောစျေးနှုန်းများနှင့် `/api/pricing` မှတစ်ဆင့် သတ်မှတ်ထားသော override များ ဖြစ်သည်။ ၎င်းတို့သည် စာရင်းစျေးနှုန်းများဖြစ်သောကြောင့် subscription provider များတွင်လည်း token တစ်ခုချင်းစီအလိုက် စျေးနှုန်းကို ပြသသည်။

```json
  "input_cache_write": "0.00000625",

  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Field များ                                                      | ယူနစ်                                | မှတ်ချက်များ                                                                                                                                                                            |
| --------------------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | token တစ်ခုလျှင် USD၊ decimal string | OpenRouter နှင့် ကိုက်ညီပြီး exponent notation ကို မည်သည့်အခါမျှ မသုံးပါ။ cache စျေးနှုန်းရှိသည့်အခါမှသာ cache field နှစ်ခု ပေါ်လာသည်။                                                  |
| `input`, `output`, `cached`, `cache_creation`                   | token 1M လျှင် USD၊ number           | အစောပိုင်း catalog version များမှ field များဖြစ်ပြီး လက်ရှိ client များအတွက် ဆက်လက်ထိန်းသိမ်းထားသည်။ pricing row တွင် ပါရှိသည့်အခါ `reasoning` နှင့် `long_context` တို့လည်း ပေါ်လာသည်။ |

- **Combo များ** သည် ၎င်းတို့၏ ပထမဆုံး မြင်နိုင်သော target ၏ စျေးနှုန်းကို ယူထားသည်။ Built-in `auto/*` combo များသည် request ပြုလုပ်ချိန်တွင် target တစ်ခုကို ရွေးချယ်သောကြောင့် ၎င်းတို့တွင် `pricing` မရှိပါ။
- **အခမဲ့မော်ဒယ်များ** သည် ၎င်းတို့၏စျေးနှုန်း သုညဖြစ်သည့်အခါ `"0"` (နှင့် `0`) ကို ပြသသည်။ pricing row မရှိသော မော်ဒယ်တစ်ခုကို catalog က အခမဲ့အဖြစ် သတ်မှတ်ထားလျှင် (`free: true`) သို့မဟုတ် built-in အခမဲ့မော်ဒယ် catalog တွင် စာရင်းသွင်းထားလျှင်လည်း `"0"` ကို ပြသသည်။
- **စျေးနှုန်းမသိရှိမှု-** entry တွင် `pricing` key မရှိပါ။
- **Credit ဖြင့် တိုင်းတာကောက်ခံသော provider များ** (ဥပမာ Kiro) သည် token တစ်ခုချင်းစီအစား request တစ်ခုချင်းစီအလိုက် ငွေတောင်းခံသည်။ ၎င်းတို့၏ entry များသည် ယခင်ကရှိခဲ့သော ဂဏန်းအမျိုးအစား per-1M field များကို ဆက်လက်ထိန်းသိမ်းထားပြီး token တစ်ခုချင်းစီအတွက် string field များ မပါဝင်ပါ။
- **Variant များ** (reasoning-effort id များ၊ no-thinking alias များ၊ discovery နှင့် gateway mirror များ) သည် ၎င်းတို့ route လုပ်ပေးသည့် မော်ဒယ်၏စျေးနှုန်းကို ကူးယူသည်။
- Field များတွင် အခြေခံနှုန်းထားများသာ ပါဝင်သည်။ Long-context tier များ (ဂဏန်းအမျိုးအစား `long_context` field) နှင့် service-tier multiplier များ (ဥပမာ Codex fast သို့မဟုတ် flex) သည် `prompt` သို့မဟုတ် `completion` ကို မပြောင်းလဲပါ။
- Anthropic ပုံစံ `x-api-key` နှင့် `anthropic-version` ပါဝင်သော request အပါအဝင် authentication ပုံစံတိုင်းအတွက် object သည် အတူတူပင်ဖြစ်သည် (response သည် `{ "object": "list",
"data": [...] }` အဖြစ် ဆက်ရှိနေသည်)။ အကောင်အထည်ဖော်ထားသည့်နေရာ- `src/app/api/v1/models/catalogPricing.ts`။

### မော်ဒယ် id prefix များ (`?prefix=`)

မော်ဒယ်အများစုကို **provider prefix** အောက်တွင် ကြေညာထားသည်။ မည်သည့် prefix ကို ရရှိမည်ကို `MODELS_CATALOG_PREFIX_MODE` feature flag က ထိန်းချုပ်ထားပြီး query parameter ဖြင့် **request တစ်ခုချင်းစီအလိုက်** override လုပ်နိုင်သည် — server တစ်ခုလုံး၏ setting ကို အခြားသူအားလုံးအတွက် မပြောင်းလဲဘဲ သန့်ရှင်းသောစာရင်းကို လိုချင်သည့် client အတွက် အသုံးဝင်သည်-

```bash
GET /v1/models?prefix=alias        # မော်ဒယ်တစ်ခုလျှင် id တစ်ခု — alias prefix အတို
GET /v1/models?prefix=dual         # ပုံစံနှစ်မျိုးလုံး (server မူလသတ်မှတ်ချက်)
GET /v1/models?prefix=canonical    # provider-id prefix အပြည့်အစုံသာ
```

| Mode        | ထုတ်ပေးသည့်အရာ                                              | မှတ်ချက်များ                                                                                                                                                                                                                     |
| ----------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **နှင့်** `claude/claude-sonnet-4-6` | **မူလသတ်မှတ်ချက်။** id နှစ်ခုလုံးသည် မော်ဒယ်တစ်ခုတည်းသို့ route လုပ်သည်။ ပုံစံတစ်ခုခုကို hardcode လုပ်ထားသော client config များ ဆက်လက်အလုပ်လုပ်နိုင်စေရန် ထိန်းသိမ်းထားသည်။ catalog အရွယ်အစားကို အကြမ်းဖျင်း နှစ်ဆတိုးစေသည်။     |
| `alias`     | `cc/claude-sonnet-4-6`                                      | မော်ဒယ်တစ်ခုလျှင် entry တစ်ခု။ သီးခြား alias မရှိသော provider များသည်လည်း ၎င်းတို့၏ entry ကို ထုတ်ပေးသဖြင့် မည်သည့်အရာမျှ မပျောက်ဆုံးပါ။                                                                                         |
| `canonical` | `claude/claude-sonnet-4-6`                                  | provider-id prefix အပြည့်အစုံအောက်တွင် မော်ဒယ်တစ်ခုလျှင် entry တစ်ခု။ သီးခြား alias မရှိသော provider များ (ဥပမာ `antigravity/…`, `agy/…`) သည်လည်း ၎င်းတို့၏ id တစ်ခုတည်းကို ဤနေရာတွင် ထုတ်ပေးသဖြင့် မည်သည့်အရာမျှ မပျောက်ဆုံးပါ။ |

`dual` mode mirror တစ်ခုကို query parameter မပါဘဲလည်း ခွဲခြားသိရှိနိုင်သည်- ၎င်းတွင် ပင်မ id ကို ညွှန်ပြသော `parent` field ပါဝင်သည်။

မော်ဒယ်ရွေးချယ်ကိရိယာကို ဖော်ပြသည့် client များသည် `?prefix=alias` ကို request လုပ်သင့်သည် — [OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md) ကလည်း ဤနည်းလမ်းကို အသုံးပြုသည်။

### ရှာဖွေဖော်ထုတ်မှု filter များ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` သည် ရွေးချယ်အသုံးပြုရသော discovery filter များကို လက်ခံသည်။ ၎င်းတို့တစ်ခုမျှ မပါရှိပါက response သည် မပြောင်းလဲပါ။ ၎င်းတို့သည် ခေါ်ဆိုသူ မြင်နိုင်ပြီးသား catalog ကို ကျဉ်းမြောင်းစေသည် (API key ခွင့်ပြုချက်များကို ဦးစွာ သက်ရောက်စေသည်)၊ ထို့နောက် OpenAI ပုံစံ `limit` / `after` paging မပြုလုပ်မီ အလုပ်လုပ်သည်-

```bash
GET /v1/models?capability=vision&capability=tool_calling   # စာရင်းတွင်ပါသော capability တိုင်း true ဖြစ်ရမည်
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # catalog `type`; ၎င်းမပါသော row များသည် `chat` ဖြစ်သည်
GET /v1/models?q=sonnet&limit=10                           # id သို့မဟုတ် name ပေါ်တွင် စာလုံးအကြီးအသေးမခွဲခြားဘဲ ကိုက်ညီမှုရှာသည်
```

| ပါရာမီတာ      | တန်ဖိုးများ                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | အနုတ်မဟုတ်သော ကိန်းပြည့်၊ `context_length` နှင့် နှိုင်းယှဉ်သည်                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | အက္ခရာ 1–200                                                                                        |

မသိရှိသောတန်ဖိုးတစ်ခု သို့မဟုတ် အနုတ်မဟုတ်သော ကိန်းပြည့်မဟုတ်သည့် `min_context` (ဥပမာ `1.5`) ကို ပေးပါက
HTTP `400` ကို ပြန်ပေးပြီး မက်ဆေ့ချ်တွင် အသုံးပြုနိုင်သော တန်ဖိုးများကို စာရင်းပြုစုပေးသည်။ အကောင်အထည်ဖော်ထားသည့်နေရာ-
`src/app/api/v1/models/catalogFilters.ts`။

### မော်ဒယ်အကျဉ်းစာရင်း (`POST /v1/models/query`)

`POST /v1/models/query` သည် တူညီသော catalog မှ တိုတောင်းပြီး အမြဲတစ်သမတ်တည်းဖြစ်သော စာရင်းတစ်ခုကို ပြန်ပေးပြီး၊
`GET /v1/models` နှင့် တူညီသော အထောက်အထားစစ်ဆေးမှုနှင့် key တစ်ခုချင်းအလိုက် မြင်နိုင်မှုကို အသုံးပြုသည်-

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Field တစ်ခုချင်းစီသည် ရွေးချယ်နိုင်သည်။ `capabilities` နှင့် `exclude` တို့သည် array သို့မဟုတ် ကော်မာဖြင့်ခွဲထားသော string ကို လက်ခံသည်။
`max_output` ကို `max_output_tokens` နှင့် နှိုင်းယှဉ်သည်။ ရလဒ်များကို ဦးစွာ `owned_by` ဖြင့်၊ ထို့နောက် `id` ဖြင့် စီစဉ်သည်။
`limit` ၏ ပုံသေတန်ဖိုးမှာ `20` ဖြစ်ပြီး `100` ထက်ပိုသောတန်ဖိုးများကို `100` အထိ ကန့်သတ်သည်။ မမှန်ကန်သော JSON၊
မသိရှိသော field သို့မဟုတ် မမှန်ကန်သောတန်ဖိုးတစ်ခုသည် HTTP `400` ကို ပြန်ပေးသည်။

### တစ်ခုချင်း သီးခြားဖျောက်ထားသော chat မော်ဒယ်များ

၎င်း၏ provider စာမျက်နှာတွင် **ဖျောက်ထားသည်** ဟု သတ်မှတ်ထားသော မော်ဒယ်တစ်ခုကို catalog မှ ဖယ်ထုတ်ထားပြီး
အတိအကျတောင်းဆိုသည့်အခါ HTTP `404` / `model_not_found` ဖြင့် ငြင်းပယ်သည်။ စစ်ဆေးမှုသည် provider alias များ၊
compatible-provider node prefix များနှင့် connection ပုံသေတန်ဖိုးများအပါအဝင် ဖြေရှင်းသတ်မှတ်ထားသော
provider နှင့် မော်ဒယ်ကို အသုံးပြုသည်။ combo တစ်ခုသည် ဖျောက်ထားသော target များကို ကျော်ပြီး မြင်နိုင်သော sibling ကို အသုံးပြုနိုင်သည်။
လုပ်ဆောင်နိုင်သော target မကျန်ရှိသည့်အခါ တူညီသော error code ကို ပြန်ပေးသည်။ ပြန်လည်ဖော်ပြခြင်းသည် နောက်လာမည့်
request တွင် သက်ရောက်သည်။ ပုံအတွက်သာဖြစ်သော visibility override များသည် ID တူညီသည့် chat မော်ဒယ်ကို မဖျောက်ပါ။

ဤမော်ဒယ်တစ်ခုချင်းစီ၏ ဆက်တင်သည် catalog တွင် ဖော်ပြခြင်းနှင့် auto-routing candidate များကို စစ်ထုတ်သော်လည်း
တိကျစွာ dispatch လုပ်ခြင်းကို ဆက်လက်ထိန်းသိမ်းထားသည့်
[မော်ဒယ်ဖော်ပြမှု allow/deny စာရင်းများ](../routing/MODEL_EXPOSURE_LIST.md) နှင့် သီးခြားဖြစ်သည်။
API key မော်ဒယ်ခွင့်ပြုချက်များသည်လည်း သီးခြားစီ ဆက်လက်သက်ရောက်သည်။ ပုံသေ catalog prefix mode သည် `dual` အဖြစ် ဆက်လက်ရှိသည်။

### Thinking မပါသော မော်ဒယ် variant များ

Thinking ကို ပံ့ပိုးနိုင်သည့် Claude မော်ဒယ်များအတွက် `/v1/models` သည် ID ကို `claude-3-omniroute-no-thinking/` ဖြင့် ရှေ့ဆက်ထားသော **thinking မပါသည့်** variant တစ်ခုကိုလည်း ဖော်ပြသည်-

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

ဤ ID ကို ရွေးချယ်ခြင်း (ဥပမာ `thinking` block တစ်ခုကို အမြဲတမ်း ပူးတွဲပေးသည့် Claude Code config တွင်) သည် reasoning ကို ပိတ်ထားလျက် အစစ်အမှန် `<provider>/<model>` သို့ ပြန်လည်ဖြေရှင်းသတ်မှတ်ပေးသည် — `/v1/messages` path တွင် `thinking:{type:"disabled"}` ကို အသုံးပြုသည် သို့မဟုတ် `/v1/chat/completions` path တွင် `reasoning`/`reasoning_effort` field များကို ဖယ်ရှားသည်။ ဤ variant ကို thinking ပံ့ပိုးနိုင်ပြီး `disabled` ကိုလည်း လိုက်နာသည့် Claude-family မော်ဒယ်များအတွက်သာ စာရင်းပြုစုသည် (**နှင့်** ကို ဆိုလိုသည်) (ထို့ကြောင့် ဥပမာ `disabled` ကို ငြင်းပယ်သော adaptive-only မော်ဒယ်များကို ဖယ်ထုတ်ထားသည်)။ Operator များသည် မော်ဒယ်တစ်ခုချင်းစီအတွက် variant ကို `ModelSpec.noThinkingAlias` မှတစ်ဆင့် အတင်းဖွင့် သို့မဟုတ် ပိတ်နိုင်သည်။

## ElevenLabs အသံထုတ်လုပ်ခြင်း

သင်၏ ElevenLabs API key ဖြင့် OmniRoute တွင် `elevenlabs` provider connection တစ်ခုကို configure လုပ်ပါ။ Client များသည် ၎င်းတို့၏ **OmniRoute** key (`Authorization: Bearer $OMNIROUTE_API_KEY`) ဖြင့် authentication လုပ်ပြီး gateway က သိမ်းဆည်းထားသော provider key ကို `xi-api-key` အဖြစ် ပေးပို့သည်။ ElevenLabs key ကို gateway bearer token အဖြစ် မည်သည့်အခါမျှ မပို့ပါနှင့်။

| Method | Path                        | တုံ့ပြန်မှု                                   | API key endpoint အမျိုးအစား |
| ------ | --------------------------- | --------------------------------------------- | --------------------------- |
| POST   | `/v1/sound-generation`      | မူရင်း audio byte များ                        | `elevenlabs`                |
| POST   | `/v1/music`                 | မူရင်း audio byte များ                        | `music`                     |
| POST   | `/v1/music/stream`          | Streaming audio byte များ                     | `music`                     |
| POST   | `/v1/music/detailed`        | မူရင်း multipart audio နှင့် composition plan | `music`                     |
| POST   | `/v1/music/detailed/stream` | မူရင်း SSE metadata နှင့် audio chunk များ    | `music`                     |
| POST   | `/v1/music/plan`            | JSON composition plan                         | `music`                     |

ဤ endpoint များသည် ရှိပြီးသား `/v1/audio/speech`၊ `/v1/audio/transcriptions`၊ `/v1/voices`၊ `/v1/text-to-speech/{voiceId}` နှင့် `/v1/speech-to-text` route များကို ဖြည့်စွက်ပေးသည်။ `output_format` နှင့် `enable_logging` ကဲ့သို့သော မူရင်း JSON field များနှင့် query parameter များကို မပြောင်းလဲဘဲ ထိန်းသိမ်းထားသည်။ `/v1/music/detailed` တုံ့ပြန်မှုများတွင် ၎င်းတို့၏ multipart boundary များကို ဆက်လက်ထိန်းသိမ်းထားသောကြောင့် multipart အဖြစ် parse လုပ်ပါ။ `/v1/music/detailed/stream` သည် composition metadata နှင့် base64 audio chunk များပါဝင်သော SSE event များဖြင့် `text/event-stream` ကို ပြန်ပေးသည်။ Route ခြောက်ခုစလုံးသည် CORS preflight ကို ပံ့ပိုးသည်။

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# တိုတောင်းသော sound effect တစ်ခု။ ကြာချိန်- 0.5 မှ 30 စက္ကန့်။
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# တေးဂီတကြာချိန်ကို millisecond ဖြင့် ဖော်ပြသည်- 3000 မှ 600000။
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Audio ကို တစ်စိတ်တစ်ပိုင်းစီ ပေးပို့ရန် တူညီသော JSON body ဖြင့် `/v1/music/stream` ကို အသုံးပြုပါ။ Composition သည် `prompt` သို့မဟုတ် `composition_plan` နှစ်ခုအနက် တစ်ခုတည်းကိုသာ လက်ခံသည်။ `/v1/music/plan` သည် `prompt` လိုအပ်ပြီး `source_composition_plan` ကို ရွေးချယ်နိုင်သော field အဖြစ် လက်ခံသည်။ မူရင်း schema များသည် အပို provider field များကို ထိန်းသိမ်းထားသောကြောင့် composition-plan version များနှင့် fine-tuning option များသည် ElevenLabs သို့ ရောက်ရှိသည်။

ပေါင်းစည်းထားသော `/v1/music/generations` endpoint သည် `elevenlabs/music_v1`၊ `elevenlabs/music_v2` နှင့် `elevenlabs/music_v2_5` တို့ကိုလည်း လက်ခံသည်။ အသုံးပြုနိုင်သော ElevenLabs connection တစ်ခုရှိပါက ဤ model များကို music catalog တွင် ဖော်ပြပေးသည်။ ဤ endpoint သည် `{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ကို ပြန်ပေးသည်။ ၎င်း၏ `duration` field သည် စက္ကန့်ယူနစ်ဖြစ်ပြီး `music_length_ms` သို့ mapping လုပ်သည်။ `music_length_ms` ကို အတိအလင်း သတ်မှတ်ထားပါက ၎င်းကို ဦးစားပေးသည်။ `instrumental` သည် `force_instrumental` သို့ mapping လုပ်ပြီး မူရင်း field ကို ဦးစားပေးသည်။ Streaming အတွက် မူရင်း streaming endpoint များကို အသုံးပြုပြီး composition plan တစ်ခုတည်းဖြင့် ဆောင်ရွက်သော request များအတွက် မူရင်း composition endpoint ကို အသုံးပြုပါ။

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Upstream call တစ်ခုမပြုလုပ်မီ endpoint၊ model၊ budget နှင့် connection ကန့်သတ်ချက်များကို သက်ရောက်စေသည်။ မူရင်း route များသည် plan ကန့်သတ်ချက်အတွက် `402` နှင့် quota ကန့်သတ်ချက်အတွက် `429` အပါအဝင် upstream status code များနှင့် error body များကို မပြောင်းလဲဘဲ ပြန်ပေးသည်။ ရှိပါက `character-cost`၊ `song-id`၊ `request-id` နှင့် `retry-after` header များကို ထိန်းသိမ်းထားသည်။ အခမဲ့ credit လက်ကျန်ရှိခြင်းသည် music model၊ output format သို့မဟုတ် API feature အားလုံးကို အသုံးပြုခွင့်ရမည်ဟု အာမမခံပါ။ Request တစ်ခုချင်းစီအတွက် အသုံးပြုခွင့်ကို ElevenLabs က ဆုံးဖြတ်သည်။ ပေါင်းစည်းထားသော endpoint သည် OmniRoute ၏ normalized error envelope အတွင်း error status code များကို ထိန်းသိမ်းထားသည်။

Upstream contract များ- [sound effect များ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)၊ [တေးဂီတဖွဲ့စည်းမှု](https://elevenlabs.io/docs/api-reference/music/compose) နှင့် [streaming တေးဂီတအသေးစိတ်များ](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)။

`Authorization: Bearer ...` ကို ထည့်သွင်း၍မရသော client များအတွက် OmniRoute သည် query-string လိုက်ဖက်ညီမှု (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) သို့မဟုတ် အောက်တွင် မှတ်တမ်းတင်ထားသော သီးသန့် `/api/v1/vscode/{token}/...` endpoint များမှတစ်ဆင့် URL ထဲရှိ API key များကိုလည်း လက်ခံသည်။

```bash
# Rerank (cloud registry provider သို့မဟုတ် "<prefix>/<model>" ပုံစံ OpenAI-compatible provider node)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina classify (Foundation API အထောက်အထားများ)

POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS အတွက် ဘာသာစကားနှင့် voice တစ်ခု လိုအပ်သည်- `language` သည် မူလတန်ဖိုးအဖြစ် "en" ဖြစ်သည်၊ မပါရှိသော
# voice သို့မဟုတ် OpenAI ၏ မူရင်း voice အမည် (alloy, nova, …) ကို "Adrian" အဖြစ် ပြောင်းလဲသည်

POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Rerank provider node များ:** `POST /v1/rerank` သည် `<node-prefix>/<model>` အဖြစ် လိပ်စာသတ်မှတ်ထားသည့် OpenAI နှင့် ကိုက်ညီသော provider node များ
> (oMLX, vLLM, Infinity, gateway နောက်ကွယ်ရှိ TEI၊ …) သို့လည်း route လုပ်ပေးသည်။ Loopback
> node များ (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ကို အမြဲတမ်း အသုံးပြုခွင့်ရှိပြီး၊ operator က
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` တွင် စာရင်းသွင်းထားသည့် hostname များကိုလည်း အသုံးပြုခွင့်ရှိသည် (ဥပမာ
> `http://reranker:8080/v1` ကဲ့သို့သော Docker/Compose service name၊ ၎င်းတို့ကို `HTTP(S)_PROXY` သို့မဟုတ်
> connection တစ်ခု၏ pinned proxy မှတစ်ဆင့် မပို့ဘဲ တိုက်ရိုက်ခေါ်ဆိုသည်)။ အခြား
> host တစ်ခုခုပေါ်ရှိ node များ — LAN စက်တစ်လုံး သို့မဟုတ် Tailscale peer — ကို operator က
> `RERANK_REMOTE_PROVIDER_NODES` feature flag ကို ဖွင့်ထားပြီး **ထို့အပြင်** node ၏ base URL သည် provider
> outbound URL policy (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) ကို ဖြတ်သန်းနိုင်မှသာ အသုံးပြုခွင့်ရှိသည်။
> memory engine ၏ rerank အဆင့်သည် ဤ route ကို
> loopback မှတစ်ဆင့် ခေါ်ဆိုသောကြောင့် Memory settings ရှိ `rerankProviderModel` ကိုလည်း တူညီသော စည်းမျဉ်းက ထိန်းချုပ်သည်။
>
> **Local server ပုံစံများ:** node ကို `<base>/v1/rerank` တွင် ခေါ်ဆိုပြီး 404 ဖြစ်ပါက `<base>/rerank`
> (Infinity, TEI) တွင် ခေါ်ဆိုသည်။ Upstream body တွင် Cohere/OpenAI စာလုံးပေါင်း (`documents`,
> `return_documents`) နှင့် TEI စာလုံးပေါင်း (`texts`, `return_text`) နှစ်မျိုးစလုံး ပါဝင်ပြီး upstream response ကို
> Cohere envelope ပုံစံသို့ စံပြုထားသည်။ TEI ၏ အပြင်ဘက် wrapper မပါသော `[{index, score, text}]`၊ ပါးလွှာသော gateway များမှ `{results: [{index, score}]}`၊
> နှင့် Voyage ပုံစံ `{data: [...]}` တို့အားလုံးကို client ထံသို့
> `{results: [{index, relevance_score, document?}]}` အဖြစ် ပြန်ပို့ပြီး score အလိုက် စီထားကာ `top_n` ဖြင့် အများဆုံးအရေအတွက် ကန့်သတ်ထားသည်။

> **Provider-node ရှာဖွေဖော်ထုတ်ခြင်း:** OpenAI နှင့် ကိုက်ညီသော provider node တစ်ခုပေါ်ရှိ model များသည် node prefix အောက်ရှိ `GET /v1/models`
> တွင် ပေါ်လာသည်။ Endpoint metadata မပါသည့် row များ (local `/v1/models` listing များတွင် ဖြစ်လေ့ရှိသည်)
> သည် node ၏ `apiType` ကို ဆက်ခံသောကြောင့် `embeddings` node ၏ model များမှာ `type: "embedding"` ဖြစ်ပြီး
> `rerank` node ၏ model များမှာ chat အဖြစ် default သတ်မှတ်ခံရမည့်အစား `type: "rerank"` ဖြစ်သည်။ Sync လုပ်ထားသော သို့မဟုတ် ကိုယ်တိုင်ထည့်ထားသော row ပေါ်ရှိ
> တိကျစွာ သတ်မှတ်ထားသည့် `supportedEndpoints` သည် ဦးစားပေးအဖြစ် ဆက်လက်သက်ရောက်သည်။

### သီးသန့် Provider Route များ

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

Provider prefix မရှိပါက အလိုအလျောက် ထည့်ပေးသည်။ ကိုက်ညီမှုမရှိသော model များအတွက် `400` ကို ပြန်ပေးသည်။

## Files API

အစုလိုက် ထည့်သွင်းမှု/ထုတ်ပေးမှုနှင့် ဖိုင်ရည်ရွယ်ချက်အလိုက် အပ်လုဒ်တင်မှုများအတွက် OpenAI နှင့် ကိုက်ညီသော ဖိုင် endpoint ဖြစ်သည်။

| နည်းလမ်း | လမ်းကြောင်း              | ဖော်ပြချက်                                                                                                                     |
| -------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| POST     | `/v1/files`              | ဖိုင်တစ်ခု အပ်လုဒ်တင်ရန် (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — အများဆုံး 512 MiB |
| GET      | `/v1/files`              | အထောက်အထားစစ်ဆေးပြီးသော API key အတွက် ဖိုင်များကို စာရင်းပြုစုရန်                                                              |
| GET      | `/v1/files/[id]`         | ဖိုင်တစ်ခု၏ metadata ကို ရယူရန်                                                                                                |
| DELETE   | `/v1/files/[id]`         | ဖိုင်တစ်ခုကို ဖျက်ရန်                                                                                                          |
| GET      | `/v1/files/[id]/content` | မူရင်းဖိုင် body ကို stream ဖြင့် ပြန်ပို့ရန်                                                                                  |

**အထောက်အထားစစ်ဆေးခြင်း:** Bearer API key — ဖိုင်များကို `getApiKeyRequestScope` မှတစ်ဆင့် API key တစ်ခုချင်းစီအလိုက် နယ်ပယ်ကန့်သတ်ထားသည်။ Key တစ်ခုသည်
၎င်း၏ကိုယ်ပိုင်ဖိုင်များကိုသာ ကြည့်ရှု၊ ဒေါင်းလုဒ်လုပ်ပြီး ဖျက်နိုင်သည်။ Key မရှိသော dashboard session သည်
instance တစ်ခုလုံးကို ဖတ်ရှုနိုင်သည်။ ပိုင်ရှင်မရှိသော ဖိုင်တစ်ခု (anonymous သို့မဟုတ် dashboard-session upload) ကို session မဟုတ်သော
ခေါ်ဆိုသူအားလုံးအတွက် အသုံးပြုခွင့် ငြင်းပယ်သည်။ `GET /v1/files` သည် anonymous ခေါ်ဆိုသူကို — ထို့အပြင် ဖြေရှင်းအတည်ပြု၍မရသော တင်ပြထားသည့် key ကိုပါ —
`REQUIRE_API_KEY=false` ဖြစ်နေလျှင်ပင် tenant အားလုံး၏
ဖိုင်များကို စာရင်းမပြဘဲ `401` ဖြင့် ငြင်းပယ်သည် (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)။

## Batches API

OpenAI နှင့် ကိုက်ညီသော အစုလိုက်လုပ်ဆောင်ခြင်း ဖြစ်သည်။

| နည်းလမ်း | လမ်းကြောင်း               | ဖော်ပြချက်                                                                                                           |
| -------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| POST     | `/v1/batches`             | Batch ဖန်တီးရန် — body ကို `v1BatchCreateSchema` ဖြင့် အတည်ပြုသည် (`input_file_id`, `endpoint`, `completion_window`) |
| GET      | `/v1/batches`             | Batch များကို စာရင်းပြုစုရန်                                                                                         |
| GET      | `/v1/batches/[id]`        | Batch အခြေအနေ + `request_counts` ကို ရယူရန်                                                                          |
| DELETE   | `/v1/batches/[id]`        | ပြီးဆုံးသော/မအောင်မြင်သော batch ကို ဖျက်ရန်                                                                          |
| POST     | `/v1/batches/[id]/cancel` | လုပ်ဆောင်နေဆဲ batch ကို ပယ်ဖျက်ရန်                                                                                   |

**အထောက်အထားစစ်ဆေးခြင်း:** Bearer API key။ Batch များကို ဖိုင်များနှင့်တူညီသော နည်းလမ်းသုံးမျိုးပါ စည်းမျဉ်းအောက်တွင် API key တစ်ခုချင်းစီအလိုက် နယ်ပယ်ကန့်သတ်ထားသည်-
ကိုယ်ပိုင် key သာ အသုံးပြုနိုင်ခြင်း၊ dashboard session က instance တစ်ခုလုံးကို အသုံးပြုနိုင်ခြင်း၊ ပိုင်ရှင် null ဖြစ်သော record များကို session မဟုတ်သည့်
ခေါ်ဆိုသူအားလုံးအတွက် ငြင်းပယ်ခြင်းတို့ ဖြစ်သည် (ရယူခြင်း၊ ဖျက်ခြင်း၊ ပယ်ဖျက်ခြင်းနှင့် ဖန်တီးချိန်ရှိ `input_file_id` စစ်ဆေးမှု)။
`GET /v1/batches` သည် `REQUIRE_API_KEY=false` ဖြစ်နေလျှင်ပင် anonymous ခေါ်ဆိုသူကို `401` ဖြင့် ငြင်းပယ်သည်။

Web/search ပံ့ပိုးပေးသူ abstraction (Tavily၊ Brave၊ Exa၊ Serper စသည်ဖြင့်)။

| နည်းလမ်း | မဂ်                    | ဖော်ပြချက်                                                                                              |
| -------- | ---------------------- | ------------------------------------------------------------------------------------------------------- |
| GET      | `/v1/search`           | ပြင်ဆင်သတ်မှတ်ထားသော ရှာဖွေရေးဝန်ဆောင်မှုပေးသူများ + စွမ်းရည်များကို စာရင်းပြုစုပါ။                     |
| POST     | `/v1/search`           | `v1SearchSchema` မှ အတည်ပြုထားသော ရှာဖွေမှု query — body ကိုဖွင့်ပါ၊ caching/coalescing ကို ပံ့ပိုးသည်။ |
| GET      | `/v1/search/analytics` | ဝန်ဆောင်မှုပေးသူတိုင်း hit/latency/cache ကိန်းဂဏန်းများ                                                 |

**အထောက်အထား-** ထမ်းသူ API သော့ (`extractApiKey` + `isValidApiKey`)။ ရှာဖွေမှုမူဝါဒကို `enforceApiKeyPolicy` မှတစ်ဆင့် ပြဋ္ဌာန်းထားသည်။

### Exa နှင့် Tavily `provider_options`

Exa နှင့် Tavily တို့သည် namespaced bag တစ်ခုမှ ပံ့ပိုးပေးသူ-သတ်သတ်မှတ်မှတ်အကွက်များကို ဖတ်သည်- `provider_options.exa` (သို့မဟုတ် `provider_options["exa-search"]`) နှင့် `provider_options.tavily` (သို့မဟုတ် `provider_options["tavily-search"]`) ။ အောက်ပါသော့များကိုသာ ထပ်ဆင့်ပို့ပါသည်။ တစ်ခုစီကို `open-sse/handlers/search/providerOptionsPassthrough.ts` တွင် ၎င်း၏ကိုယ်ပိုင် Zod schema နှင့် စစ်ဆေးပြီး အမျိုးအစားမှားနေသော သော့တစ်ခု ပြုတ်ကျသွားသည်။ auth၊ base URL၊ `stream` နှင့် `outputSchema` အပါအဝင် အခြားသော့များကို လျစ်လျူရှုထားသည်။ အခြားပံ့ပိုးပေးသူများ (`cx`, `depth`, ... ) သုံးသော flat keys များသည် ယခင်အတိုင်း အလုပ်လုပ်ပါသည်။

| ပံ့ပိုးပေးသူ | ထိပ်တန်းအဆင့်နယ်ပယ်များ                                                                                                                                                                                                                                                                                                                                                   | သိုက်                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa          | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ပြားချပ်ချပ် primitives), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` မူရင်း `{ text: true, highlights: true }` တွင် ပေါင်းစပ်ထားသည်။ |
| ဗီလီ         | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                             |

ယေဘုယျနယ်ပယ်များသည် အမြဲတမ်းအနိုင်ရသည်- `query`၊ `max_results`၊ `filters` (ဒိုမိန်းများ), `country` နှင့် `search_type` မှ ဆင်းသက်လာသော အကြောင်းအရာ။ Exa တွင် `search_type: "news"` `category: "news"` ထိန်းသိမ်းထားသည်။ Tavily သည် `search_type: "finance"` (`topic: "finance"`) ကိုလည်း လက်ခံသည်။

Firecrawl ရှာဖွေမှုကုန်ကျစရိတ်သည် ဘလော့ဂ်တစ်ခုလျှင် $0.002 (ခရက်ဒစ် 2 ခု) နှင့် ခေါ်ဆိုမှုတစ်ခုလျှင် အနည်းဆုံး ဘလောက်တစ်ခု ( [Firecrawl billing](https://docs.firecrawl.dev/billing) ): 11 ရလဒ်များသည် $0.004 ကုန်ကျသည်။

ယေဘူယျ `time_range` ယခုအခါ ဝန်ဆောင်မှုပေးသူ နှစ်ခုစလုံးသို့ ရောက်ရှိသွားသည်- Exa သည် `startPublishedDate` (ISO timestamp) နှင့် Tavily သည် `start_date` (`YYYY-MM-DD`) ရရှိသည်။ `provider_options` တွင် ပြတ်သားသောရက်စွဲသည် မြေပုံရေးဆွဲထားသော ရက်စွဲကို အစားထိုးသည်။

Exa ရလဒ်များသည် `id`, `highlight_scores`, `summary`, `subpages`, `entities` နှင့် `extras` ကို `provider_raw` တွင် ထားရှိသည်။ Tavily ရလဒ်များသည် `images` နှင့် `favicon` ကို ထိန်းထားသည်။

Linkup ရှာဖွေမှုကုန်ကျစရိတ်သည် `depth` `fast` နှင့် `standard` အတွက် $0.005 နှင့် `deep` အတွက် $0.05 ( [Linkup pricing](https://docs.linkup.so/pages/documentation/development/pricing) ) ၊ `depth` မှ `provider_options` သို့မဟုတ် ချိတ်ဆက်မှု၏ဆက်တင်များတွင်ဖြစ်စေ မှတ်တမ်းတင်ထားသည်။

Exa `type: "lite"` (Exa 3.0) သည် သေးငယ်သော နယ်ပယ်အစုံကို လက်ခံပြီး အခြားနယ်ပယ်တစ်ခုခုကို သတ်မှတ်သည့်အခါ တောင်းဆိုချက်တစ်ခုလုံးကို ငြင်းပယ်သည်။ Lite၊ `additionalQueries`၊ `systemPrompt` နှင့် `contents` ကီးတိုင်းကို ဖုန်းခေါ်ဆိုမှုမတိုင်မီ `text` နှင့် `highlights` မှလွဲ၍ ကျန်သည်။ ကန့်ကွက်ထားသော `subpages`၊ `subpageTarget`၊ `highlights.numSentences` နှင့် `highlights.highlightsPerUrl` တို့ကို ထပ်ဆင့်မပို့တော့ပါ။

ကုန်ကျစရိတ်စာရင်းအင်းသည် Exa ၏ကိုယ်ပိုင်စျေးနှုန်းဖြင့်လိုက်နာသော Exa မှလွဲ၍ `costPerQuery`, `auto` (နှင့် အမွေအနှစ် `fast`) သို့မဟုတ် `lite` (နှင့် အမွေအနှစ် `instant`) အတွက် 10 ရလဒ်များကို လွှမ်းခြုံပေးသည့် Exa မှလွဲ၍ နောက်ထပ်ရလဒ်တစ်ခုစီအတွက် $0.001; `contents.summary` သတ်မှတ်လိုက်သောအခါ ရလဒ်တစ်ခုလျှင် $0.001။ Tavily ကို `search_depth` `basic`၊ `fast` နှင့် `ultra-fast` အတွက် 1 ခရက်ဒစ် ($0.008) နှင့် `advanced` ( [Tavily API ခရက်ဒစ်](https://docs.tavily.com/documentation/api-credits) ) အတွက် ခရက်ဒစ် 2 ခု ($0.016) ဖြင့် မှတ်တမ်းတင်ထားသည်။ Tavily အဆင့်မြှင့်တင်ထားသော `auto_parameters: true` ဖြင့်ခေါ်ဆိုမှုကို 1 ခရက်ဒစ်တွင် မှတ်တမ်းတင်ထားဆဲဖြစ်သည်။

## Web Fetch API

စီစဉ်သတ်မှတ်ထားသည့် web-fetch provider (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) မှတစ်ဆင့် URL တစ်ခုမှ အကြောင်းအရာကို ထုတ်ယူပါ။

Parallel Extract (`parallel-search`, Parallel Search နှင့် API key တူညီသည်) သည် Markdown
ကိုသာ ပြန်ပေးသည် — အခြားမည်သည့် `format` မဆို `400` ဖြစ်မည် — ထို့ပြင် အကြောင်းအရာကို စာလုံးရေ 100,000 အထိ ကန့်သတ်ထားသည်။ ပစ်မှတ်စာမျက်နှာကိုယ်တိုင်ကို
ထုတ်ယူ၍မရသည့်အခါ upstream က ၎င်းကို HTTP 200 အတွင်း ထည့်သွင်းဖော်ပြသည်၊
OmniRoute ကမူ ၎င်းကို ပုံသေမက်ဆေ့ချ်နှင့်အတူ `422` အဖြစ် ဖော်ပြသည်။

| နည်းလမ်း | လမ်းကြောင်း     | ဖော်ပြချက်                                                                  |
| -------- | --------------- | --------------------------------------------------------------------------- |
| POST     | `/v1/web/fetch` | URL တစ်ခုကို ရယူ/ခြစ်ယူခြင်း — body ကို `v1WebFetchSchema` ဖြင့် အတည်ပြုသည် |

**အထောက်အထားစိစစ်ခြင်း:** Bearer API key (`extractApiKey` + `isValidApiKey`)။ မူဝါဒကို `enforceApiKeyPolicy` မှတစ်ဆင့် အကောင်အထည်ဖော်သည်။

**Quota ကို ထည့်သွင်းစဉ်းစားသည့် fallback (#8297):** တိကျသော `provider` ကို မပေးထားသည့်အခါ pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ကို ပုံသေ
ဦးစားပေးအစီအစဉ် (fill-first) အတိုင်း
တစ်ခုပြီးတစ်ခု စမ်းသပ်သည် — rate limit သို့ ရောက်နေသော်လည်း စီစဉ်သတ်မှတ်ထားသည့် provider ကို
request အား ချက်ချင်းရပ်တန့်စေမည့်အစား ကျော်သွားပြီး၊ ပြန်လည်ကြိုးစားနိုင်သော/quota ဆိုင်ရာ upstream ချို့ယွင်းမှု
(HTTP 429 အမြဲတမ်း၊ Firecrawl/Tavily/TinyFish တို့၏ quota ပုံစံ free tier များအတွက် 402/403 —
Jina Reader အတွက် မဟုတ်သည့်အပြင် ရိုးရိုး 400 bad request အတွက်လည်း လုံးဝမဟုတ်) ဖြစ်ပါက request လုပ်နေစဉ်တွင်
မစမ်းသပ်ရသေးဘဲ အထောက်အထားရှိသည့် နောက် provider သို့ ဆက်လက်လုပ်ဆောင်သည်။ Pool အတွင်းရှိ provider အားလုံး
ကုန်ဆုံးသွားသည့်အခါ endpoint သည် ယခင် generic `400` အစား `429` တစ်ခုတည်းကို
(`Retry-After` header နှင့်အတူ) ပြန်ပေးသည်။ တိကျသော `provider` ကို
တောင်းဆိုထားသည့်အခါ အသိမပေးဘဲ fallback လုပ်ခြင်း **မရှိပါ** — rate limit သို့ ရောက်နေသော သို့မဟုတ် ချို့ယွင်းနေသော တိကျသည့်
provider သည် ၎င်း၏ကိုယ်ပိုင် error ကို ဖော်ပြသည် (rate limit သို့ ရောက်နေပါက `429`၊ သို့မဟုတ်ပါက upstream
status)။

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake တစ်ခုကို အတည်ပြုပြီး wire protocol နမူနာမက်ဆေ့ချ်များ (`request`, `cancel`) ကို ပြန်ပေးသည်။ အမှန်တကယ် WS frame များကို Next.js route table ပြင်ပရှိ ထည့်သွင်းပေးထားသော WS server က ကိုင်တွယ်သည်။

**အထောက်အထားစိစစ်ခြင်း:** Handshake ပြုလုပ်စဉ် Bearer API key။

### WebSocket မှတစ်ဆင့် Responses API (codex သီးသန့်)

```bash
# HTTP API နှင့် host:port တူညီသည် (မူလတန်ဖိုး 20128)၊ connection ကို upgrade လုပ်ပါ-
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (သို့မဟုတ်- -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# ပထမ frame သည် response.create ဖြစ်ရမည်-
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy ကို **`codex` နှင့်သာ သီးသန့်** (ChatGPT
backend) ချိတ်ဆက်ထားသည်။ ၎င်းသည် API/dashboard နှင့် port တူညီသော `/v1/responses`,
`/responses` နှင့် `/api/v1/responses` လမ်းကြောင်းများတွင် စောင့်ကြည့်သည်။ ပထမဆုံး `response.create` frame တွင်
၎င်းသည် အတွင်းပိုင်း `codex-responses-ws` bridge မှတစ်ဆင့် အထောက်အထားစိစစ်ခြင်းနှင့် ပြင်ဆင်ခြင်းကို လုပ်ဆောင်ကာ
codex OAuth connection တစ်ခုကို ရွေးချယ်ပြီး `wreq-js` transport မှတစ်ဆင့်
`wss://chatgpt.com/backend-api/codex/responses` သို့ tunnel ပြုလုပ်သည်။ **codex မဟုတ်သော model များကို ငြင်းပယ်သည်** (`codex_ws_provider_required`)။
Quota-share routing အတွက် `model: "qtSd/<group>/codex/<model>"` ကို အသုံးပြုပါ။ အကောင်အထည်ဖော်ထားသည့်
ဖိုင်များမှာ `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ဖြစ်သည်။

**အထောက်အထားစိစစ်ခြင်း:** Handshake ပြုလုပ်စဉ် Bearer API key။ ထည့်သွင်းပေးထားသော HTTP server (`server-ws.mjs`)
သည် အသုံးပြုနေသော entrypoint ဖြစ်ရမည် (`app/server-ws.mjs` ရှိပါက မူလအားဖြင့် ၎င်းကို အသုံးပြုသည်)။

#### Model ID- `codex/` prefix မပါသော ChatGPT ID ကို အသုံးပြုပါ

OpenAI **Codex CLI** သည် `supports_websockets = true` ဖြစ်သည့်အခါ model အမည်ကို client ဘက်တွင် အတည်ပြုပြီး
`codex/gpt-5.5` ကဲ့သို့ **provider prefix ပါသော ID များကို ငြင်းပယ်သည်**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)။ **prefix မပါသော** ID ကို ပေးပို့ပါ (ဥပမာ `gpt-5.5`)။ OmniRoute ၏ bridge သည်
codex သီးသန့်ဖြစ်သောကြောင့် upstream သို့ tunnel မပြုလုပ်မီ prefix မပါသော ID ကို codex model တစ်ခုအဖြစ်
(`resolveCodexWsModelInfo`) ပြန်လည်ဖြေရှင်းသတ်မှတ်သည် — prefix မပါသော
`gpt-5.5` သည် HTTP မှတစ်ဆင့်ဆိုလျှင် အခြား provider တစ်ခုသို့ route လုပ်မည်ဖြစ်သော်လည်း ထိုသို့ ဆောင်ရွက်ခြင်းဖြစ်သည်။

#### OpenAI Codex CLI ကို စီစဉ်သတ်မှတ်ခြင်း

`~/.codex/config.toml` တွင် WebSocket
ပံ့ပိုးမှုပါသည့် custom provider တစ်ခု ထည့်ခြင်းဖြင့် Codex CLI ကို OmniRoute သို့ ညွှန်ပါ (ရှိပြီးသား config ကို
မထိခိုက်စေရန် သီးခြား `CODEX_HOME` တစ်ခုကို အသုံးပြုပါ)-

```toml
model = "gpt-5.5"                 # prefix မပါသော ID — "codex/gpt-5.5" မဟုတ်ပါ
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # နောက်ဆုံး slash မပါရ၊ WS URL ကို ဆင်းသက်ဖန်တီးသည် (production တွင် https/wss ကို အသုံးပြုပါ)
wire_api = "responses"                    # Feb 2026 မှစ၍ ပံ့ပိုးသည့် တစ်ခုတည်းသော တန်ဖိုး
supports_websockets = true                # Responses-over-WS transport ကို ဖွင့်ပေးသည်
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key (Bearer) ကို သိမ်းဆည်းထားသည်
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key တစ်ခု (REQUIRE_API_KEY=false ဖြစ်ပါက မည်သည့် key မဆို)
codex exec "Responda apenas: PONG"
```

CLI သည် `base_url + /responses` ကို WebSocket သို့ upgrade လုပ်ပြီး OmniRoute က ၎င်းကို
ရွေးချယ်ထားသော codex OAuth connection သို့ tunnel ပြုလုပ်သည်။ Local
server နှင့် အစမှအဆုံး အတည်ပြုစမ်းသပ်ထားသည်- ChatGPT သည် `codex.rate_limits` + `response.created` ကို ပြန်ပေးပြီး
completion ကို stream လုပ်သည်။

## ကိုယ်တိုင်ဝန်ဆောင်မှုအသုံးပြုမှု (`/api/usage/om-usage`)

မည်သည့် API key မဆို **၎င်းကိုယ်တိုင်၏** အသုံးပြုမှုနှင့် ကန့်သတ်ပမာဏများကို ဖတ်ရှုနိုင်ပြီး စီမံခန့်ခွဲမှုဆိုင်ရာ စစ်မှန်ကြောင်းအတည်ပြုခြင်း မလိုအပ်ပါ။ ဤသည်မှာ
client (CLI၊ OmniCopilot panel) တစ်ခုက key ကိုင်ဆောင်သူအား ၎င်း၏ ကုန်ကျစရိတ်ကို ပြသရန် အသုံးပြုသည့် endpoint ဖြစ်သည်။

```bash
# စာသားပုံစံ (ယခင်ကတည်းက အသုံးပြုလာသည့် သတ်မှတ်ချက် — terminal အတွက် ရိုးရိုးစာသား)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ဖွဲ့စည်းတည်ဆောက်ထားသောပုံစံ — UI တစ်ခုက အသုံးပြုသည့်ပုံစံ
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Key တွင် **`allowUsageCommand`** ကို ဖွင့်ထားရမည် (မူလသတ်မှတ်ချက်အရ ပိတ်ထားပြီး dashboard ၏ API-key
manager က key တစ်ခုချင်းစီအလိုက် ပြောင်းလဲပေးသည်)။ ၎င်းကို မဖွင့်ထားပါက endpoint သည် `403` ဖြင့် တုံ့ပြန်သည်။

`?format=json` သည် ငြင်းပယ်မှုတစ်ခုမှ data field ကို ခေါ်ယူသူက မည်သည့်အခါမျှ မဖတ်မိစေရန် ခွဲခြားသတ်မှတ်နိုင်သော ပုံသဏ္ဌာန်တစ်ခုကို ပြန်ပေးသည်။
အောင်မြင်သောအခါ-

```jsonc
{
  "allowed": true,
  // key က key တစ်ခုချင်းစီအလိုက် အသုံးပြုမှုကန့်သတ်ချက်များ (နေ့စဉ်/အပတ်စဉ် USD) ကို ရွေးချယ်ထားမှသာ ပါဝင်သည်-
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ရွေးချယ်ထားသော provider ကန့်သတ်ပမာဏ snapshot သို့မဟုတ် မည်သည့်အရာမျှ cache မလုပ်ရသေးပါက null-
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // UI တစ်ခုက provider အများအပြားကို ဘေးချင်းယှဉ်၍ ဖော်ပြနိုင်ရန် connection တိုင်း၏ snapshot-
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

ငြင်းပယ်ခံရသောအခါ (`401` မမှန်ကန်သော key / `403` ခွင့်မပြုထားခြင်း) တူညီသော route သည်
`{ "allowed": false, "error": { "message": "…" } }` ကို ပြန်ပေးသည်။ ပါရှိသော်လည်း ဗလာဖြစ်နေသော `personal`/`provider`
(key ကို ခွင့်ပြုထားသော်လည်း မည်သည့်အချက်အလက်မျှ မရရှိသေးခြင်း) သည် ငြင်းပယ်မှုနှင့် မတူညီသော အခြေအနေတစ်ခုဖြစ်ပြီး JSON ပုံစံကသာ
၎င်းတို့ကို ခွဲခြားပေးသည်။

**စစ်မှန်ကြောင်းအတည်ပြုခြင်း:** ခေါ်ယူသူ၏ ကိုယ်ပိုင် Bearer API key ကို `isValidApiKey` ဖြင့် အတည်ပြုသည်။ ဤသည်မှာ
`requireManagementAuth` နောက်ကွယ်တွင် ဆက်လက်ထားရှိသည့် စီမံခန့်ခွဲမှုဆိုင်ရာ မျက်နှာပြင် (`/api/keys/…`) _မဟုတ်ပါ_။

### မူရင်းနှင့် ဖြတ်တောက်သတ်မှတ်ချက်အလိုက် ချိန်ညှိထားသော ကန့်သတ်ပမာဏ ရာခိုင်နှုန်းများ

`/api/usage/om-usage` ကို အသုံးပြုသောအခါ ခေါ်ယူသူများသည် **ရိုးရိုးစာသား output** နှင့် ဖွဲ့စည်းတည်ဆောက်ထားသော
**JSON output** တို့တွင် ဖော်ပြသည့် ရာခိုင်နှုန်းများအကြား ကွာခြားချက်ကို သတိပြုသင့်သည်-

| အချက်                                    | ရိုးရိုးစာသားပုံစံ (`/api/usage/om-usage` / `@@om-usage`)                                                               | JSON ပုံစံ (`?format=json`)                                                                                   |
| :--------------------------------------- | :---------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| **Output field**                         | `NN% left` (ဥပမာ၊ `20% left`)                                                                                           | `provider.quotas` / `providers[].quotas`                                                                      |
| **တိုင်းတာမှု**                          | **ဖြတ်တောက်သတ်မှတ်ချက်အလိုက် ချိန်ညှိထားသော အသုံးပြုနိုင်သည့် ပမာဏ**- ဖြတ်တောက်သတ်မှတ်ချက်ထက် ကျန်ရှိသည့် စွမ်းရည်      | **မူရင်း upstream ကန့်သတ်ပမာဏ**- provider ၏ ချိန်ညှိမထားသော တိုင်းတာမှု                                       |
| **ဖြတ်တောက်မှု အတိုင်းအတာချိန်ညှိခြင်း** | အကာအကွယ်ပေးထားသော သီးသန့်ပမာဏကို `0% left` ဟု ဖော်ပြစေရန် `effectiveRemainingPercent()` မှတစ်ဆင့် အတိုင်းအတာချိန်ညှိသည် | မရှိပါ (provider က အစီရင်ခံသည့်အတိုင်း မူရင်း snapshot တန်ဖိုးများ)                                           |
| **သတ်မှတ်ချက်ဒေတာ**                      | ဖော်ပြထားသော ရာခိုင်နှုန်းထဲတွင် ထည့်သွင်းတွက်ချက်ထားသည်                                                                | connection တစ်ခုချင်းစီ၏ `quotaWindowThresholds` တွင် သိမ်းဆည်းထားသည် (သို့မဟုတ် server ၏ မူလသတ်မှတ်ချက်များ) |
| **အဓိကအသုံးပြုသူ**                       | အပြန်အလှန်တုံ့ပြန်နိုင်သော CLI များ၊ terminal prompt များ၊ လူသား operator များ                                          | ပရိုဂရမ်ဖြင့် ပေါင်းစည်းအသုံးပြုမှုများ၊ dashboard များ၊ analytics၊ billing tracker များ                      |

#### ဖြတ်တောက်မှု ချိန်ညှိခြင်း ဖော်မြူလာ

OmniRoute သည် upstream ကုန်ဆုံးမှုကို ကာကွယ်ရန် ကြိုတင်လုပ်ဆောင်သော ကန့်သတ်ပမာဏ ဖြတ်တောက်မှုများကို ပံ့ပိုးသည် (connection
`quotaWindowThresholds`၊ provider မူလသတ်မှတ်ချက်များ သို့မဟုတ် ကမ္ဘာလုံးဆိုင်ရာ resilience setting များမှတစ်ဆင့် သတ်မှတ်သည်)။ ကန့်သတ်ပမာဏ window တစ်ခုတွင် ဖြတ်တောက်သတ်မှတ်ချက်
(ဥပမာ၊ `cutoff = 25%`) ကို အသက်သွင်းထားသောအခါ text renderer သည် ကျန်ရှိသော ပမာဏကို အောက်ပါအတိုင်း တွက်ချက်သည်-

- `remaining <= cutoff` ဖြစ်ပါက `0%` ကို ပြန်ပေးသည်။
- `remaining > cutoff` ဖြစ်ပါက `((remaining - cutoff) / (100 - cutoff)) * 100` ကို ပြန်ပေးသည်။

ဖော်မတ်ပြုလုပ်ထားသော စာသား output သည် ၎င်းကို အနီးဆုံး ကိန်းပြည့်သို့ လှည့်ပေးသည် (`Math.round(...)`)။

#### ရှင်းလင်းပြသသည့် ဥပမာ

**မူရင်းအသုံးပြုမှု 60%** (ထို့ကြောင့် **မူရင်းကျန်ရှိသော ကန့်သတ်ပမာဏ 40%**) ရှိသည့် provider window တစ်ခုနှင့် သတ်မှတ်ထားသော
**ကျန်ရှိသည့်ကန့်သတ်ပမာဏ ဖြတ်တောက်သတ်မှတ်ချက် 25%** ကို စဉ်းစားကြည့်ပါ-

| ဖော်ပြပုံ                        | တွက်ချက်မှု                                        | ကျန်ရှိမှု |    သွယ်ဝိုက်ဖော်ပြသည့် အသုံးပြုပြီးပမာဏ     |
| :------------------------------- | :------------------------------------------------- | :--------: | :-----------------------------------------: |
| **မူရင်း JSON (`?format=json`)** | Upstream snapshot (`quotas[window]`)               |  **40%**   |                   **60%**                   |
| **စာသားပုံစံ (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**   | **80%** (`100 - remaining` ကို တွက်ချက်ပါက) |

- **စာသားတွင် 20% ကျန်သည်ဟု ပြသရသည့်အကြောင်းရင်း:** Account တွင် ရုပ်ပိုင်းဆိုင်ရာအရ ကျန်ရှိသည့် ကန့်သတ်ပမာဏ 40% အနက် 25% ကို
  ဖြတ်တောက်မှုမူဝါဒက သီးသန့်ထားရှိသည်။ Router က ဤ connection သို့ route လုပ်ခြင်းကို မရပ်တန့်မီ ခေါ်ယူသူအတွက် အသုံးပြုနိုင်သော စုစုပေါင်း headroom 75% အနက်
  15% သာ ကျန်ရှိသည်။ အတိုင်းအတာချိန်ညှိခြင်းကြောင့် route လုပ်ခြင်း ရပ်တန့်မည့်အချိန်နှင့် တိတိကျကျကိုက်ညီစွာ connection က ကုန်ဆုံးမှု (`0% left`) ကို
  အချက်ပြနိုင်သည်။
- **JSON က မူရင်းတန်ဖိုးများကို ထိန်းသိမ်းထားရသည့်အကြောင်းရင်း:** JSON payload သည် provider snapshot (`UsageSnapshot`) အတိအကျကို ပြန်ပေးသဖြင့်
  ပြင်ပ tool များက အမှန်တကယ်ဖြစ်သော upstream အသုံးချမှုနှင့် connection အဆင့်
  `quotaWindowThresholds` တို့ကို server ဘက်မှ အချက်အလက်ဆုံးရှုံးစေသည့် အတိုင်းအတာချိန်ညှိမှုမရှိဘဲ ရယူနိုင်သည်။

#### အသုံးပြုသူများ ပြောင်းရွှေ့အသုံးပြုရန် လမ်းညွှန်ချက်

ပြင်ပပေါင်းစည်းမှုတစ်ခု (ဥပမာ တည်းဖြတ်ကိရိယာ ပလပ်အင် သို့မဟုတ် အေးဂျင့် တိုးချဲ့မှု) သည် ယခင်က စာသား
အဆုံးမှတ် (`NN% left`) ကို ဖတ်ယူပြီး အသုံးပြုပြီး ရာခိုင်နှုန်းကို `100 - NN` အဖြစ် တွက်ချက်ခဲ့ပါက၊ `?format=json` သို့ ပြောင်းရွှေ့ခြင်းသည် အောက်ပါတို့ကို ဆိုလိုသည်-

- မူရင်း JSON တန်ဖိုးများကို ဖတ်ရှုခြင်းဖြင့် **အထက်စီးကြောင်းတွင် အမှန်တကယ် သုံးစွဲမှု** ကို ဖော်ပြပါမည် (အထက်ပါ ဥပမာတွင် 60% အသုံးပြုပြီး)။
- ပေါင်းစည်းမှုသည် စာသားအဆုံးမှတ်၏ အသုံးပြုနိုင်သည့် ခွင့်ပြုပမာဏဆိုင်ရာ အဓိပ္ပာယ်ကို ဆက်လက်ထိန်းသိမ်းလိုပါက၊ ချိတ်ဆက်မှုအဆင့် အစားထိုးသတ်မှတ်ချက်များအတွက် `quotaWindowThresholds` ကို အသုံးပြုပြီး
  လက်တွေ့ကျန်ရှိသည့် ပမာဏ ဖော်မြူလာကို ကလိုင်းယင့်ဘက်တွင် တွက်ချက်နိုင်သည်။

## အဓိပ္ပာယ်အခြေပြု ကက်ရှ်

```bash
# ကက်ရှ် စာရင်းအင်းများကို ရယူရန်
GET /api/cache/stats

# ကက်ရှ်အားလုံးကို ရှင်းလင်းရန်
DELETE /api/cache/stats
```

တုံ့ပြန်မှု နမူနာ-

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### ကြာချိန်အပေါ် သက်ရောက်မှု

အဓိပ္ပာယ်အခြေပြု ကက်ရှ်တွင် HIT ဖြစ်ပါက upstream သို့
ခေါ်ဆိုမှု **မပြုလုပ်ဘဲ** ကက်ရှ်မှ တုံ့ပြန်မှုကို ပေးပို့သောကြောင့် ဖော်ပြထားသည့် `X-OmniRoute-Response-Latency` သည်
မူလ upstream ကြာချိန်နှင့် မသက်ဆိုင်ဘဲ သုညနီးပါး ဖြစ်သည်။ ကြာချိန်ကို အထူးဂရုပြုရသည့် client များ
(စွမ်းဆောင်ရည်တိုင်းတာခြင်း၊ p50/p99 စောင့်ကြည့်ခြင်း) သည်
`X-OmniRoute-Cache-Latency` တုံ့ပြန်မှု header ကို စစ်ဆေးသင့်သည်-

| တန်ဖိုး     | အဓိပ္ပာယ်                                                                           |
| ----------- | ----------------------------------------------------------------------------------- |
| `synthetic` | ကက်ရှ်မှ တုံ့ပြန်မှုကို ပေးပို့ထားသည်၊ ကြာချိန်သည် အမှန်တကယ် upstream အချိန်မဟုတ်ပါ |
| _(မပါရှိ)_  | အမှန်တကယ် upstream ခေါ်ဆိုမှုမှ တုံ့ပြန်မှုဖြစ်သည်                                  |

### Key တစ်ခုချင်းအလိုက် ကက်ရှ်ကို ကျော်ခြင်း

API key များသည် `cacheDefaultMode` မှတစ်ဆင့် အဓိပ္ပာယ်အခြေပြု ကက်ရှ်ဖတ်ရှုမှုများကို မသုံးရန် ရွေးချယ်နိုင်သည်-

| တန်ဖိုး  | လုပ်ဆောင်ပုံ                                                  |
| -------- | ------------------------------------------------------------- |
| `legacy` | ပုံမှန် ကက်ရှ်လုပ်ဆောင်ပုံ (မူလသတ်မှတ်ချက်)                   |
| `bypass` | ကက်ရှ်ရှာဖွေမှုကို လုံးဝကျော်ပြီး upstream ကို အမြဲခေါ်ဆိုသည် |

Key ဖန်တီးချိန် (`POST /api/keys`) သို့မဟုတ် ပြင်ဆင်ချိန် (`PATCH /api/keys/[id]`) တွင် သတ်မှတ်ပါ-

```json
{ "cacheDefaultMode": "bypass" }
```

### တောင်းဆိုမှုတစ်ခုချင်းအလိုက် ကျော်ခြင်း

မည်သည့်တောင်းဆိုမှုမဆို key ဆက်တင်များနှင့် မသက်ဆိုင်ဘဲ ကက်ရှ်ကို ကျော်နိုင်သည်-

```
X-OmniRoute-No-Cache: true
```

တစ်ပြိုင်တည်းချိန်ညှိထားသော/တင်သွင်းထားသော မော်ဒယ်များအတွက် `PUT /api/provider-models` သည် `provider`၊ `modelId` နှင့်
`maxOutputTokenOverride` ကို လက်ခံသည်။ အပေါင်းကိန်းပြည့်တစ်ခုက ကိုယ်တိုင်သတ်မှတ်ထားသော အထွက်တိုကင် အများဆုံးကန့်သတ်ချက်ကို သတ်မှတ်ပေးပြီး `null`
က မူလသတ်မှတ်ချက်ကို ပြန်လည်အသုံးပြုရန် ၎င်းကို ရှင်းလင်းပေးသည်။ `GET /api/provider-models?provider=<provider>` သည် စိတ်ကြိုက်မော်ဒယ် အတန်းမရှိသည့်
မော်ဒယ်များအပါအဝင် ဤတန်ဖိုးများကို `modelOutputOverrides` ထဲတွင် ပြန်ပေးသည်။ အစားထိုးသတ်မှတ်ချက်သည်
လုပ်ဆောင်ချိန် `max_output_tokens` စွမ်းရည်ကို အသုံးပြုပြီး မော်ဒယ်ကို ပြန်လည်တစ်ပြိုင်တည်းချိန်ညှိပြီးနောက်တွင်လည်း ဆက်လက်တည်ရှိသည်။ OpenAI နှင့် တွဲဖက်အသုံးပြုနိုင်သော
ပံ့ပိုးသူစာမျက်နှာတွင် အလားတူ တည်းဖြတ်ရန်/ရှင်းလင်းရန် ထိန်းချုပ်မှုများ ပါရှိပြီး ရုပ်မြင်ဆိုင်ရာ ပံ့ပိုးမှုကို အတိအလင်းပေးထားသည့် မော်ဒယ်များကို အမှတ်အသားပြုသည်။

စိတ်ကြိုက် Chat Completions နုတ်ဒ်များသည် အတိအလင်း ကျိုးကြောင်းဆင်ခြင်မှု ပယ်ဖျက်ချက်များကို မူလ အထက်ပိုင်းဘက်အဆုံးစနစ်နှင့် ကိုက်ညီအောင် ပြောင်းလဲပေးသည်။
ချိတ်ဆက်မှု စမ်းသပ်မှု အောင်မြင်ပါက `/models` ထည့်သွင်းချက်မှ အသိအမှတ်ပြုထားသော `owned_by` တန်ဖိုးဖြစ်သည့် `vllm`၊ `sglang` သို့မဟုတ် `llamacpp`
ကို သက်သေပြနိုင်သည့် တိကျသော မော်ဒယ် ID တစ်ခုချင်းစီအတွက် chat-template ထိန်းချုပ်မှုများကို အလိုအလျောက် ရွေးချယ်ပေးသည်။
ပွင့်လင်းမြင်သာသော OpenAI နှင့် တွဲဖက်အသုံးပြုနိုင်သည့် wrapper များသည် မူရင်းမော်ဒယ် ထည့်သွင်းချက်ကို အဆင့်ဆင့်ထည့်သွင်းထားသော
`openai` အရာဝတ္ထုတစ်ခုအတွင်း ထိန်းသိမ်းထားနိုင်သည်။ စစ်ဆေးဖော်ထုတ်မှုသည် ထိုသို့သော ထုပ်ပိုးမှုများကို သုံးဆင့်အထိ လိုက်နာသည်။ ပိုင်ဆိုင်မှု မပါရှိသော၊ မသိရှိသော သို့မဟုတ်
ကွဲလွဲနေသော မော်ဒယ်များသည် ပုံမှန် OpenAI အပြုအမူကို ဆက်လက်ထိန်းသိမ်းထားသည်။ စစ်ဆေးဖော်ထုတ်မှုသည် ရှိပြီးသား ကတ်တလောက် တောင်းဆိုချက်ကို ပြန်လည်အသုံးပြုကာ
completion တိုကင်များ မထုတ်လုပ်ဘဲ ချိတ်ဆက်မှု အဆုံးမှတ် ပြောင်းလဲသည့်အခါ ပျက်ပြယ်သွားသည်။

ထို metadata ကို မဖော်ပြပေးသည့် အထက်ပိုင်းဘက်အဆုံးစနစ်တစ်ခုအတွက် အပြုအမူကို ပုံသေသတ်မှတ်ရန် ရှိပြီးသား တစ်စိတ်တစ်ပိုင်း
ပံ့ပိုးသူ အပ်ဒိတ် API ကို အသုံးပြုပါ။

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ထို body ကို `PUT /api/providers/<connection-id>` ဖြင့် ပေးပို့ပါ။ ထိုချိတ်ဆက်မှုတွင် `none` ဟု အတိအလင်းသတ်မှတ်ထားသော
ကျိုးကြောင်းဆင်ခြင်မှု အားထုတ်မှုကို `chat_template_kwargs.thinking=false` နှင့်
`chat_template_kwargs.enable_thinking=false` အဖြစ် ပေးပို့သည်။ ဆာဗာဘက်ရှိ ကျိုးကြောင်းဆင်ခြင်မှု စည်းမျဉ်းတစ်ခုက အားထုတ်မှုတစ်ခုကို မဖြစ်မနေသတ်မှတ်ခြင်းမရှိလျှင်
အတိအလင်းသတ်မှတ်ထားသော မူရင်း template တန်ဖိုးများကိုသာ အဓိကထားအသုံးပြုသည်။ ဤဆက်တင်သည် စိတ်ကြိုက်
OpenAI နှင့် တွဲဖက်အသုံးပြုနိုင်သော ချိတ်ဆက်မှုတစ်ခုက Chat Completions body တစ်ခုကို ပို့ဆောင်သည့်အခါတွင်သာ သက်ရောက်သည်။ Responses တောင်းဆိုချက်များနှင့် ပုံမှန်
ပံ့ပိုးသူများသည် ၎င်းတို့၏ မူရင်းတောင်းဆိုချက် ပုံစံကို ဆက်လက်ထိန်းသိမ်းထားသည်။ ပုံမှန် OpenAI
`reasoning_effort` ကို မပြောင်းလဲဘဲ ဖြတ်သန်းပေးရန် `reasoningControl` ကို `openai` အဖြစ် သတ်မှတ်ပါ သို့မဟုတ် အလိုအလျောက် စစ်ဆေးဖော်ထုတ်မှုကို အသုံးပြုရန် ၎င်းကို ချန်လှပ်ပါ/`null` အဖြစ် သတ်မှတ်ပါ။

Claude Code အလိုအလျောက်မုဒ် အမျိုးအစားခွဲခြားကိရိယာ တောင်းဆိုချက်များတွင် အတိအလင်း ကျိုးကြောင်းဆင်ခြင်မှု ထိန်းချုပ်ချက်များ
မပါဝင်သည့်အခါ မူရင်း thinking ကို ပိတ်ထားသည့်အခြေအနေအဖြစ် သတ်မှတ်သည်။ စစ်ဆေးဖော်ထုတ်မှုသည် မော်ဒယ်အမည်များ သို့မဟုတ် completion ကန့်သတ်ချက်များကို မသုံးဘဲ Claude ပုံစံ
တောင်းဆိုချက်များရှိ အမျိုးအစားခွဲခြားကိရိယာ၏ system marker ကို အသုံးပြုသည်။ အတိအလင်း body ထိန်းချုပ်ချက်များ၊ ပံ့ပိုးထားသော effort/thinking
header များ၊ လမ်းကြောင်းသတ်မှတ်ခြင်း စည်းမျဉ်းများနှင့် ဖြေရှင်းသတ်မှတ်ထားသော မော်ဒယ် effort တို့သည် ၎င်းတို့၏ လက်ရှိဦးစားပေးအစီအစဉ်ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ အမျိုးအစားခွဲခြားကိရိယာ
အဆင့်နှစ်ခုစလုံးသည် ၎င်းတို့၏ prompt များ၊ completion ကန့်သတ်ချက်များ၊ ရပ်တန့်မှု sequence များနှင့် အထက်ပိုင်းဘက်အဆုံးစနစ်မှ အမှန်တကယ် ခွင့်ပြုချက်
ဆုံးဖြတ်ချက်များကို ထိန်းသိမ်းထားသည်။ ဒုတိယအဆင့်သည် တောင်းဆိုထားသော မြင်သာသည့် ကျိုးကြောင်းဆင်ခြင်မှုကို သာမန်စာသားအဖြစ် ဆက်လက်ထုတ်လုပ်နိုင်သည်။

### API ကီး ခွင့်ပြုချက်များ

`PATCH /api/keys/{id}` သည် ရှိပြီးသား ကီးတစ်ခု၏ ခွင့်ပြုချက်များကို အပ်ဒိတ်လုပ်သည်။ `/api/keys*` လမ်းကြောင်းတိုင်းကဲ့သို့ပင် ၎င်းသည် inference ကီးမဟုတ်ဘဲ စီမံခန့်ခွဲမှုဆိုင်ရာ အတည်ပြုခွင့်ပြုချက် လိုအပ်သည် ([စီမံခန့်ခွဲမှုဆိုင်ရာ အထောက်အထားစစ်ဆေးခြင်း](../guides/MANAGEMENT-AUTH.md) ကို ကြည့်ပါ)။ ပြောင်းလဲလိုသော field များကိုသာ ပေးပို့ပါ၊ ၎င်းတို့ထဲမှ တစ်ခုမျှမပါဝင်သော တောင်းဆိုမှုကို `No valid fields to update` ဖြင့် ငြင်းပယ်မည်ဖြစ်သည်။ လက်ခံနိုင်သော field များကို `src/shared/validation/schemas/keys.ts` ရှိ `updateKeyPermissionsSchema` က သတ်မှတ်ထားသည်။

### ဗားရှင်းနှင့် Release Channel

```bash
GET /api/system/version
```

Loopback မှသာ အသုံးပြုနိုင်သော စီမံခန့်ခွဲမှု route (admin authentication လိုအပ်သည်)။ လက်ရှိအသုံးပြုနေသော ဗားရှင်း၊ နောက်ဆုံး
ထုတ်ဝေထားသော ဗားရှင်းနှင့် အလိုအလျောက် update အခြေအနေတို့ကို ပြန်ပေးသည်။ `releaseChannel` နှင့် `channels` တို့သည် ထပ်မံဖြည့်စွက်ထားသော
field များဖြစ်သည် (rail 3.8.54)။ `channel` သည် မူလအဓိပ္ပာယ်အတိုင်း ဆက်ရှိနေပြီး dashboard updater က
အသုံးပြုသည့် deployment mode (`npm`, `source` သို့မဟုတ် `docker-compose`) ကို ဆိုလိုသည်။

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — လက်ရှိအသုံးပြုနေသော build ၏ npm channel ဖြစ်သည်။ `-nightly.*` ဗားရှင်းများအတွက် `nightly`၊
  အခြား pre-release များ (`-rc.*`, `-beta.*`, `-alpha.*`) အတွက် `next`၊ `channels.latest` ထက် major ဗားရှင်းအဟောင်းဖြစ်သော
  stable ဗားရှင်းအတွက် `lts` ဖြစ်ပြီး၊ အခြားအခြေအနေများတွင် `latest` ဖြစ်သည်။ ထုတ်ဝေချိန်၌ npm dist-tag ကို ရွေးချယ်သည့်
  `scripts/release/dist-tag.mjs` နှင့် တူညီသော စည်းမျဉ်းများကို အသုံးပြုသည်။
- `channels` — `npm view omniroute dist-tags` မှရရှိသော dist-tag တစ်ခုစီ၏ နောက်ဆုံးထုတ်ဝေထားသည့် ဗားရှင်းဖြစ်ပြီး (registry
  HTTP fallback ပါဝင်သည်)၊ `latest` ကဲ့သို့ပင် ၁၀ မိနစ် TTL ဖြင့် cache သိမ်းထားသည်။ `latest` သည် အမြဲတမ်း ပါဝင်သည်
  (`latest` field ကို fallback အဖြစ် အသုံးပြုပြီး၊ ထို့နောက် `"unavailable"` ကို အသုံးပြုသည်)။ `next`, `nightly` နှင့် `lts` တို့သည်
  သက်ဆိုင်ရာ dist-tag ရှိမှသာ ပေါ်လာသည်။ `Cache-Control: no-cache` request တစ်ခုသည် lookup နှစ်ခုစလုံးကို refresh လုပ်သည်။

Channel model (`latest` = 4.0 GA မတိုင်မီအထိ v3၊ `next` = rc၊ `nightly` = `develop` build များ၊
`lts` = 4.0 GA နောက်ပိုင်း v3 patch များ) ကို `docs/ops/RELEASE_STRATEGY.md` တွင် ဖော်ပြထားသည်။

## အသံမှ စာသားသို့ ကူးပြောင်းခြင်း

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

ပြင်ဆင်သတ်မှတ်ထားသည့် မည်သည့် STT ပံ့ပိုးသူကိုမဆို အသုံးပြု၍ အသံဖိုင်များကို စာသားအဖြစ် ကူးပြောင်းပါ။ ပထမ path
segment သည် မူရင်းပံ့ပိုးသူ (`openai/…`, `deepgram/…`) ကို ရွေးချယ်ပေးသည်။ အခြား vendor ၏ model ကို
ပြန်လည်ထုတ်ပေးသည့် gateway များသည် အပြည့်အစုံသတ်မှတ်ထားသော id
(`openrouter/deepgram/nova-3`) ကို အသုံးပြုသည်။

**တောင်းဆိုချက်:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**တုံ့ပြန်ချက်:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**နမူနာ model id များ:** `openai/whisper-1` (OpenAI key တစ်ခု လိုအပ်သည်),
`openrouter/deepgram/nova-3` (OpenRouter key တစ်ခု လိုအပ်သည်),
`deepgram/nova-3` (မူရင်း Deepgram key တစ်ခု လိုအပ်သည်)။ `deepgram/nova-3` ကို တိုက်ရိုက်
တောင်းဆိုခြင်းသည် OpenRouter ကို **အသုံးမပြုပါ**။

**ပံ့ပိုးထားသော format များ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

Ollama ၏ API format ကို အသုံးပြုသော client များအတွက်:

```bash
# Chat endpoint (Ollama format)

# Model စာရင်း (Ollama format)
GET /api/tags
```

တောင်းဆိုချက်များကို Ollama format နှင့် internal format များအကြား အလိုအလျောက် ပြောင်းလဲပေးသည်။

## Token ပါဝင်သော VS Code / Header မပါသော Alias များ

Integration တစ်ခုသည် `Authorization` header ကို ထည့်သွင်းမပေးနိုင်ဘဲ base URL ထဲတွင် API key ကို မြှုပ်နှံထည့်သွင်းရန် လိုအပ်သည့်အခါ ဤ alias များကို အသုံးပြုပါ။

```bash
# OpenAI ပုံစံ catalog alias
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI ပုံစံ chat alias များ
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama ပုံစံ alias များ
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ဥပမာ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

မှတ်ချက်များ:

- Token ပါဝင်သော alias များသည် `/v1/*` နှင့် `/api/tags` တို့ကဲ့သို့ တူညီသော handler များကို ပြန်လည်အသုံးပြုသောကြောင့် တုံ့ပြန်ချက်ပုံစံများသည် တူညီနေမည်ဖြစ်သည်။
- Client က စိတ်ကြိုက် header များကို ပံ့ပိုးသည့်အခါတိုင်း `Authorization: Bearer ...` ကို ဦးစားပေးအသုံးပြုပါ။
- URL အခြေပြု token များသည် OmniRoute ပြင်ပရှိ reverse-proxy log များ၊ browser history နှင့် telemetry တို့တွင် ပေါ်လာနိုင်သည်။ ၎င်းတို့ကို ပုံမှန် authentication mode အဖြစ် မသတ်မှတ်ဘဲ လိုက်ဖက်ညီမှုအတွက် ရွေးချယ်စရာတစ်ခုအဖြစ်သာ သတ်မှတ်ပါ။

## ဘတ်ဂျက်

```bash
# API key အားလုံးအတွက် ဘတ်ဂျက်အခြေအနေကို ရယူရန်
GET /api/usage/budget

# ဘတ်ဂျက်တစ်ခုကို သတ်မှတ်ရန် သို့မဟုတ် အပ်ဒိတ်လုပ်ရန်
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **Schema မှတ်ချက်များ** (`setBudgetSchema`): `apiKeyId` သည် မဖြစ်မနေလိုအပ်သည်။ `dailyLimitUsd`, `weeklyLimitUsd` သို့မဟုတ် `monthlyLimitUsd` တို့အနက် အနည်းဆုံးတစ်ခုသည် သုညထက် ကြီးရမည်။ ထည့်သွင်းရန် မလိုအပ်သော field များမှာ `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`) တို့ဖြစ်သည်။ အဟောင်းဖြစ်သော `{keyId, limit, period}` ပုံစံသည် `400 Bad Request` ကို ပြန်ပေးသည်။

## Token ကန့်သတ်ချက်များ

API key တစ်ခုချင်းစီအလိုက် **token** သုံးစွဲခွင့်ပမာဏများ (အထက်ပါ USD အခြေပြု Budget နှင့် သီးခြားဖြစ်သည်)။ Request လမ်းကြောင်းပေါ်တွင် တိုက်ရိုက်စစ်ဆေးကန့်သတ်သည်။ Key တစ်ခု၏ လက်ရှိ window အသုံးပြုမှုသည် သတ်မှတ်ထားသော ကန့်သတ်ချက်သို့ ရောက်ရှိသောအခါ request များကို `429 Too Many Requests` ဖြင့် ငြင်းပယ်သည်။ ကန့်သတ်ချက်များကို သီးခြား `model` တစ်ခု၊ `provider` တစ်ခုအတွက် သတ်မှတ်နိုင်သကဲ့သို့ key တစ်ခုလုံးအတွက် `global` အဖြစ်လည်း အသုံးချနိုင်သည်။ Request တစ်ခုနှင့် ကန့်သတ်ချက်များစွာ ကိုက်ညီပါက အတင်းကျပ်ဆုံး ကန့်သတ်ချက်ကို အသုံးပြုသည်။

```bash
# Key တစ်ခု၏ token ကန့်သတ်ချက်များကို စာရင်းပြုစုပါ (လက်ရှိ window အသုံးပြုမှု ပါဝင်သည်)
GET /api/usage/token-limits?apiKeyId=key-123

# Token ကန့်သတ်ချက်တစ်ခုကို ဖန်တီးပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Token ကန့်သတ်ချက်တစ်ခုကို id ဖြင့် ဖျက်ပါ
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schema မှတ်ချက်များ** (`setTokenLimitSchema`): `apiKeyId` နှင့် `scopeType` (`model` | `provider` | `global`) တို့သည် မဖြစ်မနေ လိုအပ်သည်။ `scopeType` သည် `global` မဟုတ်ပါက `scopeValue` ကို မဖြစ်မနေ ထည့်သွင်းရမည် (`model` scope အတွက် model id၊ `provider` scope အတွက် provider id စသည်ဖြင့်)။ `tokenLimit` သည် အပေါင်းကိန်းပြည့် ဖြစ်ရမည် (string မှ အလိုအလျောက် ပြောင်းလဲပေးသည်)။ ထည့်သွင်းရန် မဖြစ်မနေမလိုသော အကွက်များမှာ `id` (အသစ်ဖန်တီးရန် ချန်လှပ်ထားပြီး အပ်ဒိတ်လုပ်ရန် ထည့်သွင်းပါ)၊ `resetInterval` (`daily` | `weekly` | `monthly`၊ မူလတန်ဖိုး `monthly`)၊ `resetTime` (`HH:MM`) နှင့် `enabled` (မူလတန်ဖိုး `true`) တို့ဖြစ်သည်။ `GET` response များတွင် ကန့်သတ်ချက်တစ်ခုစီအတွက် `tokensUsed`၊ `remaining`၊ `windowStart`၊ `periodStartAt` နှင့် `nextResetAt` တို့ကို ဖြည့်စွက်ပေးသည်။ ဤသည်မှာ management အမျိုးအစား endpoint ဖြစ်သည် (authz pipeline က authentication ကို ဗဟိုမှ စစ်ဆေးအတည်ပြုသည်)။

## Request လုပ်ဆောင်ပုံ

1. Client က request ကို `/v1/*` သို့ ပေးပို့သည်
2. Route handler က `handleChat`၊ `handleEmbedding`၊ `handleAudioTranscription` သို့မဟုတ် `handleImageGeneration` ကို ခေါ်ဆိုသည်
3. Model ကို သတ်မှတ်ဆုံးဖြတ်သည် (provider/model ကို တိုက်ရိုက်အသုံးပြုခြင်း သို့မဟုတ် alias/combo မှတစ်ဆင့်)
4. Account အသုံးပြုနိုင်မှု စစ်ထုတ်ခြင်းဖြင့် local DB မှ credentials များကို ရွေးချယ်သည်
5. Chat အတွက် `handleChatCore` က semantic/signature cache ကို စစ်ဆေးပြီး combo compression setting များကို သတ်မှတ်ဆုံးဖြတ်သည်
6. ဖွင့်ထားပါက provider translation မတိုင်မီ proactive compression ကို လုပ်ဆောင်သည် (`lite`၊ Caveman၊ RTK သို့မဟုတ် အဆင့်ဆင့် ပေါင်းစပ်ထားသည့်နည်းလမ်း)
7. Provider executor က upstream request ကို ပေးပို့သည်
8. Response ကို client format သို့ ပြန်လည်ပြောင်းလဲပေးသည် (chat အတွက်) သို့မဟုတ် မူလအတိုင်း ပြန်ပေးသည် (embeddings/images/audio အတွက်)
9. အသုံးပြုမှု၊ compression analytics နှင့် request log များကို မှတ်တမ်းတင်သည်
10. Error ဖြစ်ပါက combo စည်းမျဉ်းများအတိုင်း fallback ကို အသုံးပြုသည်

Architecture အပြည့်အစုံ ကိုးကားချက်- [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## မှတ်ပုံတင်ထားသော သော့များ (အလိုအလျောက် စီမံခန့်ခွဲမှု)

| နည်းလမ်း | လမ်းကြောင်း                           | ဖော်ပြချက်                                                                                                                                                                                                                             |
| -------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/v1/registered-keys`             | မှတ်ပုံတင်ထားသော သော့များကို စာရင်းပြုစုရန် (ဖုံးကွယ်ထားသော prefix သာ)                                                                                                                                                                 |

| DELETE   | `/api/v1/registered-keys/[id]`        | မှတ်ပုံတင်ထားသော သော့တစ်ခုကို ရုပ်သိမ်းရန်                                                                                                                                                                                             |

## Agent များဆိုင်ရာ ပရိုတိုကော

OmniRoute အသုံးပြုသူများကိုယ်စား အဝေးမှ လုပ်ဆောင်သည့် cloud agent လုပ်ဆောင်ချက်များ (Claude Code, Codex Cloud, OpenHands စသည်တို့)။

| မက်သဒ် | လမ်းကြောင်း                   | ဖော်ပြချက်                                                                                                                                                                                  |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/agents/tasks`        | လုပ်ဆောင်ချက်များကို စာရင်းပြုစုရန် — `?provider=`, `?status=`, `?limit=` (1–500၊ မူလသတ်မှတ်ချက် 50) တို့ကို ရွေးချယ်ထည့်နိုင်သည်                                                           |
| POST   | `/api/v1/agents/tasks`        | လုပ်ဆောင်ချက် ဖန်တီးရန် — body ကို `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`) ဖြင့် အတည်ပြုစစ်ဆေးသည်။ လုပ်ဆောင်ချက် envelope နှင့်အတူ `201` ကို ပြန်ပေးသည် |
| DELETE | `/api/v1/agents/tasks?id=...` | လုပ်ဆောင်ချက်တစ်ခုကို ဖျက်ရန်                                                                                                                                                               |
| GET    | `/api/v1/agents/tasks/[id]`   | လုပ်ဆောင်ချက်ကို ဖတ်ရန် — `external_id` သတ်မှတ်ထားသောအခါ upstream cloud agent ထံမှ အခြေအနေကို တစ်ပြိုင်တည်း ပြန်လည်ရယူမွမ်းမံသည်                                                            |
| POST   | `/api/v1/agents/tasks/[id]`   | ခွဲခြားသတ်မှတ်ထားသော လုပ်ဆောင်မှု — `{action: "approve"}`, `{action: "message", message}` သို့မဟုတ် `{action: "cancel"}`                                                                    |
| DELETE | `/api/v1/agents/tasks/[id]`   | သီးခြားလုပ်ဆောင်ချက်တစ်ခုကို id ဖြင့် ဖျက်ရန်                                                                                                                                               |

## စီမံခန့်ခွဲမှု Proxy များ

Provider များ၊ account များ သို့မဟုတ် ကမ္ဘာလုံးဆိုင်ရာအဖြစ် သတ်မှတ်ပေးနိုင်သည့် အထွက် HTTP(S)/SOCKS proxy များ။

| မက်သဒ် | လမ်းကြောင်း                                  | ဖော်ပြချက်                                                                                                                                                                                                       |
| ------ | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | Proxy များကို စာရင်းပြုစုရန် (`?id=` ဖြင့် တစ်ခုကို ပြန်ပေးပြီး၊ `?id=&where_used=1` ဖြင့် သတ်မှတ်ပေးထားမှု graph ကို ပြန်ပေးသည်)                                                                                |
| POST   | `/api/v1/management/proxies`                 | Proxy ဖန်တီးရန် — body ကို `createProxyRegistrySchema` ဖြင့် အတည်ပြုစစ်ဆေးသည်                                                                                                                                    |
| PATCH  | `/api/v1/management/proxies`                 | Proxy ကို အပ်ဒိတ်လုပ်ရန် — body ကို `updateProxyRegistrySchema` ဖြင့် အတည်ပြုစစ်ဆေးသည် (`id` လိုအပ်သည်)                                                                                                          |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | Proxy ကို ဖျက်ရန် (သတ်မှတ်ပေးထားမှုများကို ဖြုတ်ရန် `force=1` ကို အသုံးပြုပါ)                                                                                                                                    |
| GET    | `/api/v1/management/proxies/assignments`     | သတ်မှတ်ပေးထားမှုများကို စာရင်းပြုစုရန် — `proxy_id`, `scope`, `scope_id` ဖြင့် စစ်ထုတ်နိုင်သည်၊ ချိတ်ဆက်မှုတစ်ခုအတွက် လက်ရှိအသုံးပြုနေသော proxy ကို ဖြေရှင်းရှာဖွေရန် `resolve_connection_id=<id>` ကို ပေးပို့ပါ |
| PUT    | `/api/v1/management/proxies/assignments`     | သတ်မှတ်ပေးရန် — body ကို `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) ဖြင့် အတည်ပြုစစ်ဆေးသည်။ Dispatcher cache ကို ရှင်းလင်းသည်                                                                       |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | အစုလိုက်သတ်မှတ်ပေးရန် — body ကို `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) ဖြင့် အတည်ပြုစစ်ဆေးသည်                                                                                            |
| GET    | `/api/v1/management/proxies/health?hours=24` | အချိန်ကာလတစ်ခုအတွင်း စုစည်းထားသော proxy အခြေအနေ (အောင်မြင်/မအောင်မြင် အရေအတွက်များ၊ latency)                                                                                                                     |

**အထောက်အထားစိစစ်ခြင်း:** route တိုင်းတွင် စီမံခန့်ခွဲမှု session/API key လိုအပ်သည် (`requireManagementAuth`)။

> လုပ်ဆောင်ချက်ဖော်ပြချက်ရှိ `POST /api/v1/management/proxies/[id]/assignments` နှင့် `POST /api/v1/management/proxies/[id]/health` တို့ကို အထက်တွင်ပြထားသော အပြားပုံစံ `/assignments` နှင့် `/health` route များက ဆောင်ရွက်ပေးသည် — codebase တွင် id တစ်ခုချင်းအလိုက် subroute များ မရှိပါ။

## ခံနိုင်ရည်ရှိမှု (တိုးချဲ့ဖော်ပြချက်)

OmniRoute သည် သီးခြားလွတ်လပ်သော ယာယီချို့ယွင်းမှု ကိုင်တွယ်ရေးယန္တရား သုံးမျိုးကို ပံ့ပိုးထားပါသည်။ အောက်ပါ စီမံခန့်ခွဲမှု endpoint များမှတစ်ဆင့် အော်ပရေတာများသည် ၎င်းတို့၏အခြေအနေကို ဖတ်ရှုနိုင်ပြီး သတ်မှတ်ချက်များကို အစားထိုးပြင်ဆင်နိုင်ပါသည်-

| အတိုင်းအတာ           | အခြေအနေသိုလှောင်မှု                                | ဖတ်ရှုရန်                                 | ပြန်လည်သတ်မှတ်ရန် / ရှင်းလင်းရန်                                            |
| -------------------- | -------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------- |
| Provider breaker     | `domain_circuit_breakers` + မမ်မိုရီအတွင်း         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                                |
| ချိတ်ဆက်မှု cooldown | provider ချိတ်ဆက်မှုများပေါ်ရှိ `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (လိုအပ်ချိန်တွင် ပြန်ဖွင့်ပေးသည်၊ provider PUT မှတစ်ဆင့် ရှင်းလင်းနိုင်သည်) |
| Model lockout        | မမ်မိုရီအတွင်းရှိ model အသုံးပြုနိုင်မှု registry  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                    |

`PATCH /api/resilience` သည် `providerBreaker.oauth` နှင့် `providerBreaker.apikey` အောက်ရှိ provider breaker အစားထိုးသတ်မှတ်ချက်များကို လက်ခံပါသည်။ Profile တစ်ခုစီသည် `degradationThreshold`, `failureThreshold` နှင့် `resetTimeoutMs` တို့ကို ပံ့ပိုးပြီး တူညီသော field များကို Dashboard → ဆက်တင်များ → ခံနိုင်ရည်ရှိမှုတွင်လည်း အသုံးပြုနိုင်ပါသည်။

```bash
# Model lockout တစ်ခုတည်းကို ရှင်းလင်းရန်
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Lockout အားလုံးကို ရှင်းလင်းရန်
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

သဘောတရားဆိုင်ရာ အပြည့်အစုံ ကိုးကားချက်နှင့် breaker မူလသတ်မှတ်ချက်များအတွက် [`CLAUDE.md`](../../CLAUDE.md) → "ခံနိုင်ရည်ရှိမှု Runtime အခြေအနေ" နှင့် [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) ကို ကြည့်ပါ။

### Rate-Limit Queue နှင့် အလိုအလျောက်ဖွင့်ခြင်း ဘေးကင်းရေးယန္တရား

- **ပံ့ပိုးထားသော ရေးသားမှုလမ်းကြောင်း**: Body `{"connectionId": "<id>", "enabled": true|false}` ပါဝင်သော `POST /api/rate-limits` သည် ချိတ်ဆက်မှုတစ်ခု၏ rate-limit ကာကွယ်မှုကို အဖွင့်အပိတ်လုပ်ရန် ပံ့ပိုးထားသည့် စီမံခန့်ခွဲမှု endpoint ဖြစ်ပါသည်။ `PUT /api/providers/[id]` သည် `rateLimitProtection` ကို ရည်ရွယ်ချက်ရှိရှိ ပြင်ဆင်ခြင်း သို့မဟုတ် အဖွင့်အပိတ်လုပ်ခြင်း မပြုပါ (#11278)။
- **`enabled: false` ၏ အဓိပ္ပာယ်**: `enabled: false` သတ်မှတ်ခြင်းသည် ချိတ်ဆက်မှုအတွက် တိတိကျကျ သတ်မှတ်ထားသော ကာကွယ်မှုကို ဖယ်ရှားပေးသော်လည်း လက်ရှိအသုံးပြုနေသော API-key ချိတ်ဆက်မှုကို ကမ္ဘာလုံးဆိုင်ရာ အလိုအလျောက်ဖွင့်ခြင်း ဘေးကင်းရေးယန္တရား (`autoEnableApiKeyProviders = true`) မှ **ဖယ်ထုတ်မပေးပါ**။ `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) တွင် `false` နှင့် `undefined` သည် တူညီပြီး တိတိကျကျ သတ်မှတ်ထားသော ကာကွယ်မှုမရှိသည့် လက်ရှိအသုံးပြုနေသော API-key ချိတ်ဆက်မှုများကို အလိုအလျောက်ဖွင့်ခြင်း ဘေးကင်းရေးယန္တရားက ဆက်လက်ကာကွယ်ထားပါသည်။
- **ကမ္ဘာလုံးဆိုင်ရာ ပိတ်ခြင်း**: Rate-limit queue များမပါဘဲ API-key ချိတ်ဆက်မှုများကို အသုံးပြုရန် `RATE_LIMIT_AUTO_ENABLE=false` (ပတ်ဝန်းကျင်ဆိုင်ရာ သတ်မှတ်ချက်) သို့မဟုတ် `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (ဆက်တင်များ → ခံနိုင်ရည်ရှိမှု / `PATCH /api/resilience`) မှတစ်ဆင့် ဘေးကင်းရေးယန္တရားကို ကမ္ဘာလုံးဆိုင်ရာ ပိတ်ပါ။

## MCP ဆာဗာ

OmniRoute တွင် transport 3 မျိုး (stdio, SSE, streamable-http) နှင့် နယ်ပယ်သတ်မှတ်ထားသော ကိရိယာများပါဝင်သည့် ထည့်သွင်းပေါင်းစပ်ထားသော Model Context Protocol ဆာဗာတစ်ခု ပါရှိသည်။ အောက်ပါ dashboard endpoint များသည် အခြေအနေ/စာရင်းစစ်ဒေတာကို ဖတ်ရှုပြီး HTTP transport များကို proxy ပြုလုပ်သည်။

| နည်းလမ်း | လမ်းကြောင်း | ဖော်ပြချက် |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Heartbeat၊ transport၊ အွန်လိုင်းအခြေအနေ၊ နောက်ဆုံးခေါ်ဆိုမှု၊ ထိပ်တန်းကိရိယာများ၊ 24h အောင်မြင်မှုနှုန်း |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` တို့ပါဝင်သော MCP ကိရိယာများစာရင်း |
| GET | `/api/mcp/sse` | SSE transport အတွက် SSE stream ကို ဖွင့်ခြင်း (MCP ကို ပိတ်ထားလျှင် သို့မဟုတ် transport မကိုက်ညီလျှင် `503` ပြန်ပေးသည်) |
| POST | `/api/mcp/sse` | SSE transport ပေါ်တွင် JSON-RPC frame ပေးပို့ခြင်း |
| GET | `/api/mcp/stream` | Streamable HTTP transport ၏ SSE ဘက်ခြမ်းကို ဖွင့်ခြင်း (ဆာဗာမှ စတင်ပေးပို့သော မက်ဆေ့ချ်များ) |
| POST | `/api/mcp/stream` | Streamable HTTP transport ပေါ်တွင် JSON-RPC frame ပေးပို့ခြင်း |
| DELETE | `/api/mcp/stream` | Streamable HTTP session တစ်ခုကို အဆုံးသတ်ခြင်း |
| GET | `/api/mcp/audit` | စာရင်းစစ်မှတ်တမ်းကို ရှာဖွေခြင်း — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | စုစည်းထားသော စာရင်းစစ်ကိန်းဂဏန်းများ (စုစုပေါင်း၊ အောင်မြင်မှုနှုန်း၊ ပျမ်းမျှကြာချိန်၊ ထိပ်တန်းကိရိယာများ) |

**စစ်မှန်ကြောင်းအတည်ပြုခြင်း:** `sse`/`stream` transport များသည် MCP သီးသန့် စစ်မှန်ကြောင်းအတည်ပြုမှု မျက်နှာပြင် (`mcp` scope ပါသော Bearer API key) ကို လိုက်နာသည်။ `status`/`tools`/`audit*` route များကို dashboard မှ ဖတ်ရှုနိုင်သည် (dashboard host သို့ ရောက်ရှိနိုင်ခြင်းအပြင် ထပ်ဆောင်းစစ်မှန်ကြောင်းအတည်ပြုမှု မလိုအပ်ပါ)။

> HTTP transport နှစ်မျိုးစလုံးကို `settings.mcpEnabled` နှင့် `settings.mcpTransport` တို့ဖြင့် ထိန်းချုပ်ထားသည် — transport မကိုက်ညီပါက `400` ပြန်ပေးပြီး MCP ကို ပိတ်ထားသောအခြေအနေတွင် `503` ပြန်ပေးသည်။

## A2A ဆာဗာ

OmniRoute သည် A2A (Agent-to-Agent) JSON-RPC 2.0 endpoint တစ်ခုနှင့် စစ်ဆေးခြင်း/dashboard အသုံးပြုမှုအတွက် REST wrapper တစ်ခုကို ပံ့ပိုးပေးသည်။

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY သတ်မှတ်ထားခြင်းမရှိပါက ထည့်သွင်းရန်မလိုပါ
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

ပံ့ပိုးထားသော method များ (အားလုံးကို `settings.a2aEnabled` ဖြင့် ထိန်းချုပ်ထားသည်)-

| Method           | ဖော်ပြချက်                                                                     |
| ---------------- | ------------------------------------------------------------------------------ |
| `message/send`   | တစ်ပြိုင်တည်း skill လုပ်ဆောင်မှု၊ `{task, artifacts, metadata}` ကို ပြန်ပေးသည် |
| `message/stream` | အလားတူ skill အစုကို Streaming SSE ဖြင့် လုပ်ဆောင်မှု                           |
| `tasks/get`      | `taskId` ဖြင့် task တစ်ခုကို ရယူသည်                                            |
| `tasks/cancel`   | `taskId` ဖြင့် task တစ်ခုကို ပယ်ဖျက်သည်                                        |

ပါဝင်ပြီးသား skill များ- `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`။

### Agent Card

```bash
GET /.well-known/agent.json
```

အများသုံး A2A agent card (အမည်၊ ဖော်ပြချက်၊ လုပ်ဆောင်နိုင်စွမ်းများ၊ skill catalog၊ auth scheme) ကို ပြန်ပေးသည် — အများသုံးအဖြစ် 1h ကြာ cache လုပ်ထားသည်။ auth မလိုအပ်ပါ။

### REST helper များ

| Method | Path                         | ဖော်ပြချက်                                                                                                                       |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A ဖွင့်ထားမှု + task စာရင်းအင်းများ + cache လုပ်ထားသော agent card အကျဉ်းချုပ်                                                  |
| GET    | `/api/a2a/tasks`             | task များကို စာရင်းပြုစုသည် — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (REST helper အဖြစ် အကောင်အထည်မဖော်ရသေးပါ — JSON-RPC `message/send` မှတစ်ဆင့် ဖန်တီးပါ)                                           |
| GET    | `/api/a2a/tasks/[id]`        | task တစ်ခုကို ရယူသည်                                                                                                             |
| POST   | `/api/a2a/tasks/[id]/cancel` | task တစ်ခုကို ပယ်ဖျက်သည်                                                                                                         |

**Auth:** REST helper များသည် management auth မပါဘဲ အလုပ်လုပ်သည် (dashboard မှ ဖတ်ရှုနိုင်သည်)၊ JSON-RPC `/a2a` route သည် configure လုပ်ထားပါက Bearer `OMNIROUTE_API_KEY` ကို အသုံးပြုသည်။

| Method | Path | ဖော်ပြချက် |
| ------ | ------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------- | ----------------------------------- |
| POST | `/api/cloud/auth` | Bearer key တစ်ခုကို အတည်ပြုပြီး cloud sync client များအတွက် ဖုံးကွယ်ထားသော provider connection များ + model alias များကို ပြန်ပေးသည် |
| POST | `/api/cloud/credentials/update` | cloud နှင့် sync လုပ်ထားသော provider အတွက် encrypt လုပ်ထားသည့် credential များကို အပ်ဒိတ်လုပ်သည် |
| POST | `/api/cloud/model/resolve` | local routing table ကို အသုံးပြု၍ logical model id တစ်ခုကို တိကျသော provider/model အဖြစ် ဖြေရှင်းသည် |
| GET | `/api/cloud/models/alias` | cloud sync သို့ ဖော်ပြထားသည့် model alias များကို စာရင်းပြုစုသည် |
| GET | `/api/assess` | နောက်ဆုံး assessment အမျိုးအစားခွဲခြားမှုများကို ဖတ်ရှုသည် (provider/model တစ်ခုစီအလိုက်) |
| POST | `/api/assess` | assessment တစ်ခုကို လုပ်ဆောင်သည် — body: `{scope: {type:"all"}                                                   | {type:"provider", providerId} | {type:"model", modelId}, trigger?}` |
| GET | `/api/evals` | ပါဝင်ပြီးသား eval suite များ + နောက်ဆုံးလုပ်ဆောင်မှုများကို စာရင်းပြုစုသည် |
| POST | `/api/evals` | eval run တစ်ခုကို စတင်လုပ်ဆောင်သည် |
| POST | `/api/evals/suites` | စိတ်ကြိုက် eval suite တစ်ခုကို ဖန်တီးသည် — body ကို `evalSuiteSaveSchema` ဖြင့် အတည်ပြုသည် |
| GET | `/api/evals/suites/[id]` | စိတ်ကြိုက် eval suite တစ်ခုကို ရယူသည် |

**Auth:** `/api/cloud/auth` သည် Bearer key တစ်ခုကို တိုက်ရိုက်အတည်ပြုပြီး `manage` / `admin` scope ပါသော key အတွက်သာ connection တစ်ခုစီ၏ ဖုံးကွယ်ထားသော key နှင့် `projectId` ကို ပြန်ပေးသည်။ အခြား `/api/cloud/*`, `/api/evals/*` နှင့် `/api/assess` route များသည် management session/API key လိုအပ်သည်။ `/api/assess` POST သည် discriminated-union scope schema ပါသော `validateBody` ကို အသုံးပြုသည်။

## ACP (Agent Client Protocol) စီမံခန့်ခွဲမှု

child process များအဖြစ် လုပ်ဆောင်ပါသည်။ ဤ endpoint များသည် ACP agent ရှာဖွေခြင်းနှင့် စိတ်ကြိုက် agent မှတ်ပုံတင်ခြင်းတို့ကို စီမံခန့်ခွဲသည်။

| Method | Path              | Description                                                                                                                                                                                        |
| ------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | သိရှိထားသော CLI agent အားလုံးကို (built-in + custom) ထည့်သွင်းထားမှုအခြေအနေ၊ version နှင့် binary တို့နှင့်အတူ စာရင်းပြုစုသည်                                                                      |
| POST   | `/api/acp/agents` | စိတ်ကြိုက် ACP agent တစ်ခုကို မှတ်ပုံတင်သည် သို့မဟုတ် cache ကို ပြန်လည်ဆန်းသစ်သည် — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` သို့မဟုတ် `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | စိတ်ကြိုက် ACP agent တစ်ခုကို ဖယ်ရှားသည် — query parameter: `?id=<agentId>`                                                                                                                        |

**တုံ့ပြန်မှု နမူနာ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**စစ်မှန်ကြောင်းအတည်ပြုခြင်း:** စီမံခန့်ခွဲမှု session (dashboard `auth_token` cookie) သို့မဟုတ်
စီမံခန့်ခွဲမှု scope ပါရှိသော API key လိုအပ်သည်။

အသေးစိတ်အချက်အလက်အပြည့်အစုံအတွက် [ACP Framework](../frameworks/ACP.md) ကို ကြည့်ပါ။

## ခွဲခြမ်းစိတ်ဖြာမှုနှင့် စောင့်ကြည့်နိုင်စွမ်း

## စစ်မှန်ကြောင်းအတည်ပြုခြင်း

အထောက်အထားအမျိုးအစား လေးမျိုး (dashboard session၊ local CLI token၊ `oma_live_…` Access
Token၊ manage-scoped API key) နှင့် ၎င်းတို့က inference key များနှင့် မည်သို့ကွာခြားသည်ကို သိရှိရန်
[စီမံခန့်ခွဲမှုဆိုင်ရာ စစ်မှန်ကြောင်းအတည်ပြုခြင်း](../guides/MANAGEMENT-AUTH.md) ကို ကြည့်ပါ။

- Dashboard route များ (`/dashboard/*`) သည် `auth_token` cookie ကို အသုံးပြုသည်
- Login ဝင်ရာတွင် သိမ်းဆည်းထားသော password hash ကို အသုံးပြုပြီး၊ မရရှိပါက `INITIAL_PASSWORD` ကို အစားထိုးအသုံးပြုသည်
- `requireLogin` ကို `/api/settings/require-login` မှတစ်ဆင့် ဖွင့်/ပိတ်နိုင်သည်
- `REQUIRE_API_KEY=true` ဖြစ်သည့်အခါ `/v1/*` route များသည် Bearer API key ကို လိုအပ်နိုင်သည်
- ဤကိုးကားချက်ရှိ "စီမံခန့်ခွဲမှု token" / "စီမံခန့်ခွဲမှုနယ်ပယ်သတ်မှတ်ထားသော API key" ဆိုသည်မှာ အဆိုပါလမ်းညွှန်ရှိ အမျိုးအစားများထဲမှ တစ်မျိုးကို ဆိုလိုခြင်းဖြစ်ပြီး—သတ်မှတ်မထားသည့် ထပ်ဆောင်း secret အမျိုးအစားကို မဆိုလိုပါ

> **လိုက်ဖက်ညီမှုကို ချိုးဖောက်သော ပြောင်းလဲမှု (v3.8.0)** — `/api/v1/agents/tasks/*` နှင့် cooldown စီမံခန့်ခွဲမှု endpoint များသည် ယခုအခါ **စီမံခန့်ခွဲမှုဆိုင်ရာ စစ်မှန်ကြောင်းအတည်ပြုမှု** (dashboard `auth_token` cookie သို့မဟုတ် စီမံခန့်ခွဲမှုနယ်ပယ်သတ်မှတ်ထားသော API key) ကို လိုအပ်သည်။ ယခင်က ဤ route များကို စစ်မှန်ကြောင်းအတည်ပြုမှုမရှိဘဲ ခေါ်ဆိုခဲ့သည့် client များသည် `401 Unauthorized` ကို လက်ခံရရှိမည်ဖြစ်သည်။ commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) ကို ကြည့်ပါ။
