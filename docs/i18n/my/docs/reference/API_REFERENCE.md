OmniRoute API အတွက် အဓိကရည်ညွှန်းစာတမ်း ဖြစ်သည်။ အများပြည်သူအသုံးပြုနိုင်သော `/v1` မျက်နှာပြင်နှင့် အသုံးများဆုံး စီမံခန့်ခွဲမှု endpoint များကို ဖော်ပြထားပြီး၊ စက်ဖြင့်ဖတ်ရှုနိုင်သော [`docs/openapi.yaml`](../openapi.yaml) နှင့် `src/app/api/` အောက်ရှိ route tree တို့သည် အပြည့်စုံဆုံး အရင်းအမြစ်များ ဖြစ်သည်။

OpenAI နှင့် ကိုက်ညီသော protocol နှင့် provider စွမ်းဆောင်ရည် matrix အတွက် သီးသန့်ရည်ရွယ်ထားသော ရည်ညွှန်းချက်ကို ကြည့်ရန်
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md) ကို ကြည့်ပါ။

Deployment တစ်ခုစီသည် build ပြုလုပ်စဉ် `docs/openapi.yaml` မှ ထုတ်လုပ်ထားသော spec မိတ္တူကို `/openapi.yaml` တွင် ကိုယ်ပိုင်ပေးဆောင်သည်။ ၎င်းတွင် build ၏ version နှင့် relative server URL (`./`) ပါဝင်သောကြောင့် request များသည် စာရွက်စာတမ်းကို ပေးဆောင်ခဲ့သော host ပေါ်တွင်သာ ဆက်လက်ရှိနေသည်။ ဒေါင်းလုဒ်လုပ်ထားသောဖိုင်ကို import ပြုလုပ်သည့် tool တွင် ထိုကဲ့သို့သော host မရှိသဖြင့် base URL ကို ကိုယ်တိုင် သတ်မှတ်ပေးရန် လိုအပ်သည်။

## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### စိတ်ကြိုက် Headers

| Header                   | Direction     | Description                                                                                                                                                                                                                                                           |
| ------------------------ | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | တောင်းဆိုချက် | Cache ကိုကျော်လွှားရန် `true` သို့ သတ်မှတ်ပါ                                                                                                                                                                                                                          |
| `x-omniroute-no-memory`  | တောင်းဆိုချက် | ဤတောင်းဆိုချက်အတွက် memory + skills injection ကို ကျော်ရန် `true` သို့ သတ်မှတ်ပါ (no-cache နှင့် တူညီပြီး ခေါ်ဆိုမှုတစ်ကြိမ်ချင်းစီအလိုက် token/cost overhead ကို ရှောင်ရှားပေးသည်)                                                                                   |
| `X-OmniRoute-Progress`   | တောင်းဆိုချက် | တိုးတက်မှုဖြစ်ရပ်များအတွက် `true` သို့ သတ်မှတ်ပါ                                                                                                                                                                                                                      |
| `X-Session-Id`           | တောင်းဆိုချက် | ပြင်ပ session affinity အတွက် ကပ်လျက်အသုံးပြုမည့် session key                                                                                                                                                                                                          |
| `x_session_id`           | တောင်းဆိုချက် | Underscore ပါသော မူကွဲကိုလည်း လက်ခံသည် (တိုက်ရိုက် HTTP)                                                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | တောင်းဆိုချက် | ခေါ်ဆိုသူက ပေးသည့် session/conversation tag (memory သို့လည်း ထည့်သွင်းပေးသည်)။ ရှိပါက session တစ်ခုချင်းစီအလိုက် ကုန်ကျစရိတ်ခွဲခြမ်းသတ်မှတ်ရန် `call_logs.session_tag` သို့ မူရင်းအတိုင်း သိမ်းဆည်းသည် (#8249) — မရှိပါက မည်သည့်အရာကိုမျှ အလိုအလျောက်ဖန်တီးမည်မဟုတ်ပါ |
| `Idempotency-Key`        | တောင်းဆိုချက် | ထပ်နေသောတောင်းဆိုချက်များကို ဖယ်ရှားရန် key (5s ကြာချိန်)                                                                                                                                                                                                             |
| `X-Request-Id`           | တောင်းဆိုချက် | အခြား dedup key                                                                                                                                                                                                                                                       |
| `x-omniroute-connection` | တောင်းဆိုချက် | single-model တောင်းဆိုချက်တစ်ခုကို provider connection (account) တစ်ခုတည်းသို့ ၎င်း၏ id ဖြင့် ချိတ်ထားရန် — [တောင်းဆိုချက်တစ်ခုချင်းစီအလိုက် Account pinning](#account-pinning-per-request) ကို ကြည့်ပါ                                                               |
| `X-OmniRoute-Cache`      | တုံ့ပြန်ချက်  | `HIT` သို့မဟုတ် `MISS` (streaming မဟုတ်သော)                                                                                                                                                                                                                           |
| `X-OmniRoute-Idempotent` | တုံ့ပြန်ချက်  | deduplicate ပြုလုပ်ထားပါက `true`                                                                                                                                                                                                                                      |
| `X-OmniRoute-Progress`   | တုံ့ပြန်ချက်  | progress tracking ဖွင့်ထားပါက `enabled`                                                                                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | တုံ့ပြန်ချက်  | OmniRoute က အသုံးပြုသည့် အကျိုးသက်ရောက်သော session ID                                                                                                                                                                                                                 |
| `X-OmniRoute-Request-Id` | တုံ့ပြန်ချက်  | တောင်းဆိုချက်ဆက်စပ်မှု id (သိရှိပါက)                                                                                                                                                                                                                                  |
| `X-OmniRoute-Version`    | တုံ့ပြန်ချက်  | OmniRoute build version (အမြဲရှိသည်)                                                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | တုံ့ပြန်ချက်  | cache က HIT ဖြစ်သောအခါ ရှောင်ရှားပေးခဲ့သည့် USD ပမာဏ (cache hits များအတွက်သာ)                                                                                                                                                                                         |
| `X-OmniRoute-Decision`   | တုံ့ပြန်ချက်  | Routing trace: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` သည် combo strategy ဖြစ်ပြီး combo မဟုတ်သော တောင်းဆိုချက်အတွက် `single` ဖြစ်သည်) — ပြီးဆုံးမှုတုံ့ပြန်ချက်များတွင် အမြဲရှိသည်                                                             |

> Nginx မှတ်ချက် — underscore ပါသော header များ (ဥပမာ `x_session_id`) ကို အသုံးပြုပါက `underscores_in_headers on;` ကို ဖွင့်ထားပါ။

#### တောင်းဆိုချက်တစ်ခုချင်းစီအလိုက် Account pinning

Provider တစ်ခုတွင် connection (account သို့မဟုတ် key) များစွာရှိပါက OmniRoute သည် ပုံမှန်အားဖြင့် ၎င်း၏ account-selection strategy မှတစ်ဆင့် တစ်ခုကို ရွေးချယ်သည်။ ထိုအစား တောင်းဆိုချက်တစ်ခုသည် `x-omniroute-connection` header ဖြင့် သီးခြား connection တစ်ခုကို pin ပြုလုပ်နိုင်သည် —

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id ကို ဘယ်မှာရှာရမလဲ။** ဒက်ရှ်ဘုတ်ရှိ ပံ့ပိုးသူစာမျက်နှာကို ဖွင့်ပါ
  (**ဒက်ရှ်ဘုတ် → ပံ့ပိုးသူများ → <provider>**)၊ ထို့နောက် ချိတ်ဆက်မှုအတန်းရှိ `xxxxxxxx…` id ချစ်ပ်ကို
  နှိပ်ပါ — ၎င်းက ချိတ်ဆက်မှု id အပြည့်အစုံကို ကူးယူပေးပါမည်။
- **မည်သည့် request များက ၎င်းကို လိုက်နာသနည်း။** `/v1/chat/completions`၊
  `/v1/messages` နှင့် `/v1/responses` ပေါ်ရှိ မော်ဒယ်တစ်ခုတည်းအသုံးပြုသော request များ
  (`provider/model`) ဖြစ်သည်။ Combo များက header ကို လျစ်လျူရှုသည် — combo အဆင့်တစ်ခုချင်းစီအတွက်
  ထိုအဆင့်၏ကိုယ်ပိုင် connection မှတစ်ဆင့် account တစ်ခုကို သတ်မှတ်ပါ။
- **Pin သည် preference မဟုတ်ဘဲ တိကျစွာ သတ်မှတ်ထားခြင်းဖြစ်သည်။** Pin လုပ်ထားသော connection ကိုသာ
  သီးသန့်အသုံးပြုသည်။ Request အတွင်း အမှားတစ်ခုဖြစ်ပါက account ၏ cooldown ကို မှတ်တမ်းတင်သော်လည်း
  တူညီသော provider ၏ အခြား account သို့ ပြောင်းလဲအသုံးမပြုပါ။
- **Cooldown နှင့် quota ကြောင့် pin ကို ဖြေလျှော့ပေးသည်။** Pin လုပ်ထားသော connection သည် cooldown
  ဖြစ်နေချိန်၊ quota ကုန်ဆုံးနေချိန် သို့မဟုတ် quota policy ကြောင့် ပိတ်ပင်ခံထားရချိန်တွင် နောက်ပိုင်း
  request များသည် provider ၏ အခြား connection များသို့ ပြန်လည်လမ်းကြောင်းပြောင်းသွားမည်ဖြစ်ပြီး၊
  pin မလုပ်ထားသော traffic နှင့် အတိအကျတူညီသည်။
- **မသိရှိသော သို့မဟုတ် ပိတ်ထားသော id များသည် အမှားဖြစ်စေသည်။** Provider ၏ active pool ထဲတွင်
  မရှိသော id (ဖျက်ထားခြင်း၊ deactivate လုပ်ထားခြင်း သို့မဟုတ် အခြား provider တစ်ခုနှင့် သက်ဆိုင်ခြင်း)
  ဖြစ်ပါက အသုံးပြုနိုင်သော account မရှိတော့သဖြင့် request သည် အခြားနေရာသို့ တိတ်တဆိတ်
  လမ်းကြောင်းမပြောင်းဘဲ အမှားဖြင့် ပျက်ကွက်မည်ဖြစ်သည်။

Claude Code သည် custom headers များကို `ANTHROPIC_CUSTOM_HEADERS` မှတစ်ဆင့် ပေးပို့သည်။ ၎င်းကို
`~/.claude/settings.json` ၏ `env` block ထဲတွင် ထည့်ပါ၊ သို့မဟုတ် project တစ်ခုချင်းစီအတွက်
မတူညီသော account ကို pin လုပ်ရန် project-level `.claude/settings.json` ထဲတွင် ထည့်ပါ။

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ရင်းမြစ်: `src/sse/handlers/chat.ts` (header ဖတ်ရှုခြင်း)၊ `src/sse/services/auth.ts` နှင့်
`src/sse/services/sessionAffinityPin.ts` (pin ဖြေလျှော့ခြင်းနှင့် pool ထဲမှ ပျောက်ဆုံးနေမှု စစ်ဆေးခြင်း)။

> **ကုန်ကျစရိတ် telemetry headers:** streaming မဟုတ်သော အောင်မြင်သည့် response များတွင်လည်း
> `X-OmniRoute-*` ကုန်ကျစရိတ် telemetry အစု ပါဝင်သည် — `X-OmniRoute-Response-Cost` (USD၊
> ဒဿမ 10 နေရာအထိ ပုံသေ; အခမဲ့/စျေးနှုန်းမသတ်မှတ်ထားပါက `0.0000000000`)၊
> `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`၊ `X-OmniRoute-Model`၊
> `X-OmniRoute-Provider`၊ `X-OmniRoute-Latency-Ms`၊ `X-OmniRoute-Cache-Hit` နှင့်
> `X-OmniRoute-Fallback-Attempts` (`> 0` ဖြစ်သည့်အခါမှသာ)၊ ထို့အပြင်
> `X-OmniRoute-Request-Id` နှင့် `X-OmniRoute-Version` တို့ ဖြစ်သည်။ ၎င်းတို့ကို chat completions၊
> `/v1/responses`၊ `/v1/messages` နှင့် **media endpoints** များ — `/v1/embeddings`၊
> `/v1/images/generations`၊ `/v1/audio/speech`၊ `/v1/audio/transcriptions`၊ `/v1/rerank`၊
> `/v1/videos/generations`၊ `/v1/music/generations` နှင့် `/v1/moderations` (အမြဲတမ်း ကုန်ကျစရိတ်
> `0`) — အားလုံးတွင် ထုတ်ပေးသည်။ Media ကုန်ကျစရိတ်ကို စျေးနှုန်းရရှိပါက modality တစ်ခုချင်းစီအလိုက်
> (ပုံတစ်ပုံလျှင်၊ စက္ကန့်တစ်စက္ကန့်လျှင်၊ အက္ခရာတစ်လုံးလျှင်၊ search-unit တစ်ခုလျှင်) တွက်ချက်ပြီး၊
> မရရှိပါက `0` (fail-open) ဖြစ်သည်။

> **Cache-hit ကုန်ကျစရိတ် အဓိပ္ပာယ်ဖွင့်ဆိုချက်:** semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`)
> ဖြစ်သည့်အခါ upstream call ပြုလုပ်ခြင်း မရှိသဖြင့် `X-OmniRoute-Response-Cost` သည်
> `0.0000000000` (hit ကို ဝန်ဆောင်မှုပေးရန် လိုအပ်သော **incremental** ကုန်ကျစရိတ်) ဖြစ်သည်။
> မူလကုန်ကျစရိတ်/ဖြစ်လာနိုင်သည့်ကုန်ကျစရိတ်ကို `X-OmniRoute-Cost-Saved` တွင် သီးခြားဖော်ပြသည်။
> Billing consumer များသည် `X-OmniRoute-Response-Cost` ကို စုစုပေါင်းတွက်သင့်သည် (hit များသည်
> ကုန်ကျစရိတ်မရှိပါ); cache analytics သည် `X-OmniRoute-Cost-Saved` ကို စုစည်းနိုင်သည်။

## သီးသန့် စီမံထားသော Session Lease များ

သီးသန့် စီမံထားသော session leasing သည် ရွေးချယ်အသုံးပြုနိုင်ပြီး client အမျိုးအစားမရွေး အသုံးပြုနိုင်သော routing စာချုပ်တစ်ရပ်ဖြစ်သည်။ ၎င်းတွင် လက်ရှိပိုင်ရှင်တစ်ဦးက အရည်အချင်းပြည့်မီသော OmniRoute connection တစ်ခုကို ကိုင်ထားသည်။ ၎င်းသည် model တစ်ခုကို lease လုပ်ခြင်းမဟုတ်သလို OAuth လိုအပ်ခြင်း၊ သီးခြား client တစ်ခုကို ခွဲခြားသတ်မှတ်ခြင်း၊ သို့မဟုတ် provider တစ်ခုကို သတ်မှတ်ထားရန် လိုအပ်ခြင်းလည်း မရှိပါ။

အထောက်အထားစစ်ဆေးသည့် API key တွင် scope `lease:exclusive` နှင့် အလွတ်မဟုတ်သော `allowedConnections` list တစ်ခုကို တိတိကျကျ သတ်မှတ်ထားရမည်။ Database mutation boundary သည် key ဖန်တီးချိန်နှင့် partial update ပြုလုပ်ချိန်တို့တွင် field နှစ်ခုလုံးကို အတူတကွ အတည်ပြုသည်။

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

အောင်မြင်သော acquire၊ renew နှင့် release response များတွင် timestamp များ၊ `state` နှင့် အတိအကျ အပြုသဘောဆောင်သော `generation` တန်ဖိုးတို့ ပါဝင်သော်လည်း ရွေးချယ်ထားသော connection သို့မဟုတ် credential များကို မဖော်ပြပါ။ Renew နှင့် release တို့တွင် generation ကို JSON body ထဲ ပေးရမည်။

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

လက်ရှိ lease ပိုင်ရှင်သည် ၎င်း၏ လက်ရှိ binding အတွက် privacy-safe display metadata ကို အတိအလင်း တောင်းဆိုနိုင်သည်။

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ဤရွေးချယ်အသုံးပြုနိုင်သော status action ကို opaque owner၊ အထောက်အထားစစ်ဆေးပြီးသော managed API key နှင့် တိကျသော active generation တို့ဖြင့် database transaction တစ်ခုတည်းအတွင်း ကာကွယ်ထားသည်။ `displayName` သည် ပြင်ဆင်သတ်မှတ်ထားသော connection name ကို trim လုပ်ထားသည့် တန်ဖိုးသာဖြစ်ပြီး၊ လုံခြုံစိတ်ချရသော configured name မရှိပါက `null` ဖြစ်သည်။ OmniRoute သည် email သို့မဟုတ် အလိုအလျောက်ဖန်တီးထားသော account identity ကို အစားထိုးအသုံးမပြုပါ။ Provider တန်ဖိုးသည် အထိခိုက်မခံသော display label တစ်ခုဖြစ်ပြီး အလိုအလျောက်ဖန်တီးထားသော compatible-provider identifier မဟုတ်ပါ။ Credential များ၊ token များ၊ cookie များ၊ raw connection သို့မဟုတ် API key id များ၊ owner hash များ၊ fencing secret များနှင့် internal routing data များကို ဖယ်ရှားထားသည်။

မှားယွင်းသော key၊ မှားယွင်းသော owner၊ ခေတ်မမီတော့သော generation၊ မရှိခြင်း၊ သက်တမ်းကုန်ခြင်း၊ release လုပ်ပြီးခြင်းနှင့် invalidated lookup များအားလုံးသည် connection metadata မပါဘဲ တူညီသော `409 LEASE_FENCE_STALE` error ကို ပြန်ပေးသည်။ Capacity-wait response ကို လက်ခံရရှိသည့် client တွင် စစ်ဆေးရန် active binding မရှိပါ။ Routing က active lease တစ်ခုကို ပြောင်းလဲသောအခါ generation တစ်ခုတည်းက ဆက်လက်အကျုံးဝင်ပြီး status သည် binding အသစ်ကို atomically ပြန်ပေးသည်၊ အဟောင်းကို မည်သည့်အခါမျှ မပြန်ပေးပါ။ Acquire၊ renew၊ release နှင့် waiting response များသည် ယခင်ပုံစံများအတိုင်း ဆက်လက်ရှိနေသောကြောင့် လက်ရှိ client များကို ပြောင်းလဲရန် မလိုပါ။

ဤ server contract သည် stock OpenAI Codex `/status` ကို မပြောင်းလဲပါ။ Stock Codex သည် လက်ရှိတွင် ၎င်း၏ model provider နှင့် built-in authentication/account state ကို ပြသသော်လည်း မိမိစိတ်ကြိုက် provider account metadata များကို ပြသခြင်းမရှိပါ။ နောက်ပိုင်း client integration တစ်ခုသည် ဤ action ကို ခေါ်ယူပြီး `connection.displayName` ကို မည်သို့ ပြသမည်ကို ဆုံးဖြတ်ရမည်။

ထို့နောက် managed inference request တစ်ခုစီတွင် control header နှစ်ခုလုံးကို ပေးပို့ရမည်။

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

အထောက်အပံ့ပေးထားသော upstream attempt တစ်ခုစီ မပြုလုပ်မီ owner အတိအကျ၊ generation၊ active connection နှင့် အထောက်အထားစစ်ဆေးပြီးသော API key တို့ကို ချက်ချင်း fence လုပ်သည်။ Owner နှင့် generation ကို အခြား key တစ်ခုဖြင့် ပြန်လည်အသုံးပြုပါက ထို key သည် တူညီသော connection ကို ခွင့်ပြုထားသော်လည်း မအောင်မြင်ပါ။ Raw owner များကို သိမ်းဆည်းခြင်း၊ log မှတ်တမ်းတင်ခြင်း၊ ထိန်းသိမ်းထားခြင်း၊ request snapshot ထဲ ထည့်သွင်းခြင်း သို့မဟုတ် upstream သို့ ပေးပို့ခြင်း မပြုပါ။

ယာယီ contention ဖြစ်ပါက HTTP `429` နှင့် `Retry-After` တို့ကို အောက်ပါတို့နှင့်အတူ ပြန်ပေးသည်။

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ဤ response သည် သာမန်အရည်အချင်းပြည့်မီသော set တွင် member ရှိပြီး free candidate အားလုံးကို အခြား active lease တစ်ခုက ကိုင်ထားသည်ဟုသာ ဆိုလိုသည်။ Unsupported model/provider များ၊ policy mismatch၊ cooldown၊ quota၊ health နှင့် အခြားသာမန် eligibility ပျက်ကွက်မှုများသည် ရှိပြီးသား OmniRoute response များအတိုင်း ဆက်လက်ရှိမည်။

### `x-omniroute-compression`

Request တစ်ခုချင်းစီအတွက် compression plan ကို override ပြုလုပ်သည်။ ဦးစားပေးအမြင့်ဆုံးဖြစ်ပြီး routing-combo override၊ active profile၊ auto-trigger နှင့် panel `Default` တို့ထက် ဦးစားပေးသည်။ တန်ဖိုးများမှာ—

| Value         | Effect                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | ဤ request အတွက် compression မပြုလုပ်ပါ။                                                                                           |
| `default`     | Panel မှ ဆင်းသက်လာသော `Default` profile ကို အသုံးပြုသည် (active profile ကို လျစ်လျူရှုသည်)။ Lossy engine များကို ပိတ်ထားသည်။      |
| `safe`        | Dedup နှင့် whitespace folding ကိုသာ ပြုလုပ်သည်။                                                                                  |
| `allow-lossy` | Summaries နှင့် style rewrites အပါအဝင် ဤ request အတွက် operator plan ကို ဆက်လက်အသုံးပြုသည်။                                       |
| `engine:<id>` | ဖွင့်ထားသော engine တစ်ခုတည်းကို အသုံးပြုသည်၊ ဥပမာ `engine:rtk`။ ထို engine အတွက် request တစ်ခုချင်းစီ opt-in ပြုလုပ်ခြင်းဖြစ်သည်။ |
| `<combo>`     | အမည်ပေးထားသော combo တစ်ခုကို အမည်ဖြင့် (စာလုံးအကြီးအသေးမခွဲခြားဘဲ) ဦးစွာကိုက်ညီစေပြီး ထို့နောက် id ဖြင့် ကိုက်ညီစေသည်။            |

မှတ်ချက်များ—

- မသိသောတန်ဖိုးများကို လျစ်လျူရှုသည် (request ကို မည်သည့်အခါမျှ reject မလုပ်ပါ)။ Resolution သည် ပုံမှန် operator precedence အတိုင်း ဆက်လက်လုပ်ဆောင်သည်။
- Combo အများအပြားတွင် အမည်တူရှိပါက deterministic match ရရှိရန် combo **id** ကို ပေးပို့ပါ။
- အမည်မှာ `off` သို့မဟုတ် `default` ဖြစ်သော combo ကို အမည်ဖြင့် ရွေးချယ်၍ မရပါ (`off` နှင့် `default` keyword များကို ဦးစွာ အဓိပ္ပာယ်ဖွင့်ဆိုသည်)။ ထိုသို့သော combo ကို ၎င်း၏ id ဖြင့် ကိုးကားပါ။
- Master compression switch သည် hard gate ဖြစ်သည်။ Compression ကို global အနေဖြင့် ပိတ်ထားပါက ဤ header သည် ၎င်းကို ပြန်ဖွင့်၍ မရပါ။

အသုံးချထားသော plan ကို response header ထဲတွင် ပြန်လည်ထည့်သွင်းပေးသည်။

```
X-OmniRoute-Compression: <mode>; source=<source>
```

`<source>` သည် `request-header`၊ `routing-override`၊ `active-profile`၊ `auto-trigger`၊ `default` သို့မဟုတ် `off` တစ်ခုခု ဖြစ်သည်။

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ရရှိနိုင်သော provider များမှာ Nebius၊ OpenAI၊ Mistral၊ Together AI၊ Fireworks၊ NVIDIA၊ **OpenRouter** နှင့် Jina AI တို့ဖြစ်သည်။

Catalog id များသည် `provider/model` ပုံစံဖြစ်သည် (ဥပမာ - `jina-ai/jina-embeddings-v5-omni-small`)။ Registry တွင်ပါဝင်သော bare Jina model id များ (ဥပမာ - `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ကိုလည်း resolve လုပ်နိုင်သည်။ Jina embed/rerank/classify/segment များသည် dashboard `jina-ai` credentials ကို ဦးစားပေးအသုံးပြုသည်။ Dashboard key မရှိသည့်အခါမှသာ `JINA_AI_API_KEY` ကို fallback အဖြစ် အသုံးပြုသည်။ `jina-reader` card သည် Reader / `r.jina.ai` အတွက်သာဖြစ်ပြီး (`POST /v1/web/fetch`) embeddings သို့မဟုတ် rerank ကို မဆောင်ရွက်ပေးပါ။

Multimodal support ကို ကြော်ငြာထားသော registry model များသည် provider-neutral structured
item ၃၂ ခုအထိကိုလည်း လက်ခံသည်။ Media item type များမှာ `text`၊ `image`၊ `audio`၊ `video` နှင့် `document`
တို့ဖြစ်သည်။ ၎င်းတို့၏ media `source` သည် `{"type":"url","url":"https://..."}` သို့မဟုတ်
`{"type":"base64","data":"...","media_type":"..."}` ဖြစ်နိုင်သည်။

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
နှင့် family alias `jina-ai/jina-embeddings-v5-omni` → omni-small) သည် Jina ၏ native
EmbeddingsV5Request docs ကိုလည်း လက်ခံပြီး **၎င်းတို့ကို မပြောင်းလဲဘဲ**
`https://api.jina.ai/v1/embeddings` သို့ forward လုပ်သည်။

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Native `{ image | audio | video | pdf }` value များသည် public HTTPS URL၊ `data:` URI သို့မဟုတ် raw
base64 ဖြစ်နိုင်သည်။ OmniRoute သည် ထို object များကို string အဖြစ်ပြောင်းလဲခြင်း သို့မဟုတ် native image URL များကို fetch လုပ်ခြင်းမရှိပါ — Jina ကိုယ်တိုင်က public media ကို ရယူသည်။
Jina ၏ အပို field များ (`task`, `normalized`, `truncate`, `embedding_type`) ကို forward လုပ်သည်။
Text-only Jina SKU များသည် non-text docs များကို ဆက်လက်ငြင်းပယ်သည်။

လုံခြုံရေးနှင့် transport ကန့်သတ်ချက်များ -

- Remote media URL များသည် public HTTPS ဖြစ်ရမည်။ Canonical `{type,source:url}` item များကို server-side တွင် fetch လုပ်ပြီး
  (redirect revalidation၊ timeout၊ size limit၊ public DNS၊ connection pinning) provider call မပြုမီ
  inlined လုပ်သည်။ Jina-native `{image:"https://..."}` item များကို တူညီသော public-HTTPS စစ်ဆေးမှု ပြုလုပ်ပြီးနောက်
  မပြောင်းလဲဘဲ forward လုပ်သည်။ URL ကို Jina က fetch လုပ်သည်။
- Inline base64 media သည် item တစ်ခုလျှင် decoded 8 MiB အထိ၊ request တစ်ခုလုံးတွင် decoded 16 MiB အထိသာ ခွင့်ပြုသည်။

Provider ဘာသာပြန်ခြင်း (canonical item များကို မည်သည့်အခါမျှ မပြောင်းလဲဘဲ forward မလုပ်ပါ) -

- Jina multimodal model များတွင် top-level item တစ်ခုစီသည် data URI ကိုအသုံးပြုသည့် modality-keyed object
  (`text` / `image` / `audio` / `video` / `pdf`) တစ်ခုစီအဖြစ် ပြောင်းလဲသွားသည်။ top-level item တစ်ခုလျှင်
  vector တစ်ခုစီ ရရှိသည်။
- Gemini Embedding 2 family တွင် top-level array တစ်ခုလုံးသည် `content.parts` (`text` သို့မဟုတ် `inline_data`) ပါဝင်သော
  native `models/{model}:embedContent` request တစ်ခုတည်း ဖြစ်လာသည်။
- llama.cpp (`llama-cpp/<model>`၊ local server က load လုပ်ထားသော မည်သည့် model မဆို) တွင် canonical `text` item များကို
  plain string များအဖြစ် ပြောင်းလဲပြီး `image` / `audio` / `video` တို့ကို တစ်ခုစီအတွက်
  `{"content": [part]}` object တစ်ခုစီအဖြစ် ပြောင်းလဲသည်။ ၎င်းတို့သည် inline data ပါဝင်သော llama-server ၏ chat content part
  (`image_url`၊ `input_audio` နှင့် format `wav` / `mp3` / `flac`၊ `input_video`) များကို အသုံးပြုသည်။ top-level item တစ်ခုလျှင်
  vector တစ်ခုစီ ရရှိသည်။ Server ကို `--embedding --mmproj …` ဖြင့် run ထားရမည်။ projector မရှိပါက media ကိုယ်တိုင်က
  ငြင်းပယ်မည်ဖြစ်သည်။ `document` ကို support မလုပ်ပါ။
- Explicit modality metadata မရှိသော unknown/dynamic model များသည် structured input ကို HTTP 400 ဖြင့် ငြင်းပယ်သည်။

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

မကိုက်ညီသော model/modality ပေါင်းစပ်မှုများသည် item ကို အတင်းအကျပ်ပြောင်းလဲမည့်အစား HTTP 400 ပြန်ပေးသည်။ Legacy string/token request များတွင် input မဟုတ်သော
extension field များကို မပြောင်းလဲဘဲ ဆက်လက် pass through လုပ်သည်။

```bash
# Embedding model အားလုံးကို စာရင်းပြုစုရန်
GET /v1/embeddings
```

## ရုပ်ပုံမျိုးဆက်

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ရနိုင်သောဝန်ဆောင်မှုပေးသူများတွင် OpenAI (GPT Image 2) ၊ xAI (Grok Image ) ၊ Together AI (FLUX) ၊ Fireworks AI၊ Nebius (FLUX) ၊ ဟိုက်ပါလစ်၊ NanoBanana၊**OpenRouter** ၊**ZenMux** , SD WebUI (ဒေသခံ), ComfyUI (ဒေသခံ).

`n` `n` ပုံများကို `data[]` တွင် ပြန်ပေးသည်။ ခေါ်ဆိုမှုတစ်ခုလျှင် API အထက်ပိုင်းတွင် တစ်ပုံတစ်ပုံပြန်ပေးသည့် ဝန်ဆောင်မှုပေးသူများသည် (Black Forest Labs၊ Stability AI၊ Leonardo၊ Ideogram၊ Haiper၊ Hyperbolic၊ Magnific/Freepik၊ NVIDIA NIM၊ Cloudflare Workers AI) `n` သီးခြားအထက်ရေခေါ်ဆိုမှုများ၊ ပျံသန်းမှုတွင် အများဆုံး 4 ခု ရရှိသည်။ ပုံသေ `seed` ခေါ်ဆိုမှုအညွှန်း (`seed`, `seed + 1`, … ) ဖြင့် နှိမ်ထားသောကြောင့် ပုံများသည် ကွဲပြားသော်လည်း မျိုးပွားနိုင်သည်။ `n` 10 တွင် ကန့်သတ်ထားသည်။ ခေါ်ဆိုမှု ပျက်ကွက်ပါက တောင်းဆိုချက်တစ်ခုလုံး ပျက်ကွက်သည်။ fan-out ဖော်မတ်များစာရင်းသည် `open-sse/handlers/imageGeneration/fanOut.ts` တွင် `SINGLE_IMAGE_FANOUT_FORMATS` ဖြစ်သည်။

ZenMux ရှိပြီးသား API-ကီးချိတ်ဆက်မှုကို ပြန်လည်အသုံးပြုပြီး `zenmux/` သို့မဟုတ် `zm/` ရှေ့ဆက်များကို လက်ခံသည်-

- `zenmux/openai/gpt-image-2` ZenMux၏ OpenAI Images API အသုံးပြုသည်။ ရွေးချယ်စရာများတွင် `size`၊ `quality`၊ `n`၊ `output_format`၊ `output_compression`၊ `background` နှင့် `response_format` တို့ ပါဝင်သည်။
- `zm/meta/muse-image-1.0` ကဲ့သို့သော အခြားထုတ်ဝေသူများသည် ZenMux၏ Vertex AI `:predict` အဆုံးမှတ်ကို အသုံးပြုပါ။ `n` မြေပုံများကို `sampleCount`၊ `aspect_ratio` မှ `aspectRatio`၊ နှင့် `image_size` (`1K`, `2K`, `4K`) သို့ `sampleImageSize` pixel `size` တစ်ခုသည် အချိုးအစားတစ်ခုသာ ပံ့ပိုးပေးသည်၊၊ အာမခံချက်ရှိသော pixel အတိုင်းအတာများ။ ပံ့ပိုးထားသော အချိုးများ၊ ဆုံးဖြတ်ချက်များနှင့် အရေအတွက်များသည် မော်ဒယ်အလိုက် ကွဲပြားသည်။
- `zm/inclusionai/ming-image-0.1-design` ၎င်း၏ကိုယ်ပိုင်အတိုင်းအတာကို ရွေးချယ်သည်။ `size`, `aspect_ratio`, နှင့် `image_size` ကို ချန်လှပ်ထားသည်။ တိကျပြတ်သားသောတန်ဖိုးများသည် HTTP 400 ကို ပြန်ပေးသည်။ PNG၊ JPEG နှင့် WebP `output_format` ဖြင့် တောင်းဆိုနိုင်သည်။

ဤပေါင်းစပ်မှုသည် ရည်ညွှန်းပုံ-ပုံတည်းဖြတ်ခြင်းမဟုတ်ဘဲ စာသားမှပုံထုတ်လုပ်ခြင်းကို ပံ့ပိုးပေးသည်။ Vertex အထွက်အား `data[].b64_json` သို့ ပုံမှန်ဖြစ်အောင် ပြုလုပ်ထားသည်။ ပုံဘိုက်များသာရရှိနိုင်သောအခါ `response_format: "url"` အထက်စီးကြောင်း HTTPS URL သို့မဟုတ် base64 ဒေတာ URL ပြန်ပေးသည်။ Empty/filtered သည် အချည်းနှီးသော အောင်မြင်မှုထက် အမှားတစ်ခုကို ပြန်ပေးသည်။ မော်ဒယ်ဝင်ရောက်ခွင့်သည် ZenMux အကောင့်ပေါ်တွင်မူတည်သည်။ [ZenMux၏ Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) နှင့် [OpenAI ပုံများ API](https://docs.zenmux.ai/api/openai/generate-an-image) ကြည့်ပါ။

Microsoft 365 Copilot အကောင့်ဝင်ခြင်းချိတ်ဆက်မှုသည် Copilot၏ built-in ပုံတူးလ်မှတစ်ဆင့် `copilot-m365-web/m365-copilot-image` ဆောင်ရွက်ပေးသည်- ပုံတစ်ပုံလျှင် Copilot တစ်လှည့် (`n` 1–4), `size` လမ်းကြောင်းကိုသာ ညွှန်ပြပြီး ပုံများကို inline ပြန်ပေးသည် (`b64_json`, သို့မဟုတ် `response_format: "url"` အတွက် ဒေတာ URL )။ [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation) ကြည့်ပါ။

## စာရွက်စာတမ်း OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` သည် `provider/model` prefix မှတစ်ဆင့် OCR provider ကို ရွေးချယ်သည်။ သီးခြား model id တစ်ခု (ဥပမာ
`mistral-ocr-latest`) ကို ၎င်း၏ မှတ်ပုံတင်ထားသော provider သို့ ဖြေရှင်းပေးပြီး `model` ကို ချန်လှပ်ထားပါက
Mistral (`mistral-ocr-latest`) ကို default အဖြစ် အသုံးပြုသည်။ မှတ်ပုံတင်ထားသော provider များ (`open-sse/config/ocrRegistry.ts`) —

| Provider id                   | Model id             | `model` value                                               | Notes                                                                                                                               |
| ----------------------------- | -------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (or bare `mistral-ocr-latest`) | Synchronous — တစ်ခုတည်းသော upstream ခေါ်ဆိုမှုမှ response ကို တိုက်ရိုက် ပြန်ပေးသည်။                                                |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                 | Asynchronous upstream (`analyze` + poll) — အောက်တွင် ကြည့်ပါ။                                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                     | Vertex AI ၏ `openapi/chat/completions` partner endpoint မှတစ်ဆင့် synchronous ဖြစ်သည် — authentication/URL အတွက် အောက်တွင် ကြည့်ပါ။ |

Provider သုံးခုလုံးသည် Mistral ပုံစံတူ body တစ်ခုတည်းဖြင့် response ပြန်ပေးသည် —

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence poll လုပ်ဆောင်စီးကြောင်း

Azure Document Intelligence ၏ `analyze` API သည် asynchronous ဖြစ်သည်။ ကနဦး request သည် body အစား
`Operation-Location` header ကို ပြန်ပေးပြီး result ကို poll လုပ်ရသည်။ Handler
(`open-sse/handlers/ocr.ts`) သည် အဆိုပါ URL ကို တစ်စက္ကန့်ခြားစီ၊ အများဆုံး ၃၀ ကြိမ်အထိ poll လုပ်သည်။ `ok` မဟုတ်သော poll response သို့မဟုတ် `"failed"` status ရရှိပါက ချက်ချင်း မအောင်မြင်ကြောင်း သတ်မှတ်ပြီး (ဆက်လက် poll မလုပ်တော့ဘဲ)၊ ကြိုးစားခွင့်အရေအတွက် ကုန်ဆုံးပြီးနောက် operation သည် ဆက်လက်လုပ်ဆောင်နေဆဲဖြစ်ပါက `504` ကို ပြန်ပေးသည်။ နောက်ဆုံး Azure response ကို ပြန်လည်ပေးပို့ခြင်းမပြုမီ Mistral အသုံးပြုသည့် `pages`/`markdown` ပုံစံတူအဖြစ် ပြောင်းလဲထားသဖြင့် client code အနေဖြင့် provider အလိုက် သီးခြားစီ ကိုင်တွယ်ရန် မလိုအပ်ပါ။

### မော်ဒယ်ဈေးနှုန်းများ (`pricing`)

OmniRoute က မော်ဒယ်၏ ဈေးနှုန်းကို သိရှိထားသောအခါ entry တစ်ခုတွင် `pricing` object ပါဝင်သည်။ ဈေးနှုန်းသည် ကုန်ကျစရိတ်တွက်ချက်ရာတွင် အသုံးပြုသည့် ဈေးနှုန်းဇယားမှ ရရှိသည်။ ၎င်းတွင် built-in မူလဈေးနှုန်းများ၊ တစ်ပြိုင်တည်းချိန်ညှိထားသော ဈေးနှုန်းများနှင့် `/api/pricing` မှတစ်ဆင့် သတ်မှတ်ထားသော override များ ပါဝင်သည်။ ၎င်းတို့သည် စာရင်းပါဈေးနှုန်းများဖြစ်သောကြောင့် subscription provider များတွင်လည်း token တစ်ခုချင်းစီအလိုက် ဈေးနှုန်းကို ပြသသည်။

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Fields                                                          | Unit                          | Notes                                                                                                                                                                                        |
| --------------------------------------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD per token, decimal string | OpenRouter နှင့် ကိုက်ညီပြီး exponent notation ကို မည်သည့်အခါမျှ အသုံးမပြုပါ။ cache ဈေးနှုန်းရှိသောအခါတွင်သာ cache field နှစ်ခု ပေါ်လာသည်။                                                   |
| `input`, `output`, `cached`, `cache_creation`                   | USD per 1M tokens, number     | ယခင် catalog ဗားရှင်းများမှ field များဖြစ်ပြီး ရှိပြီးသား client များအတွက် ဆက်လက်ထိန်းသိမ်းထားသည်။ pricing row တွင် ၎င်းတို့ပါရှိသောအခါ `reasoning` နှင့် `long_context` တို့လည်း ပေါ်လာသည်။ |

- **Combos** များသည် ၎င်းတို့၏ ပထမဆုံးမြင်ရသော target ၏ ဈေးနှုန်းကို သယ်ဆောင်သည်။ built-in `auto/*` combos များသည် request ပြုလုပ်ချိန်တွင် target ကို ရွေးချယ်သောကြောင့် ၎င်းတို့တွင် `pricing` မရှိပါ။
- **အခမဲ့မော်ဒယ်များ** ၎င်းတို့၏ ဈေးနှုန်းသည် သုညဖြစ်သောအခါ `"0"` (နှင့် `0`) ကို ပြသသည်။ pricing row မရှိသော မော်ဒယ်တစ်ခုကို catalog က အခမဲ့ဟု သတ်မှတ်ထားပါက (`free: true`) သို့မဟုတ် built-in free-model catalog တွင် စာရင်းသွင်းထားပါက `"0"` ကိုလည်း ပြသသည်။
- **မသိရှိသောဈေးနှုန်း:** entry တွင် `pricing` key မရှိပါ။
- **Credit ဖြင့်တိုင်းတာသော provider များ** (ဥပမာ Kiro) သည် token အလိုက်မဟုတ်ဘဲ request တစ်ကြိမ်အလိုက် ငွေတောင်းခံသည်။ ၎င်းတို့၏ entry များတွင် ယခင်ကရှိခဲ့သော 1M-token အလိုက် numeric field များကို ဆက်လက်ထားရှိပြီး token တစ်ခုချင်းစီအလိုက် string field များ မပါဝင်ပါ။
- **Variants** (reasoning-effort ids၊ no-thinking aliases၊ discovery နှင့် gateway mirrors) များသည် ၎င်းတို့ route လုပ်သည့် မော်ဒယ်၏ ဈေးနှုန်းကို ကူးယူသည်။
- Field များတွင် အခြေခံနှုန်းထားများသာ ပါဝင်သည်။ Long-context အဆင့်များ (`long_context` numeric field) နှင့် service-tier မြှောက်ကိန်းများ (ဥပမာ Codex fast သို့မဟုတ် flex) သည် `prompt` သို့မဟုတ် `completion` ကို မပြောင်းလဲစေပါ။
- Authentication ပုံစံတိုင်းအတွက် object သည် တူညီသည်။ `x-api-key` နှင့် `anthropic-version` အသုံးပြုသည့် Anthropic-style request အပါအဝင် response သည် `{ "object": "list", "data": [...] }` အတိုင်းပင် ဖြစ်သည်။ အကောင်အထည်ဖော်ထားသည့်နေရာ: `src/app/api/v1/models/catalogPricing.ts`။

### မော်ဒယ် id prefix များ (`?prefix=`)

မော်ဒယ်အများစုကို **provider prefix** တစ်ခုအောက်တွင် ကြော်ငြာထားသည်။ ရရှိမည့် prefix ကို `MODELS_CATALOG_PREFIX_MODE` feature flag က ထိန်းချုပ်ပြီး request တစ်ခုချင်းစီအလိုက် query parameter ဖြင့် override ပြုလုပ်နိုင်သည်။ ၎င်းသည် အခြားသူများအတွက် server တစ်ခုလုံး၏ setting ကို မပြောင်းလဲဘဲ သန့်ရှင်းသောစာရင်းကို ရယူလိုသော client အတွက် အသုံးဝင်သည်။

```bash
GET /v1/models?prefix=alias        # မော်ဒယ်တစ်ခုလျှင် id တစ်ခု — အတိုကောက် alias prefix
GET /v1/models?prefix=dual         # ပုံစံနှစ်မျိုးလုံး (server မူလသတ်မှတ်ချက်)
GET /v1/models?prefix=canonical    # provider-id prefix အပြည့်အစုံကိုသာ
```

| `dual`      | `cc/claude-sonnet-4-6` **and** `claude/claude-sonnet-4-6` | **မူလသတ်မှတ်ချက်။** id နှစ်ခုလုံးသည် မော်ဒယ်တစ်ခုတည်းသို့ route လုပ်သည်။ ထို့ကြောင့် မည်သည့်ပုံစံကိုမဆို hardcode ပြုလုပ်ထားသော client config များ ဆက်လက်အလုပ်လုပ်နိုင်သည်။ catalog အရွယ်အစားသည် ခန့်မှန်းခြေအားဖြင့် နှစ်ဆဖြစ်သည်။             |
| `alias`     | `cc/claude-sonnet-4-6`                                    | မော်ဒယ်တစ်ခုလျှင် entry တစ်ခု။ ကွဲပြားသော alias မရှိသည့် provider များသည်လည်း ၎င်းတို့၏ entry ကို ဆက်လက်ထုတ်ပေးသောကြောင့် မည်သည့်အရာမျှ ပျောက်ဆုံးမည်မဟုတ်ပါ။                                                                                   |
| `canonical` | `claude/claude-sonnet-4-6`                                | provider-id prefix အပြည့်အစုံအောက်တွင် မော်ဒယ်တစ်ခုလျှင် entry တစ်ခု။ ကွဲပြားသော alias မရှိသည့် provider များ (ဥပမာ `antigravity/…`, `agy/…`) သည်လည်း ၎င်းတို့၏ id တစ်ခုတည်းကို ဤနေရာတွင် ထုတ်ပေးသောကြောင့် မည်သည့်အရာမျှ ပျောက်ဆုံးမည်မဟုတ်ပါ။ |

`dual`-mode mirror တစ်ခုကို query parameter မပါဘဲလည်း မှတ်သားနိုင်သည်။ ၎င်းတွင် primary id ကို ညွှန်ပြသည့် `parent` field ပါဝင်သည်။

Model picker ကို ဖော်ပြသော client များသည် `?prefix=alias` ကို request ပြုလုပ်သင့်သည် — [OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md) သည်လည်း ဤနည်းလမ်းကို အသုံးပြုသည်။

### Discovery filter များ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` သည် ရွေးချယ်အသုံးပြုနိုင်သော discovery filter များကို လက်ခံသည်။ ၎င်းတို့အနက် မည်သည့် filter မျှ မပါဝင်ပါက response သည် မပြောင်းလဲပါ။ ၎င်းတို့သည် ခေါ်ဆိုသူ မြင်နိုင်ပြီးသား catalog ကို ပိုမိုကျဉ်းမြောင်းစေသည် (API-key ခွင့်ပြုချက်များကို ဦးစွာအသုံးချသည်)။ ထို့နောက် OpenAI-style `limit` / `after` paging မတိုင်မီ ၎င်းတို့ကို လုပ်ဆောင်သည်။

```bash
GET /v1/models?capability=vision&capability=tool_calling   # စာရင်းပါ capability တိုင်းသည် true ဖြစ်ရမည်
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # catalog `type`; မပါဝင်သော row များသည် `chat` ဖြစ်သည်
GET /v1/models?q=sonnet&limit=10                           # id သို့မဟုတ် name တွင် စာလုံးအကြီးအသေးမခွဲခြားဘဲ ကိုက်ညီမှု
```

| ပါရာမီတာ      | တန်ဖိုးများ                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | အနုတ်မဟုတ်သော ကိန်းပြည့်၊ `context_length` နှင့် နှိုင်းယှဉ်သည်                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | စာလုံး ၁–၂၀၀                                                                                        |

မသိသောတန်ဖိုး သို့မဟုတ် အနုတ်မဟုတ်သော ကိန်းပြည့်မဟုတ်သည့် `min_context` (ဥပမာ `1.5`) ဖြစ်ပါက
HTTP `400` ကို ပြန်ပေးပြီး မှန်ကန်သောတန်ဖိုးများကို မက်ဆေ့ချ်တွင် ဖော်ပြသည်။ အကောင်အထည်ဖော်ထားသည့်နေရာမှာ
`src/app/api/v1/models/catalogFilters.ts` ဖြစ်သည်။

### မော်ဒယ်ရွေးချယ်စာရင်း (`POST /v1/models/query`)

`POST /v1/models/query` သည် တူညီသော catalog မှ တိုတောင်းပြီး အမြဲတမ်းတူညီသော စာရင်းတစ်ခုကို ပြန်ပေးသည်။ `GET /v1/models` နှင့်
တူညီသော authentication နှင့် key တစ်ခုချင်းစီအလိုက် မြင်နိုင်ခွင့်ကို အသုံးပြုသည်။

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

အကွက်တိုင်းသည် ရွေးချယ်နိုင်သည်။ `capabilities` နှင့် `exclude` တို့သည် array သို့မဟုတ် comma ဖြင့် ခွဲထားသော string ကို လက်ခံသည်။
`max_output` သည် `max_output_tokens` နှင့် နှိုင်းယှဉ်သည်။ ရလဒ်များကို `owned_by` အလိုက်၊ ထို့နောက် `id` အလိုက် စီစဉ်သည်။
`limit` ၏ မူလတန်ဖိုးမှာ `20` ဖြစ်ပြီး `100` ထက်ကြီးသော တန်ဖိုးများကို `100` သို့ ကန့်သတ်သည်။ မမှန်ကန်သော JSON၊ မသိသော
အကွက် သို့မဟုတ် မမှန်ကန်သောတန်ဖိုး ဖြစ်ပါက HTTP `400` ကို ပြန်ပေးသည်။

### တစ်ဦးချင်း ဖျောက်ထားသော chat မော်ဒယ်များ

Provider စာမျက်နှာတွင် **ဖျောက်ထားသည်** ဟု မှတ်သားထားသော မော်ဒယ်ကို catalog မှ ဖယ်ရှားထားပြီး တိတိကျကျ တောင်းဆိုသောအခါ
HTTP `404` / `model_not_found` ဖြင့် ပယ်ချသည်။ စစ်ဆေးမှုသည် provider alias များ၊ compatible-provider node prefix များနှင့်
connection default များအပါအဝင် ဖြေရှင်းပြီးသော provider နှင့် model ကို အသုံးပြုသည်။ Combo တစ်ခုသည် ဖျောက်ထားသော target များကို
ကျော်သွားပြီး မြင်နိုင်သော sibling တစ်ခုကို အသုံးပြုနိုင်သည်။ လုပ်ဆောင်နိုင်သော target မကျန်တော့ပါက တူညီသော error code ကို
ပြန်ပေးသည်။ ပြန်ဖော်ပြခြင်းသည် နောက်တစ်ကြိမ် တောင်းဆိုမှုတွင် အကျိုးသက်ရောက်သည်။ Image-only visibility override များသည် ID တူ
chat model ကို ဖျောက်မထားပါ။

ဤတစ်ဦးချင်း မော်ဒယ်ဆက်တင်သည် catalog ကြော်ငြာနှင့် auto-routing candidate များကို စစ်ထုတ်သော်လည်း explicit dispatch ကို
ဆက်လက်ထားရှိသည့် [မော်ဒယ်ဖော်ပြမှု ခွင့်ပြု/ငြင်းပယ်စာရင်းများ](../routing/MODEL_EXPOSURE_LIST.md) နှင့် သီးခြားဖြစ်သည်။
API key မော်ဒယ်ခွင့်ပြုချက်များသည်လည်း သီးခြားစီ ဆက်လက်အကျုံးဝင်သည်။ မူလ catalog prefix mode မှာ `dual` အတိုင်း ဆက်ရှိသည်။

### စဉ်းစားမှုမပါသော မော်ဒယ်မူကွဲများ

စဉ်းစားနိုင်သော Claude မော်ဒယ်များအတွက် `/v1/models` သည် `claude-3-omniroute-no-thinking/` ဖြင့် prefix ထည့်ထားသော
**စဉ်းစားမှုမပါသော** မူကွဲတစ်ခုကိုလည်း ကြော်ငြာသည်—

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

ဤ ID ကို ရွေးချယ်ပါက (ဥပမာ `thinking` block ကို အမြဲထည့်သွင်းပေးသော Claude Code config တစ်ခုတွင်) အမှန်တကယ်
`<provider>/<model>` သို့ ပြန်လည်ဖြေရှင်းပြီး reasoning ကို ပိတ်ထားသည် — `/v1/messages` လမ်းကြောင်းတွင်
`thinking:{type:"disabled"}` အဖြစ် သတ်မှတ်မည်ဖြစ်ပြီး၊ သို့မဟုတ် `/v1/chat/completions` လမ်းကြောင်းတွင်
`reasoning`/`reasoning_effort` အကွက်များကို ဖယ်ရှားမည်ဖြစ်သည်။ ဤမူကွဲကို thinking ကို ထောက်ပံ့ပြီး **နှင့်**
`disabled` ကို လက်ခံသော Claude-family မော်ဒယ်များအတွက်သာ စာရင်းပြုသည် (ဥပမာ `disabled` ကို ပယ်ချသော
adaptive-only မော်ဒယ်များကို ဖယ်ထားသည်)။ Operator များသည် မော်ဒယ်တစ်ခုချင်းစီအတွက် မူကွဲကို ဖွင့်ရန် သို့မဟုတ် ပိတ်ရန်
`ModelSpec.noThinkingAlias` မှတစ်ဆင့် အတင်းအကျပ် သတ်မှတ်နိုင်သည်။

## ElevenLabs အသံထုတ်လုပ်ခြင်း

သင်၏ ElevenLabs API key ဖြင့် OmniRoute တွင် `elevenlabs` provider connection တစ်ခုကို configure လုပ်ပါ။
Client များသည် ၎င်းတို့၏ **OmniRoute** key (`Authorization: Bearer $OMNIROUTE_API_KEY`) ဖြင့် authenticate လုပ်သည်။
Gateway သည် သိမ်းဆည်းထားသော provider key ကို `xi-api-key` အဖြစ် ပေးပို့သည်။ ElevenLabs key ကို gateway bearer token အဖြစ် မည်သည့်အခါမျှ မပေးပို့ပါနှင့်။

| Method | Path                        | Response                                      | API key endpoint category |
| ------ | --------------------------- | --------------------------------------------- | ------------------------- |
| POST   | `/v1/sound-generation`      | မူရင်း audio bytes                            | `elevenlabs`              |
| POST   | `/v1/music`                 | မူရင်း audio bytes                            | `music`                   |
| POST   | `/v1/music/stream`          | Streaming audio bytes                         | `music`                   |
| POST   | `/v1/music/detailed`        | မူရင်း multipart audio နှင့် composition plan | `music`                   |
| POST   | `/v1/music/detailed/stream` | မူရင်း SSE metadata နှင့် audio chunks        | `music`                   |
| POST   | `/v1/music/plan`            | JSON composition plan                         | `music`                   |

ဤ endpoint များသည် ရှိပြီးသား `/v1/audio/speech`၊ `/v1/audio/transcriptions`၊
`/v1/voices`၊ `/v1/text-to-speech/{voiceId}` နှင့် `/v1/speech-to-text` route များကို ဖြည့်စွက်ပေးသည်။ မူရင်း JSON field များနှင့် `output_format`၊ `enable_logging` ကဲ့သို့သော query parameter များကို မူရင်းအတိုင်း ထိန်းသိမ်းထားသည်။
`/v1/music/detailed` response များသည် ၎င်းတို့၏ multipart boundary များကို ထိန်းသိမ်းထားသောကြောင့် multipart အဖြစ် parse လုပ်ပါ။
`/v1/music/detailed/stream` သည် composition metadata နှင့် SSE event များအတွင်းရှိ base64 audio chunk များပါဝင်သော `text/event-stream` ကို ပြန်လည်ပေးပို့သည်။ Route ခြောက်ခုလုံးသည် CORS preflight ကို support လုပ်သည်။

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# A short sound effect. Duration: 0.5 to 30 seconds.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Music duration is expressed in milliseconds: 3000 to 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

တဖြည်းဖြည်း audio ပေးပို့ရန် တူညီသော JSON body ဖြင့် `/v1/music/stream` ကို အသုံးပြုပါ။ Composition တွင် `prompt` သို့မဟုတ် `composition_plan` ထဲမှ တစ်ခုတည်းကိုသာ လက်ခံသည်။ `/v1/music/plan` တွင် `prompt` လိုအပ်ပြီး `source_composition_plan` ကို ရွေးချယ်စရာအဖြစ် လက်ခံသည်။ မူရင်း schema များသည် အပို provider field များကို ထိန်းသိမ်းထားသောကြောင့် composition-plan version များနှင့် fine-tuning option များသည် ElevenLabs သို့ ရောက်ရှိမည်ဖြစ်သည်။

Unified `/v1/music/generations` endpoint သည် `elevenlabs/music_v1`၊
`elevenlabs/music_v2` နှင့် `elevenlabs/music_v2_5` ကိုလည်း လက်ခံသည်။ Active ElevenLabs connection ရှိပါက ဤ model များကို music catalog တွင် ဖော်ပြပေးသည်။ ဤ endpoint သည်
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ကို ပြန်လည်ပေးပို့သည်။ ၎င်း၏ `duration` field သည်
စက္ကန့်ဖြင့် ဖော်ပြပြီး `music_length_ms` သို့ map လုပ်သည်။ တိကျစွာ သတ်မှတ်ထားသော `music_length_ms` က ဦးစားပေးသည်။
`instrumental` သည် `force_instrumental` သို့ map လုပ်ပြီး မူရင်း field က ဦးစားပေးသည်။
Streaming အတွက် မူရင်း streaming endpoint များကို အသုံးပြုပါ။ Composition plan တစ်ခုတည်းဖြင့် မောင်းနှင်သော request များအတွက် မူရင်း composition endpoint ကို အသုံးပြုပါ။

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Endpoint၊ model၊ budget နှင့် connection restriction များကို upstream call မပြုလုပ်မီ အသုံးချသည်။ မူရင်း route များသည် upstream status code များနှင့် error body များကို မပြောင်းလဲဘဲ ပြန်လည်ပေးပို့သည်။ ထိုအထဲတွင် plan restriction အတွက် `402` နှင့် quota limit အတွက် `429` တို့ ပါဝင်သည်။
ရှိပါက `character-cost`၊ `song-id`၊ `request-id` နှင့် `retry-after` header များကို ထိန်းသိမ်းထားသည်။ Free credit balance ရှိခြင်းသည် music model တိုင်း၊ output format တိုင်း သို့မဟုတ် API feature တိုင်းကို အသုံးပြုနိုင်မည်ဟု အာမမခံပါ။ Request တစ်ခုချင်းစီအတွက် entitlement ကို ElevenLabs က ဆုံးဖြတ်သည်။
Unified endpoint သည် error status code များကို OmniRoute ၏ normalized error envelope အတွင်း ထိန်းသိမ်းထားသည်။

[music composition](https://elevenlabs.io/docs/api-reference/music/compose) နှင့်

POST route အားလုံးသည် တူညီသောပုံစံကို လိုက်နာသည်: `Bearer your-api-key` + Zod ဖြင့် validation ပြုလုပ်ထားသော JSON body (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` စသည်တို့၊ `src/shared/validation/schemas.ts` တွင်ကြည့်ပါ)။ Schema validation မအောင်မြင်ပါက 4xx ကို ပြန်ပေးသည်။

`Authorization: Bearer ...` ကို ထည့်ပေး၍မရသော client များအတွက် OmniRoute သည် အောက်တွင်မှတ်တမ်းတင်ထားသော query-string compatibility (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) သို့မဟုတ် သီးသန့် `/api/v1/vscode/{token}/...` endpoint များမှတစ်ဆင့် URL အတွင်း API key များကိုလည်း လက်ခံသည်။

```bash
# Rerank (cloud registry provider သို့မဟုတ် "<prefix>/<model>" အဖြစ် OpenAI-compatible provider node)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina classify (Foundation API အထောက်အထားများ)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina segmenter
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina search (s.jina.ai; provider aliases: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Moderations
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (သို့မဟုတ် တောင်းဆိုထားသော format) body ကို ပြန်ပေးသည်
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS တွင် ဘာသာစကားနှင့် အသံတစ်ခု လိုအပ်သည်: `language` သည် ပုံမှန်အားဖြင့် "en" ဖြစ်ပြီး၊ မရှိသော
# voice သို့မဟုတ် OpenAI ၏ မူရင်း voice အမည် (alloy, nova, …) ကို "Adrian" အဖြစ် သတ်မှတ်သည်

POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }

```

> **Rerank ပံ့ပိုးသူ node များ:** `POST /v1/rerank` သည် `<node-prefix>/<model>` အဖြစ် သတ်မှတ်ထားသော OpenAI-compatible ပံ့ပိုးသူ node များ (oMLX၊ vLLM၊ Infinity၊ gateway နောက်က TEI၊ …) သို့လည်း လမ်းကြောင်းပြောင်းပေးသည်။
> Loopback node များ (`localhost`, `127.0.0.1`, `172.16.0.0/12`) သည် အမြဲတမ်း အသုံးပြုခွင့်ရှိပြီး၊ `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` တွင် operator က စာရင်းသွင်းထားသော hostname များလည်း အလားတူ အသုံးပြုခွင့်ရှိသည် (ဥပမာ `http://reranker:8080/v1` ကဲ့သို့သော Docker/Compose service name များ၊ ၎င်းတို့ကို တိုက်ရိုက်ခေါ်ဆိုပြီး `HTTP(S)_PROXY` သို့မဟုတ် connection ၏ pinned proxy မှတစ်ဆင့် မခေါ်ဆိုပါ)။ အခြား host တစ်ခုခု — LAN box သို့မဟုတ် Tailscale peer — ပေါ်ရှိ node များသည် operator က `RERANK_REMOTE_PROVIDER_NODES` feature flag ကို ဖွင့်ထားပြီး node ၏ base URL သည် provider outbound URL policy (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) ကို ဖြတ်သန်းနိုင်မှသာ အသုံးပြုခွင့်ရှိသည်။
> Memory engine ၏ rerank အဆင့်သည် ဤ route ကို loopback မှတစ်ဆင့် ခေါ်ဆိုသောကြောင့် Memory settings ထဲရှိ `rerankProviderModel` ကိုလည်း တူညီသော စည်းမျဉ်းက ထိန်းချုပ်သည်။
>
> **Local server ပုံစံများ:** node ကို `<base>/v1/rerank` တွင် ခေါ်ဆိုပြီး 404 ရရှိပါက `<base>/rerank` တွင် ထပ်မံခေါ်ဆိုသည် (Infinity၊ TEI)။ Upstream body တွင် Cohere/OpenAI ရေးသားပုံ (`documents`, `return_documents`) နှင့် TEI ရေးသားပုံ (`texts`, `return_text`) နှစ်မျိုးလုံး ပါဝင်ပြီး upstream response ကို Cohere envelope အဖြစ် စံပြုပြောင်းလဲပေးသည်။ TEI ၏ ရိုးရိုး `[{index, score, text}]`၊ thin gateway များမှ `{results: [{index, score}]}` နှင့် Voyage ပုံစံ `{data: [...]}` တို့အားလုံးကို client ထံ `{results: [{index, relevance_score, document?}]}` အဖြစ် ပြန်လည်ပေးပို့ပြီး score အလိုက် စီကာ `top_n` အရေအတွက်အထိသာ ကန့်သတ်ပေးသည်။

> **Provider-node ရှာဖွေမှု:** OpenAI-compatible provider node ပေါ်ရှိ model များသည် node prefix အောက်ရှိ `GET /v1/models` တွင် ပေါ်လာသည်။
> Endpoint metadata မပါသော row များ (ပုံမှန် local `/v1/models` စာရင်းများတွင် တွေ့ရသည့်ပုံစံ) သည် node ၏ `apiType` ကို အမွေဆက်ခံသည်။ ထို့ကြောင့် `embeddings` node ၏ model များသည် `type: "embedding"` ဖြစ်ပြီး `rerank` node ၏ model များသည် chat အဖြစ် default မသတ်မှတ်ဘဲ `type: "rerank"` ဖြစ်သည်။ သို့သော် sync လုပ်ထားသော သို့မဟုတ် ကိုယ်တိုင်ထည့်သွင်းထားသော row တွင် `supportedEndpoints` ကို အတိအလင်း သတ်မှတ်ထားပါက ၎င်းသည် ဦးစားပေးအကျိုးသက်ရောက်မှု ရှိနေဆဲဖြစ်သည်။

## Files API

Batch input/output နှင့် file-purpose upload များအတွက် OpenAI နှင့် ကိုက်ညီသော files endpoint။

| Method | Path                     | Description                                                                                                       |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | ဖိုင်တင်ရန် (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — အများဆုံး 512 MiB |
| GET    | `/v1/files`              | အထောက်အထားပြုထားသော API key အတွက် ဖိုင်များစာရင်းရယူရန်                                                           |
| GET    | `/v1/files/[id]`         | ဖိုင်၏ metadata ကို ရယူရန်                                                                                        |
| DELETE | `/v1/files/[id]`         | ဖိုင်ကို ဖျက်ရန်                                                                                                  |
| GET    | `/v1/files/[id]/content` | မူရင်းဖိုင်အကြောင်းအရာကို stream ဖြင့် ပြန်ပို့ရန်                                                                |

**Auth:** Bearer API key — files များကို `getApiKeyRequestScope` မှတစ်ဆင့် API key တစ်ခုချင်းစီအလိုက် သီးခြားသတ်မှတ်ထားသည်။ Key တစ်ခုသည် ၎င်းပိုင်ဖိုင်များကိုသာ ကြည့်ရှု၊ download လုပ်ပြီး ဖျက်နိုင်သည်။ Key မပါသော dashboard session သည် instance တစ်ခုလုံးကို ဖတ်ရှုနိုင်သည်။ Owner မရှိသောဖိုင် (anonymous သို့မဟုတ် dashboard-session upload) ကို session မဟုတ်သော caller မည်သူမဆို အသုံးပြုခွင့်မရှိပါ။ `GET /v1/files` သည် anonymous caller — နှင့် resolve မဖြစ်သော တင်ပြထားသည့် key — ကို `REQUIRE_API_KEY=false` ဖြစ်နေသော်လည်း `401` ဖြင့် ပယ်ချသည်။ ထို့ကြောင့် tenant အားလုံး၏ ဖိုင်များကို စာရင်းပြုစုနိုင်ခြင်း မရှိတော့ပါ (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)။

| DELETE | `/v1/batches/[id]`        | ပြီးဆုံးပြီးသော/မအောင်မြင်သော batch ကို ဖျက်ရန်                                                                            |
| POST   | `/v1/batches/[id]/cancel` | လုပ်ဆောင်နေဆဲ batch ကို ပယ်ဖျက်ရန်                                                                                         |

**Auth:** Bearer API key။ Batches များကို files များနှင့် တူညီသော three-way rule အရ API key တစ်ခုချင်းစီအလိုက် သီးခြားသတ်မှတ်ထားသည် — ၎င်းကိုယ်ပိုင် key သာ အသုံးပြုနိုင်ခြင်း၊ dashboard session သည် instance တစ်ခုလုံးအတွက် အသုံးပြုနိုင်ခြင်း၊ owner မရှိသော record များကို session မဟုတ်သော caller မည်သူမဆို (retrieve, delete, cancel နှင့် create လုပ်စဉ် `input_file_id` စစ်ဆေးမှုအပါအဝင်) အသုံးပြုခွင့်မရှိခြင်းတို့ ဖြစ်သည်။ `GET /v1/batches` သည် `REQUIRE_API_KEY=false` ဖြစ်နေသော်လည်း anonymous caller ကို `401` ဖြင့် ပယ်ချသည်။

## API ရှာပါ။

Web/search ပံ့ပိုးပေးသူ abstraction (Tavily၊ Brave၊ Exa၊ Serper စသည်ဖြင့်)။

| နည်းလမ်း | မဂ်                    | ဖော်ပြချက်                                                                                              |
| -------- | ---------------------- | ------------------------------------------------------------------------------------------------------- |
| GET      | `/v1/search`           | ပြင်ဆင်သတ်မှတ်ထားသော ရှာဖွေရေးဝန်ဆောင်မှုပေးသူများ + စွမ်းရည်များကို စာရင်းပြုစုပါ။                     |
| POST     | `/v1/search`           | `v1SearchSchema` မှ အတည်ပြုထားသော ရှာဖွေမှု query — body ကိုဖွင့်ပါ၊ caching/coalescing ကို ပံ့ပိုးသည်။ |
| GET      | `/v1/search/analytics` | ဝန်ဆောင်မှုပေးသူတိုင်း hit/latency/cache ကိန်းဂဏန်းများ                                                 |

**အထောက်အထား-** ထမ်းသူ API သော့ (`extractApiKey` + `isValidApiKey`)။ ရှာဖွေမှုမူဝါဒကို `enforceApiKeyPolicy` မှတစ်ဆင့် ပြဋ္ဌာန်းထားသည်။

**Auto-select:** without `provider`, the cheapest provider with a configured connection runs first and the next cheapest is the failover. Free last-resort providers (`duckduckgo-free`) are used only when nothing else is configured. A self-hosted SearXNG counts as configured once its connection stores a real `baseUrl` (not the catalog default `http://localhost:8888/search`): it then ranks as a $0 provider ahead of keyed ones, with the cheapest keyed provider as failover, including when SearXNG answers 400, 401, 403 or 404. A `baseUrl` that is not a valid `http(s)` URL or that points at a cloud-metadata address does not count. A SearXNG connection that stores a token ranks this way only over `https://` or loopback `http://`. Over remote plain `http://` it is never a failover and stays a last resort, used only when no other provider is configured or when requested by name, so it does send the token in cleartext in those two cases.

## Web Fetch API

သတ်မှတ်ပြင်ဆင်ထားသော web-fetch provider (Firecrawl၊ Jina
Reader၊ Tavily Extract၊ TinyFish Fetch၊ Nimble Extract၊ Parallel Extract) မှတစ်ဆင့် URL တစ်ခုမှ အကြောင်းအရာကို ထုတ်ယူပါ။

Parallel Extract (`parallel-search`၊ Parallel Search နှင့် API key တစ်ခုတည်းကို အသုံးပြုသည်) သည် Markdown
သာ ပြန်ပေးသည် — အခြား `format` တန်ဖိုးများအားလုံးသည် `400` ဖြစ်သည် — ထို့အပြင် အကြောင်းအရာကို စာလုံး
100,000 အထိသာ ကန့်သတ်ထားသည်။ ရည်ညွှန်းထားသော စာမျက်နှာကိုယ်တိုင် ထုတ်ယူ၍မရသောအခါ upstream က ၎င်းကို HTTP 200
အတွင်း အကြောင်းကြားသည်၊ OmniRoute က ၎င်းကို သတ်မှတ်ထားသောစာသားဖြင့် `422` အဖြစ် ပြသသည်။

| Method | Path            | Description                                                                 |
| ------ | --------------- | --------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL ကို fetch/scrape လုပ်သည် — body ကို `v1WebFetchSchema` ဖြင့် အတည်ပြုသည် |

**Auth:** Bearer API key (`extractApiKey` + `isValidApiKey`)။ Policy ကို `enforceApiKeyPolicy` မှတစ်ဆင့် အတည်ပြုသည်။

**Quota-aware fallback (#8297):** တိကျသော `provider` မပေးထားပါက pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ကို သတ်မှတ်ထားသော
ဦးစားပေးအစီအစဉ်အတိုင်း (fill-first) ဖြတ်သန်းရွေးချယ်သည် — rate limit ဖြစ်နေသော်လည်း ပြင်ဆင်သတ်မှတ်ထားသော provider ကို request ကို ရပ်တန့်မည့်အစား ကျော်သွားသည်၊ ထို့အပြင် ပြန်လည်ကြိုးစားနိုင်သော/quota ဆိုင်ရာ upstream အမှားတစ်ခု (HTTP 429 အမြဲတမ်း၊ Firecrawl/Tavily/TinyFish quota ပုံစံ free tier များအတွက် 402/403 — Jina Reader အတွက် မဟုတ်သကဲ့သို့ ရိုးရိုး 400 bad request အတွက်လည်း မဟုတ်) ဖြစ်ပါက request ပြုလုပ်ချိန်တွင် မစမ်းရသေးသော credential ပါ provider နောက်တစ်ခုသို့ ဆက်လက်ကျော်သွားသည်။ pool အတွင်းရှိ provider အားလုံး ကုန်ဆုံးသွားသောအခါ ယခင် generic `400` အစား endpoint က `Retry-After` header ပါသော တစ်ခုတည်းသော `429` ကို ပြန်ပေးသည်။ `provider` ကို တိကျစွာ တောင်းဆိုထားပါက **silent fallback မရှိပါ** — rate limit ဖြစ်နေသော သို့မဟုတ် အလုပ်မလုပ်သော explicit provider ၏ ကိုယ်ပိုင်အမှားကို ပြသသည် (rate limit ဖြစ်ပါက `429`၊ မဟုတ်ပါက upstream status)။

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake ကို အတည်ပြုပြီး wire protocol နမူနာစာများ (`request`, `cancel`) ကို ပြန်ပေးသည်။ အမှန်တကယ် WS frames များကို Next.js route table ပြင်ပရှိ ထည့်သွင်းပါဝင်သော WS server က ကိုင်တွယ်သည်။

**Auth:** handshake အတွင်း Bearer API key။

### Responses API over WebSocket (codex only)

```bash
# HTTP API နှင့် host:port တူညီသည် (မူရင်း 20128)၊ connection ကို upgrade လုပ်ပါ:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (သို့မဟုတ်: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# ပထမဆုံး frame သည် response.create ဖြစ်ရမည်:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy ကို **`codex` အတွက်သာ** (ChatGPT backend) သီးသန့်ချိတ်ဆက်ထားသည်။ ၎င်းသည် API/dashboard နှင့် port တစ်ခုတည်းရှိ `/v1/responses`,
`/responses` နှင့် `/api/v1/responses` လမ်းကြောင်းများတွင် နားထောင်သည်။ ပထမဆုံး `response.create` frame တွင် ၎င်းသည် internal `codex-responses-ws` bridge မှတစ်ဆင့် authentication + preparation ပြုလုပ်ပြီး codex OAuth connection တစ်ခုကို ရွေးချယ်ကာ `wreq-js` transport မှတစ်ဆင့် `wss://chatgpt.com/backend-api/codex/responses` သို့ tunnel လုပ်သည်။ **codex မဟုတ်သော model များကို ပယ်ချသည်** (`codex_ws_provider_required`)။ quota-share routing အတွက် `model: "qtSd/<group>/codex/<model>"` ကို အသုံးပြုပါ။ `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` တွင် အကောင်အထည်ဖော်ထားသည်။

**Auth:** handshake အတွင်း Bearer API key။ ထည့်သွင်းပါဝင်သော HTTP server (`server-ws.mjs`) သည် အသက်ဝင်နေသော entrypoint ဖြစ်ရမည် (`app/server-ws.mjs` ရှိပါက မူရင်းအားဖြင့် ထိုသို့ဖြစ်သည်)။

#### Model id: bare ChatGPT id ကို အသုံးပြုပါ (`codex/` prefix မပါရ)

OpenAI **Codex CLI** သည် `supports_websockets = true` ဖြစ်သောအခါ model name ကို client-side တွင် အတည်ပြုပြီး
`codex/gpt-5.5` ကဲ့သို့ provider-prefixed id များကို (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`) ပယ်ချသည်။ **bare** id (ဥပမာ `gpt-5.5`) ကို ပေးပို့ပါ။ OmniRoute ၏ bridge သည် codex-only ဖြစ်သောကြောင့် upstream သို့ tunnel မလုပ်မီ bare id ကို codex model အဖြစ် ပြန်လည်ဖြေရှင်းသည်
(`resolveCodexWsModelInfo`) — bare `gpt-5.5` သည် HTTP မှတစ်ဆင့် အခြား provider သို့ route လုပ်သွားနိုင်သော်လည်း ဖြစ်သည်။

#### OpenAI Codex CLI ကို ပြင်ဆင်သတ်မှတ်ခြင်း

Codex CLI ကို OmniRoute သို့ညွှန်ပြရန် WebSocket support ပါသော custom provider တစ်ခုကို `~/.codex/config.toml` သို့ ထည့်ပါ (ရှိပြီးသား config ကို မထိခိုက်စေရန် သီးခြား `CODEX_HOME` ကို အသုံးပြုပါ)။

```toml
model = "gpt-5.5"                 # bare id — NOT "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # အဆုံးတွင် slash မထည့်ပါနှင့်; WS URL ကို ၎င်းမှ ဆင်းသက်ဖန်တီးသည် (production တွင် https/wss ကို အသုံးပြုပါ)
wire_api = "responses"                    # Feb 2026 မှစ၍ ထောက်ပံ့ထားသော တစ်ခုတည်းသော တန်ဖိုး
supports_websockets = true                # Responses-over-WS transport ကို ဖွင့်ပေးသည်
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key (Bearer) ကို သိမ်းဆည်းသည်
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key (REQUIRE_API_KEY=false ဖြစ်ပါက မည်သည့် key မဆို)
codex exec "Responda apenas: PONG"
```

CLI သည် `base_url + /responses` ကို WebSocket သို့ upgrade လုပ်ပြီး OmniRoute က ၎င်းကို ရွေးချယ်ထားသော codex OAuth connection သို့ tunnel လုပ်သည်။ local server နှင့် end-to-end အတည်ပြုပြီးဖြစ်သည်: ChatGPT က `codex.rate_limits` + `response.created` ကို ပြန်ပေးကာ completion ကို stream လုပ်သည်။

| နည်းလမ်း | မဂ်                 | ဖော်ပြချက်                                                                                             |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------ |
| GET      | `/v1/quotas/check`  | စာရင်းသွင်းသော့ကို မထုတ်ပေးမီ `provider` + `accountId` အတွက် ခွဲတမ်းကို ကြိုတင်အတည်ပြုပါ။              |
| POST     | `/v1/issues/report` | quota/key ထုတ်ပေးမှု ပျက်ကွက်မှုကို GitHub သို့ သတင်းပို့ပါ ( `GITHUB_ISSUES_REPO` + တိုကင် လိုအပ်သည်) |

**အထောက်အထား-** `/v1/quotas/check` သည် Bearer API သော့ (`isAuthenticated`) ကို ယူသည်။ `/v1/issues/report` သည် စီမံခန့်ခွဲမှု-သပ်သပ်ဖြစ်သည် (`requireManagementAuth`) သည် `/api/v1/registered-keys` ကဲ့သို့ဖြစ်သည်- ဒက်ရှ်ဘုတ်စက်ရှင်၊ ဒေသန္တရ CLI တိုကင် သို့မဟုတ် `manage`/`admin` နယ်ပယ်ပါရှိသော API သော့တစ်ခု။ အနုမာန-သီးသန့် API သော့များသည် `403` ရရှိသည်။

### Quota session ပြန်လည်ရယူခြင်း (ရွေးချယ်အသုံးပြုနိုင်သည်)

stream မပြုသော `POST /v1/chat/completions` သို့မဟုတ် `POST /v1/responses` တစ်ခုသည်
terminal quota error (`402`/`429`/`503` — body တွင် quota သို့မဟုတ် credits ကုန်ဆုံးကြောင်း ဖော်ပြထားသောအခါ) ဖြင့်
မအောင်မြင်ပါက error ပြန်ပေးမည့်အစား ခေတ္တသိမ်းထားပြီး နောက်ပိုင်းတွင် ပြန်လည်လုပ်ဆောင်နိုင်သည်။ ခေါ်ဆိုသူသည် request တစ်ခုချင်းစီအတွက် အောက်ပါ header သုံးခုဖြင့် ရွေးချယ်အသုံးပြုနိုင်သည်-

| Header                       | တန်ဖိုး                                                 |
| ---------------------------- | ------------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                                  |
| `x-omniroute-session`        | session id, `[A-Za-z0-9._:-]{1,128}`                    |
| `x-omniroute-recovery-turn`  | session အတွင်း ထူးခြားရမည့် turn id (တူညီသော စည်းမျဉ်း) |

`stream: false` ဖြစ်ပြီး tools၊ tool history သို့မဟုတ် `previous_response_id` မပါဝင်သော turn များနှင့်
`x-omniroute-connection` pin မပါဝင်သော turn များသာ အကျုံးဝင်သည်။ ထို့အပြင် `STORAGE_ENCRYPTION_KEY` သတ်မှတ်ထားရမည် (request ကို 24 နာရီအထိ encryption ဖြင့် သိမ်းဆည်းထားသည်)။ ထို့နောက် response သည်
`recovery.poll` ပါသော `202` ဖြစ်လာမည်။ `GET /v1/quota-recoveries/{id}` ဖြင့် poll ပြုလုပ်နိုင်သည် (စောင့်ဆိုင်းနေစဉ် `202`၊ ပြီးဆုံးသောအခါ recovered body ပါသော `200`) သို့မဟုတ် `DELETE` ဖြင့် ပယ်ဖျက်နိုင်သည်။ Ticket များကို ၎င်းတို့ဖန်တီးခဲ့သော API key တစ်ခုတည်းကသာ မြင်နိုင်သည်။ ရလဒ်မသေချာသော replay သည် နှစ်ကြိမ်ပေးပို့ခြင်းမဖြစ်စေရန် `needs_confirmation` အခြေအနေဖြင့် အဆုံးသတ်မည်။ မူရင်းရင်းမြစ်: `src/lib/quota/quotaSessionRecovery.ts`။

## ကိုယ်ပိုင်ဝန်ဆောင်မှုအသုံးပြုမှု (`/api/usage/om-usage`)

မည်သည့် API သော့ကိုမဆို ဖတ်နိုင်သည်။**၎င်း၏ကိုယ်ပိုင်** အသုံးပြုမှုနှင့် ခွဲတမ်း — စီမံခန့်ခွဲမှု စစ်မှန်ကြောင်း မရှိပါ။ ဤသည်မှာ ကလိုင်းယင့် (CLI၊ OmniCopilot အကန့်) သည် သော့ကိုင်ဆောင်သူတစ်ဦး၏ အသုံးစရိတ်ကို ပြသရန် အသုံးပြုသည့် အဆုံးမှတ်ဖြစ်သည်။

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

သော့ရှိရမယ်။**`allowUsageCommand`** ဖွင့်ထားပါသည် (ပုံမှန် — ဖြင့် ပိတ်ပါက ဒက်ရှ်ဘုတ်၏ API ကီးမန်နေဂျာက ၎င်းကို သော့တစ်ခုစီသို့ ပြောင်းပေးသည်)။ အဲဒါမရှိရင် အဆုံးမှတ်က `403` အဖြေပေးပါတယ်။

`?format=json` ခွဲခြားထားသောပုံသဏ္ဍာန်ကို ပြန်ပေးသည် ထို့ကြောင့် ခေါ်ဆိုသူတစ်ဦးသည် ငြင်းဆိုချက်မှ ဒေတာအကွက်ကို ဘယ်သောအခါမှ မဖတ်ပါ။ အောင်မြင်မှုအပေါ်

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

ငြင်းဆိုမှုတွင် (`401` မကောင်းသောသော့ / `403` ခွင့်မပြု) တူညီသောလမ်းကြောင်းသည် `{ "allowed": false, "error": { "message": "…" } }` — သို့ပြန်ပို့သည် လက်ရှိ-သို့သော်လည်း-ဗလာ `personal`/`provider` (သော့ခွင့်ပြုထားသည်၊ ဘာမှမသင်ယူရသေး) သည် ငြင်းချက်တစ်ခုနှင့် မတူညီသောအခြေအနေဖြစ်ပြီး JSON ဖောင်မှသာလျှင် ၎င်းတို့ကို ခွဲခြားနိုင်သည်။

**အထောက်အထား-** `isValidApiKey` — ဖြင့် အတည်ပြုထားသော ခေါ်ဆိုသူ၏ကိုယ်ပိုင် Bearer API သော့သည် ၎င်းသည် _not_ `requireManagementAuth` နောက်တွင်ရှိနေသော စီမံခန့်ခွဲမှုမျက်နှာပြင် (`/api/keys/…`) ဖြစ်သည်။

### Raw နှင့် Cutoff-Adjusted Quota ရာခိုင်နှုန်းများ

`/api/usage/om-usage` ကို အသုံးပြုသောအခါ caller များသည် **plain-text output** နှင့် ဖွဲ့စည်းတည်ဆောက်ထားသော
**JSON output** တို့တွင် ပြသထားသော ရာခိုင်နှုန်းများ၏ ကွာခြားချက်ကို သတိပြုသင့်သည်-

| ကဏ္ဍ               | Plain-text ပုံစံ (`/api/usage/om-usage` / `@@om-usage`)                                               | JSON ပုံစံ (`?format=json`)                                                                            |
| :----------------- | :---------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| **Output field**   | `NN% left` (ဥပမာ၊ `20% left`)                                                                         | `provider.quotas` / `providers[].quotas`                                                               |
| **တိုင်းတာမှု**    | **Cutoff-adjusted အသုံးပြုနိုင်သော allowance**: cutoff threshold အထက်တွင် ကျန်ရှိသော capacity         | **Raw upstream quota**: provider က တိုင်းတာပေးထားသော မပြင်ဆင်ရသေးသည့် တန်ဖိုး                          |
| **Cutoff scaling** | `effectiveRemainingPercent()` ဖြင့် scale ပြုလုပ်ထားသဖြင့် ကာကွယ်ထားသော reserve သည် `0% left` ဖြစ်သည် | မရှိ (provider က အစီရင်ခံသည့် raw snapshot တန်ဖိုးများ)                                                |
| **Threshold data** | ပြသထားသော ရာခိုင်နှုန်းထဲတွင် ထည့်သွင်းထားသည်                                                         | connection တစ်ခုချင်းစီအလိုက် `quotaWindowThresholds` (သို့မဟုတ် server defaults) တွင် သိမ်းဆည်းထားသည် |
| **အဓိကအသုံးပြုသူ** | Interactive CLI များ၊ terminal prompt များ၊ လူသား operator များ                                       | Programmatic integration များ၊ dashboard များ၊ analytics၊ billing tracker များ                         |

#### Cutoff Adjustment Formula

OmniRoute သည် upstream ကုန်ဆုံးမှုကို ကာကွယ်ရန် proactive quota cutoff များကို ပံ့ပိုးပေးသည် (connection
`quotaWindowThresholds`၊ provider defaults သို့မဟုတ် global resilience settings မှတစ်ဆင့် သတ်မှတ်သည်)။ Quota window တစ်ခုတွင် cutoff threshold
(ဥပမာ၊ `cutoff = 25%`) အသက်ဝင်နေသောအခါ text renderer သည် ကျန်ရှိသော allowance ကို အောက်ပါအတိုင်း တွက်ချက်သည်-

- `remaining <= cutoff` ဖြစ်ပါက: `0%` ကို ပြန်ပေးသည်။
- `remaining > cutoff` ဖြစ်ပါက: `((remaining - cutoff) / (100 - cutoff)) * 100` ကို ပြန်ပေးသည်။

ဖော်မတ်ပြုလုပ်ထားသော text output သည် ၎င်းကို အနီးဆုံး integer သို့ round ပြုလုပ်သည် (`Math.round(...)`)။

#### သရုပ်ပြဥပမာ

Provider window တစ်ခုတွင် **60% မူရင်းအသုံးပြုမှု** ရှိပြီး (ထို့ကြောင့် **40% မူရင်းကျန်ရှိခွင့်**)၊ သတ်မှတ်ထားသော
**25% ကျန်ရှိခွင့်ဖြတ်တောက်မှု** သတ်မှတ်ချက်ရှိသည်ဟု ယူဆပါစို့။

| ကိုယ်စားပြုပုံစံ                 | တွက်ချက်ပုံ                                        | ကျန်ရှိမှု |          အကျိုးဆက်ဖြစ်သော အသုံးပြုမှု          |
| :------------------------------- | :------------------------------------------------- | :--------: | :--------------------------------------------: |
| **မူရင်း JSON (`?format=json`)** | အထက်မှ ပေးပို့သော snapshot (`quotas[window]`)      |  **40%**   |                    **60%**                     |
| **စာသားပုံစံ (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**   | **80%** ( `100 - remaining` ဖြင့် တွက်ချက်ပါက) |

- **စာသားတွင် 20% left ဟု ပြသရသည့်အကြောင်း:** အကောင့်တွင် ရုပ်ပိုင်းဆိုင်ရာ quota 40% ကျန်ရှိသည့်အနက် 25% ကို
  ဖြတ်တောက်မှုမူဝါဒအရ သီးသန့်ထားသည်။ Router က ဤချိတ်ဆက်မှုသို့ routing မလုပ်တော့မီ အသုံးပြုနိုင်သည့် headroom
  75% အနက် ခေါ်ဆိုသူအတွက် 15% သာ ကျန်ရှိသည်။ ထို့ကြောင့် routing ရပ်တန့်မည့်အချိန်နှင့် တိတိကျကျ ကိုက်ညီစွာ
  ချိတ်ဆက်မှုက ကုန်ဆုံးမှု (`0% left`) ကို အချက်ပြနိုင်ရန် အချိုးကျပြောင်းလဲခြင်းကို အသုံးပြုထားသည်။
- **JSON က မူရင်းတန်ဖိုးများကို ထိန်းသိမ်းရသည့်အကြောင်း:** JSON payload သည် တိကျသော provider snapshot (`UsageSnapshot`)
  ကို ပြန်ပေးသောကြောင့် ပြင်ပကိရိယာများသည် server-side loss ဖြစ်စေသော scaling မပါဘဲ အထက်မှ ပေးပို့သော အမှန်တကယ်
  အသုံးပြုမှုနှင့် ချိတ်ဆက်မှုအဆင့် `quotaWindowThresholds` များကို ရယူနိုင်သည်။

#### အသုံးပြုသူဘက်မှ ပြောင်းရွှေ့ခြင်း လမ်းညွှန်ချက်

ပြင်ပပေါင်းစည်းမှုတစ်ခု (ဥပမာ editor plugin သို့မဟုတ် agent extension) သည် ယခင်က စာသား endpoint
(`NN% left`) ကို scrape လုပ်ပြီး အသုံးပြုထားသော ရာခိုင်နှုန်းကို `100 - NN` ဖြင့် တွက်ချက်ခဲ့ပါက၊ `?format=json` သို့
ပြောင်းရွှေ့ရာတွင်-

- မူရင်း JSON တန်ဖိုးများကို ဖတ်ခြင်းဖြင့် **အထက်မှ ပေးပို့သော အမှန်တကယ်အသုံးပြုမှု** (အထက်ပါဥပမာတွင် အသုံးပြုမှု 60%) ကို ဖော်ပြမည်။
- ပေါင်းစည်းမှုက စာသား endpoint ၏ အသုံးပြုနိုင်သော allowance အဓိပ္ပာယ်ကို ဆက်လက်ထိန်းသိမ်းလိုပါက၊ ချိတ်ဆက်မှုအဆင့် override များအတွက် `quotaWindowThresholds` ကို အသုံးပြု၍ ထိရောက်သော ကျန်ရှိမှုဖော်မြူလာကို client-side တွင် တွက်ချက်နိုင်သည်။

## Semantic Cache

```bash
# ကက်ရှ်စာရင်းအင်းများ ရယူရန်
GET /api/cache/stats

# ကက်ရှ်အားလုံး ရှင်းလင်းရန်
DELETE /api/cache/stats
```

တုံ့ပြန်မှု ဥပမာ-

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Latency သက်ရောက်မှု

Semantic cache HIT သည် တုံ့ပြန်မှုကို ကက်ရှ်မှ **upstream
ခေါ်ဆိုမှုမပြုဘဲ** ပေးပို့သောကြောင့် အစီရင်ခံထားသည့်
`X-OmniRoute-Response-Latency` သည် မူလ upstream latency မည်မျှပင်ရှိစေကာမူ
သုညနီးပါး ဖြစ်သည်။ Latency ကို အာရုံစိုက်သည့် client များ
(benchmarking၊ p50/p99 စောင့်ကြည့်ခြင်း) သည်
`X-OmniRoute-Cache-Latency` တုံ့ပြန်မှု header ကို စစ်ဆေးသင့်သည်-

| တန်ဖိုး     | အဓိပ္ပာယ်                                                                          |
| ----------- | ---------------------------------------------------------------------------------- |
| `synthetic` | တုံ့ပြန်မှုကို ကက်ရှ်မှ ပေးပို့ခြင်း၊ latency သည် အမှန်တကယ် upstream အချိန်မဟုတ်ပါ |
| _(absent)_  | အမှန်တကယ် upstream ခေါ်ဆိုမှုမှ တုံ့ပြန်မှု                                        |

### သော့တစ်ခုချင်းစီအလိုက် ကက်ရှ်ကျော်ခြင်း

API key များသည် `cacheDefaultMode` မှတစ်ဆင့် semantic cache ဖတ်ရှုမှုများမှ
ဖယ်ထွက်နိုင်သည်-

| တန်ဖိုး  | လုပ်ဆောင်ပုံ                                                  |
| -------- | ------------------------------------------------------------- |
| `legacy` | ပုံမှန်ကက်ရှ် လုပ်ဆောင်ပုံ (မူလသတ်မှတ်ချက်)                   |
| `bypass` | ကက်ရှ်ရှာဖွေမှုကို လုံးဝကျော်ပြီး upstream ကို အမြဲခေါ်ဆိုသည် |

သော့ဖန်တီးချိန် (`POST /api/keys`) သို့မဟုတ် အပ်ဒိတ်လုပ်ချိန် (`PATCH /api/keys/[id]`) တွင် သတ်မှတ်ပါ-

```json
{ "cacheDefaultMode": "bypass" }
```

### တောင်းဆိုမှုတစ်ခုချင်းစီအလိုက် ကက်ရှ်ကျော်ခြင်း

သော့ဆက်တင်များ မည်သို့ပင်ရှိစေကာမူ မည်သည့်တောင်းဆိုမှုမဆို ကက်ရှ်ကို
ကျော်နိုင်သည်-

```
X-OmniRoute-No-Cache: true
```

## CLIProxyAPI စီမံခန့်ခွဲမှု လိုက်ဖက်ညီမှု

OmniRoute သည် အသုံးပြုမှု dashboard များက Claude နှင့် Codex စာရင်းသွင်းမှု
ကန့်သတ်ချက်များကို ဖတ်ရှုရန် ခေါ်ဆိုသည့် [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
စီမံခန့်ခွဲမှု endpoint သုံးခုကို ဖြေကြားပေးသည်
(ဥပမာ T3 Code ၏ `cliproxy` usage-limit source)။ Client ၏ base URL ကို
OmniRoute သို့ ညွှန်ပြပြီး `manage` scope ပါသော API key ကို ၎င်း၏
စီမံခန့်ခွဲမှု key အဖြစ် အသုံးပြုပါ။ Route များကို `/v0/management/*` နှင့်
`/api/v0/management/*` တို့တွင် ပေးဆောင်ထားသည်။

| Method | Path                         | ဖော်ပြချက်                                                                                                                                                        |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Claude နှင့် Codex OAuth ချိတ်ဆက်မှုများကို `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }` အဖြစ် ပြန်ပေးသည်။ Token များ မပါဝင်ပါ          |
| POST   | `/v0/management/api-call`    | Body `{ auth_index, method, url, header?, data? }`။ ခွင့်ပြုစာရင်းပါ တောင်းဆိုမှုတစ်ခုကို အကောင့်၏ token ဖြင့် ပေးပို့ပြီး `{ status_code, body }` ကို ပြန်ပေးသည် |
| POST   | `/v0/management/reset-quota` | Body `{ auth_index }`။ အကောင့်တစ်ခု၏ connection cooldown၊ model lockout များနှင့် Codex per-scope cooldown များကို ရှင်းလင်းသည်                                   |

- `auth_index` သည် OmniRoute connection id ဖြစ်သည်။ `provider` သည် `claude` သို့မဟုတ် `codex` ဖြစ်သည် (OAuth connection များသာဖြစ်ပြီး `anthropic` API-key provider ကို မဖော်ပြပါ)။ Codex အတွက် `id_token.chatgpt_account_id` သည် သိမ်းထားသော workspace id ဖြစ်ပြီး `plan_type` သည် သိမ်းထားသော plan ဖြစ်သည်။
- `api-call` သည် အထွေထွေ proxy မဟုတ်ပါ။ Claude `GET
https://api.anthropic.com/api/oauth/usage` နှင့် Codex `GET
https://chatgpt.com/backend-api/wham/usage`၊ `GET .../wham/rate-limit-reset-credits` နှင့် `POST .../wham/rate-limit-reset-credits/consume` ကိုသာ လက်ခံပြီး တစ်ခုချင်းစီသည် ကိုက်ညီသော provider ၏အကောင့်အတွက်သာ ဖြစ်ရမည်။ အခြားအရာအားလုံးသည် upstream ကို မဆက်သွယ်ဘဲ `403` ပြန်ပေးသည်။ ခေါ်သူ၏ `Authorization` header (`$TOKEN$` placeholder အပါအဝင်) ကို လျစ်လျူရှုသည်။ OmniRoute က connection ၏ access token ကို ထည့်ပေးပြီး သက်တမ်းကုန်ခါနီးလျှင် အရင် refresh လုပ်သည်။ ခွင့်ပြုစာရင်းထဲရှိ header များကိုသာ ဆက်ပို့သည် (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`)။ `Chatgpt-Account-Id` မပါလျှင် သိမ်းထားသော workspace id ကို မူလအဖြစ် သုံးသည်။ ပထမ upstream response သည် `401` ဖြစ်လျှင် တစ်ကြိမ် refresh လုပ်ပြီး access token ပြောင်းမှသာ ထပ်ကြိုးစားသည်။ upstream attempt တစ်ခုချင်းစီသည် 15 စက္ကန့်အကြာတွင် timeout ဖြစ်ပြီး connection ၏ proxy ကို သုံးသည်။
- `reset-quota` သည် terminal state များ (banned, expired, credits_exhausted) ကို မပြောင်းပါ။ မသိသော `auth_index` သည် `404` ပြန်ပေးသည်။

**အထောက်အထားပြခြင်း:** dashboard session သို့မဟုတ် `manage`-scoped API key လိုအပ်ပြီး login ပိတ်ထားသည့်အခါတွင်ပင်
လိုအပ်သည် (`ALWAYS_PROTECTED_API_PATHS` တွင် လမ်းကြောင်းများ ပါဝင်သောကြောင့်)။ Inference-only key များသည် `403` ရရှိသည်။ အရင်းအမြစ်-
`src/lib/cliproxyCompat/managementApi.ts`.

စင့်ခ်လုပ်ထားသော/တင်သွင်းထားသော မော်ဒယ်များအတွက် `PUT /api/provider-models` သည် `provider`၊ `modelId` နှင့်
`maxOutputTokenOverride` တို့ကို လက်ခံသည်။ အပေါင်းကိန်းပြည့်တစ်ခုသည် ကိုယ်တိုင်သတ်မှတ်ထားသော output-token အမြင့်ဆုံးကန့်သတ်ချက်ကို သတ်မှတ်ပေးပြီး `null`
သည် ၎င်းကို ရှင်းလင်းကာ မူလတန်ဖိုးသို့ ပြန်ထားပေးသည်။ `GET /api/provider-models?provider=<provider>` သည် custom-model row မရှိသော မော်ဒယ်များအပါအဝင်
ဤတန်ဖိုးများကို `modelOutputOverrides` တွင် ပြန်ပေးသည်။ ဤ override သည် runtime `max_output_tokens` စွမ်းဆောင်ရည်ကို အသုံးပြုပြီး မော်ဒယ်ကို
ပြန်လည်စင့်ခ်လုပ်ပြီးနောက်တွင်လည်း ဆက်လက်တည်ရှိသည်။ OpenAI-compatible provider စာမျက်နှာတွင်လည်း တူညီသော တည်းဖြတ်/ရှင်းလင်းထိန်းချုပ်မှုများကို ပေးထားပြီး
vision support ကို အတိအလင်းပံ့ပိုးသည့် မော်ဒယ်များကို အမှတ်အသားပြုထားသည်။

ကိုက်ညီသော provider node တစ်ခုတွင် write paths (`POST`၊ `PUT`၊ `PATCH`၊ `DELETE` နှင့်
`/api/provider-models/validate-and-add`) သည် မော်ဒယ် id ကို upstream id အတိုင်းသာ သိမ်းဆည်းသည်။ node ၏ ကိုယ်ပိုင် prefix ဖြင့် ရှေ့ဆက်ထားသော listing မှ
ကူးထည့်ထားသည့် id ဖြစ်ပါက ရှေ့တွင်ရှိသော node prefix များကို ပေါင်းစည်းကာ တစ်ခုတည်းအဖြစ် ပြုလုပ်ပြီး သိမ်းဆည်းသည်။ တုံ့ပြန်ချက်များတွင်လည်း သိမ်းဆည်းထားသော id ကိုသာ ပြန်ပေးသည်။
Canonical provider များ၏ slash ပါသော id များ (ဥပမာ `nvidia/nemotron-…`) ကို မူရင်းအတိုင်း သိမ်းဆည်းသည်။ `/v1/models` သည် stacked
`<prefix>/<prefix>/<model>` id ကို မည်သည့်အခါမျှ ထုတ်ပေးမည်မဟုတ်ပါ။

စိတ်ကူးချမှုကို အတိအလင်း ပိတ်ထားသည့် ရွေးချယ်မှုများကို upstream backend သို့ လိုက်လျောညီထွေဖြစ်အောင် Custom Chat Completions node များက ပြောင်းလဲပေးသည်။ အောင်မြင်သော
ချိတ်ဆက်မှု စမ်းသပ်မှုတစ်ခုသည် `/models` entry တွင် အသိအမှတ်ပြုထားသော `owned_by` တန်ဖိုးဖြစ်သည့်
`vllm`၊ `sglang` သို့မဟုတ် `llamacpp` တစ်ခုခုကို အတည်ပြုပေးထားသော တိကျသည့် model ID တစ်ခုချင်းစီအတွက်
chat-template ထိန်းချုပ်မှုများကို အလိုအလျောက် ရွေးချယ်ပေးသည်။ ပွင့်လင်းမြင်သာသော OpenAI-compatible
wrapper များသည် မူရင်း model entry ကို nested `openai` object အတွင်း ထိန်းသိမ်းထားနိုင်သည်။ detection သည်
ထိုကဲ့သို့သော envelope များကို အများဆုံး သုံးဆင့်အထိ လိုက်လံစစ်ဆေးသည်။ ownership မရှိခြင်း၊ မသိရှိခြင်း သို့မဟုတ်
အချင်းချင်းကွဲလွဲခြင်းရှိသော model များသည် ပုံမှန် OpenAI အပြုအမူကို ဆက်လက်အသုံးပြုသည်။ detection သည်
ရှိပြီးသား catalog request ကို ပြန်လည်အသုံးပြုပြီး completion token များကို ထုတ်လုပ်ခြင်းမရှိပါ။ ချိတ်ဆက်မှု endpoint
ပြောင်းလဲသည့်အခါ ၎င်းကို ပယ်ဖျက်သည်။

ထို metadata ကို မဖော်ပြသည့် backend တစ်ခုအတွက် အပြုအမူကို သတ်မှတ်ထားလိုပါက ရှိပြီးသား partial
provider update API ကို အသုံးပြုပါ—

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ထို body ကို `PUT /api/providers/<connection-id>` ဖြင့် ပေးပို့ပါ။ ထို connection တွင် explicit
reasoning effort `none` ကို `chat_template_kwargs.thinking=false` နှင့်
`chat_template_kwargs.enable_thinking=false` အဖြစ် ပေးပို့သည်။ Explicit native template တန်ဖိုးများသည်
server-side reasoning rule တစ်ခုက effort တစ်ခုကို အတင်းသတ်မှတ်ခြင်းမရှိသရွေ့ ဦးစားပေးအာဏာရှိသည်။ ဤ setting သည်
custom OpenAI-compatible connection တစ်ခုက Chat Completions body ကို dispatch လုပ်သည့်အခါတွင်သာ သက်ရောက်သည်။
Responses request များနှင့် ပုံမှန် provider များသည် ၎င်းတို့၏ native request ပုံစံကို ဆက်လက်အသုံးပြုသည်။
ပုံမှန် OpenAI `reasoning_effort` passthrough ကို အတင်းအသုံးပြုရန် `reasoningControl` ကို `openai` သို့ သတ်မှတ်ပါ။
အလိုအလျောက် detection ကို အသုံးပြုရန် ၎င်းကို ချန်ထားပါ သို့မဟုတ် `null` သို့ သတ်မှတ်ပါ။

Claude Code auto-mode classifier request များတွင် explicit reasoning controls မပါရှိပါက native thinking ကို
ပုံမှန်အားဖြင့် disabled အဖြစ် သတ်မှတ်သည်။ detection သည် model name များ သို့မဟုတ် completion limit များကို
မသုံးဘဲ Claude-format request များရှိ classifier ၏ system marker ကို အသုံးပြုသည်။ Explicit body controls၊
ထောက်ပံ့ထားသော effort/thinking header များ၊ routing rule များနှင့် resolved model effort တို့သည် ၎င်းတို့၏
ရှိပြီးသား ဦးစားပေးအစီအစဉ်ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ classifier stage နှစ်ခုစလုံးသည် ၎င်းတို့၏ prompt များ၊
completion limit များ၊ stop sequence များနှင့် upstream မှ အမှန်တကယ်ရရှိသော permission verdict များကို
ဆက်လက်ထိန်းသိမ်းထားသည်။ ဒုတိယ stage သည် ၎င်းတောင်းဆိုထားသော မြင်နိုင်သည့် reasoning ကို ပုံမှန်စာသားအဖြစ်

#### မော်ဒယ် limit ရင်းမြစ်

`GET /api/models?withLimits=1` (ထို့အပြင် `true` ကိုလည်း အသုံးပြုနိုင်သည်။ `0`/`false` သို့မဟုတ်
မထည့်သွင်းထားပါက မူရင်း payload ကို မပြောင်းလဲစေပါ) သည် model row တစ်ခုချင်းစီသို့ `contextWindow`,
`maxInputTokens`, `maxOutputTokens` နှင့် `capsSource` object ကို ထည့်ပေးသည်။ `capsSource` သည် limit
တစ်ခုချင်းစီကို ပံ့ပိုးပေးသည့် rule ကို ဖော်ပြသဖြင့် အံ့အားသင့်ဖွယ် limit တစ်ခု (ဥပမာ 1M model ပေါ်ရှိ 128k)
ကို ၎င်း၏ မူလရင်းမြစ်အထိ ခြေရာခံနိုင်သည်။ ဖြေရှင်းပြီးသားတန်ဖိုးများသည် routing က အသုံးပြုသည့် တန်ဖိုးများနှင့်
တူညီသည်။ ဤ flag သည် field များကိုသာ ထပ်တိုးပြီး မည်သည့်တန်ဖိုးကိုမျှ မပြောင်းလဲပါ။ အခြား `withLimits`
တန်ဖိုးတစ်ခုခုကို `400` ဖြင့် ငြင်းပယ်သည်။

| `capsSource` value                           | Origin                                                                 |
| -------------------------------------------- | ---------------------------------------------------------------------- |
| `override:context`                           | Persisted context-window override (`model_context_overrides`)          |
| `override:max_input` / `override:max_output` | Persisted `max_input_tokens` / `max_output_tokens` capability override |
| `static-authoritative:<provider>/<model>`    | Static authoritative context-window table                              |
| `synced:<provider>/<model>`                  | models.dev synced capability row                                       |
| `registry:<provider>/<model>`                | Provider registry entry                                                |
| `spec:<model>`                               | Static model spec                                                      |
| `effort-base:` prefix                        | Row borrowed from the base model of an effort-suffixed variant         |
| `none`                                       | No source declares the limit (value is `null`)                         |

အကောင်အထည်ဖော်မှု: `src/lib/modelCapabilities.ts` ရှိ `getResolvedModelCapabilitiesWithLimitSources()`
နှင့် `src/lib/modelCapabilityLimits.ts` ရှိ precedence chain များ။

### ဗီဒီယိုဘောင်ကို တူးဆွခြင်း။

`GET /api/v1/video-bridge/drilldown` reads a tenant-bound opaque handle returned in `x-omniroute-video-drilldown` after an explicitly consented Video Bridge request. Both reads and `DELETE` always require a valid API key and the operator's independent `modalityBridgeVideoDrilldownRemoteEnabled` permission. Production retention additionally requires `modalityBridgeVideoDrilldownEnabled` and strict per-part `drilldown: true`. If the key has a nonempty endpoint allowlist, it must include `video` for both GET and DELETE, whether the caller uses `/v1` or `/api/v1`.

GET စုံစမ်းမှု- လိုအပ်သော `handle`; ရွေးချယ်နိုင်သော `variant` (`preview`, `standard`, `detail`), `limit` (1–8; အမွေအနှစ် `frames` လက်ခံသော်လည်း `limit`)၊ သုညအခြေခံ `page` နှင့် `start`/`end` စက္ကန့်တို့ကို ပေါင်းစပ်၍မရပါ။ အာရုံစူးစိုက်မှုဘောင်နှစ်ခုလုံးကို ဖြည့်သွင်းသောအခါ `end` `start` ထက်ကြီးနေရပါမည်။ Duplicate/unknown query keys များကို ငြင်းပယ်ထားသည်။ အောင်မြင်သော တုံ့ပြန်မှုများတွင် `derivation`၊ `durationSeconds`၊ `frames`၊ `hasMore`၊ `page`၊ `variant` နှင့် ရွေးချယ်နိုင်သော `focusWindow` ပါ၀င်သည် . no-store JSON Base64 အပါအဝင် 32 MiB တွင် ကန့်သတ်ထားသည်။ အဆမတန်ထွက်ရှိမှု 413 ကို ပြန်ပေးသည်။ ဘောင်နည်းနည်းတောင်းပါ။

`DELETE /api/v1/video-bridge/drilldown?handle=...` `{ "removed": 0|1 }` ပြန်ပေးသည်။ အမည်မသိ၊ သက်တမ်းကုန်ပြီး သော့ဖြတ်ထားသော GETs များသည် ခွဲခြား၍မရသော 404 တုံ့ပြန်မှုများ၊ cross-key DELETE ပိုင်ရှင်၏ဝင်ရောက်မှုကို မဖယ်ရှားနိုင်ပါ။ ပိတ်ထားသောဝင်ရောက်ခွင့်သည် 403၊ missing/invalid စစ်မှန်ကြောင်းအထောက်အထားပြခြင်း 401၊ မမှန်ကန်သောမေးမြန်းချက် 400၊ ပယ်ဖျက်ခြင်း 499 နှင့် ယာယီအမှားများ 503 ကို ပြန်ပေးသည်။ လက်ကိုင်များသည် လုပ်ငန်းစဉ်အတွင်းမှဖြစ်ပြီး၊ ဆယ်မိနစ်အကြာတွင် သက်တမ်းကုန်ဆုံးကာ ပြန်လည်စတင်ခြင်းတွင် မရှင်သန်ပါ။ လက်ကိုင်အသစ်များသည် `v1.` နှင့် 32-byte ကျပန်း Base64URL တိုကင်ကို အသုံးပြုသည်။ တိုကင်နံပါတ်များကိုသာ သိမ်းဆည်းထားသည်။ Legacy 64-hex တိုကင်များသည် လိုက်ဖက်ညီမှုအတွက် အဓိပ္ပါယ်တူဖြင့် ဖတ်နိုင်သည်။ သဘောတူညီချက်၊ ခွဲတမ်းနှင့် ကွဲပြားသော ဆင်းသက်လာမှုအသေးစိတ်အတွက် [ဗီဒီယိုတံတားအကာအရံများကို](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) ကြည့်ပါ။

### ဗားရှင်းနှင့် ထုတ်လွှင့်မှုချန်နယ်

```bash
GET /api/system/version
```

Loopback သီးသန့် စီမံခန့်ခွဲမှု route (admin auth) ဖြစ်သည်။ လက်ရှိအသုံးပြုနေသောဗားရှင်း၊ နောက်ဆုံးထုတ်ဝေထားသောဗားရှင်းနှင့် အလိုအလျောက်အပ်ဒိတ်အခြေအနေတို့ကို ပြန်ပေးသည်။ `releaseChannel` နှင့် `channels` တို့သည် ထပ်တိုးထည့်သွင်းထားသော field များဖြစ်သည် (rail 3.8.54)။ `channel` သည် ၎င်း၏မူလအဓိပ္ပာယ်အတိုင်း dashboard updater အသုံးပြုသည့် deployment mode (`npm`, `source` သို့မဟုတ် `docker-compose`) ကို ဆိုလိုသည်။

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — လက်ရှိ build ၏ npm ချန်နယ်ဖြစ်သည်။ `-nightly.*` ဗားရှင်းများအတွက် `nightly`၊ အခြား pre-release များ (`-rc.*`, `-beta.*`, `-alpha.*`) အတွက် `next`၊ `channels.latest` ထက် major ဗားရှင်းနိမ့်သော stable ဗားရှင်းအတွက် `lts`၊ ထို့အပြင် `latest` ဖြစ်သည်။ ထုတ်ဝေချိန်တွင် npm dist-tag ကို ရွေးချယ်သည့် `scripts/release/dist-tag.mjs` နှင့် တူညီသောစည်းမျဉ်းများကို အသုံးပြုသည်။
- `channels` — `npm view omniroute dist-tags` မှ ရရှိသော dist-tag တစ်ခုချင်းစီ၏ ထုတ်ဝေထားသော နောက်ဆုံးဗားရှင်းဖြစ်သည် (registry HTTP fallback ပါဝင်သည်)။ `latest` နှင့် တူညီသော ၁၀ မိနစ် TTL ဖြင့် cache ပြုလုပ်ထားသည်။ `latest` သည် အမြဲပါဝင်သည် (`latest` field သို့ fallback ပြုလုပ်ပြီးနောက် `"unavailable"` သို့ ပြောင်းသည်)။ `next`, `nightly` နှင့် `lts` တို့သည် ထို dist-tag ရှိမှသာ ပါဝင်သည်။ `Cache-Control: no-cache` request သည် lookup နှစ်ခုလုံးကို ပြန်လည် refresh လုပ်သည်။

ချန်နယ်မော်ဒယ် (`latest` = 4.0 GA မထွက်မီ v3၊ `next` = rc၊ `nightly` = `develop` builds၊ `lts` = 4.0 GA ထွက်ပြီးနောက် v3 patches) ကို `docs/ops/RELEASE_STRATEGY.md` တွင် ဖော်ပြထားသည်။

## အသံမှ စာသားပြောင်းခြင်း

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

ပြင်ဆင်သတ်မှတ်ထားသော STT provider တစ်ခုခုကို အသုံးပြု၍ အသံဖိုင်များကို စာသားပြောင်းပါ။ ပထမဆုံး path
segment သည် native provider (`openai/…`, `deepgram/…`) ကို ရွေးချယ်ပေးသည်။ အခြား vendor ၏ model ကို
ပြန်လည်ဖြန့်ဝေပေးသော gateway များသည် qualified id
(`openrouter/deepgram/nova-3`) ကို အသုံးပြုသည်။

**တောင်းဆိုချက်:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**တုံ့ပြန်ချက်:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**ဥပမာ model ids:** `openai/whisper-1` (OpenAI key လိုအပ်သည်)၊
`openrouter/deepgram/nova-3` (OpenRouter key လိုအပ်သည်)၊
`deepgram/nova-3` (native Deepgram key လိုအပ်သည်)။ သီးခြား
`deepgram/nova-3` တောင်းဆိုချက်သည် OpenRouter ကို အသုံးမပြုပါ။

**ပံ့ပိုးထားသော ဖိုင်အမျိုးအစားများ:** `mp3`၊ `wav`၊ `m4a`၊ `flac`၊ `ogg`၊ `webm`။

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** Gemini Live
WebSocket မှတစ်ဆင့် file-mode transcription ကို လုပ်ဆောင်သည် (Gemini API key လိုအပ်သည်)။ အပ်လုဒ်ကို
`ffmpeg` ဖြင့် 16 kHz mono PCM သို့ ပြောင်းပြီး (`PATH` တွင် ရှိရမည်၊ သို့မဟုတ် ဖိုင်သည် 16 kHz mono PCM WAV ဖြစ်ပြီးသားဖြစ်ရမည်) session သို့
streaming ပြုလုပ်ကာ အပြီးသတ်စာသားကို `{ "text": "..." }` အဖြစ် ပြန်ပေးသည်။ ရွေးချယ်နိုင်သော `language` နှင့် `prompt` form fields
များကို ဆက်လက်ပေးပို့သည်။ ကန့်သတ်ချက်များမှာ 25 MiB ထက်ကြီးသော အပ်လုဒ်များ သို့မဟုတ် decode ပြုလုပ်ပြီးနောက် 10 မိနစ်ထက်ရှည်သော အသံများအတွက်
`413` ပြန်ပေးသည်။ ပြောင်းလဲမှုလုပ်ဆောင်ချိန် 60 s ထက်ကျော်လွန်ပါက ရပ်တန့်စေပြီး `504` ပြန်ပေးသည်။ API key ကို
`x-goog-api-key` header တွင်သာ ပေးပို့ပြီး WebSocket URL တွင် မည်သည့်အခါမျှ မထည့်သွင်းပါ။

## Token ထည့်သွင်းထားသော VS Code / Header မပါသော Alias များ

Integration တစ်ခုသည် `Authorization` header ကို ထည့်သွင်းမပေးနိုင်ဘဲ API key ကို base URL ထဲတွင် ထည့်သွင်းထားရန် လိုအပ်သည့်အခါ ဤ alias များကို အသုံးပြုပါ။

```bash
# OpenAI-style catalog alias
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-style chat aliases
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-style aliases
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

နမူနာ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

မှတ်ချက်များ:

- Token ထည့်သွင်းထားသော alias များသည် `/v1/*` နှင့် `/api/tags` တို့ကဲ့သို့ handler များကို ပြန်လည်အသုံးပြုသောကြောင့် တုံ့ပြန်မှုပုံစံများသည် တူညီနေမည်ဖြစ်သည်။
- Client က custom header များကို ပံ့ပိုးပါက `Authorization: Bearer ...` ကို ဦးစားပေးအသုံးပြုပါ။
- URL အခြေပြု token များသည် reverse-proxy မှတ်တမ်းများ၊ browser မှတ်တမ်းနှင့် OmniRoute ပြင်ပရှိ telemetry များတွင် ပေါ်လာနိုင်သည်။ ၎င်းတို့ကို မူရင်း authentication နည်းလမ်းအဖြစ်မဟုတ်ဘဲ လိုက်ဖက်ညီမှုအတွက် ရွေးချယ်စရာတစ်ခုအဖြစ်သာ သတ်မှတ်အသုံးပြုပါ။

## Token Limits

API key တစ်ခုချင်းစီအတွက် **token** ဘတ်ဂျက်များ (အထက်တွင်ဖော်ပြထားသော USD အခြေပြု Budget နှင့် သီးခြား) ဖြစ်သည်။ Request လမ်းကြောင်းပေါ်တွင် တိုက်ရိုက်အကျုံးဝင်ပြီး၊ key တစ်ခု၏ လက်ရှိ window အသုံးပြုမှုသည် ၎င်း၏ limit သို့ ရောက်ရှိပါက request များကို `429 Too Many Requests` ဖြင့် ပယ်ချသည်။ Limits များကို သီးခြား `model` တစ်ခု၊ `provider` တစ်ခုအတွက် သတ်မှတ်နိုင်သကဲ့သို့ key တစ်ခုလုံးအတွက် `global` အဖြစ်လည်း သတ်မှတ်နိုင်သည်။ Request တစ်ခုနှင့် ကိုက်ညီသော limit များစွာရှိပါက အတင်းကျပ်ဆုံး limit ကို အသုံးပြုသည်။

```bash
# key တစ်ခု၏ token limits များကို စာရင်းပြုစုရန် (လက်ရှိ window အသုံးပြုမှု ပါဝင်သည်)
GET /api/usage/token-limits?apiKeyId=key-123

# token limit တစ်ခုကို ဖန်တီးရန် သို့မဟုတ် အပ်ဒိတ်လုပ်ရန်
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id ဖြင့် token limit တစ်ခုကို ဖျက်ရန်
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schema notes** (`setTokenLimitSchema`): `apiKeyId` နှင့် `scopeType` (`model` | `provider` | `global`) တို့သည် မဖြစ်မနေလိုအပ်သည်။ `scopeType` သည် `global` မဟုတ်ပါက `scopeValue` လိုအပ်သည် (`model` scope အတွက် model id၊ `provider` scope အတွက် provider id ဥပမာ)။ `tokenLimit` သည် အပေါင်းကိန်းပြည့် ဖြစ်ရမည် (string မှ coercion ပြုလုပ်သည်)။ ရွေးချယ်နိုင်သောအရာများမှာ `id` (ဖန်တီးရန် ချန်ထားပြီး၊ အပ်ဒိတ်လုပ်ရန် ထည့်ပေးရန်)၊ `resetInterval` (`daily` | `weekly` | `monthly`၊ မူရင်းမှာ `monthly`)၊ `resetTime` (`HH:MM`) နှင့် `enabled` (မူရင်းမှာ `true`) တို့ဖြစ်သည်။ `GET` response များတွင် limit တစ်ခုချင်းစီအတွက် `tokensUsed`၊ `remaining`၊ `windowStart`၊ `periodStartAt` နှင့် `nextResetAt` တို့ကို ထပ်မံဖြည့်စွက်ပေးသည်။ ၎င်းသည် management-class endpoint ဖြစ်ပြီး (auth ကို authz pipeline မှ ဗဟိုပြု၍ enforce လုပ်သည်)။

## Request Processing

1. Client က `/v1/*` သို့ request ပို့သည်
2. Route handler က `handleChat`၊ `handleEmbedding`၊ `handleAudioTranscription` သို့မဟုတ် `handleImageGeneration` ကို ခေါ်သည်
3. Model ကို ဖြေရှင်းသတ်မှတ်သည် (တိုက်ရိုက် provider/model သို့မဟုတ် alias/combo)
4. Account availability filtering ဖြင့် local DB မှ credentials များကို ရွေးချယ်သည်
5. Chat အတွက် `handleChatCore` က semantic/signature cache ကို စစ်ဆေးပြီး combo compression settings များကို ဖြေရှင်းသတ်မှတ်သည်
6. ဖွင့်ထားပါက provider translation မပြုလုပ်မီ proactive compression ကို လုပ်ဆောင်သည် (`lite`၊ Caveman၊ RTK သို့မဟုတ် stacked)
7. Provider executor က upstream request ကို ပို့သည်
8. Response ကို client format သို့ ပြန်လည်ဘာသာပြန်ပေးသည် (chat) သို့မဟုတ် မပြောင်းလဲဘဲ ပြန်ပေးသည် (embeddings/images/audio)
9. Usage၊ compression analytics နှင့် request logs များကို မှတ်တမ်းတင်သည်
10. Combo rules များအရ error ဖြစ်ပါက fallback ကို အသုံးပြုသည်

Architecture အပြည့်အစုံကို [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md) တွင် ကြည့်နိုင်သည်။

## Combo Management

အဆင့်မြင့် routing combo များ (`/api/combos*` အောက်တွင် အနှစ်ချုပ်ဖော်ပြထားပြီးဖြစ်သည်) ကို model id pattern တစ်ခုမှ 1:1 mapping ပြုလုပ်နိုင်သဖြင့် OpenAI-style model id တစ်ခုကို combo သို့ ပွင့်လင်းမြင်သာစွာ redirect ပြုလုပ်နိုင်သည်။

| Method | Path                             | Description                                                                       |
| ------ | -------------------------------- | --------------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | model→combo mappings အားလုံးကို စာရင်းပြုစုရန်                                    |
| POST   | `/api/model-combo-mappings`      | mapping ဖန်တီးရန် — body: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | mapping တစ်ခုချင်းစီကို ရယူရန်                                                    |
| PUT    | `/api/model-combo-mappings/[id]` | ရှိပြီးသား mapping ၏ fields များကို အပ်ဒိတ်လုပ်ရန်                                |
| DELETE | `/api/model-combo-mappings/[id]` | mapping တစ်ခုကို ဖယ်ရှားရန်                                                       |

**Auth:** management session/API key (`requireManagementAuth`)။

OmniRoute ဖြစ်ရပ်များ (တောင်းဆိုမှု ပြီးဆုံးခြင်း၊ quota ကုန်ဆုံးခြင်း၊ key လဲလှယ်ခြင်း စသည်တို့) အတွက် အပြင်ဘက်သို့ ပို့သော webhook စာရင်းသွင်းမှုများ။

| Method | Path                      | Description                                                                           |
| ------ | ------------------------- | ------------------------------------------------------------------------------------- |
| GET    | `/api/webhooks`           | webhook များကို စာရင်းပြုစုရန် (secrets များကို `<prefix>...` အဖြစ် ဖုံးကွယ်ထားသည်)   |
| POST   | `/api/webhooks`           | webhook ဖန်တီးရန် — body: `{url, events?: ["*"], secret?, description?}`              |
| GET    | `/api/webhooks/[id]`      | webhook တစ်ခုကို ရယူရန်                                                               |
| PUT    | `/api/webhooks/[id]`      | url/events/secret/description ကို အပ်ဒိတ်လုပ်ရန်                                      |
| DELETE | `/api/webhooks/[id]`      | webhook တစ်ခုကို ဖယ်ရှားရန်                                                           |
| POST   | `/api/webhooks/[id]/test` | စမ်းသပ် payload တစ်ခုကို webhook URL သို့ ပို့ပြီး ပေးပို့မှုအခြေအနေကို ပြန်လည်ရယူရန် |

**Auth:** စီမံခန့်ခွဲမှု session/API key (`requireManagementAuth`)။

## မှတ်ပုံတင်ထားသော သော့များ (အလိုအလျောက် စီမံခန့်ခွဲခြင်း)

အလိုအလျောက်သော့စီမံခန့်ခွဲမှုစနစ်ခွဲမှ API သော့များကို ကျောထောက်နောက်ခံ provider/account နှင့် daily/hourly ခွဲတမ်းများဖြင့် ထုတ်ကာ လှည့်ရန် အသုံးပြုသည်။

| နည်းလမ်း | မဂ်                                   | ဖော်ပြချက်                                                                                                                                                                                                           |
| -------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/v1/registered-keys`             | စာရင်းသွင်းထားသောသော့များစာရင်း (masked prefix များသာ)                                                                                                                                                               |
| POST     | `/api/v1/registered-keys`             | မှတ်ပုံတင်ထားသော သော့အသစ် — ကိုယ်- `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}` ကိုထုတ်ပါ။ ကီးစိုကို ပြန်ပေးသည်။**တစ်ကြိမ်** . ခွဲတမ်းငြင်းဆိုမှုတွင် `429` ပြန်ပေးသည်။ |
| GET      | `/api/v1/registered-keys/[id]`        | မှတ်ပုံတင်ထားသောကီး၏ မက်တာဒေတာကို ရယူပါ (ကုန်ကြမ်းမရှိပါ)                                                                                                                                                            |
| DELETE   | `/api/v1/registered-keys/[id]`        | မှတ်ပုံတင်ထားသောသော့ကို ရုပ်သိမ်းပါ။                                                                                                                                                                                 |
| POST     | `/api/v1/registered-keys/[id]/revoke` | တိကျပြတ်သားသော အဆုံးမှတ်ကို ရုပ်သိမ်းခြင်း ( DELETE နှင့် တူညီသော အကျိုးသက်ရောက်မှု)                                                                                                                                 |
| GET      | `/api/v1/providers/[provider]/limits` | ဝန်ဆောင်မှုပေးသူ၏ ထုတ်ပေးသည့်စာထုပ်များကို ဖတ်ပါ။                                                                                                                                                                    |
| PUT      | `/api/v1/providers/[provider]/limits` | ဝန်ဆောင်မှုပေးသူ၏ ထုတ်ပေးသည့်စာထုပ် — ကိုယ်ထည်ကို သတ်မှတ်ပါ- `{maxActiveKeys?, dailyIssueLimit?, hourlyIssueLimit?}`                                                                                                 |
| GET      | `/api/v1/accounts/[id]/limits`        | အကောင့်၏ထုတ်ပေးသည့်စာထုပ်များကိုဖတ်ပါ။                                                                                                                                                                               |
| PUT      | `/api/v1/accounts/[id]/limits`        | အကောင့်၏ထုတ်ပေးသည့်စာထုပ် — ဝန်ဆောင်မှုပေးသည့်လမ်းကြောင်းအတိုင်း အလားတူကိုယ်ထည်ကို သတ်မှတ်ပါ။                                                                                                                        |

**အထောက်အထား-** စီမံခန့်ခွဲမှု session/API သော့ (`requireManagementAuth`) — `/api/keys` ကဲ့သို့ တူညီသော အကာအကွယ် − ဒက်ရှ်ဘုတ် စက်ရှင်၊ ဒေသန္တရ CLI တိုကင် သို့မဟုတ် `manage`/`admin` နယ်ပယ်ပါရှိသော API သော့၊ အနုမာန-သီးသန့် API သော့များသည် `403` ရရှိသည်။ `/v1/quotas/check` နှင့် `/v1/issues/report` ကိုလည်းကြည့်ပါ။

## Agents ပရိုတိုကော

OmniRoute အသုံးပြုသူများကိုယ်စား အဝေးမှ လုပ်ဆောင်သည့် Cloud agent tasks (Claude Code, Codex Cloud, OpenHands စသည်)။

| Method | Path                          | Description                                                                                                                                                  |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/agents/tasks`        | Tasks များကို စာရင်းပြုစုရန် — ရွေးချယ်နိုင်သော `?provider=`, `?status=`, `?limit=` (1–500၊ မူရင်း 50)                                                       |
| POST   | `/api/v1/agents/tasks`        | Task ဖန်တီးရန် — `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`) ဖြင့် body ကို အတည်ပြုသည်။ Task envelope ဖြင့် `201` ပြန်ပေးသည် |
| DELETE | `/api/v1/agents/tasks?id=...` | Task တစ်ခုကို ဖျက်ရန်                                                                                                                                        |
| GET    | `/api/v1/agents/tasks/[id]`   | Task ကို ဖတ်ရန် — `external_id` သတ်မှတ်ထားပါက upstream cloud agent ထံမှ status ကို တစ်ပြိုင်နက် refresh လုပ်သည်                                              |
| POST   | `/api/v1/agents/tasks/[id]`   | ခွဲခြားသတ်မှတ်ထားသော action — `{action: "approve"}`, `{action: "message", message}`, သို့မဟုတ် `{action: "cancel"}`                                          |
| DELETE | `/api/v1/agents/tasks/[id]`   | id ဖြင့် သတ်မှတ်ထားသော task ကို ဖျက်ရန်                                                                                                                      |

> **အထောက်အထားပြခြင်း:** method တိုင်းတွင် management auth လိုအပ်သည် (`requireCloudAgentManagementAuth`)။ v3.8.0 မတိုင်မီတွင် ၎င်းတို့သည် authentication မရှိခဲ့ပါ — breaking change အတွက် commit `588a0333` ကို ကြည့်ပါ။

```bash
# Claude Code cloud task တစ်ခု ဖန်တီးရန်
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Authorization: Bearer your-management-key" \
  -H "Content-Type: application/json" \
  -d '{"providerId":"claude-code-cloud","prompt":"Fix the failing test","source":{"repo":"...","branch":"..."}}'
```

## Management Proxies

Provider များ၊ account များ သို့မဟုတ် အားလုံးအတွက် သတ်မှတ်အသုံးပြုနိုင်သော Outbound HTTP(S)/SOCKS proxies များ။

| Method | Path                                         | Description                                                                                                                                                                                                   |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | Proxy များကို စာရင်းပြုစုရန် (`?id=` ဖြင့် တစ်ခုကို ပြန်ပေးသည်၊ `?id=&where_used=1` ဖြင့် assignment graph ကို ပြန်ပေးသည်)                                                                                    |
| POST   | `/api/v1/management/proxies`                 | Proxy ဖန်တီးရန် — `createProxyRegistrySchema` ဖြင့် body ကို အတည်ပြုသည်                                                                                                                                       |
| PATCH  | `/api/v1/management/proxies`                 | Proxy ကို အပ်ဒိတ်လုပ်ရန် — `updateProxyRegistrySchema` ဖြင့် body ကို အတည်ပြုသည် (`id` လိုအပ်သည်)                                                                                                             |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | Proxy ကို ဖျက်ရန် (assignment များကို ဖြုတ်ရန် `force=1` ကို အသုံးပြုပါ)                                                                                                                                      |
| GET    | `/api/v1/management/proxies/assignments`     | Assignment များကို စာရင်းပြုစုရန် — `proxy_id`, `scope`, `scope_id` တို့ဖြင့် filter လုပ်နိုင်သည်။ Connection တစ်ခုအတွက် လက်ရှိအသုံးပြုနေသော proxy ကို ဖြေရှင်းရန် `resolve_connection_id=<id>` ကို ပေးပို့ပါ |
| PUT    | `/api/v1/management/proxies/assignments`     | သတ်မှတ်ပေးရန် — `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) ဖြင့် body ကို အတည်ပြုသည်။ Dispatcher cache ကို ရှင်းလင်းသည်                                                                          |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | အစုလိုက် သတ်မှတ်ပေးရန် — `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) ဖြင့် body ကို အတည်ပြုသည်)                                                                                             |
| GET    | `/api/v1/management/proxies/health?hours=24` | အချိန်ကာလတစ်ခုအတွင်း proxy health ကို စုစည်းဖော်ပြရန် (အောင်မြင်မှု/မအောင်မြင်မှု အရေအတွက်၊ latency)                                                                                                          |

**အထောက်အထားပြခြင်း:** route တိုင်းတွင် management session/API key လိုအပ်သည် (`requireManagementAuth`)။

> Task description ထဲရှိ `POST /api/v1/management/proxies/[id]/assignments` နှင့် `POST /api/v1/management/proxies/[id]/health` တို့ကို အထက်တွင်ပြထားသော flat `/assignments` နှင့် `/health` routes များက ဆောင်ရွက်ပေးသည် — codebase တွင် id တစ်ခုချင်းစီအတွက် subroute များ မရှိပါ။

## ခံနိုင်ရည် (တိုးချဲ့ထားသည်)

OmniRoute သည် သီးခြားစီ လုပ်ဆောင်သည့် ယာယီပျက်ကွက်မှု ယန္တရား ၃ ခုကို ပံ့ပိုးပေးသည်။ အောက်ပါ စီမံခန့်ခွဲမှု endpoint များမှတစ်ဆင့် အော်ပရေတာများသည် ၎င်းတို့၏အခြေအနေကို ဖတ်ရှုနိုင်ပြီး အစားထိုးသတ်မှတ်နိုင်သည်-

| Scope               | State storage                              | Read                                      | Reset / clear                                                                                   |
| ------------------- | ------------------------------------------ | ----------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Provider breaker    | `domain_circuit_breakers` + in-memory      | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                                                    |
| Connection cooldown | `rateLimitedUntil` on provider connections | `/api/rate-limits`, `/api/providers/[id]` | (ပြန်လည်ဖွင့်ပေးမှုကို လိုအပ်သည့်အချိန်တွင် လုပ်ဆောင်သည်; provider PUT ဖြင့် ရှင်းလင်းနိုင်သည်) |
| Model lockout       | In-memory model-availability registry      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                                        |

`PATCH /api/resilience` သည် `providerBreaker.oauth` နှင့် `providerBreaker.apikey` အောက်တွင် provider breaker override များကို လက်ခံသည်။ Profile တစ်ခုစီတွင် `degradationThreshold`၊ `failureThreshold` နှင့် `resetTimeoutMs` တို့ကို သတ်မှတ်နိုင်သည်။ အဆိုပါ field များကို Dashboard → Settings → Resilience တွင်လည်း ပြသထားသည်။

```bash
# Model lockout တစ်ခုတည်းကို ရှင်းလင်းရန်
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Lockout အားလုံးကို ဖယ်ရှားရန်
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

အယူအဆဆိုင်ရာ အပြည့်အစုံ ရည်ညွှန်းချက်နှင့် breaker မူလတန်ဖိုးများအတွက် [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" နှင့် [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) ကို ကြည့်ပါ။

### Rate-Limit Queue နှင့် Auto-Enable Safety Net

- **ပံ့ပိုးထားသော write path**: `POST /api/rate-limits` ကို body `{"connectionId": "<id>", "enabled": true|false}` ဖြင့် အသုံးပြုခြင်းသည် connection တစ်ခုအတွက် rate-limit ကာကွယ်မှုကို ဖွင့်/ပိတ်ရန် ပံ့ပိုးထားသော စီမံခန့်ခွဲမှု endpoint ဖြစ်သည်။ `PUT /api/providers/[id]` သည် `rateLimitProtection` ကို ရည်ရွယ်ချက်ရှိရှိ ပြင်ဆင်ခြင်း သို့မဟုတ် ပြောင်းလဲခြင်း မလုပ်ပါ (#11278)။
- **`enabled: false` ၏ အဓိပ္ပာယ်**: `enabled: false` သတ်မှတ်ခြင်းသည် connection အတွက် အတိအကျ သတ်မှတ်ထားသော ကာကွယ်မှုကို ဖယ်ရှားပေးသော်လည်း active API-key connection တစ်ခုကို global auto-enable safety net (`autoEnableApiKeyProviders = true`) မှ ဖယ်ထုတ်ခြင်း မဟုတ်ပါ။ `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) တွင် `false` နှင့် `undefined` တို့သည် အဓိပ္ပာယ်တူသည်။ ထို့ကြောင့် အတိအကျ ကာကွယ်မှုမရှိသော active API-key connection များသည် auto-enable safety net အောက်တွင် ဆက်လက်ကာကွယ်ခံရမည်။
- **Global disable**: API-key connection များကို rate-limit queue များမပါဘဲ လည်ပတ်လိုပါက `RATE_LIMIT_AUTO_ENABLE=false` (env) ဖြင့် သို့မဟုတ် `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) ဖြင့် safety net ကို global အဆင့်တွင် ပိတ်ပါ။

## Skills

OmniRoute ကို စိတ်ကြိုက် executable handler များဖြင့် တိုးချဲ့ရန်နှင့် marketplace ပေါင်းစည်းမှုများအတွက် Skill framework ဖြစ်သည်။

| Method | Path                              | Description                                                                                                                                                    |
| ------ | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/skills`                     | ထည့်သွင်းထားသော skill များကို စာရင်းပြုစုရန် — `?q=`၊ `?mode=on\|off\|auto`၊ `?source=skillsmp\|skillssh\|local` ဖြင့် စစ်ထုတ်နိုင်ပြီး စာမျက်နှာခွဲပြနိုင်သည် |
| GET    | `/api/skills/[id]`                | Skill တစ်ခုကို ရယူရန်                                                                                                                                          |
| PUT    | `/api/skills/[id]`                | Skill ကို အပ်ဒိတ်လုပ်ရန် (name, description, mode, schema, handler, tags)                                                                                      |

## MCP ဆာဗာ

OmniRoute တွင် transport ၃ မျိုး (stdio၊ SSE၊ streamable-http) နှင့် scope သတ်မှတ်ထားသော tools များပါဝင်သည့် ထည့်သွင်းထားသော Model Context Protocol ဆာဗာ ပါဝင်သည်။ အောက်ပါ dashboard endpoint များသည် status/audit data များကို ဖတ်ရှုပြီး HTTP transport များအတွက် proxy အဖြစ် လုပ်ဆောင်သည်။

| နည်းလမ်း | လမ်းကြောင်း            | ဖော်ပြချက်                                                                                                                               |
| -------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/mcp/status`      | Heartbeat၊ transport၊ online အခြေအနေ၊ နောက်ဆုံးခေါ်ဆိုမှု၊ ထိပ်တန်း tools များ၊ ၂၄ နာရီအတွင်း အောင်မြင်မှုနှုန်း                         |
| GET      | `/api/mcp/tools`       | `name`၊ `description`၊ `scopes`၊ `phase`၊ `auditLevel`၊ `sourceEndpoints` ပါဝင်သည့် MCP tools စာရင်း                                     |
| GET      | `/api/mcp/sse`         | SSE transport အတွက် SSE stream ကို ဖွင့်ရန် (MCP ပိတ်ထားပါက သို့မဟုတ် transport မကိုက်ညီပါက `503` ပြန်ပေးသည်)                            |
| POST     | `/api/mcp/sse`         | SSE transport ပေါ်တွင် JSON-RPC frame ပေးပို့ရန်                                                                                         |
| GET      | `/api/mcp/stream`      | Streamable HTTP transport ၏ SSE ဘက်ကို ဖွင့်ရန် (ဆာဗာမှ စတင်ပေးပို့သော messages)                                                         |
| POST     | `/api/mcp/stream`      | Streamable HTTP transport ပေါ်တွင် JSON-RPC frame ပေးပို့ရန်                                                                             |
| DELETE   | `/api/mcp/stream`      | Streamable HTTP session ကို အဆုံးသတ်ရန်                                                                                                  |
| GET      | `/api/mcp/audit`       | audit log ကို query လုပ်ရန် — `?limit=`၊ `?offset=`၊ `?tool=`၊ `?success=true                                    \| false`၊ `?apiKeyId=` |
| GET      | `/api/mcp/audit/stats` | စုစည်းထားသော audit စာရင်းအင်းများ (စုစုပေါင်း၊ အောင်မြင်မှုနှုန်း၊ ပျမ်းမျှကြာချိန်၊ ထိပ်တန်း tools များ)                                |

**အထောက်အထားပြုခြင်း:** `sse`/`stream` transport များသည် MCP-specific auth surface ( `mcp` scope ပါသော Bearer API key) ကို လိုက်နာသည်။ `status`/`tools`/`audit*` route များကို dashboard မှ ဖတ်ရှုနိုင်သည် (dashboard host သို့ ရောက်ရှိနိုင်ခြင်းအပြင် အပိုအထောက်အထားပြုရန် မလိုအပ်ပါ)။

> HTTP transport နှစ်ခုလုံးကို `settings.mcpEnabled` နှင့် `settings.mcpTransport` တို့ဖြင့် ထိန်းချုပ်ထားသည် — transport မကိုက်ညီပါက `400`၊ MCP ပိတ်ထားသည့်အခြေအနေဖြစ်ပါက `503` ပြန်ပေးသည်။

## A2A ဆာဗာ

OmniRoute သည် စစ်ဆေးခြင်း/ဒက်ရှ်ဘုတ်အသုံးပြုမှုအတွက် A2A (Agent-to-Agent) JSON-RPC 2.0 endpoint နှင့် REST wrapper တစ်ခုကို ပံ့ပိုးပေးသည်။

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY သတ်မှတ်ထားခြင်းမရှိပါကသာ ရွေးချယ်နိုင်သည်
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

ပံ့ပိုးထားသော method များ (`settings.a2aEnabled` ဖွင့်ထားမှသာ အသုံးပြုနိုင်သည်) -

| Method           | ဖော်ပြချက်                                                                          |
| ---------------- | ----------------------------------------------------------------------------------- |
| `message/send`   | တစ်ပြိုင်နက်တည်း skill လုပ်ဆောင်ခြင်း၊ `{task, artifacts, metadata}` ကို ပြန်ပေးသည် |
| `message/stream` | တူညီသော skill အစုအတွက် SSE ဖြင့် streaming လုပ်ဆောင်ခြင်း                           |
| `tasks/get`      | `taskId` ဖြင့် task တစ်ခုကို ရယူခြင်း                                               |
| `tasks/cancel`   | `taskId` ဖြင့် task တစ်ခုကို ပယ်ဖျက်ခြင်း                                           |

Built-in skills များမှာ `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report` တို့ ဖြစ်သည်။

### Agent Card

```bash
GET /.well-known/agent.json
```

အများပြည်သူကြည့်ရှုနိုင်သော A2A agent card (အမည်၊ ဖော်ပြချက်၊ လုပ်ဆောင်နိုင်စွမ်းများ၊ skill catalog၊ auth scheme) ကို ပြန်ပေးသည် — ၁ နာရီကြာ အများပြည်သူအတွက် cache လုပ်ထားသည်။ Auth မလိုအပ်ပါ။

### REST အကူအညီများ

| Method | Path                         | ဖော်ပြချက်                                                                                                           |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A ဖွင့်/ပိတ်အခြေအနေ + task စာရင်းအင်းများ + cache လုပ်ထားသော agent card အကျဉ်းချုပ်                                |
| GET    | `/api/a2a/tasks`             | Task များစာရင်း — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (REST helper အဖြစ် မလုပ်ဆောင်ရသေးပါ — JSON-RPC `message/send` ဖြင့် ဖန်တီးပါ)                                        |
| GET    | `/api/a2a/tasks/[id]`        | Task တစ်ခုကို ရယူခြင်း                                                                                               |
| POST   | `/api/a2a/tasks/[id]/cancel` | Task တစ်ခုကို ပယ်ဖျက်ခြင်း                                                                                           |

**Auth:** REST helper များသည် management auth မလိုဘဲ လုပ်ဆောင်သည် (ဒက်ရှ်ဘုတ်မှ ဖတ်ရှုနိုင်သည်)။ JSON-RPC `/a2a` route သည် သတ်မှတ်ထားပါက Bearer `OMNIROUTE_API_KEY` ကို အသုံးပြုသည်။

## ACP (Agent Client Protocol) စီမံခန့်ခွဲမှု

child process များအဖြစ်။ ဤ endpoint များသည် ACP agent ရှာဖွေတွေ့ရှိမှုနှင့် စိတ်ကြိုက် agent မှတ်ပုံတင်ခြင်းတို့ကို စီမံခန့်ခွဲသည်။

| Method | Path              | Description                                                                                                                                                                               |
| ------ | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | ထည့်သွင်းထားမှုအခြေအနေ၊ ဗားရှင်းနှင့် binary တို့နှင့်အတူ သိရှိထားသမျှ CLI agent များ (ပါဝင်ပြီးသား + စိတ်ကြိုက်) အားလုံးကို စာရင်းပြုစုရန်                                               |
| POST   | `/api/acp/agents` | စိတ်ကြိုက် ACP agent မှတ်ပုံတင်ရန် သို့မဟုတ် cache ကို ပြန်လည်ဆန်းသစ်ရန် — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` သို့မဟုတ် `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | စိတ်ကြိုက် ACP agent ကို ဖယ်ရှားရန် — query param: `?id=<agentId>`                                                                                                                        |

**တုံ့ပြန်မှု ဥပမာ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**အထောက်အထားပြခြင်း:** စီမံခန့်ခွဲမှု session (dashboard `auth_token` cookie) သို့မဟုတ် management-scoped API key လိုအပ်သည်။

အသေးစိတ်အချက်အလက်များအတွက် [ACP Framework](../frameworks/ACP.md) ကို ကြည့်ပါ။

## အထောက်အထားစိစစ်ခြင်း

အထောက်အထားအမျိုးအစား မိသားစုလေးမျိုး (ဒက်ရှ်ဘုတ် စက်ရှင်၊ ဒေသတွင်း CLI တိုကင်၊ `oma_live_…` Access Token၊ စီမံခန့်ခွဲမှုအတိုင်းအတာသတ်မှတ်ထားသော API key) နှင့် ၎င်းတို့သည် inference keys များနှင့် မည်သို့ကွာခြားသည်ကို [Management Authentication](../guides/MANAGEMENT-AUTH.md) တွင် ကြည့်ပါ။

- ဒက်ရှ်ဘုတ်လမ်းကြောင်းများ (`/dashboard/*`) သည် `auth_token` ကွတ်ကီးကို အသုံးပြုသည်
- Login သည် သိမ်းဆည်းထားသော စကားဝှက် hash ကို အသုံးပြုသည်။ မရရှိပါက `INITIAL_PASSWORD` ကို အသုံးပြုသည်
- `requireLogin` ကို `/api/settings/require-login` မှတစ်ဆင့် ဖွင့်နိုင်၊ ပိတ်နိုင်သည်
- `/v1/*` လမ်းကြောင်းများသည် `REQUIRE_API_KEY=true` ဖြစ်သောအခါ Bearer API key လိုအပ်နိုင်သည်
- ဤရည်ညွှန်းစာတမ်းတွင် “စီမံခန့်ခွဲမှုတိုကင်” / “စီမံခန့်ခွဲမှုအတိုင်းအတာသတ်မှတ်ထားသော API key” ဆိုသည်မှာ ထိုလမ်းညွှန်တွင် ဖော်ပြထားသော အမျိုးအစားများထဲမှ တစ်ခုကို ဆိုလိုခြင်းဖြစ်ပြီး — သီးခြားသတ်မှတ်မထားသော လျှို့ဝှက်ချက်အမျိုးအစားအသစ်ကို မဆိုလိုပါ

> **အပြောင်းအလဲကြီး (v3.8.0)** — `/api/v1/agents/tasks/*` နှင့် cooldown စီမံခန့်ခွဲမှု endpoint များသည် ယခုအခါ **စီမံခန့်ခွဲမှု အထောက်အထားစိစစ်ခြင်း** (ဒက်ရှ်ဘုတ် `auth_token` ကွတ်ကီး သို့မဟုတ် စီမံခန့်ခွဲမှုအတိုင်းအတာသတ်မှတ်ထားသော API key) လိုအပ်သည်။ ယခင်က ဤလမ်းကြောင်းများကို အထောက်အထားစိစစ်ခြင်းမရှိဘဲ ခေါ်ဆိုခဲ့သော client များသည် `401 Unauthorized` ကို လက်ခံရရှိမည်ဖြစ်သည်။ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) commit ကို ကြည့်ပါ။
