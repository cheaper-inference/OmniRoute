OmniRoute သည် တရားဝင်မဟုတ်သော client များကို ၎င်းတို့၏ edge များက တက်ကြွစွာ fingerprint ပြုလုပ်သည့် provider များနှင့် ချိတ်ဆက်ပေါင်းစည်းထားသည် (TLS JA3/JA4၊ header အစီအစဉ်၊ JSON body ပုံသဏ္ဌာန်၊ integrity token များ)။ ဤစာမျက်နှာတွင် OmniRoute က ဖော်ထုတ်ပေးထားသော stealth မျက်နှာပြင်များနှင့် ၎င်းတို့ကို အကောင်အထည်ဖော်ထားသည့်နေရာများကို မှတ်တမ်းတင်ထားသည်။

## ဥပဒေနှင့် ကျင့်ဝတ်ဆိုင်ရာ အသိပေးချက်

Stealth အင်္ဂါရပ်များသည် သုံးစွဲသူပိုင် တရားဝင် account များ (Claude Code CLI, Codex, Antigravity, Cursor စသည်တို့) နှင့် OmniRoute ၏ ပေါင်းစည်းထားသော API ကြားတွင် OmniRoute က compatibility layer တစ်ခုအဖြစ် လုပ်ဆောင်နိုင်ရန် တည်ရှိခြင်းဖြစ်သည်။ ၎င်းတို့သည် လိမ်လည်မှုရှာဖွေခြင်းကို ရှောင်လွှဲရန်၊ အထောက်အထားများကို မျှဝေရန် သို့မဟုတ် provider ၏ ဝန်ဆောင်မှုစည်းမျဉ်းများကို ချိုးဖောက်ရန်အတွက် **မဟုတ်ပါ**။ ထိန်းသိမ်းသူများသည် operator များအနေဖြင့် account များဖန်တီးစဉ် လက်မှတ်ရေးထိုးသဘောတူခဲ့သော upstream ToS ကို လိုက်နာရန် မျှော်လင့်ထားသည်။

## TLS လက်ဗွေခွဲခြားမှုအလွှာ

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

အကောင့် scope နှင့် ဖြေရှင်းသတ်မှတ်ထားသော proxy တစ်ခုစီအတွက် အမြဲတမ်းအသုံးပြုသည့် `wreq-js` session များကို လိုအပ်သည့်အချိန်မှသာ ဖန်တီးသည်။ Process တစ်ခုလုံးအတိုင်းအတာရှိ `TlsClient` သည် Cloudflare နောက်ကွယ်ရှိ upstream များအတွက် **macOS ပေါ်ရှိ Chrome 124** အဖြစ် အတုယူလုပ်ဆောင်သော session အများဆုံး 128 ခုကို pool ထဲတွင် ထိန်းသိမ်းထားသည်။ Native runtime မရရှိနိုင်သည့်အခါ `TlsClient.fetch()` သည် လုံခြုံစွာပိတ်ဆို့ပြီး ပျက်ကွက်သည်။ ခေါ်ယူသူသည် ဤ wrapper အပြင်ဘက်ရှိ fallback တစ်ခုကို အတိအလင်း ရွေးချယ်နိုင်သည်။

- Session profile: `browser: "chrome_124", os: "macos"`
- Proxy ဖြေရှင်းသတ်မှတ်မှု (ဦးစားပေးအစဉ်): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (စာလုံးအသေးပုံစံများလည်း ပါဝင်သည်)
- Timeout: `TLS_CLIENT_TIMEOUT_MS` (`FETCH_TIMEOUT_MS` ထံမှ ဆက်ခံသည်၊ မူလတန်ဖိုး 600000)
- `wreq-js` Response သည် fetch နှင့် ကိုက်ညီမှုရှိသည် (`headers`, `text()`, `json()`, `clone()`, `body`)။
- ပထမ byte စောင့်ကြည့်ကိရိယာ (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): Upstream header များ ရောက်ရှိသည်နှင့် `TlsClient.fetch()`
  သည် ဖြေရှင်းပြီးဆုံးသွားသောကြောင့် `TLS_CLIENT_TIMEOUT_MS` တစ်ခုတည်းဖြင့် ပထမ byte လုံးဝမထုတ်ပေးသည့်
  body တစ်ခုကို အချိန်ကန့်သတ်၍ မရနိုင်ပါ။ `guardTlsFirstByte()` သည် body ၏ ပထမဆုံး `read()` ကို
  `TLS_FIRST_BYTE_WATCHDOG_MS` (မူလတန်ဖိုး `10000`၊ `0` က ၎င်းကို ပိတ်သည်) နှင့် ပြိုင်တူလုပ်ဆောင်စေသည်။ ပုံမှန် body တစ်ခုကို
  သက်ရောက်မှုမရှိသော်လည်း ရပ်တန့်နေသော body တစ်ခုသည် wreq reader ကို ပယ်ဖျက်ပြီး `proxyFetch` ၏ ရှိပြီးသား
  TLS-fallback logic ကို direct/proxy dispatcher သို့ ဆက်လက်ကျရောက်စေသည် (ပြန်လည်ပေးပို့ရန် မလုံခြုံသော request၊ ဥပမာ
  body ပါသည့် POST သည် အသံတိတ်ပြန်လည်ကြိုးစားခြင်းအစား error ပစ်နေဆဲဖြစ်သည်)။

### Web-cookie provider သယ်ယူပို့ဆောင်မှု — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` သည် အောက်ပါ အထူးပြု web-cookie သယ်ယူပို့ဆောင်မှု ငါးခုအတွက် မျှဝေသုံး adapter ဖြစ်သည်။ ပါးလွှာသော provider wrapper တစ်ခုစီသည် browser/OS profile တစ်ခုကို ရွေးချယ်သည်။ Adapter သည် `open-sse/utils/tlsClient.ts` ရှိ တစ်ခုတည်းသော wreq runtime loader နှင့် transport pool ကို အသုံးပြုပြီး
profile + OS + ဖြေရှင်းသတ်မှတ်ထားသော proxy အလိုက် key သတ်မှတ်ထားသည်။ Request တစ်ခုစီက `cookieMode: "ephemeral"` ကို အသုံးပြုသည်။ ထို့ကြောင့် အကောင့်များနှင့်
request များသည် transport အဆင့် connection များကို မျှဝေသော်လည်း wreq session သို့မဟုတ် cookie jar ကို မည်သည့်အခါမျှ မမျှဝေပါ။

| Provider   | Profile       | အတုယူထားသော OS | Stream EOF မူဝါဒ                        |
| ---------- | ------------- | -------------- | --------------------------------------- |
| Claude     | `chrome_146`  | Linux          | `[DONE]` ကို ထည့်သွင်းသည်               |
| Perplexity | `firefox_151` | macOS          | `event: end_of_stream` ကို ထည့်သွင်းသည် |
| Grok       | `chrome_146`  | Linux          | `[DONE]` ကို ဖယ်ထုတ်သည်                 |
| Notion     | `chrome_146`  | Windows        | `[DONE]` ကို ထည့်သွင်းသည်               |
| LMArena    | `chrome_146`  | Windows        | sentinel မရှိ၊ native EOF တွင် ပိတ်သည်  |

- Streaming သည် native response `ReadableStream` ကို တိုက်ရိုက်သုံးစွဲသည်။ ယာယီ file သို့မဟုတ် sidecar ကို
  မဖန်တီးပါ။
- Stream ကို ထုတ်ဖော်မပေးမီ ကနဦး byte 256 အထိ စစ်ဆေးသည်။ SSE provider များသည် SSE မဟုတ်သော
  error များကို buffer ပြုလုပ်သည်။ Grok/LMArena သည် Cloudflare challenge များကို `403` အဖြစ်နှင့် HTML interstitial များကို `502` အဖြစ် ပြောင်းလဲသတ်မှတ်သည်။
- Native request timeout ကို အကြွင်းမဲ့ JS hard deadline တစ်ခုဖြင့် ဆက်လက်ခြုံငုံထားသည်။ Hang ဖြစ်ပါက
  သက်ရောက်မှုရှိသော profile/OS/proxy transport ကိုသာ မမှန်ကန်တော့ကြောင်း သတ်မှတ်ပြီး ပိတ်ကာ နောက် request တွင် ၎င်းကို ပြန်လည်ဖန်တီးသည်။
- Proxy ဖြေရှင်းသတ်မှတ်မှု၏ ဦးစားပေးအစဉ်မှာ ခေါ်ယူမှုတစ်ခုချင်းစီ၏ `proxyUrl` → request အလိုက် account/dashboard context →
  `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (စာလုံးအသေးပုံစံများ အပါအဝင်) ဖြစ်သည်။ ဖြေရှင်းသတ်မှတ်မှု error များသည်
  direct connection မပေါက်ကြားစေရန် လုံခြုံစွာပိတ်ဆို့ပြီး ပျက်ကွက်သည်။ LMArena သည် ရည်ရွယ်ချက်ရှိရှိ `arena.ai` ကို အခြေခံ၍ ဖြေရှင်းသတ်မှတ်သည်။
- `byteResponse` သည် UTF-8 ပျက်စီးမှုမရှိသော content type သတ်မှတ်ထားသည့် `data:` URL တစ်ခုကို ပြန်ပေးသည်။
- Error များမှာ `TlsClientUnavailableError` (package/addon မရရှိနိုင်ခြင်း)၊ `TlsClientHangError`
  (deadline ကျော်လွန်ခြင်း) နှင့် လက်ရှိအသုံးပြုနေသော သို့မဟုတ် ပိတ်နေဆဲဖြစ်သော profile/OS/proxy slot 128 ခုလုံး ပြည့်နေသည့်အခါ
  `WreqTransportCapacityError` (မျှဝေထားသော session စွမ်းရည်ဆိုင်ရာ error code) တို့ဖြစ်သည်။

အထက်ပါ ယေဘုယျ `TlsClient` session သည် အမြဲတမ်းသိမ်းဆည်းထားသော browser-backed cookie
state အတွက် အထူးပြုထားဆဲဖြစ်သည်။ လမ်းကြောင်းနှစ်ခုစလုံးသည် cache လုပ်ထားသော wreq module loader တစ်ခုနှင့် process lifecycle hook တစ်ခုကို ပြန်လည်အသုံးပြုသည်။ သို့သော် ၎င်းတို့၏ cookie သက်တမ်းများကို ရည်ရွယ်ချက်ရှိရှိ ကွဲပြားစွာထားသောကြောင့် pool များကို သီးခြားထားသည်။

Profile များကို pin လုပ်ထားသော package က ပံ့ပိုးပေးသော်လည်း အမှန်တကယ် WAF လက်ခံမှုသည်
local contract test များနှင့် မသက်ဆိုင်ဘဲ ပြောင်းလဲနိုင်သည်။ Upstream browser နှင့် တူညီမှုရှိကြောင်း မပြောဆိုမီ

## Claude Code Stealth Bundle

`cliCompatMode` ကို ဖွင့်ထားသည့်အခါ OmniRoute သည် အပြင်သို့ပို့မည့် Claude တောင်းဆိုမှုများကို `claude-cli` traffic နှင့် ခွဲခြားမရအောင် ပြန်လည်ပုံဖော်ပေးသည်။ Module သုံးခုက ပူးပေါင်းလုပ်ဆောင်သည်-

### `claudeCodeFingerprint.ts`

Billing header ထဲတွင် ထည့်သွင်းထားသည့် စာလုံး 3 လုံးပါ `cc_version` fingerprint ကို တွက်ချက်သည်-

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (code ထဲတွင် အတိအကျသတ်မှတ်ထားပြီး တရားဝင် client နှင့် ကိုက်ညီသည်)
- Input များ- ပထမဆုံး user message စာသား၏ index 4၊ 7၊ 20 ရှိ စာလုံးများ + version string
- Output- စာလုံး 3 လုံးပါ hex prefix

### `claudeCodeCCH.ts` (Client Content Hash)

တရားဝင် Claude Code CLI က Bun/Zig မှတစ်ဆင့် တွက်ချက်သည့် server-side integrity check ဖြစ်သည်။ OmniRoute က ၎င်းကို `xxhash-wasm` ဖြင့် ပြန်လည်အကောင်အထည်ဖော်ထားသည်-

1. Body ကို `cch=00000;` placeholder ဖြင့် serialize လုပ်ပါ
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. အရှေ့တွင် သုညဖြည့်ထားသည့် စာလုံး 5 လုံးပါ lowercase hex
4. `cch=00000;` ကို တွက်ချက်ရရှိသည့် token ဖြင့် အစားထိုးပါ

ကိန်းသေများ-

- Seed: `0x6e52736ac806831e`
- Pattern: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

Upstream filter များက grep ဖြင့် ရှာမတွေ့နိုင်စေရန် "အရေးကြီးသော" client အမည်များ၏ ပထမစာလုံးနောက်တွင် Unicode **zero-width joiner** (`U+200D`) တစ်ခု ထည့်သွင်းသည်။ မူလ word list-

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

အသုံးချသည့်နေရာများ- `system` block များ၊ `messages[].content` အားလုံးနှင့် `tools[].description` / `tools[].function.description`။ Operator က `setSensitiveWords()` မှတစ်ဆင့် လိုသလို အစားထိုးသတ်မှတ်နိုင်သည်။

### `claudeCodeCompatible.ts` — `anthropic-compatible-cc-*` provider များ

"Claude Code အစစ်" traffic ကိုသာ လက်ခံသည့် third-party Anthropic relay များအတွက်-

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.280 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- မူလအတိုင်း `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"`
- CC Compatible upstream တစ်ခုက redacted thinking stream များကို အထူးလိုအပ်သည့်အခါ connection တစ်ခုချင်းစီအလိုက် "Enable redact-thinking beta" toggle သည် `redact-thinking-2026-02-12` ကို ထည့်ပေးသည်
- Connection တစ်ခုချင်းစီအလိုက် "Enable summarized thinking display" toggle သည် `providerSpecificData.requestDefaults.summarizeThinking` ကို သိမ်းဆည်းပြီး display mode မသတ်မှတ်ရသေးသော CC Compatible thinking တောင်းဆိုမှုများတွင် `display: "summarized"` ကို ထည့်ပေးသည်
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (Opus/Sonnet 4.x မျိုးဆက်)
- မူလ path- `/v1/messages?beta=true`

Bundle တစ်ခုတည်းထဲရှိ ဆက်စပ် module များ-

- `claudeCodeConstraints.ts` — temperature + cache-control စည်းမျဉ်းများ
- `claudeCodeToolRemapper.ts` — tool အမည် ပြန်လည် mapping လုပ်ခြင်း
- `claudeCodeExtraRemap.ts` — နောက်ထပ် payload normalization

## Antigravity ကိုယ်ပျောက်

Antigravity သည် ခေါ်ဆိုသူစာသား byte-for-byte ကို ထိန်းသိမ်းထားသည်။ OmniRoute IDE client ကိုတုပရန် prompts သို့မဟုတ် rename/inject ကိရိယာများတွင် သုညအကျယ်အက္ခရာများကို မထည့်ပါ။

### `antigravityHeaderScrub.ts`

ထပ်ဆင့်မပို့မီတွင် Stainless SDK အမှတ်အသားများ (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`)။

### ⚠️ အန္တရာယ်- `ANTIGRAVITY_CREDITS=always` (အကောင့်-ပိတ်ပင်တားဆီးမှု hot spot)

`ANTIGRAVITY_CREDITS=always` ( `open-sse/executors/antigravity.ts`) လမ်းကြောင်းများဖြင့် စားသုံးသည်။** တိုင်း** Antigravity AI Credit Overages (paid Google ခရက်ဒစ်များ) မှတဆင့် Google၏ အခမဲ့အဆင့်ခွဲတမ်း gate များကို ခွင့်မပြုဘဲ တောင်းဆိုပါ။ ၎င်းကို အင်္ဂါရပ်တစ်ခုအဖြစ် မှတ်တမ်းတင်ထားသော်လည်း ၎င်းသည် ဖြစ်၏။** ကျွန်ုပ်တို့တွေ့မြင်ရသော အဖြစ်အများဆုံး ToS-ချိုးဖောက်မှုအစီရင်ခံစာ** — အများအပြား Google Ultra အကောင့်များကို `=always` ဖြင့် နာရီအနည်းငယ်ကြာ အသုံးပြုပြီးနောက် `403 / "service disabled for ToS violation" / insufficient_quota` ဖြင့် ပိတ်ပင်ထားသည်။

အထက်ပိုင်း ဥပဒေစိုးမိုးမှု ဖွင့်ထားသည်။**Google၏ဘေးထွက်** OmniRoute မည်သည့်အရာမှ တားဆီးနိုင်မည်မဟုတ်ပေ။ env var အမည်နှင့် ရှိပြီးသားစာရွက်စာတမ်းများသည် လှန်ရန် ဘေးကင်းသောခလုတ်တစ်ခုကဲ့သို့ အသံထွက်စေသည်။ မဟုတ်ဘူး။

**၎င်းသည် အခမဲ့အဆင့်သီးသန့်အသုံးပြုမှုထက် အလွဲသုံးစားပြုမှုကို ထောက်လှမ်းခြင်းထက် ပိုမိုပြင်းထန်စွာ အဘယ်ကြောင့်ဆွဲယူသနည်း-**

- အခမဲ့အဆင့် hits-quota-and-stops များထက် မတူညီသော Google အကောင့်အလံတစ်ခုအတွက် စဉ်ဆက်မပြတ် အလိုအလျောက် သုံးစွဲမှု။
- ခရက်ဒစ်ပိုလျှံမှုများတွင် နှုန်းထားမျက်နှာကြက်မရှိပါ၊ ထို့ကြောင့် မှားယွင်းသတ်မှတ်ထားသော client သည် မိနစ်အနည်းငယ်အတွင်း USD ရာနှင့်ချီပြီးလောင်ကျွမ်းနိုင်ပြီး API-သော့ပြန်ရောင်းခြင်း သို့မဟုတ် ဘော့တ်အသွားအလာကဲ့သို့ဖြစ်သည်။
- တူညီသောပြင်ပ IP မှ သက်တမ်းလွန်ခရက်ဒစ်များကို အပြိုင်နှိပ်သော OmniRoute သုံးစွဲသူအများအပြားသည် အချက်ပြမှုကို ပေါင်းစပ်ပေးသည်။

**အကြံပြုထားသော ကိုယ်ဟန်အနေအထား**

1. အော်ပရေတာမှ အခပေးခရက်ဒစ်နှင့် အကောင့်စိုးမိုးရေးအန္တရာယ်ကို ပြတ်သားစွာ လက်မခံပါက မူရင်း `ANTIGRAVITY_CREDITS=off` ထားရှိပါ။ `retry` သည် ပုံမှန်တောင်းဆိုချက်အား ဦးစွာပေးပို့ပြီး သတ်မှတ်ချက်ပြည့်မီသော ခွဲတမ်း 429 ပြီးနောက် တစ်ကြိမ်တွင် ခရက်ဒစ်ကို အများဆုံးထည့်သွင်းပေးပါသည်။ `always` သည် ပထမတောင်းဆိုချက်တွင် ခရက်ဒစ်ကို ထိုးသွင်းသည်။
2. **Auto-Combo မှတစ်ဆင့် ဝန်ဆောင်မှုပေးသူများအကြား ဝန်ကို ဖြန့်ကြက်ပါ။** Antigravity အကောင့်တစ်ခုတည်းကို ပြည့်နှက်မည့်အစား (`model: "auto"` သို့မဟုတ် `kr/glm/etc` -combo)။
3. **ချိတ်ဆက်မှု RPM န့်သတ်ချက်များကို သတ်မှတ်ပါ။** Antigravity ဝန်ဆောင်မှုပေးသူ၏ တည်းဖြတ်စာမျက်နှာ (ဒက်ရှ်ဘုတ် → ဝန်ဆောင်မှုပေးသူများ → Antigravity → ချိတ်ဆက်မှု → နှုန်းကန့်သတ်ချက်)။ 30-60 RPM သည် စဉ်ဆက်မပြတ်အသုံးပြုမှုအတွက် ခုခံကာကွယ်နိုင်သော အထက်ဘောင်တစ်ခုဖြစ်သည်။
4. **တည်ငြိမ်သော၊ အော်ပရေတာထိန်းချုပ်ထားသော အထက်စီးကြောင်းကွန်ရက်ကို အသုံးပြုပါ။** နှင့် မသက်ဆိုင်သော အသုံးပြုသူများ သို့မဟုတ် အလုပ်တာဝန်များကြားတွင် အကောင့်တစ်ခုမျှဝေခြင်းကို ရှောင်ကြဉ်ပါ။
5. **တားမြစ်ရင်** : `support.google.com` → မှတဆင့် အယူခံဝင်သည် " Workspace/Account ဝင်ရောက်မှုကို ပြန်လည်ရယူပါ " အတိအကျ `quota_exceeded` / `service disabled` တုံ့ပြန်မှုကိုယ်ထည် Google ပို့လိုက်သည် ။ ပြန်လည်ထူထောင်ခြင်းကို အာမမခံနိုင်ပါ။

ပတ်ဝန်းကျင်သည် အကောင့်ကို ကိုးကားပြီး ခရက်ဒစ်မုဒ်တစ်ခုစီ၏ သက်ရောက်မှုများကို သုံးစွဲသည်။

ဤဝန်ဆောင်မှုပေးသူများသည် Antigravity ထုတ်ကုန်စက်ရှင်နှင့်မတူဘဲ API ဝင်ရောက်မှုအတွက် အထောက်အထားများ Google ပြဿနာများကို အသုံးပြုသည်။ ၎င်းတို့သည် အသုံးပြုမှုတိုင်းကို လိုက်လျောညီထွေဖြစ်စေရန် သို့မဟုတ် ပြဋ္ဌာန်းခြင်း၏အန္တရာယ်ကို ဖယ်ရှားခြင်းမပြုပါ- တစ်ခုစီကို ၎င်းတို့၏ ဖြန့်ကျက်မှုအတွက် စစ်ဆေးရန် အော်ပရေတာက ၎င်း၏ကိုယ်ပိုင်သတ်မှတ်ချက်များဖြင့် အုပ်ချုပ်ထားသည်။ ဥပမာအားဖြင့်၊ [Gemini API အပိုဝန်ဆောင်မှုစည်းမျဥ်းစည်းကမ်းများသည်](https://ai.google.dev/gemini-api/terms) API ဖောက်သည်များကို ဥရောပစီးပွားရေးဧရိယာ၊ ဆွစ်ဇာလန် သို့မဟုတ် United Kingdom ရှိ သုံးစွဲသူများထံ ပေးဆောင်သည့်အခါတွင်သာ အခပေးဝန်ဆောင်မှုများကို ခွင့်ပြုပေးပြီး Google၏ ထုတ်ကုန်များကို ပိုမိုကောင်းမွန်စေရန်အတွက် ပေးပို့သည့်အကြောင်းအရာကို အသုံးပြုနိုင်ပါသည်။ Vertex AI သည် Google Cloud စည်းကမ်းချက်များ ( [Service Specific Terms](https://cloud.google.com/terms/service-terms) ) တွင် ကျရောက်သည်။ စျေးနှုန်းနှင့် ခွဲတမ်းများသည် Antigravity စာရင်းသွင်းခြင်းထက် ထို API စည်းကမ်းချက်များကို လိုက်နာသည်။

အထက်တွင်ဖော်ပြထားသော Antigravity ဆိုင်းငံ့မှုများကို ရှောင်ရှားလိုသော အော်ပရေတာများသည် ၎င်းတို့၏အသုံးပြုမှုသည် ဝန်ဆောင်မှုပေးသူ၏ သတ်မှတ်ချက်များနှင့် ကိုက်ညီမှု `agy` စစ်ဆေးပြီးနောက် ဤဝန်ဆောင်မှုပေးသူများအနက်မှ တစ်ခုမှတစ်ဆင့် Gemini အသွားအလာကို လမ်းကြောင်းပေးသင့်သည် `antigravity`

## CLI Fingerprint Registry — `open-sse/config/cliFingerprints.ts`

တရားဝင် CLI များ၏ mitmproxy trace များမှ ဖမ်းယူထားသော header အစီအစဉ်နှင့် JSON body field အစီအစဉ်ကို **အတိအကျ** သတ်မှတ်ထားသည့် provider အလိုက် ဇယားဖြစ်သည်။ လက်ရှိ မှတ်ပုံတင်ထားသည်များမှာ `codex`, `claude` နှင့် `antigravity`, `github` တို့အတွက် `providerHeaderProfiles.ts` ထဲရှိ runtime မှ ရယူဖန်တီးထားသော profile များ ဖြစ်သည်။

```ts
interface CliFingerprint {
  headerOrder: string[]; // စာလုံးအကြီးအသေး ခွဲခြားသည်
  bodyFieldOrder: string[]; // ထိပ်ဆုံးအဆင့် JSON key များ
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

Provider တစ်ခုချင်းစီအတွက် env မှတစ်ဆင့် ဖွင့်/ပိတ်နိုင်သည် (အောက်တွင် ကြည့်ပါ)။ ပိတ်ထားသည့်အခါ header/body key များသည် Node/JSON က ပေးသည့် မည်သည့်အစီအစဉ်အတိုင်းမဆို ပေါ်လာမည်ဖြစ်ပြီး fingerprint ဖော်ထုတ်ရန် လွယ်ကူသည်။

## MITM Proxy (Antigravity, Linux/macOS/Windows)

Binary များကို `OPENAI_BASE_URL` မှတစ်ဆင့် လမ်းကြောင်းပြောင်း၍မရသော CLI များအတွက် OmniRoute သည် TLS ကို အဆုံးသတ်ပေးသည့် local proxy တစ်ခုကို လုပ်ဆောင်သည်။ Endpoint များသည် `src/app/api/cli-tools/antigravity-mitm/` အောက်တွင် ရှိသည်။

| နည်းလမ်း | Endpoint                                | ရည်ရွယ်ချက်                                              |
| -------- | --------------------------------------- | -------------------------------------------------------- |
| GET      | `/api/cli-tools/antigravity-mitm`       | အခြေအနေ — လုပ်ဆောင်နေမှု၊ pid၊ dnsConfigured၊ certExists |
| POST     | `/api/cli-tools/antigravity-mitm`       | MITM စတင်ရန် (`apiKey` + `sudoPassword` လိုအပ်သည်)       |
| DELETE   | `/api/cli-tools/antigravity-mitm`       | MITM ရပ်တန့်ရန်                                          |
| GET      | `/api/cli-tools/antigravity-mitm/alias` | Model alias များကို စာရင်းပြုစုရန်                       |
| PUT      | `/api/cli-tools/antigravity-mitm/alias` | Tool တစ်ခုအတွက် model alias များကို သိမ်းဆည်းရန်         |

ကြားဖြတ်ဖမ်းယူမည့် ပစ်မှတ် host: **`daily-cloudcode-pa.googleapis.com`** (Antigravity ၏ upstream)။

### စတင်မှု အစီအစဉ် (`src/mitm/manager.ts::startMitm`)

1. `selfsigned` မှတစ်ဆင့် self-signed certificate ထုတ်လုပ်ရန် (RSA-2048, SHA-256, 1y) — `cert/generate.ts`
2. Certificate ကို system trust store ထဲသို့ ထည့်သွင်းရန် — `cert/install.ts`
3. Hosts entry `127.0.0.1 daily-cloudcode-pa.googleapis.com` ကို ထည့်ရန် — `dns/dnsConfig.ts`
4. `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (မူလတန်ဖိုး `443`) ဖြင့် `src/mitm/server.cjs` ကို spawn လုပ်ရန်
5. PID ကို `<DATA_DIR>/mitm/.mitm.pid` တွင် အမြဲတမ်းသိမ်းဆည်းရန်

### Linux dynamic trust-store ရှာဖွေခြင်း — `cert/install.ts`

`getLinuxCertConfig()` သည် ဦးစားပေးစာရင်းတစ်ခုကို အစဉ်လိုက် စစ်ဆေးပြီး ပထမဆုံးတွေ့ရှိသော directory ကို ရွေးချယ်သည်။

| Distro မျိုးနွယ်         | Directory                                   | Update command           |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Certificate ဖိုင်အမည်: `omniroute-mitm.crt`။ `getCertFingerprint()` မှတစ်ဆင့် fingerprint ကိုက်ညီမှု စစ်ဆေးသည် (DER ၏ SHA-1)။

ထို့အပြင် `certutil` ကို အသုံးပြုနိုင်သည့်အခါ `updateNssDatabases()` သည် အသုံးပြုသူတစ်ဦးချင်းစီ၏ NSS DB များဖြစ်သော `~/.pki/nssdb`, `~/snap/chromium/.../nssdb` နှင့် Firefox profile အားလုံး (snap အပါအဝင်) ထဲသို့ **`OmniRoute MITM Root CA`** ဟူသော nickname ဖြင့် ထည့်သွင်းသည်။

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** အဆင့်မြှင့်ခွင့်ဖြင့် PowerShell → `certutil -addstore Root`

### Auth

MITM endpoint အားလုံးတွင် စီမံခန့်ခွဲမှု auth (`requireCliToolsAuth`) လိုအပ်သည်။ sudo password ကို module scope ထဲတွင် cache လုပ်ထားပြီး (`globalThis` တွင် မည်သည့်အခါမျှ မထားပါ) `stopMitm()` ခေါ်သည့်အခါ ရှင်းလင်းသည်။

## Provider တစ်ခုက Fingerprint ပြောင်းသည့်အခါ အပ်ဒိတ်လုပ်ခြင်း

1. `mitmproxy` ဖြင့် တရားဝင် CLI traffic ကို ဖမ်းယူပါ (TLS interception + dump)
2. JA3/JA4 နှင့် header အစီအစဉ်အတိအကျကို ထုတ်ယူပါ
3. သက်ဆိုင်ရာ `CLI_FINGERPRINTS[...]` entry ကို အပ်ဒိတ်လုပ်ပါ
4. `.env.example` ရှိ ကိုက်ညီသော `*_USER_AGENT` မူလတန်ဖိုးကို မြှင့်တင်ပါ
5. TLS handshake ကိုယ်တိုင် ပြောင်းလဲသွားပါက သက်ဆိုင်ရာ provider wrapper သို့မဟုတ် wreq-js `browser:` option ကို အပ်ဒိတ်လုပ်ပါ
6. Provider သီးသန့် TLS test များနှင့် လက်ရှိအသုံးပြုနေသော provider အပေါ် manual canary စမ်းသပ်မှုတစ်ခုကို လုပ်ဆောင်ပါ
7. Patch release ဖြင့် ထုတ်ပြန်ပြီး `CHANGELOG.md` တွင် မှတ်တမ်းတင်ပါ
