> **အမှန်တရားအရင်းအမြစ်-** `src/lib/compliance/`၊ `src/app/api/compliance/`

OmniRoute စီမံခန့်ခွဲရေးဆိုင်ရာ လုပ်ဆောင်ချက်များ၊ အထောက်အထားစိစစ်ခြင်း ဖြစ်ရပ်များ၊ ပံ့ပိုးပေးသူ အထောက်အထား ဘဝသံသရာ အပြောင်းအလဲများနှင့် SQLite-ကျောထောက်နောက်ခံပြုထားသော စာရင်းစစ်ဇယားများသို့ MCP ကိရိယာ တောင်းခံမှုများကို မှတ်တမ်းတင်ပါသည်။ ဤစာမျက်နှာတွင် လော့ဂ်လုပ်ထားသည့်အရာ၊ ၎င်းနေထိုင်သည့်နေရာ၊ ၎င်းကို မည်မျှကြာအောင် ထိန်းသိမ်းထားသနည်း၊ API သော့များကို မည်ကဲ့သို့ ဖယ်ထုတ်နိုင်သည်နှင့် ဒေတာကို ရှာဖွေနည်းတို့ကို ဖော်ပြထားပါသည်။

အကောင်အထည်ဖော်မှုသည် `src/lib/compliance/index.ts` (T-43 — "လိုက်နာမှုထိန်းချုပ်မှုများ") နှင့် `src/lib/compliance/providerAudit.ts` တွင်တည်ရှိသည်။ စာရင်းစစ်သည် ဘယ်သောအခါမှ ပစ်မချပါ- မည်သည့်ချို့ယွင်းချက်တွင်မဆို ခေါ်ဆိုမှုကို တိတ်တဆိတ် မျိုချမိသောကြောင့် စာရင်းစစ်မှတ်တမ်းရယူခြင်းသည် ပင်မတောင်းဆိုမှုစီးဆင်းမှုကို မချိုးဖျက်နိုင်ပါ။

## မှတ်တမ်းတင်ထားသည့်အရာများ

အကြောင်းအရာတစ်ခုစီတွင် `action`၊ `actor` (မသတ်မှတ်ထားပါက `"system"` ဖြစ်သည်)၊
`target`၊ `details`/`metadata` (JSON)၊ `ip_address`၊ `resource_type`၊ `status`၊
`request_id` နှင့် `timestamp` တို့ကို သိမ်းဆည်းထားသည်။ အရေးကြီးသော key များ
(`apiKey`၊ `accessToken`၊ `refreshToken`၊ `password`၊ `*token`/`*secret`/`*apikey`
နှင့် ကိုက်ညီသည့်အရာများ စသည်) ကို အတန်းမရေးသားမီ ထပ်ဆင့်၍ `"[redacted]"` ဖြင့်
ဖုံးကွယ်ထားသည်။

`api_key.auth.touch` အတန်းများသည် request log သို့ မရောက်ရှိသည့် အောင်မြင်သော
API key metadata နှင့် ရှာဖွေဖတ်ရှုမှုများ (GET/HEAD) ကို မှတ်တမ်းတင်သည်။ မည်သည့်
key ဖြစ်သည်၊ မည်သည့်အချိန်တွင် ဖြစ်သည်နှင့် ပုံမှန်ပြုလုပ်ထားသော လမ်းကြောင်းတို့ကို
မှတ်တမ်းတင်ပြီး အတန်း ၁,၀၀၀ အထိသာ ပေါင်းစည်းကာ ကန့်သတ်ထားသည်။ `noLog` ပါသည့် key များနှင့်
ပတ်ဝန်းကျင် key ကို ကျော်လွှားထားသည်။ ခေါ်ဆိုသူ၏ IP လိပ်စာနှင့် user-agent ကို
`API_KEY_AUDIT_CLIENT_DETAILS_ENABLED` feature flag ဖွင့်ထားသည့်အခါမှသာ
ထည့်သွင်းသည် (မူလအတိုင်း ပိတ်ထားသည်)။

### Request / အသုံးပြုမှု မှတ်တမ်းများ

ဤအရာများသည် စီမံခန့်ခွဲရေး စစ်ဆေးမှတ်တမ်းများကို တင်းကျပ်စွာ မဟုတ်သော်လည်း
တူညီသော ထိန်းသိမ်းကာလ pipeline ကို မျှဝေသုံးစွဲသည့် လုပ်ငန်းဆိုင်ရာ telemetry
များဖြစ်သည်-

- `usage_history` — request တစ်ခုချင်းစီအလိုက် အသုံးပြုမှု စုစည်းမှတ်တမ်း
- `call_logs` — request တစ်ခုချင်းစီအတွက် အပြည့်အစုံ မှတ်တမ်း (အောက်တွင် ဖော်ပြထားသည့် row-cap နှင့် သက်ဆိုင်သည်)
- `proxy_logs` — proxy traffic မှတ်တမ်း (row-cap နှင့် သက်ဆိုင်သည်)
- `request_detail_logs` — ယခင်အသေးစိတ် request မှတ်တမ်း (ရှိနေပါက pruned လုပ်ဆောင်ဆဲဖြစ်သည်)

## သိမ်းဆည်းမှု Schema

`audit_log` ကို ပထမဆုံးအသုံးပြုချိန်တွင် `ensureAuditLogSchema()` က လိုအပ်မှသာ ဖန်တီးသည်-

```sql
CREATE TABLE IF NOT EXISTS audit_log (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  timestamp     TEXT NOT NULL DEFAULT (datetime('now')),
  action        TEXT NOT NULL,
  actor         TEXT NOT NULL DEFAULT 'system',
  target        TEXT,
  details       TEXT,
  ip_address    TEXT,
  resource_type TEXT,
  status        TEXT,
  request_id    TEXT,
  metadata      TEXT
);
```

Index များကို `timestamp`, `action`, `actor`, `resource_type`, `status` နှင့် `request_id` တို့တွင် ဖန်တီးထားသည်။ ယခင် DB များတွင် မရှိသေးသော column များကို လိုအပ်သည့်အချိန်တွင် `ALTER TABLE` မှတစ်ဆင့် ထည့်သွင်းသည်။

## ထိန်းသိမ်းမှုနှင့် ရှင်းလင်းမှု

သီးခြားထိန်းသိမ်းမှုကာလ နှစ်ခုကို လိုက်နာသည်-

| ပတ်ဝန်းကျင် variable        | မူလတန်ဖိုး | သက်ရောက်သည့်အရာများ                                               |
| --------------------------- | ---------- | ----------------------------------------------------------------- |
| `APP_LOG_RETENTION_DAYS`    | `7`        | `audit_log`, `mcp_tool_audit`                                     |
| `CALL_LOG_RETENTION_DAYS`   | `7`        | `usage_history`, `call_logs`, `proxy_logs`, `request_detail_logs` |
| `CALL_LOGS_TABLE_MAX_ROWS`  | `100000`   | `call_logs` အတွက် အများဆုံး row အရေအတွက်အလိုက် ဖြတ်တောက်မှု       |
| `PROXY_LOGS_TABLE_MAX_ROWS` | `100000`   | `proxy_logs` အတွက် အများဆုံး row အရေအတွက်အလိုက် ဖြတ်တောက်မှု      |

`cleanupExpiredLogs()` သည် ထိန်းသိမ်းမှုလုပ်ငန်းစဉ်ကို လုပ်ဆောင်သည်။ Server စတင်ချိန်တွင် `src/instrumentation-node.ts` မှ ၎င်းကို ခေါ်ယူသည်။ လုပ်ဆောင်မှုတစ်ကြိမ်စီတွင် table တစ်ခုချင်းစီအလိုက် ဖျက်လိုက်သည့်အရေအတွက်များနှင့်အတူ `compliance.cleanup` audit event တစ်ခုကို မှတ်တမ်းတင်သည်။ အချိန်ကြာမြင့်သော write lock များကို ရှောင်ရှားရန် proxy/call log ဖြတ်တောက်မှုကို အစုလိုက် (`BATCH_SIZE = 5000`) လုပ်ဆောင်သည်။

Request history ကို ကိုယ်တိုင်ရှင်းလင်းခြင်းသည် ထိန်းသိမ်းမှုလုပ်ငန်းစဉ်နှင့် သီးခြားဖြစ်သည်။ Request Logs စာမျက်နှာသည် `POST /api/settings/purge-request-history` ကို ခေါ်ယူပြီး `call_logs`, အဟောင်း `request_detail_logs` နှင့် `${DATA_DIR}/call_logs/` အောက်ရှိ local request artifact များကို ဖျက်သည်။

မူလတန်ဖိုးများကို `src/lib/logEnv.ts` တွင် သတ်မှတ်ထားသည် (`DEFAULT_APP_LOG_RETENTION_DAYS = 7`, `DEFAULT_CALL_LOG_RETENTION_DAYS = 7`)။

## `noLog` ဖယ်ထုတ်ခြင်း ( API သော့တစ်ခုလျှင်)

API ကီးများကို အလံပြထားနိုင်သောကြောင့် ၎င်းတို့၏ အောက်ပိုင်းခေါ်ဆိုမှုအသွားအလာကို မှတ်တမ်းမတင်ပါ။ အလံသည် `api_keys` ဇယား (`no_log INTEGER DEFAULT 0`) တွင်နေထိုင်ပြီး hot-path lookups အတွက် မမ်မိုရီအတွင်းမှ ညှိထားသည်။

```bash
# Create a no-log key (management auth required)
curl -X POST http://localhost:20128/api/keys \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"name": "Privacy key", "noLog": true}'
```

ကူညီသူများ (`src/lib/compliance/index.ts`):

- `setNoLog(apiKeyId, true|false)` — မန်မိုရီအတွင်း ဝင်ရောက်မှုကို ပြောင်းပါ။
- `isNoLog(apiKeyId)` — တောင်းဆိုချက်လမ်းကြောင်းပေါ်တွင် အမှန်ခြစ်ထားသည်။ `api_keys.no_log` မှ သိမ်းဆည်းထားသော 30 s သို့ ပြန်သွားသည်
- `NO_LOG_API_KEY_IDS` (env၊ ကော်မာ-ခြားထားသော) — boot တွင်သတ်မှတ်ထားသည့် in-memory ထဲသို့ကြိုတင်တင်ထားသည်။ ကော်လံကို တိုက်ရိုက်မပြောင်းနိုင်သောအခါတွင် အသုံးဝင်သည်။

စီမံခန့်ခွဲရေးဆိုင်ရာ စာရင်းစစ်ပွဲများ (အကောင့်ဝင်ခြင်း၊ ဝန်ဆောင်မှုပေးသူ အပြောင်းအလဲများ၊ MCP tool ခေါ်ဆိုမှုများ စသည်ဖြင့်) များဖြစ်သည်။** မဟုတ်ဘူး** `noLog` — ကြောင့် သက်ရောက်မှုရှိသော တောင်းဆိုချက်တစ်ခုအတွက်သာ ယာဉ်အသွားအလာ မှတ်တမ်းဝင်ခြင်းကို ဖယ်ထားသည်။

### ဖယ်ထုတ်ခြင်း (`x-omniroute-no-log`)

ဖောက်သည်တစ်ဦးသည် သီးသန့်သော့ကိုမဖန်တီးဘဲ payload မြဲမြံစွာတောင်းဆိုမှုတစ်ခုထဲမှ ကောက်ချက်ချတောင်းဆိုမှုကို ရွေးနိုင်သည်။ တောင်းဆိုမှုတွင် `x-omniroute-no-log: true` ပေးပို့ပါ (`1` နှင့် `yes` တို့ကိုလည်း လက်ခံပါသည်၊ စာလုံးအသေးမပါသော)။ ၎င်းသည် chat handler မှတဆင့်လည်ပတ်သော chat-family လမ်းကြောင်းတိုင်းနှင့်သက်ဆိုင်သည်- ချက်တင်ပြီးစီးမှုများ၊ တုံ့ပြန်မှုများ၊ မက်ဆေ့ချ်များ၊ ပြီးစီးမှုများနှင့် Gemini-သဟဇာတဖြစ်နိုင်သောလမ်းကြောင်း။ ခေါ်ဆိုမှုမှတ်တမ်းအတန်းကို ၎င်း၏အချိန်တံဆိပ်တုံး၊ မော်ဒယ်၊ ဝန်ဆောင်မှုပေးသူ၊ အခြေအနေ၊ ကြာချိန်နှင့် တိုကင်အရေအတွက်များဖြင့် ရေးသားထားဆဲဖြစ်သော်လည်း `request_body`၊ `response_body`၊ တောင်းဆိုချက်အကျဉ်းချုပ်များနှင့် ပိုက်လိုင်းဆိုင်ရာ ပစ္စည်းများကို ချန်လှပ်ထားသည်။

ခေါင်းစီးသည် သော့အလံပါရှိသော ORed ဖြစ်သည်- လော့ဂ်ကီးသည် ခေါင်းစီးနှင့်မသက်ဆိုင်ဘဲ လော့ဂ်မရသေးပါ၊ နှင့် ခေါင်းစီးသည် မှတ်တမ်းမရှိသောသော့အတွက် လော့ဂ်အင်ကို ပြန်ဖွင့်၍မရပါ။ တောင်းဆိုချက်ကို အထက်သို့ ထပ်ဆင့်မပို့မီ ခေါင်းစီးအား ဖယ်ရှားထားသည်။

ဒီခေါင်းစီးက ဘာလဲ။** မဟုတ်ဘူး** Memory ထုတ်ယူခြင်း သို့မဟုတ် semantic cache ကို ပိတ်ပါ။ တောင်းဆိုချက်သည် ထိုစနစ်ခွဲများတွင် ပါဝင်သည့်အကြောင်းအရာကို ဆက်လက်မလုပ်ဆောင်ရသည့်အခါ ၎င်းနှင့်အတူ `x-omniroute-no-memory: true` နှင့် `x-omniroute-no-cache: true` ပေးပို့ပါ။

### `/api/compliance/audit-log` ကို Query လုပ်ခြင်း

ပံ့ပိုးထားသော query params များ (အားလုံး မဖြစ်မနေ မဟုတ်ပါ၊ စာသားစစ်ထုတ်မှုအားလုံးအတွက်
`LIKE %value%` ကိုက်ညီမှုကို အသုံးပြုသည်):

- `action`, `actor`, `target`, `resourceType` (သို့မဟုတ် `resource_type`),
  `status`, `requestId` (သို့မဟုတ် `request_id`)
- `from` / `since`, `to` / `until` — ISO timestamp များ
- `limit` (ပုံသေ `50`၊ အနည်းဆုံး `1`၊ အများဆုံး `500`)
- `offset` (ပုံသေ `0`၊ အများဆုံး `10_000`)

တုံ့ပြန်ချက်သည် JSON array တစ်ခုဖြစ်သည်။ စာမျက်နှာခွဲခြင်း metadata ကို header များတွင် ပြန်ပေးသည်:
`x-total-count`, `x-page-limit`, `x-page-offset`။

```bash
curl "http://localhost:20128/api/compliance/audit-log?action=provider.credentials&from=2026-05-01" \
  -H "Cookie: auth_token=..."
```

## Dashboard

Dashboard တွင် စာရင်းစစ်ဒေတာကို **`/dashboard/audit`**
(`src/app/(dashboard)/dashboard/audit/page.tsx`) ၌ ရရှိနိုင်သည်။ စာမျက်နှာတွင် tab နှစ်ခုရှိသည်:

- **လိုက်နာမှု** (`ComplianceTab.tsx`) — `/api/compliance/audit-log` မှ
  စီမံခန့်ခွဲသူ စာရင်းစစ်ဖြစ်ရပ်များ။ ဖြစ်ရပ်အမျိုးအစား၊ ပြင်းထန်မှု (info / warning
  / critical၊ action + status မှ ဆင်းသက်တွက်ချက်သည်) နှင့် ရက်စွဲအပိုင်းအခြားအလိုက် စစ်ထုတ်နိုင်သည်။ ပြင်းထန်မှုကို
  action/status string များမှ client ဘက်တွင် တွက်ချက်သည်။
- **MCP** (`McpAuditTab.tsx`) — `/api/mcp/audit` မှ MCP ကိရိယာ စာရင်းစစ်၊
  ကိရိယာအမည်နှင့် အောင်မြင်/မအောင်မြင်မှုအလိုက် စစ်ထုတ်နိုင်သည်။

Tab နှစ်ခုလုံးသည် စာမျက်နှာတစ်မျက်နှာလျှင် `50` (လိုက်နာမှု) နှင့် `25` (MCP) ဖြင့်
စာမျက်နှာခွဲထားသည်။

## Provider Credential Helper များ

`src/lib/compliance/providerAudit.ts` သည် credential ဖြစ်ရပ်များ ထုတ်လွှတ်သည့်အခါ
provider စီမံခန့်ခွဲမှု route များက အသုံးပြုသော ပုံဖော်ပြင်ဆင်မှု helper များကို ပံ့ပိုးသည်:

- `summarizeProviderConnectionForAudit(connection)` — connection snapshot ကို
  `details` သို့ မရေးမီ `apiKey`, `accessToken`, `refreshToken`, `idToken` နှင့်
  `providerSpecificData.consoleApiKey` တို့ကို ဖယ်ရှားသည်။
- `getProviderAuditTarget(connection)` — `target` field အတွက် တည်ငြိမ်သော
  `"<provider>:<name|id>"` string ကို ပေါင်းစပ်ဖန်တီးသည်။
- `extractProviderWarnings(...payloads)` — provider တုံ့ပြန်ချက်များထဲမှ
  မူဝါဒ/ဘေးကင်းရေး သတိပေးချက်များ (`[sanitizer]`, `prompt injection detected`,
  `content has been filtered`, `safety filter`, `policy violation`) ကို ရှာဖွေပြီး
  တွေ့ရှိချက် ၅ ခုအထိ ဖော်ပြပေးသည်၊ တစ်ခုစီကို စာလုံးရေ 400 အထိ ဖြတ်တောက်ထားသည်။

## အကောင်းဆုံး လုပ်ထုံးလုပ်နည်းများ

- PII (ဥပဒေရေးရာ၊ ဆေးဘက်ဆိုင်ရာ စသည်) ကို ကိုင်တွယ်သော API key များကို `noLog: true` ဖြင့် အမှတ်အသားပြုပါ။
- သင်၏ ထိန်းသိမ်းမှုမူဝါဒနှင့် ကိုက်ညီစေရန် `APP_LOG_RETENTION_DAYS` /
  `CALL_LOG_RETENTION_DAYS` ကို ချိန်ညှိပါ။ ပုံသေ ၇ ရက်သည် သတိထားသော သတ်မှတ်ချက်ဖြစ်သည်။
- သင်၏ လိုက်နာမှုအစီအစဉ်က လိုအပ်သည့် အချိန်ဇယားအတိုင်း စာရင်းစစ်ဇယားကို platform ပြင်ပသို့
  (`sqlite3 dump`) ထုတ်ယူပါ — ထည့်သွင်းပေးထားသော မော်ကွန်းသိမ်းဆည်းမှု မရှိပါ။
- brute-force တိုက်ခိုက်မှုကို ရှာဖွေရန် `auth.login.failed` နှင့်
  `auth.login.locked` အရေအတွက်များကို စောင့်ကြည့်ပါ။
- စီမံခန့်ခွဲသူ endpoint အသစ်များ ထည့်သွင်းသည့်အခါ တည်ငြိမ်သော
  `domain.verb.outcome` action string ဖြင့် `logAuditEvent({ ... })` ကို ခေါ်ပြီး IP နှင့် `requestId` ကို
  အလိုအလျောက် ဖမ်းယူနိုင်ရန် request context ကို
  `getAuditRequestContext(request)` မှတစ်ဆင့် ပေးပို့ပါ။
