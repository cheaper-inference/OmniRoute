## janitor ကို ထည့်သွင်းခြင်း (စက်ပေါ်တွင် တစ်ကြိမ်သာ)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root) — မိနစ် 30 တိုင်း လုပ်ဆောင်ပြီး /var/log/runner-janitor.log သို့ မှတ်တမ်းတင်ရန်
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` လိုအပ်သည်။ janitor သည် လမ်းကြောင်းတစ်ခုကို ဖယ်ရှားခြင်းမပြုမီ ဖွင့်ထားသော
ဖိုင်များ၏ snapshot တစ်ခုဖြင့် ထိုလမ်းကြောင်းကို အသုံးပြုနေခြင်းမရှိကြောင်း သက်သေပြသည်။
ဤကိရိယာမရှိပါက မည်သည့်အရာကိုမျှ မဖယ်ရှားဘဲ ထိုအကြောင်းကို အသိပေးသည်
(exit 1)။ ပြောင်းလဲမှုတိုင်းကို ဦးစွာ `--dry-run` ဖြင့် စမ်းသပ်ပါ — ၎င်းသည်
လုပ်ဆောင်မည့်အရာကို အတိအကျ ဖော်ပြပြီး မည်သည့်အရာကိုမျှ မပြောင်းလဲပါ။

run တစ်ကြိမ်စီတွင် လုပ်ဆောင်သည့်အရာများ — **tmpfs ပေါ်တွင် 3 h** ကြာပြီးနောက်နှင့်
disk ပေါ်ရှိ `_work/_temp` တွင် 24 h ကြာပြီးနောက် မိမိတို့၏ ကျန်ရှိနေသောဖိုင်များ
(`runner-*`, `omniroute-*`, `next-build*`, `e2e-build.tar.gz`) ကို ရှင်းလင်းသည်။
75 min ထက်ပိုဟောင်းသော `next-build` ကို ရပ်တန့်သည် (မည်သည့် job မျှ ထိုမျှကြာအောင်
မလုပ်ဆောင်ပါ — 2026-08-27 တွင် GitHub က ၎င်း၏ job ပျောက်ဆုံးသွားပြီဟု
သတ်မှတ်ပြီးနောက် run တစ်ခုသည် 70 min ကြာ လုပ်ဆောင်နေခဲ့သည်)။ unit **ရပ်တန့်နေသော**
runner များ၏ 48 h သက်တမ်းရှိ checkout များကို ရှင်းလင်းသည်။ disk အသုံးပြုမှု ≥ 85 %၊
memory PSI `full/avg60` ≥ 10 % နှင့် listener အရေအတွက်သည်
`MAX_ACTIVE_RUNNERS` ထက်များနေပါက (omniroute/အခြားဟူ၍ ခွဲခြမ်းဖော်ပြလျက်)
သတိပေးသည်။ Exit 1 = စစ်ဆေးဆောင်ရွက်ရန် လိုအပ်သည်။ log ကို ဖတ်ပါ။

75-minute စည်းမျဉ်းသည် GitHub က လက်လျှော့ပြီးဖြစ်သော job တစ်ခု၏ build ကို
မဖမ်းမိနိုင်ပါ။ `Runner.Listener` က ၎င်း၏ job ကို သက်တမ်းမတိုးနိုင်သည့်အခါ
`_diag/Runner_*.log` တွင်
`POST request to …/renewjob timed out after 100 seconds` ဟု ပြသပြီး၊ နောက်ဆုံးအောင်မြင်စွာ
သက်တမ်းတိုးပြီး ဆယ်မိနစ်ခန့်အကြာတွင် API က job ကို `completed`
(failure) ဟု အစီရင်ခံသော်လည်း `next-build` သည် ချိတ်ဆက်ထားသော job မရှိဘဲ ဆက်လက်
လုပ်ဆောင်နေသည် (2026-10-18 တွင် #17066 ၏ Build သည် 19:43 တွင် failed ဖြစ်ခဲ့ပြီး
၎င်း၏ build က နောက်ထပ် ငါးမိနစ်ကြာသည့်တိုင် 40 GB ကို ဆက်လက်ယူထားဆဲဖြစ်သည်)။
နောက်ဆုံး `_diag/Worker_*.log` ထဲရှိ ref ကို အတည်ပြုပြီးနောက် build tree ကိုသာ PID ဖြင့်
SIGTERM ပို့ပါ — `next-build`, `npm run build`, `build-next-isolated.mjs` နှင့်
`_work` worker များ။ `Runner.Listener`, `RunnerService.js` သို့မဟုတ် `Runner.Worker`
တို့ကို လုံးဝမထိပါနှင့်။ worker က job ကို cancelled ဖြစ်ကြောင်း အစီရင်ခံပြီး listener သည်
မိမိဘာသာ ပြန်လည် online ဖြစ်လာမည်။

## Runner unit များ: KillMode

Runner ၏ မူလ `KillMode=process` သည် unit တစ်ခုကို ရပ်တန့်ခြင်း သို့မဟုတ်
ပြန်လည်စတင်ခြင်းပြုသည့်အခါ `Runner.Worker → npm → next-build` ကို ဆက်လက်
အသက်ရှင်စေသည် — ချိတ်ဆက်ထားသော job မရှိသည့် orphan build သည် RAM နှင့်

**ကိုယ်တိုင်လက်ခံဆောင်ရွက်သော capacity ကို ထပ်တိုးခြင်းက လက်ခံဆောင်ရွက်ပေးထားသော queue ကို မဖြေရှင်းနိုင်ပါ။** devbox
(`devbox-vm-06-dev002`, 24 vCPU / 54 GB) တွင် runner တစ်ခု လက်ခံဆောင်ရွက်နိုင်သော်လည်း agent session များကြောင့် ၎င်း၏ load သည် 20–26 တွင် ရှိနှင့်ပြီးဖြစ်သည်၊ agent container တွင် Docker daemon မရှိသည့်အပြင် ပြည့်ကျပ်နေသော lane သည်လည်း လက်ခံဆောင်ရွက်ပေးထားသည့် lane ဖြစ်သည်။ တစ်ချိန်တည်းတွင် `.113` box ၌ နေရာလွတ် 71 GB နှင့် load 5–8 ရှိခဲ့သည်။ ၎င်း၏ ကန့်သတ်ချက်မှာ CPU မဟုတ်ဘဲ အထက်ပါ listener တစ်ခုချင်းစီအတွက် memory budget (listener 6 ခု အများဆုံး) ဖြစ်သည်။ ကျန်ရှိသော ဖြေရှင်းနည်းများမှာ လုပ်ငန်းစဉ်ဆိုင်ရာ နည်းလမ်းများဖြစ်သည်- campaign PR များကို Mergify queue (`label=queue`) မှတစ်ဆင့် merge လုပ်ပါ၊ batch များသည် PR တစ်ခုလျှင် run တစ်ခုနှင့် push တစ်ခုလျှင် run တစ်ခုစီအစား `merge_group` CI run တစ်ခုကို မျှဝေသုံးစွဲသည်၊ CodeQL မူလသတ်မှတ်ချက်ရှိ language များကို လျှော့ချပါ၊ ထို့ပြင် `release-acceptance.yml` ကို ၎င်းဖတ်ရှုသော file များအလိုက် filter လုပ်ပါ။
