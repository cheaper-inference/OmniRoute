## npm Trusted Publishing (v3.8.51 မှစ၍ မူလသတ်မှတ်ချက်) — တောင်းဆိုမှ staged လုပ်ပြီး direct ကို fallback အဖြစ် အသုံးပြုခြင်း

`npm-publish.yml` သည် ပုံမှန်အားဖြင့် **npm Trusted Publishing (OIDC)** မှတစ်ဆင့်
publish လုပ်သည်။ `stage-npm` job (github-hosted) သည် ထို run အတွက်
GitHub ၏ id-token ကို အချိန်တိုအတွင်း အသုံးပြုနိုင်သော npm credential အဖြစ် လဲလှယ်ပေးသည် — repository secrets
ထဲတွင် သက်တမ်းရှည် npm token မရှိသကဲ့သို့၊ 2FA prompt လည်း မလိုအပ်ဘဲ provenance ကို ပူးတွဲပေးသည်။
2FA ကို ကျော်နိုင်သော token များကို ယခုအခါ အနားပေးနေခြင်းကြောင့် npm sanctions ကို ကျော်လွှားနိုင်သည့်
နည်းလမ်းမှာ ဤအချက်ဖြစ်သည်။ ထို့ကြောင့် v3.8.48 အထိ project တွင် ရှိခဲ့သော အပြည့်အဝ အလိုအလျောက်
လုပ်ဆောင်မှုကို ပြန်လည်ရရှိစေပြီး WS1.3 အာမခံချက်ကိုလည်း ထိန်းသိမ်းထားသည် (ပေါက်ကြားသွားသော token တစ်ခုတည်းဖြင့်
publish မလုပ်နိုင် — token မရှိသောကြောင့် ဖြစ်သည်)။

**တစ်ကြိမ်သာ ပြုလုပ်ရမည့် setup (owner):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)။ ထို setup မပြီးမချင်း အလိုအလျောက်အဆင့်သည် `ENEEDAUTH` ဖြင့် ပျက်ကွက်မည်။
`publish_mode=staged` (အောက်တွင် ဖော်ပြထားသည်) သို့မဟုတ် `direct` ဖြင့် ပြန်လည် dispatch လုပ်ပါ။

### Staged publishing (တောင်းဆိုမှ — `publish_mode=staged`)

npm-publish workflow သည် တိုက်ရိုက် publish မလုပ်တော့ဘဲ packed tarball ကို
(`check:pack-boot`) ဖြင့် စစ်ဆေးပြီးနောက် `npm stage publish` ကို run သည် — အတိအကျ ထို bytes များကို
registry ပေါ်တွင် သိမ်းထားမည်ဖြစ်ပြီး၊ **owner က အတည်မပြုမချင်း install လုပ်၍ မရပါ**။ လူက ပြုလုပ်ရသော 2FA gate ကို
proof မပြုမီမှ မဟုတ်တော့ဘဲ proof ပြုပြီးနောက်သို့ ရွှေ့ထားသည်။

**Workflow အောင်မြင်ပြီးနောက် Owner ၏ လုပ်ငန်းစဉ်:**

1. `npm stage list omniroute` — stage id ကို ရှာပါ (workflow summary တွင်လည်း ထုတ်ပြထားသည်)။
2. Staged bytes များကို စစ်ဆေးပါ (အကြံပြုသည်): `npm stage download <id>` ကို run လုပ်ပြီး၊ ထို့နောက်
   download လုပ်ထားသော tarball ကို ယာယီ prefix ထဲသို့ install လုပ်ကာ boot လုပ်ပါ
   (`npm run check:pack-boot` သည် CI ထဲတွင် အလားတူ pack→install→boot verdict ကို အလိုအလျောက် ပြုလုပ်ပေးသည်)။
3. `npm stage approve <id>` — 2FA prompt သည် publish ကို ပြုလုပ်ခြင်းပင် ဖြစ်သည်။ `npm stage reject <id>` သည်
   stage ကို ဖျက်ပစ်သည်။
4. Publish ပြီးနောက် net: post-publish verifier (v3.8.49 plan ၏ WS1.4) သည် public registry မှ
   publish လုပ်ထားသော version ကို clean container ထဲသို့ install လုပ်ပြီး boot လုပ်သည်။

**အရေးပေါ် fallback:** `workflow_dispatch` ဖြင့် `publish_mode=direct` ကို အသုံးပြုပါက
legacy immediate `npm publish` ကို ပြန်လည်ရရှိမည် (staging ကိုယ်တိုင် အဆင်မပြေသည့်အခါတွင်သာ အသုံးပြုပြီး
အကြောင်းရင်းကို မှတ်တမ်းတင်ပါ)။

**တစ်ကြိမ်သာ ပြုလုပ်ရမည့် hardening (owner, npmjs.com):** `omniroute` အတွက် Trusted Publisher ကို
stage-only mode ဖြင့် configure လုပ်ပါ။ ထိုသို့လုပ်ခြင်းဖြင့် ပေါက်ကြားသွားသော သက်တမ်းရှည် token သည်
မည်သည့်နေရာမှမဆို `npm publish` ကို တိုက်ရိုက်မလုပ်နိုင်တော့ပါ — CI သည် stage လုပ်နိုင်ရုံသာရှိပြီး owner ၏
2FA ဖြင့်သာ release လုပ်နိုင်မည်ဖြစ်သည်။

**ပျက်စီးနေသော artifact အတွက် လုပ်ဆောင်ရမည့်နည်းလမ်း (မပြောင်းလဲ):** ပုံမှန် ပထမဆုံး တုံ့ပြန်မှုအဖြစ်
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ကို အသုံးပြုပါ (မိနစ်ပိုင်းအတွင်း ပြုလုပ်နိုင်ပြီး
ပြန်လည်ပြင်ဆင်နိုင်သည်)။ `npm unpublish` ကို 72h/no-dependents window အတွင်းတွင်သာ အသုံးပြုပြီး
ပထမဆုံး လုပ်ဆောင်ချက်အဖြစ် မည်သည့်အခါမျှ မသုံးပါနှင့်။ Docker တွင် version tag ကို ဘယ်တော့မှ ပြန်မရေးပါနှင့် —
rollback သည် `latest` ကို နောက်ဆုံးအောင်မြင်သော digest သို့ ပြန်ညွှန်းခြင်းဖြစ်သည်။

**Docker Hub `latest` (တည်ငြိမ်သော SemVer publish တိုင်းတွင် မဖြစ်မနေ):** `docker-publish` workflow သည်
**နှစ်ခုစလုံး** `X.Y.Z` နှင့်၊ `should-promote-latest.sh` က ၎င်းသည် အမြင့်ဆုံး stable SemVer ဖြစ်ကြောင်း
သဘောတူသည့်အခါ `:latest` ကိုပါ **တူညီသော digest** ဖြင့် tag လုပ်ရမည်။ Job ပြီးနောက် Hub `latest` digest သည် အသစ်သော
SemVer digest နှင့် တူညီရမည်ဖြစ်ပြီး `last_updated` လည်း ပြောင်းလဲရမည်။ Release notes တွင် git ပေါ်၌သာ
ရှိသော fix များအကြောင်း ရေးထားစဉ် `:latest` ကို အဟောင်း build တစ်ခုတွင် မထားခဲ့ပါနှင့်။
Compose quickstarts သည် `:latest` ကို အသုံးပြုသည်။ GitOps သည် `X.Y.Z` ဖြင့် pinning ဆက်လက်ပြုလုပ်သင့်သည်။
[Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) နှင့် #10317 ကို ကြည့်ပါ။

**Docker Hub organization repository (`cheaperinference/omniroute`):** Docker Hub သည်
repository တစ်ခုကို namespace များအကြား ရွှေ့ပြောင်း၍ မရသောကြောင့် `diegosouzapw/omniroute` သည် ၎င်း၏ pull history
နှင့် release တိုင်းကို ဆက်လက်ထိန်းသိမ်းထားမည်ဖြစ်ပြီး `docker-publish` ၏ `mirror-org-dockerhub` job သည်
ထွက်ရှိပြီးသော version တစ်ခုချင်းစီ (promote လုပ်သည့်အခါ `:latest` ပါဝင်သည်) ကို
`ghcr.io/cheaper-inference/omniroute` မှ organization repository သို့ ကူးယူပေးမည်။ ၎င်းအတွက်
`DOCKERHUB_ORG_USERNAME` /
`DOCKERHUB_ORG_TOKEN` secrets များ လိုအပ်သည်။ ထို secrets များ မရှိပါက job သည် "Docker Hub org
mirror skipped" warning ဖြင့် အောင်မြင်စွာ ဆက်လက်ပြီး အခြား registry များသို့ ပုံမှန် publish လုပ်မည်။ ထိုနေရာတွင်
ထွက်ရှိပြီးသော version တစ်ခုကို publish လုပ်ရန် **Actions → Mirror Docker image to the Docker Hub org → Run
workflow** ကို `version=X.Y.Z` ဖြင့် run လုပ်ပါ (အမြင့်ဆုံး stable version အတွက် `promote_latest` ကို အသုံးပြုပါ)။
၎င်းသည် ရှိပြီးသား image များကိုသာ ကူးယူခြင်းဖြစ်ပြီး rebuild ပြုလုပ်မည်မဟုတ်ပါ။

## အရေးပေါ်ပြင်ဆင်မှု အမြန်လမ်းကြောင်း (label `hotfix`)

`hotfix` label တပ်ထားသော PR သည် လေးလံသည့် CI matrix (9-shard E2E၊ coverage ratchet၊
quality-gate၊ quality-extended) ကို ကျော်ပြီး မြန်ဆန်ကာ အရေးကြီးသည့် ပြဿနာများကို ကောင်းစွာဖော်ထုတ်နိုင်သော gate များဖြစ်သည့် build၊
unit shard များ၊ integration၊ vitest၊ lint/typecheck၊ docs-sync၊ `check:pack-artifact`
နှင့် tarball boot-smoke (`check:pack-boot`) တို့ကို ဆက်လက်ထားရှိသည်။ ရည်မှန်းချက်မှာ ~33min အစား ≤15min အတွင်း green ဖြစ်ရန်ဖြစ်သည်။

**ဝင်ရောက်ခွင့်မူဝါဒ — လေးချက်စလုံး လိုအပ်သည် (Chromium/VS Code/Node အရေးပေါ်လမ်းကြောင်းများကို စံနမူနာယူထားသည်):**

1. **ပြင်းထန်မှု**: production ပျက်နေခြင်း — ထုတ်ဝေထားသော artifact သည် boot လုပ်စဉ် crash ဖြစ်ခြင်း /
   လုံခြုံရေးပြင်ဆင်ချက်ဖြစ်ခြင်း / release အသုံးပြုသူတိုင်း ထိခိုက်ခြင်း။ "အရေးကြီးသည်" ဆိုသည်မှာ "ပျက်နေသည်" မဟုတ်ပါ။
2. **လုပ်ပိုင်ခွင့်**: repository owner တစ်ဦးတည်းသာ `hotfix` label ကို တပ်ရမည်။ ထို label ကိုယ်တိုင်က
   အတည်ပြုချက် ဖြစ်သည် — campaign PR တစ်ခုတွင် မိမိဘာသာ မည်သည့်အခါမျှ မတပ်ရ။
3. **အထောက်အထား**: PR body တွင် ယခင် fully-green heavy run (ကျော်ထားသော job များက
   ထပ်မံစစ်ဆေးမည့် suite) အပြင် ပြင်ဆင်ချက်ကိုယ်တိုင်၏ failing-then-passing test ကိုပါ link ချိတ်ထားရမည်။
4. **အတိုင်းအတာ**: cherry-pick-only — အနည်းဆုံးလိုအပ်သော ပြင်ဆင်ချက်သာဖြစ်ပြီး refactor များနှင့် မသက်ဆိုင်သော အပြောင်းအလဲများ မပါရ။

ကျော်ထားသော coverage/ratchet မျက်နှာပြင်ကို release branch ရှိ နောက်ထပ် full run
(စဉ်ဆက်မပြတ် release-green) က ပြန်လည်စစ်ဆေးသည် — ဤလမ်းကြောင်းသည် စောင့်ဆိုင်းချိန်ကိုသာ ကျော်ပြီး စစ်ဆေးအတည်ပြုမှုကို မည်သည့်အခါမျှ မကျော်ပါ။
Test သီးသန့် diff များ (`tests/` အောက်ရှိ file အားလုံးဖြစ်ပြီး `tests/e2e/` အောက်တွင် တစ်ခုမျှမရှိခြင်း) သည် မည်သည့် label မလိုဘဲ E2E
matrix ကို အလိုအလျောက် ကျော်သည်။

### Hooks (Husky အတည်ပြုပြီး)

Husky hooks များသည် `.husky/` တွင် ရှိပြီး git လုပ်ဆောင်ချက်များအတွင်း အလိုအလျောက် run လုပ်သည်။

### Build Layout

Repository တွင် output directory သုံးခု သီးခြားရှိသည် — ၎င်းတို့ကို မရောထွေးပါနှင့်-

| Directory | Purpose                                                        | Tracked?        |
| --------- | -------------------------------------------------------------- | --------------- |
| `src/`    | Application source (TypeScript / TSX)                          | Yes             |
| `.build/` | Build intermediates — `next build` output (`distDir`)          | No (gitignored) |
| `dist/`   | Shippable npm bundle — `assembleStandalone` ဖြင့် စုစည်းထားသည် | No (gitignored) |

> **Operator note:** remote VPS image directory သည် `/usr/lib/node_modules/omniroute/app/` အတိုင်းပင် ဖြစ်သည်။
> **in-repo** build output တစ်ခုတည်းသာ (`app/` → `dist/`) ပြောင်းလဲထားသည်။ Deploy skill များသည်
> `dist/` ၏ contents များကို remote `app/` directory ထဲသို့ rsync ပြုလုပ်သည် — VPS path ပြောင်းလဲရန် မလိုအပ်ပါ။

**Single-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy အတွက် `npm run build` ကို run ပြီးနောက် သီးခြား `npm run build:cli` ကို မ run ပါနှင့် — command တစ်ခုတည်းဖြင့် clean rebuild နှင့် sentinel ကို ပြုလုပ်ပေးသော `npm run build:release` ကို အသုံးပြုပါ။

`scripts/release/dry-run-lts-cut.mjs` သည် မည်သည့်အရာကိုမျှ လက်တွေ့လုပ်ဆောင်ခြင်းမရှိဘဲ git နှင့် `gh` ကို ဖတ်ရှုပြီး
လုပ်ငန်းစဉ်တစ်ခုလုံးကို ပရင့်ထုတ်သည် — ကြိုတင်လိုအပ်ချက်များ (source ကို resolve လုပ်နိုင်ခြင်း၊ source repository တွင် history အပြည့်အစုံရှိခြင်း —
shallow clone တစ်ခုသည် `stable/v3` ကို push မလုပ်နိုင်ပါ၊ လက်ခံသည့်ဘက်က ပထမဆုံး
grafted parent တွင် pack ကို ငြင်းပယ်မည်ဖြစ်သဖြင့် full clone မှ ခွဲထုတ်ပါ သို့မဟုတ် `git fetch --unshallow origin` ကို ဦးစွာလုပ်ဆောင်ပါ — ယခင်
tag ရှိခြင်း၊ `package.json` သည် ပစ်မှတ်ဗားရှင်း ဖြစ်ခြင်း၊ `release-freeze` issue တစ်ခု ဖွင့်ထားခြင်း၊ ရှိပြီးသား release branch တွင်
ဖွင့်ထားဆဲ `Release branch not green` issue
မရှိခြင်း — မရှိသေးသော branch တစ်ခုကို `?` unknown ဟု ဖော်ပြပြီး
green ဟု မည်သည့်အခါမျှ မသတ်မှတ်ပါ — Mergify `release` queue ကို စီစဉ်သတ်မှတ်ထားခြင်း (G11: `queue_rules`၊ `checks_timeout`၊
label `queue`)၊ `release/*` ruleset က deletion နှင့် force-push တို့ကို ဆက်လက်ပိတ်ပင်ထားခြင်းနှင့်
`stable/v3`၊ `develop` တို့ မရှိသေးခြင်း)၊ branch အဆင့်နှစ်ခု၊ dormant-workflow
trigger များနှင့် `if:` condition များအနက် မည်သည့်အရာများ true ဖြစ်လာသည် (ထို့ပြင် မည်သည့်အရာများသည် repository variable ဖြင့် ဆက်လက်ကန့်သတ်ထားသည် သို့မဟုတ်
canonical repository တွင် ပုံသေချိတ်ဆက်ထားသည်)၊ မျှော်မှန်းထားသည့် dist-tag များ (`latest` → 3.9.0၊ `next` နှင့်
`nightly` ဗလာ) နှင့် rollback တို့ဖြစ်သည်။ Exit `0` = `RESULT: READY`၊ `1` = ပိတ်ဆို့သော ကြိုတင်လိုအပ်ချက်တစ်ခု
မအောင်မြင်ပါ (`✗`)၊ `2` = အသုံးပြုမှုပုံစံအမှား။ `--advisory <id,...>` သည် စစ်ဆေးမှုတစ်ခုကို ဖုံးကွယ်ခြင်းမရှိဘဲ သတိပေးချက် (`!`)
အဖြစ် အဆင့်လျှော့ပေးသည်။

### PR preview artifact (တစ်ကြိမ်သာ build လုပ်ပြီး တူညီသော byte များကို promote လုပ်ပါ)

`.github/workflows/preview-artifact.yml` သည် PR head တစ်ခုမှ production tarball တစ်ခုကို တည်ဆောက်ပြီး
ထို build အတိအကျကို အတည်ပြုစစ်ဆေးသည် (#8084 slice (a))။ Repository တူသော PR များအတွက်သာဖြစ်ပြီး မည်သည့်အရာကိုမျှ publish မလုပ်ပါ။

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # သို့မဟုတ် `preview-artifact` label ကို ထည့်ပါ
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview ထည့်သွင်းမှု
```

Run သည် `npm ci`၊ `npm run build:release`၊ `npm run check:pack-artifact` တို့ကို လုပ်ဆောင်ပြီး
tarball ကို pack လုပ်သည်၊ `npm run check:pack-boot` (အတု secret များ၊ ယာယီ data dir) ကို လုပ်ဆောင်ပြီး ပြန်လည် pack လုပ်ကာ
digest မတူညီပါက မအောင်မြင်စေသည်။ ထို့နောက် `artifact-identity.json` (head SHA၊ base
SHA၊ lockfile hash၊ platform၊ arch၊ node ABI၊ bundler၊ build policy —
`scripts/release/artifact-identity.mjs`) ကို မှတ်တမ်းတင်ပြီး သီးခြား job တစ်ခုတွင် tarball ကို attest လုပ်သည်။ Preview တစ်ခုကို promote လုပ်ခြင်းဆိုသည်မှာ
ထို tarball ကို install လုပ်ခြင်းဖြစ်သည်- source မှ မည်သည့်အခါမျှ ပြန်လည် build မလုပ်ပါနှင့်။

### ခွဲထုတ်ခြင်း (3.9.0၊ GO ပြီးနောက်)

1. GO ကို [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) တွင် မှတ်တမ်းတင်ထားသည်။
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` က `RESULT: READY` ကို ပရင့်ထုတ်သည်။
3. Dry-run က ပရင့်ထုတ်သော command များဖြင့် `origin` တွင် branch များကို ကိုယ်တိုင်ဖန်တီးပါ —
   script သည် `origin` သို့ push လုပ်ရန် ငြင်းပယ်သည်။ Review ပြီးသော develop commit ကို ပြန်လည်အသုံးပြုရန်
   သင်၏ fork ကို ပစ်မှတ်ထား၍ 3.9.0 tip တွင် `--execute` အစမ်းလေ့ကျင့်မှုကို ဦးစွာလုပ်ဆောင်ပါ၊ ၎င်းက SHA နှစ်ခုလုံးကို ပရင့်ထုတ်ပေးပြီး
   တူညီသော commit များကို push လုပ်နိုင်သည်-

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. ပထမဆုံး PR ကို ပေါင်းစည်းခြင်းမပြုမီ `stable/v3` နှင့် `develop` ကို ကာကွယ်ပါ (စည်းမျဉ်းအစုများ + ပေါင်းစည်းမှုတန်းစီစနစ်)။
5. အသုံးမပြုဘဲထားသော workflow များသည် branch ရှိလာသည်နှင့် စတင်အလုပ်လုပ်ပါမည်- `forward-port.yml` (`stable/v3` သို့ push လုပ်ခြင်း)၊
   `validate-stable-pr.yml` (`stable/v3` သို့ PR များ) နှင့် `nightly-v4-build.yml`
   (`develop` ကို build လုပ်ခြင်း)။ တရားဝင်စတင်အသုံးမပြုမီ `secrets.FORWARD_PORT_TOKEN` repository secret ကို သတ်မှတ်ပါ (သို့မှသာ forward-port PR များတွင် CI အလုပ်လုပ်မည်)။
   ပိုင်ရှင်က repository variable `vars.NIGHTLY_PUBLISH` ကို `true` ဟု သတ်မှတ်ပြီး npm Trusted Publishing က
   `nightly-v4-build.yml` ကို လက်ခံသည့်အချိန်အထိ ညစဉ်ထုတ်ဝေမှုကို ပိတ်ထားမည်ဖြစ်သည်။ Channel သတ်မှတ်ဖြေရှင်းမှုကို `scripts/release/dist-tag.mjs` က ဆောင်ရွက်ပြီး
   `npm-publish.yml` အသုံးပြုသည့် resolver နှင့် အတူတူပင်ဖြစ်သည်။
6. Channel များကို စစ်ဆေးပါ- `npm view omniroute dist-tags --json` တွင် `latest` = 3.9.0 ဟု ပြသပြီး v4 မထုတ်ဝေမချင်း
   `next` / `nightly` မရှိကြောင်း အတည်ပြုပါ။
7. လိုအပ်ပါက ပြန်လည်ရုပ်သိမ်းရန်- `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   နှင့် `npm dist-tag add omniroute@3.8.59 latest` ကို အသုံးပြုပါ။

## နောက်ပြန်ပြောင်းခြင်း

Release တွင် အရေးကြီးသော ပြဿနာရှိပါက-

1. `gh release edit vX.Y.Z --prerelease` (နောက်ဆုံး release မဟုတ်ကြောင်း သတ်မှတ်သည်)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (အသုံးပြုသူများက မသုံးစွဲရသေးမှသာ)
3. သို့မဟုတ်- `release/vX.Y.0` တွင် hotfix ပြုလုပ်ပြီး → patch release `vX.Y.(Z+1)` ထုတ်ပါ
4. GitHub Discussions နှင့် Discord တွင် ချက်ချင်း အသိပေးပါ

## တင်းကျပ်သော စည်းမျဉ်းများ

- `main` သို့ တိုက်ရိုက် commit ဘယ်တော့မှ မလုပ်ပါနှင့်
- `main` သို့မဟုတ် `release/*` branch များသို့ `git push --force` ဘယ်တော့မှ မသုံးပါနှင့်
- Husky hook များကို (`--no-verify`) အသုံးပြု၍ ဘယ်တော့မှ ကျော်မသွားပါနှင့်
- လျှို့ဝှက်ချက်များ၊ အထောက်အထားများ သို့မဟုတ် `.env` ဖိုင်များကို ဘယ်တော့မှ commit မလုပ်ပါနှင့်
- Coverage ကို ≥60/60/60/60 (statements/lines/functions/branches) တွင် ဆက်လက်ထိန်းသိမ်းထားရမည်
- `src/`, `open-sse/`, `electron/` သို့မဟုတ် `bin/` ရှိ production code ကို ပြောင်းလဲသည့်အခါ test များကို အမြဲထည့်သွင်းပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ

## အလိုအလျောက် Sync စစ်ဆေးမှု

PR မဖွင့်မီ docs sync guard ကို local တွင် run ပါ-

```bash
npm run check:docs-sync
```

CI သည်လည်း ဤစစ်ဆေးမှုကို `.github/workflows/ci.yml` (lint job) တွင် run ပါသည်။
