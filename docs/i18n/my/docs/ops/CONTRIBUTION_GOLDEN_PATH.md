ဤလမ်းညွှန်ကို အသုံးပြုပြီး pull request တစ်ခုအတွက် ယုံကြည်စိတ်ချရသည့် အတိုဆုံး development loop ကို ရွေးချယ်ပါ။ ဤလမ်းညွှန်သည် အောက်တွင် လင့်ခ်ချိတ်ထားသည့် သက်ဆိုင်ရာနယ်ပယ်အလိုက် architecture နှင့် security စာရွက်စာတမ်းများကို အစားထိုးခြင်းမဟုတ်ပါ။ ၎င်းသည် အများအားဖြင့် တွေ့ရသော ပြောင်းလဲမှုအမျိုးအစားတစ်ခုစီကို ၎င်းတို့၏ contracts၊ အဓိကထားစစ်ဆေးမှုများနှင့် CI coverage တို့နှင့် ချိတ်ဆက်ပေးခြင်းဖြစ်သည်။

## ပြောင်းလဲမှုတိုင်း လိုက်နာရသည့် လမ်းကြောင်း

1. **မပြင်ဆင်မီ base ကို ရွေးချယ်ပါ။** လက်ရှိအသုံးပြုနေသည့် အမြင့်ဆုံး `release/v*` branch ကို ရှာဖွေပြီး
   ၎င်း၏ tip မှ branch ခွဲပါ။ `main` ကို မဟုတ်ဘဲ ထို branch ကို target လုပ်ပါ။ release freeze ပြုလုပ်ထားပါက freeze လုပ်ထားသည့်
   branch ကို target မလုပ်ပါနှင့်။ အစား
   [Branching & Release Model](BRANCHING_MODEL.md) တွင် ဖော်ပြထားသည့် နောက်ထပ် active cycle ကို အသုံးပြုပါ။
2. **Contracts များကို သတ်မှတ်ဖော်ပြပါ။** ပြောင်းလဲမှုကြောင့် သက်ရောက်မှုရှိသည့် catalog၊ schema၊ generated artifact၊ public API သို့မဟုတ် user
   interface တိုင်းကို ဖော်ထုတ်ပါ။ အောက်ပါဇယားတွင် အနည်းဆုံး စတင်ရမည့်အစုကို ဖော်ပြထားသည်။
3. **အဓိကထားသည့် tests များကို ရေးသားပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ။** `src/`၊ `open-sse/`၊ `electron/` သို့မဟုတ်
   `bin/` အတွင်းရှိ production ပြောင်းလဲမှုများအတွက် တူညီသော PR ထဲတွင် automated test တစ်ခု လိုအပ်သည်။ အပြုအမူကို သက်သေပြနိုင်သည့်
   အငယ်ဆုံး test files များကို အရင် run ပြီးနောက် ဖော်ပြထားသည့် focused gates များကို run ပါ။
4. **ကျယ်ပြန့်သည့် matrix ကို CI ဖြင့် run ပါ။** ပြည့်စုံသော unit shards၊ Vitest၊ coverage ratchet နှင့်
   production build တို့ကို PR တွင် run မည်ဖြစ်သည်။ focused failure တစ်ခုက ပိုမိုကျယ်ပြန့်သော သက်ရောက်မှုရှိကြောင်း ညွှန်ပြသည့်အခါ သို့မဟုတ်
   ပြောင်းလဲမှုသည် subsystem အများအပြားကို လွှမ်းခြုံသည့်အခါမှသာ ကျယ်ပြန့်သော suite တစ်ခုကို local တွင် run ပါ။
5. **Review မပြုမီ ညှိနှိုင်းပေါင်းစည်းပါ။** active base ကို fetch လုပ်ပြီး ၎င်း၏ commit အသစ်များနှင့် ထို base နှင့် နှိုင်းယှဉ်ထားသည့် သင့် diff ကို
   စစ်ဆေးပါ။ ထို့နောက် contributor workflow နှင့်အညီ base ကို rebase သို့မဟုတ် merge လုပ်ပါ။ generated-file
   နှင့် catalog conflicts များကို ၎င်းတို့၏ source မှ ဖြေရှင်းပြီး ပြန်လည် generate လုပ်ကာ focused loop ကို ထပ်မံ run ပါ။ ထို့နောက်
   PR သည် active release branch ကိုသာ target လုပ်နေဆဲဖြစ်ကြောင်း အတည်ပြုပါ။
6. **အထောက်အထားကို မှတ်တမ်းတင်ပါ။** PR template တွင် run ခဲ့သည့် commands များ၊ ထည့်သွင်းထားသည့် သို့မဟုတ် ပြောင်းလဲထားသည့် test file တိုင်း၊
   migrations သို့မဟုတ် feature flags များနှင့် ဆိုင်းငံ့ထားဆဲဖြစ်သည့် CI-only validation အားလုံးကို စာရင်းပြုစုပါ။

## ပြောင်းလဲမှုအမျိုးအစားအလိုက် စံပြလမ်းကြောင်းများ

အောက်ပါ commands များသည် အနည်းဆုံး focused checks များသာဖြစ်ပြီး သင်ပြောင်းလဲခဲ့သည့် အပြုအမူကို တိုက်ရိုက်လွှမ်းခြုံသည့် test တစ်ခုကို
ကျော်သွားရန် ခွင့်ပြုချက်မဟုတ်ပါ။

### Provider

**Contracts**

- `src/shared/constants/providers/` အတွင်းရှိ Provider definition နှင့်
  `src/shared/constants/providers.ts` အတွင်းရှိ ၎င်း၏ composition။
- `open-sse/config/providerRegistry.ts` သို့မဟုတ် ၎င်းမှ ခွဲထုတ်ထားသည့် registry files များအတွင်းရှိ models နှင့် capabilities။
- သက်ဆိုင်သည့်အခါ Executor/translator selection၊ OAuth သို့မဟုတ် API-key configuration၊ dashboard assets နှင့် generated
  provider reference။
- Public credentials များသည် `resolvePublicCred()` ကို အသုံးပြုရမည်။ error responses များသည် မျှဝေထားသည့် sanitized
  error helpers ကို အသုံးပြုရမည်။ `docs/security/PUBLIC_CREDS.md` (git; `/docs` ထဲသို့ compile မလုပ်ထားပါ) နှင့်
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ကို ကြည့်ပါ။

**အဓိကထားသည့် loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ပြောင်းလဲသည့်အခါ၊ generated diff ကို commit လုပ်ပါ
npm run lint
```

သက်ရောက်မှုရှိသည့် request family တိုင်းဖြစ်သော chat၊ Responses၊ images၊ embeddings၊ audio သို့မဟုတ် video တို့ကိုလည်း test လုပ်ပါ။
Generated catalog နှင့် golden diffs များကို contract ပြောင်းလဲမှုများအဖြစ် review လုပ်ပါ။ ၎င်းတို့ကို မစစ်ဆေးဘဲ လက်မခံပါနှင့်။

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts` အတွင်းရှိ public strategy values နှင့် UI metadata။
- `open-sse/services/combo.ts` နှင့် `open-sse/services/combo/` အောက်ရှိ dispatch နှင့် ordering။
- Combo schemas၊ persistence၊ resilience state၊ model capabilities နှင့် API/UI controls။
- အပြုအမူပြောင်းလဲသည့်အခါ [Auto-Combo Engine](../routing/AUTO-COMBO.md) နှင့် resilience documentation။

**အဓိကထားသည့် loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy သို့မဟုတ် dispatch ပြောင်းလဲမှုများ
npm run check:known-symbols      # strategy registration ပြောင်းလဲမှုများ
npm run lint
```

Local တွင် deterministic mocked-upstream tests များကို အသုံးပြုပါ။ Live combo smokes များအတွက် credentials လိုအပ်ပြီး
manual ဖြစ်သဖြင့် CI အစားထိုးမှုများ မဟုတ်ပါ။

### UI / UX

**Contracts**

- `src/app/` နှင့် `src/shared/components/` အောက်ရှိ Next.js route/page နှင့် shared component boundaries။
- API response shapes၊ loading/empty/error states၊ keyboard နှင့် screen-reader အပြုအမူ၊
  responsive layout၊ theming နှင့် locale expansion။
- `src/i18n/messages/en.json` အတွင်းရှိ English UI source strings။ user-facing copy အသစ်ကို hard-code မလုပ်ပါနှင့်။

**အဓိကထားသည့် loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction သို့မဟုတ် visual ပြောင်းလဲမှုများအတွက် app ကို run ပြီး ကျဉ်းသော viewport နှင့် ကျယ်သော viewport နှစ်မျိုးလုံးကို စစ်ဆေးပါ။ CI သည်
production build နှင့် ပိုမိုကျယ်ပြန့်သော suites များကို run သော်လည်း visual အပြုအမူအတွက် ပြောင်းလဲမှုနှင့်သင့်လျော်သည့် focused component၊ Playwright
သို့မဟုတ် မှတ်တမ်းတင်ထားသော manual check တစ်ခု လိုအပ်နေဆဲဖြစ်သည်။

### i18n

**Contracts**

- `src/i18n/messages/en.json` သည် UI source ဖြစ်ပြီး `config/i18n.json` သည် locale source ဖြစ်သည်။
- CLI catalogs များကို `bin/cli/locales/` အောက်တွင် သီးခြားထားရှိသည်။
- ICU placeholders နှင့် tags များကို အတိအကျ ထိန်းသိမ်းပါ။ product/provider/model အမည်များ၊
  protocol နှင့် header အမည်များ၊ commands၊ code/JSON identifiers၊ URLs၊ environment variables သို့မဟုတ်
  `OmniRoute`၊ `OAuth`၊ `MCP` နှင့် `A2A` ကဲ့သို့သော protected terms များကို ဘာသာမပြန်ပါနှင့်။ လက်ရှိ source list မှာ
  `scripts/i18n/glossary/protected-terms.json` ဖြစ်သည်။

**အဓိကထားသည့် loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs ပြောင်းလဲသည့်အခါ
npm run lint
```

ဤအရာသည် လက်ရှိ system အတွက် လမ်းညွှန်ချက်ဖြစ်ပြီး ၎င်း၏ tooling သို့မဟုတ် key model ကို တိုးချဲ့ရန် ဖိတ်ခေါ်ခြင်းမဟုတ်ပါ။
အစားထိုး system ကို ဒီဇိုင်းရေးဆွဲနေစဉ် i18n patches များကို လိုအပ်သလောက်သာ တိကျစွာ ပြင်ဆင်ပါ။ Task တွင် generated translations များကို
အတိအကျ လိုအပ်ကြောင်း ဖော်ပြထားပြီး ထွက်ပေါ်လာသည့် diff ကို သင် review လုပ်ပြီးသားဖြစ်သည့်အခြေအနေမှလွဲ၍ external services များကို
ခေါ်ယူသည့် translation commands များကို မ run ပါနှင့်။

### CLI

**Contracts**

- `bin/cli/` အောက်ရှိ အများသုံး command များနှင့် flag များ၊ ထုတ်လုပ်ထားသော API command များ၊ exit code များ၊ stdout/stderr နှင့်
  JSON output ပုံစံများ၊ config/environment အပြုအမူနှင့် package ထဲပါဝင်သော file များ။
- CLI အသုံးပြုသူမြင်ရသည့် စာသားများသည် CLI i18n layer ကို အသုံးပြုရမည်ဖြစ်ပြီး `en`/`pt-BR` catalog များကို တစ်ပြေးညီထားရမည်။
- ပံ့ပိုးထားသော runtime အဖြစ် Node ကို ဆက်လက်ထိန်းသိမ်းပြီး ထုတ်ဝေထားသော binary contract ကို မပြောင်းလဲစေရပါ။

**အဓိကထား စစ်ဆေးသည့် လုပ်ငန်းစဉ်**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ထုတ်လုပ်ထားသော/bundle လုပ်ထားသော CLI ပြောင်းလဲမှုများ
npm run check:pack-policy     # package မျက်နှာပြင်ဆိုင်ရာ ပြောင်းလဲမှုများ
npm run lint
```

အပြုအမူသည် parsing၊ file များ သို့မဟုတ် exit status ပေါ် မူတည်သည့်အခါ ယာယီ data directory တစ်ခုအတွင်း command အတိအကျကို အသုံးပြုပါ။ CI သည် ပိုမိုကျယ်ပြန့်သော package artifact နှင့် ecosystem စစ်ဆေးမှုများကို လုပ်ဆောင်သည်။

### Database

**Contract များ**

- `src/lib/db/` အောက်ရှိ domain module များ၊ သတ်မှတ်ထားသော module များကို တိုက်ရိုက် import လုပ်ပါ (`localDb.ts` re-export layer အဟောင်းကို ဖယ်ရှားထားသည်)။
- `src/lib/db/migrations/` အောက်ရှိ နံပါတ်စဉ်တပ်ထားပြီး idempotent ဖြစ်သော SQL migration များ၊ transaction ဘေးကင်းမှု၊ upgrade
  အပြုအမူ၊ index များနှင့် schema ကြောင့် သက်ရောက်မှုရှိသည့် caller အားလုံး။
- Route နှင့် handler များသည် raw SQL ကို မည်သည့်အခါမျှ တိုက်ရိုက် မလုပ်ဆောင်ရပါ။

**အဓိကထား စစ်ဆေးသည့် လုပ်ငန်းစဉ်**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration တစ်ခု ထည့်သွင်းသည့်အခါ database အသစ်တစ်ခုနှင့် ယခင် schema မှ upgrade လုပ်ခြင်း နှစ်မျိုးလုံးကို စမ်းသပ်ပါ။ Database test များသည် handle များကို ပိတ်ရမည်ဖြစ်ပြီး cleanup ပြုလုပ်စဉ် `resetDbInstance()` ကို ခေါ်ရမည်။ အကောင်းဆုံးကြိုးပမ်းမှုအဖြစ် ထားရှိသော Bun adapter လမ်းကြောင်း ပြောင်းလဲသည့်အခါမှသာ `npm run test:bun:db` ကို လုပ်ဆောင်ပါ။ Node သည် အတည်ပြုချက်အတွက် အဓိကစံအဖြစ် ဆက်လက်တည်ရှိသည်။

### Build / deploy

**Contract များ**

- Root နှင့် workspace manifest များ/lockfile၊ `scripts/build/`၊ Next.js standalone စုစည်းတည်ဆောက်မှု၊ `dist/`
  package အကြောင်းအရာများ၊ Electron platform metadata၊ CI workflow များနှင့် deployment sentinel များ။
- ပံ့ပိုးထားသော Node range များနှင့် `CLAUDE.md` တွင် allow-list ထည့်ထားသော Bun အသုံးပြုမှုကို မပြောင်းလဲဘဲ ထိန်းသိမ်းထားရမည်။
- Build artifact များကို version control တွင် track မလုပ်ရပါ။ dependency၊ license၊ workflow နှင့် package policy များကို လိုက်နာရမည်။

**အဓိကထား စစ်ဆေးသည့် လုပ်ငန်းစဉ်**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency သို့မဟုတ် lockfile ပြောင်းလဲမှုများ
npm run check:pack-policy      # ထုတ်ဝေထားသော package မျက်နှာပြင် ပြောင်းလဲမှုများ
npm run lint
```

ပြောင်းလဲမှုသည် compilation၊ standalone စုစည်းတည်ဆောက်မှု၊ asset များ သို့မဟုတ် runtime bundling ကို သက်ရောက်သည့်အခါမှသာ local တွင် `npm run build` ကို အသုံးပြုပါ။ Release/deploy အတည်ပြုမှုအတွက်သာ `npm run build:release` ကို အသုံးပြုပါ။ CI ၏ build သည် နောက်ဆုံး cross-platform အချက်ပြမှုဖြစ်သည်။ Platform သီးသန့် Electron ပြောင်းလဲမှုများအတွက် သက်ဆိုင်ရာ အဓိကထား build သို့မဟုတ် smoke စမ်းသပ်မှုအထောက်အထား လိုအပ်သည်။

## မျှဝေသုံးစက်အတွက် developer script များ

အခြား session များ အသုံးပြုနေသည့် devbox ပေါ်ရှိ local loop ကို `scripts/dev/` helper နှစ်ခုဖြင့် သတ်မှတ်ထားသည်-

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD မှ ဖိုင်များ
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ဤဖိုင်များကိုသာ အတိအကျ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # သီးခြားခွဲထားသော worktree၊ တစ်ပြိုင်နက် ဘေးကင်းစွာ အသုံးပြုနိုင်သည်
```

- `typecheck-touched.sh` သည် ပြောင်းလဲထားသော `.ts/.tsx` ဖိုင်များကိုသာ ယာယီ
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) မှတစ်ဆင့် 6 GB heap အောက်တွင် typecheck လုပ်သည်။ ထို့ကြောင့် load များသော စက်တွင် OOM
  ဖြစ်စေသည့် project တစ်ခုလုံးအတွက် `tsc -p tsconfig.json` ကို အစားထိုးပေးသည်။ ၎င်းသည် ပြောင်းလဲထားသော ဖိုင်များရှိ error များနှင့် summary စာကြောင်းတစ်ကြောင်းကို ဖော်ပြပြီး၊
  ပြောင်းလဲထားသော ဖိုင်များတွင် error ရှိပါက `1` ဖြင့် ထွက်သည်၊ error များသည် imported ဖိုင်များတွင်သာ ရှိပါက သို့မဟုတ် tsc သည်
  diagnostic မထုတ်ဘဲ ရပ်တန့်သွားပါက `2` ဖြင့် ထွက်သည် (`_artifacts/typecheck-touched/` အောက်တွင် ၎င်းဖော်ပြသည့် log ကို ဖတ်ပါ)၊
  error မရှိပါက `0` ဖြင့် ထွက်သည်။ ယာယီ tsconfig ကို အမြဲဖယ်ရှားပစ်သည်၊ ၎င်းကို ဘယ်တော့မှ commit မလုပ်ပါနှင့်။
- `new-worktree.sh` သည် `<git-common-dir>/omniroute-new-worktree.lock` ပေါ်တွင် တစ်ပြိုင်နက် run များကို အစဉ်လိုက် လုပ်ဆောင်စေသည်
  (ပုံမှန်အားဖြင့် 600 s အထိ စောင့်ပြီး မြင်သာသော message တစ်ခု ပြသသည်၊ override လုပ်နည်းကို script header တွင်
  မှတ်တမ်းတင်ထားသည်)။ ထို့ပြင် worktree မရှိသေးမီ `git worktree add` မအောင်မြင်ပါက
  ၎င်းဖန်တီးခဲ့သော branch ကို rollback လုပ်သည်။ ထို့ကြောင့် ထပ်မံကြိုးစားရာတွင် `git branch -D` ကို ကိုယ်တိုင်လုပ်ရန်
  မလိုအပ်ပါ။ Hard-link လုပ်ထားသော `node_modules` နှင့် `.husky/_` copy တို့မှာ မပြောင်းလဲပါ။

## Local candidate loop

Source test များဖြင့် packaged artifact ကို စတင်နိုင်ကြောင်း သက်သေမပြနိုင်ပါ။ Packaging list များ၊ ဖြတ်တောက်ထားသော dependency များနှင့်
native binary များသည် tarball ကို install လုပ်ပြီး စတင်သည့်အချိန်မှသာ ပျက်ကွက်နိုင်သည်။ `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) သည် RFC #8084 မှ build-once / validate / promote flow ၏ local ဘက်ခြမ်းဖြစ်သည်။
၎င်းသည် candidate တစ်ခုကို တစ်ကြိမ်သာ build လုပ်ပြီး ထို artifact အတိအကျကို validate လုပ်ကာ directory
rename များဖြင့် promote လုပ်သည်။ ထို့နောက် promote လုပ်ထားသော slot ၏ health check မအောင်မြင်ပါက rollback လုပ်သည်။

```bash
npm run dev:candidate -- run --dry-run --json  # အစီအစဉ်ကို ဖော်ပြပြီး မည်သည့်အရာကိုမျှ မပြောင်းလဲပါ
npm run dev:candidate -- run                   # build + validate + promote၊ အလိုအလျောက် rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ထဲသို့ install
npm run dev:candidate -- validate --id <id>    # လွတ်နေသော port တွင် စတင်ပြီး /api/health + /v1/models ကို စစ်ဆေးပါ
npm run dev:candidate -- promote --id <id>     # <id> → current၊ current → previous
npm run dev:candidate -- rollback              # current နှင့် previous ကို နေရာလဲပါ
npm run dev:candidate -- run --from-tarball <file.tgz>  # အခြားနေရာတွင် build လုပ်ထားသော tarball ကို ပြန်လည်အသုံးပြုပါ (CI)
```

- **တစ်ကြိမ်သာ build လုပ်ပါ။** `build` သည် လက်ရှိ tree ကို pack လုပ်သည် (`dist/server.js` လိုအပ်သောကြောင့်
  `npm run build:release` ကို ဦးစွာ run ပါ) သို့မဟုတ် `--from-tarball` ကို copy လုပ်သည်။ ထို့နောက် tarball တွင်
  `node_modules` မပါဝင်သောကြောင့် သီးခြားခွဲထားသည့် npm prefix ထဲသို့ tarball ကို install လုပ်သည်။ id သည် အတိုကောက် `HEAD`
  sha ဖြစ်ပြီး (tree တွင် local ပြောင်းလဲမှုများရှိပါက `-dirty`) tarball အတွက်မူ `tgz-<sha256>` ဖြစ်သည်။ Build လုပ်ပြီးသား
  clean id ကို ပြန်လည် build လုပ်မည့်အစား ပြန်လည်အသုံးပြုသည်။ ပြန်လည် build လုပ်ရန် `--force` ကို ပေးပါ။
- **Source မဟုတ်ဘဲ package ကို validate လုပ်ပါ။** `validate` သည် အသစ်ဖြစ်သော
  `DATA_DIR=<candidate>/data`၊ အတု secret များဖြင့် install လုပ်ထားသော CLI (`serve --port <free port>`) ကို စတင်ပြီး
  operator ၏ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` နှင့် `INITIAL_PASSWORD` ကို environment မှ ဖယ်ရှားထားသည်။
  ထို့ကြောင့် အသစ် install လုပ်ထားမှု၏ keyless loopback posture ကို စစ်ဆေးသည်။ ၎င်းသည်
  `GET /api/health` က 200 ပြန်ပေးသည်အထိ စောင့်ပြီး `GET /v1/models` က 200 ပြန်ပေးရန် သတ်မှတ်သည်၊ process group ကို ရပ်တန့်ကာ
  ရလဒ်ကို tarball hash နှင့်အတူ `validation.json` တွင် မှတ်တမ်းတင်သည်။
- **တူညီသော artifact ကို promote လုပ်ပါ။** `promote` သည် လက်ရှိ tarball hash အတွက် အောင်မြင်သော validation မရှိသည့်
  candidate ကို ငြင်းပယ်သည်။ ပုံမှန် active slot သည် `_artifacts/candidate/current` ဖြစ်သည်။ `--target <dir>`
  သည် တူညီသော filesystem ပေါ်ရှိ အခြား directory ကို ရွေးချယ်ပြီး ၎င်း၏ previous slot သည် `<dir>.previous` ဖြစ်သည်။
  Rename တစ်ခုစီသည် atomic ဖြစ်ပြီး လုပ်ဆောင်နေစဉ်တစ်ဝက်တွင် ပျက်ကွက်ပါက လုပ်ဆောင်ပြီးသား rename များကို ပြန်ပြောင်းသည်။
- **Rollback လုပ်ပါ။** `run` သည် promote လုပ်ထားသော slot ကို ထပ်မံ validate လုပ်ပြီး
  ထိုစစ်ဆေးမှု မအောင်မြင်ပါက `current` နှင့် `previous` ကို မူလအတိုင်း ပြန်လဲသည်။ ပထမ validation မအောင်မြင်သော candidate ကို မည်သည့်အခါမျှ promote မလုပ်ပါ။

အရာအားလုံးကို gitignore လုပ်ထားသော `_artifacts/candidate/` အောက်တွင် ရေးသားသည်။ ရှိပြီးသား OmniRoute
installation နှင့် ၎င်း၏ data directory ကို မည်သည့်အခါမျှ မထိပါ။ Promote လုပ်ထားသော CLI သည်
`_artifacts/candidate/current/prefix/bin/omniroute` ဖြစ်သည်။ ၎င်းကို အသုံးပြုသောအခါ သင့်ကိုယ်ပိုင် `DATA_DIR` ဖြင့်
စတင်ပါ။ Exit code များ- အောင်မြင်ပါက `0`၊ validation သို့မဟုတ် promotion မအောင်မြင်ပါက `1`၊ အသုံးပြုပုံ error သို့မဟုတ် build မရှိပါက `2`။

## စက်တွင်း loop နှင့် CI နှိုင်းယှဉ်ချက်

| ပြင်ဆင်မှုတစ်ခုစီအတွက် စက်တွင်း၌ လုပ်ဆောင်ရန်                                                   | CI က ကျယ်ပြန့်သော အချက်ပြမှုကို ပံ့ပိုးပေးသည်                                         |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| အထက်ပါ တိုက်ရိုက်အပြုအမူ စမ်းသပ်မှုများနှင့် အမျိုးအစား gate များ                               | အပိုင်းခွဲထားသော unit suite အပြည့်အစုံနှင့် serial စမ်းသပ်မှုများ                     |
| `npm run lint`                                                                                  | Vitest suite များနှင့် coverage/quality ratchet များ                                  |
| သက်ရောက်မှုရှိသော contract က လိုအပ်မှသာ typecheck သို့မဟုတ် build ပြုလုပ်ခြင်း                  | Production build၊ လုံခြုံရေး၊ docs၊ dependency နှင့် PR-policy gate များ              |
| automation ဖြင့် အပြုအမူကို သက်သေမပြနိုင်မှသာ ကိုယ်တိုင်အပြန်အလှန်စမ်းသပ်ခြင်း/live စစ်ဆေးခြင်း | workflow ဖြင့် သတ်မှတ်ထားသော job အချင်းချင်း integration နှင့် platform စစ်ဆေးမှုများ |

အာရုံစိုက်ထားသော loop အောင်မြင်ခြင်းသည် ပြောင်းလဲထားသော contract နှင့်ပတ်သက်သည့် အထောက်အထားဖြစ်ပြီး၊ မသက်ဆိုင်သော CI စစ်ဆေးမှုများ
အောင်မြင်မည်ဟု သက်သေပြခြင်းမဟုတ်ပါ။ အပြန်အလှန်အားဖြင့် စက်တွင်းပြင်ဆင်မှုတိုင်းကို repository matrix အပြည့်အစုံ ပြီးစီးသည်အထိ မစောင့်ခိုင်းပါနှင့်။

## ပြန်လည်ညှိနှိုင်းရေး စစ်ဆေးစာရင်း

သုံးသပ်ပေးရန် မတောင်းဆိုမီ-

- PR base သည် လက်ရှိအသုံးပြုနေသော အမြင့်ဆုံး `release/v*` branch ဖြစ်နေဆဲဖြစ်ကြောင်း အတည်ပြုပါ။
- ထို base ကို fetch လုပ်ပြီး သင် branch ခွဲခဲ့ပြီးနောက် ထည့်သွင်းခဲ့သော commit များကို သုံးသပ်ပါ။
- မတော်တဆ သို့မဟုတ် အလိုအလျောက်ထုတ်လုပ်ထားသော မလိုလားအပ်သည့် ပြောင်းလဲမှုများရှိမရှိ စစ်ဆေးရန် `git diff <active-base>...HEAD` ကို သုံးသပ်ပါ။
- source ကို အပ်ဒိတ်လုပ်ပြီး output ကို ပြန်လည်ထုတ်လုပ်ခြင်းဖြင့် catalog နှင့် အလိုအလျောက်ထုတ်လုပ်ထားသော document conflict များကို ဖြေရှင်းပါ။
- ပြန်လည်ညှိနှိုင်းပြီးနောက် PR ဖော်ပြချက်တွင် စာရင်းပြုထားသော အာရုံစိုက်သည့် test/gate တိုင်းကို ပြန်လည်လုပ်ဆောင်ပါ။
- ပြောင်းရွှေ့ထားသော base နှင့် ကိုက်ညီစေရန်သာ assertion များကို မည်သည့်အခါမျှ အားမလျှော့ပါနှင့်၊ သို့မဟုတ် လိုအပ်သော test များကို မဖယ်ရှားပါနှင့်။

release-freeze နှင့် retargeting စည်းမျဉ်းများအတွက်
[Branching & Release Model](BRANCHING_MODEL.md) ကို အသုံးပြုပါ။ CI စာရင်းအပြည့်အစုံအတွက်
[Quality Gates Reference](../architecture/QUALITY_GATES.md) ကို အသုံးပြုပါ။
