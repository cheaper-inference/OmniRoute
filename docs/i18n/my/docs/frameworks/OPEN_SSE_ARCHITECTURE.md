**ရင်းမြစ်:** `open-sse/` (workspace package၊ test မဟုတ်သော `.ts` ဖိုင် ~1,440)

## အဘယ်ကြောင့် သီးခြား Workspace Package တစ်ခုထားရသနည်း?

`open-sse/` သည် အကြောင်းရင်းများစွာကြောင့် OmniRoute monorepo အတွင်းရှိ **သီးခြားရပ်တည်နိုင်သော workspace** တစ်ခုဖြစ်သည်-

1. **ပြန်လည်အသုံးပြုနိုင်မှု** — `open-sse` ကို npm ပေါ်တွင် `@omniroute/open-sse` အဖြစ် ဖြန့်ချိထားသောကြောင့် အခြား project များက သီးခြားအသုံးပြုနိုင်သည်
2. **ရှင်းလင်းသော နယ်နိမိတ်များ** — streaming engine ကို OmniRoute သီးသန့် UI/DB layer နှင့် သီးခြားခွဲထားသည်
3. **စွမ်းဆောင်ရည်** — engine တွင် Next.js dependency များမရှိသောကြောင့် CLI/serverless ပတ်ဝန်းကျင်များတွင် cold start ပိုမိုမြန်ဆန်စေသည်
4. **ဗားရှင်းစီမံခန့်ခွဲမှု** — `open-sse` ကို ၎င်း၏ကိုယ်ပိုင် အချိန်ဇယားအတိုင်း release လုပ်နိုင်သည်

```json
// package.json
"workspaces": ["open-sse"]
```

## Request Pipeline

LLM တောင်းဆိုမှုတိုင်းသည် **အဆင့် ၅ ဆင့်ပါ pipeline** မှတစ်ဆင့် စီးဆင်းသည်-

```
                              ┌──────────────┐
   HTTP တောင်းဆိုမှု           │  1. ROUTE    │   combo ဖြေရှင်းခြင်း၊ model ရွေးချယ်ခြင်း
   (Next.js route)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRANSLATE│   format ပြောင်းလဲခြင်း (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXECUTE  │   provider executor၊ HTTP၊ ပြန်လည်ကြိုးစားမှု၊ breaker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE ပြောင်းလဲခြင်း၊ backpressure
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. RECORD   │   အသုံးပြုမှုခြေရာခံခြင်း၊ call log၊ error အမျိုးအစားခွဲခြင်း
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP တုံ့ပြန်မှု (SSE သို့မဟုတ် JSON)
```

### အဆင့် 1: Route (services/combo.ts)

**Entry point**: `services/combo.ts` ရှိ `handleComboChat()`

တောင်းဆိုမှုကို တိကျသော `(provider, model, account, credentials)` tuple တစ်ခုအဖြစ် ဖြေရှင်းသတ်မှတ်သည်-

- ID ဖြင့် combo ကို ရှာဖွေပါ (သို့မဟုတ် `auto/*` model များအတွက် virtual combo တစ်ခု တည်ဆောက်ပါ)
- Routing strategy ကို အသုံးချပါ (priority၊ weighted၊ round-robin စသည်)
- အခြေအနေမကောင်းသော provider များကို ဖယ်ထုတ်ပါ (circuit breaker)
- နောက်ထပ် အသုံးပြုနိုင်သော target ကို ရွေးချယ်ပါ

`auto/*` model များအတွက် ဤအဆင့်သည် အောက်ပါတို့ကိုလည်း လုပ်ဆောင်သည်-

- **အချက် ၁၆ ချက် scoring** algorithm (`services/autoCombo/`) ကို လုပ်ဆောင်သည်
- ကျန်းမာရေးအခြေအနေ၊ ကုန်ကျစရိတ်၊ latency စသည်တို့အပေါ် အခြေခံ၍ `provider+model` အတွဲတစ်ခုကို ရွေးချယ်သည်

### အဆင့် 2: Translate (translator/)

မူရင်း format (ဥပမာ OpenAI) သည် target format (ဥပမာ Claude) နှင့် ကွဲပြားပါက တောင်းဆိုမှုကို **ဘာသာပြန်ပြောင်းလဲသည်**-

- System prompt → system message
- Tool definition များ → provider သီးသန့် tool format
- Reasoning/thinking parameter များ → provider သီးသန့် တူညီသောအရာများ
- Message role စံသတ်မှတ်ခြင်း (OpenAI မဟုတ်သော provider များအတွက် `developer` → `system`)

`translator/index.ts` သည် အောက်ပါတို့ကို ဖော်ထုတ်ပေးသည်-

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### အဆင့် 3: Execute (executors/)

**Entry point**: `getExecutor(providerId).execute(request, options)`

Provider အားလုံးသည် `getExecutor()` factory fallback မှတစ်ဆင့် `DefaultExecutor` (`executors/default.ts`) ကို အသုံးပြုသည်။ Executor သည်-

- Upstream URL ကို တည်ဆောက်သည် (`buildUrl()`)
- Provider သီးသန့် header များကို ထည့်သွင်းသည် (`buildHeaders()`)
- Request body ကို ပြောင်းလဲသည် (`transformRequest()`)
- Retry + exponential backoff ဖြင့် HTTP တောင်းဆိုမှုကို ပေးပို့သည်
- လိုအပ်ပါက auth refresh ကို ကိုင်တွယ်သည် (OAuth provider များ)

Executor အားလုံးသည် အောက်ပါတို့ကို ပံ့ပိုးပေးသည့် `BaseExecutor` (`executors/base.ts`၊ LOC 1170) ကို ဆက်ခံထားသည်-

- ဘုံ retry logic
- Proxy ပေါင်းစည်းမှု
- Circuit breaker ပေါင်းစည်းမှု
- အသုံးပြုမှုမှတ်တမ်းတင်သည့် hook များ

### အဆင့် 4: Stream (utils/stream.ts)

Streaming response များအတွက် executor သည် **ReadableStream** တစ်ခုကို ပြန်ပေးသည်။ Handler သည်-

- SSE transform (`createSSETransformStreamWithLogger`) မှတစ်ဆင့် pipe လုပ်သည်
- ပြတ်တောက်နေသော connection များကို စစ်ဆေးရန် heartbeat ping များကို အသုံးပြုသည်
- Client disconnect ကို အဆင်ပြေပြေ ကိုင်တွယ်သည် (`pipeWithDisconnect`)
- Streaming မဟုတ်သော client များအတွက် SSE → JSON ပြောင်းလဲသည်

Streaming မဟုတ်သော response များအတွက် executor သည် parse လုပ်ပြီးသား JSON object တစ်ခုကို ပြန်ပေးပြီး ၎င်းကို ပြောင်းလဲမှုမရှိဘဲ ဆက်လက်ပေးပို့သည်။

### အဆင့် 5: Record (services/usage.ts)

တုံ့ပြန်မှု (အောင်မြင်သည်ဖြစ်စေ၊ မအောင်မြင်သည်ဖြစ်စေ) ပြီးနောက် အသုံးပြုမှုကို မှတ်တမ်းတင်သည်-

- တုံ့ပြန်မှုမှ `prompt_tokens`, `completion_tokens`, `cached_tokens`
- ဈေးနှုန်းဒေတာမှ တွက်ချက်ထားသော `cost_usd`
- မအောင်မြင်ပါက `latency_ms`, `status`, `error_class`
- `usage_history` ဇယားတွင် အမြဲတမ်းသိမ်းဆည်းထားသည်

ခေါ်ဆိုမှုမှတ်တမ်း အထောက်အထားများကို (ဖွင့်ထားပါက) `${DATA_DIR}/call_logs/` တွင် ရေးသားသိမ်းဆည်းသည်။

## သော့ဖိုင်များကို နက်ရှိုင်းစွာ ထိုးဆင်းပါ။

### chatCore.ts (၅၉၇၇ လိုင်း)

ဟိ** ပင်မတောင်းဆိုမှုကိုင်တွယ်သူ** . ၎င်း၏အရွယ်အစားရှိသော်လည်း၊ ၎င်းတွင်ရှင်းလင်းသောဖွဲ့စည်းပုံရှိသည်။

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

- `OpenAI → Responses API`- `input` array၊ `previous_response_id` state

### ကိုင်တွယ်ပေးထားသော အထူးဖြစ်ရပ်များ

- `developer` role → OpenAI မဟုတ်သော စနစ်များအတွက် `system`
- `system` role → GLM/ERNIE အတွက် ပထမဆုံး user message ထဲသို့ ပေါင်းထည့်ခြင်း
- `json_schema` → Gemini ၏ `responseMimeType` + `responseSchema`
- `tools` → provider အလိုက် သီးခြား tool ဖော်မတ်
- Thinking parameter များ (o1၊ Claude) → provider အလိုက် သက်ဆိုင်ရာ parameter များ

## MCP ဆာဗာ

`open-sse/mcp-server/` သည် **Model Context Protocol** ဆာဗာကို အကောင်အထည်ဖော်ထားသည်-

- **tool 110 ခု** (provider စီမံခန့်ခွဲမှု၊ combo များ၊ memory၊ cache၊ compression၊ proxy၊ skill များ၊ gamification၊ plugin များ၊ Notion၊ Obsidian၊ local corpus)
- **transport 3 မျိုး**- stdio၊ SSE၊ Streamable HTTP
- အသေးစိတ် authorization အတွက် **scope 33 ခု**

### Tool စာရင်းသွင်းခြင်း

Tool များကို `open-sse/mcp-server/tools/` ထဲတွင် သီးခြား file များအဖြစ် စာရင်းသွင်းထားပြီး၊ တစ်ခုစီမှ name၊ schema၊ handler နှင့် scope တို့ကို export လုပ်သည်-

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transport များ

```ts
// stdio (CLI အသုံးပြုမှု)
startMcpStdio(server);

// SSE (HTTP အခြေပြု streaming)
startMcpSse(server, port);

// Streamable HTTP (ခေတ်မီ MCP)
startMcpStreamable(server, port);
```

### Authorization

Tool ခေါ်ယူမှုတိုင်းသည် scope စစ်ဆေးမှုများ (`open-sse/mcp-server/auth/`) ကို ဖြတ်သန်းသည်-

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformer များ

`open-sse/transformer/` သည် **Chat Completions** နှင့် **Responses API** ဖော်မတ်များအကြား ပြောင်းလဲပေးသည်။

### သီးခြား Transformer တစ်ခု အဘယ်ကြောင့် လိုအပ်သနည်း။

Responses API သည် **stateful conversation များ** (`previous_response_id`) ပါဝင်သည့် OpenAI ၏ ဖော်မတ်အသစ်ဖြစ်သည်။ Client တစ်ခုက Responses request တစ်ခု ပေးပို့သည့်အခါ OmniRoute သည်-

1. Responses → Chat Completions အဖြစ် အတွင်းပိုင်းတွင် ပြောင်းလဲသည်
2. Provider ထံသို့ ပေးပို့သည် (Chat Completions ကို ပံ့ပိုးသည့် မည်သည့် provider မဆို)
3. Response ကို Responses ဖော်မတ်သို့ ပြန်လည်ပြောင်းလဲသည်
4. ပြောင်းလဲပြီးသော response ကို client ထံသို့ stream လုပ်သည်

Transformer (`transformer/responsesTransformer.ts`) က အောက်ပါတို့ကို ပံ့ပိုးပေးသည်-

```ts
createResponsesApiTransformStream(): TransformStream
```

၎င်းက အောက်ပါတို့ကို ကိုင်တွယ်ပေးသည်-

- `response.output_item.added` event များ
- `response.output_text.delta` event များ
- `response.completed` event
- Tool call mapping (`function_call` ↔ `tool_calls`)

## စွမ်းဆောင်ရည် ကန့်သတ်ချက်များ

Routing engine တွင် တင်းကျပ်သော စွမ်းဆောင်ရည် ဘတ်ဂျက်များ ရှိသည်-

| လုပ်ဆောင်ချက်                                | ရည်မှန်းချက် | တိုင်းတာမှု                             |
| -------------------------------------------- | ------------ | --------------------------------------- |
| Combo ဖြေရှင်းမှု                            | <10ms        | Target 50 ခုအတွက်                       |
| Rate limit စစ်ဆေးမှု                         | <1ms         | In-memory token bucket                  |
| Model family fallback                        | <5ms         | Cache လုပ်ထားသော family definition များ |
| Request routing dispatch                     | <2ms         | Hot path                                |
| **Routing hot path တွင် blocking I/O မရှိရ** | —            | အားလုံး async ဖြစ်သည်                   |

---

## ရှောင်ကြဉ်ရမည့် ပုံစံများ

❌ **`combo.ts` အတွင်းရှိ Synchronous DB call များ** — ကြိုတင်တွက်ချက်ပြီး cache လုပ်ပါ
❌ **Handler များအတွင်းရှိ retry logic** — resilience service မှ `retry()` ကို အသုံးပြုပါ
❌ **Provider config ကို တိုက်ရိုက်ရယူခြင်း** — `providerRegistry` getter များကို အသုံးပြုပါ
❌ **Hardcode လုပ်ထားသော fallback chain များ** — `modelFamilyFallback.ts` တွင် သတ်မှတ်ပါ
❌ **တစ်ပြိုင်တည်း request များကြားရှိ state ပြောင်းလဲမှုများ** — request တစ်ခုချင်းစီအလိုက် သီးခြားဖြစ်သော context ကိုသာ အသုံးပြုပါ

## Component အသစ်တစ်ခု ထည့်သွင်းခြင်း

### Service အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. သီးသန့်တာဝန်တစ်ခုအတွက် `open-sse/services/[serviceName].ts` ကို ဖန်တီးပါ
2. အဓိက handler function နှင့် လိုအပ်သည့် constant များကို export လုပ်ပါ
3. `tests/unit/services/[serviceName].test.mjs` တွင် unit test များ ထည့်ပါ
4. Routing နှင့် သက်ဆိုင်ပါက `handlers/chatCore.ts` ရှိ request pipeline ထဲသို့ ပေါင်းစပ်ပါ
5. Service က target ရွေးချယ်မှုအပေါ် သက်ရောက်ပါက `combo.ts` ရှိ routing logic ကို အပ်ဒိတ်လုပ်ပါ
6. ဤဖိုင်တွင် မှတ်တမ်းတင်ပါ

### Executor အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `BaseExecutor` ကို တိုးချဲ့ထားသော `open-sse/executors/[provider].ts` ကို ဖန်တီးပါ
2. `config/providerRegistry.ts` တွင် register လုပ်ပါ
3. `executors/index.ts` factory ထဲသို့ ထည့်ပါ
4. Executor အတွက် unit test များ ထည့်ပါ
5. `docs/architecture/ARCHITECTURE.md` တွင် မှတ်တမ်းတင်ပါ

### MCP Tool အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `open-sse/mcp-server/tools/[category]Tools.ts` ကို ဖန်တီးပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ
2. Input များအတွက် Zod schema ကို သတ်မှတ်ပါ
3. Tool ကို `mcp-server/index.ts` တွင် register လုပ်ပါ
4. `mcp-server/auth/` ရှိ scope matrix ထဲသို့ ထည့်ပါ
5. Unit test များ ထည့်ပါ
