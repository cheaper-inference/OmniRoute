- OmniRoute ၎င်းတို့အား `DATA_DIR/services/{name}/` အောက်တွင် ထည့်သွင်းသည် ( OmniRoute၏ ကိုယ်ပိုင် `package.json` မှ သီးခြားခွဲထားသည်)
- OmniRoute သည် ၎င်းတို့ကို ကလေးဖြစ်စဉ်များအဖြစ် မွေးမြူပြီး စောင့်ကြည့်သည်။
- OmniRoute ကလေး၏ပတ်ဝန်းကျင်သို့ ပေါ်ပင် API သော့ကို ထိုးသွင်းပြီး စက်ရပ်ခြင်းမရှိဘဲ ၎င်းကို လှည့်ပေးသည် (အသုံးပြုနိုင်သည့်နေရာတွင်)
- စီမံခန့်ခွဲမှုလမ်းကြောင်းအားလုံး (`/api/services/*`) များဖြစ်သည်။**LOCAL_ONLY** — loopback မှသာလျှင် ဝင်ရောက်နိုင်သည် ( hard rule #17 )

## 2. ဗိသုကာ — 4 အလွှာ

```
┌────────────────────────────────────────────────────────────────────┐
│  Layer 1 — UI                                                      │
│  /dashboard/providers/services  (tabs: CLIProxyAPI | 9Router | Mux)│
│  Logs live (SSE), Start/Stop/Restart/Update, Settings, Install     │
│                                                                    │
│  src/app/(dashboard)/dashboard/providers/services/                 │
│    ├── page.tsx               Shell + tab routing by ?tab=         │
│    ├── tabs/                  CliproxyServiceTab, NinerouterServiceTab,│
│    │                          MuxServiceTab                        │
│    └── components/            ServiceStatusCard, ServiceLifecycleButtons,│
│                               ServiceLogsPanel, ApiKeyCard, ...    │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ HTTP (Next.js fetch)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 2 — API (LOCAL_ONLY — loopback only)                        │
│                                                                    │
│  /api/services/9router/{install|start|stop|restart|update|         │
│                          rotate-key|status|auto-start|logs}        │
│  /api/services/cliproxy/{install|start|stop|restart|update|        │
│                           status|auto-start|logs}                  │
│  /api/services/mux/{install|start|stop|restart|update|             │
│                      status|auto-start|logs}                       │
│  /dashboard/providers/services/9router/embed/[...path]             │
│    (reverse HTTP + WebSocket proxy → 9Router upstream)             │
│                                                                    │
│  Gate: LOCAL_ONLY_API_PREFIXES includes "/api/services/" and       │
│        "/dashboard/providers/services/*/embed/"                    │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ in-process calls
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 3 — ServiceSupervisor (src/lib/services/)                   │
│                                                                    │
│  ServiceSupervisor.ts   Generic supervisor (child_process.spawn)   │
│    ├── install:    execFile('npm', ['install', pkg, '--prefix'])    │
│    ├── start:      spawn(node, [entrypoint], {env, cwd})           │
│    ├── api_key:    crypto.randomBytes(32) → env NINEROUTER_API_KEY  │
│    ├── port:       20130 for 9Router (configurable)                │
│    ├── logs:       stdio ring buffer 5 MB → SSE events             │
│    ├── health:     HTTP GET /health every 2–5 s, lazy recovery     │
│    └── lifecycle:  SIGTERM 15 s → SIGKILL                          │
│                                                                    │
│  registry.ts        getSupervisor(name) / registerSupervisor()     │
│  bootstrap.ts       Bootstraps all SERVICES[] at process start     │
│  apiKey.ts          getOrCreateApiKey(), generateServiceApiKey()   │
│  modelSync.ts       Periodic GET /v1/models → service_models table │
│  ringBuffer.ts      Circular log buffer (5 MB per service)         │
│  healthCheck.ts     Polling HTTP health probe                      │
│  installers/        ninerouter.ts, cliproxy.ts, mux.ts, openwa.ts  │
│                      (installer adapters)                          │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ OpenAI-compatible HTTP (loopback)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 4 — Provider / Routing                                      │
│                                                                    │
│  open-sse/executors/ninerouter.ts                                  │
│    Re-looks up port and API key per-request (no caching).          │
│    Strips "9router/" prefix from model id before proxying.         │
│    Returns 503 service_not_running if supervisor not in "running". │
```

## 3. Lifecycle state machine

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
             ကျန်းမာရေးစစ်ဆေးမှု အောင်မြင် │         ပျက်ကျ / SIGTERM    │
                               ┌────▼─────┐  (5s အတွင်း ထွက်)   │
                               │ running  │──── ပျက်ကျ ─────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

State များကို `version_manager` DB table ၏ (`status` column) တွင် သိမ်းဆည်းပြီး
`ServiceSupervisor` ၏ in-memory state ထဲတွင်လည်း တစ်ပြိုင်နက် ထင်ဟပ်ထားသည်။ လုပ်ဆောင်နေသော
process တစ်ခုအတွက် in-memory state ကို အတည်ပြုရင်းမြစ်အဖြစ် သတ်မှတ်ထားပြီး၊ DB state ကို boot
လုပ်ချိန်တွင် ရေရှည်တည်တံ့သော အရန်အဖြစ် အသုံးပြုသည်။

### State ကူးပြောင်းမှုများ

| မှ                 | ဖြစ်ရပ်                                   | သို့                            |
| ------------------ | ----------------------------------------- | ------------------------------- |
| `not_installed`    | `install()` အောင်မြင်သည်                  | `stopped`                       |
| `stopped`          | `start()` ကို ခေါ်သည်                     | `starting`                      |
| `starting`         | ကျန်းမာရေးစစ်ဆေးမှုက 200 ပြန်ပေးသည်       | `running`                       |
| `starting`         | ကျန်းမာမှုမရှိမီ process ထွက်သွားသည်      | `error`                         |
| `running`          | `stop()` ကို ခေါ်သည်                      | `stopping` → `stopped`          |
| `running`          | process မမျှော်လင့်ဘဲ ထွက်သွားသည် (< 5 s) | `error` (လျင်မြန်စွာ ပျက်ကျမှု) |
| `running`          | process မမျှော်လင့်ဘဲ ထွက်သွားသည် (> 5 s) | `error`                         |
| `error`            | `start()` ကို ခေါ်သည်                     | `starting`                      |
| မည်သည့် state မဆို | `stopping` ဖြစ်နေစဉ် `stop()` လုပ်သည်     | ဘာမျှမလုပ်                      |

### Operation lock

`ServiceSupervisor` သည် async operation lock (`withLock()`) မှတစ်ဆင့် lifecycle
operation များကို အစဉ်လိုက်လုပ်ဆောင်စေသည်။ Supervisor တစ်ခုတည်းပေါ်သို့ တစ်ပြိုင်နက်
`start()` ခေါ်ဆိုမှုများ ပြုလုပ်ပါက spawn တစ်ကြိမ်တည်းသာ အတိအကျ ဖြစ်ပေါ်မည်ဖြစ်ပြီး၊
ဒုတိယ caller သည် စောင့်ဆိုင်းကာ ရှိပြီးသား status ကို ပြန်ပေးမည်။ ဥပမာ auto-start နှင့်
UI button တစ်ခုတို့ တစ်ပြိုင်နက် အလုပ်လုပ်သည့်အခါ ဖြစ်ပေါ်နိုင်သော race condition များကို
ဤနည်းဖြင့် တားဆီးသည်။

#### `POST /api/services/9router/install`

npm မှ 9Router ကို install လုပ်ပါ။ ၎င်း၏ကိုယ်ပိုင် `package.json` နှင့် `node_modules/` ဖြင့် `DATA_DIR/services/9router/` ဖန်တီးပါ။ OmniRoute၏ကိုယ်ပိုင် deps နှင့်မဆန့်ကျင်ပါ။

**ခန္ဓာကိုယ်ကို တောင်းဆိုပါ။** (အားလုံးရွေးချယ်နိုင်သည်):

```json
{ "version": "latest" }
```

| လယ်ကွင်း  | ရိုက်ပါ။ | ပုံသေ      | ဖော်ပြချက်                                     |

**တုံ့ပြန်မှုများ-**

| အဆင့်အတန်း | ဖော်ပြချက်                                                                |
| ---------- | ------------------------------------------------------------------------- |
| `200`      | `{ ok: true, installedVersion: "x.y.z", path: "..." }`                    |
| `400`      | မမှန်ကန်သော တောင်းဆိုချက်ကိုယ်ထည် (Zod အတည်ပြုခြင်း မအောင်မြင်ပါ)         |
| `409`      | ထည့်သွင်းပြီးဖြစ်သည် (လော့ခ်ချထားသည်)                                     |
| `500`      | npm ထည့်သွင်းမှု မအောင်မြင်ပါက — အဆင်ပြေသော အမှားအတွက် `message` ကြည့်ပါ။ |

**မှတ်စုများ-** `execFile('npm', [...])` — no shell ၊ interpolation မရှိ ( hard rule #13 ) ကိုအသုံးပြုသည်။ EACCES အမှားများကို ဖော်ရွေသော မက်ဆေ့ချ်များအဖြစ် ပေါ်နေပါသည်။

open-wa (`@open-wa/wa-automate`) သည် WhatsApp ဝဘ်ကို အလိုအလျောက်လုပ်ဆောင်ရန် ဦးခေါင်းမပါသော Chromium ဥပမာ (Puppeteer မှတဆင့်) မောင်းနှင်သည်။ ၎င်းသည် Mux ကဲ့သို့ တူညီသော အဆုံးမှတ်ပုံသဏ္ဍာန်ကို အသုံးပြုသည် ( `rotate-key` လမ်းကြောင်း မရှိသေးပါ)။ ၎င်းသည် ဘဝစက်ဝန်း-စီမံခန့်ခွဲသည့် — သာလျှင် လမ်းကြောင်းပစ်မှတ်မဟုတ်ပါ၊ အလွှာ 4 executor/provider ဝင်ခွင့်မရှိပါ။

| `POST`   | `/api/services/openwa/install`    | npm (`@open-wa/wa-automate`) မှ open-wa ကိုထည့်သွင်းပါ။                  |
| `POST`   | `/api/services/openwa/start`      | ဆိပ်ကမ်း 8323 (မူလ) တွင် open-wa စတင်ပါ                                  |
| `POST`   | `/api/services/openwa/stop`       | Open-wa ရပ်ပါ။                                                           |
| `POST`   | `/api/services/openwa/restart`    | open-wa ကို ပြန်လည်စတင်ပါ။                                               |
| `POST`   | `/api/services/openwa/update`     | ဗားရှင်းအသစ်သို့ အပ်ဒိတ်လုပ်ပါ။                                          |

**API** `WA_KEY` — open-wa ၏ generic `WA_*` -prefixed env သည် ၎င်းကို `--key`/`-k` CLI ရွေးချယ်မှု (`dist/cli/setup.js::envArgs()` တွင် ထည့်သွင်းထားသည့် 4.76.0 ပက်ကေ့ချ်နှင့် စိစစ်ထားသော) တွင် ထပ်ရေးထားသည့်အတိုင်း ထည့်သွင်းထားသည်။ `generateServiceApiKey()` မှထုတ်ပေးသောအခါ ရှေ့ဆက် `ow_` ။ open-wa သည် `key`/`api_key` HTTP ခေါင်းစီးမှ သော့ကို ပြန်ဖတ်သည် ( `Authorization: Bearer` မဟုတ်ပါ။ `/api-docs*` သည် ချက်လက်မှတ် (`setupAuthenticationLayer` in `dist/cli/server.js`) မှ ပြတ်သားစွာ ကင်းလွတ်နေသောကြောင့် ကျန်းမာရေးစုံစမ်းစစ်ဆေးခြင်းတွင် auth header မလိုအပ်ပါ။

**တွဲခြင်း-** open-wa သည် တရားဝင်မဟုတ်သည့်အပြင် WhatsApp — နှင့် ဆက်စပ်မှုမရှိသော ချိတ်ဆက်ထားသောနံပါတ်သည် WhatsApp၏ကိုယ်ပိုင်အလိုအလျောက်စနစ်ရှာဖွေခြင်းမှ တားမြစ်အန္တရာယ်ကိုသယ်ဆောင်သည်။ ပထမစစချင်းတွင်၊ တွဲချိတ်ထားသည့် QR ကုဒ်ကို stdout သို့ ရိုက်နှိပ်ပြီး လက်ရှိ Logs panel/SSE stream — မှတဆင့် ဤပေါင်းစပ်မှုတွင် သီးခြား QR-image အဆုံးမှတ် မရှိသေးပါ။

| `POST`   | `/api/services/llmlingua/auto-restart-adopted` | လက်ခံထားသော (နဂိုရှိပြီးသား) ဥပမာတစ်ခု၏ အလိုအလျောက်ပြန်လည်စတင်ခြင်းကို ပြောင်းပါ။ |
| `GET`    | `/api/services/llmlingua/logs`                 | SSE မှတ်တမ်းအမြီး (မျှဝေထားသော `[name]/logs` ရွေ့လျားလမ်းကြောင်းမှတဆင့်)          |

**ဆိုက်ကား စာချုပ်-** ဆာဗာ script သည် `GET /health` (ချက်ချင်း — မော်ဒယ်ပေါ်တွင် မစောင့်ပါ) နှင့် `POST /compress` (`{ text, rate }` → `{ text, compressed, ratio }`) ကို ဖော်ထုတ်သည်။ မော်ဒယ်သည် ပထမ `/compress` ခေါ်ဆိုမှုတွင် ပျင်းရိစွာ ပွင့်သည်။

**Compression ဝါယာကြိုး-** `open-sse/services/compression/engines/llmlingua/index.ts`'s `httpSidecarBackend` `LLMLINGUA_BASE_URL` (မူလ `http://127.0.0.1:20135`) ကိုခေါ်ဆိုပြီး ၎င်းသည် ထည့်သွင်းမှုထက် တင်းကြပ်စွာ တိုတောင်းနေချိန်တွင် ဘေးတွဲကား၏ တုံ့ပြန်မှုကို လက်ခံပါသည်။ မည်သည့် ချို့ယွင်းချက်မဆို (မလည်ပတ်ခြင်း၊ အချိန်ကုန်ခြင်း၊ တုံ့ပြန်မှုမရှိခြင်း) သည် in-process worker-thread backend (`./worker.ts`) သို့ ပြန်ရောက်သွားပါသည်။

### 4.8 sing-box အဆုံးမှတ်များ (လမ်းကြောင်း 8 ခု)

sing-box တွင် Mux — no `rotate-key` လမ်းကြောင်း၊ API သော့ထိုးခြင်း မရှိပါ (`needsApiKey: false` in `bootstrap.ts`) ကဲ့သို့ အဆုံးမှတ်ပုံသဏ္ဍာန်ရှိသည်။ ၎င်းသည် lifecycle-managed only ဖြစ်သည်- routing/LLM ပံ့ပိုးပေးသူ ဘယ်တော့မှမရှိပါ။ `install()` ပင်ထိုးထားသော ဗားရှင်း (`SINGBOX_PINNED_VERSION` in `src/lib/services/installers/singbox.ts`) အတွက် တရားဝင် GitHub ထုတ်ဝေမှု binary (`SagerNet/sing-box`) ကို ဒေါင်းလုဒ်လုပ်ပြီး ၎င်းကို တူညီသောဖိုင်တွင် ဖုတ်ထားသော checksum နှင့် ၎င်း၏ SHA256 disk — သို့မရေးထားမီ အခြားတောင်းဆိုထားသည့်ဗားရှင်းကို ငြင်းပယ်ထားသည်။

### 4.9 ပြောင်းပြန် ပရောက်စီ (9Router ဒက်ရှ်ဘုတ် ထည့်သွင်းထားသည်)

ဒက်ရှ်ဘုတ်သည် 9Router ဝဘ် UI အတွင်းပိုင်းပြောင်းပြန်ပရောက်စီမှတစ်ဆင့် iframe အတွင်းတွင် ထည့်သွင်းထားသည်-

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

ဤပရောက်စီ-

- တောင်းဆိုချက်ကို `http://127.0.0.1:{port}/{path}` သို့ ထပ်ဆင့်ပို့ပါ (ပြန်လှည့်ရန်သာ)
- ဝင်လာသော `cookie` နှင့် `authorization` ခေါင်းစီးများကို ဖယ်ရှားသည် ( OmniRoute စက်ရှင်၏ ပေါက်ကြားခြင်းမရှိပါ)
- 9Router authentication အတွက် `Authorization: Bearer {apiKey}` ထိုးထည့်သည်။
- တုံ့ပြန်မှုမှ `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` အစင်းများ
- `<base href>` ထိုးသွင်းရန်နှင့် ပကတိလမ်းကြောင်းများကို ပုံမှန်ဖြစ်စေရန် HTML တုံ့ပြန်မှုများကို ပြန်လည်ရေးသားသည် (`/foo` → `/dashboard/.../embed/foo`)

ထည့်သွင်းထားသော ဒက်ရှ်ဘုတ်အတွက်WebSocket အဆင့်မြှင့်တင်မှုများကို သီးခြားဆိပ်ကမ်းတစ်ခုပေါ်ရှိ တွဲဖက်ဆာဗာတစ်ခုမှ ကိုင်တွယ်ဆောင်ရွက်သည် ( `src/lib/services/embedWsProxy.ts` ကိုကြည့်ပါ)။

**လုံခြုံရေး-** မြှုပ်သွင်းထားသော ပရောက်စီလမ်းကြောင်းများကို `LOCAL_ONLY_API_PREFIXES` အောက်တွင် ခွဲခြားထားပြီး loopback မှသာလျှင် ရောက်ရှိနိုင်သည်။ Cloudflare/Ngrok ဥမင်မှတဆင့် JWT ရယူသော တိုက်ခိုက်သူသည် မြှုပ်သွင်းထားသော ဝန်ဆောင်မှုများသို့ proxy မရနိုင်ပါ။

## 5. လုံခြုံရေး

### LOCAL_ONLY အတည်ပြုအသုံးချမှု (မဖြစ်မနေလိုက်နာရမည့် စည်းမျဉ်း #17)

`/api/services/` နှင့် `/dashboard/providers/services/*/embed/` အောက်ရှိ route အားလုံးကို
`src/server/authz/routeGuard.ts` တွင် LOCAL_ONLY အဖြစ် သတ်မှတ်ထားသည်။ Loopback စစ်ဆေးမှုကို
မည်သည့် auth branch မတိုင်မီမဆို ခြွင်းချက်မရှိ လုပ်ဆောင်သည်-

```
request ဝင်ရောက်လာသည်
  → isLocalOnlyPath(path)?
      → loopback မဟုတ်ပါက → 403 LOCAL_ONLY (အမြဲတမ်း၊ auth စစ်ဆေးမှုမတိုင်မီ)
      → loopback ဖြစ်ပါက    → ပုံမှန် auth သို့ ဆက်လက်လုပ်ဆောင်သည်
```

၎င်းက ပေါက်ကြားသွားသော JWT တစ်ခု (ဥပမာ tunnel မှတစ်ဆင့်) ကြောင့် `npm install` သို့မဟုတ်
process စတင်ခြင်းတို့ ဖြစ်ပေါ်လာခြင်းကို ကာကွယ်ပေးသည်။ Tier matrix အပြည့်အစုံအတွက်
`docs/security/ROUTE_GUARD_TIERS.md` ကို ကြည့်ပါ။

### API key ထည့်သွင်းခြင်း

9Router နှင့် Mux တို့၏ ကိုယ်ပိုင် HTTP endpoint များအတွက် API key/bearer token တစ်ခု
လိုအပ်သည်။ OmniRoute သည်-

1. Service တစ်ခုချင်းစီအလိုက် prefix (`nr_` သည် 9Router အတွက်၊ `mx_` သည် Mux အတွက်)
   ဖြင့် `crypto.randomBytes(32).toString("base64url")` ကို အသုံးပြု၍ key တစ်ခု ဖန်တီးသည်။
2. Provider credential များအတွက် အသုံးပြုသည့် တူညီသော cipher ဖြစ်သည့် AES-256-GCM ကို
   အသုံးပြု၍ သိမ်းဆည်းထားချိန်တွင် ၎င်းကို encrypt လုပ်သည်။
3. Spawn လုပ်ချိန်တွင် ၎င်းကို decrypt လုပ်ပြီး environment variable အဖြစ် ထည့်သွင်းသည် —
   9Router အတွက် `NINEROUTER_API_KEY`၊ Mux အတွက် `MUX_SERVER_AUTH_TOKEN` ဖြစ်သည် (CLI
   flag အဖြစ် ဘယ်သောအခါမျှ မပေးသောကြောင့် token သည် `ps`/process စာရင်းများတွင်
   ဘယ်သောအခါမျှ မပေါ်ပါ)။
4. မည်သည့် HTTP response တွင်မဆို plaintext key ကို ဘယ်သောအခါမျှ ပြန်မပေးပါ။

CLIProxyAPI သည် spawn လုပ်ချိန်တွင် ထည့်သွင်းပေးသည့် သီးသန့် data-plane key ကို ရရှိသည်
(`needsApiKey: true` — adapter နှင့် model sync လုပ်ရန် အသုံးပြုသည်)။

### SSRF ကာကွယ်ရေး

Reverse HTTP proxy (`/dashboard/.../embed/[...path]`) ကို
`http://127.0.0.1:{port}` သို့သာ forward လုပ်ရန် hardcode လုပ်ထားသည်။ Loopback မဟုတ်သော
destination များသို့ redirect များကို ဘယ်သောအခါမျှ မလိုက်ပါ။ Loopback range ပြင်ပသို့
resolve ဖြစ်သော upstream URL မည်သည့်အရာကိုမဆို ငြင်းပယ်ရန် `ssrf-req-filter` library ကို
အသုံးပြုထားသည်။

### Shell လုံခြုံရေး (မဖြစ်မနေလိုက်နာရမည့် စည်းမျဉ်း #13)

`npm install` ကို `execFile('npm', ['install', pkg, '--prefix', dir])` မှတစ်ဆင့် ခေါ်ယူသည် —
template literal မရှိ၊ shell မရှိ၊ ပြင်ပ path များကို command string အတွင်း
ထည့်သွင်းပေါင်းစပ်ခြင်း မရှိပါ။ Runtime value များ (port များ၊ API key များ) ကို child ၏
`env` object မှတစ်ဆင့် ပေးပို့သည်။

### Error သန့်စင်ခြင်း (မဖြစ်မနေလိုက်နာရမည့် စည်းမျဉ်း #12)

`/api/services/*` မှ error response အားလုံးသည် `buildErrorBody()` သို့မဟုတ်
`sanitizeErrorMessage()` ကို ဖြတ်သန်းသည်။ Raw `err.stack` နှင့် `err.message` တို့ကို
ခေါ်ယူသူထံ တိုက်ရိုက် ဘယ်သောအခါမျှ ပြန်မပေးပါ။

## 6. Embedded service အသစ်တစ်ခု ထည့်သွင်းခြင်း

ဤအဆင့် 8 ဆင့်ကို လိုက်နာပါ။ စံကိုးကားချက်အဖြစ် `src/lib/services/installers/` နှင့်
`src/app/api/services/` ရှိ လက်ရှိ implementation များကို ဖတ်ရှုပါ။

### အဆင့် 1 — Installer ကို ဖန်တီးပါ

`ninerouter.ts` ကို နမူနာယူ၍ `src/lib/services/installers/{name}.ts` ကို ဖန်တီးပါ-

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // အသုံးမပြုရသေးသော port တစ်ခုကို ရွေးပါ

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

`installers/utils.ts` မှ `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` ကို
အသုံးပြုပါ — `execSync` သို့မဟုတ် shell interpolation ကို ဘယ်သောအခါမျှ မသုံးပါနှင့်။

### အဆင့် 2 — Bootstrap တွင် မှတ်ပုံတင်ပါ

`src/lib/services/bootstrap.ts` ရှိ `SERVICES` array သို့ `ServiceEntry` တစ်ခု ထည့်ပါ-

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // API key မလိုအပ်ပါက false
}
```

`cfg.tool === "myservice"` ကို ကိုင်တွယ်ရန် `buildSpawnArgsFactory()` ကို တိုးချဲ့ပါ။

#### ထည့်သွင်းပြောင်းလဲနိုင်သော provider-plugin contract (အဆင့် 1၊ #7333)

`src/lib/services/providerPlugins/` သည် backend တစ်ခု၏ `bootstrap.ts` `ServiceEntry`
field များနှင့် `serviceBackends.ts` manifest-template field များကို သီးခြားဆက်နွှယ်မှုမရှိသော
file နှစ်ခုတွင် backend တစ်ခုတည်း၏ ပုံစံကို ခွဲခြားဖော်ပြမည့်အစား object တစ်ခုထဲသို့
စုစည်းပေးသည့် `ServiceProviderPlugin` contract တစ်ခုကို မိတ်ဆက်ပေးသည်။ ယခုရေးသားနေချိန်အထိ
**`9router` ကိုသာ ရွှေ့ပြောင်းပြီးဖြစ်သည်** — `bootstrap.ts` သည် ၎င်း၏ `SERVICES[]` entry ကို
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`) မှ
ရယူဖန်တီးပြီး plugin မရှိတော့ပါက startup error တစ်ခု ထုတ်ပေးသည်။ `cliproxy`, `mux` နှင့်
`bifrost` တို့သည် ပြောင်းလဲမှုမရှိဘဲ ယခင်ကတည်းကရှိသော inline `SERVICES[]` literal များကို
ဆက်လက်အသုံးပြုနေသည်။

`open-sse/config/providerPluginManifest.ts` တွင်
`SERVICE_BACKEND_MANIFEST_TEMPLATE` entry တစ်ခုမှ မှန်ကန်စွာဖွဲ့စည်းထားသော
`ProviderPluginManifestEntry` တစ်ခု တည်ဆောက်ပေးသည့် ထပ်တိုး
`createServiceBackendManifestEntry(pluginId, template)` helper တစ်ခုလည်း ရရှိလာသည် —
၎င်းကို မည်သည့် လက်ရှိအသုံးပြုနေသော request path နှင့်မျှ **မချိတ်ဆက်ရသေးပါ**
(`generateProviderPluginManifestFromRegistry()` သို့မဟုတ်
`/v1/providers/[provider]/models` နှစ်ခုစလုံးတွင် မချိတ်ဆက်ရသေးပါ)။ ဒုတိယ backend တစ်ခုအတွက်
contract ကို အတည်ပြုပြီးသည်နှင့် ၎င်းကို နောက်ဆက်တွဲအဖြစ် ဆောင်ရွက်ရန် ကျန်ရှိနေသည်။

Issue #7333 အောက်တွင် ခြေရာခံထားပြီး နောက်ဆက်တွဲ PR များသို့ ရွှေ့ဆိုင်းထားသည့် အရာများမှာ-
`cliproxyapi` ကို တူညီသော registry မှတစ်ဆင့် ရွှေ့ပြောင်းခြင်း၊ `mux`/`bifrost` ကို
`ServiceBackendPluginId` union ထဲသို့ ယေဘုယျပုံစံပြောင်းခြင်း၊ executor-routing အတွက်
အထူးကိုင်တွယ်ထားမှု (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) ကို plugin contract ထဲသို့ ပေါင်းစည်းခြင်းနှင့်
`createServiceBackendManifestEntry()` ကို လက်ရှိအသုံးပြုနေသော manifest/models code path
တစ်ခုနှင့် ချိတ်ဆက်ခြင်းတို့ ဖြစ်သည်။

## 7. ပြဿနာဖြေရှင်းခြင်း

### ဝန်ဆောင်မှု စတင်မရခြင်း

**လက္ခဏာများ:** Start ခလုတ်က 503 ကို ပြန်ပေးပြီး အခြေအနေသည် `"error"` သို့မဟုတ် `"starting"` တွင် ဆက်ရှိနေသည်။

**စစ်ဆေးရန်စာရင်း:**

1. `GET /api/services/{name}/logs` (သို့မဟုတ် dashboard ရှိ Logs panel) ကို စစ်ဆေးပါ။ `Error: ENOENT`၊ `address already in use` သို့မဟုတ် `Cannot find module` ကဲ့သို့သော စာကြောင်းများကို ရှာပါ။
2. `npm` သည် PATH ထဲတွင် ရှိကြောင်း အတည်ပြုပါ။ OmniRoute ကို အသုံးပြုလုပ်ဆောင်နေသည့် user account တစ်ခုတည်းမှ `which npm` ကို လုပ်ဆောင်ပါ။
3. ဝန်ဆောင်မှုကို ထည့်သွင်းထားကြောင်း အတည်ပြုပါ။ `installedVersion` ကို သိရှိရန် `GET /api/services/{name}/status` ကို စစ်ဆေးပါ။ `null` ဖြစ်နေပါက install ကို ဦးစွာ လုပ်ဆောင်ပါ။
4. `DATA_DIR/services/{name}/node_modules/` ရှိပြီး အလွတ်မဖြစ်ကြောင်း စစ်ဆေးပါ။
5. သန့်စင်ထားသော ထွက်ခွာရသည့်အကြောင်းရင်းကို သိရှိရန် status response ရှိ `lastError` field ကို စစ်ဆေးပါ။

### Cold start နှေးကွေးခြင်း (`running` သို့ရောက်ရန် > 10 s)

**လက္ခဏာများ:** အခြေအနေသည် `"running"` သို့မဟုတ် `"error"` သို့ မပြောင်းမီ `"starting"` တွင် အချိန်ကြာမြင့်စွာ ဆက်ရှိနေသည်။

**ရှင်းလင်းချက်:** 9Router ၏ cold start တွင် ကြီးမားသော dependency tree များ (DNS၊ tunnel၊ MITM module များ) ကို import လုပ်ခြင်း ပါဝင်သည်။ ပုံသေ health interval သည် 2 s ဖြစ်ပြီး supervisor က timeout ဖြစ်ကြောင်း မသတ်မှတ်မီ 3 ကြိမ် ကြိုးစားသည် (သို့သော် polling ကို ဆက်လက်လုပ်ဆောင်သည်)။

**ဖြေရှင်းနည်း:** `healthIntervalMs` နှင့် `waitForHealthy` timeout (`healthIntervalMs * 3`) ကို `bootstrap.ts` တွင် ပြင်ဆင်သတ်မှတ်နိုင်သည်။ စတင်ချိန် ပိုကြာသော ဝန်ဆောင်မှုများအတွက် `healthIntervalMs` ကို 5000 သို့လည်းကောင်း၊ `stopTimeoutMs` ကို 30 000 သို့လည်းကောင်း တိုးမြှင့်ပါ။

### Port တိုက်ဆိုင်မှု (`EADDRINUSE`)

**လက္ခဏာများ:** Log များတွင် `address already in use :::20130` ဟု ပြသသည်။

**အကြောင်းရင်းများ:**

- အခြား process တစ်ခုက port 20130 ကို အသုံးပြုနေပြီးဖြစ်သည်။
- ယခင် 9Router process တစ်ခုကို အပြည့်အဝ ရပ်တန့်ထားခြင်း မရှိပါ (zombie PID)။

**ဖြေရှင်းနည်း:**

1. `.env` ရှိ `NINEROUTER_PORT` environment variable မှတစ်ဆင့် ပုံသေ port ကို ပြောင်းလဲပါ။
2. တိုက်ဆိုင်နေသော process ကို ရှာဖွေပြီး ရပ်တန့်ပါ: `lsof -ti :20130 | xargs kill -9`။
3. `bootstrap.ts` ရှိ `port` field မှတစ်ဆင့် ဝန်ဆောင်မှုတစ်ခုချင်းစီအလိုက် port ကို ပြင်ဆင်သတ်မှတ်နိုင်သည်။

**မှတ်ချက်:** OmniRoute ၏ ပုံသေ port 20128 နှင့် တိုက်ဆိုင်မှုကို ရှောင်ရှားရန် 9Router သည် port 20130 ကို အထူးသဖြင့် ပုံသေအဖြစ် အသုံးပြုသည်။

### Install လုပ်စဉ် ခွင့်ပြုချက် ငြင်းပယ်ခံရခြင်း (EACCES)

**လက္ခဏာများ:** Install က 500 ကို ပြန်ပေးပြီး log များတွင် `EACCES` သို့မဟုတ် `permission denied` ဟု ပြသသည်။

**အကြောင်းရင်းများ:**

- `DATA_DIR` သို့မဟုတ် ၎င်း၏ parent တွင် OmniRoute process က ရေးသားခွင့် မရှိပါ။
- ချိတ်ဆက်ထားသော volume သို့ ရေးသားခွင့်မရှိဘဲ Docker rootless အတွင်း လုပ်ဆောင်နေခြင်း။

**ဖြေရှင်းနည်း:**

1. `DATA_DIR` (ပုံသေ: `~/.omniroute/`) ကို စစ်ဆေးပါ: `ls -la ~/.omniroute/`
2. OmniRoute process user သည် directory ကို ပိုင်ဆိုင်ကြောင်း သေချာပါစေ: `chown -R $USER ~/.omniroute/`
3. Docker တွင် volume mount သည် container user အတွက် မှန်ကန်သော ခွင့်ပြုချက်များ ရှိကြောင်း သေချာပါစေ။

---

### Update မအောင်မြင်ခြင်း (`npm install` timeout သို့မဟုတ် network error)

**လက္ခဏာများ:** Update က `InstallError` နှင့်အတူ 500 ကို ပြန်ပေးပြီး log များတွင် network timeout ဟု ပြသသည်။

**စစ်ဆေးရန်စာရင်း:**

1. npm registry သို့ ဆက်သွယ်နိုင်ကြောင်း အတည်ပြုပါ: `npm ping`။
2. ကုမ္ပဏီ proxy ရှိမရှိ စစ်ဆေးပါ: `npm config get proxy`၊ `npm config get https-proxy`။
3. Install ကို ကိုယ်တိုင် စမ်းကြည့်ပါ: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`။
4. Air-gap နောက်ကွယ်တွင် ရှိနေပါက tarball ကို ကြိုတင် download လုပ်ပြီး `npm install /path/to/tarball.tgz` ကို အသုံးပြုပါ။

---

### စတင်ပြီးသည်နှင့် ဝန်ဆောင်မှုက `"error"` အခြေအနေကို ချက်ချင်းပြသခြင်း (လျင်မြန်စွာ ပျက်သွားခြင်း)

**လက္ခဏာများ:** အခြေအနေသည် 5 စက္ကန့်အတွင်း `"starting"` မှ `"error"` သို့ ပြောင်းလဲသွားသည်။ `lastError` တွင် `"Fast crash (exited with code 1)"` ဟု ပြသသည်။

**စစ်ဆေးရန်စာရင်း:**

1. Log tail အပြည့်အစုံကို ဖတ်ပါ: `GET /api/services/{name}/logs?tail=500`။
2. အဖြစ်များသော အကြောင်းရင်းမှာ ဝန်ဆောင်မှုက လိုအပ်သော်လည်း မရှိနေသော environment variable များ ဖြစ်သည်။
3. 9Router အတွက် `NINEROUTER_DISABLE_MITM=true` နှင့် `NINEROUTER_DISABLE_TUNNEL=true` တို့သည် spawn လုပ်စဉ် ပေးပို့သော env ထဲတွင် ရှိကြောင်း အတည်ပြုပါ (`installers/ninerouter.ts` ရှိ `resolveSpawnArgs` ကို ကြည့်ပါ)။

---

## 8. မေးလေ့ရှိသော မေးခွန်းများ

**မေး: ထည့်သွင်းပေါင်းစည်းထားသော ဝန်ဆောင်မှု endpoint များကို loopback မဟုတ်သော client များထံ ဖွင့်ပေးနိုင်ပါသလား။**

မရပါ။ LOCAL_ONLY အဆင့်ကို ရည်ရွယ်ချက်ရှိရှိ သတ်မှတ်ထားခြင်းဖြစ်သည် (တင်းကျပ်သော စည်းမျဉ်း #17)။ `npm install` ကို ခေါ်ယူနိုင်သော သို့မဟုတ် `node` process များကို စတင်နိုင်သော route များသည် loopback မဟုတ်သည့် traffic မှ ဝင်ရောက်အသုံးပြုနိုင်ခြင်း မရှိရပါ။ အဘယ်ကြောင့်ဆိုသော် tunnel (Cloudflare, Ngrok, Tailscale) မှတစ်ဆင့် JWT ပေါက်ကြားသွားပါက မည်သည့် process ကိုမဆို စတင်နိုင်သွားမည်ဖြစ်သောကြောင့် ဖြစ်သည်။ `/api/services/` အတွက် ခြွင်းချက်ဖြင့် ပိတ်ပင်မှုကို ကျော်လွှားခွင့် မရှိပါ — `/api/mcp/` နှင့် မတူဘဲ ၎င်းကို manage-scope bypass စာရင်းမှ ချန်လှပ်ထားသည်။ `docs/security/ROUTE_GUARD_TIERS.md` ကို ကြည့်ပါ။

---

**မေး: 9Router နှင့် CLIProxyAPI ကို production/cloud deployment များတွင် အသုံးပြုနိုင်မည်လား။**

အသုံးပြုနိုင်ပါသည်။ ဝန်ဆောင်မှုနှစ်ခုစလုံးသည် OmniRoute ကိုယ်တိုင်ကဲ့သို့ပင် local-first မော်ဒယ်ကို လိုက်နာပါသည်။ ၎င်းတို့သည် စက်တစ်ခုတည်းပေါ်တွင် လည်ပတ်ပြီး loopback မှတစ်ဆင့် ဆက်သွယ်ကြသည်။ ဤနေရာရှိ "Production" ဆိုသည်မှာ အဝေးရှိ cloud provider ကို ဆိုလိုခြင်းမဟုတ်ဘဲ OmniRoute ကို ဖြန့်ချထားသော VPS သို့မဟုတ် local server ကို ဆိုလိုခြင်းဖြစ်သည်။

---

**မေး: supervisor ကို မည်သို့ debug လုပ်ရမည်နည်း။**

1. SSE log stream ကို tail လုပ်ပါ: `curl -N http://localhost:20128/api/services/9router/logs`။
2. OmniRoute ၏ pino output ရှိ structured log များကို `service:supervisor` namespace ဖြင့် စစ်ထုတ်၍ စစ်ဆေးပါ။
3. DB row ကို စစ်ဆေးပါ: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`။
4. လက်ရှိ live state၊ PID၊ health နှင့် `lastError` တို့ကို call တစ်ကြိမ်တည်းဖြင့် ကြည့်ရန် `GET /api/services/9router/status` ကို အသုံးပြုပါ။

---

**မေး: supervisor တွင် `health: "degraded"` သို့မဟုတ် `health: "unknown"` ဟု ပြသသော်လည်း state သည် `"running"` ဖြစ်နေပါသည်။ ပြဿနာရှိပါသလား။**

`"degraded"` ဆိုသည်မှာ health probe က 200 မဟုတ်သော response ကို ပြန်ပေးခဲ့သည်ဟု ဆိုလိုသည်။ `"unknown"` ဆိုသည်မှာ probe တစ်ခုမျှ မပြီးမြောက်သေးဟု ဆိုလိုသည် (ပထမဆုံး poll နှင့် တစ်ပြိုင်နက်ဖြစ်နေခြင်း)။ နှစ်မျိုးစလုံးသည် startup အတွင်း ယာယီဖြစ်ပေါ်နိုင်ပါသည်။ `"running"` ဖြစ်ပြီးနောက် `healthIntervalMs * 3` ms ထက်ပိုကြာသည်အထိ health က `"degraded"` အဖြစ် ဆက်ရှိနေပါက ထည့်သွင်းပေါင်းစည်းထားသော ဝန်ဆောင်မှုသည် လည်ပတ်နေသော်လည်း ၎င်း၏ HTTP API က တုံ့ပြန်ခြင်းမရှိဟု ဆိုလိုသည်။ status response ထဲရှိ port မှန်ကန်မှုရှိမရှိနှင့် ဝန်ဆောင်မှုက ထို port တွင် အမှန်တကယ် listen လုပ်နေခြင်း ရှိမရှိကို စစ်ဆေးပါ။

---

**မေး: အပြည့်အဝ restart မလုပ်ဘဲ 9Router API key ကို ပြောင်းလဲနိုင်ပါသလား။**

မရပါ။ API key ကို spawn လုပ်ချိန်တွင် environment variable မှတစ်ဆင့် 9Router ထံ ပေးပို့သည်။ လည်ပတ်နေသော process တစ်ခုရှိ environment variable များကို ပြောင်းလဲ၍ မရပါ။ `POST .../rotate-key` သည် key အသစ်ကို အသုံးချရန် ဝန်ဆောင်မှုကို အလိုအလျောက် ရပ်တန့်ပြီး ပြန်လည်စတင်ပေးသည်။ key လှည့်ပြောင်းမှုသည် ဝန်ဆောင်မှု၏ `stopTimeoutMs` (မူလသတ်မှတ်ချက် 15 s) နှင့် ၎င်း၏ startup ကြာချိန်တို့ ပေါင်းထားသော အချိန်အတွင်း သက်ရောက်မှုရှိလာသည်။

---

**မေး: ring buffer ကန့်သတ်ချက်မှာ မည်မျှဖြစ်ပြီး ၎င်းပြည့်သွားသောအခါ ဘာဖြစ်မည်နည်း။**

ဝန်ဆောင်မှုတစ်ခုစီတွင် သီးသန့် 5 MB ring buffer တစ်ခုစီရှိသည်။ buffer ပြည့်သွားသောအခါ log line အသစ်များအတွက် နေရာဖယ်ပေးရန် အဟောင်းဆုံး log line များကို ဖယ်ရှားသည်။ SSE `snapshot` event သည် `tail` ကန့်သတ်ချက်အတွင်းရှိ လတ်တလောအကျဆုံး line များကို ပြန်ပေးသည်။ DB row ထဲတွင် `logsBufferPath` ကို သတ်မှတ်မထားပါက log များကို disk ပေါ်တွင် အမြဲတမ်းသိမ်းဆည်းထားမည် မဟုတ်ပါ။
