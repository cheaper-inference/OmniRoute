OmniRoute കോൾ ലോഗുകൾ ഒരു ബാഹ്യ അനലിറ്റിക്സ് സ്റ്റോറിലേക്ക് തുടർച്ചയായും ഇൻക്രിമെന്റലായും എക്സ്പോർട്ട് ചെയ്യുന്നു.

Logs ഡാഷ്ബോർഡ് ടാബ് അഭ്യർത്ഥനാ ചരിത്രം SQLite (`call_logs`)-ൽ സൂക്ഷിക്കുന്നു; റൊട്ടേഷനും റിട്ടൻഷനും അതിന്റെ പരിധി നിർണ്ണയിക്കുന്നു. ഷെഡ്യൂൾ പ്രകാരം അതേ റെക്കോർഡ് സെറ്റ് പുറത്തേക്ക് അയയ്ക്കുന്ന ലോഗ് എക്സ്പോർട്ട്, പ്രാദേശിക ഡാറ്റാബേസിന്റെ കാലാവധിക്കപ്പുറം അവ നിലനിർത്താനും മറ്റ് ഡാറ്റയുമായി ചേർക്കാനും സഹായിക്കുന്നു. BigQuery ആണ് ആദ്യ ഡെസ്റ്റിനേഷൻ; പൈപ്പ്ലൈൻ ഒരു രജിസ്ട്രിയായതിനാൽ കൂടുതൽ ഡെസ്റ്റിനേഷനുകൾ കൂട്ടിച്ചേർക്കാം.

## 1. ഇത് പ്രവർത്തിക്കുന്ന വിധം

```
സെർവർ (കോൺഫിഗറേഷൻ ഡീക്രിപ്റ്റ് ചെയ്യുക + സാധൂകരിക്കുക, കർസർ പൊരുത്തപ്പെടുത്തുക)
  → IPC ആരംഭിക്കുക → ഒറ്റപ്പെടുത്തിയ exportChild OS പ്രോസസ്
    → റീഡ്-ഒൺലി storage.sqlite → പങ്കിട്ട കോൾ-ലോഗ് ക്വറി/മാപ്പിംഗ്
      → അസിങ്ക്രണസ് ആർട്ടിഫാക്റ്റ് ഹൈഡ്രേഷൻ → ഡെസ്റ്റിനേഷൻ prepare()/send()
        → ബാച്ച് IPC → സെർവർ കർസർ നിലനിർത്തുന്നു → ack IPC
          → അടുത്ത ബാച്ച്; done IPC → സെർവർ വിജയം രേഖപ്പെടുത്തുന്നു
```

- **ഷെഡ്യൂൾ** — `0 * * * *` (മണിക്കൂറിൽ ഒരിക്കൽ,
  UTC) ഡിഫോൾട്ടായുള്ള ഒരൊറ്റ `JobRegistry` ക്രോൺ ജോലി, `log_export`.
  `src/lib/initCloudSync.ts`-ൽ രജിസ്റ്റർ ചെയ്തിരിക്കുന്നു; `OMNIROUTE_LOG_EXPORT_CRON` ഉപയോഗിച്ച്
  മാറ്റിയെഴുതാം. ഓരോ ടിക്കിലും **പ്രവർത്തനക്ഷമമാക്കിയിട്ടുള്ള** എല്ലാ ഡെസ്റ്റിനേഷനുകളും ക്രമാനുസൃതമായി പൂർണ്ണമായി പ്രോസസ് ചെയ്യുന്നു.
- **കർസർ** — SQLite-ന്റെ ഇംപ്ലിസിറ്റ് `call_logs.rowid`, ഓരോ ഡെസ്റ്റിനേഷനുമായി ബന്ധപ്പെട്ട്
  `log_export_destinations.cursor_row_id`-ൽ നിലനിർത്തുന്നു. `timestamp` മനഃപൂർവം കർസറായി ഉപയോഗിക്കുന്നില്ല:
  കോളർമാർക്ക് സ്വന്തം മൂല്യം നൽകാനാകുന്നതിനാൽ, പിന്നീട് ആരംഭിച്ച വേഗമേറിയ അഭ്യർത്ഥനയ്ക്കുശേഷം മന്ദഗതിയിലുള്ള
  അഭ്യർത്ഥന എഴുതപ്പെടാം; അപ്പോൾ ടൈംസ്റ്റാമ്പ് കർസർ അതിനെ ഒഴിവാക്കും.
- **ബാച്ചിംഗ്** — ഓരോ അഭ്യർത്ഥനയ്ക്കും `batch_size` വരികൾ (ഡിഫോൾട്ട് 500), ഓരോ റണ്ണിനും
  `max_rows_per_run` വരികൾ (ഡിഫോൾട്ട് 10000); അതിനാൽ വലിയൊരു ബാക്ക്ലോഗ് ഒരൊറ്റ റണ്ണിനെ തടയുന്നതിന്
  പകരം നിരവധി ടിക്കുകളിലായി തീർക്കപ്പെടും.
- **ഡെലിവറി** — `send()` പൂർത്തിയായതിന് ശേഷമേ കർസർ മുന്നോട്ട് നീങ്ങൂ. പരാജയപ്പെട്ട ബാച്ച്
  കർസറിനെ അതിന്റെ നിലവിലെ സ്ഥാനത്ത് തന്നെ നിലനിർത്തുന്നതിനാൽ അടുത്ത റണ്ണിൽ അതേ വരികൾ വീണ്ടും ശ്രമിക്കും.
  ഇവിടെ ലഭിക്കുന്ന ഉറപ്പ് യഥാർത്ഥ എക്സാക്ട്ലി-വൺസ് അല്ല; കുറഞ്ഞത്-ഒരിക്കലെങ്കിലും ഡെലിവറിയും
  ഡെസ്റ്റിനേഷൻ ഭാഗത്തെ ഡീ-ഡ്യൂപ്ലിക്കേഷനുമാണ്: BigQuery ഓരോ വരിക്കും കോൾ-ലോഗ് id അടിസ്ഥാനമാക്കി കീ നൽകുന്നു,
  കൂടാതെ സ്വന്തം ഡീഡ്യൂപ്പ് വിൻഡോയ്ക്കുള്ളിൽ ബെസ്റ്റ്-എഫർട്ട് അടിസ്ഥാനത്തിൽ അതിനെ മാനിക്കുന്നു.
- **ഓവർലാപ്പ് ഗാർഡ്** — ക്രോൺ ടിക്കും `POST .../run`-ഉം ഒരേ സമയം പ്രവർത്തിക്കാം. ഇതിനകം
  പ്രോസസ് ചെയ്തുകൊണ്ടിരിക്കുന്ന ഡെസ്റ്റിനേഷൻ രണ്ടാമതും പ്രോസസ് ചെയ്യുന്നതിനുപകരം ഒഴിവാക്കപ്പെടും
  (റൺ ഫലത്തിൽ `skipped: true`); അതിനാൽ ഒരേസമയം നടക്കുന്ന മറ്റൊരു റണ്ണിന് ബാച്ച് വീണ്ടും അയയ്ക്കാനോ
  കർസർ പിന്നിലേക്ക് എഴുതാനോ കഴിയില്ല.
- **പർജ് റിക്കവറി** — `cursor_row_id`, `MAX(rowid)`-നേക്കാൾ മുകളിലായാൽ (മുഴുവൻ പട്ടികയും
  പർജ് ചെയ്ത് rowid-കൾ വീണ്ടും ആരംഭിച്ച സാഹചര്യത്തിൽ), റണ്ണർ എന്നെന്നേക്കുമായി ഡാറ്റ കാണാതാകാതിരിക്കാൻ
  കർസർ 0-ലേക്ക് തിരിച്ചുകൊണ്ടുവരും.

### ഒറ്റപ്പെടുത്തിയ റണ്ണറും പരിധികളും

Node-ലെ ഓരോ ഡെസ്റ്റിനേഷൻ റണ്ണും ഹ്രസ്വകാലത്തേക്ക് നിലനിൽക്കുന്ന വേറൊരു OS ചൈൽഡ് പ്രോസസ് ആരംഭിക്കുന്നു
(`worker_threads` അല്ല, IPC സഹിതമുള്ള `child_process`). ബോഡി റീഡുകൾ, പേലോഡ് JSON
പാർസിംഗ്/സീരിയലൈസേഷൻ, ഡെസ്റ്റിനേഷൻ `prepare()`, ഡെസ്റ്റിനേഷൻ നെറ്റ്വർക്ക് I/O എന്നിവയെല്ലാം
സെർവറിന്റെ ഇവന്റ് ലൂപ്പിലല്ല, അവിടെയാണ് പ്രവർത്തിക്കുന്നത്. കോൺഫിഗറേഷനും ചെറിയ പുരോഗതി സന്ദേശങ്ങളും
മാത്രമാണ് IPC വഴി കടന്നുപോകുന്നത്; എക്സ്പോർട്ട് ചെയ്ത റെക്കോർഡുകൾ ഒരിക്കലും സെർവറിലേക്ക് മടങ്ങുന്നില്ല.
ക്രോൺ ജോലിയും ഇപ്പോൾ റൺ ചെയ്യാനുള്ള റൂട്ടും അതേ പബ്ലിക് ഫലവും ഓവർലാപ്പ് ഗാർഡും നിലനിർത്തുന്നു.

സെർവർ പരിഹരിച്ച `DATA_DIR/storage.sqlite`, ചൈൽഡ് `node:sqlite` ഉപയോഗിച്ച് റീഡ്-ഒൺലി ആയി തുറക്കുന്നു;
`busy_timeout=5000`, `query_only=ON` എന്നിവയും ഉപയോഗിക്കുന്നു. അത് DB സിംഗിൾടൺ ഇമ്പോർട്ട് ചെയ്യുന്നില്ല;
മൈഗ്രേഷനുകളോ ബാക്കപ്പുകളോ SQLite അപ്ഡേറ്റുകളോ നടത്തുന്നുമില്ല. കേടായതോ ലഭ്യമല്ലാത്തതോ ആയ
ആർട്ടിഫാക്റ്റുകളുടെ ബുക്ക്കീപ്പിംഗ് (കേടായ ആർട്ടിഫാക്റ്റിനുള്ള UPDATE ഉൾപ്പെടെ) ഡാഷ്ബോർഡിന്റെ വിശദാംശ
പാതയിൽ മാത്രമായി തുടരുന്നു. രണ്ട് പാതകളും പ്യൂർ ഡീറ്റെയിൽ റിസോൾവർ പങ്കിടുന്നു; എക്സ്പോർട്ട്
അസിങ്ക്രണസ് ഫയൽസിസ്റ്റം റീഡുകളും ആർട്ടിഫാക്റ്റ് → ലെഗസി ഇൻലൈൻ → ലെഗസി ഡിസ്ക് → ഒന്നുമില്ല എന്ന
അതേ പരിഹാരക്രമവും ഉപയോഗിക്കുന്നു. ചൈൽഡ് അതിന്റെ റീഡർ തുറക്കുമ്പോൾ ഒരു റൺ പരമാവധി ഇൻസേർഷൻ
rowid-യുടെ സ്നാപ്പ്ഷോട്ട് എടുക്കുന്നു; പിന്നീടുള്ള ഇൻസേർഷനുകൾ അടുത്ത റണ്ണിനായി കാത്തിരിക്കും. ഇത് ഒരു
ഇൻസേർഷൻ അതിർത്തിയാണ്, ദീർഘകാല SQLite ട്രാൻസാക്ഷനല്ല: നെറ്റ്വർക്ക് കാത്തിരിപ്പുകൾക്കിടയിലും
WAL റൈറ്ററുകൾക്കും ചെക്ക്പോയിന്റുകൾക്കും സ്വതന്ത്രമായി പ്രവർത്തിക്കാം. നിലവിലുള്ള വരികളുടെ
അപ്ഡേറ്റുകളും ഡിലീഷനുകളും ഈ അതിർത്തിയാൽ ഫ്രീസ് ചെയ്യപ്പെടുന്നില്ല.

ഓരോ അംഗീകരിച്ച ബാച്ചിനും ശേഷം ചൈൽഡ് ഒരു അംഗീകാരത്തിനായി കാത്തിരിക്കും. സെർവർ ആദ്യം
`advanceLogExportCursor` ഉപയോഗിച്ച് കർസർ നിലനിർത്തുകയും തുടർന്ന് `ack` അയയ്ക്കുകയും ചെയ്യുന്നു;
അതിനു മുമ്പ് അടുത്ത ബാച്ച് ആരംഭിക്കില്ല. അയയ്ക്കൽ പരാജയം, ക്രാഷ് അല്ലെങ്കിൽ ടൈംഔട്ട് സംഭവിച്ചാൽ ആ ബാച്ചിന്റെ
കർസർ മുന്നോട്ട് നീക്കാതെ പരാജയം രേഖപ്പെടുത്തും. മുമ്പ് അംഗീകരിച്ച ബാച്ചുകൾ കമ്മിറ്റ് ചെയ്ത നിലയിൽ തുടരും;
അംഗീകരിക്കാത്ത ഒരൊറ്റ ബാച്ച് മാത്രമേ പരമാവധി വീണ്ടും അയയ്ക്കപ്പെടുകയുള്ളൂ. `done` ലഭിക്കുകയും ചൈൽഡ്
പിശകില്ലാതെ എക്സിറ്റ് ചെയ്യുകയും ചെയ്തതിന് ശേഷമേ വിജയം രേഖപ്പെടുത്തൂ. പരാജയങ്ങൾ ചൈൽഡിനെ
SIGTERM ഉപയോഗിച്ച് അവസാനിപ്പിക്കും; 500 ms കഴിഞ്ഞാൽ SIGKILL-ലേക്ക് ഉയർത്തുകയും റണ്ണർ പ്രോസസ്
പൂർണ്ണമായി അടയുന്നതുവരെ കാത്തിരിക്കുകയും ചെയ്യും.

| എൻവയോൺമെന്റ് വേരിയബിൾ                         | ഡിഫോൾട്ട് | ഉദ്ദേശ്യം                                 |
| --------------------------------------------- | --------- | ----------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000    | ഓരോ ഡെസ്റ്റിനേഷനുമുള്ള വാൾ-ക്ലോക്ക് പരിധി |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024      | ചൈൽഡ് V8 ഓൾഡ്-സ്പേസ് പരിധി, MB-യിൽ        |

അസാധുവായതോ പോസിറ്റീവ് അല്ലാത്തതോ പൂർണ്ണസംഖ്യ അല്ലാത്തതോ ആയ മൂല്യങ്ങൾക്ക് ഡിഫോൾട്ടുകൾ ഉപയോഗിക്കും.
ഹീപ്പ് ക്രമീകരണം മൊത്തത്തിലുള്ള RSS പരിധിയല്ല; വളരെ വലിയ ബാച്ചുകൾക്ക് ഇപ്പോഴും ചൈൽഡിന്റെ മെമ്മറി
തീർക്കാനും റൺ സുരക്ഷിതമായി പരാജയപ്പെടാനും കഴിയും. ബോഡികൾ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ 512 KiB
ആർട്ടിഫാക്റ്റുകളുള്ള ഡിഫോൾട്ട് 500-വരി ബാച്ചിന്, BigQuery-യുടെ ബൈറ്റ്-ചങ്ക് ചെയ്ത JSON സീരിയലൈസേഷൻ
ഉൾപ്പെടെ, ആവശ്യമായ അധിക ശേഷി 1024 MB ഡിഫോൾട്ട് നൽകുന്നു. ഇത് ബോഡികളുള്ള 10000-വരി ബാച്ചിനെ
സുരക്ഷിതമാക്കുന്നില്ല. V8 ഹീപ്പ് തീർന്നാൽ പ്രായോഗികമായി പരിഹരിക്കാവുന്ന പരാജയം രേഖപ്പെടുത്തും:
ബാച്ച് വലുപ്പം കുറയ്ക്കുക അല്ലെങ്കിൽ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` വർധിപ്പിക്കുക;
അവസാനം അംഗീകരിച്ച ബാച്ചിൽ തന്നെ കർസർ തുടരും. ചരിത്രപരമായ ഇൻലൈൻ/ഡിസ്ക് ബോഡികൾ ആധുനിക
ആർട്ടിഫാക്റ്റ് പരിധിയുടെ സംരക്ഷണത്തിൽ ഉൾപ്പെടുന്നില്ല. പ്രത്യേകിച്ച് മെമ്മറി-പരിമിതമായ കണ്ടെയ്നറുകളിൽ,
ഓപ്പറേറ്റർമാർ RSS-നുള്ള ശേഷി പ്രത്യേകം കണക്കാക്കണം.

പരിഹരിച്ച `DATA_DIR`, `NODE_ENV`, വ്യക്തമായി നൽകിയ `TZ` (ലെഗസി ഫയൽനാമത്തിന്റെ ലോക്കൽ-ടൈം
റിസല്യൂഷൻ), ലഭ്യമാണെങ്കിൽ `ELECTRON_RUN_AS_NODE`, കൂടാതെ ഇനിപ്പറയുന്ന ഔട്ട്ബൗണ്ട് ഇൻപുട്ടുകൾ എന്നിവ
മാത്രമാണ് ചൈൽഡിന് ലഭിക്കുന്നത്:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (അവയുടെ ലോവർകേസ് രൂപങ്ങളും),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
ഒരു ഗ്ലോബൽ Undici ഡിസ്പാച്ചർ, `NO_PROXY` ഉൾപ്പെടെയുള്ള സെർവറിന്റെ പ്യൂർ എൻവയോൺമെന്റ്-പ്രോക്സി
റിസല്യൂഷനും ലോക്കൽ-ഹോസ്റ്റ് ബൈപാസ് നിയമങ്ങളും പങ്കിടുന്നു; അത് `proxyFetch.ts`-ഉം അതിന്റെ
DB/ഫീച്ചർ ഫ്ലാഗുകളും ഇമ്പോർട്ട് ചെയ്യുന്നില്ല. ഫോർവേഡ് ചെയ്ത ഔട്ട്പുട്ടിലും രേഖപ്പെടുത്തിയ പിശകുകളിലും
പ്രോക്സി ക്രെഡൻഷ്യലുകൾ മറച്ചുവെക്കുന്നു. ഡെസ്റ്റിനേഷൻ ക്രെഡൻഷ്യലുകൾ ഒരൊറ്റ സ്റ്റാർട്ട് IPC സന്ദേശത്തിൽ
മാത്രമാണ് കൈമാറുന്നത്; argv-ലോ എൻവയോൺമെന്റിലോ ഒരിക്കലുമില്ല. ഔട്ട്പുട്ട്/പിശക് ഫോർവേഡിംഗിന്
പ്രിഫിക്സ് ചേർക്കുകയും അവ സാനിറ്റൈസ് ചെയ്യുകയും ചെയ്യുന്നു. ഓരോ ക്രോൺ റണ്ണിലും Node-ന്റെ SQLite
മുന്നറിയിപ്പ് ആവർത്തിക്കുന്നത് ഒഴിവാക്കാൻ ചൈൽഡ് എക്സിക്യൂഷൻ ആർഗ്യുമെന്റുകളിൽ `ExperimentalWarning`
മാത്രമാണ് പ്രവർത്തനരഹിതമാക്കുന്നത്; മറ്റ് മുന്നറിയിപ്പ് തരങ്ങൾ തുടർന്നും ദൃശ്യമാകും.

ലക്ഷ്യസ്ഥാന മൊഡ്യൂളുകൾ Next.js/server-only ഡിപെൻഡൻസികൾ ഇല്ലാതെ ഇംപോർട്ട് ചെയ്യാൻ കഴിയണം. നിലവിലുള്ള
BigQuery ഇംപ്ലിമെന്റേഷൻ ഇതിനകം ആ വ്യവസ്ഥ പാലിക്കുന്നു. ആക്സസ്-ടോക്കൺ കാഷുകൾ ചൈൽഡ്
റൺ അവസാനിക്കുന്നതുവരെ മാത്രമേ നിലനിൽക്കൂ; വ്യത്യസ്ത റണ്ണുകൾക്കിടയിൽ നിലനിൽക്കില്ല. പിന്തുണയ്ക്കുന്ന റൺടൈം Node ആണ് (`package.json`-ലെ engines), എന്നാൽ README-യിലെ Bun
ഇൻസ്റ്റലേഷൻ വിഭാഗവും `Dockerfile.bun`-ഉം `bun:sqlite` (`src/lib/db/core.ts` / അഡാപ്റ്ററുകൾ) ഉപയോഗിക്കുന്ന ഒരു പ്രൊഡക്ഷൻ അനുയോജ്യതാ മാർഗവും പരസ്യപ്പെടുത്തുന്നു. അതിനാൽ Bun-ൽ, എക്സ്പോർട്ടുകൾ മുമ്പുണ്ടായിരുന്ന
ഇൻ-പ്രോസസ് പാത നിലനിർത്തുകയും ഒറ്റത്തവണ മുന്നറിയിപ്പ് നൽകുകയും ചെയ്യുന്നു: ചൈൽഡ് ഹീപ്പ്/ടൈംഔട്ട് ഐസൊലേഷൻ ലഭ്യമല്ല. ഇവന്റ്-ലൂപ്പ്, OOM ഐസൊലേഷനുകൾക്കായി
Node ഉപയോഗിക്കുക; ഇവിടെ Bun-നെ dev-only ആയി കണക്കാക്കുന്നില്ല.

`includeBodies` പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, ഓരോ മണിക്കൂറിലുമുള്ള പേലോഡ് ബാക്ക്ലോഗ് ശേഖരിക്കുന്നതിനുപകരം
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` പോലുള്ള മിനിറ്റ്-തല ഇടവേളയ്ക്ക് മുൻഗണന നൽകുക.
ബാച്ച്, റോ പരിധികൾ ഇപ്പോഴും ഓരോ റണ്ണിനെയും നിയന്ത്രിക്കുന്നു. ഓരോ റണ്ണിലും ഓരോ ലക്ഷ്യസ്ഥാനത്തിനും പ്രോസസ് സ്റ്റാർട്ടപ്പിന്റെ ചെലവ് വരും;
ഇത് മൊത്തം CPU ഉപയോഗം കുറയ്ക്കുന്നതിനല്ല, മറിച്ച് സെർവർ ഇവന്റ്-ലൂപ്പ് ഐസൊലേഷനായി ചെറിയൊരു സ്റ്റാർട്ടപ്പ് ചെലവ് വഹിക്കുന്നതാണ്.

### പേലോഡുകൾ (പ്രോംപ്റ്റുകളും കംപ്ലീഷനുകളും)

ഡിഫോൾട്ടായി, Logs **ലിസ്റ്റ്** കാണിക്കുന്ന സംഗ്രഹ ഫീൽഡുകൾ മാത്രമാണ് എക്സ്പോർട്ടിൽ ഉൾപ്പെടുന്നത്. **പ്രോംപ്റ്റുകളും പ്രതികരണങ്ങളും എക്സ്പോർട്ട് ചെയ്യുക** (`includeBodies`) പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ, ഓരോ കോളിനും Logs **വിശദാംശ**
പെയ്ൻ കാണിക്കുന്ന വിവരങ്ങളും അധികമായി അയയ്ക്കുന്നു:

| ഫീൽഡ്                            | അതിൽ അടങ്ങിയിരിക്കുന്നത്                                        |
| -------------------------------- | --------------------------------------------------------------- |
| `request_body` / `response_body` | ഡാഷ്ബോർഡ് റെൻഡർ ചെയ്യുന്ന രീതിയിലുള്ള കോൾ പേലോഡുകൾ              |
| `pipeline_route_decision`        | റൂട്ടർ തിരഞ്ഞെടുത്ത ടാർഗറ്റും മോഡലും                            |
| `pipeline_client_request`        | ക്ലയന്റ് അയച്ചതുപോലെ കൃത്യമായ റോ അഭ്യർത്ഥന                      |

| `pipeline_client_response`       | കോളറിന് തിരികെ നൽകിയതു                                          |
| `pipeline_error`                 | പരാജയപ്പെട്ട കോളിന്റെ പൈപ്പ്ലൈൻ-തല പിശക് വിശദാംശങ്ങൾ            |
| `bodies_truncated`               | മുകളിലെ ഏതെങ്കിലും ഫീൽഡ് `maxBodyBytes` പരിധിയിലെത്തുമ്പോൾ True |

ഇത് പ്രോംപ്റ്റ് ഉള്ളടക്കമായതിനാൽ, ഇത് **ഡിഫോൾട്ടായി ഓഫാണ്**, കൂടാതെ മനഃപൂർവം ഓരോ ലക്ഷ്യസ്ഥാനത്തിനും പ്രത്യേകം തിരഞ്ഞെടുക്കാവുന്നതുമാണ്.
ഡാഷ്ബോർഡ് കാണിക്കുന്നതാണ് അയയ്ക്കപ്പെടുന്നത്, കാരണം എക്സ്പോർട്ടും `getCallLogById`-യും ഒരേ വിശദാംശ
റെസല്യൂഷൻ പങ്കിടുന്നു: പേലോഡുകൾ എഴുതപ്പെടുമ്പോൾ തന്നെ
PII-സാനിറ്റൈസ് ചെയ്യുകയും രഹസ്യങ്ങൾ റിഡാക്റ്റ് ചെയ്യുകയും ചെയ്യുന്നു; കൂടാതെ `noLog` API കീ ഉപയോഗിച്ച് നടത്തിയ കോൾ യാതൊരു പേലോഡും സംഭരിക്കാത്തതിനാൽ എക്സ്പോർട്ട് ചെയ്യാൻ ഒന്നുമുണ്ടാകില്ല.

ഫയൽസിസ്റ്റം ആർട്ടിഫാക്റ്റിൽ നിന്ന് ഓരോ റോ അടിസ്ഥാനത്തിലുമാണ് പേലോഡുകൾ വായിക്കുന്നത്, അതിനാൽ അവ ആവശ്യപ്പെട്ട ലക്ഷ്യസ്ഥാനങ്ങൾക്കായി മാത്രമേ
ഹൈഡ്രേഷൻ പ്രവർത്തിക്കൂ. ആർട്ടിഫാക്റ്റ് നഷ്ടപ്പെട്ടതോ കേടായതോ ആണെങ്കിൽ, ബാച്ച് പരാജയപ്പെടുത്തുകയും കർസർ കുടുങ്ങിപ്പോകുകയും ചെയ്യുന്നതിനുപകരം null പേലോഡുകളോടുകൂടിയ അതിന്റെ സംഗ്രഹം എക്സ്പോർട്ട് ചെയ്യും.

`maxBodyBytes` (ഡിഫോൾട്ട് 262144) ഓരോ ഫീൽഡിനും പരമാവധി പരിധി നിശ്ചയിക്കുന്നു. നീളം കൂടിയ പേലോഡുകൾ ഒഴിവാക്കുന്നതിനുപകരം **ട്രങ്കേറ്റ് ചെയ്യപ്പെടുന്നു** — ക്ലിപ്പ് ചെയ്ത പ്രോംപ്റ്റും "എന്താണ് ചോദിച്ചത്" എന്നതിന് ഉത്തരം നൽകുന്നു — കൂടാതെ റോ `bodies_truncated` ഉപയോഗിച്ച്
ഫ്ലാഗ് ചെയ്യപ്പെടുന്നു. ചങ്ക്-ബൈ-ചങ്ക് സ്ട്രീം ചെയ്ത ഡെൽറ്റകൾ എക്സ്പോർട്ട് ചെയ്യില്ല; അസംബിൾ ചെയ്ത പ്രതികരണം ഇതിനകം
`pipeline_provider_response`-ലും `pipeline_client_response`-ലും ഉണ്ട്.

## 4. BigQuery ഡെസ്റ്റിനേഷൻ

കോൺഫിഗ് കീകൾ (`type: "bigquery"`):

| കീ                   | കുറിപ്പുകൾ                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------------- |
| `projectId`          | ഡാറ്റാസെറ്റ് ഉൾക്കൊള്ളുന്ന GCP പ്രോജക്റ്റ്                                                    |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                               |
| `tableId`            | `[A-Za-z0-9_]+`                                                                               |
| `location`           | ഡാറ്റാസെറ്റ് സൃഷ്ടിക്കേണ്ടിവരുമ്പോൾ മാത്രം ഉപയോഗിക്കുന്നു (ഡിഫോൾട്ട് `EU`)                    |
| `serviceAccountJson` | സർവീസ്-അക്കൗണ്ട് കീ. സീക്രട്ട്: സംഭരിക്കുമ്പോൾ എൻക്രിപ്റ്റ് ചെയ്യും, ഒരിക്കലും തിരികെ നൽകില്ല |
| `autoCreate`         | ആദ്യ എക്സ്പോർട്ടിൽ ഡാറ്റാസെറ്റും ടേബിളും സൃഷ്ടിക്കുക (ഡിഫോൾട്ട് `true`)                       |

സർവീസ് അക്കൗണ്ടിന് ടാർഗറ്റ് ടേബിളിൽ `bigquery.tables.updateData` ആവശ്യമാണ്; കൂടാതെ
`autoCreate` ഓണായിരിക്കുമ്പോൾ `bigquery.datasets.create` / `bigquery.tables.create` എന്നിവയും ആവശ്യമാണ്.

കോൺഫിഗർ ചെയ്ത ബാച്ച് ഒരു **കർസർ** യൂണിറ്റാണ്, HTTP യൂണിറ്റല്ല: `send()` അതിനെ പരമാവധി 500 റോകളുള്ള
insertAll കോളുകളായി വിഭജിക്കുന്നു, അതിനാൽ വലിയ `batch_size` BigQuery-യുടെ 10 MB റിക്വസ്റ്റ് പരിധി ലംഘിക്കില്ല.
താൽക്കാലിക സ്റ്റാറ്റസുകൾ (408/429/500/502/503/504), അതേ insertIds വീണ്ടും ഉപയോഗിച്ചുകൊണ്ട്, എക്സ്പോണൻഷ്യൽ
ബാക്ക്ഓഫോടെ പരമാവധി മൂന്ന് തവണ റീട്രൈ ചെയ്യും; റൺ പാഴാക്കുന്നതിനു പകരം ഓത്ത്, സ്കീമ പരാജയങ്ങൾ ആദ്യ ശ്രമത്തിൽ
തന്നെ എറർ ത്രോ ചെയ്യും.

നിമിഷങ്ങൾക്ക് മുമ്പ് സൃഷ്ടിച്ച ടേബിൾ സ്ട്രീമിംഗ് എൻഡ്പോയിന്റിൽ ഉടൻ ദൃശ്യമാകില്ല, അതിനാൽ ഏതാനും സെക്കൻഡുകൾ
അത് 404 നൽകും. ആ 404 റീട്രൈ ചെയ്യും, എന്നാൽ **ഈ റൺ ടേബിൾ സൃഷ്ടിച്ചപ്പോൾ മാത്രം** —
യഥാർത്ഥത്തിൽ ടേബിൾ ഇല്ലെങ്കിൽ ഉടൻ പരാജയപ്പെടും. അടുത്തിടെ ഇല്ലാതാക്കിയ ടേബിളിന്റെ അതേ പേരിൽ വീണ്ടും ടേബിൾ
സൃഷ്ടിക്കുന്നത് ഏതാനും മിനിറ്റുകൾ സ്ട്രീമിംഗ് ഇൻസേർട്ടുകൾ നിരസിക്കാൻ BigQuery-യെ പ്രേരിപ്പിക്കുമെന്നത് ശ്രദ്ധിക്കുക;
ഇത് ഡിലീറ്റ്-ചെയ്ത്-വീണ്ടും-സൃഷ്ടിക്കുന്നതിന്റെ സ്വഭാവമാണ്, അതിനാൽ ഒരെണ്ണം ഡ്രോപ്പ് ചെയ്ത് വീണ്ടും ചേർക്കുന്നതിനേക്കാൾ
പുതിയ ടേബിൾ പേര് തിരഞ്ഞെടുക്കുക.

**ഭാഗിക പരാജയം, ശൂന്യമല്ലാത്ത `insertErrors[]` സഹിതം HTTP 200 ആയി ലഭിക്കും.** അതിനെ പരാജയമായി
കണക്കാക്കി എറർ ത്രോ ചെയ്യും; BigQuery ഒരിക്കലും സ്വീകരിക്കാത്ത റോകൾക്ക് അപ്പുറത്തേക്ക് കർസർ നീങ്ങുന്നത് ഇതാണ്
തടയുന്നത്; `tests/unit/log-export-bigquery.test.ts` ഈ സ്വഭാവം ഉറപ്പിക്കുന്നു.

ട്രാൻസ്പോർട്ട് പ്ലെയിൻ REST ആണ് — സ്വയം സൈൻ ചെയ്ത RS256 അസർഷൻ
`https://oauth2.googleapis.com/token`-ൽ ഒരു ആക്സസ് ടോക്കണായി എക്സ്ചേഞ്ച് ചെയ്യുന്നു, തുടർന്ന് റോകൾ
`tabledata.insertAll`-ലേക്ക് പോകുന്നു. Google SDK ഉൾപ്പെടുത്തുന്നില്ല. ഓരോ (സർവീസ് അക്കൗണ്ട്, സ്കോപ്പ്)
ജോഡിക്കും ആക്സസ് ടോക്കണുകൾ ഇൻ-പ്രോസസായി കാഷ് ചെയ്യുന്നു.

സൃഷ്ടിച്ച ടേബിളിൽ Logs-ടാബിലെ ഓരോ ഫീൽഡിനും ഓരോ കോളവും കൂടാതെ `exported_at`-ഉം ഉണ്ടായിരിക്കും; കോൾ ലോഗുകൾ
യഥാർത്ഥത്തിൽ ക്വറി ചെയ്യുന്ന രീതിക്കനുസരിച്ചാണ് അത് ക്രമീകരിച്ചിരിക്കുന്നത്:

- **`timestamp` അടിസ്ഥാനമാക്കി ദിവസം തിരിച്ചുള്ള പാർട്ടീഷനിംഗ്**, അതിനാൽ തീയതിയാൽ പരിമിതപ്പെടുത്തിയ ക്വറി ആ ദിവസങ്ങൾ മാത്രം സ്കാൻ ചെയ്യും.
- **`api_key_name`, `provider`, `model`, `status` എന്നിവയാൽ ക്ലസ്റ്റർ ചെയ്തത്** (ആ ക്രമത്തിൽ), അതിനാൽ
  ആരാണ് അത് റൺ ചെയ്തത്, അത് എവിടേക്കാണ് പോയത്, അല്ലെങ്കിൽ അത് പരാജയപ്പെട്ടോ എന്നിവ ഉപയോഗിച്ചുള്ള ഫിൽട്ടറിംഗ് ഓരോ
  പാർട്ടീഷനിലെയും ബ്ലോക്കുകൾ പ്രൂൺ ചെയ്യും. BigQuery പരമാവധി നാല് ക്ലസ്റ്ററിംഗ് കോളങ്ങൾ അനുവദിക്കുന്നു, കൂടാതെ ക്രമം
  പ്രധാനമാണ്: `api_key_name` മാത്രം ഉപയോഗിച്ചുള്ള ഫിൽട്ടർ പ്രൂൺ ചെയ്യും, `status` മാത്രം ഉപയോഗിച്ചുള്ള ഫിൽട്ടർ പ്രൂൺ ചെയ്യില്ല.
- **`partitionExpirationDays` വഴിയുള്ള ഓപ്ഷണൽ പാർട്ടീഷൻ നിലനിർത്തൽ** (0 എല്ലാം നിലനിർത്തും), ടേബിൾ
  സൃഷ്ടിക്കുമ്പോൾ പ്രയോഗിക്കുന്നു.

ഈ രണ്ട് ക്രമീകരണങ്ങളും സൃഷ്ടിക്കുന്ന സമയത്താണ് ബാധകമാകുന്നത്. നിലവിലുള്ള ഒരു പട്ടിക അതിന് ഇതിനകം ഉള്ള ലേഔട്ട് നിലനിർത്തും, അതിനാൽ
ഇവ സ്വീകരിക്കണമെങ്കിൽ ലക്ഷ്യസ്ഥാനം ഒരു പുതിയ പട്ടിക id-ലേക്ക് ചൂണ്ടുക.

മാപ്പറും പട്ടിക സ്കീമയും ഒരേ ക്രമത്തിൽ തുടരുന്നുവെന്ന് `tests/unit/log-export-bigquery.test.ts` ഉറപ്പാക്കുന്നു,
അതിനാൽ പുറത്തേക്ക് അയയ്ക്കുന്നതിനിടെ ഒരു പുതിയ call-log കോളം നിശ്ശബ്ദമായി ഒഴിവാക്കാനാവില്ല.

ബാച്ചുകൾ **രണ്ടും**—വരി എണ്ണവും സീരിയലൈസ് ചെയ്ത ബൈറ്റുകളും—അടിസ്ഥാനമാക്കി ചങ്കുകളായി വിഭജിക്കുന്നു. പേലോഡുകൾ എക്സ്പോർട്ട് ചെയ്തുകഴിഞ്ഞാൽ
വരി എണ്ണം മാത്രം മതിയാകില്ല: പ്രോംപ്റ്റുകൾ ഉൾക്കൊള്ളുന്ന 500 വരികൾക്ക് പതിനായിരക്കണക്കിന് മെഗാബൈറ്റുകൾ വലുപ്പമുണ്ടാകാം, കൂടാതെ 10 MB-യിൽ കൂടുതലുള്ള
ഒരു അഭ്യർത്ഥന insertAll നിരസിക്കും. ആദ്യം ഏത് പരിധിയിലെത്തുന്നുവോ അതനുസരിച്ച്, 500 വരികളിലോ 9 MB-യിലോ ചങ്കുകൾ അവസാനിപ്പിക്കും.

## 5. ഒരു destination ചേർക്കൽ

1. `LogExportDestinationType` export ചെയ്യുന്ന `src/lib/logExport/destinations/<name>.ts` സൃഷ്ടിക്കുക:
   ഒരു Zod `configSchema`, UI-യ്ക്കായുള്ള ഒരു `fields` descriptor array, `secretFields`, കൂടാതെ
   `test()` / `prepare()` / `send(records)` നൽകുന്ന ഒരു `createClient(config)`.
2. `src/lib/logExport/registry.ts`-ലെ `DESTINATIONS` array-യിലേക്ക് അത് ചേർക്കുക.
3. `tests/unit/`-ന് കീഴിൽ tests എഴുതുക.

മാറ്റം ഇത്രമാത്രമാണ്: persistence, cron job, REST layer, secret encryption, dashboard form എന്നിവയെല്ലാം registry വായിക്കുന്നു.

ഒരു പുതിയ destination-നുള്ള രണ്ട് നിയമങ്ങൾ:

- ഭാഗിക പരാജയം സംഭവിക്കുമ്പോൾ `send()` **നിർബന്ധമായും throw ചെയ്യണം**. Resolve ചെയ്യുന്നത് "destination-ൽ ഈ rows ഉണ്ട്" എന്നാണ് അർത്ഥമാക്കുന്നത്,
  തുടർന്ന് cursor അവയെ ശാശ്വതമായി മറികടന്ന് മുന്നോട്ട് നീങ്ങും.
- ഉപയോക്താവ് നൽകുന്ന URL സ്വീകരിക്കുന്ന destination, fetch ചെയ്യുന്നതിന് മുമ്പ്
  webhooks ചെയ്യുന്നതുപോലെതന്നെ, `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) വഴി അത് validate ചെയ്യണം.
  BigQuery-യ്ക്ക് ഇത് ആവശ്യമില്ല: അതിന്റെ hosts constants ആണ്.

## 6. ഇത് പ്രവർത്തിപ്പിക്കൽ

- **Dashboard**: Integrations → Log export. ഒരു destination ചേർക്കുക, rows എഴുതാതെ credentials പരിശോധിക്കാൻ **Test** പ്രവർത്തിപ്പിക്കുക,
  തുടർന്ന് അത് enable ചെയ്യുക.
- **Backlog**: ഓരോ destination card-ഉം pending rows-ഉം cursor-ഉം കാണിക്കുന്നു; `GET
/api/log-export/status` അതേ കണക്കുകൾക്കൊപ്പം അവസാനത്തെ 20 job runs-ഉം നൽകുന്നു.
- **പരാജയപ്പെടുന്ന ഒരു destination മറ്റുള്ളവയെ പരാജയപ്പെടുത്തില്ല** — run summary ഓരോ destination-ന്റെയും
  status `last_status` / `last_error` എന്നിവയിൽ രേഖപ്പെടുത്തുന്നു, കൂടാതെ job run history aggregate സൂക്ഷിക്കുന്നു.
- **ഒരു destination delete ചെയ്യുന്നത് അതിന്റെ cursor-ഉം delete ചെയ്യും.** അത് വീണ്ടും ചേർക്കുമ്പോൾ നിലനിർത്തിയിട്ടുള്ളതിൽ ഏറ്റവും പഴയ
  call log മുതൽ ആരംഭിക്കും; ഇതുവഴി destination-ൽ ഇതിനകം ഉണ്ടായിരിക്കാവുന്ന rows വീണ്ടും അയയ്ക്കപ്പെടും. BigQuery-യിൽ ഓരോ row-യ്ക്കുമുള്ള
  `insertId`, BigQuery-യുടെ സ്വന്തം de-duplication window-യ്ക്കുള്ളിൽ മാത്രമേ ഇത് കൈകാര്യം ചെയ്യൂ; അതിനാൽ destination delete ചെയ്യുന്നതിനെക്കാൾ
  disable ചെയ്യുന്നതാണ് അഭികാമ്യം.
