OmniRoute കോൾ ലോഗുകൾ ഒരു ബാഹ്യ അനലിറ്റിക്സ് സ്റ്റോറിലേക്ക് തുടർച്ചയായി, ഇൻക്രിമെന്റലായി എക്സ്പോർട്ട് ചെയ്യൽ.

ലോഗുകൾ ഡാഷ്ബോർഡ് ടാബ് അഭ്യർത്ഥനാ ചരിത്രം SQLite-ൽ (`call_logs`) സൂക്ഷിക്കുന്നു; റൊട്ടേഷനും
റിറ്റൻഷനും അതിന്റെ പരിധി നിർണയിക്കുന്നു. ലോഗ് എക്സ്പോർട്ട് അതേ റെക്കോർഡ് സെറ്റ് ഒരു ഷെഡ്യൂൾ പ്രകാരം പുറത്തേക്ക് അയയ്ക്കുന്നു. അതുവഴി അതിന്
ലോക്കൽ ഡാറ്റാബേസിനപ്പുറം നിലനിൽക്കാനും മറ്റ് ഡാറ്റയുമായി ജോയിൻ ചെയ്യപ്പെടാനും കഴിയും. BigQuery ആണ് ആദ്യ ലക്ഷ്യസ്ഥാനം;
പൈപ്പ്‌ലൈൻ ഒരു രജിസ്ട്രിയാണ്, അതിനാൽ കൂടുതൽ ലക്ഷ്യസ്ഥാനങ്ങൾ കൂട്ടിച്ചേർക്കാനാകും.

---

## 1. ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **ഷെഡ്യൂൾ** — ഒരു `JobRegistry` ക്രോൺ ജോബ്, `log_export`, ഡിഫോൾട്ടായി `0 * * * *` (മണിക്കൂറിൽ ഒരിക്കൽ,
  UTC). `src/lib/initCloudSync.ts`-ൽ രജിസ്റ്റർ ചെയ്തിരിക്കുന്നു; `OMNIROUTE_LOG_EXPORT_CRON` ഉപയോഗിച്ച് മാറ്റാം.
  ഓരോ ടിക്കിലും **പ്രവർത്തനക്ഷമമാക്കിയ** എല്ലാ ലക്ഷ്യസ്ഥാനങ്ങളിലേക്കുമുള്ള ശേഷിക്കുന്ന ഡാറ്റ ക്രമാനുസൃതമായി അയയ്ക്കുന്നു.
- **കർസർ** — SQLite-ന്റെ ഇംപ്ലിസിറ്റ് `call_logs.rowid`, ഓരോ ലക്ഷ്യസ്ഥാനത്തിനുമായി
  `log_export_destinations.cursor_row_id`-ൽ സൂക്ഷിക്കുന്നു. `timestamp` മനഃപൂർവം കർസറായി ഉപയോഗിക്കുന്നില്ല: കോളർമാർക്ക്
  സ്വന്തം മൂല്യം നൽകാനാകും. അതിനാൽ, വൈകി ആരംഭിച്ച വേഗമേറിയ അഭ്യർത്ഥനയ്ക്ക് ശേഷം മന്ദഗതിയിലുള്ള ഒരു അഭ്യർത്ഥന
  എഴുതപ്പെടാം; ടൈംസ്റ്റാമ്പ് കർസർ അതിനെ ഒഴിവാക്കും.
- **ബാച്ചിംഗ്** — ഓരോ അഭ്യർത്ഥനയിലും `batch_size` വരികൾ (ഡിഫോൾട്ട് 500), ഓരോ റണ്ണിലും `max_rows_per_run` വരികൾ
  (ഡിഫോൾട്ട് 10000). ഇതുവഴി വലിയ ബാക്ക്‌ലോഗ് ഒരു ടിക്കിനെ തടയുന്നതിനു പകരം നിരവധി ടിക്കുകളിലായി അയയ്ക്കപ്പെടുന്നു.
- **ഡെലിവറി** — `send()` വിജയകരമായി പൂർത്തിയായതിനുശേഷം മാത്രമേ കർസർ മുന്നോട്ട് നീങ്ങൂ. ഒരു ബാച്ച് പരാജയപ്പെട്ടാൽ
  കർസർ പഴയ സ്ഥാനത്തുതന്നെ തുടരും; അതിനാൽ അടുത്ത റണ്ണിൽ അതേ വരികൾ വീണ്ടും ശ്രമിക്കും. ഉറപ്പ്
  കുറഞ്ഞത് ഒരിക്കലെങ്കിലും ഡെലിവറിയും ലക്ഷ്യസ്ഥാനത്തെ ഡ്യൂപ്ലിക്കേറ്റ് നീക്കലുമാണ്, യഥാർത്ഥത്തിൽ കൃത്യം ഒരിക്കൽ മാത്രമുള്ള ഡെലിവറിയല്ല: BigQuery ഓരോ
  വരിക്കും കോൾ-ലോഗ് ഐഡി കീ ആയി ഉപയോഗിക്കുന്നു; സ്വന്തം ഡ്യൂപ്ലിക്കേറ്റ് നീക്കൽ സമയപരിധിക്കുള്ളിൽ സാധ്യമായത്ര മികച്ച രീതിയിൽ അത് മാനിക്കുന്നു.
- **ഓവർലാപ്പ് ഗാർഡ്** — ക്രോൺ ടിക്കും `POST .../run`-ഉം ഒരുമിച്ച് പ്രവർത്തിച്ചേക്കാം. ഇതിനകം
  ഡാറ്റ അയച്ചുകൊണ്ടിരിക്കുന്ന ലക്ഷ്യസ്ഥാനം രണ്ടാമതും അയയ്ക്കുന്നതിനു പകരം ഒഴിവാക്കുന്നു (റൺ ഫലത്തിൽ `skipped: true`),
  അതിനാൽ ഒരേസമയം നടക്കുന്ന റണ്ണിന് ഒരു ബാച്ച് വീണ്ടും അയയ്ക്കാനോ കർസർ പിന്നോട്ട് എഴുതാനോ കഴിയില്ല.
- **പർജിന് ശേഷമുള്ള വീണ്ടെടുക്കൽ** — `cursor_row_id`, `MAX(rowid)`-നെക്കാൾ ഉയർന്നതായാൽ (മുഴുവൻ ടേബിളും
  പർജ് ചെയ്യപ്പെടുകയും rowid-കൾ വീണ്ടും ആരംഭിക്കുകയും ചെയ്താൽ), റണ്ണർ സ്ഥിരമായി ഡാറ്റ കാണാതിരിക്കുന്നതിനു പകരം 0-ലേക്ക് മടങ്ങുന്നു.

### ഒറ്റപ്പെട്ട റണ്ണറും പരിധികളും

Node-ൽ ഓരോ ലക്ഷ്യസ്ഥാന റണ്ണും വേറിട്ട, ഹ്രസ്വകാല OS ചൈൽഡ് പ്രോസസ് ആരംഭിക്കുന്നു (IPC സഹിതമുള്ള `child_process`,
`worker_threads` അല്ല). ബോഡി വായനകൾ, പേലോഡ് JSON പാർസിംഗ്/സീരിയലൈസേഷൻ, ലക്ഷ്യസ്ഥാനത്തിന്റെ
`prepare()`, ലക്ഷ്യസ്ഥാന നെറ്റ്‌വർക്ക് I/O എന്നിവയെല്ലാം അവിടെയാണ് പ്രവർത്തിക്കുന്നത്; സെർവറിന്റെ ഇവന്റ് ലൂപ്പിലല്ല.
കോൺഫിഗറേഷനും ചെറിയ പുരോഗതി സന്ദേശങ്ങളും മാത്രമേ IPC വഴി കടന്നുപോകൂ; എക്സ്പോർട്ട് ചെയ്ത റെക്കോർഡുകൾ ഒരിക്കലും
സെർവറിലേക്ക് മടങ്ങുന്നില്ല. ക്രോൺ ജോബും ഇപ്പോൾ പ്രവർത്തിപ്പിക്കുക റൂട്ടും അതേ പബ്ലിക് ഫലവും ഓവർലാപ്പ് ഗാർഡും നിലനിർത്തുന്നു.

ചൈൽഡ്, സെർവർ നിർണയിച്ച `DATA_DIR/storage.sqlite`, `node:sqlite` ഉപയോഗിച്ച് റീഡ്-ഒൺലി ആയി തുറക്കുന്നു,
`busy_timeout=5000`, `query_only=ON` എന്നിവയോടെ. അത് DB സിംഗിൾട്ടൺ ഇംപോർട്ട് ചെയ്യുന്നില്ല;
മൈഗ്രേഷനുകളോ ബാക്കപ്പുകളോ SQLite അപ്‌ഡേറ്റുകളോ നടത്തുന്നുമില്ല. കാണാതായ/കേടായ ആർട്ടിഫാക്റ്റുകളുടെ ബുക്ക്‌കീപ്പിംഗ് (കേടായ
ആർട്ടിഫാക്റ്റിനുള്ള UPDATE ഉൾപ്പെടെ) ഡാഷ്ബോർഡ് വിശദാംശ പാതയിൽ മാത്രം തുടരുന്നു. രണ്ട് പാതകളും ഒരു പ്യൂർ
ഡീറ്റെയിൽ റിസോൾവർ പങ്കിടുന്നു; എക്സ്പോർട്ട് അസിങ്ക്രണസ് ഫയൽസിസ്റ്റം വായനകളും അതേ ആർട്ടിഫാക്റ്റ് → ലെഗസി
ഇൻലൈൻ → ലെഗസി ഡിസ്ക് → ഒന്നുമില്ല എന്ന റിസല്യൂഷൻ ക്രമവും ഉപയോഗിക്കുന്നു. ചൈൽഡ് റീഡർ തുറക്കുമ്പോൾ ഒരു റൺ പരമാവധി ഇൻസർഷൻ rowid-ന്റെ
സ്നാപ്ഷോട്ട് എടുക്കുന്നു; പിന്നീടുള്ള ഇൻസേർട്ടുകൾ അടുത്ത റൺ വരെ കാത്തിരിക്കും. ഇത് ഒരു ഇൻസർഷൻ
അതിർത്തിയാണ്, ദീർഘകാല SQLite ട്രാൻസാക്ഷനല്ല: നെറ്റ്‌വർക്ക് കാത്തിരിപ്പുകൾക്കിടയിൽ WAL റൈറ്ററുകൾക്കും ചെക്ക്‌പോയിന്റുകൾക്കും തടസ്സമില്ല.
നിലവിലുള്ള വരികളുടെ അപ്‌ഡേറ്റുകൾ/ഇല്ലാതാക്കലുകൾ ഈ അതിർത്തി തടഞ്ഞുനിർത്തുന്നില്ല.

സ്വീകരിച്ച ഓരോ ബാച്ചിനുശേഷവും ചൈൽഡ് ഒരു സ്ഥിരീകരണത്തിനായി കാത്തിരിക്കുന്നു. സെർവർ ആദ്യം
`advanceLogExportCursor` ഉപയോഗിച്ച് കർസർ സൂക്ഷിച്ചശേഷം `ack` അയയ്ക്കുന്നു; അതിനു മുമ്പ് അടുത്ത ബാച്ച് ആരംഭിക്കില്ല.
അയയ്ക്കൽ പരാജയമോ ക്രാഷോ ടൈംഔട്ടോ ഉണ്ടായാൽ ആ ബാച്ചിന്റെ കർസർ മുന്നോട്ട് നീക്കാതെ പരാജയം രേഖപ്പെടുത്തുന്നു. നേരത്തെ
സ്ഥിരീകരിച്ച ബാച്ചുകൾ കമ്മിറ്റ് ചെയ്ത നിലയിൽ തുടരും; സ്ഥിരീകരിക്കാത്ത ആ ഒരു ബാച്ച് മാത്രമേ പരമാവധി വീണ്ടും അയയ്ക്കപ്പെടാനാകൂ.
`done` ലഭിക്കുകയും ചൈൽഡ് വൃത്തിയായി എക്സിറ്റ് ചെയ്യുകയും ചെയ്തതിനുശേഷം മാത്രമേ വിജയം രേഖപ്പെടുത്തൂ. പരാജയങ്ങൾ ചൈൽഡിനെ
SIGTERM ഉപയോഗിച്ച് അവസാനിപ്പിക്കുന്നു; 500 ms-നുശേഷം SIGKILL-ലേക്ക് ഉയർത്തുന്നു. പ്രോസസ് അടയുന്നതുവരെ റണ്ണർ കാത്തിരിക്കുന്നു.

| എൻവയോൺമെന്റ് വേരിയബിൾ                         | ഡിഫോൾട്ട് | ഉദ്ദേശ്യം                                   |
| --------------------------------------------- | --------- | ------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000    | ഓരോ ലക്ഷ്യസ്ഥാനത്തിനുമുള്ള യഥാർത്ഥ സമയപരിധി |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024      | ചൈൽഡ് V8 old-space പരിധി MB-യിൽ             |

അസാധുവായ/പോസിറ്റീവ് അല്ലാത്ത/പൂർണസംഖ്യയല്ലാത്ത മൂല്യങ്ങൾക്ക് ഡിഫോൾട്ടുകൾ ഉപയോഗിക്കുന്നു. ഹീപ്പ് ക്രമീകരണം മൊത്തം
RSS പരിധിയല്ല; വളരെ വലിയ ബാച്ചുകൾക്ക് ഇപ്പോഴും ചൈൽഡ് മെമ്മറി തീർക്കാനും റൺ സുരക്ഷിതമായി പരാജയപ്പെടുത്താനും കഴിയും.
ബോഡികൾ പ്രവർത്തനക്ഷമമാക്കിയ 512 KiB ആർട്ടിഫാക്റ്റുകളുടെ ഡിഫോൾട്ട് 500-വരി ബാച്ചിന് 1024 MB ഡിഫോൾട്ട് അധിക ഇടം നൽകുന്നു;
BigQuery-യുടെ ബൈറ്റ്-ചങ്ക് ചെയ്ത JSON സീരിയലൈസേഷനും ഇതിൽ ഉൾപ്പെടുന്നു. ഇത്
10000-വരി ബോഡി ബാച്ചിനെ സുരക്ഷിതമാക്കുന്നില്ല. V8 ഹീപ്പ് തീരുന്നത് പരിഹാരനടപടി സ്വീകരിക്കാവുന്ന ഒരു പരാജയം രേഖപ്പെടുത്തുന്നു: ബാച്ച്
വലുപ്പം കുറയ്ക്കുക അല്ലെങ്കിൽ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` വർധിപ്പിക്കുക; കർസർ അവസാനം
സ്ഥിരീകരിച്ച ബാച്ചിൽ തുടരും. പഴയ ഇൻലൈൻ/ഡിസ്ക് ബോഡികൾ ആധുനിക ആർട്ടിഫാക്റ്റ് പരിധിയിൽ ഉൾപ്പെടുന്നില്ല.
ഓപ്പറേറ്റർമാർ RSS-നായി പ്രത്യേകം ബജറ്റ് നിശ്ചയിക്കണം, പ്രത്യേകിച്ച് മെമ്മറി പരിമിതപ്പെടുത്തിയ കണ്ടെയ്‌നറുകളിൽ.

ചൈൽഡിന് പരിഹരിച്ച `DATA_DIR`, `NODE_ENV`, വ്യക്തമായി നൽകിയ `TZ` (ലെഗസി ഫയൽനാമത്തിന്റെ
പ്രാദേശിക-സമയ നിർണയം), ലഭ്യമാണെങ്കിൽ `ELECTRON_RUN_AS_NODE`, കൂടാതെ ഇനിപ്പറയുന്ന ഔട്ട്ബൗണ്ട് ഇൻപുട്ടുകൾ എന്നിവ മാത്രമേ പാരമ്പര്യമായി ലഭിക്കൂ:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (അവയുടെ ചെറിയക്ഷര രൂപങ്ങളും),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
ഒരു ആഗോള Undici ഡിസ്പാച്ചർ, `NO_PROXY` ഉൾപ്പെടെ, സെർവറിന്റെ പരിസ്ഥിതി-പ്രോക്സി നിർണയവും ലോക്കൽ-ഹോസ്റ്റ്
ബൈപാസ് നിയമങ്ങളും അതേപടി പങ്കിടുന്നു; അത് `proxyFetch.ts` അല്ലെങ്കിൽ അതിന്റെ DB/ഫീച്ചർ ഫ്ലാഗുകൾ ഇംപോർട്ട് ചെയ്യുന്നില്ല.
ഫോർവേഡ് ചെയ്യുന്ന ഔട്ട്പുട്ടിൽനിന്നും രേഖപ്പെടുത്തുന്ന പിശകുകളിൽനിന്നും പ്രോക്സി ക്രെഡൻഷ്യലുകൾ മറയ്ക്കുന്നു. ഡെസ്റ്റിനേഷൻ ക്രെഡൻഷ്യലുകൾ
ഒരു ആരംഭ IPC സന്ദേശത്തിലൂടെ മാത്രമേ കൈമാറൂ; argv വഴിയോ എൻവയോൺമെന്റ് വഴിയോ ഒരിക്കലും കൈമാറില്ല; ഔട്ട്പുട്ട്/പിശക് ഫോർവേഡിംഗിൽ
പ്രിഫിക്സ് ചേർക്കുകയും ശുദ്ധീകരിക്കുകയും ചെയ്യുന്നു. ഓരോ cron റണ്ണിലും Node-ന്റെ SQLite മുന്നറിയിപ്പ്
ആവർത്തിക്കാതിരിക്കാൻ ചൈൽഡ് exec ആർഗ്യുമെന്റുകളിൽ `ExperimentalWarning` മാത്രം പ്രവർത്തനരഹിതമാക്കുന്നു; മറ്റ് മുന്നറിയിപ്പ് തരങ്ങൾ ദൃശ്യമായി തുടരും.

Next.js/server-only ഡിപെൻഡൻസികളില്ലാതെ ഡെസ്റ്റിനേഷൻ മൊഡ്യൂളുകൾ ഇംപോർട്ട് ചെയ്യാൻ കഴിയണം. നിലവിലുള്ള
BigQuery ഇംപ്ലിമെന്റേഷൻ ഇതിനകം ആ വ്യവസ്ഥ പാലിക്കുന്നു. ആക്സസ്-ടോക്കൺ കാഷുകൾ ചൈൽഡ്
റണ്ണിന്റെ കാലയളവിൽ മാത്രമേ നിലനിൽക്കൂ; റണ്ണുകൾക്കിടയിൽ നിലനിൽക്കില്ല. പിന്തുണയ്ക്കുന്ന റൺടൈം Node ആണ് (`package.json` engines), എന്നാൽ README-യിലെ Bun
ഇൻസ്റ്റലേഷൻ വിഭാഗവും `Dockerfile.bun`-ഉം `bun:sqlite` (`src/lib/db/core.ts` / അഡാപ്റ്ററുകൾ) ഉപയോഗിച്ചുള്ള
ഒരു പ്രൊഡക്ഷൻ അനുയോജ്യതാ മാർഗവും അവതരിപ്പിക്കുന്നു. അതിനാൽ Bun-ൽ, എക്സ്പോർട്ടുകൾ മുമ്പത്തെ
ഇൻ-പ്രോസസ് മാർഗം നിലനിർത്തുകയും ഒറ്റത്തവണ മുന്നറിയിപ്പ് പുറപ്പെടുവിക്കുകയും ചെയ്യുന്നു: ചൈൽഡ് ഹീപ്പ്/ടൈംഔട്ട് ഐസൊലേഷൻ ലഭ്യമല്ല. ഇവന്റ്-ലൂപ്പ്, OOM ഐസൊലേഷനായി
Node ഉപയോഗിക്കുക; ഇവിടെ Bun-നെ ഡെവലപ്മെന്റിന് മാത്രമുള്ളതായി കണക്കാക്കുന്നില്ല.

`includeBodies` പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, മണിക്കൂറിലൊരിക്കലുള്ള പേലോഡ് ബാക്ക്‌ലോഗ് കൂട്ടിവയ്ക്കുന്നതിനുപകരം
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` പോലുള്ള മിനിറ്റ്-തല ആവർത്തനക്രമം തിരഞ്ഞെടുക്കുക.
ബാച്ച്, വരി പരിധികൾ ഓരോ റണ്ണിനെയും തുടർന്നും നിയന്ത്രിക്കുന്നു. ഓരോ റണ്ണിലും ഓരോ ഡെസ്റ്റിനേഷനും
പ്രോസസ് ആരംഭിക്കുന്നതിനുള്ള ചെലവുണ്ട്; ചെറിയൊരു സ്റ്റാർട്ടപ്പ് ചെലവിന് പകരമായി സെർവർ ഇവന്റ്-ലൂപ്പ് ഐസൊലേഷനാണ്
ഇതിലൂടെ ലഭിക്കുന്നത്, മൊത്തം CPU ഉപയോഗത്തിലെ കുറവല്ല.

### പേലോഡുകൾ (പ്രോംപ്റ്റുകളും പൂർത്തീകരണങ്ങളും)

ഡിഫോൾട്ടായി, ലോഗുകളുടെ **പട്ടിക** കാണിക്കുന്ന സംഗ്രഹ ഫീൽഡുകൾ മാത്രമേ എക്സ്പോർട്ടിൽ ഉൾപ്പെടൂ.
**പ്രോംപ്റ്റുകളും പ്രതികരണങ്ങളും എക്സ്പോർട്ട് ചെയ്യുക** (`includeBodies`) പ്രവർത്തനക്ഷമമാക്കിയാൽ, ഓരോ കോളിനും ലോഗുകളുടെ **വിശദാംശ**
പാനൽ കാണിക്കുന്നവയും അധികമായി അയയ്ക്കുന്നു:

| ഫീൽഡ്                            | അതിൽ അടങ്ങിയിരിക്കുന്നത്                                         |
| -------------------------------- | ---------------------------------------------------------------- |
| `request_body` / `response_body` | ഡാഷ്ബോർഡ് പ്രദർശിപ്പിക്കുന്ന രൂപത്തിലുള്ള കോൾ പേലോഡുകൾ           |
| `pipeline_route_decision`        | റൂട്ടർ തിരഞ്ഞെടുത്ത ടാർഗെറ്റും മോഡലും                            |
| `pipeline_client_request`        | ക്ലയന്റ് അയച്ച അതേ രൂപത്തിലുള്ള അസംസ്കൃത അഭ്യർത്ഥന               |
| `pipeline_openai_request`        | ആന്തരിക OpenAI രൂപത്തിലേക്ക് പരിഭാഷപ്പെടുത്തിയതിനുശേഷമുള്ളത്     |
| `pipeline_provider_request`      | പ്രൊവൈഡറുടെ രൂപത്തിൽ യഥാർത്ഥത്തിൽ അപ്സ്ട്രീമിലേക്ക് അയച്ചത്      |
| `pipeline_provider_response`     | അസംസ്കൃത അപ്സ്ട്രീം പ്രതികരണം                                    |
| `pipeline_client_response`       | കോളറിന് തിരികെ നൽകിയതെന്തോ അത്                                   |
| `pipeline_error`                 | പരാജയപ്പെട്ട കോളിന്റെ പൈപ്പ്‌ലൈൻ-തല പിശക് വിശദാംശങ്ങൾ            |
| `bodies_truncated`               | മുകളിലുള്ള ഏതെങ്കിലും ഫീൽഡ് `maxBodyBytes` പരിധിയിലെത്തിയാൽ True |

ഇത് പ്രോംപ്റ്റ് ഉള്ളടക്കമായതിനാൽ, **ഡിഫോൾട്ടായി ഓഫാണ്**, കൂടാതെ മനഃപൂർവം ഓരോ ഡെസ്റ്റിനേഷനും പ്രത്യേകം തിരഞ്ഞെടുക്കേണ്ടതുമാണ്.
ഡാഷ്ബോർഡ് കാണിക്കുന്നതാണ് അയയ്ക്കുന്നത്, കാരണം എക്സ്പോർട്ടും `getCallLogById`-ഉം ഒരേ വിശദാംശ
നിർണയം പങ്കിടുന്നു: പേലോഡുകൾ
എഴുതുമ്പോൾ തന്നെ PII ശുദ്ധീകരിക്കുകയും രഹസ്യങ്ങൾ മറയ്ക്കുകയും ചെയ്തിരിക്കും; കൂടാതെ
`noLog` API കീ ഉപയോഗിച്ച് നടത്തുന്ന കോൾ പേലോഡൊന്നും സംഭരിക്കില്ല, അതിനാൽ എക്സ്പോർട്ട് ചെയ്യാൻ ഒന്നുമുണ്ടാകില്ല.

ഫയൽസിസ്റ്റം ആർട്ടിഫാക്റ്റിൽനിന്ന് ഓരോ വരിയുടെയും പേലോഡുകൾ വായിക്കുന്നു, അതിനാൽ ഹൈഡ്രേഷൻ ആവശ്യപ്പെട്ട
ഡെസ്റ്റിനേഷനുകൾക്കായി മാത്രമേ അത് പ്രവർത്തിക്കൂ. ആർട്ടിഫാക്റ്റ് നഷ്ടപ്പെട്ടതോ കേടായതോ ആണെങ്കിൽ, ബാച്ച് പരാജയപ്പെടുത്തുകയും
കർസറിനെ കുടുക്കുകയും ചെയ്യുന്നതിനുപകരം, null പേലോഡുകളോടെ അതിന്റെ സംഗ്രഹം എക്സ്പോർട്ട് ചെയ്യുന്നു.

`maxBodyBytes` (ഡിഫോൾട്ട് 262144) ഓരോ ഫീൽഡിനും പരിധി നിശ്ചയിക്കുന്നു. നീളമേറിയ പേലോഡുകൾ **ഒഴിവാക്കുന്നതിനുപകരം
വെട്ടിച്ചുരുക്കുന്നു** — വെട്ടിച്ചുരുക്കിയ പ്രോംപ്റ്റ് പോലും "എന്താണ് ചോദിച്ചത്" എന്നതിന് ഉത്തരം നൽകും — കൂടാതെ ആ വരിക്ക്
`bodies_truncated` ഫ്ലാഗ് നൽകുന്നു. സ്ട്രീം ചെയ്യുന്ന ചങ്ക്-ബൈ-ചങ്ക് ഡെൽറ്റകൾ എക്സ്പോർട്ട് ചെയ്യുന്നില്ല; സംയോജിപ്പിച്ച പ്രതികരണം
ഇതിനകം `pipeline_provider_response`, `pipeline_client_response` എന്നിവയിലുണ്ട്.

## 3. REST API

എല്ലാ റൂട്ടുകൾക്കും മാനേജ്മെന്റ് പ്രാമാണീകരണം ആവശ്യമാണ് (`requireManagementAuth`). രഹസ്യങ്ങൾ ഒരിക്കലും തിരികെ നൽകില്ല:
സംഭരിച്ച രഹസ്യത്തിന് പകരം `__stored__` എന്ന ലിറ്ററൽ തിരികെ ലഭിക്കും; അപ്ഡേറ്റിൽ ആ മൂല്യം തിരികെ അയച്ചാൽ
സംഭരിച്ച ക്രെഡൻഷ്യൽ നിലനിർത്തും.

രഹസ്യം പ്രഖ്യാപിക്കുന്ന തരത്തിലുള്ള ലക്ഷ്യസ്ഥാനം സൃഷ്ടിക്കാനോ അപ്ഡേറ്റ് ചെയ്യാനോ **`STORAGE_ENCRYPTION_KEY`
ആവശ്യമാണ്**. അതില്ലെങ്കിൽ `encrypt()` ഒന്നും ചെയ്യാതെ ഡാറ്റ അതേപടി കടത്തിവിടും. അതിനാൽ SQLite-ൽ ക്രെഡൻഷ്യൽ
പ്ലെയിൻടെക്സ്റ്റായി സംഭരിക്കുന്നതിനുപകരം 400 നൽകി എഴുത്ത് നിരസിക്കും (Telegram webhook-ലും

## 4. BigQuery ലക്ഷ്യസ്ഥാനം

കോൺഫിഗറേഷൻ കീകൾ (`type: "bigquery"`):

| കീ                   | കുറിപ്പുകൾ                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `projectId`          | ഡാറ്റാസെറ്റ് ഉൾക്കൊള്ളുന്ന GCP പ്രോജക്റ്റ്                                                   |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                              |
| `tableId`            | `[A-Za-z0-9_]+`                                                                              |
| `location`           | ഡാറ്റാസെറ്റ് സൃഷ്ടിക്കേണ്ടിവരുമ്പോൾ മാത്രം ഉപയോഗിക്കുന്നു (സ്ഥിരസ്ഥിതി `EU`)                 |
| `serviceAccountJson` | സർവീസ്-അക്കൗണ്ട് കീ. രഹസ്യം: സംഭരണത്തിൽ എൻക്രിപ്റ്റ് ചെയ്തിരിക്കും, ഒരിക്കലും തിരികെ നൽകില്ല |
| `autoCreate`         | ആദ്യ എക്‌സ്‌പോർട്ടിൽ ഡാറ്റാസെറ്റും പട്ടികയും സൃഷ്ടിക്കുക (സ്ഥിരസ്ഥിതി `true`)                |

സർവീസ് അക്കൗണ്ടിന് ലക്ഷ്യ പട്ടികയിൽ `bigquery.tables.updateData` അനുമതി ആവശ്യമാണ്; കൂടാതെ
`autoCreate` ഓണായിരിക്കുമ്പോൾ `bigquery.datasets.create` / `bigquery.tables.create` അനുമതികളും ആവശ്യമാണ്.

കോൺഫിഗർ ചെയ്ത ബാച്ച് ഒരു **കർസർ** യൂണിറ്റാണ്, HTTP യൂണിറ്റല്ല: `send()` അതിനെ പരമാവധി 500 വരികൾ വീതമുള്ള insertAll
കോളുകളായി വിഭജിക്കുന്നു. അതിനാൽ വലിയ `batch_size` മൂലം BigQuery-യുടെ 10 MB അഭ്യർത്ഥനാ പരിധി ലംഘിക്കപ്പെടില്ല.
താൽക്കാലിക സ്റ്റാറ്റസുകൾക്ക് (408/429/500/502/503/504) എക്സ്പൊണൻഷ്യൽ
ബാക്ക്ഓഫ് ഉപയോഗിച്ച് പരമാവധി മൂന്ന് തവണ വീണ്ടും ശ്രമിക്കുന്നു; അതേ insertIds വീണ്ടും ഉപയോഗിക്കുന്നു. പ്രാമാണീകരണ, സ്കീമ പരാജയങ്ങൾ റൺ പാഴാക്കുന്നതിനുപകരം
ആദ്യ ശ്രമത്തിൽത്തന്നെ എക്സെപ്ഷൻ ഉയർത്തുന്നു.

അൽപ്പനേരം മുമ്പ് സൃഷ്ടിച്ച പട്ടിക സ്ട്രീമിംഗ് എൻഡ്‌പോയിന്റിന് ഉടൻ ദൃശ്യമാകില്ല; അത്
ഏതാനും സെക്കൻഡുകൾ 404 മറുപടി നൽകും. ആ 404-ന് വീണ്ടും ശ്രമിക്കും, എന്നാൽ **ഈ റൺ പട്ടിക സൃഷ്ടിച്ചിട്ടുണ്ടെങ്കിൽ മാത്രം** —
യഥാർത്ഥത്തിൽ നിലവിലില്ലാത്ത പട്ടികയുടെ കാര്യത്തിൽ ഉടൻ പരാജയപ്പെടും. അടുത്തിടെ ഇല്ലാതാക്കിയ പേരിൽ ഒരു പട്ടിക
വീണ്ടും സൃഷ്ടിച്ചാൽ BigQuery ഏതാനും മിനിറ്റുകൾ സ്ട്രീമിംഗ് ഇൻസേർട്ടുകൾ നിരസിക്കുമെന്നത് ശ്രദ്ധിക്കുക; ഇത്
ഇല്ലാതാക്കിയശേഷം വീണ്ടും സൃഷ്ടിക്കുന്നതിന്റെ സ്വഭാവമാണ്. അതിനാൽ പട്ടിക നീക്കി വീണ്ടും ചേർക്കുന്നതിനുപകരം പുതിയൊരു പട്ടികപ്പേര് ഉപയോഗിക്കുക.

**ഭാഗിക പരാജയം ശൂന്യമല്ലാത്ത `insertErrors[]` സഹിതം HTTP 200 ആയി ലഭിക്കുന്നു.** അതിനെ
പരാജയമായി കണക്കാക്കി എക്സെപ്ഷൻ ഉയർത്തുന്നു. BigQuery ഒരിക്കലും സ്വീകരിക്കാത്ത വരികൾക്കപ്പുറം കർസർ
മുന്നേറുന്നത് ഇതാണ് തടയുന്നത്; `tests/unit/log-export-bigquery.test.ts` ഈ പെരുമാറ്റം ഉറപ്പാക്കുന്നു.

ട്രാൻസ്‌പോർട്ട് സാധാരണ REST ആണ് — സ്വയം ഒപ്പിട്ട RS256 അസർഷൻ
`https://oauth2.googleapis.com/token`-ൽ ഒരു ആക്‌സസ് ടോക്കണായി കൈമാറുന്നു; തുടർന്ന് വരികൾ `tabledata.insertAll`-ലേക്ക് പോകുന്നു. Google SDK ഒന്നും
ഉൾപ്പെടുത്തുന്നില്ല. ഓരോ (സർവീസ് അക്കൗണ്ട്, സ്കോപ്പ്) ജോഡിക്കും ആക്‌സസ് ടോക്കണുകൾ പ്രോസസിനുള്ളിൽ കാഷ് ചെയ്യുന്നു.

സൃഷ്ടിച്ച പട്ടികയിൽ Logs ടാബിലെ ഓരോ ഫീൽഡിനും ഓരോ കോളവും കൂടാതെ `exported_at`-ഉം ഉണ്ടാകും. കോൾ ലോഗുകൾ
യഥാർത്ഥത്തിൽ ക്വറി ചെയ്യുന്ന രീതിക്ക് അനുയോജ്യമായാണ് ഇത് ക്രമീകരിച്ചിരിക്കുന്നത്:

  ആരാണ് പ്രവർത്തിപ്പിച്ചത്, എവിടേക്കാണ് പോയത്, പരാജയപ്പെട്ടോ എന്നിവ അടിസ്ഥാനമാക്കിയുള്ള ഫിൽട്ടറുകൾ ഓരോ പാർട്ടീഷനിലെയും അനാവശ്യ ബ്ലോക്കുകൾ ഒഴിവാക്കുന്നു. BigQuery
  പരമാവധി നാല് ക്ലസ്റ്ററിംഗ് കോളങ്ങൾ അനുവദിക്കുന്നു; അവയുടെ ക്രമം പ്രധാനമാണ്: `api_key_name` മാത്രം ഉപയോഗിച്ചുള്ള ഫിൽട്ടർ
  ബ്ലോക്കുകൾ ഒഴിവാക്കും, `status` മാത്രം ഉപയോഗിച്ചുള്ള ഫിൽട്ടർ അങ്ങനെ ചെയ്യില്ല.
- `partitionExpirationDays` വഴി **ഐച്ഛിക പാർട്ടീഷൻ നിലനിർത്തൽ കാലാവധി** (0 എല്ലാം നിലനിർത്തുന്നു), പട്ടിക

## 5. OTLP/HTTP ട്രേസുകളുടെ ലക്ഷ്യസ്ഥാനം

കോൺഫിഗിൽ `type: "otlp-http"` ഉപയോഗിക്കുന്നു. സ്ഥിരമായി സംഭരിച്ച കോൾ ലോഗുകളുടെ,
കർസർ അധിഷ്ഠിതവും ഷെഡ്യൂൾ ചെയ്തതുമായ എക്സ്പോർട്ടാണിത്; ഇത്
`open-sse/services/routing/otel.ts` എന്നതിലെ പരമാവധി ശ്രമാധിഷ്ഠിത തത്സമയ റൂട്ടിംഗ്-ഇവന്റ് സിങ്ക് അല്ല.
ആ സിങ്കിന്റെ എൻവയോൺമെന്റ് വേരിയബിളുകൾ, ടൈമറുകൾ, ബഫറുകൾ എന്നിവ ഇത് വായിക്കുകയോ മാറ്റുകയോ ചെയ്യുന്നില്ല.
രണ്ടും പ്രവർത്തനക്ഷമമാക്കിയാൽ സ്വതന്ത്രമായ രണ്ട് തരത്തിലുള്ള സ്പാനുകൾ ഉണ്ടാകാം;
ഈ കോൾ-ലോഗ് സ്പാനുകളെ തിരിച്ചറിയാൻ `omniroute.log-export` ഇൻസ്ട്രുമെന്റേഷൻ സ്കോപ്പ് ഉപയോഗിക്കുക.

ആട്രിബ്യൂട്ടുകളിൽ `gen_ai.operation.name="chat"`, ദാതാവ്, അഭ്യർത്ഥിച്ച/പ്രതികരണ മോഡൽ,
ഇൻപുട്ട്/ഔട്ട്പുട്ട് ടോക്കണുകൾ, ഐച്ഛികമായ cache-read/cache-creation/reasoning ടോക്കണുകൾ,
HTTP സ്റ്റാറ്റസ്, കോംബോ, കാഷ് സോഴ്സ്, സെഷൻ ടാഗ്, കോറിലേഷൻ ഐഡി എന്നിവ ഉൾപ്പെടുന്നു.
പൂർണ്ണസംഖ്യയായ OTLP മൂല്യങ്ങളും ടൈംസ്റ്റാമ്പുകളും ദശാംശ സ്ട്രിങ്ങുകളാണ്;
സ്ട്രിങ്ങുകൾ, ബൂളിയനുകൾ, ഭിന്നസംഖ്യകൾ എന്നിവ അവയുടെ നേറ്റീവ് OTLP മൂല്യ വകഭേദങ്ങൾ ഉപയോഗിക്കുന്നു.
പിശക് സ്പാനുകൾക്ക് ERROR സ്റ്റാറ്റസും സാനിറ്റൈസ് ചെയ്ത സ്റ്റാറ്റസ് സന്ദേശവും ഉണ്ടാകും.
കാനോനിക്കൽ റെക്കോർഡിൽ അപ്സ്ട്രീം ഹോസ്റ്റ് URL ഇല്ല; അതിനാൽ കളക്ടറിനെ മോഡൽ സെർവറായി
തെറ്റായി തിരിച്ചറിയുന്നതിനുപകരം `server.address` ഒഴിവാക്കുന്നു. ചെലവ് എക്സ്പോർട്ട് ചെയ്യുന്നില്ല.

`includeBodies=true` മാത്രമാണ് ഉള്ളടക്കം ഹൈഡ്രേറ്റ് ചെയ്യുന്നത്. `langfuseMapping=false` ആയിരിക്കുമ്പോൾ,
`gen_ai.input.messages` / `gen_ai.output.messages` എന്നിവ OmniRoute സംഭരിച്ചിരിക്കുന്ന
സാനിറ്റൈസ് ചെയ്ത റിക്വസ്റ്റ്/റെസ്പോൺസ് ബോഡി JSON വഹിക്കുന്നു (പാർസ് ചെയ്യാനാകുമ്പോൾ കാനോനിക്കലൈസ് ചെയ്യുന്നു);
പുനഃക്രമീകരിച്ച semconv സന്ദേശ അറേയല്ല അവ.
വെട്ടിച്ചുരുക്കിയ/JSON അല്ലാത്ത ബോഡികൾ അസംസ്കൃത ടെക്സ്റ്റായി തുടരും. `langfuseMapping=true` ആയിരിക്കുമ്പോൾ,
ബോഡികൾ `langfuse.observation.input` / `langfuse.observation.output` ആയി മാത്രം അയയ്ക്കുന്നു;
ഓരോ ബോഡിയും ഒരിക്കൽ മാത്രം അയയ്ക്കുന്നതിനായി `gen_ai.*.messages` ആട്രിബ്യൂട്ടുകൾ ഒഴിവാക്കുന്നു.
രണ്ട് മോഡുകളും നിലവിലുള്ള ഹൈഡ്രേഷൻ പാത്തിൽനിന്ന് `maxBodyBytes` സ്വീകരിക്കുന്നു;
`omniroute.bodies_truncated=true` വെട്ടിച്ചുരുക്കൽ സൂചിപ്പിക്കുന്നു.
ഈ ലക്ഷ്യസ്ഥാനം അധിക പൈപ്പ്‌ലൈൻ സ്നാപ്ഷോട്ടുകളോ സാനിറ്റൈസ് ചെയ്യാത്ത ആർട്ടിഫാക്റ്റ് വായനകളോ ചേർക്കുന്നില്ല;
ഐച്ഛികമായ റിക്വസ്റ്റ്-ഹെഡർ ശേഖരണം താഴെ വിവരിച്ചിരിക്കുന്ന നിലവിലുള്ള ഹൈഡ്രേറ്റ് ചെയ്ത ക്ലയന്റ് സ്നാപ്ഷോട്ട് ഉപയോഗിക്കുന്നു.
ബോഡികൾ എക്സ്പോർട്ട് ചെയ്യുമ്പോൾ മണിക്കൂർ അടിസ്ഥാനത്തിലുള്ള ബാക്ക്‌ലോഗ് കുന്നുകൂടാൻ അനുവദിക്കുന്നതിനുപകരം
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` പോലുള്ള മിനിറ്റ് തലത്തിലുള്ള ഇടവേള ഉപയോഗിക്കുക.

### ഐച്ഛികമായ ക്ലയന്റ് റിക്വസ്റ്റ് ഹെഡറുകൾ

ഹെഡർ ശേഖരണം **സ്ഥിരസ്ഥിതിയായി ഓഫാണ്**. ലക്ഷ്യസ്ഥാന കോൺഫിഗിൽ `requestHeaderAllowlist`
സജ്ജീകരിക്കുകയും **പ്രോംപ്റ്റുകളും പ്രതികരണങ്ങളും എക്സ്പോർട്ട് ചെയ്യുക** പ്രവർത്തനക്ഷമമാക്കുകയും ചെയ്യുക
(ലക്ഷ്യസ്ഥാനത്ത് `includeBodies: true`).
അനുവദനീയ പട്ടിക ഒരു API അറേയോ, പുതിയ വരികൾ/കോമകൾ ഉപയോഗിച്ച് വേർതിരിച്ച പേരുകളുള്ള ടെക്സ്റ്റ്ഏരിയയോ സ്വീകരിക്കുന്നു:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

അവസാനത്തിലുള്ള ഒറ്റ `*` ശൂന്യമല്ലാത്ത ഒരു ഹെഡർ-നാമ പ്രിഫിക്സ് തിരഞ്ഞെടുക്കുന്നില്ലെങ്കിൽ, വലിയക്ഷര-ചെറിയക്ഷര വ്യത്യാസം കണക്കാക്കാതെ പേരുകൾ കൃത്യമായി പൊരുത്തപ്പെടണം.
ഒറ്റയ്ക്കുള്ള `*`, ഇടയിൽ വരുന്ന വൈൽഡ്കാർഡുകൾ, അസാധുവായ HTTP ഹെഡർ പേരുകൾ എന്നിവ നിരസിക്കപ്പെടും.
പരമാവധി 64 സെലക്ടറുകൾ അനുവദനീയമാണ്; ഓരോന്നിന്റെയും പേര്/പ്രിഫിക്സ് പരമാവധി 256 ASCII ബൈറ്റുകളായിരിക്കണം.
എക്സ്പോർട്ടറെ കളക്ടറിനോട് പ്രാമാണീകരിക്കുന്ന `headers` എന്ന ക്രമീകരണത്തിൽനിന്ന് വേറിട്ടതാണ് ഈ ക്രമീകരണം.

സംരക്ഷിച്ച വിശദമായ പൈപ്പ്ലൈനിലെ `clientRawRequest` (അല്ലെങ്കിൽ പഴയ `clientRequest`) ഉപയോഗിച്ച്
പൂരിപ്പിക്കുന്ന `pipeline_client_request` മാത്രമാണ് ക്യാപ്ചർ വായിക്കുന്നത്. പകരമായി പ്രൊവൈഡർ അഭ്യർത്ഥനയുടെ ഹെഡറുകൾ ഒരിക്കലും ഉപയോഗിക്കില്ല.
അഭ്യർത്ഥന രേഖപ്പെടുത്തിയ സമയത്ത് വിശദമായ പൈപ്പ്ലൈൻ ലോഗിങ് പ്രവർത്തനക്ഷമമായിരുന്നിരിക്കണം.
`includeBodies` പ്രവർത്തനരഹിതമാണെങ്കിലോ, ക്ലയന്റ്-സ്നാപ്ഷോട്ട് JSON ഇല്ലാതിരിക്കുകയോ കേടായിരിക്കുകയോ വെട്ടിച്ചുരുക്കപ്പെട്ടിരിക്കുകയോ ചെയ്താൽ, ഹെഡർ
ആട്രിബ്യൂട്ടുകളൊന്നും പുറപ്പെടുവിക്കില്ല. `maxBodyBytes` വർധിപ്പിക്കുന്നത് എക്സ്പോർട്ട് സമയത്തെ സ്നാപ്ഷോട്ട് വെട്ടിച്ചുരുക്കൽ ഒഴിവാക്കാൻ സഹായിക്കും;
ഒരിക്കലും സംരക്ഷിക്കാത്ത വിശദാംശങ്ങൾ അതിന് പുനഃസ്ഥാപിക്കാനാവില്ല. 1 MiB-ൽ കൂടുതലുള്ളതോ 256-ൽ കൂടുതൽ
ഹെഡർ എൻട്രികൾ അടങ്ങിയതോ ആയ സ്നാപ്ഷോട്ട് അവഗണിക്കപ്പെടും. നിലവിലുള്ള പ്രോംപ്റ്റ്/പ്രതികരണ എക്സ്പോർട്ട്, ഹെഡർ
ക്യാപ്ചറിനൊപ്പം പ്രവർത്തനക്ഷമമായി തുടരും; അനുവദനീയ പട്ടിക ഹെഡറുകൾ മാത്രമുള്ള ഹൈഡ്രേഷൻ മോഡ് നൽകുന്നില്ല.

തിരഞ്ഞെടുത്ത മൂല്യങ്ങൾ, ഒറ്റ സ്ട്രിങ് മാത്രമാണെങ്കിലും, `http.request.header.<full lowercase header name>` OTLP സ്ട്രിങ് അറേകളായി മാറുന്നു.
ഉദാഹരണത്തിന്, `X-OmniRoute-Meta-Team: example-team` എന്നത്
`http.request.header.x-omniroute-meta-team` ആയും അതിന്റെ മൂല്യം
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}` ആയും മാറുന്നു.
മുഴുവൻ പ്രിഫിക്സും നിലനിർത്തുന്നു: ഇവ സാധാരണ ഹെഡറുകളാണ്; ബിസിനസ്-ഫീൽഡ് പാഴ്സിങ്ങോ
`omniroute.metadata.*` / Langfuse മെറ്റാഡാറ്റ പരിവർത്തനമോ നടത്തുന്നില്ല. `langfuseMapping` ഹെഡറുകളുടെ
അർത്ഥവ്യവസ്ഥ മാറ്റുന്നില്ല. തിരഞ്ഞെടുത്ത, ഒറ്റ മൂല്യമുള്ള `User-Agent`, സ്റ്റാൻഡേർഡ് സ്കെയിലറായ
`user_agent.original` കൂടിയും സജ്ജമാക്കുന്നു. ഒരു മൂല്യത്തിനുള്ളിലെ കോമകൾ അടിസ്ഥാനമാക്കി വിഭജിക്കില്ല. വലിയക്ഷര-ചെറിയക്ഷര വകഭേദങ്ങൾ സംരക്ഷിച്ച
എൻട്രികളുടെ ക്രമത്തിൽ ലയിപ്പിക്കും; ഏതെങ്കിലും വകഭേദം അസാധുവാണെങ്കിൽ ആ ഹെഡർ മുഴുവനായി ഒഴിവാക്കും. ചെറിയക്ഷരത്തിലുള്ള പേരനുസരിച്ചാണ് ആട്രിബ്യൂട്ടുകൾ ക്രമീകരിക്കുന്നത്.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-key ഹെഡറുകൾ, പേരിൽ
auth/token/secret/password/credential സൂചകങ്ങളുള്ളവ, ആന്തരിക ഗേറ്റ്‌വേ ക്രെഡൻഷ്യലുകൾ എന്നിവ എല്ലായ്പ്പോഴും
ഒഴിവാക്കപ്പെടും; അവ തിരഞ്ഞെടുത്തതാണെങ്കിലും സംഭരണത്തിൽ ഭാഗികമായി മറച്ചതാണെങ്കിലും ഇത് ബാധകമാണ്. അറിയപ്പെടുന്ന ക്രെഡൻഷ്യൽ പാറ്റേണുകൾക്കായി
പങ്കിട്ട ക്രെഡൻഷ്യൽ ഡിറ്റക്ടർ വീണ്ടും ഉപയോഗിക്കുന്നു; മറയ്ക്കൽ സൂചകങ്ങൾ സുരക്ഷിത മൂല്യങ്ങളായി എക്സ്പോർട്ട് ചെയ്യാതെ ഒഴിവാക്കുന്നു.
സ്ട്രിങ്ങുകളും ശൂന്യമല്ലാത്ത സ്ട്രിങ് അറേകളും മാത്രമേ സ്വീകരിക്കൂ; സംഖ്യകളെയോ ഒബ്ജക്റ്റുകളെയോ നിർബന്ധിതമായി പരിവർത്തനം ചെയ്യില്ല.
അസാധുവായ പേരുകൾ, പ്രോട്ടോടൈപ്പ് കീകൾ, കൺട്രോൾ അക്ഷരങ്ങൾ (ഹൊറിസോണ്ടൽ ടാബ് ഒഴികെ), തെറ്റായ ഘടനയുള്ള Unicode
എന്നിവ ബാച്ച് പരാജയപ്പെടുത്താതെയും അവയുടെ ഉള്ളടക്കം പിശകുകളിൽ ഉൾപ്പെടുത്താതെയും അവഗണിക്കും.

ഓരോ സ്പാനും പരമാവധി 32 ഹെഡറുകൾ, ഓരോ ഹെഡറിനും 16 മൂല്യങ്ങൾ, ഓരോ മൂല്യത്തിനും 4096 UTF-8 ബൈറ്റുകൾ,
ക്യാപ്ചർ ചെയ്ത ഹെഡർ പേരുകളും മൂല്യങ്ങളും ചേർത്ത് ആകെ 16384 UTF-8 ബൈറ്റുകൾ എന്നിവയാണ് ക്യാപ്ചർ ചെയ്യുന്നത്. പരിധി കവിഞ്ഞതോ അസാധുവായതോ ആയ ഹെഡറുകൾ
വെട്ടിച്ചുരുക്കാതെ മുഴുവനായി ഒഴിവാക്കും. തിരഞ്ഞെടുപ്പ് ഓപ്പറേറ്ററുടെ സ്വകാര്യതാ തീരുമാനമാണ്: സുരക്ഷിതമെന്ന് തോന്നുന്ന പേരുകളിൽപ്പോലും
വ്യക്തിഗത ഡാറ്റ ഉണ്ടാകാം; ഈ പരിധികളും ഡിറ്റക്ടറുകളും പൊതുവായ PII നീക്കംചെയ്യൽ സംവിധാനമല്ല.

### ഡെലിവറി പരിധികൾ

അഭ്യർത്ഥനകൾ 500 സ്പാനുകളായും എൻവലപ്പ് ഉൾപ്പെടെ 4 MiB UTF-8 JSON ആയും പരിമിതപ്പെടുത്തിയിരിക്കുന്നു.
ഒരു കഴ്സർ ബാച്ചിന്റെ ആദ്യ അഭ്യർത്ഥനയ്ക്കുമുമ്പ് അനുവദനീയമായ ഓരോ സ്പാനിന്റെയും വലുപ്പം പരിശോധിക്കുന്നു. ഒറ്റ
സ്പാൻ പരിധിയേക്കാൾ വലുതാണെങ്കിൽ ആ ബാച്ചിന്റെ ഒരു ഭാഗവും അയയ്ക്കില്ല; `maxBodyBytes`
കുറയ്ക്കാനുള്ള നിർദേശത്തോടെ പരാജയപ്പെടും; അത് നിശ്ശബ്ദമായി ഒഴിവാക്കില്ല. പ്രീഫ്ലൈറ്റ് റെക്കോർഡ് റഫറൻസുകളും
ബൈറ്റ് എണ്ണങ്ങളും മാത്രം നിലനിർത്തുകയും ഓരോ താൽക്കാലിക സ്പാൻ/JSON-ഉം ഉപേക്ഷിക്കുകയും ചെയ്യുന്നു; ബാച്ചിന്റെ രണ്ടാമതൊരു സീരിയലൈസ് ചെയ്ത പകർപ്പ് സൂക്ഷിക്കുന്നതിനുപകരം,
പരിമിത വലുപ്പമുള്ള ഖണ്ഡങ്ങൾക്കായി സ്പാനുകൾ വീണ്ടും നിർമ്മിക്കുന്നു. HTTP 408/429/5xx, നെറ്റ്‌വർക്ക് പരാജയങ്ങൾ, ടൈംഔട്ടുകൾ എന്നിവയ്ക്ക് 250/500 ms എക്സ്പൊണൻഷ്യൽ ബാക്ക്ഓഫോടെ പരമാവധി
മൂന്ന് ശ്രമങ്ങൾ നടത്തും. `Retry-After` സെക്കൻഡുകളോ HTTP തീയതികളോ
കാലതാമസം 5 സെക്കൻഡ് വരെ നീട്ടാം. മറ്റ് സ്റ്റാറ്റസുകൾ ഉടൻ പരാജയപ്പെടും. OTLP 2xx ഭാഗിക നിരസിക്കലും
നഷ്ടപ്പെട്ട സ്പാൻ അംഗീകരിക്കുന്നതിനുപകരം പിശക് ഉയർത്തും; ശൂന്യമായതോ സാധുവായ JSON ആയതോ ആയ സ്വീകരണ സ്ഥിരീകരണങ്ങൾ അംഗീകരിക്കും;
പ്രതികരണം വായിക്കുന്നതിനുള്ള പരിധി 64 KiB ആണ്.

പിശകുകളിൽ എക്സ്പോർട്ടറുടെ സ്വന്തം വിവരങ്ങൾ മാത്രമേ ഉണ്ടാകൂ: HTTP സ്റ്റാറ്റസ്, റിട്രൈ വിഭാഗം, ശ്രമങ്ങളുടെ എണ്ണവും അയച്ച സ്പാനുകളുടെ
എണ്ണവും, അല്ലെങ്കിൽ സ്വീകരണ സ്ഥിരീകരണ/നെറ്റ്‌വർക്ക് പരാജയത്തിനുള്ള നിശ്ചിത വാചകങ്ങൾ. കളക്ടറിന്റെ പ്രതികരണ ബോഡികൾ,
ഭാഗിക വിജയത്തിന്റെ എണ്ണങ്ങൾ, പ്രതികരണ ഹെഡറുകൾ എന്നിവ ഒരിക്കലും പിശകുകളിലേക്കോ ലോഗുകളിലേക്കോ
ഡാഷ്ബോർഡിലേക്കോ പകർത്തില്ല. പരാജയപ്പെട്ടതോ ഭാഗികമായി സ്വീകരിച്ചതോ ആയ ബാച്ച് സ്ഥിരീകരിക്കപ്പെടില്ല: ലക്ഷ്യസ്ഥാനം
ആ സ്റ്റാറ്റസോടെ പരാജയാവസ്ഥ കാണിക്കും, കഴ്സർ അവസാനം സ്ഥിരീകരിച്ച ബാച്ചിൽത്തന്നെ തുടരും, അടുത്ത റൺ
അതേ വരികൾ വീണ്ടും അയയ്ക്കും. കളക്ടറോ കോൺഫിഗറേഷനോ
ശരിയാക്കുന്നതുവരെ സ്ഥിരമായ സ്റ്റാറ്റസുകൾ പരാജയപ്പെട്ടുകൊണ്ടിരിക്കും. പ്രതികരണത്തിന്റെ വിശദാംശങ്ങൾക്ക് കളക്ടറിന്റെ സ്വന്തം ലോഗുകൾ ഉപയോഗിക്കുക. കോൾ-ലോഗ് പിശക് സംഗ്രഹങ്ങൾ
അവയുടെ പ്രത്യേക മറയ്ക്കൽ നിലനിർത്തുന്നു.
`prepare()` ഒന്നും പ്രൊവിഷൻ ചെയ്യുന്നില്ല; ടെസ്റ്റ് കൃത്യമായി `{"resourceSpans":[]}` പോസ്റ്റ് ചെയ്യുകയും
കോൾ-ലോഗ് സ്പാനുകൾ എഴുതാതെ HTTP സ്റ്റാറ്റസ് റിപ്പോർട്ട് ചെയ്യുകയും ചെയ്യുന്നു.

ട്രേസ് ഐഡികളും സ്പാൻ ഐഡികളും യഥാക്രമം
`"omniroute.trace\\0" + callLogId`, `"omniroute.span\\0" + callLogId` എന്നിവയുടെ SHA-256-ലെ ആദ്യ 32/16 ഹെക്സ് അക്കങ്ങളാണ്. വീണ്ടും അയയ്ക്കുമ്പോഴും
അതേ ഐഡികൾ ഉപയോഗിക്കുന്നു. ഇത് ഡ്യൂപ്ലിക്കേറ്റുകൾ നീക്കംചെയ്യുമെന്ന ഉറപ്പല്ല: Langfuse
v4 ഇൻജെഷൻ ഉൾപ്പെടെയുള്ള ചില ബാക്ക്എൻഡുകൾ ഒരേ ഐഡിയുള്ള സ്പാനുകളുടെ ഡ്യൂപ്ലിക്കേറ്റുകൾ നീക്കംചെയ്യുന്നില്ല. ക്രാഷോ ഭാഗിക ഖണ്ഡ പരാജയമോ ഉണ്ടായാൽ,
സ്ഥിരീകരിക്കാത്ത ആ ഒരു കഴ്സർ ബാച്ച് മാത്രമാണ് പരമാവധി വീണ്ടും അയയ്ക്കുക; അതിന്റെ അവസാന HTTP ഖണ്ഡം മാത്രമല്ല,
ആ ബാച്ച് മുഴുവനും ഡ്യൂപ്ലിക്കേറ്റ് ആയേക്കാം. ഈ വിട്ടുവീഴ്ച കണക്കിലെടുത്ത് കഴ്സർ ബാച്ച് വലുപ്പം തിരഞ്ഞെടുക്കുക.

### Langfuse ഉദാഹരണം

സ്വയം ഹോസ്റ്റ് ചെയ്ത Langfuse ഇൻസ്റ്റൻസിനായി ഈ ഫീൽഡുകൾ കോൺഫിഗർ ചെയ്യുക:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

`public-key:secret-key` എന്ന അക്ഷരാർഥത്തിലുള്ള സ്ട്രിങ്ങിന്റെ Base64 ആയി Authorization മൂല്യം ലോക്കലായി നിർമ്മിക്കുക
(ഉദാഹരണത്തിന് `Buffer.from(publicKey + ":" + secretKey).toString("base64")` ഉപയോഗിച്ച്).
യഥാർഥ ക്രെഡൻഷ്യലുകൾ ലോഗുകളിലോ സ്ക്രീൻഷോട്ടുകളിലോ ഇഷ്യൂകളിലോ പേസ്റ്റ് ചെയ്യരുത്. മാപ്പിങ് സ്വയമേവ
`x-langfuse-ingestion-version: 4` സജ്ജമാക്കുന്നു; Authorization തുടർന്നും `headers` വഴിയാണ് നൽകുന്നത്.
ഹെഡറുകളും സൃഷ്ടിക്കപ്പെടുന്ന ഐഡന്റിറ്റി സാൾട്ടും നിലവിലുള്ള എൻക്രിപ്റ്റ് ചെയ്ത രഹസ്യ-ഫീൽഡ്
സംവിധാനവും API പ്ലേസ്‌ഹോൾഡറുകളും ഉപയോഗിക്കുന്നു; `STORAGE_ENCRYPTION_KEY` ആവശ്യമാണ്.

മാപ്പിംഗ്, ജനറേഷൻ തരം/മോഡൽ, JSON ഉപയോഗ വിശദാംശങ്ങൾ (ഇൻപുട്ട്/ഔട്ട്പുട്ട്/ആകെ, ലഭ്യമായ
കാഷെ കീകൾ), JSON ഇൻപുട്ട്/ഔട്ട്പുട്ട് സ്നാപ്ഷോട്ടുകൾ, ERROR/DEFAULT നില, ശുദ്ധീകരിച്ച സ്റ്റാറ്റസ് സന്ദേശം,
ട്രേസ് പേര്, സെഷൻ ഐഡി, ഐച്ഛിക എൻവയോൺമെന്റ് എന്നിവയും പ്രൊവൈഡർ, അഭ്യർത്ഥിച്ച മോഡൽ, പാത്ത്, കോംബോ, കാഷെ
ഉറവിടം, സ്റ്റാറ്റസ് എന്നിവയ്ക്കായി ഫിൽട്ടർ ചെയ്യാവുന്ന
`langfuse.observation.metadata.<key>`-യും ചേർക്കുന്നു. TTFT അറിയാവുന്നതും ദൈർഘ്യത്തിനുള്ളിൽ വരുന്നതുമായപ്പോൾ മാത്രം,
ആരംഭ സമയം + TTFT എന്നതിന്റെ ISO 8601 രൂപമാണ് `langfuse.observation.completion_start_time`.
ചെലവ് ആട്രിബ്യൂട്ടുകളൊന്നും അയയ്ക്കുന്നില്ല.

ഐഡന്റിറ്റി മോഡുകൾ `langfuse.user.id`-ന് ബാധകമാണ്:

- `pseudonymous` (ഡിഫോൾട്ട്): ഓരോ ഡെസ്റ്റിനേഷനും പ്രത്യേകം സൃഷ്ടിക്കുന്ന റാൻഡം
  32-ബൈറ്റ് സാൾട്ട് ഉപയോഗിച്ചുള്ള API കീയുടെ ആന്തരിക ഐഡിയുടെ HMAC-SHA256.
  സാൾട്ട് ഇല്ലെങ്കിൽ സൃഷ്ടിക്കുന്ന സമയത്ത് അത് ജനറേറ്റ് ചെയ്യുകയും, `identitySalt` ആയി എൻക്രിപ്റ്റ് ചെയ്യുകയും,
  ഒരിക്കലും തിരികെ നൽകാതിരിക്കുകയും, എഡിറ്റുകൾക്കിടയിൽ നിലനിർത്തുകയും ചെയ്യുന്നു. അസംസ്കൃത കീ ഐഡികൾ ഒരിക്കലും
  സ്പാൻ ആട്രിബ്യൂട്ടുകളിൽ ഉൾപ്പെടുത്തുന്നില്ല. ഒരു ഡെസ്റ്റിനേഷന്റെ സാൾട്ട് പുനഃസൃഷ്ടിക്കുകയോ റൊട്ടേറ്റ് ചെയ്യുകയോ ചെയ്യുന്നത് ഐഡന്റിറ്റികൾ മാറ്റുന്നു.
- `keyName`: കോൺഫിഗർ ചെയ്ത API കീയുടെ പേര്; ഓപ്പറേറ്റർ നൽകിയ ആ ലേബൽ മനഃപൂർവം വെളിപ്പെടുത്തുന്നു.
- `none`: ഉപയോക്തൃ ഐഡി ഇല്ല. സെഷൻ ടാഗുകൾ ഉണ്ടെങ്കിൽ അവ തുടർന്നും എക്സ്പോർട്ട് ചെയ്യപ്പെടും; ഈ മോഡുകൾ
  ഏതെങ്കിലും പ്രോംപ്റ്റ് ഉള്ളടക്കത്തെയോ ഓപ്പറേറ്റർ നൽകിയ സെഷൻ/കോറിലേഷൻ ലേബലുകളെയോ അജ്ഞാതവൽക്കരിക്കുന്നില്ല.

### മുൻകാല ഡാറ്റ പൂരിപ്പിക്കാതെ ആരംഭിക്കൽ

സൃഷ്ടിക്കുന്ന സമയത്ത് മാത്രം, **നിലവിലെ സ്ഥാനത്തുനിന്ന് ആരംഭിക്കുക (നിലവിലുള്ള ലോഗുകൾ ഒഴിവാക്കുക)** പ്രവർത്തനക്ഷമമാക്കുക അല്ലെങ്കിൽ
സൃഷ്ടിക്കാനുള്ള API പേലോഡിന്റെ മുകളിലെ തലത്തിൽ `startFromCurrentPosition: true` നൽകുക. നിലവിലുള്ള കഴ്സർ
ഹെൽപ്പറുകൾ ഉപയോഗിച്ച്, മൈഗ്രേഷൻ കൂടാതെ, നിലനിർത്തിയിട്ടുള്ള കോൾ-ലോഗിലെ നിലവിലെ പരമാവധി rowid ആയി
`cursor_row_id` ഇത് സജ്ജീകരിക്കുന്നു. ഡിഫോൾട്ട് false ആണ് (കഴ്സർ 0, നിലനിർത്തിയ ചരിത്രഡാറ്റയുടെ പൂരിപ്പിക്കൽ).
അപ്ഡേറ്റ് സമയത്ത് കഴ്സർ റീസെറ്റ് ചെയ്യാനുള്ള ക്രമീകരണമല്ല ഇത്.

പങ്കിട്ട `ttftMs` കൂട്ടിച്ചേർക്കൽ BigQuery മാപ്പറിലും പുതിയ ടേബിളിന്റെ സ്കീമയിലും null അനുവദിക്കുന്ന `ttft_ms`
കോളവും ചേർക്കുന്നു: ഓരോ കാനോനിക്കൽ റെക്കോർഡ് ഫീൽഡിനും ഒരു കോളം ഉണ്ടായിരിക്കണമെന്ന് അതിന്റെ സ്കീമ ടെസ്റ്റ് ആവശ്യപ്പെടുന്നു.
നിലവിലുള്ള ടേബിളുകൾ മാറ്റമില്ലാതെ എക്സ്പോർട്ട് ചെയ്യുന്നത് തുടരും: `prepare()` ടേബിൾ സ്കീമ വായിക്കുകയും
ആ കോളം ഇല്ലാത്തപ്പോൾ `ttft_ms` മാത്രം ഒഴിവാക്കുകയും ചെയ്യുന്നു. അടുത്ത റണ്ണിൽ TTFT ലഭിക്കാൻ null അനുവദിക്കുന്ന INT64
കോളം ചേർക്കുക, അല്ലെങ്കിൽ പുതിയ ടേബിൾ ഉപയോഗിക്കുക. PATCH, സ്വയമേവയുള്ള സ്കീമ മാറ്റം, അധിക
അനുമതികൾ എന്നിവ ആവശ്യമില്ല; മറ്റെല്ലാ റോ ഫീൽഡുകളിലും കർശനമായ സ്കീമ പരിശോധന തുടരും.

## 6. ഒരു ഡെസ്റ്റിനേഷൻ ചേർക്കൽ

1. ഒരു `LogExportDestinationType` എക്സ്പോർട്ട് ചെയ്യുന്ന `src/lib/logExport/destinations/<name>.ts` സൃഷ്ടിക്കുക:
   ഒരു Zod `configSchema`, UI-ക്കായുള്ള ഒരു `fields` ഡിസ്ക്രിപ്റ്റർ അറേ, `secretFields`, കൂടാതെ
   `test()` / `prepare()` / `send(records)` തിരികെ നൽകുന്ന ഒരു `createClient(config)`.
2. അത് `src/lib/logExport/registry.ts`-ലെ `DESTINATIONS` അറേയിലേക്ക് ചേർക്കുക.
3. `tests/unit/`-ൽ ടെസ്റ്റുകൾ എഴുതുക.

ഇത്രയും മാത്രമാണ് മാറ്റം: പെർസിസ്റ്റൻസ്, cron ജോബ്, REST ലെയർ, രഹസ്യവിവരങ്ങളുടെ എൻക്രിപ്ഷൻ,
ഡാഷ്ബോർഡ് ഫോം എന്നിവയെല്ലാം രജിസ്ട്രിയിൽ നിന്നാണ് വായിക്കുന്നത്.

പുതിയ ഡെസ്റ്റിനേഷനുള്ള രണ്ട് നിയമങ്ങൾ:

- ഭാഗിക പരാജയമുണ്ടാകുമ്പോൾ `send()` **നിർബന്ധമായും എക്സെപ്ഷൻ ത്രോ ചെയ്യണം**. വിജയകരമായി പൂർത്തിയാകുന്നത് "ഡെസ്റ്റിനേഷനിൽ ഈ വരികൾ ഉണ്ട്" എന്നാണ് അർത്ഥമാക്കുന്നത്,
  തുടർന്ന് കർസർ അവയെ ശാശ്വതമായി കടന്നുപോകുന്നു.
- ഉപയോക്താവ് നൽകുന്ന URL സ്വീകരിക്കുന്ന ഡെസ്റ്റിനേഷൻ, ഫെച്ച് ചെയ്യുന്നതിനു മുമ്പ്
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) വഴി അത് സാധൂകരിക്കണം,
  വെബ്ഹുക്കുകൾ ചെയ്യുന്നതുപോലെതന്നെ. BigQuery-ക്ക് ഇത് ആവശ്യമില്ല: അതിന്റെ ഹോസ്റ്റുകൾ സ്ഥിരാങ്കങ്ങളാണ്.

## 7. ഇത് പ്രവർത്തിപ്പിക്കൽ

- **ഡാഷ്ബോർഡ്**: ഇന്റഗ്രേഷനുകൾ → ലോഗ് എക്സ്പോർട്ട്. ഒരു ഡെസ്റ്റിനേഷൻ ചേർക്കുക, വരികൾ എഴുതാതെ
  ക്രെഡൻഷ്യലുകൾ പരിശോധിക്കാൻ **ടെസ്റ്റ്** പ്രവർത്തിപ്പിക്കുക, തുടർന്ന് അത് പ്രവർത്തനക്ഷമമാക്കുക.
- **ബാക്ക്‌ലോഗ്**: ഓരോ ഡെസ്റ്റിനേഷൻ കാർഡും ശേഷിക്കുന്ന വരികളും കർസറും കാണിക്കുന്നു; `GET
/api/log-export/status` ഇതേ കണക്കുകൾക്കൊപ്പം അവസാനത്തെ 20 ജോബ് റണ്ണുകളും തിരികെ നൽകുന്നു.
- **ഒരു ഡെസ്റ്റിനേഷൻ പരാജയപ്പെട്ടാലും മറ്റുള്ളവ പരാജയപ്പെടില്ല** — റൺ സംഗ്രഹം ഓരോ ഡെസ്റ്റിനേഷന്റെയും
  നില `last_status` / `last_error` എന്നിവയിൽ രേഖപ്പെടുത്തുന്നു, ജോബ് റൺ ചരിത്രം മൊത്തത്തിലുള്ള വിവരങ്ങൾ സൂക്ഷിക്കുന്നു.
- **ഒരു ഡെസ്റ്റിനേഷൻ ഇല്ലാതാക്കുന്നത് അതിന്റെ കർസറും ഇല്ലാതാക്കും.** അത് വീണ്ടും ചേർക്കുമ്പോൾ, നിലനിർത്തിയിട്ടുള്ള ഏറ്റവും പഴയ
  കോൾ ലോഗിൽ നിന്ന് ആരംഭിക്കുന്നു; ഇതിലൂടെ ഡെസ്റ്റിനേഷനിൽ ഇതിനകം ഉണ്ടായേക്കാവുന്ന വരികൾ വീണ്ടും അയയ്ക്കപ്പെടും. BigQuery-യിൽ ഓരോ വരിയുടെയും
  `insertId`, BigQuery-യുടെ സ്വന്തം ഡീ-ഡ്യൂപ്ലിക്കേഷൻ സമയപരിധിക്കുള്ളിൽ മാത്രമേ ഈ ആവർത്തനം ഒഴിവാക്കൂ. അതിനാൽ ഒരു ഡെസ്റ്റിനേഷൻ
  ഇല്ലാതാക്കുന്നതിനുപകരം പ്രവർത്തനരഹിതമാക്കാൻ മുൻഗണന നൽകുക.
