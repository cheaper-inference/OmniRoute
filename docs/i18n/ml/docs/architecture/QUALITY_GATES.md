ഈ പ്രമാണമാണ് OmniRoute-ലെ എല്ലാ CI ഗുണനിലവാര ഗേറ്റുകൾക്കുമുള്ള ആധികാരിക റഫറൻസ്.
ഓരോ ഗേറ്റും, അത് എന്താണ് സാധൂകരിക്കുന്നത്, ഏത് CI ജോബിലാണ് അത് പ്രവർത്തിക്കുന്നത്, അത്
ഒരു റാച്ചറ്റ് ബേസ്ലൈൻ ആണോ അതോ പാസ്/ഫെയിൽ നയമാണോ ഉപയോഗിക്കുന്നത്, ബിൽഡ് തടയുന്നതാണോ അതോ ഉപദേശാത്മകമാണോ എന്നിവ ഇതിൽ വിവരിക്കുന്നു.

ഒരു ഹ്രസ്വ സംഗ്രഹത്തിനും അനുവദനീയ പട്ടികാ നയത്തിനും `AGENTS.md`-ലെ
"ഗുണനിലവാര ഗേറ്റുകളും റാച്ചറ്റുകളും" വിഭാഗം കാണുക. ഇതേ സിസ്റ്റത്തിന്റെ നിർണായക വിലയിരുത്തൽ,
മെച്യൂരിറ്റി വർഗ്ഗീകരണം, ടൂൾ-അഗ്നോസ്റ്റിക് പുനരാവിഷ്കരണ പദ്ധതി എന്നിവയ്ക്കായി
[ഗുണനിലവാര ഗേറ്റ് പ്ലേബുക്ക്](../ops/QUALITY_GATE_PLAYBOOK.md) കാണുക.

## ഗേറ്റ് ഇൻവെന്ററിയും എക്സിക്യൂഷൻ പ്രൊഫൈലുകളും

### കാൻഡിഡേറ്റ് പ്രവേശനം

CI, Quality Gates വർക്ക്ഫ്ലോകൾ ഓരോന്നും സ്ഥിരതയുള്ള ഒരു വിധിനിർണ്ണയം പുറപ്പെടുവിക്കുന്നു: `Gate / CI`, `Gate / Quality`.
അവയുടെ പതിപ്പുനിർണ്ണയിച്ച പ്രവേശന നയം ഓരോ അപ്സ്ട്രീം ജോബിനെയും നിർബന്ധിതമോ ഉപദേശാത്മകമോ ആയി പട്ടികപ്പെടുത്തുന്നു. ബാധകമായ ഒരു നിർബന്ധിത ജോലി വിജയിക്കണം: ലഭ്യമല്ലാത്തതോ റദ്ദാക്കിയതോ ഒഴിവാക്കിയതോ തീർപ്പാകാത്തതോ അജ്ഞാതമായതോ ആയ ഫലങ്ങൾക്ക് PASS സ്ഥിരീകരിക്കാനാകില്ല. സാധുവായ docs-only അല്ലെങ്കിൽ catalog-only വർഗ്ഗീകരണം ഒരു കോഡ് ലെയിനിനെ ബാധകമല്ലാതാക്കാം;
ഒരു ഡ്രാഫ്റ്റ് PR അംഗീകൃത കാൻഡിഡേറ്റല്ല. `hotfix` ലേബൽ തെളിവിന്റെ ആവശ്യകത ഒഴിവാക്കുന്നില്ല.

രണ്ട് വർക്ക്ഫ്ലോകളും main/release ബ്രാഞ്ചുകളിലേക്കുള്ള PR-കൾ, `main`-ലേക്കുള്ള പുഷുകൾ, മാനുവൽ ഡിസ്പാച്ച്,
merge-group ഇവന്റുകൾ എന്നിവ ഉൾക്കൊള്ളുന്നു. Push, dispatch, merge-group എന്നിവ പൂർണ്ണ സെലക്ഷൻ പ്രവർത്തിപ്പിക്കുന്നു. `release/**`-ലേക്കുള്ള
പുഷുകൾ അവയെ ആരംഭിക്കുന്നില്ല (2026-10-18): ഓരോ മാറ്റവും ഇതിനകം അതിന്റെ PR-ൽ മാട്രിക്സ് പ്രവർത്തിപ്പിച്ചിട്ടുണ്ട്,
കൂടാതെ ലയിപ്പിച്ച കോമ്പിനേഷൻ Release-Green-ന്റെ ജോലിയാണ് (`docs/ops/RUNNER_BOX.md` → ഹോസ്റ്റഡ് ലെയിൻ). Fork-കളും
merge group-കളും, സാധാരണയായി self-hosted റണ്ണറുകൾ തിരഞ്ഞെടുക്കുന്ന ജോലികൾക്കായി hosted റണ്ണറുകൾ ഉപയോഗിക്കുന്നു;
റോൾഔട്ടിന് മുമ്പ് മതിയായ hosted ശേഷി പരിശോധിച്ചുറപ്പിക്കണം.

ഓരോ JSON രസീതും ചെക്ക്ഔട്ട് ചെയ്ത SHA, വർക്ക്ഫ്ലോ റൺ, ശ്രമം എന്നിവ തിരിച്ചറിയുന്നു.
ചെക്ക്ഔട്ട്/event SHA പൊരുത്തക്കേട് CLI നിരസിക്കുന്നു. പുതിയതോ നീക്കം ചെയ്തതോ ആയ ഒരു ലെയിൻ നിശ്ശബ്ദമായി അപ്രത്യക്ഷമാകാതിരിക്കാൻ,
വർക്ക്ഫ്ലോ ടെസ്റ്റുകൾ നയത്തിലെ അംഗത്വത്തെ വിധിനിർണ്ണയ ജോബിന്റെ `needs` ലിസ്റ്റുമായി ബന്ധിപ്പിക്കുന്നു.
രസീതുകൾ അവയുടെ സ്വന്തം വർക്ക്ഫ്ലോ മാത്രമാണ് ഉൾക്കൊള്ളുന്നത്; പ്രസിദ്ധീകരണം, ഡിപ്ലോയ്മെന്റ്, അല്ലെങ്കിൽ നിലവിലുള്ള ഒരു അഡ്വൈസറി സ്കാനറിന്റെ ആന്തരിക പ്രവർത്തനങ്ങൾ അവയിൽ ഉൾപ്പെടുന്നില്ല.
ബാധകമായ പരിശോധനകൾ ബ്രാഞ്ച് നിയമങ്ങളിൽ നിർബന്ധമാക്കുന്നത് ഒരു പ്രത്യേക അഡ്മിനിസ്ട്രേറ്റീവ് മാറ്റമാണ്; അവയുടെ ജോബുകൾ നിർവചിക്കുന്നത് മാത്രം ഒരു ബ്രാഞ്ചിനെ സംരക്ഷിക്കില്ല.

`API Route Typecheck` രണ്ട് സംയോജിത വിധികൾക്കും
ലോക്കൽ ഫുൾ ഒബ്സർവറിന്റെ സ്റ്റാറ്റിക് പ്രൊഫൈലിനും പുറത്തുള്ള ഒരു സ്വതന്ത്ര വർക്ക്ഫ്ലോ പരിശോധനയാണ്. കൃത്യമായ
കാൻഡിഡേറ്റിനായി അതിന്റെ ഫലം പ്രത്യേകം പരിശോധിക്കുക. `.github/workflows/api-route-typecheck.yml`, `main` അല്ലെങ്കിൽ
`release/**` എന്നിവയിലേക്കുള്ള PR-കളിലും, ഏതെങ്കിലും ബ്രാഞ്ച് ഫാമിലിയിലേക്കുള്ള പുഷുകളിലും, മാനുവൽ ഡിസ്പാച്ചിലും പ്രവർത്തിക്കുന്നു. ഇതിന് പാത്ത് ഫിൽട്ടർ ഇല്ല.
PR ബേസ് റീടാർഗെറ്റുകൾ ഒരു പുതിയ പരിശോധന അഭ്യർത്ഥിക്കുന്നു; ബോഡി/ടൈറ്റിൽ എഡിറ്റുകൾ നിരീക്ഷണത്തിന് മാത്രമുള്ള
`Admission not requested / API Route Typecheck` എന്ന പേര് ഉപയോഗിക്കുന്നതിനാൽ അഡ്മിഷൻ പരിശോധനയ്ക്ക് പകരമാകാൻ അവയ്ക്ക് കഴിയില്ല.
വർക്ക്ഫ്ലോ ഒരു മെർജ്-ഗ്രൂപ്പ് ട്രിഗർ പ്രഖ്യാപിക്കുന്നില്ല. ഈ പരിശോധന ആവശ്യമായ ഏതൊരു മെർജ്-ക്യൂ റോൾഔട്ടും
ആ ഇവന്റിനായി ഇതിന്റെ നിർവഹണം ആദ്യം സ്ഥാപിക്കണം.

### UI എക്സിക്യൂഷൻ ശേഷി

CI, പൂർണ്ണ UI ഇൻവെന്ററി നാല് `test-vitest` മാട്രിക്സ് ഷാർഡുകളായി പ്രവർത്തിപ്പിക്കുന്നു; ഓരോന്നിലും പരമാവധി
രണ്ട് വർക്കർമാരും നിലവിലുള്ള 15-മിനിറ്റ് ജോലി സമയപരിധിയുമുണ്ട്. ആദ്യ ഷാർഡ്
MCP/autoCombo Vitest സ്യൂട്ടും പ്രവർത്തിപ്പിക്കുന്നു. നിർബന്ധിത ജോലി ഫലം ഓരോ മാട്രിക്സ് ലെഗിനെയും ഉൾക്കൊള്ളുന്നു;
ഒരു ഷാർഡിന്റെ പരാജയത്തിനോ റദ്ദാക്കലിനോ കാൻഡിഡേറ്റ് പ്രവേശനം സ്ഥിരീകരിക്കാനാകില്ല.

നൈറ്റ്ലി ഒബ്സർവർ ഓരോ UI ഷാർഡിനും വേറിട്ട exact-candidate രസീത് നിലനിർത്തുന്നു;
ആദ്യ രസീതിൽ MCP എക്സിക്യൂഷനും ഉൾപ്പെടുന്നു. നാല് രസീതുകളും ലോഗുകളും പൊരുത്തപ്പെടുന്ന
എക്സിക്യൂഷൻ ഐഡന്റിറ്റികളും നിർബന്ധമാണ്. ലോക്കലായി `npm run test:vitest:ui` ഇപ്പോഴും
പൂർണ്ണ സ്യൂട്ട് തിരഞ്ഞെടുക്കുന്നു; ഒരു `--shard` റൺ ഭാഗികമായ തെളിവ് മാത്രമാണ്.

### യൂണിറ്റ് കവറേജ് ശേഖരണം

നിലവിലുള്ള ടെസ്റ്റ് എക്സിക്യൂഷനിൽ പന്ത്രണ്ട് യൂണിറ്റ് ഷാർഡുകൾ V8 കവറേജ് ശേഖരിക്കുന്നു. വിജയകരമായ
ഒരു ഷാർഡ്, ഇടക്കാല Istanbul റിപ്പോർട്ട് സൃഷ്ടിക്കാതെ യഥാർത്ഥ ഫയലുകൾ കംപ്രസ് ചെയ്യാൻ
`scripts/ci/compact-v8-coverage.mjs` പ്രവർത്തിപ്പിക്കുന്നു. അന്തിമ Coverage ജോലി പന്ത്രണ്ട് മാനിഫെസ്റ്റുകളും
കാൻഡിഡേറ്റ് SHA, റൺടൈം, സോഴ്സ് റൂട്ട്, ഡാറ്റ ഹാഷുകൾ എന്നിവയ്ക്കെതിരെ പരിശോധിച്ചശേഷം,
c8-ന്റെ റിപ്പോർട്ടറുകളും നിലവിലുള്ള കവറേജ് പരിധികളും പ്രവർത്തിപ്പിക്കുന്നു. ഇൻപുട്ടുകൾ c8-ന്റെ ഗ്ലോബൽ
ഫയൽനാമ ക്രമം നിലനിർത്തുന്നു; മിശ്രിത function/block കവറേജിന് ഓരോ ഷാർഡിലും മുൻകൂട്ടി ലയിപ്പിക്കുന്നത്
സുരക്ഷിതമല്ല. ലഭ്യമല്ലാത്തതോ തെറ്റായ ഘടനയിലുള്ളതോ പൊരുത്തമില്ലാത്തതോ ആയ ഷാർഡുകൾ പ്രവേശനം പരാജയപ്പെടുത്തും.
പരാജയപ്പെട്ട ടെസ്റ്റ് ഷാർഡുകൾ റോ ഡയഗ്നോസ്റ്റിക് കവറേജ് വേറിട്ട് നിലനിർത്തുന്നു; അതിനെ അന്തിമ ലയനത്തിൽ ഉൾപ്പെടുത്താനാകില്ല.

### യൂണിറ്റ് നിർവഹണ പുരോഗതി രസീതുകൾ

പങ്കിട്ട `test:unit:ci:shard` കമാൻഡ് `scripts/ci/unit-progress-reporter.mjs` വഴി `primary`, `dashboard`, `serial`
ഘട്ടങ്ങൾ രേഖപ്പെടുത്തുന്നു. സാധാരണ ടെസ്റ്റ് റിപ്പോർട്ട് തുടർന്നും
ലഭ്യമാണ്. മെറ്റാഡാറ്റ മാത്രം ഉൾപ്പെടുന്ന ഒരു പ്രത്യേക രസീത് ഓരോ ഫയലിന്റെയും ആരംഭവും പൂർത്തീകരണവും രേഖപ്പെടുത്തുന്നു,
കൂടാതെ 30 സെക്കൻഡ് ഇടവേളയിലുള്ള ഹാർട്ട്ബീറ്റ് ഇപ്പോഴും സജീവമായ ഫയലുകളും അവയുടെ കഴിഞ്ഞ സമയവും പട്ടികപ്പെടുത്തുന്നു. അനുവദനീയ പട്ടികയിലുള്ള
നിർവഹണ മെറ്റാഡാറ്റ മാത്രമാണ് ഇത് രേഖപ്പെടുത്തുന്നത്; ടെസ്റ്റ് വിവരണങ്ങൾ, ഔട്ട്പുട്ട്, പിശക് ഉള്ളടക്കങ്ങൾ, പൂർണ്ണ
എൻവയോൺമെന്റ് എന്നിവ സീരിയലൈസ് ചെയ്യുന്നില്ല.

CI-യും Quality-യും JSONL ഫയലുകൾ `unit-progress-ci-<run>-<attempt>-<shard>` എന്നും
`unit-progress-quality-<run>-<attempt>-<shard>` എന്നും നിലനിർത്തുന്നു. ഒരു ജോബ് ടൈംഔട്ട് പിന്നീടുള്ള അപ്ലോഡ് തടഞ്ഞേക്കാം;
ഇതിനകം പുറപ്പെടുവിച്ച ഹാർട്ട്ബീറ്റുകൾ ഡയഗ്നോസ്റ്റിക് തെളിവായി നിലനിൽക്കും. ഹാർട്ട്ബീറ്റുകൾ ഇല്ലാത്തത്
തടയപ്പെട്ടതോ അവസാനിപ്പിക്കപ്പെട്ടതോ ആയ റണ്ണർ പ്രോസസിനെയും സൂചിപ്പിക്കാം. ഈ രസീതുകൾ നിലവിലുള്ള ടെസ്റ്റ് തിരഞ്ഞെടുപ്പ്,
കൺകറൻസി, സമയപരിധികൾ, എക്സിറ്റ് സ്റ്റാറ്റസ് എന്നിവ സംരക്ഷിക്കുന്നു; അവ കാൻഡിഡേറ്റ് പ്രവേശന വിധികളല്ല.

### അംഗീകാര ഫലങ്ങൾ സംയോജിപ്പിക്കുന്ന ഘടകത്തിൽ സൂക്ഷിച്ച തെളിവുകൾ

`scripts/quality/validate-release-acceptance.mjs` നൽകിയ പ്ലാനും അതിന്റെ മാനിഫെസ്റ്റുകളും സംയോജിപ്പിക്കുന്നു; പ്ലാൻ പൂർണ്ണ റിലീസ് പൈപ്പ്ലൈൻ ഉൾക്കൊള്ളുന്നുവെന്ന് അത് സ്ഥാപിക്കുന്നില്ല. പ്ലാൻ `VERIFIED` ആയിരിക്കുമ്പോഴും അതിന്റെ റിപ്പോർട്ടുകൾ വ്യക്തമായി `releaseAcceptance: false` സജ്ജമാക്കുന്നു. `release-acceptance.yml` വർക്ക്ഫ്ലോ ഇപ്പോഴും shadow ടെസ്റ്റ് ഫിക്സ്ചറുകളാണ് ഉപയോഗിക്കുന്നത്; യഥാർഥ build, package, boot അല്ലെങ്കിൽ promotion രസീതുകളല്ല.

സൂക്ഷിച്ച തെളിവുകൾ പരിശോധിക്കാൻ CLI-ക്ക് `--evidence-root` ആവശ്യമാണ്. ഫയലുകൾ `<evidence-root>/<artifact_id>/<member>` എന്ന പാതയിൽ കണ്ടെത്തി SHA-256 ഹാഷ് കണക്കാക്കുന്നു. തെളിവില്ലാത്ത PASS റെക്കോർഡ്, കാണാതായതോ മാറിയതോ ആയ ഫയൽ, സുരക്ഷിതമല്ലാത്ത പാത അല്ലെങ്കിൽ സിംലിങ്ക് എന്നിവ സ്ഥിരീകരണം തടയുന്നു. കാണാതായ ഫയലുകൾ വിജയകരമായ റണ്ണുകളുടെ ശൂന്യമായ ലോഗുകൾക്ക് തുല്യമല്ല. നിലവിലുള്ള SHA/run/attempt പരിശോധനകൾ സ്വതന്ത്രമായി തുടരുന്നു: ബൈറ്റുകൾ പൊരുത്തപ്പെട്ടാലും കാലഹരണപ്പെട്ട രസീത് സാധുവാകില്ല. ഫയലിന്റെ സമഗ്രത നിർവഹണത്തിന്റെ ആധികാരികതയുടെയോ ആർട്ടിഫാക്റ്റിന്റെ promotion-ന്റെയോ തെളിവല്ല.

### സ്റ്റാറ്റിക് സ്കാൻ ഇൻവെന്ററി

പതിപ്പുനിർണ്ണയിച്ച npm-alias ഇൻവെന്ററിയും static-scan അംഗത്വവും
`config/quality/gate-manifest.json`-ലാണ്. സ്ക്രിപ്റ്റ് പേരുകളും കൃത്യമായ കമാൻഡുകളും
`package.json`-നെതിരെ സാധൂകരിക്കാൻ `npm run check:gate-manifest` പ്രവർത്തിപ്പിക്കുക; ചേർക്കലുകളും നീക്കംചെയ്യലുകളും
കമാൻഡ് വ്യതിയാനങ്ങളും ലോക്കൽ ഹുക്കിനെയും CI-യിലെ change-classification ജോലികളെയും പരാജയപ്പെടുത്തും.
ഒരു alias എന്നത് workflow job, matrix instance, test case എന്നിവയിൽ ഒന്നുമല്ല: ഈ എണ്ണങ്ങളെ
പരസ്പരം മാറ്റിസ്ഥാപിക്കാവുന്നതായി അവതരിപ്പിക്കരുത്.

തിരഞ്ഞെടുത്ത alias-കൾ പ്രവർത്തിപ്പിക്കാതെ പരിശോധിക്കാൻ `npm run quality:scan -- --list` അല്ലെങ്കിൽ
`npm run quality:scan:fast -- --list` ഉപയോഗിക്കുക. റണ്ണർ npm എൻട്രിപോയിന്റ് അഭ്യർത്ഥിക്കുന്നതിനാൽ,
അതിന്റെ റൺടൈം—കോൺഫിഗർ ചെയ്തിടത്തെ Bun ഉൾപ്പെടെ—നിലനിർത്തപ്പെടുന്നു.
ആ പ്രൊഫൈലുകൾക്ക് പുറത്തുള്ള alias-കൾ വേറിട്ട് പ്രവർത്തിപ്പിക്കുന്നവയായി മാനിഫെസ്റ്റ് രേഖപ്പെടുത്തുന്നു;
read-only സ്കാൻ പ്രൊഫൈലുകളിൽ maintenance കമാൻഡുകൾ നിരോധിച്ചിരിക്കുന്നു.

ഈ പ്രൊഫൈലുകൾ static scan മാത്രം ഉൾക്കൊള്ളുന്നു. അവ product tests, coverage, packaging,
external checks, അല്ലെങ്കിൽ ഒരു കാൻഡിഡേറ്റിന്റെ പൂർണ്ണ release acceptance എന്നിവ സാക്ഷ്യപ്പെടുത്തുന്നില്ല.
Workflow admission, ലിങ്ക് ചെയ്ത `config/quality/admission-policy.json`,
`scripts/quality/admission-verdict.mjs` എന്നിവ ഉപയോഗിക്കുന്നു. Release-observer പ്രൊഫൈലുകൾ വേറിട്ട് തുടരുന്നു;
അവയുടെ ബാധകമായ പരിശോധനകളും രസീതുകളും സ്വതന്ത്രമായി പരിശോധിക്കുക. പൂർണ്ണ ഒബ്സർവറിന്റെ static
കമാൻഡുകൾ `config/quality/release-green-static-profile.json`-ൽ പ്രഖ്യാപിച്ചിട്ടുണ്ട്; അവയിൽ
`audit:deps`, mutation-test selection, translation checks എന്നിവ ഉൾപ്പെടുന്നു. ലോഡർ npm
കമാൻഡുകളെ package.json-നും മോഡൽ ചെയ്ത CI/Quality പ്രഖ്യാപനങ്ങൾക്കും എതിരെ സാധൂകരിക്കുന്നു; shell token-കൾ
argument-കളായി പ്രവർത്തിപ്പിക്കുന്നതിന് പകരം വ്യതിയാനം നിരസിക്കുന്നു. നിർബന്ധിത സ്കാനറിന്റെ SKIP/INCOMPLETE ഔട്ട്പുട്ടിന്
PASS സ്ഥിരീകരിക്കാനാകില്ല. പ്രൊഫൈൽ അതിന്റെ external exclusion-കൾ രേഖപ്പെടുത്തുന്നു; hosted coverage,
test matrix-കൾ, package അല്ലെങ്കിൽ deployment തെളിവുകൾ എന്നിവയ്ക്ക് ഇത് പകരമാകുന്നില്ല. താഴെയുള്ള വിവരണാത്മക ഇൻവെന്ററി
ഒരു റഫറൻസാണ്; ഒരു gate യഥാർത്ഥത്തിൽ പ്രവർത്തിച്ചു എന്നതിന്റെ തെളിവല്ല.

സ്ക്രിപ്റ്റുകൾ `scripts/check/`-ലും (policy gates) `scripts/quality/`-ലും (ratchet engine) സ്ഥിതിചെയ്യുന്നു.
CI-യുടെ ആധികാരിക ഉറവിടം `.github/workflows/ci.yml` ആണ്.

### പ്രസിദ്ധീകരിച്ച അടിസ്ഥാന ഡോക്യുമെന്റേഷന്റെ ആരോഗ്യം

തിരഞ്ഞെടുത്ത `main`, `release/v*` പുഷുകൾക്ക് ശേഷവും മാനുവൽ ഡിസ്പാച്ചിലുമാണ് `.github/workflows/i18n-base-health.yml` ഡോക്യുമെന്റേഷന്റെ ആരോഗ്യം നിരീക്ഷിക്കുന്നത്. അതിന്റെ ഫിൽട്ടറുകൾ ഡോക്യുമെന്റേഷൻ, റൂട്ട് Markdown, `llm.txt`, വിവർത്തന നില/കോൺഫിഗറേഷൻ, ബന്ധപ്പെട്ട i18n ടൂളിംഗ് എന്നിവ ഉൾക്കൊള്ളുന്നു. ഒരേയൊരു `Published base documentation health` ജോബ് ഹോസ്റ്റ് ചെയ്ത Ubuntu ഉപയോഗിക്കുകയും അഞ്ച് മിനിറ്റ് സമയപരിധി പാലിക്കുകയും ചെയ്യുന്നു. ഡിപെൻഡൻസി ഇൻസ്റ്റാളേഷൻ, വിവർത്തനം, അല്ലെങ്കിൽ നില ഏറ്റെടുക്കൽ എന്നിവയില്ലാതെ അത് റീഡ്-ഒൺലി വാലിഡേഷൻ നടത്തുകയും ഒരു ഡയഗ്നോസ്റ്റിക് രസീത് എഴുതുകയും ചെയ്യുന്നു.

`scripts/i18n/check-base-health.mjs`-ന് സോഴ്സ്-ഹാഷ്, മിസ്സിങ്-ടാർഗറ്റ്, ടാർഗറ്റ്-ഹാഷ്, സ്റ്റേൽ-ട്രാൻസ്ലേഷൻ, സെക്ഷൻ-കാഷ് പൊരുത്തക്കേടുകൾ എന്നിവ ഒന്നും ഉണ്ടാകരുത്. നിലവിലെ കോർ ഡോക്യുമെന്റ്/ലൊക്കേൽ സ്കോപ്പും അതിന്റെ രേഖപ്പെടുത്തിയ ഉറവിടചരിത്രവും ഇത് വാലിഡേറ്റ് ചെയ്യുന്നു. അസാധുവായ കോൺടെക്സ്റ്റ്, അപൂർണ്ണമായ കവറേജ്, അല്ലെങ്കിൽ തടസ്സപ്പെട്ട ചെക്കർ എന്നിവ `INCOMPLETE` സൃഷ്ടിക്കുന്നു; സ്ഥിരീകരിച്ച ഡ്രിഫ്റ്റ് `FAIL` സൃഷ്ടിക്കുന്നു. രണ്ടും പരാജയം സൂചിപ്പിക്കുന്ന എക്സിറ്റ് സ്റ്റാറ്റസ് നൽകുന്നു. രസീത് ചെക്ക്ഔട്ട് SHA, വർക്ക്ഫ്ലോ, റൺ, അറ്റംപ്റ്റ് എന്നിവയുമായി ബന്ധിപ്പിച്ചിരിക്കുന്നു; അത് `i18n-base-health-<sha>-<run>-<attempt>` എന്ന പേരിൽ നിലനിർത്തുന്നു.

ഇത് പ്രസിദ്ധീകരിച്ച അടിസ്ഥാനത്തിന്റെ ഒരു സ്വതന്ത്ര നിരീക്ഷണമാണ്. ഇത് ഒരു PR അല്ലെങ്കിൽ മെർജ്-ഗ്രൂപ്പ് ഇവന്റ്, നിർബന്ധിത PR ചെക്ക്, npm അപരനാമം, അല്ലെങ്കിൽ സ്റ്റാറ്റിക്-സ്കാൻ പ്രൊഫൈൽ അംഗം എന്നിവ ചേർക്കുന്നില്ല. നിലവിലുള്ള ഡിഫറൻഷ്യൽ PR നയവും അടിസ്ഥാന ചെക്കറിന്റെ ഉപദേശാത്മക വർഗ്ഗീകരണങ്ങളും വേറിട്ടുതന്നെ തുടരുന്നു. വിജയകരമായ ഒരു അപ്ലോഡിന് പരാജയപ്പെട്ട ആരോഗ്യഫലത്തെ PASS ആക്കി മാറ്റാനാവില്ല.

### Release PR ഫാസ്റ്റ്-പാത്ത് (`quality.yml`)

`.github/workflows/quality.yml`, main/release PR-കൾ, `main`-ലേക്കുള്ള പുഷുകൾ,
dispatch, merge group എന്നിവയിൽ CI-യെ പൂരിപ്പിക്കുന്നു. PR-കൾ path-filtered fast checks ഉപയോഗിക്കുന്നു. ശാശ്വതമായി
പ്രവർത്തനരഹിതമാക്കിയ duplicate build നീക്കംചെയ്തു; യഥാർത്ഥ build/package/boot പരിശോധനകൾ CI-യിൽ തുടരുന്നു.

#### മറന്നുപോയ സിബ്ലിങ് ടെസ്റ്റുകളുടെ റിപ്പോർട്ട്

`npm run check:forgotten-sibling-tests`, test-impact map-ന്റെ പിന്നിലുള്ള import resolver വീണ്ടും ഉപയോഗിക്കുന്നു.
മാറ്റം വരുത്തിയ ഓരോ production module-നും, സാധ്യതയുള്ള
test pull-request diff-ൽ ഇല്ലെങ്കിൽ നിർണിതമായ
`changed module/symbol -> static consumer -> candidate sibling test` ശൃംഖലകൾ ഇത് റിപ്പോർട്ട് ചെയ്യുന്നു. Markdown സംഗ്രഹവും JSON ഫലവും, തടയൽ പ്രാബല്യത്തിൽ വരുത്തുന്നതിനു മുമ്പുള്ള കാലിബ്രേഷനായി
`forgotten-sibling-tests` workflow artifact ആയി നിലനിർത്തുന്നു.

Barrel re-export-കളും dynamic import-കളും resolution diagnostic-കൾ മാത്രമാണ്; അവ ഒരിക്കലും
തടയുന്ന finding സൃഷ്ടിക്കില്ല. അവലോകനം ചെയ്ത exception-കൾ
`config/quality/forgotten-sibling-allowlist.json`-ലാണ്. ഓരോ entry-യും consumer-നെയും സാധ്യതയുള്ള
test-നെയും വ്യക്തമാക്കുകയും, നിർദ്ദിഷ്ട rationale നൽകുകയും, ഒരു GitHub issue-യിലേക്കോ pull request-ലേക്കോ link ചെയ്യുകയും വേണം. തെറ്റായ രൂപത്തിലുള്ള entry-കൾ
closed ആയി പരാജയപ്പെടും. ഇല്ലാതാക്കിയ candidate test-നെയോ `.skip`/`.todo` ചേർക്കുന്ന diff-നെയോ exception-കൾക്ക് suppress ചെയ്യാനാകില്ല;
assertion ദുർബലപ്പെടുത്തലും മറ്റ് masking-ഉം സ്വതന്ത്രമായി merge തടയുന്ന
`check:test-masking` gate-ന്റെ നിയന്ത്രണത്തിൽ തുടരും.

### ജോലി: `docs-sync-strict`

`main` അല്ലെങ്കിൽ `release/**` ലക്ഷ്യമാക്കിയുള്ള pull request-കളിൽ, ഡ്രാഫ്റ്റ് അല്ലാത്ത (അല്ലെങ്കിൽ വിശ്വസനീയമായ ക്യൂവിലുള്ള), ഡോക്യുമെന്റേഷൻ അല്ലെങ്കിൽ കോഡ് മാറ്റങ്ങളായി വർഗ്ഗീകരിച്ച കാൻഡിഡേറ്റുകൾക്കു മാത്രമാണ് ഈ ജോലി പ്രവർത്തിക്കുന്നത്. #### `check-ui-value-drift` — കാലഹരണപ്പെട്ട-പരിഭാഷാ ഗേറ്റ്

മറ്റ് ഗേറ്റുകൾക്ക് ഘടനാപരമായി കണ്ടെത്താനാകാത്ത ഒരു i18n റിഗ്രഷൻ ഇത് കണ്ടെത്തുന്നു: ഒരു ഇംഗ്ലീഷ് മൂല്യം
വീണ്ടും എഴുതപ്പെടുമ്പോൾ, _മുമ്പത്തെ_ ഇംഗ്ലീഷിൽനിന്ന് രൂപപ്പെടുത്തിയ പരിഭാഷകൾ അവശേഷിക്കുന്നു; അതിനാൽ
ഇംഗ്ലീഷേതര ഉപയോക്താക്കൾ ആത്മവിശ്വാസത്തോടെ എഴുതിയിട്ടുള്ള, എന്നാൽ ഇപ്പോൾ തെറ്റായ പകർപ്പ് തുടർന്നും വായിക്കുന്നു.

ഇത് യഥാർഥത്തിൽ റിലീസ് ചെയ്യപ്പെട്ടിരുന്നു. Antigravity ലോഗിൻ സഹായി വന്നപ്പോൾ (#5203)
`oauthModal.googleOAuthWarning` വീണ്ടും എഴുതപ്പെട്ടു; **43 ലൊക്കേലുകളിൽ 39 എണ്ണത്തിലും**, ഓപ്പറേറ്റർമാരോട് "പൂർണ്ണ
URL പകർത്തി താഴെ ഒട്ടിക്കുക" എന്ന് പറയുന്ന ടെക്സ്റ്റ് തുടർന്നു — ആ പ്രൊവൈഡറിന് പൂർത്തിയാക്കാൻ കഴിയാത്ത ഒരു ഫ്ലോ.
താഴെപ്പറയുന്ന കാരണങ്ങളാൽ #8463 വരെ ഇത് ശ്രദ്ധിക്കപ്പെടാതെ പോയി:

- `sync-ui-keys` **ഇല്ലാത്ത** കീകൾ മാത്രമേ ബാക്ക്ഫിൽ ചെയ്യൂ; **കാലഹരണപ്പെട്ടവ** ഒരിക്കലും ചെയ്യില്ല;
- `check-ui-keys-coverage` കീയുടെ _സാന്നിധ്യം_ കണക്കാക്കുന്നു, അതിനാൽ കാലഹരണപ്പെട്ട ഒരു പരിഭാഷയും കവർ ചെയ്തതായി കണക്കാക്കപ്പെടുന്നു;
- `check-translation-drift` എന്നത് `docs/i18n/<locale>/**.md` ഡോക്യുമെന്റേഷൻ മിററുകളെ ട്രാക്ക് ചെയ്യുന്നു —
  അത് ഒരിക്കലും `src/i18n/messages/*.json` വായിക്കുന്നില്ല. 2026-09 പുനഃസമന്വയം മുതൽ `docs-sync-strict` ജോബിൽ
  ഇത് തടസ്സപ്പെടുത്തുന്നു: ഒരു കോർ ഡോക് എഡിറ്റ് ചെയ്യുക → `npm run i18n:run -- --files=<doc>` (സെക്ഷൻ-തലത്തിലുള്ളത്, ചെലവ് കുറവ്).

**ഡിഫ്-അവബോധമുള്ളത്, ബേസ്ലൈൻ പിന്തുണയുള്ളതല്ല.** മെർജ് ബേസിലെ `en.json`-നെ വർക്കിംഗ് ട്രീയുമായി ഇത് താരതമ്യം ചെയ്യുന്നു;
ഇംഗ്ലീഷ് മൂല്യം മാറിയ ഓരോ കീയിലും, മാറ്റം വരുത്താത്ത പരിഭാഷ ഇപ്പോഴും സൂക്ഷിക്കുന്ന ഏത് ലൊക്കേലും
കാലഹരണപ്പെട്ടതാണ്. ഇത് മനഃപൂർവം **മുൻപേ നിലവിലുള്ള കടം മരവിപ്പിക്കുന്നു** — ദീർഘകാലമായി നിലനിൽക്കുന്ന
ഒരു പരിഭാഷ ഏത് പഴയ ഇംഗ്ലീഷിൽനിന്നാണ് വന്നതെന്ന് ഒരു ഡിഫിന് വെളിപ്പെടുത്താനാകില്ല; അതിനാൽ നിലവിലെ മാറ്റം
സ്പർശിക്കുന്നവയെ മാത്രമാണ് ഗേറ്റ് വിലയിരുത്തുന്നത്. പകരമുള്ള മാർഗമായ ഓരോ കീയ്ക്കുമുള്ള ഹാഷ് ബേസ്ലൈന്
ഏകദേശം 600 KB വലുപ്പമുള്ള ജനറേറ്റ് ചെയ്ത ഒരു ഫയൽ ആവശ്യമായിവരും; നിലവിലുള്ള ഏറ്റവും വലിയ ബേസ്ലൈനിന്റെ
3 മടങ്ങ് വലുപ്പമുള്ള അത് ഓരോ i18n PR-ലും നിരന്തരം മാറിക്കൊണ്ടിരിക്കും.

ഇത് തൃപ്തിപ്പെടുത്താൻ രണ്ട് മാർഗങ്ങളുണ്ട്:

1. ബാധിക്കപ്പെട്ട പരിഭാഷകൾ അപ്ഡേറ്റ് ചെയ്യുക, അല്ലെങ്കിൽ
2. അവയെ `__MISSING__:<new english>` ആയി സജ്ജീകരിക്കുക — അപ്പോൾ റൺടൈം തിരുത്തിയ ഇംഗ്ലീഷ് നൽകുകയും
   (`src/i18n/request.ts::deepMergeFallback`, #7258) കീ പരിഭാഷയ്ക്കായി ക്യൂവിൽ ചേർക്കപ്പെടുകയും ചെയ്യും.

സ്ട്രിങ്ങിന്റെ **അർഥം** മാറിയിട്ടുണ്ടെങ്കിൽ, **കീയുടെ പേര് മാറ്റുന്നതിന്** മുൻഗണന നൽകുക: ഒരു പുതിയ കീയ്ക്ക്
കാലഹരണപ്പെട്ട പരിഭാഷ പാരമ്പര്യമായി ലഭിക്കാനാകില്ല. #8463 ഉപയോഗിച്ച പാറ്റേൺ അതാണ്.

```bash
npm run i18n:check-value-drift          # കർശനം (CI പ്രവർത്തിപ്പിക്കുന്നത്)
npm run i18n:check-value-drift:warn     # റിപ്പോർട്ട് മാത്രം
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

മൂല്യ-വ്യതിയാനവും പുതിയ-കീ ഗേറ്റുകളും
`scripts/i18n/resolve-ui-diff-base.mjs`-ൽ നിന്നുള്ള മാറ്റാനാകാത്ത ഒരേ താരതമ്യം പങ്കിടുന്നു. വർക്ക്ഫ്ലോ ഒരേ base, base-tip,
candidate SHA-കൾ രണ്ട് പരിശോധനകൾക്കും കൈമാറുന്നു. PR/base-retarget, push, merge-group റണ്ണുകൾ അവയുടെ event
context ഉപയോഗിക്കുന്നു. ഒരു candidate branch dispatch ചെയ്യുന്നതിന് അതിന്റെ കൃത്യമായ തുറന്ന PR അല്ലെങ്കിൽ വ്യക്തമായ
`i18n_base_sha` input ആവശ്യമാണ്. ആ input ഇല്ലാതെ `main` അല്ലെങ്കിൽ `release/vX.Y.Z`
dispatch ചെയ്യുകയോ scheduled observation നടത്തുകയോ ചെയ്താൽ, അവസാന commit-നെ അതിന്റെ ആദ്യ parent-ുമായി താരതമ്യം ചെയ്യും; ഇത്
പാരമ്പര്യമായി ലഭിച്ച മുഴുവൻ വിവർത്തന കടബാധ്യതയുടെയും audit അല്ല. Local invocation-ന് വ്യക്തമായ ഒരു comparison base ആവശ്യമാണ്,
ഉദാഹരണത്തിന് മുകളിലുള്ള `BASE_REF` command.

Comparison context ലഭ്യമല്ലാത്തതോ അവ്യക്തമായതോ ആയിരിക്കുക, ആവശ്യമായ catalog വായിക്കാനാകാത്തതോ അസാധുവായതോ ആയിരിക്കുക, കൂടാതെ
candidate മാറിയിരിക്കുക എന്നിവ warn mode-ൽ ഉൾപ്പെടെ exit code **2** സഹിതം `INCOMPLETE` സൃഷ്ടിക്കും.
Catalog വായനകൾ `scripts/i18n/read-ui-catalog.mjs` ഉപയോഗിക്കുന്നു; വായനാ പരാജയങ്ങൾക്ക് പകരമായി
ശൂന്യമായ objects ഉപയോഗിക്കില്ല. ലഭ്യമല്ലാത്ത base-ഉം അപൂർണ്ണമായ input-ഉം PASS സ്ഥാപിക്കുന്നില്ല.

  മുൻകൂർ മുന്നറിയിപ്പായി ഈ റിപ്പോർട്ടുകൾ പരിശോധിക്കുക; പ്രശ്നമുണ്ടാക്കുന്ന ഗേറ്റിന്റെ `_rebaseline_*` കുറിപ്പുകൾ പരിശോധിക്കുക. ഈ ജോലി ഇനി
  സ്ഥിരമായ ഒരു ഇഷ്യൂ സൃഷ്ടിക്കുകയോ അപ്ഡേറ്റ് ചെയ്യുകയോ ഇല്ല; മുമ്പത്തെ റിപ്പോർട്ട് ചരിത്രം #12149-ൽ സംരക്ഷിച്ചിരിക്കുന്നു.

**പുതിയ-കോഡ് മോഡ് (Clean-as-You-Code) — 2026-08-30 മുതൽ, PR അതിവേഗ പാതയിൽ മാത്രം**

`pull_request` ഇവന്റുകളിൽ `quality.yml`, `check:file-size`,
`check:complexity-ratchets`, `check:dead-code` എന്നിവയ്ക്ക് `--base-ref <PR base SHA>` കൈമാറുന്നു. `check:complexity-ratchets`,
`check:dead-code` എന്നിവയ്ക്കായി, ഗേറ്റ് HEAD-നെ മെർജ്-ബേസുമായി താരതമ്യം ചെയ്യുന്നത് **PR മാറ്റം വരുത്തിയ ഫയലുകളിൽ
മാത്രമായി പരിമിതപ്പെടുത്തിയാണ്** (`scripts/check/newCodeMode.mjs`: മെർജ്-ബേസ് താൽക്കാലികമായ ഒരു
`git worktree`-ൽ സൃഷ്ടിക്കുന്നു, അവിടെയും HEAD-ലും ESLint/knip പ്രവർത്തിപ്പിക്കുന്നു, തുടർന്ന് ഓരോ ഫയലിലെയും എണ്ണങ്ങളുടെ വ്യത്യാസം കണക്കാക്കുന്നു):

- **തടയുന്നത്** — PR മാറ്റം വരുത്തിയ ഫയലുകളിൽ സൈക്ലോമാറ്റിക്/കോഗ്നിറ്റീവ് ലംഘനങ്ങളോ ഉപയോഗിക്കാത്ത എക്സ്പോർട്ടുകളോ ചേർത്തു
  (ലോഗിൽ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ഉപദേശാത്മകം** — ആഗോള മൊത്തം, ഫ്രീസ് ചെയ്ത അടിസ്ഥാനരേഖയുമായി താരതമ്യം ചെയ്യുന്നു. പാരമ്പര്യമായി ലഭിച്ച വ്യതിയാനം
  നിരപരാധിയായ ഒരു PR-നെ ഒരിക്കലും പരാജയപ്പെടുത്തില്ല; റിലീസ് അനുരഞ്ജന സമയത്ത് പരിഹരിക്കുന്നതിനായി വ്യതിയാനം ട്രാക്ക് ചെയ്യുകയും
  ഹെഡ്റൂം ജോബ് അത് നിരീക്ഷിക്കുകയും ചെയ്യുന്നു.

`check:file-size` അതിന്റേതായ വ്യവസ്ഥകളിൽ ബേസ് റെഫ് ഉപയോഗിക്കുന്നു (`scripts/check/check-file-size.mjs`, #8522):
ട്രീയിലെ എല്ലാ സോഴ്സ്, ടെസ്റ്റ് ഫയലുകളും ഇത് പരിശോധിക്കുന്നു; PR ബേസിൽ ഓരോ ഫയലിലെയും വരികളുടെ എണ്ണം
`git show` ഉപയോഗിച്ച് വായിക്കുന്നു; തുടർന്ന്, ഒരു ഫയൽ അതിന്റെ അടിസ്ഥാനപരിധി സീലിങ്ങിലും
(`frozen` / `testFrozen`, അല്ലെങ്കിൽ അടിസ്ഥാനപരിധിക്ക് പുറത്തുള്ള ഫയലിന് `cap` / `testCap`) അതിന്റെ ബേസ്
വലുപ്പത്തിലും വലുതായതിനെക്കാൾ കൂടുതലാകുമ്പോൾ മാത്രമാണ് അതിനെ പരാജയപ്പെടുത്തുന്നത്. അതിനാൽ ബേസിൽ ഇതിനകം വ്യതിയാനം വന്ന ഒരു ഫയൽ നിരപരാധിയായ PR-നെ ഒരിക്കലും പരാജയപ്പെടുത്തില്ല.

`check:boundary:ratchet` അതിന്റെ ഏക സംഖ്യയ്ക്കും ഇതേ നിയമം പ്രയോഗിക്കുന്നു
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ഇവന്റുകളിൽ
`quality.yml` fast-gates-ഉം `ci.yml` lint job-ഉം PR base SHA കൈമാറുന്നു, base commit ഒരു
`git archive` export-ൽനിന്ന് അളക്കപ്പെടുന്നു, കൂടാതെ അതിന്റെ `open-sse → src` edge
എണ്ണം `metrics.boundaryOpenSseToSrc`-ന്റെയും base-ലെ എണ്ണത്തിന്റെയും വലിയ മൂല്യത്തെ
മറികടക്കുമ്പോൾ മാത്രമാണ് PR പരാജയപ്പെടുന്നത്. പരിധിക്ക് മുകളിലുള്ള base drift
റിപ്പോർട്ട് ചെയ്യപ്പെടുന്നു (`base drift herdado`), പക്ഷേ കുറ്റമില്ലാത്ത ഒരു PR-നെ ഒരിക്കലും
പരാജയപ്പെടുത്തില്ല; push → main കേവല പരിധി നിലനിർത്തുന്നു, പരിഹരിക്കാനാകാത്ത ഒരു base SHA
ഒരു മുന്നറിയിപ്പോടെ അതിലേക്ക് fallback ചെയ്യുന്നു.

`workflow_dispatch` runs, release-green sweep, nightly headroom job എന്നിവയ്ക്ക് PR base
ഇല്ലാത്തതിനാൽ അവ കേവലമായ (global) താരതമ്യം നിലനിർത്തുന്നു. Coverage, duplication,

## റാച്ചറ്റ് ബേസ്ലൈൻ (`quality-baseline.json`)

റാച്ചറ്റ് എൻജിൻ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` വായിക്കുകയും
പുതുതായി ശേഖരിച്ച `quality-metrics.json`-മായി അതിനെ താരതമ്യം ചെയ്യുകയും ചെയ്യുന്നു. അനുവദനീയമായ എപ്സിലോണിനപ്പുറം
പിന്നോട്ട് പോകുന്ന ഏതൊരു മെട്രിക്കും ബിൽഡ് പരാജയപ്പെടാൻ കാരണമാകും.

നിലവിൽ ട്രാക്ക് ചെയ്യുന്ന മെട്രിക്കുകൾ:

| മെട്രിക്              | ദിശ    | അർത്ഥം                                  |
| --------------------- | ------ | --------------------------------------- |
| `eslintWarnings`      | `down` | ESLint മുന്നറിയിപ്പുകളുടെ എണ്ണം കൂടരുത് |
| `coverage.statements` | `up`   | സ്റ്റേറ്റ്മെന്റ് കവറേജ് കുറയരുത്        |
| `coverage.lines`      | `up`   | ലൈൻ കവറേജ് കുറയരുത്                     |
| `coverage.functions`  | `up`   | ഫംഗ്ഷൻ കവറേജ് കുറയരുത്                  |
| `coverage.branches`   | `up`   | ബ്രാഞ്ച് കവറേജ് കുറയരുത്                |

യഥാർഥമായൊരു മെച്ചപ്പെടുത്തലിനുശേഷം ബേസ്ലൈൻ പുതുക്കാൻ:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` ഫ്ലാഗ് നിലവിൽ അളന്ന മൂല്യങ്ങൾ `quality-baseline.json`-ലേക്ക് എഴുതുന്നു.
മെട്രിക് മെച്ചപ്പെടുത്തിയ മാറ്റത്തോടൊപ്പം ഈ ഫയലും കമ്മിറ്റ് ചെയ്യുക. ബേസ്ലൈൻ പുതുക്കാതെ
ഒരു മെട്രിക് മെച്ചപ്പെടുത്തുന്ന PR, `--require-tighten` വഴി കണ്ടെത്തപ്പെടും (ഘട്ടം 6A.5,
നടപ്പാക്കൽ ശേഷിക്കുന്നു).

### CodeQL റാച്ചറ്റ്: പുതുക്കൽ ആവൃത്തിയും മാനുവൽ ട്രിഗറും

`check:codeql-ratchet` വായിക്കുന്നത് **ഒരു ഷെഡ്യൂൾ അനുസരിച്ച് പുതുക്കുന്ന റിപ്പോയുടെ അവസ്ഥയാണ് — ഓരോ PR-നും പ്രത്യേകം അല്ല.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` റിപ്പോർട്ട് ചെയ്യുന്നത്
`state: configured`, `schedule: weekly` എന്നാണ്: ഇത് GitHub-ന്റെ ഡിഫോൾട്ട്-സെറ്റപ്പ് സ്കാനാണ്, ഓരോ പുഷിനുമുള്ള
വിശകലനമല്ല. അനന്തരഫലം: അലർട്ടുകൾ പരിഹരിക്കുന്ന ഒരു PR മെർജ് ചെയ്തശേഷവും, അടുത്ത ഷെഡ്യൂൾ ചെയ്ത സ്കാൻ
പ്രവർത്തിക്കുന്നതുവരെ റാച്ചറ്റ് പഴയതും കൂടുതലുമായ എണ്ണം വായിച്ചുകൊണ്ടിരിക്കും — അതിനാൽ സ്കാൻ പുതുക്കിയ നിലയിലെത്തുന്നതുവരെ,
പരിഹാര PR-ന്റെ സ്വന്തം തുടർ PR-കൾ ഉൾപ്പെടെ തുറന്നിരിക്കുന്ന എല്ലാ PR-ലും അത് ഒരു റിഗ്രഷൻ റിപ്പോർട്ട് ചെയ്യും.

**മാനുവൽ പുതുക്കൽ**: `gh workflow run codeql.yml --ref release/vX.Y.Z` വിശകലനം വീണ്ടും പ്രവർത്തിപ്പിക്കുകയും
മിനിറ്റുകൾക്കുള്ളിൽ അലർട്ടുകൾ വീണ്ടും പ്രസിദ്ധീകരിക്കുകയും ചെയ്യുന്നു. ആദ്യം `.github/workflows/codeql.yml`
വായിക്കുക — GitHub-ന്റെ "ഡിഫോൾട്ട് സെറ്റപ്പുമായി ഇത് വൈരുധ്യമുണ്ടാക്കുന്നതിനാൽ" ഇത് `workflow_dispatch`-മാത്രമാണെന്ന്
അതിന്റെ ഹെഡർ വിശദീകരിക്കുന്നു (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). `push`/`pull_request`/
`schedule` ട്രിഗറുകൾ പുനഃസ്ഥാപിക്കുന്നതിന് ആദ്യം **ഉടമയുടെ നടപടി** ആവശ്യമാണ്: Settings → Code security →
CodeQL: Default → Advanced. ആ മാറ്റം വരുത്താതെ ഒരു `schedule:` ട്രിഗർ ചേർക്കരുത് — അത്
പരാജയപ്പെടുന്ന റണ്ണുകൾ മാത്രമേ സൃഷ്ടിക്കൂ.

ഫയൽ എൻട്രികൾക്കൊപ്പം അതേ `frozen` ഒബ്ജക്റ്റിനുള്ളിലാണ് അവ സൂക്ഷിച്ചിരിക്കുന്നത്).
ഒരു പരിധി ഉയർത്താൻ കഴിയുന്ന ബോട്ട് നിലവിലെ അവസ്ഥയെക്കാൾ തീർച്ചയായും മോശമായിരിക്കും. റിഗ്രഷൻ
ഗാർഡ്: `tests/unit/verify-ratchet-bank.test.ts`.

job ഒരിക്കലും `release/*`-ലേക്ക് പുഷ് ചെയ്യില്ല — ഒരു മനുഷ്യൻ PR മെർജ് ചെയ്യുന്നതിനാൽ, തെറ്റായ അളവ്
അവലോകനം ചെയ്യപ്പെടാതെ ഉൾപ്പെടാൻ കഴിയില്ല.

## അനുവദനീയ പട്ടികാ നയം

മുൻപേ നിലവിലുണ്ടായിരുന്ന ലംഘനങ്ങൾ കാരണം പരാജയപ്പെടാൻ പാടില്ലാത്ത ഓരോ ഗേറ്റും മാറ്റമില്ലാത്ത ഒരു അനുവദനീയ പട്ടിക ഉപയോഗിക്കുന്നു
(ഉദാ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). നയം ഇതാണ്:

**മൂലകാരണം പരിഹരിക്കുക; ലംഘനം മുൻപേ നിലവിലുള്ളതും അതേ PR-ൽ പരിഹരിക്കാൻ കഴിയാത്തതുമാണെങ്കിൽ മാത്രം അനുവദനീയ പട്ടിക ഉപയോഗിക്കുക.**

ഒരു അനുവദനീയ പട്ടികയിലേക്ക് എൻട്രി ചേർക്കുമ്പോൾ:

1. ന്യായീകരണം ഉൾപ്പെടുന്ന ഒരു കമന്റ് ചേർക്കുക.
2. ട്രാക്കിംഗ് ഇഷ്യൂ പരാമർശിക്കുക (ഉദാ., `// #3498 — Phase 2 feature, not yet implemented`).
3. ലംഘനം പരിഹരിക്കുന്ന അതേ PR-ൽ എൻട്രി നീക്കംചെയ്യുക — സജീവമായ ഒരു ലംഘനത്തെ ഇനി ഒഴിവാക്കാത്ത കാലഹരണപ്പെട്ട എൻട്രി തന്നെ ഒരു തകരാറാണ് (6A.3-ലെ കാലഹരണപ്പെട്ട എൻഫോഴ്സ്മെന്റ് നടപ്പിലാക്കിയാൽ, ഒറ്റപ്പെട്ട അനുവദനീയ പട്ടികാ എൻട്രി കാരണം ഗേറ്റ് പരാജയപ്പെടും).

ടെസ്റ്റുകൾ വേഗത്തിൽ വിജയിപ്പിക്കാൻ അനുവദനീയ പട്ടികാ എൻട്രികൾ ചേർക്കരുത്. വളർന്നുകൊണ്ടിരിക്കുന്ന അനുവദനീയ പട്ടികയോടുകൂടിയ വിജയകരമായ ഗേറ്റ് ഗുണനിലവാരത്തെക്കുറിച്ചുള്ള തെറ്റായ ആത്മവിശ്വാസമാണ് നൽകുന്നത്.

### നിങ്ങളുടെ PR-ൽ ഒരു ഗേറ്റ് പരാജയപ്പെടുമ്പോൾ

1. **ഗേറ്റ് ഔട്ട്പുട്ട് ശ്രദ്ധാപൂർവം വായിക്കുക** — ഏത് ഫയലോ സിംബലോ ആണ് നിയമം ലംഘിച്ചതെന്ന് അത് കൃത്യമായി അറിയിക്കുന്നു.
2. **ലംഘനം പരിഹരിക്കുക** — മിക്ക ഗേറ്റുകളും നിർണ്ണായകമായ ഫയൽസിസ്റ്റം പരിശോധനകളാണ്; കോഡ് ശരിയായാലുടൻ അവ വിജയിക്കും.
3. **ലംഘനം മുൻപേ നിലവിലുള്ളതാണെങ്കിൽ** (അതായത്, നിങ്ങൾ അത് അവതരിപ്പിച്ചതല്ലെങ്കിലും ഗേറ്റ് ഇപ്പോൾ അതിനെ ഉൾക്കൊള്ളുന്നു): ന്യായീകരണ കമന്റും ട്രാക്കിംഗ് ഇഷ്യൂവും സഹിതം ഒരു അനുവദനീയ പട്ടികാ എൻട്രി ചേർക്കുക.
4. **ഗേറ്റ് ഒരു റാച്ചറ്റ് ആണെങ്കിൽ** (കവറേജ്, ESLint മുന്നറിയിപ്പുകൾ, ഡ്യൂപ്ലിക്കേഷൻ, സങ്കീർണ്ണത): നിങ്ങളുടെ മാറ്റം മെട്രിക് മോശമാക്കി. അടിസ്ഥാന പ്രശ്നം പരിഹരിക്കുക, അല്ലെങ്കിൽ (അപൂർവമായി) മാറ്റം മനഃപൂർവമുള്ളതും മെട്രിക്കിലെ ഇടിവ് സ്വീകാര്യവുമാണെങ്കിൽ `npm run quality:ratchet -- --update` പ്രവർത്തിപ്പിക്കുക — എന്നാൽ PR വിവരണത്തിൽ അതിന്റെ കാരണം രേഖപ്പെടുത്തുക.
5. **ഉപദേശാത്മക ഗേറ്റുകൾ** (`continue-on-error: true`) വിവരദായകമാണ് — അവ മെർജ് തടയില്ല, എന്നാൽ CI സംഗ്രഹത്തിൽ ദൃശ്യമാകും. എന്നിരുന്നാലും അവ പരിഹരിക്കുക.

## ഒരു പുതിയ ഗേറ്റ് ചേർക്കൽ

1. `scripts/check/check-<name>.mjs` (അല്ലെങ്കിൽ `.ts`) സൃഷ്ടിക്കുക. നയ ഗേറ്റുകൾ 0/1 നിലയിൽ പുറത്തുകടക്കുന്നു.
   റാച്ചെറ്റ്-രീതിയിലുള്ള ഗേറ്റുകൾ `collect-metrics.mjs` വഴി `quality-metrics.json`-ലേക്ക് ഒരു മെട്രിക് പുറപ്പെടുവിക്കുന്നു.
2. `package.json`-ൽ `"check:<name>": "node scripts/check/check-<name>.mjs"` ചേർക്കുക, കൂടാതെ
   `config/quality/gate-manifest.json`-ൽ അപരനാമവും അതിന്റെ കൃത്യമായ കമാൻഡും സമന്വയിപ്പിക്കുക.
   നിലവിലുള്ള ഒരു സാധൂകരണ അപരനാമം മാറ്റുമ്പോഴോ നീക്കം ചെയ്യുമ്പോഴോ ഇതേ സമന്വയം പ്രയോഗിക്കുക.
   `npm run check:gate-manifest` പ്രവർത്തിപ്പിക്കുക; pre-commit hook-ഉം CI മാറ്റ വർഗ്ഗീകരണവും
   ഈ കരാർ നിർബന്ധമാക്കുന്നു.
3. ഉചിതമായ ജോബിന് കീഴിൽ `.github/workflows/ci.yml`-ൽ അത് ബന്ധിപ്പിക്കുക
   (നയം → `lint` അല്ലെങ്കിൽ `docs-sync-strict`; റാച്ചെറ്റ് → `quality-gate`).
4. അതിന് ഒരു അനുവദനീയ പട്ടികയുണ്ടെങ്കിൽ, കാലഹരണപ്പെട്ട എൻട്രികൾ സ്വയമേവ കണ്ടെത്തുന്നതിനായി
   `scripts/check/lib/allowlist.mjs`-ൽ നിന്നുള്ള `reportStaleEntries()` പ്രയോഗിക്കുക.
5. ഗേറ്റിന്റെ കണ്ടെത്തൽ ലോജിക് ഉൾക്കൊള്ളുന്ന ഒരു ടെസ്റ്റ് `tests/unit/build/`-ൽ എഴുതുക.
6. ഈ പ്രമാണം അപ്ഡേറ്റ് ചെയ്യുക (പ്രസക്തമായ ജോബ് പട്ടികയിൽ ഒരു വരി ചേർക്കുക).

- **CVE സ്കാനിംഗ്** — ❌ **വൃത്തിയുള്ള ലയനമല്ല.** `audit:deps` എല്ലാ അഞ്ച് lockfile-ുകളിലുമുള്ള ഗുരുതര ഉപദേശങ്ങളും അപൂർണ്ണമായ ഓഡിറ്റുകളും തടയുന്നു, അതേസമയം നിലവിലെ നയപ്രകാരം ഉയർന്ന തീവ്രതയുള്ള ഉപദേശങ്ങൾ മുന്നറിയിപ്പുകളായി റിപ്പോർട്ട് ചെയ്യുന്നു; `check:vuln-ratchet` (osv) ചെക്ക്-ഇൻ ചെയ്ത baseline-നോടുള്ള ഒരു _പിന്നോട്ടുപോക്ക്_ ഉണ്ടായാൽ മാത്രമേ പരാജയപ്പെടൂ, കൂടാതെ ആവശ്യമായപ്പോൾ അളവുകൾ ലഭ്യമല്ലെങ്കിൽ അവ നിരസിക്കുകയും ചെയ്യുന്നു. വ്യത്യസ്ത അർത്ഥരീതികളാണ് — `audit:deps` ഒഴിവാക്കിയാൽ സമ്പൂർണ്ണ ഗുരുതര ഗേറ്റും സ്വതന്ത്ര പാക്കേജ് ഓഡിറ്റ് രേഖകളും നഷ്ടപ്പെടും. രണ്ടും നിലനിർത്തുക.
- **സൈക്കിൾ കണ്ടെത്തൽ** — ✅ **പൂർത്തിയായി** (#15159 G-01/G-02). ഇവിടെയുള്ള പഴയ വാചകം `check:cycles`-നെ “പച്ചയായ, ക്യൂറേറ്റ് ചെയ്ത” ഗേറ്റ് എന്ന് വിളിക്കുകയും `check:circular-deps` (dpdm) 91 സൈക്കിളുകൾ റിപ്പോർട്ട് ചെയ്തതിനാൽ അതിനെ ബ്ലോക്കിംഗ് ആയി നിലനിർത്തുന്നത് ന്യായീകരിക്കുകയും ചെയ്തിരുന്നു. ആ പച്ച നില ഒരു **തെറ്റായ പച്ച** ആയിരുന്നു: `check:cycles` 5 ഉപഡയറക്ടറികൾ (450 ഫയലുകൾ) സ്കാൻ ചെയ്തു, സ്റ്റാറ്റിക് `import|export … from` മാത്രമാണ് പൊരുത്തപ്പെടുത്തിയത്, കൂടാതെ എല്ലാ `@/`, `@omniroute/open-sse/` സ്പെസിഫയറുകളും ഒഴിവാക്കി; അതിനാൽ repo-യിൽ കൂടുതലായി ഉണ്ടായിരുന്ന dynamic-import + alias സൈക്കിളുകൾ അതിന് കാണാൻ കഴിഞ്ഞില്ല. പരിഹരിച്ചു: ഗേറ്റ് ഇപ്പോൾ `src` + `open-sse` (5023 ഫയലുകൾ) പരിശോധിക്കുന്നു, TypeScript AST-യിൽനിന്ന് സ്പെസിഫയറുകൾ ശേഖരിക്കുന്നു (അതിനാൽ `import("…")` കണക്കാക്കപ്പെടും, എന്നാൽ type-position `typeof import("…")` കണക്കാക്കപ്പെടില്ല), കൂടാതെ tsconfig `paths` പരിഹരിക്കുന്നു. ഇത് 0 അല്ല, **14** സൈക്കിളുകൾ കണ്ടെത്തുന്നു. മുമ്പേ നിലവിലുണ്ടായിരുന്ന 14 സൈക്കിളുകൾ ഒരു ഗേറ്റ് PR-ൽ പരിഹരിക്കാൻ കഴിയാത്തതിനാൽ, `check:cycles` ഇപ്പോൾ ഒരു **റാച്ചറ്റ്** ആണ് (`--ratchet`, `quality-baseline.json`-ൽ പരിധി `metrics.cycles.value = 14`, `direction: down`) — ഏത് _പിന്നോട്ടുപോക്കും_ ഇത് തടയും, എണ്ണം കുറയാൻ മാത്രമേ കഴിയൂ. CI `npm run check:cycles:ratchet` പ്രവർത്തിപ്പിക്കുന്നു. ഘട്ടംഘട്ടമായ കുറയ്ക്കൽ **A-01**-നൊപ്പം പുരോഗമിക്കും. വിശാലമായ രണ്ടാമത്തെ അഭിപ്രായമായി `check:circular-deps` (dpdm) ഉപദേശാത്മകമായി തുടരും.

`check-ui-value-drift`-ന്റെ സഹോദര ഗേറ്റ്. വിവർത്തനങ്ങൾ പുതുക്കാതെ വിട്ടിരിക്കെ ഒരു ഇംഗ്ലീഷ് മൂല്യം

അത് ലഭിക്കാതെ പോയാൽ ഈ ഗേറ്റ് കണ്ടെത്തുന്നു.

`check-ui-keys-coverage`-ന് ഈ വിഭാഗം കണ്ടെത്താനാവില്ല: അത് ഓരോ locale-നും ഒരു ശതമാനപരമായ കുറഞ്ഞ

ഓരോ ഭാഷയ്ക്കുമുള്ള ഒരു ശതമാനത്തിന് "ഈ ഫീച്ചർ വിവർത്തനം ചെയ്യാതെ പുറത്തിറങ്ങി" എന്ന് പ്രകടിപ്പിക്കാനാവില്ല
