ഈ പ്രമാണമാണ് OmniRoute-ലെ എല്ലാ CI ഗുണനിലവാര ഗേറ്റുകൾക്കുമുള്ള ആധികാരിക റഫറൻസ്.
ഓരോ ഗേറ്റും, അത് എന്താണ് സാധൂകരിക്കുന്നത്, ഏത് CI ജോബിലാണ് അത് പ്രവർത്തിക്കുന്നത്, അത്
ഒരു റാച്ചറ്റ് ബേസ്ലൈൻ ആണോ അതോ പാസ്/ഫെയിൽ നയമാണോ ഉപയോഗിക്കുന്നത്, ബിൽഡ് തടയുന്നതാണോ അതോ ഉപദേശാത്മകമാണോ എന്നിവ ഇതിൽ വിവരിക്കുന്നു.

ഒരു ഹ്രസ്വ സംഗ്രഹത്തിനും അനുവദനീയ പട്ടികാ നയത്തിനും `AGENTS.md`-ലെ
"ഗുണനിലവാര ഗേറ്റുകളും റാച്ചറ്റുകളും" വിഭാഗം കാണുക. ഇതേ സിസ്റ്റത്തിന്റെ നിർണായക വിലയിരുത്തൽ,
മെച്യൂരിറ്റി വർഗ്ഗീകരണം, ടൂൾ-അഗ്നോസ്റ്റിക് പുനരാവിഷ്കരണ പദ്ധതി എന്നിവയ്ക്കായി
[ഗുണനിലവാര ഗേറ്റ് പ്ലേബുക്ക്](../ops/QUALITY_GATE_PLAYBOOK.md) കാണുക.

## ഗേറ്റ് ഇൻവെന്ററിയും എക്സിക്യൂഷൻ പ്രൊഫൈലുകളും

### സ്ഥാനാർത്ഥി പ്രവേശനം

CI, ക്വാളിറ്റി ഗേറ്റ്സ് വർക്ക്ഫ്ലോകൾ ഓരോന്നും സ്ഥിരമായ ഒരു വിധി പുറപ്പെടുവിക്കുന്നു: `Gate / CI`, `Gate / Quality`. അവരുടെ വേർഷൻ ചെയ്ത അഡ്മിഷൻ പോളിസി ഓരോ അപ്സ്ട്രീം ജോലിയും ആവശ്യമുള്ളതോ ഉപദേശമോ ആയി കണക്കാക്കുന്നു. ബാധകമായ ആവശ്യമായ ജോലി വിജയിക്കണം: നഷ്ടമായതും റദ്ദാക്കിയതും ഒഴിവാക്കിയതും തീർച്ചപ്പെടുത്താത്തതും അറിയാത്തതുമായ ഫലങ്ങൾക്ക് PASS സ്ഥാപിക്കാൻ കഴിയില്ല. സാധുവായ ഡോക്സ്-ഒൺലി അല്ലെങ്കിൽ കാറ്റലോഗ്-ഒൺലി വർഗ്ഗീകരണത്തിന് ഒരു കോഡ് ലെയ്നെ അപ്രായോഗികമാക്കാം; ഒരു സാധാരണ ഡ്രാഫ്റ്റ് PR ഒരു അംഗീകൃത സ്ഥാനാർത്ഥിയല്ല. ഒരു `hotfix` ലേബൽ തെളിവുകൾ ഒഴിവാക്കില്ല.

രണ്ട് വർക്ക്ഫ്ലോകളും PRs main/release ബ്രാഞ്ചുകളിലേക്കും, `main` ലേയ്ക്കും, മാനുവൽ ഡിസ്പാച്ച്, ലയന-ഗ്രൂപ്പ് ഇവൻ്റുകളിലേക്കും പുഷ് ചെയ്യുന്നു. പുഷ്, ഡിസ്പാച്ച്, മെർജ്-ഗ്രൂപ്പ് എന്നിവ മുഴുവൻ തിരഞ്ഞെടുപ്പും പ്രവർത്തിപ്പിക്കുക. ഒരു വിശ്വസനീയമായ Mergify ക്യൂ ഡ്രാഫ്റ്റ് ബാധകമായ `full-code`/`full-code-e2e` ജോലികളും പ്രവർത്തിപ്പിക്കുന്നു; സാധാരണ PRs അവരെ ഒഴിവാക്കുക. ഒരു മാനുവൽ ലയനത്തിന് മുമ്പ്, കൃത്യമായ കാൻഡിഡേറ്റിൽ ഒരു പൂർണ്ണ ഡിസ്പാച്ച് പ്രവർത്തിപ്പിക്കുക. `release/**` ലേക്കുള്ള പുഷുകൾ ഈ വർക്ക്ഫ്ലോകൾ ആരംഭിക്കുന്നില്ല; റിലീസ്-ഗ്രീൻ ലയിപ്പിച്ച അടിസ്ഥാനം പ്രത്യേകം നിരീക്ഷിക്കുന്നു (`docs/ops/RUNNER_BOX.md` → ഹോസ്റ്റ് ചെയ്ത പാത). ഫോർക്കുകളും ലയന ഗ്രൂപ്പുകളും ജോലികൾക്കായി ഹോസ്റ്റ് ചെയ്ത റണ്ണേഴ്സിനെ ഉപയോഗിക്കുന്നു, അല്ലാത്തപക്ഷം സ്വയം-ഹോസ്റ്റഡ് റണ്ണേഴ്സിനെ തിരഞ്ഞെടുക്കുന്നു; റോൾഔട്ടിനു മുമ്പ് മതിയായ ഹോസ്റ്റ് ശേഷി പരിശോധിച്ചിരിക്കണം.

ഒരു സാധാരണ PR ഫാസ്റ്റ് സെലക്ഷൻ പ്രവർത്തിപ്പിക്കുന്നു. അഡ്മിഷൻ പോളിസിയുടെ `full-code`, `full-code-e2e` പാതകൾ (E2E, ഇൻ്റഗ്രേഷൻ, പാക്കേജ് ആർട്ടിഫാക്റ്റ്, Electron സ്മോക്ക്, Bun SQLite, ഇക്കോസിസ്റ്റം, പ്രോട്ടോക്കോൾ ക്ലയൻ്റുകൾ) ഒരു മെർജിഫൈ ക്യൂ ഡ്രാഫ്റ്റിൽ അല്ലെങ്കിൽ ഒരു പൂർണ്ണ ഓട്ടത്തിൽ മാത്രം പ്രവർത്തിക്കുന്നു: `gh workflow run ci.yml --ref <branch>`.

ഓരോ JSON രസീതും ചെക്ക്-ഔട്ട് SHA, വർക്ക്ഫ്ലോ റൺ, ശ്രമം എന്നിവ തിരിച്ചറിയുന്നു. CLI ഒരു checkout/event SHA പൊരുത്തക്കേട് നിരസിക്കുന്നു. വർക്ക്ഫ്ലോ പരിശോധനകൾ പോളിസി അംഗത്വത്തെ വിധി ജോലിയുടെ `needs` ലിസ്റ്റുമായി ബന്ധിപ്പിക്കുന്നതിനാൽ പുതിയതോ നീക്കം ചെയ്തതോ ആയ പാത നിശബ്ദമായി അപ്രത്യക്ഷമാകില്ല. രസീതുകൾ അവരുടെ സ്വന്തം വർക്ക്ഫ്ലോ ഉൾക്കൊള്ളുന്നു, പ്രസിദ്ധീകരണമോ വിന്യാസമോ നിലവിലുള്ള ഒരു ഉപദേശക സ്കാനറിൻ്റെ ഇൻ്റേണലുകളോ അല്ല. ബ്രാഞ്ച് നിയമങ്ങളിൽ ആവശ്യമായ ബാധകമായ പരിശോധനകൾ നടത്തുന്നത് ഒരു പ്രത്യേക ഭരണപരമായ മാറ്റമാണ്; അവരുടെ ജോലികൾ നിർവചിക്കുന്നത് ഒരു ശാഖയെ സംരക്ഷിക്കുന്നില്ല.

`API Route Typecheck` ഒരു സ്വതന്ത്ര വർക്ക്ഫ്ലോ പരിശോധനയാണ്, മൊത്തത്തിലുള്ള വിധിന്യായങ്ങൾക്കും പ്രാദേശിക പൂർണ്ണ നിരീക്ഷകൻ്റെ സ്റ്റാറ്റിക് പ്രൊഫൈലിനും പുറത്താണ്. കൃത്യമായ കാൻഡിഡേറ്റിനായി അതിൻ്റെ ഫലം പ്രത്യേകം പരിശോധിക്കുക. `.github/workflows/api-route-typecheck.yml` PRs ൽ `main` അല്ലെങ്കിൽ `release/**` ആയി പ്രവർത്തിക്കുന്നു, ഒന്നുകിൽ ബ്രാഞ്ച് ഫാമിലി, മാനുവൽ ഡിസ്പാച്ച്, `checks_requested` തരം `merge_group` ഇവൻ്റുകൾ എന്നിവയിലേക്ക് തള്ളുന്നു. ഇതിന് പാത്ത് ഫിൽട്ടർ ഇല്ല. ഗ്രൂപ്പുകൾ ലയിപ്പിക്കുക `merge_group.head_sha` പരിശോധിക്കുക; മറ്റ് ഇവൻ്റുകൾ `github.sha` പരിശോധിക്കുക. എല്ലാ ഇവൻ്റുകളും ഒരേ API ഡയഗ്നോസ്റ്റിക് ഗേറ്റും ഗേറ്റ് യൂണിറ്റ് ടെസ്റ്റുകളും ഉപയോഗിക്കുന്നു. PR അടിസ്ഥാന retargets ഒരു പുതിയ പരിശോധന അഭ്യർത്ഥിക്കുന്നു; body/title എഡിറ്റുകൾ നിരീക്ഷണത്തിന് മാത്രമുള്ള പേര് `Admission not requested / API Route Typecheck` ഉപയോഗിക്കുന്നു, പ്രവേശന പരിശോധനയ്ക്ക് പകരം വയ്ക്കാൻ കഴിയില്ല.

### അക്സെപ്റ്റൻസ് റിഡ്യൂസറിൽ നിലനിർത്തുന്ന തെളിവ്

`scripts/quality/validate-release-acceptance.mjs` നൽകിയ പ്ലാനും അതിന്റെ മാനിഫെസ്റ്റുകളും റിഡ്യൂസ് ചെയ്യുന്നു; പൂർണ്ണ release പൈപ്പ്ലൈൻ ആ പ്ലാൻ ഉൾക്കൊള്ളുന്നുവെന്ന് ഇത് സ്ഥാപിക്കുന്നില്ല.
ആ പ്ലാൻ `VERIFIED` ആയിരിക്കുമ്പോഴും അതിന്റെ റിപ്പോർട്ടുകൾ `releaseAcceptance: false` എന്ന് വ്യക്തമായി സജ്ജീകരിക്കുന്നു. `release-acceptance.yml` വർക്ക്ഫ്ലോ ഇപ്പോഴും യഥാർഥ build, package, boot, promotion രസീതുകൾക്കുപകരം shadow fixtures ആണ് ഉപയോഗിക്കുന്നത്.

നിലനിർത്തിയ തെളിവ് പരിശോധിക്കാൻ CLI-ക്ക് `--evidence-root` ആവശ്യമാണ്. ഫയലുകൾ `<evidence-root>/<artifact_id>/<member>` എന്ന രീതിയിൽ പരിഹരിക്കുകയും SHA-256 ഉപയോഗിച്ച് ഹാഷ് ചെയ്യുകയും ചെയ്യുന്നു. തെളിവില്ലാത്ത ഒരു PASS റെക്കോർഡ്, ലഭ്യമല്ലാത്തതോ മാറ്റംവന്നതോ ആയ ഫയൽ, സുരക്ഷിതമല്ലാത്ത പാത, അല്ലെങ്കിൽ symlink എന്നിവ verification തടയുന്നു. ലഭ്യമല്ലാത്ത ഫയലുകൾ ശൂന്യമായ വിജയകരമായ ലോഗുകൾക്ക് തുല്യമല്ല. നിലവിലുള്ള SHA/run/attempt പരിശോധനകൾ സ്വതന്ത്രമായി തുടരുന്നു: ബൈറ്റുകൾ പൊരുത്തപ്പെടുന്നതുകൊണ്ട് കാലഹരണപ്പെട്ട ഒരു രസീതിനെ സാധൂകരിക്കാനാവില്ല. ഫയൽ സമഗ്രത എക്സിക്യൂഷന്റെ ആധികാരികതയ്ക്കോ artifact promotion-നോ തെളിവല്ല.

### സ്ഥിരീകരിച്ച CI build ആണ് DAST ഉപയോഗിക്കുന്നത്

നിർബന്ധമായ `dast-smoke` CI job, `build`-നു ശേഷം `.github/workflows/dast-smoke.yml` വിളിക്കുന്നു. പിന്തുണയുള്ള fork PR-കൾ, release ലക്ഷ്യമിടുന്ന PR-കൾ, merge group-കൾ എന്നിവയുൾപ്പെടെ build പിന്തുടരുന്ന അതേ code/draft തിരഞ്ഞെടുപ്പാണ് ഇതും പിന്തുടരുന്നത്. DAST job ഇല്ലാതാകുക, പരാജയപ്പെടുക, റദ്ദാകുക അല്ലെങ്കിൽ അപ്രതീക്ഷിതമായി ഒഴിവാക്കപ്പെടുക എന്നിവ `Gate / CI` തടയും. പുനരുപയോഗിക്കാവുന്ന workflow-യ്ക്ക് സ്വതന്ത്ര PR/dispatch trigger ഇല്ല; manual validation CI-യുടെ dispatch ഉപയോഗിക്കുന്നു. അതിനാൽ build-ഉം consumer-ഉം ഒരേ run-ൽ തുടരുന്നു.

`scripts/ci/next-build-provenance.mjs`, പൂർണ്ണ Next artifact-നെ അതിന്റെ tar digest, repository/event/run, producer attempt, head/base/checkout/tree, workflow തിരിച്ചറിയലുകൾ, lockfile, കൃത്യമായ Node version/ABI, platform, bundler എന്നിവയുമായി ബന്ധിപ്പിച്ച് ഉറപ്പിക്കുന്നു. DAST, `needs.build.outputs`-ൽ നിന്ന് മാറ്റാനാകാത്ത artifact ID തിരഞ്ഞെടുക്കുന്നു; download digest പരിശോധന നിർബന്ധമാക്കുന്നു. അനുവദിച്ച പട്ടികയിലെ രണ്ട് അംഗങ്ങളെ `scripts/ci/unpack-ci-build.py` വഴി വേർതിരിക്കുന്നതിന് മുമ്പ് ZIP hash സ്വതന്ത്രമായി കണക്കാക്കി producer digest-നോട് താരതമ്യം ചെയ്യുന്നു. Next tree വേർതിരിക്കുന്നതിന് മുമ്പ് manifest-ഉം tar archive-ഉം സ്വതന്ത്ര producer output-കളുമായി പൊരുത്തപ്പെടണം. Branch-ലെ ഏറ്റവും പുതിയ വിജയിച്ച build-നായി ഇത് ഒരിക്കലും തിരയുന്നില്ല. ID-യും എല്ലാ input-കളും ഇപ്പോഴും പൊരുത്തപ്പെടുന്നെങ്കിൽ partial rerun-ന് അതേ producer attempt വീണ്ടും ഉപയോഗിക്കാം; receipt രണ്ട് attempt-കളും രേഖപ്പെടുത്തുന്നു.

Consumer repository വായിക്കാൻ മാത്രം അനുമതിയുള്ള hosted Linux runner-ൽ പ്രവർത്തിക്കുന്നു; repository secret-കൾ ഇല്ല. Producer ഉപയോഗിച്ച കൃത്യമായ Node version ഇൻസ്റ്റാൾ ചെയ്ത ശേഷം `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` ഉപയോഗിച്ച് CLI നിർമ്മിക്കുന്നു. ഏതെങ്കിലും fallback build-നു മുമ്പ് standalone server ഇല്ലാത്ത അവസ്ഥ `scripts/build/standaloneInput.mjs` നിരസിക്കുന്നു; സാധാരണ പ്രാദേശിക CLI build-കൾ നിലവിലുള്ള fallback നിലനിർത്തുന്നു. Server readiness, Schemathesis, promptfoo എന്നിവയെല്ലാം മാറ്റമില്ലാത്ത 25 മിനിറ്റ് job പരിധിക്കുള്ളിൽ വിജയിക്കണം. Provenance receipt input തിരിച്ചറിയലും bytes-ഉം തെളിയിക്കുന്നു; വിജയിച്ച DAST scan തെളിയിക്കുന്നില്ല. Artifact കാലഹരണപ്പെടൽ, runner തടസ്സം, scanner പരാജയം എന്നിവ അപൂർണ്ണമോ പരാജയപ്പെട്ടതോ ആയ തെളിവായി തുടരും; advisory wrapper വഴി അവയെ PASS ആക്കാനാവില്ല.

### UI എക്സിക്യൂഷൻ ശേഷി

CI പൂർണ്ണ UI ഇൻവെന്ററി നാല് `test-vitest` മാട്രിക്സ് ഷാർഡുകളായി പ്രവർത്തിപ്പിക്കുന്നു; ഓരോ ഷാർഡിലും പരമാവധി രണ്ട് വർക്കറുകളും നിലവിലുള്ള 15 മിനിറ്റ് ജോബ് സമയപരിധിയും ഉണ്ടായിരിക്കും. ആദ്യ ഷാർഡ് MCP/autoCombo Vitest സ്യൂട്ടും പ്രവർത്തിപ്പിക്കുന്നു. നിർബന്ധിത ജോബ് ഫലം എല്ലാ മാട്രിക്സ് ലെഗുകളെയും ഉൾക്കൊള്ളുന്നു; ഒരു ഷാർഡിന്റെ പരാജയത്തിനോ റദ്ദാക്കലിനോ കാൻഡിഡേറ്റ് പ്രവേശനം സ്ഥാപിക്കാനാവില്ല.

nightly observer ഓരോ UI ഷാർഡിനുമായി വേറിട്ട exact-candidate രസീത് നിലനിർത്തുന്നു; ആദ്യ രസീതിലെ MCP എക്സിക്യൂഷനും ഇതിൽ ഉൾപ്പെടുന്നു. നാല് രസീതുകളും ലോഗുകളും പൊരുത്തപ്പെടുന്ന എക്സിക്യൂഷൻ ഐഡന്റിറ്റികളും നിർബന്ധമാണ്. ലോക്കൽ `npm run test:vitest:ui` ഇപ്പോഴും പൂർണ്ണ സ്യൂട്ട് തിരഞ്ഞെടുക്കുന്നു; ഒരു `--shard` റൺ ഭാഗികമായ തെളിവ് മാത്രമാണ്.

### യൂണിറ്റ് കവറേജ് ശേഖരണം

പന്ത്രണ്ട് യൂണിറ്റ് ഷാർഡുകളും അവയുടെ നിലവിലുള്ള ടെസ്റ്റ് എക്സിക്യൂഷനിൽ V8 കവറേജ് ശേഖരിക്കുന്നു. വിജയകരമായ ഒരു ഷാർഡ്, ഇടക്കാല Istanbul റിപ്പോർട്ട് സൃഷ്ടിക്കാതെ യഥാർഥ ഫയലുകൾ കംപ്രസ് ചെയ്യുന്നതിന് `scripts/ci/compact-v8-coverage.mjs` പ്രവർത്തിപ്പിക്കുന്നു. അന്തിമ Coverage ജോബ്, കാൻഡിഡേറ്റ് SHA, runtime, source root, data hash-കൾ എന്നിവയ്ക്കെതിരെ പന്ത്രണ്ട് മാനിഫെസ്റ്റുകളും പരിശോധിച്ചശേഷം c8-ന്റെ റിപ്പോർട്ടറുകളും നിലവിലുള്ള coverage threshold-കളും പ്രവർത്തിപ്പിക്കുന്നു. ഇൻപുട്ടുകൾ c8-ന്റെ ഗ്ലോബൽ filename ക്രമം നിലനിർത്തുന്നു; function/block coverage കലർന്നിരിക്കുമ്പോൾ ഓരോ ഷാർഡിനും മുൻകൂട്ടി merge ചെയ്യുന്നത് സുരക്ഷിതമല്ല. ലഭ്യമല്ലാത്തതോ തെറ്റായ രൂപത്തിലുള്ളതോ അനുയോജ്യമല്ലാത്തതോ ആയ ഷാർഡുകൾ പ്രവേശനം പരാജയപ്പെടുത്തുന്നു. പരാജയപ്പെട്ട ടെസ്റ്റ് ഷാർഡുകൾ raw diagnostic coverage വേറിട്ട് നിലനിർത്തുന്നു; അതിന് അന്തിമ merge-ൽ പ്രവേശിക്കാനാവില്ല.

### യൂണിറ്റ് നിർവഹണ പുരോഗതി രസീതുകൾ

തുടർന്ന് `Gate / CI`, `Gate / Quality`, `Merge integrity (changelog + generated skills)` എന്നിവ വിജയിക്കുമ്പോൾ
യഥാർത്ഥ PR ലയിക്കുന്നു.

Mergify അതിന്റെ ക്യൂ സംഗ്രഹം ഡ്രാഫ്റ്റിന്റെ വിവരണത്തിൽ എഴുതുന്നു. വിവരണത്തിലോ ശീർഷകത്തിലോ മാത്രം മാറ്റം വരുത്തുന്ന `pull_request` `edited` ഇവന്റുകൾ ഓരോ റണ്ണിനും പ്രത്യേകമായ കൺകറൻസി ഗ്രൂപ്പ് ഉപയോഗിക്കുന്നു; അവ വർഗ്ഗീകരണം, ടെസ്റ്റ് മാട്രിക്സുകൾ, മെർജ് ഇന്റഗ്രിറ്റി, അല്ലെങ്കിൽ പ്രവേശന വിധി എന്നിവ വീണ്ടും പ്രവർത്തിപ്പിക്കുന്നില്ല. നിരീക്ഷണത്തിനായി മാത്രം ഉപയോഗിക്കുന്ന ചെക്ക് പേരുകൾക്ക് `Gate / CI` അല്ലെങ്കിൽ `Gate / Quality` എന്നിവയെ പകരം വയ്ക്കാൻ കഴിയില്ല. ലക്ഷ്യ ബേസ് മാറ്റുന്ന ഒരു എഡിറ്റ് കാൻഡിഡേറ്റിന്റെ പുതിയ വാലിഡേഷൻ ആവശ്യപ്പെടുന്നു.

ക്യൂവിൽനിന്ന് നീക്കിയ ശേഷം, ഒരു പുഷ് എല്ലായ്പ്പോഴും PR-നെ വീണ്ടും ക്യൂവിലാക്കണമെന്നില്ല.
അതിൽ `@mergifyio queue` എന്ന് കമന്റ് ചെയ്യുക.

### സ്റ്റാറ്റിക് സ്കാൻ ഇൻവെന്ററി

പതിപ്പിട്ട npm-alias ഇൻവെന്ററിയും static-scan അംഗത്വവും
`config/quality/gate-manifest.json`-ലാണ്. `package.json`-നെതിരെ script പേരുകളും കൃത്യമായ command-കളും പരിശോധിക്കാൻ `npm run check:gate-manifest` പ്രവർത്തിപ്പിക്കുക; ചേർക്കലുകൾ, നീക്കംചെയ്യലുകൾ, command വ്യതിയാനം എന്നിവ local hook-നെയും CI-യിലെ change-classification ജോബുകളെയും പരാജയപ്പെടുത്തും.
ഒരു alias എന്നത് workflow job, matrix instance, test case എന്നിവയൊന്നുമല്ല: ഈ എണ്ണങ്ങൾ പരസ്പരം മാറ്റിസ്ഥാപിക്കാവുന്നവയായി അവതരിപ്പിക്കരുത്.

തിരഞ്ഞെടുത്ത alias-കൾ എക്സിക്യൂട്ട് ചെയ്യാതെ പരിശോധിക്കാൻ `npm run quality:scan -- --list` അല്ലെങ്കിൽ `npm run quality:scan:fast -- --list` ഉപയോഗിക്കുക.
റണ്ണർ npm entrypoint-നെ വിളിക്കുന്നതിനാൽ, അതിന്റെ runtime—കോൺഫിഗർ ചെയ്തിടത്ത് Bun ഉൾപ്പെടെ—നിലനിർത്തപ്പെടുന്നു.
ആ പ്രൊഫൈലുകൾക്ക് പുറത്തുള്ള alias-കൾ പ്രത്യേകം invoke ചെയ്യുന്നവയായി മാനിഫെസ്റ്റ് രേഖപ്പെടുത്തുന്നു; read-only scan പ്രൊഫൈലുകളിൽ maintenance command-കൾ നിരോധിച്ചിരിക്കുന്നു.

ഈ പ്രൊഫൈലുകൾ static scan മാത്രമാണ് ഉൾക്കൊള്ളുന്നത്. അവ product test-കൾ, coverage, packaging, external check-കൾ, അല്ലെങ്കിൽ ഒരു കാൻഡിഡേറ്റിന്റെ പൂർണ്ണ release acceptance എന്നിവ സാക്ഷ്യപ്പെടുത്തുന്നില്ല.
Workflow admission, ലിങ്ക് ചെയ്ത `config/quality/admission-policy.json`, `scripts/quality/admission-verdict.mjs` എന്നിവ ഉപയോഗിക്കുന്നു. Release-observer പ്രൊഫൈലുകൾ വേറിട്ടുതന്നെ തുടരുന്നു; അവയുടെ ബാധകമായ check-കളും receipt-കളും സ്വതന്ത്രമായി പരിശോധിക്കുക. പൂർണ്ണ observer-ന്റെ static command-കൾ `config/quality/release-green-static-profile.json`-ൽ പ്രഖ്യാപിച്ചിരിക്കുന്നു; അവയിൽ `audit:deps`, mutation-test selection, translation check-കൾ എന്നിവ ഉൾപ്പെടുന്നു. loader, package.json-നും മോഡൽ ചെയ്ത CI/Quality പ്രഖ്യാപനങ്ങൾക്കും എതിരെ npm command-കൾ പരിശോധിക്കുന്നു; shell token-കളെ argument-കളായി എക്സിക്യൂട്ട് ചെയ്യുന്നതിനുപകരം വ്യതിയാനം നിരസിക്കുന്നു. നിർബന്ധിത scanner-ന്റെ SKIP/INCOMPLETE ഔട്ട്പുട്ടിന് PASS സ്ഥാപിക്കാനാവില്ല. പ്രൊഫൈൽ അതിന്റെ external exclusion-കൾ രേഖപ്പെടുത്തുന്നു; hosted coverage, test matrix-കൾ, package അല്ലെങ്കിൽ deployment തെളിവുകൾ എന്നിവയെ അത് പകരംവയ്ക്കുന്നില്ല. താഴെയുള്ള വിവരണാത്മക ഇൻവെന്ററി ഒരു റഫറൻസാണ്; ഒരു gate യഥാർഥത്തിൽ പ്രവർത്തിച്ചതിന്റെ തെളിവല്ല.

സ്ക്രിപ്റ്റുകൾ `scripts/check/`-ലും (policy gate-കൾ) `scripts/quality/`-ലും (ratchet engine) സ്ഥിതിചെയ്യുന്നു.
CI-യുടെ ആധികാരിക ഉറവിടം `.github/workflows/ci.yml` ആണ്.

### പ്രസിദ്ധീകരിച്ച അടിസ്ഥാന ഡോക്യുമെൻ്റേഷൻ ആരോഗ്യം

`main`, `release/v*` എന്നിവയിലേക്കുള്ള തിരഞ്ഞെടുത്ത പുഷ്കൾക്കു ശേഷവും മാനുവൽ ഡിസ്പാച്ചിലും`.github/workflows/i18n-base-health.yml` ഡോക്യുമെൻ്റേഷൻ ആരോഗ്യം നിരീക്ഷിക്കുന്നു. ഇതിൻ്റെ ഫിൽട്ടറുകൾ ഡോക്യുമെൻ്റേഷൻ, റൂട്ട് മാർക്ക്ഡൗൺ, `llm.txt`, പരിഭാഷ state/configuration, പ്രസക്തമായ i18n ടൂളിംഗ് എന്നിവ ഉൾക്കൊള്ളുന്നു. സിംഗിൾ `Published base documentation health` ജോലി ഹോസ്റ്റ് ചെയ്ത ഉബുണ്ടുവും അഞ്ച് മിനിറ്റ് സമയപരിധിയും ഉപയോഗിക്കുന്നു. ഇത് വായന-മാത്രം മൂല്യനിർണ്ണയം നടത്തുകയും ഡിപൻഡൻസി ഇൻസ്റ്റാളേഷനോ വിവർത്തനമോ സംസ്ഥാന ദത്തെടുക്കലോ ഇല്ലാതെ ഒരു ഡയഗ്നോസ്റ്റിക് രസീത് എഴുതുകയും ചെയ്യുന്നു.

`scripts/i18n/check-base-health.mjs` സീറോ സോഴ്സ്-ഹാഷ്, മിസ്സിംഗ്-ടാർഗെറ്റ്, ടാർഗെറ്റ്-ഹാഷ്, സ്റ്റേൽ-ട്രാൻസ്ലേഷൻ, സെക്ഷൻ-കാഷെ പൊരുത്തക്കേടുകൾ എന്നിവ ആവശ്യമാണ്. ഇത് നിലവിലെ കോർ document/locale സ്കോപ്പും അതിൻ്റെ റെക്കോർഡ് ചെയ്ത ഉറവിടവും സാധൂകരിക്കുന്നു. അസാധുവായ സന്ദർഭം, അപൂർണ്ണമായ കവറേജ് അല്ലെങ്കിൽ തടസ്സപ്പെട്ട ചെക്കർ `INCOMPLETE` നിർമ്മിക്കുന്നു ; സ്ഥിരീകരിച്ച ഡ്രിഫ്റ്റ് `FAIL` ഉത്പാദിപ്പിക്കുന്നു. രണ്ടും പരാജയപ്പെട്ട എക്സിറ്റ് സ്റ്റാറ്റസ് നൽകുന്നു. രസീത് ചെക്ക്ഔട്ട് SHA, വർക്ക്ഫ്ലോ, റൺ, ശ്രമം എന്നിവയ്ക്ക് വിധേയമാണ്, കൂടാതെ `i18n-base-health-<sha>-<run>-<attempt>` ആയി നിലനിർത്തുകയും ചെയ്യുന്നു.

പ്രസിദ്ധീകരിച്ച അടിത്തറയുടെ ഒരു സ്വതന്ത്ര നിരീക്ഷണമാണിത്. ഇത് ഒരു PR അല്ലെങ്കിൽ ലയന-ഗ്രൂപ്പ് ഇവൻ്റ്, ആവശ്യമായ PR പരിശോധന, ഒരു npm അപരനാമം അല്ലെങ്കിൽ ഒരു സ്റ്റാറ്റിക്-സ്കാൻ പ്രൊഫൈൽ അംഗം എന്നിവ ചേർക്കുന്നില്ല. അണ്ടർലൈയിംഗ് ചെക്കർ അഞ്ച് ക്ലാസുകളും സമ്പൂർണ്ണ മോഡിൽ തടയുന്നു. സാധാരണ PR തയ്യാറെടുപ്പ് പ്രവേശനത്തിൽ നിന്ന് വേറിട്ടുനിൽക്കുന്നു. ഒരു വിജയകരമായ അപ്ലോഡിന് പരാജയപ്പെട്ട ആരോഗ്യ ഫലത്തെ PASS ആക്കി മാറ്റാൻ കഴിയില്ല.

ഒരു സാധാരണ PR `--baseline-evidence` ജനറേറ്റ് ചെയ്ത അടിസ്ഥാന റിപ്പോർട്ടുള്ള `--preflight` ഉപയോഗിക്കുന്നു. പൂർണ്ണമായ വിവർത്തന റെക്കോർഡും യഥാർത്ഥ ടാർഗെറ്റ് ബൈറ്റുകളും ആ കൃത്യമായ അടിത്തറയിൽ നിന്ന് മാറ്റമില്ലാതെ വരുമ്പോൾ മാത്രമേ ഇത് ഒരു ഇംഗ്ലീഷ് ഉറവിടം ശേഷിക്കാതെ വിട്ടേക്കാം. പുതിയ ടാർഗെറ്റ് അല്ലെങ്കിൽ സെക്ഷൻ-കാഷെ പൊരുത്തക്കേടുകൾ ഇപ്പോഴും തടയുന്നു, കൂടാതെ അപൂർണ്ണമായ തെളിവുകൾ തയ്യാറാക്കുന്നത് അംഗീകരിക്കാൻ കഴിയില്ല. റിപ്പോർട്ട് `preparationPending`, `mergeReady` വെവ്വേറെ തുറന്നുകാട്ടുന്നു: വിജയകരമായ തയ്യാറെടുപ്പ് തീർപ്പാക്കാത്ത വിവർത്തനങ്ങൾ ലയിപ്പിക്കാൻ തയ്യാറാകുന്നില്ല. പ്രവേശനത്തിന് മുമ്പ് കമ്പോസ് ചെയ്ത കാൻഡിഡേറ്റിലെ ബാധിച്ച കണ്ണാടികൾ പുതുക്കുക. വിശ്വസനീയമായ മെർജിഫൈ ക്യൂ കാൻഡിഡേറ്റ്, `merge_group`, ബ്രാഞ്ച് പുഷുകൾ, മാനുവൽ CI റണ്ണുകൾ എന്നിവ `--warn` അല്ലെങ്കിൽ പാരമ്പര്യ പരാജയം ക്ഷമിക്കാതെ കേവല ചെക്കർ ഉപയോഗിക്കുന്നു. നഷ്ടമായ ടാർഗെറ്റ് ഹാഷുകളും ഇല്ലാതാക്കിയ റെക്കോർഡുചെയ്ത കോർ ഫയലുകളാൽ കുറയുന്ന സ്കോപ്പും വിജയകരമായ ഒരു സമ്പൂർണ്ണ വിധി പുറപ്പെടുവിക്കാൻ കഴിയില്ല.

### PR ഫാസ്റ്റ്-പാത്ത് (`quality.yml`) റിലീസ് ചെയ്യുക

`.github/workflows/quality.yml` main/release PRs ൽ CI പൂർത്തീകരിക്കുന്നു, `main` ലേക്ക് തള്ളുന്നു, ഗ്രൂപ്പുകൾ അയയ്ക്കുകയും ലയിപ്പിക്കുകയും ചെയ്യുന്നു. PRs പാത്ത്-ഫിൽട്ടർ ചെയ്ത ഫാസ്റ്റ് ചെക്കുകൾ ഉപയോഗിക്കുന്നു. സ്ഥിരമായി പ്രവർത്തനരഹിതമാക്കിയ ഡ്യൂപ്ലിക്കേറ്റ് ബിൽഡ് നീക്കം ചെയ്തു; യഥാർത്ഥ build/package/boot പരിശോധനകൾ CI ൽ തന്നെ നിലനിൽക്കും. യൂണിറ്റ് സ്യൂട്ടും വിറ്റസ്റ്റും CI (`Unit Tests (N/12)`, `Vitest`) ൽ മാത്രം പ്രവർത്തിക്കുന്നു.

#### മറന്നുപോയ സഹോദരങ്ങളുടെ ടെസ്റ്റ് റിപ്പോർട്ട്

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` യുടെ ഒരു ഉപദേശക ഘട്ടമായി പ്രവർത്തിക്കുകയും ടെസ്റ്റ്-ഇംപാക്റ്റ് മാപ്പിന് പിന്നിലെ ഇറക്കുമതി റിസോൾവർ വീണ്ടും ഉപയോഗിക്കുകയും ചെയ്യുന്നു. മാറ്റപ്പെട്ട ഓരോ പ്രൊഡക്ഷൻ മൊഡ്യൂളിനും, കാൻഡിഡേറ്റ് ടെസ്റ്റ് പുൾ-അഭ്യർത്ഥന വ്യത്യാസത്തിൽ ഇല്ലാതിരിക്കുമ്പോൾ അത് ഡിറ്റർമിനിസ്റ്റിക് `changed module/symbol -> static consumer -> candidate sibling test` ചെയിനുകൾ റിപ്പോർട്ട് ചെയ്യുന്നു. മാർക്ക്ഡൗൺ സംഗ്രഹവും JSON ഫലവും ഏതെങ്കിലും തടയൽ റോൾഔട്ടിന് മുമ്പായി കാലിബ്രേഷനുള്ള `forgotten-sibling-tests` വർക്ക്ഫ്ലോ ആർട്ടിഫാക്റ്റായി നിലനിർത്തുന്നു.

ബാരൽ റീ-കയറ്റുമതിയും ഡൈനാമിക് ഇറക്കുമതിയും റെസല്യൂഷൻ ഡയഗ്നോസ്റ്റിക്സ് മാത്രമാണ്; അവർ ഒരിക്കലും തടയുന്ന ഒരു കണ്ടെത്തൽ സൃഷ്ടിക്കുന്നില്ല. അവലോകനം ചെയ്ത ഒഴിവാക്കലുകൾ `config/quality/forgotten-sibling-allowlist.json` ൽ തത്സമയം. ഓരോ എൻട്രിയും ഉപഭോക്താവിൻ്റെയും കാൻഡിഡേറ്റിൻ്റെയും പരിശോധനയ്ക്ക് പേര് നൽകണം, ഒരു നിർദ്ദിഷ്ട യുക്തി നൽകണം, കൂടാതെ ഒരു GitHub ഇഷ്യൂ ലിങ്ക് ചെയ്യുകയോ അഭ്യർത്ഥന പിൻവലിക്കുകയോ വേണം. തെറ്റായ എൻട്രികൾ പരാജയപ്പെട്ടു. ഒഴിവാക്കലുകൾക്ക് ഇല്ലാതാക്കിയ കാൻഡിഡേറ്റ് ടെസ്റ്റ് അല്ലെങ്കിൽ `.skip`/`.todo` ചേർക്കുന്ന ഒരു വ്യത്യാസം ഇല്ലാതാക്കാൻ കഴിയില്ല ; അവകാശവാദം ദുർബലപ്പെടുത്തലും മറ്റ് മാസ്കിംഗും സ്വതന്ത്രമായി തടയുന്ന `check:test-masking` ഗേറ്റിൻ്റെ ഉടമസ്ഥതയിൽ തുടരുന്നു.

#### രണ്ട് typecheck പ്രോഗ്രാമുകൾ വ്യത്യസ്ത ഉത്തരങ്ങൾ നൽകുന്നു

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`)-യും `check:build-typecheck`-ഉം വ്യത്യസ്ത options-ുകൾക്ക് കീഴിൽ
വ്യത്യസ്ത programs compile ചെയ്യുന്നു; അതിനാൽ ഒരേ file ഒന്ന് clean ആയിരിക്കുമ്പോൾ
മറ്റൊന്നിൽ errors നിറഞ്ഞിരിക്കാം.

`tsconfig.build.json` `"strict": false` സജ്ജീകരിക്കുന്നു, അതിനാൽ `noImplicitAny` ഓഫ്
ആണ്. Core config കൂടുതൽ കർശനമായ options-ുകളോടെ തിരഞ്ഞെടുത്ത 27-ഫയൽ allowlist
compile ചെയ്യുകയും ഓരോ entry-യുടെയും import graph പിന്തുടരുകയും ചെയ്യുന്നു. അതിനാൽ
build program-ൽ ഒരിക്കലും പ്രത്യക്ഷപ്പെടാത്ത files പോലും അവിടെ പരിശോധിക്കപ്പെടുന്നു.

ഒരു file typed ആണോ എന്ന് വിലയിരുത്തുമ്പോൾ ഇതിന്റെ ഫലം പ്രധാനമാണ്:
**`check:build-typecheck`-ന് കീഴിലുള്ള zero diagnostics എന്നത് zero errors എന്നാണ്
അർത്ഥമാക്കുന്നത് അല്ല**. 26 files-ൽ നിന്ന് `@ts-nocheck` നീക്കിയപ്പോൾ build
program-ൽ അവയിൽ 23 എണ്ണം clean ആണെന്ന് കണ്ടെത്തി; അവയിൽ പതിനാറെണ്ണം strict
program-ൽ ഏകദേശം 120 implicit-any errors കണ്ടെത്തി. ഒരു file clean ആണെന്ന്
പറയുന്നതിന് മുമ്പ് രണ്ടും പരിശോധിക്കുക.

2. അവയെ `__MISSING__:<new english>` ആയി സജ്ജീകരിക്കുക — തുടർന്ന് runtime ശരിയാക്കിയ ഇംഗ്ലീഷ് നൽകും
   (`src/i18n/request.ts::deepMergeFallback`, #7258), കൂടാതെ കീ വിവർത്തനത്തിനായി ക്യൂവിൽ ചേരും.

സ്ട്രിങ്ങിന്റെ **അർഥം** മാറിയിട്ടുണ്ടെങ്കിൽ, **കീയുടെ പേര് മാറ്റുന്നതിന്** മുൻഗണന നൽകുക: ഒരു പുതിയ കീയ്ക്ക്
കാലഹരണപ്പെട്ട വിവർത്തനം പാരമ്പര്യമായി ലഭിക്കാനാവില്ല. #8463 ഉപയോഗിച്ച മാതൃക അതാണ്.

```bash
npm run i18n:check-value-drift          # കർശനം (CI പ്രവർത്തിപ്പിക്കുന്നത്)
npm run i18n:check-value-drift:warn     # റിപ്പോർട്ട് മാത്രം
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

മൂല്യ-വ്യതിയാനവും പുതിയ-കീ ഗേറ്റുകളും
`scripts/i18n/resolve-ui-diff-base.mjs`-ൽ നിന്നുള്ള മാറ്റാനാകാത്ത ഒരേ താരതമ്യം പങ്കിടുന്നു. വർക്ക്ഫ്ലോ ഒരേ base, base-tip,
candidate SHA-കൾ രണ്ട് പരിശോധനകൾക്കും കൈമാറുന്നു. PR/base-retarget, push, merge-group റണ്ണുകൾ അവയുടെ event
context ഉപയോഗിക്കുന്നു. ഒരു candidate branch dispatch ചെയ്യുന്നതിന് അതിന്റെ കൃത്യമായ തുറന്ന PR അല്ലെങ്കിൽ വ്യക്തമായ
`i18n_base_sha` input ആവശ്യമാണ്. ആ input ഇല്ലാതെ `main` അല്ലെങ്കിൽ `release/vX.Y.Z`
dispatch ചെയ്യുകയോ scheduled observation നടത്തുകയോ ചെയ്താൽ, അവസാന commit-നെ അതിന്റെ ആദ്യ parent-ുമായി താരതമ്യം ചെയ്യും; ഇത്
പാരമ്പര്യമായി ലഭിച്ച മുഴുവൻ വിവർത്തന കടബാധ്യതയുടെയും audit അല്ല. Local invocation-ന് വ്യക്തമായ ഒരു comparison base ആവശ്യമാണ്,
ഉദാഹരണത്തിന് മുകളിലുള്ള `BASE_REF` command.

Comparison context ലഭ്യമല്ലാത്തതോ അവ്യക്തമായതോ ആയിരിക്കുക, ആവശ്യമായ catalog വായിക്കാനാകാത്തതോ അസാധുവായതോ ആയിരിക്കുക, കൂടാതെ
candidate മാറിയിരിക്കുക എന്നിവ warn mode-ൽ ഉൾപ്പെടെ exit code **2** സഹിതം `INCOMPLETE` സൃഷ്ടിക്കും.
Catalog വായനകൾ `scripts/i18n/read-ui-catalog.mjs` ഉപയോഗിക്കുന്നു; വായനാ പരാജയങ്ങൾക്ക് പകരമായി
ശൂന്യമായ objects ഉപയോഗിക്കില്ല. ലഭ്യമല്ലാത്ത base-ഉം അപൂർണ്ണമായ input-ഉം PASS സ്ഥാപിക്കുന്നില്ല.

  (`scripts/quality/baseline-headroom.mjs`). രാത്രികാല `baseline-headroom` ജോലി, വർക്ക്ഫ്ലോ റൺ സംഗ്രഹത്തിൽ
  പട്ടിക പ്രസിദ്ധീകരിക്കുകയും അതിന്റെ JSON/Markdown റിപ്പോർട്ട്

  സ്ഥിരമായ ഒരു ഇഷ്യൂ സൃഷ്ടിക്കുകയോ അപ്ഡേറ്റ് ചെയ്യുകയോ ഇല്ല; മുമ്പത്തെ റിപ്പോർട്ട് ചരിത്രം #12149-ൽ സംരക്ഷിച്ചിരിക്കുന്നു.

  നിരപരാധിയായ ഒരു PR-നെ ഒരിക്കലും പരാജയപ്പെടുത്തില്ല; റിലീസ് അനുരഞ്ജന സമയത്ത് പരിഹരിക്കുന്നതിനായി വ്യതിയാനം ട്രാക്ക് ചെയ്യുകയും

## റാച്ചറ്റ് ബേസ്ലൈൻ (`quality-baseline.json`)

റാച്ചറ്റ് എൻജിൻ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` വായിക്കുകയും
പുതുതായി ശേഖരിച്ച `quality-metrics.json`-മായി അതിനെ താരതമ്യം ചെയ്യുകയും ചെയ്യുന്നു. അനുവദനീയമായ എപ്സിലോണിനപ്പുറം
പിന്നോട്ട് പോകുന്ന ഏതൊരു മെട്രിക്കും ബിൽഡ് പരാജയപ്പെടാൻ കാരണമാകും.

നിലവിൽ ട്രാക്ക് ചെയ്യുന്ന മെട്രിക്കുകൾ:

| `coverage.statements` | `up`   | സ്റ്റേറ്റ്മെന്റ് കവറേജ് കുറയരുത്        |

### CodeQL റാറ്റ്ചെറ്റ്: കാൻഡിഡേറ്റ് അഡ്മിഷനും റിപ്പോസിറ്ററി ഇൻവെൻ്ററിയും

CI ഒരു വ്യക്തമായ ആശ്രിതത്വ ശൃംഖലയിലൂടെ കാൻഡിഡേറ്റ് CodeQL പ്രവേശനം സ്വന്തമാക്കി: `codeql.yml` യിലെ നാല് ഭാഷാ മാട്രിക്സിനെ `codeql-scan` വിളിക്കുന്നു, തുടർന്ന് `codeql-admission` `node scripts/check/check-codeql-ratchet.mjs --candidate` പ്രവർത്തിപ്പിക്കുന്നു. `Gate / CI` രണ്ട് ഫലങ്ങളും ആവശ്യമാണ്. ഗുണനിലവാരം അതിൻ്റെ സ്വന്തം സംഖ്യാ പരിശോധനകൾ നിലനിർത്തുന്നു, എന്നാൽ നിർമ്മാതാവ് പൂർത്തിയാകുന്നതിന് മുമ്പ് സ്കാനറോട് അന്വേഷിക്കുന്നില്ല; `Gate / Quality` മാത്രം പൂർണ്ണമായ സ്ഥാനാർത്ഥി പ്രവേശനമല്ല. ഡോക്സ് മാത്രമുള്ള കാൻഡിഡേറ്റുകളിൽ CodeQL ആവശ്യമാണ്.

`config/quality/codeql-admission-policy.json` യിലെ നയം, പ്രവർത്തനങ്ങൾ, C/C++, JavaScript/TypeScript, Python എന്നിവ തിരഞ്ഞെടുക്കുന്നു, സ്യൂട്ട് ഡിഫോൾട്ട്, റിമോട്ട് ഭീഷണി മോഡൽ, ബിൽഡ് മോഡ് ഒന്നുമില്ല. പ്രൊഡ്യൂസർ പ്രിഫ്ലൈറ്റ് തീർപ്പുകൽപ്പിക്കാത്ത ആക്റ്റിവേഷൻ റെക്കോർഡ് നിരസിക്കുകയും വ്യക്തമായ ടാർഗെറ്റ് ലിസ്റ്റിന് പുറത്തുള്ള ശാഖകൾ നൽകുകയും ചെയ്യുന്നു. നിലവിലെ ലക്ഷ്യങ്ങൾ പ്രധാനമാണ്, release/v3.8.54. കരാർ ടെസ്റ്റുകൾ ഈ പരിമിത ലിസ്റ്റും മെയിൻ്റനൻസ് പുഷ് ട്രിഗറും പാക്കേജ് പതിപ്പുമായി താരതമ്യം ചെയ്യുന്നു; അടുത്ത പതിപ്പിന് ഓൺബോർഡിംഗ് അവലോകനം ചെയ്യേണ്ടതുണ്ട്. CI ൻ്റെ നിലവിലുള്ള വിശാലമായ റിലീസ് PR ട്രിഗർ നിലനിർത്തിയിട്ടുണ്ട്, എന്നാൽ ഒരു അൺബോർഡ് ചെയ്യാത്ത ടാർഗെറ്റ് അളക്കാത്ത PASS നേടുന്നതിനുപകരം വേർതിരിച്ചെടുക്കുന്നതിന് മുമ്പ് HOLD റിപ്പോർട്ട് ചെയ്യുന്നു.

ഓരോ മാട്രിക്സ് ജോലിയും അതിൻ്റെ യഥാർത്ഥ SARIF അപ്ലോഡ് ID, ഭാഷ, വിഭാഗം, റൺ ആൻഡ് ശ്രമം, കോളർ വർക്ക്ഫ്ലോ ഐഡൻ്റിറ്റി, ഇവൻ്റ് ref/head/base/merge SHA, പോളിസി ഹാഷ് എന്നിവ രേഖപ്പെടുത്തുന്നു. ആശ്രിത ജോലി ഈ റണ്ണിൻ്റെ രസീതുകൾ മാത്രം ഡൗൺലോഡ് ചെയ്യുകയും ആർട്ടിഫാക്റ്റ് ഡൈജസ്റ്റുകൾ സാധൂകരിക്കുകയും ചെയ്യുന്നു. ഇതിന് നാല് വിഭാഗങ്ങളും ആവശ്യമാണ്, ഒരു വിജയകരമായ നിർമ്മാതാവ്, ഓരോ കൃത്യമായ അപ്ലോഡിൻ്റെയും പ്രോസസ്സിംഗ് പൂർത്തിയാക്കി. ഇത് API യുടെ sarif_id ഫിൽട്ടർ ഉപയോഗിക്കുന്നു, ഒരു ബ്രാഞ്ചിൽ കണ്ടെത്തിയ ഏറ്റവും പുതിയ വിശകലനമല്ല. ഭാഗികമായ ആവർത്തനങ്ങൾ ഒരേ റണ്ണിൻ്റെയും സ്ഥാനാർത്ഥിയുടെയും മുമ്പത്തെ ശ്രമത്തിൽ നിന്നുള്ള വിജയകരമായ വിഭാഗങ്ങൾ വീണ്ടും ഉപയോഗിച്ചേക്കാം, ഉൽപ്പാദിപ്പിക്കുന്ന ശ്രമം സംരക്ഷിക്കുന്നു; പരാജയപ്പെട്ട നിലവിലെ നിർമ്മാതാവിന് മുമ്പത്തെ പച്ച തെളിവുകൾ വീണ്ടും ഉപയോഗിക്കാൻ കഴിയില്ല.

CodeQL പ്രവർത്തനം പ്രോസസ്സിംഗിനായി കാത്തിരിക്കുന്നു, എന്നാൽ അതിൻ്റെ പിൻ ചെയ്ത നടപ്പാക്കലിന് മുന്നറിയിപ്പ് നൽകാനും സ്റ്റാറ്റസ് റീഡ് പരാജയം അല്ലെങ്കിൽ ക്ഷീണിച്ച കാത്തിരിപ്പിന് ശേഷവും തുടരാനും കഴിയും. അതിനാൽ പ്രവേശനം പ്രോസസ്സിംഗ് വീണ്ടും പരിശോധിക്കുന്നു. നഷ്ടമായ വിഭാഗങ്ങൾ, ശേഷിക്കുന്ന പ്രോസസ്സിംഗ്, പരാജയപ്പെട്ട അല്ലെങ്കിൽ റദ്ദാക്കിയ ജോലികൾ, പഴകിയ ഐഡൻ്റിറ്റി, അപൂർണ്ണമായ പേജിനേഷൻ അല്ലെങ്കിൽ ലഭ്യമല്ലാത്ത APIs HOLD ഉൽപ്പാദിപ്പിച്ച് പുറത്തുകടക്കുക 2. ഒരു സ്വതന്ത്ര സ്കാനർ വർക്ക്ഫ്ലോയ്ക്കായി സ്ഥിരമായ കാത്തിരിപ്പ് അവശേഷിക്കുന്നില്ല. സ്കാൻ ചെയ്യാത്ത PR കടന്നുപോകാൻ കഴിയില്ല കാരണം ഒരു അലേർട്ട് ക്വറി 0 നൽകി. `metrics.codeqlAlerts.value` മുകളിലുള്ള അളന്ന എണ്ണം 1-ൽ നിന്ന് പുറത്തുകടക്കുന്നു; മറ്റൊരു ബ്രാഞ്ചിൻ്റെ അലേർട്ടുകൾ ആഗിരണം ചെയ്യാൻ അടിസ്ഥാനം ഉയർത്തിയിട്ടില്ല. [അപ്ലോഡ് സ്റ്റാറ്റസും വിശകലന ലുക്കപ്പും](https://docs.github.com/en/rest/code-scanning/code-scanning).

രസീത് രേഖകൾ അപ്ലോഡ് ചെയ്യുകയും വിശകലനം ചെയ്യുകയും ചെയ്യുന്നു IDs, വിഭാഗങ്ങൾ, ടൂൾ പതിപ്പുകൾ, ref/SHA, ബേസ്ലൈൻ, അലേർട്ട് നമ്പറുകൾ. SARIF identity/result കൗണ്ട്, മിനിമം റൂൾ കൗണ്ടുകൾ, കൃത്യമായ അലേർട്ട് സംഭവങ്ങൾ എന്നിവ നിർബന്ധമായി തുടരുന്നു. സ്വീകരിക്കുന്നതിന് മുമ്പ് PR/analysis ഐഡൻ്റിറ്റികൾ വീണ്ടും പരിശോധിക്കും. ഈ പരിശോധനകൾ കോൺഫിഗർ ചെയ്ത വിഭാഗ കവറേജ് സ്ഥാപിക്കുന്നു, എക്സ്ട്രാക്റ്റുചെയ്ത എല്ലാ സോഴ്സ് ഫയലിൻ്റെയും ഇൻവെൻ്ററിയല്ല. C/C++ നോ-ബിൽഡ് എക്സ്ട്രാക്ഷനിൽ ഒരു പ്രോജക്റ്റ് ബിൽഡ് സമയത്ത് ജനറേറ്റുചെയ്ത കോഡ് ഉൾപ്പെടുന്നില്ല. ഉറവിട ഒഴിവാക്കലുകൾക്ക് ഇപ്പോഴും അവലോകനം ആവശ്യമാണ്, കൂടാതെ സംഭാവക ആട്രിബ്യൂഷന് താരതമ്യപ്പെടുത്താവുന്ന കൃത്യമായ അടിസ്ഥാന തെളിവുകൾ ആവശ്യമാണ്.

`codeql-maintenance.yml` സജീവ-റിലീസ് പുഷ് സ്കാനുകളും PR/main നിർമ്മാതാക്കളെ തനിപ്പകർപ്പാക്കാതെ പ്രതിവാര ഷെഡ്യൂളും നൽകുന്നു. `--strict-measurement`, അളവെടുക്കൽ ലഭ്യമല്ലാത്തപ്പോൾ പരാജയം എന്നിവയ്ക്കൊപ്പം `nightly-codeql-inventory.yml` ശേഖരം-വൈഡ് ബേസ്ലൈൻ പ്രത്യേകമായി സൂക്ഷിക്കുന്നു. സ്ഥാനാർത്ഥി പ്രവേശനമല്ല ലോക്കൽ ലെഗസി കളക്ടറുടെ കൃപയുള്ള ഒഴിവാക്കൽ. പരിശോധിച്ചുറപ്പിച്ച കുറഞ്ഞ ആഗോള എണ്ണത്തിന് ശേഷം കർശനമാക്കൽ ഒരു വ്യക്തമായ `--update` ആയി തുടരുന്നു.

ഡിഫോൾട്ട് സെറ്റപ്പ് കോൺഫിഗർ ചെയ്യുമ്പോൾ വിപുലമായ വർക്ക്ഫ്ലോ പ്രസിദ്ധീകരിക്കാൻ പാടില്ല: GitHub ആ കോമ്പിനേഷൻ നിരസിക്കുന്നു. അവലോകനം ചെയ്ത അഡ്മിനിസ്ട്രേറ്റീവ് പരിവർത്തനം തിരികെ വായിക്കുന്നത് വരെ അതിൻ്റെ പതിപ്പ് നയം തീർച്ചപ്പെടുത്തിയിട്ടില്ല. പ്രസിദ്ധീകരിക്കുന്നതിന് മുമ്പ്, ഒരു ഓപ്പറേറ്റർ പിൻസ് റിപ്പോസിറ്ററി, head/base/tree, policy/patch/rollback ഹാഷുകളും നിരീക്ഷിച്ച സജ്ജീകരണ നിലയും; `node scripts/quality/codeql-producer.mjs verify-admin-readback` വിതരണം ചെയ്ത പ്രതീക്ഷിക്കുന്നതും യഥാർത്ഥവുമായ JSON റെക്കോർഡുകൾ പരിശോധിക്കുന്നു. ഇതൊരു സാങ്കേതിക ഗാർഡാണ്, ഓപ്പറേറ്ററുടെ അംഗീകാരമോ പുതിയ റീഡ്ബാക്കുകൾ ലഭ്യമാക്കുന്നതിനുള്ള പകരമോ അല്ല. PR ടോക്കൺ ഒരിക്കലും അഡ്മിനിസ്ട്രേഷൻ ആക്സസ് അഭ്യർത്ഥിക്കുന്നില്ല. റോൾഔട്ടിനും ഏതെങ്കിലും സ്കാനർ മാറ്റത്തിനും പ്രത്യേക റീഡ്ബാക്ക് കൂടാതെ യഥാർത്ഥ PR, ഫോർക്ക്, മെർജ്-ഗ്രൂപ്പ് അനുയോജ്യത തെളിവുകൾ എന്നിവ ആവശ്യമാണ്.

ഫോർക്കുകൾ ഹോസ്റ്റ് ചെയ്ത റണ്ണേഴ്സ് ഉപയോഗിക്കുന്നു, സ്ഥിരമായ ക്രെഡൻഷ്യലുകളില്ലാതെ ചെക്ക്ഔട്ട് ചെയ്യുന്നു, പ്രൊഡ്യൂസറിൽ പ്രോജക്റ്റ് install/build ഇല്ല, പാരമ്പര്യമായി ലഭിച്ച ശേഖര രഹസ്യങ്ങളൊന്നുമില്ല. GitHub അതിൻ്റെ കുറഞ്ഞ ഫോർക്ക് ടോക്കൺ ഉപയോഗിച്ച് pull_request ഇവൻ്റിനായി SARIF അപ്ലോഡിനെ പിന്തുണയ്ക്കുന്നു; ആദ്യ തവണ സംഭാവന നിർവ്വഹണ അംഗീകാരം GitHub നയമായി തുടരുന്നു. വിശ്വസനീയമല്ലാത്ത കോഡ് എക്സിക്യൂട്ട് ചെയ്യാൻ ഒരിക്കലും pull_request_target ഉപയോഗിക്കരുത്. മൈഗ്രേഷൻ പൂർത്തിയായതായി പരിഗണിക്കുന്നതിന് മുമ്പ് നിയന്ത്രിത കാനറിയിലെ യഥാർത്ഥ ടോക്കൺ അനുമതികൾ, വിശകലന_കീ, എല്ലാ വിഭാഗം പരിതസ്ഥിതികളും സ്ഥിരീകരിക്കുക. മറ്റെന്തും പരാജയപ്പെടും: ഒരു സംഖ്യ ഉയർത്തുക, ഒരു എൻട്രി ചേർക്കുക, `cap`/`testCap` മാറ്റുക, അല്ലെങ്കിൽ
ഒരു `_rebaseline_*` കുറിപ്പ് ഇല്ലാതാക്കുക/വീണ്ടും എഴുതുക (ഓരോ പരിധിയും എന്തുകൊണ്ട് നിലവിലുണ്ട് എന്നതിനുള്ള ഓഡിറ്റ് ട്രെയിലാണ് ആ കുറിപ്പുകൾ;
ഫയൽ എൻട്രികൾക്കൊപ്പം അതേ `frozen` ഒബ്ജക്റ്റിനുള്ളിലാണ് അവ സൂക്ഷിച്ചിരിക്കുന്നത്).
ഒരു പരിധി ഉയർത്താൻ കഴിയുന്ന ബോട്ട് നിലവിലെ അവസ്ഥയെക്കാൾ തീർച്ചയായും മോശമായിരിക്കും. റിഗ്രഷൻ
ഗാർഡ്: `tests/unit/verify-ratchet-bank.test.ts`.

job ഒരിക്കലും `release/*`-ലേക്ക് പുഷ് ചെയ്യില്ല — ഒരു മനുഷ്യൻ PR മെർജ് ചെയ്യുന്നതിനാൽ, തെറ്റായ അളവ്
അവലോകനം ചെയ്യപ്പെടാതെ ഉൾപ്പെടാൻ കഴിയില്ല.

## അനുവദനീയ പട്ടികാ നയം

മുൻപേ നിലവിലുണ്ടായിരുന്ന ലംഘനങ്ങൾ കാരണം പരാജയപ്പെടാൻ പാടില്ലാത്ത ഓരോ ഗേറ്റും മാറ്റമില്ലാത്ത ഒരു അനുവദനീയ പട്ടിക ഉപയോഗിക്കുന്നു
(ഉദാ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). നയം ഇതാണ്:

**മൂലകാരണം പരിഹരിക്കുക; ലംഘനം മുൻപേ നിലവിലുള്ളതും അതേ PR-ൽ പരിഹരിക്കാൻ കഴിയാത്തതുമാണെങ്കിൽ മാത്രം അനുവദനീയ പട്ടിക ഉപയോഗിക്കുക.**

ഒരു അനുവദനീയ പട്ടികയിലേക്ക് എൻട്രി ചേർക്കുമ്പോൾ:

1. ന്യായീകരണം ഉൾപ്പെടുന്ന ഒരു കമന്റ് ചേർക്കുക.
2. ട്രാക്കിംഗ് ഇഷ്യൂ പരാമർശിക്കുക (ഉദാ., `// #3498 — Phase 2 feature, not yet implemented`).
3. ലംഘനം പരിഹരിക്കുന്ന അതേ PR-ൽ എൻട്രി നീക്കംചെയ്യുക — സജീവമായ ഒരു ലംഘനത്തെ ഇനി ഒഴിവാക്കാത്ത കാലഹരണപ്പെട്ട എൻട്രി തന്നെ ഒരു തകരാറാണ് (6A.3-ലെ കാലഹരണപ്പെട്ട എൻഫോഴ്സ്മെന്റ് നടപ്പിലാക്കിയാൽ, ഒറ്റപ്പെട്ട അനുവദനീയ പട്ടികാ എൻട്രി കാരണം ഗേറ്റ് പരാജയപ്പെടും).

ടെസ്റ്റുകൾ വേഗത്തിൽ വിജയിപ്പിക്കാൻ അനുവദനീയ പട്ടികാ എൻട്രികൾ ചേർക്കരുത്. വളർന്നുകൊണ്ടിരിക്കുന്ന അനുവദനീയ പട്ടികയോടുകൂടിയ വിജയകരമായ ഗേറ്റ് ഗുണനിലവാരത്തെക്കുറിച്ചുള്ള തെറ്റായ ആത്മവിശ്വാസമാണ് നൽകുന്നത്.

### നിങ്ങളുടെ PR-ൽ ഒരു ഗേറ്റ് പരാജയപ്പെടുമ്പോൾ

1. **ഗേറ്റ് ഔട്ട്പുട്ട് ശ്രദ്ധാപൂർവം വായിക്കുക** — ഏത് ഫയലോ സിംബലോ ആണ് നിയമം ലംഘിച്ചതെന്ന് അത് കൃത്യമായി അറിയിക്കുന്നു.
2. **ലംഘനം പരിഹരിക്കുക** — മിക്ക ഗേറ്റുകളും നിർണ്ണായകമായ ഫയൽസിസ്റ്റം പരിശോധനകളാണ്; കോഡ് ശരിയായാലുടൻ അവ വിജയിക്കും.
3. **ലംഘനം മുൻപേ നിലവിലുള്ളതാണെങ്കിൽ** (അതായത്, നിങ്ങൾ അത് അവതരിപ്പിച്ചതല്ലെങ്കിലും ഗേറ്റ് ഇപ്പോൾ അതിനെ ഉൾക്കൊള്ളുന്നു): ന്യായീകരണ കമന്റും ട്രാക്കിംഗ് ഇഷ്യൂവും സഹിതം ഒരു അനുവദനീയ പട്ടികാ എൻട്രി ചേർക്കുക.
4. **ഗേറ്റ് ഒരു റാച്ചറ്റ് ആണെങ്കിൽ** (കവറേജ്, ESLint മുന്നറിയിപ്പുകൾ, ഡ്യൂപ്ലിക്കേഷൻ, സങ്കീർണ്ണത): നിങ്ങളുടെ മാറ്റം മെട്രിക് മോശമാക്കി. അടിസ്ഥാന പ്രശ്നം പരിഹരിക്കുക, അല്ലെങ്കിൽ (അപൂർവമായി) മാറ്റം മനഃപൂർവമുള്ളതും മെട്രിക്കിലെ ഇടിവ് സ്വീകാര്യവുമാണെങ്കിൽ `npm run quality:ratchet -- --update` പ്രവർത്തിപ്പിക്കുക — എന്നാൽ PR വിവരണത്തിൽ അതിന്റെ കാരണം രേഖപ്പെടുത്തുക.
5. **ഉപദേശാത്മക ഗേറ്റുകൾ** (`continue-on-error: true`) വിവരദായകമാണ് — അവ മെർജ് തടയില്ല, എന്നാൽ CI സംഗ്രഹത്തിൽ ദൃശ്യമാകും. എന്നിരുന്നാലും അവ പരിഹരിക്കുക.

## ഒരു പുതിയ ഗേറ്റ് ചേർക്കൽ

1. `scripts/check/check-<name>.mjs` (അല്ലെങ്കിൽ `.ts`) സൃഷ്ടിക്കുക. നയ ഗേറ്റുകൾ 0/1 നിലയിൽ പുറത്തുകടക്കുന്നു.
   റാച്ചെറ്റ്-രീതിയിലുള്ള ഗേറ്റുകൾ `collect-metrics.mjs` വഴി `quality-metrics.json`-ലേക്ക് ഒരു മെട്രിക് പുറപ്പെടുവിക്കുന്നു.
2. `package.json`-ൽ `"check:<name>": "node scripts/check/check-<name>.mjs"` ചേർക്കുക, കൂടാതെ
   `config/quality/gate-manifest.json`-ൽ അപരനാമവും അതിന്റെ കൃത്യമായ കമാൻഡും സമന്വയിപ്പിക്കുക.
   നിലവിലുള്ള ഒരു സാധൂകരണ അപരനാമം മാറ്റുമ്പോഴോ നീക്കം ചെയ്യുമ്പോഴോ ഇതേ സമന്വയം പ്രയോഗിക്കുക.
   `npm run check:gate-manifest` പ്രവർത്തിപ്പിക്കുക; pre-commit hook-ഉം CI മാറ്റ വർഗ്ഗീകരണവും
   ഈ കരാർ നിർബന്ധമാക്കുന്നു.
3. ഉചിതമായ ജോബിന് കീഴിൽ `.github/workflows/ci.yml`-ൽ അത് ബന്ധിപ്പിക്കുക
   (നയം → `lint` അല്ലെങ്കിൽ `docs-sync-strict`; റാച്ചെറ്റ് → `quality-gate`).
4. അതിന് ഒരു അനുവദനീയ പട്ടികയുണ്ടെങ്കിൽ, കാലഹരണപ്പെട്ട എൻട്രികൾ സ്വയമേവ കണ്ടെത്തുന്നതിനായി
   `scripts/check/lib/allowlist.mjs`-ൽ നിന്നുള്ള `reportStaleEntries()` പ്രയോഗിക്കുക.
5. ഗേറ്റിന്റെ കണ്ടെത്തൽ ലോജിക് ഉൾക്കൊള്ളുന്ന ഒരു ടെസ്റ്റ് `tests/unit/build/`-ൽ എഴുതുക.
6. ഈ പ്രമാണം അപ്ഡേറ്റ് ചെയ്യുക (പ്രസക്തമായ ജോബ് പട്ടികയിൽ ഒരു വരി ചേർക്കുക).

- **`check:docs-sync` രണ്ടുതവണ പ്രവർത്തിക്കുന്നു** — `lint` ജോലിയിൽ സ്വതന്ത്രമായും `check:docs-all`-നുള്ളിലും (`docs-sync-strict`), കൂടാതെ husky pre-commit ഹുക്കിലും. ✅ **പൂർത്തിയായി** — സ്വതന്ത്ര `lint` ഇൻവൊക്കേഷൻ നീക്കംചെയ്തു.
- **CVE സ്കാനിംഗ്** — ❌ **വൃത്തിയുള്ള ലയനമല്ല.** `audit:deps` എല്ലാ അഞ്ച് lockfile-ുകളിലുമുള്ള ഗുരുതര ഉപദേശങ്ങളും അപൂർണ്ണമായ ഓഡിറ്റുകളും തടയുന്നു, അതേസമയം നിലവിലെ നയപ്രകാരം ഉയർന്ന തീവ്രതയുള്ള ഉപദേശങ്ങൾ മുന്നറിയിപ്പുകളായി റിപ്പോർട്ട് ചെയ്യുന്നു; `check:vuln-ratchet` (osv) ചെക്ക്-ഇൻ ചെയ്ത baseline-നോടുള്ള ഒരു _പിന്നോട്ടുപോക്ക്_ ഉണ്ടായാൽ മാത്രമേ പരാജയപ്പെടൂ, കൂടാതെ ആവശ്യമായപ്പോൾ അളവുകൾ ലഭ്യമല്ലെങ്കിൽ അവ നിരസിക്കുകയും ചെയ്യുന്നു. വ്യത്യസ്ത അർത്ഥരീതികളാണ് — `audit:deps` ഒഴിവാക്കിയാൽ സമ്പൂർണ്ണ ഗുരുതര ഗേറ്റും സ്വതന്ത്ര പാക്കേജ് ഓഡിറ്റ് രേഖകളും നഷ്ടപ്പെടും. രണ്ടും നിലനിർത്തുക.
- **സൈക്കിൾ കണ്ടെത്തൽ** — ✅ **പൂർത്തിയായി** (#15159 G-01/G-02). ഇവിടെയുള്ള പഴയ വാചകം `check:cycles`-നെ “പച്ചയായ, ക്യൂറേറ്റ് ചെയ്ത” ഗേറ്റ് എന്ന് വിളിക്കുകയും `check:circular-deps` (dpdm) 91 സൈക്കിളുകൾ റിപ്പോർട്ട് ചെയ്തതിനാൽ അതിനെ ബ്ലോക്കിംഗ് ആയി നിലനിർത്തുന്നത് ന്യായീകരിക്കുകയും ചെയ്തിരുന്നു. ആ പച്ച നില ഒരു **തെറ്റായ പച്ച** ആയിരുന്നു: `check:cycles` 5 ഉപഡയറക്ടറികൾ (450 ഫയലുകൾ) സ്കാൻ ചെയ്തു, സ്റ്റാറ്റിക് `import|export … from` മാത്രമാണ് പൊരുത്തപ്പെടുത്തിയത്, കൂടാതെ എല്ലാ `@/`, `@omniroute/open-sse/` സ്പെസിഫയറുകളും ഒഴിവാക്കി; അതിനാൽ repo-യിൽ കൂടുതലായി ഉണ്ടായിരുന്ന dynamic-import + alias സൈക്കിളുകൾ അതിന് കാണാൻ കഴിഞ്ഞില്ല. പരിഹരിച്ചു: ഗേറ്റ് ഇപ്പോൾ `src` + `open-sse` (5023 ഫയലുകൾ) പരിശോധിക്കുന്നു, TypeScript AST-യിൽനിന്ന് സ്പെസിഫയറുകൾ ശേഖരിക്കുന്നു (അതിനാൽ `import("…")` കണക്കാക്കപ്പെടും, എന്നാൽ type-position `typeof import("…")` കണക്കാക്കപ്പെടില്ല), കൂടാതെ tsconfig `paths` പരിഹരിക്കുന്നു. ഇത് 0 അല്ല, **14** സൈക്കിളുകൾ കണ്ടെത്തുന്നു. മുമ്പേ നിലവിലുണ്ടായിരുന്ന 14 സൈക്കിളുകൾ ഒരു ഗേറ്റ് PR-ൽ പരിഹരിക്കാൻ കഴിയാത്തതിനാൽ, `check:cycles` ഇപ്പോൾ ഒരു **റാച്ചറ്റ്** ആണ് (`--ratchet`, `quality-baseline.json`-ൽ പരിധി `metrics.cycles.value = 14`, `direction: down`) — ഏത് _പിന്നോട്ടുപോക്കും_ ഇത് തടയും, എണ്ണം കുറയാൻ മാത്രമേ കഴിയൂ. CI `npm run check:cycles:ratchet` പ്രവർത്തിപ്പിക്കുന്നു. ഘട്ടംഘട്ടമായ കുറയ്ക്കൽ **A-01**-നൊപ്പം പുരോഗമിക്കും. വിശാലമായ രണ്ടാമത്തെ അഭിപ്രായമായി `check:circular-deps` (dpdm) ഉപദേശാത്മകമായി തുടരും.
- **സങ്കീർണ്ണത** — ✅ **പൂർത്തിയായി** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ഒരൊറ്റ ESLint പരിശോധന; cyclomatic+max-lines, cognitive baseline-ുകൾ സ്വതന്ത്രമായി തുടരുന്നതിനായി ruleId അനുസരിച്ച് എണ്ണുന്നു; പ്രാദേശിക `--update`-നായി വ്യക്തിഗത `check:complexity` / `check:cognitive-complexity` നിലനിർത്തുന്നു.
