ഈ പ്രമാണമാണ് OmniRoute-ലെ എല്ലാ CI ഗുണനിലവാര ഗേറ്റുകൾക്കുമുള്ള ആധികാരിക റഫറൻസ്.
ഓരോ ഗേറ്റും, അത് എന്താണ് സാധൂകരിക്കുന്നത്, ഏത് CI ജോബിലാണ് അത് പ്രവർത്തിക്കുന്നത്, അത്
ഒരു റാച്ചറ്റ് ബേസ്ലൈൻ ആണോ അതോ പാസ്/ഫെയിൽ നയമാണോ ഉപയോഗിക്കുന്നത്, ബിൽഡ് തടയുന്നതാണോ അതോ ഉപദേശാത്മകമാണോ എന്നിവ ഇതിൽ വിവരിക്കുന്നു.

ഒരു ഹ്രസ്വ സംഗ്രഹത്തിനും അനുവദനീയ പട്ടികാ നയത്തിനും `AGENTS.md`-ലെ
"ഗുണനിലവാര ഗേറ്റുകളും റാച്ചറ്റുകളും" വിഭാഗം കാണുക. ഇതേ സിസ്റ്റത്തിന്റെ നിർണായക വിലയിരുത്തൽ,
മെച്യൂരിറ്റി വർഗ്ഗീകരണം, ടൂൾ-അഗ്നോസ്റ്റിക് പുനരാവിഷ്കരണ പദ്ധതി എന്നിവയ്ക്കായി
[ഗുണനിലവാര ഗേറ്റ് പ്ലേബുക്ക്](../ops/QUALITY_GATE_PLAYBOOK.md) കാണുക.

## ഗേറ്റ് ഇൻവെൻ്ററി, എക്സിക്യൂഷൻ പ്രൊഫൈലുകൾ

### സ്ഥാനാർത്ഥി പ്രവേശനം

CI, ക്വാളിറ്റി ഗേറ്റ്സ് വർക്ക്ഫ്ലോകൾ ഓരോന്നും സ്ഥിരമായ ഒരു വിധി പുറപ്പെടുവിക്കുന്നു: `Gate / CI`, `Gate / Quality`. അവരുടെ പതിപ്പ് അഡ്മിഷൻ പോളിസി ഓരോ അപ്സ്ട്രീം ജോലിയും ആവശ്യമുള്ളതോ ഉപദേശമോ ആയി കണക്കാക്കുന്നു. ബാധകമായ ആവശ്യമായ ജോലി വിജയിച്ചിരിക്കണം: നഷ്ടമായതും റദ്ദാക്കിയതും ഒഴിവാക്കിയതും തീർച്ചപ്പെടുത്താത്തതും അറിയാത്തതുമായ ഫലങ്ങൾക്ക് PASS സ്ഥാപിക്കാൻ കഴിയില്ല. സാധുവായ ഡോക്സ്-ഒൺലി അല്ലെങ്കിൽ കാറ്റലോഗ്-ഒൺലി വർഗ്ഗീകരണത്തിന് ഒരു കോഡ് ലെയ്നെ അപ്രായോഗികമാക്കാൻ കഴിയും; ഒരു ഡ്രാഫ്റ്റ് PR ഒരു അംഗീകൃത സ്ഥാനാർത്ഥിയല്ല. ഒരു `hotfix` ലേബൽ തെളിവുകൾ ഒഴിവാക്കില്ല.

രണ്ട് വർക്ക്ഫ്ലോകളും PRs main/release ബ്രാഞ്ചുകളിലേക്കും, `main` ലേയ്ക്കും, മാനുവൽ ഡിസ്പാച്ച്, ലയന-ഗ്രൂപ്പ് ഇവൻ്റുകളിലേക്കും പുഷ് ചെയ്യുന്നു. പുഷ്, ഡിസ്പാച്ച്, മെർജ്-ഗ്രൂപ്പ് എന്നിവ മുഴുവൻ തിരഞ്ഞെടുപ്പും പ്രവർത്തിപ്പിക്കുക. `release/**` ലേക്കുള്ള പുഷ്കൾ അവ ആരംഭിക്കരുത് (2026-10-18): ഓരോ മാറ്റവും ഇതിനകം തന്നെ അതിൻ്റെ PR യിൽ മാട്രിക്സ് പ്രവർത്തിപ്പിച്ചു, ലയിപ്പിച്ച സംയോജനമാണ് റിലീസ്-ഗ്രീൻ്റെ ജോലി (`docs/ops/RUNNER_BOX.md` → ഹോസ്റ്റഡ് ലെയ്ൻ). ഫോർക്കുകളും ലയന ഗ്രൂപ്പുകളും ജോലികൾക്കായി ഹോസ്റ്റ് ചെയ്ത റണ്ണർമാരെ ഉപയോഗിക്കുന്നു, അല്ലാത്തപക്ഷം സ്വയം-ഹോസ്റ്റഡ് റണ്ണർമാരെ തിരഞ്ഞെടുക്കുന്നു; റോൾഔട്ടിനു മുമ്പ് മതിയായ ഹോസ്റ്റ് ശേഷി പരിശോധിച്ചിരിക്കണം.

ഒരു സാധാരണ PR ഫാസ്റ്റ് സെലക്ഷൻ പ്രവർത്തിപ്പിക്കുന്നു. അഡ്മിഷൻ പോളിസിയുടെ `full-code`, `full-code-e2e` പാതകൾ (E2E, ഇൻ്റഗ്രേഷൻ, പാക്കേജ് ആർട്ടിഫാക്റ്റ്, Electron സ്മോക്ക്, Bun SQLite, ഇക്കോസിസ്റ്റം, പ്രോട്ടോക്കോൾ ക്ലയൻ്റുകൾ) ഒരു മെർജിഫൈ ക്യൂ ഡ്രാഫ്റ്റിൽ അല്ലെങ്കിൽ ഒരു പൂർണ്ണ ഓട്ടത്തിൽ മാത്രം പ്രവർത്തിക്കുന്നു: `gh workflow run ci.yml --ref <branch>`.

ഓരോ JSON രസീതും ചെക്ക്-ഔട്ട് SHA, വർക്ക്ഫ്ലോ റൺ, ശ്രമം എന്നിവ തിരിച്ചറിയുന്നു. CLI ഒരു checkout/event SHA പൊരുത്തക്കേട് നിരസിക്കുന്നു. വർക്ക്ഫ്ലോ ടെസ്റ്റുകൾ പോളിസി അംഗത്വത്തെ വിധി ജോലിയുടെ `needs` ലിസ്റ്റുമായി ബന്ധിപ്പിക്കുന്നതിനാൽ പുതിയതോ നീക്കം ചെയ്തതോ ആയ ഒരു പാത നിശബ്ദമായി അപ്രത്യക്ഷമാകില്ല. രസീതുകൾ അവരുടെ സ്വന്തം വർക്ക്ഫ്ലോ ഉൾക്കൊള്ളുന്നു, പ്രസിദ്ധീകരണമോ വിന്യാസമോ നിലവിലുള്ള ഒരു ഉപദേശക സ്കാനറിൻ്റെ ഇൻ്റേണലുകളോ അല്ല. ബ്രാഞ്ച് നിയമങ്ങളിൽ രണ്ട് ചെക്ക് നാമങ്ങളും സജീവമാക്കുന്നത് ഒരു പ്രത്യേക ഭരണപരമായ മാറ്റമാണ്; ഈ ജോലികൾ ചേർക്കുന്നത് ഒരു ശാഖയെ സംരക്ഷിക്കുന്നില്ല.

### ക്യൂ ലയിപ്പിക്കുക

`queue` ലേബൽ മെർജിഫൈ ക്യൂവിലേക്ക് (`.mergify.yml`) ഒരു PR അയയ്ക്കുന്നു. Mergify ഒരു `mergify/merge-queue/` ബ്രാഞ്ചിൽ ഒരു ഡ്രാഫ്റ്റ് PR തുറക്കുന്നു, CI അവിടെ മുഴുവൻ സെലക്ഷനും പ്രവർത്തിപ്പിക്കുന്നു, `Gate / CI`, `Gate / Quality`, `Merge integrity (changelog + generated skills)` എന്നിവ കടന്നുപോകുമ്പോൾ യഥാർത്ഥ PR ലയിക്കുന്നു.

മെർജിഫൈ അതിൻ്റെ ക്യൂ സംഗ്രഹം ഡ്രാഫ്റ്റിൻ്റെ വിവരണത്തിൽ എഴുതുന്നു, മറ്റ് ആപ്പുകൾക്ക് ഇത് എഡിറ്റ് ചെയ്യാനും കഴിയും. അത്തരം ഒരു ഡ്രാഫ്റ്റിലെ ഒരു `pull_request` `edited` ഇവൻ്റ് അതിൻ്റെ സ്വന്തം കൺകറൻസി ഗ്രൂപ്പ് (`-queue-edit-<run_id>`) എടുക്കുന്നു, അതിനാൽ അതിന് ഡ്രാഫ്റ്റിൻ്റെ യഥാർത്ഥ റൺ റദ്ദാക്കാൻ കഴിയില്ല, മാത്രമല്ല അത് ഗേറ്റും മാട്രിക്സും ഒഴിവാക്കുന്നു. `Merge integrity` മാത്രമേ ഇപ്പോഴും പ്രവർത്തിക്കൂ. ഒഴിവാക്കിയ ഗേറ്റ് ജോലിക്ക് മറ്റൊരു ചെക്ക് നാമമുണ്ട്, കാരണം Mergify ഒരു ഒഴിവാക്കിയ `Gate / CI` പരാജയപ്പെട്ട ചെക്കായി വായിക്കുകയും PR ഡീക്യൂവ് ചെയ്യുകയും ചെയ്യുന്നു.

ഒരു ഡീക്യൂവിന് ശേഷം, ഒരു പുഷ് എപ്പോഴും PR ക്യൂവുചെയ്യുന്നില്ല. അതിൽ `@mergifyio queue` കമൻ്റ് ചെയ്യുക.

### സ്വീകാര്യത റിഡ്യൂസറിൽ തെളിവുകൾ നിലനിർത്തി

`scripts/quality/validate-release-acceptance.mjs` ഒരു വിതരണം ചെയ്ത പദ്ധതിയും അതിൻ്റെ പ്രകടനവും കുറയ്ക്കുന്നു; പ്ലാൻ പൂർണ്ണമായ റിലീസ് പൈപ്പ്ലൈനിനെ ഉൾക്കൊള്ളുന്നുവെന്ന് ഇത് സ്ഥാപിക്കുന്നില്ല. പ്ലാൻ `VERIFIED` ആണെങ്കിലും അതിൻ്റെ റിപ്പോർട്ടുകൾ `releaseAcceptance: false` വ്യക്തമായി സജ്ജീകരിച്ചിരിക്കുന്നു. `release-acceptance.yml` വർക്ക്ഫ്ലോ ഇപ്പോഴും ഷാഡോ ഫിക്ചറുകളാണ് ഉപയോഗിക്കുന്നത്, യഥാർത്ഥ ബിൽഡ്, പാക്കേജ്, ബൂട്ട് അല്ലെങ്കിൽ പ്രൊമോഷൻ രസീതുകളല്ല.

നിലനിർത്തിയ തെളിവുകൾ പരിശോധിക്കാൻ CLI `--evidence-root` ആവശ്യമാണ്. ഫയലുകൾ `<evidence-root>/<artifact_id>/<member>` ആയി പരിഹരിച്ച് SHA-256 ആയി ഹാഷ് ചെയ്യുന്നു. തെളിവുകളില്ലാത്ത ഒരു PASS റെക്കോർഡ്, നഷ്ടപ്പെട്ടതോ മാറ്റിയതോ ആയ ഫയൽ, സുരക്ഷിതമല്ലാത്ത പാത അല്ലെങ്കിൽ സിംലിങ്ക് എന്നിവ സ്ഥിരീകരണത്തെ തടയുന്നു. വിട്ടുപോയ ഫയലുകൾ വിജയകരമായ ലോഗുകൾക്ക് തുല്യമല്ല. നിലവിലുള്ള SHA/run/attempt പരിശോധനകൾ സ്വതന്ത്രമായി തുടരുന്നു: പൊരുത്തപ്പെടുന്ന ബൈറ്റുകൾക്ക് പഴകിയ രസീത് വീണ്ടെടുക്കാൻ കഴിയില്ല. ഫയൽ സമഗ്രത എന്നത് നിർവ്വഹണ ആധികാരികതയുടെയോ ആർട്ടിഫാക്റ്റ് പ്രൊമോഷൻ്റെയോ തെളിവല്ല.

### സ്റ്റാറ്റിക് സ്കാൻ ഇൻവെൻ്ററി

പതിപ്പ് npm-അലിയാസ് ഇൻവെൻ്ററിയും സ്റ്റാറ്റിക്-സ്കാൻ അംഗത്വവും `config/quality/gate-manifest.json` യിൽ തത്സമയം. സ്ക്രിപ്റ്റ് നാമങ്ങളും `package.json` നെതിരെ കൃത്യമായ കമാൻഡുകളും സാധൂകരിക്കുന്നതിന് `npm run check:gate-manifest` പ്രവർത്തിപ്പിക്കുക; കൂട്ടിച്ചേർക്കലുകൾ, നീക്കം ചെയ്യലുകൾ, കമാൻഡ് ഡ്രിഫ്റ്റ് എന്നിവ CI ലെ ലോക്കൽ ഹുക്കിലും മാറ്റ-ക്ലാസിഫിക്കേഷൻ ജോലികളിലും പരാജയപ്പെടുന്നു. ഒരു അപരനാമം ഒരു വർക്ക്ഫ്ലോ ജോലിയോ മാട്രിക്സ് സന്ദർഭമോ ടെസ്റ്റ് കേസോ അല്ല: ഈ കണക്കുകൾ പരസ്പരം മാറ്റാവുന്നവയായി അവതരിപ്പിക്കാൻ പാടില്ല.

തിരഞ്ഞെടുത്ത അപരനാമങ്ങൾ എക്സിക്യൂട്ട് ചെയ്യാതെ പരിശോധിക്കാൻ `npm run quality:scan -- --list` അല്ലെങ്കിൽ `npm run quality:scan:fast -- --list` ഉപയോഗിക്കുക. റണ്ണർ npm എൻട്രി പോയിൻ്റ് ആവശ്യപ്പെടുന്നു, അതിനാൽ അതിൻ്റെ റൺടൈം (കോൺഫിഗർ ചെയ്തിരിക്കുന്ന Bun ഉൾപ്പെടെ) സംരക്ഷിക്കപ്പെടുന്നു. മാനിഫെസ്റ്റ് റെക്കോർഡുകൾ ആ പ്രൊഫൈലുകൾക്ക് പുറത്തുള്ള അപരനാമങ്ങൾ വെവ്വേറെ അഭ്യർത്ഥിച്ചിരിക്കുന്നു, കൂടാതെ റീഡ്-ഒൺലി സ്കാൻ പ്രൊഫൈലുകളിൽ മെയിൻ്റനൻസ് കമാൻഡുകൾ നിരോധിച്ചിരിക്കുന്നു.

ഈ പ്രൊഫൈലുകൾ സ്റ്റാറ്റിക് സ്കാൻ മാത്രം ഉൾക്കൊള്ളുന്നു. ഉൽപ്പന്ന പരിശോധനകൾ, കവറേജ്, പാക്കേജിംഗ്, ബാഹ്യ പരിശോധനകൾ അല്ലെങ്കിൽ ഒരു സ്ഥാനാർത്ഥിയുടെ പൂർണ്ണ റിലീസ് സ്വീകാര്യത എന്നിവ അവർ സാക്ഷ്യപ്പെടുത്തുന്നില്ല. വർക്ക്ഫ്ലോ പ്രവേശനം ലിങ്ക് ചെയ്ത `config/quality/admission-policy.json`, `scripts/quality/admission-verdict.mjs` എന്നിവ ഉപയോഗിക്കുന്നു. റിലീസ്-ഓബ്സർവർ പ്രൊഫൈലുകൾ പ്രത്യേകമായി നിലകൊള്ളുന്നു; അവരുടെ ബാധകമായ ചെക്കുകളും രസീതുകളും സ്വതന്ത്രമായി പരിശോധിക്കുക. `audit:deps`, മ്യൂട്ടേഷൻ-ടെസ്റ്റ് തിരഞ്ഞെടുക്കൽ, വിവർത്തന പരിശോധനകൾ എന്നിവയുൾപ്പെടെ പൂർണ്ണ നിരീക്ഷകൻ്റെ സ്റ്റാറ്റിക് കമാൻഡുകൾ `config/quality/release-green-static-profile.json` ൽ പ്രഖ്യാപിച്ചു. package.json, മോഡൽ ചെയ്ത CI/Quality പ്രഖ്യാപനങ്ങൾ എന്നിവയ്ക്കെതിരായ npm കമാൻഡുകൾ ലോഡർ സാധൂകരിക്കുന്നു; ഷെൽ ടോക്കണുകൾ ആർഗ്യുമെൻ്റുകളായി നടപ്പിലാക്കുന്നതിനുപകരം അത് ഡ്രിഫ്റ്റ് നിരസിക്കുന്നു. ആവശ്യമായ സ്കാനർ SKIP/INCOMPLETE ഔട്ട്പുട്ടിന് PASS സ്ഥാപിക്കാൻ കഴിയില്ല. പ്രൊഫൈൽ അതിൻ്റെ ബാഹ്യ ഒഴിവാക്കലുകൾ രേഖപ്പെടുത്തുന്നു കൂടാതെ ഹോസ്റ്റ് ചെയ്ത കവറേജ്, ടെസ്റ്റ് മെട്രിക്സ്, പാക്കേജ് അല്ലെങ്കിൽ വിന്യാസ തെളിവുകൾ എന്നിവ മാറ്റിസ്ഥാപിക്കുന്നില്ല. ചുവടെയുള്ള ഗദ്യ ഇൻവെൻ്ററി ഒരു റഫറൻസാണ്, ഒരു ഗേറ്റ് യഥാർത്ഥത്തിൽ ഓടിയെന്നതിൻ്റെ തെളിവല്ല.

സ്ക്രിപ്റ്റുകൾ `scripts/check/` (പോളിസി ഗേറ്റ്സ്), `scripts/quality/` (റാറ്റ്ചെറ്റ് എഞ്ചിൻ) എന്നിവയ്ക്ക് കീഴിലാണ് ജീവിക്കുന്നത്. സത്യത്തിൻ്റെ CI ഉറവിടം `.github/workflows/ci.yml` ആണ്.

### PR ഫാസ്റ്റ്-പാത്ത് (`quality.yml`) റിലീസ് ചെയ്യുക

`.github/workflows/quality.yml`, main/release PR-കളിലും `main`-ലേക്കുള്ള pushes-ലും dispatch-ലും merge groups-ലും CI-യെ പൂരിപ്പിക്കുന്നു. PR-കൾ path-filtered fast checks ഉപയോഗിക്കുന്നു. സ്ഥിരമായി പ്രവർത്തനരഹിതമാക്കിയിരുന്ന duplicate build നീക്കം ചെയ്തു; യഥാർത്ഥ build/package/boot checks CI-യിൽ തന്നെ തുടരുന്നു. Unit suite-ഉം vitest-ഉം CI-യിൽ മാത്രം പ്രവർത്തിക്കുന്നു (`Unit Tests (N/8)`, `Vitest`).

#### മറന്നുപോയ സഹോദര ടെസ്റ്റുകളുടെ റിപ്പോർട്ട്

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` യുടെ ഒരു ഉപദേശക ഘട്ടമായി പ്രവർത്തിക്കുകയും ടെസ്റ്റ്-ഇംപാക്റ്റ് മാപ്പിന് പിന്നിലെ ഇറക്കുമതി റിസോൾവർ വീണ്ടും ഉപയോഗിക്കുകയും ചെയ്യുന്നു. മാറ്റപ്പെട്ട ഓരോ പ്രൊഡക്ഷൻ മൊഡ്യൂളിനും, കാൻഡിഡേറ്റ് ടെസ്റ്റ് പുൾ-അഭ്യർത്ഥന വ്യത്യാസത്തിൽ ഇല്ലാതിരിക്കുമ്പോൾ അത് ഡിറ്റർമിനിസ്റ്റിക് `changed module/symbol -> static consumer -> candidate sibling test` ചെയിനുകൾ റിപ്പോർട്ട് ചെയ്യുന്നു. മാർക്ക്ഡൗൺ സംഗ്രഹവും JSON ഫലവും ഏതെങ്കിലും തടയൽ റോൾഔട്ടിന് മുമ്പായി കാലിബ്രേഷനുള്ള `forgotten-sibling-tests` വർക്ക്ഫ്ലോ ആർട്ടിഫാക്റ്റായി നിലനിർത്തുന്നു.

ബാരൽ റീ-കയറ്റുമതിയും ഡൈനാമിക് ഇറക്കുമതിയും റെസല്യൂഷൻ ഡയഗ്നോസ്റ്റിക്സ് മാത്രമാണ്; അവർ ഒരിക്കലും തടയുന്ന ഒരു കണ്ടെത്തൽ സൃഷ്ടിക്കുന്നില്ല. അവലോകനം ചെയ്ത ഒഴിവാക്കലുകൾ `config/quality/forgotten-sibling-allowlist.json` ൽ തത്സമയം. ഓരോ എൻട്രിയും ഉപഭോക്താവിൻ്റെയും കാൻഡിഡേറ്റിൻ്റെയും പരിശോധനയ്ക്ക് പേര് നൽകണം, ഒരു നിർദ്ദിഷ്ട യുക്തി നൽകണം, കൂടാതെ ഒരു GitHub ഇഷ്യൂ ലിങ്ക് ചെയ്യുകയോ അഭ്യർത്ഥന പിൻവലിക്കുകയോ വേണം. തെറ്റായ എൻട്രികൾ പരാജയപ്പെട്ടു. ഒഴിവാക്കലുകൾക്ക് ഇല്ലാതാക്കിയ കാൻഡിഡേറ്റ് ടെസ്റ്റ് അല്ലെങ്കിൽ `.skip`/`.todo` ചേർക്കുന്ന ഒരു വ്യത്യാസം ഇല്ലാതാക്കാൻ കഴിയില്ല ; അവകാശവാദം ദുർബലപ്പെടുത്തലും മറ്റ് മാസ്കിംഗും സ്വതന്ത്രമായി തടയുന്ന `check:test-masking` ഗേറ്റിൻ്റെ ഉടമസ്ഥതയിൽ തുടരുന്നു.

#### രണ്ട് ടൈപ്പ് ചെക്ക് പ്രോഗ്രാമുകൾ വ്യത്യസ്തമായി ഉത്തരം നൽകുന്നു

`typecheck:core`, `check:build-typecheck` എന്നിവ വ്യത്യസ്ത ഓപ്ഷനുകൾക്ക് കീഴിൽ വ്യത്യസ്ത പ്രോഗ്രാമുകൾ കംപൈൽ ചെയ്യുന്നു, ഒരേ ഫയൽ ഒന്നിൽ വൃത്തിയുള്ളതും മറ്റൊന്നിൽ പിശകുകൾ നിറഞ്ഞതും ആയിരിക്കും.

`tsconfig.build.json` `"strict": false` സജ്ജമാക്കുന്നു, അതിനാൽ `noImplicitAny` ഓഫാണ്. കോർ കോൺഫിഗറേഷൻ കർശനമായ ഓപ്ഷനുകളുള്ള ഒരു ക്യൂറേറ്റ് ചെയ്ത 27-ഫയൽ അനുവദനീയ പട്ടിക സമാഹരിക്കുകയും ഓരോ എൻട്രിയുടെയും ഇറക്കുമതി ഗ്രാഫ് പിന്തുടരുകയും ചെയ്യുന്നു, അതിനാൽ ബിൽഡ് പ്രോഗ്രാമിൽ ഒരിക്കലും ദൃശ്യമാകാത്ത ഫയലുകൾ ഇപ്പോഴും അവിടെ പരിശോധിക്കും.

ഒരു ഫയൽ ടൈപ്പ് ചെയ്തിട്ടുണ്ടോ എന്ന് വിലയിരുത്തുമ്പോൾ അനന്തരഫലം പ്രധാനമാണ്:** `check:build-typecheck` യുടെ കീഴിലുള്ള സീറോ ഡയഗ്നോസ്റ്റിക്സ് പൂജ്യം എന്നല്ല അർത്ഥമാക്കുന്നത്** . 26 ഫയലുകളിൽ നിന്ന് `@ts-nocheck` സ്ട്രിപ്പുചെയ്യുന്നത് ബിൽഡ് പ്രോഗ്രാമിൽ 23 എണ്ണം വൃത്തിയുള്ളതായി കാണിച്ചു; അതിൽ പതിനാറ് എണ്ണം 120 ഓളം പ്രത്യക്ഷമായി - കർശനമായതിൽ എന്തെങ്കിലും പിശകുകൾ. ഒരു ഫയൽ ക്ലീൻ ചെയ്യുന്നതിനു മുമ്പ് രണ്ടും പരിശോധിക്കുക.

#### വിവർത്തന മിററുകൾ ഉരുത്തിരിഞ്ഞ ഫയലുകളാണ് (PR മോഡ് vs റിലീസ് മോഡ്)

ഒരു ഫീച്ചർ PR ഇംഗ്ലീഷ് ഉറവിടങ്ങൾ മാത്രം എഡിറ്റ് ചെയ്യുന്നു. `docs/i18n/<locale>/**` മിററുകളും (66 `llm.txt` പകർപ്പുകളും വിവർത്തനം ചെയ്ത `CHANGELOG.md` ഫയലുകളും ഉൾപ്പെടെ) `.i18n-state.json` എന്നിവ ഒരു ഘട്ടത്തിൽ വിവർത്തന തരംഗത്തിലൂടെയും (`docs/i18n-*` / `chore/i18n-*` ശാഖകൾ, ഷെഡ്യൂൾ ചെയ്ത `i18n-mirror-refresh.yml`) റിലീസ് വഴിയും (`npm run release:sync-changelog-i18n`) മാറ്റിയെഴുതുന്നു. അതിനാൽ മിറർ ഗേറ്റുകൾ രണ്ട് മോഡുകളിൽ പ്രവർത്തിക്കുന്നു, `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`, പിന്നെ `OMNIROUTE_GATE_MODE`, തുടർന്ന് പ്രവർത്തന ഇവൻ്റ്; ഒരു ലോക്കൽ റൺ `release` ആണ്):

- `check:docs-sync` — റിലീസ് മോഡ് എല്ലാ പരിശോധനകളും നടത്തുന്നു. PR മോഡ് package.json/OpenAPI പതിപ്പ്,
  റൂട്ട് CHANGELOG തലക്കെട്ടുകൾ, superseded-docs ഗാർഡ് എന്നിവ നിലനിർത്തുകയും,
  `llm.txt` മിറർ പകർപ്പുകൾക്കും വിവർത്തനം ചെയ്ത CHANGELOG വിഭാഗങ്ങൾക്കും
  `SKIP reason=pr-mode` പ്രിന്റ് ചെയ്യുകയും ചെയ്യുന്നു — എന്നാൽ PR മിററുകൾ എഴുതുന്നുവെങ്കിൽ:
  `config/quality/derived-paths/*.json`-ൽ `docs/i18n/**` കുടുംബത്തിന്റെ writer ആയി പ്രഖ്യാപിച്ചിരിക്കുന്ന
  head branch രണ്ട് പരിശോധനകളും കർശനമായി നടത്തും. കൂടാതെ diff base പരിഹരിക്കപ്പെടുമ്പോൾ,
  സ്വന്തം diff `docs/i18n/<locale>/llm.txt` അല്ലെങ്കിൽ `CHANGELOG.md` തിരുത്തുന്ന മാറ്റം ആ പരിശോധന
  കർശനമായി നടത്തും. depth-1 checkout-ൽ ( `docs-sync-strict` job) diff base പരിഹരിക്കപ്പെടുന്നില്ല,
  അതിനാൽ PR മോഡ് base ആവശ്യമില്ലാത്ത ഒരു പരിശോധനയും നടത്തുന്നു: ഓരോ `llm.txt` മിററും
  ഉണ്ടായിരിക്കണം, അതിലെ `---` separator നിലനിർത്തണം, കൂടാതെ റൂട്ട് body അല്ലെങ്കിൽ മിക്ക മിററുകളും
  പങ്കിടുന്ന body വഹിക്കണം. Base മാറിയാൽ എല്ലാ മിററുകളും ഒരുപോലെ പഴയതാകും, അതിനാൽ പരിശോധന
  വിജയിക്കും; എന്നാൽ ഒരു മിറർ കൈകൊണ്ട് തിരുത്തിയാൽ പരാജയപ്പെടും. depth-1 PR checkout-ൽ
  വിവർത്തനം ചെയ്ത `CHANGELOG.md` ഫയലുകൾക്ക് ഇത്തരത്തിലുള്ള പരിശോധനയില്ല.

- Pre-commit hook `check-docs-sync.mjs --mode=pr` പ്രവർത്തിപ്പിക്കുന്നു: ഒരു commit അത് ചെയ്യുന്ന
  മാറ്റത്തിന്റെ അടിസ്ഥാനത്തിലാണ് വിലയിരുത്തപ്പെടുന്നത്. Flag ഇല്ലെങ്കിൽ local run release മോഡായിരിക്കും,
  കൂടാതെ റൂട്ട് `llm.txt` തിരുത്തുന്ന ഒരു merged PR, wave പ്രവർത്തിക്കുന്നതുവരെ ആ base-ലുള്ള
  എല്ലാ പിന്നീടുള്ള commit-ുകളെയും തടയും. Husky hook പ്രവർത്തിപ്പിക്കുന്ന mode-aware gate-ുകൾക്കും
  ഇതേ നിയമമാണ്: hook `--mode=pr` പാസാക്കും, എന്നാൽ strict verdict release-mode run-ുകളിൽ
  തന്നെ തുടരും (release PR, `main`-ലേക്കുള്ള pushes, plain local run).
- മിറർ-ഉള്ളടക്ക യൂണിറ്റ് ടെസ്റ്റുകൾ (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) — റിലീസ് മോഡ് എല്ലാ ലൊക്കേലും ഉറപ്പിക്കുന്നു. PR മോഡ് `.i18n-state.json` അനുസരിച്ച് ഇംഗ്ലീഷ് ഉറവിടത്തിനൊപ്പം നിലവിലുള്ള മിററുകൾ മാത്രം ഉറപ്പിക്കുന്നു (മുഴുവൻ-ഫയൽ ഹാഷ്, അല്ലെങ്കിൽ വിഭാഗത്തിൻ്റെ റെക്കോർഡ് ചെയ്ത സെക്ഷൻ ഹാഷ് ടെസ്റ്റ് പിൻസ്) കൂടാതെ പഴകിയവ ഒഴിവാക്കുകയും ചെയ്യുന്നു. `target_hash` പ്രൊവെനൻസ് ചെക്കുകൾ ഓരോ ലൊക്കേലിനും രണ്ട് മോഡുകളിലും പ്രവർത്തിക്കുന്നു. ഫ്രഷ്നെസ് ഓരോ `## ` വിഭാഗത്തിനും ആണ്, യൂണിറ്റ് `run-translation.mjs` ഹാഷുകൾ; ഒരു നീണ്ട ഭാഗം (ഈ ഫയലിൻ്റെ ഗേറ്റ് ഇൻവെൻ്ററി അതിൻ്റെ പകുതിയോളം വരും) അർത്ഥമാക്കുന്നത് അതിലെ ഏതെങ്കിലും എഡിറ്റ് ആ മിററുകൾ പഴകിയതാക്കി മാറ്റുന്നു, കൂടാതെ അവരുടെ പിആർ മോഡ് അവകാശവാദങ്ങൾ അടുത്ത തരംഗം വരെ ഒഴിവാക്കുകയും ചെയ്യും. ഇംഗ്ലീഷ് ഉറവിടത്തിൽ ഇനി അടങ്ങാത്ത ഒരു ആങ്കർ മുഴുവൻ ഫയൽ താരതമ്യത്തിലേക്ക് മടങ്ങുന്നു.

### ഉരുത്തിരിഞ്ഞ മൂല്യങ്ങൾ: `pr`, `release` ഗേറ്റ് മോഡുകൾ

ഒരു ഫീച്ചർ PR ഒരിക്കലും അതിൻ്റെ അടിത്തറയുടെ അവസ്ഥയെ ആശ്രയിച്ചിരിക്കുന്ന ഒരു മൂല്യം എഴുതുന്നില്ല: ദാതാവ്, മൈഗ്രേഷൻ, MCP- ടൂൾ, സ്ട്രാറ്റജി കൗണ്ടുകൾ, README SVG നമ്പറുകൾ, വസ്തുതകളുടെ സ്നാപ്പ്ഷോട്ട്. ഒരു ഘട്ടം അവയെല്ലാം റീകമ്പ്യൂട്ടുചെയ്യുന്നു, `npm run release:refresh-derived`, റിലീസിലൂടെയും രാത്രിയിൽ ലഭിച്ച പുതുക്കിയ PR വഴിയും പ്രവർത്തിക്കുന്നു. അങ്ങനെ** റിലീസുകൾക്കിടയിലുള്ള അടിസ്ഥാനം ഡിസൈൻ പ്രകാരം ലൈവ് കോഡിന് പിന്നിലാണ്** , കൂടാതെ ഒരു സഹോദരൻ ഒരു ദാതാവിനെ ചേർത്തതിന് ശേഷം, തത്സമയ കോഡുമായി ട്രീയെ താരതമ്യം ചെയ്യുന്ന ഒരു ഗേറ്റോ ടെസ്റ്റോ ഓരോ PR ലും ചുവപ്പായിരിക്കും. മൂല്യങ്ങളെ വിലയിരുത്തുന്ന ഗേറ്റുകൾ രണ്ട് മോഡുകളിൽ ഒന്നിൽ പ്രവർത്തിക്കുന്നു, `scripts/check/lib/gateMode.mjs` (ആദ്യ മത്സര വിജയങ്ങൾ):

1. കമാൻഡ് ലൈനിൽ `--mode=pr|release` ;
2. `OMNIROUTE_GATE_MODE` എൻവയോൺമെൻ്റ് വേരിയബിൾ (`pr` അല്ലെങ്കിൽ `release`);
3. automatic, from the GitHub Actions event: a `pull_request` whose head is not `release/v*`, a `merge_group`, or a push to `omni-queue/**` → `pr`; മറ്റെല്ലാം (പുഷ്, ഷെഡ്യൂൾ, ഡിസ്പാച്ച്, റിലീസ് PR `release/v* → main`, ഏതെങ്കിലും പ്രാദേശിക റൺ) → `release`.

ഓരോ മോഡിലും എന്ത് `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) പരാജയപ്പെടുന്നു:

| മോഡ്      | പരാജയപ്പെടുന്നു                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | തത്സമയ വസ്തുതകൾ ആവശ്യമാണ് |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| `release` | ഓരോ പരിശോധനയും, മരത്തിൽ നിന്ന് ശേഖരിക്കുന്ന വസ്തുതകൾക്കെതിരായ കർശനമായ തുല്യത (ഗേറ്റിന് എപ്പോഴും ഉണ്ടായിരുന്ന സ്വഭാവം): പഴകിയ എണ്ണം, പതിപ്പ്, കവറേജ് ഫ്ലോർ അല്ലെങ്കിൽ SVG നമ്പർ ഒരു STRICT ഡ്രിഫ്റ്റ് ആണ്                                                                                                                                                                                                                                                                        | അതെ                       |
| `pr`      | ഒരേ ക്ലെയിം എക്സ്ട്രാക്റ്ററുകളുള്ള PR ബേസുമായി വ്യത്യസ്തമായി മാറ്റം വരുത്തിയത് മാത്രം: (1) ആ പരിശോധനയ്ക്കും ഫയലിനുമായി ബേസിൽ നിലവിലില്ലാത്ത ഒരു നിയന്ത്രിത മൂല്യം ("PR എഡിറ്റ് ചെയ്ത ഒരു നിയന്ത്രിത സംഖ്യ — അടിസ്ഥാന വാചകത്തിലേക്ക് ലൈൻ പുനഃസ്ഥാപിക്കുക"); (2) അടിസ്ഥാനം വഹിക്കുകയും തല നഷ്ടപ്പെടുകയും ചെയ്ത ഒരു ആവശ്യമായ അവകാശവാദം. വസ്തുതകൾ ആവശ്യമില്ലാത്ത ഉള്ളടക്ക മാറ്റങ്ങൾ റിലീസ് മോഡിൽ പ്രവർത്തിക്കുന്നു; റിലീസ്-മാത്രം ചെക്കുകൾ ലിസ്റ്റ് ചെയ്യുകയും ഒഴിവാക്കുകയും ചെയ്തു | ഇല്ല                      |

ഏജൻ്റ്-നിർദ്ദേശ ഫയലുകൾ വഹിക്കുന്നു** ഇല്ല** ഉരുത്തിരിഞ്ഞ എണ്ണം: `AGENTS.md`, `llm.txt` (അതിൻ്റെ `docs/i18n/*/llm.txt` പകർപ്പുകൾ), bs `AGENTS.md` ഫോർക്ക്, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` കൂടാതെ ഓരോ `skills/*/SKILL.md` പോയിൻ്റും ഉറവിടത്തിലേക്കും (ഉദാഹരണത്തിന് `ROUTING_STRATEGY_VALUES` ലെ `src/shared/constants/routingStrategies.ts`) പകരം `npm run facts` യിലേക്കും. മാറ്റമില്ലാത്ത "ഡിറൈവ്ഡ് കൗണ്ടുകൾ ഇല്ല (ഏജൻറ്-ഇൻസ്ട്രക്ഷൻ ഫയൽ ...)" രണ്ട് മോഡുകളിലും (ദാതാക്കൾ, മൈഗ്രേഷനുകൾ, MCP ടൂളുകളും സ്കോപ്പുകളും, റൂട്ടിംഗ് സ്ട്രാറ്റജികൾ, സ്കോറിംഗ് ഘടകങ്ങൾ, മോഡ് പാക്കുകൾ) ഒരു എണ്ണത്തിൽ പരാജയപ്പെടുന്നു, അതിനാൽ റിലീസ് റിഫ്രഷിന് ഒരിക്കലും ഒരു നിർദ്ദേശ ഫയൽ വീണ്ടും എഴുതേണ്ടതില്ല.

`pr` മോഡിൽ, റൈറ്റർ ബ്രാഞ്ചുകൾക്ക് നിയന്ത്രിത മൂല്യങ്ങൾ എഡിറ്റ് ചെയ്യാം: `chore/derived-*` (രാത്രിയിലെ പുതുക്കൽ PR), `release/v*`, വിവർത്തന തരംഗങ്ങളായ `docs/i18n-*`, `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). ക്യൂ ബാച്ചുകൾ (`merge_group`, Mergify ഡ്രാഫ്റ്റുകൾ, `omni-queue/**`) വീണ്ടും വിലയിരുത്തപ്പെടുന്നില്ല: അവ PRs ഗേറ്റിനെ ഒന്നൊന്നായി കണക്കാക്കുന്നു.

STRICT `0` `1` — `OMNIROUTE_FACTS_TIMEOUT_MS` `--strict` `2` CIPR എക്സിറ്റ് 2 ഒരിക്കലും ഒരു ഡോക്യുമെൻ്റേഷൻ വ്യതിചലനമല്ല: ജോലി വീണ്ടും പ്രവർത്തിപ്പിക്കുക അല്ലെങ്കിൽ പരിസ്ഥിതി പരിഹരിക്കുക.

ലോക്കൽ-പാരിറ്റി യൂണിറ്റ് ടെസ്റ്റുകൾ (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) `tests/_helpers/localeParityMode.ts` വഴിയുള്ള അതേ മോഡുകൾ പിന്തുടരുന്നു: `pr` മോഡിൽ അവർ കീ-പാരിറ്റി അവകാശവാദങ്ങൾ ഒഴിവാക്കുകയും റിലീസിന് വിടുകയും ചെയ്യുന്നു, കൂടാതെ ലയനത്തിന് ശേഷം ഇംഗ്ലീഷ് മാറിയത് മുതൽ യൂണിറ്റ് ബേസ് വായിക്കാൻ കഴിയാത്ത കീകളുടെ പ്ലെയ്സ്ഹോൾഡർ പാരിറ്റി പുതുക്കുന്നു. ആ സഹായിയാണ്** മാത്രം** അനുവദിച്ച മോഡ്-കണ്ടീഷണൽ skip: `check:test-masking` കണക്കാക്കുന്നത് `.skip(`, `{ skip: true }`, പക്ഷേ അത് തിരികെ നൽകുന്ന കമ്പ്യൂട്ട് ചെയ്ത `{ skip: "<reason>" }` അല്ല, അതിനാൽ `tests/unit/locale-parity-mode.test.ts` അത് ഉപയോഗിക്കാൻ അനുവദിച്ചിരിക്കുന്ന ടെസ്റ്റുകളുടെ ലിസ്റ്റ് പിൻ ചെയ്യുന്നു — ആ ലിസ്റ്റിലേക്ക് ഒരു അവലോകനം ചെയ്ത എഡിറ്റ് ചേർക്കുന്നു.

#### `check-ui-value-drift` — പഴകിയ-വിവർത്തന ഗേറ്റ്

മറ്റ് ഗേറ്റുകൾക്ക് ഘടനാപരമായി കാണാൻ കഴിയാത്ത ഒരു i18n റിഗ്രഷൻ ക്യാച്ച് ചെയ്യുന്നു: ഒരു ഇംഗ്ലീഷ് മൂല്യം മാറ്റിയെഴുതുകയും _previous_ ഇംഗ്ലീഷിൽ നിന്ന് ഉരുത്തിരിഞ്ഞ വിവർത്തനങ്ങൾ പിന്നിലായിരിക്കുകയും ചെയ്യുന്നു, അതിനാൽ ഇംഗ്ലീഷല്ലാത്ത ഉപയോക്താക്കൾ ആത്മവിശ്വാസത്തോടെ വാക്കുകളുള്ളതും ഇപ്പോൾ തെറ്റായതുമായ പകർപ്പ് വായിക്കുന്നു.

ഇത് യഥാർത്ഥമായി അയച്ചു. ആൻ്റിഗ്രാവിറ്റി ലോഗിൻ സഹായി ഇറങ്ങിയപ്പോൾ `oauthModal.googleOAuthWarning` മാറ്റിയെഴുതി (#5203);** 43 പ്രദേശങ്ങളിൽ 39 എണ്ണം** "പൂർണ്ണ URL പകർത്തി താഴെ ഒട്ടിക്കുക" എന്ന് ഓപ്പറേറ്റർമാരോട് പറയുന്ന ടെക്സ്റ്റ് ആ ദാതാവിന് പൂർത്തിയാക്കാൻ കഴിയാത്ത ഒരു ഫ്ലോ —. #8463 വരെ ഇത് ശ്രദ്ധിക്കപ്പെടാതെ പോയി കാരണം:

- `sync-ui-keys` ബാക്ക്ഫിൽ ചെയ്യുന്ന കീകൾ മാത്രം** ഇല്ല** , ഒരിക്കലും അല്ലാത്തവ** പഴകിയ** ;
- `check-ui-keys-coverage` കീ _സാന്നിധ്യം_ കണക്കാക്കുന്നു, അതിനാൽ ഒരു പഴകിയ വിവർത്തനം കവർ ചെയ്തതുപോലെ സ്കോർ ചെയ്യുന്നു;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ഡോക്യുമെൻ്റേഷൻ മിറർ ചെയ്യുന്നു — അത് ഒരിക്കലും `src/i18n/messages/*.json` വായിക്കുന്നില്ല. ഇത് ജോബ് `docs-sync-strict` ൽ പ്രവർത്തിക്കുന്നു: PRs നെക്കുറിച്ചുള്ള ഉപദേശം, തള്ളുന്നതിലും രാത്രിയിലും കർശനമായി; വിവർത്തന തരംഗം കണ്ണാടികളെ പുതുക്കുന്നു, സവിശേഷത PR അല്ല.

**വ്യത്യസ്തമായി അറിയാം, അടിസ്ഥാനപരമായ പിന്തുണയുള്ളതല്ല.** ഇത് ലയന അടിത്തറയിലുള്ള `en.json` പ്രവർത്തിക്കുന്ന മരവുമായി താരതമ്യം ചെയ്യുന്നു; ഇംഗ്ലീഷ് മൂല്യം മാറിയ എല്ലാ കീകൾക്കും, അസ്പൃശ്യമായ വിവർത്തനം കൈവശമുള്ള ഏതൊരു ഭാഷയും പഴയതാണ്. ഇത് ബോധപൂർവ്വം** മുമ്പുണ്ടായിരുന്ന കടം മരവിപ്പിക്കുന്നു** — ഒരു വ്യത്യാസത്തിന് ഏത് പഴയ ഇംഗ്ലീഷിൽ നിന്നാണ് ദീർഘകാല വിവർത്തനം വന്നതെന്ന് വെളിപ്പെടുത്താൻ കഴിയില്ല, അതിനാൽ നിലവിലെ മാറ്റം എന്താണ് സ്പർശിക്കുന്നതെന്ന് ഗേറ്റ് വിലയിരുത്തുന്നു. ബദലായി (ഓരോ-കീ ഹാഷ് ബേസ്ലൈനും) ഒരു ~ 600 KB ജനറേറ്റഡ് ഫയലിന് ചിലവാകും, 3 × നിലവിലുള്ള ഏറ്റവും വലിയ ബേസ്ലൈൻ, ഓരോ i18n PR ലും കറങ്ങുന്നു.

അത് തൃപ്തിപ്പെടുത്താൻ രണ്ട് വഴികൾ:

1. ബാധിച്ച വിവർത്തനങ്ങൾ അപ്ഡേറ്റ് ചെയ്യുക, അല്ലെങ്കിൽ
2. അവയെ `__MISSING__:<new english>` — ആയി സജ്ജീകരിക്കുക, റൺടൈം തിരുത്തിയ ഇംഗ്ലീഷും (`src/i18n/request.ts::deepMergeFallback`, #7258) വിവർത്തനത്തിനുള്ള പ്രധാന ക്യൂകളും നൽകുന്നു.

സ്ട്രിംഗ് ആണെങ്കിൽ** അർത്ഥം** മാറ്റി, മുൻഗണന** കീയുടെ പേര് മാറ്റുന്നു** : ഒരു പുതിയ കീയ്ക്ക് പഴകിയ വിവർത്തനം അവകാശമാക്കാൻ കഴിയില്ല. അതാണ് #8463 പാറ്റേൺ ഉപയോഗിച്ചിരിക്കുന്നത്.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

അടിസ്ഥാന കാറ്റലോഗ് വായിക്കാൻ കഴിയാത്തപ്പോൾ `SKIP reason=base-unresolved` ഉപയോഗിച്ച് 0-ൽ നിന്ന് പുറത്തുകടക്കുന്നു (ബേസ് റെഫറില്ലാത്ത ആഴമില്ലാത്ത ക്ലോൺ), `check-openapi-breaking` മിററിംഗ് ചെയ്യുന്നു. റിലീസ് മോഡ് മാത്രം: ഒരു സവിശേഷത PR ഇംഗ്ലീഷിൽ വീണ്ടും എഴുതുകയും അവിടെ നിർത്തുകയും ചെയ്യുന്നു; റിലീസ് പുതുക്കൽ അത് ഉപേക്ഷിച്ച വിവർത്തനങ്ങളെ അടയാളപ്പെടുത്തുന്നു (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, അതേ `findStaleTranslations`).

**പുതിയ-കോഡ് മോഡ് (Clean-as-You-Code) — 2026-08-30 മുതൽ, PR fast-path-ൽ മാത്രം**

`pull_request` ഇവന്റുകളിൽ `quality.yml`, `check:file-size`,
`check:complexity-ratchets`, `check:dead-code` എന്നിവയ്ക്ക് `--base-ref <PR base SHA>` നൽകുന്നു. `check:complexity-ratchets`, `check:dead-code` എന്നിവയ്ക്കായി
ഗേറ്റ് merge-base-നെ **PR സ്പർശിച്ച ഫയലുകളിൽ മാത്രം പരിമിതപ്പെടുത്തി** HEAD-ുമായി താരതമ്യം ചെയ്യുന്നു
(`scripts/check/newCodeMode.mjs`: merge-base താൽക്കാലികമായി ഉപയോഗിക്കുന്ന ഒരു
`git worktree`-യിൽ materialize ചെയ്യുന്നു, ESLint/knip അവിടെയും HEAD-ലും പ്രവർത്തിപ്പിക്കുന്നു, ഓരോ ഫയലിലെയും
കണക്കുകൾ തമ്മിൽ diff ചെയ്യുന്നു):

- **blocking** — PR മാറ്റം വരുത്തിയ ഫയലുകളിൽ cyclomatic/cognitive ലംഘനങ്ങളോ dead exports-ഓ PR ചേർത്താൽ
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` എന്നിവ ലോഗിൽ);
- **advisory** — ഫ്രീസ് ചെയ്ത ബേസ്ലൈനുമായി താരതമ്യം ചെയ്യുന്ന ആഗോള ആകെ എണ്ണം. പാരമ്പര്യമായി ലഭിച്ച drift
  ഒരു നിരപരാധിയായ PR-നെ ഒരിക്കലും red ആക്കില്ല; release reconciliation സമയത്ത് drift വീണ്ടും freeze ചെയ്യുകയും
  headroom job അത് നിരീക്ഷിക്കുകയും ചെയ്യും.

`check:file-size` base ref-നെ സ്വന്തം നിബന്ധനകൾ പ്രകാരം ഉപയോഗിക്കുന്നു
(`scripts/check/check-file-size.mjs`, #8522):
ഇത് tree-യിലെ എല്ലാ source, test ഫയലുകളും പരിശോധിക്കുന്നു, `git show` ഉപയോഗിച്ച് PR base-ൽ ഓരോ ഫയലിന്റെയും
line count വായിക്കുന്നു, കൂടാതെ അതിന്റെ baseline ceiling
(`frozen` / `testFrozen`, അല്ലെങ്കിൽ baseline-ന് പുറത്തുള്ള ഫയലിനുള്ള `cap` / `testCap`)യും base
size-ഉം തമ്മിലുള്ള വലുതായ മൂല്യം കടന്നാൽ മാത്രമേ ഒരു ഫയൽ പരാജയപ്പെടുകയുള്ളൂ. Base-ൽ തന്നെ drift ചെയ്തിട്ടുള്ള
ഒരു ഫയൽ അതിനാൽ നിരപരാധിയായ PR-നെ ഒരിക്കലും red ആക്കില്ല.

`check:boundary:ratchet` അതിന്റെ ഏക സംഖ്യയ്ക്കും ഇതേ നിയമം പ്രയോഗിക്കുന്നു
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ഇവന്റുകളിൽ
`quality.yml`-ലെ ഫാസ്റ്റ്-ഗേറ്റുകളും `ci.yml`-ലെ lint ജോബും PR-ന്റെ base SHA കൈമാറുന്നു,
base commit ഒരു `git archive` എക്സ്പോർട്ടിൽ നിന്ന് അളക്കുന്നു, കൂടാതെ അതിന്റെ
`open-sse → src` എഡ്ജ് എണ്ണം `metrics.boundaryOpenSseToSrc`-നും base-ലെ എണ്ണത്തിനും ഇടയിലെ
വലുതിനെ കവിയുമ്പോഴേ PR പരാജയപ്പെടുകയുള്ളൂ. ceiling-നു മുകളിലുള്ള base drift
(`base drift herdado`) റിപ്പോർട്ട് ചെയ്യും, എന്നാൽ നിരപരാധിയായ PR-നെ ഒരിക്കലും ചുവപ്പിക്കില്ല;
push → main absolute ceiling നിലനിർത്തുന്നു, പരിഹരിക്കാനാകാത്ത base SHA ഒരു മുന്നറിയിപ്പോടെ
അതിലേക്കു fallback ചെയ്യും.

## റാച്ചറ്റ് അടിസ്ഥാനരേഖ (`quality-baseline.json`)

റാച്ചറ്റ് എഞ്ചിൻ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` വായിച്ച്,
പുതുതായി ശേഖരിച്ച `quality-metrics.json`-നുമായി താരതമ്യം ചെയ്യുന്നു. ഏതെങ്കിലും മെട്രിക്
അതിന്റെ എപ്സിലോണിനെക്കാൾ കൂടുതലായി പിന്നോട്ടുപോയാൽ ബിൽഡ് പരാജയപ്പെടും.

നിലവിൽ ട്രാക്ക് ചെയ്യുന്ന മെട്രിക്കുകൾ:

| മെട്രിക്              | ദിശ    | അർത്ഥം                                      |
| --------------------- | ------ | ------------------------------------------- |
| `eslintWarnings`      | `down` | ESLint മുന്നറിയിപ്പുകളുടെ എണ്ണം വർധിക്കരുത് |
| `coverage.statements` | `up`   | സ്റ്റേറ്റ്മെന്റ് കവറേജ് കുറയരുത്            |
| `coverage.lines`      | `up`   | ലൈൻ കവറേജ് കുറയരുത്                         |
| `coverage.functions`  | `up`   | ഫംഗ്ഷൻ കവറേജ് കുറയരുത്                      |
| `coverage.branches`   | `up`   | ബ്രാഞ്ച് കവറേജ് കുറയരുത്                    |

യഥാർത്ഥമായ മെച്ചപ്പെടുത്തലിന് ശേഷം അടിസ്ഥാനരേഖ അപ്ഡേറ്റ് ചെയ്യാൻ:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

റീബിൽഡ് ചെയ്യുകയും ഓരോ തവണയും സമ്പൂർണ്ണ ESLint പരിശോധനയ്ക്കുള്ള ചെലവ് വഹിക്കുകയും ചെയ്യും. കണ്ടെത്തൽ `push`-ൽ തന്നെ തുടരുന്നു
(`release-green`); ബാങ്കിംഗ് മാത്രമാണ് ബാച്ച് ചെയ്യുന്നത്.

### സുരക്ഷാ വെരിഫയർ

job മേൽനോട്ടമില്ലാതെ ബേസ്ലൈനുകളിലേക്ക് എഴുതുന്നതിനാൽ, അത് സ്വീകാര്യമാക്കുന്നത് `verify-ratchet-bank.mjs` ആണ്.
ഇത് `--update`-ന് ശേഷമുള്ള ട്രീയെ `HEAD`-മായി diff ചെയ്യുകയും, ഓരോ മാറ്റവും താഴെപ്പറയുന്നവയിൽ ഒന്നല്ലെങ്കിൽ,
**ഏതെങ്കിലും കമ്മിറ്റ് ഉണ്ടാകുന്നതിന് മുമ്പ് job നിർത്തലാക്കുകയും** ചെയ്യുന്നു — ഒരു PR-ഉം തുറക്കില്ല:

- `frozen` / `testFrozen` സംഖ്യാ എൻട്രി **താഴ്ത്തിയത്** അല്ലെങ്കിൽ **നീക്കിയത്**
- `complexity-baseline.json` → `count` **താഴ്ത്തിയത്**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **താഴ്ത്തിയത്**

മറ്റെന്തും പരാജയപ്പെടും: ഒരു സംഖ്യ ഉയർത്തുക, ഒരു എൻട്രി ചേർക്കുക, `cap`/`testCap` മാറ്റുക, അല്ലെങ്കിൽ
ഒരു `_rebaseline_*` കുറിപ്പ് ഇല്ലാതാക്കുക/വീണ്ടും എഴുതുക (ഓരോ പരിധിയും എന്തുകൊണ്ട് നിലവിലുണ്ട് എന്നതിനുള്ള ഓഡിറ്റ് ട്രെയിലാണ് ആ കുറിപ്പുകൾ;
ഫയൽ എൻട്രികൾക്കൊപ്പം അതേ `frozen` ഒബ്ജക്റ്റിനുള്ളിലാണ് അവ സൂക്ഷിച്ചിരിക്കുന്നത്).
ഒരു പരിധി ഉയർത്താൻ കഴിയുന്ന ബോട്ട് നിലവിലെ അവസ്ഥയെക്കാൾ തീർച്ചയായും മോശമായിരിക്കും. റിഗ്രഷൻ
ഗാർഡ്: `tests/unit/verify-ratchet-bank.test.ts`.

job ഒരിക്കലും `release/*`-ലേക്ക് പുഷ് ചെയ്യില്ല — ഒരു മനുഷ്യൻ PR മെർജ് ചെയ്യുന്നതിനാൽ, തെറ്റായ അളവ്
അവലോകനം ചെയ്യപ്പെടാതെ ഉൾപ്പെടാൻ കഴിയില്ല.

## അനുവദനീയ പട്ടിക നയം

മുൻകൂട്ടി നിലനിന്ന ലംഘനങ്ങളിൽ പരാജയപ്പെടാൻ കഴിയാത്ത എല്ലാ ഗേറ്റുകളും ഒരു മരവിപ്പിച്ച അനുവദനീയ പട്ടിക ഉപയോഗിക്കുന്നു
(ഉദാ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). നയം ഇതാണ്:

**മൂലകാരണമാണ് പരിഹരിക്കേണ്ടത്; ലംഘനം മുൻകൂട്ടി നിലനിന്നതും അതേ PR-ൽ
പരിഹരിക്കാൻ കഴിയാത്തതുമായ സാഹചര്യങ്ങളിൽ മാത്രം അനുവദനീയ പട്ടിക ഉപയോഗിക്കുക.**

അനുവദനീയ പട്ടികയിൽ ഒരു എൻട്രി ചേർക്കുമ്പോൾ:

1. വിശദീകരണത്തോടുകൂടിയ ഒരു കമന്റ് ഉൾപ്പെടുത്തുക.
2. ട്രാക്കിംഗ് ഇഷ്യൂ പരാമർശിക്കുക (ഉദാ., `// #3498 — Phase 2 feature, not yet implemented`).
3. ലംഘനം പരിഹരിക്കുന്ന അതേ PR-ൽ എൻട്രി നീക്കം ചെയ്യുക — സജീവമായ ഒരു ലംഘനം ഇനി
   അടിച്ചമർത്താത്ത പഴകിയ എൻട്രി തന്നെ ഒരു തകരാറാണ് (നടപ്പിലാക്കിയാൽ 6A.3 stale-enforcement
   ഒരു അനാഥ അനുവദനീയ പട്ടിക എൻട്രിയിലുള്ള ഗേറ്റിൽ പരാജയപ്പെടും).

ടെസ്റ്റുകൾ വേഗത്തിൽ വിജയിപ്പിക്കാനായി അനുവദനീയ പട്ടിക എൻട്രികൾ ചേർക്കരുത്. വളർന്നുകൊണ്ടിരിക്കുന്ന
അനുവദനീയ പട്ടികയോടുകൂടിയ പച്ച ഗേറ്റ് ഗുണനിലവാരത്തെക്കുറിച്ചുള്ള തെറ്റായ ധാരണയാണ്.

### നിങ്ങളുടെ PR-ൽ ഒരു ഗേറ്റ് പരാജയപ്പെടുമ്പോൾ

1. **ഗേറ്റിന്റെ ഔട്ട്പുട്ട് ശ്രദ്ധാപൂർവം വായിക്കുക** — നിയമം ലംഘിച്ച കൃത്യമായ ഫയലോ സിംബലോ അത് വ്യക്തമാക്കുന്നു.
2. **ലംഘനം പരിഹരിക്കുക** — മിക്ക ഗേറ്റുകളും കോഡ് ശരിയായ ഉടൻ വിജയിക്കുന്ന നിർണയാത്മക ഫയൽസിസ്റ്റം പരിശോധനകളാണ്.
3. **ലംഘനം മുൻകൂട്ടി നിലനിന്നതാണെങ്കിൽ** (അതായത്, നിങ്ങൾ അത് അവതരിപ്പിച്ചിട്ടില്ലെങ്കിലും ഗേറ്റ് ഇപ്പോൾ അത് ഉൾക്കൊള്ളുന്നുവെങ്കിൽ): വിശദീകരണ കമന്റും ട്രാക്കിംഗ് ഇഷ്യൂവും സഹിതം അനുവദനീയ പട്ടിക എൻട്രി ചേർക്കുക.
4. **ഗേറ്റ് ഒരു റാച്ചറ്റാണെങ്കിൽ** (കവറേജ്, ESLint മുന്നറിയിപ്പുകൾ, ഡ്യൂപ്ലിക്കേഷൻ, സങ്കീർണ്ണത):
   നിങ്ങളുടെ മാറ്റം മെട്രിക് മോശമാക്കി. അടിസ്ഥാന പ്രശ്നം പരിഹരിക്കുക, അല്ലെങ്കിൽ (അപൂർവമായി മാത്രം)
   മാറ്റം ഉദ്ദേശ്യപ്രകാരമുള്ളതും മെട്രിക് കുറയുന്നത് അംഗീകരിക്കാവുന്നതുമായെങ്കിൽ
   `npm run quality:ratchet -- --update` പ്രവർത്തിപ്പിക്കുക — എന്നാൽ PR വിവരണത്തിൽ കാരണം രേഖപ്പെടുത്തുക.
5. **ഉപദേശാത്മക ഗേറ്റുകൾ** (`continue-on-error: true`) വിവരാവശ്യത്തിനുള്ളവയാണ് — അവ
   ലയനം തടയില്ലെങ്കിലും CI സംഗ്രഹത്തിൽ പ്രത്യക്ഷപ്പെടും. എന്നിരുന്നാലും അവ പരിഹരിക്കുക.

## ഒരു പുതിയ ഗേറ്റ് ചേർക്കൽ

1. `scripts/check/check-<name>.mjs` (അല്ലെങ്കിൽ `.ts`) സൃഷ്ടിക്കുക. നയ ഗേറ്റുകൾ 0/1 നിലയിൽ പുറത്തുകടക്കുന്നു.
   റാച്ചെറ്റ്-രീതിയിലുള്ള ഗേറ്റുകൾ `collect-metrics.mjs` വഴി `quality-metrics.json`-ലേക്ക് ഒരു മെട്രിക് പുറപ്പെടുവിക്കുന്നു.
2. `package.json`-ലേക്ക് `"check:<name>": "node scripts/check/check-<name>.mjs"` ചേർക്കുക.
3. ഉചിതമായ ജോബിന് കീഴിൽ `.github/workflows/ci.yml`-ൽ അത് ബന്ധിപ്പിക്കുക
   (നയം → `lint` അല്ലെങ്കിൽ `docs-sync-strict`; റാച്ചെറ്റ് → `quality-gate`).
4. അതിന് ഒരു അനുവദനീയ പട്ടികയുണ്ടെങ്കിൽ, കാലഹരണപ്പെട്ട എൻട്രികൾ സ്വയമേവ കണ്ടെത്തുന്നതിനായി
   `scripts/check/lib/allowlist.mjs`-ൽ നിന്നുള്ള `reportStaleEntries()` പ്രയോഗിക്കുക.
5. ഗേറ്റിന്റെ കണ്ടെത്തൽ ലോജിക് ഉൾക്കൊള്ളുന്ന ഒരു ടെസ്റ്റ് `tests/unit/build/`-ൽ എഴുതുക.
6. ഈ പ്രമാണം അപ്ഡേറ്റ് ചെയ്യുക (പ്രസക്തമായ ജോബ് പട്ടികയിൽ ഒരു വരി ചേർക്കുക).

### മെർജ് / ഡ്യൂപ്ലിക്കേറ്റ് നീക്കം (യാന്ത്രികം, കുറഞ്ഞ അപകടസാധ്യത)

ഓരോ സ്ഥാനാർഥിയും 2026-06-17-ന് ലൈവ് ഗേറ്റ് നിലയ്ക്കെതിരെ പരിശോധിച്ച് സ്ഥിരീകരിച്ചു (വിശ്വസിക്കുക, പക്ഷേ പരിശോധിക്കുക);
നിരവധി "വ്യക്തമായ" മെർജുകൾ കടബാധ്യത മറച്ചുവെച്ചതായി തെളിഞ്ഞു, അതിനാൽ അവ **നേരിട്ട് മാറ്റിസ്ഥാപിക്കാവുന്നവയല്ല**.

- **`check:docs-sync` രണ്ട് തവണ പ്രവർത്തിക്കുന്നു** — `lint` ജോബിൽ സ്വതന്ത്രമായും വീണ്ടും `check:docs-all`-ന്റെ ഉള്ളിൽ (`docs-sync-strict`) കൂടാതെ husky pre-commit ഹുക്കിലും. ✅ **പൂർത്തിയായി** — സ്വതന്ത്രമായ `lint` ഇൻവൊക്കേഷൻ നീക്കം ചെയ്തു.
- **CVE സ്കാനിംഗ്** — ❌ **ശുദ്ധമായ മെർജ് അല്ല.** നിലവിലെ നയപ്രകാരം എല്ലാ അഞ്ച് ലോക്ക്ഫയലുകളിലുമുള്ള ഗുരുതര അഡ്വൈസറികളും അപൂർണ്ണമായ ഓഡിറ്റുകളും `audit:deps` ബ്ലോക്ക് ചെയ്യുന്നു, അതേസമയം ഉയർന്ന ഗൗരവമുള്ള അഡ്വൈസറികളെ മുന്നറിയിപ്പുകളായി റിപ്പോർട്ട് ചെയ്യുന്നു; `check:vuln-ratchet` (osv) ചെക്ക്-ഇൻ ചെയ്ത ബേസ്ലൈനുമായി താരതമ്യപ്പെടുത്തിയുള്ള _റിഗ്രഷൻ_ ഉണ്ടായാൽ മാത്രമേ പരാജയപ്പെടൂ, കൂടാതെ ആവശ്യമായപ്പോൾ അളവുകൾ ലഭ്യമല്ലെങ്കിൽ അത് നിരസിക്കുകയും ചെയ്യും. അർത്ഥതലങ്ങൾ വ്യത്യസ്തമാണ് — `audit:deps` നീക്കം ചെയ്താൽ സമ്പൂർണ്ണമായ ഗുരുതര-നില ഗേറ്റും സ്വതന്ത്ര പാക്കേജ് ഓഡിറ്റ് രസീതുകളും നഷ്ടപ്പെടും. രണ്ടും നിലനിർത്തുക.
- **സൈക്കിൾ കണ്ടെത്തൽ** — ✅ **പൂർത്തിയായി** (#15159 G-01/G-02). പഴയ വാചകം `check:cycles`-നെ "ഗ്രീൻ, ക്യൂറേറ്റ് ചെയ്ത" ഗേറ്റ് എന്ന് വിളിക്കുകയും `check:circular-deps` (dpdm) 91 സൈക്കിളുകൾ റിപ്പോർട്ട് ചെയ്തതിനാൽ അത് ബ്ലോക്കിംഗായി നിലനിർത്തണമെന്ന് ന്യായീകരിക്കുകയും ചെയ്തിരുന്നു. ആ ഗ്രീൻ **തെറ്റായ ഗ്രീൻ** ആയിരുന്നു: `check:cycles` 5 സബ്ഡയറക്ടറികൾ (450 ഫയലുകൾ) മാത്രം സ്കാൻ ചെയ്തു, സ്റ്റാറ്റിക് `import|export … from`-നോട് മാത്രം പൊരുത്തപ്പെട്ടു, എല്ലാ `@/` , `@omniroute/open-sse/` സ്പെസിഫയറുകളും ഒഴിവാക്കി; അതിനാൽ റിപ്പോസിറ്ററിയിൽ ആധിപത്യം പുലർത്തിയിരുന്ന ഡൈനാമിക്-ഇംപോർട്ട് + അലിയാസ് സൈക്കിളുകൾ കണ്ടെത്താൻ അതിന് കഴിഞ്ഞില്ല. പരിഹരിച്ചു: ഗേറ്റ് ഇപ്പോൾ `src` + `open-sse` (5023 ഫയലുകൾ) സഞ്ചരിക്കുകയും TypeScript AST-ൽ നിന്ന് സ്പെസിഫയറുകൾ ശേഖരിക്കുകയും ചെയ്യുന്നു (`import("…")` എണ്ണപ്പെടുന്നു, ടൈപ്പ്-പോസിഷനിലെ `typeof import("…")` എണ്ണപ്പെടുന്നില്ല), കൂടാതെ tsconfig `paths` പരിഹരിക്കുകയും ചെയ്യുന്നു. ഇത് 0 അല്ല, **14** സൈക്കിളുകൾ കണ്ടെത്തുന്നു. മുമ്പേ ഉണ്ടായിരുന്ന 14 സൈക്കിളുകൾ ഒരു ഗേറ്റ് PR-ൽ പരിഹരിക്കാനാകാത്തതിനാൽ, `check:cycles` ഇപ്പോൾ ഒരു **റാച്ചറ്റ്** ആണ് (`--ratchet`, `quality-baseline.json`-ലെ `metrics.cycles.value = 14` സീലിംഗ്, `direction: down`) — ഏത് _റിഗ്രഷനും_ ഇത് തടയുന്നു, എണ്ണം കുറയുക മാത്രമേ കഴിയൂ. CI `npm run check:cycles:ratchet` പ്രവർത്തിപ്പിക്കുന്നു. ബേൺ-ഡൗൺ **A-01**-നൊപ്പം നടക്കുന്നു. കൂടുതൽ വിശാലമായ രണ്ടാമത്തെ അഭിപ്രായമായി `check:circular-deps` (dpdm) ഉപദേശാത്മകമായി തുടരുന്നു.

#### `check-new-key-coverage` — പുതിയ കീ i18n ഗേറ്റ്

`check-ui-value-drift`-ന്റെ sibling ആണിത്. translations മാറ്റിവെച്ചിരിക്കെ ഒരു English value
**rewritten** ചെയ്തതിനെ അത് കണ്ടെത്തുന്നു; ചില locale-കൾക്ക് ലഭിക്കാതെ ഒരു English key
**added** ചെയ്തതിനെ ഇത് കണ്ടെത്തുന്നു.

`check-ui-keys-coverage`-ന് ഈ വിഭാഗം കണ്ടെത്താനാകില്ല: ഓരോ locale-ക്കും അത് ഒരു percentage floor
നിർബന്ധമാക്കുന്നു, ഏകദേശം 13,000 ലീഫുകളിൽ പതിനൊന്ന് കീകൾ ഇല്ലാതിരുന്നാലും coverage 99.9 % ആയി
തുടരും. ഓരോ ഭാഷയ്ക്കുമുള്ള ഒരു ശതമാനം കൊണ്ട് "ഈ feature വിവർത്തനം ചെയ്യാതെ shipped ചെയ്തു"
എന്ന് പ്രകടിപ്പിക്കാനാകില്ല — text ഇല്ലാത്ത ഒരു പുതിയ locale-ൽ മുഴുവൻ feature-വും എത്തിച്ചേരുകയും
നമ്പർ ഒരിക്കലും മാറാതിരിക്കുകയും ചെയ്യാം.
