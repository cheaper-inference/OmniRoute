> **ചുരുക്കത്തിൽ**: OmniRoute ഓരോ അഭ്യർത്ഥനയുടെയും ടോക്കൺ ഉപയോഗം ട്രാക്ക് ചെയ്യുന്നു, ചെലവ് കണക്കാക്കുന്നു, ഓരോ API കീയുടെയും ക്വാട്ട നടപ്പിലാക്കുന്നു, കൂടാതെ ഡാഷ്ബോർഡിൽ അനലിറ്റിക്സ് പ്രദർശിപ്പിക്കുന്നു. ഇതെല്ലാം എങ്ങനെ പ്രവർത്തിക്കുന്നുവെന്ന് ഈ ഗൈഡ് വിശദീകരിക്കുന്നു.

**സ്രോതസ്സുകൾ:**

- `open-sse/services/usage.ts` (~70KB) — പ്രധാന ഉപയോഗ ട്രാക്കിംഗ്
- `src/lib/usageAnalytics.ts` (~10KB) — ഡാഷ്ബോർഡിനായുള്ള സമാഹരണം
- `src/lib/db/quotaSnapshots.ts` — ചരിത്രപരമായ ക്വാട്ട ഡാറ്റ
- `src/lib/db/usage*.ts` — ഉപയോഗവുമായി ബന്ധപ്പെട്ട ഒന്നിലധികം DB മൊഡ്യൂളുകൾ

## അവലോകനം

OmniRoute-ലൂടെ കടന്നുപോകുന്ന ഓരോ അഭ്യർത്ഥനയും ഇനിപ്പറയുന്ന വിവരങ്ങൾ രേഖപ്പെടുത്തുന്ന ഒരു **ഉപയോഗ റെക്കോർഡ്** സൃഷ്ടിക്കുന്നു:

- **ഐഡന്റിറ്റി**: ഏത് API കീ, പ്രൊവൈഡർ, മോഡൽ, കോംബോ
- **ടോക്കണുകൾ**: പ്രോംപ്റ്റ് ടോക്കണുകൾ, കംപ്ലീഷൻ ടോക്കണുകൾ, കാഷ് ചെയ്ത ടോക്കണുകൾ, ആകെ
- **ചെലവ്**: USD തുക (വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് കണക്കാക്കിയത്)
- **സമയവിവരങ്ങൾ**: ലേറ്റൻസി, ആരംഭ/അവസാന ടൈംസ്റ്റാമ്പുകൾ
- **സ്റ്റാറ്റസ്**: വിജയം, പിശക്, നിരക്ക്-പരിമിതപ്പെടുത്തിയത് തുടങ്ങിയവ

ഈ റെക്കോർഡുകൾ **അനലിറ്റിക്സ്** ആയി സമാഹരിക്കുകയും, **ക്വാട്ട സ്നാപ്പ്ഷോട്ടുകൾ** ആയി സ്ഥിരമായി സംഭരിക്കുകയും, **ഓരോ കീയുടെയും ബജറ്റ് പരിധികൾ** നടപ്പിലാക്കാൻ ഉപയോഗിക്കുകയും ചെയ്യുന്നു.

```
അഭ്യർത്ഥന ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    അനലിറ്റിക്സ്  ക്വാട്ട  ബില്ലിംഗ്
                    (ഡാഷ്ബോർഡ്) (നടപ്പാക്കൽ) (എക്സ്പോർട്ട്)
```

## എന്തൊക്കെയാണ് രേഖപ്പെടുത്തുന്നത്

ഓരോ അഭ്യർത്ഥനയ്ക്കും `usage.ts` സേവനം ഒരു **ഉപയോഗ ഇവന്റ്** രേഖപ്പെടുത്തുന്നു:

| ഫീൽഡ്              | തരം     | ഉറവിടം                                                           |
| ------------------ | ------- | ---------------------------------------------------------------- |
| `id`               | string  | രേഖപ്പെടുത്തുമ്പോൾ സൃഷ്ടിക്കുന്ന UUID                            |
| `apiKeyId`         | string  | അഭ്യർത്ഥന ആരംഭിച്ച API കീ                                        |
| `provider`         | string  | ദാതാവിന്റെ ID (openai, anthropic, തുടങ്ങിയവ)                     |
| `model`            | string  | മോഡൽ ID (gpt-5, claude-opus-4-6, തുടങ്ങിയവ)                      |
| `comboId`          | string? | ഒരു കോംബോയിലൂടെ റൂട്ട് ചെയ്തിട്ടുണ്ടെങ്കിൽ അതിന്റെ ID            |
| `promptTokens`     | number  | അപ്‌സ്ട്രീം പ്രതികരണത്തിൽ നിന്ന്                                 |
| `completionTokens` | number  | അപ്‌സ്ട്രീം പ്രതികരണത്തിൽ നിന്ന്                                 |
| `cachedTokens`     | number  | കാഷ് ഹിറ്റ് ടോക്കണുകൾ (Anthropic പ്രോംപ്റ്റ് കാഷിംഗ്, തുടങ്ങിയവ) |
| `totalTokens`      | number  | പ്രോംപ്റ്റ് + കംപ്ലീഷൻ                                           |
| `costUsd`          | number  | വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് കണക്കാക്കുന്നത്                       |
| `latencyMs`        | number  | അഭ്യർത്ഥനയുടെ തുടക്കം മുതൽ അവസാനം വരെയുള്ള ദൈർഘ്യം               |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`       |
| `errorClass`       | string? | സ്റ്റാറ്റസ് success അല്ലെങ്കിൽ പിശകിന്റെ ക്ലാസ്                  |
| `timestamp`        | string  | ISO 8601 UTC                                                     |
| `metadata`         | object  | പ്ലഗിൻ ചേർക്കുന്ന ഇഷ്ടാനുസൃത ഡാറ്റ                               |

### ടോക്കണുകൾ എവിടെ നിന്ന് വരുന്നു

അപ്‌സ്ട്രീം ദാതാവിന്റെ പ്രതികരണത്തിൽ നിന്ന് **റെസ്‌പോൺസ് ഹാൻഡ്‌ലറിൽ** ടോക്കണുകൾ വേർതിരിച്ചെടുക്കുന്നു:

```ts
// open-sse/handlers/chatCore.ts എന്നതിൽ നിന്ന്
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

ഉപയോഗവിവരങ്ങൾ തിരികെ നൽകാത്ത ദാതാക്കൾക്കായി (ചില വെബ്-കുക്കി ദാതാക്കൾ), `~4 chars per token` എന്ന ഏകദേശ നിയമം ഉപയോഗിച്ച് OmniRoute ടോക്കണുകൾ **കണക്കാക്കുന്നു** (`open-sse/services/autoCombo/pipelineRouter.ts` കാണുക).

### കാഷ് ചെയ്ത ടോക്കണുകൾ

OmniRoute `cached_tokens` എന്നത് `prompt_tokens` എന്നതിൽ നിന്ന് വേർതിരിച്ച് ട്രാക്ക് ചെയ്യുന്നു, കാരണം:

- Anthropic പ്രോംപ്റ്റ് കാഷിംഗ്, കാഷ് ചെയ്ത ടോക്കണുകൾക്ക് കുറഞ്ഞ നിരക്കാണ് ഈടാക്കുന്നത് (സാധാരണ നിരക്കിന്റെ 10%)
- ചില ദാതാക്കൾ വ്യത്യസ്ത നിരക്ക് ബാധകമാക്കേണ്ട `cache_read_input_tokens` തിരികെ നൽകുന്നു
- അനലിറ്റിക്സിന് **കാഷ് ഹിറ്റ് നിരക്ക്** = `cached_tokens / prompt_tokens` കാണിക്കാനാകും

### കാഷ്-റൈറ്റ് ടിയർ ഡയഗ്നോസ്റ്റിക്സ്

അനലിറ്റിക്സ് ഡാഷ്‌ബോർഡിലെ പ്രോംപ്റ്റ്-കാഷ് ഹെൽത്ത് പാനൽ, ദാതാവ് റിപ്പോർട്ട് ചെയ്യുന്ന
5-മിനിറ്റ്, 1-മണിക്കൂർ കാഷ് റൈറ്റുകൾ വേർതിരിച്ചുകാണിക്കുന്നു. Anthropic-ന്റെ
`usage.cache_creation.ephemeral_5m_input_tokens`,
`usage.cache_creation.ephemeral_1h_input_tokens` എന്നിവ സ്ട്രീമിംഗ്,
നോൺ-സ്ട്രീമിംഗ് ഉപയോഗവിവര പരിവർത്തനങ്ങളിലുടനീളം നിലനിർത്തുകയും കോൾ-ലോഗ് സംഗ്രഹങ്ങളോടൊപ്പം സൂക്ഷിക്കുകയും ചെയ്യുന്നു. സംയോജിത
കാഷ്-റൈറ്റ് ആകെ തുക ആ വിഭാഗങ്ങളിലേക്ക് രണ്ടാമതും ചേർക്കുന്നില്ല.

പഴയ രേഖകൾ ഉൾപ്പെടെ, സംയോജിത റൈറ്റ് കൗണ്ടർ മാത്രമുള്ള കോളുകളുടെ ടിയർ
അജ്ഞാതമായിരിക്കും. ഭാഗികമായ വിഭജനത്തിൽ, നിയോഗിക്കാത്ത ശേഷിപ്പ് അജ്ഞാതമായി നിലനിർത്തുന്നു; അസാധുവായതോ
പരസ്പരവിരുദ്ധമായതോ ആയ കൗണ്ടറുകൾക്ക് നിശ്ശബ്ദമായി TTL നിയോഗിക്കുന്നതിന് പകരം അവ അടയാളപ്പെടുത്തുന്നു. അഭ്യർത്ഥനയുടെ ഭാഗത്തുള്ള
TTL മാർക്കറുകൾ ബിൽ ചെയ്ത ടിയറിന്റെ തെളിവല്ല.

പാനലിന്റെ API-തുല്യ റൈറ്റ് എസ്റ്റിമേറ്റ് റിപ്പോർട്ട് ചെയ്തതും വില നിശ്ചയിച്ചിട്ടുള്ളതുമായ ടിയറുകൾ മാത്രം ഉൾക്കൊള്ളുന്നു,
മുഴുവൻ അഭ്യർത്ഥനയെയും അല്ല. നേറ്റീവ് Claude/Anthropic മോഡൽ വിലനിർണ്ണയത്തിന്, 5-മിനിറ്റ് റൈറ്റുകൾക്ക്
ഇൻപുട്ട് നിരക്കിന്റെ 1.25 മടങ്ങും 1-മണിക്കൂർ റൈറ്റുകൾക്ക് ഇൻപുട്ട് നിരക്കിന്റെ ഇരട്ടിയും ഇത് ഉപയോഗിക്കുന്നു. വിലനിർണ്ണയവിവരം
ഇല്ലെങ്കിൽ അത് ലഭ്യമല്ല എന്നാണ്, പൂജ്യം എന്നല്ല. ഓരോ പുതിയ കോളും ലോഗ് ചെയ്യുമ്പോൾ വിലകൾ രേഖപ്പെടുത്തുന്നു;
ചരിത്രരേഖകൾക്ക് വീണ്ടും വില കണക്കാക്കുന്നില്ല. അതിനാൽ സബ്‌സ്‌ക്രിപ്‌ഷൻ അക്കൗണ്ടുകൾക്ക്,
ആ തുക പണച്ചെലവായോ സബ്‌സ്‌ക്രിപ്‌ഷൻ ക്വോട്ടയായോ ഈടാക്കപ്പെടാതെ തന്നെ
ഒരു API-തുല്യ എസ്റ്റിമേറ്റ് ഉണ്ടാകാം. നിലവിലുള്ള ക്വോട്ട, ബജറ്റ്, ദാതാവിന്റെ കൃത്യമായ ചെലവ് കണക്കുകൂട്ടലുകൾ എന്നിവയ്ക്ക് മാറ്റമില്ല.

ഈ ഡയഗ്നോസ്റ്റിക്സ് നിലവിലുള്ള പരിധിനിശ്ചയിച്ച കാഷ്-ഹെൽത്ത് സംഗ്രഹവും കോൾ-ലോഗ്
നിലനിർത്തലും ഉപയോഗിക്കുന്നു. അവ അഭ്യർത്ഥനയുടെ ഡിഫോൾട്ട് TTL മൂല്യങ്ങളോ റൂട്ടിംഗോ അക്കൗണ്ട് തിരഞ്ഞെടുപ്പോ മാറ്റുന്നില്ല.
ദാതാവിലേക്ക് അയയ്ക്കുന്ന ഘട്ടത്തിൽ, ക്ലയന്റ് അഭ്യർത്ഥിച്ച TTL-ഉം യഥാർത്ഥത്തിൽ പുറത്തേക്ക് അയയ്ക്കുന്ന TTL-ഉം
രേഖപ്പെടുത്തുന്നത് പിന്നത്തേക്ക് മാറ്റിവെച്ചിരിക്കുന്നു; ഈ പാനൽ റിപ്പോർട്ട് ചെയ്യുന്നത് രസീതിലെ ടിയറുകളാണ്, യഥാർത്ഥത്തിൽ പുറത്തേക്ക് അയയ്ക്കുന്ന TTL അല്ല.

നടപ്പാക്കൽ: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, കൂടാതെ `open-sse/utils/cacheWriteUsage.ts`.

## ചെലവ് കണക്കാക്കൽ

LiteLLM-ൽ നിന്ന് സമന്വയിപ്പിച്ച **വിലനിർണ്ണയ ഡാറ്റ** (`src/lib/pricingSync.ts`) ഉപയോഗിച്ചാണ് ചെലവുകൾ കണക്കാക്കുന്നത്:

| മോഡൽ              | ഇൻപുട്ട് $/1M | ഔട്ട്പുട്ട് $/1M | കാഷ് ചെയ്തത് $/1M |
| ----------------- | ------------- | ---------------- | ----------------- |
| gpt-5             | $2.50         | $10.00           | —                 |
| claude-opus-4-6   | $15.00        | $75.00           | $1.50             |
| claude-sonnet-4-5 | $3.00         | $15.00           | $0.30             |
| gemini-2.5-pro    | $1.25         | $10.00           | —                 |

ചെലവ് കണക്കാക്കുന്നതിനുള്ള സൂത്രവാക്യം (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **പ്രോംപ്റ്റിൽ നിന്ന് കാഷ് ചെയ്ത ഭാഗം കുറയ്ക്കുന്നത് എന്തുകൊണ്ട്?** കാഷ് ചെയ്ത ഭാഗത്തിന് പ്രത്യേകം വില നിശ്ചയിച്ചിരിക്കുന്നതിനാൽ, മുഴുവൻ പ്രോംപ്റ്റിനും ഇൻപുട്ട് വില ഈടാക്കുന്നത് ചെലവ് അധികമായി കണക്കാക്കാൻ ഇടയാക്കും.

### വിലനിർണ്ണയ സമന്വയം

ബിൽറ്റ്-ഇൻ cron ടാസ്ക് പ്രവർത്തനക്ഷമമാക്കുന്ന `/api/pricing/sync` എൻഡ്പോയിന്റ് വഴി LiteLLM-ൽ നിന്ന് വിലനിർണ്ണയ ഡാറ്റ സ്വയമേവ സമന്വയിപ്പിക്കുന്നു (ഉപയോക്താവിന് ലഭ്യമായ env var വഴിയല്ല):

```bash
# മാനുവൽ ട്രിഗർ
curl -X POST http://localhost:20128/api/pricing/sync
```

വിലനിർണ്ണയ ഡാറ്റയില്ലാത്ത മോഡലുകൾക്കായി, ആന്തരിക ശരാശരി നിരക്കുകൾ ഉപയോഗിച്ച് (LiteLLM-ന്റെ വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് ലഭിച്ചത്) OmniRoute **ചെലവ് കണക്കാക്കുന്നു**.

## തീയതി പരിധി അടിസ്ഥാനത്തിലുള്ള സമാഹരണം

`usageAnalytics.ts` മൊഡ്യൂൾ അസംസ്കൃത ഉപയോഗ ഡാറ്റയിൽ നിന്ന് ഡാഷ്ബോർഡ് വിജറ്റുകൾ കണക്കാക്കുന്നു. ഇത് 7 സമയ പരിധികളെ പിന്തുണയ്ക്കുന്നു:

| പരിധി    | കാലയളവ്                               | ഉപയോഗ സാഹചര്യം                                  |
| -------- | ------------------------------------- | ----------------------------------------------- |
| `1d`     | കഴിഞ്ഞ 24 മണിക്കൂർ                    | മണിക്കൂർ അടിസ്ഥാനത്തിലുള്ള ചെലവ് വർധന കണ്ടെത്തൽ |
| `7d`     | കഴിഞ്ഞ 7 ദിവസം                        | പ്രതിവാര അവലോകനം                                |
| `30d`    | കഴിഞ്ഞ 30 ദിവസം                       | പ്രതിമാസ ബില്ലിംഗ്                              |
| `90d`    | കഴിഞ്ഞ 90 ദിവസം                       | ത്രൈമാസ വിശകലനം                                 |
| `ytd`    | നടപ്പുവർഷം ജനുവരി 1 മുതൽ              | വാർഷിക ബജറ്റ് നിരീക്ഷണം                         |
| `all`    | മുഴുവൻ കാലയളവും                       | ആകെ കാലയളവിലെ സ്ഥിതിവിവരക്കണക്കുകൾ              |
| `custom` | ഉപയോക്താവ് നിർവചിക്കുന്ന ആരംഭം/അവസാനം | ഓഡിറ്റുകൾ, ആവശ്യാനുസൃത ക്വറികൾ                  |

### കണക്കാക്കുന്ന ഡാഷ്ബോർഡ് വിജറ്റുകൾ

ഏത് തീയതി പരിധിക്കും, അനലിറ്റിക്സ് ലെയർ ഇനിപ്പറയുന്നവ കണക്കാക്കുന്നു:

| വിജറ്റ്                       | വിവരണം                                                                   |
| ----------------------------- | ------------------------------------------------------------------------ |
| **സംഗ്രഹ കാർഡുകൾ**            | ആകെ അഭ്യർത്ഥനകൾ, ആകെ ചെലവ്, ആകെ ടോക്കണുകൾ, വിജയ നിരക്ക്                  |
| **പ്രതിദിന പ്രവണതാ ചാർട്ട്**  | പ്രതിദിന ചെലവ് + ടോക്കണുകൾ, മോഡൽ അനുസരിച്ച് അടുക്കിയത്                   |
| **പ്രവർത്തന ഹീറ്റ്മാപ്പ്**    | ദിവസത്തിലെ മണിക്കൂർ × ആഴ്ചയിലെ ദിവസം ഗ്രിഡ്, നിറം = അഭ്യർത്ഥനകളുടെ എണ്ണം |
| **മോഡൽ തിരിച്ചുള്ള വിഭജനം**   | മോഡൽ അനുസരിച്ചുള്ള ചെലവിന്റെ പൈ ചാർട്ട്                                  |
| **ദാതാവ് തിരിച്ചുള്ള വിഭജനം** | ദാതാവ് അനുസരിച്ചുള്ള അഭ്യർത്ഥനകളുടെ ബാർ ചാർട്ട്                          |
| **മുൻനിര API കീകൾ**           | ചെലവ് അനുസരിച്ചുള്ള മുൻനിര 10 കീകളുടെ പട്ടിക                             |
| **പിശക് വിശകലനം**             | കാലക്രമത്തിലുള്ള പിശക് നിരക്ക്, പ്രധാന പിശക് വിഭാഗങ്ങൾ                   |

### പ്രോഗ്രാമിലൂടെയുള്ള ആക്സസ്

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // ഉപയോഗ ചരിത്ര രേഖകൾ
  "7d",                 // സമയ പരിധി: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // ദാതാവിന്റെ കണക്ഷൻ മാപ്പ് (connectionId → അക്കൗണ്ട് പേര്)
  {
    startDate: "2025-01-01",  // ഐച്ഛികം: "custom" പരിധിക്ക്
    endDate: "2025-06-01",   // ഐച്ഛികം: "custom" പരിധിക്ക്
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (സെന്റുകൾ)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ക്വോട്ട നടപ്പാക്കൽ

ഓരോ API കീയ്ക്കുമുള്ള ക്വോട്ട രണ്ട് ഇടങ്ങളിൽ നടപ്പാക്കുന്നു:

1. **മൃദു പരിധി** (`quotaWarnAt`): ഉപയോഗം നിശ്ചിത പരിധി കവിയുമ്പോൾ ഡാഷ്ബോർഡിൽ മുന്നറിയിപ്പ്
2. **കർശന പരിധി** (`quotaLimit`): പരിധി കവിഞ്ഞാൽ HTTP 429 ഉപയോഗിച്ച് അഭ്യർത്ഥന നിരസിക്കുന്നു

### കോൺഫിഗറേഷൻ

```ts
// ഓരോ API കീയ്ക്കും
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — മുന്നറിയിപ്പ് കാണിക്കുക
  quotaLimit: 10_00,    // $10.00 — കർശനമായി നിർത്തുക
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### നടപ്പാക്കൽ പ്രവാഹം

```
അഭ്യർത്ഥന ──▶ quotaCheck()
              │
              ├── പരിധിക്കുള്ളിലാണോ?  ──▶ അനുവദിക്കുക
              │
              └── പരിധി കവിഞ്ഞോ?  ──▶ 429 അഭ്യർത്ഥനകൾ വളരെ കൂടുതലാണ്
                                   Retry-After ഹെഡറിനൊപ്പം
```

### ക്വോട്ട സ്നാപ്പ്ഷോട്ടുകൾ

പ്രവണതാ വിശകലനത്തിനായി `quotaSnapshots` പട്ടിക **ക്വോട്ടയുടെ മുൻകാല നില** സംഭരിക്കുന്നു:

| ഫീൽഡ് | വിവരണം |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | നിരീക്ഷിക്കുന്ന കീ |
| `window` | "ദിവസം" | "ആഴ്ച" | "മാസം" |
| `used` | ഈ കാലയളവിൽ ഉപയോഗിച്ച ചെലവ് (സെന്റുകൾ) |
| `limit` | പരിധി (സെന്റുകൾ) |
| `resetAt` | കാലയളവ് പുനഃസജ്ജമാകുന്ന സമയം |
| `createdAt` | സ്നാപ്പ്ഷോട്ട് എടുത്ത സമയം |

ചെലവ് > 0 ആയ **ഓരോ അഭ്യർത്ഥനയിലും** സ്നാപ്പ്ഷോട്ടുകൾ എടുക്കുന്നു. അവ ഇനിപ്പറയുന്ന ആവശ്യങ്ങൾക്ക് ഉപയോഗിക്കുന്നു:

- ഡാഷ്ബോർഡിൽ ക്വോട്ട പുരോഗതി ബാർ പ്രദർശിപ്പിക്കുക
- 30 ദിവസത്തെ ക്വോട്ട പ്രവണതാ ചാർട്ടുകൾ കാണിക്കുക
- ഉപയോഗം പരിധിയോട് അടുക്കുമ്പോൾ അലേർട്ടുകൾ പ്രവർത്തനക്ഷമമാക്കുക

ഉപയോഗ ഡാറ്റ ലഭ്യമാകുന്നത് ഡാഷ്ബോർഡ് അല്ലെങ്കിൽ MCP ടൂളുകൾ വഴിയാണ്, നേരിട്ടുള്ള REST എക്സ്പോർട്ട് എൻഡ്പോയിന്റുകൾ വഴിയല്ല. ലഭ്യമായ വിശകലനങ്ങൾ:

- **`/api/usage/analytics`** — സമാഹരിച്ച ഉപയോഗ മെട്രിക്കുകൾ (മോഡൽ, ദാതാവ്, കീ എന്നിവ അനുസരിച്ച് ഗ്രൂപ്പുചെയ്യുക)
- **`/api/usage/quota`** — ഓരോ API കീയുടെയും നിലവിലെ ക്വോട്ട നില
- **`/api/usage/history`** — അഭ്യർത്ഥനാ ചരിത്ര ലോഗുകൾ

## നിലനിർത്തലും ശുചീകരണവും

ഓരോ അഭ്യർത്ഥനയ്ക്കും ഉപയോഗ ഡാറ്റ ~1-10KB വീതം വർധിക്കുന്നു. വലിയ തോതിൽ ഇത് ഗണ്യമായേക്കാം.

### നിലനിർത്തൽ ക്രമീകരണങ്ങൾ

ഉപയോഗ ചരിത്രം നിലനിർത്തുന്നത് UI-യിലെ ഡാറ്റാബേസ് ക്രമീകരണങ്ങൾ വഴിയോ `/api/settings/database` വഴിയോ ക്രമീകരിക്കാം.

സ്ഥിരസ്ഥിതിയായി, ഉപയോഗ ചരിത്രം **90 ദിവസം** നിലനിർത്തുന്നു.

### ശുചീകരണം

പഴയ രേഖകൾ `src/lib/db/cleanup.ts` വഴി നീക്കംചെയ്യുന്നു:

- പശ്ചാത്തല ക്രോൺ പ്രക്രിയയാൽ പ്രവർത്തനക്ഷമമാക്കുന്നു
- ക്രമീകരിച്ച `usageHistory` നിലനിർത്തൽ കാലയളവിനേക്കാൾ പഴക്കമുള്ള രേഖകൾ `usage_history`-യിൽ നിന്ന് ഇല്ലാതാക്കുന്നു

### സംഭരണത്തിന്റെ ഏകദേശ കണക്ക്

| അഭ്യർത്ഥനാ നിരക്ക്        | 30 ദിവസത്തെ സംഭരണം | 90 ദിവസത്തെ സംഭരണം |
| ------------------------- | ------------------ | ------------------ |
| 100 അഭ്യർത്ഥനകൾ/ദിവസം     | ~3MB               | ~9MB               |
| 1,000 അഭ്യർത്ഥനകൾ/ദിവസം   | ~30MB              | ~90MB              |
| 10,000 അഭ്യർത്ഥനകൾ/ദിവസം  | ~300MB             | ~900MB             |
| 100,000 അഭ്യർത്ഥനകൾ/ദിവസം | ~3GB               | ~9GB               |

വളരെ ഉയർന്ന ട്രാഫിക്കിന്, ഇവ പരിഗണിക്കുക:

- ഡാറ്റാബേസ് ക്രമീകരണങ്ങൾ വഴി നിലനിർത്തൽ കാലയളവ് കുറയ്ക്കുക
- അസംസ്കൃത രേഖകൾക്ക് പകരം `aggregated_metrics` ഉപയോഗിക്കുക (വിശകലനത്തിന് മാത്രം)

## ചെലവ് കുറയ്ക്കാനുള്ള നുറുങ്ങുകൾ

### 1. ശരിയായ മോഡൽ ഉപയോഗിക്കുക

```bash
# പെട്ടെന്നുള്ള ഉത്തരം — ചെലവ് കുറഞ്ഞതും വേഗതയേറിയതും ഉപയോഗിക്കുക
curl -d '{"model":"auto/fast","messages":[...]}'

# സങ്കീർണ്ണമായ ജോലി — ഗുണനിലവാരത്തിന് മുൻഗണന നൽകുക
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. കാഷിംഗ് പ്രവർത്തനക്ഷമമാക്കുക

Anthropic പ്രോംപ്റ്റ് കാഷിംഗ് **ആവർത്തിക്കുന്ന സന്ദർഭത്തിൽ 90% ചെലവ് ലാഭിക്കുന്നു**:

```ts
// കാഷിംഗ് സ്വയമേവ നടക്കുന്നു — അതേ വലിയ സിസ്റ്റം പ്രോംപ്റ്റ് ഉൾപ്പെടുത്തിയാൽ മതി
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // സ്വയമേവ കാഷ് ചെയ്യപ്പെടും
  messages: [{ role: "user", content: "..." }],
});
```

### 3. കംപ്രഷൻ ഉപയോഗിക്കുക

RTK + Caveman കംപ്രഷൻ **ടൂളുകൾ കൂടുതലായി ഉപയോഗിക്കുന്ന സെഷനുകളിൽ 15-95% ചെലവ് ലാഭിക്കുന്നു**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. ഓരോ കീയ്ക്കും ക്വോട്ട നിശ്ചയിക്കുക

ചെലവ് നിയന്ത്രണാതീതമാകുന്നത് തടയാൻ എല്ലായ്പ്പോഴും `quotaLimit` സജ്ജമാക്കുക:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // പ്രതിമാസം $10 പരിധി
```

### 5. ഏറ്റവും കൂടുതൽ ഉപയോഗിക്കുന്നവ പരിശോധിക്കുക

API കീ അനുസരിച്ച് ഗ്രൂപ്പുചെയ്യാനും ചെലവ് അനുസരിച്ച് ക്രമീകരിക്കാനും ഡാഷ്‌ബോർഡ് അല്ലെങ്കിൽ **`/api/usage/analytics`** ഉപയോഗിക്കുക:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## പ്രശ്നപരിഹാരം

### "ചെലവ് പ്രതീക്ഷിച്ചതിലും കൂടുതലാണ്"

1. **`/api/usage/analytics?groupBy=model`** പരിശോധിക്കുക — ചെലവേറിയ മോഡൽ കണ്ടെത്തുക
2. **`/api/usage/analytics?groupBy=apiKey`** പരിശോധിക്കുക — കൂടുതൽ ഉപയോഗിക്കുന്ന കീ കണ്ടെത്തുക
3. വിലനിർണ്ണയ ഡാറ്റ കാലികമാണെന്ന് ഉറപ്പാക്കുക: `POST /api/pricing/sync`

### "റെക്കോർഡുകൾ കാണാനില്ല"

- ഡാഷ്‌ബോർഡ് → ഡാറ്റാബേസ് → ക്ലീനപ്പ് എന്നതിൽ DB നിലനിർത്തൽ ക്രമീകരണങ്ങൾ പരിശോധിക്കുക — നിശ്ചിത ഇടവേളകളിൽ പ്രവർത്തിക്കുന്ന ക്ലീനപ്പ് ടാസ്ക് പഴയ റെക്കോർഡുകൾ നീക്കംചെയ്യുന്നു (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts` എന്നതിൽ പിശകുകളുണ്ടോ എന്ന് പരിശോധിക്കുക — DB-യിൽ എഴുതുന്നതിലെ പരാജയങ്ങൾ ലോഗ് ചെയ്യപ്പെടുന്നു, പക്ഷേ പുറത്തു കാണിക്കപ്പെടുന്നില്ല
- അഭ്യർത്ഥന യഥാർത്ഥത്തിൽ `chatCore`-ൽ എത്തിയെന്ന് ഉറപ്പാക്കുക — കോംബോ റൂട്ടിംഗ് പരിശോധിക്കുക

### "ക്വോട്ട നടപ്പാക്കപ്പെടുന്നില്ല"

- കീയുടെ `quotaLimit` ക്രമീകരണം പരിശോധിക്കുക
- `quotaWindow` ശരിയായി സജ്ജമാക്കിയിട്ടുണ്ടെന്ന് ഉറപ്പാക്കുക
- `quotaSnapshots` റെക്കോർഡുകൾ ഉണ്ടോ എന്ന് നോക്കുക — ഓരോ അഭ്യർത്ഥനയിലും അവ സൃഷ്ടിക്കപ്പെടണം
