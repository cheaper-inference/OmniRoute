## പെട്ടെന്നുള്ള ഓട്ടം

> **ഒരു കമാൻഡിൽ സ്വയം ഹോസ്റ്റ് ചെയ്യണോ?** [സെൽഫ്-ഹോസ്റ്റ് ഗൈഡ്](../getting-started/SELF_HOST_GUIDE.md) — `docker compose -f docker-compose.selfhost.yml up -d` കാണുക (പ്രസിദ്ധീകരിച്ച ചിത്രം + Redis, ലൂപ്പ്ബാക്ക്-മാത്രം, പ്രൊഫൈൽ ചോയ്സ് ഇല്ല). മറ്റെവിടെയെങ്കിലും Redis പ്രവർത്തിപ്പിക്കുന്ന ഉപയോക്താക്കൾക്കുള്ള സിംഗിൾ-കണ്ടെയ്നർ പാതയാണ് ചുവടെയുള്ള ക്വിക്ക് റൺ.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  cheaperinference/omniroute:latest
```

## പരിസ്ഥിതി ഫയലിനൊപ്പം

```bash
# Copy and edit .env first

  --stop-timeout 40 \

```

## Docker Compose

```bash
# അടിസ്ഥാന പ്രൊഫൈൽ (CLI ടൂളുകളില്ല)
docker compose --profile base up -d

# CLI പ്രൊഫൈൽ (Claude Code, Codex, OpenClaw എന്നിവ ബിൽറ്റ്-ഇൻ)
docker compose --profile cli up -d

# ഹോസ്റ്റ് പ്രൊഫൈൽ (പ്രധാനമായും Linux-നായി; ഹോസ്റ്റ് CLI ബൈനറികളെ റീഡ്-ഒൺലിയായി മൗണ്ട് ചെയ്യുന്നു)
docker compose --profile host up -d

# വെബ് പ്രൊഫൈൽ (വെബ്-സെഷൻ പ്രൊവൈഡർമാർക്കായി Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI സൈഡ്കാർ സംയോജിപ്പിക്കുക
docker compose --profile cli --profile cliproxyapi up -d
```

## ലഭ്യമായ പ്രൊഫൈലുകൾ

പ്രധാന വിന്യാസ രീതികൾക്കായുള്ള Compose പ്രൊഫൈലുകൾ OmniRoute-നൊപ്പം ലഭ്യമാണ്. നിങ്ങളുടെ പരിസ്ഥിതിക്ക് യോജിക്കുന്ന ഒന്ന് തിരഞ്ഞെടുക്കുക.

| പ്രൊഫൈൽ            | സേവനം            | എപ്പോൾ ഉപയോഗിക്കണം                                                                                                                                                 | കമാൻഡ്                                       |
| ------------------ | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| `base` (ഡിഫോൾട്ട്) | `omniroute-base` | ഹെഡ്ലെസ് സെർവർ / മിനിമൽ റൺടൈം; പ്രൊവൈഡർ CLI-കൾ ഉൾപ്പെടുത്തിയിട്ടില്ല                                                                                               | `docker compose --profile base up -d`        |
| `cli`              | `omniroute-cli`  | `omniroute providers/setup/doctor`, ഉൾപ്പെടുത്തിയ CLI-കൾ (Codex, Claude Code, Droid, OpenClaw) എന്നിവ വിളിക്കുന്ന ഏജന്റിക് വർക്ക്ഫ്ലോകൾ                            | `docker compose --profile cli up -d`         |
| `host`             | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` മുതലായവ റീഡ്-ഒൺലിയായി മൗണ്ട് ചെയ്തുകൊണ്ട് ഹോസ്റ്റ് CLI-കളിലേക്ക് `network_mode` പോലുള്ള ആക്സസ് ആവശ്യമുള്ള Linux ഹോസ്റ്റുകൾ | `docker compose --profile host up -d`        |
| `cliproxyapi`      | `cliproxyapi`    | അപ്സ്ട്രീം CLI പ്രോക്സിയിങ്ങിനായി `8317` പോർട്ടിൽ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) സൈഡ്കാർ പ്രവർത്തിപ്പിക്കുക                           | `docker compose --profile cliproxyapi up -d` |
| `web`              | `omniroute-web`  | ബ്രൗസർ ആവശ്യമുള്ള വെബ്-സെഷൻ പ്രൊവൈഡർമാർ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ബിൽഡ് ചെയ്യുന്നു; Chromium ഉൾപ്പെടുത്തിയിട്ടുണ്ട്)           | `docker compose --profile web up -d`         |

> ഒന്നിലധികം പ്രൊഫൈലുകൾ സംയോജിപ്പിക്കാം: `docker compose --profile cli --profile cliproxyapi up -d`.

## OmniRoute Docker-ൽ പ്രവർത്തിക്കുമ്പോൾ ഹോസ്റ്റ് CLI ടൂളുകൾ ക്രമീകരിക്കൽ

`omniroute setup-codex`, `setup-claude`, `config set <tool>` എന്നിവയും ഡാഷ്ബോർഡിലെ
**കോൺഫിഗറേഷൻ സംരക്ഷിക്കുക** ബട്ടണും `~/.codex/*.config.toml` പോലുള്ള ഫയലുകളിലാണ് എഴുതുന്നത്. CLI യഥാർത്ഥത്തിൽ പ്രവർത്തിക്കുന്ന മെഷീനിൽ മാത്രമാണ് ആ പാതകൾക്ക് പ്രസക്തിയുള്ളത്. അവ കണ്ടെയ്നറിനുള്ളിൽ പ്രവർത്തിപ്പിച്ചാൽ, എഴുത്ത് കണ്ടെയ്നറിന്റെ സ്വന്തം ഹോമിലാണ് (`/home/node` —
ഇമേജ് `USER node` ആയി പ്രവർത്തിക്കുന്നു) നടക്കുക. ഒരു ഹോസ്റ്റ് CLI-യും അത് വായിക്കുകയില്ല; കൂടാതെ കണ്ടെയ്നർ പുനഃസൃഷ്ടിക്കുന്ന നിമിഷം തന്നെ അത് ഉപേക്ഷിക്കപ്പെടുകയും ചെയ്യും.

OmniRoute ഇത് കണ്ടെത്തുകയും നിങ്ങൾക്ക് ഉപയോഗിക്കാനാകാത്ത ഒരു വിജയം റിപ്പോർട്ട് ചെയ്യുന്നതിന് പകരം നിർദ്ദേശങ്ങളോടെ എഴുത്ത് നിരസിക്കുകയും ചെയ്യുന്നു: CLI `2` എന്ന കോഡോടെ പുറത്തുകടക്കും, API `containerEphemeralTarget: true` സഹിതം `422` മറുപടി നൽകും.

### ശുപാർശ ചെയ്യുന്നത്: CLI ഹോസ്റ്റിലും OmniRoute Docker-ലും പ്രവർത്തിപ്പിക്കുക

കണ്ടെയ്നർ API നൽകുന്നു; CLI നിങ്ങളുടെ ഹോസ്റ്റ് ടൂളുകൾ ക്രമീകരിക്കുന്നു.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI-യെ കണ്ടെയ്നറിലേക്ക് ചൂണ്ടിക്കാണിക്കുക
omniroute setup-codex                      # നിങ്ങളുടെ ഹോസ്റ്റിലെ യഥാർത്ഥ ~/.codex-ലേക്ക് എഴുതുന്നു
```

Codex, Claude Code, Cursor അല്ലെങ്കിൽ സമാനമായവ നിങ്ങളുടെ ലാപ്ടോപ്പിൽ പ്രവർത്തിക്കുമ്പോൾ ഇതാണ് ശരിയായ തിരഞ്ഞെടുപ്പ് — സാധാരണയായി ഉപയോഗിക്കുന്ന സജ്ജീകരണവും ഇതുതന്നെയാണ്.

### മറ്റൊരു മാർഗം: ഹോസ്റ്റ് കോൺഫിഗറേഷൻ ഡയറക്ടറികൾ bind-mount ചെയ്യുക (`host` പ്രൊഫൈൽ)

കണ്ടെയ്നർ തന്നെ നിങ്ങളുടെ ഹോസ്റ്റ് കോൺഫിഗറേഷനിൽ എഴുതണമെന്ന് നിങ്ങൾ ആഗ്രഹിക്കുന്നുവെങ്കിൽ, ഡയറക്ടറികൾ mount ചെയ്യുകയും mount root-ലേക്ക് `CLI_CONFIG_HOME` ചൂണ്ടിക്കാണിക്കുകയും ചെയ്യുക. `host` പ്രൊഫൈൽ ഇത് ഇതിനകം ചെയ്യുന്നു:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

ഒരു bind mount ആണ് പാതയെ വിശ്വസനീയമാക്കുന്നത്: OmniRoute
`/proc/self/mountinfo` വായിക്കുകയും mounted പാതകളിലേക്ക് എഴുതാൻ അനുവദിക്കുകയും ചെയ്യുന്നു (കൂടാതെ ചൈൽഡ് ഡയറക്ടറികൾ mount ചെയ്തിട്ടുള്ള ഡയറക്ടറികളിലേക്കും അനുവദിക്കുന്നു; മുകളിൽ കാണിച്ചിരിക്കുന്ന `/host-home` ഘടന കൃത്യമായി ഇതുതന്നെയാണ്), അതേസമയം mount ചെയ്യാത്തവയിലേക്കുള്ള എഴുത്ത് നിരസിക്കുന്നത് തുടരുകയും ചെയ്യുന്നു.

### അടിയന്തര ഒഴിവുവഴി: കണ്ടെയ്നറിന്റെ സ്വന്തം CLI-കൾ ക്രമീകരിക്കുക (വളരെ പരിമിതമായി ഉപയോഗിക്കുക)

CLI-കൾ യഥാർത്ഥത്തിൽ കണ്ടെയ്നറിനുള്ളിൽ തന്നെയാണ് പ്രവർത്തിക്കുന്നതെങ്കിൽ (`cli` പ്രൊഫൈൽ), എഴുത്ത് ഉദ്ദേശ്യപൂർവമായിരിക്കും. ഏതെങ്കിലും `setup-*` കമാൻഡിന് `--allow-container-write` നൽകുക, അല്ലെങ്കിൽ സെർവറിനായി
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` സജ്ജമാക്കുക. കണ്ടെയ്നറിനെ അതിജീവിച്ച് എഴുത്ത് നിലനിൽക്കില്ലെന്ന മുന്നറിയിപ്പോടെ എഴുത്ത് തുടരും.

> **സുരക്ഷാ മുന്നറിയിപ്പ് — `cli` പ്രൊഫൈൽ + `docker.sock` mount.**
> ഹോസ്റ്റ് daemon ഉപയോഗിച്ച് കണ്ടെയ്നറിനുള്ളിലെ auto-updater-ന് stack പുനഃസൃഷ്ടിക്കാൻ കഴിയുന്നതിനായി `cli` പ്രൊഫൈൽ `/var/run/docker.sock` bind-mount ചെയ്യുന്നു
> (`src/lib/system/autoUpdate.ts` ആ socket ഉണ്ടോയെന്ന് പരിശോധിക്കുകയും അത് ഇല്ലെങ്കിൽ
> Docker പാത ഒഴിവാക്കുകയും ചെയ്യുന്നു). ആ socket **ഹോസ്റ്റ്-root വിശ്വാസപരിധിയാണ്**:
> അതിലേക്ക് പ്രവേശിക്കാനാകുന്ന എന്തിനും root ആയി ഹോസ്റ്റ് Docker daemon-നെ നിയന്ത്രിക്കാനാകും — ഹോസ്റ്റിലെ ഏത് കണ്ടെയ്നറും സൃഷ്ടിക്കാനും പരിശോധിക്കാനും നിർത്താനും നീക്കം ചെയ്യാനും അതിന് കഴിയും.
> ഇതിന്റെ പ്രത്യാഘാതങ്ങൾ:
>
> 1. **`cli` പ്രൊഫൈലിന്റെ port ഒരിക്കലും നെറ്റ്വർക്കിലേക്ക് തുറന്നുകാട്ടരുത്.**
>    അത് `127.0.0.1`-ൽ publish ചെയ്യുക (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN-ൽ നിന്ന് എത്തിച്ചേരാവുന്ന ഒരു `cli` പ്രൊഫൈൽ, ഡാഷ്ബോർഡ് തലത്തിലുള്ള ഏതൊരു RCE-യെയും പൂർണ്ണമായ ഹോസ്റ്റ് കൈയേറ്റമാക്കി മാറ്റുന്നു.
> 2. **`cli` പ്രൊഫൈലിലേക്ക് അധിക ഹോസ്റ്റ് ഡയറക്ടറികളൊന്നും bind ചെയ്യരുത്.**
>    Docker socket-നൊപ്പം മറ്റേതെങ്കിലും mount കൂടിയുണ്ടെങ്കിൽ, അത് കണ്ടെയ്നറിന് നിങ്ങളുടെ ഫയൽസിസ്റ്റത്തിലേക്കും ഹോസ്റ്റ് കോൺഫിഗറേഷനിലേക്കും പൂർണ്ണമായ read/write പ്രവേശനം നൽകുന്നു. ഒരു ടൂളിന് ഒരു project കാണേണ്ടതുണ്ടെങ്കിൽ, CLI binary ഉപയോഗിച്ച് അത് പ്രാദേശികമായി പ്രവർത്തിപ്പിക്കുക — `cli` കണ്ടെയ്നറിലേക്ക് അത് mount ചെയ്യരുത്.
>
> കണ്ടെയ്നറിനുള്ളിലെ auto-update ആവശ്യമില്ലെങ്കിൽ, `cli` പ്രൊഫൈൽ പ്രവർത്തനരഹിതമായി നിലനിർത്തുക
> (`COMPOSE_PROFILES=core,redis` അല്ലെങ്കിൽ അതിലും ചുരുങ്ങിയത്). മറ്റ് പ്രൊഫൈലുകൾ
> Docker socket mount ചെയ്യുന്നില്ല.
>
> MITM-നെ ചുറ്റിപ്പറ്റിയുള്ള അനുബന്ധ threat model-നായി `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`-ലേക്ക് compile ചെയ്തിട്ടില്ല) കാണുക; കൂടാതെ
> `codex`/`claude-code`/`droid`/`openclaw` binary provenance chain-നായി
> `docs/security/SUPPLY_CHAIN.md` കാണുക.

## Redis സൈഡ്കാർ

വിതരണം ചെയ്ത നിരക്ക് നിയന്ത്രണത്തിനും പങ്കിട്ട കാഷിനും OmniRoute Redis-നെ ആശ്രയിക്കുന്നു. `redis` സർവീസ് `docker-compose.yml`-ൽ **എല്ലായ്പ്പോഴും നിർവചിച്ചിരിക്കുന്നു** (ഇതിന് പ്രൊഫൈൽ ഗേറ്റ് ഇല്ല), കൂടാതെ മറ്റേതൊരു പ്രൊഫൈലിനോടൊപ്പവും ഇത് ആരംഭിക്കുന്നു.

| വിശദാംശം                   | മൂല്യം                                          |
| -------------------------- | ----------------------------------------------- |
| ഇമേജ്                      | `redis:7-alpine`                                |
| കണ്ടെയ്നറിന്റെ പേര്        | `omniroute-redis`                               |
| ആന്തരിക പോർട്ട്            | `6379`                                          |
| ഹോസ്റ്റ് പോർട്ട് (ഓവർറൈഡ്) | `REDIS_PORT` (സ്ഥിരസ്ഥിതിയായി `6379`)           |
| ഹോസ്റ്റ് ബൈൻഡ് (ഓവർറൈഡ്)   | `REDIS_BIND_HOST` (സ്ഥിരസ്ഥിതിയായി `127.0.0.1`) |
| വോള്യം                     | `omniroute-redis-data` → `/data`                |
| ആരോഗ്യ പരിശോധന             | `redis-cli ping` (10 സെക്കൻഡ് ഇടവേള)            |

ബന്ധപ്പെട്ട എൻവയോൺമെന്റ് വേരിയബിളുകൾ:

- `REDIS_URL` — ആപ്പിലേക്ക് നൽകുന്ന കണക്ഷൻ സ്ട്രിംഗ് (സ്ഥിരസ്ഥിതിയായി `redis://redis:6379`).
- `REDIS_PORT` — Redis കണ്ടെയ്നറിനുള്ള ഹോസ്റ്റ്-സൈഡ് പോർട്ട് മാപ്പിംഗ്.
- `REDIS_BIND_HOST` — പോർട്ട് പ്രസിദ്ധീകരിക്കുന്ന ഹോസ്റ്റ് ഇന്റർഫേസ്. സ്ഥിരസ്ഥിതിയായി `127.0.0.1`.

> **എന്തുകൊണ്ട് സ്ഥിരസ്ഥിതിയായി ലൂപ്പ്ബാക്ക്:** സൈഡ്കാർ `requirepass` ഇല്ലാതെ പ്രവർത്തിക്കുന്നു, കൂടാതെ ആപ്പ്
> കണ്ടെയ്നറുകൾ compose നെറ്റ്വർക്കിലൂടെ (`redis:6379`) അതിലേക്ക് എത്തുന്നു — പ്രസിദ്ധീകരിച്ച പോർട്ട്
> ഹോസ്റ്റ്-സൈഡ് ടൂളുകൾക്ക് (`redis-cli`, ഒരു ലോക്കൽ `npm run dev`) വേണ്ടി മാത്രമുള്ളതാണ്. `0.0.0.0`-ൽ
> പ്രസിദ്ധീകരിക്കുന്നത് നിങ്ങളുടെ LAN-ലെ എല്ലാ ഹോസ്റ്റുകൾക്കും പ്രാമാണീകരണമില്ലാത്ത Redis ലഭ്യമാക്കും. നിങ്ങൾ
> `REDIS_BIND_HOST=0.0.0.0` സജ്ജമാക്കുകയാണെങ്കിൽ, സർവീസിന്റെ `command:`-ൽ `--requirepass` കൂടി ചേർക്കുക.

**Redis പ്രവർത്തനരഹിതമാക്കുന്നത്** ശുപാർശ ചെയ്യുന്നില്ല (നിരക്ക് നിയന്ത്രണം ഇൻ-മെമ്മറി ഫാൾബാക്കിലേക്ക് തരംതാഴും). നിർബന്ധമാണെങ്കിൽ, `docker-compose.yml`-ലെ `redis:` സർവീസ് ബ്ലോക്ക് നീക്കം ചെയ്യുക/കമന്റ് ചെയ്യുക, അല്ലെങ്കിൽ അതിനെ പൂജ്യത്തിലേക്ക് സ്കെയിൽ ചെയ്യുക:

```bash
docker compose up -d --scale redis=0
```

## പ്രൊഡക്ഷൻ Compose

ഡെവിനോടൊപ്പം പ്രവർത്തിക്കുന്ന ഒരു ഒറ്റപ്പെട്ട പ്രൊഡക്ഷൻ സ്നാപ്പ്ഷോട്ടിനായി `docker-compose.prod.yml` ഉപയോഗിക്കുക.

| വിശദാംശം                      | മൂല്യം                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| ഫയൽ                           | `docker-compose.prod.yml`                                                                                 |
| സ്ഥിരസ്ഥിതി ഡാഷ്ബോർഡ് പോർട്ട് | `PROD_DASHBOARD_PORT=20130` (ആന്തരിക `${DASHBOARD_PORT:-20128}`-ലേക്ക് മാപ്പ് ചെയ്യുന്നു)                 |
| സ്ഥിരസ്ഥിതി API പോർട്ട്       | `PROD_API_PORT=20131`                                                                                     |
| ഇമേജ്                         | `omniroute:prod` (`runner-cli` ടാർഗറ്റിൽ നിന്ന് ബിൽഡ് ചെയ്തത്)                                            |
| Redis കണ്ടെയ്നർ               | `omniroute-redis-prod` (`redis:8.6.2`, സമർപ്പിത `redis-prod-data` വോള്യം)                                 |
| ഡാറ്റാ വോള്യം                 | `omniroute-prod-data` (പേരിട്ടത്, റീബിൽഡുകളിലുടനീളം നിലനിൽക്കുന്നത്)                                      |
| ആരോഗ്യ പരിശോധനകൾ              | `node healthcheck.mjs` + `redis-cli ping`, Redis-ന്റെ ആരോഗ്യത്തെ അടിസ്ഥാനമാക്കി ഗേറ്റ് ചെയ്ത `depends_on` |

ഉപയോഗിക്കേണ്ട വിധം:

```bash
# പ്രൊഡക്ഷൻ സ്റ്റാക്ക് ബിൽഡ് ചെയ്ത് ആരംഭിക്കുക
docker compose -f docker-compose.prod.yml up -d --build

# ലോഗുകൾ സ്ട്രീം ചെയ്യുക
docker compose -f docker-compose.prod.yml logs -f

# നിർത്തി നീക്കം ചെയ്യുക (വോള്യങ്ങൾ നിലനിർത്തുക)
docker compose -f docker-compose.prod.yml down
```

പ്രൊഡ് സ്റ്റാക്ക് ഡെവ് compose-നൊപ്പം സമാന്തരമായി പ്രവർത്തിക്കുന്നു (വ്യത്യസ്ത കണ്ടെയ്നർ പേരുകൾ, പോർട്ടുകൾ, വോള്യങ്ങൾ എന്നിവ ഉപയോഗിച്ച്), അതിനാൽ പ്രൊഡക്ഷൻ പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുമ്പോൾ തന്നെ നിങ്ങൾക്ക് ലോക്കലായി ആവർത്തിച്ച് വികസിപ്പിക്കുന്നത് തുടരാം.

| `runner-base` | `node:26-trixie-slim` | Next.js സ്റ്റാൻഡ്എലോൺ ഔട്ട്പുട്ടിനൊപ്പം പ്രൊഡക്ഷൻ റൺടൈം.** ദാതാവ് CLIs ബണ്ടിൽ ചെയ്തിട്ടില്ല.**                                                                                                                                                                                                           |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose`, ഗ്ലോബൽ CLIs എന്നിവ ചേർക്കുന്നു: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`.** ഏജൻ്റ് വർക്ക്ഫ്ലോകൾക്കായി ഇത് തിരഞ്ഞെടുക്കുക.**                                                                                                               |
| `runner-web`  | `runner-base`         | വെബ് സെഷൻ ദാതാക്കൾക്കായി Playwright + ഒരു Chromium ബ്രൗസർ (`--with-deps`) ചേർക്കുന്നു: `gemini-web`, `claude-web`, `claude-turnstile`.** നിങ്ങൾ ആ ദാതാക്കളെ ഉപയോഗിക്കുമ്പോൾ ഇത് തിരഞ്ഞെടുക്കുക** — അഭ്യർത്ഥന സമയത്ത് പ്ലെയിൻ ഇമേജ് പരാജയപ്പെടുന്നു (റിലീസ് ചാനലുകൾക്ക് കീഴിലുള്ള `-web` കുറിപ്പ് കാണുക). |

ഒരു നിർദ്ദിഷ്ട ലക്ഷ്യം സ്വമേധയാ നിർമ്മിക്കുക:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ബിൽഡ്-ടൈം വിഭവങ്ങൾ

മൂന്ന് ബിൽഡ് ആർഗുകൾ `builder` സ്റ്റേജിൻ്റെ വിലയെ നിയന്ത്രിക്കുന്നു. അവ ബിൽഡ്-ടൈം മാത്രമാണ് — `OMNIROUTE_MEMORY_MB` (ചുവടെ) ഒരു പ്രത്യേക, റൺടൈം നോബ് ആണ്.

| ആർഗ് നിർമ്മിക്കുക           | സ്ഥിരസ്ഥിതി | പ്രഭാവം                                                                                                          |
| --------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`         | `0` വെബ്പാക്ക് ഉപയോഗിച്ച് നിർമ്മിക്കുന്നു: കുറഞ്ഞ പീക്ക് മെമ്മറി, വേഗത കുറവാണ്. `1` Turbopack തിരഞ്ഞെടുക്കുന്നു. |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`      | വി 8 ഹീപ്പ് സീലിംഗ് (`--max-old-space-size`) മുട്ടയിടുന്ന `next build`.                                          |
| `OMNIROUTE_BUILD_WORKERS`   | `2`         | ഫീഡുകൾ `CIRCLE_NODE_TOTAL`; അടുത്തത് പേജ്-ഡാറ്റ ശേഖരണത്തിനായി `workers = N - 1` ലഭിക്കുന്നു.                     |

`OMNIROUTE_BUILD_WORKERS` എന്നത് ഒരു വലിയ ബിൽഡറുടെ മേൽ വളർത്താനുള്ളതും പരിമിതമായ ഒരു ബിൽഡ് മരിക്കുമ്പോൾ സംശയിക്കേണ്ടതും ആണ്** ശേഷം** `✓ Compiled successfully`. ഓരോ പേജ്-ഡാറ്റ വർക്കറും അതിൻ്റേതായ പ്രക്രിയയാണ്, അതുപോലെ തന്നെ രക്ഷാകർതൃ `next build` യും; ഒരു തത്സമയ VPS പുനർനിർമ്മാണം (ഇഷ്യൂ #7518) ഓരോ പ്രക്രിയയുടെയും പീക്ക് RSS അളക്കുന്നത് `NODE_OPTIONS` ഹീപ്പ് ഫ്ലാഗിൽ നിന്ന് സ്വതന്ത്രമായി ~ 4.5 GB ആണ് (Turbopack കംപൈൽ ചെയ്യുന്നത് native/Rust മെമ്മറിയിൽ V8 ഹീപ്പിന് പുറത്ത്). പബ്ലിഷ് പൈപ്പ്ലൈൻ ഉപയോഗിക്കുന്ന 16 GB / 4 vCPU GitHub-ഹോസ്റ്റഡ് റണ്ണേഴ്സിനായി `2` ൻ്റെ ഡിഫോൾട്ട് (→ 1 വർക്കർ, ആകെ 2 പ്രോസസ്സുകൾ) വലുപ്പമുള്ളതാണ്. `8` ൽ (→ 7 തൊഴിലാളികൾ) ആ ഓട്ടക്കാരൻ്റെ മെമ്മറി തീർന്നു, ബിൽഡ്കിറ്റ് `ResourceExhausted: ... cannot allocate memory` ൻ്റെ ഘട്ടത്തിൽ പരാജയപ്പെട്ടു; `3` (→ 2 തൊഴിലാളികൾ) അനുമാനിക്കുന്നതിനുപകരം ഓരോ പ്രോസസ്സിനും RSS നേരിട്ട് അളന്നുകഴിഞ്ഞാൽ അപ്പോഴും യോജിച്ചില്ല. `tests/unit/docker-build-memory-budget.test.ts` അളന്ന കണക്കിന് വിരുദ്ധമായി ഗണിതശാസ്ത്രം ചെയ്യുന്നു, ഒന്നുകിൽ നോബ് റണ്ണറെ മറികടക്കുകയാണെങ്കിൽ പരാജയപ്പെടുന്നു.

ജീവിക്കുന്ന റസ്റ്റ് മെമ്മറിയിൽ Turbopack കംപൈൽ ചെയ്യുന്നു** പുറത്ത്** V8 കൂമ്പാരം, അതിനാൽ `OMNIROUTE_BUILD_MEMORY_MB` അതിനെ ബന്ധിക്കുന്നില്ല. മെമ്മറി സീലിംഗ് ഉള്ള ഒരു ഹോസ്റ്റിൽ, OOM കില്ലർ ബിൽഡ് SIGKILLed ആണ്, — ഒരു പിശക് ടെക്സ്റ്റും കൂടാതെ അത് മിഡ്-`Creating an optimized production build` ൽ നിർത്തുന്നു, ഇത് മെമ്മറിക്ക് പുറത്തുള്ളതിനേക്കാൾ ഹാംഗ് പോലെ വായിക്കുന്നു. അതുകൊണ്ടാണ് `Dockerfile` ഡിഫോൾട്ടായി വെബ്പാക്ക് (`OMNIROUTE_USE_TURBOPACK=0`), `npm run dev` / `npm run build` പോലെയല്ല, ഇവിടെ Turbopack കോഡ് ഡിഫോൾട്ടാണ്: ബിൽഡ് ആർഗുകളില്ലാത്ത ഒരു ബെയർ `docker build .` (റെയിൽവേയും മറ്റ് ഒറ്റ-ക്ലിക്ക് ഹോസ്റ്റുകളും പ്രവർത്തിപ്പിക്കുന്നത്) മെമ്മറി-ക്യാപ്പ്ഡ് ബിൽഡറിൽ നിശബ്ദമായി മരിക്കരുത്. പ്രസിദ്ധീകരിച്ച ചിത്രങ്ങൾ ഇതിനകം `docker-publish.yml` ൽ വ്യക്തമായി `OMNIROUTE_USE_TURBOPACK=0` കടന്നുപോകുന്നു. ധാരാളം RAM ഉള്ള ഒരു ബിൽഡറിൽ, വേഗത്തിലുള്ള ബിൽഡിനായി Turbopack തിരഞ്ഞെടുക്കുക:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുന്നു, അതിനാൽ `next build` ഒരു രക്ഷിതാവിനെ പ്രവർത്തിപ്പിക്കുന്നു** ഒപ്പം** ഒരു തൊഴിലാളി പ്രക്രിയയും ഓരോന്നും `OMNIROUTE_BUILD_MEMORY_MB` പ്രത്യേകം ബഹുമാനിക്കുന്നു. കണ്ടെയ്നർ സീലിംഗിൻ്റെ വലുപ്പം അതിൻ്റെ ഏകദേശം ഇരട്ടി മൂല്യത്തിന് മുകളിലാണ്, ഒന്നല്ല.

ഈ മരത്തിൽ അളന്നു (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ബണ്ടർ      | കണ്ടെയ്നർ സീലിംഗ് | ഫലം                                  |
| ---------- | ----------------- | ------------------------------------ |
| Turbopack  | 8 GiB / 16 GiB    | OOM-നിശ്ശബ്ദമായി രണ്ടുപേരെയും കൊന്നു |
| വെബ്പാക്ക് | 8 GiB             | പണിയുന്ന തൊഴിലാളി SIGKILLed          |
| വെബ്പാക്ക് | 12 GiB            | വിജയിച്ചു, 11.1 GiB ഉയർന്നു          |

### റൺടൈം ഡിഫോൾട്ടുകൾ

`runner-base` കയറ്റുമതി ചെയ്യുന്ന സ്ഥിരസ്ഥിതികൾ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Docker യിലെ മെമ്മറി പെരുമാറ്റം:

- ചിത്രം `OMNIROUTE_MEMORY_MB=1024` സജ്ജമാക്കുകയും അതിൽ നിന്ന് `NODE_OPTIONS=--max-old-space-size=1024` നേടുകയും ചെയ്യുന്നു.
- `OMNIROUTE_MEMORY_MB` വായിക്കുകയും `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` കൂട്ടിച്ചേർക്കുകയും ചെയ്യുന്ന സ്റ്റാൻഡ്ലോൺ ലോഞ്ചറാണ് യഥാർത്ഥ സെർവർ പ്രോസസ്സ് ആരംഭിക്കുന്നത്.
- നോഡ് അവസാനമായി ആവർത്തിക്കുന്ന `--max-old-space-size` മൂല്യം ഉപയോഗിക്കുന്നു, അതിനാൽ `OMNIROUTE_MEMORY_MB` സജ്ജീകരിക്കുന്നത് ഫലപ്രദമായ Docker ഹീപ്പ് പരിധിയെ നിയന്ത്രിക്കുന്നു.
- ചിത്രം എല്ലായ്പ്പോഴും അത് സജ്ജീകരിക്കുന്നതിനാൽ, ലോഞ്ചറിൻ്റെ സ്വന്തം റാം-കാലിബ്രേറ്റഡ് ഫാൾബാക്ക് ഒരിക്കലും Docker കീഴിൽ ബാധകമല്ല. ജോലിഭാരത്തിനായി ഇത് വ്യക്തമായി ഉയർത്തുക (താഴെയുള്ള പട്ടിക). കോഡിംഗ് ഏജൻ്റ് `/v1/responses` ന് `2048` ഇപ്പോഴും വളരെ ചെറുതാണ്.

### കോഡിംഗ് ഏജൻ്റുകൾക്കുള്ള റൺടൈം RAM

1 GiB Docker ഡിഫോൾട്ട് ഒരു dashboard/light-chat നിലയാണ്, ഉൽപ്പാദന വലുപ്പമല്ല. നീളമുള്ള `POST /v1/responses` ബോഡികൾ (നൂറുകണക്കിന് സന്ദേശങ്ങൾ, പതിനായിരക്കണക്കിന് ഉപകരണങ്ങൾ) കംപ്രഷൻ സമയത്ത് ഒന്നിലധികം ഇൻ-മെമ്മറി ഗ്രാഫുകൾ നിലനിർത്തുന്നു. രണ്ട് ഓവർലാപ്പിംഗ് ~ 3 MiB / ~ 750k-ടോക്കൺ അഭ്യർത്ഥനകൾ ഒരു സമയത്ത് V8 നിർത്തലാക്കി** 12 GiB** പഴയ ഇടം (`FATAL ERROR: Reached heap limit`) കൂടാതെ 16 GiB cgroup OOM ഹിറ്റ് ചെയ്യുക. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) കാണുക.

വലിപ്പം** കൂമ്പാരത്തിന് മുകളിൽ cgroup `--memory`** — നേറ്റീവ് ബഫറുകൾ, SQLite, കംപ്രഷൻ ഇൻ്റർമീഡിയറ്റുകൾ എന്നിവ V8 ന് പുറത്ത് ഇരിക്കുന്നു.

| ജോലിഭാരം                               | `OMNIROUTE_MEMORY_MB`       | കണ്ടെയ്നർ / സി ഗ്രൂപ്പ് | കുറിപ്പുകൾ                                                                                                         |
| -------------------------------------- | --------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------ |
| ഡാഷ്ബോർഡ്, ഒരു ലൈറ്റ് ചാറ്റ്           | `1024` (ചിത്രം സ്ഥിരസ്ഥിതി) | ≥2 GiB                  |                                                                                                                    |
| ഒരു കോഡിംഗ് ഏജൻ്റ് (Claude/Codex/Grok) | `8192`                      | ≥10 GiB                 | സാധാരണ ഒറ്റ-സെഷൻ `/v1/responses`                                                                                   |
| രണ്ട് സമാന്തര നീളമുള്ള `/v1/responses` | `10240`–`12288`             | ≥12–16 GiB              | ~ 12 GiB കൂമ്പാരത്തിൽ V8 അബോർട്ട് ചെയ്യുന്നു                                                                       |
| മൂന്ന്+ ഒരേസമയം നീണ്ട സന്ദർഭങ്ങൾ       | ഒരു പ്രക്രിയയിൽ ചെയ്യരുത്   | സീരിയലൈസ് / കൂടുതൽ RAM  | ഡിഫോൾട്ട് ഹെവിവെയ്റ്റ് പ്രവേശനം 1 ഇൻ-ഫ്ലൈറ്റാണ്; RAM ഇല്ലാതെ ഉയർത്തുന്നത് ഗർഭച്ഛിദ്രത്തെ വീണ്ടും അവതരിപ്പിക്കുന്നു |

ബെയർ മെറ്റലിൽ `omniroute serve` `OMNIROUTE_MEMORY_MB` RAM ~ 35% (ക്ലാമ്പ്ഡ് `[512, 4096]`) കാലിബ്രേറ്റ് ചെയ്യുന്നു** സജ്ജീകരിക്കാത്തത്** . Docker എല്ലായ്പ്പോഴും `1024` സജ്ജമാക്കുന്നു, അതിനാൽ കാലിബ്രേഷൻ ഒരിക്കലും ഔദ്യോഗിക ഇമേജിൽ പ്രവർത്തിക്കില്ല.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data cheaperinference/omniroute:latest
```

## ഒരു ഉപപാതയിലെ റിവേഴ്സ് പ്രോക്സി (Traefik / nginx)

Next.js `basePath` is compiled into the standalone bundle. OmniRoute records the baked value in a sentinel file at the app root (written during `npm run build`; read by `scripts/docker/ensure-docker-base-path.mjs`) and compares it with `OMNIROUTE_BASE_PATH` when the container starts. When they differ and the image was built for the domain root, the entrypoint rewrites the standalone manifests, the embedded `basePath`/`assetPrefix` literals (Next 16 renders SSR asset URLs from `assetPrefix` alone — the patcher mirrors the subpath into it), the baked `/_next/static` asset URLs (client-reference manifests, media imports, prerendered error pages) and the client `process.env` shim before `node dev/run-standalone.mjs` runs.

### ബിൽഡ് രചിക്കുക (ശുപാർശ ചെയ്യുന്നത്)

രണ്ട് വേരിയബിളുകളും `.env` യിൽ സജ്ജമാക്കുക, തുടർന്ന് പുനർനിർമ്മിക്കുക, അങ്ങനെ ചിത്രവും റൺടൈമും യോജിക്കുന്നു:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml` ഒരു Docker ബിൽഡ്-ആർഗ് ആയും റൺടൈം എൻവയോൺമെൻ്റ് വേരിയബിളായും `OMNIROUTE_BASE_PATH` ഫോർവേഡ് ചെയ്യുന്നു.

### പ്രീ-ബിൽറ്റ് റൂട്ട് ഇമേജ് + റൺടൈം സബ്പാത്ത്

പ്രസിദ്ധീകരിച്ച `cheaperinference/omniroute:*` ചിത്രങ്ങൾ ഡൊമെയ്ൻ റൂട്ടിനായി നിർമ്മിച്ചതാണ്. നിങ്ങൾക്ക് ഇപ്പോഴും റൺടൈമിൽ `OMNIROUTE_BASE_PATH` സജ്ജമാക്കാൻ കഴിയും; സ്റ്റാർട്ടപ്പിൽ ഒരിക്കൽ കണ്ടെയ്നർ ബണ്ടിൽ പാച്ച് ചെയ്യുന്നു. പൊരുത്തപ്പെടുന്ന പൊതു ഉത്ഭവവുമായി ഇത് ജോടിയാക്കുക:

```yaml
services:
  omniroute:
    image: cheaperinference/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

ഫോർവേഡ് ചെയ്യാൻ റിവേഴ്സ് പ്രോക്സി കോൺഫിഗർ ചെയ്യുക** നിറഞ്ഞു** ബാഹ്യ പാത (പ്രിഫിക്സ് സ്ട്രിപ്പ് ചെയ്യരുത്). Traefik `PathPrefix(`/omniroute `)` `StripPrefix` ഇല്ലാതെ കണ്ടെയ്നറിലേക്ക് നയിക്കണം, അതിനാൽ Next.js `/omniroute/...` സ്വീകരിക്കുകയും `/omniroute/_next/...` ൽ നിന്ന് അസറ്റുകൾ നൽകുകയും ചെയ്യുന്നു.

Docker ആരോഗ്യ പരിശോധന, സജീവമായ `OMNIROUTE_BASE_PATH` പ്രിഫിക്സ് ചെയ്ത ഭാരം കുറഞ്ഞ `/healthz` ലൈഫ്സൈക്കിൾ എൻഡ്പോയിൻ്റ് പരിശോധിക്കുന്നു. human/dashboard ഡയഗ്നോസ്റ്റിക്സിനായി `/api/monitoring/health` അവശേഷിക്കുന്നു; കണ്ടെയ്നർ HEALTHCHECK അതിലേക്ക് തിരിച്ചുവിടാൻ (ഉദാഹരണത്തിന് ആഴത്തിലുള്ള ആരോഗ്യ നിർവ്വഹണത്തിന്), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` സജ്ജമാക്കുക. ആ പാത എ** ആഴമുള്ള** പരിശോധിക്കുക (DB + മോണിറ്ററിംഗ് സംഗ്രഹം) നിങ്ങൾ തിരികെ തിരഞ്ഞെടുക്കുകയാണെങ്കിൽ Docker ൻ്റെ അപൂർവ്വമായ `HEALTHCHECK` ന് — അനുയോജ്യം, പക്ഷേ** അല്ല** Kubernetes `livenessProbe` ഇടവേളകൾക്കായി.

ഓർക്കസ്ട്രേറ്റർമാർക്കായി (കുബർനെറ്റസ്, നോമാഡ്, മുതലായവ):

| അന്വേഷണം                     | മുൻഗണന നൽകുക                                                                  | ഒഴിവാക്കുക                                                            |
| ---------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| സജീവത                        | പ്രധാന പോർട്ടിൽ HTTP `GET /livez`, അല്ലെങ്കിൽ TCP (`PORT`, ഡിഫോൾട്ട് `20128`) | `/api/monitoring/health` ജീവനുള്ളതായി                                 |
| സന്നദ്ധത                     | HTTP `GET /healthz`                                                           | തിരക്കുള്ള ഇവൻ്റ്-ലൂപ്പിനെ മരിച്ചതായി കണക്കാക്കുന്ന ടൈറ്റ് ടൈംഔട്ടുകൾ |
| ആഴത്തിലുള്ള / ബ്ലാക്ക്ബോക്സ് | `/api/monitoring/health`                                                      | —                                                                     |

`/healthz` പ്രോസസ് ലൈഫ് സൈക്കിൾ റിപ്പോർട്ട് ചെയ്യുന്നു (`ok` / `starting` / `stopping`). `/livez` പ്രോസസ്സ്-ലൈവ് ആണ് (200 ഹാൻഡ്ലറിന് പ്രവർത്തിപ്പിക്കാൻ കഴിയുമ്പോഴെല്ലാം; അത് സന്നദ്ധതയ്ക്കായി കാത്തിരിക്കുന്നില്ല). അഭ്യർത്ഥന കൈകാര്യം ചെയ്യുന്നതിനായി രണ്ടും ഇപ്പോഴും ഒരേ നോഡ് ഇവൻ്റ് ലൂപ്പിൽ പ്രവർത്തിക്കുന്നു, അതിനാൽ സിപിയു-ബൗണ്ട് കാറ്റലോഗ് അല്ലെങ്കിൽ കംപ്രഷൻ വർക്ക് അവരെ — തിരക്കുള്ള ≠ ഡെഡ് ആയി വൈകിപ്പിക്കും. HTTP അന്വേഷണം സമയപരിധി കഴിഞ്ഞാൽ TCP ലൈവ്നെസ് തിരഞ്ഞെടുക്കുക. പൂർണ്ണ അന്വേഷണ മാർഗ്ഗനിർദ്ദേശം: [മോണിറ്ററിംഗ് ഗൈഡ് — കുബർനെറ്റസ് പ്രോബ് ശുപാർശകൾ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Docker കാഡി ഉപയോഗിച്ച് രചിക്കുക (HTTPS ഓട്ടോ-TLS)

കാഡിയുടെ ഓട്ടോമാറ്റിക് SSL പ്രൊവിഷനിംഗ് ഉപയോഗിച്ച്OmniRoute സുരക്ഷിതമായി തുറന്നുകാട്ടാനാകും. നിങ്ങളുടെ ഡൊമെയ്നിൻ്റെ DNS A റെക്കോർഡ് നിങ്ങളുടെ സെർവറിൻ്റെ IP ലേക്ക് പോയിൻ്റ് ചെയ്യുന്നു എന്ന് ഉറപ്പാക്കുക.

```yaml
services:
  omniroute:
    image: cheaperinference/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # Browser-facing origin for OAuth callbacks, dashboard links, and generated public URLs.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # Internal server-to-server URL for scheduled jobs / self-fetches.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

അപ്സ്ട്രീം കണ്ടെയ്നറിനായി കാഡി സ്റ്റാൻഡേർഡ് ഫോർവേഡിംഗ് ഹെഡറുകൾ സജ്ജമാക്കുന്നു. OmniRoute OAuth കോൾബാക്കുകൾക്കും ജനറേറ്റഡ് പബ്ലിക് ലിങ്കുകൾക്കുമായി കാനോനിക്കൽ പൊതു ഉത്ഭവമായി `NEXT_PUBLIC_BASE_URL` ഉപയോഗിക്കുന്നു; ആധികാരികമായ ഡാഷ്ബോർഡ് റൈറ്റുകൾ ഒരേ ഒറിജിൻ അഭ്യർത്ഥനകളും സെഷൻ-ബൗണ്ട് CSRF പരിരക്ഷയും ഉപയോഗിക്കുന്നു. വ്യക്തമായ കോൺഫിഗറേഷനുപകരം വിശ്വസനീയമായ ഫോർവേഡഡ് ഹെഡറുകളിൽ നിന്ന് പൊതു ഉത്ഭവം OmniRoute ലഭിക്കാൻ നിങ്ങൾ മനഃപൂർവ്വം ആഗ്രഹിക്കുന്ന വിപുലമായ വിന്യാസങ്ങൾക്കായി മാത്രം `OMNIROUTE_TRUST_PROXY` പ്രവർത്തനക്ഷമമാക്കുക.

## Cloudflare Quick Tunnel

Docker ഡിപ്ലോയ്മെന്റുകൾക്കുള്ള ഡാഷ്ബോർഡ് പിന്തുണയിൽ `Dashboard → Endpoints` എന്നതിൽ ഒറ്റ ക്ലിക്കിൽ പ്രവർത്തനക്ഷമമാക്കാവുന്ന **Cloudflare Quick Tunnel** ഉൾപ്പെടുന്നു. ആദ്യം പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ, ആവശ്യമായാൽ മാത്രം `cloudflared` ഡൗൺലോഡ് ചെയ്യുകയും നിങ്ങളുടെ നിലവിലെ `/v1` എൻഡ്പോയിന്റിലേക്ക് ഒരു താൽക്കാലിക ടണൽ ആരംഭിക്കുകയും സൃഷ്ടിച്ച `https://*.trycloudflare.com/v1` URL നിങ്ങളുടെ സാധാരണ പൊതു URL-ന് നേരെ താഴെ പ്രദർശിപ്പിക്കുകയും ചെയ്യുന്നു.

സജീവ ടണലിന്റെ നില മാറ്റാതെ `Settings → Appearance` എന്നതിൽനിന്ന് എൻഡ്പോയിന്റ് ടണൽ പാനലുകൾ (Cloudflare, Tailscale, ngrok) കാണിക്കാനോ മറയ്ക്കാനോ കഴിയും.

### ടണൽ കുറിപ്പുകൾ

- Quick Tunnel URL-കൾ താൽക്കാലികമാണ്, ഓരോ റീസ്റ്റാർട്ടിനുശേഷവും അവ മാറും.
- OmniRoute അല്ലെങ്കിൽ കണ്ടെയ്നർ റീസ്റ്റാർട്ട് ചെയ്തശേഷം Quick Tunnel-കൾ സ്വയമേവ പുനഃസ്ഥാപിക്കപ്പെടില്ല. ആവശ്യമുള്ളപ്പോൾ ഡാഷ്ബോർഡിൽനിന്ന് അവ വീണ്ടും പ്രവർത്തനക്ഷമമാക്കുക.
- മാനേജ്ഡ് ഇൻസ്റ്റാൾ നിലവിൽ `x64` / `arm64` ആർക്കിടെക്ചറുകളിലുള്ള Linux, macOS, Windows എന്നിവയെ പിന്തുണയ്ക്കുന്നു.
- നിയന്ത്രിത കണ്ടെയ്നർ പരിതസ്ഥിതികളിലെ അനാവശ്യമായ QUIC UDP ബഫർ മുന്നറിയിപ്പുകൾ ഒഴിവാക്കാൻ മാനേജ്ഡ് Quick Tunnel-കൾ ഡിഫോൾട്ടായി HTTP/2 ട്രാൻസ്പോർട്ട് ഉപയോഗിക്കുന്നു. മറ്റൊരു ട്രാൻസ്പോർട്ട് വേണമെങ്കിൽ `CLOUDFLARED_PROTOCOL=quic` അല്ലെങ്കിൽ `auto` സജ്ജീകരിക്കുക.
- Docker ഇമേജുകൾ സിസ്റ്റം CA റൂട്ടുകൾ ഉൾപ്പെടുത്തുകയും അവയെ മാനേജ്ഡ് `cloudflared`-ലേക്ക് കൈമാറുകയും ചെയ്യുന്നു; കണ്ടെയ്നറിനുള്ളിൽ ടണൽ ബൂട്ട്സ്ട്രാപ്പ് ചെയ്യുമ്പോഴുള്ള TLS വിശ്വാസ്യതാ പരാജയങ്ങൾ ഇത് ഒഴിവാക്കുന്നു.
- ഒന്ന് ഡൗൺലോഡ് ചെയ്യുന്നതിനുപകരം നിലവിലുള്ള ഒരു ബൈനറി OmniRoute ഉപയോഗിക്കണമെന്ന് നിങ്ങൾ ആഗ്രഹിക്കുന്നുവെങ്കിൽ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` സജ്ജീകരിക്കുക.

ഓരോ ആർക്കിടെക്ചർ ഡൈജസ്റ്റുകളിലും ഒരേ ചിത്രങ്ങൾ മൂന്ന് റിപ്പോസിറ്ററികളിൽ പ്രസിദ്ധീകരിക്കുന്നു: `cheaperinference/omniroute` (Docker Hub, Cheaper Inference Organisation, from 3.8.53 on), `ghcr.io/cheaper-inference/omniroute`, the legacy `diegosouzapw/omniroute`, അത് അതിൻ്റെ പുൾ ഹിസ്റ്ററി നിലനിർത്തുകയും ഇപ്പോഴും എല്ലാ റിലീസുകളും സ്വീകരിക്കുകയും ചെയ്യുന്നു. നിലവിലുള്ള `diegosouzapw/omniroute` വിന്യാസങ്ങൾ പുതുക്കിക്കൊണ്ടിരിക്കുന്നു; ചിത്രത്തിൻ്റെ പേര് മാറ്റുന്നത് ഓപ്ഷണൽ ആണ്. ചുവടെയുള്ള `:next` / `:next-web` പ്രീ-റിലീസ് ചാനൽ `diegosouzapw/omniroute`, GHCR എന്നിവയിൽ മാത്രം പ്രസിദ്ധീകരിക്കുന്നു.

മൾട്ടി-പ്ലാറ്റ്ഫോം മാനിഫെസ്റ്റ്: `linux/amd64` + `linux/arm64` നേറ്റീവ് (ആപ്പിൾ സിലിക്കൺ, AWS ഗ്രാവിറ്റൺ, റാസ്ബെറി പൈ). Docker പൊരുത്തപ്പെടുന്ന ആർക്കിടെക്ചർ സ്വയമേവ തിരഞ്ഞെടുക്കുന്നു; നിങ്ങൾക്ക് ARM ഹോസ്റ്റുകളിൽ AMD64 എമുലേഷൻ നിർബന്ധമാക്കണമെങ്കിൽ `--platform linux/amd64` പാസ്സാക്കുക.

### ചാനലുകൾ റിലീസ് ചെയ്യുക

സ്ഥിരതയുള്ള റിലീസുകൾ, സജീവമായ റിലീസ്-ബ്രാഞ്ച് ടെസ്റ്റിംഗ്, ഡെവലപ്മെൻ്റ് ബിൽഡുകൾ എന്നിവയ്ക്കായിOmniRoute പ്രത്യേക Docker ചാനലുകൾ പ്രസിദ്ധീകരിക്കുന്നു.

#### വെബ് സെഷൻ ദാതാക്കൾ: `-web` ചിത്രങ്ങൾ

മുകളിലുള്ള എല്ലാ ചാനലുകളും ഒരു `-web` ടാഗായി (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ഇരട്ടിയാകുന്നു, `runner-web` ഘട്ടത്തിൽ — ഒരേ ഇമേജും Playwright ഉം ഒരു Chromium ബ്രൗസറും ഉപയോഗിച്ച് നിർമ്മിച്ചതാണ്. പ്ലെയിൻ ഇമേജ് ഷിപ്പുകൾ** ഇല്ലാതെ** ക്രോമിയം; `gemini-web`, `claude-web`, `claude-turnstile` എന്നിവയ്ക്ക് ഇത് ആവശ്യമാണ്.

പരാജയം മാറ്റിവച്ചതാണ്, സ്റ്റാർട്ടപ്പ് സമയമല്ല: ആ ദാതാക്കൾ അവരുടെ മോഡലുകൾ ലിസ്റ്റുചെയ്ത് ഡാഷ്ബോർഡിൽ കണക്റ്റ് ചെയ്തിരിക്കുന്നതായി കാണിക്കുന്നു, ആദ്യ അഭ്യർത്ഥന മാത്രം പരാജയപ്പെടുന്നു

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

നിങ്ങൾ ആ ദാതാക്കളെ ഉപയോഗിക്കുകയാണെങ്കിൽ, നിങ്ങൾ ഇതിനകം — ൽ ഉള്ള ചാനലിൻ്റെ `-web` ടാഗ് വലിക്കുക, മറ്റൊന്നും മാറില്ല. ഒരു npm/CLI ഇൻസ്റ്റാളിൽ ( Docker ഇമേജ് ഇല്ല), തത്തുല്യമായ നഷ്ടമായ ഭാഗം ബ്രൗസർ ബൈനറിയാണ്: ഹോസ്റ്റിൽ `npx playwright install chromium` പ്രവർത്തിപ്പിക്കുക.

#### പ്രീ-റിലീസ് ചാനൽ ഉപയോഗിക്കുന്നു

നിലവിലെ ഡിഫോൾട്ട് `release/v*` ശാഖയിലേക്കുള്ള ഓരോ പുഷിലും `next` ചാനൽ പുനർനിർമ്മിക്കുകയും AMD64, ARM64 എന്നിവയ്ക്കായി പ്രസിദ്ധീകരിക്കുകയും ചെയ്യുന്നു. പഴയ മെയിൻ്റനൻസ് ബ്രാഞ്ചുകൾക്ക് ഇത് തിരുത്തിയെഴുതാൻ കഴിയില്ല. അടുത്ത സ്ഥിരതയുള്ള ടാഗ് മുറിക്കുന്നതിന് മുമ്പ് സജീവമായ റിലീസ് ബ്രാഞ്ചിലേക്ക് ലയിപ്പിച്ച പരിഹാരങ്ങൾക്കായി ചാനൽ ഒരു വലിക്കാവുന്ന ചിത്രം നൽകുന്നു.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker കമ്പോസിനായി, തിരഞ്ഞെടുത്ത പ്രൊഫൈൽ ഉപയോഗിച്ച ഇമേജ് ടാഗ് അസാധുവാക്കുക, തുടർന്ന് സേവനം വലിച്ച് പുനഃസൃഷ്ടിക്കുക:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### സുരക്ഷയും റോൾബാക്കും

`next` ഒരു ഫ്ലോട്ടിംഗ് പ്രീ-റിലീസ് ചാനലാണ്. സജീവമായ റിലീസ് ബ്രാഞ്ചിലേക്കുള്ള ഏത് പുഷിലും ഇത് മാറിയേക്കാം** ഉൽപ്പാദന ഉപയോഗത്തിന് പിന്തുണയില്ല** . ഒരു നിർദ്ദിഷ്ട ബിൽഡ് വിലയിരുത്തുമ്പോൾ ഇമേജ് ഡൈജസ്റ്റ് പിൻ ചെയ്യുക:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

പരിശോധിക്കുന്നതിന് മുമ്പ്, OmniRoute ഡാറ്റ വോളിയം അല്ലെങ്കിൽ ബൈൻഡ്-മൌണ്ട് ചെയ്ത ഡാറ്റ ഡയറക്ടറി ബാക്കപ്പ് ചെയ്യുക. റോൾ ബാക്ക് ചെയ്യുന്നതിന്, മുമ്പ് ഉപയോഗിച്ച സ്ഥിരമായ പതിപ്പ് പുനഃസ്ഥാപിക്കുക അല്ലെങ്കിൽ കണ്ടെയ്നർ ഡൈജസ്റ്റ് ചെയ്ത് പുനഃസൃഷ്ടിക്കുക:

```bash
docker pull cheaperinference/omniroute:<stable-version>
docker compose up -d
```

ഒരു റിലീസ്-ബ്രാഞ്ച് ബിൽഡിന് ഒരിക്കലും `latest` നീക്കാൻ കഴിയില്ല; യോഗ്യമായ സ്ഥിരതയുള്ള സെമാൻ്റിക് പതിപ്പ് മാത്രമേ സ്ഥിരതയുള്ള പോയിൻ്ററിനെ പ്രോത്സാഹിപ്പിക്കുകയുള്ളൂ. `next` ഇമേജുകൾ റിലീസ് ഇമേജ് പരിശോധന നിലനിർത്തുകയും ക്രിട്ടിക്കൽ-വൾനറബിലിറ്റി ഗേറ്റ് തടയുകയും ചെയ്യുന്നു.

**`latest` git-ന് ഒരു കറൻസി ഗ്യാരണ്ടി അല്ല.** `main` അല്ലെങ്കിൽ സജീവമായ `release/v*` ബ്രാഞ്ചിൽ ലയിപ്പിച്ച പരിഹാരങ്ങൾ** അല്ല** സ്ഥിരതയുള്ള ഒരു SemVer ഇമേജ് പ്രസിദ്ധീകരിക്കുകയും പ്രസിദ്ധീകരിക്കുന്ന ജോലി `:latest` SemVer ചെയ്യുന്നത് വരെ `:latest` ൽ GitHub ഇതിനകം തന്നെ ഫിക്സ് കാണിക്കുമ്പോൾ `latest` ഫ്രീസ് ചെയ്തതായി തോന്നുന്നുവെങ്കിൽ, റിലീസ് ബ്രാഞ്ച് പരിശോധിക്കുന്നതിന് `:next` വലിക്കുക അല്ലെങ്കിൽ SemVer ടാഗിനായി കാത്തിരിക്കുക.

| നിങ്ങൾ ആഗ്രഹിക്കുന്നു                                                               | ഉപയോഗിക്കുക                               |
| ----------------------------------------------------------------------------------- | ----------------------------------------- |
| ഒഴുകാൻ പാടില്ലാത്ത GitOps / ഉത്പാദനം                                                | പിൻ `:X.Y.Z` (അല്ലെങ്കിൽ ഇമേജ് ഡൈജസ്റ്റ്) |
| പ്രസിദ്ധീകരിച്ച സ്റ്റേബിളുകൾ പിന്തുടർന്ന് ഓരോ റിലീസിലും ഒരു പുനഃസൃഷ്ടി സ്വീകരിക്കുക | `:latest`                                 |
| റിലീസ് ചെയ്യാത്ത `release/v*` കമ്മിറ്റുകൾ പരീക്ഷിക്കുക                              | `:next` (ഉൽപാദനമല്ല)                      |
| ടെസ്റ്റ് `main`                                                                     | `:main` (ഉൽപാദനമല്ല)                      |

## Docker-ലെ ഡാഷ്ബോർഡ് അപ്ഡേറ്റുകൾ

പ്രസിദ്ധീകരിച്ച ഇമേജിൽനിന്നുള്ള ഒരു കണ്ടെയ്നറിന് സ്വയം മാറ്റിസ്ഥാപിക്കാനാകില്ല. OmniRoute ഒരു കണ്ടെയ്നറിനുള്ളിലാണ് പ്രവർത്തിക്കുന്നതെന്ന് കണ്ടെത്തുമ്പോൾ (`.git` checkout അല്ല, npm ഇൻസ്റ്റാളും അല്ല), ഹോം ഡാഷ്ബോർഡിന്റെ അപ്ഡേറ്റ് ബാനർ npm/git നിർദ്ദേശങ്ങൾക്ക് പകരം ഹോസ്റ്റിൽ പ്രവർത്തിപ്പിക്കേണ്ട കമാൻഡ് ഒരു കോപ്പി ബട്ടണോടുകൂടി കാണിക്കുന്നു:

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

സേവനത്തിന്റെ പേര് `AUTO_UPDATE_SERVICE`-ൽ നിന്നാണ് ലഭിക്കുന്നത് (ഡിഫോൾട്ട് `omniroute`, `docker-compose.selfhost.yml`-ലെ സേവനം). `pull` ഒരു ഫ്ലോട്ടിങ് ടാഗിനെ (`latest`, `next`) മാത്രമേ മുന്നോട്ട് നീക്കുകയുള്ളൂ; പിൻ ചെയ്ത `:X.Y.Z` ടാഗാണെങ്കിൽ ആദ്യം ടാഗ് തിരുത്തുക.

### ഹോസ്റ്റ് ട്രിഗർ ഫയൽ ഉപയോഗിച്ചുള്ള ഒറ്റ-ക്ലിക്ക് അപ്ഡേറ്റുകൾ

ഹോസ്റ്റിൽ കണ്ടെയ്നറിന് root അധികാരം നൽകുന്ന `/var/run/docker.sock` മൗണ്ട് ചെയ്യാതെ **Update Now** പ്രവർത്തനക്ഷമമായി നിലനിർത്താൻ — മുകളിലെ `cli` പ്രൊഫൈൽ മുന്നറിയിപ്പ് കാണുക — OmniRoute സേവനത്തിൽ `DOCKER_UPDATE_TRIGGER_FILE` സജ്ജീകരിച്ച് ഹോസ്റ്റിൽ ഒരു വാച്ചർ പ്രവർത്തിപ്പിക്കുക:

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

പാത്ത് `DATA_DIR`-നുള്ളിലായിരിക്കണം (ആപേക്ഷിക മൂല്യങ്ങൾ അതിനെ അടിസ്ഥാനമാക്കി നിർണ്ണയിക്കപ്പെടും); മറ്റെന്തും നിരസിക്കപ്പെടും. തുടർന്ന് **Update Now**, `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }` ആ ഫയലിലേക്ക് എഴുതുകയും `202` മറുപടി നൽകുകയും ചെയ്യും; പുതിയ പതിപ്പ് പ്രവർത്തനക്ഷമമാകുന്നതുവരെ ഡാഷ്ബോർഡ് `/api/system/version` പോൾ ചെയ്തശേഷം റീലോഡ് ചെയ്യും. ഈ മോഡിൽ OmniRoute ഒരിക്കലും shell അല്ലെങ്കിൽ Docker കമാൻഡ് പ്രവർത്തിപ്പിക്കില്ല. എല്ലാ അപ്ഡേറ്റ് പ്രവർത്തനങ്ങളെയും പോലെ, loopback/LAN ക്ലയന്റുകളിൽ നിന്നുള്ള അഭ്യർത്ഥനകൾ മാത്രമേ സ്വീകരിക്കൂ.

bind-mount ചെയ്ത ഡാറ്റ ഡയറക്ടറി ഹോസ്റ്റിന് നിരീക്ഷിക്കാൻ സ്ഥിരതയുള്ള ഒരു പാത്ത് നൽകുന്നു. മാതൃകാ `systemd` യൂണിറ്റുകൾ (`/srv/omniroute` എന്നത് നിങ്ങളുടെ compose ഫയലും `data/` ഡയറക്ടറിയും ഉൾക്കൊള്ളുന്ന ഡയറക്ടറിയായി ക്രമീകരിക്കുക):

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=OmniRoute ഡാഷ്ബോർഡ് അപ്ഡേറ്റ് അഭ്യർത്ഥനകൾ നിരീക്ഷിക്കുക

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=OmniRoute കണ്ടെയ്നർ pull ചെയ്ത് പുനഃസൃഷ്ടിക്കുക

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

പരാജയപ്പെട്ട പ്രവർത്തനം ലൂപ്പാകാതിരിക്കാൻ pull ചെയ്യുന്നതിന് മുമ്പ് സേവനം അഭ്യർത്ഥന നീക്കംചെയ്യുന്നു. `DOCKER_UPDATE_TRIGGER_FILE` ഇല്ലെങ്കിൽ ഡാഷ്ബോർഡ് മാനുവൽ കമാൻഡ് പ്രവാഹം നിലനിർത്തും.

## ലഭ്യത: ഡിഫോൾട്ട് SQLite സിംഗിൾ റെപ്ലിക്കയാണ്

സ്റ്റോക്ക് Docker / Kubernetes OmniRoute ആണ്** ഒരു നോഡ് പ്രോസസ്സ് + ഒരു SQLite റൈറ്റർ** . ഉയർന്ന ലഭ്യതയാണ്** പിന്തുണയ്ക്കുന്നില്ല** ആ ടോപ്പോളജിയിൽ.

| പരിമിതി                                                | അനന്തരഫലം                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ഏക എഴുത്തുകാരൻ                                         | ചെയ്യുക** അല്ല** ഒരേ SQLite ഫയലിനെതിരെ ഒന്നിലധികം പകർപ്പുകൾ പ്രവർത്തിപ്പിക്കുക. അത് DB യെ ദുഷിപ്പിക്കുന്നു.                                                                                                                                                                                                                                            |
| പുനഃസൃഷ്ടിക്കുക / പുനരാരംഭിക്കുക / HEALTHCHECK കൊല്ലുക | **പൂർണ്ണ തടസ്സം** ഇൻ-ഫ്ലൈറ്റ് SSE, ഡാഷ്ബോർഡ് സെഷനുകൾ, ഇൻ-മെമ്മറി അവസ്ഥ. കണക്റ്റുചെയ്ത ഓരോ ക്ലയൻ്റും കുറയുന്നു. ശൂന്യമായ എൻഡ് പോയിൻ്റ് വിൻഡോയിൽ പുതിയ അഭ്യർത്ഥനകൾക്ക് ഒരു റിവേഴ്സ് പ്രോക്സി ലഭിക്കും**`502 Bad Gateway: Unknown error`** , OmniRoute JSON അല്ല — ക്ലയൻ്റുകൾക്ക് ഇത് ഒരു ദാതാവിൻ്റെ പരാജയത്തിൽ നിന്ന് വേർതിരിച്ചറിയാൻ കഴിയില്ല (#11015). |
| `/healthz` അതേ ഇവൻ്റ് ലൂപ്പ്                           | തിരക്കുള്ള കാറ്റലോഗ് അല്ലെങ്കിൽ കംപ്രഷൻ ടിക്ക് പേടകങ്ങൾ വൈകിപ്പിക്കും; ഒരു ചെറിയ സമയപരിധി പിന്നീട് പുനരാരംഭിക്കുന്നു** മാത്രം** പകർപ്പ്.                                                                                                                                                                                                               |

**പ്രോബ് മാട്രിക്സ്** ( [കുബർനെറ്റസ് അന്വേഷണ ശുപാർശകളും](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) കാണുക):

| അന്വേഷണം              | ലക്ഷ്യം                                                               | ഉപയോഗിക്കരുത്                                                         |
| --------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------- |
| സജീവത                 | TCP ൽ `PORT` (ഡിഫോൾട്ട് `20128`), അല്ലെങ്കിൽ സോഫ്റ്റ് HTTP `/healthz` | `/api/monitoring/health`                                              |
| സന്നദ്ധത              | HTTP `GET /healthz`                                                   | തിരക്കുള്ള ഇവൻ്റ്-ലൂപ്പിനെ മരിച്ചതായി കണക്കാക്കുന്ന ടൈറ്റ് ടൈംഔട്ടുകൾ |
| ആഴത്തിലുള്ള / മനുഷ്യർ | `/api/monitoring/health`                                              | ഓട്ടോമേറ്റഡ് കുബെലെറ്റ് ലൈവ്നെസ്                                      |

**അപ്ഗ്രേഡുകൾ:** ഓരോ സെഷനും കുറയുമെന്ന് പ്രതീക്ഷിക്കുക. നിങ്ങൾക്ക് കഴിയുമെങ്കിൽ ക്ലയൻ്റുകൾ ഒഴിക്കുക; സ്ഥിരസ്ഥിതി SQLite യിൽ റോളിംഗ് അപ്ഡേറ്റ് ഒന്നുമില്ല. `restart: unless-stopped` പ്ലസ് Docker `HEALTHCHECK` രചിക്കുക, കണ്ടെയ്നർ അനാരോഗ്യകരമാകുമ്പോൾ ഒരേയൊരു പ്രക്രിയയെ മാറ്റിസ്ഥാപിക്കും - അതേ സ്ഫോടന ആരം.

റെഡിമെയ്ഡ് മാനിഫെസ്റ്റുകളും ഹെൽം ചാർട്ടും `deploy/kubernetes/`, `deploy/helm/omniroute/` എന്നിവയിൽ തത്സമയമാണ് - [കുബർനെറ്റസ് വിന്യാസ ഗൈഡ്](../ops/KUBERNETES_DEPLOYMENT_GUIDE.md) കാണുക.

കുബെർനെറ്റസ് സ്നിപ്പെറ്റ് എ** ഒറ്റ പകർപ്പ്** (പുനഃസൃഷ്ടി ആവശ്യമാണ്; ഒരു SQLite ഫയലിനെതിരെ `replicas` ഉയർത്തരുത്):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` സ്ലീപ്പ് SIGTERM ന് മുമ്പായി സേവന എൻഡ്പോയിൻ്റുകൾ ഡ്രോപ്പ് ചെയ്യാൻ kube അനുവദിക്കുന്നു** പുതിയത്** മരിക്കുന്ന പ്രക്രിയയെ തടസ്സപ്പെടുത്തുന്ന ഗതാഗതം നിർത്തുന്നു. ഇൻ-ഫ്ലൈറ്റ് `/v1/responses` SSE ഹെവിവെയ്റ്റ് അഡ്മിഷൻ ലീസുകളിലൂടെ (#11015) `SHUTDOWN_TIMEOUT_MS` (സ്ഥിരസ്ഥിതി 30സെ) വരെ വറ്റിച്ചു. ഇപ്പോഴും പ്രോസസ്സിൽ എത്തുന്ന പുതിയ അഭ്യർത്ഥനകൾക്ക് `503` + `Retry-After: 5` ലഭിക്കും. മാറ്റിസ്ഥാപിക്കൽ തയ്യാറാകുന്നതുവരെ ശൂന്യ-എൻഡ്പോയിൻ്റ് വിടവ് പുനഃസൃഷ്ടിക്കുന്നത് ഒരു ഹാർഡ് ഔട്ടേജായി തുടരുന്നു - അതാണ് SQLite ടോപ്പോളജി, ഒരു പ്രോബ് തെറ്റായ കോൺഫിഗറല്ല.

ബാഹ്യ Postgres / മൾട്ടി-റൈറ്റർ HA ആണ്** അല്ല** ഒരു ഡോക്യുമെൻ്റഡ് സ്റ്റോക്ക് പാത. നിങ്ങൾക്ക് HA ആവശ്യമുണ്ടെങ്കിൽ, ഒരൊറ്റ പകർപ്പ് സൂക്ഷിക്കുക അല്ലെങ്കിൽ പ്രോജക്റ്റ് പ്രത്യേകം പരിശോധിച്ച് ഡോക്യുമെൻ്റ് ചെയ്ത ഒരു ടോപ്പോളജി പ്രവർത്തിപ്പിക്കുക. Postgres/MySQL വർക്ക് [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) -ൽ താമസിക്കുന്നു. അത് ഷിപ്പുചെയ്യുന്നത് വരെ, ഗുണിക്കുന്നതിനുള്ള ഏക പിന്തുണയുള്ള മാർഗം** വലിയ** `/v1/responses` ശേഷി N സ്വതന്ത്ര പ്രക്രിയകളാണ് (അടുത്ത ഭാഗം), ഒരു വോള്യത്തിൽ `replicas > 1` അല്ല.

## സ്കെയിൽ-ഔട്ട്: N സ്വതന്ത്ര പ്രക്രിയകൾ

### Codex ടോക്കൺ റൊട്ടേഷൻ ഉടമസ്ഥാവകാശം

ഒരു Codex അക്കൗണ്ടിൻ്റെ പകർപ്പുകൾ അതിൻ്റെ ഒറ്റത്തവണ ഉപയോഗിക്കാവുന്ന പുതുക്കിയ ടോക്കൺ സ്വതന്ത്രമായി ഉപയോഗിക്കരുത്. സമന്വയിപ്പിച്ച ക്രെഡൻഷ്യലുകൾ മാത്രം ഉപയോഗിക്കുന്ന സന്ദർഭങ്ങളിൽ, `OMNIROUTE_TOKEN_REFRESH_PASSIVE_PROVIDERS=codex` (അപരനാമം `cx`) സജ്ജമാക്കുക. ഒറ്റ റൊട്ടേഷൻ ഉടമയിൽ ഇത് സജ്ജമാക്കാതെ വിടുക. ഓരോ പ്രക്രിയയ്ക്കും അതിൻ്റേതായ `DATA_DIR` ആവശ്യമാണ്; ഈ ഓപ്ഷൻ SQLite പങ്കിടുകയോ ടോക്കൺ സിൻക്രൊണൈസേഷനോ വിതരണം ചെയ്ത ലോക്കോ നൽകുകയോ ചെയ്യുന്നില്ല.

ഒരു പുതുക്കൽ ആവശ്യമായി വരുമ്പോൾ നിഷ്ക്രിയ ഉദാഹരണം കണക്ഷൻ വീണ്ടും വായിക്കുകയും കാലഹരണപ്പെടാത്ത മറ്റൊരു ആക്സസ് ടോക്കൺ മാത്രം സ്വീകരിക്കുകയും ചെയ്യുന്നു. അല്ലെങ്കിൽ, കണക്ഷൻ കാലഹരണപ്പെടാതെ അല്ലെങ്കിൽ നിർജ്ജീവമാക്കാതെ അല്ലെങ്കിൽ പുതുക്കൽ ബ്രേക്കർ പരാജയം കണക്കാക്കാതെ പുതുക്കൽ പ്രവർത്തനരഹിതമാക്കുന്നു. യഥാർത്ഥ അപ്സ്ട്രീം പ്രാമാണീകരണ പരാജയങ്ങൾ ഇപ്പോഴും സാധാരണ പരാജയ അക്കൗണ്ടിംഗ്, എക്സ്പോണൻഷ്യൽ കൂൾഡൗൺ, സാധാരണ ക്ലയൻ്റ് പിശക് എന്നിവ ഉപയോഗിക്കുന്നു; അക്കൗണ്ട് നിർജ്ജീവമാക്കൽ ശാശ്വതമായി തുടരുന്നു. ആക്സസ് ടോക്കണുകൾ കാലഹരണപ്പെടുന്നതിന് മുമ്പ് ഉടമയുടെ റൊട്ടേറ്റഡ് ടോക്കണുകൾ സമന്വയിപ്പിക്കുക (ഡിഫോൾട്ട് പ്രോആക്ടീവ് റിഫ്രഷ് ലീഡ് അഞ്ച് മിനിറ്റാണ്), അല്ലെങ്കിൽ Codex auth ഫയൽ വീണ്ടും ഇറക്കുമതി ചെയ്യുക. നിഷ്ക്രിയ ഇമ്പോർട്ടുകൾ, ടോക്കൺ എൻഡ് പോയിൻ്റിൽ സാധൂകരിക്കാതെ വിതരണം ചെയ്ത ടോക്കണുകളെ സംഭരിക്കുന്നു. മാനുവൽ dashboard/API പുതുക്കൽ `409 refresh_disabled` തിരികെ നൽകുന്നു; പുതിയ OAuth ലോഗിനുകൾക്ക് മാറ്റമില്ല. [പരിസ്ഥിതി റഫറൻസ്](../reference/ENVIRONMENT.md#passive-codex-token-refresh) കാണുക.

ഒരു നോഡ് പ്രക്രിയയാണ്** ഒരു V8 കൂമ്പാരം** . രണ്ട് ഓവർലാപ്പിംഗ് ~ 3 MiB / ~ 750k-ടോക്കൺ കോഡിംഗ്-ഏജൻ്റ് `POST /v1/responses` (RTK + Caveman) ആ കൂമ്പാരം ~ 12 Gi (`FATAL ERROR: Reached heap limit`) ൽ നിർത്തലാക്കുകയും OOM a 16 Gi cgroup ലേക്ക് നയിക്കുകയും ചെയ്യാം. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) കാണുക. ആ അളവ് എ** മെമ്മറി-ബജറ്റ്** മുന്നറിയിപ്പ്, രണ്ട് ഒരേസമയം നീളമുള്ള `/v1/responses` ഉള്ള ഒരു ഉൽപ്പന്നമല്ല. ഹെവിവെയ്റ്റ് ചാറ്റ് പ്രവേശനം, അതേ V8/cgroup സീലിംഗ് — ൽ നിന്ന് വലുപ്പമുള്ള ഒരു സ്വയമേവയുള്ള ഇൻജസ്റ്റ് ബൈറ്റ് ബഡ്ജറ്റ് (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) മുഖേന ഗേറ്റ് ചെയ്യപ്പെടുന്നു, അത് ഇതിനകം വലിപ്പമുള്ള ഒരു പ്രക്രിയയിൽ മുകളിലേക്ക് (അല്ലെങ്കിൽ ലെഗസി `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` അഭ്യർത്ഥന-കൗണ്ട് ക്യാപ് സജ്ജീകരിക്കുന്നത്) അബോർട്ട് വീണ്ടും അവതരിപ്പിക്കുന്നു. ചെറിയ ചാറ്റുകൾ, `/healthz`, `/v1/models`, MCP എന്നിവയാണ്** അല്ല** ആ തൊപ്പിയിൽ.

### ഒരു-പ്രക്രിയ: രണ്ടിൽ കൂടുതൽ നീളമുള്ള `/v1/responses`

എ** ആരോഗ്യമുള്ള** പ്രക്രിയ ( `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ന് താഴെയുള്ള കൂമ്പാരം , സ്ഥിരസ്ഥിതി `0.75`)** മെയ്** പ്രോസസ്-വൈഡ് ഇൻഫ്ലൈറ്റ്-ബൈറ്റ് ബജറ്റിന് (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ഇപ്പോഴും ഇടമുണ്ടെങ്കിൽ രണ്ടിൽ കൂടുതൽ ഒരേസമയം നീളമുള്ള `POST /v1/responses` പ്രവർത്തിപ്പിക്കുക. `OMNIROUTE_CHAT_LARGE_BODY_BYTES` അതിനു മുകളിലോ ഉള്ള ബോഡികൾ (സ്ഥിരസ്ഥിതി 256 KiB) സ്ട്രക്ച്ചർ-ഹെവി അഭ്യർത്ഥനകൾക്ക് സമാനമായ ഹെവിവെയ്റ്റ് പാട്ടം എടുക്കുകയും അതേ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` എസ്കേപ്പ് (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ഉപയോഗിക്കുകയും ചെയ്യുന്നു. പതിനായിരക്കണക്കിന് നീളമുള്ള SSE ക്ലയൻ്റുകൾ (ഓപ്പറേറ്റർമാർക്ക് പലപ്പോഴും 40-50 ആവശ്യമാണ്) a** മെമ്മറി-ബജറ്റ്** ചോദ്യം — വലിപ്പം കൂമ്പാരം + primary/headroom സ്ലോട്ടുകൾ + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` — ഒരു ഹാർഡ് "പരമാവധി 2" ഉൽപ്പന്ന പരിധി അല്ല. വീണ്ടും ശ്രമിക്കാവുന്ന `503` ഉപയോഗിച്ച് സമ്മർദ്ദം ചെലുത്തിയ ഒരു കൂമ്പാരം ഇപ്പോഴും ചൊരിയുന്നു, അതിനാൽ #7849 തിരികെ വരില്ല.

സെഷൻ-ടു-അക്കൗണ്ട് അഫിനിറ്റി Redis വഴിയും പങ്കിടാൻ കഴിയും: ഓരോ പ്രക്രിയയിലും ഒരേ `REDIS_KEY_PREFIX`, പോസിറ്റീവ് `sessionAffinityTtlMs` ക്രമീകരണം എന്നിവ ഉപയോഗിച്ച് `OMNIROUTE_SESSION_AFFINITY_STORE=redis`, `REDIS_URL` എന്നിവ സജ്ജമാക്കുക. ഓരോ പ്രോസസ്സിൻ്റെയും യോഗ്യമായ ലോക്കൽ കണക്ഷനിലേക്ക് പിന്നുകൾ ഹാഷ് ചെയ്ത ഉപയോഗ-അക്കൗണ്ട് ഐഡൻ്റിറ്റികൾ പരിഹരിക്കുന്നു, അതിനാൽ പൊരുത്തപ്പെടുന്ന ഐഡൻ്റിറ്റി മെറ്റാഡാറ്റയുള്ള OAuth അക്കൗണ്ടുകൾക്ക് പൊരുത്തപ്പെടുന്ന കണക്ഷൻ IDs ആവശ്യമില്ല. പിൻ റെസല്യൂഷനിലും ഗാർഡഡ് എവിക്ഷനിലും വൈരുദ്ധ്യമുള്ള ലോക്കൽ IDs നേക്കാൾ അറിയപ്പെടുന്ന അക്കൗണ്ട് ഐഡൻ്റിറ്റികൾ മുൻഗണന നൽകുന്നു; ഐഡൻ്റിറ്റി ഇല്ലാത്ത രേഖകൾ (അല്ലെങ്കിൽ ഐഡൻ്റിറ്റി ഇല്ലാത്ത കുടിയൊഴിപ്പിക്കൽ വിളിക്കുന്നവർ) ലെഗസി ID ഗാർഡ് നിലനിർത്തുന്നു. സ്ഥിരമായ ഉപയോഗ ഐഡൻ്റിറ്റി ഇല്ലാത്ത അക്കൗണ്ടുകൾക്ക് ഇപ്പോഴും പൊരുത്തപ്പെടൽ IDs ആവശ്യമാണ്. Redis പിശകുകൾ അല്ലെങ്കിൽ 100 ms-ൽ കൂടുതലുള്ള കോളുകൾ ലോക്കൽ SQLite ലേക്ക് മടങ്ങുന്നു. ഓരോ Redis അഫിനിറ്റി സ്റ്റോറും മികച്ച പ്രവർത്തനങ്ങളെ 8-ൽ പരിമിതപ്പെടുത്തുന്നു, Redis നിറയുമ്പോൾ ഉടനടി ബൈപാസ് ചെയ്യുന്നു, കൂടാതെ കോളർ സമയപരിധിയിലല്ല, അടിസ്ഥാന ജോലി തീർന്നാൽ മാത്രം സ്ലോട്ടുകൾ റിലീസ് ചെയ്യുന്നു. ഒരു Redis ഔട്ടേജ് സമയത്ത് പങ്കിട്ട സത്യമൊന്നുമില്ല: ഓരോ സംഭവവും അതിൻ്റേതായ പ്രാദേശിക ബന്ധത്തിലേക്ക് മടങ്ങുന്നു, സെഷനുകൾ ഓരോ തവണയും വീണ്ടും പിൻ ചെയ്തേക്കാം, കൂടാതെ സംഭവങ്ങൾ വ്യതിചലിച്ചേക്കാം. സ്റ്റിക്കിനസ് വീണ്ടെടുക്കുമ്പോൾ Redis വഴി വീണ്ടും ഒത്തുചേരുന്നു. ടൈംഔട്ട് ബൗണ്ടുകൾ കാത്തിരിപ്പാണ്, അയച്ച EVAL അല്ല, അത് ഫാൾബാക്ക് കഴിഞ്ഞ് വന്നേക്കാം. റൂട്ടിംഗ് റൈറ്റുകൾ റൂട്ടിംഗ് തീരുമാനത്തിലൂടെ നിരീക്ഷിച്ച കൃത്യമായ മൂല്യത്തെ താരതമ്യം ചെയ്യുന്നു, ഒരു പുതിയ മ്യൂട്ടേഷൻ-ടൈം റീഡല്ല; ഒരു നിരീക്ഷിച്ച മിസ് അല്ലെങ്കിൽ ഒരു SQLite ഫാൾബാക്ക് നിരീക്ഷണം ഒരു അബ്സെൻ്റ് Redis കീ ആയി താരതമ്യം ചെയ്യുന്നു. കാലഹരണപ്പെട്ട പിന്നുകൾ ഒരു CAS ൽ മാറ്റിസ്ഥാപിക്കുന്നു, അതിനാൽ ഒരു വൈകിയുള്ള കമാൻഡിന് പുതിയതും വ്യത്യസ്തവുമായ പിൻ മാറ്റിസ്ഥാപിക്കാനോ ഇല്ലാതാക്കാനോ കഴിയില്ല. Redis മൂല്യവും ശേഷിക്കുന്ന സെർവറും TTL ആറ്റോമിക് റിട്ടേൺ ചെയ്യുന്നു; പോസിറ്റീവ് PTTL (അല്ലെങ്കിൽ കാലഹരണപ്പെടില്ല) ലൈവ് നെസ് നിർണ്ണയിക്കുന്നു, എഴുത്തുകാരൻ്റെ JSON ടൈംസ്റ്റാമ്പോ വായനക്കാരൻ്റെ ക്ലോക്കോ അല്ല. പ്രാദേശിക സ്നാപ്പ്ഷോട്ടുകൾ ഒരു പ്രാദേശിക സമയപരിധി വരെ ശേഷിക്കുന്ന TTL മാപ്പ്; നിലവിലുള്ള JSON കീകൾ റീഡബിൾ ആയി തുടരുകയും അവയുടെ റോ ബൈറ്റുകൾ CAS നിലനിർത്തുകയും ചെയ്യുന്നു. ഉത്തരം നൽകുമ്പോൾ സത്യത്തിൻ്റെ ഏക ഉറവിടം Redis ആണ്. സ്ഥിരീകരിച്ച പങ്കിട്ട അപ്സെർട്ടുകളും സ്പർശനങ്ങളും ഇല്ലാതാക്കലും പ്രാദേശിക എൻട്രി നീക്കംചെയ്യുന്നു, ഒരിക്കലും അത് ഇൻസ്റ്റാൾ ചെയ്യുകയോ പുതുക്കുകയോ ചെയ്യരുത്. Redis പാതയിലെ SQLite Redis പിശകുകൾ, ടൈംഔട്ടുകൾ അല്ലെങ്കിൽ അഡ്മിഷൻ സാച്ചുറേഷൻ എന്നിവയിൽ നിന്നുള്ള ഈ സംഭവത്തിൻ്റെ സ്വന്തം ഫാൾബാക്ക് തീരുമാനങ്ങൾ മാത്രമേ കൈവശം വച്ചിട്ടുള്ളൂ, മുമ്പത്തെപ്പോലെ TTL-ബൗണ്ടഡ്. പിന്നീടുള്ള ഔട്ടേജിൽ ഒരു ലോക്കൽ പിൻ നഷ്ടപ്പെടുമ്പോൾ ഒരു പുതിയ പിക്കിന് (ഒരു പ്രോംപ്റ്റ്-കാഷെ മിസ്) ചിലവാകും, തെറ്റായതോ പുറത്താക്കപ്പെട്ടതോ ആയ അക്കൗണ്ടല്ല. നിരസിക്കപ്പെട്ട അപ്സെറ്റുകൾ പങ്കിട്ട വിജയിയെയും അതിൻ്റെ ശേഷിക്കുന്ന TTL നെയും ആറ്റോമികമായി തിരികെ നൽകുന്നു: സാധാരണ തിരഞ്ഞെടുപ്പ് മാപ്പ് ചെയ്ത ലോക്കൽ ഡെഡ്ലൈൻ വീണ്ടും പരിശോധിക്കുകയും ഇപ്പോഴും തത്സമയ യോഗ്യതയുള്ള വിജയിയെ ഉപയോഗിക്കുകയും സ്പർശിക്കുകയും മറ്റൊരു പങ്കിട്ട റൈറ്റില്ലാതെ ആ അക്കൗണ്ടിലേക്ക് ലോഗ് ചെയ്യുകയും ചെയ്യുന്നു. ഇത് ലഭ്യമല്ലെങ്കിൽ, തിരഞ്ഞെടുക്കൽ പ്രാദേശിക സ്ഥാനാർത്ഥിയെ നിലനിർത്തുകയും പങ്കിട്ട പിൻ മാറ്റാതെ വിടുകയും ഒരു ഡീബഗ് സന്ദേശം പുറപ്പെടുവിക്കുകയും ചെയ്യുന്നു. നിരസിച്ച CAS SQLite എഴുതുന്നില്ല; Redis പിശകുകൾ, കാലഹരണപ്പെടലുകൾ അല്ലെങ്കിൽ പ്രവേശന സാച്ചുറേഷൻ എന്നിവയ്ക്ക് പകരം നിലവിലുള്ള പ്രാദേശിക പ്രവർത്തനം ബാധകമാണ്. അയച്ച മ്യൂട്ടേഷൻ്റെ മറുപടി കാലഹരണപ്പെട്ടതിന് ശേഷം (അംഗീകരിച്ചോ, നിരസിച്ചതോ അല്ലെങ്കിൽ പിശകോ) വന്നാൽ, ഒരു സിൻക്രണസ് കൃത്യമായ സീരിയലൈസ്ഡ്-വാല്യൂ താരതമ്യം-ഇല്ലാതാക്കൽ, ബൈറ്റ്-സമാനമായ ടൈംഔട്ട് ഫോൾബാക്ക് വരി മാത്രം നീക്കംചെയ്യുന്നു. ആ താരതമ്യവും ഇല്ലാതാക്കലും തമ്മിൽ കാത്തിരിപ്പില്ല; ഒരു പുതിയ ഔട്ടേജ് എഴുത്ത് സംരക്ഷിക്കപ്പെട്ടിരിക്കുന്നു. ഗാർഡഡ് എവിക്ഷൻ, പരാജയപ്പെട്ട അക്കൗണ്ടിൻ്റെ സ്വന്തം ലോക്കൽ പിൻ Redis ഡൗൺ ചെയ്താലും നീക്കം ചെയ്യുന്നു, ഒപ്പം പങ്കിട്ട ഒഴിപ്പിക്കൽ സ്ഥിരീകരിച്ചതിന് ശേഷം അത് വീണ്ടും വൃത്തിയാക്കുന്നു. പങ്കിട്ട വിജയങ്ങൾ ഒരിക്കലും SQLite എഴുതാത്തതിനാൽ നേരത്തെ പങ്കിട്ട മറുപടികൾ തീർപ്പാക്കാത്തതിനാൽ പുറത്താക്കപ്പെട്ട ലോക്കൽ പിൻ പുനഃസ്ഥാപിക്കാൻ കഴിയില്ല. പിന്നീടുള്ള ഔട്ടേജ് ഫാൾബാക്ക് ഒരു അക്കൗണ്ട് റീപിൻ ചെയ്യാം; പിന്നീട് അംഗീകരിക്കപ്പെട്ട ഒരു പങ്കിട്ട എഴുത്ത് Redis ൽ മാത്രമേ നിലവിലുള്ളൂ. Redis മിസ്സുകൾ പ്രാദേശിക ഫാൾബാക്ക് അവസ്ഥ പരിശോധിക്കുന്നില്ല. ഡ്രൈവർ ഓഫായാൽ, പുതുതായി തിരഞ്ഞെടുത്ത പിന്നുകൾ ലെഗസി ഫോർ-ഫീൽഡ് SQLite JSON ആകൃതി നിലനിർത്തുന്നു; Redis റൂട്ടിംഗ് മാത്രമേ ഹാഷ്ഡ് അക്കൗണ്ട് ഐഡൻ്റിറ്റി ചേർക്കൂ. പ്രീഫെച്ച്ഡ് പിന്നുകൾ അവയുടെ കാലഹരണപ്പെടൽ അതിർത്തിയിൽ വീണ്ടും പരിശോധിക്കുന്നു. Redis നോൺ-ലീസ് സെലക്ഷൻ സ്റ്റോർ വീണ്ടും വായിക്കുന്നു, എന്നാൽ സിൻക്രണസ് ലീസ് പ്ലാനിംഗിന് പ്രീഫെച്ചിനും പ്ലാനിംഗിനും ഇടയിൽ ഒഴിവാക്കിയ പിൻ ഉപയോഗിക്കാനാകും (ഒരു അംഗീകൃത മികച്ച പ്രയത്ന വിൻഡോ). ഒരു ദീർഘകാല ക്ലെയിമിന് ശേഷം ഒരു വാടക കമ്മിറ്റിന് അക്കൗണ്ടുകൾ മാറ്റാൻ കഴിയില്ല: നിരസിച്ച അപ്സെർട്ടിൽ അത് ക്ലെയിം ചെയ്ത സ്ഥാനാർത്ഥിയെ ആ അഭ്യർത്ഥനയ്ക്കായി മാത്രം നിലനിർത്തുകയും പങ്കിട്ട വിജയിയെ സ്പർശിക്കാതെ വിടുകയും ചെയ്യുന്നു, അതിനാൽ സന്ദർഭങ്ങളിലുടനീളം കരാർ ആ പാതയിൽ പരിമിതപ്പെടുത്തിയിരിക്കുന്നു. ബാക്കിയുള്ള പട്ടിക ഇപ്പോഴും ബാധകമാണ്: ഇത് കോംബോ സെഷൻ സ്റ്റിക്കിനസ്, നേറ്റീവ് Codex ടേൺ പിൻസ്, അക്കൗണ്ട് സെമാഫോറുകൾ, ലോക്കൗട്ടുകൾ, ചെലവ് പരിധികൾ, കോൺഫിഗറേഷൻ അല്ലെങ്കിൽ കോൾ ലോഗുകൾ എന്നിവ പങ്കിടില്ല.

ഹാർഡ്വെയർ: പെർ-ഇൻസ്റ്റൻസ് കൺകറൻ്റ് ലോംഗ് `/v1/responses` a ആണ്** മെമ്മറി-ബജറ്റ്** ചോദ്യം (ഹീപ്പ് + ഇൻഫ്ലൈറ്റ്-ബൈറ്റ് / #10110). `N` സ്വതന്ത്ര `DATA_DIR` s ഇപ്പോഴും കൂമ്പാരങ്ങൾ വർദ്ധിപ്പിക്കുന്നു: ഹോസ്റ്റ് RAM `N × cgroup` കവർ ചെയ്യണം, "N = 8 ഉള്ള ഒരു 16 Gi പോഡ്" അല്ല. ഒരു SQLite ഫയലിൽ ഒരിക്കലും `replicas > 1`.

സ്കെച്ച് രചിക്കുക (രണ്ട് കൂമ്പാരങ്ങൾ, രണ്ട് വാല്യങ്ങൾ — അല്ല `deploy.replicas: 2`):

```yaml
services:

    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

ഇൻ-പ്രോസസ് ഡെൻസിറ്റി ( HTTP ഐസൊലേറ്റിൽ നിന്നുള്ള കംപ്രഷൻ) [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ആണ്. പങ്കിട്ട ഡ്യൂറബിൾ സ്റ്റേറ്റിലെ ഒരു ലോജിക്കൽ ക്ലസ്റ്റർ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ആണ്.

`User location is not supported for the API use.` എന്ന സന്ദേശവും നൽകാനാകും. ഹോസ്റ്റിൽ ഒരു അഭ്യർത്ഥന വിജയിക്കുന്നത്
കണ്ടെയ്നർ അതേ ഔട്ട്ബൗണ്ട് റൂട്ട് ഉപയോഗിക്കുന്നു എന്ന് തെളിയിക്കുന്നില്ല. DNS ക്രമീകരണം,
IPv4/IPv6 കണക്റ്റിവിറ്റി, VPN റൂട്ടിംഗ്, കോൺഫിഗർ ചെയ്ത പ്രോക്സികൾ എന്നിവ വ്യത്യസ്തമായിരിക്കാം.
[Google പിന്തുണയ്ക്കുന്ന പ്രദേശങ്ങൾ](https://ai.google.dev/gemini-api/docs/available-regions)
എന്നതോടൊപ്പം യഥാർത്ഥ കണക്ഷൻ റൂട്ടും പരിശോധിക്കുക; ഈ പിശക് മാത്രം ഒരു തെറ്റായ API കീ ആണെന്ന് സൂചിപ്പിക്കുന്നില്ല.

### കണക്ഷൻ-നിർദ്ദിഷ്ട പ്രോക്സിക്ക് മുൻഗണന നൽകുക

ബാധിച്ച Gemini കണക്ഷനായി OmniRoute-ന്റെ [ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ഉപയോഗിക്കുക, തുടർന്ന് അതേ മോഡൽ ഉപയോഗിച്ച് **കണക്ഷൻ പരിശോധിക്കുക** എന്നതും ഒരു ചെറിയ അഭ്യർത്ഥനയും
വീണ്ടും നടത്തുക. ഇത് റൂട്ടിംഗ് മാറ്റം ആ കണക്ഷനിൽ മാത്രമായി പരിമിതപ്പെടുത്തുന്നു. പ്രോക്സി
കണ്ടെയ്നറിൽ നിന്ന് ആക്സസ് ചെയ്യാനാകുന്നുണ്ടെന്നും കണക്ഷൻ യഥാർത്ഥത്തിൽ അതിനെ തിരഞ്ഞെടുക്കുന്നുണ്ടെന്നും
സ്ഥിരീകരിക്കുക. റൂട്ട് മാറ്റുന്നത് അപ്സ്ട്രീം പ്രാദേശിക യോഗ്യത ഉറപ്പാക്കുന്നില്ല.

### ഹോസ്റ്റിന്റെയും കണ്ടെയ്നറിന്റെയും നെറ്റ്വർക്കിംഗ് താരതമ്യം ചെയ്യുക

ഓതന്റിക്കേറ്റ് ചെയ്ത ഫലങ്ങൾ താരതമ്യം ചെയ്യുമ്പോൾ കീയും മോഡലും അഭ്യർത്ഥനയും ഒരേപോലെ നിലനിർത്തുക; ക്രെഡൻഷ്യലുകൾ,
പ്രോക്സി പാസ്വേഡുകൾ, അല്ലെങ്കിൽ പൂർണ്ണമായ ഓതറൈസേഷൻ ഹെഡറുകൾ ഒരിക്കലും ഒരു ഇഷ്യൂവിൽ
പേസ്റ്റ് ചെയ്യരുത്. ആദ്യം OS റിസോൾവർ ഏതൊക്കെ അഡ്രസ് ഫാമിലികളാണ് നൽകുന്നതെന്ന് പരിശോധിക്കുക; ഹോസ്റ്റിലും
കണ്ടെയ്നറിനുള്ളിലും ഒരേ കമാൻഡ് ഉപയോഗിക്കുക:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` എന്നത് നിങ്ങൾ പ്രവർത്തിപ്പിക്കുന്ന സർവീസ് ഉപയോഗിച്ച് മാറ്റിസ്ഥാപിക്കുക (ഉദാഹരണത്തിന്, `omniroute-web`). ഈ
കമാൻഡുകൾ ക്രെഡൻഷ്യലുകളോ IP വിലാസങ്ങളോ ഇല്ലാതെ അഡ്രസ് ഫാമിലികൾ പ്രിന്റ് ചെയ്യുന്നു. മടക്കിനൽകുന്ന `6`
ഒരു IPv6 DNS ഫലം മാത്രമാണ് കാണിക്കുന്നത്: അത് ഉപയോഗിക്കാനാകുന്ന IPv6 റൂട്ടോ API ആക്സസോ
തെളിയിക്കുന്നില്ല. `curl` ഇൻസ്റ്റാൾ ചെയ്തിട്ടുള്ളിടത്ത്, രണ്ട് പരിതസ്ഥിതികളിലും
`curl -4 -I https://generativelanguage.googleapis.com` എന്നത്
`curl -6 -I https://generativelanguage.googleapis.com` എന്നതുമായി താരതമ്യം ചെയ്യുക.
ഓതന്റിക്കേറ്റ് ചെയ്യാത്ത പിശകാണെങ്കിലും, ഒരു HTTP പ്രതികരണം ആ പരിശോധനയ്ക്കുള്ള കണക്റ്റിവിറ്റി തെളിയിക്കുന്നു;
ഓതന്റിക്കേറ്റ് ചെയ്ത മോഡൽ അഭ്യർത്ഥന മാത്രമാണ് Gemini യോഗ്യത പരിശോധിക്കുന്നത്.

### ഹോസ്റ്റ്-തല പകരമാർഗം: പ്രവർത്തിക്കുന്ന IPv6-ഉം റിസോൾവർ നയവും

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762)-ന്റെ റിപ്പോർട്ടർ കണ്ടെയ്നർ IPv6 പ്രവർത്തനക്ഷമമാക്കുകയും glibc അഡ്രസ്
തിരഞ്ഞെടുക്കൽ മാറ്റുകയും ചെയ്തുകൊണ്ട് അവരുടെ പരിതസ്ഥിതിയിൽ ആക്സസ് പുനഃസ്ഥാപിച്ചു.
ഇതിനെ പരിതസ്ഥിതി-നിർദ്ദിഷ്ടമായ ഒരു പകരമാർഗമായി കണക്കാക്കുക. റിസോൾവർ മുൻഗണനകൾ ക്രമീകരിക്കുന്നതിന് മുമ്പ്
ഹോസ്റ്റിൽ പ്രവർത്തിക്കുന്ന IPv6, കണ്ടെയ്നർ എഗ്രസ്/റൂട്ടിംഗ്, ഫയർവാൾ നിയമങ്ങൾ എന്നിവ സ്ഥിരീകരിക്കുക.
ഒരു സ്വകാര്യ ULA വിലാസം മാത്രമുള്ളത് പൊതു IPv6 കണക്റ്റിവിറ്റി സ്ഥാപിക്കുന്നില്ല.

Compose-ന്റെ ഡിഫോൾട്ട് നെറ്റ്വർക്കിൽ ഇതിനകം അറ്റാച്ച് ചെയ്തിരിക്കുന്ന സർവീസുകൾക്ക്, ഈ ഫ്രാഗ്മെന്റ്
ആ നെറ്റ്വർക്കിൽ IPv6 പ്രവർത്തനക്ഷമമാക്കുന്നു; നിങ്ങളുടെ സർവീസിന്റെ ശേഷിക്കുന്ന ഭാഗങ്ങളും പോർട്ടുകളും വോള്യങ്ങളും കോൺഫിഗറേഷനും നിലനിർത്തുക:

```yaml
networks:
  default:
    enable_ipv6: true
```

നാമകരണം ചെയ്ത നെറ്റ്വർക്കാണെങ്കിൽ, സർവീസ് യഥാർത്ഥത്തിൽ ചേരുന്ന നെറ്റ്വർക്കിൽ ഇത് പ്രവർത്തനക്ഷമമാക്കുക. Docker-ന്
ഒരു ULA സബ്നെറ്റ് അനുവദിക്കാനാകും; നിങ്ങളുടെ നെറ്റ്വർക്കിന് ആവശ്യമുള്ളപ്പോൾ മാത്രം, മറ്റൊന്നുമായി ഓവർലാപ്പ് ചെയ്യാത്ത വ്യക്തമായൊരു സബ്നെറ്റ്
തിരഞ്ഞെടുക്കുക. [Docker IPv6 നെറ്റ്വർക്കിംഗ്](https://docs.docker.com/engine/daemon/ipv6/)
എന്നതും [Compose നെറ്റ്വർക്ക് ഓപ്ഷനുകൾ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) എന്നതും കാണുക.

ഒരു **glibc-അധിഷ്ഠിത ഇമേജിൽ**, `/etc/gai.conf`-ന് അഡ്രസ് തിരഞ്ഞെടുക്കൽ മാറ്റാനാകും. നിലവിലെ
റെപ്പോസിറ്ററി Dockerfile Debian ഉപയോഗിക്കുന്നു; ഇഷ്ടാനുസൃത musl-അധിഷ്ഠിത ഇമേജുകൾ ഈ സംവിധാനം പങ്കിടുന്നില്ല.
റിപ്പോർട്ട് ചെയ്ത ക്രമീകരണം ULA ലേബൽ `label fc00::/7 6` എന്നതിൽ നിന്ന്
`label fc00::/7 1` എന്നതിലേക്ക് മാറ്റുന്നു. ഇമേജിന്റെ പൂർണ്ണ നയ പട്ടികയിൽ നിന്ന് ആരംഭിക്കുകയും അതിലെ മറ്റ്
എൻട്രികൾ നിലനിർത്തുകയും ചെയ്യുക: ഒരു `label` അല്ലെങ്കിൽ `precedence` എൻട്രി ചേർക്കുന്നത് ആ ഡിഫോൾട്ട് പട്ടികയെ മാറ്റിസ്ഥാപിക്കുന്നു, അതിനാൽ മാറ്റിയ വരി
മാത്രം അടങ്ങിയ ഫയൽ മതിയാകില്ല.
[glibc കോൺഫിഗറേഷൻ റഫറൻസ്](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ആ സെമാന്റിക്സ് രേഖപ്പെടുത്തുന്നു. അവലോകനം ചെയ്ത ഫയൽ `/etc/gai.conf`-ൽ റീഡ്-ഒൺലി ആയി ബൈൻഡ്-മൗണ്ട്
ചെയ്ത ശേഷം, അത് പ്രയോഗിക്കുന്നതിനായി സർവീസ് പുനഃസൃഷ്ടിക്കുക.

ഇത് **ആ കണ്ടെയ്നറിലെ എല്ലാ ഔട്ട്ബൗണ്ട് ട്രാഫിക്കിനുമുള്ള** OS അഡ്രസ് തിരഞ്ഞെടുക്കൽ മാറ്റുന്നു.
ഇത് എല്ലാ ആപ്ലിക്കേഷനെയും IPv6 തിരഞ്ഞെടുക്കാൻ നിർബന്ധിക്കുന്നില്ല: Node-ന്റെ DNS ക്രമവും കണക്ഷൻ
തിരഞ്ഞെടുക്കലും പ്രസക്തമാണ്. പ്രത്യേകിച്ച്, `--dns-result-order=ipv4first` IPv4-ന് മുൻഗണന നൽകുന്നു,
അതിനാൽ IPv4-മാത്രമുള്ള പരാജയത്തിന് അതൊരു പരിഹാരമല്ല. [Node DNS ക്രമീകരണം](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) കാണുക.

ഹോസ്റ്റ്-തല മാറ്റങ്ങൾക്ക് ശേഷം Gemini-യും നിങ്ങളുടെ മറ്റ് പ്രൊവൈഡർമാരും വീണ്ടും പരിശോധിക്കുക. പഴയ നിലയിലേക്ക് മടങ്ങാൻ,
ഇഷ്ടാനുസൃത `gai.conf` മൗണ്ട് നീക്കംചെയ്യുക, മുമ്പത്തെ നെറ്റ്വർക്ക് കോൺഫിഗറേഷൻ പുനഃസ്ഥാപിക്കുക, കൂടാതെ
ഒരു മെയിന്റനൻസ് വിൻഡോയിൽ ബാധിച്ച സർവീസ്/നെറ്റ്വർക്ക് പുനഃസൃഷ്ടിക്കുക. ഒരു നെറ്റ്വർക്ക് പുനഃസൃഷ്ടിക്കുന്നത്
അതിലേക്ക് അറ്റാച്ച് ചെയ്തിരിക്കുന്ന മറ്റ് കണ്ടെയ്നറുകൾക്ക് തടസ്സമുണ്ടാക്കാം; സ്ഥിരമായ ഡാറ്റ വോള്യം ഇല്ലാതാക്കരുത്.

## പ്രധാന കുറിപ്പുകൾ

- **SQLite WAL മോഡ്:** ഏറ്റവും പുതിയ മാറ്റങ്ങൾ `storage.sqlite`-ലേക്ക് checkpoint ചെയ്യാൻ OmniRoute-ന് കഴിയുന്നവിധം `docker stop` പൂർത്തിയാകാൻ അനുവദിക്കണം. ഉൾപ്പെടുത്തിയിട്ടുള്ള Compose ഫയലുകളിൽ ഇതിനകം 40s stop grace period സജ്ജീകരിച്ചിട്ടുണ്ട്. നിങ്ങൾ image നേരിട്ട് പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, `--stop-timeout 40` നിലനിർത്തുക.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** പതിവ്/pre-write backup-കൾ ബാഹ്യമായി കൈകാര്യം ചെയ്യുന്നുണ്ടെങ്കിൽ ഇത് `true` ആയി സജ്ജീകരിക്കുക. നിലവിലുള്ള database migration-കൾക്ക് അവയുടേതായ ദീർഘകാലം നിലനിൽക്കുന്ന സുരക്ഷാ snapshot-ഉം mass-migration guard-ഉം ഇപ്പോഴും ആവശ്യമാണ്.
- **ഡാറ്റ നിലനിർത്തൽ:** container പുനരാരംഭങ്ങൾക്കിടയിലും നിങ്ങളുടെ database, key-കൾ, configuration-കൾ എന്നിവ നിലനിർത്താൻ എല്ലായ്പ്പോഴും `/app/data`-ലേക്ക് ഒരു volume mount ചെയ്യുക.
- **പോർട്ട് കോൺഫിഗറേഷൻ:** ഡിഫോൾട്ട് `20128` port മാറ്റാൻ `PORT` environment variable override ചെയ്യുക.
