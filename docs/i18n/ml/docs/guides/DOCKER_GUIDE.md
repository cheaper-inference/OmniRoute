## വേഗത്തിലുള്ള പ്രവർത്തനം

> **ഒരൊറ്റ കമാൻഡ് ഉപയോഗിച്ച് സ്വയം ഹോസ്റ്റ് ചെയ്യണോ?**
> [സ്വയം ഹോസ്റ്റ് ചെയ്യുന്നതിനുള്ള ഗൈഡ്](../getting-started/SELF_HOST_GUIDE.md) കാണുക —
> `docker compose -f docker-compose.selfhost.yml up -d` (പ്രസിദ്ധീകരിച്ച ഇമേജ് +
> Redis, ലൂപ്പ്ബാക്കിൽ മാത്രം, പ്രൊഫൈൽ തിരഞ്ഞെടുക്കേണ്ടതില്ല). ഇതിനകം മറ്റെവിടെയെങ്കിലും Redis പ്രവർത്തിപ്പിക്കുന്ന
> ഉപയോക്താക്കൾക്കായുള്ള ഒറ്റ കണ്ടെയ്നർ രീതിയാണ് താഴെയുള്ള വേഗത്തിലുള്ള പ്രവർത്തനം.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## എൻവയോൺമെന്റ് ഫയലിനൊപ്പം

```bash
# ആദ്യം .env പകർത്തി എഡിറ്റ് ചെയ്യുക
cp .env.example .env

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Docker Compose

```bash
# അടിസ്ഥാന പ്രൊഫൈൽ (CLI ടൂളുകളില്ല)
docker compose --profile base up -d

# CLI പ്രൊഫൈൽ (Claude Code, Codex, OpenClaw എന്നിവ ബിൽറ്റ്-ഇൻ)
docker compose --profile cli up -d

# ഹോസ്റ്റ് പ്രൊഫൈൽ (പ്രധാനമായും Linux-നായി; ഹോസ്റ്റ് CLI ബൈനറികളെ റീഡ്-ഒൺലിയായി മൗണ്ട് ചെയ്യുന്നു)
docker compose --profile host up -d

# വെബ് പ്രൊഫൈൽ (വെബ്-സെഷൻ പ്രൊവൈഡർമാർക്കായി Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI സൈഡ്കാർ സംയോജിപ്പിക്കുക
docker compose --profile cli --profile cliproxyapi up -d
```

## ലഭ്യമായ പ്രൊഫൈലുകൾ

പ്രധാന വിന്യാസ രീതികൾക്കായുള്ള Compose പ്രൊഫൈലുകൾ OmniRoute-നൊപ്പം ലഭ്യമാണ്. നിങ്ങളുടെ പരിസ്ഥിതിക്ക് യോജിക്കുന്ന ഒന്ന് തിരഞ്ഞെടുക്കുക.

| പ്രൊഫൈൽ            | സേവനം            | എപ്പോൾ ഉപയോഗിക്കണം                                                                                                                                                 | കമാൻഡ്                                       |
| ------------------ | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| `base` (ഡിഫോൾട്ട്) | `omniroute-base` | ഹെഡ്ലെസ് സെർവർ / മിനിമൽ റൺടൈം; പ്രൊവൈഡർ CLI-കൾ ഉൾപ്പെടുത്തിയിട്ടില്ല                                                                                               | `docker compose --profile base up -d`        |
| `cli`              | `omniroute-cli`  | `omniroute providers/setup/doctor`, ഉൾപ്പെടുത്തിയ CLI-കൾ (Codex, Claude Code, Droid, OpenClaw) എന്നിവ വിളിക്കുന്ന ഏജന്റിക് വർക്ക്ഫ്ലോകൾ                            | `docker compose --profile cli up -d`         |
| `host`             | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` മുതലായവ റീഡ്-ഒൺലിയായി മൗണ്ട് ചെയ്തുകൊണ്ട് ഹോസ്റ്റ് CLI-കളിലേക്ക് `network_mode` പോലുള്ള ആക്സസ് ആവശ്യമുള്ള Linux ഹോസ്റ്റുകൾ | `docker compose --profile host up -d`        |
| `cliproxyapi`      | `cliproxyapi`    | അപ്സ്ട്രീം CLI പ്രോക്സിയിങ്ങിനായി `8317` പോർട്ടിൽ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) സൈഡ്കാർ പ്രവർത്തിപ്പിക്കുക                           | `docker compose --profile cliproxyapi up -d` |
| `web`              | `omniroute-web`  | ബ്രൗസർ ആവശ്യമുള്ള വെബ്-സെഷൻ പ്രൊവൈഡർമാർ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ബിൽഡ് ചെയ്യുന്നു; Chromium ഉൾപ്പെടുത്തിയിട്ടുണ്ട്)           | `docker compose --profile web up -d`         |

> ഒന്നിലധികം പ്രൊഫൈലുകൾ സംയോജിപ്പിക്കാം: `docker compose --profile cli --profile cliproxyapi up -d`.

## OmniRoute Docker-ൽ പ്രവർത്തിക്കുമ്പോൾ ഹോസ്റ്റ് CLI ടൂളുകൾ ക്രമീകരിക്കൽ

`omniroute setup-codex`, `setup-claude`, `config set <tool>` എന്നിവയും ഡാഷ്ബോർഡിലെ
**കോൺഫിഗറേഷൻ സംരക്ഷിക്കുക** ബട്ടണും `~/.codex/*.config.toml` പോലുള്ള ഫയലുകളിലാണ് എഴുതുന്നത്. CLI യഥാർത്ഥത്തിൽ പ്രവർത്തിക്കുന്ന മെഷീനിൽ മാത്രമാണ് ആ പാതകൾക്ക് പ്രസക്തിയുള്ളത്. അവ കണ്ടെയ്നറിനുള്ളിൽ പ്രവർത്തിപ്പിച്ചാൽ, എഴുത്ത് കണ്ടെയ്നറിന്റെ സ്വന്തം ഹോമിലാണ് (`/home/node` —
ഇമേജ് `USER node` ആയി പ്രവർത്തിക്കുന്നു) നടക്കുക. ഒരു ഹോസ്റ്റ് CLI-യും അത് വായിക്കുകയില്ല; കൂടാതെ കണ്ടെയ്നർ പുനഃസൃഷ്ടിക്കുന്ന നിമിഷം തന്നെ അത് ഉപേക്ഷിക്കപ്പെടുകയും ചെയ്യും.

OmniRoute ഇത് കണ്ടെത്തുകയും നിങ്ങൾക്ക് ഉപയോഗിക്കാനാകാത്ത ഒരു വിജയം റിപ്പോർട്ട് ചെയ്യുന്നതിന് പകരം നിർദ്ദേശങ്ങളോടെ എഴുത്ത് നിരസിക്കുകയും ചെയ്യുന്നു: CLI `2` എന്ന കോഡോടെ പുറത്തുകടക്കും, API `containerEphemeralTarget: true` സഹിതം `422` മറുപടി നൽകും.

### ശുപാർശ ചെയ്യുന്നത്: CLI ഹോസ്റ്റിലും OmniRoute Docker-ലും പ്രവർത്തിപ്പിക്കുക

കണ്ടെയ്നർ API നൽകുന്നു; CLI നിങ്ങളുടെ ഹോസ്റ്റ് ടൂളുകൾ ക്രമീകരിക്കുന്നു.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI-യെ കണ്ടെയ്നറിലേക്ക് ചൂണ്ടിക്കാണിക്കുക
omniroute setup-codex                      # നിങ്ങളുടെ ഹോസ്റ്റിലെ യഥാർത്ഥ ~/.codex-ലേക്ക് എഴുതുന്നു
```

Codex, Claude Code, Cursor അല്ലെങ്കിൽ സമാനമായവ നിങ്ങളുടെ ലാപ്ടോപ്പിൽ പ്രവർത്തിക്കുമ്പോൾ ഇതാണ് ശരിയായ തിരഞ്ഞെടുപ്പ് — സാധാരണയായി ഉപയോഗിക്കുന്ന സജ്ജീകരണവും ഇതുതന്നെയാണ്.

### മറ്റൊരു മാർഗം: ഹോസ്റ്റ് കോൺഫിഗറേഷൻ ഡയറക്ടറികൾ bind-mount ചെയ്യുക (`host` പ്രൊഫൈൽ)

കണ്ടെയ്നർ തന്നെ നിങ്ങളുടെ ഹോസ്റ്റ് കോൺഫിഗറേഷനിൽ എഴുതണമെന്ന് നിങ്ങൾ ആഗ്രഹിക്കുന്നുവെങ്കിൽ, ഡയറക്ടറികൾ mount ചെയ്യുകയും mount root-ലേക്ക് `CLI_CONFIG_HOME` ചൂണ്ടിക്കാണിക്കുകയും ചെയ്യുക. `host` പ്രൊഫൈൽ ഇത് ഇതിനകം ചെയ്യുന്നു:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

ഒരു bind mount ആണ് പാതയെ വിശ്വസനീയമാക്കുന്നത്: OmniRoute
`/proc/self/mountinfo` വായിക്കുകയും mounted പാതകളിലേക്ക് എഴുതാൻ അനുവദിക്കുകയും ചെയ്യുന്നു (കൂടാതെ ചൈൽഡ് ഡയറക്ടറികൾ mount ചെയ്തിട്ടുള്ള ഡയറക്ടറികളിലേക്കും അനുവദിക്കുന്നു; മുകളിൽ കാണിച്ചിരിക്കുന്ന `/host-home` ഘടന കൃത്യമായി ഇതുതന്നെയാണ്), അതേസമയം mount ചെയ്യാത്തവയിലേക്കുള്ള എഴുത്ത് നിരസിക്കുന്നത് തുടരുകയും ചെയ്യുന്നു.

### അടിയന്തര ഒഴിവുവഴി: കണ്ടെയ്നറിന്റെ സ്വന്തം CLI-കൾ ക്രമീകരിക്കുക (വളരെ പരിമിതമായി ഉപയോഗിക്കുക)

CLI-കൾ യഥാർത്ഥത്തിൽ കണ്ടെയ്നറിനുള്ളിൽ തന്നെയാണ് പ്രവർത്തിക്കുന്നതെങ്കിൽ (`cli` പ്രൊഫൈൽ), എഴുത്ത് ഉദ്ദേശ്യപൂർവമായിരിക്കും. ഏതെങ്കിലും `setup-*` കമാൻഡിന് `--allow-container-write` നൽകുക, അല്ലെങ്കിൽ സെർവറിനായി
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` സജ്ജമാക്കുക. കണ്ടെയ്നറിനെ അതിജീവിച്ച് എഴുത്ത് നിലനിൽക്കില്ലെന്ന മുന്നറിയിപ്പോടെ എഴുത്ത് തുടരും.

> **സുരക്ഷാ മുന്നറിയിപ്പ് — `cli` പ്രൊഫൈൽ + `docker.sock` mount.**
> ഹോസ്റ്റ് daemon ഉപയോഗിച്ച് കണ്ടെയ്നറിനുള്ളിലെ auto-updater-ന് stack പുനഃസൃഷ്ടിക്കാൻ കഴിയുന്നതിനായി `cli` പ്രൊഫൈൽ `/var/run/docker.sock` bind-mount ചെയ്യുന്നു
> (`src/lib/system/autoUpdate.ts` ആ socket ഉണ്ടോയെന്ന് പരിശോധിക്കുകയും അത് ഇല്ലെങ്കിൽ
> Docker പാത ഒഴിവാക്കുകയും ചെയ്യുന്നു). ആ socket **ഹോസ്റ്റ്-root വിശ്വാസപരിധിയാണ്**:
> അതിലേക്ക് പ്രവേശിക്കാനാകുന്ന എന്തിനും root ആയി ഹോസ്റ്റ് Docker daemon-നെ നിയന്ത്രിക്കാനാകും — ഹോസ്റ്റിലെ ഏത് കണ്ടെയ്നറും സൃഷ്ടിക്കാനും പരിശോധിക്കാനും നിർത്താനും നീക്കം ചെയ്യാനും അതിന് കഴിയും.
> ഇതിന്റെ പ്രത്യാഘാതങ്ങൾ:
>
> 1. **`cli` പ്രൊഫൈലിന്റെ port ഒരിക്കലും നെറ്റ്വർക്കിലേക്ക് തുറന്നുകാട്ടരുത്.**
>    അത് `127.0.0.1`-ൽ publish ചെയ്യുക (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN-ൽ നിന്ന് എത്തിച്ചേരാവുന്ന ഒരു `cli` പ്രൊഫൈൽ, ഡാഷ്ബോർഡ് തലത്തിലുള്ള ഏതൊരു RCE-യെയും പൂർണ്ണമായ ഹോസ്റ്റ് കൈയേറ്റമാക്കി മാറ്റുന്നു.
> 2. **`cli` പ്രൊഫൈലിലേക്ക് അധിക ഹോസ്റ്റ് ഡയറക്ടറികളൊന്നും bind ചെയ്യരുത്.**
>    Docker socket-നൊപ്പം മറ്റേതെങ്കിലും mount കൂടിയുണ്ടെങ്കിൽ, അത് കണ്ടെയ്നറിന് നിങ്ങളുടെ ഫയൽസിസ്റ്റത്തിലേക്കും ഹോസ്റ്റ് കോൺഫിഗറേഷനിലേക്കും പൂർണ്ണമായ read/write പ്രവേശനം നൽകുന്നു. ഒരു ടൂളിന് ഒരു project കാണേണ്ടതുണ്ടെങ്കിൽ, CLI binary ഉപയോഗിച്ച് അത് പ്രാദേശികമായി പ്രവർത്തിപ്പിക്കുക — `cli` കണ്ടെയ്നറിലേക്ക് അത് mount ചെയ്യരുത്.
>
> കണ്ടെയ്നറിനുള്ളിലെ auto-update ആവശ്യമില്ലെങ്കിൽ, `cli` പ്രൊഫൈൽ പ്രവർത്തനരഹിതമായി നിലനിർത്തുക
> (`COMPOSE_PROFILES=core,redis` അല്ലെങ്കിൽ അതിലും ചുരുങ്ങിയത്). മറ്റ് പ്രൊഫൈലുകൾ
> Docker socket mount ചെയ്യുന്നില്ല.
>
> MITM-നെ ചുറ്റിപ്പറ്റിയുള്ള അനുബന്ധ threat model-നായി `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`-ലേക്ക് compile ചെയ്തിട്ടില്ല) കാണുക; കൂടാതെ
> `codex`/`claude-code`/`droid`/`openclaw` binary provenance chain-നായി
> `docs/security/SUPPLY_CHAIN.md` കാണുക.

## Redis സൈഡ്കാർ

വിതരണം ചെയ്ത നിരക്ക് നിയന്ത്രണത്തിനും പങ്കിട്ട കാഷിനും OmniRoute Redis-നെ ആശ്രയിക്കുന്നു. `redis` സർവീസ് `docker-compose.yml`-ൽ **എല്ലായ്പ്പോഴും നിർവചിച്ചിരിക്കുന്നു** (ഇതിന് പ്രൊഫൈൽ ഗേറ്റ് ഇല്ല), കൂടാതെ മറ്റേതൊരു പ്രൊഫൈലിനോടൊപ്പവും ഇത് ആരംഭിക്കുന്നു.

| വിശദാംശം                   | മൂല്യം                                          |
| -------------------------- | ----------------------------------------------- |
| ഇമേജ്                      | `redis:7-alpine`                                |
| കണ്ടെയ്നറിന്റെ പേര്        | `omniroute-redis`                               |
| ആന്തരിക പോർട്ട്            | `6379`                                          |
| ഹോസ്റ്റ് പോർട്ട് (ഓവർറൈഡ്) | `REDIS_PORT` (സ്ഥിരസ്ഥിതിയായി `6379`)           |
| ഹോസ്റ്റ് ബൈൻഡ് (ഓവർറൈഡ്)   | `REDIS_BIND_HOST` (സ്ഥിരസ്ഥിതിയായി `127.0.0.1`) |
| വോള്യം                     | `omniroute-redis-data` → `/data`                |
| ആരോഗ്യ പരിശോധന             | `redis-cli ping` (10 സെക്കൻഡ് ഇടവേള)            |

ബന്ധപ്പെട്ട എൻവയോൺമെന്റ് വേരിയബിളുകൾ:

- `REDIS_URL` — ആപ്പിലേക്ക് നൽകുന്ന കണക്ഷൻ സ്ട്രിംഗ് (സ്ഥിരസ്ഥിതിയായി `redis://redis:6379`).
- `REDIS_PORT` — Redis കണ്ടെയ്നറിനുള്ള ഹോസ്റ്റ്-സൈഡ് പോർട്ട് മാപ്പിംഗ്.
- `REDIS_BIND_HOST` — പോർട്ട് പ്രസിദ്ധീകരിക്കുന്ന ഹോസ്റ്റ് ഇന്റർഫേസ്. സ്ഥിരസ്ഥിതിയായി `127.0.0.1`.

> **എന്തുകൊണ്ട് സ്ഥിരസ്ഥിതിയായി ലൂപ്പ്ബാക്ക്:** സൈഡ്കാർ `requirepass` ഇല്ലാതെ പ്രവർത്തിക്കുന്നു, കൂടാതെ ആപ്പ്
> കണ്ടെയ്നറുകൾ compose നെറ്റ്വർക്കിലൂടെ (`redis:6379`) അതിലേക്ക് എത്തുന്നു — പ്രസിദ്ധീകരിച്ച പോർട്ട്
> ഹോസ്റ്റ്-സൈഡ് ടൂളുകൾക്ക് (`redis-cli`, ഒരു ലോക്കൽ `npm run dev`) വേണ്ടി മാത്രമുള്ളതാണ്. `0.0.0.0`-ൽ
> പ്രസിദ്ധീകരിക്കുന്നത് നിങ്ങളുടെ LAN-ലെ എല്ലാ ഹോസ്റ്റുകൾക്കും പ്രാമാണീകരണമില്ലാത്ത Redis ലഭ്യമാക്കും. നിങ്ങൾ
> `REDIS_BIND_HOST=0.0.0.0` സജ്ജമാക്കുകയാണെങ്കിൽ, സർവീസിന്റെ `command:`-ൽ `--requirepass` കൂടി ചേർക്കുക.

**Redis പ്രവർത്തനരഹിതമാക്കുന്നത്** ശുപാർശ ചെയ്യുന്നില്ല (നിരക്ക് നിയന്ത്രണം ഇൻ-മെമ്മറി ഫാൾബാക്കിലേക്ക് തരംതാഴും). നിർബന്ധമാണെങ്കിൽ, `docker-compose.yml`-ലെ `redis:` സർവീസ് ബ്ലോക്ക് നീക്കം ചെയ്യുക/കമന്റ് ചെയ്യുക, അല്ലെങ്കിൽ അതിനെ പൂജ്യത്തിലേക്ക് സ്കെയിൽ ചെയ്യുക:

```bash
docker compose up -d --scale redis=0
```

## പ്രൊഡക്ഷൻ Compose

ഡെവിനോടൊപ്പം പ്രവർത്തിക്കുന്ന ഒരു ഒറ്റപ്പെട്ട പ്രൊഡക്ഷൻ സ്നാപ്പ്ഷോട്ടിനായി `docker-compose.prod.yml` ഉപയോഗിക്കുക.

| വിശദാംശം                      | മൂല്യം                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| ഫയൽ                           | `docker-compose.prod.yml`                                                                                 |
| സ്ഥിരസ്ഥിതി ഡാഷ്ബോർഡ് പോർട്ട് | `PROD_DASHBOARD_PORT=20130` (ആന്തരിക `${DASHBOARD_PORT:-20128}`-ലേക്ക് മാപ്പ് ചെയ്യുന്നു)                 |
| സ്ഥിരസ്ഥിതി API പോർട്ട്       | `PROD_API_PORT=20131`                                                                                     |
| ഇമേജ്                         | `omniroute:prod` (`runner-cli` ടാർഗറ്റിൽ നിന്ന് ബിൽഡ് ചെയ്തത്)                                            |
| Redis കണ്ടെയ്നർ               | `omniroute-redis-prod` (`redis:8.6.2`, സമർപ്പിത `redis-prod-data` വോള്യം)                                 |
| ഡാറ്റാ വോള്യം                 | `omniroute-prod-data` (പേരിട്ടത്, റീബിൽഡുകളിലുടനീളം നിലനിൽക്കുന്നത്)                                      |
| ആരോഗ്യ പരിശോധനകൾ              | `node healthcheck.mjs` + `redis-cli ping`, Redis-ന്റെ ആരോഗ്യത്തെ അടിസ്ഥാനമാക്കി ഗേറ്റ് ചെയ്ത `depends_on` |

ഉപയോഗിക്കേണ്ട വിധം:

```bash
# പ്രൊഡക്ഷൻ സ്റ്റാക്ക് ബിൽഡ് ചെയ്ത് ആരംഭിക്കുക
docker compose -f docker-compose.prod.yml up -d --build

# ലോഗുകൾ സ്ട്രീം ചെയ്യുക
docker compose -f docker-compose.prod.yml logs -f

# നിർത്തി നീക്കം ചെയ്യുക (വോള്യങ്ങൾ നിലനിർത്തുക)
docker compose -f docker-compose.prod.yml down
```

പ്രൊഡ് സ്റ്റാക്ക് ഡെവ് compose-നൊപ്പം സമാന്തരമായി പ്രവർത്തിക്കുന്നു (വ്യത്യസ്ത കണ്ടെയ്നർ പേരുകൾ, പോർട്ടുകൾ, വോള്യങ്ങൾ എന്നിവ ഉപയോഗിച്ച്), അതിനാൽ പ്രൊഡക്ഷൻ പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുമ്പോൾ തന്നെ നിങ്ങൾക്ക് ലോക്കലായി ആവർത്തിച്ച് വികസിപ്പിക്കുന്നത് തുടരാം.

## Dockerfile ഘട്ടങ്ങൾ

റിപ്പോസിറ്ററിയിൽ ഒരു multi-stage Dockerfile (`Dockerfile`) ഉൾപ്പെടുത്തിയിട്ടുണ്ട്. നാല് ഘട്ടങ്ങൾ ലഭ്യമാണ്; നിങ്ങളുടെ ഉപയോഗസാഹചര്യത്തിന് അനുയോജ്യമായ `target` തിരഞ്ഞെടുക്കുക.

| ഘട്ടം         | അടിസ്ഥാന ഇമേജ്        | ഉദ്ദേശ്യം                                                                                                                                                                                                                                                                                                                  |
| ------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ഡിപെൻഡൻസികൾ ഇൻസ്റ്റാൾ ചെയ്യുകയും (`npm ci --legacy-peer-deps`) `npm run build` പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു (സ്ഥിരസ്ഥിതിയിൽ Turbopack — താഴെയുള്ള ബിൽഡ്-സമയ റിസോഴ്സുകൾ കാണുക)                                                                                                                                          |
| `runner-base` | `node:26-trixie-slim` | Next.js standalone ഔട്ട്പുട്ടോടുകൂടിയ പ്രൊഡക്ഷൻ റൺടൈം. **പ്രൊവൈഡർ CLI-കളൊന്നും ഉൾപ്പെടുത്തിയിട്ടില്ല.**                                                                                                                                                                                                                    |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` എന്നിവയും ആഗോള CLI-കളായ `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw` എന്നിവയും ചേർക്കുന്നു. **ഏജന്റിക് വർക്ക്ഫ്ലോകൾക്കായി ഇത് തിരഞ്ഞെടുക്കുക.**                                                                                                                  |

### ബിൽഡ്-സമയ റിസോഴ്സുകൾ

`builder` ഘട്ടത്തിന്റെ റിസോഴ്സ് ചെലവ് മൂന്ന് build args നിയന്ത്രിക്കുന്നു. അവ ബിൽഡ്-സമയത്ത് മാത്രമുള്ളവയാണ് —
`OMNIROUTE_MEMORY_MB` (താഴെ) ഒരു വേറിട്ട റൺടൈം ക്രമീകരണമാണ്.

| Build arg                   | സ്ഥിരസ്ഥിതി | പ്രഭാവം                                                                                                             |
| --------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`         | `0` webpack ഉപയോഗിച്ച് ബിൽഡ് ചെയ്യുന്നു: പരമാവധി മെമ്മറി ഉപയോഗം കുറവ്, വേഗത കുറവ്. `1` Turbopack തിരഞ്ഞെടുക്കുന്നു. |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`      | സൃഷ്ടിക്കപ്പെടുന്ന `next build`-നുള്ള V8 heap പരിധി (`--max-old-space-size`).                                       |
| `OMNIROUTE_BUILD_WORKERS`   | `2`         | `CIRCLE_NODE_TOTAL`-ലേക്ക് മൂല്യം നൽകുന്നു; page-data ശേഖരണത്തിനായി Next `workers = N - 1` കണക്കാക്കുന്നു.          |

വലിയൊരു builder-ൽ ഉയർത്തേണ്ടതും, പരിമിതമായ റിസോഴ്സുകളുള്ള ഒരു ബിൽഡ്
`✓ Compiled successfully` എന്നതിന് **ശേഷം** അവസാനിക്കുമ്പോൾ സംശയിക്കേണ്ടതും
`OMNIROUTE_BUILD_WORKERS` ആണ്. ഓരോ page-data worker-ഉം സ്വതന്ത്രമായ ഒരു
process ആണ്, അതുപോലെ parent `next build` തന്നെയും; ഒരു തത്സമയ VPS പുനരാവിഷ്കരണം
(issue #7518), `NODE_OPTIONS` heap flag-ൽനിന്ന് സ്വതന്ത്രമായി ഓരോ process-ന്റെയും
പരമാവധി RSS ~4.5 GB ആണെന്ന് അളന്നു (Turbopack, V8 heap-ന് പുറത്തുള്ള native/Rust
മെമ്മറിയിലാണ് compile ചെയ്യുന്നത്). സ്ഥിരസ്ഥിതിയായ `2` (→ 1 worker, ആകെ 2
processes) പ്രസിദ്ധീകരണ pipeline ഉപയോഗിക്കുന്ന 16 GB / 4 vCPU GitHub-hosted
runners-ന് അനുയോജ്യമായി നിശ്ചയിച്ചതാണ്. `8`-ൽ (→ 7 workers) ആ runner-ന്റെ
മെമ്മറി തീരുകയും buildkit, `ResourceExhausted: ... cannot allocate memory`
എന്ന സന്ദേശത്തോടെ ഘട്ടം പരാജയപ്പെടുത്തുകയും ചെയ്തു; ഓരോ process-ന്റെയും RSS
അനുമാനിക്കുന്നതിനുപകരം നേരിട്ട് അളന്നപ്പോൾ `3` (→ 2 workers) പോലും മതിയായില്ല.
`tests/unit/docker-build-memory-budget.test.ts`, അളന്ന കണക്കിനെ അടിസ്ഥാനമാക്കി
ഗണിതം നിർവഹിക്കുകയും ഏതെങ്കിലും ക്രമീകരണം runner-ന്റെ പരിധി കവിഞ്ഞാൽ
പരാജയപ്പെടുകയും ചെയ്യുന്നു.

Turbopack, V8 heap-ന് **പുറത്ത്** നിലനിൽക്കുന്ന native Rust മെമ്മറിയിലാണ് compile
ചെയ്യുന്നത്, അതിനാൽ `OMNIROUTE_BUILD_MEMORY_MB` അതിനെ പരിമിതപ്പെടുത്തുന്നില്ല.
മെമ്മറി പരിധിയുള്ള ഒരു host-ൽ, യാതൊരു error text-ഉം ഇല്ലാതെ OOM killer ബിൽഡിനെ
SIGKILL ചെയ്യുന്നു — `Creating an optimized production build` എന്നതിന്റെ
മധ്യത്തിൽ അത് വെറുതെ നിൽക്കുന്നു; അതിനാൽ out-of-memory എന്നതിനേക്കാൾ hang
ആയതുപോലെ തോന്നും. അതുകൊണ്ടാണ് `npm run dev` / `npm run build` എന്നിവയിൽ
Turbopack code default ആയിരിക്കുമ്പോഴും `Dockerfile` webpack
(`OMNIROUTE_USE_TURBOPACK=0`) സ്ഥിരസ്ഥിതിയാക്കുന്നത്: build args ഒന്നുമില്ലാത്ത
ഒരു അടിസ്ഥാന `docker build .` (Railway-യും മറ്റ് one-click hosts-ഉം
പ്രവർത്തിപ്പിക്കുന്നത്) മെമ്മറി പരിധിയുള്ള builder-ൽ നിശ്ശബ്ദമായി അവസാനിക്കരുത്.
പ്രസിദ്ധീകരിച്ച ഇമേജുകൾ ഇതിനകം `docker-publish.yml`-ൽ
`OMNIROUTE_USE_TURBOPACK=0` വ്യക്തമായി നൽകുന്നു. ധാരാളം RAM ഉള്ള builder-ൽ
വേഗമേറിയ ബിൽഡിനായി Turbopack തിരഞ്ഞെടുക്കുക:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` സജ്ജമാക്കിയതിനാൽ, `next build` ഒരു parent process-ഉം
ഒരു worker process-ഉം പ്രവർത്തിപ്പിക്കുന്നു; ഓരോന്നും
`OMNIROUTE_BUILD_MEMORY_MB` പ്രത്യേകം പാലിക്കുന്നു. Container പരിധി ആ മൂല്യത്തിന്റെ
ഏകദേശം ഇരട്ടിയിലും മുകളിലായി ക്രമീകരിക്കുക, ഒരിരട്ടിയല്ല.

ഈ tree-ൽ അളന്നത് (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| Bundler   | Container പരിധി | ഫലം                                             |
| --------- | --------------- | ----------------------------------------------- |
| Turbopack | 8 GiB / 16 GiB  | രണ്ടിലും യാതൊരു സന്ദേശവുമില്ലാതെ OOM-killed ആയി |
| webpack   | 8 GiB           | build worker SIGKILLed ആയി                      |
| webpack   | 12 GiB          | വിജയിച്ചു, പരമാവധി 11.1 GiB വരെ എത്തി           |

### റൺടൈം സ്ഥിരസ്ഥിതികൾ

`runner-base` export ചെയ്യുന്ന സ്ഥിരസ്ഥിതികൾ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Docker-ലെ മെമ്മറി സ്വഭാവം:

- ഇമേജ് `OMNIROUTE_MEMORY_MB=1024` സജ്ജീകരിക്കുകയും അതിൽനിന്ന് `NODE_OPTIONS=--max-old-space-size=1024` നിർണ്ണയിക്കുകയും ചെയ്യുന്നു.
- യഥാർഥ സെർവർ പ്രോസസ്സ് standalone launcher ആണ് ആരംഭിക്കുന്നത്; അത് `OMNIROUTE_MEMORY_MB` വായിച്ച് `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ചേർക്കുന്നു.
- ആവർത്തിച്ചുള്ള `--max-old-space-size` മൂല്യങ്ങളിൽ അവസാനത്തേതാണ് Node ഉപയോഗിക്കുന്നത്, അതിനാൽ `OMNIROUTE_MEMORY_MB` സജ്ജീകരിക്കുന്നത് പ്രാബല്യത്തിലുള്ള Docker heap പരിധി നിയന്ത്രിക്കുന്നു.
- ഇമേജ് എല്ലായ്പ്പോഴും ഇത് സജ്ജീകരിക്കുന്നതിനാൽ, launcher's-ന്റെ സ്വന്തം RAM-അധിഷ്ഠിത fallback Docker-ൽ ഒരിക്കലും പ്രയോഗിക്കപ്പെടില്ല. workload-ന് അനുയോജ്യമായി ഇത് വ്യക്തമായി വർധിപ്പിക്കുക (താഴെയുള്ള പട്ടിക കാണുക). coding-agent `/v1/responses`-ന് `2048` ഇപ്പോഴും വളരെ കുറവാണ്.

### coding agents-നുള്ള runtime RAM

1 GiB Docker default എന്നത് dashboard/light-chat-നുള്ള ഏറ്റവും കുറഞ്ഞ പരിധിയാണ്, production വലുപ്പമല്ല. ദൈർഘ്യമേറിയ `POST /v1/responses` bodies (നൂറുകണക്കിന് messages, പതിനക്കണക്കിന് tools) compression സമയത്ത് ഒന്നിലധികം in-memory graphs നിലനിർത്തുന്നു. ഒരേസമയം പ്രവർത്തിക്കുന്ന ഏകദേശം ~3 MiB / ~750k-token വലുപ്പമുള്ള രണ്ട് requests, **12 GiB** old-space-ൽ V8 abort ചെയ്യാൻ കാരണമായിട്ടുണ്ട് (`FATAL ERROR: Reached heap limit`); കൂടാതെ 16 GiB cgroup OOM-ലും എത്തിയിട്ടുണ്ട്. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) കാണുക.

**cgroup `--memory` heap-നേക്കാൾ കൂടുതലായി ക്രമീകരിക്കുക** — native buffers, SQLite, compression intermediates എന്നിവ V8-ന് പുറത്താണ് നിലനിൽക്കുന്നത്.

| Workload                                  | `OMNIROUTE_MEMORY_MB`    | Container / cgroup             | കുറിപ്പുകൾ                                                                                                                             |
| ----------------------------------------- | ------------------------ | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard, ഒരു ലഘു chat                   | `1024` (image default)   | ≥2 GiB                         |                                                                                                                                        |
| ഒരു coding agent (Claude/Codex/Grok)      | `8192`                   | ≥10 GiB                        | സാധാരണ single-session `/v1/responses`                                                                                                  |
| ഒരേസമയം രണ്ട് ദൈർഘ്യമേറിയ `/v1/responses` | `10240`–`12288`          | ≥12–16 GiB                     | ഏകദേശം 12 GiB heap-ൽ V8 abort അളക്കപ്പെട്ടു                                                                                            |
| ഒരേസമയം മൂന്ന്+ ദൈർഘ്യമേറിയ contexts      | ഒറ്റ process-ൽ ചെയ്യരുത് | serialize ചെയ്യുക / കൂടുതൽ RAM | Default heavyweight admission-ൽ 1 in-flight മാത്രമേ അനുവദിക്കൂ; RAM വർധിപ്പിക്കാതെ ഇത് ഉയർത്തുന്നത് abort വീണ്ടും സംഭവിക്കാൻ ഇടയാക്കും |

bare metal-ൽ `OMNIROUTE_MEMORY_MB` **സജ്ജീകരിച്ചിട്ടില്ലാത്തപ്പോൾ**, `omniroute serve` RAM-ന്റെ ഏകദേശം 35% ആയി calibrate ചെയ്യുന്നു (`[512, 4096]` പരിധിയിൽ). Docker എല്ലായ്പ്പോഴും `1024` സജ്ജീകരിക്കുന്നതിനാൽ, official image-ൽ ആ calibration ഒരിക്കലും പ്രവർത്തിക്കില്ല.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ഉപപാതയിലെ റിവേഴ്സ് പ്രോക്സി (Traefik / nginx)

Next.js `basePath` സ്റ്റാൻഡ്എലോൺ ബണ്ടിലിലേക്ക് കംപൈൽ ചെയ്യപ്പെടുന്നു. OmniRoute, ആപ്പിന്റെ റൂട്ടിലുള്ള ഒരു സെന്റിനൽ ഫയലിൽ ബിൽഡ് ചെയ്തുചേർത്ത മൂല്യം രേഖപ്പെടുത്തുകയും (`npm run build` സമയത്ത് എഴുതുന്നു; `scripts/docker/ensure-docker-base-path.mjs` വായിക്കുന്നു), കണ്ടെയ്നർ ആരംഭിക്കുമ്പോൾ അതിനെ `OMNIROUTE_BASE_PATH`-മായി താരതമ്യം ചെയ്യുകയും ചെയ്യുന്നു. അവ വ്യത്യസ്തമായിരിക്കുകയും ഇമേജ് ഡൊമെയ്ൻ റൂട്ടിനായി ബിൽഡ് ചെയ്തതായിരിക്കുകയും ചെയ്യുമ്പോൾ, `node dev/run-standalone.mjs` പ്രവർത്തിക്കുന്നതിന് മുമ്പ് എൻട്രിപോയിന്റ് സ്റ്റാൻഡ്എലോൺ മാനിഫെസ്റ്റുകൾ, എംബഡ് ചെയ്ത `basePath`/`assetPrefix` ലിറ്ററലുകൾ (Next 16, `assetPrefix`-ൽ നിന്ന് മാത്രം SSR അസറ്റ് URL-കൾ റെൻഡർ ചെയ്യുന്നു — പാച്ചർ ഉപപാത അതിലേക്കും പകർത്തുന്നു), ബിൽഡ് ചെയ്തുചേർത്ത `/_next/static` അസറ്റ് URL-കൾ (ക്ലയന്റ്-റഫറൻസ് മാനിഫെസ്റ്റുകൾ, മീഡിയ ഇംപോർട്ടുകൾ, മുൻകൂട്ടി റെൻഡർ ചെയ്ത പിശക് പേജുകൾ), ക്ലയന്റ് `process.env` ഷിം എന്നിവ തിരുത്തിയെഴുതുന്നു.

### Compose ബിൽഡ് (ശുപാർശ ചെയ്യുന്നത്)

`.env`-ൽ രണ്ട് വേരിയബിളുകളും സജ്ജമാക്കിയശേഷം, ഇമേജും റൺടൈമും ഒരേ ക്രമീകരണം ഉപയോഗിക്കുന്നതിനായി വീണ്ടും ബിൽഡ് ചെയ്യുക:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH`-നെ ഒരു Docker build-arg ആയും റൺടൈം എൻവയോൺമെന്റ് വേരിയബിൾ ആയും കൈമാറുന്നു.

### മുൻകൂട്ടി ബിൽഡ് ചെയ്ത റൂട്ട് ഇമേജ് + റൺടൈം ഉപപാത

പ്രസിദ്ധീകരിച്ച `diegosouzapw/omniroute:*` ഇമേജുകൾ ഡൊമെയ്ൻ റൂട്ടിനായി ബിൽഡ് ചെയ്തവയാണ്. എന്നിരുന്നാലും, റൺടൈമിൽ നിങ്ങൾക്ക് `OMNIROUTE_BASE_PATH` സജ്ജമാക്കാം; സ്റ്റാർട്ടപ്പിൽ കണ്ടെയ്നർ ബണ്ടിൽ ഒരുതവണ പാച്ച് ചെയ്യും. അതിനോടൊപ്പം പൊരുത്തപ്പെടുന്ന പബ്ലിക് ഒറിജിൻ നൽകുക:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

**പൂർണ്ണമായ** ബാഹ്യ പാത ഫോർവേഡ് ചെയ്യുന്നതിനായി റിവേഴ്സ് പ്രോക്സി കോൺഫിഗർ ചെയ്യുക (പ്രിഫിക്സ് നീക്കം ചെയ്യരുത്). Traefik, `StripPrefix` ഇല്ലാതെ `PathPrefix(`/omniroute`)` കണ്ടെയ്നറിലേക്ക് റൂട്ട് ചെയ്യണം; അങ്ങനെ Next.js-ന് `/omniroute/...` ലഭിക്കുകയും `/omniroute/_next/...`-ൽ നിന്ന് അസറ്റുകൾ നൽകുകയും ചെയ്യും.

Docker ഹെൽത്ത്ചെക്ക്, സജീവമായ `OMNIROUTE_BASE_PATH` പ്രിഫിക്സ് ചേർത്ത ലഘുവായ `/healthz` ലൈഫ്സൈക്കിൾ എൻഡ്പോയിന്റ് പരിശോധിക്കുന്നു. മനുഷ്യർ/ഡാഷ്ബോർഡുകൾ നടത്തുന്ന ഡയഗ്നോസ്റ്റിക്സിനായി `/api/monitoring/health` തുടർന്നും ലഭ്യമാണ്; കണ്ടെയ്നറിന്റെ HEALTHCHECK വീണ്ടും അതിലേക്ക് ചൂണ്ടാൻ (ഉദാഹരണത്തിന്, ഡീപ് ഹെൽത്ത് നിർബന്ധമാക്കാൻ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` സജ്ജമാക്കുക. ആ പാത ഒരു **ഡീപ്** പരിശോധനയാണ് (DB + മോണിറ്ററിംഗ് സംഗ്രഹം) — നിങ്ങൾ അത് വീണ്ടും തിരഞ്ഞെടുക്കുകയാണെങ്കിൽ, Docker-ന്റെ വിരളമായ `HEALTHCHECK`-ന് അനുയോജ്യമാണ്; എന്നാൽ Kubernetes `livenessProbe` ഇടവേളകൾക്ക് അനുയോജ്യമല്ല.

ഓർക്കസ്ട്രേറ്ററുകൾക്കായി (Kubernetes, Nomad മുതലായവ):

| പ്രോബ്                | മുൻഗണന നൽകുക                                                                   | ഒഴിവാക്കുക                                                                                |
| --------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| ലൈവ്നെസ്              | HTTP `GET /livez`, അല്ലെങ്കിൽ പ്രധാന പോർട്ടിലെ TCP (`PORT`, ഡിഫോൾട്ട് `20128`) | ലൈവ്നെസായി `/api/monitoring/health`                                                       |
| റെഡിനെസ്              | HTTP `GET /healthz`                                                            | ഇവന്റ് ലൂപ്പ് തിരക്കിലായിരിക്കുന്നതിനെ പ്രവർത്തനരഹിതമായി കണക്കാക്കുന്ന കർശനമായ ടൈംഔട്ടുകൾ |
| ഡീപ് / ബ്ലാക്ക്ബോക്സ് | `/api/monitoring/health`                                                       | —                                                                                         |

`/healthz`, പ്രോസസ് ലൈഫ്സൈക്കിൾ (`ok` / `starting` / `stopping`) റിപ്പോർട്ട് ചെയ്യുന്നു. `/livez` പ്രോസസ് സജീവമാണോ എന്ന് മാത്രം പരിശോധിക്കുന്നു (ഹാൻഡ്ലർ പ്രവർത്തിക്കാൻ കഴിയുമ്പോഴെല്ലാം 200; ഇത് റെഡിനെസിനായി കാത്തിരിക്കില്ല). രണ്ടും അഭ്യർത്ഥനകൾ കൈകാര്യം ചെയ്യുന്ന അതേ Node ഇവന്റ് ലൂപ്പിലാണ് പ്രവർത്തിക്കുന്നത്; അതിനാൽ CPU-ബന്ധിത കാറ്റലോഗ് അല്ലെങ്കിൽ കംപ്രഷൻ പ്രവർത്തനം അവയെ വൈകിപ്പിക്കാം — തിരക്ക് ≠ പ്രവർത്തനരഹിതം. HTTP പ്രോബുകൾ ടൈംഔട്ട് ആകുകയാണെങ്കിൽ TCP ലൈവ്നെസിന് മുൻഗണന നൽകുക. പൂർണ്ണമായ പ്രോബ് മാർഗനിർദേശം:
[മോണിറ്ററിംഗ് ഗൈഡ് — Kubernetes പ്രോബ് ശുപാർശകൾ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Caddy ഉപയോഗിച്ചുള്ള Docker Compose (HTTPS Auto-TLS)

Caddy-യുടെ സ്വയമേവയുള്ള SSL പ്രൊവിഷനിംഗ് ഉപയോഗിച്ച് OmniRoute സുരക്ഷിതമായി ലഭ്യമാക്കാം. നിങ്ങളുടെ ഡൊമെയ്നിന്റെ DNS A റെക്കോർഡ് നിങ്ങളുടെ സെർവറിന്റെ IP-യിലേക്കാണ് ചൂണ്ടുന്നതെന്ന് ഉറപ്പാക്കുക.

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth കോൾബാക്കുകൾക്കും ഡാഷ്ബോർഡ് ലിങ്കുകൾക്കും സൃഷ്ടിക്കുന്ന പൊതു URL-കൾക്കുമുള്ള ബ്രൗസർ അഭിമുഖീകരിക്കുന്ന ഒറിജിൻ.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ഷെഡ്യൂൾ ചെയ്ത ജോലികൾക്കും സ്വയം നടത്തുന്ന ഫെച്ചുകൾക്കുമുള്ള ആന്തരിക സെർവർ-ടു-സെർവർ URL.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

അപ്സ്ട്രീം കണ്ടെയ്നറിനായി Caddy സ്റ്റാൻഡേർഡ് ഫോർവേഡിംഗ് ഹെഡറുകൾ സജ്ജീകരിക്കുന്നു. OAuth കോൾബാക്കുകൾക്കും സൃഷ്ടിക്കുന്ന പൊതു
ലിങ്കുകൾക്കുമുള്ള കാനോണിക്കൽ പൊതു ഒറിജിനായി OmniRoute `NEXT_PUBLIC_BASE_URL` ഉപയോഗിക്കുന്നു;
ഓതന്റിക്കേഷൻ ആവശ്യമായ ഡാഷ്ബോർഡ് റൈറ്റ് പ്രവർത്തനങ്ങൾ same-origin അഭ്യർത്ഥനകളും സെഷനുമായി ബന്ധിപ്പിച്ച CSRF
പരിരക്ഷയും ഉപയോഗിക്കുന്നു. വ്യക്തമായ കോൺഫിഗറേഷനുപകരം വിശ്വസനീയമായ ഫോർവേഡഡ് ഹെഡറുകളിൽനിന്ന്
OmniRoute പൊതു ഒറിജിൻ നിർണ്ണയിക്കണമെന്ന് നിങ്ങൾ മനഃപൂർവം ആഗ്രഹിക്കുന്ന വിപുലമായ ഡിപ്ലോയ്മെന്റുകളിൽ മാത്രം `OMNIROUTE_TRUST_PROXY` പ്രവർത്തനക്ഷമമാക്കുക.

## Cloudflare Quick Tunnel

Docker ഡിപ്ലോയ്മെന്റുകൾക്കുള്ള ഡാഷ്ബോർഡ് പിന്തുണയിൽ `Dashboard → Endpoints` എന്നതിൽ ഒറ്റ ക്ലിക്കിൽ പ്രവർത്തനക്ഷമമാക്കാവുന്ന **Cloudflare Quick Tunnel** ഉൾപ്പെടുന്നു. ആദ്യം പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ, ആവശ്യമായാൽ മാത്രം `cloudflared` ഡൗൺലോഡ് ചെയ്യുകയും നിങ്ങളുടെ നിലവിലെ `/v1` എൻഡ്പോയിന്റിലേക്ക് ഒരു താൽക്കാലിക ടണൽ ആരംഭിക്കുകയും സൃഷ്ടിച്ച `https://*.trycloudflare.com/v1` URL നിങ്ങളുടെ സാധാരണ പൊതു URL-ന് നേരെ താഴെ പ്രദർശിപ്പിക്കുകയും ചെയ്യുന്നു.

സജീവ ടണലിന്റെ നില മാറ്റാതെ `Settings → Appearance` എന്നതിൽനിന്ന് എൻഡ്പോയിന്റ് ടണൽ പാനലുകൾ (Cloudflare, Tailscale, ngrok) കാണിക്കാനോ മറയ്ക്കാനോ കഴിയും.

### ടണൽ കുറിപ്പുകൾ

- Quick Tunnel URL-കൾ താൽക്കാലികമാണ്, ഓരോ റീസ്റ്റാർട്ടിനുശേഷവും അവ മാറും.
- OmniRoute അല്ലെങ്കിൽ കണ്ടെയ്നർ റീസ്റ്റാർട്ട് ചെയ്തശേഷം Quick Tunnel-കൾ സ്വയമേവ പുനഃസ്ഥാപിക്കപ്പെടില്ല. ആവശ്യമുള്ളപ്പോൾ ഡാഷ്ബോർഡിൽനിന്ന് അവ വീണ്ടും പ്രവർത്തനക്ഷമമാക്കുക.
- മാനേജ്ഡ് ഇൻസ്റ്റാൾ നിലവിൽ `x64` / `arm64` ആർക്കിടെക്ചറുകളിലുള്ള Linux, macOS, Windows എന്നിവയെ പിന്തുണയ്ക്കുന്നു.
- നിയന്ത്രിത കണ്ടെയ്നർ പരിതസ്ഥിതികളിലെ അനാവശ്യമായ QUIC UDP ബഫർ മുന്നറിയിപ്പുകൾ ഒഴിവാക്കാൻ മാനേജ്ഡ് Quick Tunnel-കൾ ഡിഫോൾട്ടായി HTTP/2 ട്രാൻസ്പോർട്ട് ഉപയോഗിക്കുന്നു. മറ്റൊരു ട്രാൻസ്പോർട്ട് വേണമെങ്കിൽ `CLOUDFLARED_PROTOCOL=quic` അല്ലെങ്കിൽ `auto` സജ്ജീകരിക്കുക.
- Docker ഇമേജുകൾ സിസ്റ്റം CA റൂട്ടുകൾ ഉൾപ്പെടുത്തുകയും അവയെ മാനേജ്ഡ് `cloudflared`-ലേക്ക് കൈമാറുകയും ചെയ്യുന്നു; കണ്ടെയ്നറിനുള്ളിൽ ടണൽ ബൂട്ട്സ്ട്രാപ്പ് ചെയ്യുമ്പോഴുള്ള TLS വിശ്വാസ്യതാ പരാജയങ്ങൾ ഇത് ഒഴിവാക്കുന്നു.
- ഒന്ന് ഡൗൺലോഡ് ചെയ്യുന്നതിനുപകരം നിലവിലുള്ള ഒരു ബൈനറി OmniRoute ഉപയോഗിക്കണമെന്ന് നിങ്ങൾ ആഗ്രഹിക്കുന്നുവെങ്കിൽ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` സജ്ജീകരിക്കുക.

#### വെബ്-സെഷൻ പ്രൊവൈഡറുകൾ: `-web` ഇമേജുകൾ

മുകളിലുള്ള ഓരോ ചാനലിനും `-web` ടാഗ് (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) കൂടിയുണ്ട്; ഇത് `runner-web` സ്റ്റേജിൽനിന്ന് ബിൽഡ് ചെയ്യപ്പെടുന്നു — അതേ ഇമേജിനൊപ്പം Playwright-ഉം Chromium ബ്രൗസറും ഉൾപ്പെടുന്നു. സാധാരണ ഇമേജ് Chromium **ഇല്ലാതെയാണ്** ലഭിക്കുന്നത്; `gemini-web`, `claude-web`, `claude-turnstile` എന്നിവയ്ക്ക് അത് ആവശ്യമാണ്.

പരാജയം സ്റ്റാർട്ടപ്പ് സമയത്തല്ല, പിന്നീടാണ് സംഭവിക്കുക: ആ പ്രൊവൈഡറുകൾ അവരുടെ മോഡലുകൾ ലിസ്റ്റ് ചെയ്യുകയും ഡാഷ്ബോർഡിൽ കണക്റ്റഡ് ആയി കാണിക്കുകയും ചെയ്യും, എന്നാൽ ആദ്യ അഭ്യർത്ഥന മാത്രം ഇനിപ്പറയുന്ന പിശകോടെ പരാജയപ്പെടും

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ആ പ്രൊവൈഡറുകൾ നിങ്ങൾ ഉപയോഗിക്കുന്നുവെങ്കിൽ, നിങ്ങൾ നിലവിൽ ഉപയോഗിക്കുന്ന ചാനലിന്റെ `-web` ടാഗ് പുൾ ചെയ്യുക — മറ്റൊന്നും മാറുന്നില്ല. npm/CLI ഇൻസ്റ്റാളേഷനിൽ (Docker ഇമേജ് ഇല്ലാതെ), ഇതിന് തുല്യമായി കാണാതായിരിക്കുന്ന ഘടകം ബ്രൗസർ ബൈനറിയാണ്: ഹോസ്റ്റിൽ `npx playwright install chromium` പ്രവർത്തിപ്പിക്കുക.

#### പ്രീ-റിലീസ് ചാനൽ ഉപയോഗിക്കൽ

നിലവിലെ ഡിഫോൾട്ട് `release/v*` ബ്രാഞ്ചിലേക്കുള്ള ഓരോ push-ലും `next` ചാനൽ വീണ്ടും build ചെയ്യപ്പെടുകയും AMD64, ARM64 എന്നിവയ്ക്കായി പ്രസിദ്ധീകരിക്കപ്പെടുകയും ചെയ്യുന്നു. പഴയ maintenance ബ്രാഞ്ചുകൾക്ക് ഇതിനെ overwrite ചെയ്യാൻ കഴിയില്ല. അടുത്ത stable tag സൃഷ്ടിക്കുന്നതിന് മുമ്പ് സജീവമായ release ബ്രാഞ്ചിലേക്ക് merge ചെയ്ത പരിഹാരങ്ങൾ ഉൾക്കൊള്ളുന്ന, pull ചെയ്യാവുന്ന ഒരു image ഈ ചാനൽ നൽകുന്നു.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose-നായി, തിരഞ്ഞെടുത്ത profile ഉപയോഗിക്കുന്ന image tag override ചെയ്തശേഷം service pull ചെയ്ത് വീണ്ടും സൃഷ്ടിക്കുക:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### സുരക്ഷയും rollback-ഉം

`next` എന്നത് സ്ഥിരമായി മാറിക്കൊണ്ടിരിക്കുന്ന ഒരു pre-release ചാനലാണ്. സജീവമായ release ബ്രാഞ്ചിലേക്കുള്ള ഏത് push-ലും ഇത് മാറാം, കൂടാതെ **production ഉപയോഗത്തിന് ഇത് പിന്തുണയ്ക്കപ്പെടുന്നില്ല**. ഒരു നിർദ്ദിഷ്ട build വിലയിരുത്തുമ്പോൾ image digest സ്ഥിരപ്പെടുത്തുക:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

പരിശോധനയ്ക്ക് മുമ്പ് OmniRoute data volume അല്ലെങ്കിൽ bind-mounted data directory backup ചെയ്യുക. rollback ചെയ്യാൻ, മുമ്പ് ഉപയോഗിച്ചിരുന്ന stable version അല്ലെങ്കിൽ digest പുനഃസ്ഥാപിച്ചശേഷം container വീണ്ടും സൃഷ്ടിക്കുക:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

ഒരു release-branch build-നും ഒരിക്കലും `latest` മാറ്റാൻ കഴിയില്ല; യോഗ്യമായ stable semantic version-ന് മാത്രമേ stable pointer promote ചെയ്യാനാകൂ. `next` images, release image inspection-ഉം തടയൽ പ്രാബല്യമുള്ള CRITICAL-vulnerability gate-ഉം നിലനിർത്തുന്നു.

**git-നെ സംബന്ധിച്ചിടത്തോളം `latest` ഏറ്റവും പുതിയതാണെന്ന ഉറപ്പല്ല.** `main`-ലോ സജീവമായ `release/v*` ബ്രാഞ്ചിലോ merge ചെയ്ത പരിഹാരങ്ങൾ, ഒരു stable SemVer image പ്രസിദ്ധീകരിക്കുകയും publish job `:latest` promote ചെയ്യുകയും ചെയ്യുന്നതുവരെ **`:latest`-ൽ ഉൾപ്പെടില്ല** (ആ SemVer-ന്റെ അതേ digest). GitHub-ൽ പരിഹാരം ഇതിനകം കാണുന്നുണ്ടെങ്കിലും `latest` മാറാതെ നിൽക്കുന്നതായി തോന്നുന്നുവെങ്കിൽ, release ബ്രാഞ്ച് പരിശോധിക്കാൻ `:next` pull ചെയ്യുക അല്ലെങ്കിൽ SemVer tag-നായി കാത്തിരിക്കുക.

| നിങ്ങൾക്ക് വേണ്ടത്                                                                                         | ഉപയോഗിക്കേണ്ടത്                                     |
| ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| മാറ്റങ്ങൾ സ്വയമേവ സംഭവിക്കാൻ പാടില്ലാത്ത GitOps / production                                               | `:X.Y.Z` (അല്ലെങ്കിൽ image digest) സ്ഥിരപ്പെടുത്തുക |
| പ്രസിദ്ധീകരിച്ച stable releases പിന്തുടരുകയും ഓരോ release-ലും recreate ചെയ്യുന്നത് അംഗീകരിക്കുകയും ചെയ്യുക | `:latest`                                           |
| പ്രസിദ്ധീകരിക്കാത്ത `release/v*` commits പരിശോധിക്കുക                                                      | `:next` (production-നല്ല)                           |
| `main` പരിശോധിക്കുക                                                                                        | `:main` (production-നല്ല)                           |

## Docker-ലെ ഡാഷ്ബോർഡ് അപ്ഡേറ്റുകൾ

പ്രസിദ്ധീകരിച്ച ഇമേജിൽനിന്നുള്ള ഒരു കണ്ടെയ്നറിന് സ്വയം മാറ്റിസ്ഥാപിക്കാനാകില്ല. OmniRoute ഒരു കണ്ടെയ്നറിനുള്ളിലാണ് പ്രവർത്തിക്കുന്നതെന്ന് കണ്ടെത്തുമ്പോൾ (`.git` checkout അല്ല, npm ഇൻസ്റ്റാളും അല്ല), ഹോം ഡാഷ്ബോർഡിന്റെ അപ്ഡേറ്റ് ബാനർ npm/git നിർദ്ദേശങ്ങൾക്ക് പകരം ഹോസ്റ്റിൽ പ്രവർത്തിപ്പിക്കേണ്ട കമാൻഡ് ഒരു കോപ്പി ബട്ടണോടുകൂടി കാണിക്കുന്നു:

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

സേവനത്തിന്റെ പേര് `AUTO_UPDATE_SERVICE`-ൽ നിന്നാണ് ലഭിക്കുന്നത് (ഡിഫോൾട്ട് `omniroute`, `docker-compose.selfhost.yml`-ലെ സേവനം). `pull` ഒരു ഫ്ലോട്ടിങ് ടാഗിനെ (`latest`, `next`) മാത്രമേ മുന്നോട്ട് നീക്കുകയുള്ളൂ; പിൻ ചെയ്ത `:X.Y.Z` ടാഗാണെങ്കിൽ ആദ്യം ടാഗ് തിരുത്തുക.

### ഹോസ്റ്റ് ട്രിഗർ ഫയൽ ഉപയോഗിച്ചുള്ള ഒറ്റ-ക്ലിക്ക് അപ്ഡേറ്റുകൾ

ഹോസ്റ്റിൽ കണ്ടെയ്നറിന് root അധികാരം നൽകുന്ന `/var/run/docker.sock` മൗണ്ട് ചെയ്യാതെ **Update Now** പ്രവർത്തനക്ഷമമായി നിലനിർത്താൻ — മുകളിലെ `cli` പ്രൊഫൈൽ മുന്നറിയിപ്പ് കാണുക — OmniRoute സേവനത്തിൽ `DOCKER_UPDATE_TRIGGER_FILE` സജ്ജീകരിച്ച് ഹോസ്റ്റിൽ ഒരു വാച്ചർ പ്രവർത്തിപ്പിക്കുക:

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

പാത്ത് `DATA_DIR`-നുള്ളിലായിരിക്കണം (ആപേക്ഷിക മൂല്യങ്ങൾ അതിനെ അടിസ്ഥാനമാക്കി നിർണ്ണയിക്കപ്പെടും); മറ്റെന്തും നിരസിക്കപ്പെടും. തുടർന്ന് **Update Now**, `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }` ആ ഫയലിലേക്ക് എഴുതുകയും `202` മറുപടി നൽകുകയും ചെയ്യും; പുതിയ പതിപ്പ് പ്രവർത്തനക്ഷമമാകുന്നതുവരെ ഡാഷ്ബോർഡ് `/api/system/version` പോൾ ചെയ്തശേഷം റീലോഡ് ചെയ്യും. ഈ മോഡിൽ OmniRoute ഒരിക്കലും shell അല്ലെങ്കിൽ Docker കമാൻഡ് പ്രവർത്തിപ്പിക്കില്ല. എല്ലാ അപ്ഡേറ്റ് പ്രവർത്തനങ്ങളെയും പോലെ, loopback/LAN ക്ലയന്റുകളിൽ നിന്നുള്ള അഭ്യർത്ഥനകൾ മാത്രമേ സ്വീകരിക്കൂ.

bind-mount ചെയ്ത ഡാറ്റ ഡയറക്ടറി ഹോസ്റ്റിന് നിരീക്ഷിക്കാൻ സ്ഥിരതയുള്ള ഒരു പാത്ത് നൽകുന്നു. മാതൃകാ `systemd` യൂണിറ്റുകൾ (`/srv/omniroute` എന്നത് നിങ്ങളുടെ compose ഫയലും `data/` ഡയറക്ടറിയും ഉൾക്കൊള്ളുന്ന ഡയറക്ടറിയായി ക്രമീകരിക്കുക):

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=OmniRoute ഡാഷ്ബോർഡ് അപ്ഡേറ്റ് അഭ്യർത്ഥനകൾ നിരീക്ഷിക്കുക

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=OmniRoute കണ്ടെയ്നർ pull ചെയ്ത് പുനഃസൃഷ്ടിക്കുക

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

പരാജയപ്പെട്ട പ്രവർത്തനം ലൂപ്പാകാതിരിക്കാൻ pull ചെയ്യുന്നതിന് മുമ്പ് സേവനം അഭ്യർത്ഥന നീക്കംചെയ്യുന്നു. `DOCKER_UPDATE_TRIGGER_FILE` ഇല്ലെങ്കിൽ ഡാഷ്ബോർഡ് മാനുവൽ കമാൻഡ് പ്രവാഹം നിലനിർത്തും.

## ലഭ്യത: ഡിഫോൾട്ട് SQLite സിംഗിൾ റെപ്ലിക്കയാണ്

സ്റ്റോക്ക് Docker / Kubernetes OmniRoute ആണ്** ഒരു നോഡ് പ്രോസസ്സ് + ഒരു SQLite റൈറ്റർ** . ഉയർന്ന ലഭ്യതയാണ്** പിന്തുണയ്ക്കുന്നില്ല** ആ ടോപ്പോളജിയിൽ.

| പരിമിതി                                                | അനന്തരഫലം                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ഏക എഴുത്തുകാരൻ                                         | ചെയ്യുക** അല്ല** ഒരേ SQLite ഫയലിനെതിരെ ഒന്നിലധികം പകർപ്പുകൾ പ്രവർത്തിപ്പിക്കുക. അത് DB യെ ദുഷിപ്പിക്കുന്നു.                                                                                                                                                                                                                                            |
| പുനഃസൃഷ്ടിക്കുക / പുനരാരംഭിക്കുക / HEALTHCHECK കൊല്ലുക | **പൂർണ്ണ തടസ്സം** ഇൻ-ഫ്ലൈറ്റ് SSE, ഡാഷ്ബോർഡ് സെഷനുകൾ, ഇൻ-മെമ്മറി അവസ്ഥ. കണക്റ്റുചെയ്ത ഓരോ ക്ലയൻ്റും കുറയുന്നു. ശൂന്യമായ എൻഡ് പോയിൻ്റ് വിൻഡോയിൽ പുതിയ അഭ്യർത്ഥനകൾക്ക് ഒരു റിവേഴ്സ് പ്രോക്സി ലഭിക്കും**`502 Bad Gateway: Unknown error`** , OmniRoute JSON അല്ല — ക്ലയൻ്റുകൾക്ക് ഇത് ഒരു ദാതാവിൻ്റെ പരാജയത്തിൽ നിന്ന് വേർതിരിച്ചറിയാൻ കഴിയില്ല (#11015). |
| `/healthz` അതേ ഇവൻ്റ് ലൂപ്പ്                           | തിരക്കുള്ള കാറ്റലോഗ് അല്ലെങ്കിൽ കംപ്രഷൻ ടിക്ക് പേടകങ്ങൾ വൈകിപ്പിക്കും; ഒരു ചെറിയ സമയപരിധി പിന്നീട് പുനരാരംഭിക്കുന്നു** മാത്രം** പകർപ്പ്.                                                                                                                                                                                                               |

**പ്രോബ് മാട്രിക്സ്** ( [കുബർനെറ്റസ് അന്വേഷണ ശുപാർശകളും](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) കാണുക):

| അന്വേഷണം              | ലക്ഷ്യം                                                               | ഉപയോഗിക്കരുത്                                                         |
| --------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------- |
| സജീവത                 | TCP ൽ `PORT` (ഡിഫോൾട്ട് `20128`), അല്ലെങ്കിൽ സോഫ്റ്റ് HTTP `/healthz` | `/api/monitoring/health`                                              |
| സന്നദ്ധത              | HTTP `GET /healthz`                                                   | തിരക്കുള്ള ഇവൻ്റ്-ലൂപ്പിനെ മരിച്ചതായി കണക്കാക്കുന്ന ടൈറ്റ് ടൈംഔട്ടുകൾ |
| ആഴത്തിലുള്ള / മനുഷ്യർ | `/api/monitoring/health`                                              | ഓട്ടോമേറ്റഡ് കുബെലെറ്റ് ലൈവ്നെസ്                                      |

**അപ്ഗ്രേഡുകൾ:** ഓരോ സെഷനും കുറയുമെന്ന് പ്രതീക്ഷിക്കുക. നിങ്ങൾക്ക് കഴിയുമെങ്കിൽ ക്ലയൻ്റുകൾ ഒഴിക്കുക; സ്ഥിരസ്ഥിതി SQLite യിൽ റോളിംഗ് അപ്ഡേറ്റ് ഒന്നുമില്ല. `restart: unless-stopped` പ്ലസ് Docker `HEALTHCHECK` രചിക്കുക, കണ്ടെയ്നർ അനാരോഗ്യകരമാകുമ്പോൾ ഒരേയൊരു പ്രക്രിയയെ മാറ്റിസ്ഥാപിക്കും - അതേ സ്ഫോടന ആരം.

റെഡിമെയ്ഡ് മാനിഫെസ്റ്റുകളും ഹെൽം ചാർട്ടും `deploy/kubernetes/`, `deploy/helm/omniroute/` എന്നിവയിൽ തത്സമയമാണ് - [കുബർനെറ്റസ് വിന്യാസ ഗൈഡ്](../ops/KUBERNETES_DEPLOYMENT_GUIDE.md) കാണുക.

കുബെർനെറ്റസ് സ്നിപ്പെറ്റ് എ** ഒറ്റ പകർപ്പ്** (പുനഃസൃഷ്ടി ആവശ്യമാണ്; ഒരു SQLite ഫയലിനെതിരെ `replicas` ഉയർത്തരുത്):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` സ്ലീപ്പ് SIGTERM ന് മുമ്പായി സേവന എൻഡ്പോയിൻ്റുകൾ ഡ്രോപ്പ് ചെയ്യാൻ kube അനുവദിക്കുന്നു** പുതിയത്** മരിക്കുന്ന പ്രക്രിയയെ തടസ്സപ്പെടുത്തുന്ന ഗതാഗതം നിർത്തുന്നു. ഇൻ-ഫ്ലൈറ്റ് `/v1/responses` SSE ഹെവിവെയ്റ്റ് അഡ്മിഷൻ ലീസുകളിലൂടെ (#11015) `SHUTDOWN_TIMEOUT_MS` (സ്ഥിരസ്ഥിതി 30സെ) വരെ വറ്റിച്ചു. ഇപ്പോഴും പ്രോസസ്സിൽ എത്തുന്ന പുതിയ അഭ്യർത്ഥനകൾക്ക് `503` + `Retry-After: 5` ലഭിക്കും. മാറ്റിസ്ഥാപിക്കൽ തയ്യാറാകുന്നതുവരെ ശൂന്യ-എൻഡ്പോയിൻ്റ് വിടവ് പുനഃസൃഷ്ടിക്കുന്നത് ഒരു ഹാർഡ് ഔട്ടേജായി തുടരുന്നു - അതാണ് SQLite ടോപ്പോളജി, ഒരു പ്രോബ് തെറ്റായ കോൺഫിഗറല്ല.

ബാഹ്യ Postgres / മൾട്ടി-റൈറ്റർ HA ആണ്** അല്ല** ഒരു ഡോക്യുമെൻ്റഡ് സ്റ്റോക്ക് പാത. നിങ്ങൾക്ക് HA ആവശ്യമുണ്ടെങ്കിൽ, ഒരൊറ്റ പകർപ്പ് സൂക്ഷിക്കുക അല്ലെങ്കിൽ പ്രോജക്റ്റ് പ്രത്യേകം പരിശോധിച്ച് ഡോക്യുമെൻ്റ് ചെയ്ത ഒരു ടോപ്പോളജി പ്രവർത്തിപ്പിക്കുക. Postgres/MySQL വർക്ക് [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) -ൽ താമസിക്കുന്നു. അത് ഷിപ്പുചെയ്യുന്നത് വരെ, ഗുണിക്കുന്നതിനുള്ള ഏക പിന്തുണയുള്ള മാർഗം** വലിയ** `/v1/responses` ശേഷി N സ്വതന്ത്ര പ്രക്രിയകളാണ് (അടുത്ത ഭാഗം), ഒരു വോള്യത്തിൽ `replicas > 1` അല്ല.

## സ്കെയിൽ-ഔട്ട്: N സ്വതന്ത്ര പ്രോസസ്സുകൾ

ഒരു Node പ്രോസസിന് **ഒരു V8 heap** ആണ് ഉള്ളത്. പരസ്പരം ഓവർലാപ്പ് ചെയ്യുന്ന ~3 MiB / ~750k-token വലുപ്പമുള്ള രണ്ട് coding-agent `POST /v1/responses` അഭ്യർത്ഥനകൾ (RTK + Caveman), ~12 Gi-ൽ ആ heap-നെ അബോർട്ട് ചെയ്യുകയും (`FATAL ERROR: Reached heap limit`) 16 Gi cgroup-ൽ OOM ഉണ്ടാക്കുകയും ചെയ്യാം. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) കാണുക. ആ അളവ് ഒരു **മെമ്മറി-ബജറ്റ്** മുന്നറിയിപ്പാണ്; ഒരേസമയം പ്രവർത്തിക്കുന്ന ദൈർഘ്യമേറിയ `/v1/responses` അഭ്യർത്ഥനകളുടെ എണ്ണം രണ്ടായി പരിമിതപ്പെടുത്തുന്ന ഉൽപ്പന്നത്തിന്റെ hard-max അല്ല. അതേ V8/cgroup പരിധിയിൽനിന്ന് വലുപ്പം സ്വയമേവ നിർണ്ണയിക്കുന്ന ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ഉപയോഗിച്ചാണ് heavyweight chat admission നിയന്ത്രിക്കുന്നത് — ഇതിനകം വലുപ്പം നിർണ്ണയിച്ച ഒരു പ്രോസസ്സിൽ അതിനെ ഉയർന്ന മൂല്യത്തിലേക്ക് override ചെയ്യുന്നത് (അല്ലെങ്കിൽ പഴയ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` request-count cap സജ്ജീകരിക്കുന്നത്) വീണ്ടും അബോർട്ടിന് കാരണമാകും. ചെറിയ chats, `/healthz`, `/v1/models`, MCP എന്നിവ ആ cap-ൽ **ഉൾപ്പെടുന്നില്ല**.

### ഒരു പ്രോസസ്: രണ്ടിലധികം ദൈർഘ്യമേറിയ `/v1/responses`

പ്രോസസ്-വ്യാപകമായ inflight-byte budget-ൽ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ഇപ്പോഴും ഇടമുണ്ടെങ്കിൽ, **ആരോഗ്യകരമായ** ഒരു പ്രോസസിന് (`OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO`-നേക്കാൾ താഴെയുള്ള heap, സ്ഥിരസ്ഥിതി `0.75`) ഒരേസമയം രണ്ടിലധികം ദൈർഘ്യമേറിയ `POST /v1/responses` അഭ്യർത്ഥനകൾ പ്രവർത്തിപ്പിക്കാൻ **കഴിഞ്ഞേക്കാം**. `OMNIROUTE_CHAT_LARGE_BODY_BYTES`-ന് തുല്യമോ അതിലധികമോ വലുപ്പമുള്ള bodies (സ്ഥിരസ്ഥിതി 256 KiB), ഘടനാപരമായി ഭാരമേറിയ അഭ്യർത്ഥനകളുടെ അതേ heavyweight lease എടുക്കുകയും അതേ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` escape (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ഉപയോഗിക്കുകയും ചെയ്യുന്നു. ഒരേസമയം പ്രവർത്തിക്കുന്ന പതിനുകണക്കിന് ദൈർഘ്യമേറിയ SSE clients (operators-ന് പലപ്പോഴും 40–50 ആവശ്യമാണ്) എന്നത് ഒരു **മെമ്മറി-ബജറ്റ്** ചോദ്യമാണ് — heap + primary/headroom slots + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` എന്നിവയ്ക്ക് അനുയോജ്യമായി വലുപ്പം നിശ്ചയിക്കുക — അല്ലാതെ ഉൽപ്പന്നത്തിന്റെ “പരമാവധി 2” എന്ന കർശന പരിധിയല്ല. സമ്മർദ്ദത്തിലായ heap തുടർന്നും retry ചെയ്യാവുന്ന `503` ഉപയോഗിച്ച് ലോഡ് ഒഴിവാക്കുന്നതിനാൽ #7849 വീണ്ടും സംഭവിക്കില്ല.

**heaps വർധിപ്പിക്കാൻ** (സ്വതന്ത്ര V8 old-spaces) **ഇപ്പോൾ**:

| ചെയ്യുക                                                                                                                                                                                         | ചെയ്യരുത്                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **N containers/pods** പ്രവർത്തിപ്പിക്കുക; ഓരോന്നിനും അതിന്റേതായ `DATA_DIR` / volume ഉണ്ടായിരിക്കണം                                                                                              | ഒരു SQLite file-നായി `replicas > 1` സജ്ജീകരിക്കരുത്                    |
| heap / inflight-byte budget അടിസ്ഥാനമാക്കി heavy in-flight + healthy-headroom-ന്റെ വലുപ്പം നിശ്ചയിക്കുക; 1–2 എന്നത് യാഥാസ്ഥിതികമായ #7849 സ്ഥിരസ്ഥിതിയാണ്, ഉൽപ്പന്നത്തിന്റെ കർശനമായ പരമാവധി അല്ല | ഒരു പ്രോസസിന് 8× RAM-ഉം പരിധിയില്ലാത്ത count cap-ഉം നൽകരുത്            |
| ഐച്ഛികം: **പങ്കിട്ട quota counters**-നായി `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                                                  | Redis-നെ പങ്കിട്ട SQLite ആയി കണക്കാക്കരുത് — അത് അങ്ങനെയല്ല            |
| ഓരോ instance-ലേക്കും provider secrets പകർത്തുക (അല്ലെങ്കിൽ വിഭജിക്കപ്പെട്ട dashboards അംഗീകരിക്കുക)                                                                                             | instances-ൽ ഉടനീളം ഒരൊറ്റ dashboard / ഒരൊറ്റ call-log പ്രതീക്ഷിക്കരുത് |
| ഏതെങ്കിലും load balancer മുന്നിൽ ഉപയോഗിക്കുക; API key അല്ലെങ്കിൽ session അടിസ്ഥാനമാക്കിയുള്ള sticky routing മതിയാകും                                                                            | vendor-specific size-aware middleware നിർബന്ധമാക്കരുത്                 |

ഹാർഡ്വെയർ: ഓരോ instance-ലും ഒരേസമയം പ്രവർത്തിക്കാവുന്ന ദൈർഘ്യമേറിയ `/v1/responses` അഭ്യർത്ഥനകളുടെ എണ്ണം ഒരു **മെമ്മറി-ബജറ്റ്** ചോദ്യമാണ് (heap + inflight-byte / #10110). സ്വതന്ത്രമായ `N` `DATA_DIR`-കൾ ഇപ്പോഴും heaps വർധിപ്പിക്കുന്നു: host RAM, `N × cgroup` ഉൾക്കൊള്ളണം; “N=8 ഉള്ള ഒരൊറ്റ 16 Gi pod” അല്ല. ഒരൊറ്റ SQLite file-ൽ ഒരിക്കലും `replicas > 1` ഉപയോഗിക്കരുത്.

Compose മാതൃക (രണ്ട് heaps, രണ്ട് volumes — `deploy.replicas: 2` അല്ല):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

ഇൻ-പ്രോസസ് സാന്ദ്രത (HTTP isolate-ന് പുറത്തുള്ള compression) [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ആണ്. പങ്കിട്ട durable state-ലുള്ള ഒരൊറ്റ logical cluster [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ആണ്.

## Docker-നുള്ളിലെ Gemini പ്രാദേശിക പിശകുകൾ

Google AI Studio / Gemini API-ക്ക് HTTP 400-ഉം FAILED_PRECONDITION-ഉം കൂടാതെ
`User location is not supported for the API use.` എന്ന സന്ദേശവും നൽകാനാകും. ഹോസ്റ്റിൽ ഒരു അഭ്യർത്ഥന വിജയിക്കുന്നത്
കണ്ടെയ്നർ അതേ ഔട്ട്ബൗണ്ട് റൂട്ട് ഉപയോഗിക്കുന്നു എന്ന് തെളിയിക്കുന്നില്ല. DNS ക്രമീകരണം,
IPv4/IPv6 കണക്റ്റിവിറ്റി, VPN റൂട്ടിംഗ്, കോൺഫിഗർ ചെയ്ത പ്രോക്സികൾ എന്നിവ വ്യത്യസ്തമായിരിക്കാം.
[Google പിന്തുണയ്ക്കുന്ന പ്രദേശങ്ങൾ](https://ai.google.dev/gemini-api/docs/available-regions)
എന്നതോടൊപ്പം യഥാർത്ഥ കണക്ഷൻ റൂട്ടും പരിശോധിക്കുക; ഈ പിശക് മാത്രം ഒരു തെറ്റായ API കീ ആണെന്ന് സൂചിപ്പിക്കുന്നില്ല.

### കണക്ഷൻ-നിർദ്ദിഷ്ട പ്രോക്സിക്ക് മുൻഗണന നൽകുക

ബാധിച്ച Gemini കണക്ഷനായി OmniRoute-ന്റെ [ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ഉപയോഗിക്കുക, തുടർന്ന് അതേ മോഡൽ ഉപയോഗിച്ച് **കണക്ഷൻ പരിശോധിക്കുക** എന്നതും ഒരു ചെറിയ അഭ്യർത്ഥനയും
വീണ്ടും നടത്തുക. ഇത് റൂട്ടിംഗ് മാറ്റം ആ കണക്ഷനിൽ മാത്രമായി പരിമിതപ്പെടുത്തുന്നു. പ്രോക്സി
കണ്ടെയ്നറിൽ നിന്ന് ആക്സസ് ചെയ്യാനാകുന്നുണ്ടെന്നും കണക്ഷൻ യഥാർത്ഥത്തിൽ അതിനെ തിരഞ്ഞെടുക്കുന്നുണ്ടെന്നും
സ്ഥിരീകരിക്കുക. റൂട്ട് മാറ്റുന്നത് അപ്സ്ട്രീം പ്രാദേശിക യോഗ്യത ഉറപ്പാക്കുന്നില്ല.

### ഹോസ്റ്റിന്റെയും കണ്ടെയ്നറിന്റെയും നെറ്റ്വർക്കിംഗ് താരതമ്യം ചെയ്യുക

ഓതന്റിക്കേറ്റ് ചെയ്ത ഫലങ്ങൾ താരതമ്യം ചെയ്യുമ്പോൾ കീയും മോഡലും അഭ്യർത്ഥനയും ഒരേപോലെ നിലനിർത്തുക; ക്രെഡൻഷ്യലുകൾ,
പ്രോക്സി പാസ്വേഡുകൾ, അല്ലെങ്കിൽ പൂർണ്ണമായ ഓതറൈസേഷൻ ഹെഡറുകൾ ഒരിക്കലും ഒരു ഇഷ്യൂവിൽ
പേസ്റ്റ് ചെയ്യരുത്. ആദ്യം OS റിസോൾവർ ഏതൊക്കെ അഡ്രസ് ഫാമിലികളാണ് നൽകുന്നതെന്ന് പരിശോധിക്കുക; ഹോസ്റ്റിലും
കണ്ടെയ്നറിനുള്ളിലും ഒരേ കമാൻഡ് ഉപയോഗിക്കുക:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` എന്നത് നിങ്ങൾ പ്രവർത്തിപ്പിക്കുന്ന സർവീസ് ഉപയോഗിച്ച് മാറ്റിസ്ഥാപിക്കുക (ഉദാഹരണത്തിന്, `omniroute-web`). ഈ
കമാൻഡുകൾ ക്രെഡൻഷ്യലുകളോ IP വിലാസങ്ങളോ ഇല്ലാതെ അഡ്രസ് ഫാമിലികൾ പ്രിന്റ് ചെയ്യുന്നു. മടക്കിനൽകുന്ന `6`
ഒരു IPv6 DNS ഫലം മാത്രമാണ് കാണിക്കുന്നത്: അത് ഉപയോഗിക്കാനാകുന്ന IPv6 റൂട്ടോ API ആക്സസോ
തെളിയിക്കുന്നില്ല. `curl` ഇൻസ്റ്റാൾ ചെയ്തിട്ടുള്ളിടത്ത്, രണ്ട് പരിതസ്ഥിതികളിലും
`curl -4 -I https://generativelanguage.googleapis.com` എന്നത്
`curl -6 -I https://generativelanguage.googleapis.com` എന്നതുമായി താരതമ്യം ചെയ്യുക.
ഓതന്റിക്കേറ്റ് ചെയ്യാത്ത പിശകാണെങ്കിലും, ഒരു HTTP പ്രതികരണം ആ പരിശോധനയ്ക്കുള്ള കണക്റ്റിവിറ്റി തെളിയിക്കുന്നു;
ഓതന്റിക്കേറ്റ് ചെയ്ത മോഡൽ അഭ്യർത്ഥന മാത്രമാണ് Gemini യോഗ്യത പരിശോധിക്കുന്നത്.

### ഹോസ്റ്റ്-തല പകരമാർഗം: പ്രവർത്തിക്കുന്ന IPv6-ഉം റിസോൾവർ നയവും

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762)-ന്റെ റിപ്പോർട്ടർ കണ്ടെയ്നർ IPv6 പ്രവർത്തനക്ഷമമാക്കുകയും glibc അഡ്രസ്
തിരഞ്ഞെടുക്കൽ മാറ്റുകയും ചെയ്തുകൊണ്ട് അവരുടെ പരിതസ്ഥിതിയിൽ ആക്സസ് പുനഃസ്ഥാപിച്ചു.
ഇതിനെ പരിതസ്ഥിതി-നിർദ്ദിഷ്ടമായ ഒരു പകരമാർഗമായി കണക്കാക്കുക. റിസോൾവർ മുൻഗണനകൾ ക്രമീകരിക്കുന്നതിന് മുമ്പ്
ഹോസ്റ്റിൽ പ്രവർത്തിക്കുന്ന IPv6, കണ്ടെയ്നർ എഗ്രസ്/റൂട്ടിംഗ്, ഫയർവാൾ നിയമങ്ങൾ എന്നിവ സ്ഥിരീകരിക്കുക.
ഒരു സ്വകാര്യ ULA വിലാസം മാത്രമുള്ളത് പൊതു IPv6 കണക്റ്റിവിറ്റി സ്ഥാപിക്കുന്നില്ല.

Compose-ന്റെ ഡിഫോൾട്ട് നെറ്റ്വർക്കിൽ ഇതിനകം അറ്റാച്ച് ചെയ്തിരിക്കുന്ന സർവീസുകൾക്ക്, ഈ ഫ്രാഗ്മെന്റ്
ആ നെറ്റ്വർക്കിൽ IPv6 പ്രവർത്തനക്ഷമമാക്കുന്നു; നിങ്ങളുടെ സർവീസിന്റെ ശേഷിക്കുന്ന ഭാഗങ്ങളും പോർട്ടുകളും വോള്യങ്ങളും കോൺഫിഗറേഷനും നിലനിർത്തുക:

```yaml
networks:
  default:
    enable_ipv6: true
```

നാമകരണം ചെയ്ത നെറ്റ്വർക്കാണെങ്കിൽ, സർവീസ് യഥാർത്ഥത്തിൽ ചേരുന്ന നെറ്റ്വർക്കിൽ ഇത് പ്രവർത്തനക്ഷമമാക്കുക. Docker-ന്
ഒരു ULA സബ്നെറ്റ് അനുവദിക്കാനാകും; നിങ്ങളുടെ നെറ്റ്വർക്കിന് ആവശ്യമുള്ളപ്പോൾ മാത്രം, മറ്റൊന്നുമായി ഓവർലാപ്പ് ചെയ്യാത്ത വ്യക്തമായൊരു സബ്നെറ്റ്
തിരഞ്ഞെടുക്കുക. [Docker IPv6 നെറ്റ്വർക്കിംഗ്](https://docs.docker.com/engine/daemon/ipv6/)
എന്നതും [Compose നെറ്റ്വർക്ക് ഓപ്ഷനുകൾ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) എന്നതും കാണുക.

ഒരു **glibc-അധിഷ്ഠിത ഇമേജിൽ**, `/etc/gai.conf`-ന് അഡ്രസ് തിരഞ്ഞെടുക്കൽ മാറ്റാനാകും. നിലവിലെ
റെപ്പോസിറ്ററി Dockerfile Debian ഉപയോഗിക്കുന്നു; ഇഷ്ടാനുസൃത musl-അധിഷ്ഠിത ഇമേജുകൾ ഈ സംവിധാനം പങ്കിടുന്നില്ല.
റിപ്പോർട്ട് ചെയ്ത ക്രമീകരണം ULA ലേബൽ `label fc00::/7 6` എന്നതിൽ നിന്ന്
`label fc00::/7 1` എന്നതിലേക്ക് മാറ്റുന്നു. ഇമേജിന്റെ പൂർണ്ണ നയ പട്ടികയിൽ നിന്ന് ആരംഭിക്കുകയും അതിലെ മറ്റ്
എൻട്രികൾ നിലനിർത്തുകയും ചെയ്യുക: ഒരു `label` അല്ലെങ്കിൽ `precedence` എൻട്രി ചേർക്കുന്നത് ആ ഡിഫോൾട്ട് പട്ടികയെ മാറ്റിസ്ഥാപിക്കുന്നു, അതിനാൽ മാറ്റിയ വരി
മാത്രം അടങ്ങിയ ഫയൽ മതിയാകില്ല.
[glibc കോൺഫിഗറേഷൻ റഫറൻസ്](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ആ സെമാന്റിക്സ് രേഖപ്പെടുത്തുന്നു. അവലോകനം ചെയ്ത ഫയൽ `/etc/gai.conf`-ൽ റീഡ്-ഒൺലി ആയി ബൈൻഡ്-മൗണ്ട്
ചെയ്ത ശേഷം, അത് പ്രയോഗിക്കുന്നതിനായി സർവീസ് പുനഃസൃഷ്ടിക്കുക.

ഇത് **ആ കണ്ടെയ്നറിലെ എല്ലാ ഔട്ട്ബൗണ്ട് ട്രാഫിക്കിനുമുള്ള** OS അഡ്രസ് തിരഞ്ഞെടുക്കൽ മാറ്റുന്നു.
ഇത് എല്ലാ ആപ്ലിക്കേഷനെയും IPv6 തിരഞ്ഞെടുക്കാൻ നിർബന്ധിക്കുന്നില്ല: Node-ന്റെ DNS ക്രമവും കണക്ഷൻ
തിരഞ്ഞെടുക്കലും പ്രസക്തമാണ്. പ്രത്യേകിച്ച്, `--dns-result-order=ipv4first` IPv4-ന് മുൻഗണന നൽകുന്നു,
അതിനാൽ IPv4-മാത്രമുള്ള പരാജയത്തിന് അതൊരു പരിഹാരമല്ല. [Node DNS ക്രമീകരണം](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) കാണുക.

ഹോസ്റ്റ്-തല മാറ്റങ്ങൾക്ക് ശേഷം Gemini-യും നിങ്ങളുടെ മറ്റ് പ്രൊവൈഡർമാരും വീണ്ടും പരിശോധിക്കുക. പഴയ നിലയിലേക്ക് മടങ്ങാൻ,
ഇഷ്ടാനുസൃത `gai.conf` മൗണ്ട് നീക്കംചെയ്യുക, മുമ്പത്തെ നെറ്റ്വർക്ക് കോൺഫിഗറേഷൻ പുനഃസ്ഥാപിക്കുക, കൂടാതെ
ഒരു മെയിന്റനൻസ് വിൻഡോയിൽ ബാധിച്ച സർവീസ്/നെറ്റ്വർക്ക് പുനഃസൃഷ്ടിക്കുക. ഒരു നെറ്റ്വർക്ക് പുനഃസൃഷ്ടിക്കുന്നത്
അതിലേക്ക് അറ്റാച്ച് ചെയ്തിരിക്കുന്ന മറ്റ് കണ്ടെയ്നറുകൾക്ക് തടസ്സമുണ്ടാക്കാം; സ്ഥിരമായ ഡാറ്റ വോള്യം ഇല്ലാതാക്കരുത്.

## പ്രധാന കുറിപ്പുകൾ

- **SQLite WAL മോഡ്:** ഏറ്റവും പുതിയ മാറ്റങ്ങൾ `storage.sqlite`-ലേക്ക് checkpoint ചെയ്യാൻ OmniRoute-ന് കഴിയുന്നവിധം `docker stop` പൂർത്തിയാകാൻ അനുവദിക്കണം. ഉൾപ്പെടുത്തിയിട്ടുള്ള Compose ഫയലുകളിൽ ഇതിനകം 40s stop grace period സജ്ജീകരിച്ചിട്ടുണ്ട്. നിങ്ങൾ image നേരിട്ട് പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, `--stop-timeout 40` നിലനിർത്തുക.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** പതിവ്/pre-write backup-കൾ ബാഹ്യമായി കൈകാര്യം ചെയ്യുന്നുണ്ടെങ്കിൽ ഇത് `true` ആയി സജ്ജീകരിക്കുക. നിലവിലുള്ള database migration-കൾക്ക് അവയുടേതായ ദീർഘകാലം നിലനിൽക്കുന്ന സുരക്ഷാ snapshot-ഉം mass-migration guard-ഉം ഇപ്പോഴും ആവശ്യമാണ്.
- **ഡാറ്റ നിലനിർത്തൽ:** container പുനരാരംഭങ്ങൾക്കിടയിലും നിങ്ങളുടെ database, key-കൾ, configuration-കൾ എന്നിവ നിലനിർത്താൻ എല്ലായ്പ്പോഴും `/app/data`-ലേക്ക് ഒരു volume mount ചെയ്യുക.
- **പോർട്ട് കോൺഫിഗറേഷൻ:** ഡിഫോൾട്ട് `20128` port മാറ്റാൻ `PORT` environment variable override ചെയ്യുക.
