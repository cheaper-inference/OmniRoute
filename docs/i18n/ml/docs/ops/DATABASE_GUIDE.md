- `src/lib/db/core.ts` — സിംഗിൾടൺ + SCHEMA_SQL (17 അടിസ്ഥാന പട്ടികകൾ)
- `src/lib/db/migrationRunner.ts` — പതിപ്പ് അടിസ്ഥാനമാക്കിയുള്ള മൈഗ്രേഷനുകൾ

- `src/lib/db/encryption.ts` — എൻക്രിപ്ഷൻ സഹായികൾ
- `src/lib/db/backup.ts` — ബാക്കപ്പ് എക്സ്പോർട്ട്/ഇംപോർട്ട്
- `src/lib/db/healthCheck.ts` — ആരോഗ്യനില നിർണ്ണയം

## എന്തുകൊണ്ട് SQLite?

നിരവധി കാരണങ്ങളാൽ PostgreSQL/MySQL-നേക്കാൾ SQLite ആണ് OmniRoute തിരഞ്ഞെടുത്തത്:

| ഘടകം               | SQLite                                    | PostgreSQL                                      |
| ------------------ | ----------------------------------------- | ----------------------------------------------- |
| **വിന്യാസം**       | എംബെഡഡ് — പ്രത്യേക സെർവർ ആവശ്യമില്ല       | സെർവർ സജ്ജീകരണം ആവശ്യമാണ്                       |
| **എൻക്രിപ്ഷൻ**     | ആപ്ലിക്കേഷൻ-തലം (AES-256-GCM)             | ബിൽറ്റ്-ഇൻ TDE                                  |
| **പ്രകടനം**        | ചെറുതും ഇടത്തരവുമായ വർക്ക്ലോഡുകൾക്ക് വേഗത | വലിയ തോതിലുള്ള സമകാലിക റൈറ്റുകൾക്ക് മികച്ചത്    |
| **സമകാലികത**       | WAL മോഡ് സമകാലിക റീഡുകൾ അനുവദിക്കുന്നു    | സമ്പൂർണ്ണ MVCC                                  |
| **ബാക്കപ്പ്**      | ഒറ്റ ഫയലിന്റെ പകർപ്പ്                     | `pg_dump` അല്ലെങ്കിൽ ഫയൽസിസ്റ്റം സ്നാപ്പ്ഷോട്ട് |
| **ഉപയോഗ സാഹചര്യം** | ഓരോ ഉപയോക്താവിനുമുള്ള ഇൻസ്റ്റാൾ, എംബെഡഡ്  | മൾട്ടി-ടെനന്റ് SaaS                             |

**ഒറ്റ ഉപയോക്താവ്, ഒറ്റ ഇൻസ്റ്റൻസ്** വിന്യാസങ്ങൾക്ക് (OmniRoute-ന്റെ പ്രാഥമിക ഉപയോഗ സാഹചര്യം), SQLite കൂടുതൽ ലളിതവും വേഗതയേറിയതുമാണ്.

### WAL ജേർണലിങ്

`core.ts` ഡാറ്റാബേസ് **WAL (Write-Ahead Logging) മോഡിൽ** തുറക്കുന്നു:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

റൈറ്റുകൾ നടക്കുമ്പോൾ **സമകാലിക റീഡുകൾ** WAL അനുവദിക്കുന്നു — അഭ്യർത്ഥനകൾ രേഖപ്പെടുത്തുന്നതിനിടെ ക്വറികൾ നടത്തുന്ന ഡാഷ്ബോർഡിന് ഇത് പ്രധാനമാണ്.

ഡിഫോൾട്ട് കാഷ് വലുപ്പം **65,536 KiB (64 MiB)** ആണ്. നെഗറ്റീവ്
`cache_size`-നെ KiB-യിലുള്ള ഏകദേശ ഉയർന്ന പരിധിയായി SQLite വ്യാഖ്യാനിക്കുകയും ആവശ്യാനുസരണം പേജുകൾ അനുവദിക്കുകയും ചെയ്യുന്നു.
**ക്രമീകരണങ്ങൾ > സിസ്റ്റവും സംഭരണവും > കാഷ് വലുപ്പം** എന്നതിൽ **1 മുതൽ
1,000,000 KiB** വരെയുള്ള പൂർണ്ണസംഖ്യാ മൂല്യങ്ങൾ സ്വീകരിക്കുന്നു; ക്രമീകരണം സംരക്ഷിക്കുമ്പോൾ അത് നിലവിൽ പ്രവർത്തിക്കുന്ന ഡാറ്റാബേസ് കണക്ഷനിൽ പ്രയോഗിക്കപ്പെടുന്നു,
കൂടാതെ സ്റ്റാർട്ടപ്പിൽ നിലനിർത്തിയ മൂല്യം OmniRoute പുനഃസ്ഥാപിക്കുന്നു.

## ഡാറ്റാബേസ് സ്ഥാനം

SQLite ഫയൽ ഇവിടെ സംഭരിച്ചിരിക്കുന്നു:

| OS      | പാത                                                       |
| ------- | --------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                             |
| macOS   | `~/.omniroute/storage.sqlite`                             |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                 |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` വഴി ക്രമീകരിക്കാം) |

അനുബന്ധ ഫയലുകൾ:

- `storage.sqlite-wal` — റൈറ്റ്-അഹെഡ് ലോഗ്
- `storage.sqlite-shm` — പങ്കിട്ട മെമ്മറി ഫയൽ
- `call_logs/` — അഭ്യർത്ഥന പേലോഡ് ആർട്ടിഫാക്റ്റുകൾ (പ്രവർത്തനക്ഷമമാക്കിയിട്ടുണ്ടെങ്കിൽ)

**സ്ഥാനം ഓവർറൈഡ് ചെയ്യുക:**

```bash
DATA_DIR=/custom/path omniroute
```

## ഡൊമെയ്ൻ മൊഡ്യൂൾ ആർക്കിടെക്ചർ

OmniRoute-ന്റെ ഡാറ്റാബേസിൽ `src/lib/db/` എന്നതിൽ **110 ടോപ്പ്-ലെവൽ TypeScript മൊഡ്യൂളുകൾ** ഉണ്ട്. ഓരോ ഡൊമെയ്ൻ മൊഡ്യൂളും:

- ഒന്നോ അതിലധികമോ നിർദ്ദിഷ്ട ടേബിളുകളുടെ ഉടമസ്ഥത വഹിക്കുന്നു
- ടൈപ്പ് ചെയ്ത CRUD ഫങ്ഷനുകൾ എക്സ്പോർട്ട് ചെയ്യുന്നു
- മറ്റൊരു മൊഡ്യൂളിന്റെ ടേബിളുകൾ ഒരിക്കലും നേരിട്ട് ഉപയോഗിക്കുന്നില്ല
- DB ആക്സസ് ചെയ്യാൻ `core.ts`-ൽ നിന്നുള്ള `getDbInstance()` ഉപയോഗിക്കുന്നു

### മൊഡ്യൂൾ അതിരുകൾ

ഒരു പ്രധാന ആർക്കിടെക്ചറൽ നിയമം: **മൊഡ്യൂളുകൾ പരസ്പരം മറ്റൊന്നിന്റെ ടേബിളുകൾ നേരിട്ട് ആക്സസ് ചെയ്യരുത്**. മറ്റൊരു മൊഡ്യൂളിന്റെ ഡാറ്റ ഉപയോഗിച്ച് പ്രവർത്തിക്കാൻ, ആ മൊഡ്യൂളിൽ നിന്നുള്ള ഫങ്ഷൻ ഇംപോർട്ട് ചെയ്യുക.

```ts
// ❌ തെറ്റ്: മറ്റൊരു മൊഡ്യൂളിൽ നിന്നുള്ള നേരിട്ടുള്ള SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ശരി: providers മൊഡ്യൂളിലെ ഫങ്ഷൻ ഉപയോഗിക്കുക
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

ഈ നിയമം കോഡ് റിവ്യൂവിലൂടെ നടപ്പാക്കുന്നു — സ്റ്റാറ്റിക് പരിശോധനയില്ല, എന്നാൽ ലംഘനങ്ങൾ ഫ്ലാഗ് ചെയ്യപ്പെടും.

## മൈഗ്രേഷനുകൾ

OmniRoute ഉപയോഗിക്കുന്നു** വേർഷൻ ചെയ്ത, ഐഡമ്പറ്റൻ്റ് മൈഗ്രേഷനുകൾ** `src/lib/db/migrations/`. ഓരോ മൈഗ്രേഷനും ഒരൊറ്റ SQL ഫയലാണ്. രണ്ട് പേരിടൽ ഫോർമാറ്റുകൾ ഒരുമിച്ച് നിലനിൽക്കുന്നു; `_omniroute_migrations` ൽ രേഖപ്പെടുത്തിയിരിക്കുന്ന പതിപ്പ് സംഖ്യാ പ്രിഫിക്സാണ്.

### മൈഗ്രേഷൻ നാമകരണം

| ഫോർമാറ്റ്                                           | ഉദാഹരണം                              | ഇതിനായി ഉപയോഗിച്ചു                                                                                                                                                         |
| --------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (കൃത്യമായി 3 അക്കങ്ങൾ)        | `241_seen_models.sql`                | പഴയ സീരീസ് `001`–`241`. ടൈംസ്റ്റാമ്പ് ഫോർമാറ്റ് വന്നപ്പോൾ ഫ്രീസുചെയ്തു (`240`, `241` അതിന് തൊട്ടുമുമ്പ് ലയിപ്പിച്ചിരുന്നു): ഒരു പുതിയ ഫയലിനും തുടർച്ചയായ നമ്പർ ലഭിക്കില്ല. |
| `YYYYMMDDHHMMSS_description.sql` (14 അക്കങ്ങൾ, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 മുതൽ സൃഷ്ടിച്ച ഓരോ മൈഗ്രേഷനും.                                                                                                                                  |

എന്തുകൊണ്ടാണ് മാറ്റം: തുടർച്ചയായ സംഖ്യകൾക്കൊപ്പം, സമാന്തര PRs അതേ അടുത്ത സംഖ്യ തിരഞ്ഞെടുത്തു, ഒന്നൊഴികെ മറ്റെല്ലാവരും ലയിപ്പിക്കുന്നതിന് മുമ്പ് വീണ്ടും നമ്പർ നൽകേണ്ടതുണ്ട്. ഒരു UTC ടൈംസ്റ്റാമ്പ് ഓരോ PR യ്ക്കും അതിൻ്റേതായ പതിപ്പ് നൽകുന്നു.

ടൈംസ്റ്റാമ്പ് ഫോർമാറ്റിനുള്ള നിയമങ്ങൾ ( `npm run check:migration-numbering` നടപ്പിലാക്കിയത്, `scripts/check/lib/migrationNaming.mjs` ലെ ജനറേറ്ററുമായി പങ്കിട്ടത്):

- ടൈംസ്റ്റാമ്പ് ഒരു യഥാർത്ഥ UTC തീയതിയും സമയവുമാണ്, `20261113000000` നേക്കാൾ മുമ്പല്ല, ഭാവിയിൽ 10 മിനിറ്റിൽ കൂടരുത്.
- ഒരു അക്ഷരത്തിൽ (`a-z`, `0-9`, പദങ്ങൾക്കിടയിലുള്ള ഒറ്റ `_` ) ആരംഭിക്കുന്ന ചെറിയക്ഷരം `snake_case` ആണ് വിവരണം, പരമാവധി 80 പ്രതീകങ്ങൾ.
- ഒരേ ടൈംസ്റ്റാമ്പുള്ള രണ്ട് ഫയലുകൾ ഡ്യൂപ്ലിക്കേറ്റാണ്.
- നോ-ഗാപ്പ് നിയമം പഴയ സീരീസിന് മാത്രമേ ബാധകമാകൂ: അറിയപ്പെടുന്ന വിടവുകൾ `026`, `055`, `121` ഒഴികെ `001` മുതൽ `241` വരെയുള്ള എല്ലാ സംഖ്യകളും നിലനിൽക്കണം. `241` (അല്ലെങ്കിൽ ഏതെങ്കിലും പഴയ ഫയൽ) ഇല്ലാതാക്കുന്നത് ഗേറ്റ് പരാജയപ്പെടുന്നു. `001`, `241` ഒരിക്കലും `KNOWN_GAPS` അനുവദനീയ പട്ടികയിൽ ചേർക്കാൻ കഴിയില്ല. ടൈംസ്റ്റാമ്പ് ചെയ്ത ഫയലുകൾ ഒരിക്കലും വിടവ് സൃഷ്ടിക്കുന്നില്ല.
- `src/lib/db/migrations/` യിലെ എല്ലാ എൻട്രികളും സാധുവായ ചെറിയക്ഷര `.sql` നാമമുള്ള ഒരു സാധാരണ ഫയലായിരിക്കണം. ഒരു ഡയറക്ടറി, ഒരു സിംലിങ്ക്, ഒരു `.SQL` അല്ലെങ്കിൽ `.sql.bak` ഫയൽ, ഒരു മറഞ്ഞിരിക്കുന്ന ഫയൽ അല്ലെങ്കിൽ സ്പെയ്സുള്ള ഒരു പേര് ഗേറ്റിനെ പരാജയപ്പെടുത്തുന്നു, കാരണം റണ്ണർ അത് നിശബ്ദമായി ഒഴിവാക്കുകയോ ബൂട്ടിൽ തകരുകയോ ചെയ്യും.

**ഓർഡർ പ്രയോഗിക്കുക.** പ്രിഫിക്സിൻ്റെ സംഖ്യാ മൂല്യമനുസരിച്ചാണ് റണ്ണർ അടുക്കുന്നത്, ടെക്സ്റ്റ് മുഖേനയല്ല: പഴയ `001`–`241` ഫയലുകൾ, പിന്നീട് ടൈംസ്റ്റാമ്പ് ക്രമത്തിൽ ടൈംസ്റ്റാമ്പ് ചെയ്ത ഫയലുകൾ, തുടർന്ന് `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ൽ രജിസ്റ്റർ ചെയ്തിട്ടുള്ള ഏതെങ്കിലും നെയിംസ്പെയ്സ് ഡയറക്ടറികൾ ( `ee-001` പോലുള്ള പതിപ്പുകൾ). തീർച്ചപ്പെടുത്താത്ത മൈഗ്രേഷൻ എന്നത് `_omniroute_migrations` യിൽ ഇല്ലാത്ത ഏത് ഫയലാണ്, അതിനാൽ പുതിയതിന് ശേഷം ലയിക്കുന്ന പഴയ ബ്രാഞ്ചിൽ നിന്നുള്ള മൈഗ്രേഷൻ നിലവിലുള്ള ഡാറ്റാബേസുകളിൽ ഇപ്പോഴും ബാധകമാണ്.

**ടൈംസ്റ്റാമ്പ് സൃഷ്ടി ക്രമമാണ്, ലയന ക്രമമല്ല.** നിങ്ങളുടെ മൈഗ്രേഷൻ a ഉപയോഗിച്ചുള്ള മൈഗ്രേഷൻ സൃഷ്ടിച്ച പട്ടികയെയോ നിരയെയോ ആശ്രയിച്ചിരിക്കുന്നുവെങ്കിൽ** പുതിയത്** ടൈംസ്റ്റാമ്പ് (ഉദാഹരണത്തിന്, ആദ്യം ലയിപ്പിച്ച മറ്റൊരു PR യിൽ നിന്ന് ഒന്ന്), ഒരു പുതിയ ഡാറ്റാബേസ് ആദ്യം നിങ്ങളുടേത് പ്രവർത്തിപ്പിക്കുകയും പരാജയപ്പെടുകയും ചെയ്യും. നിങ്ങളുടെ PR ഇപ്പോഴും തുറന്നിരിക്കുമ്പോൾ, ഫയലിൻ്റെ പേര് `npm run db:new-migration` ഉപയോഗിച്ച് പുനഃസൃഷ്ടിക്കുക, അതുവഴി അതിന് ഒരു പുതിയ ടൈംസ്റ്റാമ്പ് ലഭിക്കും, അല്ലെങ്കിൽ അത് സ്വതന്ത്രമാക്കുക. `npm run test:migrations:fresh` ഓരോ മൈഗ്രേഷനും ഒരു ശൂന്യമായ ഡാറ്റാബേസിലേക്ക് പ്രയോഗിക്കുകയും ഇത് പിടിക്കുകയും ചെയ്യുന്നു.

### ലയിപ്പിച്ച മൈഗ്രേഷൻ ഒരിക്കലും ഇല്ലാതാക്കുകയോ പുനർനാമകരണം ചെയ്യുകയോ ചെയ്യുന്നില്ല

ഒരു മൈഗ്രേഷൻ ഫയൽ ഒരു റിലീസ് ബ്രാഞ്ചിലോ `main` യിലോ ആയിക്കഴിഞ്ഞാൽ, അത് ഇതിനകം തന്നെ ഹോമോലോഗ്, ഡെവലപ്പർ ഡാറ്റാബേസുകളിലും VPS ഇൻസ്റ്റാളുകളിലും എൻ്റർപ്രൈസ് സമന്വയത്തിലും പ്രവർത്തിക്കുന്നു. അന്നുമുതൽ:

- **ഒരിക്കലും ഇല്ലാതാക്കരുത്.** നവീകരിച്ച ഡാറ്റാബേസുകൾ സൂക്ഷിക്കുമ്പോൾ പുതിയ ഇൻസ്റ്റാളുകൾക്ക് അതിൻ്റെ സ്കീമ നഷ്ടപ്പെടും.
- **ഒരിക്കലും പേരുമാറ്റരുത്.** `_omniroute_migrations` യിലെ പതിപ്പ് ഇനി ഒരു ഫയലുമായി പൊരുത്തപ്പെടുന്നില്ല, അതിനാൽ ഇതിനകം പ്രയോഗിച്ച എല്ലാ ഡാറ്റാബേസും അത് വീണ്ടും പ്രവർത്തിപ്പിക്കും. നോൺ-ഇംപോട്ടൻ്റ് SQL തുടർന്ന് ഡാറ്റ ഡ്യൂപ്ലിക്കേറ്റ് ചെയ്യുകയോ ബൂട്ട് നിർത്തുകയോ ചെയ്യുന്നു.
- **മറ്റൊരു സ്കീമ ആവശ്യമുണ്ടോ?** `npm run db:new-migration` ഉപയോഗിച്ച് ഒരു പുതിയ മൈഗ്രേഷൻ സൃഷ്ടിക്കുക.

ഇതുവരെ ലയിപ്പിച്ചിട്ടില്ലാത്ത ഒരു ഫയലിന് മാത്രമേ പേരുമാറ്റൽ സുരക്ഷിതമാകൂ, ഗേറ്റിൻ്റെ സൂചനകൾ സൂചിപ്പിക്കുന്നത് ഇതാണ്. ഒരു റിലീസ് ടാഗ് ഇവിടെ ഒന്നും മാറ്റുന്നില്ല: ഒരു `release/v*` ബ്രാഞ്ചിലേക്കുള്ള ഓരോ പുഷും Docker `:next` ഇമേജ് പ്രസിദ്ധീകരിക്കുകയും ഹോമോലോഗ്, VPS ഇൻസ്റ്റാളുകൾ, എൻ്റർപ്രൈസ് സമന്വയം എന്നിവയിൽ പ്രവർത്തിക്കുകയും ചെയ്യുന്നു, അതിനാൽ ഏതെങ്കിലും `vX.Y.Z` ടാഗ് നിലനിൽക്കുന്നതിന് മുമ്പ് ഒരു ലയിപ്പിച്ച മൈഗ്രേഷൻ യഥാർത്ഥ ഡാറ്റാബേസുകളിൽ പ്രവർത്തിക്കുന്നു. ടാഗ് ചെയ്താലും ഇല്ലെങ്കിലും അടിസ്ഥാന ഫയലിൻ്റെ എല്ലാ നീക്കം ചെയ്യലും ഗേറ്റ് പരാജയപ്പെടുന്നു.

- **ലയിപ്പിച്ച മൈഗ്രേഷൻ പഴയപടിയാക്കുന്നു.** ഫയൽ ഇല്ലാതാക്കുന്ന ഒരു `git revert` ഗേറ്റിനെ പരാജയപ്പെടുത്തുന്നു. ഒരു പുതിയ മൈഗ്രേഷനിൽ ഫയൽ സൂക്ഷിക്കുകയും അതിൻ്റെ സ്കീമ പഴയപടിയാക്കുകയും ചെയ്യുക: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` മുതലായവ. നവീകരിച്ചതും പുതിയതുമായ ഡാറ്റാബേസുകൾ അതേ സ്കീമയിൽ അവസാനിക്കും.
- **ഒരു അംഗീകൃത പുനർനാമകരണം: ഒരു അനുയോജ്യത എൻട്രിയും സമാനമായ ഉള്ളടക്കവും.** ഒരു ലയിപ്പിച്ച ഫയൽ നീങ്ങേണ്ടതുണ്ടെങ്കിൽ (ഉദാഹരണത്തിന്, ലയിപ്പിച്ച രണ്ട് ഫയലുകൾ ടൈംസ്റ്റാമ്പ് പങ്കിടുകയും റണ്ണർ ഒരു പതിപ്പ് കൂട്ടിയിടിയോടെ നിർത്തുകയും ചെയ്യുന്നു), പിന്നീടുള്ളതിൻ്റെ പേര് SQL തൊടാതെ തന്നെ പുനർനാമകരണം ചെയ്യുകയും `src/lib/db/migrationRunner/constants.ts` ൽ `RENAMED_MIGRATION_COMPATIBILITY` യിലേക്ക് `{ fromVersion, fromName, toVersion, toName }` ചേർക്കുകയും ചെയ്യുക. പഴയ പതിപ്പ് പ്രയോഗിച്ച ഡാറ്റാബേസുകൾക്ക് ഫയൽ വീണ്ടും പ്രവർത്തിപ്പിക്കുന്നതിന് പകരം അവയുടെ `_omniroute_migrations` വരി നീക്കി. അത്തരമൊരു പുനർനാമകരണത്തെക്കുറിച്ച് ഗേറ്റ് മുന്നറിയിപ്പ് നൽകുന്നു, പുതിയ ടൈംസ്റ്റാമ്പ് എന്തായാലും അതിൽ കമ്മ്യൂട്ടേഷൻ പരിശോധന നടത്തുന്നു: പുതിയ ഇൻസ്റ്റാളുകൾ ഫയലിനെ അതിൻ്റെ പുതിയ സ്ഥാനത്ത് പ്രയോഗിക്കുന്നു, അപ്ഗ്രേഡുചെയ്ത ഡാറ്റാബേസുകൾ അങ്ങനെയല്ല, അതിനാൽ പഴയതിന് സമീപം പുതിയ ടൈംസ്റ്റാമ്പ് തിരഞ്ഞെടുക്കുക. ഉള്ളടക്കം മാറിയാലോ (ഒരു സ്കീമ മാറ്റം ഇപ്പോഴും പുതിയ മൈഗ്രേഷനിൽ നടക്കുന്നു) അല്ലെങ്കിൽ എൻട്രിയുടെ ടാർഗെറ്റ് ഫയൽ ഡിസ്കിൽ ഇല്ലെങ്കിൽ ഗേറ്റ് പുനർനാമകരണം ചെയ്യുന്നതിൽ പരാജയപ്പെടുന്നു.
- **ഒരേ ടൈംസ്റ്റാമ്പിനുള്ളിൽ ഒരിക്കലും പേരുമാറ്റരുത്.** ടൈംസ്റ്റാമ്പ് നിലനിർത്തുകയും വിവരണം മാത്രം മാറ്റുകയും ചെയ്യുന്ന ഒരു പേരുമാറ്റം പ്രവേശനത്തോടെയോ അല്ലാതെയോ ഗേറ്റിനെ പരാജയപ്പെടുത്തുന്നു. `toVersion` അതിൻ്റെ `fromVersion` ന് തുല്യമായ ഒരു എൻട്രി ഉപയോഗിച്ച്, റണ്ണർ പഴയ `_omniroute_migrations` വരി ഇല്ലാതാക്കുകയും ഇതിനകം പ്രവർത്തിപ്പിച്ച എല്ലാ ഡാറ്റാബേസിലും ഫയൽ വീണ്ടും പ്രയോഗിക്കുകയും ചെയ്യുന്നു. ഒരു എൻട്രി കൂടാതെ, റണ്ണർ പതിപ്പ് മാത്രം ട്രാക്കുചെയ്യുന്നു: അത് ആ ഡാറ്റാബേസുകളിലെ ഫയൽ ഒഴിവാക്കുന്നു (പുതിയ ഉള്ളടക്കം ഒരിക്കലും അവിടെ പ്രവർത്തിക്കില്ല) കൂടാതെ ഓരോ ബൂട്ടിലും ഒരു റീനമ്പറിംഗ് പിശക് രേഖപ്പെടുത്തുന്നു. മറ്റൊരു ടൈംസ്റ്റാമ്പും ഒരു അനുയോജ്യത എൻട്രിയും ഉപയോഗിക്കുക അല്ലെങ്കിൽ പേര് സൂക്ഷിക്കുക.
- **പേരുമാറ്റിയ ഫയൽ വീണ്ടും റൺ ചെയ്യുന്നില്ലെന്ന് ഗേറ്റ് പരിശോധിക്കുന്നു.** ഓരോ പുനർനാമകരണത്തിനും, ഗേറ്റ് പുതിയ ഫയലിൻ്റെ പേര് `--must-not-apply` ഉപയോഗിച്ച് കമ്മ്യൂട്ടേഷൻ പരിശോധനയ്ക്ക് കൈമാറുന്നു. ചെക്ക് അപ്ഗ്രേഡ് ചെയ്ത ഡാറ്റാബേസ് യഥാർത്ഥ റണ്ണറുമായി ബൂട്ട് ചെയ്യുന്നു, കൂടാതെ റണ്ണർ ആ ഫയൽ വീണ്ടും പ്രയോഗിക്കുകയാണെങ്കിൽ (ഉദാഹരണത്തിന്, എൻട്രിക്ക് തെറ്റായ പതിപ്പോ പേരോ ഉള്ളതിനാലോ അല്ലെങ്കിൽ ഗേറ്റിൻ്റെ ടെക്സ്റ്റ് പാഴ്സർ TypeScript യിൽ നിന്ന് വ്യത്യസ്തമായി `constants.ts` വായിച്ചതിനാലോ), ഗേറ്റ് `migration renomeada rodaria de novo` ൽ പരാജയപ്പെടുകയും എൻട്രിയുടെ പഴയതും പുതിയതുമായ പതിപ്പുകൾ പരിശോധിക്കാൻ നിങ്ങളോട് ആവശ്യപ്പെടുകയും ചെയ്യുന്നു.

### അടിത്തറയ്ക്കെതിരെ ഗേറ്റ് എന്താണ് പരിശോധിക്കുന്നത്

പുൾ അഭ്യർത്ഥനയിലും ലയിപ്പിക്കൽ-ക്യൂ റണ്ണിലും, `npm run check:migration-numbering` ബേസ് ബ്രാഞ്ചിലെ അതേ ഡയറക്ടറിയുമായി ഡിസ്കിലെ `src/lib/db/migrations/` താരതമ്യം ചെയ്യുന്നു. അടിസ്ഥാനം, ഈ ക്രമത്തിലാണ്: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` വേരിയബിൾ, അല്ലെങ്കിൽ, `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` അല്ലെങ്കിൽ `merge_group` ആയിരിക്കുമ്പോൾ, ലയന കമ്മിറ്റിൻ്റെ ആദ്യ രക്ഷകർത്താവ്, ഇവൻ്റ് പേലോഡിൻ്റെ `merge_group.base_sha`, അല്ലെങ്കിൽ `git merge-base HEAD origin/$GITHUB_BASE_REF`. ഒരു പുൾ അഭ്യർത്ഥനയിലോ ലയന-ക്യൂ റണ്ണിലോ പരിഹരിക്കാവുന്ന അടിത്തറയില്ലാതെ ഗേറ്റ് പരാജയപ്പെടുന്നു. `--base` ഇല്ലാതെ CI പുറത്ത് ഇത് `comparação com a base: pulada (sem --base)` പ്രിൻ്റ് ചെയ്യുകയും ഈ നിയമങ്ങൾ ഒഴിവാക്കുകയും ചെയ്യുന്നു.

`--base-latest-tag` ഏറ്റവും പുതിയ റിലീസ് ടാഗുമായി താരതമ്യപ്പെടുത്തുന്നു (സെംവർ ക്രമത്തിൽ `vX.Y.Z` ; നൈറ്റ്ലൈസ് പോലുള്ള പ്രത്യയ ടാഗുകൾ കണക്കാക്കില്ല) അത് `HEAD` യുടെ ചരിത്രത്തിൽ `--base` യുടെ അതേ നിയമങ്ങളോടെയാണ്. Release-Green (`scripts/quality/validate-release-green.mjs`) ഗേറ്റ് ഈ രീതിയിൽ പ്രവർത്തിപ്പിക്കുന്നു, കാരണം പുഷ്, ഷെഡ്യൂൾ ചെയ്ത റണ്ണുകൾക്ക് പുൾ CI ബേസ് ഇല്ല. ചരിത്രത്തിൽ റിലീസ് ടാഗില്ലാതെ ഗേറ്റ് പരാജയപ്പെടുന്നു; `git fetch --tags` റൺ ചെയ്യുക ( CI ൽ, `actions/checkout` ൽ `fetch-depth: 0` ടാഗുകൾ കൊണ്ടുവരുന്നു).

കമ്മ്യൂട്ടേഷൻ പരിശോധനയുടെ ഒരു ഓട്ടം ക്രമരഹിതമായതും എഡിറ്റ് ചെയ്തതും പുനർനാമകരണം ചെയ്തതുമായ ഫയലുകൾ ഒരുമിച്ച് ഉൾക്കൊള്ളുന്നു.

കമ്മ്യൂട്ടേഷൻ ചെക്ക് (`scripts/check/migration-commutation.ts`) യഥാർത്ഥ ഇൻസ്റ്റാളേഷൻ പാത ഉപയോഗിച്ച് രണ്ട് താൽക്കാലിക ഡാറ്റാബേസുകൾ നിർമ്മിക്കുന്നു: ഒരു** നവീകരിച്ചു** ഒന്ന് (അടിസ്ഥാന മൈഗ്രേഷനുകൾ ഉപയോഗിച്ച് ബൂട്ട് ചെയ്യുക, തുടർന്ന് പുൾ അഭ്യർത്ഥനയുടെ മൈഗ്രേഷൻ ഉപയോഗിച്ച് അതേ ഫയലിൽ വീണ്ടും ബൂട്ട് ചെയ്യുക) കൂടാതെ a** പുതിയത്** ഒന്ന് (പുൾ അഭ്യർത്ഥനയുടെ മൈഗ്രേഷനുള്ള ഒരു ബൂട്ട്). ഫലമായുണ്ടാകുന്ന സ്കീമകളെ ഇത് താരതമ്യം ചെയ്യുന്നു: പട്ടികകളും നിരകളും (കോളത്തിൻ്റെ ക്രമം അവഗണിച്ച്), UNIQUE / PRIMARY KEY, FOREIGN KEY നിയന്ത്രണങ്ങൾ, ഓരോ പട്ടികയുടെയും നോർമലൈസ് ചെയ്ത `CREATE TABLE` ടെക്സ്റ്റ് (ഇത് CHECK നിയന്ത്രണങ്ങൾ, കൂട്ടുകെട്ടുകൾ, സൃഷ്ടിച്ച നിരകളും പട്ടിക ഓപ്ഷനുകളും ഉൾക്കൊള്ളുന്നു), സൂചികകൾ, ട്രിഗറുകൾ, കാഴ്ചകൾ. വരി ഡാറ്റ താരതമ്യം ചെയ്തിട്ടില്ല. അവ പൊരുത്തപ്പെടുന്നെങ്കിൽ, ഫയൽ ക്രമത്തിലല്ലെന്നും എന്നാൽ യാത്രാമാർഗ്ഗമെന്നും ഗേറ്റ് പ്രിൻറ് ചെയ്യുന്നു. അവ വ്യത്യസ്തമാണെങ്കിൽ, ഗേറ്റ് പരാജയപ്പെടുകയും കേസിൻ്റെ സൂചന നൽകുകയും ചെയ്യും: ക്രമരഹിതമായ ഫയലിനായി, അതിൻ്റെ പേര് `npm run db:new-migration` ഉപയോഗിച്ച് പുനഃസൃഷ്ടിക്കുക, ഫയൽ ഇതുവരെ ലയിപ്പിച്ചിട്ടില്ലാത്തതിനാൽ സുരക്ഷിതമാണ്; എഡിറ്റുചെയ്ത അടിസ്ഥാന ഫയലിനായി, അടിസ്ഥാന ഉള്ളടക്കം പുനഃസ്ഥാപിക്കുകയും പുതിയ മൈഗ്രേഷനിൽ മാറ്റം വരുത്തുകയും ചെയ്യുക; പുനർനാമകരണം ചെയ്ത ഫയലിനായി, പുനർനാമകരണം പഴയപടിയാക്കുക അല്ലെങ്കിൽ അത് യാത്ര ചെയ്യുന്നിടത്ത് മറ്റൊരു പുതിയ ടൈംസ്റ്റാമ്പ് തിരഞ്ഞെടുക്കുക, ഒരിക്കലും മറ്റൊരു പേരിനൊപ്പം ഒരേ ടൈംസ്റ്റാമ്പ് ഉണ്ടാകരുത്. ചെക്ക് തന്നെ പ്രവർത്തിപ്പിക്കാൻ കഴിയുന്നില്ലെങ്കിൽ, ഗേറ്റ് CI ൽ പരാജയപ്പെടുകയും പ്രാദേശികമായി മുന്നറിയിപ്പ് നൽകുകയും ചെയ്യുന്നു. എഡിറ്റ് ചെയ്ത അടിസ്ഥാന ഫയലിനായി, അപ്ഗ്രേഡ് ചെയ്ത ഡാറ്റാബേസ് ആ ഫയലിൻ്റെ അടിസ്ഥാന ഉള്ളടക്കം ഉപയോഗിച്ചാണ് നിർമ്മിച്ചിരിക്കുന്നത്, രണ്ടാമത്തെ ബൂട്ട് അതിൻ്റെ പതിപ്പ് ഇതിനകം റെക്കോർഡ് ചെയ്തതിനാൽ അത് ഒഴിവാക്കുന്നു. പുനർനാമകരണം ചെയ്ത ഫയലിനായി, അപ്ഗ്രേഡ് ചെയ്ത ഡാറ്റാബേസ് അതിൻ്റെ പഴയ പേരിൽ ഫയൽ ഉപയോഗിച്ചാണ് നിർമ്മിച്ചിരിക്കുന്നത്, രണ്ടാമത്തെ ബൂട്ട് അതിൻ്റെ `_omniroute_migrations` വരി വീണ്ടും പ്രവർത്തിപ്പിക്കുന്നതിന് പകരം കോംപാറ്റിബിലിറ്റി എൻട്രിയിലൂടെ നീക്കുന്നു; ഗേറ്റ് പുതിയ പേര് `--must-not-apply` ഉപയോഗിച്ച് കടന്നുപോകുന്നു, അതിനാൽ രണ്ടാമത്തെ ബൂട്ട് പ്രയോഗിച്ചാൽ പരിശോധന പരാജയപ്പെടും. അപ്ഗ്രേഡ് ചെയ്ത പാതയിൽ ഒരു പുൾ അഭ്യർത്ഥന മൈഗ്രേഷൻ പ്രയോഗിക്കുന്നതിൽ പരാജയപ്പെടുകയാണെങ്കിൽ, അതായത്, ഓരോ അടിസ്ഥാന മൈഗ്രേഷനു ശേഷവും (പുതിയ ഇൻസ്റ്റാളിൽ അത് പരാജയപ്പെട്ടാലും ഇല്ലെങ്കിലും), ഗേറ്റ് `migration do PR não aplica` റിപ്പോർട്ട് ചെയ്യുകയും ബേസിൻ്റെ നിലവിലെ സ്കീമയ്ക്കെതിരായി SQL ശരിയാക്കാൻ നിങ്ങളോട് ആവശ്യപ്പെടുകയും ചെയ്യുന്നു; പിന്നീടുള്ള ടൈംസ്റ്റാമ്പ് ഉപയോഗിച്ച് ഫയൽ മറ്റൊരു പുൾ അഭ്യർത്ഥന മൈഗ്രേഷനെ ആശ്രയിച്ചിരിക്കുന്നുവെങ്കിൽ, അതിൻ്റെ പേര് `npm run db:new-migration` ഉപയോഗിച്ച് പുനഃസൃഷ്ടിക്കുക.

പ്രാദേശികമായി സമാന താരതമ്യം പ്രവർത്തിപ്പിക്കുന്നതിന്, അടിസ്ഥാനം വ്യക്തമായി കൈമാറുക, ഉദാഹരണത്തിന് `npm run check:migration-numbering -- --base origin/<base-branch>`, അല്ലെങ്കിൽ ഏറ്റവും പുതിയ റിലീസുമായി താരതമ്യം ചെയ്യാൻ `npm run check:migration-numbering -- --base-latest-tag`.

### ഒരു ഓപ്പൺ PR's `NNN` മൈഗ്രേഷൻ പരിവർത്തനം ചെയ്യുന്നു

സ്വിച്ചിന് മുമ്പ് തുറന്ന ഒരു പുൾ അഭ്യർത്ഥന ഇപ്പോഴും `242_add_widgets.sql` പോലെയുള്ള ഒരു തുടർച്ചയായ ഫയൽ വഹിക്കാനിടയുണ്ട്. `241` ന് മുകളിലുള്ള പഴയ സംഖ്യകൾ നിരസിക്കപ്പെട്ടതിനാൽ ലയിപ്പിക്കുന്നതിന് മുമ്പ് ഇത് പരിവർത്തനം ചെയ്യുക:

1. **വിവരണം നിലനിർത്തിക്കൊണ്ട് ജനറേറ്റർ ഉപയോഗിച്ച് ഫയലിൻ്റെ പേര് മാറ്റുക.** പുതിയ പേര് ലഭിക്കാൻ `npm run db:new-migration -- <same description>` പ്രവർത്തിപ്പിക്കുക, അതിലേക്ക് SQL നീക്കുക, പഴയ `NNN_` ഫയൽ ഇല്ലാതാക്കുക. വിവരണം സമാനമായിരിക്കണം: താഴെയുള്ള അനുയോജ്യത എൻട്രി അതിനോട് പൊരുത്തപ്പെടുന്നു.
2. **സ്ഥിരമായ ഒരു ഡാറ്റാബേസ് പഴയ നമ്പർ പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ ഒരു അനുയോജ്യത എൻട്രി ചേർക്കുക.** സൂക്ഷിച്ചിരിക്കുന്ന ഏതെങ്കിലും ഡാറ്റാബേസ് (homolog, a VPS, ഒരു സംഭാവകൻ്റെ സ്വന്തം ഇൻസ്റ്റാളേഷൻ) `NNN_` ഫയലിനൊപ്പം PR ൻ്റെ ഒരു ബിൽഡ് പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, `src/lib/db/migrationRunner/constants.ts` ൽ `RENAMED_MIGRATION_COMPATIBILITY` ലേക്ക് `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` ചേർക്കുക. ഇതാണ്** `237` മുതൽ `241` വരെ ആവശ്യമാണ്** : ആ സ്ലോട്ടുകൾ ഇപ്പോൾ കാനോനിക്കൽ `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql`, `241_seen_models.sql` എന്നിവ കൈവശം വയ്ക്കുന്നു, കൂടാതെ എൻട്രി കൂടാതെ അത്തരം ഒരു ഡാറ്റാബേസ് കാനോനിക്കൽ മൈഗ്രേഷൻ എന്നെന്നേക്കുമായി ഒഴിവാക്കുകയും പരിവർത്തനം ചെയ്ത ഒന്ന് വീണ്ടും പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു. ലക്ഷ്യസ്ഥാനം ഒരു ടൈംസ്റ്റാമ്പായിരിക്കുമ്പോൾ, `242` പോലുള്ള ശൂന്യമായി തുടരുന്ന ഒരു സ്ലോട്ടിനും ഇത് പ്രവർത്തിക്കുന്നു. സംശയമുണ്ടെങ്കിൽ, എൻട്രി ചേർക്കുക. നിങ്ങൾ അത് അറേയിൽ എവിടെ ചേർക്കുന്നു `usage_history_calculated_cost` പ്രശ്നമല്ല: ഒരു എൻട്രിയുടെ ടാർഗെറ്റ് സ്ലോട്ട് മറ്റൊരു എൻട്രി നീങ്ങുന്ന ഒരു വരി നിലനിർത്തുമ്പോൾ (ഉദാഹരണത്തിന് `237` ഒരു PR വരി പിടിച്ച് `237` ലേക്ക് നീങ്ങാൻ കാത്തിരിക്കുമ്പോൾ), സ്ലോട്ട് സ്വതന്ത്രമാകുന്നത് വരെ ആ എൻട്രി കാത്തിരിക്കാൻ റണ്ണർ അനുവദിക്കുന്നു. ഒരു വരി നോ എൻട്രി മൂവുകളോ കൈവശം വച്ചിരിക്കുന്ന സ്ലോട്ട് അല്ലെങ്കിൽ സ്ലോട്ടുകൾ സ്വാപ്പ് ചെയ്യുന്ന രണ്ട് എൻട്രികൾ പോലെയുള്ള ഒരു യഥാർത്ഥ വൈരുദ്ധ്യം മാത്രമേ `Cannot reconcile ...` ഉപയോഗിച്ച് ബൂട്ട് നിർത്തുകയുള്ളൂ.
3. **SQL ദുർബലമായി സൂക്ഷിക്കുക** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), കാരണം പരിവർത്തനം ചെയ്ത മൈഗ്രേഷൻ അതിൻ്റെ സ്കീമ നിലവിലിരിക്കുന്ന ഒരു ഡാറ്റാബേസ് കണ്ടുമുട്ടിയേക്കാം.
4. **പതിപ്പ്-കീയുള്ള പ്രത്യേക കേസുകൾ നീക്കുക.** PR അതിൻ്റെ പഴയ നമ്പറിനായി `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) അല്ലെങ്കിൽ `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) എന്നിവയിൽ ഒരു കേസ് ചേർത്തിട്ടുണ്ടെങ്കിൽ, കീ പുതിയ ടൈംസ്റ്റാമ്പിലേക്ക് മാറ്റുക.

`tests/unit/db/codex-fence-migration-rename.test.ts` എന്നത് പുനർനാമകരണം ചെയ്ത മൈഗ്രേഷനുള്ള ഒരു പരീക്ഷണത്തിൻ്റെ പ്രവർത്തന ഉദാഹരണമാണ്.

### മാറുന്നതിന് മുമ്പുള്ള ശാഖകളിലേക്കുള്ള ബാക്ക്പോർട്ടുകൾ

സ്വിച്ചിന് മുമ്പുള്ള ഒരു ശാഖയിലേക്ക് (ഉദാഹരണത്തിന് ഒരു പഴയ `release/v*` ബ്രാഞ്ച്) `YYYYMMDDHHMMSS_` ഫയൽ ഒരിക്കലും ചെറി-പിക്ക് ചെയ്യുകയോ ബാക്ക്പോർട്ട് ചെയ്യുകയോ ചെയ്യരുത്. അവിടെയുള്ള റണ്ണർ ഫയലുകളുടെ പേരുകൾ ടെക്സ്റ്റായി അടുക്കുന്നു, അതിനാൽ ടൈംസ്റ്റാമ്പ് ചെയ്ത ഒരു ഫയൽ പുതിയ ഡാറ്റാബേസിൽ `201_` നും `202_` ഇടയിൽ പ്രവർത്തിക്കും, അവിടെയുള്ള പഴയ ഗേറ്റിന് 14 അക്ക പ്രിഫിക്സുകൾ മനസ്സിലാകുന്നില്ല. അത്തരം ഒരു ശാഖയിൽ, ആ ബ്രാഞ്ചിൻ്റെ സ്വന്തം അടുത്ത `NNN_` ഫയലായി മാറ്റം എഴുതുക, idempotent, അതിനാൽ ടൈംസ്റ്റാമ്പ് ചെയ്ത പതിപ്പ് പിന്നീട് വരുമ്പോൾ അത് ഒരു നോ-ഓപ് ആണ്.

### മൈഗ്രേഷൻ എങ്ങനെ പ്രവർത്തിക്കുന്നു

തുടക്കത്തിൽ, `migrationRunner.ts`:

1. നിലവിലില്ലെങ്കിൽ `_omniroute_migrations` പട്ടിക സൃഷ്ടിക്കുന്നു
2. ഇതിനകം പ്രയോഗിച്ച മൈഗ്രേഷനുകൾക്കുള്ള അന്വേഷണങ്ങൾ
3. ഓരോ ഇടപാടിലും ഓരോ പുതിയ മൈഗ്രേഷനും ക്രമത്തിൽ പ്രയോഗിക്കുന്നു
4. പ്രയോഗിച്ച ഓരോ മൈഗ്രേഷനും ടൈംസ്റ്റാമ്പ് ഉപയോഗിച്ച് രേഖപ്പെടുത്തുന്നു

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### ഐഡമ്പറ്റൻസി

കുടിയേറ്റങ്ങൾ ആയിരിക്കണം** ബുദ്ധിശൂന്യൻ** — അവ രണ്ടുതവണ പ്രവർത്തിപ്പിക്കുന്നത് ഒരു നോ-ഓപ് ആയിരിക്കണം:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, `OR IGNORE` / `OR REPLACE` ക്ലോസുകൾ ഉദാരമായി ഉപയോഗിക്കുക.

### ഒരു പുതിയ മൈഗ്രേഷൻ ചേർക്കുന്നു

1. **ജനറേറ്റർ ഉപയോഗിച്ച് ഫയൽ സൃഷ്ടിക്കുക** : `npm run db:new-migration -- <description>` (ഉദാഹരണത്തിന് `npm run db:new-migration -- add combo priority`). നിലവിലെ UTC സമയവും ഒരു കമൻ്റ് ഹെഡറും ഉപയോഗിച്ച് ഇത് `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` എഴുതുന്നു, ആ ടൈംസ്റ്റാമ്പ് എടുത്താൽ ഒരു സെക്കൻഡ് മുന്നോട്ട് നീങ്ങുന്നു, ഒരു ഫയലും പുനരാലേഖനം ചെയ്യുന്നില്ല. കൈകൊണ്ട് ഒരു നമ്പർ തിരഞ്ഞെടുക്കരുത്.
2. **സുരക്ഷിതമായ DDL ഉപയോഗിക്കുക** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **ഡാറ്റ ശ്രദ്ധാപൂർവ്വം പൂരിപ്പിക്കുക** : നിലവിലുള്ള വരികൾ കൈകാര്യം ചെയ്യാൻ `UPDATE ... WHERE ...` ഉപയോഗിക്കുക
4. **ക്രമവും പേരിടലും പരിശോധിക്കുക** : `npm run test:migrations:fresh` (ഒരു ശൂന്യമായ ഡാറ്റാബേസിലെ എല്ലാ മൈഗ്രേഷനുകളും) കൂടാതെ `npm run check:migration-numbering`
5. **ഒരു പകർപ്പിൽ പരീക്ഷിക്കുക** : ഉൽപ്പാദനത്തിൽ ഒരിക്കലും പരീക്ഷിക്കാത്ത മൈഗ്രേഷനുകൾ നടത്തരുത്

ഉദാഹരണം:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **പിന്നോട്ട്-അനുയോജ്യമായ മാറ്റങ്ങൾ** (ഉദാഹരണത്തിന്, നിരകൾ ഇടുന്നത്) ബുദ്ധിമുട്ടാണ്. OmniRoute NOT പിന്തുണയ്ക്കുന്നു — ഒരു മൈഗ്രേഷൻ പ്രയോഗിച്ചുകഴിഞ്ഞാൽ, സ്കീമ മാറ്റം ശാശ്വതമാണ്. അതിനനുസരിച്ച് പ്ലാൻ ചെയ്യുക.

## സംഭരണത്തിലുള്ള എൻക്രിപ്ഷൻ

സെൻസിറ്റീവ് ഫീൽഡുകൾ (API കീകൾ, OAuth ടോക്കണുകൾ, കണക്ഷൻ സ്ട്രിങ്ങുകൾ) സംഭരണത്തിലിരിക്കുമ്പോൾ **AES-256-GCM** ഉപയോഗിച്ച് എൻക്രിപ്റ്റ് ചെയ്യുന്നു.

### ഇത് പ്രവർത്തിക്കുന്ന വിധം

```ts
// src/lib/db/encryption.ts (ലളിതമാക്കിയത്)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### ഇത് ഉപയോഗിക്കുന്ന ഇടങ്ങൾ

- `provider_connections.api_key` — ആപ്ലിക്കേഷൻ തലത്തിൽ എൻക്രിപ്റ്റ് ചെയ്യുന്നു
- `provider_connections.access_token`, `refresh_token`, `id_token` — ആപ്ലിക്കേഷൻ തലത്തിൽ എൻക്രിപ്റ്റ് ചെയ്യുന്നു
- `namespace = "secrets"` ഉള്ള `key_value` എൻട്രികൾ — ആപ്ലിക്കേഷൻ തലത്തിൽ എൻക്രിപ്റ്റ് ചെയ്യുന്നു
- `proxy_registry.auth` — നിലവിലുണ്ടെങ്കിൽ, ആപ്ലിക്കേഷൻ തലത്തിൽ എൻക്രിപ്റ്റ് ചെയ്യുന്നു

### എൻക്രിപ്ഷൻ കീ

എൻക്രിപ്ഷൻ കീ ഒരു **പാസ്ഫ്രെയ്സിൽ** നിന്നും (`STORAGE_ENCRYPTION_KEY` എൻവയോൺമെന്റ് വേരിയബിൾ വഴി സജ്ജമാക്കുന്നത്) ഒരു **സാൾട്ടിൽ** നിന്നും (DB-യിൽ സംഭരിക്കുന്നത്) ഡെറൈവ് ചെയ്യുന്നു. ഡാറ്റ ഡീക്രിപ്റ്റ് ചെയ്യാൻ രണ്ടും ആവശ്യമാണ്.

```bash
# സുരക്ഷിതമായ ഒരു പാസ്ഫ്രെയ്സ് സൃഷ്ടിക്കുക
openssl rand -hex 32

# .env-ൽ സജ്ജമാക്കുക
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **നിർണായകം**: എൻക്രിപ്ഷൻ കീ നഷ്ടപ്പെടുന്നത് എൻക്രിപ്റ്റ് ചെയ്ത എല്ലാ ഡാറ്റയിലേക്കുമുള്ള പ്രവേശനം നഷ്ടപ്പെടുന്നതിന് തുല്യമാണ്. **ഡാറ്റാബേസിൽനിന്ന് വേറിട്ട് കീയുടെ ബാക്കപ്പ് എടുക്കുക**.

### എൻക്രിപ്റ്റ് ചെയ്യാത്തവ

പ്രകടനക്ഷമത കണക്കിലെടുത്ത്, ഇനിപ്പറയുന്നവ പ്ലെയിൻടെക്സ്റ്റിലാണ് സംഭരിക്കുന്നത്:

- പ്രൊവൈഡറിന്റെ പ്രദർശന നാമങ്ങൾ
- മോഡൽ നിർവചനങ്ങൾ (ഇതിനകം പൊതുവായി ലഭ്യമാണ്)
- റൂട്ടിങ് നിയമങ്ങൾ
- ഉപയോഗ രേഖകൾ (PII ഇല്ല)

## എൻക്രിപ്ഷൻ സംബന്ധിച്ച മുന്നറിയിപ്പുകൾ (v3.8.16+)

രണ്ട് എൻക്രിപ്ഷൻ സ്കീമുകൾ സുതാര്യമായി കൈകാര്യം ചെയ്യാൻ OmniRoute **`migrateLegacyEncryptedString()`** ഉപയോഗിക്കുന്നു:

- **ലെഗസി** (v3.5.0-ന് മുമ്പ്): XOR അടിസ്ഥാനമാക്കിയുള്ള "എൻക്രിപ്ഷൻ" (യഥാർത്ഥ ക്രിപ്റ്റോഗ്രഫിയല്ല)
- **നിലവിലുള്ളത്**: ശരിയായ IV-യും ഓത്ത് ടാഗും ഉള്ള AES-256-GCM

മൈഗ്രേഷൻ ഹെൽപ്പർ ലെഗസി ഫോർമാറ്റ് കണ്ടെത്തുകയും ആദ്യമായി വായിക്കുമ്പോൾ പുതിയ സ്കീം ഉപയോഗിച്ച് വീണ്ടും എൻക്രിപ്റ്റ് ചെയ്യുകയും ചെയ്യുന്നു. ക്രെഡൻഷ്യലുകൾ നഷ്ടപ്പെടാതെ ഒരു പഴയ ഡാറ്റാബേസ് അപ്ഗ്രേഡ് ചെയ്യാൻ ഇതിലൂടെ കഴിയും.

## റീഡ് കാഷ്

പതിവായി വായിക്കുന്ന ഡാറ്റയ്ക്കായി (മോഡലുകൾ, പ്രൊവൈഡറുകൾ, ക്രമീകരണങ്ങൾ), `readCache.ts` ഒരു **ഇൻ-മെമ്മറി കാഷ്** നൽകുന്നു:

```ts
// സ്റ്റാർട്ടപ്പിൽ കാഷ് ചെയ്യുന്നു, എഴുതുമ്പോൾ അസാധുവാക്കുന്നു
const providers = await getCachedProviders(); // വേഗതയേറിയത്, ഇൻ-മെമ്മറി
const fresh = await listProviders(); // വേഗത കുറഞ്ഞത്, DB ആക്സസ് ചെയ്യുന്നു
```

| കാഷ് ചെയ്ത എന്റിറ്റി   | കാഷ് കീ        | TTL           |
| ---------------------- | -------------- | ------------- |
| `models`               | `models:v1`    | എഴുതുന്നതുവരെ |
| `provider_connections` | `providers:v1` | എഴുതുന്നതുവരെ |
| `settings`             | `settings:v1`  | എഴുതുന്നതുവരെ |
| `combos`               | `combos:v1`    | എഴുതുന്നതുവരെ |

അനുബന്ധ പട്ടികയിലേക്ക് ഓരോ തവണ എഴുതുമ്പോഴും കാഷ് അസാധുവാക്കപ്പെടുന്നു.

## ബാക്കപ്പും വീണ്ടെടുക്കലും

### മാനുവൽ ബാക്കപ്പ്

```bash
# ഒരു ലോക്കൽ ബാക്കപ്പ് സൃഷ്ടിക്കാൻ CLI ഉപയോഗിക്കുക
omniroute backup create --name pre-migration

# അല്ലെങ്കിൽ API വഴി
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

ബാക്കപ്പ് ഫയലിൽ ഉൾപ്പെടുന്നവ:

- എല്ലാ DB പട്ടികകളും (JSON ആയി സീരിയലൈസ് ചെയ്തത്)
- കോൾ ലോഗ് ആർട്ടിഫാക്റ്റുകൾ (base64-എൻകോഡ് ചെയ്തത്, ഐച്ഛികം)
- ക്രമീകരണങ്ങൾ + സീക്രട്ടുകൾ (എൻക്രിപ്റ്റ് ചെയ്തത്)
- പ്ലഗിൻ കോൺഫിഗറേഷൻ

### പുനഃസ്ഥാപിക്കൽ

```bash
# CLI വഴി
omniroute restore pre-migration

# API വഴി
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **മുന്നറിയിപ്പ്**: പുനഃസ്ഥാപിക്കൽ മുഴുവൻ DB-യും ഓവർറൈറ്റ് ചെയ്യും. ആദ്യം എല്ലാ ക്ലയന്റുകളും നിർത്തുക.

### ഓട്ടോമേറ്റഡ് ബാക്കപ്പുകൾ

```bash
# CLI വഴി ഓട്ടോമേറ്റഡ് പ്രതിദിന ബാക്കപ്പുകൾ പ്രവർത്തനക്ഷമമാക്കുക
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

ഓരോ 30 സെക്കൻഡിലും പ്രവർത്തിക്കുന്ന ഒരു പശ്ചാത്തല ജോബ് സെർവർ ഭാഗത്ത് ഷെഡ്യൂൾ നിർവഹിക്കുകയും
(ഡിഫോൾട്ട്) ലോക്കൽ സെർവർ സമയത്തിന് അനുസരിച്ച് cron എക്സ്പ്രഷൻ വിലയിരുത്തുകയും ചെയ്യുന്നു.

| വേരിയബിൾ                                    | ഡിഫോൾട്ട് | വിവരണം                                                                                                                                       |
| ------------------------------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`   | ms-ലുള്ള ടിക്ക് ഇടവേള (കുറഞ്ഞത് `5000`). പൊരുത്തപ്പെടുന്ന cron മിനിറ്റിനുള്ളിൽ വിശ്വസനീയമായി പ്രവർത്തിക്കാൻ ഇത് 60 s-നേക്കാൾ കുറവായിരിക്കണം. |

### SQLite ഹോട്ട് ബാക്കപ്പ്

പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുന്ന ഒരു DB-യുടെ സീറോ-ഡൗൺടൈം ബാക്കപ്പിനായി:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

ഇത് SQLite-ന്റെ ഓൺലൈൻ ബാക്കപ്പ് API ഉപയോഗിക്കുന്നു — OmniRoute പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുമ്പോൾ ഇത് സുരക്ഷിതമായി പ്രവർത്തിപ്പിക്കാം.

## പ്രകടന ട്യൂണിംഗ്

### WAL മോഡ്

സ്ഥിരസ്ഥിതിയായിWAL പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുന്നു. ഉയർന്ന എഴുത്ത് ജോലിഭാരങ്ങൾക്കായി, പരിഗണിക്കുക:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` സജ്ജമാക്കുന്നില്ല. ഒരു ചെക്ക് പോയിൻ്റ് പ്രധാന ഫയലിലേക്ക് WAL ഫ്രെയിമുകൾ നീക്കുന്നു, എന്നാൽ WAL ഫയൽ അതിൻ്റെ ഏറ്റവും വലിയ അനുവദിച്ച വലുപ്പം നിലനിർത്തുന്നു. `OMNIROUTE_WAL_GUARD_MAX_MB` ഗാർഡ് മുന്നറിയിപ്പ് നൽകുകയും `wal_checkpoint(RESTART)` പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു; ഇത് ഒരു ഡിസ്ക്-സൈസ് ക്യാപ് അല്ല.

### സൂചികകൾ

പ്രകടനത്തിനുള്ള പ്രധാന സൂചികകൾ (മൈഗ്രേഷൻ വഴി സ്വയമേവ സൃഷ്ടിച്ചത്):

- ദാതാവ് മുഖേന `idx_models_provider` — മോഡൽ ലുക്കപ്പുകൾ
- `idx_combo_targets_combo_id` — കോംബോ ടാർഗെറ്റ് വിപുലീകരണം
- `idx_usage_history_api_key_timestamp` — ഉപയോഗ വിശകലനം
- `idx_quota_snapshots_api_key_window` — ക്വാട്ട ട്രാക്കിംഗ്
- `idx_call_logs_timestamp` — കോൾ ലോഗ് അന്വേഷണങ്ങൾ

ഒരു പുതിയ സൂചിക ചേർക്കുന്നതിന്, ഒരു മൈഗ്രേഷൻ സൃഷ്ടിക്കുക:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### മെമ്മറി-മാപ്പ് ചെയ്ത I/O

വളരെ വലിയ ഡാറ്റാബേസുകൾക്ക് (> 10GB), മെമ്മറി മാപ്പിംഗ് SQLite പ്രാഗ്മ വഴി ക്രമീകരിക്കാൻ കഴിയും:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### കോംപാക്ഷൻ

ഇടയ്ക്കിടെയുള്ള `VACUUM` ൽ നിന്ന് ദീർഘകാലം പ്രവർത്തിക്കുന്ന OmniRoute സംഭവങ്ങൾക്ക് പ്രയോജനം ലഭിക്കും:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

ട്രാഫിക് കുറവുള്ള വിൻഡോകളിൽ പ്രതിമാസം പ്രവർത്തിപ്പിക്കുക. (WAL മോഡ് ആവശ്യം കുറയ്ക്കുന്നു, പക്ഷേ അത് ഇല്ലാതാക്കുന്നില്ല.)

## ഹെൽത്ത് ചെക്ക്

`src/lib/db/healthCheck.ts` **ഡാറ്റാബേസ്-തല ഹെൽത്ത് ഡയഗ്നോസ്റ്റിക്സ്** നൽകുന്നു:

രണ്ട് വെർബുകൾക്കും ഓതന്റിക്കേഷൻ ആവശ്യമാണ് (അല്ലെങ്കിൽ `401`). `GET` ഡയഗ്നോസ് ചെയ്യുക മാത്രം ചെയ്യുന്നു; `POST`, `autoRepair` പ്രവർത്തനക്ഷമമാക്കി അതേ പരിശോധന നടത്തുന്നു.

```bash
GET  /api/db/health   # ഡയഗ്നോസ് ചെയ്യുക
POST /api/db/health   # ഡയഗ്നോസ് ചെയ്യുക + നന്നാക്കുക
```

പ്രതികരണം `runDbHealthCheck()` സൃഷ്ടിക്കുന്ന `DbHealthCheckResult` ആണ്
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "ഇപ്പോൾ നിലവിലില്ലാത്ത API കീകളെയാണ് ഡൊമെയ്ൻ ബജറ്റുകൾ പരാമർശിച്ചത്.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ഫീൽഡ്             | അർത്ഥം                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `isHealthy`       | `issues` ശൂന്യമാകുമ്പോൾ `true`. `driver` ഇതിനെ ഒരിക്കലും സ്വാധീനിക്കില്ല.                                                                                    |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` എന്നിവയിൽ ഒന്ന്.                                                             |
| `repairedCount`   | ഈ റണ്ണിൽ നന്നാക്കിയ വരികൾ; `autoRepair` false ആയിരിക്കുമ്പോൾ എല്ലായ്പ്പോഴും `0`.                                                                             |
| `backupCreated`   | നന്നാക്കുന്നതിന് മുമ്പ് ഒരു ബാക്കപ്പ് എടുത്തോ എന്നത്.                                                                                                        |
| `checkedAt`       | റണ്ണിനും അത് എഴുതുന്ന ഏതൊരു റിപ്പയർ കുറിപ്പിനും പൊതുവായ ISO ടൈംസ്റ്റാമ്പ്.                                                                                   |
| `driver.name`     | പരിശോധിച്ച ഡാറ്റാബേസിന് സേവനം നൽകുന്ന SQLite ഡ്രൈവർ.                                                                                                         |
| `driver.degraded` | റൈറ്റുകൾ ഡാറ്റാബേസ് ഫയലിൽ സ്ഥിരമായി ബാക്ക് ചെയ്യപ്പെടാത്തപ്പോൾ `true` — `sql.js` WASM ഫാൾബാക്ക് (മുഴുവൻ-ഫയൽ പെർസിസ്റ്റൻസ്) അല്ലെങ്കിൽ ഇൻ-മെമ്മറി ഡാറ്റാബേസ്. |

ഇതേ പേലോഡ് `omniroute_db_health_check` MCP ടൂളും തിരികെ നൽകുന്നു.

കറപ്ഷൻ കണ്ടെത്താൻ `PRAGMA integrity_check` പ്രവർത്തിപ്പിക്കുക:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ഇങ്ങനെ പ്രിന്റ് ചെയ്യണം: ok
```

ഇത് `ok` അല്ലാതെ മറ്റെന്തെങ്കിലും തിരികെ നൽകുന്നുവെങ്കിൽ, **ഡാറ്റാബേസ് ഉപയോഗിക്കുന്നത് ഉടൻ നിർത്തുക**, തുടർന്ന് ബാക്കപ്പിൽ നിന്ന് പുനഃസ്ഥാപിക്കുക.

---

## ദുരന്താനന്തര വീണ്ടെടുക്കൽ

### സാഹചര്യം 1: WAL ഫയൽ നഷ്ടപ്പെട്ടു

`-wal` ഫയൽ കാണാനില്ല, എന്നാൽ `-shm` ഫയലും പ്രധാന DB-യും കേടുകൂടാതെ നിലനിൽക്കുന്നു:

```bash
# അടുത്ത തവണ തുറക്കുമ്പോൾ സ്വയമേവ വീണ്ടെടുക്കുന്നു
omniroute
```

SQLite-ന് സ്വയമേവ വീണ്ടെടുക്കാൻ കഴിയുന്നില്ലെങ്കിൽ:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### സാഹചര്യം 2: പ്രധാന DB ഫയൽ കേടായി

ബാക്കപ്പിൽ നിന്ന് പുനഃസ്ഥാപിക്കുക:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` പ്രവർത്തിക്കുന്ന ഒരു സെർവറിൽ നിന്ന് പൂർണ്ണമായ ഒരു `.tar.gz` ആർക്കൈവ് ഡൗൺലോഡ് ചെയ്യുക മാത്രമാണ് ചെയ്യുന്നത്
(`GET /api/db-backups/exportAll`, ഓപ്പറേറ്റർ ക്രെഡൻഷ്യൽ ആവശ്യമാണ്); ഇത് ഒന്നും പുനഃസ്ഥാപിക്കുന്നില്ല.

### സാഹചര്യം 3: എൻക്രിപ്ഷൻ കീ നഷ്ടപ്പെട്ടു

കീ ഇല്ലാതെ **വീണ്ടെടുക്കൽ സാധ്യമല്ല**. എൻക്രിപ്റ്റ് ചെയ്ത ഫീൽഡുകൾ വായിക്കാൻ കഴിയില്ല. പുതിയ ക്രെഡൻഷ്യലുകൾ ഉപയോഗിച്ച് എല്ലാ പ്രൊവൈഡറുകളെയും മാനുവലായി വീണ്ടും ചേർക്കുക.

> **ലഘൂകരണ നടപടി**: എൻക്രിപ്ഷൻ കീ എപ്പോഴും പ്രത്യേകം ബാക്കപ്പ് ചെയ്യുക; ഏറ്റവും ഉചിതമായി, ഒരു പാസ്വേഡ് മാനേജറിലോ KMS-ലോ സൂക്ഷിക്കുക.

### സാഹചര്യം 4: ഡിസ്ക് നിറഞ്ഞു

SQLite `SQLITE_FULL` പിശകുകൾ നൽകും. ഡിസ്ക് ഇടം ഒഴിവാക്കിയ ശേഷം:

```bash
# ഇടം ഒഴിവാക്കാൻ WAL ചെക്ക്പോയിന്റ് ചെയ്യുക
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## സാധാരണ പ്രവർത്തനങ്ങൾ

### ഒരു പട്ടിക പരിശോധിക്കുക

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### എല്ലാ പട്ടികകളിലെയും വരികളുടെ എണ്ണം കണക്കാക്കുക

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### എല്ലാ ഡാറ്റയും റീസെറ്റ് ചെയ്യുക (മായ്ക്കുക)

```bash
# ആദ്യം OmniRoute നിർത്തുക
omniroute stop

# DB ഫയൽ ഇല്ലാതാക്കുക
rm ~/.omniroute/storage.sqlite*

# പുനരാരംഭിക്കുക (ശൂന്യമായ DB വീണ്ടും സൃഷ്ടിക്കും)
omniroute
```

**തിരഞ്ഞെടുത്തുള്ള** റീസെറ്റിനായി (പ്രൊവൈഡറുകളെ നിലനിർത്തി ഉപയോഗ ഡാറ്റ മായ്ക്കുക):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### ഒറ്റ പട്ടിക എക്സ്പോർട്ട് ചെയ്യുക

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## പ്രശ്നപരിഹാരം

### "ഡാറ്റാബേസ് ലോക്ക് ചെയ്തിരിക്കുന്നു"

മറ്റൊരു പ്രോസസ് ഒരു റൈറ്റ് ലോക്ക് കൈവശം വച്ചിരിക്കുന്നു. ഇനിപ്പറയുന്നവയിൽ ഒന്ന് ചെയ്യുക:

- മറ്റേ പ്രോസസ് പൂർത്തിയാകുന്നതുവരെ കാത്തിരിക്കുക (`lsof | grep storage.sqlite` പരിശോധിക്കുക)
- മറ്റേ പ്രോസസ് അവസാനിപ്പിക്കുക
- പ്രശ്നം തുടരുകയാണെങ്കിൽ OmniRoute പുനരാരംഭിക്കുക

### "ഫോറിൻ കീ നിയന്ത്രണം പരാജയപ്പെട്ടു"

ഒരു ഡൊമെയ്ൻ മൊഡ്യൂൾ റഫറൻഷ്യൽ ഇന്റഗ്രിറ്റി ലംഘിക്കുന്നു. ഇനിപ്പറയുന്നവ പരിശോധിക്കുക:

- ആശ്രിത പട്ടികകളിലെ അനാഥ വരികൾ
- പ്രചരിക്കാതിരുന്ന കാസ്കേഡിംഗ് ഡിലീറ്റുകൾ
- ഫോറിൻ കീ മാറ്റിയ സമീപകാല മൈഗ്രേഷൻ

ലംഘനങ്ങൾ കണ്ടെത്താൻ `PRAGMA foreign_key_check;` പ്രവർത്തിപ്പിക്കുക.

### "മെമ്മറി തീർന്നു"

SQLite-ന്റെ മെമ്മറി-മാപ്പ്ഡ് I/O, OS പരിധി കവിയുന്നു. SQLite pragma ഉപയോഗിച്ച് കുറയ്ക്കുക:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB-ന് പകരം 128MB
```

അല്ലെങ്കിൽ പ്രവർത്തനരഹിതമാക്കുക:

```sql
PRAGMA mmap_size = 0;
```

### "മൈഗ്രേഷൻ പാതിവഴിയിൽ പരാജയപ്പെട്ടു"

മൈഗ്രേഷൻ ഒരു ട്രാൻസാക്ഷനിലാണ് പ്രവർത്തിച്ചത്, അതിനാൽ അത് റോൾ ബാക്ക് ചെയ്തിരിക്കണം. അങ്ങനെ സംഭവിച്ചില്ലെങ്കിൽ:

1. **OmniRoute നിർത്തുക** (കൂടുതൽ ശ്രമങ്ങൾ തടയുക)
2. `sqlite3` ഉപയോഗിച്ച് **DB-യുടെ അവസ്ഥ പരിശോധിക്കുക**
3. ഭാഗികമായ മൈഗ്രേഷൻ **മാനുവലായി പരിഹരിക്കുക**
4. OmniRoute **വീണ്ടും പ്രവർത്തിപ്പിക്കുക** (മൈഗ്രേഷൻ വീണ്ടും ശ്രമിക്കും)

ഇത് തടയാൻ, മൈഗ്രേഷനുകൾ എപ്പോഴും ആദ്യം ഒരു പകർപ്പിൽ പരീക്ഷിക്കുക.
