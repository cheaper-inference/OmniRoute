ഒരു pull request-നായി ഏറ്റവും ചെറുതും വിശ്വസനീയവുമായ development loop തിരഞ്ഞെടുക്കാൻ ഈ മാർഗ്ഗനിർദ്ദേശം ഉപയോഗിക്കുക. താഴെ ലിങ്ക് ചെയ്തിരിക്കുന്ന
മേഖലാ-നിർദ്ദിഷ്ട architecture, security രേഖകൾക്ക് ഇത് പകരമല്ല; സാധാരണയായി വരുന്ന ഓരോ
മാറ്റത്തിന്റെ തരത്തെയും അതിന്റെ contracts, focused checks, CI coverage എന്നിവയുമായി ഇത് ബന്ധിപ്പിക്കുന്നു.

## ഓരോ മാറ്റവും പിന്തുടരുന്ന പാത

1. **തിരുത്തുന്നതിന് മുമ്പ് base തിരഞ്ഞെടുക്കുക.** ഏറ്റവും ഉയർന്ന active `release/v*` branch കണ്ടെത്തി അതിന്റെ
   tip-ൽനിന്ന് branch സൃഷ്ടിക്കുക. `main`-നെ അല്ല, ആ branch-നെയാണ് target ചെയ്യേണ്ടത്. ഒരു release freeze സജീവമാണെങ്കിൽ, frozen
   branch-നെ target ചെയ്യരുത്; പകരം
   [Branching & Release Model](BRANCHING_MODEL.md)-ൽ വിവരിച്ചിരിക്കുന്ന അടുത്ത active cycle ഉപയോഗിക്കുക.
2. **Contracts വ്യക്തമാക്കുക.** മാറ്റം ബാധിക്കുന്ന എല്ലാ catalog, schema, generated artifact, public API, അല്ലെങ്കിൽ user
   interface എന്നിവയും തിരിച്ചറിയുക. താഴെയുള്ള പട്ടിക ഏറ്റവും കുറഞ്ഞ ആരംഭസമുച്ചയം നൽകുന്നു.
3. **Focused tests എഴുതുകയോ പുതുക്കുകയോ ചെയ്യുക.** `src/`, `open-sse/`, `electron/`, അല്ലെങ്കിൽ
   `bin/` എന്നിവയിലെ production മാറ്റങ്ങൾക്ക് അതേ PR-ൽ ഒരു automated test ആവശ്യമാണ്. behavior തെളിയിക്കുന്ന ഏറ്റവും ചെറിയ test files
   ആദ്യം പ്രവർത്തിപ്പിക്കുക, തുടർന്ന് പട്ടികപ്പെടുത്തിയ focused gates പ്രവർത്തിപ്പിക്കുക.
4. **വിശാലമായ matrix CI പ്രവർത്തിപ്പിക്കട്ടെ.** സമ്പൂർണ്ണ unit shards, Vitest, coverage ratchet, കൂടാതെ
   production build എന്നിവ PR-ൽ പ്രവർത്തിക്കും. ഒരു focused failure കൂടുതൽ വ്യാപകമായ സ്വാധീനം സൂചിപ്പിക്കുമ്പോഴോ
   മാറ്റം നിരവധി subsystems-ൽ വ്യാപിക്കുമ്പോഴോ മാത്രം വിശാലമായ suite local ആയി പ്രവർത്തിപ്പിക്കുക.
5. **Review-ന് മുമ്പ് സമന്വയിപ്പിക്കുക.** Active base fetch ചെയ്യുക, അതിലെ പുതിയ commits-ഉം അതിനെതിരായ നിങ്ങളുടെ diff-ഉം
   പരിശോധിക്കുക, തുടർന്ന് contributor workflow അനുസരിച്ച് base rebase ചെയ്യുകയോ merge ചെയ്യുകയോ ചെയ്യുക. Generated-file,
   catalog conflicts എന്നിവ അവയുടെ source-ൽനിന്ന് പരിഹരിക്കുക, അവ വീണ്ടും generate ചെയ്യുക, focused loop വീണ്ടും പ്രവർത്തിപ്പിക്കുക, കൂടാതെ
   PR ഇപ്പോഴും active release branch-നെയാണ് target ചെയ്യുന്നതെന്ന് സ്ഥിരീകരിക്കുക.
6. **തെളിവുകൾ രേഖപ്പെടുത്തുക.** PR template-ൽ പ്രവർത്തിപ്പിച്ച commands, ചേർത്തതോ മാറ്റിയതോ ആയ എല്ലാ test files,
   migrations അല്ലെങ്കിൽ feature flags, കൂടാതെ ഇനിയും ശേഷിക്കുന്ന CI-only validation എന്നിവ പട്ടികപ്പെടുത്തുക.

## മാറ്റത്തിന്റെ തരം അനുസരിച്ചുള്ള Golden paths

താഴെയുള്ള commands ഏറ്റവും കുറഞ്ഞ focused checks ആണ്; നിങ്ങൾ മാറ്റിയ
behavior-നെ നേരിട്ട് ഉൾക്കൊള്ളുന്ന test ഒഴിവാക്കാനുള്ള അനുമതിയല്ല.

### Provider

**Contracts**

- `src/shared/constants/providers/`-ലെ Provider definition-ഉം
  `src/shared/constants/providers.ts`-ലെ അതിന്റെ composition-ഉം.
- `open-sse/config/providerRegistry.ts` അല്ലെങ്കിൽ അതിൽനിന്ന് വേർതിരിച്ചെടുത്ത registry files എന്നിവയിലെ models-ഉം capabilities-ഉം.
- ബാധകമാകുമ്പോൾ executor/translator selection, OAuth അല്ലെങ്കിൽ API-key configuration, dashboard assets, കൂടാതെ generated
  provider reference.
- Public credentials `resolvePublicCred()` ഉപയോഗിക്കണം; error responses പങ്കിട്ട sanitized
  error helpers ഉപയോഗിക്കണം. `docs/security/PUBLIC_CREDS.md` (git; `/docs`-ലേക്ക് compile ചെയ്യപ്പെടുന്നില്ല), കൂടാതെ
  [Error Sanitization](../security/ERROR_SANITIZATION.md) കാണുക.

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog മാറുമ്പോൾ; generated diff commit ചെയ്യുക
npm run lint
```

ബാധിക്കപ്പെട്ട ഓരോ request family-യും test ചെയ്യുക: chat, Responses, images, embeddings, audio, അല്ലെങ്കിൽ video.
Generated catalog, golden diffs എന്നിവ contract മാറ്റങ്ങളായി review ചെയ്യുക; അവ അന്ധമായി അംഗീകരിക്കരുത്.

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts`-ലെ Public strategy values-ഉം UI metadata-യും.
- `open-sse/services/combo.ts`, `open-sse/services/combo/` എന്നിവയ്ക്ക് കീഴിലുള്ള dispatch-ഉം ordering-ഉം.
- Combo schemas, persistence, resilience state, model capabilities, കൂടാതെ API/UI controls.
- Behavior മാറുമ്പോൾ [Auto-Combo Engine](../routing/AUTO-COMBO.md), resilience documentation എന്നിവ.

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy അല്ലെങ്കിൽ dispatch മാറ്റങ്ങൾ
npm run check:known-symbols      # strategy registration മാറ്റങ്ങൾ
npm run lint
```

Local ആയി deterministic mocked-upstream tests ഉപയോഗിക്കുക. Live combo smokes-ന് credentials ആവശ്യമാണ്; അവ
manual ആണ്, CI-യ്ക്ക് പകരമല്ല.

### UI / UX

**Contracts**

- `src/app/`, `src/shared/components/` എന്നിവയ്ക്ക് കീഴിലുള്ള Next.js route/page, shared component boundaries.
- API response shapes, loading/empty/error states, keyboard, screen-reader behavior,
  responsive layout, theming, locale expansion.
- `src/i18n/messages/en.json`-ലെ English UI source strings; പുതിയ user-facing copy hard-code ചെയ്യരുത്.

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction അല്ലെങ്കിൽ visual മാറ്റങ്ങൾക്കായി app പ്രവർത്തിപ്പിച്ച് narrow, wide viewports രണ്ടും പരിശോധിക്കുക. CI
production build-ഉം കൂടുതൽ വിശാലമായ suites-ഉം പ്രവർത്തിപ്പിക്കും; visual behavior-ന് ഇപ്പോഴും മാറ്റത്തിന് അനുയോജ്യമായ focused component, Playwright,
അല്ലെങ്കിൽ രേഖപ്പെടുത്തിയ manual check ആവശ്യമാണ്.

### i18n

**Contracts**

- `src/i18n/messages/en.json` ആണ് UI source; `config/i18n.json` ആണ് locale source.
- CLI catalogs പ്രത്യേകം `bin/cli/locales/`-ന് കീഴിലാണ്.
- ICU placeholders, tags എന്നിവ മാറ്റമില്ലാതെ കൃത്യമായി നിലനിർത്തുക. Product/provider/model names,
  protocol, header names, commands, code/JSON identifiers, URLs, environment variables, അല്ലെങ്കിൽ
  `OmniRoute`, `OAuth`, `MCP`, `A2A` പോലുള്ള protected terms എന്നിവ വിവർത്തനം ചെയ്യരുത്. നിലവിലെ source list
  `scripts/i18n/glossary/protected-terms.json` ആണ്.

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs മാറുമ്പോൾ
npm run lint
```

ഇത് നിലവിലുള്ള system-നുള്ള മാർഗ്ഗനിർദ്ദേശമാണ്; അതിന്റെ tooling അല്ലെങ്കിൽ key model വിപുലീകരിക്കാനുള്ള ക്ഷണമല്ല.
Replacement system രൂപകൽപ്പന ചെയ്തുകൊണ്ടിരിക്കുമ്പോൾ i18n patches കൃത്യവും പരിമിതവുമാക്കി നിലനിർത്തുക. Task വ്യക്തമായി generated translations ആവശ്യപ്പെടുകയും
തത്ഫലമായ diff നിങ്ങൾ review ചെയ്തിരിക്കുകയും ചെയ്യുന്നില്ലെങ്കിൽ external services വിളിക്കുന്ന translation
commands പ്രവർത്തിപ്പിക്കരുത്.

### CLI

**Contracts**

- `bin/cli/`-യിലെ പൊതു കമാൻഡുകളും ഫ്ലാഗുകളും, ജനറേറ്റ് ചെയ്ത API കമാൻഡുകൾ, എക്സിറ്റ് കോഡുകൾ, stdout/stderr,
  JSON ഔട്ട്പുട്ട് ഘടനകൾ, കോൺഫിഗ്/എൻവയോൺമെന്റ് പെരുമാറ്റം, പാക്കേജ് ചെയ്ത ഫയലുകൾ.
- CLI ഉപയോക്താവിന് ദൃശ്യമാകുന്ന സ്ട്രിങ്ങുകൾ CLI i18n ലെയർ ഉപയോഗിക്കുകയും `en`/`pt-BR` കാറ്റലോഗുകൾ പരസ്പരം പൊരുത്തപ്പെടുത്തി നിലനിർത്തുകയും വേണം.
- പിന്തുണയ്ക്കുന്ന റൺടൈമായി Node-ഉം പ്രസിദ്ധീകരിച്ച ബൈനറി കരാറും സംരക്ഷിക്കുക.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ജനറേറ്റ് ചെയ്ത/ബണ്ടിൽ ചെയ്ത CLI മാറ്റങ്ങൾ
npm run check:pack-policy     # പാക്കേജ് ഉപരിതലത്തിലെ മാറ്റങ്ങൾ
npm run lint
```

പെരുമാറ്റം പാർസിങ്, ഫയലുകൾ, അല്ലെങ്കിൽ എക്സിറ്റ് സ്റ്റാറ്റസ് എന്നിവയെ ആശ്രയിക്കുമ്പോൾ, ഒരു താൽക്കാലിക ഡാറ്റ ഡയറക്ടറിയിൽ കൃത്യമായ കമാൻഡ് ഉപയോഗിക്കുക. CI കൂടുതൽ വിപുലമായ പാക്കേജ് ആർട്ടിഫാക്റ്റ്, ഇക്കോസിസ്റ്റം പരിശോധനകൾ നടത്തുന്നു.

### ഡാറ്റാബേസ്

**കരാറുകൾ**

- `src/lib/db/`-ന് കീഴിലുള്ള ഡൊമെയ്ൻ മൊഡ്യൂളുകൾ; നിർദ്ദിഷ്ട മൊഡ്യൂളുകൾ നേരിട്ട് ഇംപോർട്ട് ചെയ്യുക (പഴയ `localDb.ts` റീ-എക്സ്പോർട്ട് ലെയർ നീക്കം ചെയ്തിട്ടുണ്ട്).
- `src/lib/db/migrations/`-ന് കീഴിലുള്ള നമ്പർ നൽകിയ, ഐഡംപൊട്ടന്റ് SQL മൈഗ്രേഷനുകൾ, ട്രാൻസാക്ഷൻ സുരക്ഷ, അപ്ഗ്രേഡ്
  പെരുമാറ്റം, ഇൻഡക്സുകൾ, സ്കീമ ബാധിക്കുന്ന ഓരോ കോളറും.
- റൂട്ടുകളും ഹാൻഡ്ലറുകളും ഒരിക്കലും റോ SQL നേരിട്ട് പ്രവർത്തിപ്പിക്കരുത്.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ഒരു മൈഗ്രേഷൻ ചേർക്കുമ്പോൾ പുതിയ ഡാറ്റാബേസും മുൻ സ്കീമയിൽ നിന്നുള്ള അപ്ഗ്രേഡും പരീക്ഷിക്കുക. ഡാറ്റാബേസ് ടെസ്റ്റുകൾ ക്ലീനപ്പ് സമയത്ത് ഹാൻഡിലുകൾ ക്ലോസ് ചെയ്യുകയും `resetDbInstance()` വിളിക്കുകയും വേണം. പരമാവധി ശ്രമം മാത്രം ഉറപ്പാക്കുന്ന Bun അഡാപ്റ്റർ പാത മാറുമ്പോൾ മാത്രം `npm run test:bun:db` പ്രവർത്തിപ്പിക്കുക; Node തന്നെയാണ് ആധികാരികം.

### ബിൽഡ് / ഡിപ്ലോയ്

**കരാറുകൾ**

- റൂട്ട്, വർക്ക്സ്പേസ് മാനിഫെസ്റ്റുകൾ/ലോക്ക്ഫയൽ, `scripts/build/`, Next.js സ്റ്റാൻഡ്എലോൺ അസംബ്ലി, `dist/`
  പാക്കേജ് ഉള്ളടക്കം, Electron പ്ലാറ്റ്ഫോം മെറ്റാഡാറ്റ, CI വർക്ക്ഫ്ലോകൾ, ഡിപ്ലോയ്മെന്റ് സെന്റിനലുകൾ.
- പിന്തുണയ്ക്കുന്ന Node ശ്രേണികളും `CLAUDE.md`-ൽ അനുമതി-പട്ടികപ്പെടുത്തിയ Bun ഉപയോഗവും മാറ്റമില്ലാതെ നിലനിർത്തണം.
- ബിൽഡ് ആർട്ടിഫാക്റ്റുകൾ ട്രാക്ക് ചെയ്യാതെ നിലനിർത്തുക; ഡിപെൻഡൻസി, ലൈസൻസ്, വർക്ക്ഫ്ലോ, പാക്കേജ് നയങ്ങൾ ബാധകമാണ്.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ഡിപെൻഡൻസി അല്ലെങ്കിൽ ലോക്ക്ഫയൽ മാറ്റങ്ങൾ
npm run check:pack-policy      # പ്രസിദ്ധീകരിച്ച പാക്കേജ് ഉപരിതലത്തിലെ മാറ്റങ്ങൾ

```

മാറ്റം കമ്പൈലേഷൻ, സ്റ്റാൻഡ്എലോൺ അസംബ്ലി, അസറ്റുകൾ, അല്ലെങ്കിൽ റൺടൈം ബണ്ട്ലിങ് എന്നിവയെ ബാധിക്കുമ്പോൾ മാത്രം ലോക്കലായി `npm run build` ഉപയോഗിക്കുക. റിലീസ്/ഡിപ്ലോയ് സാധൂകരണത്തിന് മാത്രം `npm run build:release` ഉപയോഗിക്കുക. CI-യുടെ ബിൽഡാണ് അന്തിമ ക്രോസ്-പ്ലാറ്റ്ഫോം സൂചന; പ്ലാറ്റ്ഫോം-നിർദ്ദിഷ്ട Electron മാറ്റങ്ങൾക്ക് അതിനനുസരിച്ചുള്ള കേന്ദ്രീകൃത ബിൽഡ് അല്ലെങ്കിൽ സ്മോക്ക് പരിശോധനാ തെളിവ് ആവശ്യമാണ്.

## പങ്കിട്ട മെഷീനിനായുള്ള ഡെവലപ്പർ സ്ക്രിപ്റ്റുകൾ

മറ്റ് സെഷനുകൾ സജീവമായ ഒരു devbox-ലെ ലോക്കൽ ലൂപ്പ് രണ്ട് `scripts/dev/` സഹായികൾ നിർവചിക്കുന്നു:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD-ൽ നിന്നുള്ള ഫയലുകൾ
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # കൃത്യമായി ഈ ഫയലുകൾ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # ഒറ്റപ്പെട്ട worktree, സമാന്തരമായി സുരക്ഷിതം
```

- `typecheck-touched.sh`, 6 GB heap-നു കീഴിൽ ഒരു താൽക്കാലിക
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) വഴി മാറ്റം വരുത്തിയ `.ts/.tsx` ഫയലുകൾ മാത്രം typecheck ചെയ്യുന്നു; അതിനാൽ ലോഡുള്ള
  മെഷീനിൽ OOM ആകുന്ന പ്രോജക്റ്റ്-വ്യാപകമായ `tsc -p tsconfig.json`-ന് പകരമായി ഇത് പ്രവർത്തിക്കുന്നു.
  മാറ്റം വരുത്തിയ ഫയലുകളിലെ പിശകുകളും ഒരു സംഗ്രഹ വരിയും ഇത് പ്രിന്റ് ചെയ്യുന്നു; മാറ്റം വരുത്തിയ ഫയലുകളിൽ
  പിശകുകളുണ്ടെങ്കിൽ `1`, പിശകുകൾ imported ഫയലുകളിൽ മാത്രമാണെങ്കിൽ അല്ലെങ്കിൽ diagnostics ഇല്ലാതെ tsc
  പ്രവർത്തനം അവസാനിപ്പിച്ചെങ്കിൽ `2` (`_artifacts/typecheck-touched/`-ന് കീഴിൽ ഇത് സൂചിപ്പിക്കുന്ന log വായിക്കുക),
  പ്രശ്നങ്ങളില്ലെങ്കിൽ `0` എന്നിങ്ങനെ exit ചെയ്യുന്നു. താൽക്കാലിക tsconfig എല്ലായ്പ്പോഴും നീക്കം ചെയ്യപ്പെടും;
  അത് ഒരിക്കലും commit ചെയ്യരുത്.
- `new-worktree.sh`, `<git-common-dir>/omniroute-new-worktree.lock`-ൽ ഒരേസമയം നടക്കുന്ന റണ്ണുകൾ
  ക്രമാനുസൃതമാക്കുന്നു (ഡിഫോൾട്ടായി 600 s വരെ, ദൃശ്യമാകുന്ന ഒരു സന്ദേശത്തോടെ, കാത്തിരിക്കുന്നു; override
  എങ്ങനെ ചെയ്യാമെന്ന് സ്ക്രിപ്റ്റിന്റെ header വിശദീകരിക്കുന്നു). കൂടാതെ, worktree നിലവിൽ വരുന്നതിന് മുമ്പ്
  `git worktree add` പരാജയപ്പെട്ടാൽ അത് സൃഷ്ടിച്ച branch പിൻവലിക്കുകയും ചെയ്യുന്നു; അതിനാൽ വീണ്ടും
  ശ്രമിക്കുന്നതിന് മാനുവലായി `git branch -D` നൽകേണ്ടതില്ല. Hard-linked ആയ `node_modules`-ഉം
  `.husky/_` പകർപ്പും മാറ്റമില്ലാതെ തുടരും.

## ലോക്കൽ candidate ലൂപ്പ്

പാക്കേജ് ചെയ്ത artifact boot ചെയ്യുമെന്ന് source tests-ന് തെളിയിക്കാനാകില്ല: packaging ലിസ്റ്റുകൾ, pruned
dependencies, native binaries എന്നിവ tarball ഇൻസ്റ്റാൾ ചെയ്ത് ആരംഭിച്ചതിനുശേഷം മാത്രമേ പരാജയപ്പെടൂ.
`npm run dev:candidate` (`scripts/dev/candidate.mjs`) എന്നത് RFC #8084-ലെ build-once / validate /
promote ഫ്ലോയുടെ ലോക്കൽ ഭാഗമാണ്: ഇത് ഒരു candidate build ചെയ്യുന്നു, അതേ artifact validate ചെയ്യുന്നു,
directory rename-കൾ ഉപയോഗിച്ച് അതിനെ promote ചെയ്യുന്നു, promoted slot-ന്റെ health check പരാജയപ്പെട്ടാൽ
അതിനെ roll back ചെയ്യുന്നു.

```bash
npm run dev:candidate -- run --dry-run --json  # പ്ലാൻ പ്രിന്റ് ചെയ്യുക, ഒന്നും മാറ്റരുത്
npm run dev:candidate -- run                   # build + validate + promote, സ്വയമേവ rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/-ലേക്ക് ഇൻസ്റ്റാൾ ചെയ്യുക
npm run dev:candidate -- validate --id <id>    # ഒഴിവുള്ള port-ൽ boot ചെയ്യുക, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current-ഉം previous-ഉം പരസ്പരം മാറ്റുക
npm run dev:candidate -- run --from-tarball <file.tgz>  # മറ്റൊരിടത്ത് (CI) build ചെയ്ത tarball വീണ്ടും ഉപയോഗിക്കുക
```

- **ഒരിക്കൽ മാത്രം build ചെയ്യുക.** `build`, നിലവിലെ tree pack ചെയ്യുന്നു (അതിന് `dist/server.js`
  ആവശ്യമാണ്, അതിനാൽ ആദ്യം `npm run build:release` പ്രവർത്തിപ്പിക്കുക) അല്ലെങ്കിൽ `--from-tarball`
  പകർത്തുന്നു; തുടർന്ന് tarball-ൽ `node_modules` ഇല്ലാത്തതിനാൽ അതിനെ ഒറ്റപ്പെട്ട npm prefix-ലേക്ക്
  ഇൻസ്റ്റാൾ ചെയ്യുന്നു. id എന്നത് short `HEAD` sha (tree-യിൽ ലോക്കൽ മാറ്റങ്ങളുണ്ടെങ്കിൽ `-dirty`) അല്ലെങ്കിൽ
  tarball-നുള്ള `tgz-<sha256>` ആണ്. ഇതിനകം build ചെയ്തിട്ടുള്ള clean id വീണ്ടും build ചെയ്യുന്നതിന് പകരം
  പുനരുപയോഗിക്കും; വീണ്ടും build ചെയ്യാൻ `--force` നൽകുക.
- **Source അല്ല, package validate ചെയ്യുക.** `validate`, പുതിയ `DATA_DIR=<candidate>/data`, വ്യാജ
  secrets എന്നിവ ഉപയോഗിച്ചും operator-ന്റെ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY`,
  `INITIAL_PASSWORD` എന്നിവ environment-ൽ നിന്ന് നീക്കം ചെയ്തും ഇൻസ്റ്റാൾ ചെയ്ത CLI
  (`serve --port <free port>`) ആരംഭിക്കുന്നു; അതിനാൽ ഒരു പുതിയ install-ന്റെ keyless loopback posture
  ഇത് പരിശോധിക്കുന്നു. `GET /api/health` 200 നൽകുന്നതുവരെ ഇത് കാത്തിരിക്കുന്നു, `GET /v1/models`
  200 നൽകണമെന്ന് നിർബന്ധമാക്കുന്നു, process group നിർത്തുന്നു, കൂടാതെ tarball hash-നൊപ്പം verdict
  `validation.json`-ൽ രേഖപ്പെടുത്തുന്നു.
- **അതേ artifact promote ചെയ്യുക.** നിലവിലെ tarball hash-നായി വിജയകരമായ validation ഇല്ലാത്ത
  candidate-നെ `promote` നിരസിക്കുന്നു. ഡിഫോൾട്ട് active slot `_artifacts/candidate/current` ആണ്;
  `--target <dir>` അതേ filesystem-ലെ മറ്റൊരു directory തിരഞ്ഞെടുക്കുന്നു, അതിന്റെ previous slot
  `<dir>.previous` ആയിരിക്കും. ഓരോ rename-ഉം atomic ആണ്; ഇടയിൽ പരാജയമുണ്ടായാൽ ഇതിനകം നടന്ന
  rename-കൾ തിരിച്ചാക്കപ്പെടും.
- **Roll back ചെയ്യുക.** `run`, promoted slot വീണ്ടും validate ചെയ്യുകയും ആ പരിശോധന പരാജയപ്പെട്ടാൽ
  `current`-ഉം `previous`-ഉം തിരികെ പരസ്പരം മാറ്റുകയും ചെയ്യുന്നു. ആദ്യ validation പരാജയപ്പെടുന്ന
  candidate ഒരിക്കലും promote ചെയ്യപ്പെടില്ല.

എല്ലാം gitignore ചെയ്ത `_artifacts/candidate/`-ന് കീഴിലാണ് എഴുതപ്പെടുന്നത്; നിലവിലുള്ള OmniRoute
installation-ഉം അതിന്റെ data directory-യും ഒരിക്കലും സ്പർശിക്കപ്പെടില്ല. Promoted CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ആണ്; അത് ഉപയോഗിക്കുമ്പോൾ നിങ്ങളുടെ സ്വന്തം
`DATA_DIR` ഉപയോഗിച്ച് ആരംഭിക്കുക. Exit codes: `0` വിജയം, `1` validation അല്ലെങ്കിൽ promotion പരാജയം,
`2` ഉപയോഗത്തിലെ പിശക് അല്ലെങ്കിൽ build ലഭ്യമല്ല.

## ലോക്കൽ ലൂപ്പും CI-യും തമ്മിലുള്ള താരതമ്യം

| ഓരോ പാച്ചിനും ലോക്കലായി പ്രവർത്തിപ്പിക്കേണ്ടവ                                           | CI നൽകുന്ന വിപുലമായ സൂചന                                                       |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| മുകളിലുള്ള നേരിട്ടുള്ള പെരുമാറ്റ പരിശോധനകളും വിഭാഗ ഗേറ്റുകളും                           | ഷാർഡ് ചെയ്ത സമ്പൂർണ്ണ യൂണിറ്റ് സ്യൂട്ടും സീരിയൽ പരിശോധനകളും                    |
| `npm run lint`                                                                          | Vitest സ്യൂട്ടുകളും കവറേജ്/ഗുണനിലവാര റാച്ചറ്റുകളും                             |
| ബാധിക്കപ്പെട്ട കരാർ ആവശ്യപ്പെടുമ്പോൾ മാത്രം ടൈപ്പ് പരിശോധനയോ ബിൽഡോ നടത്തുക              | പ്രൊഡക്ഷൻ ബിൽഡ്, സുരക്ഷ, ഡോക്സ്, ഡിപെൻഡൻസി, PR-നയ ഗേറ്റുകൾ                     |
| ഓട്ടോമേഷന് പെരുമാറ്റം തെളിയിക്കാൻ കഴിയാത്തപ്പോൾ മാത്രം മാനുവൽ ഇന്ററാക്ഷൻ/ലൈവ് പരിശോധനകൾ | വർക്ക്ഫ്ലോ കോൺഫിഗർ ചെയ്തിട്ടുള്ള ക്രോസ്-ജോബ് ഇന്റഗ്രേഷൻ, പ്ലാറ്റ്ഫോം പരിശോധനകൾ |

വിജയകരമായ ഒരു കേന്ദ്രീകൃത ലൂപ്പ്, മാറ്റം വരുത്തിയ കരാറിനെക്കുറിച്ചുള്ള തെളിവാണ്; ബന്ധമില്ലാത്ത CI പരിശോധനകൾ
വിജയിക്കുമെന്നതിനുള്ള തെളിവല്ല. അതേസമയം, ഓരോ ലോക്കൽ എഡിറ്റും സമ്പൂർണ്ണ റിപ്പോസിറ്ററി മാട്രിക്സ് പൂർത്തിയാകുന്നതുവരെ കാത്തിരിക്കേണ്ടതില്ല.

## പൊരുത്തപ്പെടുത്തൽ ചെക്ക്ലിസ്റ്റ്

റിവ്യൂ അഭ്യർത്ഥിക്കുന്നതിന് മുമ്പ്:

- PR ബേസ് ഇപ്പോഴും ഏറ്റവും ഉയർന്ന സജീവ `release/v*` ബ്രാഞ്ചാണെന്ന് സ്ഥിരീകരിക്കുക.
- ആ ബേസ് ഫെച്ച് ചെയ്ത്, നിങ്ങൾ ബ്രാഞ്ച് സൃഷ്ടിച്ചതിനുശേഷം ലാൻഡ് ചെയ്ത കമ്മിറ്റുകൾ റിവ്യൂ ചെയ്യുക.
- അബദ്ധത്തിൽ സംഭവിച്ചതോ ജനറേറ്റ് ചെയ്തതോ ആയ അനാവശ്യ മാറ്റങ്ങൾ കണ്ടെത്താൻ `git diff <active-base>...HEAD` റിവ്യൂ ചെയ്യുക.
- ഉറവിടം അപ്ഡേറ്റ് ചെയ്ത് ഔട്ട്പുട്ട് വീണ്ടും ജനറേറ്റ് ചെയ്തുകൊണ്ട് കാറ്റലോഗിലെയും ജനറേറ്റ് ചെയ്ത ഡോക്യുമെന്റുകളിലെയും കോൺഫ്ലിക്റ്റുകൾ പരിഹരിക്കുക.
- പൊരുത്തപ്പെടുത്തലിനുശേഷം PR വിവരണത്തിൽ ലിസ്റ്റ് ചെയ്തിട്ടുള്ള എല്ലാ കേന്ദ്രീകൃത ടെസ്റ്റുകളും ഗേറ്റുകളും വീണ്ടും പ്രവർത്തിപ്പിക്കുക.
- മാറിയ ബേസുമായി പൊരുത്തപ്പെടാൻ വേണ്ടി മാത്രം അസർഷനുകൾ ഒരിക്കലും ദുർബലപ്പെടുത്തുകയോ ആവശ്യമായ ടെസ്റ്റുകൾ ഒഴിവാക്കുകയോ ചെയ്യരുത്.

റിലീസ്-ഫ്രീസ്, റീടാർഗറ്റിംഗ് നിയമങ്ങൾക്കായി
