> **ചുരുക്കത്തിൽ**: ബിൽറ്റ്-ഇൻ ആരോഗ്യ നിരീക്ഷണം, പ്രൊവൈഡർ ഓട്ടോപൈലറ്റ്, ക്വാട്ട ട്രാക്കിംഗ്, ഒബ്സർവബിലിറ്റി ഹുക്കുകൾ എന്നിവയോടെയാണ് OmniRoute ലഭ്യമാകുന്നത്. ഡാഷ്ബോർഡ്, അലേർട്ടുകൾ, ട്രബിൾഷൂട്ടിംഗ് എന്നിവ ഈ ഗൈഡിൽ ഉൾപ്പെടുത്തിയിരിക്കുന്നു.

**സ്രോതസ്സുകൾ:**

- `src/lib/monitoring/observability.ts` — ഒബ്സർവബിലിറ്റി സ്നാപ്പ്ഷോട്ട്
- `src/lib/monitoring/comboHealthAutopilot.ts` — കോംബോ ഹെൽത്ത് ഓട്ടോപൈലറ്റ്
- `src/lib/monitoring/providerHealthAutopilot.ts` — പ്രൊവൈഡർ ഓട്ടോപൈലറ്റ്
- `src/lib/monitoring/providerHealthMatrix.ts` — പ്രൊവൈഡർ ഹെൽത്ത് മാട്രിക്സ്
- `src/lib/localHealthCheck.ts` — ലോക്കൽ ഹെൽത്ത് പരിശോധന
- `src/lib/tokenHealthCheck.ts` — ടോക്കൺ പുതുക്കലിന്റെ ആരോഗ്യം
- `src/lib/proxyHealth.ts` — പ്രോക്സി ഹെൽത്ത് കാഷ് (PROXY_GUIDE.md-ൽ ഉൾപ്പെടുത്തിയിരിക്കുന്നു)

## അവലോകനം

OmniRoute-ന് **നിരീക്ഷണത്തിന്റെ 3 ലെയറുകൾ** ഉണ്ട്:

```
┌──────────────────────────────────────────────────────────────┐
│  ലെയർ 1: സിസ്റ്റം ഹെൽത്ത് (സെർവർ തലം)                        │
│  ├─ localHealthCheck.ts — DB, പോർട്ടുകൾ, നേറ്റീവ് ഡിപെൻഡൻസികൾ │
│  ├─ db/healthCheck.ts — സമഗ്രത, FK, അനാഥ ആർട്ടിഫാക്റ്റുകൾ     │
│  └─ ഡാഷ്ബോർഡ്: /dashboard/health                            │
├──────────────────────────────────────────────────────────────┤
│  ലെയർ 2: പ്രൊവൈഡർ ഹെൽത്ത് (ഓരോ പ്രൊവൈഡറിനുമുള്ള പ്രതിരോധശേഷി) │
│  ├─ providerHealthAutopilot.ts — സർക്യൂട്ട് ബ്രേക്കർ, കൂൾഡൗണുകൾ │
│  ├─ providerHealthMatrix.ts — പ്രൊവൈഡർ/മോഡൽ അനുസരിച്ചുള്ള ഹെൽത്ത് സ്കോറുകൾ │
│  └─ ഡാഷ്ബോർഡ്: /dashboard/providers                         │
├──────────────────────────────────────────────────────────────┤
│  ലെയർ 3: ലൈവ് ഒബ്സർവബിലിറ്റി (റൺടൈം സ്നാപ്പ്ഷോട്ടുകൾ)          │
│  ├─ observability.ts — സർക്യൂട്ട് ബ്രേക്കറുകൾ, സെഷനുകൾ, ക്വാട്ട │
│  ├─ tokenHealthCheck.ts — OAuth ടോക്കൺ പുതുക്കലിന്റെ ആരോഗ്യം  │
│  └─ MCP ടൂളുകൾ: omniroute_get_health, omniroute_get_session_snapshot │
└──────────────────────────────────────────────────────────────┘
```

## ഡാഷ്ബോർഡ് പേജുകൾ

### `/dashboard/health` (സിസ്റ്റം ഹെൽത്ത്)

ഉയർന്ന തലത്തിലുള്ള ഹെൽത്ത് ഡാഷ്ബോർഡ് ഇനിപ്പറയുന്നവ കാണിക്കുന്നു:

| വിഭാഗം                  | കാണിക്കുന്നത്                                                   |
| ----------------------- | --------------------------------------------------------------- |
| **സെർവർ നില**           | പ്രവർത്തനസമയം, പതിപ്പ്, പോർട്ട്, സജീവ കണക്ഷനുകൾ                 |
| **ഡാറ്റാബേസ്**          | കണക്ഷൻ, സമഗ്രത, WAL വലുപ്പം, സമീപകാല മൈഗ്രേഷനുകൾ                |
| **പ്രൊവൈഡർ സംഗ്രഹം**    | സജീവ എണ്ണം, ആരോഗ്യകരമായവയുടെ എണ്ണം, തുറന്ന ബ്രേക്കറുകളുടെ എണ്ണം |
| **ക്വാട്ട മോണിറ്ററുകൾ** | സജീവ സെഷനുകൾ, അലേർട്ടിംഗ്, തീർന്നവ                              |
| **സമീപകാല പിശകുകൾ**     | സ്റ്റാക്ക് ട്രേസുകളോടുകൂടിയ അവസാന 10 പിശകുകൾ                    |
| **റിസോഴ്സ് ഉപയോഗം**     | മെമ്മറി, CPU, ഹീപ്പ് പ്രഷർ ഇൻഡിക്കേറ്റർ                         |

### `/dashboard/providers` (പ്രൊവൈഡർ ഹെൽത്ത്)

ഓരോ പ്രൊവൈഡറിനുമുള്ള ഡാഷ്ബോർഡ്:

| കോളം       | വിവരണം                                                      |
| ---------- | ----------------------------------------------------------- |
| പ്രൊവൈഡർ   | പ്രൊവൈഡർ ID + പ്രദർശന നാമം                                  |
| ആരോഗ്യം    | പച്ച/മഞ്ഞ/ചുവപ്പ് നില                                       |
| സർക്യൂട്ട് | തുറന്ന/അടച്ച/പകുതി തുറന്ന അവസ്ഥ                             |
| കണക്ഷനുകൾ  | കണക്ഷനുകളുടെ എണ്ണം, അവസാന പുതുക്കൽ                          |
| മോഡലുകൾ    | ലഭ്യമായ മോഡലുകൾ, ഓരോ മോഡലിന്റെയും ആരോഗ്യം                   |
| ചെലവ്      | ഇന്നത്തെ ചെലവ്, 7 ദിവസത്തെ പ്രവണത                           |
| പിശകുകൾ    | കഴിഞ്ഞ 24 മണിക്കൂറിലെ പിശകുകളുടെ എണ്ണം, പ്രധാന പിശക് ക്ലാസ് |

കൂടുതൽ വിവരങ്ങൾ കാണാൻ ഒരു പ്രൊവൈഡറിൽ ക്ലിക്ക് ചെയ്യുക:

- ലേറ്റൻസി വിഭജനത്തോടുകൂടിയ സമീപകാല അഭ്യർത്ഥനകൾ
- ഓരോ കണക്ഷനുമുള്ള ഹെൽത്ത് സ്കോറുകൾ
- ഓരോ മോഡലിനുമുള്ള ലോക്കൗട്ടുകൾ
- ഓട്ടോപൈലറ്റ് ശുപാർശകൾ

### `/dashboard/quota` (ക്വാട്ട ട്രാക്കിംഗ്)

ഓരോ API കീക്കും:

- നിലവിലെ ഉപയോഗവും പരിധിയും (പ്രോഗ്രസ് ബാർ)
- ക്വാട്ട പ്രവണത (30 ദിവസത്തെ ചാർട്ട്)
- അടുത്ത റീസെറ്റ് സമയം
- അലേർട്ട് ചരിത്രം

### `/dashboard/combos` (കോംബോ ഹെൽത്ത്)

ഓരോ കോംബോയ്ക്കും:

- സ്ട്രാറ്റജി + ടാർഗെറ്റുകൾ
- ഓരോ ടാർഗെറ്റിന്റെയും ആരോഗ്യം
- സമീപകാല ഫാൾബാക്ക് ഇവന്റുകൾ
- വിജയനിരക്ക് (24 മണിക്കൂർ, 7 ദിവസം, 30 ദിവസം)

## ആരോഗ്യ പരിശോധന API

OmniRoute തുറന്നുകാട്ടുന്നു** രണ്ട്** HTTP ആരോഗ്യ പ്രതലങ്ങൾ. ഓർക്കസ്ട്രേറ്റർമാർക്കായി അവ പരസ്പരം മാറ്റാവുന്നതല്ല.

| പാത                          | ഉദ്ദേശ്യം                                                              | ഭാരം                             | ഇതിനായി ഉപയോഗിക്കുക                                                                   |
| ---------------------------- | ---------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------- |
| `GET /healthz`               | ജീവിതചക്രം liveness/readiness (`ok` / `starting` / `stopping`)         | നിസ്സാരം (ഘട്ട പതാക മാത്രം)      | കുബെർനെറ്റസ്** സന്നദ്ധത** ; മൃദുവായ** സജീവത** നിങ്ങൾ HTTP ഉപയോഗിക്കേണ്ടതുണ്ടെങ്കിൽ    |
| `GET /api/monitoring/health` | ഡീപ് സിസ്റ്റം + പ്രൊവൈഡർ സംഗ്രഹം (DB, ഹീപ്പ്, കാറ്റലോഗ് കൗണ്ടുകൾ, ...) | ഹെവി ( DB / മോണിറ്ററിംഗ് വർക്ക്) | ഡാഷ്ബോർഡുകൾ, ബ്ലാക്ക്ബോക്സ് ആഴത്തിലുള്ള പരിശോധനകൾ, Docker's ബിൽറ്റ്-ഇൻ ആരോഗ്യ പരിശോധന |

> **കുറിപ്പ്:** പ്രൊവൈഡർ ഹെൽത്ത് മെട്രിക്സ്, ഓട്ടോപൈലറ്റ് പ്രശ്നങ്ങൾ, ക്വാട്ട മോണിറ്ററുകൾ, ടോക്കൺ ഹെൽത്ത്, `/api/monitoring/health` അപ്പുറത്തുള്ള ലേറ്റൻസി വിശദാംശങ്ങൾ എന്നിവ വഴി ലഭ്യമാണ്**MCP ഉപകരണം** `observability_snapshot` അല്ലെങ്കിൽ** ഡാഷ്ബോർഡ്** പേജുകൾ — അവയ്ക്കായി പ്രത്യേക REST റൂട്ടുകളൊന്നുമില്ല.

രണ്ട് റൂട്ടുകളും ഓടുന്നു** അതേ നോഡ് ഇവൻ്റ് ലൂപ്പ്** അഭ്യർത്ഥന കൈകാര്യം ചെയ്യുന്നതുപോലെ. ഒരു സിപിയു-ബൗണ്ട് പാത്ത് (വലിയ `GET /v1/models` കാറ്റലോഗ് വർക്ക്, ദൈർഘ്യമേറിയ സന്ദർഭ കംപ്രഷൻ / ടോക്കൺ കൗണ്ടിംഗ്) വൈകും** എല്ലാം** HTTP ഹാൻഡ്ലറുകൾ, `/healthz` ഉൾപ്പെടെ. ഇവൻ്റ്-ലൂപ്പ് തിരക്കുള്ള ≠ പ്രോസസ്സ് മരിച്ചു. ഹോഗ് ശരിയാക്കാൻ മുൻഗണന നൽകുക; പ്രോബ് ട്യൂണിംഗ് തെറ്റായ കൊലപാതകങ്ങൾ കുറയ്ക്കുന്നു.

### ഭാരം കുറഞ്ഞ ഓർക്കസ്ട്രേറ്റർ അന്വേഷണം

```bash
GET /healthz
# or HEAD /healthz
```

- **200** സെർവർ ലൈഫ് സൈക്കിൾ ഘട്ടം തയ്യാറാകുമ്പോൾ + ബോഡി `ok`
- **503** ബൂട്ട് അല്ലെങ്കിൽ ഷട്ട്ഡൗൺ സമയത്ത് + `starting` / `stopping`
- നടപ്പിലാക്കൽ: `src/app/healthz/route.ts` ( DB പിംഗ് ഇല്ല)

#### `credentialHealth`: probe-cache vs SQLite `test_status`

`GET /api/monitoring/health` → `credentialHealth` ആണ്** ഇൻ-മെമ്മറി പ്രോബ്-കാഷെ ഗേജ്** , `provider_connections.test_status` ൻ്റെ ലൈവ് ഡംപ് അല്ല. #12532 ശേഷം അഭ്യർത്ഥന പാത `getCachedCredentialHealthSummary()` മാത്രം വായിക്കുന്നു; പശ്ചാത്തല പ്രോബുകൾ ഇവൻ്റ് ലൂപ്പിൽ നിന്ന് കാഷെ പുതുക്കുന്നു.

| പാളി                            | എവിടെ                                                                 | എന്താണ് അർത്ഥമാക്കുന്നത്                                                                                                                                                                                                                            |
| ------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| പ്രോബ്-കാഷെ ഗേജ്                | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | അവസാന ക്രെഡൻഷ്യൽ-ആരോഗ്യ അന്വേഷണ ഫലങ്ങൾ ഇപ്പോഴും പ്രോസസ്സ് മെമ്മറിയിൽ സൂക്ഷിച്ചിരിക്കുന്നു. `source` എപ്പോഴും `probe-cache` ആണ്.                                                                                                                     |
| പരാജയപ്പെട്ട കണക്ഷൻ വിശദാംശങ്ങൾ | `credentialHealth.failedConnections`                                  | അവതരിപ്പിക്കുക** `failed > 0` ആയിരിക്കുമ്പോൾ മാത്രം** . `status=error` (`connectionId`, `status`, sanitized `lastError` / `lastErrorType`) ഉള്ള കാഷെ വരികളുടെ ബൗണ്ടഡ് ലിസ്റ്റ്. ലിസ്റ്റ് ക്യാപ് ചെയ്യുമ്പോൾ `failedOmitted` സജ്ജീകരിച്ചിരിക്കുന്നു. |
| SQLite സ്റ്റിക്കി സ്റ്റാറ്റസ്   | `credentialHealth.staleDbNonOkCount`                                  | എണ്ണം** സജീവമാണ്** (`is_active=1`) കണക്ഷൻ വരികൾ നിലനിൽക്കുന്ന `test_status` അറിയപ്പെടുന്ന നോൺ-ഓകെ (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).                                                                |

രണ്ട് ലെയറുകൾക്ക് ഉദ്ദേശ്യത്തോടെ വിയോജിക്കാം:

- `staleDbNonOkCount>0` — SQLite ഇപ്പോഴും ഒരു സ്റ്റിക്കി `test_status` ഉള്ളപ്പോൾ `failed=0` അളക്കുക (ഉദാഹരണത്തിന് `expired` അല്ലെങ്കിൽ `credits_exhausted`) ഏറ്റവും പുതിയ പ്രോബ്-കാഷെ സ്നാപ്പ്ഷോട്ട് `status=error` ആയി കണക്കാക്കില്ല.
- SQLite ആരോഗ്യകരമായി കാണുമ്പോൾ `failed>0` അളക്കുക — അടുത്തിടെ നടത്തിയ ഒരു അന്വേഷണം പരാജയപ്പെട്ടു, കാഷെ ചെയ്തു; DB വരി പുതുക്കിയിട്ടില്ല, അല്ലെങ്കിൽ പിന്നീട് മായ്ക്കപ്പെട്ടു.

ഈ എൻഡ് പോയിൻ്റ് സ്ക്രാപ്പ് ചെയ്യുമ്പോൾ `provider_connections.test_status` യിൽ മാത്രം അലേർട്ട് ചെയ്യരുത്. തത്സമയ പ്രോബ് പരാജയങ്ങൾക്ക് `failed` + `failedConnections` ഉപയോഗിക്കുക, നിങ്ങൾക്ക് സ്ഥിരമായ സ്റ്റിക്കി-സ്റ്റാറ്റസ് കൗണ്ട് ആവശ്യമുള്ളപ്പോൾ `staleDbNonOkCount` ഉപയോഗിക്കുക.

### കുബർനെറ്റസ് ശുപാർശകൾ അന്വേഷിക്കുന്നു

OmniRoute a ആണ്** ഒറ്റ നോഡ് പ്രക്രിയ** (ഒരു ഇവൻ്റ് ലൂപ്പ്). സ്റ്റോക്ക് Docker `HEALTHCHECK` ഭാരം കുറഞ്ഞ `/healthz` ലക്ഷ്യമിടുന്നു. `/api/monitoring/health` ആണ്** വളരെ ഭാരം** കുബെലെറ്റ് ലൈവ്നെസ് ഇടവേളകൾക്കായി.

| അന്വേഷണം                | ശുപാർശ ചെയ്യുന്ന ലക്ഷ്യം                                                               | കുറിപ്പുകൾ                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **സ്റ്റാർട്ടപ്പ്**      | നീളമുള്ള `failureThreshold` (അല്ലെങ്കിൽ വലിയ `startPeriod`) ഉള്ള `GET /healthz` HTTP   | കോൾഡ് സ്റ്റാർട്ട് + SQLite മൈഗ്രേഷൻ കുറച്ച് സെക്കൻഡുകൾ കവിഞ്ഞേക്കാം                                                                                                                                                                                                                                                                                                                                                   |
| **സന്നദ്ധത**            | HTTP `GET /healthz`                                                                    | ജീവിതചക്രം `ok` / `starting` / `stopping` (200 vs 503). ലൂപ്പ് CPU-ബ്ലോക്ക് ആണെങ്കിൽ ഇപ്പോഴും ഫ്ലാപ്പുചെയ്യുന്നു. എ** ഒന്നിലധികം സെക്കൻഡിൽ 200 എന്നത് ആരോഗ്യകരമല്ല** (#10303) — ഇതിനർത്ഥം 3-ബൈറ്റ് ഹാൻഡ്ലർ പ്രവർത്തിക്കുന്നതിന് മുമ്പ് ഇവൻ്റ് ലൂപ്പ് പട്ടിണിയിലായിരുന്നു എന്നാണ്.                                                                                                                                     |
| **സജീവത**               | HTTP `GET /livez`,** അല്ലെങ്കിൽ TCP** പ്രധാന സേവന പോർട്ടിൽ (`PORT`, ഡിഫോൾട്ട് `20128`) | `/livez` പ്രോസസ്സ്-ലൈവ് മാത്രമാണ് (ഹാൻഡ്ലർ പ്രവർത്തിക്കുകയാണെങ്കിൽ എല്ലായ്പ്പോഴും 200). ഇത് ഇപ്പോഴും ഇവൻ്റ് ലൂപ്പ് — തിരക്കേറിയ ≠ മരിച്ചതായി പങ്കിടുന്നു, കൂടാതെ TCP ചെയ്യുന്നതിനേക്കാൾ മികച്ച ഇവൻ്റ്-ലൂപ്പ് പട്ടിണി (#10303) ഇത് കണ്ടെത്തുന്നില്ല. മുൻഗണന നൽകുക**TCP** catalog/compression ലോഡിന് കീഴിൽ HTTP അന്വേഷണം സമയം കഴിഞ്ഞു എങ്കിൽ; ചെയ്യുക** അല്ല** ഷോർട്ട് ഇവൻ്റ്-ലൂപ്പ് സ്റ്റാളുകളിൽ ഒന്നുകിൽ പോഡ് കൊല്ലുക |
| **ആഴത്തിലുള്ള ആരോഗ്യം** | ഒരു ബാഹ്യ ചെക്കറിൽ നിന്ന്`GET /api/monitoring/health`                                  | kubelet `livenessProbe` / tight `readinessProbe` എന്നതിനുള്ളതല്ല                                                                                                                                                                                                                                                                                                                                                      |

ഉദാഹരണ രൂപം (നിങ്ങളുടെ കോൾഡ്-സ്റ്റാർട്ട്, കംപ്രഷൻ ലോഡിലേക്ക് പരിധി ക്രമീകരിക്കുക):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Under event-loop stall HTTP /livez can still time out. TCP is the
  # conservative alternative:
  # tcpSocket:
  #   port: http
```

**ചെയ്യരുത്** പോയിൻ്റ് kubelet** സജീവത** `/api/monitoring/health` യിൽ. ആ പാത യഥാർത്ഥ DB/monitoring വർക്ക് ചെയ്യുന്നു, അത് ലോഡിൽ തെറ്റായ പോസിറ്റീവ് ആയിരിക്കും.

ബന്ധപ്പെട്ടത്: [#10052](https://github.com/cheaper-inference/OmniRoute/issues/10052) (ഇവൻ്റ് ലൂപ്പ് തിരക്കിലായിരിക്കുമ്പോൾ അന്വേഷണം), [#9685](https://github.com/cheaper-inference/OmniRoute/issues/9685) / [#10055](https://github.com/cheaper-inference/OmniRoute/pull/10055) (കാറ്റലോഗ് പ്രൈസിംഗ് ഹോഗ്), [#10117](https://github.com/cheaper-inference/OmniRoute/issues/10117) (കംപ്രഷൻ ടോക്കൺ-കൗണ്ട് ഹോഗ്).

### systemd വാച്ച്ഡോഗ് (ഫ്രോസൺ ഇവൻ്റ് ലൂപ്പ്)

ഒരു systemd ഹോസ്റ്റിൽ, OmniRoute അത് തയ്യാറാകുമ്പോൾ സേവന മാനേജരോട് പറയുകയും അത് പിംഗ് ചെയ്യുന്നത് തുടരുകയും ചെയ്യുന്നു, അതിനാൽ ഇവൻ്റ് ലൂപ്പ് കുടുങ്ങിയ ഒരു സെർവർ കൊല്ലപ്പെടുകയും നിശബ്ദത പാലിക്കുന്നതിനുപകരം പുനരാരംഭിക്കുകയും ചെയ്യുന്നു. സെർവറിൻ്റെ സ്വന്തം ഇവൻ്റ് ലൂപ്പിൽ നിന്നാണ് പിംഗുകൾ വരുന്നത്: അത് തടയുമ്പോൾ, അവ നിർത്തുന്നു, കൂടാതെ `WatchdogSec` ഒന്നുമില്ലാതെ കഴിഞ്ഞാൽ systemd സേവനം പുനരാരംഭിക്കുന്നു.

[`omniroute autostart enable`](../../bin/cli/tray/autostart.mjs) ഇതിനോടകം ഒരു ഉപയോക്തൃ യൂണിറ്റ് എഴുതുന്നു. നിങ്ങൾ സ്വയം എഴുതുന്ന യൂണിറ്റിന് (ഡിഫോൾട്ട് `Type=simple`) വാച്ച്ഡോഗ് ലഭിക്കില്ല, അതിനാൽ ഈ വരികൾ അതിൻ്റെ `[Service]` വിഭാഗത്തിലേക്ക് ചേർക്കുക:

```ini
[Service]
Type=notify
NotifyAccess=all
WatchdogSec=180
TimeoutStartSec=300
```

ജനറേറ്റ് ചെയ്ത യൂണിറ്റ് `Restart=on-failure` സജ്ജീകരിക്കുന്നു, അതിനാൽ ആ വരിയും — ഉം ചേർക്കാതെ വാച്ച്ഡോഗ് അത് പുനരാരംഭിക്കുന്നതിനുപകരം സ്റ്റക്ക് സേവനത്തെ ഇല്ലാതാക്കുന്നു.

- `Type=notify`: സെർവർ `READY=1` അയയ്ക്കുമ്പോൾ സേവനം "ആരംഭിക്കുന്നു", പ്രോസസ്സ് ഫോർക്ക് ചെയ്യുമ്പോൾ അല്ല. `TimeoutStartSec` ഒരു മന്ദഗതിയിലുള്ള തുടക്കത്തെ പരിമിതപ്പെടുത്തുന്നു.
- `NotifyAccess=all`: `omniroute serve` സൂപ്പർവൈസറുടെ കുട്ടിയായ സെർവർ പ്രക്രിയയാണ് പിംഗുകൾ അയയ്ക്കുന്നത്.
- `WatchdogSec`: ഓരോ 60 സെക്കൻഡിലും പിംഗുകൾ പുറത്തേക്ക് പോകുന്നു, അതിനാൽ ഉപയോഗിക്കുക** 120 അല്ലെങ്കിൽ കൂടുതൽ** . ചെറിയ മൂല്യങ്ങൾ ആരോഗ്യകരമായ സെർവർ പുനരാരംഭിക്കും.
- മുൻവശത്ത് `omniroute serve` പ്രവർത്തിപ്പിക്കുക. `--daemon` യൂണിറ്റിൻ്റെ cgroup-ൽ നിന്ന് സെർവറിനെ വേർപെടുത്തുന്നു, അറിയിപ്പ് ഹാൻഡ്ഷേക്ക് ഒരിക്കലും പൂർത്തിയാകുന്നില്ല.

പുനരാരംഭിച്ചതിന് ശേഷം ഇത് സജീവമാണോയെന്ന് പരിശോധിക്കുക:

```bash
systemctl --user show omniroute -p WatchdogUSec -p WatchdogTimestamp
```

`WatchdogUSec` ക്രമീകരിച്ചിരിക്കുന്ന കാലതാമസം കാണിക്കുന്നു, കൂടാതെ `WatchdogTimestamp` ഓരോ മിനിറ്റിലും മുന്നോട്ട് നീങ്ങുന്നു. വാച്ച്ഡോഗ് മൂലമുണ്ടാകുന്ന പുനരാരംഭം `Result=watchdog` ആയി രേഖപ്പെടുത്തുന്നു. യൂണിറ്റ് അതേപടി നിലനിർത്തുമ്പോൾ പിംഗ്സ് ഓഫ് ചെയ്യാൻ, `OMNIROUTE_DISABLE_SD_NOTIFY=1` സജ്ജമാക്കുക; ഒരു `NOTIFY_SOCKET` ഇല്ലാതെ (ടെർമിനൽ, Docker, Electron, Windows) ഒന്നും അയയ്ക്കില്ല.

ഇവൻ്റ് ലൂപ്പ് പ്രവർത്തിക്കുന്നത് തുടരുന്നുണ്ടോ എന്ന് മാത്രമാണ് വാച്ച്ഡോഗ് പരിശോധിക്കുന്നത്. വേഗത കുറഞ്ഞതും എന്നാൽ ഇപ്പോഴും തിരിയുന്നതുമായ ഒരു സെർവർ പുനരാരംഭിച്ചിട്ടില്ല.

### ഓപ്ഷണൽ അഭ്യർത്ഥന-പാത്ത് വർക്ക് (മെമ്മറി, കഴിവുകൾ, ടോക്കൺ പുതുക്കൽ)

മെമ്മറി എക്സ്ട്രാക്ഷൻ, സ്കിൽസ് ഇഞ്ചക്ഷൻ, OAuth ടോക്കൺ പുതുക്കൽ എന്നിവ പങ്കിടുന്നു** പ്രധാന നോഡ് ഇവൻ്റ് ലൂപ്പ്** `/healthz` ഉപയോഗിച്ച്. അവ ഡാഷ്ബോർഡ്-ടോഗിൾ ഫീച്ചറുകളാണ് (`memoryEnabled`, `skillsEnabled`), ഒരു വർക്കർ പൂൾ അല്ല. [പരിസ്ഥിതി — ഇവൻ്റ്-ലൂപ്പ് ചെലവ്](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349) കാണുക.

### ദാതാവിൻ്റെ ആരോഗ്യം

> **REST അവസാന പോയിൻ്റ് ഇല്ല.** ദാതാവിൻ്റെ ആരോഗ്യ ഡാറ്റ MCP ടൂൾ `observability_snapshot` അല്ലെങ്കിൽ ഡാഷ്ബോർഡ് `/dashboard/providers` പേജ് വഴി ലഭ്യമാണ്.

### ദാതാവിൻ്റെ വിശദാംശങ്ങൾ

> **REST അവസാന പോയിൻ്റ് ഇല്ല.** ദാഷ്ബോർഡ് `/dashboard/providers` പേജ് വഴി ഓരോ ദാതാവിൻ്റെയും വിശദാംശങ്ങൾ ലഭ്യമാണ്.

## പ്രൊവൈഡർ ഹെൽത്ത് ഓട്ടോപൈലറ്റ്

`providerHealthAutopilot.ts` മൊഡ്യൂൾ ഇനിപ്പറയുന്ന കാര്യങ്ങൾ ചെയ്യുന്ന ഒരു **സ്വയം സുഖപ്പെടുന്ന സിസ്റ്റമാണ്**:

1. പ്രൊവൈഡറിലെ പ്രശ്നങ്ങൾ കണ്ടെത്തുന്നു (സർക്യൂട്ട് തുറന്നിരിക്കുക, കൂൾഡൗണുകൾ, ലോക്കൗട്ടുകൾ, ക്വോട്ട മുന്നറിയിപ്പുകൾ)
2. അവ പരിഹരിക്കുന്നതിനുള്ള **ശുപാർശചെയ്ത നടപടികൾ** സൃഷ്ടിക്കുന്നു
3. കുറഞ്ഞ അപകടസാധ്യതയുള്ള നടപടികൾ വേണമെങ്കിൽ **സ്വയമേവ നടപ്പിലാക്കുന്നു**

> **REST എൻഡ്പോയിന്റ് ഇല്ല.** ഓട്ടോപൈലറ്റ് പ്രശ്നങ്ങൾ MCP ടൂൾ `observability_snapshot` വഴിയോ ഡാഷ്ബോർഡിലൂടെയോ ലഭ്യമാണ്. ഓട്ടോപൈലറ്റ് ആന്തരികമായി പ്രവർത്തിക്കുന്നു; അതിന്റെ പെരുമാറ്റം പരിസ്ഥിതി വേരിയബിളുകൾ വഴിയല്ല, ക്രമീകരണ DB-യിലെ (ഓരോ കണക്ഷനിലുമുള്ള `autopilotMode` ഫീൽഡ്) ക്രമീകരണങ്ങളിലൂടെയാണ് നിർണ്ണയിക്കുന്നത് — ഓട്ടോപൈലറ്റ്-മോഡ് env var-നായി `grep -rn` പ്രവർത്തിപ്പിച്ചാൽ ഫലങ്ങളൊന്നും ലഭിക്കില്ല.

### ഓട്ടോപൈലറ്റ് മോഡ്

ഓട്ടോപൈലറ്റ് സ്ഥിരസ്ഥിതിയായി **മാനുവൽ മോഡിലാണ്** പ്രവർത്തിക്കുന്നത് — ഇത് പ്രശ്നങ്ങൾ കണ്ടെത്തുകയും ശുപാർശചെയ്ത നടപടികൾ സൃഷ്ടിക്കുകയും ചെയ്യുന്നു, എന്നാൽ അവ സ്വയമേവ പ്രയോഗിക്കുന്നില്ല. ഡാഷ്ബോർഡ് വഴി നടപടികൾ പ്രയോഗിക്കാം.

## ക്വോട്ട മോണിറ്ററുകൾ

സബ്സ്ക്രിപ്ഷൻ പ്രൊവൈഡറുകൾക്കായി (Claude Code, Codex, GitHub Copilot) `observability.ts` **ഓരോ സെഷനുമുള്ള ക്വോട്ട മോണിറ്ററുകൾ** ലഭ്യമാക്കുന്നു:

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### സ്റ്റാറ്റസുകളുടെ അർത്ഥം

| സ്റ്റാറ്റസ് | എപ്പോൾ                          | UI നടപടി                                               |
| ----------- | ------------------------------- | ------------------------------------------------------ |
| `starting`  | പ്രാരംഭ പോളിംഗ് പുരോഗമിക്കുന്നു | സ്പിന്നർ                                               |
| `idle`      | സമീപകാല പ്രവർത്തനമൊന്നുമില്ല    | ഡാഷ്ബോർഡിൽനിന്ന് മറയ്ക്കുന്നു                          |
| `healthy`   | ക്വോട്ടയിൽ > 50% ശേഷിക്കുന്നു   | പച്ച ബിന്ദു                                            |
| `warning`   | ക്വോട്ടയിൽ < 50% ശേഷിക്കുന്നു   | മഞ്ഞ മുന്നറിയിപ്പ്                                     |
| `exhausted` | ക്വോട്ട = 0%                    | ചുവന്ന ബ്ലോക്ക്, അടുത്ത പ്രൊവൈഡറിലേക്ക് റൂട്ട് ചെയ്യുക |
| `error`     | പോളിംഗ് പരാജയപ്പെട്ടു           | ചുവന്ന ബിന്ദു, ഉടൻ വീണ്ടും ശ്രമിക്കുക                  |

### API

> **REST എൻഡ്പോയിന്റ് ഇല്ല.** ക്വോട്ട മോണിറ്റർ ഡാറ്റ MCP ടൂൾ `observability_snapshot` വഴിയോ ഡാഷ്ബോർഡിലൂടെയോ ലഭ്യമാണ്.

## നിരീക്ഷണക്ഷമതാ സ്നാപ്പ്ഷോട്ട്

    }

## ടോക്കൺ ആരോഗ്യ പരിശോധന

OAuth പ്രൊവൈഡറുകൾക്ക് (Claude Code, GitHub Copilot, Cursor) **ആനുകാലിക ടോക്കൺ പുതുക്കൽ** ആവശ്യമാണ്. `src/lib/tokenHealthCheck.ts` ഒരു പശ്ചാത്തല ഷെഡ്യൂളർ പ്രവർത്തിപ്പിക്കുന്നു:

- **സ്വീപ്പ് ടിക്ക്**: ഓരോ 60 സെക്കൻഡിലും (`src/lib/tokenHealthCheck.ts:30`-ലെ `TICK_MS = 60 * 1000` സ്വീപ്പ്)
- **ഓരോ കണക്ഷനുമുള്ള ആരോഗ്യ പരിശോധനാ ഇടവേള**: ഡിഫോൾട്ടായി 60 മിനിറ്റ് (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`); ക്രമീകരണ DB വഴി കോൺഫിഗർ ചെയ്യാം
- **401 ലഭിക്കുമ്പോഴുള്ള മുൻകരുതൽ പുതുക്കൽ**: ഓരോ കണക്ഷനുമുള്ള ഇന്റർസെപ്റ്റർ കൈകാര്യം ചെയ്യുന്നു

### ടോക്കൺ ആരോഗ്യനില

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### കോൺഫിഗറേഷൻ

ടോക്കൺ ആരോഗ്യ പരിശോധനാ കോൺഫിഗറേഷൻ `tokenHealthCheck.ts` ആന്തരികമായി കൈകാര്യം ചെയ്യുന്നു.

### ടോക്കൺ ആരോഗ്യം

> **REST എൻഡ്പോയിന്റ് ഇല്ല.** ടോക്കൺ ആരോഗ്യ ഡാറ്റ ഡാഷ്ബോർഡ് വഴിയോ MCP ടൂൾ `observability_snapshot` വഴിയോ ലഭ്യമാണ്.

## പ്രശ്നപരിഹാരം

### "പ്രൊവൈഡർ ആരോഗ്യകരമാണെന്ന് പറയുന്നു, പക്ഷേ അഭ്യർത്ഥനകൾ പരാജയപ്പെടുന്നു"

1. **autopilot പ്രശ്നങ്ങൾ** പരിശോധിക്കുക — ഒരു മോഡൽ ലോക്ക് ഔട്ട് ആയിരിക്കാം
2. നിർദ്ദിഷ്ട പിശക് ക്ലാസിനായി **സമീപകാല പിശകുകൾ** നോക്കുക
3. പ്രൊവൈഡർ കാർഡിലെ **കണക്ഷൻ ടെസ്റ്റ്** പരീക്ഷിക്കുക
4. പ്രൊവൈഡർ **അപ്സ്ട്രീമിൽ റേറ്റ്-ലിമിറ്റ് ചെയ്യപ്പെട്ടിട്ടുണ്ടോ** എന്ന് പരിശോധിക്കുക (ലോക്കലായി ദൃശ്യമല്ല)

### "ക്വോട്ട ആരോഗ്യകരമാണെന്ന് പറയുന്നു, പക്ഷേ എനിക്ക് 429-കൾ കാണുന്നു"

- 429 എന്നത് നിങ്ങൾ ക്വോട്ട ഉപയോഗിച്ചുതീർത്തതായി പ്രൊവൈഡർ പറയുന്നു എന്നാണ് അർത്ഥം
- OmniRoute-ന്റെ ക്വോട്ട ട്രാക്കിംഗ് **കാലഹരണപ്പെട്ടത്** ആയിരിക്കാം — പ്രൊവൈഡറുടെ അപ്സ്ട്രീം വിവരമാണ് ആധികാരികം
- ആന്തരിക ക്വോട്ട മോണിറ്റർ വഴി ക്വോട്ട ഡാറ്റ സ്വയമേവ പുതുക്കപ്പെടുന്നു

### "എല്ലാ ടാർഗറ്റുകളും ആരോഗ്യകരമായി കാണപ്പെടുന്നുണ്ടെങ്കിലും Combo പരാജയപ്പെടുന്നു"

- ടാർഗറ്റ് ക്രമീകരണ പ്രശ്നങ്ങൾക്കായി **combo health** ഡാഷ്ബോർഡ് പരിശോധിക്കുക
- **fallback ഇവന്റുകൾ** നോക്കുക — combo വളരെ വേഗത്തിൽ എല്ലാ ഓപ്ഷനുകളും ഉപയോഗിച്ചുതീർക്കുന്നുണ്ടാകാം
- **strategy** നിങ്ങളുടെ ഉപയോഗ സാഹചര്യവുമായി പൊരുത്തപ്പെടുന്നുവെന്ന് ഉറപ്പാക്കുക (priority vs round-robin vs auto)

### "ഡാറ്റാബേസ് ഹെൽത്ത് ചെക്ക് പരാജയപ്പെടുന്നു"

- `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"` പ്രവർത്തിപ്പിക്കുക
- "ok" ആണെങ്കിൽ — തെറ്റായ മുന്നറിയിപ്പാണ്; ഹെൽത്ത് ചെക്ക് ആവശ്യത്തിലധികം കർശനമാണ്
- മറ്റെന്തെങ്കിലും ആണെങ്കിൽ — **OmniRoute നിർത്തുക**, തുടർന്ന് [ദുരന്ത വീണ്ടെടുക്കൽ ഗൈഡ്](./DATABASE_GUIDE.md#disaster-recovery) പിന്തുടരുക

### "മെമ്മറി ഹീപ്പ് സമ്മർദ്ദം ഗുരുതരമാണ്"

```bash
# നിലവിലെ ഹീപ്പ് പരിശോധിക്കുക
node -e "console.log(process.memoryUsage())"

# മാനുവൽ GC ട്രിഗർ ചെയ്യുക (--expose-gc ആണെങ്കിൽ)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# ഒരേസമയം കൈകാര്യം ചെയ്യുന്ന അഭ്യർത്ഥനകളുടെ എണ്ണം കുറയ്ക്കുക (ഒരു env var വഴിയല്ല, ഡാഷ്ബോർഡിലെ Settings പേജ് വഴി സജ്ജീകരിക്കുക)
# `MAX_CONCURRENT_REQUESTS` env var ഇല്ല — Settings → Concurrency എന്നതിൽ ഇത് കോൺഫിഗർ ചെയ്യുക.
```
