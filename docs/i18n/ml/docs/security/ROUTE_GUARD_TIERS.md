## അവലോകനം

എല്ലാ OmniRoute മാനേജ്മെന്റ് API റൂട്ടുകളും മൂന്ന് സംരക്ഷണ
തലങ്ങളിൽ ഒന്നായി വർഗ്ഗീകരിച്ചിരിക്കുന്നു. ഈ വർഗ്ഗീകരണം സ്ഥിരമാണ്,
`src/server/authz/routeGuard.ts`-ൽ നിർവചിച്ചിരിക്കുന്നു, കൂടാതെ മറ്റേതെങ്കിലും ഓത്ത് ശാഖ
പ്രവർത്തിക്കുന്നതിന് മുമ്പ് വിലയിരുത്തപ്പെടുന്നു.

## നിരകൾ

### ടയർ 1 — LOCAL_ONLY

**നടപ്പിലാക്കിയത്:** `isLocalOnlyPath(path)` → ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന** ബൈപാസ്:** സ്ഥിരസ്ഥിതിയായി ഒന്നുമില്ല. അഭ്യർത്ഥന `manage` സ്കോപ്പുള്ള ഒരു സാധുവായ API കീ വഹിക്കുമ്പോൾ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ലെ പാതകൾക്കായി ഇടുങ്ങിയ കാർവ്-ഔട്ട് (കാണുക [-സ്കോപ്പ് കാർവ്-ഔട്ട് നിയന്ത്രിക്കുക](#manage-scope-carve-out) ).

ഈ റൂട്ടുകൾ ചൈൽഡ് പ്രോസസുകളെ സൃഷ്ടിക്കുന്നു അല്ലെങ്കിൽ റൺടൈം കോഡ് നടപ്പിലാക്കുന്നു. നോൺ-ലൂപ്പ്ബാക്ക് ട്രാഫിക്കിലേക്ക് അവരെ തുറന്നുകാട്ടുന്നത്, ഒരു സാധുവായ JWT (ഉദാഹരണത്തിന്, ഒരു Cloudflared/Ngrok ടണൽ വഴി) നേടിയ ഒരു ആക്രമണകാരിയെ, അറിയപ്പെടുന്ന CVE ക്ലാസ് ( [GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj) ) — ട്രിഗർ ചെയ്യാൻ അനുവദിക്കും.

**എന്താണ് GHSA-fhh6-4qxv-rpqj (ആക്രമണ ക്ലാസ്):** ഒരു management/agent സെർവർ ഒരു ഉപപ്രോസസ് (`npm install`, `node`, ഒരു ബ്രൗസർ, ഒരു പ്രോക്സി, `git`, `tar`, ...) സമാരംഭിക്കുന്ന ഒരു എൻഡ് പോയിൻ്റ് തുറന്നുകാട്ടുന്നു. ഒരു nginx/Cloudflare/Tailscale ടണലിന് പിന്നിൽ ഓപ്പറേറ്റർ OmniRoute ഇടുകയും ഒരു JWT ചോർന്നൊലിക്കുകയോ ഓത്ത് തെറ്റായി കോൺഫിഗർ ചെയ്തതുകൊണ്ടോ ഓഫ്-ഹോസ്റ്റ് — ൽ നിന്ന് ആ എൻഡ്പോയിൻ്റിൽ എത്തിച്ചേരാനാകുകയാണെങ്കിൽ — ആക്രമണകാരി "ഒരു API" എന്നതിനെ "ഹോസ്റ്റിൽ ഒരു കമാൻഡ് പ്രവർത്തിപ്പിക്കുക" (റിമോട്ട് കോഡ് എക്സിക്യൂഷൻ) ആക്കി മാറ്റുന്നു. OmniRoute ഇത് ക്ലോസ് ചെയ്യുന്നു** ഏതെങ്കിലും ഓത്ത് പരിശോധനയ്ക്ക് മുമ്പ്, ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് നിരുപാധികമായി പരിശോധിക്കുക** , മുട്ടയിടാൻ കഴിയുന്ന എല്ലാ റൂട്ടുകളിലും: ഒരു തുരങ്കത്തിന് മുകളിലൂടെ ചോർന്ന ടോക്കണിന് ഇപ്പോഴും സ്പോണിൽ എത്താൻ കഴിയില്ല.

**മുഴുവൻ LOCAL_ONLY സെറ്റ്.** `src/server/authz/routeGuard.ts` ൽ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ആണ് ആധികാരിക ഉറവിടം; ചുവടെയുള്ള പട്ടിക നിലവിലെ അവസ്ഥയെ പ്രതിഫലിപ്പിക്കുന്നു. `check-route-guard-membership` ഗേറ്റ് ഓരോ `route.ts` സ്പോൺ ശേഷിയുള്ള പ്രിഫിക്സുകൾക്ക് കീഴെ കണക്കാക്കുകയും പ്രാദേശികമായി മാത്രം തരംതിരിച്ചിട്ടില്ലെങ്കിൽ CI പരാജയപ്പെടുകയും ചെയ്യുന്നു.

#### മാനേജ്-സ്കോപ്പ് കാർവ്-ഔട്ട്

അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പ് (അല്ലെങ്കിൽ `admin`) ഉൾപ്പെടുന്ന ഒരു `Authorization: Bearer <api-key>` ഉണ്ടെങ്കിൽ മാത്രമേ LOCAL_ONLY പാതകളുടെ MAY ൻ്റെ ഒരു ഉപവിഭാഗം നോൺ-ലൂപ്പ്ബാക്കിൽ നിന്നും ആക്സസ് ചെയ്യാൻ കഴിയൂ. കാർവ്-ഔട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` വഴി ഓരോ പാതയിലും വ്യക്തമായി ഗേറ്റ് ചെയ്തിരിക്കുന്നു, അതിനാൽ ഏതെങ്കിലും പുതിയ LOCAL_ONLY പാതയുടെ സ്ഥിരസ്ഥിതി കർശനമായ ലൂപ്പ്ബാക്ക് ആയി തുടരും. ആധികാരികതയില്ലാത്ത അഭ്യർത്ഥനകളും നോൺ-മാനേജ് കീകളുള്ള അഭ്യർത്ഥനകളും ഇപ്പോഴും `403 LOCAL_ONLY` ഉപയോഗിച്ച് നിരസിച്ചിരിക്കുന്നു.

ഇന്ന് മറികടക്കാവുന്ന ഒരേയൊരു ഉപസർഗ്ഗം `/api/mcp/` ആണ്. `/api/cli-tools/runtime/`, `/api/services/` എന്നിവ മനപ്പൂർവ്വം ഒഴിവാക്കിയിരിക്കുന്നു, കാരണം അവയ്ക്ക് അനിയന്ത്രിതമായ ഉപപ്രോസസുകൾ (`npm install`, `node`) സൃഷ്ടിക്കാൻ കഴിയും, ഇത് തടയാൻ LOCAL_ONLY ടയർ നിലനിൽക്കുന്ന കൃത്യമായ CVE ക്ലാസ് ആണ്.

**#7895 — `mcp:connect` ഇടുങ്ങിയ വ്യാപ്തി:** ഇടുങ്ങിയ `mcp:connect` സ്കോപ്പ് (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`) കൈവശമുള്ള ഒരു ബെയറർ കീ `/api/mcp/` കാർവ്-ഔട്ട് ALSO സ്വീകരിക്കുന്നു, `src/server/authz/policies/management.ts` ൽ `hasMcpConnectOrManageScope()` വഴി പരിശോധിച്ചു. ഇത് `/api/mcp/` ONLY — `mcp:connect` മറ്റേതെങ്കിലും മാനേജ്മെൻ്റ് റൂട്ടിൽ ഒന്നും നൽകുന്നില്ല (മറ്റെല്ലാ LOCAL_ONLY ബൈപാസ് പ്രിഫിക്സും ഉൾപ്പെടെ, ഒരെണ്ണം എപ്പോഴെങ്കിലും ചേർക്കണം), കൂടാതെ ഇത് `MANAGEMENT_API_KEY_SCOPES` ൽ നിന്ന് മനഃപൂർവ്വം ഒഴിവാക്കിയിരിക്കുന്നു. `manage`/`admin` കൈവശമുള്ള ഒരു കീ ഇപ്പോഴും മുമ്പത്തെപ്പോലെ തന്നെ കാർവ്-ഔട്ട് കടന്നുപോകുന്നു; ബ്രോഡ് മാനേജ്മെൻ്റ് ആക്സസ് ആവശ്യമില്ലാത്ത റിമോട്ട് എംസിപി-മാത്രം കോളർമാർക്കുള്ള ലോവർ പ്രിവിലേജ് ബദലാണ് `mcp:connect`.

#### ഓപ്പറേറ്റർ മാർഗ്ഗനിർദ്ദേശവും ഓഡിറ്റിംഗും

നിങ്ങൾ ഒരു റിവേഴ്സ് പ്രോക്സി അല്ലെങ്കിൽ ടണലിന് (nginx, Caddy, Cloudflare ടണൽ, Tailscale, Ngrok) പിന്നിൽ OmniRoute പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, ലൂപ്പ്ബാക്ക് പരിശോധന ഇപ്പോഴും — മുകളിലുള്ള സ്പോൺ-കഴിവുള്ള റൂട്ടുകളെ സംരക്ഷിക്കുന്നു, അതിൻ്റെ ക്ലയൻ്റ് വിലാസം നോൺ-ലൂപ്പ്ബാക്ക് ആയതിനാൽ `403 LOCAL_ONLY` ഉപയോഗിച്ച് നിരസിക്കപ്പെടും.** auth ഓടുന്നതിന് മുമ്പ്** , അതിനാൽ ചോർന്ന JWT ഒരു സ്പോണിൽ എത്താൻ കഴിയില്ല. രണ്ട് ഓപ്പറേറ്റർ ഉത്തരവാദിത്തങ്ങൾ അവശേഷിക്കുന്നു:

- **ക്ലയൻ്റ് IP ലൂപ്പ്ബാക്ക് ആയി കെട്ടിച്ചമച്ച് 403 "പരിഹരിക്കുക" ചെയ്യരുത്.** `X-Forwarded-For: 127.0.0.1` ക്രമീകരണം അല്ലെങ്കിൽ ഉറവിട വിലാസം ലൂപ്പ്ബാക്കിലേക്ക് മാറ്റിയെഴുതുന്ന ഒരു പ്രോക്സി, ഈ ടയർ അടയ്ക്കുന്ന RCE ക്ലാസ് കൃത്യമായി വീണ്ടും തുറക്കുന്നു. പ്രോക്സി — മുഖേന dashboard/API തുറന്നുകാട്ടുക.
- **മാനേജ്-സ്കോപ്പ് ബൈപാസ് ഏറ്റവും കുറവായി നിലനിർത്തുക.** `/api/mcp/` മാത്രമേ മറികടക്കാൻ കഴിയൂ, ഒരു `manage` -scoped API കീ ഉപയോഗിച്ച് മാത്രം. `SPAWN_CAPABLE_PREFIXES` ബൈപാസ് പട്ടികയിൽ ഒരിക്കലും ചേർക്കാൻ കഴിയില്ല — zod സ്കീമ അവരെ നിരസിക്കുകയും `isLocalOnlyBypassableByManageScope` റൺടൈമിൽ (പ്രതിരോധം-ആഴം) നിരസിക്കുകയും ചെയ്യുന്നു, ഇതാണ് ഡാഷ്ബോർഡ് അർത്ഥമാക്കുന്നത് "ബൈപാസ് ചെയ്യാൻ കഴിയില്ല". — `/api/oauth/kiro/auto-import` (ഹോസ്റ്റ്-ലോക്കൽ Kiro ക്രെഡൻഷ്യൽ ഫയലുകൾ വായിക്കുന്നു), `/api/discovery/`, `/api/issue-agent/` എന്നിവയ്ക്ക് വിദൂരമായി എത്തിച്ചേരാനാകാത്ത ചില LOCAL_ONLY റൂട്ടുകളും ഇതേ നിരാകരണ പട്ടികയിൽ ഉണ്ട്. റൺടൈം സ്നാപ്പ്ഷോട്ട് ലോഡറും ഒരു സംഭരിച്ച ക്രമീകരണ വരിയിൽ നിന്ന് അത്തരം എൻട്രികൾ ഉപേക്ഷിക്കുന്നു, കൂടാതെ ലെഗസി JSON ഇറക്കുമതി (`/api/settings/import-json`) ഒരിക്കലും ബൈപാസ് കീകൾ എഴുതുന്നില്ല. എല്ലാ `LOCAL_ONLY_API_PREFIXES` എൻട്രിയും നിരസിക്കൽ ലിസ്റ്റിലായിരിക്കണം അല്ലെങ്കിൽ ബൈപാസ് യോഗ്യതയുള്ളതായി അവലോകനം ചെയ്യണം (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/` (ഉദാ: `/login`, `/refresh-cursor`) കീഴിലുള്ള ഡൈനാമിക്-സെഗ്മെൻ്റും സ്റ്റാറ്റിക്-പാത്ത് സ്പോൺ ശേഷിയുള്ള റൂട്ടുകളും `src/shared/constants/spawnCapablePrefixes.ts` ലെ റീജക്സ് അധിഷ്ഠിത `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` കമ്പാനിയൻ മുഖേനയാണ് കവർ ചെയ്യുന്നത്, ഫ്ലാറ്റ് `SPAWN_CAPABLE_PREFIXES` അറേ — മുഖേനയല്ല, ഫ്ലാറ്റ് അറേ `/api/providers/` റൂട്ട് മുഴുവനായും തിരിച്ചുപിടിക്കണം ദാഷ്ബോർഡുകൾ ദാതാവ് CRUD നിയമപരമായി ഉപയോഗിക്കുന്നു.

**ഓഡിറ്റിംഗ് ആക്സസ്** ഓഫ്-ഹോസ്റ്റ് ഒന്നും ഈ റൂട്ടുകളിൽ എത്തുന്നില്ലെന്ന് പരിശോധിക്കാൻ — :

- തുറക്കുക** ഓതറൈസേഷൻ ഇൻവെൻ്ററി** `/dashboard/settings/security` ൽ : ഇത് ലൈവ് LOCAL_ONLY പ്രിഫിക്സ് ലിസ്റ്റ് റെൻഡർ ചെയ്യുന്നു, പ്രിഫിക്സുകൾ ബൈപാസ് ചെയ്യാവുന്നവയാണ്, കൂടാതെ കംപൈൽ-ടൈം സ്പോൺ-കാപ്പബിൾ ("ബൈപാസ് ചെയ്യാൻ കഴിയില്ല") സെറ്റ്.
- നോൺ-ലൂപ്പ്ബാക്ക് ക്ലയൻ്റ് വിലാസവുമായി ജോടിയാക്കിയ മുകളിലുള്ള പ്രിഫിക്സുകൾക്കായി നിങ്ങളുടെ റിവേഴ്സ്-പ്രോക്സി / ആക്സസ് ലോഗുകൾ ഗ്രെപ്പ് ചെയ്യുക. `403 LOCAL_ONLY` ന് പകരം `200` തിരിച്ചുനൽകിയ അത്തരം ഏതെങ്കിലും ഹിറ്റ് അർത്ഥമാക്കുന്നത് പ്രോക്സി യഥാർത്ഥ ക്ലയൻ്റ് IP — പ്രോക്സിയെ മറയ്ക്കുന്നു എന്നാണ്.
- ഈ പാതകളിലൊന്നിൻ്റെ OmniRoute യുടെ ലോഗുകളിലെ ഒരു `403 LOCAL_ONLY`, ഉദ്ദേശിച്ച രീതിയിൽ പ്രവർത്തിക്കുന്ന ഗാർഡ് ആണ്, അടിച്ചമർത്താനുള്ള ഒരു പിശകല്ല.

മുകളിലുള്ള ടയർ _some_ ക്രെഡൻഷ്യൽ ആവശ്യമാണോ എന്ന് മാത്രം തീരുമാനിക്കുന്നു. സംഭരിച്ച ക്രെഡൻഷ്യലുകൾ ഡൗൺലോഡ് ചെയ്യുന്ന റൂട്ടുകൾ ഹാൻഡ്ലറിൽ രണ്ടാമത്തെ പരിശോധന ചേർക്കുന്നു: `GET /api/settings/export-json` (ഡീക്രിപ്റ്റ് ചെയ്ത പ്രൊവൈഡർ കണക്ഷനുകളും റോ API കീകളും), `GET /api/db-backups/export` ( SQLite ഫയൽ), `GET /api/db-backups/exportAll` (പൂർണ്ണ ആർക്കൈവ്) കോൾ `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). ഇത് ഒരു ഡാഷ്ബോർഡ് സെഷൻ, ലോക്കൽ CLI വിഷയം അല്ലെങ്കിൽ ലോഗിൻ പ്രവർത്തനരഹിതമാക്കിയ ഒരു ഉദാഹരണം സ്വീകരിക്കുന്നു, കൂടാതെ ഏത് സ്കോപ്പിൻ്റെയും ( `manage`, `admin` ഉൾപ്പെടെ) API കീകളിലേക്കും `oma_` ആക്സസ് ടോക്കണുകളിലേക്കും `403` ഉത്തരം നൽകുന്നു. വിനാശകരമായ എതിരാളികൾ ഒരേ അതിരുകൾ സൂക്ഷിക്കുന്നു: `POST /api/db-backups/import` (അപ്ലോഡ് ചെയ്ത `.sqlite`, `dryRun=true` ഉൾപ്പെടുത്തിയിട്ടുണ്ട്), `POST /api/db-backups` (ഐഡി ഉപയോഗിച്ച് സംഭരിച്ച ബാക്കപ്പ് പുനഃസ്ഥാപിക്കുക), `POST /api/settings/import-json` (ലെഗസി JSON പുനഃസ്ഥാപിക്കുക) തത്സമയ ഡാറ്റാബേസിനോ മുഴുവൻ settings/connections/API-key സെറ്റിനോ പകരം വയ്ക്കുന്നു, അതിനാൽ ഒരു മെഷീൻ ക്രെഡൻഷ്യലിനും അവയെ പ്രവർത്തനക്ഷമമാക്കാൻ കഴിയില്ല. പുനഃസ്ഥാപിക്കൽ പോയിൻ്റുകൾ നശിപ്പിക്കുന്നത് ഒരേ അതിർത്തിയാണ്: `DELETE /api/db-backups` (ക്ലീനപ്പ് — ഏറ്റവും പുതിയ N / ഡ്രോപ്പ് D ദിവസത്തേക്കാൾ പഴയതായി നിലനിർത്തുക), `PATCH /api/db-backups` (നിലനിർത്തൽ ക്രമീകരണങ്ങൾ), കാരണം സ്ഥിരമായ നിലനിർത്തൽ `cleanupDbBackups()` എല്ലാ ഓട്ടോമാറ്റിക് ബാക്കപ്പിനും (`src/lib/db/backup.ts`) ബാധകമാണ്, അതിനാൽ `keepLatest: 1` എല്ലാം സംരക്ഷിക്കാൻ കഴിയുന്ന ഒരു മെഷീൻ ക്രെഡൻഷ്യൽ. ബാക്കപ്പുകൾ ലിസ്റ്റുചെയ്യുന്നതും സൃഷ്ടിക്കുന്നതും (`GET`/`PUT /api/db-backups`) സാധാരണ മാനേജ്മെൻ്റ് ഓത്ത് നിലനിർത്തുന്നു. സമന്വയ ടോക്കൺ ഇഷ്യുവിന് (`POST /api/sync/tokens`) അതേ സഹായിയും കൂടാതെ വിശ്വസനീയമായ ലൂപ്പ്ബാക്ക് ഇൻ്റേണൽ-സർവീസ് ടോക്കണും ഉപയോഗിക്കുന്നു.

### ഫ്രഷ്-ഇൻസ്റ്റാൾ ബൂട്ട്സ്ട്രാപ്പ് യഥാർത്ഥ പിയർ മുഖേനയുള്ള ലൂപ്പ്ബാക്ക്-മാത്രം — ആണ്, `Host` അല്ല

മാനേജ്മെൻ്റ് പാസ്വേഡ് കോൺഫിഗർ ചെയ്തിട്ടില്ലാത്തതിനാൽ ( `INITIAL_PASSWORD` ഇല്ല), `src/shared/utils/apiAuth.ts` ലെ `isAuthRequired()` അജ്ഞാത ബൂട്ട്സ്ട്രാപ്പ് തുറന്ന് സൂക്ഷിക്കുന്നു.** ലൂപ്പ്ബാക്ക് സമപ്രായക്കാർക്ക് മാത്രം** . വിശ്വസനീയ പിയർ സിഗ്നലുകളിൽ നിന്ന് ലൂപ്പ്ബാക്ക് തീരുമാനിക്കുന്നത്, ക്രമത്തിൽ: ടോക്കൺ-സ്റ്റാമ്പ് ചെയ്ത യഥാർത്ഥ TCP പിയർ (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, നയം എന്താണ് കാണുന്നത്), പൈപ്പ്ലൈനിൻ്റെ സ്വന്തം `AUTHZ_HEADER_PEER_LOCALITY` വിധി (ഏത് റൂട്ട് ഹാൻഡ്ലർമാർ കാണുന്നു, `OMNIROUTE_PEER_STAMP_TOKEN` സജ്ജീകരിക്കുമ്പോൾ മാത്രം വിശ്വസിക്കുന്നു), അല്ലെങ്കിൽ നേരിട്ട് വിളിക്കുന്നവർക്കായി ഒരു യഥാർത്ഥ സോക്കറ്റ് പിയർ. `Host` / `nextUrl.hostname` ഒരിക്കലും കൺസൾട്ട് ചെയ്യപ്പെടുന്നില്ല, കൂടാതെ ആദ്യ പാസ്വേഡ് റൈറ്റ് (`POST /api/settings/require-login`) എല്ലാ നെറ്റ്വർക്ക് പിയർക്കും (GHSA-7pq4-8pvv-rx7r) തുറക്കുന്നതിനുപകരം ഒരേ നിയന്ത്രണത്തിലാണ്. `managementPolicy` അതിൻ്റെ സ്വന്തം `peerContext` വിധിന്യായം വ്യക്തമായി പാസാക്കുന്നു, അതിനാൽ ORIGINAL (പ്രീ-സ്ട്രിപ്പ്) അഭ്യർത്ഥനയുടെ തലക്കെട്ടുകൾ ഒരിക്കലും അത് തീരുമാനിക്കില്ല.

### ടയർ 3 — MANAGEMENT (സ്ഥിരസ്ഥിതി)

മറ്റെല്ലാ മാനേജ്മെൻ്റ് റൂട്ടുകളും. `requireLogin=false` കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിൽ ഓത്ത് ആവശ്യമാണ്. CLI ടോക്കണുകൾക്ക് ഈ റൂട്ടുകൾ ആധികാരികമാക്കാൻ കഴിയും (ലൂപ്പ്ബാക്ക് + സാധുവായ HMAC).

## മൂല്യനിർണ്ണയ ക്രമം

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ലൂപ്പ്ബാക്ക്                                  → അടുത്ത ഘട്ടത്തിലേക്ക്
     → ലൂപ്പ്ബാക്ക് അല്ലാത്തത്, manage-scope Bearer
        കൂടാതെ isLocalOnlyBypassableByManageScope   → അനുവദിക്കുക (management_key)
     → അല്ലെങ്കിൽ                                   → നിരസിക്കുക 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → അനുവദിക്കുക (system)
  3. hasValidCliToken(headers)?
     → അനുവദിക്കുക (cli) [ലൂപ്പ്ബാക്ക് + timingSafeEqual HMAC പരിശോധന]
  4. isAlwaysProtectedPath(path) അല്ലെങ്കിൽ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → അനുവദിക്കുക (dashboard_session)
     → മറികടക്കാനാകാത്ത പാതയിൽ manage-scope Bearer ഉണ്ടോ?
        → അനുവദിക്കുക (management_key)
     → നിരസിക്കുക 401/403
  5. requireLogin=false?
     → അനുവദിക്കുക (anonymous)
```

ഘട്ടം 1-ലെ manage-scope ശാഖ മാത്രമാണ് ഒരു LOCAL_ONLY റൂട്ടിന്റെ ആവശ്യകത നിറവേറ്റാൻ കഴിയുന്ന പ്രാമാണീകരിച്ച പാത; കാലഹരണപ്പെട്ട DB നിശ്ശബ്ദമായി "നിരസിക്കുക" എന്നതിലേക്ക് തരംതാഴാതിരിക്കാൻ auth-backend പരാജയ മോഡ് 403-ന് പകരം 503 നൽകുന്നു.

## പ്രോസസുകൾ സൃഷ്ടിക്കാൻ കഴിയുന്ന പുതിയ റൂട്ട് ചേർക്കൽ

1. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_API_PREFIXES`-ലേക്ക് പാതാ പ്രിഫിക്സ് ചേർക്കുക
2. പുതിയ പ്രിഫിക്സിന് `isLocalOnlyPath()` true നൽകുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഒരു ടെസ്റ്റ് `tests/unit/authz/routeGuard.test.ts`-ൽ ചേർക്കുക
3. **ഈ ഘട്ടം ഒരിക്കലും ഒഴിവാക്കരുത്** — `CLAUDE.md`-ലെ കർശന നിയമം #15 കാണുക
4. തീരുമാനിക്കുക: ഈ റൂട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലും ഉൾപ്പെടണമോ?
   സ്വതവേയുള്ള ഉത്തരം **ഇല്ല** എന്നാണ്. manage-scope ഉടമയ്ക്ക് തുറന്നുകൊടുക്കാൻ റൂട്ട് സുരക്ഷിതമാണെങ്കിൽ മാത്രം ഇത് തിരഞ്ഞെടുക്കുക (അതായത്, ഉപയോക്താവ് നിയന്ത്രിക്കുന്ന ഏതെങ്കിലും കോഡ് അത് പ്രോസസായി സൃഷ്ടിക്കരുത്).

## manage-scope വഴി മറികടക്കാവുന്ന പാത ചേർക്കൽ

1. ഉപയോക്താവ് നൽകുന്ന കോഡോ കമാൻഡുകളോ റൂട്ട് പ്രവർത്തിപ്പിക്കുന്നില്ലെന്ന് സ്ഥിരീകരിക്കുക. പ്രവർത്തിപ്പിക്കുന്നുണ്ടെങ്കിൽ നിർത്തുക — ഈ പ്രത്യേക ഇളവ് അതിന് അനുയോജ്യമായ ഉപകരണമല്ല.
2. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലേക്ക് പ്രിഫിക്സ് ചേർക്കുക
3. നാല് അഭ്യർത്ഥനാ രൂപങ്ങൾക്കും `tests/unit/authz/management-policy.test.ts`-ൽ കവറേജ് ചേർക്കുക: Bearer ഇല്ല (403), manage Bearer (അനുവദിക്കുക), non-manage Bearer (403), കൂടാതെ manage Bearer ഉണ്ടായാലും `/api/cli-tools/runtime/*` കർശനമായ ലൂപ്പ്ബാക്ക് മാത്രമായി തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഓരോ പ്രിഫിക്സിനുമായുള്ള റിഗ്രഷൻ.

## OpenAPI-യിൽ സുരക്ഷാ ടയറുകൾ രേഖപ്പെടുത്തൽ

`docs/openapi.yaml`-ലേക്ക് പുതിയ റൂട്ട് ചേർക്കുമ്പോൾ, റൂട്ട് `routeGuard.ts` പ്രകാരം വർഗ്ഗീകരിച്ചിട്ടുണ്ടെങ്കിൽ അനുബന്ധ vendor extension പ്രയോഗിക്കുക:

| routeGuard.ts വർഗ്ഗീകരണം        | YAML അനോട്ടേഷൻ             | നിർബന്ധിത നിയന്ത്രണം                                      |
| ------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`       | `x-loopback-only: true`    | ലൂപ്പ്ബാക്ക് അല്ലാത്തവയിൽ നിന്ന് നിരുപാധികമായി തടയുന്നു   |
| `ALWAYS_PROTECTED_API_PATHS`    | `x-always-protected: true` | `requireLogin=false` ആണെങ്കിലും പ്രാമാണീകരണം ആവശ്യമാണ്    |
| ആന്തരിക admin/debug റൂട്ട്      | `x-internal: true`         | സ്വതവേ /dashboard/api-endpoints-ൽ നിന്ന് മറച്ചിരിക്കുന്നു |
| ഒന്നുമില്ല (പൊതു / സാധാരണ auth) | (അനോട്ടേഷൻ ആവശ്യമില്ല)     | സാധാരണ `requireLogin` നിയന്ത്രിത ആക്സസ്                   |

### സാധൂകരണം

YAML അനോട്ടേഷനുകളും `routeGuard.ts`-ഉം തമ്മിലുള്ള സ്ഥിരത രണ്ട് സ്ക്രിപ്റ്റുകൾ നിർബന്ധമാക്കുന്നു:

- `scripts/check/check-openapi-coverage.mjs` — കവറേജ് < 99% ആണെങ്കിൽ പരാജയപ്പെടുന്നു
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` അല്ലെങ്കിൽ
  `x-always-protected` അനോട്ടേഷനുകൾ കംപൈൽ സമയ സ്ഥിരാങ്കങ്ങളിൽ നിന്ന് വ്യതിചലിച്ചാൽ പരാജയപ്പെടുന്നു

രണ്ട് സ്ക്രിപ്റ്റുകളും pre-commit hook-ലും CI-ലും പ്രവർത്തിക്കുന്നു.

### തെറ്റായ പോസിറ്റീവ് നിയമം

`routeGuard.ts` സ്ഥിരാങ്കത്തിൽ ഉൾപ്പെടാത്ത ഒരു റൂട്ടിൽ `x-always-protected` അല്ലെങ്കിൽ `x-loopback-only` അനോട്ടേറ്റ് ചെയ്താൽ, കവറേജ് സ്ക്രിപ്റ്റ് പരാജയപ്പെടുന്നു. `routeGuard.ts` യഥാർത്ഥത്തിൽ നിർബന്ധമാക്കുന്ന കാര്യവുമായി YAML-നെ പൊരുത്തപ്പെടുത്തുക എന്നതാണ് എല്ലായ്പ്പോഴും പരിഹാരം — നിർബന്ധിത നിയന്ത്രണ ലോജിക് നടപ്പാക്കാതെ `routeGuard.ts`-ലേക്ക് റൂട്ടുകൾ ചേർക്കുകയല്ല.
