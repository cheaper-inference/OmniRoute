## അവലോകനം

എല്ലാ OmniRoute മാനേജ്മെന്റ് API റൂട്ടുകളും മൂന്ന് സംരക്ഷണ
തലങ്ങളിൽ ഒന്നായി വർഗ്ഗീകരിച്ചിരിക്കുന്നു. ഈ വർഗ്ഗീകരണം സ്ഥിരമാണ്,
`src/server/authz/routeGuard.ts`-ൽ നിർവചിച്ചിരിക്കുന്നു, കൂടാതെ മറ്റേതെങ്കിലും ഓത്ത് ശാഖ
പ്രവർത്തിക്കുന്നതിന് മുമ്പ് വിലയിരുത്തപ്പെടുന്നു.

## ടിയറുകൾ

### ടിയർ 1 — LOCAL_ONLY

**നടപ്പിലാക്കുന്നത്:** `isLocalOnlyPath(path)` → ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന  
**ബൈപാസ്:** ഡിഫോൾട്ടായി ഒന്നുമില്ല. അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പുള്ള സാധുവായ API കീ ഉണ്ടായിരിക്കുമ്പോൾ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലുള്ള പാതകൾക്ക് മാത്രമായി പരിമിതപ്പെടുത്തിയ ഇളവ് (കാണുക [Manage-scope carve-out](#manage-scope-carve-out)).

ഈ റൂട്ടുകൾ ചൈൽഡ് പ്രോസസ്സുകൾ ആരംഭിക്കുകയോ റൺടൈം കോഡ് എക്സിക്യൂട്ട് ചെയ്യുകയോ ചെയ്യുന്നു. ഇവയെ ലൂപ്പ്ബാക്ക് അല്ലാത്ത ട്രാഫിക്കിന് ലഭ്യമാക്കുന്നത്, സാധുവായ JWT സ്വന്തമാക്കിയ ഒരു ആക്രമണകാരിക്ക് (ഉദാ., Cloudflared/Ngrok ടണൽ വഴി) പ്രോസസ്സുകൾ ആരംഭിക്കാൻ അവസരം നൽകും — ഇത് അറിയപ്പെടുന്ന ഒരു CVE വിഭാഗമാണ് ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj എന്താണ് (ആക്രമണ വിഭാഗം):** ഒരു മാനേജ്മെന്റ്/ഏജന്റ് സെർവർ ഒരു സബ്പ്രോസസ്സ് (`npm install`, `node`, ഒരു ബ്രൗസർ, ഒരു പ്രോക്സി, `git`, `tar`, …) ആരംഭിക്കുന്ന ഒരു എൻഡ്പോയിന്റ് ലഭ്യമാക്കുന്നു. ആ എൻഡ്പോയിന്റ് ഹോസ്റ്റിന് പുറത്തുനിന്ന് എത്തിച്ചേരാനാകുന്നതാണെങ്കിൽ — ഓപ്പറേറ്റർ OmniRoute-നെ nginx/Cloudflare/Tailscale ടണലിന് പിന്നിൽ സ്ഥാപിക്കുകയും ഒരു JWT ചോർന്നുപോകുകയും ചെയ്തതിനാലോ, ഓത്ത് തെറ്റായി കോൺഫിഗർ ചെയ്തതിനാലോ — ആക്രമണകാരിക്ക് "ഒരു API വിളിക്കുക" എന്നതിനെ "ഹോസ്റ്റിൽ ഒരു കമാൻഡ് പ്രവർത്തിപ്പിക്കുക" എന്നതാക്കി മാറ്റാൻ കഴിയും (റിമോട്ട് കോഡ് എക്സിക്യൂഷൻ). പ്രോസസ്സുകൾ ആരംഭിക്കാൻ കഴിയുന്ന ഓരോ റൂട്ടിലും **ഏതൊരു ഓത്ത് പരിശോധനയ്ക്കും മുമ്പ്, ഉപാധികളില്ലാതെ ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന** നിർബന്ധമാക്കിക്കൊണ്ട് OmniRoute ഇത് തടയുന്നു: ഒരു ടണലിലൂടെ ചോർന്ന ടോക്കണിന് അപ്പോഴും പ്രോസസ്സ് ആരംഭിക്കുന്ന റൂട്ടിൽ എത്തിച്ചേരാനാകില്ല.

**പൂർണ്ണമായ LOCAL_ONLY സെറ്റ്.** ആധികാരിക ഉറവിടം `src/server/authz/routeGuard.ts`-ലുള്ള `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ആണ്; താഴെയുള്ള പട്ടിക നിലവിലെ അവസ്ഥയെ പ്രതിഫലിപ്പിക്കുന്നു. `check-route-guard-membership` ഗേറ്റ്, പ്രോസസ്സുകൾ ആരംഭിക്കാൻ കഴിയുന്ന പ്രിഫിക്സുകൾക്ക് കീഴിലുള്ള ഓരോ `route.ts`-ഉം എണ്ണിപ്പട്ടികപ്പെടുത്തുകയും അവയിൽ ഏതെങ്കിലും local-only ആയി വർഗ്ഗീകരിച്ചിട്ടില്ലെങ്കിൽ CI പരാജയപ്പെടുത്തുകയും ചെയ്യുന്നു.

#### മാനേജ്-സ്കോപ്പ് ഇളവ്

LOCAL_ONLY പാതകളുടെ ഒരു ഉപവിഭാഗം നോൺ-ലൂപ്പ്ബാക്കിൽ നിന്നും ആക്സസ് ചെയ്യാൻ കഴിയുക
അഭ്യർത്ഥനയിൽ `Authorization: Bearer <api-key>` ഉണ്ടായിരിക്കുകയും അതിന്റെ
മെറ്റാഡാറ്റയിൽ `manage` സ്കോപ്പ് (അല്ലെങ്കിൽ `admin`) ഉൾപ്പെട്ടിരിക്കുകയും ചെയ്താൽ മാത്രമാണ്.
ഈ ഇളവ് ഓരോ പാതയ്ക്കും `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` വഴി വ്യക്തമായി
ഗേറ്റ് ചെയ്തിരിക്കുന്നു; അതിനാൽ ഏതൊരു പുതിയ LOCAL_ONLY പാതയ്ക്കുമുള്ള ഡിഫോൾട്ട്
കർശന-ലൂപ്പ്ബാക്കായി തുടരും. ഓതന്റിക്കേഷൻ ഇല്ലാത്ത അഭ്യർത്ഥനകളും മാനേജ് ഇതര കീകളുള്ള
അഭ്യർത്ഥനകളും ഇപ്പോഴും `403 LOCAL_ONLY` നൽകി നിരസിക്കപ്പെടും.

നിലവിൽ ബൈപാസ് ചെയ്യാവുന്ന ഏക പ്രിഫിക്സ് `/api/mcp/` ആണ്. `/api/cli-tools/runtime/`-ഉം
`/api/services/`-ഉം മനഃപൂർവം ഒഴിവാക്കിയിരിക്കുന്നു, കാരണം അവയ്ക്ക് ഇഷ്ടാനുസൃത
സബ്പ്രോസസുകൾ (`npm install`, `node`) സ്പോൺ ചെയ്യാൻ കഴിയും; കൃത്യമായും ഈ CVE
വിഭാഗം തടയാനാണ് LOCAL_ONLY ടിയർ നിലവിലുള്ളത്.

#### ഓപ്പറേറ്റർ മാർഗ്ഗനിർദ്ദേശവും ഓഡിറ്റിംഗും

നിങ്ങൾ OmniRoute ഒരു റിവേഴ്സ് പ്രോക്സിയുടെയോ ടണലിന്റെയോ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) പിന്നിലാണ് പ്രവർത്തിപ്പിക്കുന്നതെങ്കിലും, മുകളിലെ സ്പോൺ-ശേഷിയുള്ള
റൂട്ടുകളെ ലൂപ്പ്ബാക്ക് പരിശോധന തുടർന്നും സംരക്ഷിക്കുന്നു — ക്ലയന്റ് വിലാസം നോൺ-ലൂപ്പ്ബാക്ക്
ആയ ഒരു അഭ്യർത്ഥന **ഓതന്റിക്കേഷൻ പ്രവർത്തിക്കുന്നതിന് മുമ്പ്** `403 LOCAL_ONLY` നൽകി
നിരസിക്കപ്പെടുന്നു; അതിനാൽ ചോർന്ന JWT-യ്ക്ക് ഒരു സ്പോണിലേക്ക് എത്താനാവില്ല. ഓപ്പറേറ്റർമാർക്ക്
രണ്ട് ഉത്തരവാദിത്തങ്ങൾ അവശേഷിക്കുന്നു:

- **ക്ലയന്റ് IP-യെ ലൂപ്പ്ബാക്കായി വ്യാജമായി സജ്ജീകരിച്ച് 403 "പരിഹരിക്കരുത്".** `X-Forwarded-For: 127.0.0.1` സജ്ജീകരിക്കുന്നതോ ഉറവിട വിലാസം ലൂപ്പ്ബാക്കായി മാറ്റിയെഴുതുന്ന ഒരു പ്രോക്സിയോ ഈ ടയർ അടച്ചുപൂട്ടുന്ന അതേ RCE വിഭാഗം വീണ്ടും തുറക്കുന്നു. പ്രോക്സിയിലൂടെ dashboard/API ലഭ്യമാക്കുക — spawn ചെയ്യാൻ കഴിയുന്ന റൂട്ടുകൾ ഒരിക്കലും ലഭ്യമാക്കരുത്.
- **manage-scope ബൈപാസ് പരമാവധി പരിമിതമായി നിലനിർത്തുക.** `/api/mcp/` മാത്രമാണ് ബൈപാസ് ചെയ്യാനാകുക, അതും `manage`-സ്കോപ്പുള്ള API കീ ഉപയോഗിച്ച് മാത്രം. `SPAWN_CAPABLE_PREFIXES` ഒരിക്കലും ബൈപാസ് പട്ടികയിൽ ചേർക്കാനാകില്ല — zod സ്കീമ അവ നിരസിക്കുകയും runtime-ൽ `isLocalOnlyBypassableByManageScope` അവ നിഷേധിക്കുകയും ചെയ്യുന്നു (ആഴത്തിലുള്ള പ്രതിരോധം); dashboard-ലെ "ബൈപാസ് ചെയ്യാവുന്നതാക്കാൻ കഴിയില്ല" എന്നതിന്റെ അർത്ഥം ഇതാണ്. spawn ചെയ്യാത്തതെങ്കിലും ഒരിക്കലും വിദൂരമായി ലഭ്യമാകാൻ പാടില്ലാത്ത ഏതാനും LOCAL_ONLY റൂട്ടുകളും ഇതേ നിഷേധപ്പട്ടികയിൽ ഉൾപ്പെടുന്നു — `/api/oauth/kiro/auto-import` (ഹോസ്റ്റിൽ പ്രാദേശികമായ Kiro ക്രെഡൻഷ്യൽ ഫയലുകൾ വായിക്കുന്നു), `/api/discovery/`, `/api/issue-agent/`. സംഭരിച്ച settings വരിയിൽനിന്ന് runtime snapshot loader ഇത്തരം എൻട്രികൾ നീക്കം ചെയ്യുകയും legacy JSON import (`/api/settings/import-json`) ഒരിക്കലും ബൈപാസ് കീകൾ എഴുതാതിരിക്കുകയും ചെയ്യുന്നു. ഓരോ `LOCAL_ONLY_API_PREFIXES` എൻട്രിയും ഒന്നുകിൽ നിഷേധപ്പട്ടികയിൽ ഉണ്ടായിരിക്കണം, അല്ലെങ്കിൽ ബൈപാസിന് യോഗ്യമാണോയെന്ന് അവലോകനം ചെയ്തിരിക്കണം (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`-ന് കീഴിലുള്ള ഡൈനാമിക് സെഗ്മെന്റും സ്റ്റാറ്റിക് പാത്തുമുള്ള spawn-സാധ്യമായ റൂട്ടുകൾ (ഉദാ. `/login`, `/refresh-cursor`) ഉൾക്കൊള്ളുന്നത് `src/shared/constants/spawnCapablePrefixes.ts`-ലെ regex-അധിഷ്ഠിത `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` കൂട്ടാളിയാണ്, ഫ്ലാറ്റ് `SPAWN_CAPABLE_PREFIXES` അറേ അല്ല — അവ കണ്ടെത്താൻ ഫ്ലാറ്റ് അറേയിൽ മുഴുവൻ `/api/providers/` പ്രിഫിക്സും ഉൾപ്പെടുത്തേണ്ടിവരും; ഇത് വിദൂര dashboards provider CRUD-നായി നിയമാനുസൃതമായി ഉപയോഗിക്കുന്ന ഒരു റൂട്ട് ട്രീയെ ആവശ്യത്തിലധികം വ്യാപിപ്പിക്കും.

**ആക്സസ് ഓഡിറ്റ് ചെയ്യൽ** — ഹോസ്റ്റിന് പുറത്തുനിന്ന് ഒന്നും ഈ റൂട്ടുകളിൽ എത്തുന്നില്ലെന്ന് സ്ഥിരീകരിക്കാൻ:

- `/dashboard/settings/security`-ൽ **Authorization Inventory** തുറക്കുക: അത് സജീവമായ LOCAL_ONLY പ്രിഫിക്സ് പട്ടികയും ബൈപാസ് ചെയ്യാനാകുന്ന പ്രിഫിക്സുകളും compile-time spawn-സാധ്യമായ ("ബൈപാസ് ചെയ്യാവുന്നതാക്കാൻ കഴിയില്ല") സെറ്റും പ്രദർശിപ്പിക്കുന്നു.
- മുകളിലുള്ള പ്രിഫിക്സുകൾ ലൂപ്പ്ബാക്ക് അല്ലാത്ത ക്ലയന്റ് വിലാസത്തോടൊപ്പം വരുന്നുണ്ടോയെന്ന് നിങ്ങളുടെ reverse-proxy / access ലോഗുകളിൽ grep ചെയ്യുക. അത്തരത്തിലുള്ള ഏതെങ്കിലും അഭ്യർത്ഥനയ്ക്ക് `403 LOCAL_ONLY`-ന് പകരം `200` ലഭിച്ചിട്ടുണ്ടെങ്കിൽ, പ്രോക്സി യഥാർഥ ക്ലയന്റ് IP മറയ്ക്കുകയാണ് — പ്രോക്സി ശരിയാക്കുക.
- ഈ പാത്തുകളിലൊന്നിനായി OmniRoute-ന്റെ ലോഗുകളിൽ കാണുന്ന `403 LOCAL_ONLY`, guard ഉദ്ദേശിച്ചപോലെ പ്രവർത്തിക്കുന്നതിന്റെ സൂചനയാണ്; അടിച്ചമർത്തേണ്ട പിശകല്ല.

#### Call-site probe gate ഉള്ള വിദൂരമായി ലഭ്യമായ റൂട്ടുകൾ

ചില റൂട്ടുകൾ ഒരു വിദൂര dashboard-ൽനിന്ന് ലഭ്യമായി തുടരേണ്ടതുണ്ട്, എന്നാൽ പ്രാദേശിക കോളർമാർക്കായി ഹോസ്റ്റിൽ ഒരു probe (`which <binary>`, `<binary> --version`, `tailscale status --json`) പ്രവർത്തിപ്പിക്കുകയും വേണം. `GET`-നായി അവ LOCAL_ONLY അല്ല; പകരം handler `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) ഉപയോഗിച്ച് വിശ്വസനീയമായ peer verdict വായിക്കുകയും `loopback` / `lan` കോളർമാർക്കായി മാത്രം probe പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു. `remote` കോളർക്ക് spawn ചെയ്യാത്ത ഉറവിടങ്ങളിൽനിന്ന് (സ്ഥിരമായി സംഭരിച്ച state, settings, fs പരിശോധനകൾ) നിർമ്മിച്ച അതേ response shape ലഭിക്കുന്നു; അതിൽ `probed: false` എന്ന് അടയാളപ്പെടുത്തിയിരിക്കും.

| റൂട്ട്                                                             | വിദൂര കോളർമാർക്കായി ഒഴിവാക്കുന്ന probe                            |
| ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`       | CLI runtime probe (`allowLocalRuntimeProbe`), CLI-fallback spawn  |

ഹോസ്റ്റിനെ probe ചെയ്യുന്ന ഒരു പുതിയ read route ഇതേ മാതൃക പിന്തുടരുകയോ നേരിട്ട് LOCAL_ONLY ആയി വർഗ്ഗീകരിക്കപ്പെടുകയോ വേണം.

#### ക്രെഡൻഷ്യൽ exports operators-ക്ക് മാത്രം

മുകളിലുള്ള ടയർ _ഏതെങ്കിലും_ ക്രെഡൻഷ്യൽ ആവശ്യമാണോ എന്ന് മാത്രമാണ് തീരുമാനിക്കുന്നത്. സംഭരിച്ച ക്രെഡൻഷ്യലുകൾ
ഡൗൺലോഡ് ചെയ്യുന്ന റൂട്ടുകൾ ഹാൻഡ്ലറിൽ രണ്ടാമതൊരു പരിശോധന ചേർക്കുന്നു: `GET /api/settings/export-json` (ഡീക്രിപ്റ്റ് ചെയ്ത
പ്രൊവൈഡർ കണക്ഷനുകളും അസംസ്കൃത API കീകളും), `GET /api/db-backups/export` (SQLite ഫയൽ), കൂടാതെ
`GET /api/db-backups/exportAll` (പൂർണ്ണ ആർക്കൈവ്) എന്നിവ `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`) വിളിക്കുന്നു. ഇത് ഒരു ഡാഷ്ബോർഡ് സെഷൻ, ലോക്കൽ CLI സബ്ജക്റ്റ്, അല്ലെങ്കിൽ
ലോഗിൻ പ്രവർത്തനരഹിതമാക്കിയ ഒരു ഇൻസ്റ്റൻസ് എന്നിവ സ്വീകരിക്കുകയും ഏത് സ്കോപ്പിലുമുള്ള API കീകൾക്കും (`manage`,
`admin` എന്നിവ ഉൾപ്പെടെ) `oma_` ആക്സസ് ടോക്കണുകൾക്കും `403` മറുപടി നൽകുകയും ചെയ്യുന്നു. സിങ്ക് ടോക്കൺ നൽകൽ (`POST /api/sync/tokens`)
ഇതേ ഹെൽപ്പറും കൂടാതെ വിശ്വസനീയമായ ലൂപ്പ്ബാക്ക് ഇന്റേണൽ-സർവീസ് ടോക്കണും ഉപയോഗിക്കുന്നു.

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### പുതിയ ഇൻസ്റ്റാളേഷനിലെ ബൂട്ട്സ്ട്രാപ്പ് ലൂപ്പ്ബാക്കിന് മാത്രമാണ് — `Host` അടിസ്ഥാനമാക്കിയല്ല, യഥാർഥ പിയർ അടിസ്ഥാനമാക്കി

മാനേജ്മെന്റ് പാസ്വേഡ് കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിൽ (`INITIAL_PASSWORD`-ഉം ഇല്ലെങ്കിൽ),
`src/shared/utils/apiAuth.ts`-ലെ `isAuthRequired()` അജ്ഞാത ബൂട്ട്സ്ട്രാപ്പ് **ലൂപ്പ്ബാക്ക് പിയറുകൾക്ക് മാത്രം**
തുറന്നുവെക്കുന്നു. വിശ്വസനീയമായ പിയർ സിഗ്നലുകളിൽ നിന്ന് താഴെപ്പറയുന്ന ക്രമത്തിലാണ് ലൂപ്പ്ബാക്ക് തീരുമാനിക്കുന്നത്: ടോക്കൺ പതിപ്പിച്ച യഥാർഥ TCP പിയർ
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, പോളിസി കാണുന്നത്), പൈപ്പ്ലൈനിന്റെ സ്വന്തം
`AUTHZ_HEADER_PEER_LOCALITY` വിധി (റൂട്ട് ഹാൻഡ്ലറുകൾ കാണുന്നത്, `OMNIROUTE_PEER_STAMP_TOKEN`
സജ്ജീകരിച്ചിരിക്കുമ്പോൾ മാത്രം വിശ്വസനീയം), അല്ലെങ്കിൽ നേരിട്ടുള്ള കോളർമാർക്കുള്ള യഥാർഥ സോക്കറ്റ് പിയർ. `Host` /
`nextUrl.hostname` ഒരിക്കലും പരിശോധിക്കപ്പെടുന്നില്ല; ആദ്യ പാസ്വേഡ് എഴുതൽ
(`POST /api/settings/require-login`) എല്ലാ നെറ്റ്വർക്ക് പിയറുകൾക്കും തുറന്നുകൊടുക്കുന്നതിന് പകരം ഇതേ നിയന്ത്രണത്തിന് കീഴിലാണ്
(GHSA-7pq4-8pvv-rx7r). `managementPolicy` അതിന്റെ സ്വന്തം `peerContext` വിധി
വ്യക്തമായി താഴേക്ക് കൈമാറുന്നതിനാൽ ORIGINAL (സ്ട്രിപ്പ് ചെയ്യുന്നതിന് മുമ്പുള്ള) അഭ്യർത്ഥനയുടെ ഹെഡറുകൾ ഒരിക്കലും അത് തീരുമാനിക്കുന്നില്ല.

### ടയർ 3 — MANAGEMENT (ഡിഫോൾട്ട്)

മറ്റെല്ലാ മാനേജ്മെന്റ് റൂട്ടുകളും. `requireLogin=false` കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിൽ
ഓതന്റിക്കേഷൻ ആവശ്യമാണ്. CLI ടോക്കണുകൾക്ക് ഈ റൂട്ടുകളിൽ ഓതന്റിക്കേറ്റ് ചെയ്യാൻ കഴിയും (ലൂപ്പ്ബാക്ക് + സാധുവായ HMAC).

## മൂല്യനിർണ്ണയ ക്രമം

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ലൂപ്പ്ബാക്ക്                                  → അടുത്ത ഘട്ടത്തിലേക്ക്
     → ലൂപ്പ്ബാക്ക് അല്ലാത്തത്, manage-scope Bearer
        കൂടാതെ isLocalOnlyBypassableByManageScope   → അനുവദിക്കുക (management_key)
     → അല്ലെങ്കിൽ                                   → നിരസിക്കുക 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → അനുവദിക്കുക (system)
  3. hasValidCliToken(headers)?
     → അനുവദിക്കുക (cli) [ലൂപ്പ്ബാക്ക് + timingSafeEqual HMAC പരിശോധന]
  4. isAlwaysProtectedPath(path) അല്ലെങ്കിൽ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → അനുവദിക്കുക (dashboard_session)
     → മറികടക്കാനാകാത്ത പാതയിൽ manage-scope Bearer ഉണ്ടോ?
        → അനുവദിക്കുക (management_key)
     → നിരസിക്കുക 401/403
  5. requireLogin=false?
     → അനുവദിക്കുക (anonymous)
```

ഘട്ടം 1-ലെ manage-scope ശാഖ മാത്രമാണ് ഒരു LOCAL_ONLY റൂട്ടിന്റെ ആവശ്യകത നിറവേറ്റാൻ കഴിയുന്ന പ്രാമാണീകരിച്ച പാത; കാലഹരണപ്പെട്ട DB നിശ്ശബ്ദമായി "നിരസിക്കുക" എന്നതിലേക്ക് തരംതാഴാതിരിക്കാൻ auth-backend പരാജയ മോഡ് 403-ന് പകരം 503 നൽകുന്നു.

## പ്രോസസുകൾ സൃഷ്ടിക്കാൻ കഴിയുന്ന പുതിയ റൂട്ട് ചേർക്കൽ

1. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_API_PREFIXES`-ലേക്ക് പാതാ പ്രിഫിക്സ് ചേർക്കുക
2. പുതിയ പ്രിഫിക്സിന് `isLocalOnlyPath()` true നൽകുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഒരു ടെസ്റ്റ് `tests/unit/authz/routeGuard.test.ts`-ൽ ചേർക്കുക
3. **ഈ ഘട്ടം ഒരിക്കലും ഒഴിവാക്കരുത്** — `CLAUDE.md`-ലെ കർശന നിയമം #15 കാണുക
4. തീരുമാനിക്കുക: ഈ റൂട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലും ഉൾപ്പെടണമോ?
   സ്വതവേയുള്ള ഉത്തരം **ഇല്ല** എന്നാണ്. manage-scope ഉടമയ്ക്ക് തുറന്നുകൊടുക്കാൻ റൂട്ട് സുരക്ഷിതമാണെങ്കിൽ മാത്രം ഇത് തിരഞ്ഞെടുക്കുക (അതായത്, ഉപയോക്താവ് നിയന്ത്രിക്കുന്ന ഏതെങ്കിലും കോഡ് അത് പ്രോസസായി സൃഷ്ടിക്കരുത്).

## manage-scope വഴി മറികടക്കാവുന്ന പാത ചേർക്കൽ

1. ഉപയോക്താവ് നൽകുന്ന കോഡോ കമാൻഡുകളോ റൂട്ട് പ്രവർത്തിപ്പിക്കുന്നില്ലെന്ന് സ്ഥിരീകരിക്കുക. പ്രവർത്തിപ്പിക്കുന്നുണ്ടെങ്കിൽ നിർത്തുക — ഈ പ്രത്യേക ഇളവ് അതിന് അനുയോജ്യമായ ഉപകരണമല്ല.
2. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലേക്ക് പ്രിഫിക്സ് ചേർക്കുക
3. നാല് അഭ്യർത്ഥനാ രൂപങ്ങൾക്കും `tests/unit/authz/management-policy.test.ts`-ൽ കവറേജ് ചേർക്കുക: Bearer ഇല്ല (403), manage Bearer (അനുവദിക്കുക), non-manage Bearer (403), കൂടാതെ manage Bearer ഉണ്ടായാലും `/api/cli-tools/runtime/*` കർശനമായ ലൂപ്പ്ബാക്ക് മാത്രമായി തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഓരോ പ്രിഫിക്സിനുമായുള്ള റിഗ്രഷൻ.

## OpenAPI-യിൽ സുരക്ഷാ ടയറുകൾ രേഖപ്പെടുത്തൽ

`docs/openapi.yaml`-ലേക്ക് പുതിയ റൂട്ട് ചേർക്കുമ്പോൾ, റൂട്ട് `routeGuard.ts` പ്രകാരം വർഗ്ഗീകരിച്ചിട്ടുണ്ടെങ്കിൽ അനുബന്ധ vendor extension പ്രയോഗിക്കുക:

| routeGuard.ts വർഗ്ഗീകരണം        | YAML അനോട്ടേഷൻ             | നിർബന്ധിത നിയന്ത്രണം                                      |
| ------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`       | `x-loopback-only: true`    | ലൂപ്പ്ബാക്ക് അല്ലാത്തവയിൽ നിന്ന് നിരുപാധികമായി തടയുന്നു   |
| `ALWAYS_PROTECTED_API_PATHS`    | `x-always-protected: true` | `requireLogin=false` ആണെങ്കിലും പ്രാമാണീകരണം ആവശ്യമാണ്    |
| ആന്തരിക admin/debug റൂട്ട്      | `x-internal: true`         | സ്വതവേ /dashboard/api-endpoints-ൽ നിന്ന് മറച്ചിരിക്കുന്നു |
| ഒന്നുമില്ല (പൊതു / സാധാരണ auth) | (അനോട്ടേഷൻ ആവശ്യമില്ല)     | സാധാരണ `requireLogin` നിയന്ത്രിത ആക്സസ്                   |

### സാധൂകരണം

YAML അനോട്ടേഷനുകളും `routeGuard.ts`-ഉം തമ്മിലുള്ള സ്ഥിരത രണ്ട് സ്ക്രിപ്റ്റുകൾ നിർബന്ധമാക്കുന്നു:

- `scripts/check/check-openapi-coverage.mjs` — കവറേജ് < 99% ആണെങ്കിൽ പരാജയപ്പെടുന്നു
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` അല്ലെങ്കിൽ
  `x-always-protected` അനോട്ടേഷനുകൾ കംപൈൽ സമയ സ്ഥിരാങ്കങ്ങളിൽ നിന്ന് വ്യതിചലിച്ചാൽ പരാജയപ്പെടുന്നു

രണ്ട് സ്ക്രിപ്റ്റുകളും pre-commit hook-ലും CI-ലും പ്രവർത്തിക്കുന്നു.

### തെറ്റായ പോസിറ്റീവ് നിയമം

`routeGuard.ts` സ്ഥിരാങ്കത്തിൽ ഉൾപ്പെടാത്ത ഒരു റൂട്ടിൽ `x-always-protected` അല്ലെങ്കിൽ `x-loopback-only` അനോട്ടേറ്റ് ചെയ്താൽ, കവറേജ് സ്ക്രിപ്റ്റ് പരാജയപ്പെടുന്നു. `routeGuard.ts` യഥാർത്ഥത്തിൽ നിർബന്ധമാക്കുന്ന കാര്യവുമായി YAML-നെ പൊരുത്തപ്പെടുത്തുക എന്നതാണ് എല്ലായ്പ്പോഴും പരിഹാരം — നിർബന്ധിത നിയന്ത്രണ ലോജിക് നടപ്പാക്കാതെ `routeGuard.ts`-ലേക്ക് റൂട്ടുകൾ ചേർക്കുകയല്ല.
