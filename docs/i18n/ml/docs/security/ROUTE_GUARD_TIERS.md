## അവലോകനം

എല്ലാ OmniRoute മാനേജ്മെന്റ് API റൂട്ടുകളും മൂന്ന് സംരക്ഷണ
തലങ്ങളിൽ ഒന്നായി വർഗ്ഗീകരിച്ചിരിക്കുന്നു. ഈ വർഗ്ഗീകരണം സ്ഥിരമാണ്,
`src/server/authz/routeGuard.ts`-ൽ നിർവചിച്ചിരിക്കുന്നു, കൂടാതെ മറ്റേതെങ്കിലും ഓത്ത് ശാഖ
പ്രവർത്തിക്കുന്നതിന് മുമ്പ് വിലയിരുത്തപ്പെടുന്നു.

## ടയറുകൾ

### ടയർ 1 — LOCAL_ONLY

**നടപ്പിലാക്കുന്നത്:** `isLocalOnlyPath(path)` → ലൂപ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന
**ബൈപ്പാസ്:** ഡിഫോൾട്ടായി ഒന്നുമില്ല. അഭ്യർത്ഥന `manage` സ്കോപ്പുള്ള സാധുവായ ഒരു API കീ കൊണ്ടുപോകുമ്പോൾ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ൽ ഉള്ള പാതകൾക്ക് ഇടുങ്ങിയ ഇളവ് (കാണുക [Manage-സ്കോപ്പ് ഇളവ്](#manage-scope-carve-out)).

ഈ റൂട്ടുകൾ ചൈൽഡ് പ്രോസസുകൾ സ്പോൺ ചെയ്യുകയോ റൺടൈം കോഡ് എക്സിക്യൂട്ട് ചെയ്യുകയോ ചെയ്യുന്നു. അവയെ നോൺ-ലൂപ്ബാക്ക് ട്രാഫിക്കിന് തുറന്നുകൊടുക്കുന്നത് സാധുവായ ഒരു JWT നേടിയ ഒരു ആക്രമണകാരന് (ഉദാ: ഒരു Cloudflared/Ngrok ടണൽ വഴി) പ്രോസസ് സ്പോണിംഗ് ട്രിഗർ ചെയ്യാൻ അനുവദിക്കും — അറിയപ്പെടുന്ന ഒരു CVE വിഭാഗം ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj എന്താണ് (ആക്രമണ വിഭാഗം):** ഒരു മാനേജ്മെന്റ്/ഏജന്റ് സെർവർ ഒരു സബ്ബ്രോസസ് ലോഞ്ച് ചെയ്യുന്ന ഒരു എൻഡ്പോയിന്റ് തുറന്നുകാട്ടുന്നു (`npm install`, `node`, ഒരു ബ്രൗസർ, ഒരു പ്രോക്സി, `git`, `tar`, …). ആ എൻഡ്പോയിന്റ് ഹോസ്റ്റിന് പുറത്തുനിന്ന് എത്തിച്ചേരാൻ കഴിഞ്ഞാൽ — ഓപ്പറേറ്റർ OmniRoute-നെ ഒരു nginx/Cloudflare/Tailscale ടണലിന് പിറകിൽ വച്ച് ഒരു JWT ചോർന്നതുകൊണ്ടോ, അല്ലെങ്കിൽ ഓത്ത് തെറ്റായി ക്രമീകരിച്ചതുകൊണ്ടോ — ആക്രമണകാരൻ "ഒരു API വിളിക്കുക" എന്നതിനെ "ഹോസ്റ്റിൽ ഒരു കമാൻഡ് റൺ ചെയ്യുക" എന്നാക്കി മാറ്റുന്നു (റിമോട്ട് കോഡ് എക്സിക്യൂഷൻ). ഓരോ സ്പോൺ-ശേഷിയുള്ള റൂട്ടിലും **ഏതൊരു ഓത്ത് പരിശോധനയ്ക്കും മുമ്പ്, നിബന്ധനയില്ലാതെ ലൂപ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന** നടപ്പിലാക്കിയാണ് OmniRoute ഈ ദ്വാരം അടയ്ക്കുന്നത്: ടണലിലൂടെ ചോർന്ന ഒരു ടോക്കണിനും സ്പോണിലെത്താൻ കഴിയില്ല.

**പൂർണ്ണമായ LOCAL_ONLY ഗണം.** അധികാരപരമായ ഉറവിടം `src/server/authz/routeGuard.ts`-ൽ ഉള്ള `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ആണ്; താഴെയുള്ള പട്ടിക നിലവിലെ അവസ്ഥയെ പ്രതിഫലിപ്പിക്കുന്നു. `check-route-guard-membership` ഗേറ്റ് സ്പോൺ-ശേഷിയുള്ള പ്രിഫിക്സുകൾക്ക് കീഴിലുള്ള ഓരോ `route.ts`-യെയും പട്ടികപ്പെടുത്തുകയും, ഏതെങ്കിലും ഒന്ന് local-only ആയി തരംതിരിക്കപ്പെട്ടിട്ടില്ലെങ്കിൽ CI പരാജയപ്പെടുത്തുകയും ചെയ്യുന്നു.

#### Manage-scope കാർവ്-ഔട്ട്

LOCAL_ONLY പാതകളുടെ ഒരു ഉപവിഭാഗം നോൺ-ലൂപ്പ്ബാക്കിൽ നിന്നും ആക്സസ് ചെയ്യാം — അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പ് (അല്ലെങ്കിൽ `admin`) ഉൾപ്പെടുന്ന മെറ്റാഡേറ്റയുള്ള ഒരു `Authorization: Bearer <api-key>` ഉണ്ടെങ്കിൽ മാത്രം. ഏത് പുതിയ LOCAL_ONLY പാതയ്ക്കും ഡിഫോൾട്ട് strict-loopback ആയി തുടരുന്നതിനായി, കാർവ്-ഔട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` വഴി പാത-തലത്തിൽ വ്യക്തമായി ഗേറ്റ് ചെയ്യപ്പെട്ടിരിക്കുന്നു. പ്രാമാണീകരിക്കാത്ത അഭ്യർത്ഥനകളും manage അല്ലാത്ത കീകളുള്ള അഭ്യർത്ഥനകളും തുടർന്നും `403 LOCAL_ONLY` കൊണ്ട് നിരസിക്കപ്പെടും.

ഇന്ന് ബൈപാസ് ചെയ്യാവുന്ന ഏക പ്രീഫിക്സ് `/api/mcp/` ആണ്. `/api/cli-tools/runtime/`, `/api/services/` എന്നിവ ബോധപൂർവ്വം ഒഴിവാക്കിയിരിക്കുന്നു — കാരണം അവയ്ക്ക് ഏകസിവിലായ subprocess-കൾ (`npm install`, `node`) സ്പോൺ ചെയ്യാൻ കഴിയും, ഇത് LOCAL_ONLY ടയർ തടയാനായി നിലവിലുള്ള കൃത്യമായ CVE വിഭാഗം തന്നെയാണ്.

**#7895 — `mcp:connect` ഇടുങ്ങിയ സ്കോപ്പ്:** `/api/mcp/` കാർവ്-ഔട്ട് ഇടുങ്ങിയ `mcp:connect` സ്കോപ്പ് ഉള്ള ഒരു Bearer കീയും സ്വീകരിക്കുന്നു (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), ഇത് `src/server/authz/policies/management.ts`-ലെ `hasMcpConnectOrManageScope()` വഴി പരിശോധിക്കുന്നു. ഇത് `/api/mcp/` ലേക്ക് മാത്രമാണ് പരിമിതപ്പെടുത്തിയിരിക്കുന്നത് — `mcp:connect` മറ്റൊരു മാനേജ്മെന്റ് റൂട്ടിലും (ഭാവിയിൽ മറ്റൊരു LOCAL_ONLY ബൈപാസ് പ്രീഫിക്സ് ചേർന്നാലും അതുൾപ്പെടെ) ഒന്നും അനുവദിക്കുന്നില്ല, കൂടാതെ ഇത് `MANAGEMENT_API_KEY_SCOPES`-ൽ നിന്ന് ബോധപൂർവ്വം ഒഴിവാക്കിയിരിക്കുന്നു. `manage`/`admin` ഉള്ള ഒരു കീ മുൻപേ പോലെ തന്നെ കാർവ്-ഔട്ട് പാസ് ചെയ്യും; `mcp:connect` എന്നത് വിശാലമായ മാനേജ്മെന്റ് ആക്സസ് ആവശ്യമില്ലാത്ത റിമോട്ട് MCP-മാത്ര കോളർമാർക്കുള്ള കുറഞ്ഞ-അധികാര ബദലാണ്.

#### ഓപ്പറേറ്റർ മാർഗ്ഗനിർദ്ദേശവും ഓഡിറ്റിംഗും

നിങ്ങൾ OmniRoute ഒരു റിവേഴ്സ് പ്രോക്സിക്കോ ടണലിനോ (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok) പിന്നിൽ പ്രവർത്തിപ്പിക്കുന്നുവെങ്കിൽ, ലൂപ്പ്ബാക്ക് പരിശോധന മുകളിലെ spawn-ശേഷിയുള്ള റൂട്ടുകളെ ഇപ്പോഴും സംരക്ഷിക്കുന്നു — ക്ലയന്റ് വിലാസം നോൺ-ലൂപ്പ്ബാക്കായ ഒരു അഭ്യർത്ഥന **ഓത്ത് പ്രവർത്തിക്കുന്നതിന് മുമ്പ്** `403 LOCAL_ONLY` കൊണ്ട് നിരസിക്കപ്പെടുന്നു, അതിനാൽ ചോർന്ന ഒരു JWT-ക്ക് ഒരു spawn-ൽ എത്തിച്ചേരാൻ കഴിയില്ല. രണ്ട് ഓപ്പറേറ്റർ ഉത്തരവാദിത്തങ്ങൾ അവശേഷിക്കുന്നു:

- **ക്ലയന്റ് IP-യെ loopback ആയി വ്യാജമായി മാറ്റി 403 "പരിഹരിക്ക"രുത്.**
  `X-Forwarded-For: 127.0.0.1` സജ്ജീകരിക്കുന്നതോ, സോഴ്സ് വിലാസത്തെ loopback-ലേക്ക്
  തിരുത്തിയെഴുതുന്ന പ്രോക്സിയോ, ഈ ടയർ അടയ്ക്കുന്ന RCE കласт് തന്നെ വീണ്ടും
  തുറക്കുന്നു. ഡാഷ്ബോർഡ്/API പ്രോക്സി വഴി എക്സ്പോസ് ചെയ്യുക — spawn-capable
  റൂട്ടുകൾ ഒരിക്കലുമല്ല.
- **manage-scope ബൈപാസ് ഏറ്റവും ചുരുങ്ങിയതായി സൂക്ഷിക്കുക.** `/api/mcp/` മാത്രമേ
  ബൈപാസ് ചെയ്യാനാവൂ, അതും `manage`-scoped API കീ ഉപയോഗിച്ച് മാത്രം.
  `SPAWN_CAPABLE_PREFIXES` ഒരിക്കലും ബൈപാസ് ലിസ്റ്റിൽ ചേർക്കാൻ കഴിയില്ല — zod
  സ്കീമ അവയെ നിരാകരിക്കുകയും `isLocalOnlyBypassableByManageScope` റൺടൈമിൽ അവയെ
  തടയുകയും ചെയ്യുന്നു (defence-in-depth); ഡാഷ്ബോർഡ് "cannot be made bypassable"
  എന്ന് ഉദ്ദേശിക്കുന്നത് ഇതിനെയാണ്. സ്പോൺ ചെയ്യാത്തതെങ്കിലും ഒരിക്കലും റിമോട്ടായി
  എത്താൻ പാടില്ലാത്ത ചില LOCAL_ONLY റൂട്ടുകളും അതേ deny-list-ൽ ഉണ്ട് —
  `/api/oauth/kiro/auto-import` (ഹോസ്റ്റ്-ലോക്കൽ Kiro ക്രെഡൻഷ്യൽ ഫയലുകൾ വായിക്കുന്നു),
  `/api/discovery/`, `/api/issue-agent/` എന്നിവ. റൺടൈം സ്നാപ്ഷോട്ട് ലോഡർ സംഭരിച്ച
  settings വരിയിൽ നിന്ന് ഇത്തരം എൻട്രികൾ കളയുകയും ചെയ്യുന്നു; ലെഗസി JSON ഇംപോർട്ട്
  (`/api/settings/import-json`) ബൈപാസ് കീകൾ ഒരിക്കലും എഴുതുന്നില്ല. ഓരോ
  `LOCAL_ONLY_API_PREFIXES` എൻട്രിയും deny-list-ൽ ആയിരിക്കണം, അല്ലെങ്കിൽ
  ബൈപാസ്-യോഗ്യതയ്ക്കായി അവലോകനം ചെയ്യപ്പെടണം
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`
  കീഴിലുള്ള ഡൈനാമിക്-സെഗ്മെന്റ്, സ്റ്റാറ്റിക്-പാത്ത് spawn-capable റൂട്ടുകൾ
  (ഉദാ. `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts`-ലെ
  regex-അടിസ്ഥാന `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS`
  കംപാനിയനാണ് കവർ ചെയ്യുന്നത്, ഫ്ലാറ്റ് `SPAWN_CAPABLE_PREFIXES` അറേ അല്ല —
  അവയെ പിടികൂടാൻ ഫ്ലാറ്റ് അറേ മുഴുവൻ `/api/providers/` പ്രിഫിക്സും കവർ ചെയ്യേണ്ടി
  വരും, അത് റിമോട്ട് ഡാഷ്ബോർഡുകൾ provider CRUD-ക്കായി നിയമാനുസൃതമായി ഉപയോഗിക്കുന്ന
  റൂട്ട് ട്രീയെ അമിതമായി വ്യാപകമാക്കും.

**ആക്സസ് ഓഡിറ്റ് ചെയ്യൽ** — ഹോസ്റ്റിന് പുറത്തുള്ള ഒന്നും ഈ റൂട്ടുകളിൽ എത്തുന്നില്ലെന്ന് ഉറപ്പാക്കാൻ:

- `/dashboard/settings/security`-ലെ **Authorization Inventory** തുറക്കുക: അത് ലൈവ്
  LOCAL_ONLY പ്രിഫിക്സ് ലിസ്റ്റ്, ഏത് പ്രിഫിക്സുകളാണ് ബൈപാസ് ചെയ്യാവുന്നത്, കംപൈൽ-ടൈം
  spawn-capable ("cannot be made bypassable") സെറ്റ് എന്നിവ കാണിക്കുന്നു.
- മുകളിലെ പ്രിഫിക്സുകൾ non-loopback ക്ലയന്റ് വിലാസത്തോടൊപ്പം ഉള്ളവയ്ക്കായി നിങ്ങളുടെ
  reverse-proxy / ആക്സസ് ലോഗുകളിൽ grep ചെയ്യുക. `403 LOCAL_ONLY`-ക്ക് പകരം `200`
  മടങ്ങിയ ഇത്തരമൊരു ഹിറ്റ് പ്രോക്സി യഥാർത്ഥ ക്ലയന്റ് IP-യെ മറയ്ക്കുന്നുവെന്നാണ്
  അർത്ഥമാക്കുന്നത് — പ്രോക്സി ശരിയാക്കുക.
- ഈ പാതകളിൽ ഒന്നിനായി OmniRoute-ന്റെ ലോഗുകളിലെ `403 LOCAL_ONLY` എന്നത് ഗാർഡ്
  ഉദ്ദേശിച്ചപോലെ പ്രവർത്തിക്കുന്നതാണ്, അടിച്ചമർത്തേണ്ട പിഴവല്ല.

`tailscale status --json`) റൺ ചെയ്യുന്നു. അവ `GET`-ന് LOCAL_ONLY അല്ല; പകരം ഹാൻഡ്ലർ
`getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) ഉപയോഗിച്ച് വിശ്വസനീയമായ
പിയർ തീർപ്പ് വായിക്കുകയും `loopback` / `lan` കോളറുകൾക്ക് മാത്രം പ്രോബ് റൺ
ചെയ്യുകയും ചെയ്യുന്നു. ഒരു `remote` കോളർക്ക് സ്പോൺ ചെയ്യാത്ത ഉറവിടങ്ങളിൽ നിന്ന്
(സ്ഥിരമായി സൂക്ഷിച്ചിരിക്കുന്ന സ്റ്റേറ്റ്, settings, fs പരിശോധനകൾ) നിർമ്മിച്ച അതേ

### ടയർ 2 — ALWAYS_PROTECTED

**നടപ്പിലാക്കുന്നത്:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ബൈപാസ് ഒഴിവാക്കുക

GHSA-62vw `GET` പാസ്വേഡ് വെളിപ്പാടിനെ മറച്ചു മാത്രമേ ചെയ്തുള്ളൂ; ഇഷ്യൂവൻസ് ഇപ്പോഴും ഫെയിൽ-ഓപ്പൺ ടീയറിലായിരുന്നു (GHSA-7pq4-8pvv-rx7r). കൂടാതെ `enableObsidianVaultSync()` ഡാറ്റാ ഡയറക്ടറിയായ, അതിനുള്ളിൽ സ്ഥിതിചെയ്യുന്ന, അല്ലെങ്കിൽ അതിനെ ഉൾക്കൊള്ളുന്ന ഒരു വോൾട്ടിനെ നിരാകരിക്കുന്നു.

#### ക്രെഡൻഷ്യൽ എക്സ്പോർട്ടുകളും റീസ്റ്റോറുകളും ഓപ്പറേറ്റർ-മാത്രം

മുകളിലെ ടീയർ _ഏതെങ്കിലും_ ക്രെഡൻഷ്യൽ ആവശ്യമാണോ എന്ന് മാത്രമേ തീരുമാനിക്കൂ. സൂക്ഷിച്ചിട്ടുള്ള ക്രെഡൻഷ്യലുകൾ ഡൗൺലോഡ് ചെയ്യുന്ന റൂട്ടുകൾ ഹാൻഡ്ലറിൽ ഒരു രണ്ടാമത്തെ പരിശോധന ചേർക്കുന്നു: `GET /api/settings/export-json` (ഡീക്രിപ്റ്റ് ചെയ്ത പ്രൊവൈഡർ കണക്ഷനുകളും അസംസ്കൃത API കീകളും), `GET /api/db-backups/export` (SQLite ഫയൽ), `GET /api/db-backups/exportAll` (മുഴുവൻ ആർക്കൈവ്) എന്നിവ `requireOperatorCredential()`-നെ (`src/lib/api/operatorCredential.ts`) വിളിക്കുന്നു. ഇത് ഒരു ഡാഷ്ബോർഡ് സെഷനെയോ, ലോക്കൽ CLI സബ്ജക്ടിനെയോ, ലോഗിൻ പ്രവർത്തനരഹിതമാക്കിയ ഒരു ഇൻസ്റ്റൻസിനെയോ അംഗീകരിക്കുന്നു, കൂടാതെ ഏത് സ്കോപ്പിലുമുള്ള API കീകൾക്ക് (`manage`, `admin` ഉൾപ്പെടെ) `oma_` ആക്സസ് ടോക്കണുകൾക്കും `403` മറുപടി നൽകുന്നു. നശീകരണ പ്രവൃത്തികളായ അനുബന്ധ റൂട്ടുകളും അതേ അതിർത്തി നിലനിർത്തുന്നു: `POST /api/db-backups/import` (അപ്ലോഡ് ചെയ്ത `.sqlite`, `dryRun=true` ഉൾപ്പെടെ), `POST /api/db-backups` (ഐഡി വഴി സൂക്ഷിച്ച ബാക്കപ്പ് റീസ്റ്റോർ ചെയ്യുക), `POST /api/settings/import-json` (ലെഗസി JSON റീസ്റ്റോർ) എന്നിവ സജീവ ഡാറ്റാബേസിനെയോ മുഴുവൻ settings/connections/API-key സെറ്റിനെയോ മാറ്റിസ്ഥാപിക്കുന്നു, അതിനാൽ ഒരു മെഷീൻ ക്രെഡൻഷ്യലിനും അവയെ ട്രിഗർ ചെയ്യാൻ കഴിയില്ല. റീസ്റ്റോർ പോയിന്റുകൾ നശിപ്പിക്കുന്നതും അതേ അതിർത്തി നിലനിർത്തുന്നു: `DELETE /api/db-backups` (ക്ലീനപ്പ് — ഏറ്റവും പുതിയ N എണ്ണം സൂക്ഷിക്കുക / D ദിവസത്തേക്കാൾ പഴയത് ഉപേക്ഷിക്കുക), `PATCH /api/db-backups` (റിടൻഷൻ ക്രമീകരണങ്ങൾ), കാരണം സ്ഥിരമായി സൂക്ഷിച്ചിട്ടുള്ള റിടൻഷൻ തന്നെയാണ് ഓരോ ഓട്ടോമാറ്റിക് ബാക്കപ്പിനും ശേഷം `cleanupDbBackups()` പ്രയോഗിക്കുന്നത് (`src/lib/db/backup.ts`), അതിനാൽ `keepLatest: 1` സേവ് ചെയ്യാൻ കഴിയുന്ന ഒരു മെഷീൻ ക്രെഡൻഷ്യൽ അടുത്ത സ്നാപ്ഷോട്ടിൽ എല്ലാം പ്രൂൺ ചെയ്യും. ബാക്കപ്പുകൾ ലിസ്റ്റ് ചെയ്യുന്നതും സൃഷ്ടിക്കുന്നതും (`GET`/`PUT /api/db-backups`) സാധാരണ മാനേജ്മെന്റ് ഓത്ത് നിലനിർത്തുന്നു. സിങ്ക് ടോക്കൺ ഇഷ്യൂവൻസ് (`POST /api/sync/tokens`) അതേ ഹെൽപ്പർ ഉപയോഗിക്കുന്നു, കൂടാതെ വിശ്വസ്ത ലൂപ്പ്ബാക്ക് ഇന്റേണൽ-സർവീസ് ടോക്കണും.

### ഫ്രഷ്-ഇൻസ്റ്റാൾ ബൂട്ട്സ്ട്രാപ്പ് ലൂപ്പ്ബാക്ക്-മാത്രം — യഥാർത്ഥ പിയർ വഴി, `Host` അല്ല

മാനേജ്മെന്റ് പാസ്വേഡ് ഒന്നും കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിൽ (`INITIAL_PASSWORD`-ഉം ഇല്ലെങ്കിൽ), `src/shared/utils/apiAuth.ts`-ലെ `isAuthRequired()` അജ്ഞാത ബൂട്ട്സ്ട്രാപ്പ് **ലൂപ്പ്ബാക്ക് പിയറുകൾക്ക് മാത്രം** തുറന്നു നിലനിർത്തുന്നു. ലൂപ്പ്ബാക്ക് തീരുമാനിക്കുന്നത് വിശ്വസ്ത പിയർ സിഗ്നലുകളിൽ നിന്നാണ്, ഈ ക്രമത്തിൽ: ടോക്കൺ-സ്റ്റാമ്പ് ചെയ്ത യഥാർത്ഥ TCP പിയർ (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, പോളിസി കാണുന്നത്), പൈപ്പ്ലൈനിന്റെ സ്വന്തം `AUTHZ_HEADER_PEER_LOCALITY` തീർപ്പ് (റൂട്ട് ഹാൻഡ്ലറുകൾ കാണുന്നത്, `OMNIROUTE_PEER_STAMP_TOKEN` സെറ്റ് ആയിരിക്കുമ്പോൾ മാത്രം വിശ്വസിക്കുന്നു), അല്ലെങ്കിൽ നേരിട്ട് വിളിക്കുന്നവർക്ക് ഒരു യഥാർത്ഥ സോക്കറ്റ് പിയർ. `Host` / `nextUrl.hostname` ഒരിക്കലും പരിഗണിക്കുന്നില്ല, കൂടാതെ ആദ്യ-പാസ്വേഡ് എഴുത്ത് (`POST /api/settings/require-login`) എല്ലാ നെറ്റ്വർക്ക് പിയറുകൾക്കും തുറന്നതിന് പകരം അതേ നിയന്ത്രണത്തിന് കീഴിലാണ് (GHSA-7pq4-8pvv-rx7r). `managementPolicy` അതിന്റെ സ്വന്തം `peerContext` തീർപ്പ് വ്യക്തമായി താഴേക്ക് കൈമാറുന്നു, അതിനാൽ യഥാർത്ഥ (സ്ട്രിപ്പ് ചെയ്യുന്നതിന് മുൻപുള്ള) റിക്കസ്റ്റിന്റെ ഹെഡറുകൾ ഒരിക്കലും അത് തീരുമാനിക്കുന്നില്ല.

### ടീയർ 3 — MANAGEMENT (സ്ഥിരസ്ഥിതി)

മറ്റ് എല്ലാ മാനേജ്മെന്റ് റൂട്ടുകളും. `requireLogin=false` കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിൽ ഓത്ത് ആവശ്യമാണ്. CLI ടോക്കണുകൾക്ക് ഈ റൂട്ടുകൾ ഓതന്റിക്കേറ്റ് ചെയ്യാൻ കഴിയും (ലൂപ്പ്ബാക്ക് + സാധുവായ HMAC).

## മൂല്യനിർണ്ണയ ക്രമം

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ലൂപ്പ്ബാക്ക്                                  → അടുത്ത ഘട്ടത്തിലേക്ക്
     → ലൂപ്പ്ബാക്ക് അല്ലാത്തത്, manage-scope Bearer
        കൂടാതെ isLocalOnlyBypassableByManageScope   → അനുവദിക്കുക (management_key)
     → അല്ലെങ്കിൽ                                   → നിരസിക്കുക 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → അനുവദിക്കുക (system)
  3. hasValidCliToken(headers)?
     → അനുവദിക്കുക (cli) [ലൂപ്പ്ബാക്ക് + timingSafeEqual HMAC പരിശോധന]
  4. isAlwaysProtectedPath(path) അല്ലെങ്കിൽ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → അനുവദിക്കുക (dashboard_session)
     → മറികടക്കാനാകാത്ത പാതയിൽ manage-scope Bearer ഉണ്ടോ?
        → അനുവദിക്കുക (management_key)
     → നിരസിക്കുക 401/403
  5. requireLogin=false?
     → അനുവദിക്കുക (anonymous)
```

ഘട്ടം 1-ലെ manage-scope ശാഖ മാത്രമാണ് ഒരു LOCAL_ONLY റൂട്ടിന്റെ ആവശ്യകത നിറവേറ്റാൻ കഴിയുന്ന പ്രാമാണീകരിച്ച പാത; കാലഹരണപ്പെട്ട DB നിശ്ശബ്ദമായി "നിരസിക്കുക" എന്നതിലേക്ക് തരംതാഴാതിരിക്കാൻ auth-backend പരാജയ മോഡ് 403-ന് പകരം 503 നൽകുന്നു.

## പ്രോസസുകൾ സൃഷ്ടിക്കാൻ കഴിയുന്ന പുതിയ റൂട്ട് ചേർക്കൽ

1. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_API_PREFIXES`-ലേക്ക് പാതാ പ്രിഫിക്സ് ചേർക്കുക
2. പുതിയ പ്രിഫിക്സിന് `isLocalOnlyPath()` true നൽകുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഒരു ടെസ്റ്റ് `tests/unit/authz/routeGuard.test.ts`-ൽ ചേർക്കുക
3. **ഈ ഘട്ടം ഒരിക്കലും ഒഴിവാക്കരുത്** — `CLAUDE.md`-ലെ കർശന നിയമം #15 കാണുക
4. തീരുമാനിക്കുക: ഈ റൂട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലും ഉൾപ്പെടണമോ?
   സ്വതവേയുള്ള ഉത്തരം **ഇല്ല** എന്നാണ്. manage-scope ഉടമയ്ക്ക് തുറന്നുകൊടുക്കാൻ റൂട്ട് സുരക്ഷിതമാണെങ്കിൽ മാത്രം ഇത് തിരഞ്ഞെടുക്കുക (അതായത്, ഉപയോക്താവ് നിയന്ത്രിക്കുന്ന ഏതെങ്കിലും കോഡ് അത് പ്രോസസായി സൃഷ്ടിക്കരുത്).

## manage-scope വഴി മറികടക്കാവുന്ന പാത ചേർക്കൽ

1. ഉപയോക്താവ് നൽകുന്ന കോഡോ കമാൻഡുകളോ റൂട്ട് പ്രവർത്തിപ്പിക്കുന്നില്ലെന്ന് സ്ഥിരീകരിക്കുക. പ്രവർത്തിപ്പിക്കുന്നുണ്ടെങ്കിൽ നിർത്തുക — ഈ പ്രത്യേക ഇളവ് അതിന് അനുയോജ്യമായ ഉപകരണമല്ല.
2. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലേക്ക് പ്രിഫിക്സ് ചേർക്കുക
3. നാല് അഭ്യർത്ഥനാ രൂപങ്ങൾക്കും `tests/unit/authz/management-policy.test.ts`-ൽ കവറേജ് ചേർക്കുക: Bearer ഇല്ല (403), manage Bearer (അനുവദിക്കുക), non-manage Bearer (403), കൂടാതെ manage Bearer ഉണ്ടായാലും `/api/cli-tools/runtime/*` കർശനമായ ലൂപ്പ്ബാക്ക് മാത്രമായി തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഓരോ പ്രിഫിക്സിനുമായുള്ള റിഗ്രഷൻ.

## OpenAPI-യിൽ സുരക്ഷാ ടയറുകൾ രേഖപ്പെടുത്തൽ

`docs/openapi.yaml`-ലേക്ക് പുതിയ റൂട്ട് ചേർക്കുമ്പോൾ, റൂട്ട് `routeGuard.ts` പ്രകാരം വർഗ്ഗീകരിച്ചിട്ടുണ്ടെങ്കിൽ അനുബന്ധ vendor extension പ്രയോഗിക്കുക:

| routeGuard.ts വർഗ്ഗീകരണം        | YAML അനോട്ടേഷൻ             | നിർബന്ധിത നിയന്ത്രണം                                      |
| ------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`       | `x-loopback-only: true`    | ലൂപ്പ്ബാക്ക് അല്ലാത്തവയിൽ നിന്ന് നിരുപാധികമായി തടയുന്നു   |
| `ALWAYS_PROTECTED_API_PATHS`    | `x-always-protected: true` | `requireLogin=false` ആണെങ്കിലും പ്രാമാണീകരണം ആവശ്യമാണ്    |
| ആന്തരിക admin/debug റൂട്ട്      | `x-internal: true`         | സ്വതവേ /dashboard/api-endpoints-ൽ നിന്ന് മറച്ചിരിക്കുന്നു |
| ഒന്നുമില്ല (പൊതു / സാധാരണ auth) | (അനോട്ടേഷൻ ആവശ്യമില്ല)     | സാധാരണ `requireLogin` നിയന്ത്രിത ആക്സസ്                   |

### സാധൂകരണം

YAML അനോട്ടേഷനുകളും `routeGuard.ts`-ഉം തമ്മിലുള്ള സ്ഥിരത രണ്ട് സ്ക്രിപ്റ്റുകൾ നിർബന്ധമാക്കുന്നു:

- `scripts/check/check-openapi-coverage.mjs` — കവറേജ് < 99% ആണെങ്കിൽ പരാജയപ്പെടുന്നു
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` അല്ലെങ്കിൽ
  `x-always-protected` അനോട്ടേഷനുകൾ കംപൈൽ സമയ സ്ഥിരാങ്കങ്ങളിൽ നിന്ന് വ്യതിചലിച്ചാൽ പരാജയപ്പെടുന്നു

രണ്ട് സ്ക്രിപ്റ്റുകളും pre-commit hook-ലും CI-ലും പ്രവർത്തിക്കുന്നു.

### തെറ്റായ പോസിറ്റീവ് നിയമം

`routeGuard.ts` സ്ഥിരാങ്കത്തിൽ ഉൾപ്പെടാത്ത ഒരു റൂട്ടിൽ `x-always-protected` അല്ലെങ്കിൽ `x-loopback-only` അനോട്ടേറ്റ് ചെയ്താൽ, കവറേജ് സ്ക്രിപ്റ്റ് പരാജയപ്പെടുന്നു. `routeGuard.ts` യഥാർത്ഥത്തിൽ നിർബന്ധമാക്കുന്ന കാര്യവുമായി YAML-നെ പൊരുത്തപ്പെടുത്തുക എന്നതാണ് എല്ലായ്പ്പോഴും പരിഹാരം — നിർബന്ധിത നിയന്ത്രണ ലോജിക് നടപ്പാക്കാതെ `routeGuard.ts`-ലേക്ക് റൂട്ടുകൾ ചേർക്കുകയല്ല.
