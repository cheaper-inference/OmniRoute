> അനുയോജ്യമായ കോൺടെക്സ്റ്റിൽ സ്വയമേവ 15-95% ലാഭിക്കുക. പെട്ടെന്നുള്ള ഒരു അവലോകനത്തിനായി, [README കംപ്രഷൻ വിഭാഗം](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) കാണുക.

## അവലോകനം

അപ്സ്ട്രീം പ്രൊവൈഡർമാരിലേക്ക് അഭ്യർത്ഥനകൾ എത്തുന്നതിന് **മുൻകൂട്ടി** പ്രവർത്തിക്കുന്ന ഒരു മോഡുലാർ പ്രോംപ്റ്റ് കംപ്രഷൻ പൈപ്പ്ലൈൻ OmniRoute നടപ്പിലാക്കുന്നു. അതായത്, നിങ്ങളുടെ ടോക്കൺ ലാഭം സുതാര്യമായി സംഭവിക്കുന്നു — നിങ്ങളുടെ വർക്ക്ഫ്ലോയിൽ മാറ്റങ്ങളൊന്നും ആവശ്യമില്ല.

```
ക്ലയന്റ് അഭ്യർത്ഥന
  → കംപ്രഷൻ സ്ട്രാറ്റജി സെലക്ടർ
    → കോംബോ ഓവർറൈഡ്? → കോംബോ ക്രമീകരണം ഉപയോഗിക്കുക
    → ഓട്ടോ-ട്രിഗർ പരിധി? → ഓട്ടോ മോഡ് ഉപയോഗിക്കുക
    → ഡിഫോൾട്ട് മോഡ്? → ഗ്ലോബൽ ക്രമീകരണം ഉപയോഗിക്കുക
    → ഓഫ്? → കംപ്രഷൻ ഒഴിവാക്കുക
  → തിരഞ്ഞെടുത്ത കംപ്രഷൻ മോഡ്
    → ഓഫ്: കംപ്രഷൻ ഇല്ല
    → ലൈറ്റ്: സുരക്ഷിതമായ വൈറ്റ്സ്പേസ്/ഫോർമാറ്റിംഗ് വൃത്തിയാക്കൽ (~15%)
    → സ്റ്റാൻഡേർഡ്: ഗുഹാമനുഷ്യ ശൈലിയിൽ അനാവശ്യ പദങ്ങൾ നീക്കംചെയ്യൽ (~30%)
    → അഗ്രസീവ്: ഹിസ്റ്ററി ഏജിംഗ് + സംഗ്രഹിക്കൽ (~50%)
    → അൾട്രാ: ഹ്യൂറിസ്റ്റിക് പ്രൂണിംഗ് + കോഡ്-ബ്ലോക്ക് ലഘൂകരിക്കൽ (~75%)
    → RTK: കമാൻഡ്-അവബോധമുള്ള ടെർമിനൽ/ടൂൾ-ഔട്ട്പുട്ട് ഫിൽട്ടറിംഗ് (അപ്സ്ട്രീം പരിധി 60-90%)
    → സ്റ്റാക്ക്ഡ്: ക്രമീകരിച്ച മൾട്ടി-എഞ്ചിൻ പൈപ്പ്ലൈൻ, സാധാരണയായി RTK, തുടർന്ന് Caveman (അനുയോജ്യമായ പരിധി 78-95%)
  → കംപ്രസ് ചെയ്ത അഭ്യർത്ഥന → പ്രൊവൈഡർ
```

## കംപ്രഷൻ മോഡുകൾ

### ഓഫ്

കംപ്രഷൻ പ്രയോഗിച്ചിട്ടില്ല. എല്ലാ സന്ദേശങ്ങളും മാറ്റമില്ലാതെ കടന്നുപോകുന്നു.

### ലൈറ്റ് മോഡ് (~15% ലാഭം, <1ms ലേറ്റൻസി)

ഏറ്റവും സുരക്ഷിതമായ മോഡ് — ഫോർമാറ്റിംഗ് വൃത്തിയാക്കൽ. ഇതിലെ tool-result truncation നഷ്ടപരമായതിനാൽ, ഡിഫോൾട്ട്
പാത (`allow-lossy`, `engine:lite` അല്ലെങ്കിൽ പേരിട്ട കോമ്പോ opt-in ഇല്ലാത്തത്) `compressToolResults: false` ഉപയോഗിച്ച്
lite ആയി പ്രവർത്തിക്കുന്നു: മുമ്പത്തെ tool ഫലങ്ങൾ provider-ലേക്ക് മാറ്റമില്ലാതെ എത്തുന്നു.

| സാങ്കേതികവിദ്യ           | വിവരണം                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| `collapseWhitespace`     | തുടർച്ചയായ ശൂന്യവരികളും അവസാനത്തെ spaces-ഉം ലയിപ്പിക്കുക                                         |
| `dedupSystemPrompt`      | ആവർത്തിക്കുന്ന system സന്ദേശങ്ങൾ നീക്കം ചെയ്യുക                                                  |
| `compressToolResults`    | മുമ്പത്തെ tool ഫലങ്ങൾ lite പരിധിയിലേക്ക് ചുരുക്കുക (നഷ്ടപരമാണ്: request opt-in ഉള്ളപ്പോൾ മാത്രം) |
| `removeRedundantContent` | ആവർത്തിക്കുന്ന നിർദ്ദേശങ്ങൾ നീക്കം ചെയ്യുക                                                       |
| `replaceImageUrls`       | base64 image data URI-കളുടെ ദൈർഘ്യം കുറയ്ക്കുക                                                   |

**ഏറ്റവും അനുയോജ്യം:** എല്ലായ്പ്പോഴും പ്രവർത്തിക്കുന്ന ഉപയോഗം, സുരക്ഷാ-നിർണായകമായ workflow-കൾ.

### സ്റ്റാൻഡേർഡ് മോഡ് (~30% ലാഭം)

[കേവ്മാൻ](https://github.com/JuliusBrussee/caveman)-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ട് — അർത്ഥം നിലനിർത്തിക്കൊണ്ട്
പൂരകവാക്കുകളും വാചാലമായ പ്രയോഗങ്ങളും നീക്കം ചെയ്യുന്നു:

- പൂരകവാക്കുകൾ നീക്കം ചെയ്യുന്നു ("please", "I think", "basically", "actually")
- വാചാലമായ പ്രയോഗങ്ങൾ ചുരുക്കുന്നു ("in order to" → "to", "as a result of" → "because")
- വിനയപരമായ അനിശ്ചിതപ്രയോഗങ്ങൾ നീക്കം ചെയ്യുന്നു ("Would you mind...", "If you could possibly...")
- coding prompt-ുകൾക്കായി ക്രമീകരിച്ച 30+ regex നിയമങ്ങൾ

**ഏറ്റവും അനുയോജ്യം:** ദൈനംദിന coding workflow-കൾ, ചെലവിനെക്കുറിച്ച് ശ്രദ്ധിക്കുന്ന ടീമുകൾ.

### അഗ്രസീവ് മോഡ് (~50% ലാഭം)

ദൈർഘ്യമേറിയ സെഷനുകൾക്കായുള്ള സ്മാർട്ട് history മാനേജ്മെന്റ്:

- **Message Aging** — പഴയ സന്ദേശങ്ങൾ ക്രമേണ ചുരുക്കപ്പെടുന്നു
- **Tool Result Compression** — ദൈർഘ്യമേറിയ tool output-ുകൾ truncate ചെയ്യുകയോ ഒഴിവാക്കുകയോ ചെയ്യുന്നു (ആദ്യ/അവസാന വരികൾ,
  match-line filtering, JSON key compaction)
- **Structural Integrity Guards** — `tool_use` + `tool_result` ജോഡികൾ സ്ഥിരതയോടെ തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്നു
- **Context Window Awareness** — ഓരോ model-ിന്റെയും token പരിധികൾ മാനിക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** ദൈർഘ്യമേറിയ debugging സെഷനുകൾ, വലിയ codebase-ുകൾ.

### അൾട്രാ മോഡ് (~75% ലാഭം)

token-നിർണായക സാഹചര്യങ്ങൾക്കായുള്ള പരമാവധി കംപ്രഷൻ:

- **Heuristic Pruning** — prose-ന്റെ score അടിസ്ഥാനമാക്കിയുള്ള token pruning
- **Structure Preservation** — fenced code block-ുകൾ, inline code, URL-കൾ, identifier-കൾ എന്നിവ tombstone ചെയ്ത്
  മാറ്റമില്ലാതെ വീണ്ടും ചേർക്കുന്നു; ഒരിക്കലും prune ചെയ്യുന്നില്ല
- **Optional SLM tier** — ക്രമീകരിച്ചിരിക്കുമ്പോൾ ഒരു ചെറിയ local model-ന് prune മെച്ചപ്പെടുത്താൻ കഴിയും
- അഗ്രസീവ് മോഡിൽ നിന്ന് സ്വതന്ത്രം: ഇത് message aging, tool-result compression അല്ലെങ്കിൽ fallback summarizer
  പ്രവർത്തിപ്പിക്കുന്നില്ല (ഒരു SLM-tier പരാജയം മാത്രമേ fallback pass-നെ
  അഗ്രസീവ് വഴിയാക്കി റൂട്ട് ചെയ്യുകയുള്ളൂ)

**ഏറ്റവും അനുയോജ്യം:** context പരിധികൾ ആവർത്തിച്ച് നേരിടുമ്പോൾ.

### RTK മോഡ് (അപ്സ്ട്രീം പരിധിയിൽ 60-90%)

coding-agent സെഷനുകളിൽ കാണുന്ന verbose tool output-ുകൾക്കായി RTK മോഡ് ക്രമീകരിച്ചിരിക്കുന്നു:

- `git status`, `git diff`, `git log`, test runner-ുകൾ,
  TypeScript/Vite/Webpack build-ുകൾ, ESLint/Biome/Prettier, npm audit/install-ുകൾ, Docker log-ുകൾ, infra
  output, generic shell output എന്നിവ പോലുള്ള command/output class-ുകൾ കണ്ടെത്തുന്നു
- `open-sse/services/compression/engines/rtk/filters/`-ൽ നിന്നുള്ള JSON filter pack-ുകൾ പ്രയോഗിക്കുന്നു
- project അല്ലെങ്കിൽ global `filters.toml` ഫയലുകളിൽ നിന്നുള്ള RTK TOML schema v1 filter-ുകൾ import ചെയ്യുന്നു, inline-test
  validation-ും project file-ുകൾക്കുള്ള trust-gating-ഉം സഹിതം
- inline verify sample-ുകളുള്ള 56 built-in filter-ുകൾ ഉൾക്കൊള്ളുന്നു
- ANSI control sequence-ുകൾ, progress bar-ുകൾ, ആവർത്തിക്കുന്ന വരികൾ, പ്രവർത്തനക്ഷമമല്ലാത്ത noise എന്നിവ നീക്കം ചെയ്യുന്നു
- failures, errors, warnings, changed files, summaries, ദൈർഘ്യമേറിയ output-ന്റെ tail എന്നിവ നിലനിർത്തുന്നു
- trust-gated project filter-ുകൾ, global filter-ുകൾ, ഐച്ഛികമായി redacted raw-output recovery എന്നിവ പിന്തുണയ്ക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** shell, build, test, git, grep, file-output transcript-ുകളുള്ള agent സെഷനുകൾ.

### സ്റ്റാക്ക്ഡ് മോഡ് (യോഗ്യമായ പരിധിയിൽ 78-95%)

സ്റ്റാക്ക്ഡ് മോഡ് ഒന്നിലധികം compression engine-ുകൾ നിർണായകമായ ക്രമത്തിൽ പ്രവർത്തിപ്പിക്കുന്നു. ഡിഫോൾട്ട് pipeline:

```txt
RTK -> Caveman
```

ഈ ക്രമം ആദ്യം terminal/tool output ചുരുക്കമായി നിലനിർത്തുകയും, തുടർന്ന് ശേഷിക്കുന്ന natural-language prompt-ൽ
Caveman semantic condensation പ്രയോഗിക്കുകയും ചെയ്യുന്നു. സ്റ്റാക്ക്ഡ് pipeline-ുകൾ ആഗോളമായി അല്ലെങ്കിൽ routing combo-കൾക്ക്
assign ചെയ്ത compression combo-കൾ വഴി ക്രമീകരിക്കാം.

**ഏറ്റവും അനുയോജ്യം:** വലിയ tool log-ുകളും മനുഷ്യ നിർദ്ദേശങ്ങളോ assistant summary-കളോ ഉള്ള mixed context.

## അപ്സ്ട്രീം ലാഭത്തിന്റെ കണക്ക്

OmniRoute രണ്ട് ഉറവിടങ്ങളിൽ നിന്നുള്ള കംപ്രഷൻ ലാഭം രേഖപ്പെടുത്തുന്നു: അപ്സ്ട്രീം പ്രോജക്റ്റ് ബെഞ്ച്മാർക്കുകളും
OmniRoute-ന്റെ സ്വന്തം എഞ്ചിൻ സംയോജനവും.

| ഉറവിടം  | ഇവിടെ ഉപയോഗിച്ചിരിക്കുന്ന അപ്സ്ട്രീം README സംഖ്യ                                                                                   |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` കുറവ് ഔട്ട്പുട്ട് ടോക്കണുകൾ, `65%` ബെഞ്ച്മാർക്ക് ശരാശരി ഔട്ട്പുട്ട് ലാഭം, `22-87%` പരിധി, കൂടാതെ `~46%` ഇൻപുട്ട് കംപ്രഷൻ ടൂൾ |
| RTK     | കമാൻഡ്-ഔട്ട്പുട്ടിൽ `60-90%` ലാഭം; സാമ്പിൾ സെഷനിൽ `~118,000 -> ~23,900` ടോക്കണുകൾ, അഥവാ `79.7%` ലാഭം (`~80%`)                       |

ഓവർലാപ്പ് ചെയ്യുന്ന ടൂൾ/കോൺടെക്സ്റ്റ് പേലോഡുകൾക്കായി, ഡിഫോൾട്ട് OmniRoute കോംബോ എഞ്ചിനുകളെ ഒന്നിനുപുറകെ ഒന്നായി പ്രയോഗിക്കുന്നു:

```txt
RTK -> Caveman
```

സംയോജിത ലാഭം അഡിറ്റീവ് അല്ല, മൾട്ടിപ്ലിക്കേറ്റീവ് ആണ്:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK-യ്ക്കും Caveman-നും ഒരേ ഇൻപുട്ട്/കോൺടെക്സ്റ്റ് പേലോഡ് കുറയ്ക്കാൻ കഴിയുമ്പോഴാണ് ആ `78-95%` സംഖ്യ ബാധകമാകുന്നത്.
Caveman റെസ്പോൺസ് ഔട്ട്പുട്ട് മോഡ് വേറിട്ടതാണ്: അത് പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, Caveman-ന്റെ സ്വന്തം ഔട്ട്പുട്ട് ലാഭം (`65%`
ശരാശരി, `~75%` പ്രധാന കണക്ക്, `22-87%` പരിധി) ഉപയോഗിക്കുക. മൊത്തം ബില്ലിംഗ് ലാഭം നിങ്ങളുടെ പ്രോംപ്റ്റ്/ഔട്ട്പുട്ട് അനുപാതത്തെ ആശ്രയിച്ചിരിക്കുന്നു.

### "യോഗ്യമായത്" യഥാർത്ഥത്തിൽ എന്താണ് അർത്ഥമാക്കുന്നത്

15-95% എന്ന പ്രധാന പരിധി യഥാർത്ഥമാണ്, പക്ഷേ അത് **ആവർത്തനമുള്ളതോ അനാവശ്യമായി ദൈർഘ്യമേറിയതോ ആയ** ഉള്ളടക്കത്തിന് മാത്രമാണ് ബാധകമാകുന്നത് — ആവർത്തിക്കുന്ന
പിശക് വരികൾ, ഒരേ മുന്നറിയിപ്പ് നിരന്തരം പ്രദർശിപ്പിക്കുന്ന ബിൽഡ് ലോഗ്, അമിതമായി വലുതായ `grep`/ഫയൽ-റീഡ് ഡമ്പ് എന്നിവയ്ക്ക്.
**എല്ലാ** അഭ്യർത്ഥനകളിലും ഇത്രയും ലാഭമുണ്ടാകുമെന്ന് ഇതിനർത്ഥമില്ല.

പ്രായോഗികമായി സ്ഥിരീകരിച്ചത് (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): സമാനമായ 300
പിശക് വരികൾ അടങ്ങിയ Anthropic-രൂപത്തിലുള്ള `tool_result` ബ്ലോക്കിൽ നടത്തിയ ഒരു `stacked` (RTK + Caveman) റൺ
**95.93% ടോക്കൺ ലാഭം / 96.26% ക്യാരക്ടർ ലാഭം** നൽകി — പരസ്യപ്പെടുത്തിയ പരിധിക്കുള്ളിൽത്തന്നെ.
എന്നാൽ സാധാരണവും ആവർത്തനമില്ലാത്തതുമായ ടൂൾ ഔട്ട്പുട്ടിൽ (വൃത്തിയുള്ള ഒരു `grep` മാച്ച് ലിസ്റ്റ്,
ഹ്രസ്വമായ ഫയൽ റീഡ്, സാധാരണ സംഭാഷണ ടെക്സ്റ്റ്) അതേ പൈപ്പ്ലൈൻ പ്രവർത്തിപ്പിക്കുമ്പോൾ, ശരിയായി **പൂജ്യത്തോട് അടുത്ത ലാഭം** മാത്രമാണ് ലഭിക്കുന്നത്, കാരണം
നീക്കം ചെയ്യാൻ ആവർത്തനമുള്ള ഒന്നുമില്ല; കൂടാതെ കോഡ് ബ്ലോക്കുകൾ, URL-കൾ, തലക്കെട്ടുകൾ, പതിപ്പുകൾ, അല്ലെങ്കിൽ ALL-CAPS കോൺസ്റ്റന്റ് ഐഡന്റിഫയറുകൾ
ഒഴിവാക്കുകയോ മാറ്റുകയോ ചെയ്യുന്ന ഒരു റീറൈറ്റ് അയയ്ക്കാൻ `validateCompression()` (`validation.ts`) അനുവദിക്കില്ല.

ഇത് പ്രതീക്ഷിക്കാവുന്ന സുരക്ഷിതമായ പെരുമാറ്റമാണ്, ബഗ് അല്ല: കംപ്രഷൻ പൂർണ്ണമായി പ്രവർത്തനക്ഷമമാക്കിയിട്ടും, പ്രധാനമായും വൃത്തിയുള്ള ഫയലുകൾ
വായിക്കുകയോ grep ചെയ്യുകയോ ചെയ്യുന്ന ഒരു കോഡിംഗ് സെഷനിൽ മൊത്തത്തിലുള്ള ലാഭം മിതമായിരിക്കും; അതേസമയം, പരാജയപ്പെടുന്ന ഒരു
ലൂപ്പോ അമിതമായി ഔട്ട്പുട്ട് നൽകുന്ന ലിന്ററോ നേരിടുന്ന സെഷനിൽ, ആ ട്രാഫിക്കിൽ പൂർണ്ണമായ 78-95% പരിധിയിലുള്ള ലാഭം ലഭിക്കും. കംപ്രഷൻ തെറ്റായി കോൺഫിഗർ ചെയ്തിരിക്കുന്നു എന്നതിന് തെളിവായി ഒരൊറ്റ സെഷനിലെ
കുറഞ്ഞ മൊത്തം ലാഭശതമാനം ഉപയോഗിക്കരുത് — ആദ്യം അടിസ്ഥാന ടൂൾ ഔട്ട്പുട്ട് യഥാർത്ഥത്തിൽ ആവർത്തനമുള്ളതായിരുന്നോ എന്ന് പരിശോധിക്കുക.

## കോൺഫിഗറേഷൻ

### ഡാഷ്ബോർഡ്

`Dashboard → Context & Cache` എന്നതിലേക്ക് നാവിഗേറ്റ് ചെയ്യുക:

- **Caveman** — മോഡ് തിരഞ്ഞെടുക്കൽ, ഭാഷാ പാക്കുകൾ, പ്രിവ്യൂ, ആഗോള ഡിഫോൾട്ടുകൾ
- **RTK** — കമാൻഡ്-ഫിൽട്ടർ പ്രിവ്യൂ, RTK സുരക്ഷാ ക്രമീകരണങ്ങൾ, ഫിൽട്ടർ കാറ്റലോഗ്
- **Compression Combos** — റൂട്ടിംഗ് കോമ്പോകൾക്ക് നിയോഗിച്ച പേരിട്ട എൻജിൻ പൈപ്പ്ലൈനുകൾ
- **Auto-Trigger Threshold** — ടോക്കൺ എണ്ണം പരിധി കവിയുമ്പോൾ കംപ്രഷൻ സ്വയമേവ സജീവമാക്കുക

### ഓരോ കോമ്പിനുമുള്ള ഓവർറൈഡ്

`Dashboard → Context & Cache → Compression Combos` എന്നതിൽ ഒരു കംപ്രഷൻ കോമ്പോയെ ഒരു റൂട്ടിംഗ്
കോമ്പോയിലേക്ക് നിയോഗിക്കുക:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

പണമടച്ചുള്ള സബ്സ്ക്രിപ്ഷനുകളിൽ lite മോഡ് നിലനിർത്തിക്കൊണ്ട്, സൗജന്യ/കോഡിംഗ് പ്രൊവൈഡറുകളിൽ
സ്റ്റാക്ക് ചെയ്ത കംപ്രഷൻ ഉപയോഗിക്കാൻ ഇത് നിങ്ങളെ അനുവദിക്കുന്നു.

ഈ "Per-Combo Override" നിയോഗം, **routing-combo compression
mode** ഓവർറൈഡിൽ നിന്ന് (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ഫീൽഡിന്റെ
schema `rtk`, `stacked`, `omniglyph` എന്നിവയും സ്വീകരിക്കുന്നു) വ്യത്യസ്തമായ ഒരു നിയന്ത്രണമാണ് — ആ
ഓവർറൈഡ് പേരിട്ട ഒരു compression-combo പൈപ്പ്ലൈൻ തിരഞ്ഞെടുക്കുന്നില്ല; പകരം
`resolveCompressionPlan` പരിശോധിക്കുന്ന `compressionMode` ഫീൽഡ് മാത്രം സജ്ജമാക്കുന്നു. ഇത് കോമ്പോ
കാർഡിൽ (`Dashboard → Combos`) അല്ലെങ്കിൽ #6760 മുതൽ,
`Dashboard → Context & Cache → Compression Combos` എന്നതിലെ "Assign to routing" പട്ടികയിൽ ഓരോ
റൂട്ടിംഗ് കോമ്പിനും സജ്ജമാക്കാം; മുകളിൽ രേഖപ്പെടുത്തിയ പൈപ്പ്ലൈൻ-നിയോഗ ചെക്ക്ബോക്സിന്
തൊട്ടടുത്താണ് ഇത്. രണ്ട് ഇന്റർഫേസുകളും ഒരേ `PUT /api/combos/{id}` എൻഡ്പോയിന്റ് വഴിയാണ്
സംരക്ഷിക്കപ്പെടുന്നത്.

### ഓരോ അഭ്യർത്ഥനയ്ക്കുമുള്ള ഓവർറൈഡ്

ഒറ്റ അഭ്യർത്ഥനയ്ക്കുള്ള കംപ്രഷൻ പ്ലാൻ ഓവർറൈഡ് ചെയ്യാൻ `x-omniroute-compression` അഭ്യർത്ഥന
ഹെഡർ അയയ്ക്കുക. ഇതിന് ഏറ്റവും ഉയർന്ന മുൻഗണനയാണ് — ഇത് റൂട്ടിംഗ്-കോമ്പോ ഓവർറൈഡ്, സജീവമായ
പ്രൊഫൈൽ, ഓട്ടോ-ട്രിഗർ, പാനൽ ഡിഫോൾട്ട് എന്നിവയെ മറികടക്കുന്നു. പരിചയമില്ലാത്ത മൂല്യങ്ങൾ
അവഗണിക്കപ്പെടും (അഭ്യർത്ഥന ഒരിക്കലും നിരസിക്കപ്പെടില്ല); ആഗോള മാസ്റ്റർ സ്വിച്ച് ഇപ്പോഴും
എല്ലാം നിയന്ത്രിക്കുന്നു: ആഗോളമായി കംപ്രഷൻ ഓഫായിരിക്കുമ്പോൾ ഹെഡറിന് അത് ഓൺ ചെയ്യാൻ കഴിയില്ല.
മൂല്യങ്ങൾ:

| Value         | Effect                                                                                                           |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `off`         | ഈ അഭ്യർത്ഥനയ്ക്ക് കംപ്രഷൻ ഇല്ല.                                                                                  |
| `default`     | പാനലിൽ നിന്ന് ലഭിക്കുന്ന Default പ്രൊഫൈൽ (സജീവമായ പ്രൊഫൈലിനെ അവഗണിക്കുന്നു). Lossy എൻജിനുകൾ ഓഫായി തുടരും.        |
| `safe`        | ഹെഡർ ഒഴിവാക്കിയതിന് സമാനം.                                                                                       |
| `allow-lossy` | summaries, relevance filters, style rewrites എന്നിവ ഉൾപ്പെടെ ഈ അഭ്യർത്ഥനയുടെ operator പ്ലാൻ നിലനിർത്തുക.         |
| `engine:<id>` | പ്രാപ്തമാക്കിയിരിക്കുമ്പോൾ ഒരു എൻജിൻ മാത്രം, ഉദാ. `engine:rtk`. ആ എൻജിനുള്ള ഓരോ അഭ്യർത്ഥനയിലുമുള്ള opt-in ഇതാണ്. |
| `<combo>`     | പേരുപ്രകാരം (case-insensitive) ആദ്യം, തുടർന്ന് id പ്രകാരം പൊരുത്തപ്പെടുത്തുന്ന പേരിട്ട കോമ്പോ.                   |

`allow-lossy`, `engine:<id>`, അല്ലെങ്കിൽ പേരിട്ട കോമ്പോ ഇല്ലെങ്കിൽ, lossy എൻജിനുകൾ പ്രയോഗിക്കില്ല.
ഒരു lossy Default, auto-trigger, അല്ലെങ്കിൽ routing override തരംതാഴ്ത്തുമ്പോൾ, കോൺഫിഗർ ചെയ്ത
stacked പൈപ്പ്ലൈനിൽ നിന്നുള്ള തിരിച്ചറിഞ്ഞ lossless ഘട്ടങ്ങൾ കോൺഫിഗർ ചെയ്ത ക്രമത്തിൽ തന്നെ
OmniRoute നിലനിർത്തുന്നു. കോൺഫിഗർ ചെയ്ത lossless ഘട്ടങ്ങളൊന്നും ശേഷിക്കാത്തപ്പോൾ മാത്രമാണ്
`session-dedup → lite` എന്നതിലേക്ക് fallback ചെയ്യുന്നത്.

Settings പാനലിലെ **Effective pipeline** പ്രിവ്യൂ സാധാരണ at-rest പ്ലാൻ കാണിക്കുന്നു. ഒരു
auto-trigger പ്രവർത്തിക്കാൻ കഴിയുമ്പോൾ, അതേ പ്രിവ്യൂ അതിന്റെ conditional effective pipeline-യും
കാണിക്കും; ഇതുവഴി പാനലും ഹെഡർ ഇല്ലാത്ത runtime resolution-ഉം ഒരേ നിലയിൽ തുടരും.

പ്രയോഗിച്ച പ്ലാൻ `X-OmniRoute-Compression: <mode>; source=<source>` എന്ന response
ഹെഡറിൽ തിരിച്ചുനൽകുന്നു; ഇവിടെ `<source>` എന്നത് `request-header`, `routing-override`,
`active-profile`, `auto-trigger`, `default`, അല്ലെങ്കിൽ `off` എന്നിവയിൽ ഒന്നായിരിക്കും.

### API

```bash
# കംപ്രഷൻ ക്രമീകരണങ്ങൾ നേടുക
curl http://localhost:20128/api/settings/compression

# കംപ്രഷൻ ക്രമീകരണങ്ങൾ അപ്ഡേറ്റ് ചെയ്യുക
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ഒരു നിർദ്ദിഷ്ട RTK/stacked payload പ്രിവ്യൂ ചെയ്യുക
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK ഫിൽട്ടർ പാക്കുകൾ പട്ടികപ്പെടുത്തുക
curl http://localhost:20128/api/context/rtk/filters

# ഓപ്ഷണൽ കമാൻഡ് മെറ്റാഡാറ്റയോടെ RTK നേരിട്ട് പരിശോധിക്കുക
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## അംഗീകാരങ്ങൾ

Standard മോഡ് കംപ്രഷൻ നിയമങ്ങൾ **[JuliusBrussee](https://github.com/JuliusBrussee)**-യുടെ **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+)-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ടവയാണ് — വൈറലായ "കുറച്ച് ടോക്കണുകൾകൊണ്ട് കാര്യം നടക്കുമ്പോൾ എന്തിന് കൂടുതൽ ടോക്കണുകൾ ഉപയോഗിക്കണം" എന്ന പ്രോജക്റ്റ്. `~75%` കുറവ് ഔട്ട്പുട്ട് ടോക്കണുകളും, ബെഞ്ച്മാർക്കുകളിൽ ശരാശരി `65%` ഔട്ട്പുട്ട് ലാഭവും, `22-87%` ഔട്ട്പുട്ട് പരിധിയും, `~46%` ഇൻപുട്ട്-കംപ്രഷൻ ടൂളും Caveman റിപ്പോർട്ട് ചെയ്യുന്നു.

RTK മോഡ് **[RTK AI](https://github.com/rtk-ai)**-യുടെ **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)**-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ടതാണ് — ടെർമിനൽ, ബിൽഡ്, ടെസ്റ്റ്, git, ടൂൾ-ഔട്ട്പുട്ട് ഫിൽട്ടറിംഗ് എന്നിവയ്ക്കായുള്ള ഉയർന്ന പ്രകടനമുള്ള കമാൻഡ്-ഔട്ട്പുട്ട് കംപ്രഷൻ പ്രോജക്റ്റ്. RTK `60-90%` ലാഭം റിപ്പോർട്ട് ചെയ്യുന്നു; അതിന്റെ README സാമ്പിൾ സെഷനിൽ `~80%` ലാഭിച്ചതായി കാണിക്കുന്നു.

## വിപുലമായ കംപ്രഷൻ സിസ്റ്റങ്ങൾ

മുകളിൽ വിവരിച്ച 7 മോഡുകൾക്കപ്പുറം (സ്രോതസ്സ് `codex-responses`, `omniglyph` മോഡുകൾ സ്വീകരിക്കുന്നു, ഈ ഗൈഡ് ഉൾക്കൊള്ളുന്നില്ല), ആ മോഡുകൾക്കുള്ളിലോ അതിനോടൊപ്പമോ പ്രവർത്തിക്കുന്ന ഫീച്ചറുകൾ ചുവടെയുള്ള വിഭാഗങ്ങൾ ഉൾക്കൊള്ളുന്നു: ടൂൾ റിസൾട്ട് കംപ്രഷനും പ്രോഗ്രസീവ് ഏജിംഗും ആക്രമണാത്മക എഞ്ചിൻ്റെ 1, 2 ഘട്ടങ്ങളാണ് (അഗ്രസീവ് മോഡ്, ഒരു `aggressive` പൈപ്പ്ലൈൻ സ്റ്റെക്ക്, സ്റ്റെക്ക്ഡ് പൈപ്പ്ലൈൻ പ്രവർത്തിക്കുന്നു), സ്റ്റാക്ക് മോഡ്, സ്റ്റക്ക്ഡ് പൈപ്പ്ലൈൻ എങ്ങനെ പ്രവർത്തിക്കുന്നു. കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ കാഷിംഗ് ദാതാക്കൾക്കായി Cache-Aware Compression `aggressive`, `ultra` എന്നിവയെ `standard` ലേക്ക് തരംതാഴ്ത്തുന്നു, കൂടാതെ കേവ്മാൻ ഔട്ട്പുട്ട് മോഡും ഔട്ട്പുട്ട് ശൈലികളും ഓപ്റ്റ്-ഇൻ സിസ്റ്റം-പ്രോംപ്റ്റ് നിർദ്ദേശങ്ങളാണ്, ഡിഫോൾട്ടായി ഓഫാണ്, അത് അഭ്യർത്ഥന കംപ്രസ്സുചെയ്യുന്നതിന് പകരം മോഡലിൻ്റെ ഔട്ട്പുട്ടിനെ രൂപപ്പെടുത്തുന്നു.

### കാഷെ-അവെയർ കംപ്രഷൻ

ചില ദാതാക്കൾ (പ്രോംപ്റ്റ് കാഷിംഗ് ഉള്ള Anthropic പോലെ) പിന്തുണ** പെട്ടെന്നുള്ള കാഷിംഗ്** , ചെലവും കാലതാമസവും കുറയ്ക്കുന്നതിന് പ്രോംപ്റ്റിൻ്റെ ഭാഗങ്ങൾ കാഷെ ചെയ്യാൻ ഇത് അവരെ അനുവദിക്കുന്നു. കാഷിംഗ് പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ, യഥാർത്ഥത്തിൽ ആക്രമണാത്മക കംപ്രഷൻ സാധ്യമാണ്** വേദനിപ്പിച്ചു** കാഷെ അസാധുവാക്കിക്കൊണ്ട് കാഷെ ചെയ്ത ടോക്കണുകൾ മാറ്റുന്നതിനാൽ പ്രകടനം.

`cachingAware.ts` മൊഡ്യൂൾ ഇത് പരിഹരിക്കുന്നു** കാഷിംഗ് സന്ദർഭം കണ്ടെത്തുന്നു** ഒപ്പം** കംപ്രഷൻ തന്ത്രം ക്രമീകരിക്കുന്നു** അതനുസരിച്ച്.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

1. **കാഷിംഗ് സന്ദർഭം കണ്ടെത്തുക** — `cache_control` മാർക്കറുകൾക്കായുള്ള അഭ്യർത്ഥന ബോഡി സ്കാൻ ചെയ്യുന്നു
2. **കാഷിംഗ് ദാതാക്കളെ തിരിച്ചറിയുക** ടാർഗെറ്റ് പ്രൊവൈഡർ കാഷിംഗ് പിന്തുണയ്ക്കുന്നുണ്ടോയെന്ന് — പരിശോധിക്കുന്നു
3. **തന്ത്രം ക്രമീകരിക്കുക** കാഷിംഗ് ദാതാക്കൾക്കായി — `aggressive`/`ultra` ലേക്ക് `standard` തരം താഴ്ത്തുന്നു
4. **സിസ്റ്റം പ്രോംപ്റ്റ് ഒഴിവാക്കുക** — സിസ്റ്റം പ്രോംപ്റ്റുകൾ സാധാരണയായി കാഷെ ചെയ്യപ്പെടുന്നു, അതിനാൽ അവയെ കംപ്രസ് ചെയ്യരുത്

സ്ട്രാറ്റജി ഹെൽപ്പറും ഒരു `deterministicOnly` ഫ്ലാഗ് തിരികെ നൽകുന്നു, എന്നാൽ പ്ലാൻ ബിൽഡർ സ്ട്രാറ്റജി — മാത്രമേ ഉപയോഗിക്കുന്നുള്ളൂ, താഴെയുള്ള ഒന്നും ഇന്ന് ഫ്ലാഗ് വായിക്കുന്നില്ല.

#### കോഡ് ഉദാഹരണം

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### എപ്പോൾ ഉപയോഗിക്കണം

Cache-aware compression ആണ്** എപ്പോഴും ഓണാണ്** — കോൺഫിഗറേഷൻ ആവശ്യമില്ല. കംപ്രഷൻ ഓണായിരിക്കുമ്പോഴെല്ലാം ഇത് കിക്ക് ഇൻ ചെയ്യുന്നു, കൂടാതെ ടാർഗെറ്റ് പ്രൊവൈഡർ പ്രോംപ്റ്റ് കാഷിംഗ് പിന്തുണയ്ക്കുന്നു (Anthropic, OpenAI, മുതലായവ); വ്യക്തമായ `cache_control` മാർക്കറുകൾ ആവശ്യമില്ല — ഒരു കാഷിംഗ് പ്രൊവൈഡർ മാത്രം ഡൗൺഗ്രേഡ് ട്രിഗർ ചെയ്യുന്നു, മാർക്കറുകൾ മാത്രം ഒരിക്കലും ചെയ്യില്ല (മാർക്കർ കണ്ടെത്തൽ കാഷെ ടെലിമെട്രിയെ ഫീഡ് ചെയ്യുന്നു, തന്ത്രപരമായ തീരുമാനമല്ല).

`anthropic/*` മോഡലുകൾക്കായി മാത്രംOpenRouter ഒരു കാഷിംഗ് പ്രൊവൈഡറായി കണക്കാക്കുന്നു: Claude കോഡ് അഭ്യർത്ഥനകൾ അവയുടെ `cache_control` ബ്രേക്ക്പോയിൻ്റുകൾ (ഏറ്റവും 4) നിലനിർത്തുകയും ഗാർഡ് പ്രിഫിക്സ് പരിരക്ഷിക്കുകയും ചെയ്യുന്നു, അതേസമയം മറ്റെല്ലാ OpenRouter കുടുംബവും (`openai/`, `google/`, `qwen/`, …) സ്ട്രിപ്പ് ചെയ്യപ്പെടുകയും സംരക്ഷിക്കപ്പെടാതിരിക്കുകയും ചെയ്യുന്നു.

### പുരോഗമന വാർദ്ധക്യം

ദൈർഘ്യമേറിയ സംഭാഷണങ്ങൾ നിരവധി സന്ദേശ തിരിവുകൾ ശേഖരിക്കുന്നു, എന്നാൽ പഴയ തിരിവുകൾക്ക് പ്രസക്തി കുറയുന്നു. `progressiveAging.ts` മൊഡ്യൂൾ** ടേൺ ദൂരം അനുസരിച്ച് സന്ദേശങ്ങളെ തരംതാഴ്ത്തുന്നു** (സംഭാഷണത്തിൻ്റെ അവസാനം മുതൽ അളക്കുന്ന ദൂരം). ഷിപ്പ് ചെയ്ത ഡിഫോൾട്ടുകൾക്കൊപ്പം (`verbatim: 2, light: 2, moderate: 3`):

- **അവസാന 2 തിരിവുകൾ (ദൂരം ≤ 2)** : അക്ഷരാർത്ഥത്തിൽ സൂക്ഷിച്ചു
- **ദൂരം 3** : കേവ്മാൻ കംപ്രഷൻ (ഫില്ലർ നീക്കം)
- **ദൂരം 4 +** : അസിസ്റ്റൻ്റ് സന്ദേശങ്ങൾ സംഗ്രഹിച്ചു; ഉപയോക്തൃ സന്ദേശങ്ങൾ അവയുടെ ആദ്യ വരിയിലേക്ക് ചുരുക്കി, 120 പ്രതീകങ്ങൾ; മറ്റ് റോളുകൾ സ്പർശിക്കാത്തതാണ്. സിസ്റ്റം നിർദ്ദേശങ്ങൾ, ഇതിനകം പ്രായമായ സന്ദേശങ്ങൾ, ഏറ്റവും പുതിയ ഉപയോക്തൃ സന്ദേശങ്ങൾ എന്നിവ ദൂരം പരിഗണിക്കാതെ എപ്പോഴും പദാനുപദമായി സൂക്ഷിക്കുന്നു. ഒന്നും പൂർണ്ണമായി ഉപേക്ഷിക്കപ്പെടുന്നില്ല, കൂടാതെ ഷിപ്പ് ചെയ്ത ഡിഫോൾട്ടുകളിൽ (`light` സമം `verbatim`) `light` ബാൻഡിൽ എത്തിച്ചേരാനാകില്ല.

#### കോഡ് ഉദാഹരണം

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### എപ്പോൾ ഉപയോഗിക്കണം

പുരോഗമന വാർദ്ധക്യം ആണ്** എപ്പോഴും ഓൺ** `aggressive` മോഡ് — ന് ഇത് `compressAggressive()` യുടെ രണ്ടാം ഘട്ടമാണ്. അൾട്രാ മോഡ് ഇത് പ്രവർത്തിപ്പിക്കുന്നില്ല. ഇത് പ്രത്യേകിച്ച് ഫലപ്രദമാണ്:

- ദീർഘകാല കോഡിംഗ് സെഷനുകൾ
- ഒന്നിലധികം ദിവസത്തെ സംഭാഷണങ്ങൾ
- നിരവധി ടൂൾ കോളുകളുള്ള ഏജൻ്റ് വർക്ക്ഫ്ലോകൾ

### കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ്

കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ് കൂട്ടിച്ചേർക്കുന്നു** സിസ്റ്റം പ്രോംപ്റ്റ് നിർദ്ദേശങ്ങൾ** അത് മോഡലിനോട് തന്നെ ടെഴ്സ് ഔട്ട്പുട്ട് — ആവശ്യപ്പെടുന്നു, `lite` ലെവൽ പൂർണ്ണ വാക്യങ്ങൾ സൂക്ഷിക്കുന്ന സംക്ഷിപ്ത ഉത്തരങ്ങൾ ആവശ്യപ്പെടുന്നു, `full` അതിനോട് "സ്മാർട്ട് ഗുഹാമനുഷ്യനെപ്പോലെ പ്രതികരിക്കാൻ" ആവശ്യപ്പെടുന്നു, കൂടാതെ `ultra` ടെലിഗ്രാഫിക് ഔട്ട്പുട്ടിനായി ആവശ്യപ്പെടുന്നു; നിർദ്ദേശങ്ങൾ മാത്രമേ ചോദിക്കൂ, അവർക്ക് അത് ഉറപ്പുനൽകാൻ കഴിയില്ല. അഭ്യർത്ഥനകൾ `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) വഴി സ്വീകരിക്കുന്നു: `open-sse/handlers/chatCore.ts` ആദ്യം ബാക്ക്-കോംപാറ്റ് ഷിം ( `open-sse/services/compression/outputStyles/backCompat.ts` ൽ `resolveOutputStyleSelection()` ) ഉപയോഗിച്ച് തിരഞ്ഞെടുക്കൽ പരിഹരിക്കുന്നു, ഇത് `outputStyles` ശൂന്യമാണെങ്കിലും, `cavemanOutputMode.intensity` ലെ `terse-prose` ഔട്ട്പുട്ട് ശൈലിയിലേക്ക് പ്രാപ്തമാക്കിയ `cavemanOutputMode` മാപ്പ് ചെയ്യുന്നു (ചുവടെയുള്ള ബാക്ക്-കോംപാറ്റ് കാണുക); ശൂന്യമല്ലാത്ത `outputStyles` സെലക്ഷൻ അതേപടി ഉപയോഗിക്കുന്നു, `cavemanOutputMode.enabled`, `intensity` എന്നിവയ്ക്ക് പിന്നീട് യാതൊരു ഫലവുമില്ല, അതേസമയം അതിൻ്റെ `autoClarity` ടോഗിൾ ഇപ്പോഴും ബാധകമാണ്. ഇൻസ്ട്രക്ഷൻ ടെക്സ്റ്റുകൾ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), ഉള്ളടക്ക ബൈപാസ്, കുത്തിവയ്പ്പ് ഉപയോഗിക്കുന്ന പ്ലേസ്മെൻ്റ് ഹെൽപ്പർ എന്നിവ `outputMode.ts` കൈവശം വച്ചിരിക്കുന്നു; സ്വന്തം `applyCavemanOutputMode()` ഇൻജക്ടറിന് പ്രൊഡക്ഷൻ കോളർ ഇല്ല.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

ഈ മോഡ് ഇൻപുട്ട് കംപ്രസ് ചെയ്യുന്നില്ല. ഇത് സിസ്റ്റം പ്രോംപ്റ്റിലേക്ക് ഒരു ഇൻസ്ട്രക്ഷൻ ബ്ലോക്ക് ചേർക്കുന്നു (ചുവടെയുള്ള കുത്തിവയ്പ്പ് എങ്ങനെ പ്രവർത്തിക്കുന്നു എന്ന് കാണുക), അഭ്യർത്ഥനയ്ക്കായി തിരഞ്ഞെടുത്ത ഏതെങ്കിലും ഇൻപുട്ട് കംപ്രഷൻ മോഡ് അതിനുശേഷം പ്രവർത്തിക്കുന്നു, ഇപ്പോൾ ബ്ലോക്ക് വഹിക്കുന്ന ബോഡിയിൽ. എല്ലാ ലെവലും അവസാനിക്കുന്ന പങ്കിട്ട അതിരുകൾ ക്ലോസിനു മുന്നിൽ, ഇംഗ്ലീഷ് `full` ലെവൽ ഇങ്ങനെ വായിക്കുന്നു:

> "സ്മാർട്ട് ഗുഹാമനുഷ്യനെപ്പോലെ രൂക്ഷമായി പ്രതികരിക്കുക. ഡ്രോപ്പ് ലേഖനങ്ങൾ (a/an/the), ഫില്ലർ (just/really/basically/actually/simply), pleasantries, ഹെഡ്ജിംഗ്. ശകലങ്ങൾ OK. ഹ്രസ്വ പര്യായങ്ങൾ (വലുത് വിസ്തൃതമല്ല, ശരിയാക്കുക നടപ്പിലാക്കില്ല). എല്ലാ സാങ്കേതിക പദാർത്ഥങ്ങളും, കോഡും, പിശകുകളും, URLs, ഐഡൻ്റിഫയറുകളും കൃത്യമായി സൂക്ഷിക്കുക."

ഇത് പ്രത്യേകിച്ചും നന്നായി പ്രവർത്തിക്കുന്നു:

- കോഡ് ജനറേഷൻ (ടെസർ ഔട്ട്പുട്ട് = കുറച്ച് ടോക്കണുകൾ)
- ദ്രുത ചോദ്യോത്തരം (വിശദമായ വിശദീകരണങ്ങളുടെ ആവശ്യമില്ല)
- ബാച്ച് പ്രോസസ്സിംഗ് (പരമാവധി ത്രൂപുട്ട്)

#### എപ്പോൾ ഉപയോഗിക്കണം

കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ് ആണ്** തിരഞ്ഞെടുക്കൽ** . കംപ്രഷൻ ഓൺ ഉപയോഗിച്ച് (`enabled: true`, കംപ്രഷൻ ക്രമീകരണ പേജിലെ മാസ്റ്റർ ടോഗിൾ), `cavemanOutputMode.enabled` ഉപയോഗിച്ച് അത് ഓണാക്കുക; `intensity` `lite`, `full` അല്ലെങ്കിൽ `ultra` തിരഞ്ഞെടുക്കുന്നു:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ഒരു കംപ്രഷൻ കോമ്പോസ്** ഔട്ട്പുട്ട് മോഡ്** ടോഗിൾ (`outputMode`, `outputModeIntensity` ലെ ലെവൽ) കോംബോ ബാധകമായ അഭ്യർത്ഥനകൾക്ക് ഒരേ സ്വിച്ച് സജ്ജമാക്കുന്നു, കൂടാതെ `omniroute_set_compression_engine` MCP ടൂൾ അതിൻ്റെ ബൂളിയൻ `outputMode` ആർഗ്യുമെൻ്റിലൂടെ അത് എഴുതുന്നു. ഈ സ്വിച്ചിനെക്കാൾ ശൂന്യമല്ലാത്ത `outputStyles` തിരഞ്ഞെടുക്കൽ മുൻഗണന നൽകുന്നു. ഡാഷ്ബോർഡിൽ, പ്രവർത്തനക്ഷമമാക്കുന്നു** തീവ്രമായ ഗദ്യം** ഔട്ട്പുട്ട് ശൈലി അതേ ബ്ലോക്ക് കുത്തിവയ്ക്കുന്നു (ചുവടെയുള്ള ഔട്ട്പുട്ട് ശൈലികൾ കാണുക).

#### കുത്തിവയ്പ്പ് എങ്ങനെ പ്രവർത്തിക്കുന്നു

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) കാറ്റലോഗിന് എതിരായ തിരഞ്ഞെടുപ്പ് പരിഹരിക്കുന്നു (അജ്ഞാത ഐഡികളും ലോക്കൽ-പൊരുത്തമില്ലാത്ത ശൈലികളും ഒഴിവാക്കപ്പെടുന്നു, ഒരിക്കലും ഒരു പിശക്; ഒരു ശൈലിയും പരിഹരിക്കാത്ത ഒരു തിരഞ്ഞെടുപ്പ് ബോഡി മാറ്റമില്ലാതെ തുടരുന്നു, `no_styles` ആയി ഒഴിവാക്കുന്നു), തിരഞ്ഞെടുത്ത നിർദ്ദേശങ്ങൾ കാറ്റലോഗ് ക്രമത്തിൽ സംയോജിപ്പിക്കുന്നു, അതിരുകൾ ക്ലോസ് കൂട്ടിച്ചേർക്കുന്നു** ഒരിക്കൽ** (സുരക്ഷാ ക്ലോസ്, `SAFETY_BOUNDARIES` അല്ലെങ്കിൽ അതിൻ്റെ വിവർത്തനം, `less-code` അല്ലെങ്കിൽ `ponytail` തിരഞ്ഞെടുക്കുമ്പോൾ), കൂടാതെ ഒരൊറ്റ ഐഡമ്പോട്ടൻസി മാർക്കർ (`[OmniRoute Output Styles]`) ഉപയോഗിച്ച് ബ്ലോക്ക് ആരംഭിക്കുന്നു, അതിനാൽ വീണ്ടും പ്രയോഗിക്കുന്നത് ഒരു ഓപ് ആണ്. പരിഹരിച്ച ഭാഷയ്ക്ക് (ചുവടെയുള്ള ഭാഷ തിരഞ്ഞെടുക്കൽ കാണുക) ഒരു വിവർത്തനം ഉള്ളപ്പോൾ, ഇംഗ്ലീഷിന് പകരം പ്രാദേശികവൽക്കരിച്ച നിർദ്ദേശം കുത്തിവയ്ക്കുന്നു.

ശൂന്യമല്ലാത്ത `messages` അറേ ഉള്ള ഒരു ബോഡിയിൽ, ഉള്ളടക്കം ബൈപാസിന് മുമ്പായി ഐഡമ്പോട്ടൻസി പരിശോധന പ്രവർത്തിക്കുന്നു: `[OmniRoute Output Styles]` മാർക്കർ ഇതിനകം തന്നെ ഉയർന്ന തലത്തിലുള്ള `system` ഫീൽഡിലോ (ഒരു സ്ട്രിംഗ് അല്ലെങ്കിൽ ഒരു ഉള്ളടക്ക-ബ്ലോക്ക് അറേ) അല്ലെങ്കിൽ സ്ട്രിംഗ് ഉള്ളടക്കമുള്ള ഒരു സിസ്റ്റം സന്ദേശത്തിലോ ആയിരിക്കുമ്പോൾ, ബോഡി മാറ്റമില്ലാതെ `already_applied` ആയി പ്രവർത്തിക്കുന്നു, കീവേഡ് പരിശോധിക്കുന്നില്ല. അല്ലാത്തപക്ഷം, ഒരു ഉള്ളടക്ക ബൈപാസ് (`shouldBypassCavemanOutputMode()` ഇൻ `open-sse/services/compression/outputMode.ts`) അവസാനത്തെ മൂന്ന് സന്ദേശങ്ങളുടെ വാചകം, അവയുടെ റോൾ എന്തുതന്നെയായാലും പരിശോധിച്ച്, ആ ടെക്സ്റ്റ് അതിൻ്റെ സുരക്ഷ, മാറ്റാനാകാത്ത-പ്രവർത്തനം അല്ലെങ്കിൽ ക്ലാരിഫിക്കേഷൻ കീവേഡുകൾ, അല്ലെങ്കിൽ ഒരു ഓർഡർ-സെൻസിറ്റീവ് സീക്വൻസ് എന്നിവയുമായി പൊരുത്തപ്പെടുമ്പോൾ മുഴുവൻ ടേണിനുമുള്ള ശൈലികൾ ഒഴിവാക്കുന്നു: `first`, `then`, `after that` `deploy` `before` ഉള്ളിൽ `delete`, `drop`, `migrate`, `rollback` അല്ലെങ്കിൽ `backup` പ്രകാരം `release` പ്രതീകങ്ങൾ. അതേസമയം ബൈപാസ് ഓടുന്നു** യാന്ത്രിക-വ്യക്തത ബൈപാസ്** ടോഗിൾ (`cavemanOutputMode.autoClarity`, സ്ഥിരസ്ഥിതിയായി ഓൺ) ഓണാണ്; ടോഗിൾ ഓഫ് ചെയ്യുന്നത് കീവേഡ് പരിശോധന ഒഴിവാക്കുന്നു.

ബൈപാസ് വഴി തിരിയാൻ അനുവദിക്കുമ്പോൾ, ഒരിക്കലും ഒരു പുതിയ `messages[0]` സൃഷ്ടിക്കാത്ത `placeSystemInstruction()` (അതേ ഫയൽ), അത് കണ്ടെത്തുന്ന ഇവയിൽ ആദ്യത്തേതിൽ ബ്ലോക്ക് സ്ഥാപിക്കുന്നു:

1. സ്ട്രിംഗ് ഉള്ളടക്കമുള്ള ഒരു മുൻനിര സിസ്റ്റം സന്ദേശം: ബ്ലോക്ക് അതിൻ്റെ വാചകത്തിന് ശേഷം ചേർത്തിരിക്കുന്നു.
2. ടോപ്പ്-ലെവൽ `system` ഫീൽഡ്: ഒരു സ്ട്രിംഗിൻ്റെ ടെക്സ്റ്റിന് ശേഷം ബ്ലോക്ക് ചേർക്കുന്നു, അല്ലെങ്കിൽ ഒരു ഉള്ളടക്ക-ബ്ലോക്ക് അറേയിലേക്ക് ഒരു പുതിയ ടെക്സ്റ്റ് ബ്ലോക്കായി ചേർക്കുന്നു.
3. സ്ട്രിംഗ് ഉള്ളടക്കമുള്ള ആദ്യത്തെ പിന്നീടുള്ള സിസ്റ്റം സന്ദേശം: ബ്ലോക്ക് അതിൻ്റെ ടെക്സ്റ്റിന് ശേഷം ചേർത്തിരിക്കുന്നു.
4. മുകളിൽ പറഞ്ഞവ ഒന്നുമല്ല: ബ്ലോക്ക് `messages` യുടെ അവസാനം ഒരു പുതിയ സിസ്റ്റം സന്ദേശത്തിലേക്ക് പോകുന്നു.

`messages` അറേ ഇല്ലാത്ത (അല്ലെങ്കിൽ ശൂന്യമായ ഒരു ബോഡിയിൽ), ഉള്ളടക്കം ബൈപാസ് റണ്ണുകളൊന്നും കൂടാതെ ഒരു ഉയർന്ന തലത്തിലുള്ള `system` ഫീൽഡ് കൂടിയാലോചിക്കുന്നില്ല. ഒരു സ്ട്രിംഗ് `instructions` ഫീൽഡിൻ്റെ ടെക്സ്റ്റിന് ശേഷം ബ്ലോക്ക് ചേർക്കുന്നു, ആ ഫീൽഡിൽ ഇതിനകം `[OmniRoute Output Styles]` മാർക്കർ അടങ്ങിയിട്ടില്ലെങ്കിൽ, ബോഡി മാറ്റമില്ലാതെ `already_applied` ആയി അവശേഷിക്കുന്നു. ബോഡിക്ക് സ്ട്രിംഗ് `instructions` ഫീൽഡ് ഇല്ലെങ്കിലും `input` (ഒരു സ്ട്രിംഗ് അല്ലെങ്കിൽ ഒരു അറേ) വഹിക്കുമ്പോൾ, ബ്ലോക്ക് `instructions` ആയി മാറുന്നു, ഫീൽഡ് കൈവശമുള്ള ഏതെങ്കിലും നോൺ-സ്ട്രിംഗ് മൂല്യത്തെ മാറ്റിസ്ഥാപിക്കുന്നു. ഒരു സ്ട്രിംഗ് `instructions` ഫീൽഡോ സ്ട്രിംഗോ അറേയോ `input` ഇല്ലാത്ത ഒരു ബോഡി മാറ്റമില്ലാതെ ഉപേക്ഷിക്കുകയും `no_messages` ആയി ഒഴിവാക്കുകയും ചെയ്യുന്നു.

#### എങ്ങനെ പ്രവർത്തനക്ഷമമാക്കാം

ഡാഷ്ബോർഡിൽ:** കംപ്രഷൻ സന്ദർഭം → കംപ്രഷൻ ക്രമീകരണങ്ങൾ** (`/dashboard/context/settings`), ഔട്ട്പുട്ട് ശൈലികൾ വിഭാഗം: on/off ടോഗിളും ഒരു ലെവൽ സെലക്ടറും ഉള്ള ഓരോ സ്റ്റൈലിനും ഒരു വരി. കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ ശൈലികൾ കുത്തിവയ്ക്കുന്നു (പേജിൻ്റെ മാസ്റ്റർ ടോഗിൾ, `enabled`). ദി** യാന്ത്രിക-വ്യക്തത ബൈപാസ്** ടോഗിൾ ആണ്** ഗുഹാമനുഷ്യൻ** പേജ് (`/dashboard/context/caveman`), അതിൽ** ഔട്ട്പുട്ട് മോഡ്** കാർഡ്. പ്രോഗ്രമാറ്റിക്കായി, കംപ്രഷൻ കോൺഫിഗറേഷൻ തിരഞ്ഞെടുക്കൽ തുടരുന്നു:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ബാക്ക്-കോംപാറ്റ്: `outputStyles` ശൂന്യമായിരിക്കുമ്പോൾ, ലെഗസി `cavemanOutputMode.enabled` `cavemanOutputMode.intensity` ൽ `terse-prose` ലേക്ക് മാപ്പുകൾ ക്രമീകരിക്കുന്നു. ബ്ലോക്ക് പിന്നീട് ആരംഭിക്കുന്നത് `[OmniRoute Output Styles]` മാർക്കറിൽ നിന്നാണ്, അവിടെ ലെഗസി `applyCavemanOutputMode()` ഇൻജക്ടർ `[OmniRoute Caveman Output Mode]` എന്ന് എഴുതിയിരിക്കുന്നു. മാർക്കറിന് താഴെ, en, pt-BR, es, de, fr, it, ru, id, vi എന്നിവയിലെ ലെഗസി ഇഞ്ചക്ഷനുമായി ടെക്സ്റ്റ് പൊരുത്തപ്പെടുന്നു; ja, zh എന്നിവയിൽ ഇത് അതിരുകൾ ക്ലോസിന് മുമ്പ് ഒരു അധിക ഇടം വഹിക്കുന്നു. `terse-prose` എന്നത് pt-BR, es, de, fr, it, ru, zh, ja, id, vi എന്നിങ്ങനെ വിവർത്തനം ചെയ്യുന്നു, അതിനാൽ `hu` എന്ന പരിഹരിച്ച ഭാഷയിലുള്ള ഒരു അഭ്യർത്ഥനയ്ക്ക് ഇംഗ്ലീഷ് ടെക്സ്റ്റ് ലഭിക്കുന്നു, അവിടെ ലെഗസി ഇൻജക്റ്റർ അതിൻ്റെ ഹംഗേറിയൻ ഉപയോഗിച്ചു.

ഔട്ട്പുട്ട് ശൈലിയിലുള്ള ഭാഷാ തിരഞ്ഞെടുപ്പ് (`resolveOutputStyleLanguage()` ൽ `outputStyles/apply.ts`): `languageConfig.enabled` ഓണാക്കി, അഭ്യർത്ഥനയുടെ `messages` അറേയിലെ ഏറ്റവും പുതിയ ഉപയോക്തൃ സന്ദേശം `autoDetect` സാമ്പിൾ ചെയ്യുന്നു, അത് ടെക്സ്റ്റ് (സ്ട്രിംഗ് ഉള്ളടക്കം അല്ലെങ്കിൽ അതിൻ്റെ ഉള്ളടക്ക ഭാഗങ്ങളുടെ `text` ) ഉള്ളതും അതിൽ കേവ്മാൻ എഞ്ചിൻ്റെ ഡിറ്റക്ടർ (`detectCompressionLanguage()`) പ്രവർത്തിപ്പിക്കുന്നതും. ഹാൻ പ്രതീകങ്ങളുള്ളതും കാന ഇല്ലാത്തതുമായ ടെക്സ്റ്റിനായി ഡിറ്റക്ടർ `zh` നൽകുന്നു; അല്ലാത്തപക്ഷം `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu`, `id` എന്നിവയിൽ ഏതാണ് കൂടുതൽ സൂചന പൊരുത്തങ്ങൾ ഉള്ളത് അത് തിരികെ നൽകുന്നു, കൂടാതെ `en` ടെക്സ്റ്റ് വർഗ്ഗീകരിക്കാൻ കഴിയാത്തപ്പോൾ — ടെക്സ്റ്റ് ഇംഗ്ലീഷിൽ ലഭിക്കുന്നില്ല, `defaultLanguage` `vi` `vi` കണ്ടെത്തില്ല. ഒരു പ്രതികരണങ്ങൾ API ബോഡി അതിൻ്റെ തിരിവുകൾ `input` ൽ സൂക്ഷിക്കുന്നു, അത് സാമ്പിൾ ചെയ്യാത്തതിനാൽ അത് `defaultLanguage` മാറുന്നു, തുടർന്ന് ഇംഗ്ലീഷ്. `messages` ൽ ഒരു ഉപയോക്തൃ സന്ദേശത്തിനും ടെക്സ്റ്റ് ഇല്ലാത്തപ്പോൾ അല്ലെങ്കിൽ `autoDetect` ഓഫായിരിക്കുമ്പോൾ, `defaultLanguage` ബാധകമാകും, തുടർന്ന് ഇംഗ്ലീഷ്. `languageConfig.enabled` ഓഫാണെങ്കിൽ, അഭ്യർത്ഥനയ്ക്ക് ഒരു കംപ്രഷൻ കോംബോ ബാധകമാകുന്നില്ലെങ്കിൽ ഭാഷ ഇംഗ്ലീഷ് — ആണ് (അഭ്യർത്ഥനയുടെ റൂട്ടിംഗ് കോംബോയിലേക്ക് അസൈൻ ചെയ്തിരിക്കുന്ന ഒരു കോംബോ, അല്ലെങ്കിൽ ബിൽറ്റ്-ഇൻ സ്റ്റാക്ക് ചെയ്ത പൈപ്പ്ലൈനിലേക്ക് ഡിഫോൾട്ട് കംപ്രഷൻ കോംബോ chatCore വീഴുന്നു): ഒരു കോംബോ പ്രയോഗിക്കുന്നത് ആ അഭ്യർത്ഥനയ്ക്കായി `languageConfig.enabled` ൽ നിന്ന് `defaultLanguage` മൂല്യം സംരക്ഷിക്കുന്നു. ഇത് കോമ്പോയുടെ പാക്കുകളിൽ ഒന്നാണെങ്കിൽ, അല്ലാത്തപക്ഷം കോംബോയുടെ ആദ്യ പായ്ക്ക്, അത് `en` ലേക്ക് സ്ഥിരസ്ഥിതിയായി മാറുന്നു, അതേസമയം സംരക്ഷിച്ച `autoDetect` (സ്ഥിരസ്ഥിതിയായി ഓൺ) ഇപ്പോഴും ബാധകമാണ്. കേവ്മാൻ ഇൻപുട്ട് എഞ്ചിൻ അതിൻ്റെ റൂൾ-പാക്ക് ഭാഷ ഓരോ ടെക്സ്റ്റ് ഭാഗത്തിനും വ്യത്യസ്തമായി — തിരഞ്ഞെടുക്കുന്നു, കൂടാതെ സ്വയമേവ കണ്ടെത്തൽ ഓഫായി `enabledPacks` ൽ ഗേറ്റ് ചെയ്തു.

The style × language matrix is pinned by `tests/unit/compression/output-styles-i18n-matrix.test.ts`: every catalog style needs an entry in the test's `BASELINE_LANGUAGES`; a style that is not locale-gated must ship a pt-BR translation (the locale-gated `terse-cjk` is exempt from this rule) unless it is listed in `KNOWN_ENGLISH_ONLY`, which may hold only styles with no translations at all — a listed style that has any translation fails the test; and a style fails the test when it loses a language that its `BASELINE_LANGUAGES` entry lists. To add a style, see [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### ടൂൾ റിസൾട്ട് കംപ്രഷൻ

`open-sse/services/compression/toolResultCompressor.ts` ലെ`compressToolResult()` ടൂൾ-ഫല ടെക്സ്റ്റ് കംപ്രസ് ചെയ്യുന്നു** 5 തന്ത്രങ്ങൾ** . ഇത് ഈ ക്രമത്തിൽ അവരെ പരീക്ഷിക്കുന്നു, കൂടാതെ ഉള്ളടക്കവുമായി പൊരുത്തപ്പെടുന്ന ആദ്യ പ്രവർത്തന തന്ത്രം ഫലം തീരുമാനിക്കുന്നു:

1. **`fileContent`** : ലീഡിംഗ് ഇൻഡൻ്റേഷൻ അവഗണിച്ച്, കുറഞ്ഞത് ഒരു വരിയെങ്കിലും `import `, `export `, `function `, `class `, `const `, `let `, `var ` അല്ലെങ്കിൽ `return ` (കീവേഡ് പ്ലസ് ഒരു സ്പെയ്സ്) എന്നിവയിൽ ആരംഭിക്കുന്ന 3 അല്ലെങ്കിൽ ` (` കൂടുതൽ വരികളുടെ ഉള്ളടക്കം, അല്ലെങ്കിൽ `if`, `for` അല്ലെങ്കിൽ `while` `(` ശേഷം സൂക്ഷിക്കുക 20-ഉം അവസാനത്തെ 5 വരികളും, എലിഡഡ് മധ്യഭാഗം അടയാളപ്പെടുത്തിയിരിക്കുന്നു.
2. **`grepSearch`** : `<path>:<digits>:` ഫോമിൻ്റെ ഒരു വരിയെങ്കിലും ഉള്ള ഉള്ളടക്കം, ആദ്യത്തെ കോളണിന് മുമ്പുള്ള ടെക്സ്റ്റിന് വൈറ്റ്സ്പെയ്സ് ഇല്ല, പരമാവധി 30 വരികൾ മാത്രമേ നിലനിർത്തൂ, തുടർന്ന് ഏതെങ്കിലും പൊരുത്തങ്ങളുടെ എണ്ണവും പൊരുത്തപ്പെടുന്ന ഫയലുകളുടെ ലിസ്റ്റും; മറ്റെല്ലാ വരികളും ഒഴിവാക്കിയിരിക്കുന്നു. സ്ട്രാറ്റജി പ്രവർത്തനക്ഷമമാക്കാൻ അത്തരം ഒരു വരി മതിയാകും, അതിനാൽ `12:30:45` പോലുള്ള ടൈംസ്റ്റാമ്പിൽ ആരംഭിക്കുന്ന ഒരു ലോഗ് ലൈനും കണക്കാക്കുന്നു.
3. **`shellOutput`** : ഒരു ANSI CSI സീക്വൻസ് (`ESC[` പിന്നെ അക്കങ്ങൾ അല്ലെങ്കിൽ അർദ്ധവിരാമങ്ങൾ, പിന്നെ ഒരു അക്ഷരം, കളർ കോഡുകളിലെന്നപോലെ) അല്ലെങ്കിൽ ഒരു `$` വാചകത്തിൽ എവിടെയെങ്കിലും വൈറ്റ്സ്പെയ്സ് എന്നിവ അടങ്ങിയിരിക്കുന്ന ഔട്ട്പുട്ട് ആ ശ്രേണികൾ നഷ്ടപ്പെടുത്തുന്നു ( `ESC[?25l` അല്ലെങ്കിൽ ഒരു OSC വിൻഡോ-ശീർഷക ക്രമം പോലെയുള്ള മറ്റ് എസ്കേപ്പുകൾ സൂക്ഷിക്കുന്നു. ചുരുക്കിയ വരികൾ തുടർച്ചയായി 50 വരിയായി ചുരുക്കുന്നു കാരണം, ഈ പരിശോധന `json`, `errorMessage` എന്നിവയ്ക്ക് മുമ്പായി പ്രവർത്തിക്കുന്നു, JSON അല്ലെങ്കിൽ അത്തരം ഒരു `$` അടങ്ങിയിരിക്കുന്ന പിശക് ഔട്ട്പുട്ട് `shellOutput` ഓണായിരിക്കുമ്പോൾ ഒരിക്കലും അവയിൽ എത്തിച്ചേരില്ല.
4. **`json`** : `{` അല്ലെങ്കിൽ `[` (ഓപ്ഷണൽ വൈറ്റ്സ്പെയ്സിന് ശേഷം) പാഴ്സുകളിൽ ആരംഭിക്കുന്ന 2,000 പ്രതീകങ്ങളേക്കാൾ കൂടുതലുള്ള ഒരു JSON പേലോഡ് സംഗ്രഹിച്ചിരിക്കുന്നു: 7-ലധികം ഇനങ്ങളുടെ ഒരു ശ്രേണി അതിൻ്റെ ആദ്യത്തെ 5 ഉം അവസാനത്തെയും 2 ഇനങ്ങളും അതിൻ്റെ ആകെ എണ്ണവും നിലനിർത്തുന്നു, കൂടാതെ ഒരു ഒബ്ജക്റ്റ് അതിൻ്റെ ആദ്യത്തെ 20 കീകൾ സൂക്ഷിക്കുന്നു അതിൻ്റെ ദൈർഘ്യം) കൂടാതെ കീകൾ എണ്ണുന്ന ഒരു `{…N keys}` മാർക്കറും ആദ്യ 20-നേക്കാൾ കുറഞ്ഞു. `_remaining_<N>_keys` മൂല്യങ്ങൾ മുഴുവനായും പകർത്തി, അതിനാൽ 20 കീകളോ അതിൽ കുറവോ ഉള്ള ഒരു ഒബ്ജക്റ്റ് നെസ്റ്റഡ് മൂല്യങ്ങളില്ലാതെ — വീണ്ടും ഇൻഡൻ്റ് ചെയ്താൽ, ചെറുതാക്കിയത് പ്രതീകങ്ങൾ നേടുകയും മാറ്റമില്ലാതെ തുടരുകയും ചെയ്യുന്നു.
5. **`errorMessage`** : എവിടെയും ഏത് അക്ഷര കേസിലും, `error:`, `error ` ( `no error found` പോലെയുള്ള ഒരു സ്പെയ്സ് പിന്തുടരുന്ന വാക്ക്), `[error]`, `exception:`, `exception `, `[exception]` അല്ലെങ്കിൽ `traceback` എന്നിവ അടങ്ങുന്ന ഔട്ട്പുട്ട്, അതിൻ്റെ ആദ്യ വരിയും അടുത്ത 10 വരികളും അവസാന 3 നും ഇടയിൽ `… [N frames elided] …` മാർക്കറുമായി നിലനിർത്തുന്നു. 13-ലധികം വരികൾ ആദ്യ വരി പിന്തുടരുമ്പോൾ മാത്രമേ മാർക്കർ ദൃശ്യമാകൂ, അതിനാൽ 14 വരികളോ അതിൽ കുറവോ ഉള്ള പിശക് ഔട്ട്പുട്ട് ചെറുതാക്കില്ല (12 അല്ലെങ്കിൽ 13 വരികളിൽ അവസാനത്തെ 3 ആവർത്തന വരികൾ ഇതിനകം സൂക്ഷിച്ചിരിക്കുന്നു).

ഒരു തന്ത്രം പൊരുത്തപ്പെട്ടുകഴിഞ്ഞാൽ, ഒന്നും ലാഭിക്കാത്ത ഒന്ന് പോലും, പിന്നീടുള്ള തന്ത്രങ്ങൾ പരീക്ഷിക്കപ്പെടുന്നില്ല. പൊരുത്തപ്പെടുത്തൽ തന്ത്രം കണക്കാക്കിയ ടോക്കണുകളൊന്നും സംരക്ഷിക്കാത്തപ്പോൾ ( ÷ 4, വൃത്താകൃതിയിലുള്ള നീളം) — ഉദാഹരണത്തിന് 25 ലൈനുകളോ അതിൽ കുറവോ ഉള്ള ഒരു കോഡ് പോലുള്ള ഫയൽ, അല്ലെങ്കിൽ 7 ഇനങ്ങളോ അതിൽ കുറവോ — ഉള്ള 2,000 പ്രതീകങ്ങളുള്ള `compressAggressive()` JSON അറേയോ `compressAnthropicToolResultBlock()` എഞ്ചിൻ യഥാർത്ഥ ടൂൾ നിലനിർത്തുന്നു `saved` അല്ലെങ്കിൽ താഴെ, `compressToolResult()` തന്നെ ഇപ്പോഴും ആ തന്ത്രത്തിൻ്റെ ഔട്ട്പുട്ട് നൽകുന്നു. ടൂൾ ഫല ഘട്ടം അവസാന വാക്കല്ല: എഞ്ചിൻ്റെ ഫാൾബാക്ക് സംഗ്രഹത്തിന് 8,192 പ്രതീകങ്ങളിൽ കൂടുതൽ നീളമുള്ള ഒരു `tool` അല്ലെങ്കിൽ `function` സന്ദേശത്തെ ചെറുതാക്കാൻ കഴിയും (`maxTokensPerMessage`, 2,048, തവണ 4).

#### എപ്പോൾ ഉപയോഗിക്കണം

ടൂൾ റിസൾട്ട് കംപ്രഷൻ എന്നത് അഗ്രസീവ് എഞ്ചിൻ്റെ (`compressAggressive()` ൽ `open-sse/services/compression/aggressive.ts`) സ്റ്റെപ്പ് 1 ആണ്, അതിനാൽ ഇത് അഗ്രസീവ് മോഡിലും അടുക്കിയിരിക്കുന്ന പൈപ്പ്ലൈനിൻ്റെ `aggressive` സ്റ്റെപ്പിലും പ്രവർത്തിക്കുന്നു. ഇത് OpenAI ആകൃതിയിലുള്ള `tool`, `function` സന്ദേശങ്ങളും Anthropic `tool_result` ബ്ലോക്കുകൾക്കുള്ളിലെ വാചകവും കംപ്രസ്സുചെയ്യുന്നു. ഓരോ തന്ത്രത്തിനും `aggressive.toolStrategies` ന് കീഴിൽ അതിൻ്റേതായ സ്വിച്ച് ഉണ്ട്, എല്ലാം സ്ഥിരസ്ഥിതിയായി ഓണാണ്. ഡാഷ്ബോർഡിൽ, സ്വിച്ചുകൾ കേവ്മാൻ പേജിലാണ്** വിപുലമായ** കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ കാണുക, സ്ഥിരസ്ഥിതി മോഡ് ആക്രമണാത്മകമാണ്.

### അടുക്കിയ പൈപ്പ്ലൈൻ

സ്റ്റാക്ക് ചെയ്ത മോഡ് പ്രവർത്തിക്കുന്നു** ക്രമത്തിൽ ഒന്നിലധികം എഞ്ചിനുകൾ** — സാധാരണയായി ആദ്യം RTK (ടൂൾ ഔട്ട്പുട്ടിൽ 60-90% സേവിംഗ്സ്), തുടർന്ന് ശേഷിക്കുന്ന വാചകത്തിൽ കേവ്മാൻ (~ 46% ഇൻപുട്ട് സേവിംഗ്സ്). രചിച്ചത്, അതാണ്** 78-95% യോഗ്യതയുള്ള ശ്രേണി** (മുകളിലുള്ള അപ്സ്ട്രീം സേവിംഗ്സ് മാത്ത് കാണുക): `1 - (1 - 0.60..0.90) × (1 - 0.46)` ശരാശരി ≈ 89%.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### എപ്പോൾ ഉപയോഗിക്കണം

ഇതിനായി സ്റ്റാക്ക് ചെയ്ത മോഡ് ഉപയോഗിക്കുക:

- ടൂൾ-ഹെവി വർക്ക്ഫ്ലോകൾ (ഏജൻറിക് കോഡിംഗ്, ഗവേഷണം)
- കോസ്റ്റ് സെൻസിറ്റീവ് ബാച്ച് പ്രോസസ്സിംഗ്
- നിങ്ങൾക്ക് പരമാവധി ടോക്കൺ സേവിംഗ്സ് ആവശ്യമുള്ളപ്പോൾ

ആഗോള `stackedPipeline` കംപ്രഷൻ ക്രമീകരണം വഴിയോ അല്ലെങ്കിൽ ഒരു റൂട്ടിംഗ് കോമ്പോയ്ക്ക് നൽകിയിരിക്കുന്ന പേരിലുള്ള കംപ്രഷൻ കോംബോ വഴിയോ അടുക്കിയിരിക്കുന്ന പൈപ്പ്ലൈനുകൾ ക്രമീകരിച്ചിരിക്കുന്നു (മുകളിലുള്ള ഓരോ കോംബോ ഓവർറൈഡ് കാണുക) — ഒരു ഓട്ടോ-കോംബോ `modePack` വഴിയല്ല (ആ ഫീൽഡ് ഓട്ടോ-കോംബോ മോഡൽ തിരഞ്ഞെടുക്കൽ വീണ്ടും വെയ്റ്റ് ചെയ്യുന്നു, കൂടാതെ `stacked` ഒരു സാധുവായ പായ്ക്ക് നാമമല്ല).

## കോംപ്രഷൻ കോംബോ ഓവർറൈഡുകൾ

വ്യത്യസ്ത ഉപയോഗ സാഹചര്യങ്ങൾക്കായി പ്രവർത്തനം സൂക്ഷ്മമായി ക്രമീകരിക്കുന്നതിന് ഗ്ലോബൽ കോംപ്രഷൻ മോഡ് **ഓരോ കോംബോയ്ക്കും** ഓവർറൈഡ് ചെയ്യാം:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ഇത് ഇനിപ്പറയുന്നവയ്ക്ക് ഉപകാരപ്രദമാണ്:

- **കോഡിംഗ് കോംബോകൾ**: ദൈർഘ്യമേറിയ സെഷനുകൾക്കായി `aggressive` മോഡ് ഉപയോഗിക്കുക
- **ദ്രുത ചോദ്യോത്തര കോംബോകൾ**: വേഗത്തിലുള്ള പ്രതികരണങ്ങൾക്കായി `lite` മോഡ് ഉപയോഗിക്കുക
- **ടൂൾ-അധിഷ്ഠിത കോംബോകൾ**: പരമാവധി ലാഭത്തിനായി `stacked` മോഡ് ഉപയോഗിക്കുക
- **പ്രൊഡക്ഷൻ കോംബോകൾ**: കാഷിംഗ് പ്രൊവൈഡറുകൾക്കായി ഓവർറൈഡ് ഓഫാക്കി വെക്കുക — എല്ലായ്പ്പോഴും സജീവമായ
  കാഷ്-അവെയർ ക്രമീകരണം `aggressive`/`ultra` മോഡുകളെ സ്വയമേവ `standard` ആയി ഡൗൺഗ്രേഡ് ചെയ്യുന്നു
  (തിരഞ്ഞെടുക്കാവുന്ന `cache-aware` മോഡ് നിലവിലില്ല)
