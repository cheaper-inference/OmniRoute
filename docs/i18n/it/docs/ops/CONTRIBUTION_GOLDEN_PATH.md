Usa questa guida per scegliere il ciclo di sviluppo affidabile più breve per una pull request. Non
sostituisce i documenti di architettura e sicurezza specifici per area collegati di seguito; associa
ogni tipo comune di modifica ai relativi contratti, controlli mirati e copertura CI.

## Il percorso seguito da ogni modifica

1. **Scegli la base prima di apportare modifiche.** Individua il branch `release/v*` attivo con la
   versione più alta e crea un branch a partire dal suo commit più recente. Usa quel branch come
   destinazione, non `main`. Se è in corso un blocco della release, non usare come destinazione il
   branch bloccato; utilizza il ciclo attivo successivo descritto in
   [Modello di branching e release](BRANCHING_MODEL.md).
2. **Individua i contratti.** Identifica ogni catalogo, schema, artefatto generato, API pubblica o
   interfaccia utente interessati dalla modifica. La tabella seguente indica l'insieme minimo iniziale.
3. **Scrivi o aggiorna test mirati.** Le modifiche al codice di produzione in `src/`, `open-sse/`,
   `electron/` o `bin/` richiedono un test automatizzato nella stessa PR. Esegui i file di test
   minimi che dimostrano il comportamento, quindi i controlli mirati indicati.
4. **Lascia che la CI esegua la matrice completa.** Gli shard completi dei test unitari, Vitest, il
   controllo incrementale della copertura e la build di produzione vengono eseguiti nella PR. Esegui
   localmente una suite estesa solo quando un errore mirato indica un impatto più ampio o quando la
   modifica interessa diversi sottosistemi.
5. **Riallinea prima della revisione.** Recupera la base attiva, esamina i nuovi commit e il tuo diff
   rispetto a essa, quindi esegui il rebase o il merge della base secondo il flusso di lavoro per i
   contributori. Risolvi i conflitti nei file generati e nei cataloghi intervenendo sulla relativa
   sorgente, rigenerali, riesegui il ciclo mirato e verifica che la PR abbia ancora come destinazione
   il branch di release attivo.
6. **Registra le evidenze.** Nel template della PR, elenca i comandi eseguiti, ogni file di test
   aggiunto o modificato, le migrazioni o i feature flag e qualsiasi convalida da eseguire
   esclusivamente in CI ancora in sospeso.

## Percorsi consigliati per tipo di modifica

I comandi seguenti sono controlli mirati minimi, non un'autorizzazione a omettere un test che copre
direttamente il comportamento modificato.

### Provider

**Contratti**

- Definizione del provider in `src/shared/constants/providers/` e relativa composizione in
  `src/shared/constants/providers.ts`.
- Modelli e funzionalità in `open-sse/config/providerRegistry.ts` o nei relativi file di registro
  estratti.
- Selezione dell'executor/translator, configurazione OAuth o delle chiavi API, risorse della dashboard
  e documentazione di riferimento generata del provider, quando applicabile.
- Le credenziali pubbliche devono usare `resolvePublicCred()`; le risposte di errore devono usare gli
  helper condivisi per la sanitizzazione degli errori. Consulta `docs/security/PUBLIC_CREDS.md`
  (git; non compilato in `/docs`) e
  [Sanitizzazione degli errori](../security/ERROR_SANITIZATION.md).

**Ciclo mirato**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # quando cambia il catalogo; esegui il commit del diff generato
npm run lint
```

Testa inoltre ogni famiglia di richieste interessata: chat, Responses, immagini, embedding, audio o
video. Esamina i diff dei cataloghi generati e dei golden file come modifiche contrattuali; non
accettarli alla cieca.

### Routing

**Contratti**

- Valori pubblici delle strategie e metadati dell'interfaccia utente in
  `src/shared/constants/routingStrategies.ts`.
- Dispatch e ordinamento in `open-sse/services/combo.ts` e `open-sse/services/combo/`.
- Schemi combo, persistenza, stato di resilienza, funzionalità dei modelli e controlli API/UI.
- [Motore Auto-Combo](../routing/AUTO-COMBO.md) e documentazione sulla resilienza quando cambia il
  comportamento.

**Ciclo mirato**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # modifiche alla strategia o al dispatch
npm run check:known-symbols      # modifiche alla registrazione delle strategie
npm run lint
```

Usa localmente test deterministici con upstream simulati. Gli smoke test live delle combo richiedono
credenziali e sono manuali, non sostituiscono la CI.

### UI / UX

**Contratti**

- Route/pagina Next.js e confini dei componenti condivisi in `src/app/` e
  `src/shared/components/`.
- Formati delle risposte API, stati di caricamento/vuoto/errore, comportamento della tastiera e degli
  screen reader, layout responsivo, temi ed espansione delle lingue supportate.
- Stringhe sorgente dell'interfaccia utente in inglese in `src/i18n/messages/en.json`; non inserire
  direttamente nel codice nuovi testi rivolti all'utente.

**Ciclo mirato**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Esegui l'app per le modifiche visive o di interazione e controlla viewport sia strette sia ampie. La
CI esegue la build di produzione e le suite più estese; il comportamento visivo richiede comunque un
controllo mirato appropriato alla modifica, tramite componente, Playwright o verifica manuale
documentata.

### i18n

**Contratti**

- `src/i18n/messages/en.json` è la sorgente dell'interfaccia utente; `config/i18n.json` è la sorgente
  delle lingue supportate.
- I cataloghi della CLI si trovano separatamente in `bin/cli/locales/`.
- Mantieni invariati i placeholder e i tag ICU. Non tradurre nomi di prodotti/provider/modelli, nomi
  di protocolli e header, comandi, identificatori di codice/JSON, URL, variabili d'ambiente o termini
  protetti come `OmniRoute`, `OAuth`, `MCP` e `A2A`. L'elenco sorgente attuale è
  `scripts/i18n/glossary/protected-terms.json`.

**Ciclo mirato**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # quando cambiano stringhe/cataloghi della CLI
npm run lint
```

Queste sono indicazioni per il sistema esistente, non un invito ad ampliarne gli strumenti o il
modello delle chiavi. Mantieni le patch i18n circoscritte mentre viene progettato il sistema
sostitutivo. Non eseguire comandi di traduzione che chiamano servizi esterni, salvo quando l'attività
richiede esplicitamente traduzioni generate e hai esaminato il diff risultante.

### CLI

**Contratti**

- Comandi pubblici e flag in `bin/cli/`, comandi API generati, codici di uscita, stdout/stderr e
  strutture dell'output JSON, comportamento della configurazione/dell'ambiente e file inclusi nel pacchetto.
- Le stringhe della CLI rivolte all'utente devono usare il livello i18n della CLI e mantenere allineati i cataloghi `en`/`pt-BR`.
- Mantenere Node come runtime supportato e rispettare il contratto del binario pubblicato.

**Ciclo mirato**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # modifiche alla CLI generata/in bundle
npm run check:pack-policy     # modifiche alla superficie del pacchetto
npm run lint
```

Usare il comando esatto in una directory dati temporanea quando il comportamento dipende dal parsing, dai file o dallo stato
di uscita. La CI esegue i controlli più ampi sugli artefatti del pacchetto e sull'ecosistema.

### Database

**Contratti**

- Moduli di dominio in `src/lib/db/`; importare direttamente i moduli specifici (il precedente livello di riesportazione `localDb.ts` è stato rimosso).
- Migrazioni SQL numerate e idempotenti in `src/lib/db/migrations/`, sicurezza delle transazioni, comportamento
  degli aggiornamenti, indici e ogni chiamante interessato dallo schema.
- Le route e gli handler non eseguono mai direttamente SQL grezzo.

**Ciclo mirato**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Quando si aggiunge una migrazione, testare sia un database nuovo sia l'aggiornamento dallo schema precedente. I test del database
devono chiudere gli handle e chiamare `resetDbInstance()` durante la pulizia. Eseguire `npm run test:bun:db` solo quando
cambia il percorso dell'adattatore Bun senza garanzia di supporto; Node rimane autorevole.

### Build / deployment

**Contratti**

- Manifest e lockfile della radice e dei workspace, `scripts/build/`, assemblaggio standalone di Next.js, contenuti del pacchetto
  `dist/`, metadati Electron specifici della piattaforma, workflow di CI e sentinelle di deployment.
- Gli intervalli di versioni Node supportati e l'uso di Bun incluso nell'elenco consentito in `CLAUDE.md` devono rimanere invariati.
- Gli artefatti di build rimangono non tracciati; si applicano le policy relative a dipendenze, licenze, workflow e pacchetti.

**Ciclo mirato**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # modifiche alle dipendenze o al lockfile
npm run check:pack-policy      # modifiche alla superficie del pacchetto pubblicato
npm run lint
```

Usare `npm run build` localmente solo quando la modifica riguarda la compilazione, l'assemblaggio standalone, gli asset
o il bundling a runtime. Usare `npm run build:release` solo per la validazione della release/del deployment. La build della CI è
il segnale multipiattaforma definitivo; le modifiche di Electron specifiche della piattaforma richiedono la build mirata corrispondente
o evidenze di smoke test.

## Script per sviluppatori per una macchina condivisa

Due strumenti di supporto in `scripts/dev/` codificano il ciclo locale su una devbox in cui sono attive altre sessioni:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # file da merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # esattamente questi file
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # worktree isolato, sicuro in parallelo
```

- `typecheck-touched.sh` esegue il controllo dei tipi solo sui file `.ts/.tsx` modificati tramite un
  `tsconfig.touched.tmp.json` temporaneo (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) con un heap da 6 GB, sostituendo quindi il comando `tsc -p tsconfig.json`
  sull'intero progetto, che causa un OOM su una macchina sotto carico. Stampa gli errori nei file
  modificati più una riga di riepilogo e termina con `1` per errori nei file modificati, `2` quando
  gli unici errori si trovano nei file importati oppure tsc è terminato senza diagnostica
  (leggere il log indicato in `_artifacts/typecheck-touched/`), `0` quando non ci sono errori.
  Il tsconfig temporaneo viene sempre rimosso; non eseguirne mai il commit.
- `new-worktree.sh` serializza le esecuzioni simultanee tramite
  `<git-common-dir>/omniroute-new-worktree.lock` (attende fino a 600 s per impostazione predefinita,
  mostrando un messaggio; l'intestazione dello script documenta come sovrascrivere tale valore) e
  annulla la creazione del branch quando `git worktree add` non riesce prima che il worktree esista,
  così un nuovo tentativo non richiede l'esecuzione manuale di `git branch -D`. I `node_modules`
  collegati tramite hard link e la copia di `.husky/_` rimangono invariati.

## Ciclo locale del candidato

I test del sorgente non possono dimostrare che l'artefatto pacchettizzato si avvii: gli elenchi di
packaging, le dipendenze eliminate e i binari nativi generano errori solo dopo che il tarball viene
installato e avviato. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) è il lato locale del
flusso compila una volta / convalida / promuovi definito nell'RFC #8084: compila un candidato,
convalida esattamente quell'artefatto, lo promuove rinominando le directory e ne esegue il rollback
quando lo slot promosso non supera il controllo di integrità.

```bash
npm run dev:candidate -- run --dry-run --json  # stampa il piano senza modificare nulla
npm run dev:candidate -- run                   # compila + convalida + promuove, rollback automatico
npm run dev:candidate -- build                 # npm pack + installazione in _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # avvia su una porta libera, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # scambia current e previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # riutilizza un tarball compilato altrove (CI)
```

- **Compila una volta.** `build` crea un pacchetto dall'albero corrente (richiede
  `dist/server.js`, quindi eseguire prima `npm run build:release`) oppure copia `--from-tarball`,
  quindi installa il tarball in un prefisso npm isolato, perché il tarball non contiene
  `node_modules`. L'id è lo sha breve di `HEAD` (`-dirty` quando l'albero contiene modifiche locali)
  oppure `tgz-<sha256>` per un tarball. Un id pulito già compilato viene riutilizzato anziché
  ricompilato; passare `--force` per ricompilarlo.
- **Convalida il pacchetto, non il sorgente.** `validate` avvia la CLI installata
  (`serve --port <free port>`) con un nuovo `DATA_DIR=<candidate>/data`, segreti fittizi e le
  variabili `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` e `INITIAL_PASSWORD` dell'operatore
  rimosse dall'ambiente, in modo da verificare la configurazione loopback senza chiavi di una nuova
  installazione. Attende che `GET /api/health` restituisca 200, richiede che `GET /v1/models`
  restituisca 200, arresta il gruppo di processi e registra il verdetto in `validation.json`
  insieme all'hash del tarball.
- **Promuovi lo stesso artefatto.** `promote` rifiuta un candidato privo di una convalida superata
  per l'hash del suo tarball corrente. Lo slot attivo predefinito è
  `_artifacts/candidate/current`; `--target <dir>` seleziona un'altra directory sullo stesso
  filesystem e il relativo slot precedente è `<dir>.previous`. Ogni ridenominazione è atomica e,
  in caso di errore durante il processo, le ridenominazioni già eseguite vengono annullate.
- **Esegui il rollback.** `run` convalida nuovamente lo slot promosso e ripristina lo scambio tra
  `current` e `previous` quando tale controllo non riesce. Un candidato che non supera la prima
  convalida non viene mai promosso.

Tutto viene scritto nella directory ignorata da git `_artifacts/candidate/`; un'installazione
OmniRoute esistente e la relativa directory dei dati non vengono mai modificate. La CLI promossa è
`_artifacts/candidate/current/prefix/bin/omniroute`; avviarla con il proprio `DATA_DIR` quando la si
utilizza. Codici di uscita: `0` operazione riuscita, `1` convalida o promozione non riuscita, `2`
errore di utilizzo o build mancante.

## Ciclo locale rispetto alla CI

| Eseguito localmente per ogni patch                                                               | La CI fornisce un riscontro più ampio                                                        |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Test diretti del comportamento e controlli di categoria indicati sopra                           | Suite completa di unit test suddivisa in shard e test seriali                                |
| `npm run lint`                                                                                   | Suite Vitest e soglie incrementali di copertura/qualità                                      |
| Controllo dei tipi o build solo quando richiesto dal contratto interessato                       | Build di produzione, sicurezza, documentazione, dipendenze e controlli delle policy delle PR |
| Interazione manuale/verifiche live solo quando l'automazione non può dimostrare il comportamento | Controlli di integrazione tra job e della piattaforma configurati dal workflow               |

Un ciclo focalizzato completato con esito positivo costituisce una prova relativa al contratto modificato, non garantisce che i controlli CI non correlati
vengano superati. Analogamente, non attendere l'esecuzione dell'intera matrice del repository per ogni modifica locale.

## Checklist di riconciliazione

Prima di richiedere una revisione:

- Verifica che la base della PR sia ancora il branch `release/v*` attivo con la versione più alta.
- Esegui il fetch di tale base ed esamina i commit aggiunti da quando hai creato il branch.
- Esamina `git diff <active-base>...HEAD` per individuare modifiche accidentali o generate.
- Risolvi i conflitti nei cataloghi e nei documenti generati aggiornando la sorgente e rigenerando l'output.
- Riesegui ogni test/controllo focalizzato elencato nella descrizione della PR dopo la riconciliazione.
- Non indebolire mai le asserzioni né rimuovere i test obbligatori solo per adeguarti a una base modificata.

Per le regole relative al blocco dei rilasci e al retargeting, consulta
[Modello di branching e rilascio](BRANCHING_MODEL.md). Per l'inventario completo della CI, consulta
[Riferimento dei controlli di qualità](../architecture/QUALITY_GATES.md).
