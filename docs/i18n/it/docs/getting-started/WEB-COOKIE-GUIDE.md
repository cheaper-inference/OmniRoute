I provider Web Cookie consentono a OmniRoute di utilizzare un servizio di IA tramite la sessione esistente del browser anziché tramite una chiave API. Sono utili quando hai già accesso a un servizio attraverso il relativo sito web e desideri che OmniRoute utilizzi la stessa sessione autenticata.

A differenza dei provider basati su chiave API, i provider Web Cookie eseguono l'autenticazione utilizzando le credenziali inviate dal browser al sito web.

---

# Prima di iniziare

> **Importante:** copia sempre le credenziali da una **richiesta di rete attiva**, **non** dall'archivio dei cookie del browser.

Molti problemi di autenticazione sono causati dalla copia dei cookie dalla posizione sbagliata.

## NON copiare dall'archivio dei cookie

La maggior parte dei browser espone i cookie memorizzati tramite:

```
DevTools
→ Application (or Storage)
→ Cookies
```

Sebbene questi cookie possano sembrare corretti, potrebbero essere:

- obsoleti
- incompleti
- privi di cookie inviati solo nelle richieste autenticate

L'utilizzo di questi valori può causare errori di autenticazione anche se sembrano validi.

## Copiare da una richiesta attiva

Utilizza invece i cookie di una richiesta completata correttamente:

```
DevTools
→ Network
→ Refresh the page
→ Open a chat or conversation request
→ Request Headers
→ Cookie
```

L'intestazione della richiesta `Cookie` contiene le informazioni di autenticazione esatte utilizzate correttamente dal browser.

Per la maggior parte dei provider Web Cookie, questo è il valore da incollare in OmniRoute.

# Configurazione generale

Il processo di configurazione è lo stesso per la maggior parte dei provider Web Cookie.

1. Accedi al sito web del provider.
2. Apri gli strumenti per sviluppatori del browser.
3. Apri la scheda **Rete**.
4. Aggiorna la pagina.
5. Apri una richiesta autenticata di chat o conversazione.
6. Copia le credenziali di autenticazione richieste.
7. Apri OmniRoute.
8. Vai a **Provider → Aggiungi provider**.
9. Seleziona il tuo provider Web Cookie.
10. Incolla le credenziali.
11. Fai clic su **Verifica connessione**.
12. Salva il provider.

Le credenziali esatte richieste dipendono dal provider.

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) è una piattaforma di chat gratuita per utenti, senza registrazione obbligatoria: la sessione viene creata in modo anonimo alla prima visita e persiste tramite tre cookie: `uid`, `si_usr_id` e `si_ses_id`. OmniRoute inoltra tramite proxy lo stesso endpoint `/api/dispatch` attraverso un unico ID modello (`notrack-c`, alias `ntw`).

### Passaggi per la connessione

1. Apri [notrack.ai](https://notrack.ai) nel browser e attendi che venga impostato il cookie della sessione anonima.
2. Apri **Strumenti per sviluppatori → Rete**, aggiorna la pagina e fai clic su una qualsiasi richiesta `/api`.
3. In **Intestazioni della richiesta**, copia il valore completo dell'intestazione `Cookie`.
4. In OmniRoute, vai a **Provider → Aggiungi provider → NoTrack Web (gratuito)**.
5. Incolla la stringa dei cookie nel campo `apiKey` e fai clic su **Salva**.

OmniRoute estrae `uid`, `si_usr_id` e `si_ses_id` dalla stringa incollata e ricostruisce un'intestazione `Cookie` pulita contenente solo queste coppie, oltre a `nt_session` (il token `ntk_…` impostato per gli account autenticati), se presente. Se manca uno dei tre valori, la stringa originale incollata viene inoltrata senza modifiche, in modo che gli operatori possano sperimentare formati alternativi.

### ID modello

| ID modello  | Nome visualizzato | Note                                                          |
| ----------- | ----------------- | ------------------------------------------------------------- |
| `notrack-c` | NoTrack C         | Predefinito: il modello di dispatch upstream `C`.             |
| `C`         | NoTrack C         | Alias di `notrack-c` (codice di dispatch upstream originale). |
| `notrack`   | NoTrack C         | Alias di `notrack-c`.                                         |
| `ntw`       | NoTrack C         | Alias breve di `notrack-c`.                                   |

Tutti e quattro gli ID modello corrispondono allo stesso modello di dispatch upstream (`C`).

### Opzioni della richiesta

L'esecutore accetta i seguenti campi facoltativi nel corpo della richiesta:

| Campo del corpo       | Valore predefinito | Scopo                                                                               |
| --------------------- | ------------------ | ----------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`            | Modalità di dispatch (stringa in formato libero; l'upstream accetta `usual`, …)     |
| `notrack_max_turns`   | `6`                | Numero di turni interni che l'upstream può effettuare prima di rispondere.          |
| `notrack_chat_id`     | `null`             | Riprende una chat upstream esistente (omettere per una nuova chat).                 |
| `notrack_attachments` | `[]`               | Array pass-through dei descrittori degli allegati upstream.                         |
| `notrack_regenerate`  | `false`            | Impostare su `true` per richiedere una risposta rigenerata per il turno precedente. |

### Funzionalità

- Completamenti chat **in streaming e non in streaming**.
- **Chiamata di strumenti**: imposta `tools: [...]` nella richiesta; l'esecutore li serializza in un contratto envelope per le chiamate di strumenti e analizza le risposte del modello riconvertendole in `tool_calls` di OpenAI.
- **`response_format`**: sono supportati `json_object` e `json_schema`. L'esecutore estrae il primo oggetto JSON dalla risposta del modello e lo serializza come stringa prima di restituirlo.
- **Indicazione del ragionamento**: l'esecutore emette un delta `reasoning` quando l'upstream invia un evento `thinking`.

### Limitazioni

- L'upstream applica quote di utilizzo anonimo: quando vengono superate, l'esecutore restituisce un errore 429 con un messaggio descrittivo.
- Tutti gli ID modello vengono risolti nello stesso modello di dispatch upstream; non è possibile selezionare un modello diverso per ciascun ID.
- L'esecutore non chiama l'endpoint `/api/chats` dell'upstream, pertanto la cronologia delle chat e le sessioni non vengono gestite automaticamente. Usa `notrack_chat_id` per riprendere una chat upstream esistente.

# Cosa possono e non possono fare i provider basati su cookie web

I provider basati su cookie web riutilizzano l'interfaccia di chat di un sito web. **Non** offrono le stesse funzionalità delle API ufficiali.

## Supportato

- Autenticazione tramite la sessione esistente del browser
- Accesso ai modelli disponibili tramite il proprio account
- Streaming delle risposte della chat
- Nessuna chiave API richiesta

## Non supportato

- Chiamata di funzioni
- Chiamata di strumenti
- Modifica automatica dei file
- Flussi di lavoro agentici nell'IDE
- Funzionalità disponibili solo tramite API

Questo è il comportamento previsto e **non** è un bug.

Se è necessaria l'esecuzione di strumenti, la modifica automatica dei file o altri flussi di lavoro agentici, utilizzare un **provider con chiave API** anziché un provider Web Cookie.

---

# Avvertenza sulla convalida

Il superamento del **Test Connection** o della convalida dei cookie verifica soltanto che le credenziali fornite sembrino essere nel formato previsto.

Finché l'Issue #7857 non sarà risolta, il superamento della convalida **non garantisce** che il provider riesca ad autenticarsi correttamente.

Se l'autenticazione continua a non riuscire, verificare che le credenziali siano state copiate da una richiesta di rete attiva anziché dall'archivio dei cookie del browser.

---

# Risoluzione dei problemi

## Autenticazione non riuscita

Verificare che le credenziali siano state copiate da:

```
Network
→ Request Headers
→ Cookie
```

e **non** da:

```
Application
→ Cookies
```

---

## Il cookie funziona nel browser ma non in OmniRoute

Alcuni provider includono cookie che vengono inviati solo durante le richieste autenticate.

Copiare nuovamente le credenziali da una nuova richiesta di rete dopo aver aperto correttamente una conversazione.

---

## Sessione scaduta

I provider Web Cookie utilizzano la sessione esistente del browser.

Se la sessione del browser scade o si effettua la disconnessione, è necessario copiare un nuovo set di credenziali. Per automatizzare il rinnovo dei cookie per i provider web supportati, consultare lo strumento complementare [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md).

---

## Il test della connessione riesce, ma le richieste non vanno a buon fine

Finché l'Issue #7857 non sarà risolta, il superamento della convalida non garantisce che la richiesta di autenticazione abbia esito positivo.

Prima di procedere con ulteriori tentativi di risoluzione dei problemi, copiare nuovamente le credenziali da una nuova richiesta autenticata.

---

## ChatGPT Web non funziona e mostra "Unsupported ChatGPT integrity dependency"

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

La credenziale è valida: l'errore proviene dal bridge, non dalla sessione. chatgpt.com assegna gli ID dei
moduli a ogni distribuzione e il bridge in precedenza vincolava l'ID dell'helper Sentinel che istanzia; pertanto,
una nuova build di chatgpt.com che ha rinominato l'helper ha interrotto ogni interazione, mentre il cookie è rimasto valido. Autorizzare
nuovamente la connessione non può risolvere il problema.

Le build che risolvono il modulo tramite il runtime della pagina stessa non vincolano alcun ID e non riscontrano questo problema. Se viene visualizzato
l'errore, aggiornare OmniRoute ed eseguire nuovamente il controllo della connessione.

# Procedure consigliate

- Copiare le credenziali da una nuova richiesta autenticata.
- Evitare di riutilizzare cookie obsoleti.
- Mantenere attiva la sessione del browser durante l'utilizzo dei provider Web Cookie.
- Trattare i cookie copiati come credenziali sensibili.
- Utilizzare provider con chiave API quando sono necessarie la chiamata di funzioni o flussi di lavoro agentici.
