## Come funziona

```
CLI Code's / CLI Agents (flusso di utilizzo):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (tutti puntano a OmniRoute)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute instrada verso il provider corretto)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (flusso inverso di avvio):
    Richiesta del client → OmniRoute → avvia la CLI tramite stdio/ACP → risposta
```

**Vantaggi:**

- Un'unica chiave API per gestire tutti gli strumenti
- Monitoraggio dei costi di tutte le CLI nella dashboard
- Cambio di modello senza dover riconfigurare ogni strumento
- Funziona in locale e su server remoti (VPS, Docker, Akamai, Cloudflare Tunnel)

## Autoconfigurazione con `setup-*`

Non è necessario scrivere manualmente la configurazione di ogni strumento. OmniRoute fornisce un comando `setup-*` per CLI supportato che legge il file** vivere** catalogo dei modelli da uno OmniRoute in esecuzione (locale o remoto) e scrive la configurazione dello strumento sul tuo computer:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
omniroute setup-whycodes
```

Ciascuno accetta `--remote <url> --api-key <key>` (configura uno strumento locale rispetto a uno OmniRoute remoto), `--dry-run` (anteprima senza scrittura) e `--port`. Gli strumenti senza rilevamento automatico del modello (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive, WhyCodes) accettano `--model <id>` (e `--yes` per le corse non interattive). `setup-5dive` è l'unica ricetta che non scrive sotto `$HOME`: configura una flotta di agenti 5dive scrivendo un profilo di autenticazione di proprietà di root sull'host della flotta, quindi riesegue tramite `sudo` e non ha una propria modalità remota. Per avviare uno CLI con l'env corretto inserito e nessuna configurazione scritta, utilizzare il launcher `omniroute run <target>` generico (claude, codex, aider, goose, opencode, qwen, gemini, whycodes — target e alias provengono da `bin/cli/cli-manifest.mjs`); i lanciatori legacy per strumento `omniroute launch` (Claude Code) e `omniroute launch-codex` (Codex) rimangono disponibili. Gemini CLI è di solo lancio: è un target `omniroute run` ma non ha una ricetta `setup-*`/`configure`.

> **Riferimento completo:** la tabella principale - cosa scrive ogni comando, ogni flag, locale vs remoto e quali strumenti vogliono un suffisso `/v1` - vive in** [CLI Integrazioni](../guides/CLI-INTEGRATIONS.md)** .

### Eseguendoli all'interno di un contenitore

Un comando `setup-*` eseguito all'interno del contenitore OmniRoute scrive nella home del contenitore, che nessun host CLI legge e che scompare con il contenitore. OmniRoute lo rileva ed esce `2` con le istruzioni anziché con la scrittura. Due modi supportati: installare CLI sull'host e `omniroute connect` nel contenitore oppure eseguire il bind-mount delle directory di configurazione e impostare `CLI_CONFIG_HOME` (il profilo `host` di composizione). Ogni comando `setup-*`, più `omniroute configure` e `omniroute config set`, accetta `--allow-container-write` quando si configura CLIs proprio del contenitore è ciò che intendevi effettivamente; `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` fa lo stesso per il server. Consulta [la Guida Docker → Configurazione degli strumenti CLI dell'host](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker).

Quello del cruscotto** applicare l'endpoint** (`POST /api/cli-tools/apply`) impone la stessa guardia: in un contenitore, una scrittura la cui destinazione non è vincolata dall'host risponde**`422`** con `containerEphemeralTarget: true`, il testo dell'errore sicuro e — per gli strumenti con una ricetta host (claude, codex, opencode, cline, kilo, continue) — uno `hostSetupCommand` (ad esempio `omniroute setup-opencode`) da eseguire invece sull'host; non c'è scritto nulla. `dryRun: true` continua a funzionare in modalità contenitore e restituisce un percorso di destinazione + in anteprima oscurato senza toccare il disco. Il contenuto di anteprima non è una configurazione con credenziali da copiare o importare. Applicare con gli input tool/base URL/API key/model originali sull'host oppure utilizzare il comando di configurazione lato host indicato. Consulta [la sicurezza della configurazione CLI](../security/CLI-CONFIGURATION.md) per l'intestazione di anteprima e il contratto di richiesta. Questo comportamento è intenzionale e protetto da regressione da `tests/unit/api/cli-tools/apply-container-guard.test.ts` : non "aggiustare" mai un 422 rimuovendo la protezione.

## Fonte autorevole

Il catalogo unificato si trova in `src/shared/constants/cliTools.ts` come `CLI_TOOLS: Record<string, CliCatalogEntry>`.

Ogni voce contiene questi campi (definiti in `src/shared/schemas/cliCatalog.ts`):

| Campo                                           | Tipo                                                         | Descrizione                                                              |
| ----------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------ |
| `category`                                      | `"code" \| "agent"`                                          | La pagina in cui viene visualizzato lo strumento                         |
| `vendor`                                        | `string`                                                     | Origine dello strumento ("Anthropic", "OSS (P. Gauthier)")               |
| `acpSpawnable`                                  | `boolean`                                                    | Utilizzabile anche come agente ACP (viene mostrato un badge)             |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | Livello di supporto per endpoint personalizzati. `"none"` = backlog MITM |
| `configType`                                    | `"env" \| "custom" \| "guide" \| "custom-builder" \| "mitm"` | Meccanismo di configurazione                                             |
| `id`, `name`, `color`, `description`, `docsUrl` | standard                                                     | Campi principali di visualizzazione                                      |

Le voci con `baseUrlSupport: "none"` **non vengono mostrate** nelle pagine della dashboard: sono registrate nel backlog MITM per il piano 11 (vedere `_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md`).

### Livelli di funzionalità (catalogato × rilevabile × configurabile × avviabile)

Non tutti gli strumenti catalogati sono rilevabili, configurabili o avviabili. Ogni livello ha una
singola fonte dichiarativa e un test di divergenza ne mantiene l'allineamento:

| Livello           | Significato                                                                                      | Dichiarato in                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| **Catalogato**    | Compare nel catalogo della dashboard (nome, fornitore, documentazione, tipo di configurazione)   | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                   |
| **Rilevabile**    | Rilevamento del binario/della configurazione, controlli di integrità, percorsi di configurazione | `src/shared/services/cliRuntime.ts` (catalogo runtime `CLI_TOOLS`) |
| **Configurabile** | Supportato da `omniroute configure <cli>` (esiste una procedura di configurazione)               | `bin/cli/cli-manifest.mjs` (`configure: true`)                     |
| **Avviabile**     | Supportato da `omniroute run <target>` (iniezione di variabili d'ambiente/argomenti definita)    | `bin/cli/cli-manifest.mjs` (`run: true`)                           |

`bin/cli/cli-manifest.mjs` è il manifest eseguibile canonico per le interfacce dei comandi CLI:
`run`, `configure` e i generatori di completamento della shell derivano tutti da esso i propri
elenchi di destinazioni, la risoluzione degli alias (ad esempio `kilocode`/`kilo-code`/`kilo_cli` → `kilo`)
e il collegamento del flag `--model`. Il controllo di divergenza
`tests/unit/cli/cli-manifest-drift.test.ts` verifica che il manifest, il catalogo runtime,
il catalogo dell'interfaccia utente e ogni interfaccia che li utilizza rimangano sincronizzati: una destinazione aggiunta a
un'interfaccia ma non alle altre fa fallire la suite anziché consentire una divergenza silenziosa.

## 5. API di rilevamento in batch

Il rilevamento di tutti gli strumenti viene aggregato tramite un unico endpoint:

**`GET /api/cli-tools/all-statuses`**

- Autenticazione: `requireCliToolsAuth(request)` (come per le altre route `/api/cli-tools/`)
- Restituisce: `Record<toolId, ToolBatchStatus>` (tipo: `src/shared/types/cliBatchStatus.ts`)
- Strategia: `Promise.all` su tutti gli strumenti, timeout di 5s per strumento
- Cache: LRU in memoria indicizzata in base al valore `mtime` del file di configurazione. La cache viene invalidata quando `mtime` cambia. Viene reimpostata al riavvio del server.

Struttura della risposta per ogni strumento:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // sanificato, senza tracce dello stack
}
```

## 10. CLI interna di OmniRoute

Il binario `omniroute` fornisce comandi per il ciclo di vita del server, la configurazione, la diagnostica e la gestione dei provider. Punto di ingresso: `bin/omniroute.mjs`.

```bash
omniroute                              # Avvia il server (porta predefinita 20128)
omniroute setup                        # Procedura guidata di configurazione interattiva
omniroute doctor                       # Controlla configurazione, DB, porte e runtime
omniroute providers list               # Connessioni ai provider configurate
omniroute providers test-all           # Verifica tutte le connessioni attive
omniroute reset-password               # Reimposta la password dell'amministratore
omniroute logs                         # Trasmette i log delle richieste
omniroute health                       # Stato dettagliato (circuit breaker, cache, memoria)
omniroute --version                    # Mostra la versione
omniroute --help                       # Mostra tutti i comandi
```

### Configurazione e inizializzazione

```bash
omniroute setup                        # Procedura guidata di configurazione interattiva
omniroute setup --non-interactive      # Modalità CI/automazione (legge variabili d'ambiente + flag)
omniroute setup --password '<value>'   # Imposta direttamente la password dell'amministratore
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # Aggiunge e verifica un provider in un'unica operazione
```

Variabili d'ambiente riconosciute per la configurazione non interattiva:

| Variabile           | Scopo                                                                           |
| ------------------- | ------------------------------------------------------------------------------- |
| `OMNIROUTE_API_KEY` | Chiave API del provider (associata a `--api-key` tramite `.env()` di Commander) |
| `DATA_DIR`          | Sostituisce la directory dei dati di OmniRoute                                  |

Tutti gli altri input non interattivi vengono passati come flag, non come variabili d'ambiente:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(vedere le opzioni di `omniroute setup` sopra).

### Diagnostica

```bash
omniroute doctor                       # Controlla configurazione, DB, porte, runtime, memoria e operatività
omniroute doctor --json                # JSON leggibile dalle macchine
omniroute doctor --no-liveness         # Ignora il controllo di integrità HTTP
omniroute doctor --host 0.0.0.0        # Sostituisce l'host per il controllo di operatività
omniroute doctor --liveness-url <url>  # Sostituisce l'URL completo dell'endpoint di integrità
```

Il comando doctor esegue questi controlli: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` e `Server liveness`. Termina con un codice diverso da zero se uno dei controlli restituisce `fail`.

### Gestione dei provider

```bash
omniroute providers available                       # Catalogo dei provider OmniRoute
omniroute providers available --search openai       # Filtra il catalogo per ID/nome/alias/categoria
omniroute providers available --category api-key    # Filtra per categoria (api-key, oauth, free, ...)
omniroute providers available --json                # JSON leggibile dalle macchine

omniroute providers list                            # Connessioni ai provider configurate
omniroute providers list --json

omniroute providers test <id|name>                  # Verifica una connessione configurata
omniroute providers test-all                        # Verifica tutte le connessioni attive
omniroute providers validate                        # Convalida strutturale esclusivamente locale
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # Flusso OAuth esistente
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` utilizzano principalmente l'API e funzionano quindi con
il contesto attivo locale o remoto. Per l'inserimento delle credenziali è consigliabile utilizzare
`--credential-stdin` o `--credential-env`; `--dry-run --json` riporta solamente
la presenza/struttura con i dati sensibili oscurati. `providers available` legge il catalogo di OmniRoute;
`providers list/test/test-all/validate` mantengono il loro comportamento SQLite locale e
non richiedono che il server sia in esecuzione.

Per un nodo personalizzato compatibile con OpenAI o Anthropic, associa le credenziali
all'ID del nodo restituito da `omniroute nodes add`, utilizzando `omniroute keys add "$NODE_ID" --stdin`.
Ciò richiede un server in esecuzione e l'autenticazione di gestione per il contesto attivo.
La CLI utilizza `POST /api/providers`, che convalida il nodo e copia le impostazioni del relativo endpoint
nella connessione. Un nodo mancante, un errore di autorizzazione o un server non disponibile
restituisce un errore senza creare credenziali locali di ripiego.

`nodes add --base-url` imposta l'endpoint del nodo; è distinto dall'indirizzo del server
in `OMNIROUTE_BASE_URL`. Per i file OpenAPI, utilizza
`omniroute openapi dump --format json --out ./openapi.json`; l'opzione globale `--output`
seleziona la formattazione di visualizzazione della CLI, non il nome di un file di destinazione.

### Ripristino e reimpostazione

```bash
omniroute reset-password                # Reimposta la password dell'amministratore (anche: omniroute-reset-password)
omniroute reset-encrypted-columns       # Mostra un avviso + una simulazione per la reimpostazione delle credenziali crittografate
omniroute reset-encrypted-columns --force  # Imposta effettivamente a null le credenziali crittografate in SQLite
```

### Esportazione delle credenziali (⚠ maneggiare con cautela)

```bash
omniroute auth export                                 # Mostra un avviso + richiesta di conferma — nessun accesso al DB
omniroute auth export --force                          # Esporta le credenziali DECRITTOGRAFATE di TUTTE le connessioni su stdout come JSON
omniroute auth export --force --id <id>                 # Esporta solo la connessione corrispondente
omniroute auth export --force --format env               # Genera righe OMNIROUTE_<PROVIDER>_<FIELD>=<value>
omniroute auth export --force --out creds.json           # Scrive in un file (creato con autorizzazioni 0600)
```

`auth export` è **solo locale** (lettura diretta di SQLite, nessuna route HTTP) e stampa/scrive intenzionalmente
i valori **in chiaro** di `apiKey`/`accessToken`/`refreshToken`/`idToken`: questa è una funzionalità, non un
bug. Nulla viene letto dal database e nulla viene decifrato senza `--force`. Un banner di
avviso viene sempre stampato su stderr prima che vengano emessi dati in chiaro. Richiede che
`STORAGE_ENCRYPTION_KEY` sia impostata. Un campo che non può essere decifrato (chiave obsoleta, testo cifrato danneggiato) viene segnalato come
`<field>DecryptFailed: true`, anziché interrompere l'intera esportazione o esporre l'errore sottostante.

## Gestire i criteri delle chiavi di inferenza con la CLI OmniRoute

Usa un contesto di gestione autenticato (consulta [Modalità remota](../guides/REMOTE-MODE.md))
per esaminare o aggiornare una chiave di inferenza esistente tramite il relativo ID:

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted` è un alias di `--model-access-mode all`. L'aggiornamento cancella
l'elenco dei modelli consentiti. Mantiene ambiti, regole di connessione, modelli bloccati, limiti di frequenza
e limiti di costo, quindi questi altri controlli possono comunque negare una richiesta. Anche
`--allowed-models ""` seleziona `all`; combinalo con
`--model-access-mode restricted` per mantenere una chiave con restrizioni senza modelli consentiti.
Un elenco non vuoto separato da virgole seleziona `restricted`, a meno che non sia specificato esplicitamente.
La combinazione contraddittoria di `all` e di un elenco non vuoto di modelli consentiti viene rifiutata prima dell'invio di una richiesta.

`--rate-limit 30` imposta le richieste al minuto e mantiene le regole per le altre finestre
temporali. `--max-cost 5` abilita il limite giornaliero in USD senza modificare quello settimanale;
`--max-cost 0` rimuove il limite giornaliero e mantiene l'impostazione esistente del limite di utilizzo
e il limite settimanale. I campi dei criteri omessi rimangono invariati. Le modifiche ai limiti di frequenza leggono
prima i criteri correnti; evita modifiche simultanee all'array dei limiti di frequenza della stessa chiave.

I comandi dei criteri usano richieste autenticate `GET`/`PATCH /api/keys/{id}` e rispettano il contesto
attivo e l'opzione globale `--api-key`. L'output JSON contiene solo i campi dei criteri,
senza la chiave memorizzata né la sua rappresentazione mascherata. Una credenziale destinata esclusivamente
all'inferenza non può autorizzare modifiche di gestione. Una risposta 401/403 richiede di controllare la credenziale
e il contesto di gestione; non dimostra un errore del token CLI locale o del salt.
Consulta [Token CLI](../security/CLI_TOKEN.md) per il contratto separato di autenticazione locale.
