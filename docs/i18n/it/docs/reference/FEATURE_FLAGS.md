> Opzioni di runtime che modificano il comportamento di OmniRoute **senza una nuova distribuzione**.
> Ogni flag elencato qui è definito in
> [`src/shared/constants/featureFlagDefinitions.ts`](../../src/shared/constants/featureFlagDefinitions.ts)
> — l'unica fonte autorevole. Sia la dashboard sia l'API REST leggono da
> quel file, quindi la tabella seguente viene generata in modo da corrispondervi 1:1.

---

## Cosa sono i feature flag

Un feature flag è un'opzione denominata (booleana o enum) il cui valore può essere modificato in
fase di esecuzione e salvato nel database, senza richiedere la ridistribuzione del processo. Ogni
flag è descritto da una `FeatureFlagDefinition` con `key`, `label`,
`description`, `category`, `defaultValue`, `type` e un'indicazione `requiresRestart`.

### Ordine di risoluzione

Il **valore effettivo** di un flag viene determinato da
[`resolveFeatureFlag()`](../../src/shared/utils/featureFlags.ts) secondo questo
ordine di precedenza (vince quello più alto):

1. **Override del DB** — un valore archiviato nella tabella `key_value` nello
   spazio dei nomi `feature_flags` (impostato tramite la dashboard o l'API REST).
2. **Variabile di ambiente** — `process.env[<KEY>]`, se impostata e non vuota.
3. **Valore predefinito della definizione** — il `defaultValue` di `featureFlagDefinitions.ts`.

Un flag booleano è considerato **abilitato** quando il suo valore effettivo è `"true"`,
`"1"` o `"yes"` (vedere `isFeatureFlagEnabled()`).

> [!NOTE]
> La maggior parte dei flag dispone anche di una variabile di ambiente corrispondente con lo **stesso nome**,
> documentata in [`ENVIRONMENT.md`](./ENVIRONMENT.md). L'override del DB del flag
> ha la precedenza su tale variabile di ambiente. Un flag con
> `requiresRestart: true` viene salvato immediatamente, ma riletto solo all'avvio
> del processo: modificandolo, nella dashboard viene visualizzato un banner **"Riavvia il server"**.

## Attivazione/disattivazione dei flag

### Pannello di controllo

Vai a** Dashboard → Impostazioni → Flag funzionalità** (`/dashboard/settings/feature-flags`). La griglia (`src/app/(dashboard)/dashboard/settings/components/FeatureFlagsGrid.tsx`) supporta:

- **Ricerca** per chiave o descrizione e** filtro** per categoria (più un sintetico** Richiede il riavvio** visualizzazione).
- UN** attivare/disattivare** per flag booleani e a** cadere in picchiata** per i flag enum (`src/app/(dashboard)/dashboard/settings/components/FeatureFlagCard.tsx`).
- UN** distintivo di origine** per flag — `DB`, `ENV` o `DEF` — che mostra da dove proviene il valore effettivo.
- UN** Reset** pulsante (mostrato solo per i flag `DB` -sourced ) per eliminare l'override e a** Ripristina tutte le sostituzioni** pulsante in basso.
- UN** Riavvia il server** banner quando viene modificata una bandiera `requiresRestart`.

### REST API

Tutte le operazioni passano attraverso un unico percorso: [`src/app/api/settings/feature-flags/route.ts`](../../src/app/api/settings/feature-flags/route.ts). Ogni metodo richiede una sessione dashboard autenticata (altrimenti `401` ).

Con login disabilitato (`requireLogin=false`) il percorso è aperto, ad eccezione dei flag protetti: ogni flag della categoria Sicurezza più `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`, `OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS`, `MITM_DISABLE_TLS_VERIFY`, `OMNIROUTE_MCP_ENFORCE_SCOPES` e `SKILLS_SANDBOX_NETWORK_ENABLED` (`isProtectedFeatureFlag()` in `protectedFeatureFlags.ts`). Uno `PUT` su uno di essi e uno `DELETE` mentre uno di essi ha un override DB, necessita comunque di una sessione del dashboard, di una chiave `manage` -scope API, di un token di accesso `oma_` con ambito di scrittura o superiore o del token CLI o del token di servizio interno inviato dal loopback. Questo insieme è più ampio rispetto a quello con il login attivo, dove il percorso accetta solo una sessione o una chiave `manage` -scope.

```jsonc
      "source": "default", // "db" | "env" | "default"
      "requiresRestart": false,
      "warningLevel": "caution",
    },
    // ... all 126 flags
  ],
  "summary": {
    "total": 126,
    "active": 0,
    "inactive": 0,
    "overriddenByDb": 0,

```

#### `PUT /api/settings/feature-flags`

Imposta o rimuovi una singola sostituzione. Corpo: `{ key: string; value?: string }`. L'omissione `value` rimuove l'override (ripristino env/default).

```bash
# Set a DB override
curl -X PUT http://localhost:20128/api/settings/feature-flags \
  -H "Content-Type: application/json" \
  -d '{"key":"REQUIRE_API_KEY","value":"true"}'

# Remove the override (no "value")
curl -X PUT http://localhost:20128/api/settings/feature-flags \
  -H "Content-Type: application/json" \
  -d '{"key":"REQUIRE_API_KEY"}'
```

La risposta fa eco ai nuovi `effectiveValue`/`source`, `previousValue`/ `previousSource` e `requiresRestart`. Chiavi sconosciute e valori enumerativi fuori intervallo vengono rifiutati con `400`.

#### `DELETE /api/settings/feature-flags`

Cancella** Tutto** DB esegue l'override immediatamente, ripristinando ogni flag al suo valore env / predefinito. Restituisce `{ cleared: <count>, message: "..." }`.

> [!NOTE]
> I flag con `requiresRestart: true` hanno effetto solo dopo il ricaricamento del processo. Il flusso di riavvio del dashboard chiama `POST /api/restart` e quindi esegue il polling `GET /api/health/ping` fino al ripristino del server.

## Fallback di emergenza per il budget

`OMNIROUTE_EMERGENCY_FALLBACK` (categoria `runtime`, valore predefinito `true`) controlla il
percorso di fallback gratuito di emergenza in
[`open-sse/services/emergencyFallback.ts`](../../open-sse/services/emergencyFallback.ts).
Quando è abilitato, le richieste che esauriscono il proprio budget vengono instradate verso un
provider/modello di fallback gratuito anziché non riuscire del tutto. Impostarlo su `false` (o `0`) — tramite
l'interruttore nella dashboard, un override nel DB o la variabile di ambiente
`OMNIROUTE_EMERGENCY_FALLBACK` — per disabilitare questo comportamento e lasciare che le richieste
con budget esaurito non vadano a buon fine. (Reso disponibile come interruttore nella dashboard nelle PR #3741 / #3752.)

Una risposta fornita da questo fallback contiene
`X-OmniRoute-Emergency-Fallback: from=<provider/model>; to=<provider/model>`, in modo che un
client possa rilevare che è stata reinstradata senza confrontare `X-OmniRoute-Provider` con la propria
richiesta. L'header è assente in tutte le altre risposte.
