## Completamenti chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Header personalizzati

| Header                   | Direzione | Descrizione                                                                                                                                                                                                                                           |
| ------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Richiesta | Impostare su `true` per ignorare la cache                                                                                                                                                                                                             |
| `x-omniroute-no-memory`  | Richiesta | Impostare su `true` per saltare l'iniezione di memoria e competenze per questa richiesta (rispecchia no-cache ed evita il sovraccarico di token/costi per chiamata)                                                                                   |
| `X-OmniRoute-Progress`   | Richiesta | Impostare su `true` per gli eventi di avanzamento                                                                                                                                                                                                     |
| `X-Session-Id`           | Richiesta | Chiave di sessione persistente per l'affinità con sessioni esterne                                                                                                                                                                                    |
| `x_session_id`           | Richiesta | È accettata anche la variante con trattino basso (HTTP diretto)                                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | Richiesta | Tag di sessione/conversazione fornito dal chiamante (utilizzato anche dalla memoria). Quando presente, viene salvato testualmente in `call_logs.session_tag` per l'attribuzione dei costi per sessione (#8249); non viene mai generato quando assente |
| `Idempotency-Key`        | Richiesta | Chiave di deduplicazione (finestra di 5 s)                                                                                                                                                                                                            |
| `X-Request-Id`           | Richiesta | Chiave di deduplicazione alternativa                                                                                                                                                                                                                  |
| `x-omniroute-connection` | Richiesta | Associa una richiesta per un singolo modello a una connessione del provider (account) tramite il relativo ID; vedere [Associazione dell'account per richiesta](#account-pinning-per-request)                                                          |
| `X-OmniRoute-Cache`      | Risposta  | `HIT` o `MISS` (senza streaming)                                                                                                                                                                                                                      |
| `X-OmniRoute-Idempotent` | Risposta  | `true` se deduplicata                                                                                                                                                                                                                                 |
| `X-OmniRoute-Progress`   | Risposta  | `enabled` se il monitoraggio dell'avanzamento è attivo                                                                                                                                                                                                |
| `X-OmniRoute-Session-Id` | Risposta  | ID di sessione effettivo utilizzato da OmniRoute                                                                                                                                                                                                      |
| `X-OmniRoute-Request-Id` | Risposta  | ID di correlazione della richiesta (quando noto)                                                                                                                                                                                                      |
| `X-OmniRoute-Version`    | Risposta  | Versione della build di OmniRoute (sempre presente)                                                                                                                                                                                                   |
| `X-OmniRoute-Cost-Saved` | Risposta  | Importo in USD risparmiato grazie alla cache in caso di HIT (solo per i riscontri nella cache)                                                                                                                                                        |
| `X-OmniRoute-Decision`   | Risposta  | Traccia dell'instradamento: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` è la strategia della combo oppure `single` per una richiesta non combo); sempre presente nelle risposte di completamento                                    |

> Nota per Nginx: se utilizzi header con caratteri di sottolineatura (ad esempio `x_session_id`), abilita `underscores_in_headers on;`.

#### Associazione dell'account per richiesta

Quando un provider dispone di più connessioni (account o chiavi), OmniRoute normalmente ne seleziona una
tramite la propria strategia di selezione dell'account. Una richiesta può invece essere associata a una connessione
specifica mediante l'header `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Dove trovare l'ID.** Apri la pagina del provider nella dashboard
  (**Dashboard → Provider → <provider>**) e fai clic sul badge dell'ID `xxxxxxxx…` nella riga di una connessione:
  l'ID completo della connessione verrà copiato.
- **Quali richieste lo rispettano.** Le richieste a modello singolo (`provider/model`) su
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. Le combinazioni ignorano l'header: associa
  un account a ogni passaggio della combinazione tramite la connessione specifica del passaggio.
- **L'associazione è rigida, non una preferenza.** La connessione associata viene utilizzata in modo esclusivo. Un
  errore durante la richiesta registra il periodo di cooldown dell'account, ma **non** passa a un
  altro account dello stesso provider.
- **Il cooldown e la quota annullano l'associazione.** Mentre la connessione associata è in cooldown,
  ha esaurito la quota o è bloccata da una policy relativa alla quota, le richieste successive passano alle
  altre connessioni del provider, esattamente come il traffico non associato.
- **Gli ID sconosciuti o disabilitati generano un errore.** Un ID che non appartiene al pool attivo del provider (perché eliminato,
  disattivato o appartenente a un altro provider) non lascia alcun account idoneo, quindi la richiesta
  non riesce invece di essere instradata altrove silenziosamente.

Claude Code invia gli header personalizzati tramite `ANTHROPIC_CUSTOM_HEADERS`. Inseriscilo nel blocco `env`
di `~/.claude/settings.json` oppure in un file `.claude/settings.json` a livello di progetto per associare un
account diverso a ciascun progetto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fonte: `src/sse/handlers/chat.ts` (lettura dell'header), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (rilascio dell'associazione e verifica dell'assenza dal pool).

> **Header di telemetria dei costi:** anche le risposte non in streaming completate con successo includono il set di telemetria dei costi `X-OmniRoute-*`: `X-OmniRoute-Response-Cost` (USD, con 10 cifre decimali fisse; `0.0000000000` per richieste gratuite o senza prezzo), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (solo quando > 0), oltre a `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Questi header vengono emessi dai completamenti di chat, da `/v1/responses`, da `/v1/messages` **e dagli endpoint multimediali**: `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (costo sempre pari a `0`). Il costo dei contenuti multimediali viene calcolato per modalità (per immagine, per secondo, per carattere o per unità di ricerca) quando sono disponibili informazioni sui prezzi; in caso contrario è pari a `0` (comportamento permissivo).

> **Semantica dei costi per i riscontri nella cache:** in caso di HIT della cache semantica (`X-OmniRoute-Cache-Hit: true`) non viene effettuata alcuna chiamata upstream, quindi `X-OmniRoute-Response-Cost` è pari a `0.0000000000` (il costo **incrementale** per servire il riscontro). Il costo originale, o quello che si sarebbe sostenuto, viene riportato separatamente in `X-OmniRoute-Cost-Saved`. I sistemi di fatturazione devono sommare `X-OmniRoute-Response-Cost` (i riscontri non hanno alcun costo); i sistemi di analisi della cache possono aggregare `X-OmniRoute-Cost-Saved`.

## Lease gestiti esclusivi di sessione

Il leasing gestito esclusivo di sessione è un contratto di routing facoltativo e indipendente dal client: un proprietario attivo
detiene una connessione OmniRoute idonea. Non concede in lease un modello, non richiede OAuth, non identifica un
client specifico e non richiede un provider specifico.

La chiave API usata per l'autenticazione deve avere l'ambito `lease:exclusive` e un elenco
`allowedConnections` esplicito e non vuoto. Il limite transazionale delle mutazioni del database applica entrambi i campi congiuntamente durante la
creazione della chiave e gli aggiornamenti parziali.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Le risposte di acquisizione, rinnovo e rilascio riusciti espongono i timestamp, `state` e l'esatto valore positivo di
`generation`, ma mai la connessione selezionata o le credenziali. Il rinnovo e il rilascio specificano la
generazione nel corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Il proprietario di un lease attivo può richiedere esplicitamente metadati di visualizzazione rispettosi della privacy per la propria associazione corrente:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Questa azione di stato facoltativa è protetta, in un'unica transazione del database, dal proprietario opaco, dalla chiave API gestita autenticata e dall'esatta
generazione attiva. `displayName` contiene esclusivamente il nome configurato della
connessione, senza spazi iniziali o finali; è `null` quando non esiste un nome configurato sicuro. OmniRoute non lo sostituisce mai con un
indirizzo email o con un'identità account generata. Il valore del provider è un'etichetta di visualizzazione non sensibile e non è mai
un identificatore generato di provider compatibile. Sono esclusi credenziali, token, cookie, ID non elaborati della connessione o della chiave
API, hash del proprietario, segreti di fencing e dati di routing interni.

Le ricerche con chiave errata, proprietario errato, generazione obsoleta, lease mancante, scaduto, rilasciato o invalidato
restituiscono tutte lo stesso errore `409 LEASE_FENCE_STALE`, senza metadati della connessione. Un client che ha ricevuto la risposta di attesa della capacità non dispone di un'associazione attiva da esaminare. Quando il routing sposta un lease attivo,
la stessa generazione rimane valida e lo stato restituisce atomicamente la nuova associazione, mai quella precedente.
I client esistenti rimangono invariati perché le risposte di acquisizione, rinnovo, rilascio e attesa mantengono
i formati precedenti.

Questo contratto del server non modifica `/status` di OpenAI Codex standard. Attualmente, Codex standard segnala il proprio
provider del modello e lo stato integrato di autenticazione/account, ma non visualizza metadati account arbitrari di
provider personalizzati; una futura integrazione client dovrà chiamare questa azione e decidere come
visualizzare `connection.displayName`.

Ogni richiesta di inferenza gestita fornisce quindi entrambe le intestazioni di controllo:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Il proprietario esatto, la generazione, la connessione attiva e la chiave API autenticata vengono sottoposti a fencing immediatamente
prima di ogni tentativo upstream supportato. La riproduzione di proprietario e generazione con un'altra chiave non riesce anche
quando tale chiave consente la stessa connessione. I proprietari non elaborati non vengono conservati, registrati nei log, mantenuti nello
snapshot della richiesta o inoltrati upstream.

La contesa temporanea restituisce HTTP `429` con `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Questa risposta indica soltanto che l'insieme ordinario di connessioni idonee non era vuoto e che ogni candidato libero era
detenuto da un lease attivo altrui. Modelli/provider non supportati, mancata corrispondenza dei criteri, cooldown, quota,
integrità e altri errori ordinari di idoneità mantengono le risposte OmniRoute esistenti.

### `x-omniroute-compression`

Override per richiesta del piano di compressione. Ha la precedenza più alta: prevale sull'override della combinazione di routing,
sul profilo attivo, sull'attivazione automatica e sull'impostazione predefinita del pannello. Valori:

| Valore        | Effetto                                                                                                              |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| `off`         | Nessuna compressione per questa richiesta.                                                                           |
| `default`     | Il profilo predefinito derivato dal pannello (ignora il profilo attivo). I motori con perdita rimangono disattivati. |
| `safe`        | Solo deduplicazione e riduzione degli spazi vuoti.                                                                   |
| `allow-lossy` | Mantiene il piano dell'operatore per questa richiesta, inclusi riepiloghi e riscritture stilistiche.                 |
| `engine:<id>` | Un singolo motore, se abilitato, ad es. `engine:rtk`. Adesione per richiesta per tale motore.                        |
| `<combo>`     | Una combinazione denominata, cercata prima per nome (senza distinzione tra maiuscole e minuscole), poi per ID.       |

Note:

- I valori sconosciuti vengono ignorati (la richiesta non viene mai rifiutata); la risoluzione prosegue secondo la normale precedenza dell'operatore.
- Se più combinazioni condividono lo stesso nome, specificare l'**id** della combinazione per ottenere una corrispondenza deterministica.
- Una combinazione il cui nome è `off` o `default` non può essere selezionata per nome (queste parole chiave vengono interpretate per prime); fare riferimento a tale combinazione tramite il relativo ID.
- L'interruttore principale della compressione è un vincolo assoluto: quando la compressione è disabilitata globalmente, questa intestazione non può abilitarla.

Il piano applicato viene restituito nell'intestazione della risposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

dove `<source>` è uno tra `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` oppure `off`.

## Embedding

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Provider disponibili: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Gli ID del catalogo sono nel formato `provider/model` (esempio: `jina-ai/jina-embeddings-v5-omni-small`). Vengono risolti anche gli ID dei modelli Jina senza prefisso presenti nel registro (ad esempio `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`). Le operazioni Jina di embedding/rerank/classificazione/segmentazione usano prima le credenziali `jina-ai` della dashboard; `JINA_AI_API_KEY` viene usata come fallback solo quando non esiste alcuna chiave nella dashboard. La scheda `jina-reader` è riservata a Reader / `r.jina.ai` (`POST /v1/web/fetch`) e non fornisce mai embedding o rerank.

I modelli del registro che dichiarano il supporto multimodale accettano anche fino a 32 elementi strutturati
indipendenti dal provider. I tipi di elementi multimediali sono `text`, `image`, `audio`, `video` e `document`. Il relativo `source`
è `{"type":"url","url":"https://..."}` oppure
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
e l'alias della famiglia `jina-ai/jina-embeddings-v5-omni` → omni-small) accetta anche i documenti EmbeddingsV5Request
nativi di Jina e **li inoltra intatti** a `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

I valori nativi `{ image | audio | video | pdf }` possono essere un URL HTTPS pubblico, un URI `data:` oppure dati
base64 non elaborati. OmniRoute non converte tali oggetti in stringhe né recupera gli URL delle immagini native: Jina recupera
direttamente i contenuti multimediali pubblici. I campi Jina aggiuntivi (`task`, `normalized`, `truncate`, `embedding_type`) vengono
inoltrati. Gli SKU Jina solo testuali continuano a rifiutare i documenti non testuali.

Limiti di sicurezza e trasporto:

- Gli URL dei contenuti multimediali remoti devono essere HTTPS pubblici. Gli elementi canonici `{type,source:url}` vengono recuperati
  lato server (nuova convalida dei reindirizzamenti, timeout, limiti di dimensione, DNS pubblico, pinning della connessione) e
  incorporati prima della chiamata al provider. Gli elementi nativi Jina `{image:"https://..."}` vengono inoltrati così come sono
  dopo lo stesso controllo HTTPS pubblico; Jina recupera l'URL.
- I contenuti multimediali base64 incorporati sono limitati a 8 MiB decodificati per elemento e a 16 MiB decodificati per l'intera richiesta.

Traduzione per provider (gli elementi canonici non vengono mai inoltrati senza modifiche):

- Modelli multimodali Jina: ogni elemento di primo livello diventa un oggetto con chiave corrispondente alla modalità
  (`text` / `image` / `audio` / `video` / `pdf`), usando URI di dati per i contenuti multimediali incorporati; un vettore per
  ogni elemento di primo livello.
- Famiglia Gemini Embedding 2: un array di primo livello diventa una singola richiesta nativa
  `models/{model}:embedContent` con `content.parts` (`text` o `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualsiasi modello caricato dal server locale): gli elementi canonici `text`
  diventano stringhe semplici, mentre `image` / `audio` / `video` diventano ciascuno un oggetto
  `{"content": [part]}`, usando le parti di contenuto chat di llama-server (`image_url`,
  `input_audio` con formato `wav` / `mp3` / `flac`, `input_video`) con dati incorporati; un vettore
  per ogni elemento di primo livello. Il server deve essere eseguito con `--embedding --mmproj …`; senza un proiettore,
  rifiuta autonomamente i contenuti multimediali. `document` non è supportato.
- I modelli sconosciuti/dinamici senza metadati espliciti sulle modalità rifiutano l'input strutturato con HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Le combinazioni modello/modalità non supportate restituiscono HTTP 400 anziché forzare la conversione dell'elemento. I campi di estensione
diversi dall'input nelle richieste legacy con stringhe/token continuano a essere inoltrati senza modifiche.

```bash
# Elenca tutti i modelli di embedding
GET /v1/embeddings
```

## Generazione di immagini

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

I provider disponibili includono OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (locale), ComfyUI (locale).

`n` restituisce `n` immagini in `data[]`. Per i provider la cui API a monte restituisce un'immagine per chiamata
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), vengono effettuate `n` chiamate separate a monte, con un massimo di 4 simultanee. Un
`seed` fisso viene incrementato in base all'indice della chiamata (`seed`, `seed + 1`, …), così le immagini risultano diverse ma rimangono
riproducibili. `n` è limitato a 10. L'intera richiesta non riesce se una qualsiasi chiamata non riesce. L'elenco
dei formati con fan-out è `SINGLE_IMAGE_FANOUT_FORMATS` in
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux riutilizza la connessione con chiave API esistente e accetta i prefissi `zenmux/` o `zm/`:

- `zenmux/openai/gpt-image-2` utilizza l'API OpenAI Images di ZenMux. Le opzioni includono `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Gli altri publisher, come `zm/meta/muse-image-1.0`, utilizzano l'endpoint `:predict`
  di Vertex AI tramite ZenMux. `n` viene mappato a `sampleCount`, `aspect_ratio` a `aspectRatio` e `image_size`
  (`1K`, `2K`, `4K`) a `sampleImageSize`. Un valore `size` in pixel specifica solo le proporzioni,
  non dimensioni in pixel garantite. Le proporzioni, le risoluzioni e le quantità supportate variano in base al modello.
- `zm/inclusionai/ming-image-0.1-design` sceglie autonomamente le proprie dimensioni. Omettere `size`,
  `aspect_ratio` e `image_size`; i valori espliciti restituiscono HTTP 400. È possibile richiedere PNG, JPEG e WebP
  tramite `output_format`.

Questa integrazione supporta la generazione da testo a immagine, non la modifica di immagini di riferimento. L'output di Vertex
viene normalizzato in `data[].b64_json`; `response_format: "url"` restituisce un URL HTTPS a monte
oppure un URL dati base64 quando sono disponibili solo i byte dell'immagine. Gli output vuoti/filtrati
restituiscono un errore anziché un successo vuoto. L'accesso ai modelli dipende dall'account ZenMux.
Consultare l'[API Vertex di ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) e
l'[API OpenAI Images](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Elenca tutti i modelli di immagini
GET /v1/images/generations
```

## OCR dei documenti

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleziona il provider OCR tramite un prefisso `provider/model`; un ID modello senza prefisso (ad esempio
`mistral-ocr-latest`) viene associato al relativo provider registrato, mentre se `model` viene omesso, il valore predefinito è
Mistral (`mistral-ocr-latest`). Provider registrati (`open-sse/config/ocrRegistry.ts`):

| ID provider                   | ID modello           | Valore `model`                                                      | Note                                                                                                                    |
| ----------------------------- | -------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (o semplicemente `mistral-ocr-latest`) | Sincrono: la risposta viene restituita direttamente dalla singola chiamata a monte.                                     |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                         | Servizio a monte asincrono (`analyze` + polling): vedere di seguito.                                                    |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                             | Sincrono, tramite l'endpoint partner `openapi/chat/completions` di Vertex AI: vedere di seguito per autenticazione/URL. |

Tutti e tre i provider rispondono con lo stesso corpo nel formato di Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Flusso di polling di Azure Document Intelligence

L'API `analyze` di Azure Document Intelligence è asincrona: la richiesta iniziale restituisce
un'intestazione `Operation-Location` anziché un corpo e il risultato deve essere recuperato tramite polling. L'handler
(`open-sse/handlers/ocr.ts`) esegue il polling di tale URL ogni secondo per un massimo di 30 tentativi, termina immediatamente (senza
continuare il polling) in caso di risposta al polling non `ok` o di stato `"failed"` e restituisce `504` se
l'operazione è ancora in esecuzione dopo l'esaurimento del numero di tentativi. La risposta finale di Azure viene
normalizzata nello stesso formato `pages`/`markdown` utilizzato da Mistral prima di essere restituita al
chiamante, così il codice client non deve gestire il provider come caso speciale.

### Autenticazione e risoluzione dell'endpoint OCR DeepSeek di Vertex AI

`vertex-deepseek-ocr` riutilizza la stessa autenticazione Vertex AI già supportata da OmniRoute per
il traffico di chat/immagini (`open-sse/executors/vertex.ts`): la chiave API della connessione è una
credenziale JSON di un Service Account (scambiata con un token di accesso OAuth di breve durata tramite il flusso JWT-bearer)
oppure un token di accesso OAuth già emesso, utilizzato così com'è. L'URL dell'endpoint a monte è
l'endpoint partner generico `openapi/chat/completions` di Vertex, creato a partire dal progetto e dalla
regione della connessione: un valore esplicito di `providerSpecificData.project`/`providerSpecificData.region` ha sempre la precedenza;
in caso contrario, il progetto viene ricavato dal campo `project_id` del JSON del Service Account e il valore predefinito della regione
è `us-central1`. Entrambe le risoluzioni avvengono in `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e vengono utilizzate da
`src/app/api/v1/ocr/route.ts` prima dell'inoltro a `handleOcr`.

## Elenco dei modelli

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Restituisce tutti i modelli di chat, embedding e immagini + le combinazioni nel formato OpenAI
```

### Prezzi dei modelli (`pricing`)

Una voce include un oggetto `pricing` quando OmniRoute conosce il prezzo del modello. Il prezzo proviene
dalla tabella dei prezzi utilizzata per la contabilizzazione dei costi: valori predefiniti integrati, prezzi sincronizzati e
sostituzioni impostate tramite `/api/pricing`. Si tratta di prezzi di listino, quindi anche i provider in abbonamento
mostrano un prezzo per token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Campi                                                           | Unità                              | Note                                                                                                                                                                   |
| --------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD per token, stringa decimale    | Compatibile con OpenRouter, mai in notazione esponenziale. I due campi della cache sono presenti solo quando esiste un prezzo per la cache.                            |
| `input`, `output`, `cached`, `cache_creation`                   | USD per 1 milione di token, numero | Campi delle versioni precedenti del catalogo, mantenuti per i client esistenti. Anche `reasoning` e `long_context` sono presenti quando la riga dei prezzi li include. |

- Le **combinazioni** riportano il prezzo della loro prima destinazione visibile. Le combinazioni integrate `auto/*` scelgono una
  destinazione al momento della richiesta, quindi non hanno `pricing`.
- I **modelli gratuiti** mostrano `"0"` (e `0`) quando il loro prezzo è zero. Un modello privo di una riga dei prezzi
  mostra anch'esso `"0"` quando il catalogo lo contrassegna come gratuito (`free: true`) o quando è incluso nel catalogo
  integrato dei modelli gratuiti.
- **Prezzo sconosciuto:** la voce non contiene la chiave `pricing`.
- I **provider con fatturazione a crediti** (come Kiro) fatturano per richiesta anziché per token. Le loro
  voci mantengono i campi numerici per 1 milione di token che avevano in precedenza e non contengono campi stringa per token.
- Le **varianti** (ID relativi allo sforzo di ragionamento, alias senza ragionamento, mirror di discovery e gateway)
  copiano il prezzo del modello verso cui instradano.
- I campi contengono solo le tariffe di base. I livelli per contesti lunghi (il campo numerico `long_context`) e
  i moltiplicatori del livello di servizio (ad esempio Codex fast o flex) non modificano `prompt` o
  `completion`.
- L'oggetto è lo stesso per ogni modalità di autenticazione, inclusa una richiesta in stile Anthropic
  con `x-api-key` e `anthropic-version` (la risposta rimane `{ "object": "list",
"data": [...] }`). Implementazione: `src/app/api/v1/models/catalogPricing.ts`.

### Prefissi degli ID dei modelli (`?prefix=`)

La maggior parte dei modelli viene pubblicizzata con un **prefisso del provider**. Il prefisso ottenuto è controllato dal
feature flag `MODELS_CATALOG_PREFIX_MODE` e può essere sostituito **per ogni richiesta** con un
parametro di query, utile per un client che desidera un elenco pulito senza modificare l'impostazione globale
del server per tutti gli altri:

```bash
GET /v1/models?prefix=alias        # un ID per modello: il prefisso breve dell'alias
GET /v1/models?prefix=dual         # entrambe le forme (impostazione predefinita del server)
GET /v1/models?prefix=canonical    # solo il prefisso completo dell'ID del provider
```

| Modalità    | Restituisce                                             | Note                                                                                                                                                                                                                                               |
| ----------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **e** `claude/claude-sonnet-4-6` | **Predefinita.** Entrambi gli ID instradano allo stesso modello; vengono mantenuti affinché le configurazioni dei client che hanno codificato direttamente una delle due forme continuino a funzionare. Raddoppia approssimativamente il catalogo. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Una voce per modello. I provider senza un alias distinto restituiscono comunque la propria voce, quindi non si perde nulla.                                                                                                                        |
| `canonical` | `claude/claude-sonnet-4-6`                              | Una voce per modello con il prefisso completo dell'ID del provider. Anche i provider senza un alias distinto (ad esempio `antigravity/…`, `agy/…`) restituiscono qui il proprio unico ID, quindi non si perde nulla.                               |

Un mirror in modalità `dual` può essere riconosciuto anche senza il parametro di query: contiene un campo `parent`
che punta all'ID principale.

I client che visualizzano un selettore di modelli dovrebbero richiedere `?prefix=alias`: è ciò che fa
[l'estensione OmniCopilot per VS Code](../guides/VSCODE-COPILOT.md).

### Filtri di discovery (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accetta filtri di discovery facoltativi. In assenza di questi filtri, la risposta rimane
invariata. I filtri restringono il catalogo già visibile al chiamante (vengono applicate prima le autorizzazioni della chiave API)
e vengono elaborati prima della paginazione in stile OpenAI con `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # tutte le funzionalità elencate devono essere vere
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` del catalogo; le righe senza un valore sono `chat`
GET /v1/models?q=sonnet&limit=10                           # corrispondenza senza distinzione tra maiuscole e minuscole nell'ID o nel nome
```

| Parametro     | Valori                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | numero intero non negativo, confrontato con `context_length`                                        |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caratteri                                                                                     |

Un valore sconosciuto, oppure un `min_context` che non è un numero intero non negativo (ad esempio `1.5`),
restituisce HTTP `400` e il messaggio elenca i valori validi. Implementazione:
`src/app/api/v1/models/catalogFilters.ts`.

### Selezione ristretta dei modelli (`POST /v1/models/query`)

`POST /v1/models/query` restituisce un elenco breve e deterministico dallo stesso catalogo, con la stessa
autenticazione e visibilità per chiave di `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Ogni campo è facoltativo. `capabilities` ed `exclude` accettano un array o una stringa separata da virgole;
`max_output` viene confrontato con `max_output_tokens`. I risultati sono ordinati prima per `owned_by`, quindi per `id`.
Il valore predefinito di `limit` è `20` e i valori superiori a `100` vengono limitati a `100`. JSON non valido, un campo
sconosciuto o un valore non valido restituiscono HTTP `400`.

### Modelli di chat nascosti singolarmente

Un modello contrassegnato come **Nascosto** nella pagina del relativo provider viene escluso dal catalogo e rifiutato
con HTTP `404` / `model_not_found` quando viene richiesto esplicitamente. Il controllo utilizza il provider e il modello
risolti, inclusi gli alias dei provider, i prefissi dei nodi dei provider compatibili e le impostazioni predefinite
della connessione. Una combinazione ignora le destinazioni nascoste e può utilizzare un modello correlato visibile; quando non
rimane alcuna destinazione eseguibile, restituisce lo stesso codice di errore. La rimozione dell'impostazione Nascosto ha effetto alla richiesta
successiva. Le sostituzioni della visibilità relative alle sole immagini non nascondono il modello di chat con lo stesso ID.

Questa impostazione del singolo modello è separata dagli
[elenchi di inclusione/esclusione per l'esposizione dei modelli](../routing/MODEL_EXPOSURE_LIST.md), che filtrano
la pubblicazione nel catalogo e i candidati per l'instradamento automatico, mantenendo al contempo l'invio esplicito. Le autorizzazioni
dei modelli per le chiavi API continuano ad applicarsi in modo indipendente. La modalità predefinita dei prefissi del catalogo rimane `dual`.

### Varianti dei modelli senza thinking

Per i modelli Claude compatibili con il thinking, `/v1/models` pubblica anche una variante **senza thinking** il cui ID ha come prefisso `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

La selezione di questo ID (ad esempio, in una configurazione di Claude Code che include sempre un blocco `thinking`) viene ricondotta al vero `<provider>/<model>` con il ragionamento disabilitato: `thinking:{type:"disabled"}` nel percorso `/v1/messages`, oppure con i campi `reasoning`/`reasoning_effort` rimossi nel percorso `/v1/chat/completions`. La variante viene elencata solo per i modelli della famiglia Claude che supportano il thinking **e** rispettano `disabled` (pertanto, ad esempio, sono esclusi i modelli esclusivamente adattivi che rifiutano `disabled`). Gli operatori possono abilitare o disabilitare forzatamente la variante per ciascun modello tramite `ModelSpec.noThinkingAlias`.

## Generazione audio con ElevenLabs

Configura in OmniRoute una connessione al provider `elevenlabs` con la tua chiave API ElevenLabs.
I client si autenticano con la propria chiave **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
il gateway fornisce la chiave del provider memorizzata come `xi-api-key`. Non inviare mai una chiave ElevenLabs
come token bearer del gateway.

| Metodo | Percorso                    | Risposta                                   | Categoria dell'endpoint della chiave API |
| ------ | --------------------------- | ------------------------------------------ | ---------------------------------------- |
| POST   | `/v1/sound-generation`      | Byte audio nativi                          | `elevenlabs`                             |
| POST   | `/v1/music`                 | Byte audio nativi                          | `music`                                  |
| POST   | `/v1/music/stream`          | Byte audio in streaming                    | `music`                                  |
| POST   | `/v1/music/detailed`        | Audio multipart nativo e piano compositivo | `music`                                  |
| POST   | `/v1/music/detailed/stream` | Metadati SSE nativi e frammenti audio      | `music`                                  |
| POST   | `/v1/music/plan`            | Piano compositivo JSON                     | `music`                                  |

Questi endpoint integrano le route esistenti `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` e `/v1/speech-to-text`. I campi JSON nativi
e i parametri di query come `output_format` e `enable_logging` vengono mantenuti.
Le risposte di `/v1/music/detailed` mantengono i propri delimitatori multipart; analizzale come multipart.
`/v1/music/detailed/stream` restituisce `text/event-stream` con i metadati della composizione e
frammenti audio base64 negli eventi SSE. Tutte e sei le route supportano la preflight CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Un breve effetto sonoro. Durata: da 0,5 a 30 secondi.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# La durata della musica è espressa in millisecondi: da 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilizza `/v1/music/stream` con lo stesso corpo JSON per la distribuzione incrementale dell'audio. La composizione
accetta esattamente uno tra `prompt` e `composition_plan`; `/v1/music/plan` richiede `prompt`
e accetta facoltativamente `source_composition_plan`. Gli schemi nativi mantengono i campi aggiuntivi
del provider affinché le versioni del piano compositivo e le opzioni di fine-tuning raggiungano ElevenLabs.

Anche l'endpoint unificato `/v1/music/generations` accetta `elevenlabs/music_v1`,
`elevenlabs/music_v2` e `elevenlabs/music_v2_5`. Con una connessione ElevenLabs attiva,
questi modelli vengono esposti dal catalogo musicale. Questo endpoint restituisce
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Il relativo campo `duration` è espresso in
secondi e viene mappato a `music_length_ms`; un valore `music_length_ms` esplicito ha la precedenza.
`instrumental` viene mappato a `force_instrumental`, con precedenza per il campo nativo.
Utilizza gli endpoint di streaming nativi per lo streaming e l'endpoint di composizione nativo
per le richieste basate esclusivamente su un piano compositivo.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Le restrizioni relative a endpoint, modello, budget e connessione vengono applicate prima di una chiamata upstream. Le route
native restituiscono invariati i codici di stato e i corpi degli errori upstream, incluso `402` per una restrizione
del piano e `429` per un limite di quota. Le intestazioni `character-cost`, `song-id`, `request-id` e `retry-after`
vengono mantenute quando presenti. Un saldo di crediti gratuiti non garantisce l'accesso a ogni
modello musicale, formato di output o funzionalità API: ElevenLabs determina l'idoneità per ciascuna richiesta.
L'endpoint unificato mantiene i codici di stato degli errori nell'envelope di errore normalizzato di OmniRoute.

Contratti upstream: [effetti sonori](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composizione musicale](https://elevenlabs.io/docs/api-reference/music/compose) e
[dettagli della musica in streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

# Reranking (provider del registro cloud oppure nodo provider compatibile con OpenAI come "<prefix>/<model>")

> **Nodi provider di reranking:** `POST /v1/rerank` instrada anche verso nodi provider compatibili con OpenAI
> (oMLX, vLLM, Infinity, TEI dietro un gateway, …) indirizzati come `<node-prefix>/<model>`. I nodi
> di loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) sono sempre idonei, così come i nomi host
> elencati dall'operatore in `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (ad es. il nome di un servizio
> Docker/Compose come `http://reranker:8080/v1`; questi vengono chiamati direttamente, mai tramite
> `HTTP(S)_PROXY` o il proxy fissato di una connessione). I nodi su qualsiasi altro
> host, ad esempio una macchina nella LAN o un peer Tailscale, sono idonei solo quando l'operatore abilita
> il flag di funzionalità `RERANK_REMOTE_PROVIDER_NODES` **e** l'URL di base del nodo soddisfa i criteri
> relativi agli URL in uscita del provider (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Il passaggio di reranking del motore di memoria chiama questa route tramite
> loopback, quindi la stessa regola disciplina `rerankProviderModel` nelle impostazioni della memoria.
>
> **Formati dei server locali:** il nodo viene chiamato all'indirizzo `<base>/v1/rerank` e, in caso di errore 404, all'indirizzo `<base>/rerank`
> (Infinity, TEI). Il corpo inviato all'upstream include sia la nomenclatura Cohere/OpenAI (`documents`,
> `return_documents`) sia quella TEI (`texts`, `return_text`), mentre la risposta upstream viene
> normalizzata nel formato Cohere: l'array semplice di TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> proveniente da gateway leggeri e il formato Voyage `{data: [...]}` vengono tutti restituiti al client come
> `{results: [{index, relevance_score, document?}]}`, ordinati per punteggio e limitati a `top_n`.

> **Rilevamento dei nodi provider:** i modelli su un nodo provider compatibile con OpenAI appaiono in `GET /v1/models`
> sotto il prefisso del nodo. Le righe prive di metadati degli endpoint (tipiche degli elenchi locali di `/v1/models`)
> ereditano l'`apiType` del nodo, quindi i modelli di un nodo `embeddings` sono `type: "embedding"` e quelli di un
> nodo `rerank` sono `type: "rerank"` anziché usare la chat come valore predefinito; un valore
> `supportedEndpoints` esplicito in una riga sincronizzata o aggiunta manualmente ha comunque la precedenza.

### `provider_options` di Exa e Tavily

Exa e Tavily leggono i campi specifici del provider da un contenitore con namespace:
`provider_options.exa` (o `provider_options["exa-search"]`) e `provider_options.tavily`
(o `provider_options["tavily-search"]`). Vengono inoltrate solo le chiavi riportate di seguito. Ciascuna viene
verificata rispetto al proprio schema Zod in `open-sse/handlers/search/providerOptionsPassthrough.ts`
e una chiave con un tipo errato viene scartata. Qualsiasi altra chiave viene ignorata, incluse quelle relative ad autenticazione, URL di base,
`stream` e `outputSchema`. Le chiavi non annidate utilizzate dagli altri provider (`cx`, `depth`, ...) continuano a funzionare
come prima.

| Provider | Campi di primo livello                                                                                                                                                                                                                                                                                                                                                    | Annidati                                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitive non annidate), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                       | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` uniti ai valori predefiniti `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                     |

I campi generici hanno sempre la precedenza: `query`, `max_results`, `filters` (domini), `country` e l'argomento
derivato da `search_type`. In Exa, `search_type: "news"` mantiene `category: "news"`.
Tavily accetta anche `search_type: "finance"` (`topic: "finance"`).

Il campo generico `time_range` ora raggiunge entrambi i provider: Exa riceve `startPublishedDate` (timestamp
ISO) e Tavily riceve `start_date` (`YYYY-MM-DD`). Una data esplicita in `provider_options`
sovrascrive quella mappata.

I risultati di Exa mantengono `id`, `highlight_scores`, `summary`, `subpages`, `entities` ed `extras` in
`provider_raw`. I risultati di Tavily mantengono `images` e `favicon`.

La contabilizzazione dei costi utilizza ancora il registro non annidato `costPerQuery`. Tavily addebita
più crediti per chiamata per `search_depth: "advanced"` e tale differenza non è riportata in
`usage.search_cost_usd`.

## API Web Fetch

Estrae contenuti da un URL tramite un provider di web fetch configurato (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, stessa chiave API di Parallel Search) restituisce solo
Markdown — qualsiasi altro `format` produce un `400` — e limita il contenuto a 100.000 caratteri.
Quando la pagina di destinazione non può essere estratta, il servizio upstream lo segnala all'interno
di una risposta HTTP 200; OmniRoute espone tale condizione come `422` con un messaggio fisso.

| Metodo | Percorso        | Descrizione                                                                     |
| ------ | --------------- | ------------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Recupera/esegue lo scraping di un URL — corpo convalidato da `v1WebFetchSchema` |

**Autenticazione:** chiave API Bearer (`extractApiKey` + `isValidApiKey`). Criteri applicati tramite `enforceApiKeyPolicy`.

**Fallback basato sulla quota (#8297):** quando non viene specificato alcun `provider`, il pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) viene
scorso secondo un ordine di priorità fisso
(fill-first): un provider configurato ma soggetto a limitazione di frequenza viene ignorato
anziché interrompere immediatamente la richiesta, mentre un errore upstream riprovabile o
relativo alla quota (HTTP 429 sempre; 402/403 per i livelli gratuiti con limiti di quota di
Firecrawl/Tavily/TinyFish — non per Jina Reader e mai per una semplice richiesta non valida
con stato 400) determina il passaggio, al momento della richiesta, al successivo provider
non ancora provato e dotato di credenziali. Quando tutti i provider del pool sono esauriti,
l'endpoint restituisce un singolo `429` (con un'intestazione `Retry-After`) anziché il
precedente `400` generico. Quando viene richiesto un `provider` esplicito, **non** viene
eseguito alcun fallback implicito: un provider esplicito soggetto a limitazione di frequenza
o non funzionante espone il proprio errore (`429` se soggetto a limitazione di frequenza,
altrimenti lo stato upstream).

## Streaming WebSocket

```bash
GET /v1/ws?handshake=1
```

Convalida un handshake di aggiornamento WebSocket e restituisce i messaggi di esempio del protocollo wire (`request`, `cancel`). I frame WS effettivi vengono gestiti dal server WS incluso, al di fuori della tabella delle route di Next.js.

**Autenticazione:** chiave API Bearer durante l'handshake.

### Responses API tramite WebSocket (solo codex)

```bash
# Stessi host e porta dell'API HTTP (valore predefinito 20128); esegue l'upgrade della connessione:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (oppure: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Il primo frame DEVE essere response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Un proxy Responses API tramite WebSocket è collegato **esclusivamente a `codex`** (backend
ChatGPT). Resta in ascolto sulla stessa porta dell'API/dashboard nei percorsi `/v1/responses`,
`/responses` e `/api/v1/responses`. Al primo frame `response.create`, esegue
l'autenticazione e la preparazione tramite il bridge interno `codex-responses-ws`, seleziona
una connessione OAuth codex e crea un tunnel verso `wss://chatgpt.com/backend-api/codex/responses`
tramite il trasporto `wreq-js`. **I modelli non codex vengono rifiutati** (`codex_ws_provider_required`).
Per il routing con condivisione della quota, usa `model: "qtSd/<group>/codex/<model>"`. Implementato in
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticazione:** chiave API Bearer durante l'handshake. Il server HTTP incluso (`server-ws.mjs`)
deve essere l'entry point attivo (e lo è per impostazione predefinita quando esiste `app/server-ws.mjs`).

#### ID del modello: usa l'ID ChatGPT semplice (senza il prefisso `codex/`)

La **Codex CLI** di OpenAI convalida il nome del modello lato client quando
`supports_websockets = true` e **rifiuta gli ID con prefisso del provider**, come
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Invia l'ID **semplice** (ad esempio `gpt-5.5`). Il bridge di
OmniRoute è riservato a codex, quindi prima di creare il tunnel upstream risolve nuovamente
un ID semplice come modello codex (`resolveCodexWsModelInfo`), anche se un ID semplice
`gpt-5.5` verrebbe altrimenti instradato verso un altro provider tramite HTTP.

#### Configurazione della Codex CLI di OpenAI

Indirizza la Codex CLI verso OmniRoute aggiungendo a `~/.codex/config.toml` un provider
personalizzato con supporto WebSocket (usa un `CODEX_HOME` separato per evitare di modificare
una configurazione esistente):

```toml
model = "gpt-5.5"                 # ID semplice — NON "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # nessuna barra finale; l'URL WS viene derivato (usa https/wss in produzione)
wire_api = "responses"                    # unico valore supportato da febbraio 2026
supports_websockets = true                # abilita il trasporto Responses tramite WS
env_key = "OMNIROUTE_API_KEY"             # contiene la chiave API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # una chiave API OmniRoute (qualsiasi chiave se REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

La CLI aggiorna `base_url + /responses` a una connessione WebSocket e OmniRoute crea un tunnel
verso la connessione OAuth codex selezionata. Flusso convalidato end-to-end rispetto al server
locale: ChatGPT restituisce `codex.rate_limits` + `response.created` e trasmette in streaming il
completamento.

## Utilizzo self-service (`/api/usage/om-usage`)

Qualsiasi chiave API può leggere il **proprio** utilizzo e le proprie quote, senza autenticazione di gestione. Questo è l'endpoint usato da un
client (CLI, il pannello OmniCopilot) per mostrare al titolare di una chiave la propria spesa.

```bash
# Formato testuale (il contratto storico: testo normale per un terminale)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato strutturato: quello utilizzato da un'interfaccia utente
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

La chiave deve avere **`allowUsageCommand`** abilitato (disabilitato per impostazione predefinita: il gestore
delle chiavi API della dashboard lo abilita o disabilita per ogni chiave). Senza questa opzione, l'endpoint risponde con `403`.

`?format=json` restituisce una struttura discriminata, in modo che il chiamante non legga mai un campo dati da una
risposta di rifiuto. In caso di esito positivo:

```jsonc
{
  "allowed": true,
  // presente solo quando la chiave ha attivato limiti di utilizzo per chiave (USD giornalieri/settimanali):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // l'istantanea della quota del provider selezionato, oppure null quando non è ancora presente nella cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // le istantanee di tutte le connessioni, affinché un'interfaccia utente possa mostrare più provider affiancati:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

In caso di rifiuto (`401` chiave non valida / `403` operazione non consentita), lo stesso percorso restituisce
`{ "allowed": false, "error": { "message": "…" } }`: un campo `personal`/`provider` presente ma vuoto
(chiave autorizzata, nessun dato ancora acquisito) rappresenta uno stato diverso da un rifiuto e solo il formato JSON
permette di distinguerli.

**Autenticazione:** la chiave API Bearer del chiamante, convalidata tramite `isValidApiKey`: questa _non_ è
l'interfaccia di gestione (`/api/keys/…`), che rimane protetta da `requireManagementAuth`.

### Percentuali di quota non elaborate e rettificate in base alla soglia limite

Quando utilizzano `/api/usage/om-usage`, i chiamanti devono tenere presente la differenza tra le
percentuali presentate dall'**output in testo normale** e quelle dell'**output JSON** strutturato:

| Aspetto                                     | Formato in testo normale (`/api/usage/om-usage` / `@@om-usage`)                                                           | Formato JSON (`?format=json`)                                                                     |
| :------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------ |
| **Campo di output**                         | `NN% left` (ad es., `20% left`)                                                                                           | `provider.quotas` / `providers[].quotas`                                                          |
| **Misurazione**                             | **Disponibilità utilizzabile rettificata in base alla soglia limite**: capacità rimanente al di sopra della soglia limite | **Quota upstream non elaborata**: misurazione del provider non rettificata                        |
| **Riscalatura rispetto alla soglia limite** | Riscalata tramite `effectiveRemainingPercent()` affinché la riserva protetta venga indicata come `0% left`                | Nessuna (valori non elaborati dell'istantanea, così come comunicati dal provider)                 |
| **Dati della soglia**                       | Incorporati nella percentuale visualizzata                                                                                | Memorizzati in `quotaWindowThresholds` per ciascuna connessione (o valori predefiniti del server) |
| **Utilizzatore principale**                 | CLI interattive, prompt del terminale, operatori umani                                                                    | Integrazioni programmatiche, dashboard, analisi, strumenti di monitoraggio della fatturazione     |

#### Formula di rettifica in base alla soglia limite

OmniRoute supporta soglie limite proattive per le quote, allo scopo di prevenire l'esaurimento delle risorse upstream (configurate tramite
`quotaWindowThresholds` della connessione, valori predefiniti del provider o impostazioni globali di resilienza). Quando è attiva una soglia limite
(ad es., `cutoff = 25%`) per una finestra di quota, il renderer di testo calcola la disponibilità rimanente nel modo seguente:

- Se `remaining <= cutoff`: restituisce `0%`.
- Se `remaining > cutoff`: restituisce `((remaining - cutoff) / (100 - cutoff)) * 100`.

L'output testuale formattato arrotonda il valore all'intero più vicino (`Math.round(...)`).

#### Esempio illustrativo

Si consideri una finestra del provider con **un utilizzo non elaborato del 60%** (quindi **il 40% di quota non elaborata rimanente**) e una soglia limite configurata
del **25% della quota rimanente**:

| Rappresentazione                        | Calcolo                                            | Rimanente |           Utilizzo implicito           |
| :-------------------------------------- | :------------------------------------------------- | :-------: | :------------------------------------: |
| **JSON non elaborato (`?format=json`)** | Istantanea upstream (`quotas[window]`)             |  **40%**  |                **60%**                 |
| **Formato testuale (`NN% left`)**       | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (calcolando `100 - remaining`) |

- **Perché il testo mostra il 20% rimanente:** del 40% di quota fisica rimasta sull'account, il 25% è riservato dalla
  politica della soglia limite. Al chiamante rimane solo il 15% dei 75 punti percentuali di margine utilizzabile prima che il router interrompa
  l'instradamento verso questa connessione. La riscalatura garantisce che la connessione segnali l'esaurimento (`0% left`) esattamente quando
  l'instradamento verrà interrotto.
- **Perché JSON conserva i valori non elaborati:** il payload JSON restituisce l'istantanea esatta del provider (`UsageSnapshot`),
  affinché gli strumenti esterni possano accedere all'utilizzo upstream effettivo e ai
  `quotaWindowThresholds` a livello di connessione senza una riscalatura con perdita di informazioni lato server.

#### Indicazioni per la migrazione dei consumer

Se un'integrazione esterna (come un plugin per editor o un'estensione per agenti) in precedenza estraeva dati dall'endpoint
testuale (`NN% left`) e calcolava la percentuale utilizzata come `100 - NN`, la migrazione a `?format=json` comporta quanto segue:

- La lettura dei valori JSON non elaborati rifletterà il **consumo effettivo a monte** (60% utilizzato nell'esempio precedente).
- Se l'integrazione desidera preservare la semantica della disponibilità utilizzabile dell'endpoint testuale, può valutare
  lato client la formula per la disponibilità effettiva rimanente utilizzando `quotaWindowThresholds` per gli override a livello di connessione.

## Cache semantica

```bash
# Ottieni le statistiche della cache
GET /api/cache/stats

# Svuota tutte le cache
DELETE /api/cache/stats
```

Esempio di risposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impatto sulla latenza

Un HIT della cache semantica restituisce la risposta dalla cache **senza una
chiamata upstream**, pertanto il valore riportato in `X-OmniRoute-Response-Latency` è prossimo allo zero
(indipendentemente dalla latenza upstream originale). I client sensibili alla latenza
(benchmark, monitoraggio p50/p99) devono controllare l'header di risposta
`X-OmniRoute-Cache-Latency`:

| Valore      | Significato                                                               |
| ----------- | ------------------------------------------------------------------------- |
| `synthetic` | Risposta restituita dalla cache; la latenza non è il tempo upstream reale |
| _(assente)_ | Risposta proveniente da una chiamata upstream reale                       |

### Esclusione dalla cache per chiave

Le chiavi API possono disattivare le letture dalla cache semantica tramite `cacheDefaultMode`:

| Valore   | Comportamento                                                      |
| -------- | ------------------------------------------------------------------ |
| `legacy` | Comportamento normale della cache (predefinito)                    |
| `bypass` | Ignora completamente la ricerca nella cache; usa sempre l'upstream |

Impostare durante la creazione della chiave (`POST /api/keys`) o l'aggiornamento (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Esclusione per richiesta

Qualsiasi richiesta può ignorare la cache indipendentemente dalle impostazioni della chiave:

```
X-OmniRoute-No-Cache: true
```

Per i modelli sincronizzati/importati, `PUT /api/provider-models` accetta `provider`, `modelId` e
`maxOutputTokenOverride`: un numero intero positivo imposta il limite manuale dei token di output, mentre `null`

utilizza la funzionalità di runtime `max_output_tokens` e persiste dopo una nuova sincronizzazione del modello. La pagina
del provider compatibile con OpenAI offre gli stessi controlli di modifica/rimozione e contrassegna i modelli con supporto esplicito per la visione.

I nodi Chat Completions personalizzati adattano le esclusioni esplicite del ragionamento al backend upstream. Un
test di connessione riuscito seleziona automaticamente i controlli del template di chat per ogni ID modello esatto
la cui voce `/models` dimostra un valore `owned_by` riconosciuto: `vllm`, `sglang` o `llamacpp`.
I wrapper trasparenti compatibili con OpenAI possono conservare la voce originale del modello all'interno di un oggetto
`openai` annidato; il rilevamento segue fino a tre di questi livelli. I modelli con informazioni sulla proprietà mancanti,
sconosciute o in conflitto mantengono il comportamento OpenAI ordinario. Il rilevamento riutilizza la richiesta del catalogo
esistente, non genera token di completamento e viene invalidato quando cambia l'endpoint di connessione.

Per fissare il comportamento per un backend che non espone tali metadati, utilizzare l'API esistente di aggiornamento
parziale del provider:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Inviare questo corpo con `PUT /api/providers/<connection-id>`. Su tale connessione, un livello di
ragionamento esplicito pari a `none` viene inviato come `chat_template_kwargs.thinking=false` e
`chat_template_kwargs.enable_thinking=false`. I valori espliciti del template nativo mantengono la precedenza,
a meno che una regola di ragionamento lato server non imponga un livello. L'impostazione si applica solo quando una
connessione personalizzata compatibile con OpenAI invia un corpo Chat Completions; le richieste Responses e i provider
ordinari mantengono la struttura nativa della richiesta. Impostare `reasoningControl` su `openai` per forzare il normale
inoltro di `reasoning_effort` di OpenAI, oppure ometterlo/impostarlo su `null` per utilizzare il rilevamento automatico.

Le richieste del classificatore della modalità automatica di Claude Code disabilitano per impostazione predefinita il
ragionamento nativo quando non contengono controlli espliciti del ragionamento. Il rilevamento utilizza il marcatore di sistema
del classificatore nelle richieste in formato Claude, non i nomi dei modelli o i limiti di completamento. I controlli espliciti
del corpo, le intestazioni supportate relative al livello/alla modalità di ragionamento, le regole di instradamento e il livello
del modello risolto mantengono la priorità esistente. Entrambe le fasi del classificatore conservano i rispettivi prompt, limiti
di completamento, sequenze di arresto e verdetti effettivi sulle autorizzazioni upstream; la seconda fase può comunque produrre
il ragionamento visibile richiesto come testo ordinario.

### Versione e canale di rilascio

```bash
GET /api/system/version
```

Route di gestione accessibile solo tramite loopback (autenticazione amministratore). Restituisce la versione in esecuzione, l'ultima versione
pubblicata e lo stato dell'aggiornamento automatico. `releaseChannel` e `channels` sono campi
aggiuntivi (linea 3.8.54); `channel` mantiene il proprio significato, ovvero la modalità di distribuzione utilizzata
dal programma di aggiornamento della dashboard (`npm`, `source` o `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canale npm della build in esecuzione: `nightly` per le versioni `-nightly.*`,
  `next` per le altre versioni preliminari (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` per una versione stabile di una
  major precedente rispetto a `channels.latest`, altrimenti `latest`. Le regole sono le stesse di
  `scripts/release/dist-tag.mjs`, che seleziona il dist-tag npm al momento della pubblicazione.
- `channels` — versione più recente pubblicata per ciascun dist-tag, ottenuta da `npm view omniroute dist-tags` (con fallback
  HTTP al registry), memorizzata nella cache con lo stesso TTL di 10 minuti di `latest`. `latest` è sempre presente
  (esegue il fallback al campo `latest`, quindi a `"unavailable"`); `next`, `nightly` e `lts` vengono visualizzati
  solo quando il relativo dist-tag esiste. Una richiesta `Cache-Control: no-cache` aggiorna entrambe le ricerche.

Il modello dei canali (`latest` = v3 fino alla disponibilità generale della versione 4.0, `next` = rc, `nightly` = build di `develop`,
`lts` = patch v3 dopo la disponibilità generale della versione 4.0) è descritto in `docs/ops/RELEASE_STRATEGY.md`.

## Trascrizione audio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Trascrivi file audio utilizzando qualsiasi provider STT configurato. Il primo segmento
del percorso seleziona il provider nativo (`openai/…`, `deepgram/…`). I gateway che
riesportano il modello di un altro fornitore utilizzano un ID qualificato
(`openrouter/deepgram/nova-3`).

**Richiesta:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Risposta:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Esempi di ID modello:** `openai/whisper-1` (richiede una chiave OpenAI),
`openrouter/deepgram/nova-3` (richiede una chiave OpenRouter),
`deepgram/nova-3` (richiede una chiave Deepgram nativa). Una richiesta
`deepgram/nova-3` senza qualificatore **non** utilizza OpenRouter.

**Formati supportati:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Limiti dei token

Budget di **token** per chiave API (distinti dal budget basato su USD indicato sopra). Vengono applicati direttamente durante l'elaborazione della richiesta: quando l'utilizzo nella finestra corrente di una chiave raggiunge il limite, le richieste vengono rifiutate con `429 Too Many Requests`. I limiti possono essere circoscritti a uno specifico `model`, a un `provider` oppure applicati `global`mente all'intera chiave; quando più limiti corrispondono a una richiesta, viene applicato quello più restrittivo.

```bash
# Elenca i limiti di token di una chiave (include l'utilizzo corrente nella finestra)
GET /api/usage/token-limits?apiKeyId=key-123

# Crea o aggiorna un limite di token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Elimina un limite di token in base all'id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Note sullo schema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) sono obbligatori. `scopeValue` è obbligatorio, a meno che `scopeType` non sia `global` (ad esempio, un ID modello per l'ambito `model` o un ID provider per l'ambito `provider`). `tokenLimit` deve essere un numero intero positivo (convertito da stringa). Facoltativi: `id` (omettere per creare, specificare per aggiornare), `resetInterval` (`daily` | `weekly` | `monthly`, valore predefinito `monthly`), `resetTime` (`HH:MM`), `enabled` (valore predefinito `true`). Le risposte `GET` arricchiscono ogni limite con `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Questo è un endpoint della classe di gestione (l'autenticazione viene applicata centralmente dalla pipeline di autorizzazione).

## Elaborazione delle richieste

1. Il client invia una richiesta a `/v1/*`
2. Il gestore della route chiama `handleChat`, `handleEmbedding`, `handleAudioTranscription` o `handleImageGeneration`
3. Il modello viene risolto (provider/modello diretto oppure alias/combinazione)
4. Le credenziali vengono selezionate dal DB locale filtrando in base alla disponibilità dell'account
5. Per la chat: `handleChatCore` controlla la cache semantica/delle firme e risolve le impostazioni di compressione della combinazione
6. La compressione proattiva viene eseguita prima della traduzione per il provider, quando abilitata (`lite`, Caveman, RTK o in sequenza)
7. L'esecutore del provider invia la richiesta al servizio upstream
8. La risposta viene riconvertita nel formato del client (chat) oppure restituita così com'è (incorporamenti/immagini/audio)
9. Vengono registrati l'utilizzo, le analisi della compressione e i log delle richieste
10. In caso di errore viene applicato il fallback in base alle regole della combinazione

Riferimento completo dell'architettura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resilienza (estesa)

OmniRoute espone tre meccanismi indipendenti per gli errori temporanei; gli endpoint di gestione riportati di seguito consentono agli operatori di consultarli e sovrascriverli:

| Ambito                   | Archiviazione dello stato                       | Lettura                                   | Reimpostazione / cancellazione                                   |
| ------------------------ | ----------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| Circuit breaker provider | `domain_circuit_breakers` + memoria             | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                     |
| Cooldown connessione     | `rateLimitedUntil` nelle connessioni provider   | `/api/rate-limits`, `/api/providers/[id]` | (si riabilita in modo lazy; cancellare tramite PUT del provider) |
| Blocco modello           | Registro in memoria della disponibilità modelli | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                         |

`PATCH /api/resilience` accetta sovrascritture dei circuit breaker dei provider in `providerBreaker.oauth` e `providerBreaker.apikey`. Ogni profilo supporta `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; gli stessi campi sono disponibili in Dashboard → Impostazioni → Resilienza.

```bash
# Cancella il blocco di un singolo modello
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Cancella tutti i blocchi
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Per il riferimento concettuale completo e i valori predefiniti dei circuit breaker, vedere [`CLAUDE.md`](../../CLAUDE.md) → "Stato di resilienza in fase di esecuzione" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Coda dei limiti di frequenza e rete di sicurezza per l'abilitazione automatica

- **Percorso di scrittura supportato**: `POST /api/rate-limits` con corpo `{"connectionId": "<id>", "enabled": true|false}` è l'endpoint di gestione supportato per attivare o disattivare la protezione dai limiti di frequenza per una connessione. `PUT /api/providers/[id]` non modifica né inverte deliberatamente `rateLimitProtection` (#11278).
- **Semantica di `enabled: false`**: L'impostazione di `enabled: false` rimuove la protezione esplicita per la connessione, ma **non** esclude una connessione con chiave API attiva dalla rete di sicurezza globale per l'abilitazione automatica (`autoEnableApiKeyProviders = true`). In `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` sono equivalenti; le connessioni con chiave API attive prive di protezione esplicita rimangono protette dalla rete di sicurezza per l'abilitazione automatica.
- **Disabilitazione globale**: Per eseguire connessioni con chiave API senza code per i limiti di frequenza, disabilitare globalmente la rete di sicurezza tramite `RATE_LIMIT_AUTO_ENABLE=false` (variabile di ambiente) oppure `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Impostazioni → Resilienza / `PATCH /api/resilience`).

## Server A2A

OmniRoute espone un endpoint A2A (Agent-to-Agent) JSON-RPC 2.0 e un wrapper REST per l'ispezione e l'uso nella dashboard.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # facoltativo, salvo che OMNIROUTE_API_KEY sia impostata
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Metodi supportati (tutti subordinati a `settings.a2aEnabled`):

| Metodo           | Descrizione                                                                |
| ---------------- | -------------------------------------------------------------------------- |
| `message/send`   | Esecuzione sincrona della skill; restituisce `{task, artifacts, metadata}` |
| `message/stream` | Esecuzione in streaming SSE dello stesso insieme di skill                  |
| `tasks/get`      | Recupera un'attività tramite `taskId`                                      |
| `tasks/cancel`   | Annulla un'attività tramite `taskId`                                       |

Skill integrate: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Scheda agente

```bash
GET /.well-known/agent.json
```

Restituisce la scheda pubblica dell'agente A2A (nome, descrizione, funzionalità, catalogo delle skill, schema di autenticazione), memorizzata pubblicamente nella cache per 1 ora. Non è richiesta alcuna autenticazione.

### Helper REST

| Metodo | Percorso                     | Descrizione                                                                                                             |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | Stato di abilitazione A2A + statistiche delle attività + riepilogo della scheda agente memorizzata nella cache          |
| GET    | `/api/a2a/tasks`             | Elenca le attività — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Non implementato come helper REST — creare tramite JSON-RPC `message/send`)                                            |
| GET    | `/api/a2a/tasks/[id]`        | Recupera una singola attività                                                                                           |
| POST   | `/api/a2a/tasks/[id]/cancel` | Annulla un'attività                                                                                                     |

**Autenticazione:** gli helper REST vengono eseguiti senza autenticazione di gestione (consultabili dalla dashboard); la route JSON-RPC `/a2a` utilizza il token Bearer `OMNIROUTE_API_KEY`, se configurato.

## Autenticazione

Consulta [Autenticazione per la gestione](../guides/MANAGEMENT-AUTH.md) per informazioni sulle quattro
famiglie di credenziali (sessione della dashboard, token CLI locale, token di accesso
`oma_live_…`, chiave API con ambito di gestione) e sulle differenze rispetto alle chiavi di inferenza.

- Le route della dashboard (`/dashboard/*`) utilizzano il cookie `auth_token`
- L'accesso utilizza l'hash della password salvato, con fallback su `INITIAL_PASSWORD`
- `requireLogin` è attivabile o disattivabile tramite `/api/settings/require-login`
- Le route `/v1/*` possono richiedere facoltativamente una chiave API Bearer quando `REQUIRE_API_KEY=true`
- In questa documentazione, "token di gestione" / "chiave API con ambito di gestione" indica una delle famiglie descritte in quella guida, non un tipo aggiuntivo di segreto non definito

> **Modifica incompatibile (v3.8.0)** — `/api/v1/agents/tasks/*` e gli endpoint di gestione del cooldown ora richiedono l'**autenticazione per la gestione** (cookie `auth_token` della dashboard o una chiave API con ambito di gestione). I client che in precedenza chiamavano queste route senza autenticazione riceveranno `401 Unauthorized`. Consulta il commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
