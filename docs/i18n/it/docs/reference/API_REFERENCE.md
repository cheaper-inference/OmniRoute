## Completamenti chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Intestazioni personalizzate

| Header                   | Direzione | Descrizione                                                                                                                                                                                                                                      |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | Richiesta | Impostare su `true` per bypassare la cache                                                                                                                                                                                                       |
| `x-omniroute-no-memory`  | Richiesta | Impostare su `true` per ignorare l'iniezione di memoria + competenze per questa richiesta (rispecchia no-cache; evita il sovraccarico di token/costi per chiamata)                                                                               |
| `X-OmniRoute-Progress`   | Richiesta | Impostare su `true` per gli eventi di avanzamento                                                                                                                                                                                                |
| `X-Session-Id`           | Richiesta | Chiave di sessione persistente per l'affinità della sessione esterna                                                                                                                                                                             |
| `x_session_id`           | Richiesta | È accettata anche la variante con carattere di sottolineatura (HTTP diretto)                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Richiesta | Tag della sessione/conversazione fornito dal chiamante (alimenta anche la memoria). Quando presente, viene salvato verbatim in `call_logs.session_tag` per l'attribuzione dei costi per sessione (#8249) — non viene mai generato quando assente |
| `Idempotency-Key`        | Richiesta | Chiave di deduplicazione (finestra di 5 s)                                                                                                                                                                                                       |
| `X-Request-Id`           | Richiesta | Chiave di deduplicazione alternativa                                                                                                                                                                                                             |
| `x-omniroute-connection` | Richiesta | Associa una richiesta a modello singolo a una connessione del provider (account) tramite il relativo ID — vedere [Associazione dell'account per richiesta](#account-pinning-per-request)                                                         |
| `X-OmniRoute-Cache`      | Risposta  | `HIT` o `MISS` (senza streaming)                                                                                                                                                                                                                 |
| `X-OmniRoute-Idempotent` | Risposta  | `true` se deduplicata                                                                                                                                                                                                                            |
| `X-OmniRoute-Progress`   | Risposta  | `enabled` se il monitoraggio dell'avanzamento è attivo                                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | Risposta  | ID di sessione effettivo utilizzato da OmniRoute                                                                                                                                                                                                 |
| `X-OmniRoute-Request-Id` | Risposta  | ID di correlazione della richiesta (quando noto)                                                                                                                                                                                                 |
| `X-OmniRoute-Version`    | Risposta  | Versione della build di OmniRoute (sempre presente)                                                                                                                                                                                              |
| `X-OmniRoute-Cost-Saved` | Risposta  | Valore in USD risparmiato dalla cache in caso di HIT (solo cache hit)                                                                                                                                                                            |
| `X-OmniRoute-Decision`   | Risposta  | Traccia del routing: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` è la strategia combinata oppure `single` per una richiesta non combinata) — sempre presente nelle risposte al completamento                                   |

> Nota su Nginx: se si utilizzano intestazioni con caratteri di sottolineatura (ad esempio `x_session_id`), abilitare `underscores_in_headers on;`.

#### Associazione dell'account per richiesta

Quando un provider dispone di più connessioni (account o chiavi), OmniRoute normalmente ne seleziona una
tramite la propria strategia di selezione degli account. In alternativa, una richiesta può essere associata a una connessione specifica
con l'intestazione `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Dove trovare l'id.** Apri la pagina del provider nella dashboard
  (**Dashboard → Provider → <provider>**) e fai clic sul chip dell'id `xxxxxxxx…` in una riga
  di connessione: copierà l'id completo della connessione.
- **Quali richieste lo rispettano.** Le richieste a modello singolo (`provider/model`) su
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. Le combinazioni ignorano l'header:
  fissa un account per ogni passaggio della combinazione tramite la connessione specifica del passaggio.
- **Il pin è vincolante, non una preferenza.** La connessione fissata viene utilizzata esclusivamente. Un
  errore all'interno della richiesta registra il cooldown dell'account, ma **non** passa a un
  account associato dello stesso provider.
- **Il cooldown e la quota rilasciano il pin.** Mentre la connessione fissata è in cooldown,
  ha esaurito la quota o è bloccata da una policy di quota, le richieste successive passano alle altre
  connessioni del provider, esattamente come il traffico senza pin.
- **Gli id sconosciuti o disabilitati causano un errore.** Un id che non si trova nel pool attivo del provider (eliminato,
  disattivato o appartenente a un altro provider) non lascia alcun account idoneo, quindi la richiesta
  fallisce invece di essere instradata silenziosamente altrove.

Claude Code invia gli header personalizzati tramite `ANTHROPIC_CUSTOM_HEADERS`. Inseriscilo nel blocco `env`
di `~/.claude/settings.json`, oppure in un file `.claude/settings.json` a livello di progetto per fissare un
account diverso per ogni progetto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fonte: `src/sse/handlers/chat.ts` (lettura dell'header), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (rilascio del pin e controllo dell'assenza dal pool).

> **Header di telemetria dei costi:** le risposte con esito positivo senza streaming includono anche l'insieme di telemetria dei costi `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 decimali fissi; `0.0000000000` per contenuti gratuiti o senza prezzo), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (solo quando > 0), oltre a `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Questi header vengono emessi da chat completions, `/v1/responses`, `/v1/messages` **e dagli endpoint multimediali** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (sempre con costo `0`). Il costo dei contenuti multimediali viene calcolato per modalità (per immagine, per secondo, per carattere, per unità di ricerca) quando il prezzo è disponibile, altrimenti è `0` (fail-open).

> **Semantica dei costi per i cache hit:** in caso di HIT della cache semantica (`X-OmniRoute-Cache-Hit: true`) non viene effettuata alcuna chiamata upstream, quindi `X-OmniRoute-Response-Cost` è `0.0000000000` (il costo **incrementale** della gestione dell'hit). Il costo originale/che si sarebbe sostenuto viene riportato separatamente in `X-OmniRoute-Cost-Saved`. I sistemi di fatturazione devono sommare `X-OmniRoute-Response-Cost` (gli hit non hanno costi); le analisi della cache possono aggregare `X-OmniRoute-Cost-Saved`.

## Lease di sessione gestite esclusive

Il leasing esclusivo di sessioni gestite è un contratto di instradamento opt-in e neutrale rispetto al client: un unico proprietario attivo detiene una connessione OmniRoute idonea. Non concede in leasing un modello, non richiede OAuth, non identifica un client specifico e non richiede un provider specifico.

La chiave API di autenticazione deve avere l'ambito `lease:exclusive` e un elenco `allowedConnections` esplicito e non vuoto. Il confine di mutazione del database applica entrambi i campi insieme durante la creazione delle chiavi e negli aggiornamenti parziali.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Le risposte riuscite di acquisizione, rinnovo e rilascio espongono i timestamp, `state` e il valore `generation` positivo esatto, ma mai la connessione selezionata o le credenziali. Il rinnovo e il rilascio forniscono `generation` nel corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Il proprietario di un lease attivo può richiedere esplicitamente metadati di visualizzazione sicuri per la privacy relativi al proprio binding corrente:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Questa azione di stato opt-in è vincolata dal proprietario opaco, dalla chiave API gestita autenticata e dalla generazione attiva esatta in un'unica transazione del database. `displayName` è esclusivamente il nome della connessione configurato e sottoposto a trim; è `null` quando non esiste alcun nome configurato sicuro. OmniRoute non sostituisce mai il nome con un indirizzo email o con un'identità dell'account generata. Il valore del provider è un'etichetta di visualizzazione non sensibile e non è mai un identificatore di provider compatibile generato. Credenziali, token, cookie, ID grezzi delle connessioni o delle chiavi API, hash dei proprietari, segreti di fencing e dati interni di instradamento sono esclusi.

Le ricerche con chiave errata, proprietario errato, generazione obsoleta, dati mancanti, lease scaduto, rilasciato o invalidato restituiscono tutte lo stesso errore `409 LEASE_FENCE_STALE`, senza metadati della connessione. Un client che ha ricevuto la risposta di attesa della capacità non ha alcun binding attivo da ispezionare. Quando l'instradamento effettua la transizione di un lease attivo, la stessa generazione rimane valida e lo stato restituisce atomicamente il nuovo binding, mai quello precedente. I client esistenti rimangono invariati perché le risposte di acquisizione, rinnovo, rilascio e attesa mantengono i formati precedenti.

Questo contratto del server non modifica `/status` di OpenAI Codex standard. Attualmente Codex standard segnala il provider del modello e lo stato integrato di autenticazione/account, ma non visualizza metadati arbitrari dell'account di provider personalizzati; una successiva integrazione client dovrà chiamare questa azione e decidere come visualizzare `connection.displayName`.

Ogni richiesta di inferenza gestita fornisce quindi entrambe le intestazioni di controllo:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Il proprietario esatto, la generazione, la connessione attiva e la chiave API autenticata vengono sottoposti a fencing immediatamente prima di ogni tentativo upstream supportato. La riproduzione di proprietario e generazione con un'altra chiave non va a buon fine, anche quando tale chiave consente la stessa connessione. I proprietari grezzi non vengono persistiti, registrati nei log, conservati nello snapshot della richiesta né inoltrati upstream.

La contesa temporanea restituisce HTTP `429` con `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Questa risposta significa soltanto che l'insieme ordinario delle connessioni idonee non era vuoto e che ogni candidato libero era detenuto da un lease attivo esterno. Modelli/provider non supportati, mancata corrispondenza dei criteri, cooldown, quota, stato di integrità e altri normali errori di idoneità mantengono le risposte OmniRoute esistenti.

### `x-omniroute-compression`

Override per richiesta del piano di compressione. Ha la precedenza massima: prevale sull'override della combinazione di instradamento, sul profilo attivo, sull'attivazione automatica e sul valore predefinito del pannello. Valori:

| Valore        | Effetto                                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | Nessuna compressione per questa richiesta.                                                                            |
| `default`     | Il profilo predefinito derivato dal pannello (ignora il profilo attivo). I motori lossy vengono lasciati disattivati. |
| `safe`        | Solo deduplicazione e fusione degli spazi bianchi.                                                                    |
| `allow-lossy` | Mantiene il piano dell'operatore per questa richiesta, inclusi riepiloghi e riscritture dello stile.                  |
| `engine:<id>` | Un singolo motore quando abilitato, ad esempio `engine:rtk`. Opt-in per richiesta per quel motore.                    |
| `<combo>`     | Una combinazione denominata, confrontata prima per nome (senza distinzione tra maiuscole e minuscole), quindi per ID. |

Note:

- I valori sconosciuti vengono ignorati (la richiesta non viene mai rifiutata); la risoluzione prosegue secondo la normale precedenza dell'operatore.
- Se più combinazioni condividono lo stesso nome, passa l'**ID** della combinazione per ottenere una corrispondenza deterministica.
- Una combinazione il cui nome è `off` o `default` non può essere selezionata per nome (le parole chiave vengono interpretate per prime); fai riferimento a tale combinazione tramite il relativo ID.
- L'interruttore principale della compressione è un vincolo rigido: quando la compressione è disabilitata globalmente, questa intestazione non può abilitarla.

Il piano applicato viene restituito nell'intestazione della risposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

dove `<source>` è uno tra `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` o `off`.

## Embedding

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Provider disponibili: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Gli ID del catalogo sono `provider/model` (esempio: `jina-ai/jina-embeddings-v5-omni-small`). Anche gli ID dei modelli Jina senza prefisso presenti nel registro (ad esempio `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) vengono risolti. Jina embed/rerank/classify/segment utilizzano prima le credenziali `jina-ai` della dashboard; `JINA_AI_API_KEY` è un fallback solo quando non esiste alcuna chiave della dashboard. La scheda `jina-reader` è esclusivamente Reader / `r.jina.ai` (`POST /v1/web/fetch`) e non fornisce mai embedding o rerank.

I modelli del registro che dichiarano il supporto multimodale accettano anche fino a 32 elementi strutturati indipendenti dal provider.
I tipi di elementi multimediali sono `text`, `image`, `audio`, `video` e `document`. La `source`
dei relativi media è `{"type":"url","url":"https://..."}` oppure
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
e l'alias della famiglia `jina-ai/jina-embeddings-v5-omni` → omni-small) accetta anche la documentazione nativa
EmbeddingsV5Request di Jina e li **inoltra intatti** a `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

I valori nativi `{ image | audio | video | pdf }` possono essere un URL HTTPS pubblico, un URI `data:` o
base64 grezzo. OmniRoute non converte questi oggetti in stringhe né recupera gli URL nativi delle immagini: è Jina a recuperare
direttamente i media pubblici. I campi Jina aggiuntivi (`task`, `normalized`, `truncate`, `embedding_type`) vengono
inoltrati. Le SKU Jina di solo testo rifiutano comunque i documenti non testuali.

Limiti di sicurezza e trasporto:

- Gli URL dei media remoti devono essere HTTPS pubblici. Gli elementi canonici `{type,source:url}` vengono recuperati
  lato server (riverifica dei reindirizzamenti, timeout, limiti di dimensione, DNS pubblico, fissaggio della connessione) e incorporati
  prima della chiamata al provider. Gli elementi nativi Jina `{image:"https://..."}` vengono inoltrati così come sono
  dopo lo stesso controllo HTTPS pubblico; è Jina a recuperare l'URL.
- I media base64 incorporati sono limitati a 8 MiB decodificati per elemento e a 16 MiB decodificati per richiesta.

Traduzione del provider (gli elementi canonici non vengono mai inoltrati invariati):

- Modelli multimodali Jina: ogni elemento di primo livello diventa un oggetto con una chiave per modalità
  (`text` / `image` / `audio` / `video` / `pdf`) usando URI data per i media incorporati; un vettore per
  ogni elemento di primo livello.
- Famiglia Gemini Embedding 2: un unico array di primo livello diventa una singola richiesta nativa
  `models/{model}:embedContent` con `content.parts` (`text` o `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualsiasi modello caricato dal server locale): gli elementi canonici `text`
  diventano stringhe semplici, mentre `image` / `audio` / `video` diventano ciascuno un oggetto
  `{"content": [part]}`, usando le parti di contenuto della chat di llama-server (`image_url`,
  `input_audio` con formato `wav` / `mp3` / `flac`, `input_video`) con dati incorporati; un vettore per
  ogni elemento di primo livello. Il server deve essere eseguito con `--embedding --mmproj …`; senza un proiettore
  rifiuta direttamente i media. `document` non è supportato.
- I modelli sconosciuti/dinamici senza metadati espliciti sulle modalità rifiutano l'input strutturato con HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Le combinazioni modello/modalità non supportate restituiscono HTTP 400 invece di forzare la conversione dell'elemento. I campi
di estensione non relativi all'input nelle richieste legacy con stringhe/token continuano a essere trasmessi invariati.

```bash
# Elenca tutti i modelli di embedding
GET /v1/embeddings
```

## Generazione di immagini

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

I provider disponibili includono OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (locale), ComfyUI (locale).

`n` restituisce `n` immagini in `data[]`. I provider la cui API upstream restituisce un'immagine per chiamata
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) ricevono `n` chiamate upstream separate, con al massimo 4 chiamate
in corso contemporaneamente. Un `seed` fisso viene incrementato in base all'indice della chiamata
(`seed`, `seed + 1`, …), in modo che le immagini siano diverse ma riproducibili. `n` è limitato a 10.
La richiesta fallisce nel suo complesso se una qualsiasi chiamata fallisce. L'elenco dei formati
fan-out è `SINGLE_IMAGE_FANOUT_FORMATS` in
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux riutilizza la connessione esistente con la chiave API e accetta i prefissi `zenmux/` o `zm/`:

- `zenmux/openai/gpt-image-2` utilizza l'API Images di OpenAI di ZenMux. Le opzioni includono `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Altri publisher, come `zm/meta/muse-image-1.0`, utilizzano l'endpoint Vertex AI `:predict` di ZenMux.
  `n` viene mappato a `sampleCount`, `aspect_ratio` ad `aspectRatio` e `image_size`
  (`1K`, `2K`, `4K`) a `sampleImageSize`. Un valore `size` in pixel fornisce solo un rapporto
  d'aspetto e non garantisce dimensioni in pixel. Rapporti, risoluzioni e quantità supportati variano
  in base al modello.
- `zm/inclusionai/ming-image-0.1-design` sceglie autonomamente le proprie dimensioni. Omettere `size`,
  `aspect_ratio` e `image_size`; i valori espliciti restituiscono HTTP 400. È possibile richiedere
  PNG, JPEG e WebP con `output_format`.

Questa integrazione supporta la generazione da testo a immagine, non la modifica di immagini di riferimento.
L'output Vertex viene normalizzato in `data[].b64_json`; `response_format: "url"` restituisce un URL HTTPS
upstream oppure un URL dati base64 quando sono disponibili solo i byte dell'immagine. Gli output vuoti o
filtrati restituiscono un errore anziché una risposta corretta vuota. L'accesso ai modelli dipende
dall'account ZenMux. Consulta [l'API Vertex di ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images)
e [l'API Images di OpenAI](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Elenca tutti i modelli di immagini
GET /v1/images/generations
```

## OCR dei documenti

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleziona il provider OCR tramite un prefisso `provider/model`; un ID modello semplice (ad es.
`mistral-ocr-latest`) viene risolto nel provider registrato corrispondente, mentre se `model` viene
omesso viene utilizzato Mistral (`mistral-ocr-latest`). Provider registrati
(`open-sse/config/ocrRegistry.ts`):

| Provider id                   | Model id             | Valore di `model`                                     | Note                                                                                                                    |
| ----------------------------- | -------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (o `mistral-ocr-latest`) | Sincrono — la risposta viene restituita direttamente dalla singola chiamata upstream.                                   |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`           | Upstream asincrono (`analyze` + polling) — vedi sotto.                                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`               | Sincrono, tramite l'endpoint partner `openapi/chat/completions` di Vertex AI — vedi sotto per l'autenticazione e l'URL. |

Tutti e tre i provider rispondono con lo stesso corpo nel formato Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Flusso di polling di Azure Document Intelligence

L'API `analyze` di Azure Document Intelligence è asincrona: la richiesta iniziale restituisce
un'intestazione `Operation-Location` invece di un corpo e il risultato deve essere sottoposto a polling.
Il gestore (`open-sse/handlers/ocr.ts`) esegue il polling di quell'URL ogni secondo per un massimo di
30 tentativi, interrompe immediatamente (senza continuare il polling) in caso di risposta di polling
non `ok` o di stato `"failed"` e restituisce `504` se l'operazione è ancora in esecuzione dopo
l'esaurimento dei tentativi disponibili. La risposta Azure finale viene normalizzata nella stessa
struttura `pages`/`markdown` utilizzata da Mistral prima di essere restituita al chiamante, perciò
il codice client non deve gestire casi specifici per il provider.

### Autenticazione e risoluzione dell'endpoint OCR DeepSeek di Vertex AI

`vertex-deepseek-ocr` riutilizza la stessa autenticazione Vertex AI che OmniRoute supporta già per
il traffico di chat/immagini (`open-sse/executors/vertex.ts`): la chiave API della connessione è
una credenziale JSON di Service Account (scambiata con un token di accesso OAuth di breve durata
tramite il flusso JWT-bearer) oppure un token di accesso OAuth già emesso, utilizzato così com'è.
L'URL dell'endpoint upstream è l'endpoint partner generico `openapi/chat/completions` di Vertex,
costruito a partire dal progetto e dalla regione della connessione: un valore esplicito
`providerSpecificData.project`/`providerSpecificData.region` ha sempre la precedenza; in caso
contrario, il progetto viene derivato dal valore `project_id` del JSON del Service Account e la
regione predefinita è `us-central1`. Entrambe le risoluzioni avvengono in
`open-sse/handlers/ocr.ts` (`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e vengono
utilizzate da `src/app/api/v1/ocr/route.ts` prima dell'invio a `handleOcr`.

## Elenca modelli

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Restituisce tutti i modelli di chat, embedding e immagini + le combinazioni in formato OpenAI
```

### Prezzi dei modelli (`pricing`)

Una voce include un oggetto `pricing` quando OmniRoute conosce il prezzo del modello. Il prezzo proviene dalla tabella dei prezzi utilizzata dalla contabilizzazione dei costi: valori predefiniti integrati, prezzi sincronizzati e override impostati tramite `/api/pricing`. Questi sono prezzi di listino, quindi anche i provider in abbonamento mostrano un prezzo per token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Fields                                                          | Unit                          | Notes                                                                                                                                                                   |
| --------------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD per token, decimal string | Compatibile con OpenRouter, mai in notazione esponenziale. I due campi della cache compaiono solo quando esiste un prezzo della cache.                                  |
| `input`, `output`, `cached`, `cache_creation`                   | USD per 1M tokens, number     | Campi delle versioni precedenti del catalogo, mantenuti per i client esistenti. `reasoning` e `long_context` compaiono anch'essi quando la riga dei prezzi li contiene. |

- Le **combinazioni** riportano il prezzo della loro prima destinazione visibile. Le combinazioni integrate `auto/*` scelgono una destinazione al momento della richiesta, quindi non hanno `pricing`.
- I **modelli gratuiti** mostrano `"0"` (e `0`) quando il loro prezzo è zero. Un modello senza una riga dei prezzi mostra anch'esso `"0"` quando il catalogo lo contrassegna come gratuito (`free: true`) oppure quando è incluso nel catalogo integrato dei modelli gratuiti.
- **Prezzo sconosciuto:** la voce non contiene la chiave `pricing`.
- I **provider con tariffazione a crediti** (come Kiro) fatturano per richiesta anziché per token. Le loro voci mantengono i campi numerici per 1M che avevano in precedenza e non contengono campi stringa per token.
- Le **varianti** (id per il livello di ragionamento, alias senza ragionamento, mirror di discovery e gateway) copiano il prezzo del modello a cui effettuano il routing.
- I campi riportano solo le tariffe di base. I livelli per contesto esteso (il campo numerico `long_context`) e i moltiplicatori del livello di servizio (ad esempio Codex fast o flex) non modificano `prompt` o `completion`.
- L'oggetto è lo stesso per ogni stile di autenticazione, inclusa una richiesta in stile Anthropic con `x-api-key` e `anthropic-version` (la risposta rimane `{ "object": "list", "data": [...] }`). Implementazione: `src/app/api/v1/models/catalogPricing.ts`.

### Prefissi degli id dei modelli (`?prefix=`)

La maggior parte dei modelli viene pubblicizzata con un **prefisso del provider**. Il prefisso ottenuto è controllato dal feature flag `MODELS_CATALOG_PREFIX_MODE` e può essere sovrascritto **per richiesta** con un parametro di query — utile per un client che desidera un elenco più pulito senza modificare l'impostazione dell'intero server per tutti gli altri:

```bash
GET /v1/models?prefix=alias        # un id per modello — il prefisso alias breve
GET /v1/models?prefix=dual         # entrambe le forme (predefinito del server)
GET /v1/models?prefix=canonical    # solo il prefisso completo dell'id del provider
```

| Mode        | Emits                                                     | Notes                                                                                                                                                                                                                                      |
| ----------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **and** `claude/claude-sonnet-4-6` | **Predefinito.** Entrambi gli id effettuano il routing allo stesso modello; mantenuti affinché le configurazioni dei client che hanno codificato hardcoded una delle due forme continuino a funzionare. Il catalogo raddoppia all'incirca. |
| `alias`     | `cc/claude-sonnet-4-6`                                    | Una voce per modello. I provider senza un alias distinto emettono comunque la propria voce, quindi non si perde nulla.                                                                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                                | Una voce per modello con il prefisso completo dell'id del provider. I provider senza un alias distinto (ad es. `antigravity/…`, `agy/…`) emettono qui anch'essi il loro singolo id, quindi non si perde nulla.                             |

Un mirror in modalità `dual` può anche essere riconosciuto senza il parametro di query: contiene un campo `parent` che punta all'id principale.

I client che visualizzano un selettore di modelli dovrebbero richiedere `?prefix=alias` — è ciò che fa l'[estensione OmniCopilot per VS Code](../guides/VSCODE-COPILOT.md).

### Filtri di discovery (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accetta filtri di discovery facoltativi. In assenza di questi filtri, la risposta rimane invariata. Restringono il catalogo già visibile al chiamante (le autorizzazioni della chiave API vengono applicate per prime) e vengono eseguiti prima della paginazione `limit` / `after` in stile OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ogni capacità elencata deve essere true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` del catalogo; le righe senza questo campo sono `chat`
GET /v1/models?q=sonnet&limit=10                           # corrispondenza senza distinzione tra maiuscole e minuscole su id o nome
```

| Param         | Valori                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | intero non negativo, confrontato con `context_length`                                               |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caratteri                                                                                     |

Un valore sconosciuto o un valore `min_context` che non sia un intero non negativo (ad esempio `1.5`)
restituisce HTTP `400` e il messaggio elenca i valori validi. Implementazione:
`src/app/api/v1/models/catalogFilters.ts`.

### Elenco ridotto dei modelli (`POST /v1/models/query`)

`POST /v1/models/query` restituisce un elenco breve e deterministico dallo stesso catalogo, con la stessa
autenticazione e visibilità per chiave di `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Ogni campo è facoltativo. `capabilities` ed `exclude` accettano un array o una stringa separata da virgole;
`max_output` viene confrontato con `max_output_tokens`. I risultati sono ordinati per `owned_by`, quindi per `id`.
`limit` ha come valore predefinito `20` e i valori superiori a `100` vengono limitati a `100`. JSON non valido, un
campo sconosciuto o un valore non valido restituisce HTTP `400`.

### Modelli chat nascosti individualmente

Un modello contrassegnato come **Nascosto** nella pagina del provider viene escluso dal catalogo e rifiutato
con HTTP `404` / `model_not_found` quando richiesto esplicitamente. Il controllo utilizza il provider e il modello
risolti, inclusi gli alias dei provider, i prefissi dei nodi dei provider compatibili e i valori predefiniti della
connessione. Una combinazione ignora le destinazioni nascoste e può utilizzare un elemento visibile dello stesso
gruppo; quando non rimane alcuna destinazione eseguibile, restituisce lo stesso codice di errore. La rimozione
dello stato nascosto ha effetto sulla richiesta successiva. Le sovrascritture della visibilità solo per le immagini
non nascondono il modello chat con lo stesso ID.

Questa impostazione del singolo modello è separata dalle
[liste di consentiti/negati per l'esposizione dei modelli](../routing/MODEL_EXPOSURE_LIST.md), che filtrano
la pubblicità nel catalogo e i candidati per l'instradamento automatico, mantenendo al contempo l'invio esplicito.
Le autorizzazioni dei modelli per chiave API continuano ad applicarsi in modo indipendente. La modalità predefinita
del prefisso del catalogo rimane `dual`.

### Varianti dei modelli senza thinking

Per i modelli Claude che supportano il thinking, `/v1/models` pubblicizza anche una variante **senza thinking** il cui id
è preceduto da `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

La selezione di questo id (ad esempio in una configurazione di Claude Code che allega sempre un blocco `thinking`)
risolve nuovamente al vero `<provider>/<model>` con il ragionamento soppresso: `thinking:{type:"disabled"}` sul
percorso `/v1/messages`, oppure i campi `reasoning`/`reasoning_effort` rimossi sul percorso
`/v1/chat/completions`. La variante viene elencata solo per i modelli della famiglia Claude che supportano il thinking
**e** rispettano `disabled` (quindi, ad esempio, i modelli che supportano solo la modalità adattiva e rifiutano
`disabled` sono esclusi). Gli operatori possono forzare l'attivazione o la disattivazione della variante per modello
tramite `ModelSpec.noThinkingAlias`.

## Generazione audio ElevenLabs

Configura una connessione del provider `elevenlabs` in OmniRoute con la tua chiave API ElevenLabs.
I client effettuano l'autenticazione con la propria chiave **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
il gateway fornisce la chiave del provider memorizzata come `xi-api-key`. Non inviare mai una chiave ElevenLabs
come token bearer del gateway.

| Metodo | Percorso                    | Risposta                                       | Categoria endpoint chiave API |
| ------ | --------------------------- | ---------------------------------------------- | ----------------------------- |
| POST   | `/v1/sound-generation`      | Byte audio nativi                              | `elevenlabs`                  |
| POST   | `/v1/music`                 | Byte audio nativi                              | `music`                       |
| POST   | `/v1/music/stream`          | Byte audio in streaming                        | `music`                       |
| POST   | `/v1/music/detailed`        | Audio multipart nativo e piano di composizione | `music`                       |
| POST   | `/v1/music/detailed/stream` | Metadati SSE nativi e segmenti audio           | `music`                       |
| POST   | `/v1/music/plan`            | Piano di composizione JSON                     | `music`                       |

Questi endpoint completano le route esistenti `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` e `/v1/speech-to-text`. I campi JSON nativi
e i parametri di query come `output_format` e `enable_logging` vengono preservati.
Le risposte di `/v1/music/detailed` mantengono i relativi delimitatori multipart; analizzale come multipart.
`/v1/music/detailed/stream` restituisce `text/event-stream` con metadati della composizione e
segmenti audio codificati in base64 negli eventi SSE. Tutte e sei le route supportano il preflight CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Un breve effetto sonoro. Durata: da 0,5 a 30 secondi.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# La durata della musica è espressa in millisecondi: da 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilizza `/v1/music/stream` con lo stesso corpo JSON per la distribuzione incrementale dell'audio. La composizione
accetta esattamente uno tra `prompt` e `composition_plan`; `/v1/music/plan` richiede `prompt`
e accetta facoltativamente `source_composition_plan`. Gli schemi nativi preservano campi aggiuntivi
del provider, così le versioni dei piani di composizione e le opzioni di ottimizzazione raggiungono ElevenLabs.

L'endpoint unificato `/v1/music/generations` accetta anche `elevenlabs/music_v1`,
`elevenlabs/music_v2` e `elevenlabs/music_v2_5`. Con una connessione ElevenLabs attiva,
questi modelli vengono esposti dal catalogo musicale. Questo endpoint restituisce
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Il campo `duration` è espresso in
secondi e viene mappato a `music_length_ms`; un valore esplicito di `music_length_ms` ha la precedenza.
`instrumental` viene mappato a `force_instrumental`, con il campo nativo che ha la precedenza.
Utilizza gli endpoint nativi di streaming per lo streaming e l'endpoint nativo di composizione
per le richieste basate esclusivamente su un piano di composizione.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Le restrizioni relative a endpoint, modello, budget e connessione vengono applicate prima della chiamata upstream. Le route native
restituiscono i codici di stato e i corpi degli errori upstream invariati, incluso `402` per una restrizione del piano
e `429` per un limite di quota. Gli header `character-cost`, `song-id`, `request-id` e `retry-after`
vengono preservati quando presenti. Un saldo di crediti gratuito non garantisce l'accesso a ogni
modello musicale, formato di output o funzionalità API: ElevenLabs stabilisce i diritti per ogni richiesta.
L'endpoint unificato preserva i codici di stato degli errori nell'envelope di errore normalizzato di OmniRoute.

Contratti upstream: [effetti sonori](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composizione musicale](https://elevenlabs.io/docs/api-reference/music/compose) e
[dettagli della musica in streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Nodi provider per il reranking:** `POST /v1/rerank` instrada anche verso nodi provider compatibili con OpenAI
> (oMLX, vLLM, Infinity, TEI dietro un gateway, …) indirizzati come `<node-prefix>/<model>`. I nodi di loopback
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) sono sempre idonei, così come i nomi host elencati dall'operatore in
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (ad esempio un nome di servizio Docker/Compose come
> `http://reranker:8080/v1`; questi vengono contattati direttamente, mai tramite `HTTP(S)_PROXY` o il proxy
> associato alla connessione). I nodi su qualsiasi altro
> host — un dispositivo della LAN o un peer Tailscale — sono idonei solo quando l'operatore abilita il
> flag di funzionalità `RERANK_REMOTE_PROVIDER_NODES` **e** l'URL di base del nodo supera i criteri per gli URL in uscita dei provider
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Il passaggio di reranking del motore di memoria chiama questa route tramite
> loopback, quindi la stessa regola disciplina `rerankProviderModel` nelle impostazioni della memoria.
>
> **Formati dei server locali:** il nodo viene chiamato a `<base>/v1/rerank` e, in caso di 404, a `<base>/rerank`
> (Infinity, TEI). Il corpo inviato al servizio upstream contiene entrambe le convenzioni di denominazione Cohere/OpenAI (`documents`,
> `return_documents`) e quella di TEI (`texts`, `return_text`), mentre la risposta upstream
> viene normalizzata nel contenitore Cohere: l'array TEI semplice `[{index, score, text}]`, `{results: [{index, score}]}`
> dei gateway minimali e `{data: [...]}` nello stile Voyage vengono tutti restituiti al client come
> `{results: [{index, relevance_score, document?}]}`, ordinati per punteggio e limitati a `top_n`.

> **Individuazione dei nodi provider:** i modelli su un nodo provider compatibile con OpenAI compaiono in `GET /v1/models`
> con il prefisso del nodo. Le righe che non contengono metadati sull'endpoint (tipico degli elenchi locali di `/v1/models`)
> ereditano il relativo `apiType` del nodo, quindi i modelli di un nodo `embeddings` hanno
> `type: "embedding"` e quelli di un nodo `rerank` hanno `type: "rerank"` invece di impostare per impostazione predefinita il tipo chat;
> un valore `supportedEndpoints` esplicito in una riga sincronizzata o aggiunta manualmente mantiene comunque la precedenza.

| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ |
| GET    | `/v1/search`           | Elenca i provider di ricerca configurati e le relative funzionalità                              |

### `provider_options` di Exa e Tavily

Exa e Tavily leggono i campi specifici del provider da un contenitore con namespace:
`provider_options.exa` (o `provider_options["exa-search"]`) e `provider_options.tavily`
(o `provider_options["tavily-search"]`). Vengono inoltrate solo le chiavi riportate di seguito. Ognuna
viene verificata rispetto al proprio schema Zod in `open-sse/handlers/search/providerOptionsPassthrough.ts`,
e una chiave con il tipo errato viene eliminata. Qualsiasi altra chiave viene ignorata, incluse autenticazione, URL di base,
`stream` e `outputSchema`. Le chiavi piatte usate dagli altri provider (`cx`, `depth`, ...) continuano a funzionare come prima.

| Provider | Campi di primo livello                                                                                                                                                                                                                                                                                                                                                    | Nidificati                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitive piatte), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` uniti a quelli predefiniti `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                           |

I campi generici hanno sempre la precedenza: `query`, `max_results`, `filters` (domini), `country` e l'argomento
derivato da `search_type`. In Exa, `search_type: "news"` mantiene `category: "news"`.
Tavily accetta anche `search_type: "finance"` (`topic: "finance"`).

Il costo della ricerca Firecrawl viene registrato per ogni blocco di 10 risultati restituiti avviato, a $0.002 (2
crediti) per blocco e con almeno un blocco per chiamata
([fatturazione Firecrawl](https://docs.firecrawl.dev/billing)): 11 risultati costano $0.004.

Il valore generico `time_range` ora raggiunge entrambi i provider: Exa riceve `startPublishedDate` (timestamp ISO)
e Tavily riceve `start_date` (`YYYY-MM-DD`). Una data esplicita in `provider_options`
sovrascrive quella mappata.

I risultati Exa mantengono `id`, `highlights` (ogni evidenziazione, non solo la prima usata come
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` ed `extras` in
`provider_raw`. I risultati Tavily mantengono `images` e `favicon`.

Il costo della ricerca Linkup viene registrato a $0.005 per `depth` `fast` e `standard` e a $0.05 per
`deep` ([prezzi Linkup](https://docs.linkup.so/pages/documentation/development/pricing)),
indipendentemente dal fatto che `depth` provenga da `provider_options` o dalle impostazioni della connessione.

Exa `type: "lite"` (Exa 3.0) accetta un insieme più ristretto di campi e rifiuta l'intera richiesta
quando viene impostato qualsiasi altro campo. Per lite, `additionalQueries`, `systemPrompt` e ogni chiave di
`contents` eccetto `text` e `highlights` vengono eliminati prima della chiamata. I valori deprecati
`subpages`, `subpageTarget`, `highlights.numSentences` e `highlights.highlightsPerUrl` non vengono più inoltrati.

La contabilizzazione dei costi utilizza il registro piatto `costPerQuery`, tranne per Exa, che segue i propri
prezzi: $0.007 per chiamata per `auto` (e il legacy `fast`) o $0.004 per `lite` (e il legacy `instant`), a copertura di
10 risultati; $0.001 per ogni risultato aggiuntivo; e $0.001 per ogni risultato restituito quando è impostato
`contents.summary`. Tavily viene registrato a 1 credito ($0.008) per `search_depth` `basic`, `fast` e `ultra-fast`, e a 2
crediti ($0.016) per `advanced`
([crediti API Tavily](https://docs.tavily.com/documentation/api-credits)). Una chiamata con
`auto_parameters: true` che Tavily porta a `advanced` viene comunque registrata a 1 credito.

## API Web Fetch

Estrae contenuti da un URL tramite un provider di web fetch configurato (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, con la stessa chiave API di Parallel Search) restituisce
solo Markdown — qualsiasi altro `format` genera un `400` — e limita il contenuto a 100.000
caratteri. Quando non è possibile estrarre direttamente la pagina di destinazione, il
servizio upstream lo segnala all'interno di un HTTP 200;
OmniRoute lo espone come `422` con un messaggio fisso.

| Metodo | Percorso        | Descrizione                                                                  |
| ------ | --------------- | ---------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Esegue il fetch/scraping di un URL — corpo convalidato da `v1WebFetchSchema` |

**Autenticazione:** chiave API Bearer (`extractApiKey` + `isValidApiKey`). La policy viene
applicata tramite `enforceApiKeyPolicy`.

**Fallback consapevole della quota (#8297):** quando non viene specificato alcun `provider`, il pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) viene percorso in ordine di priorità fisso (fill-first) — un provider
limitato dalla frequenza ma configurato viene saltato invece di interrompere la richiesta,
e un errore upstream ritentabile/relativo alla quota (HTTP 429 sempre; 402/403 per i
free tier con quota in stile Firecrawl/Tavily/TinyFish — non per Jina Reader e mai per un
semplice 400 dovuto a una richiesta non valida) passa al provider successivo non ancora
tentato e dotato di credenziali al momento della richiesta. Quando tutti i provider del
pool sono esauriti, l'endpoint restituisce un singolo `429` (con un'intestazione
`Retry-After`) invece del precedente `400` generico. Quando viene richiesto un `provider`
esplicito, **non** è previsto alcun fallback silenzioso — un provider esplicito limitato
dalla frequenza o in errore espone il proprio errore (`429` se limitato dalla frequenza,
altrimenti lo stato upstream).


Un proxy Responses-API-over-WebSocket è collegato **esclusivamente a `codex`** (backend
ChatGPT). È in ascolto sulla stessa porta dell'API/dashboard nei percorsi
`/v1/responses`, `/responses` e `/api/v1/responses`. Al primo frame `response.create`
esegue l'autenticazione e la preparazione tramite il bridge interno
`codex-responses-ws`, seleziona una connessione OAuth codex e crea un tunnel verso
`wss://chatgpt.com/backend-api/codex/responses` tramite il trasporto `wreq-js`. I modelli
diversi da codex vengono rifiutati (`codex_ws_provider_required`).
Per il routing della condivisione della quota, usare `model: "qtSd/<group>/codex/<model>"`.
Implementato in
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticazione:** chiave API Bearer durante l'handshake. Il server HTTP incluso
(`server-ws.mjs`) deve essere l'entrypoint attivo (lo è per impostazione predefinita quando
esiste `app/server-ws.mjs`).

#### ID del modello: usare l'ID ChatGPT senza prefisso `codex/`

**Codex CLI** di OpenAI convalida il nome del modello lato client quando
`supports_websockets = true` e rifiuta gli ID con prefisso del provider come
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Inviare l'ID **senza prefisso** (ad es. `gpt-5.5`). Il bridge di
OmniRoute è solo codex, quindi risolve nuovamente un ID senza prefisso come modello codex
(`resolveCodexWsModelInfo`) prima di creare il tunnel upstream — anche se un semplice
`gpt-5.5` verrebbe altrimenti instradato verso un altro provider tramite HTTP.

#### Configurazione di OpenAI Codex CLI

Indirizzare Codex CLI a OmniRoute aggiungendo un provider personalizzato con supporto
WebSocket a `~/.codex/config.toml` (usare un `CODEX_HOME` separato per evitare di
modificare una configurazione esistente):

```toml
model = "gpt-5.5"                 # id senza prefisso — NON "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # nessuna slash finale; l'URL WS viene derivato (usare https/wss in produzione)
wire_api = "responses"                    # unico valore supportato da febbraio 2026
supports_websockets = true                # abilita il trasporto Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # contiene la chiave API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # una chiave API OmniRoute (qualsiasi chiave se REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

La CLI aggiorna `base_url + /responses` a un WebSocket e OmniRoute crea un tunnel verso la
connessione OAuth codex selezionata. Convalidato end-to-end sul server locale: ChatGPT
restituisce `codex.rate_limits` + `response.created` e trasmette in streaming il
completamento.

### Recupero della sessione di quota (facoltativo)

Una richiesta `POST /v1/chat/completions` o `POST /v1/responses` non in streaming che restituisce un errore di quota terminale (`402`/`429`/`503` il cui corpo indica che la quota o i crediti sono esauriti) può essere messa in attesa e riprodotta in seguito invece di restituire l'errore. Il chiamante abilita questa opzione per ogni richiesta con tre intestazioni:

| Intestazione                 | Valore                                              |
| ---------------------------- | --------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                              |
| `x-omniroute-session`        | ID sessione, `[A-Za-z0-9._:-]{1,128}`               |
| `x-omniroute-recovery-turn`  | ID del turno univoco nella sessione (stessa regola) |

I ticket sono visibili solo alla chiave API che li ha creati. Una riproduzione il cui esito è incerto termina in `needs_confirmation` invece di essere inviata due volte. Fonte: `src/lib/quota/quotaSessionRecovery.ts`.

## Utilizzo self-service (`/api/usage/om-usage`)

Qualsiasi chiave API può leggere il **proprio** utilizzo e le proprie quote, senza autenticazione di gestione. Questo è l'endpoint utilizzato da un client (CLI, pannello OmniCopilot) per mostrare al titolare di una chiave la propria spesa.

```bash
# Formato testuale (il contratto storico — testo semplice per un terminale)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato strutturato — quello utilizzato da un'interfaccia utente
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

La chiave deve avere **`allowUsageCommand`** abilitato (disabilitato per impostazione predefinita — il gestore delle chiavi API del dashboard lo attiva o disattiva per ogni chiave). In sua assenza, l'endpoint restituisce `403`.

`?format=json` restituisce una struttura discriminata, in modo che il chiamante non legga mai un campo dati da un rifiuto. In caso di successo:

```jsonc
{
  "allowed": true,
  // presente solo quando la chiave ha scelto di utilizzare limiti di utilizzo per chiave (USD giornalieri/settimanali):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // snapshot della quota del provider selezionato, oppure null quando non è ancora presente alcun dato nella cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // snapshot di ogni connessione, così un'interfaccia utente può visualizzare diversi provider affiancati:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

In caso di rifiuto (chiave `401` non valida / `403` non autorizzata), la stessa route restituisce
`{ "allowed": false, "error": { "message": "…" } }` — un `personal`/`provider` presente ma vuoto
(chiave autorizzata, nessuna informazione ancora disponibile) rappresenta uno stato diverso da un rifiuto, e solo il formato JSON consente di distinguerli.

**Autenticazione:** la chiave API Bearer del chiamante, convalidata tramite `isValidApiKey` — questa _non_ è la superficie di gestione (`/api/keys/…`), che rimane protetta da `requireManagementAuth`.

### Percentuali di quota grezze rispetto a quelle adeguate alla soglia

Quando utilizzano `/api/usage/om-usage`, i chiamanti devono considerare la differenza tra le percentuali presentate dall'**output in testo semplice** e quelle dell'**output JSON strutturato**:

| Aspetto                          | Formato testo semplice (`/api/usage/om-usage` / `@@om-usage`)                                            | Formato JSON (`?format=json`)                                                               |
| :------------------------------- | :------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| **Campo di output**              | `NN% left` (ad es. `20% left`)                                                                           | `provider.quotas` / `providers[].quotas`                                                    |
| **Misurazione**                  | **Disponibilità utilizzabile adeguata alla soglia**: capacità residua al di sopra della soglia di cutoff | **Quota upstream grezza**: misurazione del provider non modificata                          |
| **Ridimensionamento del cutoff** | Ridimensionata tramite `effectiveRemainingPercent()` in modo che la riserva protetta risulti `0% left`   | Nessuno (valori grezzi dello snapshot come riportati dal provider)                          |
| **Dati della soglia**            | Incorporati nella percentuale visualizzata                                                               | Archiviati in `quotaWindowThresholds` per connessione (o nei valori predefiniti del server) |
| **Utilizzatore principale**      | CLI interattive, prompt del terminale, operatori umani                                                   | Integrazioni programmatiche, dashboard, analisi, sistemi di monitoraggio della fatturazione |

#### Formula dell'adeguamento al cutoff

OmniRoute supporta cutoff proattivi della quota per evitare l'esaurimento upstream (configurati tramite
`quotaWindowThresholds` della connessione, valori predefiniti del provider o impostazioni globali di resilienza). Quando una soglia di cutoff
(ad es. `cutoff = 25%`) è attiva in una finestra di quota, il renderer testuale calcola la disponibilità residua come segue:

- Se `remaining <= cutoff`: restituisce `0%`.
- Se `remaining > cutoff`: restituisce `((remaining - cutoff) / (100 - cutoff)) * 100`.

L'output testuale formattato arrotonda il risultato all'intero più vicino (`Math.round(...)`).

#### Esempio illustrativo

Considerare una finestra del provider con **60% di utilizzo effettivo** (quindi **40% di quota effettiva rimanente**) e una soglia configurata di **25% di quota rimanente**:

| Rappresentazione                 | Calcolo                                            | Rimanente |           Utilizzato implicito            |
| :------------------------------- | :------------------------------------------------- | :-------: | :---------------------------------------: |
| **JSON grezzo (`?format=json`)** | Snapshot upstream (`quotas[window]`)               |  **40%**  |                  **60%**                  |
| **Formato testo (`NN% left`)**   | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (se si calcola `100 - remaining`) |

- **Perché il testo mostra 20% rimanente:** Dei 40% di quota fisica rimanente sull'account, il 25% è riservato dalla
  politica di cutoff. Il chiamante dispone soltanto del 15% dei 75% di margine utilizzabile rimanente prima che il router interrompa
  l'instradamento verso questa connessione. La scalatura garantisce che la connessione segnali l'esaurimento (`0% left`) esattamente
  quando l'instradamento verrà interrotto.
- **Perché JSON conserva i valori grezzi:** Il payload JSON restituisce lo snapshot esatto del provider (`UsageSnapshot`),
  in modo che gli strumenti esterni abbiano accesso all'utilizzo upstream effettivo e a `quotaWindowThresholds` a livello di connessione,
  senza una scalatura con perdita di informazioni lato server.

#### Indicazioni per la migrazione dei consumer

Se un'integrazione esterna (come un plugin per editor o un'estensione per agenti) in precedenza analizzava l'endpoint di testo
(`NN% left`) e calcolava la percentuale utilizzata come `100 - NN`, la migrazione a `?format=json` comporta:

- La lettura dei valori JSON grezzi rifletterà il **consumo effettivo upstream** (60% utilizzato nell'esempio precedente).
- Se l'integrazione desidera mantenere la semantica dell'allocazione utilizzabile dell'endpoint di testo, può valutare
  la formula effettiva del rimanente lato client utilizzando `quotaWindowThresholds` per le sostituzioni a livello di connessione.

## Cache semantica

```bash
# Ottieni le statistiche della cache
GET /api/cache/stats

# Cancella tutte le cache
DELETE /api/cache/stats
```

Esempio di risposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impatto sulla latenza

Un HIT della cache semantica restituisce la risposta dalla cache **senza una
chiamata upstream**, pertanto `X-OmniRoute-Response-Latency` riportato è quasi
zero (indipendentemente dalla latenza upstream originale). I client sensibili
alla latenza (benchmark, monitoraggio p50/p99) devono controllare l'header di
risposta `X-OmniRoute-Cache-Latency`:

| Valore      | Significato                                                                |
| ----------- | -------------------------------------------------------------------------- |
| `synthetic` | Risposta fornita dalla cache; la latenza non è il tempo upstream effettivo |
| _(absent)_  | Risposta da una chiamata upstream reale                                    |

### Esclusione della cache per chiave

Le chiavi API possono disattivare le letture dalla cache semantica tramite
`cacheDefaultMode`:

| Valore   | Comportamento                                                           |
| -------- | ----------------------------------------------------------------------- |
| `legacy` | Comportamento normale della cache (predefinito)                         |
| `bypass` | Ignora completamente la ricerca nella cache; accede sempre all'upstream |

Impostare alla creazione della chiave (`POST /api/keys`) o durante
l'aggiornamento (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Esclusione della cache per richiesta

Qualsiasi richiesta può ignorare la cache indipendentemente dalle impostazioni
della chiave:

```
X-OmniRoute-No-Cache: true
```

## Compatibilità con la gestione di CLIProxyAPI

OmniRoute risponde ai tre endpoint di gestione di
[CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) che i dashboard di
utilizzo chiamano per leggere i limiti degli abbonamenti Claude e Codex
(ad esempio, la sorgente dei limiti di utilizzo `cliproxy` di T3 Code). Impostare
l'URL di base del client su OmniRoute e utilizzare una chiave API con lo scope
`manage` come chiave di gestione. Le route sono disponibili in
`/v0/management/*` e `/api/v0/management/*`.

| Metodo | Percorso                     | Descrizione                                                                                                                                         |
| ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Connessioni OAuth Claude e Codex come `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Nessun token                          |
| POST   | `/v0/management/api-call`    | Corpo `{ auth_index, method, url, header?, data? }`. Invia una richiesta consentita con il token dell'account e restituisce `{ status_code, body }` |
| POST   | `/v0/management/reset-quota` | Corpo `{ auth_index }`. Cancella il cooldown della connessione, i blocchi del modello e i cooldown per ambito di Codex di un account                |

- `auth_index` è l'ID della connessione OmniRoute. `provider` è `claude` o `codex` (solo
  connessioni OAuth; il provider con chiave API `anthropic` non è elencato). Per Codex,
  `id_token.chatgpt_account_id` è l'ID dello spazio di lavoro memorizzato e `plan_type` il piano memorizzato.
- `api-call` non è un proxy generico. Accetta solo Claude `GET
https://api.anthropic.com/api/oauth/usage` e Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` e
  `POST .../wham/rate-limit-reset-credits/consume`, ciascuno esclusivamente per un account del provider corrispondente. Qualsiasi altra richiesta restituisce `403` senza contattare l'upstream. L'header
  `Authorization` del chiamante (incluso il segnaposto `$TOKEN$`) viene ignorato: OmniRoute inserisce il token di accesso della connessione, aggiornandolo prima quando è vicino alla scadenza, e inoltra solo
  gli header consentiti (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`). Se `Chatgpt-Account-Id` è assente, viene utilizzato per impostazione predefinita l'ID dello spazio di lavoro memorizzato.
  Le richieste scadono dopo 15 secondi e utilizzano il proxy della connessione.
- `reset-quota` lascia invariati gli stati terminali (banned, expired, credits_exhausted). Un
  `auth_index` sconosciuto restituisce `404`.

**Autenticazione:** sessione del dashboard o chiave API con scope `manage`, obbligatoria anche quando l'accesso è disabilitato
(i percorsi sono inclusi in `ALWAYS_PROTECTED_API_PATHS`). Le chiavi utilizzabili solo per l'inferenza ricevono `403`. Sorgente:
`src/lib/cliproxyCompat/managementApi.ts`.

Per i modelli sincronizzati/importati, `PUT /api/provider-models` accetta `provider`, `modelId` e
`maxOutputTokenOverride`: un intero positivo imposta il limite manuale dei token di output, mentre `null`
lo rimuove per ripristinare il valore predefinito. `GET /api/provider-models?provider=<provider>` restituisce questi
valori in `modelOutputOverrides`, inclusi i modelli privi di una riga di modello personalizzato. L'override

Su un nodo provider compatibile, i percorsi di scrittura (`POST`, `PUT`, `PATCH`, `DELETE` e
`/api/provider-models/validate-and-add`) memorizzano l'ID del modello come ID upstream senza prefisso: un ID
incollato da un elenco con prefisso vede ogni sequenza iniziale del prefisso del nodo stesso ridotta a una sola, e
le risposte restituiscono l'ID memorizzato. Gli ID con slash dei provider canonici (ad es. `nvidia/nemotron-…`) vengono
memorizzati verbatim. `/v1/models` non restituisce mai un ID impilato `<prefix>/<prefix>/<model>`.

I nodi Custom Chat Completions adattano gli opt-out espliciti dal ragionamento al backend upstream. Un test di connessione riuscito seleziona automaticamente i controlli dei chat template per ogni ID modello esatto la cui voce `/models` dimostra un valore `owned_by` riconosciuto: `vllm`, `sglang` o `llamacpp`. I wrapper trasparenti compatibili con OpenAI possono preservare la voce del modello originale all'interno di un oggetto `openai` annidato; il rilevamento segue fino a tre di questi envelope. I modelli con ownership mancante, sconosciuta o in conflitto mantengono il comportamento OpenAI ordinario. Il rilevamento riutilizza la richiesta al catalogo esistente, non genera token di completamento e viene invalidato quando cambia l'endpoint di connessione.

Per fissare il comportamento di un backend che non espone questi metadati, usa l'API esistente per gli aggiornamenti parziali del provider:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Invia questo body con `PUT /api/providers/<connection-id>`. Su quella connessione, un livello di ragionamento esplicito pari a `none` viene inviato come `chat_template_kwargs.thinking=false` e `chat_template_kwargs.enable_thinking=false`. I valori espliciti del template nativo restano autorevoli, a meno che una regola di ragionamento lato server non imponga un livello. L'impostazione si applica solo quando una connessione personalizzata compatibile con OpenAI invia un body Chat Completions; le richieste Responses e i provider ordinari mantengono la loro forma nativa. Imposta `reasoningControl` su `openai` per forzare il normale passthrough OpenAI di `reasoning_effort`, oppure omettilo/impostalo su `null` per usare il rilevamento automatico.

Le richieste del classificatore in modalità automatica di Claude Code disabilitano per impostazione predefinita il thinking nativo quando non contengono controlli espliciti del ragionamento. Il rilevamento usa il marker di sistema del classificatore nelle richieste in formato Claude, non i nomi dei modelli o i limiti di completamento. I controlli espliciti nel body, gli header supportati per effort/thinking, le regole di routing e il livello di effort risolto del modello mantengono la priorità esistente. Entrambe le fasi del classificatore conservano i rispettivi prompt, limiti di completamento, sequenze di arresto e verdetti reali sui permessi upstream; la seconda fase può ancora produrre il ragionamento visibile richiesto come testo ordinario.

### Versione e canale di rilascio

```bash
GET /api/system/version
```

Route di gestione accessibile solo tramite loopback (autenticazione amministratore). Restituisce la versione in esecuzione, l'ultima versione pubblicata e lo stato dell'aggiornamento automatico. `releaseChannel` e `channels` sono campi aggiuntivi (rail 3.8.54); `channel` mantiene il proprio significato: la modalità di distribuzione utilizzata dall'aggiornamento della dashboard (`npm`, `source` o `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canale npm della build in esecuzione: `nightly` per le versioni `-nightly.*`,
  `next` per le altre versioni preliminari (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` per una versione stabile di una
  major precedente a `channels.latest`, altrimenti `latest`. Le stesse regole di
  `scripts/release/dist-tag.mjs`, che seleziona il dist-tag npm al momento della pubblicazione.
- `channels` — versione principale pubblicata di ciascun dist-tag, ottenuta da `npm view omniroute dist-tags` (con fallback HTTP al registry), memorizzata nella cache con lo stesso TTL di 10 minuti di `latest`. `latest` è sempre presente
  (come fallback usa il campo `latest`, quindi `"unavailable"`); `next`, `nightly` e `lts` compaiono
  solo quando quel dist-tag esiste. Una richiesta con `Cache-Control: no-cache` aggiorna entrambe le ricerche.

Il modello dei canali (`latest` = v3 fino alla disponibilità generale della versione 4.0, `next` = rc, `nightly` = build di `develop`,
`lts` = patch di v3 dopo la disponibilità generale della versione 4.0) è descritto in
`docs/ops/RELEASE_STRATEGY.md`.

## Trascrizione audio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Trascrivi file audio utilizzando qualsiasi provider STT configurato. Il primo segmento
del percorso seleziona il provider nativo (`openai/…`, `deepgram/…`). I gateway che
riesportano il modello di un altro fornitore utilizzano un ID qualificato
(`openrouter/deepgram/nova-3`).

**Richiesta:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Risposta:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**ID modello di esempio:** `openai/whisper-1` (richiede una chiave OpenAI),
`openrouter/deepgram/nova-3` (richiede una chiave OpenRouter),
`deepgram/nova-3` (richiede una chiave Deepgram nativa). Una richiesta
`deepgram/nova-3` semplice **non** utilizza OpenRouter.

**Formati supportati:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** trascrizione in modalità file tramite il
WebSocket Gemini Live (richiede una chiave API Gemini). Il caricamento viene convertito in PCM mono a 16 kHz con `ffmpeg`
(deve essere disponibile in `PATH`, a meno che il file non sia già un WAV PCM mono a 16 kHz), trasmesso alla sessione e
il testo finalizzato viene restituito come `{ "text": "..." }`. I campi modulo facoltativi `language` e `prompt`
vengono inoltrati. Limiti: i caricamenti superiori a 25 MiB o l'audio decodificato più lungo di 10 minuti restituiscono
`413`; una conversione che dura più di 60 s viene terminata e restituisce `504`. La chiave API viene inviata
solo nell'header `x-goog-api-key`, mai nell'URL WebSocket.

```bash
GET /api/v1/vscode/{token}/api/tags
```

## Limiti dei token

Budget di **token** per chiave API (distinti dal Budget basato su USD descritto sopra). Applicati inline nel percorso della richiesta: quando l'utilizzo della finestra corrente di una chiave raggiunge il relativo limite, le richieste vengono rifiutate con `429 Too Many Requests`. I limiti possono essere associati a un `model` o a un `provider` specifico, oppure applicati in modo `global` alla chiave; quando più limiti corrispondono a una richiesta, viene applicato quello più restrittivo.

```bash
# Elenca i limiti di token di una chiave (include l'utilizzo live della finestra)
GET /api/usage/token-limits?apiKeyId=key-123

# Crea o aggiorna un limite di token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Elimina un limite di token tramite id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Note sullo schema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) sono obbligatori. `scopeValue` è obbligatorio a meno che `scopeType` non sia `global` (ad esempio, un id del modello per l'ambito `model`, un id del provider per l'ambito `provider`). `tokenLimit` deve essere un intero positivo (convertito da stringa). Opzionali: `id` (omettere per la creazione, fornire per l'aggiornamento), `resetInterval` (`daily` | `weekly` | `monthly`, valore predefinito `monthly`), `resetTime` (`HH:MM`), `enabled` (valore predefinito `true`). Le risposte `GET` arricchiscono ogni limite con `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Questo è un endpoint di classe di gestione (l'autenticazione viene applicata centralmente dalla pipeline authz).

## Elaborazione delle richieste

1. Il client invia la richiesta a `/v1/*`
2. Il gestore della route chiama `handleChat`, `handleEmbedding`, `handleAudioTranscription` o `handleImageGeneration`
3. Il modello viene risolto (provider/modello diretto o alias/combinazione)
4. Le credenziali vengono selezionate dal database locale con il filtraggio della disponibilità degli account
5. Per la chat: `handleChatCore` controlla la cache semantica/delle firme e risolve le impostazioni di compressione della combinazione
6. La compressione proattiva viene eseguita prima della traduzione verso il provider quando abilitata (`lite`, Caveman, RTK o impilata)
7. L'esecutore del provider invia la richiesta upstream
8. La risposta viene riconvertita nel formato del client (chat) oppure restituita così com'è (embedding/immagini/audio)
9. Vengono registrati l'utilizzo, le analisi della compressione e i log delle richieste
10. Il fallback viene applicato in caso di errori secondo le regole della combinazione

Riferimento completo all'architettura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resilienza (estesa)

OmniRoute espone tre meccanismi indipendenti per la gestione degli errori temporanei; gli endpoint di gestione seguenti consentono agli operatori di leggerne lo stato e sovrascriverlo:

| Ambito                       | Archiviazione dello stato                           | Lettura                                   | Reimpostazione / cancellazione                             |
| ---------------------------- | --------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| Circuit breaker del provider | `domain_circuit_breakers` + memoria                 | `/api/monitoring/health`                  | `POST /api/resilience/reset`                               |
| Cooldown della connessione   | `rateLimitedUntil` sulle connessioni del provider   | `/api/rate-limits`, `/api/providers/[id]` | (riabilitazione lazy; cancellare tramite PUT del provider) |
| Blocco del modello           | Registro della disponibilità dei modelli in memoria | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                   |

`PATCH /api/resilience` accetta override del circuit breaker del provider tramite `providerBreaker.oauth` e `providerBreaker.apikey`. Ogni profilo supporta `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; gli stessi campi sono esposti in Dashboard → Impostazioni → Resilienza.

```bash
# Cancella il blocco di un singolo modello
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Cancella tutti i blocchi
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Per il riferimento concettuale completo e i valori predefiniti del circuit breaker, vedere [`CLAUDE.md`](../../CLAUDE.md) → "Stato runtime della resilienza" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Coda per il limite di frequenza e rete di sicurezza per l'abilitazione automatica

- **Percorso di scrittura supportato**: `POST /api/rate-limits` con body `{"connectionId": "<id>", "enabled": true|false}` è l'endpoint di gestione supportato per attivare o disattivare la protezione dal limite di frequenza per una connessione. `PUT /api/providers/[id]` deliberatamente non modifica né inverte `rateLimitProtection` (#11278).
- **Semantica di `enabled: false`**: l'impostazione di `enabled: false` rimuove la protezione esplicita per la connessione, ma **non** esclude una connessione con chiave API attiva dalla rete di sicurezza globale per l'abilitazione automatica (`autoEnableApiKeyProviders = true`). In `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` sono equivalenti; le connessioni con chiave API attive senza protezione esplicita rimangono protette dalla rete di sicurezza per l'abilitazione automatica.
- **Disabilitazione globale**: per eseguire connessioni con chiave API senza code per il limite di frequenza, disabilitare globalmente la rete di sicurezza tramite `RATE_LIMIT_AUTO_ENABLE=false` (env) oppure `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Impostazioni → Resilienza / `PATCH /api/resilience`).

## Autenticazione

Consulta [Autenticazione della gestione](../guides/MANAGEMENT-AUTH.md) per le quattro
famiglie di credenziali (sessione del dashboard, token CLI locale, token di accesso
`oma_live_…`, chiave API con ambito di gestione) e per le differenze rispetto alle
chiavi di inferenza.

- Le route del dashboard (`/dashboard/*`) usano il cookie `auth_token`
- L'accesso usa l'hash della password salvata; fallback a `INITIAL_PASSWORD`
- L'opzione `requireLogin` può essere attivata o disattivata tramite `/api/settings/require-login`
- Le route `/v1/*` richiedono facoltativamente una chiave API Bearer quando `REQUIRE_API_KEY=true`
- In questo riferimento, "token di gestione" / "chiave API con ambito di gestione" indica una delle famiglie descritte in quella guida — non un tipo aggiuntivo di segreto non definito

> **Modifica che interrompe la compatibilità (v3.8.0)** — `/api/v1/agents/tasks/*` e gli endpoint di gestione del cooldown ora richiedono **autenticazione di gestione** (cookie `auth_token` del dashboard o una chiave API con ambito di gestione). I client che in precedenza chiamavano queste route senza autenticazione riceveranno `401 Unauthorized`. Consulta il commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
