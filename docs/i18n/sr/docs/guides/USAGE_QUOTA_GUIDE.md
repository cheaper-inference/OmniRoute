> **УКРАТКО**: OmniRoute прати потрошњу токена за сваки захтев, израчунава трошкове, примењује квоте за сваки API кључ и приказује аналитику на контролној табли. Овај водич објашњава како све то функционише.

**Извори:**

- `open-sse/services/usage.ts` (~70KB) — главно праћење потрошње
- `src/lib/usageAnalytics.ts` (~10KB) — агрегација за контролну таблу
- `src/lib/db/quotaSnapshots.ts` — историјски подаци о квотама
- `src/lib/db/usage*.ts` — више DB модула повезаних са потрошњом

---

## Преглед

Сваки захтев који пролази кроз OmniRoute генерише **запис о потрошњи** који бележи:

- **Идентитет**: који API кључ, добављач, модел и комбинација
- **Токене**: токене упита, токене одговора, кеширане токене и укупан број
- **Трошак**: износ у USD (израчунат на основу података о ценама)
- **Временске податке**: кашњење и временске ознаке почетка/завршетка
- **Статус**: успех, грешка, ограничење брзине итд.

Ови записи се агрегирају у **аналитику**, чувају као **снимци квота** и користе за примену **ограничења буџета по кључу**.

```
Захтев ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    аналитика  квота   наплата
                   (контр. табла) (примена) (извоз)
```

## Шта се бележи

Сервис `usage.ts` бележи **догађај коришћења** за сваки захтев:

| Поље               | Тип     | Извор                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID генерисан при бележењу                                |
| `apiKeyId`         | string  | API кључ којим је покренут захтев                          |
| `provider`         | string  | ID провајдера (openai, anthropic итд.)                     |
| `model`            | string  | ID модела (gpt-5, claude-opus-4-6 итд.)                    |
| `comboId`          | string? | ID комбинације ако је захтев усмерен кроз комбинацију      |
| `promptTokens`     | number  | Из одговора узводног провајдера                            |
| `completionTokens` | number  | Из одговора узводног провајдера                            |
| `cachedTokens`     | number  | Токени пронађени у кешу (Anthropic кеширање упита итд.)    |
| `totalTokens`      | number  | упит + генерисани одговор                                  |
| `costUsd`          | number  | Израчунато на основу података о ценама                     |
| `latencyMs`        | number  | Укупно трајање захтева                                     |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | Класа грешке ако статус није success                       |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | Прилагођени подаци које додаје додатак                     |

### Одакле долазе токени

Токени се издвајају из одговора узводног провајдера у **обрађивачу одговора**:

```ts
// Из open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

За провајдере који не враћају податке о коришћењу (неки провајдери засновани на веб-колачићима), OmniRoute **процењује** број токена помоћу хеуристике `~4 chars per token` (погледајте `open-sse/services/autoCombo/pipelineRouter.ts`).

### Кеширани токени

OmniRoute прати `cached_tokens` одвојено од `prompt_tokens` зато што:

- Anthropic кеширање упита наплаћује кеширане токене по сниженој цени (10% уобичајене)
- Неки провајдери враћају `cache_read_input_tokens`, за које треба применити другачију цену
- Аналитика може да прикаже **стопу погодака кеша** = `cached_tokens / prompt_tokens`

### Дијагностика нивоа уписа у кеш

Панел стања кеша упита на контролној табли аналитике разликује уписе у кеш
са трајањем од 5 минута и 1 сата које пријављује провајдер. Anthropic поља
`usage.cache_creation.ephemeral_5m_input_tokens` и
`usage.cache_creation.ephemeral_1h_input_tokens` задржавају се при превођењу података о коришћењу у стриминг и
нестриминг режиму и чувају се уз сажетке евиденције позива. Обједињени
укупан број уписа у кеш не додаје се тим категоријама други пут.

Позиви са само обједињеним бројачем уписа, укључујући старије записе, имају непознат
ниво. Код делимичне расподеле, недодељени остатак остаје непознат; неважећи или
противречни бројачи се означавају уместо да им се неприметно додели TTL. TTL ознаке
на страни захтева нису доказ о наплаћеном нивоу.

Процена уписа у панелу, изражена као API еквивалент, обухвата само пријављене нивое са познатом ценом, а не
цео захтев. За изворне цене Claude/Anthropic модела користи 1,25 пута
цену улазних токена за уписе од 5 минута и двоструку цену улазних токена за уписе од 1 сата. Недостајућа
цена означава се као недоступна, а не као нула. Цене се бележе при евидентирању сваког новог позива;
цене историјских записа не обрачунавају се поново. Зато претплатнички налози могу имати
процену у API еквиваленту, а да тај износ не представља новчани трошак или потрошњу претплатничке
квоте. Постојећи обрачуни квота, буџета и трошкова према тачним подацима провајдера остају непромењени.

Ова дијагностика користи постојећи сажетак стања кеша са ограниченим обимом и постојећа правила
чувања евиденције позива. Не мења подразумеване TTL вредности захтева, усмеравање нити избор налога.
Бележење TTL вредности коју је клијент затражио у односу на стварну излазну TTL вредност на месту слања
провајдеру одложено је за касније; овај панел приказује нивое са потврда провајдера, а не стварну излазну TTL вредност.

Имплементација: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` и `open-sse/utils/cacheWriteUsage.ts`.

## Обрачун трошкова

Трошкови се израчунавају на основу **података о ценама** синхронизованих из LiteLLM-а (`src/lib/pricingSync.ts`):

| Модел             | Улаз $/1M | Излаз $/1M | Кеширано $/1M |
| ----------------- | --------- | ---------- | ------------- |
| gpt-5             | $2.50     | $10.00     | —             |
| claude-opus-4-6   | $15.00    | $75.00     | $1.50         |
| claude-sonnet-4-5 | $3.00     | $15.00     | $0.30         |
| gemini-2.5-pro    | $1.25     | $10.00     | —             |

Формула за израчунавање трошкова (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Зашто се кеширани токени одузимају од токена упита?** Кеширани део се обрачунава засебно; примена улазне цене на цео упит довела би до двоструког обрачуна.

### Синхронизација цена

Подаци о ценама се аутоматски синхронизују из LiteLLM-а преко крајње тачке `/api/pricing/sync` (покреће је уграђени cron задатак, а не кориснички доступна променљива окружења):

```bash
# Ручно покретање
curl -X POST http://localhost:20128/api/pricing/sync
```

За моделе без података о ценама, OmniRoute прелази на **процену трошкова** помоћу интерних просечних тарифа (изведених из LiteLLM података о ценама).

## Агрегација по временском опсегу

Модул `usageAnalytics.ts` израчунава виџете контролне табле на основу сирових података о коришћењу. Подржава 7 временских опсега:

| Опсег    | Период                            | Примена                                     |
| -------- | --------------------------------- | ------------------------------------------- |
| `1d`     | Последња 24 сата                  | Откривање наглих скокова трошкова по сатима |
| `7d`     | Последњих 7 дана                  | Недељни преглед                             |
| `30d`    | Последњих 30 дана                 | Месечни обрачун                             |
| `90d`    | Последњих 90 дана                 | Квартална анализа                           |
| `ytd`    | Од 1. јануара текуће године       | Праћење годишњег буџета                     |
| `all`    | Цео период                        | Статистика за целокупан период              |
| `custom` | Кориснички дефинисан почетак/крај | Ревизије, ад хок упити                      |

### Виџети контролне табле који се израчунавају

За сваки временски опсег, аналитички слој израчунава:

| Виџет                        | Опис                                                                     |
| ---------------------------- | ------------------------------------------------------------------------ |
| **Картице са сажетком**      | Укупан број захтева, укупан трошак, укупан број токена, стопа успешности |
| **Графикон дневног тренда**  | Трошкови + токени по дану, наслагани по моделу                           |
| **Топлотна мапа активности** | Мрежа сат у дану × дан у недељи, боја = број захтева                     |
| **Расподела по моделима**    | Кружни графикон трошкова по моделу                                       |
| **Расподела по добављачима** | Стубичасти графикон захтева по добављачу                                 |
| **Водећи API кључеви**       | Табела 10 водећих кључева по трошку                                      |
| **Анализа грешака**          | Стопа грешака током времена, најчешће класе грешака                      |

### Програмски приступ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // записи историје коришћења
  "7d",                 // временски опсег: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // мапа веза добављача (connectionId → назив налога)
  {
    startDate: "2025-01-01",  // опционо: за опсег "custom"
    endDate: "2025-06-01",   // опционо: за опсег "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (центи)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Спровођење квота

Квота по API кључу спроводи се на два места:

1. **Меко ограничење** (`quotaWarnAt`): упозорење на контролној табли када коришћење премаши праг
2. **Чврсто ограничење** (`quotaLimit`): захтев се одбија уз HTTP 429 када се ограничење премаши

### Конфигурација

```ts
// По API кључу
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — прикажи упозорење
  quotaLimit: 10_00,    // $10.00 — потпуна обустава
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Ток спровођења

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### Снимци стања квота

Табела `quotaSnapshots` чува **историјско стање квота** за анализу трендова:

| Поље | Опис |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Кључ који се прати |
| `window` | "day" | "week" | "month" |
| `used` | Трошак у овом периоду (центи) |
| `limit` | Ограничење (центи) |
| `resetAt` | Када се период ресетује |
| `createdAt` | Када је снимак стања направљен |

Снимци стања се праве **при сваком захтеву** чији је трошак > 0 и користе се за:

- Приказ траке напретка квоте на контролној табли
- Приказ графикона тренда квоте за 30 дана
- Покретање упозорења када се коришћење приближи ограничењу

### Упити за аналитику коришћења

Подацима о коришћењу приступа се преко контролне табле или MCP алата, а не преко директних REST крајњих тачака за извоз. Доступна аналитика:

- **`/api/usage/analytics`** — агрегиране метрике коришћења (груписање по моделу, добављачу, кључу)
- **`/api/usage/quota`** — тренутно стање квоте по API кључу
- **`/api/usage/history`** — евиденција историје захтева

---

## MCP алати

Два MCP алата омогућавају агентима приступ подацима о коришћењу (погледајте `open-sse/mcp-server/tools/`):

| Алат                    | Опис                                                   |
| ----------------------- | ------------------------------------------------------ |
| `omniroute_cost_report` | Генерише извештај о трошковима по кључу за дати период |
| `omniroute_check_quota` | Враћа тренутно стање квоте за API кључ                 |

Пример позива од стране агента:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## Чување и чишћење

Обим података о коришћењу расте за ~1-10KB по захтеву. При великом обиму, то може бити значајно.

### Подешавања чувања

Чување историје коришћења подешава се преко подешавања базе података у корисничком интерфејсу или преко `/api/settings/database`.

Подразумевано, историја коришћења чува се **90 дана**.

### Чишћење

Старе записе чисти `src/lib/db/cleanup.ts`:

- Покреће га позадински cron процес
- Брише записе из `usage_history` старије од периода чувања подешеног опцијом `usageHistory`

### Процена простора за складиштење

| Учесталост захтева  | Простор за 30 дана | Простор за 90 дана |
| ------------------- | ------------------ | ------------------ |
| 100 захтева/дан     | ~3MB               | ~9MB               |
| 1,000 захтева/дан   | ~30MB              | ~90MB              |
| 10,000 захтева/дан  | ~300MB             | ~900MB             |
| 100,000 захтева/дан | ~3GB               | ~9GB               |

За веома велики саобраћај, размотрите:

- Скраћивање периода чувања преко подешавања базе података
- Коришћење `aggregated_metrics` уместо необрађених записа (само за аналитику)

## Савети за оптимизацију трошкова

### 1. Користите одговарајући модел

```bash
# Брз одговор — користите јефтин и брз модел
curl -d '{"model":"auto/fast","messages":[...]}'

# Сложен задатак — користите квалитетан модел
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Омогућите кеширање

Кеширање промптова компаније Anthropic доноси **уштеду од 90% на поновљеном контексту**:

```ts
// Кеширање је аутоматско — само укључите исти велики системски промпт
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Биће аутоматски кеширано
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Користите компресију

Компресија RTK + Caveman доноси **уштеду од 15-95% у сесијама са интензивном употребом алата**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Подесите квоте по кључу

Увек подесите `quotaLimit` да бисте спречили неконтролисан раст трошкова:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Ограничење од 10 долара месечно
```

### 5. Проверите највеће потрошаче

Користите контролну таблу или **`/api/usage/analytics`** за груписање по API кључу и сортирање по трошковима:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Решавање проблема

### "Трошкови су већи од очекиваних"

1. Проверите **`/api/usage/analytics?groupBy=model`** — пронађите скуп модел
2. Проверите **`/api/usage/analytics?groupBy=apiKey`** — пронађите великог потрошача
3. Проверите да ли су подаци о ценама ажурни: `POST /api/pricing/sync`

### "Недостају записи"

- Проверите подешавања задржавања података у бази у одељку Контролна табла → База података → Чишћење — стари записи се бришу периодичним задатком чишћења (`src/lib/db/cleanup.ts`)
- Проверите да ли има грешака у `src/lib/db/usage*.ts` — неуспешни уписи у базу података се евидентирају, али се не приказују
- Проверите да ли је захтев заиста стигао до `chatCore` — проверите комбиновано рутирање

### "Квота се не примењује"

- Проверите подешавање `quotaLimit` за тај кључ
- Проверите да ли је `quotaWindow` исправно подешен
- Потражите записе `quotaSnapshots` — требало би да се креирају при сваком захтеву
