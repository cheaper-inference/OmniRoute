> **Укратко**: OmniRoute користи **SQLite са WAL журналисањем** као примарно складиште, уз **AES-256-GCM** шифровање осетљивих поља у мировању. Овај водич обухвата шему, миграције, прављење резервних копија/опоравак и оперативна упутства.

**Извори:**

- `src/lib/db/core.ts` — синглтон + SCHEMA_SQL (17 основних табела)
- `src/lib/db/migrationRunner.ts` — верзионисане миграције
- `src/lib/db/migrations/` — 167 верзионисаних SQL датотека
- `src/lib/db/encryption.ts` — помоћне функције за шифровање
- `src/lib/db/backup.ts` — извоз/увоз резервних копија
- `src/lib/db/healthCheck.ts` — дијагностика исправности

## Зашто SQLite?

OmniRoute је изабрао SQLite уместо PostgreSQL/MySQL из неколико разлога:

| Фактор              | SQLite                                 | PostgreSQL                              |
| ------------------- | -------------------------------------- | --------------------------------------- |
| **Примена**         | Уграђен — није потребан засебан сервер | Захтева подешавање сервера              |
| **Шифровање**       | На нивоу апликације (AES-256-GCM)      | Уграђени TDE                            |
| **Перформансе**     | Бржи за мала/средња радна оптерећења   | Бољи за огроман број истовремених уписа |
| **Конкурентност**   | WAL режим омогућава истовремена читања | Потпуни MVCC                            |
| **Резервна копија** | Копирање једне датотеке                | `pg_dump` или снимак система датотека   |
| **Случај употребе** | Инсталација по кориснику, уграђено     | Вишекориснички SaaS                     |

За примене са **једним корисником и једном инстанцом** (примарни случај употребе за OmniRoute), SQLite је једноставнији и бржи.

### WAL журналисање

`core.ts` отвара базу података у **WAL (Write-Ahead Logging) режиму**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL омогућава **истовремена читања** током уписа — што је важно за контролну таблу, која извршава упите док се захтеви бележе.

Подразумевана величина кеша је **65.536 KiB (64 MiB)**. SQLite тумачи негативну вредност
`cache_size` као приближну горњу границу у KiB и додељује странице по потреби.
**Подешавања > Систем и складиште > Величина кеша** прихвата целобројне вредности од **1 до
1.000.000 KiB**; чување подешавања примењује га на активну везу са базом података,
а OmniRoute враћа сачувану вредност при покретању.

## Локација базе података

SQLite датотека се чува на следећој локацији:

| ОС      | Путања                                                 |
| ------- | ------------------------------------------------------ |
| Linux   | `~/.omniroute/storage.sqlite`                          |
| macOS   | `~/.omniroute/storage.sqlite`                          |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`              |
| Docker  | `/app/data/storage.sqlite` (подесиво преко `DATA_DIR`) |

Пратеће датотеке:

- `storage.sqlite-wal` — дневник писања унапред
- `storage.sqlite-shm` — датотека дељене меморије
- `call_logs/` — артефакти садржаја захтева (ако је омогућено)

**Промена локације:**

```bash
DATA_DIR=/custom/path omniroute
```

### Границе модула

Основно архитектонско правило: **модули не приступају директно табелама других модула**. Да бисте радили са подацима другог модула, увезите функцију из тог модула.

```ts
// ❌ ПОГРЕШНО: директан SQL из другог модула
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ИСПРАВНО: користите функцију модула providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

Ово правило се спроводи прегледом кода — не постоји статичка провера, али се кршења означавају.

## Миграције

OmniRoute користи** верзионисане, идемпотентне миграције** у `src/lib/db/migrations/`. Свака миграција је једна SQL датотека. Два формата именовања коегзистирају; верзија снимљена у `_omniroute_migrations` је нумерички префикс.

### Именовање миграције

| Формат                                            | Пример                               | Користи се за                                                                                                                                                          |
| ------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (тачно 3 цифре)             | `241_seen_models.sql`                | Стара серија `001`–`241`. Замрзнуто када је формат временске ознаке слетео (`240` и `241` су спојени непосредно пре њега): ниједна нова датотека не добија редни број. |
| `YYYYMMDDHHMMSS_description.sql` (14 цифара, UTC) | `20261113120000_add_usage_index.sql` | Свака миграција направљена од 13.11.2026.                                                                                                                              |

Зашто промена: са узастопним бројевима, паралелни PRs је изабрао исти следећи број и сви осим једног су морали да пренумеришу пре спајања. Временска ознака UTC даје сваком PR у своју верзију.

Правила за формат временске ознаке (наметнута `npm run check:migration-numbering`, дељена са генератором у `scripts/check/lib/migrationNaming.mjs`):

- Временска ознака је прави UTC датум и време, не раније од `20261113000000` и не више од 10 минута у будућности.
- Опис је `snake_case` малим словима који почиње словом (`a-z`, `0-9`, један `_` између речи), највише 80 знакова.
- Две датотеке са истом временском ознаком су дупликат.
- Правило без размака се примењује само на стару серију: сваки број од `001` до `241` мора постојати, осим познатих празнина `026`, `055` и `121`. Брисање `241` (или било које старе датотеке) не успева. `001` и `241` се никада не могу додати на `KNOWN_GAPS` листу дозвољених. Датотеке са временским ознакама никада не стварају празнину.
- Сваки унос у `src/lib/db/migrations/` мора бити обична датотека са важећим малим словима `.sql` именом. Директоријум, симболична веза, `.SQL` или `.sql.bak` датотека, скривена датотека или име са размаком не успевају на капији, јер би их покретач тихо прескочио или би се срушио при покретању.

**Примени ред.** Тркач сортира према нумеричкој вредности префикса, а не по тексту: прво старе датотеке `001`–`241`, затим датотеке са временским жигом у редоследу временске ознаке, затим било који директоријум са простором између имена регистрован са `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (верзије као што је `ee-001`). Миграција на чекању је свака датотека чија верзија није у `_omniroute_migrations`, тако да се миграција са старије гране која се спаја након нове гране и даље примењује на постојеће базе података.

**Временска ознака је редослед креирања, а не редослед спајања.** Ако ваша миграција зависи од табеле или колоне креиране миграцијом са а** новије** временска ознака (на пример, једна из друге PR која се прва спојила), нова база података би прва покренула вашу и пропала. Док је ваш PR још увек отворен, регенеришите име датотеке помоћу `npm run db:new-migration` тако да добије новију временску ознаку или га учините независним. `npm run test:migrations:fresh` примењује сваку миграцију на празну базу података и хвата ово.

### Спојена миграција се никада не брише нити преименује

Једном када се датотека за миграцију нађе на грани издања или `main`, већ је покренута на хомологним базама података и базама података програмера, на VPS инсталацијама и у Ентерприсе синхронизацији. Од тада па надаље:

- **Никада га немојте брисати.** Нове инсталације би изгубиле своју шему док би је надограђене базе података задржале.
- **Никада га не преименуј.** Верзија у `_omniroute_migrations` више се не би подударала са датотеком, тако да би је свака база података која је већ применила поново покренула. Не-идемпотентни SQL затим дуплира податке или зауставља покретање.
- **Треба вам друга шема?** Креирајте нову миграцију помоћу `npm run db:new-migration`.

Преименовање је безбедно само за фајл који још није спојен, што је случај на који се наговештаји капије односе. Ознака издања овде ништа не мења: сваки притисак на `release/v*` грану објављује Docker `:next` слику и ради на хомологу, VPS инсталацијама и Ентерприсе синхронизацији, тако да је обједињена миграција покренута на стварним базама података пре него што постоји било која `vX.Y.Z` ознака. Капија не успева при сваком уклањању основне датотеке, означене или не.

- **Враћање обједињене миграције.** `git revert` који брише датотеку пада на капију. Задржите датотеку и поништите њену шему у новој миграцији: `npm run db:new-migration -- <description>`, са `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` и тако даље. Надограђене и свеже базе података се завршавају истом шемом.
- **Једно прихваћено преименовање: унос компатибилности и идентичан садржај.** Ако спојена датотека мора да се помери (на пример, две спојене датотеке деле временску ознаку и покретач се зауставља са колизијом верзије), преименујте каснију без додиривања њеног SQL и додајте `{ fromVersion, fromName, toVersion, toName }` у `RENAMED_MIGRATION_COMPATIBILITY` у `src/lib/db/migrationRunner/constants.ts`. Базе података које су примениле стару верзију померају свој `_omniroute_migrations` ред уместо да поново покрећу датотеку. Гејт упозорава на такво преименовање и увек покреће проверу комутације на њему, без обзира на нову временску ознаку: нове инсталације примењују датотеку на њеној новој позицији, надограђене базе података не, па изаберите нову временску ознаку близу старе. Гејт не успе у преименовању ако се садржај промени (промена шеме и даље иде у новој миграцији) или ако циљна датотека уноса није на диску.
- **Никада немојте преименовати унутар исте временске ознаке.** Преименовање које задржава временску ознаку и мења само опис не успева на капији, са или без уноса. Са уносом чији `toVersion` једнак његовом `fromVersion`, покретач брише стари `_omniroute_migrations` ред и поново примењује датотеку на сваку базу података која га је већ покренула. Без уноса, покретач прати само верзију: прескаче датотеку у тим базама података (нови садржај се тамо никада не покреће) и бележи грешку при промени нумерације при сваком покретању. Користите другу временску ознаку плус унос компатибилности или задржите име.
- **Капија проверава да се преименована датотека не покреће поново.** За свако покривено преименовање, капија прослеђује ново име датотеке у проверу комутације помоћу `--must-not-apply`. Провера покреће надограђену базу података са правим покретачем, и ако покретач поново примени ту датотеку (на пример, зато што унос има погрешну верзију или име, или зато што парсер текста капије чита `constants.ts` другачије од TypeScript), капија не успе са `migration renomeada rodaria de novo` и тражи од вас да проверите стару и нову верзију и називе уноса.

### Шта капија проверава у односу на базу

Приликом покретања захтева за повлачењем и стапања у реду, `npm run check:migration-numbering` упоређује `src/lib/db/migrations/` на диску са истим директоријумом на основној грани. База је, овим редоследом: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` променљива, или, када је `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` или `merge_group`, први родитељ урезивања спајања, `merge_group.base_sha` корисног оптерећења догађаја или `git merge-base HEAD origin/$GITHUB_BASE_REF`. У захтеву за повлачење или извођењу стапања у реду без базе која се може решити, капија не успева. Изван CI без `--base` штампа `comparação com a base: pulada (sem --base)` и прескаче ова правила.

`--base-latest-tag` се упоређује са најновијом ознаком издања (`vX.Y.Z` у семвер редоследу; ознаке са суфиксима, као што су нигхтлиес се не рачунају) која је у историји `HEAD`, са истим правилима као `--base`. Релеасе-Греен (`scripts/quality/validate-release-green.mjs`) покреће капију на овај начин, јер пусх и заказана покретања немају базу захтева за повлачење и спајање може да дође без новог CI покретања. Без ознаке ослобађања у историји капија не успева; покрените `git fetch --tags` (у CI, `actions/checkout` са `fetch-depth: 0` доноси ознаке).

Провера комутације (`scripts/check/migration-commutation.ts`) прави две привремене базе података са правом путањом за инсталацију:** надограђен** један (покретање са базним миграцијама, а затим поновно покретање на истој датотеци са миграцијама захтева за повлачење) и** свеже** један (једно покретање са миграцијама захтева за повлачење). Упоређује резултујуће шеме: табеле и колоне (занемарујући редослед колона), UNIQUE / PRIMARY KEY и FOREIGN KEY ограничења, нормализовани `CREATE TABLE` текст сваке табеле (који покрива CHECK ограничења, упоређивање, генерисане колоне и опције табеле), индексе, покретаче и приказе. Подаци реда се не пореде. Ако се поклапају, капија штампа да датотека није у реду, али да прелази на посао и пролази. Ако се разликују, капија не успева са разликом и наговештајем за случај: за датотеку која није у реду, регенеришите њено име помоћу `npm run db:new-migration`, што је безбедно јер датотека још није спојена; за уређену основну датотеку, вратите основни садржај и ставите промену у нову миграцију; за преименовану датотеку, поништите преименовање или изаберите другу нову временску ознаку на којој се креће, никада исту временску ознаку са другим именом. Ако сама провера не може да се покрене, капија не успе у CI и упозорава само локално. За уређену основну датотеку, надограђена база података се гради са садржајем базе те датотеке, а друго покретање је прескаче јер је њена верзија већ снимљена. За преименовану датотеку, надограђена база података се прави са датотеком под њеним старим именом, а друго покретање помера њен `_omniroute_migrations` ред кроз унос компатибилности уместо да је поново покреће; капија преноси ново име са `--must-not-apply`, тако да провера не успе ако га примени друго покретање. Ако миграција захтева за повлачење не успе да се примени на надограђеној путањи, то јест, након сваке миграције базе (без обзира да ли не успе и при новој инсталацији), капија извештава `migration do PR não aplica` и тражи од вас да поправите SQL са тренутном шемом базе; ако датотека зависи од друге миграције захтева за повлачење са каснијом временском ознаком, регенеришите њено име помоћу `npm run db:new-migration`.

Да бисте покренули исто поређење локално, експлицитно проследите базу, на пример `npm run check:migration-numbering -- --base origin/<base-branch>` или `npm run check:migration-numbering -- --base-latest-tag` да бисте упоредили са најновијим издањем.

### Конвертовање PR зка `NNN` миграције

Захтев за повлачењем отворен пре прекидача може и даље да носи секвенцијалну датотеку као што је `242_add_widgets.sql`. Стари бројеви изнад `241` се одбијају, па их конвертујте пре спајања:

1. **Преименујте датотеку са генератором, задржавајући опис.** Покрените `npm run db:new-migration -- <same description>` да бисте добили ново име, преместите SQL у њега и избришите стару `NNN_` датотеку. Опис мора остати идентичан: унос компатибилности испод одговара њему.
2. **Додајте унос компатибилности ако је трајна база података покренула стари број.** Ако је било која база података која се чува (хомолог, VPS, сопствена инсталација сарадника) покренула буилд PR са `NNN_` датотеком, додајте `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` у `RENAMED_MIGRATION_COMPATIBILITY` у `src/lib/db/migrationRunner/constants.ts`. Ово је** потребно за `237` до `241`** : ти слотови сада држе канонске `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` и `241_seen_models.sql`, а без уноса таква база података заувек прескаче канонску миграцију и поново покреће конвертовану. Такође функционише за слот који остаје празан, као што је `242`, када је одредиште временска ознака. Када сте у недоумици, додајте унос. Где га додате у низ није важно: када циљни слот уноса и даље држи ред који други унос помера (на пример `237` држи PR ред док старији `usage_history_calculated_cost` ред чека да се пресели у `237`), покретач дозвољава том уносу да чека док се слот не ослободи. Само прави конфликт, као што је слот који држи ред без померања уноса, или два уноса која замењују слотове, зауставља покретање помоћу `Cannot reconcile ...`.
3. **Држите SQL идемпотентним** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), јер конвертована миграција може да задовољи базу података где њена шема већ постоји.
4. **Померите посебне случајеве са кључем верзије.** Ако је PR додао велико и мало за свој стари број у `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) или у `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`), промените кључ на нову временску ознаку.

`tests/unit/db/codex-fence-migration-rename.test.ts` је радни пример теста за преименовану миграцију.

### Повратни портови до грана пре пребацивања

Никада немојте бирати или преносити `YYYYMMDDHHMMSS_` датотеку у грану која је претходила пребацивању (на пример старија `release/v*` грана). Руннер тамо сортира имена датотека као текст, тако да би датотека са временским жигом радила између `201_` и `202_` на новој бази података, а стара капија не разуме 14-цифрене префиксе. На таквој грани, напишите промену као следећу `NNN_` датотеку те гране, идемпотентну, тако да је не-оп када верзија са временским жигом стигне касније.

### Како се одвијају миграције

Приликом покретања, `migrationRunner.ts`:

1. Креира `_omniroute_migrations` табелу ако не постоји
2. Упити за већ примењене миграције
3. Примењује све нове миграције по редоследу, сваку у трансакцији
4. Записује сваку примењену миграцију са временском ознаком

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### Идемпотенција

Миграције морају бити** идемпотентан** — да их покрене двапут би требало да буде без операције:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

Слободно користите клаузуле `IF NOT EXISTS`, `IF EXISTS` и `OR IGNORE` / `OR REPLACE`.

### Додавање нове миграције

1. **Креирајте датотеку са генератором** : `npm run db:new-migration -- <description>` (на пример `npm run db:new-migration -- add combo priority`). Записује `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` са тренутним UTC временом и заглављем коментара, помера се за једну секунду унапред ако се узме та временска ознака и никада не преписује датотеку. Не бирајте број ручно.
2. **Користите безбедну DDL** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **Пажљиво попуните податке** : користите `UPDATE ... WHERE ...` за руковање постојећим редовима
4. **Проверите редослед и именовање** : `npm run test:migrations:fresh` (све миграције на празну базу података) и `npm run check:migration-numbering`
5. **Тестирајте на копији** : никада не покретати непроверене миграције у производњи
6. **Табела креирана из кода такође треба да се пренесе** : ако модул такође креира табелу лењо (`CREATE TABLE IF NOT EXISTS`, чува се као путања за самоизлечење), миграција је мора креирати са истим DDL. У супротном, чиста инсталација и надограђена инсталација завршавају са различитим шемама, у зависности од тога да ли је та путања кода покренута. `tests/unit/db/lazy-table-migration-guard.test.ts` скенира `src/` и `open-sse/` и не успева на лењи `CREATE` без миграције (#20557). Пример: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

Пример:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **Промене које нису компатибилне уназад** (нпр. испуштање колона) су незгодне. OmniRoute подржава ли NOT — надоградњу када се примени миграција, промена шеме је трајна. Планирајте у складу са тим.

## Шифровање података у мировању

Осетљива поља (API кључеви, OAuth токени, ниске за повезивање) шифрују се у мировању помоћу алгоритма **AES-256-GCM**.

### Како функционише

```ts
// src/lib/db/encryption.ts (поједностављено)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### Где се користи

- `provider_connections.api_key` — шифрује се на нивоу апликације
- `provider_connections.access_token`, `refresh_token`, `id_token` — шифрују се на нивоу апликације
- Уноси `key_value` са `namespace = "secrets"` — шифрују се на нивоу апликације
- `proxy_registry.auth` — шифрује се на нивоу апликације (ако постоји)

### Кључ за шифровање

Кључ за шифровање изводи се из **приступне фразе** (постављене путем променљиве окружења `STORAGE_ENCRYPTION_KEY`) и **соли** (која се чува у бази података). Оба су неопходна за дешифровање података.

```bash
# Генеришите безбедну приступну фразу
openssl rand -hex 32

# Поставите је у .env
STORAGE_ENCRYPTION_KEY=<ваш-кључ>
```

> **Критично**: Губитак кључа за шифровање значи губитак приступа свим шифрованим подацима. **Направите резервну копију кључа одвојено од базе података**.

### Шта НИЈЕ шифровано

Ради бољих перформанси, следећи подаци чувају се као отворени текст:

- Приказни називи добављача
- Дефиниције модела (већ су јавне)
- Правила усмеравања
- Записи о коришћењу (без података који омогућавају идентификацију личности)

---

## Напомене о шифровању (v3.8.16+)

OmniRoute користи **`migrateLegacyEncryptedString()`** за транспарентно руковање двема шемама шифровања:

- **Застарела** (пре v3.5.0): „шифровање“ засновано на XOR-у (није права криптографија)
- **Тренутна**: AES-256-GCM са исправним IV-ом и ознаком за аутентификацију

Помоћна функција за миграцију открива застарели формат и поново шифрује податке новом шемом при првом читању. То значи да можете надоградити стару базу података без губитка акредитива.

## Кеш за читање

За податке који се често читају (модели, добављачи, подешавања), `readCache.ts` обезбеђује **кеш у меморији**:

```ts
// Кеширано при покретању, поништава се при упису
const providers = await getCachedProviders(); // Брзо, у меморији
const fresh = await listProviders(); // Споро, приступа бази података
```

| Кеширани ентитет       | Кључ кеша      | TTL      |
| ---------------------- | -------------- | -------- |
| `models`               | `models:v1`    | До уписа |
| `provider_connections` | `providers:v1` | До уписа |
| `settings`             | `settings:v1`  | До уписа |
| `combos`               | `combos:v1`    | До уписа |

Кеш се поништава при сваком упису у одговарајућу табелу.

## Прављење и враћање резервних копија

### Ручно прављење резервне копије

```bash
# Користите CLI да бисте направили локалну резервну копију
omniroute backup create --name pre-migration

# Или путем API-ја
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

Датотека резервне копије садржи:

- Све табеле базе података (серијализоване у JSON)
- Артефакте евиденције позива (кодиране у base64, опционално)
- Подешавања + тајне (шифроване)
- Конфигурацију додатака

### Враћање

```bash
# Путем CLI-ја
omniroute restore pre-migration

# Путем API-ја
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **Упозорење**: Враћање преписује целу базу података. Прво зауставите све клијенте.

### Аутоматизоване резервне копије

```bash
# Омогућите аутоматизоване дневне резервне копије путем CLI-ја
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

Распоред се извршава на страни сервера путем позадинског задатка који се активира сваких 30 секунди
(подразумевано) и проверава cron израз у односу на локално време сервера.

| Променљива                                  | Подразумевано | Опис                                                                                                           |
| ------------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`       | Интервал активирања у ms (мин. `5000`). Мора бити краћи од 60 s да би поуздано упао у одговарајући cron минут. |

### SQLite резервна копија активне базе

За прављење резервне копије активне базе података без прекида рада:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

Ово користи SQLite API за прављење резервних копија на мрежи — безбедно је за покретање док OmniRoute ради.

## Подешавање перформанси

### WAL Моде

WAL је подразумевано омогућен. За велика оптерећења писања, узмите у обзир:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute не поставља `journal_size_limit`. Контролна тачка помера WAL оквире у главну датотеку, али WAL датотека задржава своју највећу додељену величину. `OMNIROUTE_WAL_GUARD_MAX_MB` чувар само упозорава и покреће `wal_checkpoint(RESTART)`; није ограничење величине диска.

### Индекси

Кључни индекси за учинак (аутоматски креирани миграцијама):

- `idx_models_provider` — тражења модела по провајдеру
- `idx_combo_targets_combo_id` — комбиновано проширење циља
- `idx_usage_history_api_key_timestamp` аналитика употребе —
- `idx_quota_snapshots_api_key_window` — праћење квота
- `idx_call_logs_timestamp` — упити за евиденцију позива

Да бисте додали нови индекс, направите миграцију:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### Мемори-Маппед I/O

За веома велике базе података (> 10ГБ), мапирање меморије се може подесити преко SQLite прагма:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### Збијање

Дуготрајне OmniRoute инстанце имају користи од повременог `VACUUM`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

Покрени месечно током периода са малим прометом. (WAL режим смањује потребу, али је не елиминише.)

## Провера исправности

`src/lib/db/healthCheck.ts` пружа **дијагностику исправности на нивоу базе података**:

Оба глагола захтевају аутентификацију (у супротном се враћа `401`). `GET` служи само за дијагностику; `POST` покреће
исту проверу са омогућеним `autoRepair`.

```bash
GET  /api/db/health   # дијагностика
POST /api/db/health   # дијагностика + поправка
```

Одговор је `DbHealthCheckResult` који производи `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Буџети домена упућивали су на API кључеве који више не постоје.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| Поље              | Значење                                                                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | Има вредност `true` када је `issues` празан. `driver` никада не утиче на њега.                                                                                              |
| `issues[].type`   | Једна од вредности `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`.                                                                         |
| `repairedCount`   | Редови поправљени током овог покретања; увек је `0` када `autoRepair` има вредност false.                                                                                   |
| `backupCreated`   | Да ли је резервна копија направљена пре поправке.                                                                                                                           |
| `checkedAt`       | ISO временска ознака коју деле покретање и свака белешка о поправци коју оно упише.                                                                                         |
| `driver.name`     | SQLite управљачки програм који опслужује проверену базу података.                                                                                                           |
| `driver.degraded` | Има вредност `true` када уписи нису трајно сачувани у датотеци базе података — резервна `sql.js` WASM варијанта (трајно чување целе датотеке) или база података у меморији. |

Исти садржај враћа MCP алатка `omniroute_db_health_check`.

Покрените `PRAGMA integrity_check` да бисте открили оштећење:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# Требало би да испише: ok
```

Ако врати било шта осим `ok`, **одмах престаните да користите базу података** и вратите је из резервне копије.

## Опоравак од катастрофе

### Сценарио 1: WAL датотека је изгубљена

Датотека `-wal` недостаје, али су `-shm` и главна база података нетакнуте:

```bash
# Аутоматски се опоравља при следећем отварању
omniroute
```

Ако SQLite не може аутоматски да изврши опоравак:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### Сценарио 2: Главна датотека базе података је оштећена

Вратите је из резервне копије:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` само преузима целу `.tar.gz` архиву са покренутог сервера
(`GET /api/db-backups/exportAll`, неопходни су акредитиви оператера); не врши никакво враћање података.

### Сценарио 3: Кључ за шифровање је изгубљен

**Опоравак није могућ** без кључа. Шифрована поља су нечитљива. Поново ручно додајте све провајдере са новим акредитивима.

> **Ублажавање ризика**: Увек засебно правите резервну копију кључа за шифровање, по могућству у менаџеру лозинки или KMS-у.

### Сценарио 4: Диск је пун

SQLite ће враћати грешке `SQLITE_FULL`. Ослободите простор на диску, а затим:

```bash
# Направите контролну тачку WAL-а да бисте ослободили простор
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## Решавање проблема

### „База података је закључана“

Други процес држи закључавање за упис. Можете:

- Сачекати да се други процес заврши (проверите помоћу `lsof | grep storage.sqlite`)
- Прекинути други процес
- Ако се проблем настави, поново покренути OmniRoute

### „Ограничење страног кључа није испуњено“

Модул домена нарушава референцијални интегритет. Проверите:

- Редове без одговарајућих родитељских записа у зависним табелама
- Каскадна брисања која се нису пренела
- Недавну миграцију која је променила страни кључ

Покрените `PRAGMA foreign_key_check;` да бисте пронашли нарушавања.

### „Нема довољно меморије“

SQLite-ов меморијски мапирани У/И премашује ограничење оперативног система. Смањите га помоћу SQLite прагме:

```sql
PRAGMA mmap_size = 134217728;  -- 128MB уместо 256MB
```

Или га онемогућите:

```sql
PRAGMA mmap_size = 0;
```

### „Миграција није успела на пола процеса“

Миграција је извршавана у трансакцији, па је требало да буде поништена. Ако није:

1. **Зауставите OmniRoute** (спречите даље покушаје)
2. **Проверите стање базе података** помоћу `sqlite3`
3. **Ручно исправите** делимичну миграцију
4. **Поново покрените** OmniRoute (миграција ће бити поново покушана)

Да бисте ово спречили, увек прво тестирајте миграције на копији.
