Traffic Inspector — це вбудований в OmniRoute засіб налагодження HTTPS-трафіку, подібний до Charles Proxy / mitmweb / HTTP Toolkit, який **враховує особливості LLM** та **агентів**. Він доступний за адресою `/dashboard/tools/traffic-inspector` і отримує трафік у реальному часі щонайбільше з 5 одночасних джерел захоплення.

**Розташування в панелі керування:** `/dashboard/tools/traffic-inspector`
**Група на бічній панелі:** Інструменти (після AgentBridge)
**Див. також:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge є режимом захоплення 1.

### Архітектура одним абзацом

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) — це спільний кільцевий буфер у пам’яті (за замовчуванням 1000 записів, налаштовується через `INSPECTOR_BUFFER_SIZE`). Усі джерела захоплення записують до нього через `push()`. Клас буфера класифікує кожен запис за допомогою `kindDetector.ts` (визначає, чи є він запитом до LLM), обчислює `contextKey` (відбиток системного промпту на основі SHA-256) і транслює дані всім WebSocket-підписникам через `globalTrafficBuffer.subscribe()`. Панель керування підключається через `GET /api/tools/traffic-inspector/ws` і після підключення отримує знімок стану, а потім події `new`/`update`/`clear`.

## §2 Режими перехоплення

Traffic Inspector підтримує **5 одночасних джерел перехоплення**. Кожне з них можна вмикати й вимикати незалежно. Поле `source` у кожному `InterceptedRequest` (`src/mitm/inspector/types.ts`) має одне зі значень: `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` або `"tproxy"`.

### Режим 1 — AgentBridge (типовий, завжди ввімкнений)

**Джерело:** Обробники AgentBridge (`src/mitm/handlers/base.ts`)
**Механізм:** Кожен виклик `intercept()` у `MitmHandlerBase` викликає `hookBufferStart()` перед пересиланням і `hookBufferUpdate()` після завершення. Жодної додаткової конфігурації — працює одразу після запуску AgentBridge.
**Охоплення:** 9 IDE-агентів, налаштованих в AgentBridge
**Примітка:** Поле `source` в `InterceptedRequest` = `"agent-bridge"`

### Режим 2 — Власні хости (перенаправлення DNS)

**Джерело:** Визначений користувачем список хостів (таблиця `inspector_custom_hosts`)
**Механізм:** Додавання хоста через інтерфейс додає `127.0.0.1 <host>` до `/etc/hosts` (потрібен sudo). Наявний MITM-сервер AgentBridge (порт 443) динамічно генерує SNI-сертифікат для нового хоста.
**Охоплення:** Будь-який застосунок, що використовує доданий хост — змінювати конфігурацію застосунку не потрібно
**Примітка:** `source` = `"custom-host"`

Приклади використання:

- Відстеження `api.openai.com` зі скриптів Python
- Налагодження `my-internal-llm.company.com`
- Перехоплення трафіку з мобільних пристроїв у тій самій мережі (через ARP-спуфінг — для досвідчених користувачів)

### Режим 3 — Прослуховувач HTTP_PROXY (порт 8080)

**Джерело:** Застосунки, що використовують змінні середовища `HTTP_PROXY`/`HTTPS_PROXY`
**Механізм:** Вторинний прослуховувач на порту 8080 (`src/mitm/inspector/httpProxyServer.ts`), який працює як стандартний явний HTTP/HTTPS-проксі. Приймає тунелі `CONNECT` (HTTPS) і прямі HTTP-запити.
**Охоплення:** Будь-який застосунок, що враховує змінну середовища `HTTP_PROXY` — без зміни DNS і без sudo
**Примітка:** `source` = `"http-proxy"`

```bash
# Швидке перехоплення для однієї команди:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Постійне перехоплення в сеансі оболонки:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**Обмеження TLS:** HTTPS проходить через звичайний тунель `CONNECT`: прослуховувач пересилає зашифровані байти без змін і записує лише метадані (хост, порт, часові показники). Він ніколи не розшифровує HTTPS, і для цього режиму немає налаштування, яке вмикає розшифрування. Щоб перехоплювати тіла HTTPS-запитів і відповідей, спрямуйте хост через режим 1 (AgentBridge), режим 2 (власні хости) або режим 5 (розшифрування TPROXY).

**Конфлікт порту:** Якщо порт 8080 уже використовується, AgentBridge повертає 409 зі структурованою помилкою. Змініть порт за допомогою змінної середовища `INSPECTOR_HTTP_PROXY_PORT`.

### Режим 4 — Загальносистемний проксі (для досвідчених користувачів, вмикається окремо)

**Джерело:** Налаштування проксі на рівні ОС (застосовуються до всіх застосунків на комп’ютері)
**Механізм:** Використовує API ОС для перенаправлення всього HTTP/HTTPS-трафіку через прослуховувач HTTP_PROXY:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Охоплення:** Кожен застосунок на комп’ютері, що враховує системні налаштування проксі
  **Примітка:** `source` = `"system-proxy"`

**Механізми безпеки:**

- Таймер автоматичного вимкнення (типово 30 хвилин, налаштовується через `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- Попередній стан системного проксі зберігається в БД і відновлюється під час скасування
- Якщо користувач переходить на іншу сторінку, коли проксі активний, на панелі керування відображається запит «Скасування системного проксі»
- В інтерфейсі відображається значок `⚠ Для досвідчених` і прапорець явного підтвердження

### Режим 5 — Прозоре розшифрування TPROXY (Linux, root, вмикається окремо)

**Джерело:** TPROXY ядра + маршрутизація на основі політик (`src/mitm/tproxy/`)
**Механізм:** Позначає нові локальні вихідні TCP-з’єднання з цільовим портом (типово `443`) у `mangle OUTPUT`, правило `ip rule` перенаправляє позначені пакети на локальну доставку, а ціль `TPROXY` у `mangle PREROUTING` передає їх прозорому прослуховувачу (**IP_TRANSPARENT**) (типовий порт `8443`). Прослуховувач завершує TLS за допомогою кінцевого сертифіката, який динамічний центр сертифікації видає **на вимогу для кожного імені хоста SNI**, перехоплює розшифрований обмін і пересилає повторно зашифрований запит до початкового призначення.
**Охоплення:** **Довільні** хости призначення на цільовому порту — без підміни `/etc/hosts`, змінної середовища `HTTP_PROXY` або зміни загальносистемного проксі. Перехоплюваний процес не потребує зміни конфігурації, але має довіряти динамічному центру сертифікації.
**Примітка:** `source` = `"tproxy"`

**Вимоги:** Лише Linux (**IP_TRANSPARENT** доступний тільки в Linux), можливість **CAP_NET_ADMIN** (root) і нативний додаток N-API, який потрібно зібрати за допомогою набору інструментів C (`npm run build:native:tproxy`). Якщо потрібні компоненти недоступні, перемикач на панелі керування вимкнено, а підказка містить текст «Для розшифрування TPROXY потрібні Linux + root + нативний додаток». Правила брандмауера застосовуються та скасовуються транзакційно (збій ніколи не залишає правило `mangle`), а після перезавантаження очищаються. Механізм запобігання зацикленню на основі SO_MARK не дає проксі повторно перехоплювати власне повторно зашифроване пересилання.

Це значна підсистема з окремим спеціалізованим посібником для операторів — повний рецепт налаштування брандмауера, динамічний центр сертифікації для кожного SNI та інсталятор сховища довіри, локальний маршрут, відомості про запобігання зацикленню й схему конфігурації див. у `docs/security/MITM-TPROXY-DECRYPT.md` (git; не компілюється в `/docs`). Перемикач керується через `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (зверніть увагу: маршрут розміщено під префіксом AgentBridge, а не Traffic Inspector).

- **Кольорова смуга контексту**: ліва межа завтовшки 1px, забарвлена за `contextKey` (SHA-256 системної підказки), — візуально групує пов’язані розмови
- **Ліниве завантаження тіла**: у вкладках із відомостями матеріалізується лише тіло вибраного запиту (щоб уникнути рендерингу 1000 тіл по 1MB)

## §4 Функції з урахуванням LLM

### 4.1 Визначення типу (`src/mitm/inspector/kindDetector.ts`)

Класифікує кожен запит як `"llm"`, `"app"` або `"unknown"` за допомогою 4 сигналів:

1. **Реєстр хостів** — приблизно 18 відомих імен хостів API LLM (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot тощо)
2. **Шаблони шляхів** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` тощо
3. **Структура тіла** — виявляє поля `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **Підказки user-agent** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` у рядку UA

Власні хости, додані через режим 2, успадковують свій `kind` із введених у формі даних (типове значення — `"custom"`).

### 4.2 Об’єднувач SSE (`src/mitm/inspector/sseMerger.ts`)

**Незалежна реалізація, створена з чистого аркуша.** Розбір подій відповідає
[алгоритму подій, надісланих сервером, WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
а реконструкція відповідає загальнодоступним схемам потокового передавання
[OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) і
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent).

Відтворює остаточне повідомлення асистента з необроблених дельта-подій SSE:

- **Anthropic**: накопичує `content_block_delta` за індексом; обробляє `text_delta`, `input_json_delta` (виклики інструментів), `thinking_delta`
- **OpenAI**: накопичує варіанти Chat Completions/виклики інструментів і вихідні елементи Responses API
  за індексом
- **Gemini**: накопичує `candidates[i].content.parts`
- **Невідомий формат**: повертає необроблені події без змін

На вкладці Response відображається перемикач: **«Необроблені події ↔ Об’єднаний результат»**.

### 4.3 Нормалізатор розмов (`src/mitm/inspector/conversationNormalizer.ts`)

**Незалежна реалізація, створена з чистого аркуша.** Нормалізацію визначають локальні контракти
«чорної скриньки» та загальнодоступні схеми повідомлень OpenAI, Anthropic і Gemini; вихідний код
сторонніх реалізацій не використовується.

Перетворює формати повідомлень OpenAI, Anthropic і Gemini на єдиний `NormalizedConversation` перед відтворенням:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // повідомлення / вміст / запит із тіла запиту
  response: NormalizedTurn[]; // відповідь асистента (об’єднана через sseMerger)
  contextKey: string | null; // відбиток системного запиту SHA-256
}
```

Типи блоків: `text`, `tool_use`, `tool_result`. Вкладка Conversation використовує цю структуру незалежно від постачальника.

### 4.4 Кольорове позначення ключа контексту (`src/mitm/inspector/contextKey.ts`)

- Обчислює `SHA-256` системного запиту (перше повідомлення `role:system`, поле `system` або `systemInstruction` Gemini)
- Повертає 12-символьний шістнадцятковий префікс (`"a3f9c2..."`)
- Інтерфейс зіставляє ключ із детермінованим кольором HSL для смуги лівої межі
- **Фільтр «той самий контекст»**: натискання мітки `ctx #a3f` додає фільтр, який показує лише запити з тим самим відбитком

Це дає змогу легко візуально розрізняти різні «персони» або завдання, що виконуються в межах одного сеансу агента.

### 4.5 Видобування метаданих LLM

Для запитів LLM вкладка LLM Details видобуває:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // із тіла запиту або відповіді
  messages: number; // кількість реплік
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true, якщо це відповідь SSE
  mappedTo: string | null; // заголовок x-omniroute-mapped
  costEstimateUsd: number | null; // орієнтовна вартість на основі тарифів OmniRoute
}
```

### 4.6 Фільтр активних запитів у реальному часі

Поле `status` запиту має тип `number | "in-flight" | "error"` — запис
додається зі значенням `"in-flight"` у момент початку запиту та **оновлюється на місці**,
коли надходить відповідь (або виникає помилка). Перемикач **«Наживо»** на панелі інструментів
(`liveOnly`, ключ i18n `trafficInspector.liveOnly`) обмежує список записами,
у яких `status === "in-flight"`, даючи змогу спостерігати за відкритими з’єднаннями в реальному часі.

Фільтр є чистим предикатом на стороні клієнта у
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

Стан перемикача зберігається в `useTrafficFilters` (хуки панелі інспектора) і
поєднується з іншими фільтрами (профіль, хост, агент, джерело, статус, контекст).

### 4.7 Прив’язування до процесу (Linux)

У Linux кожен перехоплений запит можна пов’язати з **локальним процесом-джерелом**.
До `InterceptedRequest` додаються два необов’язкові поля:

```ts
pid?: number;          // ідентифікатор процесу-джерела (лише Linux)
processName?: string;  // назва процесу-джерела (лише Linux)
```

`src/mitm/inspector/processAttribution.ts` зіставляє тимчасовий порт _клієнта_
з PID і назвою таким чином:

1. Читає `/proc/net/tcp` і `/proc/net/tcp6`, щоб знайти inode сокета для
   порту (`parseProcNetTcpForInode` — чистий парсер, який можна тестувати на фікстурах).
2. Переглядає `/proc/<pid>/fd/` у пошуках символічного посилання на `socket:[<inode>]`.
3. Читає назву процесу з `/proc/<pid>/comm`.

Кеш із TTL 1 секунда обмежує витрати на сканування procfs під навантаженням. Прив’язування
виконується **за можливості** — за будь-якої помилки повертається `null`, і захоплення ніколи
не блокується. У macOS/Windows функція повертає `null` (заглушка; підтримку
`lsof`/`GetExtendedTcpTable` буде додано згодом).

## §5 Сеанси

### 5.1 Запис сеансу

1. Натисніть **"● Записати сеанс"** на панелі інструментів → введіть назву (необов’язково)
2. Відображення даних у реальному часі продовжується у звичайному режимі; червоний пульсуючий індикатор показує `◉ ЗАПИС · <назва> · 00:42 · 23 запити`
3. Натисніть **"⏹ Зупинити"** → знімок сеансу буде збережено до `inspector_sessions` + `inspector_session_requests`

### 5.2 Перегляд записаного сеансу

Розкривний список **Сеанси** на панелі інструментів містить збережені сеанси. Після вибору сеансу:

- Завантажується знімок сеансу (зафіксований стан)
- На банері відображається: `Перегляд записаного сеансу "<назва>" — [Повернутися до даних у реальному часі]`
- Стає доступною вкладка «Статистика» з агрегованими даними Recharts

### 5.3 Формати експорту

Кожен сеанс можна експортувати в таких форматах:

| Формат                     | Використання                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------- |
| **HAR** (HTTP Archive 1.2) | Сумісний із Chrome DevTools, Charles, Fiddler — імпортуйте для офлайн-аналізу      |
| **JSONL**                  | Один `InterceptedRequest` у кожному рядку — сумісний із форматом `llm-interceptor` |

Експортуйте через `GET /api/tools/traffic-inspector/sessions/{id}/export.har` або за допомогою кнопки ⬇ у розкривному списку «Сеанси».

## §6 Безпека

Інспектор трафіку показує **весь перехоплений HTTPS-трафік**, включно із заголовками авторизації та тілами запитів. Застосовуються такі засоби контролю:

| Засіб контролю                      | Докладні відомості                                                                                                                                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                      | Усі маршрути та кінцева точка WebSocket доступні лише через loopback-інтерфейс (це забезпечується в `routeGuard.ts` до автентифікації)                                                               |
| **Маскування секретів**             | Лінійний сканер `maskSecret()` приховує облікові дані Bearer за RFC 6750, ключі з префіксами провайдерів і довгі непрозорі токени перед викликом `TrafficBuffer.push()`                              |
| **Обмеження розміру тіла**          | Тіла розміром понад `INSPECTOR_MAX_BODY_KB` (за замовчуванням — 1024 КБ) обрізаються з повідомленням `"(truncated for performance)"`                                                                 |
| **Очищення заголовків**             | Назви переводяться в нижній регістр; заголовки фреймінгу, hop-by-hop і проксі-автентифікації видаляються; файли cookie повністю приховуються; значення облікових даних передаються до `maskSecret()` |
| **CSP**                             | На сторінках Інспектора трафіку діє сувора політика безпеки вмісту, яка запобігає XSS через впроваджені тіла відповідей                                                                              |
| **Без збереження за замовчуванням** | `TrafficBuffer` зберігається в пам’яті та втрачається після перезапуску сервера. Сеанси зберігаються лише за явного запуску запису                                                                   |

### Застосовані жорсткі правила

| Правило                           | Застосування                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Усі HTTP-відповіді з помилками від маршрутів Інспектора трафіку очищуються                        |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` має статус LOCAL_ONLY + SPAWN_CAPABLE (команди системного проксі) |

### Відомі обмеження

- **Загальносистемний режим проксі** впливає на всі програми на комп’ютері, включно з VPN-клієнтами та SSO. Завжди використовуйте його з таймером автоматичного вимкнення. Не використовуйте на комп’ютерах зі спільним доступом.
- **HTTPS через тунель CONNECT**: режим 3 (HTTP_PROXY) для HTTPS-призначень перехоплює лише метадані тунелю й ніколи не розшифровує трафік. Це передбачено конструкцією: для розшифрування кожен клієнт мав би довіряти MITM-сертифікату, тому прослуховувач зберігає наскрізне шифрування HTTPS. Якщо вам потрібні тіла HTTPS-повідомлень, використовуйте AgentBridge, Custom Hosts або розшифрування TPROXY.
- **Жорстко закодовані рядки в деяких компонентах**: деякі компоненти інтерфейсу користувача (F7/F8) містять невелику кількість жорстко закодованих рядків, які ще не охоплені ключами i18n. Їх задокументовано як відоме обмеження у звіті про прогалини i18n; їх буде перенесено під час наступного етапу. Зачеплені рядки є декоративними мітками інтерфейсу користувача, які не потребують перекладу для функціонального використання.

## §7 Усунення несправностей

### Відключення WebSocket

Якщо в потоці даних у реальному часі відображається «Відключено»:

1. Перевірте, чи сервер усе ще працює: `GET /api/tools/traffic-inspector/capture-modes`
2. Перезавантажте сторінку — WebSocket повторно підключиться й отримає новий знімок
3. Якщо сервер було перезапущено, буфер у пам’яті було очищено — старі записи втрачено, якщо сеанс не було записано

### Конфлікт порту 8080

Якщо режим HTTP_PROXY не запускається:

```bash
lsof -i :8080    # знайти процес
```

Змініть порт:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Системний проксі не повернуто до попереднього стану

Якщо OmniRoute аварійно завершує роботу, коли активний загальносистемний режим проксі:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

Під час наступного завантаження панель керування також запропонує «Повернути системний проксі до попереднього стану», якщо виявить, що стан у БД указує на активний проксі.

### Буфер заповнений

Коли буфер досягає розміру `INSPECTOR_BUFFER_SIZE` (типово 1000), нові записи витісняють найстаріші. Якщо важливі запити втрачаються:

- Збільште `INSPECTOR_BUFFER_SIZE` (наприклад, до 5000) — це збільшить використання пам’яті, але дасть змогу зберігати більше записів
- Запишіть сеанс, щоб зберегти відповідний проміжок у БД

### Режими перехоплення

| Метод | Шлях                          | Опис                                                                              |
| ----- | ----------------------------- | --------------------------------------------------------------------------------- |
| GET   | `/capture-modes`              | Стан режимів AgentBridge / користувацьких хостів / HTTP_PROXY / системного проксі |
| POST  | `/capture-modes/http-proxy`   | Запустити/зупинити прослуховувач HTTP_PROXY (`{action: "start"\|"stop"}`)         |
| POST  | `/capture-modes/system-proxy` | Застосувати/скасувати системний проксі (`{action: "apply"\|"revert"}`)            |

> **Розшифрування TPROXY** (режим перехоплення 5) керується **окремим** маршрутом із
> префіксом AgentBridge — `GET / POST / DELETE /api/tools/agent-bridge/tproxy` — а не
> в межах `/api/tools/traffic-inspector/`. Див.
> `docs/security/MITM-TPROXY-DECRYPT.md` (git; не компілюється в `/docs`).
