> **Версія:** v3.8.44** Останнє оновлення:** 2026-10-28** аудиторія:** Інженери додають, підтримують або налагоджують вбудовані служби (9Router, CLIProxyAPI, Mux, Bifrost, open-wa, LLMLingua, sing-box).

Вбудовані служби — це локально встановлені інструменти побічної обробки процесів, які OmniRoute встановлює, контролює та надає як першокласні цілі маршрутизації. На відміну від зовнішніх провайдерів (до яких можна підключитися через Інтернет за допомогою ключів API ), вбудовані служби працюють на тій же машині, що й OmniRoute і обмінюються даними через петлю.

Усі вісім дотримуються однієї моделі нагляду:

- OmniRoute встановлює їх під `DATA_DIR/services/{name}/` (ізольовано від власного `package.json` OmniRoute)
- OmniRoute породжує та контролює їх як дочірні процеси
- OmniRoute вводить ефемерний ключ API у дочірнє середовище та обертає його без простою (де це можливо)
- Усі маршрути керування (`/api/services/*`) є**LOCAL_ONLY** — доступний лише через loopback (жорстке правило №17)

│    │                          MuxServiceTab                        │
│    └── components/            ServiceStatusCard, ServiceLifecycleButtons,│

└──────────────────────┬─────────────────────────────────────────────┘
                       │ HTTP (Next.js fetch)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 2 — API (LOCAL_ONLY — loopback only)                        │
│                                                                    │
│  /api/services/9router/{install|start|stop|restart|update|         │
│                          rotate-key|status|auto-start|logs}        │
│  /api/services/cliproxy/{install|start|stop|restart|update|        │
│                           status|auto-start|logs}                  │
│  /api/services/mux/{install|start|stop|restart|update|             │
│                      status|auto-start|logs}                       │

│                                                                    │
│  Gate: LOCAL_ONLY_API_PREFIXES includes "/api/services/" and       │

┌──────────────────────▼─────────────────────────────────────────────┐

│                                                                    │

│    ├── api_key:    crypto.randomBytes(32) → env NINEROUTER_API_KEY  │

│  healthCheck.ts     Polling HTTP health probe                      │
│  installers/        ninerouter.ts, cliproxy.ts, mux.ts, openwa.ts  │
│                      (installer adapters)                          │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ OpenAI-compatible HTTP (loopback)
┌──────────────────────▼─────────────────────────────────────────────┐
│  Layer 4 — Provider / Routing                                      │
│                                                                    │
│  open-sse/executors/ninerouter.ts                                  │
│    Re-looks up port and API key per-request (no caching).          │
│    Strips "9router/" prefix from model id before proxying.         │
│    Returns 503 service_not_running if supervisor not in "running". │
│                                                                    │
│  src/shared/constants/providers.ts                                 │
│    Entry for "9router": isEmbeddedService: true                    │
│                                                                    │
│  open-sse/config/providerRegistry.ts                               │
│    Models stored as "9router/{sub}/{model}" (prefixed).            │
│    Synced every 5 min by modelSync.ts.                             │
│                                                                    │

## 3. Автомат станів життєвого циклу

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
            перевірка стану успішна │         збій / SIGTERM    │
                               ┌────▼─────┐  (вихід у межах 5 с)│
                               │ running  │──── збій ───────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Стани зберігаються в таблиці БД `version_manager` (стовпець `status`) і дублюються
у стані `ServiceSupervisor` у пам’яті. Для запущеного процесу стан у пам’яті є
авторитетним джерелом; стан у БД є надійним резервним джерелом під час завантаження.

### Переходи між станами

| Зі стану        | Подія                                   | До стану               |
| --------------- | --------------------------------------- | ---------------------- |
| `not_installed` | `install()` завершується успішно        | `stopped`              |
| `stopped`       | викликано `start()`                     | `starting`             |
| `starting`      | перевірка стану повертає 200            | `running`              |
| `starting`      | процес завершується до готовності       | `error`                |
| `running`       | викликано `stop()`                      | `stopping` → `stopped` |
| `running`       | процес неочікувано завершується (< 5 с) | `error` (швидкий збій) |
| `running`       | процес неочікувано завершується (> 5 с) | `error`                |
| `error`         | викликано `start()`                     | `starting`             |
| будь-який       | `stop()` під час `stopping`             | без дії                |

### Блокування операцій

`ServiceSupervisor` послідовно виконує операції життєвого циклу за допомогою
асинхронного блокування операцій (`withLock()`). Одночасні виклики `start()` для
того самого супервізора призводять рівно до одного запуску процесу; другий виклик
очікує та повертає наявний стан. Це запобігає станам перегонів, коли, наприклад,
автоматичний запуск і натискання кнопки в інтерфейсі відбуваються одночасно.

## 4. посилання API

Усі маршрути під `/api/services/` є**LOCAL_ONLY** (тільки петля, жорстке правило №17). Запити без зворотного зв’язку отримують `403 LOCAL_ONLY` незалежно від маркера авторизації.

### 4.1 Кінцеві точки маршрутизатора 9 (11 маршрутів)

#### `POST /api/services/9router/install`

Встановіть 9Router з npm. Створює `DATA_DIR/services/9router/` з власними `package.json` і `node_modules/`. Не конфліктує з власними відділами OmniRoute.

**Тіло запиту** (все необов'язково):

```json
{ "version": "latest" }
```

| Поле      | Тип      | За замовчуванням | опис                                       |
| --------- | -------- | ---------------- | ------------------------------------------ |
| `version` | `string` | `"latest"`       | тег версії npm або semver для встановлення |

**Відповіді:**

| Статус | опис                                                           |
| ------ | -------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`         |
| `400`  | Недійсне тіло запиту (збій перевірки Zod )                     |
| `409`  | Уже встановлюється (заблоковано)                               |
| `500`  | Помилка встановлення npm — див. `message` для дружньої помилки |

**Примітки:** Використовує `execFile('npm', [...])` — без оболонки, без інтерполяції (жорстке правило №13). Помилки EACCES відображаються як дружні повідомлення.

#### `POST /api/services/9router/start`

### 4.9 Зворотний проксі (вбудована інформаційна панель 9Router)

Інформаційна панель вбудовує веб- UI 9Router в iframe через внутрішній зворотний проксі-сервер за адресою:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Цей проксі:

- Пересилає запит до `http://127.0.0.1:{port}/{path}` (тільки петля)
- Видаляє вхідні заголовки `cookie` та `authorization` (без витоку сесії OmniRoute )
- Впроваджує `Authorization: Bearer {apiKey}` для аутентифікації 9Router
- Видаляє `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` з відповіді
- Переписує відповіді HTML для введення `<base href>` і нормалізації абсолютних шляхів (`/foo` → `/dashboard/.../embed/foo`)

Оновлення WebSocket для вбудованої інформаційної панелі обробляються супутнім сервером на спеціальному порту (див. `src/lib/services/embedWsProxy.ts`).

**Безпека:** Вбудовані проксі-маршрути класифікуються як `LOCAL_ONLY_API_PREFIXES`, і доступ до них можливий лише через петлю. Зловмисник, який отримує JWT через тунель Cloudflare/Ngrok не може використовувати проксі-сервер для вбудованих служб.

## 5. Безпека

### Забезпечення LOCAL_ONLY (жорстке правило #17)

Усі маршрути в `/api/services/` та `/dashboard/providers/services/*/embed/`
класифікуються як LOCAL_ONLY у `src/server/authz/routeGuard.ts`. Перевірка loopback
виконується безумовно перед будь-якою гілкою автентифікації:

```
надходить запит
  → isLocalOnlyPath(path)?
      → не loopback → 403 LOCAL_ONLY (завжди, до перевірки автентифікації)
      → loopback    → перехід до звичайної автентифікації
```

Це запобігає використанню скомпрометованого JWT (наприклад, через тунель) для запуску
`npm install` або створення процесів. Повну матрицю рівнів див. у
`docs/security/ROUTE_GUARD_TIERS.md`.

### Впровадження API-ключа

9Router і Mux вимагають API-ключ або bearer-токен для власних HTTP-ендпоінтів.
OmniRoute:

1. Генерує ключ за допомогою `crypto.randomBytes(32).toString("base64url")` із
   префіксом, специфічним для сервісу (`nr_` для 9Router, `mx_` для Mux).
2. Шифрує його під час зберігання за допомогою AES-256-GCM (того самого шифру, який використовується для облікових даних провайдера).
3. Розшифровує та впроваджує його як змінну середовища під час створення процесу —
   `NINEROUTER_API_KEY` для 9Router, `MUX_SERVER_AUTH_TOKEN` для Mux (ніколи не як CLI-прапорець,
   тому токен ніколи не з’являється у `ps` або списках процесів).
4. Ніколи не повертає ключ у відкритому вигляді в жодній HTTP-відповіді.

CLIProxyAPI отримує окремий ключ рівня даних, впроваджений під час створення процесу
(`needsApiKey: true` — використовується для синхронізації моделей з адаптером).

### Захист від SSRF

Зворотний HTTP-проксі (`/dashboard/.../embed/[...path]`) жорстко налаштований на пересилання
лише до `http://127.0.0.1:{port}`. Він ніколи не переходить за перенаправленнями до
адрес, що не належать до loopback. Бібліотека `ssrf-req-filter` використовується для відхилення
будь-якої upstream-URL-адреси, яка резолвиться поза діапазоном loopback.

### Безпека shell-команд (жорстке правило #13)

`npm install` викликається через `execFile('npm', ['install', pkg, '--prefix', dir])` —
без шаблонних літералів, shell та інтерполяції зовнішніх шляхів у рядок команди.
Значення часу виконання (порти, API-ключі) передаються через об’єкт `env` дочірнього процесу.

### Санітизація помилок (жорстке правило #12)

Усі відповіді з помилками від `/api/services/*` проходять через `buildErrorBody()` або
`sanitizeErrorMessage()`. Необроблені `err.stack` та `err.message` ніколи не повертаються
викликачеві дослівно.

`src/lib/services/providerPlugins/` запроваджує контракт `ServiceProviderPlugin`, який

контракт буде перевірено для другого бекенда.

Відкладено до наступних PR і відстежується в межах задачі #7333: міграція `cliproxyapi` через
той самий реєстр, узагальнення `mux`/`bifrost` у тип-об’єднання `ServiceBackendPluginId`,
інтеграція спеціальної логіки маршрутизації виконавців (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) у контракт плагіна та підключення
`createServiceBackendManifestEntry()` до активного шляху обробки коду маніфесту/моделей.

## 7. Усунення несправностей

### Служба не запускається

**Симптоми:** Кнопка запуску повертає 503, стан залишається `"error"` або `"starting"`.

**Контрольний список:**

1. Перевірте `GET /api/services/{name}/logs` (або панель журналів на інформаційній панелі). Шукайте
   рядки на кшталт `Error: ENOENT`, `address already in use` або `Cannot find module`.
2. Переконайтеся, що `npm` є в PATH: виконайте `which npm` з того самого облікового запису користувача, від імені якого працює OmniRoute.
3. Переконайтеся, що службу встановлено: перевірте `GET /api/services/{name}/status` на наявність
   `installedVersion`. Якщо значення — `null`, спочатку виконайте встановлення.
4. Переконайтеся, що `DATA_DIR/services/{name}/node_modules/` існує й не є порожнім.
5. Перевірте поле `lastError` у відповіді зі станом, щоб дізнатися очищену від конфіденційних даних причину завершення.

---

### Холодний запуск триває довго (> 10 с до переходу в стан `running`)

**Симптоми:** Стан залишається `"starting"` протягом тривалого часу, перш ніж перейти в `"running"` або `"error"`.

**Пояснення:** Холодний запуск 9Router включає імпортування великих дерев залежностей (модулів DNS,
тунелю та MITM). Стандартний інтервал перевірки працездатності становить 2 с із 3 спробами, перш ніж
супервізор оголосить про перевищення часу очікування (але продовжить опитування).

**Виправлення:** `healthIntervalMs` і час очікування `waitForHealthy`
(`healthIntervalMs * 3`) можна налаштувати в `bootstrap.ts`. Для служб із тривалішим
часом запуску збільште `healthIntervalMs` до 5000, а `stopTimeoutMs` — до 30 000.

---

### Конфлікт порту (`EADDRINUSE`)

**Симптоми:** У журналах відображається `address already in use :::20130`.

**Причини:**

- Інший процес уже використовує порт 20130.
- Попередній процес 9Router не було повністю зупинено (PID процесу-зомбі).

**Виправлення:**

1. Змініть стандартний порт за допомогою змінної середовища `NINEROUTER_PORT` у `.env`.
2. Знайдіть і завершіть конфліктний процес: `lsof -ti :20130 | xargs kill -9`.
3. Порт можна налаштувати для кожної служби в `bootstrap.ts` за допомогою поля `port`.

**Примітка:** 9Router за замовчуванням використовує порт 20130 спеціально для уникнення конфлікту зі
стандартним портом 20128 OmniRoute.

---

### Відмовлено в доступі (EACCES) під час встановлення

**Симптоми:** Встановлення повертає 500, у журналах відображається `EACCES` або `permission denied`.

**Причини:**

- `DATA_DIR` або його батьківський каталог недоступний для запису процесом OmniRoute.
- Запуск у Docker без прав root і без доступу на запис до підключеного тому.

**Виправлення:**

1. Перевірте `DATA_DIR` (за замовчуванням: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. Переконайтеся, що користувач процесу OmniRoute є власником каталогу: `chown -R $USER ~/.omniroute/`
3. У Docker переконайтеся, що підключений том має правильні дозволи для користувача контейнера.

---

### Не вдається виконати оновлення (перевищено час очікування `npm install` або сталася помилка мережі)

**Симптоми:** Оновлення повертає 500 з `InstallError`, у журналах відображається повідомлення про перевищення часу очікування мережі.

**Контрольний список:**

1. Переконайтеся, що реєстр npm доступний: `npm ping`.
2. Перевірте наявність корпоративного проксі-сервера: `npm config get proxy`, `npm config get https-proxy`.
3. Спробуйте встановити вручну: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. Якщо система ізольована від мережі, попередньо завантажте tarball і скористайтеся командою `npm install /path/to/tarball.tgz`.

---

### Служба переходить у стан `"error"` одразу після запуску (швидкий аварійний вихід)

**Симптоми:** Стан переходить із `"starting"` у `"error"` менш ніж за 5 секунд.
`lastError` відображає `"Fast crash (exited with code 1)"`.

**Контрольний список:**

1. Перегляньте повний кінець журналу: `GET /api/services/{name}/logs?tail=500`.
2. Поширена причина: відсутні змінні середовища, необхідні службі.
3. Для 9Router: переконайтеся, що `NINEROUTER_DISABLE_MITM=true` і
   `NINEROUTER_DISABLE_TUNNEL=true` передаються в середовищі під час створення процесу (див.
   `installers/ninerouter.ts` `resolveSpawnArgs`).

## 8. Поширені запитання

**З: Чи можу я зробити кінцеві точки вбудованих сервісів доступними для клієнтів поза loopback-інтерфейсом?**

Ні. Рівень LOCAL_ONLY запроваджено навмисно (жорстке правило №17). Маршрути, які можуть викликати
`npm install` або породжувати процеси `node`, не повинні бути доступними для трафіку
не з loopback-інтерфейсу, оскільки витік JWT через тунель (Cloudflare, Ngrok, Tailscale)
інакше дозволив би довільне породження процесів. Для
`/api/services/` немає винятку з можливістю відмови — на відміну від `/api/mcp/`, його виключено зі списку
обходу перевірки області manage. Див. `docs/security/ROUTE_GUARD_TIERS.md`.

---

**З: Чи будуть 9Router і CLIProxyAPI доступні в робочих/хмарних розгортаннях?**

Так. Обидва сервіси дотримуються тієї самої локально-орієнтованої моделі, що й сам OmniRoute. Вони працюють
на тому самому комп’ютері та обмінюються даними через loopback-інтерфейс. «Робоче середовище» тут означає VPS
або локальний сервер, на якому розгорнуто OmniRoute, а не віддаленого хмарного провайдера.

---

**З: Як налагоджувати супервізор?**

1. Переглядайте потік журналів SSE у реальному часі: `curl -N http://localhost:20128/api/services/9router/logs`.
2. Перевірте структуровані журнали у виводі pino OmniRoute, відфільтровані за простором імен
   `service:supervisor`.
3. Перевірте рядок БД: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. Скористайтеся `GET /api/services/9router/status`, щоб одним викликом переглянути поточний фактичний стан, PID, працездатність
   і `lastError`.

---

**З: Супервізор показує `health: "degraded"` або `health: "unknown"`, але стан — `"running"`. Це проблема?**

`"degraded"` означає, що перевірка працездатності повернула відповідь, відмінну від 200. `"unknown"` означає, що жодну
перевірку ще не завершено (конфлікт у часі з першим опитуванням). Обидва стани є тимчасовими під час запуску.
Якщо стан працездатності залишається `"degraded"` довше ніж `healthIntervalMs * 3` мс після переходу до
`"running"`, вбудований сервіс працює, але його HTTP API не відповідає. Перевірте,
чи правильний порт указано у відповіді стану та чи справді сервіс
прослуховує цей порт.

---

**З: Чи можу я змінити ключ API 9Router без повного перезапуску?**

Ні. Ключ API передається до 9Router через змінну середовища під час породження процесу.
Змінні середовища неможливо змінити в запущеному процесі. `POST .../rotate-key`
автоматично зупиняє та перезапускає сервіс, щоб застосувати новий ключ. Ротація ключа
набуває чинності протягом `stopTimeoutMs` сервісу (за замовчуванням 15 с) плюс час,
потрібний для його запуску.

---

**З: Яке обмеження має кільцевий буфер і що відбувається, коли він заповнюється?**

Кожен сервіс має окремий кільцевий буфер обсягом 5 МБ. Коли буфер заповнюється, найстаріші
рядки журналу видаляються, щоб звільнити місце для нових. Подія SSE `snapshot` повертає
найновіші рядки в межах обмеження `tail`. Журнали не зберігаються на диску, якщо
в рядку БД не встановлено `logsBufferPath`.
