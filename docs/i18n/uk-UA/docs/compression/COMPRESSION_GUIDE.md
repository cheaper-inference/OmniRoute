> Автоматично заощаджуйте 15–95% токенів у придатному для стиснення контексті. Короткий огляд наведено в [розділі README про стиснення](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## Огляд

OmniRoute реалізує модульний конвеєр стиснення промптів, який запускається **проактивно**, перш ніж запити надходять до зовнішніх провайдерів. Це означає, що токени заощаджуються прозоро — жодних змін у вашому робочому процесі не потрібно.

```
Запит клієнта
  → Засіб вибору стратегії стиснення
    → Є перевизначення комбінацією? → Використати налаштування комбінації
    → Досягнуто порога автоматичного запуску? → Використати автоматичний режим
    → Режим за замовчуванням? → Використати глобальне налаштування
    → Вимкнено? → Пропустити стиснення
  → Вибраний режим стиснення
    → Вимкнено: без стиснення
    → Легкий: безпечне очищення пробілів і форматування (~15%)
    → Стандартний: видалення зайвих слів у телеграфному стилі (~30%)
    → Агресивний: ущільнення історії + узагальнення (~50%)
    → Ультра: евристичне скорочення + проріджування блоків коду (~75%)
    → RTK: фільтрування виводу термінала/інструментів з урахуванням команд (діапазон 60–90% для висхідних запитів)
    → Стековий: упорядкований багатоетапний конвеєр, зазвичай RTK, а потім Caveman (діапазон 78–95% для придатного вмісту)
  → Стиснений запит → Провайдер
```

## Режими стиснення

### Режим Off

Стиснення не застосовується. Усі повідомлення проходять без змін.

### Режим Lite (~15% економії, затримка <1 мс)

Найбезпечніший режим — жодних семантичних змін, лише очищення форматування:

| Техніка                  | Опис                                                        |
| ------------------------ | ----------------------------------------------------------- |
| `collapseWhitespace`     | Об'єднує послідовні порожні рядки та пробіли в кінці рядків |
| `dedupSystemPrompt`      | Видаляє дублікати системних повідомлень                     |
| `compressToolResults`    | Стискає багатослівні виводи інструментів/функцій            |
| `removeRedundantContent` | Усуває повторювані інструкції                               |
| `replaceImageUrls`       | Скорочує base64 data URI зображень                          |

**Найкраще підходить для:** постійно увімкненого використання, критичних щодо безпеки робочих процесів.

### Режим Standard (~30% економії)

Натхненний [Caveman](https://github.com/JuliusBrussee/caveman) — видаляє слова-паразити та багатослівні формулювання, зберігаючи зміст:

- Видаляє слова-паразити ("please", "I think", "basically", "actually")
- Ущільнює багатослівні фрази ("in order to" → "to", "as a result of" → "because")
- Усуває ввічливі обмовки ("Would you mind...", "If you could possibly...")
- Понад 30 regex-правил, налаштованих під промпти програмування

**Найкраще підходить для:** щоденних робочих процесів програмування, команд, які економлять витрати.

### Режим Aggressive (~50% економії)

Розумне керування історією для тривалих сесій:

- **Старіння повідомлень** — старіші повідомлення поступово стискаються дедалі сильніше
- **Стиснення результатів інструментів** — довгі виводи інструментів обрізаються або пропускаються (перші/останні рядки,
  фільтрація рядків за збігом, ущільнення ключів JSON)
- **Засоби захисту структурної цілісності** — гарантують узгодженість пар `tool_use` + `tool_result`
- **Врахування контекстного вікна** — дотримується лімітів токенів кожної моделі

**Найкраще підходить для:** тривалих сесій налагодження, великих кодових баз.

### Режим Ultra (~75% економії)

Максимальне стиснення для критичних щодо токенів сценаріїв:

- **Евристичне скорочення** — скорочення токенів у прозі на основі оцінювання
- **Збереження структури** — огороджені блоки коду, вбудований код, URL-адреси та ідентифікатори
  позначаються маркерами-заповнювачами і зшиваються назад дослівно, без скорочення
- **Опціональний рівень SLM** — мала локальна модель може уточнити скорочення, якщо її налаштовано
- Незалежний від режиму Aggressive: не виконує старіння повідомлень, стиснення результатів інструментів
  чи резервне підсумовування (лише збій рівня SLM може спрямувати резервний прохід
  через режим Aggressive)

**Найкраще підходить для:** випадків, коли ви постійно впираєтеся в ліміти контексту.

### Режим RTK (60–90% у верхньому діапазоні)

Режим RTK оптимізовано для багатослівних виводів інструментів, які з'являються в сесіях агентів кодування:

- Розпізнає класи команд/виводів, такі як `git status`, `git diff`, `git log`, раннери тестів,
  збірки TypeScript/Vite/Webpack, ESLint/Biome/Prettier, npm audit/установки, логи Docker, інфраструктурний
  вивід і загальний вивід оболонки
- Застосовує пакети JSON-фільтрів з `open-sse/services/compression/engines/rtk/filters/`
- Імпортує фільтри RTK TOML schema v1 з проєктних або глобальних файлів `filters.toml`, з валідацією
  вбудованими тестами та контролем довіри для проєктних файлів
- Постачається з 56 вбудованими фільтрами з вбудованими зразками для перевірки
- Видаляє керувальні послідовності ANSI, індикатори прогресу, повторювані рядки та неінформативний шум
- Зберігає збої, помилки, попередження, змінені файли, підсумки та кінець довгого виводу
- Підтримує проєктні фільтри з контролем довіри, глобальні фільтри та опціональне відновлення сирого виводу з маскуванням

**Найкраще підходить для:** сесій агентів із транскриптами оболонки, збірок, тестів, git, grep та виводу файлів.

### Режим Stacked (78–95% у застосовному діапазоні)

Режим Stacked запускає кілька рушіїв стиснення в детермінованому порядку. Типовий конвеєр:

```txt
RTK -> Caveman
```

Такий порядок спочатку ущільнює вивід термінала/інструментів, а потім застосовує семантичне ущільнення
Caveman до природномовного промпту, що залишився. Конвеєри Stacked можна налаштовувати глобально або через
комбінації стиснення, призначені комбінаціям маршрутизації.

**Найкраще підходить для:** змішаного контексту з великими логами інструментів у поєднанні з людськими інструкціями або підсумками асистента.

## Розрахунок економії від вихідних проєктів

OmniRoute документує економію завдяки стисненню з двох джерел: тестів продуктивності вихідних проєктів і
власної композиції рушіїв OmniRoute.

| Джерело | Показник із README вихідного проєкту, використаний тут                                                                                             |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | на `~75%` менше вихідних токенів, у середньому `65%` економії вихідних даних у тестах, діапазон `22-87%` і засіб стиснення вхідних даних на `~46%` |
| RTK     | `60-90%` економії для виводу команд; приклад сеансу: `~118,000 -> ~23,900` токенів, або `79.7%` економії (`~80%`)                                  |

Для перекривних корисних даних інструментів/контексту стандартна комбінація OmniRoute послідовно застосовує рушії:

```txt
RTK -> Caveman
```

Сукупна економія є мультиплікативною, а не адитивною:

```txt
сукупна  = 1 - (1 - економія RTK) * (1 - економія вхідних даних Caveman)
середня  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
діапазон = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Показник `78-95%` застосовується, коли і RTK, і Caveman можуть скоротити ті самі вхідні/контекстні корисні дані.
Режим вихідних даних відповіді Caveman є окремим: коли його ввімкнено, використовуйте власні показники економії вихідних даних Caveman (у середньому `65%`,
основний заявлений показник `~75%`, діапазон `22-87%`). Загальна економія на оплаті залежить від співвідношення запитів і вихідних даних.

### Що насправді означає "придатний"

Заявлений діапазон 15-95% є реальним, але він застосовується лише до **надлишкового або багатослівного** вмісту — повторюваних
рядків помилок, журналу збірки, що засмічується тим самим попередженням, завеликого виводу `grep`/читання файлу. Це
**не** означає, що кожен запит забезпечує таку економію.

Перевірено емпірично (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): запуск
`stacked` (RTK + Caveman) для блока `tool_result` у форматі Anthropic, що містить 300 однакових
рядків помилок, забезпечив **95.93% економії токенів / 96.26% економії символів** — точно в межах заявленого
діапазону. Але запуск того самого конвеєра для звичайного, ненадлишкового виводу інструментів (чистого списку збігів `grep`,
короткого читання файлу, звичайного тексту розмови) цілком правильно забезпечує **майже нульову економію**, оскільки
немає нічого повторюваного, що можна було б видалити, а `validateCompression()` (`validation.ts`) не дозволяє надсилати
переписаний вміст, який вилучає або змінює блоки коду, URL-адреси, заголовки, версії чи ідентифікатори констант, записані ВЕЛИКИМИ ЛІТЕРАМИ.

Це очікувана й безпечна поведінка, а не помилка: сеанс програмування, у якому переважно читаються чисті файли або виконується `grep`,
матиме помірну загальну економію навіть із повністю ввімкненим стисненням, тоді як сеанс, що стикається з циклом помилок
або багатослівним лінтером, забезпечить повний діапазон 78-95% для такого трафіку. Не вважайте низький
сукупний відсоток економії окремого сеансу доказом неправильного налаштування стиснення — спочатку перевірте, чи
був базовий вивід інструментів справді надлишковим.

## Візуалізація економії токенів

```
Без стиснення:       47K токенів надіслано до LLM
З Lite:              40K токенів надіслано          (15% економії — безпечний, завжди ввімкнений)
З Standard:          33K токенів надіслано          (30% економії — правила caveman-speak)
З Aggressive:        24K токенів надіслано          (50% економії — старіння + узагальнення)
З Ultra:             12K токенів надіслано          (75% економії — евристичне відсікання)
З RTK:               19K-5K токенів надіслано       (60-90% економії на виводі команд/інструментів)
З Stacked:           10K-2.5K токенів надіслано     (78-95% для придатного діапазону RTK+Caveman)
```

## Конфігурація

### Панель керування

Перейдіть до `Dashboard → Context & Cache`:

- **Caveman** — вибір режиму, мовні пакети, попередній перегляд і глобальні налаштування за замовчуванням
- **RTK** — попередній перегляд фільтрації команд, налаштування безпеки RTK і каталог фільтрів
- **Compression Combos** — іменовані конвеєри рушіїв, призначені комбінаціям маршрутизації
- **Auto-Trigger Threshold** — автоматичне ввімкнення стиснення, коли кількість токенів перевищує порогове значення

### Перевизначення для окремої комбінації

У `Dashboard → Context & Cache → Compression Combos` призначте комбінацію стиснення комбінації
маршрутизації:

```txt
Комбінація: "free-tier-fallback"
  Комбінація стиснення: "coding-agent-stack"
  Конвеєр: RTK -> Caveman
  Цілі:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Це дає змогу використовувати багаторівневе стиснення для безплатних постачальників або постачальників
для програмування, зберігаючи полегшений режим для платних підписок.

Це призначення «Перевизначення для окремої комбінації» є іншим елементом керування, ніж перевизначення
**режиму стиснення комбінації маршрутизації** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses —
схема цього поля також приймає `rtk`, `stacked` і `omniglyph`) — це перевизначення не вибирає іменований
конвеєр комбінації стиснення; воно лише задає поле `compressionMode`, яке використовує
`resolveCompressionPlan`. Його можна встановити на картці комбінації (`Dashboard → Combos`) або, починаючи
з #6760, для кожної комбінації маршрутизації в списку «Assign to routing» у
`Dashboard → Context & Cache → Compression Combos`, безпосередньо поруч із прапорцем призначення конвеєра,
описаним вище. Обидва інтерфейси зберігають зміни через той самий кінцевий пункт `PUT /api/combos/{id}`.

### Перевизначення для окремого запиту

Надішліть заголовок запиту `x-omniroute-compression`, щоб перевизначити план стиснення для окремого
запиту. Він має найвищий пріоритет — він переважає перевизначення комбінації маршрутизації, активний
профіль, автоматичне спрацьовування та значення Default на панелі. Невідомі значення ігноруються
(запит ніколи не відхиляється), а глобальний головний перемикач усе одно керує всім: якщо стиснення
глобально вимкнено, заголовок не може його ввімкнути. Значення:

| Значення      | Ефект                                                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `off`         | Не застосовувати стиснення до цього запиту.                                                                             |
| `default`     | Профіль Default, визначений панеллю (активний профіль ігнорується). Рушії з втратами вимкнено.                          |
| `safe`        | Те саме, що й відсутність заголовка: лише дедуплікація та згортання пробілів.                                           |
| `allow-lossy` | Зберегти операторський план цього запиту, включно з підсумками, фільтрами релевантності та переписуванням стилю.        |
| `engine:<id>` | Один рушій, якщо його ввімкнено, наприклад `engine:rtk`. Це явна згода на використання цього рушія для окремого запиту. |
| `<combo>`     | Іменована комбінація: спочатку зіставляється за назвою без урахування регістру, а потім за ідентифікатором.             |

Без `allow-lossy`, `engine:<id>` або іменованої комбінації рушії з втратами не застосовуються.
Коли стиснення ввімкнено, до запиту все одно застосовуються дедуплікація сеансу та згортання пробілів.

Застосований план повертається в заголовку відповіді `X-OmniRoute-Compression: <mode>; source=<source>`,
де `<source>` має одне зі значень: `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` або `off`.

## Подяки

Правила стиснення стандартного режиму натхненні проєктом **[Caveman](https://github.com/JuliusBrussee/caveman)** від **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) — вірусним проєктом «навіщо використовувати багато токенів, коли достатньо кількох». Caveman повідомляє про `~75%` менше токенів виводу, `65%` середньої економії виводу за результатами тестів, діапазон економії виводу `22-87%` та інструмент стиснення вводу на `~46%`.

Режим RTK натхненний **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** від **[RTK AI](https://github.com/rtk-ai)** — високопродуктивним проєктом стиснення виводу команд для фільтрації виводу термінала, збирання, тестів, git та інструментів. RTK повідомляє про економію `60-90%`, а приклад сеансу в його README демонструє економію `~80%`.

## Розширені системи стиснення

Окрім 7 режимів, описаних вище (джерело також підтримує режими `codex-responses` і
`omniglyph`, які не розглядаються в цьому посібнику), наведені нижче розділи описують функції,
що працюють усередині цих режимів або разом із ними: стиснення результатів інструментів і прогресивне старіння
є кроками 1 і 2 агресивного рушія (режим Aggressive та крок `aggressive`
складеного конвеєра), складений конвеєр визначає роботу режиму Stacked, стиснення з урахуванням кешу
знижує рівень `aggressive` і `ultra` до `standard` для постачальників із кешуванням, коли стиснення
ввімкнено, а режим печерного виведення та стилі виведення — це необов’язкові інструкції системного промпту,
вимкнені за замовчуванням, які формують виведення моделі замість стиснення запиту.

### Стиснення з урахуванням кешу

Деякі постачальники (наприклад, Anthropic із кешуванням промптів) підтримують **кешування промптів**,
що дає їм змогу кешувати частини промпту для зменшення витрат і затримки. Коли
кешування ввімкнено, агресивне стиснення фактично може **погіршити** продуктивність,
оскільки воно змінює кешовані токени, роблячи кеш недійсним.

Модуль `cachingAware.ts` вирішує цю проблему шляхом **виявлення контексту кешування** та
відповідного **коригування стратегії стиснення**.

#### Як це працює

1. **Виявлення контексту кешування** — сканує тіло запиту на наявність маркерів `cache_control`
2. **Визначення постачальників із кешуванням** — перевіряє, чи підтримує цільовий постачальник кешування
3. **Коригування стратегії** — знижує рівень `aggressive`/`ultra` до `standard` для постачальників із кешуванням
4. **Пропуск системного промпту** — системні промпти зазвичай кешуються, тому не стискає їх

Допоміжна функція стратегії також повертає прапорець `deterministicOnly`, але побудовник плану використовує
лише стратегію — наразі ніщо на наступних етапах не зчитує цей прапорець.

#### Приклад коду

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Маркер кешу
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Коли використовувати

Стиснення з урахуванням кешу **завжди ввімкнене** — налаштування не потрібне. Воно активується щоразу,
коли стиснення ввімкнено й цільовий постачальник підтримує кешування промптів (Anthropic, OpenAI
тощо); явні маркери `cache_control` не потрібні — самого постачальника з кешуванням
достатньо для зниження рівня, тоді як самі маркери ніколи цього не спричиняють (виявлення маркерів передає дані
телеметрії кешу, а не впливає на рішення щодо стратегії).

### Прогресивне старіння

Довгі розмови накопичують багато ходів повідомлень, але старіші ходи стають менш
релевантними. Модуль `progressiveAging.ts` **спрощує повідомлення залежно від відстані між ходами**
(відстань вимірюється від кінця розмови). Зі стандартними налаштуваннями постачання
(`verbatim: 2, light: 2, moderate: 3`):

- **Останні 2 ходи (відстань ≤ 2)**: зберігаються дослівно
- **Відстань 3**: печерне стиснення (видалення слів-наповнювачів)
- **Відстань 4+**: повідомлення асистента підсумовуються; повідомлення користувача скорочуються до першого
  рядка з обмеженням у 120 символів; інші ролі залишаються без змін. Системні промпти, уже зістарені
  повідомлення й останнє повідомлення користувача завжди зберігаються дослівно незалежно від відстані.
  Ніщо не видаляється повністю, а діапазон `light`
  недосяжний зі стандартними налаштуваннями постачання (`light` дорівнює `verbatim`).

#### Приклад коду

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ще 50 ходів ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // останні 3 ходи: дослівно
  light: 8, // відстань <= 8: легке стиснення
  moderate: 20, // відстань <= 20: печерне стиснення
  fullSummary: 5, // вимагається типом, але не зчитується кодом розподілу за діапазонами
  // відстань > 20: підсумовується (асистент) / зберігається перший рядок (користувач)
});

// saved = кількість заощаджених токенів
```

#### Коли використовувати

Прогресивне старіння **завжди ввімкнене** для режиму `aggressive` — це крок 2
`compressAggressive()`. Режим Ultra його не запускає. Воно
особливо ефективне для:

- Тривалих сеансів програмування
- Розмов, що тривають кілька днів
- Агентних робочих процесів із великою кількістю викликів інструментів

### Режим печерного виведення

Режим печерного виведення додає **інструкції системного промпту**, які просять саму модель
надавати стислий результат — рівень `lite` просить давати лаконічні відповіді зі збереженням повних речень, `full`
просить її «відповідати стисло, як розумна печерна людина», а `ultra` — використовувати телеграфний стиль;
інструкції лише висловлюють прохання й не можуть гарантувати його виконання. Запити отримують їх через
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`):
`open-sse/handlers/chatCore.ts` спочатку визначає вибір за допомогою шару зворотної сумісності
(`resolveOutputStyleSelection()` у
`open-sse/services/compression/outputStyles/backCompat.ts`), який, коли `outputStyles`
порожній, зіставляє ввімкнений `cavemanOutputMode` зі стилем виведення `terse-prose` на рівні
`cavemanOutputMode.intensity` (див. розділ про зворотну сумісність нижче); непорожній вибір `outputStyles`
використовується без змін, після чого `cavemanOutputMode.enabled` та `intensity` не мають
жодного впливу, тоді як перемикач `autoClarity` усе ще застосовується. `outputMode.ts` містить
тексти інструкцій (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), обхід обробки вмісту та
допоміжну функцію розміщення, яку використовує впровадження; його власний механізм упровадження `applyCavemanOutputMode()` не має
викликів у робочому середовищі.

#### Як це працює

Цей режим не стискає вхідні дані. Він додає блок інструкцій до системного запиту
(див. «Як працює ін’єкція» нижче), а будь-який режим стискання вхідних даних, вибраний для запиту,
усе одно запускається після цього для тіла, яке тепер містить цей блок. Перед спільним
пунктом про обмеження, яким завершується кожен рівень, англійський рівень `full` має такий вигляд:

> "Відповідай стисло, як розумний печерний чоловік. Прибирай артиклі (a/an/the), слова-паразити (just/really/basically/actually/simply), люб’язності, пом’якшення. Фрагменти допустимі. Короткі синоніми (big, а не extensive; fix, а не implement). Зберігай увесь технічний зміст, код, помилки, URL-адреси й ідентифікатори без змін."

Це особливо добре працює для:

- Генерування коду (лаконічніший результат = менше токенів)
- Швидких запитань і відповідей (немає потреби в розлогих поясненнях)
- Пакетної обробки (максимальна пропускна здатність)

#### Коли використовувати

Режим печерного виводу є **добровільним**. Коли стискання ввімкнено (`enabled: true`, головний перемикач
на сторінці налаштувань стискання), увімкніть його за допомогою `cavemanOutputMode.enabled`; `intensity`
вибирає `lite`, `full` або `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Перемикач **Режим виводу** комбінації стискання (`outputMode`, рівень у `outputModeIntensity`)
встановлює той самий параметр для запитів, до яких застосовується ця комбінація, а
MCP-інструмент `omniroute_set_compression_engine` записує його через свій логічний аргумент `outputMode`.
Непорожній вибір `outputStyles` має пріоритет над цим перемикачем. На панелі керування ввімкнення
стилю виводу **Лаконічна проза** додає той самий блок (див. «Стилі виводу»
нижче).

Кожен стиль постачається з трьома рівнями інтенсивності — `lite`, `full`, `ultra` — і кожен рівень
завершується спільним пунктом про обмеження (`SHARED_BOUNDARIES` у `outputMode.ts`), який
зберігає блоки коду, шляхи до файлів, команди, помилки й URL-адреси без змін. Тексти рівнів `terse-prose` та
`terse-cjk` також додають до цього списку ідентифікатори.

`terse-cjk` обмежено локаллю `zh` у двох місцях. Сторінка налаштувань стискання показує
його рядок лише тоді, коли мовою інтерфейсу панелі керування є китайська (`zh-CN` або `zh-TW`), а
`applyOutputStyles()` додає його лише тоді, коли визначена мова запиту (див. «Вибір мови»
нижче) — `zh`. Приховування рядка не очищає збережений вибір `terse-cjk`:
API налаштувань приймає будь-який ідентифікатор стилю, а збереження інших стилів на сторінці зберігає його. Під час
запиту перевірка мови в `applyOutputStyles()` є єдиним обмеженням за локаллю.

#### Як працює ін’єкція

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) зіставляє
вибір із каталогом (невідомі ідентифікатори та стилі, що не відповідають локалі,
відкидаються й ніколи не спричиняють помилки; якщо після зіставлення не залишається
жодного стилю, тіло залишається без змін, а обробка пропускається як `no_styles`),
об’єднує вибрані інструкції в порядку каталогу,
додає умову щодо меж **один раз** (разом з умовою безпеки, `SAFETY_BOUNDARIES` або її
перекладом, коли вибрано `less-code` чи `ponytail`) і починає блок з одного маркера
ідемпотентності (`[OmniRoute Output Styles]`), тому повторне застосування нічого не
змінює. Коли для визначеної мови (див. розділ «Вибір мови» нижче) є переклад, замість
англійської інструкції додається локалізована.

Для тіла з непорожнім масивом `messages` перевірка ідемпотентності виконується до
обходу за вмістом: коли маркер `[OmniRoute Output Styles]` уже присутній у полі
`system` верхнього рівня (рядку або масиві блоків вмісту) чи в системному повідомленні
з рядковим вмістом, тіло залишається без змін зі статусом `already_applied`, а перевірка
ключових слів не виконується. Інакше обхід за вмістом
(`shouldBypassCavemanOutputMode()` у
`open-sse/services/compression/outputMode.ts`) перевіряє текст останніх трьох
повідомлень незалежно від їхньої ролі й пропускає стилі для всього поточного запиту,
коли цей текст відповідає ключовим словам, пов’язаним із безпекою, незворотними діями
чи уточненням, або залежній від порядку послідовності: `first`, `then`, `after that`,
`before`, `rollback` чи `backup`, після якого в межах 240 символів іде `delete`, `drop`,
`migrate`, `deploy` чи `release`. Обхід працює, доки перемикач **Auto-Clarity Bypass**
(`cavemanOutputMode.autoClarity`, увімкнений за замовчуванням) увімкнено; вимкнення
перемикача пропускає перевірку ключових слів.

Коли обхід дозволяє обробити поточний запит, `placeSystemInstruction()` (у тому самому
файлі), який ніколи не створює новий `messages[0]`, розміщує блок у першому знайденому
місці з наведених нижче:

1. Початкове системне повідомлення з рядковим вмістом: блок додається після його тексту.
2. Поле `system` верхнього рівня: блок додається після тексту рядка або як новий
   текстовий блок до масиву блоків вмісту.
3. Перше наступне системне повідомлення з рядковим вмістом: блок додається після його
   тексту.
4. Нічого з наведеного вище: блок додається до нового системного повідомлення наприкінці `messages`.

Для тіла без масиву `messages` (або з порожнім масивом) обхід за вмістом не виконується,
а поле `system` верхнього рівня не перевіряється. Блок додається після тексту рядкового
поля `instructions`, якщо це поле ще не містить маркер
`[OmniRoute Output Styles]`; якщо містить, тіло залишається без змін зі статусом
`already_applied`. Якщо тіло не має рядкового поля `instructions`, але містить `input`
(рядок або масив), блок стає значенням `instructions`, замінюючи будь-яке нерядкове
значення, яке мало це поле. Тіло, що не має ані рядкового поля `instructions`, ані
рядкового чи масивного `input`, залишається без змін, а обробка пропускається як
`no_messages`.

#### Як увімкнути

На панелі керування: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), розділ Output styles: один рядок на стиль із
перемикачем увімкнення/вимкнення та вибором рівня. Стилі додаються, доки ввімкнено саме
стиснення (головний перемикач сторінки, `enabled`). Перемикач **Auto-Clarity Bypass**
розташований на сторінці **Caveman** (`/dashboard/context/caveman`), у картці
**Output Mode**. Програмно конфігурація стиснення зберігає вибір так:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Зворотна сумісність: доки `outputStyles` порожній, застаріле налаштування
`cavemanOutputMode.enabled` зіставляється з `terse-prose` на рівні
`cavemanOutputMode.intensity`. У такому разі блок починається з маркера
`[OmniRoute Output Styles]`, тоді як застарілий інжектор `applyCavemanOutputMode()`
додавав `[OmniRoute Caveman Output Mode]`. Нижче маркера текст відповідає застарілій
вставці для en, pt-BR, es, de, fr, it, ru, id і vi; для ja та zh перед умовою щодо меж
є один додатковий пробіл. `terse-prose` має переклади для pt-BR, es, de, fr, it, ru,
zh, ja, id і vi, тому запит із визначеною мовою `hu` отримує англійський текст там, де
застарілий інжектор використовував угорський.

Вибір мови стилю виведення (`resolveOutputStyleLanguage()` у
`outputStyles/apply.ts`): коли `languageConfig.enabled` увімкнено, `autoDetect` бере
зразок з останнього повідомлення користувача в масиві `messages` запиту, яке містить
текст (рядковий вміст або `text` його частин вмісту), і запускає для нього детектор
рушія Caveman (`detectCompressionLanguage()`). Детектор повертає `zh` для тексту з
ієрогліфами Хань без кани; інакше він повертає ту з мов `it`, `pt-BR`, `es`, `de`,
`fr`, `ru`, `ja`, `hu` та `id`, яка має найбільше збігів із підказками, і `en`, коли
збігів немає — текст, який він не може класифікувати, отримує англійську, а не
`defaultLanguage`, і `vi` ніколи не визначається, хоча стилі містять текст `vi`. Тіло
Responses API зберігає свої репліки в `input`, із якого зразок не береться, тому воно
отримує `defaultLanguage`, а потім англійську. Коли жодне повідомлення користувача в
`messages` не містить тексту або коли `autoDetect` вимкнено, застосовується
`defaultLanguage`, а потім англійська. Коли `languageConfig.enabled` вимкнено, мовою є
англійська — крім випадку, коли до запиту застосовується комбінація стиснення
(комбінація, призначена комбінації маршрутизації запиту, або типова комбінація
стиснення, яку chatCore використовує як резервну для вбудованого багатошарового
конвеєра): застосування комбінації вмикає `languageConfig.enabled` для цього запиту та
задає `defaultLanguage` із мовних пакетів комбінації (збережене значення, якщо воно
належить до пакетів комбінації, інакше перший пакет комбінації, типовим значенням якого
є `en`), тоді як збережене значення `autoDetect` (увімкнене за замовчуванням) і далі
застосовується. Рушій введення Caveman вибирає мову пакета правил інакше — окремо для
кожної текстової частини, а коли автоматичне визначення вимкнено, ще й з урахуванням
`enabledPacks`.

Матриця стилів × мов закріплена тестом
`tests/unit/compression/output-styles-i18n-matrix.test.ts`: кожен стиль каталогу повинен
мати запис у `BASELINE_LANGUAGES` тесту; стиль, не обмежений локаллю, повинен постачатися
з перекладом pt-BR (стиль `terse-cjk`, обмежений локаллю, звільнений від цієї вимоги), якщо
його немає в `KNOWN_ENGLISH_ONLY`, де можуть бути лише стилі без жодних перекладів —
наявність будь-якого перекладу для стилю з цього списку спричиняє помилку тесту; також
тест для стилю завершується помилкою, якщо стиль втрачає мову, зазначену в його записі
`BASELINE_LANGUAGES`. Щоб додати стиль, див.
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### Стиснення результатів інструментів

`compressToolResult()` у `open-sse/services/compression/toolResultCompressor.ts`
стискає текст результату інструмента за допомогою **5 стратегій**. Вони перевіряються
в такому порядку, а результат визначає перша ввімкнена стратегія, перевірка якої
відповідає вмісту:

1. **`fileContent`**: для вмісту з 3 або більше рядків, у якому принаймні один рядок,
   якщо не враховувати початкові відступи, починається з `import `, `export `,
   `function `, `class `, `const `, `let `, `var ` або `return ` (ключове слово
   та пробіл), чи з `if`, `for` або `while`, після якого йде `(` чи ` (`, зберігає
   перші 20 та останні 5 рядків, позначаючи пропущену середину.
2. **`grepSearch`**: для вмісту з принаймні одним рядком вигляду `<path>:<digits>:`,
   де текст перед першою двокрапкою не містить пробілів, зберігає лише такі рядки,
   щонайбільше 30, після чого додає кількість подальших збігів і список файлів зі
   збігами; усі інші рядки відкидаються. Для спрацювання стратегії достатньо одного
   такого рядка, тому рядок журналу, що починається з часової позначки на кшталт
   `12:30:45`, також зараховується.
3. **`shellOutput`**: із виводу, що містить послідовність ANSI CSI (`ESC[`, потім цифри
   або крапки з комою, а далі літера, як у кодах кольорів) чи символ `$`, після якого
   будь-де в тексті йде пробільний символ, видаляє ці послідовності (інші керівні
   послідовності, як-от `ESC[?25l` або OSC-послідовність заголовка вікна,
   зберігаються) і залишає останні 50 рядків, згортаючи послідовні повторювані рядки.
   Оскільки ця перевірка виконується перед `json` і `errorMessage`, JSON або вивід
   помилки, що містить такий `$`, ніколи до них не доходить, доки ввімкнено
   `shellOutput`.
4. **`json`**: коректний JSON-вміст завдовжки понад 2 000 символів, який починається
   з `{` або `[` (після необов’язкових пробільних символів), стисло підсумовується:
   для масиву з понад 7 елементів зберігаються перші 5 та останні 2 елементи, а також
   їхня загальна кількість; для об’єкта зберігаються перші 20 ключів, причому кожне
   значення у вигляді вкладеного об’єкта або масиву замінюється заповнювачем
   `{…N keys}` (для масиву N — це його довжина), а маркер `_remaining_<N>_keys`
   підраховує ключі, відкинуті після перших 20. Скалярні значення копіюються повністю,
   тому об’єкт із 20 або меншою кількістю ключів без вкладених значень лише отримує
   нові відступи — мінімізований об’єкт збільшується в символах і залишається без змін.
5. **`errorMessage`**: для виводу, що будь-де та незалежно від регістру літер містить
   `error:`, `error ` (слово, після якого йде пробіл, як у `no error found`),
   `[error]`, `exception:`, `exception `, `[exception]` або `traceback`, зберігає
   перший рядок, наступні 10 рядків та останні 3, замінюючи рядки між ними маркером
   `… [N frames elided] …`. Маркер з’являється лише тоді, коли після першого рядка є
   понад 13 рядків, тому вивід помилки з 14 або меншою кількістю рядків не скорочується
   (за наявності 12 або 13 рядків останні 3 повторюють уже збережені рядки).

Після збігу зі стратегією, навіть якщо вона нічого не заощаджує, наступні стратегії
не перевіряються. Коли відповідна стратегія не заощаджує жодного оціненого токена
(довжина ÷ 4 з округленням угору) — наприклад, для схожого на код файлу з 25 або
меншою кількістю рядків чи масиву JSON завдовжки понад 2 000 символів із 7 або меншою
кількістю елементів — агресивний рушій зберігає початковий результат інструмента:
обидва виклики (`compressAggressive()` і `compressAnthropicToolResultBlock()`)
зберігають оригінал, коли `saved` дорівнює 0 або менше, тоді як сама функція
`compressToolResult()` усе одно повертає вивід цієї стратегії. Етап обробки результату
інструмента не є остаточним: резервний підсумовувач рушія все одно може скоротити
повідомлення `tool` або `function` завдовжки понад 8 192 символи
(`maxTokensPerMessage`, 2 048, помножене на 4).

#### Коли використовувати

Стиснення результатів інструментів — це крок 1 агресивного рушія
(`compressAggressive()` у `open-sse/services/compression/aggressive.ts`), тому воно
виконується в режимі Aggressive та на кроці `aggressive` складеного конвеєра. Воно
стискає повідомлення `tool` і `function` у форматі OpenAI, а також текст усередині
блоків Anthropic `tool_result`. Кожна стратегія має власний перемикач у
`aggressive.toolStrategies`; за замовчуванням усі вони ввімкнені. На інформаційній
панелі ці перемикачі розташовані в поданні **Advanced** сторінки Caveman, коли
стиснення ввімкнено, а режимом за замовчуванням є Aggressive.

### Складений конвеєр

Складений режим запускає **кілька рушіїв послідовно** — зазвичай спочатку RTK
(економія 60–90% для виводу інструментів), а потім Caveman для решти тексту
(економія ~46% вхідних даних). У поєднанні це дає **діапазон економії 78–95% для
придатного вмісту** (див. розділ «Математика економії Upstream» вище):
`1 - (1 - 0.60..0.90) × (1 - 0.46)` у середньому становить ≈89%.

#### Як це працює

```
Вхідні дані (1000 токенів)
  → RTK (фільтр з урахуванням команд) → 200 токенів
    → Caveman (видалення надлишкового тексту) → 108 токенів
  → Вихідні дані (108 токенів, економія ~89%)
```

#### Коли використовувати

Використовуйте складений режим для:

- Робочих процесів з інтенсивним використанням інструментів (агентне програмування, дослідження)
- Пакетної обробки, чутливої до витрат
- Випадків, коли потрібна максимальна економія токенів

Складені конвеєри налаштовуються через глобальний параметр стиснення
`stackedPipeline` або через іменовану комбінацію стиснення, призначену комбінації
маршрутизації (див. розділ «Перевизначення для окремої комбінації» вище), — а не
через `modePack` автоматичної комбінації (це поле лише змінює ваги вибору моделі
автоматичною комбінацією, а `stacked` не є допустимою назвою пакета).

---

## Перевизначення стиснення для комбінацій

Ви можете перевизначити глобальний режим стиснення **для кожної окремої комбінації**, щоб точніше налаштувати поведінку
для різних сценаріїв використання:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Це корисно для:

- **Комбінацій для програмування**: використовуйте режим `aggressive` для тривалих сеансів
- **Комбінацій для швидких запитань і відповідей**: використовуйте режим `lite` для швидких відповідей
- **Комбінацій з інтенсивним використанням інструментів**: використовуйте режим `stacked` для максимальної економії
- **Робочих комбінацій**: не вмикайте перевизначення для провайдерів із кешуванням — постійно активне
  коригування з урахуванням кешу автоматично знижує `aggressive`/`ultra` до `standard`
  (режим `cache-aware` не можна вибрати)
