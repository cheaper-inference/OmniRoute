> Автоматично заощаджуйте 15–95% токенів у придатному для стиснення контексті. Короткий огляд наведено в [розділі README про стиснення](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## Огляд

OmniRoute реалізує модульний конвеєр стиснення промптів, який запускається **проактивно**, перш ніж запити надходять до зовнішніх провайдерів. Це означає, що токени заощаджуються прозоро — жодних змін у вашому робочому процесі не потрібно.

```
Запит клієнта
  → Засіб вибору стратегії стиснення
    → Є перевизначення комбінацією? → Використати налаштування комбінації
    → Досягнуто порога автоматичного запуску? → Використати автоматичний режим
    → Режим за замовчуванням? → Використати глобальне налаштування
    → Вимкнено? → Пропустити стиснення
  → Вибраний режим стиснення
    → Вимкнено: без стиснення
    → Легкий: безпечне очищення пробілів і форматування (~15%)
    → Стандартний: видалення зайвих слів у телеграфному стилі (~30%)
    → Агресивний: ущільнення історії + узагальнення (~50%)
    → Ультра: евристичне скорочення + проріджування блоків коду (~75%)
    → RTK: фільтрування виводу термінала/інструментів з урахуванням команд (діапазон 60–90% для висхідних запитів)
    → Стековий: упорядкований багатоетапний конвеєр, зазвичай RTK, а потім Caveman (діапазон 78–95% для придатного вмісту)
  → Стиснений запит → Провайдер
```

## Режими стиснення

### Вимкнено

Стиснення не застосовується. Усі повідомлення проходять без змін.

### Полегшений режим (~15% економії, затримка <1 мс)

Найбезпечніший режим — очищення форматування. Усікання результатів інструментів призводить до втрати даних, тому стандартний
шлях (без `allow-lossy`, `engine:lite` або явного ввімкнення іменованої комбінації) запускає полегшений режим із
`compressToolResults: false`: попередні результати інструментів надходять до провайдера без змін.

| Техніка                  | Опис                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | Об’єднання послідовних порожніх рядків і кінцевих пробілів                                                          |
| `dedupSystemPrompt`      | Видалення дублікатів системних повідомлень                                                                          |
| `compressToolResults`    | Усікання попередніх результатів інструментів до ліміту полегшеного режиму (із втратою даних: лише за явного запиту) |
| `removeRedundantContent` | Видалення повторюваних інструкцій                                                                                   |
| `replaceImageUrls`       | Скорочення URI даних зображень у форматі base64                                                                     |

**Найкраще підходить для:** Постійного використання, критичних до безпеки робочих процесів.

### Стандартний режим (~30% економії)

Натхненний [Caveman](https://github.com/JuliusBrussee/caveman) — видаляє слова-паразити й багатослівні формулювання, зберігаючи зміст:

- Видаляє слова-паразити ("будь ласка", "я думаю", "по суті", "насправді")
- Скорочує багатослівні фрази ("для того, щоб" → "щоб", "у результаті" → "через")
- Усуває ввічливі пом’якшувальні формулювання ("Чи не могли б ви...", "Якщо ви могли б, будь ласка...")
- Понад 30 регулярних виразів, налаштованих для запитів із програмування

**Найкраще підходить для:** Щоденних робочих процесів програмування, команд, що прагнуть зменшити витрати.

### Агресивний режим (~50% економії)

Інтелектуальне керування історією для тривалих сеансів:

- **Старіння повідомлень** — старіші повідомлення поступово стискаються
- **Стиснення результатів інструментів** — довгі результати інструментів усікаються або приховуються (перші/останні рядки,
  фільтрація рядків із відповідностями, ущільнення ключів JSON)
- **Засоби захисту структурної цілісності** — забезпечують узгодженість пар `tool_use` + `tool_result`
- **Обізнаність про контекстне вікно** — враховує обмеження токенів для кожної моделі

**Найкраще підходить для:** Тривалих сеансів налагодження, великих кодових баз.

### Ультрарежим (~75% економії)

Максимальне стиснення для сценаріїв із критичним обмеженням токенів:

- **Евристичне скорочення** — скорочення прозового тексту на основі оцінювання токенів
- **Збереження структури** — блоки коду з огорожею, вбудований код, URL-адреси та ідентифікатори
  тимчасово вилучаються й повторно вставляються без змін, ніколи не скорочуються
- **Необов’язковий рівень SLM** — невелика локальна модель може уточнювати скорочення, якщо її налаштовано
- Незалежний від агресивного режиму: не виконує старіння повідомлень, стиснення результатів інструментів
  або резервний підсумовувач (лише збій рівня SLM може спрямувати резервний прохід через агресивний режим)

**Найкраще підходить для:** Випадків, коли ви неодноразово досягаєте обмежень контексту.

### Режим RTK (60–90% для висхідного потоку)

Режим RTK оптимізовано для багатослівних результатів інструментів, що з’являються в сеансах агентів програмування:

- Виявляє класи команд/результатів, як-от `git status`, `git diff`, `git log`, засоби запуску тестів,
  збірки TypeScript/Vite/Webpack, ESLint/Biome/Prettier, аудит/встановлення npm, журнали Docker, результати інфраструктури
  та загальні результати оболонки
- Застосовує пакети фільтрів JSON із `open-sse/services/compression/engines/rtk/filters/`
- Імпортує фільтри схеми RTK TOML v1 із файлів `filters.toml` проєкту або глобальних файлів із перевіркою
  вбудованих тестів і контролем довіри до файлів проєкту
- Постачається з 56 вбудованими фільтрами зі зразками для вбудованої перевірки
- Видаляє керівні послідовності ANSI, індикатори виконання, повторювані рядки та неактуальний шум
- Зберігає невдалі операції, помилки, попередження, змінені файли, підсумки та кінцеву частину довгих результатів
- Підтримує фільтри проєкту з контролем довіри, глобальні фільтри та необов’язкове відновлення необроблених результатів із редагуванням

**Найкраще підходить для:** Сеансів агентів з оболонкою, збірками, тестами, git, grep і транскриптами виводу файлів.

### Комбінований режим (діапазон для придатних даних 78–95%)

Комбінований режим запускає кілька механізмів стиснення в детермінованому порядку. Стандартний конвеєр:

```txt
RTK -> Caveman
```

Такий порядок спочатку робить вивід термінала/інструментів компактним, а потім застосовує семантичне ущільнення Caveman до
залишкового запиту природною мовою. Комбіновані конвеєри можна налаштувати глобально або через комбінації стиснення, призначені комбінаціям маршрутизації.

**Найкраще підходить для:** Змішаного контексту з великими журналами інструментів і людськими інструкціями або підсумками асистента.

## Розрахунок економії від вихідних проєктів

OmniRoute документує економію завдяки стисненню з двох джерел: тестів продуктивності вихідних проєктів і
власної композиції рушіїв OmniRoute.

| Джерело | Показник із README вихідного проєкту, використаний тут                                                                                             |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | на `~75%` менше вихідних токенів, у середньому `65%` економії вихідних даних у тестах, діапазон `22-87%` і засіб стиснення вхідних даних на `~46%` |
| RTK     | `60-90%` економії для виводу команд; приклад сеансу: `~118,000 -> ~23,900` токенів, або `79.7%` економії (`~80%`)                                  |

Для перекривних корисних даних інструментів/контексту стандартна комбінація OmniRoute послідовно застосовує рушії:

```txt
RTK -> Caveman
```

Сукупна економія є мультиплікативною, а не адитивною:

```txt
сукупна  = 1 - (1 - економія RTK) * (1 - економія вхідних даних Caveman)
середня  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
діапазон = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Показник `78-95%` застосовується, коли і RTK, і Caveman можуть скоротити ті самі вхідні/контекстні корисні дані.
Режим вихідних даних відповіді Caveman є окремим: коли його ввімкнено, використовуйте власні показники економії вихідних даних Caveman (у середньому `65%`,
основний заявлений показник `~75%`, діапазон `22-87%`). Загальна економія на оплаті залежить від співвідношення запитів і вихідних даних.

### Що насправді означає "придатний"

Заявлений діапазон 15-95% є реальним, але він застосовується лише до **надлишкового або багатослівного** вмісту — повторюваних
рядків помилок, журналу збірки, що засмічується тим самим попередженням, завеликого виводу `grep`/читання файлу. Це
**не** означає, що кожен запит забезпечує таку економію.

Перевірено емпірично (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): запуск
`stacked` (RTK + Caveman) для блока `tool_result` у форматі Anthropic, що містить 300 однакових
рядків помилок, забезпечив **95.93% економії токенів / 96.26% економії символів** — точно в межах заявленого
діапазону. Але запуск того самого конвеєра для звичайного, ненадлишкового виводу інструментів (чистого списку збігів `grep`,
короткого читання файлу, звичайного тексту розмови) цілком правильно забезпечує **майже нульову економію**, оскільки
немає нічого повторюваного, що можна було б видалити, а `validateCompression()` (`validation.ts`) не дозволяє надсилати
переписаний вміст, який вилучає або змінює блоки коду, URL-адреси, заголовки, версії чи ідентифікатори констант, записані ВЕЛИКИМИ ЛІТЕРАМИ.

Це очікувана й безпечна поведінка, а не помилка: сеанс програмування, у якому переважно читаються чисті файли або виконується `grep`,
матиме помірну загальну економію навіть із повністю ввімкненим стисненням, тоді як сеанс, що стикається з циклом помилок
або багатослівним лінтером, забезпечить повний діапазон 78-95% для такого трафіку. Не вважайте низький
сукупний відсоток економії окремого сеансу доказом неправильного налаштування стиснення — спочатку перевірте, чи
був базовий вивід інструментів справді надлишковим.

## Візуалізація економії токенів

```
Без стиснення:       47K токенів надіслано до LLM
З Lite:              40K токенів надіслано          (15% економії — безпечний, завжди ввімкнений)
З Standard:          33K токенів надіслано          (30% економії — правила caveman-speak)
З Aggressive:        24K токенів надіслано          (50% економії — старіння + узагальнення)
З Ultra:             12K токенів надіслано          (75% економії — евристичне відсікання)
З RTK:               19K-5K токенів надіслано       (60-90% економії на виводі команд/інструментів)
З Stacked:           10K-2.5K токенів надіслано     (78-95% для придатного діапазону RTK+Caveman)
```

## Конфігурація

### Панель керування

Перейдіть до `Dashboard → Context & Cache`:

- **Caveman** — вибір режиму, мовні пакети, попередній перегляд і глобальні значення за замовчуванням
- **RTK** — попередній перегляд фільтра команд, параметри безпеки RTK і каталог фільтрів
- **Compression Combos** — іменовані конвеєри рушіїв, призначені комбінаціям маршрутизації
- **Auto-Trigger Threshold** — автоматично вмикає стиснення, коли кількість токенів перевищує порогове значення

### Перевизначення для комбінації

У `Dashboard → Context & Cache → Compression Combos` призначте комбінацію стиснення комбінації
маршрутизації:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Це дає змогу використовувати каскадне стиснення для безкоштовних провайдерів і провайдерів
для написання коду, зберігаючи полегшений режим для платних підписок.

Це призначення «Перевизначення для комбінації» є окремим елементом керування від
**режиму стиснення комбінації маршрутизації** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses —
схема поля також приймає `rtk`, `stacked` і `omniglyph`) — це перевизначення не вибирає іменований
конвеєр комбінації стиснення; воно лише встановлює поле `compressionMode`, яке обробляє
`resolveCompressionPlan`. Його можна встановити на картці комбінації (`Dashboard → Combos`) або,
починаючи з #6760, для кожної комбінації маршрутизації у списку «Assign to routing» в розділі
`Dashboard → Context & Cache → Compression Combos`, поруч із прапорцем призначення конвеєра,
описаним вище. Обидва інтерфейси зберігають дані через одну й ту саму кінцеву точку
`PUT /api/combos/{id}`.

### Перевизначення для окремого запиту

Надішліть заголовок запиту `x-omniroute-compression`, щоб перевизначити план стиснення для одного
запиту. Він має найвищий пріоритет — він має перевагу над перевизначенням комбінації маршрутизації,
активним профілем, автоматичним запуском і значенням Default на панелі. Невідомі значення
ігноруються (запит ніколи не відхиляється), а глобальний головний перемикач і надалі керує всім:
коли стиснення глобально вимкнене, заголовок не може його ввімкнути. Значення:

| Значення      | Ефект                                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `off`         | Без стиснення для цього запиту.                                                                                  |
| `default`     | Профіль Default, визначений панеллю (ігнорує активний профіль). Рушії зі втратами вимкнені.                      |
| `safe`        | Те саме, що й без цього заголовка.                                                                               |
| `allow-lossy` | Зберігає операторський план цього запиту, включно з резюме, фільтрами релевантності та перезаписами стилю.       |
| `engine:<id>` | Один рушій, якщо його ввімкнено, наприклад `engine:rtk`. Це явний дозвіл на використання цього рушія для запиту. |
| `<combo>`     | Іменована комбінація, спочатку знайдена за назвою (без урахування регістру), а потім за ідентифікатором.         |

Без `allow-lossy`, `engine:<id>` або іменованої комбінації рушії зі втратами не застосовуються. Коли
Default, автоматичний запуск або перевизначення маршрутизації зі втратами знижуються до безпечнішого
рівня, OmniRoute зберігає розпізнані кроки без втрат із налаштованого каскадного конвеєра в
налаштованому порядку. До `session-dedup → lite` система переходить лише тоді, коли жоден
налаштований крок без втрат не залишається.

Попередній перегляд **Effective pipeline** на панелі Settings показує звичайний план у стані
зберігання. Коли може виконуватися автоматичний запуск, той самий попередній перегляд також показує
умовний ефективний конвеєр, щоб роздільна здатність панелі та середовища виконання без заголовка
залишалися узгодженими.

Застосований план повертається в заголовку відповіді
`X-OmniRoute-Compression: <mode>; source=<source>`, де `<source>` — одне зі значень:
`request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` або `off`.

## Подяки

Правила стиснення стандартного режиму натхненні проєктом **[Caveman](https://github.com/JuliusBrussee/caveman)** від **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) — вірусним проєктом «навіщо використовувати багато токенів, коли достатньо кількох». Caveman повідомляє про `~75%` менше токенів виводу, `65%` середньої економії виводу за результатами тестів, діапазон економії виводу `22-87%` та інструмент стиснення вводу на `~46%`.

Режим RTK натхненний **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** від **[RTK AI](https://github.com/rtk-ai)** — високопродуктивним проєктом стиснення виводу команд для фільтрації виводу термінала, збирання, тестів, git та інструментів. RTK повідомляє про економію `60-90%`, а приклад сеансу в його README демонструє економію `~80%`.

## Розширені системи стиснення

Окрім 7 режимів, описаних вище (джерело також підтримує режими `codex-responses` та `omniglyph`, які не розглядаються в цьому посібнику), розділи нижче охоплюють функції, які працюють у цих режимах або поруч із ними: Стиснення результатів інструменту та прогресивне старіння є кроками 1 та 2 агресивного механізму (агресивний режим та крок `aggressive` стекового конвеєра), Stacked Pipeline — це те, як працює стековий режим, Cache-Aware Стиснення знижує `aggressive` і `ultra` до `standard` для постачальників кешування, коли стиснення ввімкнено, а Режим виведення Caveman і Стилі виведення є системними інструкціями, вимкненими за замовчуванням, які формують вихідні дані моделі замість стиснення запиту.

### Стиснення з урахуванням кешу

Деякі провайдери (наприклад, Anthropic з оперативним кешуванням) підтримують** оперативне кешування** , що дозволяє кешувати частини підказки, щоб зменшити витрати та затримку. Коли кешування ввімкнено, агресивне стиснення дійсно може** боляче** продуктивність, оскільки він змінює кешовані маркери, роблячи кеш недійсним.

Модуль `cachingAware.ts` вирішує це за допомогою** виявлення контексту кешування** і** налаштування стратегії стиснення** відповідно.

#### Як це працює

1. **Виявлення контексту кешування** — Сканує тіло запиту на наявність маркерів `cache_control`
2. **Визначте постачальників кешування** — Перевіряє, чи цільовий постачальник підтримує кешування
3. **Налаштуйте стратегію** — Зменшує `aggressive`/`ultra` до `standard` для постачальників кешування
4. **Пропустити системну підказку** — Системні підказки зазвичай кешуються, тому не стискайте їх

Помічник стратегії також повертає прапор `deterministicOnly`, але розробник плану використовує лише стратегію — сьогодні цей прапорець не зчитується.

#### Приклад коду

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Коли використовувати

Стиснення з урахуванням кешу є** завжди ввімкнено** — конфігурація не потрібна. Він запускається щоразу, коли стиснення ввімкнено, а цільовий постачальник підтримує швидке кешування (Anthropic, OpenAI тощо); явні маркери `cache_control` не потрібні. — лише постачальник кешування ініціює пониження версії, а самі маркери ніколи цього не роблять (виявлення маркерів передає телеметрію кешу, а не стратегічне рішення).

OpenRouter вважається постачальником кешування лише для моделей `anthropic/*` : запити коду Claude зберігають свої точки зупинки `cache_control` (щонайбільше 4), а guard захищає префікс, тоді як будь-яке інше сімейство OpenRouter (`openai/`, `google/`, `qwen/`, …) залишається оголеним і незахищеним.

### Прогресивне старіння

Довгі розмови накопичують багато поворотів повідомлень, але старі повороти стають менш актуальними. Модуль `progressiveAging.ts`** погіршує повідомлення залежно від відстані повороту** (відстань вимірюється від кінця розмови). Зі стандартними параметрами (`verbatim: 2, light: 2, moderate: 3`):

- **Останні 2 повороти (відстань ≤ 2)** : Зберігається дослівно
- **Відстань 3** : Компресія Caveman (видалення наповнювача)
- **Відстань 4 +** : підсумовані повідомлення помічника; повідомлення користувача скорочені до першого рядка, що не перевищує 120 символів; інші ролі недоторкані. Системні підказки, старі повідомлення та останнє повідомлення користувача завжди зберігаються дослівно незалежно від відстані. Нічого не відкидається відразу, і діапазон `light` недоступний із надісланими параметрами за замовчуванням (`light` дорівнює `verbatim`).

#### Приклад коду

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### Коли використовувати

Прогресивне старіння є** завжди ввімкнено** для режиму `aggressive` — це крок 2 `compressAggressive()`. Режим Ultra не запускає його. Це особливо ефективно для:

- Тривалі сеанси кодування
- Багатоденні бесіди
- Агентські робочі процеси з багатьма викликами інструментів

### Режим виведення Caveman

Режим виведення Caveman додає** системні підказки** які запитують у самої моделі стислі виведення — рівень `lite` запитує стислі відповіді, які містять повні речення, `full` просить її «відповідати коротко, як розумна печерна людина», а `ultra` запитує телеграфний вихід; запитують лише інструкції, вони не можуть цього гарантувати. Запити отримують їх через `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`): `open-sse/handlers/chatCore.ts` спочатку розв’язує вибір за допомогою зворотної сумісності (`resolveOutputStyleSelection()` у `open-sse/services/compression/outputStyles/backCompat.ts`), яка, поки `outputStyles` порожній, відображає ввімкнений `cavemanOutputMode` на стиль виводу `terse-prose` у `cavemanOutputMode.intensity` (дивіться Back-compat нижче); непорожній вибір `outputStyles` використовується як є, і `cavemanOutputMode.enabled` та `intensity` тоді не мають ефекту, тоді як його перемикач `autoClarity` все ще застосовується. `outputMode.ts` містить тексти інструкцій (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), обхід вмісту та помічник розміщення, який використовує ін’єкція; його власний інжектор `applyCavemanOutputMode()` не має робочого виклику.

#### Як це працює

Цей режим не стискає вхідні дані. Він додає блок інструкцій до системної підказки (дивіться, як працює ін’єкція нижче), і будь-який режим стиснення введення, вибраний для запиту, продовжує працювати після цього в тілі, яке зараз містить блок. Попереду пункту про спільні кордони, яким закінчується кожен рівень, англійський рівень `full` читається:

> «Відповідайте лаконічно, як розумна печерна людина. Відкидайте статті (a/an/the), наповнювач (just/really/basically/actually/simply), люб’язності, хеджування. Фрагменти OK. Короткі синоніми (великі, не розширені, виправлення не впроваджено). Зберігайте всю технічну суть, код, помилки, URLs, ідентифікатори точними».

Це особливо добре працює для:

- Генерація коду (терсер виводить = менше токенів)
- Швидкі запитання та відповіді (не потребує детальних пояснень)
- Пакетна обробка (максимальна продуктивність)

#### Коли використовувати

Режим виведення Caveman є** зареєструватися** . Якщо стиснення ввімкнено (`enabled: true`, головний перемикач на сторінці налаштувань стиснення), увімкніть його за допомогою `cavemanOutputMode.enabled`; `intensity` вибирає `lite`, `full` або `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Компресійне комбо** Режим виводу** toggle (`outputMode`, рівень у `outputModeIntensity`) встановлює той самий перемикач для запитів, до яких застосовується combo, а інструмент `omniroute_set_compression_engine` MCP записує його через свій логічний аргумент `outputMode`. Непорожній вибір `outputStyles` має пріоритет над цим перемикачем. На інформаційній панелі, увімкнувши** Лаконічна проза** стиль виведення вставляє той самий блок (див. Стилі виводу нижче).

Адаптовано з [ayghri/i-have-adhd](https://github.com/ayghri/i-have-adhd) (MIT).                                                                              | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |

Обидва стилі проти скупчення додають межу без мертвих елементів керування / без виготовлення претензій. | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |

Кожен стиль містить три рівні інтенсивності — `lite`, `full`, `ultra` —, і кожен рівень закінчується пунктом спільних меж (`SHARED_BOUNDARIES` і `outputMode.ts`), який зберігає точність блоків коду, шляхів до файлів, команд, помилок і URLs. Тексти рівня `terse-prose` та `terse-cjk` додають ідентифікатори до цього списку.

`terse-cjk` обмежено локалізацією на `zh` у двох місцях. Сторінка «Параметри стиснення» містить свій рядок лише тоді, коли мовою UI панелі інструментів є китайська (`zh-CN` або `zh-TW`), а `applyOutputStyles()` вводить її лише тоді, коли мова дозволеного запиту (див. Вибір мови нижче) — `zh`. Приховування рядка не очищає збережений вибір `terse-cjk` : параметри API приймають будь-який ідентифікатор стилю, а збереження інших стилів на сторінці зберігає його. Під час запиту перевірка мови `applyOutputStyles()` є єдиним шлюзом локалі.

#### Як працює ін'єкція

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) розв’язує вибір із каталогом (невідомі ідентифікатори та стилі, що не відповідають локалізації, видаляються, ніколи не виникає помилка; вибір, який розв’язується без стилю, залишає тіло незмінним, пропускається як `no_styles`), об’єднує вибрані інструкції в порядку каталогу, додає пропозицію про межі** один раз** (плюс положення про безпеку, `SAFETY_BOUNDARIES` або його переклад, коли вибрано `less-code` або `ponytail` ), і починає блок з єдиного маркера ідемпотентності (`[OmniRoute Output Styles]`), тому повторне застосування є безопераційним. Якщо вирішена мова (див. Вибір мови нижче) має переклад, замість англійської вводиться локалізована інструкція.

On a body with a non-empty `messages` array, the idempotency check runs before the content bypass: when the `[OmniRoute Output Styles]` marker is already in the top-level `system` field (a string or a content-block array) or in a system message with string content, the body is left unchanged as `already_applied` and no keyword check runs. Otherwise a content bypass (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) checks the text of the last three messages, whatever their role, and skips the styles for the whole turn when that text matches its security, irreversible-action or clarification keywords, or an order-sensitive sequence: `first`, `then`, `after that`, `before`, `rollback` or `backup` followed within 240 characters by `delete`, `drop`, `migrate`, `deploy` or `release`. The bypass runs while the **Auto-Clarity Bypass** toggle (`cavemanOutputMode.autoClarity`, on by default) is on; turning the toggle off skips the keyword check.

Коли обхід пропускає поворот, `placeSystemInstruction()` (той самий файл), який ніколи не створює новий `messages[0]`, розміщує блок у першому з них, який знайде:

1. Початкове системне повідомлення з вмістом рядка: блок додається після його тексту.
2. Поле `system` верхнього рівня: блок додається після тексту рядка або додається як новий текстовий блок до масиву блоків вмісту.
3. Перше наступне системне повідомлення з вмістом рядка: блок додається після його тексту.
4. Нічого з перерахованого вище: блок переходить у нове системне повідомлення в кінці `messages`.

У тілі без масиву `messages` (або з порожнім масивом) обхід вмісту не виконується, а поле `system` верхнього рівня не перевіряється. Блок додається після тексту поля `instructions` рядка, якщо це поле вже не містить маркер `[OmniRoute Output Styles]`, у цьому випадку тіло залишається незмінним як `already_applied`. Якщо тіло не має рядкового поля `instructions` але містить `input` (рядок або масив), блок стає `instructions`, замінюючи будь-яке нерядкове значення, яке зберігалося в цьому полі. Тіло, що не містить ані рядкового поля `instructions`, ані рядка чи масиву `input` залишається незмінним і пропускається як `no_messages`.

#### Як включити

На інформаційній панелі:** Контекст стиснення → Параметри стиснення** (`/dashboard/context/settings`), Розділ стилів виводу: один рядок на стиль із перемикачем on/off і селектором рівня. Стилі вводяться, коли ввімкнено саме стиснення (головний перемикач сторінки, `enabled`). The** Auto-Clarity Bypass** перемикач знаходиться на** Печерна людина** сторінки (`/dashboard/context/caveman`), у своїй** Режим виводу** картку. Програмно конфігурація стиснення зберігає вибір як:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Back-compat: поки `outputStyles` порожній, застаріле налаштування `cavemanOutputMode.enabled` відображається на `terse-prose` у `cavemanOutputMode.intensity`. Потім блок починається з маркера `[OmniRoute Output Styles]`, де застарілий інжектор `applyCavemanOutputMode()` написав `[OmniRoute Caveman Output Mode]`. Під маркером текст відповідає старій ін’єкції в en, pt-BR, es, de, fr, it, ru, id і vi; у ja та zh він містить один додатковий пробіл перед пропозицією boundaries. `terse-prose` перекладається на pt-BR, es, de, fr, it, ru, zh, ja, id і vi, тому запит, розв’язаною мовою якого є `hu` отримує англійський текст, де застарілий інжектор використовував угорський.

Вибір мови стилю виведення (`resolveOutputStyleLanguage()` в `outputStyles/apply.ts`): якщо `languageConfig.enabled` увімкнено, `autoDetect` вибирає останнє повідомлення користувача в масиві `messages` запиту, яке містить текст (рядковий вміст або `text` його частин вмісту), і запускає на ньому детектор механізму Caveman (`detectCompressionLanguage()`). Детектор повертає `zh` для тексту з символами Han і без kana; інакше він повертає будь-який з `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` і `id` має найбільше збігів підказок, і `en` коли жоден не збігається з текстом — який він не може класифікувати, отримує англійську мову, ніколи не `defaultLanguage`, і `vi` ніколи не виявляється, хоча стилі надсилають текст `vi`. Тіло відповідей API зберігає свої черги в `input`, який не вибирається, тому отримує `defaultLanguage`, а потім англійську. Якщо жодне повідомлення користувача в `messages` не містить тексту або якщо `autoDetect` вимкнено, застосовується `defaultLanguage`, а потім англійська. Якщо `languageConfig.enabled` вимкнено, мовою буде англійська — якщо до запиту не буде застосовано комбінацію стиснення (комбінацію, призначену комбінації маршрутизації запиту, або комбінацію стиснення за замовчуванням, до якої chatCore повертається для вбудованого стекового конвеєра): застосування комбінації вмикає `languageConfig.enabled` для цього запиту та встановлює `defaultLanguage` із мовних пакетів комбінації (збережене значення, якщо це одне з пакети комбо, інакше перший пакет комбо, який за замовчуванням має значення `en`), тоді як збережений `autoDetect` (увімкнено за замовчуванням) все ще застосовується. Механізм введення Caveman вибирає свою мову пакета правил по-різному — для кожної текстової частини та, з вимкненим автоматичним визначенням, шлюзує `enabledPacks`.

Матриця мови стилю × закріплена `tests/unit/compression/output-styles-i18n-matrix.test.ts`: кожен стиль каталогу потребує запису в `BASELINE_LANGUAGES` тесту; стиль, який не обмежено локалізацією, повинен надавати переклад pt-BR ( `terse-cjk` із локалізацією не поширюється на це правило), якщо він не перерахований у `KNOWN_ENGLISH_ONLY`, який може містити лише стилі без жодних перекладів — перерахований стиль, який має будь-який переклад, не пройшов тест; і стиль не проходить тест, коли він втрачає мову, яку містить його запис `BASELINE_LANGUAGES`. Щоб додати стиль, перегляньте [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### Стиснення результатів інструменту

`compressToolResult()` в `open-sse/services/compression/toolResultCompressor.ts` стискає текст результату інструменту за допомогою** 5 стратегій** . Він пробує їх у такому порядку, і перша ввімкнена стратегія, перевірка якої відповідає вмісту, визначає результат:

1. **`fileContent`** : вміст із 3 або більше рядків, у яких принаймні один рядок, ігноруючи початковий відступ, починається з `import `, `export `, `function `, `class `, `const `, `let `, `var ` або `return ` (ключове слово плюс пробіл) або з `if`, `for` або `while` після яких іде `(` або ` (`, зберігає свої перші 20 і останні 5 рядків із прибраними середина позначена.
2. **`grepSearch`** : вміст із принаймні одним рядком у формі `<path>:<digits>:`, де текст перед першою двокрапкою не має пробілів, зберігає лише ці рядки, щонайбільше 30, за якими йде підрахунок будь-яких подальших збігів і список відповідних файлів; кожен другий рядок випадає. Одного такого рядка достатньо, щоб запустити стратегію, тому рядок журналу, що починається з мітки часу, як-от `12:30:45` також зараховується.
3. **`shellOutput`** : вивід, який містить послідовність ANSI CSI (`ESC[` потім цифри або крапки з комою, потім літеру, як у кольорових кодах) або `$` за якими слідують пробіли в будь-якому місці тексту, втрачає ці послідовності (інші вихідні символи, такі як `ESC[?25l` або послідовність заголовка вікна OSC, зберігаються) і зберігає останні 50 рядків із згорнутими послідовними повторюваними рядками. Оскільки ця перевірка виконується до `json` і `errorMessage`, JSON або вихідні дані про помилку, які містять такий `$` ніколи не досягають їх, поки `shellOutput` увімкнено.
4. **`json`** : корисне навантаження JSON понад 2000 символів, яке починається з `{` або `[` (після необов’язкового пробілу) і аналізується підсумовано: масив із понад 7 елементів зберігає перші 5 і останні 2 елементи та загальну кількість, а об’єкт зберігає свої перші 20 ключів, причому кожне значення вкладеного об’єкта чи масиву замінено заповнювачем `{…N keys}` (для масиву N є його довжиною) та Маркер `_remaining_<N>_keys` підраховує ключі, пропущені після перших 20. Скалярні значення копіюються повністю, тому об’єкт із 20 ключами або менше без вкладених значень лише повторно змінюється. — зменшений отримує символи та залишається незмінним.
5. **`errorMessage`** : вивід, який містить у будь-якому місці та в будь-якому регістрі букв `error:`, `error ` (слово після пробілу, як у `no error found`), `[error]`, `exception:`, `exception `, `[exception]` або `traceback` зберігає свій перший рядок, наступні 10 рядків і останні 3, з маркером `… [N frames elided] …` замість рядків між ними. Маркер з’являється лише тоді, коли після першого рядка йде більше 13 рядків, тому виведення помилок у 14 або менше рядків не скорочується (у 12 або 13 рядках уже зберігаються останні 3 повторювані рядки).

Після збігу стратегії, навіть тієї, яка нічого не рятує, наступні стратегії не пробуються. Коли стратегія відповідності не зберігає приблизних токенів (довжина ÷ 4, округлена в більшу сторону), — наприклад, кодовий файл із 25 рядків або менше, або масив JSON понад 2000 символів із 7 елементами або менше — агресивний механізм зберігає оригінальний результат інструменту: обидва абоненти (`compressAggressive()` та `compressAnthropicToolResultBlock()`) зберігають оригінал, коли `saved` дорівнює 0 або менше, тоді як сам `compressToolResult()` повертає результат цієї стратегії. Крок інструментального результату – не останнє: резервний підсумовувач механізму може скоротити повідомлення `tool` або `function` довжиною понад 8192 символи (`maxTokensPerMessage`, 2048, помножити на 4).

#### Коли використовувати

Стиснення результатів інструменту є кроком 1 агресивного механізму (`compressAggressive()` в `open-sse/services/compression/aggressive.ts`), тому він працює в агресивному режимі та на етапі `aggressive` стекового конвеєра. Він стискає повідомлення OpenAI-форми `tool` і `function` і текст всередині блоків Anthropic `tool_result`. Кожна стратегія має власний перемикач у `aggressive.toolStrategies`, усі включені за умовчанням. На інформаційній панелі перемикачі знаходяться на сторінці Caveman** Просунутий** переглядати, коли стиснення ввімкнено, а режим за замовчуванням — агресивний.

### Складений конвеєр

Запускається режим стека** кілька двигунів послідовно** — зазвичай спочатку RTK (60-90% економії на виведенні інструменту), потім Печерна людина на решті тексту (~ 46% економії на введенні). Складено, тобто** 78-95% прийнятний діапазон** (див. математику заощаджень у розвідці вище): `1 - (1 - 0.60..0.90) × (1 - 0.46)` становить у середньому ≈ 89%.

#### Як це працює

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### Коли використовувати

Використовуйте режим стека для:

- Робочі процеси з великою кількістю інструментів (агентне кодування, дослідження)
- Економна пакетна обробка
- Коли вам потрібна максимальна економія токенів

Конвеєри зі стеком налаштовуються за допомогою глобального параметра стиснення `stackedPipeline` або за допомогою іменованої комбінації стиснення, призначеної комбінації маршрутизації (див. Перевизначення кожного комбо вище) — а не через автоматичне комбо `modePack` (це поле лише повторно зважує вибір моделі автоматичного комбо, а `stacked` не є дійсною назвою пакета).

## Перевизначення стиснення для комбінацій

Ви можете перевизначити глобальний режим стиснення **для кожної окремої комбінації**, щоб точніше налаштувати поведінку
для різних сценаріїв використання:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Це корисно для:

- **Комбінацій для програмування**: використовуйте режим `aggressive` для тривалих сеансів
- **Комбінацій для швидких запитань і відповідей**: використовуйте режим `lite` для швидких відповідей
- **Комбінацій з інтенсивним використанням інструментів**: використовуйте режим `stacked` для максимальної економії
- **Робочих комбінацій**: не вмикайте перевизначення для провайдерів із кешуванням — постійно активне
  коригування з урахуванням кешу автоматично знижує `aggressive`/`ultra` до `standard`
  (режим `cache-aware` не можна вибрати)
