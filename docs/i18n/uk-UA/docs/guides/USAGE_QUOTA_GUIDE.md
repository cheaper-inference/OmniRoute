> **Коротко**: OmniRoute відстежує використання токенів для кожного запиту, обчислює вартість, застосовує квоти для кожного API-ключа та відображає аналітику на інформаційній панелі. У цьому посібнику пояснюється, як усе це працює.

**Джерела:**

- `open-sse/services/usage.ts` (~70KB) — основна логіка відстеження використання
- `src/lib/usageAnalytics.ts` (~10KB) — агрегація даних для інформаційної панелі
- `src/lib/db/quotaSnapshots.ts` — історичні дані про квоти
- `src/lib/db/usage*.ts` — кілька модулів БД, пов’язаних із використанням

## Огляд

Кожен запит, що проходить через OmniRoute, створює **запис про використання**, який містить:

- **Ідентифікаційні дані**: API-ключ, провайдер, модель і комбінація
- **Токени**: токени запиту, токени відповіді, кешовані токени, загальна кількість
- **Вартість**: сума в USD (обчислена на основі даних про ціни)
- **Часові показники**: затримка, часові позначки початку та завершення
- **Статус**: успіх, помилка, обмеження частоти запитів тощо

Ці записи агрегуються в **аналітику**, зберігаються як **знімки квот** і використовуються для застосування **бюджетних обмежень для кожного ключа**.

```
Запит ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    аналітика  квота   білінг
                    (панель)  (контроль) (експорт)
```

## Що записується

Сервіс `usage.ts` фіксує **подію використання** для кожного запиту:

| Поле               | Тип     | Джерело                                                       |
| ------------------ | ------- | ------------------------------------------------------------- |
| `id`               | string  | UUID, згенерований під час запису                             |
| `apiKeyId`         | string  | Ключ API, що ініціював запит                                  |
| `provider`         | string  | Ідентифікатор провайдера (openai, anthropic тощо)             |
| `model`            | string  | Ідентифікатор моделі (gpt-5, claude-opus-4-6 тощо)            |
| `comboId`          | string? | Ідентифікатор комбінації, якщо запит маршрутизовано через неї |
| `promptTokens`     | number  | Із відповіді провайдера                                       |
| `completionTokens` | number  | Із відповіді провайдера                                       |
| `cachedTokens`     | number  | Токени, знайдені в кеші (кешування промптів Anthropic тощо)   |
| `totalTokens`      | number  | Промпт + завершення                                           |
| `costUsd`          | number  | Обчислюється на основі даних про ціни                         |
| `latencyMs`        | number  | Повна тривалість запиту                                       |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`    |
| `errorClass`       | string? | Клас помилки, якщо статус != success                          |
| `timestamp`        | string  | ISO 8601 UTC                                                  |
| `metadata`         | object  | Користувацькі дані, додані плагіном                           |

### Звідки беруться токени

Токени видобуваються з відповіді провайдера в **обробнику відповіді**:

```ts
// Із open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Для провайдерів, які не повертають дані про використання (деякі провайдери на основі вебкукі), OmniRoute **оцінює** кількість токенів за допомогою евристики `~4 chars per token` (див. `open-sse/services/autoCombo/pipelineRouter.ts`).

### Кешовані токени

OmniRoute відстежує `cached_tokens` окремо від `prompt_tokens`, оскільки:

- За кешування промптів Anthropic стягує знижену плату за кешовані токени (10% від звичайної)
- Деякі провайдери повертають `cache_read_input_tokens`, для яких слід застосовувати інші ціни
- Аналітика може показувати **частку влучань у кеш** = `cached_tokens / prompt_tokens`

### Діагностика рівнів запису в кеш

Панель стану кешу промптів на інформаційній панелі аналітики розрізняє повідомлені провайдером
записи в кеш на 5 хвилин і на 1 годину. Поля Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` і
`usage.cache_creation.ephemeral_1h_input_tokens` зберігаються під час перетворення даних про використання в потоковому та
непотоковому режимах і записуються разом зі зведеннями журналу викликів. Загальна
кількість записів у кеш не додається до цих категорій повторно.

Виклики лише із загальним лічильником записів, зокрема старі записи, мають невідомий
рівень. За часткової деталізації нерозподілений залишок зберігається як невідомий; некоректні або
суперечливі лічильники позначаються, а не отримують TTL без попередження. Позначки
TTL на боці запиту не є свідченням тарифікованого рівня.

Оцінка вартості записів в еквіваленті API на цій панелі охоплює лише повідомлені рівні з відомими цінами, а не
весь запит. Для стандартних тарифів моделей Claude/Anthropic вона використовує 1,25 від
вхідного тарифу для записів на 5 хвилин і подвійний вхідний тариф для записів на 1 годину. Відсутня
ціна означає недоступність оцінки, а не нуль. Ціни фіксуються під час реєстрації кожного нового виклику;
історичні записи не перераховуються. Тому облікові записи з передплатою можуть мати
оцінку в еквіваленті API без фактичного списання цієї суми як грошових витрат або з квоти
передплати. Наявні розрахунки квот, бюджету та точної вартості за даними провайдера залишаються незмінними.

Ця діагностика використовує наявне зведення стану кешу з обмеженим обсягом і правила зберігання журналу
викликів. Вона не змінює типові значення TTL запитів, маршрутизацію чи вибір облікового запису.
Фіксацію запитаного клієнтом TTL і фактичного вихідного TTL у точці надсилання
провайдеру відкладено; ця панель показує рівні за даними квитанцій, а не фактичний вихідний TTL.

Реалізація: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` і `open-sse/utils/cacheWriteUsage.ts`.

## Розрахунок вартості

Вартість обчислюється на основі **даних про ціни**, синхронізованих із LiteLLM (`src/lib/pricingSync.ts`):

| Модель            | Вхідні $/1М | Вихідні $/1М | Кешовані $/1М |
| ----------------- | ----------- | ------------ | ------------- |
| gpt-5             | $2.50       | $10.00       | —             |
| claude-opus-4-6   | $15.00      | $75.00       | $1.50         |
| claude-sonnet-4-5 | $3.00       | $15.00       | $0.30         |
| gemini-2.5-pro    | $1.25       | $10.00       | —             |

Формула розрахунку вартості (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Навіщо віднімати кешовані токени від токенів запиту?** Кешована частина тарифікується окремо; застосування ціни вхідних токенів до всього запиту призвело б до подвійного врахування.

### Синхронізація цін

Дані про ціни автоматично синхронізуються з LiteLLM через кінцеву точку `/api/pricing/sync` (запускається вбудованим завданням cron, а не доступною користувачеві змінною середовища):

```bash
# Запуск вручну
curl -X POST http://localhost:20128/api/pricing/sync
```

Для моделей, для яких немає даних про ціни, OmniRoute використовує **оцінювання вартості** за внутрішніми середніми тарифами (отриманими з даних про ціни LiteLLM).

## Агрегація за діапазоном дат

Модуль `usageAnalytics.ts` обчислює віджети інформаційної панелі на основі необроблених даних про використання. Він підтримує 7 часових діапазонів:

| Діапазон | Період                                | Сценарій використання                |
| -------- | ------------------------------------- | ------------------------------------ |
| `1d`     | Останні 24 години                     | Виявлення погодинних сплесків витрат |
| `7d`     | Останні 7 днів                        | Щотижневий огляд                     |
| `30d`    | Останні 30 днів                       | Щомісячне виставлення рахунків       |
| `90d`    | Останні 90 днів                       | Щоквартальний аналіз                 |
| `ytd`    | Від 1 січня поточного року            | Відстеження річного бюджету          |
| `all`    | Увесь час                             | Статистика за весь час               |
| `custom` | Початок і кінець, задані користувачем | Аудити, спеціальні запити            |

### Обчислювані віджети інформаційної панелі

Для будь-якого діапазону дат аналітичний шар обчислює:

| Віджет                          | Опис                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Зведені картки**              | Загальна кількість запитів, загальні витрати, загальна кількість токенів, частка успішних запитів |
| **Графік щоденної динаміки**    | Витрати + токени за день із накопиченням за моделями                                              |
| **Теплова карта активності**    | Сітка «година доби × день тижня», колір = кількість запитів                                       |
| **Розподіл за моделями**        | Кругова діаграма витрат за моделями                                                               |
| **Розподіл за постачальниками** | Стовпчикова діаграма запитів за постачальниками                                                   |
| **Провідні ключі API**          | Таблиця 10 ключів із найбільшими витратами                                                        |
| **Аналіз помилок**              | Частота помилок у часі, найпоширеніші класи помилок                                               |

### Програмний доступ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // записи історії використання
  "7d",                 // часовий діапазон: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // мапа підключень постачальників (connectionId → назва облікового запису)
  {
    startDate: "2025-01-01",  // необов’язково: для діапазону "custom"
    endDate: "2025-06-01",   // необов’язково: для діапазону "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (центи)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Застосування квот

Квота для кожного ключа API застосовується у двох місцях:

1. **М’який ліміт** (`quotaWarnAt`): попередження на інформаційній панелі, коли використання перевищує поріг
2. **Жорсткий ліміт** (`quotaLimit`): у разі перевищення запит відхиляється з кодом HTTP 429

### Налаштування

```ts
// Для кожного ключа API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — показати попередження
  quotaLimit: 10_00,    // $10.00 — повне блокування
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Схема застосування

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### Знімки стану квот

Таблиця `quotaSnapshots` зберігає **історичний стан квот** для аналізу тенденцій:

| Поле | Опис |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Ключ, що відстежується |
| `window` | "day" | "week" | "month" |
| `used` | Витрати за цей період (центи) |
| `limit` | Ліміт (центи) |
| `resetAt` | Час скидання періоду |
| `createdAt` | Час створення знімка |

Знімки створюються **для кожного запиту**, витрати на який > 0, і використовуються, щоб:

- Відображати індикатор використання квоти на інформаційній панелі
- Показувати графіки динаміки квот за 30 днів
- Надсилати сповіщення, коли використання наближається до ліміту


### Запит аналітики використання

Доступ до даних використання здійснюється через панель керування або інструменти MCP, а не через прямі кінцеві точки REST для експорту. Доступна аналітика:

- **`/api/usage/analytics`** — агреговані показники використання (групування за моделлю, постачальником, ключем)
- **`/api/usage/quota`** — поточний стан квоти для кожного ключа API
- **`/api/usage/history`** — журнали історії запитів

## Інструменти MCP

Два інструменти MCP надають агентам доступ до даних використання (див. `open-sse/mcp-server/tools/`):

| Інструмент              | Опис                                                         |
| ----------------------- | ------------------------------------------------------------ |
| `omniroute_cost_report` | Створює звіт про витрати за кожним ключем за вказаний період |
| `omniroute_check_quota` | Повертає поточний стан квоти для ключа API                   |

Приклад виклику агентом:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## Зберігання та очищення

Обсяг даних використання зростає приблизно на 1–10 КБ із кожним запитом. За великих масштабів це може бути суттєво.

### Налаштування терміну зберігання

Термін зберігання історії використання налаштовується в розділі налаштувань бази даних в інтерфейсі користувача або через `/api/settings/database`.

За замовчуванням історія використання зберігається протягом **90 днів**.

### Очищення

Старі записи очищуються за допомогою `src/lib/db/cleanup.ts`:

- Запускається фоновим процесом cron
- Видаляє з `usage_history` записи, старші за термін зберігання, заданий параметром `usageHistory`

### Оцінка обсягу сховища

| Частота запитів      | Обсяг за 30 днів | Обсяг за 90 днів |
| -------------------- | ---------------- | ---------------- |
| 100 запитів/день     | ~3 МБ            | ~9 МБ            |
| 1,000 запитів/день   | ~30 МБ           | ~90 МБ           |
| 10,000 запитів/день  | ~300 МБ          | ~900 МБ          |
| 100,000 запитів/день | ~3 ГБ            | ~9 ГБ            |

За дуже великого трафіку варто розглянути:

- Скорочення терміну зберігання через налаштування бази даних
- Використання `aggregated_metrics` замість необроблених записів (лише для аналітики)

## Поради щодо оптимізації витрат

### 1. Використовуйте відповідну модель

```bash
# Швидка відповідь — використовуйте дешеву та швидку модель
curl -d '{"model":"auto/fast","messages":[...]}'

# Складне завдання — віддавайте перевагу якості
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Увімкніть кешування

Кешування промптів Anthropic заощаджує **90% витрат на повторюваний контекст**:

```ts
// Кешування автоматичне — просто додавайте той самий великий системний промпт
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Буде кешовано автоматично
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Використовуйте стиснення

Стиснення RTK + Caveman заощаджує **15-95% витрат у сеансах з інтенсивним використанням інструментів**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Установлюйте квоти для кожного ключа

Завжди встановлюйте `quotaLimit`, щоб запобігти неконтрольованим витратам:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Ліміт $10 на місяць
```

### 5. Перевіряйте найбільших споживачів

Використовуйте панель керування або **`/api/usage/analytics`**, щоб згрупувати дані за ключем API та відсортувати за вартістю:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Усунення несправностей

### "Витрати вищі за очікувані"

1. Перевірте **`/api/usage/analytics?groupBy=model`** — знайдіть дорогу модель
2. Перевірте **`/api/usage/analytics?groupBy=apiKey`** — знайдіть найбільшого споживача
3. Переконайтеся, що дані про ціни актуальні: `POST /api/pricing/sync`

### "Записи відсутні"

- Перевірте налаштування зберігання даних БД у розділі Панель керування → База даних → Очищення — старі записи видаляються періодичним завданням очищення (`src/lib/db/cleanup.ts`)
- Перевірте наявність помилок у `src/lib/db/usage*.ts` — помилки запису до БД фіксуються в журналах, але не відображаються
- Переконайтеся, що запит справді надійшов до `chatCore` — перевірте маршрутизацію комбінацій

### "Квота не застосовується"

- Перевірте налаштування `quotaLimit` для ключа
- Переконайтеся, що `quotaWindow` налаштовано правильно
- Знайдіть записи `quotaSnapshots` — вони мають створюватися для кожного запиту
