Нейтральний контракт `config/cli-tools-manifest.json` оголошує канонічний IDs, псевдоніми, двійкові кандидати, рецепти налаштування, аргументи моделі та можливості. Звичайний адаптер Node у `bin/cli/cli-manifest.mjs` і адаптер TypeScript у `src/shared/constants/cliIntegrationManifest.ts` читають той самий файл. Час виконання, каталог, налаштування, завершення, генератори та реєстрація серверної частини перевіряються разом `tests/unit/cli/cli-manifest-drift.test.ts`. Бути каталогізованим не означає, що інструмент можна запустити або налаштувати. Зокрема, 5dive залишається доступним лише для налаштування.

## Середовище та життєвий цикл дитини

`omniroute run`, `omniroute launch` і `omniroute launch-codex` успадковують дозволений список сумісності OS/terminal і вводять облікові дані вибраного цільового елемента. Непов’язані секрети постачальника та бази даних не успадковуються за замовчуванням. `--inherit-env` явно відновлює повне успадкування батьківського середовища; використовуйте його лише тоді, коли вибраний процес третьої сторони має отримати ці значення. Це фільтрація середовища, а не пісочниця OS : процес усе ще виконується з дозволами файлової системи абонента.

Сигнали переривання та завершення пересилаються дитині. Перед видаленням тимчасової конфігурації програма запуску очікує події закриття дочірньої програми. `OMNIROUTE_CHILD_SIGNAL_TIMEOUT_MS` контролює пільговий період перед примусовим припиненням (за замовчуванням 5000 мілісекунд).

## постійне налаштування Gemini

```bash
omniroute setup-gemini --remote https://omni.example --model provider/model --yes
omniroute configure gemini --model provider/model --yes
omniroute run gemini --model provider/model --dry-run --json
```

Перші дві команди налаштовують цю машину для вибраного локального або віддаленого сервера. Інсталяція зберігає непов’язані налаштування JSON, вибирає автентифікацію ключа API Gemini і записує кінцеву точку та облікові дані в приватний файл `.gemini/.env`. Він відхиляє недійсний JSON а не перезаписує його. Кінцева точка URLs має бути HTTP(S), без вбудованих облікових даних, параметрів запиту чи фрагментів. Dry-run друкує шляхи, а не облікові дані.

`GEMINI_CLI_HOME` або `--gemini-home` вибирає постійний домашній корінь. Фактичний `run gemini` створює та пізніше видаляє свій власний тимчасовий дім. Жоден режим не обходить перевірку довіри робочого простору Gemini.

## профілі Codex

`configure codex` записує приватний `<name>.config.toml` із моделлю та її кінцевою точкою постачальника OmniRoute. Посилання на облікові дані здійснюється через `OMNIROUTE_API_KEY`, ніколи не вбудовуються. Команда запуску встановлює вибрану модель у ключі `model` верхнього рівня, а не всередині `model_providers`.

Окремі файли профілю є поточним задокументованим контрактом Codex ; вони накладаються на конфігурацію користувача, якщо їх вибрано за допомогою `codex --profile <name>`. Див. [посилання на офіційний профіль](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) і [посібник OmniRoute Codex](./CODEX-CLI-CONFIGURATION.md).

## Герметичне виконання команд

З явним параметром `DATA_DIR` налаштування `OMNIROUTE_CLI_SKIP_DEFAULT_DATA_ENV=1` запобігає переходу під час запуску до середовища облікових даних каталогу даних користувача за замовчуванням. Це корисно для ізольованих тестів. Це не вимикає інші явно вибрані файли середовища.

## Робочий каталог `.env`

CLI читає файли `.env` у такому порядку, і перший файл, який встановить ключ, виграє: явний `DATA_DIR`, каталог даних за замовчуванням, поточний робочий каталог, потім каталог пакетів. Змінні оболонки завжди виграють.

Робочий каталог може належати комусь іншому (клоноване сховище, розпакований архів), і `omniroute serve` передає середовище CLI на сервер і до кожного інструменту, який запускає сервер. Отже, `.env` може встановити лише ці ключі, перелічені в `bin/cli/utils/untrustedCwdEnv.mjs`:

| ключ                            | Прийняті значення                                                                |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `REQUIRE_API_KEY`               | `true`, `1` або `yes` у будь-якому випадку, значення, які сервер розглядає як on |
| `LANG`, `LC_ALL`, `LC_MESSAGES` | до 64 літер, цифр, `_`, `.`, `@` або `-`                                         |
| `LANGUAGE`                      | те саме, плюс `:`                                                                |
| `TZ`                            | до 64 літер, цифр, `_`, `+`, `-` або `/`, які не починаються з `/`               |
| `NO_COLOR`, `FORCE_COLOR`       | до 16 літер і цифр                                                               |

Кожне значення, яке приймає `REQUIRE_API_KEY`, вмикає перевірку, тому файл не може вимкнути перевірку сам. Однак це не вирішує результат: сервер читає перевизначення `REQUIRE_API_KEY` що зберігається в базі даних перед середовищем, тоді як попередження про прослуховування на всіх інтерфейсах без ключа API читає лише середовище. Зі збереженим перевизначенням `false` робочий каталог `REQUIRE_API_KEY=true` залишає API відкритим і приховує це попередження. Правило `TZ` є вужчим за POSIX: воно відхиляє `.`, `:`, `,` і `<>`, тому форма `:Area/City` і правила, такі як `EST5EDT,M3.2.0,M11.1.0` повинні бути встановлені в оболонці або в `<DATA_DIR>/.env`.

Імена повинні точно збігатися, у верхньому регістрі. Будь-який інший рядок, значення, яке не пройшло перевірку, і ім’я, яке не складається з простих літер ASCII, цифр і `_` (наприклад, з байтом NUL або схожою літерою) пропускаються. CLI друкує одне попередження, яке називає ключі, які він не може встановити, і інше, яке називає дозволені ключі, які він ігнорує, у кожному з яких указано, що потрібно змінити (`TZ (expected a zone name such as Europe/Berlin)`, `lang (write the name as LANG)`). Жоден не друкує значення. Шляхи до файлів у цих повідомленнях і звіти про шлях `.env` `omniroute doctor` екрануються, якщо вони містять символи управління або біді. Обмеження не застосовується, якщо робочим каталогом є каталог даних або каталог пакетів.

`PORT`, `API_PORT` і `DASHBOARD_PORT` немає в списку. Без базового URL із джерела з вищим пріоритетом CLI спілкується з `localhost:<PORT>`, і все, що там прослуховує, отримує ключ API CLI, маркер контексту та машинний маркер CLI (`x-omniroute-cli-token`, див. [CLI_TOKEN.md](../security/CLI_TOKEN.md) ), які локальний сервер приймає для викликів керування з loopback. Порт із робочого каталогу дозволить цьому файлу вибрати слухача, тому встановіть порти в оболонці, у `<DATA_DIR>/.env` або за допомогою опції `--port` команд, які мають один (`serve`, `launch`, `run`).

Парсер не має синтаксису `export`. Такий рядок, як `export LD_PRELOAD=...` називає змінну `export LD_PRELOAD`; з робочого каталогу він пропускається, а в інших файлах `.env` він встановлює те літеральне ім’я, яке нічого не читається.

CLI об’єднує збережений маркер контексту (токен доступу або застарілий ключ API ) лише з власним джерелом цього контексту: схемою, хостом і портом у порівнянні з `URL.origin`. Це стосується запитів, зроблених через HTTP -клієнт CLI(`--base-url`, `OMNIROUTE_BASE_URL`, `omniroute connect <new-url>`), а також команд `launch`, `launch codex`, `configure` і `setup-*`, які записують базовий URL і ключ до конфігурації іншого інструменту. Націлені на інший сервер за допомогою `--remote`, вони використовують явний `--api-key` або `OMNIROUTE_API_KEY` якщо такий встановлений, і не використовують маркер контексту. Порівняння є точним, тому `localhost` і `127.0.0.1`, або хост із кінцевою крапкою та без неї вважаються різними серверами та не отримують маркер контексту. URL з інформацією про користувача, зворотною скісною рискою або пробілом ніколи не збігається, оскільки інші аналізатори URL (наприклад, `urllib` та `httpx` Python) можуть читати з нього інший хост. Для запитів, які CLI надсилає сам, ця перевірка охоплює лише схему та повноваження, тому ідентифікатор із пробілом у шляху чи запиті зберігає маркер.
