Скористайтеся цим посібником, щоб вибрати найменший надійний цикл розробки для pull request. Він не
замінює наведені нижче документи з архітектури та безпеки для окремих областей; він пов’язує кожен поширений
тип зміни з його контрактами, цільовими перевірками та покриттям CI.

## Шлях, який проходить кожна зміна

1. **Виберіть базову гілку перед редагуванням.** Знайдіть найвищу активну гілку `release/v*` і створіть гілку від
   її вершини. Спрямовуйте зміни до цієї гілки, а не до `main`. Якщо триває замороження релізу, не спрямовуйте зміни до замороженої
   гілки; використовуйте наступний активний цикл, описаний у
   [Моделі гілок і релізів](BRANCHING_MODEL.md).
2. **Назвіть контракти.** Визначте кожен каталог, схему, згенерований артефакт, публічний API або користувацький
   інтерфейс, на який впливає зміна. У таблиці нижче наведено мінімальний початковий набір.
3. **Напишіть або оновіть цільові тести.** Зміни робочого коду в `src/`, `open-sse/`, `electron/` або
   `bin/` вимагають автоматизованого тесту в тому самому PR. Запустіть найменший набір тестових файлів, що підтверджує
   потрібну поведінку, а потім — перелічені цільові перевірки.
4. **Дозвольте CI виконати широку матрицю.** Повні сегменти модульних тестів, Vitest, контрольне підвищення покриття та
   робоча збірка запускаються в PR. Запускайте широкий набір локально лише тоді, коли цільова помилка вказує на
   ширший вплив або коли зміна охоплює кілька підсистем.
5. **Узгодьте зміни перед перевіркою.** Отримайте актуальний стан активної базової гілки, перегляньте її нові коміти та різницю ваших змін відносно
   неї, а потім виконайте rebase або merge базової гілки відповідно до процесу для учасників. Вирішуйте конфлікти згенерованих файлів
   і каталогів у їхньому джерелі, повторно генеруйте їх, знову запустіть цільовий цикл і підтвердьте, що
   PR усе ще спрямований до активної гілки релізу.
6. **Зафіксуйте підтвердження.** У шаблоні PR перелічіть виконані команди, кожен доданий або змінений тестовий файл,
   міграції чи прапорці функцій, а також усі перевірки, що виконуються лише в CI й досі очікуються.

## Типові шляхи за типом зміни

Наведені нижче команди є мінімальними цільовими перевірками, а не дозволом пропускати тест, який безпосередньо перевіряє
змінену вами поведінку.

### Провайдер

**Контракти**

- Визначення провайдера в `src/shared/constants/providers/` та його компонування в
  `src/shared/constants/providers.ts`.
- Моделі й можливості в `open-sse/config/providerRegistry.ts` або у винесених із нього файлах реєстру.
- Вибір виконавця/перетворювача, конфігурація OAuth або API-ключа, ресурси інформаційної панелі та згенерований
  довідник провайдерів, якщо застосовно.
- Для загальнодоступних облікових даних потрібно використовувати `resolvePublicCred()`; у відповідях із помилками потрібно використовувати спільні
  допоміжні засоби очищення помилок. Див. `docs/security/PUBLIC_CREDS.md` (git; не компілюється до `/docs`) і
  [Очищення помилок](../security/ERROR_SANITIZATION.md).

**Цільовий цикл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # коли каталог змінюється; закомітьте згенеровану різницю
npm run lint
```

Також протестуйте кожну зачеплену групу запитів: чат, Responses, зображення, вбудовування, аудіо чи відео.
Розглядайте зміни у згенерованому каталозі та еталонних даних як зміни контрактів; не приймайте їх без перевірки.

### Маршрутизація

**Контракти**

- Публічні значення стратегій і метадані UI в `src/shared/constants/routingStrategies.ts`.
- Диспетчеризація та впорядкування в `open-sse/services/combo.ts` і `open-sse/services/combo/`.
- Схеми combo, збереження даних, стан стійкості, можливості моделей і елементи керування API/UI.
- [Рушій Auto-Combo](../routing/AUTO-COMBO.md) і документація зі стійкості, коли змінюється поведінка.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # зміни стратегії або диспетчеризації
npm run check:known-symbols      # зміни реєстрації стратегії
npm run lint
```

Локально використовуйте детерміновані тести з імітацією зовнішнього сервісу. Перевірки combo у робочому середовищі потребують облікових даних і виконуються
вручну, а не замість CI.

### UI / UX

**Контракти**

- Маршрут/сторінка Next.js і межі спільних компонентів у `src/app/` та
  `src/shared/components/`.
- Форми відповідей API, стани завантаження/відсутності даних/помилок, поведінка клавіатури та засобів читання з екрана,
  адаптивний макет, теми та розширення локалей.
- Англійські вихідні рядки UI у `src/i18n/messages/en.json`; не додавайте новий текст для користувачів безпосередньо в код.

**Цільовий цикл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Для змін взаємодії або візуального оформлення запустіть застосунок і перевірте як вузьку, так і широку області перегляду. CI запускає
робочу збірку та ширші набори тестів; візуальна поведінка все одно потребує цільового тесту компонента, Playwright
або задокументованої ручної перевірки, що відповідає зміні.

### i18n

**Контракти**

- `src/i18n/messages/en.json` є джерелом UI; `config/i18n.json` є джерелом локалей.
- Каталоги CLI зберігаються окремо в `bin/cli/locales/`.
- Зберігайте заповнювачі й теги ICU без змін. Не перекладайте назви продуктів/провайдерів/моделей,
  назви протоколів і заголовків, команди, ідентифікатори коду/JSON, URL-адреси, змінні середовища або
  захищені терміни, як-от `OmniRoute`, `OAuth`, `MCP` і `A2A`. Поточний вихідний список міститься в
  `scripts/i18n/glossary/protected-terms.json`.

**Цільовий цикл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # коли змінюються рядки/каталоги CLI
npm run lint
```

Це настанови для наявної системи, а не запрошення розширювати її інструментарій або модель ключів.
Поки проєктується система на заміну, робіть зміни i18n точковими. Не запускайте команди перекладу,
які звертаються до зовнішніх сервісів, якщо завдання явно не вимагає згенерованих перекладів і
ви не перевірили отриману різницю.

### CLI

**Контракти**

- Публічні команди та прапорці в `bin/cli/`, згенеровані команди API, коди завершення, stdout/stderr і
  структури виводу JSON, поведінка конфігурації/середовища та файли пакета.
- Рядки CLI, видимі користувачеві, мають використовувати шар інтернаціоналізації CLI, а каталоги `en`/`pt-BR` мають залишатися синхронізованими.
- Зберігайте Node як підтримуване середовище виконання та дотримуйтеся опублікованого контракту бінарного файлу.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # зміни у згенерованому/зібраному CLI
npm run check:pack-policy     # зміни поверхні пакета
npm run lint
```

Використовуйте точну команду в тимчасовому каталозі даних, коли поведінка залежить від синтаксичного аналізу, файлів або
статусу завершення. CI виконує ширші перевірки артефактів пакета та екосистеми.

### База даних

**Контракти**

- Доменні модулі розміщено в `src/lib/db/`; імпортуйте конкретні модулі безпосередньо (старий шар реекспорту `localDb.ts` було видалено).
- Нумеровані ідемпотентні міграції SQL у `src/lib/db/migrations/`, безпечність транзакцій, поведінка
  оновлення, індекси та кожен викликач, на який впливає схема.
- Маршрути й обробники ніколи не виконують необроблений SQL безпосередньо.

**Цільовий цикл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Під час додавання міграції тестуйте як нову базу даних, так і оновлення з попередньої схеми. Тести бази даних
мають закривати дескриптори та викликати `resetDbInstance()` під час очищення. Запускайте `npm run test:bun:db` лише тоді, коли
змінюється допоміжний шлях адаптера Bun; Node залишається основним середовищем.

### Збірка / розгортання

**Контракти**

- Кореневі маніфести/lock-файл і маніфести/lock-файли робочих просторів, `scripts/build/`, автономне компонування Next.js, вміст пакета `dist/`,
  метадані платформи Electron, робочі процеси CI та контрольні маркери розгортання.
- Підтримувані діапазони Node і дозволене використання Bun, зазначене в `CLAUDE.md`, мають залишатися незмінними.
- Артефакти збірки не мають відстежуватися; застосовуються політики залежностей, ліцензій, робочих процесів і пакетів.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # зміни залежностей або lock-файлу
npm run check:pack-policy      # зміни поверхні опублікованого пакета
npm run lint
```

Використовуйте `npm run build` локально лише тоді, коли зміна впливає на компіляцію, автономне компонування, ресурси
або пакування середовища виконання. Використовуйте `npm run build:release` лише для перевірки випуску/розгортання. Збірка CI є
остаточним кросплатформним сигналом; платформозалежні зміни Electron потребують відповідної цільової збірки
або підтвердження базовою перевіркою.

## Скрипти для розробників на спільній машині

Два допоміжні скрипти в `scripts/dev/` реалізують локальний цикл роботи на devbox, де активні інші сеанси:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # файли з merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # саме ці файли
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # ізольоване робоче дерево, безпечне для паралельної роботи
```

- `typecheck-touched.sh` перевіряє типи лише у змінених файлах `.ts/.tsx` за допомогою тимчасового
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) з обмеженням купи у 6 ГБ, тож він замінює перевірку всього проєкту
  `tsc -p tsconfig.json`, яка призводить до OOM на завантаженій машині. Він виводить помилки у
  змінених файлах разом з одним підсумковим рядком і завершується з кодом `1`, якщо у змінених
  файлах є помилки, `2`, якщо помилки є лише в імпортованих файлах або tsc аварійно завершився
  без діагностики (перегляньте вказаний ним журнал у `_artifacts/typecheck-touched/`), і `0`, якщо
  помилок немає. Тимчасовий tsconfig завжди видаляється; ніколи не додавайте його до коміту.
- `new-worktree.sh` серіалізує паралельні запуски за допомогою
  `<git-common-dir>/omniroute-new-worktree.lock` (типово очікує до 600 с, показуючи повідомлення;
  у заголовку скрипту задокументовано спосіб змінити це значення) і відкочує створену ним гілку,
  якщо `git worktree add` завершується помилкою до появи робочого дерева, тож для повторної спроби
  не потрібен ручний виклик `git branch -D`. Жорстко зв’язаний каталог `node_modules` і копія
  `.husky/_` залишаються без змін.

## Локальний цикл роботи з кандидатом

Тести вихідного коду не можуть довести, що запакований артефакт запускається: проблеми зі списками
файлів у пакеті, скороченими залежностями та нативними бінарними файлами проявляються лише після
встановлення й запуску tarball. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) — це локальна
частина процесу «одноразова збірка / перевірка / просування» з RFC #8084: він збирає одного
кандидата, перевіряє саме цей артефакт, просуває його перейменуванням каталогів і відкочує, якщо
просунутий слот не проходить перевірку працездатності.

```bash
npm run dev:candidate -- run --dry-run --json  # вивести план, нічого не змінюючи
npm run dev:candidate -- run                   # зібрати + перевірити + просунути, автоматично відкотити
npm run dev:candidate -- build                 # npm pack + встановлення в _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # запустити на вільному порту, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # поміняти місцями current і previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # повторно використати tarball, зібраний в іншому місці (CI)
```

- **Одноразова збірка.** `build` пакує поточне дерево (для цього потрібен `dist/server.js`, тому
  спочатку виконайте `npm run build:release`) або копіює `--from-tarball`, а потім установлює
  tarball в ізольований префікс npm, оскільки tarball не містить `node_modules`. Ідентифікатором є
  скорочений sha `HEAD` (`-dirty`, якщо дерево містить локальні зміни) або `tgz-<sha256>` для
  tarball. Уже зібраний ідентифікатор чистого дерева повторно використовується замість нової збірки;
  передайте `--force`, щоб перебудувати його.
- **Перевіряйте пакет, а не вихідний код.** `validate` запускає встановлений CLI
  (`serve --port <free port>`) зі свіжим `DATA_DIR=<candidate>/data`, фіктивними секретами та
  видаленими із середовища значеннями оператора `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` і
  `INITIAL_PASSWORD`, щоб перевірити поведінку свіжої інсталяції без ключів у loopback-режимі.
  Він очікує, доки `GET /api/health` поверне 200, вимагає, щоб `GET /v1/models` повернув 200,
  зупиняє групу процесів і записує результат у `validation.json` разом із хешем tarball.
- **Просувайте той самий артефакт.** `promote` відхиляє кандидата без успішної перевірки для його
  поточного хешу tarball. Типовим активним слотом є `_artifacts/candidate/current`;
  `--target <dir>` вибирає інший каталог у тій самій файловій системі, а його попереднім слотом є
  `<dir>.previous`. Кожне перейменування є атомарним, а збій посеред процесу скасовує вже виконані
  перейменування.
- **Відкочування.** `run` повторно перевіряє просунутий слот і повертає `current` та `previous` у
  попередній стан, якщо ця перевірка завершується невдало. Кандидат, який не проходить першу
  перевірку, ніколи не просувається.

Усе записується до ігнорованого Git каталогу `_artifacts/candidate/`; наявна інсталяція OmniRoute
та її каталог даних ніколи не змінюються. Просунутий CLI розташований за шляхом
`_artifacts/candidate/current/prefix/bin/omniroute`; під час використання запускайте його зі своїм
`DATA_DIR`. Коди завершення: `0` — успіх, `1` — невдала перевірка або просування, `2` — помилка
використання або відсутня збірка.

## Локальний цикл проти CI

| Локальний запуск для кожного патча                                                           | CI надає загальну картину                                                     |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Прямі тести поведінки та наведені вище перевірки категорій                                   | Розподілений повний набір модульних тестів і послідовні тести                 |
| `npm run lint`                                                                               | Набори тестів Vitest і порогові перевірки покриття/якості                     |
| Перевірка типів або збірка лише тоді, коли цього вимагає змінений контракт                   | Продакшн-збірка, перевірки безпеки, документації, залежностей і політик PR    |
| Ручна взаємодія/перевірки наживо лише тоді, коли автоматизація не може підтвердити поведінку | Міжзадачні інтеграційні та платформні перевірки, налаштовані робочим процесом |

Успішний цільовий цикл є свідченням щодо зміненого контракту, а не доказом того, що не пов’язані з ним перевірки CI
пройдуть успішно. Водночас не змушуйте кожне локальне редагування чекати на повну матрицю репозиторію.

## Контрольний список узгодження

Перед запитом на перевірку:

- Переконайтеся, що базовою гілкою PR досі є найновіша активна гілка `release/v*`.
- Отримайте оновлення цієї базової гілки та перегляньте коміти, додані після створення вашої гілки.
- Перегляньте `git diff <active-base>...HEAD` на наявність випадкових або згенерованих змін.
- Розв’язуйте конфлікти каталогів і згенерованих документів, оновлюючи джерело та повторно генеруючи результат.
- Після узгодження повторно запустіть усі цільові тести/перевірки, зазначені в описі PR.
- Ніколи не послаблюйте твердження та не вилучайте обов’язкові тести лише для узгодження зі зміненою базовою гілкою.

Правила щодо заморожування релізу та зміни цільової гілки наведено в документі
[Модель розгалуження та релізів](BRANCHING_MODEL.md). Повний перелік CI наведено в документі
[Довідник перевірок якості](../architecture/QUALITY_GATES.md).
