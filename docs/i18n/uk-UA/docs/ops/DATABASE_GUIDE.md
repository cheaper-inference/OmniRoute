> **Коротко**: OmniRoute використовує **SQLite із журналюванням WAL** як основне сховище та шифрування **AES-256-GCM** для конфіденційних полів у стані спокою. У цьому посібнику розглянуто схему, міграції, резервне копіювання й відновлення, а також операційні інструкції.

**Джерела:**

- `src/lib/db/core.ts` — синглтон + SCHEMA_SQL (17 базових таблиць)
- `src/lib/db/migrationRunner.ts` — версійні міграції
- `src/lib/db/migrations/` — 167 версійних SQL-файлів
- `src/lib/db/encryption.ts` — допоміжні засоби шифрування
- `src/lib/db/backup.ts` — експорт/імпорт резервних копій
- `src/lib/db/healthCheck.ts` — діагностика стану

## Чому SQLite?

OmniRoute вибрав SQLite замість PostgreSQL/MySQL з кількох причин:

| Фактор                    | SQLite                                         | PostgreSQL                                     |
| ------------------------- | ---------------------------------------------- | ---------------------------------------------- |
| **Розгортання**           | Вбудована — окремий сервер не потрібен         | Потребує налаштування сервера                  |
| **Шифрування**            | На рівні застосунку (AES-256-GCM)              | Вбудоване TDE                                  |
| **Продуктивність**        | Швидша для малих/середніх навантажень          | Краща для великої кількості одночасних записів |
| **Паралельність**         | Режим WAL дозволяє паралельне читання          | Повноцінний MVCC                               |
| **Резервне копіювання**   | Копіювання одного файлу                        | `pg_dump` або знімок файлової системи          |
| **Сценарій використання** | Встановлення для одного користувача, вбудована | Багатокористувацький SaaS                      |

Для розгортань з **одним користувачем і одним екземпляром** (основний сценарій використання OmniRoute) SQLite простіша та швидша.

### Журналювання WAL

`core.ts` відкриває базу даних у **режимі WAL (Write-Ahead Logging)**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL дозволяє виконувати **паралельне читання** під час запису — це важливо для інформаційної панелі, яка виконує запити, поки реєструються звернення.

Стандартний розмір кешу становить **65 536 КіБ (64 МіБ)**. SQLite інтерпретує від’ємне значення
`cache_size` як приблизну верхню межу в КіБ і виділяє сторінки за потреби.
Параметр **Налаштування > Система та сховище > Розмір кешу** приймає цілі значення від **1 до
1 000 000 КіБ**; збереження параметра застосовує його до активного з’єднання з базою даних,
а OmniRoute відновлює збережене значення під час запуску.

## Розташування бази даних

Файл SQLite зберігається за адресою:

| ОС      | Шлях                                                         |
| ------- | ------------------------------------------------------------ |
| Linux   | `~/.omniroute/storage.sqlite`                                |
| macOS   | `~/.omniroute/storage.sqlite`                                |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                    |
| Docker  | `/app/data/storage.sqlite` (налаштовується через `DATA_DIR`) |

Супровідні файли:

- `storage.sqlite-wal` — журнал випереджального запису
- `storage.sqlite-shm` — файл спільної пам’яті
- `call_logs/` — артефакти корисного навантаження запитів (якщо ввімкнено)

**Зміна розташування:**

```bash
DATA_DIR=/custom/path omniroute
```

### Межі модулів

Основне архітектурне правило: **модулі не звертаються безпосередньо до таблиць один одного**. Щоб працювати з даними іншого модуля, імпортуйте функцію з цього модуля.

```ts
// ❌ НЕПРАВИЛЬНО: прямий SQL-запит з іншого модуля
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ПРАВИЛЬНО: використовуйте функцію модуля providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

Дотримання цього правила забезпечується перевіркою коду — статичної перевірки немає, але порушення позначаються.

## Міграції

OmniRoute використовує** версії, ідемпотентні міграції** в `src/lib/db/migrations/`. Кожна міграція є одним файлом SQL. Співіснують два формати іменування; версія, записана в `_omniroute_migrations` є числовим префіксом.

### Іменування міграції

| Формат                                          | приклад                              | Використовується для                                                                                                                                                            |
| ----------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (рівно 3 цифри)           | `241_seen_models.sql`                | Стара серія `001`–`241`. Зависло після встановлення формату позначки часу (`240` і `241` були об’єднані безпосередньо перед цим): жоден новий файл не отримує порядковий номер. |
| `YYYYMMDDHHMMSS_description.sql` (14 цифр, UTC) | `20261113120000_add_usage_index.sql` | Кожна міграція, створена з 2026-11-13.                                                                                                                                          |

Чому ця зміна: з послідовними номерами паралельний PRs вибрав той самий наступний номер, і всі, крім одного, мали перенумерувати перед об’єднанням. Мітка часу UTC надає кожному PR власну версію.

Правила для формату позначки часу (застосовуються `npm run check:migration-numbering`, спільно з генератором у `scripts/check/lib/migrationNaming.mjs`):

- Мітка часу — це справжня дата й час UTC, не раніше ніж `20261113000000` і не більше ніж на 10 хвилин у майбутньому.
- Опис складається з малих літер `snake_case` починаючи з літери (`a-z`, `0-9`, одинарний `_` між словами), щонайбільше 80 символів.
- Два файли з однаковою міткою часу є дублікатами.
- Правило відсутності прогалин застосовується лише до старого ряду: кожне число від `001` до `241` повинно існувати, крім відомих прогалин `026`, `055` і `121`. Видалення `241` (або будь-якого старого файлу) не працює. `001` і `241` ніколи не можна додати до білого списку `KNOWN_GAPS`. Файли з мітками часу ніколи не створюють проміжків.
- Кожен запис у `src/lib/db/migrations/` має бути звичайним файлом із правильною назвою `.sql` у нижньому регістрі. Каталог, символічне посилання, файл `.SQL` або `.sql.bak`, прихований файл або ім’я з пробілом не проходять, оскільки бігун пропустив би його мовчки або завершив роботу під час завантаження.

**Застосувати замовлення.** Бігун сортує за числовим значенням префікса, а не за текстом: спочатку старі файли `001`–`241`, потім файли з мітками часу в порядку міток часу, потім будь-які каталоги з простором імен, зареєстровані в `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (версії, такі як `ee-001`). Міграція, яка очікує на розгляд, — це будь-який файл, версія якого не в `_omniroute_migrations`, тому міграція зі старішої гілки, яка об’єднується після нової, все ще застосовується до існуючих баз даних.

**Мітка часу — це порядок створення, а не порядок злиття.** Якщо ваша міграція залежить від таблиці або стовпця, створеного міграцією з a** новіший** мітку часу (наприклад, одну з іншої PR, яка об’єдналася першою), нова база даних спочатку запустить вашу та зазнає помилки. Поки ваш PR все ще відкритий, повторно згенеруйте ім’я файлу за допомогою `npm run db:new-migration`, щоб він отримав новішу позначку часу, або зробіть його незалежним. `npm run test:migrations:fresh` застосовує кожну міграцію до порожньої бази даних і вловлює це.

### Об’єднану міграцію ніколи не видаляють і не перейменовують

Після того, як файл міграції знаходиться у гілці випуску або `main`, він уже запускається в гомологічних базах даних і базах даних розробників, під час інсталяцій VPS і синхронізації Enterprise. Відтоді:

- **Ніколи не видаляйте його.** Свіжі інсталяції втратять схему, тоді як оновлені бази даних її збережуть.
- **Ніколи не перейменовуйте його.** Версія в `_omniroute_migrations` більше не збігатиметься з файлом, тому кожна база даних, яка її вже застосувала, запускатиме її знову. Потім неідемпотентний SQL дублює дані або зупиняє завантаження.
- **Потрібна інша схема?** Створіть нову міграцію за допомогою `npm run db:new-migration`.

Перейменування безпечне лише для файлу, який ще не об’єднано, про що йдеться у підказках шлюзу. Тег випуску тут нічого не змінює: кожне надсилання до гілки `release/v*` публікує образ Docker `:next` і виконується на основі гомолога, установок VPS і синхронізації Enterprise, тому об’єднана міграція виконується на реальних базах даних до того, як існує будь-який тег `vX.Y.Z`. Шлюз не виконує кожне видалення базового файлу, позначеного чи ні.

- **Повернення об’єднаної міграції.** Функція `git revert`, яка видаляє файл, не проходить шлюз. Збережіть файл і скасуйте його схему під час нової міграції: `npm run db:new-migration -- <description>`, з `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` тощо. Оновлені та нові бази даних потім завершуються тією самою схемою.
- **Єдине прийняте перейменування: запис сумісності та ідентичний вміст.** Якщо об’єднаний файл потрібно перемістити (наприклад, два об’єднані файли мають спільну позначку часу, а програма запуску зупиняється через конфлікт версій), перейменуйте пізніший файл, не торкаючись його SQL, і додайте `{ fromVersion, fromName, toVersion, toName }` до `RENAMED_MIGRATION_COMPATIBILITY` у `src/lib/db/migrationRunner/constants.ts`. Бази даних, які застосовували стару версію, переміщують рядок `_omniroute_migrations` замість повторного запуску файлу. Шлюз попереджає про таке перейменування та завжди запускає для нього перевірку комутації, незалежно від нової мітки часу: свіжі інсталяції застосовують файл у його новій позиції, оновлені бази даних – ні, тому виберіть нову мітку часу поруч із старою. Шлюз не вдається перейменувати, якщо вміст змінився (зміна схеми все ще відбувається під час нової міграції) або якщо цільового файлу запису немає на диску.
- **Ніколи не перейменовуйте в межах однієї позначки часу.** Перейменування, яке зберігає мітку часу та змінює лише опис, не проходить ворота, із записом або без нього. З записом, у якого `toVersion` дорівнює його `fromVersion`, програма запуску видаляє старий рядок `_omniroute_migrations` і знову застосовує файл до кожної бази даних, яка його вже запускала. Без запису програма запуску відстежує лише версію: вона пропускає файл у цих базах даних (новий вміст там ніколи не запускається) і реєструє помилку перенумерації під час кожного завантаження. Використовуйте іншу позначку часу та запис про сумісність або збережіть назву.
- **Шлюз перевіряє, щоб перейменований файл не запускався знову.** Для кожного покритого перейменування шлюз передає нову назву файлу для перевірки комутації за допомогою `--must-not-apply`. Перевірка завантажує оновлену базу даних за допомогою справжнього засобу запуску, і якщо програма виконання знову застосовує цей файл (наприклад, через те, що запис має неправильну версію чи ім’я, або через те, що аналізатор тексту шлюзу читає `constants.ts` інакше, ніж TypeScript), шлюз не працює з `migration renomeada rodaria de novo` і просить вас перевірити стару та нову версії та імена запису.

### Що ворота перевіряють на базу

Під час виконання запиту на отримання та виконання черги злиття `npm run check:migration-numbering` порівнює `src/lib/db/migrations/` на диску з тим самим каталогом у базовій гілці. Основою є, у такому порядку: `--base-latest-tag`, `--base <ref>`, змінна `MIGRATION_BASE_REF` або, коли `GITHUB_EVENT_NAME` є `pull_request`, `pull_request_target` або `merge_group`, перший батько коміту злиття, `merge_group.base_sha` корисного навантаження події або `git merge-base HEAD origin/$GITHUB_BASE_REF`. Під час виконання запиту на отримання або виконання черги злиття без розв’язної бази шлюз дає збій. Поза CI без `--base` він друкує `comparação com a base: pulada (sem --base)` і пропускає ці правила.

`--base-latest-tag` порівнює з найновішим тегом випуску (`vX.Y.Z` у порядку semver; суфіксовані теги, такі як nightlies, не враховуються), який є в історії `HEAD`, за тими самими правилами, що й `--base`. Release-Green (`scripts/quality/validate-release-green.mjs`) запускає шлюз таким чином, оскільки push і заплановані запуски не мають бази запитів на отримання, і злиття може завершитися без нового запуску CI. За відсутності мітки випуску в історії ворота виходять з ладу; запустіть `git fetch --tags` (у CI, `actions/checkout` з `fetch-depth: 0` приносить теги).

Перевірка комутації (`scripts/check/migration-commutation.ts`) створює дві тимчасові бази даних із справжнім шляхом встановлення:** оновлений** один (завантаження з базовими міграціями, потім завантаження того самого файлу з міграціями запиту на отримання) і** свіжий** один (одне завантаження з міграціями запиту на отримання). Він порівнює отримані схеми: таблиці та стовпці (без урахування порядку стовпців), обмеження UNIQUE / PRIMARY KEY і FOREIGN KEY, нормалізований текст `CREATE TABLE` кожної таблиці (який охоплює обмеження CHECK, порівняння, згенеровані стовпці та параметри таблиці), індекси, тригери та перегляди. Дані рядків не порівнюються. Якщо вони збігаються, шлюз друкує, що файл не в порядку, але перемикається та пропускає. Якщо вони відрізняються, шлюз не працює з різницею та підказкою для випадку: для файлу, що не відповідає порядку, повторно згенеруйте його ім’я за допомогою `npm run db:new-migration`, що безпечно, оскільки файл ще не об’єднано; для відредагованого базового файлу відновіть базовий вміст і внесіть зміни в нову міграцію; для перейменованого файлу скасуйте перейменування або виберіть іншу нову позначку часу, де він переходить, ніколи ту саму позначку часу з іншою назвою. Якщо сама перевірка не виконується, шлюз не працює в CI і попереджає лише локально. Для відредагованого базового файлу оновлена база даних створюється з базовим вмістом цього файлу, а друге завантаження пропускає його, оскільки його версію вже записано. Для перейменованого файлу оновлена база даних створюється з файлом під його старим іменем, а друге завантаження переміщує його рядок `_omniroute_migrations` через запис сумісності замість повторного запуску; шлюз передає нове ім’я за допомогою `--must-not-apply`, тому перевірка не вдається, якщо його застосовує друге завантаження. Якщо міграція запиту на вилучення не вдається застосувати на оновленому шляху, тобто після кожної базової міграції (незалежно від того, чи не відбувається вона також під час нової інсталяції), шлюз повідомляє `migration do PR não aplica` і просить вас виправити SQL відповідно до поточної схеми бази; якщо файл залежить від іншої міграції запиту на отримання з пізнішою міткою часу, повторно згенеруйте його назву за допомогою `npm run db:new-migration`.

Щоб запустити те саме порівняння локально, передайте базу явно, наприклад `npm run check:migration-numbering -- --base origin/<base-branch>` або `npm run check:migration-numbering -- --base-latest-tag` для порівняння з останнім випуском.

### Перетворення міграції `NNN` Open PR

Запит на отримання, відкритий перед комутатором, може містити послідовний файл, наприклад `242_add_widgets.sql`. Старі числа вище `241` відхиляються, тому конвертуйте їх перед об’єднанням:

1. **Перейменуйте файл за допомогою генератора, зберігаючи опис.** Запустіть `npm run db:new-migration -- <same description>`, щоб отримати нове ім’я, перемістіть у нього SQL і видаліть старий файл `NNN_`. Опис має залишатися ідентичним: запис сумісності нижче відповідає ньому.
2. **Додайте запис про сумісність, якщо постійна база даних запускала старий номер.** Якщо будь-яка база даних, яка зберігається (гомолог, VPS, власна інсталяція учасника), запустила збірку PR із файлом `NNN_`, додайте `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` до `RENAMED_MIGRATION_COMPATIBILITY` у `src/lib/db/migrationRunner/constants.ts`. Це є** необхідний для `237` до `241`** : ці слоти тепер містять канонічні `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` і `241_seen_models.sql`, і без запису така база даних пропускає канонічну міграцію назавжди та запускає перетворену повторно. Це також працює для слота, який залишається порожнім, наприклад `242`, коли адресатом є позначка часу. Якщо сумніваєтеся, додайте запис. Місце, де ви додаєте його в масиві, не має значення: коли цільовий слот запису все ще містить рядок, який інший запис пересуває (наприклад, `237` утримує рядок PR тоді як старіший рядок `usage_history_calculated_cost` чекає, щоб переміститися в `237`), бігун дозволяє цьому запису чекати, поки слот не звільниться. Лише реальний конфлікт, такий як слот, утримуваний рядком, який не переміщує запис, або два записи, які міняються місцями, зупиняє завантаження за допомогою `Cannot reconcile ...`.
3. **Тримайте SQL ідемпотентом** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), тому що перетворена міграція може зустрітися з базою даних, де її схема вже існує.
4. **Перемістити спеціальні випадки з ключем версії.** Якщо PR додав регістр для свого старого номера в `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) або в `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`), змініть ключ на нову позначку часу.

`tests/unit/db/codex-fence-migration-rename.test.ts` є робочим прикладом тесту для перейменованої міграції.

### Зворотні порти до філій перед комутатором

Ніколи не вибирайте та не портуйте файл `YYYYMMDDHHMMSS_` до гілки, яка передувала перемиканню (наприклад, старішої гілки `release/v*` ). Там бігун сортує імена файлів як текст, тому файл із мітками часу працюватиме між `201_` і `202_` у свіжій базі даних, а старий шлюз там не розуміє 14-значних префіксів. У такій гілці запишіть зміну як власний наступний `NNN_` файл цієї гілки, ідемпотентний, тому це буде безопераційно, коли версія з міткою часу надходить пізніше.

### Як виконуються міграції

Під час запуску `migrationRunner.ts`:

1. Створює таблицю `_omniroute_migrations`, якщо не існує
2. Запити для вже застосованих міграцій
3. Застосовує будь-які нові міграції по порядку, кожну в транзакції
4. Записує кожну застосовану міграцію з міткою часу

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### Ідемпотентність

Міграції повинні бути** ідемпотент** — запустивши їх двічі, має бути безопераційним:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

Використовуйте пропозиції `IF NOT EXISTS`, `IF EXISTS` і `OR IGNORE` / `OR REPLACE`.

### Додавання нової міграції

1. **Створіть файл за допомогою генератора** : `npm run db:new-migration -- <description>` (наприклад `npm run db:new-migration -- add combo priority`). Він записує `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` із поточним часом UTC і заголовком коментаря, переміщається вперед на одну секунду, якщо береться ця позначка часу, і ніколи не перезаписує файл. Не вибирайте число вручну.
2. **Використовуйте безпечний DDL** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **Ретельно заповнюйте дані** : використовувати `UPDATE ... WHERE ...` для обробки наявних рядків
4. **Перевірте порядок і найменування** : `npm run test:migrations:fresh` (усі міграції на порожній базі даних) і `npm run check:migration-numbering`
5. **Тест на копії** : ніколи не запускайте неперевірені міграції у виробництві
6. **Таблиця, створена з коду, також потребує міграції** : якщо модуль також створює таблицю ліниво (`CREATE TABLE IF NOT EXISTS`, зберігається як шлях самовідновлення), міграція повинна створити її з тим самим DDL. Інакше чисте встановлення та оновлене встановлення закінчуються різними схемами, залежно від того, чи запущено цей шлях коду. `tests/unit/db/lazy-table-migration-guard.test.ts` сканує `src/` і `open-sse/` і не виконується на лінивому `CREATE` без міграції (#20557). Приклад: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

приклад:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **Зворотно-несумісні зміни** (наприклад, видалення стовпців) складно. OmniRoute чи підтримує NOT пониження версії — після застосування міграції, зміна схеми є постійною. Плануйте відповідно.

## Шифрування даних у стані спокою

Конфіденційні поля (ключі API, токени OAuth, рядки підключення) шифруються у стані спокою за допомогою **AES-256-GCM**.

### Як це працює

```ts
// src/lib/db/encryption.ts (спрощено)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### Де це використовується

- `provider_connections.api_key` — шифрується на рівні застосунку
- `provider_connections.access_token`, `refresh_token`, `id_token` — шифруються на рівні застосунку
- Записи `key_value` з `namespace = "secrets"` — шифруються на рівні застосунку
- `proxy_registry.auth` — шифрується на рівні застосунку (за наявності)

### Ключ шифрування

Ключ шифрування утворюється з **парольної фрази** (задається через змінну середовища `STORAGE_ENCRYPTION_KEY`) і **солі** (зберігається в БД). Для розшифрування даних потрібні обидва компоненти.

```bash
# Згенеруйте безпечну парольну фразу
openssl rand -hex 32

# Задайте в .env
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **Критично важливо**: втрата ключа шифрування означає втрату доступу до всіх зашифрованих даних. **Зберігайте резервну копію ключа окремо від бази даних**.

### Що НЕ шифрується

З міркувань продуктивності наведені нижче дані зберігаються як звичайний текст:

- Відображувані назви постачальників
- Визначення моделей (вони вже загальнодоступні)
- Правила маршрутизації
- Записи про використання (без персональних даних)

---

## Застереження щодо шифрування (v3.8.16+)

OmniRoute використовує **`migrateLegacyEncryptedString()`** для прозорої підтримки двох схем шифрування:

- **Застаріла** (до v3.5.0): «шифрування» на основі XOR (не справжня криптографія)
- **Поточна**: AES-256-GCM із належним IV і тегом автентифікації

Допоміжна функція міграції виявляє застарілий формат і повторно шифрує дані за новою схемою під час першого читання. Це дає змогу оновити стару базу даних без втрати облікових даних.

## Кеш читання

Для даних, які часто зчитуються (моделей, постачальників, налаштувань), `readCache.ts` надає **кеш у пам’яті**:

```ts
// Кешується під час запуску, анулюється під час запису
const providers = await getCachedProviders(); // Швидко, у пам’яті
const fresh = await listProviders(); // Повільно, звертається до БД
```

| Кешована сутність      | Ключ кешу      | TTL                  |
| ---------------------- | -------------- | -------------------- |
| `models`               | `models:v1`    | До наступного запису |
| `provider_connections` | `providers:v1` | До наступного запису |
| `settings`             | `settings:v1`  | До наступного запису |
| `combos`               | `combos:v1`    | До наступного запису |

Кеш анулюється під час кожного запису до відповідної таблиці.

## Резервне копіювання та відновлення

### Ручне резервне копіювання

```bash
# Використайте CLI, щоб створити локальну резервну копію
omniroute backup create --name pre-migration

# Або через API
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

Файл резервної копії містить:

- Усі таблиці БД (серіалізовані у JSON)
- Артефакти журналу викликів (закодовані у base64, необов’язково)
- Налаштування та секрети (зашифровані)
- Конфігурацію плагінів

### Відновлення

```bash
# Через CLI
omniroute restore pre-migration

# Через API
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **Попередження**: відновлення перезаписує всю БД. Спочатку зупиніть усі клієнти.

### Автоматизоване резервне копіювання

```bash
# Увімкніть автоматизоване щоденне резервне копіювання через CLI
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

Розклад виконується на боці сервера фоновим завданням, яке запускається кожні 30 секунд
(за замовчуванням) і перевіряє вираз cron відповідно до локального часу сервера.

| Змінна                                      | Значення за замовчуванням | Опис                                                                                                              |
| ------------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`                   | Інтервал запуску в мс (мін. `5000`). Має бути коротшим за 60 с, щоб надійно потрапляти у відповідну хвилину cron. |

### Гаряче резервне копіювання SQLite

Для резервного копіювання активної БД без простою:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

Ця команда використовує API оперативного резервного копіювання SQLite — її безпечно запускати під час роботи OmniRoute.

## Налаштування продуктивності

### Режим WAL

WAL увімкнено за замовчуванням. Для великих робочих навантажень запису враховуйте:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute не встановлює `journal_size_limit`. Контрольна точка переміщує кадри WAL в головний файл, але файл WAL зберігає свій найбільший виділений розмір. Захист `OMNIROUTE_WAL_GUARD_MAX_MB` лише попереджає та запускає `wal_checkpoint(RESTART)`; це не обмеження розміру диска.

### Індекси

Ключові індекси продуктивності (автоматично створені міграціями):

- `idx_models_provider` — пошук моделі за постачальником
- `idx_combo_targets_combo_id` — комбіноване цільове розширення
- `idx_usage_history_api_key_timestamp` — аналітика використання
- відстеження квот `idx_quota_snapshots_api_key_window` —
- `idx_call_logs_timestamp` — запити журналу викликів

Щоб додати новий індекс, створіть міграцію:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### Memory-Mapped I/O

Для дуже великих баз даних (> 10 ГБ) відображення пам’яті можна налаштувати за допомогою прагми SQLite :

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### Ущільнення

Тривалі екземпляри OmniRoute виграють від випадкових `VACUUM`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

Запускати щомісяця під час вікон із низьким трафіком. (режим WAL зменшує потребу, але не усуває її.)

## Перевірка стану

`src/lib/db/healthCheck.ts` надає **діагностику стану на рівні БД**:

Обидва методи потребують автентифікації (інакше повертається `401`). `GET` лише виконує діагностику; `POST` запускає
ту саму перевірку з увімкненим `autoRepair`.

```bash
GET  /api/db/health   # діагностика
POST /api/db/health   # діагностика + відновлення
```

У відповіді повертається `DbHealthCheckResult`, створений функцією `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Бюджети доменів посилалися на ключі API, яких більше не існує.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| Поле              | Значення                                                                                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `true`, коли `issues` порожній. `driver` ніколи не впливає на це значення.                                                                                  |
| `issues[].type`   | Одне зі значень: `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`.                                                           |
| `repairedCount`   | Кількість рядків, відновлених під час цього запуску; завжди `0`, коли `autoRepair` має значення false.                                                      |
| `backupCreated`   | Чи було створено резервну копію перед відновленням.                                                                                                         |
| `checkedAt`       | Позначка часу ISO, спільна для запуску та будь-якої створеної ним примітки про відновлення.                                                                 |
| `driver.name`     | Драйвер SQLite, який обслуговує перевірену базу даних.                                                                                                      |
| `driver.degraded` | `true`, коли запис не має надійного збереження у файлі бази даних — резервний WASM-драйвер `sql.js` (зі збереженням усього файлу) або база даних у пам’яті. |

Такий самий вміст повертає інструмент MCP `omniroute_db_health_check`.

Запустіть `PRAGMA integrity_check`, щоб виявити пошкодження:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# Має вивести: ok
```

Якщо команда повертає будь-що, крім `ok`, **негайно припиніть використання бази даних** і відновіть її з резервної копії.

## Аварійне відновлення

### Сценарій 1: втрачено файл WAL

Файл `-wal` відсутній, але `-shm` і основна база даних не пошкоджені:

```bash
# Автоматично відновлюється під час наступного відкриття
omniroute
```

Якщо SQLite не може виконати автоматичне відновлення:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### Сценарій 2: пошкоджено файл основної бази даних

Відновіть із резервної копії:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` лише завантажує повний архів `.tar.gz` із запущеного сервера
(`GET /api/db-backups/exportAll`, потрібні облікові дані оператора); ця команда нічого не відновлює.

### Сценарій 3: втрачено ключ шифрування

Без ключа **відновлення неможливе**. Зашифровані поля неможливо прочитати. Повторно додайте всіх провайдерів вручну з новими обліковими даними.

> **Запобіжний захід**: завжди створюйте окрему резервну копію ключа шифрування, бажано в менеджері паролів або KMS.

### Сценарій 4: диск заповнений

SQLite повертатиме помилки `SQLITE_FULL`. Звільніть місце на диску, а потім виконайте:

```bash
# Створіть контрольну точку WAL, щоб звільнити місце
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## Усунення несправностей

### "Базу даних заблоковано"

Інший процес утримує блокування запису. Можна:

- Зачекати, доки інший процес завершиться (перевірте за допомогою `lsof | grep storage.sqlite`)
- Примусово завершити інший процес
- Якщо проблема не зникає, перезапустити OmniRoute

### "Порушено обмеження зовнішнього ключа"

Доменний модуль порушує посилальну цілісність. Перевірте:

- Осиротілі рядки в залежних таблицях
- Каскадні видалення, які не були поширені
- Нещодавню міграцію, яка змінила зовнішній ключ

Виконайте `PRAGMA foreign_key_check;`, щоб знайти порушення.

### "Недостатньо пам’яті"

Відображене в пам’ять введення-виведення SQLite перевищує обмеження ОС. Зменште обсяг за допомогою прагми SQLite:

```sql
PRAGMA mmap_size = 134217728;  -- 128 МБ замість 256 МБ
```

Або вимкніть:

```sql
PRAGMA mmap_size = 0;
```

### "Помилка міграції на проміжному етапі"

Міграція виконувалася в транзакції, тому зміни мали бути відкладені. Якщо цього не сталося:

1. **Зупиніть OmniRoute** (щоб запобігти подальшим спробам)
2. **Перевірте стан БД** за допомогою `sqlite3`
3. **Вручну виправте** частково виконану міграцію
4. **Повторно запустіть** OmniRoute (буде здійснено повторну спробу міграції)

Щоб запобігти цьому, завжди спочатку тестуйте міграції на копії.
