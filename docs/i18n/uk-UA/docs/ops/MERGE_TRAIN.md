## Посадка на випускну гілку

Omni-черга керує посадками в `release/vX.Y.Z`. Прочитайте `mode` верхнього рівня в `config/merge-queue/config.json` у гілці за замовчуванням, перш ніж отримати PR. Див. [Omni-Queue](OMNI_QUEUE.md).

- **`shadow`** запускає перевірку та залишає посадку для ручного злиття. Застосуйте `omni-queue` до схваленого PR на його остаточній голові. Перевірте придатність за допомогою `npm run queue -- why <PR>`. Чекайте вердикту для цієї голови в `npm run queue -- history --base <branch>`. Продовжити на `would-land`. На `culprit-found` або `would-dequeue` утримайте злиття та усуньте причину.
- **Тіньові винятки.** Поїзд із зеленим повним CI проти поточної базової підказки може продовжити без окремого вердикту черги. Той самий виняток застосовується, коли головка PR вже містить поточний базовий наконечник.
- **`live`** використовує мітку `omni-queue` для запуску посадки. Лише черга приземляє PR. Залиште команди злиття та прямі надсилання до черги.

Кожна посадка потребує дозволу власника та відповідних необхідних перевірок. Застосовувати `omni-queue` тільки після дозволу власника на посадку. Поставлений у чергу PRs що стосується захищених шляхів, також потребує рішення власника `protected-approved` для цього PR.

Набір правил «Вимагати зелених воріт для активного випуску» вимагає зелених `Gate / CI` та `Gate / Quality` на голові. Ніколи не використовуйте `--admin` для обходу червоних воріт. Блоки заморожування випуску зливаються в заморожену гілку. Див. [жорстке правило 21](HARD_RULES_DETAIL.md). Ніколи не позначайте, не об’єднуйте та не надсилайте запит на отримання, що інший сеанс працює. Див. [жорстке правило 22](HARD_RULES_DETAIL.md).

## Запит на тягу поїзда

1. Розпочніть гілку поїзда з поточного базового кінця випуску. Інтегруйте точні схвалені голови учасників за допомогою комітів злиття. Зберігайте історію комітів, уникаючи стиснення та перебазування.
2. Відкрийте один запит на вилучення для залізничної гілки. Перевірте цей PR за допомогою власного повного CI на поточній базовій підказці. Перед приземленням ще раз перевірте наконечник основи та схвалені головки елементів. Оновіть потяг і його CI коли перевірений кандидат зміниться.
3. Висадіть поїзд PR за допомогою коміту злиття у відповідному режимі черги. У режимі реального часу метод посадки `merge-ff` черги зберігає коміти злиття. Оригінальні голови учасників стають доступними з гілки випуску. GitHub позначає член PRs як об’єднаний, а коміти зберігають своїх авторів.

Загальнодоступним прикладом є [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071). Він об’єднав 18 членів PRs і приземлився з комітом злиття 2026-11-24.

Повернення синхронізації від `main` до наступної гілки випуску також здійснюється через комміт злиття. Для подальшої синхронізації потрібне збереження походження `main`. Див. [Ізоляція робочого дерева](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash).

## Локальний валідатор злиття

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

Валідатор отримує базову та PR головки та поєднує їх у одноразове робоче дерево. Він запускає свій пакет парності один раз на результуючому дереві. Невдала вибірка заголовка або конфлікт злиття викидає цей PR, а сценарій продовжує роботу з PRs що залишився.

- **`--plan`** друкує кроки вибраного режиму та виходить без створення робочого дерева або зв’язку з пультом дистанційного керування. Поєднайте його з `--fast`, щоб перевірити швидкий план.
- **`--fast`** запускає загальні статичні ворота, вибрані змінені файли `node:test` у `tests/unit/` та `npm run test:vitest`. Запустіть повну локальну перевірку принаймні раз на день накопиченої підказки в швидкому режимі.
- **Повний режим** додає повні статичні ворота та запускає `npm run test:unit` та `npm run test:vitest`.

Несправний статичний вентиль повторно запускається на недоторканій базі, якщо базовий зонд доступний. Сценарій повідомляє про успадковані помилки та продовжує роботу, коли кожен розпізнаний рядок порушення також з’являється в базі, а загальна кількість не збільшується.

| Вихід | Значення                                                                                                                                                  |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`   | Роздрукував план або завершив сюїту. У підсумку набору наведено всі успадковані статичні збої та видалені PRs.                                            |
| `1`   | Недійсні аргументи, відсутність перевірки Git, помилка попередньої перевірки або відсутність підключення до PR.                                           |
| `2`   | Перевірка набору не вдалася, і він не кваліфікувався як успадкований. Оператор може розділити пакет навпіл, вилучити несправний PR та запустити повторно. |

Місцева перепустка надає діагностичні докази лише для досьє власника. Кожна посадка все ще потребує авторизації власника, власних обов’язкових перевірок і вердикту тіньової черги, якщо це можливо.

## Розрівнювання

- **За PR.** CI і перевірки вибору якості на основі змінених шляхів. Код PRs запускає швидкі шлюзи якості та перевірки впливу з окремими завданнями блоку та Vitest у CI.
- **За кандидата в чергу.** CI та Quality запускають повний профіль для складеного кандидата в його черзі ref.
- **Підказка щодо випуску.** Release-Green запускає швидкі жорсткі ворота за натисканнями, які відповідають його фільтрам шляху. Три заплановані запуску на день використовують повну розгортку для гілки випуску.
- **За випуск.** Повна матриця CI включає фрагменти E2E, перевірку пакетів, завантажувальний файл tarball і перевірки покриття. Перегляньте [контрольний список випуску](RELEASE_CHECKLIST.md).

## Передумови для оновленої перевірки для `merge-train.sh`

Попередня перевірка виконується перед створенням робочих дерев. Встановіть залежності за допомогою `npm ci`. Переконайтеся, що `node_modules/.bin/tsc` є виконуваним і що `node_modules/node_modules` відсутній. Перевірте успішність `node_modules/.bin/bun --version`.

Якщо післяінсталяція Bun була пропущена, запустіть `(cd node_modules/bun && node install.js)`. Узгодженість постачальника та перевірки відомих символів використовують Bun. Валідатор запускає `npm run check:cycles:ratchet` як блокуючий шлюз. Окрема команда `npm run check:cycles` є рекомендаційною.
