OmniRoute має три різні, але пов’язані механізми стійкості. Кожна з них має різні масштаби та призначення. Тримайте їх окремо під час налагодження поведінки маршрутизації.

![3-layer resilience model](../diagrams/exported/resilience-3layers.svg)

> Джерело: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd)

> **Env-vs-dashboard пріоритет для перемикачів стійкості.** Перемикання стійкості під час вибору, заповнені середовищем — `QUOTA_PREFLIGHT_CUTOFF_ENABLED`, `PROVIDER_COOLDOWN_ENABLED`, `STREAM_RECOVERY_ENABLED`, `STREAM_RECOVERY_MIDSTREAM_ENABLED`, `STREAM_THROUGHPUT_WATCHDOG_ENABLED` — дають лише значення _default_ (`DEFAULT_RESILIENCE_SETTINGS`, `src/lib/resilience/settings.ts`). Логічне значення зберігалося в `resilienceSettings` (інформаційна панель →** Налаштування стійкості →** / `PATCH /api/resilience`, що зберігається в `key_value`) перемагає значення env: нормалізація (`toBoolean`, `src/lib/resilience/settings/normalize.ts`) зберігає збережене логічне значення, коли воно існує. Встановлення такої змінної env на `true` у розгортанні, де на інформаційній панелі вже збережено `false` отже, нічого не змінюється — перемикає перемикач** Налаштування стійкості →** (або очистіть збережене поле).

## 1. Автоматичний вимикач провайдера (Provider Circuit Breaker)

**Область дії:** весь провайдер (наприклад, `glm`, `openai`, `anthropic`).

**Призначення:** припинити надсилання трафіку провайдеру, який неодноразово зазнає збоїв на рівні upstream/сервісу.

**Реалізація:**

- Основний клас: `src/shared/utils/circuitBreaker.ts`
- Підключення: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API статусу: `GET /api/monitoring/health`
- API скидання: `POST /api/resilience/reset`
- Обгортки: `open-sse/services/accountFallback.ts`
- Таблиця БД: `domain_circuit_breakers`

**Стани:**

- `CLOSED` — звичайний трафік дозволено
- `DEGRADED` — трафік усе ще дозволено, але відстежуються зростаючі збої провайдера; повертається до `CLOSED` після достатньої кількості успіхів, після успішного тесту з'єднання або після найтривалішого утримання `OPEN` для останнього типу збою (його значення `cooldownByKind`, інакше `resetTimeout`, × `maxBackoffMultiplier`, щонайменше один cooldown) без нового збою
- `OPEN` — провайдера тимчасово заблоковано; комбінована маршрутизація пропускає його
- `HALF_OPEN` — тайм-аут скидання минув; дозволено пробний запит

**Типові значення, що налаштовуються (`open-sse/config/constants.ts`, доступні в Панель керування → Налаштування → Стійкість):**

| Клас    | Деградація після | Відкриття після | Тайм-аут скидання |
| ------- | ---------------- | --------------- | ----------------- |
| OAuth   | 5 збоїв          | 8 збоїв         | 60s               |
| API-key | 7 збоїв          | 12 збоїв        | 30s               |
| Local   | похідне          | 2 збоїв         | 15s               |

`degradationThreshold` визначає, коли провайдер переходить у стан `DEGRADED`; `failureThreshold` визначає, коли він відкривається та пропускається. Профілі локальних провайдерів поки що не відображаються на сторінці налаштувань стійкості.

**Коди спрацьовування:** лише статуси рівня провайдера `[408, 500, 502, 503, 504]`. НЕ спрацьовує для помилок рівня облікового запису (більшість 401/403/429 — вони належать до періоду охолодження або блокування).

**Ліниве відновлення:** коли дія `OPEN` спливає, `getStatus()`, `canExecute()`, `getRetryAfterMs()` оновлюють стан до `HALF_OPEN`. Ті самі зчитування (і наступний збій) повертають застарілий `DEGRADED` назад до `CLOSED`. Фоновий таймер не потрібен.

### Опційний глобальний Provider Cooldown (віконний гейт)

Четвертий, **опційний** шар (`PROVIDER_COOLDOWN_ENABLED`, типово **вимкнено**) зберігає
міжзапитну пам'ять про провайдерів, що зазнають збоїв, у
`open-sse/services/providerCooldownTracker.ts`; її використовує визначення цілей
комбінації, щоб послідовні комбіновані запити не проходили повторно через
провайдера, який щойно зазнав збою. Записи рівня провайдера дотримуються віконного
гейту `PROVIDER_PROFILES`:

| Профіль | спрацьовує після (`providerFailureThreshold`) | протягом (`providerFailureWindowMs`) | охолоджується протягом (`providerCooldownMs`) |
| ------- | --------------------------------------------: | -----------------------------------: | --------------------------------------------: |
| OAuth   |                                          `10` |                              `15min` |                                        `5min` |
| API key |                                          `15` |                              `30min` |                                       `10min` |

Нижче порогу провайдер **не** вважається таким, що охолоджується; успіх очищує
вікно. Записи рівня з'єднання (`provider:connectionId`) натомість зберігають
експоненціальний backoff `minRetryCooldownMs → maxRetryCooldownMs`. Перевизначення:
`OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`.
Захист від регресій: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Період очікування підключення

**Область дії:** одне підключення/обліковий запис/ключ постачальника.

**Мета:** пропустити один недійсний ключ, поки інші підключення цього самого постачальника продовжують обслуговувати запити.

**Реалізація:**

- Позначення як недоступного: `src/sse/services/auth.ts::markAccountUnavailable()`
- Вибір: `getProviderCredentials*` у тому самому файлі
- Обчислення періоду очікування: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Налаштування: `src/lib/resilience/settings.ts`

**Поля для кожного підключення:**

- `rateLimitedUntil` — мітка часу, до якої триває період очікування
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — лічильник експоненційної затримки

**Періоди очікування за замовчуванням:**

- Базовий для OAuth: 5 с
- Базовий для API-ключа: 3 с
- API-ключ, 429: перевага надається upstream-заголовкам `Retry-After`/заголовкам скидання/тексту зі скиданням, який можна розібрати
- Затримка: `baseCooldownMs * 2 ** failureIndex`

**Затримка повторної спроби для постачальника.** На сторінці відомостей про постачальника є список **Retry delay** (Auto, від 15 с до 1 год). Він зберігає значення `resilienceSettings.providerQuotaOverrides[<providerId>].rateLimitCooldownSeconds` (1–21600) через `PATCH /api/resilience`. Якщо помилка обмеження частоти не містить upstream-підказки щодо повторної спроби, це значення замінює масштабовану затримку та скидає `backoffLevel` до 0 (`open-sse/services/rotationConfig.ts::overrideFor`). Пріоритети для помилки обмеження частоти, від найвищого до найнижчого: upstream-підказка щодо повторної спроби, потім `providerSpecificData.rotationOverrides.rateLimitResetSeconds` для підключення, потім затримка повторної спроби для постачальника, потім `OMNIROUTE_ROTATION_RATE_LIMIT_RESET_SECONDS` із середовища, потім масштабована затримка. Auto видаляє поле. Це впливає лише на причину обмеження частоти, а не на кінцеві стани.

**Захист від ефекту стада:** запобігає тому, щоб одночасні помилки надмірно продовжували період очікування або двічі збільшували `backoffLevel`.

**429 через обмеження паралельності не підвищують рівень затримки.** `429`, тіло якого повідомляє про обмеження паралельності ("too many concurrent requests", "concurrency limit", "parallel request limit", GLM `并发数过高`), означає, що обліковий запис справний, але зайнятий. `checkFallbackError()` повертає причину `concurrency_limited`: негайно перемкнутися на наступне підключення, призупинити це підключення на фіксований час `CONCURRENCY_LIMIT_COOLDOWN_MS` (1 с) або до upstream-підказки щодо повторної спроби, залишити `backoffLevel` без змін і встановити `skipProviderBreaker`. Явне тіло про квоту має перевагу, тому тіло, яке також відповідає шаблону квоти, залишається вердиктом щодо квоти. Виявлення: `looksLikeConcurrencyLimit()` у `src/shared/utils/classify429.ts`; вердикт: `open-sse/services/accountFallback/concurrencyLimit429.ts`. `classify429()` (значення `FailureKind` автоматичного розмикача) не змінюється й продовжує повертати `rate_limit` для таких тіл.

**Зависання вмісту потоку не призупиняють обліковий запис.** Коли сторожовий таймер зависання вмісту (`open-sse/utils/streamHandler.ts`) припиняє очікування потоку, який вчасно не надіслав жодного виводу моделі, `markAccountUnavailable()` записує помилку для підключення, але не встановлює період очікування: зависання належить цьому запиту й найчастіше спричинене тривалим етапом міркування без виводу. Оператори можуть увімкнути цю поведінку через `resilienceSettings.streamStallCooldown.enabled` (типово `false`).

**Необов’язковий сигнал затримки для вибору облікового запису `p2c`.** Кожна спроба, що передається на виконання, записує час до першого байта та результат для кожного підключення (а також для кожної пари підключення + моделі) у ковзному вікні в пам’яті: останні 20 зразків за 15 хвилин (`open-sse/services/connectionLatencyTracker.ts`, записуються з `safeLogEvents()` у `src/sse/handlers/chatHelpers.ts`). Коли значення `resilienceSettings.p2cLatency.weight` перевищує `0` (діапазон 0–20, типове значення `0` = вимкнено), `compareP2CConnections()` у `src/sse/services/auth.ts` додає до кожного кандидата в парі до `weight` балів. Половина цього значення походить від затримки як співвідношення з швидшим кандидатом (удвічі повільніший кандидат отримує всю половину), а друга половина — від частоти помилок у ковзному вікні. Цей показник застосовується лише тоді, коли обидва кандидати мають щонайменше 3 зразки, тому нові облікові записи не штрафуються, а його верхня межа залишається нижчою за штрафи за заблоковану та вичерпану квоту. Він не створює окремого автоматичного вимикача: облікові записи з помилками й надалі обробляються рівнями періоду очікування, блокування та автоматичного розмикача. Установіть його через `PATCH /api/resilience` `{ "p2cLatency": { "weight": 10 } }`.

**Кадри міркування перезапускають бюджет зависання вмісту.** Модель міркування може думати кілька хвилин до появи першого видимого токена: Claude передає кадри `thinking_delta`, текст міркування в яких може бути порожнім, а Responses API передає один елемент міркування за іншим. `isReasoningProgressFrame()` (`open-sse/utils/streamReadiness.ts`) розпізнає ці кадри, і сторожовий таймер перезапускає свій бюджет після кожного з них замість скасування етапу. Вони все ще не є виводом моделі, тому етап, що завершується лише міркуванням, і надалі повідомляється як порожній, а етап, у якому міркування припиняється й надсилаються лише сигнали активності, усе одно активує сторожовий таймер.

Двійкові кадри Kiro `reasoningContentEvent` із непорожнім підписом зберігають цю активність міркування через виконавець як порожню дельту `reasoning_content`. Підпис не передається далі. Метадані, неповні кадри та порожні підписи не перезапускають бюджет вмісту; незалежний тайм-аут активного потоку та скасування клієнтом усе одно діють (`open-sse/executors/kiro/reasoning.ts`).

**Кінцеві стани (НЕ періоди очікування):**

- `banned` — встановлюється виявленням забороненого ключового слова або блокуванням облікового запису (див. [BAN_DETECTION](../security/BAN_DETECTION.md)). Відмови upstream для окремого запиту (`request_rejected`, наприклад Anthropic OAuth 403 "Request not allowed") ніколи його не встановлюють: вони рахуються для кожного підключення та моделі й вилучають цю модель із ротації зі зростаючим періодом очікування, обмеженим `REQUEST_REJECTED_MAX_COOLDOWN_MS` (1 год), або призупиняють підключення, якщо модель невідома — `open-sse/services/requestRejectedStreak.ts`
- `expired` (переходить до кінцевого стану після обмеженої кількості повторних спроб — `EXPIRED_RETRY_MAX = 3` з експоненційною затримкою — щоб тимчасові помилки OAuth могли самостійно виправитися до остаточної деактивації облікового запису)
- `credits_exhausted`

Ці стани зберігаються, доки облікові дані не зміняться або оператор не скине їх. Не перезаписуйте термінальні стани тимчасовим станом періоду охолодження.

**Ліниве відновлення:** коли час `rateLimitedUntil` минув, з’єднання знову стає доступним. Після успішного використання `clearAccountError()` очищає всі поля помилок.

### Обмеження використання Claude OAuth: канал із нижчим пріоритетом + скидання ліміту сеансу

**Область застосування:** одне з’єднання з підпискою Claude (OAuth). Обидві функції є **необов’язковими для кожного з’єднання** (Редагувати з’єднання → розділ Claude → `lowPriorityMode` / `autoLimitReset` у `providerSpecificData`, обидві за замовчуванням вимкнені) і відтворюють команди Claude Code `/low-priority` та `/limit-reset` (мережевий контракт зафіксовано в Claude Code 2.1.263).

**Реалізація:**

- Машина станів і класифікація відповідей: `open-sse/services/claudeLowPriority.ts`
- Клієнт стану/запиту на скидання: `open-sse/services/claudeLimitReset.ts`
- Хук виконавця (вставка заголовка + повторна спроба для того самого облікового запису): `open-sse/executors/base.ts::execute()`
- Збереження opt-in: `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**Тригер:** 5-годинне обмеження використання — відповідь `429`, заголовки якої містять
`anthropic-ratelimit-unified-status: rejected` і, коли обліковий запис доступний,
`anthropic-ratelimit-unified-slow-offer: treatment`. До першої відповіді `429` через це обмеження нічого не надсилається; пікова відповідь `429` без уніфікованих заголовків проходить звичайним шляхом періоду охолодження.

**Канал із нижчим пріоритетом** (`lowPriorityMode`):

- Після відповіді `429` через обмеження виконавець приймає пропозицію та негайно повторює запит до **того самого** облікового запису з `anthropic-usage-limit: slow`; канал залишається активним до оголошеного `anthropic-ratelimit-unified-reset` (+ 60 с пільгового часу), і кожен запит у цей період містить цей заголовок. Перехоплена відповідь `429` не потрапляє до `handleChatCore`, тому з’єднання **не** переводиться в період охолодження й не перемикається на інше.
- `anthropic-ratelimit-unified-slow-status` у наступних відповідях: `active` / `not_needed` зберігають канал; `slot_busy` (429) або `529` очікують значення `anthropic-ratelimit-unified-slow-retry-after`, наданого сервером (типове значення 20 с, обмеження 5–600 с, випадкове відхилення ±30%), і повторюють запит, але не довше за `anthropic-ratelimit-unified-slow-max-wait` (типове значення 20 хв, обмеження 1 хв–6 год) — після цього канал завершується, а 10-хвилинний період охолодження блокує повторне прийняття. Очікування додатково обмежується часом, що залишився до власного тайм-ауту початку upstream-запиту (`resolveFetchStartTimeout`, типово 10 хв), за винятком 5 с: без цього обмеження типове максимальне очікування 20 хв перевищило б тривалість запиту, а сон було б перервано посеред очікування, що спричинило б `TimeoutError` замість коректного завершення `max_wait` і періоду охолодження.
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, перехід 5-годинного вікна або `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (що завершує його як `extra_usage` за будь-якого статусу, оскільки платне перевищення тепер покриває це обмеження) завершують канал; після цього відповідь проходить звичайним шляхом періоду охолодження. `budget_exhausted` запам’ятовується до оголошеного скидання бюджету (≤ 8 днів).
- Перевірка обмеження виконується після власних повторних спроб виконавця через `400` у межах однієї спроби (редагування контексту, обмеження thinking/effort, автоматичне навчання параметрів), тому відповідь `429` через обмеження, яка виникла лише під час однієї з таких повторних спроб, усе одно перехоплюється, а не потрапляє до шляху періоду охолодження.
- Стан зберігається в пам’яті для кожного з’єднання (після перезапуску потрібна ще одна відповідь `429` через обмеження, щоб повторно прийняти пропозицію).

**Скидання ліміту сеансу** (`autoLimitReset`, виконується перед каналом, якщо ввімкнено обидві функції):

- `GET https://api.anthropic.com/api/oauth/usage?at_wall=1&skip_spend=1` → блок `juniper_tide`; якщо `arm: "reset"` і `available: true`,
  `POST https://api.anthropic.com/api/organizations/{orgUUID}/reset_rate_limits` із
  `{ "program": "juniper_tide" }` (UUID організації з `providerSpecificData.organizationUUID`, резервне значення з bootstrap).
- `result: reset|not_limited` → запит повторюється на повній швидкості (без заголовка slow).
  `already_used` / `not_offered` запам’ятовують `next_available_at` (типове значення — один тиждень); після будь-якої помилки виконується відкладена повторна спроба на 15 хвилин. Скидання виконується раз на тиждень і все одно враховується в тижневому ліміті.

Регресійні перевірки: `tests/unit/claude-low-priority-mode.test.ts`,
`tests/unit/claude-limit-reset.test.ts`, `tests/unit/claude-low-priority-executor.test.ts`.

### Прив’язка сеансу (#7274)

**Область застосування:** один клієнтський сеанс (заголовок `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session`) закріплюється за одним з’єднанням для **будь-якого** провайдера.

**Призначення:** зберігати багатоетапного агента (Claude Code, aider, власні агенти) в тому самому обліковому записі між запитами, зменшуючи втрату контексту через зміну облікового запису та повторні пікові відповіді `429` під час холодного запуску для провайдерів зі станом сеансу на рівні облікового запису.

**Реалізація:**

- Визначення TTL: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Вибір/створення прив’язки: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Витягування заголовка (універсально, для будь-якого провайдера): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Таблиця збережених прив’язок: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Налаштування: `sessionAffinityTtlMs` (глобальний TTL у мс, `0` вимикає функцію) — `src/lib/db/settings.ts`. Перейменовано з призначеного лише для Codex `codexSessionAffinityTtlMs` міграцією `124_generic_session_affinity_ttl.sql`, яка переносить будь-який раніше налаштований TTL Codex як нове значення за замовчуванням.

До #7274 `resolveSessionAffinityTtlMs()` безумовно повертав `0` для кожного провайдера, крім `codex`, тому налаштування TTL (і заголовки сеансу) ніде більше не діяли, хоча механізм прив’язки та витягування заголовків уже не залежали від провайдера. Виправлення усунуло це раннє повернення; тепер TTL однаково застосовується до кожного провайдера, якщо його глобально встановлено вище за `0`.

Три заголовки прив’язки сеансу ніколи не пересилаються upstream — виконавці створюють власні upstream-заголовки з нуля, а не передають клієнтські заголовки, тому цей ідентифікатор залишається лише внутрішнім ідентифікатором кореляції.

### Ексклюзивні оренди керованих з’єднань сеансу

**Область дії:** один активний керований HTTP-клієнт/сеанс володіє одним придатним з’єднанням OmniRoute.

**Мета:** забезпечити довговічне ексклюзивне володіння з’єднанням для клієнтів, яким потрібен жорсткий
бар’єр маршрутизації між запитами. Це відрізняється від прив’язки до сеансу, яка є м’якою перевагою
безперервності: ексклюзивна оренда зберігає стан життєвого циклу в SQLite, забезпечує глобальну
унікальність активного власника й активного з’єднання та відхиляє застаріле покоління до передавання
запиту провайдеру.

Функція вмикається окремо для кожного API-ключа. Керований ключ повинен мати область дії
`lease:exclusive` і явний непорожній список `allowedConnections`. Будь-який HTTP-клієнт може
використовувати кінцеву точку життєвого циклу; ім’я клієнта, user-agent, провайдер, метод OAuth або
модель не потрібні. Оренда володіє з’єднанням, а не моделлю, тому зміна моделі зберігає прив’язку,
доки з’єднання залишається звичайно придатним. Звичайні правила моделі, квоти, працездатності,
періоду охолодження та списку дозволених підключень залишаються пріоритетними й можуть перевести те
саме покоління на інше вільне придатне з’єднання.

Життєвий цикл представлений як `POST /api/v1/session-leases` із діями JSON `acquire`, `renew` і
`release`. Керовані запити на виконання інференсу передають непрозоре значення
`X-OmniRoute-Lease-Owner` і точне значення `X-OmniRoute-Lease-Generation`. Власник використовує
префікс `vlo_`, за яким ідуть 43 символи base64url; зберігається лише його хеш SHA-256. Кожен
остаточний бар’єр передавання запиту також прив’язує ідентифікатор автентифікованого API-ключа та
ідентифікатор активного з’єднання. Керувальні заголовки оренди видаляються з журналів, збережених
знімків запитів і заголовків виконавця на стороні провайдера.

Якщо звичайна маршрутизація має придатних керованих кандидатів, але кожен вільний кандидат зайнятий
чужою активною орендою, OmniRoute повертає HTTP `429`, код lease-capacity-unavailable, стан
waiting-for-capacity і обмежений заголовок `Retry-After`, обчислений на основі найранішого відповідного
терміну завершення. Звичайна відсутність придатних кандидатів не є конкуренцією за оренду й зберігає
наявну семантику помилок маршрутизації.

Пов’язані механізми залишаються окремими:

- Зайнятість сеансів OAuth — це локальний для процесу м’який розподіл між обліковими записами OAuth.
- Семафори облікових записів надають дозволи на паралельне виконання запитів і завершуються після завершення запиту.
- Ексклюзивні оренди керованих сеансів — це довговічне володіння в межах життєвого циклу з бар’єром покоління.

## 3. Блокування моделі

**Область дії:** трійка «постачальник + підключення + модель».

**Область ключа за статусом:** статус помилки визначає, у яку область записується блокування
(`resolveLockoutScope()` у `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — сигнал квоти або доступу — блокувати **сімейство квот**:
  для codex — усю область `codex` / `spark` (кожну модель `gpt-5*` цього
  підключення), для інших постачальників — `getQuotaScopedModelForProvider()`.
- `404` блокує базову модель (`getModelLockKey()` звужує `not_found`).
- Будь-який інший статус — помилки транспорту/сервера `5xx` і власний
  синтезований OmniRoute `502` після перевірки якості — блокує лише **точну**
  кортежну комбінацію «постачальник/підключення/модель». Невдалий потік для однієї
  моделі не є доказом проблеми з квотою облікового запису; до появи цього правила
  одна порожня відповідь для `codex/gpt-5.6-luna` вилучала з маршрутизації кожну модель
  `gpt-5*` цього підключення на 2–30 хв (із поступовим збільшенням), тоді як його квота
  залишалася незмінною.
- Явно вказаний викликачем параметр `scope` завжди має пріоритет (Antigravity передає `"exact"`).

**Мета:** уникати вимкнення всього підключення, коли недоступна або обмежена квотою лише одна модель.

**Приклади:**

- Постачальники з поквотною моделлю, які повертають 429
- Локальні постачальники, які повертають 404 для однієї відсутньої моделі
- Помилки дозволів для певного режиму/моделі постачальника (наприклад, режими Grok)

**Реалізація:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

### Панель керування періодами охолодження моделей (v3.8.0)

Інтерфейс: Налаштування → Періоди охолодження моделей (`src/app/(dashboard)/dashboard/settings/components/ModelCooldownsCard.tsx`)

Містить список активних блокувань із такими даними: постачальник, підключення, модель, причина, expiresAt. Оператори можуть вручну повторно ввімкнути модель із картки.

**REST API:**

- `GET /api/resilience/model-cooldowns` — список активних блокувань
- `DELETE /api/resilience/model-cooldowns` — повторне ввімкнення вручну. Тіло: `{provider, connection, model}`. Автентифікація: management.

### Менеджер періодів охолодження

Інтерфейс: Моніторинг → Менеджер періодів охолодження (`src/app/(dashboard)/dashboard/resilience/cooldowns/`).

Одна сторінка для кожного підключення, яке вилучене з маршрутизації через тимчасову причину, замість
відкриття сторінки кожного постачальника. На ній відображаються періоди охолодження підключень,
блокування моделей і термінальні стани; їх можна очищати для окремого підключення,
вибраних підключень або всіх підключень постачальника, а також редагувати найважливіші правила
періодів охолодження: `streamStallCooldown.enabled` і базовий період охолодження
`connectionCooldown` для OAuth / ключа API та максимальну кількість кроків збільшення затримки
(зберігається через `PATCH /api/resilience`). Термінальні стани (`banned`, `expired`, `credits_exhausted`) тут
відображаються, але ніколи не очищаються.

Картка **Правила періодів охолодження для помилок** на цій самій сторінці редагує правила помилок оператора
(`settings.providerErrorRules`) і стандартні загальні правила для кожного постачальника
(`settings.providerErrorDefaults`) через `PATCH /api/settings` — див. розділ «Правила,
оголошені оператором» у §7, де описано принцип їх зіставлення. Тривалість: стандартна (без явного
періоду охолодження), 30 хв, 1 год, 5 год, 24 год або спеціальна — від 1 до 43 200 хвилин (30 днів).

**REST API** (`src/lib/resilience/cooldownManager.ts`, автентифікація: management):

- `GET /api/resilience/cooldowns[?provider=]` — підключення зі статусом, залишковим періодом охолодження,
  рівнем збільшення затримки, типом останньої помилки та блокуваннями моделей (без облікових даних)
- `POST /api/resilience/cooldowns` — тіло `{connectionIds: string[]}` або
  `{all: true, provider?}`; повертає `{cleared, unchanged, skippedTerminal, lockoutsCleared}`

### Інтерфейс налаштувань блокування моделей + відновлення зі зменшенням після успішних відповідей (v3.8.23)

Блокування моделей перетворилося з постійно ввімкненої жорстко закодованої поведінки
на повністю налаштовувану функцію, яку потрібно явно ввімкнути, із власною карткою налаштувань
і механізмом самовідновлення.

**Картка налаштувань:** Налаштування → Блокування моделі
(`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`).
Це **окрема** картка від доступної лише для читання `ModelCooldownsCard` вище (вона лише
_перелічує_ активні блокування) — нова картка _налаштовує параметри_. Стандартні значення
зберігаються в `DEFAULT_MODEL_LOCKOUT_SETTINGS`
(`src/lib/resilience/modelLockoutSettings.ts`):

| Налаштування            | Стандартне значення              | Значення                                                                |
| ----------------------- | -------------------------------- | ----------------------------------------------------------------------- |
| `enabled`               | `false`                          | Головний перемикач — блокування моделей **типово вимкнено**.            |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Статуси upstream, які вважаються помилкою в області моделі.             |
| `baseCooldownMs`        | `120_000` (120 с)                | Початкова тривалість блокування після першої помилки.                   |
| `maxCooldownMs`         | `1_800_000` (30 хв)              | Максимальна тривалість збільшеного періоду охолодження.                 |
| `maxBackoffSteps`       | `10`                             | Максимальна кількість кроків експоненційного збільшення.                |
| `useExponentialBackoff` | `true`                           | Чи мають повторні помилки експоненційно збільшувати період охолодження. |

Налаштування зберігаються через звичайне сховище налаштувань і перевіряються за схемою
налаштувань стійкості; картка обмежує `baseCooldownMs`/`maxCooldownMs`
(з умовою `maxCooldownMs ≥ baseCooldownMs`) і `maxBackoffSteps`.

**Відновлення зі зменшенням після успішних відповідей:** відновлення відбувається **не лише**
після завершення таймера. Здорова відповідь зменшує лічильник помилок моделі, тому модель,
яка відновилася в середині вікна, припиняє збільшувати період охолодження (і розблоковується)
раніше, ніж завершиться її таймер. Після успішного цільового комбо
`open-sse/services/combo.ts` викликає `decayModelFailureCount()`
(`open-sse/services/accountFallback.ts`), яка **ділить навпіл** збережений
`failureCount` (`Math.floor(failureCount / 2)`); коли він досягає `0`, запис блокування
повністю видаляється. Відповідна функція `recordModelLockoutFailure()`
збільшує лічильник (і збільшує період охолодження) для помилок у межах вікна ескалації. Це
зменшення після успішних відповідей доповнює звичайне завершення таймера —
будь-який із цих шляхів може повторно ввімкнути модель.

**Стан:** блокування зберігаються **в пам’яті** (у `Map` для кожного процесу, з
`ModelLockoutEntry`, ключами яких є `provider:connectionId:model`, а для блокувань
у точній області дії — `provider:connectionId:exact:model`), а не в
БД — після перезапуску вони втрачаються. _Налаштування_ зберігаються; активний
_стан_ блокування є ефемерним.

## 4. Керування паралелізмом на основі спільної квоти (v3.8.36)

Облікові записи підписок (GLM, MiniMax тощо) часто приймають лише ~1–3 одночасні
запити; перевищення цього обмеження спричиняє 429 і періоди охолодження. Особливо
гостро це проявляється для комбінацій **quota-share** (`qtSd/…`), де кілька API-ключів
спільно використовують один обліковий запис у висхідній системі. Три рівні
запобігають перевантаженню спільного облікового запису.

### Обмеження паралелізму для підключення (`max_concurrent`)

Кожне підключення провайдера може оголосити максимальне значення
`max_concurrent`
(`provider_connections.max_concurrent`, яке задається у вікні підключення / API / БД).
Залиште поле порожнім, щоб не встановлювати обмеження. Це єдиний параметр, який
керує наведеним нижче рівнем серіалізації — встановіть його відповідно до фактичного
паралелізму облікового запису (наприклад, для GLM ~1, для MiniMax ~2).

### Обмеження паралелізму для моделей (`modelConcurrency`)

Підключення також може оголосити точні обмеження паралелізму для окремих моделей
у своїй мапі `rateLimitOverrides`:

```json
{
  "rateLimitOverrides": {
    "maxConcurrent": 4,
    "modelConcurrency": { "glm-5": 1, "glm-4.7": 3 }
  }
}
```

Задайте це у вікні підключення (**Rate limit overrides → Per-model
concurrency caps**, по одному `model=cap` у рядку) або через
`PATCH /api/providers/[id]` із такою самою структурою JSON. Основні правила:

- **Загальне для підключення та специфічне для моделі:** `maxConcurrent` залишається
  спільним обмеженням для всього підключення. Якщо застосовуються обидва обмеження,
  обидва шлюзи захоплюються атомарно в одному складеному шлюзі
  (`global → provider → account → model`); фактична поведінка визначається
  суворішим застосовним обмеженням.
- **Точна відповідність ключа моделі:** ключ — це рядок моделі, переданий виконавцю
  після визначення маршруту, зазвичай базовий ідентифікатор моделі у висхідній системі
  (`glm-5`), а не псевдонім `provider/model` на боці клієнта (`zai/glm-5` не
  відповідає `glm-5`). Значення — додатні цілі числа, що задають максимальну кількість
  одночасних запитів.
- **Локальна постановка в чергу, без виявлення:** надлишкові запити стають у локальну
  чергу з наявною семантикою черги/тайм-ауту (типізовані помилки допуску
  `SEMAPHORE_TIMEOUT` / `SEMAPHORE_QUEUE_FULL`). OmniRoute не виявляє та не виводить
  політику висхідної системи — він застосовує точні обмеження, налаштовані оператором.
  Насичений шлюз моделі ніколи не вимикає провайдера й не створює постійного
  блокування моделі; поведінка щодо 429/охолодження/резервного маршруту у висхідній
  системі залишається резервним механізмом обробки помилок.
- **Область дії для кожного підключення та процесу:** обмеження діють для кожного
  підключення до бази даних і зберігаються в пам’яті, тому два підключення, що повторно
  використовують той самий API-ключ висхідної системи, не координують роботу між собою.
- **Неналаштоване значення означає відсутність змін:** пропуск мапи (або порожнє поле
  на інформаційній панелі) не додає шлюзу моделі. Приклад конфігурації без
  встановлення універсального обмеження для провайдера:

```text
glm-5=1
glm-4.7=3
```

### Серіалізація запитів quota-share

Коли диспетчеризація quota-share спрямована на підключення, для якого оголошено додатне
значення `max_concurrent`, одночасні запити до цього **облікового запису** серіалізуються
через семафор для кожного підключення (ключ `qsconn:<connectionId>`): надлишкові запити
**очікують у черзі**, а не перевантажують обліковий запис. Це працює в режимі
**fail-open** — насичена черга або тайм-аут продовжує виконання без слота й ніколи не
відхиляє запит, який можна диспетчеризувати. Увімкнути параметр можна в
**Settings → Resilience → Quota-share per-connection
concurrency** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, типово
увімкнено). Без обмеження `max_concurrent` поведінка не змінюється.

> Шлюз маршрутизації quota-share (`selectQuotaShareTarget`, DRR + P2C) сам працює в режимі
> fail-open і лише _знижує пріоритет_ підключення, яке досягло обмеження. Якщо в пулі
> лише одне підключення, він не може встановити жорстке обмеження, тож саме цей семафор
> фактично стримує перевантаження.

### Повторна спроба комбінації з урахуванням періоду охолодження

Для кожної стратегії комбінацій (якщо її ввімкнено) запит, який призвів би до 429
через КОРОТКИЙ перехідний період охолодження, очікує його завершення та повторно
диспетчеризується замість повернення 429. Це охоплює вікна TPM/RPM класу Gemini
(приблизно 60 с до повторної спроби) у комбінаціях із кількома моделями, наприклад
коли обидві цілі комбінації з двох моделей досягають обмеження частоти запитів для
моделі. Поведінка обмежується `comboCooldownWait` (`enabled`, `maxWaitMs`, `maxAttempts`,
`budgetMs`) у **Settings → Resilience**. Очікування ніколи не виконується для
`quota_exhausted` (заблоковано до опівночі) або причин, пов’язаних з автентифікацією чи
відсутністю.

Комбінація може відмовитися від цієї функції за допомогою
`config.comboCooldownWaitEnabled: false`. Лише літеральне значення `false` вимикає ці
спільні очікування комбінацій (охолодження після диспетчеризації та очікування
розімкненого автоматичного вимикача/блокування моделі перед диспетчеризацією), а також
розширення нижньої межі тайм-ауту очікування. Відсутнє значення або `true` зберігає
глобальну політику; `true` не може ввімкнути глобально вимкнене очікування. Явно
вказане `targetTimeoutMs` має вищий пріоритет. Ця відмова не змінює окреме
переддиспетчеризаційне очікування native-Codex для фіксації ходу.

Той самий шлюз охоплює випадок перед диспетчеризацією (#16319): коли кожна ціль
комбінації пропускається ще до першої спроби, оскільки її модель перебуває в короткому
перехідному блокуванні, шлях із нульовою кількістю спроб очікує завершення блокування
за тими самими обмеженнями та повторно диспетчеризує запит, замість повернення
`503 ALL_TARGETS_SKIPPED` без підказки. Коли очікування заборонене (досягнуто
обмеження, вичерпано кількість спроб або бюджет, чи функцію вимкнено), кінцева
відповідь змінюється на `429 rate_limit_error` і містить `retry_after` / `reset_at`
для найранішого завершення перехідного блокування; блокування квоти, автентифікації
та відсутності продовжують повертати 503 без підказки.

```text
#16319 · comboCooldownWait · pre-dispatch (attempts = 0)
all targets skipped + transient model lockout:
  enabled ∧ 0 < waitMs ≤ maxWaitMs ∧ attempt < maxAttempts ∧ budgetLeftMs ≥ waitMs
    → wait → re-dispatch
  wait = false → HTTP 429 rate_limit_error
  retry_after / reset_at ← earliest transient lock expiry
quota_exhausted / auth_error / not_found / not_found_local:
  no transient hint → HTTP 503 ALL_TARGETS_SKIPPED
```

## 5. Контроль прийому у чергу запитів (v3.8.49 · issue #6593)

**Область дії**: локальна черга обмеження частоти запитів для кожного провайдера+з'єднання (`open-sse/services/rateLimitManager.ts`, на основі Bottleneck), один рівень нижче трьох механізмів вище.

**`maxWaitMs` обмежує очікування в черзі; `executionMaxWaitMs` обмежує виконання.**
Ці два параметри навмисно розділені, і жоден не живить іншого.

`resilienceSettings.requestQueue.maxWaitMs` — це **бюджет очікування в черзі**: він
покриває очікування слота провайдера, а потім перебування у стані QUEUED, і його таймер
зупиняється в момент, коли завдання виходить зі стану QUEUED і починає виконуватися
(`rateLimitManager.ts`, `wrappedFn`). Запит, що перевищив його, ніколи не досягає
виконання. Типово 30000 мс, задається `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS`
у `src/lib/resilience/settings.ts` і фіксується тестом
`tests/unit/ratelimit-admission-control-6593.test.ts`, тому зміна цього значення зробить
цей тест червоним, а не залишить цей абзац тихо застарілим.

`resilienceSettings.requestQueue.executionMaxWaitMs` — це те, що Bottleneck
отримує як `expiration` завдання, чий таймер запускається лише після відправлення. Це
запобіжник для виконавців без власного таймауту до джерела даних, і його
підвищують до власного таймауту початку завантаження виконавця, коли той довший, тому він
не може обірвати здорову відповідь у польоті. Типово 600000 мс (10 хв).

Саме підмішування бюджету черги в `expiration` колись вбивало неінкрементні
шлюзи посеред польоту — вони легітимно працюють хвилинами до перших байтів —
і тому термін дії позначається як `code:
"RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504), тоді як бюджет черги несе
код таймауту черги. Будь-який з них перевизначається через `RATE_LIMIT_MAX_WAIT_MS` /
`RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (змінні середовища) або панель керування
(**Settings → Resilience**). Обидва обмежуються діапазоном 1 мс–24 год під час нормалізації.

**Пріоритет, для обох:** змінна середовища задає лише _типове_ значення. Значення,
збережене в `resilienceSettings.requestQueue` (патч через панель керування / API, зберігається
в `key_value`), перемагає його, а `rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` для
конкретного з'єднання перемагає те. Отже, встановлення
змінної середовища на розгортанні, яке вже має збережене значення, нічого не
змінює — натомість очистіть або оновіть збережене налаштування.

Перебування в черзі обмежується `maxWaitMs`; `maxQueueDepth` нижче обмежує, скільки
викликачів можуть бути в черзі одночасно.

**Повтори, заявлені в тілі відповіді: темпування проти блокування.** Тіло 429 може назвати власне очікування
(Gemini `RetryInfo.retryDelay`, текст "retry after Ns"), яке
читає `updateFromResponseBody`. Очікування, що вміщується в `maxWaitMs`
з'єднання — це темпування: обмежувач спустошує свій резервуар на цей час, і виклики
в черзі відправляються, коли він заповнюється. Очікування довше за `maxWaitMs` — це не те, що
черга може висидіти — Gemini відповідає на вичерпану денну квоту
`retryDelay: "86399s"`. Ретрансльований `Retry-After` на перебудованій відповіді 429 (#16528)
вже змушує рушій резервування блокувати модель на це вікно, але призупинення
обмежувача на нього теж все одно загальмувало б будь-який виклик, що досягає ключа рано
(після скидання стійкості, наприклад), на весь `maxWaitMs`. Коли таке очікування надходить від типізованої деталі Google `RetryInfo`
(походження `google_rpc_retry_info`) і обмежувач ключа
вже обмежений моделлю (див. `getLimiterKey`), відповідь 429 стає натомість
блокуванням моделі на цьому з'єднанні (`lockModelForLongBodyRetry` у
`open-sse/services/rateLimitManager/bodyRetryPause.ts`, обмежене 24 год), а
обмежувач залишається непризупиненим. Вибір облікового запису пропускає це блокування через
`isModelLocked()`, і так само комбінований контроль перед відправленням для цілей, прив'язаних до
з'єднання. На antigravity, чий обмежувач діє за сімейством квот, блокування
стається для конкретної моделі, як і його інші блокування квот. Ім'я, яке запитував клієнт,
також блокується, коли псевдонім розв'язав його до цієї моделі, бо ці перевірки використовують
запитуване ім'я; воно блокується точно (`lockExactModel`), тому псевдонім, що
перетинає сімейство квот antigravity або область codex, ніколи не блокує своє.
Прозова підказка, нетипізований `retryDelay` або
обмежувач, спільний для всього з'єднання, зберігають призупинення. Коли обмежувач, який щойно
перебудував шлях 429, дійсно призупиняється, викликач, чий залишок часу в черзі закінчується
до кінця призупинення, відхиляється одразу з кодом таймауту черги
(`checkLimiterPause`) замість того, щоб чекати цей час; записаний кінець
закріплюється до побудови обмежувача, там, де Bottleneck запускає свій годинник
оновлення, і будь-яка пізніша зміна резервуару його забуває. Покрито
`tests/unit/rate-limit-long-body-retry-lockout.test.ts` та
`tests/unit/rate-limit-body-retry-pause.test.ts`.

**`maxQueueDepth` — необов'язкове обмеження прийому (нове).** `resilienceSettings.requestQueue.maxQueueDepth`
обмежує, скільки запитів можуть перебувати в черзі (ще не відправлені) для одного
провайдера+з'єднання одночасно. Коли черга вже містить `maxQueueDepth`
запитів, новий запит швидко відхиляється з типізованою
помилкою `code: "RATE_LIMIT_QUEUE_FULL"` **до** того, як він взагалі досягає `limiter.schedule()`
— тому відхилення дешеве і відбувається перед будь-якою подальшою роботою з
стиснення запиту / перекладу для цього запиту. Типово `0` =
вимкнено, що зберігає існуючу поведінку необмеженої черги; обмежене 0–100000.
Перевизначення через `RATE_LIMIT_MAX_QUEUE_DEPTH` (змінна середовища) або
`resilienceSettings.requestQueue.maxQueueDepth` (патч через панель керування/API).

Сама перевірка прийому — чиста функція
(`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), тому
її можна модульно тестувати без реального обмежувача Bottleneck.

> RFC, який відкрив #6593, також пропонував прапорець
> `bypassCompressionOnRateLimit`. Пайплайн `open-sse/services/compression/`
> цього репозиторію — це стиснення промпту/контексту у вихідному запиті до
> LLM (`chatCore.ts`, приблизно навколо блоку
> `resolveCompressionSettings`/`selectCompressionStrategy`), а не
> HTTP-стиснення відповідей для синтезованих тіл 429 — відповідного шляху в
> коді для буквального прапорця обходу не існує. Цей крок стиснення промпту
> також наразі виконується _до_ `withRateLimit()` у пайплайні запитів, тому
> перевпорядкування для його пропуску під час відхилення через переповнення
> черги — це окрема, масштабніша зміна, ніж обсяг цього issue; вона навмисно
> **не** була реалізована тут і залишена як подальша робота на випадок, якщо
> виграш у економії CPU вартий ризику перевпорядкування.

### Захисна сітка автоматичного вмикання обмеження частоти запитів і захист з'єднання (`rateLimitProtection`)

**Захисна сітка автоматичного вмикання** (`resilienceSettings.requestQueue.autoEnableApiKeyProviders`, типово `true`):
Типово OmniRoute автоматично вмикає захист чергою обмеження частоти запитів для всіх активних з'єднань провайдерів з API-ключами (`getProviderCategory(provider) === "apikey"`). Це гарантує, що вхідні запити до апстрімових API-ключів, чутливих до частоти, ставляться в чергу та дроселюються через Bottleneck, а не викликають сплески апстрімових помилок 429. Захисну сітку можна перевизначити через змінну середовища `RATE_LIMIT_AUTO_ENABLE` (`false`/`0`/`off` — вимикає, `true`/`1`/`on` — примусово вмикає), яка має пріоритет над збереженим налаштуванням панелі керування (**Налаштування → Відмовостійкість** / `PATCH /api/resilience`).

**Семантика `rateLimitProtection` для окремого з'єднання:**
Захист обмеження частоти запитів для окремого з'єднання відстежується через булеве поле `rateLimitProtection` у з'єднаннях провайдерів (зберігається як `rate_limit_protection` у SQLite):

- **Явно увімкнено (`rateLimitProtection === true`)**: захист обмеження частоти запитів явно ввімкнено для цього з'єднання, незалежно від категорії провайдера чи того, чи активна захисна сітка автоматичного вмикання.
- **Явно вимкнено (`rateLimitProtection === false`)**: вимикає явний захист, але **не** виводить активне з'єднання з API-ключем з-під дії глобальної захисної сітки автоматичного вмикання. У `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значення `false` та `undefined` еквівалентні: лише `rateLimitProtection === true` розглядається як явне перевизначення. Якщо `rateLimitProtection` дорівнює `false` (або не встановлено), активне з'єднання з API-ключем усе одно відповідає умові автоматичного вмикання та залишається захищеним обмеженням частоти запитів.
- **Відсутність відмови для окремого з'єднання**: оператор наразі не може виразити «це конкретне активне з'єднання з API-ключем має працювати без захисту чергою обмеження частоти запитів», зберігаючи автоматичне вмикання активним для інших. Щоб повністю запускати з'єднання з API-ключами без черг обмеження частоти запитів, захисну сітку потрібно вимкнути глобально (`RATE_LIMIT_AUTO_ENABLE=false` або `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`).

**Підтримувані шляхи запису:**

- **`POST /api/rate-limits`**: підтримуваний керувальний шлях запису для перемикання `rateLimitProtection` для з'єднання (`{ connectionId: string, enabled: boolean }`). Виклик із `enabled: true` вмикає явний захист; виклик із `enabled: false` знімає явний захист (хоча активні з'єднання з API-ключами залишаються під захистом глобальної захисної сітки, якщо автоматичне вмикання активне).
- **`PUT /api/providers/[id]`**: навмисно **не** приймає і не перемикає `rateLimitProtection` (#11278). Оновлення метаданих з'єднання провайдера через `PUT /api/providers/[id]` ніколи не змінить збережений стан захисту обмеження частоти запитів.

## 6. Контроль пропускної здатності повільного потоку (#9709)

Додаткова функція `resilienceSettings.streamRecovery.throughputWatchdog` guard виявляє висхідний канал, який усе ще надсилає фрагменти, але видає помічник, нижчий за налаштовану швидкість корисного виведення. Він навмисно відрізняється від тайм-ауту простою: серцебиття та метадані не скидають жоден таймер і не зараховуються як прогрес. Він також відрізняється від крайнього терміну жорсткої спроби (#9153), який залишається абсолютною межею безпеки незалежно від якості результату.

Сторожовому таймеру потрібен період розігріву, після якого слідує повне рухливе вікно, перш ніж він зможе припинити роботу. Він підраховує текстові дельти від завершень чату та відповідей на вихідні події API (консервативний байтовий проксі UTF-8 ), ігнорує події, пов’язані лише з використанням, і порожні події, а також призупиняє оцінювання, поки відбуваються події виклику інструментів або міркування. За замовчуванням його вимкнено, і його можна ввімкнути за допомогою `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true` (це значення env створює лише значення — за замовчуванням, а збережене логічне значення `resilienceSettings.streamRecovery.throughputWatchdog.enabled` виграє; див. примітку щодо пріоритету env-vs-dashboard у верхній частині цього посібника); вікно, розминка, мінімальна швидкість і мінімальний вимірний вихід обмежені нормальним шаром нормалізації налаштувань стійкості.

Якщо ввімкнено, сторожове переривання застосовується лише до активної спроби висхідного потоку. Перед будь-якими видимими для клієнта байтами існуючий шлях раннього відновлення того самого облікового запису може повторно відкрити спробу. Після фіксації потік ніколи не відтворюється наосліп; лише існуючий безпечний договір продовження в середині потоку може зшити суфікс. Фіналізація залишається одноразовою, тому облік використання та випуск семафора не дублюються.

## 7. Повторне встановлення статусу upstream (помилково вказані помилки квоти)

**Область застосування:** один upstream-шлюз, який повідомляє про тимчасове вичерпання квоти з неправильним HTTP-статусом.

**Мета:** виправити оманливий статус ДО класифікації, щоб downstream-споживачі (механізм резервного перемикання, агрегація комбінацій, відповідь для клієнта) бачили справжню можливість повторної спроби для цієї помилки.

Деякі шлюзи сигналізують про ТИМЧАСОВЕ вичерпання квоти HTTP-статусом, який не передбачає повторної спроби. `agentrouter.org` повертає `403` (іноді `400`) із китайським тілом відповіді
(`用户额度不足` / `额度不足`) замість стандартного `429`. Клієнти на кшталт Claude
Code сприймають `403` як постійну помилку й переривають сеанс, а без виправлення
механізм резервного перемикання класифікував би її як `AUTH_ERROR`, а не як подію
вичерпання квоти.

**Реалізація:**

- Реєстр і зіставник: `open-sse/config/upstreamStatusRestatement.ts` — список правил для кожного постачальника (`{id, fromStatuses, toStatus, textMarkers, excludeMarkers, defaultRetryAfterMs}`), які зіставляються через `applyStatusRestatement()`.
- Місце виклику: блок `providerFailure:` у `open-sse/handlers/chatCore.ts`
  (приблизно рядок 3654), одразу після того, як `parseUpstreamError()` розбирає
  upstream-відповідь із HTTP-статусом помилки (`!providerResponse.ok`), і до запуску будь-якої класифікації, щоб кожен downstream-споживач бачив виправлений статус. Помилки, вбудовані у SSE-потік із кодом `200`, проходять окремим, пізнішим шляхом розбору потоку й **не** охоплюються цим хуком наразі — це відоме обмеження, яке поки не потрібне для помилки з неправильним статусом у agentrouter (там вона виникає як HTTP-статус помилки).
- Можливість повторної спроби: `429` входить до `RETRY_AFTER_ELIGIBLE_STATUSES`
  (`open-sse/services/combo/unavailableRetryGate.ts`), тому помилка з повторно встановленим статусом отримує реальне вікно для повторної спроби замість того, щоб повертатися як безповоротна `403`.
- Синтетичне значення `60s` для `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`) — це лише те, що відповідь із повторно встановленим статусом повідомляє **клієнту**; воно не є внутрішньою тривалістю охолодження/блокування з’єднання — нею окремо керує механізм, який фактично обробляє помилку з повторно встановленим статусом (наростальна затримка Connection Cooldown, §2, із базовим значенням `3s` для постачальників API-ключів; або Model Lockout, §3, для постачальників із квотою на рівні моделі, таких як agentrouter). Маршрутизатор може стати внутрішньо готовим до повторної спроби раніше, ніж завершиться 60-секундне вікно, оголошене клієнту, — це навмисний запас, а не помилка.

Постійні помилки (у agentrouter `无权访问模型` — немає доступу до цієї моделі)
НІКОЛИ не отримують повторно встановлений статус: `excludeMarkers` скасовує правило навіть тоді, коли спрацьовує `textMarkers`, тому помилка зберігає початковий статус і ніщо не повторює спробу нескінченно. Відповідне правило класифікації постачальника
(`agentrouter-model-access-denied` у `open-sse/config/providerErrorRules.ts`:
`reason: "auth_error"`, `scope: "model"`, оголошене базове охолодження `6h`) перевіряється функцією `checkFallbackError` (`open-sse/services/accountFallback.ts`)
_до_ загального раннього повернення для категорії apikey `FORBIDDEN`, якщо виконується
`honorsRuleLockScope(provider)` (#10334 — наразі доступне лише для agentrouter через список дозволених постачальників `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у
`providerErrorRules.ts`). Оголошене правилом 6-годинне охолодження передається як
`fallbackResult.baseCooldownMs`, але воно все одно потрапляє до наявного шляху блокування на рівні моделі для квоти на модель (`lockModelIfPerModelQuota()` /
`recordModelLockoutFailure()`, який #10334 не змінює, за винятком джерела тривалості охолодження): його обмежено значенням `mlSettings.maxCooldownMs` оператора (типове значення `1_800_000ms` / 30 хв), як і будь-яке інше блокування моделі, а _збережена причина блокування_ залишається попередньо заданим у коді значенням `"forbidden"`, а не `"auth_error"` із правила — наскрізь враховується лише тривалість охолодження, а не рядок причини. Саме з’єднання залишається активним; сусідні моделі в тому самому з’єднанні не зазнають впливу.

Помилки повторно встановленої квоти (`额度不足`) у production доходять до правила постачальника
(`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`, `scope:
"connection"`, без власного оголошеного охолодження — застосовується масштабоване
типове значення затримки рівня збереження). Починаючи з #10334, `scope` у
`ProviderErrorRuleMatch` СПОЖИВАЄТЬСЯ наскрізь, але **лише** для постачальників зі списку
дозволених `HONORS_RULE_LOCK_SCOPE_PROVIDERS` (`providerErrorRules.ts` —
сьогодні це лише `"agentrouter"`, із перевіркою через `honorsRuleLockScope()`). Для всіх
інших постачальників `scope` залишається інформаційним, як і до #10334.
`checkFallbackError` передає область зіставленого правила як
`fallbackResult.ruleScope`; `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) — це спільна перевірка, яка підтверджує, що
`ruleScope` справді безпечно трактувати як сигнал на рівні всього з’єднання, що
самостійно відновлюється (область `"connection"`, причина `quota_exhausted`, ніколи
не `permanent` і не `creditsExhausted` — захист від майбутнього поєднання області
`"connection"` із постійним станом облікового запису). Її викликають два споживачі:

- **Збереження** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  замість переходу до гілки блокування **для кожної моделі** passthrough-провайдера
  (agentrouter має `passthroughModels: true` → `hasPerModelQuota()`
  повертає `true`), застосовується **тимчасове охолодження підключення** —
  `testStatus: "unavailable"` + `rateLimitedUntil`, але ніколи не встановлюється
  термінальний статус (`credits_exhausted`/`banned`/`expired`) — тому підключення
  самостійно відновлюється після завершення періоду охолодження, а не потребує
  ручного скидання облікових даних.
  Для підключень із `disableCooling: true` це пропускається (#2997): такий
  opt-out переходить до блокування для кожної моделі (це задокументований
  компроміс — див. коментар у коді над цією гілкою).
- **Маршрутизація комбінацій у межах одного запиту** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): той самий захист додає
  підключення до внутрішнього набору `exhaustedConnections`, ключем якого є
  `${provider}:${connectionId}`. Це лише пропускає ціль SAME-REQUEST, що
  залишилася, якщо _сама вже містить точно такий `connectionId`_ у власному
  об’єкті цілі (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` перед пошуком у `exhaustedConnections`) — звичайна комбінація
  зі списком моделей, де сусідні цілі не містять власного закріпленого
  `connectionId`, а один із них визначається для кожної диспетчеризації з
  заголовка `X-OmniRoute-Selected-Connection-Id` відповіді, ніколи не знаходить
  відповідного ключа. У цьому поширеному випадку реальний захист від повторного
  використання щойно вичерпаного облікового запису іншою частиною маршруту —
  це НЕ цей Set, а рівень збереження вище (`rateLimitedUntil` підключення тепер
  має майбутнє значення) у поєднанні з тим, що цей самий захист не додає
  `transientRateLimitedProviders` для цієї помилки (див. «Двоетапна конструкція»
  та коментар у коді для гілки
  `isAgentrouterConnectionQuotaScope` у `targetExhaustion.ts`): якщо цей Set
  залишити без позначки, примусовий дозвіл `allowRateLimitedConnection` у
  `combo.ts` (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) НЕ
  активується для решти частин маршруту цього провайдера, тому фільтр
  `rateLimitedUntil` під час вибору облікових даних
  (`src/sse/services/auth.ts:1238`) працює у звичайному режимі, і наступна
  частина маршруту або вибирає інше, усе ще доступне підключення agentrouter,
  або завершується без доступних облікових даних — вона не змушує систему
  знову використати підключення, для якого ця гілка щойно ввімкнула охолодження.

### Двоетапна конструкція: повторне формулювання статусу, потім класифікація

Повторне формулювання статусу (`upstreamStatusRestatement.ts`) і правила
класифікації провайдера (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) — це окремі реєстри, які обидва використовують
ідентифікатор провайдера й текстові маркери як ключі, але запускаються в різних
місцях і мають різне призначення: повторне формулювання рано переписує статус
HTTP у `chatCore.ts`; правила класифікації вибирають резервний `reason` і
блокують `scope` (`model` / `provider` / `connection`) усередині
`checkFallbackError()` (`open-sse/services/accountFallback.ts`).

Правила класифікації бачать повний **текст** помилки (необхідний для зіставлення
маркерів у тілі, як-от `额度不足`) лише для провайдерів, перелічених у списку
дозволених `FULL_TEXT_RULE_PROVIDERS` у `providerErrorRules.ts` — наразі лише
`"agentrouter"`. Для кожного іншого провайдера з **вбудованого каталогу**
`checkFallbackError` передає `getProviderErrorRuleMatch` лише структуровану
помилку (`{code, type}`), якої достатньо для правил на основі заголовків,
статусу й коду, але недостатньо для маркерів у тексті тіла. Допоміжна функція
`resolveRuleMatchBody()` виконує цей вибір: повний текст помилки для провайдерів
зі списку дозволених, структуровану помилку — в інших випадках. Додавання
**вбудованого** провайдера до `FULL_TEXT_RULE_PROVIDERS` є явним дозволом для
конкретного провайдера — це потрібно для того, щоб типовий шлях для кожного
провайдера, якого немає у списку, залишався незмінним побайтово.

`scope` правила (`model` / `provider` / `connection`) є окремим дозволом,
незалежним від `FULL_TEXT_RULE_PROVIDERS`: `checkFallbackError` лише повертає
його як `fallbackResult.ruleScope`, а наступні споживачі враховують його не лише
як інформаційну мітку для провайдерів зі списку дозволених
`HONORS_RULE_LOCK_SCOPE_PROVIDERS` у тому самому файлі (перевірка виконується
через `honorsRuleLockScope()` — сьогодні це лише `"agentrouter"`). Див. вище
«Повторно сформульовані помилки квоти», щоб дізнатися, що насправді робить
зіставлення `scope: "connection"`, коли провайдер є в цьому списку дозволених.

**#11104 — правила, оголошені оператором, обходять обидва списки дозволених.**
Оператор може оголосити правило для конкретного провайдера під час виконання
через `settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`),
не редагуючи цей файл. Обмеження операторського правила списками
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — списками,
призначеними для захисту **типової** поведінки правил вбудованого каталогу —
зробило б механізм налаштувань неактивним для кожного провайдера, крім уже
перелічених у них, оскільки оголошення правила вже є явним дозволом оператора.
`resolveRuleMatchBody()` і `honorsRuleLockScope()` спочатку перевіряють
`hasOperatorRuleForProvider()`: провайдер із операторським правилом отримує
необроблений текст помилки, а оголошений ним `scope` враховується незалежно
від того, чи присутній провайдер також у будь-якому зі списків дозволених.

**Правила, оголошені оператором** (`OperatorProviderErrorRule`): кожне правило
має необов’язкові `status` і `match` (звичайний підрядок тексту помилки без
урахування регістру, ніколи не RegExp, тому воно не може спричинити ReDoS) і
має містити принаймні одне з них. Якщо задано обидва, вони поєднуються через
AND; пропущене поле відповідає будь-якому значенню, тому
`{match: "insufficient_quota"}` відповідає будь-якому статусу, що містить цей
код. Перше відповідне правило має пріоритет. `cooldownMs` приймає значення
тривалістю до 30 днів; загалом дозволено не більше 50 правил.

**Загальні значення за замовчуванням** (`settings.providerErrorDefaults`, опціонально, задаються через
`setOperatorProviderErrorDefaults`): `{[provider]: {cooldownMs, scope?, reason?}}`
з `cooldownMs` від 1 хвилини до 30 днів. Значення за замовчуванням застосовується лише тоді, коли не
спрацювало жодне правило оператора та жодне вбудоване правило каталогу, і лише для помилок 402, 403, 408,
429 і 5xx. Помилки форми запиту (400, 404, 409, 413, 422) і звичайні 401 зберігають власну
обробку. Якщо `reason` не вказано явно, причина визначається зі статусу так само, як це робить
`classifyError`. Оголошення значення за замовчуванням враховується як правило оператора для
`hasOperatorRuleForProvider()`, тому його `scope` (типово `"connection"`) враховується. Ефективний
період блокування для значення за замовчуванням є довшим із його `cooldownMs` і власної підказки
провайдера щодо повторної спроби (`Retry-After`, `x-ratelimit-reset` або підказка про скидання в тілі — та
сама підказка, яку механізм враховує, коли ввімкнено налаштування періоду блокування з’єднання
"use upstream retry hints"), тож значення за замовчуванням може подовжити коротку підказку від
провайдера, але ніколи не скорочує фактичний період до скидання. Явне правило оператора зберігає своє
точне значення `cooldownMs`. Ані правило, ані значення за замовчуванням не обходять захисти періоду
блокування з’єднання в `markAccountUnavailable`: активний довший період блокування ніколи не скорочується,
а термінальний статус ніколи не перезаписується. Вбудовані текстові детектори, які виконуються раніше в
`checkFallbackError` (вичерпано кредити, денну квоту, обліковий запис деактивовано), усе ще мають пріоритет
для власних фраз.

**Відома прогалина — `providerRuleRegistry` ніколи не перевіряється для HTTP 400.**
Гілка `BAD_REQUEST` у `checkFallbackError` повністю класифікує статус 400 через власні масиви шаблонів
(`MODEL_ACCESS_DENIED_PATTERNS`, `CONTEXT_OVERFLOW_PATTERNS` тощо в `accountFallback.ts`) і повертає
результат до того, як буде досягнуто розташовану вище гілку
`configuredRule`/`getProviderErrorRuleMatch`. Вбудоване правило каталогу (або правило оператора) зі
`status: 400` є синтаксично коректним, але ніколи не спрацює. Наразі жодне наявне правило не націлене
на 400, тому в робочому середовищі це ні на що не впливає — однак для майбутнього правила 400 спочатку
потрібно змінити цю гілку. Це масштабніша зміна, ніж додавання правила (вона повторно класифікує 400
для кожного провайдера, який уже покладається на поведінку масивів шаблонів), і вона виходить за межі
додавання правила для одного провайдера.

### Додавання нового шлюзу, що неправильно повідомляє про квоту

1. Зареєструйте один масив правил у `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Зберігайте `textMarkers`
   специфічними для провайдера; ніколи не використовуйте повторно загальні англійські фрази, які
   конфліктують із `CREDITS_EXHAUSTED_SIGNALS` (`open-sse/services/accountFallback.ts`).
2. За потреби зареєструйте правила класифікації в
   `open-sse/config/providerErrorRules.ts` (`providerRuleRegistry`), щоб вибрати правильну область
   блокування (`connection` для квоти на весь обліковий запис, `model` для помилок окремої моделі). Цей
   крок набуває чинності у робочому середовищі лише для провайдерів, чиї правила потребують повного
   тексту помилки (маркери в тілі): додайте ідентифікатор провайдера до `FULL_TEXT_RULE_PROVIDERS` у
   тому самому файлі — інакше `checkFallbackError` передаватиме правилу лише структуровану помилку
   `{code, type}`, і правило для тексту тіла ніколи не відповідатиме реальному трафіку.
   Правила, що зіставляються суто за `status`/`headers` (як у Opencode або Minimax), не потребують
   цього дозволу. Окремо, якщо правило оголошує `scope: "connection"` і метою є фактичне блокування
   всього з’єднання разом із пропуском комбінації для того самого запиту (а не лише інформаційна
   мітка), додайте ідентифікатор провайдера до `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у тому самому файлі —
   саме це керує використанням у стилі `isAgentrouterConnectionQuotaScope()` в
   `markAccountUnavailable()` (`src/sse/services/auth.ts`) і
   `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`); без цього `scope`
   усе одно передається через `fallbackResult.ruleScope`, але нічого не робить із ним.
3. Додайте модульні тести за аналогією з
   `tests/unit/upstream-status-restatement.test.ts`
   і `tests/unit/agentrouter-error-rules.test.ts` (зокрема перевірки
   not-permanent / not-creditsExhausted, а також — якщо провайдер цього потребує
   — тест, який підтверджує, що `resolveRuleMatchBody()` повертає повний текст лише для цього
   провайдера).

Жодних змін у `chatCore.ts`, `classifyError` або combo не потрібно.

#### Блокування з групуванням за вихідним каналом (#10880)

Провайдери в `EGRESS_BUCKETED_LOCK_PROVIDERS` (сімейство opencode) розглядаються
як upstream із групуванням за IP-адресою (безкоштовний рівень opencode групується за IP, а не за
обліковим записом — див. #9611): статус-429, класифікований як `quota_exhausted`
**або** `rate_limit_exceeded`, охолоджує кожне з’єднання дозволеного сімейства,
чия остання відома вихідна IP-адреса збігається з адресою з’єднання, що зазнало помилки, перш ніж
ротація зможе спробувати їх
— це запобігає N-1 гарантовано невдалим викликам upstream (та сама схема, що й у #10460/#10525).
`rate_limit_exceeded` додано навмисно: на шляху `markAccountUnavailable`
специфічні правила opencode ніколи не спрацьовують (до `checkFallbackError` не передаються заголовки/тіло,
а opencode не входить до `FULL_TEXT_RULE_PROVIDERS`), тому 429, тіло якого містить текст про квоту
підписки ("monthly usage limit reached"), класифікується як `quota_exhausted` резервним визначенням
за текстом квоти (`buildSubscriptionQuotaFallback`, `accountFallback.ts`; період блокування 1 година)
ще до того, як буде досягнуто правило `status_429` — тоді як 429 без тексту про квоту (звичайне
обмеження частоти) класифікується через правило `status_429` як `rate_limit_exceeded` і також охолоджує
сімейство IP. Реалістичні обмеження:

- **За принципом найкращого зусилля**: блокування визначає останній відомий `egress_ip` з’єднання через `proxy_logs` (вікно 24 год., синхронно, без кешу). Холодний кеш (IP виходу ніколи не перевірявся) або відсутність рядка → з’єднання, що спричинило помилку, усе одно переводиться гілкою в режим охолодження (це записується так само, як і сьогодні), просто жодне споріднене з’єднання не блокується.
- **Ніколи не є термінальним**: охолодження — це вікно квоти, що поновлюється
  (`testStatus: "unavailable"`); постійний стан ніколи не виводиться із сигналу на рівні IP. З’єднання з `disableCooling` повністю пропускають цю гілку.
- **Гранулярність блокування змінюється для дозволеного сімейства**: це зміна області дії, а не лише оптимізація для споріднених з’єднань. opencode — це провайдер `passthroughModels`, тому до цієї гілки помилка 429 спричиняла блокування на рівні МОДЕЛІ; тепер вона спричиняє охолодження з’єднання — зокрема для оператора, який використовує лише одне з’єднання без жодного спорідненого. Саме таку гранулярність уже оголошено правильною в таблиці правил opencode (`scope: "connection"`, `providerErrorRules.ts`), але досі її не було задіяно, оскільки opencode не входить до `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Гілка сама записує охолодження з’єднання, що спричинило помилку, і `backoffLevel`, наслідуючи гілку agentrouter з областю дії на рівні з’єднання, а потім повертає результат — блокування на рівні моделі та наведений нижче загальний шлях ніколи не досягаються.
- **Комбінації включено**: як і гілка agentrouter, область дії навмисно ігнорує зниження `persistUnavailableState`/`isCombo`, яке застосовує викликач комбінації до 429. Блокування на рівні моделі — це не слабша форма цієї області дії, а неправильна одиниця: воно нічого не говорить про вичерпаний IP, тому ротація комбінації продовжувала б витрачати один гарантовано невдалий виклик на кожне споріднене з’єднання.
- **Безпека споріднених з’єднань**: споріднене з’єднання, яке вже перебуває в термінальному стані (banned/credits_exhausted) або вже має довше охолодження, ніколи не перезаписується.
- **Виключний список дозволених**: розширення `EGRESS_BUCKETED_LOCK_PROVIDERS` є явним рішенням власника; жодного загального підключення (патерн #10334/#10419). Запит споріднених з’єднань використовує той самий список дозволених, а не дублює його як SQL-літерал, тому його розширення залишається однорядковою зміною.
- **Ротація IP виходу в обох напрямках**: вікно пошуку (24 год.) значно ширше за TTL кешу IP виходу (5 хв.), тому «останній відомий IP» — це історія, а не поточний стан. Якщо проксі з’єднання змінився протягом вікна, блокування може **пропустити** справді спільний IP (записаний IP є новим і ще не вичерпаним) — і, симетрично, може **перевести в режим охолодження споріднене з’єднання, яке відтоді змінило IP** і більше не використовує вичерпаний IP. Другий випадок коштує цьому спорідненому з’єднанню одного вікна охолодження; обидва випадки є прийнятними обмеженнями пошуку на основі історії.
- **Вартість**: два обмежені сканування `proxy_logs` (із фільтрацією за вікном через `idx_pl_timestamp`), лише з частотою 429. Новий індекс не потрібен (міграція 134 YAGNI). Виміряно на копії бази даних із реальним трафіком помірного розміру; екземпляр із високою пропускною здатністю зберігає пропорційно більше рядків у тому самому вікні.

## Налагодження

- Зважене комбо відповідає `503 all_targets_cooling_down` (`Retry-After` встановлено, `diagnostics.excluded` перелічує кожну ціль із `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → пул налаштовано та підключено, кожну ціль просто виключено таймером стійкості; попередження `[COMBO] Weighted selection: every target excluded before dispatch — …` називає причини та секунди, що залишилися. `404 no_executable_targets` від того самого комбо означає, що таймер стійкості не брав участі (немає чого виконувати, або кожен обліковий запис не пройшов перевірку доступності). Реалізовано в `open-sse/services/combo/pinRecovery.ts` на основі виключень, зібраних у `targetResolution.ts`.
- Усі ключі провайдера пропущено → перевірте як стан circuit breaker, ТАК і `rateLimitedUntil`/`testStatus` кожного з'єднання.
- Провайдер назавжди виключений після вікна скидання → код читає сирий `state` замість `getStatus()`/`canExecute()`.
- Один ключ не працює, інші мають працювати → надайте перевагу connection cooldown перед circuit breaker.
- Не працює лише одна модель → надайте перевагу model lockout перед connection cooldown.
- Стан має самовідновлюватися, але не відновлюється → перевірте наявність мітки часу в майбутньому + шлях читання, що оновлює прострочений стан. Постійні статуси вимагають ручних змін.

## Стан середовища виконання — швидка довідка для агента

> Перенесено дослівно з `AGENTS.md` → «Resilience Runtime State» (PR #12743), щоб посібник
> агента залишався в межах бюджету контексту 40k. Це стислий, орієнтований на агента огляд
> наведених вище розділів; пронумеровані розділи залишаються повною довідкою.

OmniRoute має три пов'язані, але різні механізми обробки тимчасових збоїв. Під час
налагодження поведінки маршрутизації тримайте їхні межі окремо. Див.
[діаграму 3-рівневої стійкості](../diagrams/exported/resilience-3layers.svg)
(джерело: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd))
для швидкого огляду.

### Circuit Breaker провайдера

**Область дії**: весь провайдер, напр. `glm`, `openai`, `anthropic`.

**Призначення**: припинити надсилання трафіку провайдеру, який постійно зазнає збоїв на
рівні апстріму/сервісу, щоб один нездоровий провайдер не сповільнював кожен запит.

**Реалізація**:

- Основний клас: `src/shared/utils/circuitBreaker.ts`
- Підключення шлюзу/виконання чату: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API стану середовища виконання: `src/app/api/monitoring/health/route.ts`
- Спільні обгортки: `open-sse/services/accountFallback.ts`
- Таблиця збереженого стану: `domain_circuit_breakers`

**Стани** (4 — `src/shared/utils/circuitBreaker.ts`):

- `CLOSED`: звичайний трафік дозволено.
- `DEGRADED`: зона раннього попередження — збої перетнули поріг деградації, але ще не
  поріг вимикача; трафік усе ще йде, дашборди показують попередження. Успішний тест
  з'єднання або тихе вікно без нових збоїв повертає його до `CLOSED`
  (вікно описано в `docs/architecture/RESILIENCE_GUIDE.md`).
- `OPEN`: провайдера тимчасово заблоковано; виклики отримують відповідь provider-circuit-open
  або комбо-маршрутизація переходить до іншої цілі.
- `HALF_OPEN`: тайм-аут скидання минув; дозволяється пробний запит. Успіх закриває
  вимикач, збій знову відкриває його.

**Значення за замовчуванням** (`open-sse/config/constants.ts` → `PROVIDER_PROFILES`, споживається через
`DEFAULT_RESILIENCE_SETTINGS.providerBreaker` у `src/lib/resilience/settings.ts` →
`getCircuitBreaker(provider, …)` у `src/sse/handlers/chatHelpers.ts`). Вимикач усього
провайдера працює на `circuitBreakerThreshold` / `circuitBreakerReset`:

| Профіль   | деградує при | відкривається при (`circuitBreakerThreshold`) | скидання (`circuitBreakerReset`) |
| --------- | -----------: | --------------------------------------------: | -------------------------------: |
| OAuth     |          `5` |                                           `8` |                            `60s` |
| API-ключ  |          `7` |                                          `12` |                            `30s` |
| Локальний |    (похідне) |                                           `2` |                            `15s` |

`PROVIDER_PROFILES` також визначає `providerFailureThreshold` (10/15/2),
`providerFailureWindowMs` (15/30/5 хв) і `providerCooldownMs` (5/10/1 хв): вони живлять
**віконний шлюз опційного глобального Provider Cooldown** (`PROVIDER_COOLDOWN_ENABLED`, за замовчуванням
вимкнено) — запис рівня провайдера в `open-sse/services/providerCooldownTracker.ts` вважається таким,
що охолоджується, лише після `providerFailureThreshold` збоїв усередині `providerFailureWindowMs`, а потім
охолоджується протягом `providerCooldownMs`. Це НЕ пороги активного вимикача — не налаштовуйте їх,
очікуючи поведінки вимикача. Кожне значення за замовчуванням можна перевизначити через
змінні середовища `OMNIROUTE_PROVIDER_BREAKER_*` і `OMNIROUTE_CIRCUIT_BREAKER_*`;
точна довідкова таблиця середовища виконання знаходиться в `docs/architecture/RESILIENCE_GUIDE.md`.

Лише статуси збоїв рівня провайдера мають спричиняти спрацювання вимикача провайдера:

```ts
(408, 500, 502, 503, 504);
```

Не спричиняйте спрацювання вимикача усього провайдера для звичайних помилок облікового запису/ключа/моделі,
як-от більшість випадків `401`, `403` або `429`. Вони зазвичай належать до connection cooldown або
model lockout. Звичайний `403` провайдера API-ключа має бути відновлюваним, якщо його не
класифіковано як термінальну помилку провайдера/облікового запису.

Вимикач використовує ліниве відновлення, а не фоновий таймер. Коли термін дії стану
`OPEN` спливає, зчитування, такі як `getStatus()`, `canExecute()` і `getRetryAfterMs()`,
оновлюють стан до `HALF_OPEN`, тож дашборди та конструктори кандидатів для комбо не
продовжують виключати простроченого провайдера назавжди.

### Охолодження з'єднання

**Область дії**: одне з'єднання/обліковий запис/ключ провайдера.

**Призначення**: тимчасово пропускати один несправний ключ/обліковий запис, дозволяючи
іншим з'єднанням того самого провайдера продовжувати обслуговувати запити.

**Реалізація**:

- Шлях запису/оновлення: `src/sse/services/auth.ts::markAccountUnavailable()`
- Вибір/фільтрація облікових записів: `src/sse/services/auth.ts::getProviderCredentials...`
- Розрахунок охолодження: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Налаштування: `src/lib/resilience/settings.ts`

Важливі поля на з'єднаннях провайдера:

```ts
rateLimitedUntil;
testStatus: "unavailable";
lastError;
lastErrorType;
errorCode;
backoffLevel;
```

Під час вибору облікового запису з'єднання пропускається, поки:

```ts
new Date(rateLimitedUntil).getTime() > Date.now();
```

Охолодження також ліниві: коли `rateLimitedUntil` опиняється в минулому, з'єднання
знову стає придатним. Після успішного використання `clearAccountError()` очищає
`testStatus`, `rateLimitedUntil`, поля помилок і `backoffLevel`.

Типова поведінка охолодження з'єднання:

- Базове охолодження OAuth: `5s`.
- Базове охолодження для API-ключів: `3s`.
- Для `429` з API-ключем слід надавати перевагу підказкам повтору від апстріму
  (`Retry-After`, заголовки скидання або текст скидання, що піддається розбору), коли
  вони доступні.
- Повторні відновлювані збої використовують експоненційну затримку:

```ts
baseCooldownMs * 2 ** failureIndex;
```

Захист від «громової черги» (thundering herd) запобігає тому, щоб конкурентні збої на
тому самому з'єднанні повторно подовжували охолодження або подвійно збільшували
`backoffLevel`.

Термінальні стани — це не охолодження. `banned`, `expired` (який стає термінальним лише
після N обмежених повторних спроб через `EXPIRED_RETRY_MAX`) і `credits_exhausted` мають
залишатися недоступними, доки не зміняться облікові дані/налаштування або оператор не
скине їх. Не перезаписуйте термінальні стани тимчасовим станом охолодження.

### Блокування моделі

**Область дії**: провайдер + з'єднання + модель.

**Призначення**: уникати вимкнення цілого з'єднання, коли лише одна модель недоступна
або обмежена квотою для цього з'єднання.

Приклади:

- Провайдери з помодельними квотами, що повертають `429`.
- Локальні провайдери, що повертають `404` для однієї відсутньої моделі.
- Специфічні для провайдера збої дозволів режиму/моделі, як-от окремі режими Grok.

Блокування моделі реалізовано в `open-sse/services/accountFallback.ts` і дозволяє тому
самому з'єднанню продовжувати обслуговувати інші моделі.

### Рекомендації з налагодження

- Якщо всі ключі провайдера пропускаються, перевірте як стан вимикача провайдера, так і
  `rateLimitedUntil`/`testStatus` кожного з'єднання.
- Якщо провайдер здається назавжди виключеним після вікна скидання, перевірте, чи код
  не зчитує сирий `state` замість використання `getStatus()`/`canExecute()`.
- Якщо один ключ провайдера дає збій, а інші мають працювати, надавайте перевагу
  охолодженню з'єднання над вимикачем провайдера.
- Якщо зазнає збою лише одна модель, надавайте перевагу блокуванню моделі над
  охолодженням з'єднання.
- Якщо стан має самовідновлюватися, він повинен мати майбутню мітку часу/таймаут
  скидання та шлях зчитування, що оновлює прострочений стан. Постійні статуси вимагають
  ручної зміни облікових даних або конфігурації.

## Тестування стійкості (Фаза 8 · Блок C)

Окрім модульних тестів логіки стійкості, три тести перевіряють середовище виконання
в реальних умовах стресу/відмов (усі — інтеграційні/нічні, жоден не блокує PR-и):

| Тест                           | Що перевіряє                                                                                                                                                                                                                   | Запуск                                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| Хаос (Chaos)                   | Вузол фальшивого апстріму інжектує реальні затримки/скидання/тайм-аути/503; перевіряє, що переривач ланцюга (circuit breaker) відкривається/відновлюється, і що `checkFallbackError` класифікує 503 як відновлюваний fallback. | `RUN_CHAOS_INT=1 npm run test:chaos`    |
| Зростання купи (Heap-growth)   | ~500 потоків на `createSSEStream` під `--expose-gc`; завершується невдачею, якщо купа зростає понад стелю (захист від OOM, #3069).                                                                                             | `npm run test:heap`                     |
| Тривале навантаження k6 (soak) | Тривале навантаження на `/api/monitoring/health`; пороги p95/помилок.                                                                                                                                                          | `k6 run tests/load/k6-soak.js` (нічний) |

Оркеструється `.github/workflows/nightly-resilience.yml` (cron + dispatch). У
стандартному `test:integration` тести хаосу та купи пропускаються автоматично (без `RUN_CHAOS_INT`/`--expose-gc`).
