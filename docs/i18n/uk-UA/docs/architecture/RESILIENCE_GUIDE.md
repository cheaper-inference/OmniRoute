OmniRoute має три різні, але пов’язані механізми стійкості. Кожна з них має різні масштаби та призначення. Тримайте їх окремо під час налагодження поведінки маршрутизації.

![3-layer resilience model](../diagrams/exported/resilience-3layers.svg)

> Джерело: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd)

> **Env-vs-dashboard пріоритет для перемикачів стійкості.** Перемикання стійкості під час вибору, заповнені середовищем — `QUOTA_PREFLIGHT_CUTOFF_ENABLED`, `PROVIDER_COOLDOWN_ENABLED`, `STREAM_RECOVERY_ENABLED`, `STREAM_RECOVERY_MIDSTREAM_ENABLED`, `STREAM_THROUGHPUT_WATCHDOG_ENABLED` — дають лише значення _default_ (`DEFAULT_RESILIENCE_SETTINGS`, `src/lib/resilience/settings.ts`). Логічне значення зберігалося в `resilienceSettings` (інформаційна панель →** Налаштування стійкості →** / `PATCH /api/resilience`, що зберігається в `key_value`) перемагає значення env: нормалізація (`toBoolean`, `src/lib/resilience/settings/normalize.ts`) зберігає збережене логічне значення, коли воно існує. Встановлення такої змінної env на `true` у розгортанні, де на інформаційній панелі вже збережено `false` отже, нічого не змінюється — перемикає перемикач** Налаштування стійкості →** (або очистіть збережене поле).

## 1. Автоматичний вимикач провайдера (Provider Circuit Breaker)

**Область дії:** весь провайдер (наприклад, `glm`, `openai`, `anthropic`).

**Призначення:** припинити надсилання трафіку провайдеру, який неодноразово зазнає збоїв на рівні upstream/сервісу.

**Реалізація:**

- Основний клас: `src/shared/utils/circuitBreaker.ts`
- Підключення: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API статусу: `GET /api/monitoring/health`
- API скидання: `POST /api/resilience/reset`
- Обгортки: `open-sse/services/accountFallback.ts`
- Таблиця БД: `domain_circuit_breakers`

**Стани:**

- `CLOSED` — звичайний трафік дозволено
- `DEGRADED` — трафік усе ще дозволено, але відстежуються зростаючі збої провайдера; повертається до `CLOSED` після достатньої кількості успіхів, після успішного тесту з'єднання або після найтривалішого утримання `OPEN` для останнього типу збою (його значення `cooldownByKind`, інакше `resetTimeout`, × `maxBackoffMultiplier`, щонайменше один cooldown) без нового збою
- `OPEN` — провайдера тимчасово заблоковано; комбінована маршрутизація пропускає його
- `HALF_OPEN` — тайм-аут скидання минув; дозволено пробний запит

**Типові значення, що налаштовуються (`open-sse/config/constants.ts`, доступні в Панель керування → Налаштування → Стійкість):**

| Клас    | Деградація після | Відкриття після | Тайм-аут скидання |
| ------- | ---------------- | --------------- | ----------------- |
| OAuth   | 5 збоїв          | 8 збоїв         | 60s               |
| API-key | 7 збоїв          | 12 збоїв        | 30s               |
| Local   | похідне          | 2 збоїв         | 15s               |

`degradationThreshold` визначає, коли провайдер переходить у стан `DEGRADED`; `failureThreshold` визначає, коли він відкривається та пропускається. Профілі локальних провайдерів поки що не відображаються на сторінці налаштувань стійкості.

**Коди спрацьовування:** лише статуси рівня провайдера `[408, 500, 502, 503, 504]`. НЕ спрацьовує для помилок рівня облікового запису (більшість 401/403/429 — вони належать до періоду охолодження або блокування).

**Ліниве відновлення:** коли дія `OPEN` спливає, `getStatus()`, `canExecute()`, `getRetryAfterMs()` оновлюють стан до `HALF_OPEN`. Ті самі зчитування (і наступний збій) повертають застарілий `DEGRADED` назад до `CLOSED`. Фоновий таймер не потрібен.

### Опційний глобальний Provider Cooldown (віконний гейт)

Четвертий, **опційний** шар (`PROVIDER_COOLDOWN_ENABLED`, типово **вимкнено**) зберігає
міжзапитну пам'ять про провайдерів, що зазнають збоїв, у
`open-sse/services/providerCooldownTracker.ts`; її використовує визначення цілей
комбінації, щоб послідовні комбіновані запити не проходили повторно через
провайдера, який щойно зазнав збою. Записи рівня провайдера дотримуються віконного
гейту `PROVIDER_PROFILES`:

| Профіль | спрацьовує після (`providerFailureThreshold`) | протягом (`providerFailureWindowMs`) | охолоджується протягом (`providerCooldownMs`) |
| ------- | --------------------------------------------: | -----------------------------------: | --------------------------------------------: |
| OAuth   |                                          `10` |                              `15min` |                                        `5min` |
| API key |                                          `15` |                              `30min` |                                       `10min` |

Нижче порогу провайдер **не** вважається таким, що охолоджується; успіх очищує
вікно. Записи рівня з'єднання (`provider:connectionId`) натомість зберігають
експоненціальний backoff `minRetryCooldownMs → maxRetryCooldownMs`. Перевизначення:
`OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`.
Захист від регресій: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Перезарядка підключення

**Сфера застосування:** один провайдер connection/account/key.

**Призначення:** пропустити один несправний ключ, поки інші з’єднання для того самого провайдера продовжують обслуговувати.

**Реалізація:**

- Позначити як недоступний: `src/sse/services/auth.ts::markAccountUnavailable()`
- Вибір: `getProviderCredentials*` в тому ж файлі
- Розрахунок часу відновлення: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Налаштування: `src/lib/resilience/settings.ts`

**Поля на підключення:**

- `rateLimitedUntil` — мітка часу до закінчення часу відновлення
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — експоненціальний лічильник відступу

**Час відновлення за замовчуванням:**

- OAuth base: 5s
- База API-ключів: 3с
- API-ключ 429: надає перевагу вихідному тексту `Retry-After`/reset headers/parseable reset
- Відкат: `baseCooldownMs * 2 ** failureIndex`

**Затримка повторної спроби для кожного постачальника.** На сторінці з інформацією про постачальника є a** Затримка повторної спроби** вибрати (Авто, від 15 с до 1 год.). Зберігає `resilienceSettings.providerQuotaOverrides[<providerId>].rateLimitCooldownSeconds` (1–21600, через `PATCH /api/resilience`). Якщо помилка обмеження швидкості не містить підказки щодо повторної спроби висхідного потоку, це значення замінює масштабовану затримку для постачальника та скидає `backoffLevel` до 0 (`open-sse/services/rotationConfig.ts::overrideFor`). Пріоритет для помилки з обмеженням швидкості, спочатку найвищий: підказка щодо повторної спроби висхідного каналу, потім `providerSpecificData.rotationOverrides.rateLimitResetSeconds` для кожного з’єднання, потім затримка повторної спроби для кожного постачальника, потім env `OMNIROUTE_ROTATION_RATE_LIMIT_RESET_SECONDS`, потім масштабована відстрочка. Авто видаляє поле. Це впливає лише на причину обмеження швидкості, а не на термінальні стани.

**Протигромовий охоронець стада:** запобігає одночасним збоям через надмірне збільшення часу відновлення або подвійне збільшення `backoffLevel`.

**Обмеження паралельності 429 не піднімаються по сходах відступу.** `429` тіло якого повідомляє про обмеження паралельності («забагато одночасних запитів», «ліміт паралельних запитів», «ліміт паралельних запитів», GLM `并发数过高`), означає, що обліковий запис справний, але зайнятий. `checkFallbackError()` повертає причину `concurrency_limited`: перейдіть до наступного з’єднання зараз, охолодіть це для фіксованого `CONCURRENCY_LIMIT_COOLDOWN_MS` (1 с) або підказки щодо повторної спроби вгорі, збережіть `backoffLevel` незмінним і встановіть `skipProviderBreaker`. Тіло явної квоти все одно виграє, тому тіло, яке також відповідає шаблону квоти, залишається вердиктом квоти. Виявлення: `looksLikeConcurrencyLimit()` в `src/shared/utils/classify429.ts`; вердикт: `open-sse/services/accountFallback/concurrencyLimit429.ts`. `classify429()` ( `FailureKind` ламника) не змінився та все ще читає `rate_limit` для цих тіл.

**Стойки потокового контенту не охолоджують обліковий запис.** Коли спостерігач зупинки вмісту (`open-sse/utils/streamHandler.ts`) відмовляється від потоку, який вчасно не надіслав вихідних даних моделі, `markAccountUnavailable()` записує помилку з’єднання, але не встановлює час відновлення: зупинка належить цьому запиту, найчастіше це довгий хід міркування без виведення. Оператори можуть знову включити `resilienceSettings.streamStallCooldown.enabled` (за замовчуванням `false`).

**Сигнал затримки підключення для вибору облікового запису `p2c`.** Кожна надіслана спроба записує свій час до першого байта та результат для кожного з’єднання (і для кожної моделі + підключення) у змінному вікні в пам’яті: останні 20 зразків протягом 15 хвилин (`open-sse/services/connectionLatencyTracker.ts`, записані з `safeLogEvents()` у `src/sse/handlers/chatHelpers.ts`). Коли `resilienceSettings.p2cLatency.weight` вище `0` (діапазон 0-20, за замовчуванням `0` = вимкнено), `compareP2CConnections()` у `src/sse/services/auth.ts` додає до `weight` балів для кожного кандидата в парі. Половина цього отримана від затримки як відношення до швидшого кандидата (вдвічі повільніший займає повну половину), а половина — від частоти помилок. Термін застосовується лише тоді, коли обидва кандидати мають принаймні 3 зразки, тому нові облікові записи не штрафуються, а його верхня межа залишається нижчою штрафів за квоту та вичерпану квоту. Він не додає власної схеми: невдалі облікові записи все ще обробляються рівнями відновлення, блокування та розриву. Встановіть його за допомогою `PATCH /api/resilience` `{ "p2cLatency": { "weight": 10 } }`.

**Фрейми обґрунтування перезапускають бюджет припинення вмісту.** Модель міркування може думати кілька хвилин, перш ніж її перший видимий маркер: Claude передає кадри `thinking_delta`, текст мислення яких може бути порожнім, а відповіді API передають один елемент міркування за іншим. `isReasoningProgressFrame()` (`open-sse/utils/streamReadiness.ts`) розпізнає ці кадри, і сторожовий таймер перезапускає свій бюджет на кожному з них замість того, щоб скасовувати хід. Вони все ще не є виводом моделі, тому хід, який закінчується лише міркуванням, усе ще повідомляється як порожній, а хід, який припиняє міркування та надсилає лише серцебиття, все одно відключає сторожовий пес.

Двійкові кадри `reasoningContentEvent` Kiro непорожньою сигнатурою зберігають цю операцію міркування через виконавця як порожню дельту `reasoning_content`. Підпис не пересилається. Метадані, незавершені кадри та порожні підписи не перезапускають бюджет вмісту; час очікування незалежного активного потоку та скасування клієнта все ще застосовуються (`open-sse/executors/kiro/reasoning.ts`).

**Термінальні стани (зарядки NOT ):**

- `banned` — встановлюється виявленням заборонених ключових слів/заборонених облікових записів (див. [BAN_DETECTION](../security/BAN_DETECTION.md) ) і трьома послідовними відмовами на запит (`request_rejected`, наприклад Anthropic OAuth 403 "Запит не дозволено" — `open-sse/services/requestRejectedStreak.ts`); одинична відмова тільки охолоджує зв'язок
- `expired` (перехід до терміналу після обмежених повторних спроб — `EXPIRED_RETRY_MAX = 3` з експоненціальним відстрочкою — тому тимчасові помилки OAuth можуть самовідновлюватися до того, як обліковий запис буде остаточно деактивовано)
- `credits_exhausted`

Вони зберігаються, доки облікові дані не зміняться або оператор не скине їх. Не перезаписуйте стани терміналів тимчасовим станом відновлення.

**Ледаче відновлення:** коли `rateLimitedUntil` минуло, з’єднання знову стає придатним. Після успішного використання `clearAccountError()` очищає всі поля помилок.

### Claude OAuth usage wall: смуга нижчого пріоритету + скидання ліміту сесії

**Сфера застосування:** одне з’єднання передплати Claude (OAuth). Обидві функції є** підключення до підключення** (Редагувати розділ підключення → Claude → `lowPriorityMode` / `autoLimitReset` у `providerSpecificData`, обидва за замовчуванням вимкнено) і віддзеркалити команди `/low-priority` і `/limit-reset` коду Claude (контракт зв’язку взято з коду Claude 2.1.263).

**Реалізація:**

- Класифікація реакції кінцевого автомата + : `open-sse/services/claudeLowPriority.ts`
- Скинути клієнт status/claim : `open-sse/services/claudeLimitReset.ts`
- Хук-виконавець (повторна спроба ін’єкції заголовка + того самого облікового запису): `open-sse/executors/base.ts::execute()`
- Постійність підключення: `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**Тригер:** 5-годинна стіна використання — a `429`, заголовки якої містять `anthropic-ratelimit-unified-status: rejected` і, якщо обліковий запис відповідає вимогам, `anthropic-ratelimit-unified-slow-offer: treatment`. Нічого не надсилається до першої стіни 429; пакет 429 без уніфікованих заголовків проходить звичайний шлях відновлення.

**Смуга нижчого пріоритету** (`lowPriorityMode`):

- На стіні 429 виконавець приймає пропозицію та негайно повторює спробу** те саме** обліковий запис у `anthropic-usage-limit: slow`; смуга залишається активною до оголошеного `anthropic-ratelimit-unified-reset` (+ 60s grace), і кожен запит у цьому вікні містить заголовок. Перехоплений код 429 ніколи не досягає `handleChatCore`, тому з’єднання є** ні** поміщається в режим відновлення і не обертається.
- `anthropic-ratelimit-unified-slow-status` на наступних відповідях: `active` / `not_needed` тримати смугу; `slot_busy` (429) або `529` очікують `anthropic-ratelimit-unified-slow-retry-after` сервера (за замовчуванням 20 с, фіксація 5–600 с, ± 30% тремтіння) і повторюють спробу, обмежену `anthropic-ratelimit-unified-slow-max-wait` (за замовчуванням 20 хв, фіксація 1 хв–6 год) — після закінчення смуги та 10-хвилинного охолодження блокує повторне прийняття. Очікування додатково обмежується тим, що залишилося від власного тайм-ауту початку висхідного потоку запиту (`resolveFetchStartTimeout`, 10 хвилин за замовчуванням) мінус запас у 5 с: без цього обмеження 20-хвилинне максимальне очікування за замовчуванням пережило б запит, а сплячий режим був би перерваний під час очікування, виводячи `TimeoutError` замість витонченого охолодження `max_wait` +.
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, 5-годинне перекидання вікна або `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (що закінчується як `extra_usage` у будь-якому статусі, оскільки оплачений надлишок тепер покриває стіну) закінчує смугу; відповідь потім переходить у звичайний шлях відновлення. `budget_exhausted` зберігається до оголошеного скидання бюджету (≤ 8 днів).
- Перевірка стіни виконується після 400 власних спроб виконавця всередині спроби (редагування контексту, затискачі thinking/effort, автоматичне навчання параметрів), тому стіна 429, яка з’являється на поверхні лише під час однієї з цих спроб, усе ще перехоплюється замість досягнення шляху відновлення.
- Стан знаходиться в пам'яті для кожного з'єднання (перезапуск коштує 429 додаткових стін, щоб повторно прийняти).

**Скидання ліміту сесії** (`autoLimitReset`, спроба перед смугою, коли обидва включені):

- `GET https://api.anthropic.com/api/oauth/usage?at_wall=1&skip_spend=1` → `juniper_tide` блок; коли `arm: "reset"` і `available: true`, `POST https://api.anthropic.com/api/organizations/{orgUUID}/reset_rate_limits` з `{ "program": "juniper_tide" }` (організація UUID від `providerSpecificData.organizationUUID`, резервне завантаження).
- `result: reset|not_limited` → запит повторюється на повній швидкості (без повільного заголовка). `already_used` / `not_offered` memoise `next_available_at` (за замовчуванням один тиждень); будь-яка помилка відступає 15 хвилин. Скидання відбувається раз на тиждень і все одно враховується в тижневий ліміт.

Охоронці регресії: `tests/unit/claude-low-priority-mode.test.ts`, `tests/unit/claude-limit-reset.test.ts`, `tests/unit/claude-low-priority-executor.test.ts`.

### Спорідненість сеансу (#7274)

**Сфера застосування:** один клієнтський сеанс (заголовок `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session` ), закріплений на одному з’єднанні, для** будь-який** провайдер.

**Призначення:** підтримувати багаточерговий агент (код Claude, помічник, спеціальні агенти) в одному обліковому записі для всіх запитів, зменшуючи втрату контексту між обліковими записами та повторювані холодні старти 429 у постачальників із станом сеансу для кожного облікового запису.

**Реалізація:**

- роздільна здатність TTL : `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Pin selection/creation: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Витяг заголовка (загальний, будь-який постачальник): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Постійна таблиця контактів: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Налаштування: `sessionAffinityTtlMs` (глобальний TTL у мс, `0` вимикає) — `src/lib/db/settings.ts`. Перейменовано з `codexSessionAffinityTtlMs` лише для Codex шляхом міграції `124_generic_session_affinity_ttl.sql`, який переносить будь-який попередньо налаштований Codex TTL як нове значення за замовчуванням.

До #7274 `resolveSessionAffinityTtlMs()` жорстко підключався до `0` для кожного провайдера, крім `codex`, тому налаштування TTL (і заголовки сеансу) не мали жодного ефекту ніде в іншому місці, навіть якщо механізм закріплення та вилучення заголовка вже не залежали від провайдера. Виправлення видалило це раннє повернення; TTL тепер рівномірно застосовується до кожного постачальника, коли він встановлений глобально вище `0`.

Три заголовки афінності сеансу ніколи не пересилаються вгору. Виконавці — створюють власні висхідні заголовки з нуля, а не передають клієнтські заголовки, тому це залишається лише ідентифікатором внутрішньої кореляції.

### Оренда ексклюзивного підключення до керованого сеансу

**Сфера застосування:** один активний керований HTTP client/session володіє одним прийнятним підключенням OmniRoute.

**Призначення:** забезпечте надійне ексклюзивне право власності на з’єднання для клієнтів, яким потрібна жорстка маршрутизація між запитами. Це відрізняється від спорідненості сеансу, яка є перевагою м’якої безперервності: ексклюзивна оренда зберігає стан життєвого циклу в SQLite, забезпечує глобальну унікальність активного власника та активного з’єднання та відхиляє застарілу генерацію перед відправкою постачальника.

Ця функція полягає в підключенні за ключем API. Керований ключ повинен мати область `lease:exclusive` і явний непорожній список `allowedConnections`. Будь-який клієнт HTTP може використовувати кінцеву точку життєвого циклу; ім’я клієнта, агент користувача, постачальник, метод OAuth або модель не потрібні. Оренда володіє з’єднанням, а не моделлю, тому зміна моделі зберігає обов’язковість, у той час як з’єднання залишається прийнятним. Звичайна модель, квота, здоров’я, час відновлення та правила білого списку залишаються авторитетними та можуть перенести те саме покоління на інше безкоштовне відповідне підключення.

Життєвий цикл — це `POST /api/v1/session-leases` з діями JSON `acquire`, `renew` і `release`. Запити на керований висновок представляють непрозоре значення `X-OmniRoute-Lease-Owner` і точне `X-OmniRoute-Lease-Generation`. Власник використовує `vlo_` за яким слідують 43 символи base64url; зберігається лише його хеш SHA-256. Кожен остаточний диспетчерський паркан також пов’язує автентифікований ключ API ID і активне з’єднання ID. Заголовки керування орендою видаляються з журналів, збережених знімків запитів і заголовків виконавців у верхній частині.

Якщо звичайна маршрутизація має прийнятні керовані кандидати, але кожен вільний кандидат зайнятий іноземною активною орендою, OmniRoute повертає HTTP `429`, код недоступності оренди потужності, стан очікування пропускної здатності та обмежений `Retry-After` отриманий від найранішого відповідного закінчення терміну дії. Звичайна порожня правомочність не є суперечкою щодо оренди та зберігає свою існуючу семантику помилки маршрутизації.

Відповідні механізми залишаються окремими:

- Заповненість сеансу OAuth — це локальний м’який розподіл для облікових записів OAuth.
- Семафори облікового запису надають дозволи на паралельність запитів і завершуються, коли запит завершується.
- Ексклюзивна оренда керованого сеансу – це довговічне володіння протягом життєвого циклу з огорожею від покоління.

## 3. Блокування моделі

**Область дії:** трійка провайдер + з'єднання + модель.

**Область ключа за статусом:** статус збою визначає, до якого ключа записується блокування (`resolveLockoutScope()` у `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — сигнал про квоту або права доступу — блокується **сімейство квот**: для codex — весь діапазон `codex` / `spark` (кожна модель `gpt-5*` цього з'єднання), для інших провайдерів — `getQuotaScopedModelForProvider()`.
- `404` блокує саму модель (`getModelLockKey()` звужує `not_found`).
- Будь-який інший статус — транспортні/серверні збої `5xx` та власний синтезований OmniRoute `502` від валідації якості — блокує лише **точну** трійку провайдер/з'єднання/модель. Поганий стрім на одній моделі не є доказом щодо квоти акаунта; до цієї зміни одна порожня відповідь на `codex/gpt-5.6-luna` вилучала з маршрутизації кожну модель `gpt-5*` цього з'єднання на 2–30 хв (з ескалацією), хоча її квота залишалася недоторканою.
- Явна опція `scope` викликаючої сторони завжди має пріоритет (Antigravity передає `"exact"`).

**Призначення:** не вимикати ціле з'єднання, коли недоступна або обмежена квотою лише одна модель.

**Приклади:**

- Провайдери з квотою на модель, що повертають 429
- Локальні провайдери, що повертають 404 для однієї відсутньої моделі
- Специфічні для провайдера помилки дозволів на режим/модель (напр., режими Grok)

**Реалізація:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

### Дашборд Model Cooldowns (v3.8.0)

Інтерфейс: Налаштування → Model Cooldowns (`src/app/(dashboard)/dashboard/settings/components/ModelCooldownsCard.tsx`)

Показує активні блокування з полями: provider, connection, model, reason, expiresAt. Оператори можуть вручну повторно ввімкнути модель із картки.

**REST API:**

- `GET /api/resilience/model-cooldowns` — список активних блокувань
- `DELETE /api/resilience/model-cooldowns` — ручне повторне ввімкнення. Тіло: `{provider, connection, model}`. Автентифікація: management.

### Менеджер кулдаунів

Інтерфейс: Моніторинг → Cooldown Manager (`src/app/(dashboard)/dashboard/resilience/cooldowns/`).

Одна сторінка для кожного з'єднання, вилученого з маршрутизації з тимчасової причини, замість відкриття сторінки кожного провайдера. Вона показує кулдауни з'єднань, блокування моделей і термінальні стани, очищає їх для окремого з'єднання, для вибраної групи або для всіх з'єднань провайдера, а також редагує найчастіше налаштовувані правила кулдаунів: `streamStallCooldown.enabled` та базовий кулдаун `connectionCooldown` для OAuth / API-ключа і максимальну кількість кроків бекофа (зберігається через `PATCH /api/resilience`). Термінальні стани (`banned`, `expired`, `credits_exhausted`) перераховуються, але ніколи не очищаються тут.

**REST API** (`src/lib/resilience/cooldownManager.ts`, автентифікація: management):

- `GET /api/resilience/cooldowns[?provider=]` — з'єднання зі статусом, залишком кулдауна, рівнем бекофа, типом останньої помилки та блокуваннями моделей (без облікових даних)
- `POST /api/resilience/cooldowns` — тіло `{connectionIds: string[]}` або `{all: true, provider?}`; повертає `{cleared, unchanged, skippedTerminal, lockoutsCleared}`

### Інтерфейс налаштувань блокування + відновлення згасанням за успіхами (v3.8.23)

Блокування моделі перетворилося із завжди ввімкненої жорстко закодованої поведінки на повністю настроювану функцію з явним увімкненням (opt-in), власною карткою налаштувань і шляхом самовідновлення.

**Картка налаштувань:** Налаштування → Model Lockout (`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`). Вона **відрізняється** від read-only картки `ModelCooldownsCard` вище (яка лише _перераховує_ активні блокування) — нова картка _налаштовує параметри_. Значення за замовчуванням містяться в `DEFAULT_MODEL_LOCKOUT_SETTINGS` (`src/lib/resilience/modelLockoutSettings.ts`):

| Параметр                | За замовчуванням                 | Значення                                                              |
| ----------------------- | -------------------------------- | --------------------------------------------------------------------- |
| `enabled`               | `false`                          | Головний перемикач — блокування моделі **вимкнено за замовчуванням**. |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Статуси апстріма, що вважаються збоєм на рівні моделі.                |
| `baseCooldownMs`        | `120_000` (120 с)                | Початкова тривалість блокування для першого збою.                     |
| `maxCooldownMs`         | `1_800_000` (30 хв)              | Верхня межа ескальованого кулдауна.                                   |
| `maxBackoffSteps`       | `10`                             | Максимальна кількість кроків ескалації експоненціального бекофа.      |
| `useExponentialBackoff` | `true`                           | Чи ескалюють повторні збої кулдаун експоненціально.                   |

Налаштування зберігаються через звичайне сховище налаштувань і валідуються за схемою налаштувань відмовостійкості; картка обмежує значення `baseCooldownMs`/`maxCooldownMs` (з умовою `maxCooldownMs ≥ baseCooldownMs`) та `maxBackoffSteps`.

**Відновлення згасанням за успіхами:** відновлення — це **не** лише сплин таймера. Коректна відповідь зменшує лічильник збоїв моделі, тож модель, що відновилася в середині вікна, припиняє ескалацію (і очищається) раніше, ніж сплинув би її таймер. За успішного звернення до combo-цілі `open-sse/services/combo.ts` викликає `decayModelFailureCount()` (`open-sse/services/accountFallback.ts`), який **вдвічі зменшує** збережений `failureCount` (`Math.floor(failureCount / 2)`); коли він досягає `0`, запис блокування видаляється повністю. Протилежна функція `recordModelLockoutFailure()` збільшує лічильник (і ескалює кулдаун) за збоїв у межах вікна ескалації. Це згасання за успіхами — на додачу до звичайного сплину таймера: будь-який із цих шляхів може повторно ввімкнути модель.

**Стан:** блокування зберігаються **в пам'яті** (екземпляри `Map` на рівні процесу з елементами `ModelLockoutEntry`, ключованими за `provider:connectionId:model`, а блокування точної області — за `provider:connectionId:exact:model`) і не записуються в БД — вони втрачаються після перезапуску. _Налаштування_ зберігаються; активний _стан_ блокувань — ефемерний.

## 4. Керування паралелізмом на основі спільної квоти (v3.8.36)

Облікові записи підписок (GLM, MiniMax тощо) часто приймають лише ~1–3 одночасні
запити; перевищення цього обмеження спричиняє 429 і періоди охолодження. Особливо
гостро це проявляється для комбінацій **quota-share** (`qtSd/…`), де кілька API-ключів
спільно використовують один обліковий запис у висхідній системі. Три рівні
запобігають перевантаженню спільного облікового запису.

### Обмеження паралелізму для підключення (`max_concurrent`)

Кожне підключення провайдера може оголосити максимальне значення
`max_concurrent`
(`provider_connections.max_concurrent`, яке задається у вікні підключення / API / БД).
Залиште поле порожнім, щоб не встановлювати обмеження. Це єдиний параметр, який
керує наведеним нижче рівнем серіалізації — встановіть його відповідно до фактичного
паралелізму облікового запису (наприклад, для GLM ~1, для MiniMax ~2).

### Обмеження паралелізму для моделей (`modelConcurrency`)

Підключення також може оголосити точні обмеження паралелізму для окремих моделей
у своїй мапі `rateLimitOverrides`:

```json
{
  "rateLimitOverrides": {
    "maxConcurrent": 4,
    "modelConcurrency": { "glm-5": 1, "glm-4.7": 3 }
  }
}
```

Задайте це у вікні підключення (**Rate limit overrides → Per-model
concurrency caps**, по одному `model=cap` у рядку) або через
`PATCH /api/providers/[id]` із такою самою структурою JSON. Основні правила:

- **Загальне для підключення та специфічне для моделі:** `maxConcurrent` залишається
  спільним обмеженням для всього підключення. Якщо застосовуються обидва обмеження,
  обидва шлюзи захоплюються атомарно в одному складеному шлюзі
  (`global → provider → account → model`); фактична поведінка визначається
  суворішим застосовним обмеженням.
- **Точна відповідність ключа моделі:** ключ — це рядок моделі, переданий виконавцю
  після визначення маршруту, зазвичай базовий ідентифікатор моделі у висхідній системі
  (`glm-5`), а не псевдонім `provider/model` на боці клієнта (`zai/glm-5` не
  відповідає `glm-5`). Значення — додатні цілі числа, що задають максимальну кількість
  одночасних запитів.
- **Локальна постановка в чергу, без виявлення:** надлишкові запити стають у локальну
  чергу з наявною семантикою черги/тайм-ауту (типізовані помилки допуску
  `SEMAPHORE_TIMEOUT` / `SEMAPHORE_QUEUE_FULL`). OmniRoute не виявляє та не виводить
  політику висхідної системи — він застосовує точні обмеження, налаштовані оператором.
  Насичений шлюз моделі ніколи не вимикає провайдера й не створює постійного
  блокування моделі; поведінка щодо 429/охолодження/резервного маршруту у висхідній
  системі залишається резервним механізмом обробки помилок.
- **Область дії для кожного підключення та процесу:** обмеження діють для кожного
  підключення до бази даних і зберігаються в пам’яті, тому два підключення, що повторно
  використовують той самий API-ключ висхідної системи, не координують роботу між собою.
- **Неналаштоване значення означає відсутність змін:** пропуск мапи (або порожнє поле
  на інформаційній панелі) не додає шлюзу моделі. Приклад конфігурації без
  встановлення універсального обмеження для провайдера:

```text
glm-5=1
glm-4.7=3
```

### Серіалізація запитів quota-share

Коли диспетчеризація quota-share спрямована на підключення, для якого оголошено додатне
значення `max_concurrent`, одночасні запити до цього **облікового запису** серіалізуються
через семафор для кожного підключення (ключ `qsconn:<connectionId>`): надлишкові запити
**очікують у черзі**, а не перевантажують обліковий запис. Це працює в режимі
**fail-open** — насичена черга або тайм-аут продовжує виконання без слота й ніколи не
відхиляє запит, який можна диспетчеризувати. Увімкнути параметр можна в
**Settings → Resilience → Quota-share per-connection
concurrency** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, типово
увімкнено). Без обмеження `max_concurrent` поведінка не змінюється.

> Шлюз маршрутизації quota-share (`selectQuotaShareTarget`, DRR + P2C) сам працює в режимі
> fail-open і лише _знижує пріоритет_ підключення, яке досягло обмеження. Якщо в пулі
> лише одне підключення, він не може встановити жорстке обмеження, тож саме цей семафор
> фактично стримує перевантаження.

### Повторна спроба комбінації з урахуванням періоду охолодження

Для кожної стратегії комбінацій (якщо її ввімкнено) запит, який призвів би до 429
через КОРОТКИЙ перехідний період охолодження, очікує його завершення та повторно
диспетчеризується замість повернення 429. Це охоплює вікна TPM/RPM класу Gemini
(приблизно 60 с до повторної спроби) у комбінаціях із кількома моделями, наприклад
коли обидві цілі комбінації з двох моделей досягають обмеження частоти запитів для
моделі. Поведінка обмежується `comboCooldownWait` (`enabled`, `maxWaitMs`, `maxAttempts`,
`budgetMs`) у **Settings → Resilience**. Очікування ніколи не виконується для
`quota_exhausted` (заблоковано до опівночі) або причин, пов’язаних з автентифікацією чи
відсутністю.

Комбінація може відмовитися від цієї функції за допомогою
`config.comboCooldownWaitEnabled: false`. Лише літеральне значення `false` вимикає ці
спільні очікування комбінацій (охолодження після диспетчеризації та очікування
розімкненого автоматичного вимикача/блокування моделі перед диспетчеризацією), а також
розширення нижньої межі тайм-ауту очікування. Відсутнє значення або `true` зберігає
глобальну політику; `true` не може ввімкнути глобально вимкнене очікування. Явно
вказане `targetTimeoutMs` має вищий пріоритет. Ця відмова не змінює окреме
переддиспетчеризаційне очікування native-Codex для фіксації ходу.

Той самий шлюз охоплює випадок перед диспетчеризацією (#16319): коли кожна ціль
комбінації пропускається ще до першої спроби, оскільки її модель перебуває в короткому
перехідному блокуванні, шлях із нульовою кількістю спроб очікує завершення блокування
за тими самими обмеженнями та повторно диспетчеризує запит, замість повернення
`503 ALL_TARGETS_SKIPPED` без підказки. Коли очікування заборонене (досягнуто
обмеження, вичерпано кількість спроб або бюджет, чи функцію вимкнено), кінцева
відповідь змінюється на `429 rate_limit_error` і містить `retry_after` / `reset_at`
для найранішого завершення перехідного блокування; блокування квоти, автентифікації
та відсутності продовжують повертати 503 без підказки.

```text
#16319 · comboCooldownWait · pre-dispatch (attempts = 0)
all targets skipped + transient model lockout:
  enabled ∧ 0 < waitMs ≤ maxWaitMs ∧ attempt < maxAttempts ∧ budgetLeftMs ≥ waitMs
    → wait → re-dispatch
  wait = false → HTTP 429 rate_limit_error
  retry_after / reset_at ← earliest transient lock expiry
quota_exhausted / auth_error / not_found / not_found_local:
  no transient hint → HTTP 503 ALL_TARGETS_SKIPPED
```

## 5. Контроль прийому у чергу запитів (v3.8.49 · issue #6593)

**Область дії**: локальна черга обмеження частоти запитів для кожного провайдера+з'єднання (`open-sse/services/rateLimitManager.ts`, на основі Bottleneck), один рівень нижче трьох механізмів вище.

**`maxWaitMs` обмежує очікування в черзі; `executionMaxWaitMs` обмежує виконання.**
Ці два параметри навмисно розділені, і жоден не живить іншого.

`resilienceSettings.requestQueue.maxWaitMs` — це **бюджет очікування в черзі**: він
покриває очікування слота провайдера, а потім перебування у стані QUEUED, і його таймер
зупиняється в момент, коли завдання виходить зі стану QUEUED і починає виконуватися
(`rateLimitManager.ts`, `wrappedFn`). Запит, що перевищив його, ніколи не досягає
виконання. Типово 30000 мс, задається `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS`
у `src/lib/resilience/settings.ts` і фіксується тестом
`tests/unit/ratelimit-admission-control-6593.test.ts`, тому зміна цього значення зробить
цей тест червоним, а не залишить цей абзац тихо застарілим.

`resilienceSettings.requestQueue.executionMaxWaitMs` — це те, що Bottleneck
отримує як `expiration` завдання, чий таймер запускається лише після відправлення. Це
запобіжник для виконавців без власного таймауту до джерела даних, і його
підвищують до власного таймауту початку завантаження виконавця, коли той довший, тому він
не може обірвати здорову відповідь у польоті. Типово 600000 мс (10 хв).

Саме підмішування бюджету черги в `expiration` колись вбивало неінкрементні
шлюзи посеред польоту — вони легітимно працюють хвилинами до перших байтів —
і тому термін дії позначається як `code:
"RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504), тоді як бюджет черги несе
код таймауту черги. Будь-який з них перевизначається через `RATE_LIMIT_MAX_WAIT_MS` /
`RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (змінні середовища) або панель керування
(**Settings → Resilience**). Обидва обмежуються діапазоном 1 мс–24 год під час нормалізації.

**Пріоритет, для обох:** змінна середовища задає лише _типове_ значення. Значення,
збережене в `resilienceSettings.requestQueue` (патч через панель керування / API, зберігається
в `key_value`), перемагає його, а `rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` для
конкретного з'єднання перемагає те. Отже, встановлення
змінної середовища на розгортанні, яке вже має збережене значення, нічого не
змінює — натомість очистіть або оновіть збережене налаштування.

Перебування в черзі обмежується `maxWaitMs`; `maxQueueDepth` нижче обмежує, скільки
викликачів можуть бути в черзі одночасно.

**Повтори, заявлені в тілі відповіді: темпування проти блокування.** Тіло 429 може назвати власне очікування
(Gemini `RetryInfo.retryDelay`, текст "retry after Ns"), яке
читає `updateFromResponseBody`. Очікування, що вміщується в `maxWaitMs`
з'єднання — це темпування: обмежувач спустошує свій резервуар на цей час, і виклики
в черзі відправляються, коли він заповнюється. Очікування довше за `maxWaitMs` — це не те, що
черга може висидіти — Gemini відповідає на вичерпану денну квоту
`retryDelay: "86399s"`. Ретрансльований `Retry-After` на перебудованій відповіді 429 (#16528)
вже змушує рушій резервування блокувати модель на це вікно, але призупинення
обмежувача на нього теж все одно загальмувало б будь-який виклик, що досягає ключа рано
(після скидання стійкості, наприклад), на весь `maxWaitMs`. Коли таке очікування надходить від типізованої деталі Google `RetryInfo`
(походження `google_rpc_retry_info`) і обмежувач ключа
вже обмежений моделлю (див. `getLimiterKey`), відповідь 429 стає натомість
блокуванням моделі на цьому з'єднанні (`lockModelForLongBodyRetry` у
`open-sse/services/rateLimitManager/bodyRetryPause.ts`, обмежене 24 год), а
обмежувач залишається непризупиненим. Вибір облікового запису пропускає це блокування через
`isModelLocked()`, і так само комбінований контроль перед відправленням для цілей, прив'язаних до
з'єднання. На antigravity, чий обмежувач діє за сімейством квот, блокування
стається для конкретної моделі, як і його інші блокування квот. Ім'я, яке запитував клієнт,
також блокується, коли псевдонім розв'язав його до цієї моделі, бо ці перевірки використовують
запитуване ім'я; воно блокується точно (`lockExactModel`), тому псевдонім, що
перетинає сімейство квот antigravity або область codex, ніколи не блокує своє.
Прозова підказка, нетипізований `retryDelay` або
обмежувач, спільний для всього з'єднання, зберігають призупинення. Коли обмежувач, який щойно
перебудував шлях 429, дійсно призупиняється, викликач, чий залишок часу в черзі закінчується
до кінця призупинення, відхиляється одразу з кодом таймауту черги
(`checkLimiterPause`) замість того, щоб чекати цей час; записаний кінець
закріплюється до побудови обмежувача, там, де Bottleneck запускає свій годинник
оновлення, і будь-яка пізніша зміна резервуару його забуває. Покрито
`tests/unit/rate-limit-long-body-retry-lockout.test.ts` та
`tests/unit/rate-limit-body-retry-pause.test.ts`.

**`maxQueueDepth` — необов'язкове обмеження прийому (нове).** `resilienceSettings.requestQueue.maxQueueDepth`
обмежує, скільки запитів можуть перебувати в черзі (ще не відправлені) для одного
провайдера+з'єднання одночасно. Коли черга вже містить `maxQueueDepth`
запитів, новий запит швидко відхиляється з типізованою
помилкою `code: "RATE_LIMIT_QUEUE_FULL"` **до** того, як він взагалі досягає `limiter.schedule()`
— тому відхилення дешеве і відбувається перед будь-якою подальшою роботою з
стиснення запиту / перекладу для цього запиту. Типово `0` =
вимкнено, що зберігає існуючу поведінку необмеженої черги; обмежене 0–100000.
Перевизначення через `RATE_LIMIT_MAX_QUEUE_DEPTH` (змінна середовища) або
`resilienceSettings.requestQueue.maxQueueDepth` (патч через панель керування/API).

Сама перевірка прийому — чиста функція
(`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), тому
її можна модульно тестувати без реального обмежувача Bottleneck.

> RFC, який відкрив #6593, також пропонував прапорець
> `bypassCompressionOnRateLimit`. Пайплайн `open-sse/services/compression/`
> цього репозиторію — це стиснення промпту/контексту у вихідному запиті до
> LLM (`chatCore.ts`, приблизно навколо блоку
> `resolveCompressionSettings`/`selectCompressionStrategy`), а не
> HTTP-стиснення відповідей для синтезованих тіл 429 — відповідного шляху в
> коді для буквального прапорця обходу не існує. Цей крок стиснення промпту
> також наразі виконується _до_ `withRateLimit()` у пайплайні запитів, тому
> перевпорядкування для його пропуску під час відхилення через переповнення
> черги — це окрема, масштабніша зміна, ніж обсяг цього issue; вона навмисно
> **не** була реалізована тут і залишена як подальша робота на випадок, якщо
> виграш у економії CPU вартий ризику перевпорядкування.

### Захисна сітка автоматичного вмикання обмеження частоти запитів і захист з'єднання (`rateLimitProtection`)

**Захисна сітка автоматичного вмикання** (`resilienceSettings.requestQueue.autoEnableApiKeyProviders`, типово `true`):
Типово OmniRoute автоматично вмикає захист чергою обмеження частоти запитів для всіх активних з'єднань провайдерів з API-ключами (`getProviderCategory(provider) === "apikey"`). Це гарантує, що вхідні запити до апстрімових API-ключів, чутливих до частоти, ставляться в чергу та дроселюються через Bottleneck, а не викликають сплески апстрімових помилок 429. Захисну сітку можна перевизначити через змінну середовища `RATE_LIMIT_AUTO_ENABLE` (`false`/`0`/`off` — вимикає, `true`/`1`/`on` — примусово вмикає), яка має пріоритет над збереженим налаштуванням панелі керування (**Налаштування → Відмовостійкість** / `PATCH /api/resilience`).

**Семантика `rateLimitProtection` для окремого з'єднання:**
Захист обмеження частоти запитів для окремого з'єднання відстежується через булеве поле `rateLimitProtection` у з'єднаннях провайдерів (зберігається як `rate_limit_protection` у SQLite):

- **Явно увімкнено (`rateLimitProtection === true`)**: захист обмеження частоти запитів явно ввімкнено для цього з'єднання, незалежно від категорії провайдера чи того, чи активна захисна сітка автоматичного вмикання.
- **Явно вимкнено (`rateLimitProtection === false`)**: вимикає явний захист, але **не** виводить активне з'єднання з API-ключем з-під дії глобальної захисної сітки автоматичного вмикання. У `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значення `false` та `undefined` еквівалентні: лише `rateLimitProtection === true` розглядається як явне перевизначення. Якщо `rateLimitProtection` дорівнює `false` (або не встановлено), активне з'єднання з API-ключем усе одно відповідає умові автоматичного вмикання та залишається захищеним обмеженням частоти запитів.
- **Відсутність відмови для окремого з'єднання**: оператор наразі не може виразити «це конкретне активне з'єднання з API-ключем має працювати без захисту чергою обмеження частоти запитів», зберігаючи автоматичне вмикання активним для інших. Щоб повністю запускати з'єднання з API-ключами без черг обмеження частоти запитів, захисну сітку потрібно вимкнути глобально (`RATE_LIMIT_AUTO_ENABLE=false` або `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`).

**Підтримувані шляхи запису:**

- **`POST /api/rate-limits`**: підтримуваний керувальний шлях запису для перемикання `rateLimitProtection` для з'єднання (`{ connectionId: string, enabled: boolean }`). Виклик із `enabled: true` вмикає явний захист; виклик із `enabled: false` знімає явний захист (хоча активні з'єднання з API-ключами залишаються під захистом глобальної захисної сітки, якщо автоматичне вмикання активне).
- **`PUT /api/providers/[id]`**: навмисно **не** приймає і не перемикає `rateLimitProtection` (#11278). Оновлення метаданих з'єднання провайдера через `PUT /api/providers/[id]` ніколи не змінить збережений стан захисту обмеження частоти запитів.

## 6. Контроль пропускної здатності повільного потоку (#9709)

Додаткова функція `resilienceSettings.streamRecovery.throughputWatchdog` guard виявляє висхідний канал, який усе ще надсилає фрагменти, але видає помічник, нижчий за налаштовану швидкість корисного виведення. Він навмисно відрізняється від тайм-ауту простою: серцебиття та метадані не скидають жоден таймер і не зараховуються як прогрес. Він також відрізняється від крайнього терміну жорсткої спроби (#9153), який залишається абсолютною межею безпеки незалежно від якості результату.

Сторожовому таймеру потрібен період розігріву, після якого слідує повне рухливе вікно, перш ніж він зможе припинити роботу. Він підраховує текстові дельти від завершень чату та відповідей на вихідні події API (консервативний байтовий проксі UTF-8 ), ігнорує події, пов’язані лише з використанням, і порожні події, а також призупиняє оцінювання, поки відбуваються події виклику інструментів або міркування. За замовчуванням його вимкнено, і його можна ввімкнути за допомогою `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true` (це значення env створює лише значення — за замовчуванням, а збережене логічне значення `resilienceSettings.streamRecovery.throughputWatchdog.enabled` виграє; див. примітку щодо пріоритету env-vs-dashboard у верхній частині цього посібника); вікно, розминка, мінімальна швидкість і мінімальний вимірний вихід обмежені нормальним шаром нормалізації налаштувань стійкості.

Якщо ввімкнено, сторожове переривання застосовується лише до активної спроби висхідного потоку. Перед будь-якими видимими для клієнта байтами існуючий шлях раннього відновлення того самого облікового запису може повторно відкрити спробу. Після фіксації потік ніколи не відтворюється наосліп; лише існуючий безпечний договір продовження в середині потоку може зшити суфікс. Фіналізація залишається одноразовою, тому облік використання та випуск семафора не дублюються.

## 7. Переоголошення статусу апстріму (помилки квоти з хибним статусом)

**Область застосування:** один апстрім-шлюз, що повідомляє про тимчасове вичерпання квоти з неправильним HTTP-статусом.

**Призначення:** виправити оманливий статус ДО класифікації, щоб нижчі за потоком споживачі (рушій фолбеку, агрегація комбо, відповідь клієнту) бачили справжню природу збою, що допускає повторну спробу.

Деякі шлюзи сигналізують про ТИМЧАСОВЕ вичерпання квоти HTTP-статусом,
що не допускає повторної спроби. `agentrouter.org` повертає `403`
(іноді `400`) з тілом китайською (`用户额度不足` / `额度不足`) замість
стандартного `429`. Клієнти на кшталт Claude Code трактують `403` як
постійну помилку й переривають сесію, а без виправлення рушій фолбеку
класифікував би її як `AUTH_ERROR` замість події квоти.

**Реалізація:**

- Реєстр + матчер: `open-sse/config/upstreamStatusRestatement.ts` —
  список правил для кожного провайдера (`{id, fromStatuses, toStatus, textMarkers,
excludeMarkers, defaultRetryAfterMs}`), що зіставляються через
  `applyStatusRestatement()`.
- Місце виклику: блок `providerFailure:` у `open-sse/handlers/chatCore.ts`
  (приблизно рядок 3654), одразу після того, як `parseUpstreamError()`
  розбирає відповідь апстріму з помилковим HTTP-статусом
  (`!providerResponse.ok`), і перед будь-якою класифікацією, щоб кожен
  нижчий за потоком споживач бачив виправлений статус. Помилки,
  вбудовані всередину SSE-потоку зі статусом `200`, проходять окремим,
  пізнішим шляхом розбору потоку й **не** охоплюються цим гаком
  станом на сьогодні — відоме обмеження, яке поки не потрібне для
  хибного статусу agentrouter (який проявляється як помилковий
  HTTP-статус).
- Придатність до повторної спроби: `429` входить до
  `RETRY_AFTER_ELIGIBLE_STATUSES`
  (`open-sse/services/combo/unavailableRetryGate.ts`), тож переоголошена
  помилка несе реальне вікно повторної спроби замість того, щоб
  виглядати як мертвий `403`.
- Синтетичний `60s` `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`)
  — це лише те, що переоголошена відповідь повідомляє **клієнту**; це не
  внутрішня тривалість кулдауну/локауту з'єднання — вона керується
  окремо тим механізмом, який фактично обробляє переоголошену помилку
  (ескалаційний бекоф Connection Cooldown, §2, базовий `3s` для
  провайдерів API-ключів; або Model Lockout, §3, для провайдерів з
  квотою на модель, як-от agentrouter). Роутер може стати придатним до
  внутрішньої повторної спроби раніше, ніж мине 60-секундне вікно, яке
  він оголошує клієнту, — навмисний запас, а не помилка.

Постійні помилки (agentrouter'ів `无权访问模型` — немає доступу до цієї
моделі) НІКОЛИ не переоголошуються: `excludeMarkers` ветує правило,
навіть коли `textMarkers` спрацьовують, тож помилка зберігає свій
оригінальний статус, і ніщо не повторює її нескінченно. Відповідне
правило класифікації провайдера
(`agentrouter-model-access-denied` у `open-sse/config/providerErrorRules.ts`:
`reason: "auth_error"`, `scope: "model"`, заявлений базовий кулдаун
`6h`) опитується `checkFallbackError` (`open-sse/services/accountFallback.ts`)
_перед_ загальним раннім поверненням `FORBIDDEN` категорії apikey, з
умовою `honorsRuleLockScope(provider)` (#10334 — наразі ексклюзивно для
agentrouter через список дозволених `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у
`providerErrorRules.ts`). Заявлений правилом 6-годинний кулдаун
проходить наскрізь як `fallbackResult.baseCooldownMs`, але все одно
живить вже наявний шлях локауту за квотою на модель
(`lockModelIfPerModelQuota()` / `recordModelLockoutFailure()`, незмінений
у #10334, крім джерела кулдауну): він обрізається вниз до
`mlSettings.maxCooldownMs` оператора (типово `1_800_000ms` / 30 хв), як
і будь-який інший локаут моделі, а _збережена причина локауту_ лишається
раніше захардкодженою `"forbidden"`, а не `"auth_error"` з правила —
наскрізь враховується лише тривалість кулдауну, а не рядок причини.
Саме з'єднання лишається активним; інші моделі на тому самому з'єднанні
не зачіпаються.

Переоголошені помилки квоти (`额度不足`) досягають правила провайдера в
продакшені (`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`,
`scope: "connection"`, власного заявленого кулдауну немає — застосовується
типовий масштабований бекоф шару персистентності). Починаючи з #10334,
`scope` у `ProviderErrorRuleMatch` СПОЖИВАЄТЬСЯ наскрізь, але **лише** для
провайдерів зі списку дозволених `HONORS_RULE_LOCK_SCOPE_PROVIDERS`
(`providerErrorRules.ts` — на сьогодні лише `"agentrouter"`, через
`honorsRuleLockScope()`). Для всіх інших провайдерів `scope` лишається
інформаційним, точно як до #10334. `checkFallbackError` виставляє scope
знайденого правила як `fallbackResult.ruleScope`;
`isAgentrouterConnectionQuotaScope()` (`src/sse/services/auth.ts`) — це
спільна захисна перевірка, яка підтверджує, що `ruleScope` справді
безпечно враховувати як сигнал на все з'єднання, що самовідновлюється
(scope `"connection"`, причина `quota_exhausted`, ніколи `permanent`,
ніколи `creditsExhausted` — захист від майбутнього правила, що поєднує
scope `"connection"` з постійним станом акаунта). Її викликають два
споживачі:

- **Персистентність** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  замість провалювання до гілки **помодельного** блокування passthrough-провайдера
  (agentrouter має `passthroughModels: true` → `hasPerModelQuota()`
  повертає `true`), застосовується **тимчасове охолодження з'єднання** —
  `testStatus: "unavailable"` + `rateLimitedUntil`, ніколи не термінальний статус
  (`credits_exhausted`/`banned`/`expired`) — тож з'єднання самовідновлюється
  після спливу охолодження замість потреби в ручному скиданні облікових даних.
  Пропускається для з'єднань із `disableCooling: true` (#2997): така відмова
  натомість провалюється до помодельного блокування (задокументований компроміс —
  див. коментар у коді над гілкою).
- **Маршрутизація комбо в межах того ж запиту** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): той самий захист позначає
  з'єднання в множині `exhaustedConnections` у пам'яті, з ключем
  `${provider}:${connectionId}`. Це пропускає лише ту ціль ТОГО Ж ЗАПИТУ, що
  залишилася, яка _сама вже несе саме цей `connectionId`_ на власному
  об'єкті цілі (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` перед пошуком у `exhaustedConnections`) — звичайне
  комбо зі списку моделей, де сусідні цілі не несуть закріпленого `connectionId`
  власного, а він розв'язується лише на момент відправки із заголовка відповіді
  `X-OmniRoute-Selected-Connection-Id`, ніколи не потрапляє на збіг цього ключа. Для
  цього поширеного випадку справжнім захистом від повторного використання кроком,
  що залишився, щойно вичерпаного облікового запису є НЕ ця множина — це рівень
  персистентності вище (`rateLimitedUntil` з'єднання тепер у майбутньому) у
  поєднанні з тим, що той самий захист пригнічує `transientRateLimitedProviders`
  для цієї відмови (див. «Двоетапний дизайн» та коментар у коді на гілці
  `isAgentrouterConnectionQuotaScope` у `targetExhaustion.ts`): коли цю множину
  залишено без позначки, примусовий дозвіл `allowRateLimitedConnection` у `combo.ts`
  (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) НЕ спрацьовує для
  решти кроків провайдера, тому фільтр `rateLimitedUntil` вибору облікових даних
  (`src/sse/services/auth.ts:1238`) дотримується звичайним чином, і
  крок, що залишився, або обирає інше, досі придатне з'єднання agentrouter,
  або зазнає невдачі через відсутність доступних облікових даних — він не
  прокладає собі силоміць шлях назад на з'єднання, яке ця гілка щойно охолодила.

### Двоетапний дизайн: переформулювання статусу, потім класифікація

Переформулювання статусу (`upstreamStatusRestatement.ts`) і правила
класифікації провайдерів (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) — це окремі реєстри, які обидва ключуються за
ідентифікатором провайдера та текстовими маркерами, але вони виконуються в
різних місцях і слугують різним цілям: переформулювання переписує HTTP-статус
на ранньому етапі в `chatCore.ts`; правила класифікації обирають запасну
`reason` і фіксують `scope` (`model` / `provider` / `connection`) всередині
`checkFallbackError()` (`open-sse/services/accountFallback.ts`).

Правила класифікації бачать повний **текст** помилки (потрібний для збігу
маркерів тіла, як-от `额度不足`) лише для провайдерів, перелічених у списку
дозволених `FULL_TEXT_RULE_PROVIDERS` у `providerErrorRules.ts` — наразі лише
`"agentrouter"`. Для кожного іншого провайдера **вбудованого каталогу**
`checkFallbackError` передає `getProviderErrorRuleMatch` лише структуровану
помилку (`{code, type}`), якої достатньо для правил на основі
заголовків/статусів/кодів, але вона сліпа до маркерів тексту тіла. Допоміжна
функція `resolveRuleMatchBody()` виконує цей вибір: повний текст помилки для
провайдерів зі списку дозволених, структуровану помилку — інакше. Додавання
**вбудованого** провайдера до `FULL_TEXT_RULE_PROVIDERS` — це явна згода на
рівні окремого провайдера — вона існує для того, щоб типовий шлях для кожного
провайдера, якого немає у списку, залишався байт-у-байт незмінним.

`scope` правила (`model` / `provider` / `connection`) — це окрема згода,
незалежна від `FULL_TEXT_RULE_PROVIDERS`: `checkFallbackError` лише виставляє
його як `fallbackResult.ruleScope`, і нижчі за потоком споживачі вшановують
його як щось більше, ніж інформаційну мітку, лише для провайдерів у списку
дозволених `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у тому самому файлі
(контрольовано через `honorsRuleLockScope()` — сьогодні лише `"agentrouter"`).
Див. «Переформульовані помилки квоти» вище щодо того, що насправді робить збіг
`scope: "connection"`, коли провайдер уже є в цьому списку дозволених.

**#11104 — правила, оголошені оператором, обходять обидва списки дозволених.**
Оператор може оголосити правило на рівні провайдера під час виконання через
`settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`) без
редагування цього файлу. Контроль правила оператора через
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — списки
дозволених, покликані захистити **типову** поведінку правил вбудованого
каталогу — зробив би механізм налаштувань інертним для кожного провайдера, крім
тих, що вже перелічені там, оскільки оголошення правила вже є явною згодою
оператора. `resolveRuleMatchBody()` і `honorsRuleLockScope()` обидві спочатку
перевіряють `hasOperatorRuleForProvider()`: провайдер із правилом оператора
отримує сирий текст помилки, і його оголошений `scope` вшановується, незалежно
від того, чи він також фігурує в будь-якому зі списків дозволених.

**Відома прогалина — `providerRuleRegistry` ніколи не запитується для HTTP 400.** Гілка `BAD_REQUEST` у `checkFallbackError` класифікує статус 400 повністю
через власні масиви шаблонів (`MODEL_ACCESS_DENIED_PATTERNS`,
`CONTEXT_OVERFLOW_PATTERNS` тощо в `accountFallback.ts`) і повертається до того,
як буде досягнуто гілки `configuredRule`/`getProviderErrorRuleMatch` над нею.
Правило вбудованого каталогу (або правило оператора) зі `status: 400` є
синтаксично дійсним, але ніколи не спрацює. Жодне існуюче правило сьогодні не
націлене на 400, тож нічого у продакшені не зачіпається — але майбутнє правило
для 400 потребує спершу зміни цієї гілки, що є більшою зміною, ніж додавання
правила (воно перекласифікує 400 для кожного провайдера, який уже покладається
на поведінку масивів шаблонів), і виходить за межі обсягу додавання правила для
одного провайдера.

### Додавання нового шлюзу, що спотворює квоти

1. Зареєструйте один масив правил у `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Тримайте `textMarkers`
   специфічними для провайдера; ніколи не повторно використовуйте загальні
   англійські фрази, які перетинаються з
   `CREDITS_EXHAUSTED_SIGNALS` (`open-sse/services/accountFallback.ts`).
2. За бажанням зареєструйте правила класифікації в
   `open-sse/config/providerErrorRules.ts` (`providerRuleRegistry`), щоб
   обирати правильну область блокування (`connection` для квоти на рівні
   облікового запису, `model` для помилок на рівні моделі). Цей крок діє
   у продакшені лише для провайдерів, чиї правила потребують повного тексту
   помилки (маркери тіла): додайте ідентифікатор провайдера до
   `FULL_TEXT_RULE_PROVIDERS` у тому самому файлі — інакше
   `checkFallbackError` завжди передаватиме правилу лише структуровану
   помилку `{code, type}`, і правило за текстом тіла ніколи не спрацює
   на живому трафіку. Правила, що зіставляються виключно за
   `status`/`headers` (як у Opencode або Minimax), не потребують цього
   явного дозволу. Окремо, якщо правило декларує
   `scope: "connection"` і метою є справжнє охолодження всього з'єднання
   плюс пропуск комбо в межах того самого запиту (а не просто інформаційна
   мітка), додайте ідентифікатор провайдера до
   `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у тому самому файлі — саме це
   контролює споживання в стилі `isAgentrouterConnectionQuotaScope()` у
   `markAccountUnavailable()` (`src/sse/services/auth.ts`) та
   `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`); без цього `scope`
   все одно проходить через `fallbackResult.ruleScope`, але ніщо на нього
   не реагує.
3. Додайте юніт-тести за зразком `tests/unit/upstream-status-restatement.test.ts`
   та `tests/unit/agentrouter-error-rules.test.ts` (включно з перевірками

#### Блокування за egress-кошиком (#10880)

Провайдери з `EGRESS_BUCKETED_LOCK_PROVIDERS` (сімейство opencode)
розглядаються як апстріми з кошикуванням за IP (безкоштовний тариф
opencode кошикується за IP, а не за обліковим записом — див. #9611):
помилка зі статусом 429, класифікована як `quota_exhausted`
**або** `rate_limit_exceeded`, охолоджує кожне з'єднання сімейства зі
списку дозволених, чия остання відома egress-IP-адреса збігається з
адресою з'єднання, що зазнало невдачі, ще до того, як ротація зможе
їх спробувати
— уникаючи N-1 гарантовано невдалих апстрім-викликів (та сама схема,
що в #10460/#10525).
`rate_limit_exceeded` включено навмисно: на шляху `markAccountUnavailable`
специфічні для opencode правила ніколи не збігаються (жодних headers/body
не передається до `checkFallbackError`, opencode відсутній у
`FULL_TEXT_RULE_PROVIDERS`), тому помилка 429, чиє тіло містить текст про
квоту підписки ("monthly usage limit reached"), класифікується як
`quota_exhausted` резервним механізмом за текстом квоти
(`buildSubscriptionQuotaFallback`, `accountFallback.ts`; охолодження 1 год)
ще до того, як буде досягнуто правила `status_429` — тоді як помилка 429
без тексту квоти (звичайне обмеження частоти) класифікується через правило
`status_429` як `rate_limit_exceeded` і все одно охолоджує IP-сімейство.
Для провайдера зі списку дозволених обмеження частоти з кошикуванням за IP
є тим самим сигналом, що й вичерпана квота. Чесні обмеження:

- **Найкраще з можливого**: блокування визначає останню відому `egress_ip`
  з'єднання з `proxy_logs` (вікно 24 год, синхронно, без кешу). Холодний кеш
  (egress IP ніколи не досліджувався) або відсутність рядка → з'єднання, що
  зазнало помилки, все одно охолоджується гілкою (записується, як і сьогодні),
  лише жодне споріднене з'єднання не блокується.
- **Ніколи не термінальний**: період охолодження — це поновлюване квотне вікно
  (`testStatus: "unavailable"`); постійний стан ніколи не виводиться з сигналу
  рівня IP. З'єднання з `disableCooling` повністю пропускають гілку.
- **Зміна гранулярності блокування для сімейства з білого списку**: це зміна
  області дії, а не лише оптимізація споріднених з'єднань. opencode є
  провайдером `passthroughModels`, тому до цієї гілки код 429 спричиняв
  блокування на рівні МОДЕЛІ; тепер він спричиняє охолодження з'єднання —
  включно для оператора, що використовує одне-єдине з'єднання взагалі без
  споріднених. Це та гранулярність, яку таблиця правил opencode вже оголошує
  правильною (`scope: "connection"`, `providerErrorRules.ts`), але яка досі
  ніколи не дотримувалася, бо opencode відсутній у
  `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Гілка сама записує період охолодження
  з'єднання, що зазнало помилки, + `backoffLevel`, дзеркалюючи гілку
  agentrouter з областю дії на рівні з'єднання, і повертається — блок на
  рівні моделі та загальний шлях нижче ніколи не досягаються.
- **Combo враховано**: як і гілка agentrouter, ця область дії навмисно ігнорує
  пониження `persistUnavailableState`/`isCombo`, яке комбо-викликач застосовує
  до 429. Блокування на рівні моделі — не слабша форма цієї області дії, а
  неправильна одиниця: воно нічого не каже про вичерпану IP-адресу, тож
  комбо-ротація продовжувала б спалювати один гарантовано невдалий виклик на
  кожне споріднене з'єднання.
- **Безпека споріднених з'єднань**: споріднене з'єднання, яке вже перебуває в
  термінальному стані (banned/credits_exhausted) або вже в довшому періоді
  охолодження, ніколи не перезаписується.
- **Ексклюзивний білий список**: розширення `EGRESS_BUCKETED_LOCK_PROVIDERS` —
  це явне рішення власника; жодного узагальненого підключення (патерн
  #10334/#10419). Запит споріднених з'єднань прив'язує той самий білий список
  замість повторення його як SQL-літералу, тож його розширення залишається
  зміною в один рядок.
- **Ротація egress IP в обох напрямках**: вікно пошуку (24 год) значно ширше
  за TTL кешу egress-IP (5 хв), тож «остання відома IP-адреса» — це історія,
  а не поточний стан. Якщо проксі з'єднання ротувався протягом вікна,
  блокування може **пропустити** дійсно спільну IP-адресу (записана IP — нова,
  невичерпана) — і симетрично воно може **охолодити споріднене з'єднання, яке
  відтоді ротувалося геть** від вичерпаної IP. Другий випадок коштує цьому
  спорідненому з'єднанню одного вікна охолодження; обидва — прийнятні
  обмеження найкращого з можливого для пошуку на основі історії.
- **Вартість**: два обмежені сканування `proxy_logs` (фільтровані за вікном
  через `idx_pl_timestamp`), лише з частотою помилок 429. Жодного нового
  індексу (міграція 134 — YAGNI). Виміряно на копії БД з реальним трафіком
  помірного розміру; високопродуктивний інстанс містить пропорційно більше
  рядків у тому самому вікні.

## Налагодження

- Зважене комбо відповідає `503 all_targets_cooling_down` (`Retry-After` встановлено, `diagnostics.excluded` перелічує кожну ціль із `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → пул налаштовано та підключено, кожну ціль просто виключено таймером стійкості; попередження `[COMBO] Weighted selection: every target excluded before dispatch — …` називає причини та секунди, що залишилися. `404 no_executable_targets` від того самого комбо означає, що таймер стійкості не брав участі (немає чого виконувати, або кожен обліковий запис не пройшов перевірку доступності). Реалізовано в `open-sse/services/combo/pinRecovery.ts` на основі виключень, зібраних у `targetResolution.ts`.
- Усі ключі провайдера пропущено → перевірте як стан circuit breaker, ТАК і `rateLimitedUntil`/`testStatus` кожного з'єднання.
- Провайдер назавжди виключений після вікна скидання → код читає сирий `state` замість `getStatus()`/`canExecute()`.
- Один ключ не працює, інші мають працювати → надайте перевагу connection cooldown перед circuit breaker.
- Не працює лише одна модель → надайте перевагу model lockout перед connection cooldown.
- Стан має самовідновлюватися, але не відновлюється → перевірте наявність мітки часу в майбутньому + шлях читання, що оновлює прострочений стан. Постійні статуси вимагають ручних змін.

## Стан середовища виконання — швидка довідка для агента

> Перенесено дослівно з `AGENTS.md` → «Resilience Runtime State» (PR #12743), щоб посібник
> агента залишався в межах бюджету контексту 40k. Це стислий, орієнтований на агента огляд
> наведених вище розділів; пронумеровані розділи залишаються повною довідкою.

OmniRoute має три пов'язані, але різні механізми обробки тимчасових збоїв. Під час
налагодження поведінки маршрутизації тримайте їхні межі окремо. Див.
[діаграму 3-рівневої стійкості](../diagrams/exported/resilience-3layers.svg)
(джерело: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd))
для швидкого огляду.

### Circuit Breaker провайдера

**Область дії**: весь провайдер, напр. `glm`, `openai`, `anthropic`.

**Призначення**: припинити надсилання трафіку провайдеру, який постійно зазнає збоїв на
рівні апстріму/сервісу, щоб один нездоровий провайдер не сповільнював кожен запит.

**Реалізація**:

- Основний клас: `src/shared/utils/circuitBreaker.ts`
- Підключення шлюзу/виконання чату: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API стану середовища виконання: `src/app/api/monitoring/health/route.ts`
- Спільні обгортки: `open-sse/services/accountFallback.ts`
- Таблиця збереженого стану: `domain_circuit_breakers`

**Стани** (4 — `src/shared/utils/circuitBreaker.ts`):

- `CLOSED`: звичайний трафік дозволено.
- `DEGRADED`: зона раннього попередження — збої перетнули поріг деградації, але ще не
  поріг вимикача; трафік усе ще йде, дашборди показують попередження. Успішний тест
  з'єднання або тихе вікно без нових збоїв повертає його до `CLOSED`
  (вікно описано в `docs/architecture/RESILIENCE_GUIDE.md`).
- `OPEN`: провайдера тимчасово заблоковано; виклики отримують відповідь provider-circuit-open
  або комбо-маршрутизація переходить до іншої цілі.
- `HALF_OPEN`: тайм-аут скидання минув; дозволяється пробний запит. Успіх закриває
  вимикач, збій знову відкриває його.

**Значення за замовчуванням** (`open-sse/config/constants.ts` → `PROVIDER_PROFILES`, споживається через
`DEFAULT_RESILIENCE_SETTINGS.providerBreaker` у `src/lib/resilience/settings.ts` →
`getCircuitBreaker(provider, …)` у `src/sse/handlers/chatHelpers.ts`). Вимикач усього
провайдера працює на `circuitBreakerThreshold` / `circuitBreakerReset`:

| Профіль   | деградує при | відкривається при (`circuitBreakerThreshold`) | скидання (`circuitBreakerReset`) |
| --------- | -----------: | --------------------------------------------: | -------------------------------: |
| OAuth     |          `5` |                                           `8` |                            `60s` |
| API-ключ  |          `7` |                                          `12` |                            `30s` |
| Локальний |    (похідне) |                                           `2` |                            `15s` |

`PROVIDER_PROFILES` також визначає `providerFailureThreshold` (10/15/2),
`providerFailureWindowMs` (15/30/5 хв) і `providerCooldownMs` (5/10/1 хв): вони живлять
**віконний шлюз опційного глобального Provider Cooldown** (`PROVIDER_COOLDOWN_ENABLED`, за замовчуванням
вимкнено) — запис рівня провайдера в `open-sse/services/providerCooldownTracker.ts` вважається таким,
що охолоджується, лише після `providerFailureThreshold` збоїв усередині `providerFailureWindowMs`, а потім
охолоджується протягом `providerCooldownMs`. Це НЕ пороги активного вимикача — не налаштовуйте їх,
очікуючи поведінки вимикача. Кожне значення за замовчуванням можна перевизначити через
змінні середовища `OMNIROUTE_PROVIDER_BREAKER_*` і `OMNIROUTE_CIRCUIT_BREAKER_*`;
точна довідкова таблиця середовища виконання знаходиться в `docs/architecture/RESILIENCE_GUIDE.md`.

Лише статуси збоїв рівня провайдера мають спричиняти спрацювання вимикача провайдера:

```ts
(408, 500, 502, 503, 504);
```

Не спричиняйте спрацювання вимикача усього провайдера для звичайних помилок облікового запису/ключа/моделі,
як-от більшість випадків `401`, `403` або `429`. Вони зазвичай належать до connection cooldown або
model lockout. Звичайний `403` провайдера API-ключа має бути відновлюваним, якщо його не
класифіковано як термінальну помилку провайдера/облікового запису.

Вимикач використовує ліниве відновлення, а не фоновий таймер. Коли термін дії стану
`OPEN` спливає, зчитування, такі як `getStatus()`, `canExecute()` і `getRetryAfterMs()`,
оновлюють стан до `HALF_OPEN`, тож дашборди та конструктори кандидатів для комбо не
продовжують виключати простроченого провайдера назавжди.

### Охолодження з'єднання

**Область дії**: одне з'єднання/обліковий запис/ключ провайдера.

**Призначення**: тимчасово пропускати один несправний ключ/обліковий запис, дозволяючи
іншим з'єднанням того самого провайдера продовжувати обслуговувати запити.

**Реалізація**:

- Шлях запису/оновлення: `src/sse/services/auth.ts::markAccountUnavailable()`
- Вибір/фільтрація облікових записів: `src/sse/services/auth.ts::getProviderCredentials...`
- Розрахунок охолодження: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Налаштування: `src/lib/resilience/settings.ts`

Важливі поля на з'єднаннях провайдера:

```ts
rateLimitedUntil;
testStatus: "unavailable";
lastError;
lastErrorType;
errorCode;
backoffLevel;
```

Під час вибору облікового запису з'єднання пропускається, поки:

```ts
new Date(rateLimitedUntil).getTime() > Date.now();
```

Охолодження також ліниві: коли `rateLimitedUntil` опиняється в минулому, з'єднання
знову стає придатним. Після успішного використання `clearAccountError()` очищає
`testStatus`, `rateLimitedUntil`, поля помилок і `backoffLevel`.

Типова поведінка охолодження з'єднання:

- Базове охолодження OAuth: `5s`.
- Базове охолодження для API-ключів: `3s`.
- Для `429` з API-ключем слід надавати перевагу підказкам повтору від апстріму
  (`Retry-After`, заголовки скидання або текст скидання, що піддається розбору), коли
  вони доступні.
- Повторні відновлювані збої використовують експоненційну затримку:

```ts
baseCooldownMs * 2 ** failureIndex;
```

Захист від «громової черги» (thundering herd) запобігає тому, щоб конкурентні збої на
тому самому з'єднанні повторно подовжували охолодження або подвійно збільшували
`backoffLevel`.

Термінальні стани — це не охолодження. `banned`, `expired` (який стає термінальним лише
після N обмежених повторних спроб через `EXPIRED_RETRY_MAX`) і `credits_exhausted` мають
залишатися недоступними, доки не зміняться облікові дані/налаштування або оператор не
скине їх. Не перезаписуйте термінальні стани тимчасовим станом охолодження.

### Блокування моделі

**Область дії**: провайдер + з'єднання + модель.

**Призначення**: уникати вимкнення цілого з'єднання, коли лише одна модель недоступна
або обмежена квотою для цього з'єднання.

Приклади:

- Провайдери з помодельними квотами, що повертають `429`.
- Локальні провайдери, що повертають `404` для однієї відсутньої моделі.
- Специфічні для провайдера збої дозволів режиму/моделі, як-от окремі режими Grok.

Блокування моделі реалізовано в `open-sse/services/accountFallback.ts` і дозволяє тому
самому з'єднанню продовжувати обслуговувати інші моделі.

### Рекомендації з налагодження

- Якщо всі ключі провайдера пропускаються, перевірте як стан вимикача провайдера, так і
  `rateLimitedUntil`/`testStatus` кожного з'єднання.
- Якщо провайдер здається назавжди виключеним після вікна скидання, перевірте, чи код
  не зчитує сирий `state` замість використання `getStatus()`/`canExecute()`.
- Якщо один ключ провайдера дає збій, а інші мають працювати, надавайте перевагу
  охолодженню з'єднання над вимикачем провайдера.
- Якщо зазнає збою лише одна модель, надавайте перевагу блокуванню моделі над
  охолодженням з'єднання.
- Якщо стан має самовідновлюватися, він повинен мати майбутню мітку часу/таймаут
  скидання та шлях зчитування, що оновлює прострочений стан. Постійні статуси вимагають
  ручної зміни облікових даних або конфігурації.

## Тестування стійкості (Фаза 8 · Блок C)

Окрім модульних тестів логіки стійкості, три тести перевіряють середовище виконання
в реальних умовах стресу/відмов (усі — інтеграційні/нічні, жоден не блокує PR-и):

| Тест                           | Що перевіряє                                                                                                                                                                                                                   | Запуск                                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| Хаос (Chaos)                   | Вузол фальшивого апстріму інжектує реальні затримки/скидання/тайм-аути/503; перевіряє, що переривач ланцюга (circuit breaker) відкривається/відновлюється, і що `checkFallbackError` класифікує 503 як відновлюваний fallback. | `RUN_CHAOS_INT=1 npm run test:chaos`    |
| Зростання купи (Heap-growth)   | ~500 потоків на `createSSEStream` під `--expose-gc`; завершується невдачею, якщо купа зростає понад стелю (захист від OOM, #3069).                                                                                             | `npm run test:heap`                     |
| Тривале навантаження k6 (soak) | Тривале навантаження на `/api/monitoring/health`; пороги p95/помилок.                                                                                                                                                          | `k6 run tests/load/k6-soak.js` (нічний) |

Оркеструється `.github/workflows/nightly-resilience.yml` (cron + dispatch). У
стандартному `test:integration` тести хаосу та купи пропускаються автоматично (без `RUN_CHAOS_INT`/`--expose-gc`).
