Цей документ є авторитетним довідником щодо всіх шлюзів якості CI в OmniRoute.
У ньому описано кожен шлюз, що він перевіряє, у якому завданні CI запускається, чи використовує
базову лінію з храповим механізмом або політику успішного/неуспішного проходження, а також чи блокує він збірку або має рекомендаційний характер.

Короткий огляд і політику списку дозволів див. у розділі "Шлюзи якості та храпові механізми"
у `AGENTS.md`. Критичну оцінку, класифікацію зрілості та незалежний від інструментів
план відтворення цієї ж системи див. у
[Посібнику зі шлюзів якості](../ops/QUALITY_GATE_PLAYBOOK.md).

## Інвентар воріт та профілі виконання

### Прийом кандидатів

Робочі процеси CI та Quality Gates видають стабільний вердикт: `Gate / CI` та `Gate / Quality`. Їхня політика прийому з версіями перераховує кожну вакансію, яка є обов’язковою або рекомендованою. Відповідне обов’язкове завдання має бути успішним: відсутні, скасовані, пропущені, очікувані та невідомі результати не можуть встановити PASS. Дійсна класифікація лише для документів або лише для каталогу може зробити кодову смугу незастосовною; звичайний проект PR не є прийнятним кандидатом. Мітка `hotfix` не скасовує докази.

Обидва робочі процеси охоплюють PRs у гілки main/release, надсилання до `main`, ручну диспетчеризацію та події злиття груп. Push, dispatch і merge-group запускають повний вибір. Надійний проект черги Mergify також запускає відповідні завдання `full-code`/`full-code-e2e` ; звичайні PRs пропускають їх. Перед об’єднанням вручну запустіть повну диспетчеризацію для точного кандидата. Надсилання до `release/**` не запускає ці робочі процеси; Release-Green спостерігає за об’єднаною базою окремо (`docs/ops/RUNNER_BOX.md` → Hosted lane). Розгалуження та групи злиття використовують розміщені бігуни для завдань, які в іншому випадку вибирають саморозміщені бігуни; перед розгортанням необхідно перевірити достатню потужність хостингу.

Звичайний PR виконує швидкий вибір. Доріжки `full-code` і `full-code-e2e` політики доступу (E2E, інтеграція, артефакт пакета, Electron smoke, Bun SQLite, клієнти екосистеми та протоколу) запускаються лише на чернетці черги Mergify або на повному циклі: `gh workflow run ci.yml --ref <branch>`.

Кожна квитанція JSON ідентифікує виписаний SHA, запуск робочого процесу та спробу. CLI відхиляє невідповідність checkout/event SHA. Тести робочого циклу пов’язують членство в політиці зі списком `needs` вердикту, тому нова або видалена смуга не може мовчки зникнути. Квитанції охоплюють їхній власний робочий процес, а не публікацію, розгортання чи внутрішню роботу наявного консультативного сканера. Здійснення відповідних перевірок, необхідних у правилах філії, є окремою адміністративною зміною; визначення їхніх робочих місць саме по собі не захищає галузь.

`API Route Typecheck` — це незалежна перевірка робочого процесу, поза як сукупними вердиктами, так і статичним профілем локального повного спостерігача. Перегляньте його результат окремо для конкретного кандидата. `.github/workflows/api-route-typecheck.yml` запускається на PRs у `main` або `release/**`, надсилає до будь-якої гілки сімейства, ручної диспетчеризації та подій `merge_group` типу `checks_requested`. Він не має фільтра шляху. Об'єднати групи перевірити `merge_group.head_sha`; інші події дивіться `github.sha`. Для всіх подій використовуються однакові діагностичні шлюзи API і тести блоків воріт. PR base retargets запитують нову перевірку; Редагування body/title використовує назву `Admission not requested / API Route Typecheck` лише для спостереження та не може замінити перевірку допуску.

### Збережені докази в редукторі приймання

`scripts/quality/validate-release-acceptance.mjs` скорочує наданий план і його маніфести; він не встановлює, що план охоплює повний випуск. Його звіти явно встановлюють `releaseAcceptance: false`, навіть якщо цим планом є `VERIFIED`. Робочий процес `release-acceptance.yml` все ще використовує тіньові прилади, а не реальні квитанції про збірку, упаковку, завантаження чи просування.

CLI вимагає від `--evidence-root` перевірити збережені докази. Файли розпізнаються як `<evidence-root>/<artifact_id>/<member>` і хешуються як SHA-256. Запис PASS без доказів, відсутній або змінений файл, небезпечний шлях або символічне посилання перешкоджають перевірці. Відсутні файли не еквівалентні порожнім успішним журналам. Існуючі перевірки SHA/run/attempt залишаються незалежними: збіг байтів не може врятувати застарілу квитанцію. Цілісність файлу не є доказом автентичності виконання чи просування артефактів.

### DAST використовує перевірену збірку CI

Необхідне завдання `dast-smoke` CI викликає `.github/workflows/dast-smoke.yml` після `build`. Він дотримується того самого вибору code/draft, що й збірка, включаючи підтримуваний форк PRs, цільовий випуск PRs і групи злиття. Відсутнє, невдале, скасоване або неочікувано пропущене завдання DAST блокує `Gate / CI`. Робочий процес багаторазового використання не має незалежного тригера PR/dispatch ; ручна перевірка використовує диспетчеризацію CI, тому збірка та споживач залишаються в одному запуску.

`scripts/ci/next-build-provenance.mjs` запечатує повний артефакт Next за допомогою дайджесту tar, repository/event/run, спроби виробника, head/base/checkout/tree, ідентифікаторів робочого циклу, файлу блокування, точного вузла version/ABI, платформи та збірника. DAST вибирає незмінний артефакт ID із `needs.build.outputs`, вимагає перевірки дайджесту завантаження та незалежно хешує ZIP проти дайджесту виробника перед тим, як видобувати його два члени з білого списку через `scripts/ci/unpack-ci-build.py`. Архів маніфесту та tar також має відповідати виходам незалежних виробників, перш ніж буде видобуто наступне дерево. Він ніколи не шукає останню успішну збірку гілки. Частковий повторний запуск може повторно використовувати ту саму спробу виробника, якщо його ID та всі вхідні дані все ще збігаються; квитанція записує обидві спроби.

Споживач залишається на розміщеному бігуні Linux з дозволом сховища лише для читання та без секретів сховища. Він встановлює точну версію Node від виробника, а потім збирає CLI за допомогою `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1`. `scripts/build/standaloneInput.mjs` відхиляє відсутній автономний сервер перед будь-якою резервною збіркою; звичайні локальні збірки CLI зберігають наявний запасний варіант. Готовність сервера, Schemathesis і promptfoo мають бути успішними в межах незмінного 25-хвилинного ліміту завдань. Квитанція про походження підтверджує ідентифікацію введених даних і байти, а не успішне сканування DAST. Закінчення терміну дії артефакту, переривання бігуна або несправність сканера залишаються неповними або невдалими доказами; він не може стати PASS через консультативну оболонку.

### Потужність виконання UI

CI запускає повну інвентаризацію UI у вигляді чотирьох осколків матриці `test-vitest`, кожен із яких містить щонайбільше два працівники на шард і наявний 15-хвилинний термін виконання завдань. Перший сегмент також запускає пакет MCP/autoCombo Vitest. Необхідний результат роботи охоплює кожну ніжку матриці; збій або скасування одного шарда не може свідчити про допуск кандидата.

Щоночі спостерігач зберігає окрему квитанцію точного кандидата для кожного фрагмента UI, включаючи виконання MCP у першій квитанції. Потрібні всі чотири квитанції, журнали та відповідні ідентифікатори виконання. Місцевий `npm run test:vitest:ui` все ще вибирає повний пакет; один запуск `--shard` є лише частковим доказом.

### Колекція покриття одиниць

Дванадцять фрагментів блоків збирають покриття V8 під час поточного виконання тесту. Успішний шард запускає `scripts/ci/compact-v8-coverage.mjs` для стиснення вихідних файлів без створення проміжного звіту Стамбула. Остаточне завдання Coverage перевіряє всі дванадцять маніфестів щодо SHA кандидата, середовища виконання, кореневої версії джерела та хешів даних, а потім запускає звіти c8 та існуючі порогові значення покриття. Вхідні дані зберігають глобальний порядок імен файлів c8; Попереднє злиття на сегмент небезпечно для змішаного покриття function/block. Відсутні, неправильно сформовані або несумісні сегменти не приймаються. Шарди невдалого тестування зберігають необроблене діагностичне покриття окремо; він не може увійти до остаточного злиття.

### Квитанції про виконання підрозділу

Спільна команда `test:unit:ci:shard` записує фази `primary`, `dashboard` і `serial` через `scripts/ci/unit-progress-reporter.mjs`. Звичайний звіт про випробування залишається доступним. Окрема квитанція лише про отримання метаданих записує початок і завершення кожного файлу, а 30-секундний пульс містить список файлів, які все ще активні, і час, що минув. Він записує лише дозволені метадані виконання; описи тестів, вихідні дані, тіла помилок і повне середовище не серіалізуються.

CI зберігає файли JSONL як `unit-progress-ci-<run>-<attempt>-<shard>`. Тайм-аут завдання може перешкодити пізнішому завантаженню; вже випущені серцеві скорочення залишаються діагностичними доказами. Відсутність серцевих скорочень також може вказувати на заблокований або припинений процес запуску. Ці квитанції зберігають наявний вибір тесту, паралелізм, кінцеві терміни та статус виходу; вони не є вердиктами про вступ кандидата.

### Об'єднати чергу

Мітка `queue` надсилає PR до черги Mergify (`.mergify.yml`). Mergify відкриває чернетку PR у гілці `mergify/merge-queue/`, CI виконує повний вибір там, а оригінальний PR об’єднується, коли `Gate / CI`, `Gate / Quality` та `Merge integrity (changelog + generated skills)` проходять.

Mergify записує свій підсумок черги в опис чернетки. Події Body/title-only `pull_request` `edited` використовують специфічну для виконання групу паралельності й не запускають повторно класифікацію, тестові матриці, цілісність злиття чи вердикт про допуск. Імена перевірок лише для спостереження не можуть замінити `Gate / CI` або `Gate / Quality`. Редагування, яке змінює цільову базу, вимагає перевірки нового кандидата.

Після вилучення з черги надсилання не завжди повертає PR в чергу. Прокоментуйте це `@mergifyio queue`.

### Інвентар статичного сканування

Версійний інвентар npm-alias і членство в static-scan живуть у `config/quality/gate-manifest.json`. Запустіть `npm run check:gate-manifest`, щоб перевірити імена сценаріїв і точні команди на `package.json`; додавання, видалення та дрейф команд не виконують як локальний підхоплювач, так і завдання класифікації змін у CI. Псевдонім не є завданням робочого циклу, екземпляром матриці чи тестовим випадком: ці показники не можна подавати як взаємозамінні.

Використовуйте `npm run quality:scan -- --list` або `npm run quality:scan:fast -- --list`, щоб перевірити вибрані псевдоніми без їх виконання. Програма запуску викликає точку входу npm, тому її час виконання (включаючи Bun де налаштовано) зберігається. Маніфест записує псевдоніми поза цими профілями як викликані окремо, а команди обслуговування заборонені в профілях сканування лише для читання.

Ці профілі охоплюють лише статичне сканування. Вони не сертифікують випробування продукту, покриття, упаковку, зовнішні перевірки або повне прийняття кандидата. Допуск робочого процесу використовує пов’язані `config/quality/admission-policy.json` та `scripts/quality/admission-verdict.mjs`. Профілі спостерігачів випуску залишаються окремими; самостійно перевіряти відповідні чеки та квитанції. Повні статичні команди спостерігача оголошені в `config/quality/release-green-static-profile.json`, включаючи `audit:deps`, вибір тесту на мутацію та перевірки трансляції. Завантажувач перевіряє команди npm на відповідність package.json та змодельованим оголошенням CI/Quality ; він відхиляє дрейф замість того, щоб виконувати маркери оболонки як аргументи. Необхідний вихід сканера SKIP/INCOMPLETE не може встановити PASS. Профіль записує свої зовнішні виключення та не замінює розміщене покриття, тестові матриці, пакет або докази розгортання. Наведений нижче перелік прози є посиланням, а не доказом того, що ворота справді пробігли.

Сценарії живуть під `scripts/check/` (політики) і `scripts/quality/` (храповик). Джерелом правди CI є `.github/workflows/ci.yml`.

### Опублікована база документації здоров'я

`.github/workflows/i18n-base-health.yml` спостерігає за справністю документації після вибраних надсилань до `main` і `release/v*`, а також під час відправки вручну. Його фільтри охоплюють документацію, root Markdown, `llm.txt`, переклад state/configuration та відповідні інструменти i18n. Одне завдання `Published base documentation health` використовує хостинг Ubuntu і п’ятихвилинний крайній термін. Він виконує перевірку лише для читання та записує діагностичну квитанцію без встановлення залежностей, перекладу чи прийняття стану.

`scripts/i18n/check-base-health.mjs` вимагає нульового гешу джерела, відсутньої цілі, гешу цілі, невідповідності застарілого перекладу та кешу розділів. Він також підтверджує поточну основну область document/locale і її зареєстроване походження. Недійсний контекст, неповне покриття або перервана перевірка створює `INCOMPLETE`; підтверджений дрейф створює `FAIL`. Обидва повертають невдалий статус виходу. Квитанція прив’язана до перевірки SHA, робочого процесу, запуску та спроби та зберігається як `i18n-base-health-<sha>-<run>-<attempt>`.

Це незалежне спостереження опублікованої бази. Він не додає подію PR або групи злиття, обов’язкову перевірку PR, псевдонім npm або учасника профілю статичного сканування. Базовий засіб перевірки також блокує всі п'ять класів в абсолютному режимі. Звичайна підготовка PR залишається окремою від вступу. Успішне завантаження не може перетворити невдалий результат здоров’я на PASS.

Звичайний PR використовує `--preflight` із базовим звітом, створеним `--baseline-evidence`. Це може залишити джерело англійською мовою в очікуванні лише тоді, коли повний запис перекладу та фактичні цільові байти не змінюються порівняно з цією точною базою. Нові невідповідності цілі або кешу розділу все ще блокуються, а неповні докази не можуть дозволити підготовку. Звіт розкриває `preparationPending` і `mergeReady` окремо: успішна підготовка не робить незавершені переклади готовими до об’єднання. Оновіть уражені дзеркала у складеному кандидаті перед прийомом. Довірений кандидат у чергу Mergify, `merge_group`, надсилання гілок і запуск CI вручну використовують абсолютну перевірку без `--warn` або пробачення успадкованих помилок. Відсутність цільових хешів і обсяг, зменшений видаленими записаними файлами ядра, не можуть дати абсолютний вердикт про успішність.

### Випуск PR fast-path (`quality.yml`)

`.github/workflows/quality.yml` доповнює CI на main/release PRs, надсилає до `main`, відправляє та об’єднує групи. PRs використовує швидкі перевірки з фільтрацією шляху. Постійно вимкнену дублікату збірки видалено; справжні чеки build/package/boot залишаються в CI. Набір модулів і vitest працюють лише в CI (`Unit Tests (N/12)` і `Vitest`).

#### Звіт про тести на забутих братів і сестер

`npm run check:forgotten-sibling-tests` працює як консультативний етап `Fast Quality Gates` і повторно використовує розпізнавач імпорту за картою впливу тесту. Для кожного зміненого виробничого модуля він повідомляє про детерміновані ланцюжки `changed module/symbol -> static consumer -> candidate sibling test`, коли тест-кандидат відсутній у розрізненні запитів на отримання. Підсумок Markdown і результат JSON зберігаються як артефакт робочого циклу `forgotten-sibling-tests` для калібрування перед будь-яким розгортанням блокування.

Реекспорт стовбура та динамічний імпорт є лише діагностикою роздільної здатності; вони ніколи не створюють блокуючого висновку. Переглянуті винятки живуть у `config/quality/forgotten-sibling-allowlist.json`. У кожному записі необхідно назвати тест споживача та кандидата, надати конкретне обґрунтування та пов’язати проблему GitHub або запит на отримання. Неправильно сформовані записи не вдалося закрити. Винятки не можуть придушити видалений тест-кандидат або різницю, яка додає `.skip`/`.todo`; ослаблення твердження та інше маскування залишаються у власності незалежного блокуючого воріт `check:test-masking`.

#### Дві програми перевірки типів відповідають по-різному

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) і `check:build-typecheck` компілюють різні програми за різними параметрами, і той самий файл може бути чистим в одній і повним помилок в іншій.

`tsconfig.build.json` встановлює `"strict": false`, тому `noImplicitAny` вимкнено. Основна конфігурація складає підібраний білий список із 27 файлів із суворішими параметрами та дотримується графіка імпорту кожного запису, тож файли, які ніколи не з’являються в програмі збирання, все ще перевіряються там.

Наслідки мають значення, коли судять про те, чи набраний файл:**нульова діагностика за `check:build-typecheck` не означає нуль** . Видалення `@ts-nocheck` з 26 файлів показало, що 23 з них чисті в програмі збірки; шістнадцять із них виявили близько 120 неявних будь-яких помилок у строгому. Перевірте обидва, перш ніж назвати файл чистим.

#### `check-ui-value-drift` — застарілий шлюз перекладу

Вловлює одну i18n регресію, яку інші ворота структурно не бачать: значення англійською мовою переписується, а переклади, отримані з _попередньої_ англійської мови, залишаються позаду, тому неангломовні користувачі продовжують читати впевнено сформульовану, тепер неправильну копію.

Це справді відправлено. `oauthModal.googleOAuthWarning` було переписано, коли приземлився помічник входу Antigravity (#5203);**39 з 43 локалізацій** зберіг текст, який повідомляє операторам «скопіювати повний URL і вставити його нижче» — потік, який не може завершитися для цього постачальника. Це залишилося непоміченим до #8463 оскільки:

- `sync-ui-keys` заповнює лише ключі, які є **відсутній** , ніколи не є **несвіжий** ;
- `check-ui-keys-coverage` зараховує _присутність_ ключа, тому застарілий переклад вважається покритим;
- `check-translation-drift` відстежує документацію `docs/i18n/<locale>/**.md`, що відображає — і ніколи не читає `src/i18n/messages/*.json`. Блокування в роботі `docs-sync-strict` після повторної синхронізації 2026-09: відредагуйте основний документ → `npm run i18n:run -- --files=<doc>` (на рівні розділу, дешево).

**З урахуванням відмінностей, без підтримки базової лінії.** Він порівнює `en.json` на базі злиття з робочим деревом; для кожного ключа, англійське значення якого змінено, будь-яка локаль, яка все ще містить незайманий переклад, є застарілою. Це свідомо **заморожує наявну заборгованість** — a diff не може виявити, з якої давньої англійської походить давній переклад, тому гейт оцінює лише те, що стосується поточної зміни. Альтернатива (базова лінія хешу для кожного ключа) коштуватиме файлу, згенерованого ~ 600 KB, 3 × найбільшого існуючого базового рівня, що збивається на кожному i18n PR.

Два способи задовольнити це:

1. оновити відповідні переклади, або
2. встановіть для них значення `__MISSING__:<new english>` — а потім середовище виконання обслуговує виправлену англійську (`src/i18n/request.ts::deepMergeFallback`, #7258) і ключові черги для перекладу.

Якщо рядок **значення** змінений, воліти **перейменування ключа** : новий ключ не може успадкувати застарілий переклад. Це використаний шаблон #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Варіанти відхилення значень і нові ключі мають одне незмінне порівняння з `scripts/i18n/resolve-ui-diff-base.mjs`. Робочий процес передає ту саму основу, наконечник основи та потенційний SHAs для обох перевірок. Запуски PR/base-retarget, push і merge-group використовують контекст подій. Відправка гілки-кандидата вимагає його точного відкритого PR або явного введення `i18n_base_sha`. Відправлення або заплановане спостереження `main` або `release/vX.Y.Z` без цього введення порівнює останній комміт з його першим батьківським; це не перевірка всіх успадкованих перекладацьких боргів. Для локального виклику потрібна явна база порівняння, наприклад команда `BASE_REF` вище.

Відсутній або неоднозначний контекст порівняння, нечитабельний або недійсний необхідний каталог і змінений кандидат створюють `INCOMPLETE` з кодом виходу **2** , в тому числі в режимі попередження. Зчитування каталогу використовують `scripts/i18n/read-ui-catalog.mjs`; помилки читання не замінюються порожніми об'єктами. Ані недоступна база, ані неповний вхід не встановлюють PASS.

**Інструменти**

  приміткою.
- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` —
  вимірює кожну числову перевірку так само, як це робить CI, і виводить залишок запасу для кожної перевірки
  (`scripts/quality/baseline-headroom.mjs`). Нічне завдання `baseline-headroom` публікує
  таблицю в підсумку запуску робочого процесу та завантажує свій звіт у форматах JSON/Markdown як
  `baseline-headroom-<run_id>` зі зберіганням протягом 90 днів. Рядки з попередженнями та критичними станами визначають перевірки,
  що перебувають у межах 10% від свого обмеження або вже перевищили його. Переглядайте ці звіти як раннє попередження про
  вичерпання бюджетів; перевіряйте примітки `_rebaseline_*` відповідної перевірки. Завдання більше
  не створює й не оновлює постійну задачу; #12149 зберігає попередню історію звітів.

**Режим нового коду (Clean-as-You-Code) — з 2026-08-30, лише для швидкого шляху PR**

Для подій `pull_request` файл `quality.yml` передає `--base-ref <PR base SHA>` до `check:file-size`,
`check:complexity-ratchets` і `check:dead-code`. Для `check:complexity-ratchets` і
`check:dead-code` перевірка порівнює HEAD із базою злиття **лише для файлів, яких торкнувся PR**
(`scripts/check/newCodeMode.mjs`: база злиття матеріалізується в тимчасовому
`git worktree`, ESLint/knip запускаються там і на HEAD, після чого порівнюються різниці кількості для кожного файлу):

- **блокує** — PR додав порушення цикломатичної/когнітивної складності або мертві експорти у змінених ним файлах
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` у журналі);
- **рекомендаційний** — глобальний підсумок порівняно із зафіксованим базовим рівнем. Успадковане відхилення ніколи не робить
  невинний PR червоним; відхилення відстежується для виправлення під час узгодження релізу та контролюється
  завданням резерву.

`check:file-size` використовує базове посилання за власними правилами (`scripts/check/check-file-size.mjs`, #8522):
він перевіряє кожен файл вихідного коду й тестів у дереві, зчитує кількість рядків кожного з них у базі PR
за допомогою `git show` і позначає файл як непройдений лише тоді, коли той виростає понад більше з двох значень: його базову верхню межу
(`frozen` / `testFrozen` або `cap` / `testCap` для файлу поза базовою лінією) чи його базовий
розмір. Тому файл, який уже відхилився в базі, ніколи не робить невинний PR червоним.

`check:boundary:ratchet` застосовує те саме правило до свого єдиного числа
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): під час подій PR і швидкі
перевірки `quality.yml`, і завдання lint у `ci.yml` передають SHA базової версії PR; базовий коміт
вимірюється з експорту `git archive`, а PR завершується помилкою лише тоді, коли кількість його
зв’язків `open-sse → src` перевищує більше зі значень `metrics.boundaryOpenSseToSrc` і кількості
в базовій версії. Дрейф базової версії вище граничного значення повідомляється
(`base drift herdado`), але ніколи не спричиняє помилку в невинному PR; push → main
зберігає абсолютне граничне значення, а якщо SHA базової версії неможливо визначити,
використовується це значення з попередженням.

Запуски `workflow_dispatch`, повна перевірка перед релізом і нічне завдання перевірки запасу
не мають базової версії PR та зберігають абсолютне (глобальне) порівняння. Покриття,
дублювання й покриття типами наразі залишаються глобальними (їхні інструменти не дають змоги
дешево отримати різницю для окремих файлів) — це кандидати на таку саму обробку.

**Завершення етапу на v4.0 (LTS = суворіше, ніж раніше, а не «повернення до норми»)**

1. На чистій верхівці `release/v4.0.0`: виконайте `npm run quality:headroom --json` для фіксації,
   потім `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, а також `--update` для кожної
   перевірки типів — усі базові значення знижуються до виміряного рівня.
2. Видаліть `_policy` з `quality-baseline.json` (це повторно активує `--require-tighten` і нічне
   накопичення запасу), відновіть `THRESHOLD = 36` (або вище) у `check-openapi-coverage.mjs`.
3. Зробіть обмеження суворішими за виміряні значення там, де модульність дала результат:
   поверніть `cap` розміру файлу до 1000 (або 800), підвищте мінімальні пороги покриття на 5,
   установіть 0 мертвих експортів для модульних пакетів.

## Базовий рівень храповика (`quality-baseline.json`)

Механізм храповика (`scripts/quality/check-quality-ratchet.mjs`) зчитує `quality-baseline.json`
і порівнює його зі щойно зібраним `quality-metrics.json`. Будь-яка метрика, що погіршується
понад допустиме значення epsilon, призводить до невдалої збірки.

Метрики, які наразі відстежуються:

| Метрика               | Напрямок | Значення                                         |
| --------------------- | -------- | ------------------------------------------------ |
| `eslintWarnings`      | `down`   | Кількість попереджень ESLint не повинна зростати |
| `coverage.statements` | `up`     | Покриття інструкцій не повинно зменшуватися      |
| `coverage.lines`      | `up`     | Покриття рядків не повинно зменшуватися          |
| `coverage.functions`  | `up`     | Покриття функцій не повинно зменшуватися         |
| `coverage.branches`   | `up`     | Покриття гілок не повинно зменшуватися           |

Щоб оновити базовий рівень після фактичного покращення:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

Прапорець `--update` записує поточні виміряні значення у `quality-baseline.json`.
Зафіксуйте цей файл у тому самому коміті, що й зміну, яка покращила метрику. PR, який покращує
метрику без оновлення базового рівня, буде виявлено за допомогою `--require-tighten` (Фаза 6A.5,
очікує на реалізацію).

### Ratchet CodeQL : прийом кандидатів та інвентаризація сховища

CI володіє допуском кандидата CodeQL через явний ланцюжок залежностей: `codeql-scan` викликає чотиримовну матрицю в `codeql.yml`, потім `codeql-admission` запускає `node scripts/check/check-codeql-ratchet.mjs --candidate`. `Gate / CI` вимагає обох результатів. Якість зберігає власні цифрові перевірки, але не запитує сканер до того, як виробник закінчить; Сама по собі `Gate / Quality` не є повним допуском кандидата. CodeQL залишається обов’язковим для кандидатів лише з документами.

Політика в `config/quality/codeql-admission-policy.json` вибирає дії, C/C++, JavaScript/TypeScript і Python, набір запитів за замовчуванням, модель віддаленої загрози та режим збірки. Попередня перевірка виробника відхиляє незавершений запис активації та розгалужується за межі явного цільового списку. Поточні цілі є основними, а тести контракту release/v3.8.54. порівнюють цей кінцевий список і тригер підтримки з версією пакета; наступний випуск потребує перегляду адаптації. Існуючий тригер PR із ширшим випуском CI зберігається, але незакріплена мішень повідомляє HOLD перед вилученням, а не отримує невиміряний PASS.

Кожне завдання матриці записує своє фактичне завантаження SARIF ID, мову, категорію, запуск і спробу, ідентифікатор робочого циклу абонента, подію ref/head/base/merge SHA і хеш політики. Залежне завдання завантажує лише квитанції цього запуску та перевіряє дайджести артефактів. Для цього потрібні всі чотири категорії, успішний продюсер і завершена обробка кожного точного завантаження. Він використовує фільтр sarif_id API, а не останній аналіз, знайдений у гілці. Часткові повтори можуть повторно використовувати успішні категорії з попередньої спроби того самого запуску та кандидата, зберігаючи спробу створення; невдалий поточний виробник не може повторно використовувати попередні зелені докази.

Дія CodeQL очікує на обробку, але її закріплена реалізація може попередити та продовжити роботу після помилки читання статусу або очікування вичерпання. Таким чином, прийом ще раз підтверджує обробку. Відсутні категорії, очікують на обробку, невдалі або скасовані завдання, застарілі ідентифікаційні дані, неповна розбивка сторінок або недоступний APIs створюють HOLD і виходять 2. Немає фіксованого очікування незалежного робочого процесу сканера. Несканований PR не може пройти, тому що запит попередження повернув 0. Виміряна кількість вище `metrics.codeqlAlerts.value` виходить 1; базова лінія не підвищується для поглинання сповіщень іншої гілки. [Статус завантаження та аналіз аналізу](https://docs.github.com/en/rest/code-scanning/code-scanning).

Квитанція фіксує завантаження й аналіз IDs, категорії, версії інструментів, ref/SHA, базову лінію та номери сповіщень. Кількість SARIF identity/result, мінімальна кількість правил і точні випадки попередження залишаються обов’язковими. Ідентифікатори PR/analysis перевіряються повторно перед прийняттям. Ці перевірки встановлюють охоплення налаштованої категорії, а не перелік кожного видобутого вихідного файлу. C/C++ без складання не включає код, згенерований під час складання проекту. Виключення джерел все ще потребують перегляду, а атрибуція співавторів потребує порівнянних точних доказів.

`codeql-maintenance.yml` надає push-скани активного випуску та тижневий графік без дублювання виробників PR/main. `nightly-codeql-inventory.yml` зберігає базову лінію для всього сховища окремо, із `--strict-measurement` і помилкою, коли вимірювання недоступне. Витончений стрибок місцевого колекціонера спадщини не є допуском кандидата. Посилення залишається явним `--update` після підтвердженого нижчого загального підрахунку.

Розширений робочий процес не можна публікувати, поки налаштовано параметри за замовчуванням: GitHub відхиляє цю комбінацію. Його політика з версіями залишається на розгляді, доки не буде прочитано перевірений адміністративний перехід. Перед публікацією оператор закріплює репозиторій, хеші head/base/tree, policy/patch/rollback і спостережуваний стан налаштування; `node scripts/quality/codeql-producer.mjs verify-admin-readback` перевіряє надані очікувані та фактичні записи JSON. Це технічний захист, а не схвалення оператора чи заміна для отримання свіжих зчитувань. Маркер PR ніколи не запитує доступ адміністратора. Розгортання та будь-які зміни в сканері вимагають окремого зворотного читання, а також реальних доказів сумісності PR, fork і merge-group.

Форки використовують розміщені бігуни, перевірку без постійних облікових даних, відсутність проекту install/build у виробнику та відсутність успадкованих секретів сховища. GitHub підтримує завантаження SARIF для події pull_request зі своїм скороченим маркером розгалуження; схвалення першого внеску залишається політикою GitHub. Ніколи не використовуйте pull_request_target для виконання ненадійного коду. Підтвердьте фактичні дозволи маркера, analysis_key і всі середовища категорій у контрольованій канарці, перш ніж вважати міграцію завершеною. [Правила завантаження форків](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible), [конфліктні режими налаштування](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows).

**Звільнення - це виклик оператора (Hard Rule #14)** — ніколи не відхиляє сповіщення CodeQL, не записавши технічне обґрунтування в коментарі відхилення: `won't fix` для вимоги передового протоколу, `used in tests` для тестового приладу, `false positive` для дезінфікуючого засобу CodeQL не бачить (прецедент: `docs/security/ERROR_SANITIZATION.md`).

## Політика повторного запуску тестів (WS5.4, v3.8.49)

Повторний запуск налаштовується для кожного раннера окремо, а не глобально — глобальний повторний запуск перетворює реальні регресії
на непомітні нестабільні збої:

| Раннер           | Політика                                                                                                                                                   | Чому                                                                                                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Playwright (e2e) | `retries: 1` лише в CI, з `trace: on-first-retry`                                                                                                          | Часові характеристики браузера/мережі справді недетерміновані; один повторний запуск із трасуванням перетворює нестабільний збій на артефакт, придатний для діагностики |
| Vitest           | БЕЗ глобального повторного запуску. Тест із підтвердженою нестабільністю отримує явний повторний запуск на рівні тесту (видимий у diff і перевірений у PR) | Зберігає список карантину в репозиторії, а не в непрозорому вигляді                                                                                                     |
| node:test (unit) | БЕЗ повторних запусків за жодних обставин                                                                                                                  | Нестабільний модульний тест — це помилка в тесті: виправте її, а не запускайте тест навмання повторно                                                                   |

Цільові SLO після впровадження телеметрії нестабільних тестів (WS5.2/5.3): частота нестабільних збоїв <1% на тест
(поріг «виправити негайно»), частка успішних проходжень ≥95% на пайплайн. Значення, прийняті в галузі як орієнтири, —
їх слід відкалібрувати за нашими власними вимірюваннями.

## Дрейф храповика на рівні релізу (WS5.5, v3.8.49)

Коли храповик (розмір файлу, складність, попередження eslint) регресує на ЧИСТІЙ верхівці гілки релізу
— тобто регресію спричинила КОМБІНАЦІЯ злиттів, а жоден окремий PR не відтворює її
у власній гілці, — виправлення має виконати **капітан релізу, один раз, у
гілці релізу**: надавайте перевагу виділенню коду/рефакторингу; змінюйте базову лінію лише з документованим
обґрунтуванням. Ніколи не перекладайте комбінований дрейф на PR учасника та ніколи
не змінюйте базову лінію окремо для кожного PR (це приховує реальні регресії). Спочатку розрізніть причини: відтворіть
помилку на чистій верхівці в тестовому worktree, перш ніж припускати, що її спричинив ваш PR.

## Фіксація знижень храповика — рух донизу (#8584)

Храповик автоматизований лише наполовину, до того ж не в той бік. **Підвищення** ліміту — це
ручне редагування JSON, що займає десять секунд і є найшвидшим способом розблокувати червоний PR.
**Зниження** ліміту вимагає, щоб хтось запустив `--update` і закомітив результат — а до
появи завдання `bank-ratchet-shrinks` жоден робочий процес цього не робив. Виміряний наслідок
(2026-07-25): 18 заморожених файлів уже мали не більше ніж 800 рядків — ліміт для нових файлів; найгірший випадок
перевищував фактичний розмір у 132 рази (`src/shared/validation/schemas.ts`, 19 рядків із лімітом 2 523);
стеля складності зросла з `1794 → 2169` упродовж ~37 приміток про зміну базової лінії, лише з одним
зниженням (−1); а фразу «посилити через `--update` у наступному циклі» написали 31 раз, але виконали
лише один раз. Ліміт, який пережив код, через який його запровадили, непомітно перетворює кожну завершену
декомпозицію на дозвіл збільшувати код для наступного, хто редагуватиме файл.

`nightly-release-green.yml` → завдання **`bank-ratchet-shrinks`** замикає цей цикл:

|           |                                                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Запуск    | `schedule` (3×/день) + `workflow_dispatch` — навмисно **не** `push`                                                                    |
| Вимірює   | найвищу `release/vX.Y.Z`, з тією самою логікою визначення та захистом від ін’єкцій, що й `release-green`                               |
| Записує   | `check:file-size --update` і `check:complexity-ratchets --update` (обидві команди за своєю структурою можуть лише зменшувати значення) |
| Перевіряє | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                               |
| Доставляє | один завжди актуальний PR до гілки релізу — примусово оновлюваний, без спаму                                                           |

Фіксація виконується пакетно, а не під час кожного push, оскільки вона не має вимог щодо затримки (зафіксувати
зниження протягом 8 годин цілком прийнятно), тоді як запуск під час кожного злиття неодноразово перебудовував би гілку PR
під час кампаній зі злиття та щоразу оплачував би повний прохід ESLint. Виявлення залишається на
push (`release-green`); пакетно виконується лише фіксація.

### Перевірка безпеки

Завдання змінює базові лінії без нагляду, тому саме `verify-ratchet-bank.mjs` робить
це прийнятним. Він порівнює дерево після `--update` з `HEAD` і **перериває завдання
ще до створення будь-якого коміту** — не відкриваючи PR, — якщо не кожна зміна належить до одного з таких типів:

- числовий запис `frozen` / `testFrozen` **знижено** або **видалено**
- `complexity-baseline.json` → `count` **знижено**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **знижено**

Усе інше спричиняє помилку: підвищення числа, додавання запису, зміна `cap`/`testCap` або
видалення/перезапис примітки `_rebaseline_*` (ці примітки є журналом аудиту причин існування кожної
стелі та зберігаються всередині того самого об’єкта `frozen`, що й записи файлів).
Бот, здатний підвищувати ліміт, був би однозначно гіршим за поточний стан. Захист від
регресій: `tests/unit/verify-ratchet-bank.test.ts`.

Завдання ніколи не виконує push до `release/*` — PR зливає людина, тож помилковий результат вимірювання
не може потрапити до гілки без перевірки.

## Політика списків дозволених винятків

Кожна перевірка, яка не може завершитися помилкою через наявні раніше порушення, використовує зафіксований список дозволених винятків
(наприклад, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). Політика така:

**Усувайте першопричину; використовуйте список дозволених винятків лише тоді, коли порушення існувало раніше й
не може бути виправлене в тому самому PR.**

Додаючи запис до списку дозволених винятків:

1. Додайте коментар з обґрунтуванням.
2. Додайте посилання на задачу для відстеження (наприклад, `// #3498 — Phase 2 feature, not yet implemented`).
3. Видаліть запис у тому самому PR, який виправляє порушення — застарілий запис, що більше
   не приховує активне порушення, сам є дефектом (перевірка застарілих правил 6A.3
   завершуватиметься помилкою через осиротілий запис у списку дозволених винятків після її реалізації).

**Не** додавайте записи до списків дозволених винятків, щоб пришвидшити проходження тестів. Успішна перевірка за постійного розширення
списку дозволених винятків створює хибне відчуття якості.

### Коли перевірка завершується помилкою у вашому PR

1. **Уважно прочитайте вивід перевірки** — у ньому точно зазначено, який файл або символ порушив
   правило.
2. **Виправте порушення** — більшість перевірок є детермінованими перевірками файлової системи, які проходять, щойно
   код виправлено.
3. **Якщо порушення існувало раніше** (тобто ви його не внесли, але тепер перевірка
   його охоплює): додайте запис до списку дозволених винятків із коментарем-обґрунтуванням і посиланням на задачу для відстеження.
4. **Якщо перевірка використовує храповий механізм** (покриття, попередження ESLint, дублювання, складність):
   ваша зміна погіршила метрику. Виправте першопричину або (у рідкісних випадках) виконайте
   `npm run quality:ratchet -- --update`, якщо зміна є навмисною, а погіршення
   метрики — прийнятним, але поясніть причину в описі PR.
5. **Рекомендаційні перевірки** (`continue-on-error: true`) мають інформаційний характер — вони не блокують
   злиття, але відображаються у зведенні CI. Усе одно виправляйте їх.

#### `check-key-completeness` — шлюз паритету наборів ключів

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, завдання `i18n-ui-coverage`).
Порівнює набір кінцевих ключів кожного `src/i18n/messages/<locale>.json` з `en.json` і завершується
помилкою за наявності будь-якого відсутнього або зайвого кінцевого ключа, незалежно від того, коли
цей ключ було додано. Заповнювачі `__MISSING__:` вважаються наявними (їхній вміст належить до сфери
відповідальності шлюзу співвідношення). Це абсолютне доповнення до двох шлюзів на основі різниці
та відсотків: `check-ui-keys-coverage` встановлює мінімальний поріг 80 % для кожної локалі
(навіть за відсутності 43 ключів із ~13 000 результат усе одно становить 99,7 %), а
`check-new-key-coverage` перевіряє лише ключі, які PR додає до `en.json`. Пакет локалей генерується
з актуального `en.json` у день створення його гілки, після чого переклад триває кілька днів, тоді
як у базовій гілці продовжують додаватися ключі; сам пакетний PR не додає жодного ключа, тому обидва
споріднені шлюзи не спрацювали, коли пакет 1 (#13044) було об’єднано з браком 43 ключів у дев’яти
локалях, а пакет 2 (#13660) — із браком 10 ключів у восьми (2026-09-15). Щоб виправити червоний
статус, виконайте `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`;
кінцевий ключ зі статусом `extra` означає, що його було видалено з джерела, — видаліть його
з локалі. `--warn` повідомляє про проблему без завершення з помилкою.
`--catalog=cli` виконує таке саме порівняння для `bin/cli/locales`
(`npm run i18n:check-keys:cli`); обидва кроки містяться в завданні `i18n-ui-coverage`.

#### `check-new-key-coverage` — шлюз i18n для нових ключів

Споріднений із `check-ui-value-drift`. Той шлюз виявляє випадки, коли англійське значення було
**переписано**, а його переклади залишилися без змін; цей шлюз виявляє випадки, коли англійський
ключ було **додано**, але деякі локалі його так і не отримали.

`check-ui-keys-coverage` не може виявити проблеми цього класу: він установлює мінімальний відсотковий
поріг для кожної локалі, а одинадцять відсутніх ключів із ~13 000 залишають покриття на рівні
99,9 %. Відсотковий показник для окремої мови не здатен виразити твердження «цю функцію випущено
без перекладу» — цілу функцію можна додати до нової локалі без жодного тексту, і показник навіть
не зміниться.

Інцидент, який він формалізує: на етапі 3 Orchestration Canvas одинадцять його ключів було
перекладено для 42 локалей, що існували на той момент. Кілька годин потому пакет мов ЄС (#13044)
збільшив кількість локалей у репозиторії до 51, а дев’ять нових локалей (`el`, `et`, `ga`, `hr`,
`lt`, `lv`, `mt`, `sl`, `sr`) так і не отримали цих ключів. `deepMergeFallback` підставляє
англійський текст для відсутнього ключа, тому наслідком був неперекладений, а не порожній
інтерфейс — реальна проблема, яка за своєю природою залишалася непомітною.

Як і споріднений шлюз, він **враховує різницю**, порівнюючи англійську версію в базі злиття
з робочим деревом, тому вже наявні прогалини залишаються зафіксованими, а для ввімкнення шлюзу
не знадобилася міграція.

**Маркер `__MISSING__:<english>` не задовольняє цю перевірку (з 2026-09-17).** Раніше він був
задокументованим способом відкласти переклад — середовище виконання повертається до коректного
англійського тексту, — доки вісім PR із функціональністю від 2026-09-16 не додали 61 ключ
і не проставили цей маркер у всіх 65 локалях замість перекладу: цей шлюз прийняв кожен із них,
жоден PR не було заблоковано, а обов’язковий шлюз співвідношення справжніх перекладів після цього
завершився помилкою на верхівці релізної гілки для всіх (pt-BR 3,2 % > 2,5 % + 0,5). Тепер маркер
оцінюється як відсутній переклад. Щоб виправити червоний статус, виконайте
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` або
обробіть усі локалі паралельно за допомогою `npm run i18n:translate-new-keys`
(`scripts/i18n/translate-new-keys.sh`, безпечно працює у від’єднаному режимі та відмовляється
запускатися без змінних середовища `OMNIROUTE_TRANSLATION_*`). Ключ, який має залишатися
англійською мовою (зафіксована назва продукту, рушія або прапорця), повинен міститися
в `scripts/i18n/untranslatable-keys.json`, а не приховуватися за маркером. `vi` повністю
забороняє маркери (`tests/unit/i18n-vi-completeness.test.ts`).

#### `check-vitest-exclusions` — шлюз відкладених тестів

Файл у списку `exclude` в `vitest.config.ts` — це тест, який не виконується, хоча для того,
хто переглядає дерево, він виглядає як покриття. Шістдесят два файли накопичилися за коментарем
`// #8618 — pre-existing failure; remove this exclusion when fixed`. Задачу #8618 було закрито
2026-08-11, тоді як відстежуваний нею список зріс із 45 до 62 записів, кожен новий із яких
успадковував коментар із посиланням на вже закриту задачу. Коли список нарешті перевірили окремо
для кожного файла (#13204), **51 із 62 тестів успішно пройшли на поточному дереві без жодних змін
у вихідному коді**.

Шлюз вимагає, щоб кожен виняток, який відповідає реальному файлу, (a) містив номер задачі
для відстеження та (b) був зазначений у `config/quality/vitest-exclusions.json` разом із виміряним
статусом, завдяки чому додавання винятку стає придатною для перевірки різницею в окремому файлі,
а не ще одним рядком у масиві із 60 записів. Він навмисно не запускає виключені тести повторно —
це займає ~10 хвилин і має виконуватися в періодичному завданні; в інвентарі зазначається, коли
кожен тест востаннє перевіряли.
