Цей документ є авторитетним довідником щодо всіх шлюзів якості CI в OmniRoute.
У ньому описано кожен шлюз, що він перевіряє, у якому завданні CI запускається, чи використовує
базову лінію з храповим механізмом або політику успішного/неуспішного проходження, а також чи блокує він збірку або має рекомендаційний характер.

Короткий огляд і політику списку дозволів див. у розділі "Шлюзи якості та храпові механізми"
у `AGENTS.md`. Критичну оцінку, класифікацію зрілості та незалежний від інструментів
план відтворення цієї ж системи див. у
[Посібнику зі шлюзів якості](../ops/QUALITY_GATE_PLAYBOOK.md).

## Інвентаризація гейтів і профілі виконання

### Допуск кандидатів

Робочі процеси CI та Quality Gates кожен видають стабільний вердикт: `Gate / CI` і
`Gate / Quality`. Їхня версіонована політика допуску перелічує кожне висхідне завдання як
обов’язкове або рекомендаційне. Застосовне обов’язкове завдання має завершитися успішно:
відсутні, скасовані, пропущені, очікувані та невідомі результати не можуть встановити PASS.
Допустима класифікація лише документації або лише каталогу може зробити кодовий канал
незастосовним; чернетка PR не є прийнятим кандидатом. Мітка `hotfix` не скасовує вимогу
щодо доказів.

Обидва робочі процеси охоплюють PR до гілок main/release, push до `main`, ручний запуск
і події merge-group. Push, dispatch і merge-group запускають повний вибір. Push до
`release/**` не запускає їх (2026-10-18): кожна зміна вже виконала матрицю у своєму PR,
а об’єднана комбінація є завданням Release-Green (`docs/ops/RUNNER_BOX.md` → Hosted lane).
Fork і групи злиття використовують hosted runners для завдань, які інакше вибирають
self-hosted runners; перед розгортанням потрібно перевірити достатню місткість hosted.

Звичайний PR запускає швидкий вибір. Канали `full-code` і `full-code-e2e` політики
допуску (E2E, інтеграційні перевірки, артефакт пакета, перевірка Electron, Bun SQLite,
клієнти екосистеми та протоколу) запускаються лише в чернетці черги Mergify або під час
повного запуску:
`gh workflow run ci.yml --ref <branch>`.

Кожна квитанція JSON ідентифікує SHA перевіреного коду, запуск робочого процесу та спробу.
CLI відхиляє невідповідність SHA checkout/event. Тести робочого процесу прив’язують членство
в політиці до списку `needs` завдання вердикту, тому новий або вилучений канал не може
непомітно зникнути. Квитанції охоплюють власний робочий процес, але не публікацію,
розгортання чи внутрішні компоненти наявного рекомендаційного сканера. Активація обох
назв перевірок у правилах гілки є окремою адміністративною зміною; додавання цих завдань
саме по собі не захищає гілку.

### Черга злиття

Мітка `queue` надсилає PR до черги Mergify (`.mergify.yml`). Mergify відкриває чернетку PR у
гілці `mergify/merge-queue/`, CI запускає там повний вибір, а початковий PR зливається,
коли проходять `Gate / CI`, `Gate / Quality` і
`Merge integrity (changelog + generated skills)`.

Mergify записує зведення черги в опис чернетки, і інші застосунки також можуть його
редагувати. Подія `pull_request` `edited` для такої чернетки отримує власну групу
конкурентності (`-queue-edit-<run_id>`), тому не може скасувати фактичний запуск чернетки,
а також пропускає gate і матрицю. Запускається лише `Merge integrity`. Пропущене завдання
gate має іншу назву перевірки, оскільки Mergify сприймає пропущений `Gate / CI` як невдалу
перевірку та вилучає PR із черги.

Після вилучення з черги push не завжди повторно додає PR до черги. Додайте до нього коментар
`@mergifyio queue`.

### Збережені докази в редукторі прийняття

`scripts/quality/validate-release-acceptance.mjs` редукує наданий план і його
маніфести; він не встановлює, що план охоплює повний конвеєр випуску.
У його звітах явно встановлюється `releaseAcceptance: false`, навіть коли цей план має
статус `VERIFIED`. Робочий процес `release-acceptance.yml` і досі використовує тіньові
фікстури, а не справжні квитанції складання, пакування, запуску чи просування.

CLI вимагає `--evidence-root` для перевірки збережених доказів. Файли розв’язуються як
`<evidence-root>/<artifact_id>/<member>` і хешуються за SHA-256. Запис PASS без доказів,
відсутній або змінений файл, небезпечний шлях чи символічне посилання перешкоджають
перевірці. Відсутні файли не є еквівалентом порожніх успішних журналів. Наявні перевірки
SHA/run/attempt залишаються незалежними: відповідні байти не можуть виправити застарілу
квитанцію. Цілісність файлу не є доказом автентичності виконання або просування артефакту.

### Інвентаризація статичного сканування

Версіонований інвентар npm-аліасів і членство в статичному скануванні зберігаються в
`config/quality/gate-manifest.json`. Запустіть `npm run check:gate-manifest`, щоб
перевірити назви скриптів і точні команди відповідно до `package.json`; додавання,
вилучення та зміни команд спричиняють помилку як локального hook, так і завдань
класифікації змін у CI. Аліас не є завданням робочого процесу, екземпляром матриці або
тестовим прикладом: ці кількості не можна подавати як взаємозамінні.

Використовуйте `npm run quality:scan -- --list` або `npm run quality:scan:fast -- --list`,
щоб переглянути вибрані аліаси без їх виконання. Runner викликає npm entrypoint, тому його
середовище виконання (зокрема Bun, якщо налаштовано) зберігається. Маніфест записує аліаси
поза цими профілями як такі, що викликаються окремо, а команди обслуговування заборонені в
профілях сканування лише для читання.

Ці профілі охоплюють лише статичне сканування. Вони не засвідчують продуктові тести,
покриття, пакування, зовнішні перевірки або повне прийняття кандидата до випуску.
Допуск робочого процесу використовує пов’язаний `config/quality/admission-policy.json` і
`scripts/quality/admission-verdict.mjs`. Профілі release-observer залишаються окремими;
перевіряйте їхні застосовні перевірки та квитанції незалежно. Статичні команди повного
observer оголошені в `config/quality/release-green-static-profile.json`, включно з
`audit:deps`, вибором mutation-test і перевірками перекладів. Loader перевіряє npm-команди
відповідно до package.json і змодельованих декларацій CI/Quality; він відхиляє розбіжності,
замість того щоб виконувати shell-токени як аргументи. Вивід SKIP/INCOMPLETE обов’язкового
сканера не може встановити PASS. Профіль записує свої зовнішні виключення та не замінює
hosted coverage, тестові матриці, докази пакета або розгортання. Наведений нижче опис
інвентарю є довідковим і не доводить, що gate справді виконувався.

Скрипти розташовані в `scripts/check/` (гейти політики) і `scripts/quality/` (механізм
ratchet). Єдиним джерелом правди для CI є `.github/workflows/ci.yml`.

### Швидкий шлях PR для випуску (`quality.yml`)

`.github/workflows/quality.yml` доповнює CI для PR до main/release, push до `main`,
dispatch і merge groups. Для PR використовуються швидкі перевірки з фільтрацією за шляхами.
Постійно вимкнену дубльовану збірку вилучено; справжні перевірки збірки/пакета/запуску
залишаються в CI. Набір модульних тестів і vitest запускаються лише в CI
(`Unit Tests (N/8)` і `Vitest`).

| Завдання                                         | Область застосування                                                                                                                                      | Блокує                  |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `Docs Gates (fast-path)`                         | PR документації/коду; посилання на документацію API та docs-all                                                                                           | Так                     |
| `Fast Quality Gates`                             | PR коду; статичні перевірки, перевірка типів, перевірка типів дашборда, модульні тести для змінених компонентів, забуті споріднені тести (рекомендаційно) |
| `No new ESLint warnings`                         | PR коду; захисна перевірка lint з урахуванням подавлень                                                                                                   | Так, зокрема для форків |
| `Merge integrity (changelog + generated skills)` | Не чернеткові PR; синхронізація журналу змін і згенерованих навичок                                                                                       | Так, зокрема для форків |

#### Звіт про забуті споріднені тести

`npm run check:forgotten-sibling-tests` запускається як рекомендаційний крок `Fast Quality Gates` і повторно використовує
резолвер імпортів, що лежить в основі карти впливу тестів.
Для кожного зміненого продуктивного модуля він повідомляє детерміновані ланцюжки
`changed module/symbol -> static consumer -> candidate sibling test`, якщо кандидатний
тест відсутній у diff запиту на злиття. Зведення Markdown і результат JSON зберігаються як
артефакт робочого процесу `forgotten-sibling-tests` для калібрування перед будь-яким блокувальним розгортанням.

Повторні експорти через barrel і динамічні імпорти є лише діагностикою розв’язання; вони ніколи не створюють
блокувальних зауважень. Перевірені винятки зберігаються у
`config/quality/forgotten-sibling-allowlist.json`. Кожен запис має містити назви споживача та кандидатного
тесту, конкретне обґрунтування й посилання на проблему або запит на злиття GitHub. Некоректно сформовані записи
призводять до відхилення. Винятки не можуть приховати видалений кандидатний тест або diff, що додає `.skip`/`.todo`;
ослаблення перевірок та інше маскування залишаються відповідальністю незалежно блокувального
гейта `check:test-masking`.

#### Дві програми перевірки типів дають різні відповіді

`typecheck:core` і `check:build-typecheck` компілюють різні програми з різними
параметрами, тому той самий файл може бути чистим в одній і містити безліч помилок в іншій.

`tsconfig.build.json` встановлює `"strict": false`, тому `noImplicitAny` вимкнено. Основна
конфігурація компілює підібраний список дозволених 27 файлів із суворішими параметрами та проходить
граф імпортів кожного запису, тому файли, які ніколи не потрапляють до програми збірки, все одно
перевіряються там.

Цей наслідок важливий під час оцінювання типізації файлу: **нуль діагностичних повідомлень
у `check:build-typecheck` не означає нуль**. Видалення `@ts-nocheck` із 26
файлів показало, що 23 з них чисті в програмі збірки; у шістнадцяти з них сувора перевірка виявила
близько 120 помилок implicit-any. Перевіряйте обидві програми, перш ніж вважати файл чистим.

| `check:docs-symbols`           | Кожне посилання `/api/...` у `docs/**/*.md` відповідає реальному `route.ts` (запобігання галюцинаціям)                                                                                      | Так                         |
| `i18n translation drift`       | Дзеркала `docs/i18n/**` порівняно з `.i18n-state.json` — рекомендаційно для PR (дзеркала оновлюються хвилею перекладу), суворо під час push і вночі                                         | **Рекомендаційно** для PR   |

#### Дзеркала перекладів є похідними файлами (режим PR проти режиму випуску)

Функціональний PR редагує лише англомовні джерела. Дзеркала `docs/i18n/<locale>/**` (зокрема 66
копій `llm.txt` і перекладені файли `CHANGELOG.md`) та `.i18n-state.json` перезаписуються одним
кроком хвилею перекладу (гілки `docs/i18n-*` / `chore/i18n-*`, запланований
`i18n-mirror-refresh.yml`) і випуском (`npm run release:sync-changelog-i18n`). Тому перевірки
дзеркал виконуються у двох режимах, які визначаються через `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`,
потім `OMNIROUTE_GATE_MODE`, потім подія Actions; локальний запуск використовує `release`):

- `check:docs-sync` — у режимі випуску виконується кожна перевірка. У режимі PR зберігаються версія package.json/OpenAPI,
  заголовки кореневого CHANGELOG і захист від застарілих документів, а для дзеркальних копій
  `llm.txt` і перекладених секцій CHANGELOG виводиться
  `SKIP reason=pr-mode` —
  якщо тільки PR не записує дзеркала: гілка head, оголошена як записувач сімейства
  `docs/i18n/**` у `config/quality/derived-paths/*.json`, виконує обидві перевірки суворо, а коли
  база diff визначається, зміна, чий власний diff редагує `docs/i18n/<locale>/llm.txt` або
  `CHANGELOG.md`, виконує відповідну перевірку суворо. База diff не визначається в checkout
  глибиною 1 (завдання `docs-sync-strict`), тому режим PR також виконує одну перевірку, якій база не потрібна:
  кожен дзеркальний `llm.txt` має існувати, зберігати свій роздільник `---` і містити або тіло з кореневого файлу,
  або тіло, спільне для більшості дзеркал. Якщо база перемістилася, усі дзеркала однаково застарівають і перевірка проходить;
  ручне редагування одного дзеркала призводить до помилки. Для перекладених файлів `CHANGELOG.md` у checkout PR
  глибиною 1 такої перевірки немає.
- Хук pre-commit запускає `check-docs-sync.mjs --mode=pr`: коміт оцінюється за тим, що він робить.
  Без цього прапорця локальний запуск виконується в режимі випуску, і один об’єднаний PR, який редагує кореневий `llm.txt`,
  блокував би кожен наступний коміт на цій базі, доки не було б виконано хвилю. Це саме правило діє для будь-якого
  перевірочного шлюзу, чутливого до режиму, який запускає хук Husky: хук передає `--mode=pr`, а суворий результат
  залишається за запусками в режимі випуску (release PR, надсилання змін до `main`, звичайний локальний запуск).
- Модульні тести вмісту дзеркал (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`,
  `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`,
  `docs/*-locales`) — у режимі випуску перевіряють кожну локаль. У режимі PR перевіряються лише дзеркала,
  актуальні щодо англійського джерела відповідно до `.i18n-state.json` (хеш усього файлу або записаний хеш секції,
  яку фіксує тест), а застарілі пропускаються із зазначенням причини. Перевірки походження `target_hash` виконуються
  для кожної локалі в обох режимах. Актуальність визначається для кожної секції `## `; модульний
  `run-translation.mjs` обчислює хеші. Довга секція (реєстр шлюзів у цьому файлі займає приблизно половину)
  означає, що будь-яке редагування в ній робить ці дзеркала застарілими, а їхні перевірки в режимі PR пропускаються
  до наступної хвилі. Якщо якоря більше немає в англійському джерелі, використовується порівняння всього файлу.
- `i18n translation drift` — інформаційний на PR, суворий під час надсилання змін, нічного запуску та створення
  випуску, щоб застаріле дзеркало не потрапило до випуску.

`scripts/i18n/sync-llm-mirrors.mjs` (також експортується як `syncLlmMirrors()`, із `--dry-run`)
перезаписує дзеркала `llm.txt`; оновлення випуску, хвиля перекладу та запланований
`i18n-mirror-refresh.yml` запускають його (оновлення виявляє застарілі дзеркала `llm.txt` у режимі пробного запуску,
оскільки звіт про дрейф їх не перелічує, і синхронізує їх перед `check:docs-all`).

Дванадцять SVG-файлів README у `docs/diagrams/` генеруються (`scripts/docs/gen-readme-<name>.mjs`;
`npm run docs:readme-diagrams` повторно генерує всі). Для кожного є модульний тест побайтного порівняння
(`tests/unit/docs/readme-*-svg.test.ts`, завдання `test-unit`), який завершується помилкою, якщо зафіксований файл
застарів у режимі випуску; у PR `check:generated-artifacts` оцінює SVG, який редагує PR, а дрейф бази
залишається на оновлення випуску (див. [Згенеровані файли та похідні базові стани, записані під час випуску](#generated-files-and-derived-baselines-written-at-release)) — а `check:docs-counts` зчитує канонічні числа з їхніх вузлів `<text>` — саме тому
крок обведення зберігає кожен обведений рядок у файлі як невидимий `<text>`. Перевірка канонічних чисел SVG
зчитує файли, перелічені в `SVG_DIAGRAM_FILES` (`scripts/check/check-docs-counts-sync.mjs`): `docs/diagrams/readme-hero.svg`,
`free-tier-budget.svg`, `promise-pillars.svg`, `comparison-table.svg`, `cli-terminal.svg`,
`tier-cascade.svg`, а також `public/images/tier-flow-dark.svg` і `tier-flow-light.svg`;
твердження щодо free-forever, catalog-entry, recurring-pool і scoring-factors також зчитують
`promise-pillars.svg`, `free-tier-budget.svg` і `strategies-grid.svg`. Числа, які малюють ці
генератори (загальна кількість провайдерів, інструменти MCP, стратегії маршрутизації, провайдери free-forever тощо),
надходять зі знімка фактів `docs/reference/derived-facts.json` через `scripts/docs/readmeFacts.mjs`,
а не з літералів, тому повторне генерування діаграми в будь-якій гілці відтворює зафіксований файл.
`free-tier-budget.svg` малює свої рядки з того самого знімка (`code.freeTierBudget`, зведення каталогу,
зафіксоване пробою фактів), тому зміна `FREE_MODEL_BUDGETS` потрапляє на картку під час наступного оновлення,
а не спричиняє помилку CI.

### Похідні значення: режими шлюзів `pr` і `release`

Функціональний PR ніколи не записує значення, що залежать від стану його бази: кількість провайдерів, міграцій,
інструментів MCP і стратегій, числа у SVG README, знімок фактів. Один крок перераховує їх усі —
`npm run release:refresh-derived`; його запускають випуск і нічний PR оновлення похідних даних.
Тож **між випусками база навмисно відстає від актуального коду**, і шлюз або тест,
який порівнював би дерево з актуальним кодом, завершувався б помилкою в кожному PR після того,
як інший PR додав провайдера. Шлюзи, які оцінюють похідні значення, працюють в одному з двох режимів,
визначених `scripts/check/lib/gateMode.mjs` (перша відповідність має пріоритет):

1. `--mode=pr|release` у командному рядку;
2. змінна середовища `OMNIROUTE_GATE_MODE` (`pr` або `release`);
3. автоматично, з події GitHub Actions: `pull_request`, чий head не є `release/v*`,
   `merge_group` або push до `omni-queue/**` → `pr`; усе інше (push, schedule,
   dispatch, release PR `release/v* → main`, будь-який локальний запуск) → `release`.

Що саме перевірка `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) вважає помилкою в кожному режимі:

| Режим     | Вважається помилкою                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Потрібні актуальні факти |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `release` | Кожна перевірка, строге порівняння з фактами, зібраними з дерева (поведінка, яка завжди була в gate): застарілий лічильник, версія, мінімальний поріг покриття або число в SVG є STRICT-відхиленням                                                                                                                                                                                                                                                                                | Так                      |
| `pr`      | Лише те, що змінила ця зміна, порівняно з базою PR за допомогою тих самих засобів вилучення тверджень: (1) кероване значення, якого не існувало в базі для цієї перевірки та файлу ("PR змінив кероване число — відновіть рядок до тексту з бази"); (2) обов’язкове твердження, яке містила база, але було втрачено в head. Інваріанти вмісту, для яких факти не потрібні, виконуються як у режимі release; перевірки, призначені лише для release, перелічуються та пропускаються | Ні                       |

Файли з інструкціями для агента **не містять жодного похідного лічильника**: `AGENTS.md`, `llm.txt` (і його
копії `docs/i18n/*/llm.txt`), форк bs `AGENTS.md`, `open-sse/services/AGENTS.md`,
`src/shared/constants/agentSkills.ts`, `skills/README.md` і кожен `skills/*/SKILL.md` посилаються на
джерело (наприклад, `ROUTING_STRATEGY_VALUES` у `src/shared/constants/routingStrategies.ts`) і натомість
на `npm run facts`. Інваріант "No derived counts (agent-instruction file …)" виявляє лічильник там
(провайдери, міграції, інструменти та області MCP, стратегії маршрутизації, фактори оцінювання, пакети режимів)
в обох режимах, тому оновлення release ніколи не має перезаписувати файл інструкцій.

У режимі `pr` гілки авторів можуть редагувати керовані значення: `chore/derived-*` (нічне оновлення),
`release/v*` і хвилі перекладів `docs/i18n-*` та `chore/i18n-*`
(`scripts/check/lib/derivedClaimsDiff.mjs`). Пакетні черги (`merge_group`, чернетки Mergify,
`omni-queue/**`) повторно не оцінюються: вони об’єднують PR, які gate уже оцінив по одному.

Коди завершення: `0` — усе чисто · `1` — STRICT-відхилення (або м’яке відхилення з `--strict`) чи порушення
керованого значення · `2` — інфраструктура — факти коду не вдалося зібрати (probe tsx завершився з помилкою або
перевищив час очікування; тайм-аут задається через `OMNIROUTE_FACTS_TIMEOUT_MS`, стандартне значення — 600000 мс)
або в CI не вдалося визначити базу diff PR. Код завершення 2 ніколи не означає розбіжність документації: повторно
запустіть job або виправте середовище.

Де виконується кожен режим:

| Де                                                                                                                 | Режим                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Feature PR — job `docs-sync-strict` у `ci.yml`, крок "Docs accuracy" у `quality.yml`                               | `pr` (автоматично); job передає базу як `BASE_SHA` і виконує checkout із `fetch-depth: 2`                                                                                                                     |
| Кандидати `merge_group`, `omni-queue/**`, повний список перевірок merge train                                      | `pr`                                                                                                                                                                                                          |
| Release PR (`release/v* → main`), push-операції, заплановані та ручні запуски                                      | `release`                                                                                                                                                                                                     |
| Release-Green (`scripts/quality/validate-release-green.mjs`)                                                       | Елементи HARD виконуються з `OMNIROUTE_GATE_MODE=pr` ("чи зламала база?"); елемент DRIFT `derived-refresh` виконує `npm run release:refresh-derived -- --check` (строгий режим, ніколи не відкриває base-red) |
| Release (`/generate-release`, фази 0a і 1; підключення skill є окремою зміною, схваленою відповідальним власником) | `npm run release:refresh-derived` записує похідні файли; власні перевірки release PR потім виконуються в режимі `release`                                                                                     |
| `nightly-derived-refresh.yml` (щодня, найвищий `release/vX.Y.Z`, пропускається під час release-freeze)             | `npm run release:refresh-derived -- --profile=nightly`; у разі diff залишає відкритим ОДИН PR із `chore/derived-refresh`; ніколи не виконує merge                                                             |

Команди, що лежать в його основі:

- `npm run facts` виводить кожне похідне число у форматі JSON (`scripts/release/facts.mjs`).
  `--key=code.mcpTools` виводить одне значення, а `--snapshot` читає зафіксований знімок замість
  актуального дерева. Завершується з кодом 2, якщо факти неможливо зібрати.
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) перераховує похідні
  файли за один прохід у такому порядку (ідентифікатори кроків для `--only=`):
  `provider-reference`
  (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (знімок), `numbers` (план перезапису,
  створений перевіркою кількості, застосовується до документації, а потім переноситься до її
  дзеркал у `docs/i18n/`), `readme-diagrams`,
  `skills` (згенерований `SKILL.md`), `e2e-timings` (пропускається, доки дерево не міститиме
  `syncE2eTimings`), `ui-keys` (видаляє ключі, вилучені з `en.json`, а з
  `--rewritten-since=<ref>` — за замовчуванням `origin/main` — повторно ставить у чергу
  англійські значення, переписані після останнього випуску), `llm-mirrors` і `verify-generated`
  (після запису `check:generated-artifacts` і `check:agent-skills-sync` у режимі випуску мають
  пройти; пропускаються в `--check` і коли `--only` не містить цей крок; помилка має код 2). Крок
  `changelog` є необов’язковим (`--with-changelog`, лише профіль випуску).
  `--profile=nightly` ніколи не змінює твердження про версію. З `-- --check` нічого не записується,
  а процес завершується з кодом 1, якщо будь-який файл мав би змінитися або кероване значення
  потребує ручного редагування (виводяться обидва списки); код 2 означає інфраструктурну помилку.
  `--json` виводить результат у форматі JSON.
- `docs/reference/derived-facts.json` — це знімок фактів, використаних під час останнього
  оновлення. Записувати його може лише оновлення. Генератори SVG для README читають його, а
  модульні тести під час перевірки PR порівнюють зафіксовану документацію та згенеровані файли
  саме з ним — ніколи з актуальним кодом. Єдине порівняння з актуальним кодом у наборі тестів —
  «оновлення випуску замикає цикл» у `tests/unit/check-docs-counts-sync.test.ts`: з актуальними
  фактами план перезапису, застосований у пам’яті, не залишає жодного невідповідного STRICT,
  про який не повідомлено, а повторне планування нічого не змінює.

Щоб відтворити локально (локальний запуск за замовчуванням використовує `release`):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

Якщо немає доступної бази (відсутні `BASE_SHA`/`BASE_REF` і немає локального
`origin/release/v<version>`), локальний запуск у режимі `pr` виводить попередження та пропускає
порівняння замість завершення з помилкою.

Потрібен `fetch-depth: 0` — перевірка розбіжностей значень порівнює `en.json` із базою злиття.

**Два режими (з 2026-11-13).** PR функції додає або переписує ключі в `en.json` (і
`bin/cli/locales/en.json`) та не змінює жодної іншої локалі; `check:pr-derived-paths` (завдання
`pr-test-policy`, сімейство `config/quality/derived-paths/translation.json`) завершується помилкою
для PR функції, який це робить. Інші локалі доповнюються один раз за випуск за допомогою
`release:refresh-derived`, який викликає `syncUiKeys()` у `scripts/i18n/sync-ui-keys.mjs`
(додає відсутні ключі, видаляє вилучені, позначає переклади переписаних англійських значень за
допомогою `rewrittenSinceRef`, перекладає), або під час хвилі перекладу.
Перевірки читають режим із `scripts/check/lib/gateMode.mjs`: у режимі `pr` (PR функції,
`merge_group`, `omni-queue/**`) наведені перевірки режиму випуску виводять `SKIP reason=pr-mode`
і завершуються з кодом 0; у режимі `release` (PR випуску, надсилання до `main`,
`workflow_dispatch`, локальні запуски) вони залишаються суворими, як і раніше, а для PR випуску
перевірки, що враховують розбіжності, отримують `BASE_REF=origin/main`, тому перевіряють кожен
ключ, доданий або переписаний у цьому циклі. Попередній результат для PR функції можна локально
переглянути за допомогою `--mode=pr`.

PR, який у режимі `pr` все ще змінює каталоги локалей (хвиля перекладу, оновлення перед випуском або виправлення, що стосується лише перекладу), не пропускається: `check-key-completeness` порівнює кожен змінений ним каталог із тим самим каталогом у базовій версії злиття (`scripts/i18n/lib/touched-catalogs.mjs`) і завершується помилкою, якщо каталог втратив ключ, якого немає в `en.json`, якщо справжній переклад перетворився на маркер `__MISSING__:` або на англійський текст, чи якщо значення більше не інтерполює заповнювачі/теги англійського рядка, якого PR не змінював. Каталог, доданий у PR, повинен містити весь набір ключів `en.json`. Це охоплює те, що побачили б перевірки співвідношення та відповідності CLI для каталогів, яких торкається PR.

Модульні тести відповідності локалей (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`,
`i18n-placeholder-parity`) використовують ті самі режими через `tests/_helpers/localeParityMode.ts`: у
режимі `pr` вони пропускають перевірки відповідності ключів і залишають оновленню перед випуском перевірку відповідності заповнювачів для ключів, англійський текст яких змінився відносно базової версії злиття (для всіх ключів, коли неглибока копія, яку використовує завдання модульних тестів, не може її прочитати). Цей допоміжний модуль є **єдиним** дозволеним пропуском, залежним від режиму:
`check:test-masking` враховує `.skip(` і `{ skip: true }`, але не обчислюване
`{ skip: "<reason>" }`, яке він повертає, тому `tests/unit/locale-parity-mode.test.ts` фіксує список тестів, яким дозволено його використовувати — додавання нового тесту до цього списку є зміною, що проходить рев’ю.

#### `check-ui-value-drift` — перевірка застарілого перекладу

Виявляє одну регресію i18n, яку інші структурні перевірки не можуть побачити: англійське значення переписується, а переклади, створені на основі _попереднього_ англійського тексту, залишаються незміненими, через що користувачі неанглійських локалей продовжують читати впевнений за тоном, але вже неправильний текст.

Це справді сталося. `oauthModal.googleOAuthWarning` було переписано після появи допоміжного компонента входу Antigravity (#5203); **39 із 43 локалей** зберегли текст із вказівкою операторам «скопіювати повну URL-адресу та вставити її нижче» — потік, який неможливо завершити для цього провайдера. Проблему не помічали до #8463, оскільки:

- `sync-ui-keys` доповнює лише **відсутні** ключі, ніколи не оновлюючи застарілі;
- `check-ui-keys-coverage` підраховує _наявність_ ключів, тому застарілий переклад вважається покритим;
- `check-translation-drift` відстежує дзеркала документації `docs/i18n/<locale>/**.md` —
  він ніколи не читає `src/i18n/messages/*.json`. Він запускається в завданні `docs-sync-strict`: має рекомендаційний характер для PR, але є обов’язковим для push і нічних запусків; хвиля перекладу оновлює дзеркала, а не PR із функціональною зміною.

**Залежить від diff, а не від базової лінії.** Він порівнює `en.json` у базовій версії злиття з робочим деревом; для кожного ключа, значення якого в англійському каталозі змінилося, будь-яка локаль, у якій досі зберігається незмінений переклад, вважається застарілою. Це навмисно **фіксує наявний борг** — diff не може показати, від якого старого англійського тексту походить давній переклад, тому перевірка оцінює лише те, чого торкається поточна зміна. Альтернатива (хеш-базова лінія для кожного ключа) потребувала б згенерованого файлу розміром близько 600 КБ, що втричі більше за найбільшу наявну базову лінію, і змінювалася б у кожному i18n PR.

Є два способи виконати цю перевірку:

1. оновити відповідні переклади, або
2. встановити для них `__MISSING__:<new english>` — середовище виконання тоді використає виправлений англійський текст
   (`src/i18n/request.ts::deepMergeFallback`, #7258), а ключ буде додано до черги перекладу.

Якщо **значення** рядка змінилося, краще **перейменувати ключ**: новий ключ не може успадкувати застарілий переклад. Саме цей підхід використано в #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Завершується з кодом 0 і `SKIP reason=base-unresolved`, коли базовий каталог неможливо прочитати (неглибока копія без базового ref), аналогічно до `check-openapi-breaking`. Лише режим випуску: функціональний PR переписує англійський текст і зупиняється на цьому; оновлення перед випуском позначає переклади, які він залишив (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, той самий `findStaleTranslations`).

**Режим нового коду (Clean-as-You-Code) — з 2026-08-30, лише для швидкого шляху PR**

Для подій `pull_request` файл `quality.yml` передає `--base-ref <PR base SHA>` до
`check:file-size`, `check:complexity-ratchets` і `check:dead-code`. Для `check:complexity-ratchets` і
`check:dead-code` поріг порівнює HEAD із merge-base, **обмежуючись файлами, яких торкнувся PR**
(`scripts/check/newCodeMode.mjs`: merge-base матеріалізується в тимчасовому
`git worktree`, ESLint/knip запускаються там і на HEAD, після чого порівнюється кількість для кожного файла):

- **блокуючий** — PR додав цикломатичні/когнітивні порушення або мертві експорти у змінених ним файлах
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` у журналі);
- **рекомендаційний** — глобальний підсумок порівняно із зафіксованим базовим рівнем. Успадкований дрейф ніколи не робить невинний PR червоним; дрейф повторно фіксується під час узгодження релізу та відстежується завданням headroom.

`check:file-size` використовує базове посилання за власними правилами (`scripts/check/check-file-size.mjs`, #8522):
він перевіряє кожен вихідний файл і тестовий файл у дереві, отримує кількість рядків кожного з них на базовій версії PR
за допомогою `git show` і завершується помилкою для файла лише тоді, коли він перевищує більше з двох значень: свого
базового стельового значення (`frozen` / `testFrozen` або `cap` / `testCap` для файла поза базовим рівнем) і свого
розміру на базовій версії. Тому файл, у якому вже був дрейф на базовій версії, ніколи не робить невинний PR червоним.

`check:boundary:ratchet` застосовує те саме правило до свого єдиного числа
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): під час подій PR і
швидкі перевірки `quality.yml`, і завдання lint у `ci.yml` передають базовий SHA PR, базовий
коміт вимірюється з експорту `git archive`, а PR завершується помилкою лише тоді, коли його
кількість ребер `open-sse → src` перевищує більше з двох значень: `metrics.boundaryOpenSseToSrc`
і кількості в базовій версії. Дрейф базової версії понад обмеження повідомляється
(`base drift herdado`), але ніколи не спричиняє помилку невинного PR; для push → main
зберігається абсолютне обмеження, а якщо базовий SHA неможливо розв’язати, використовується
це обмеження з попередженням.

Кандидат omni-queue (push до `omni-queue/**`, див. [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md))
отримує таке саме опрацювання, як і pull request: обидва робочі процеси передають базу
кандидата (`needs.changes.outputs.candidateBase`) як `--base-ref`, а
`check:ts7-diagnostics-ratchet` також запускається для неї. Для двох перевірок нового коду
базою порівняння є саме цей SHA, а не перший батьківський коміт верхнього merge-коміту, тож
оцінюється кожен pull request пакета.

Запуски `workflow_dispatch`, перевірка release-green і нічне завдання headroom не мають бази
PR і використовують абсолютне (глобальне) порівняння. Покриття, дублювання та покриття типами
поки що залишаються глобальними (їхні інструменти не створюють diff для кожного файлу без
значних витрат) — кандидати на таке саме опрацювання.

**Завершення етапу у v4.0 (LTS = жорсткіше, ніж раніше, а не «повернення до норми»)**

1. На чистій вершині `release/v4.0.0`: для запису виконайте `npm run quality:headroom --json`, потім
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, а також
   `--update` для кожної перевірки типів — кожна базова лінія зменшиться до виміряного значення.
2. Видаліть `_policy` з `quality-baseline.json` (це знову активує `--require-tighten` і нічне
   накопичення запасу), відновіть `THRESHOLD = 36` (або вище) у `check-openapi-coverage.mjs`.
3. Посильте обмеження понад виміряні значення там, де модульність дала результат: для розміру
   файлів поверніть `cap` до 1000 (або 800), підвищте мінімальні рівні покриття на 5, а кількість
   невикористаних експортів встановіть у 0 для модульованих пакетів.

## Базовий рівень храпового механізму (`quality-baseline.json`)

Рушій храпового механізму (`scripts/quality/check-quality-ratchet.mjs`) зчитує `quality-baseline.json`
і порівнює його зі щойно зібраним `quality-metrics.json`. Будь-яка метрика, що регресує
понад її епсилон, призводить до помилки збірки.

Метрики, що наразі відстежуються:

| Метрика               | Напрямок | Значення                                         |
| --------------------- | -------- | ------------------------------------------------ |
| `eslintWarnings`      | `down`   | Кількість попереджень ESLint не повинна зростати |
| `coverage.statements` | `up`     | Покриття інструкцій не повинно знижуватися       |
| `coverage.lines`      | `up`     | Покриття рядків не повинно знижуватися           |
| `coverage.functions`  | `up`     | Покриття функцій не повинно знижуватися          |
| `coverage.branches`   | `up`     | Покриття гілок не повинно знижуватися            |

Щоб оновити базовий рівень після реального покращення:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

Прапорець `--update` записує поточні виміряні значення до `quality-baseline.json`.
Фіксація покращення є завданням релізного/нічного процесу, а не PR із новою функціональністю: `--require-tighten`
(Фаза 6A.5) призводить до помилки через незафіксоване покращення лише в режимі релізу (push, schedule, релізний PR,
локальні запуски). У PR із новою функціональністю (режим шлюзу `pr`) покращення виводиться як інформація,
і перевірка проходить успішно; регресія призводить до помилки в обох режимах. Під час фази прискореної розробки ця перевірка всюди має рекомендаційний характер
(`_policy.requireTighten: false`). Див.
[Згенеровані файли та похідні базові рівні](#generated-files-and-derived-baselines-written-at-release).

### Храповий механізм CodeQL: частота оновлення та ручний запуск

`check:codeql-ratchet` зчитує **стан репозиторію, що оновлюється за розкладом, а не для кожного PR.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` повідомляє
`state: configured`, `schedule: weekly`: це сканування стандартного налаштування GitHub, а не аналіз для кожного push.
Наслідок: після злиття PR, який ВИПРАВЛЯЄ сповіщення, храповий механізм продовжує зчитувати
стару, більшу кількість, доки не запуститься наступне заплановане сканування, — тому він повідомляє про регресію
в кожному відкритому PR, включно з подальшими змінами самого виправного PR, доки сканування не оновить дані.

**Ручне оновлення**: `gh workflow run codeql.yml --ref release/vX.Y.Z` повторно запускає
аналіз і повторно публікує сповіщення протягом кількох хвилин. Спочатку прочитайте `.github/workflows/codeql.yml`
— у його заголовку пояснено, що він підтримує лише `workflow_dispatch`, **оскільки це конфліктує зі
«стандартним налаштуванням» GitHub** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). Відновлення тригерів `push`/`pull_request`/
`schedule` спочатку потребує **дії власника**: Налаштування → Безпека коду →
CodeQL: Стандартне → Розширене. Не додавайте тригер `schedule:` без цього перемикання — він
лише створюватиме невдалі запуски.

**Посильте базовий рівень після зменшення кількості** — `node scripts/check/check-codeql-ratchet.mjs
--update` записує нову виміряну кількість до `quality-baseline.json` →
`metrics.codeqlAlerts.value`, щоб храповий механізм не дозволяв непомітно повернутися до
старої верхньої межі. Практичний приклад (2026-09-02/03): PR #12502 виправив 7 реальних сповіщень
(13 → 6 виміряних відкритих); PR #12530 посилив зафіксований базовий рівень з 11 до 6, щоб він відповідав виміряному значенню; решту
6 сповіщень потім було відхилено з окремим обґрунтуванням для кожного, у результаті чого залишилося 0 відкритих.

**Відхилення — це рішення оператора (Жорстке правило #14)** — ніколи не відхиляйте сповіщення CodeQL,
не вказавши технічне обґрунтування в коментарі до відхилення: `won't fix` для
вимоги зовнішнього протоколу, `used in tests` для тестової фікстури, `false positive`
для санітайзера, який CodeQL не може розпізнати (прецедент: `docs/security/ERROR_SANITIZATION.md`).

## Політика повторного запуску тестів (WS5.4, v3.8.49)

Повторний запуск налаштовується для кожного раннера окремо, а не глобально — глобальний повторний запуск перетворює реальні регресії
на непомітні нестабільні збої:

| Раннер           | Політика                                                                                                                                                   | Чому                                                                                                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Playwright (e2e) | `retries: 1` лише в CI, з `trace: on-first-retry`                                                                                                          | Часові характеристики браузера/мережі справді недетерміновані; один повторний запуск із трасуванням перетворює нестабільний збій на артефакт, придатний для діагностики |
| Vitest           | БЕЗ глобального повторного запуску. Тест із підтвердженою нестабільністю отримує явний повторний запуск на рівні тесту (видимий у diff і перевірений у PR) | Зберігає список карантину в репозиторії, а не в непрозорому вигляді                                                                                                     |
| node:test (unit) | БЕЗ повторних запусків за жодних обставин                                                                                                                  | Нестабільний модульний тест — це помилка в тесті: виправте її, а не запускайте тест навмання повторно                                                                   |

Цільові SLO після впровадження телеметрії нестабільних тестів (WS5.2/5.3): частота нестабільних збоїв <1% на тест
(поріг «виправити негайно»), частка успішних проходжень ≥95% на пайплайн. Значення, прийняті в галузі як орієнтири, —
їх слід відкалібрувати за нашими власними вимірюваннями.

## Дрейф храповика на рівні релізу (WS5.5, v3.8.49)

Коли храповик (розмір файлу, складність, попередження eslint) регресує на ЧИСТІЙ верхівці гілки релізу
— тобто регресію спричинила КОМБІНАЦІЯ злиттів, а жоден окремий PR не відтворює її
у власній гілці, — виправлення має виконати **капітан релізу, один раз, у
гілці релізу**: надавайте перевагу виділенню коду/рефакторингу; змінюйте базову лінію лише з документованим
обґрунтуванням. Ніколи не перекладайте комбінований дрейф на PR учасника та ніколи
не змінюйте базову лінію окремо для кожного PR (це приховує реальні регресії). Спочатку розрізніть причини: відтворіть
помилку на чистій верхівці в тестовому worktree, перш ніж припускати, що її спричинив ваш PR.

один рядок із назвою визначеного режиму (`[agent-skills-sync] mode=release (auto: local run)`).

`check:test-masking` перелічує у блоці лише для звіту (це не `.skip(` і не `{ skip: true }`, тому
не вважається жорстким пропуском). `check:generated-artifacts` запускається там, де базову версію можна визначити: у завданні
`lint` (`fetch-depth: 0`), одразу після `check:agent-skills-sync`. Локально
`npm run check:generated-artifacts -- --mode=pr` показує, що саме ця перевірка оцінює в PR. Перехресна
перевірка загальної кількості провайдерів у `check:docs-counts` («Загальна кількість посилань на провайдерів (документація проти активних модулів)») є частиною
перевірки кількості та дотримується власних режимів цієї перевірки.

`admission-policy.json`, `provider-assets-provenance.jsonl`, `model-lifecycle.json`), а також обмеження, які PR із функціональністю може
вимагати редагувати разом із кодом (записи метрик у `quality-baseline.json`, базові показники перевірки типів, розміру файлів і
складності, `eslint-suppressions.json` — очищується запуском ESLint у pre-commit, коли PR виправляє зафіксоване порушення).
`src/i18n/routeNamespaces.generated.json` також генерується, але залишається у PR із функціональністю: застосунок імпортує його під час виконання,
тому він не може чекати на оновлення.

## Фіксація знижень храповика — рух донизу (#8584)

Храповик автоматизований лише наполовину, до того ж не в той бік. **Підвищення** ліміту — це
ручне редагування JSON, що займає десять секунд і є найшвидшим способом розблокувати червоний PR.
**Зниження** ліміту вимагає, щоб хтось запустив `--update` і закомітив результат — а до
появи завдання `bank-ratchet-shrinks` жоден робочий процес цього не робив. Виміряний наслідок
(2026-07-25): 18 заморожених файлів уже мали не більше ніж 800 рядків — ліміт для нових файлів; найгірший випадок
перевищував фактичний розмір у 132 рази (`src/shared/validation/schemas.ts`, 19 рядків із лімітом 2 523);
стеля складності зросла з `1794 → 2169` упродовж ~37 приміток про зміну базової лінії, лише з одним
зниженням (−1); а фразу «посилити через `--update` у наступному циклі» написали 31 раз, але виконали
лише один раз. Ліміт, який пережив код, через який його запровадили, непомітно перетворює кожну завершену
декомпозицію на дозвіл збільшувати код для наступного, хто редагуватиме файл.

`nightly-release-green.yml` → завдання **`bank-ratchet-shrinks`** замикає цей цикл:

|           |                                                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Запуск    | `schedule` (3×/день) + `workflow_dispatch` — навмисно **не** `push`                                                                    |
| Вимірює   | найвищу `release/vX.Y.Z`, з тією самою логікою визначення та захистом від ін’єкцій, що й `release-green`                               |
| Записує   | `check:file-size --update` і `check:complexity-ratchets --update` (обидві команди за своєю структурою можуть лише зменшувати значення) |
| Перевіряє | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                               |
| Доставляє | один завжди актуальний PR до гілки релізу — примусово оновлюваний, без спаму                                                           |

Фіксація виконується пакетно, а не під час кожного push, оскільки вона не має вимог щодо затримки (зафіксувати
зниження протягом 8 годин цілком прийнятно), тоді як запуск під час кожного злиття неодноразово перебудовував би гілку PR
під час кампаній зі злиття та щоразу оплачував би повний прохід ESLint. Виявлення залишається на
push (`release-green`); пакетно виконується лише фіксація.

### Перевірка безпеки

Завдання змінює базові лінії без нагляду, тому саме `verify-ratchet-bank.mjs` робить
це прийнятним. Він порівнює дерево після `--update` з `HEAD` і **перериває завдання
ще до створення будь-якого коміту** — не відкриваючи PR, — якщо не кожна зміна належить до одного з таких типів:

- числовий запис `frozen` / `testFrozen` **знижено** або **видалено**
- `complexity-baseline.json` → `count` **знижено**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **знижено**

Усе інше спричиняє помилку: підвищення числа, додавання запису, зміна `cap`/`testCap` або
видалення/перезапис примітки `_rebaseline_*` (ці примітки є журналом аудиту причин існування кожної
стелі та зберігаються всередині того самого об’єкта `frozen`, що й записи файлів).
Бот, здатний підвищувати ліміт, був би однозначно гіршим за поточний стан. Захист від
регресій: `tests/unit/verify-ratchet-bank.test.ts`.

Завдання ніколи не виконує push до `release/*` — PR зливає людина, тож помилковий результат вимірювання
не може потрапити до гілки без перевірки.

## Політика списку дозволів

Кожна перевірка, яка не може завершитися помилкою через попередньо наявні порушення, використовує зафіксований список дозволів
(наприклад, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). Політика така:

**Виправляйте першопричину; використовуйте список дозволів лише тоді, коли порушення існувало раніше
й не може бути виправлене в тому самому PR.**

Додаючи запис до списку дозволів:

1. Додайте коментар із обґрунтуванням.
2. Вкажіть задачу відстеження (наприклад, `// #3498 — Phase 2 feature, not yet implemented`).
3. Видаліть запис у тому самому PR, у якому виправляється порушення — застарілий запис, який більше
   не пригнічує активне порушення, сам є дефектом (перевірка застарілих записів 6A.3
   завершить перевірку помилкою через осиротілий запис у списку дозволів після реалізації).

**Не додавайте записи до списку дозволів, щоб швидше пройти тести.** Зелена перевірка зі списком дозволів, що постійно
зростає, створює хибне відчуття якості.

### Якщо перевірка завершується помилкою у вашому PR

1. **Уважно прочитайте вивід перевірки** — він точно вказує, який файл або символ порушив правило.
2. **Виправте порушення** — більшість перевірок є детермінованими перевірками файлової системи, які проходять одразу,
   щойно код стає правильним.
3. **Якщо порушення існувало раніше** (тобто ви його не внесли, але тепер воно охоплюється перевіркою): додайте запис
   до списку дозволів із коментарем-обґрунтуванням і задачею відстеження.
4. **Якщо перевірка використовує порогове підвищення** (покриття, попередження ESLint, дублювання, складність):
   ваша зміна погіршила показник. Виправте основну проблему або (у рідкісних випадках) виконайте
   `npm run quality:ratchet -- --update`, якщо зміна є навмисною, а погіршення показника прийнятним — але опишіть причину в описі PR.
5. **Рекомендаційні перевірки** (`continue-on-error: true`) мають інформаційний характер — вони не блокують
   злиття, але відображаються у зведенні CI. Усе одно виправляйте їх.

#### `check-key-completeness` — шлюз парності наборів ключів

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, job `i18n-ui-coverage`).
Порівнює набір листових ключів кожного `src/i18n/messages/<locale>.json` з `en.json` і завершується
помилкою за наявності будь-якого відсутнього або зайвого листового ключа, незалежно від того, коли
ключ було додано. Заповнювачі `__MISSING__:` вважаються наявними (їхній вміст належить до логіки
перевірки співвідношення). Це абсолютне доповнення до двох перевірок на основі diff/відсотків:
`check-ui-keys-coverage` забезпечує мінімум 80 % для кожної локалі (43 відсутні ключі з приблизно
13 000 усе ще дають 99,7 %), а `check-new-key-coverage` оцінює лише ключі, які PR додає до
`en.json`. Пакет локалі генерується з `en.json` у день створення її гілки й перекладається протягом
кількох днів, поки база продовжує додавати ключі; PR пакета сам не додає ключів, тому обидва
сусідні шлюзи не спрацювали, коли пакет 1 (#13044) надійшов із 43 відсутніми ключами у дев’яти
локалях, а пакет 2 (#13660) — із 10 відсутніми ключами у восьми (2026-09-15). Виправте червоне
позначення за допомогою
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`; `extra` означає, що
ключ було видалено з джерела — `sync-ui-keys` видалить його (`--prune-extra`, значення за
замовчуванням). `--warn` звітує без завершення з помилкою.
`--catalog=cli` запускає те саме порівняння для `bin/cli/locales` (`npm run i18n:check-keys:cli`);
обидва кроки виконуються в job `i18n-ui-coverage`. Абсолютна перевірка виконується лише в режимі
релізу: feature PR бачить `SKIP reason=pr-mode`, а виправлення запускається в оновленні релізу або
хвилі перекладів, ніколи у feature PR; PR, який змінює каталоги локалей, натомість перевіряється
для кожного з них порівняно з базою злиття (див. «Два режими» в job `i18n-ui-coverage`).

#### `check-new-key-coverage` — шлюз i18n для нових ключів

Сусідній до `check-ui-value-drift`. Той виявляє англійське значення, яке було **переписано**,
тоді як його переклади залишилися без змін; цей виявляє англійський ключ, який було **додано**,
тоді як деякі локалі його так і не отримали.

`check-ui-keys-coverage` не бачить цей клас проблем: він забезпечує мінімальний відсоток для кожної
локалі, і одинадцять відсутніх ключів із приблизно 13 000 листових ключів дають покриття 99,9 %.
Відсоток для мови не може виразити ситуацію «цю функцію випущено без перекладу» — ціла функція
може з’явитися в новій локалі без тексту, і показник ніколи не зміниться.

Інцидент, який він кодує: одинадцять ключів Phase 3 для Orchestration Canvas було перекладено для
42 локалей, що існували на той момент. Через кілька годин пакет мов ЄС (#13044) збільшив кількість
локалей у репозиторії до 51, і дев’ять нових (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`)
так і не отримали ці ключі. `deepMergeFallback` підставляє англійське значення для відсутнього
ключа, тому результатом було неперекладене, а не порожнє, UI — реальна й за задумом непомітна
проблема.

Як і його сусідній шлюз, він **враховує diff**, порівнюючи англійську версію в базі злиття з
робочим деревом, тому попередні прогалини залишаються зафіксованими, і для його ввімкнення не
потрібна міграція.

**Маркер `__MISSING__:<english>` не задовольняє цю перевірку (починаючи з 2026-09-17).** Раніше
це було задокументоване відтермінування — середовище виконання повертається до правильного
англійського тексту — доки 2026-09-16 вісім feature PR додали 61 ключ і встановили маркер у всіх
65 локалях замість перекладу: цей шлюз прийняв кожен із них, нічого не заблокувало PR, а шлюз
співвідношення реальних перекладів, який блокує випуск, потім завершився помилкою на вершині
релізу для всіх (pt-BR 3,2 % > 2,5 % + 0,5). Тепер маркер оцінюється як відсутній переклад. Лише
в режимі релізу починаючи з 2026-11-13: feature PR бачить `SKIP reason=pr-mode`, а в релізному
PR (`BASE_REF=origin/main`) шлюз оцінює кожен ключ, доданий у цьому циклі. Виправте червоне
позначення в оновленні релізу або хвилі перекладів за допомогою
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` або
всі локалі паралельно за допомогою `npm run i18n:translate-new-keys`
(`scripts/i18n/translate-new-keys.sh`, безпечний для detached HEAD, відмовляється запускатися без
змінних середовища `OMNIROUTE_TRANSLATION_*`). Ключ, який має залишатися англійською (закріплена
назва продукту/рушія/прапорця), слід додати до `scripts/i18n/untranslatable-keys.json`, а не
ховати за маркером. `vi` повністю забороняє маркери (`tests/unit/i18n-vi-completeness.test.ts`).

#### `check-vitest-exclusions` — шлюз відкладених тестів

Файл у списку `exclude` конфігурації `vitest.config.ts` — це тест, який не запускається, але для
того, хто переглядає дерево, він виглядає як покриття. Шістдесят два файли накопичилися за
коментарем `// #8618 — pre-existing failure; remove this exclusion when fixed`. Issue #8618 було
закрито 2026-08-11, хоча список, за яким воно відстежувалося, зріс із 45 до 62 записів, причому
кожен новий запис успадковував коментар із посиланням на неактуальну issue. Коли список нарешті
виміряли для кожного файлу (#13204), **51 із 62 пройшов перевірку в поточному дереві без змін у
джерельному коді**.

Шлюз вимагає, щоб кожне виключення, яке відповідає реальному файлу, (a) містило назву issue і
(b) з’являлося в `config/quality/vitest-exclusions.json` із виміряним статусом, щоб його додавання
було diff, який можна перевірити, в окремому файлі, а не ще одним рядком у масиві з 60 записів.
Він навмисно не запускає повторно виключені тести — це займає приблизно 10 хвилин і має
виконуватися в періодичному job; інвентаризація фіксує, коли кожен тест востаннє вимірювали.
