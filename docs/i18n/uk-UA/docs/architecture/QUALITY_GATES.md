Цей документ є авторитетним довідником щодо всіх шлюзів якості CI в OmniRoute.
У ньому описано кожен шлюз, що він перевіряє, у якому завданні CI запускається, чи використовує
базову лінію з храповим механізмом або політику успішного/неуспішного проходження, а також чи блокує він збірку або має рекомендаційний характер.

Короткий огляд і політику списку дозволів див. у розділі "Шлюзи якості та храпові механізми"
у `AGENTS.md`. Критичну оцінку, класифікацію зрілості та незалежний від інструментів
план відтворення цієї ж системи див. у
[Посібнику зі шлюзів якості](../ops/QUALITY_GATE_PLAYBOOK.md).

## Інвентар воріт та профілі виконання

### Прийом кандидатів

Робочі процеси CI та Quality Gates видають стабільний вердикт: `Gate / CI` та `Gate / Quality`. Їхня політика прийому з версіями перераховує кожну вакансію, яка є обов’язковою або рекомендованою. Відповідне обов’язкове завдання має бути успішним: відсутні, скасовані, пропущені, очікувані та невідомі результати не можуть встановити PASS. Дійсна класифікація лише для документів або лише для каталогу може зробити кодову смугу незастосовною; проект PR не є прийнятним кандидатом. Мітка `hotfix` не відмовляється від доказів.

Обидва робочі процеси охоплюють PRs у гілках main/release, надсилання до `main`, ручну диспетчеризацію та події злиття груп. Push, dispatch і merge-group запускають повний вибір. Пуші до `release/**` не запускають їх (2026-10-18): кожна зміна вже запустила матрицю на своєму PR, а об’єднана комбінація є завданням Release-Green (`docs/ops/RUNNER_BOX.md` → Hosted lane). Розгалуження та групи злиття використовують розміщені бігуни для завдань, які в іншому випадку вибирають саморозміщувані бігуни; перед розгортанням необхідно перевірити достатню потужність хостингу.

Звичайний PR виконує швидкий вибір. Доріжки `full-code` і `full-code-e2e` політики доступу (E2E, інтеграція, артефакт пакета, Electron smoke, Bun SQLite, клієнти екосистеми та протоколу) запускаються лише в чернетці черги Mergify або під час повного виконання: `gh workflow run ci.yml --ref <branch>`.

Кожна квитанція JSON ідентифікує знятий SHA, запуск робочого процесу та спробу. CLI відхиляє невідповідність checkout/event SHA. Тести робочого циклу прив’язують членство в політиці до списку `needs` вердикту, тому нова або видалена смуга не може мовчки зникнути. Квитанції охоплюють їхній власний робочий процес, а не публікацію, розгортання чи внутрішню роботу наявного консультативного сканера. Активація обох імен перевірок у правилах гілок є окремою адміністративною зміною; додавання цих завдань саме по собі не захищає гілку.

### Об'єднати чергу

Мітка `queue` надсилає PR до черги Mergify (`.mergify.yml`). Mergify відкриває чернетку PR у гілці `mergify/merge-queue/`, CI запускає повний вибір там, а вихідний PR об’єднується, коли `Gate / CI`, `Gate / Quality` та `Merge integrity (changelog + generated skills)` проходять.

Mergify записує свій підсумок черги в опис чернетки, і інші програми також можуть його редагувати. Подія `pull_request` `edited` у такій чернетці приймає власну групу паралельності (`-queue-edit-<run_id>`), тому вона не може скасувати реальний запуск чернетки, і вона пропускає ворота та матрицю. Тільки `Merge integrity` все ще працює. Пропущене завдання шлюзу має іншу назву перевірки, оскільки Mergify зчитує пропущений `Gate / CI` як невдалу перевірку та вилучає з черги PR.

Після вилучення з черги push не завжди повертає PR в чергу. Прокоментуйте це `@mergifyio queue`.

### Збережені докази в редукторі приймання

`scripts/quality/validate-release-acceptance.mjs` скорочує наданий план і його маніфести; він не встановлює, що план охоплює повний випуск. Його звіти явно встановлюють `releaseAcceptance: false`, навіть якщо цим планом є `VERIFIED`. Робочий процес `release-acceptance.yml` все ще використовує тіньові кріплення, а не реальні квитанції про збірку, пакет, завантаження чи просування.

CLI вимагає від `--evidence-root` перевірити збережені докази. Файли розпізнаються як `<evidence-root>/<artifact_id>/<member>` і хешуються як SHA-256. Запис PASS без доказів, відсутній або змінений файл, небезпечний шлях або символічне посилання перешкоджають перевірці. Відсутні файли не еквівалентні порожнім успішним журналам. Існуючі перевірки SHA/run/attempt залишаються незалежними: збіг байтів не може врятувати застарілу квитанцію. Цілісність файлу не є доказом автентичності виконання чи просування артефактів.

### Інвентар статичного сканування

Версійний інвентар npm-alias і членство в static-scan живуть у `config/quality/gate-manifest.json`. Запустіть `npm run check:gate-manifest`, щоб перевірити імена сценаріїв і точні команди на `package.json`; додавання, видалення та дрейф команд не виконують як локальний підхоплювач, так і завдання класифікації змін у CI. Псевдонім не є завданням робочого циклу, екземпляром матриці чи тестовим випадком: ці показники не можна подавати як взаємозамінні.

Використовуйте `npm run quality:scan -- --list` або `npm run quality:scan:fast -- --list` щоб перевірити вибрані псевдоніми без їх виконання. Програма запуску викликає точку входу npm, тому її час виконання (включаючи Bun де налаштовано) зберігається. Маніфест записує псевдоніми поза цими профілями як викликані окремо, а команди обслуговування заборонені в профілях сканування лише для читання.

Ці профілі охоплюють лише статичне сканування. Вони не сертифікують випробування продукту, покриття, упаковку, зовнішні перевірки або повне прийняття кандидата. Прийом робочого процесу використовує пов’язані `config/quality/admission-policy.json` та `scripts/quality/admission-verdict.mjs`. Профілі спостерігачів випуску залишаються окремими; самостійно перевіряти відповідні чеки та квитанції. Повні статичні команди спостерігача оголошені в `config/quality/release-green-static-profile.json`, включаючи `audit:deps`, вибір тесту на мутацію та перевірки трансляції. Завантажувач перевіряє команди npm на відповідність package.json та змодельованим оголошенням CI/Quality ; він відхиляє дрейф замість того, щоб виконувати маркери оболонки як аргументи. Потрібний вихід сканера SKIP/INCOMPLETE не може встановити PASS. Профіль записує свої зовнішні виключення та не замінює розміщене покриття, тестові матриці, пакет або докази розгортання. Наведений нижче перелік прози є посиланням, а не доказом того, що ворота справді пробігли.

Сценарії живуть під `scripts/check/` (політика gates) і `scripts/quality/` (ratchet engine). Джерелом правди CI є `.github/workflows/ci.yml`.

### Випуск PR fast-path (`quality.yml`)

`.github/workflows/quality.yml` доповнює CI на main/release PRs, надсилає до `main`, відправляє та зливає групи. PRs використовує швидкі перевірки з фільтрацією шляху. Постійно вимкнену дублікату збірки видалено; реальні перевірки build/package/boot залишаються в CI. Набір модулів і vitest працюють лише в CI (`Unit Tests (N/8)` і `Vitest`).

| Робота                                           | Область застосування                                                                                                                                | Блокування               |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API docs refs і docs-all                                                                                                             | так                      |
| `Fast Quality Gates`                             | Код PRs; статичні перевірки, перевірка типів, перевірка типів інформаційної панелі, пов'язані модульні тести, забуті однорідні тести (консультація) |
| `No new ESLint warnings`                         | Код PRs; захист від ворсу                                                                                                                           | Так, включно з виделками |
| `Merge integrity (changelog + generated skills)` | Нечорновий PRs; журнал змін і синхронізація створених навичок                                                                                       | Так, включно з виделками |

#### Звіт про тести на забутих братів і сестер

`npm run check:forgotten-sibling-tests` виконується як консультативний крок `Fast Quality Gates` і повторно використовує розпізнавач імпорту за картою тестового впливу. Для кожного зміненого виробничого модуля він повідомляє про детерміновані ланцюжки `changed module/symbol -> static consumer -> candidate sibling test`, коли тест-кандидат відсутній у diff запиту на отримання. Підсумок Markdown і результат JSON зберігаються як артефакт робочого процесу `forgotten-sibling-tests` для калібрування перед будь-яким розгортанням блокування.

Реекспорт стовбура та динамічний імпорт є лише діагностикою роздільної здатності; вони ніколи не створюють блокуючих знахідок. Переглянуті винятки живуть у `config/quality/forgotten-sibling-allowlist.json`. У кожному записі необхідно назвати тест споживача та кандидата, надати конкретне обґрунтування та пов’язати проблему GitHub або запит на отримання. Неправильно сформовані записи не вдалося закрити. Винятки не можуть придушити видалений тест-кандидат або різницю, яка додає `.skip`/`.todo`; ослаблення твердження та інше маскування залишаються у власності незалежного блокуючого воріт `check:test-masking`.

#### Дві програми перевірки типів відповідають по-різному

`typecheck:core` і `check:build-typecheck` компілюють різні програми з різними параметрами, і той самий файл може бути чистим в одній і повним помилок в іншій.

`tsconfig.build.json` встановлює `"strict": false`, тому `noImplicitAny` вимкнено. Основна конфігурація складає підібраний білий список із 27 файлів із суворішими параметрами та дотримується графіка імпорту кожного запису, тож файли, які ніколи не з’являються в програмі збирання, все ще перевіряються там.

Наслідки мають значення, коли судять про те, чи набраний файл:** нульова діагностика під `check:build-typecheck` не означає нуль** . Видалення `@ts-nocheck` з 26 файлів показало, що 23 з них чисті в програмі збирання; шістнадцять із них виявили близько 120 неявних будь-яких помилок у строгому. Перевірте обидва, перш ніж назвати файл чистим.

#### Дзеркала перекладу — це похідні файли (режим PR проти режиму випуску)

Таким чином, дзеркальні ворота працюють у двох режимах, розв’язаних `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`, потім `OMNIROUTE_GATE_MODE`, потім подія Actions; локальний запуск — `release`):

- `check:docs-sync` Режим випуску — запускає кожну перевірку. Режим PR зберігає версію package.json/OpenAPI, кореневі заголовки CHANGELOG і захист замінених документів, а також друкує `SKIP reason=pr-mode` для дзеркальних копій `llm.txt` і перекладених розділів CHANGELOG — якщо PR не записує дзеркала: головна гілка, оголошена як записувач сімейства `docs/i18n/**` у `config/quality/derived-paths/*.json` строго виконує обидві перевірки, і, коли diff base вирішує, зміна, чиї власні diff редагують `docs/i18n/<locale>/llm.txt` або `CHANGELOG.md` виконує сувору перевірку. База відмінностей не вирішується в перевірці depth-1 (завдання `docs-sync-strict` ), тому в режимі PR також виконується одна перевірка, яка не потребує бази: кожне дзеркало `llm.txt` має існувати, зберігати свій роздільник `---` і мати або кореневе тіло, або тіло, яке спільне для більшості дзеркал. Основа, яка перемістилася, залишає всі дзеркала однаково несвіжими та пропускає; ручне редагування одного дзеркала не вдається. Перекладені файли `CHANGELOG.md` не мають такої перевірки в depth-1 PR checkout.
- Хук перед фіксацією запускає `check-docs-sync.mjs --mode=pr`: коміт оцінюється за тим, що він робить. Без прапора локальний запуск є режимом випуску, і один об’єднаний PR, який редагує кореневий `llm.txt` блокував би кожне наступне фіксування на цій базі, доки не запуститься хвиля. Те саме правило діє для будь-якого шлюза з урахуванням режиму, який запускає хук Husky: хук пропускає `--mode=pr`, а суворий вердикт залишається для запуску режиму випуску (звільнення PR, надсилання до `main`, звичайний локальний запуск).
- Модичні тести дзеркального вмісту (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) Режим випуску — затверджує кожну локаль. Режим PR затверджує лише дзеркала, які є поточними з джерелом англійською мовою відповідно до `.i18n-state.json` (хеш усього файлу або записаний хеш розділу розділу, який тестує), і пропускає застарілі з певною причиною. Перевірки походження `target_hash` виконуються для кожної локалі в обох режимах. Свіжість на розділ `## `, одиниця хешування `run-translation.mjs` ; довгий розділ (перелік воріт цього файлу становить приблизно половину) означає, що будь-яке редагування в ньому залишає ці дзеркала застарілими, а їхні твердження в режимі PR пропускаються до наступної хвилі. Прив’язка, яку англійське джерело більше не містить, повертається до порівняння всього файлу.
- `i18n translation drift` — консультація щодо PRs, сувора щодо push, nightly та the release cut, тому застаріле дзеркало не може бути відправлено у випуск.

`scripts/i18n/sync-llm-mirrors.mjs` (також експортований як `syncLlmMirrors()`, з `--dry-run`) переписує дзеркала `llm.txt` ; оновлення випуску, хвиля перекладу та запланований запуск `i18n-mirror-refresh.yml` (оновлення виявляє застарілі дзеркала `llm.txt` за допомогою сухого запуску, оскільки звіт про дрейф їх не містить, і синхронізує їх перед `check:docs-all`).

Генеруються дванадцять README SVGs під `docs/diagrams/` (`scripts/docs/gen-readme-<name>.mjs`; `npm run docs:readme-diagrams` регенерує їх усіх). Кожен має одиничний тест порівняння байтів (`tests/unit/docs/readme-*-svg.test.ts`, job `test-unit`), який завершується помилкою, коли зафіксований файл застарів у режимі випуску; у PR `check:generated-artifacts` оцінює SVG, PR редагує, а дрейф бази залишається для оновлення випуску (див. [Створені файли та похідні базові лінії](#generated-files-and-derived-baselines-written-at-release) ) — і `check:docs-counts` зчитує канонічні числа зі своїх вузлів `<text>` — тому етап окреслення зберігає кожен окреслений рядок у файлі як невидимий `<text>`. Перевірка канонічних чисел SVG читає файли, перелічені в `SVG_DIAGRAM_FILES` (`scripts/check/check-docs-counts-sync.mjs`): `docs/diagrams/readme-hero.svg`, `free-tier-budget.svg`, `promise-pillars.svg`, `comparison-table.svg`, `cli-terminal.svg`, `tier-cascade.svg`, а також `public/images/tier-flow-dark.svg` і `tier-flow-light.svg`; твердження про безкоштовність назавжди, запис у каталог, повторюваний пул і коефіцієнти оцінки також читаються як `promise-pillars.svg`, `free-tier-budget.svg` і `strategies-grid.svg`. Підрахунки, які ці генератори збирають (загальна кількість постачальників, інструменти MCP, стратегії маршрутизації, безкоштовні назавжди постачальники, …) походять із знімків фактів `docs/reference/derived-facts.json` до `scripts/docs/readmeFacts.mjs`, а не з літералів, тому регенерація діаграми в будь-якій гілці відтворює зафіксований файл. `free-tier-budget.svg` малює свої рядки з того самого знімка (`code.freeTierBudget`, підсумок каталогу фактів, записаний датчиком), тому зміна на `FREE_MODEL_BUDGETS` потрапляє на картку під час наступного оновлення замість того, щоб зробити CI червоним.

### Похідні значення: режими затвора `pr` та `release`

Функція PR ніколи не записує значення, яке залежить від стану її бази: постачальника, міграції, MCP-інструменту та кількості стратегій, чисел README SVG, моментального знімка фактів. Один крок переобчислює всі з них, `npm run release:refresh-derived`, запускається випуском і нічним похідним оновленням PR. Отже** між релізами за проектом база стоїть за живим кодом** , а шлюз або тест, які порівнюють дерево з живим кодом, будуть червоними на кожному PR після того, як рідний брат додасть постачальника. Таким чином, ворота, які оцінюють похідні значення, працюють в одному з двох режимів, розв’язаних `scripts/check/lib/gateMode.mjs` (перемагає перший матч):

1. `--mode=pr|release` в командному рядку;
2. змінна середовища `OMNIROUTE_GATE_MODE` (`pr` або `release`);
3. автоматичний, з події GitHub Actions: `pull_request` голова якого не є `release/v*`, `merge_group` або push до `omni-queue/**` → `pr`; все інше (push, розклад, диспетчеризація, випуск PR `release/v* → main`, будь-який локальний запуск) → `release`.

Що `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) не працює в кожному режимі:

| Режим     | Не вдається                                                                                                                                                                                                                                                                                                                                                                                                                                | Потрібні живі факти |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------- |
| `release` | Кожна перевірка, сувора рівність із фактами, зібраними з дерева (поведінка, яку завжди мав шлюз): застаріла кількість, версія, рівень покриття або номер SVG є дрейфом STRICT                                                                                                                                                                                                                                                              | так                 |
| `pr`      | Лише те, що зміни зробили, відрізнялося від бази PR з тими самими екстракторами претензій: (1) кероване значення, яке не існувало в базі для цієї перевірки та файлу ("PR відредагував керований номер — відновив рядок до базового тексту"); (2) необхідна претензія, підстава перенесена, а голова втрачена. Інваріанти вмісту, які не потребують фактів, працюють як у режимі випуску; перевірки лише випуску перераховані та пропущені | немає               |

Файли інструкцій агента несуть** немає** похідний підрахунок взагалі: `AGENTS.md`, `llm.txt` (і його копії `docs/i18n/*/llm.txt` ), bs `AGENTS.md` fork, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` і кожен `skills/*/SKILL.md` вказує на джерело (наприклад `ROUTING_STRATEGY_VALUES` в `src/shared/constants/routingStrategies.ts`) і замість цього на `npm run facts`. Інваріант «Немає похідних підрахунків (файл інструкцій агента…)» не виконує підрахунок там (постачальники, міграції, інструменти та області MCP, стратегії маршрутизації, коефіцієнти оцінки, пакети режимів) в обох режимах, тому оновлення випуску ніколи не потребує переписування файлу інструкцій.

У режимі `pr` гілки запису можуть редагувати керовані значення: `chore/derived-*` (ночне оновлення PR), `release/v*` і хвилі трансляції `docs/i18n-*` і `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). Пакети черги (`merge_group`, чернетки Mergify, `omni-queue/**`) не оцінюються знову: вони підсумовують PRs вже оцінені ворота один за одним.

Коди виходу: `0` clean · `1` STRICT drift (або м’який drift з `--strict`) або порушення керованого значення · `2` інфраструктура — факти коду не вдалося зібрати (зонд tsx не вдався або минув час очікування; час очікування `OMNIROUTE_FACTS_TIMEOUT_MS`, за замовчуванням 600 000 мс) або, у CI, PR diff base не вдалося вирішити. Вихід 2 ніколи не є розбіжністю в документації: повторно запустіть завдання або виправте середовище.

Де працює кожен режим:

| Де                                                                                                        | Режим                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Функція PR — `ci.yml` завдання `docs-sync-strict`, крок `quality.yml` "Точність документів"               | `pr` (автоматичний); завдання передає базу як `BASE_SHA` і перевіряє через `fetch-depth: 2`                                                                                                                                          |
| `merge_group`, `omni-queue/**` кандидати, повний список воріт для злиття                                  | `pr`                                                                                                                                                                                                                                 |
| Випуск PR (`release/v* → main`), натискання, запланований і ручний запуск                                 | `release`                                                                                                                                                                                                                            |
| Release-Green (`scripts/quality/validate-release-green.mjs`)                                              | елементи HARD запускаються за допомогою `OMNIROUTE_GATE_MODE=pr` («база зламалася?»); елемент DRIFT `derived-refresh` запускає `npm run release:refresh-derived -- --check` (суворий перегляд, ніколи не відкриває базовий червоний) |
| Випуск (фази 0a та 1 `/generate-release` ; підключення навичок є окремою зміною, затвердженою власником)  | `npm run release:refresh-derived` записує похідні файли; Власні перевірки випуску PR потім запускаються в режимі `release`                                                                                                           |
| `nightly-derived-refresh.yml` (щодня, найвищий `release/vX.Y.Z`, пропущено під час випуску-заморожування) | `npm run release:refresh-derived -- --profile=nightly`; на diff він утримує ONE PR відкритим із `chore/derived-refresh`; ніколи не зливається                                                                                        |

Команди за ним:

- `npm run facts` друкує кожне похідне число як JSON (`scripts/release/facts.mjs`). `--key=code.mcpTools` друкує одне значення, `--snapshot` читає зафіксований знімок замість живого дерева. Вихід 2, коли неможливо зібрати факти.
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) повторно обчислює отримані файли за один прохід у такому порядку (ідентифікатори кроків для `--only=`): `provider-reference` (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (знімок), `numbers` (план перезапису шлюзу підрахунку, застосований до документів, а потім перенесений до їхніх дзеркал `docs/i18n/` ), `readme-diagrams`, `skills` (генерований `SKILL.md`), `e2e-timings` (пропущено, доки дерево не буде доставлено) `syncE2eTimings`), `ui-keys` (відкидає ключі `en.json`, а за допомогою `--rewritten-since=<ref>` — за замовчуванням `origin/main` — повторно ставить у чергу значення англійською мовою, переписані з моменту останнього випуску; значення перекладаються під час того самого виконання серверною програмою, налаштованою в середовищі, або в `.env` (`OMNIROUTE_TRANSLATION_*`, лише ці ключі зчитуються) або механізмом Google. Без серверної програми він ніколи не записує маркери `__MISSING__` : профіль випуску не вдається, nightly пропускає ключі, а `--allow-untranslated` записує їх навмисно), `llm-mirrors` та `verify-generated` (після запису `check:generated-artifacts` та `check:agent-skills-sync` у режимі випуску мають пройти; пропускається в `--check` і коли `--only` залишає його; помилка — вихід 2). Крок `changelog` це згода (`--with-changelog`, лише профіль випуску). `--profile=nightly` ніколи не торкається заявки на версію. За допомогою `-- --check` він нічого не записує і завершує роботу 1, коли будь-який файл буде змінено або кероване значення потребує редагування вручну (перелік обох); вихід 2 у разі збою інфраструктури. `--json` друкує результат як JSON.
- `docs/reference/derived-facts.json` — це моментальний знімок фактів, використаних під час останнього оновлення. Пише тільки оновлення. Генератори README SVG зчитують його, а одиничні тести PR-time порівнюють закріплені документи та згенеровані файли з ним — ніколи з живим кодом. Єдине живе порівняння набору: «оновлення випуску замикає цикл» у `tests/unit/check-docs-counts-sync.test.ts`: з живими фактами план перезапису оновлення, застосований у пам’яті, не залишає дрейфу STRICT, про який він не повідомляє, а перепланування нічого не змінює.

Щоб відтворити локально (локальний запуск за замовчуванням має `release`):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

Без розв’язуваної бази (без `BASE_SHA`/`BASE_REF`, без локального `origin/release/v<version>`) локальний запуск `pr` друкує попередження та пропускає різницю замість помилки.

### Посада: `i18n-ui-coverage`

| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |

| `check:ui-icu`                        | Кожне повідомлення кожного каталогу UI компілюється за допомогою `IntlMessageFormat`                                                                                                        | Так (обидва режими)     |
| `check-ui-value-drift` (вбудований)   | Переписана англійська** значення** не залишає застарілих перекладів                                                                                                                         | Так (лише режим спуску) |
| `check-new-key-coverage` (вбудований) | А** новий** Англійський ключ перекладається в кожній локалі —, а маркер `__MISSING__:` відхиляється                                                                                         | Так (лише режим спуску) |
| `check-key-completeness` (вбудований) | Кожен каталог UI (і, з `--catalog=cli`, кожен каталог CLI ) містить точно набір ключів свого `en.json`; у режимі `pr` кожен каталог, який PR змінив проти самого себе на базі злиття        | Так (обидва режими)     |

Потрібен `fetch-depth: 0` — ворота дрейфу значення відрізняє `en.json` від бази злиття.

**Два режими (з 13.11.2026).** Функція PR додає або переписує ключі в `en.json` (і `bin/cli/locales/en.json`) і не стосується інших локалей; `check:pr-derived-paths` (завдання `pr-test-policy`, родина `config/quality/derived-paths/translation.json`) не працює з функцією PR яка є. Інші локалі завершуються один раз за випуск за допомогою `release:refresh-derived`, який викликає `syncUiKeys()` в `scripts/i18n/sync-ui-keys.mjs` (додати відсутні ключі, вирізати пропущені, позначити переклади переписаної англійської мови за допомогою `rewrittenSinceRef`, перекласти), або за допомогою хвилі перекладу. Шлюзи зчитують режим із `scripts/check/lib/gateMode.mjs`: у режимі `pr` (функція PRs, `merge_group`, `omni-queue/**`) вентилі режиму випуску вище друкують `SKIP reason=pr-mode` і виходять 0; у режимі `release` (випуск PR, надсилання до `main`, `workflow_dispatch`, локальний запуск) вони суворі, як і раніше, а у випуску PR ті, хто знає diff, отримують `BASE_REF=origin/main`, тому вони оцінюють кожен ключ, доданий або переписаний циклом. Попередньо перегляньте вердикт PR-функцій локально за допомогою `--mode=pr`.

PR який усе ще змінює каталоги локалізацій у режимі `pr` (хвиля перекладу, оновлення випуску, виправлення лише для перекладу), не пропускається: `check-key-completeness` порівнює кожен змінений каталог із тим самим каталогом у базі злиття (`scripts/i18n/lib/touched-catalogs.mjs`) і виходить з ладу за ключем, який каталог втратив, ключем, якого не вистачає в `en.json`, справжнім перекладом, перетвореним на маркер `__MISSING__:` або в англійський текст, або значенням, яке більше не інтерполює placeholders/tags англійського рядка PR не торкався. Новий каталог у PR повинен містити весь набір ключів `en.json`. Для каталогів, яких торкається PR, це охоплює те, що бачитимуть співвідношення та вентилі парності CLI.

Модульні тести паритету локалі (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) дотримуються тих самих режимів через `tests/_helpers/localeParityMode.ts`: у режимі `pr` вони пропускають твердження парності ключа та залишають до випуску оновлення паритету заповнювача для ключів, англійська мова яких змінена з моменту створення бази злиття (кожен ключ, коли поверхнева перевірка завдання модульного тесту не може його прочитати). Цей помічник є** тільки** санкціонований умовний пропуск режиму: `check:test-masking` підраховує `.skip(` і `{ skip: true }`, але не обчислений `{ skip: "<reason>" }` який він повертає, тому `tests/unit/locale-parity-mode.test.ts` закріплює список тестів, дозволених для його використання. — додавання одного є перевіреним виправленням до цього списку.

#### `check-ui-value-drift` — шлюз застарілого перекладу

Вловлює одну i18n регресію, яку інші ворота структурно не бачать: значення англійською мовою переписується, а переклади, отримані з _попередньої_ англійської мови, залишаються позаду, тому неангломовні користувачі продовжують читати впевнено сформульовану, тепер неправильну копію.

Це справді відправлено. `oauthModal.googleOAuthWarning` було переписано, коли приземлився помічник входу в систему Antigravity (#5203);** 39 з 43 локалізацій** зберіг текст, який повідомляє операторам «скопіювати повний URL і вставити його нижче» — потік, який не може завершитися для цього постачальника. Це залишилося непоміченим до #8463 оскільки:

- `sync-ui-keys` заповнює лише ключі, які є** відсутній** , ніколи не є** несвіжий** ;
- `check-ui-keys-coverage` підраховує _присутність_ ключа, тому застарілий переклад вважається покритим;
- `check-translation-drift` відстежує документацію `docs/i18n/<locale>/**.md`, дзеркала — вона ніколи не читає `src/i18n/messages/*.json`. Він виконується в завданнях `docs-sync-strict`: консультативний на PRs, суворий на push і щоночі; хвиля перекладу оновлює дзеркала, а не функція PR.

**З урахуванням відмінностей, без підтримки базової лінії.** Він порівнює `en.json` на базі злиття з робочим деревом; для кожного ключа, англійське значення якого змінено, будь-яка локаль, яка все ще містить незайманий переклад, є застарілою. Це свідомо** заморожує наявну заборгованість** — a diff не може виявити, з якої давньої англійської походить давній переклад, тому гейт оцінює лише те, що стосується поточної зміни. Альтернатива (базова лінія хешу для кожного ключа) коштувала б ~ 600 KB, згенерований файл, 3 × найбільший існуючий базовий рівень, збиваючи на кожному i18n PR.

Два способи задовольнити це:

1. оновити відповідні переклади, або
2. встановіть для них `__MISSING__:<new english>` — середовище виконання, а потім обслуговує виправлену англійську (`src/i18n/request.ts::deepMergeFallback`, #7258) і ключові черги для перекладу.

Якщо рядок** значення** змінений, воліти** перейменування ключа** : новий ключ не може успадкувати застарілий переклад. Це використаний шаблон #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Виходить 0 із `SKIP reason=base-unresolved`, коли базовий каталог неможливо прочитати (неглибокий клон без базового посилання), віддзеркалюючи `check-openapi-breaking`. Лише режим випуску: функція PR переписує англійську мову та зупиняється на цьому; оновлення випуску позначає переклади, які воно залишило (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, той самий `findStaleTranslations`).

  звіти як раннє попередження про використання бюджетів; перевіряйте примітки `_rebaseline_*` відповідного порогу.

**Режим нового коду (Clean-as-You-Code) — з 2026-08-30, лише для швидкого шляху PR**

Для подій `pull_request` файл `quality.yml` передає `--base-ref <PR base SHA>` до
`check:file-size`, `check:complexity-ratchets` і `check:dead-code`. Для `check:complexity-ratchets` і
`check:dead-code` поріг порівнює HEAD із merge-base, **обмежуючись файлами, яких торкнувся PR**
(`scripts/check/newCodeMode.mjs`: merge-base матеріалізується в тимчасовому
`git worktree`, ESLint/knip запускаються там і на HEAD, після чого порівнюється кількість для кожного файла):

- **блокуючий** — PR додав цикломатичні/когнітивні порушення або мертві експорти у змінених ним файлах
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` у журналі);
- **рекомендаційний** — глобальний підсумок порівняно із зафіксованим базовим рівнем. Успадкований дрейф ніколи не робить невинний PR червоним; дрейф повторно фіксується під час узгодження релізу та відстежується завданням headroom.

`check:file-size` використовує базове посилання за власними правилами (`scripts/check/check-file-size.mjs`, #8522):
він перевіряє кожен вихідний файл і тестовий файл у дереві, отримує кількість рядків кожного з них на базовій версії PR
за допомогою `git show` і завершується помилкою для файла лише тоді, коли він перевищує більше з двох значень: свого
базового стельового значення (`frozen` / `testFrozen` або `cap` / `testCap` для файла поза базовим рівнем) і свого
розміру на базовій версії. Тому файл, у якому вже був дрейф на базовій версії, ніколи не робить невинний PR червоним.

`check:boundary:ratchet` застосовує те саме правило до свого єдиного числа
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): під час подій PR і
швидкі перевірки `quality.yml`, і завдання lint у `ci.yml` передають базовий SHA PR, базовий
коміт вимірюється з експорту `git archive`, а PR завершується помилкою лише тоді, коли його
кількість ребер `open-sse → src` перевищує більше з двох значень: `metrics.boundaryOpenSseToSrc`
і кількості в базовій версії. Дрейф базової версії понад обмеження повідомляється
(`base drift herdado`), але ніколи не спричиняє помилку невинного PR; для push → main
зберігається абсолютне обмеження, а якщо базовий SHA неможливо розв’язати, використовується
це обмеження з попередженням.

Кандидат omni-queue (push до `omni-queue/**`, див. [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md))
отримує таке саме опрацювання, як і pull request: обидва робочі процеси передають базу
кандидата (`needs.changes.outputs.candidateBase`) як `--base-ref`, а
`check:ts7-diagnostics-ratchet` також запускається для неї. Для двох перевірок нового коду
базою порівняння є саме цей SHA, а не перший батьківський коміт верхнього merge-коміту, тож
оцінюється кожен pull request пакета.

Запуски `workflow_dispatch`, перевірка release-green і нічне завдання headroom не мають бази
PR і використовують абсолютне (глобальне) порівняння. Покриття, дублювання та покриття типами
поки що залишаються глобальними (їхні інструменти не створюють diff для кожного файлу без
значних витрат) — кандидати на таке саме опрацювання.

**Завершення етапу у v4.0 (LTS = жорсткіше, ніж раніше, а не «повернення до норми»)**

1. На чистій вершині `release/v4.0.0`: для запису виконайте `npm run quality:headroom --json`, потім
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, а також
   `--update` для кожної перевірки типів — кожна базова лінія зменшиться до виміряного значення.
2. Видаліть `_policy` з `quality-baseline.json` (це знову активує `--require-tighten` і нічне
   накопичення запасу), відновіть `THRESHOLD = 36` (або вище) у `check-openapi-coverage.mjs`.
3. Посильте обмеження понад виміряні значення там, де модульність дала результат: для розміру
   файлів поверніть `cap` до 1000 (або 800), підвищте мінімальні рівні покриття на 5, а кількість
   невикористаних експортів встановіть у 0 для модульованих пакетів.

## Базовий рівень храпового механізму (`quality-baseline.json`)

Рушій храпового механізму (`scripts/quality/check-quality-ratchet.mjs`) зчитує `quality-baseline.json`
і порівнює його зі щойно зібраним `quality-metrics.json`. Будь-яка метрика, що регресує
понад її епсилон, призводить до помилки збірки.

Метрики, що наразі відстежуються:

| Метрика               | Напрямок | Значення                                         |
| --------------------- | -------- | ------------------------------------------------ |
| `eslintWarnings`      | `down`   | Кількість попереджень ESLint не повинна зростати |
| `coverage.statements` | `up`     | Покриття інструкцій не повинно знижуватися       |
| `coverage.lines`      | `up`     | Покриття рядків не повинно знижуватися           |
| `coverage.functions`  | `up`     | Покриття функцій не повинно знижуватися          |
| `coverage.branches`   | `up`     | Покриття гілок не повинно знижуватися            |

Щоб оновити базовий рівень після реального покращення:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

Прапорець `--update` записує поточні виміряні значення до `quality-baseline.json`.
Фіксація покращення є завданням релізного/нічного процесу, а не PR із новою функціональністю: `--require-tighten`
(Фаза 6A.5) призводить до помилки через незафіксоване покращення лише в режимі релізу (push, schedule, релізний PR,
локальні запуски). У PR із новою функціональністю (режим шлюзу `pr`) покращення виводиться як інформація,
і перевірка проходить успішно; регресія призводить до помилки в обох режимах. Під час фази прискореної розробки ця перевірка всюди має рекомендаційний характер
(`_policy.requireTighten: false`). Див.
[Згенеровані файли та похідні базові рівні](#generated-files-and-derived-baselines-written-at-release).

### Храповий механізм CodeQL: частота оновлення та ручний запуск

`check:codeql-ratchet` зчитує **стан репозиторію, що оновлюється за розкладом, а не для кожного PR.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` повідомляє
`state: configured`, `schedule: weekly`: це сканування стандартного налаштування GitHub, а не аналіз для кожного push.
Наслідок: після злиття PR, який ВИПРАВЛЯЄ сповіщення, храповий механізм продовжує зчитувати
стару, більшу кількість, доки не запуститься наступне заплановане сканування, — тому він повідомляє про регресію
в кожному відкритому PR, включно з подальшими змінами самого виправного PR, доки сканування не оновить дані.

**Ручне оновлення**: `gh workflow run codeql.yml --ref release/vX.Y.Z` повторно запускає
аналіз і повторно публікує сповіщення протягом кількох хвилин. Спочатку прочитайте `.github/workflows/codeql.yml`
— у його заголовку пояснено, що він підтримує лише `workflow_dispatch`, **оскільки це конфліктує зі
«стандартним налаштуванням» GitHub** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). Відновлення тригерів `push`/`pull_request`/
`schedule` спочатку потребує **дії власника**: Налаштування → Безпека коду →
CodeQL: Стандартне → Розширене. Не додавайте тригер `schedule:` без цього перемикання — він
лише створюватиме невдалі запуски.

**Посильте базовий рівень після зменшення кількості** — `node scripts/check/check-codeql-ratchet.mjs
--update` записує нову виміряну кількість до `quality-baseline.json` →
`metrics.codeqlAlerts.value`, щоб храповий механізм не дозволяв непомітно повернутися до
старої верхньої межі. Практичний приклад (2026-09-02/03): PR #12502 виправив 7 реальних сповіщень
(13 → 6 виміряних відкритих); PR #12530 посилив зафіксований базовий рівень з 11 до 6, щоб він відповідав виміряному значенню; решту
6 сповіщень потім було відхилено з окремим обґрунтуванням для кожного, у результаті чого залишилося 0 відкритих.

**Відхилення — це рішення оператора (Жорстке правило #14)** — ніколи не відхиляйте сповіщення CodeQL,
не вказавши технічне обґрунтування в коментарі до відхилення: `won't fix` для
вимоги зовнішнього протоколу, `used in tests` для тестової фікстури, `false positive`
для санітайзера, який CodeQL не може розпізнати (прецедент: `docs/security/ERROR_SANITIZATION.md`).

## Політика повторного запуску тестів (WS5.4, v3.8.49)

Повторний запуск налаштовується для кожного раннера окремо, а не глобально — глобальний повторний запуск перетворює реальні регресії
на непомітні нестабільні збої:

| Раннер           | Політика                                                                                                                                                   | Чому                                                                                                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Playwright (e2e) | `retries: 1` лише в CI, з `trace: on-first-retry`                                                                                                          | Часові характеристики браузера/мережі справді недетерміновані; один повторний запуск із трасуванням перетворює нестабільний збій на артефакт, придатний для діагностики |
| Vitest           | БЕЗ глобального повторного запуску. Тест із підтвердженою нестабільністю отримує явний повторний запуск на рівні тесту (видимий у diff і перевірений у PR) | Зберігає список карантину в репозиторії, а не в непрозорому вигляді                                                                                                     |
| node:test (unit) | БЕЗ повторних запусків за жодних обставин                                                                                                                  | Нестабільний модульний тест — це помилка в тесті: виправте її, а не запускайте тест навмання повторно                                                                   |

Цільові SLO після впровадження телеметрії нестабільних тестів (WS5.2/5.3): частота нестабільних збоїв <1% на тест
(поріг «виправити негайно»), частка успішних проходжень ≥95% на пайплайн. Значення, прийняті в галузі як орієнтири, —
їх слід відкалібрувати за нашими власними вимірюваннями.

## Дрейф храповика на рівні релізу (WS5.5, v3.8.49)

Коли храповик (розмір файлу, складність, попередження eslint) регресує на ЧИСТІЙ верхівці гілки релізу
— тобто регресію спричинила КОМБІНАЦІЯ злиттів, а жоден окремий PR не відтворює її
у власній гілці, — виправлення має виконати **капітан релізу, один раз, у
гілці релізу**: надавайте перевагу виділенню коду/рефакторингу; змінюйте базову лінію лише з документованим
обґрунтуванням. Ніколи не перекладайте комбінований дрейф на PR учасника та ніколи
не змінюйте базову лінію окремо для кожного PR (це приховує реальні регресії). Спочатку розрізніть причини: відтворіть
помилку на чистій верхівці в тестовому worktree, перш ніж припускати, що її спричинив ваш PR.

## Згенеровані файли та отримані базові лінії (написані під час випуску)

План 2026-11-13 («похідні номери та тексти вирішуються лише під час випуску»): функція PR змінює** джерело** — `src/shared/constants/providers.ts`, `docs/openapi.yaml`, каталог навичок, каталог безкоштовних рівнів, нова специфікація e2e. Він не регенерує файли, обчислені з цього джерела, і не записує виміряне покращення в базовий рівень. Ці файли перезаписуються один раз за допомогою оновлення випуску (`release:refresh-derived`) або нічного оновлення PR. До цього кожен рідний PR мав власну відновлену копію та конфліктував з наступним злиттям (2026-11-13: 30 із 321 відкритих PRs переписали `PROVIDER_REFERENCE.md`, 26–28 переписали діаграми README ).

**Охоронець.** `check:pr-derived-paths` (завдання `pr-test-policy`) не виконує функцію PR, яка торкається файлу сімейства в `config/quality/derived-paths/`:

| Сім'я       | Файли                                                                                                                                                                                      | Переписав                                                                                                                |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `generated` | `docs/reference/derived-facts.json`; `docs/reference/PROVIDER_REFERENCE.md`; дванадцять створених README SVGs; `skills/*/references/**`; файли `SKILL.md`, які не мають спеціального блоку | `release:refresh-derived` (факти), `gen:provider-reference`, `docs:readme-diagrams`, `generate-agent-skills.mjs --apply` |
| `baselines` | `config/quality/e2e-timings.json`                                                                                                                                                          | `balance-e2e-shards.mjs --sync` (`syncE2eTimings()`)                                                                     |

Писачі (`release/v*`, `chore/derived-*` і `chore/bank-ratchet-*` для базових ліній) звільнені; так само і PR, який змінює лише одне сімейство плюс його супутники (для `generated`: сценарії генератора, їхні тести, вхідні дані навичок агента — `src/shared/constants/agentSkills.ts`, рукописні документи `skills/**`, `docs/openapi.yaml` — і `changelog.d/**`), наприклад, зміна макета героя з його відновленим SVG або виправлення навичок, тест якого читає відновлені файли `SKILL.md`. `SKILL.md` із рукописним блоком `<!-- skill:custom-start -->` не входить до сімейства: його спеціальний блок залишається доступним для редагування поруч із функцією.

Очищення сирот також не оцінюється сім’ями: PR може видалити `docs/i18n/<locale>/<doc>`, коли база злиття мала це дзеркало, і `<doc>` більше не існує в голові PR, і може редагувати `.i18n-state.json` лише для видалення таких документів із `sources`. Охоронець перераховує ці файли в `orphan-cleanup`. Видалення дзеркала документа, який все ще існує, залишається порушенням: жоден інший конвеєр не відстежує цей стан, а дзеркала `llm.txt` і `CHANGELOG.md` мають власні автори.

**Перевірки в режимі воріт** (`scripts/check/lib/gateMode.mjs`; допоміжний `scripts/check/lib/derivedArtifactScope.mjs`):

| Перевірте                                                                         | `release` (push, розклад, випуск PR, локальний)                         | `pr` (функція PR, партія черги)                                                                                                                                                                    |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check:agent-skills-sync`                                                         | кожен навик повинен дорівнювати потужності генератора                   | лише навички, чий створений текст (поза спеціальним блоком) або `references/` редагує PR ; інакше `SKIP reason=pr-mode`                                                                            |
| `check:generated-artifacts` ( таймінги README SVGs + e2e; потрібна повна історія) | кожен SVG дорівнює своєму генератору; кожна специфікація має запис часу | лише артефакти, які редагує PR ; решта `SKIP reason=pr-mode`; no diff base → кожен артефакт оцінюється (закривається після помилки)                                                                |
| README SVG тести порівняння байтів (`tests/unit/docs/readme-*-svg.test.ts`)       | кожен SVG                                                               | лише SVG PR редагує, коли база вирішує; Неглибока перевірка PR `test-unit` не має бази, тому тест пропускається з `SKIP reason=base-unresolved`, а `check:generated-artifacts` володіє порівнянням |

| `check-quality-ratchet.mjs --require-tighten`                                     | un-banking покращення не вдається (якщо не `_policy`)                   | повідомляється про покращення, жодного разу невдача; регрес все одно не вдається                                                                                                                   |

Режим випуску зберігає вердикти, коди виходу та повідомлення, які ці перевірки мали до поділу; додається щонайбільше один рядок із назвою дозволеного режиму (`[agent-skills-sync] mode=release (auto: local run)`). Тести пропускають опцію `{ skip: releaseOnlyUnlessTouched(...) }` у node:test, яку `check:test-masking` перераховує у блоці лише для звітів (це не є ні `.skip(`, ні `{ skip: true }`, тому не вважається жорстким пропуском). `check:generated-artifacts` працює там, де можна розв’язати базу: завдання `lint` (`fetch-depth: 0`), відразу після `check:agent-skills-sync`. Локально `npm run check:generated-artifacts -- --mode=pr` показує, що цей крок оцінює для PR. Перехресна перевірка загальної кількості постачальників для `check:docs-counts` («Загальна кількість посилань постачальника (документація та живі модулі)») є частиною підрахунків і слідує власним режимам цього шлюзу.

Навмисно не в сім’ї: файли політики, визначені людьми (`gate-manifest.json`, списки дозволених, `admission-policy.json`, `provider-assets-provenance.jsonl`, `model-lifecycle.json`) і стелі функції, які PR можливо, доведеться редагувати разом із кодом (записи метрики `quality-baseline.json`, базові лінії typecheck/file-size/complexity, `eslint-suppressions.json` — скорочений за допомогою попереднього запуску ESLint коли PR виправляє заморожене порушення). `src/i18n/routeNamespaces.generated.json` також генерується, але залишається у функції PRs: програма імпортує його під час виконання, тому не може чекати оновлення.

## Фіксація знижень храповика — рух донизу (#8584)

Храповик автоматизований лише наполовину, до того ж не в той бік. **Підвищення** ліміту — це
ручне редагування JSON, що займає десять секунд і є найшвидшим способом розблокувати червоний PR.
**Зниження** ліміту вимагає, щоб хтось запустив `--update` і закомітив результат — а до
появи завдання `bank-ratchet-shrinks` жоден робочий процес цього не робив. Виміряний наслідок
(2026-07-25): 18 заморожених файлів уже мали не більше ніж 800 рядків — ліміт для нових файлів; найгірший випадок
перевищував фактичний розмір у 132 рази (`src/shared/validation/schemas.ts`, 19 рядків із лімітом 2 523);
стеля складності зросла з `1794 → 2169` упродовж ~37 приміток про зміну базової лінії, лише з одним
зниженням (−1); а фразу «посилити через `--update` у наступному циклі» написали 31 раз, але виконали
лише один раз. Ліміт, який пережив код, через який його запровадили, непомітно перетворює кожну завершену
декомпозицію на дозвіл збільшувати код для наступного, хто редагуватиме файл.

`nightly-release-green.yml` → завдання **`bank-ratchet-shrinks`** замикає цей цикл:

|           |                                                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Запуск    | `schedule` (3×/день) + `workflow_dispatch` — навмисно **не** `push`                                                                    |
| Вимірює   | найвищу `release/vX.Y.Z`, з тією самою логікою визначення та захистом від ін’єкцій, що й `release-green`                               |
| Записує   | `check:file-size --update` і `check:complexity-ratchets --update` (обидві команди за своєю структурою можуть лише зменшувати значення) |
| Перевіряє | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                               |
| Доставляє | один завжди актуальний PR до гілки релізу — примусово оновлюваний, без спаму                                                           |

Фіксація виконується пакетно, а не під час кожного push, оскільки вона не має вимог щодо затримки (зафіксувати
зниження протягом 8 годин цілком прийнятно), тоді як запуск під час кожного злиття неодноразово перебудовував би гілку PR
під час кампаній зі злиття та щоразу оплачував би повний прохід ESLint. Виявлення залишається на
push (`release-green`); пакетно виконується лише фіксація.

### Перевірка безпеки

Завдання змінює базові лінії без нагляду, тому саме `verify-ratchet-bank.mjs` робить
це прийнятним. Він порівнює дерево після `--update` з `HEAD` і **перериває завдання
ще до створення будь-якого коміту** — не відкриваючи PR, — якщо не кожна зміна належить до одного з таких типів:

- числовий запис `frozen` / `testFrozen` **знижено** або **видалено**
- `complexity-baseline.json` → `count` **знижено**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **знижено**

Усе інше спричиняє помилку: підвищення числа, додавання запису, зміна `cap`/`testCap` або
видалення/перезапис примітки `_rebaseline_*` (ці примітки є журналом аудиту причин існування кожної
стелі та зберігаються всередині того самого об’єкта `frozen`, що й записи файлів).
Бот, здатний підвищувати ліміт, був би однозначно гіршим за поточний стан. Захист від
регресій: `tests/unit/verify-ratchet-bank.test.ts`.

Завдання ніколи не виконує push до `release/*` — PR зливає людина, тож помилковий результат вимірювання
не може потрапити до гілки без перевірки.

## Політика списку дозволів

Кожна перевірка, яка не може завершитися помилкою через попередньо наявні порушення, використовує зафіксований список дозволів
(наприклад, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). Політика така:

**Виправляйте першопричину; використовуйте список дозволів лише тоді, коли порушення існувало раніше
й не може бути виправлене в тому самому PR.**

Додаючи запис до списку дозволів:

1. Додайте коментар із обґрунтуванням.
2. Вкажіть задачу відстеження (наприклад, `// #3498 — Phase 2 feature, not yet implemented`).
3. Видаліть запис у тому самому PR, у якому виправляється порушення — застарілий запис, який більше
   не пригнічує активне порушення, сам є дефектом (перевірка застарілих записів 6A.3
   завершить перевірку помилкою через осиротілий запис у списку дозволів після реалізації).

**Не додавайте записи до списку дозволів, щоб швидше пройти тести.** Зелена перевірка зі списком дозволів, що постійно
зростає, створює хибне відчуття якості.

### Якщо перевірка завершується помилкою у вашому PR

1. **Уважно прочитайте вивід перевірки** — він точно вказує, який файл або символ порушив правило.
2. **Виправте порушення** — більшість перевірок є детермінованими перевірками файлової системи, які проходять одразу,
   щойно код стає правильним.
3. **Якщо порушення існувало раніше** (тобто ви його не внесли, але тепер воно охоплюється перевіркою): додайте запис
   до списку дозволів із коментарем-обґрунтуванням і задачею відстеження.
4. **Якщо перевірка використовує порогове підвищення** (покриття, попередження ESLint, дублювання, складність):
   ваша зміна погіршила показник. Виправте основну проблему або (у рідкісних випадках) виконайте
   `npm run quality:ratchet -- --update`, якщо зміна є навмисною, а погіршення показника прийнятним — але опишіть причину в описі PR.
5. **Рекомендаційні перевірки** (`continue-on-error: true`) мають інформаційний характер — вони не блокують
   злиття, але відображаються у зведенні CI. Усе одно виправляйте їх.

#### `check-key-completeness` — шлюз парності наборів ключів

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, job `i18n-ui-coverage`).
Порівнює набір листових ключів кожного `src/i18n/messages/<locale>.json` з `en.json` і завершується
помилкою за наявності будь-якого відсутнього або зайвого листового ключа, незалежно від того, коли
ключ було додано. Заповнювачі `__MISSING__:` вважаються наявними (їхній вміст належить до логіки
перевірки співвідношення). Це абсолютне доповнення до двох перевірок на основі diff/відсотків:
`check-ui-keys-coverage` забезпечує мінімум 80 % для кожної локалі (43 відсутні ключі з приблизно
13 000 усе ще дають 99,7 %), а `check-new-key-coverage` оцінює лише ключі, які PR додає до
`en.json`. Пакет локалі генерується з `en.json` у день створення її гілки й перекладається протягом
кількох днів, поки база продовжує додавати ключі; PR пакета сам не додає ключів, тому обидва
сусідні шлюзи не спрацювали, коли пакет 1 (#13044) надійшов із 43 відсутніми ключами у дев’яти
локалях, а пакет 2 (#13660) — із 10 відсутніми ключами у восьми (2026-09-15). Виправте червоне
позначення за допомогою
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`; `extra` означає, що
ключ було видалено з джерела — `sync-ui-keys` видалить його (`--prune-extra`, значення за
замовчуванням). `--warn` звітує без завершення з помилкою.
`--catalog=cli` запускає те саме порівняння для `bin/cli/locales` (`npm run i18n:check-keys:cli`);
обидва кроки виконуються в job `i18n-ui-coverage`. Абсолютна перевірка виконується лише в режимі
релізу: feature PR бачить `SKIP reason=pr-mode`, а виправлення запускається в оновленні релізу або
хвилі перекладів, ніколи у feature PR; PR, який змінює каталоги локалей, натомість перевіряється
для кожного з них порівняно з базою злиття (див. «Два режими» в job `i18n-ui-coverage`).

#### `check-new-key-coverage` — шлюз i18n для нових ключів

Сусідній до `check-ui-value-drift`. Той виявляє англійське значення, яке було **переписано**,
тоді як його переклади залишилися без змін; цей виявляє англійський ключ, який було **додано**,
тоді як деякі локалі його так і не отримали.

`check-ui-keys-coverage` не бачить цей клас проблем: він забезпечує мінімальний відсоток для кожної
локалі, і одинадцять відсутніх ключів із приблизно 13 000 листових ключів дають покриття 99,9 %.
Відсоток для мови не може виразити ситуацію «цю функцію випущено без перекладу» — ціла функція
може з’явитися в новій локалі без тексту, і показник ніколи не зміниться.

Інцидент, який він кодує: одинадцять ключів Phase 3 для Orchestration Canvas було перекладено для
42 локалей, що існували на той момент. Через кілька годин пакет мов ЄС (#13044) збільшив кількість
локалей у репозиторії до 51, і дев’ять нових (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`)
так і не отримали ці ключі. `deepMergeFallback` підставляє англійське значення для відсутнього
ключа, тому результатом було неперекладене, а не порожнє, UI — реальна й за задумом непомітна
проблема.

Як і його сусідній шлюз, він **враховує diff**, порівнюючи англійську версію в базі злиття з
робочим деревом, тому попередні прогалини залишаються зафіксованими, і для його ввімкнення не
потрібна міграція.

**Маркер `__MISSING__:<english>` не задовольняє цю перевірку (починаючи з 2026-09-17).** Раніше
це було задокументоване відтермінування — середовище виконання повертається до правильного
англійського тексту — доки 2026-09-16 вісім feature PR додали 61 ключ і встановили маркер у всіх
65 локалях замість перекладу: цей шлюз прийняв кожен із них, нічого не заблокувало PR, а шлюз
співвідношення реальних перекладів, який блокує випуск, потім завершився помилкою на вершині
релізу для всіх (pt-BR 3,2 % > 2,5 % + 0,5). Тепер маркер оцінюється як відсутній переклад. Лише
в режимі релізу починаючи з 2026-11-13: feature PR бачить `SKIP reason=pr-mode`, а в релізному
PR (`BASE_REF=origin/main`) шлюз оцінює кожен ключ, доданий у цьому циклі. Виправте червоне
позначення в оновленні релізу або хвилі перекладів за допомогою
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` або
всі локалі паралельно за допомогою `npm run i18n:translate-new-keys`
(`scripts/i18n/translate-new-keys.sh`, безпечний для detached HEAD, відмовляється запускатися без
змінних середовища `OMNIROUTE_TRANSLATION_*`). Ключ, який має залишатися англійською (закріплена
назва продукту/рушія/прапорця), слід додати до `scripts/i18n/untranslatable-keys.json`, а не
ховати за маркером. `vi` повністю забороняє маркери (`tests/unit/i18n-vi-completeness.test.ts`).

#### `check-vitest-exclusions` — шлюз відкладених тестів

Файл у списку `exclude` конфігурації `vitest.config.ts` — це тест, який не запускається, але для
того, хто переглядає дерево, він виглядає як покриття. Шістдесят два файли накопичилися за
коментарем `// #8618 — pre-existing failure; remove this exclusion when fixed`. Issue #8618 було
закрито 2026-08-11, хоча список, за яким воно відстежувалося, зріс із 45 до 62 записів, причому
кожен новий запис успадковував коментар із посиланням на неактуальну issue. Коли список нарешті
виміряли для кожного файлу (#13204), **51 із 62 пройшов перевірку в поточному дереві без змін у
джерельному коді**.

Шлюз вимагає, щоб кожне виключення, яке відповідає реальному файлу, (a) містило назву issue і
(b) з’являлося в `config/quality/vitest-exclusions.json` із виміряним статусом, щоб його додавання
було diff, який можна перевірити, в окремому файлі, а не ще одним рядком у масиві з 60 записів.
Він навмисно не запускає повторно виключені тести — це займає приблизно 10 хвилин і має
виконуватися в періодичному job; інвентаризація фіксує, коли кожен тест востаннє вимірювали.
