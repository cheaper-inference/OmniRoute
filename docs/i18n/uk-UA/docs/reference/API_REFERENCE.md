Основний довідник API OmniRoute. Він охоплює загальнодоступну поверхню `/v1` і найчастіше використовувані кінцеві точки керування; машиночитний [`docs/openapi.yaml`](../openapi.yaml) і дерево маршрутів у `src/app/api/` є вичерпними джерелами.

Зосереджену матрицю можливостей сумісного з OpenAI протоколу та провайдерів дивіться в
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md).

Кожне розгортання надає власну копію специфікації за адресою `/openapi.yaml`, згенеровану з `docs/openapi.yaml` під час складання. Вона містить версію збірки та відносну URL-адресу сервера (`./`), тому запити залишаються на хості, який надав цей документ. Інструмент, що імпортує завантажений файл, не має такого хоста, тому базову URL-адресу потрібно вказати вручну.

## Чатові доповнення

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Користувацькі заголовки

| Header                   | Напрямок  | Опис                                                                                                                                                                                                                                    |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Запит     | Установіть значення `true`, щоб обійти кеш                                                                                                                                                                                              |
| `x-omniroute-no-memory`  | Запит     | Установіть значення `true`, щоб пропустити ін’єкцію пам’яті й навичок для цього запиту (працює аналогічно до no-cache; уникає накладних витрат на токени/вартість для кожного виклику)                                                  |
| `X-OmniRoute-Progress`   | Запит     | Установіть значення `true` для подій перебігу                                                                                                                                                                                           |
| `X-Session-Id`           | Запит     | Ключ закріпленого сеансу для зовнішньої прив’язки сеансів                                                                                                                                                                               |
| `x_session_id`           | Запит     | Також приймається варіант із символом підкреслення (безпосередній HTTP)                                                                                                                                                                 |
| `X-OmniRoute-Session-Id` | Запит     | Тег сеансу/розмови, наданий викликувачем (також передається до пам’яті). Якщо присутній, зберігається без змін у `call_logs.session_tag` для атрибуції вартості за сеансами (#8249) — ніколи не створюється автоматично, якщо відсутній |
| `Idempotency-Key`        | Запит     | Ключ дедуплікації (5-секундне вікно)                                                                                                                                                                                                    |
| `X-Request-Id`           | Запит     | Альтернативний ключ дедуплікації                                                                                                                                                                                                        |
| `x-omniroute-connection` | Запит     | Прив’язує запит до однієї моделі до одного підключення постачальника (облікового запису) за його ідентифікатором — див. [Прив’язка облікового запису для кожного запиту](#account-pinning-per-request)                                  |
| `X-OmniRoute-Cache`      | Відповідь | `HIT` або `MISS` (без потокової передачі)                                                                                                                                                                                               |
| `X-OmniRoute-Idempotent` | Відповідь | `true`, якщо виконано дедуплікацію                                                                                                                                                                                                      |
| `X-OmniRoute-Progress`   | Відповідь | `enabled`, якщо відстеження перебігу увімкнено                                                                                                                                                                                          |
| `X-OmniRoute-Session-Id` | Відповідь | Фактичний ідентифікатор сеансу, використаний OmniRoute                                                                                                                                                                                  |
| `X-OmniRoute-Request-Id` | Відповідь | Ідентифікатор кореляції запиту (якщо відомий)                                                                                                                                                                                           |
| `X-OmniRoute-Version`    | Відповідь | Версія збірки OmniRoute (завжди присутня)                                                                                                                                                                                               |
| `X-OmniRoute-Cost-Saved` | Відповідь | Сума в USD, заощаджена завдяки кешу під час `HIT` (лише для влучань у кеш)                                                                                                                                                              |
| `X-OmniRoute-Decision`   | Відповідь | Трасування маршрутизації: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` — комбінована стратегія або `single` для запиту без комбінації) — завжди присутнє у відповідях після завершення                                 |

> Примітка щодо Nginx: якщо ви покладаєтеся на заголовки з символом підкреслення (наприклад, `x_session_id`), увімкніть `underscores_in_headers on;`.

#### Прив’язка облікового запису для кожного запиту

Якщо постачальник має кілька підключень (облікових записів або ключів), OmniRoute зазвичай вибирає одне
за допомогою стратегії вибору облікового запису. Натомість запит може прив’язати одне конкретне підключення
за допомогою заголовка `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Де знайти ідентифікатор.** Відкрийте сторінку провайдера на інформаційній панелі
  (**Dashboard → Providers → <provider>**) і натисніть чип ідентифікатора `xxxxxxxx…` у рядку
  підключення — буде скопійовано повний ідентифікатор підключення.
- **Які запити його враховують.** Запити до однієї моделі (`provider/model`) на
  `/v1/chat/completions`, `/v1/messages` і `/v1/responses`. Комбіновані запити ігнорують цей
  заголовок: закріплюйте обліковий запис для кожного кроку комбінації через власне підключення
  цього кроку.
- **Закріплення є суворим, а не бажаним налаштуванням.** Закріплене підключення використовується
  виключно. Помилка під час виконання запиту фіксує період охолодження облікового запису, але
  **не** перемикає запит на дочірній обліковий запис того самого провайдера.
- **Період охолодження та квота скасовують закріплення.** Поки закріплене підключення перебуває
  на охолодженні, вичерпало квоту або заблоковане політикою квот, наступні запити переходять до
  інших підключень провайдера — так само, як і незакріплений трафік.
- **Невідомі або вимкнені ідентифікатори спричиняють помилку.** Ідентифікатор, якого немає в
  активному пулі провайдера (видалений, деактивований або такий, що належить іншому провайдеру),
  не залишає доступних облікових записів, тому запит завершується помилкою, а не непомітно
  перенаправляється в інше місце.

Claude Code надсилає власні заголовки через `ANTHROPIC_CUSTOM_HEADERS`. Додайте його до блоку
`env` файлу `~/.claude/settings.json` або до `.claude/settings.json` на рівні проєкту, щоб
закріпити інший обліковий запис для кожного проєкту:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Джерело: `src/sse/handlers/chat.ts` (читання заголовка), `src/sse/services/auth.ts` і
`src/sse/services/sessionAffinityPin.ts` (скасування закріплення та перевірка відсутності в пулі).

> **Заголовки телеметрії вартості:** відповіді про успішне виконання без потокової передачі також містять набір заголовків телеметрії вартості `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фіксовані 10 десяткових знаків; `0.0000000000` для безкоштовних запитів або запитів без визначеної вартості), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` і `X-OmniRoute-Fallback-Attempts` (лише якщо значення > 0), а також `X-OmniRoute-Request-Id` і `X-OmniRoute-Version`. Вони надсилаються для chat completions, `/v1/responses`, `/v1/messages` **і медіаендпоїнтів** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` і `/v1/moderations` (вартість завжди `0`). Вартість медіа обчислюється для кожної модальності (за зображення, за секунду, за символ, за одиницю пошуку), якщо ціни доступні; в іншому разі використовується `0` (режим fail-open).

> **Семантика вартості в разі влучання в кеш:** у разі влучання в семантичний кеш (`X-OmniRoute-Cache-Hit: true`) виклик upstream не здійснюється, тому `X-OmniRoute-Response-Cost` дорівнює `0.0000000000` (**приростовій** вартості обслуговування влучання). Початкова/гіпотетична вартість передається окремо в `X-OmniRoute-Cost-Saved`. Споживачі даних для білінгу мають підсумовувати `X-OmniRoute-Response-Cost` (влучання нічого не коштують); аналітика кешу може агрегувати `X-OmniRoute-Cost-Saved`.

## Ексклюзивні оренди керованих сеансів

Ексклюзивна оренда керованого сеансу — це опційний, нейтральний до клієнта контракт маршрутизації: один активний власник
утримує одне придатне для використання з’єднання OmniRoute. Вона не орендує модель, не потребує OAuth, не ідентифікує
певного клієнта та не потребує певного провайдера.

Ключ автентифікації повинен мати область `lease:exclusive` і явний непорожній
список `allowedConnections`. Межа мутації бази даних забезпечує наявність обох полів разом під час створення ключа
та часткових оновлень.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

У відповідях на успішні операції acquire, renew і release містяться часові позначки, `state` і точне додатне
значення `generation`, але ніколи не вказуються вибране з’єднання чи облікові дані. Операції renew і release передають
значення generation у тілі JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Активний власник оренди може явно запитати безпечні для конфіденційності метадані відображення для свого поточного
прив’язування:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ця опційна дія status захищена непрозорим власником, автентифікованим керованим API-ключем і точним
активним generation в одній транзакції бази даних. `displayName` — це лише обрізане налаштоване
ім’я з’єднання; якщо безпечного налаштованого імені немає, використовується `null`. OmniRoute ніколи не підставляє
електронну адресу або згенеровану ідентичність облікового запису. Значення provider — це нечутлива мітка
відображення, а не згенерований ідентифікатор сумісного провайдера. Облікові дані, токени, файли cookie, необроблені
ідентифікатори з’єднань або API-ключів, хеші власників, секрети захисту від повторного використання та внутрішні дані
маршрутизації виключаються.

Пошуки з неправильним ключем, неправильним власником, застарілим generation, відсутнім, простроченим, вивільненим або
недійсним записом повертають ту саму помилку `409 LEASE_FENCE_STALE` без метаданих з’єднання. Клієнт, який отримав
відповідь про очікування доступної місткості, не має активного прив’язування для перевірки. Коли маршрутизація перемикає
активну оренду, той самий generation залишається дійсним, а status атомарно повертає нове прив’язування, ніколи не
повертаючи старе. Наявні клієнти залишаються без змін, оскільки acquire, renew, release і відповіді очікування зберігають
попередні формати.

Цей серверний контракт не змінює стандартний OpenAI Codex `/status`. Стандартний Codex наразі повідомляє свого
провайдера моделі та вбудований стан автентифікації/облікового запису, але не відображає довільні метадані облікового
запису власного провайдера; подальша інтеграція клієнта повинна викликати цю дію та вирішити, як відображати
`connection.displayName`.

Кожен керований запит до системи висновування після цього передає обидва керувальні заголовки:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точні owner, generation, активне з’єднання й автентифікований API-ключ перевіряються безпосередньо перед кожною
підтримуваною спробою звернення до upstream. Повторне використання owner і generation з іншим ключем завершується
помилкою, навіть якщо цей ключ дозволяє те саме з’єднання. Необроблені owner не зберігаються, не записуються в журнали,
не утримуються у знімку запиту та не пересилаються до upstream.

Тимчасова конкуренція повертає HTTP `429` із `Retry-After` і:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Ця відповідь означає лише, що звичайний придатний для використання набір не був порожнім, а кожен вільний кандидат
утримувався сторонньою активною орендою. Непідтримувані моделі/провайдери, невідповідність політиці, період
охолодження, квота, стан працездатності та інші звичайні причини непридатності зберігають наявні відповіді OmniRoute.

### `x-omniroute-compression`

Перевизначення плану стиснення для окремого запиту. Найвищий пріоритет — має перевагу над перевизначенням
комбінації маршрутизації, активним профілем, автоматичним тригером і значенням Default на панелі. Значення:

| Значення      | Ефект                                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `off`         | Для цього запиту стиснення не виконується.                                                                       |
| `default`     | Профіль Default, визначений панеллю (активний профіль ігнорується). Збиткові рушії вимикаються.                  |
| `safe`        | Лише дедуплікація та згортання пробілів.                                                                         |
| `allow-lossy` | Для цього запиту зберігається план оператора, включно з резюме та переписуванням стилю.                          |
| `engine:<id>` | Один рушій, якщо його ввімкнено, наприклад `engine:rtk`. Опційне використання цього рушія для запиту.            |
| `<combo>`     | Іменована комбінація, що спочатку зіставляється за іменем (без урахування регістру), а потім за ідентифікатором. |

Примітки:

- Невідомі значення ігноруються (запит ніколи не відхиляється); визначення переходить до звичайного пріоритету оператора.
- Якщо кілька комбінацій мають спільне ім’я, передайте **id** комбінації для детермінованого зіставлення.
- Комбінацію, ім’я якої — `off` або `default`, не можна вибрати за іменем (ці ключові слова інтерпретуються першими); таку комбінацію потрібно вказувати за її id.
- Головний перемикач стиснення є жорсткою умовою: коли стиснення глобально вимкнено, цей заголовок не може його ввімкнути.

Застосований план повертається у заголовку відповіді:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

де `<source>` — одне зі значень `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` або `off`.

## Вбудовування

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Доступні постачальники: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Ідентифікатори каталогу мають формат `provider/model` (приклад: `jina-ai/jina-embeddings-v5-omni-small`). Скорочені ідентифікатори моделей Jina, які є в реєстрі (наприклад, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), також розпізнаються. Для Jina embed/rerank/classify/segment спочатку використовуються облікові дані `jina-ai` з dashboard; `JINA_AI_API_KEY` є резервним варіантом лише за відсутності ключа в dashboard. Картка `jina-reader` призначена лише для Reader / `r.jina.ai` (`POST /v1/web/fetch`) і ніколи не обслуговує вбудовування або rerank.

Моделі реєстру, які декларують підтримку мультимодальності, також приймають до 32 структурованих елементів, незалежних від постачальника. Типи медіаелементів: `text`, `image`, `audio`, `video` і `document`. Їхнє медіаджерело `source` має формат `{"type":"url","url":"https://..."}` або
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
і псевдонім сімейства `jina-ai/jina-embeddings-v5-omni` → omni-small) також приймає власну
документацію EmbeddingsV5Request Jina і **передає її без змін** до `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Власні значення `{ image | audio | video | pdf }` можуть бути загальнодоступною URL-адресою HTTPS, URI `data:` або необробленим base64. OmniRoute не перетворює ці об’єкти на рядки й не завантажує власні URL-адреси зображень — Jina отримує загальнодоступні медіадані самостійно. Додаткові поля Jina (`task`, `normalized`, `truncate`, `embedding_type`) передаються далі. Текстові SKU Jina також відхиляють документи, що містять нетекстові дані.

Обмеження безпеки й транспортування:

- Віддалені URL-адреси медіа мають бути загальнодоступними HTTPS-адресами. Канонічні елементи `{type,source:url}` завантажуються на стороні сервера (повторна перевірка перенаправлень, тайм-аут, обмеження розміру, загальнодоступний DNS, прив’язка з’єднання) і вбудовуються перед викликом постачальника. Власні елементи Jina `{image:"https://..."}` передаються без змін після тієї самої перевірки загальнодоступного HTTPS; Jina завантажує URL-адресу.
- Вбудовані медіадані base64 обмежені 8 MiB декодованих даних на елемент і 16 MiB декодованих даних на весь запит.

Переклад для постачальників (канонічні елементи ніколи не передаються без змін):

- Мультимодальні моделі Jina: кожен елемент верхнього рівня перетворюється на один об’єкт із ключем модальності (`text` / `image` / `audio` / `video` / `pdf`) із використанням URI `data:` для вбудованих медіаданих; один вектор на кожен елемент верхнього рівня.
- Сімейство Gemini Embedding 2: один масив верхнього рівня перетворюється на один власний запит `models/{model}:embedContent` із `content.parts` (`text` або `inline_data`).
- llama.cpp (`llama-cpp/<model>`, будь-яка модель, завантажена локальним сервером): канонічні елементи `text` перетворюються на звичайні рядки, а `image` / `audio` / `video` — на окремий об’єкт `{"content": [part]}` кожен із використанням частин вмісту чату llama-server (`image_url`, `input_audio` із форматом `wav` / `mp3` / `flac`, `input_video`) із вбудованими даними; один вектор на кожен елемент верхнього рівня. Сервер має працювати з `--embedding --mmproj …`; без проєктора він сам відхиляє медіадані. `document` не підтримується.
- Невідомі/динамічні моделі без явних метаданих модальності відхиляють структурований ввід із HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Непідтримувані комбінації моделей і модальностей повертають HTTP 400 замість примусового перетворення елемента. Додаткові поля, не пов’язані з вводом, у застарілих запитах із рядками/токенами й надалі передаються без змін.

```bash
# List all embedding models
GET /v1/embeddings
```

## Генерація зображень

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Доступні постачальники включають OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локальний), ComfyUI (локальний).

`n` повертає `n` зображень у `data[]`. Постачальники, чиї API вищого рівня повертають одне зображення за виклик
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), отримують `n` окремих викликів API вищого рівня, одночасно виконується не більше 4. Фіксований
`seed` зміщується на індекс виклику (`seed`, `seed + 1`, …), тому зображення відрізняються, але залишаються відтворюваними. Значення `n` обмежене 10. Запит завершується помилкою повністю, якщо будь-який виклик завершується помилкою. Список форматів із розгалуженням викликів міститься в
`SINGLE_IMAGE_FANOUT_FORMATS` у
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux повторно використовує наявне підключення з ключем API та приймає префікси `zenmux/` або `zm/`:

- `zenmux/openai/gpt-image-2` використовує API зображень OpenAI від ZenMux. Доступні такі параметри: `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` і `response_format`.
- Інші видавці, як-от `zm/meta/muse-image-1.0`, використовують кінцеву точку Vertex AI `:predict` від ZenMux. `n` відповідає `sampleCount`, `aspect_ratio` — `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — `sampleImageSize`. Значення `size` у пікселях задає лише співвідношення сторін,
  а не гарантовані розміри в пікселях. Підтримувані співвідношення сторін, роздільні здатності та кількість зображень залежать від моделі.
- `zm/inclusionai/ming-image-0.1-design` самостійно вибирає розміри. Не вказуйте `size`,
  `aspect_ratio` і `image_size`; явне задання цих параметрів повертає HTTP 400. Формати PNG, JPEG і WebP
  можна запитати за допомогою `output_format`.

Ця інтеграція підтримує генерацію зображень із тексту, але не редагування зображень за еталонним зображенням. Вивід Vertex нормалізується до `data[].b64_json`; `response_format: "url"` повертає URL HTTPS від API вищого рівня або URL даних у форматі base64, якщо доступні лише байти зображення. Порожній або відфільтрований результат повертає помилку, а не успішну відповідь із порожнім результатом. Доступ до моделей залежить від облікового запису ZenMux.
Див. [Vertex API ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) і
[API зображень OpenAI](https://docs.zenmux.ai/api/openai/generate-an-image).

Підключення через вхід Microsoft 365 Copilot обслуговує `copilot-m365-web/m365-copilot-image`
через вбудований інструмент зображень Copilot: один сеанс Copilot на зображення (`n` від 1 до 4), `size` впливає
лише на орієнтацію, а зображення повертаються вбудованими (`b64_json` або URL даних для
`response_format: "url"`). Див. [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# Перелік усіх моделей зображень
GET /v1/images/generations
```

```bash
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` вибирає провайдера OCR за префіксом `provider/model`; ідентифікатор моделі без префікса (наприклад,
`mistral-ocr-latest`) зіставляється із зареєстрованим провайдером, а якщо `model` не вказано, використовується
Mistral (`mistral-ocr-latest`). Зареєстровані провайдери (`open-sse/config/ocrRegistry.ts`):

| Ідентифікатор провайдера      | Ідентифікатор моделі | Значення `model`                                        | Примітки                                                                                                                            |
| ----------------------------- | -------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (або `mistral-ocr-latest`) | Синхронний — відповідь повертається безпосередньо з єдиного upstream-виклику.                                                       |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`             | Асинхронний upstream (`analyze` + опитування) — див. нижче.                                                                         |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                 | Синхронний, через партнерську кінцеву точку Vertex AI `openapi/chat/completions` — відомості про авторизацію та URL наведено нижче. |

Усі три провайдери повертають тіло в тому самому форматі, що й Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процес опитування Azure Document Intelligence

API `analyze` Azure Document Intelligence є асинхронним: початковий запит повертає заголовок
`Operation-Location` замість тіла, а результат потрібно отримати за допомогою опитування. Обробник
(`open-sse/handlers/ocr.ts`) опитує цю URL-адресу щосекунди, виконуючи до 30 спроб, негайно завершує роботу (не
продовжує опитування) у разі відповіді опитування з не-`ok` або статусом `"failed"` і повертає `504`, якщо
після вичерпання ліміту спроб операція все ще виконується. Фінальна відповідь Azure нормалізується до тієї самої
структури `pages`/`markdown`, що використовується Mistral, перш ніж повернути її клієнту, тому клієнтському коду
не потрібно обробляти провайдера окремо.

### Авторизація та визначення кінцевої точки Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` повторно використовує ту саму автентифікацію Vertex AI, яку OmniRoute вже підтримує для
трафіку чату/зображень (`open-sse/executors/vertex.ts`): API-ключ підключення — це або облікові дані Service Account
у форматі JSON (обмінюються на короткоживучий токен доступу OAuth через потік JWT-bearer), або вже отриманий токен
доступу OAuth, який використовується без змін. URL upstream-кінцевої точки — це загальна партнерська кінцева точка
Vertex `openapi/chat/completions`, сформована на основі проєкту та регіону підключення: явно вказані
`providerSpecificData.project`/`providerSpecificData.region` завжди мають пріоритет; в іншому разі проєкт
визначається з `project_id` у JSON Service Account, а регіоном за замовчуванням є `us-central1`. Обидва способи
визначення реалізовано в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), а викликаються вони з
`src/app/api/v1/ocr/route.ts` перед передаванням запиту до `handleOcr`.


### Ціни моделей (`pricing`)

Запис містить об’єкт `pricing`, якщо OmniRoute знає ціну моделі. Ціна надходить із таблиці
цін, яку використовує облік витрат: вбудовані значення за замовчуванням, синхронізовані ціни та
перевизначення, задані через `/api/pricing`. Це ціни зі списку, тому для провайдерів із
підпискою також відображається ціна за токен.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Поля                                                            | Одиниця                        | Примітки                                                                                                                                       |
| --------------------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD за токен, десятковий рядок | Сумісні з OpenRouter, ніколи не використовують експоненціальний запис. Два поля кешу відображаються лише за наявності ціни кешування.          |
| `input`, `output`, `cached`, `cache_creation`                   | USD за 1 млн токенів, число    | Поля з попередніх версій каталогу, збережені для наявних клієнтів. `reasoning` і `long_context` також відображаються, якщо вони є в рядку цін. |

- **Комбінації** містять ціну своєї першої видимої цілі. Вбудовані комбінації `auto/*` обирають
  ціль під час виконання запиту, тому не мають `pricing`.
- **Безкоштовні моделі** відображають `"0"` (і `0`), якщо їхня ціна дорівнює нулю. Модель без
  рядка цін також відображає `"0"`, якщо каталог позначає її як безкоштовну (`free: true`) або
  якщо вона міститься у вбудованому каталозі безкоштовних моделей.
- **Невідома ціна:** запис не містить ключа `pricing`.
- **Провайдери з оплатою за кредитами** (наприклад, Kiro) стягують плату за запит, а не за токен. Їхні
  записи зберігають наявні раніше числові поля за 1 млн токенів і не містять рядкових полів за токен.
- **Варіанти** (ідентифікатори рівня зусиль міркування, псевдоніми без міркування, дзеркала
  виявлення та шлюзу) копіюють ціну моделі, до якої вони маршрутизують.
- Поля містять лише базові ставки. Рівні для довгого контексту (числове поле `long_context`) і
  множники рівня обслуговування (наприклад, Codex fast або flex) не змінюють `prompt` або
  `completion`.
- Об’єкт однаковий для всіх способів автентифікації, зокрема для запиту в стилі Anthropic із
  `x-api-key` і `anthropic-version` (відповідь залишається `{ "object": "list",
"data": [...] }`). Реалізація: `src/app/api/v1/models/catalogPricing.ts`.

### Префікси ідентифікаторів моделей (`?prefix=`)

Більшість моделей рекламуються під **префіксом провайдера**. Який префікс ви отримуєте,
визначається функціональним прапорцем `MODELS_CATALOG_PREFIX_MODE` і може бути перевизначений
**для кожного запиту** параметром запиту — це корисно для клієнта, якому потрібен компактний
список без зміни загальносерверного налаштування для всіх інших:

```bash
GET /v1/models?prefix=alias        # один ідентифікатор на модель — короткий префікс-псевдонім
GET /v1/models?prefix=dual         # обидві форми (значення за замовчуванням сервера)
GET /v1/models?prefix=canonical    # лише повний префікс ідентифікатора провайдера
```

| Режим       | Виводить                                                | Примітки                                                                                                                                                                                                                |
| ----------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **і** `claude/claude-sonnet-4-6` | **Значення за замовчуванням.** Обидва ідентифікатори маршрутизуються до тієї самої моделі; збережені для сумісності з конфігураціями клієнтів, у яких жорстко задано будь-яку з форм. Каталог приблизно подвоюється.    |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Один запис на модель. Провайдери без окремого псевдоніма все одно виводять свій запис, тому нічого не втрачається.                                                                                                      |
| `canonical` | `claude/claude-sonnet-4-6`                              | Один запис на модель під повним префіксом ідентифікатора провайдера. Провайдери без окремого псевдоніма (наприклад, `antigravity/…`, `agy/…`) також виводять тут свій єдиний ідентифікатор, тому нічого не втрачається. |

Дзеркало режиму `dual` також можна розпізнати без параметра запиту: воно містить поле `parent`,
що вказує на основний ідентифікатор.

Клієнтам, які відображають засіб вибору моделі, слід надсилати запит із `?prefix=alias` — саме
так робить [розширення OmniCopilot для VS Code](../guides/VSCODE-COPILOT.md).

### Фільтри виявлення (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` підтримує необов’язкові фільтри виявлення. Без них відповідь не змінюється. Вони
звужують каталог, який уже бачить викликач (дозволи API-ключа застосовуються першими), і
виконуються перед посторінковою навігацією у стилі OpenAI через `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # кожна зазначена можливість має бути істинною
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` каталогу; рядки без нього є `chat`
GET /v1/models?q=sonnet&limit=10                           # регістронезалежний пошук за ідентифікатором або назвою
```

| Параметр      | Значення                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | невід’ємне ціле число, що порівнюється з `context_length`                                           |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 символів                                                                                      |

Невідоме значення або `min_context`, яке не є невід’ємним цілим числом (наприклад, `1.5`),
повертає HTTP `400`, а повідомлення містить список допустимих значень. Реалізація:
`src/app/api/v1/models/catalogFilters.ts`.

### Список моделей (`POST /v1/models/query`)

`POST /v1/models/query` повертає короткий детермінований список із того самого каталогу з такими самими
автентифікацією та видимістю для кожного ключа, як і `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Усі поля необов’язкові. `capabilities` і `exclude` приймають масив або рядок, розділений комами;
`max_output` порівнюється з `max_output_tokens`. Результати сортуються за `owned_by`, а потім за `id`.
Значення `limit` за замовчуванням становить `20`, а значення понад `100` обмежуються `100`. Некоректний
JSON, невідоме поле або неприпустиме значення повертає HTTP `400`.

### Індивідуально приховані чат-моделі

Модель, позначена як **Прихована** на сторінці її провайдера, виключається з каталогу та відхиляється
з HTTP `404` / `model_not_found`, якщо її запитано явно. Перевірка використовує визначених провайдера
й модель, зокрема псевдоніми провайдерів, префікси вузлів сумісних провайдерів і значення підключення
за замовчуванням. Комбінація пропускає приховані цілі та може використовувати видимого сусіда; якщо
виконуваних цілей не залишилося, повертається той самий код помилки. Скасування приховування набуває
чинності під час наступного запиту. Перевизначення видимості лише для зображень не приховують чат-модель
із тим самим ідентифікатором.

Цей індивідуальний параметр моделі є окремим від
[списків дозволених/заборонених моделей](../routing/MODEL_EXPOSURE_LIST.md), які фільтрують
відображення в каталозі та кандидатів для автоматичної маршрутизації, водночас зберігаючи явну
диспетчеризацію. Дозволи API-ключа на моделі продовжують застосовуватися незалежно. Режим префіксів
каталогу за замовчуванням залишається `dual`.

### Варіанти моделей без міркування

Для моделей Claude із підтримкою міркування `/v1/models` також рекламує варіант **без міркування**, ідентифікатор
якого має префікс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Вибір цього ідентифікатора (наприклад, у конфігурації Claude Code, яка завжди додає блок `thinking`)
повертає його до справжніх `<provider>/<model>` із вимкненим міркуванням — `thinking:{type:"disabled"}`
для шляху `/v1/messages` або з вилученими полями `reasoning`/`reasoning_effort` для шляху
`/v1/chat/completions`. Варіант наводиться в списку лише для моделей сімейства Claude, які підтримують
міркування **і** враховують `disabled` (отже, наприклад, моделі, що підтримують лише адаптивний режим
і відхиляють `disabled`, виключаються). Оператори можуть примусово ввімкнути або вимкнути цей варіант
для кожної моделі за допомогою `ModelSpec.noThinkingAlias`.

## Генерація аудіо ElevenLabs

Налаштуйте підключення провайдера `elevenlabs` в OmniRoute за допомогою ключа API ElevenLabs.
Клієнти проходять автентифікацію за допомогою ключа **OmniRoute**
(`Authorization: Bearer $OMNIROUTE_API_KEY`); шлюз передає збережений ключ провайдера як `xi-api-key`.
Ніколи не надсилайте ключ ElevenLabs як токен bearer шлюзу.

| Метод | Шлях                        | Відповідь                                  | Категорія кінцевої точки ключа API |
| ----- | --------------------------- | ------------------------------------------ | ---------------------------------- |
| POST  | `/v1/sound-generation`      | Нативні байти аудіо                        | `elevenlabs`                       |
| POST  | `/v1/music`                 | Нативні байти аудіо                        | `music`                            |
| POST  | `/v1/music/stream`          | Потокові байти аудіо                       | `music`                            |
| POST  | `/v1/music/detailed`        | Нативне multipart-аудіо та план композиції | `music`                            |
| POST  | `/v1/music/detailed/stream` | Нативні метадані SSE та фрагменти аудіо    | `music`                            |
| POST  | `/v1/music/plan`            | JSON-план композиції                       | `music`                            |

Ці кінцеві точки доповнюють наявні маршрути `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` і `/v1/speech-to-text`. Нативні поля JSON
та параметри запиту, як-от `output_format` і `enable_logging`, зберігаються.
Відповіді `/v1/music/detailed` зберігають свої multipart-роздільники; обробляйте їх як multipart.
`/v1/music/detailed/stream` повертає `text/event-stream` із метаданими композиції та
аудіофрагментами base64 у подіях SSE. Усі шість маршрутів підтримують попередню перевірку CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Короткий звуковий ефект. Тривалість: від 0.5 до 30 секунд.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Тривалість музики виражається в мілісекундах: від 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Використовуйте `/v1/music/stream` з таким самим тілом JSON для поступової доставки аудіо. Композиція
приймає рівно одне з `prompt` або `composition_plan`; `/v1/music/plan` вимагає `prompt`
і додатково приймає `source_composition_plan`. Нативні схеми зберігають додаткові
поля провайдера, тому версії планів композиції та параметри тонкого налаштування передаються до ElevenLabs.

Уніфікована кінцева точка `/v1/music/generations` також приймає
`elevenlabs/music_v1`, `elevenlabs/music_v2` і `elevenlabs/music_v2_5`. За активного підключення ElevenLabs
ці моделі доступні в каталозі музики. Ця кінцева точка повертає
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Її поле `duration` задається в
секундах і відповідає `music_length_ms`; явно вказане `music_length_ms` має пріоритет.
`instrumental` відповідає `force_instrumental`, причому нативне поле має пріоритет.
Для потокової передачі використовуйте нативні потокові кінцеві точки, а для запитів, що керуються лише
планом композиції, — нативну кінцеву точку композиції.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Обмеження кінцевої точки, моделі, бюджету та підключення застосовуються до виклику upstream. Нативні
маршрути повертають коди стану та тіла помилок upstream без змін, зокрема `402` для обмеження плану
та `429` для перевищення квоти. Заголовки `character-cost`, `song-id`, `request-id` і `retry-after`
зберігаються, якщо вони присутні. Наявність безкоштовного кредитного балансу не гарантує доступу до кожної
музичної моделі, формату виведення чи функції API: ElevenLabs визначає доступність для кожного запиту.
Уніфікована кінцева точка зберігає коди стану помилок у нормалізованій оболонці помилки OmniRoute.

Контракти upstream: [звукові ефекти](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[композиція музики](https://elevenlabs.io/docs/api-reference/music/compose) та
[деталі потокової музики](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# Для Soniox TTS потрібні мова та голос: `language` за замовчуванням має значення "en"; відсутній
# голос або стандартне ім’я голосу OpenAI (alloy, nova, …) перетворюється на "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png
```

> **Вузли провайдерів rerank:** `POST /v1/rerank` також маршрутизує запити до сумісних з OpenAI вузлів провайдерів
> (oMLX, vLLM, Infinity, TEI за шлюзом, …), адресованих як `<node-prefix>/<model>`. Вузли
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) завжди доступні, як і імена хостів,
> перелічені оператором у `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (наприклад, назва сервісу Docker/Compose,
> така як `http://reranker:8080/v1`; до них звертаються безпосередньо, ніколи через
> `HTTP(S)_PROXY` або закріплений проксі підключення). Вузли на будь-яких інших
> хостах — у локальній мережі або однорангові вузли Tailscale — доступні лише коли оператор вмикає
> функціональний прапорець `RERANK_REMOTE_PROVIDER_NODES` **і** базова URL-адреса вузла відповідає
> політиці вихідних URL-адрес провайдера (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Крок повторного ранжування рушія пам’яті викликає цей маршрут через
> loopback, тому це саме правило визначає поведінку `rerankProviderModel` у налаштуваннях Memory.
>
> **Формати локального сервера:** виклик вузла виконується за адресою `<base>/v1/rerank`, а у разі 404 — за адресою `<base>/rerank`
> (Infinity, TEI). Тіло запиту до upstream містить обидва варіанти написання Cohere/OpenAI (`documents`,
> `return_documents`) і варіант написання TEI (`texts`, `return_text`), а відповідь upstream
> нормалізується до конверта Cohere: необгорнутий масив TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> від тонких шлюзів і `{data: [...]}` у стилі Voyage повертаються клієнту як
> `{results: [{index, relevance_score, document?}]}`, відсортовані за оцінкою та обмежені значенням `top_n`.

> **Виявлення вузлів провайдерів:** моделі на сумісному з OpenAI вузлі провайдера з’являються в `GET /v1/models`
> із префіксом вузла. Рядки без метаданих кінцевої точки (типово для локальних списків `/v1/models`)
> успадковують `apiType` вузла, тому моделі вузла `embeddings` мають тип `type: "embedding"`, а
> моделі вузла `rerank` — тип `type: "rerank"` замість типового chat; явне значення
> `supportedEndpoints` у синхронізованому або доданому вручну рядку все одно має пріоритет.

## API пошуку

Абстракція постачальника вебпошуку/пошуку (Tavily, Brave, Exa, Serper тощо).

| Метод | Шлях                   | Опис                                                                                                                   |
| ----- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | Список налаштованих постачальників пошуку та їхніх можливостей                                                         |
| POST  | `/v1/search`           | Виконання пошукового запиту — тіло перевіряється за допомогою `v1SearchSchema`, підтримує кешування/об’єднання запитів |
| GET   | `/v1/search/analytics` | Статистика звернень/затримок/кешу для кожного постачальника                                                            |

**Автентифікація:** ключ API Bearer (`extractApiKey` + `isValidApiKey`). Політика пошуку застосовується через `enforceApiKeyPolicy`.

**Автоматичний вибір:** якщо `provider` не вказано, спочатку використовується найдешевший постачальник із налаштованим підключенням, а наступний за ціною є резервним. Безкоштовні резервні постачальники останньої інстанції (`duckduckgo-free`) використовуються лише тоді, коли більше нічого не налаштовано. Власний SearXNG вважається налаштованим, щойно його підключення зберігає справжній `baseUrl` (а не типовий URL каталогу `http://localhost:8888/search`): тоді він займає позицію постачальника за $0 перед постачальниками з ключами, а найдешевший постачальник із ключем є резервним, зокрема коли SearXNG відповідає кодом 400, 401, 403 або 404. Значення `baseUrl`, яке не є дійсним URL `http(s)` або вказує на адресу хмарних метаданих, не враховується. Підключення SearXNG, у якому зберігається токен, ранжується таким чином лише для `https://` або loopback `http://`. Для віддаленого звичайного `http://` воно ніколи не є резервним і залишається варіантом останньої інстанції: використовується лише тоді, коли не налаштовано жодного іншого постачальника або коли його запитано за назвою; у цих двох випадках токен справді надсилається у відкритому вигляді.

### `provider_options` для Exa і Tavily

Exa і Tavily зчитують специфічні для постачальника поля з простору імен:
`provider_options.exa` (або `provider_options["exa-search"]`) і `provider_options.tavily`
(або `provider_options["tavily-search"]`). Передаються лише наведені нижче ключі. Кожен із них
перевіряється за власною схемою Zod у `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ із неправильним типом відкидається. Будь-який інший ключ ігнорується, зокрема ключі автентифікації, базовий URL,
`stream` і `outputSchema`. Плоскі ключі, які використовуються іншими постачальниками (`cx`, `depth`, ...), працюють
як і раніше.

| Постачальник | Поля верхнього рівня                                                                                                                                                                                                                                                                                                                                                      | Вкладені                                                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa          | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоскі примітиви), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` об’єднуються зі типовим значенням `{ text: true, highlights: true }` |
| Tavily       | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                  |

Загальні поля завжди мають пріоритет: `query`, `max_results`, `filters` (домени), `country` і
тема, отримана з `search_type`. Для Exa значення `search_type: "news"` зберігає
`category: "news"`.
Tavily також приймає `search_type: "finance"` (`topic: "finance"`).

Вартість пошуку Firecrawl записується за кожен розпочатий блок із 10 повернутих результатів — по $0.002 (2
кредити) за блок, причому за один виклик стягується плата щонайменше за один блок
([тарифи Firecrawl](https://docs.firecrawl.dev/billing)): 11 результатів коштують $0.004.

Загальний `time_range` тепер передається обом постачальникам: Exa отримує `startPublishedDate` (мітку часу ISO),
а Tavily — `start_date` (`YYYY-MM-DD`). Явно вказана дата в `provider_options`
має пріоритет над зіставленою датою.

Результати Exa зберігають `id`, `highlights` (кожне виділення, а не лише перше, використане як
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` і `extras` у
`provider_raw`. Результати Tavily зберігають `images` і `favicon`.

Вартість пошуку Linkup записується як $0.005 для `depth` `fast` і `standard` та $0.05 для
`deep` ([тарифи Linkup](https://docs.linkup.so/pages/documentation/development/pricing)),
незалежно від того, чи походить `depth` із `provider_options`, чи з налаштувань підключення.

Exa `type: "lite"` (Exa 3.0) приймає менший набір полів і відхиляє весь запит, якщо встановлено будь-яке інше поле. Для lite
`additionalQueries`, `systemPrompt` і кожен ключ `contents`, крім `text` і `highlights`, відкидаються перед викликом. Застарілі
`subpages`, `subpageTarget`, `highlights.numSentences` і `highlights.highlightsPerUrl` більше не передаються.

Облік вартості здійснюється за плоским реєстром `costPerQuery`, за винятком Exa, для якого діють власні тарифи Exa: $0.007 за виклик для `auto` (і застарілого `fast`) або $0.004 для `lite` (і застарілого `instant`), що охоплює 10 результатів; $0.001 за кожен наступний результат; і $0.001 за кожен повернений результат, якщо встановлено `contents.summary`. Tavily обліковується як 1 кредит ($0.008) для `search_depth` `basic`, `fast` і `ultra-fast`, а також як 2 кредити ($0.016) для `advanced`
([кредити API Tavily](https://docs.tavily.com/documentation/api-credits)). Виклик із
`auto_parameters: true`, для якого Tavily підвищує рівень до advanced, усе одно обліковується як 1 кредит.

## API отримання вебданих

Видобуває вміст із URL-адреси через налаштованого постачальника отримання вебданих (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, той самий ключ API, що й для Parallel Search) повертає лише Markdown — будь-який інший
`format` спричиняє помилку `400` — і обмежує вміст до 100 000 символів. Якщо цільову сторінку неможливо видобути, upstream повідомляє про це всередині HTTP 200;
OmniRoute подає це як `422` із фіксованим повідомленням.

| Метод | Шлях            | Опис                                                                        |
| ----- | --------------- | --------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Отримати/зішкребти URL — тіло перевіряється за допомогою `v1WebFetchSchema` |

**Автентифікація:** ключ API Bearer (`extractApiKey` + `isValidApiKey`). Політика застосовується через `enforceApiKeyPolicy`.

**Резервний варіант із урахуванням квоти (#8297):** якщо явний `provider` не вказано, пул
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) проходиться у фіксованому
порядку пріоритету (fill-first) — налаштований постачальник, який обмежений частотою запитів, пропускається
замість дострокового завершення запиту, а повторювана/квотна помилка upstream (HTTP 429 завжди; 402/403 для Firecrawl/Tavily/TinyFish у випадку безкоштовних рівнів із квотами —
але не для Jina Reader і ніколи не для звичайного некоректного запиту 400) передається наступному ще не перевіреному постачальнику з обліковими даними під час виконання запиту. Коли всі постачальники в пулі вичерпано, кінцева точка повертає один `429` (із заголовком `Retry-After`) замість попереднього загального `400`. Коли запитано явний `provider`, **тихого резервного переходу немає** — постачальник, указаний явно, передає власну помилку (`429`, якщо перевищено обмеження частоти, інакше статус upstream).

## Потокова передача через WebSocket

```bash
GET /v1/ws?handshake=1
```

Перевіряє рукостискання оновлення WebSocket і повертає приклади повідомлень протоколу дроту (`request`, `cancel`). Фактичні кадри WS обробляються вбудованим WS-сервером поза таблицею маршрутів Next.js.

**Автентифікація:** ключ API Bearer під час рукостискання.

### Responses API через WebSocket (лише codex)

```bash
# Той самий host:port, що й для HTTP API (типово 20128); оновлення з’єднання:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (або: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Першим кадром MUST бути response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Проксі Responses-API-over-WebSocket підключено **виключно до `codex`** (серверної частини ChatGPT). Він прослуховує той самий порт, що й API/панель керування, за шляхами `/v1/responses`,
`/responses` і `/api/v1/responses`. Під час першого кадру `response.create` він автентифікує запит і готує його через внутрішній міст `codex-responses-ws`, вибирає OAuth-з’єднання codex і тунелює запит до
`wss://chatgpt.com/backend-api/codex/responses` через транспорт `wreq-js`. **Моделі, що не належать до codex, відхиляються** (`codex_ws_provider_required`).
Для маршрутизації зі спільним використанням квоти застосовуйте `model: "qtSd/<group>/codex/<model>"`. Реалізовано у
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Автентифікація:** ключ API Bearer під час рукостискання. Вбудований HTTP-сервер (`server-ws.mjs`)
має бути активною точкою входу (типово це так, коли існує `app/server-ws.mjs`).

#### Ідентифікатор моделі: використовуйте базовий ідентифікатор ChatGPT (без префікса `codex/`)

OpenAI **Codex CLI** перевіряє назву моделі на стороні клієнта, коли
`supports_websockets = true`, і **відхиляє ідентифікатори з префіксом постачальника**, як-от
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Надсилайте **базовий** ідентифікатор (наприклад, `gpt-5.5`). Міст OmniRoute працює лише з codex, тому повторно визначає базовий ідентифікатор як модель codex
(`resolveCodexWsModelInfo`) перед тунелюванням upstream — навіть попри те, що базовий
`gpt-5.5` в іншому разі через HTTP маршрутизувався б до іншого постачальника.

#### Налаштування OpenAI Codex CLI

Спрямуйте Codex CLI до OmniRoute, додавши спеціального постачальника з підтримкою WebSocket до `~/.codex/config.toml` (використовуйте окремий
`CODEX_HOME`, щоб не змінювати наявну конфігурацію):

```toml
model = "gpt-5.5"                 # базовий ідентифікатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без кінцевої косої риски; URL WS виводиться автоматично (у production використовуйте https/wss)
wire_api = "responses"                    # єдине підтримуване значення з лютого 2026 року
supports_websockets = true                # вмикає транспорт Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # містить ключ API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ключ API OmniRoute (будь-який ключ, якщо REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI оновлює `base_url + /responses` до WebSocket, а OmniRoute тунелює його до вибраного OAuth-з’єднання codex. Перевірено наскрізним тестуванням на локальному сервері: ChatGPT повертає
`codex.rate_limits` + `response.created` і передає результат потоково.

### Відновлення сеансу квоти (за вибором)

Не потоковий `POST /v1/chat/completions` або `POST /v1/responses`, який завершується
термінальною помилкою квоти (`402`/`429`/`503`), тіло якої повідомляє про вичерпання квоти
або кредитів, можна призупинити й повторити пізніше замість повернення помилки. Викликач
вмикає цю функцію для кожного запиту за допомогою трьох заголовків:

| Заголовок                    | Значення                                                         |
| ---------------------------- | ---------------------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                                           |
| `x-omniroute-session`        | ідентифікатор сеансу, `[A-Za-z0-9._:-]{1,128}`                   |
| `x-omniroute-recovery-turn`  | ідентифікатор кроку, унікальний у межах сеансу (те саме правило) |

Право на відновлення мають лише кроки зі `stream: false`, без інструментів, історії інструментів
або `previous_response_id`, а також без фіксації `x-omniroute-connection`; крім того, має бути
встановлено `STORAGE_ENCRYPTION_KEY` (запит зберігається в зашифрованому вигляді до 24 годин).
Після цього відповідь має статус `202` і містить `recovery.poll`; опитуйте
`GET /v1/quota-recoveries/{id}` (`202` у стані очікування, `200` із
відновленим тілом після завершення) або скасуйте операцію за допомогою `DELETE`. Квитки видимі
лише API-ключу, який їх створив. Повторне виконання, результат якого невідомий, завершується
станом `needs_confirmation`, а не надсилається двічі. Джерело: `src/lib/quota/quotaSessionRecovery.ts`.

## Використання самообслуговування (`/api/usage/om-usage`)

Будь-який ключ API може читати** свій власний** використання та квоти — без авторизації керування. Це кінцева точка, яку використовує клієнт (CLI, панель OmniCopilot ), щоб показати власнику ключа свої витрати.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Ключ повинен мати**`allowUsageCommand`** увімкнено (вимкнено за замовчуванням — менеджер ключів API інформаційної панелі вмикає його для кожного ключа). Без нього кінцева точка відповідає `403`.

`?format=json` повертає дискриміновану форму, тому абонент ніколи не читає поле даних із відмови. На успіх:

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При відмові (`401` поганий ключ / `403` не дозволено) той самий маршрут повертає `{ "allowed": false, "error": { "message": "…" } }` — наявний, але порожній `personal`/`provider` (ключ дозволено, нічого ще не вивчено) – це інший стан від відмови, і їх розрізняє лише форма JSON.

**авторизація:** власний ключ API носія абонента, перевірений за допомогою `isValidApiKey` — це _не_ поверхня керування (`/api/keys/…`), яка залишається за `requireManagementAuth`.

### Необроблені відсотки квот, скориговані за обмеженням

Споживаючи `/api/usage/om-usage`, абоненти повинні звернути увагу на різницю між відсотками, представленими в** виведення звичайного тексту** і структурований** вихід JSON** :

| Аспект                     | Формат звичайного тексту (`/api/usage/om-usage` / `@@om-usage`)                                 | формат JSON (`?format=json`)                                                                      |
| :------------------------- | :---------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| **Поле виводу**            | `NN% left` (наприклад, `20% left`)                                                              | `provider.quotas` / `providers[].quotas`                                                          |
| **Вимірювання**            | **Коригований граничний припуск** : залишкова ємність вище порогу відключення                   | **Необроблена квота вгору** : невідкоригований показник постачальника                             |
| **Відрізне масштабування** | Масштабується через `effectiveRemainingPercent()`, тому захищений резерв читається як `0% left` | Немає (необроблені значення знімка, як повідомляє постачальник)                                   |
| **Порогові дані**          | Включено до відображеного відсотка                                                              | Зберігається в `quotaWindowThresholds` для кожного з’єднання (або стандартних параметрів сервера) |
| **Первинний споживач**     | Інтерактивний CLIs, термінальні підказки, оператори                                             | Програмні інтеграції, інформаційні панелі, аналітика, трекери білінгу                             |

#### Формула коригування відсічення

OmniRoute підтримує проактивне обмеження квот, щоб запобігти виснаженню висхідного потоку (налаштовується через підключення `quotaWindowThresholds`, стандартні параметри постачальника або глобальні налаштування стійкості). Коли порогове значення відсікання (наприклад, `cutoff = 25%`) активне у вікні квоти, засіб відтворення тексту обчислює залишок дозволу як:

- Якщо `remaining <= cutoff`: повертає `0%`.
- Якщо `remaining > cutoff`: повертає `((remaining - cutoff) / (100 - cutoff)) * 100`.

Відформатований текст округляє це до найближчого цілого числа (`Math.round(...)`).

#### Ілюстративний приклад

Розглянемо вікно провайдера з** 60% використання в сирому вигляді** (отже** 40% квоти, що залишилася** ) і налаштований** 25% залишкової квоти** поріг:

| Представництво                         | Розрахунок                                         | Залишилося |               Мається на увазі                |
| :------------------------------------- | :------------------------------------------------- | :--------: | :-------------------------------------------: |
| **Необроблений JSON (`?format=json`)** | Вихідний знімок (`quotas[window]`)                 |  **40%**   |                    **60%**                    |
| **Текстовий формат (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**   | **80%** (якщо обчислюється `100 - remaining`) |

- **Чому текст показує 20% зліва:** З 40% фізичної квоти, що залишилася на рахунку, 25% зарезервовано політикою відключення. Абонент має лише 15% із 75% корисного запасу, перш ніж маршрутизатор припинить маршрутизацію до цього з’єднання. Масштабування забезпечує вичерпання сигналів підключення (`0% left`) саме тоді, коли маршрутизація припиняється.
- **Чому JSON зберігає необроблені значення:** Корисне навантаження JSON повертає точний знімок провайдера (`UsageSnapshot`), тому зовнішні інструменти мають доступ до використання наземної істини вгорі та `quotaWindowThresholds` на рівні підключення без масштабування з втратами на стороні сервера.

#### Керівництво щодо міграції споживачів

Якщо зовнішня інтеграція (наприклад, плагін редактора або розширення агента) попередньо скопіювала кінцеву точку тексту (`NN% left`) і обчислювала використаний відсоток як `100 - NN`, перехід на `?format=json` означає:

- Читання необроблених значень JSON відобразить** фактичне споживання нагорі** (60% використано у прикладі вище).
- Якщо інтеграція бажає зберегти семантику допустимого використання текстової кінцевої точки, вона може оцінити ефективну формулу, що залишилася, на стороні клієнта, використовуючи `quotaWindowThresholds` для перевизначення на рівні підключення.

## Семантичний кеш

```bash
# Отримати статистику кешу
GET /api/cache/stats

# Очистити всі кеші
DELETE /api/cache/stats
```

Приклад відповіді:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Вплив на затримку

Влучання в семантичний кеш обслуговує відповідь із кешу **без виклику
upstream-сервера**, тому значення `X-OmniRoute-Response-Latency` майже нульове
(незалежно від початкової затримки upstream-сервера). Клієнтам, чутливим до затримки
(бенчмаркінг, моніторинг p50/p99), слід перевіряти заголовок відповіді
`X-OmniRoute-Cache-Latency`:

| Значення      | Значення                                                                |
| ------------- | ----------------------------------------------------------------------- |
| `synthetic`   | Відповідь надано з кешу; затримка не є фактичним часом upstream-сервера |
| _(відсутній)_ | Відповідь від реального виклику upstream-сервера                        |

### Обхід кешу для окремого ключа

Ключі API можуть відмовитися від читання семантичного кешу через `cacheDefaultMode`:

| Значення | Поведінка                                                               |
| -------- | ----------------------------------------------------------------------- |
| `legacy` | Звичайна поведінка кешу (за замовчуванням)                              |
| `bypass` | Повністю пропустити пошук у кеші; завжди звертатися до upstream-сервера |

Задається під час створення ключа (`POST /api/keys`) або оновлення (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Обхід кешу для окремого запиту

Будь-який запит може обійти кеш незалежно від налаштувань ключа:

```
X-OmniRoute-No-Cache: true
```

## Сумісність керування CLIProxyAPI

OmniRoute обробляє три кінцеві точки керування [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI),
які панелі використання викликають для читання лімітів підписок Claude і Codex
(наприклад, джерело лімітів використання `cliproxy` у T3 Code). Вкажіть базову URL-адресу клієнта
на OmniRoute і використовуйте ключ API з областю дії `manage` як ключ керування. Маршрути
доступні за адресами `/v0/management/*` і `/api/v0/management/*`.

| Метод | Шлях                         | Опис                                                                                                                                                         |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET   | `/v0/management/auth-files`  | OAuth-підключення Claude і Codex у форматі `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Токени не передаються                     |
| POST  | `/v0/management/api-call`    | Тіло `{ auth_index, method, url, header?, data? }`. Надсилає один дозволений запит із токеном облікового запису та повертає `{ status_code, body }`          |
| POST  | `/v0/management/reset-quota` | Тіло `{ auth_index }`. Очищує період очікування підключення, блокування моделей і періоди очікування Codex для окремих областей дії одного облікового запису |

- `auth_index` — це ідентифікатор підключення OmniRoute. `provider` — `claude` або `codex` (лише
  OAuth-підключення; постачальник API-ключів `anthropic` не відображається). Для Codex
  `id_token.chatgpt_account_id` — це збережений ідентифікатор робочого простору, а `plan_type` — збережений тарифний план.
- `api-call` не є універсальним проксі. Він приймає лише Claude `GET
https://api.anthropic.com/api/oauth/usage` і Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` і
  `POST .../wham/rate-limit-reset-credits/consume`, причому кожен запит — лише для облікового запису відповідного
  постачальника. Усі інші запити повертають `403`, не звертаючись до upstream-сервера. Заголовок
  `Authorization` виклику (включно із заповнювачем `$TOKEN$`) ігнорується: OmniRoute вставляє
  токен доступу підключення, спочатку оновлюючи його, якщо термін дії майже сплив, і пересилає лише
  дозволені заголовки (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`). Якщо `Chatgpt-Account-Id` не вказано, за замовчуванням використовується збережений ідентифікатор робочого простору.
  Час очікування запитів становить 15 секунд; для них використовується проксі підключення.
- `reset-quota` не змінює кінцеві стани (banned, expired, credits_exhausted). Невідоме
  значення `auth_index` повертає `404`.

**Автентифікація:** сеанс панелі або ключ API з областю дії `manage`; автентифікація

Для моделей synced/imported `PUT /api/provider-models` приймає `provider`, `modelId` і `maxOutputTokenOverride`: додатне ціле число встановлює обмеження ручного виводу токенів, а `null` очищає його, щоб відновити значення за замовчуванням. `GET /api/provider-models?provider=<provider>` повертає ці значення в `modelOutputOverrides`, включаючи моделі без рядка спеціальної моделі. Заміна використовує можливість виконання `max_output_tokens` і зберігається після повторної синхронізації моделі. Сторінка постачальника, сумісного з OpenAI, пропонує ті самі елементи керування edit/clear і позначає моделі з явною підтримкою зору.

На сумісному вузлі постачальника шляхи запису (`POST`, `PUT`, `PATCH`, `DELETE` і `/api/provider-models/validate-and-add`) зберігають ідентифікатор моделі як чистий ідентифікатор висхідного потоку: ідентифікатор, вставлений зі списку з префіксом, має будь-який провідний стек власного префікса вузла згорнутий, а відповіді повторюють збережений ідентифікатор. Розрізнені ідентифікатори канонічних постачальників (наприклад, `nvidia/nemotron-…`) зберігаються дослівно. `/v1/models` ніколи не видає зібраний ідентифікатор `<prefix>/<prefix>/<model>`.

Вузли користувацьких завершень чату адаптують відмову від чітких міркувань до базової версії. Успішний тест з’єднання автоматично вибирає елементи керування шаблону чату для кожної конкретної моделі ID чий запис `/models` підтверджує розпізнане значення `owned_by` : `vllm`, `sglang` або `llamacpp`. Прозорі оболонки, сумісні з OpenAI, можуть зберігати оригінальний запис моделі всередині вкладеного об’єкта `openai` ; виявлення слідує до трьох таких конвертів. Моделі з відсутнім, невідомим або конфліктним правом власності зберігають звичайну поведінку OpenAI. Виявлення повторно використовує наявний запит до каталогу, не генерує маркерів завершення та стає недійсним, коли змінюється кінцева точка підключення.

Щоб закріпити поведінку для серверної частини, яка не розкриває ці метадані, скористайтеся наявним частковим оновленням провайдера API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Надішліть це тіло за допомогою `PUT /api/providers/<connection-id>`. У такому з’єднанні явні міркування `none` надсилаються як `chat_template_kwargs.thinking=false` і `chat_template_kwargs.enable_thinking=false`. Явні власні значення шаблону залишаються авторитетними, якщо правило міркування на стороні сервера не вимагає зусиль. Параметр застосовується лише тоді, коли спеціальне з’єднання, сумісне з OpenAI, надсилає тіло завершення чату; Запити-відповіді та звичайні постачальники зберігають свою рідну форму запиту. Встановіть для `reasoningControl` `openai`, щоб примусово проходити звичайний OpenAI `reasoning_effort`, або опустіть для it/set значення `null` щоб використовувати автоматичне виявлення.

Класифікатор автоматичного режиму коду Claude запитує вимкнути нативне мислення за замовчуванням, якщо воно не містить явних елементів керування аргументацією. Виявлення використовує системний маркер класифікатора в запитах у форматі Claude, а не назви моделей чи обмеження завершення. Явні елементи керування тілом, підтримувані заголовки effort/thinking, правила маршрутизації та дозволена робота моделі зберігають існуючий пріоритет. Обидва етапи класифікатора зберігають свої підказки, ліміти завершення, послідовності зупинок і вердикти реальних дозволів висхідного потоку; друга стадія все ще може створювати необхідне видиме міркування як звичайний текст.

#### Граничне походження моделі

`GET /api/models?withLimits=1` (також `true`; `0`/`false` або його опущення зберігає корисне навантаження за замовчуванням незмінним) додає `contextWindow`, `maxInputTokens`, `maxOutputTokens` і об’єкт `capsSource` до кожного рядка моделі. `capsSource` називає правило, яке встановлює кожне обмеження, тому дивовижне обмеження (наприклад, 128k на моделі 1M) можна простежити до його походження. Вирішені значення є тими самими, що використовуються в маршрутизації; прапор лише додає поля і ніколи не змінює значення. Будь-яке інше значення `withLimits` відхиляється за допомогою `400`.

| значення `capsSource`                        | Походження                                                                   |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| `override:context`                           | Постійне перевизначення контекстного вікна (`model_context_overrides`)       |
| `override:max_input` / `override:max_output` | Перевизначення постійної можливості `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Статична авторитетна контекстно-віконна таблиця                              |
| `synced:<provider>/<model>`                  | рядок синхронізованих можливостей models.dev                                 |
| `registry:<provider>/<model>`                | Запис у реєстрі постачальників                                               |
| `spec:<model>`                               | Статична модель спец                                                         |
| префікс `effort-base:`                       | Ряд, запозичений з базової моделі варіанта з суфіксом зусилля                |
| `none`                                       | Жодне джерело не оголошує обмеження (значення `null`)                        |

Реалізація: `getResolvedModelCapabilitiesWithLimitSources()` в `src/lib/modelCapabilities.ts` і ланцюжки пріоритету в `src/lib/modelCapabilityLimits.ts`.

### Деталізація кадрів відео

`GET /api/v1/video-bridge/drilldown` зчитує пов’язаний із орендарем непрозорий дескриптор, який повертається в `x-omniroute-video-drilldown` після явно погодженого запиту Video Bridge. Для читання та `DELETE` завжди потрібен дійсний ключ API і незалежний дозвіл `modalityBridgeVideoDrilldownRemoteEnabled` від оператора. Збереження виробництва додатково вимагає `modalityBridgeVideoDrilldownEnabled` і суворого `drilldown: true` для кожної частини. Якщо ключ має непорожній список дозволених кінцевих точок, він повинен містити `video` як для GET, так і для DELETE, незалежно від того, чи використовує абонент `/v1` чи `/api/v1`.

запит GET : потрібно `handle`; необов’язковий `variant` (`preview`, `standard`, `detail`), `limit` (1–8; застарілий `frames` приймається, але не може поєднуватися з `limit`), `page` з нульовою базою та `start`/`end` секунди. Якщо задано обидві межі фокусу, `end` має бути більше, ніж `start`. ключі запиту Duplicate/unknown відхилено. Успішні відповіді містять `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` та необов’язковий `focusWindow`; JSON без зберігання обмежено 32 MiB, включаючи Base64. Надмірний вихід повертає 413; запросити менше кадрів.

`DELETE /api/v1/video-bridge/drilldown?handle=...` повертає `{ "removed": 0|1 }`. Невідомий, прострочений і перехресний ключ GETs є нерозрізненими відповідями 404; перехресна клавіша DELETE не може видалити запис власника. Вимкнений доступ повертає 403, автентифікація missing/invalid 401, недійсні запити 400, скасування 499 і тимчасові помилки 503. Дескриптори є локальними для процесу, закінчуються через десять хвилин і не виживають після перезавантаження. Нові дескриптори використовують `v1.` плюс 32-байтовий випадковий маркер Base64URL ; зберігаються лише хеші маркерів. Застарілі 64-шістнадцяткові маркери залишаються синтаксично читабельними для сумісності. Перегляньте [огорожі Video Bridge,](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) щоб дізнатися про згоду, квоти та деталі похідних варіантів.

### Версія та канал випуску

```bash
GET /api/system/version
```

Маршрут керування лише петлею (автентифікація адміністратора). Повертає поточну версію, останню опубліковану версію та статус автоматичного оновлення. `releaseChannel` і `channels` — адитивні поля (rail 3.8.54); `channel` зберігає своє значення — режим розгортання, який використовує програма оновлення панелі інструментів (`npm`, `source` або `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm канал поточної збірки: `nightly` для версій `-nightly.*`, `next` для інших попередніх версій (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` для стабільної версії більш старої, ніж `channels.latest`, інакше `latest`. Ті самі правила, що й у `scripts/release/dist-tag.mjs`, який вибирає npm dist-tag під час публікації.
- `channels` — опублікував заголовок кожного dist-тегу з `npm view omniroute dist-tags` (резервний HTTP реєстру), кешований з тим самим 10-хвилинним TTL що й `latest`. `latest` завжди присутній (повертається до поля `latest`, потім `"unavailable"`); `next`, `nightly` і `lts` з'являються лише тоді, коли цей тег dist існує. Запит `Cache-Control: no-cache` оновлює обидва пошуки.

Модель каналу (`latest` = v3 до версії 4.0 GA, `next` = rc, `nightly` = `develop`, виправлення `lts` = v3 після версії 4.0 GA) описано в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрипція аудіо

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибуйте аудіофайли за допомогою будь-якого налаштованого постачальника STT. Перший сегмент шляху вибирає нативного постачальника (`openai/…`, `deepgram/…`). Шлюзи, які повторно експортують модель іншого постачальника, використовують кваліфікований ідентифікатор
(`openrouter/deepgram/nova-3`).

**Запит:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Відповідь:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Приклади ідентифікаторів моделей:** `openai/whisper-1` (потребує ключ OpenAI),
`openrouter/deepgram/nova-3` (потребує ключ OpenRouter),
`deepgram/nova-3` (потребує нативний ключ Deepgram). Окремий
запит `deepgram/nova-3` **не** використовує OpenRouter.

**Підтримувані формати:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** транскрипція у файловому режимі через WebSocket Gemini Live
(потребує ключ API Gemini). Завантаження перетворюється на монофонічний PCM із частотою 16 кГц за допомогою `ffmpeg`
(`ffmpeg` має бути доступним у `PATH`, якщо файл уже не є монофонічним PCM WAV із частотою 16 кГц), передається до сеансу,
а фіналізований текст повертається як `{ "text": "..." }`. Необов’язкові поля форми `language` і `prompt`
передаються далі. Обмеження: для завантажень понад 25 MiB або декодованого аудіо тривалістю понад 10 хвилин повертається
`413`; перетворення, яке триває понад 60 с, припиняється, і повертається `504`. Ключ API надсилається лише
в заголовку `x-goog-api-key`, ніколи не додається до URL WebSocket.

## Токенізовані псевдоніми VS Code / без заголовків

Використовуйте ці псевдоніми, коли інтеграція не може додати заголовок `Authorization` і потребує вбудовування ключа API в базову URL-адресу.

```bash
# Псевдонім каталогу у стилі OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Псевдоніми чату у стилі OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Псевдоніми у стилі Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Приклад:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Примітки:

- Токенізовані псевдоніми повторно використовують ті самі обробники, що й `/v1/*` та `/api/tags`; форми відповідей залишаються ідентичними.
- За можливості віддавайте перевагу `Authorization: Bearer ...`, якщо клієнт підтримує власні заголовки.
- Токени в URL можуть з’являтися в журналах зворотного проксі, історії браузера та телеметрії за межами OmniRoute. Розглядайте їх як сумісний варіант, а не стандартний режим автентифікації.

```bash
# Отримати стан бюджету для всіх ключів API
```

> **Примітки щодо схеми** (`setBudgetSchema`): `apiKeyId` є обов’язковим; принаймні одне з `dailyLimitUsd`, `weeklyLimitUsd` або `monthlyLimitUsd` має бути більшим за нуль. Необов’язкові поля: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Застаріла форма `{keyId, limit, period}` повертає `400 Bad Request`.

## Ліміти токенів

Ліміти **токенів** для кожного API-ключа (відрізняються від зазначеного вище бюджету в доларах США). Застосовуються безпосередньо під час обробки запиту: коли використання поточного вікна для ключа досягає ліміту, запити відхиляються з помилкою `429 Too Many Requests`. Ліміти можна встановити для конкретної `model`, `provider` або застосувати `global`но до всього ключа; якщо запиту відповідає кілька лімітів, застосовується найсуворіший.

```bash
# Перелік лімітів токенів ключа (містить дані про використання у поточному вікні)
GET /api/usage/token-limits?apiKeyId=key-123

# Створення або оновлення ліміту токенів
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Видалення ліміту токенів за ідентифікатором
DELETE /api/usage/token-limits?id=tl-abc
```

> **Примітки щодо схеми** (`setTokenLimitSchema`): `apiKeyId` і `scopeType` (`model` | `provider` | `global`) є обов’язковими. `scopeValue` є обов’язковим, якщо `scopeType` не має значення `global` (наприклад, ідентифікатор моделі для області `model`, ідентифікатор провайдера для області `provider`). `tokenLimit` має бути додатним цілим числом (перетворюється зі строкового значення). Необов’язкові поля: `id` (не вказувати під час створення, передавати під час оновлення), `resetInterval` (`daily` | `weekly` | `monthly`, значення за замовчуванням — `monthly`), `resetTime` (`HH:MM`), `enabled` (значення за замовчуванням — `true`). Відповіді `GET` доповнюють кожен ліміт полями `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` і `nextResetAt`. Це кінцева точка класу керування (автентифікація централізовано виконується конвеєром авторизації).

## Обробка запитів

1. Клієнт надсилає запит до `/v1/*`
2. Обробник маршруту викликає `handleChat`, `handleEmbedding`, `handleAudioTranscription` або `handleImageGeneration`
3. Визначається модель (безпосередньо провайдер/модель або псевдонім/комбінація)
4. Облікові дані вибираються з локальної БД із фільтрацією доступності облікових записів
5. Для чату: `handleChatCore` перевіряє семантичний кеш/кеш підписів і визначає параметри стиснення комбінації
6. Перед трансляцією для провайдера виконується проактивне стиснення, якщо його ввімкнено (`lite`, Caveman, RTK або стек)
7. Виконавець провайдера надсилає запит висхідному сервісу
8. Відповідь перекладається назад у формат клієнта (чат) або повертається без змін (вбудовування/зображення/аудіо)
9. Записуються дані про використання, аналітика стиснення та журнали запитів
10. У разі помилок застосовується резервний варіант відповідно до правил комбінації

Повний опис архітектури: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Відмовостійкість (розширений опис)

OmniRoute надає три незалежні механізми обробки тимчасових збоїв; наведені нижче кінцеві точки керування дають операторам змогу переглядати їхній стан і перевизначати його:

| Область                       | Зберігання стану                             | Перегляд                                  | Скидання / очищення                                         |
| ----------------------------- | -------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------- |
| Розмикач провайдера           | `domain_circuit_breakers` + пам’ять          | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                |
| Період очікування підключення | `rateLimitedUntil` у підключеннях провайдера | `/api/rate-limits`, `/api/providers/[id]` | (повторно вмикається ліниво; очищення через PUT провайдера) |
| Блокування моделі             | Реєстр доступності моделей у пам’яті         | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                    |

`PATCH /api/resilience` приймає перевизначення розмикачів провайдерів у `providerBreaker.oauth` і `providerBreaker.apikey`. Кожен профіль підтримує `degradationThreshold`, `failureThreshold` і `resetTimeoutMs`; ці самі поля доступні в Панель керування → Налаштування → Відмовостійкість.

```bash
# Очистити блокування однієї моделі
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Видалити всі блокування
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Повний концептуальний довідник і стандартні значення розмикачів див. у [`CLAUDE.md`](../../CLAUDE.md) → «Стан виконання відмовостійкості» та [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Черга обмеження швидкості та автоматичне ввімкнення захисного механізму

- **Підтримуваний шлях запису**: `POST /api/rate-limits` із тілом `{"connectionId": "<id>", "enabled": true|false}` — це підтримувана кінцева точка керування для перемикання захисту від обмеження швидкості для підключення. `PUT /api/providers/[id]` навмисно не змінює та не перемикає `rateLimitProtection` (#11278).
- **Семантика `enabled: false`**: встановлення `enabled: false` вилучає явно заданий захист для підключення, але **не виключає** активне підключення з API-ключем із глобального захисного механізму автоматичного ввімкнення (`autoEnableApiKeyProviders = true`). У `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значення `false` і `undefined` є еквівалентними; активні підключення з API-ключем без явно заданого захисту залишаються захищеними глобальним механізмом автоматичного ввімкнення.
- **Глобальне вимкнення**: щоб запускати підключення з API-ключем без черг обмеження швидкості, вимкніть глобальний захисний механізм через `RATE_LIMIT_AUTO_ENABLE=false` (env) або `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Налаштування → Відмовостійкість / `PATCH /api/resilience`).

## Сервер MCP

OmniRoute постачається із вбудованим сервером Model Context Protocol із 3 транспортами (stdio, SSE, streamable-http) та інструментами з обмеженою областю дії. Наведені нижче кінцеві точки інформаційної панелі зчитують дані про стан/аудит і проксують HTTP-транспорти.

| Метод  | Шлях                   | Опис                                                                                                                             | -------------------- |
| ------ | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| GET    | `/api/mcp/status`      | Сигнал доступності, транспорт, стан онлайн, останній виклик, найпопулярніші інструменти, відсоток успішних викликів за 24 години |
| GET    | `/api/mcp/tools`       | Список інструментів MCP із `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints`                             |
| GET    | `/api/mcp/sse`         | Відкрити потік SSE для транспорту SSE (повертає `503`, якщо MCP вимкнено або транспорт не збігається)                            |
| POST   | `/api/mcp/sse`         | Надіслати кадр JSON-RPC через транспорт SSE                                                                                      |
| GET    | `/api/mcp/stream`      | Відкрити сторону SSE транспорту Streamable HTTP (повідомлення, ініційовані сервером)                                             |
| POST   | `/api/mcp/stream`      | Надіслати кадр JSON-RPC через транспорт Streamable HTTP                                                                          |
| DELETE | `/api/mcp/stream`      | Завершити сеанс Streamable HTTP                                                                                                  |
| GET    | `/api/mcp/audit`       | Виконати запит до журналу аудиту — `?limit=`, `?offset=`, `?tool=`, `?success=true                                               | false`, `?apiKeyId=` |
| GET    | `/api/mcp/audit/stats` | Зведена статистика аудиту (загальна кількість, відсоток успішних викликів, середня тривалість, найпопулярніші інструменти)       |

**Автентифікація:** транспорти `sse`/`stream` використовують спеціальну поверхню автентифікації MCP (ключ API Bearer з областю дії `mcp`); маршрути `status`/`tools`/`audit*` доступні для читання з інформаційної панелі (без додаткової автентифікації, окрім доступу до хоста інформаційної панелі).

> Обидва HTTP-транспорти контролюються параметрами `settings.mcpEnabled` і `settings.mcpTransport` — невідповідність транспорту повертає `400`, а вимкнений стан MCP повертає `503`.

## A2A-сервер

OmniRoute надає кінцеву точку A2A (Agent-to-Agent) JSON-RPC 2.0, а також REST-обгортку для інспекції та використання інформаційної панелі.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # необов’язково, якщо не встановлено OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Підтримувані методи (усі доступні лише за умови `settings.a2aEnabled`):

| Method           | Description                                                         |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Синхронне виконання навички; повертає `{task, artifacts, metadata}` |
| `message/stream` | Потокове виконання тієї самої навички через SSE                     |
| `tasks/get`      | Отримання завдання за `taskId`                                      |
| `tasks/cancel`   | Скасування завдання за `taskId`                                     |

Вбудовані навички: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Картка агента

```bash
GET /.well-known/agent.json
```

Повертає загальнодоступну картку агента A2A (назву, опис, можливості, каталог навичок, схему автентифікації), яка кешується публічно на 1 годину. Автентифікація не потрібна.

### Допоміжні REST-методи

| Method | Path                         | Description                                                                                                         |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | Стан A2A (увімкнено чи ні) + статистика завдань + зведення кешованої картки агента                                  |
| GET    | `/api/a2a/tasks`             | Список завдань — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Не реалізовано як REST-метод — створюйте через JSON-RPC `message/send`)                                            |
| GET    | `/api/a2a/tasks/[id]`        | Отримання одного завдання                                                                                           |
| POST   | `/api/a2a/tasks/[id]/cancel` | Скасування завдання                                                                                                 |

**Автентифікація:** допоміжні REST-методи працюють без автентифікації керування (доступні для перегляду в інформаційній панелі); маршрут JSON-RPC `/a2a` використовує Bearer `OMNIROUTE_API_KEY`, якщо його налаштовано.

## Плагіни

Керуйте плагінами OmniRoute (сторонніми розширеннями).

| Метод  | Шлях                               | Опис                                |
| ------ | ---------------------------------- | ----------------------------------- |
| GET    | `/api/plugins`                     | Перелік встановлених плагінів       |
| POST   | `/api/plugins/marketplace/install` | Встановлення плагіна з маркетплейсу |
| DELETE | `/api/plugins/[name]`              | Видалення плагіна                   |
| POST   | `/api/plugins/[name]/activate`     | Активація плагіна                   |
| POST   | `/api/plugins/[name]/deactivate`   | Деактивація плагіна                 |
| GET    | `/api/plugins/[name]/config`       | Отримання конфігурації плагіна      |
| PUT    | `/api/plugins/[name]/config`       | Оновлення конфігурації плагіна      |

**Автентифікація:** потрібен сеанс керування.

Докладні відомості див. у розділі [Фреймворк плагінів](../frameworks/PLUGIN_SDK.md).

## Тіньова маршрутизація

Тіньове порівняння постачальників / A-B **не є окремим REST-інтерфейсом** — воно налаштовується через маршрутизацію комбо (див. [Auto-Combo](../routing/AUTO-COMBO.md)). Метрики порівняння для кожного комбо надаються через `GET /api/combos/metrics`.

## Засоби захисту

Перевіряйте засоби захисту середовища виконання (виявлення PII, виявлення ін’єкцій у підказки, об’єднання даних для роботи із зображеннями). Засоби захисту виконуються для кожного запиту; вимкнення для окремого виклику здійснюється через заголовок запиту `x-omniroute-disabled-guardrails` — збереженого інтерфейсу для ввімкнення/вимкнення не існує.

| Метод | Шлях                   | Опис                                                                                                     |
| ----- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| GET   | `/api/guardrails`      | Перелік зареєстрованих засобів захисту та їхнього стану (назва / увімкнено / пріоритет)                  |
| POST  | `/api/guardrails/test` | Тестовий запуск конвеєра перед викликом на прикладі вхідних даних — тіло: `{input, disabledGuardrails?}` |

**Автентифікація:** потрібен сеанс керування.

Докладні відомості див. у розділі [Безпека > Засоби захисту](../security/GUARDRAILS.md).

## Автентифікація

Див. [Автентифікація керування](../guides/MANAGEMENT-AUTH.md), щоб дізнатися про чотири
сімейства облікових даних (сеанс панелі керування, локальний токен CLI, токен доступу
`oma_live_…`, ключ API з областю дії керування) і про те, чим вони відрізняються від
ключів для інференсу.

- Маршрути панелі керування (`/dashboard/*`) використовують cookie `auth_token`
- Вхід використовує збережений хеш пароля; резервний варіант — `INITIAL_PASSWORD`
- Перемикач `requireLogin` можна змінювати через `/api/settings/require-login`
- Маршрути `/v1/*` можуть вимагати ключ API Bearer, якщо `REQUIRE_API_KEY=true`
- «токен керування» / «ключ API з областю дії керування» у цьому довіднику означає один із сімейств, описаних у тому посібнику, — це не невизначений додатковий тип секрету

> **Несумісна зміна (v3.8.0)** — `/api/v1/agents/tasks/*` і кінцеві точки керування періодом очікування тепер вимагають **автентифікацію керування** (cookie `auth_token` панелі керування або ключ API з областю дії керування). Клієнти, які раніше викликали ці маршрути без автентифікації, отримуватимуть `401 Unauthorized`. Див. коміт `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
