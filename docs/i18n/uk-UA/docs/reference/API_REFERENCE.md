## Завершення чату

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Власні заголовки

| Заголовок                | Напрямок  | Опис                                                                                                                                                                                                                                  |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Запит     | Установіть значення `true`, щоб обійти кеш                                                                                                                                                                                            |
| `x-omniroute-no-memory`  | Запит     | Установіть значення `true`, щоб пропустити додавання пам’яті та навичок для цього запиту (аналогічно до вимкнення кешу; дає змогу уникнути накладних витрат токенів і коштів для кожного виклику)                                     |
| `X-OmniRoute-Progress`   | Запит     | Установіть значення `true`, щоб отримувати події перебігу виконання                                                                                                                                                                   |
| `X-Session-Id`           | Запит     | Ключ закріпленої сесії для зовнішньої спорідненості сесій                                                                                                                                                                             |
| `x_session_id`           | Запит     | Також приймається варіант із підкресленнями (безпосередній HTTP)                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | Запит     | Надана викликачем позначка сесії/розмови (також передається до пам’яті). Якщо вона присутня, дослівно зберігається в `call_logs.session_tag` для віднесення витрат до окремих сесій (#8249) — ніколи не генерується за її відсутності |
| `Idempotency-Key`        | Запит     | Ключ дедуплікації (вікно 5 с)                                                                                                                                                                                                         |
| `X-Request-Id`           | Запит     | Альтернативний ключ дедуплікації                                                                                                                                                                                                      |
| `x-omniroute-connection` | Запит     | Закріплює запит до однієї моделі за одним підключенням провайдера (обліковим записом) за його ідентифікатором — див. [Закріплення облікового запису для окремого запиту](#account-pinning-per-request)                                |
| `X-OmniRoute-Cache`      | Відповідь | `HIT` або `MISS` (без потокового передавання)                                                                                                                                                                                         |
| `X-OmniRoute-Idempotent` | Відповідь | `true`, якщо виконано дедуплікацію                                                                                                                                                                                                    |
| `X-OmniRoute-Progress`   | Відповідь | `enabled`, якщо ввімкнено відстеження перебігу виконання                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | Відповідь | Фактичний ідентифікатор сесії, використаний OmniRoute                                                                                                                                                                                 |
| `X-OmniRoute-Request-Id` | Відповідь | Ідентифікатор кореляції запиту (якщо відомий)                                                                                                                                                                                         |
| `X-OmniRoute-Version`    | Відповідь | Версія збірки OmniRoute (завжди присутня)                                                                                                                                                                                             |
| `X-OmniRoute-Cost-Saved` | Відповідь | Сума в USD, заощаджена завдяки кешу в разі `HIT` (лише для влучань у кеш)                                                                                                                                                             |
| `X-OmniRoute-Decision`   | Відповідь | Трасування маршрутизації: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` — стратегія комбінації або `single` для запиту без комбінації) — завжди присутнє у відповідях про завершення                                  |

> Примітка щодо Nginx: якщо ви використовуєте заголовки з підкресленнями (наприклад, `x_session_id`), увімкніть `underscores_in_headers on;`.

#### Закріплення облікового запису для кожного запиту

Коли постачальник має кілька підключень (облікових записів або ключів), OmniRoute зазвичай вибирає одне
відповідно до своєї стратегії вибору облікового запису. Натомість запит може закріпити конкретне підключення
за допомогою заголовка `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Де знайти ідентифікатор.** Відкрийте сторінку постачальника на панелі керування
  (**Панель керування → Постачальники → <provider>**) і натисніть плашку ідентифікатора `xxxxxxxx…` у рядку
  підключення — повний ідентифікатор підключення буде скопійовано.
- **Які запити його враховують.** Запити з однією моделлю (`provider/model`) до
  `/v1/chat/completions`, `/v1/messages` і `/v1/responses`. Комбінації ігнорують цей заголовок: закріплюйте
  обліковий запис для кожного кроку комбінації через власне підключення цього кроку.
- **Закріплення є суворим, а не бажаним.** Закріплене підключення використовується виключно. Збій
  під час запиту реєструє період очікування облікового запису, але **не** перемикає на
  інший обліковий запис того самого постачальника.
- **Період очікування та квота скасовують закріплення.** Поки закріплене підключення перебуває в періоді очікування,
  вичерпало квоту або заблоковане політикою квот, наступні запити перемикаються на інші
  підключення постачальника так само, як і незакріплений трафік.
- **Невідомі або вимкнені ідентифікатори спричиняють помилку.** Ідентифікатор, якого немає в активному пулі постачальника (видалений,
  деактивований або належить іншому постачальнику), не залишає жодного придатного облікового запису, тому запит
  завершується помилкою замість непомітного переспрямування в інше місце.

Claude Code надсилає користувацькі заголовки через `ANTHROPIC_CUSTOM_HEADERS`. Додайте його до блоку `env`
у `~/.claude/settings.json` або до файлу `.claude/settings.json` на рівні проєкту, щоб закріпити інший
обліковий запис для кожного проєкту:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Джерело: `src/sse/handlers/chat.ts` (зчитування заголовка), `src/sse/services/auth.ts` і
`src/sse/services/sessionAffinityPin.ts` (скасування закріплення та перевірка відсутності в пулі).

> **Заголовки телеметрії вартості:** успішні відповіді без потокового передавання також містять набір телеметрії вартості `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фіксовані 10 десяткових знаків; `0.0000000000` для безкоштовних послуг або послуг без визначеної ціни), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` і `X-OmniRoute-Fallback-Attempts` (лише коли > 0), а також `X-OmniRoute-Request-Id` і `X-OmniRoute-Version`. Їх повертають завершення чатів, `/v1/responses`, `/v1/messages`, **а також кінцеві точки для медіа** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` і `/v1/moderations` (вартість завжди становить `0`). Вартість медіа обчислюється за кожною модальністю (за зображення, секунду, символ або одиницю пошуку), коли дані про ціни доступні; інакше вона становить `0` (у разі помилки обробка продовжується).

> **Семантика вартості в разі влучання в кеш:** у разі ВЛУЧАННЯ в семантичний кеш (`X-OmniRoute-Cache-Hit: true`) звернення до зовнішнього сервісу не виконується, тому значення `X-OmniRoute-Response-Cost` дорівнює `0.0000000000` (**додатковій** вартості обслуговування влучання). Початкова або потенційна вартість повідомляється окремо в `X-OmniRoute-Cost-Saved`. Споживачам білінгових даних слід підсумовувати `X-OmniRoute-Response-Cost` (влучання нічого не коштують); для аналітики кешу можна агрегувати `X-OmniRoute-Cost-Saved`.

## Ексклюзивні оренди керованих сеансів

Ексклюзивна оренда керованих сеансів — це необов’язковий, незалежний від клієнта контракт маршрутизації: один активний власник
утримує одне придатне підключення OmniRoute. Він не надає модель в оренду, не вимагає OAuth, не ідентифікує
конкретного клієнта й не вимагає конкретного провайдера.

API-ключ, що використовується для автентифікації, повинен мати область дії `lease:exclusive` і явний непорожній
список `allowedConnections`. Межа мутації бази даних забезпечує спільне дотримання вимог до обох полів під час
створення ключа та часткових оновлень.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успішні відповіді на отримання, поновлення та звільнення містять часові позначки, `state` і точне додатне
значення `generation`, але ніколи не розкривають вибране підключення або облікові дані. Для поновлення та звільнення
покоління передається в тілі JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Активний власник оренди може явно запросити безпечні з погляду конфіденційності метадані відображення для свого поточного прив’язування:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ця необов’язкова дія перевірки стану захищена непрозорим ідентифікатором власника, автентифікованим керованим API-ключем і точним
активним поколінням у межах однієї транзакції бази даних. `displayName` містить лише налаштовану назву
підключення без початкових і кінцевих пробілів; якщо безпечної налаштованої назви немає, значенням є `null`. OmniRoute ніколи не підставляє
адресу електронної пошти або згенеровану ідентичність облікового запису. Значення провайдера є неконфіденційною міткою для відображення й ніколи
не є згенерованим ідентифікатором сумісного провайдера. Облікові дані, токени, файли cookie, необроблені ідентифікатори підключень або
API-ключів, хеші власників, секрети відсікання та внутрішні дані маршрутизації не включаються.

Пошуки з неправильним ключем, неправильним власником, застарілим поколінням, а також відсутні, прострочені, звільнені та анульовані оренди
повертають ту саму помилку `409 LEASE_FENCE_STALE` без метаданих підключення. Клієнт, який отримав відповідь про очікування доступної місткості, не має активного прив’язування для перевірки. Коли маршрутизація змінює активну оренду,
те саме покоління залишається чинним, а перевірка стану атомарно повертає нове прив’язування, але ніколи не старе.
Наявні клієнти залишаються без змін, оскільки відповіді на отримання, поновлення, звільнення та очікування зберігають
свої попередні формати.

Цей серверний контракт не змінює стандартний `/status` OpenAI Codex. Наразі стандартний Codex повідомляє про свого
провайдера моделі та вбудований стан автентифікації/облікового запису, але не відображає довільні метадані облікових записів
користувацьких провайдерів; майбутня клієнтська інтеграція має викликати цю дію та вирішувати, як
відображати `connection.displayName`.

Після цього кожен керований запит інференсу передає обидва керівні заголовки:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точний власник, покоління, активне підключення та автентифікований API-ключ перевіряються безпосередньо
перед кожною підтримуваною спробою звернення до висхідного сервісу. Повторне використання власника й покоління з іншим ключем завершується невдало, навіть
якщо цей ключ дозволяє те саме підключення. Необроблені ідентифікатори власників не зберігаються, не записуються до журналів, не утримуються у
знімку запиту й не пересилаються висхідному сервісу.

Тимчасова конкуренція за ресурси повертає HTTP `429` із `Retry-After` і:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Ця відповідь означає лише те, що звичайний набір придатних підключень був непорожнім, а кожен вільний кандидат
утримувався чужою активною орендою. Непідтримувані моделі/провайдери, невідповідність політиці, період очікування, квота,
стан працездатності та інші звичайні помилки придатності зберігають свої наявні відповіді OmniRoute.

### `x-omniroute-compression`

Перевизначення плану стиснення для окремого запиту. Має найвищий пріоритет — перевершує перевизначення комбінації маршрутизації,
активний профіль, автоматичний тригер і значення Default панелі. Значення:

| Значення      | Ефект                                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `off`         | Без стиснення для цього запиту.                                                                                  |
| `default`     | Профіль Default, визначений панеллю (активний профіль ігнорується). Рушії з втратами залишаються вимкненими.     |
| `safe`        | Лише дедуплікація та згортання пробільних символів.                                                              |
| `allow-lossy` | Зберігає операторський план для цього запиту, включно з узагальненнями та переписуванням стилю.                  |
| `engine:<id>` | Один рушій, якщо його ввімкнено, наприклад `engine:rtk`. Увімкнення цього рушія на рівні окремого запиту.        |
| `<combo>`     | Іменована комбінація, що спочатку зіставляється за назвою (без урахування регістру), а потім за ідентифікатором. |

Примітки:

- Невідомі значення ігноруються (запит ніколи не відхиляється); визначення переходить до звичайного порядку пріоритетів оператора.
- Якщо кілька комбінацій мають однакову назву, передайте **id** комбінації для детермінованого зіставлення.
- Комбінацію з назвою `off` або `default` не можна вибрати за назвою (спочатку інтерпретуються ці ключові слова); посилайтеся на таку комбінацію за її ідентифікатором.
- Головний перемикач стиснення є жорстким обмеженням: коли стиснення глобально вимкнене, цей заголовок не може його ввімкнути.

Застосований план повертається в заголовку відповіді:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

де `<source>` є одним із `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` або `off`.

## Ембединги

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Доступні постачальники: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Ідентифікатори каталогу мають формат `provider/model` (приклад: `jina-ai/jina-embeddings-v5-omni-small`). Ідентифікатори моделей Jina без префікса, наявні в реєстрі (наприклад, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), також розпізнаються. Операції Jina embed/rerank/classify/segment спочатку використовують облікові дані `jina-ai` з панелі керування; `JINA_AI_API_KEY` застосовується як резервний варіант, лише якщо в панелі керування немає ключа. Картка `jina-reader` призначена лише для Reader / `r.jina.ai` (`POST /v1/web/fetch`) і ніколи не обслуговує запити ембедингу чи rerank.

Моделі реєстру, для яких заявлено підтримку мультимодальності, також приймають до 32 структурованих
елементів у форматі, незалежному від постачальника. Типи медіаелементів: `text`, `image`, `audio`, `video` і `document`. Їхнє медіаджерело `source`
має вигляд `{"type":"url","url":"https://..."}` або
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
і псевдонім сімейства `jina-ai/jina-embeddings-v5-omni` → omni-small) також приймає нативні для Jina
документи EmbeddingsV5Request і **пересилає їх без змін** до `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Нативні значення `{ image | audio | video | pdf }` можуть бути загальнодоступною URL-адресою HTTPS, URI `data:` або необробленими
даними base64. OmniRoute не перетворює ці об’єкти на рядки та не завантажує нативні URL-адреси зображень — Jina самостійно отримує
загальнодоступні медіадані. Додаткові поля Jina (`task`, `normalized`, `truncate`, `embedding_type`)
пересилаються. Текстові SKU Jina, як і раніше, відхиляють нетекстові документи.

Обмеження безпеки та передавання:

- Віддалені URL-адреси медіаданих мають бути загальнодоступними й використовувати HTTPS. Канонічні елементи `{type,source:url}` завантажуються
  на сервері (із повторною перевіркою перенаправлень, тайм-аутом, обмеженнями розміру, загальнодоступною DNS і фіксацією з’єднання) та
  вбудовуються перед викликом постачальника. Нативні для Jina елементи `{image:"https://..."}` пересилаються без змін
  після такої самої перевірки загальнодоступності HTTPS; URL-адресу завантажує Jina.
- Вбудовані медіадані base64 обмежено 8 МіБ декодованих даних на елемент і 16 МіБ декодованих даних на весь запит.

Перетворення для постачальників (канонічні елементи ніколи не пересилаються без змін):

- Мультимодальні моделі Jina: кожен елемент верхнього рівня стає одним об’єктом із ключем модальності
  (`text` / `image` / `audio` / `video` / `pdf`), що використовує URI даних для вбудованих медіаданих; один вектор на
  кожен елемент верхнього рівня.
- Сімейство Gemini Embedding 2: один масив верхнього рівня стає єдиним нативним запитом
  `models/{model}:embedContent` із `content.parts` (`text` або `inline_data`).
- llama.cpp (`llama-cpp/<model>`, будь-яка модель, завантажена локальним сервером): канонічні елементи `text`
  стають звичайними рядками, а `image` / `audio` / `video` — окремими об’єктами
  `{"content": [part]}` кожен, із використанням частин вмісту чату llama-server (`image_url`,
  `input_audio` з форматом `wav` / `mp3` / `flac`, `input_video`) і вбудованими даними; один вектор
  на кожен елемент верхнього рівня. Сервер має бути запущений із `--embedding --mmproj …`; без проєктора він
  самостійно відхиляє медіадані. `document` не підтримується.
- Невідомі/динамічні моделі без явних метаданих модальності відхиляють структуровані вхідні дані з HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Непідтримувані комбінації моделі й модальності повертають HTTP 400 замість примусового перетворення елемента. Додаткові поля,
не пов’язані з вхідними даними, у застарілих запитах із рядками/токенами й надалі передаються без змін.

```bash
# Перелічити всі моделі ембедингів
GET /v1/embeddings
```

## Генерування зображень

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Доступні провайдери включають OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локально), ComfyUI (локально).

`n` повертає `n` зображень у `data[]`. Для провайдерів, API яких повертає одне зображення за виклик
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), виконується `n` окремих викликів до зовнішнього API, але не більше 4 одночасно. Фіксоване
значення `seed` зміщується на індекс виклику (`seed`, `seed + 1`, …), тому зображення відрізняються, але залишаються
відтворюваними. Значення `n` обмежене до 10. Якщо будь-який виклик завершується помилкою, весь запит
вважається невдалим. Перелік форматів із розподілом на окремі виклики міститься в `SINGLE_IMAGE_FANOUT_FORMATS` у
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux повторно використовує наявне підключення з API-ключем і приймає префікси `zenmux/` або `zm/`:

- `zenmux/openai/gpt-image-2` використовує OpenAI Images API від ZenMux. Серед параметрів: `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` і `response_format`.
- Інші видавці, як-от `zm/meta/muse-image-1.0`, використовують кінцеву точку Vertex AI `:predict`
  від ZenMux. `n` зіставляється із `sampleCount`, `aspect_ratio` — з `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — із `sampleImageSize`. Значення `size` у пікселях визначає лише співвідношення сторін,
  а не гарантовані розміри в пікселях. Підтримувані співвідношення сторін, роздільні здатності та кількості залежать від моделі.
- `zm/inclusionai/ming-image-0.1-design` самостійно вибирає розміри. Не вказуйте `size`,
  `aspect_ratio` та `image_size`; явне зазначення цих значень призводить до повернення HTTP 400. Формати PNG, JPEG і WebP
  можна запитувати за допомогою `output_format`.

Ця інтеграція підтримує генерування зображень із тексту, але не редагування на основі референсного зображення. Вихідні дані Vertex
нормалізуються до `data[].b64_json`; `response_format: "url"` повертає HTTPS URL від зовнішнього сервісу
або URL даних base64, якщо доступні лише байти зображення. Порожні або відфільтровані вихідні дані
призводять до помилки, а не до порожньої успішної відповіді. Доступ до моделей залежить від облікового запису ZenMux.
Див. [Vertex API від ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) та
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Перелічити всі моделі зображень
GET /v1/images/generations
```

## OCR документів

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` вибирає провайдера OCR за допомогою префікса `provider/model`; ідентифікатор моделі без префікса (наприклад,
`mistral-ocr-latest`) зіставляється із зареєстрованим для нього провайдером, а якщо `model` не вказано, за замовчуванням
використовується Mistral (`mistral-ocr-latest`). Зареєстровані провайдери (`open-sse/config/ocrRegistry.ts`):

| Ідентифікатор провайдера      | Ідентифікатор моделі | Значення `model`                                                     | Примітки                                                                                                                                |
| ----------------------------- | -------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (або `mistral-ocr-latest` без префікса) | Синхронний — відповідь повертається безпосередньо з єдиного виклику до зовнішнього API.                                                 |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                          | Асинхронний зовнішній API (`analyze` + опитування) — див. нижче.                                                                        |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                              | Синхронний, через партнерську кінцеву точку Vertex AI `openapi/chat/completions` — інформацію про автентифікацію та URL наведено нижче. |

Усі три провайдери повертають відповідь в однаковому форматі Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процес опитування Azure Document Intelligence

API `analyze` від Azure Document Intelligence є асинхронним: початковий запит повертає заголовок
`Operation-Location` замість тіла відповіді, а результат потрібно отримувати шляхом опитування. Обробник
(`open-sse/handlers/ocr.ts`) опитує цей URL щосекунди, виконуючи до 30 спроб, негайно завершується помилкою (не
продовжує опитування), якщо відповідь на запит опитування має статус, відмінний від `ok`, або статус `"failed"`, і повертає `504`, якщо
операція все ще виконується після вичерпання дозволеної кількості спроб. Остаточна відповідь Azure
нормалізується до тієї самої структури `pages`/`markdown`, яку використовує Mistral, перш ніж повертається
клієнту, тому клієнтському коду не потрібно окремо обробляти цього провайдера.

### Автентифікація та визначення кінцевої точки Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` повторно використовує ту саму автентифікацію Vertex AI, яку OmniRoute уже підтримує для
трафіку чатів і зображень (`open-sse/executors/vertex.ts`): API-ключ підключення є або
обліковими даними Service Account у форматі JSON (які обмінюються на короткостроковий токен доступу OAuth за допомогою
процесу JWT-bearer), або вже випущеним токеном доступу OAuth, який використовується без змін. URL зовнішньої кінцевої точки — це
загальна партнерська кінцева точка Vertex `openapi/chat/completions`, сформована на основі проєкту та
регіону підключення: явно задані `providerSpecificData.project`/`providerSpecificData.region` завжди мають пріоритет;
інакше проєкт визначається з `project_id` у JSON Service Account, а регіоном
за замовчуванням є `us-central1`. Обидва значення визначаються в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) і використовуються в
`src/app/api/v1/ocr/route.ts` перед передаванням до `handleOcr`.

## Список моделей

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Повертає всі моделі чату, вбудовувань і зображень, а також комбінації у форматі OpenAI
```

### Ціни моделей (`pricing`)

Запис містить об’єкт `pricing`, коли OmniRoute знає ціну моделі. Ціна береться
з таблиці цін, яку використовує облік витрат: вбудованих значень за замовчуванням, синхронізованих цін і
перевизначень, установлених через `/api/pricing`. Це прейскурантні ціни, тому постачальники з підпискою також
показують ціну за токен.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Поля                                                            | Одиниця вимірювання            | Примітки                                                                                                                                      |
| --------------------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD за токен, десятковий рядок | Сумісні з OpenRouter, ніколи не записуються в експоненціальній нотації. Два поля кешу з’являються лише за наявності ціни кешу.                |
| `input`, `output`, `cached`, `cache_creation`                   | USD за 1 млн токенів, число    | Поля з попередніх версій каталогу, збережені для наявних клієнтів. `reasoning` і `long_context` також з’являються, коли рядок цін їх містить. |

- **Комбінації** отримують ціну своєї першої видимої цільової моделі. Вбудовані комбінації `auto/*` вибирають
  цільову модель під час запиту, тому не мають `pricing`.
- **Безкоштовні моделі** показують `"0"` (і `0`), коли їхня ціна дорівнює нулю. Модель без рядка цін
  також показує `"0"`, коли каталог позначає її як безкоштовну (`free: true`) або вона міститься у вбудованому
  каталозі безкоштовних моделей.
- **Невідома ціна:** запис не має ключа `pricing`.
- **Постачальники з тарифікацією за кредитами** (наприклад, Kiro) виставляють рахунок за запит, а не за токен. Їхні
  записи зберігають числові поля вартості за 1 млн токенів, які вони мали раніше, і не містять рядкових полів ціни за токен.
- **Варіанти** (ідентифікатори рівня інтенсивності міркування, псевдоніми без міркування, дзеркала виявлення та шлюзу)
  копіюють ціну моделі, до якої вони спрямовують запити.
- Поля містять лише базові тарифи. Рівні для довгого контексту (числове поле `long_context`) і
  множники рівня обслуговування (наприклад, Codex fast або flex) не змінюють `prompt` чи
  `completion`.
- Об’єкт однаковий для всіх способів автентифікації, зокрема для запиту в стилі Anthropic
  з `x-api-key` і `anthropic-version` (відповідь залишається `{ "object": "list",
"data": [...] }`). Реалізація: `src/app/api/v1/models/catalogPricing.ts`.

### Префікси ідентифікаторів моделей (`?prefix=`)

Більшість моделей публікуються з **префіксом постачальника**. Префікс, який ви отримуєте, контролюється
прапорцем функції `MODELS_CATALOG_PREFIX_MODE` і може бути перевизначений **для кожного запиту** за допомогою
параметра запиту — це корисно для клієнта, якому потрібен чистий список без зміни загальносерверного
налаштування для всіх інших:

```bash
GET /v1/models?prefix=alias        # один ідентифікатор на модель — короткий префікс-псевдонім
GET /v1/models?prefix=dual         # обидві форми (налаштування сервера за замовчуванням)
GET /v1/models?prefix=canonical    # лише повний префікс ідентифікатора постачальника
```

| Режим       | Виводить                                                | Примітки                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **і** `claude/claude-sonnet-4-6` | **За замовчуванням.** Обидва ідентифікатори спрямовують до тієї самої моделі; збережено, щоб конфігурації клієнтів із жорстко заданою будь-якою з форм продовжували працювати. Приблизно подвоює каталог.                    |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Один запис на модель. Постачальники без окремого псевдоніма все одно виводять свій запис, тому нічого не втрачається.                                                                                                        |
| `canonical` | `claude/claude-sonnet-4-6`                              | Один запис на модель із повним префіксом ідентифікатора постачальника. Постачальники без окремого псевдоніма (наприклад, `antigravity/…`, `agy/…`) також виводять тут свій єдиний ідентифікатор, тому нічого не втрачається. |

Дзеркало в режимі `dual` також можна розпізнати без параметра запиту: воно містить поле `parent`,
що вказує на основний ідентифікатор.

Клієнти, які відображають засіб вибору моделі, мають надсилати запит із `?prefix=alias` — саме так робить
[розширення OmniCopilot для VS Code](../guides/VSCODE-COPILOT.md).

### Фільтри виявлення (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` приймає необов’язкові фільтри виявлення. Без жодного з них відповідь
не змінюється. Вони звужують каталог, який уже бачить викликач (спочатку застосовуються дозволи API-ключа),
і виконуються до пагінації в стилі OpenAI за допомогою `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # кожна зазначена можливість має мати значення true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` каталогу; рядки без нього мають тип `chat`
GET /v1/models?q=sonnet&limit=10                           # зіставлення ідентифікатора або назви без урахування регістру
```

| Параметр      | Значення                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | невід’ємне ціле число, порівнюється з `context_length`                                              |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 символів                                                                                      |

Невідоме значення або значення `min_context`, яке не є невід’ємним цілим числом (наприклад, `1.5`),
повертає HTTP `400`, а повідомлення містить перелік допустимих значень. Реалізація:
`src/app/api/v1/models/catalogFilters.ts`.

### Короткий список моделей (`POST /v1/models/query`)

`POST /v1/models/query` повертає короткий детермінований список із того самого каталогу, з такою самою
автентифікацією та видимістю для кожного ключа, що й `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Кожне поле є необов’язковим. `capabilities` і `exclude` приймають масив або рядок зі значеннями, розділеними комами;
`max_output` порівнюється з `max_output_tokens`. Результати сортуються спочатку за `owned_by`, а потім за `id`.
Значення `limit` за замовчуванням дорівнює `20`, а значення понад `100` обмежуються до `100`. Некоректний JSON, невідоме
поле або некоректне значення повертає HTTP `400`.

### Окремо приховані моделі чату

Модель, позначена як **Прихована** на сторінці її провайдера, виключається з каталогу, а явний запит до неї
відхиляється з HTTP `404` / `model_not_found`. Перевірка використовує визначені
провайдера та модель, зокрема псевдоніми провайдерів, префікси вузлів сумісного провайдера та
значення з’єднання за замовчуванням. Комбінація пропускає приховані цільові моделі й може використовувати видиму споріднену модель; якщо не
залишається жодної доступної для виконання цільової моделі, повертається той самий код помилки. Скасування приховування набуває чинності під час наступного
запиту. Перевизначення видимості лише для зображень не приховують модель чату з тим самим ідентифікатором.

Це налаштування окремої моделі не пов’язане зі
[списками дозволу/заборони публікації моделей](../routing/MODEL_EXPOSURE_LIST.md), які фільтрують
відображення в каталозі та кандидатів для автоматичної маршрутизації, зберігаючи явну маршрутизацію. Дозволи моделей
для API-ключів і надалі застосовуються незалежно. Режим префіксів каталогу за замовчуванням залишається `dual`.

### Варіанти моделей без міркування

Для моделей Claude із підтримкою міркування `/v1/models` також публікує варіант **без міркування**, ідентифікатор якого має префікс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Вибір цього ідентифікатора (наприклад, у конфігурації Claude Code, яка завжди додає блок `thinking`) знову зіставляється з реальною моделлю `<provider>/<model>` із вимкненим міркуванням — `thinking:{type:"disabled"}` для шляху `/v1/messages` або з вилученими полями `reasoning`/`reasoning_effort` для шляху `/v1/chat/completions`. Варіант відображається лише для моделей сімейства Claude, які підтримують міркування **та** враховують `disabled` (тому, наприклад, моделі лише з адаптивним режимом, які відхиляють `disabled`, виключаються). Оператори можуть примусово ввімкнути або вимкнути цей варіант для кожної моделі через `ModelSpec.noThinkingAlias`.

## Генерування аудіо ElevenLabs

Налаштуйте підключення провайдера `elevenlabs` в OmniRoute за допомогою вашого API-ключа ElevenLabs.
Клієнти автентифікуються за допомогою свого ключа **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюз передає збережений ключ провайдера як `xi-api-key`. Ніколи не надсилайте ключ ElevenLabs
як bearer-токен шлюзу.

| Метод | Шлях                        | Відповідь                                  | Категорія кінцевої точки API-ключа |
| ----- | --------------------------- | ------------------------------------------ | ---------------------------------- |
| POST  | `/v1/sound-generation`      | Нативні байти аудіо                        | `elevenlabs`                       |
| POST  | `/v1/music`                 | Нативні байти аудіо                        | `music`                            |
| POST  | `/v1/music/stream`          | Потокові байти аудіо                       | `music`                            |
| POST  | `/v1/music/detailed`        | Нативне multipart-аудіо та план композиції | `music`                            |
| POST  | `/v1/music/detailed/stream` | Нативні метадані SSE та аудіофрагменти     | `music`                            |
| POST  | `/v1/music/plan`            | План композиції у форматі JSON             | `music`                            |

Ці кінцеві точки доповнюють наявні маршрути `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` і `/v1/speech-to-text`. Нативні поля JSON
і параметри запиту, як-от `output_format` та `enable_logging`, зберігаються.
Відповіді `/v1/music/detailed` зберігають свої межі multipart; обробляйте їх як multipart.
`/v1/music/detailed/stream` повертає `text/event-stream` з метаданими композиції та
аудіофрагментами base64 у подіях SSE. Усі шість маршрутів підтримують попередні запити CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Короткий звуковий ефект. Тривалість: від 0,5 до 30 секунд.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Тривалість музики задається в мілісекундах: від 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Використовуйте `/v1/music/stream` з тим самим тілом JSON для поступового передавання аудіо. Для композиції
приймається лише одне з полів: `prompt` або `composition_plan`; `/v1/music/plan` вимагає `prompt`
і необов’язково приймає `source_composition_plan`. Нативні схеми зберігають додаткові
поля провайдера, щоб версії планів композиції та параметри тонкого налаштування передавалися до ElevenLabs.

Уніфікована кінцева точка `/v1/music/generations` також приймає `elevenlabs/music_v1`,
`elevenlabs/music_v2` і `elevenlabs/music_v2_5`. За наявності активного підключення ElevenLabs
ці моделі відображаються в каталозі музики. Ця кінцева точка повертає
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Її поле `duration` задається в
секундах і зіставляється з `music_length_ms`; явно вказане `music_length_ms` має пріоритет.
`instrumental` зіставляється з `force_instrumental`, причому нативне поле має пріоритет.
Використовуйте нативні потокові кінцеві точки для потокового передавання, а нативну кінцеву точку композиції —
для запитів, що ґрунтуються лише на плані композиції.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Обмеження кінцевої точки, моделі, бюджету та підключення застосовуються до виклику зовнішнього сервісу. Нативні
маршрути повертають коди стану й тіла помилок зовнішнього сервісу без змін, зокрема `402` для обмеження
тарифного плану та `429` для перевищення квоти. Заголовки `character-cost`, `song-id`, `request-id` і `retry-after`
зберігаються, якщо вони наявні. Безкоштовний кредитний баланс не гарантує доступу до кожної
музичної моделі, формату виводу або функції API: ElevenLabs визначає право доступу для кожного запиту.
Уніфікована кінцева точка зберігає коди стану помилок у нормалізованій оболонці помилок OmniRoute.

Контракти зовнішнього сервісу: [звукові ефекти](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[створення музичної композиції](https://elevenlabs.io/docs/api-reference/music/compose) та
[деталі потокового передавання музики](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

Усі маршрути POST мають однакову структуру: `Bearer your-api-key` + тіло JSON, перевірене за допомогою Zod (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` тощо; див. `src/shared/validation/schemas.ts`). У разі невдалої перевірки схеми повертається 4xx.

Для клієнтів, які не можуть додати `Authorization: Bearer ...`, OmniRoute також приймає ключі API в URL через сумісні параметри рядка запиту (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) або через спеціальні кінцеві точки `/api/v1/vscode/{token}/...`, описані нижче.

```bash
# Переранжування (постачальник із хмарного реєстру або вузол постачальника, сумісний з OpenAI, у форматі "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Класифікація Jina (облікові дані Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Сегментатор Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Пошук Jina (s.jina.ai; псевдоніми постачальника: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Модерація
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — повертає тіло audio/mpeg (або тіло в запитаному форматі)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Для Soniox TTS потрібні мова й голос: `language` за замовчуванням має значення "en"; відсутній
# голос або назва стандартного голосу OpenAI (alloy, nova, …) замінюється на "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Редагування зображення (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генерування відео / музики (ідентифікатор моделі з префіксом постачальника)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Вузли провайдерів для переранжування:** `POST /v1/rerank` також спрямовує запити до OpenAI-сумісних вузлів провайдерів
> (oMLX, vLLM, Infinity, TEI за шлюзом, …), адресованих як `<node-prefix>/<model>`. Вузли зворотного зв’язку
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) завжди доступні, як і імена хостів, які
> оператор зазначає в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (наприклад, ім’я сервісу Docker/Compose,
> як-от `http://reranker:8080/v1`; вони викликаються безпосередньо, ніколи через `HTTP(S)_PROXY` або
> закріплений проксі з’єднання). Вузли на будь-якому іншому
> хості — пристрій у LAN або вузол Tailscale — доступні лише тоді, коли оператор увімкнув
> прапорець функції `RERANK_REMOTE_PROVIDER_NODES` **і** базова URL-адреса вузла відповідає політиці
> вихідних URL-адрес провайдера (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Етап переранжування рушія пам’яті викликає цей маршрут через
> зворотний зв’язок, тому те саме правило застосовується до `rerankProviderModel` у налаштуваннях пам’яті.
>
> **Формати локальних серверів:** вузол викликається за адресою `<base>/v1/rerank`, а в разі відповіді 404 — за адресою `<base>/rerank`
> (Infinity, TEI). Тіло запиту до висхідного сервера містить як варіант написання Cohere/OpenAI (`documents`,
> `return_documents`), так і варіант TEI (`texts`, `return_text`), а відповідь висхідного сервера
> нормалізується до конверта Cohere: непакований масив TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> від мінімалістичних шлюзів і формат Voyage `{data: [...]}` повертаються клієнту як
> `{results: [{index, relevance_score, document?}]}`, відсортовані за оцінкою та обмежені значенням `top_n`.
>
> **Виявлення вузлів провайдерів:** моделі на OpenAI-сумісному вузлі провайдера відображаються в `GET /v1/models`
> під префіксом вузла. Рядки без метаданих кінцевої точки (типово для локальних списків `/v1/models`)
> успадковують `apiType` вузла, тому моделі вузла `embeddings` мають `type: "embedding"`, а моделі
> вузла `rerank` — `type: "rerank"` замість типового значення chat; явно задане
> `supportedEndpoints` у синхронізованому або доданому вручну рядку все одно має пріоритет.

### `provider_options` для Exa та Tavily

Exa та Tavily зчитують специфічні для провайдера поля з простору імен:
`provider_options.exa` (або `provider_options["exa-search"]`) і `provider_options.tavily`
(або `provider_options["tavily-search"]`). Передаються лише наведені нижче ключі. Кожен із них
перевіряється за власною схемою Zod у `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ із неправильним типом відкидається. Усі інші ключі ігноруються, зокрема автентифікація, базова URL-адреса,
`stream` і `outputSchema`. Плоскі ключі, які використовують інші провайдери (`cx`, `depth`, ...), працюють
як і раніше.

| Провайдер | Поля верхнього рівня                                                                                                                                                                                                                                                                                                                                                      | Вкладені                                                                                                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоскі примітиви), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` об’єднується зі стандартним значенням `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                               |

Загальні поля завжди мають пріоритет: `query`, `max_results`, `filters` (домени), `country` і
тема, отримана з `search_type`. Для Exa значення `search_type: "news"` зберігає `category: "news"`.
Tavily також приймає `search_type: "finance"` (`topic: "finance"`).

Загальне поле `time_range` тепер передається обом провайдерам: Exa отримує `startPublishedDate` (часова позначка
ISO), а Tavily — `start_date` (`YYYY-MM-DD`). Явно задана дата в `provider_options`
перевизначає зіставлене значення.

Результати Exa зберігають `id`, `highlight_scores`, `summary`, `subpages`, `entities` і `extras` у
`provider_raw`. Результати Tavily зберігають `images` і `favicon`.

Облік вартості, як і раніше, використовує плоский реєстр `costPerQuery`. Tavily стягує
більше кредитів за виклик для `search_depth: "advanced"`, і ця різниця не відображається в
`usage.search_cost_usd`.

## Web Fetch API

Видобуває вміст з URL-адреси через налаштованого постачальника web-fetch (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, той самий ключ API, що й для Parallel Search) повертає лише
Markdown — будь-який інший `format` призводить до відповіді `400` — і обмежує вміст 100 000 символів. Коли
цільову сторінку неможливо видобути, upstream-сервіс повідомляє про це у відповіді HTTP 200;
OmniRoute перетворює її на `422` із фіксованим повідомленням.

| Метод | Шлях            | Опис                                                                              |
| ----- | --------------- | --------------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Отримує/зішкрібає URL-адресу — тіло перевіряється за допомогою `v1WebFetchSchema` |

**Автентифікація:** Bearer-ключ API (`extractApiKey` + `isValidApiKey`). Політика застосовується через `enforceApiKeyPolicy`.

**Резервне перемикання з урахуванням квот (#8297):** коли явний `provider` не вказано, пул
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)
обходиться у фіксованому
порядку пріоритетності (спочатку заповнення) — налаштований постачальник з обмеженою частотою запитів пропускається
замість негайного завершення запиту, а повторювана помилка upstream-сервісу або помилка квоти
(HTTP 429 завжди; 402/403 для безплатних рівнів Firecrawl/Tavily/TinyFish із квотами —
але не для Jina Reader і ніколи не для звичайного некоректного запиту 400) під час запиту спричиняє перехід
до наступного ще не випробуваного постачальника з налаштованими обліковими даними. Коли всі постачальники в
пулі вичерпані, кінцева точка повертає єдиний `429` (із заголовком `Retry-After`)
замість попереднього загального `400`. Коли запитується явний `provider`,
**прихованого** резервного перемикання немає — явний постачальник з обмеженою частотою запитів або помилкою
повертає власну помилку (`429` у разі обмеження частоти запитів, інакше — статус
upstream-сервісу).

## Потокове передавання через WebSocket

```bash
GET /v1/ws?handshake=1
```

Перевіряє handshake для оновлення з’єднання до WebSocket і повертає приклади повідомлень протоколу передавання (`request`, `cancel`). Фактичні WS-фрейми обробляються вбудованим WS-сервером поза таблицею маршрутів Next.js.

**Автентифікація:** Bearer-ключ API під час handshake.

### Responses API через WebSocket (лише codex)

```bash
# Той самий хост і порт, що й для HTTP API (типово 20128); оновіть з’єднання:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (або: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Першим фреймом ОБОВ’ЯЗКОВО має бути response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Проксі Responses API через WebSocket підключено **виключно до `codex`** (бекенд ChatGPT).
Він прослуховує той самий порт, що й API/панель керування, за шляхами `/v1/responses`,
`/responses` і `/api/v1/responses`. Під час отримання першого фрейму `response.create` він
виконує автентифікацію та підготовку через внутрішній міст `codex-responses-ws`, вибирає
OAuth-з’єднання codex і створює тунель до `wss://chatgpt.com/backend-api/codex/responses`
через транспорт `wreq-js`. **Моделі, відмінні від codex, відхиляються** (`codex_ws_provider_required`).
Для маршрутизації зі спільною квотою використовуйте `model: "qtSd/<group>/codex/<model>"`. Реалізовано у
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Автентифікація:** Bearer-ключ API під час handshake. Вбудований HTTP-сервер (`server-ws.mjs`)
має бути активною точкою входу (і є нею за замовчуванням, коли існує `app/server-ws.mjs`).

#### Ідентифікатор моделі: використовуйте базовий ідентифікатор ChatGPT (без префікса `codex/`)

**Codex CLI** від OpenAI перевіряє назву моделі на боці клієнта, коли
`supports_websockets = true`, і **відхиляє ідентифікатори з префіксом постачальника**, як-от
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Надсилайте **базовий** ідентифікатор (наприклад, `gpt-5.5`). Міст OmniRoute
працює лише з codex, тому перед створенням тунелю до upstream-сервісу він повторно визначає базовий ідентифікатор
як модель codex (`resolveCodexWsModelInfo`) — навіть попри те, що базовий
`gpt-5.5` інакше маршрутизувався б до іншого постачальника через HTTP.

#### Налаштування OpenAI Codex CLI

Спрямуйте Codex CLI до OmniRoute, додавши спеціального постачальника з підтримкою
WebSocket до `~/.codex/config.toml` (використовуйте окремий `CODEX_HOME`, щоб не змінювати
наявну конфігурацію):

```toml
model = "gpt-5.5"                 # базовий ідентифікатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без кінцевої скісної риски; URL-адреса WS визначається автоматично (у робочому середовищі використовуйте https/wss)
wire_api = "responses"                    # єдине підтримуване значення з лютого 2026 року
supports_websockets = true                # вмикає транспорт Responses через WS
env_key = "OMNIROUTE_API_KEY"             # містить ключ API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ключ API OmniRoute (будь-який ключ, якщо REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI оновлює `base_url + /responses` до WebSocket, а OmniRoute створює тунель
до вибраного OAuth-з’єднання codex. Перевірено наскрізно на локальному
сервері: ChatGPT повертає `codex.rate_limits` + `response.created` і потоково передає
результат.

## Самообслуговування для перегляду використання (`/api/usage/om-usage`)

Будь-який API-ключ може переглядати **власні** дані про використання та квоти — автентифікація для керування не потрібна. Це кінцева точка, яку
клієнт (CLI, панель OmniCopilot) використовує, щоб показати власнику ключа його витрати.

```bash
# Текстовий формат (історичний контракт — звичайний текст для термінала)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Структурований формат — те, що використовує інтерфейс користувача
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Для ключа має бути ввімкнено **`allowUsageCommand`** (типово вимкнено — менеджер API-ключів
на панелі керування перемикає цей параметр окремо для кожного ключа). Без нього кінцева точка повертає `403`.

`?format=json` повертає дискриміновану структуру, щоб клієнт ніколи не зчитував поле даних із
відповіді про відмову. У разі успіху:

```jsonc
{
  "allowed": true,
  // наявне лише тоді, коли для ключа ввімкнено індивідуальні ліміти використання (денні/тижневі в USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // знімок квоти вибраного провайдера або null, якщо в кеші ще нічого немає:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // знімок кожного підключення, щоб інтерфейс міг відобразити кількох провайдерів поруч:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

У разі відмови (`401` — неправильний ключ / `403` — доступ не дозволено) цей самий маршрут повертає
`{ "allowed": false, "error": { "message": "…" } }` — наявне, але порожнє поле `personal`/`provider`
(ключ дозволено, але даних ще не отримано) є станом, відмінним від відмови, і лише JSON-формат
дає змогу їх розрізнити.

**Автентифікація:** власний Bearer API-ключ клієнта, перевірений за допомогою `isValidApiKey` — це _не_
інтерфейс керування (`/api/keys/…`), який залишається захищеним за допомогою `requireManagementAuth`.

### Необроблені та скориговані за порогом відсікання відсотки квоти

Під час використання `/api/usage/om-usage` клієнтам слід враховувати різницю між
відсотками, представленими у **простому текстовому виведенні**, і структурованим **JSON-виведенням**:

| Аспект                   | Простий текст (`/api/usage/om-usage` / `@@om-usage`)                                              | Формат JSON (`?format=json`)                                                                                   |
| :----------------------- | :------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------- |
| **Поле виведення**       | `NN% left` (наприклад, `20% left`)                                                                | `provider.quotas` / `providers[].quotas`                                                                       |
| **Вимірювання**          | **Доступний обсяг, скоригований за порогом відсікання**: залишок понад порогове значення          | **Необроблена квота провайдера**: нескориговане вимірювання провайдера                                         |
| **Масштабування порога** | Масштабується через `effectiveRemainingPercent()`, щоб захищений резерв відображався як `0% left` | Відсутнє (необроблені значення знімка, надані провайдером)                                                     |
| **Дані про поріг**       | Враховані у відображуваному відсотку                                                              | Зберігаються в `quotaWindowThresholds` для кожного підключення (або використовуються серверні типові значення) |
| **Основний споживач**    | Інтерактивні CLI, запити термінала, оператори                                                     | Програмні інтеграції, панелі керування, аналітика, засоби відстеження витрат                                   |

#### Формула коригування за порогом відсікання

OmniRoute підтримує превентивні пороги відсікання квоти, щоб запобігти вичерпанню ресурсів провайдера (налаштовуються через
`quotaWindowThresholds` підключення, типові значення провайдера або глобальні параметри стійкості). Коли для вікна квоти
активний поріг відсікання (наприклад, `cutoff = 25%`), засіб текстового рендерингу обчислює доступний залишок так:

- Якщо `remaining <= cutoff`: повертає `0%`.
- Якщо `remaining > cutoff`: повертає `((remaining - cutoff) / (100 - cutoff)) * 100`.

У форматованому текстовому виведенні результат округлюється до найближчого цілого числа (`Math.round(...)`).

#### Наочний приклад

Розглянемо вікно провайдера з **60% необробленого використання** (тобто **40% необробленого залишку квоти**) і налаштованим
порогом відсікання на рівні **25% залишку квоти**:

| Представлення                          | Обчислення                                         | Залишок |           Припустиме використання            |
| :------------------------------------- | :------------------------------------------------- | :-----: | :------------------------------------------: |
| **Необроблений JSON (`?format=json`)** | Знімок провайдера (`quotas[window]`)               | **40%** |                   **60%**                    |
| **Текстовий формат (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (якщо обчислювати `100 - remaining`) |

- **Чому текст показує 20% залишку:** із 40% фізичної квоти, що залишилася в обліковому записі, 25% зарезервовано
  політикою відсікання. Клієнту доступно лише 15% із 75% корисного запасу до моменту, коли маршрутизатор припинить
  спрямовувати запити до цього підключення. Масштабування гарантує, що підключення сигналізуватиме про вичерпання (`0% left`) саме тоді, коли
  маршрутизацію буде припинено.
- **Чому JSON зберігає необроблені значення:** корисне навантаження JSON повертає точний знімок провайдера (`UsageSnapshot`),
  щоб зовнішні інструменти мали доступ до достовірних даних про використання ресурсів провайдера та
  `quotaWindowThresholds` на рівні підключення без серверного масштабування з втратою даних.

#### Рекомендації щодо міграції клієнтів

Якщо зовнішня інтеграція (наприклад, плагін редактора або розширення агента) раніше аналізувала текстову
кінцеву точку (`NN% left`) і обчислювала використаний відсоток як `100 - NN`, перехід на `?format=json` означає:

- Читання необроблених значень JSON відображатиме **фактичне споживання на стороні постачальника** (60% використано в наведеному вище прикладі).
- Якщо інтеграція прагне зберегти семантику доступного залишку текстової кінцевої точки, вона може обчислювати
  формулу ефективного залишку на стороні клієнта, використовуючи `quotaWindowThresholds` для перевизначень на рівні з’єднання.

```bash
# Очистити всі кеші

```

Приклад відповіді:

```json
{
  "semanticCache": {

    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,

  }
```

### Вплив на затримку

У разі ВЛУЧАННЯ в семантичний кеш відповідь надається з кешу **без виклику
висхідного сервісу**, тому вказана затримка `X-OmniRoute-Response-Latency` є майже нульовою
(незалежно від початкової затримки висхідного сервісу). Клієнтам, чутливим до
затримки (бенчмаркінг, моніторинг p50/p99), слід перевіряти заголовок відповіді
`X-OmniRoute-Cache-Latency`:

| Значення     | Опис                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| `synthetic`  | Відповідь надано з кешу; затримка не є реальним часом висхідного сервісу |
| _(відсутнє)_ | Відповідь від реального виклику висхідного сервісу                       |

### Обхід кешу для окремого ключа

API-ключі можуть відмовитися від читання із семантичного кешу через `cacheDefaultMode`:

| Значення | Поведінка                                                                 |
| -------- | ------------------------------------------------------------------------- |
| `legacy` | Звичайна поведінка кешу (за замовчуванням)                                |
| `bypass` | Повністю пропустити пошук у кеші; завжди звертатися до висхідного сервісу |

Установлюється під час створення ключа (`POST /api/keys`) або оновлення (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Обхід для окремого запиту

Будь-який запит може обійти кеш незалежно від налаштувань ключа:

```
X-OmniRoute-No-Cache: true
```

Для синхронізованих/імпортованих моделей `PUT /api/provider-models` приймає `provider`, `modelId` і
`maxOutputTokenOverride`: додатне ціле число встановлює ручне обмеження вихідних токенів, а `null`

значення в `modelOutputOverrides`, включно з моделями без рядка користувацької моделі. Перевизначення
використовує можливість середовища виконання `max_output_tokens` і зберігається після повторної синхронізації моделі. Сторінка OpenAI-сумісного
постачальника пропонує ті самі елементи керування редагуванням/скасуванням і позначає моделі з явно заявленою підтримкою зору.

Користувацькі вузли Chat Completions адаптують явну відмову від міркування для upstream-бекенду. У разі
успішної перевірки підключення автоматично вибираються елементи керування шаблоном чату для кожного точного ідентифікатора моделі,
запис якої в `/models` підтверджує розпізнане значення `owned_by`: `vllm`, `sglang` або `llamacpp`.
Прозорі OpenAI-сумісні обгортки можуть зберігати початковий запис моделі у вкладеному
об’єкті `openai`; виявлення охоплює до трьох таких оболонок. Моделі з відсутніми, невідомими або
суперечливими даними про власника зберігають звичайну поведінку OpenAI. Виявлення повторно використовує наявний запит до каталогу,
не генерує токенів завершення та анулюється в разі зміни кінцевої точки підключення.

Щоб зафіксувати цю поведінку для бекенду, який не надає такі метадані, скористайтеся наявним API
часткового оновлення постачальника:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Надішліть це тіло запиту через `PUT /api/providers/<connection-id>`. Для цього підключення явне
значення інтенсивності міркування `none` надсилається як `chat_template_kwargs.thinking=false` і
`chat_template_kwargs.enable_thinking=false`. Явні нативні значення шаблону залишаються пріоритетними,
якщо серверне правило міркування не нав’язує певну інтенсивність. Налаштування застосовується лише тоді, коли користувацьке
OpenAI-сумісне підключення надсилає тіло Chat Completions; запити Responses і звичайні
постачальники зберігають свою нативну структуру запиту. Установіть для `reasoningControl` значення `openai`, щоб примусово використовувати звичайне
передавання OpenAI-параметра `reasoning_effort`, або не вказуйте його чи встановіть значення `null`, щоб використовувати автоматичне виявлення.

Запити класифікатора автоматичного режиму Claude Code за замовчуванням вимикають нативне мислення, якщо вони
не містять явних елементів керування міркуванням. Виявлення використовує системний маркер класифікатора в запитах
формату Claude, а не назви моделей чи обмеження завершення. Явні елементи керування в тілі запиту, підтримувані заголовки effort/thinking,
правила маршрутизації та визначена інтенсивність міркування моделі зберігають наявний пріоритет. Обидва етапи класифікатора
зберігають свої підказки, обмеження завершення, стоп-послідовності та фактичні рішення upstream-сервера
щодо дозволів; другий етап усе ще може виводити запитане видиме міркування як звичайний текст.

### Версія та канал випуску

```bash
GET /api/system/version
```

Маршрут керування, доступний лише через loopback (автентифікація адміністратора). Повертає запущену версію, останню
опубліковану версію та стан автоматичного оновлення. `releaseChannel` і `channels` є додатковими
полями (гілка 3.8.54); `channel` зберігає своє значення — режим розгортання, який використовує
засіб оновлення панелі керування (`npm`, `source` або `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — канал npm запущеної збірки: `nightly` для версій `-nightly.*`,
  `next` для інших попередніх випусків (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` для стабільної версії
  старішої основної гілки, ніж `channels.latest`, інакше — `latest`. Застосовуються ті самі правила, що й у
  `scripts/release/dist-tag.mjs`, який вибирає dist-tag npm під час публікації.
- `channels` — остання опублікована версія для кожного dist-tag, отримана з `npm view omniroute dist-tags` (із резервним
  зверненням до реєстру через HTTP), кешована з тим самим 10-хвилинним TTL, що й `latest`. `latest` присутній завжди
  (у разі недоступності використовується поле `latest`, а потім `"unavailable"`); `next`, `nightly` і `lts` з’являються
  лише тоді, коли відповідний dist-tag існує. Запит із `Cache-Control: no-cache` оновлює обидва результати пошуку.

Модель каналів (`latest` = v3 до загальнодоступного випуску 4.0, `next` = rc, `nightly` = збірки `develop`,
`lts` = виправлення v3 після загальнодоступного випуску 4.0) описана в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрибування аудіо

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

```bash
  -F "model=openai/whisper-1"
```

**Відповідь:**

Використовуйте ці псевдоніми, коли інтеграція не може додати заголовок `Authorization` і потребує вбудовування ключа API в базову URL-адресу.

```bash
# Псевдонім каталогу в стилі OpenAI
GET /api/v1/vscode/{token}/
```

Приклад:


## Ліміти токенів

Бюджети **токенів** для кожного API-ключа (окремо від наведеного вище бюджету на основі USD). Застосовуються безпосередньо під час обробки запиту: коли використання ключа в поточному вікні досягає ліміту, запити відхиляються з помилкою `429 Too Many Requests`. Ліміти можна обмежити певною `model`, певним `provider` або застосувати `global` до всього ключа; якщо запиту відповідають кілька лімітів, застосовується найсуворіший із них.

```bash
# Вивести ліміти токенів ключа (включно з поточним використанням у вікні)
GET /api/usage/token-limits?apiKeyId=key-123

# Створити або оновити ліміт токенів
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Видалити ліміт токенів за ідентифікатором
DELETE /api/usage/token-limits?id=tl-abc
```

> **Примітки щодо схеми** (`setTokenLimitSchema`): `apiKeyId` і `scopeType` (`model` | `provider` | `global`) є обов’язковими. `scopeValue` є обов’язковим, якщо `scopeType` не має значення `global` (наприклад, ідентифікатор моделі для області дії `model` або ідентифікатор провайдера для області дії `provider`). `tokenLimit` має бути додатним цілим числом (перетворюється з рядка). Необов’язкові поля: `id` (не вказуйте для створення, вкажіть для оновлення), `resetInterval` (`daily` | `weekly` | `monthly`, типове значення — `monthly`), `resetTime` (`HH:MM`), `enabled` (типове значення — `true`). Відповіді `GET` доповнюють кожен ліміт полями `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` і `nextResetAt`. Це кінцева точка класу керування (автентифікація застосовується централізовано конвеєром авторизації).

## Обробка запиту

1. Клієнт надсилає запит до `/v1/*`
2. Обробник маршруту викликає `handleChat`, `handleEmbedding`, `handleAudioTranscription` або `handleImageGeneration`
3. Визначається модель (безпосередня пара провайдер/модель або псевдонім/комбінація)
4. Облікові дані вибираються з локальної БД із фільтрацією за доступністю облікового запису
5. Для чату: `handleChatCore` перевіряє семантичний кеш/кеш сигнатур і визначає налаштування стиснення комбінації
6. Якщо ввімкнено, проактивне стиснення виконується до перетворення запиту для провайдера (`lite`, Caveman, RTK або їх поєднання)
7. Виконавець провайдера надсилає запит до зовнішнього сервісу
8. Відповідь перетворюється назад у формат клієнта (чат) або повертається без змін (векторні представлення/зображення/аудіо)
9. Реєструються використання, аналітика стиснення та журнали запитів
10. У разі помилок застосовується резервний варіант відповідно до правил комбінації

Повний опис архітектури: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Відмовостійкість (розширено)

OmniRoute надає три незалежні механізми обробки тимчасових збоїв; наведені нижче кінцеві точки керування дають операторам змогу переглядати та перевизначати їх:

| Область дії                 | Сховище стану                              | Перегляд                                  | Скидання / очищення                                             |
| --------------------------- | ------------------------------------------ | ----------------------------------------- | --------------------------------------------------------------- |
| Запобіжник провайдера       | `domain_circuit_breakers` + у пам’яті      | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                    |
| Період очікування з’єднання | `rateLimitedUntil` у з’єднаннях провайдера | `/api/rate-limits`, `/api/providers/[id]` | (повторно вмикається відкладено; очищення через PUT провайдера) |
| Блокування моделі           | Реєстр доступності моделей у пам’яті       | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                        |

`PATCH /api/resilience` приймає перевизначення запобіжників провайдерів у `providerBreaker.oauth` і `providerBreaker.apikey`. Кожен профіль підтримує `degradationThreshold`, `failureThreshold` і `resetTimeoutMs`; ці самі поля доступні в Панель керування → Налаштування → Відмовостійкість.

```bash
# Очистити блокування однієї моделі
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Видалити всі блокування
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Повний опис концепції та стандартні значення запобіжників: див. [`CLAUDE.md`](../../CLAUDE.md) → «Стан середовища виконання відмовостійкості» і [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Черга обмеження частоти та захисний механізм автоматичного ввімкнення

- **Підтримуваний спосіб запису**: `POST /api/rate-limits` із тілом `{"connectionId": "<id>", "enabled": true|false}` — це підтримувана кінцева точка керування для перемикання захисту від обмеження частоти для з’єднання. `PUT /api/providers/[id]` навмисно не змінює та не перемикає `rateLimitProtection` (#11278).
- **Семантика `enabled: false`**: Установлення `enabled: false` видаляє явний захист для з’єднання, але **не** виключає активне з’єднання з API-ключем із глобального захисного механізму автоматичного ввімкнення (`autoEnableApiKeyProviders = true`). У `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значення `false` і `undefined` є еквівалентними; активні з’єднання з API-ключами без явного захисту залишаються захищеними глобальним механізмом автоматичного ввімкнення.
- **Глобальне вимкнення**: Щоб використовувати з’єднання з API-ключами без черг обмеження частоти, глобально вимкніть захисний механізм через `RATE_LIMIT_AUTO_ENABLE=false` (змінна середовища) або `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Налаштування → Відмовостійкість / `PATCH /api/resilience`).

## Сервер MCP

OmniRoute постачається з вбудованим сервером Model Context Protocol із 3 транспортами (stdio, SSE, streamable-http) та інструментами з обмеженими областями доступу. Наведені нижче кінцеві точки панелі керування зчитують дані про стан/аудит і проксіюють HTTP-транспорти.

| Метод | Шлях | Опис |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Сигнал активності, транспорт, стан підключення, останній виклик, найпопулярніші інструменти, рівень успішності за 24 год |
| GET | `/api/mcp/tools` | Список інструментів MCP із `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Відкриття потоку SSE для транспорту SSE (повертає `503`, якщо MCP вимкнено або транспорт не відповідає налаштуванню) |
| POST | `/api/mcp/sse` | Надсилання фрейму JSON-RPC через транспорт SSE |
| GET | `/api/mcp/stream` | Відкриття сторони SSE транспорту Streamable HTTP (повідомлення, ініційовані сервером) |
| POST | `/api/mcp/stream` | Надсилання фрейму JSON-RPC через транспорт Streamable HTTP |
| DELETE | `/api/mcp/stream` | Завершення сеансу Streamable HTTP |
| GET | `/api/mcp/audit` | Запит журналу аудиту — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Агрегована статистика аудиту (загальна кількість, рівень успішності, середня тривалість, найпопулярніші інструменти) |

**Автентифікація:** транспорти `sse`/`stream` використовують окремий механізм автентифікації MCP (Bearer-ключ API з областю доступу `mcp`); маршрути `status`/`tools`/`audit*` доступні для читання з панелі керування (додаткова автентифікація, окрім доступу до хоста панелі керування, не потрібна).

> Обидва HTTP-транспорти контролюються параметрами `settings.mcpEnabled` і `settings.mcpTransport` — невідповідність транспорту повертає `400`, а вимкнений стан MCP повертає `503`.

## Сервер A2A

OmniRoute надає кінцеву точку A2A (Agent-to-Agent) JSON-RPC 2.0, а також REST-обгортку для перевірки та використання в панелі керування.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # необов'язково, якщо не задано OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Підтримувані методи (усі керуються параметром `settings.a2aEnabled`):

| Метод            | Опис                                                                |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Синхронне виконання навички; повертає `{task, artifacts, metadata}` |
| `message/stream` | Потокове виконання того самого набору навичок через SSE             |
| `tasks/get`      | Отримання завдання за `taskId`                                      |
| `tasks/cancel`   | Скасування завдання за `taskId`                                     |

Вбудовані навички: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Картка агента

```bash
GET /.well-known/agent.json
```

Повертає загальнодоступну картку агента A2A (назва, опис, можливості, каталог навичок, схема автентифікації), яка публічно кешується на 1 годину. Автентифікація не потрібна.

### Допоміжні REST-маршрути

| Метод | Шлях                         | Опис                                                                                                                |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Стан увімкнення A2A, статистика завдань і кешований підсумок картки агента                                          |
| GET   | `/api/a2a/tasks`             | Список завдань — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не реалізовано як допоміжний REST-маршрут — створюйте через JSON-RPC `message/send`)                               |
| GET   | `/api/a2a/tasks/[id]`        | Отримання одного завдання                                                                                           |
| POST  | `/api/a2a/tasks/[id]/cancel` | Скасування завдання                                                                                                 |

**Автентифікація:** допоміжні REST-маршрути працюють без автентифікації для керування (доступні для читання з панелі керування); маршрут JSON-RPC `/a2a` використовує Bearer `OMNIROUTE_API_KEY`, якщо його налаштовано.

## Автентифікація

Відомості про чотири сімейства облікових даних (сеанс панелі керування, локальний токен CLI, токен доступу `oma_live_…`, API-ключ з областю керування) та їхні відмінності від ключів інференсу див. у розділі [Автентифікація керування](../guides/MANAGEMENT-AUTH.md).

- Маршрути панелі керування (`/dashboard/*`) використовують файл cookie `auth_token`
- Для входу використовується збережений хеш пароля; резервний варіант — `INITIAL_PASSWORD`
- `requireLogin` можна перемикати через `/api/settings/require-login`
- Маршрути `/v1/*` можуть вимагати Bearer API-ключ, якщо `REQUIRE_API_KEY=true`
- «Токен керування» / «API-ключ з областю керування» в цьому довіднику означає одне із сімейств, описаних у зазначеному посібнику, а не невизначений додатковий тип секрету

> **Критична зміна (v3.8.0)** — `/api/v1/agents/tasks/*` і кінцеві точки керування періодом очікування тепер вимагають **автентифікації керування** (файл cookie `auth_token` панелі керування або API-ключ з областю керування). Клієнти, які раніше викликали ці маршрути без автентифікації, отримуватимуть `401 Unauthorized`. Див. коміт `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
