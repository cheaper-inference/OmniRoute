> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-10-17 — v3.8.52 (додано [Покриття та обмеження](#coverage-and-limits):
> які маршрути та шляхи відповідей охоплюють хуки, об'єднані заголовки вимкнення (#16412), режим
> блокування ін'єкцій як обов'язкова межа (#16413) і що бачить відповідь перед post-call)

Guardrails забезпечують безпеку, політики та трансформації вмісту на межі
між OmniRoute та апстрим-провайдерами. Кожен guardrail може інспектувати (і
за потреби відхиляти, трансформувати або анотувати) тіла запитів (`preCall`)
та апстрим-відповіді (`postCall`).

Система працює за принципом **fail-open**: якщо guardrail кидає виняток під час
виконання, реєстр фіксує помилку й переходить до наступного guardrail, а не
провалює запит. Блокування — це явне рішення (`block: true`), а не випадковість.
Єдиний виняток — перерваний запит: коли `signal` викликача переривається,
guardrail, що кинув виняток, відхиляє запуск хука, а не пропускається.

Хуки **не** виконуються на кожному маршруті та не для кожної відповіді. Прочитайте
[Покриття та обмеження](#coverage-and-limits), перш ніж покладатися на guardrail
як на засіб безпеки.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Базова модель GLM 5.3 і `glm-5.3-{low,high,max}` мають чіткі метадані `supportsVision:false` registry/spec. Варіанти GLM 5.3 Flash залишаються нативними моделями. Маршрут `/v1/messages` коду Claude входить у спільний ланцюг огорожі перед викликом `handleChat`** раніше** Переклад Claude-to-OpenAI; вкладені зображення результатів інструменту `Read` повинні бути описані або оброблені до того, як цей переклад перенесе їх у вміст OpenAI `image_url` (#17069).

Перехоплює запити, що містять зображення, спрямовані на** моделі без зору** і або перенаправляє весь запит до моделі з підтримкою бачення, або замінює частини зображення текстовими описами, створеними настроюваною моделлю бачення перед вихідним викликом. Це дозволяє постачальникам лише текстових даних прозоро обробляти мультимодальні корисні навантаження.

Потік:

1. Пропустіть, якщо цільова модель уже підтримує vision (якщо вона не з’являється у списку примусових мостів `isVisionBridgeForcedModel`).
2. Витягніть частини зображення через `extractImageParts(messages)` (`visionBridgeHelpers.ts`), який делегує** уніфікований медіадетектор** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдине джерело правди, яке поділяється з комбінованим фільтром сумісності. Екстракція включена до дозволеного списку форм, `replaceImageParts` може з’єднувати назад (екстракт ↔ замінює контракт): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"` і відповіді API `input_image`. Відповідні зображення, вкладені в Claude Код `tool_result.content` і вихідні дані інструментів Responses, також витягуються та замінюються на їхні вихідні шляхи; фігури лише для індикаторів є матеріалом комбінованого фільтра і не витягуються. Пропустити, якщо нічого не знайдено.
3. Вирішити конфігурацію середовища виконання через `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*` виграють; застарілі ключі `visionBridge*` залишаються a** одноцикловий резервний варіант** (вікно відкату). Пропустити перед будь-яким обходом медіа, коли міст вимкнено.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) вирішує змінити маршрут проти опису. Reroute повертає `modifiedPayload` лише з заміною `model` і мета `{ rerouted, fromModel, toModel, imagesKept }`.
5. Описати шлях: обмежити зображення на `maxImages`, створити підказку з урахуванням завдань, переглянути кеш опису, викликати модель бачення** паралельно** (`Promise.allSettled`) і вставте частини тексту `[Image N]: <description>` на їхнє місце. Невдалий опис дає `null`: необроблене зображення зберігається для цілей unknown/vision-capable (#4012), але** підтверджена пряма мета лише для тексту** або комбінація з нульовим баченням отримує явну текстову заглушку `(unavailable — no vision-capable provider connected)` для кожного неописаного зображення, включаючи часткові помилки та зображення за межами обмеження виклику опису (#17069). Існуюча повна помилка комбінованого опису резервного варіанту залишається на місці (#8430).
6. Повернути `modifiedPayload` + мета (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | За замовчуванням | Поведінка                                                                                                                                                                                                                                                                                      |
| ---------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔                | Застаріла евристика, незмінна (#6640/#7204): некомбіновані моделі/моделі `auto/` перенаправляються до найкращої моделі бачення, якщо оригінальна модель уже не має придатних облікових даних (потім опишіть); комбіновані цілі завжди описують.                                                |
| `describe` |                  | Завжди описуйте — блок перенаправлення повністю пропускається; завжди відповідає обрана користувачем модель.                                                                                                                                                                                   |
| `reroute`  |                  | Примусове перенаправлення: захист моделі з обліковими даними обійдеться. Змінний маршрут -** мета** Credential guard все ще застосовує — коли не існує придатної для використання цілі зору, міст блокує явну помилку, а не описує або надсилає необроблені зображення до цілі лише з текстом. |

Форсовані режими короткого замикання** раніше** автоматичний евристичний запуск; Поведінка `auto` є байтовою ідентичною поведінці pre-PR-1 guardrail.

#### Область дії ключа API (`visionBridgeKeyScope.ts`)

Коли ключ API абонента обмежує `allowedConnections`, пули квот (`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`), міст лише вибирає перенаправлення та описує моделі, які може використовувати ключ, у з’єднаннях, які може використовувати ключ. Потім виклик describe завжди проходить через самоцикл OmniRoute із заголовком `x-omniroute-self-loop-key-id`, тож отриманий запит чату знову забезпечує підключення цього ключа та політику моделі. `enforceApiKeyPolicy()` враховує цей заголовок лише разом із носієм власного циклу, тому він може лише звузити доступ, а ідентифікатор, який не вирішується, відхиляється.

Якщо модель візуалізації не дозволена для ключа, a** підтверджена текстова мета** відхиляє запит зображення локально за допомогою чіткого HTTP 400 замість того, щоб пересилати байти зображення на непрацездатний вихідний канал (#17069). Для цілей з невідомими або власними можливостями бачення шлях опису зберігає свою попередню поведінку при відмові (meta `{ skipped: true, reason: "no_permitted_vision_model" }`). Запити без ключа та ключі без цих обмежень поводяться так само, як і раніше.

#### Підказка опису з урахуванням завдань (`modalityBridgeVisionTaskAware`)

За замовчуванням** правда** . `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає текст** останнє повідомлення користувача** (урізаний до 500 символів) до підказки базового опису, спрямовуючи опис до того, що насправді запитував користувач (шаблон codex-vision-proxy), і запитуючи модель бачення транскрибувати видимий текст. З вимкненим прапорцем — або відсутнім текстом користувача — базова підказка використовується без змін.

Власний OpenAI-сумісний запит describe self-loop (`callVisionModelSingle()` в `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` — безумовно, для кожного caller/provider, без стробування за жодним сигналом клієнта. Вибірка з низьким рівнем деталізації знижує точність OCR саме для завдання транскрипції тексту, яке вимагає це підказка, тому сам виклик describe завжди запитує високу деталізацію, незалежно від того, який рівень деталізації використав вихідний вхідний запит. Це впливає лише на внутрішнє тіло запиту на опис; це не змінює те, як OmniRoute пересилає власний `image_url.detail` абонента на основний запит — який за замовчуванням застосовується окремо та лише для виявлених клієнтів OpenCode у `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка формату проводів Anthropic циклу describe self не має поля `detail` і на неї не впливає жоден параметр за замовчуванням.

#### Опишіть вихідний ліміт (`modalityBridgeVisionMaxChars`)

| ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає** немає кришки** — опис, який повертає `callVisionModel()` передається незміненим, зберігаючи існуючу поведінку. Будь-яке значення в діапазоні 100–50000 скорочує опис суфіксом `…` перед тим, як він буде з’єднаний як `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`). Підніміть це для важких завдань OCR, де низхідна модель потребує повної транскрипції; знизити його до зв’язаного використання маркера на балакучих моделях зору. Поле інформаційної панелі знаходиться на вкладці «Зір Zod на панелі «Додатково» (`modality-bridge-max-chars` `z.union([z.literal(0), z.number().int().min(100).max(50000)])` `ModalityBridgeVisionTab.tsx`) і `0` будь-яке значення від `0` до 99 до 100 поверху, залишаючи явне значення — недоторканим.

#### Описати кеш (`modalityBridge/bridgeCache.ts`)

Кеш LRU + TTL в пам’яті для опису виходів, спільний для всього процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` з кадруванням префікса довжини (без колізій меж поля). Компонентом моделі є** налаштовано** модель мосту, а не модель, яка фактично відповіла — `callVisionModel` може відновитися внутрішньо, і введення ключа за спробу фрагментує кеш. Невдалі описи ніколи не кешуються. Налаштування:

| ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Дистанційна нормалізація зображення (автоциклічна вибірка describe/base64 )

Коли міст приносить a** дистанційний** саме зображення — Anthropic описує самовиклик і перетворення base64 формату claude-wire (`ensureBase64ImagesForClaudeWire`), обидва через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — отримані дані URI передаються через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед тим, як бути вбудованими в запит моделі бачення. Великі зображення зменшено до a** Довгий край 2048 пікселів** (відповідність обмеженню зміни розміру OpenAI/Anthropic вже застосовується на стороні сервера), що скорочує завантаження bytes/latency не змінюючи те, що бачить модель зору. Для зміни розміру використовується `sharp`, завантажений через динамічний імпорт: на платформі, де не вдається завантажити рідний двійковий файл, `normalizeDataUri()`** ніколи не кидає** — повертається до проходження вихідних байтів, тому шлях describe/base64-conversion завжди продовжує працювати. Байти без зображення (вибірка, яка не повернула зображення, яке можна декодувати), також пропускаються без змін. Ця нормалізація стосується зображень, які міст отримує для власного самовиклику — вона ніколи не застосовується до необробленого наскрізного корисного навантаження абонента, що відповідає принципу мутації лише за бажанням (жорстке правило №20).

#### Налаштування схеми міграції +

Нові ключі `modalityBridge*` підтверджені Zod у `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, тріо `modalityBridgeCache*` і група `modalityBridgeAudio*`, яка використовується Audio Bridge. Міграція `141_modality_bridge_settings.sql` копіює існуючі застарілі значення `visionBridge*` у відповідні нові ключі (ідемпотентний, ніколи не перезаписує встановлене оператором значення `modalityBridge*` ); застарілі ключі залишаються прийнятими як запасні для читання протягом одного циклу випуску.

#### Прозорість заголовка + stats

Перетворені описом відповіді містять `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (створений `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`, позначений `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`). Перенаправлені запити отримують** немає** заголовок — корисне навантаження було недоторканим, а зміна моделі вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (автентифікація керування, той самий рівень, що й `GET /api/settings`) повертає лічильники `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для кожної модальності в пам’яті для `vision`, `audio` та `video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як свій знаменник; операція без синхронізації не створює вибірку нуль мілісекунд. `bridged` залишається зворотно сумісним псевдонімом для успішних перетворень; невдалі спроби не збільшують його. Лічильники скидаються під час перезапуску процесу за проектом (телеметрія, а не облік).

#### Конфігурація приладової панелі

Спеціальною сторінкою інформаційної панелі є `/dashboard/settings/modality-bridge`. Його вкладки `Vision`, `Audio` і `Video` з URL-адресою зберігають параметри запиту під час перемикання значення `tab`. Вкладка Vision показує ввімкнення, режим, вибір моделі (включно з автоматичним за замовчуванням), підказки з урахуванням завдань, розширені обмеження timeout/image/description-length/cache, лічильники часу виконання та захищений запит зразка. Вкладка «Аудіо» також активна: на ній доступні параметри ввімкнення, вибір моделі лише для STT із автоматичним налаштуванням, обмеженнями timeout/max-clip, лічильниками аудіо та зразком тесту `input_audio`. Вкладка «Відео» є функціональною: вона повідомляє про стан виконання FFmpeg/ffprobe — один із чотирьох явних станів UI (`unknown`, коли зонд працює або не може завершитися, `restricted` на хості інформаційної панелі без зворотного зв’язку, де зонд пропускається на стороні клієнта, `unavailable` після перевірки та підтвердженої відсутності, або `available` з версіями FFmpeg/ffprobe ) — зберігає обмеження enable/model/frame/video/timeout, фільтрує засіб вибору моделі на моделі, здатні бачити, і показує лічильники відео.

Попередня карта Vision Bridge у налаштуваннях AI є посиланням сумісності на нову сторінку; він більше не володіє другою копією форми. Постачальники медіа також пов’язують робочі процеси «Зображення в текст» і «Мовлення в текст» із відповідними вкладками Modality Bridge, не видаляючи існуючий ігровий майданчик «Мовлення в текст».

**Обхід входу самостійної петлі:** коли виклик describe маршрутизується через власний цикл `/v1` OmniRoute(нестандартна модель провайдера), підзапит надсилає `x-omniroute-admission-bypass: internal` і проходить автентифікацію за допомогою розв’язаних облікових даних самоциклу — локального дозорного `sk_omniroute` у локальному режимі або настроєного оператором ключа `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env (#1350), щоб розгортання `REQUIRE_API_KEY=true` все ще могли запускати виклик describe. Обхід виконується лише для тих облікових даних, тому зовнішні клієнти не можуть використовувати заголовок, щоб пропустити допуск.

Застарілі параметри за замовчуванням діють у `src/shared/constants/visionBridgeDefaults.ts`; нові параметри mode/task-aware/cache за замовчуванням і резолвер налаштувань доступні в `src/shared/constants/modalityBridgeDefaults.ts`. Огородження відкриває опцію конструктора `deps`, щоб тести могли вводити підроблені реалізації `getSettings` та `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює аудіозапити чату до того, як вони досягнуть цілі, яка, як відомо, не приймає аудіовхід. Він ніколи не перенаправляє запит на чат: аудіочастини транскрибуються через існуючу кінцеву точку, сумісну з OpenAI, і вибрана модель чату продовжує текстові стенограми.

Потік:

1. Розв’яжіть `supportsAudio` через `getResolvedModelCapabilities()`. Перемагають явні метадані реєстру провайдера, потім метадані статичної моделі, потім синхронізований `modalities_input`. Оголошений список введення без `audio` - це `false`; жодних доказів можливості не залишається `null`. І `false` і `null` активують консервативний міст, тоді як `true` обходить його.
2. Вирішуйте параметри `modalityBridgeAudio*` та вилучайте з’єднувані аудіочастини верхнього рівня з кожного повідомлення через спільний детектор `detectMediaParts()`. Підтримувані форми проводів: OpenAI, `input_audio`, `audio_url` та `source.media_type: "audio/*"`. Вкладене аудіо виявляється для маршрутизації, але не видаляється шляхом з’єднання. Робота обмежена `modalityBridgeAudioMaxClips`; пізніші частини залишаються недоторканими.
3. Зверніть увагу на налаштований `provider/model` або дозвольте `selectAudioBridgeModel()` ходити `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та виберіть першу модель із доступними обліковими даними активного постачальника.
4. `callAudioTranscription()` перетворює аудіо base64/data-URI у багатокомпонентний `file` або завантажує віддалений `audio_url` через загальнодоступний вихідний захист із закріпленням DNS та обмеженням 25 MB. Потім він POSTs файл і вибрану модель до локального самоциклу `/v1/audio/transcriptions`, автентифікованого за допомогою `resolveSelfLoopBearer()`. Існуючий маршрут транскрипції виконує звичайний пошук облікових даних, обробку cooldown/rate-limit і відправлення постачальника.
5. Успішні дзвінки замінюють свої частини на `[Audio N]: <transcript>`. Дзвінки виконуються за допомогою `Promise.allSettled`: окрема помилка зберігає оригінальну звукову частину (контракт #4012). Якщо кожен виклик зазнає невдачі, а ціль підтверджено `supportsAudio === false`, частини стають `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для невідомої цілі (`null`) результат повної невдачі залишається незмінним. Перевірена лише текстова ціль без придатних облікових даних STT отримує ту саму явну заглушку без здійснення мережевого виклику.

Успішні стенограми використовують кеш LRU/TTL Modality Bridge для всього процесу. Ключ поєднує звукове посилання, мітку стабільної роботи `audio-transcription` і вибрану модель STT ; помилки ніколи не кешуються. Спроби звуку оновлюють спільні лічильники `bridged`, `cacheHits`, `failures` і `lastUsedAt`. Трансформовані відповіді містять `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; недоторкані запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання підтримуються БД і підтверджуються Zod:

| ключ                          | За замовчуванням | Діапазон        |
| ----------------------------- | ---------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`           | —               |
| `modalityBridgeAudioModel`    | `""`             | Авто або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`          | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`              | 1–10            |

Спільний кеш залишається під контролем `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` і `modalityBridgeCacheMaxEntries`.

### Відеоміст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює частини відео верхнього рівня в завершеннях чату `messages` та відповідях API `input` перед викликом цілі без відомої підтримки відео. Підтримувані форми: `input_video`, `video_url`, `video_source`, HTTPS URLs і `data:video/*;base64,...` data URIs. Звичайні назви файлів у тексті не вважаються відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) володіє обходом запитів, перевіркою capability/policy, агрегацією для кожного запиту та корисним навантаженням відповіді. Отримання — для кожного відео, кеш усього результату, що описує послідовність кадрів (що об’єднує будь-яку заявлену абонентом аудіотранскрипцію), і metrics/abort/cleanup для кожної спроби — приховані за `processVideoPart` у `videoBridgePipeline.ts`, що викликається один раз для кожної частини відео в циклі `preCall`. Цей модуль також визначає явні межі порту `VideoMediaBrokerPort` (отримання байтів і вилучення вибіркових кадрів), `VideoAudioTranscriptionPort` (об’єднання аудіотранскрипту, оголошеного абонентом, із вибірковими підписами) і `VideoDrilldownPort` (межа постійності деталізації кадрів; ще не підключено до `processVideoPart` — сьогодні лише окремий маршрут `/api/modality-bridge/video/drilldown` записує детальні записи).

Загальнодоступний шлях запиту `/v1` ніколи не імпортує та не викликає підпроцес. Віддалені відео завантажуються в межах 50 MiB ; вбудовані відео base64 мають консервативне обмеження 36 MiB декодованих для кожного відео, тому конверт model/messages/framing може залишатися в межах загальнодоступного ліміту запиту JSON 50 MiB. Оцінки внутрішньої довжини та декодованого розміру перевіряються перед розподілом. HTTPS потрібний для початкового віддаленого URL і кожного перенаправлення, використовуючи наявний загальнодоступний вихідний захист із закріпленням DNS. Потім байти перетинають точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`. Цей маршрут є як `LOCAL_ONLY` так і `SPAWN_CAPABLE`, приймає лише автентифікований для кожного процесу запит довіреної петлі та ніколи не приймає URL, шлях до файлової системи, виконуваний файл або список аргументів. Конвеєр розміру тіла API і зчитувач тіла обробника з приростом незалежно один від одного забезпечують обмеження введення брокера 50 MiB. Його обмежена черга запускає одне видобування за раз, дозволяє чотири незавершені завдання та обмежує очікуваний вхід 100 MiB.

У брокері `ffprobe` читає приватний локальний файл; дозволений список фіксованого формату виключає формати списку відтворення та маніфесту. Для дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV залишаються вимкненими за замовчуванням, а команда fixed не підключається до них. І `ffprobe` і `ffmpeg` використовують білий список протоколу `file` -only, один потік, фіксовані масиви аргументів, відсутність оболонки та виконувані файли, вирішені з `PATH`. Потоки обкладинок із прикріпленими зображеннями не є кандидатами для відтворення. Усі потоки, які можна відтворювати, мають відповідати обмеженням, і явний потік за замовчуванням є кращим перед детермінованим резервним варіантом із найнижчим індексом. Відео обмежено 600 секундами, 8192 пікселями на розмір і 33 554 432 пікселями джерела. FFmpeg відбирає 1–16 середніх кадрів JPEG, зменшує довгий край максимум до 1024 пікселів без масштабування менших вхідних даних і ніколи не отримує URL. Типово вибірка — `uniform`. Додаткові політики `scene_aware` і експериментальна `segment_aware` виконують один додатковий фіксований прохід FFmpeg через уже перевірений локальний потік, вибирають обмежені мітки часу сцени `showinfo` та детерміновано повертаються до тих самих рівномірних середніх точок у разі відмови детектора, тайм-ауту, неправильного виведення або порожнього набору кандидатів. Режим з урахуванням сегментів розподіляє середні зразки пропорційно підтвердженим інтервалам сцени; докази з урахуванням сегментів і резервна поведінка детально описані нижче. Жорстке обмеження на 16 кадрів застосовується після вибору в кожній політиці. Коли запит з урахуванням сцени має лише бюджет одного кадру, він використовує рівномірну середню точку активного повного відео або фокусного вікна та повідомляє `policyEffective: uniform`: один вибраний кадр сцени не може зберегти обидва часові кінці. Абонент може додатково надати кінцеве вікно фокусу (`start`/`end` секунд); межі обмежуються тривалістю медіа, зворотні або нескінченні вікна відхиляються, а всі політики вибірки виконуються лише в межах нормалізованого інтервалу. Отримане вікно включено в метадані вибірки та в ненадійний префікс опису, щоб подальші моделі могли відрізнити сфокусований уривок від повної шкали часу.

Фокус семантичного підпису – це окреме, явне налаштування. Режим аналізу `full` за замовчуванням зберігає наявний кадр підказки та ніколи не пересилає текст запиту до моделі підпису. У режимі `focused` міст читає лише останні непорожні `text`/`input_text`, створені користувачем, із того самого контейнера Chat або Responses, нормалізує його до NFC, згортає контрольні символи та пробіли та обмежує до 500 кодових точок Unicode. Порожній результат повертається до точного запиту `full`. Користна підказка серіалізується як JSON у спеціальному блоці контексту ненадійного користувача та може визначати пріоритет лише для спостережуваних деталей; воно не може замінити окреме попередження про недотримання інструкцій, видимих або чутних у ЗМІ. Текстовий фокус ніколи не визначає `start`/`end` і не змінює часову вибірку.

#### свідоцтво структурного сегмента FU-07

`segment_aware` використовує один обмежений прохід попереднього аналізу над уже перевіреним локальним відеопотоком. Фіксований ланцюжок фільтрів спочатку масштабується до 320 пікселів у ширину, виявляє зміни сцени та заморожені інтервали, а потім виконує вибірку зі швидкістю 1 кадр на секунду для інформації про розмиття, середню яскравість і spatial/temporal. Перепустка обмежена 600 структурними зразками, одним потоком FFmpeg/filter, тим самим протоколом `file` -only і списками дозволених контейнерів, обмеженням 1 MiB для виведення процесу та щонайбільше 30 секундами всередині спільного abort/deadline. брокера. Він ніколи не приймає команду, фільтр, шлях або URL із запиту.

Структурні значення є детермінованим доказом вибірки, а не семантичним розумінням відео. Вони не визначають теми, дії, підписи, мову чи наміри користувача. Межі сцени та стоп-кадри утворюють сегменти; охоплення стоп-кадра, розмиття, експозиція, просторові деталі та тимчасові зміни впливають лише на те, як розподіляється наявний бюджет від 1 до 16 кадрів. Повністю заморожений сегмент обмежений одним кадром, тоді як незаморожені сегменти змагаються за решту бюджету. Коли межі перевищують кількість кадрів, рівномірне покриття часової шкали зберігається, тому швидкі ранні скорочення не можуть приховати довгий кінцевий сегмент. Межі сцени в межах 1-секундної роздільної здатності межі закріплення об’єднуються.

Відсутні фільтри, докази malformed/empty, помилка детектора або обмежений час очікування попереднього аналізу не відкривають точної єдиної політики середньої точки. Кінцевий термін виклику або брокера не відкривається: він завершує поточний підпроцес, запобігає подальшому вилученню кадрів, а приватне тимчасове дерево видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні фікстури FFmpeg для економії викликів субтитрів після дедупування, розподілу бюджету щільного руху, доказів blur/exposure/SI-TI, швидких скорочень із довгим хвостом та хибних спрацьовувань із поступовим зникненням. Він записує час стіни перед аналізом і, якщо доступний `/usr/bin/time`, дочірній CPU та пік RSS. Його перевірки якості є лише структурними оракулами. Якість реальної моделі субтитрів залишається `HOLD` оскільки цей джгут не має авторизованої кінцевої точки чи замороженого судді. Грошові заощадження також залишаються `HOLD` якщо `--caption-cost-per-call-usd` не надає чітку позитивну оцінку за дзвінок; сценарій ніколи не створює жодного результату.

Кожен кадр обмежений 4 MiB, усі необроблені кадри разом 23 MiB, а серіалізована відповідь посередника – 32 MiB. Приватний тимчасовий каталог видалено в `finally`. OmniRoute не об’єднує FFmpeg і не приймає настроюваний шлях до виконуваного файлу. Перед субтитрами міст застосовує консервативну візуальну дедуплікацію: кожен JPEG зменшується до буфера 16 × 16 градацій сірого та порівнюється лише з останнім збереженим кадром. Для запитуваного бюджету субтитрів понад один кадр вилучення надає обмежений пул кандидатів, що може бути вдвічі більшим за бюджет і ніколи не перевищує 16 кадрів. Запитане обмеження застосовується лише після дедуплікації, причому перший і останній вибрані кандидати зберігаються під час остаточного зрідження, коли бюджет становить принаймні два. Версійна політика `grayscale-16x16-mean-cells-v2` використовує більшу величину з середньої дельти яскравості та співвідношення комірок мініатюр, нормалізована дельта яких становить принаймні 0,05. Дублюючий поріг є константою 0,04, обраною для передбачуваності, а не виставленою як налаштування під час виконання. Цей вторинний висококонтрастний сигнал зберігає незначні рухи та зміни видимого тексту, які може приховати лише середнє порівняння. Помилки компаратора або декодера не відкриваються та не зберігають покриття. Вихідні метадані відокремлюють витягнуті кандидати, успішно використані кадри та видалені візуальні дублікати.

Явно позначена частина відео може вимагати контактну сторінку з позначкою часу. Міст створює сітку JPEG щонайбільше з 4 стовпців і 16 кадрів. Кожна 512-піксельна комірка записує свою вихідну мітку часу у висококонтрастну нижню смугу, тоді як ті самі мітки часу залишаються в текстових метаданих для асоціації та перевірки. Повний JPEG залишається обмеженим у 32 MiB. Якщо `sharp` не може декодувати або скласти сітку, міст повертається до окремих кадрів JPEG ; клієнтське скасування все ще поширюється через операцію аркуша.

Докази просування навмисно відокремлені від мікротесту синтетичної композиції. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає схемно-версійний джгут A/B для реальних OpenAI-сумісних моделей зору. Він вимірює маркери, надані постачальником, наскрізну затримку стіни (включаючи композицію аркуша), кількість викликів моделі та збереження фактів, визначених маніфестом. Необроблені відповіді моделі не записуються до звіту; зберігаються лише дайджести SHA-256 і відповідний факт IDs. Кабель не здійснює жодних мережевих або платних викликів, якщо не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` і `OMNIROUTE_API_KEY`. Без цього явного реального запуску його машиночитаний вердикт залишається `HOLD`; лише синтетичні вимірювання payload/call-count не є доказом просування.

Абоненти можуть приєднати додатковий масив `transcript.cues` до підтримуваної частини відео, якщо вони вже мають вирівняний текст. Кожна репліка повинна містити `text`, кінцевий інтервал `start`/`end` всередині досліджуваної тривалості, і `source` з білого списку (`client`, `embedded` або `audio-bridge`); `confidence` за замовчуванням має значення `1` і має залишатися між `0` і `1`. Точні дублікати сигналів згортаються. OmniRoute ніколи не починає транскрипцію з цих метаданих: перевірені підказки копіюються в описаний результат із джерелом, достовірністю та інтервалом і відображаються як ненадійні спостереження разом із підписами кадрів. Недійсний текст, текст, що виходить за межі діапазону, або текст без походження відхиляється, а не додається до потоку субтитрів. Обидва канали транскрипції тіла запиту нормалізують надане походження до `client`, включаючи самостверджені мітки `embedded` або `audio-bridge`. Лише серверний адаптер може призначати ці довірені мітки через аргумент `trustedSource` лише для коду; поле запиту JSON не може досягти цього аргументу. Текст стенограми залишається ненадійним медіа-контентом, незалежно від його походження, і ніколи не повинен визначати авторизацію.

Досвідчений абонент може надати трек `audioTranscript` для того самого відео; він розглядається як текст, наданий клієнтом, а не як доказ транскрипції сервера. Fusion seam виконує візуальні та аудіоспостереження за одним кінцевим терміном і сигналом скасування, упорядковує їх на загальній часовій шкалі, згортає точні дублікати та повідомляє про частковий результат, коли лише одна сторона вдається. Недійсний `audioTranscript` знижується до цього часткового результату — візуальний опис зберігається, а аудіогілка записує дезінфікований код помилки — замість помилки всього відео. Доступність для кожної гілки, частковий прапор і дезінфіковані коди помилок зберігаються в описаному результаті, у метаданих огородження (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), у метаданих кешу результатів і в лічильниках об’єднання мостів. Шлях Video Bridge за замовчуванням не викликає перетворення мовлення в текст і не завантажує другу медіа-копію; без цього явного треку він залишається лише відео.

**Збереження стенограми (#12150 P1).** Це застосовується автоматично щоразу, коли Video Bridge (саме ввімкнуте) рендерить стенограму cue — окремого прапорця збереження немає. Коли запит рендерить будь-яку розшифровку репліки (заявлену абонентом `transcript` або об’єднану `audioTranscript`), огородження позначає її `videoBridgeObserved` і створює відредаговану тінь опису відео — ідентичне відтворення, у якому тіло вільного тексту кожної репліки замінюється на `[redacted-video-transcript]`, створене шляхом заміни структурованого поля репліки перед складанням рядка (ніколи не шляхом аналізу зведеного тексту, тому не cue content — змагальний або звичайний, включаючи тіла, що містять `]`, такі як `[inaudible]`/`[music]` — можуть вижити). Постійне тіло запиту журналу викликів замінює кожну текстову частину, отриману з відео, на цю відредаговану тінь, що відповідає рівності вмісту; прив’язка `fullText` перечитується з готового корисного навантаження огородження перед викликом, тому збіг все ще вдається після того, як пізніші огородження ланцюга ( PII і засоби маскування облікових даних, пріоритети 10/95) переписують текст опису на місці та після ін’єкції system-prompt/handoff/memory змінюють форму масиву повідомлень. Тіло, надіслане вище за течією до моделі, не змінюється. Спостережуваний запит також не заповнює постійну пам’ять (вилучення як із запиту, так і з відповіді пропускається), тому власна відповідь моделі не може повторити текст стенограми в пам’ять.

**Необроблені відеополя (#12430).** Коли міст увімкнено, а підтримка рідного відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved` навіть після помилки опису або обмеження `maxVideos`. `null` і кількість порожніх рядків; відсутні поля та метадані, не пов’язані з відео. Збережені копії редагують ці поля або пропускають запит, а caches/Memory пропускаються.

На цих резервних шляхах дійсні сигнали абонента стають підтримуваними частинами `text`/`input_text`, а не нестандартними полями провайдера. Обидві доріжки, надані за запитом, залишаються ненадійними спостереженнями `client` із явним попередженням про те, що відео не було описано, а мітки часу не перевірено на медіа. Існуючі загальні бюджети 256-cue/64-KiB і бюджети на репліки застосовуються до двох доріжок разом; мітки часу повинні відповідати 600-секундній стелі брокера та будь-якому наданому фокусному вікну. Недійсні треки відкидаються, а не пересилаються як довільний текст; дійсний рідний брат все ще може використовуватися, якщо їх сумарний бюджет не перевищено. Поля Null/empty не додають тексту. Цей запасний варіант не додає жодних медіа-запитів або транскрипції. Поля розширення транскрипції видаляються з резервного носія відео та його об’єктів `video_url`/`source`. Список дозволених проводів OpenAI залишається суворим; невідомі рідні носії відео залишаються доступними, а відомі лише текстові цілі зберігають безпечні маркери. Структуровані тіні редагування захищають доданий текст стенограми, тоді як вихідний запит абонента залишається незмінним. Нативні цілі та вимкнені мости зберігають існуючу поведінку обходу.

Додаткові збережені копії використовують той самий спостережуваний сигнал запиту. Необроблений знімок клієнтського запиту перед огорожею, незавершений запит у пам’яті та журнал ранніх відхилених запитів структурно замінюють поля стенограми у частинах відео; рядкові підказки, синтезовані етапами конвеєра та контекстною передачею, редагуються в приймачі persisted-request-body. Постійний маркер `video_content_removed` змушує продовження `previous_response_id` не закриватися, а не реконструювати текст, який було навмисно відкинуто. Якщо спостережуваний запит втрачає тінь редагування для кожної частини перед реєстрацією або навіть одна з кількох тіней відео не збігається після пізніших змін запиту, збережене тіло запиту повністю пропускається замість збереження частково відредагованого стенограми.

Для спостережуваного запиту модель відповіді може цитувати будь-яку частину стенограми без структурованої межі підказки. Таким чином, його постійний журнал викликів `responseBody` замінюється маркером пропуску; детальний артефакт конвеєра (який може включати тіла upstream/client і фрагменти потоку) не зберігається. Семантичний кеш, кеш ідемпотентності та відтворення міркувань обходять читання та запис для цього запиту. Запит постачальника та видима клієнтом відповідь залишаються незмінними. Ранні байти підтримки активності зливаються з тимчасового буфера, коли детальний артефакт пропускається. Попередження Kiro про некоректний EventStream повідомляє лише кількість байтів корисного навантаження, а не його вміст чи помилку аналізатора JSON. Це не означає, що кожна непов’язана діагностика provider/plugin була перевірена; ширша розгортка утриманого раковини відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою підкладкою кешу loopback/token-authenticated. Кожна операція також вимагає канонічного непрозорого принципала ID. Перш ніж увімкнути виробничий виклик, він має отримати цей ID від автентифікованого клієнта та ніколи не повинен пересилати значення, вибране клієнтом. Ключі кешу прив’язують цього принципала до канонічного сеансу та відео-посилання IDs, зберігають лише свої ключі SHA-256-derived, а читання та видалення застосовують до одного принципала. Кеш зберігає щонайбільше 16 отриманих JPEG кадрів на запис, термін їх дії закінчується через десять хвилин і підтримує обмежене зчитування `start`/`end` або явне видалення сеансу.

Кожен принципал обмежений 16 записами та 64 MiB канонічних даних JPEG. Ці обмеження не залежать від глобальної стелі 64-entry/256 MiB : тиск квоти принципала вилучає лише останні нещодавно використані записи цього принципала, перш ніж розглядається глобальне виселення LRU. Записи, термін дії яких минув, видаляються як з основного, так і з глобального обліку активності кешу, тоді як скасування та помилка перевірки не призводять до часткової заміни.

Кеш відхиляє неканонічні Base64, надлишкові заповнення, носії не JPEG, неправильно сформовані або скорочені JPEGs та JPEGs, які створюють попередження під час обмеженого декодування повного зображення `sharp`. Він повторно кодує кожне прийняте зображення як канонічний JPEG, отримує ширину та висоту з декодованих байтів замість того, щоб довіряти полям виклику, і відкидає будь-які кінцеві поліглотні байти, а не зберігає їх. Лише обмежений канонічний стислий буфер стягується з обох квот. Ліміт проводів JSON включає накладні витрати Base64 для стелі декодованого входу 32 MiB. Кожна збережена деривація записує свій підтверджений JPEG format/resolution, політику вибірки, версію деривації, час створення, обчислений сервером хеш вмісту та хешовану батьківську посилання, а також хеш батьківського вмісту довіреного абонента. Скасування перевіряється між асинхронними фазами decode/hash перед фіксацією атомарного кешу.

Цей транш ще не підключає виробника продукції до маршруту та не забезпечує вибір варіантів із різною роздільною здатністю. Таким чином, прозорий шлях запиту Video Bridge не вимагає додаткової роботи, тоді як вихідний принципал, пов’язаний із клієнтом, і повний життєвий цикл FU-08 з кількома роздільними властивостями залишаються явною подальшою роботою, а не документованою як повна поведінка.

Кадри послідовно підписуються відповідно до налаштованої моделі Video. Порожнє перевизначення відео успадковує параметр Vision; якщо обидва порожні, автоматичний маршрутизатор Vision вибирає ефективну модель, здатну бачити. Успішні субтитри замінюють оригінальну частину стабільним префіксом `[Video description:`, який також позначає текст як ненадійне спостереження, отримане з медіа, і повідомляє подальшим моделям не слідувати інструкціям, які містяться в медіа. Ключі кешу підпису кадру включають байти JPEG, підказку, мітку часу та ефективну модель; кешуються лише успішні підписи. Записи кешу зберігають фактичну успішну модель виробника, включаючи резервну модель; міст повідомляє `mixed`, коли різні рами були виготовлені різними моделями. Звернення до кешу повторно використовує цей ідентифікатор виробника замість того, щоб перемаркувати його як запитуваний план маршрутизації. Кеш результатів усього відео встановлюється на кожному вході, який змінює вихідну підказку —, ефективну модель, політику вибірки, кількість кадрів, режим семантичного аналізу, відбиток SHA-256 нормалізованої підказки фокусу, вікно фокусу, `transcript`, `audioTranscript` і прапорець — контактного аркуша, тому зміна будь-якого з цих розмірів є промахом кешу, а не застарілим повторним використанням. Версія політики візуального дедуплювання, порогове значення та обмежена кількість кадрів-кандидатів також чітко вказуються в ключі кешу результатів і метаданих; тому зміна політики не може повторно використовувати застарілий опис цілого відео. Метадані Result-cache v4 зберігають режим і відбиток, а не необроблене завдання користувача. Метадані Guardrail повідомляють про запитуваний і ефективний режими аналізу; запитуваний режим `focused` без придатного для використання тексту користувача повідомляється як ефективний `full`.

Огородження витягує кожну підтримувану частину відео, але описує не більше ніж `modalityBridgeVideoMaxVideos`. Для об’єкта, який має `supportsVideo === false`, невдалі відео та відео з перевищенням ліміту стають явними маркерами безпечного тексту, тому жодне необроблене відео не виживає. Якщо можливості невідомі, ці частини зберігають свій відеоносій; будь-яка резервна транскрипція виконує перетворення обмеженого тексту вище. Цілі з `supportsVideo === true` обходять міст. Сигнал скасування запиту клієнта поширюється через завантаження, чергу брокера, підпроцеси та виклики субтитрів; перериває зупинку між відео та ніколи не відкриває необроблені медіафайли.

Налаштування середовища виконання підтримуються БД і підтверджуються Zod:

| ключ                                | За замовчуванням | Діапазон / поведінка                                                                                           |
| ----------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`          | Додатковий час виконання, підключення                                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`         | `full` зберігає загальні підписи; `focused` використовує обмежений, ненадійний контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`             | Успадкуйте модель Vision Bridge                                                                                |
| `modalityBridgeVideoFrameCount`     | `8`              | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`      | `uniform`, `scene_aware` або пропорційний `segment_aware`; збій детектора повертається до `uniform`            |
| `modalityBridgeVideoMaxVideos`      | `1`              | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`         | 1000–120000 мс                                                                                                 |

Застарілі значення тайм-ауту відео понад 120 секунд прив’язуються до кінцевого терміну посередника; записи нових налаштувань, що перевищують це обмеження, відхиляються. `GET /api/modality-bridge/video/runtime` вимагає довіреної позначки петлевої локалізації перед автентифікацією або перевіркою під час виконання, а потім вимагає автентифікації керування. Він повертає лише `available`, очищені версії FFmpeg/ffprobe і фіксовану причину, коли середовище виконання недоступне. Внутрішня кінцева точка вилучення не є загальнодоступним завантаженням API: насиченість черги повертає `503` плюс `Retry-After`, роз’єднання абонента повертає `499`, а фіксований кінцевий термін посередника повертає `504`. Перетворені відповіді додають `video->text;model=<visionModel>;parts=<videos>` до центрального заголовка `x-omniroute-modality-bridge` без видалення сегментів Vision або Audio.

### PII Masker (`piiMasker.ts`)

Бігає далі** обидва** етапи.

- **`preCall`** клонує корисне навантаження, проходить `system`, `messages`, `input` і `prompt` (включаючи звичайні рядкові елементи) і застосовує `processPII()` (від `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли `PII_REDACTION_ENABLED=true`, виявлений PII редагується у вихідному корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який лише контролює політику підказки). Коли редагування вимкнено, виявлення записів викликів зараховується без перезапису вмісту.
- **`postCall`** глибоко клонує відповідь, запускає `sanitizePIIResponse()` і засіб маскування Responses-API (`maskResponsesOutput` — охоплює `output_text` та `output[].content[].text`). Якщо відбувається редагування, змінена відповідь замінює оригінал.

Огорожа ніколи не блокується; він лише анотує (`meta.detections`, `meta.redacted`) або переписує.

#### Вибір за типом, спеціальні шаблони та лічильники виявлення

**Інформаційна панель → Налаштування → Безпека → PII маскування** вибирає _що_ маскується. Він не вмикає маскування: це все ще `PII_REDACTION_ENABLED` (запит) і `PII_RESPONSE_SANITIZATION` (відповідь + SSE), обидва вимкнено за замовчуванням.

- **Вибір за типом** — вбудовані ідентифікатори перераховані в `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Unset означає кожен тип (поведінка до існування цього параметра). Шаблон `ssn_us` механізму запитів відображається на `ssn`. Шаблони (мінімальний, стандартний, фінансовий, бразильський, USA, GDPR, POPIA, повний) лише заповнюють прапорці в UI.
- **ідентифікатори GDPR та POPIA** — дванадцять вбудованих ідентифікаторів, що охоплюють EU і південноафриканські персональні ідентифікатори (таблиця нижче). Їхні регулярні вирази, валідатори та теги юрисдикції живуть в одній таблиці, `src/shared/utils/piiPatterns.ts`, яку споживають дезінфікуючий засіб відповіді (`src/lib/piiSanitizer.ts`) і засіб маскування запиту (`src/shared/utils/inputSanitizer.ts`). Збіг редагується лише тоді, коли його валідатор приймає; простого ряду цифр ніколи не буває достатньо. Оператор, який зберіг звужений вибір до того, як існували ці ідентифікатори, зберігає свою поведінку, доки не буде позначено нові ідентифікатори.
- **Викрійки на замовлення** — до 20 шаблонів регулярних виразів або символів підстановки (`*` = до 64 символів, які не є пробілами, `?` = один). Збіги стають `[CUSTOM_REDACTED]`. Кожен шаблон проходить через `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): щонайбільше 500 символів, прапори обмежені `g i m s u`, повинні компілюватися, повинні проходити `safe-regex` (катастрофічне відстеження) і не повинні збігатися з порожнім рядком або заповнювачем редагування. Невдалий шаблон відхиляється під час збереження та тестування, а збережений рядок, який не вдається, пропускається під час виконання замість компіляції. Спеціальні шаблони запускаються лише тоді, коли ввімкнено маскування.
- **Лічильники виявлення** — підраховує тип (ніколи не збігаються значення), зберігається в пам’яті та скидається під час перезапуску (`src/lib/pii/piiDetectionStats.ts`). Під час маскування вони лише збільшуються.

Параметри зберігаються в таблиці `key_value` (простір імен `pii_settings`, `src/lib/db/piiSettings.ts`) і зчитуються через кеш-пам’ять, яка триває 1 с. API:

| метод  | шлях                     | призначення                                                                    |
| ------ | ------------------------ | ------------------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | Стан прапора, `enabledTypes`, `customPatterns`, лічильники виявлення           |
| `PUT`  | `/api/settings/pii`      | Замініть `enabledTypes` (`null` = все) and/or `customPatterns`                 |
| `POST` | `/api/settings/pii/test` | Сухий прогон одного зразка проти зразка не більше 8 KB; нічого не зберігається |

Усі три вимагають автентифікації керування та перевірки тіла за допомогою Zod (`src/shared/validation/schemas/piiSettings.ts`).

Оскільки формати, що містять лише цифри, конфліктують із номерами замовлень, номерами збірок і часовими мітками, найслабші з них (`za_vat`, `za_tax_ref`) потребують підказки ключового слова, а простий десятизначний номер `0..` не розглядається як номер телефону Південної Африки. Саме маскування залишається доступним (Жорстке правило №20): ніщо тут не змінює прапор функції за замовчуванням.

### Оперативна ін'єкція (`promptInjection.ts`)

Виявляє конкурентні структури в наданому користувачем вмісті та забезпечує виконання налаштованої політики. Поведінка визначається змінними середовища та параметрами конструктора:

| Налаштування     | Env вар                                                                                                   | За замовчуванням | Ефект                                                                                                                                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                 | `true`           | Коли `false`, огорожа коротке замикання.                                                                                                                                                              |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                           | `warn`           | Політика введення: `block`, `warn` або `log`. (`redact` приймається для зворотного співставлення, але робить** ні** смужка ін'єкції тексту; запит PII rewrite контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальний рівень серйозності, необхідний для блокування. Середній за замовчуванням доступний лише для спостереження.                                                                                |

**Пріоритет режиму** (`getMode`): абонент `options.mode` → `INJECTION_GUARD_MODE`** перевизначення прапора функції DB** (Панель інструментів → Параметри → Функціональні позначки) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env → `warn`. Таким чином, перевизначення інформаційної панелі має перевагу над змінними env, тому Feature Flags UI керує поточним захистом (без перезапуску). Читання DB є безвідмовним: у разі помилки охоронець повертається до поведінки на основі env, а якщо перевизначення не встановлено, поведінка є ідентичною розв’язанню лише env.

Джерела виявлення:

1. `sanitizeRequest()` від `@/shared/utils/inputSanitizer` (спільний набір детекторів, який використовується деінде в конвеєрі).
2. Вбудований `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` і `markdown_system_block`, обидва мають рівень серйозності `high` ).
3. Додатковий `customPatterns` що передається через параметри конструктора (рядки, регулярні вирази або записи `{ name, pattern, severity }` ).

Коли `mode === "block"`** і** принаймні одне виявлення відповідає порогу серйозності, `preCall` повертає `{ block: true, message: "Request rejected: suspicious content detected" }`. У режимах `warn`/`log` огорожа реєструє, але дозволяє виклик. Спільний допоміжний `evaluatePromptInjection()` також експортується для абонентів, які потребують оцінки підказок без перегляду реєстру.

**Сканування пов’язане (v3.8.20):** детектор лише перевіряє** перші 16 KB** об’єднаного тексту підказки — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у `src/shared/utils/inputSanitizer.ts`. І `detectInjection()`, і `evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском циклу шаблону. Директиви ін’єкції розташовуються у верхній частині вхідних даних, тому це обмежує регулярний вираз CPU/GC на корисних навантаженнях у кілька сотень КБ без послаблення виявлення (див. #3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Бігає далі** обидва** етапи, останні в ланцюжку за замовчуванням (пріоритет `95`). Редагує добре відомі шаблони ключів API/секретних маркерів із вихідного корисного навантаження (вміст повідомлення, аргументи виклику інструменту, результати інструменту)** і** відповідь постачальника, тому облікові дані, вставлені в підказку (або повторені результатом інструменту), не просочуються до вищестоящого постачальника або назад до клієнта.

- **Лише згода** , така ж угода, що й редагування PII (жорсткое правило №20-прилеглий): вимкнено, якщо тільки `settings.credentialRedactionEnabled === true`** або** `CREDENTIAL_REDACTION_ENABLED=true`. Якщо його вимкнено, огорожа є безопераційним — він ніколи не блокує та ніколи не переписує.
- `redactCredentials()` проходить повне дерево payload/response (`walkValue()`, prototype-pollution-safe, cycle-safe через `WeakSet`) і замінює збіги заповнювачем `[REDACTED:<type>]`, клонуючи лише гілки, які фактично змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі провайдера LLM (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack, Linear, Notion, npm, Postman, Discord), ключі оплати (Stripe, Square), хмарні ключі (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWTs, рядки підключення з обліковими даними (`mongodb://user:pass@...` тощо) і загальний шаблон значення заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключі у формі заголовка (`authorization`, `x-api-key`, `api-key`, `apikey`) відредаговано структурно (тільки значення, збережено префікс схеми, як-от `Bearer `/`Basic ` ), а не через загальний текстовий регулярний вираз.
- Огорожа ніколи не блокується; він лише переписує (`modifiedPayload` / `modifiedResponse`) і анотує (`meta.credentialsRedacted`, `meta.count`).

Захист регресії: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true здійснює коротке замикання ланцюжка
  message?: string; // показується під час блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail сигналізує «без змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, яке передається ланцюжком далі, для наступних guardrail-ів.
`signal?: AbortSignal` переносить життєвий цикл викликача в guardrail-и. Скасування запиту — це навмисний виняток fail-open: медіамости припиняють роботу та очищуються, не відновлюючи сирі медіадані до цілі, про яку відомо, що вона їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) guardrail і
  повторно сортує за зростанням `priority`.
- `clear()` / `list()` — адміністративні допоміжні методи.
- `runPreCallHooks(payload, context)` — перебирає активні guardrail-и, передає
  payload через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на боці відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан і за бажанням
  повторно реєструє guardrail-и за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`,
де `results` — це масив записів `GuardrailExecutionResult`, які містять
поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного guardrail-а,
корисні для трасування.

### Вимкнення guardrail-ів для окремого запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` збирає
дедубльований список імен guardrail-ів, які слід пропустити для поточного
запиту. Існує п'ять каналів, які зчитуються в цьому порядку та об'єднуються в один список
(під час дедублікації перемагає перше входження):

1. `apiKeyInfo.disabledGuardrails`
2. Тіло запиту `disabledGuardrails` (верхній рівень)
3. Тіло запиту `metadata.disabledGuardrails` (лише коли `metadata` є об'єктом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Застарілий заголовок `x-disabled-guardrails`

Усі п'ять каналів об'єднуються, включно з обома заголовками: надсилання обох
`x-omniroute-disabled-guardrails` і `x-disabled-guardrails` пропускає об'єднання
їхніх списків, а порожній сучасний заголовок більше не приховує застарілий
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), виправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значення можуть бути масивами рядків або рядком, розділеним комами; імена обрізаються
та нормалізуються до kebab-case у нижньому регістрі (`pii_masker` → `pii-masker`), а порожні
записи відкидаються. Результат передається через `context.disabledGuardrails`
до реєстру, який пропускає відповідні guardrail-и (`skipped: true` у `results`).

Список вимкнення впливає лише на **реєстр**. Режим `block` захисту від ін'єкцій у промпти — це
обов'язкова межа: middleware injection-guard
(`src/middleware/promptInjectionGuard.ts`) викликає `evaluatePromptInjection()`
без будь-якого контрольованого викликачем списку вимкнення (мертвий виклик
`resolveDisabledGuardrails({ body })`, який він раніше виконував, було видалено в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), тому запит,
який вимикає `prompt-injection`, все одно відхиляється в режимі `block`. Це зроблено
навмисно. Канали вимкнення контролюються викликачем (тіло запиту,
metadata, заголовки), а викликач не повинен мати змоги вимкнути засіб безпеки,
встановлений оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Об'єднання заголовків
з [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
змінює лише те, які guardrail-и реєстру пропускаються; воно не дозволяє клієнту
обійти middleware. Обов'язкові політики guardrail-ів на рівні ключа та групи
відстежуються в RFC v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
Див. [Покриття та обмеження](#coverage-and-limits).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts` (маршрути сімейства chat, перелічені в розділі
[Покриття та обмеження](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` будує список пропусків з API-ключа, тіла
   запиту та заголовків.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускає guardrails у порядку
   зростання пріоритету:
   - Вимкнені guardrails фіксуються як `skipped`.
   - Кожен `preCall` guardrail може перезаписати payload через `modifiedPayload`.
   - Перший `block: true` перериває ланцюжок, і обробник повертає
     відповідь про відхилення guardrail.
3. (Потенційно перезаписаний) payload надходить до combo-маршрутизації та
   відправлення до upstream.
4. **Лише non-streaming:** після складання відповіді
   `guardrailRegistry.runPostCallHooks(...)` запускає той самий ланцюжок на
   відповіді. `block: true` тут відкидає відповідь upstream і повертає HTTP 400. Потокові відповіді повністю пропускають цей крок.

Guardrails, що кидають винятки, фіксуються з `error: <message>` і логуються через
`logger.warn`, але ланцюжок продовжується — fail-open за задумом.

## Покриття та обмеження

Реєстр guardrails підключено лише до chat-конвеєра. Ці обмеження
закріплені в `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` та
`tests/unit/guardrail-pipeline-characterization.test.ts`; оновлюйте ці тести
свідомо, коли поведінка змінюється.

### Де виконуються хуки

| Хук / контроль                      | Виконується на                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runPreCallHooks`                   | Запити, що обробляються `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (та `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*` і Telegram-проксі чату. А також тестовий ендпоінт дашборда `/api/guardrails/test`. Блокування на pre-call повертає HTTP 400. |
| `runPostCallHooks`                  | Лише **non-streaming** chat-відповіді (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). Потокові відповіді ніколи туди не потрапляють.                                                                                                                                                                                                                                                                                        |
| Потоковий PII                       | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`), підключається в `streamingPipeline.ts`, коли ввімкнено `PII_RESPONSE_SANITIZATION`. Це не guardrail, тому канали вимкнення на нього не впливають.                                                                                                                                                                                                                     |
| Middleware injection-guard (legacy) | Кожен `/v1` маршрут, що несе промпт, включно з сімейством chat (див. [покриття маршрутів](#injection-guard-route-coverage--red-team-phase-8--block-d)). Лише prompt injection.                                                                                                                                                                                                                                                      |

### Що не покривається

- **Маршрути медіа, embeddings та даних** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) ніколи не досягають реєстру.
  Там не виконуються ані маскування PII, ані маскування облікових даних, ані
  modality bridge. Їхня єдина перевірка — legacy middleware injection-guard.
- **Потокові відповіді** не отримують post-call guardrails: жодного post-call
  `pii-masker` чи `credential-masker`, жодного post-call блокування. Застосовується лише
  потокове PII-перетворення (коли ввімкнено `PII_RESPONSE_SANITIZATION`). Облікові
  дані, повернені у потоковій відповіді, не редагуються.
- **Канали вимкнення проти middleware (за задумом):** middleware оцінює
  prompt injection власним викликом `evaluatePromptInjection()`, не передаючи
  жодного контрольованого caller'ом списку вимкнень. Режим `block` — це обов'язкова
  межа, яку контрольовані caller'ом вимкнення не можуть обійти, зокрема на маршрутах
  сімейства chat
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Вимкнення
  `prompt-injection` лише пропускає guardrail реєстру.

### Що бачить відповідь до post-call

На non-streaming шляху порядок такий: вилучення пам'яті → виконання вбудованих
інструментів → post-call guardrails → вихід через post-call блок → збереження в семантичний кеш.

- **Витягування пам'яті** та **виконання інструментів** бачать відповідь до того, як пост-викликові
  механізми захисту (guardrails) можуть її переписати або заблокувати. Починаючи з
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), витягування пам'яті
  пропускає витягнутий текст через `sanitizePII`, коли
  `PII_RESPONSE_SANITIZATION` увімкнено (як у потоковому, так і в непотоковому режимі), але
  відповідь, яку пост-виклик пізніше блокує, все одно вже була запропонована пам'яті та
  інструментам.
- **Семантичний кеш** зберігає відповідь після пост-виклику, тому він зберігає
  переписану відповідь, а заблокована відповідь ніколи не кешується. Записи кешу
  прив'язані до ключа API.

Змінні середовища, які зчитуються вбудованими механізмами захисту:

| Змінна                                | Використовується                | Дія                                                                                                           |
| ------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`              | Встановіть `false`, щоб повністю вимкнути виявлення.                                                          |

| `INJECTION_GUARD_MODE`                | `prompt-injection`              | Режим захисту від ін'єкцій; також прапорець функції в БД, який **перевизначає** змінні середовища (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`              | Мінімальний рівень серйозності, який відхиляє `MODE=block`: `high` (за замовчуванням), `medium` або `low`.    |

Механізми захисту Modality Bridge зчитують конфігурацію під час виконання зі
сховища налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` і
`modalityBridgeCacheMaxEntries`. Застарілі ключі
`visionBridge*` приймаються лише як задокументований одноцикловий резервний
варіант читання; записи з панелі керування використовують основні ключі.
Значення за замовчуванням і резолвер резервного варіанту містяться в
`src/shared/constants/modalityBridgeDefaults.ts`, а застарілі константи
збережено в `src/shared/constants/visionBridgeDefaults.ts`.

Audio використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` і `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Audio не має резервного варіанту застарілих
ключів, оскільки ці ключі було запроваджено разом зі схемою Modality Bridge.

Video використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` і
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Воно вимкнено за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а генерація підписів до кадрів додає затримку та
витрати на модель.

## Користувацькі гардрейли

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1. Створіть `src/lib/guardrails/myGuardrail.ts`, що розширює `BaseGuardrail`.
2. Реалізуйте `preCall` та/або `postCall`.
3. Або зареєструйте під час імпорту (додавши в `registerDefaultGuardrails`), або
   викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
   будь-який попередній гардрейл із таким самим нормалізованим ім'ям.
4. Додайте тести в `tests/unit/` (наявні приклади:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб починати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнім реєстром і
зареєструвати лише гардрейли, які тестуються. Vision Bridge підтримує
впровадження залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge
надає еквівалентні точки розширення для налаштувань, можливостей, вибору моделі STT,
перевірки облікових даних і транскрипції. Тому тести можуть проганяти обидва потоки
без доступу до БД чи мережі.

## Покриття маршрутів injection-guard і red-team (Фаза 8 · Блок D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають промпти користувача. Він враховує `INJECTION_GUARD_MODE` (типово `warn` = лише
журналювання; `block` = повертає HTTP 400 `SECURITY_001`).

| Тип               | Маршрути                                                                                                                                             | Типовий режим |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| Текстові (наявні) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| Генеративні       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| Дані              | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

Витягнення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (щоночі, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут
блокує корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає проби
(пропускається без секрету). `moderations` включено для узгодженості. Режим блокування є
обов'язковою межею: `evaluatePromptInjection()` ігнорує список вимкнень на рівні запиту,
який передає йому middleware, тому `disabledGuardrails` **не** звільняє маршрут
від нього ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Нічний workflow (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокувальне)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен адверсаріальний кейс (наприклад, "ignore all
  previous instructions…", джейлбрейки в стилі DAN) перевіряє, що відповідь містить
  `error.code === "SECURITY_001"`, тобто що захист дійсно відхилив запит.
- **`garak` (консультативне)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Виконується лише
  за наявності секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); коректно пропускається
  та має суфікс `|| true`, тому звітує, не провалюючи CI.

Покриття помічника захисту (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що несе промпт; текст промпта витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
функцією `extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
