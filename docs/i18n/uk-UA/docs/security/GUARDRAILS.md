> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-10-17 — v3.8.52 (додано [Покриття та обмеження](#coverage-and-limits):
> які маршрути та шляхи відповідей охоплюють хуки, об'єднані заголовки вимкнення (#16412), режим
> блокування ін'єкцій як обов'язкова межа (#16413) і що бачить відповідь перед post-call)

Guardrails забезпечують безпеку, політики та трансформації вмісту на межі
між OmniRoute та апстрим-провайдерами. Кожен guardrail може інспектувати (і
за потреби відхиляти, трансформувати або анотувати) тіла запитів (`preCall`)
та апстрим-відповіді (`postCall`).

Система працює за принципом **fail-open**: якщо guardrail кидає виняток під час
виконання, реєстр фіксує помилку й переходить до наступного guardrail, а не
провалює запит. Блокування — це явне рішення (`block: true`), а не випадковість.
Єдиний виняток — перерваний запит: коли `signal` викликача переривається,
guardrail, що кинув виняток, відхиляє запуск хука, а не пропускається.

Хуки **не** виконуються на кожному маршруті та не для кожної відповіді. Прочитайте
[Покриття та обмеження](#coverage-and-limits), перш ніж покладатися на guardrail
як на засіб безпеки.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Базова модель GLM 5.3 та `glm-5.3-{low,high,max}` мають явні метадані
`supportsVision:false` у реєстрі/специфікації. Варіанти GLM 5.3 Flash
залишаються моделями з нативною підтримкою зору. Маршрут `/v1/messages` у
Claude Code входить у спільний pre-call ланцюжок guardrail `handleChat`
**до** трансляції Claude→OpenAI; вкладені зображення з результатів інструмента
`Read` мають бути описані або оброблені до того, як ця трансляція перенесе
їх у вміст OpenAI `image_url` (#17069).

Перехоплює запити із зображеннями, спрямовані до **моделей без підтримки
зору**, і або перенаправляє весь запит до моделі з підтримкою зору, або
замінює частини із зображеннями текстовими описами, згенерованими
налаштовуваною vision-моделлю, до апстрим-виклику. Це дозволяє суто текстовим
провайдерам прозоро обробляти мультимодальні корисні навантаження.

Алгоритм:

1. Пропустити, якщо цільова модель уже підтримує зір (якщо вона не входить
   до списку примусового мосту `isVisionBridgeForcedModel`).
2. Витягнути частини із зображеннями через `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), який делегує **уніфікованому детектору
   медіа** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиному
   джерелу істини, спільному з фільтром сумісності комбо.
   Витягнення обмежене списком дозволених форм, які `replaceImageParts` може
   вставити назад (контракт extract↔replace): OpenAI `image_url`, Anthropic
   base64 `source.type:"base64"`, Anthropic URL `source.type:"url"` та
   Responses API `input_image`. Відповідні зображення, вкладені в
   `tool_result.content` Claude Code та у виходи інструментів Responses,
   також витягуються й замінюються на своїх початкових шляхах; форми лише з
   індикаторами — це матеріал для комбо-фільтра, і вони не витягуються.
   Пропустити, якщо нічого не знайдено.
3. Розв'язати конфігурацію середовища виконання через
   `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань
   `modalityBridge*` мають пріоритет; застарілі ключі `visionBridge*`
   залишаються **фолбеком на один цикл** (вікно відкату). Пропустити до
   будь-якого обходу медіа, якщо міст вимкнено.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) вирішує:
   перенаправлення чи опис. Перенаправлення повертає `modifiedPayload` лише з
   підміненим `model`, плюс мета `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити кількість зображень значенням `maxImages`, скласти
   промпт з урахуванням задачі, перевірити кеш описів, викликати vision-модель
   **паралельно** (`Promise.allSettled`) і вставити на їхнє місце текстові
   частини `[Image N]: <description>`. Невдалий опис дає `null`: необроблене
   зображення зберігається для невідомих/vision-сумісних цілей (#4012), але
   **підтверджена суто текстова пряма ціль** або комбо без жодної vision-моделі
   отримує явну текстову заглушку
   `(unavailable — no vision-capable provider connected)` для кожного
   неописаного зображення, включно з частковими збоями та зображеннями понад
   ліміт викликів опису (#17069). Наявний фолбек опису комбо при повному збої
   залишається чинним (#8430).
6. Повернути `modifiedPayload` + мета (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | Типово | Поведінка                                                                                                                                                                                                                                                                                                       |
| ---------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | Успадкована евристика, без змін (#6640/#7204): некомбо/`auto/` моделі перенаправляються на найкращу vision-модель, якщо вихідна модель ще не має придатних облікових даних (тоді describe); комбо-цілі завжди виконують describe.                                                                               |
| `describe` |        | Завжди describe — блок перенаправлення пропускається повністю; обрана користувачем модель завжди відповідає.                                                                                                                                                                                                    |
| `reroute`  |        | Примусове перенаправлення: захист збереження моделі з обліковими даними обходиться. Захист облікових даних **цілі** перенаправлення й надалі діє — коли немає придатної vision-цілі, міст блокує запит зі зрозумілою помилкою замість describe чи надсилання сирих зображень до цілі, що працює лише з текстом. |

Примусові режими переривають ланцюг **до** виконання евристики `auto`; поведінка
`auto` побайтово ідентична захисному механізму до PR-1.

#### Область дії API-ключа (`visionBridgeKeyScope.ts`)

Коли API-ключ викликача обмежує `allowedConnections`, пули квот
(`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), міст обирає лише ті
моделі перенаправлення та describe, які ключ може використовувати, і лише на
з'єднаннях, які ключ може використовувати. Виклик describe тоді завжди проходить
через self-loop OmniRoute із заголовком `x-omniroute-self-loop-key-id`, тож
чат-запит, що його отримує, повторно застосовує політику з'єднань і моделей
цього ключа. `enforceApiKeyPolicy()` враховує цей заголовок лише разом із
bearer-токеном self-loop, тож він може лише звужувати доступ, а ідентифікатор,
який не вдається розпізнати, відхиляється.

Якщо ключу не дозволено жодної vision-моделі, **підтверджена ціль лише для
тексту** відхиляє запит із зображенням локально зі зрозумілою помилкою HTTP 400
замість пересилання байтів зображення до неспроможного апстріму (#17069). Для
цілей із невідомою або вбудованою можливістю зору шлях describe зберігає свою
попередню fail-open поведінку (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запити без ключа та ключі без цих обмежень поводяться так само, як раніше.

#### Describe-промпт з урахуванням завдання (`modalityBridgeVisionTaskAware`)

Типово **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає текст
**останнього повідомлення користувача** (обрізаний до 500 символів) до базового
промпту describe, спрямовуючи опис до того, про що користувач насправді запитав
(патерн codex-vision-proxy), і просить vision-модель транскрибувати видимий
текст. З вимкненим прапорцем — або за відсутності тексту користувача —
використовується базовий промпт без змін.

Власний OpenAI-сумісний запит self-loop describe (`callVisionModelSingle()` у
`visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного викликача/провайдера, не залежачи від жодного
клієнтського сигналу. Обробка з низькою деталізацією погіршує точність OCR саме
для завдання транскрипції тексту, якого вимагає цей промпт, тож виклик describe
завжди запитує високу деталізацію незалежно від того, який рівень деталізації
використовував вихідний вхідний запит. Це впливає лише на тіло внутрішнього
запиту describe; це не змінює те, як OmniRoute пересилає власний
`image_url.detail` викликача в основному запиті — це типове значення
застосовується окремо, і лише для виявлених клієнтів OpenCode, у
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка
мережевого формату Anthropic у self-loop describe не має поля `detail` і не
зазнає впливу жодного з цих типових значень.

#### Обмеження виводу describe (`modalityBridgeVisionMaxChars`)

| Ключ                           | Типово | Діапазон          |
| ------------------------------ | ------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`    | `0` або 100–50000 |

`0` (типово) означає **без обмеження** — опис, повернений
`callVisionModel()`, передається без змін, зберігаючи наявну
поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис із суфіксом
`…` перед тим, як його буде вставлено назад як `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`).
Збільшуйте це значення для насичених деталями завдань OCR, де наступній моделі
потрібна повна транскрипція; зменшуйте його, щоб обмежити використання токенів
на балакучих vision-моделях. Поле панелі керування розташоване на вкладці
Vision у панелі Advanced (`modality-bridge-max-chars` у
`ModalityBridgeVisionTab.tsx`) і підтягує будь-яке значення від 1 до 99 до
нижньої межі 100, залишаючи явний `0` без змін — `0` є коректним значенням Zod
само по собі (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`),
а не лише типовим значенням «не встановлено».

#### Кеш describe (`modalityBridge/bridgeCache.ts`)

Кеш у пам'яті типу LRU + TTL для результатів describe, спільний для всього
процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` з
кадруванням префіксами довжини (без колізій на межах полів). Компонент моделі —
це **налаштована** модель моста, а не модель, що фактично відповіла —
`callVisionModel` може внутрішньо перемикатися на запасну, і ключування за
кожною спробою фрагментувало б кеш. Невдалі describe ніколи не кешуються.
Налаштування:

| Ключ                            | Типово | Діапазон |
| ------------------------------- | ------ | -------- |
| `modalityBridgeCacheEnabled`    | `true` | —        |
| `modalityBridgeCacheTtlMinutes` | `60`   | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`  | 10–5000  |

#### Нормалізація віддалених зображень (self-loop describe/завантаження base64)

Коли міст сам завантажує **віддалене** зображення — self-виклик describe Anthropic та конвертація base64 у форматі claude-wire
(`ensureBase64ImagesForClaudeWire`), обидва через
`fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий data
URI пропускається через `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) перед вбудовуванням у запит до vision-моделі. Надмірно великі зображення зменшуються до **2048px по довгому краю** (відповідно до обмеження розміру, яке OpenAI/Anthropic уже застосовують на стороні сервера), що скорочує обсяг байтів для вивантаження та затримку без зміни того, що бачить vision-модель. Зміна розміру використовує `sharp`, завантажений через динамічний імпорт: на платформі, де його нативний бінарний файл не вдається завантажити, `normalizeDataUri()` **ніколи не генерує виняток** — вона повертається до наскрізної передачі оригінальних байтів, тому шлях describe/конвертації base64 завжди продовжує працювати. Байти, що не є зображенням (завантаження, результат якого не вдалося декодувати як зображення), також передаються без змін. Ця нормалізація охоплює лише зображення, які міст завантажує для власного self-виклику — вона ніколи не застосовується до сирого наскрізного корисного навантаження викликача, відповідно до принципу зміни лише за згодою (Жорстке правило №20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` валідуються Zod у `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, трійка `modalityBridgeCache*` та група
`modalityBridgeAudio*`, яку використовує Audio Bridge. Міграція
`141_modality_bridge_settings.sql` копіює наявні застарілі значення
`visionBridge*` у відповідні нові ключі (ідемпотентно, ніколи не перезаписує
встановлене оператором значення `modalityBridge*`); застарілі ключі залишаються
прийнятними як резервний варіант читання протягом одного циклу релізу.

#### Заголовок прозорості + статистика

Describe-трансформовані відповіді містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створюється `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`,
проставляється `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`).
Перенаправлені запити **не** отримують заголовка — корисне навантаження не
змінювалося, а заміна моделі вже видима в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (management-автентифікація, той самий рівень, що й
`GET /api/settings`) повертає внутрішньопам'ятні лічильники за модальністю
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та
`video`. `averageLatencyMs` використовує як знаменник `latencySamples`, а не всі
спроби; операція без вимірювання часу не фабрикує нуль-мілісекундний
зразок. `bridged` залишається зворотно сумісним псевдонімом успішних
конверсій; невдалі спроби його не збільшують.
Лічильники скидаються при перезапуску процесу за задумом
(телеметрія, а не облік).

#### Конфігурація дашборда

Виділена сторінка дашборда —
`/dashboard/settings/modality-bridge`. Її URL-адресовані вкладки `Vision`, `Audio`
та `Video` зберігають параметри запиту при перемиканні значення `tab`.
Вкладка Vision надає ввімкнення, режим, вибір моделі (включно з автоматичним
значенням за замовчуванням), task-aware-промптинг, розширені ліміти таймауту/зображень/довжини опису/кешу, лічильники
виконання та захищений зразковий запит. Вкладка Audio також активна: вона надає
ввімкнення, вибір лише STT-моделей з Auto, ліміти таймауту/максимального кліпу, аудіолічильники та зразковий тест `input_audio`. Вкладка Video функціональна: вона повідомляє
стан середовища виконання FFmpeg/ffprobe — один із чотирьох явних станів UI (`unknown`, поки
перевірка триває або не змогла завершитися, `restricted` на не-loopback
хості дашборда, де перевірка пропускається на стороні клієнта, `unavailable` після перевірки
та підтвердження відсутності, або `available` з версіями FFmpeg/ffprobe) — зберігає
ліміти ввімкнення/моделі/кадрів/відео/таймауту, фільтрує вибір моделей до сумісних із vision
моделей та надає відеолічильники.

Колишня картка Vision Bridge в налаштуваннях AI — це посилання сумісності на
нову сторінку; вона більше не містить другої копії форми. Media Providers також
пов'язує робочі процеси Image-to-Text та Speech-to-Text з відповідними вкладками Modality
Bridge, не видаляючи наявний майданчик Speech-to-Text.

**Обхід допуску self-loop:** коли виклик describe маршрутизується через власний
self-loop `/v1` OmniRoute (нестандартна модель провайдера), підзапит надсилає
`x-omniroute-admission-bypass: internal` і автентифікується з розв'язаними
обліковими даними self-loop — локальним маркером `sk_omniroute` у локальному режимі або
налаштованим оператором ключем середовища `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб
розгортання з `REQUIRE_API_KEY=true` усе ще могли виконувати виклик describe. Обхід
визнається лише для цих конкретних облікових даних, тому зовнішні клієнти не можуть використовувати
заголовок для пропуску допуску.

Застарілі значення за замовчуванням знаходяться в `src/shared/constants/visionBridgeDefaults.ts`;
нові значення за замовчуванням режиму/task-aware/кешу та розв'язувач налаштувань знаходяться в
`src/shared/constants/modalityBridgeDefaults.ts`. Guardrail надає
опцію конструктора `deps`, щоб тести могли впроваджувати фейкові реалізації `getSettings` та
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює чат-запити, що містять аудіо, перш ніж вони досягнуть цілі, для якої
невідомо, що вона приймає аудіовхід. Він ніколи не перенаправляє чат-запит: аудіочастини
транскрибуються через наявний OpenAI-сумісний multipart-ендпоінт, а
обрана чат-модель продовжує роботу з текстовими транскриптами.

Потік:

1. Розв'язує `supportsAudio` через `getResolvedModelCapabilities()`. Пріоритет мають явні метадані реєстру провайдерів, далі статичні метадані моделі, потім синхронізовані `modalities_input`. Оголошений список входів без `audio` дає `false`; за відсутності доказів можливості залишається `null`. І `false`, і `null` активують консервативний міст, тоді як `true` обходить його.
2. Розв'язує налаштування `modalityBridgeAudio*` та витягує придатні для вирізання аудіочастини верхнього рівня з кожного повідомлення через спільний детектор `detectMediaParts()`. Підтримувані формати передачі: OpenAI `input_audio`, `audio_url` та `source.media_type: "audio/*"`. Вкладене аудіо виявляється для маршрутизації, але не видаляється шляхом вирізання. Обсяг роботи обмежено `modalityBridgeAudioMaxClips`; наступні частини залишаються недоторканими.
3. Дотримується налаштованого `provider/model` або дозволяє `selectAudioBridgeModel()` пройти `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та вибрати першу модель із придатними активними обліковими даними провайдера.
4. `callAudioTranscription()` перетворює аудіо base64/data-URI на multipart-`file` або завантажує віддалений `audio_url` через захист вихідних з'єднань лише до публічних адрес із DNS-закріпленням і межею 25 МБ. Потім він надсилає POST-запит із файлом і вибраною моделлю до локальної самопетлі `/v1/audio/transcriptions`, автентифікованої за допомогою `resolveSelfLoopBearer()`. Існуючий маршрут транскрипції виконує звичайний пошук облікових даних, обробку cooldown/обмеження швидкості та відправлення провайдеру.
5. Успішні виклики замінюють свої частини на `[Audio N]: <transcript>`. Виклики виконуються з `Promise.allSettled`: окрема невдача зберігає відповідну оригінальну аудіочастину (контракт #4012). Якщо всі виклики невдалі та доведено, що ціль має `supportsAudio === false`, частини стають `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для невідомої цілі (`null`) результат із усіма невдачами залишається недоторканим. Доведена текстова ціль без придатних облікових даних STT отримує таку саму явну заглушку без виконання мережевого виклику.

Успішні транскрипти використовують загальнопроцесний LRU/TTL-кеш моста модальностей. Ключ поєднує посилання на аудіо, стабільну мітку операції `audio-transcription` та вибрану STT-модель; невдачі ніколи не кешуються. Аудіоспроби оновлюють спільні лічильники `bridged`, `cacheHits`, `failures` і `lastUsedAt`. Перетворені відповіді містять `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; недоторкані запити не отримують сегмента аудіомоста.

Налаштування виконання зберігаються в базі даних і валідуються Zod:

| Ключ                          | Типово  | Діапазон        |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | Авто або STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

Спільний кеш і надалі контролюється `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.

### Відеоміст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює відеочастини верхнього рівня в `messages` Chat Completions та `input` Responses API перед викликом цілі без відомої нативної підтримки відео. Підтримувані форми: `input_video`, `video_url`, `video_source`, HTTPS-URL та data-URI `data:video/*;base64,...`. Звичайні імена файлів у тексті не вважаються відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запиту, перевірку можливостей/політики, агрегацію в межах запиту та корисне навантаження відповіді. Робота над кожним відео — отримання, кеш цілісного результату, опис послідовності кадрів (який об'єднує будь-який оголошений викликачем аудіотранскрипт) та метрики/переривання/очищення кожної спроби — прихована за `processVideoPart` у `videoBridgePipeline.ts`, що викликається один раз на відеочастину всередині циклу `preCall`. Цей модуль також визначає явні межі портів: `VideoMediaBrokerPort` (отримання байтів і витягнення вибіркових кадрів), `VideoAudioTranscriptionPort` (об'єднання оголошеного викликачем аудіотранскрипту з підписами вибіркових кадрів) та `VideoDrilldownPort` (межа збереження деталізації кадрів; ще не під'єднана до `processVideoPart` — наразі лише окремий маршрут `/api/modality-bridge/video/drilldown` записує записи деталізації).

Публічний шлях запиту `/v1` ніколи не імпортує й не викликає підпроцес. Віддалені відео завантажуються з межею 50 МіБ; вбудовані base64-відео мають консервативне обмеження 36 МіБ декодованого розміру на відео, щоб оболонка моделі/повідомлень/форматування залишалася в межах публічної межі допуску JSON-запитів у 50 МіБ. Оцінки вбудованої довжини та декодованого розміру перевіряються перед виділенням пам'яті. HTTPS обов'язковий для початкового віддаленого URL і кожного перенаправлення, з використанням існуючого захисту вихідних з'єднань лише до публічних адрес із DNS-закріпленням. Далі байти перетинають точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`. Цей маршрут є одночасно `LOCAL_ONLY` і `SPAWN_CAPABLE`, приймає лише автентифікований у межах процесу запит із довіреного loopback і ніколи не приймає URL, шлях у файловій системі, виконуваний файл або список аргументів. Конвеєр розміру тіла API та інкрементальний зчитувач тіла обробника незалежно забезпечують обмеження вхідних даних брокера 50 МіБ. Його обмежена черга виконує одне витягнення за раз, допускає чотири завдання в очікуванні та обмежує вхідні дані в очікуванні 100 МіБ.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований список дозволених форматів виключає формати списків відтворення та маніфестів. Для дозволених контейнерів родини MOV зовнішні посилання на дані MOV залишаються вимкненими за замовчуванням, і фіксована команда не вмикає їх. І `ffprobe`, і `ffmpeg` використовують білий список протоколів лише `file`, один потік, фіксовані масиви аргументів, без оболонки, а виконувані файли розв'язуються з `PATH`. Потоки обкладинок із прикріпленими зображеннями не є кандидатами на відтворення. Усі відтворювані потоки мають відповідати обмеженням, і явно заданий потік за замовчуванням має перевагу перед детермінованим резервним вибором потоку з найменшим індексом. Відео обмежені 600 секундами, 8,192 пікселями на вимір і 33,554,432 вихідними пікселями. FFmpeg відбирає 1–16 кадрів JPEG із середніх точок, зменшує довгий край щонайбільше до 1,024 пікселів без збільшення менших вхідних даних і ніколи не отримує URL. За замовчуванням вибірка — `uniform`. Необов'язкова політика `scene_aware` та експериментальна політика `segment_aware` виконують один додатковий фіксований прохід FFmpeg над уже перевіреним локальним потоком, вибирають обмежені часові мітки сцен `showinfo` і детерміновано повертаються до тих самих рівномірних середніх точок у разі збою детектора, тайм-ауту, некоректного виводу або порожнього набору кандидатів. Режим з урахуванням сегментів розподіляє вибірки середніх точок пропорційно до перевірених інтервалів сцен; докази та резервна поведінка режиму з урахуванням сегментів детально описані нижче. Жорстке обмеження в 16 кадрів застосовується після вибору в кожній політиці. Коли запит з урахуванням сцен має бюджет лише в один кадр, використовується рівномірна середня точка активного вікна повного відео або фокусного вікна, і повідомляється `policyEffective: uniform`: один вибраний кадр сцени не може зберегти обидва часові кінці. Викликач може за бажанням надати скінченне фокусне вікно (секунди `start`/`end`); межі обрізаються до тривалості медіа, перевернуті або нескінченні вікна відхиляються, і всі політики вибірки виконуються лише всередині нормалізованого інтервалу. Отримане вікно включається в метадані вибірки та в префікс недовіреного опису, щоб подальші моделі могли відрізнити сфокусований уривок від повної часової шкали.

Семантичний фокус підписів — це окреме явне налаштування. Типовий режим аналізу `full` зберігає наявний запит кадрів і ніколи не пересилає текст запиту до моделі підписів. У режимі `focused` міст читає лише останній непорожній створений користувачем `text`/`input_text` з того самого контейнера Chat або Responses, нормалізує його до NFC, згортає керівні символи та пробіли й обмежує його 500 кодовими точками Unicode. Порожній результат повертається до точного запиту `full`. Придатна підказка серіалізується як JSON у спеціальному блоці недовіреного контексту користувача й може лише надавати пріоритет спостережуваним деталям; вона не може перевизначити окреме попередження про заборону виконання інструкцій, видимих або чутних у медіа. Текстовий фокус ніколи не виводить `start`/`end` і не змінює часовий семплер.

#### Структурні докази сегментів FU-07

`segment_aware` використовує один обмежений прохід попереднього аналізу над уже перевіреним локальним відеопотоком. Фіксований ланцюжок фільтрів спочатку масштабується щонайбільше до 320 пікселів завширшки, виявляє зміни сцен і заморожені інтервали, а потім виконує вибірку зі швидкістю 1 кадр за секунду для розмиття, середньої яскравості та просторової/часової інформації. Прохід обмежений 600 структурними вибірками, одним потоком FFmpeg/фільтра, тими самими списками дозволених протоколів лише `file` і контейнерів, межею виводу процесу в 1 МіБ і щонайбільше 30 секундами в межах спільного переривання/дедлайну брокера. Він ніколи не приймає команду, фільтр, шлях або URL із запиту.

Структурні значення — це детерміновані докази вибірки, а не семантичне розуміння відео. Вони не виводять суб'єктів, дій, підписів, мовлення чи намірів користувача. Межі сцен і заморожувань утворюють сегменти; покриття заморожування, розмиття, експозиція, просторова деталізація та часові зміни лише впливають на те, як розподіляється наявний бюджет у 1–16 кадрів. Повністю заморожений сегмент обмежується одним кадром, тоді як незаморожені сегменти змагаються за решту бюджету. Коли меж більше, ніж кадрів, зберігається рівномірне покриття часової шкали, щоб швидкі ранні склейки не могли приховати довгий завершальний сегмент. Межі сцен у межах 1-секундної роздільної здатності аналізу від межі заморожування об'єднуються.

Відсутні фільтри, некоректні/порожні докази, помилка детектора або обмежений тайм-аут попереднього аналізу спричиняють відкритий збій із поверненням до точної політики рівномірних середніх точок. Переривання викликачем або дедлайн брокера не спричиняє відкритого збою: це завершує активний підпроцес, запобігає подальшому вилученню кадрів, а приватне тимчасове дерево видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні фікстури FFmpeg для заощаджень на викликах підписів після дедуплікації, розподілу бюджету для щільного руху, доказів розмиття/експозиції/SI-TI, швидких склейок із довгим хвостом та хибнопозитивних спрацьовувань поступового затухання. Він записує астрономічний час попереднього аналізу та, де доступний `/usr/bin/time`, час CPU дочірнього процесу й піковий RSS. Його перевірки якості — лише структурні оракули. Реальна якість моделі підписів залишається `HOLD`, оскільки ця обв'язка не має авторизованої кінцевої точки або замороженого судді. Грошові заощадження також залишаються `HOLD`, якщо `--caption-cost-per-call-usd` не надає явної додатної оцінки вартості за виклик; скрипт ніколи не вигадує жодного з цих результатів.

Кожен кадр обмежено 4 МіБ, усі необроблені кадри разом — 23 МіБ, а серіалізовану відповідь брокера — 32 МіБ. Приватний тимчасовий каталог видаляється у `finally`. OmniRoute не постачає FFmpeg у комплекті й не приймає власний шлях до виконуваного файла. Перед створенням підписів міст виконує консервативний прохід візуальної дедуплікації: кожен JPEG зменшується до буфера відтінків сірого 16×16 і порівнюється лише з останнім збереженим кадром. Для запитуваного бюджету підписів понад один кадр видобування надає обмежений пул кандидатів розміром до подвійного бюджету й ніколи не більше 16 кадрів. Запитуване обмеження застосовується лише після дедуплікації, при цьому перший і останній вибрані кандидати зберігаються під час фінального проріджування, коли бюджет становить щонайменше два. Версіонована політика `grayscale-16x16-mean-cells-v2` використовує більше з двох значень: середню дельту яскравості та частку комірок мініатюри, чия нормалізована дельта становить щонайменше 0.05. Поріг дубліката — константа 0.04, обрана заради передбачуваності, а не винесена як параметр часу виконання. Цей вторинний висококонтрастний сигнал зберігає дрібний рух і зміни видимого тексту, які може приховати порівняння лише за середнім значенням. Помилки компаратора чи декодера не блокують обробку (fail open) і зберігають покриття. Вихідні метадані розділяють видобутих кандидатів, успішно використані кадри та відкинуті візуальні дублікати.

Явно позначена відеочастина може запитувати контактний аркуш із позначками часу. Міст будує щонайбільше 4-стовпчикову JPEG-сітку з 16 кадрів. Кожна 512-піксельна комірка впечатує свою вихідну позначку часу у висококонтрастну нижню смугу, тоді як ті самі позначки часу залишаються в текстових метаданих для подальшої асоціації та аудиту. Повний JPEG залишається обмеженим 32 МіБ. Якщо `sharp` не може декодувати або скласти сітку, міст повертається до окремих кадрів JPEG; скасування клієнтом усе одно поширюється крізь операцію з аркушем.

Докази просування свідомо відокремлені від синтетичного мікробенчмарку композиції. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає версіонований за схемою A/B-стенд для реальних OpenAI-сумісних моделей бачення. Він вимірює токени, звітовані провайдером, наскрізну реальну затримку (включно зі складанням аркуша), кількість викликів моделі та утримання фактів, визначене маніфестом. Необроблені відповіді моделі не записуються у звіт; зберігаються лише дайджести SHA-256 і зіставлені ідентифікатори фактів. Стенд не виконує жодних мережевих чи платних викликів моделі, доки не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без цього явного реального запуску його машиночитаний вердикт залишається `HOLD`; самі по собі синтетичні вимірювання корисного навантаження/кількості викликів не є доказами просування.

Викликачі можуть долучати необов'язковий масив `transcript.cues` до підтримуваної відеочастини, коли вже мають вирівняний текст. Кожна репліка має містити `text`, скінченний інтервал `start`/`end` у межах тривалості, встановленої зондуванням, та внесений до білого списку `source` (`client`, `embedded` або `audio-bridge`); `confidence` за замовчуванням дорівнює `1` і має залишатися між `0` і `1`. Точні дублікати реплік згортаються. OmniRoute ніколи не запускає транскрипцію з цих метаданих: перевірені репліки копіюються в результат опису з джерелом, впевненістю та інтервалом і відображаються як недовірені спостереження поряд із підписами кадрів. Недійсний, позадіапазонний або позбавлений походження текст відхиляється, а не змішується з потоком підписів. Обидва канали транскрипту тіла запиту нормалізують надане походження до `client`, включно з самопроголошеними мітками `embedded` або `audio-bridge`. Лише серверний адаптер може призначати ці довірені мітки через доступний лише в коді аргумент `trustedSource`; поле JSON запиту не може досягти цього аргументу. Текст транскрипту залишається недовіреним вмістом, отриманим із медіа, незалежно від його походження, і ніколи не повинен визначати авторизацію.

Просунутий викликач може надати доріжку `audioTranscript` для того самого відео; вона розглядається як наданий клієнтом текст, а не доказ серверної транскрипції. Шов злиття запускає візуальні та аудіоспостереження під спільним граничним строком і сигналом скасування, упорядковує їх на спільній часовій шкалі, згортає точні дублікати та повідомляє частковий результат, коли успішна лише одна сторона. Недійсний `audioTranscript` деградує до цього часткового результату — візуальний опис зберігається, а аудіогілка фіксує очищений код збою — замість збою всього відео. Доступність за гілками, прапорець частковості та очищені коди збоїв зберігаються в результаті опису, в метаданих запобіжника (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), в метаданих кешу результатів і в лічильниках злиття моста. Стандартний шлях Video Bridge не викликає перетворення мовлення в текст і не завантажує другу копію медіа; без цієї явної доріжки він залишається лише відео.

**Зберігання транскриптів (#12150 P1).** Це застосовується автоматично щоразу, коли
Video Bridge (який сам потребує явного ввімкнення) відтворює репліку транскрипту — окремого
прапорця зберігання немає. Коли запит відтворює будь-яку репліку транскрипту (оголошений викликачем
`transcript` або об’єднаний `audioTranscript`), захисний механізм позначає його як
`videoBridgeObserved` і створює редаговану тінь опису відео —
ідентичне представлення, у якому довільний текст кожної репліки замінено на
`[redacted-video-transcript]`; воно створюється шляхом підстановки в структуроване поле репліки
до формування рядка (і ніколи — шляхом розбору зведеного тексту, тому жоден вміст репліки —
зловмисний чи звичайний, включно з текстом, що містить `]`, як-от
`[inaudible]`/`[music]`, — не може зберегтися). У збереженому тілі запиту журналу викликів
кожна похідна від відео текстова частина замінюється цією редагованою тінню зі
зіставленням за рівністю вмісту; прив’язка `fullText` повторно зчитується із завершеного
корисного навантаження захисного механізму перед викликом, тому зіставлення й надалі виконується після того, як наступні
захисні механізми ланцюжка (маскувальники персональних даних і облікових даних із пріоритетами 10/95) змінюють текст опису на місці, а також
після того, як ін’єкція системного запиту, передавання контексту чи пам’яті змінює форму масиву повідомлень. Тіло,
надіслане моделі, не змінюється. Спостережуваний запит також не заповнює
довготривалу Memory (вилучення даних як із запиту, так і з відповіді пропускається),
тому власна відповідь моделі не може відтворити текст транскрипту в Memory.

**Необроблені поля відео (#12430).** Коли міст увімкнено, а вбудована підтримка відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після помилки опису або досягнення обмеження `maxVideos`. `null` і порожні рядки враховуються; відсутні поля та метадані, не пов’язані з відео, — ні. У збережених копіях ці поля редагуються або запит пропускається, а кеші/Memory обходяться.

На цих резервних шляхах коректні репліки, надані викликачем, перетворюються на підтримувані частини `text`/`input_text`,
а не на нестандартні поля провайдера. Обидві надані в запиті доріжки
залишаються недовіреними спостереженнями `client` із явним попередженням про те, що відео
не було описано, а часові позначки не було звірено з медіаданими. Наявні
обмеження у 256 реплік/64 КіБ загалом і на одну репліку застосовуються до обох доріжок разом;
часові позначки мають вкладатися в 600-секундну межу брокера та будь-яке надане
вікно фокуса. Некоректні доріжки відкидаються, а не пересилаються як довільний текст; коректна
сусідня доріжка все ще може використовуватися, якщо не перевищено їхній сукупний бюджет. Null/порожні
поля не додають тексту. Цей резервний механізм не додає отримання медіаданих або транскрибування.
Поля розширення транскрипту видаляються з резервного носія відео та його
об’єктів `video_url`/`source`. Суворий список дозволених полів OpenAI не змінюється; носії відео
з невідомою вбудованою підтримкою залишаються доступними, а відомі цільові системи лише з текстовою підтримкою зберігають безпечні маркери.
Структуровані редаговані тіні захищають доданий текст транскрипту, тоді як
оригінальний запит викликача залишається незміненим. Цільові системи з вбудованою підтримкою та
вимкнені мости зберігають наявну поведінку обходу.

Додаткові збережені копії використовують той самий сигнал спостережуваного запиту. У необробленому
знімку клієнтського запиту до застосування захисного механізму, очікуваному запиті в пам’яті та ранньому
журналі відхиленого запиту поля транскрипту в частинах відео замінюються структурно;
рядкові запити, синтезовані етапами конвеєра та передаванням контексту, редагуються
в точці збереження тіла запиту. Збережений маркер `video_content_removed`
змушує продовження через `previous_response_id` завершуватися безпечною відмовою замість відновлення
тексту, який було навмисно видалено. Якщо спостережуваний запит втрачає свою
редаговану тінь для окремої частини до журналювання або якщо хоча б одна з кількох тіней відео
не збігається після наступних змін запиту, збережене тіло запиту
повністю пропускається замість збереження частково відредагованого транскрипту.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину
транскрипту без структурованої межі репліки. Тому її збережений у журналі викликів
`responseBody` замінюється маркером пропуску; докладний
артефакт конвеєра (який може містити тіла обміну з постачальником/клієнтом і фрагменти потоку)
не зберігається. Семантичний кеш, кеш ідемпотентності та кеш повторного відтворення міркувань
обходять читання й запис для такого запиту. Запит до провайдера та видима клієнту
відповідь залишаються незміненими. Ранні байти підтримання з’єднання видаляються з тимчасового
буфера, коли докладний артефакт пропускається. Попередження Kiro про некоректний EventStream
повідомляє лише кількість байтів корисного навантаження, але ніколи не його вміст або необроблену помилку
JSON-парсера.
Це не означає, що було перевірено кожну не пов’язану з цим діагностику провайдера/плагіна;
ширше охоплення точок збереження відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою,
автентифікованою через loopback/токен кеш-підсистемою. Кожна операція також потребує
канонічного непрозорого ідентифікатора суб’єкта. Перш ніж активувати робочого викликача, він має
виводити цей ідентифікатор з автентифікованого орендаря та ніколи не пересилати
значення, вибране клієнтом. Ключі кешу прив’язують цього суб’єкта до канонічних ідентифікаторів
сеансу та посилання на відео, зберігають лише похідні від них ключі SHA-256 і обмежують як читання,
так і видалення тим самим суб’єктом. Кеш зберігає щонайбільше 16 похідних JPEG-кадрів
на запис, видаляє їх через десять хвилин і підтримує обмежене читання
`start`/`end` або явне видалення сеансу.

Кожен суб’єкт обмежений 16 записами та 64 МіБ канонічних даних JPEG. Ці
обмеження не залежать від глобальної межі в 64 записи/256 МіБ: тиск квоти суб’єкта
витісняє лише найдавніше використані записи цього суб’єкта, перш ніж розглядатиметься
глобальне витіснення LRU. Прострочені записи видаляються як з обліку суб’єкта, так і з
глобального обліку під час активності кешу, тоді як скасування та помилка перевірки
не фіксують часткову заміну.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, не-JPEG медіа, пошкоджені або
обрізані JPEG-файли, а також JPEG-файли, які видають попередження під час обмеженого
повнокадрового декодування через `sharp`. Він перекодовує кожне прийняте зображення в
канонічний JPEG, виводить ширину та висоту з декодованих байтів замість довіри до полів
викликача і відкидає будь-які кінцеві поліглотні байти, а не зберігає їх. Лише обмежений
канонічний стиснений буфер зараховується в обидві квоти. Обмеження JSON-передачі включає
накладні витрати Base64 для стелі декодованого вводу в 32 MiB. Кожне
збережене похідне записує свій підтверджений формат/роздільну здатність JPEG, політику
семплювання, версію похідного, час створення, обчислений сервером хеш вмісту, а також
хешоване посилання на батьківський елемент плюс хеш батьківського вмісту довіреного
викликача. Скасування перевіряється між асинхронними фазами декодування/хешування перед
атомарним комітом кешу.

Цей транш ще не підключає продакшн-виробника до маршруту і не забезпечує вибір варіантів
із кількома роздільними здатностями. Прозорий шлях запиту Video Bridge тому не зазнає
додаткової роботи, тоді як деривація принципала, прив'язаного до тенанта, та повний
життєвий цикл FU-08 із кількома роздільними здатностями залишаються явно запланованою
подальшою роботою, а не задокументовані як завершена поведінка.

Кадри описуються послідовно налаштованою моделлю Video. Порожнє перевизначення Video
успадковує налаштування Vision; якщо обидва порожні, автомаршрутизатор Vision обирає
ефективну модель із підтримкою зору. Успішні описи замінюють оригінальну частину
стабільним префіксом `[Video description:`, який також позначає текст як недовірене
спостереження, отримане з медіа, і вказує наступним моделям не виконувати інструкції,
знайдені в медіа. Ключі кешу описів кадрів включають байти JPEG, промпт, мітку часу та
ефективну модель; кешуються лише успішні описи. Записи кешу зберігають фактичну успішну
модель-виробника, включно з резервною моделлю; міст повідомляє `mixed`, коли різні кадри
були створені різними моделями. Влучання в кеш повторно використовує цю ідентичність
виробника замість перейменування її на запитаний план маршрутизації. Кеш результатів
цілого відео ключується за кожним входом, що змінює вихід, — промптом, ефективною
моделлю, політикою семплювання, кількістю кадрів, режимом семантичного аналізу, відбитком
SHA-256 нормалізованої підказки фокуса, вікном фокуса, `transcript`, `audioTranscript` та
прапорцем контактного аркуша — тому зміна будь-якого з цих вимірів є промахом кешу, а
ніколи не застарілим повторним використанням. Версія політики візуальної дедуплікації,
поріг та обмежена кількість кадрів-кандидатів також явно вказані в ключі кешу результатів
і метаданих; зміна політики тому не може повторно використати застарілий опис цілого
відео. Метадані кешу результатів v4 зберігають режим і відбиток, ніколи — сире завдання
користувача. Метадані guardrail повідомляють як запитаний, так і ефективний режими
аналізу; запитаний режим `focused` без придатного тексту користувача повідомляється як
фактично `full`.

Guardrail витягує кожну підтримувану відеочастину, але описує не більше ніж
`modalityBridgeVideoMaxVideos`. Для цілі, для якої доведено
`supportsVideo === false`, невдалі та надлімітні відео стають явними безпечними
текстовими маркерами, тож жодне сире відео не залишається. Коли можливість невідома, ці
частини зберігають свій відеоносій; будь-який резервний транскрипт проходить обмежене
перетворення тексту, описане вище. Цілі з `supportsVideo === true` обходять міст.
Сигнал переривання запиту клієнта поширюється крізь завантаження, чергу брокера,
підпроцеси та виклики створення описів; переривання зупиняються між відео і ніколи не
пропускають сире медіа у разі збою.

Налаштування середовища виконання зберігаються в БД і валідуються Zod:

| Ключ                                | За замовчуванням | Діапазон / поведінка                                                                                         |
| ----------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------ |
| `modalityBridgeVideoEnabled`        | `false`          | Необов'язкове середовище виконання, вмикається явно                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`         | `full` зберігає загальні описи; `focused` використовує обмежений недовірений контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`             | Успадковує модель Vision Bridge                                                                              |
| `modalityBridgeVideoFrameCount`     | `8`              | 1–16                                                                                                         |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`      | `uniform`, `scene_aware` або пропорційний `segment_aware`; збій детектора повертає до `uniform`              |
| `modalityBridgeVideoMaxVideos`      | `1`              | 1–4                                                                                                          |
| `modalityBridgeVideoTimeout`        | `120000`         | 1000–120000 мс                                                                                               |

Застарілі збережені значення таймауту Video понад 120 секунд обмежуються дедлайном
брокера; нові записи налаштувань понад цей ліміт відхиляються.
`GET /api/modality-bridge/video/runtime` вимагає довіреної промаркованої локальності
loopback перед автентифікацією або зондуванням середовища виконання, а потім вимагає
автентифікації керування. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та
фіксовану причину, коли середовище виконання недоступне. Внутрішня кінцева точка
витягування не є публічним API завантаження: насичення черги повертає `503` плюс
`Retry-After`, відключення викликача повертає `499`, а фіксований дедлайн брокера повертає
`504`. Конвертовані відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до центрального заголовка
`x-omniroute-modality-bridge` без видалення сегментів Vision або Audio.

### PII Masker (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує payload, проходить по `system`, `messages`, `input` та
  `prompt` (включно з простими рядковими елементами) і застосовує `processPII()` (зі
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII маскуються у вихідному
  payload. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою щодо prompt-ін'єкцій). Коли маскування вимкнено, виклик лише
  фіксує лічильники виявлень, не переписуючи вміст.
- **`postCall`** глибоко клонує відповідь, запускає `sanitizePIIResponse()` разом
  із маскувальником форми Responses API (`maskResponsesOutput` — охоплює
  `output_text` та `output[].content[].text`). Якщо відбулося хоч якесь маскування,
  змінена відповідь замінює оригінальну.

Guardrail ніколи не блокує; він лише анотує (`meta.detections`,
`meta.redacted`) або переписує.

#### Вибір за типами, власні шаблони та лічильники виявлень

**Дашборд → Налаштування → Безпека → Маскування PII** визначає _що_ маскується.
Цей розділ не вмикає маскування: це як і раніше роблять `PII_REDACTION_ENABLED`
(запит) та `PII_RESPONSE_SANITIZATION` (відповідь + SSE), обидві вимкнені за
замовчуванням.

- **Вибір за типами** — вбудовані ідентифікатори перелічено в
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Якщо значення не задано,
  діють усі типи (поведінка, що існувала до появи цього налаштування). Шаблон
  `ssn_us` рушія запитів відповідає `ssn`. Шаблони (Minimal, Standard, Financial,
  Brazilian, USA, Full) лише заповнюють прапорці в інтерфейсі.
- **Власні шаблони** — до 20 регулярних виразів або шаблонів із підстановними
  знаками (`*` = до 64 непробільних символів, `?` = один). Збіги замінюються на
  `[CUSTOM_REDACTED]`. Кожен шаблон проходить через `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): щонайбільше 500 символів, прапорці
  обмежено до `g i m s u`, шаблон має компілюватися, проходити перевірку
  `safe-regex` (катастрофічний бектрекінг) і не повинен збігатися з порожнім
  рядком або із заповнювачем маскування. Шаблон, що не проходить перевірку,
  відхиляється під час збереження та тестування, а збережений рядок, який не
  проходить, пропускається під час виконання замість компіляції. Власні шаблони
  працюють лише за увімкненого маскування.
- **Лічильники виявлень** — кількості за типами (ніколи не самі знайдені
  значення), що зберігаються в пам'яті й скидаються під час перезапуску
  (`src/lib/pii/piiDetectionStats.ts`). Вони зростають лише за увімкненого
  маскування.

Налаштування зберігаються в таблиці `key_value` (простір імен `pii_settings`,
`src/lib/db/piiSettings.ts`) і читаються через кеш на 1 с. API:

| Метод  | Шлях                     | Призначення                                                             |
| ------ | ------------------------ | ----------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Стан прапорців, `enabledTypes`, `customPatterns`, лічильники виявлень   |
| `PUT`  | `/api/settings/pii`      | Замінює `enabledTypes` (`null` = усі) та/або `customPatterns`           |
| `POST` | `/api/settings/pii/test` | Пробний запуск одного шаблону на зразку до 8 КБ; нічого не зберігається |

Усі три вимагають автентифікації з правами керування та валідують тіло за
допомогою Zod (`src/shared/validation/schemas/piiSettings.ts`).

### Prompt-ін'єкції (`promptInjection.ts`)

Виявляє ворожі структури у вмісті, наданому користувачем, і застосовує
налаштовану політику. Поведінка визначається змінними середовища та параметрами
конструктора:

| Налаштування     | Змінна середовища                                                                                       | За замовчуванням | Ефект                                                                                                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                               | `true`           | Якщо `false`, guardrail одразу завершує обробку.                                                                                                                                                     |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                         | `warn`           | Політика щодо ін'єкцій: `block`, `warn` або `log`. (`redact` приймається для зворотної сумісності, але **не** видаляє текст ін'єкції; переписування PII у запиті керується `PII_REDACTION_ENABLED`.) |
| Поріг блокування | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (аліас `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальна серйозність, необхідна для блокування. За замовчуванням рівень medium лише спостерігається.                                                                                               |

**Пріоритет режимів** (`getMode`): `options.mode` викликача →
`INJECTION_GUARD_MODE` **перевизначення через прапорці функцій у БД** (Дашборд →
Налаштування → Прапорці функцій) → env `INJECTION_GUARD_MODE` → env
`INPUT_SANITIZER_MODE` → `warn`. Отже, перевизначення з дашборда має пріоритет
над змінними середовища, тож інтерфейс прапорців функцій керує працюючим
guardrail наживо (без перезапуску). Читання з БД є відмовостійким: у разі
помилки guard повертається до поведінки на основі змінних середовища, а коли
перевизначення не задано, поведінка ідентична розв'язанню лише через env.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір
   детекторів, що використовується в інших місцях конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` та
   `markdown_system_block`, обидва з серйозністю `high`).
3. Необов'язкові `customPatterns`, передані через параметри конструктора
   (рядки, регулярні вирази або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення досягає порогу
серйозності, `preCall` повертає `{ block: true, message: "Request rejected:
suspicious content detected" }`. У режимах `warn`/`log` ґардрейл лише логує,
але дозволяє виклик. Спільний хелпер `evaluatePromptInjection()` також
експортується для викликачів, яким потрібно оцінювати промпти без звернення
до реєстру.

**Межа сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об'єднаного тексту промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024`
(16 384 байти) у `src/shared/utils/inputSanitizer.ts`. І `detectInjection()`,
і `evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)`
перед запуском циклу шаблонів. Директиви ін'єкції зазвичай розташовані біля
початку введення, тож це обмежує навантаження regex на CPU/GC для пейлоадів
завбільшки у сотні кілобайт без послаблення виявлення (див. #3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Працює на **обох** етапах, останнім у стандартному ланцюжку (пріоритет `95`).
Маскує відомі шаблони API-ключів / секретних токенів у вихідному пейлоаді
(вміст повідомлень, аргументи викликів інструментів, результати інструментів)
**і** у відповіді провайдера, тож облікові дані, вставлені в промпт (або
повернуті результатом інструмента), не просочуються до апстрим-провайдера чи
назад до клієнта.

- **Лише opt-in**, та сама конвенція, що й для маскування PII (суміжне з
  Жорстким правилом №20): вимкнено, доки `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true`. Коли вимкнено, ґардрейл є no-op —
  він ніколи не блокує й ніколи не переписує.
- `redactCredentials()` обходить все дерево пейлоада/відповіді (`walkValue()`,
  безпечно щодо prototype pollution, безпечно щодо циклів завдяки `WeakSet`)
  і замінює збіги плейсхолдером `[REDACTED:<type>]`, клонуючи лише ті гілки,
  які справді змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі LLM-провайдерів (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square),
  хмарні ключі (AWS access key, Twilio, SendGrid, Mailgun), приватні ключі /
  JWT, рядки підключення з обліковими даними (`mongodb://user:pass@...` тощо)
  та загальний шаблон значення заголовка
  `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключі у формі заголовків
  (`authorization`, `x-api-key`, `api-key`, `apikey`) маскуються структурно
  (лише значення, префікс схеми на кшталт `Bearer `/`Basic ` зберігається),
  а не через загальний текстовий regex.
- Ґардрейл ніколи не блокує; він лише переписує (`modifiedPayload` /
  `modifiedResponse`) та анотує (`meta.credentialsRedacted`, `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true здійснює коротке замикання ланцюжка
  message?: string; // показується під час блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail сигналізує «без змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, яке передається ланцюжком далі, для наступних guardrail-ів.
`signal?: AbortSignal` переносить життєвий цикл викликача в guardrail-и. Скасування запиту — це навмисний виняток fail-open: медіамости припиняють роботу та очищуються, не відновлюючи сирі медіадані до цілі, про яку відомо, що вона їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) guardrail і
  повторно сортує за зростанням `priority`.
- `clear()` / `list()` — адміністративні допоміжні методи.
- `runPreCallHooks(payload, context)` — перебирає активні guardrail-и, передає
  payload через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на боці відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан і за бажанням
  повторно реєструє guardrail-и за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`,
де `results` — це масив записів `GuardrailExecutionResult`, які містять
поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного guardrail-а,
корисні для трасування.

### Вимкнення guardrail-ів для окремого запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` збирає
дедубльований список імен guardrail-ів, які слід пропустити для поточного
запиту. Існує п'ять каналів, які зчитуються в цьому порядку та об'єднуються в один список
(під час дедублікації перемагає перше входження):

1. `apiKeyInfo.disabledGuardrails`
2. Тіло запиту `disabledGuardrails` (верхній рівень)
3. Тіло запиту `metadata.disabledGuardrails` (лише коли `metadata` є об'єктом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Застарілий заголовок `x-disabled-guardrails`

Усі п'ять каналів об'єднуються, включно з обома заголовками: надсилання обох
`x-omniroute-disabled-guardrails` і `x-disabled-guardrails` пропускає об'єднання
їхніх списків, а порожній сучасний заголовок більше не приховує застарілий
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), виправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значення можуть бути масивами рядків або рядком, розділеним комами; імена обрізаються
та нормалізуються до kebab-case у нижньому регістрі (`pii_masker` → `pii-masker`), а порожні
записи відкидаються. Результат передається через `context.disabledGuardrails`
до реєстру, який пропускає відповідні guardrail-и (`skipped: true` у `results`).

Список вимкнення впливає лише на **реєстр**. Режим `block` захисту від ін'єкцій у промпти — це
обов'язкова межа: middleware injection-guard
(`src/middleware/promptInjectionGuard.ts`) викликає `evaluatePromptInjection()`
без будь-якого контрольованого викликачем списку вимкнення (мертвий виклик
`resolveDisabledGuardrails({ body })`, який він раніше виконував, було видалено в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), тому запит,
який вимикає `prompt-injection`, все одно відхиляється в режимі `block`. Це зроблено
навмисно. Канали вимкнення контролюються викликачем (тіло запиту,
metadata, заголовки), а викликач не повинен мати змоги вимкнути засіб безпеки,
встановлений оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Об'єднання заголовків
з [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
змінює лише те, які guardrail-и реєстру пропускаються; воно не дозволяє клієнту
обійти middleware. Обов'язкові політики guardrail-ів на рівні ключа та групи
відстежуються в RFC v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
Див. [Покриття та обмеження](#coverage-and-limits).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts` (маршрути сімейства chat, перелічені в розділі
[Покриття та обмеження](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` будує список пропусків з API-ключа, тіла
   запиту та заголовків.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускає guardrails у порядку
   зростання пріоритету:
   - Вимкнені guardrails фіксуються як `skipped`.
   - Кожен `preCall` guardrail може перезаписати payload через `modifiedPayload`.
   - Перший `block: true` перериває ланцюжок, і обробник повертає
     відповідь про відхилення guardrail.
3. (Потенційно перезаписаний) payload надходить до combo-маршрутизації та
   відправлення до upstream.
4. **Лише non-streaming:** після складання відповіді
   `guardrailRegistry.runPostCallHooks(...)` запускає той самий ланцюжок на
   відповіді. `block: true` тут відкидає відповідь upstream і повертає HTTP 400. Потокові відповіді повністю пропускають цей крок.

Guardrails, що кидають винятки, фіксуються з `error: <message>` і логуються через
`logger.warn`, але ланцюжок продовжується — fail-open за задумом.

## Покриття та обмеження

Реєстр guardrails підключено лише до chat-конвеєра. Ці обмеження
закріплені в `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` та
`tests/unit/guardrail-pipeline-characterization.test.ts`; оновлюйте ці тести
свідомо, коли поведінка змінюється.

### Де виконуються хуки

| Хук / контроль                      | Виконується на                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runPreCallHooks`                   | Запити, що обробляються `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (та `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*` і Telegram-проксі чату. А також тестовий ендпоінт дашборда `/api/guardrails/test`. Блокування на pre-call повертає HTTP 400. |
| `runPostCallHooks`                  | Лише **non-streaming** chat-відповіді (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). Потокові відповіді ніколи туди не потрапляють.                                                                                                                                                                                                                                                                                        |
| Потоковий PII                       | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`), підключається в `streamingPipeline.ts`, коли ввімкнено `PII_RESPONSE_SANITIZATION`. Це не guardrail, тому канали вимкнення на нього не впливають.                                                                                                                                                                                                                     |
| Middleware injection-guard (legacy) | Кожен `/v1` маршрут, що несе промпт, включно з сімейством chat (див. [покриття маршрутів](#injection-guard-route-coverage--red-team-phase-8--block-d)). Лише prompt injection.                                                                                                                                                                                                                                                      |

### Що не покривається

- **Маршрути медіа, embeddings та даних** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) ніколи не досягають реєстру.
  Там не виконуються ані маскування PII, ані маскування облікових даних, ані
  modality bridge. Їхня єдина перевірка — legacy middleware injection-guard.
- **Потокові відповіді** не отримують post-call guardrails: жодного post-call
  `pii-masker` чи `credential-masker`, жодного post-call блокування. Застосовується лише
  потокове PII-перетворення (коли ввімкнено `PII_RESPONSE_SANITIZATION`). Облікові
  дані, повернені у потоковій відповіді, не редагуються.
- **Канали вимкнення проти middleware (за задумом):** middleware оцінює
  prompt injection власним викликом `evaluatePromptInjection()`, не передаючи
  жодного контрольованого caller'ом списку вимкнень. Режим `block` — це обов'язкова
  межа, яку контрольовані caller'ом вимкнення не можуть обійти, зокрема на маршрутах
  сімейства chat
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Вимкнення
  `prompt-injection` лише пропускає guardrail реєстру.

### Що бачить відповідь до post-call

На non-streaming шляху порядок такий: вилучення пам'яті → виконання вбудованих
інструментів → post-call guardrails → вихід через post-call блок → збереження в семантичний кеш.

- **Витягування пам'яті** та **виконання інструментів** бачать відповідь до того, як пост-викликові
  механізми захисту (guardrails) можуть її переписати або заблокувати. Починаючи з
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), витягування пам'яті
  пропускає витягнутий текст через `sanitizePII`, коли
  `PII_RESPONSE_SANITIZATION` увімкнено (як у потоковому, так і в непотоковому режимі), але
  відповідь, яку пост-виклик пізніше блокує, все одно вже була запропонована пам'яті та
  інструментам.
- **Семантичний кеш** зберігає відповідь після пост-виклику, тому він зберігає
  переписану відповідь, а заблокована відповідь ніколи не кешується. Записи кешу
  прив'язані до ключа API.

## Конфігурація

Змінні середовища, які зчитуються вбудованими механізмами захисту:

| Змінна                                | Використовується                | Дія                                                                                                           |
| ------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`              | Встановіть `false`, щоб повністю вимкнути виявлення.                                                          |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`              | Політика щодо ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.   |
| `INJECTION_GUARD_MODE`                | `prompt-injection`              | Режим захисту від ін'єкцій; також прапорець функції в БД, який **перевизначає** змінні середовища (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`              | Мінімальний рівень серйозності, який відхиляє `MODE=block`: `high` (за замовчуванням), `medium` або `low`.    |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`              | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                   |
| `PII_REDACTION_ENABLED`               | `pii-masker`                    | Якщо `true`, PII запиту маскуються (незалежно від режиму ін'єкцій).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (подальша обробка) | Керує поведінкою маскувальника на боці відповіді.                                                             |

Механізми захисту Modality Bridge зчитують конфігурацію під час виконання зі
сховища налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` і
`modalityBridgeCacheMaxEntries`. Застарілі ключі
`visionBridge*` приймаються лише як задокументований одноцикловий резервний
варіант читання; записи з панелі керування використовують основні ключі.
Значення за замовчуванням і резолвер резервного варіанту містяться в
`src/shared/constants/modalityBridgeDefaults.ts`, а застарілі константи
збережено в `src/shared/constants/visionBridgeDefaults.ts`.

Audio використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` і `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Audio не має резервного варіанту застарілих
ключів, оскільки ці ключі було запроваджено разом зі схемою Modality Bridge.

Video використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` і
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Воно вимкнено за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а генерація підписів до кадрів додає затримку та
витрати на модель.

## Користувацькі гардрейли

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1. Створіть `src/lib/guardrails/myGuardrail.ts`, що розширює `BaseGuardrail`.
2. Реалізуйте `preCall` та/або `postCall`.
3. Або зареєструйте під час імпорту (додавши в `registerDefaultGuardrails`), або
   викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
   будь-який попередній гардрейл із таким самим нормалізованим ім'ям.
4. Додайте тести в `tests/unit/` (наявні приклади:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб починати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнім реєстром і
зареєструвати лише гардрейли, які тестуються. Vision Bridge підтримує
впровадження залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge
надає еквівалентні точки розширення для налаштувань, можливостей, вибору моделі STT,
перевірки облікових даних і транскрипції. Тому тести можуть проганяти обидва потоки
без доступу до БД чи мережі.

## Покриття маршрутів injection-guard і red-team (Фаза 8 · Блок D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають промпти користувача. Він враховує `INJECTION_GUARD_MODE` (типово `warn` = лише
журналювання; `block` = повертає HTTP 400 `SECURITY_001`).

| Тип               | Маршрути                                                                                                                                             | Типовий режим |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| Текстові (наявні) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| Генеративні       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| Дані              | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

Витягнення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (щоночі, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут
блокує корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає проби
(пропускається без секрету). `moderations` включено для узгодженості. Режим блокування є
обов'язковою межею: `evaluatePromptInjection()` ігнорує список вимкнень на рівні запиту,
який передає йому middleware, тому `disabledGuardrails` **не** звільняє маршрут
від нього ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Нічний workflow (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокувальне)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен адверсаріальний кейс (наприклад, "ignore all
  previous instructions…", джейлбрейки в стилі DAN) перевіряє, що відповідь містить
  `error.code === "SECURITY_001"`, тобто що захист дійсно відхилив запит.
- **`garak` (консультативне)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Виконується лише
  за наявності секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); коректно пропускається
  та має суфікс `|| true`, тому звітує, не провалюючи CI.

Покриття помічника захисту (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що несе промпт; текст промпта витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
функцією `extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
