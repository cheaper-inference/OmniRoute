## Огляд

Усі маршрути API керування OmniRoute належать до одного з трьох рівнів захисту. Класифікація є статичною, визначається у `src/server/authz/routeGuard.ts` і перевіряється до виконання будь-якої іншої гілки автентифікації.

## Яруси

### Рівень 1 — LOCAL_ONLY

**Забезпечується:** `isLocalOnlyPath(path)` → петлева перевірка хоста** Обхід:** За замовчуванням немає. Звузьте виділення для шляхів у `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, коли запит містить дійсний ключ API із областю `manage` (див. [Виділення області керування](#manage-scope-carve-out) ).

Ці маршрути породжують дочірні процеси або виконують код виконання. Відкриття їх трафіку без зворотного зв’язку дозволить зловмиснику, який отримав дійсний JWT (наприклад, через тунель Cloudflared/Ngrok ), ініціювати процес породження — відомого класу CVE ( [GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj) ).

**Що таке GHSA-fhh6-4qxv-rpqj (клас атаки):** сервер management/agent відкриває кінцеву точку, яка запускає підпроцес (`npm install`, `node`, браузер, проксі, `git`, `tar`, …). Якщо ця кінцева точка доступна з стороннього хоста — тому що оператор поставив OmniRoute за тунель nginx/Cloudflare/Tailscale і JWT витік, або автентифікація була неправильно налаштована — зловмисник перетворює «виклик API» на «виконати команду на хості» (віддалене виконання коду). OmniRoute закриває це, застосовуючи a** петлева перевірка хоста без умов, перед будь-якою перевіркою авторизації** , на кожному маршруті, придатному для відродження: витік жетона через тунель все ще не може досягти відродження.

**Повний набір LOCAL_ONLY.** Авторитетним джерелом є `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` у `src/server/authz/routeGuard.ts`; таблиця нижче відображає поточний стан. Шлюз `check-route-guard-membership` перераховує кожен `route.ts` під префіксами, здатними до породження, і не виконує CI якщо якийсь не класифікується лише локально.

#### Виділення обсягу управління

До підмножини шляхів LOCAL_ONLY MAY також можна отримати доступ із беззацикленого доступу, якщо і тільки якщо запит містить `Authorization: Bearer <api-key>` метадані якого включають область `manage` (або `admin`). Виділення явно шлюзується для кожного шляху через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, тому за замовчуванням для будь-якого нового шляху LOCAL_ONLY залишається strict-loopback. Неавтентифіковані запити та запити з ключами без керування все одно відхиляються за допомогою `403 LOCAL_ONLY`.

Сьогодні єдиним обхідним префіксом є `/api/mcp/`. `/api/cli-tools/runtime/` і `/api/services/` навмисно виключені, оскільки вони можуть породжувати довільні підпроцеси (`npm install`, `node`), що є точним класом CVE якому існує рівень LOCAL_ONLY щоб запобігти.

**#7895 — `mcp:connect` вузька область:** виділення `/api/mcp/` ALSO приймає ключ носія, що містить вузьку область `mcp:connect` (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), перевіряється через `hasMcpConnectOrManageScope()` у `src/server/authz/policies/management.ts`. Це стосується `/api/mcp/` ONLY — `mcp:connect` нічого не надає на будь-якому іншому маршруті керування (включно з будь-яким іншим префіксом обходу LOCAL_ONLY, якщо його коли-небудь буде додано), і його навмисно виключено з `MANAGEMENT_API_KEY_SCOPES`. Ключ, що тримає `manage`/`admin` усе ще пропускає вирізання точно так само, як і раніше; `mcp:connect` є альтернативою з нижчими привілеями для віддалених абонентів, які викликають лише MCP, яким не потрібен широкий доступ до керування.

| запит                                          | шлях                       | Результат        |
| ---------------------------------------------- | -------------------------- | ---------------- |
| Non-loopback, no Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| Non-loopback, Bearer with `manage` scope       | `/api/mcp/*`               | Дозволити        |
| Non-loopback, Bearer with `mcp:connect` scope  | `/api/mcp/*`               | Дозволити        |
| Non-loopback, носій без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| Non-loopback, Bearer with `mcp:connect` scope  | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| Non-loopback, Bearer with `manage` scope       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| Loopback, носій any/no                         | будь-який LOCAL_ONLY       | Дозволити (паси) |

#### Керівництво та аудит оператора

Якщо ви запускаєте OmniRoute за зворотним проксі-сервером або тунелем (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), loopback перевірка все одно захищає маршрути, здатні породжувати вище — запит, адреса клієнта якого не є loopback, відхиляється за допомогою `403 LOCAL_ONLY`** до запуску авторизації** , тому злитий JWT не може досягти породи. Залишаються два обов'язки оператора:

- **Не «виправляйте» помилку 403, підробляючи клієнтську IP як петлеву.** Налаштування `X-Forwarded-For: 127.0.0.1` або проксі-сервера, який переписує адресу джерела на петлю, повторно відкриває саме той клас RCE який цей рівень закриває. Відкривайте dashboard/API через проксі-сервер — але ніколи не створюйте маршрути.
- **Зберігайте мінімальний обхід області керування.** Лише `/api/mcp/` можна обійти, і тільки з ключем `manage` -scoped API. `SPAWN_CAPABLE_PREFIXES` ніколи не можна додати до списку обходу. — схема zod відхиляє їх, а `isLocalOnlyBypassableByManageScope` забороняє їх під час виконання (поглиблений захист), що означає «неможливо зробити обхідним» на інформаційній панелі. Той самий список заборон також містить кілька маршрутів LOCAL_ONLY, які не створюються, але ніколи не повинні бути доступними віддалено, або — `/api/oauth/kiro/auto-import` (читає файли облікових даних Kiro на локальному хості), `/api/discovery/` і `/api/issue-agent/`. Завантажувач знімків під час виконання також видаляє такі записи зі збереженого рядка налаштувань, а застарілий імпорт JSON (`/api/settings/import-json`) ніколи не записує ключі обходу. Кожен запис `LOCAL_ONLY_API_PREFIXES` має бути або в списку заборонених, або розглядатися як придатний для обходу (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршрути з можливістю створення динамічних сегментів і статичних шляхів під `/api/providers/` (наприклад `/login`, `/refresh-cursor`) охоплюються супутнім `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` на основі регулярних виразів у `src/shared/constants/spawnCapablePrefixes.ts`, а не плоским масивом `SPAWN_CAPABLE_PREFIXES` — плоский масив повинен охоплювати весь префікс `/api/providers/`, щоб уловити їх, надмірно розширюючи дерево маршрутів, яке законно використовують віддалені інформаційні панелі для постачальника CRUD.

**Аудит доступу** — щоб переконатися, що нічого поза хостом не досягає цих маршрутів:

- Відкрийте** Інвентар авторизації** на `/dashboard/settings/security`: він рендерить живий список префіксів LOCAL_ONLY, які префікси можна обійти, і набір можливих для створення під час компіляції («неможливо зробити обхідним»).
- Перевірте журнали зворотного проксі-сервера/доступу на префікси вище в поєднанні з адресою клієнта без зворотного зв’язку. Будь-яке таке звернення, яке повернуло `200` замість `403 LOCAL_ONLY` означає, що проксі-сервер маскує справжнього клієнта IP — fix the proxy.
- `403 LOCAL_ONLY` в журналах OmniRoute для одного з цих шляхів означає, що захисник працює належним чином, а не помилку, яку потрібно придушити.

#### Дистанційно доступні маршрути з шлюзом зонду виклику

Деякі маршрути повинні залишатися доступними з віддаленої панелі, але запускати зонд на стороні хоста (`which <binary>`, `<binary> --version`, `tailscale status --json`) для місцевих абонентів. Вони не є LOCAL_ONLY для `GET`; натомість обробник читає вердикт довіреного однорангового вузла за допомогою `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) і запускає зонд лише для абонентів, що викликають `loopback` / `lan`. Виклик `remote` отримує ту саму форму відповіді, створену з джерел, що не породжуються (постійний стан, налаштування, перевірки fs), позначений `probed: false`.

| Маршрут                                                          | Зондування пропущено для віддалених абонентів                     |
| ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI runtime probe (`allowLocalRuntimeProbe`) і CLI-fallback spawn |
| `GET /api/headroom/status`                                       | `which headroom` та зонди python `--version`                      |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew` |
| `GET /api/tunnels/cloudflared` (GET-виключено з LOCAL_ONLY)      | `which cloudflared` PATH пошук                                    |

Новий маршрут читання, який досліджує хост, дотримується того ж шаблону або класифікується як LOCAL_ONLY.

### Рівень 2 — ALWAYS_PROTECTED

**Забезпечується:** `isAlwaysProtectedPath(path)` → пропустити обхід `requireLogin=false`** Обхід:** Немає, коли `requireLogin=false`; JWT завжди потрібен

Ці шляхи є руйнівними або незворотними. Якщо дозволити їм установку без пароля, будь-хто на тому самому LAN зможе стерти базу даних або припинити серверний процес.

**Відповідь на порушення:** `401 Authentication required`

`/api/settings/obsidian` охоплює свій дочірній елемент `/webdav` : `POST` вказує на файлову службу WebDAV — яка обслуговується користувацьким рівнем Node перед Next.js, поза цим конвеєром — у вибраному абонентом корені та повторює щойно створені облікові дані Basic, `DELETE` обертає їх, а батьківський `POST` зберігає маркер Obsidian REST API. GHSA-62vw лише замаскував розкриття пароля `GET` ; випуск все ще перебував на відкритому рівні (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` додатково відмовляється від сховища, яке знаходиться всередині або містить каталог даних.

#### Експорт облікових даних і відновлення доступні лише оператору

Рівень вище лише вирішує, чи потрібні _деякі_ облікові дані. Маршрути, які завантажують збережені облікові дані, додають другу перевірку в обробнику: `GET /api/settings/export-json` (розшифровані з’єднання провайдера та необроблені ключі API ), `GET /api/db-backups/export` (файл SQLite ) і `GET /api/db-backups/exportAll` (повний архів) викликають `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). Він приймає сеанс інформаційної панелі, локальну тему CLI або екземпляр із вимкненим входом і відповідає на ключі `403` до API будь-якого обсягу (включаючи `manage` і `admin`) і маркери доступу `oma_`. Деструктивні відповідники мають ті самі межі: `POST /api/db-backups/import` (завантажений `.sqlite`, включений `dryRun=true` ), `POST /api/db-backups` (відновлення збереженої резервної копії за ідентифікатором) і `POST /api/settings/import-json` (відновлення застарілого JSON ) замінюють живу базу даних або весь набір settings/connections/API-key, тому облікові дані машини також не можуть їх активувати. Знищення точок відновлення має ті самі межі: `DELETE /api/db-backups` ( — очищення зберігає останні N/drop старше D днів) і `PATCH /api/db-backups` (параметри збереження), оскільки постійне збереження — це саме те, що `cleanupDbBackups()` застосовує після кожного автоматичного резервного копіювання (`src/lib/db/backup.ts`), тому облікові дані машини, які можуть зберегти `keepLatest: 1` видалять усе на наступному знімку. Перерахування та створення резервних копій (`GET`/`PUT /api/db-backups`) зберігають звичайну автентифікацію керування. Видача маркера синхронізації (`POST /api/sync/tokens`) використовує той самий помічник, а також маркер внутрішньої служби довіреної петлі.

### Нова інсталяція початкового завантаження — це лише зворотна перевірка — реальним одноранговим вузлом, а не `Host`

Без налаштованого пароля керування (і без `INITIAL_PASSWORD`), `isAuthRequired()` у `src/shared/utils/apiAuth.ts` зберігає відкритим анонімний завантажувач** лише для зациклених однорангових вузлів** . Зворотний зв’язок визначається на основі сигналів довірених однорангових вузлів у такому порядку: справжній одноранговий вузол TCP із маркером (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, те, що бачить політика), власний вердикт `AUTHZ_HEADER_PEER_LOCALITY` конвеєра (те, що бачать обробники маршруту, довірені лише тоді, коли встановлено `OMNIROUTE_PEER_STAMP_TOKEN` ), або реальний одноранговий гніздо для прямих викликів. `Host` / `nextUrl.hostname` ніколи не перевіряються, а запис першого пароля (`POST /api/settings/require-login`) знаходиться під тим самим обмеженням, а не відкритим для всіх однорангових мереж (GHSA-7pq4-8pvv-rx7r). `managementPolicy` чітко передає власний вердикт `peerContext`, тому заголовки запиту ORIGINAL (pre-strip) ніколи не вирішують його.

### Рівень 3 — MANAGEMENT (за замовчуванням)

Усі інші маршрути управління. Потрібна авторизація, якщо не налаштовано `requireLogin=false`. токени CLI можуть автентифікувати ці маршрути (loopback + valid HMAC).

## Порядок оцінювання

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти далі
     → не loopback, Bearer із областю manage
        І isLocalOnlyBypassableByManageScope     → дозволити (management_key)
     → інакше                                     → відхилити 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → дозволити (system)
  3. hasValidCliToken(headers)?
     → дозволити (cli) [loopback + перевірка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) або requireLogin=true?
     → isDashboardSessionAuthenticated?
        → дозволити (dashboard_session)
     → Bearer із областю manage на маршруті, який не можна обійти?
        → дозволити (management_key)
     → відхилити 401/403
  5. requireLogin=false?
     → дозволити (anonymous)
```

Гілка області manage на кроці 1 — це єдиний автентифікований шлях, який може задовольнити маршрут
LOCAL_ONLY; режим помилки бекенду автентифікації повертає 503 (а не 403), щоб
прострочена БД непомітно не призводила до зниження рівня до «відхилити».

## Додавання нового маршруту з можливістю спавну

1. Додайте префікс шляху до `LOCAL_ONLY_API_PREFIXES` в `src/server/authz/routeGuard.ts`
2. Додайте тест у `tests/unit/authz/routeGuard.test.ts` який підтверджує, що `isLocalOnlyPath()` повертає true для нового префікса
3. **Ніколи не пропускайте цей крок** — див. жорстке правило #15 у `CLAUDE.md`
4. Вирішіть: чи належить цей маршрут ALSO до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`? Відповідь за замовчуванням:** немає** . Увімкніть лише тоді, коли маршрут безпечний для доступу до власника області керування (тобто чи створює NOT довільний код, керований користувачем).

## Додавання шляху, який можна обійти за допомогою manage-scope

1. Переконайтеся, що маршрут не виконує наданий користувачем код або команди. Якщо
   виконує, зупиніться — цей виняток тут не підходить.
2. Додайте префікс до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` у
   `src/server/authz/routeGuard.ts`
3. Додайте покриття в `tests/unit/authz/management-policy.test.ts` для всіх чотирьох
   варіантів запиту: без Bearer (403), manage Bearer (дозволити), не-manage Bearer
   (403), а також окрему регресійну перевірку для кожного префікса, щоб
   `/api/cli-tools/runtime/*` залишався доступним лише через loopback навіть із manage Bearer.

## Документування рівнів безпеки в OpenAPI

Під час додавання нового маршруту до `docs/openapi.yaml` застосуйте відповідне
розширення постачальника, якщо маршрут класифіковано в `routeGuard.ts`:

| Класифікація routeGuard.ts                      | YAML-анотація              | Застосування правил                                       |
| ----------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                       | `x-loopback-only: true`    | Безумовно блокується для з’єднань не через loopback       |
| `ALWAYS_PROTECTED_API_PATHS`                    | `x-always-protected: true` | Автентифікація обов’язкова навіть за `requireLogin=false` |
| Внутрішній маршрут адміністрування/налагодження | `x-internal: true`         | Типово прихований у /dashboard/api-endpoints              |
| Немає (публічний / стандартна автентифікація)   | (анотація не потрібна)     | Стандартний доступ, керований `requireLogin`              |

### Валідація

Два скрипти забезпечують узгодженість між YAML-анотаціями та `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершується помилкою, якщо покриття < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершується помилкою, якщо анотації `x-loopback-only` або
  `x-always-protected` не відповідають константам часу компіляції

Обидва скрипти запускаються в pre-commit hook і в CI.

### Правило щодо хибнопозитивних результатів

Якщо `x-always-protected` або `x-loopback-only` додано до маршруту, якого НЕМАЄ у
відповідній константі `routeGuard.ts`, скрипт перевірки покриття завершується помилкою. Правильне виправлення — завжди узгодити
YAML із тим, що фактично забезпечує `routeGuard.ts`, а не додавати маршрути до `routeGuard.ts`
без одночасної реалізації логіки застосування відповідних правил.
