## Огляд

Усі маршрути API керування OmniRoute належать до одного з трьох рівнів захисту. Класифікація є статичною, визначається у `src/server/authz/routeGuard.ts` і перевіряється до виконання будь-якої іншої гілки автентифікації.

## Рівні

### Рівень 1 — LOCAL_ONLY

**Забезпечується:** `isLocalOnlyPath(path)` → перевірка loopback-хоста
**Обхід:** За замовчуванням відсутній. Вузький виняток для шляхів у
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, коли запит містить дійсний
ключ API з областю `manage` (див. [Виняток для області manage](#manage-scope-carve-out)).

Ці маршрути породжують дочірні процеси або виконують код середовища виконання. Відкриття їх для
не-loopback трафіку дозволило б зловмиснику, який отримав дійсний JWT (наприклад,
через тунель Cloudflared/Ngrok), ініціювати породження процесів — відомий клас
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Що таке GHSA-fhh6-4qxv-rpqj (клас атаки):** сервер керування/агент
надає кінцеву точку, яка запускає підпроцес (`npm install`, `node`, браузер,
проксі, `git`, `tar`, …). Якщо ця кінцева точка доступна ззовні — бо
оператор розмістив OmniRoute за тунелем nginx/Cloudflare/Tailscale і JWT
злився, або автентифікацію було неправильно налаштовано — зловмисник перетворює «викликати API» на «виконати
команду на хості» (віддалене виконання коду). OmniRoute закриває це, примусово виконуючи
**перевірку loopback-хоста безумовно, перед будь-якою перевіркою автентифікації**, на кожному
маршруті, здатному породжувати процеси: навіть витік токена через тунель не дає доступу до породження процесів.

**Повний набір LOCAL_ONLY.** Авторитетним джерелом є
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` у
`src/server/authz/routeGuard.ts`; таблиця нижче відображає поточний стан.
Перевірка `check-route-guard-membership` перелічує кожен `route.ts` під
префіксами, здатними породжувати процеси, і провалює CI, якщо будь-який з них не класифіковано як local-only.

#### Виняток для manage-області

Підмножина шляхів LOCAL_ONLY ТАКОЖ може бути доступною з не-loopback адрес
тоді й лише тоді, коли запит містить заголовок `Authorization: Bearer <api-key>`,
метадані якого включають область `manage` (або `admin`). Виняток явно
контролюється для кожного шляху через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`,
тому типовою поведінкою для будь-якого нового шляху LOCAL_ONLY залишається
суворий loopback. Неавтентифіковані запити та запити з ключами без
manage-області все одно відхиляються з `403 LOCAL_ONLY`.

Наразі єдиний префікс, для якого можливий обхід, — це `/api/mcp/`.
`/api/cli-tools/runtime/` та `/api/services/` навмисно виключені, оскільки вони
можуть запускати довільні підпроцеси (`npm install`, `node`), що є саме тим
класом CVE, для запобігання якого існує рівень LOCAL_ONLY.

**#7895 — вузька область `mcp:connect`:** виняток для `/api/mcp/` ТАКОЖ приймає
Bearer-ключ із вузькою областю `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), що
перевіряється через `hasMcpConnectOrManageScope()` у
`src/server/authz/policies/management.ts`. Це стосується ЛИШЕ `/api/mcp/` —
`mcp:connect` не надає жодних прав на будь-який інший маршрут керування
(включно з будь-яким іншим префіксом обходу LOCAL_ONLY, якщо такий коли-небудь
буде додано), і вона навмисно виключена з `MANAGEMENT_API_KEY_SCOPES`. Ключ із
`manage`/`admin` як і раніше проходить виняток так само; `mcp:connect` — це
альтернатива з нижчими привілеями для віддалених клієнтів, яким потрібен лише
MCP і які не повинні мати широкого доступу до керування.

| Запит                                          | Шлях                       | Результат                      |
| ---------------------------------------------- | -------------------------- | ------------------------------ |
| Не-loopback, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не-loopback, Bearer з областю `manage`         | `/api/mcp/*`               | Дозволено                      |
| Не-loopback, Bearer з областю `mcp:connect`    | `/api/mcp/*`               | Дозволено                      |
| Не-loopback, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не-loopback, Bearer з областю `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Не-loopback, Bearer з областю `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Loopback, з будь-яким/без Bearer               | будь-який LOCAL_ONLY       | Дозволено (контроль проходить) |

#### Рекомендації для операторів і аудит

Якщо ви запускаєте OmniRoute за зворотним проксі або тунелем (nginx, Caddy,
Cloudflare Tunnel, Tailscale, Ngrok), loopback-перевірка все одно захищає
наведені вище маршрути, здатні запускати процеси, — запит, чия клієнтська
адреса не є loopback, відхиляється з `403 LOCAL_ONLY` **до виконання
автентифікації**, тому витік JWT не може досягти запуску процесу. Залишаються
два обов'язки оператора:

- **Не «виправляйте» 403 підробкою IP клієнта як loopback.** Встановлення
  `X-Forwarded-For: 127.0.0.1` або проксі, що переписує адресу джерела на
  loopback, повторно відкриває саме той клас RCE, який цей рівень закриває.
  Публікуйте через проксі лише дашборд/API — ніколи не маршрути зі здатністю до спавну.
- **Тримайте обхід manage-scope мінімальним.** Обхід можливий лише для `/api/mcp/` і
  лише з API-ключем зі scope `manage`. Префікси `SPAWN_CAPABLE_PREFIXES` ніколи не
  можуть бути додані до списку обходу — схема zod відхиляє їх, а
  `isLocalOnlyBypassableByManageScope` відхиляє їх під час виконання (захист у глибину),
  що саме й має на увазі дашборд під «cannot be made bypassable». Той самий
  список заборон також містить кілька маршрутів LOCAL_ONLY, які не спавнять процесів, але
  також ніколи не повинні бути доступними віддалено — `/api/oauth/kiro/auto-import` (читає
  локальні файли облікових даних Kiro хоста), `/api/discovery/` та `/api/issue-agent/`.
  Завантажувач знімка стану під час виконання також відкидає такі записи зі збереженого
  рядка налаштувань, а імпорт legacy JSON (`/api/settings/import-json`) ніколи не записує
  ключі обходу. Кожен запис `LOCAL_ONLY_API_PREFIXES` має бути або у списку заборон, або
  перевірений як придатний для обходу (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`).
  Маршрути зі здатністю до спавну з динамічними сегментами та статичними шляхами під
  `/api/providers/` (напр., `/login`, `/refresh-cursor`) покриваються супутнім механізмом
  на основі регулярних виразів `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` у
  `src/shared/constants/spawnCapablePrefixes.ts`, а не пласким масивом
  `SPAWN_CAPABLE_PREFIXES` — плаский масив мусив би покривати
  весь префікс `/api/providers/`, щоб перехопити їх, надмірно розширюючи дерево
  маршрутів, яке віддалені дашборди легітимно використовують для CRUD провайдерів.

**Аудит доступу** — щоб переконатися, що ніщо поза хостом не дістається цих маршрутів:

- Відкрийте **Authorization Inventory** на `/dashboard/settings/security`: там відображається
  актуальний список префіксів LOCAL_ONLY, які префікси можна обходити, та
  визначений під час компіляції набір маршрутів зі здатністю до спавну («cannot be made bypassable»).
- Шукайте через grep у логах вашого зворотного проксі / логах доступу наведені вище префікси
  у парі з не-loopback адресою клієнта. Будь-яке таке збігання, що повернуло `200`
  замість `403 LOCAL_ONLY`, означає, що проксі маскує реальну IP-адресу клієнта — виправте проксі.
- `403 LOCAL_ONLY` у логах OmniRoute для одного з цих шляхів — це захист,
  що працює як задумано, а не помилка, яку треба придушувати.

#### Віддалено доступні маршрути з бар'єром перевірки в точці виклику

Деякі маршрути мають залишатися доступними з віддаленого дашборда, але виконують перевірку
на стороні хоста (`which <binary>`, `<binary> --version`, `tailscale status --json`) для локальних
викликів. Вони не є LOCAL_ONLY для `GET`; натомість обробник зчитує довірений вердикт про
розташування вузла за допомогою `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) і виконує
перевірку лише для викликів `loopback` / `lan`. Віддалений (`remote`) виклик отримує ту саму
форму відповіді, побудовану з джерел без спавну (збережений стан, налаштування, перевірки
файлової системи), з позначкою `probed: false`.

| Маршрут                                                          | Перевірка, пропущена для віддалених викликів                           |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | Перевірка CLI-рантайму (`allowLocalRuntimeProbe`) та спавн CLI-фолбека |
| `GET /api/headroom/status`                                       | `which headroom` та python-перевірки `--version`                       |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`      |
| `GET /api/tunnels/cloudflared` (виняток з LOCAL_ONLY для GET)    | Пошук `which cloudflared` у PATH                                       |

Новий маршрут читання, що перевіряє хост, слідує тому самому шаблону або
класифікується як LOCAL_ONLY одразу.

### Рівень 2 — ALWAYS_PROTECTED

**Забезпечується:** `isAlwaysProtectedPath(path)` → пропуск обходу `requireLogin=false`
**Обхід:** Жодного за `requireLogin=false`; JWT завжди обов'язковий

Ці маршрути є руйнівними або незворотними. Дозвіл на них в інсталяції «без пароля»
означав би, що будь-хто в тій самій LAN зміг би знищити базу даних або завершити
процес сервера.

| Шлях                                      | Причина                                                                 |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершує процес сервера                                                 |
| `/api/settings/database`                  | Експорт, імпорт та очищення бази даних                                  |
| `/api/db-backups`                         | Доступ до повного архіву резервних копій бази даних                     |
| `/api/settings/export-json`               | Експортує повний набір налаштувань (включно з секретами)                |
| `/api/settings/import-json`               | Замінює повний набір налаштувань                                        |
| `/api/providers/health-autopilot/actions` | Виконує коригувальні дії автопілота                                     |
| `/api/settings/obsidian`                  | Створює багаторазові облікові дані WebDAV для будь-якого кореня сховища |
| `/api/relay/tokens`                       | Створює, перераховує, редагує та відкликає relay-токени                 |
| `/api/cli-tools/apply`                    | Перезаписує конфігурацію CLI на хості оператора                         |
| `/api/cli-tools/guide-settings`           | Записує конфігураційні файли CLI за гайдом                              |
| `/api/cli-tools/hermes-agent-settings`    | Записує конфігурацію агента Hermes                                      |
| `/api/cli-tools/backups`                  | Відновлює та видаляє резервні копії конфігурації CLI                    |
| `/api/log-export`                         | Надсилає логи викликів до налаштованого призначення                     |
| `/api/restart`                            | Перезапускає процес сервера                                             |

**Відповідь на порушення:** `401 Authentication required`

`/api/settings/obsidian` охоплює свій дочірній `/webdav`: `POST` спрямовує файловий сервіс WebDAV — який обслуговується власним шаром Node перед Next.js, поза цим конвеєром — на вибраний викликом корінь і повертає щойно згенеровані облікові дані Basic, `DELETE` ротує їх, а батьківський `POST` зберігає токен Obsidian REST API. GHSA-62vw лише приховав розкриття пароля через `GET`; видача все ще залишалася на рівні fail-open (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` додатково відхиляє сховище, яке є каталогом даних, міститься всередині нього або містить його.

#### Експорт і відновлення облікових даних — лише для операторів

Рівень вище лише визначає, чи потрібні _якісь_ облікові дані. Маршрути, що завантажують збережені облікові дані, додають другу перевірку в обробнику: `GET /api/settings/export-json` (розшифровані підключення провайдерів і сирі ключі API), `GET /api/db-backups/export` (файл SQLite) і `GET /api/db-backups/exportAll` (повний архів) викликають `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). Вона приймає сесію панелі керування, локальний суб'єкт CLI або екземпляр із вимкненим входом і відповідає `403` на ключі API будь-якої області (включно з `manage` та `admin`) і на токени доступу `oma_`. Руйнівні аналоги дотримуються тієї ж межі: `POST /api/db-backups/import` (завантажений `.sqlite`, включно з `dryRun=true`), `POST /api/db-backups` (відновлення збереженої резервної копії за id) і `POST /api/settings/import-json` (відновлення застарілого JSON) замінюють робочу базу даних або весь набір налаштувань/підключень/ключів API, тож машинні облікові дані також не можуть їх запустити. Знищення точок відновлення дотримується тієї ж межі: `DELETE /api/db-backups` (очищення — залишити останні N / видалити старші за D днів) і `PATCH /api/db-backups` (налаштування зберігання), оскільки збережена політика зберігання — це саме те, що `cleanupDbBackups()` застосовує після кожного автоматичного резервного копіювання (`src/lib/db/backup.ts`), тож машинні облікові дані, які могли б зберегти `keepLatest: 1`, видалили б усе під час наступного знімка. Перегляд списку та створення резервних копій (`GET`/`PUT /api/db-backups`) зберігають звичайну автентифікацію керування. Видача токенів синхронізації (`POST /api/sync/tokens`) використовує той самий помічник, плюс довірений loopback-токен внутрішньої служби.

### Bootstrap нової інсталяції — лише для loopback, за реальним піром, а не `Host`

Якщо пароль керування не налаштовано (і немає `INITIAL_PASSWORD`), `isAuthRequired()` у `src/shared/utils/apiAuth.ts` залишає анонімний bootstrap відкритим **лише для loopback-пірів**. Loopback визначається за довіреними сигналами піра, у такому порядку: реальний TCP-пір, позначений токеном (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, те, що бачить політика), власний висновок конвеєра `AUTHZ_HEADER_PEER_LOCALITY` (те, що бачать обробники маршрутів; йому довіряють лише доки встановлено `OMNIROUTE_PEER_STAMP_TOKEN`), або реальний сокетний пір для прямих викликів. `Host` / `nextUrl.hostname` ніколи не враховуються, а запис першого пароля (`POST /api/settings/require-login`) підпадає під те саме обмеження, а не відкритий для будь-якого мережевого піра (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передає вниз власний висновок `peerContext`, тож заголовки ОРИГІНАЛЬНОГО (до очищення) запиту ніколи цього не визначають.

### Рівень 3 — MANAGEMENT (за замовчуванням)

Усі інші маршрути керування. Автентифікація обов'язкова, якщо не налаштовано `requireLogin=false`. Токени CLI можуть автентифікувати ці маршрути (loopback + дійсний HMAC).

## Порядок оцінювання

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти далі
     → не loopback, Bearer із областю manage
        І isLocalOnlyBypassableByManageScope     → дозволити (management_key)
     → інакше                                     → відхилити 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → дозволити (system)
  3. hasValidCliToken(headers)?
     → дозволити (cli) [loopback + перевірка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) або requireLogin=true?
     → isDashboardSessionAuthenticated?
        → дозволити (dashboard_session)
     → Bearer із областю manage на маршруті, який не можна обійти?
        → дозволити (management_key)
     → відхилити 401/403
  5. requireLogin=false?
     → дозволити (anonymous)
```

Гілка області manage на кроці 1 — це єдиний автентифікований шлях, який може задовольнити маршрут
LOCAL_ONLY; режим помилки бекенду автентифікації повертає 503 (а не 403), щоб
прострочена БД непомітно не призводила до зниження рівня до «відхилити».

## Додавання нового маршруту, здатного запускати процеси

1. Додайте префікс шляху до `LOCAL_ONLY_API_PREFIXES` у
   `src/server/authz/routeGuard.ts`
2. Додайте тест до `tests/unit/authz/routeGuard.test.ts`, який перевіряє, що
   `isLocalOnlyPath()` повертає true для нового префікса
3. **Ніколи не пропускайте цей крок** — див. жорстке правило №15 у `CLAUDE.md`
4. Вирішіть: чи має цей маршрут ТАКОЖ входити до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Типова відповідь — **ні**. Додавайте його лише тоді, коли маршрут безпечно надавати
   власнику manage-scope (тобто він НЕ запускає довільний код, керований користувачем).

## Додавання шляху, який можна обійти за допомогою manage-scope

1. Переконайтеся, що маршрут не виконує наданий користувачем код або команди. Якщо
   виконує, зупиніться — цей виняток тут не підходить.
2. Додайте префікс до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` у
   `src/server/authz/routeGuard.ts`
3. Додайте покриття в `tests/unit/authz/management-policy.test.ts` для всіх чотирьох
   варіантів запиту: без Bearer (403), manage Bearer (дозволити), не-manage Bearer
   (403), а також окрему регресійну перевірку для кожного префікса, щоб
   `/api/cli-tools/runtime/*` залишався доступним лише через loopback навіть із manage Bearer.

## Документування рівнів безпеки в OpenAPI

Під час додавання нового маршруту до `docs/openapi.yaml` застосуйте відповідне
розширення постачальника, якщо маршрут класифіковано в `routeGuard.ts`:

| Класифікація routeGuard.ts                      | YAML-анотація              | Застосування правил                                       |
| ----------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                       | `x-loopback-only: true`    | Безумовно блокується для з’єднань не через loopback       |
| `ALWAYS_PROTECTED_API_PATHS`                    | `x-always-protected: true` | Автентифікація обов’язкова навіть за `requireLogin=false` |
| Внутрішній маршрут адміністрування/налагодження | `x-internal: true`         | Типово прихований у /dashboard/api-endpoints              |
| Немає (публічний / стандартна автентифікація)   | (анотація не потрібна)     | Стандартний доступ, керований `requireLogin`              |

### Валідація

Два скрипти забезпечують узгодженість між YAML-анотаціями та `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершується помилкою, якщо покриття < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершується помилкою, якщо анотації `x-loopback-only` або
  `x-always-protected` не відповідають константам часу компіляції

Обидва скрипти запускаються в pre-commit hook і в CI.

### Правило щодо хибнопозитивних результатів

Якщо `x-always-protected` або `x-loopback-only` додано до маршруту, якого НЕМАЄ у
відповідній константі `routeGuard.ts`, скрипт перевірки покриття завершується помилкою. Правильне виправлення — завжди узгодити
YAML із тим, що фактично забезпечує `routeGuard.ts`, а не додавати маршрути до `routeGuard.ts`
без одночасної реалізації логіки застосування відповідних правил.
