## Огляд

Усі маршрути API керування OmniRoute належать до одного з трьох рівнів захисту. Класифікація є статичною, визначається у `src/server/authz/routeGuard.ts` і перевіряється до виконання будь-якої іншої гілки автентифікації.

## Рівні

### Рівень 1 — LOCAL_ONLY

**Застосовується через:** `isLocalOnlyPath(path)` → перевірка loopback-хоста
**Обхід:** За замовчуванням відсутній. Вузький виняток для шляхів у
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, коли запит містить дійсний
API-ключ з областю доступу `manage` (див. [Виняток для області доступу manage](#manage-scope-carve-out)).

Ці маршрути породжують дочірні процеси або виконують код середовища виконання. Надання
доступу до них для трафіку не з loopback-інтерфейсу дозволило б зловмиснику, який отримав дійсний JWT (наприклад,
через тунель Cloudflared/Ngrok), запускати породження процесів — відомий клас
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Що таке GHSA-fhh6-4qxv-rpqj (клас атаки):** сервер керування/агента
надає кінцеву точку, яка запускає підпроцес (`npm install`, `node`, браузер,
проксі, `git`, `tar`, …). Якщо ця кінцева точка доступна ззовні хоста — через те, що
оператор розмістив OmniRoute за тунелем nginx/Cloudflare/Tailscale, а JWT
витік, або автентифікацію було налаштовано неправильно — зловмисник перетворює «виклик API» на «виконання
команди на хості» (віддалене виконання коду). OmniRoute запобігає цьому, безумовно виконуючи
**перевірку loopback-хоста перед будь-якою перевіркою автентифікації** для кожного
маршруту, здатного породжувати процеси: витік токена через тунель усе одно не дає доступу до породження процесу.

**Повний набір LOCAL_ONLY.** Авторитетним джерелом є
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` у
`src/server/authz/routeGuard.ts`; наведена нижче таблиця відображає поточний стан. Перевірка
`check-route-guard-membership` перелічує кожен `route.ts` у
префіксах, здатних породжувати процеси, і спричиняє збій CI, якщо будь-який із них не класифіковано як доступний лише локально.

#### Виняток для області керування

До підмножини шляхів LOCAL_ONLY ТАКОЖ МОЖНА отримати доступ не через loopback тоді й
лише тоді, коли запит містить `Authorization: Bearer <api-key>`, метадані якого
включають область `manage` (або `admin`). Виняток дозволяється
явно для кожного шляху через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, тому
типовим режимом для кожного нового шляху LOCAL_ONLY залишається сувора вимога loopback. Неавтентифіковані
запити та запити з ключами без області керування, як і раніше, відхиляються з
`403 LOCAL_ONLY`.

Наразі єдиним префіксом, для якого дозволено обхід, є `/api/mcp/`. `/api/cli-tools/runtime/` і
`/api/services/` навмисно виключені, оскільки вони можуть запускати довільні
підпроцеси (`npm install`, `node`), а це саме той клас CVE, якому
має запобігати рівень LOCAL_ONLY.

**#7895 — вузька область `mcp:connect`:** виняток для `/api/mcp/` ТАКОЖ приймає
ключ Bearer із вузькою областю `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), що перевіряється через
`hasMcpConnectOrManageScope()` у `src/server/authz/policies/management.ts`.
Ця область обмежена ВИКЛЮЧНО `/api/mcp/` — `mcp:connect` не надає жодних прав на будь-якому іншому
маршруті керування (включно з усіма іншими префіксами обходу LOCAL_ONLY, якщо такі
коли-небудь буде додано), і її навмисно виключено з
`MANAGEMENT_API_KEY_SCOPES`. Ключ з областю `manage`/`admin`, як і раніше, проходить
перевірку винятку без змін; `mcp:connect` є альтернативою з нижчими привілеями
для віддалених клієнтів, що використовують лише MCP і не повинні мати широкого доступу до керування.

| Запит                                                | Шлях                       | Результат                      |
| ---------------------------------------------------- | -------------------------- | ------------------------------ |
| Не через loopback, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не через loopback, Bearer з областю `manage`         | `/api/mcp/*`               | Дозволити                      |
| Не через loopback, Bearer з областю `mcp:connect`    | `/api/mcp/*`               | Дозволити                      |
| Не через loopback, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не через loopback, Bearer з областю `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Не через loopback, Bearer з областю `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Через loopback, із будь-яким Bearer або без нього    | будь-який LOCAL_ONLY       | Дозволити (перевірку пройдено) |

#### Рекомендації для операторів і аудит

Якщо ви запускаєте OmniRoute за зворотним проксі або тунелем (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), перевірка loopback і надалі захищає наведені вище
маршрути, здатні запускати процеси, — запит, адреса клієнта якого не є loopback-адресою, відхиляється з
`403 LOCAL_ONLY` **до виконання автентифікації**, тому витік JWT не дасть змоги запустити процес. Залишаються два
обов’язки оператора:

- **Не «виправляйте» помилку 403, підробляючи IP-адресу клієнта як loopback-адресу.** Установлення
  `X-Forwarded-For: 127.0.0.1` або використання проксі, який замінює адресу джерела на
  loopback-адресу, знову уможливлює саме той клас RCE, який блокує цей рівень. Надавайте
  доступ через проксі до панелі керування/API — але ніколи до маршрутів, здатних запускати процеси.
- **Зберігайте обхід через область `manage` мінімальним.** Обхід дозволено лише для `/api/mcp/`
  і лише з API-ключем з областю `manage`. `SPAWN_CAPABLE_PREFIXES` за жодних умов не можна
  додати до списку обходу — схема zod відхиляє їх, а
  `isLocalOnlyBypassableByManageScope` забороняє їх під час виконання (багаторівневий захист),
  саме це й означає напис «cannot be made bypassable» на панелі керування. Той самий
  список заборон також містить кілька маршрутів LOCAL_ONLY, які не запускають процеси, але
  також ніколи не мають бути доступними віддалено: `/api/oauth/kiro/auto-import` (читає
  локальні для хоста файли облікових даних Kiro), `/api/discovery/` і `/api/issue-agent/`.
  Завантажувач знімка стану під час виконання також видаляє такі записи зі збереженого рядка
  налаштувань, а застарілий імпорт JSON (`/api/settings/import-json`) ніколи не записує ключі
  обходу. Кожен запис `LOCAL_ONLY_API_PREFIXES` має або входити до списку заборон, або
  бути перевірений на придатність до обходу (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршрути
  з динамічними сегментами та статичними шляхами, здатні запускати процеси, у `/api/providers/`
  (наприклад, `/login`, `/refresh-cursor`) охоплюються супровідними регулярними виразами
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` у
  `src/shared/constants/spawnCapablePrefixes.ts`, а не пласким масивом
  `SPAWN_CAPABLE_PREFIXES` — інакше плаский масив мав би охоплювати весь префікс
  `/api/providers/`, надмірно розширюючи охоплення дерева маршрутів, яке віддалені
  панелі керування правомірно використовують для CRUD-операцій із провайдерами.

**Аудит доступу** — щоб переконатися, що жодні зовнішні щодо хоста запити не досягають цих маршрутів:

- Відкрийте **Інвентаризацію авторизації** на `/dashboard/settings/security`: там відображаються
  актуальний список префіксів LOCAL_ONLY, префікси, для яких можливий обхід, і визначений під час
  компіляції набір маршрутів, здатних запускати процеси («cannot be made bypassable»).
- Знайдіть у журналах зворотного проксі / журналах доступу наведені вище префікси в поєднанні
  з адресою клієнта, яка не є loopback-адресою. Якщо такий запит повернув `200` замість
  `403 LOCAL_ONLY`, це означає, що проксі приховує справжню IP-адресу клієнта — виправте проксі.
- Запис `403 LOCAL_ONLY` у журналах OmniRoute для одного з цих шляхів означає, що захист
  працює належним чином, а не помилку, яку слід приховувати.

#### Віддалено доступні маршрути із захистом перевірки в місці виклику

Деякі маршрути мають залишатися доступними з віддаленої панелі керування, але виконувати локальну
перевірку на хості (`which <binary>`, `<binary> --version`, `tailscale status --json`) для локальних
викликів. Для `GET` вони не є LOCAL_ONLY; натомість обробник зчитує довірений результат визначення
джерела запиту за допомогою `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) і запускає
перевірку лише для джерел `loopback` / `lan`. Віддалений виклик із джерела `remote` отримує відповідь
тієї самої структури, сформовану з джерел, що не запускають процеси (збережений стан, налаштування,
перевірки файлової системи), із позначкою `probed: false`.

| Маршрут                                                          | Перевірка, яку пропущено для віддалених викликів                                     |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | Перевірка середовища виконання CLI (`allowLocalRuntimeProbe`) і резервний запуск CLI |
| `GET /api/headroom/status`                                       | Перевірки `which headroom` і python `--version`                                      |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`                    |
| `GET /api/tunnels/cloudflared` (виняток `GET` із LOCAL_ONLY)     | Пошук `which cloudflared` у PATH                                                     |

Новий маршрут читання, який перевіряє хост, має використовувати той самий шаблон або бути
повністю класифікований як LOCAL_ONLY.

### Рівень 2 — ALWAYS_PROTECTED

**Забезпечується через:** `isAlwaysProtectedPath(path)` → пропуск обходу `requireLogin=false`
**Обхід:** відсутній, коли `requireLogin=false`; JWT потрібен завжди

Ці маршрути виконують руйнівні або незворотні дії. Якби вони були дозволені в інсталяції
«без пароля», будь-хто в тій самій LAN міг би стерти базу даних або завершити
серверний процес.

| Шлях                                      | Причина                                                                 |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершує серверний процес                                               |
| `/api/settings/database`                  | Експорт, імпорт і повне очищення бази даних                             |
| `/api/db-backups`                         | Доступ до повного архіву резервної копії бази даних                     |
| `/api/settings/export-json`               | Експортує повний об’єкт налаштувань (включно із секретами)              |
| `/api/settings/import-json`               | Замінює повний об’єкт налаштувань                                       |
| `/api/providers/health-autopilot/actions` | Виконує дії автоматичного виправлення autopilot                         |
| `/api/settings/obsidian`                  | Створює багаторазові облікові дані WebDAV для будь-якого кореня сховища |
| `/api/relay/tokens`                       | Mints, lists, edits and revokes relay tokens                            |

**Відповідь у разі порушення:** `401 Authentication required`

`/api/settings/obsidian` охоплює свій дочірній маршрут `/webdav`: `POST` спрямовує файлову службу WebDAV —
яка обслуговується спеціальним шаром Node перед Next.js, поза цим конвеєром — на корінь, вибраний
викликачем, і повертає щойно створені облікові дані Basic; `DELETE` виконує їхню ротацію, а батьківський
`POST` зберігає токен REST API Obsidian. GHSA-62vw лише приховав розкриття пароля через `GET`;
видавання облікових даних і надалі залишалося на рівні, відкритому в разі збою (GHSA-7pq4-8pvv-rx7r).
`enableObsidianVaultSync()` додатково відхиляє сховище, яке є каталогом даних, розташоване всередині
нього або містить його.

#### Експорт облікових даних доступний лише оператору

Рівень вище лише визначає, чи потрібні _якісь_ облікові дані. Маршрути, які завантажують
збережені облікові дані, додають другу перевірку в обробнику: `GET /api/settings/export-json` (розшифровані
підключення до провайдерів і необроблені ключі API), `GET /api/db-backups/export` (файл SQLite) і
`GET /api/db-backups/exportAll` (повний архів) викликають `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). Вона приймає сесію панелі керування, локальний суб’єкт CLI або
екземпляр із вимкненим входом і відповідає `403` на ключі API з будь-якою областю дії (включно з `manage`
і `admin`), а також на токени доступу `oma_`. Видача токенів синхронізації (`POST /api/sync/tokens`) використовує
той самий допоміжний метод, а також довірений токен внутрішньої служби через loopback.

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### Початкове налаштування нової інсталяції доступне лише через loopback — за реальною адресою вузла, а не `Host`

Якщо пароль керування не налаштовано (і немає `INITIAL_PASSWORD`), `isAuthRequired()` у
`src/shared/utils/apiAuth.ts` залишає анонімне початкове налаштування відкритим **лише для loopback-вузлів**.
Loopback визначається за довіреними сигналами вузла в такому порядку: реальний TCP-вузол, позначений токеном
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, який бачить політика), власний вердикт конвеєра
`AUTHZ_HEADER_PEER_LOCALITY` (який бачать обробники маршрутів і якому довіряють лише тоді, коли
встановлено `OMNIROUTE_PEER_STAMP_TOKEN`), або реальний вузол сокета для прямих викликів. `Host` /
`nextUrl.hostname` ніколи не враховуються, а початкове встановлення пароля
(`POST /api/settings/require-login`) підпорядковується тому самому обмеженню, замість того щоб бути відкритим для кожного
вузла мережі (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передає нижче власний вердикт `peerContext`,
тому заголовки ПОЧАТКОВОГО (до видалення заголовків) запиту ніколи не визначають його.

### Рівень 3 — КЕРУВАННЯ (за замовчуванням)

Усі інші маршрути керування. Автентифікація обов’язкова, якщо не налаштовано
`requireLogin=false`. Токени CLI можуть автентифікувати ці маршрути (loopback + дійсний HMAC).

## Порядок оцінювання

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти далі
     → не loopback, Bearer із областю manage
        І isLocalOnlyBypassableByManageScope     → дозволити (management_key)
     → інакше                                     → відхилити 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → дозволити (system)
  3. hasValidCliToken(headers)?
     → дозволити (cli) [loopback + перевірка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) або requireLogin=true?
     → isDashboardSessionAuthenticated?
        → дозволити (dashboard_session)
     → Bearer із областю manage на маршруті, який не можна обійти?
        → дозволити (management_key)
     → відхилити 401/403
  5. requireLogin=false?
     → дозволити (anonymous)
```

Гілка області manage на кроці 1 — це єдиний автентифікований шлях, який може задовольнити маршрут
LOCAL_ONLY; режим помилки бекенду автентифікації повертає 503 (а не 403), щоб
прострочена БД непомітно не призводила до зниження рівня до «відхилити».

## Додавання нового маршруту, здатного запускати процеси

1. Додайте префікс шляху до `LOCAL_ONLY_API_PREFIXES` у
   `src/server/authz/routeGuard.ts`
2. Додайте тест до `tests/unit/authz/routeGuard.test.ts`, який перевіряє, що
   `isLocalOnlyPath()` повертає true для нового префікса
3. **Ніколи не пропускайте цей крок** — див. жорстке правило №15 у `CLAUDE.md`
4. Вирішіть: чи має цей маршрут ТАКОЖ входити до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Типова відповідь — **ні**. Додавайте його лише тоді, коли маршрут безпечно надавати
   власнику manage-scope (тобто він НЕ запускає довільний код, керований користувачем).

## Додавання шляху, який можна обійти за допомогою manage-scope

1. Переконайтеся, що маршрут не виконує наданий користувачем код або команди. Якщо
   виконує, зупиніться — цей виняток тут не підходить.
2. Додайте префікс до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` у
   `src/server/authz/routeGuard.ts`
3. Додайте покриття в `tests/unit/authz/management-policy.test.ts` для всіх чотирьох
   варіантів запиту: без Bearer (403), manage Bearer (дозволити), не-manage Bearer
   (403), а також окрему регресійну перевірку для кожного префікса, щоб
   `/api/cli-tools/runtime/*` залишався доступним лише через loopback навіть із manage Bearer.

## Документування рівнів безпеки в OpenAPI

Під час додавання нового маршруту до `docs/openapi.yaml` застосуйте відповідне
розширення постачальника, якщо маршрут класифіковано в `routeGuard.ts`:

| Класифікація routeGuard.ts                      | YAML-анотація              | Застосування правил                                       |
| ----------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                       | `x-loopback-only: true`    | Безумовно блокується для з’єднань не через loopback       |
| `ALWAYS_PROTECTED_API_PATHS`                    | `x-always-protected: true` | Автентифікація обов’язкова навіть за `requireLogin=false` |
| Внутрішній маршрут адміністрування/налагодження | `x-internal: true`         | Типово прихований у /dashboard/api-endpoints              |
| Немає (публічний / стандартна автентифікація)   | (анотація не потрібна)     | Стандартний доступ, керований `requireLogin`              |

### Валідація

Два скрипти забезпечують узгодженість між YAML-анотаціями та `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершується помилкою, якщо покриття < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершується помилкою, якщо анотації `x-loopback-only` або
  `x-always-protected` не відповідають константам часу компіляції

Обидва скрипти запускаються в pre-commit hook і в CI.

### Правило щодо хибнопозитивних результатів

Якщо `x-always-protected` або `x-loopback-only` додано до маршруту, якого НЕМАЄ у
відповідній константі `routeGuard.ts`, скрипт перевірки покриття завершується помилкою. Правильне виправлення — завжди узгодити
YAML із тим, що фактично забезпечує `routeGuard.ts`, а не додавати маршрути до `routeGuard.ts`
без одночасної реалізації логіки застосування відповідних правил.
