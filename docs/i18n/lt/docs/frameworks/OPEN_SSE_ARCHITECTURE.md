> **Trumpai**: `open-sse/` yra pagrindinis srautinio perdavimo variklis, apdorojantis kiekvieną LLM užklausą sistemoje „OmniRoute“. Jį sudaro ~1 400 failų, kuriuose įgyvendintas užklausų apdorojimo konvejeris, vykdyklės, paslaugos, MCP serveris ir vertimo sluoksnis. Šiame vadove paaiškinama, kaip šios dalys susijungia į bendrą visumą.

**Šaltinis:** `open-sse/` (darbo srities paketas, ~1 440 ne testinių `.ts` failų)

## Kodėl naudojamas atskiras darbo srities paketas?

`open-sse/` yra **savarankiška darbo sritis** „OmniRoute“ monorepozitorijoje dėl kelių priežasčių:

1. **Pakartotinis panaudojimas** — `open-sse` publikuojamas npm kaip `@omniroute/open-sse`, todėl kiti projektai gali jį naudoti nepriklausomai
2. **Aiškios ribos** — srautinio perdavimo variklis atskirtas nuo „OmniRoute“ specifinio UI / DB sluoksnio
3. **Našumas** — variklis neturi Next.js priklausomybių, todėl CLI ir serverio neturinčiose aplinkose paleidimas iš neaktyvios būsenos yra spartesnis
4. **Versijų valdymas** — `open-sse` gali leisti versijas pagal savo tvarkaraštį

```json
// package.json
"workspaces": ["open-sse"]
```

## Užklausų apdorojimo konvejeris

Kiekviena LLM užklausa apdorojama **5 etapų konvejeriu**:

```
                              ┌──────────────────┐
   HTTP užklausa               │  1. MARŠRUTAS    │   derinio nustatymas, modelio parinkimas
   (Next.js maršrutas)         └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  2. VERTIMAS      │   formato konvertavimas (OpenAI ↔ Claude ↔ Gemini)
                              └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  3. VYKDYMAS      │   teikėjo vykdyklė, HTTP, kartojimas, grandinės pertraukiklis
                              └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  4. SRAUTAS       │   SSE transformavimas, atgalinis slėgis
                              └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  5. REGISTRAVIMAS │   naudojimo stebėjimas, iškvietimų žurnalas, klaidų klasifikavimas
                              └────────┬─────────┘
                                       │
                                       ▼
                              HTTP atsakas (SSE arba JSON)
```

### 1 etapas: maršruto parinkimas (services/combo.ts)

**Įėjimo taškas**: `handleComboChat()`, esantis `services/combo.ts`

Užklausa susiejama su konkrečiu `(provider, model, account, credentials)` rinkiniu:

- Derinys surandamas pagal ID (arba sukuriamas virtualus `auto/*` modelių derinys)
- Pritaikoma maršruto parinkimo strategija (prioritetinė, svertinė, ciklinė ir kt.)
- Atmetami sutrikę teikėjai (grandinės pertraukiklis)
- Parenkamas kitas tinkamas tikslas

Naudojant `auto/*` modelius, šiame etape taip pat:

- Paleidžiamas **16 veiksnių vertinimo** algoritmas (`services/autoCombo/`)
- Pagal veikimo būklę, kainą, delsą ir kitus veiksnius parenkama `provider+model` pora

### 2 etapas: vertimas (translator/)

Jei pradinis formatas (pvz., OpenAI) skiriasi nuo tikslinio formato (pvz., Claude), užklausa **išverčiama**:

- Sistemos raginimas → sistemos pranešimas
- Įrankių apibrėžtys → konkrečiam teikėjui skirtas įrankių formatas
- Samprotavimo / mąstymo parametrai → konkrečiam teikėjui skirti atitikmenys
- Pranešimų vaidmenų normalizavimas (`developer` → `system`, kai naudojamas ne OpenAI)

`translator/index.ts` pateikia:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 3 etapas: vykdymas (executors/)

**Įėjimo taškas**: `getExecutor(providerId).execute(request, options)`

Visi teikėjai naudoja `DefaultExecutor` (`executors/default.ts`) per atsarginę `getExecutor()` gamyklą. Vykdyklė:

- Sukuria išorinės paslaugos URL (`buildUrl()`)
- Prideda konkrečiam teikėjui skirtas antraštes (`buildHeaders()`)
- Transformuoja užklausos turinį (`transformRequest()`)
- Siunčia HTTP užklausą, taikydama pakartotinius bandymus ir eksponentinį laukimo intervalo didinimą
- Prireikus atnaujina autentifikavimą (OAuth teikėjams)

Visos vykdyklės išplečia `BaseExecutor` (`executors/base.ts`, 1170 kodo eilučių), kuris suteikia:

- Bendrą pakartotinių bandymų logiką
- Integraciją su tarpiniu serveriu
- Integraciją su grandinės pertraukikliu
- Naudojimo registravimo kablius

### 4 etapas: srautas (utils/stream.ts)

Srautinių atsakų atveju vykdyklė grąžina **ReadableStream**. Apdorojimo modulis:

- Perduoda duomenis per SSE transformavimo srautą (`createSSETransformStreamWithLogger`)
- Periodiškai siunčia ryšio palaikymo signalus neaktyviems ryšiams aptikti
- Sklandžiai apdoroja kliento atsijungimą (`pipeWithDisconnect`)
- Nesrautiniams klientams transformuoja SSE → JSON

Nesrautinių atsakų atveju vykdyklė grąžina išanalizuotą JSON objektą, kuris perduodamas nepakeistas.

### 5 etapas: registravimas (services/usage.ts)

Po atsako (sėkmingo ar nesėkmingo) užregistruojami naudojimo duomenys:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` iš atsako
- `cost_usd`, apskaičiuota pagal kainodaros duomenis
- `latency_ms`, `status`, `error_class`, jei įvyko klaida
- Išsaugoma lentelėje `usage_history`

Iškvietimų žurnalų artefaktai (jei įjungta) įrašomi į `${DATA_DIR}/call_logs/`.

## Pagrindiniai failai Deep-Dive

### chatCore.ts (5977 eilutės)

The** pagrindinis užklausų tvarkytojas** . Nepaisant dydžio, jis turi aiškią struktūrą:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

Nepaisant to, kad ji yra viena milžiniška funkcija, ji suskirstyta į** komentuojamos skiltys** kad žemėlapis į 5 etapų dujotiekį.

### combo.ts (4456 LOC)

The** maršruto variklis** kuri išsprendžia kombinaciją su užsakytais taikiniais.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

### base.ts (1170 LOC)

The** abstraktus vykdytojas** kad kiekviena vykdytojų klasė tęsiasi (tiesiogiai arba per `DefaultExecutor` ir kitus poklasius). Jame yra:

- `buildUrl()` — numatytoji URL konstrukcija (pritaikius poklasius nepaisoma)
- `buildHeaders()` — numatytosios antraštės (auth, turinio tipas)
- `transformRequest()` — perdavimas pagal numatytuosius nustatymus
- `execute()` — pagrindinė HTTP kilpa su retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

Konkrečios teikėjo elgsena (auth antraštės, bazinės URL, versijos antraštės) konfigūruojama per teikėjo registrą, o ne atskiras vykdytojų klases.

````

## Vykdytojai (150 modulių)

Dažniausiai vienas failas vienam teikėjui. Visos vykdytojų klasės išplečia `BaseExecutor` ir nepaiso to, kas skiriasi; kiti moduliai yra pagalbininkai pagal teikėją (įrankių schemos, fetch/TTS adapteriai, keiksmažodžių tvarkyklės).

### Įprasti modeliai

Teikėjai išsprendžiami per `getExecutor(providerId)`, kuris grąžina sukonfigūruotą vykdytoją. OpenAI/Anthropic-compatible teikėjai naudoja `DefaultExecutor` (`executors/default.ts`). Konkrečiam teikėjui būdinga elgsena (bazinė URL, autentifikavimo antraštės, API versija) sukonfigūruota `open-sse/config/providers/`, o užklausos turinio transformacijos apdorojamos `open-sse/translator/`.

**Individualus URL** nustatyta per teikėjo konfigūraciją:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Tinkintas autentifikavimas** tvarkoma per teikėjo registro autentifikavimo konfigūraciją (API raktas, OAuth, antraštės profiliai).

**Individualios užklausos kūnas** transformacijos (pvz., Anthropic atskiriančios `system` nuo `messages`) kiekvienam teikėjui registruojamos `open-sse/translator/`.

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Rezoliucija eina per `ExecutorRegistry` (`executors/registry.ts`): kiekvienas specializuotas vykdytojas yra deklaruojamas integruotoje `executors/index.ts` lentelėje ir registruojamas per `registerExecutor(alias, instance)` modulio apkrovos metu; `getExecutor()` konsultuojasi su registru ir grįžta į atmintyje įrašytą `DefaultExecutor` bet kuriam teikėjui be specializuoto įrašo. Visą slapyvardžio → vykdytojo atvaizdavimą apibūdina auksinis testas `tests/unit/executor-map-golden.test.ts`.

## Vertikliai

Verčia tarp **3 formatų**: OpenAI, Anthropic, Gemini, taip pat naujosios Responses API.

### Kada atliekamas vertimas

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Dažniausi vertimai:

- `OpenAI → Anthropic`: atskiras `system` laukas, `x-api-key` antraštė
- `OpenAI → Gemini`: `contents` vietoje `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input` masyvas, `previous_response_id` būsena

### Apdorojami išskirtiniai atvejai

- `developer` vaidmuo → `system` ne OpenAI teikėjams
- `system` vaidmuo → sujungiamas su pirmuoju naudotojo pranešimu GLM/ERNIE sistemose
- `json_schema` → Gemini `responseMimeType` + `responseSchema`
- `tools` → teikėjui būdingas įrankių formatas
- Mąstymo parametrai (o1, Claude) → teikėjui būdingi atitikmenys

## MCP serveris

`open-sse/mcp-server/` įgyvendina **Model Context Protocol** serverį:

- **110 įrankių** (teikėjų valdymas, deriniai, atmintis, podėlis, glaudinimas, tarpinis serveris, įgūdžiai, žaidybinimas, papildiniai, Notion, Obsidian, vietinis tekstynas)
- **3 transportai**: stdio, SSE, Streamable HTTP
- **33 aprėptys**, skirtos detaliam įgaliojimų valdymui

### Įrankių registravimas

Įrankiai registruojami kaip atskiri failai kataloge `open-sse/mcp-server/tools/`; kiekvienas jų eksportuoja pavadinimą, schemą, apdorojimo funkciją ir aprėptį:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Gauti sistemos būklės momentinę kopiją",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transportai

```ts
// stdio (CLI naudojimas)
startMcpStdio(server);

// SSE (HTTP pagrįstas srautinis perdavimas)
startMcpSse(server, port);

// Streamable HTTP (šiuolaikinis MCP)
startMcpStreamable(server, port);
```

### Įgaliojimų tikrinimas

Kiekvienam įrankio iškvietimui atliekamos aprėpties patikros (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Nepakankama aprėptis");
}
```

## Transformatoriai

`open-sse/transformer/` konvertuoja tarp **Chat Completions** ir **Responses API** formatų.

### Kodėl naudojamas atskiras transformatorius?

Responses API yra naujasis OpenAI formatas, palaikantis **būseną išlaikančius pokalbius** (`previous_response_id`). Kai klientas siunčia Responses užklausą, OmniRoute:

1. Viduje konvertuoja Responses → Chat Completions
2. Išsiunčia teikėjui (bet kuriam teikėjui, palaikančiam Chat Completions)
3. Konvertuoja atsakymą atgal į Responses formatą
4. Srautiniu būdu perduoda konvertuotą atsakymą klientui

Transformatorius (`transformer/responsesTransformer.ts`) pateikia:

```ts
createResponsesApiTransformStream(): TransformStream
```

Jis apdoroja:

- `response.output_item.added` įvykius
- `response.output_text.delta` įvykius
- `response.completed` įvykį
- Įrankių iškvietimų susiejimą (`function_call` ↔ `tool_calls`)

## Antimodeliai

❌ **Sinchroniniai DB iškvietimai faile `combo.ts`** — iš anksto apskaičiuokite ir laikykite talpykloje
❌ **Pakartotinių bandymų logika apdorojimo funkcijose** — naudokite `retry()` iš atsparumo paslaugos
❌ **Tiesioginė prieiga prie teikėjo konfigūracijos** — naudokite `providerRegistry` prieigos metodus
❌ **Programiniame kode fiksuotos atsarginių variantų grandinės** — apibrėžkite faile `modelFamilyFallback.ts`
❌ **Būsenos keitimas tarp lygiagrečių užklausų** — naudokite tik užklausos aprėpties kontekstą

## Naujo komponento pridėjimas

### Naujos paslaugos pridėjimas

1. Sukurkite `open-sse/services/[serviceName].ts`, turintį aiškiai apibrėžtą atsakomybę
2. Eksportuokite pagrindinę apdorojimo funkciją ir visas konstantas
3. Pridėkite vienetinius testus faile `tests/unit/services/[serviceName].test.mjs`
4. Integruokite į užklausų apdorojimo konvejerį faile `handlers/chatCore.ts` (jei susiję su maršrutizavimu)
5. Atnaujinkite maršrutizavimo logiką faile `combo.ts`, jei paslauga turi įtakos paskirties taško pasirinkimui
6. Aprašykite šiame faile

### Naujo vykdiklio pridėjimas

1. Sukurkite `open-sse/executors/[provider].ts`, išplečiantį `BaseExecutor`
2. Užregistruokite faile `config/providerRegistry.ts`
3. Pridėkite prie `executors/index.ts` fabriko
4. Pridėkite vykdiklio vienetinius testus
5. Aprašykite faile `docs/architecture/ARCHITECTURE.md`

### Naujo MCP įrankio pridėjimas

1. Sukurkite arba atnaujinkite `open-sse/mcp-server/tools/[category]Tools.ts`
2. Apibrėžkite įvesčių Zod schemą
3. Užregistruokite įrankį faile `mcp-server/index.ts`
4. Pridėkite prie aprėpčių matricos kataloge `mcp-server/auth/`
5. Pridėkite vienetinius testus
