वेब कुकी प्रदाता OmniRoute को API कुंजी के बजाय आपके मौजूदा ब्राउज़र सत्र के माध्यम से किसी AI सेवा का उपयोग करने देते हैं। ये तब उपयोगी होते हैं जब आपके पास पहले से ही किसी सेवा की वेबसाइट के माध्यम से उसकी पहुँच हो और आप चाहते हों कि OmniRoute उसी प्रमाणित सत्र का उपयोग करे।

API-कुंजी प्रदाताओं के विपरीत, वेब कुकी प्रदाता उन क्रेडेंशियल्स का उपयोग करके प्रमाणीकरण करते हैं जिन्हें आपका ब्राउज़र वेबसाइट पर भेजता है।

---

# शुरू करने से पहले

> **महत्वपूर्ण:** क्रेडेंशियल्स हमेशा किसी **लाइव नेटवर्क अनुरोध** से कॉपी करें, अपने ब्राउज़र के कुकी स्टोरेज से **नहीं**।

कई प्रमाणीकरण समस्याएँ गलत स्थान से कुकीज़ कॉपी करने के कारण होती हैं।

## कुकी स्टोरेज से कॉपी न करें

अधिकांश ब्राउज़र संग्रहीत कुकीज़ को इस माध्यम से दिखाते हैं:

```
डेवलपर टूल्स
→ एप्लिकेशन (या स्टोरेज)
→ कुकीज़
```

हालाँकि ये कुकीज़ सही दिख सकती हैं, लेकिन वे:

- पुरानी हो सकती हैं
- अधूरी हो सकती हैं
- उनमें ऐसी कुकीज़ अनुपस्थित हो सकती हैं जो केवल प्रमाणित अनुरोधों के साथ भेजी जाती हैं

इन मानों का उपयोग करने पर प्रमाणीकरण विफल हो सकता है, भले ही वे मान्य दिखाई दें।

## लाइव अनुरोध से कॉपी करें

इसके बजाय, किसी सफल अनुरोध की कुकीज़ का उपयोग करें:

```
डेवलपर टूल्स
→ नेटवर्क
→ पेज रीफ़्रेश करें
→ कोई चैट या वार्तालाप अनुरोध खोलें
→ अनुरोध हेडर
→ कुकी
```

`Cookie` अनुरोध हेडर में वही सटीक प्रमाणीकरण जानकारी होती है जिसका आपके ब्राउज़र ने सफलतापूर्वक उपयोग किया था।

अधिकांश वेब कुकी प्रदाताओं के लिए, यही वह मान है जिसे OmniRoute में पेस्ट किया जाना चाहिए।

# सामान्य सेटअप

अधिकांश वेब कुकी प्रदाताओं के लिए सेटअप प्रक्रिया समान होती है।

1. प्रदाता की वेबसाइट में साइन इन करें।
2. ब्राउज़र के डेवलपर टूल्स खोलें।
3. **नेटवर्क** टैब खोलें।
4. पेज रीफ़्रेश करें।
5. कोई प्रमाणित चैट या वार्तालाप अनुरोध खोलें।
6. आवश्यक प्रमाणीकरण क्रेडेंशियल्स कॉपी करें।
7. OmniRoute खोलें।
8. **प्रदाता → प्रदाता जोड़ें** पर जाएँ।
9. अपना वेब कुकी प्रदाता चुनें।
10. क्रेडेंशियल्स पेस्ट करें।
11. **कनेक्शन का परीक्षण करें** पर क्लिक करें।
12. प्रदाता को सहेजें।

आवश्यक सटीक क्रेडेंशियल्स प्रदाता पर निर्भर करते हैं।

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) एक निःशुल्क उपभोक्ता चैट प्लेटफ़ॉर्म है, जिसके लिए साइन अप करना आवश्यक नहीं है — पहले विज़िट पर सत्र गुमनाम रूप से बनाया जाता है और तीन कुकी के माध्यम से बना रहता है: `uid`, `si_usr_id`, और `si_ses_id`। OmniRoute एक ही मॉडल आईडी (`notrack-c`, उपनाम `ntw`) के माध्यम से उसी `/api/dispatch` एंडपॉइंट को प्रॉक्सी करता है।

### कनेक्ट करने के चरण

1. अपने ब्राउज़र में [notrack.ai](https://notrack.ai) खोलें और गुमनाम सत्र कुकी को सेट होने दें।
2. **DevTools → Network** खोलें, पेज को रीफ़्रेश करें और किसी भी `/api` अनुरोध पर क्लिक करें।
3. **Request Headers** में, पूरे `Cookie` हेडर का मान कॉपी करें।
4. OmniRoute में, **Providers → Add Provider → NoTrack Web (Free)** पर जाएँ।
5. कुकी स्ट्रिंग को `apiKey` फ़ील्ड में पेस्ट करें और **Save** करें।

OmniRoute पेस्ट की गई स्ट्रिंग से `uid`, `si_usr_id`, और `si_ses_id` निकालता है और केवल उन्हीं युग्मों के साथ एक साफ़ `Cookie` हेडर फिर से बनाता है — साथ ही, मौजूद होने पर `nt_session` (लॉग-इन खातों के लिए सेट किया गया `ntk_…` टोकन) भी शामिल करता है। यदि इन तीनों में से कोई भी मौजूद नहीं है, तो मूल पेस्ट की गई स्ट्रिंग बिना बदलाव के अग्रेषित कर दी जाती है, ताकि ऑपरेटर वैकल्पिक संरचनाओं के साथ प्रयोग कर सकें।

### मॉडल आईडी

| मॉडल आईडी   | प्रदर्शित नाम | टिप्पणियाँ                                        |
| ----------- | ------------- | ------------------------------------------------- |
| `notrack-c` | NoTrack C     | डिफ़ॉल्ट — अपस्ट्रीम डिस्पैच मॉडल `C`।            |
| `C`         | NoTrack C     | `notrack-c` का उपनाम (मूल अपस्ट्रीम डिस्पैच कोड)। |
| `notrack`   | NoTrack C     | `notrack-c` का उपनाम।                             |
| `ntw`       | NoTrack C     | `notrack-c` का संक्षिप्त उपनाम।                   |

चारों मॉडल आईडी एक ही अपस्ट्रीम डिस्पैच मॉडल (`C`) पर मैप होती हैं।

### अनुरोध विकल्प

एक्ज़ीक्यूटर अनुरोध बॉडी में इन वैकल्पिक फ़ील्ड को स्वीकार करता है:

| बॉडी फ़ील्ड           | डिफ़ॉल्ट | उद्देश्य                                                                    |
| --------------------- | -------- | --------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`  | डिस्पैच मोड (मुक्त-रूप स्ट्रिंग; अपस्ट्रीम `usual`, … स्वीकार करता है)      |
| `notrack_max_turns`   | `6`      | उत्तर देने से पहले अपस्ट्रीम द्वारा लिए जा सकने वाले आंतरिक टर्न की संख्या। |
| `notrack_chat_id`     | `null`   | किसी मौजूदा अपस्ट्रीम चैट को फिर से शुरू करें (नई चैट के लिए इसे छोड़ दें)। |
| `notrack_attachments` | `[]`     | अपस्ट्रीम अटैचमेंट डिस्क्रिप्टरों की पास-थ्रू ऐरे।                          |
| `notrack_regenerate`  | `false`  | पिछले टर्न के लिए दोबारा बनाया गया उत्तर माँगने हेतु `true` सेट करें।       |

### क्षमताएँ

- **स्ट्रीमिंग और नॉन-स्ट्रीमिंग** चैट कम्प्लीशन।
- **टूल कॉलिंग** — अनुरोध पर `tools: [...]` सेट करें; एक्ज़ीक्यूटर उन्हें टूल-कॉल एनवेलप कॉन्ट्रैक्ट में क्रमबद्ध करता है और मॉडल की प्रतिक्रियाओं को वापस OpenAI `tool_calls` में पार्स करता है।
- **`response_format`** — `json_object` और `json_schema` समर्थित हैं। एक्ज़ीक्यूटर मॉडल के उत्तर से पहला JSON ऑब्जेक्ट निकालता है और लौटाने से पहले उसे स्ट्रिंग में बदलता है।
- **रीज़निंग संकेत** — जब अपस्ट्रीम कोई `thinking` इवेंट भेजता है, तो एक्ज़ीक्यूटर एक `reasoning` डेल्टा उत्सर्जित करता है।

### सीमाएँ

- अपस्ट्रीम गुमनाम उपयोग कोटा लागू करता है — सीमा पार होने पर एक्ज़ीक्यूटर उपयोगकर्ता-अनुकूल संदेश के साथ 429 प्रदर्शित करता है।
- सभी मॉडल आईडी एक ही अपस्ट्रीम डिस्पैच मॉडल पर रिज़ॉल्व होती हैं; प्रति-मॉडल स्विच उपलब्ध नहीं है।
- एक्ज़ीक्यूटर अपस्ट्रीम के `/api/chats` एंडपॉइंट को कॉल नहीं करता, इसलिए चैट इतिहास / सत्रों को अपने-आप प्रबंधित नहीं किया जाता। किसी मौजूदा अपस्ट्रीम चैट को फिर से शुरू करने के लिए `notrack_chat_id` का उपयोग करें।

# वेब कुकी प्रोवाइडर क्या कर सकते हैं और क्या नहीं

वेब कुकी प्रोवाइडर किसी वेबसाइट के चैट इंटरफ़ेस का दोबारा उपयोग करते हैं। वे आधिकारिक API जैसी क्षमताएँ **प्रदान नहीं** करते।

## समर्थित

- अपने मौजूदा ब्राउज़र सत्र का उपयोग करके प्रमाणीकरण करना
- अपने खाते के माध्यम से उपलब्ध मॉडलों तक पहुँचना
- चैट प्रतिक्रियाओं को स्ट्रीम करना
- किसी API कुंजी की आवश्यकता नहीं

## समर्थित नहीं

- फ़ंक्शन कॉलिंग
- टूल कॉलिंग
- स्वचालित फ़ाइल संपादन
- एजेंट-आधारित IDE कार्यप्रवाह
- केवल-API सुविधाएँ

यह अपेक्षित व्यवहार है और **कोई** बग नहीं है।

यदि आपको टूल निष्पादन, स्वचालित फ़ाइल संपादन या अन्य एजेंट कार्यप्रवाहों की आवश्यकता है, तो वेब कुकी प्रदाता के बजाय किसी **API-कुंजी प्रदाता** का उपयोग करें।

---

# सत्यापन संबंधी चेतावनी

सफल **कनेक्शन परीक्षण** या कुकी सत्यापन केवल यह पुष्टि करता है कि प्रदान किए गए क्रेडेंशियल अपेक्षित प्रारूप में प्रतीत होते हैं।

Issue #7857 का समाधान होने तक, सफल सत्यापन इस बात की **गारंटी नहीं देता** कि प्रदाता सफलतापूर्वक प्रमाणीकरण करेगा।

यदि प्रमाणीकरण फिर भी विफल रहता है, तो पुष्टि करें कि आपने क्रेडेंशियल ब्राउज़र कुकी स्टोरेज के बजाय किसी सक्रिय नेटवर्क अनुरोध से कॉपी किए हैं।

---

# समस्या निवारण

## प्रमाणीकरण विफल होता है

पुष्टि करें कि क्रेडेंशियल यहाँ से कॉपी किए गए थे:

```
Network
→ Request Headers
→ Cookie
```

और यहाँ से **नहीं**:

```
Application
→ Cookies
```

---

## कुकी ब्राउज़र में काम करती है, लेकिन OmniRoute में नहीं

कुछ प्रदाताओं में ऐसी कुकी शामिल होती हैं, जो केवल प्रमाणित अनुरोधों के दौरान भेजी जाती हैं।

किसी वार्तालाप को सफलतापूर्वक खोलने के बाद नए नेटवर्क अनुरोध से क्रेडेंशियल दोबारा कॉपी करें।

---

## सत्र समाप्त हो गया

वेब कुकी प्रदाता आपके मौजूदा ब्राउज़र सत्र का उपयोग करते हैं।

यदि आपका ब्राउज़र सत्र समाप्त हो जाता है या आप साइन आउट करते हैं, तो आपको क्रेडेंशियल का नया सेट कॉपी करना होगा। समर्थित वेब प्रदाताओं के लिए कुकी नवीनीकरण स्वचालित करने हेतु सहायक टूल [ब्राउज़र सत्र सिंक एक्सटेंशन](../guides/SESSION-SYNC-EXTENSION.md) देखें।

---

## कनेक्शन परीक्षण सफल होता है, लेकिन अनुरोध विफल होते हैं

Issue #7857 का समाधान होने तक, सत्यापन में सफल होना इस बात की गारंटी नहीं देता कि प्रमाणीकरण अनुरोध सफल होगा।

आगे समस्या निवारण करने से पहले किसी नए प्रमाणित अनुरोध से अपने क्रेडेंशियल दोबारा कॉपी करें।

---

## ChatGPT Web में "Unsupported ChatGPT integrity dependency" के साथ विफलता

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

क्रेडेंशियल ठीक है — यह त्रुटि सत्र से नहीं, बल्कि ब्रिज से आती है। chatgpt.com प्रत्येक डिप्लॉयमेंट के लिए अपने
मॉड्यूल आईडी निर्धारित करता है, और पहले ब्रिज अपने द्वारा इंस्टैंशिएट किए गए Sentinel सहायक की आईडी को पिन करता था, इसलिए
chatgpt.com के ऐसे रीबिल्ड ने, जिसमें सहायक का नाम बदल गया था, कुकी के वैध बने रहने के बावजूद हर टर्न को विफल कर दिया। कनेक्शन को
दोबारा अधिकृत करने से इसे ठीक नहीं किया जा सकता।

वे बिल्ड, जो पेज के अपने रनटाइम के माध्यम से मॉड्यूल को रिज़ॉल्व करते हैं, किसी आईडी को पिन नहीं करते और इस समस्या से प्रभावित नहीं होते। यदि आपको यह
त्रुटि दिखाई देती है, तो OmniRoute को अपग्रेड करें और कनेक्शन जाँच दोबारा चलाएँ।

# प्रदाता का उदाहरण

किसी प्रदाता के लिए संपूर्ण चरण-दर-चरण मार्गदर्शन हेतु देखें:

- **Claude Web** — `docs/providers/CLAUDE_WEB.md`

Claude Web मार्गदर्शिका वेब कुकी प्रदाता के लिए संपूर्ण सेटअप प्रक्रिया प्रदर्शित करती है और संदर्भ कार्यान्वयन के रूप में काम करती है।

# सर्वोत्तम अभ्यास

- किसी नए प्रमाणित अनुरोध से क्रेडेंशियल कॉपी करें।
- पुरानी कुकी का दोबारा उपयोग करने से बचें।
- वेब कुकी प्रदाताओं का उपयोग करते समय अपने ब्राउज़र सत्र को सक्रिय रखें।
- कॉपी की गई कुकी को संवेदनशील क्रेडेंशियल मानें।
- जब आपको फ़ंक्शन कॉलिंग या एजेंट कार्यप्रवाहों की आवश्यकता हो, तब API-कुंजी प्रदाताओं का उपयोग करें।
