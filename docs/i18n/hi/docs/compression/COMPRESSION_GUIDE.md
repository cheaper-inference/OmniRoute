> योग्य कॉन्टेक्स्ट पर स्वचालित रूप से 15-95% बचाएँ। त्वरित अवलोकन के लिए, [README का कम्प्रेशन अनुभाग](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) देखें।

## अवलोकन

OmniRoute एक मॉड्यूलर प्रॉम्प्ट कम्प्रेशन पाइपलाइन लागू करता है, जो अनुरोधों के अपस्ट्रीम प्रदाताओं तक पहुँचने से **पहले ही सक्रिय रूप से** चलती है। इसका अर्थ है कि आपके टोकन की बचत पारदर्शी रूप से होती है — आपके वर्कफ़्लो में किसी बदलाव की आवश्यकता नहीं है।

```
क्लाइंट अनुरोध
  → कम्प्रेशन रणनीति चयनकर्ता
    → कॉम्बो ओवरराइड? → कॉम्बो सेटिंग का उपयोग करें
    → ऑटो-ट्रिगर थ्रेशोल्ड? → ऑटो मोड का उपयोग करें
    → डिफ़ॉल्ट मोड? → ग्लोबल सेटिंग का उपयोग करें
    → बंद? → कम्प्रेशन छोड़ें
  → चयनित कम्प्रेशन मोड
    → बंद: कोई कम्प्रेशन नहीं
    → लाइट: सुरक्षित व्हाइटस्पेस/फ़ॉर्मेटिंग क्लीनअप (~15%)
    → स्टैंडर्ड: Caveman-शैली में फ़िलर हटाना (~30%)
    → एग्रेसिव: हिस्ट्री एजिंग + सारांशीकरण (~50%)
    → अल्ट्रा: ह्यूरिस्टिक प्रूनिंग + कोड-ब्लॉक थिनिंग (~75%)
    → RTK: कमांड-सचेत टर्मिनल/टूल-आउटपुट फ़िल्टरिंग (60-90% अपस्ट्रीम सीमा)
    → स्टैक्ड: क्रमबद्ध मल्टी-इंजन पाइपलाइन, आम तौर पर पहले RTK फिर Caveman (78-95% योग्य सीमा)
  → कम्प्रेस किया गया अनुरोध → प्रदाता
```

## संपीड़न मोड

### बंद

कोई संपीड़न लागू नहीं किया जाता। सभी संदेश बिना किसी बदलाव के आगे भेजे जाते हैं।

### लाइट मोड (~15% बचत, <1ms विलंबता)

सबसे सुरक्षित मोड — फ़ॉर्मैटिंग की सफ़ाई। इसके टूल-रिज़ल्ट ट्रंकेशन में डेटा नष्ट हो सकता है, इसलिए डिफ़ॉल्ट
पथ (बिना `allow-lossy`, `engine:lite` या नामित-कॉम्बो ऑप्ट-इन के) `compressToolResults: false` के साथ लाइट मोड
चलाता है: पहले के टूल-रिज़ल्ट प्रदाता तक बिना किसी बदलाव के पहुँचते हैं।

| तकनीक                    | विवरण                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | लगातार आने वाली खाली पंक्तियों और अंत के स्पेस को मिलाना                                    |
| `dedupSystemPrompt`      | डुप्लिकेट सिस्टम संदेश हटाना                                                                |
| `compressToolResults`    | पहले के टूल-रिज़ल्ट को लाइट कैप तक ट्रंकेट करना (डेटा-हानिकारक: केवल अनुरोध ऑप्ट-इन के साथ) |
| `removeRedundantContent` | दोहराए गए निर्देश हटाना                                                                     |
| `replaceImageUrls`       | बेस64 इमेज डेटा URI को छोटा करना                                                            |

**इनके लिए सबसे उपयुक्त:** हमेशा चालू उपयोग, सुरक्षा-आवश्यक वर्कफ़्लो।

### मानक मोड (~30% बचत)

[Caveman](https://github.com/JuliusBrussee/caveman) से प्रेरित — अर्थ बनाए रखते हुए भराव शब्दों और विस्तृत वाक्यांशों को हटाता है:

- भराव शब्द हटाता है ("please", "I think", "basically", "actually")
- विस्तृत वाक्यांशों को संक्षिप्त करता है ("in order to" → "to", "as a result of" → "because")
- विनम्र अनिश्चितता वाले वाक्यांश हटाता है ("Would you mind...", "If you could possibly...")
- कोडिंग प्रॉम्प्ट के लिए अनुकूलित 30+ रेगेक्स नियम

**इनके लिए सबसे उपयुक्त:** दैनिक कोडिंग वर्कफ़्लो, लागत-सचेत टीमें।

### आक्रामक मोड (~50% बचत)

लंबे सत्रों के लिए स्मार्ट हिस्ट्री प्रबंधन:

- **संदेश एजिंग** — पुराने संदेशों को क्रमशः अधिक संपीड़ित किया जाता है
- **टूल-रिज़ल्ट संपीड़न** — लंबे टूल आउटपुट को ट्रंकेट या हटाया जाता है (पहली/अंतिम पंक्तियाँ,
  मैच-पंक्ति फ़िल्टरिंग, JSON कुंजी संक्षिप्तीकरण)
- **संरचनात्मक अखंडता सुरक्षा** — सुनिश्चित करती है कि `tool_use` + `tool_result` युग्म सुसंगत रहें
- **कॉन्टेक्स्ट विंडो जागरूकता** — प्रति-मॉडल टोकन सीमाओं का पालन करती है

**इनके लिए सबसे उपयुक्त:** विस्तृत डीबगिंग सत्र, बड़े कोडबेस।

### अल्ट्रा मोड (~75% बचत)

टोकन-आवश्यकता वाले परिदृश्यों के लिए अधिकतम संपीड़न:

- **ह्यूरिस्टिक प्रूनिंग** — गद्य का स्कोर-आधारित टोकन प्रूनिंग
- **संरचना संरक्षण** — फ़ेंस किए गए कोड ब्लॉक, इनलाइन कोड, URL और आइडेंटिफ़ायर को
  टॉम्बस्टोन किया जाता है और फिर बिना किसी बदलाव के पुनः जोड़ा जाता है; उन्हें कभी प्रून नहीं किया जाता
- **वैकल्पिक SLM स्तर** — कॉन्फ़िगर किए जाने पर एक छोटा स्थानीय मॉडल प्रूनिंग को परिष्कृत कर सकता है
- आक्रामक मोड से स्वतंत्र: यह संदेश एजिंग, टूल-रिज़ल्ट संपीड़न
  या फ़ॉलबैक सारांशकार नहीं चलाता (केवल SLM-स्तर की विफलता ही आक्रामक मोड के माध्यम से फ़ॉलबैक पास भेज सकती है)

**इनके लिए सबसे उपयुक्त:** जब आपको बार-बार कॉन्टेक्स्ट सीमाओं का सामना करना पड़ता है।

### RTK मोड (अपस्ट्रीम रेंज का 60-90%)

RTK मोड को कोडिंग-एजेंट सत्रों में दिखाई देने वाले विस्तृत टूल आउटपुट के लिए अनुकूलित किया गया है:

- `git status`, `git diff`, `git log`, टेस्ट रनर,
  TypeScript/Vite/Webpack बिल्ड, ESLint/Biome/Prettier, npm audit/इंस्टॉल, Docker लॉग, इंफ़्रा
  आउटपुट और सामान्य शेल आउटपुट जैसी कमांड/आउटपुट श्रेणियों का पता लगाता है
- `open-sse/services/compression/engines/rtk/filters/` से JSON फ़िल्टर पैक लागू करता है
- प्रोजेक्ट या वैश्विक `filters.toml` फ़ाइलों से RTK TOML स्कीमा v1 फ़िल्टर आयात करता है, जिसमें इनलाइन-टेस्ट
  सत्यापन और प्रोजेक्ट फ़ाइलों के लिए ट्रस्ट-गेटिंग शामिल है
- इनलाइन सत्यापन नमूनों के साथ 56 अंतर्निहित फ़िल्टर उपलब्ध कराता है
- ANSI नियंत्रण अनुक्रम, प्रोग्रेस बार, दोहराई गई पंक्तियाँ और गैर-कार्रवाई योग्य शोर हटाता है
- विफलताओं, त्रुटियों, चेतावनियों, बदली गई फ़ाइलों, सारांशों और लंबे आउटपुट के अंतिम भाग को सुरक्षित रखता है
- ट्रस्ट-गेटेड प्रोजेक्ट फ़िल्टर, वैश्विक फ़िल्टर और वैकल्पिक रिडैक्टेड रॉ-आउटपुट रिकवरी का समर्थन करता है

**इनके लिए सबसे उपयुक्त:** शेल, बिल्ड, टेस्ट, git, grep और फ़ाइल-आउटपुट ट्रांसक्रिप्ट वाले एजेंट सत्र।

### स्टैक्ड मोड (पात्र रेंज का 78-95%)

स्टैक्ड मोड कई संपीड़न इंजनों को एक नियत क्रम में चलाता है। डिफ़ॉल्ट पाइपलाइन है:

```txt
RTK -> Caveman
```

यह क्रम पहले टर्मिनल/टूल आउटपुट को संक्षिप्त रखता है, फिर शेष प्राकृतिक-भाषा प्रॉम्प्ट पर
Caveman का अर्थगत संक्षेपण लागू करता है। स्टैक्ड पाइपलाइन को वैश्विक रूप से या रूटिंग कॉम्बो को
सौंपे गए संपीड़न कॉम्बो के माध्यम से कॉन्फ़िगर किया जा सकता है।

**इनके लिए सबसे उपयुक्त:** बड़े टूल लॉग के साथ मानवीय निर्देशों या असिस्टेंट सारांशों वाले मिश्रित कॉन्टेक्स्ट।

## अपस्ट्रीम बचत का गणित

OmniRoute दो स्रोतों से प्राप्त कम्प्रेशन बचत का दस्तावेज़ीकरण करता है: अपस्ट्रीम प्रोजेक्ट बेंचमार्क और
OmniRoute की अपनी इंजन संरचना।

| स्रोत   | यहाँ उपयोग की गई अपस्ट्रीम README संख्या                                                            |
| ------- | --------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` कम आउटपुट टोकन, `65%` बेंचमार्क औसत आउटपुट बचत, `22-87%` सीमा, और `~46%` इनपुट कम्प्रेशन टूल |
| RTK     | `60-90%` कमांड-आउटपुट बचत; नमूना सत्र में `~118,000 -> ~23,900` टोकन, या `79.7%` बचत (`~80%`)       |

ओवरलैप होने वाले टूल/कॉन्टेक्स्ट पेलोड के लिए, डिफ़ॉल्ट OmniRoute कॉम्बो इंजनों को क्रमबद्ध करता है:

```txt
RTK -> Caveman
```

संयुक्त बचत गुणात्मक होती है, योगात्मक नहीं:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

यह `78-95%` संख्या तब लागू होती है, जब RTK और Caveman दोनों समान इनपुट/कॉन्टेक्स्ट पेलोड को कम कर सकते हैं।
Caveman प्रतिक्रिया आउटपुट मोड अलग है: सक्षम होने पर, Caveman की अपनी आउटपुट बचत (`65%`
औसत, `~75%` प्रमुख आँकड़ा, `22-87%` सीमा) का उपयोग करें। कुल बिलिंग बचत आपके प्रॉम्प्ट/आउटपुट मिश्रण पर निर्भर करती है।

### "पात्र" का वास्तव में क्या अर्थ है

15-95% की प्रमुख सीमा वास्तविक है, लेकिन यह केवल **अनावश्यक रूप से दोहराई गई या अत्यधिक विस्तृत** सामग्री पर लागू होती है — बार-बार आने वाली
त्रुटि पंक्तियाँ, एक बिल्ड लॉग जो उसी चेतावनी को बार-बार दिखाता है, या बहुत बड़ा `grep`/फ़ाइल-रीड डंप। इसका
अर्थ यह **नहीं** है कि प्रत्येक अनुरोध में इतनी बचत होगी।

प्रायोगिक रूप से सत्यापित (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 समान
त्रुटि पंक्तियों वाले Anthropic-आकार के `tool_result` ब्लॉक पर चलाए गए
`stacked` (RTK + Caveman) रन ने **95.93% टोकन बचत / 96.26% कैरेक्टर बचत** दी — जो विज्ञापित
सीमा के ठीक भीतर है। लेकिन सामान्य, गैर-दोहराव वाले टूल आउटपुट (एक साफ़ `grep` मिलान सूची,
एक छोटी फ़ाइल रीड, सामान्य संवादात्मक टेक्स्ट) पर चलाई गई वही पाइपलाइन सही रूप से **लगभग शून्य बचत** देती है, क्योंकि
हटाने के लिए कुछ भी दोहराव वाला नहीं होता और `validateCompression()` (`validation.ts`) ऐसे
पुनर्लेखन को भेजने से मना कर देता है जो कोड ब्लॉक, URLs, शीर्षक, संस्करण, या ALL-CAPS स्थिरांक पहचानकर्ताओं को हटा या बदल सकता हो।

यह अपेक्षित और सुरक्षित व्यवहार है, कोई बग नहीं: ऐसा कोडिंग सत्र जो मुख्यतः साफ़ फ़ाइलों को पढ़ता/grep करता है,
पूर्ण रूप से सक्षम कम्प्रेशन के बावजूद मामूली कुल बचत दिखाएगा, जबकि विफल
लूप या अत्यधिक आउटपुट देने वाले लिंटर का सामना करने वाला सत्र उस ट्रैफ़िक पर पूरी 78-95% सीमा देखेगा। किसी एक सत्र की
कम समग्र बचत प्रतिशत को इस बात का प्रमाण न मानें कि कम्प्रेशन गलत तरीके से कॉन्फ़िगर किया गया है — पहले जाँचें कि
अंतर्निहित टूल आउटपुट वास्तव में दोहराव वाला था या नहीं।

## कॉन्फ़िगरेशन

### डैशबोर्ड

`Dashboard → Context & Cache` पर जाएँ:

- **Caveman** — मोड चयन, भाषा पैक, पूर्वावलोकन और वैश्विक डिफ़ॉल्ट
- **RTK** — कमांड-फ़िल्टर पूर्वावलोकन, RTK सुरक्षा सेटिंग और फ़िल्टर कैटलॉग
- **Compression Combos** — रूटिंग कॉम्बो को असाइन की गई नामित इंजन पाइपलाइन
- **Auto-Trigger Threshold** — टोकन की संख्या थ्रेशोल्ड से अधिक होने पर कम्प्रेशन अपने-आप सक्रिय करना

### प्रति-कॉम्बो ओवरराइड

`Dashboard → Context & Cache → Compression Combos` में किसी रूटिंग
कॉम्बो को कम्प्रेशन कॉम्बो असाइन करें:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

इससे आप निःशुल्क/कोडिंग प्रदाताओं पर स्टैक्ड कम्प्रेशन का उपयोग कर सकते हैं, जबकि भुगतान किए गए
सब्सक्रिप्शन पर लाइट मोड बनाए रख सकते हैं।

यह "Per-Combo Override", **रूटिंग-कॉम्बो कम्प्रेशन
मोड** ओवरराइड (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — फ़ील्ड का स्कीमा
`rtk`, `stacked` और `omniglyph` भी स्वीकार करता है) से अलग नियंत्रण है — वह ओवरराइड किसी नामित
कम्प्रेशन-कॉम्बो पाइपलाइन का चयन नहीं करता; यह केवल `resolveCompressionPlan` द्वारा परामर्श किए
जाने वाले `compressionMode` फ़ील्ड को सेट करता है। इसे कॉम्बो कार्ड (`Dashboard → Combos`) पर या
#6760 के बाद, `Dashboard → Context & Cache → Compression Combos` में "Assign to routing" सूची
में प्रति रूटिंग कॉम्बो सेट किया जा सकता है, ठीक ऊपर दस्तावेज़ीकृत पाइपलाइन-असाइनमेंट चेकबॉक्स के
पास। दोनों स्थान एक ही `PUT /api/combos/{id}` एंडपॉइंट के माध्यम से स्थायी रूप से सहेजे जाते हैं।

### प्रति-अनुरोध ओवरराइड

किसी एक अनुरोध के लिए कम्प्रेशन प्लान को ओवरराइड करने हेतु `x-omniroute-compression` अनुरोध
हेडर भेजें। इसकी प्राथमिकता सबसे अधिक है — यह रूटिंग-कॉम्बो ओवरराइड, सक्रिय प्रोफ़ाइल,
ऑटो-ट्रिगर और पैनल के Default को भी ओवरराइड करता है। अज्ञात मानों को अनदेखा कर दिया जाता है
(अनुरोध कभी अस्वीकार नहीं किया जाता) और वैश्विक मास्टर स्विच अभी भी सभी चीज़ों को नियंत्रित करता
है: जब कम्प्रेशन वैश्विक रूप से बंद हो, तो हेडर इसे चालू नहीं कर सकता। मान:

| मान           | प्रभाव                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| `off`         | इस अनुरोध के लिए कोई कम्प्रेशन नहीं।                                                                 |
| `default`     | पैनल से प्राप्त Default प्रोफ़ाइल (सक्रिय प्रोफ़ाइल को अनदेखा करता है)। Lossy इंजन बंद रहते हैं।     |
| `safe`        | हेडर छोड़ने के समान।                                                                                 |
| `allow-lossy` | इस अनुरोध का ऑपरेटर प्लान बनाए रखें, जिसमें सारांश, प्रासंगिकता फ़िल्टर और शैली पुनर्लेखन शामिल हैं। |
| `engine:<id>` | सक्षम होने पर एकल इंजन, जैसे `engine:rtk`। यह उस इंजन के लिए प्रति-अनुरोध ऑप्ट-इन है।                |
| `<combo>`     | नाम से मिलान किया गया नामित कॉम्बो (पहले केस-असंवेदनशील रूप से, फिर id द्वारा)।                      |

`allow-lossy`, `engine:<id>` या किसी नामित कॉम्बो के बिना, lossy इंजन लागू नहीं किए जाते। जब किसी
lossy Default, ऑटो-ट्रिगर या रूटिंग ओवरराइड को डाउनग्रेड किया जाता है, तो OmniRoute कॉन्फ़िगर की गई
स्टैक्ड पाइपलाइन से पहचाने गए lossless चरणों को कॉन्फ़िगर किए गए क्रम में बनाए रखता है। केवल तब
`session-dedup → lite` पर वापस जाता है, जब कोई भी कॉन्फ़िगर किया गया lossless चरण शेष न रहे।

Settings पैनल का **Effective pipeline** पूर्वावलोकन सामान्य स्थिर प्लान दिखाता है। जब कोई
ऑटो-ट्रिगर चल सकता है, तो यही पूर्वावलोकन उसका सशर्त प्रभावी पाइपलाइन भी दिखाता है, ताकि पैनल और
हेडर-रहित रनटाइम रिज़ॉल्यूशन एक-दूसरे के अनुरूप रहें।

लागू किया गया प्लान `X-OmniRoute-Compression: <mode>; source=<source>` प्रतिक्रिया हेडर में वापस
दिया जाता है, जहाँ `<source>` निम्न में से एक होता है: `request-header`, `routing-override`,
`active-profile`, `auto-trigger`, `default` या `off`।

## उन्नत संपीड़न प्रणालियाँ

ऊपर वर्णित 7 मोड से परे (स्रोत `codex-responses` और `omniglyph` मोड को भी स्वीकार करता है, जिसे यह गाइड कवर नहीं करता है), नीचे दिए गए अनुभाग उन सुविधाओं को कवर करते हैं जो उन मोड के अंदर या साथ काम करते हैं: टूल रिजल्ट कंप्रेशन और प्रोग्रेसिव एजिंग आक्रामक इंजन के चरण 1 और 2 हैं (आक्रामक मोड और एक स्टैक्ड पाइपलाइन का `aggressive` चरण), स्टैक्ड पाइपलाइन स्टैक्ड मोड को कैसे चलाता है, कैश-अवेयर कंप्रेशन `aggressive` डाउनग्रेड करता है और संपीड़न चालू होने पर कैशिंग प्रदाताओं के लिए `ultra` से `standard`, और केवमैन आउटपुट मोड और आउटपुट शैलियाँ ऑप्ट-इन सिस्टम-प्रॉम्प्ट निर्देश हैं, जो डिफ़ॉल्ट रूप से बंद हैं, जो अनुरोध को संपीड़ित करने के बजाय मॉडल के आउटपुट को आकार देते हैं।

### कैश-अवेयर कम्प्रेशन

कुछ प्रदाता (जैसे शीघ्र कैशिंग के साथ Anthropic ) समर्थन करते हैं** शीघ्र कैशिंग** , जो उन्हें लागत और विलंबता को कम करने के लिए प्रॉम्प्ट के कुछ हिस्सों को कैश करने देता है। जब कैशिंग सक्षम होती है, तो वास्तव में आक्रामक संपीड़न हो सकता है** आहत** प्रदर्शन क्योंकि यह कैश्ड टोकन को बदल देता है, कैश को अमान्य कर देता है।

`cachingAware.ts` मॉड्यूल इसे हल करता है** कैशिंग संदर्भ का पता लगाना** और** संपीड़न रणनीति को समायोजित करना** इसलिए।

#### यह काम किस प्रकार करता है

1. **कैशिंग प्रसंग का पता लगाएं** — `cache_control` मार्करों के लिए अनुरोध निकाय को स्कैन करता है
2. **कैशिंग प्रदाताओं की पहचान करें** — जाँचता है कि लक्ष्य प्रदाता कैशिंग का समर्थन करता है या नहीं
3. **रणनीति समायोजित करें** — कैशिंग प्रदाताओं के लिए `aggressive`/`ultra` को `standard` में डाउनग्रेड करता है
4. **सिस्टम प्रॉम्प्ट छोड़ें** — सिस्टम प्रॉम्प्ट आमतौर पर कैश्ड होते हैं, इसलिए उन्हें संपीड़ित न करें

रणनीति सहायक भी एक `deterministicOnly` ध्वज लौटाता है, लेकिन योजना निर्माता केवल रणनीति — का उपभोग करता है, कुछ भी डाउनस्ट्रीम आज ध्वज को नहीं पढ़ता है।

#### कोड उदाहरण

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### कब उपयोग करें

कैश-जागरूक संपीड़न है** हमेशा बने रहें** — किसी कॉन्फ़िगरेशन की आवश्यकता नहीं है. जब भी संपीड़न चालू होता है तो यह चालू हो जाता है और लक्ष्य प्रदाता शीघ्र कैशिंग (Anthropic, OpenAI, आदि) का समर्थन करता है; स्पष्ट `cache_control` मार्करों की आवश्यकता नहीं है — एक कैशिंग प्रदाता अकेले डाउनग्रेड को ट्रिगर करता है, और अकेले मार्कर कभी ऐसा नहीं करते हैं (मार्कर का पता लगाने से कैश टेलीमेट्री फ़ीड होती है, रणनीति निर्णय नहीं)।

OpenRouter केवल `anthropic/*` मॉडल के लिए एक कैशिंग प्रदाता के रूप में गिना जाता है: Claude कोड अनुरोध अपने `cache_control` ब्रेकप्वाइंट (अधिकतम 4) रखते हैं और गार्ड उपसर्ग की सुरक्षा करता है, जबकि हर दूसरा OpenRouter परिवार (`openai/`, `google/`, `qwen/`,…) छीन लिया जाता है और असुरक्षित रहता है।

### प्रगतिशील बुढ़ापा

लंबी बातचीत में कई संदेशात्मक परिवर्तन होते हैं, लेकिन पुराने वार्तालाप कम प्रासंगिक हो जाते हैं। `progressiveAging.ts` मॉड्यूल** बारी दूरी के आधार पर संदेशों को ख़राब करता है** (बातचीत के अंत से मापी गई दूरी)। शिप किए गए डिफ़ॉल्ट (`verbatim: 2, light: 2, moderate: 3`) के साथ:

- **अंतिम 2 मोड़ (दूरी ≤ 2)** : शब्दशः रखा गया
- **दूरी 3** : केवमैन संपीड़न (भराव हटाना)
- **दूरी 4 +** : सहायक संदेशों का सारांश; उपयोगकर्ता संदेशों को उनकी पहली पंक्ति में घटाकर 120 अक्षरों तक सीमित कर दिया गया; अन्य भूमिकाएँ अछूती। सिस्टम संकेत, पहले से पुराने संदेश और नवीनतम उपयोगकर्ता संदेश को दूरी की परवाह किए बिना हमेशा शब्दशः रखा जाता है। कुछ भी एकमुश्त नहीं छोड़ा गया है, और `light` बैंड शिप किए गए डिफ़ॉल्ट के साथ पहुंच योग्य नहीं है (`light` बराबर `verbatim`)।

#### कोड उदाहरण

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### कब उपयोग करें

प्रगतिशील उम्र बढ़ना है** हमेशा बने रहें** `aggressive` मोड — के लिए यह `compressAggressive()` का चरण 2 है। अल्ट्रा मोड इसे नहीं चलाता है. यह इनके लिए विशेष रूप से प्रभावी है:

- लंबे समय तक चलने वाले कोडिंग सत्र
- कई दिनों की बातचीत
- कई टूल कॉल के साथ एजेंट वर्कफ़्लो

### केवमैन आउटपुट मोड

केवमैन आउटपुट मोड जोड़ता है** सिस्टम शीघ्र निर्देश** वह मॉडल से ही संक्षिप्त आउटपुट के लिए पूछता है — `lite` स्तर संक्षिप्त उत्तर मांगता है जो पूर्ण वाक्य रखता है, `full` इसे "स्मार्ट केवमैन की तरह संक्षिप्त उत्तर देने" के लिए कहता है, और `ultra` टेलीग्राफिक आउटपुट के लिए पूछता है; निर्देश केवल पूछते हैं, वे इसकी गारंटी नहीं दे सकते। अनुरोध उन्हें `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) के माध्यम से प्राप्त होते हैं: `open-sse/handlers/chatCore.ts` पहले बैक-कॉम्पैट शिम (`resolveOutputStyleSelection()` in `open-sse/services/compression/outputStyles/backCompat.ts`) के साथ चयन को हल करता है, जो कि `outputStyles` खाली होने पर, `cavemanOutputMode.intensity` पर `terse-prose` आउटपुट शैली में सक्षम `cavemanOutputMode` मैप करता है (नीचे बैक-कॉम्पैट देखें); एक गैर-रिक्त `outputStyles` चयन का उपयोग वैसे ही किया जाता है, और `cavemanOutputMode.enabled` और `intensity` कोई प्रभाव नहीं पड़ता है, जबकि इसका `autoClarity` टॉगल अभी भी लागू होता है। `outputMode.ts` निर्देश पाठ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), सामग्री बाईपास और इंजेक्शन द्वारा उपयोग किए जाने वाले प्लेसमेंट सहायक को रखता है; इसके स्वयं के `applyCavemanOutputMode()` इंजेक्टर में कोई उत्पादन कॉलर नहीं है।

#### यह काम किस प्रकार करता है

यह मोड इनपुट को संपीड़ित नहीं करता है. यह सिस्टम प्रॉम्प्ट में एक निर्देश ब्लॉक जोड़ता है (नीचे देखें कि इंजेक्शन कैसे काम करता है), और अनुरोध के लिए चयनित कोई भी इनपुट संपीड़न मोड बाद में भी चलता है, उस बॉडी पर जो अब ब्लॉक को ले जाती है। साझा सीमा खंड के आगे, जिसके साथ प्रत्येक स्तर समाप्त होता है, अंग्रेजी `full` स्तर पढ़ता है:

> "स्मार्ट केवमैन की तरह संक्षिप्त उत्तर दें। आलेख (a/an/the), फिलर (just/really/basically/actually/simply), सुखदता, हेजिंग छोड़ें। टुकड़े OK। लघु पर्यायवाची (बड़े नहीं व्यापक, फिक्स लागू नहीं)। सभी तकनीकी सामग्री, कोड, त्रुटियां, URLs, पहचानकर्ताओं को सटीक रखें।"

यह इनके लिए विशेष रूप से अच्छा काम करता है:

- कोड जनरेशन (टर्सर आउटपुट = कम टोकन)
- त्वरित प्रश्नोत्तर (विस्तृत स्पष्टीकरण की कोई आवश्यकता नहीं)
- बैच प्रोसेसिंग (थ्रूपुट को अधिकतम करें)

#### कब उपयोग करें

केवमैन आउटपुट मोड है** में चुनें** . संपीड़न चालू होने पर (`enabled: true`, संपीड़न सेटिंग्स पृष्ठ पर मास्टर टॉगल), इसे `cavemanOutputMode.enabled` के साथ चालू करें; `intensity` `lite`, `full` या `ultra` चुनता है:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

एक संपीड़न कॉम्बो** आउटपुट मोड** टॉगल (`outputMode`, लेवल इन `outputModeIntensity`) उन अनुरोधों के लिए वही स्विच सेट करता है जिन पर कॉम्बो लागू होता है, और `omniroute_set_compression_engine` MCP टूल इसे अपने बूलियन `outputMode` तर्क के माध्यम से लिखता है। एक गैर-रिक्त `outputStyles` चयन को इस स्विच पर प्राथमिकता दी जाती है। डैशबोर्ड में, सक्षम करना** संक्षिप्त गद्य** आउटपुट शैली उसी ब्लॉक को इंजेक्ट करती है (नीचे आउटपुट शैलियाँ देखें)।

### आउटपुट शैलियाँ (कैटलॉग)

| संक्षिप्त CJK (文言)            | `terse-cjk`     | शास्त्रीय चीनी (文言) में`full`/`ultra` उत्तर; `lite` केवल संक्षिप्त उत्तर मांगता है, बिना क्रियात्मक शब्दों, प्रसन्नता या अलंकरण के।                                                                                                               | zh (लोकेल-गेटेड, नीचे देखें)                                    |

प्रत्येक शैली तीन तीव्रता स्तर — `lite`, `full`, `ultra` — भेजती है और प्रत्येक स्तर साझा सीमा खंड (`SHARED_BOUNDARIES` में `outputMode.ts`) के साथ समाप्त होता है, जो कोड ब्लॉक, फ़ाइल पथ, कमांड, त्रुटियां और URLs सटीक रखता है। `terse-prose` और `terse-cjk` स्तर के पाठ उस सूची में पहचानकर्ता जोड़ते हैं।

`terse-cjk` दो स्थानों पर `zh` से स्थानीय रूप से जुड़ा हुआ है। संपीड़न सेटिंग्स पृष्ठ अपनी पंक्ति को केवल तभी सूचीबद्ध करता है जब डैशबोर्ड UI भाषा चीनी (`zh-CN` या `zh-TW`) होती है, और `applyOutputStyles()` इसे तभी इंजेक्ट करता है जब अनुरोध की हल की गई भाषा (नीचे भाषा चयन देखें) `zh` है। पंक्ति को छिपाने से सहेजा गया `terse-cjk` चयन साफ़ नहीं होता है: सेटिंग्स API किसी भी शैली आईडी को स्वीकार करती है, और पृष्ठ पर अन्य शैलियों को सहेजने से वह बनी रहती है। अनुरोध समय पर, `applyOutputStyles()` भाषा जांच एकमात्र स्थानीय गेट है।

#### इंजेक्शन कैसे काम करता है

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) कैटलॉग के विरुद्ध चयन को हल करता है (अज्ञात आईडी और स्थानीय-बेमेल शैलियों को हटा दिया जाता है, कभी कोई त्रुटि नहीं होती है; एक चयन जो किसी भी शैली को हल नहीं करता है, मुख्य भाग को अपरिवर्तित छोड़ देता है, `no_styles` के रूप में छोड़ दिया जाता है), कैटलॉग क्रम में चयनित निर्देशों को जोड़ता है, सीमा खंड जोड़ता है** एक बार** (साथ ही सुरक्षा खंड, `SAFETY_BOUNDARIES` या उसका अनुवाद, जब `less-code` या `ponytail` चयन किया जाता है), और ब्लॉक को एकल इडेम्पोटेंसी मार्कर (`[OmniRoute Output Styles]`) के साथ शुरू करता है, इसलिए दोबारा आवेदन करना कोई विकल्प नहीं है। जब हल की गई भाषा (नीचे भाषा चयन देखें) का अनुवाद होता है, तो अंग्रेजी के बजाय स्थानीयकृत निर्देश इंजेक्ट किया जाता है।

गैर-रिक्त `messages` सरणी वाले निकाय पर, सामग्री बाईपास से पहले निष्क्रियता जांच चलती है: जब `[OmniRoute Output Styles]` मार्कर पहले से ही शीर्ष-स्तरीय `system` फ़ील्ड (एक स्ट्रिंग या सामग्री-ब्लॉक सरणी) में या स्ट्रिंग सामग्री वाले सिस्टम संदेश में होता है, तो निकाय को `already_applied` के रूप में अपरिवर्तित छोड़ दिया जाता है और कोई कीवर्ड चेक नहीं चलता है। अन्यथा एक सामग्री बाईपास (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) पिछले तीन संदेशों के पाठ की जांच करता है, चाहे उनकी भूमिका कुछ भी हो, और जब वह पाठ अपनी सुरक्षा, अपरिवर्तनीय-क्रिया या स्पष्टीकरण कीवर्ड, या ऑर्डर-संवेदनशील अनुक्रम से मेल खाता है तो पूरे चरण के लिए शैलियों को छोड़ देता है: `first`, `then`, `after that`, `before`, `rollback` या `backup` 240 अक्षरों के भीतर `delete`, `drop`, `migrate`, `deploy` या `release`. जबकि बाईपास चलता है** ऑटो-स्पष्टता बाईपास** टॉगल (`cavemanOutputMode.autoClarity`, डिफ़ॉल्ट रूप से चालू) चालू है; टॉगल को बंद करने से कीवर्ड जांच छूट जाती है।

जब बायपास मुड़ने देता है, `placeSystemInstruction()` (वही फ़ाइल), जो कभी भी नया `messages[0]` नहीं बनाता है, ब्लॉक को इनमें से सबसे पहले पाता है:

1. स्ट्रिंग सामग्री के साथ एक प्रमुख सिस्टम संदेश: ब्लॉक को इसके पाठ के बाद जोड़ा जाता है।
2. शीर्ष-स्तरीय `system` फ़ील्ड: ब्लॉक को स्ट्रिंग के टेक्स्ट के बाद जोड़ा जाता है, या सामग्री-ब्लॉक सरणी में एक नए टेक्स्ट ब्लॉक के रूप में जोड़ा जाता है।
3. स्ट्रिंग सामग्री के साथ पहला बाद वाला सिस्टम संदेश: ब्लॉक को उसके पाठ के बाद जोड़ा जाता है।
4. उपरोक्त में से कोई नहीं: ब्लॉक `messages` के अंत में एक नए सिस्टम संदेश में चला जाता है।

बिना `messages` सरणी (या खाली सरणी के साथ) वाले शरीर पर, कोई भी सामग्री बाईपास नहीं चलती है और शीर्ष-स्तरीय `system` फ़ील्ड की सलाह नहीं ली जाती है। ब्लॉक को स्ट्रिंग `instructions` फ़ील्ड के टेक्स्ट के बाद जोड़ा जाता है, जब तक कि उस फ़ील्ड में पहले से ही `[OmniRoute Output Styles]` मार्कर न हो, उस स्थिति में बॉडी को `already_applied` के रूप में अपरिवर्तित छोड़ दिया जाता है। जब बॉडी में कोई स्ट्रिंग `instructions` फ़ील्ड नहीं है, लेकिन `input` (एक स्ट्रिंग या एक सरणी) रखता है, तो ब्लॉक `instructions` बन जाता है, जो उस फ़ील्ड में मौजूद किसी भी गैर-स्ट्रिंग मान को प्रतिस्थापित कर देता है। एक बॉडी जिसमें न तो कोई स्ट्रिंग `instructions` फ़ील्ड है और न ही कोई स्ट्रिंग या सरणी `input` को अपरिवर्तित छोड़ दिया गया है और `no_messages` के रूप में छोड़ दिया गया है।

#### कैसे सक्षम करें

डैशबोर्ड में:** संपीड़न संदर्भ → संपीड़न सेटिंग्स** (`/dashboard/context/settings`), आउटपुट शैलियाँ अनुभाग: on/off टॉगल और एक स्तर चयनकर्ता के साथ प्रति शैली एक पंक्ति। शैलियाँ तब इंजेक्ट होती हैं जब संपीड़न स्वयं चालू होता है (पेज का मास्टर टॉगल, `enabled`)।** ऑटो-स्पष्टता बाईपास** टॉगल चालू है** गुफाओं का आदमी** पेज (`/dashboard/context/caveman`), इसके में** आउटपुट मोड** कार्ड. प्रोग्रामेटिक रूप से, संपीड़न कॉन्फ़िगरेशन चयन को इस प्रकार जारी रखता है:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

बैक-कंपैट: जबकि `outputStyles` खाली है, विरासत `cavemanOutputMode.enabled` सेटिंग `cavemanOutputMode.intensity` पर `terse-prose` पर मैप करती है। ब्लॉक फिर `[OmniRoute Output Styles]` मार्कर से शुरू होता है, जहां विरासत `applyCavemanOutputMode()` इंजेक्टर ने `[OmniRoute Caveman Output Mode]` लिखा है। मार्कर के नीचे, टेक्स्ट एन, पीटी-बीआर, ईएस, डी, एफआर, आईटी, आरयू, आईडी और वीआई में विरासत इंजेक्शन से मेल खाता है; ja और zh में यह सीमा खंड से पहले एक अतिरिक्त स्थान रखता है। `terse-prose` pt-BR, es, de, fr, it, ru, zh, ja, id और vi में अनुवाद करता है, इसलिए एक अनुरोध जिसकी हल की गई भाषा `hu` है उसे अंग्रेजी पाठ मिलता है जहां विरासत इंजेक्टर ने अपने हंगेरियन का उपयोग किया है।

आउटपुट-शैली भाषा चयन (`resolveOutputStyleLanguage()` in `outputStyles/apply.ts`): `languageConfig.enabled` चालू होने पर, `autoDetect` अनुरोध के `messages` सरणी में नवीनतम उपयोगकर्ता संदेश का नमूना लेता है जिसमें टेक्स्ट (स्ट्रिंग सामग्री, या इसके सामग्री भागों का `text` ) होता है और उस पर केवमैन इंजन का डिटेक्टर (`detectCompressionLanguage()`) चलता है। डिटेक्टर हान वर्णों और बिना काना वाले पाठ के लिए `zh` लौटाता है; अन्यथा यह `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` और `id` में से जो भी सबसे अधिक संकेत मेल खाता है उसे लौटाता है, और `en` जब कोई भी — पाठ से मेल नहीं खाता है तो इसे अंग्रेजी में वर्गीकृत नहीं किया जा सकता है, कभी `defaultLanguage` नहीं होता है, और `vi` कभी पता नहीं चलता है, हालांकि शैलियाँ `vi` पाठ भेजती हैं। एक प्रतिक्रिया API बॉडी अपने घुमावों को `input` में रखती है, जिसका नमूना नहीं है, इसलिए इसे `defaultLanguage` मिलता है, फिर अंग्रेजी। जब `messages` में किसी उपयोगकर्ता संदेश में टेक्स्ट नहीं है, या `autoDetect` बंद है, तो `defaultLanguage` लागू होता है, तब अंग्रेजी। `languageConfig.enabled` बंद के साथ, भाषा अंग्रेजी — है जब तक कि एक संपीड़न कॉम्बो अनुरोध पर लागू नहीं होता है (अनुरोध के रूटिंग कॉम्बो को सौंपा गया कॉम्बो, या अंतर्निहित स्टैक्ड पाइपलाइन के लिए डिफ़ॉल्ट संपीड़न कॉम्बो chatCore वापस आ जाता है): कॉम्बो लागू करने से उस अनुरोध के लिए `languageConfig.enabled` चालू हो जाता है और कॉम्बो के भाषा पैक से `defaultLanguage` सेट हो जाता है (यदि यह कॉम्बो के पैक में से एक है तो सहेजा गया मान, अन्यथा कॉम्बो का पहला पैक, जो डिफ़ॉल्ट रूप से `en` है), जबकि सहेजा गया `autoDetect` (डिफ़ॉल्ट रूप से चालू) अभी भी लागू होता है। केवमैन इनपुट इंजन अपनी नियम-पैक भाषा को प्रत्येक पाठ भाग के अनुसार अलग-अलग — चुनता है और, ऑटो-डिटेक्ट ऑफ के साथ, `enabledPacks` पर गेट किया जाता है।

शैली × भाषा मैट्रिक्स को `tests/unit/compression/output-styles-i18n-matrix.test.ts` द्वारा पिन किया गया है: प्रत्येक कैटलॉग शैली को परीक्षण के `BASELINE_LANGUAGES` में एक प्रविष्टि की आवश्यकता होती है; एक शैली जो लोकेल-गेटेड नहीं है, उसे एक पीटी-बीआर अनुवाद भेजना होगा (लोकेल-गेटेड `terse-cjk` इस नियम से छूट दी गई है) जब तक कि यह `KNOWN_ENGLISH_ONLY` में सूचीबद्ध न हो, जो केवल शैलियों को बिना किसी अनुवाद के रख सकता है — एक सूचीबद्ध शैली जिसमें कोई अनुवाद होता है वह परीक्षण में विफल रहता है; और एक शैली परीक्षण में विफल हो जाती है जब वह अपनी `BASELINE_LANGUAGES` प्रविष्टि सूची वाली भाषा खो देती है। शैली जोड़ने के लिए, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) देखें।

### उपकरण परिणाम संपीड़न

`open-sse/services/compression/toolResultCompressor.ts` में`compressToolResult()` टूल-परिणाम टेक्स्ट को संपीड़ित करता है** 5 रणनीतियाँ** . यह उन्हें इस क्रम में आज़माता है, और पहली सक्षम रणनीति जिसका चेक सामग्री से मेल खाता है परिणाम तय करता है:

1. **`fileContent`**: content of 3 or more lines in which at least one line, ignoring leading indentation, starts with `import `, `export `, `function `, `class `, `const `, `let `, `var ` or `return ` (the keyword plus a space), or with `if`, `for` or `while` followed by `(` or ` (`, keeps its first 20 and last 5 lines, with the elided middle marked.
2. **`grepSearch`** : प्रपत्र `<path>:<digits>:` की कम से कम एक पंक्ति वाली सामग्री, जहां पहले कोलन से पहले के पाठ में कोई रिक्त स्थान नहीं है, केवल उन पंक्तियों को रखता है, अधिकतम 30, इसके बाद किसी भी अन्य मिलान की गिनती और मिलान की गई फ़ाइलों की सूची; हर दूसरी पंक्ति हटा दी गई है। ऐसी एक लाइन रणनीति को ट्रिगर करने के लिए पर्याप्त है, इसलिए `12:30:45` जैसे टाइमस्टैम्प से शुरू होने वाली लॉग लाइन भी मायने रखती है।
3. **`shellOutput`** : आउटपुट जिसमें एक ANSI CSI अनुक्रम होता है (`ESC[` फिर अंक या अर्धविराम फिर एक अक्षर, जैसा कि रंग कोड में होता है) या पाठ में कहीं भी रिक्त स्थान के बाद एक `$` उन अनुक्रमों को खो देता है (अन्य एस्केप, जैसे `ESC[?25l` या एक OSC विंडो-शीर्षक अनुक्रम, रखा जाता है) और लगातार दोहराई गई पंक्तियों के साथ इसकी अंतिम 50 पंक्तियाँ रखता है। क्योंकि यह चेक `json` और `errorMessage` से पहले चलता है, JSON या त्रुटि आउटपुट जिसमें ऐसा `$` होता है, `shellOutput` चालू होने पर उन तक कभी नहीं पहुंचता है।
4. **`json`** : 2,000 से अधिक वर्णों वाला एक JSON पेलोड जो `{` या `[` (वैकल्पिक रिक्त स्थान के बाद) से शुरू होता है और पार्स को संक्षेप में प्रस्तुत किया जाता है: 7 से अधिक आइटमों की एक सरणी अपने पहले 5 और अंतिम 2 आइटम और इसकी कुल गिनती रखती है, और एक ऑब्जेक्ट अपनी पहली 20 कुंजियाँ रखता है, प्रत्येक नेस्टेड ऑब्जेक्ट या सरणी मान को `{…N keys}` प्लेसहोल्डर द्वारा प्रतिस्थापित किया जाता है (एक सरणी के लिए, N इसकी लंबाई है) और एक `_remaining_<N>_keys` मार्कर पिछले छोड़ी गई कुंजियों की गिनती करता है पहले 20. स्केलर मानों को संपूर्ण रूप से कॉपी किया जाता है, इसलिए 20 कुंजियों या उससे कम की कोई वस्तु जिसमें कोई नेस्टेड मान नहीं होता है, केवल पुनः इंडेंट किया जाता है — एक छोटा अक्षर प्राप्त करता है और अपरिवर्तित रहता है।
5. **`errorMessage`** : आउटपुट जिसमें, कहीं भी और किसी भी अक्षर के मामले में, `error:`, `error ` (शब्द के बाद एक रिक्त स्थान होता है, जैसे कि `no error found` में), `[error]`, `exception:`, `exception `, `[exception]` या `traceback` अपनी पहली पंक्ति, अगली 10 पंक्तियाँ और अंतिम 3, उनके बीच की रेखाओं के स्थान पर एक `… [N frames elided] …` मार्कर के साथ रखता है। मार्कर केवल तब दिखाई देता है जब 13 से अधिक पंक्तियाँ पहली पंक्ति का अनुसरण करती हैं, इसलिए 14 पंक्तियों या उससे कम का त्रुटि आउटपुट छोटा नहीं होता है (12 या 13 पंक्तियों पर अंतिम 3 दोहराई गई पंक्तियाँ पहले से ही रखी जाती हैं)।

एक रणनीति के मेल खाने के बाद, यहां तक कि जो कुछ भी नहीं बचाता है, बाद की रणनीतियों को आजमाया नहीं जाता है। जब मिलान रणनीति कोई अनुमानित टोकन नहीं बचाती है (लंबाई ÷ 4, गोलाकार) — उदाहरण के लिए 25 लाइनों या उससे कम की एक कोड-जैसी फ़ाइल, या 7 आइटम या उससे कम — के साथ 2,000 वर्णों से अधिक JSON सरणी, आक्रामक इंजन मूल टूल परिणाम रखता है: दोनों कॉलर्स (`compressAggressive()` और `compressAnthropicToolResultBlock()`) `saved` 0 या उससे नीचे होने पर मूल रखते हैं, जबकि `compressToolResult()` स्वयं अभी भी उसे लौटाता है रणनीति का आउटपुट. टूल-परिणाम चरण अंतिम शब्द नहीं है: इंजन का फ़ॉलबैक सारांश अभी भी 8,192 वर्णों (`maxTokensPerMessage`, 2,048, गुना 4) से अधिक लंबे `tool` या `function` संदेश को छोटा कर सकता है।

#### कब उपयोग करें

टूल परिणाम संपीड़न आक्रामक इंजन (`compressAggressive()` in `open-sse/services/compression/aggressive.ts`) का चरण 1 है, इसलिए यह आक्रामक मोड में और स्टैक्ड पाइपलाइन के `aggressive` चरण में चलता है। यह OpenAI-आकार `tool` और `function` संदेशों और Anthropic `tool_result` ब्लॉक के अंदर पाठ को संपीड़ित करता है। प्रत्येक रणनीति का `aggressive.toolStrategies` के अंतर्गत अपना स्वयं का स्विच होता है, जो सभी डिफ़ॉल्ट रूप से चालू होता है। डैशबोर्ड में, स्विच केवमैन पेज में हैं** विकसित** संपीड़न चालू होने पर देखें और डिफ़ॉल्ट मोड आक्रामक है।

### स्टैक्ड पाइपलाइन

स्टैक्ड मोड चलता है** क्रम में एकाधिक इंजन** — आमतौर पर पहले RTK (टूल आउटपुट पर 60-90% बचत), फिर शेष पाठ पर केवमैन (~ 46% इनपुट बचत)। रचित, वह है** 78-95% योग्य सीमा** (ऊपर अपस्ट्रीम सेविंग्स गणित देखें): `1 - (1 - 0.60..0.90) × (1 - 0.46)` औसत ≈ 89%।

#### यह काम किस प्रकार करता है

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### कब उपयोग करें

इसके लिए स्टैक्ड मोड का उपयोग करें:

- टूल-हेवी वर्कफ़्लोज़ (एजेंट कोडिंग, अनुसंधान)
- लागत-संवेदनशील बैच प्रसंस्करण
- जब आपको अधिकतम टोकन बचत की आवश्यकता हो

स्टैक्ड पाइपलाइनों को वैश्विक `stackedPipeline` संपीड़न सेटिंग के माध्यम से कॉन्फ़िगर किया गया है, या एक रूटिंग कॉम्बो को निर्दिष्ट नामित संपीड़न कॉम्बो के माध्यम से कॉन्फ़िगर किया गया है (ऊपर प्रति-कॉम्बो ओवरराइड देखें) — एक ऑटो-कॉम्बो `modePack` के माध्यम से नहीं (वह फ़ील्ड केवल ऑटो-कॉम्बो मॉडल चयन को फिर से वेट करता है, और `stacked` एक वैध पैक नाम नहीं है)।

## कंप्रेशन कॉम्बो ओवरराइड

अलग-अलग उपयोग मामलों के लिए व्यवहार को बेहतर ढंग से समायोजित करने हेतु, आप वैश्विक कंप्रेशन मोड को **प्रत्येक कॉम्बो के लिए** ओवरराइड कर सकते हैं:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

यह इनके लिए उपयोगी है:

- **कोडिंग कॉम्बो**: लंबे सत्रों के लिए `aggressive` मोड का उपयोग करें
- **त्वरित प्रश्नोत्तर कॉम्बो**: तेज़ प्रतिक्रियाओं के लिए `lite` मोड का उपयोग करें
- **अधिक टूल वाले कॉम्बो**: अधिकतम बचत के लिए `stacked` मोड का उपयोग करें
- **प्रोडक्शन कॉम्बो**: कैशिंग प्रदाताओं के लिए ओवरराइड बंद रखें — हमेशा सक्रिय
  कैश-जागरूक समायोजन `aggressive`/`ultra` को स्वचालित रूप से `standard` में डाउनग्रेड कर देता है
  (चयन योग्य `cache-aware` मोड उपलब्ध नहीं है)
