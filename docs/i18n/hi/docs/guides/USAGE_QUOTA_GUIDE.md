> **संक्षेप में**: OmniRoute हर अनुरोध के टोकन उपयोग को ट्रैक करता है, लागत की गणना करता है, प्रत्येक API कुंजी के लिए कोटा लागू करता है और डैशबोर्ड में विश्लेषण प्रस्तुत करता है। यह मार्गदर्शिका बताती है कि यह सब कैसे काम करता है।

**स्रोत:**

- `open-sse/services/usage.ts` (~70KB) — मुख्य उपयोग ट्रैकिंग
- `src/lib/usageAnalytics.ts` (~10KB) — डैशबोर्ड के लिए एकत्रीकरण
- `src/lib/db/quotaSnapshots.ts` — ऐतिहासिक कोटा डेटा
- `src/lib/db/usage*.ts` — उपयोग से संबंधित कई DB मॉड्यूल

## अवलोकन

OmniRoute से होकर जाने वाला प्रत्येक अनुरोध एक **उपयोग रिकॉर्ड** उत्पन्न करता है, जिसमें ये विवरण दर्ज होते हैं:

- **पहचान**: कौन-सी API कुंजी, प्रदाता, मॉडल और कॉम्बो
- **टोकन**: प्रॉम्प्ट टोकन, पूर्णता टोकन, कैश किए गए टोकन और कुल टोकन
- **लागत**: USD राशि (मूल्य-निर्धारण डेटा से परिकलित)
- **समय**: विलंबता, आरंभ/समाप्ति टाइमस्टैम्प
- **स्थिति**: सफल, त्रुटि, दर-सीमित आदि

इन रिकॉर्ड्स को एकत्रित करके **विश्लेषण** तैयार किया जाता है, **कोटा स्नैपशॉट** के रूप में स्थायी रूप से संग्रहीत किया जाता है और **प्रति-कुंजी बजट सीमाएँ** लागू करने के लिए उपयोग किया जाता है।

```
अनुरोध ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                     विश्लेषण   कोटा    बिलिंग
                    (डैशबोर्ड) (प्रवर्तन) (निर्यात)
```

## क्या रिकॉर्ड किया जाता है

`usage.ts` सेवा हर अनुरोध के लिए एक **उपयोग इवेंट** कैप्चर करती है:

| फ़ील्ड             | प्रकार  | स्रोत                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | रिकॉर्ड करते समय जनरेट किया गया UUID                       |
| `apiKeyId`         | string  | अनुरोध शुरू करने वाली API कुंजी                            |
| `provider`         | string  | प्रदाता ID (openai, anthropic, आदि)                        |
| `model`            | string  | मॉडल ID (gpt-5, claude-opus-4-6, आदि)                      |
| `comboId`          | string? | यदि किसी कॉम्बो के माध्यम से रूट किया गया हो, तो कॉम्बो ID |
| `promptTokens`     | number  | अपस्ट्रीम प्रतिक्रिया से                                   |
| `completionTokens` | number  | अपस्ट्रीम प्रतिक्रिया से                                   |
| `cachedTokens`     | number  | कैश हिट टोकन (Anthropic प्रॉम्प्ट कैशिंग, आदि)             |
| `totalTokens`      | number  | प्रॉम्प्ट + कम्प्लीशन                                      |
| `costUsd`          | number  | मूल्य-निर्धारण डेटा से गणना की गई                          |
| `latencyMs`        | number  | अनुरोध की शुरू से अंत तक की अवधि                           |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | यदि स्थिति != success हो, तो त्रुटि वर्ग                   |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | प्लगइन द्वारा जोड़ा गया कस्टम डेटा                         |

### टोकन कहाँ से आते हैं

टोकन **प्रतिक्रिया हैंडलर** में अपस्ट्रीम प्रदाता की प्रतिक्रिया से निकाले जाते हैं:

```ts
// open-sse/handlers/chatCore.ts से
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

जो प्रदाता उपयोग डेटा नहीं लौटाते (कुछ वेब-कुकी प्रदाता), उनके लिए OmniRoute `~4 chars per token` अनुमान-नियम का उपयोग करके टोकन का **अनुमान लगाता है** (`open-sse/services/autoCombo/pipelineRouter.ts` देखें)।

### कैश किए गए टोकन

OmniRoute `cached_tokens` को `prompt_tokens` से अलग ट्रैक करता है, क्योंकि:

- Anthropic प्रॉम्प्ट कैशिंग में कैश किए गए टोकन के लिए कम दर (सामान्य दर का 10%) ली जाती है
- कुछ प्रदाता `cache_read_input_tokens` लौटाते हैं, जिनका मूल्य-निर्धारण अलग होना चाहिए
- एनालिटिक्स में **कैश हिट दर** = `cached_tokens / prompt_tokens` दिखाई जा सकती है

### कैश-राइट टियर डायग्नोस्टिक्स

एनालिटिक्स डैशबोर्ड का प्रॉम्प्ट-कैश स्वास्थ्य पैनल प्रदाता द्वारा रिपोर्ट किए गए
5-मिनट और 1-घंटे वाले कैश राइट के बीच अंतर करता है। Anthropic के
`usage.cache_creation.ephemeral_5m_input_tokens` और
`usage.cache_creation.ephemeral_1h_input_tokens` को स्ट्रीमिंग और
नॉन-स्ट्रीमिंग उपयोग डेटा रूपांतरण के दौरान बनाए रखा जाता है और कॉल-लॉग सारांशों के साथ संग्रहीत किया जाता है। संयुक्त
कैश-राइट कुल को उन श्रेणियों में दूसरी बार नहीं जोड़ा जाता।

केवल संयुक्त राइट काउंटर वाली कॉल का टियर अज्ञात होता है, जिसमें पुराने रिकॉर्ड भी शामिल हैं।
आंशिक विवरण में उसका अनावंटित शेष भाग अज्ञात रखा जाता है; अमान्य या
परस्पर विरोधी काउंटरों को चुपचाप TTL आवंटित करने के बजाय फ़्लैग किया जाता है। अनुरोध-पक्ष के
TTL मार्कर बिल किए गए टियर का प्रमाण नहीं हैं।

पैनल का API-समतुल्य राइट अनुमान केवल रिपोर्ट किए गए, मूल्य-निर्धारित टियर को कवर करता है,
पूरे अनुरोध को नहीं। मूल Claude/Anthropic मॉडल मूल्य-निर्धारण के लिए यह
5-मिनट वाले राइट पर इनपुट दर का 1.25 गुना और 1-घंटे वाले राइट पर इनपुट दर का दोगुना उपयोग करता है। अनुपलब्ध
मूल्य-निर्धारण को अनुपलब्ध माना जाता है, शून्य नहीं। हर नई कॉल लॉग करते समय कीमतें कैप्चर की जाती हैं;
पुराने रिकॉर्ड का मूल्य-निर्धारण दोबारा नहीं किया जाता। इसलिए सदस्यता खातों में
API-समतुल्य अनुमान हो सकता है, भले ही उतनी राशि नकद खर्च या सदस्यता
कोटा के रूप में न लगे। मौजूदा कोटा, बजट और प्रदाता की सटीक लागत गणनाएँ अपरिवर्तित रहती हैं।

ये डायग्नोस्टिक्स मौजूदा सीमित कैश-स्वास्थ्य सारांश और कॉल-लॉग
प्रतिधारण का उपयोग करते हैं। वे अनुरोध के डिफ़ॉल्ट TTL, रूटिंग या खाता चयन को नहीं बदलते।
प्रदाता को अनुरोध भेजने के बिंदु पर क्लाइंट द्वारा अनुरोधित TTL बनाम प्रभावी आउटगोइंग TTL को कैप्चर करना
स्थगित रखा गया है; यह पैनल रसीद में दिए गए टियर रिपोर्ट करता है, प्रभावी आउटगोइंग TTL नहीं।

कार्यान्वयन: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, और `open-sse/utils/cacheWriteUsage.ts`।

## लागत की गणना

लागत की गणना LiteLLM से सिंक किए गए **मूल्य-निर्धारण डेटा** (`src/lib/pricingSync.ts`) से की जाती है:

| मॉडल              | इनपुट $/1M | आउटपुट $/1M | कैश किया गया $/1M |
| ----------------- | ---------- | ----------- | ----------------- |
| gpt-5             | $2.50      | $10.00      | —                 |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50             |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30             |
| gemini-2.5-pro    | $1.25      | $10.00      | —                 |

लागत का सूत्र (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **कैश किए गए टोकन को प्रॉम्प्ट से क्यों घटाया जाता है?** कैश किए गए हिस्से का मूल्य अलग से निर्धारित होता है; पूरे प्रॉम्प्ट पर इनपुट मूल्य लगाने से लागत की अतिरिक्त गणना हो जाएगी।

### मूल्य-निर्धारण सिंक

मूल्य-निर्धारण डेटा `/api/pricing/sync` एंडपॉइंट के माध्यम से LiteLLM से स्वतः सिंक किया जाता है (इसे अंतर्निहित cron कार्य ट्रिगर करता है, न कि उपयोगकर्ता के लिए उपलब्ध कोई env var):

```bash
# मैन्युअल ट्रिगर
curl -X POST http://localhost:20128/api/pricing/sync
```

जिन मॉडलों के लिए मूल्य-निर्धारण डेटा उपलब्ध नहीं है, उनके लिए OmniRoute आंतरिक औसत दरों (LiteLLM के मूल्य-निर्धारण डेटा से प्राप्त) का उपयोग करके **लागत का अनुमान** लगाता है।

## दिनांक सीमा एकत्रीकरण

`usageAnalytics.ts` मॉड्यूल कच्चे उपयोग डेटा से डैशबोर्ड विजेट की गणना करता है। यह 7 समय सीमाओं का समर्थन करता है:

| सीमा     | अवधि                                     | उपयोग का उद्देश्य                             |
| -------- | ---------------------------------------- | --------------------------------------------- |
| `1d`     | पिछले 24 घंटे                            | प्रति घंटे लागत में अचानक वृद्धि का पता लगाना |
| `7d`     | पिछले 7 दिन                              | साप्ताहिक समीक्षा                             |
| `30d`    | पिछले 30 दिन                             | मासिक बिलिंग                                  |
| `90d`    | पिछले 90 दिन                             | तिमाही विश्लेषण                               |
| `ytd`    | वर्तमान वर्ष की 1 जनवरी से               | वार्षिक बजट की निगरानी                        |
| `all`    | संपूर्ण समय                              | संपूर्ण अवधि के आँकड़े                        |
| `custom` | उपयोगकर्ता द्वारा निर्धारित आरंभ/समाप्ति | ऑडिट, तदर्थ क्वेरी                            |

### गणना किए जाने वाले डैशबोर्ड विजेट

किसी भी दिनांक सीमा के लिए, विश्लेषण परत निम्नलिखित की गणना करती है:

| विजेट                       | विवरण                                                       |
| --------------------------- | ----------------------------------------------------------- |
| **सारांश कार्ड**            | कुल अनुरोध, कुल लागत, कुल टोकन, सफलता दर                    |
| **दैनिक रुझान चार्ट**       | प्रतिदिन लागत + टोकन, मॉडल के अनुसार स्टैक किए गए           |
| **गतिविधि हीटमैप**          | दिन का घंटा × सप्ताह का दिन ग्रिड, रंग = अनुरोधों की संख्या |
| **मॉडल के अनुसार विवरण**    | मॉडल के अनुसार लागत का पाई चार्ट                            |
| **प्रदाता के अनुसार विवरण** | प्रदाता के अनुसार अनुरोधों का बार चार्ट                     |
| **शीर्ष API कुंजियाँ**      | लागत के अनुसार शीर्ष 10 कुंजियों की तालिका                  |
| **त्रुटि विश्लेषण**         | समय के साथ त्रुटि दर, प्रमुख त्रुटि वर्ग                    |

### प्रोग्राम के माध्यम से पहुँच

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // उपयोग इतिहास के रिकॉर्ड
  "7d",                 // समय सीमा: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // प्रदाता कनेक्शन मैप (connectionId → खाते का नाम)
  {
    startDate: "2025-01-01",  // वैकल्पिक: "custom" सीमा के लिए
    endDate: "2025-06-01",   // वैकल्पिक: "custom" सीमा के लिए
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (सेंट)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## कोटा लागू करना

प्रत्येक API कुंजी का कोटा दो स्थानों पर लागू किया जाता है:

1. **सॉफ्ट सीमा** (`quotaWarnAt`): उपयोग निर्धारित सीमा से अधिक होने पर डैशबोर्ड चेतावनी
2. **हार्ड सीमा** (`quotaLimit`): सीमा पार होने पर HTTP 429 के साथ अनुरोध अस्वीकार

### कॉन्फ़िगरेशन

```ts
// प्रत्येक API कुंजी के लिए
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — चेतावनी दिखाएँ
  quotaLimit: 10_00,    // $10.00 — पूर्ण रोक
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### कोटा लागू करने का प्रवाह

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### कोटा स्नैपशॉट

`quotaSnapshots` तालिका रुझान विश्लेषण के लिए **कोटे की ऐतिहासिक स्थिति** संग्रहीत करती है:

| फ़ील्ड | विवरण |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | वह कुंजी जिसकी निगरानी की जा रही है |
| `window` | "day" | "week" | "month" |
| `used` | इस अवधि में उपयोग की गई लागत (सेंट) |
| `limit` | सीमा (सेंट) |
| `resetAt` | अवधि रीसेट होने का समय |
| `createdAt` | स्नैपशॉट लिए जाने का समय |

स्नैपशॉट **हर उस अनुरोध पर** लिए जाते हैं जिसकी लागत > 0 होती है, और इनका उपयोग निम्नलिखित के लिए किया जाता है:

- डैशबोर्ड में कोटा प्रगति बार दिखाना
- 30-दिवसीय कोटा रुझान चार्ट दिखाना
- उपयोग सीमा के करीब पहुँचने पर अलर्ट सक्रिय करना

## प्रतिधारण और सफ़ाई

उपयोग डेटा प्रत्येक अनुरोध पर ~1-10KB बढ़ता है। बड़े पैमाने पर यह काफ़ी अधिक हो सकता है।

### प्रतिधारण सेटिंग्स

उपयोग इतिहास का प्रतिधारण UI में डेटाबेस सेटिंग्स या `/api/settings/database` के माध्यम से कॉन्फ़िगर किया जाता है।

डिफ़ॉल्ट रूप से, उपयोग इतिहास **90 दिनों** तक रखा जाता है।

### सफ़ाई

पुराने रिकॉर्ड की सफ़ाई `src/lib/db/cleanup.ts` द्वारा की जाती है:

- पृष्ठभूमि cron प्रक्रिया द्वारा शुरू की जाती है
- कॉन्फ़िगर की गई `usageHistory` प्रतिधारण अवधि से पुराने रिकॉर्ड `usage_history` से हटाती है

### स्टोरेज का अनुमान

| अनुरोध दर          | 30 दिनों का स्टोरेज | 90 दिनों का स्टोरेज |
| ------------------ | ------------------- | ------------------- |
| 100 अनुरोध/दिन     | ~3MB                | ~9MB                |
| 1,000 अनुरोध/दिन   | ~30MB               | ~90MB               |
| 10,000 अनुरोध/दिन  | ~300MB              | ~900MB              |
| 100,000 अनुरोध/दिन | ~3GB                | ~9GB                |

बहुत अधिक ट्रैफ़िक होने पर, इन विकल्पों पर विचार करें:

- डेटाबेस सेटिंग्स के माध्यम से प्रतिधारण अवधि कम करना
- कच्चे रिकॉर्ड के बजाय `aggregated_metrics` का उपयोग करना (केवल विश्लेषण के लिए)

## लागत अनुकूलन के सुझाव

### 1. सही मॉडल का उपयोग करें

```bash
# त्वरित उत्तर — सस्ते + तेज़ मॉडल का उपयोग करें
curl -d '{"model":"auto/fast","messages":[...]}'

# जटिल कार्य — गुणवत्ता वाले मॉडल का उपयोग करें
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. कैशिंग सक्षम करें

Anthropic प्रॉम्प्ट कैशिंग **बार-बार उपयोग किए जाने वाले संदर्भ पर 90% की बचत** करती है:

```ts
// कैशिंग स्वचालित है — बस वही बड़ा सिस्टम प्रॉम्प्ट शामिल करें
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // स्वचालित रूप से कैश किया जाएगा
  messages: [{ role: "user", content: "..." }],
});
```

### 3. संपीड़न का उपयोग करें

RTK + Caveman संपीड़न **टूल के अधिक उपयोग वाले सत्रों में 15-95% की बचत** करता है:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. प्रत्येक कुंजी के लिए कोटा सेट करें

अनियंत्रित लागत से बचने के लिए हमेशा `quotaLimit` सेट करें:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // $10/माह की अधिकतम सीमा
```

### 5. सबसे अधिक उपयोग करने वालों का ऑडिट करें

API कुंजी के आधार पर समूह बनाने और लागत के आधार पर क्रमबद्ध करने के लिए डैशबोर्ड या **`/api/usage/analytics`** का उपयोग करें:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## समस्या निवारण

### "लागत अपेक्षा से अधिक है"

1. **`/api/usage/analytics?groupBy=model`** जाँचें — महँगा मॉडल खोजें
2. **`/api/usage/analytics?groupBy=apiKey`** जाँचें — अधिक उपयोग करने वाले को खोजें
3. सत्यापित करें कि मूल्य निर्धारण डेटा अद्यतन है: `POST /api/pricing/sync`

### "रिकॉर्ड गायब हैं"

- डैशबोर्ड → डेटाबेस → सफ़ाई के अंतर्गत DB प्रतिधारण सेटिंग्स जाँचें — पुराने रिकॉर्ड आवधिक सफ़ाई कार्य (`src/lib/db/cleanup.ts`) द्वारा हटा दिए जाते हैं
- `src/lib/db/usage*.ts` में त्रुटियाँ जाँचें — DB में लिखने की विफलताएँ लॉग की जाती हैं, लेकिन दिखाई नहीं जातीं
- सत्यापित करें कि अनुरोध वास्तव में `chatCore` तक पहुँचा था — कॉम्बो रूटिंग जाँचें

### "कोटा लागू नहीं हो रहा है"

- कुंजी की `quotaLimit` सेटिंग जाँचें
- सत्यापित करें कि `quotaWindow` सही ढंग से सेट है
- `quotaSnapshots` रिकॉर्ड खोजें — ये हर अनुरोध पर बनाए जाने चाहिए
