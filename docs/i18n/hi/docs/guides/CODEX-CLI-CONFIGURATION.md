OmniRoute को OpenAI-संगत बैकएंड के रूप में उपयोग करने के लिए Codex CLI की संपूर्ण मार्गदर्शिका।

---

> **TOML ही एकमात्र प्रभावी प्रारूप है।** आधुनिक Codex केवल `~/.codex/config.toml`
> को पढ़ता है (codex-cli 0.147.0 के साथ सत्यापित: `codex --help` में
> `-c/--config` ओवरराइड को "`~/.codex/config.toml` से लोड किया गया" बताया गया है)। पुरानी
> `~/.codex/config.yaml` लेगेसी npm CLI से संबंधित थी और उसे बिना किसी सूचना के अनदेखा कर दिया जाता है।
> डैशबोर्ड जनरेटर (`/api/cli-tools/apply`, टूल `codex`) एक
> सतर्क मर्ज के साथ TOML लिखता है — मौजूदा कुंजियाँ और अन्य प्रोवाइडर ब्लॉक सुरक्षित रहते हैं,
> API कुंजी `OMNIROUTE_API_KEY` में रहती है (फ़ाइल में कभी नहीं), और बची हुई लेगेसी
> `config.yaml` को बिना छुए माइग्रेशन नोट के रूप में रिपोर्ट किया जाता है।

## सीधे पेस्ट करने योग्य config.toml

`<YOUR_HOST>` और `<YOUR_KEY>` को अपने मानों से बदलें:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # प्रत्येक टूल कॉल के लिए इतिहास संग्रहण सीमा

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc या ~/.zshrc — वास्तविक कुंजी मान, config.toml में कभी नहीं
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT ऐप के भीतर बंडल किया गया Codex

यदि आपने ChatGPT डेस्कटॉप ऐप के माध्यम से Codex इंस्टॉल किया है, तो `codex` बाइनरी
केवल ऐप बंडल के भीतर मौजूद हो सकती है और अभी आपके शेल `PATH` में उपलब्ध नहीं हो सकती। अपने
शेल स्टार्टअप फ़ाइल में resources डायरेक्टरी जोड़ें:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

नया शेल खोलें, फिर सत्यापित करें:

```bash
command -v codex
codex --version
```

### स्थानीय अप्रमाणित OmniRoute: प्लेसहोल्डर कुंजी पर्याप्त है

Codex यह सत्यापित करता है कि `env_key` द्वारा नामित पर्यावरण चर
CLI से पहला अनुरोध बाहर जाने के **पहले** मौजूद है। यदि आपके **स्थानीय** OmniRoute
इंस्टेंस को प्रमाणीकरण की आवश्यकता नहीं है, तो कोई भी गैर-रिक्त प्लेसहोल्डर काम करेगा:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

यदि आपका OmniRoute सर्वर सुरक्षित या रिमोट है, तो इसके बजाय वास्तविक कुंजी का उपयोग करें।

> **सामान्य होस्ट विकल्प**
>
> | पहुँच           | URL                           |
> | --------------- | ----------------------------- |
> | स्थानीय नेटवर्क | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | लूपबैक          | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — यह सभी मॉडलों के लिए क्यों काम करता है

Codex CLI ने फ़रवरी 2026 में `wire_api = "chat"` (Chat Completions) को बहिष्कृत कर दिया और अब `wire_api = "responses"` (OpenAI Responses API) की **आवश्यकता** है। `wire_api = "chat"` सेट करने से v0.138 के बाद तुरंत स्टार्टअप क्रैश होता है।

GLM और Kimi सहित कई प्रोवाइडर अभी भी केवल Chat Completions एंडपॉइंट उपलब्ध कराते हैं। DeepSeek V4 अब Anthropic-संगत एंडपॉइंट के साथ-साथ एक नेटिव Responses API भी उपलब्ध कराता है; OmniRoute डिफ़ॉल्ट रूप से Responses का उपयोग करता है और प्रत्येक DeepSeek कनेक्शन को Anthropic संगतता चुनने देता है।

**OmniRoute इसे पारदर्शी ढंग से हल करता है:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute प्रोवाइडर के नेटिव प्रोटोकॉल का चयन करता है और आवश्यकता होने पर अनुवाद करता है
    → POST /responses (DeepSeek V4) या /chat/completions (Mistral / GLM / Kimi / अन्य)
```

OmniRoute का उपयोग करते समय आपको कभी भी अलग अनुवाद प्रॉक्सी की आवश्यकता नहीं होती। **सभी मॉडल `wire_api = "responses"` का उपयोग करते हैं** — बाकी सब OmniRoute संभालता है।

> **`wire_api` डिफ़ॉल्ट है** — फ़ील्ड का डिफ़ॉल्ट मान `"responses"` है और इसे `config.toml` से पूरी तरह छोड़ा जा सकता है। इसे स्पष्ट रूप से केवल तभी सेट करें, जब आप उद्देश्य का दस्तावेज़ीकरण कर रहे हों।

## कॉन्टेक्स्ट विंडो और कॉम्पैक्शन

### टोकन कॉन्फ़िगरेशन फ़ील्ड

| फ़ील्ड                           | विवरण                                                                                                                                                                                                 |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | सक्रिय मॉडल के लिए कुल टोकन बजट। इसे मॉडल की घोषित सीमा पर सेट करें।                                                                                                                                  |
| `model_auto_compact_token_limit` | वह थ्रेशोल्ड जो स्वचालित हिस्ट्री कॉम्पैक्शन को ट्रिगर करता है। **अधिकतम: `model_context_window` का 90%** — 90% से अधिक मानों को बिना सूचना के अनदेखा कर दिया जाता है।                                |
| `tool_output_token_limit`        | हिस्ट्री में प्रति टूल कॉल आउटपुट संग्रहीत किए जाने वाले टोकनों की सीमा। यह किसी एक बड़े टूल रिस्पॉन्स को पूरी विंडो भरने से रोकता है। **यह अधिकतम आउटपुट नहीं है** — यह हिस्ट्री स्टोरेज की सीमा है। |
| `compact_prompt`                 | कॉम्पैक्शन के दौरान उपयोग किए जाने वाले सिस्टम प्रॉम्प्ट के लिए इनलाइन ओवरराइड (v0.138+)।                                                                                                             |

> **`model_max_output_tokens` पर टिप्पणी**: यह फ़ील्ड **Codex CLI कॉन्फ़िग स्कीमा का भाग नहीं है** (Codex Rust कोडबेस में अनुपस्थित)। सेट किए जाने पर इसे बिना सूचना के अनदेखा कर दिया जाता है। इस पर निर्भर न रहें — हिस्ट्री में कितना टूल आउटपुट संग्रहीत हो, इसे नियंत्रित करने के लिए `tool_output_token_limit` का उपयोग करें।

## रीजनिंग प्रयास

यह नियंत्रित करता है कि प्रतिक्रिया देने से पहले मॉडल कितना "सोचता" है।

| मान      | इसके लिए उपयोग करें                      |
| -------- | ---------------------------------------- |
| `none`   | कोई रीजनिंग नहीं — सीधे प्रतिक्रिया      |
| `low`    | साधारण कार्य (नाम बदलना, फ़ॉर्मैट करना)  |
| `medium` | निर्दिष्ट न होने पर **सर्वर डिफ़ॉल्ट**   |
| `high`   | मध्यवर्ती कार्य (रीफ़ैक्टरिंग, डीबगिंग)  |
| `xhigh`  | आर्किटेक्चर, गहन विश्लेषण, जटिल समस्याएँ |

```bash
# प्रत्येक आह्वान के लिए ओवरराइड
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

रीजनिंग **सारांश** भी सेट करें, ताकि Desktop सोच संबंधी टेक्स्ट रेंडर कर सके (केवल एन्क्रिप्टेड ब्लॉब नहीं):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # या समर्थित होने पर ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute थिंकिंग बजट (सर्वर सेटिंग)

OmniRoute होस्ट पर, Codex प्रयास/सारांश को अपस्ट्रीम तक पहुँचाने के लिए **Settings → AI → Thinking Budget** को **`passthrough`** पर सेट करना आवश्यक है। **`auto` मोड** क्लाइंट के सभी `reasoning` / `reasoning_effort` फ़ील्ड हटा देता है और Codex सही ढंग से कॉन्फ़िगर होने पर भी थिंकिंग पैनल खाली कर देगा।

पूरी गाइड: [THINKING_BUDGET.md](./THINKING_BUDGET.md)।

कंप्रेशन और प्रॉम्प्ट कैश स्वतंत्र हैं और `passthrough` के अंतर्गत काम करते रहते हैं।

## प्रोफ़ाइल — प्रत्येक मॉडल/वर्कफ़्लो के लिए नामित कॉन्फ़िगरेशन

प्रोफ़ाइल आपको एक ही फ़्लैग से मॉडल + कॉन्टेक्स्ट विंडो बदलने देते हैं। प्रत्येक प्रोफ़ाइल एक सपाट
`~/.codex/<name>.config.toml` फ़ाइल है, जो आधारभूत `config.toml` के ऊपर ओवरले होती है।

> **नामकरण नियम (Codex CLI v0.137+):** फ़ाइल `~/.codex/<name>.config.toml` ही होनी चाहिए — **`profile-` प्रीफ़िक्स नहीं होना चाहिए**।
> CLI `-p kimi-k27` को → `~/.codex/kimi-k27.config.toml` के रूप में रिज़ॉल्व करता है। यदि फ़ाइल नहीं मिलती, तो डिफ़ॉल्ट बिना किसी सूचना के लागू हो जाता है।

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # तेज़, सस्ता
```

## `omniroute setup-codex` के साथ प्रोफ़ाइल स्वचालित रूप से जनरेट करना

यदि आप OmniRoute को VPS पर चलाते हैं, तो आप लाइव मॉडल कैटलॉग से प्रोफ़ाइल फ़ाइलें स्वचालित रूप से जनरेट कर सकते हैं:

```bash
# VPS से (पोर्ट 20128 पर स्थानीय OmniRoute का उपयोग करता है)
omniroute setup-codex

# किसी भी मशीन से — अपने VPS को निर्दिष्ट करें
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# फ़ाइलें लिखे बिना पूर्वावलोकन करें
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# केवल GLM और Kimi प्रोफ़ाइल जनरेट करें
omniroute setup-codex --only glm,kimi

# किसी कस्टम डायरेक्टरी में लिखें
omniroute setup-codex --codex-home /path/to/.codex
```

यह कमांड `/v1/models` प्राप्त करता है, ज्ञात मॉडलों के लिए अनुकूलित प्रोफ़ाइल का उपयोग करता है, अन्य संगत टेक्स्ट मॉडलों के लिए कैटलॉग मेटाडेटा का सहारा लेता है, और प्रत्येक के लिए `~/.codex/<name>.config.toml` लिखता है। यह आइडेम्पोटेंट है — इसे दोबारा चलाना सुरक्षित है।

यदि मूल `config.toml` में `model_providers.omniroute` की परिभाषा नहीं है, तो स्पष्ट
`setup-codex` प्रत्येक जनरेट किए गए ओवरले में वह परिभाषा शामिल करता है और चुने गए
स्थानीय या रिमोट एंडपॉइंट का उपयोग करता है। यह मूल फ़ाइल को अपरिवर्तित छोड़ता है। मौजूदा प्रोवाइडर
परिभाषा उसके एंडपॉइंट और प्रमाणीकरण सेटिंग्स सहित इनहेरिट की जाती है। अमान्य
मूल TOML, प्रोफ़ाइल लिखे जाने से पहले जनरेशन रोक देता है।

जब आप `--api-key` या `OMNIROUTE_API_KEY` प्रदान करते हैं, तो नई परिभाषित प्रोवाइडर प्रविष्टि
`env_key = "OMNIROUTE_API_KEY"` को संदर्भित करती है; स्वयं कुंजी को कभी सहेजा या
पूर्वावलोकन में प्रिंट नहीं किया जाता। उस परिवेश में यह वेरिएबल सेट करें जहाँ आप Codex लॉन्च करते हैं। बिना
प्रदान की गई कुंजी के, नई परिभाषा में कुंजी की कोई आवश्यकता नहीं होती, जो ऐसे OmniRoute इंस्टेंस
के लिए है जिसे बिना प्रमाणीकरण वाले अनुरोध स्वीकार करने हेतु कॉन्फ़िगर किया गया हो।

नीचे वर्णित ऑप्ट-इन कैटलॉग ऑटो-सिंक, ओवरले में पहले से मौजूद प्रोवाइडर परिभाषाओं को
सुरक्षित रखता है, लेकिन नई प्रोवाइडर सेटिंग्स को बूटस्ट्रैप नहीं करता; पहले स्पष्ट सेटअप या
डैशबोर्ड के माध्यम से प्रोवाइडर कॉन्फ़िगर करें। मौजूदा प्रोवाइडर सेटिंग्स को ड्राई-रन पूर्वावलोकन
से बाहर रखा जाता है, क्योंकि उनमें ऑपरेटर द्वारा प्रबंधित क्रेडेंशियल हो सकते हैं।

सफल प्रोवाइडर मॉडल खोज/इंपोर्ट द्वारा लाइव कैटलॉग में बदलाव किए जाने के बाद OmniRoute इन्हीं प्रोफ़ाइल फ़ाइलों को **स्वचालित रूप से सिंक** भी कर सकता है। यह **ऑप्ट-इन है और डिफ़ॉल्ट रूप से बंद रहता है**: इसे **CLI Code डैशबोर्ड** ("CLI profile auto-sync" → Codex) से टॉगल करें, या `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` सेट करें (यह `CLI_ALLOW_CONFIG_WRITES` का भी पालन करता है, जो डिफ़ॉल्ट रूप से चालू है)। सक्षम होने पर यह केवल अलग-अलग `~/.codex/*.config.toml` प्रोफ़ाइल फ़ाइलें लिखता है; यह सक्रिय/डिफ़ॉल्ट `~/.codex/config.toml`, Codex-lb सेटिंग्स, प्रमाणीकरण या प्रोवाइडर चयन को कभी नहीं बदलता।

## `omniroute launch-codex` के साथ Codex लॉन्च करना

Codex लॉन्च करने से पहले आपके OmniRoute इंस्टेंस की स्वास्थ्य-जाँच करता है:

```bash
# स्थानीय OmniRoute के विरुद्ध लॉन्च करें (डिफ़ॉल्ट पोर्ट 20128)
omniroute launch-codex

# किसी विशिष्ट प्रोफ़ाइल के साथ लॉन्च करें
omniroute launch-codex --profile kimi-k27

# किसी रिमोट VPS के विरुद्ध लॉन्च करें
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# codex को अतिरिक्त आर्ग्युमेंट पास करें
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex दो सामान्य मैनिफ़ेस्ट-संचालित एंट्री पॉइंट्स का भी एक लक्ष्य है
(`bin/cli/cli-manifest.mjs`):

```bash
# इंटरैक्टिव मॉडल पिकर → ~/.codex/<name>.config.toml लिखता है (TOML, env_key)
omniroute configure codex

# -c फ़्लैग के माध्यम से omniroute प्रोवाइडर इंजेक्ट करके codex लॉन्च करें (कोई कॉन्फ़िगरेशन नहीं लिखा जाता)
omniroute run codex
```

## लंबे समय से चल रहे कार्य

दो OmniRoute डिफॉल्ट्स चुपचाप कई घंटों के Codex CLI सत्रों को नुकसान पहुंचा सकते हैं। न ही कोई Codex CLI सेटिंग — है, दोनों OmniRoute पक्ष पर रहते हैं। अपस्ट्रीम प्रॉक्सी से कॉन्फ़िगरेशन माइग्रेट करने वाले उपयोगकर्ता, जो खातों को पिन करते हैं और निष्क्रिय कटऑफ को अक्षम करते हैं, अक्सर दोनों को प्रभावित करते हैं और निष्कर्ष निकालते हैं कि OmniRoute "लंबे सत्र को बनाए नहीं रख सकता है।"

| लक्षण                                                                          | संभावित कारण                                                                         | दस्ता                    |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------ |
| सत्र खातों को बदलता रहता है / बदलावों के बीच प्रॉम्प्ट-कैश निरंतरता खो जाती है | सत्र एफ़िनिटी TTL `0` है (अक्षम)                                                     | `sessionAffinityTtlMs`   |
| क्लाइंट-फेसिंग प्रॉम्प्ट के अभाव में कनेक्शन बीच में ही बंद हो जाता है         | स्ट्रीम निष्क्रिय वॉचडॉग को बिना किसी अपस्ट्रीम खंड के 10 मिनट के बाद निकाल दिया गया | `STREAM_IDLE_TIMEOUT_MS` |

संबंधित चर्चाएँ: [#7126](https://github.com/cheaper-inference/OmniRoute/discussions/7126) (लंबा कार्य ड्रॉप), [#5718](https://github.com/cheaper-inference/OmniRoute/discussions/5718) (एफ़िनिटी डिफ़ॉल्ट बंद क्यों होता है)। ट्रैकिंग: [#7287](https://github.com/cheaper-inference/OmniRoute/issues/7287) ।

### 1. सत्र एफ़िनिटी — एक वार्तालाप को एक खाते में पिन करें

**गलती करना:** `sessionAffinityTtlMs = 0` (अक्षम)।

**इसे कहां सेट करें**

- डैशबोर्ड →** सेटिंग्स → रूटिंग** →** सत्र आत्मीयता** →** एफ़िनिटी TTL (सेकंड)** (`ComboDefaultsTab`)
- या `sessionAffinityTtlMs` के साथ PATCH सेटिंग्स** मिलीसेकंड** (Zod रेंज `0`-`86_400_000`, यानी 24 घंटे तक)

> कोडेक्स-केवल `codexSessionAffinityTtlMs` से #7274 में नाम बदला गया। लीगेसी कुंजी अभी भी केवल पढ़ने योग्य उपनाम के रूप में स्वीकार की जाती है; नई कॉन्फ़िगरेशन में `sessionAffinityTtlMs` उपयोग करना चाहिए। आत्मीयता अब लागू होती है** कोई** प्रदाता एक बार TTL `0` से ऊपर है, न केवल Codex — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → सत्र एफ़िनिटी देखें।

**0 पर रहने पर क्या टूटता है?**

मल्टी-टर्न Codex वार्तालाप का प्रत्येक मोड़ सक्रिय कॉम्बो रणनीति द्वारा स्वतंत्र रूप से रूट किया जाता है और एक पर उतर सकता है** प्रति मोड़ अलग खाता** . इससे अपस्ट्रीम सत्र/प्रॉम्प्ट-कैश निरंतरता टूट जाती है। OmniRoute केवल Codex सत्र हेडर (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) और बॉडी फ़ील्ड जैसे `prompt_cache_key` / `session_id` से परामर्श करता है जब TTL `0` ( `src/sse/services/auth.ts` में`extractSessionAffinityKey` ) से अधिक होता है।

**कई घंटों के एकल कार्य के लिए अनुशंसित**

TTL सेट करें** कार्य की अपेक्षित दीवार-घड़ी की लंबाई से ऊपर** (UI मैक्स है** 86400 सेकंड** = 24 घंटे):

| अपेक्षित कार्य लंबाई | एफ़िनिटी TTL (UI, सेकंड)  | `sessionAffinityTtlMs` |
| -------------------- | ------------------------- | ---------------------- |
| कुछ घंटे             | `14400` (4 घंटे)          | `14400000`             |
| रात भर / ~ 12h       | `43200` (12 घंटे)         | `43200000`             |
| पूरा दिन             | `86400` (24 घंटे, अधिकतम) | `86400000`             |

ऑप्ट-इन जानबूझकर किया गया है: एफ़िनिटी को अक्षम करने से खातों में लोड-संतुलन को बढ़ावा मिलता है; इसे सक्षम करने से एक लंबे एजेंट सत्र के लिए निरंतरता को बढ़ावा मिलता है। यह मार्गदर्शिका करती है** नहीं** लंबे Codex कार्यों को चलाने वाले डिफ़ॉल्ट — ऑपरेटरों को बदलें, इसमें ऑप्ट इन करना होगा।

### 2. स्ट्रीम निष्क्रिय टाइमआउट — शांत तर्क मोड़ को खत्म न करें

**गलती करना:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 मिनट)। अनसेट होने पर यह `REQUEST_TIMEOUT_MS` से विरासत में मिलता है; साझा आधार रेखा भी 600000 है। [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → टाइमआउट देखें।

**डिफ़ॉल्ट पर क्या टूटता है**

एक Codex तर्क/उपकरण मोड़ जो 10 मिनट से अधिक समय तक मौन रहता है** कोई वास्तविक अपस्ट्रीम हिस्सा नहीं** SSE आइडल वॉचडॉग (`open-sse/utils/stream.ts`) द्वारा बलपूर्वक बंद किया गया है। क्लाइंट को अक्सर "बिना किसी सूचना के स्वचालित रूप से बंद हो गया" मिलान वाला एक बेअर कनेक्शन ड्रॉप — दिखाई देता है।

महत्वपूर्ण विवरण: OmniRoute का सिंथेटिक SSE** दिल की धड़कन दोबारा नहीं रुकती** निष्क्रिय घड़ी. केवल एक वास्तविक अपस्ट्रीम बॉडी चंक `lastChunkTime` को अपडेट करता है। एक शांत मॉडल जो अभी भी "सोच" रहा है, निगरानीकर्ता के दृष्टिकोण से एक रुके हुए अपस्ट्रीम के समान दिखता है।

संबंधित अंडरसी बॉडी निष्क्रियता: `FETCH_BODY_TIMEOUT_MS` (उसी 10-मिनट की बेसलाइन पर भी डिफ़ॉल्ट; `0` इसे अक्षम कर देता है)। स्ट्रीमिंग के लिए, स्ट्रीम सक्रिय होने के बाद `FETCH_TIMEOUT_MS` केवल कनेक्शन सेटअप/पहले हेडर — को कवर करता है, स्टॉल `STREAM_IDLE_TIMEOUT_MS` और `FETCH_BODY_TIMEOUT_MS` द्वारा नियंत्रित होते हैं।

**कई घंटों के एकल कार्य के लिए अनुशंसित**

OmniRoute प्रक्रिया वातावरण में (`.env` /compose/systemd):

```bash
# Disable stream idle + body inactivity cutoffs for long reasoning turns
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

या उन्हें आपके अपेक्षित सबसे लंबे शांत अंतराल से ऊपर उठाएं (मान मिलीसेकंड हैं):

```bash
# Example: allow up to 2 hours of silence between upstream chunks
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

इन env vars को बदलने के बाद OmniRoute को पुनरारंभ करें।

### कंक्रीट रेसिपी — बहु-घंटे Codex कार्य

1. **खाता पिन करें:** डैशबोर्ड → सेटिंग्स → रूटिंग → सत्र एफ़िनिटी → एफ़िनिटी TTL = `43200` (12 घंटे) या `86400` (अधिकतम 24 घंटे)।
2. **निष्क्रिय कटऑफ़ बढ़ाएँ/अक्षम करें** OmniRoute के वातावरण में:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. इन दो व्यवहारों के लिए सामान्य Codex `config.toml` (`wire_api = "responses"`, सही `base_url`, `OMNIROUTE_API_KEY`) — रखें, कोई कोडेक्स-साइड affinity/idle नॉब मौजूद नहीं है।
4. OmniRoute पुनरारंभ करें, फिर लंबा Codex कार्य प्रारंभ करें।

### डिफ़ॉल्ट निर्णय (#7287)

| दस्ता                    | जहाज डिफ़ॉल्ट      | इस गाइड में बदलाव?                                                                                |
| ------------------------ | ------------------ | ------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (बंद)          | **नहीं** — ऑप्ट-इन बना हुआ है (लोड-संतुलन बनाम निरंतरता; चर्चा #5718 देखें)                       |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 मिनट) | **नहीं** सामान्य यातायात के लिए — 10 मिनट रहता है; long Codex ऑपरेटर इसे बढ़ाते या अक्षम करते हैं |

विश्व स्तर पर किसी भी डिफ़ॉल्ट को फ़्लिप करने से केवल Codex ही नहीं, बल्कि किसी इंस्टेंस के प्रत्येक क्लाइंट के लिए व्यवहार बदल जाएगा। घुंडी का दस्तावेजीकरण करें; जब तक कोई स्पष्ट ऑपरेटर निर्णय अन्यथा न कहे तब तक डिफ़ॉल्ट को अकेला छोड़ दें।

### निष्क्रिय कटौती का निदान

जब निष्क्रिय वॉचडॉग फायर करता है, OmniRoute एक रेखा लॉग करता है जिसका आकार इस प्रकार होता है:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` के लिए Grep (या कोड `stream_idle_timeout` /त्रुटि नाम `StreamIdleTimeoutError`)। प्रदाता खंड OmniRoute है जो उस अनुरोध के लिए उपयोग किया जाता है (`codex`, अन्य प्रदाता आईडी, या अज्ञात होने पर `provider` ) — यह हमेशा शाब्दिक स्ट्रिंग `codex` नहीं होता है।

## समस्या निवारण

**`Error: wire_api = "chat" is no longer supported`** अपने कॉन्फिगरेशन से `wire_api = "chat"` हटाएँ। `wire_api = "responses"` सेट करें या फ़ील्ड छोड़ें (v0.138 के बाद से डिफ़ॉल्ट `"responses"` है)।

**`Error: model not found`** सत्यापित करें कि मॉडल सही उपसर्ग के साथ OmniRoute में मौजूद है। `omniroute models list` प्रयोग करें या `/dashboard/providers/<provider>` खोलें।

**`Authentication error`** पुष्टि करें कि `OMNIROUTE_API_KEY` निर्यात किया गया है: `echo $OMNIROUTE_API_KEY`।

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`** Codex पुष्टि करता है कि पहला अनुरोध करने से पहले env var मौजूद है। संरक्षित सर्वर के लिए एक वास्तविक कुंजी, या एक गैर-रिक्त प्लेसहोल्डर जैसे `OMNIROUTE_API_KEY=local` निर्यात करें जब आपका** स्थानीय** OmniRoute उदाहरण के लिए प्रमाणीकरण की आवश्यकता नहीं है। यदि आपने इसे `~/.bashrc` या `~/.zshrc` में जोड़ा है तो शेल को पुनः आरंभ करें।

**`Connection refused`** सत्यापित करें OmniRoute चल रहा है और `base_url` host/port आपके नेटवर्क के लिए सही है (स्थानीय बनाम Tailscale बनाम VPS)।

**संदर्भ सीमा के निकट सत्र क्रैश हो गया** `model_context_window` और `model_auto_compact_token_limit` स्पष्ट रूप से सेट करें। ऊपर संदर्भ विंडो तालिका देखें।

**संघनन बहुत देर से जलता है** `model_auto_compact_token_limit` विंडो के 80-85% तक कम करें। कभी भी 90% से ऊपर सेट न करें।

**प्रोफ़ाइल लोड नहीं हो रही (`-p <name>` चुपचाप अनदेखा कर दिया)** पुष्टि करें कि फ़ाइल `~/.codex/<name>.config.toml` पर मौजूद है (कोई `profile-` उपसर्ग नहीं)। `ls ~/.codex/*.config.toml` चलाएँ।

**लंबा Codex कार्य बीच में ही रुक जाता है/खातों को मोड़ों के बीच स्विच कर देता है** [लंबे समय से चल रहे कार्य](#long-running-tasks) देखें. सत्र एफ़िनिटी सक्षम करें (कार्य लंबाई से ऊपर TTL ) और `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` बढ़ाएँ या अक्षम करें। ग्रेप OmniRoute `Idle timeout: no data from` के लिए लॉग करता है।
