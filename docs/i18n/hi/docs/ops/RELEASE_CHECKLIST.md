## npm विश्वसनीय प्रकाशन (v3.8.51 से डिफ़ॉल्ट) — अनुरोध पर मंचित, फ़ॉलबैक के रूप में प्रत्यक्ष

`npm-publish.yml` के माध्यम से प्रकाशित करता है** एनपीएम विश्वसनीय प्रकाशन (OIDC)** डिफ़ॉल्ट रूप से: `stage-npm` जॉब (github-होस्टेड) उस रन के लिए अल्पकालिक npm क्रेडेंशियल के लिए GitHub के आईडी-टोकन का आदान-प्रदान करता है, रिपॉजिटरी रहस्यों में कोई लंबे समय तक चलने वाला npm टोकन नहीं —, कोई 2FA प्रॉम्प्ट नहीं है, उद्गम संलग्न है। यह अब बायपास एनपीएम प्रतिबंधों का मामला है, जो टोकन 2एफए को छोड़ देते हैं उन्हें हटा दिया जा रहा है; यह WS1.3 गारंटी को बनाए रखते हुए परियोजना के v3.8.48 तक के पूर्ण स्वचालित प्रवाह को पुनर्स्थापित करता है (एक लीक हुआ टोकन अकेले प्रकाशित नहीं हो सकता है — कोई टोकन नहीं है)।

**एक बार का सेटअप (मालिक):** npmjs.com → पैकेज `omniroute` → सेटिंग्स → _विश्वसनीय प्रकाशक_ → GitHub: मालिक `diegosouzapw`, रेपो `OmniRoute`, वर्कफ़्लो `npm-publish.yml` (पर्यावरण: कोई नहीं)। जब तक वह मौजूद नहीं होता, स्वचालित चरण `ENEEDAUTH` के साथ विफल हो जाता है: `publish_mode=staged` (नीचे) या `direct` के साथ पुनः प्रेषण।

### चरणबद्ध प्रकाशन (अनुरोध पर — `publish_mode=staged`)

एनपीएम-प्रकाशन वर्कफ़्लो अब सीधे प्रकाशित नहीं होता है: यह पैक किए गए टारबॉल (`check:pack-boot`) को बूट करता है और फिर `npm stage publish` — चलाता है, सटीक बाइट्स रजिस्ट्री पर पार्क किए जाते हैं,** इंस्टॉल करने योग्य नहीं** जब तक मालिक मंजूरी न दे दे. मानव 2FA गेट सबूत को AFTER के लिए ले जाया गया, उससे पहले नहीं।

**वर्कफ़्लो के हरा होने के बाद स्वामी प्रवाह:**

1. `npm stage list omniroute` — स्टेज आईडी ढूंढें (वर्कफ़्लो सारांश में भी मुद्रित)।
2. चरणबद्ध बाइट्स सत्यापित करें (अनुशंसित): `npm stage download <id>`, फिर डाउनलोड किए गए टारबॉल को एक अस्थायी उपसर्ग में स्थापित करें और इसे बूट करें (`npm run check:pack-boot` उसी पैक को स्वचालित करता है→ install → बूट निर्णय CI में)।
3. `npm stage approve <id>` — 2FA प्रॉम्प्ट IS प्रकाशित करें। `npm stage reject <id>` त्याग देता है।
4. पोस्ट-पब्लिश नेट: पोस्ट-पब्लिश सत्यापनकर्ता (v3.8.49 योजना काWS1.4) सार्वजनिक रजिस्ट्री से प्रकाशित संस्करण को एक साफ कंटेनर में स्थापित करता है और इसे बूट करता है।

**आपातकालीन फ़ॉलबैक:** `publish_mode=direct` के साथ `workflow_dispatch` विरासत को तत्काल `npm publish` पुनर्स्थापित करता है (केवल तभी उपयोग करें यदि स्टेजिंग स्वयं गलत व्यवहार करती है; रिकॉर्ड क्यों करें)।

**एक बार का सख्तीकरण (मालिक, npmjs.com):** `omniroute` के लिए विश्वसनीय प्रकाशक को स्टेज-ओनली मोड में कॉन्फ़िगर करें ताकि एक लीक हुआ लंबे समय तक चलने वाला टोकन कहीं से भी सीधे `npm publish` न कर सके — CI केवल स्टेज कर सके; केवल स्वामी की 2FA रिलीज़ होती है।

**टूटी-पुरानी कलाकृति प्लेबुक (अपरिवर्तित):** डिफ़ॉल्ट रिफ्लेक्स के रूप में `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` (मिनट, प्रतिवर्ती); `npm unpublish` केवल 72h/no-dependents विंडो के अंदर और पहली चाल के रूप में कभी नहीं। Docker: किसी संस्करण टैग को कभी भी दोबारा न लिखें — रोलबैक `latest` को अंतिम अच्छे डाइजेस्ट की ओर पुनः निर्देशित कर रहा है।

**Docker हब `latest` (प्रत्येक स्थिर SemVer प्रकाशन पर आवश्यक):** `docker-publish` वर्कफ़्लो को टैग करना होगा** दोनों** `X.Y.Z` और, जब `should-promote-latest.sh` सहमत होता है तो यह उच्चतम स्थिर SemVer है, `:latest` इसके साथ** वही डाइजेस्ट** . कार्य के बाद: हब `latest` डाइजेस्ट नए SemVer डाइजेस्ट के बराबर है और `last_updated` स्थानांतरित हो गया है। `:latest` पुराने बिल्ड पर न छोड़ें जबकि रिलीज़ नोट्स उन सुधारों के बारे में बात करते हैं जो केवल git पर मौजूद हैं। क्विकस्टार्ट लिखें `:latest` उपयोग करें; GitOps `X.Y.Z` पिन करते रहना चाहिए। [Docker रिलीज़ चैनल](../guides/DOCKER_GUIDE.md#release-channels) और #10317 देखें।

**Docker हब संगठन रिपॉजिटरी (`cheaperinference/omniroute`):** Docker हब नामस्थानों के बीच एक रिपॉजिटरी को स्थानांतरित नहीं कर सकता है, इसलिए `diegosouzapw/omniroute` अपना पुल इतिहास और प्रत्येक रिलीज़ रखता है, और `docker-publish` का `mirror-org-dockerhub` कार्य प्रत्येक रिलीज़ किए गए संस्करण (और प्रचारित होने पर `:latest` ) को `ghcr.io/cheaper-inference/omniroute` से संगठन रिपॉजिटरी में कॉपी करता है। इसे `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` रहस्यों की आवश्यकता है; उनके बिना कार्य "Docker हब ऑर्ग मिरर स्किप्ड" चेतावनी के साथ हरा रहता है और अन्य रजिस्ट्रियां सामान्य रूप से प्रकाशित होती हैं। वहां जारी संस्करण को बाद में प्रकाशित करने के लिए, चलाएँ** क्रियाएँ → मिरर Docker छवि को Docker हब org → पर वर्कफ़्लो चलाएँ** `version=X.Y.Z` के साथ (और उच्चतम स्थिर संस्करण के लिए `promote_latest` ): यह मौजूदा छवियों की प्रतिलिपि बनाता है, कोई पुनर्निर्माण नहीं।

## हॉटफिक्स फ़ास्ट-लेन (लेबल `hotfix`)

`hotfix` लेबल वाला PR भारी CI मैट्रिक्स (9-शार्ड E2E, कवरेज रैचेट,
क्वालिटी-गेट, क्वालिटी-एक्सटेंडेड) को छोड़ देता है और तेज़, उच्च-संकेत वाले गेट बनाए रखता है: बिल्ड,
यूनिट शार्ड, इंटीग्रेशन, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
और टारबॉल बूट-स्मोक (`check:pack-boot`)। लक्ष्य: ~33 मिनट के बजाय ≤15 मिनट में सफल परिणाम।

**प्रवेश नीति — चारों आवश्यक (Chromium/VS Code/Node की आपातकालीन लेन के अनुरूप):**

1. **गंभीरता**: प्रोडक्शन बाधित है — प्रकाशित आर्टिफ़ैक्ट बूट होते समय क्रैश होता है /
   कोई सुरक्षा सुधार / रिलीज़ का प्रत्येक उपयोगकर्ता प्रभावित है। "महत्वपूर्ण" का अर्थ "बाधित" नहीं है।
2. **प्राधिकार**: केवल रिपॉज़िटरी स्वामी ही `hotfix` लेबल लगाता है। लेबल ही
   स्वीकृति है — किसी कैंपेन PR पर इसे स्वयं लागू न करें।
3. **साक्ष्य**: PR बॉडी में पिछली पूरी तरह सफल भारी रन (वह सुइट जिसे
   छोड़े गए जॉब फिर से सत्यापित करते) के साथ-साथ सुधार के अपने पहले विफल और फिर सफल हुए टेस्ट का लिंक होता है।
4. **दायरा**: केवल चेरी-पिक — न्यूनतम सुधार, कोई रीफ़ैक्टर नहीं, कोई असंबंधित बदलाव नहीं।

छोड़ी गई कवरेज/रैचेट सतह को रिलीज़ ब्रांच पर अगली पूर्ण रन
(निरंतर रिलीज़-सफलता) द्वारा फिर से सत्यापित किया जाता है — यह लेन केवल प्रतीक्षा छोड़ती है, सत्यापन कभी नहीं।
केवल टेस्ट वाले अंतर (`tests/` के अंतर्गत सभी फ़ाइलें, `tests/e2e/` के अंतर्गत कोई नहीं) बिना किसी लेबल के
E2E मैट्रिक्स को स्वचालित रूप से छोड़ देते हैं।

### लेआउट बनाएँ

रिपॉजिटरी तीन अलग-अलग आउटपुट निर्देशिकाओं का उपयोग करती है — उन्हें कभी भी मिश्रित नहीं करता है:

| निर्देशिका | उद्देश्य                                                                 | ट्रैक किया गया?  |
| ---------- | ------------------------------------------------------------------------ | ---------------- |
| `src/`     | एप्लिकेशन स्रोत (TypeScript / TSX)                                       | हाँ              |
| `.build/`  | मध्यवर्ती — `next build` आउटपुट बनाएं (`distDir`)                        | नहीं (gitignore) |
| `dist/`    | शिप करने योग्य एनपीएम बंडल — `assembleStandalone` द्वारा असेंबल किया गया | नहीं (gitignore) |

> **ऑपरेटर नोट:** दूरस्थ VPS छवि निर्देशिका `/usr/lib/node_modules/omniroute/app/` बनी हुई है। केवल** इन-रेपो** बिल्ड आउटपुट स्थानांतरित (`app/` → `dist/`)। दूरस्थ `app/` dir — में तैनाती कौशल rsync `dist/` सामग्री के लिए कोई VPS पथ परिवर्तन की आवश्यकता नहीं है।

**एकल-निर्माण प्रवाह:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

क्या NOT `npm run build` चलाता है, इसके बाद — को तैनात करने के लिए एक अलग `npm run build:cli` चलाता है `npm run build:release` उपयोग करता है जो एक कमांड में + प्रहरी का एक साफ पुनर्निर्माण करता है।

## 3.9.0 LTS कट (3.8.58 में पूर्वाभ्यास)

v3.8.59 के बाद अगला संस्करण 3.9.0 है, और इसकी नोक दो लंबे समय तक रहने वाली शाखाएं बन जाती है: `stable/v3` (v3 LTS लाइन, npm `latest`) और `develop` (v4, 4.0.0, npm `nightly` पर पहुंच गया)। branch/channel मॉडल, फॉरवर्ड-पोर्ट और लेबल [RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md) में हैं; योजना [ROADMAP](../../ROADMAP.md) (चरण 3) में है। कट एक बार चलता है; 3.8.58 एक कांटे पर शुरू से अंत तक इसका पूर्वाभ्यास करता है, और 3.8.59 [GO/NO-GO चेकलिस्ट](./LTS_GO_NO_GO.md) के साथ बंद होता है।

### ड्राई-रन (केवल पढ़ने के लिए, किसी भी समय सुरक्षित)

```bash
npm run release:dry-run-lts-cut                       # the real cut: 3.9.0 from HEAD, previous tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # pin the source commit
```

`scripts/release/dry-run-lts-cut.mjs` कुछ भी निष्पादित नहीं करता है: यह git और `gh` पढ़ता है और पूरे अनुक्रम — पूर्व शर्त को प्रिंट करता है (स्रोत हल करता है, स्रोत रिपॉजिटरी में — पूरा इतिहास है, एक उथला क्लोन `stable/v3` धक्का नहीं दे सकता है, प्राप्त करने वाला पक्ष पहले ग्राफ्टेड पैरेंट पर पैक को अस्वीकार कर देता है, इसलिए पहले पूर्ण क्लोन या `git fetch --unshallow origin` से काटें — पिछला टैग मौजूद है, `package.json` लक्ष्य संस्करण है, एक `release-freeze` मुद्दा खुला है, कोई खुला नहीं है मौजूदा रिलीज शाखा पर `Release branch not green` मुद्दा — एक ऐसी शाखा है जो अस्तित्व में नहीं है रिपोर्ट `?` अज्ञात है, कभी भी हरी — ओमनी-क्यू रिलीज PRs लैंड नहीं करती है (G11: `config/merge-queue/config.json` वैध है, इसका `bases` रिलीज शाखा का प्रबंधन करता है, `mode` `live`, इसका लेबल मौजूद है), `release/*` नियम सेट अभी भी विलोपन और बल-पुश को रोकता है, और `stable/v3` और `develop` अभी तक मौजूद नहीं है), दो शाखा चरण, कौन से निष्क्रिय-वर्कफ़्लो ट्रिगर और `if:` स्थितियाँ सत्य हो जाती हैं (और जो एक रिपॉजिटरी वेरिएबल द्वारा गेटेड रहती हैं या कैनोनिकल रिपॉजिटरी पर पिन की जाती हैं), अपेक्षित डिस्ट-टैग (`latest` → 3.9.0, `next` और `nightly` खाली) और रोलबैक। `0` = `RESULT: READY` बाहर निकलें, `1` = एक अवरुद्ध पूर्व शर्त विफल (`✗`), `2` = उपयोग त्रुटि। `--advisory <id,...>` किसी चेक को छुपाए बिना उसे चेतावनी (`!`) में डाउनग्रेड कर देता है।

वास्तविक कट का ड्राई-रन चलाएँ जबकि 3.9.0 रिलीज़ फ़्रीज़ अभी भी खुला है — टैग के बाद शाखाएँ बनाई जाती हैं और चरण 12सी फ़्रीज़ हटाने से पहले।

### PR पूर्वावलोकन आर्टिफैक्ट (एक बार बनाएं, समान बाइट्स को बढ़ावा दें)

`.github/workflows/preview-artifact.yml` एक PR हेड से एक उत्पादन टारबॉल बनाता है और उस सटीक निर्माण (#8084 स्लाइस (ए)) को मान्य करता है। केवल समान-भंडार PRs ; कुछ भी प्रकाशित नहीं है.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # or add the `preview-artifact` label
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview install
```

रन `npm ci`, `npm run build:release`, `npm run check:pack-artifact` करता है, टारबॉल को पैक करता है, `npm run check:pack-boot` (नकली रहस्य, अल्पकालिक डेटा dir) चलाता है, फिर से पैक करता है और तब तक विफल रहता है जब तक कि डाइजेस्ट समान न हो, फिर `artifact-identity.json` (हेड SHA, बेस SHA, लॉकफाइल हैश, प्लेटफ़ॉर्म, आर्क, नोड ABI, बंडलर, बिल्ड पॉलिसी — `scripts/release/artifact-identity.mjs`) को रिकॉर्ड करता है और प्रमाणित करता है एक अलग काम में टारबॉल. पूर्वावलोकन को बढ़ावा देने का अर्थ है उस टारबॉल को स्थापित करना: कभी भी स्रोत से पुनर्निर्माण न करें।

### कट (3.9.0, GO के बाद)

1. GO [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) में रिकॉर्ड किया गया।


4. पहली PR भूमि से पहले `stable/v3` और `develop` (नियम सेट + मर्ज कतार) को सुरक्षित रखें।
5. निष्क्रिय वर्कफ़्लो शाखा अस्तित्व द्वारा चालू होते हैं: `forward-port.yml` ( `stable/v3` पर पुश करें), `validate-stable-pr.yml` (PRs से `stable/v3`) और `nightly-v4-build.yml` ( `develop` बनाता है)। गो-लाइव से पहले, `secrets.FORWARD_PORT_TOKEN` रिपॉजिटरी सीक्रेट सेट करें (ताकि CI फॉरवर्ड-पोर्ट PRs पर चले); रात्रिकालीन प्रकाशन तब तक बंद रहता है जब तक स्वामी रिपॉजिटरी वेरिएबल `vars.NIGHTLY_PUBLISH` को `true` पर सेट नहीं कर देता और npm विश्वसनीय प्रकाशन `nightly-v4-build.yml` स्वीकार नहीं कर लेता। चैनल रिज़ॉल्यूशन `scripts/release/dist-tag.mjs` है, वही रिज़ॉल्वर `npm-publish.yml` उपयोग करता है।
6. चैनल सत्यापित करें: `npm view omniroute dist-tags --json` `latest` = 3.9.0 दिखाता है और v4 प्रकाशित होने तक कोई `next` / `nightly` नहीं दिखाता है।
7. यदि आवश्यक हो तो रोलबैक करें: `git push origin --delete refs/heads/stable/v3 refs/heads/develop` और `npm dist-tag add omniroute@3.8.59 latest`।

## रोलबैक

यदि रिलीज़ में कोई गंभीर समस्या हो:

1. `gh release edit vX.Y.Z --prerelease` (इसे नवीनतम नहीं के रूप में चिह्नित करता है)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (केवल तभी, जब उपयोगकर्ताओं ने इसे अभी तक अपनाया न हो)
3. या: `release/vX.Y.0` पर हॉटफ़िक्स → पैच रिलीज़ `vX.Y.(Z+1)`
4. GitHub Discussions और Discord में तुरंत सूचना दें

## सख्त नियम

- `main` में कभी भी सीधे कमिट न करें
- `main` या `release/*` ब्रांचों पर कभी भी `git push --force` का उपयोग न करें
- Husky हुक्स (`--no-verify`) को कभी भी न छोड़ें
- सीक्रेट्स, क्रेडेंशियल्स या `.env` फ़ाइलों को कभी भी कमिट न करें
- कवरेज ≥60/60/60/60 (स्टेटमेंट्स/लाइन्स/फ़ंक्शन्स/ब्रांचेस) रहना चाहिए
- `src/`, `open-sse/`, `electron/` या `bin/` में प्रोडक्शन कोड बदलते समय हमेशा टेस्ट शामिल करें या अपडेट करें

## स्वचालित सिंक जाँच

PR खोलने से पहले डॉक्स सिंक गार्ड को स्थानीय रूप से चलाएँ:

```bash
npm run check:docs-sync
```

CI भी इस जाँच को `.github/workflows/ci.yml` (लिंट जॉब) में चलाता है।
