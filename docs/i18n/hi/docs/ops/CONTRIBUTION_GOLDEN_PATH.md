इस गाइड का उपयोग किसी पुल रिक्वेस्ट के लिए सबसे छोटा विश्वसनीय डेवलपमेंट लूप चुनने हेतु करें। यह नीचे लिंक किए गए क्षेत्र-विशिष्ट आर्किटेक्चर और सुरक्षा दस्तावेज़ों को
प्रतिस्थापित नहीं करता; यह प्रत्येक सामान्य परिवर्तन प्रकार को उसके अनुबंधों, केंद्रित जाँचों और CI कवरेज से जोड़ता है।

## प्रत्येक परिवर्तन द्वारा अपनाया जाने वाला पथ

1. **संपादन से पहले बेस चुनें।** उच्चतम सक्रिय `release/v*` ब्रांच खोजें और
   उसके नवीनतम सिरे से ब्रांच बनाएँ। उसी ब्रांच को लक्ष्य बनाएँ, `main` को नहीं। यदि कोई रिलीज़ फ़्रीज़ सक्रिय है, तो फ़्रीज़ की गई
   ब्रांच को लक्ष्य न बनाएँ; इसके बजाय
   [ब्रांचिंग और रिलीज़ मॉडल](BRANCHING_MODEL.md) में वर्णित अगले सक्रिय चक्र का उपयोग करें।
2. **अनुबंधों को नाम दें।** प्रत्येक ऐसे कैटलॉग, स्कीमा, जनरेट किए गए आर्टिफ़ैक्ट, सार्वजनिक API या उपयोगकर्ता
   इंटरफ़ेस की पहचान करें जिसे परिवर्तन प्रभावित करता है। नीचे दी गई तालिका न्यूनतम आरंभिक सेट बताती है।
3. **केंद्रित टेस्ट लिखें या अपडेट करें।** `src/`, `open-sse/`, `electron/`, या
   `bin/` में प्रोडक्शन परिवर्तनों के लिए उसी PR में एक स्वचालित टेस्ट आवश्यक है। पहले उन सबसे छोटी टेस्ट फ़ाइलों को चलाएँ जो
   व्यवहार को प्रमाणित करती हैं, फिर सूचीबद्ध केंद्रित गेट चलाएँ।
4. **CI को व्यापक मैट्रिक्स चलाने दें।** पूर्ण यूनिट शार्ड, Vitest, कवरेज रैचेट और
   प्रोडक्शन बिल्ड PR पर चलते हैं। स्थानीय रूप से व्यापक सुइट केवल तभी चलाएँ जब कोई केंद्रित विफलता
   व्यापक प्रभाव की ओर संकेत करे या परिवर्तन कई सबसिस्टम तक फैला हो।
5. **समीक्षा से पहले समन्वय करें।** सक्रिय बेस को फ़ेच करें, उसकी नई कमिट और उसके सापेक्ष अपने डिफ़ का
   निरीक्षण करें, फिर योगदानकर्ता वर्कफ़्लो के अनुसार बेस को रीबेस या मर्ज करें। जनरेट की गई फ़ाइल
   और कैटलॉग के टकरावों को उनके स्रोत से हल करें, उन्हें फिर से जनरेट करें, केंद्रित लूप दोबारा चलाएँ और पुष्टि करें कि
   PR अब भी सक्रिय रिलीज़ ब्रांच को लक्षित करता है।
6. **साक्ष्य दर्ज करें।** PR टेम्पलेट में चलाए गए कमांड, जोड़ी या बदली गई प्रत्येक टेस्ट फ़ाइल,
   माइग्रेशन या फ़ीचर फ़्लैग और अब भी लंबित किसी भी केवल-CI सत्यापन को सूचीबद्ध करें।

## परिवर्तन प्रकार के अनुसार आदर्श पथ

नीचे दिए गए कमांड न्यूनतम केंद्रित जाँचें हैं, आपके द्वारा बदले गए व्यवहार को सीधे कवर करने वाले टेस्ट को छोड़ने की
अनुमति नहीं।

### प्रोवाइडर

**अनुबंध**

- `src/shared/constants/providers/` में प्रोवाइडर परिभाषा और
  `src/shared/constants/providers.ts` में उसका संयोजन।
- `open-sse/config/providerRegistry.ts` या उसकी निकाली गई रजिस्ट्री फ़ाइलों में मॉडल और क्षमताएँ।
- लागू होने पर एक्ज़ीक्यूटर/ट्रांसलेटर चयन, OAuth या API-कुंजी कॉन्फ़िगरेशन, डैशबोर्ड एसेट और जनरेट किया गया
  प्रोवाइडर संदर्भ।
- सार्वजनिक क्रेडेंशियल को `resolvePublicCred()` का उपयोग करना चाहिए; त्रुटि प्रतिक्रियाओं को साझा सैनिटाइज़्ड
  त्रुटि हेल्पर का उपयोग करना चाहिए। `docs/security/PUBLIC_CREDS.md` (git; `/docs` में कंपाइल नहीं किया गया) और
  [त्रुटि सैनिटाइज़ेशन](../security/ERROR_SANITIZATION.md) देखें।

**केंद्रित लूप**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # जब कैटलॉग बदलता है; जनरेट किए गए डिफ़ को कमिट करें
npm run lint
```

प्रभावित प्रत्येक अनुरोध परिवार का भी टेस्ट करें: चैट, Responses, इमेज, एम्बेडिंग, ऑडियो या वीडियो।
जनरेट किए गए कैटलॉग और गोल्डन डिफ़ की समीक्षा अनुबंध परिवर्तनों के रूप में करें; उन्हें बिना जाँचे स्वीकार न करें।

### रूटिंग

**अनुबंध**

- `src/shared/constants/routingStrategies.ts` में सार्वजनिक स्ट्रैटेजी मान और UI मेटाडेटा।
- `open-sse/services/combo.ts` और `open-sse/services/combo/` के अंतर्गत डिस्पैच और क्रम निर्धारण।
- कॉम्बो स्कीमा, परसिस्टेंस, रेज़िलिएंस स्थिति, मॉडल क्षमताएँ और API/UI नियंत्रण।
- व्यवहार बदलने पर [ऑटो-कॉम्बो इंजन](../routing/AUTO-COMBO.md) और रेज़िलिएंस दस्तावेज़।

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # स्ट्रैटेजी या डिस्पैच परिवर्तन
npm run check:known-symbols      # स्ट्रैटेजी पंजीकरण परिवर्तन
npm run lint
```

स्थानीय रूप से निर्धारक मॉक्ड-अपस्ट्रीम टेस्ट का उपयोग करें। लाइव कॉम्बो स्मोक टेस्ट के लिए क्रेडेंशियल आवश्यक हैं और वे
मैन्युअल हैं, CI के विकल्प नहीं।

### UI / UX

**अनुबंध**

- `src/app/` और `src/shared/components/` के अंतर्गत Next.js रूट/पेज और साझा कंपोनेंट सीमाएँ।
- API प्रतिक्रिया संरचनाएँ, लोडिंग/रिक्त/त्रुटि स्थितियाँ, कीबोर्ड और स्क्रीन-रीडर व्यवहार,
  रिस्पॉन्सिव लेआउट, थीमिंग और लोकेल विस्तार।
- `src/i18n/messages/en.json` में अंग्रेज़ी UI स्रोत स्ट्रिंग; नया उपयोगकर्ता-दृश्य टेक्स्ट हार्ड-कोड न करें।

**केंद्रित लूप**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

इंटरैक्शन या विज़ुअल परिवर्तनों के लिए ऐप चलाएँ और संकरे तथा चौड़े, दोनों व्यूपोर्ट जाँचें। CI
प्रोडक्शन बिल्ड और व्यापक सुइट चलाता है; विज़ुअल व्यवहार के लिए अब भी परिवर्तन के अनुरूप केंद्रित कंपोनेंट, Playwright
या दस्तावेज़ित मैन्युअल जाँच आवश्यक है।

### i18n

**अनुबंध**

- `src/i18n/messages/en.json` UI स्रोत है; `config/i18n.json` लोकेल स्रोत है।
- CLI कैटलॉग अलग से `bin/cli/locales/` के अंतर्गत स्थित हैं।
- ICU प्लेसहोल्डर और टैग को बिल्कुल यथावत रखें। प्रोडक्ट/प्रोवाइडर/मॉडल नाम,
  प्रोटोकॉल और हेडर नाम, कमांड, कोड/JSON पहचानकर्ता, URLs, पर्यावरण चर या
  `OmniRoute`, `OAuth`, `MCP`, और `A2A` जैसे संरक्षित शब्दों का अनुवाद न करें। वर्तमान स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` है।

**केंद्रित लूप**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # जब CLI स्ट्रिंग/कैटलॉग बदलते हैं
npm run lint
```

यह मौजूदा सिस्टम के लिए मार्गदर्शन है, इसकी टूलिंग या कुंजी मॉडल का विस्तार करने का आमंत्रण नहीं।
जब तक प्रतिस्थापन सिस्टम डिज़ाइन किया जा रहा है, i18n पैच को अत्यंत सीमित रखें। बाहरी सेवाओं को कॉल करने वाले अनुवाद
कमांड तब तक न चलाएँ, जब तक कार्य में स्पष्ट रूप से जनरेट किए गए अनुवाद आवश्यक न हों और
आपने परिणामी डिफ़ की समीक्षा न कर ली हो।

### CLI

**अनुबंध**

- `bin/cli/` में सार्वजनिक commands और flags, जनरेट किए गए API commands, exit codes, stdout/stderr और
  JSON output shapes, config/environment व्यवहार, और पैकेज की गई फ़ाइलें।
- CLI के उपयोगकर्ता-सामना करने वाले strings को CLI i18n layer का उपयोग करना चाहिए और `en`/`pt-BR` catalogs को समन्वित रखना चाहिए।
- Node को समर्थित runtime और प्रकाशित binary contract के रूप में बनाए रखें।

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # जनरेट किए गए/बंडल किए गए CLI बदलाव
npm run check:pack-policy     # पैकेज-सतह के बदलाव
npm run lint
```

जब व्यवहार parsing, फ़ाइलों या exit status पर निर्भर हो, तो अस्थायी data directory में सटीक command का उपयोग करें। CI व्यापक package artifact और ecosystem जाँच करता है।

### डेटाबेस

**अनुबंध**

- `src/lib/db/` के अंतर्गत domain modules; विशिष्ट modules को सीधे import करें (पुरानी `localDb.ts` re-export layer हटा दी गई थी)।
- `src/lib/db/migrations/` के अंतर्गत क्रमांकित, idempotent SQL migrations, transaction safety, upgrade
  व्यवहार, indexes, और schema से प्रभावित प्रत्येक caller।
- Routes और handlers कभी भी सीधे raw SQL जारी नहीं करते।

**केंद्रित लूप**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration जोड़ते समय नए database और पिछले schema से upgrade, दोनों का परीक्षण करें। Database tests को handles बंद करने चाहिए और cleanup के दौरान `resetDbInstance()` को call करना चाहिए। `npm run test:bun:db` केवल तभी चलाएँ जब best-effort Bun adapter path बदलता है; Node प्रामाणिक बना रहता है।

### Build / deploy

**अनुबंध**

- Root और workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package contents, Electron platform metadata, CI workflows, और deployment sentinels।
- समर्थित Node ranges और `CLAUDE.md` में allow-listed Bun उपयोग अक्षुण्ण रहने चाहिए।
- Build artifacts untracked रहें; dependency, license, workflow, और package policies लागू होते हैं।

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency या lockfile में बदलाव
npm run check:pack-policy      # प्रकाशित package surface में बदलाव
npm run lint
```

`npm run build` का स्थानीय रूप से उपयोग केवल तभी करें, जब बदलाव compilation, standalone assembly, assets,
या runtime bundling को प्रभावित करता हो। `npm run build:release` का उपयोग केवल release/deploy validation के लिए करें। CI का build अंतिम cross-platform संकेत है; platform-specific Electron बदलावों के लिए संबंधित focused build या smoke evidence आवश्यक है।

## साझा मशीन के लिए डेवलपर स्क्रिप्ट

दो `scripts/dev/` सहायक ऐसी devbox पर स्थानीय लूप को परिभाषित करते हैं जहाँ अन्य सत्र सक्रिय हैं:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD से फ़ाइलें
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # बिल्कुल यही फ़ाइलें
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # पृथक worktree, समानांतर रूप से सुरक्षित
```

- `typecheck-touched.sh` केवल बदली गई `.ts/.tsx` फ़ाइलों की typecheck एक अस्थायी
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) के माध्यम से 6 GB heap के अंतर्गत करता है, इसलिए यह पूरे प्रोजेक्ट के
  `tsc -p tsconfig.json` को प्रतिस्थापित करता है, जो अत्यधिक लोड वाली मशीन पर OOM हो जाता है।
  यह बदली गई फ़ाइलों की त्रुटियों के साथ एक सारांश पंक्ति प्रिंट करता है और बदली गई फ़ाइलों में
  त्रुटियाँ होने पर `1`, जब केवल आयातित फ़ाइलों में त्रुटियाँ हों या tsc बिना diagnostics के बंद
  हो गया हो तब `2` (इसके द्वारा बताए गए `_artifacts/typecheck-touched/` के अंतर्गत log को पढ़ें),
  और कोई त्रुटि न होने पर `0` के साथ बाहर निकलता है। अस्थायी tsconfig हमेशा हटा दिया जाता है;
  इसे कभी commit न करें।
- `new-worktree.sh`, `<git-common-dir>/omniroute-new-worktree.lock` पर समवर्ती runs को क्रमबद्ध
  करता है (डिफ़ॉल्ट रूप से अधिकतम 600 s तक, एक दृश्यमान संदेश के साथ, प्रतीक्षा करता है; script
  header में override का दस्तावेज़ीकरण है) और जब worktree के अस्तित्व में आने से पहले
  `git worktree add` विफल होता है, तो यह अपने द्वारा बनाई गई branch को वापस हटा देता है, इसलिए
  दोबारा प्रयास करने के लिए मैन्युअल `git branch -D` की आवश्यकता नहीं होती। hard-linked
  `node_modules` और `.husky/_` की कॉपी अपरिवर्तित रहती है।

## स्थानीय candidate लूप

Source tests यह प्रमाणित नहीं कर सकते कि पैकेज किया गया artifact boot होता है: packaging सूचियाँ,
हटाई गई dependencies और native binaries की समस्याएँ tarball के install और start होने के बाद ही
सामने आती हैं। `npm run dev:candidate` (`scripts/dev/candidate.mjs`), RFC #8084 के
build-once / validate / promote flow का स्थानीय पक्ष है: यह एक candidate बनाता है, ठीक उसी
artifact को validate करता है, directory renames के साथ उसे promote करता है, और promoted slot
के health check में विफल होने पर उसे roll back करता है।

```bash
npm run dev:candidate -- run --dry-run --json  # योजना प्रिंट करें, कुछ न बदलें
npm run dev:candidate -- run                   # बनाएँ + validate करें + promote करें, स्वतः rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ में install करें
npm run dev:candidate -- validate --id <id>    # किसी खाली port पर boot करें, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current और previous की अदला-बदली करें
npm run dev:candidate -- run --from-tarball <file.tgz>  # कहीं और (CI में) बने tarball का पुनः उपयोग करें
```

- **एक बार बनाएँ।** `build` वर्तमान tree को pack करता है (इसके लिए `dist/server.js` आवश्यक है,
  इसलिए पहले `npm run build:release` चलाएँ) या `--from-tarball` को copy करता है, फिर tarball को
  एक पृथक npm prefix में install करता है, क्योंकि tarball में `node_modules` नहीं होता। id छोटा
  `HEAD` sha होता है (जब tree में स्थानीय बदलाव हों तो `-dirty`) या tarball के लिए
  `tgz-<sha256>` होता है। पहले से build की गई clean id को दोबारा build करने के बजाय पुनः उपयोग
  किया जाता है; उसे फिर से build करने के लिए `--force` दें।
- **Source को नहीं, package को validate करें।** `validate`, install किए गए CLI को
  (`serve --port <free port>`) एक नए `DATA_DIR=<candidate>/data`, नकली secrets और environment से
  हटाई गई operator की `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` तथा `INITIAL_PASSWORD` के
  साथ start करता है, ताकि यह fresh install की keyless loopback posture की जाँच कर सके। यह
  `GET /api/health` द्वारा 200 लौटाए जाने की प्रतीक्षा करता है, `GET /v1/models` द्वारा 200
  लौटाया जाना आवश्यक बनाता है, process group को रोकता है और tarball hash के साथ verdict को
  `validation.json` में दर्ज करता है।
- **उसी artifact को promote करें।** `promote` ऐसे candidate को अस्वीकार करता है जिसके वर्तमान
  tarball hash के लिए passing validation न हो। डिफ़ॉल्ट active slot
  `_artifacts/candidate/current` है; `--target <dir>` उसी filesystem पर कोई अन्य directory
  चुनता है और उसका previous slot `<dir>.previous` होता है। प्रत्येक rename atomic है और बीच
  में विफलता होने पर पहले से किए जा चुके renames को उलट दिया जाता है।
- **Roll back करें।** `run`, promoted slot को फिर से validate करता है और वह check विफल होने पर
  `current` तथा `previous` को वापस अदला-बदली करता है। पहली validation में विफल होने वाले
  candidate को कभी promote नहीं किया जाता।

सब कुछ git द्वारा अनदेखी की जाने वाली `_artifacts/candidate/` के अंतर्गत लिखा जाता है; किसी
मौजूदा OmniRoute installation और उसकी data directory को कभी नहीं छुआ जाता। Promoted CLI
`_artifacts/candidate/current/prefix/bin/omniroute` है; इसका उपयोग करते समय इसे अपने
`DATA_DIR` के साथ start करें। Exit codes: सफलता के लिए `0`, validation या promotion विफल होने
पर `1`, और usage error या build मौजूद न होने पर `2`।

| प्रत्येक पैच के लिए स्थानीय रूप से चलाएँ                                       | CI व्यापक संकेत प्रदान करता है                                        |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| ऊपर दिए गए प्रत्यक्ष व्यवहार परीक्षण और श्रेणी गेट                             | शार्ड किया गया पूर्ण यूनिट सुइट और क्रमिक परीक्षण                     |
| `npm run lint`                                                                 | Vitest सुइट और कवरेज/गुणवत्ता रैचेट                                   |
| टाइपचेक या बिल्ड केवल तभी, जब प्रभावित अनुबंध में इसकी आवश्यकता हो             | प्रोडक्शन बिल्ड, सुरक्षा, दस्तावेज़, निर्भरता और PR-नीति गेट          |
| मैन्युअल इंटरैक्शन/लाइव जाँच केवल तभी, जब स्वचालन व्यवहार को प्रमाणित न कर सके | वर्कफ़्लो द्वारा कॉन्फ़िगर की गई क्रॉस-जॉब एकीकरण और प्लेटफ़ॉर्म जाँच |

एक सफल केंद्रित लूप बदले गए अनुबंध के बारे में प्रमाण है, यह इस बात का प्रमाण नहीं है कि असंबंधित CI जाँचें
पास होंगी। इसके विपरीत, प्रत्येक स्थानीय संपादन को पूर्ण रिपॉज़िटरी मैट्रिक्स की प्रतीक्षा न करवाएँ।

## समन्वय जाँच-सूची

समीक्षा का अनुरोध करने से पहले:

- पुष्टि करें कि PR का आधार अभी भी उच्चतम सक्रिय `release/v*` शाखा है।
- उस आधार को फ़ेच करें और अपनी शाखा बनाने के बाद से शामिल हुए कमिट की समीक्षा करें।
- अनचाहे या जनरेट किए गए बदलावों के लिए `git diff <active-base>...HEAD` की समीक्षा करें।
- स्रोत को अपडेट करके और आउटपुट को पुनः जनरेट करके कैटलॉग और जनरेट किए गए दस्तावेज़ों के टकराव हल करें।
- समन्वय के बाद PR विवरण में सूचीबद्ध प्रत्येक केंद्रित परीक्षण/गेट को फिर से चलाएँ।
- बदले हुए आधार से मेल कराने मात्र के लिए कभी भी अभिकथनों को कमज़ोर न करें या आवश्यक परीक्षण न हटाएँ।

रिलीज़-फ़्रीज़ और रीटार्गेटिंग नियमों के लिए,
[ब्रांचिंग और रिलीज़ मॉडल](BRANCHING_MODEL.md) का उपयोग करें। संपूर्ण CI सूची के लिए,
[गुणवत्ता गेट संदर्भ](../architecture/QUALITY_GATES.md) का उपयोग करें।
