> **संक्षेप में**: OmniRoute अपने प्राथमिक स्टोर के रूप में **WAL जर्नलिंग के साथ SQLite** का उपयोग करता है, जिसमें संवेदनशील फ़ील्ड के स्थिर डेटा के लिए **AES-256-GCM** एन्क्रिप्शन होता है। यह मार्गदर्शिका स्कीमा, माइग्रेशन, बैकअप/रिकवरी और परिचालन रनबुक को कवर करती है।

**स्रोत:**

- `src/lib/db/core.ts` — सिंगलटन + SCHEMA_SQL (17 आधार टेबल)
- `src/lib/db/migrationRunner.ts` — संस्करणयुक्त माइग्रेशन
- `src/lib/db/migrations/` — 167 संस्करणयुक्त SQL फ़ाइलें
- `src/lib/db/encryption.ts` — एन्क्रिप्शन सहायक
- `src/lib/db/backup.ts` — बैकअप एक्सपोर्ट/इम्पोर्ट
- `src/lib/db/healthCheck.ts` — स्वास्थ्य निदान

## SQLite क्यों?

OmniRoute ने कई कारणों से PostgreSQL/MySQL के बजाय SQLite को चुना:

| कारक             | SQLite                                | PostgreSQL                        |
| ---------------- | ------------------------------------- | --------------------------------- |
| **डिप्लॉयमेंट**  | एम्बेडेड — अलग सर्वर की आवश्यकता नहीं | सर्वर सेटअप आवश्यक                |
| **एन्क्रिप्शन**  | एप्लिकेशन-स्तरीय (AES-256-GCM)        | अंतर्निहित TDE                    |
| **प्रदर्शन**     | छोटे/मध्यम वर्कलोड के लिए तेज़        | अत्यधिक समवर्ती लेखन के लिए बेहतर |
| **समवर्तीता**    | WAL मोड समवर्ती पठन की अनुमति देता है | पूर्ण MVCC                        |
| **बैकअप**        | एकल-फ़ाइल कॉपी                        | `pg_dump` या फ़ाइलसिस्टम स्नैपशॉट |
| **उपयोग-स्थिति** | प्रति-उपयोगकर्ता इंस्टॉल, एम्बेडेड    | मल्टी-टेनेंट SaaS                 |

**एकल-उपयोगकर्ता, एकल-इंस्टेंस** डिप्लॉयमेंट (OmniRoute का प्राथमिक उपयोग-क्षेत्र) के लिए, SQLite अधिक सरल और तेज़ है।

### WAL जर्नलिंग

`core.ts` डेटाबेस को **WAL (Write-Ahead Logging) मोड** में खोलता है:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL लेखन के दौरान **समवर्ती पठन** की अनुमति देता है — यह डैशबोर्ड के लिए महत्वपूर्ण है, जो अनुरोध रिकॉर्ड किए जाने के दौरान क्वेरी करता है।

डिफ़ॉल्ट कैश आकार **65,536 KiB (64 MiB)** है। SQLite ऋणात्मक
`cache_size` को KiB में एक अनुमानित ऊपरी सीमा के रूप में समझता है और आवश्यकता के अनुसार पेज आवंटित करता है।
**सेटिंग्स > सिस्टम और स्टोरेज > कैश आकार** में **1 से
1,000,000 KiB** तक के पूर्णांक मान स्वीकार किए जाते हैं; सेटिंग सहेजने पर इसे सक्रिय डेटाबेस कनेक्शन पर लागू कर दिया जाता है,
और OmniRoute स्टार्टअप पर स्थायी मान को पुनर्स्थापित करता है।

## डेटाबेस का स्थान

SQLite फ़ाइल यहाँ संग्रहीत होती है:

| OS      | पथ                                                                        |
| ------- | ------------------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                             |
| macOS   | `~/.omniroute/storage.sqlite`                                             |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                                 |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` के माध्यम से कॉन्फ़िगर करने योग्य) |

सहायक फ़ाइलें:

- `storage.sqlite-wal` — राइट-अहेड लॉग
- `storage.sqlite-shm` — साझा मेमोरी फ़ाइल
- `call_logs/` — अनुरोध पेलोड आर्टिफ़ैक्ट (यदि सक्षम हो)

**स्थान को ओवरराइड करें:**

```bash
DATA_DIR=/custom/path omniroute
```

### मॉड्यूल सीमाएँ

एक मुख्य आर्किटेक्चरल नियम: **मॉड्यूल एक-दूसरे की टेबल को सीधे एक्सेस नहीं करते**। किसी अन्य मॉड्यूल के डेटा के साथ काम करने के लिए, उस मॉड्यूल से फ़ंक्शन इम्पोर्ट करें।

```ts
// ❌ गलत: किसी अन्य मॉड्यूल से सीधे SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ सही: providers मॉड्यूल के फ़ंक्शन का उपयोग करें
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

यह नियम कोड समीक्षा के माध्यम से लागू किया जाता है—इसके लिए कोई स्थिर जाँच नहीं है, लेकिन उल्लंघनों को चिह्नित किया जाता है।

- `acp_*` टेबल — एजेंट क्लाइंट प्रोटोकॉल
- `oneproxy_*` टेबल — 1proxy मार्केटप्लेस
- `proxy_assignments` — प्रॉक्सी स्कोप बाइंडिंग
- `detailed_call_artifacts` — कॉल लॉग आर्टिफ़ैक्ट मेटाडेटा
- `quota_alert_history` — कोटा अलर्ट ऑडिट
- `command_code_auth_sessions` — कमांड कोड OAuth सत्र

लगभग 30+ टेबलों की पूरी सूची `src/lib/db/migrations/` में है।

## माइग्रेशन

OmniRoute उपयोग करता है** संस्करणबद्ध, निष्क्रिय प्रवासन** `src/lib/db/migrations/` में. प्रत्येक माइग्रेशन एक एकल SQL फ़ाइल है। दो नामकरण प्रारूप सह-अस्तित्व में हैं; `_omniroute_migrations` में रिकॉर्ड किया गया संस्करण संख्यात्मक उपसर्ग है।

### प्रवासन नामकरण

| प्रारूप                                        | उदाहरण                               | के लिए इस्तेमाल होता है                                                                                                                                                    |
| ---------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (बिल्कुल 3 अंक)          | `241_seen_models.sql`                | पुरानी श्रृंखला `001`-`241`। जब टाइमस्टैम्प प्रारूप उतरा तो जम गया (`240` और `241` इसके ठीक पहले विलय कर दिया गया था): किसी भी नई फ़ाइल को अनुक्रमिक संख्या नहीं मिलती है। |
| `YYYYMMDDHHMMSS_description.sql` (14 अंक, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 से निर्मित प्रत्येक माइग्रेशन।                                                                                                                                  |

परिवर्तन क्यों: अनुक्रमिक संख्याओं के साथ, समानांतर PRs वही अगली संख्या चुनी और विलय से पहले एक को छोड़कर सभी को पुन: क्रमांकित करना पड़ा। एक UTC टाइमस्टैम्प प्रत्येक PR अपना स्वयं का संस्करण देता है।

टाइमस्टैम्प प्रारूप के लिए नियम ( `npm run check:migration-numbering` द्वारा लागू, `scripts/check/lib/migrationNaming.mjs` में जनरेटर के साथ साझा):

- टाइमस्टैम्प एक वास्तविक UTC दिनांक और समय है, `20261113000000` से पहले नहीं और भविष्य में 10 मिनट से अधिक नहीं।
- विवरण लोअरकेस `snake_case` है जो एक अक्षर (`a-z`, `0-9`, शब्दों के बीच एकल `_` ) से शुरू होता है, अधिकतम 80 अक्षर।
- समान टाइमस्टैम्प वाली दो फ़ाइलें डुप्लिकेट हैं।
- नो-गैप नियम केवल पुरानी श्रृंखला पर लागू होता है: ज्ञात अंतराल `026`, `055` और `121` को छोड़कर, `001` से `241` तक प्रत्येक संख्या मौजूद होनी चाहिए। `241` (या कोई पुरानी फ़ाइल) को हटाने से गेट विफल हो जाता है। `001` और `241` कभी भी `KNOWN_GAPS` अनुमति सूची में नहीं जोड़ा जा सकता। टाइमस्टैम्प्ड फ़ाइलें कभी भी अंतराल पैदा नहीं करतीं।
- `src/lib/db/migrations/` में प्रत्येक प्रविष्टि वैध लोअरकेस `.sql` नाम के साथ एक नियमित फ़ाइल होनी चाहिए। एक निर्देशिका, एक सिम्लिंक, एक `.SQL` या `.sql.bak` फ़ाइल, एक छिपी हुई फ़ाइल या एक स्थान के साथ एक नाम गेट को विफल कर देता है, क्योंकि धावक इसे चुपचाप छोड़ देगा या बूट पर क्रैश हो जाएगा।

**आदेश लागू करें.** रनर उपसर्ग के संख्यात्मक मान के आधार पर क्रमबद्ध करता है, पाठ के आधार पर नहीं: पहले पुरानी `001`-`241` फ़ाइलें, फिर टाइमस्टैम्प क्रम में टाइमस्टैम्प वाली फ़ाइलें, फिर `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ( `ee-001` जैसे संस्करण) के साथ पंजीकृत कोई भी नामस्थान वाली निर्देशिका। लंबित माइग्रेशन वह फ़ाइल है जिसका संस्करण `_omniroute_migrations` में नहीं है, इसलिए किसी पुरानी शाखा से माइग्रेशन जो नई शाखा के बाद विलय हो जाता है, अभी भी मौजूदा डेटाबेस पर लागू होता है।

**टाइमस्टैम्प निर्माण क्रम है, मर्ज क्रम नहीं।** यदि आपका माइग्रेशन किसी माइग्रेशन द्वारा बनाई गई तालिका या कॉलम पर निर्भर करता है** नई** टाइमस्टैम्प (उदाहरण के लिए, दूसरे PR से एक जो पहले विलय हुआ था), एक ताज़ा डेटाबेस आपका पहले चलाएगा और विफल हो जाएगा। जबकि आपका PR अभी भी खुला है, फ़ाइल नाम को `npm run db:new-migration` के साथ पुनर्जीवित करें ताकि इसे एक नया टाइमस्टैम्प मिल सके, या इसे स्वतंत्र बना सकें। `npm run test:migrations:fresh` प्रत्येक माइग्रेशन को एक खाली डेटाबेस पर लागू करता है और इसे पकड़ता है।

### मर्ज किए गए माइग्रेशन को कभी भी हटाया या बदला नहीं जाता है

एक बार जब कोई माइग्रेशन फ़ाइल रिलीज़ शाखा या `main` पर होती है, तो यह पहले से ही होमोलॉग और डेवलपर डेटाबेस, VPS इंस्टॉल पर और एंटरप्राइज़ सिंक में चल चुकी होती है। तब से:

- **इसे कभी न हटाएं.** ताज़ा इंस्टॉल अपना स्कीमा खो देंगे जबकि उन्नत डेटाबेस इसे बनाए रखेंगे।
- **इसका नाम कभी न बदलें.** `_omniroute_migrations` में संस्करण अब किसी फ़ाइल से मेल नहीं खाएगा, इसलिए इसे पहले से लागू करने वाला प्रत्येक डेटाबेस इसे फिर से चलाएगा। नॉन-इडेम्पोटेंट SQL फिर डेटा को डुप्लिकेट करता है या बूट बंद कर देता है।
- **एक अलग स्कीमा की आवश्यकता है?** `npm run db:new-migration` के साथ एक नया माइग्रेशन बनाएं।

नाम बदलना केवल उस फ़ाइल के लिए सुरक्षित है जिसे अभी तक मर्ज नहीं किया गया है, गेट के संकेत यही स्थिति दर्शाते हैं। एक रिलीज़ टैग यहां कुछ भी नहीं बदलता है: `release/v*` शाखा में प्रत्येक पुश Docker `:next` छवि प्रकाशित करता है और होमोलोग, VPS इंस्टॉल और एंटरप्राइज़ सिंक पर चलता है, इसलिए किसी भी `vX.Y.Z` टैग मौजूद होने से पहले एक मर्ज किया गया माइग्रेशन वास्तविक डेटाबेस पर चलता है। गेट आधार फ़ाइल के प्रत्येक निष्कासन को विफल कर देता है, चाहे टैग किया गया हो या नहीं।

- **मर्ज किए गए माइग्रेशन को पूर्ववत करना.** फ़ाइल को हटाने वाला `git revert` गेट विफल हो जाता है। फ़ाइल को रखें और उसके स्कीमा को एक नए माइग्रेशन में पूर्ववत करें: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` इत्यादि के साथ। उन्नत और ताज़ा डेटाबेस फिर उसी स्कीमा के साथ समाप्त होते हैं।
- **एक स्वीकृत नाम: एक अनुकूलता प्रविष्टि और समान सामग्री।** यदि मर्ज की गई फ़ाइल को स्थानांतरित करना होगा (उदाहरण के लिए, दो मर्ज की गई फ़ाइलें एक टाइमस्टैम्प साझा करती हैं और रनर एक संस्करण टकराव के साथ रुक जाता है), तो उसके SQL छुए बिना बाद वाले का नाम बदलें और `src/lib/db/migrationRunner/constants.ts` में `{ fromVersion, fromName, toVersion, toName }` को `RENAMED_MIGRATION_COMPATIBILITY` में जोड़ें। पुराने संस्करण को लागू करने वाले डेटाबेस में फ़ाइल को दोबारा चलाने के बजाय उनकी `_omniroute_migrations` पंक्ति को स्थानांतरित कर दिया जाता है। गेट इस तरह के नाम बदलने के बारे में चेतावनी देता है और हमेशा उस पर कम्यूटेशन चेक चलाता है, चाहे नया टाइमस्टैम्प कुछ भी हो: ताजा इंस्टॉल फ़ाइल को उसकी नई स्थिति पर लागू करता है, अपग्रेड किए गए डेटाबेस ऐसा नहीं करते हैं, इसलिए पुराने के पास एक नया टाइमस्टैंप चुनें। यदि सामग्री बदल गई है (एक स्कीमा परिवर्तन अभी भी नए माइग्रेशन में जाता है), या यदि प्रविष्टि की लक्ष्य फ़ाइल डिस्क पर नहीं है, तो गेट नाम बदलने में विफल रहता है।
- **एक ही टाइमस्टैम्प के भीतर कभी भी नाम न बदलें।** एक नाम बदलें जो टाइमस्टैम्प रखता है और केवल विवरण बदलता है, प्रवेश के साथ या उसके बिना, गेट में विफल रहता है। एक प्रविष्टि के साथ जिसका `toVersion` उसके `fromVersion` बराबर है, धावक पुरानी `_omniroute_migrations` पंक्ति को हटा देता है और फ़ाइल को पहले से ही चलाने वाले प्रत्येक डेटाबेस पर फिर से लागू करता है। किसी प्रविष्टि के बिना, रनर केवल संस्करण को ट्रैक करता है: यह उन डेटाबेस पर फ़ाइल को छोड़ देता है (नई सामग्री वहां कभी नहीं चलती है) और प्रत्येक बूट पर एक पुन: क्रमांकन त्रुटि लॉग करता है। किसी अन्य टाइमस्टैम्प और संगतता प्रविष्टि का उपयोग करें, या नाम रखें।
- **गेट जाँच करता है कि पुनर्नामित फ़ाइल दोबारा नहीं चलती है।** प्रत्येक कवर किए गए नाम के लिए, गेट `--must-not-apply` के साथ कम्यूटेशन चेक के लिए नया फ़ाइल नाम पास करता है। चेक अपग्रेड किए गए डेटाबेस को वास्तविक रनर के साथ बूट करता है, और यदि रनर उस फ़ाइल को फिर से लागू करता है (उदाहरण के लिए, क्योंकि प्रविष्टि में गलत संस्करण या नाम है, या क्योंकि गेट का टेक्स्ट पार्सर `constants.ts` TypeScript से अलग पढ़ता है), तो गेट `migration renomeada rodaria de novo` के साथ विफल हो जाता है और आपको प्रविष्टि के पुराने और नए संस्करणों और नामों की जांच करने के लिए कहता है।

### गेट आधार के विरुद्ध क्या जाँच करता है

पुल अनुरोध और मर्ज-क्यू चलने पर, `npm run check:migration-numbering` बेस शाखा पर समान निर्देशिका के साथ डिस्क पर `src/lib/db/migrations/` तुलना करता है। आधार, इस क्रम में है: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` वैरिएबल, या, जब `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` या `merge_group` है, तो मर्ज कमिट का पहला पैरेंट, इवेंट पेलोड का `merge_group.base_sha`, या `git merge-base HEAD origin/$GITHUB_BASE_REF`। बिना समाधान योग्य आधार के चलने वाले पुल अनुरोध या मर्ज-क्यू में गेट विफल हो जाता है। `--base` के बिना CI बाहर यह `comparação com a base: pulada (sem --base)` प्रिंट करता है और इन नियमों को छोड़ देता है।

`--base-latest-tag` तुलना नवीनतम रिलीज टैग (सेम्वर ऑर्डर में`vX.Y.Z` ; नाइटलीज़ जैसे प्रत्यय टैग की गणना नहीं की जाती है) से की जाती है जो कि `HEAD` के इतिहास में है, `--base` के समान नियमों के साथ। रिलीज-ग्रीन (`scripts/quality/validate-release-green.mjs`) इस तरह से गेट चलाता है, क्योंकि पुश और शेड्यूल किए गए रन में कोई पुल अनुरोध आधार नहीं होता है और एक मर्ज ताजा CI रन के बिना लैंड कर सकता है। इतिहास में कोई रिलीज़ टैग न होने से गेट विफल हो जाता है; `git fetch --tags` चलाएँ ( CI में, `actions/checkout` `fetch-depth: 0` के साथ टैग लाता है)।

IF EXISTS` के साथ एक नया माइग्रेशन जोड़ें।                                                                              |

कम्यूटेशन चेक का एक रन आउट-ऑफ़-ऑर्डर, संपादित और नामांकित फ़ाइलों को एक साथ कवर करता है।

कम्यूटेशन चेक (`scripts/check/migration-commutation.ts`) वास्तविक इंस्टॉल पथ के साथ दो अस्थायी डेटाबेस बनाता है: एक** अपग्रेड** एक (बेस माइग्रेशन के साथ बूट करें, फिर पुल अनुरोध के माइग्रेशन के साथ उसी फ़ाइल पर दोबारा बूट करें) और एक** ताजा** एक (पुल अनुरोध के माइग्रेशन के साथ एक बूट)। यह परिणामी स्कीमा की तुलना करता है: टेबल और कॉलम (कॉलम क्रम को अनदेखा करना), UNIQUE / PRIMARY KEY और FOREIGN KEY बाधाएं, प्रत्येक तालिका का सामान्यीकृत `CREATE TABLE` पाठ (जिसमें CHECK बाधाएं, संयोजन, उत्पन्न कॉलम और तालिका विकल्प शामिल हैं), अनुक्रमित, ट्रिगर और दृश्य। पंक्ति डेटा की तुलना नहीं की गई है. यदि वे मेल खाते हैं, तो गेट प्रिंट करता है कि फ़ाइल क्रम से बाहर है, लेकिन आवागमन करती है, और पास हो जाती है। यदि वे भिन्न हैं, तो गेट अंतर के साथ विफल हो जाता है और मामले के लिए एक संकेत देता है: एक आउट-ऑफ-ऑर्डर फ़ाइल के लिए, उसका नाम `npm run db:new-migration` के साथ पुन: उत्पन्न करें, जो सुरक्षित है क्योंकि फ़ाइल अभी तक मर्ज नहीं हुई है; संपादित आधार फ़ाइल के लिए, आधार सामग्री को पुनर्स्थापित करें और परिवर्तन को एक नए माइग्रेशन में डालें; पुनर्नामित फ़ाइल के लिए, नाम बदलें को पूर्ववत करें या कोई अन्य नया टाइमस्टैम्प चुनें जहाँ यह आवागमन करता है, किसी अन्य नाम के साथ समान टाइमस्टैम्प कभी नहीं। यदि चेक स्वयं नहीं चल सकता है, तो गेट CI में विफल हो जाता है और केवल स्थानीय रूप से चेतावनी देता है। एक संपादित आधार फ़ाइल के लिए, उन्नत डेटाबेस उस फ़ाइल के आधार की सामग्री के साथ बनाया गया है, और दूसरा बूट इसे छोड़ देता है क्योंकि इसका संस्करण पहले से ही रिकॉर्ड किया गया है। नामांकित फ़ाइल के लिए, उन्नत डेटाबेस को उसके पुराने नाम के तहत फ़ाइल के साथ बनाया गया है, और दूसरा बूट इसे फिर से चलाने के बजाय संगतता प्रविष्टि के माध्यम से अपनी `_omniroute_migrations` पंक्ति को स्थानांतरित करता है; गेट `--must-not-apply` के साथ नया नाम पास करता है, इसलिए यदि दूसरा बूट इसे लागू करता है तो चेक विफल हो जाता है। यदि पुल अनुरोध माइग्रेशन अपग्रेड किए गए पथ पर लागू होने में विफल रहता है, यानी, प्रत्येक बेस माइग्रेशन के बाद (चाहे वह ताजा इंस्टॉल पर भी विफल हो या नहीं), गेट `migration do PR não aplica` रिपोर्ट करता है और आपको आधार की वर्तमान स्कीमा के विरुद्ध SQL को ठीक करने के लिए कहता है; यदि फ़ाइल बाद के टाइमस्टैम्प के साथ किसी अन्य पुल अनुरोध माइग्रेशन पर निर्भर करती है, तो उसका नाम `npm run db:new-migration` के साथ पुन: उत्पन्न करें।

समान तुलना को स्थानीय रूप से चलाने के लिए, आधार को स्पष्ट रूप से पास करें, उदाहरण के लिए `npm run check:migration-numbering -- --base origin/<base-branch>`, या नवीनतम रिलीज़ के साथ तुलना करने के लिए `npm run check:migration-numbering -- --base-latest-tag` ।

### एक खुले PR के `NNN` माइग्रेशन को कनवर्ट करना

स्विच से पहले खोला गया एक पुल अनुरोध अभी भी `242_add_widgets.sql` जैसी अनुक्रमिक फ़ाइल ले जा सकता है। `241` से ऊपर के पुराने नंबर अस्वीकार कर दिए जाते हैं, इसलिए विलय से पहले इसे परिवर्तित करें:

1. **विवरण रखते हुए जनरेटर के साथ फ़ाइल का नाम बदलें।** नया नाम पाने के लिए `npm run db:new-migration -- <same description>` चलाएँ, SQL को उसमें ले जाएँ और पुरानी `NNN_` फ़ाइल को हटा दें। विवरण समान रहना चाहिए: नीचे दी गई संगतता प्रविष्टि उससे मेल खाती है।
2. **यदि कोई सतत डेटाबेस पुराना नंबर चलाता है तो एक संगतता प्रविष्टि जोड़ें।** यदि कोई डेटाबेस जो रखा गया है (होमोलॉग, एक VPS, एक योगदानकर्ता का स्वयं का इंस्टॉल) `NNN_` फ़ाइल के साथ PR का निर्माण चलाता है, तो `src/lib/db/migrationRunner/constants.ts` में `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` को `RENAMED_MIGRATION_COMPATIBILITY` में जोड़ें। यह है** `237` से `241` के लिए आवश्यक** : वे स्लॉट अब कैनोनिकल `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` और `241_seen_models.sql` रखते हैं, और प्रविष्टि के बिना ऐसा डेटाबेस हमेशा के लिए कैनोनिकल माइग्रेशन को छोड़ देता है और परिवर्तित को फिर से चलाता है। यह उस स्लॉट के लिए भी काम करता है जो खाली रहता है, जैसे कि `242`, जब गंतव्य एक टाइमस्टैम्प होता है। संदेह होने पर प्रविष्टि जोड़ें. आप इसे सरणी में कहां जोड़ते हैं, इससे कोई फर्क नहीं पड़ता: जब किसी प्रविष्टि का लक्ष्य स्लॉट अभी भी एक पंक्ति रखता है तो दूसरी प्रविष्टि दूर चली जाती है (उदाहरण के लिए `237` एक PR पंक्ति रखता है जबकि एक पुरानी `usage_history_calculated_cost` पंक्ति `237` में जाने की प्रतीक्षा करती है), धावक उस प्रविष्टि को स्लॉट मुक्त होने तक प्रतीक्षा करने देता है। केवल एक वास्तविक संघर्ष, जैसे कि एक पंक्ति द्वारा रखा गया स्लॉट जिसमें कोई प्रविष्टि नहीं चलती है, या दो प्रविष्टियाँ जो स्लॉट स्वैप करती हैं, `Cannot reconcile ...` के साथ बूट को रोकती हैं।
3. **SQL निष्क्रिय रखें** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), क्योंकि परिवर्तित माइग्रेशन एक डेटाबेस से मिल सकता है जहां इसकी स्कीमा पहले से मौजूद है।
4. **संस्करण-कुंजी वाले विशेष मामलों को स्थानांतरित करें।** यदि PR `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) या `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) में अपने पुराने नंबर के लिए कोई केस जोड़ा है, तो कुंजी को नए टाइमस्टैम्प में बदलें।

`tests/unit/db/codex-fence-migration-rename.test.ts` पुनर्नामित माइग्रेशन के लिए परीक्षण का एक कार्यशील उदाहरण है।

### स्विच से पहले शाखाओं को बैकपोर्ट

कभी भी `YYYYMMDDHHMMSS_` फ़ाइल को उस शाखा में चेरी-पिक या बैकपोर्ट न करें जो स्विच से पहले की हो (उदाहरण के लिए एक पुरानी `release/v*` शाखा)। वहां का रनर फ़ाइल नामों को टेक्स्ट के रूप में सॉर्ट करता है, इसलिए एक टाइमस्टैम्प्ड फ़ाइल एक ताज़ा डेटाबेस पर `201_` और `202_` के बीच चलेगी, और वहां पुराना गेट 14-अंकीय उपसर्गों को नहीं समझता है। ऐसी शाखा पर, परिवर्तन को उस शाखा की अपनी अगली `NNN_` फ़ाइल के रूप में लिखें, idempotent, ताकि टाइमस्टैम्प्ड संस्करण बाद में आने पर यह नो-ऑप हो।

### माइग्रेशन कैसे चलता है

स्टार्टअप पर, `migrationRunner.ts`:

1. यदि मौजूद नहीं है तो `_omniroute_migrations` तालिका बनाता है
2. पहले से लागू माइग्रेशन के लिए प्रश्न
3. प्रत्येक लेनदेन में किसी भी नए माइग्रेशन को क्रम में लागू करता है
4. प्रत्येक लागू माइग्रेशन को टाइमस्टैम्प के साथ रिकॉर्ड करता है

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### नपुंसकता

पलायन तो होना ही चाहिए** निष्क्रिय** — उन्हें दो बार चलाना नो-ऑप होना चाहिए:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, और `OR IGNORE` / `OR REPLACE` खंडों का उदारतापूर्वक उपयोग करें।

### एक नया माइग्रेशन जोड़ना

1. **जनरेटर के साथ फ़ाइल बनाएँ** : `npm run db:new-migration -- <description>` (उदाहरण के लिए `npm run db:new-migration -- add combo priority`)। यह वर्तमान UTC समय और एक टिप्पणी शीर्षलेख के साथ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` लिखता है, यदि वह टाइमस्टैम्प लिया जाता है तो एक सेकंड आगे बढ़ता है, और कभी भी किसी फ़ाइल को अधिलेखित नहीं करता है। किसी संख्या को हाथ से न चुनें.
2. **सुरक्षित DDL प्रयोग करें** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **डेटा को सावधानीपूर्वक बैकफ़िल करें** : मौजूदा पंक्तियों को संभालने के लिए `UPDATE ... WHERE ...` उपयोग करें
4. **क्रम और नामकरण की जाँच करें** : `npm run test:migrations:fresh` (खाली डेटाबेस पर सभी माइग्रेशन) और `npm run check:migration-numbering`
5. **एक प्रति पर परीक्षण करें** : उत्पादन पर कभी भी परीक्षण न किया गया माइग्रेशन न चलाएं
6. **कोड से बनाई गई तालिका को भी माइग्रेशन की आवश्यकता होती है** : यदि कोई मॉड्यूल आलस्य से तालिका बनाता है (`CREATE TABLE IF NOT EXISTS`, एक स्व-उपचार पथ के रूप में रखा जाता है), तो माइग्रेशन को इसे उसी DDL के साथ बनाना होगा। अन्यथा एक क्लीन इंस्टाल और एक अपग्रेडेड इंस्टाल अलग-अलग स्कीमा के साथ समाप्त होता है, यह इस बात पर निर्भर करता है कि वह कोड पथ चला या नहीं। `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` और `open-sse/` स्कैन करता है और माइग्रेशन (#20557) के बिना आलसी `CREATE` पर विफल रहता है। उदाहरण: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

उदाहरण:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **पश्चगामी-असंगत परिवर्तन** (उदाहरण के लिए, कॉलम गिराना) मुश्किल हैं। एक बार माइग्रेशन लागू होने के बाद, OmniRoute NOT डाउनग्रेड — का समर्थन करता है, स्कीमा परिवर्तन स्थायी होता है। तदनुसार योजना बनाएं.

## स्थिर अवस्था में एन्क्रिप्शन

संवेदनशील फ़ील्ड (API कुंजियाँ, OAuth टोकन, कनेक्शन स्ट्रिंग) **AES-256-GCM** का उपयोग करके स्थिर अवस्था में एन्क्रिप्ट किए जाते हैं।

### यह कैसे काम करता है

```ts
// src/lib/db/encryption.ts (सरलीकृत)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### इसका उपयोग कहाँ होता है

- `provider_connections.api_key` — एप्लिकेशन स्तर पर एन्क्रिप्ट किया गया
- `provider_connections.access_token`, `refresh_token`, `id_token` — एप्लिकेशन स्तर पर एन्क्रिप्ट किए गए
- `namespace = "secrets"` वाली `key_value` प्रविष्टियाँ — एप्लिकेशन स्तर पर एन्क्रिप्ट की गईं
- `proxy_registry.auth` — एप्लिकेशन स्तर पर एन्क्रिप्ट किया गया (यदि मौजूद हो)

### एन्क्रिप्शन कुंजी

एन्क्रिप्शन कुंजी एक **पासफ़्रेज़** (`STORAGE_ENCRYPTION_KEY` env var के माध्यम से सेट किया गया) और एक **सॉल्ट** (DB में संग्रहीत) से प्राप्त की जाती है। डेटा को डिक्रिप्ट करने के लिए दोनों आवश्यक हैं।

```bash
# एक सुरक्षित पासफ़्रेज़ जनरेट करें
openssl rand -hex 32

# .env में सेट करें
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **अत्यंत महत्वपूर्ण**: एन्क्रिप्शन कुंजी खोने का अर्थ है सभी एन्क्रिप्ट किए गए डेटा तक पहुँच खोना। **कुंजी का बैकअप डेटाबेस से अलग रखें**।

### क्या एन्क्रिप्ट नहीं किया जाता

प्रदर्शन संबंधी कारणों से, निम्नलिखित को प्लेनटेक्स्ट में संग्रहीत किया जाता है:

- प्रोवाइडर के प्रदर्शन नाम
- मॉडल परिभाषाएँ (पहले से सार्वजनिक)
- रूटिंग नियम
- उपयोग रिकॉर्ड (कोई PII नहीं)

---

## एन्क्रिप्शन संबंधी सावधानियाँ (v3.8.16+)

OmniRoute दो एन्क्रिप्शन योजनाओं को पारदर्शी रूप से संभालने के लिए **`migrateLegacyEncryptedString()`** का उपयोग करता है:

- **लीगेसी** (v3.5.0 से पहले): XOR-आधारित "एन्क्रिप्शन" (वास्तविक क्रिप्टोग्राफ़ी नहीं)
- **वर्तमान**: उचित IV और प्रमाणीकरण टैग के साथ AES-256-GCM

माइग्रेशन सहायक लीगेसी प्रारूप का पता लगाता है और पहली बार पढ़े जाने पर नई योजना के साथ पुनः एन्क्रिप्ट करता है। इसका अर्थ है कि आप क्रेडेंशियल खोए बिना किसी पुराने डेटाबेस को अपग्रेड कर सकते हैं।

## रीड कैश

बार-बार पढ़े जाने वाले डेटा (मॉडल, प्रोवाइडर, सेटिंग्स) के लिए, `readCache.ts` एक **इन-मेमोरी कैश** प्रदान करता है:

```ts
// स्टार्टअप पर कैश किया जाता है, लिखने पर अमान्य किया जाता है
const providers = await getCachedProviders(); // तेज़, इन-मेमोरी
const fresh = await listProviders(); // धीमा, DB को एक्सेस करता है
```

| कैश की गई इकाई         | कैश कुंजी      | TTL          |
| ---------------------- | -------------- | ------------ |
| `models`               | `models:v1`    | लिखे जाने तक |
| `provider_connections` | `providers:v1` | लिखे जाने तक |
| `settings`             | `settings:v1`  | लिखे जाने तक |
| `combos`               | `combos:v1`    | लिखे जाने तक |

संबंधित तालिका में प्रत्येक लेखन पर कैश अमान्य कर दिया जाता है।

## बैकअप और रिकवरी

### मैन्युअल बैकअप

```bash
# स्थानीय बैकअप बनाने के लिए CLI का उपयोग करें
omniroute backup create --name pre-migration

# या API के माध्यम से
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

बैकअप फ़ाइल में ये शामिल होते हैं:

- सभी DB तालिकाएँ (JSON में क्रमबद्ध)
- कॉल लॉग आर्टिफ़ैक्ट (base64-एन्कोडेड, वैकल्पिक)
- सेटिंग्स + सीक्रेट्स (एन्क्रिप्टेड)
- प्लगइन कॉन्फ़िगरेशन

### पुनर्स्थापना

```bash
# CLI के माध्यम से
omniroute restore pre-migration

# API के माध्यम से
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **चेतावनी**: पुनर्स्थापना संपूर्ण DB को ओवरराइट कर देती है। पहले सभी क्लाइंट बंद करें।

### स्वचालित बैकअप

```bash
# CLI के माध्यम से स्वचालित दैनिक बैकअप सक्षम करें
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

शेड्यूल को सर्वर की ओर से एक बैकग्राउंड जॉब द्वारा निष्पादित किया जाता है, जो प्रत्येक 30 सेकंड
(डिफ़ॉल्ट) में सक्रिय होता है और स्थानीय सर्वर समय के अनुसार cron एक्सप्रेशन का मूल्यांकन करता है।

| वेरिएबल                                     | डिफ़ॉल्ट | विवरण                                                                                                                                 |
| ------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`  | ms में सक्रियण अंतराल (न्यूनतम `5000`)। मेल खाने वाले cron मिनट के भीतर विश्वसनीय रूप से सक्रिय होने के लिए यह 60 s से कम होना चाहिए। |

### SQLite हॉट बैकअप

लाइव DB का शून्य-डाउनटाइम बैकअप लेने के लिए:

```bash

```

यह SQLite के ऑनलाइन बैकअप API का उपयोग करता है — OmniRoute के चलते समय इसे चलाना सुरक्षित है।

## प्रदर्शन ट्यूनिंग

### WAL मोड

WAL डिफ़ॉल्ट रूप से सक्षम है। उच्च लेखन कार्यभार के लिए, इस पर विचार करें:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` सेट नहीं करता है। एक चेकपॉइंट WAL फ़्रेम को मुख्य फ़ाइल में ले जाता है, लेकिन WAL फ़ाइल अपना सबसे बड़ा आवंटित आकार बनाए रखती है। `OMNIROUTE_WAL_GUARD_MAX_MB` गार्ड केवल चेतावनी देता है और `wal_checkpoint(RESTART)` चलाता है; यह डिस्क-आकार की टोपी नहीं है.

### इंडेक्स

प्रदर्शन के लिए मुख्य सूचकांक (माइग्रेशन द्वारा स्वतः निर्मित):

- प्रदाता द्वारा`idx_models_provider` — मॉडल लुकअप
- `idx_combo_targets_combo_id` — कॉम्बो लक्ष्य विस्तार
- `idx_usage_history_api_key_timestamp` — उपयोग विश्लेषण
- `idx_quota_snapshots_api_key_window` — कोटा ट्रैकिंग
- `idx_call_logs_timestamp` — कॉल लॉग क्वेरीज़

नया इंडेक्स जोड़ने के लिए, माइग्रेशन बनाएं:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### मेमोरी-मैप्ड I/O

बहुत बड़े डेटाबेस (> 10GB) के लिए, मेमोरी मैपिंग को SQLite pragma के माध्यम से समायोजित किया जा सकता है:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### संघनन

लंबे समय तक चलने वाले OmniRoute उदाहरणों को कभी-कभार `VACUUM` से लाभ होता है:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

कम ट्रैफ़िक वाली विंडो के दौरान मासिक चलाएँ। (WAL मोड आवश्यकता को कम करता है, लेकिन समाप्त नहीं करता है।)

## स्वास्थ्य जाँच

`src/lib/db/healthCheck.ts` **DB-स्तरीय स्वास्थ्य निदान** प्रदान करता है:

दोनों वर्ब के लिए प्रमाणीकरण आवश्यक है (अन्यथा `401`)। `GET` केवल निदान करता है; `POST`
`autoRepair` सक्षम करके वही जाँच चलाता है।

```bash
GET  /api/db/health   # निदान
POST /api/db/health   # निदान + मरम्मत
```

प्रतिक्रिया में `runDbHealthCheck()` द्वारा उत्पन्न `DbHealthCheckResult` होता है
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "डोमेन बजट ने ऐसी API कुंजियों को संदर्भित किया जो अब मौजूद नहीं हैं।",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| फ़ील्ड            | अर्थ                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | जब `issues` खाली हो, तब `true`। `driver` इसे कभी प्रभावित नहीं करता।                                                                      |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` में से एक।                                                |
| `repairedCount`   | इस रन के दौरान मरम्मत की गई पंक्तियाँ; `autoRepair` के false होने पर हमेशा `0`।                                                           |
| `backupCreated`   | मरम्मत से पहले बैकअप लिया गया था या नहीं।                                                                                                 |
| `checkedAt`       | रन और उसके द्वारा लिखे गए किसी भी मरम्मत नोट द्वारा साझा किया गया ISO टाइमस्टैम्प।                                                        |
| `driver.name`     | जाँचे गए डेटाबेस को सेवा प्रदान करने वाला SQLite ड्राइवर।                                                                                 |
| `driver.degraded` | जब लेखन डेटाबेस फ़ाइल द्वारा टिकाऊ रूप से समर्थित न हो, तब `true` — `sql.js` WASM फ़ॉलबैक (संपूर्ण-फ़ाइल स्थायित्व) या इन-मेमोरी डेटाबेस। |

यही पेलोड `omniroute_db_health_check` MCP टूल द्वारा लौटाया जाता है।

करप्शन का पता लगाने के लिए `PRAGMA integrity_check` चलाएँ:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# यह प्रिंट होना चाहिए: ok
```

यदि यह `ok` के अलावा कुछ और लौटाता है, तो **डेटाबेस का उपयोग तुरंत बंद कर दें** और बैकअप से पुनर्स्थापित करें।

## आपदा पुनर्प्राप्ति

### परिदृश्य 1: WAL फ़ाइल खो गई

`-wal` फ़ाइल अनुपलब्ध है, लेकिन `-shm` और मुख्य DB सुरक्षित हैं:

```bash
# अगली बार खोलने पर स्वचालित रूप से पुनर्प्राप्त हो जाता है
omniroute
```

यदि SQLite स्वतः पुनर्प्राप्त नहीं कर सकता:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### परिदृश्य 2: मुख्य DB फ़ाइल दूषित हो गई

बैकअप से पुनर्स्थापित करें:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` केवल चल रहे सर्वर से एक पूर्ण `.tar.gz` संग्रह डाउनलोड करता है
(`GET /api/db-backups/exportAll`, ऑपरेटर क्रेडेंशियल आवश्यक); यह कुछ भी पुनर्स्थापित नहीं करता।

### परिदृश्य 3: एन्क्रिप्शन कुंजी खो गई

कुंजी के बिना **पुनर्प्राप्ति संभव नहीं है**। एन्क्रिप्ट किए गए फ़ील्ड पढ़े नहीं जा सकते। नए क्रेडेंशियल के साथ सभी प्रदाताओं को मैन्युअल रूप से दोबारा जोड़ें।

> **जोखिम न्यूनीकरण**: एन्क्रिप्शन कुंजी का हमेशा अलग से बैकअप लें, आदर्श रूप से किसी पासवर्ड मैनेजर या KMS में।

### परिदृश्य 4: डिस्क भर गई

SQLite `SQLITE_FULL` त्रुटियाँ लौटाएगा। डिस्क में स्थान खाली करें, फिर:

```bash
# स्थान खाली करने के लिए WAL को चेकपॉइंट करें
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### सभी तालिकाओं में पंक्तियाँ गिनें

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### सभी डेटा को रीसेट (मिटाएँ) करें

```bash
# पहले OmniRoute को रोकें
omniroute stop

# DB फ़ाइल हटाएँ
rm ~/.omniroute/storage.sqlite*

# पुनः शुरू करें (खाली DB दोबारा बनाया जाएगा)
omniroute
```

**चयनात्मक** रीसेट के लिए (प्रदाताओं को रखें, उपयोग डेटा मिटाएँ):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### एकल तालिका निर्यात करें

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## समस्या निवारण

### "डेटाबेस लॉक है"

कोई अन्य प्रोसेस राइट लॉक बनाए हुए है। इनमें से कोई एक उपाय करें:

- दूसरे प्रोसेस के पूरा होने की प्रतीक्षा करें (`lsof | grep storage.sqlite` से जाँचें)
- दूसरे प्रोसेस को बंद करें
- यदि समस्या बनी रहती है, तो OmniRoute को पुनः शुरू करें

### "फ़ॉरेन-की बाधा विफल हुई"

कोई डोमेन मॉड्यूल रेफ़रेंशियल इंटेग्रिटी का उल्लंघन कर रहा है। इनकी जाँच करें:

- आश्रित तालिकाओं में अनाथ पंक्तियाँ
- कैस्केडिंग डिलीट जो आगे प्रसारित नहीं हुए
- हालिया माइग्रेशन जिसने किसी फ़ॉरेन-की को बदला है

उल्लंघनों का पता लगाने के लिए `PRAGMA foreign_key_check;` चलाएँ।

### "मेमोरी समाप्त हो गई"

SQLite का मेमोरी-मैप्ड I/O, OS की सीमा से अधिक हो रहा है। SQLite pragma के माध्यम से इसे कम करें:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB के बजाय 128MB
```

या इसे अक्षम करें:

```sql
PRAGMA mmap_size = 0;
```

### "माइग्रेशन बीच में विफल हो गया"

माइग्रेशन एक ट्रांज़ैक्शन में चला था, इसलिए इसे रोल बैक हो जाना चाहिए था। यदि ऐसा नहीं हुआ:

1. **OmniRoute को रोकें** (आगे के प्रयासों को रोकें)
2. `sqlite3` से **DB की स्थिति जाँचें**
3. आंशिक माइग्रेशन को **मैन्युअल रूप से ठीक करें**
4. OmniRoute को **दोबारा चलाएँ** (माइग्रेशन का पुनः प्रयास किया जाएगा)

इसे रोकने के लिए, माइग्रेशन का परीक्षण हमेशा पहले एक प्रतिलिपि पर करें।
