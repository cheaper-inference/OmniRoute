## शून्य-कॉन्फ़िगर ऑटो-रूटिंग (`auto/` उपसर्ग)

किसी कॉम्बो निर्माण की आवश्यकता नहीं है. सीधे अपने क्लाइंट में `auto` या `auto/` वैरिएंट का उपयोग करें।

### त्वरित उदाहरण

| मॉडल ID             | व्यवहार                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`              | योग्य प्रदाता मॉडल, LKGP रणनीति और संतुलित वजन                                                                                                |
| `auto/coding`       | कोडिंग कार्यों के लिए गुणवत्ता-प्रथम भार                                                                                                      |
| `auto/fast`         | कम विलंबता और स्वस्थ प्रदाताओं का पक्ष लेता है                                                                                                |
| `auto/cheap`        | लागत-बचत भार: कम कैटलॉग कीमतों का समर्थन करता है; LKGP चिपचिपाहट रखता है, सख्त सबसे सस्ता-पहला प्रकार नहीं                                    |
| `auto/subscription` | केवल योजना में शामिल कोटा, लाइव सत्यापित; एक खाली पूल HTTP 503 लौटाता है, कभी भी बिल वापस नहीं किया जाता                                      |
| `auto/thrifty`      | सदस्यता → बिना चाबी → मुफ़्त → सस्ता → प्रीमियम, एक समय में एक पायदान; बिल कर सकते हैं                                                        |
| `auto/offline`      | कोटा उपलब्धता और प्रदाता स्वास्थ्य (`offline-friendly` पैक) के पक्ष में; ऑफ़लाइन अनुमान नहीं — अनुरोध अभी भी दूरस्थ प्रदाताओं के पास जाते हैं |
| `auto/smart`        | 10% अन्वेषण दर के साथ गुणवत्ता-प्रथम भार                                                                                                      |
| `auto/lkgp`         | स्पष्ट LKGP, डिफ़ॉल्ट `auto` के समान भार के साथ                                                                                               |
| `auto/chaos`        | प्रति प्रदाता एक मॉडल वाला समानांतर पैनल, डिफ़ॉल्ट रूप से अधिकतम पांच, एक उत्तर लौटाता है                                                     |

वज़न वैरिएंट LKGP चिपचिपाहट बनाए रखता है, इसलिए `fast` और `cheap` प्रत्येक अनुरोध पर न्यूनतम विलंबता या कीमत की गारंटी देने के बजाय प्राथमिकताएँ व्यक्त करते हैं। `auto/chaos` एकाधिक अपस्ट्रीम कॉल करता है। `auto/thrifty` भुगतान क्षमता का उपयोग कर सकता है; योजना कोटा पर लौटना नवीनीकृत पात्रता और कनेक्शन कूलडाउन पर निर्भर करता है, न कि केवल रीसेट समय पर। [सदस्यता-प्रथम रूटिंग](./SUBSCRIPTION_LADDER.md) देखें.

### श्रेणी × टियर संरचना (`auto/<category>:<tier>`)

ओपनराउटर-शैली प्रत्यय अलग** किस प्रकार का मार्ग** (श्रेणी) से** इसे कैसे अनुकूलित करें** (स्तर), ताकि आप उन्हें स्वतंत्र रूप से बना सकें (#4235 चरण बी, `open-sse/services/autoCombo/suffixComposition.ts`):

- **श्रेणियाँ** : `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` दृष्टि-सक्षम मॉडल रखें; `reasoning` reasoning/thinking मॉडल रखता है। `coding` और `chat` कोई क्षमता फ़िल्टर नहीं जोड़ते हैं। गैर-चैट श्रेणियां किसी भी स्तर को ओवरराइड करने से पहले गुणवत्ता-प्रथम भार का चयन करती हैं।
- **स्तरों** (स्कोरिंग वेट / पूल फ़िल्टर चुनें): `fast` (शिप-फास्ट) · `cheap` (उर्फ `floor`, लागत-बचतकर्ता) · `reliable` (सर्किट-ब्रेकर स्वास्थ्य + विलंबता स्थिरता) · `free` / `pro` ( `classifyTier` — फ्री-टियर बनाम प्रीमियम के माध्यम से मॉडल टियर द्वारा पूल को फ़िल्टर करें)। `subscription` और `thrifty` कनेक्शन-आधारित [सदस्यता सीढ़ी](./SUBSCRIPTION_LADDER.md) लागू करते हैं।

| उदाहरण                 | का संकल्प करता है                                  |
| ---------------------- | -------------------------------------------------- |
| `auto/coding:fast`     | पात्र पूल, कम-विलंबता भार                          |
| `auto/coding:cheap`    | पात्र पूल, लागत-बचत भार (उर्फ `auto/coding:floor`) |
| `auto/reasoning:pro`   | केवल reasoning/thinking मॉडल, प्रीमियम स्तर        |
| `auto/vision`          | गुणवत्ता-प्रथम भार के साथ दृष्टि-सक्षम मॉडल        |
| `auto/multimodal:free` | मल्टीमॉडल-सक्षम मॉडल, केवल निःशुल्क स्तर           |

कोई भी वैध `auto/<category>[:<tier>]` मांग पर समाधान करता है; एक क्यूरेटेड सबसेट `/v1/models` और डैशबोर्ड (`AUTO_SUFFIX_VARIANTS` in `open-sse/services/autoCombo/builtinCatalog.ts`) में विज्ञापित किया गया है। Category/tier फ़िल्टरिंग है** डिफ़ॉल्ट रूप से विफल-बंद** : यदि कोई योग्य मॉडल मेल नहीं खाता है, तो वर्चुअल कॉम्बो में एक खाली पूल होता है और चैट रिज़ॉल्वर HTTP 503 (`src/sse/handlers/chatHelpers.ts`) लौटाता है। फ़िल्टर `open-sse/services/autoCombo/virtualFactory.ts` में `narrowPoolByCategoryTier` है।

जब फ़िल्टर कुछ भी मेल नहीं खाता तो`OMNIROUTE_AUTO_FREE_FALLBACK_TO_FULL_POOL=true` पुराने category/tier फ़ॉलबैक को पूर्ण पूल में पुनर्स्थापित करता है; यह अनुरोधित स्तर या क्षमता बाधा को दूर कर सकता है। मॉडल-फ़ैमिली फ़िल्टर कभी भी उस फ़ॉलबैक का उपयोग नहीं करते हैं, और केवल-सदस्यता रूटिंग के लिए अभी भी सत्यापित योजना-शामिल क्षमता की आवश्यकता होती है।

> **लाइव मॉडल इंटेलिजेंस:** ऑटो-रूटिंग फिटनेस की जानकारी लाइव द्वारा दी जाती है** अखाड़ा ELO** रैंकिंग +** मॉडल.देव** जब `ARENA_ELO_SYNC_ENABLED` फ़्लैग चालू होता है तो टियर डेटा (अन्यथा स्थिर फ़िटनेस मानचित्र पर वापस आ जाता है)।

**का उपयोग कैसे करें:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # favor coding task fit
model: "auto/fast"            # favor lower latency
model: "auto/cheap"           # favor lower catalog cost
```

**क्या होता है:**

1. OmniRoute `src/sse/handlers/chat.ts` में `auto/` उपसर्ग का पता लगाता है
2. सभी से पूछताछ** सक्रिय प्रदाता कनेक्शन** डेटाबेस से
3. क्रेडेंशियल, मॉडल-दृश्यता और पात्रता फ़िल्टर लागू करता है
4. उपलब्ध मॉडलों से तार्किक provider/model उम्मीदवारों का निर्माण करता है, प्रेषण के लिए योग्य खाता अनुमति सूची रखता है
5. एक बनाता है** आभासी कॉम्बो** इन-मेमोरी ( DB में संग्रहीत नहीं)
6. चयनित वैरिएंट की वज़न प्रोफ़ाइल + LKGP रणनीति का उपयोग करते हुए रूट

**प्रमुख गुण:**

- ✅** हमेशा बने रहें:** कोई टॉगल नहीं, कोई कॉम्बो निर्माण नहीं, कोई कॉन्फ़िगरेशन की आवश्यकता नहीं है
- ✅** गतिशील:** वर्तमान कनेक्टेड प्रदाताओं को स्वचालित रूप से दर्शाता है
- ✅** सत्र चिपचिपाहट:** LKGP सुनिश्चित करता है कि अंतिम सफल प्रदाता को प्राथमिकता दी जाए
- ✅** बहु-खाता जागरूक:** तार्किक provider/model उम्मीदवार पात्र खाता अनुमति सूची बनाए रखते हैं
- ✅** किसी सहेजे गए कॉम्बो की आवश्यकता नहीं है:** वर्चुअल कॉन्फ़िगरेशन मेमोरी में रहता है; सामान्य रूटिंग मेट्रिक्स और रनटाइम स्थिति अभी भी बनी रह सकती है

### प्रति-कुंजी उम्मीदवार नियंत्रण (#7819, स्तर 1 + 2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` के बाद प्रत्यय, या बेस चैनल के लिए शाब्दिक `auto` ) एक है** केवल पढ़ने के लिए** एंडपॉइंट जो एक `auto/*` चैनल के वर्तमान उम्मीदवार पूल को लाइव रीचैबिलिटी से सजाता है, मौजूदा लचीलेपन का पुन: उपयोग करता है पढ़ता है (कभी भी कच्चा ब्रेकर `state`):

- प्रदाता सर्किट ब्रेकर — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- हल की गई `provider_connections` पंक्ति पर कनेक्शन कूलडाउन — `rateLimitedUntil` / `testStatus`
- मॉडल लॉकआउट — `isModelLocked(provider, connectionId, model)`

प्रत्येक उम्मीदवार इस API कुंजी का `excluded` ध्वज भी रखता है। `apiKeyId` प्रति-एपीआई — कुंजी (`auto_candidate_overrides` तालिका,`open-sse/services/autoCombo/candidateOverrides.ts` `128`) — संग्रहीत `users` `filterExcludedCandidates()` `open-sse/services/autoCombo/virtualFactory.ts` OmniRoute फ़िल्टर है** फेल-खुला** : एक अनसेट apiKeyId/channel या एक DB लुकअप विफलता दोनों पूल को अनफ़िल्टर्ड छोड़ देती है, इसलिए बिना ओवरराइड कॉन्फ़िगर वाला ऑपरेटर इस सुविधा से पहले रूटिंग बाइट-समान देखता है।

**अनुवर्ती मुद्दे के लिए टाल दिया गया:** प्रति-उम्मीदवार भार + स्पष्ट क्रम (स्तर 3 — मौजूदा weighted/priority रणनीति पथों में फ़ीड) और प्रति `auto/*` चैनल (स्तर 4) के लिए एक विशिष्ट `combo.ts` रणनीति पिन करना। इस खुले प्रश्न के लिए #7819 योजना देखें कि क्या ओवरराइड्स को प्रति-एपीआई-कुंजी रहना चाहिए या एकल-किरायेदार मॉडल को देखते हुए वैश्विक हो जाना चाहिए।

**पर्दे के पीछे:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

## सहेजे गए ऑटो कॉम्बो के लिए खाता प्राथमिकताएँ

इंटेलिजेंट ऑटो संपादक एक वैकल्पिक प्रदान करता है** खाता प्राथमिकताएँ** अनुभाग। प्रत्येक कनेक्शन पसंदीदा, सामान्य (डिफ़ॉल्ट), आरक्षित या बहिष्कृत हो सकता है। एकाधिक कनेक्शन एक स्तर साझा कर सकते हैं। पहले पात्र स्तर के भीतर स्वत: चयन करता है, वहां उसका scoring/router व्यवहार बरकरार रहता है; असफल प्रयास शेष ठोस खातों में चले जाते हैं, जिन्हें रिजर्व से पहले सामान्य से पहले प्राथमिकता दी जाती है। इस कॉम्बो द्वारा बहिष्कृत कनेक्शन का उपयोग कभी नहीं किया जाता है।

सेटिंग को `config.accountPreferences` के रूप में संग्रहीत किया जाता है, कनेक्शन ID द्वारा कुंजीबद्ध किया जाता है:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

छोड़ा गया या खाली नक्शा मौजूदा रूटिंग को बरकरार रखता है। प्राथमिकताएँ अक्षम कनेक्शनों को सक्षम नहीं करती हैं, एपीआई-कुंजी पहुंच प्रदान नहीं करती हैं, कोटा-अवरुद्ध उम्मीदवारों को पुनर्स्थापित नहीं करती हैं, या बजट जांच को बायपास नहीं करती हैं। प्रत्येक प्रयास उसके ठोस कनेक्शन तक ही सीमित है, इसलिए खाता फ़ॉलबैक कॉम्बो राउटर के पीछे के स्तर में नहीं जा सकता। मौजूदा सत्र एफ़िनिटी एक योग्य खाता बनाए रख सकती है; मूल टर्न से बंधे खाते को बाहर करने से खाते चुपचाप बदलने के बजाय वह टर्न रुक जाता है।

कॉन्फ़िगर की गई प्राथमिकताएं खाता-जागरूक ऑटो पथ का उपयोग करती हैं: अनबाउंड संदर्भ-कैश, स्मार्ट-पाइपलाइन, अराजकता और छाया शॉर्टकट प्रेषित नहीं किए जाते हैं। इन अनुरोधों के लिए सट्टा हेजिंग अक्षम है इसलिए आरक्षित खाते पसंदीदा खातों की दौड़ में शामिल नहीं हो सकते हैं। अन्य कॉम्बो रणनीतियाँ इस सेटिंग की व्याख्या नहीं करती हैं। कॉम्बो को ऑटो से दूर बदलने से बाद में स्विच करने के लिए सहेजी गई प्राथमिकताएँ वापस रहती हैं।

## कॉम्बो नाम जो वास्तविक मॉडल आईडी से मेल खाते हैं

एक कॉम्बो जिसका `name` एक नंगे मॉडल आईडी के समान है (उदाहरण के लिए `gpt-5.5` नामक कॉम्बो) एक है** जानबूझकर, समर्थित पैटर्न** , कोई बग नहीं: यह [#6940](https://github.com/cheaper-inference/OmniRoute/issues/6940) में प्रलेखित प्रति-मॉडल-आईडी प्रदाता फ़ॉलबैक के लिए तंत्र है। क्योंकि कॉम्बो रिज़ॉल्यूशन को बेअर-मॉडल-आईडी रिज़ॉल्यूशन (`getComboForModel()` in `src/sse/services/model.ts`) से पहले जांचा जाता है, बेअर आईडी `gpt-5.5` के लिए एक अनुरोध सीधे एकल प्रदाता — के बजाय कॉम्बो के लक्ष्यों (उदाहरण के लिए `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) के माध्यम से भेजा जाता है, यह [#3227/#3233](https://github.com/cheaper-inference/OmniRoute/issues/3227) के लिए निर्मित कॉम्बो-बिफोर-रीराइट प्राथमिकता का पुन: उपयोग करता है और `tests/unit/responses-combo-resolution-3227.test.ts` और `tests/unit/combo-name-codex-responses-rewrite.test.ts` द्वारा प्रतिगमन-परीक्षण किया जाता है। .

किसी ऐसे नाम के लिए कॉम्बो बनाना या उसका नाम बदलना जो वास्तविक मॉडल आईडी को छाया देता है** कभी अस्वीकार नहीं किया** — ऐसा करने से यह दस्तावेज़ीकृत वर्कफ़्लो टूट जाएगा। इसके बजाय (#8530), `POST /api/combos` और `PUT /api/combos/[id]` प्रतिक्रिया के लिए एक गैर-अवरुद्ध `warning` फ़ील्ड संलग्न करते हैं जब (नया) नाम वास्तविक मॉडल आईडी से टकराता है:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

बूट पर, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) प्रत्येक मौजूदा कॉम्बो की गणना करते हुए एक-पंक्ति `[STARTUP]` चेतावनी भी लॉग करता है जो एक मॉडल आईडी को छाया देता है, इसलिए जो ऑपरेटर इसे दुर्घटनावश मारते हैं (जानबूझकर, प्रति #6940 के बजाय) उनके पास एक संकेत होता है। डिटेक्शन हेल्पर `src/lib/combos/modelNameCollision.ts` में रहता है।

## किसी क्लाइंट से कस्टम कॉम्बो कॉल करना

लगातार कॉम्बो (सेटिंग्स → कॉम्बो) का उपयोग केवल तब किया जाता है जब क्लाइंट कॉम्बो भेजता है** सटीक नाम** `model` फ़ील्ड — में कॉम्बो नाम का कोई अस्पष्ट या आंशिक मिलान नहीं है, और कोई `auto/` उपसर्ग शामिल नहीं है। संकल्प क्रम (`getComboForModel()` in `src/sse/services/model.ts`):

1. सटीक कॉम्बो-नाम मिलान (`model: "my-combo"`),
2. `combo/<name>` उपसर्ग (`model: "combo/my-combo"`),
3. मॉडल → कॉम्बो ग्लोब मैपिंग (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

दो सामान्य नुकसान:

- **`auto` आपके कॉम्बो का उपयोग नहीं करता है.** `auto`/`auto/*` अपना स्वयं का शून्य-कॉन्फिग उम्मीदवार पूल बनाता है और केवल तभी कायम कॉम्बो से परामर्श करता है यदि कॉम्बो का शाब्दिक नाम `auto` है (अनुशंसित नहीं)। किसी कॉम्बो के माध्यम से रूट करने के लिए, उसका सटीक नाम — भेजें न कि `auto`।
- **`openrouter/auto` एक वास्तविक भुगतान वाला OpenRouter उत्पाद है** ("ऑटो बेस्ट अवेलेबल"), कोई OmniRoute उपनाम नहीं। यह OpenRouter रजिस्ट्री (`open-sse/config/providers/registry/openrouter/index.ts`) की एकल स्थिर मॉडल प्रविष्टि है और इसे अलग से बिल किया जाता है। इसे `auto` पूल से बाहर करने के लिए सेटिंग्स → रूटिंग → छिपाएँ भुगतान मॉडल का उपयोग करें।

इस दस्तावेज़ में मूल भ्रम के लिए [#7992](https://github.com/cheaper-inference/OmniRoute/issues/7992) और [#7111](https://github.com/cheaper-inference/OmniRoute/issues/7111) देखें।

## यह कैसे काम करता है (पर्सिस्टेड ऑटो-कॉम्बोज़)

ऑटो-कॉम्बो इंजन गतिशील रूप से provider/model उम्मीदवारों का उपयोग करके स्कोर करता है** 16 घोषित कारक** ( `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` में परिभाषित)। डिफ़ॉल्ट वज़न का योग `1.0` है; कस्टम वज़न को `normalizeScoringWeights()` द्वारा पुनः सामान्यीकृत किया जाता है। तीन कारकों का वजन डिफ़ॉल्ट रूप से शून्य होता है: `cacheAffinity`, `resetWindowAffinity` और `reliability`। मोड पैक `reliability` `0.03` का भार देते हैं, या `reliability-first` में `0.04` ; `quality` डिफ़ॉल्ट रूप से `quality-first` में `0.03` रखता है, और अन्य पैक में `0.02` है। `cacheAffinity` भारित स्कोर के बाहर प्रॉम्प्ट-कैश डिडुप्लीकेशन भी गेट करता है।

इन-मेमोरी `quality` ट्रैकर (`open-sse/services/routing/quality.ts`) कोल्ड रीस्टार्ट के बाद खाली है, इसलिए प्रत्येक उम्मीदवार पहला अवलोकन आने तक एक तटस्थ `0.5` स्कोर करता है।

> **अपठनीय कोटा (#15347)।** जब एक प्रदाता के पास एक कोटा फ़ेचर होता है, लेकिन यह पढ़ने योग्य कुछ भी नहीं देता है (असफल फ़ेच, गायब क्रेडेंशियल, संदेश-केवल उपयोग, या एक विकृत स्नैपशॉट जिसमें कोई पार्स करने योग्य `windows` नहीं है और `percentUsed: null` सहित कोई परिमित `percentUsed` नहीं है), उम्मीदवार `quota` अक्ष पर `0` स्कोर करता है और उसका अंतिम स्कोर `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`) से गुणा किया जाता है, वही सॉफ्ट-पेनल्टी पैटर्न कनेक्शन-स्थिति दंड के रूप में। एक असफल उपयोग रीड टेलीमेट्री के बारे में सबूत है, प्रदाता के बारे में नहीं, इसलिए यह किसी भी वास्तविक रीडिंग से सख्ती से नीचे है, जिसमें 100%-used पुष्टि भी शामिल है, लेकिन इसे कभी भी हार्ड-ब्लॉक या बेदखल नहीं किया जाता है। बिना किसी सीमा वाला प्रदाता `unlimited: true` रिपोर्ट करता है और पूर्ण कोटा के रूप में स्कोर करता है; बिना पंजीकृत कोटा फ़ेचर वाले प्रदाता के पास कोई टेलीमेट्री स्रोत नहीं होता है और वह `100` का डिफ़ॉल्ट रखता है।

**जोड़:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` जैसा कि `DEFAULT_WEIGHTS` में घोषित किया गया है; उपयोगकर्ता-कॉन्फ़िगर किए गए वज़न को स्कोरिंग से पहले `normalizeScoringWeights()` द्वारा वितरण में पुनः सामान्यीकृत किया जाता है।

### प्रति-अनुरोध नियंत्रण (हेडर) — #6023 / #6024 / #6025 / #3470

किसी `auto` कॉम्बो की संग्रहीत कॉन्फ़िगरेशन को बदले बिना, तीन हेडर के माध्यम से उसे **प्रति अनुरोध** निर्देशित किया जा सकता है। ये केवल `auto` रणनीति और केवल उन्हें भेजने वाले अनुरोध पर लागू होते हैं; हेडर अनुपस्थित होने पर कॉम्बो के सहेजे गए `modePack`/`budgetCap`/`budgetFallback` का उपयोग किया जाता है।

| हेडर                          | स्वीकार्य मान                                                                                                                                                                              | प्रभाव                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| :---------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-Mode`            | कोई प्रीसेट उपनाम (`fast`, `balanced`, `quality`, `cheap`, `reliable`, `offline`) या कोई मूल पैक नाम (`ship-fast`, `cost-saver`, `quality-first`, `offline-friendly`, `reliability-first`) | इस अनुरोध के लिए स्कोरिंग भारों को ओवरराइड करता है। `balanced`/`default` डिफ़ॉल्ट भार लागू करते हैं (कोई पैक नहीं)। अज्ञात मानों को अनदेखा किया जाता है (कॉन्फ़िगरेशन संरक्षित रहता है)।                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

```bash

  -H "X-OmniRoute-Mode: fast" \
  -H "X-OmniRoute-Budget: 0.05" \
  -H "X-OmniRoute-Budget-Fallback: strict" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

निर्धारण एक शुद्ध फ़ंक्शन (`open-sse/services/autoCombo/requestControls.ts`) है;
निर्धारित मान इंजन के मौजूदा `config.modePack` / `config.budgetCap` /
`config.budgetFallback` इनपुट में जाते हैं। किसी कॉम्बो का संग्रहीत `config.budgetFallback` ("strict" |
"cheapest") स्थायी नीति निर्धारित करता है; हेडर इसे एकल अनुरोध के लिए ओवरराइड करता है।

| `jev`               | उपयोगकर्ता-रैंक वाली वरीयता सूची; TypeSafe Jev स्वीकार करता है कि इस अनुरोध के लिए कौन सी प्रविष्टियाँ चलती हैं। विजेता पहले, अन्य स्वीकृत लक्ष्य आपका आदेश बनाए रखें। ऑप्ट-इन और भुगतान: केवल तब कॉल किया जाता है जब `COMBO_JEV_STRATEGY_ENABLED` चालू होता है (डिफ़ॉल्ट बंद); प्रत्येक कॉल api.typesafe.ai पर एक सीमित अंश भेजती है। अनुपलब्ध होने पर आपके ऑर्डर पर वापस आ जाता है (#15276) |

⭐ = v3.8.0 में नया · 🧬 = v3.8.36 में नया

`jev` रणनीति सशुल्क TypeSafe कॉल तभी करती है जब `COMBO_JEV_STRATEGY_ENABLED` सक्षम होता है। अकेले संग्रहीत TypeSafe कुंजी इसे सक्षम नहीं करती है। फ़्लैग ऑफ़ के साथ, कॉम्बो उस कॉल (`open-sse/services/combo/jevAsk.ts`) को किए बिना ऑपरेटर के ऑर्डर को बनाए रखता है।

### `weighted` शब्दार्थ

`weighted` एक है** प्रति अनुरोध आनुपातिक यादृच्छिक ड्रा** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), एक तुल्यकारक नहीं:

- प्रत्येक अनुरोध खींचता है** एक** संभाव्यता `weight / totalWeight` के साथ कदम; शेष चरणों को उस अनुरोध के लिए फ़ॉलबैक श्रृंखला के रूप में घटते वजन के आधार पर क्रमबद्ध किया जाता है।
- एक कदम जिसका वजन `0` (या गायब) है** कभी नहीं खींचा गया** जबकि किसी भी अन्य चरण का भार > 0 — होता है, यह केवल खींचे गए चरण के विफल होने के बाद फ़ॉलबैक के रूप में कार्य कर सकता है। केवल जब** सभी** वज़न 0 है क्या चयन एक समान हो जाता है?
- वे चरण जिनके लक्ष्य सभी अनुपलब्ध — प्रदाता सर्किट ब्रेकर `OPEN`, कनेक्शन कूलडाउन, मॉडल लॉकआउट — हैं, ऐसा होने से पहले ड्रा से हटा दिए जाते हैं (`open-sse/services/combo/targetResolution.ts`), इसलिए एक स्वस्थ कदम अस्थायी रूप से हर अनुरोध को जीत सकता है।
- `stickyWeightedLimit` (कॉम्बो कॉन्फ़िगरेशन, डिफ़ॉल्ट `1` = बंद) पुन: ड्राइंग से पहले लगातार कई सफलताओं के लिए खींचे गए चरण को पिन करता है।

सख्त रोटेशन के लिए `round-robin` उपयोग करें; `weighted` पर समान भार सांख्यिकीय — देते हैं न कि सख्त — संतुलन।

### एजेंटिक पाइपलाइन मोड

कम से कम दो मॉडलों वाला एक `pipeline` कॉम्बो `config.agenticOrchestration.enabled` के साथ planner/executor रूटिंग का विकल्प चुन सकता है। पहला लक्ष्य योजना और अंतिम उत्तर का मालिक है; दूसरा लक्ष्य क्लाइंट-नेटिव टूल कॉल उत्सर्जित करता है। OmniRoute अनुरोध प्रोटोकॉल से टूल-परिणाम निरंतरता का पता लगाता है, प्लानर से पूछता है कि क्या किसी अन्य टूल राउंड की आवश्यकता है, और गतिशील रूप से निष्पादक या प्लानर को क्लाइंट-फेसिंग अंतिम चरण बनाता है।

वैकल्पिक `config.agenticOrchestration.contextCompaction` प्रत्येक योजनाकार या निष्पादक प्रेषण से पहले एक अलग पेलोड बजट लागू करता है। इसे स्पष्ट रूप से सक्षम करें:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

ये ऑपरेटर द्वारा चयनित क्रमबद्ध JSON वर्ण बजट हैं, न कि टोकन संदर्भ विंडो या गारंटीकृत अपस्ट्रीम सीमाएँ। सटीक मॉडल IDs डिफ़ॉल्ट को ओवरराइड करता है। सीमा से ऊपर, संघनन समान उपकरण परिभाषाओं को हटा देता है, एक डाइजेस्ट के साथ बड़े आकार के उपकरण साक्ष्य को ट्रिम कर देता है, और लक्ष्य अनुपात की ओर पुराने पूर्ण इतिहास समूहों को हटा देता है। यह system/developer निर्देश, नवीनतम उपयोगकर्ता अनुरोध, समानांतर calls/results सहित अंतिम टूल राउंड और Gemini के प्रमुख रूटिंग निर्देश को बरकरार रखता है। शीर्ष-स्तरीय निर्देश और टूल सेटिंग्स संरक्षित हैं। एक चूक मार्कर हटाए गए इतिहास को रिकॉर्ड करता है; यह नियतिवादी काट-छाँट है, अर्थ संबंधी सारांश नहीं। यदि पिन किया गया संदर्भ अभी भी बजट से अधिक है, तो मॉडल से संपर्क करने से पहले अनुरोध 413 लौटाता है। संघनन अक्षम होने पर या सीमा से नीचे होने पर अनुरोध अपरिवर्तित रहता है।

टूल-परिणाम निरंतरता पर, OmniRoute तब भी निष्पादन बंद कर देता है जब दो लगातार पूर्ण किए गए राउंड अपरिवर्तित परिणामों के साथ समान टूल कॉल दोहराते हैं, या जब लगातार दो राउंड में प्रत्येक स्पष्ट रूप से चिह्नित परिणाम विफल हो जाता है। बदले हुए परिणाम बार-बार कॉल करने की अनुमति देते हैं (उदाहरण के लिए, मतदान)। गार्ड एक नए उपयोगकर्ता अनुरोध पर रीसेट करता है, समानांतर कॉल को एक राउंड में समूहित करता है, और Anthropic, चैट पूर्णता, प्रतिक्रिया और Gemini इतिहास का समर्थन करता है। योजनाकार कारण प्राप्त करता है और अंतिम उत्तर का स्वामी होता है, भले ही वह किसी अन्य टूल राउंड का अनुरोध करता हो।

दूसरे लक्ष्य के बाद अतिरिक्त मॉडलों को निष्पादक बैकअप का आदेश दिया जाता है। एक असफल HTTP प्रतिक्रिया या परिवहन अपवाद अगले निष्पादक के लिए आगे बढ़ता है, वही योजनाकार निर्णय और मूल उपकरण ले जाता है लेकिन उस निष्पादक का अपना चरण संकेत और हल किया गया कनेक्शन होता है। पहली सफल प्रतिक्रिया अपरिवर्तित लौटा दी जाती है, जिसमें SSE स्ट्रीमिंग भी शामिल है; एक सफल स्ट्रीम प्रारंभ होने के बाद विफलताओं का यहां पुनः प्रयास नहीं किया जा सकता है। यदि सभी निष्पादक विफल हो जाते हैं, तो अंतिम विफलता वापस आ जाती है। ग्राहक प्रेषण रोकना बंद कर देता है।

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

निष्पादक एक प्रतिक्रिया में कई स्वतंत्र कॉल उत्सर्जित कर सकता है। आश्रित कॉलों को बाद के क्लाइंट टूल-परिणाम मोड़ों में नियंत्रित किया जाता है, जिसमें योजनाकार प्रत्येक परिणाम की समीक्षा करता है। `maxToolRounds` `8` पर डिफॉल्ट करता है और `1`-`32` स्वीकार करता है; एक बार पहुंचने के बाद, योजनाकार को सर्वोत्तम उपलब्ध अंतिम उत्तर प्रस्तुत करना होगा। आंतरिक योजनाकार निर्णय बफ़र किए जाते हैं, जबकि चयनित क्लाइंट-सामना वाली प्रतिक्रिया मूल स्ट्रीमिंग प्राथमिकता को सुरक्षित रखती है।

### `round-robin` स्टिकी बैच और खाता विस्तार

राउंड-रॉबिन बैच किया गया है, प्रति चरण एक-अनुरोध नहीं:

- `stickyRoundRobinLimit` (कॉम्बो कॉन्फ़िगरेशन, फिर `comboStickyRoundRobinLimit`, फिर `settings.stickyRoundRobinLimit`, डिफ़ॉल्ट** 3** ) घूमने से पहले लगातार कई सफलताओं के लिए एक ही लक्ष्य रखता है। एक-अनुरोध रोटेशन के लिए कॉम्बो ओवरराइड को `1` पर सेट करें। कॉम्बो संपादक प्रभावी मूल्य दिखाता है और यह किस परत से आया है।
- `connectionAwareExpansion` (कॉम्बो कॉन्फ़िगरेशन, फिर सेटिंग्स, डिफ़ॉल्ट** असत्य** ) रोटेशन से पहले प्रत्येक प्रदाता-स्तरीय चरण को प्रति-खाता लक्ष्य में विस्तारित करता है। समूह-बी रणनीतियाँ (प्राथमिकता, भारित, राउंड-रॉबिन, यादृच्छिक, पी2सी, कम से कम उपयोग, लागत-अनुकूलित, एलकेजीपी, भरण-प्रथम, सख्त-यादृच्छिक, संदर्भ-अनुकूलित, कैश-अनुकूलित, संदर्भ-रिले, फ़्यूज़न, पाइपलाइन, जेईवी) जब तक यह चालू न हो तब तक प्रदाता-स्तर का दृश्य रखें। कॉम्बो संपादक इनहेरिट/चालू/बंद को उजागर करता है; इनहेरिट वैश्विक डिफ़ॉल्ट (बंद) का उपयोग करता है।
- प्रॉम्प्ट-कैश लोकैलिटी रूटिंग (`promptCacheAffinityEnabled`, default** सत्य** ) पिन किए गए कनेक्शनों को पुन: व्यवस्थित करता है ताकि मिलान करने वाली कैश कुंजियाँ एक खाते पर बनी रहें। यह पिन किए गए प्रति-खाता चरणों में राउंड-रॉबिन और भारित रोटेशन पर पूर्वता लेता है। यदि आपको सख्त रोटेशन की आवश्यकता है तो इसे सेटिंग्स → कॉम्बो डिफ़ॉल्ट के तहत बंद करें। कोई प्रति-कॉम्बो ओवरराइड नहीं है.

एक मॉडल पर मल्टी-अकाउंट रोटेशन के लिए, प्राथमिकता दें** एक गतिशील-खाता कदम** (खाली `connectionId`, पूरा पूल) चिपचिपी सीमा `1` के साथ, तीन पिन वाले `connectionId` s नहीं। RR काउंटर के आगे बढ़ने पर भी पिन किए गए चरण और एफ़िनिटी एक ही खाते पर सिमट जाते हैं।

## फ़्यूज़न रणनीति

`fusion` ऐसी एकमात्र रणनीति है जो किसी एक लक्ष्य को **नहीं** चुनती। यह प्रॉम्प्ट को
**प्रत्येक पैनल मॉडल के पास समानांतर रूप से** भेजती है, फिर एक कॉन्फ़िगर करने योग्य **जज मॉडल**
सभी पैनल प्रतिक्रियाओं से एक अंतिम उत्तर तैयार करता है। इसे अपस्ट्रीम `decolua/9router`
(OpenRouter के Fusion डिज़ाइन) से पोर्ट किया गया है; कार्यान्वयन `open-sse/services/fusion.ts` में है।

यह कैसे काम करता है:

0. **टूल-युक्त बाइपास** — ऐसा अनुरोध जिसमें एक गैर-रिक्त `tools` ऐरे हो और
   `tool_choice` स्पष्ट रूप से `"none"` न हो, वह पैनल को पूरी तरह छोड़ देता है: इसे
   सीधे एक मॉडल (कॉन्फ़िगर किया गया जज, या `panel[0]`) पर रूट किया जाता है, जबकि
   `tools`/`tool_choice` को बिना बदलाव के आगे भेजा जाता है। पैनल सदस्यों के पास टूल
   एक्सेस नहीं होती और जज का संश्लेषण निर्देश टूल-कॉल उत्सर्जन को हतोत्साहित करता है,
   इसलिए एजेंटिक/टूल-कॉलिंग क्लाइंट को संश्लेषित गद्य के बजाय वास्तविक टूल-कॉल निर्णय
   मिलता है (#6771)।
1. **फ़ैन-आउट** (केवल टूल-रहित अनुरोधों के लिए) — प्रॉम्प्ट को सभी पैनल
   मॉडलों के पास एक साथ भेजा जाता है, टूल हटाकर और नॉन-स्ट्रीमिंग को बाध्य करके
   (संश्लेषण के लिए जज को पूरा गद्य चाहिए)।
2. **कोरम-ग्रेस संग्रह** — जैसे ही `minPanel` उत्तर आ जाते हैं, पीछे रह गए मॉडलों
   के लिए एक छोटा ग्रेस टाइमर शुरू हो जाता है, फिर जो कुछ भी एकत्र हुआ है उसके साथ
   फ़्यूज़न आगे बढ़ता है। इससे सबसे धीमे मॉडल के कारण वॉल टाइम पर पड़ने वाला दंड
   सीमित रहता है और एक हार्ड टाइमआउट से बाधित होता है।
3. **जज संश्लेषण** — पैनल उत्तरों को अनाम बनाया जाता है (`Source 1`, `Source 2`, … —
   ताकि जज मॉडल ब्रांड के बजाय विषय-वस्तु को महत्व दे) और जज को सौंपा जाता है, जो
   सहमति / विरोधाभासों / आंशिक कवरेज / विशिष्ट अंतर्दृष्टियों / अनदेखे पहलुओं का
   विश्लेषण करता है, फिर **एक** प्रामाणिक उत्तर लिखता है। जज कॉल क्लाइंट के मूल
   `stream` फ़्लैग + टूल को बनाए रखती है, इसलिए स्ट्रीमिंग और डाउनस्ट्रीम टूल उपयोग
   फिर भी काम करते हैं।
4. **सुचारु अवनयन** — 0 पैनल उत्तर → `503`; ठीक 1 उत्तरदाता → वही उत्तर
   सीधे लौटाया जाता है (फ़्यूज़ करने के लिए कुछ नहीं); एकल-मॉडल पैनल सीधे उत्तर देता है।

पैनल सदस्य एक `combo-ref` चरण (`{kind: "combo-ref", comboName: "..."}`) भी हो सकता है, जो
किसी अन्य कॉम्बो को संदर्भित करता है — यह **एक ब्लैक-बॉक्स पैनल आवाज़** के रूप में रिज़ॉल्व
होता है (संदर्भित कॉम्बो में पूर्ण रिकर्सिव डिस्पैच, न कि उस कॉम्बो के अपने लक्ष्यों का
फ़ैन-आउट), और इसमें वही गहराई/चक्र सुरक्षा होती है जिसका उपयोग पहले से ही प्रत्येक अन्य
combo-ref-उपयोग करने वाली रणनीति करती है (#6764)।

### कॉन्फ़िगरेशन

कॉम्बो के `config` ब्लॉब पर कॉन्फ़िगर किया जाता है (कोई स्कीमा माइग्रेशन नहीं — यह मौजूदा
`combos` तालिका का पुनः उपयोग करता है):

| फ़ील्ड                                   | प्रकार   | डिफ़ॉल्ट       | उद्देश्य                                                                            |
| :--------------------------------------- | :------- | :------------- | :---------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | पहला पैनल मॉडल | अंतिम उत्तर का संश्लेषण करने वाला मॉडल                                              |
| `config.fusionTuning.minPanel`           | `number` | `2`            | ग्रेस टाइमर शुरू होने से पहले आवश्यक सफल उत्तर (`[2, panelSize]` की सीमा में सीमित) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`         | कोरम पूरा होने के बाद पीछे रह गए मॉडलों के लिए कितनी देर प्रतीक्षा करनी है          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`        | पूर्ण सीमा, ताकि कोई एक अटका हुआ मॉडल अनुरोध को रोक न सके                           |

डिफ़ॉल्ट मान `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) में मौजूद हैं।

## वर्चुअल ऑटो-कॉम्बो फ़ैक्टरी

Auto Combo इंजन को पहले से परिभाषित कॉम्बो की आवश्यकता नहीं होती। इसके बजाय, `open-sse/services/autoCombo/virtualFactory.ts` तत्काल उम्मीदवार बनाता है:

1. `getProviderConnections({ isActive: true })` (सभी सक्षम कनेक्शन) प्राप्त करता है
2. वैध क्रेडेंशियल वाले कनेक्शन फ़िल्टर करता है (API कुंजी या `hasUsableOAuthToken()` के माध्यम से गैर-समाप्त OAuth टोकन)
3. मॉडल उपलब्धता + मूल्य निर्धारण के लिए `getProviderRegistry()` के साथ क्रॉस-रेफ़रेंस करता है
4. प्रत्येक टपल `(provider, model, connection)` के लिए एक `VirtualAutoComboCandidate` बनाता है
5. डिस्पैच लक्ष्य के रूप में `connection.defaultModel` (या रजिस्ट्री का पहला मॉडल) चुनता है
6. 16-फ़ैक्टर वाले `scorePool()` और वेरिएंट के वेट पैक का उपयोग करके प्रत्येक उम्मीदवार को स्कोर करता है
7. `handleComboChat()` के लिए परिणामी इन-मेमोरी `AutoComboConfig` लौटाता है — इसे कभी भी DB में स्थायी रूप से संग्रहीत नहीं किया जाता

इसका अर्थ है कि **`auto/*` सक्षम वाला नया प्रोवाइडर जोड़ने पर उम्मीदवार पूल अपने-आप विस्तृत हो जाता है** — कॉम्बो को मैन्युअल रूप से संपादित करने की आवश्यकता नहीं होती। वर्चुअल कॉम्बो प्रत्येक अनुरोध के लिए दोबारा बनाया जाता है, इसलिए नए जोड़े गए या फिर से स्वस्थ हुए कनेक्शन तुरंत चुन लिए जाते हैं।

## स्व-उपचार

- **अस्थायी बहिष्करण**: स्कोर < 0.2 → 5 मिनट के लिए बहिष्कृत (प्रगतिशील बैकऑफ़, अधिकतम 30 मिनट)
- **सर्किट ब्रेकर जागरूकता**: OPEN → स्वतः बहिष्कृत; HALF_OPEN → प्रोब अनुरोध
- **घटना मोड**: >50% OPEN → अन्वेषण अक्षम करें, स्थिरता अधिकतम करें
- **कूलडाउन रिकवरी**: बहिष्करण के बाद पहला अनुरोध कम टाइमआउट वाला एक "प्रोब" होता है

## बैंडिट अन्वेषण

5% अनुरोध (कॉन्फ़िगर करने योग्य) अन्वेषण के लिए यादृच्छिक प्रोवाइडरों तक रूट किए जाते हैं। घटना मोड में यह अक्षम रहता है।

## API

वहाँ है** कोई समर्पित `POST /api/combos/auto` समापन बिंदु नहीं** — ऑटो-कॉम्बो का उपभोग दो तरीकों से किया जाता है:

1. **शून्य-विन्यास (अनुशंसित):** किसी भी चैट समापन अनुरोध को `model: "auto"` या `model: "auto/<variant>"` के साथ भेजें। वर्चुअल फ़ैक्टरी प्रति अनुरोध — कॉम्बो बनाती है, कोई दृढ़ता नहीं, कोई API कॉल की आवश्यकता नहीं है।

2. **`strategy: "auto"` के साथ कायम कॉम्बो:** `POST /api/combos` के माध्यम से एक नियमित कॉम्बो बनाएं और `strategy: "auto"` प्लस `config.auto.weights` / `config.auto.candidatePool` सेट करें। उसी स्कोरिंग इंजन का उपयोग किया जाता है; कॉम्बो को `combos` में संग्रहीत किया जाता है और ID द्वारा पुन: प्रयोज्य किया जाता है।

खोज के लिए, `GET /api/combos/auto` अपने हल किए गए उम्मीदवार पूल प्लस `context_length` / `max_output_tokens` — MAX के साथ उम्मीदवार पूल की विंडो में प्रत्येक संस्करण को सूचीबद्ध करता है। ग्राहकों (उदाहरण के लिए ओपनकोड प्लगइन) को `0` के बजाय इन मानों का विज्ञापन करना चाहिए: एक शून्य संदर्भ ओपनकोड के ऑटो-कॉम्पैक्शन को पूरी तरह से अक्षम कर देता है, जिससे सत्र बढ़ने लगते हैं जब तक कि गेटवे का इतिहास पर्ज संदर्भ को नष्ट नहीं कर देता। MAX का विज्ञापन करना सुरक्षित है क्योंकि ऑटो-कॉम्बो संदर्भ प्री-फ़िल्टर बड़े-विंडो वाले उम्मीदवारों के अनुरोधों को बड़े पैमाने पर रूट करता है।

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ऑटो राउटर रणनीतियाँ

निरंतर `strategy: "auto"` कॉम्बो `config.routerStrategy` (या लीगेसी `config.auto.routerStrategy`) को इनमें से किसी एक पर सेट कर सकते हैं:

- `rules` — डिफ़ॉल्ट भारित स्कोरिंग
- `score` — उच्चतम कॉन्फ़िगर किए गए भारित स्कोर का चयन करता है। सटीक संबंध कॉन्फ़िगर किए गए उम्मीदवार क्रम को संरक्षित करते हैं; पूर्ण रैंक वाले पूल से मौजूदा `explorationRate` नमूने।
- `cost` / `eco` — सबसे सस्ता स्वस्थ प्रदाता
- `latency` / `fast` — विश्वसनीयता दंड के साथ न्यूनतम p95 विलंबता
- `sla-aware` / `sla` — उन उम्मीदवारों को प्राथमिकता देते हैं जो p95 विलंबता, त्रुटि-दर और वैकल्पिक लागत को संतुष्ट करते हैं SLOs
- `lkgp` — अंतिम ज्ञात अच्छा प्रदाता प्रथम
- `nadir` — [नादिर](https://getnadir.com) के निर्णय से पूछता है API पूल में किस मॉडल की शीघ्र आवश्यकता है; ऑप्ट-इन करें, `rules` में फेल-ओपन करें
- `decision` — एक कॉन्फ़िगर किए गए निर्णायक से पूछें (TypeSafe सिस्टम वन, आपका अपना निर्णय URL, या कॉम्बो के स्वयं के मॉडल में से एक) पूल में कौन सा मॉडल अनुरोध को फिट करता है; डिफॉल्ट-ऑफ `COMBO_DECISION_ROUTER_ENABLED` ध्वज के पीछे, `rules` के लिए फेल-ओपन

### राउटर रणनीतियाँ विस्तार से

ऑटो-कॉम्बो इंजन 7 प्लगेबल को उजागर करता है**RouterStrategy** कार्यान्वयन जिन्हें आप `config.routerStrategy` (या विरासत `config.auto.routerStrategy`) के माध्यम से स्वैप कर सकते हैं। प्रत्येक रणनीति उम्मीदवार पूल से एक प्रदाता को चुनती है, जिसे `RoutingContext` (कार्य प्रकार, tool/vision संकेत, टोकन अनुमान, वैकल्पिक SLA नीति, वैकल्पिक अंतिम-ज्ञात-अच्छा प्रदाता) दिया जाता है।

#### 1. `rules` (डिफ़ॉल्ट) — 16-कारक भारित स्कोरिंग

मौजूदा स्कोरिंग इंजन को लपेटता है। `OPEN` सर्किट-ब्रेकर उम्मीदवारों को फ़िल्टर करता है, फिर शीर्ष-स्कोरिंग प्रदाता को चुनते हुए, वर्तमान कार्य प्रकार और `getTaskFitness()` के साथ `scorePool()` चलाता है।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**कब उपयोग करें** : गलती करना। जब आप सभी संकेतों पर संतुलित व्यापार-बंद चाहते हों तो इसका उपयोग करें।

**उपनाम** : `rules` (कोई उपनाम नहीं)

---

#### 2. `cost` / `eco` — सबसे सस्ता स्वस्थ प्रदाता

उम्मीदवार पूल को `costPer1MTokens` (आरोही) के आधार पर क्रमबद्ध करता है और सबसे सस्ता चुनता है। पहले `OPEN` उम्मीदवारों को फ़िल्टर करें।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कब उपयोग करें** : लागत-संवेदनशील कार्यभार, बैच प्रोसेसिंग, या पृष्ठभूमि कार्य।

**उपनाम** : `cost`, `eco`

---

#### 3. `latency` / `fast` — विश्वसनीयता दंड के साथ न्यूनतम p95 विलंबता

`p95LatencyMs + (errorRate * 1000)` के अनुसार क्रमबद्ध। त्रुटि-दर जुर्माना यह सुनिश्चित करता है कि अविश्वसनीय प्रदाताओं को निचली रैंक दी जाए, भले ही उनकी नाममात्र विलंबता कम हो।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कब उपयोग करें** : वास्तविक समय चैट, स्वत: पूर्ण, या इंटरैक्टिव कोडिंग सहायक जैसे विलंबता-संवेदनशील कार्यभार।

**उपनाम** : `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO अनुपालन

प्रत्येक उम्मीदवार को इस आधार पर स्कोर दिया जाता है कि वह कॉन्फ़िगर की गई SLO नीति को कितनी अच्छी तरह संतुष्ट करता है:

| कारक            | वज़न | FORMULA                                           |
| --------------- | ---- | ------------------------------------------------- |
| विलंबता स्कोर   | 35%  | `threshold / max(value, ε)`                       |
| त्रुटि स्कोर    | 35%  | `threshold / max(value, ε)`                       |
| स्वास्थ्य स्कोर | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| लागत स्कोर      | 10%  | `threshold / max(value, ε)` या उलटा सामान्यीकृत   |
| स्थिरता स्कोर   | 5%   | उलटा सामान्यीकृत विलंबता stddev                   |

जब `hardConstraints: true`, उम्मीदवारों को मुख्य रूप से क्रमबद्ध किया जाता है** उल्लंघन स्कोर** (वे किसी भी SLO कितनी अधिक हैं), फिर समग्र स्कोर द्वारा। अन्यथा यह केवल समग्र स्कोर है।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA फ़ील्ड** (कॉम्बो कॉन्फ़िगरेशन पर सेट करें):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**कब उपयोग करें** : सख्त विलंबता, त्रुटि-दर, या लागत बजट के साथ उत्पादन कार्यभार।

**उपनाम** : `sla-aware`, `sla`

---

#### 5. `lkgp` — अंतिम ज्ञात अच्छा प्रदाता प्रथम

कोशिश करता है** अंतिम ज्ञात अच्छा प्रदाता** (यदि सेट हो) पहले, फिर `rules` रणनीति पर वापस आ जाता है। सत्र चिपचिपाहट के लिए उपयोगी — वही प्रदाता वार्तालाप में अनुवर्ती अनुरोधों को संभालता है।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**कब उपयोग करें** : मल्टी-टर्न वार्तालाप जहां आप चाहते हैं कि एक ही प्रदाता अनुवर्ती अनुरोधों को संभाले (उदाहरण के लिए, कैशिंग, संदर्भ निरंतरता, या मूल्य निर्धारण स्थिरता के लिए)।

**उपनाम** : `lkgp` (कोई उपनाम नहीं)

#### 6. नादिर के माध्यम से `nadir` — प्रॉम्प्ट-अवेयर मॉडल विकल्प

उपरोक्त प्रत्येक रणनीति उम्मीदवारों को उनकी अपनी टेलीमेट्री के आधार पर रैंक करती है; उनमें से कोई भी अनुरोध नहीं पढ़ता है। `nadir` अंतिम उपयोगकर्ता मोड़ और पूल के मॉडल आईडी को [नादिर](https://getnadir.com) के निर्णय API (`POST /v1/bucket`) पर भेजता है और उस मेनू से नादिर द्वारा चुने गए मॉडल पर रूट भेजता है (`simple` → सबसे सस्ता सक्षम मॉडल, `complex` → सबसे आगे)। उस मॉडल की सेवा देने वाला कनेक्शन अभी भी `rules` द्वारा चुना जाता है, इसलिए कोटा, स्वास्थ्य और लागत यह तय करते रहते हैं कि कौन सा खाता है।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` और `OMNIROUTE_NADIR_BASE_URL` दो स्ट्रिंग्स के लिए env फ़ॉलबैक हैं। `baseUrl` केवल स्व-होस्टेड नादिर के लिए आवश्यक है (एक अनुगामी `/v1` सहन किया जाता है)। कीलेस कॉल नादिर के अज्ञात स्तर पर आती है, जो प्रति IP दर-सीमित है। एक कुंजी ( [एक बनाएं](https://app.getnadir.com/dashboard/api-keys) ) के साथ, प्रत्येक निर्णय आपके नादिर डैशबोर्ड पर लॉग किया जाता है। पूर्ण सेटअप और सत्यापन: [getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/) ।

बॉक्स में क्या निकलता है: अंतिम उपयोगकर्ता संदेश का पाठ (पहले 16k अक्षर), उम्मीदवार मॉडल आईडी और एक `source: "omniroute"` चैनल टैग। कोई सिस्टम प्रॉम्प्ट, इतिहास, उपकरण या हेडर नहीं।

विफलता व्यवहार विफल-खुला है: एक टाइमआउट (डिफ़ॉल्ट 2000 एमएस), एक non-2xx, एक पहुंच योग्य होस्ट, एक विकृत प्रतिक्रिया या पूल के बाहर एक चयन `rules` निर्णय का समाधान करता है और कारण उपसर्ग `NadirStrategy: fallback (…)` है। विफल कॉल के बाद रणनीति 30 सेकंड के लिए नेटवर्क को छोड़ देती है, इसलिए आउटेज के लिए प्रति अनुरोध एक के बजाय प्रति 30 सेकंड में एक टाइमआउट खर्च होता है। रूटिंग इवेंट रिपोर्ट तभी `strategy: "nadir"` जब नादिर ने वास्तव में चुनाव किया हो।

**कब उपयोग करें** : एक पूल पर मिश्रित-कठिनाई वाला ट्रैफ़िक जो मॉडल स्तरों (एक छोटा, एक मध्य और एक सीमांत मॉडल) तक फैला है, जहां हमेशा-सीमांत वह लागत है जिसे आप कम करना चाहते हैं।

**उपनाम** : `nadir` (कोई उपनाम नहीं)

#### 7. `decision` — प्लगेबल डिसाइडर मॉडल चुनता है

`decision` एक पूछता है** निर्णायक** पूल में कौन सा मॉडल अनुरोध को फिट करता है, फिर पूल को उस मॉडल तक सीमित कर देता है और `rules` कनेक्शन चुनने देता है (कोटा, स्वास्थ्य और लागत अभी भी खाता चुनता है)। निर्णायक को कॉम्बो के निर्णय ब्लॉक — `config.decision` में सेट किया जाता है जब राउटर नॉब्स `config` के शीर्ष पर बैठते हैं (डैशबोर्ड क्या लिखता है), या `config.auto.decision` `config.auto.routerStrategy` के बगल में:

| `decider`     | कौन उत्तर देता है                                                                                                | ज़रूरत                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `systemone`   | TypeSafe सिस्टम वन (`POST https://api.typesafe.ai/v1/systemone`), डिफ़ॉल्ट मॉडल `jev-latest`                     | एक `typesafe` कनेक्शन या env कुंजी                    |
| `http`        | `baseUrl` पर आपका अपना निर्णायक: `wire: "systemone"` (`{baseUrl}/v1/systemone`) या `"openai-chat"` (चैट पूर्णता) | `baseUrl` + `model`; कुंजी वैकल्पिक                   |
| `combo-model` | आपके प्रदाता मॉडल में से एक, फ़्यूज़न जज की तरह प्रक्रिया में बुलाया गया                                         | `model` `provider/model` के रूप में (कोई कॉम्बो नहीं) |

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "decision",
    "decision": {
      "decider": "http",
      "baseUrl": "https://decider.example.com",
      "wire": "openai-chat",
      "model": "qwen-small",
      "connectionId": "<stored connection id>",
      "timeoutMs": 2000,
      "minConfidence": 0.6,
      "descriptions": { "gpt-4o-mini": "Quick drafts and short answers" }
    }
  }
}
```

फ़ील्ड्स (सहेजने पर और फिर अनुरोध समय पर एक सख्त स्कीमा द्वारा मान्य):

- `decider` — `systemone`, `http` या `combo-model`.
- `model` — TypeSafe मॉडल, आपके URL पर निर्णय मॉडल, या कॉम्बो-मॉडल कॉल का `provider/model` (200 वर्ण तक)।
- केवल `baseUrl` — `http` : 500 वर्णों तक का एक `http(s)` URL, बिना क्रेडेंशियल, क्वेरी या खंड के। इस OmniRoute (लूपबैक + `PORT`) की ओर इशारा करने वाले URL अस्वीकार कर दिया गया है।
- `wire` — `http` केवल: `systemone` (डिफ़ॉल्ट) या `openai-chat`।
- `connectionId` — संग्रहीत कनेक्शन जिसकी कुंजी का उपयोग किया जाता है (केवल कॉलिंग API कुंजी के अनुमत कनेक्शन के अंदर)। इसके बिना, `systemone` एक `typesafe` कनेक्शन पढ़ता है और प्रत्येक नेटवर्क निर्णायक `OMNIROUTE_DECISION_API_KEY` पर वापस आ जाता है। कोई `apiKey` फ़ील्ड नहीं है: किसी कुंजी को कभी भी कॉम्बो में संग्रहीत नहीं किया जाता है।
- `timeoutMs` — पूर्णांक, 100-5000, डिफ़ॉल्ट 2000।
- `minConfidence` — 0-1; कम आत्मविश्वास वाला उत्तर `rules` पर वापस आ जाता है (एक निर्णायक जो अविश्वास की रिपोर्ट करता है उसे 0 के रूप में गिना जाता है)।
- 50 प्रविष्टियों तक `descriptions` — (300 तक कुंजी, 1000 वर्णों तक पाठ), मॉडल आईडी या `provider/model` द्वारा कुंजीबद्ध; अनसेट प्रविष्टियों को एक उत्पन्न लागत-रैंक विवरण मिलता है।

**झंडा।** `COMBO_DECISION_ROUTER_ENABLED` (डिफ़ॉल्ट `false`) प्रत्येक निर्णायक को गेट करता है। जबकि यह बंद है, एक `decision` कॉम्बो कोई क्रेडेंशियल नहीं पढ़ता है, कोई कॉल नहीं करता है और `rules` के साथ रूट करता है; लॉग कहता है `fallback (disabled)`. अकेले संग्रहित कुंजी इसे कभी भी चालू नहीं करती है। निर्णय ब्लॉक के बिना कॉम्बो बिल्कुल भी प्रभावित नहीं होते हैं।

**बॉक्स क्या छोड़ता है.** केवल अंतिम उपयोगकर्ता संदेश का पाठ (8000 वर्ण तक; chat/Claude `messages` या प्रतिक्रियाएं `input`) और उनके विवरण के साथ मॉडल आईडी का मेनू। कभी भी सिस्टम प्रॉम्प्ट, प्रतिक्रियाएँ `instructions`, उपकरण, इतिहास, हेडर या खाता डेटा नहीं। नेटवर्क कॉल प्रदाता आउटबाउंड गार्ड के माध्यम से बिना किसी पुनर्प्रयास, बिना रीडायरेक्ट और 64 KB प्रतिक्रिया सीमा के गुजरती हैं। `combo-model` कॉल 256-टोकन बजट के साथ गैर-स्ट्रीमिंग, टूल-मुक्त, `temperature: 0` है; निर्णय कॉल के अंदर शुरू किए गए निर्णय को अस्वीकार कर दिया जाता है।

**असफल व्यवहार** विफल-खुला है: कोई भी विफलता `rules` निर्णय को हल करती है, और कारण `decision(<decider>): fallback (<reason>)` पढ़ता है, `<reason>` के साथ `disabled`, `not_configured`, `missing_credential`, `timeout`, `http_error`, `invalid_response`, `out_of_menu`, `refused`, `cooldown`, `network_error`, `recursion`, `low_confidence`, `single_option` या `no_user_text` में से एक . टाइमआउट, HTTP त्रुटि या नेटवर्क त्रुटि के बाद समापन बिंदु 30 सेकंड के लिए छोड़ दिया जाता है। एक सफल चयन `decision(<decider>): selected <model> from <n>; confidence <c> (<rules reason>)` पढ़ता है। कोई URL, कुंजी, प्रॉम्प्ट या अपस्ट्रीम बॉडी लॉग तक नहीं पहुंचती है।

कॉम्बो बिल्डर इन फ़ील्ड्स को तब दिखाता है जब राउटर रणनीति `decision` होती है, प्लेसहोल्डर और ए के रूप में उत्पन्न विवरण के साथ** परीक्षण का निर्णय** बटन जो बिना सहेजी गई सेटिंग्स (समान ध्वज) के साथ एक बार `POST /api/combos/decision-preview` कॉल करता है।

**कब उपयोग करें** : मिश्रित-कठिनाई वाला ट्रैफ़िक जहां आप चाहते हैं कि आपके द्वारा चुने गए क्लासिफायर द्वारा अनुरोध के अनुसार स्तर चुना जाए, न कि विशेष रूप से नादिर द्वारा।

**उपनाम** : `decision` (कोई उपनाम नहीं)

### कस्टम राउटर रणनीतियाँ

आप सार्वजनिक API के माध्यम से अपना स्वयं का `RouterStrategy` कार्यान्वयन पंजीकृत कर सकते हैं:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

फिर इसका उपयोग करें:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### राउटर रणनीति चयन गाइड

| उदाहरण                 | रणनीति      | कारण                                     |
| ---------------------- | ----------- | ---------------------------------------- |
| संतुलित कार्यभार       | `rules`     | डिफ़ॉल्ट — सभी कारकों पर विचार करता है   |
| लागत कम करें           | `cost`      | हमेशा सबसे सस्ता चुनता है                |
| विलंबता को कम करें     | `latency`   | सबसे तेज़ विश्वसनीय प्रदाता चुनता है     |
| सख्त SLOs              | `sla-aware` | p95/error/cost थ्रेसहोल्ड द्वारा फ़िल्टर |
| मल्टी-टर्न चैट         | `lkgp`      | सत्र चिपचिपाहट                           |
| मिश्रित कठिनाई         | `nadir`     | प्रति प्रॉम्प्ट मॉडल स्तर चुनता है       |
| स्वयं का वर्गीकरणकर्ता | `decision`  | आपका निर्णायक मॉडल चुनता है              |

SLA-जागरूक फ़ील्ड:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## कार्य उपयुक्तता

6 कार्य प्रकारों (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) में 30+ मॉडलों को स्कोर दिया गया है। वाइल्डकार्ड पैटर्न समर्थित हैं (उदा., `*-coder` → उच्च कोडिंग स्कोर)।

## ऑटो वेरिएंट पुनर्कथन

`AutoVariant` `autoPrefix.ts` में घोषित करता है** 7 मान** (`coding`, `fast`, `cheap`, `offline`, `smart`, `lkgp`, `chaos`)। नंगे `auto` के साथ Together ( `parseAutoPrefix()` द्वारा `variant: undefined` के रूप में प्रबंधित) और दो फ्लैट टियर ओवरले `auto/subscription` और `auto/thrifty` ( `builtinCatalog.ts` में`FLAT_TIER_OVERLAY_IDS` ), वहाँ हैं** 10 फ्लैट मॉडल IDs** :

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`, `auto/chaos`, `auto/subscription`, `auto/thrifty`

उनसे परे, `auto/<category>[:<tier>]` रचनाएँ, मॉडल-परिवार IDs (उदाहरण के लिए `auto/claude-opus`) और `builtinCatalog.ts` में `auto/best-*` / `auto/pro-*` उपनाम भी हल करते हैं।

## टियर Auto-Combo में कैसे समाहित होते हैं

16-फ़ैक्टर वाला स्कोरिंग फ़ंक्शन (`open-sse/services/autoCombo/scoring.ts`) टियर
सदस्यता को दो संकेतों के रूप में मानता है: `tierPriority` (0.0476) और `tierAffinity` (0.0476)। संपूर्ण
`DEFAULT_WEIGHTS` सेट के लिए ऊपर दी गई प्रामाणिक [स्कोरिंग फ़ैक्टर तालिका](#how-it-works-persisted-auto-combos) देखें — प्रत्येक पैक के ओवरराइड (ship-fast/cost-saver/quality-first/
offline-friendly) "प्रति पैक वेट प्रोफ़ाइल" तालिका में सूचीबद्ध हैं।

केवल टियर, टियर 1 को पहले रखने के लिए **बाध्य** नहीं करता — यदि टियर 1 की लेटेंसी खराब है या
लागत-बनाम-गुणवत्ता इष्टतम नहीं है, तो टियर 2 विजेता होता है। टियर क्रम को बाध्य करने के लिए, कॉम्बो
रणनीति `priority` का उपयोग करें और प्रदाताओं को टियर के अनुसार व्यवस्थित करें।

टियर 1 (सब्सक्रिप्शन) को मज़बूत प्राथमिकता देने के लिए, `tierPriority` का वेट बढ़ाएँ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

टियर की परिभाषाओं और प्रदाता वर्गीकरण के लिए [`docs/guides/TIERS.md`](../guides/TIERS.md) देखें।

## परीक्षण एवं कवरेज

### नियतात्मक रूटिंग-निर्णय मैट्रिक्स (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` रूटिंग को सिद्ध करता है** फ़ैसला** यह नकली अपस्ट्रीम के साथ वास्तविक कॉम्बो पाइपलाइन के माध्यम से शुरू से अंत तक सार्वजनिक रणनीतियों को कवर करता है। कवरेज में शामिल हैं:

- 22 सार्वजनिक `ROUTING_STRATEGY_VALUES` रणनीतियों में से 18 (आदेशित, भारित, लागत, संदर्भ, संलयन, ...); `quota-weighted`, `cache-optimized`, `pipeline` और `jev` मैट्रिक्स द्वारा प्रयोग नहीं किए जाते हैं और अपने स्वयं के यूनिट परीक्षणों पर निर्भर होते हैं।
- `quota-share` (आंतरिक) एंड-टू-एंड: DRR निष्पक्षता + संतृप्ति deprioritization वास्तविक `selectQuotaShareTarget` सीम (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`) के माध्यम से।
- प्रत्येक लक्ष्य गणना में`context-relay` यूनिवर्सल-हैंडऑफ़ कवरेज।

यह सुइट CI (`test:integration` जॉब) में `--test-concurrency=1` और `--test-force-exit` के साथ चलता है इसलिए यह नियतात्मक है और इसके लिए लाइव क्रेडेंशियल की आवश्यकता नहीं है।

### गेटेड लाइव स्मोक (NOT इन CI — रियल प्रोवाइडर्स)

| आज्ञा                                  | यह क्या करता है                                                                     |
| :------------------------------------- | :---------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` के साथ इन-प्रोसेस वास्तविक रूटिंग; स्नैपशॉट एक लाइव OmniRoute DB |
| `npm run test:combo:live:vps`          | HTTP लाइव OmniRoute सर्वर के विरुद्ध कॉल करता है ( `COMBO_LIVE_BASE_URL` सेट करें)  |
| `npm run test:combo:live:vps:failover` | जानबूझकर फेलओवर परिदृश्यों के साथ भी ऐसा ही है                                      |

ये धुआं परीक्षण वास्तविक तार पथ (कॉम्बो → प्रदाता → पूर्णता) का अभ्यास करते हैं। उन्हें जानबूझकर CI से बाहर रखा गया है क्योंकि उन्हें लाइव क्रेडेंशियल्स और VPS एक्सेस की आवश्यकता होती है।
