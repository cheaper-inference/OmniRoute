## चैट पूर्णताएँ

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### कस्टम हेडर

| हेडर                     | दिशा        | विवरण                                                                                                                                                                                                                                  |
| ------------------------ | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | अनुरोध      | कैश को बायपास करने के लिए `true` पर सेट करें                                                                                                                                                                                           |
| `x-omniroute-no-memory`  | अनुरोध      | इस अनुरोध के लिए मेमोरी + कौशल इंजेक्शन छोड़ने हेतु `true` पर सेट करें (नो-कैश के समान; प्रत्येक कॉल के टोकन/लागत ओवरहेड से बचाता है)                                                                                                  |
| `X-OmniRoute-Progress`   | अनुरोध      | प्रगति ईवेंट्स के लिए `true` पर सेट करें                                                                                                                                                                                               |
| `X-Session-Id`           | अनुरोध      | बाहरी सत्र एफ़िनिटी के लिए स्टिकी सत्र कुंजी                                                                                                                                                                                           |
| `x_session_id`           | अनुरोध      | अंडरस्कोर वाला संस्करण भी स्वीकार किया जाता है (प्रत्यक्ष HTTP)                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | अनुरोध      | कॉलर द्वारा दिया गया सत्र/वार्तालाप टैग (मेमोरी को भी फ़ीड करता है)। मौजूद होने पर, प्रति-सत्र लागत निर्धारण (#8249) के लिए इसे हूबहू `call_logs.session_tag` में स्थायी किया जाता है — अनुपस्थित होने पर कभी संश्लेषित नहीं किया जाता |
| `Idempotency-Key`        | अनुरोध      | डुप्लिकेट हटाने की कुंजी (5 सेकंड की विंडो)                                                                                                                                                                                            |
| `X-Request-Id`           | अनुरोध      | वैकल्पिक डुप्लिकेट हटाने की कुंजी                                                                                                                                                                                                      |
| `x-omniroute-connection` | अनुरोध      | एकल-मॉडल अनुरोध को उसके id के आधार पर किसी एक प्रदाता कनेक्शन (खाते) से पिन करें — [प्रति अनुरोध खाता पिनिंग](#account-pinning-per-request) देखें                                                                                      |
| `X-OmniRoute-Cache`      | प्रतिक्रिया | `HIT` या `MISS` (गैर-स्ट्रीमिंग)                                                                                                                                                                                                       |
| `X-OmniRoute-Idempotent` | प्रतिक्रिया | डुप्लिकेट हटाए जाने पर `true`                                                                                                                                                                                                          |
| `X-OmniRoute-Progress`   | प्रतिक्रिया | प्रगति ट्रैकिंग चालू होने पर `enabled`                                                                                                                                                                                                 |
| `X-OmniRoute-Session-Id` | प्रतिक्रिया | OmniRoute द्वारा उपयोग किया गया प्रभावी सत्र ID                                                                                                                                                                                        |
| `X-OmniRoute-Request-Id` | प्रतिक्रिया | अनुरोध सहसंबंध id (ज्ञात होने पर)                                                                                                                                                                                                      |
| `X-OmniRoute-Version`    | प्रतिक्रिया | OmniRoute बिल्ड संस्करण (हमेशा मौजूद)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | प्रतिक्रिया | किसी HIT पर कैश द्वारा बचाई गई USD राशि (केवल कैश हिट)                                                                                                                                                                                 |
| `X-OmniRoute-Decision`   | प्रतिक्रिया | रूटिंग ट्रेस: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` कॉम्बो रणनीति है, या गैर-कॉम्बो अनुरोध के लिए `single`) — पूर्णता प्रतिक्रियाओं में हमेशा मौजूद                                                            |

> Nginx नोट: यदि आप अंडरस्कोर वाले हेडर (उदाहरण के लिए `x_session_id`) पर निर्भर हैं, तो `underscores_in_headers on;` सक्षम करें।

#### प्रति अनुरोध खाता पिन करना

जब किसी प्रदाता के पास कई कनेक्शन (खाते या कुंजियाँ) होते हैं, तो OmniRoute सामान्यतः अपनी
खाता-चयन रणनीति के माध्यम से उनमें से एक को चुनता है। इसके बजाय, कोई अनुरोध
`x-omniroute-connection` हेडर के साथ किसी विशिष्ट कनेक्शन को पिन कर सकता है:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **आईडी कहाँ मिलेगी।** डैशबोर्ड में प्रदाता का पृष्ठ खोलें
  (**डैशबोर्ड → प्रदाता → <provider>**) और किसी कनेक्शन पंक्ति में `xxxxxxxx…` आईडी चिप पर क्लिक करें
  — इससे पूरी कनेक्शन आईडी कॉपी हो जाती है।
- **कौन-से अनुरोध इसका पालन करते हैं।** `/v1/chat/completions`, `/v1/messages` और
  `/v1/responses` पर एकल-मॉडल अनुरोध (`provider/model`)। कॉम्बो इस हेडर को अनदेखा करते हैं: इसके बजाय
  प्रत्येक कॉम्बो चरण के लिए उसके अपने कनेक्शन के माध्यम से खाता पिन करें।
- **पिन सख्त है, केवल प्राथमिकता नहीं।** पिन किए गए कनेक्शन का ही विशेष रूप से उपयोग किया जाता है। किसी
  अनुरोध के भीतर हुई विफलता खाते की कूलडाउन अवधि दर्ज करती है, लेकिन उसी प्रदाता के
  किसी अन्य संबद्ध खाते पर **स्विच नहीं** करती।
- **कूलडाउन और कोटा पिन को हटा देते हैं।** जब पिन किया गया कनेक्शन कूलडाउन में हो,
  उसका कोटा समाप्त हो गया हो या वह किसी कोटा नीति द्वारा अवरुद्ध हो, तो बाद के अनुरोध प्रदाता के
  अन्य कनेक्शनों पर फ़ॉलबैक करते हैं, ठीक वैसे ही जैसे बिना पिन वाला ट्रैफ़िक।
- **अज्ञात या अक्षम आईडी विफल होती हैं।** ऐसी आईडी जो प्रदाता के सक्रिय पूल में नहीं है (हटा दी गई,
  निष्क्रिय की गई या किसी अन्य प्रदाता से संबंधित), कोई पात्र खाता नहीं छोड़ती, इसलिए अनुरोध
  चुपचाप कहीं और रूट होने के बजाय विफल हो जाता है।

Claude Code, `ANTHROPIC_CUSTOM_HEADERS` के माध्यम से कस्टम हेडर भेजता है। इसे
`~/.claude/settings.json` के `env` ब्लॉक में रखें, या प्रत्येक प्रोजेक्ट के लिए अलग
खाता पिन करने हेतु प्रोजेक्ट-स्तरीय `.claude/settings.json` में रखें:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

स्रोत: `src/sse/handlers/chat.ts` (हेडर पढ़ना), `src/sse/services/auth.ts` और
`src/sse/services/sessionAffinityPin.ts` (पिन हटाना और पूल में अनुपस्थित होने की जाँच)।

> **लागत टेलीमेट्री हेडर:** गैर-स्ट्रीमिंग सफल प्रतिक्रियाओं में `X-OmniRoute-*` लागत-टेलीमेट्री सेट भी होता है — `X-OmniRoute-Response-Cost` (USD, निश्चित 10 दशमलव स्थान; मुफ़्त/बिना मूल्य वाले के लिए `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, और `X-OmniRoute-Fallback-Attempts` (केवल जब > 0 हो), साथ ही `X-OmniRoute-Request-Id` और `X-OmniRoute-Version`। ये चैट पूर्णताओं, `/v1/responses`, `/v1/messages`, **और मीडिया एंडपॉइंट** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, और `/v1/moderations` (लागत हमेशा `0`) — द्वारा उत्सर्जित किए जाते हैं। मूल्य निर्धारण उपलब्ध होने पर मीडिया लागत की गणना प्रत्येक मोडैलिटी (प्रति छवि, प्रति सेकंड, प्रति वर्ण, प्रति खोज-इकाई) के अनुसार की जाती है, अन्यथा `0` (फेल-ओपन)।

> **कैश-हिट लागत अर्थविज्ञान:** सिमेंटिक-कैश HIT (`X-OmniRoute-Cache-Hit: true`) पर कोई अपस्ट्रीम कॉल नहीं किया जाता, इसलिए `X-OmniRoute-Response-Cost`, `0.0000000000` होता है (हिट को सर्व करने की **वृद्धिशील** लागत)। मूल/संभावित लागत को `X-OmniRoute-Cost-Saved` में अलग से रिपोर्ट किया जाता है। बिलिंग उपभोक्ताओं को `X-OmniRoute-Response-Cost` का योग करना चाहिए (हिट की कोई लागत नहीं होती); कैश एनालिटिक्स `X-OmniRoute-Cost-Saved` को समेकित कर सकता है।

## विशिष्ट प्रबंधित सत्र लीज़

विशिष्ट प्रबंधित सत्र लीज़िंग एक ऑप्ट-इन, क्लाइंट-निरपेक्ष रूटिंग अनुबंध है: एक सक्रिय स्वामी
एक पात्र OmniRoute कनेक्शन को अपने पास रखता है। यह किसी मॉडल को लीज़ पर नहीं देता, OAuth की आवश्यकता नहीं रखता, किसी
विशिष्ट क्लाइंट की पहचान नहीं करता और न ही किसी विशिष्ट प्रदाता की आवश्यकता रखता है।

प्रमाणीकरण करने वाली API कुंजी के पास `lease:exclusive` स्कोप और एक स्पष्ट गैर-रिक्त
`allowedConnections` सूची होनी चाहिए। डेटाबेस म्यूटेशन सीमा कुंजी
बनाने और आंशिक अपडेट, दोनों के दौरान इन दोनों फ़ील्ड को एक साथ लागू करती है।

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

सफल acquire, renew और release प्रतिक्रियाएँ टाइमस्टैम्प, `state` और सटीक धनात्मक
`generation` दिखाती हैं, लेकिन चयनित कनेक्शन या क्रेडेंशियल कभी नहीं दिखातीं। Renew और release
JSON बॉडी में generation प्रदान करते हैं:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

एक सक्रिय लीज़ स्वामी अपनी वर्तमान बाइंडिंग के लिए स्पष्ट रूप से गोपनीयता-सुरक्षित प्रदर्शन मेटाडेटा का अनुरोध कर सकता है:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

यह ऑप्ट-इन status क्रिया एक ही डेटाबेस ट्रांज़ैक्शन में अपारदर्शी स्वामी, प्रमाणीकृत प्रबंधित API कुंजी और सटीक
सक्रिय generation द्वारा सुरक्षित की जाती है। `displayName` केवल ट्रिम किया गया कॉन्फ़िगर किया हुआ
कनेक्शन नाम है; कोई सुरक्षित कॉन्फ़िगर किया हुआ नाम मौजूद न होने पर यह `null` होता है। OmniRoute कभी भी इसके स्थान पर
ईमेल या जनरेट की गई खाता पहचान का उपयोग नहीं करता। provider मान एक गैर-संवेदनशील प्रदर्शन लेबल है और कभी भी
जनरेट किया गया संगत-प्रदाता पहचानकर्ता नहीं होता। क्रेडेंशियल, टोकन, कुकी, अपरिष्कृत कनेक्शन या API
कुंजी ids, स्वामी हैश, फ़ेंसिंग सीक्रेट और आंतरिक रूटिंग डेटा शामिल नहीं किए जाते।

गलत कुंजी, गलत स्वामी, पुरानी generation, अनुपलब्ध, समय-सीमा समाप्त, रिलीज़ की गई और अमान्य की गई लुकअप स्थितियाँ
सभी कनेक्शन मेटाडेटा के बिना समान `409 LEASE_FENCE_STALE` त्रुटि लौटाती हैं। क्षमता-प्रतीक्षा प्रतिक्रिया प्राप्त करने वाले क्लाइंट के पास निरीक्षण के लिए कोई सक्रिय बाइंडिंग नहीं होती। जब रूटिंग किसी सक्रिय लीज़ को स्थानांतरित करती है,
तो वही generation मान्य रहता है और status पुरानी बाइंडिंग के बजाय नई बाइंडिंग को परमाण्विक रूप से लौटाता है।
मौजूदा क्लाइंट अपरिवर्तित रहते हैं, क्योंकि acquire, renew, release और waiting प्रतिक्रियाएँ
अपनी पिछली संरचनाएँ बनाए रखती हैं।

यह सर्वर अनुबंध मानक OpenAI Codex `/status` को नहीं बदलता। मानक Codex वर्तमान में अपने
मॉडल प्रदाता और अंतर्निहित प्रमाणीकरण/खाता स्थिति की रिपोर्ट करता है, लेकिन मनमाना कस्टम
प्रदाता खाता मेटाडेटा रेंडर नहीं करता; भविष्य के किसी क्लाइंट एकीकरण को यह क्रिया कॉल करनी होगी और यह तय करना होगा कि
`connection.displayName` को कैसे प्रदर्शित किया जाए।

इसके बाद प्रत्येक प्रबंधित इन्फ़रेंस अनुरोध दोनों नियंत्रण हेडर प्रदान करता है:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

हर समर्थित अपस्ट्रीम प्रयास से ठीक पहले सटीक स्वामी, generation, सक्रिय कनेक्शन और प्रमाणीकृत API कुंजी को
फ़ेंस किया जाता है। किसी अन्य कुंजी के साथ स्वामी और generation को दोबारा चलाना तब भी विफल रहता है,
जब वह कुंजी उसी कनेक्शन की अनुमति देती हो। अपरिष्कृत स्वामियों को स्थायी रूप से संग्रहीत, लॉग, अनुरोध
स्नैपशॉट में बनाए रखा या अपस्ट्रीम अग्रेषित नहीं किया जाता।

अस्थायी प्रतिस्पर्धा HTTP `429` को `Retry-After` और निम्नलिखित के साथ लौटाती है:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

इस प्रतिक्रिया का अर्थ केवल यह है कि सामान्य पात्र सेट गैर-रिक्त था और प्रत्येक उपलब्ध उम्मीदवार
किसी अन्य स्वामी की सक्रिय लीज़ के अधीन था। असमर्थित मॉडल/प्रदाता, नीति असंगति, कूलडाउन, कोटा,
स्वास्थ्य और अन्य सामान्य पात्रता विफलताओं के लिए उनकी मौजूदा OmniRoute प्रतिक्रियाएँ बनी रहती हैं।

### `x-omniroute-compression`

कम्प्रेशन योजना का प्रति-अनुरोध ओवरराइड। सर्वोच्च प्राथमिकता — यह रूटिंग-कॉम्बो
ओवरराइड, सक्रिय प्रोफ़ाइल, ऑटो-ट्रिगर और पैनल के डिफ़ॉल्ट को पीछे छोड़ देता है। मान:

| मान           | प्रभाव                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `off`         | इस अनुरोध के लिए कोई कम्प्रेशन नहीं।                                                             |
| `default`     | पैनल से प्राप्त डिफ़ॉल्ट प्रोफ़ाइल (सक्रिय प्रोफ़ाइल को अनदेखा करती है)। लॉसी इंजन बंद रहते हैं। |
| `safe`        | केवल डीडुप्लिकेशन और व्हाइटस्पेस फोल्डिंग।                                                       |
| `allow-lossy` | इस अनुरोध के लिए ऑपरेटर योजना बनाए रखें, जिसमें सारांश और शैली पुनर्लेखन शामिल हैं।              |
| `engine:<id>` | सक्षम होने पर एकल इंजन, उदाहरण के लिए `engine:rtk`। उस इंजन के लिए प्रति-अनुरोध ऑप्ट-इन।         |
| `<combo>`     | एक नामित कॉम्बो, जिसका मिलान पहले नाम (केस-असंवेदी), फिर id के आधार पर किया जाता है।             |

टिप्पणियाँ:

- अज्ञात मानों को अनदेखा किया जाता है (अनुरोध कभी अस्वीकार नहीं किया जाता); समाधान सामान्य ऑपरेटर प्राथमिकता पर आगे बढ़ता है।
- यदि कई कॉम्बो का नाम समान है, तो नियतात्मक मिलान के लिए कॉम्बो **id** दें।
- जिस कॉम्बो का नाम `off` या `default` है, उसे नाम द्वारा नहीं चुना जा सकता (इन कीवर्ड की व्याख्या पहले की जाती है); ऐसे कॉम्बो को उसके id द्वारा संदर्भित करें।
- मास्टर कम्प्रेशन स्विच एक सख्त गेट है: जब कम्प्रेशन वैश्विक रूप से अक्षम हो, तो यह हेडर उसे सक्षम नहीं कर सकता।

लागू की गई योजना को प्रतिक्रिया हेडर में वापस प्रतिध्वनित किया जाता है:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

जहाँ `<source>`, `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` या `off` में से एक होता है।

## एम्बेडिंग्स

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

उपलब्ध प्रदाता: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI।

कैटलॉग आईडी `provider/model` होते हैं (उदाहरण: `jina-ai/jina-embeddings-v5-omni-small`)। रजिस्ट्री में मौजूद केवल Jina मॉडल आईडी (उदाहरण के लिए `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) भी रिज़ॉल्व होते हैं। Jina के embed/rerank/classify/segment पहले डैशबोर्ड के `jina-ai` क्रेडेंशियल्स का उपयोग करते हैं; `JINA_AI_API_KEY` केवल तभी फ़ॉलबैक है, जब कोई डैशबोर्ड कुंजी मौजूद न हो। `jina-reader` कार्ड केवल Reader / `r.jina.ai` (`POST /v1/web/fetch`) के लिए है और कभी भी एम्बेडिंग्स या रीरैंक उपलब्ध नहीं कराता।

मल्टीमॉडल समर्थन दर्शाने वाले रजिस्ट्री मॉडल अधिकतम 32 प्रदाता-निरपेक्ष संरचित
आइटम भी स्वीकार करते हैं। मीडिया आइटम के प्रकार `text`, `image`, `audio`, `video`, और `document` हैं। उनका मीडिया `source`
या तो `{"type":"url","url":"https://..."}` होता है या
`{"type":"base64","data":"...","media_type":"..."}`।

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
और फ़ैमिली एलियास `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina के नेटिव
EmbeddingsV5Request दस्तावेज़ भी स्वीकार करता है और उन्हें `https://api.jina.ai/v1/embeddings` पर **ज्यों का त्यों फ़ॉरवर्ड करता है**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

नेटिव `{ image | audio | video | pdf }` मान कोई सार्वजनिक HTTPS URL, `data:` URI, या रॉ
base64 हो सकते हैं। OmniRoute उन ऑब्जेक्ट्स को स्ट्रिंग में नहीं बदलता या नेटिव इमेज URL फ़ेच नहीं करता — Jina
सार्वजनिक मीडिया को स्वयं प्राप्त करता है। अतिरिक्त Jina फ़ील्ड (`task`, `normalized`, `truncate`, `embedding_type`)
फ़ॉरवर्ड किए जाते हैं। केवल-टेक्स्ट वाले Jina SKU अब भी गैर-टेक्स्ट दस्तावेज़ों को अस्वीकार करते हैं।

सुरक्षा और ट्रांसपोर्ट सीमाएँ:

- रिमोट मीडिया URL सार्वजनिक HTTPS होने चाहिए। कैनोनिकल `{type,source:url}` आइटम
  सर्वर-साइड पर फ़ेच किए जाते हैं (रीडायरेक्ट का पुनः सत्यापन, टाइमआउट, आकार सीमाएँ, सार्वजनिक DNS, कनेक्शन पिनिंग) और
  प्रदाता कॉल से पहले इनलाइन किए जाते हैं। Jina-नेटिव `{image:"https://..."}` आइटम समान सार्वजनिक-HTTPS जाँच के बाद
  ज्यों के त्यों फ़ॉरवर्ड किए जाते हैं; Jina URL को फ़ेच करता है।
- इनलाइन base64 मीडिया प्रति आइटम डिकोड किए हुए 8 MiB और पूरे अनुरोध में डिकोड किए हुए 16 MiB तक सीमित है।

प्रदाता रूपांतरण (कैनोनिकल आइटम कभी भी अपरिवर्तित रूप में फ़ॉरवर्ड नहीं किए जाते):

- Jina मल्टीमॉडल मॉडल: प्रत्येक शीर्ष-स्तरीय आइटम एक मोडैलिटी-कुंजी वाला ऑब्जेक्ट बनता है
  (`text` / `image` / `audio` / `video` / `pdf`), जिसमें इनलाइन मीडिया के लिए डेटा URI का उपयोग होता है; प्रत्येक
  शीर्ष-स्तरीय आइटम के लिए एक वेक्टर।
- Gemini Embedding 2 फ़ैमिली: एक शीर्ष-स्तरीय ऐरे, `content.parts` (`text` या `inline_data`) के साथ एकल नेटिव
  `models/{model}:embedContent` अनुरोध बन जाता है।
- llama.cpp (`llama-cpp/<model>`, स्थानीय सर्वर द्वारा लोड किया गया कोई भी मॉडल): कैनोनिकल `text` आइटम
  सामान्य स्ट्रिंग बन जाते हैं, और `image` / `audio` / `video` प्रत्येक एक
  `{"content": [part]}` ऑब्जेक्ट बनते हैं, जिसमें इनलाइन डेटा के साथ llama-server के चैट कंटेंट पार्ट्स (`image_url`,
  `input_audio`, जिसके फ़ॉर्मैट `wav` / `mp3` / `flac` हैं, `input_video`) का उपयोग होता है; प्रत्येक शीर्ष-स्तरीय
  आइटम के लिए एक वेक्टर। सर्वर को `--embedding --mmproj …` के साथ चलना चाहिए; प्रोजेक्टर के बिना यह
  स्वयं मीडिया को अस्वीकार कर देता है। `document` समर्थित नहीं है।
- स्पष्ट मोडैलिटी मेटाडेटा के बिना अज्ञात/डायनेमिक मॉडल HTTP 400 के साथ संरचित इनपुट को अस्वीकार करते हैं।

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

असमर्थित मॉडल/मोडैलिटी संयोजन आइटम को रूपांतरित करने के बजाय HTTP 400 लौटाते हैं। पुराने स्ट्रिंग/टोकन अनुरोधों पर गैर-इनपुट
एक्सटेंशन फ़ील्ड पहले की तरह अपरिवर्तित रूप में पास होते रहते हैं।

```bash
# सभी एम्बेडिंग मॉडल सूचीबद्ध करें
GET /v1/embeddings
```

## इमेज जनरेशन

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

उपलब्ध प्रोवाइडरों में OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (लोकल), ComfyUI (लोकल) शामिल हैं।

`n`, `data[]` में `n` इमेज लौटाता है। जिन प्रोवाइडरों की अपस्ट्रीम API प्रति कॉल एक इमेज लौटाती है
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), उनके लिए `n` अलग-अलग अपस्ट्रीम कॉल किए जाते हैं, जिनमें अधिकतम 4 कॉल एक साथ प्रगति पर रहते हैं। एक
निश्चित `seed` को कॉल इंडेक्स के अनुसार ऑफ़सेट किया जाता है (`seed`, `seed + 1`, …), ताकि इमेज अलग हों, लेकिन
दोबारा उसी तरह बनाई जा सकें। `n` की अधिकतम सीमा 10 है। यदि कोई भी कॉल विफल होता है, तो पूरा अनुरोध
विफल हो जाता है। फ़ैन-आउट फ़ॉर्मेट की सूची
`open-sse/handlers/imageGeneration/fanOut.ts` में `SINGLE_IMAGE_FANOUT_FORMATS` है।

ZenMux मौजूदा API-की कनेक्शन का पुनः उपयोग करता है और `zenmux/` या `zm/` प्रीफ़िक्स स्वीकार करता है:

- `zenmux/openai/gpt-image-2`, ZenMux की OpenAI Images API का उपयोग करता है। विकल्पों में `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, और `response_format` शामिल हैं।
- अन्य पब्लिशर, जैसे `zm/meta/muse-image-1.0`, ZenMux के Vertex AI `:predict`
  एंडपॉइंट का उपयोग करते हैं। `n`, `sampleCount` से; `aspect_ratio`, `aspectRatio` से; और `image_size`
  (`1K`, `2K`, `4K`), `sampleImageSize` से मैप होता है। पिक्सेल `size` केवल एक आस्पेक्ट रेशियो प्रदान करता है,
  गारंटीकृत पिक्सेल आयाम नहीं। समर्थित रेशियो, रिज़ॉल्यूशन और संख्या मॉडल के अनुसार अलग-अलग होते हैं।
- `zm/inclusionai/ming-image-0.1-design` अपने आयाम स्वयं चुनता है। `size`,
  `aspect_ratio`, और `image_size` को छोड़ दें; स्पष्ट मान देने पर HTTP 400 लौटता है। `output_format` के साथ
  PNG, JPEG, और WebP का अनुरोध किया जा सकता है।

यह इंटीग्रेशन टेक्स्ट-टू-इमेज जनरेशन का समर्थन करता है, रेफ़रेंस-इमेज संपादन का नहीं। Vertex
आउटपुट को `data[].b64_json` में सामान्यीकृत किया जाता है; `response_format: "url"` एक अपस्ट्रीम
HTTPS URL लौटाता है, या जब केवल इमेज बाइट उपलब्ध हों, तब एक base64 डेटा URL लौटाता है। खाली/फ़िल्टर किए गए आउटपुट
खाली सफलता के बजाय एक त्रुटि लौटाते हैं। मॉडल ऐक्सेस ZenMux अकाउंट पर निर्भर करता है।
[ZenMux की Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) और
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) देखें।

```bash
# सभी इमेज मॉडल सूचीबद्ध करें
GET /v1/images/generations
```

## डॉक्यूमेंट OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`, `provider/model` प्रीफ़िक्स के माध्यम से OCR प्रोवाइडर चुनता है; केवल मॉडल ID (उदाहरण के लिए,
`mistral-ocr-latest`) उसके रजिस्टर्ड प्रोवाइडर में रिज़ॉल्व होता है, और `model` न दिए जाने पर डिफ़ॉल्ट रूप से
Mistral (`mistral-ocr-latest`) का उपयोग होता है। रजिस्टर्ड प्रोवाइडर (`open-sse/config/ocrRegistry.ts`):

| प्रोवाइडर ID                  | मॉडल ID              | `model` का मान                                              | टिप्पणियाँ                                                                                                           |
| ----------------------------- | -------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (या केवल `mistral-ocr-latest`) | सिंक्रोनस — रिस्पॉन्स सीधे एकमात्र अपस्ट्रीम कॉल से लौटाया जाता है।                                                  |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                 | एसिंक्रोनस अपस्ट्रीम (`analyze` + पोल) — नीचे देखें।                                                                 |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                     | सिंक्रोनस, Vertex AI के `openapi/chat/completions` पार्टनर एंडपॉइंट के माध्यम से — प्रमाणीकरण/URL के लिए नीचे देखें। |

तीनों प्रोवाइडर समान Mistral-आकार वाली बॉडी में जवाब देते हैं:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence पोल फ़्लो

Azure Document Intelligence की `analyze` API एसिंक्रोनस है: प्रारंभिक अनुरोध बॉडी के बजाय
`Operation-Location` हेडर लौटाता है, और परिणाम के लिए पोल करना आवश्यक होता है। हैंडलर
(`open-sse/handlers/ocr.ts`) उस URL को हर सेकंड अधिकतम 30 प्रयासों तक पोल करता है, किसी गैर-`ok`
पोल रिस्पॉन्स या `"failed"` स्थिति पर तुरंत विफल हो जाता है (पोलिंग जारी नहीं रखता), और यदि प्रयासों की
सीमा समाप्त होने के बाद भी ऑपरेशन चल रहा हो, तो `504` लौटाता है। कॉलर को लौटाए जाने से पहले अंतिम Azure रिस्पॉन्स को
Mistral द्वारा उपयोग किए जाने वाले समान `pages`/`markdown` आकार में सामान्यीकृत किया जाता है,
इसलिए क्लाइंट कोड को प्रोवाइडर के लिए अलग से विशेष प्रबंधन करने की आवश्यकता नहीं होती।

### Vertex AI DeepSeek OCR प्रमाणीकरण और एंडपॉइंट रिज़ॉल्यूशन

`vertex-deepseek-ocr` उसी Vertex AI प्रमाणीकरण का पुनः उपयोग करता है जिसका OmniRoute पहले से ही
चैट/इमेज ट्रैफ़िक के लिए समर्थन करता है (`open-sse/executors/vertex.ts`): कनेक्शन की API की या तो
Service Account JSON क्रेडेंशियल होती है (जिसे JWT-bearer फ़्लो के माध्यम से अल्पकालिक OAuth ऐक्सेस टोकन के लिए
एक्सचेंज किया जाता है) या पहले से जारी किया गया OAuth ऐक्सेस टोकन होता है, जिसे ज्यों का त्यों उपयोग किया जाता है। अपस्ट्रीम एंडपॉइंट URL, Vertex का
सामान्य `openapi/chat/completions` पार्टनर एंडपॉइंट है, जिसे कनेक्शन के प्रोजेक्ट और
रीजन से बनाया जाता है — स्पष्ट `providerSpecificData.project`/`providerSpecificData.region` को हमेशा प्राथमिकता दी जाती है;
अन्यथा प्रोजेक्ट को Service Account JSON के `project_id` से प्राप्त किया जाता है और रीजन
डिफ़ॉल्ट रूप से `us-central1` होता है। दोनों रिज़ॉल्यूशन `open-sse/handlers/ocr.ts`
में होते हैं (`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), जिन्हें
`handleOcr` को डिस्पैच करने से पहले `src/app/api/v1/ocr/route.ts` द्वारा उपयोग किया जाता है।

## मॉडल सूचीबद्ध करें

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ सभी चैट, एम्बेडिंग और इमेज मॉडल + संयोजन OpenAI प्रारूप में लौटाता है
```

### मॉडल की कीमतें (`pricing`)

जब OmniRoute को मॉडल की कीमत ज्ञात होती है, तो प्रविष्टि में एक `pricing` ऑब्जेक्ट होता है। कीमत उस मूल्य निर्धारण तालिका से आती है जिसका उपयोग लागत लेखांकन करता है: अंतर्निहित डिफ़ॉल्ट, सिंक की गई कीमतें और `/api/pricing` के माध्यम से सेट किए गए ओवरराइड। ये सूची कीमतें हैं, इसलिए सदस्यता प्रदाता भी प्रति-टोकन कीमत दिखाते हैं।

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| फ़ील्ड                                                          | इकाई                           | टिप्पणियाँ                                                                                                                                                         |
| --------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | प्रति टोकन USD, दशमलव स्ट्रिंग | OpenRouter-संगत, कभी भी घातांक संकेतन में नहीं। दोनों कैश फ़ील्ड केवल तभी दिखाई देते हैं जब कैश की कोई कीमत हो।                                                    |
| `input`, `output`, `cached`, `cache_creation`                   | प्रति 1M टोकन USD, संख्या      | पुराने कैटलॉग संस्करणों के फ़ील्ड, मौजूदा क्लाइंट के लिए बनाए रखे गए हैं। मूल्य निर्धारण पंक्ति में मौजूद होने पर `reasoning` और `long_context` भी दिखाई देते हैं। |

- **संयोजनों** में उनके पहले दृश्यमान लक्ष्य की कीमत होती है। अंतर्निहित `auto/*` संयोजन अनुरोध के समय
  लक्ष्य चुनते हैं, इसलिए उनमें कोई `pricing` नहीं होता।
- **निःशुल्क मॉडल** अपनी कीमत शून्य होने पर `"0"` (और `0`) दिखाते हैं। जिस मॉडल की कोई मूल्य निर्धारण पंक्ति
  नहीं है, वह भी `"0"` दिखाता है, यदि कैटलॉग उसे निःशुल्क (`free: true`) चिह्नित करता है या अंतर्निहित निःशुल्क-मॉडल
  कैटलॉग उसे सूचीबद्ध करता है।
- **अज्ञात कीमत:** प्रविष्टि में कोई `pricing` कुंजी नहीं होती।
- **क्रेडिट-आधारित मीटरिंग वाले प्रदाता** (जैसे Kiro) प्रति टोकन के बजाय प्रति अनुरोध बिल करते हैं। उनकी
  प्रविष्टियाँ पहले वाले संख्यात्मक प्रति-1M फ़ील्ड बनाए रखती हैं और उनमें प्रति-टोकन स्ट्रिंग फ़ील्ड नहीं होते।
- **वेरिएंट** (reasoning-effort ids, no-thinking aliases, discovery और gateway mirrors)
  उस मॉडल की कीमत कॉपी करते हैं जिस पर वे रूट करते हैं।
- फ़ील्ड में केवल आधार दरें होती हैं। लॉन्ग-कॉन्टेक्स्ट टियर (संख्यात्मक `long_context` फ़ील्ड) और
  सर्विस-टियर गुणक (उदाहरण के लिए Codex fast या flex) `prompt` या
  `completion` को नहीं बदलते।
- ऑब्जेक्ट हर प्रमाणीकरण शैली के लिए समान होता है, जिसमें `x-api-key` और
  `anthropic-version` वाला Anthropic-शैली का अनुरोध भी शामिल है (प्रतिक्रिया `{ "object": "list",
"data": [...] }` ही रहती है)। कार्यान्वयन: `src/app/api/v1/models/catalogPricing.ts`।

### मॉडल id प्रीफ़िक्स (`?prefix=`)

अधिकांश मॉडल **प्रदाता प्रीफ़िक्स** के अंतर्गत प्रस्तुत किए जाते हैं। आपको कौन-सा प्रीफ़िक्स मिलेगा, यह
`MODELS_CATALOG_PREFIX_MODE` फ़ीचर फ़्लैग द्वारा नियंत्रित होता है और इसे क्वेरी पैरामीटर के साथ **प्रति अनुरोध**
ओवरराइड किया जा सकता है — यह उस क्लाइंट के लिए उपयोगी है जो बाकी सभी के लिए सर्वर-व्यापी
सेटिंग बदले बिना एक साफ़ सूची चाहता है:

```bash
GET /v1/models?prefix=alias        # प्रति मॉडल एक id — संक्षिप्त उपनाम प्रीफ़िक्स
GET /v1/models?prefix=dual         # दोनों रूप (सर्वर डिफ़ॉल्ट)
GET /v1/models?prefix=canonical    # केवल पूर्ण provider-id प्रीफ़िक्स
```

| मोड         | उत्पन्न करता है                                          | टिप्पणियाँ                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **और** `claude/claude-sonnet-4-6` | **डिफ़ॉल्ट।** दोनों ids एक ही मॉडल पर रूट करते हैं; इसे इसलिए बनाए रखा गया है ताकि किसी भी रूप को हार्डकोड करने वाले क्लाइंट कॉन्फ़िग काम करते रहें। इससे कैटलॉग लगभग दोगुना हो जाता है।          |
| `alias`     | `cc/claude-sonnet-4-6`                                   | प्रति मॉडल एक प्रविष्टि। विशिष्ट उपनाम के बिना प्रदाता भी अपनी प्रविष्टि उत्पन्न करते हैं, इसलिए कुछ भी नहीं छूटता।                                                                               |
| `canonical` | `claude/claude-sonnet-4-6`                               | पूर्ण provider-id प्रीफ़िक्स के अंतर्गत प्रति मॉडल एक प्रविष्टि। विशिष्ट उपनाम के बिना प्रदाता (जैसे `antigravity/…`, `agy/…`) भी यहाँ अपना एकमात्र id उत्पन्न करते हैं, इसलिए कुछ भी नहीं छूटता। |

`dual`-मोड मिरर को क्वेरी पैरामीटर के बिना भी पहचाना जा सकता है: इसमें प्राथमिक id की ओर संकेत करने वाला `parent`
फ़ील्ड होता है।

मॉडल पिकर रेंडर करने वाले क्लाइंट को `?prefix=alias` का अनुरोध करना चाहिए — यही
[OmniCopilot VS Code एक्सटेंशन](../guides/VSCODE-COPILOT.md) करता है।

### डिस्कवरी फ़िल्टर (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` वैकल्पिक डिस्कवरी फ़िल्टर स्वीकार करता है। इनमें से किसी के बिना प्रतिक्रिया
अपरिवर्तित रहती है। ये उस कैटलॉग को सीमित करते हैं जिसे कॉलर पहले से देख सकता है (API-key अनुमतियाँ पहले लागू होती हैं),
और ये OpenAI-शैली की `limit` / `after` पेजिंग से पहले चलते हैं:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # सूचीबद्ध प्रत्येक क्षमता true होनी चाहिए
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # कैटलॉग `type`; इसके बिना पंक्तियाँ `chat` होती हैं
GET /v1/models?q=sonnet&limit=10                           # id या नाम पर केस-असंवेदनशील मिलान
```

| पैरामीटर      | मान                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | गैर-ऋणात्मक पूर्णांक, जिसकी तुलना `context_length` से की जाती है                                    |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 वर्ण                                                                                          |

कोई अज्ञात मान, या ऐसा `min_context` जो गैर-ऋणात्मक पूर्णांक नहीं है (उदाहरण के लिए `1.5`),
HTTP `400` लौटाता है और संदेश में मान्य मानों की सूची होती है। कार्यान्वयन:
`src/app/api/v1/models/catalogFilters.ts`।

### मॉडल शॉर्टलिस्ट (`POST /v1/models/query`)

`POST /v1/models/query` उसी कैटलॉग से एक छोटी, नियतात्मक सूची लौटाता है, जिसमें `GET /v1/models`
के समान प्रमाणीकरण और प्रति-कुंजी दृश्यता होती है:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

प्रत्येक फ़ील्ड वैकल्पिक है। `capabilities` और `exclude` एक ऐरे या कॉमा से अलग की गई स्ट्रिंग स्वीकार करते हैं;
`max_output` की तुलना `max_output_tokens` से की जाती है। परिणामों को पहले `owned_by`, फिर `id` के अनुसार क्रमबद्ध किया जाता है।
`limit` का डिफ़ॉल्ट मान `20` है और `100` से अधिक मानों को `100` तक सीमित कर दिया जाता है। अमान्य JSON, कोई अज्ञात
फ़ील्ड या अमान्य मान HTTP `400` लौटाता है।

### अलग-अलग छिपाए गए चैट मॉडल

अपने प्रोवाइडर पेज पर **छिपा हुआ** चिह्नित मॉडल को कैटलॉग से बाहर रखा जाता है और स्पष्ट रूप से
अनुरोध किए जाने पर HTTP `404` / `model_not_found` के साथ अस्वीकार कर दिया जाता है। जाँच में निर्धारित
प्रोवाइडर और मॉडल का उपयोग किया जाता है, जिसमें प्रोवाइडर एलियास, संगत-प्रोवाइडर नोड प्रीफ़िक्स और
कनेक्शन डिफ़ॉल्ट शामिल हैं। कोई कॉम्बो छिपे हुए लक्ष्यों को छोड़ देता है और किसी दृश्यमान सहोदर का उपयोग कर सकता है; जब कोई
निष्पादन योग्य लक्ष्य शेष नहीं रहता, तो यह वही त्रुटि कोड लौटाता है। मॉडल को फिर से दृश्यमान बनाने का प्रभाव अगले
अनुरोध पर लागू होता है। केवल-इमेज दृश्यता ओवरराइड समान ID वाले चैट मॉडल को नहीं छिपाते हैं।

यह व्यक्तिगत मॉडल सेटिंग
[मॉडल एक्सपोज़र अनुमति/निषेध सूचियों](../routing/MODEL_EXPOSURE_LIST.md) से अलग है, जो स्पष्ट डिस्पैच को बनाए रखते हुए कैटलॉग
प्रदर्शन और ऑटो-रूटिंग उम्मीदवारों को फ़िल्टर करती हैं। API-कुंजी मॉडल
अनुमतियाँ स्वतंत्र रूप से लागू होती रहती हैं। डिफ़ॉल्ट कैटलॉग प्रीफ़िक्स मोड `dual` ही रहता है।

### बिना-थिंकिंग वाले मॉडल वेरिएंट

थिंकिंग-सक्षम Claude मॉडलों के लिए, `/v1/models` एक **बिना-थिंकिंग** वाला वेरिएंट भी प्रदर्शित करता है, जिसकी id के आगे `claude-3-omniroute-no-thinking/` प्रीफ़िक्स लगा होता है:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

इस id को चुनने पर (उदाहरण के लिए ऐसी Claude Code कॉन्फ़िगरेशन में जो हमेशा `thinking` ब्लॉक जोड़ती है), यह रीजनिंग को दबाते हुए वास्तविक `<provider>/<model>` पर वापस रिज़ॉल्व होता है—`/v1/messages` पथ पर `thinking:{type:"disabled"}`, या `/v1/chat/completions` पथ पर `reasoning`/`reasoning_effort` फ़ील्ड हटा दिए जाते हैं। यह वेरिएंट केवल उन Claude-परिवार मॉडलों के लिए सूचीबद्ध होता है जो थिंकिंग का समर्थन करते हैं **और** `disabled` का पालन करते हैं (इसलिए, उदाहरण के लिए, केवल-अनुकूली मॉडल जो `disabled` को अस्वीकार करते हैं, शामिल नहीं किए जाते)। ऑपरेटर `ModelSpec.noThinkingAlias` के माध्यम से प्रत्येक मॉडल के लिए इस वेरिएंट को बलपूर्वक चालू या बंद कर सकते हैं।

## ElevenLabs ऑडियो जनरेशन

अपनी ElevenLabs API कुंजी के साथ OmniRoute में एक `elevenlabs` प्रोवाइडर कनेक्शन कॉन्फ़िगर करें।
क्लाइंट अपनी **OmniRoute** कुंजी (`Authorization: Bearer $OMNIROUTE_API_KEY`) से प्रमाणित होते हैं;
गेटवे संग्रहीत प्रोवाइडर कुंजी को `xi-api-key` के रूप में प्रदान करता है। गेटवे बेयरर टोकन के रूप में कभी भी ElevenLabs कुंजी न भेजें।

| विधि | पाथ                         | प्रतिक्रिया                               | API कुंजी एंडपॉइंट श्रेणी |
| ---- | --------------------------- | ----------------------------------------- | ------------------------- |
| POST | `/v1/sound-generation`      | नेटिव ऑडियो बाइट्स                        | `elevenlabs`              |
| POST | `/v1/music`                 | नेटिव ऑडियो बाइट्स                        | `music`                   |
| POST | `/v1/music/stream`          | स्ट्रीमिंग ऑडियो बाइट्स                   | `music`                   |
| POST | `/v1/music/detailed`        | नेटिव मल्टीपार्ट ऑडियो और कंपोज़िशन प्लान | `music`                   |
| POST | `/v1/music/detailed/stream` | नेटिव SSE मेटाडेटा और ऑडियो चंक           | `music`                   |
| POST | `/v1/music/plan`            | JSON कंपोज़िशन प्लान                      | `music`                   |

ये एंडपॉइंट मौजूदा `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` और `/v1/speech-to-text` रूट के पूरक हैं। नेटिव JSON फ़ील्ड
और `output_format` तथा `enable_logging` जैसे क्वेरी पैरामीटर संरक्षित रहते हैं।
`/v1/music/detailed` प्रतिक्रियाएँ अपनी मल्टीपार्ट सीमाएँ बनाए रखती हैं; उन्हें मल्टीपार्ट के रूप में पार्स करें।
`/v1/music/detailed/stream`, SSE इवेंट में कंपोज़िशन मेटाडेटा और base64 ऑडियो चंक के साथ `text/event-stream` लौटाता है। सभी छह रूट CORS प्रीफ़्लाइट का समर्थन करते हैं।

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# एक छोटा ध्वनि प्रभाव। अवधि: 0.5 से 30 सेकंड।
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# संगीत की अवधि मिलीसेकंड में व्यक्त की जाती है: 3000 से 600000।
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

इंक्रीमेंटल ऑडियो डिलीवरी के लिए समान JSON बॉडी के साथ `/v1/music/stream` का उपयोग करें। कंपोज़िशन
`prompt` या `composition_plan` में से ठीक एक को स्वीकार करता है; `/v1/music/plan` के लिए `prompt`
आवश्यक है और यह वैकल्पिक रूप से `source_composition_plan` स्वीकार करता है। नेटिव स्कीमा अतिरिक्त
प्रोवाइडर फ़ील्ड को संरक्षित रखते हैं, ताकि कंपोज़िशन-प्लान वर्ज़न और फ़ाइन-ट्यूनिंग विकल्प ElevenLabs तक पहुँच सकें।

एकीकृत `/v1/music/generations` एंडपॉइंट `elevenlabs/music_v1`,
`elevenlabs/music_v2` और `elevenlabs/music_v2_5` को भी स्वीकार करता है। किसी सक्रिय ElevenLabs कनेक्शन के साथ,
ये मॉडल संगीत कैटलॉग द्वारा उपलब्ध कराए जाते हैं। यह एंडपॉइंट
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` लौटाता है। इसका `duration` फ़ील्ड
सेकंड में होता है और `music_length_ms` पर मैप होता है; स्पष्ट रूप से दिया गया `music_length_ms` प्राथमिकता लेता है।
`instrumental`, `force_instrumental` पर मैप होता है, जिसमें नेटिव फ़ील्ड को प्राथमिकता मिलती है।
स्ट्रीमिंग के लिए नेटिव स्ट्रीमिंग एंडपॉइंट और केवल कंपोज़िशन प्लान द्वारा संचालित अनुरोधों के लिए नेटिव कंपोज़िशन एंडपॉइंट का उपयोग करें।

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

अपस्ट्रीम कॉल से पहले एंडपॉइंट, मॉडल, बजट और कनेक्शन संबंधी प्रतिबंध लागू होते हैं। नेटिव
रूट अपस्ट्रीम स्थिति कोड और त्रुटि बॉडी को बिना बदलाव के लौटाते हैं, जिसमें प्लान
प्रतिबंध के लिए `402` और कोटा सीमा के लिए `429` शामिल हैं। उपलब्ध होने पर `character-cost`, `song-id`, `request-id` और `retry-after`
हेडर संरक्षित रहते हैं। निःशुल्क क्रेडिट बैलेंस प्रत्येक संगीत मॉडल, आउटपुट फ़ॉर्मेट या API सुविधा तक पहुँच की गारंटी नहीं देता: ElevenLabs प्रत्येक अनुरोध के लिए पात्रता तय करता है।
एकीकृत एंडपॉइंट OmniRoute के सामान्यीकृत त्रुटि एनवलप में त्रुटि स्थिति कोड संरक्षित रखता है।

अपस्ट्रीम अनुबंध: [ध्वनि प्रभाव](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[संगीत कंपोज़िशन](https://elevenlabs.io/docs/api-reference/music/compose) और
[स्ट्रीमिंग संगीत विवरण](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)।

```bash
# रीरैंक (क्लाउड रजिस्ट्री प्रदाता, या "<prefix>/<model>" के रूप में OpenAI-संगत प्रदाता नोड)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina वर्गीकरण (Foundation API क्रेडेंशियल्स)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina सेगमेंटर
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina खोज (s.jina.ai; प्रदाता उपनाम: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# मॉडरेशन
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (या अनुरोधित प्रारूप) बॉडी लौटाता है
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS के लिए language और voice आवश्यक हैं: `language` का डिफ़ॉल्ट "en" है; अनुपस्थित
# voice या OpenAI का मानक voice नाम (alloy, nova, …) "Adrian" बन जाता है
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# इमेज संपादन (मल्टीपार्ट)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# वीडियो / संगीत जनरेशन (प्रदाता-प्रीफ़िक्स वाला मॉडल id)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **रीरैंक प्रोवाइडर नोड्स:** `POST /v1/rerank` अनुरोधों को OpenAI-संगत प्रोवाइडर नोड्स
> (oMLX, vLLM, Infinity, किसी गेटवे के पीछे TEI, …) पर भी रूट करता है, जिन्हें `<node-prefix>/<model>` के रूप में संबोधित किया जाता है। लूपबैक
> नोड्स (`localhost`, `127.0.0.1`, `172.16.0.0/12`) हमेशा पात्र होते हैं, और वे होस्टनेम भी पात्र होते हैं जिन्हें
> ऑपरेटर `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` में सूचीबद्ध करता है (उदाहरण के लिए कोई Docker/Compose सेवा नाम, जैसे
> `http://reranker:8080/v1`; इन्हें सीधे कॉल किया जाता है, कभी भी `HTTP(S)_PROXY` या किसी
> कनेक्शन के पिन किए गए प्रॉक्सी के माध्यम से नहीं)। किसी अन्य
> होस्ट पर मौजूद नोड — जैसे कोई LAN मशीन या Tailscale पीयर — केवल तभी पात्र होते हैं, जब ऑपरेटर
> `RERANK_REMOTE_PROVIDER_NODES` फ़ीचर फ़्लैग सक्षम करता है **और** नोड का बेस URL प्रोवाइडर की
> आउटबाउंड URL नीति (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) को पूरा करता है।
> मेमोरी इंजन का रीरैंक चरण इस रूट को
> लूपबैक के माध्यम से कॉल करता है, इसलिए यही नियम Memory सेटिंग्स में `rerankProviderModel` पर लागू होता है।
>
> **स्थानीय सर्वर प्रारूप:** नोड को `<base>/v1/rerank` पर और 404 मिलने पर `<base>/rerank`
> (Infinity, TEI) पर कॉल किया जाता है। अपस्ट्रीम बॉडी में Cohere/OpenAI वर्तनी (`documents`,
> `return_documents`) और TEI वर्तनी (`texts`, `return_text`) दोनों होती हैं, और अपस्ट्रीम प्रतिक्रिया को
> Cohere एनवेलप में सामान्यीकृत किया जाता है: TEI का बिना एनवेलप वाला `[{index, score, text}]`, हल्के गेटवे से मिला `{results: [{index, score}]}`
> और Voyage-शैली का `{data: [...]}`, सभी क्लाइंट को
> `{results: [{index, relevance_score, document?}]}` के रूप में लौटाए जाते हैं, स्कोर के अनुसार क्रमबद्ध और `top_n` तक सीमित।
>
> **प्रोवाइडर-नोड खोज:** किसी OpenAI-संगत प्रोवाइडर नोड पर मौजूद मॉडल, नोड प्रीफ़िक्स के अंतर्गत `GET /v1/models`
> में दिखाई देते हैं। जिन पंक्तियों में कोई एंडपॉइंट मेटाडेटा नहीं होता (स्थानीय `/v1/models` सूचियों में सामान्य),
> वे नोड का `apiType` इनहेरिट करती हैं, इसलिए किसी `embeddings` नोड के मॉडल `type: "embedding"` और किसी
> `rerank` नोड के मॉडल चैट पर डिफ़ॉल्ट होने के बजाय `type: "rerank"` होते हैं; सिंक की गई या मैन्युअल रूप से जोड़ी गई पंक्ति पर स्पष्ट
> `supportedEndpoints` को फिर भी प्राथमिकता मिलती है।

गैर-सत्र कॉलर के लिए अस्वीकृत होती है। `GET /v1/files` किसी अनाम कॉलर — और ऐसी दी गई कुंजी जिसका
समाधान नहीं होता — को `REQUIRE_API_KEY=false` होने पर भी प्रत्येक टेनेंट की
फ़ाइलें सूचीबद्ध करने के बजाय `401` के साथ अस्वीकार करता है (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)।

| POST   | `/v1/batches`             | बैच बनाएँ — बॉडी को `v1BatchCreateSchema` (`input_file_id`, `endpoint`, `completion_window`) द्वारा सत्यापित किया जाता है |

| GET  | `/v1/search/analytics` | प्रत्येक प्रदाता के हिट/लेटेंसी/कैश आँकड़े                                                                    |

**प्रमाणीकरण:** Bearer API कुंजी (`extractApiKey` + `isValidApiKey`)। खोज नीति `enforceApiKeyPolicy` के माध्यम से लागू की जाती है।

### Exa और Tavily के `provider_options`

Exa और Tavily प्रदाता-विशिष्ट फ़ील्ड को नेमस्पेसयुक्त संग्रह से पढ़ते हैं:
`provider_options.exa` (या `provider_options["exa-search"]`) और `provider_options.tavily`
(या `provider_options["tavily-search"]`)। केवल नीचे दी गई कुंजियाँ अग्रेषित की जाती हैं। प्रत्येक की
जाँच `open-sse/handlers/search/providerOptionsPassthrough.ts` में उसके अपने Zod स्कीमा के विरुद्ध की जाती है,
और गलत प्रकार वाली कुंजी हटा दी जाती है। प्रमाणीकरण, आधार URL,
`stream` और `outputSchema` सहित किसी भी अन्य कुंजी को अनदेखा किया जाता है। अन्य प्रदाताओं द्वारा उपयोग की जाने वाली सपाट कुंजियाँ (`cx`, `depth`, ...)
पहले की तरह काम करती हैं।

| प्रदाता | शीर्ष-स्तरीय फ़ील्ड                                                                                                                                                                                                                                                                                                                                                       | नेस्टेड                                                                                                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (सपाट प्रिमिटिव), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                               | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` को डिफ़ॉल्ट `{ text: true, highlights: true }` के ऊपर मर्ज किया जाता है |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                              |

सामान्य फ़ील्ड हमेशा प्राथमिकता लेते हैं: `query`, `max_results`, `filters` (डोमेन), `country` और
`search_type` से व्युत्पन्न विषय। Exa पर, `search_type: "news"` से `category: "news"` बना रहता है।
Tavily `search_type: "finance"` (`topic: "finance"`) को भी स्वीकार करता है।

सामान्य `time_range` अब दोनों प्रदाताओं तक पहुँचता है: Exa को `startPublishedDate` (ISO
टाइमस्टैम्प) मिलता है और Tavily को `start_date` (`YYYY-MM-DD`) मिलता है। `provider_options`
में दी गई स्पष्ट तारीख मैप की गई तारीख को ओवरराइड करती है।

Exa परिणाम `provider_raw` में `id`, `highlight_scores`, `summary`, `subpages`, `entities` और `extras`
को बनाए रखते हैं। Tavily परिणाम `images` और `favicon` को बनाए रखते हैं।

लागत लेखांकन अभी भी सपाट रजिस्ट्री `costPerQuery` है। Tavily में
`search_depth: "advanced"` के लिए प्रति कॉल अधिक क्रेडिट बिल किए जाते हैं, और यह अंतर
`usage.search_cost_usd` में प्रतिबिंबित नहीं होता है।

## Web Fetch API

कॉन्फ़िगर किए गए web-fetch प्रदाता (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) के माध्यम से किसी URL से सामग्री निकालें।

Parallel Extract (`parallel-search`, वही API कुंजी जो Parallel Search की है) केवल Markdown लौटाता है — कोई भी अन्य `format` होने पर `400` मिलता है — और सामग्री को 100,000 वर्णों तक सीमित करता है। जब लक्षित पृष्ठ को ही एक्सट्रैक्ट नहीं किया जा सकता, तो अपस्ट्रीम इसे HTTP 200 के भीतर रिपोर्ट करता है; OmniRoute इसे एक निश्चित संदेश के साथ `422` के रूप में प्रस्तुत करता है।

| विधि | पथ              | विवरण                                                                           |
| ---- | --------------- | ------------------------------------------------------------------------------- |
| POST | `/v1/web/fetch` | URL फ़ेच/स्क्रैप करें — बॉडी को `v1WebFetchSchema` द्वारा सत्यापित किया जाता है |

**प्रमाणीकरण:** Bearer API कुंजी (`extractApiKey` + `isValidApiKey`)। नीति `enforceApiKeyPolicy` के माध्यम से लागू की जाती है।

**कोटा-सजग फ़ॉलबैक (#8297):** जब कोई स्पष्ट `provider` नहीं दिया जाता, तो पूल
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) को निश्चित
प्राथमिकता क्रम (पहले भरें) में आज़माया जाता है — दर-सीमित लेकिन कॉन्फ़िगर किए गए प्रदाता को अनुरोध तुरंत समाप्त करने के बजाय छोड़ दिया जाता है, और पुनः प्रयास योग्य/कोटा-संबंधी अपस्ट्रीम विफलता
(HTTP 429 हमेशा; Firecrawl/Tavily/TinyFish के कोटा-शैली वाले निःशुल्क टियर के लिए 402/403 —
Jina Reader के लिए नहीं, और सामान्य 400 खराब अनुरोध के लिए कभी नहीं) अनुरोध के समय अगले ऐसे प्रदाता पर चली जाती है जिसे अभी तक नहीं आज़माया गया है और जिसके क्रेडेंशियल उपलब्ध हैं। जब पूल के सभी प्रदाता
समाप्त हो जाते हैं, तो एंडपॉइंट पिछले सामान्य `400` के बजाय एकल `429` (`Retry-After`
हेडर के साथ) लौटाता है। जब स्पष्ट `provider` का अनुरोध किया जाता है, तो **कोई** मूक फ़ॉलबैक नहीं होता — दर-सीमित या विफल स्पष्ट प्रदाता अपनी स्वयं की त्रुटि प्रस्तुत करता है (दर-सीमित होने पर `429`, अन्यथा अपस्ट्रीम
स्थिति)।

## WebSocket स्ट्रीमिंग

```bash
GET /v1/ws?handshake=1
```

WebSocket अपग्रेड हैंडशेक को सत्यापित करता है और वायर प्रोटोकॉल के उदाहरण संदेश (`request`, `cancel`) लौटाता है। वास्तविक WS फ़्रेम, Next.js रूट तालिका के बाहर बंडल किए गए WS सर्वर द्वारा संभाले जाते हैं।

**प्रमाणीकरण:** हैंडशेक के दौरान Bearer API कुंजी।

### WebSocket के माध्यम से Responses API (केवल codex)

```bash
# HTTP API वाला ही होस्ट:पोर्ट (डिफ़ॉल्ट 20128); कनेक्शन अपग्रेड करें:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (या: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# पहला फ़्रेम response.create होना अनिवार्य है:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket प्रॉक्सी **विशेष रूप से `codex`** (ChatGPT
बैकएंड) से जुड़ी है। यह API/डैशबोर्ड वाले पोर्ट पर ही `/v1/responses`,
`/responses`, और `/api/v1/responses` पथों पर सुनती है। पहले `response.create` फ़्रेम पर यह
आंतरिक `codex-responses-ws` ब्रिज के माध्यम से प्रमाणीकरण + तैयारी करती है, एक
codex OAuth कनेक्शन चुनती है, और `wreq-js` ट्रांसपोर्ट के माध्यम से `wss://chatgpt.com/backend-api/codex/responses`
तक टनल बनाती है। **गैर-codex मॉडल अस्वीकार कर दिए जाते हैं** (`codex_ws_provider_required`)।
कोटा-शेयर रूटिंग के लिए `model: "qtSd/<group>/codex/<model>"` का उपयोग करें। इसे
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` में कार्यान्वित किया गया है।

**प्रमाणीकरण:** हैंडशेक के दौरान Bearer API कुंजी। बंडल किया गया HTTP सर्वर (`server-ws.mjs`)
सक्रिय एंट्रीपॉइंट होना चाहिए (जब `app/server-ws.mjs` मौजूद हो, तो डिफ़ॉल्ट रूप से यही होता है)।

#### मॉडल id: मूल ChatGPT id का उपयोग करें (`codex/` प्रीफ़िक्स के बिना)

जब `supports_websockets = true` होता है, तो OpenAI **Codex CLI** क्लाइंट-साइड पर मॉडल नाम को सत्यापित करता है और
`codex/gpt-5.5` जैसे **प्रदाता-प्रीफ़िक्स वाले ids को अस्वीकार करता है**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)। **मूल** id (उदाहरण के लिए `gpt-5.5`) भेजें। OmniRoute का ब्रिज
केवल codex के लिए है, इसलिए यह अपस्ट्रीम तक टनल बनाने से पहले मूल id को codex मॉडल के रूप में पुनः हल करता है
(`resolveCodexWsModelInfo`) — भले ही मूल
`gpt-5.5` अन्यथा HTTP पर किसी दूसरे प्रदाता को रूट हो जाता।

#### OpenAI Codex CLI को कॉन्फ़िगर करना

`~/.codex/config.toml` में WebSocket समर्थन वाला कस्टम प्रदाता जोड़कर Codex CLI को OmniRoute की ओर इंगित करें (मौजूदा कॉन्फ़िगरेशन को प्रभावित करने से बचने के लिए अलग `CODEX_HOME` का उपयोग करें):

```toml
model = "gpt-5.5"                 # मूल id — "codex/gpt-5.5" नहीं
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # अंत में स्लैश नहीं; WS URL इससे प्राप्त होता है (प्रोडक्शन में https/wss का उपयोग करें)
wire_api = "responses"                    # फ़रवरी 2026 से एकमात्र समर्थित मान
supports_websockets = true                # Responses-over-WS ट्रांसपोर्ट सक्षम करता है
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API कुंजी (Bearer) रखता है
```

```bash
export OMNIROUTE_API_KEY=sk-...           # एक OmniRoute API कुंजी (यदि REQUIRE_API_KEY=false हो तो कोई भी कुंजी)
codex exec "Responda apenas: PONG"
```

CLI, `base_url + /responses` को WebSocket में अपग्रेड करता है और OmniRoute इसे
चुने गए codex OAuth कनेक्शन तक टनल करता है। स्थानीय
सर्वर के विरुद्ध शुरू से अंत तक सत्यापित: ChatGPT `codex.rate_limits` + `response.created` लौटाता है और
पूर्णता को स्ट्रीम करता है।

## स्वयं-सेवा उपयोग (`/api/usage/om-usage`)

कोई भी API कुंजी **अपने स्वयं के** उपयोग और कोटा को पढ़ सकती है — प्रबंधन प्रमाणीकरण की आवश्यकता नहीं है। यह वह एंडपॉइंट है जिसका उपयोग कोई
क्लाइंट (CLI, OmniCopilot पैनल) कुंजी धारक को उसका व्यय दिखाने के लिए करता है।

```bash
# टेक्स्ट प्रारूप (ऐतिहासिक अनुबंध — टर्मिनल के लिए सादा टेक्स्ट)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# संरचित प्रारूप — जिसका उपयोग UI करता है
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

कुंजी के लिए **`allowUsageCommand`** सक्षम होना चाहिए (डिफ़ॉल्ट रूप से बंद — डैशबोर्ड का API-कुंजी
प्रबंधक इसे प्रत्येक कुंजी के लिए टॉगल करता है)। इसके बिना एंडपॉइंट `403` लौटाता है।

`?format=json` एक विभेदित संरचना लौटाता है, ताकि कॉलर किसी अस्वीकृति से डेटा फ़ील्ड कभी न पढ़े।
सफलता पर:

```jsonc
{
  "allowed": true,
  // केवल तब मौजूद होता है जब कुंजी ने प्रति-कुंजी उपयोग सीमाएँ (दैनिक/साप्ताहिक USD) चुनी हों:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // चयनित प्रदाता कोटा स्नैपशॉट, या जब अभी तक कुछ भी कैश न किया गया हो तो null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // प्रत्येक कनेक्शन का स्नैपशॉट, ताकि UI कई प्रदाताओं को साथ-साथ रेंडर कर सके:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

अस्वीकृति पर (`401` अमान्य कुंजी / `403` अनुमति नहीं) वही रूट
`{ "allowed": false, "error": { "message": "…" } }` लौटाता है — मौजूद-लेकिन-खाली `personal`/`provider`
(कुंजी अनुमत है, पर अभी तक कुछ ज्ञात नहीं हुआ) अस्वीकृति से अलग स्थिति है, और केवल JSON प्रारूप
इनमें अंतर करता है।

**प्रमाणीकरण:** कॉलर की अपनी Bearer API कुंजी, जिसे `isValidApiKey` से सत्यापित किया जाता है — यह
प्रबंधन इंटरफ़ेस (`/api/keys/…`) _नहीं_ है, जो `requireManagementAuth` के पीछे ही रहता है।

### अपरिष्कृत बनाम कटऑफ-समायोजित कोटा प्रतिशत

`/api/usage/om-usage` का उपयोग करते समय, कॉलर को **सादे-टेक्स्ट आउटपुट** और संरचित **JSON आउटपुट**
द्वारा प्रस्तुत प्रतिशतों के बीच अंतर पर ध्यान देना चाहिए:

| पहलू                  | सादा-टेक्स्ट प्रारूप (`/api/usage/om-usage` / `@@om-usage`)                                                        | JSON प्रारूप (`?format=json`)                                          |
| :-------------------- | :----------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------- |
| **आउटपुट फ़ील्ड**     | `NN% left` (उदा., `20% left`)                                                                                      | `provider.quotas` / `providers[].quotas`                               |
| **मापन**              | **कटऑफ-समायोजित उपयोग योग्य भत्ता**: कटऑफ सीमा से ऊपर की शेष क्षमता                                                | **अपरिष्कृत अपस्ट्रीम कोटा**: प्रदाता का असमायोजित मापन                |
| **कटऑफ स्केलिंग**     | `effectiveRemainingPercent()` के माध्यम से स्केल किया जाता है, ताकि संरक्षित रिज़र्व `0% left` के रूप में दिखाई दे | कोई नहीं (प्रदाता द्वारा रिपोर्ट किए गए अपरिष्कृत स्नैपशॉट मान)        |
| **सीमा डेटा**         | प्रदर्शित प्रतिशत में शामिल                                                                                        | प्रति कनेक्शन `quotaWindowThresholds` में संग्रहीत (या सर्वर डिफ़ॉल्ट) |
| **प्राथमिक उपभोक्ता** | इंटरैक्टिव CLI, टर्मिनल प्रॉम्प्ट, मानव ऑपरेटर                                                                     | प्रोग्रामेटिक एकीकरण, डैशबोर्ड, एनालिटिक्स, बिलिंग ट्रैकर              |

#### कटऑफ समायोजन सूत्र

OmniRoute अपस्ट्रीम समाप्ति को रोकने के लिए सक्रिय कोटा कटऑफ का समर्थन करता है (इसे कनेक्शन
`quotaWindowThresholds`, प्रदाता डिफ़ॉल्ट या वैश्विक रेज़िलिएंस सेटिंग्स के माध्यम से कॉन्फ़िगर किया जाता है)। जब किसी कोटा विंडो पर कटऑफ सीमा
(उदा., `cutoff = 25%`) सक्रिय होती है, तो टेक्स्ट रेंडरर शेष भत्ते की गणना इस प्रकार करता है:

- यदि `remaining <= cutoff`: `0%` लौटाता है।
- यदि `remaining > cutoff`: `((remaining - cutoff) / (100 - cutoff)) * 100` लौटाता है।

स्वरूपित टेक्स्ट आउटपुट इसे निकटतम पूर्णांक तक राउंड करता है (`Math.round(...)`)।

#### व्याख्यात्मक उदाहरण

किसी प्रदाता विंडो पर विचार करें जिसमें **60% अपरिष्कृत उपयोग** (अर्थात **40% अपरिष्कृत शेष कोटा**) और कॉन्फ़िगर की गई
**25% शेष-कोटा कटऑफ** सीमा हो:

| प्रस्तुति                           | गणना                                               |   शेष   |                  निहित उपयोग                   |
| :---------------------------------- | :------------------------------------------------- | :-----: | :--------------------------------------------: |
| **अपरिष्कृत JSON (`?format=json`)** | अपस्ट्रीम स्नैपशॉट (`quotas[window]`)              | **40%** |                    **60%**                     |
| **टेक्स्ट प्रारूप (`NN% left`)**    | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (यदि `100 - remaining` की गणना की जाए) |

- **टेक्स्ट में 20% शेष क्यों दिखाई देता है:** खाते पर शेष 40% वास्तविक कोटे में से 25% कटऑफ
  नीति द्वारा आरक्षित है। राउटर द्वारा इस कनेक्शन पर रूटिंग बंद करने से पहले कॉलर के पास 75% उपयोग योग्य हेडरूम में से केवल 15%
  शेष है। स्केलिंग यह सुनिश्चित करती है कि कनेक्शन ठीक उसी समय समाप्ति (`0% left`) का संकेत दे
  जब रूटिंग बंद होगी।
- **JSON अपरिष्कृत मान क्यों संरक्षित रखता है:** JSON पेलोड सटीक प्रदाता स्नैपशॉट (`UsageSnapshot`)
  लौटाता है, ताकि बाहरी टूल को सर्वर-साइड हानिपूर्ण स्केलिंग के बिना वास्तविक अपस्ट्रीम उपयोग और कनेक्शन-स्तरीय
  `quotaWindowThresholds` उपलब्ध हों।

#### उपभोक्ता माइग्रेशन मार्गदर्शन

यदि कोई बाहरी इंटीग्रेशन (जैसे कि कोई एडिटर प्लगइन या एजेंट एक्सटेंशन) पहले टेक्स्ट
एंडपॉइंट (`NN% left`) से डेटा स्क्रैप करता था और उपयोग किए गए प्रतिशत की गणना `100 - NN` के रूप में करता था, तो `?format=json` पर माइग्रेट करने का अर्थ है:

- अपरिष्कृत JSON मान पढ़ने पर **वास्तविक अपस्ट्रीम खपत** दिखाई देगी (ऊपर दिए गए उदाहरण में 60% उपयोग)।
- यदि इंटीग्रेशन टेक्स्ट एंडपॉइंट के उपयोग-योग्य शेष सीमा संबंधी अर्थ को बनाए रखना चाहता है, तो वह कनेक्शन-स्तरीय ओवरराइड के लिए `quotaWindowThresholds` का उपयोग करके क्लाइंट-साइड पर प्रभावी शेष सीमा के फ़ॉर्मूले का मूल्यांकन कर सकता है।

सिंक/आयात किए गए मॉडलों के लिए, `PUT /api/provider-models` में `provider`, `modelId`, और
`maxOutputTokenOverride` स्वीकार किए जाते हैं: एक धनात्मक पूर्णांक मैन्युअल आउटपुट-टोकन सीमा निर्धारित करता है, और `null`
डिफ़ॉल्ट पुनर्स्थापित करने के लिए उसे हटा देता है। `GET /api/provider-models?provider=<provider>` इन
मानों को `modelOutputOverrides` में लौटाता है, जिसमें कस्टम-मॉडल पंक्ति के बिना वाले मॉडल भी शामिल होते हैं। यह ओवरराइड
रनटाइम `max_output_tokens` क्षमता का उपयोग करता है और मॉडल को फिर से सिंक किए जाने के बाद भी बना रहता है। OpenAI-संगत
प्रदाता पृष्ठ वही संपादन/हटाने के नियंत्रण प्रदान करता है और स्पष्ट विज़न समर्थन वाले मॉडलों को चिह्नित करता है।

कस्टम Chat Completions नोड स्पष्ट रीजनिंग ऑप्ट-आउट को अपस्ट्रीम बैकएंड के अनुरूप ढालते हैं। एक
सफल कनेक्शन परीक्षण प्रत्येक सटीक मॉडल ID के लिए स्वतः चैट-टेम्पलेट नियंत्रण चुनता है,
जिसकी `/models` प्रविष्टि किसी मान्यताप्राप्त `owned_by` मान को प्रमाणित करती है: `vllm`, `sglang`, या `llamacpp`।
पारदर्शी OpenAI-संगत रैपर मूल मॉडल प्रविष्टि को नेस्ट किए गए
`openai` ऑब्जेक्ट के भीतर बनाए रख सकते हैं; पहचान ऐसे अधिकतम तीन आवरणों का अनुसरण करती है। अनुपस्थित, अज्ञात या
परस्पर-विरोधी स्वामित्व वाले मॉडल सामान्य OpenAI व्यवहार बनाए रखते हैं। पहचान मौजूदा कैटलॉग अनुरोध का पुनः उपयोग करती है,
कोई कंप्लीशन टोकन उत्पन्न नहीं करती, और कनेक्शन एंडपॉइंट बदलने पर अमान्य हो जाती है।

ऐसे बैकएंड के लिए व्यवहार को स्थिर करने हेतु, जो यह मेटाडेटा उजागर नहीं करता, मौजूदा आंशिक
प्रदाता अपडेट API का उपयोग करें:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

उस बॉडी को `PUT /api/providers/<connection-id>` के साथ भेजें। उस कनेक्शन पर, `none` का स्पष्ट
रीजनिंग प्रयास `chat_template_kwargs.thinking=false` और
`chat_template_kwargs.enable_thinking=false` के रूप में भेजा जाता है। स्पष्ट नेटिव टेम्पलेट मान प्रभावी बने रहते हैं,
जब तक कि कोई सर्वर-साइड रीजनिंग नियम किसी प्रयास को बाध्य न करे। यह सेटिंग केवल तब लागू होती है, जब कोई कस्टम
OpenAI-संगत कनेक्शन Chat Completions बॉडी डिस्पैच करता है; Responses अनुरोध और सामान्य
प्रदाता अपने नेटिव अनुरोध का स्वरूप बनाए रखते हैं। सामान्य OpenAI
`reasoning_effort` पासथ्रू को बाध्य करने के लिए `reasoningControl` को `openai` पर सेट करें, या स्वचालित पहचान का उपयोग करने के लिए इसे छोड़ दें/`null` पर सेट करें।

Claude Code ऑटो-मोड क्लासिफ़ायर अनुरोधों में कोई
स्पष्ट रीजनिंग नियंत्रण न होने पर, उनके लिए नेटिव थिंकिंग डिफ़ॉल्ट रूप से अक्षम रहती है। पहचान Claude-प्रारूप
अनुरोधों में क्लासिफ़ायर के सिस्टम मार्कर का उपयोग करती है, न कि मॉडल नामों या कंप्लीशन सीमाओं का। स्पष्ट बॉडी नियंत्रण, समर्थित प्रयास/थिंकिंग
हेडर, रूटिंग नियम और समाधान किया गया मॉडल प्रयास अपनी मौजूदा प्राथमिकता बनाए रखते हैं। क्लासिफ़ायर के दोनों
चरण अपने प्रॉम्प्ट, कंप्लीशन सीमाएँ, स्टॉप अनुक्रम और वास्तविक अपस्ट्रीम अनुमति
निर्णय बनाए रखते हैं; दूसरा चरण अब भी अपनी अनुरोधित दृश्यमान रीजनिंग को सामान्य टेक्स्ट के रूप में उत्पन्न कर सकता है।

`DELETE /api/db-backups` (संग्रहीत बैकअप हटाना) और `PATCH /api/db-backups` (प्रतिधारण सेटिंग:
स्थायी रूप से सहेजे गए मान प्रत्येक बैकअप के बाद स्वचालित हटाने की प्रक्रिया को नियंत्रित करते हैं) पर भी लागू होती है। सूचीबद्ध करना (`GET`) और

### संस्करण और रिलीज़ चैनल

```bash
GET /api/system/version
```

केवल लूपबैक के लिए प्रबंधन रूट (एडमिन प्रमाणीकरण)। यह चल रहे संस्करण, नवीनतम प्रकाशित संस्करण और स्वचालित अपडेट की स्थिति लौटाता है। `releaseChannel` और `channels` जोड़े गए फ़ील्ड हैं (रेल 3.8.54); `channel` का अर्थ वही रहता है — वह डिप्लॉयमेंट मोड जिसका उपयोग डैशबोर्ड अपडेटर करता है (`npm`, `source` या `docker-compose`)।

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — चल रहे बिल्ड का npm चैनल: `-nightly.*` संस्करणों के लिए `nightly`,
  अन्य प्री-रिलीज़ (`-rc.*`, `-beta.*`, `-alpha.*`) के लिए `next`, `channels.latest` से पुराने
  मेजर के स्थिर संस्करण के लिए `lts`, अन्यथा `latest`। ये वही नियम हैं जो
  `scripts/release/dist-tag.mjs` में हैं, जो प्रकाशन के समय npm dist-tag चुनता है।
- `channels` — प्रत्येक dist-tag का प्रकाशित नवीनतम संस्करण, `npm view omniroute dist-tags` से
  (रजिस्ट्री HTTP फ़ॉलबैक), जिसे `latest` के समान 10-मिनट की TTL के साथ कैश किया जाता है।
  `latest` हमेशा मौजूद होता है (पहले `latest` फ़ील्ड और फिर `"unavailable"` पर फ़ॉलबैक करता है);
  `next`, `nightly` और `lts` केवल तभी दिखाई देते हैं, जब वह dist-tag मौजूद हो। एक
  `Cache-Control: no-cache` अनुरोध दोनों लुकअप को रीफ़्रेश करता है।

चैनल मॉडल (`latest` = 4.0 GA तक v3, `next` = rc, `nightly` = `develop` बिल्ड,
`lts` = 4.0 GA के बाद v3 पैच) का वर्णन `docs/ops/RELEASE_STRATEGY.md` में किया गया है।

## टोकनयुक्त VS Code / हेडर-रहित उपनाम

इन उपनामों का उपयोग तब करें, जब कोई एकीकरण `Authorization` हेडर इंजेक्ट नहीं कर सकता और API कुंजी को बेस URL में एम्बेड करने की आवश्यकता होती है।

```bash
# OpenAI-शैली का कैटलॉग उपनाम
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-शैली के चैट उपनाम
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-शैली के उपनाम
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

उदाहरण:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

टिप्पणियाँ:

- टोकनयुक्त उपनाम `/v1/*` और `/api/tags` वाले समान हैंडलर का पुनः उपयोग करते हैं; प्रतिक्रिया संरचनाएँ समान रहती हैं।
- जब भी क्लाइंट कस्टम हेडर का समर्थन करे, `Authorization: Bearer ...` को प्राथमिकता दें।
- URL-आधारित टोकन रिवर्स-प्रॉक्सी लॉग, ब्राउज़र इतिहास और OmniRoute से बाहर की टेलीमेट्री में दिखाई दे सकते हैं। इन्हें संगतता विकल्प के रूप में उपयोग करें, डिफ़ॉल्ट प्रमाणीकरण मोड के रूप में नहीं।

## बजट

```bash
# सभी API कुंजियों के लिए बजट स्थिति प्राप्त करें
GET /api/usage/budget

# बजट सेट या अपडेट करें
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **स्कीमा टिप्पणियाँ** (`setBudgetSchema`): `apiKeyId` आवश्यक है; `dailyLimitUsd`, `weeklyLimitUsd`, या `monthlyLimitUsd` में से कम-से-कम एक का मान शून्य से अधिक होना चाहिए। वैकल्पिक फ़ील्ड: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`)। लेगेसी `{keyId, limit, period}` संरचना `400 Bad Request` लौटाती है।

## टोकन सीमाएँ

प्रति-API-कुंजी **टोकन** बजट (ऊपर दिए गए USD-आधारित बजट से अलग)। अनुरोध पथ पर ही लागू किए जाते हैं: जब किसी कुंजी की वर्तमान विंडो का उपयोग उसकी सीमा तक पहुँच जाता है, तो अनुरोध `429 Too Many Requests` के साथ अस्वीकार कर दिए जाते हैं। सीमाओं को किसी विशिष्ट `model`, किसी `provider` तक सीमित किया जा सकता है या पूरी कुंजी पर `global` रूप से लागू किया जा सकता है; जब किसी अनुरोध से कई सीमाएँ मेल खाती हैं, तो सबसे कठोर सीमा लागू होती है।

```bash
# किसी कुंजी की टोकन सीमाएँ सूचीबद्ध करें (लाइव विंडो उपयोग सहित)
GET /api/usage/token-limits?apiKeyId=key-123

# टोकन सीमा बनाएँ या अपडेट करें
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id द्वारा टोकन सीमा हटाएँ
DELETE /api/usage/token-limits?id=tl-abc
```

> **स्कीमा संबंधी टिप्पणियाँ** (`setTokenLimitSchema`): `apiKeyId` और `scopeType` (`model` | `provider` | `global`) आवश्यक हैं। `scopeValue` तब तक आवश्यक है, जब तक `scopeType`, `global` न हो (उदाहरण के लिए, `model` स्कोप हेतु मॉडल id और `provider` स्कोप हेतु प्रोवाइडर id)। `tokenLimit` एक धनात्मक पूर्णांक होना चाहिए (स्ट्रिंग से रूपांतरित)। वैकल्पिक: `id` (बनाने के लिए छोड़ दें, अपडेट करने के लिए प्रदान करें), `resetInterval` (`daily` | `weekly` | `monthly`, डिफ़ॉल्ट `monthly`), `resetTime` (`HH:MM`), `enabled` (डिफ़ॉल्ट `true`)। `GET` प्रतिक्रियाएँ प्रत्येक सीमा में `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, और `nextResetAt` जोड़ती हैं। यह एक प्रबंधन-श्रेणी का एंडपॉइंट है (प्रमाणीकरण को authz पाइपलाइन द्वारा केंद्रीय रूप से लागू किया जाता है)।

## अनुरोध संसाधन

1. क्लाइंट `/v1/*` पर अनुरोध भेजता है
2. रूट हैंडलर `handleChat`, `handleEmbedding`, `handleAudioTranscription`, या `handleImageGeneration` को कॉल करता है
3. मॉडल का निर्धारण किया जाता है (प्रत्यक्ष प्रोवाइडर/मॉडल या उपनाम/कॉम्बो)
4. खाते की उपलब्धता फ़िल्टरिंग के साथ स्थानीय DB से क्रेडेंशियल चुने जाते हैं
5. चैट के लिए: `handleChatCore` सिमेंटिक/सिग्नेचर कैश की जाँच करता है और कॉम्बो कम्प्रेशन सेटिंग्स निर्धारित करता है
6. सक्षम होने पर प्रोवाइडर अनुवाद से पहले प्रोऐक्टिव कम्प्रेशन चलता है (`lite`, Caveman, RTK, या स्टैक्ड)
7. प्रोवाइडर एक्ज़ीक्यूटर अपस्ट्रीम अनुरोध भेजता है
8. प्रतिक्रिया को वापस क्लाइंट प्रारूप में अनुवादित किया जाता है (चैट) या उसी रूप में लौटाया जाता है (एम्बेडिंग/इमेज/ऑडियो)
9. उपयोग, कम्प्रेशन एनालिटिक्स, और अनुरोध लॉग रिकॉर्ड किए जाते हैं
10. त्रुटियाँ होने पर कॉम्बो नियमों के अनुसार फ़ॉलबैक लागू होता है

संपूर्ण आर्किटेक्चर संदर्भ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

| विधि   | पथ                                    | विवरण                                                                                                                                                                                                 |
| ------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | पंजीकृत कुंजियाँ सूचीबद्ध करें (केवल छिपा हुआ प्रीफ़िक्स)                                                                                                                                             |

## लचीलापन (विस्तृत)

OmniRoute अस्थायी विफलता के लिए तीन स्वतंत्र तंत्र उपलब्ध कराता है; नीचे दिए गए प्रबंधन एंडपॉइंट ऑपरेटरों को उन्हें पढ़ने और ओवरराइड करने की सुविधा देते हैं:

| दायरा           | स्थिति संग्रहण                          | पढ़ें                                     | रीसेट / साफ़ करें                                                                  |
| --------------- | --------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| प्रदाता ब्रेकर  | `domain_circuit_breakers` + इन-मेमोरी   | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                                       |
| कनेक्शन कूलडाउन | प्रदाता कनेक्शनों पर `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (आवश्यकता पड़ने पर स्वतः फिर से सक्षम होता है; प्रदाता PUT के माध्यम से साफ़ करें) |
| मॉडल लॉकआउट     | इन-मेमोरी मॉडल-उपलब्धता रजिस्ट्री       | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                           |

`PATCH /api/resilience`, `providerBreaker.oauth` और `providerBreaker.apikey` के अंतर्गत प्रदाता ब्रेकर ओवरराइड स्वीकार करता है। प्रत्येक प्रोफ़ाइल `degradationThreshold`, `failureThreshold`, और `resetTimeoutMs` का समर्थन करती है; यही फ़ील्ड Dashboard → Settings → Resilience में भी उपलब्ध हैं।

```bash
# किसी एक मॉडल लॉकआउट को साफ़ करें
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# प्रत्येक लॉकआउट को मिटाएँ
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

संपूर्ण वैचारिक संदर्भ और ब्रेकर डिफ़ॉल्ट के लिए: [`CLAUDE.md`](../../CLAUDE.md) → "लचीलापन रनटाइम स्थिति" और [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) देखें।

### दर-सीमा कतार और स्वतः-सक्षमता सुरक्षा तंत्र

- **समर्थित लेखन पथ**: `{"connectionId": "<id>", "enabled": true|false}` बॉडी के साथ `POST /api/rate-limits`, किसी कनेक्शन के लिए दर-सीमा सुरक्षा को चालू या बंद करने हेतु समर्थित प्रबंधन एंडपॉइंट है। `PUT /api/providers/[id]` जानबूझकर `rateLimitProtection` को संशोधित या उलटता नहीं है (#11278)।
- **`enabled: false` का अर्थ**: `enabled: false` सेट करने से कनेक्शन की स्पष्ट सुरक्षा हट जाती है, लेकिन यह किसी सक्रिय API-कुंजी कनेक्शन को वैश्विक स्वतः-सक्षमता सुरक्षा तंत्र (`autoEnableApiKeyProviders = true`) से **बाहर नहीं करता**। `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) में `false` और `undefined` समान हैं; स्पष्ट सुरक्षा के बिना सक्रिय API-कुंजी कनेक्शन स्वतः-सक्षमता सुरक्षा तंत्र के अंतर्गत संरक्षित रहते हैं।
- **वैश्विक निष्क्रियता**: API-कुंजी कनेक्शनों को दर-सीमा कतारों के बिना चलाने के लिए, `RATE_LIMIT_AUTO_ENABLE=false` (परिवेश) या `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) के माध्यम से सुरक्षा तंत्र को वैश्विक रूप से निष्क्रिय करें।

## MCP सर्वर

OmniRoute में 3 ट्रांसपोर्ट (stdio, SSE, streamable-http) और स्कोप किए गए टूल वाला एक अंतर्निहित Model Context Protocol सर्वर शामिल है। नीचे दिए गए डैशबोर्ड एंडपॉइंट स्थिति/ऑडिट डेटा पढ़ते हैं और HTTP ट्रांसपोर्ट को प्रॉक्सी करते हैं।

| विधि | पथ | विवरण |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | हार्टबीट, ट्रांसपोर्ट, ऑनलाइन स्थिति, अंतिम कॉल, शीर्ष टूल, 24 घंटे की सफलता दर |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` सहित MCP टूल की सूची |
| GET | `/api/mcp/sse` | SSE ट्रांसपोर्ट के लिए SSE स्ट्रीम खोलें (यदि MCP अक्षम है या ट्रांसपोर्ट मेल नहीं खाता है, तो `503` लौटाता है) |
| POST | `/api/mcp/sse` | SSE ट्रांसपोर्ट पर JSON-RPC फ़्रेम भेजें |
| GET | `/api/mcp/stream` | Streamable HTTP ट्रांसपोर्ट का SSE पक्ष खोलें (सर्वर द्वारा आरंभ किए गए संदेश) |
| POST | `/api/mcp/stream` | Streamable HTTP ट्रांसपोर्ट पर JSON-RPC फ़्रेम भेजें |
| DELETE | `/api/mcp/stream` | Streamable HTTP सत्र समाप्त करें |
| GET | `/api/mcp/audit` | ऑडिट लॉग क्वेरी करें — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | समेकित ऑडिट आँकड़े (कुल संख्या, सफलता दर, औसत अवधि, शीर्ष टूल) |

**प्रमाणीकरण:** `sse`/`stream` ट्रांसपोर्ट MCP-विशिष्ट प्रमाणीकरण सतह का पालन करते हैं (`mcp` स्कोप वाली Bearer API कुंजी); `status`/`tools`/`audit*` रूट डैशबोर्ड से पढ़े जा सकते हैं (डैशबोर्ड होस्ट तक पहुँचने के अतिरिक्त किसी प्रमाणीकरण की आवश्यकता नहीं है)।

> दोनों HTTP ट्रांसपोर्ट `settings.mcpEnabled` और `settings.mcpTransport` द्वारा नियंत्रित हैं — ट्रांसपोर्ट का मेल न होने पर `400` लौटाया जाता है, जबकि MCP अक्षम होने पर `503` लौटाया जाता है।

## A2A सर्वर

OmniRoute निरीक्षण/डैशबोर्ड उपयोग के लिए एक REST रैपर के साथ A2A (Agent-to-Agent) JSON-RPC 2.0 एंडपॉइंट उपलब्ध कराता है।

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # वैकल्पिक, जब तक OMNIROUTE_API_KEY सेट न हो
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

समर्थित विधियाँ (सभी `settings.a2aEnabled` द्वारा नियंत्रित):

| विधि             | विवरण                                                            |
| ---------------- | ---------------------------------------------------------------- |
| `message/send`   | सिंक्रोनस कौशल निष्पादन; `{task, artifacts, metadata}` लौटाता है |
| `message/stream` | समान कौशल-समूह का स्ट्रीमिंग SSE निष्पादन                        |
| `tasks/get`      | `taskId` द्वारा कोई कार्य प्राप्त करें                           |
| `tasks/cancel`   | `taskId` द्वारा कोई कार्य रद्द करें                              |

अंतर्निहित कौशल: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`।

### एजेंट कार्ड

```bash
GET /.well-known/agent.json
```

सार्वजनिक A2A एजेंट कार्ड (नाम, विवरण, क्षमताएँ, कौशल कैटलॉग, प्रमाणीकरण योजना) लौटाता है — सार्वजनिक रूप से 1h के लिए कैश किया जाता है। प्रमाणीकरण आवश्यक नहीं है।

### REST सहायक

| विधि | पथ                           | विवरण                                                                                                                    |
| ---- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| GET  | `/api/a2a/status`            | A2A सक्षम स्थिति + कार्य आँकड़े + कैश किए गए एजेंट कार्ड का सारांश                                                       |

| GET    | `/api/webhooks/[id]/deliveries` | किसी वेबहुक का डिलीवरी इतिहास सूचीबद्ध करें (सफलता/विफलता लॉग)   |
| POST   | `/api/webhooks/[id]/test`       | किसी वेबहुक को परीक्षण ईवेंट भेजें                               |

**प्रमाणीकरण:** प्रबंधन सत्र आवश्यक है।

ईवेंट प्रकारों की पूरी सूची के लिए [वेबहुक फ़्रेमवर्क](../frameworks/WEBHOOKS.md) देखें।

## गार्डरेल्स

रनटाइम गार्डरेल्स (PII पहचान, प्रॉम्प्ट इंजेक्शन पहचान, विज़न ब्रिजिंग) का निरीक्षण करें। गार्डरेल्स प्रत्येक अनुरोध पर चलते हैं; प्रत्येक कॉल के लिए ऑप्ट-आउट `x-omniroute-disabled-guardrails` अनुरोध हेडर के माध्यम से किया जाता है — सक्षम/अक्षम स्थिति को स्थायी रूप से सहेजने के लिए कोई सरफ़ेस नहीं है।

| विधि | पथ                     | विवरण                                                                                    |
| ---- | ---------------------- | ---------------------------------------------------------------------------------------- |
| GET  | `/api/guardrails`      | पंजीकृत गार्डरेल्स और उनकी स्थिति (नाम / सक्षम / प्राथमिकता) सूचीबद्ध करें               |
| POST | `/api/guardrails/test` | नमूना इनपुट पर प्री-कॉल पाइपलाइन का ड्राई-रन करें — बॉडी: `{input, disabledGuardrails?}` |

**प्रमाणीकरण:** प्रबंधन सत्र आवश्यक है।

पूरी जानकारी के लिए [सुरक्षा > गार्डरेल्स](../security/GUARDRAILS.md) देखें।

## प्रमाणीकरण

चार क्रेडेंशियल परिवारों (डैशबोर्ड सत्र, स्थानीय CLI टोकन, `oma_live_…` एक्सेस टोकन, प्रबंधन-स्कोप वाली API कुंजी) और उनके इन्फ़रेंस कुंजियों से अंतर के लिए [प्रबंधन प्रमाणीकरण](../guides/MANAGEMENT-AUTH.md) देखें।

- डैशबोर्ड रूट (`/dashboard/*`) `auth_token` कुकी का उपयोग करते हैं
- लॉगिन सहेजे गए पासवर्ड हैश का उपयोग करता है; फ़ॉलबैक के रूप में `INITIAL_PASSWORD`
- `requireLogin` को `/api/settings/require-login` के माध्यम से टॉगल किया जा सकता है
- `REQUIRE_API_KEY=true` होने पर `/v1/*` रूट वैकल्पिक रूप से Bearer API कुंजी की आवश्यकता रखते हैं
- इस संदर्भ में "प्रबंधन टोकन" / "प्रबंधन-स्कोप वाली API कुंजी" का अर्थ उस गाइड में दिए गए परिवारों में से एक है — कोई अपरिभाषित अतिरिक्त सीक्रेट प्रकार नहीं

> **ब्रेकिंग परिवर्तन (v3.8.0)** — `/api/v1/agents/tasks/*` और कूलडाउन प्रबंधन एंडपॉइंट को अब **प्रबंधन प्रमाणीकरण** (डैशबोर्ड `auth_token` कुकी या प्रबंधन-स्कोप वाली API कुंजी) की आवश्यकता है। जो क्लाइंट पहले इन रूट को बिना प्रमाणीकरण के कॉल करते थे, उन्हें `401 Unauthorized` प्राप्त होगा। कमिट `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) देखें।
