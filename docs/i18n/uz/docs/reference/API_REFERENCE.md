OpenAI bilan mos protokol va provayder imkoniyatlari matritsasiga bag‘ishlangan ma’lumot uchun
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md) sahifasiga qarang.

Har bir joylashtirish `/openapi.yaml` manzilida o‘z spetsifikatsiya nusxasini taqdim etadi; u yig‘ish jarayonida `docs/openapi.yaml` faylidan hosil qilinadi. Unda yig‘ish jarayonining versiyasi va nisbiy server URL manzili (`./`) mavjud bo‘lib, so‘rovlar hujjatni taqdim etgan xostda qolishini ta’minlaydi. Yuklab olingan faylni import qiladigan vositada bunday xost bo‘lmaydi, shu sababli asosiy URL manzilini qo‘lda o‘rnatish kerak.

## Chat yakunlash

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Maxsus sarlavhalar

| Header                   | Direction | Description                                                                                                                                                                                                                                                         |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `x-omniroute-no-memory`  | So‘rov    | Ushbu so‘rov uchun xotira + ko‘nikmalarni kiritishni o‘tkazib yuborish uchun `true` qiymatiga o‘rnating (no-cache bilan bir xil ishlaydi; har bir chaqiruv uchun token/xarajat qo‘shimcha sarfini oldini oladi)                                                     |
| `X-OmniRoute-Progress`   | So‘rov    | Jarayon hodisalari uchun `true` qiymatiga o‘rnating                                                                                                                                                                                                                 |
| `X-Session-Id`           | So‘rov    | Tashqi sessiya bog‘liqligi uchun yopishqoq sessiya kaliti                                                                                                                                                                                                           |
| `x_session_id`           | So‘rov    | Pastki chiziqli varianti ham qabul qilinadi (to‘g‘ridan-to‘g‘ri HTTP)                                                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | So‘rov    | Chaqiruvchi taqdim etgan sessiya/suhbat tegi (xotiraga ham uzatiladi). Mavjud bo‘lganda, sessiya bo‘yicha xarajatlarni bog‘lash uchun `call_logs.session_tag` maydoniga aynan o‘z holicha saqlanadi (#8249) — mavjud bo‘lmaganda hech qachon avtomatik yaratilmaydi |
| `Idempotency-Key`        | So‘rov    | Takroriylikni bartaraf etish kaliti (5 soniyalik oyna)                                                                                                                                                                                                              |
| `X-Request-Id`           | So‘rov    | Muqobil takroriylikni bartaraf etish kaliti                                                                                                                                                                                                                         |
| `x-omniroute-connection` | So‘rov    | Bitta modelga yuboriladigan so‘rovni ID raqami bo‘yicha bitta provayder ulanishiga (akkauntga) biriktirish — [Har bir so‘rov uchun akkauntni biriktirish](#account-pinning-per-request) bo‘limiga qarang                                                            |
| `X-OmniRoute-Cache`      | Javob     | `HIT` yoki `MISS` (oqimlashtirilmagan)                                                                                                                                                                                                                              |
| `X-OmniRoute-Idempotent` | Javob     | Takroriylik bartaraf etilgan bo‘lsa `true`                                                                                                                                                                                                                          |

#### Har bir so‘rov uchun akkauntni biriktirish

Provayderda bir nechta ulanishlar (akkauntlar yoki kalitlar) mavjud bo‘lsa, OmniRoute odatda akkaunt tanlash strategiyasi orqali ulardan birini tanlaydi. So‘rov o‘rniga `x-omniroute-connection` sarlavhasi yordamida ma’lum bir ulanishga biriktirilishi mumkin:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Id ni qayerdan topish mumkin.** Dashboarddagi provayder sahifasini oching
  (**Dashboard → Providers → <provider>**) va ulanish qatoridagi `xxxxxxxx…` id chipini bosing —
  bu to‘liq ulanish id sini nusxalaydi.
- **U qaysi so‘rovlarda ishlaydi.** `/v1/chat/completions`, `/v1/messages` va
  `/v1/responses` dagi bitta modelga yuboriladigan so‘rovlarda (`provider/model`). Kombinatsiyalar
  sarlavhani e’tiborsiz qoldiradi: har bir kombinatsiya bosqichi uchun hisobni bosqichning
  o‘z ulanishi orqali biriktiring.
- **Biriktirish qat’iy, afzallik emas.** Biriktirilgan ulanishdan faqat o‘zi foydalaniladi.
  So‘rov ichidagi xatolik hisobning kutish holatini qayd etadi, ammo shu provayderga tegishli
  boshqa hisobga o‘tmaydi.
- **Kutish holati va kvota biriktirishni bekor qiladi.** Biriktirilgan ulanish kutish holatida
  bo‘lganida, kvota tugaganida yoki kvota siyosati tomonidan bloklanganida, keyingi so‘rovlar
  xuddi biriktirilmagan trafik kabi provayderning boshqa ulanishlariga o‘tadi.
- **Noma’lum yoki o‘chirilgan id lar xatolik bilan yakunlanadi.** Provayderning faol havzasida
  mavjud bo‘lmagan id (o‘chirilgan, faolsizlantirilgan yoki boshqa provayderga tegishli id)
  mos hisob qoldirmaydi, shuning uchun so‘rov boshqa joyga jimgina yo‘naltirilish o‘rniga
  xatolik bilan yakunlanadi.

Claude Code maxsus sarlavhalarni `ANTHROPIC_CUSTOM_HEADERS` orqali yuboradi. Uni
`~/.claude/settings.json` faylining `env` blokiga yoki har bir loyiha uchun boshqa hisobni
biriktirish maqsadida loyiha darajasidagi `.claude/settings.json` fayliga qo‘shing:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Manba: `src/sse/handlers/chat.ts` (sarlavhani o‘qish), `src/sse/services/auth.ts` va
`src/sse/services/sessionAffinityPin.ts` (biriktirishni bekor qilish va havzada mavjud
bo‘lmagan ulanishni tekshirish).

> **Xarajat telemetriyasi sarlavhalari:** oqimdan foydalanilmaydigan muvaffaqiyatli javoblarda
> `X-OmniRoute-*` xarajat telemetriyasi to‘plami ham yuboriladi —
> `X-OmniRoute-Response-Cost` (AQSh dollari, o‘nlikdan keyin aniq 10 ta raqam;
> bepul yoki narxi belgilanmagan holatda `0.0000000000`), `X-OmniRoute-Tokens-In` /
> `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`,
> `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` va `X-OmniRoute-Fallback-Attempts`
> (faqat `> 0` bo‘lganda), shuningdek `X-OmniRoute-Request-Id` va `X-OmniRoute-Version`.
> Ular chat completions, `/v1/responses`, `/v1/messages` **va media endpointlari** —
> `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`,
> `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`,
> `/v1/music/generations` va `/v1/moderations` (har doim `0` xarajat bilan) tomonidan
> yuboriladi. Media xarajati narxlash mavjud bo‘lganda har bir modallik bo‘yicha
> (har bir rasm, har bir soniya, har bir belgi, har bir qidiruv birligi uchun) hisoblanadi,
> aks holda `0` qiymati qaytariladi (xatolik sababli ishlashni to‘xtatmaydi).

> **Keshdan olingan natija xarajati semantikasi:** semantik keshda HIT
> (`X-OmniRoute-Cache-Hit: true`) yuz berganda upstream chaqiruv amalga oshirilmaydi,
> shuning uchun `X-OmniRoute-Response-Cost` `0.0000000000` ga teng bo‘ladi
> (natijani keshdan taqdim etishning **qo‘shimcha** xarajati). Asl yoki yuz berishi mumkin
> bo‘lgan xarajat `X-OmniRoute-Cost-Saved` da alohida ko‘rsatiladi. Hisob-kitobni amalga
> oshiruvchi iste’molchilar `X-OmniRoute-Response-Cost` ni jamlashi kerak (HIT lar
> hech narsa turmaydi); kesh tahlili esa `X-OmniRoute-Cost-Saved` ni jamlashi mumkin.

## Eksklyuziv boshqariladigan sessiya ijara-lari

Eksklyuziv boshqariladigan sessiyani ijaraga berish — ixtiyoriy, mijentdan mustaqil marshrutlash shartnomasi: bitta faol egasi bitta mos OmniRoute ulanishini egallaydi. U modelni ijaraga bermaydi, OAuth’ni talab qilmaydi, muayyan mijentni aniqlamaydi va muayyan provayderni talab qilmaydi.

Autentifikatsiya qiluvchi API kaliti `lease:exclusive` qamroviga va bo‘sh bo‘lmagan aniq `allowedConnections` ro‘yxatiga ega bo‘lishi kerak. Ma’lumotlar bazasidagi mutatsiya chegarasi kalit yaratish va qisman yangilash vaqtida ikkala maydonni birgalikda talab qiladi.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Muvaffaqiyatli acquire, renew va release javoblarida vaqt belgilar, `state` va aniq musbat
`generation` ko‘rsatiladi, biroq tanlangan ulanish yoki hisob ma’lumotlari hech qachon berilmaydi. Renew va release `generation` qiymatini JSON tanasida yuboradi:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Faol sessiya egasi joriy bog‘lanishi uchun maxfiylikni saqlovchi ko‘rsatish metama’lumotlarini aniq so‘rashi mumkin:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Bu ixtiyoriy status amali bitta ma’lumotlar bazasi tranzaksiyasida shaffof bo‘lmagan egasi,
autentifikatsiyadan o‘tgan boshqariladigan API kaliti va aniq faol generation orqali himoyalanadi. `displayName` faqat sozlangan ulanish nomining bo‘shliqlari olib tashlangan ko‘rinishidir; xavfsiz sozlangan nom mavjud bo‘lmaganda u `null` bo‘ladi. OmniRoute hech qachon elektron pochta manzilini yoki yaratilgan hisob identifikatorini uning o‘rniga qo‘ymaydi. Provayder qiymati maxfiy bo‘lmagan ko‘rsatish yorlig‘i bo‘lib, hech qachon yaratilgan mos-provayder identifikatori bo‘lmaydi. Hisob ma’lumotlari, tokenlar, cookie’lar, xom ulanish yoki API kaliti identifikatorlari, egalar xeshlari, chegaralovchi sirlar va ichki marshrutlash ma’lumotlari chiqarib tashlanadi.

Noto‘g‘ri kalit, noto‘g‘ri egasi, eskirgan generation, mavjud bo‘lmagan, muddati o‘tgan, bo‘shatilgan va bekor qilingan qidiruvlarning barchasi ulanish metama’lumotlarisiz bir xil `409 LEASE_FENCE_STALE` xatosini qaytaradi. Sig‘im kutilayotgani haqidagi javobni olgan mijent tekshirish uchun faol bog‘lanishga ega bo‘lmaydi. Marshrutlash faol sessiyani boshqa holatga o‘tkazganda, xuddi shu generation amal qilishda davom etadi va status atomik tarzda yangi bog‘lanishni qaytaradi, eski bog‘lanishni esa hech qachon qaytarmaydi. Mavjud mijentlar o‘zgarmaydi, chunki acquire, renew, release va kutish javoblari avvalgi shakllarini saqlab qoladi.

Bu server shartnomasi standart OpenAI Codex `/status` amalini o‘zgartirmaydi. Standart Codex hozirda o‘zining model provayderi va o‘rnatilgan autentifikatsiya/hisob holatini bildiradi, biroq ixtiyoriy maxsus provayder hisob metama’lumotlarini ko‘rsatmaydi; keyingi mijent integratsiyasi ushbu amalni chaqirishi va `connection.displayName` qanday ko‘rsatilishini hal qilishi kerak.

Shundan so‘ng har bir boshqariladigan inference so‘rovi ikkala boshqaruv sarlavhasini ham yuboradi:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Aniq egasi, generation, faol ulanish va autentifikatsiyadan o‘tgan API kaliti qo‘llab-quvvatlanadigan har bir upstream urinishidan bevosita oldin tekshiriladi. Egasi va generation qiymatlarini boshqa kalit bilan takrorlash, hatto ushbu kalit o‘sha ulanishga ruxsat bergan bo‘lsa ham, muvaffaqiyatsiz tugaydi. Xom egalar saqlanmaydi, jurnalga yozilmaydi, so‘rov snapshot’ida saqlab qolinmaydi va upstream’ga uzatilmaydi.

Vaqtinchalik raqobat `Retry-After` bilan HTTP `429` va quyidagi javobni qaytaradi:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Bu javob faqat odatiy mos to‘plam bo‘sh bo‘lmaganini va barcha bo‘sh nomzodlar boshqa faol sessiya tomonidan egallanganini anglatadi. Qo‘llab-quvvatlanmaydigan modellar/provayderlar, siyosatga mos kelmaslik, cooldown, kvota, holat va boshqa odatiy moslikdagi xatolar avvalgi OmniRoute javoblarini saqlab qoladi.

### `x-omniroute-compression`

Siqish rejasini har bir so‘rov uchun almashtirish. Eng yuqori ustuvorlikka ega — routing-combo almashtirishidan, faol profildan, auto-trigger’dan va paneldagi Default qiymatidan ustun turadi. Qiymatlar:

| Qiymat        | Ta’siri                                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | Ushbu so‘rov uchun siqish yo‘q.                                                                                       |
| `default`     | Paneldan olingan Default profili (faol profil e’tiborga olinmaydi). Yo‘qotishli dvigatellar o‘chirilgan holda qoladi. |
| `safe`        | Faqat takroriy ma’lumotlarni olib tashlash va bo‘shliqlarni birlashtirish.                                            |
| `allow-lossy` | Ushbu so‘rov uchun operator rejasini, jumladan xulosalar va uslubiy qayta yozishlarni saqlab qolish.                  |
| `engine:<id>` | Yoqilgan bitta dvigatel, masalan, `engine:rtk`. Ushbu dvigatel uchun har bir so‘rov bo‘yicha ixtiyoriy yoqish.        |
| `<combo>`     | Nomi bo‘yicha (avval katta-kichik harflarni farqlamagan holda), keyin id bo‘yicha moslashtiriladigan nomlangan combo. |

Izohlar:

- Noma’lum qiymatlar e’tiborga olinmaydi (so‘rov hech qachon rad etilmaydi); aniqlash odatiy operator ustuvorligi bo‘yicha davom etadi.
- Agar bir nechta combo bir xil nomga ega bo‘lsa, deterministik moslashtirish uchun combo **id** qiymatini yuboring.
- Nomi `off` yoki `default` bo‘lgan combo’ni nomi orqali tanlab bo‘lmaydi (bu kalit so‘zlar avval talqin qilinadi); bunday combo’ga uning id qiymati orqali murojaat qiling.
- Asosiy siqish tugmasi qat’iy cheklovdir: siqish global ravishda o‘chirilganida, bu sarlavha uni yoqa olmaydi.

Qo‘llangan reja javob sarlavhasida qaytariladi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

bu yerda `<source>` quyidagilardan biri bo‘ladi: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` yoki `off`.

## Embeddinglar

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Mavjud provayderlar: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog identifikatorlari `provider/model` ko‘rinishida bo‘ladi (masalan: `jina-ai/jina-embeddings-v5-omni-small`). Reyestrda mavjud bo‘lgan Jina model identifikatorlari (masalan, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ham aniqlanadi. Jina embed/rerank/classify/segment uchun avval dashboard `jina-ai` hisob ma’lumotlaridan foydalaniladi; `JINA_AI_API_KEY` faqat dashboard kaliti mavjud bo‘lmaganda zaxira sifatida ishlatiladi. `jina-reader` kartasi faqat Reader / `r.jina.ai` uchun (`POST /v1/web/fetch`) va embeddings yoki rerank xizmatlarini taqdim etmaydi.

Multimodal qo‘llab-quvvatlashini e’lon qilgan reyestr modellari provayderga bog‘liq bo‘lmagan, tuzilgan ko‘rinishdagi 32 tagacha elementni ham qabul qiladi. Media elementlari turlari `text`, `image`, `audio`, `video` va `document`dan iborat. Ularning media `source`i `{"type":"url","url":"https://..."}` yoki `{"type":"base64","data":"...","media_type":"..."}` bo‘ladi.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` va oilaviy taxallus `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina’ning mahalliy EmbeddingsV5Request hujjatlarini ham qabul qiladi va ularni o‘zgartirmagan holda `https://api.jina.ai/v1/embeddings` manziliga **uzatadi**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Mahalliy `{ image | audio | video | pdf }` qiymatlari umumiy HTTPS URL, `data:` URI yoki xom base64 bo‘lishi mumkin. OmniRoute bu obyektlarni satrga aylantirmaydi yoki mahalliy image URL manzillaridan ma’lumot yuklamaydi — Jina ommaviy medianing o‘zini oladi. Qo‘shimcha Jina maydonlari (`task`, `normalized`, `truncate`, `embedding_type`) uzatiladi. Faqat matnni qo‘llab-quvvatlaydigan Jina SKU’lari hamon matn bo‘lmagan hujjatlarni rad etadi.

Xavfsizlik va transport cheklovlari:

- Masofaviy media URL manzillari ommaviy HTTPS bo‘lishi shart. Kanonik `{type,source:url}` elementlari provayder chaqiruvidan oldin server tomonida olinadi (qayta yo‘naltirishni qayta tekshirish, kutish vaqti, hajm cheklovlari, ommaviy DNS, ulanishni pinlash) va so‘rov ichiga joylashtiriladi. Jina-mahalliy `{image:"https://..."}` elementlari xuddi shu ommaviy-HTTPS tekshiruvidan so‘ng o‘z holicha uzatiladi; URL manzilidan Jina ma’lumot oladi.
- Inline base64 media har bir element uchun dekodlangan holda 8 MiB va butun so‘rov bo‘yicha dekodlangan holda 16 MiB bilan cheklangan.

Provayderga moslashtirish (kanonik elementlar hech qachon o‘zgartirilmagan holda uzatilmaydi):

- Jina multimodal modellari: yuqori darajadagi har bir element ma’lumot URI’laridan foydalangan holda bitta modallikka mos kalitli obyektga (`text` / `image` / `audio` / `video` / `pdf`) aylanadi; har bir yuqori darajadagi element uchun bittadan vektor hosil qilinadi.
- Gemini Embedding 2 oilasi: bitta yuqori darajadagi massiv `content.parts` (`text` yoki `inline_data`) bilan yagona mahalliy `models/{model}:embedContent` so‘roviga aylanadi.
- llama.cpp (`llama-cpp/<model>`, mahalliy server yuklagan har qanday model): kanonik `text` elementlari oddiy satrlarga, `image` / `audio` / `video` esa har biri bittadan `{"content": [part]}` obyektiga aylanadi; bunda inline ma’lumotlar bilan llama-server’ning chat kontent qismlari (`image_url`, `format` qiymati `wav` / `mp3` / `flac` bo‘lgan `input_audio`, `input_video`) ishlatiladi. Har bir yuqori darajadagi element uchun bittadan vektor hosil qilinadi. Server `--embedding --mmproj …` parametrlari bilan ishga tushirilishi shart; proyektorsiz u medianing o‘zini rad etadi. `document` qo‘llab-quvvatlanmaydi.
- Aniq modallik metama’lumotlariga ega bo‘lmagan noma’lum/dinamik modellar tuzilgan kiritmani HTTP 400 bilan rad etadi.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Qo‘llab-quvvatlanmaydigan model/modallik kombinatsiyalari elementni majburan o‘zgartirish o‘rniga HTTP 400 qaytaradi. Eski string/token so‘rovlaridagi kiritmaga tegishli bo‘lmagan kengaytma maydonlari o‘zgartirilmagan holda uzatilishda davom etadi.

```bash
# Barcha embedding modellarini ro‘yxatlash
GET /v1/embeddings
```

### Model narxlari (`pricing`)

OmniRoute model narxini bilganida, yozuv `pricing` obyektini o‘z ichiga oladi. Narxlar
xarajatlarni hisoblashda foydalaniladigan narxlar jadvalidan olinadi: o‘rnatilgan standart
qiymatlar, sinxronlangan narxlar va `/api/pricing` orqali o‘rnatilgan almashtirishlar. Bular
ro‘yxatdagi narxlar bo‘lgani sababli, obuna provayderlari uchun ham token boshiga narx
ko‘rsatiladi.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Maydonlar                                                       | Birlik                       | Izohlar                                                                                                                                                             |
| --------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | Token uchun USD, o‘nlik satr | OpenRouter bilan mos, hech qachon eksponensial yozuvda bo‘lmaydi. Ikki cache maydoni faqat cache narxi mavjud bo‘lganda ko‘rsatiladi.                               |
| `input`, `output`, `cached`, `cache_creation`                   | 1M token uchun USD, son      | Katalogning oldingi versiyalaridan qolgan maydonlar, mavjud mijozlar uchun saqlangan. Narxlar qatorida ular bo‘lsa, `reasoning` va `long_context` ham ko‘rsatiladi. |

- **Kombinatsiyalar** birinchi ko‘rinadigan nishonining narxini oladi. O‘rnatilgan `auto/*`
  kombinatsiyalari so‘rov vaqtida nishon tanlaydi, shuning uchun ularda `pricing` bo‘lmaydi.
- **Bepul modellar** narxi nol bo‘lganda `"0"` (va `0`) ko‘rsatadi. Narxlar qatoriga ega
  bo‘lmagan model katalogda bepul deb belgilangan (`free: true`) yoki o‘rnatilgan bepul
  modellar katalogida ko‘rsatilgan bo‘lsa, `"0"` ni ham ko‘rsatadi.
- **Noma’lum narx:** yozuvda `pricing` kaliti bo‘lmaydi.
- **Kredit asosida hisob-kitob qiluvchi provayderlar** (masalan, Kiro) token boshiga emas,
  so‘rov boshiga haq oladi. Ularning yozuvlarida avval mavjud bo‘lgan 1M token uchun
  raqamli maydonlar saqlanadi, token boshiga satrli maydonlar esa bo‘lmaydi.
- **Variantlar** (reasoning-effort identifikatorlari, no-thinking taxalluslari, discovery va
  gateway akslari) yo‘naltiriladigan model narxini nusxalaydi.
- Maydonlarda faqat bazaviy tariflar ko‘rsatiladi. Uzoq kontekst darajalari (raqamli
  `long_context` maydoni) va xizmat darajasi ko‘paytirgichlari (masalan, Codex fast yoki
  flex) `prompt` yoki `completion` qiymatlarini o‘zgartirmaydi.
- Obyekt barcha autentifikatsiya uslublari uchun bir xil, jumladan `x-api-key` va
  `anthropic-version` bilan Anthropic uslubidagi so‘rov uchun ham (javob
  `{ "object": "list", "data": [...] }` ko‘rinishida qoladi). Amalga oshirilishi:
  `src/app/api/v1/models/catalogPricing.ts`.

### Model id prefikslari (`?prefix=`)

Aksariyat modellar **provayder prefiksi** bilan e’lon qilinadi. Qaysi prefiks olinishi
`MODELS_CATALOG_PREFIX_MODE` funksiya bayrog‘i orqali boshqariladi va so‘rov boshiga query
parametri bilan almashtirilishi mumkin — bu serverning umumiy sozlamasini boshqalar uchun
o‘zgartirmagan holda toza ro‘yxat olishni istagan mijozlar uchun foydali:

```bash
GET /v1/models?prefix=alias        # har bir model uchun bitta id — qisqa taxallus prefiksi
GET /v1/models?prefix=dual         # ikkala shakl (server standart qiymati)
GET /v1/models?prefix=canonical    # faqat to‘liq provayder-id prefiksi
```

| Rejim       | Chiqaradi                                                | Izoh                                                                                                                                                                                                                                |
| ----------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **va** `claude/claude-sonnet-4-6` | **Standart qiymat.** Ikkala id ham bir xil modelga yo‘naltiriladi; konfiguratsiyalarida ikkala shakldan birini qattiq kodlagan mijozlar ishlashda davom etishi uchun saqlangan. Katalog hajmini taxminan ikki baravar oshiradi.     |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Har bir model uchun bitta yozuv. Alohida taxallusga ega bo‘lmagan provayderlar ham o‘z yozuvini chiqaradi, shuning uchun hech narsa yo‘qolmaydi.                                                                                    |
| `canonical` | `claude/claude-sonnet-4-6`                               | Har bir model uchun to‘liq provayder-id prefiksi ostida bitta yozuv. Alohida taxallusga ega bo‘lmagan provayderlar (masalan, `antigravity/…`, `agy/…`) bu yerda ham yagona id sini chiqaradi, shuning uchun hech narsa yo‘qolmaydi. |

`dual` rejimidagi aksni query parametrisiz ham aniqlash mumkin: unda asosiy id ga ishora
qiluvchi `parent` maydoni mavjud.

Model tanlash oynasini ko‘rsatuvchi mijozlar `?prefix=alias` parametrini so‘rashi kerak —
[OmniCopilot VS Code kengaytmasi](../guides/VSCODE-COPILOT.md) aynan shunday qiladi.

### Discovery filtrlari (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ixtiyoriy discovery filtrlarini qabul qiladi. Ulardan hech biri berilmasa,
javob o‘zgarmaydi. Ular chaqiruvchi allaqachon ko‘rishi mumkin bo‘lgan katalogni toraytiradi
(API-key ruxsatlari avval qo‘llanadi) va OpenAI uslubidagi `limit` / `after` sahifalashdan
oldin bajariladi:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ro‘yxatdagi har bir capability true bo‘lishi kerak
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogdagi `type`; bunday qiymatga ega bo‘lmagan qatorlar `chat`
GET /v1/models?q=sonnet&limit=10                           # id yoki nom bo‘yicha katta-kichik harflarni farqlamaydigan moslik
```

| Param         | Values                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | manfiy boʻlmagan butun son, `context_length` bilan taqqoslanadi                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 ta belgi                                                                                      |

Nomaʼlum qiymat yoki manfiy boʻlmagan butun son boʻlmagan `min_context` (masalan, `1.5`)
HTTP `400` qaytaradi va xabarda yaroqli qiymatlar roʻyxati keltiriladi. Amalga oshirish:
`src/app/api/v1/models/catalogFilters.ts`.

### Modellarning saralangan roʻyxati (`POST /v1/models/query`)

`POST /v1/models/query` xuddi shu katalogdan, `GET /v1/models` bilan bir xil
autentifikatsiya va har bir kalit uchun koʻrinish qoidalaridan foydalangan holda qisqa,
deterministik roʻyxat qaytaradi:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Barcha maydonlar ixtiyoriy. `capabilities` va `exclude` massiv yoki vergul bilan ajratilgan satrni
qabul qiladi; `max_output` `max_output_tokens` bilan taqqoslanadi. Natijalar avval `owned_by`,
soʻng `id` boʻyicha saralanadi. `limit` sukut boʻyicha `20` ga teng, `100` dan yuqori qiymatlar
`100` bilan cheklanadi. Notoʻgʻri JSON, nomaʼlum maydon yoki yaroqsiz qiymat HTTP `400` qaytaradi.

### Alohida yashirilgan chat modellari

Provayder sahifasida **Yashirin** deb belgilangan model katalogdan chiqarib tashlanadi va aniq
soʻralganda HTTP `404` / `model_not_found` bilan rad etiladi. Tekshiruv yechilgan provayder va
modeldan, jumladan provayder taxalluslari, mos provayder tuguni prefikslari va ulanish
sukut boʻyicha sozlamalaridan foydalanadi. Kombo yashirilgan maqsadlarni oʻtkazib yuborishi va
koʻrinadigan qoʻshni modeldan foydalanishi mumkin; bajariladigan maqsad qolmaganda esa xuddi shu
xato kodini qaytaradi. Yashirishni bekor qilish keyingi soʻrovda kuchga kiradi. Faqat tasvirlar
uchun qoʻllanadigan koʻrinish ustuvorliklari ayni ID ga ega chat modelini yashirmaydi.

Bu alohida model sozlamasi
[modelni oshkor qilishga ruxsat/taqiq roʻyxatlari](../routing/MODEL_EXPOSURE_LIST.md) dan alohida boʻlib,
ular aniq joʻnatishni saqlab qolgan holda katalogdagi eʼlonlar va avtomatik yoʻnaltirish
nomzodlarini filtrlaydi. API kalitining model ruxsatlari bundan mustaqil ravishda qoʻllanadi.
Katalog prefiksining sukut boʻyicha rejimi `dual` boʻlib qoladi.

### Fikrlashsiz model variantlari

Fikrlash qobiliyatiga ega Claude modellari uchun `/v1/models` id qiymati
`claude-3-omniroute-no-thinking/` bilan prefiks qilingan **fikrlashsiz** variantni ham eʼlon qiladi:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Ushbu id tanlanganda (masalan, har doim `thinking` blokini biriktiradigan Claude Code
konfiguratsiyasida) u haqiqiy `<provider>/<model>` ga qayta yechiladi va fikrlash oʻchiriladi —
`/v1/messages` yoʻlida `thinking:{type:"disabled"}` yoki
`/v1/chat/completions` yoʻlida `reasoning`/`reasoning_effort` maydonlari olib tashlanadi.
Variant faqat fikrlashni qoʻllab-quvvatlaydigan **va** `disabled` qiymatini qabul qiladigan
Claude oilasi modellarida roʻyxatga kiritiladi (masalan, `disabled` qiymatini rad etadigan
faqat moslashuvchan modellar chiqarib tashlanadi). Operatorlar har bir model uchun
`ModelSpec.noThinkingAlias` orqali variantni majburan yoqishi yoki oʻchirishi mumkin.

## ElevenLabs audio generatsiyasi

ElevenLabs API kalitingiz bilan OmniRoute’da `elevenlabs` provider ulanishini sozlang.
Mijozlar **OmniRoute** kaliti orqali autentifikatsiyadan o‘tadi (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gateway saqlangan provider kalitini `xi-api-key` sifatida yuboradi. ElevenLabs kalitini hech qachon gateway bearer tokeni sifatida yubormang.

| Usul | Yo‘l                        | Javob                                           | API kaliti endpoint toifasi |
| ---- | --------------------------- | ----------------------------------------------- | --------------------------- |
| POST | `/v1/sound-generation`      | Native audio baytlari                           | `elevenlabs`                |
| POST | `/v1/music`                 | Native audio baytlari                           | `music`                     |
| POST | `/v1/music/stream`          | Oqimli audio baytlari                           | `music`                     |
| POST | `/v1/music/detailed`        | Native multipart audio va kompozitsiya rejasi   | `music`                     |
| POST | `/v1/music/detailed/stream` | Native SSE metama’lumotlari va audio bo‘laklari | `music`                     |
| POST | `/v1/music/plan`            | JSON kompozitsiya rejasi                        | `music`                     |

Ushbu endpointlar mavjud `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` va `/v1/speech-to-text` yo‘nalishlarini to‘ldiradi. Native JSON maydonlari
hamda `output_format` va `enable_logging` kabi query parametrlari saqlanadi.
`/v1/music/detailed` javoblari o‘z multipart chegaralarini saqlab qoladi; ularni multipart sifatida tahlil qiling.
`/v1/music/detailed/stream` kompozitsiya metama’lumotlari va SSE hodisalaridagi
base64 audio bo‘laklari bilan `text/event-stream` qaytaradi. Barcha oltita yo‘nalish CORS preflight’ni qo‘llab-quvvatlaydi.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Qisqa ovoz effekti. Davomiyligi: 0.5 dan 30 sekundgacha.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Musiqa davomiyligi millisekundlarda ifodalanadi: 3000 dan 600000 gacha.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Bosqichma-bosqich audio yetkazib berish uchun xuddi shu JSON tanasi bilan `/v1/music/stream` dan foydalaning. Kompozitsiya `prompt` yoki `composition_plan` dan aynan bittasini qabul qiladi; `/v1/music/plan` uchun `prompt` talab qilinadi va u ixtiyoriy ravishda `source_composition_plan` ni qabul qiladi. Native sxemalar qo‘shimcha provider maydonlarini saqlab qoladi, shuning uchun kompozitsiya rejasi versiyalari va nozik sozlash parametrlari ElevenLabs’ga yetib boradi.

Yagona `/v1/music/generations` endpointi shuningdek
`elevenlabs/music_v1`, `elevenlabs/music_v2` va `elevenlabs/music_v2_5` ni qabul qiladi. Faol ElevenLabs ulanishi mavjud bo‘lganda, ushbu modellar musiqa katalogida ko‘rsatiladi. Bu endpoint
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ni qaytaradi. Uning `duration` maydoni
sekundlarda bo‘ladi va `music_length_ms` ga moslashtiriladi; aniq ko‘rsatilgan `music_length_ms` ustuvor hisoblanadi.
`instrumental` `force_instrumental` ga moslashtiriladi, native maydon esa ustuvor hisoblanadi.
Oqimli uzatish uchun native oqimli endpointlardan, faqat kompozitsiya rejasi asosidagi so‘rovlar uchun esa native kompozitsiya endpointidan foydalaning.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Endpoint, model, budjet va ulanish cheklovlari upstream chaqiruvidan oldin qo‘llanadi. Native
yo‘nalishlar upstream status kodlari va xatolik tanalarini o‘zgartirmagan holda qaytaradi, jumladan
reja cheklovi uchun `402` va kvota cheklovi uchun `429`. Mavjud bo‘lganda `character-cost`, `song-id`, `request-id` va `retry-after`
sarlavhalari saqlanadi. Bepul kredit qoldig‘i har bir musiqa modeli, chiqish formati yoki API funksiyasidan foydalanish imkoniyatini kafolatlamaydi: har bir so‘rov bo‘yicha huquqni ElevenLabs belgilaydi.
Yagona endpoint xatolik status kodlarini OmniRoute’ning me’yorlashtirilgan xatolik konvertida saqlab qoladi.

Upstream shartnomalari: [ovoz effektlari](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[musiqa kompozitsiyasi](https://elevenlabs.io/docs/api-reference/music/compose) va
[oqimli musiqa tafsilotlari](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

Barcha POST yo‘llari bir xil shakldan foydalanadi: `Bearer your-api-key` + Zod tomonidan tekshirilgan JSON tanasi (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` va boshqalar, `src/shared/validation/schemas.ts` fayliga qarang). Sxema tekshiruvi muvaffaqiyatsiz bo‘lsa, 4xx qaytariladi.

```bash
# Qayta tartiblash (bulut registri provayderi yoki "<prefix>/<model>" ko‘rinishidagi OpenAI bilan mos provayder tuguni)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina tasniflash (Foundation API hisob ma’lumotlari)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina segmentatori
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina qidiruvi (s.jina.ai; provayder taxalluslari: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Moderatsiyalar
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (yoki so‘ralgan formatdagi) tanani qaytaradi
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS uchun til va ovoz talab qilinadi: `language` sukut bo‘yicha "en" qiymatiga ega; yetishmayotgan
# ovoz yoki OpenAI standart ovoz nomi (alloy, nova, …) "Adrian" ga aylantiriladi
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Rasmni tahrirlash (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Video / musiqa generatsiyasi (provayder prefiksli model identifikatori)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Rerank provayder tugunlari:** `POST /v1/rerank` endi `<node-prefix>/<model>` manzili orqali OpenAI bilan mos provayder tugunlariga (oMLX, vLLM, Infinity, gateway ortidagi TEI, …) ham yo‘naltiriladi. Loopback tugunlari (`localhost`, `127.0.0.1`, `172.16.0.0/12`) har doim mos keladi, shuningdek operator `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` da ko‘rsatgan xost nomlari ham mos keladi (masalan, `http://reranker:8080/v1` kabi Docker/Compose xizmati nomi; bunday tugunlar to‘g‘ridan-to‘g‘ri chaqiriladi, hech qachon `HTTP(S)_PROXY` yoki ulanishning biriktirilgan proksisi orqali emas). Boshqa istalgan xostdagi tugunlar — LAN kompyuteri yoki Tailscale peer’i — faqat operator `RERANK_REMOTE_PROVIDER_NODES` feature flag’ini yoqqanida **va** tugunning asosiy URL’i provayderning chiqish URL siyosatidan (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) o‘tgandagina mos keladi. Xotira mexanizmining rerank bosqichi loopback orqali ushbu yo‘nalishni chaqiradi, shuning uchun Xotira sozlamalaridagi `rerankProviderModel` uchun ham ayni qoida amal qiladi.
>
> **Mahalliy server shakllari:** tugun `<base>/v1/rerank` manzilida chaqiriladi va 404 holatida `<base>/rerank` manzilida chaqiriladi (Infinity, TEI). Upstream tanasi Cohere/OpenAI yozilish variantini (`documents`, `return_documents`) ham, TEI yozilish variantini (`texts`, `return_text`) ham o‘z ichiga oladi, upstream javobi esa Cohere konvertiga normallashtiriladi: TEI’ning oddiy `[{index, score, text}]` javobi, yupqa gateway’lardan keladigan `{results: [{index, score}]}` va Voyage uslubidagi `{data: [...]}` javoblarning barchasi mijozga `{results: [{index, relevance_score, document?}]}` ko‘rinishida, ball bo‘yicha saralangan va `top_n` bilan cheklangan holda qaytariladi.

> **Provayder tugunlarini aniqlash:** OpenAI bilan mos provayder tugunidagi modellar `GET /v1/models` javobida tugun prefiksi ostida ko‘rinadi. Endpoint metama’lumotlariga ega bo‘lmagan qatorlar (mahalliy `/v1/models` ro‘yxatlariga xos holat) tugunning `apiType` qiymatini meros qilib oladi, shuning uchun `embeddings` tugunidagi modellar chat turiga sukut bo‘yicha o‘tish o‘rniga `type: "embedding"`, `rerank` tugunidagi modellar esa `type: "rerank"` bo‘ladi; sinxronlangan yoki qo‘lda qo‘shilgan qatordagi aniq `supportedEndpoints` qiymati bundan ustun turadi.

### Xom va chegara bo‘yicha moslashtirilgan kvota foizlari

`/api/usage/om-usage` dan foydalanayotganda chaqiruvchilar **oddiy matnli chiqish** va strukturaviy
**JSON chiqishi** tomonidan taqdim etiladigan foizlar o‘rtasidagi farqni hisobga olishlari kerak:

| Jihat                      | Oddiy matn formati (`/api/usage/om-usage` / `@@om-usage`)                                                         | JSON formati (`?format=json`)                                                           |
| :------------------------- | :---------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------- |
| **Chiqish maydoni**        | `NN% left` (masalan, `20% left`)                                                                                  | `provider.quotas` / `providers[].quotas`                                                |
| **O‘lchov**                | **Chegara bo‘yicha moslashtirilgan foydalanish mumkin bo‘lgan ruxsat**: chegara qiymatidan yuqorida qolgan sig‘im | **Provayderning xom kvotasi**: moslashtirilmagan provayder o‘lchovi                     |
| **Chegarani masshtablash** | Himoyalangan zaxira `0% left` sifatida ko‘rsatilishi uchun `effectiveRemainingPercent()` orqali masshtablanadi    | Mavjud emas (provayder xabar qilgan xom holat qiymatlari)                               |
| **Chegara ma’lumotlari**   | Ko‘rsatiladigan foizga kiritiladi                                                                                 | Har bir ulanish uchun `quotaWindowThresholds` da (yoki server standartlarida) saqlanadi |
| **Asosiy iste’molchi**     | Interaktiv CLI’lar, terminal so‘rovlari, inson operatorlar                                                        | Dasturiy integratsiyalar, dashboard’lar, tahlil va hisob-kitob kuzatuvchilari           |

#### Chegarani moslashtirish formulasi

OmniRoute yuqori oqimdagi tugashlarning oldini olish uchun proaktiv kvota chegaralarini qo‘llab-quvvatlaydi
(ular ulanishdagi `quotaWindowThresholds`, provayder standartlari yoki global barqarorlik sozlamalari
orqali sozlanadi). Kvota oynasida chegara (masalan, `cutoff = 25%`) faol bo‘lsa, matn ko‘rsatuvchisi
qolgan ruxsatni quyidagicha hisoblaydi:

- Agar `remaining <= cutoff` bo‘lsa: `0%` qaytaradi.
- Agar `remaining > cutoff` bo‘lsa: `((remaining - cutoff) / (100 - cutoff)) * 100`.

Formatlangan matn chiqishi buni eng yaqin butun songacha (`Math.round(...)`) yaxlitlaydi.

#### Misol tariqasida

Provider oynasida **60% xom foydalanish** (shuning uchun **40% xom qolgan kvota**) va sozlangan
**25% qolgan-kvota kesish** chegarasi mavjud:

| Ko‘rinish                     | Hisoblash                                          | Qolgan  |           Nazarda tutilgan foydalanilgan           |
| :---------------------------- | :------------------------------------------------- | :-----: | :------------------------------------------------: |
| **Xom JSON (`?format=json`)** | Yuqori oqim surati (`quotas[window]`)              | **40%** |                      **60%**                       |
| **Matn formati (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (agar `100 - remaining` orqali hisoblansa) |

- **Matn nima uchun 20% qolganini ko‘rsatadi:** Hisobdagi jismoniy kvotaning 40% qolgani ichidan 25% kesish siyosati tomonidan
  band qilinadi. Router ushbu ulanishga yo‘naltirishni to‘xtatishidan oldin chaqiruvchida foydalanish mumkin bo‘lgan 75% zaxiraning
  atigi 15% qolgani mavjud. Masshtablash ulanish yo‘naltirish to‘xtatiladigan paytda aynan (`0% left`) tugaganini bildirishi uchun
  ta’minlaydi.
- **JSON nima uchun xom qiymatlarni saqlab qoladi:** JSON ma’lumotlar to‘plami aniq provayder suratini (`UsageSnapshot`) qaytaradi,
  shuning uchun tashqi vositalar server tomonidagi axborot yo‘qotuvchi masshtablashsiz yuqori oqimdagi foydalanish va ulanish darajasidagi
  `quotaWindowThresholds` qiymatlaridan foydalanishi mumkin.

#### Iste’molchilarni ko‘chirish bo‘yicha yo‘riqnoma

Agar tashqi integratsiya (masalan, muharrir plagini yoki agent kengaytmasi) ilgari matn
endpointidan (`NN% left`) ma’lumotlarni ajratib olib, foydalanilgan foizni `100 - NN` sifatida hisoblagan bo‘lsa,
`?format=json` ga ko‘chirish quyidagilarni anglatadi:

- Xom JSON qiymatlarini o‘qish **haqiqiy yuqori oqim iste’molini** aks ettiradi (yuqoridagi misolda foydalanilgan qiymat 60%).
- Agar integratsiya matn endpointining foydalanish mumkin bo‘lgan ruxsat semantikasini saqlab qolishni istasa, u
  ulanish darajasidagi almashtirishlar uchun `quotaWindowThresholds` dan foydalanib, samarali qolgan qiymat formulasini mijoz tomonida
  hisoblay oladi.

### Kechikishga ta’siri

Semantik keshdagi **HIT** javobni **upstream chaqiruvisiz** keshdan qaytaradi, shu sababli bildirilgan `X-OmniRoute-Response-Latency` deyarli nolga teng bo‘ladi
(asl upstream kechikishidan qat’i nazar). Kechikishga sezgir mijozlar
(benchmark va p50/p99 monitoring) javob sarlavhasidagi
`X-OmniRoute-Cache-Latency` qiymatini tekshirishi kerak:

| Value       | Meaning                                                         |
| ----------- | --------------------------------------------------------------- |
| `synthetic` | Javob keshdan qaytarildi; kechikish haqiqiy upstream vaqti emas |
| _(absent)_  | Javob haqiqiy upstream chaqiruvidan qaytarildi                  |

### Kalit bo‘yicha keshni chetlab o‘tish

API kalitlari `cacheDefaultMode` orqali semantik keshdan o‘qishni o‘chirib qo‘yishi mumkin:

| Value    | Behavior                                                                         |
| -------- | -------------------------------------------------------------------------------- |
| `legacy` | Oddiy kesh xatti-harakati (standart)                                             |
| `bypass` | Kesh qidiruvini butunlay o‘tkazib yuboradi; har doim upstream’ga murojaat qiladi |

Kalit yaratishda (`POST /api/keys`) yoki yangilashda (`PATCH /api/keys/[id]`) belgilanadi:

```json
{ "cacheDefaultMode": "bypass" }
```

### So‘rov bo‘yicha keshni chetlab o‘tish

Har qanday so‘rov kalit sozlamalaridan qat’i nazar, keshni chetlab o‘tishi mumkin:

```
X-OmniRoute-No-Cache: true
```

OmniRoute foydalanish panellari Claude va Codex obuna limitlarini o‘qish uchun chaqiradigan uchta [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)

OmniRoute’ga yo‘naltiring va boshqaruv kaliti sifatida `manage` qamroviga ega API kalitidan foydalaning. Yo‘nalishlar
`/v0/management/*` va `/api/v0/management/*` manzillarida taqdim etiladi.

| Method | Path                         | Description                                                                                                                                                                    |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/v0/management/auth-files`  | Claude va Codex OAuth ulanishlari `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }` ko‘rinishida. Tokenlar mavjud emas                                    |
| POST   | `/v0/management/api-call`    | `{ auth_index, method, url, header?, data? }` tanasi. Hisob qaydnomasining tokeni bilan ruxsat berilgan bitta so‘rovni yuboradi va `{ status_code, body }` qiymatini qaytaradi |
| POST   | `/v0/management/reset-quota` | `{ auth_index }` tanasi. Bitta hisob qaydnomasining ulanish kutish vaqtini, model bloklanishlarini va Codex’ning qamrov bo‘yicha kutish vaqtlarini tozalaydi                   |

- `auth_index` — OmniRoute ulanish identifikatori. `provider` — `claude` yoki `codex` (faqat OAuth
  ulanishlari; `anthropic` API-key provayderi ro‘yxatga kiritilmaydi). Codex uchun
  `id_token.chatgpt_account_id` saqlangan ish maydoni identifikatori, `plan_type` esa saqlangan tarifdir.
- `api-call` umumiy proksi emas. U faqat Claude uchun `GET
https://api.anthropic.com/api/oauth/usage` va Codex uchun `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` hamda
  `POST .../wham/rate-limit-reset-credits/consume` so‘rovlarini qabul qiladi; har biri faqat mos
  provayderga tegishli hisob qaydnomasi uchun ishlaydi. Boshqa barcha so‘rovlar upstream’ga ulanmasdan
  `403` qaytaradi. Murojaat qiluvchining
  `Authorization` sarlavhasi (`$TOKEN$` o‘rnini bosuvchi qiymat bilan birga) e’tiborga olinmaydi: OmniRoute
  ulanishning kirish tokenini qo‘shadi, token muddati tugashiga yaqin bo‘lsa, avval uni yangilaydi va faqat

  `Accept`, `Content-Type`) uzatadi. `Chatgpt-Account-Id` mavjud bo‘lmasa, saqlangan ish maydoni identifikatori
  standart qiymat sifatida ishlatiladi.
  So‘rovlar 15 soniyadan so‘ng vaqt tugashi bilan to‘xtatiladi va ulanish proksisidan foydalanadi.
- `reset-quota` terminal holatlarni (`banned`, `expired`, `credits_exhausted`) o‘zgartirmaydi. Noma’lum
  `auth_index` `404` qaytaradi.

**Autentifikatsiya:** dashboard sessiyasi yoki `manage` qamroviga ega API kaliti, hatto login o‘chirilgan
bo‘lsa ham talab qilinadi (yo‘llar `ALWAYS_PROTECTED_API_PATHS` tarkibida). Faqat inference uchun mo‘ljallangan kalitlar

Sinxronlangan/import qilingan modellar uchun `PUT /api/provider-models` `provider`, `modelId` va
`maxOutputTokenOverride` qiymatlarini qabul qiladi: musbat butun son qo‘lda belgilangan chiqish tokenlari

ishlash vaqtidagi `max_output_tokens` imkoniyatidan foydalanadi va model qayta sinxronlanganda ham saqlanib qoladi. OpenAI bilan mos
provayder sahifasida xuddi shu tahrirlash/tozalash boshqaruvlari mavjud bo‘lib, aniq tasvirni ko‘rish qo‘llab-quvvatlashiga ega modellarni belgilaydi.

Mos provayder tugunida yozish yo‘llari (`POST`, `PUT`, `PATCH`, `DELETE` va
`/api/provider-models/validate-and-add`) model identifikatorini yuqori oqimdagi yalang‘och identifikator sifatida saqlaydi: prefiksli ro‘yxatdan
qo‘yilgan identifikator tugunning o‘z prefiksining boshidagi takroriy ketma-ketlikni qisqartiradi va javoblarda saqlangan identifikator qaytariladi. Kanonik provayderlarning qiya chiziqli identifikatorlari (masalan, `nvidia/nemotron-…`)
o‘zgartirilmasdan saqlanadi. `/v1/models` hech qachon ichma-ich joylashgan `<prefix>/<prefix>/<model>` identifikatorini chiqarmaydi.

Custom Chat Completions tugunlari aniq reasoning opt-out sozlamalarini upstream backend uchun moslashtiradi. Muvaffaqiyatli ulanish testi `/models` yozuvida tan olingan `owned_by` qiymati: `vllm`, `sglang` yoki `llamacpp` ekanini tasdiqlagan har bir aniq model ID uchun chat-template boshqaruvlarini avtomatik tanlaydi. Shaffof OpenAI-compatible wrapperlar asl model yozuvini ichki `openai` obyektida saqlab qolishi mumkin; aniqlash bunday envelope’larning uchtasigacha davom etadi. Egalik ma’lumoti mavjud bo‘lmagan, noma’lum yoki qarama-qarshi bo‘lgan modellar oddiy OpenAI xatti-harakatini saqlab qoladi. Aniqlash mavjud katalog so‘rovini qayta ishlatadi, completion tokenlarini yaratmaydi va ulanish endpointi o‘zgarganda bekor qilinadi.

Bu metama’lumotni taqdim etmaydigan backend uchun xatti-harakatni belgilash maqsadida mavjud qisman provider update API’dan foydalaning:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Ushbu body’ni `PUT /api/providers/<connection-id>` bilan yuboring. Bu ulanishda `none` qiymatiga ega aniq reasoning effort `chat_template_kwargs.thinking=false` va `chat_template_kwargs.enable_thinking=false` sifatida yuboriladi. Server tomoni reasoning qoidasi effort’ni majburlamasa, aniq native template qiymatlari ustuvor bo‘lib qoladi. Bu sozlama faqat custom OpenAI-compatible ulanish Chat Completions body’sini yuborganda qo‘llanadi; Responses so‘rovlari va oddiy providerlar o‘zlarining native request shaklini saqlab qoladi. Oddiy OpenAI `reasoning_effort` passthrough’ini majburlash uchun `reasoningControl` qiymatini `openai` qilib belgilang yoki avtomatik aniqlashdan foydalanish uchun uni olib tashlang/`null` qilib belgilang.

Claude Code auto-mode classifier so‘rovlari aniq reasoning boshqaruvlarini o‘z ichiga olmaganda, native thinking’ni sukut bo‘yicha o‘chirilgan holatga o‘rnatadi. Aniqlash model nomlari yoki completion limitlaridan emas, Claude-format so‘rovlaridagi classifier’ning system marker’idan foydalanadi. Aniq body boshqaruvlari, qo‘llab-quvvatlanadigan effort/thinking header’lari, routing qoidalari va aniqlangan model effort’i mavjud ustuvorliklarini saqlab qoladi. Har ikkala classifier bosqichi ham o‘z prompt’lari, completion limitlari, stop sequence’lari va upstream’dan olingan haqiqiy ruxsat verdict’larini saqlab qoladi; ikkinchi bosqich so‘ralgan visible reasoning’ni oddiy matn sifatida hali ham hosil qilishi mumkin.

#### Model limitlarining kelib chiqishi

`GET /api/models?withLimits=1` (`true` ham mumkin; `0`/`false` yoki parametrni qoldirib ketish standart payload’ni o‘zgartirmaydi) har bir model qatoriga `contextWindow`, `maxInputTokens`, `maxOutputTokens` va `capsSource` obyektini qo‘shadi. `capsSource` har bir limitni ta’minlagan qoidani ko‘rsatadi, shuning uchun kutilmagan limitni (masalan, 1M modelda 128k) uning kelib chiqishigacha kuzatish mumkin. Aniqlangan qiymatlar routing foydalanadigan qiymatlarning o‘zidir; bu flag faqat maydonlarni qo‘shadi va hech qachon qiymatni o‘zgartirmaydi. Boshqa istalgan `withLimits` qiymati `400` bilan rad etiladi.

| `capsSource` value                           | Kelib chiqishi                                                         |
| -------------------------------------------- | ---------------------------------------------------------------------- |
| `override:context`                           | Saqlangan context-window override (`model_context_overrides`)          |
| `override:max_input` / `override:max_output` | Saqlangan `max_input_tokens` / `max_output_tokens` capability override |
| `static-authoritative:<provider>/<model>`    | Statik authoritative context-window jadvali                            |
| `synced:<provider>/<model>`                  | models.dev’dan sinxronlangan capability qatori                         |
| `registry:<provider>/<model>`                | Provider registry yozuvi                                               |
| `spec:<model>`                               | Statik model spetsifikatsiyasi                                         |
| `effort-base:` prefix                        | Effort-suffixed variantning base modelidan olingan qator               |
| `none`                                       | Hech bir manba limitni e’lon qilmaydi (qiymat `null`)                  |

Implementatsiya: `src/lib/modelCapabilities.ts` ichidagi `getResolvedModelCapabilitiesWithLimitSources()` va `src/lib/modelCapabilityLimits.ts` ichidagi ustuvorlik zanjirlari.

## Audio transkripsiyasi

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Sozlangan istalgan STT provayderidan foydalanib audio fayllarni transkripsiya qiling. Yo‘lning birinchi segmenti mahalliy provayderni (`openai/…`, `deepgram/…`) tanlaydi. Boshqa vendor modelini qayta eksport qiladigan gatewaylar kvalifikatsiyalangan identifikatordan foydalanadi
(`openrouter/deepgram/nova-3`).

**So‘rov:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Javob:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Model identifikatorlariga misollar:** `openai/whisper-1` (OpenAI kalitini talab qiladi),
`openrouter/deepgram/nova-3` (OpenRouter kalitini talab qiladi),
`deepgram/nova-3` (mahalliy Deepgram kalitini talab qiladi). Oddiy
`deepgram/nova-3` so‘rovi OpenRouter’dan **foydalanmaydi**.

**Qo‘llab-quvvatlanadigan formatlar:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** Gemini Live
WebSocket orqali fayl rejimida transkripsiya qilish (Gemini API kalitini talab qiladi). Yuklangan fayl
`ffmpeg` yordamida 16 kHz mono PCM formatiga o‘tkaziladi
(`PATH` da bo‘lishi kerak, agar fayl allaqachon 16 kHz mono PCM WAV bo‘lmasa), sessiyaga uzatiladi va
yakuniy matn `{ "text": "..." }` ko‘rinishida qaytariladi. Ixtiyoriy `language` va `prompt` forma maydonlari
uzatiladi. Cheklovlar: 25 MiB dan katta yuklamalar yoki dekodlangan audio davomiyligi 10 daqiqadan
uzun bo‘lsa, `413` javobi qaytariladi; konvertatsiya 60 soniyadan ko‘proq davom etsa, jarayon
to‘xtatiladi va `504` javobi qaytariladi. API kaliti faqat `x-goog-api-key` sarlavhasida yuboriladi, hech qachon WebSocket URL manzilida emas.

## Token Limitlari

Har bir API kaliti uchun **token** byudjetlari (yuqoridagi USD asosidagi Budgetdan farqli). So‘rov yo‘lida inline tarzda qo‘llanadi: kalitning joriy oyna bo‘yicha sarfi limitiga yetganda, so‘rovlar `429 Too Many Requests` bilan rad etiladi. Limitlar muayyan `model`, `provider` uchun belgilan yoki kalit bo‘yicha `global` qo‘llanilishi mumkin; so‘rovga bir nechta limit mos kelganda, eng cheklovchisi ustun bo‘ladi.

```bash
# Kalitning token limitlarini ro‘yxatlash (joriy oyna sarfini o‘z ichiga oladi)
GET /api/usage/token-limits?apiKeyId=key-123

# Token limitini yaratish yoki yangilash
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Token limitini id bo‘yicha o‘chirish
DELETE /api/usage/token-limits?id=tl-abc
```

> **Sxema qaydlari** (`setTokenLimitSchema`): `apiKeyId` va `scopeType` (`model` | `provider` | `global`) majburiy. `scopeType` `global` bo‘lmaganda, `scopeValue` majburiy (masalan, `model` qamrovi uchun model id, `provider` qamrovi uchun provider id). `tokenLimit` musbat butun son bo‘lishi kerak (satr qiymatdan o‘giriladi). Ixtiyoriy maydonlar: `id` (yaratishda kiritilmaydi, yangilashda beriladi), `resetInterval` (`daily` | `weekly` | `monthly`, standart qiymati `monthly`), `resetTime` (`HH:MM`), `enabled` (standart qiymati `true`). `GET` javoblarida har bir limit `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` va `nextResetAt` bilan boyitiladi. Bu boshqaruv sinfidagi endpoint hisoblanadi (autentifikatsiya markaziy authz pipeline tomonidan majburiy qo‘llanadi).

1. Mijoz `/v1/*` manziliga so‘rov yuboradi
2. Route handler `handleChat`, `handleEmbedding`, `handleAudioTranscription` yoki `handleImageGeneration` funksiyasini chaqiradi
3. Model aniqlanadi (bevosita provider/model yoki alias/combo)
4. Hisob mavjudligini filtrlash orqali lokal DB’dan hisob ma’lumotlari tanlanadi
5. Chat uchun: `handleChatCore` semantik/imzo keshini tekshiradi va combo siqish sozlamalarini aniqlaydi
6. Yoqilganda, provider tarjimasidan oldin proaktiv siqish ishga tushadi (`lite`, Caveman, RTK yoki stekli)
7. Provider executor yuqori darajadagi so‘rovni yuboradi
8. Javob mijoz formatiga qayta tarjima qilinadi (chat uchun) yoki o‘zgartirilmagan holda qaytariladi (embeddings/images/audio)
9. Foydalanish ma’lumotlari, siqish analitikasi va so‘rov jurnallari qayd etiladi
10. Xatolar yuz berganda, combo qoidalariga muvofiq fallback qo‘llanadi

Arxitekturaning to‘liq ma’lumotnomasi: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Barqarorlik (kengaytirilgan)

OmniRoute uchta mustaqil vaqtinchalik xatolik mexanizmini taqdim etadi; quyidagi boshqaruv endpointlari operatorlarga ularni o‘qish va bekor qilish imkonini beradi:

| Qo‘llanish sohasi    | Holat saqlanishi                             | O‘qish                                    | Qayta o‘rnatish / tozalash                                                          |
| -------------------- | -------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------- |
| Provayder uzgichi    | `domain_circuit_breakers` + xotirada         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                                        |
| Ulanish kutish vaqti | Provayder ulanishlaridagi `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (qayta faollashtirish kechiktirib amalga oshiriladi; provayder PUT orqali tozalang) |
| Model blokirovkasi   | Xotiradagi model mavjudligi reyestri         | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                            |

`PATCH /api/resilience` `providerBreaker.oauth` va `providerBreaker.apikey` ostidagi provayder uzgichi sozlamalarini bekor qilishni qabul qiladi. Har bir profil `degradationThreshold`, `failureThreshold` va `resetTimeoutMs` maydonlarini qo‘llab-quvvatlaydi; ayni maydonlar Dashboard → Settings → Resilience bo‘limida ham mavjud.

```bash
# Bitta model blokirovkasini tozalash
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Barcha blokirovkalarni o‘chirish
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

To‘liq konseptual ma’lumotnoma va uzgichning standart sozlamalari uchun [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" va [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) hujjatlariga qarang.

### Tezlik cheklovi navbati va avtomatik yoqish xavfsizlik tarmog‘i

- **Qo‘llab-quvvatlanadigan yozish yo‘li**: `POST /api/rate-limits` orqali `{"connectionId": "<id>", "enabled": true|false}` tanasi bilan ulanish uchun tezlik cheklovi himoyasini yoqish yoki o‘chirish mumkin. `PUT /api/providers/[id]` ataylab `rateLimitProtection`ni o‘zgartirmaydi yoki almashtirmaydi (#11278).
- **`enabled: false` ma’nosi**: `enabled: false` qiymatini belgilash ulanish uchun aniq ko‘rsatilgan himoyani olib tashlaydi, ammo **faol API-key ulanishini global avtomatik yoqish xavfsizlik tarmog‘idan (`autoEnableApiKeyProviders = true`) chiqarib tashlamaydi**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) ichida `false` va `undefined` bir xil hisoblanadi; aniq himoyaga ega bo‘lmagan faol API-key ulanishlari avtomatik yoqish xavfsizlik tarmog‘i ostida himoyalangan bo‘lib qoladi.
- **Global o‘chirish**: API-key ulanishlarini tezlik cheklovi navbatsiz ishlatish uchun xavfsizlik tarmog‘ini `RATE_LIMIT_AUTO_ENABLE=false` (env) orqali yoki `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) yordamida global miqyosda o‘chiring.

```bash

Authorization: Bearer your-api-key   # ixtiyoriy, faqat OMNIROUTE_API_KEY o‘rnatilgan bo‘lmasa
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Qo‘llab-quvvatlanadigan metodlar (`settings.a2aEnabled` yoqilgan bo‘lishi kerak):

O‘rnatilgan skilllar: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

## Autentifikatsiya

Toʻrtta hisob maʼlumotlari oilasi (dashboard sessiyasi, mahalliy CLI tokeni, `oma_live_…` Access Token, manage doirasidagi API kaliti) va ularning inference kalitlaridan farqi haqida [Management Authentication](../guides/MANAGEMENT-AUTH.md) qoʻllanmasiga qarang.

- Dashboard yoʻnalishlari (`/dashboard/*`) `auth_token` cookieʼsidan foydalanadi
- Kirishda saqlangan parol xeshi ishlatiladi; muqobil holatda `INITIAL_PASSWORD`
- `requireLogin` `/api/settings/require-login` orqali yoqilishi yoki oʻchirilishi mumkin
- `/v1/*` yoʻnalishlari `REQUIRE_API_KEY=true` boʻlganda ixtiyoriy ravishda Bearer API kalitini talab qiladi
- Ushbu maʼlumotnomadagi "management token" / "management-scoped API key" atamalari shu qoʻllanmada keltirilgan oilalardan birini anglatadi — aniqlanmagan qoʻshimcha maxfiy turini emas

> **Moslikni buzuvchi oʻzgarish (v3.8.0)** — `/api/v1/agents/tasks/*` va cooldown boshqaruv endpointlari endi **management auth** (dashboard `auth_token` cookieʼsi yoki management-scoped API kaliti)ni talab qiladi. Avval ushbu yoʻnalishlarga autentifikatsiyasiz murojaat qilgan mijozlar `401 Unauthorized` javobini oladi. `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) kommitiga qarang.
