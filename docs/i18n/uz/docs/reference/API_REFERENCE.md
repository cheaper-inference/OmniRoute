## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Funksiya yozing..."}
  ],
  "stream": true
}
```

#### Har bir soʻrov uchun hisobni biriktirish

Provayderda bir nechta ulanish (hisoblar yoki kalitlar) mavjud boʻlsa, OmniRoute odatda ulardan birini
hisob tanlash strategiyasi orqali tanlaydi. Buning oʻrniga soʻrov `x-omniroute-connection` sarlavhasi
yordamida muayyan ulanishga biriktirilishi mumkin:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "salom"}]}'
```

- **ID’ni qayerdan topish mumkin.** Boshqaruv panelida provayder sahifasini oching
  (**Dashboard → Providers → <provider>**) va ulanish qatoridagi `xxxxxxxx…` ID belgisini
  bosing — bu to‘liq ulanish ID’sini nusxalaydi.
- **Qaysi so‘rovlar uni hisobga oladi.** `/v1/chat/completions`, `/v1/messages` va
  `/v1/responses` manzillaridagi bitta modelli so‘rovlar (`provider/model`). Kombinatsiyalar sarlavhani e’tiborsiz qoldiradi:
  buning o‘rniga har bir kombinatsiya bosqichi uchun hisobni o‘sha bosqichning o‘z ulanishi orqali biriktiring.
- **Biriktirish afzallik emas, qat’iy qoidadir.** Faqat biriktirilgan ulanishdan foydalaniladi.
  So‘rov ichidagi nosozlik hisobning kutish muddatini qayd etadi, ammo ayni provayderning
  boshqa hisobiga **o‘tmaydi**.
- **Kutish muddati va kvota biriktirishni bekor qiladi.** Biriktirilgan ulanish kutish muddatida bo‘lsa,
  kvotasi tugagan yoki kvota siyosati tomonidan bloklangan bo‘lsa, keyingi so‘rovlar, xuddi biriktirilmagan trafik kabi,
  provayderning boshqa ulanishlariga o‘tadi.
- **Noma’lum yoki o‘chirilgan ID’lar xatolikka olib keladi.** Provayderning faol to‘plamida bo‘lmagan ID
  (o‘chirilgan, faolsizlantirilgan yoki boshqa provayderga tegishli) mos hisob qoldirmaydi, shuning uchun so‘rov
  boshqa yo‘nalishga sezdirmasdan yuborilish o‘rniga xatolik bilan yakunlanadi.

Claude Code maxsus sarlavhalarni `ANTHROPIC_CUSTOM_HEADERS` orqali yuboradi. Uni
`~/.claude/settings.json` faylidagi `env` blokiga yoki har bir loyiha uchun boshqa hisobni biriktirish maqsadida
loyiha darajasidagi `.claude/settings.json` fayliga joylashtiring:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Manba: `src/sse/handlers/chat.ts` (sarlavhani o‘qish), `src/sse/services/auth.ts` va
`src/sse/services/sessionAffinityPin.ts` (biriktirishni bekor qilish va to‘plamda mavjud emasligini tekshirish).

> **Xarajat telemetriyasi sarlavhalari:** oqimsiz muvaffaqiyatli javoblar `X-OmniRoute-*` xarajat telemetriyasi to‘plamini ham o‘z ichiga oladi — `X-OmniRoute-Response-Cost` (USD, nuqtadan keyin qat’iy 10 ta raqam; bepul/narxi belgilanmagan holatlar uchun `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` va `X-OmniRoute-Fallback-Attempts` (faqat > 0 bo‘lganda), shuningdek `X-OmniRoute-Request-Id` va `X-OmniRoute-Version`. Ular chat yakunlash so‘rovlari, `/v1/responses`, `/v1/messages` **hamda media endpointlari** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` va `/v1/moderations` (xarajat har doim `0`) tomonidan chiqariladi. Narxlash mavjud bo‘lsa, media xarajati har bir modallik bo‘yicha (har bir rasm, soniya, belgi yoki qidiruv birligi uchun) hisoblanadi, aks holda `0` bo‘ladi (xatoda ishlashni davom ettirish).

> **Keshga mos kelish xarajati semantikasi:** semantik keshga mos kelganda (`X-OmniRoute-Cache-Hit: true`) yuqori oqimga hech qanday chaqiruv qilinmaydi, shuning uchun `X-OmniRoute-Response-Cost` qiymati `0.0000000000` bo‘ladi (moslikni taqdim etishning **qo‘shimcha** xarajati). Asl/yuzaga kelishi mumkin bo‘lgan xarajat `X-OmniRoute-Cost-Saved` orqali alohida ko‘rsatiladi. Billing tizimi iste’molchilari `X-OmniRoute-Response-Cost` qiymatlarini jamlashi kerak (keshga mos kelishlar hech qanday xarajat talab qilmaydi); kesh tahlili esa `X-OmniRoute-Cost-Saved` qiymatlarini jamlashi mumkin.

## Eksklyuziv boshqariladigan sessiya ijaralari

Eksklyuziv boshqariladigan sessiya ijarasi ixtiyoriy, mijozdan mustaqil marshrutlash shartnomasidir: bitta faol egasi bitta mos OmniRoute ulanishiga ega boʻladi. U modelni ijaraga olmaydi, OAuth talab qilmaydi, maʼlum bir mijozni aniqlamaydi yoki maʼlum bir provayderni talab qilmaydi.

Autentifikatsiya qiluvchi API kaliti `lease:exclusive` doirasiga va aniq boʻsh boʻlmagan `allowedConnections` roʻyxatiga ega boʻlishi kerak. Maʼlumotlar bazasini oʻzgartirish chegarasi kalit yaratish va qisman yangilashda ikkala maydonni birgalikda qoʻllaydi.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Muvaffaqiyatli olish, yangilash va chiqarish javoblari vaqt tamgʻalarini, `state`ni va aniq musbat `generation`ni koʻrsatadi, ammo hech qachon tanlangan ulanish yoki hisobga olish maʼlumotlarini koʻrsatmaydi. Yangilash va chiqarish JSON tanasida generationni taqdim etadi:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Faol ijara egasi joriy bogʻlanishi uchun maxfiylikni saqlovchi koʻrsatish metamaʼlumotlarini aniq soʻrashi mumkin:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ushbu ixtiyoriy status harakati shaffof egasi, autentifikatsiya qilingan boshqariladigan API kaliti va bitta maʼlumotlar bazasi tranzaksiyasidagi aniq faol generation bilan himoyalangan. `displayName` faqat qisqartirilgan konfiguratsiya qilingan ulanish nomi; xavfsiz konfiguratsiya qilingan nom mavjud boʻlmaganda u `null` boʻladi. OmniRoute hech qachon elektron pochta yoki yaratilgan hisob identifikatorini almashtirmaydi. Provayder qiymati sezgir boʻlmagan koʻrsatish yorligʻi boʻlib, hech qachon yaratilgan mos keluvchi provayder identifikatori emas. Hisobga olish maʼlumotlari, tokenlar, cookie-fayllar, xom ulanish yoki API kalit identifikatorlari, egalik xeshlari, himoya sirlari va ichki marshrutlash maʼlumotlari chiqarib tashlanadi.

Notoʻgʻri kalit, notoʻgʻri egalik, eskirgan generation, yoʻqolgan, muddati oʻtgan, chiqarilgan va bekor qilingan qidiruvlarning barchasi ulanish metamaʼlumotlarisiz bir xil `409 LEASE_FENCE_STALE` xatosini qaytaradi. Imkoniyatni kutish javobini olgan mijozda tekshirish uchun faol bogʻlanish mavjud emas. Marshrutlash faol ijarani oʻzgartirganda, bir xil generation haqiqiy boʻlib qoladi va status atomik tarzda yangi bogʻlanishni qaytaradi, hech qachon eskisini emas. Mavjud mijozlar oʻzgarishsiz qoladi, chunki olish, yangilash, chiqarish va kutish javoblari oʻzlarining oldingi shakllarini saqlab qoladi.

Ushbu server shartnomasi standart OpenAI Codex `/status`ni oʻzgartirmaydi. Standart Codex hozirda oʻzining model provayderini va oʻrnatilgan autentifikatsiya/hisob holatini xabar qiladi, ammo ixtiyoriy maxsus provayder hisob metamaʼlumotlarini koʻrsatmaydi; keyingi mijoz integratsiyasi ushbu harakatni chaqirishi va `connection.displayName`ni qanday koʻrsatishni hal qilishi kerak.

Har bir boshqariladigan xulosa soʻrovi keyin ikkala boshqaruv sarlavhasini taqdim etadi:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Aniq egasi, generation, faol ulanish va autentifikatsiya qilingan API kaliti har bir qoʻllab-quvvatlanadigan yuqori oqim urinishidan oldin darhol himoyalanadi. Egasi va generationni boshqa kalit bilan qayta ijro etish, hatto bu kalit bir xil ulanishga ruxsat bersa ham, muvaffaqiyatsiz tugaydi. Xom egalar saqlanmaydi, qayd etilmaydi, soʻrov snapshotida saqlanmaydi yoki yuqori oqimga yuborilmaydi.

Vaqtinchalik tortishuv HTTP `429`ni `Retry-After` bilan va quyidagilarni qaytaradi:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Ushbu javob faqat oddiy mos keluvchi toʻplam boʻsh emasligini va har bir boʻsh nomzod chet el faol ijarasi tomonidan ushlab turilganligini anglatadi. Qoʻllab-quvvatlanmaydigan modellar/provayderlar, siyosat mos kelmasligi, sovutish, kvota, sogʻliq va boshqa oddiy moslik xatolari oʻzlarining mavjud OmniRoute javoblarini saqlab qoladi.

### `x-omniroute-compression`

Siqish rejasini har bir soʻrov boʻyicha bekor qilish. Eng yuqori ustuvorlik — marshrutlash-kombinatsiyasini bekor qilish, faol profil, avtomatik trigger va panelning Standartini bekor qiladi. Qiymatlar:

| Qiymat        | Effekt                                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Ushbu soʻrov uchun siqish yoʻq.                                                                                                      |
| `default`     | Panel tomonidan olingan Standart profil (faol profilni eʼtiborsiz qoldiradi). Yoʻqotishli dvigatellar oʻchirilgan holda qoldiriladi. |
| `safe`        | Faqat takrorlash va boʻsh joyni yigʻish.                                                                                             |
| `allow-lossy` | Ushbu soʻrov uchun operator rejasini saqlab qolish, shu jumladan xulosalar va uslubni qayta yozish.                                  |
| `engine:<id>` | Yoqilganda bitta dvigatel, masalan, `engine:rtk`. Ushbu dvigatel uchun har bir soʻrov boʻyicha ixtiyoriy qoʻshilish.                 |
| `<combo>`     | Nomlangan kombinatsiya, avval nomi boʻyicha (katta-kichik harflarga sezgir emas), keyin identifikatori boʻyicha mos keladi.          |

Eslatmalar:

- Nomaʼlum qiymatlar eʼtiborsiz qoldiriladi (soʻrov hech qachon rad etilmaydi); yechim oddiy operator ustuvorligiga tushadi.
- Agar bir nechta kombinatsiyalar bir xil nomga ega boʻlsa, aniq moslik uchun kombinatsiya **id**sini kiriting.
- Nomi `off` yoki `default` boʻlgan kombinatsiya nomi boʻyicha tanlanishi mumkin emas (bu kalit soʻzlar birinchi navbatda talqin qilinadi); bunday kombinatsiyaga uning identifikatori boʻyicha murojaat qiling.
- Asosiy siqish tugmasi qattiq darvoza: siqish global ravishda oʻchirilgan boʻlsa, bu sarlavha uni yoqa olmaydi.

Qoʻllanilgan reja javob sarlavhasida aks ettiriladi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

bu yerda `<source>` `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` yoki `off` dan biri.

## Embeddinglar

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Mavjud provayderlar: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog identifikatorlari `provider/model` formatida bo‘ladi (masalan: `jina-ai/jina-embeddings-v5-omni-small`). Reestrda mavjud prefikssiz Jina model identifikatorlari (masalan, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ham aniqlanadi. Jina embed/rerank/classify/segment amallari avval boshqaruv panelidagi `jina-ai` hisob ma’lumotlaridan foydalanadi; `JINA_AI_API_KEY` faqat boshqaruv panelida kalit mavjud bo‘lmaganda zaxira sifatida ishlatiladi. `jina-reader` kartasi faqat Reader / `r.jina.ai` uchun (`POST /v1/web/fetch`) mo‘ljallangan va hech qachon embedding yoki rerank xizmatini ko‘rsatmaydi.

Multimodal qo‘llab-quvvatlashni e’lon qiladigan reestr modellari provayderga bog‘liq bo‘lmagan 32 tagacha tuzilmali elementni ham qabul qiladi. Media elementlarining turlari: `text`, `image`, `audio`, `video` va `document`. Ularning media `source` qiymati `{"type":"url","url":"https://..."}` yoki `{"type":"base64","data":"...","media_type":"..."}` ko‘rinishida bo‘ladi.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` va `jina-ai/jina-embeddings-v5-omni` → omni-small oilaviy taxallusi) Jina’ning mahalliy EmbeddingsV5Request hujjatlarini ham qabul qiladi va ularni `https://api.jina.ai/v1/embeddings` manziliga **o‘zgartirmasdan uzatadi**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

Mahalliy `{ image | audio | video | pdf }` qiymatlari ommaviy HTTPS URL, `data:` URI yoki xom base64 bo‘lishi mumkin. OmniRoute ushbu obyektlarni satrga aylantirmaydi yoki mahalliy tasvir URL manzillarini yuklab olmaydi — ommaviy mediani Jina o‘zi oladi. Qo‘shimcha Jina maydonlari (`task`, `normalized`, `truncate`, `embedding_type`) uzatiladi. Faqat matnli Jina SKU’lari matn bo‘lmagan hujjatlarni rad etishda davom etadi.

Xavfsizlik va uzatish cheklovlari:

- Masofaviy media URL manzillari ommaviy HTTPS bo‘lishi kerak. Kanonik `{type,source:url}` elementlari server tomonida yuklab olinadi (qayta yo‘naltirishni takroran tekshirish, vaqt chegarasi, hajm cheklovlari, ommaviy DNS, ulanishni mahkamlash) va provayder chaqiruvidan oldin ichki ko‘rinishda joylashtiriladi. Jina’ga xos `{image:"https://..."}` elementlari ayni ommaviy HTTPS tekshiruvidan so‘ng o‘z holicha uzatiladi; URL manzilini Jina yuklab oladi.
- Ichki base64 media har bir element uchun dekodlangan holda 8 MiB, butun so‘rov bo‘yicha esa dekodlangan holda 16 MiB bilan cheklangan.

Provayderga moslashtirish (kanonik elementlar hech qachon o‘zgartirilmagan holda uzatilmaydi):

- Jina multimodal modellari: har bir yuqori darajadagi element ichki media uchun data URI’lardan foydalangan holda modal kalitli bitta obyektga (`text` / `image` / `audio` / `video` / `pdf`) aylanadi; har bir yuqori darajadagi element uchun bitta vektor.
- Gemini Embedding 2 oilasi: bitta yuqori darajadagi massiv `content.parts` (`text` yoki `inline_data`) bilan yagona mahalliy `models/{model}:embedContent` so‘roviga aylanadi.
- llama.cpp (`llama-cpp/<model>`, mahalliy server yuklagan istalgan model): kanonik `text` elementlari oddiy satrlarga, `image` / `audio` / `video` elementlari esa har biri bitta `{"content": [part]}` obyektiga aylanadi. Bunda llama-server’ning ichki ma’lumotli chat kontent qismlaridan (`image_url`, `wav` / `mp3` / `flac` formatidagi `input_audio`, `input_video`) foydalaniladi; har bir yuqori darajadagi element uchun bitta vektor. Server `--embedding --mmproj …` parametrlari bilan ishga tushirilishi kerak; projektor bo‘lmasa, server mediani o‘zi rad etadi. `document` qo‘llab-quvvatlanmaydi.
- Aniq modal metama’lumotlari bo‘lmagan noma’lum/dinamik modellar tuzilmali kirishni HTTP 400 bilan rad etadi.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Qo‘llab-quvvatlanmaydigan model/modallik kombinatsiyalari elementni majburan moslashtirish o‘rniga HTTP 400 qaytaradi. Eski satr/token so‘rovlaridagi kirishga aloqador bo‘lmagan kengaytma maydonlari o‘zgartirilmasdan uzatilishda davom etadi.

```bash
# Barcha embedding modellarini ro‘yxatlash
GET /v1/embeddings
```

## Tasvir yaratish

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "Togʻlar uzra goʻzal quyosh botishi",
  "size": "1024x1024"
}
```

Mavjud provayderlar qatoriga OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (mahalliy), ComfyUI (mahalliy) kiradi.

`n` parametrida `data[]` ichida `n` ta tasvir qaytariladi. Yuqori darajadagi API har bir chaqiruvda bittadan tasvir qaytaradigan provayderlar
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) uchun yuqori darajadagi API ga `n` ta alohida chaqiruv yuboriladi, bir vaqtning oʻzida koʻpi bilan 4 tasi bajariladi. Qatʼiy
`seed` qiymati chaqiruv indeksi boʻyicha siljitiladi (`seed`, `seed + 1`, …), shu sababli tasvirlar bir-biridan farq qiladi, ammo
qayta yaratilishi mumkin boʻlib qoladi. `n` qiymati koʻpi bilan 10 boʻlishi mumkin. Agar chaqiruvlardan biri muvaffaqiyatsiz tugasa, butun soʻrov
muvaffaqiyatsiz hisoblanadi. Tarqatib chaqirish formatlari roʻyxati
`open-sse/handlers/imageGeneration/fanOut.ts` faylidagi `SINGLE_IMAGE_FANOUT_FORMATS` ichida joylashgan.

ZenMux mavjud API kaliti ulanishidan qayta foydalanadi va `zenmux/` yoki `zm/` prefikslarini qabul qiladi:

- `zenmux/openai/gpt-image-2` ZenMux’ning OpenAI Images API xizmatidan foydalanadi. Parametrlar qatoriga `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` va `response_format` kiradi.
- `zm/meta/muse-image-1.0` kabi boshqa nashriyotchilar ZenMux’ning Vertex AI `:predict`
  yakuniy nuqtasidan foydalanadi. `n` — `sampleCount` ga, `aspect_ratio` — `aspectRatio` ga va `image_size`
  (`1K`, `2K`, `4K`) — `sampleImageSize` ga moslanadi. Piksellarda koʻrsatilgan `size` faqat tomonlar nisbatini belgilaydi,
  piksel oʻlchamlari esa kafolatlanmaydi. Qoʻllab-quvvatlanadigan nisbatlar, aniqliklar va miqdorlar modelga qarab farq qiladi.
- `zm/inclusionai/ming-image-0.1-design` oʻz oʻlchamlarini mustaqil tanlaydi. `size`,
  `aspect_ratio` va `image_size` parametrlarini koʻrsatmang; aniq qiymatlar HTTP 400 javobini qaytaradi. PNG, JPEG va WebP
  formatlarini `output_format` orqali soʻrash mumkin.

Bu integratsiya tayanch tasvirni tahrirlashni emas, matndan tasvir yaratishni qoʻllab-quvvatlaydi. Vertex
chiqishi `data[].b64_json` formatiga normallashtiriladi; `response_format: "url"` yuqori darajadagi
HTTPS URL manzilini yoki faqat tasvir baytlari mavjud boʻlsa, base64 maʼlumotlar URL manzilini qaytaradi. Boʻsh yoki filtrlangan natijalar
boʻsh muvaffaqiyatli javob oʻrniga xatolik qaytaradi. Modellardan foydalanish imkoniyati ZenMux hisobiga bogʻliq.
[ZenMux’ning Vertex API hujjatlari](https://docs.zenmux.ai/api/vertexai/generate-images) va
[OpenAI Images API hujjatlari](https://docs.zenmux.ai/api/openai/generate-an-image) bilan tanishing.

```bash
# Barcha tasvir modellarini roʻyxatlash
GET /v1/images/generations
```

## Hujjat OCR'i

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` OCR provayderini `provider/model` prefiksi orqali tanlaydi; faqat model identifikatori (masalan,
`mistral-ocr-latest`) uning roʻyxatdan oʻtgan provayderiga moslashtiriladi, `model` koʻrsatilmasa esa sukut boʻyicha
Mistral (`mistral-ocr-latest`) ishlatiladi. Roʻyxatdan oʻtgan provayderlar (`open-sse/config/ocrRegistry.ts`):

| Provayder identifikatori      | Model identifikatori | `model` qiymati                                                | Izohlar                                                                                                                      |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (yoki faqat `mistral-ocr-latest`) | Sinxron — javob yagona yuqori oqim chaqiruvidan bevosita qaytariladi.                                                        |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | Asinxron yuqori oqim (`analyze` + soʻrovnoma) — quyiga qarang.                                                               |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Sinxron, Vertex AI'ning `openapi/chat/completions` hamkor soʻnggi nuqtasi orqali — autentifikatsiya/URL uchun quyiga qarang. |

Har uchala provayder ham bir xil Mistral shaklidagi tanada javob beradi:

```json
{
  "pages": [{ "index": 0, "markdown": "# Ajratib olingan matn..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence soʻrovnoma oqimi

Azure Document Intelligence'ning `analyze` API'si asinxron: dastlabki soʻrov tana oʻrniga
`Operation-Location` sarlavhasini qaytaradi va natijani soʻrovnoma orqali tekshirish kerak. Ishlov beruvchi
(`open-sse/handlers/ocr.ts`) ushbu URL'ni har soniyada, koʻpi bilan 30 marta tekshiradi, `ok` boʻlmagan
soʻrovnoma javobi yoki `"failed"` holatida darhol xatolik bilan yakunlanadi (tekshirishda davom etmaydi) va
urinishlar limiti tugagach, operatsiya hali ham bajarilayotgan boʻlsa, `504` qaytaradi. Yakuniy Azure javobi
chaqiruvchiga qaytarilishidan oldin Mistral ishlatadigan xuddi shu `pages`/`markdown` shakliga
normallashtiriladi, shu sababli mijoz kodi provayder uchun alohida holatni koʻrib chiqishi shart emas.

### Vertex AI DeepSeek OCR autentifikatsiyasi va soʻnggi nuqtani aniqlash

`vertex-deepseek-ocr` OmniRoute chat/tasvir trafigi uchun allaqachon qoʻllab-quvvatlaydigan ayni Vertex AI
autentifikatsiyasidan qayta foydalanadi (`open-sse/executors/vertex.ts`): ulanishning API kaliti Service
Account JSON hisob maʼlumotlari (JWT-bearer oqimi orqali qisqa muddatli OAuth kirish tokeniga almashtiriladi)
yoki oʻz holicha ishlatiladigan, avvaldan yaratilgan OAuth kirish tokeni boʻlishi mumkin. Yuqori oqimdagi
soʻnggi nuqta URL'i ulanish loyihasi va hududi asosida yaratiladigan Vertex'ning umumiy
`openapi/chat/completions` hamkor soʻnggi nuqtasidir — aniq koʻrsatilgan `providerSpecificData.project`/`providerSpecificData.region`
har doim ustunlikka ega; aks holda loyiha Service Account JSON'ining `project_id` qiymatidan olinadi va hudud
sukut boʻyicha `us-central1` boʻladi. Har ikkala aniqlash jarayoni ham `open-sse/handlers/ocr.ts` ichida
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) bajariladi va `handleOcr`'ga yuborilishidan oldin
`src/app/api/v1/ocr/route.ts` tomonidan ishlatiladi.

## Modellarning roʻyxatini olish

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Barcha chat, embedding va tasvir modellari hamda kombinatsiyalarni OpenAI formatida qaytaradi
```

### Model id prefikslari (`?prefix=`)

Aksariyat modellar **provayder prefiksi** ostida taqdim etiladi. Qaysi prefiks olinishini
`MODELS_CATALOG_PREFIX_MODE` funksiya bayrogʻi boshqaradi va uni soʻrov parametri orqali **har bir soʻrov uchun**
alohida bekor qilish mumkin — bu server miqyosidagi sozlamani boshqalar uchun oʻzgartirmasdan, toza roʻyxat olishni
xohlaydigan mijoz uchun foydalidir:

```bash
GET /v1/models?prefix=alias        # har bir model uchun bitta id — qisqa taxallus prefiksi
GET /v1/models?prefix=dual         # ikkala shakl (server standarti)
GET /v1/models?prefix=canonical    # faqat toʻliq provayder-id prefiksi
```

| Rejim       | Chiqaradi                                                | Izohlar                                                                                                                                                                                                                             |
| ----------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **va** `claude/claude-sonnet-4-6` | **Standart.** Har ikkala id bir xil modelga yoʻnaltiriladi; ikkala shakldan birini qatʼiy belgilagan mijoz konfiguratsiyalari ishlashda davom etishi uchun saqlangan. Katalog hajmini taxminan ikki baravar oshiradi.               |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Har bir model uchun bitta yozuv. Alohida taxallusi boʻlmagan provayderlar ham oʻz yozuvini chiqaradi, shuning uchun hech narsa yoʻqolmaydi.                                                                                         |
| `canonical` | `claude/claude-sonnet-4-6`                               | Toʻliq provayder-id prefiksi ostida har bir model uchun bitta yozuv. Alohida taxallusi boʻlmagan provayderlar (masalan, `antigravity/…`, `agy/…`) ham bu yerda yagona id qiymatini chiqaradi, shuning uchun hech narsa yoʻqolmaydi. |

`dual` rejimidagi nusxani soʻrov parametrisiz ham aniqlash mumkin: unda asosiy id qiymatiga
ishora qiluvchi `parent` maydoni mavjud.

Model tanlash interfeysini koʻrsatadigan mijozlar `?prefix=alias` parametrini soʻrashi kerak —
[OmniCopilot VS Code kengaytmasi](../guides/VSCODE-COPILOT.md) aynan shunday qiladi.

### Qidirish filtrlari (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ixtiyoriy qidirish filtrlarini qabul qiladi. Ularning hech biri berilmasa,
javob oʻzgarmaydi. Ular chaqiruvchi allaqachon koʻra oladigan katalogni toraytiradi (avval API kaliti
ruxsatlari qoʻllanadi) va OpenAI uslubidagi `limit` / `after` sahifalashidan oldin ishlaydi:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # roʻyxatdagi har bir imkoniyat true boʻlishi kerak
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogdagi `type`; u mavjud boʻlmagan qatorlar `chat` hisoblanadi
GET /v1/models?q=sonnet&limit=10                           # id yoki nom boʻyicha registrga bogʻliq boʻlmagan moslik
```

| Parametr      | Qiymatlar                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | manfiy boʻlmagan butun son, `context_length` bilan taqqoslanadi                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 ta belgi                                                                                      |

Nomaʼlum qiymat yoki manfiy boʻlmagan butun son boʻlmagan `min_context` (masalan, `1.5`)
HTTP `400` javobini qaytaradi va xabarda yaroqli qiymatlar koʻrsatiladi. Amalga oshirish:
`src/app/api/v1/models/catalogFilters.ts`.

### Modellarning qisqa roʻyxati (`POST /v1/models/query`)

`POST /v1/models/query` xuddi shu katalogdan qisqa, deterministik roʻyxatni, `GET /v1/models`
bilan bir xil autentifikatsiya va har bir kalitga tegishli koʻrinish qoidalari asosida qaytaradi:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Har bir maydon ixtiyoriy. `capabilities` va `exclude` massiv yoki vergul bilan ajratilgan satrni
qabul qiladi; `max_output` qiymati `max_output_tokens` bilan taqqoslanadi. Natijalar avval
`owned_by`, keyin `id` boʻyicha saralanadi. `limit` uchun standart qiymat `20`, `100` dan yuqori
qiymatlar esa `100` bilan cheklanadi. Notoʻgʻri JSON, nomaʼlum maydon yoki yaroqsiz qiymat HTTP `400`
javobini qaytaradi.

### Alohida yashirilgan chat modellari

Provayder sahifasida **Yashirin** deb belgilangan model katalogdan chiqarib tashlanadi va bevosita
soʻralganda HTTP `404` / `model_not_found` bilan rad etiladi. Tekshiruv aniqlangan provayder va
modeldan, jumladan provayder taxalluslari, mos provayder tuguni prefikslari va ulanishning standart
qiymatlaridan foydalanadi. Kombinatsiya yashirin nishonlarni oʻtkazib yuboradi va koʻrinadigan muqobil
modeldan foydalanishi mumkin; bajariladigan nishon qolmasa, u xuddi shu xato kodini qaytaradi.
Yashirishni bekor qilish keyingi soʻrovda kuchga kiradi. Faqat tasvirlarga tegishli koʻrinish
istisnolari ayni ID qiymatiga ega chat modelini yashirmaydi.

Bu alohida model sozlamasi katalogda koʻrsatiladigan modellar va avtomatik yoʻnaltirish
nomzodlarini filtrlab, bevosita yuborishni saqlab qoladigan
[modellarni taqdim etish uchun ruxsat berish/rad etish roʻyxatlaridan](../routing/MODEL_EXPOSURE_LIST.md)
alohida hisoblanadi. API kalitining model ruxsatlari mustaqil ravishda qoʻllanishda davom etadi.
Standart katalog prefiksi rejimi `dual` boʻlib qoladi.

### Fikrlashsiz model variantlari

Fikrlash imkoniyatiga ega Claude modellari uchun `/v1/models` id qiymati `claude-3-omniroute-no-thinking/`
prefiksi bilan boshlanadigan **fikrlashsiz** variantni ham taqdim etadi:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Ushbu id'ni tanlash (masalan, har doim `thinking` blokini biriktiradigan Claude Code konfiguratsiyasida) mulohaza yuritish o‘chirilgan holda haqiqiy `<provider>/<model>` modeliga qayta yo‘naltiradi — `/v1/messages` yo‘lida `thinking:{type:"disabled"}` qo‘llanadi yoki `/v1/chat/completions` yo‘lida `reasoning`/`reasoning_effort` maydonlari olib tashlanadi. Variant faqat fikrlashni qo‘llab-quvvatlaydigan **va** `disabled` qiymatiga amal qiladigan Claude oilasidagi modellar uchun ko‘rsatiladi (shu sababli, masalan, `disabled` qiymatini rad etadigan faqat adaptiv rejimdagi modellar chiqarib tashlanadi). Operatorlar har bir model uchun `ModelSpec.noThinkingAlias` orqali variantni majburan yoqishi yoki o‘chirishi mumkin.

> **Qayta saralash provayder tugunlari:** `POST /v1/rerank` soʻrovi `<node-prefix>/<model>` shaklida manzillanadigan OpenAI bilan mos provayder tugunlariga
> (oMLX, vLLM, Infinity, shlyuz ortidagi TEI, …) ham yoʻnaltiriladi. Loopback
> tugunlari (`localhost`, `127.0.0.1`, `172.16.0.0/12`) har doim ruxsat etiladi; operator
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` roʻyxatiga kiritgan host nomlariga ham ruxsat beriladi (masalan,
> `http://reranker:8080/v1` kabi Docker/Compose xizmat nomi; ularga har doim toʻgʻridan-toʻgʻri murojaat
> qilinadi, hech qachon `HTTP(S)_PROXY` yoki ulanishga biriktirilgan proksi orqali emas). Boshqa istalgan
> hostdagi tugunlarga — LAN qurilmasi yoki Tailscale tuguniga — faqat operator
> `RERANK_REMOTE_PROVIDER_NODES` funksiya bayrogʻini yoqsa **va** tugunning asosiy URL manzili provayderning
> chiquvchi URL siyosatidan (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)
> oʻtsa, ruxsat beriladi. Xotira mexanizmining qayta saralash bosqichi ushbu marshrutga
> loopback orqali murojaat qiladi, shuning uchun Xotira sozlamalaridagi `rerankProviderModel` uchun ham
> ayni qoida amal qiladi.
>
> **Mahalliy server formatlari:** tugunga `<base>/v1/rerank` manzili orqali, 404 holatida esa
> `<base>/rerank` (Infinity, TEI) orqali murojaat qilinadi. Yuqori oqim tanasi Cohere/OpenAI yozilishini
> (`documents`, `return_documents`) hamda TEI yozilishini (`texts`, `return_text`) oʻz ichiga oladi va
> yuqori oqim javobi Cohere konvertiga normallashtiriladi: TEI’ning oddiy `[{index, score, text}]`,
> sodda shlyuzlardan keladigan `{results: [{index, score}]}` va Voyage uslubidagi `{data: [...]}` javoblarining
> barchasi mijozga `{results: [{index, relevance_score, document?}]}` shaklida, ball boʻyicha saralangan
> va `top_n` bilan cheklangan holda qaytariladi.

> **Provayder tugunlarini aniqlash:** OpenAI bilan mos provayder tugunidagi modellar `GET /v1/models`
> ichida tugun prefiksi ostida koʻrinadi. Endpoint metamaʼlumotlari boʻlmagan qatorlar (mahalliy
> `/v1/models` roʻyxatlari uchun odatiy holat) tugunning `apiType` qiymatini meros qilib oladi, shuning
> uchun `embeddings` tugunining modellari sukut boʻyicha chat turiga oʻtish oʻrniga `type: "embedding"`,
> `rerank` tugunining modellari esa `type: "rerank"` boʻladi; sinxronlangan yoki qoʻlda qoʻshilgan
> qatordagi aniq `supportedEndpoints` hali ham ustunlikka ega.

## Web Fetch API

Sozlangan web-fetch provayderi (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) orqali URL manzilidan kontentni ajratib oling.

Parallel Extract (`parallel-search`, Parallel Search bilan bir xil API kaliti) faqat Markdown qaytaradi — boshqa har qanday `format` `400` xatosiga olib keladi — va kontent hajmini 100 000 ta belgi bilan cheklaydi. Maqsadli sahifaning o‘zini ajratib bo‘lmaganda, yuqori oqim xizmati bu haqda HTTP 200 javobi ichida xabar beradi; OmniRoute esa buni belgilangan xabar bilan `422` sifatida taqdim etadi.

| Metod | Yo‘l            | Tavsif                                                                                    |
| ----- | --------------- | ----------------------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL manzilini olish/qirib ajratish — so‘rov tanasi `v1WebFetchSchema` orqali tekshiriladi |

**Autentifikatsiya:** Bearer API kaliti (`extractApiKey` + `isValidApiKey`). Siyosat `enforceApiKeyPolicy` orqali qo‘llanadi.

**Kvotani hisobga oluvchi zaxira mexanizmi (#8297):** aniq `provider` berilmaganda, pull
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)
belgilangan ustuvorlik tartibida (birinchisini to‘ldirish tamoyili asosida) ko‘rib chiqiladi — tezlik chekloviga uchragan, ammo sozlangan provayder so‘rovni darhol to‘xtatish o‘rniga o‘tkazib yuboriladi va qayta urinish mumkin bo‘lgan/kvota bilan bog‘liq yuqori oqim xatosi
(HTTP 429 har doim; Firecrawl/Tavily/TinyFish’ning kvota uslubidagi bepul tariflari uchun 402/403 —
Jina Reader uchun emas va oddiy 400 noto‘g‘ri so‘rov uchun hech qachon emas) so‘rov vaqtida hali sinab ko‘rilmagan, hisob ma’lumotlari mavjud keyingi provayderga o‘tadi. Puldagi barcha provayderlar imkoniyati tugaganda, endpoint avvalgi umumiy `400` o‘rniga yagona `429` javobini (`Retry-After` sarlavhasi bilan) qaytaradi. Aniq `provider` so‘ralganda, **hech qanday** yashirin zaxira mexanizmi qo‘llanmaydi — tezlik chekloviga uchragan yoki ishlamay qolgan aniq provayder o‘z xatosini ko‘rsatadi (tezlik cheklangan bo‘lsa `429`, aks holda yuqori oqim statusi).

## Mustaqil foydalanish (`/api/usage/om-usage`)

Har qanday API kaliti **oʻzining** foydalanish maʼlumotlari va kvotalarini boshqaruv autentifikatsiyasisiz oʻqiy oladi. Bu mijoz (CLI, OmniCopilot paneli) kalit egasiga uning xarajatlarini koʻrsatish uchun foydalanadigan endpointdir.

```bash
# Matnli shakl (tarixiy shartnoma — terminal uchun oddiy matn)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Tuzilmali shakl — UI foydalanadigan shakl
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Kalitda **`allowUsageCommand`** yoqilgan boʻlishi kerak (standart holatda oʻchiq — boshqaruv panelidagi API kalitlari menejeri uni har bir kalit uchun alohida yoqadi). U yoqilmagan boʻlsa, endpoint `403` javobini qaytaradi.

`?format=json` diskriminatsiyalangan tuzilmani qaytaradi, shu sababli chaqiruvchi rad etish javobidan hech qachon maʼlumot maydonini oʻqimaydi. Muvaffaqiyatli javob:

```jsonc
{
  "allowed": true,
  // faqat kalit har bir kalit uchun foydalanish limitlarini (kunlik/haftalik USD) tanlaganida mavjud:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // tanlangan provayder kvotasining oniy nusxasi yoki hali hech narsa keshlanmagan boʻlsa null:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // UI bir nechta provayderni yonma-yon koʻrsatishi uchun har bir ulanishning oniy nusxasi:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Rad etilganda (`401` notoʻgʻri kalit / `403` ruxsat berilmagan) xuddi shu marshrut
`{ "allowed": false, "error": { "message": "…" } }` javobini qaytaradi — mavjud, ammo boʻsh `personal`/`provider`
(kalitga ruxsat berilgan, lekin hali hech qanday maʼlumot olinmagan) rad etishdan farqli holat boʻlib, ularni faqat JSON shakli ajratib koʻrsatadi.

**Autentifikatsiya:** chaqiruvchining `isValidApiKey` orqali tekshiriladigan oʻz Bearer API kaliti — bu `requireManagementAuth` ortida qoladigan boshqaruv interfeysi (`/api/keys/…`) _emas_.

### Xom va chegara boʻyicha tuzatilgan kvota foizlari

`/api/usage/om-usage` dan foydalanishda chaqiruvchilar **oddiy matnli chiqish** va tuzilmali **JSON chiqishi** taqdim etadigan foizlar oʻrtasidagi farqni hisobga olishlari kerak:

| Jihat                    | Oddiy matn formati (`/api/usage/om-usage` / `@@om-usage`)                                                     | JSON formati (`?format=json`)                                                             |
| :----------------------- | :------------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------------------------- |
| **Chiqish maydoni**      | `NN% left` (masalan, `20% left`)                                                                              | `provider.quotas` / `providers[].quotas`                                                  |
| **Oʻlchov**              | **Chegara boʻyicha tuzatilgan foydalanish mumkin boʻlgan limit**: chegara qiymatidan yuqoridagi qolgan sigʻim | **Xom yuqori oqim kvotasi**: provayderning tuzatilmagan oʻlchovi                          |
| **Chegara masshtabi**    | Himoyalangan zaxira `0% left` sifatida koʻrinishi uchun `effectiveRemainingPercent()` orqali masshtablanadi   | Yoʻq (provayder xabar qilgan xom oniy nusxa qiymatlari)                                   |
| **Chegara maʼlumotlari** | Koʻrsatiladigan foiz tarkibiga kiritiladi                                                                     | Har bir ulanish uchun `quotaWindowThresholds` ichida saqlanadi (yoki server standartlari) |
| **Asosiy isteʼmolchi**   | Interaktiv CLIlar, terminal soʻrovlari, inson operatorlari                                                    | Dasturiy integratsiyalar, boshqaruv panellari, tahlil va hisob-kitob kuzatuvchilari       |

#### Chegara boʻyicha tuzatish formulasi

OmniRoute yuqori oqim resurslarining tugab qolishiga yoʻl qoʻymaslik uchun proaktiv kvota chegaralarini qoʻllab-quvvatlaydi (ulanishning `quotaWindowThresholds`, provayder standartlari yoki global barqarorlik sozlamalari orqali sozlanadi). Kvota oynasida chegara qiymati (masalan, `cutoff = 25%`) faol boʻlsa, matn renderer qolgan limitni quyidagicha hisoblaydi:

- Agar `remaining <= cutoff` boʻlsa: `0%` qaytaradi.
- Agar `remaining > cutoff` boʻlsa: `((remaining - cutoff) / (100 - cutoff)) * 100` qaytaradi.

Formatlangan matnli chiqish bu qiymatni eng yaqin butun songa yaxlitlaydi (`Math.round(...)`).

#### Koʻrgazmali misol

**60% xom foydalanish** (demak, **40% xom qolgan kvota**) va sozlangan **25% qolgan kvota chegarasi** mavjud provayder oynasini koʻrib chiqamiz:

| Koʻrinish                     | Hisoblash                                          | Qolgan  |         Nazarda tutilgan sarf          |
| :---------------------------- | :------------------------------------------------- | :-----: | :------------------------------------: |
| **Xom JSON (`?format=json`)** | Yuqori oqim oniy nusxasi (`quotas[window]`)        | **40%** |                **60%**                 |
| **Matn formati (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` hisoblansa) |

- **Nima uchun matn 20% qolganini koʻrsatadi:** Hisobda jismonan qolgan 40% kvotaning 25%i chegara siyosati tomonidan zaxiralangan. Router ushbu ulanishga yoʻnaltirishni toʻxtatishidan oldin chaqiruvchida foydalanish mumkin boʻlgan 75% oraliqning faqat 15%i qolgan. Masshtablash ulanish aynan yoʻnaltirish toʻxtatilgan paytda tugaganlik holatini (`0% left`) koʻrsatishini taʼminlaydi.
- **Nima uchun JSON xom qiymatlarni saqlaydi:** JSON foydali yuklamasi provayderning aniq oniy nusxasini (`UsageSnapshot`) qaytaradi, natijada tashqi vositalar server tomonida yoʻqotishli masshtablashsiz yuqori oqimdagi haqiqiy foydalanish va ulanish darajasidagi `quotaWindowThresholds` maʼlumotlariga kira oladi.

#### Isteʼmolchilarni migratsiya qilish boʻyicha koʻrsatma

Agar tashqi integratsiya (masalan, muharrir plagini yoki agent kengaytmasi) avval matnli endpointdan (`NN% left`) maʼlumotni ajratib olib, foydalanilgan foizni `100 - NN` sifatida hisoblagan boʻlsa, `?format=json` ga migratsiya qilish quyidagilarni anglatadi:

- Xom JSON qiymatlarini oʻqish **yuqori oqimdagi haqiqiy sarfni** aks ettiradi (yuqoridagi misolda 60% ishlatilgan).
- Agar integratsiya matnli endpointning foydalanish mumkin boʻlgan limit semantikasini saqlamoqchi boʻlsa, ulanish darajasidagi qayta belgilashlar uchun `quotaWindowThresholds` dan foydalanib, samarali qolgan limit formulasini mijoz tomonida hisoblashi mumkin.

OpenAI-mos provayder sahifasi xuddi shu tahrirlash/tozalash boshqaruv elementlarini taklif qiladi va aniq vision qoʻllab-quvvatlashiga ega modellarni belgilaydi.

Maxsus Chat Completions tugunlari aniq reasoning opt-out sozlamalarini upstream backendga moslashtiradi. Muvaffaqiyatli ulanish sinovi `/models` yozuvi tan olingan `owned_by` qiymatini isbotlovchi har bir aniq model IDsi uchun chat-shablon boshqaruv elementlarini avtomatik tanlaydi: `vllm`, `sglang` yoki `llamacpp`. Shaffof OpenAI-mos oʻramlar asl model yozuvini ichki `openai` obyekti ichida saqlashi mumkin; aniqlash bunday uchtagacha qobiqni kuzatadi. Egalik maʼlumoti yoʻq, nomaʼlum yoki ziddiyatli boʻlgan modellar oddiy OpenAI xatti-harakatini saqlaydi. Aniqlash mavjud katalog soʻrovini qayta ishlatadi, hech qanday completion tokeni yaratmaydi va ulanish manzili oʻzgarganda bekor qilinadi.

Bu metamaʼlumotlarni taqdim etmaydigan backend uchun xatti-harakatni qayd qilish maqsadida mavjud qisman provayder yangilash APIʼsidan foydalaning:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Ushbu tanani `PUT /api/providers/<connection-id>` bilan yuboring. Bu ulanishda `none` qiymatidagi aniq fikrlash darajasi `chat_template_kwargs.thinking=false` va `chat_template_kwargs.enable_thinking=false` sifatida yuboriladi. Server tomonidagi fikrlash qoidasi darajani majburlamaguncha, aniq native shablon qiymatlari hal qiluvchi bo'lib qoladi. Bu sozlama faqat maxsus OpenAI-mos ulanish Chat Completions tanasini jo'natganda qo'llaniladi; Responses so'rovlari va oddiy provayderlar o'zlarining native so'rov shaklini saqlaydi. Oddiy OpenAI `reasoning_effort` uzatishini majburlash uchun `reasoningControl`ni `openai`ga o'rnating, yoki avtomatik aniqlashdan foydalanish uchun uni o'tkazib yuboring/`null`ga tenglashtiring.

Claude Code avto-rejim klassifikator so'rovlarida aniq fikrlash boshqaruvlari bo'lmasa, native fikrlash sukut bo'yicha o'chirilgan holatga o'rnatiladi. Aniqlash model nomlari yoki completion limitlaridan emas, balki Claude-format so'rovlaridagi klassifikatorning tizim markeridan foydalanadi. Aniq tana boshqaruvlari, qo'llab-quvvatlanadigan effort/thinking sarlavhalari, marshrutlash qoidalari va aniqlangan model darajasi mavjud ustuvorligini saqlaydi. Klassifikatorning ikkala bosqichi ham o'z promptlari, completion limitlari, to'xtatish ketma-ketliklari va haqiqiy upstream ruxsat qarorlarini saqlaydi; ikkinchi bosqich so'ralgan ko'rinadigan fikrlashni hali ham oddiy matn sifatida ishlab chiqarishi mumkin.

### Versiya va reliz kanali

```bash
GET /api/system/version
```

Faqat loopback orqali ishlaydigan boshqaruv marshruti (admin autentifikatsiyasi). Ishlayotgan versiyani, eʼlon qilingan eng soʻnggi versiyani va avtomatik yangilanish holatini qaytaradi. `releaseChannel` va `channels` — qoʻshimcha maydonlar (rail 3.8.54); `channel` esa oʻz maʼnosini saqlaydi — boshqaruv paneli yangilagichi foydalanadigan joylashtirish rejimi (`npm`, `source` yoki `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ishlayotgan buildning npm kanali: `-nightly.*` versiyalari uchun `nightly`, boshqa pre-relizlar (`-rc.*`, `-beta.*`, `-alpha.*`) uchun `next`, `channels.latest`dan eskiroq major versiyaning barqaror versiyasi uchun `lts`, aks holda `latest`. Qoidalar nashr paytida npm dist-tag'ni tanlaydigan `scripts/release/dist-tag.mjs` bilan bir xil.
- `channels` — har bir dist-tag'ning eʼlon qilingan eng soʻnggi versiyasi; `npm view omniroute dist-tags`dan (zaxira variant sifatida registry HTTP orqali) olinadi va `latest` kabi 10 daqiqalik TTL bilan keshlanadi. `latest` har doim mavjud (topilmasa, avval `latest` maydoniga, soʻng `"unavailable"`ga qaytadi); `next`, `nightly` va `lts` esa faqat shu dist-tag mavjud boʻlgandagina paydo boʻladi. `Cache-Control: no-cache` soʻrovi ikkala qidiruvni ham yangilaydi.

Kanal modeli (`latest` = 4.0 GA'gacha v3, `next` = rc, `nightly` = `develop` buildlari, `lts` = 4.0 GA'dan keyingi v3 patchlari) `docs/ops/RELEASE_STRATEGY.md` faylida tasvirlangan.

## Audio transkripsiyasi

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Sozlangan istalgan STT provayderi yordamida audio fayllarni transkripsiya qiling. Yoʻlning birinchi
segmenti bevosita provayderni tanlaydi (`openai/…`, `deepgram/…`). Boshqa yetkazib
beruvchining modelini qayta eksport qiluvchi shlyuzlar toʻliq identifikatordan foydalanadi
(`openrouter/deepgram/nova-3`).

**Soʻrov:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Javob:**

```json
{
  "text": "Salom, bu transkripsiya qilingan audio kontent.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
```

## Token limitlari

Har bir API kaliti uchun **token** budjetlari (yuqoridagi USD asosidagi budjetdan farqli). Soʻrov yoʻlida bevosita nazorat qilinadi: kalitning joriy davrdagi sarfi limitga yetganda, soʻrovlar `429 Too Many Requests` bilan rad etiladi. Limitlar muayyan `model`, `provider` doirasida yoki kalit boʻylab `global` tarzda qoʻllanishi mumkin; agar soʻrovga bir nechta limit mos kelsa, eng qatʼiy limit ustun keladi.

```bash
# Kalitning token limitlarini roʻyxatlash (joriy davrdagi sarfni ham oʻz ichiga oladi)
GET /api/usage/token-limits?apiKeyId=key-123

# Token limitini yaratish yoki yangilash
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Token limitini id boʻyicha oʻchirish
DELETE /api/usage/token-limits?id=tl-abc
```

> **Sxema izohlari** (`setTokenLimitSchema`): `apiKeyId` va `scopeType` (`model` | `provider` | `global`) majburiy. `scopeType` qiymati `global` boʻlmasa, `scopeValue` majburiy (masalan, `model` doirasi uchun model identifikatori, `provider` doirasi uchun provayder identifikatori). `tokenLimit` musbat butun son boʻlishi kerak (satrdan o‘giriladi). Ixtiyoriy: `id` (yaratish uchun koʻrsatmang, yangilash uchun kiriting), `resetInterval` (`daily` | `weekly` | `monthly`, standart qiymati `monthly`), `resetTime` (`HH:MM`), `enabled` (standart qiymati `true`). `GET` javoblari har bir limitni `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` va `nextResetAt` bilan boyitadi. Bu boshqaruv toifasidagi endpoint hisoblanadi (autentifikatsiya `authz` konveyeri tomonidan markazlashgan holda taʼminlanadi).

## Chidamlilik (kengaytirilgan)

OmniRoute uchta mustaqil vaqtinchalik xatolik mexanizmini taqdim etadi; quyidagi boshqaruv endpointlari operatorlarga ularni oʻqish va bekor qilish imkonini beradi:

| Qamrov                 | Holatni saqlash                              | Oʻqish                                    | Tiklash / tozalash                                                  |
| ---------------------- | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| Provayder uzgichi      | `domain_circuit_breakers` + xotirada         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                        |
| Ulanish sovutish davri | Provayder ulanishlaridagi `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (dangasa tarzda qayta faollashadi; provayder PUT orqali tozalanadi) |
| Model blokirovkasi     | Xotiradagi model-mavjudligi reestri          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                            |

`PATCH /api/resilience` provayder uzgichini bekor qilish qiymatlarini `providerBreaker.oauth` va `providerBreaker.apikey` ostida qabul qiladi. Har bir profil `degradationThreshold`, `failureThreshold` va `resetTimeoutMs` maydonlarini qoʻllab-quvvatlaydi; xuddi shu maydonlar Boshqaruv paneli → Sozlamalar → Chidamlilik boʻlimida ham koʻrsatiladi.

```bash
# Bitta model blokirovkasini tozalash
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Barcha blokirovkalarni oʻchirish
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Toʻliq kontseptual maʼlumotnoma va uzgichning standart qiymatlari: [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" va [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) ga qarang.

### Rate-Limit navbati va avtomatik yoqish himoya mexanizmi

- **Qoʻllab-quvvatlanadigan yozish yoʻli**: ulanish uchun rate-limit himoyasini almashtirishda qoʻllab-quvvatlanadigan boshqaruv endpointi — `{"connectionId": "<id>", "enabled": true|false}` tanasi bilan `POST /api/rate-limits`. `PUT /api/providers/[id]` ataylab `rateLimitProtection` ni oʻzgartirmaydi yoki almashtirmaydi (#11278).
- **`enabled: false` semantikasi**: `enabled: false` oʻrnatish ulanish uchun aniq belgilangan himoyani olib tashlaydi, lekin faol API-kalit ulanishini global avtomatik yoqish himoya mexanizmidan (`autoEnableApiKeyProviders = true`) **chiqarmaydi**. `reconcileEnabledConnections` da (`open-sse/services/rateLimitManager.ts`) `false` va `undefined` teng kuchli; aniq himoyaga ega boʻlmagan faol API-kalit ulanishlari avtomatik yoqish himoya mexanizmi ostida himoyalangan boʻlib qoladi.
- **Global oʻchirish**: API-kalit ulanishlarini rate-limit navbatlarisiz ishlatish uchun himoya mexanizmini global ravishda `RATE_LIMIT_AUTO_ENABLE=false` (env) yoki `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Sozlamalar → Chidamlilik / `PATCH /api/resilience`) orqali oʻchiring.

## A2A serveri

OmniRoute tekshirish/boshqaruv panelida foydalanish uchun A2A (Agent-to-Agent) JSON-RPC 2.0 endpointini hamda REST o‘ramini taqdim etadi.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY o‘rnatilmagan bo‘lsa, ixtiyoriy
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Ushbu dasturlash vazifasini yo‘naltir"}]
  }
}
```

Qo‘llab-quvvatlanadigan metodlar (barchasi `settings.a2aEnabled` orqali boshqariladi):

| Metod            | Tavsif                                                               |
| ---------------- | -------------------------------------------------------------------- |
| `message/send`   | Ko‘nikmani sinxron bajaradi; `{task, artifacts, metadata}` qaytaradi |
| `message/stream` | Xuddi shu ko‘nikmalar to‘plamini oqimli SSE orqali bajaradi          |
| `tasks/get`      | Vazifani `taskId` bo‘yicha oladi                                     |
| `tasks/cancel`   | Vazifani `taskId` bo‘yicha bekor qiladi                              |

Ichki ko‘nikmalar: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agent kartasi

```bash
GET /.well-known/agent.json
```

Ommaviy A2A agent kartasini (nomi, tavsifi, imkoniyatlari, ko‘nikmalar katalogi, autentifikatsiya sxemasi) qaytaradi — ommaviy tarzda 1 soatga keshlanadi. Autentifikatsiya talab qilinmaydi.

### REST yordamchilari

| Metod | Yo‘l                         | Tavsif                                                                                                                  |
| ----- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A yoqilganligi + vazifa statistikasi + keshlangan agent kartasi xulosasi                                              |
| GET   | `/api/a2a/tasks`             | Vazifalar ro‘yxati — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST yordamchisi sifatida amalga oshirilmagan — JSON-RPC `message/send` orqali yarating)                               |
| GET   | `/api/a2a/tasks/[id]`        | Bitta vazifani olish                                                                                                    |
| POST  | `/api/a2a/tasks/[id]/cancel` | Vazifani bekor qilish                                                                                                   |

**Autentifikatsiya:** REST yordamchilari boshqaruv autentifikatsiyasisiz ishlaydi (boshqaruv panelidan o‘qish mumkin); JSON-RPC `/a2a` marshruti sozlangan bo‘lsa, Bearer `OMNIROUTE_API_KEY` kalitidan foydalanadi.

## Autentifikatsiya

Toʻrtta hisob maʼlumotlari oilasi (boshqaruv paneli seansi, mahalliy CLI tokeni, `oma_live_…` kirish tokeni, boshqaruv doirasidagi API kaliti) va ularning inferensiya kalitlaridan farqi haqida [Boshqaruv autentifikatsiyasi](../guides/MANAGEMENT-AUTH.md) qoʻllanmasiga qarang.

- Boshqaruv paneli marshrutlari (`/dashboard/*`) `auth_token` cookie faylidan foydalanadi
- Tizimga kirishda saqlangan parol xeshidan foydalaniladi; zaxira variant sifatida `INITIAL_PASSWORD` ishlatiladi
- `requireLogin` sozlamasini `/api/settings/require-login` orqali yoqish yoki oʻchirish mumkin
- `REQUIRE_API_KEY=true` boʻlganda, `/v1/*` marshrutlari ixtiyoriy ravishda Bearer API kalitini talab qiladi
- Ushbu maʼlumotnomadagi «boshqaruv tokeni» / «boshqaruv doirasidagi API kaliti» yuqoridagi qoʻllanmada keltirilgan oilalardan birini anglatadi — bu taʼriflanmagan qoʻshimcha maxfiy maʼlumot turi emas

> **Orqaga mos kelmaydigan oʻzgarish (v3.8.0)** — `/api/v1/agents/tasks/*` va kutish muddatini boshqarish endpointlari endi **boshqaruv autentifikatsiyasini** (boshqaruv panelining `auth_token` cookie fayli yoki boshqaruv doirasidagi API kaliti) talab qiladi. Avval ushbu marshrutlarni autentifikatsiyasiz chaqirgan mijozlar `401 Unauthorized` javobini oladi. `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) commitiga qarang.
