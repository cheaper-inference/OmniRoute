Ushbu qoʻllanmadan pull request uchun eng kichik ishonchli ishlab chiqish siklini tanlashda foydalaning. U quyida havola qilingan sohaga xos arxitektura va xavfsizlik hujjatlarini
almashtirmaydi; u har bir keng tarqalgan oʻzgartirish turini uning shartnomalari, yoʻnaltirilgan tekshiruvlari va CI qamrovi bilan bogʻlaydi.

## Har bir oʻzgartirish oʻtadigan yoʻl

1. **Tahrirlashdan oldin asosiy branchni tanlang.** Eng yuqori faol `release/v*` branchini toping va
   uning eng soʻnggi holatidan yangi branch yarating. `main`ni emas, oʻsha branchni maqsad qiling. Agar relizni muzlatish amalda boʻlsa, muzlatilgan
   branchni maqsad qilmang; [Branch yaratish va reliz modeli](BRANCHING_MODEL.md)da tavsiflangan
   keyingi faol sikldan foydalaning.
2. **Shartnomalarni nomlang.** Oʻzgartirish taʼsir qiladigan har bir katalog, sxema, generatsiya qilingan artefakt, ommaviy API yoki foydalanuvchi
   interfeysini aniqlang. Quyidagi jadvalda boshlash uchun zarur boʻlgan minimal toʻplam berilgan.
3. **Yoʻnaltirilgan testlarni yozing yoki yangilang.** `src/`, `open-sse/`, `electron/` yoki
   `bin/` ichidagi ishlab chiqarish kodiga kiritilgan oʻzgartirishlar ayni PR ichida avtomatlashtirilgan testni talab qiladi. Xatti-harakatni tasdiqlaydigan eng kichik
   test fayllarini, soʻng roʻyxatda keltirilgan yoʻnaltirilgan nazoratlarni ishga tushiring.
4. **Keng matritsani CI ishga tushirsin.** Toʻliq unit shardlar, Vitest, qamrov ratcheti va
   ishlab chiqarish buildi PRda ishga tushadi. Keng testlar toʻplamini lokal ravishda faqat yoʻnaltirilgan testdagi xato
   taʼsir kengroq ekanini koʻrsatsa yoki oʻzgartirish bir nechta quyi tizimni qamrab olsa ishga tushiring.
5. **Koʻrib chiqishdan oldin muvofiqlashtiring.** Faol asosiy branchni fetch qiling, uning yangi commitlari va unga nisbatan diffingizni
   tekshiring, soʻng hissa qoʻshuvchi ish jarayoniga muvofiq asosiy branchni rebase yoki merge qiling. Generatsiya qilingan fayllar
   va kataloglardagi ziddiyatlarni ularning manbasidan bartaraf eting, ularni qayta generatsiya qiling, yoʻnaltirilgan siklni qayta ishga tushiring va
   PR hanuz faol reliz branchini maqsad qilayotganini tasdiqlang.
6. **Dalillarni qayd eting.** PR shablonida ishga tushirilgan buyruqlar, qoʻshilgan yoki oʻzgartirilgan har bir test fayli,
   migratsiyalar yoki feature flaglar hamda faqat CI orqali bajarilishi kutilayotgan tekshiruvlarni koʻrsating.

## Oʻzgartirish turi boʻyicha asosiy yoʻllar

Quyidagi buyruqlar minimal yoʻnaltirilgan tekshiruvlardir, ular siz oʻzgartirgan
xatti-harakatni bevosita qamrab oladigan testni oʻtkazib yuborishga ruxsat bermaydi.

### Provayder

**Shartnomalar**

- `src/shared/constants/providers/` ichidagi provayder taʼrifi va uning
  `src/shared/constants/providers.ts` ichidagi kompozitsiyasi.
- `open-sse/config/providerRegistry.ts` yoki undan ajratib olingan registr fayllaridagi modellar va imkoniyatlar.
- Zarur boʻlganda executor/translator tanlovi, OAuth yoki API kaliti konfiguratsiyasi, boshqaruv paneli resurslari va generatsiya qilingan
  provayder maʼlumotnomasi.
- Ommaviy hisob maʼlumotlari `resolvePublicCred()`dan foydalanishi kerak; xato javoblarida umumiy sanitizatsiya qilingan
  xato yordamchi vositalaridan foydalanish shart. `docs/security/PUBLIC_CREDS.md` (git; `/docs` ichiga kompilyatsiya qilinmaydi) va
  [Xatolarni sanitizatsiya qilish](../security/ERROR_SANITIZATION.md)ga qarang.

**Yoʻnaltirilgan sikl**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # katalog oʻzgarganda; generatsiya qilingan diffni commit qiling
npm run lint
```

Shuningdek, taʼsirlangan har bir soʻrov oilasini test qiling: chat, Responses, tasvirlar, embeddinglar, audio yoki video.
Generatsiya qilingan katalog va golden difflarni shartnoma oʻzgarishlari sifatida koʻrib chiqing; ularni koʻr-koʻrona qabul qilmang.

### Marshrutlash

**Shartnomalar**

- `src/shared/constants/routingStrategies.ts` ichidagi ommaviy strategiya qiymatlari va UI metamaʼlumotlari.
- `open-sse/services/combo.ts` va `open-sse/services/combo/` ostidagi dispatch hamda tartiblash.
- Combo sxemalari, saqlash, bardoshlilik holati, model imkoniyatlari va API/UI boshqaruv elementlari.
- Xatti-harakat oʻzgarganda [Auto-Combo Engine](../routing/AUTO-COMBO.md) va bardoshlilik hujjatlari.

**Yoʻnaltirilgan sikl**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategiya yoki dispatch oʻzgarishlari
npm run check:known-symbols      # strategiyani roʻyxatdan oʻtkazishdagi oʻzgarishlar
npm run lint
```

Lokal ravishda deterministik, yuqori oqim mock qilingan testlardan foydalaning. Jonli combo smoke testlari hisob maʼlumotlarini talab qiladi va
qoʻlda bajariladi, ular CI oʻrnini bosmaydi.

### UI / UX

**Shartnomalar**

- `src/app/` va `src/shared/components/` ostidagi Next.js marshrut/sahifa va umumiy komponent chegaralari.
- API javob shakllari, yuklanish/boʻsh/xato holatlari, klaviatura va ekran oʻquvchi xatti-harakati,
  moslashuvchan maket, mavzular va lokal kengaytirish.
- `src/i18n/messages/en.json` ichidagi inglizcha UI manba satrlari; foydalanuvchiga koʻrinadigan yangi matnni kodga bevosita yozmang.

**Yoʻnaltirilgan sikl**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaktiv yoki vizual oʻzgarishlar uchun ilovani ishga tushiring hamda tor va keng viewportlarni tekshiring. CI
ishlab chiqarish buildi va kengroq testlar toʻplamini ishga tushiradi; vizual xatti-harakat uchun baribir oʻzgartirishga mos yoʻnaltirilgan komponent testi, Playwright
testi yoki hujjatlashtirilgan qoʻlda tekshiruv zarur.

### i18n

**Shartnomalar**

- `src/i18n/messages/en.json` — UI manbasi; `config/i18n.json` — lokallar manbasi.
- CLI kataloglari `bin/cli/locales/` ostida alohida joylashgan.
- ICU placeholderlari va teglarini aynan saqlang. Mahsulot/provayder/model nomlari,
  protokol va header nomlari, buyruqlar, kod/JSON identifikatorlari, URLlar, muhit oʻzgaruvchilari yoki
  `OmniRoute`, `OAuth`, `MCP` va `A2A` kabi himoyalangan atamalarni tarjima qilmang. Joriy manba roʻyxati:
  `scripts/i18n/glossary/protected-terms.json`.

**Yoʻnaltirilgan sikl**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
```

Bu mavjud tizim uchun koʻrsatma, uning vositalari yoki kalit modelini kengaytirishga taklif emas.
Oʻrnini bosuvchi tizim loyihalanayotgan paytda i18n patchlarini aniq va cheklangan tuting. Vazifa generatsiya qilingan tarjimalarni aniq talab qilmasa va
natijaviy diffni koʻrib chiqmagan boʻlsangiz, tashqi xizmatlarni chaqiradigan tarjima buyruqlarini ishga tushirmang.

### CLI

**Shartnomalar**

- `bin/cli/` ichidagi ommaviy buyruqlar va bayroqlar, generatsiya qilingan API buyruqlari, chiqish kodlari, stdout/stderr va

- CLI foydalanuvchiga ko‘rinadigan satrlari CLI i18n qatlamidan foydalanishi va `en`/`pt-BR` kataloglari o‘zaro mosligini saqlashi kerak.

Xatti-harakat tahlil qilish, fayllar yoki chiqish holatiga bog‘liq bo‘lsa, aniq buyruqni vaqtinchalik ma’lumotlar katalogida ishlating. CI kengroq paket artefakti va ekotizim tekshiruvlarini bajaradi.

### Qurish / joylashtirish

**Shartnomalar**

- Ildiz va ish maydoni manifestlari/qulf fayli, `scripts/build/`, Next.js mustaqil yig‘ilishi, `dist/`
  paketi tarkibi, Electron platformasi metama’lumotlari, CI ish jarayonlari va joylashtirish nazorat belgilari.
- Qo‘llab-quvvatlanadigan Node diapazonlari va `CLAUDE.md` ichida ruxsat etilgan Bun ishlatilishi o‘zgarishsiz qolishi kerak.
- Qurish artefaktlari kuzatuvga olinmaydi; bog‘liqlik, litsenziya, ish jarayoni va paket siyosatlari amal qiladi.

**Yo‘naltirilgan sikl**

Faqat o‘zgarish kompilyatsiya, mustaqil yig‘ilish, resurslar yoki bajarish muhiti paketlanishiga ta’sir qilganda `npm run build` buyrug‘ini lokal ravishda ishlating. `npm run build:release` buyrug‘idan faqat reliz/joylashtirishni tekshirish uchun foydalaning. CI qurishi platformalararo yakuniy signal hisoblanadi; muayyan platformaga xos Electron o‘zgarishlari mos yo‘naltirilgan qurish yoki smoke sinovi dalilini talab qiladi.

## Umumiy mashina uchun dasturchi skriptlari

Ishlayotgan boshqa sessiyalar mavjud devbox’da mahalliy siklni ikkita `scripts/dev/` yordamchi skripti ta’minlaydi:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD dagi fayllar
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # aynan shu fayllar
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # izolyatsiyalangan worktree, parallel ishlatish xavfsiz
```

- `typecheck-touched.sh` faqat o‘zgartirilgan `.ts/.tsx` fayllarini vaqtinchalik
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) orqali 6 GB heap bilan tur tekshiruvidan o‘tkazadi, shu sababli u yuklangan
  mashinada OOM holatiga olib keladigan loyiha miqyosidagi `tsc -p tsconfig.json` o‘rnini bosadi.
  U o‘zgartirilgan fayllardagi xatolarni va bitta yakuniy satrni chiqaradi hamda o‘zgartirilgan
  fayllarda xatolar bo‘lsa `1`, xatolar faqat import qilingan fayllarda bo‘lsa yoki tsc
  diagnostikasiz to‘xtasa `2` (u `_artifacts/typecheck-touched/` ichida ko‘rsatgan jurnalni o‘qing),
  hammasi toza bo‘lsa `0` kodi bilan yakunlanadi. Vaqtinchalik tsconfig har doim o‘chiriladi;
  uni hech qachon commit qilmang.
- `new-worktree.sh` bir vaqtda bajarilayotgan ishlarni `<git-common-dir>/omniroute-new-worktree.lock`
  orqali ketma-ketlashtiradi (standart holatda ko‘rinadigan xabar bilan 600 s gacha kutadi;
  skript sarlavhasida bu qiymatni almashtirish usuli hujjatlashtirilgan) va
  `git worktree add` worktree yaratilishidan oldin muvaffaqiyatsiz tugasa, o‘zi yaratgan branch’ni
  orqaga qaytaradi, shu sababli qayta urinish uchun `git branch -D` buyrug‘ini qo‘lda bajarish
  shart emas. Hard link qilingan `node_modules` va `.husky/_` nusxasi o‘zgarmaydi.

## Mahalliy nomzod sikli

Manba testlari paketlangan artefakt ishga tushishini isbotlay olmaydi: paketlash ro‘yxatlari,
qisqartirilgan bog‘liqliklar va mahalliy binar fayllardagi muammolar faqat tarball o‘rnatilib,
ishga tushirilgandan keyin yuzaga chiqadi. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) — RFC #8084 dagi bir marta qurish / tekshirish / ilgari surish
jarayonining mahalliy tomoni: u bitta nomzodni quradi, aynan shu artefaktni tekshiradi, kataloglarni
qayta nomlash orqali uni ilgari suradi va ilgari surilgan slot salomatlik tekshiruvidan o‘tmasa,
uni orqaga qaytaradi.

```bash
npm run dev:candidate -- run --dry-run --json  # rejani chiqaring, hech narsani o‘zgartirmang
npm run dev:candidate -- run                   # qurish + tekshirish + ilgari surish, avtomatik orqaga qaytarish
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ichiga o‘rnatish
npm run dev:candidate -- validate --id <id>    # bo‘sh portda ishga tushirish, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current va previous o‘rinlarini almashtirish
npm run dev:candidate -- run --from-tarball <file.tgz>  # boshqa joyda (CI’da) qurilgan tarball’dan qayta foydalanish
```

- **Bir marta quring.** `build` joriy daraxtni paketlaydi (unga `dist/server.js` kerak, shuning uchun
  avval `npm run build:release` buyrug‘ini bajaring) yoki `--from-tarball` orqali berilgan faylni
  nusxalaydi, so‘ng tarball tarkibida `node_modules` bo‘lmagani sababli uni izolyatsiyalangan npm
  prefiksiga o‘rnatadi. Id — qisqa `HEAD` sha (daraxtda mahalliy o‘zgarishlar bo‘lsa `-dirty`) yoki
  tarball uchun `tgz-<sha256>`. Allaqachon qurilgan toza id qayta qurish o‘rniga qayta ishlatiladi;
  uni qayta qurish uchun `--force` parametrini bering.
- **Manbani emas, paketni tekshiring.** `validate` o‘rnatilgan CLI’ni
  (`serve --port <free port>`) yangi `DATA_DIR=<candidate>/data`, soxta maxfiy ma’lumotlar bilan
  hamda operatorning `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` va `INITIAL_PASSWORD`
  o‘zgaruvchilarini muhitdan olib tashlagan holda ishga tushiradi; shu tariqa u yangi o‘rnatmaning
  kalitsiz loopback holatini tekshiradi. U `GET /api/health` 200 qaytarishini kutadi,
  `GET /v1/models` 200 qaytarishini talab qiladi, jarayonlar guruhini to‘xtatadi va natijani tarball
  xeshi bilan birga `validation.json` fayliga yozadi.
- **Aynan shu artefaktni ilgari suring.** `promote` joriy tarball xeshi uchun muvaffaqiyatli
  tekshiruvga ega bo‘lmagan nomzodni rad etadi. Standart faol slot
  `_artifacts/candidate/current`; `--target <dir>` xuddi shu fayl tizimidagi boshqa katalogni
  tanlaydi, uning oldingi sloti esa `<dir>.previous` bo‘ladi. Har bir qayta nomlash atomar tarzda
  bajariladi, jarayon o‘rtasidagi nosozlik esa allaqachon bajarilgan qayta nomlashlarni bekor qiladi.
- **Orqaga qaytaring.** `run` ilgari surilgan slotni yana tekshiradi va bu tekshiruv muvaffaqiyatsiz
  tugasa, `current` hamda `previous` slotlarini qayta almashtiradi. Birinchi tekshiruvdan o‘ta
  olmagan nomzod hech qachon ilgari surilmaydi.

Barcha ma’lumotlar git tomonidan e’tiborsiz qoldiriladigan `_artifacts/candidate/` ichiga yoziladi;
mavjud OmniRoute o‘rnatmasi va uning ma’lumotlar katalogiga hech qachon tegilmaydi. Ilgari surilgan
CLI — `_artifacts/candidate/current/prefix/bin/omniroute`; undan foydalanganda uni o‘zingizning
`DATA_DIR` qiymatingiz bilan ishga tushiring. Chiqish kodlari: `0` — muvaffaqiyat, `1` — tekshiruv
yoki ilgari surish muvaffaqiyatsiz, `2` — foydalanish xatosi yoki qurilma mavjud emas.

## Mahalliy sikl va CI taqqoslanishi

| Har bir patch uchun mahalliy ishga tushiring                                                 | CI keng qamrovli signalni taqdim etadi                                         |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Yuqoridagi bevosita xatti-harakat testlari va toifa darvozalari                              | Boʻlaklarga ajratilgan toʻliq unit-testlar toʻplami va ketma-ket testlar       |
| `npm run lint`                                                                               | Vitest toʻplamlari hamda qamrov/sifat ratchetlari                              |
| Faqat taʼsirlangan kontrakt talab qilgandagina tur tekshiruvi yoki build                     | Production build, xavfsizlik, hujjatlar, bogʻliqlik va PR siyosati darvozalari |
| Faqat avtomatlashtirish xatti-harakatni isbotlay olmaganda qoʻlda ishlash/jonli tekshiruvlar | Workflow orqali sozlangan joblararo integratsiya va platforma tekshiruvlari    |

Yashil holatdagi yoʻnaltirilgan sikl — oʻzgartirilgan kontraktga oid dalil, biroq aloqasiz CI tekshiruvlari
muvaffaqiyatli oʻtishining isboti emas. Aksincha, har bir mahalliy tahrirni repozitoriyning toʻliq matritsasini kutishga majburlamang.

## Muvofiqlashtirish nazorat roʻyxati

Koʻrib chiqishni soʻrashdan oldin:

- PR bazasi hanuz eng yuqori faol `release/v*` branch ekanini tasdiqlang.
- Shu bazani fetch qiling va branch yaratganingizdan beri qoʻshilgan commitlarni koʻrib chiqing.
- Tasodifiy yoki generatsiya qilingan keraksiz oʻzgarishlarni aniqlash uchun `git diff <active-base>...HEAD` natijasini koʻrib chiqing.
- Katalog va generatsiya qilingan hujjatlardagi konfliktlarni manbani yangilash va natijani qayta generatsiya qilish orqali hal qiling.
- Muvofiqlashtirishdan soʻng PR tavsifida sanab oʻtilgan har bir yoʻnaltirilgan test/darvozani qayta ishga tushiring.
- Siljigan bazaga moslashish uchungina assertionlarni hech qachon zaiflashtirmang yoki majburiy testlarni olib tashlamang.

Release freeze va qayta yoʻnaltirish qoidalari uchun
[Branch yaratish va release modeli](BRANCHING_MODEL.md)dan foydalaning. Toʻliq CI inventari uchun
[Sifat darvozalari maʼlumotnomasi](../architecture/QUALITY_GATES.md)dan foydalaning.
