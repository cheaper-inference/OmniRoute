> **Özet**: `open-sse/`, OmniRoute'taki her LLM isteğine güç veren temel akış motorudur. İstek işlem hattını, yürütücüleri, servisleri, MCP sunucusunu ve çeviri katmanını uygulayan yaklaşık 1.400 dosya içerir. Bu kılavuz, parçaların nasıl bir araya geldiğini açıklar.

**Kaynak:** `open-sse/` (çalışma alanı paketi, yaklaşık 1.440 test dışı `.ts` dosyası)

## Neden Ayrı Bir Çalışma Alanı Paketi?

`open-sse/`, çeşitli nedenlerle OmniRoute monorepo'sunda **bağımsız bir çalışma alanıdır**:

1. **Yeniden kullanılabilirlik** — `open-sse`, npm üzerinde `@omniroute/open-sse` olarak yayımlanır; böylece diğer projeler onu bağımsız olarak kullanabilir
2. **Net sınırlar** — akış motoru, OmniRoute'a özgü UI/DB katmanından ayrıştırılmıştır
3. **Performans** — motorun Next.js bağımlılığı yoktur; bu da CLI/sunucusuz bağlamlarda daha hızlı soğuk başlatmalar sağlar
4. **Sürümleme** — `open-sse` kendi yayın takvimine göre sürüm çıkarabilir

```json
// package.json
"workspaces": ["open-sse"]
```

## İstek İşlem Hattı

Her LLM isteği **5 aşamalı bir işlem hattından** geçer:

```
                              ┌──────────────┐
   HTTP isteği                │  1. YÖNLENDİR│   combo çözümleme, model seçimi
   (Next.js rotası)           └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. ÇEVİR    │   biçim dönüştürme (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. YÜRÜT    │   sağlayıcı yürütücüsü, HTTP, yeniden deneme, devre kesici
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. AKIŞ     │   SSE dönüşümü, geri basınç
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. KAYDET   │   kullanım takibi, çağrı günlüğü, hata sınıflandırma
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP yanıtı (SSE veya JSON)
```

### Aşama 1: Yönlendirme (services/combo.ts)

**Giriş noktası**: `services/combo.ts` içindeki `handleComboChat()`

İsteği somut bir `(provider, model, account, credentials)` demetine çözümler:

- Combo'yu kimliğine göre ara (veya `auto/*` modelleri için sanal bir combo oluştur)
- Yönlendirme stratejisini uygula (öncelik, ağırlıklı, round-robin vb.)
- Sağlıksız sağlayıcıları filtrele (devre kesici)
- Sıradaki kullanılabilir hedefi seç

`auto/*` modelleri için bu aşama ayrıca:

- **16 faktörlü puanlama** algoritmasını çalıştırır (`services/autoCombo/`)
- Sağlık, maliyet, gecikme vb. ölçütlere göre bir `provider+model` çifti seçer

### Aşama 2: Çeviri (translator/)

Kaynak biçim (ör. OpenAI) hedef biçimden (ör. Claude) farklıysa istek **çevrilir**:

- Sistem istemi → sistem mesajı
- Araç tanımları → sağlayıcıya özgü araç biçimi
- Akıl yürütme/düşünme parametreleri → sağlayıcıya özgü eşdeğerler
- Mesaj rolü normalizasyonu (OpenAI dışındakiler için `developer` → `system`)

`translator/index.ts` şunları dışa açar:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Aşama 3: Yürütme (executors/)

**Giriş noktası**: `getExecutor(providerId).execute(request, options)`

Tüm sağlayıcılar, `getExecutor()` fabrika yedeği aracılığıyla `DefaultExecutor` (`executors/default.ts`) kullanır. Yürütücü:

- Üst servis URL'sini oluşturur (`buildUrl()`)
- Sağlayıcıya özgü başlıkları ekler (`buildHeaders()`)
- İstek gövdesini dönüştürür (`transformRequest()`)
- HTTP isteğini yeniden deneme + üstel geri çekilme ile gönderir
- Gerektiğinde kimlik doğrulama bilgilerini yeniler (OAuth sağlayıcıları)

Tüm yürütücüler, aşağıdakileri sağlayan `BaseExecutor`'ı (`executors/base.ts`, 1170 LOC) genişletir:

- Ortak yeniden deneme mantığı
- Proxy entegrasyonu
- Devre kesici entegrasyonu
- Kullanım kaydı kancaları

### Aşama 4: Akış (utils/stream.ts)

Akış yanıtlarında yürütücü bir **ReadableStream** döndürür. İşleyici:

- Bir SSE dönüşümü üzerinden aktarır (`createSSETransformStreamWithLogger`)
- Kopmuş bağlantıları algılamak için periyodik sinyaller uygular
- İstemci bağlantısının kesilmesini sorunsuz biçimde işler (`pipeWithDisconnect`)
- Akış kullanmayan istemciler için SSE → JSON dönüşümü yapar

Akışsız yanıtlarda yürütücü, değişiklik yapılmadan aktarılan ayrıştırılmış bir JSON nesnesi döndürür.

### Aşama 5: Kaydetme (services/usage.ts)

Yanıttan sonra (başarılı veya başarısız), kullanım kaydedilir:

- Yanıttaki `prompt_tokens`, `completion_tokens`, `cached_tokens`
- Fiyatlandırma verilerinden hesaplanan `cost_usd`
- Başarısız olması durumunda `latency_ms`, `status`, `error_class`
- `usage_history` tablosunda kalıcı olarak saklanır

Çağrı günlüğü yapıtları (etkinleştirilmişse) `${DATA_DIR}/call_logs/` dizinine yazılır.

## Anahtar Dosyalara Derin Bakış

### chatCore.ts (5977 satır)

**ana istek işleyicisi** . Boyutuna rağmen net bir yapıya sahiptir:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

Devasa bir işlev olmasına rağmen, şu şekilde organize edilmiştir:** yorumlanan bölümler** 5 aşamalı boru hattının haritası.

// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);

    try {
      return await handleSingleModel(target, body);

### base.ts (1170 LOC)

**soyut uygulayıcı** her uygulayıcı sınıfının genişletildiği (doğrudan veya `DefaultExecutor` ve diğer alt sınıflar aracılığıyla). Şunları içerir:

- `buildUrl()` — varsayılan URL yapısı (özel için alt sınıflar geçersiz kılınır)
- `buildHeaders()` — varsayılan üstbilgileri (kimlik doğrulama, içerik türü)
- `transformRequest()` — varsayılan olarak doğrudan geçiş
- `execute()` — retry/backoff/breaker ile ana HTTP döngüsü

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

Sağlayıcıya özgü davranış (kimlik doğrulama üstbilgileri, temel URL, sürüm üstbilgileri), ayrı yürütücü sınıfları tarafından değil, sağlayıcı kayıt defteri aracılığıyla yapılandırılır.

## Yürütücüler (150 modül)

Çoğunlukla sağlayıcı başına bir dosya. Yürütücü sınıfların tümü `BaseExecutor` genişletir ve farklı olanı geçersiz kılar; diğer modüller sağlayıcı başına yardımcılardır (araç şemaları, fetch/TTS bağdaştırıcıları, tuhaf işleyiciler).

### Ortak Desenler

Sağlayıcılar, yapılandırılmış yürütücüyü döndüren `getExecutor(providerId)` aracılığıyla çözümlenir. OpenAI/Anthropic-compatible sağlayıcıları `DefaultExecutor` (`executors/default.ts`) kullanır. Sağlayıcıya özgü davranış (temel URL, kimlik doğrulama başlıkları, API sürümü) `open-sse/config/providers/` yapılandırılırken, istek gövdesi dönüşümleri `open-sse/translator/` işlenir.

**Özel URL** sağlayıcı yapılandırması aracılığıyla ayarlanır:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Özel kimlik doğrulama** sağlayıcı kayıt defterinin kimlik doğrulama yapılandırması (API anahtarı, OAuth, başlık profilleri) aracılığıyla gerçekleştirilir.

**Özel istek gövdesi** dönüşümler (örneğin, `system` `messages` ayıran Anthropic ), `open-sse/translator/` sağlayıcı başına kaydedilir.

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Çözüm `ExecutorRegistry` (`executors/registry.ts`) üzerinden geçer: her özel uygulayıcı `executors/index.ts` yerleşik tablosunda bildirilir ve modül yükünde `registerExecutor(alias, instance)` aracılığıyla kaydedilir; `getExecutor()` kayıt defterine danışır ve özel bir girişi olmayan herhangi bir sağlayıcı için not edilmiş bir `DefaultExecutor` geri döner. Tam takma ad → yürütücü eşlemesi, altın test `tests/unit/executor-map-golden.test.ts` ile karakterize edilir.

## Çeviriciler

Yeni Responses API'nin yanı sıra **3 format** arasında çeviri yapar: OpenAI, Anthropic, Gemini.

### Çevirinin Gerçekleştiği Durumlar

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Yaygın çeviriler:

- `OpenAI → Anthropic`: ayrı `system` alanı, `x-api-key` üst bilgisi
- `OpenAI → Gemini`: `messages` yerine `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` dizisi, `previous_response_id` durumu

### Ele Alınan Uç Durumlar

- `developer` rolü → OpenAI dışındaki sağlayıcılar için `system`
- `system` rolü → GLM/ERNIE için ilk kullanıcı mesajıyla birleştirilir
- `json_schema` → Gemini'nin `responseMimeType` + `responseSchema` alanları
- `tools` → sağlayıcıya özgü araç formatı
- Düşünme parametreleri (o1, Claude) → sağlayıcıya özgü karşılıklar

## MCP Sunucusu

`open-sse/mcp-server/`, **Model Context Protocol** sunucusunu uygular:

- **110 araç** (sağlayıcı yönetimi, kombinasyonlar, bellek, önbellek, sıkıştırma, proxy, beceriler, oyunlaştırma, eklentiler, Notion, Obsidian, yerel külliyat)
- **3 aktarım yöntemi**: stdio, SSE, Streamable HTTP
- Ayrıntılı yetkilendirme için **33 kapsam**

### Araç Kaydı

Araçlar, `open-sse/mcp-server/tools/` içinde bağımsız dosyalar olarak kaydedilir; her biri bir ad, şema, işleyici ve kapsam dışa aktarır:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Sistem durumu anlık görüntüsünü al",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Aktarım Yöntemleri

```ts
// stdio (CLI kullanımı)
startMcpStdio(server);

// SSE (HTTP tabanlı akış)
startMcpSse(server, port);

// Streamable HTTP (modern MCP)
startMcpStreamable(server, port);
```

### Yetkilendirme

Her araç çağrısı kapsam denetimlerinden geçer (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Yetersiz kapsam");
}
```

## Dönüştürücüler

`open-sse/transformer/`, **Chat Completions** ve **Responses API** formatları arasında dönüşüm yapar.

### Neden Ayrı Bir Dönüştürücü Var?

Responses API, OpenAI'ın **durum bilgisi tutan konuşmalar** (`previous_response_id`) içeren yeni formatıdır. Bir istemci Responses isteği gönderdiğinde OmniRoute:

1. Responses formatını dahili olarak Chat Completions formatına dönüştürür
2. İsteği sağlayıcıya gönderir (Chat Completions destekleyen herhangi bir sağlayıcı)
3. Yanıtı tekrar Responses formatına dönüştürür
4. Dönüştürülen yanıtı istemciye akış olarak iletir

Dönüştürücü (`transformer/responsesTransformer.ts`) şunu sağlar:

```ts
createResponsesApiTransformStream(): TransformStream
```

Bu, şunları işler:

- `response.output_item.added` olayları
- `response.output_text.delta` olayları
- `response.completed` olayı
- Araç çağrısı eşleme (`function_call` ↔ `tool_calls`)

## Yapılandırma

`open-sse/config/` konfigürasyon katmanını tutar:

| Dosya                         | Amaç                                                 |
| ----------------------------- | ---------------------------------------------------- |
| `providerRegistry.ts`         | 394 sağlayıcı kataloğu üzerinden sohbet modeli kaydı |
| `providerModels.ts`           | Model takma adları, format eşleme                    |
| `constants.ts`                | Zaman aşımları, sınırlar, durum kodları              |
| `defaultThinkingSignature.ts` | Varsayılan Claude düşünme imzası                     |
| `modelStrip.ts` (hizmetlerde) | Sağlayıcı başına alan ayırma                         |

### Sağlayıcı Kayıt Şeması

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Modül yükünde Zod doğrulaması, tüm sağlayıcı yapılandırmalarının geçerli olmasını sağlar.

## Kaçınılması Gereken Kalıplar

❌ **`combo.ts` içinde senkron veritabanı çağrıları** — önceden hesaplayın ve önbelleğe alın
❌ **İşleyicilerde yeniden deneme mantığı** — dayanıklılık hizmetindeki `retry()` işlevini kullanın
❌ **Sağlayıcı yapılandırmasına doğrudan erişim** — `providerRegistry` alıcılarını kullanın
❌ **Sabit kodlanmış geri dönüş zincirleri** — `modelFamilyFallback.ts` içinde tanımlayın
❌ **Eşzamanlı istekler arasında durum değişiklikleri** — yalnızca istek kapsamlı bağlam kullanın

## Yeni Bir Bileşen Ekleme

### Yeni Bir Hizmet Ekleme

1. Odaklanmış bir sorumlulukla `open-sse/services/[serviceName].ts` oluşturun
2. Ana işleyici işlevini ve varsa sabitleri dışa aktarın
3. `tests/unit/services/[serviceName].test.mjs` içine birim testleri ekleyin
4. Yönlendirmeyle ilgiliyse `handlers/chatCore.ts` içindeki istek işlem hattına entegre edin
5. Hizmet hedef seçimini etkiliyorsa `combo.ts` içindeki yönlendirme mantığını güncelleyin
6. Bu dosyada belgelendirin

### Yeni Bir Yürütücü Ekleme

1. `BaseExecutor` sınıfını genişleten `open-sse/executors/[provider].ts` dosyasını oluşturun
2. `config/providerRegistry.ts` içinde kaydedin
3. `executors/index.ts` fabrikasına ekleyin
4. Yürütücü için birim testleri ekleyin
5. `docs/architecture/ARCHITECTURE.md` içinde belgelendirin

### Yeni Bir MCP Aracı Ekleme

1. `open-sse/mcp-server/tools/[category]Tools.ts` dosyasını oluşturun veya güncelleyin
2. Girdiler için Zod şemasını tanımlayın
3. Aracı `mcp-server/index.ts` içinde kaydedin
4. `mcp-server/auth/` içindeki kapsam matrisine ekleyin
5. Birim testleri ekleyin
