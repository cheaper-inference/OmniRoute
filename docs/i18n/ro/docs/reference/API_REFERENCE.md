## Completări de chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Anteturi personalizate

| Header                   | Direction | Description                                                                                                                                                                                                                                             |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Cerere    | Setați la `true` pentru a ocoli cache-ul                                                                                                                                                                                                                |
| `x-omniroute-no-memory`  | Cerere    | Setați la `true` pentru a omite injectarea memoriei și a competențelor pentru această cerere (oglindește no-cache; evită costurile suplimentare de tokeni/cost per apel)                                                                                |
| `X-OmniRoute-Progress`   | Cerere    | Setați la `true` pentru evenimente de progres                                                                                                                                                                                                           |
| `X-Session-Id`           | Cerere    | Cheie de sesiune persistentă pentru afinitatea sesiunii externe                                                                                                                                                                                         |
| `x_session_id`           | Cerere    | Varianta cu caracter de subliniere este, de asemenea, acceptată (HTTP direct)                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | Cerere    | Etichetă de sesiune/conversație furnizată de apelant (alimentează și memoria). Când este prezentă, este păstrată textual în `call_logs.session_tag` pentru atribuirea costurilor per sesiune (#8249) — nu este niciodată generată automat când lipsește |
| `Idempotency-Key`        | Cerere    | Cheie de deduplicare (fereastră de 5 s)                                                                                                                                                                                                                 |
| `X-Request-Id`           | Cerere    | Cheie alternativă de deduplicare                                                                                                                                                                                                                        |
| `x-omniroute-connection` | Cerere    | Fixează o cerere către un singur model la o conexiune de furnizor (cont) după identificatorul acesteia — consultați [Fixarea contului per cerere](#account-pinning-per-request)                                                                         |
| `X-OmniRoute-Cache`      | Răspuns   | `HIT` sau `MISS` (fără streaming)                                                                                                                                                                                                                       |
| `X-OmniRoute-Idempotent` | Răspuns   | `true` dacă cererea a fost deduplicată                                                                                                                                                                                                                  |
| `X-OmniRoute-Progress`   | Răspuns   | `enabled` dacă urmărirea progresului este activată                                                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | Răspuns   | ID-ul efectiv al sesiunii utilizat de OmniRoute                                                                                                                                                                                                         |
| `X-OmniRoute-Request-Id` | Răspuns   | ID-ul de corelare al cererii (când este cunoscut)                                                                                                                                                                                                       |
| `X-OmniRoute-Version`    | Răspuns   | Versiunea build-ului OmniRoute (prezentă întotdeauna)                                                                                                                                                                                                   |
| `X-OmniRoute-Cost-Saved` | Răspuns   | Valoarea în USD economisită de cache la un `HIT` (doar pentru accesările din cache)                                                                                                                                                                     |
| `X-OmniRoute-Decision`   | Răspuns   | Urmărirea rutării: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` este strategia combinată sau `single` pentru o cerere care nu este combinată) — prezentă întotdeauna în răspunsurile de finalizare                                     |

> Notă pentru Nginx: dacă vă bazați pe antete cu caractere de subliniere (de exemplu, `x_session_id`), activați `underscores_in_headers on;`.

#### Fixarea contului per cerere

Când un furnizor are mai multe conexiuni (conturi sau chei), OmniRoute selectează în mod normal una
folosind strategia sa de selectare a contului. În schimb, o cerere poate fixa o conexiune
specifică folosind antetul `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Unde găsești id-ul.** Deschide pagina furnizorului în dashboard
  (**Dashboard → Providers → <provider>**) și fă clic pe cipul cu id-ul `xxxxxxxx…` dintr-un rând
  de conexiune — acesta copiază id-ul complet al conexiunii.
- **Ce solicitări îl respectă.** Solicitările pentru un singur model (`provider/model`) de pe
  `/v1/chat/completions`, `/v1/messages` și `/v1/responses`. Combinațiile ignoră antetul: fixează
  un cont pentru fiecare pas al combinației prin conexiunea proprie a pasului.
- **Fixarea este strictă, nu o preferință.** Conexiunea fixată este utilizată exclusiv. Un
  eșec în timpul solicitării înregistrează perioada de răcire a contului, dar **nu** trece la un
  cont asociat al aceluiași furnizor.
- **Perioada de răcire și cota eliberează fixarea.** În timp ce conexiunea fixată se află în
  perioada de răcire, cota este epuizată sau accesul este blocat de o politică de cotă,
  solicitările ulterioare revin la celelalte conexiuni ale furnizorului, exact ca traficul fără
  fixare.
- **ID-urile necunoscute sau dezactivate eșuează.** Un ID care nu se află în grupul activ al
  furnizorului (șters, dezactivat sau aparținând altui furnizor) nu lasă niciun cont eligibil,
  astfel încât solicitarea eșuează în loc să fie direcționată în tăcere în altă parte.

Claude Code trimite antete personalizate prin `ANTHROPIC_CUSTOM_HEADERS`. Adaugă-l în blocul
`env` din `~/.claude/settings.json` sau într-un fișier `.claude/settings.json` la nivel de
proiect pentru a fixa un cont diferit pentru fiecare proiect:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Sursă: `src/sse/handlers/chat.ts` (citirea antetului), `src/sse/services/auth.ts` și
`src/sse/services/sessionAffinityPin.ts` (eliberarea fixării și verificarea absenței din grup).

> **Antete de telemetrie a costurilor:** răspunsurile reușite care nu sunt de tip streaming includ, de asemenea, setul de telemetrie a costurilor `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 zecimale fixe; `0.0000000000` pentru gratuit/fără preț), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` și `X-OmniRoute-Fallback-Attempts` (doar când > 0), plus `X-OmniRoute-Request-Id` și `X-OmniRoute-Version`. Acestea sunt emise de completările de chat, `/v1/responses`, `/v1/messages` **și endpointurile media** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` și `/v1/moderations` (cost întotdeauna `0`). Costul media este calculat pentru fiecare modalitate (per imagine, per secundă, per caracter, per unitate de căutare) atunci când prețurile sunt disponibile, altfel `0` (fail-open).

> **Semantica costului pentru accesările din cache:** la un HIT în cache-ul semantic (`X-OmniRoute-Cache-Hit: true`) nu se efectuează niciun apel upstream, astfel încât `X-OmniRoute-Response-Cost` este `0.0000000000` (costul **incremental** al servirii accesării). Costul inițial/care ar fi fost efectuat este raportat separat în `X-OmniRoute-Cost-Saved`. Consumatorii de facturare ar trebui să însumeze `X-OmniRoute-Response-Cost` (accesările nu costă nimic); analizele cache-ului pot agrega `X-OmniRoute-Cost-Saved`.

## Închirieri exclusive de sesiuni gestionate

Închirierea exclusivă a sesiunilor gestionate este un contract de rutare opțional, neutru față de client: un singur proprietar activ deține o singură conexiune OmniRoute eligibilă. Nu închiriază un model, nu necesită OAuth, nu identifică un anumit client și nu necesită un anumit furnizor.

Cheia API de autentificare trebuie să aibă domeniul `lease:exclusive` și o listă `allowedConnections` explicită și nevidă. Limita de mutație a bazei de date impune ambele câmpuri împreună la crearea cheii și la actualizările parțiale.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Răspunsurile reușite pentru acquire, renew și release expun marcaje temporale, `state` și valoarea exactă pozitivă a `generation`, dar niciodată conexiunea selectată sau acreditările. Renew și release furnizează valoarea generation în corpul JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Un proprietar activ al unei închirieri poate solicita explicit metadate de afișare sigure din punct de vedere al confidențialității pentru asocierea sa curentă:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Această acțiune de status opțională este protejată într-o singură tranzacție a bazei de date de proprietarul opac, de cheia API gestionată autentificată și de generația activă exactă. `displayName` este doar numele configurat al conexiunii, cu spațiile de la început și de la sfârșit eliminate; este `null` atunci când nu există un nume configurat sigur. OmniRoute nu înlocuiește niciodată acest nume cu un e-mail sau cu o identitate de cont generată. Valoarea provider este o etichetă de afișare nesensibilă și nu este niciodată un identificator de furnizor compatibil generat. Acreditările, tokenurile, cookie-urile, identificatorii neprelucrați ai conexiunilor sau ai cheilor API, hashurile proprietarilor, secretele de protecție și datele interne de rutare sunt excluse.

Căutările cu cheie greșită, proprietar greșit, generație învechită, lipsă, expirată, eliberată sau invalidată returnează toate aceeași eroare `409 LEASE_FENCE_STALE`, fără metadate despre conexiune. Un client care a primit răspunsul de așteptare pentru capacitate nu are nicio asociere activă de inspectat. Atunci când rutarea face tranziția unei închirieri active, aceeași generație rămâne validă, iar statusul returnează atomic noua asociere, niciodată pe cea veche. Clienții existenți rămân neschimbați, deoarece răspunsurile pentru acquire, renew, release și waiting își păstrează formele anterioare.

Acest contract al serverului nu modifică `/status` din OpenAI Codex standard. Codex standard raportează în prezent furnizorul modelului și starea încorporată a autentificării/contului, dar nu afișează metadate arbitrare despre contul unui furnizor personalizat; o integrare ulterioară a clientului trebuie să apeleze această acțiune și să decidă cum să afișeze `connection.displayName`.

Fiecare solicitare de inferență gestionată furnizează apoi ambele antete de control:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Proprietarul exact, generația, conexiunea activă și cheia API autentificată sunt verificate imediat înaintea fiecărei încercări acceptate către upstream. Reutilizarea proprietarului și a generației împreună cu o altă cheie eșuează chiar și atunci când cheia respectivă permite aceeași conexiune. Proprietarii neprelucrați nu sunt persistați, înregistrați în jurnale, păstrați în instantaneul solicitării sau redirecționați către upstream.

Contestația temporară returnează HTTP `429` cu `Retry-After` și:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Acest răspuns înseamnă doar că setul obișnuit de eligibile nu era gol și că fiecare candidat liber era deținut de o închiriere activă străină. Modelele/furnizorii nesuportați, nepotrivirea politicii, perioada de cooldown, cota, starea de sănătate și celelalte eșecuri obișnuite de eligibilitate își păstrează răspunsurile OmniRoute existente.

### `x-omniroute-compression`

Suprascriere per solicitare a planului de comprimare. Are cea mai mare prioritate — prevalează asupra suprascrierii combinației de rutare, profilului activ, declanșatorului automat și valorii Default din panou. Valori:

| Valoare       | Efect                                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | Fără comprimare pentru această solicitare.                                                                        |
| `default`     | Profilul Default derivat din panou (ignoră profilul activ). Motoarele cu pierderi rămân oprite.                   |
| `safe`        | Doar deduplicarea și compactarea spațiilor albe.                                                                  |
| `allow-lossy` | Păstrează planul operatorului pentru această solicitare, inclusiv rezumatele și rescrierile de stil.              |
| `engine:<id>` | Un singur motor atunci când este activat, de exemplu `engine:rtk`. Activare per solicitare pentru acel motor.     |
| `<combo>`     | O combinație denumită, potrivită mai întâi după nume (fără diferențiere între litere mari și mici), apoi după id. |

Note:

- Valorile necunoscute sunt ignorate (solicitarea nu este niciodată respinsă); rezoluția continuă conform priorității normale a operatorului.
- Dacă mai multe combinații au același nume, transmiteți **id**-ul combinației pentru o potrivire deterministă.
- O combinație al cărei nume este `off` sau `default` nu poate fi selectată după nume (aceste cuvinte-cheie sunt interpretate mai întâi); faceți referire la o astfel de combinație folosind id-ul său.
- Comutatorul principal al comprimării este o poartă strictă: atunci când comprimarea este dezactivată global, acest antet nu o poate activa.

Planul aplicat este returnat în antetul de răspuns:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

unde `<source>` este unul dintre `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` sau `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Furnizori disponibili: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

ID-urile catalogului sunt `provider/model` (exemplu: `jina-ai/jina-embeddings-v5-omni-small`). ID-urile de modele Jina simple care apar în registru (de exemplu, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) sunt, de asemenea, rezolvate. Pentru embed/rerank/classify/segment Jina sunt utilizate mai întâi acreditările `jina-ai` din tabloul de bord; `JINA_AI_API_KEY` este folosit ca alternativă doar când nu există nicio cheie în tabloul de bord. Cardul `jina-reader` este destinat exclusiv Reader / `r.jina.ai` (`POST /v1/web/fetch`) și nu furnizează niciodată embeddings sau rerank.

Modelele din registru care declară suport multimodal acceptă, de asemenea, până la 32 de elemente structurate independente de furnizor. Tipurile de elemente media sunt `text`, `image`, `audio`, `video` și `document`. `source`-ul media este fie `{"type":"url","url":"https://..."}`, fie `{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` și aliasul familiei `jina-ai/jina-embeddings-v5-omni` → omni-small) acceptă, de asemenea, documentația nativă Jina EmbeddingsV5Request și o **redirecționează intactă** către `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Valorile native `{ image | audio | video | pdf }` pot fi un URL HTTPS public, un URI `data:` sau base64 brut. OmniRoute nu transformă aceste obiecte în șiruri de caractere și nu preia URL-urile native ale imaginilor — Jina preia direct materialele media publice. Câmpurile Jina suplimentare (`task`, `normalized`, `truncate`, `embedding_type`) sunt redirecționate. SKU-urile Jina exclusiv textuale resping în continuare documentele care nu sunt text.

Limite de securitate și transport:

- URL-urile media la distanță trebuie să fie HTTPS public. Elementele canonice `{type,source:url}` sunt preluate pe partea serverului (revalidarea redirecționărilor, timeout, limite de dimensiune, DNS public, fixarea conexiunii) și încorporate înainte de apelul către furnizor. Elementele native Jina `{image:"https://..."}` sunt redirecționate ca atare după aceeași verificare HTTPS publică; Jina preia URL-ul.
- Media base64 încorporată este limitată la 8 MiB decodați pentru fiecare element și la 16 MiB decodați pentru întreaga cerere.

Traducerea către furnizor (elementele canonice nu sunt niciodată redirecționate nemodificate):

- Modelele multimodale Jina: fiecare element de nivel superior devine un obiect cu o singură cheie de modalitate (`text` / `image` / `audio` / `video` / `pdf`), utilizând URI-uri `data:` pentru media încorporată; un vector pentru fiecare element de nivel superior.
- Familia Gemini Embedding 2: o singură matrice de nivel superior devine o singură cerere nativă `models/{model}:embedContent`, cu `content.parts` (`text` sau `inline_data`).
- llama.cpp (`llama-cpp/<model>`, orice model încărcat de serverul local): elementele canonice `text` devin șiruri simple, iar `image` / `audio` / `video` devin fiecare câte un obiect `{"content": [part]}`, utilizând părțile de conținut pentru conversații ale llama-server (`image_url`, `input_audio` cu formatul `wav` / `mp3` / `flac`, `input_video`) cu date încorporate; un vector pentru fiecare element de nivel superior. Serverul trebuie să ruleze cu `--embedding --mmproj …`; fără un proiector, acesta respinge singur media. `document` nu este acceptat.
- Modelele necunoscute/dinamice fără metadate explicite privind modalitățile resping intrarea structurată cu HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Combinațiile de modele/modalități care nu sunt acceptate returnează HTTP 400 în loc să forțeze conversia elementului. Câmpurile de extensie care nu țin de input din cererile legacy cu șiruri/token-uri continuă să fie transmise nemodificate.

```bash
# Listează toate modelele de embedding
GET /v1/embeddings
```

## Generarea imaginilor

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
```

Printre furnizorii disponibili se numără OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local), ComfyUI (local).

`n` returnează `n` imagini în `data[]`. Furnizorii ale căror API-uri upstream returnează câte o imagine per apel
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) efectuează `n` apeluri upstream separate, cu cel mult 4 în execuție simultană. O valoare
fixă pentru `seed` este incrementată cu indexul apelului (`seed`, `seed + 1`, …), astfel încât imaginile să difere, dar să rămână reproductibile. `n` este limitat la 10. Întreaga solicitare eșuează dacă un apel eșuează. Lista formatelor pentru distribuirea apelurilor este `SINGLE_IMAGE_FANOUT_FORMATS` din
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux reutilizează conexiunea existentă bazată pe cheia API și acceptă prefixele `zenmux/` sau `zm/`:

- `zenmux/openai/gpt-image-2` utilizează API-ul OpenAI Images al ZenMux. Opțiunile includ `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` și `response_format`.
- Alți editori, precum `zm/meta/muse-image-1.0`, utilizează endpointul `:predict` Vertex AI al ZenMux. `n` este mapat la `sampleCount`, `aspect_ratio` la `aspectRatio`, iar `image_size`
  (`1K`, `2K`, `4K`) la `sampleImageSize`. O valoare în pixeli pentru `size` furnizează doar un raport de aspect,
  nu dimensiuni garantate în pixeli. Rapoartele acceptate, rezoluțiile și numărul de imagini diferă în funcție de model.
- `zm/inclusionai/ming-image-0.1-design` își alege propriile dimensiuni. Omiteți `size`,
  `aspect_ratio` și `image_size`; valorile explicite returnează HTTP 400. PNG, JPEG și WebP
  pot fi solicitate cu `output_format`.

Această integrare acceptă generarea de imagini din text, nu editarea imaginilor de referință. Rezultatul Vertex
este normalizat la `data[].b64_json`; `response_format: "url"` returnează un URL upstream
HTTPS sau un URL de date base64 atunci când sunt disponibili doar octeții imaginii. Rezultatele goale/filtrate
returnează o eroare, nu un răspuns de succes gol. Accesul la modele depinde de contul ZenMux.
Consultați [API-ul Vertex al ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) și
[API-ul OpenAI Images](https://docs.zenmux.ai/api/openai/generate-an-image).

## OCR pentru documente

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` selectează furnizorul OCR printr-un prefix `provider/model`; un identificator de model simplu (de exemplu,
`mistral-ocr-latest`) este asociat furnizorului înregistrat, iar dacă `model` este omis, se utilizează implicit
Mistral (`mistral-ocr-latest`). Furnizorii înregistrați (`open-sse/config/ocrRegistry.ts`):

| ID furnizor                   | ID model             | Valoarea `model`                                               | Note                                                                                                                     |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (sau simplu `mistral-ocr-latest`) | Sincron — răspunsul este returnat direct din singurul apel upstream.                                                     |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | Upstream asincron (`analyze` + sondare) — consultați mai jos.                                                            |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Sincron, prin endpointul partener `openapi/chat/completions` al Vertex AI — consultați mai jos pentru autentificare/URL. |

Toți cei trei furnizori răspund cu același corp de răspuns în format Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxul de sondare pentru Azure Document Intelligence

API-ul `analyze` al Azure Document Intelligence este asincron: solicitarea inițială returnează un antet
`Operation-Location` în locul unui corp, iar rezultatul trebuie obținut prin sondare. Handlerul
(`open-sse/handlers/ocr.ts`) interoghează URL-ul respectiv la fiecare secundă, pentru cel mult 30 de încercări, eșuează rapid (nu continuă
sondarea) în cazul unui răspuns de sondare care nu este `ok` sau al unei stări `"failed"` și returnează `504` dacă operațiunea este încă în desfășurare după epuizarea bugetului de încercări. Răspunsul final Azure este
normalizat în aceeași structură `pages`/`markdown` utilizată de Mistral înainte de a fi returnat apelantului, astfel încât codul clientului nu trebuie să trateze furnizorul în mod special.

### Autentificarea și rezoluția endpointului pentru Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` reutilizează autentificarea Vertex AI pe care OmniRoute o acceptă deja pentru
traficul de chat/imagini (`open-sse/executors/vertex.ts`): cheia API a conexiunii este fie un
credential JSON pentru un Cont de serviciu (schimbat pentru un token de acces OAuth cu durată scurtă prin fluxul JWT-bearer), fie un token de acces OAuth deja emis, utilizat ca atare. URL-ul endpointului upstream este endpointul partener generic `openapi/chat/completions` al Vertex, construit din proiectul și regiunea conexiunii — un `providerSpecificData.project`/`providerSpecificData.region` explicit are întotdeauna prioritate; în caz contrar, proiectul este derivat din `project_id` al JSON-ului Contului de serviciu, iar regiunea implicită este `us-central1`. Ambele rezoluții au loc în `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), fiind utilizate de
`src/app/api/v1/ocr/route.ts` înainte de trimiterea către `handleOcr`.

## Listă de modele

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Returnează toate modelele de chat, de embedding și de imagini + combinațiile în format OpenAI
```

### Prețurile modelelor (`pricing`)

O intrare conține un obiect `pricing` atunci când OmniRoute cunoaște prețul modelului. Prețul
provine din tabelul de prețuri utilizat pentru contabilizarea costurilor: valori implicite
încorporate, prețuri sincronizate și suprascrieri configurate prin `/api/pricing`. Acestea sunt
prețuri de listă, astfel încât furnizorii de abonamente afișează și un preț per token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Câmpuri                                                         | Unitate                    | Note                                                                                                                                                                   |
| --------------------------------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD per token, șir zecimal | Compatibil cu OpenRouter, niciodată în notație exponențială. Cele două câmpuri pentru cache apar numai atunci când există un preț pentru cache.                        |
| `input`, `output`, `cached`, `cache_creation`                   | USD per 1M tokeni, număr   | Câmpuri din versiunile anterioare ale catalogului, păstrate pentru clienții existenți. `reasoning` și `long_context` apar și atunci când rândul de prețuri le conține. |

- **Combinațiile** folosesc prețul primei ținte vizibile. Combinațiile `auto/*` încorporate aleg o
  țintă în momentul solicitării, astfel încât nu au `pricing`.
- **Modelele gratuite** afișează `"0"` (și `0`) atunci când prețul lor este zero. Un model fără rând
  de prețuri afișează, de asemenea, `"0"` atunci când catalogul îl marchează ca fiind gratuit
  (`free: true`) sau când este inclus în catalogul încorporat de modele gratuite.
- **Preț necunoscut:** intrarea nu are cheia `pricing`.
- **Furnizorii contorizați pe credite** (precum Kiro) facturează per solicitare, nu per token. Intrările
  lor păstrează câmpurile numerice per 1M pe care le aveau anterior și nu conțin câmpuri șir per token.
- **Variantele** (identificatori pentru nivelul de efort al raționamentului, aliasuri fără gândire,
  oglinzi pentru descoperire și gateway) copiază prețul modelului către care direcționează.
- Câmpurile conțin doar tarifele de bază. Nivelurile pentru context extins (câmpul numeric
  `long_context`) și multiplicatorii nivelului de serviciu (de exemplu Codex fast sau flex) nu modifică
  `prompt` sau `completion`.
- Obiectul este același pentru orice stil de autentificare, inclusiv pentru o solicitare în stil
  Anthropic cu `x-api-key` și `anthropic-version` (răspunsul rămâne `{ "object": "list",
"data": [...] }`). Implementare: `src/app/api/v1/models/catalogPricing.ts`.

### Prefixele identificatorilor modelelor (`?prefix=`)

Majoritatea modelelor sunt promovate sub un **prefix al furnizorului**. Prefixul pe care îl primiți
este controlat de indicatorul de funcționalitate `MODELS_CATALOG_PREFIX_MODE` și poate fi înlocuit
**pentru fiecare solicitare** cu un parametru de interogare — util pentru un client care dorește o
listă simplă, fără a modifica setarea valabilă la nivelul întregului server pentru toți ceilalți:

```bash
GET /v1/models?prefix=alias        # un singur identificator per model — prefixul scurt alias
GET /v1/models?prefix=dual         # ambele forme (valoarea implicită a serverului)
GET /v1/models?prefix=canonical    # numai prefixul complet al identificatorului furnizorului
```

| Mod         | Emite                                                    | Note                                                                                                                                                                                                                                          |
| ----------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **și** `claude/claude-sonnet-4-6` | **Implicit.** Ambele identificatoare direcționează către același model; sunt păstrate astfel încât configurațiile clienților care au codificat în mod fix oricare dintre forme să continue să funcționeze. Catalogul este aproximativ dublat. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Câte o intrare per model. Furnizorii fără un alias distinct își emit în continuare intrarea, astfel încât nimic nu se pierde.                                                                                                                 |
| `canonical` | `claude/claude-sonnet-4-6`                               | Câte o intrare per model sub prefixul complet al identificatorului furnizorului. Furnizorii fără un alias distinct (de exemplu `antigravity/…`, `agy/…`) își emit și aici unicul identificator, astfel încât nimic nu se pierde.              |

O oglindă în modul `dual` poate fi recunoscută și fără parametrul de interogare: aceasta conține un
câmp `parent` care indică identificatorul principal.

Clienții care afișează un selector de modele ar trebui să solicite `?prefix=alias` — aceasta este
abordarea utilizată de [extensia OmniCopilot pentru VS Code](../guides/VSCODE-COPILOT.md).

### Filtre de descoperire (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` acceptă filtre de descoperire opționale. Fără niciunul dintre acestea, răspunsul
rămâne neschimbat. Ele restrâng catalogul pe care apelantul îl vede deja (permisiunile cheii API
se aplică mai întâi) și sunt executate înaintea paginării `limit` / `after` în stil OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # toate funcționalitățile listate trebuie să fie true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` al catalogului; rândurile fără unul sunt `chat`
GET /v1/models?q=sonnet&limit=10                           # potrivire fără diferențiere între litere mari și mici pentru id sau nume
```

| Parametru     | Valori                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | întreg nenegativ, comparat cu `context_length`                                                      |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 de caractere                                                                                  |

O valoare necunoscută sau un `min_context` care nu este un întreg nenegativ (de exemplu, `1.5`)
returnează HTTP `400`, iar mesajul enumeră valorile valide. Implementare:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista scurtă de modele (`POST /v1/models/query`)

`POST /v1/models/query` returnează o listă scurtă și deterministă din același catalog, cu aceeași
autentificare și vizibilitate per cheie ca `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Toate câmpurile sunt opționale. `capabilities` și `exclude` acceptă un tablou sau un șir de caractere
separate prin virgule; `max_output` este comparat cu `max_output_tokens`. Rezultatele sunt sortate
după `owned_by`, apoi după `id`. `limit` are valoarea implicită `20`, iar valorile mai mari de `100`
sunt limitate la `100`. JSON-ul nevalid, un câmp necunoscut sau o valoare nevalidă returnează HTTP `400`.

### Modele de chat ascunse individual

Un model marcat **Ascuns** pe pagina furnizorului este exclus din catalog și respins cu
HTTP `404` / `model_not_found` atunci când este solicitat explicit. Verificarea folosește furnizorul
și modelul rezolvate, inclusiv aliasurile furnizorilor, prefixele nodurilor furnizorilor compatibili
și valorile implicite ale conexiunii. O combinație ignoră țintele ascunse și poate utiliza un model
frate vizibil; atunci când nu mai rămâne nicio țintă executabilă, returnează același cod de eroare.
Dezascunderea intră în vigoare la următoarea solicitare. Suprascrierile de vizibilitate doar pentru
imagini nu ascund modelul de chat cu același ID.

Această setare individuală a modelului este separată de
[listele de permitere/respingere pentru expunerea modelelor](../routing/MODEL_EXPOSURE_LIST.md), care
filtrează promovarea în catalog și candidații pentru rutarea automată, păstrând în același timp
trimiterea explicită. Permisiunile modelelor pentru cheile API continuă să se aplice independent.
Modul implicit pentru prefixul catalogului rămâne `dual`.

### Variante de modele fără gândire

Pentru modelele Claude compatibile cu gândirea, `/v1/models` promovează și o variantă
**fără gândire**, al cărei ID are prefixul `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Selectarea acestui ID (de exemplu, într-o configurație Claude Code care atașează întotdeauna
un bloc `thinking`) se rezolvă înapoi la `<provider>/<model>` real, cu raționamentul suprimat —
`thinking:{type:"disabled"}` pe ruta `/v1/messages` sau cu câmpurile `reasoning`/`reasoning_effort`
eliminate pe ruta `/v1/chat/completions`. Varianta este listată numai pentru modelele din familia
Claude care acceptă gândirea **și** respectă `disabled` (astfel, de exemplu, modelele care acceptă
doar modul adaptiv și resping `disabled` sunt excluse). Operatorii pot activa sau dezactiva forțat
varianta pentru fiecare model prin `ModelSpec.noThinkingAlias`.

## Generarea audio ElevenLabs

Configurați o conexiune de furnizor `elevenlabs` în OmniRoute cu cheia API ElevenLabs.
Clienții se autentifică folosind cheia lor **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gateway-ul furnizează cheia de furnizor stocată ca `xi-api-key`. Nu trimiteți niciodată o cheie ElevenLabs
ca token bearer al gateway-ului.

| Metodă | Cale                        | Răspuns                                     | Categorie endpoint cheie API |
| ------ | --------------------------- | ------------------------------------------- | ---------------------------- |
| POST   | `/v1/sound-generation`      | Octeți audio nativi                         | `elevenlabs`                 |
| POST   | `/v1/music`                 | Octeți audio nativi                         | `music`                      |
| POST   | `/v1/music/stream`          | Octeți audio transmiși în flux              | `music`                      |
| POST   | `/v1/music/detailed`        | Audio multipart nativ și plan de compoziție | `music`                      |
| POST   | `/v1/music/detailed/stream` | Metadate SSE native și fragmente audio      | `music`                      |
| POST   | `/v1/music/plan`            | Plan de compoziție JSON                     | `music`                      |

Aceste endpointuri completează rutele existente `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` și `/v1/speech-to-text`. Câmpurile JSON native
și parametrii de interogare precum `output_format` și `enable_logging` sunt păstrați.
Răspunsurile `/v1/music/detailed` își păstrează delimitatorii multipart; analizați-le ca multipart.
`/v1/music/detailed/stream` returnează `text/event-stream` cu metadate de compoziție și
fragmente audio codificate în base64 în evenimente SSE. Toate cele șase rute acceptă preflight CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Un efect sonor scurt. Durata: între 0.5 și 30 de secunde.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Durata muzicii este exprimată în milisecunde: între 3000 și 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilizați `/v1/music/stream` cu același corp JSON pentru livrarea incrementală a audio. Compoziția
acceptă exact una dintre valorile `prompt` sau `composition_plan`; `/v1/music/plan` necesită `prompt`
și acceptă opțional `source_composition_plan`. Schemele native păstrează câmpuri suplimentare
ale furnizorului, astfel încât versiunile planului de compoziție și opțiunile de ajustare fină să ajungă la ElevenLabs.

Endpointul unificat `/v1/music/generations` acceptă, de asemenea, `elevenlabs/music_v1`,
`elevenlabs/music_v2` și `elevenlabs/music_v2_5`. Cu o conexiune ElevenLabs activă,
aceste modele sunt expuse în catalogul muzical. Acest endpoint returnează
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Câmpul său `duration` este exprimat în
secunde și este mapat la `music_length_ms`; o valoare explicită `music_length_ms` are prioritate.
`instrumental` este mapat la `force_instrumental`, câmpul nativ având prioritate.
Utilizați endpointurile native de streaming pentru transmisie în flux și endpointul nativ de compoziție
pentru solicitările bazate exclusiv pe un plan de compoziție.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Restricțiile privind endpointul, modelul, bugetul și conexiunea se aplică înaintea unui apel upstream. Rutele native
returnează codurile de stare și corpurile erorilor upstream neschimbate, inclusiv `402` pentru o restricție de plan
și `429` pentru o limită de cotă. Antetele `character-cost`, `song-id`, `request-id` și `retry-after`
sunt păstrate atunci când sunt prezente. Un sold disponibil de credite gratuite nu garantează accesul la fiecare
model muzical, format de ieșire sau funcție API: ElevenLabs decide drepturile pentru fiecare solicitare.
Endpointul unificat păstrează codurile de stare ale erorilor în plicul de erori normalizat al OmniRoute.

Contracte upstream: [efecte sonore](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[compoziție muzicală](https://elevenlabs.io/docs/api-reference/music/compose) și
[detalii despre muzica transmisă în flux](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Noduri de furnizori pentru rerankare:** `POST /v1/rerank` direcționează de asemenea cererile către noduri de furnizori compatibile cu OpenAI
> (oMLX, vLLM, Infinity, TEI în spatele unui gateway, …), adresate ca `<node-prefix>/<model>`. Nodurile
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) sunt întotdeauna eligibile, la fel ca numele de gazdă pe care
> operatorul le enumeră în `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (de exemplu, un nume de serviciu Docker/Compose precum
> `http://reranker:8080/v1`; acestea sunt apelate direct, niciodată prin `HTTP(S)_PROXY` sau prin proxy-ul
> fixat pentru o conexiune). Nodurile de pe orice altă gazdă — un dispozitiv din LAN sau un partener Tailscale — sunt
> eligibile numai când operatorul activează indicatorul de funcționalitate `RERANK_REMOTE_PROVIDER_NODES` **și** URL-ul de bază al nodului trece politica URL-urilor de ieșire pentru furnizori
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Pasul de rerankare al motorului de memorie apelează această rută prin
> loopback, astfel încât aceeași regulă se aplică pentru `rerankProviderModel` din setările Memory.
>
> **Formatele serverelor locale:** nodul este apelat la `<base>/v1/rerank` și, la 404, la `<base>/rerank`
> (Infinity, TEI). Corpul cererii către upstream conține atât denumirile Cohere/OpenAI (`documents`,
> `return_documents`), cât și denumirile TEI (`texts`, `return_text`), iar răspunsul upstream este
> normalizat la envelope-ul Cohere: lista simplă a TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> de la gateway-uri minimale și `{data: [...]}` în stil Voyage sunt returnate toate clientului ca
> `{results: [{index, relevance_score, document?}]}`, sortate după scor și limitate la `top_n`.

> **Descoperirea nodurilor furnizorilor:** modelele de pe un nod de furnizor compatibil cu OpenAI apar în `GET /v1/models`
> sub prefixul nodului. Rândurile care nu conțin metadate despre endpoint (tipic pentru listările locale `/v1/models`)
> moștenesc `apiType` al nodului, astfel încât modelele unui nod `embeddings` au `type: "embedding"`, iar cele ale unui
> nod `rerank` au `type: "rerank"`, în loc să aibă implicit tipul chat; un `supportedEndpoints` explicit
> pe un rând sincronizat sau adăugat manual are în continuare prioritate.

### `provider_options` pentru Exa și Tavily

Exa și Tavily citesc câmpurile specifice furnizorului dintr-o structură cu namespace:
`provider_options.exa` (sau `provider_options["exa-search"]`) și `provider_options.tavily`
(sau `provider_options["tavily-search"]`). Sunt transmise mai departe doar cheile de mai jos. Fiecare este
verificată în raport cu propria schemă Zod din
`open-sse/handlers/search/providerOptionsPassthrough.ts`, iar o cheie cu tipul greșit este eliminată. Orice altă cheie este ignorată, inclusiv autentificarea, URL-ul de bază,
`stream` și `outputSchema`. Cheile plate utilizate de ceilalți furnizori (`cx`, `depth`, ...) funcționează
ca înainte.

| Furnizor | Câmpuri de nivel superior                                                                                                                                                                                                                                                                                                                                                 | Imbricate                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitive plate), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                              | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` îmbinate peste valoarea implicită `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                  |

Câmpurile generice au întotdeauna prioritate: `query`, `max_results`, `filters` (domenii), `country` și
subiectul derivat din `search_type`. Pentru Exa, `search_type: "news"` păstrează
`category: "news"`. Tavily acceptă și `search_type: "finance"` (`topic: "finance"`).

Costul căutării Firecrawl este înregistrat pentru fiecare bloc început de 10 rezultate returnate, la 0,002 USD (2
credite) per bloc și cel puțin un bloc per apel
([facturarea Firecrawl](https://docs.firecrawl.dev/billing)): 11 rezultate costă 0,004 USD.

Câmpul generic `time_range` ajunge acum la ambii furnizori: Exa primește `startPublishedDate` (marcaj temporal ISO), iar Tavily primește `start_date` (`YYYY-MM-DD`). O dată explicită din `provider_options`
înlocuiește data mapată.

Rezultatele Exa păstrează `id`, `highlights` (fiecare evidențiere, nu doar prima utilizată ca
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` și `extras` în
`provider_raw`. Rezultatele Tavily păstrează `images` și `favicon`.

Costul căutării Linkup este înregistrat la 0,005 USD pentru `depth` `fast` și `standard` și la 0,05 USD pentru
`deep` ([prețurile Linkup](https://docs.linkup.so/pages/documentation/development/pricing)),
indiferent dacă `depth` provine din `provider_options` sau din setările conexiunii.

Exa `type: "lite"` (Exa 3.0) acceptă un set mai restrâns de câmpuri și respinge întreaga solicitare
atunci când este setat orice alt câmp. Pentru lite, `additionalQueries`, `systemPrompt` și fiecare cheie
`contents`, cu excepția `text` și `highlights`, sunt eliminate înainte de apel. Câmpurile depreciate
`subpages`, `subpageTarget`, `highlights.numSentences` și `highlights.highlightsPerUrl` nu mai sunt
transmise.

Exa: 0,007 USD per apel pentru `auto` (și `fast` moștenit) sau 0,004 USD pentru `lite` (și `instant` moștenit), acoperind 10 rezultate; 0,001 USD pentru fiecare rezultat suplimentar; și 0,001 USD per rezultat returnat când `contents.summary` este setat. Tavily este înregistrat la 1 credit (0,008 USD) pentru `search_depth` `basic`, `fast` și `ultra-fast` și 2 credite (0,016 USD) pentru `advanced` ( [credite Tavily API](https://docs.tavily.com/documentation/api-credits) ). Un apel cu `auto_parameters: true` pe care Tavily face upgrade la avansat este încă înregistrat la 1 credit.

## API-ul Web Fetch

Extrage conținutul de la un URL prin intermediul unui furnizor de web-fetch configurat (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, aceeași cheie API ca pentru Parallel Search) returnează doar Markdown — orice alt
`format` produce un `400` — și limitează conținutul la 100.000 de caractere. Atunci când pagina țintă nu poate fi
extrasă, serviciul upstream raportează acest lucru într-un HTTP 200;
OmniRoute îl expune ca `422` cu un mesaj fix.

| Metodă | Cale            | Descriere                                                        |
| ------ | --------------- | ---------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Preia/extrage un URL — corpul este validat de `v1WebFetchSchema` |

**Autentificare:** cheie API Bearer (`extractApiKey` + `isValidApiKey`). Politica este aplicată prin `enforceApiKeyPolicy`.

**Fallback în funcție de cotă (#8297):** atunci când nu este furnizat niciun `provider` explicit, pool-ul
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) este parcurs în ordinea fixă a priorității (fill-first) — un furnizor limitat de rată, dar configurat, este omis
în loc să scurtcircuiteze cererea, iar o eroare upstream reîncercabilă/de cotă (HTTP 429 întotdeauna; 402/403 pentru nivelurile gratuite de tip cotă ale Firecrawl/Tavily/TinyFish —
nu pentru Jina Reader și niciodată pentru o cerere simplă 400 invalidă) trece la următorul furnizor autentificat, încă neîncercat, în momentul cererii. Atunci când fiecare furnizor din pool este epuizat, endpointul returnează un singur `429` (cu un antet `Retry-After`) în locul vechiului `400` generic. Atunci când este solicitat un `provider` explicit, **nu există fallback silențios** — un furnizor explicit limitat de rată sau care eșuează își expune propria eroare (`429` dacă este limitat de rată, altfel statusul upstream).

## Streaming WebSocket

```bash
GET /v1/ws?handshake=1
```

Validează un handshake de upgrade WebSocket și returnează exemplele de mesaje ale protocolului wire (`request`, `cancel`). Cadrele WS propriu-zise sunt gestionate de serverul WS inclus, în afara tabelului de rute Next.js.

**Autentificare:** cheie API Bearer în timpul handshake-ului.

### API-ul Responses prin WebSocket (doar codex)

```bash
# Același host:port ca API-ul HTTP (implicit 20128); faceți upgrade conexiunii:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (sau: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Primul cadru TREBUIE să fie response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Un proxy Responses-API-over-WebSocket este conectat **exclusiv la `codex`** (backendul ChatGPT). Acesta ascultă pe același port ca API-ul/dashboardul, la căile `/v1/responses`,
`/responses` și `/api/v1/responses`. La primul cadru `response.create`, se autentifică + se pregătește prin puntea internă `codex-responses-ws`, selectează o conexiune OAuth codex și face tunel către
`wss://chatgpt.com/backend-api/codex/responses`
prin transportul `wreq-js`. Modelele care nu sunt codex sunt respinse (`codex_ws_provider_required`).
Pentru rutarea prin quota-share, folosiți `model: "qtSd/<group>/codex/<model>"`. Implementat în
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autentificare:** cheie API Bearer în timpul handshake-ului. Serverul HTTP inclus (`server-ws.mjs`)
trebuie să fie punctul de intrare activ (este implicit atunci când există `app/server-ws.mjs`).

#### ID-ul modelului: utilizați ID-ul ChatGPT simplu (fără prefixul `codex/`)

**Codex CLI** de la OpenAI validează numele modelului pe partea clientului atunci când
`supports_websockets = true` și **respinge ID-urile cu prefix de furnizor**, precum
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Trimiteți ID-ul **simplu** (de exemplu `gpt-5.5`). Puntea OmniRoute este exclusiv codex, așadar rezolvă din nou un ID simplu ca model codex
(`resolveCodexWsModelInfo`) înainte de tunelarea upstream — chiar dacă un `gpt-5.5` simplu ar fi rutat altfel către un alt furnizor prin HTTP.

#### Configurarea OpenAI Codex CLI

Direcționați Codex CLI către OmniRoute adăugând un furnizor personalizat cu suport WebSocket în
`~/.codex/config.toml` (utilizați un `CODEX_HOME` separat pentru a evita modificarea unei configurații existente):

```toml
model = "gpt-5.5"                 # id simplu — NU "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # fără slash final; URL-ul WS este derivat (utilizați https/wss în producție)
wire_api = "responses"                    # singura valoare acceptată din februarie 2026
supports_websockets = true                # activează transportul Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # conține cheia API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # o cheie API OmniRoute (orice cheie dacă REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI face upgrade pentru `base_url + /responses` la un WebSocket, iar OmniRoute îl conectează prin tunel la conexiunea OAuth codex selectată. Validat end-to-end împotriva serverului local: ChatGPT returnează `codex.rate_limits` + `response.created` și transmite rezultatul.

### Recuperarea sesiunii pentru cote (opțională)

O solicitare `POST /v1/chat/completions` sau `POST /v1/responses` care nu este transmisă în flux și care eșuează
cu o eroare terminală de cotă (`402`/`429`/`503` al cărei corp indică faptul că limita cotei sau creditele au fost epuizate)
poate fi pusă în așteptare și reluată ulterior în loc să returneze eroarea. Apelantul optează pentru acest comportament
pentru fiecare solicitare, folosind trei antete:

| Antet                        | Valoare                                                |
| ---------------------------- | ------------------------------------------------------ |
| `x-omniroute-quota-recovery` | `auto`                                                 |
| `x-omniroute-session`        | id-ul sesiunii, `[A-Za-z0-9._:-]{1,128}`               |
| `x-omniroute-recovery-turn`  | id-ul rundei, unic în cadrul sesiunii (aceeași regulă) |

Sunt eligibile doar rundele cu `stream: false`, fără instrumente, istoric de instrumente sau `previous_response_id` și fără
un pin `x-omniroute-connection`, iar `STORAGE_ENCRYPTION_KEY` trebuie să fie setat (solicitarea este stocată criptat
timp de cel mult 24 de ore). Răspunsul este apoi `202` cu `recovery.poll`; interogați
`GET /v1/quota-recoveries/{id}` (`202` cât timp este în așteptare, `200` cu corpul recuperat când se finalizează)
sau anulați folosind `DELETE`. Biletele sunt vizibile numai pentru cheia API care le-a creat. O reluare al cărei rezultat
este incert se încheie în `needs_confirmation`, în loc să fie trimisă de două ori. Sursa: `src/lib/quota/quotaSessionRecovery.ts`.

## Utilizarea în regim self-service (`/api/usage/om-usage`)

Orice cheie API poate citi propria utilizare și propriile cote — fără autentificare de administrare. Acesta este endpointul pe care
un client (CLI, panoul OmniCopilot) îl folosește pentru a afișa titularului unei chei cheltuielile sale.

```bash
# Format text (contractul istoric — text simplu pentru un terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Format structurat — cel consumat de o interfață de utilizator
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Cheia trebuie să aibă activată opțiunea **`allowUsageCommand`** (dezactivată implicit — managerul de chei API al
tabloului de bord o comută pentru fiecare cheie). Fără aceasta, endpointul răspunde cu `403`.

`?format=json` returnează o structură discriminată, astfel încât apelantul să nu citească niciodată un câmp de date dintr-un
răspuns de refuz. La succes:

```jsonc
{
  "allowed": true,
  // prezent doar când cheia a optat pentru limite de utilizare per cheie (USD zilnic/săptămânal):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // instantaneul cotei furnizorului selectat sau null când încă nu există nimic în cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // instantaneul fiecărei conexiuni, astfel încât o interfață să poată afișa mai mulți furnizori alături:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

În caz de refuz (`401` cheie nevalidă / `403` nepermis), aceeași rută returnează
`{ "allowed": false, "error": { "message": "…" } }` — un `personal`/`provider` prezent, dar gol
(cheia este permisă, însă nu s-au obținut încă informații) reprezintă o stare diferită de un refuz, iar numai forma JSON
le diferențiază.

**Autentificare:** propria cheie API Bearer a apelantului, validată cu `isValidApiKey` — aceasta _nu_ este suprafața
de administrare (`/api/keys/…`), care rămâne protejată de `requireManagementAuth`.

### Procentele cotelor brute vs. ajustate în funcție de prag

La consumarea `/api/usage/om-usage`, apelanții trebuie să observe diferența dintre procentele prezentate de
**ieșirea în text simplu** și cele din **ieșirea JSON structurată**:

| Aspect                          | Format text simplu (`/api/usage/om-usage` / `@@om-usage`)                                              | Format JSON (`?format=json`)                                                                           |
| :------------------------------ | :----------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| **Câmpul de ieșire**            | `NN% left` (de exemplu, `20% left`)                                                                    | `provider.quotas` / `providers[].quotas`                                                               |
| **Măsurarea**                   | **Alocație utilizabilă ajustată în funcție de prag**: capacitatea rămasă peste pragul de întrerupere   | **Cotă brută din amonte**: măsurătoare a furnizorului fără ajustări                                    |
| **Scalarea în funcție de prag** | Scalată prin `effectiveRemainingPercent()`, astfel încât rezerva protejată să fie afișată ca `0% left` | Niciuna (valorile brute ale instantaneului, conform raportării furnizorului)                           |
| **Date despre prag**            | Integrate în procentul afișat                                                                          | Stocate în `quotaWindowThresholds` pentru fiecare conexiune (sau în valorile implicite ale serverului) |
| **Consumator principal**        | CLI-uri interactive, solicitări de terminal, operatori umani                                           | Integrări programatice, tablouri de bord, analize, sisteme de urmărire a facturării                    |

#### Formula ajustării în funcție de prag

OmniRoute acceptă praguri proactive de întrerupere a cotelor pentru a preveni epuizarea în amonte (configurate prin
`quotaWindowThresholds` ale conexiunii, valorile implicite ale furnizorului sau setările globale de reziliență). Când un prag
de întrerupere (de exemplu, `cutoff = 25%`) este activ într-o fereastră de cotă, redarea textului calculează alocația rămasă astfel:

- Dacă `remaining <= cutoff`: returnează `0%`.
- Dacă `remaining > cutoff`: returns `((remaining - cutoff) / (100 - cutoff)) * 100`.

Ieșirea textului formatat rotunjește această valoare la cel mai apropiat număr întreg (`Math.round(...)`).

#### Exemplu ilustrativ

Considerați o fereastră a furnizorului cu **60% utilizare brută** (prin urmare, **40% cotă brută rămasă**) și un prag configurat de **25% cotă rămasă**:

| Reprezentare                   | Calcul                                             |  Rămas  |               Utilizat implicit                |
| :----------------------------- | :------------------------------------------------- | :-----: | :--------------------------------------------: |
| **JSON brut (`?format=json`)** | Instantaneu din upstream (`quotas[window]`)        | **40%** |                    **60%**                     |
| **Format text (`NN% left`)**   | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (dacă se calculează `100 - remaining`) |

- **De ce textul afișează 20% rămas:** Din cei 40% de cotă fizică rămasă în cont, 25% este rezervată de
  politica de prag. Apelantului îi mai rămân doar 15% din cei 75% de spațiu utilizabil înainte ca routerul
  să oprească rutarea către această conexiune. Scalarea asigură faptul că semnalul de epuizare al conexiunii
  (`0% left`) apare exact în momentul în care rutarea încetează.
- **De ce JSON păstrează valorile brute:** Payload-ul JSON returnează instantaneul exact al furnizorului
  (`UsageSnapshot`), astfel încât instrumentele externe să aibă acces la utilizarea reală din upstream și
  la `quotaWindowThresholds` la nivel de conexiune, fără scalare cu pierderi pe server.

#### Îndrumări pentru migrarea consumatorilor

Dacă o integrare externă (precum un plugin de editor sau o extensie de agent) analiza anterior endpointul text
(`NN% left`) și calcula procentul utilizat ca `100 - NN`, migrarea la `?format=json` înseamnă:

- Citirea valorilor brute JSON va reflecta **consumul real din upstream** (60% utilizat în exemplul de mai sus).
- Dacă integrarea dorește să păstreze semantica alocației utilizabile a endpointului text, poate evalua
  formula pentru procentul efectiv rămas în partea client folosind `quotaWindowThresholds` pentru
  suprascrierile la nivel de conexiune.

## Cache semantic

```bash
# Obțineți statisticile cache-ului
GET /api/cache/stats

# Goliți toate cache-urile
DELETE /api/cache/stats
```

Exemplu de răspuns:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impactul asupra latenței

Un HIT al cache-ului semantic furnizează răspunsul din cache **fără un apel upstream**, astfel încât `X-OmniRoute-Response-Latency` raportată este aproape zero
(indiferent de latența upstream inițială). Clienții sensibili la latență
(benchmarking, monitorizarea p50/p99) ar trebui să verifice antetul de răspuns
`X-OmniRoute-Cache-Latency`:

| Valoare     | Semnificație                                                           |
| ----------- | ---------------------------------------------------------------------- |
| `synthetic` | Răspuns furnizat din cache; latența nu reprezintă timpul upstream real |
| _(absent)_  | Răspuns provenit dintr-un apel upstream real                           |

### Omiterea cache-ului pentru fiecare cheie

Cheile API pot renunța la citirea din cache-ul semantic prin `cacheDefaultMode`:

| Valoare  | Comportament                                                   |
| -------- | -------------------------------------------------------------- |
| `legacy` | Comportament normal al cache-ului (implicit)                   |
| `bypass` | Omite complet căutarea în cache; apelează întotdeauna upstream |

Setați la crearea cheii (`POST /api/keys`) sau la actualizare (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Omiterea cache-ului pentru fiecare cerere

Orice cerere poate omite cache-ul, indiferent de setările cheii:

```
X-OmniRoute-No-Cache: true
```

## Compatibilitate de administrare cu CLIProxyAPI

OmniRoute răspunde la cele trei endpointuri de administrare [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
pe care tablourile de bord de utilizare le apelează pentru a citi limitele abonamentelor Claude și Codex
(de exemplu, sursa de limite de utilizare `cliproxy` din T3 Code). Indicați URL-ul de bază al clientului către
OmniRoute și utilizați o cheie API cu scopul `manage` drept cheie de administrare. Rutele sunt
disponibile la `/v0/management/*` și la `/api/v0/management/*`.

| Metodă | Cale                         | Descriere                                                                                                                                                   |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Conexiunile OAuth Claude și Codex ca `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Fără tokenuri                                  |
| POST   | `/v0/management/api-call`    | Corp `{ auth_index, method, url, header?, data? }`. Trimite o singură cerere permisă cu tokenul contului și returnează `{ status_code, body }`              |
| POST   | `/v0/management/reset-quota` | Corp `{ auth_index }`. Șterge perioada de așteptare a conexiunii, blocările modelelor și perioadele de așteptare Codex pentru fiecare domeniu ale unui cont |

- `auth_index` este ID-ul conexiunii OmniRoute. `provider` este `claude` sau `codex` (numai conexiuni OAuth; furnizorul `anthropic` cu cheie API nu este inclus). Pentru Codex, `id_token.chatgpt_account_id` este ID-ul spațiului de lucru stocat, iar `plan_type` este planul stocat.
- `api-call` nu este un proxy generic. Acceptă numai Claude `GET
https://api.anthropic.com/api/oauth/usage` și Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` și `POST .../wham/rate-limit-reset-credits/consume`, fiecare doar pentru un cont al furnizorului corespunzător. Orice altceva returnează `403` fără a contacta upstreamul. Antetul `Authorization` al apelantului (inclusiv substituentul `$TOKEN$`) este ignorat: OmniRoute inserează tokenul de acces al conexiunii, reîmprospătându-l mai întâi când este aproape de expirare, și redirecționează numai antetele permise (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`). Dacă lipsește `Chatgpt-Account-Id`, se folosește ID-ul spațiului de lucru stocat. Dacă primul răspuns upstream este `401`, se reîmprospătează o dată și se reîncearcă numai când tokenul de acces se schimbă. Fiecare încercare upstream are un timeout de 15 secunde și folosește proxy-ul conexiunii.
- `reset-quota` lasă stările terminale (banned, expired, credits_exhausted) neschimbate. Un `auth_index` necunoscut returnează `404`.

**Autentificare:** sesiunea tabloului de bord sau o cheie API cu scopul `manage`, obligatorie chiar și atunci când autentificarea este dezactivată
(căile se află în `ALWAYS_PROTECTED_API_PATHS`). Cheile destinate exclusiv inferenței primesc `403`. Sursa:
`src/lib/cliproxyCompat/managementApi.ts`.

Pentru modelele sincronizate/importate, `PUT /api/provider-models` acceptă `provider`, `modelId` și
`maxOutputTokenOverride`: un număr întreg pozitiv setează limita manuală a tokenurilor de ieșire, iar `null`

folosește capacitatea de rulare `max_output_tokens` și se păstrează după resincronizarea unui model. Pagina furnizorului
compatibil cu OpenAI oferă aceleași controale de editare/ștergere și marchează modelele cu suport explicit pentru viziune.

Pe un nod de furnizor compatibil, căile de scriere (`POST`, `PUT`, `PATCH`, `DELETE` și
`/api/provider-models/validate-and-add`) stochează identificatorul modelului ca identificator upstream necalificat: un identificator
lipit dintr-o listare cu prefix are orice serie de prefixuri inițiale ale nodului propriu redusă, iar
răspunsurile reflectă identificatorul stocat. Identificatorii cu bare oblice ai furnizorilor canonici (de exemplu, `nvidia/nemotron-…`) sunt
stocați fără modificări. `/v1/models` nu emite niciodată un identificator suprapus de forma `<prefix>/<prefix>/<model>`.

Nodurile Custom Chat Completions adaptează opțiunile explicite de dezactivare a raționamentului la backend-ul din amonte. Un test de conexiune reușit selectează automat controalele pentru șablonul de chat pentru fiecare ID exact de model a cărui intrare din `/models` confirmă o valoare `owned_by` recunoscută: `vllm`, `sglang` sau `llamacpp`. Wrapper-ele transparente compatibile cu OpenAI pot păstra intrarea originală a modelului într-un obiect `openai` imbricat; detectarea urmărește cel mult trei astfel de învelișuri. Modelele cu proprietar absent, necunoscut sau contradictoriu păstrează comportamentul OpenAI obișnuit. Detectarea reutilizează cererea existentă către catalog, nu generează tokenuri de completare și este invalidată atunci când se modifică endpointul conexiunii.

Pentru a fixa comportamentul pentru un backend care nu expune aceste metadate, utilizați API-ul existent de actualizare parțială a furnizorului:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Trimiteți acest corp cu `PUT /api/providers/<connection-id>`. Pentru conexiunea respectivă, un efort explicit de raționament `none` este trimis ca `chat_template_kwargs.thinking=false` și `chat_template_kwargs.enable_thinking=false`. Valorile explicite ale șablonului nativ rămân prioritare, cu excepția cazului în care o regulă de raționament de pe server impune un anumit efort. Setarea se aplică numai atunci când o conexiune personalizată compatibilă cu OpenAI dispune un corp Chat Completions; cererile Responses și furnizorii obișnuiți își păstrează forma nativă a cererii. Setați `reasoningControl` la `openai` pentru a forța transmiterea obișnuită OpenAI a `reasoning_effort` sau omiteți-l/setați-l la `null` pentru a utiliza detectarea automată.

Cererile clasificatorului pentru modul automat Claude Code dezactivează implicit raționamentul nativ atunci când nu conțin controale explicite pentru raționament. Detectarea utilizează marcatorul de sistem al clasificatorului din cererile în format Claude, nu numele modelelor sau limitele de completare. Controalele explicite din corp, antetele acceptate pentru efort/raționament, regulile de rutare și efortul rezolvat al modelului își păstrează prioritatea existentă. Ambele etape ale clasificatorului își păstrează prompturile, limitele de completare, secvențele de oprire și verdicturile reale de permisiune ale upstream-ului; a doua etapă poate produce în continuare raționamentul vizibil solicitat sub formă de text obișnuit.

#### Proveniența limitelor modelelor

`GET /api/models?withLimits=1` (și `true`; `0`/`false` sau omiterea acestuia păstrează neschimbat payloadul implicit) adaugă `contextWindow`, `maxInputTokens`, `maxOutputTokens` și un obiect `capsSource` la fiecare rând de model. `capsSource` indică regula care a furnizat fiecare limită, astfel încât o limită neașteptată (de exemplu, 128k pentru un model de 1M) să poată fi urmărită până la origine. Valorile rezolvate sunt aceleași pe care le utilizează rutarea; marcajul doar adaugă câmpuri și nu modifică niciodată o valoare. Orice altă valoare `withLimits` este respinsă cu `400`.

| Valoarea `capsSource`                        | Origine                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------- |
| `override:context`                           | Suprascriere persistentă a ferestrei de context (`model_context_overrides`)     |
| `override:max_input` / `override:max_output` | Suprascriere persistentă a capacității `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Tabel static autorizat al ferestrei de context                                  |
| `synced:<provider>/<model>`                  | Rând de capacități sincronizat din models.dev                                   |
| `registry:<provider>/<model>`                | Intrare din registrul furnizorului                                              |
| `spec:<model>`                               | Specificație statică a modelului                                                |
| Prefixul `effort-base:`                      | Rând împrumutat de la modelul de bază al unei variante cu sufix de efort        |
| `none`                                       | Nicio sursă nu declară limita (valoarea este `null`)                            |

Implementare: `getResolvedModelCapabilitiesWithLimitSources()` din `src/lib/modelCapabilities.ts` și lanțurile de precedență din `src/lib/modelCapabilityLimits.ts`.

### Versiunea și canalul de lansare

```bash
GET /api/system/version
```

Rută de gestionare disponibilă numai prin loopback (cu autentificare de administrator). Returnează versiunea în execuție, cea mai recentă versiune
publicată și starea actualizării automate. `releaseChannel` și `channels` sunt
câmpuri aditive (rail 3.8.54); `channel` își păstrează semnificația — modul de implementare pe care îl
folosește actualizatorul tabloului de bord (`npm`, `source` sau `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canalul npm al buildului în execuție: `nightly` pentru versiunile `-nightly.*`,
  `next` pentru alte versiuni preliminare (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` pentru o versiune stabilă a unei
  versiuni majore mai vechi decât `channels.latest`, în caz contrar `latest`. Aceleași reguli ca în
  `scripts/release/dist-tag.mjs`, care selectează dist-tag-ul npm la publicare.
- `channels` — versiunea principală publicată pentru fiecare dist-tag, din `npm view omniroute dist-tags` (cu fallback HTTP către registru), memorată în cache cu același TTL de 10 minute ca `latest`. `latest` este întotdeauna prezent (folosește ca fallback câmpul `latest`, apoi `"unavailable"`); `next`, `nightly` și `lts` apar doar atunci când dist-tag-ul respectiv există. O solicitare `Cache-Control: no-cache` reîmprospătează ambele căutări.

Modelul canalelor (`latest` = v3 până la GA-ul 4.0, `next` = rc, `nightly` = builduri `develop`,
`lts` = patch-uri v3 după GA-ul 4.0) este descris în
`docs/ops/RELEASE_STRATEGY.md`.

## Transcriere audio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transcrie fișiere audio folosind orice furnizor STT configurat. Primul segment al
căii selectează furnizorul nativ (`openai/…`, `deepgram/…`). Gateway-urile care
reexportă modelul unui alt furnizor folosesc un identificator calificat
(`openrouter/deepgram/nova-3`).

**Solicitare:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Răspuns:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Exemple de identificatori de modele:** `openai/whisper-1` (necesită o cheie
OpenAI), `openrouter/deepgram/nova-3` (necesită o cheie OpenRouter),
`deepgram/nova-3` (necesită o cheie Deepgram nativă). O solicitare simplă
`deepgram/nova-3` **nu** utilizează OpenRouter.

**Formate acceptate:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** transcrierea în modul fișier prin WebSocket-ul
Gemini Live (necesită o cheie API Gemini). Încărcarea este convertită în PCM mono la 16 kHz cu `ffmpeg`
(`PATH` trebuie să îl includă, cu excepția cazului în care fișierul este deja un WAV PCM mono la 16 kHz),
apoi este transmisă sesiunii, iar textul finalizat este returnat ca `{ "text": "..." }`. Câmpurile de formular
opționale `language` și `prompt` sunt transmise mai departe. Limite: încărcările de peste 25 MiB sau
fișierele audio decodificate cu o durată mai mare de 10 minute returnează
`413`; o conversie care rulează mai mult de 60 s este oprită și returnează `504`. Cheia API este trimisă
doar în antetul `x-goog-api-key`, niciodată în URL-ul WebSocket.

> **Note despre schemă** (`setBudgetSchema`): `apiKeyId` este obligatoriu; cel puțin unul dintre `dailyLimitUsd`, `weeklyLimitUsd` sau `monthlyLimitUsd` trebuie să fie mai mare decât zero. Câmpuri opționale: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Forma moștenită `{keyId, limit, period}` returnează `400 Bad Request`.

## Limite de tokenuri

Bugete de **tokenuri** per cheie API (distincte de bugetul bazat pe USD de mai sus). Sunt aplicate inline pe calea cererii: atunci când utilizarea curentă din fereastra unei chei atinge limita sa, cererile sunt respinse cu `429 Too Many Requests`. Limitele pot fi asociate unui anumit `model`, unui `provider` sau pot fi aplicate `global` la nivelul întregii chei; atunci când mai multe limite corespund unei cereri, se aplică cea mai restrictivă.

```bash
# Listează limitele de tokenuri ale unei chei (include utilizarea în timp real din fereastră)
GET /api/usage/token-limits?apiKeyId=key-123

# Creează sau actualizează o limită de tokenuri
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Șterge o limită de tokenuri după id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Note privind schema** (`setTokenLimitSchema`): `apiKeyId` și `scopeType` (`model` | `provider` | `global`) sunt obligatorii. `scopeValue` este obligatoriu, cu excepția cazului în care `scopeType` este `global` (de exemplu, un id de model pentru domeniul `model`, un id de furnizor pentru domeniul `provider`). `tokenLimit` trebuie să fie un număr întreg pozitiv (convertit din șir). Opționale: `id` (omiteți pentru creare, furnizați pentru actualizare), `resetInterval` (`daily` | `weekly` | `monthly`, valoarea implicită fiind `monthly`), `resetTime` (`HH:MM`), `enabled` (valoarea implicită fiind `true`). Răspunsurile `GET` completează fiecare limită cu `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` și `nextResetAt`. Acesta este un endpoint din clasa de administrare (autentificarea este impusă centralizat de conducta authz).

## Procesarea cererilor

1. Clientul trimite cererea către `/v1/*`
2. Handlerul rutei apelează `handleChat`, `handleEmbedding`, `handleAudioTranscription` sau `handleImageGeneration`
3. Modelul este rezolvat (furnizor/model direct sau alias/combo)
4. Credentialele sunt selectate din baza de date locală, cu filtrarea disponibilității contului
5. Pentru chat: `handleChatCore` verifică memoria cache semantică/de semnătură și rezolvă setările de comprimare pentru combo
6. Comprimarea proactivă rulează înainte de traducerea pentru furnizor, atunci când este activată (`lite`, Caveman, RTK sau în lanț)
7. Executorul furnizorului trimite cererea în amonte
8. Răspunsul este tradus înapoi în formatul clientului (chat) sau returnat ca atare (embeddings/imagini/audio)
9. Sunt înregistrate utilizarea, analizele comprimării și jurnalele cererilor
10. Mecanismul de rezervă se aplică în cazul erorilor, conform regulilor combo

Referința completă a arhitecturii: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Reziliență (extinsă)

OmniRoute expune trei mecanisme independente pentru eșecuri temporare; endpointurile de management de mai jos le permit operatorilor să le citească și să le suprascrie:

| Domeniu                            | Stocarea stării                                 | Citire                                    | Resetare / ștergere                                  |
| ---------------------------------- | ----------------------------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| Întrerupător provider              | `domain_circuit_breakers` + în memorie          | `/api/monitoring/health`                  | `POST /api/resilience/reset`                         |
| Perioadă de așteptare a conexiunii | `rateLimitedUntil` pe conexiunile providerilor  | `/api/rate-limits`, `/api/providers/[id]` | (reactivează leneș; șterge prin PUT-ul providerului) |
| Blocare model                      | Registrul disponibilității modelelor în memorie | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`             |

`PATCH /api/resilience` acceptă suprascrieri pentru întrerupătoarele providerilor în `providerBreaker.oauth` și `providerBreaker.apikey`. Fiecare profil acceptă `degradationThreshold`, `failureThreshold` și `resetTimeoutMs`; aceleași câmpuri sunt expuse în Dashboard → Settings → Resilience.

```bash
# Șterge blocarea unui singur model
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Șterge toate blocările
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Pentru referința conceptuală completă și valorile implicite ale întrerupătoarelor: consultați [`CLAUDE.md`](../../CLAUDE.md) → „Resilience Runtime State” și [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Coada pentru limitarea ratei și plasa de siguranță pentru activarea automată

- **Calea de scriere acceptată**: `POST /api/rate-limits` cu corpul `{"connectionId": "<id>", "enabled": true|false}` este endpointul de management acceptat pentru comutarea protecției la limitarea ratei pentru o conexiune. `PUT /api/providers/[id]` nu modifică și nu comută în mod deliberat `rateLimitProtection` (#11278).
- **Semantica `enabled: false`**: Setarea `enabled: false` elimină protecția explicită pentru conexiune, dar **nu** exclude o conexiune activă cu cheie API din plasa globală de siguranță pentru activarea automată (`autoEnableApiKeyProviders = true`). În `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` și `undefined` sunt echivalente; conexiunile active cu cheie API fără protecție explicită rămân protejate de plasa de siguranță pentru activarea automată.
- **Dezactivare globală**: Pentru a rula conexiuni cu cheie API fără cozi pentru limitarea ratei, dezactivați global plasa de siguranță prin `RATE_LIMIT_AUTO_ENABLE=false` (env) sau `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`).

## Server MCP

OmniRoute include un server încorporat pentru Model Context Protocol, cu 3 transporturi (stdio, SSE, streamable-http) și instrumente cu domeniu de aplicare. Endpointurile tabloului de bord de mai jos citesc date despre stare/audit și intermediază transporturile HTTP.

| Metodă | Cale                   | Descriere                                                                                                                               |
| ------ | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/mcp/status`      | Semnal de activitate, transport, stare online, ultimul apel, instrumente principale, rata de succes în ultimele 24 de ore               |
| GET    | `/api/mcp/tools`       | Lista instrumentelor MCP cu `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints`                                   |
| GET    | `/api/mcp/sse`         | Deschide fluxul SSE pentru transportul SSE (returnează `503` dacă MCP este dezactivat sau transportul nu corespunde)                    |
| POST   | `/api/mcp/sse`         | Trimite cadrul JSON-RPC pe transportul SSE                                                                                              |
| GET    | `/api/mcp/stream`      | Deschide partea SSE a transportului Streamable HTTP (mesaje inițiate de server)                                                         |
| POST   | `/api/mcp/stream`      | Trimite cadrul JSON-RPC pe transportul Streamable HTTP                                                                                  |
| DELETE | `/api/mcp/stream`      | Încheie o sesiune Streamable HTTP                                                                                                       |
| GET    | `/api/mcp/audit`       | Interoghează jurnalul de audit — `?limit=`, `?offset=`, `?tool=`, `?success=true                                \| false`, `?apiKeyId=` |
| GET    | `/api/mcp/audit/stats` | Statistici agregate de audit (totaluri, rata de succes, durata medie, instrumente principale)                                           |

**Autentificare:** transporturile `sse`/`stream` respectă suprafața de autentificare specifică MCP (cheie API Bearer cu domeniul `mcp`); rutele `status`/`tools`/`audit*` pot fi citite din tabloul de bord (fără autentificare suplimentară în afară de accesarea gazdei tabloului de bord).

## Server A2A

OmniRoute expune un endpoint A2A (Agent-to-Agent) JSON-RPC 2.0, precum și un wrapper REST pentru inspecție/utilizare în tabloul de bord.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opțional, cu excepția cazului în care OMNIROUTE_API_KEY este setată
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Metode acceptate (toate condiționate de `settings.a2aEnabled`):

| Method           | Description                                                                 |
| ---------------- | --------------------------------------------------------------------------- |
| `message/send`   | Executarea sincronă a competenței; returnează `{task, artifacts, metadata}` |
| `message/stream` | Executarea în flux SSE a aceluiași set de competențe                        |
| `tasks/get`      | Preia o sarcină după `taskId`                                               |
| `tasks/cancel`   | Anulează o sarcină după `taskId`                                            |

Competențe integrate: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Cardul agentului

```bash
GET /.well-known/agent.json
```

Returnează cardul public al agentului A2A (nume, descriere, capabilități, catalogul competențelor, schema de autentificare) — memorat public în cache timp de 1h. Nu este necesară autentificarea.

### Ajutoare REST

| Method | Path                         | Description                                                                                                             |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A activat + statistici despre sarcini + rezumatul cardului agentului din cache                                        |
| GET    | `/api/a2a/tasks`             | Listează sarcinile — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Nu este implementat ca ajutor REST — creați prin JSON-RPC `message/send`)                                              |
| GET    | `/api/a2a/tasks/[id]`        | Preia o singură sarcină                                                                                                 |
| POST   | `/api/a2a/tasks/[id]/cancel` | Anulează o sarcină                                                                                                      |

**Autentificare:** ajutoarele REST rulează fără autentificare de management (pot fi citite din tabloul de bord); ruta JSON-RPC `/a2a` utilizează Bearer `OMNIROUTE_API_KEY` dacă este configurată.

## Autentificare

Consultați [Autentificarea pentru management](../guides/MANAGEMENT-AUTH.md) pentru cele patru
familii de acreditări (sesiunea tabloului de bord, tokenul CLI local, tokenul de acces `oma_live_…`, cheia API cu domeniul de aplicare manage) și pentru modul în care acestea diferă de cheile de inferență.

- Rutele tabloului de bord (`/dashboard/*`) folosesc cookie-ul `auth_token`
- Autentificarea folosește hash-ul parolei salvate; ca alternativă, `INITIAL_PASSWORD`
- Comutatorul `requireLogin` poate fi configurat prin `/api/settings/require-login`
- Rutele `/v1/*` necesită opțional o cheie API Bearer când `REQUIRE_API_KEY=true`
- „token de management” / „cheie API cu domeniul de aplicare management” în această referință înseamnă una dintre familiile din ghidul respectiv — nu un tip suplimentar nedefinit de secret

> **Modificare incompatibilă (v3.8.0)** — `/api/v1/agents/tasks/*` și endpointurile de management al perioadei de așteptare necesită acum **autentificare pentru management** (cookie-ul `auth_token` al tabloului de bord sau o cheie API cu domeniul de aplicare management). Clienții care apelau anterior aceste rute fără autentificare vor primi `401 Unauthorized`. Consultați commitul `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
