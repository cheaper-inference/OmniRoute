## Tokens 💰 ~ 1,62B/mês em níveis gratuitos de terceiros

</div>

> **Traga as suas próprias contas de fornecedor.** Este é um agregado estimado entre níveis gratuitos de terceiros elegíveis separadamente, e não uma concessão de tokens do OmniRoute. Registe-se, obtenha credenciais quando necessário e ligue os fornecedores que pode utilizar; cada fornecedor controla os seus limites, disponibilidade e termos.
>
> Empilhar níveis gratuitos manualmente é doloroso — dezenas de SDKs, dezenas de limites de taxa e não tenho ideia de quanto realmente tem. Catálogos OmniRoute**466 entradas de nível gratuito em 34 chaves de pool recorrentes** e calcula o título do token a partir do **17 pools com um orçamento mensal positivo publicado mais cinco limites Groq por modelo** , desduplicado pelo pool partilhado. As quotas que só abrem após uma verificação de identidade regional (hoje: ModelScope) são mostradas separadamente, +~ 6 milhões atrás da verificação de identidade regional, e nunca somadas no título. O resultado é visível no painel (`/dashboard/free-tiers`).

<img src="./docs/diagrams/free-tier-budget.svg" width="100%" alt="OmniRoute free-tier budget card: ~1.62B free tokens per month steady, up to ~2.22B in the first month with signup credits, from 34 documented recurring pool keys covering 466 cataloged free-tier entries behind one endpoint. Honest pool-deduped math — each shared pool counted once, including 17 recurring pools with a published positive monthly token budget plus five per-model Groq caps; 12 providers are marked avoid in the terms-risk catalog so you decide. Budget bar includes Mistral 1B, Nara 210M, LLM7 150M, xKiro 150M, Groq 30M (five per-model caps) and smaller pools, plus first-month signup credits and permanently-free no-token-cap providers surfaced separately so they never inflate the headline. Live used/remaining on /dashboard/free-tiers."/>

> Resumo animado da página `/dashboard/free-tiers` ao vivo. Metodologia completa (desduplicação de pool, níveis de crédito, termos do fornecedor):**[docs/reference/FREE_TIERS.md](docs/reference/FREE_TIERS.md)** .
>
> <sub>Estes números são novamente auditados a cada duas semanas em relação ao catálogo ao vivo e **deslocar-se para os dois lados** — um fornecedor termina um nível gratuito e o número desce; um novo pousa e sobe. Publicamos o que o catálogo realmente calcula, nunca um melhor caso arredondado.</sub>

## Instale 🆓, ligue um fornecedor e faça o encaminhamento através de um endpoint

</div>

<img src="./docs/diagrams/works-zero-config.svg" width="100%" alt="Three steps: install and start OmniRoute, connect an eligible provider with your own account or API key, then point your tool at localhost:20128/v1 using an OmniRoute API key and model auto.
```bash
# After connecting a provider, copy your OmniRoute key from Dashboard → Endpoints:
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer YOUR_OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"Hello!"}]}'
```

## 🎯 Combos — A Funcionalidade Principal

</div>

<img src="./docs/diagrams/strategies-grid.svg" width="100%" alt="Exemplos animados de 18 das 20 estratégias de encaminhamento de combos — um mosaico por estratégia: priority, fill-first, weighted, round-robin, p2c, least-used, random, strict-random, cost-optimized, headroom, reset-window, reset-aware, context-relay, context-optimized, lkgp, auto, fusion, pipeline. cache-optimized e quota-weighted não são animadas; a tabela abaixo descreve as 20."/>

> Um **combo** é uma cadeia de modelos entre os quais o OmniRoute encaminha pedidos **automaticamente**. Se a quota se esgotar, um fornecedor falhar ou os custos dispararem, o combo pode avançar para o modelo elegível e operacional seguinte. 🛡️

Não é necessário criar nenhum combo. Defina o seu modelo como `auto` (ou uma variante) e o OmniRoute cria um combo virtual a partir dos fornecedores ligados, avaliados em tempo real:

## 📡 OmniRoute Radar

O valor principal do nível gratuito continua a ser **~1,62 mil milhões de tokens/mês**, com base no catálogo documentado e sem duplicações entre pools apresentado acima. Os créditos temporários de registo dos fornecedores podem aumentar separadamente o total do primeiro mês para **~2,22 mil milhões**. O Radar é uma sobreposição opcional e assinada do catálogo, destinada a quem pretende informações mais atualizadas sobre a disponibilidade de modelos gratuitos entre lançamentos do OmniRoute; o catálogo da comunidade e todas as funcionalidades gratuitas existentes continuam a ser gratuitos.

Os apoiantes podem receber o catálogo em tempo real e oportunidades adicionais de fornecedores. O respetivo limite máximo, separado e variável, é de **aproximadamente 3 mil milhões de tokens/mês, no máximo**, dependendo da disponibilidade dos fornecedores. Este limite máximo não constitui uma garantia: os fornecedores podem alterar as quotas, os critérios de elegibilidade, os modelos ou as regiões a qualquer momento.

O Radar é opcional e utiliza apenas pedidos GET. O cliente OmniRoute não envia prompts, tráfego, configurações de fornecedores, telemetria de utilização nem o estado local relativo à dispensa de anúncios. Saiba mais sobre a elegibilidade e o catálogo atual em **[radar.omniroute.online/planos](https://radar.omniroute.online/planos)**.

## 🔌 CLI completo + A2A e MCP

</div>

> Para além do servidor, o OmniRoute é um **cockpit completo de linha de comandos** com **mais de 80 comandos**, além de protocolos de agentes abertos para que um agente de IA o possa controlar **de forma autónoma**.

### ⌨️ Uma CLI a sério (não apenas `start`)

```bash
omniroute               # inicia o gateway + painel (porta 20128)
omniroute chat          # cliente de chat TUI interativo (atalhos: /model /combo /skill /memory)
omniroute setup         # assistente guiado de primeira execução
omniroute doctor        # diagnostica fornecedores, portas e dependências nativas
```

### 🛰️ Modo remoto — execute a CLI aqui e o OmniRoute num VPS

Tem o OmniRoute num servidor? Controle-o a partir do seu portátil com a **mesma CLI**. Inicie sessão uma vez
com um token de acesso com âmbito definido; a partir daí, todos os comandos têm como destino o servidor remoto.

```bash
omniroute connect 192.168.0.15            # palavra-passe → token com âmbito definido, guardado como contexto
omniroute models                         # ← executado no servidor REMOTO
omniroute configure codex                 # ← escolhe um modelo remoto e cria um perfil Codex local
omniroute tokens create --name ci --scope read   # emite tokens mais restritos para outras máquinas
omniroute contexts use default            # ← volta ao servidor local
```

Os tokens têm os âmbitos `read` / `write` / `admin`; as rotas que iniciam processos continuam limitadas ao loopback.

## 🗜️ Poupe 15–95% de tokens — automaticamente

</div>

### 📖 Como funciona — pipeline, arquitetura e matemática das poupanças

<img src="./docs/diagrams/compression-pipeline.svg" width="100%" alt="Pipeline de compressão do OmniRoute: um pedido de cliente ilustrativo de 10 000 tokens passa por 12 motores combináveis — Session-Dedup, CCR, Lite, RTK, Responses Tool Output, Headroom, Relevance, Caveman, Aggressive, LLMLingua-2, Ultra e OmniGlyph — e pode chegar ao fornecedor com cerca de 1 080 tokens no exemplo empilhado documentado. O conteúdo estruturado é protegido por guardas de preservação e portões de fidelidade por passo; modos explicitamente com perdas ou experimentais podem transformar conteúdo elegível."/>

O combo empilhado predefinido executa `RTK → Caveman`. Quando ambos atuam sobre o mesmo payload de ferramenta/contexto, as poupanças compõem-se:

```txt
combined = 1 − (1 − RTK) × (1 − Caveman_input)
average  = 1 − (1 − 0.80) × (1 − 0.46) = 89.2%
range    = 78.4 – 94.6%
```

Blocos de código, URLs, JSON e dados estruturados estão **sempre protegidos** pelo motor de preservação.

> **Porquê usar muitos tokens quando poucos tokens bastam?** Cada pedido passa pelo pipeline de compressão do OmniRoute de forma **transparente** — sem alterações no cliente. É agora uma **pilha de 12 motores combináveis** que correm em ordem e se misturam e combinam por combo de encaminhamento — com base em ideias de [RTK](https://github.com/rtk-ai/rtk), [Caveman](https://github.com/JuliusBrussee/caveman) (⭐ 90K+), [LLMLingua-2](https://github.com/microsoft/LLMLingua) e [Troglodita](https://github.com/leninejunior/troglodita) (PT-BR).

### 🎚️ Para além dos estilos de saída — dos motores, o mostrador adaptativo e o controlo por pedido

Os 12 motores acima encolhem o que acontece **em** . Mais três camadas de forma **como** ,**quando** , e o que vem **fora** :

- **Estilos de saída 🪄** _(direção do eixo de saída)_ — injeta instruções determinísticas e de modelação de resposta seguras em cache; combináveis, cada um com intensidade `lite` / `full` / `ultra`. Adicionar um estilo é uma entrada de registo de uma linha:
  - **Prosa concisa** Enchimento de gotas — /artigos/cobertura; manter a substância técnica exata.
  - **Menos código** — "desenvolvedor sénior preguiçoso" YAGNI: menor mudança de trabalho, sem andaimes não solicitados.
  - **Rabo de cavalo (desenvolvedor sénior preguiçoso)** — sobe na escada YAGNI, corrige a causa raiz, menor diferença funcional.
  - **Eu tenho ADHD (acção primeiro)** A próxima ação — leva, passos numerados, um próximo passo concreto, sem preâmbulo.
  - **CJK conciso (文言)** Estilo ultraconciso — clássico-chinês (localizado para `zh`).
- **Orçamento de contexto adaptativo 🎯** _(o mostrador)_ — em vez de um limite de token on/off, escale os mecanismos mais baratos e sem perdas apenas na medida do necessário para **ajustar a janela de contexto do modelo** . Política: `reserve-output` (padrão, com reconhecimento do modelo) · `percentage` · `absolute`. Modo: `floor` (ajuste da garantia) · `replace-autotrigger` (a sua escolha explícita ganha) · `off` (limiar legado).
- **🎛️ Onde a compressão é decidida** _(precedência, → baixo elevado)_ Cabeçalho `x-omniroute-compression` — por pedido › substituição de combinação de encaminhamento › perfil nomeado ativo › adaptável/acionamento automático › padrão do painel › desativado. O plano aplicado tem eco no cabeçalho de resposta `X-OmniRoute-Compression: <mode>; source=<source>`.

Acione automaticamente por limite de token, ative o mostrador adaptativo, fixe um perfil nomeado, defina um único por pedido ou atribua um pipeline por combinação de encaminhamento — o que for adequado à carga de trabalho. Uma opção offline **arnês de avaliação** (`npm run eval:compression`) avalia a fidelidade versus economia num corpus fixado antes de promover uma mudança.

> ```

## 📦 Mais métodos de instalação — Docker, código-fonte, pnpm, Arch

**🐳 Docker**

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

`:latest` acompanha a versão SemVer estável **publicada** mais elevada. Não acompanha o `main` do git. Fixe `:X.Y.Z` para GitOps. Consulte [Canais de lançamento do Docker](docs/guides/DOCKER_GUIDE.md#release-channels). A imagem fixa **`OMNIROUTE_MEMORY_MB=1024`**. Isto é suficiente para o painel e conversas ligeiras. Os **agentes de programação** (`POST /v1/responses` do Claude Code, Codex, Grok, …) precisam de uma heap V8 muito maior; caso contrário, o processo apresenta `FATAL ERROR` por volta dos 12 GiB com dois contextos longos sobrepostos. Dimensione o contentor acima da heap (os buffers nativos ficam fora do V8):

| Carga de trabalho                         | Heap (`-e OMNIROUTE_MEMORY_MB`) | Contentor (`--memory`) |
| ----------------------------------------- | ------------------------------- | ---------------------- |
| Painel / conversas ligeiras               | `1024` (predefinição da imagem) | ≥2 g                   |
| Um agente de programação                  | `8192`                          | ≥10 g                  |
| Duas `/v1/responses` longas em simultâneo | `10240`–`12288`                 | ≥12–16 g               |

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

Tabela completa: [Guia do Docker — RAM em tempo de execução](docs/guides/DOCKER_GUIDE.md#runtime-ram-for-coding-agents).

**🥟 Bun**

O `bun install` padrão e a instalação global (`bun install -g omniroute`) são suportados através da deteção do ambiente de execução Bun:

**⚡ Instalação mais rápida / leve (ignorar a compilação nativa)**

O motor SQLite nativo (`better-sqlite3`) é uma dependência **opcional**, pelo que uma instalação
global nunca fica bloqueada a compilar a partir do código-fonte: utiliza um binário pré-compilado quando existe um compatível
com a sua plataforma/Node e, caso contrário, recorre de forma transparente a um motor JavaScript puro
(`node:sqlite` no Node 22+, ou o WASM `sql.js` incluído) — sem necessidade de ferramentas de compilação.

Para ignorar totalmente a **preparação nativa** pós-instalação (CI, sistemas sem interface gráfica ou máquinas lentas).

```bash
OMNIROUTE_SKIP_POSTINSTALL=1 npm install -g omniroute   # CI=1 também o ignora
```

[guia do Termux](docs/guides/TERMUX_GUIDE.md). A CLI e o painel Web são disponibilizados pelo
mesmo processo numa única porta, pelo que atualmente não existe um pacote separado apenas para a CLI.

<table>
  <tr><th align="left">Camada</th><th align="left">Tecnologia</th></tr>
  <tr><td nowrap><b>Runtime</b></td><td>Node.js 22.x / 24.x LTS — <code>&gt;=22.22.2 &lt;23 || &gt;=24.0.0 &lt;27</code></td></tr>
  <tr><td nowrap><b>Linguagem</b></td><td>TypeScript 6.0 — <b>100% TypeScript</b> em <code>src/</code> e <code>open-sse/</code> (zero <code>any</code> no núcleo desde a v2.0)</td></tr>
  <tr><td nowrap><b>Framework</b></td><td>Next.js 16 + React 19 + Tailwind CSS 4</td></tr>
  <tr><td nowrap><b>Base de dados</b></td><td>better-sqlite3 (SQLite, journaling WAL) + LowDB (JSON legado) — 147 módulos de domínio, 229 migrações</td></tr>
  <tr><td nowrap><b>Memória</b></td><td>Pesquisa de texto completo SQLite FTS5 + embeddings vetoriais quantizados em int8, decaimento tipado</td></tr>
  <tr><td nowrap><b>Esquemas</b></td><td>Zod 4 — validação de I/O de ferramentas MCP + contratos de API</td></tr>
  <tr><td nowrap><b>Protocolos</b></td><td>MCP (stdio / HTTP / SSE) + A2A v0.3 (JSON-RPC 2.0 + SSE)</td></tr>
  <tr><td nowrap><b>Streaming</b></td><td>Server-Sent Events (SSE) + ponte WebSocket (<code>/v1/ws</code>)</td></tr>
  <tr><td nowrap><b>Compressão</b></td><td>Pipeline com 12 motores — RTK, Caveman, LLMLingua-2 (MobileBERT ONNX), GCF, OmniGlyph</td></tr>
  <tr><td nowrap><b>Autenticação e segurança</b></td><td>OAuth 2.0 (PKCE) + JWT + chaves de API + autenticação MCP com âmbito · AES-256-GCM em repouso · DOMPurify</td></tr>
  <tr><td nowrap><b>Discrição</b></td><td>wreq-js — personificação de impressões digitais TLS JA3 / JA4, proxy de 3 níveis</td></tr>
  <tr><td nowrap><b>Resiliência</b></td><td>Circuit breaker, recuo exponencial, prevenção de thundering herd, autorrecuperação auto-combo</td></tr>
  <tr><td nowrap><b>Registo</b></td><td>pino — registos JSON estruturados com contexto do pedido</td></tr>
  <tr><td nowrap><b>Testes</b></td><td>Executor de testes do Node.js + Vitest — <b>mais de 60 000 declarações de testes estáticos</b> em mais de 8 400 ficheiros de teste monitorizados (unitários, de integração, E2E, de segurança, do ecossistema)</td></tr>
  <tr><td nowrap><b>Plataformas</b></td><td>Desktop (Electron) · Android (Termux) · PWA (qualquer navegador)</td></tr>
  <tr><td nowrap><b>CI/CD</b></td><td>GitHub Actions — publicação automática no npm + Docker Hub aquando de um lançamento</td></tr>
  <tr><td nowrap><b>Ligações</b></td><td><a href="https://omniroute.online">Site</a> · <a href="https://www.npmjs.com/package/omniroute">npm</a> · <a href="https://hub.docker.com/r/diegosouzapw/omniroute">Docker Hub</a></td></tr>

### Como contribuir

1. Faça um fork do repositório
2. Crie um branch a partir do tip `release/vX.Y.Z` **ativo** (não de `main`) — consulte [Modelo de Branching e Releases](docs/ops/BRANCHING_MODEL.md)
3. Crie o seu branch de funcionalidade (`git checkout -b feat/amazing-feature`)
4. Faça commit das suas alterações (`git commit -m 'feat: add amazing feature'`)
5. Envie para o branch (`git push origin feat/amazing-feature`)
6. Abra um Pull Request com a **base = esse branch `release/vX.Y.Z`**

Consulte [CONTRIBUTING.md](CONTRIBUTING.md) para obter orientações detalhadas.

```bash
# Criar uma release — a publicação no npm acontece automaticamente
```
