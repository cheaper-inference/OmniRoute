## Como funciona

```
CLI Code's / CLI Agents (fluxo de consumo):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (todos apontam para o OmniRoute)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (o OmniRoute encaminha para o fornecedor correto)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (fluxo inverso de inicialização):
    Pedido do cliente → OmniRoute → inicia a CLI através de stdio/ACP → resposta
```

**Vantagens:**

- Uma única chave de API para gerir todas as ferramentas
- Acompanhamento de custos de todas as CLIs no painel
- Mudança de modelo sem reconfigurar cada ferramenta
- Funciona localmente e em servidores remotos (VPS, Docker, Akamai, Cloudflare Tunnel)

## Configuração automática com `setup-*`

Não tem de escrever manualmente a configuração de cada ferramenta. O OmniRoute disponibiliza um comando `setup-*`
por cada CLI suportada, que lê o catálogo de modelos **em tempo real** de uma instância
do OmniRoute em execução (local ou remota) e escreve a configuração da própria ferramenta na sua máquina:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
```

Cada um aceita `--remote <url> --api-key <key>` (para configurar uma ferramenta local com uma
instância remota do OmniRoute), `--dry-run` (para pré-visualizar sem escrever) e `--port`. As ferramentas
sem descoberta automática de modelos (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive) aceitam
`--model <id>` (e `--yes` para execuções não interativas). `setup-5dive` é a única
receita que não escreve em `$HOME`: configura uma frota de agentes 5dive,
escrevendo um perfil de autenticação pertencente ao utilizador root no anfitrião da frota, pelo que volta a executar-se através de `sudo`
e não tem um modo remoto próprio. Para iniciar uma CLI com as
variáveis de ambiente corretas injetadas e sem escrever qualquer configuração, utilize o iniciador genérico
`omniroute run <target>` (claude, codex, aider, goose, opencode, qwen,
gemini — os alvos e aliases provêm de `bin/cli/cli-manifest.mjs`); os iniciadores legados
por ferramenta `omniroute launch` (Claude Code) e `omniroute launch-codex`
(Codex) continuam disponíveis. A Gemini CLI só pode ser iniciada: é um alvo de `omniroute run`,
mas não tem qualquer receita `setup-*`/`configure`.

> **Referência completa:** a tabela principal — o que cada comando escreve, todas as opções,
> modo local vs. remoto e que ferramentas requerem o sufixo `/v1` — encontra-se em
> **[Integrações de CLI](../guides/CLI-INTEGRATIONS.md)**.

### Executar estes comandos dentro de um contentor

Um comando `setup-*` executado dentro do contentor do OmniRoute escreve no diretório pessoal
do próprio contentor, que não é lido por nenhuma CLI do anfitrião e desaparece com o
contentor. O OmniRoute deteta esta situação e termina com o código `2`, apresentando instruções em vez de
escrever. Existem duas formas suportadas de prosseguir — instalar a CLI no anfitrião e utilizar
`omniroute connect` para ligar ao contentor, ou montar os diretórios de configuração através de bind mount e definir
`CLI_CONFIG_HOME` (o perfil `host` do Compose). Todos os comandos `setup-*`, bem como
`omniroute configure` e `omniroute config set`, aceitam
`--allow-container-write` quando o objetivo é efetivamente configurar as próprias CLIs do
contentor; `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` faz o mesmo para
o servidor. Consulte
[Guia do Docker → Configurar ferramentas de CLI do anfitrião](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker).

O **endpoint de aplicação** do painel (`POST /api/cli-tools/apply`) impõe a
mesma proteção: num contentor, uma escrita cujo destino não esteja montado a partir do
anfitrião através de bind mount responde com **`422`**, `containerEphemeralTarget: true`, o texto de erro
seguro e — para as ferramentas com uma receita para o anfitrião (claude, codex, opencode, cline,
kilo, continue) — um `hostSetupCommand` (por exemplo, `omniroute setup-opencode`) para executar
no anfitrião em alternativa; nada é escrito. `dryRun: true` continua a funcionar no modo de
contentor e devolve uma pré-visualização com dados sensíveis ocultados + o caminho de destino sem tocar no disco. O conteúdo da
pré-visualização não é uma configuração com credenciais que deva ser copiada ou importada. Aplique a configuração
no anfitrião com as entradas originais de ferramenta/URL base/chave de API/modelo, ou utilize o comando de
configuração no anfitrião indicado. Consulte [Segurança da configuração de CLI](../security/CLI-CONFIGURATION.md)
para conhecer o cabeçalho de pré-visualização e o contrato do pedido. Este comportamento é
intencional e está protegido contra regressões por
`tests/unit/api/cli-tools/apply-container-guard.test.ts` — nunca «corrija» um erro 422
removendo a proteção.

## Fonte da Verdade

O catálogo unificado encontra-se em `src/shared/constants/cliTools.ts` como `CLI_TOOLS: Record<string, CliCatalogEntry>`.

Cada entrada tem estes campos (definidos em `src/shared/schemas/cliCatalog.ts`):

| Campo                                           | Tipo                                                         | Descrição                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| `category`                                      | `"code" \| "agent"`                                          | Página em que a ferramenta aparece                                          |
| `vendor`                                        | `string`                                                     | Origem da ferramenta ("Anthropic", "OSS (P. Gauthier)")                     |
| `acpSpawnable`                                  | `boolean`                                                    | Também utilizável como Agente ACP (distintivo visível)                      |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | Nível de suporte para endpoints personalizados. `"none"` = pendente de MITM |
| `configType`                                    | `"env" \| "custom" \| "guide" \| "custom-builder" \| "mitm"` | Mecanismo de configuração                                                   |
| `id`, `name`, `color`, `description`, `docsUrl` | padrão                                                       | Campos principais de apresentação                                           |

As entradas com `baseUrlSupport: "none"` **não são apresentadas** nas páginas do painel — estão registadas na lista de pendentes de MITM para o plano 11 (consulte `_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md`).

### Níveis de capacidade (catalogável × detetável × configurável × executável)

Nem todas as ferramentas catalogadas são detetáveis, configuráveis ou executáveis. Cada nível tem uma
única fonte de declaração, e um teste de divergência mantém-nos alinhados:

| Nível            | Significado                                                                          | Declarado em                                                           |
| ---------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **Catalogável**  | Aparece no catálogo do painel (nome, fornecedor, documentação, tipo de configuração) | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                       |
| **Detetável**    | Deteção de binários/configuração, verificações de estado, caminhos de configuração   | `src/shared/services/cliRuntime.ts` (catálogo de execução `CLI_TOOLS`) |
| **Configurável** | Suportado por `omniroute configure <cli>` (existe uma receita de configuração)       | `bin/cli/cli-manifest.mjs` (`configure: true`)                         |
| **Executável**   | Suportado por `omniroute run <target>` (injeção de ambiente/argumentos definida)     | `bin/cli/cli-manifest.mjs` (`run: true`)                               |

`bin/cli/cli-manifest.mjs` é o manifesto executável canónico para as interfaces de comandos
da CLI: `run`, `configure` e os geradores de conclusão da shell obtêm todos dele
as respetivas listas de destinos, a resolução de aliases (por exemplo, `kilocode`/`kilo-code`/`kilo_cli` → `kilo`)
e a configuração do sinalizador `--model`. A proteção contra divergências
`tests/unit/cli/cli-manifest-drift.test.ts` verifica que o manifesto, o catálogo de execução,
o catálogo da IU e todas as interfaces consumidoras permanecem sincronizados — um destino adicionado a
uma interface sem ser adicionado às restantes faz com que a bateria de testes falhe, em vez de divergir silenciosamente.

## 5. API de Deteção em Lote

Toda a deteção de ferramentas é agregada através de um único endpoint:

**`GET /api/cli-tools/all-statuses`**

- Autenticação: `requireCliToolsAuth(request)` (igual às outras rotas `/api/cli-tools/`)
- Devolve: `Record<toolId, ToolBatchStatus>` (tipo: `src/shared/types/cliBatchStatus.ts`)
- Estratégia: `Promise.all` para todas as ferramentas, com um tempo limite de 5 s por ferramenta
- Cache: LRU em memória indexada pelo `mtime` do ficheiro de configuração. A cache é invalidada quando o mtime é alterado. É reinicializada quando o servidor reinicia.

Estrutura da resposta por ferramenta:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // sanitizado, sem rastreios de pilha
}
```

## 10. CLI interno do OmniRoute

O binário `omniroute` fornece comandos para o ciclo de vida do servidor, configuração, diagnóstico e gestão de fornecedores. Ponto de entrada: `bin/omniroute.mjs`.

```bash
omniroute                              # Iniciar o servidor (porta predefinida 20128)
omniroute setup                        # Assistente de configuração interativo
omniroute doctor                       # Verificar configuração, BD, portas e ambiente de execução
omniroute providers list               # Ligações de fornecedores configuradas
omniroute providers test-all           # Testar todas as ligações ativas
omniroute reset-password               # Repor a palavra-passe de administrador
omniroute logs                         # Transmitir registos de pedidos
omniroute health                       # Estado de funcionamento detalhado (disjuntores, cache, memória)
omniroute --version                    # Apresentar a versão
omniroute --help                       # Mostrar todos os comandos
```

### Configuração e inicialização

```bash
omniroute setup                        # Assistente de configuração interativo
omniroute setup --non-interactive      # Modo de CI/automatização (lê variáveis de ambiente + opções)
omniroute setup --password '<value>'   # Definir diretamente a palavra-passe de administrador
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # Adicionar e testar um fornecedor de uma só vez
```

Variáveis de ambiente reconhecidas para a configuração não interativa:

| Variável            | Finalidade                                                                            |
| ------------------- | ------------------------------------------------------------------------------------- |
| `OMNIROUTE_API_KEY` | Chave de API do fornecedor (associada a `--api-key` através de `.env()` do Commander) |
| `DATA_DIR`          | Substituir o diretório de dados do OmniRoute                                          |

Todas as outras entradas não interativas são transmitidas como opções, e não como variáveis de ambiente:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(consulte as opções de `omniroute setup` acima).

### Diagnóstico

```bash
omniroute doctor                       # Verificar configuração, BD, portas, ambiente de execução, memória e disponibilidade
omniroute doctor --json                # JSON legível por máquina
omniroute doctor --no-liveness         # Ignorar a verificação de estado HTTP
omniroute doctor --host 0.0.0.0        # Substituir o anfitrião da verificação de disponibilidade
omniroute doctor --liveness-url <url>  # Substituir o URL completo do endpoint de estado
```

O doctor executa estas verificações: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` e `Server liveness`. Termina com um código diferente de zero se alguma verificação tiver o estado `fail`.

### Gestão de fornecedores

```bash
omniroute providers available                       # Catálogo de fornecedores do OmniRoute
omniroute providers available --search openai       # Filtrar o catálogo por ID/nome/alias/categoria
omniroute providers available --category api-key    # Filtrar por categoria (api-key, oauth, gratuito, ...)
omniroute providers available --json                # JSON legível por máquina

omniroute providers list                            # Ligações de fornecedores configuradas
omniroute providers list --json

omniroute providers test <id|name>                  # Testar uma ligação configurada
omniroute providers test-all                        # Testar todas as ligações ativas
omniroute providers validate                        # Validação estrutural exclusivamente local
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # Fluxo OAuth existente
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` utilizam prioritariamente a API e, por conseguinte, funcionam no
contexto ativo, seja este local ou remoto. A introdução de credenciais deve utilizar
`--credential-stdin` ou `--credential-env`; `--dry-run --json` comunica apenas
a presença/estrutura com os dados ocultados. `providers available` lê o catálogo do OmniRoute;
`providers list/test/test-all/validate` mantêm o respetivo comportamento SQLite local e
não exigem que o servidor esteja em execução.

Para um nó personalizado compatível com OpenAI ou Anthropic, associe as credenciais ao
ID do nó devolvido por `omniroute nodes add`, utilizando `omniroute keys add "$NODE_ID" --stdin`.
Isto requer um servidor em execução e autenticação de gestão para o contexto ativo.
A CLI utiliza `POST /api/providers`, que valida o nó e copia as respetivas definições de endpoint
para a ligação. Um nó em falta, uma falha de autorização ou um servidor indisponível
devolve um erro sem criar uma credencial local alternativa.

`nodes add --base-url` define o endpoint do nó; é distinto do endereço do servidor
em `OMNIROUTE_BASE_URL`. Para ficheiros OpenAPI, utilize
`omniroute openapi dump --format json --out ./openapi.json`; a opção global `--output`
seleciona a formatação de apresentação da CLI, e não um nome de ficheiro de destino.

### Recuperação e reposição

```bash
omniroute reset-password                # Repor a palavra-passe de administrador (também: omniroute-reset-password)
omniroute reset-encrypted-columns       # Mostrar aviso + simulação da reposição de credenciais encriptadas
omniroute reset-encrypted-columns --force  # Anular efetivamente as credenciais encriptadas no SQLite
```

### Exportação de credenciais (⚠ manusear com cuidado)

```bash
omniroute auth export                                 # Mostrar aviso + pedido de confirmação — sem acesso à BD
omniroute auth export --force                          # Exportar para stdout, como JSON, as credenciais DESENCRIPTADAS de TODAS as ligações
omniroute auth export --force --id <id>                 # Exportar apenas a ligação correspondente
omniroute auth export --force --format env               # Emitir linhas OMNIROUTE_<PROVIDER>_<FIELD>=<value>
omniroute auth export --force --out creds.json           # Escrever num ficheiro (criado com permissões 0600)
```

`auth export` é **exclusivamente local** (leitura direta do SQLite, sem rota HTTP) e imprime/escreve
intencionalmente valores **em texto simples** de `apiKey`/`accessToken`/`refreshToken`/`idToken` — isso é uma funcionalidade, não um
erro. Nada é lido da base de dados e nada é desencriptado sem `--force`. É sempre apresentada uma
faixa de aviso em stderr antes de ser emitido qualquer texto simples. Requer que `STORAGE_ENCRYPTION_KEY`
esteja definida. Um campo cuja desencriptação falhe (chave obsoleta, texto cifrado corrompido) é indicado como
`<field>DecryptFailed: true`, em vez de interromper toda a exportação ou expor o erro subjacente.

## Gerir a política de chaves de inferência com a CLI do OmniRoute

Utilize um contexto de gestão autenticado (consulte [Modo remoto](../guides/REMOTE-MODE.md))
para inspecionar ou atualizar uma chave de inferência existente através do respetivo ID:

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted` é um alias de `--model-access-mode all`. A atualização limpa a
lista de modelos permitidos. Preserva âmbitos, regras de ligação, modelos bloqueados, limites de taxa
e limites de custos, pelo que esses outros controlos ainda podem recusar um pedido. Um
`--allowed-models ""` explícito também seleciona `all`; combine-o com
`--model-access-mode restricted` para manter uma chave restrita sem modelos permitidos.
Uma lista não vazia, separada por vírgulas, seleciona `restricted`, salvo indicação explícita em contrário.
Uma combinação contraditória de `all` com uma lista de modelos permitidos não vazia é rejeitada antes do envio de um pedido.

`--rate-limit 30` define os pedidos por minuto e preserva as regras para outras janelas
temporais. `--max-cost 5` ativa o limite diário em USD sem alterar o limite semanal;
`--max-cost 0` remove o limite diário e preserva a opção existente de limite de utilização
e o limite semanal. Os campos de política omitidos permanecem inalterados. As alterações de taxa leem
primeiro a política atual; evite edições simultâneas ao conjunto de limites de taxa da mesma chave.

Os comandos de política utilizam `GET`/`PATCH /api/keys/{id}` autenticados e respeitam o
contexto ativo e a opção global `--api-key`. A saída JSON contém apenas campos de política,
sem a chave armazenada nem a respetiva representação mascarada. Uma credencial apenas de
inferência não pode autorizar alterações de gestão. Uma resposta 401/403 requer a verificação da credencial
e do contexto de gestão; não comprova uma falha do token da CLI ou do salt local.
Consulte [Token da CLI](../security/CLI_TOKEN.md) para conhecer o contrato de autenticação local separado.
