## Conclusões de chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Cabeçalhos personalizados

| Cabeçalho                | Direção  | Descrição                                                                                                                                                                                                                                 |
| ------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Pedido   | Defina como `true` para ignorar a cache                                                                                                                                                                                                   |
| `x-omniroute-no-memory`  | Pedido   | Defina como `true` para ignorar a injeção de memória + competências neste pedido (espelha no-cache; evita a sobrecarga de tokens/custos por chamada)                                                                                      |
| `X-OmniRoute-Progress`   | Pedido   | Defina como `true` para eventos de progresso                                                                                                                                                                                              |
| `X-Session-Id`           | Pedido   | Chave de sessão fixa para afinidade de sessão externa                                                                                                                                                                                     |
| `x_session_id`           | Pedido   | A variante com sublinhado também é aceite (HTTP direto)                                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | Pedido   | Etiqueta de sessão/conversação fornecida pelo chamador (também alimenta a memória). Quando presente, é persistida literalmente em `call_logs.session_tag` para atribuição de custos por sessão (#8249) — nunca sintetizada quando ausente |
| `Idempotency-Key`        | Pedido   | Chave de deduplicação (janela de 5 s)                                                                                                                                                                                                     |
| `X-Request-Id`           | Pedido   | Chave de deduplicação alternativa                                                                                                                                                                                                         |
| `x-omniroute-connection` | Pedido   | Fixa um pedido de modelo único a uma ligação de fornecedor (conta) através do respetivo ID — consulte [Fixação de conta por pedido](#account-pinning-per-request)                                                                         |
| `X-OmniRoute-Cache`      | Resposta | `HIT` ou `MISS` (sem transmissão em fluxo)                                                                                                                                                                                                |
| `X-OmniRoute-Idempotent` | Resposta | `true` se tiver sido deduplicado                                                                                                                                                                                                          |
| `X-OmniRoute-Progress`   | Resposta | `enabled` se o acompanhamento do progresso estiver ativo                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | Resposta | ID de sessão efetivo utilizado pelo OmniRoute                                                                                                                                                                                             |
| `X-OmniRoute-Request-Id` | Resposta | ID de correlação do pedido (quando conhecido)                                                                                                                                                                                             |
| `X-OmniRoute-Version`    | Resposta | Versão da compilação do OmniRoute (sempre presente)                                                                                                                                                                                       |
| `X-OmniRoute-Cost-Saved` | Resposta | Valor em USD que a cache evitou num `HIT` (apenas em acertos da cache)                                                                                                                                                                    |
| `X-OmniRoute-Decision`   | Resposta | Rastro de encaminhamento: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` é a estratégia combinada ou `single` para um pedido não combinado) — sempre presente nas respostas de conclusão                                   |

#### Fixação de conta por pedido

Quando um fornecedor tem várias ligações (contas ou chaves), o OmniRoute normalmente seleciona uma
através da respetiva estratégia de seleção de contas. Em alternativa, um pedido pode fixar uma ligação específica
com o cabeçalho `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Onde encontrar o id.** Abra a página do fornecedor no dashboard
  (**Dashboard → Fornecedores → <provider>**) e clique no identificador `xxxxxxxx…` numa linha de ligação
  — o id completo da ligação é copiado.
- **Quais pedidos o respeitam.** Pedidos de modelo único (`provider/model`) em
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. As combinações ignoram o cabeçalho: fixe
  uma conta por passo da combinação através da ligação própria desse passo.
- **A fixação é estrita, não uma preferência.** A ligação fixada é usada exclusivamente. Uma
  falha dentro do pedido regista o período de espera da conta, mas **não** muda para uma conta
  irmã do mesmo fornecedor.
- **O período de espera e a quota libertam a fixação.** Enquanto a ligação fixada estiver num período
  de espera, com a quota esgotada ou bloqueada por uma política de quotas, os pedidos seguintes
  recorrem às outras ligações do fornecedor, exatamente como o tráfego não fixado.
- **Ids desconhecidos ou desativados falham.** Um id que não esteja no conjunto ativo de ligações do fornecedor (eliminado,
  desativado ou pertencente a outro fornecedor) não deixa nenhuma conta elegível, pelo que o pedido
  falha em vez de ser encaminhado silenciosamente para outro local.

O Claude Code envia cabeçalhos personalizados através de `ANTHROPIC_CUSTOM_HEADERS`. Coloque-o no bloco `env`
de `~/.claude/settings.json`, ou num `.claude/settings.json` ao nível do projeto para fixar uma conta diferente por projeto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Origem: `src/sse/handlers/chat.ts` (leitura do cabeçalho), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (libertação da fixação e verificação de ausência no conjunto).

> **Cabeçalhos de telemetria de custos:** as respostas bem-sucedidas sem streaming também incluem o conjunto de telemetria de custos `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 casas decimais fixas; `0.0000000000` para conteúdo gratuito/sem preço), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (apenas quando > 0), além de `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Estes são emitidos por conclusões de chat, `/v1/responses`, `/v1/messages` **e pelos endpoints de multimédia** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (sempre com custo `0`). O custo de multimédia é calculado por modalidade (por imagem, por segundo, por carácter, por unidade de pesquisa) quando existe informação de preços; caso contrário, é `0` (fail-open).

> **Semântica do custo de acerto da cache:** num HIT da cache semântica (`X-OmniRoute-Cache-Hit: true`) não é feita nenhuma chamada ao serviço upstream, pelo que `X-OmniRoute-Response-Cost` é `0.0000000000` (o custo **incremental** de servir o acerto). O custo original/que teria sido aplicado é comunicado separadamente em `X-OmniRoute-Cost-Saved`. Os consumidores de faturação devem somar `X-OmniRoute-Response-Cost` (os acertos não têm custo); as análises da cache podem agregar `X-OmniRoute-Cost-Saved`.

## Concessões Exclusivas de Sessões Geridas

A concessão exclusiva de sessões geridas é um contrato de encaminhamento opcional e neutro em relação ao cliente: um único proprietário ativo mantém uma ligação OmniRoute elegível. Não concede um modelo, não requer OAuth, não identifica um cliente específico nem requer um fornecedor específico.

A chave de API de autenticação tem de possuir o âmbito `lease:exclusive` e uma lista `allowedConnections` explícita e não vazia. A fronteira de mutação da base de dados impõe ambos os campos em conjunto aquando da criação de chaves e das atualizações parciais.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

As respostas bem-sucedidas de aquisição, renovação e libertação expõem marcas temporais, `state` e o `generation` positivo exato, mas nunca a ligação selecionada nem as credenciais. A renovação e a libertação fornecem o `generation` no corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Um proprietário de concessão ativo pode solicitar explicitamente metadados de apresentação que preservam a privacidade para a sua associação atual:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Esta ação de estado opcional é protegida pelo proprietário opaco, pela chave de API gerida autenticada e pela geração ativa exata numa única transação da base de dados. `displayName` é apenas o nome da ligação configurado e sem espaços no início ou no fim; é `null` quando não existe um nome configurado seguro. O OmniRoute nunca substitui esse valor por um e-mail ou por uma identidade de conta gerada. O valor de `provider` é uma etiqueta de apresentação não sensível e nunca um identificador de fornecedor compatível gerado. São excluídos credenciais, tokens, cookies, IDs de ligações ou de chaves de API em bruto, hashes de proprietários, segredos de proteção e dados internos de encaminhamento.

As consultas com chave errada, proprietário errado, geração obsoleta, inexistente, expirada, libertada ou invalidada devolvem todas o mesmo erro `409 LEASE_FENCE_STALE`, sem metadados da ligação. Um cliente que recebeu a resposta de espera por capacidade não tem nenhuma associação ativa para consultar. Quando o encaminhamento faz a transição de uma concessão ativa, a mesma geração continua válida e o estado devolve atomicamente a nova associação, nunca a antiga. Os clientes existentes permanecem inalterados, porque as respostas de aquisição, renovação, libertação e espera mantêm os formatos anteriores.

Este contrato do servidor não altera o `/status` do OpenAI Codex padrão. Atualmente, o Codex padrão comunica o seu fornecedor de modelos e o estado integrado de autenticação/conta, mas não apresenta metadados arbitrários de contas de fornecedores personalizados; uma integração futura do cliente terá de chamar esta ação e decidir como apresentar `connection.displayName`.

Cada pedido de inferência gerido fornece então ambos os cabeçalhos de controlo:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

O proprietário exato, a geração, a ligação ativa e a chave de API autenticada são protegidos imediatamente antes de cada tentativa suportada a montante. Repetir o proprietário e a geração com outra chave falha, mesmo quando essa chave permite a mesma ligação. Os proprietários em bruto não são persistidos, registados, mantidos no instantâneo do pedido nem encaminhados a montante.

A contenção temporária devolve HTTP `429` com `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Esta resposta significa apenas que o conjunto elegível normal não estava vazio e que todas as candidatas livres estavam ocupadas por uma concessão ativa estrangeira. Modelos/fornecedores não suportados, incompatibilidade de políticas, período de espera, quota, estado de funcionamento e outras falhas normais de elegibilidade mantêm as respostas OmniRoute existentes.

### `x-omniroute-compression`

Substituição por pedido do plano de compressão. Precedência máxima — sobrepõe-se à substituição da combinação de encaminhamento, ao perfil ativo, ao acionamento automático e ao Default do painel. Valores:

| Valor         | Efeito                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Sem compressão para este pedido.                                                                                         |
| `default`     | O perfil Default derivado do painel (ignora o perfil ativo). Os motores com perdas ficam desativados.                    |
| `safe`        | Apenas eliminação de duplicados e agrupamento de espaços em branco.                                                      |
| `allow-lossy` | Mantém o plano do operador para este pedido, incluindo resumos e reescritas de estilo.                                   |
| `engine:<id>` | Um único motor quando ativado, por exemplo, `engine:rtk`. Ativação desse motor por pedido.                               |
| `<combo>`     | Uma combinação nomeada, correspondida primeiro pelo nome (sem distinção entre maiúsculas e minúsculas) e depois pelo ID. |

Notas:

- Os valores desconhecidos são ignorados (o pedido nunca é rejeitado); a resolução prossegue segundo a precedência normal do operador.
- Se várias combinações partilharem um nome, forneça o **id** da combinação para obter uma correspondência determinística.
- Uma combinação cujo nome seja `off` ou `default` não pode ser selecionada pelo nome (essas palavras-chave são interpretadas primeiro); faça referência a essa combinação através do respetivo ID.
- O interruptor mestre da compressão é uma barreira rígida: quando a compressão está globalmente desativada, este cabeçalho não a pode ativar.

O plano aplicado é devolvido no cabeçalho de resposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

em que `<source>` é um de `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ou `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Provedores disponíveis: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Os IDs do catálogo têm o formato `provider/model` (exemplo: `jina-ai/jina-embeddings-v5-omni-small`). Os IDs de modelos Jina simples que aparecem no registo (por exemplo, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) também são resolvidos. Os modelos de incorporação, reordenação, classificação e segmentação da Jina utilizam primeiro as credenciais `jina-ai` do dashboard; `JINA_AI_API_KEY` é utilizado como alternativa apenas quando não existe uma chave no dashboard. O cartão `jina-reader` é apenas Reader / `r.jina.ai` (`POST /v1/web/fetch`) e nunca fornece incorporações ou reordenação.

Os modelos do registo que anunciam suporte multimodal também aceitam até 32 itens estruturados independentes do provedor. Os tipos de itens multimédia são `text`, `image`, `audio`, `video` e `document`. A `source` do suporte multimédia é `{"type":"url","url":"https://..."}` ou
`{"type":"base64","data":"...","media_type":"..."}`.

O Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
e o alias da família `jina-ai/jina-embeddings-v5-omni` → omni-small) também aceita os documentos nativos de EmbeddingsV5Request da Jina e **reencaminha-os intactos** para `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Os valores nativos `{ image | audio | video | pdf }` podem ser um URL HTTPS público, um URI `data:` ou
base64 bruto. O OmniRoute não converte esses objetos em strings nem obtém URLs de imagens nativas — a Jina obtém os conteúdos multimédia públicos por si própria. Os campos Jina adicionais (`task`, `normalized`, `truncate`, `embedding_type`) são reencaminhados. Os SKUs Jina apenas de texto continuam a rejeitar documentos que não sejam de texto.

Limites de segurança e transporte:

- Os URLs multimédia remotos têm de ser HTTPS públicos. Os itens canónicos `{type,source:url}` são obtidos no lado do servidor (revalidação de redirecionamentos, tempo limite, limites de tamanho, DNS público, fixação da ligação) e incorporados antes da chamada ao provedor. Os itens nativos Jina `{image:"https://..."}` são reencaminhados tal como estão após a mesma verificação de HTTPS público; a Jina obtém o URL.
- Os conteúdos multimédia base64 incorporados estão limitados a 8 MiB descodificados por item e 16 MiB descodificados por pedido.

Tradução para os provedores (os itens canónicos nunca são reencaminhados sem alterações):

- Modelos multimodais Jina: cada item de nível superior torna-se um objeto com uma chave correspondente à modalidade
  (`text` / `image` / `audio` / `video` / `pdf`), utilizando URIs de dados para conteúdos multimédia incorporados; um vetor por
  item de nível superior.
- Família Gemini Embedding 2: um único array de nível superior torna-se um único pedido nativo
  `models/{model}:embedContent`, com `content.parts` (`text` ou `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualquer modelo carregado pelo servidor local): os itens canónicos `text`
  tornam-se strings simples, e `image` / `audio` / `video` tornam-se, cada um, um objeto
  `{"content": [part]}`, utilizando as partes de conteúdo de chat do llama-server (`image_url`,
  `input_audio` com o formato `wav` / `mp3` / `flac`, `input_video`) com dados incorporados; um vetor
  por item de nível superior. O servidor tem de ser executado com `--embedding --mmproj …`; sem um projetor, rejeita os conteúdos multimédia por si próprio. `document` não é suportado.
- Os modelos desconhecidos/dinâmicos sem metadados explícitos de modalidade rejeitam a entrada estruturada com HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

As combinações de modelo/modalidade não suportadas devolvem HTTP 400 em vez de converterem o item. Os campos de extensão que não sejam de entrada nos pedidos legados de strings/tokens continuam a ser transmitidos sem alterações.

```bash
# Listar todos os modelos de embeddings
GET /v1/embeddings
```

## Geração de imagem

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Os fornecedores disponíveis incluem OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana,**OpenRouter** ,**ZenMux** , SD WebUI (local), ComfyUI (local).

`n` devolve imagens `n` em `data[]`. Os fornecedores cujo API upstream devolve uma imagem por chamada (Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik, NVIDIA NIM, Cloudflare Workers AI) recebem `n` chamadas upstream separadas, no máximo 4 em curso. Um `seed` fixo é compensado pelo índice de chamada (`seed`, `seed + 1`,…), pelo que as imagens diferem, mas permanecem reproduzíveis. `n` está limitado a 10. O pedido falhará como um todo se alguma chamada falhar. A lista de formatos de distribuição é `SINGLE_IMAGE_FANOUT_FORMATS` em `open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux reutiliza a ligação de chave API existente e aceita prefixos `zenmux/` ou `zm/` :

- `zenmux/openai/gpt-image-2` utiliza imagens ZenMux do OpenAI API. As opções incluem `size`, `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Outros editores, como `zm/meta/muse-image-1.0`, utilizam o endpoint Vertex AI `:predict` do ZenMux. `n` mapeia para `sampleCount`, `aspect_ratio` para `aspectRatio` e `image_size` (`1K`, `2K`, `4K`) para `sampleImageSize`. Um pixel `size` fornece apenas uma relação de aspecto, não dimensões de pixel garantidas. As proporções, resoluções e contagens suportadas variam de acordo com o modelo.
- `zm/inclusionai/ming-image-0.1-design` escolhe as suas próprias dimensões. Omita `size`, `aspect_ratio` e `image_size`; valores explícitos devolvem HTTP 400. PNG, JPEG e WebP podem ser solicitados com `output_format`.

Esta integração suporta a geração de texto para imagem, e não a edição de imagens de referência. A saída do vértice é normalizada a `data[].b64_json`; `response_format: "url"` devolve um HTTPS URL upstream ou um URL de dados base64 quando apenas estão disponíveis bytes de imagem. As saídas Empty/filtered devolvem um erro em vez de um sucesso vazio. O acesso ao modelo depende da conta ZenMux. Veja [o vértice ZenMux do API](https://docs.zenmux.ai/api/vertexai/generate-images) e as [imagens OpenAI API](https://docs.zenmux.ai/api/openai/generate-an-image).

Uma ligação de login Microsoft 365 Copilot serve `copilot-m365-web/m365-copilot-image` através da ferramenta de imagem integrada do Copilot: uma volta Copilot por imagem (`n` 1–4), `size` direccionando apenas a orientação e imagens devolvidas em linha (`b64_json`, ou um URL de dados para `response_format: "url"`). Consulte [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# List all image models
GET /v1/images/generations
```

## OCR de documentos

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleciona o fornecedor de OCR através de um prefixo `provider/model`; um ID de modelo simples (por exemplo,
`mistral-ocr-latest`) é associado ao seu fornecedor registado e, quando `model` não é especificado, é utilizado por predefinição
o Mistral (`mistral-ocr-latest`). Fornecedores registados (`open-sse/config/ocrRegistry.ts`):

| ID do fornecedor              | ID do modelo         | Valor de `model`                                       | Notas                                                                                                                                           |
| ----------------------------- | -------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (ou `mistral-ocr-latest`) | Síncrono — a resposta é devolvida diretamente pela única chamada upstream.                                                                      |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`            | Upstream assíncrono (`analyze` + consulta) — consulte abaixo.                                                                                   |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                | Síncrono, através do endpoint parceiro `openapi/chat/completions` do Vertex AI — consulte abaixo para obter informações sobre autenticação/URL. |

Os três fornecedores respondem com o mesmo corpo no formato Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxo de consulta do Azure Document Intelligence

A API `analyze` do Azure Document Intelligence é assíncrona: o pedido inicial devolve um cabeçalho
`Operation-Location` em vez de um corpo, e é necessário consultar o resultado. O processador
(`open-sse/handlers/ocr.ts`) consulta esse URL a cada segundo durante um máximo de 30 tentativas, falha imediatamente (não
continua a consultar) perante uma resposta de consulta que não seja `ok` ou um estado `"failed"` e devolve `504` se a
operação ainda estiver em execução depois de esgotado o número de tentativas. A resposta final do Azure é
normalizada para a mesma estrutura `pages`/`markdown` utilizada pelo Mistral antes de ser devolvida ao
chamador, pelo que o código cliente não precisa de tratar o fornecedor de forma especial.

### Autenticação e resolução do endpoint do OCR DeepSeek do Vertex AI

`vertex-deepseek-ocr` reutiliza a mesma autenticação do Vertex AI que o OmniRoute já suporta para
tráfego de chat/imagens (`open-sse/executors/vertex.ts`): a chave de API da ligação é uma credencial JSON de uma
Conta de Serviço (trocada por um token de acesso OAuth de curta duração através do fluxo JWT-bearer)
ou um token de acesso OAuth já emitido, utilizado tal como está. O URL do endpoint upstream é o endpoint parceiro
genérico `openapi/chat/completions` do Vertex, construído a partir do projeto e da região da ligação — um
`providerSpecificData.project`/`providerSpecificData.region` explícito tem sempre precedência; caso contrário, o projeto
é obtido do `project_id` do JSON da Conta de Serviço e a região assume `us-central1`. Ambas as resoluções ocorrem em `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e são utilizadas por
`src/app/api/v1/ocr/route.ts` antes de o pedido ser encaminhado para `handleOcr`.

## Listar modelos

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Devolve todos os modelos de chat, incorporação e imagem + combinações no formato OpenAI
```

### Preços dos modelos (`pricing`)

Uma entrada inclui um objeto `pricing` quando o OmniRoute conhece o preço do modelo. O preço
provém da tabela de preços utilizada pela contabilização de custos: predefinições incorporadas, preços
sincronizados e substituições definidas através de `/api/pricing`. Estes são preços de tabela, pelo
que os fornecedores de subscrição também apresentam um preço por token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Campos                                                          | Unidade                       | Notas                                                                                                                                                         |
| --------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD por token, cadeia decimal | Compatível com o OpenRouter, nunca em notação exponencial. Os dois campos de cache aparecem apenas quando existe um preço de cache.                           |
| `input`, `output`, `cached`, `cache_creation`                   | USD por 1M de tokens, número  | Campos de versões anteriores do catálogo, mantidos para clientes existentes. `reasoning` e `long_context` também aparecem quando a linha de preços os inclui. |

- As **combinações** têm o preço do seu primeiro destino visível. As combinações `auto/*`
  incorporadas escolhem um destino no momento do pedido, pelo que não têm `pricing`.
- Os **modelos gratuitos** apresentam `"0"` (e `0`) quando o seu preço é zero. Um modelo sem
  uma linha de preços também apresenta `"0"` quando o catálogo o marca como gratuito (`free: true`)
  ou quando o catálogo incorporado de modelos gratuitos o inclui.
- **Preço desconhecido:** a entrada não tem a chave `pricing`.
- Os **fornecedores cujo custo é medido por créditos** (como o Kiro) cobram por pedido em vez de
  por token. As suas entradas mantêm os campos numéricos por 1M que tinham anteriormente e não
  incluem campos de cadeia por token.
- As **variantes** (ids de esforço de raciocínio, aliases sem pensamento, espelhos de descoberta
  e de gateway) copiam o preço do modelo para o qual encaminham.
- Os campos incluem apenas as tarifas base. Os escalões de contexto longo (o campo numérico
  `long_context`) e os multiplicadores de nível de serviço (por exemplo, Codex fast ou flex) não
  alteram `prompt` ou `completion`.
- O objeto é o mesmo para todos os estilos de autenticação, incluindo um pedido ao estilo
  Anthropic com `x-api-key` e `anthropic-version` (a resposta permanece `{ "object": "list",
"data": [...] }`). Implementação: `src/app/api/v1/models/catalogPricing.ts`.

### Prefixos dos ids dos modelos (`?prefix=`)

A maioria dos modelos é anunciada com um **prefixo de fornecedor**. O prefixo que obtém é controlado
pela flag de funcionalidade `MODELS_CATALOG_PREFIX_MODE` e pode ser substituído **por pedido**
através de um parâmetro de consulta — útil para um cliente que pretenda uma lista limpa sem alterar a
definição global do servidor para todos os outros:

```bash
GET /v1/models?prefix=alias        # um id por modelo — o prefixo de alias curto
GET /v1/models?prefix=dual         # ambas as formas (predefinição do servidor)
GET /v1/models?prefix=canonical    # apenas o prefixo completo do id do fornecedor
```

| Modo        | Emite                                                   | Notas                                                                                                                                                                                                            |
| ----------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **e** `claude/claude-sonnet-4-6` | **Predefinição.** Ambos os ids encaminham para o mesmo modelo; mantidos para que as configurações de clientes que tenham uma destas formas codificada continuem a funcionar. Duplica aproximadamente o catálogo. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Uma entrada por modelo. Os fornecedores sem um alias distinto também emitem a sua entrada, pelo que nada se perde.                                                                                               |
| `canonical` | `claude/claude-sonnet-4-6`                              | Uma entrada por modelo com o prefixo completo do id do fornecedor. Os fornecedores sem um alias distinto (por exemplo, `antigravity/…`, `agy/…`) também emitem aqui o seu único id, pelo que nada se perde.      |

Um espelho no modo `dual` também pode ser reconhecido sem o parâmetro de consulta: inclui um campo
`parent` que aponta para o id principal.

Os clientes que apresentam um seletor de modelos devem solicitar `?prefix=alias` — é isso que a
[extensão OmniCopilot para VS Code](../guides/VSCODE-COPILOT.md) faz.

### Filtros de descoberta (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` aceita filtros de descoberta opcionais. Sem nenhum deles, a resposta não é
alterada. Estes filtros restringem o catálogo que o autor da chamada já consegue ver (as permissões
da chave da API são aplicadas primeiro) e são executados antes da paginação `limit` / `after` ao
estilo OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # todas as capacidades indicadas têm de ser verdadeiras
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` do catálogo; as linhas sem um são `chat`
GET /v1/models?q=sonnet&limit=10                           # correspondência sem distinção entre maiúsculas e minúsculas no id ou nome
```

| Parâmetro     | Valores                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | inteiro não negativo, comparado com `context_length`                                                |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caracteres                                                                                    |

Um valor desconhecido ou um `min_context` que não seja um inteiro não negativo (por exemplo, `1.5`) devolve HTTP `400` e a mensagem apresenta os valores válidos. Implementação:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista curta de modelos (`POST /v1/models/query`)

`POST /v1/models/query` devolve uma lista curta e determinística do mesmo catálogo, com a mesma
autenticação e visibilidade por chave que `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Todos os campos são opcionais. `capabilities` e `exclude` aceitam um array ou uma cadeia de caracteres
separada por vírgulas; `max_output` é comparado com `max_output_tokens`. Os resultados são ordenados por
`owned_by` e, em seguida, por `id`. `limit` assume o valor predefinido `20` e os valores superiores a
`100` são limitados a `100`. JSON inválido, um campo desconhecido ou um valor inválido devolve HTTP `400`.

### Modelos de chat ocultos individualmente

Um modelo marcado como **Oculto** na página do respetivo fornecedor é excluído do catálogo e rejeitado
com HTTP `404` / `model_not_found` quando solicitado explicitamente. A verificação utiliza o fornecedor e o
modelo resolvidos, incluindo aliases de fornecedores, prefixos de nós de fornecedores compatíveis e
predefinições de ligação. Uma combinação ignora destinos ocultos e pode utilizar um irmão visível; quando
não resta nenhum destino executável, devolve o mesmo código de erro. A remoção da ocultação tem efeito no
pedido seguinte. As substituições de visibilidade exclusivas para imagens não ocultam o modelo de chat
com o mesmo ID.

Esta definição de modelo individual é separada das
[listas de permissão/negação de exposição de modelos](../routing/MODEL_EXPOSURE_LIST.md), que filtram
a divulgação no catálogo e os candidatos ao encaminhamento automático, mantendo o despacho explícito.
As permissões de modelos da chave de API continuam a ser aplicadas de forma independente. O modo de
prefixo predefinido do catálogo permanece `dual`.

### Variantes de modelos sem thinking

Para modelos Claude compatíveis com thinking, `/v1/models` também anuncia uma variante **sem thinking** cujo
id tem o prefixo `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

A seleção deste id (por exemplo, numa configuração do Claude Code que anexa sempre um bloco `thinking`)
resolve novamente para o `<provider>/<model>` real com o raciocínio suprimido — `thinking:{type:"disabled"}`
no caminho `/v1/messages`, ou com os campos `reasoning`/`reasoning_effort` removidos no caminho
`/v1/chat/completions`. A variante só é listada para modelos da família Claude que suportam thinking
**e** respeitam `disabled` (por isso, por exemplo, os modelos apenas adaptativos que rejeitam `disabled`
são excluídos). Os operadores podem forçar a ativação ou desativação da variante por modelo através de
`ModelSpec.noThinkingAlias`.

## Geração de áudio com ElevenLabs

Configure uma ligação de fornecedor `elevenlabs` no OmniRoute com a sua chave de API do ElevenLabs.
Os clientes autenticam-se com a sua chave do **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
o gateway fornece a chave de fornecedor armazenada como `xi-api-key`. Nunca envie uma chave do ElevenLabs
como token bearer do gateway.

| Método | Caminho                     | Resposta                                     | Categoria do endpoint da chave de API |
| ------ | --------------------------- | -------------------------------------------- | ------------------------------------- |
| POST   | `/v1/sound-generation`      | Bytes de áudio nativos                       | `elevenlabs`                          |
| POST   | `/v1/music`                 | Bytes de áudio nativos                       | `music`                               |
| POST   | `/v1/music/stream`          | Bytes de áudio em streaming                  | `music`                               |
| POST   | `/v1/music/detailed`        | Áudio multipart nativo e plano de composição | `music`                               |
| POST   | `/v1/music/detailed/stream` | Metadados SSE nativos e blocos de áudio      | `music`                               |
| POST   | `/v1/music/plan`            | Plano de composição JSON                     | `music`                               |

Estes endpoints complementam as rotas existentes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` e `/v1/speech-to-text`. Os campos JSON nativos
e os parâmetros de consulta, como `output_format` e `enable_logging`, são preservados.
As respostas de `/v1/music/detailed` mantêm os seus limites multipart; analise-as como multipart.
`/v1/music/detailed/stream` devolve `text/event-stream` com metadados de composição e blocos de áudio
codificados em base64 nos eventos SSE. Todas as seis rotas suportam preflight CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Um efeito sonoro curto. Duração: 0,5 a 30 segundos.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# A duração da música é expressa em milissegundos: 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilize `/v1/music/stream` com o mesmo corpo JSON para obter a entrega incremental de áudio. A composição
aceita exatamente um de `prompt` ou `composition_plan`; `/v1/music/plan` requer `prompt`
e aceita opcionalmente `source_composition_plan`. Os esquemas nativos preservam campos adicionais
do fornecedor, para que as versões dos planos de composição e as opções de ajuste fino cheguem ao ElevenLabs.

O endpoint unificado `/v1/music/generations` também aceita `elevenlabs/music_v1`,
`elevenlabs/music_v2` e `elevenlabs/music_v2_5`. Com uma ligação ElevenLabs ativa,
estes modelos são disponibilizados pelo catálogo de música. Este endpoint devolve
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. O seu campo `duration` é expresso em
segundos e é associado a `music_length_ms`; um `music_length_ms` explícito tem precedência.
`instrumental` é associado a `force_instrumental`, sendo o campo nativo prioritário.
Utilize os endpoints nativos de streaming para streaming e o endpoint de composição nativo
para pedidos orientados exclusivamente por um plano de composição.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

As restrições de endpoint, modelo, orçamento e ligação são aplicadas antes de uma chamada upstream. As rotas nativas
devolvem os códigos de estado e os corpos de erro upstream inalterados, incluindo `402` para uma restrição
do plano e `429` para um limite de quota. Os cabeçalhos `character-cost`, `song-id`, `request-id` e `retry-after`
são preservados quando presentes. Um saldo de créditos gratuito não garante acesso a todos os
modelos de música, formatos de saída ou funcionalidades da API: o ElevenLabs determina a elegibilidade para cada pedido.
O endpoint unificado preserva os códigos de estado de erro no envelope de erro normalizado do OmniRoute.

Contratos upstream: [efeitos sonoros](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composição musical](https://elevenlabs.io/docs/api-reference/music/compose) e
[detalhes de música em streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Nós de fornecedor de rerank:** `POST /v1/rerank` também encaminha pedidos para nós de fornecedores compatíveis com OpenAI
> (oMLX, vLLM, Infinity, TEI através de um gateway, …) endereçados como `<node-prefix>/<model>`. Os nós de loopback
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) são sempre elegíveis, tal como os nomes de anfitrião que o
> operador especificar em `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (por exemplo, um nome de serviço Docker/Compose, como
> `http://reranker:8080/v1`; estes são contactados diretamente, nunca através de `HTTP(S)_PROXY` ou do proxy fixado
> numa ligação). Os nós em qualquer outro anfitrião — uma máquina na LAN ou um par Tailscale — só são elegíveis quando o operador ativa a
> flag de funcionalidade `RERANK_REMOTE_PROVIDER_NODES` **e** o URL base do nó cumpre a política de URLs de saída do fornecedor
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> O passo de rerank do motor de memória chama esta rota através de loopback, pelo que a mesma regra rege
> `rerankProviderModel` nas definições de Memória.
>
> **Formatos de servidores locais:** o nó é chamado em `<base>/v1/rerank` e, em caso de 404, em `<base>/rerank`
> (Infinity, TEI). O corpo enviado a montante contém ambas as convenções do Cohere/OpenAI (`documents`,
> `return_documents`) e a convenção do TEI (`texts`, `return_text`), e a resposta a montante é
> normalizada para o envelope do Cohere: o `[{index, score, text}]` simples do TEI, `{results: [{index, score}]}`
> de gateways simples e `{data: [...]}` ao estilo do Voyage são todos devolvidos ao cliente como
> `{results: [{index, relevance_score, document?}]}`, ordenados por pontuação e limitados a `top_n`.

> **Descoberta de nós de fornecedores:** os modelos num nó de fornecedor compatível com OpenAI aparecem em `GET /v1/models`
> sob o prefixo do nó. As linhas que não contêm metadados de endpoint (típico das listagens locais de `/v1/models`)
> herdam o `apiType` do nó, pelo que os modelos de um nó `embeddings` têm `type: "embedding"` e os
> modelos de um nó `rerank` têm `type: "rerank"`, em vez de assumirem por predefinição o tipo chat; um
> `supportedEndpoints` explícito numa linha sincronizada ou adicionada manualmente continua a ter precedência.

### Combinações search/fetch nomeadas

Tanto `POST /v1/search` como `POST /v1/web/fetch` aceitam `model` como nome de combinação guardado. Utilize `model` ou um `provider` explícito; enviar ambos retorna `400`. Sem nenhum dos campos, a seleção automática existente do fornecedor permanece inalterada.

Tanto o Combo Builder como o seu catálogo Add Model expõem entradas nativas de operação web aos fornecedores ligados, mesmo quando estes não possuem uma lista de modelos LLM. Serper mostra** Pesquisa na Web** ; Tavily mostra** Pesquisa na Web/extração de páginas** e os fornecedores apenas de busca mostram** Extração de página** . Escolha a entrada e a conta normalmente. Uma única entrada Tavily serve ambos os endpoints da web; estas entradas de operação não são adicionadas aos seletores de cliente apenas de chat ou aos testes de modelo de chat.

Por exemplo, crie um** prioridade** combo denominado `shared-free` com estes alvos ordenados:

1. `openai/gpt-4o`
2. `tavily-search/web`
3. `serper-search/web`
4. `jina-reader/fetch`

De seguida, utilize o mesmo nome em cada superfície:

```json
{ "model": "shared-free", "query": "Open source speech recognition", "max_results": 5 }
```

```json
{ "model": "shared-free", "url": "https://example.com", "format": "markdown" }
```

A pesquisa considera Tavily e depois Serper; procurar considera Tavily e depois Jina Reader; chat ignora os fornecedores search/fetch dedicados e considera OpenAI. A compatibilidade vem dos registos do executor search/fetch, e não das palavras no nome do modelo. A filtragem precede a seleção e envio de credenciais e nunca edita o combo guardado.

As rotas sem capacidade de chat suportam `priority`, `fill-first`, `round-robin`, `weighted`, `random`, `strict-random`, `least-used` e `p2c`. As estratégias de síntese apenas de chat, como `fusion`, `pipeline` e `context-relay` são rejeitadas em rotas que não sejam de chat, em vez de serem aplicadas silenciosamente à pesquisa ou aos media gerados. O mecanismo de combinação existente lida com o fallback ordenado, incluindo falhas de quota upstream, e mantém o passo IDs, os pinos de conta, as listas de permissões de conta por passo, as referências aninhadas, os escopos connection/quota do chamador e a política de acesso combinado. Os resultados mantêm o seu esquema search/fetch nativo, incluindo o fornecedor real; `X-OmniRoute-Combo-Trace` identifica a decisão de encaminhamento. Combos desconhecidos retornam `404`; combos e combinações inativas sem alvos compatíveis retornam `400`.

Cada tentativa de combinação utiliza um fornecedor explícito. Não pode invocar o pool de fornecedores automático nativo nas costas do combo. Os pedidos de fornecedor explícito mantêm o comportamento existente de fornecedor único. Os pedidos de chat direto direcionados a fornecedores search/fetch dedicados devolvem um JSON `400` acionável em vez de passar para um executor estilo OpenAI.

### Rotas combinadas específicas de capacidade

Os combos guardados podem conter um objeto `routes` cujas chaves são capacidades API. Cada rota tem a sua lista de alvos, estratégia e configuração de tempo de execução. Os `models`, `strategy` e `config` de nível superior continuam a ser o plano de chat compatível com o legado; os combos antigos sem `routes` continuam a funcionar inalterados.

As chaves de rota suportadas são `chat`, `search`, `web-fetch`, `embeddings`, `rerank`, `images`, `image-edits`, `videos`, `music`, `ocr`, `audio-speech`, `audio-transcriptions`, `audio-translations` e `audio-generation`. A projeção do endpoint acontece antes da seleção, pontuação ou envio da credencial. As referências de combinação aninhadas selecionam a rota do combo filho para o mesmo recurso.

`POST /v1/music/generations` e `POST /v1/ocr` aceitam um nome de combinação em `model`. O `POST /v1/music` nativo compatível com ElevenLabs também aceita um nome de combinação em `model_id`, mas cada destino utilizável nesse endpoint nativo deve ser um modelo de música ElevenLabs para que o seu contrato de resposta binária seja preservado. `POST /v1/sound-generation` aceita um combo `audio-generation` em `model_id` sob a mesma restrição binária nativa. Utilize `/v1/music/generations` para fornecedores de música heterogéneos.

**Seleção automática:** sem `provider`, o fornecedor mais barato com uma ligação configurada é executado em primeiro lugar e o próximo mais barato é o failover. Os fornecedores de último recurso gratuitos (`duckduckgo-free`) são utilizados apenas quando nada mais está configurado. Um SearXNG auto-hospedado conta como configurado quando a sua ligação armazena um `baseUrl` real (não o padrão do catálogo `http://localhost:8888/search`): é então classificado como um fornecedor $0 à frente dos com chave, com o fornecedor com chave mais barato como failover, incluindo quando SearXNG responde 400, 401, 403 ou 404. Um `baseUrl` que não é um `http(s)` URL válido ou que aponta para um endereço de metadados de nuvem não conta. Uma ligação SearXNG que armazena um token é classificada desta forma apenas em `https://` ou loopback `http://`. No `http://` simples remoto, nunca é um failover e permanece como último recurso, utilizado apenas quando nenhum outro fornecedor está configurado ou quando solicitado pelo nome, pelo que envia o token em texto não encriptado nestes dois casos.

### Exa e Tavily `provider_options`

Exa e Tavily lêem campos específicos do fornecedor de um pacote com namespace: `provider_options.exa` (ou `provider_options["exa-search"]`) e `provider_options.tavily` (ou `provider_options["tavily-search"]`). Apenas as chaves abaixo são encaminhadas. Cada um é verificado em relação ao seu próprio esquema Zod em `open-sse/handlers/search/providerOptionsPassthrough.ts` e uma chave com o tipo errado é descartada. Qualquer outra chave é ignorada, incluindo auth, base URL, `stream` e `outputSchema`. As chaves simples utilizadas por outros fornecedores (`cx`, `depth`, ...) funcionam como anteriormente.

| Provedor | Campos de nível superior                                                                                                                                                                                                                                                                                                                                                  | Aninhado                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitivas planas), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` fundido com o `{ text: true, highlights: true }` padrão |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                     |

Vencem sempre os campos genéricos: `query`, `max_results`, `filters` (domínios), `country` e o tópico derivado de `search_type`. No Exa, `search_type: "news"` mantém `category: "news"`. Tavily também aceita `search_type: "finance"` (`topic: "finance"`).

O custo da pesquisa Firecrawl é registado por bloco iniciado de 10 resultados devolvidos, em 0,002 dólares (2 créditos) por bloco e pelo menos um bloco por chamada ( [facturação Firecrawl](https://docs.firecrawl.dev/billing) ): 11 resultados custam 0,004 dólares.

O `time_range` genérico chega agora a ambos os fornecedores: Exa obtém `startPublishedDate` (ISO timestamp) e Tavily obtém `start_date` (`YYYY-MM-DD`). Uma data explícita em `provider_options` substitui a data mapeada.

Os resultados do Exa mantêm `id`, `highlights` (cada destaque, e não apenas o primeiro utilizado como `snippet`), `highlight_scores`, `summary`, `subpages`, `entities` e `extras` em `provider_raw`. Os resultados Tavily mantêm `images` e `favicon`.

O custo da pesquisa de linkup está registado em 0,005 dólares para `depth` `fast` e `standard` e 0,05 dólares para `deep` ( [linkup price](https://docs.linkup.so/pages/documentation/development/pricing) ), independentemente de `depth` vir `provider_options` ou das definições da ligação.

O Exa `type: "lite"` (Exa 3.0) aceita um conjunto mais pequeno de campos e rejeita todo o pedido quando qualquer outro campo é definido. Para Lite, `additionalQueries`, `systemPrompt` e todas as teclas `contents` exceto `text` e `highlights` são descartadas antes da chamada. Os obsoletos `subpages`, `subpageTarget`, `highlights.numSentences` e `highlights.highlightsPerUrl` já não são encaminhados.

A contabilidade de custos é o registo simples `costPerQuery`, exceto para o Exa, que segue o próprio preço do Exa: 0,007 dólares por chamada para o `auto` (e o legado `fast`) ou 0,004 dólares para `lite` (e o legado `instant`), cobrindo 10 resultados; 0,001 dólares por cada resultado adicional; e 0,001 dólares por resultado devolvido quando `contents.summary` estiver definido. Tavily está registado em 1 crédito (0,008 dólares) para `search_depth` `basic`, `fast` e `ultra-fast`, e 2 créditos (0,016 dólares) para `advanced` ( [créditos Tavily API](https://docs.tavily.com/documentation/api-credits) ). Uma chamada com `auto_parameters: true` que Tavily atualiza para avançado ainda está registada com 1 crédito.

## Pesquisa na Web API

Extraia o conteúdo de um URL através de um fornecedor de pesquisa web configurado (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract, Keenable Fetch).

Extracção Paralela (`parallel-search`, mesma chave API da Pesquisa Paralela) devolve Markdown apenas — qualquer outro `format` é um `400` — e limita o conteúdo a 100.000 caracteres. Quando a própria página de destino não pode ser extraída, o upstream reporta-a dentro de um HTTP 200; OmniRoute apresenta-o como um `422` com uma mensagem fixa.

Keenable Fetch (`keenable-search`) também devolve apenas Markdown (qualquer outro `format` é `400`) e limita o conteúdo a 100.000 caracteres. Funciona sem chave: um pedido `provider: "keenable-search"` explícito sem ligação utiliza o endpoint sem chave do Keenable (limites de taxa por IP). Uma chave configurada apenas aumenta estes limites; a seleção automática utiliza o Keenable apenas quando uma chave é configurada.

| Método | Percurso        | Descrição                                                  |
| ------ | --------------- | ---------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Fetch/scrape a URL — corpo validado por `v1WebFetchSchema` |

**Autenticação:** Chave API do portador (`extractApiKey` + `isValidApiKey`). Política aplicada via `enforceApiKeyPolicy`.

As combinações nomeadas utilizam o [contrato de encaminhamento `model`](#named-searchfetch-combinations) acima, preservando opções e respostas específicas de pesquisa.

**Fallback com reconhecimento de quota (#8297):** quando nem `provider` nem `model` são fornecidos, o pool (`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search` → `keenable-search`) é percorrido por ordem de prioridade fixa (preencher primeiro) — um fornecedor com taxa limitada, mas configurado é ignorado em vez de causar curto-circuito no pedido e uma falha no upstream retryable/quota (HTTP 429 sempre; 402/403 para Firecrawl/Tavily/TinyFish níveis gratuitos de estilo de quota — não para Jina Reader e nunca para um pedido incorreto simples de 400) passa para o próximo fornecedor credenciado não testado no momento do pedido. Quando todos os fornecedores do pool se esgotam, o endpoint devolve um único `429` (com um cabeçalho `Retry-After` ) em vez do `400` genérico anterior. Quando um `provider` explícito é solicitado, há** Não** fallback silencioso — um fornecedor explícito com taxa limitada ou com falha apresenta o seu próprio erro (`429` se for limitado por taxa, caso contrário, o estado upstream).

## Transmissão por WebSocket

```bash
GET /v1/ws?handshake=1
```

Valida um handshake de atualização para WebSocket e devolve as mensagens de exemplo do protocolo de comunicação (`request`, `cancel`). Os frames WS reais são processados pelo servidor WS incluído, fora da tabela de rotas do Next.js.

**Autenticação:** chave de API Bearer durante o handshake.

### API de Responses através de WebSocket (apenas codex)

```bash
# Mesmo host:port que a API HTTP (predefinição 20128); atualiza a ligação:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ou: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# O primeiro frame TEM DE SER response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Um proxy Responses-API-over-WebSocket está ligado **exclusivamente ao `codex`** (backend do ChatGPT). Escuta na mesma porta que a API/dashboard, nos caminhos `/v1/responses`,
`/responses` e `/api/v1/responses`. No primeiro frame `response.create`, autentica e prepara-se através da bridge interna `codex-responses-ws`, seleciona uma ligação OAuth do codex e estabelece um túnel para `wss://chatgpt.com/backend-api/codex/responses` através do transporte `wreq-js`. Os modelos que não sejam codex são rejeitados (`codex_ws_provider_required`).
Para o encaminhamento com partilha de quota, use `model: "qtSd/<group>/codex/<model>"`. Implementado em
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticação:** chave de API Bearer durante o handshake. O servidor HTTP incluído (`server-ws.mjs`)
tem de ser o ponto de entrada ativo (por predefinição, é-o quando `app/server-ws.mjs` existe).

#### ID do modelo: use o ID simples do ChatGPT (sem o prefixo `codex/`)

A **CLI do OpenAI Codex** valida o nome do modelo no lado do cliente quando
`supports_websockets = true` e **rejeita IDs com prefixo do fornecedor**, como
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Envie o ID **simples** (por exemplo, `gpt-5.5`). A bridge do OmniRoute funciona apenas com codex, pelo que volta a resolver um ID simples como um modelo codex
(`resolveCodexWsModelInfo`) antes de estabelecer o túnel upstream — apesar de um `gpt-5.5` simples poder, de outro modo, ser encaminhado para outro fornecedor através de HTTP.

#### Configurar a CLI do OpenAI Codex

Aponte a CLI do Codex para o OmniRoute adicionando um fornecedor personalizado com suporte para WebSocket a `~/.codex/config.toml` (use um `CODEX_HOME` separado para evitar alterar uma configuração existente):

```toml
model = "gpt-5.5"                 # id simples — NÃO "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # sem barra final; o URL WS é derivado (use https/wss em produção)
wire_api = "responses"                    # único valor suportado desde fevereiro de 2026
supports_websockets = true                # ativa o transporte Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # contém a chave de API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # uma chave de API OmniRoute (qualquer chave se REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

A CLI atualiza `base_url + /responses` para um WebSocket e o OmniRoute estabelece um túnel para a ligação OAuth do codex selecionada. Validado de ponta a ponta contra o servidor local: o ChatGPT devolve `codex.rate_limits` + `response.created` e transmite a conclusão.

### Recuperação de sessão de quotas (opt-in)

Um `POST /v1/chat/completions` ou `POST /v1/responses` sem streaming que falha com um erro de quota de terminal (`402`/`429`/`503` cujo corpo diz que a quota ou os créditos estão esgotados) pode ser estacionado e reproduzido posteriormente em vez de devolver o erro. O chamador aceita por pedido com três cabeçalhos:

| Cabeçalho                    | Valor                                     |
| ---------------------------- | ----------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                    |
| `x-omniroute-session`        | ID da sessão, `[A-Za-z0-9._:-]{1,128}`    |
| `x-omniroute-recovery-turn`  | tornar o id único na sessão (mesma regra) |

Apenas as voltas `stream: false` sem ferramentas, histórico de ferramentas ou `previous_response_id` e sem pin `x-omniroute-connection` são elegíveis e `STORAGE_ENCRYPTION_KEY` deve ser definido (o pedido é armazenado encriptado até 24 horas). A resposta é então `202` com `recovery.poll`; poll `GET /v1/quota-recoveries/{id}` (`202` enquanto pendente, `200` com o corpo recuperado quando concluído) ou cancelar com `DELETE`. Os tickets são apenas visíveis para a chave API que os criou. Um replay cujo resultado é incerto termina em `needs_confirmation` em vez de ser enviado duas vezes. Fonte: `src/lib/quota/quotaSessionRecovery.ts`.

## Utilização de self-service (`/api/usage/om-usage`)

Qualquer chave API pode ler** próprio** utilização e quotas — sem autenticação de gestão. Este é o endpoint que um cliente (CLI, o painel OmniCopilot ) utiliza para mostrar ao detentor da chave os seus gastos.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

A chave deve ter**`allowUsageCommand`** ativado (desativado por defeito — o gestor de chaves API do painel alterna por chave). Sem ele, o endpoint responde `403`.

`?format=json` devolve uma forma discriminada para que um chamador nunca leia um campo de dados de uma recusa. Sobre o sucesso:

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Em caso de recusa (`401` bad key / `403` não permitido) a mesma rota retorna `{ "allowed": false, "error": { "message": "…" } }` — um `personal`/`provider` presente, mas vazio (chave permitida, nada aprendido ainda) é um estado diferente de uma recusa, e apenas a forma JSON os distingue.

**Autenticação:** a própria chave Bearer API do chamador, validada com `isValidApiKey` — esta _não_ é a superfície de gestão (`/api/keys/…`), que fica atrás de `requireManagementAuth`.

### Percentagens de quota bruta versus ajustada por corte

Ao consumir `/api/usage/om-usage`, o chamador deverá observar a distinção entre as percentagens apresentadas pelo** saída de texto simples** e o estruturado** saída JSON** :

| Aspeto                  | Formato de texto simples (`/api/usage/om-usage` / `@@om-usage`)                                      | formato JSON (`?format=json`)                                               |
| :---------------------- | :--------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| **Campo de saída**      | `NN% left` (por exemplo, `20% left`)                                                                 | `provider.quotas` / `providers[].quotas`                                    |
| **Medição**             | **Subsídio utilizável ajustado por corte** : capacidade restante acima do limite de corte            | **Quota upstream bruta** : medição não ajustada do fornecedor               |
| **Escala de corte**     | Dimensionado via `effectiveRemainingPercent()` para que a reserva protegida seja lida como `0% left` | Nenhum (valores brutos de instantâneos conforme reportados pelo fornecedor) |
| **Dados limite**        | Incorporado na percentagem exibida                                                                   | Armazenado em `quotaWindowThresholds` por ligação (ou padrões do servidor)  |
| **Consumidor primário** | CLIs interativo, prompts de terminal, operadores humanos                                             | Integrações programáticas, painéis, análises, rastreadores de faturação     |

#### A fórmula de ajuste do corte

OmniRoute suporta cortes de quota proativos para evitar o esgotamento upstream (configurado através da ligação `quotaWindowThresholds`, padrões do fornecedor ou definições de resiliência global). Quando um limite de corte (por exemplo, `cutoff = 25%`) está ativo numa janela de cota, o renderizador de texto calcula a margem restante como:

- Se `remaining <= cutoff`: retorna `0%`.
- Se `remaining > cutoff`: retorna `((remaining - cutoff) / (100 - cutoff)) * 100`.

A saída de texto formatado arredonda para o número inteiro mais próximo (`Math.round(...)`).

#### Exemplo Ilustrativo

Considere uma janela de fornecedor com** 60% de utilização bruta** (por isso** 40% da quota restante bruta** ) e um configurado** Corte de 25% da quota restante** limiar:

| Representação                     | Cálculo                                            | Restante |                   Uso implícito                   |
| :-------------------------------- | :------------------------------------------------- | :------: | :-----------------------------------------------: |
| **JSON bruto (`?format=json`)**   | Instantâneo upstream (`quotas[window]`)            | **40%**  |                      **60%**                      |
| **Formato de texto (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (se estiver a calcular `100 - remaining`) |

- **Por que razão o texto mostra 20% restantes:** Dos 40% da quota física restante na conta, 25% são reservados pela política de corte. O chamador tem apenas 15% dos 75% de espaço útil restante antes de o router parar de encaminhar para esta ligação. O escalonamento garante o esgotamento dos sinais de ligação (`0% left`) exatamente quando o encaminhamento terminará.
- **Por que razão JSON preserva valores brutos:** A carga JSON devolve o instantâneo exato do fornecedor (`UsageSnapshot`) para que as ferramentas externas tenham acesso à utilização upstream verdadeira e ao `quotaWindowThresholds` ao nível da ligação sem escalonamento com perdas no lado do servidor.

#### Orientação sobre a migração de consumidores

Se uma integração externa (como um plug-in de editor ou uma extensão de agente) extraiu anteriormente o endpoint de texto (`NN% left`) e calculou a percentagem utilizada como `100 - NN`, migrar para `?format=json` significa:

- A leitura dos valores JSON brutos refletirá** consumo real a montante** (60% utilizado no exemplo acima).
- Se a integração desejar preservar a semântica de permissão utilizável do endpoint de texto, pode avaliar a fórmula restante efetiva no lado do cliente utilizando `quotaWindowThresholds` para substituições ao nível da ligação.

## Cache semântica

```bash
# Obter estatísticas da cache
GET /api/cache/stats

# Limpar todas as caches
DELETE /api/cache/stats
```

Exemplo de resposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impacto na latência

Um **HIT** da cache semântica fornece a resposta a partir da cache **sem uma
chamada upstream**, pelo que a `X-OmniRoute-Response-Latency` comunicada é próxima de zero
(independentemente da latência upstream original). Os clientes sensíveis à latência
(benchmarking, monitorização p50/p99) devem verificar o
cabeçalho de resposta `X-OmniRoute-Cache-Latency`:

| Valor       | Significado                                                                             |
| ----------- | --------------------------------------------------------------------------------------- |
| `synthetic` | Resposta fornecida a partir da cache; a latência não corresponde ao tempo upstream real |
| _(absent)_  | Resposta de uma chamada upstream real                                                   |

### Ignorar a cache por chave

As chaves de API podem optar por não ler a cache semântica através de `cacheDefaultMode`:

| Valor    | Comportamento                                                        |
| -------- | -------------------------------------------------------------------- |
| `legacy` | Comportamento normal da cache (predefinido)                          |
| `bypass` | Ignora completamente a pesquisa na cache; contacta sempre o upstream |

Definido aquando da criação da chave (`POST /api/keys`) ou da atualização (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Ignorar a cache por pedido

Qualquer pedido pode ignorar a cache, independentemente das definições da chave:

```
X-OmniRoute-No-Cache: true
```

## Compatibilidade de gestão com CLIProxyAPI

O OmniRoute responde aos três endpoints de gestão do [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
que os painéis de utilização consultam para ler os limites das subscrições Claude e Codex
(por exemplo, a origem de limites de utilização `cliproxy` do T3 Code). Aponte o URL base do cliente para
o OmniRoute e utilize uma chave de API com o âmbito `manage` como chave de gestão. As rotas são
disponibilizadas em `/v0/management/*` e em `/api/v0/management/*`.

| Método | Caminho                      | Descrição                                                                                                                                      |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Ligações OAuth do Claude e do Codex como `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Sem tokens                    |
| POST   | `/v0/management/api-call`    | Corpo `{ auth_index, method, url, header?, data? }`. Envia um pedido permitido com o token da conta e devolve `{ status_code, body }`          |
| POST   | `/v0/management/reset-quota` | Corpo `{ auth_index }`. Limpa o período de espera da ligação, os bloqueios de modelos e os períodos de espera por âmbito do Codex de uma conta |

- `auth_index` é o ID da ligação do OmniRoute. `provider` é `claude` ou `codex` (apenas ligações
  OAuth; o fornecedor de chaves de API `anthropic` não é listado). Para o Codex,
  `id_token.chatgpt_account_id` é o ID do espaço de trabalho armazenado e `plan_type` é o plano armazenado.
- `api-call` não é um proxy genérico. Aceita apenas Claude `GET
https://api.anthropic.com/api/oauth/usage` e Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` e
  `POST .../wham/rate-limit-reset-credits/consume`, cada um apenas para uma conta do fornecedor correspondente. Qualquer outra coisa devolve
  `403` sem contactar o upstream. O cabeçalho `Authorization` do autor do pedido (incluindo o marcador `$TOKEN$`) é ignorado: o OmniRoute injeta o token de acesso da ligação, atualizando-o primeiro quando estiver próximo de expirar, e encaminha apenas
  cabeçalhos permitidos (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`). Se `Chatgpt-Account-Id` não for indicado, é utilizado por predefinição o ID do espaço de trabalho armazenado.
  Os pedidos expiram após 15 segundos e utilizam o proxy da ligação.
- `reset-quota` deixa inalterados os estados terminais (banned, expired, credits_exhausted). Um
  `auth_index` desconhecido devolve `404`.

**Autenticação:** sessão do painel ou uma chave de API com o âmbito `manage`, necessária mesmo quando o início de sessão está desativado
(os caminhos encontram-se em `ALWAYS_PROTECTED_API_PATHS`). As chaves apenas de inferência recebem `403`. Origem:
`src/lib/cliproxyCompat/managementApi.ts`.

| `/api/provider-models/validate-and-add` | POST                      | Validação de ligação estrita opcional, autenticada pela gestão e registo de modelo personalizado atómico; ver [Validação de modelo](../guides/MODEL-VALIDATION.md) |

Para os modelos synced/imported, `PUT /api/provider-models` aceita `provider`, `modelId` e `maxOutputTokenOverride`: um número inteiro positivo define o limite do token de saída manual e `null` limpa-o para restaurar o padrão. `GET /api/provider-models?provider=<provider>` devolve estes valores em `modelOutputOverrides`, incluindo modelos sem uma linha de modelo personalizado. A substituição utiliza a característica `max_output_tokens` de tempo de execução e sobrevive a uma ressincronização do modelo. A página do fornecedor compatível com OpenAI oferece os mesmos controlos edit/clear e marca modelos com suporte de visão explícito.

Num nó fornecedor compatível, os caminhos de escrita (`POST`, `PUT`, `PATCH`, `DELETE` e `/api/provider-models/validate-and-add`) armazenam o ID do modelo como o ID upstream simples: um ID colado de uma listagem prefixada tem qualquer pilha principal do próprio prefixo do nó recolhida e as respostas ecoam o ID armazenado. Os IDs cortados dos fornecedores canónicos (por exemplo, `nvidia/nemotron-…`) são armazenados literalmente. `/v1/models` nunca emite um ID `<prefix>/<prefix>/<model>` empilhado.

Os nós de conclusão de chat personalizados adaptam as desativações de raciocínio explícito ao back-end upstream. Um teste de ligação bem-sucedido seleciona automaticamente os controlos do modelo de chat para cada modelo exato ID cuja entrada `/models` comprova um valor `owned_by` reconhecido: `vllm`, `sglang` ou `llamacpp`. Os wrappers transparentes compatíveis com OpenAI podem preservar a entrada do modelo original dentro de um objeto `openai` aninhado; a deteção segue até três destes envelopes. Os modelos com propriedade ausente, desconhecida ou conflituosa mantêm o comportamento OpenAI normal. A deteção reutiliza o pedido de catálogo existente, não gera tokens de conclusão e é invalidada quando o ponto final da ligação é alterado.

Para fixar o comportamento de um back-end que não expõe estes metadados, utilize a atualização parcial do fornecedor existente API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envie esse corpo com `PUT /api/providers/<connection-id>`. Nesta ligação, um esforço de raciocínio explícito de `none` é enviado como `chat_template_kwargs.thinking=false` e `chat_template_kwargs.enable_thinking=false`. Os valores explícitos do modelo nativo permanecem autoritativos, a menos que uma regra de raciocínio do lado do servidor force um esforço. A configuração aplica-se apenas quando uma ligação personalizada compatível com OpenAI despacha um corpo de conclusões de chat; Os pedidos de resposta e os fornecedores comuns mantêm o seu formato de pedido nativo. Defina `reasoningControl` como `openai` para forçar a passagem OpenAI `reasoning_effort` comum ou omita it/set como `null` para utilizar a deteção automática.

O classificador de modo automático do código Claude solicita que o pensamento nativo padrão seja desativado quando não contém controlos de raciocínio explícitos. A deteção utiliza o marcador do sistema do classificador em pedidos no formato Claude, e não nomes de modelos ou limites de conclusão. Os controlos de corpo explícitos, os cabeçalhos effort/thinking suportados, as regras de encaminhamento e o esforço de modelo resolvido mantêm a sua prioridade existente. Ambos os estágios do classificador retêm os seus prompts, limites de conclusão, sequências de paragem e veredictos reais de permissão a montante; a segunda etapa pode ainda produzir o raciocínio visível solicitado como texto comum.

#### Proveniência limite do modelo

`GET /api/models?withLimits=1` (também `true`; `0`/`false` ou omiti-lo mantém a carga padrão inalterada) adiciona `contextWindow`, `maxInputTokens`, `maxOutputTokens` e um objeto `capsSource` a cada linha do modelo. `capsSource` nomeia a regra que forneceu cada limiar, pelo que um limiar surpreendente (por exemplo, 128k num modelo 1M) pode ser rastreado até à sua origem. Os valores resolvidos são os mesmos utilizados pelo encaminhamento; o sinalizador apenas adiciona campos e nunca altera um valor. Qualquer outro valor `withLimits` é rejeitado com `400`.

| valor `capsSource`                           | Origem                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| `override:context`                           | Substituição persistente da janela de contexto (`model_context_overrides`)   |
| `override:max_input` / `override:max_output` | Substituição persistente do recurso `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Tabela de janela de contexto autoritativa estática                           |
| `synced:<provider>/<model>`                  | linha de capacidade sincronizada models.dev                                  |
| `registry:<provider>/<model>`                | Entrada de registo do fornecedor                                             |
| `spec:<model>`                               | Especificação do modelo estático                                             |
| prefixo `effort-base:`                       | Linha emprestada do modelo básico de uma variante com sufixo de esforço      |
| `none`                                       | Nenhuma fonte declara o limite (o valor é `null`)                            |

### Detalhamento do quadro de vídeo

`GET /api/v1/video-bridge/drilldown` lê um identificador opaco ligado ao tenant devolvido em `x-omniroute-video-drilldown` após um pedido de Video Bridge explicitamente consentido. Tanto as leituras como `DELETE` requerem sempre uma chave API válida e a permissão `modalityBridgeVideoDrilldownRemoteEnabled` independente do operador. A retenção da produção requer adicionalmente `modalityBridgeVideoDrilldownEnabled` e `drilldown: true` rigoroso por peça. Se a chave tiver uma lista de permissões de endpoint não vazia, deverá incluir `video` para GET e DELETE, independentemente de o chamador utilizar `/v1` ou `/api/v1`.

consulta GET : `handle` obrigatório; opcional `variant` (`preview`, `standard`, `detail`), `limit` (1–8; legado `frames` é aceite, mas não pode ser combinado com `limit`), `page` baseado em zero e `start`/`end` segundos. Quando ambos os limites de focagem são fornecidos, `end` deve ser maior que `start`. As chaves de consulta Duplicate/unknown são rejeitadas. As respostas bem-sucedidas contêm `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` e `focusWindow` opcional ; JSON sem armazenamento está limitado a 32 MiB incluindo o Base64. A saída sobredimensionada retorna 413; solicitar menos quadros.

`DELETE /api/v1/video-bridge/drilldown?handle=...` retorna `{ "removed": 0|1 }`. GETs desconhecido, expirado e chave cruzada são respostas 404 indistinguíveis; cross-key DELETE não pode remover a entrada do proprietário. O acesso desativado retorna 403, autenticação missing/invalid 401, consultas inválidas 400, cancelamento 499 e erros temporários 503. Os identificadores são locais do processo, expiram após dez minutos e não sobrevivem a um reinício. Os novos identificadores utilizam `v1.` mais um token Base64URL aleatório de 32 bytes; apenas os hashes de token são retidos. Os tokens herdados de 64 hexadecimais permanecem sintaticamente legíveis para compatibilidade. Consulte [as proteções do Video Bridge](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) para obter o consentimento, as cotas e os detalhes da derivação de variantes.

### Versão e canal de lançamento

```bash
GET /api/system/version
```

Rota de gestão apenas loopback (autenticação de administrador). Retorna a versão em execução, a última versão publicada e o estado de atualização automática. `releaseChannel` e `channels` são campos aditivos (rail 3.8.54); `channel` mantém o seu significado — o modo de implementação que o atualizador do painel utiliza (`npm`, `source` ou `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal npm da compilação em execução: `nightly` para versões `-nightly.*`, `next` para outros pré-lançamentos (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para uma versão estável de uma versão principal mais antiga que `channels.latest`, caso contrário `latest`. Mesmas regras do `scripts/release/dist-tag.mjs`, que escolhe a tag dist npm no momento da publicação.
- `channels` — publicou o cabeçalho de cada tag dist, do `npm view omniroute dist-tags` ( HTTP fallback record), armazenado em cache com o mesmo TTL 10 minutos que `latest`. `latest` está sempre presente (regressa ao campo `latest` e depois `"unavailable"`); `next`, `nightly` e `lts` aparecem apenas quando esta tag dist existe. Uma solicitação `Cache-Control: no-cache` atualiza ambas as pesquisas.

O modelo de canal (`latest` = v3 até 4.0 GA, `next` = rc, `nightly` = `develop` builds, `lts` = v3 patches após 4.0 GA) é descrito em `docs/ops/RELEASE_STRATEGY.md`.

## Transcrição de áudio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transcreva ficheiros de áudio utilizando qualquer fornecedor STT configurado. O primeiro segmento do caminho seleciona o fornecedor nativo (`openai/…`, `deepgram/…`). Os gateways que exportam novamente o modelo de outro fornecedor utilizam um ID qualificado
(`openrouter/deepgram/nova-3`).

**Pedido:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Resposta:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**IDs de modelo de exemplo:** `openai/whisper-1` (requer uma chave OpenAI),
`openrouter/deepgram/nova-3` (requer uma chave OpenRouter),
`deepgram/nova-3` (requer uma chave nativa Deepgram). Um pedido simples
`deepgram/nova-3` **não** utiliza o OpenRouter.

**Formatos suportados:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** transcrição em modo de ficheiro através do WebSocket
Gemini Live (requer uma chave de API Gemini). O carregamento é convertido para PCM mono de 16 kHz com `ffmpeg`
(deve estar em `PATH`, exceto quando o ficheiro já for um WAV PCM mono de 16 kHz), transmitido para a sessão e
o texto finalizado é devolvido como `{ "text": "..." }`. Os campos de formulário opcionais `language` e `prompt`
são encaminhados. Limites: os carregamentos superiores a 25 MiB ou áudio descodificado com mais de 10 minutos respondem
com `413`; uma conversão que demore mais de 60 s é terminada e responde com `504`. A chave de API é enviada
apenas no cabeçalho `x-goog-api-key`, nunca no URL do WebSocket.

## Limites de tokens

Orçamentos de **tokens** por chave de API (distintos do Orçamento baseado em USD acima). Aplicados diretamente no percurso do pedido: quando a utilização atual da janela de uma chave atinge o respetivo limite, os pedidos são rejeitados com `429 Too Many Requests`. Os limites podem ser definidos para um `model` específico, um `provider` ou aplicados `global`mente à chave; quando vários limites correspondem a um pedido, prevalece o mais restritivo.

```bash
# Lista os limites de tokens de uma chave (inclui a utilização atual da janela)
GET /api/usage/token-limits?apiKeyId=key-123

# Cria ou atualiza um limite de tokens
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Elimina um limite de tokens pelo id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Notas sobre o esquema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) são obrigatórios. `scopeValue` é obrigatório, exceto quando `scopeType` é `global` (por exemplo, um id de modelo para o âmbito `model`, um id de fornecedor para o âmbito `provider`). `tokenLimit` tem de ser um número inteiro positivo (convertido a partir de uma cadeia de caracteres). Opcional: `id` (omitir para criar, fornecer para atualizar), `resetInterval` (`daily` | `weekly` | `monthly`, predefinição `monthly`), `resetTime` (`HH:MM`), `enabled` (predefinição `true`). As respostas de `GET` enriquecem cada limite com `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Este é um endpoint da classe de gestão (a autenticação é aplicada centralmente pelo pipeline de autorização).

## Processamento de pedidos

1. O cliente envia um pedido para `/v1/*`
2. O handler da rota chama `handleChat`, `handleEmbedding`, `handleAudioTranscription` ou `handleImageGeneration`
3. O modelo é resolvido (fornecedor/modelo direto ou alias/combinação)
4. As credenciais são selecionadas da base de dados local, filtrando pela disponibilidade da conta
5. Para chat: `handleChatCore` verifica a cache semântica/de assinaturas e resolve as definições de compressão da combinação
6. A compressão proativa é executada antes da tradução para o fornecedor quando ativada (`lite`, Caveman, RTK ou em camadas)
7. O executor do fornecedor envia o pedido a montante
8. A resposta é traduzida novamente para o formato do cliente (chat) ou devolvida tal como está (embeddings/imagens/áudio)
9. A utilização, as análises de compressão e os registos dos pedidos são registados
10. O fallback é aplicado em caso de erros, de acordo com as regras da combinação

Referência completa da arquitetura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resiliência (alargada)

O OmniRoute expõe três mecanismos independentes para falhas temporárias; os endpoints de gestão abaixo permitem aos operadores consultá-los e substituí-los:

| Âmbito                   | Armazenamento do estado                          | Leitura                                   | Repor / limpar                                                      |
| ------------------------ | ------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------------------- |
| Disjuntor do fornecedor  | `domain_circuit_breakers` + memória              | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                        |
| Arrefecimento da ligação | `rateLimitedUntil` nas ligações do fornecedor    | `/api/rate-limits`, `/api/providers/[id]` | (reativa-se de forma diferida; limpar através de PUT do fornecedor) |
| Bloqueio do modelo       | Registo de disponibilidade de modelos em memória | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                            |

`PATCH /api/resilience` aceita substituições do disjuntor do fornecedor em `providerBreaker.oauth` e `providerBreaker.apikey`. Cada perfil suporta `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; os mesmos campos estão disponíveis em Painel → Definições → Resiliência.

```bash
# Limpar o bloqueio de um único modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Limpar todos os bloqueios
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Para obter a referência conceptual completa e os valores predefinidos dos disjuntores, consulte [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Fila de limitação de taxa e mecanismo de segurança de ativação automática

- **Caminho de escrita suportado**: `POST /api/rate-limits` com o corpo `{"connectionId": "<id>", "enabled": true|false}` é o endpoint de gestão suportado para ativar ou desativar a proteção contra limitação de taxa de uma ligação. `PUT /api/providers/[id]` não modifica nem alterna deliberadamente `rateLimitProtection` (#11278).
- **Semântica de `enabled: false`**: definir `enabled: false` remove a proteção explícita da ligação, mas **não** exclui uma ligação ativa com chave de API do mecanismo de segurança global de ativação automática (`autoEnableApiKeyProviders = true`). Em `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` são equivalentes; as ligações ativas com chave de API sem proteção explícita continuam protegidas pelo mecanismo de segurança de ativação automática.
- **Desativação global**: para executar ligações com chave de API sem filas de limitação de taxa, desative globalmente o mecanismo de segurança através de `RATE_LIMIT_AUTO_ENABLE=false` (env) ou de `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Definições → Resiliência / `PATCH /api/resilience`).

OmniRoute fornece um servidor Model Context Protocol integrado com 3 transportes (stdio, SSE, streamable-http) e ferramentas com âmbito definido. Os endpoints do painel abaixo lêem os dados status/audit e fazem proxy dos transportes HTTP.

| POST | `/api/mcp/sse` | Enviar trama JSON-RPC no transporte SSE |

## Servidor A2A

O OmniRoute expõe um endpoint JSON-RPC 2.0 A2A (Agent-to-Agent), além de um wrapper REST para fins de inspeção/dashboard.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opcional, exceto se OMNIROUTE_API_KEY estiver definido
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Métodos suportados (todos dependentes de `settings.a2aEnabled`):

| Method           | Description                                                             |
| ---------------- | ----------------------------------------------------------------------- |
| `message/send`   | Execução síncrona da competência; devolve `{task, artifacts, metadata}` |
| `message/stream` | Execução SSE em streaming do mesmo conjunto de competências             |
| `tasks/get`      | Obtém uma tarefa através de `taskId`                                    |
| `tasks/cancel`   | Cancela uma tarefa através de `taskId`                                  |

Competências integradas: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Cartão do agente

```bash
GET /.well-known/agent.json
```

Devolve o cartão público do agente A2A (nome, descrição, capacidades, catálogo de competências, esquema de autenticação) — armazenado publicamente em cache durante 1h. Não é necessária autenticação.

### Auxiliares REST

| Method | Path                         | Description                                                                                                        |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/a2a/status`            | A2A ativado + estatísticas das tarefas + resumo do cartão do agente em cache                                       |
| GET    | `/api/a2a/tasks`             | Lista tarefas — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Não implementado como auxiliar REST — criar através de JSON-RPC `message/send`)                                   |
| GET    | `/api/a2a/tasks/[id]`        | Obtém uma tarefa                                                                                                   |
| POST   | `/api/a2a/tasks/[id]/cancel` | Cancela uma tarefa                                                                                                 |

**Autenticação:** os auxiliares REST funcionam sem autenticação de gestão (podem ser lidos pelo dashboard); a rota JSON-RPC `/a2a` utiliza Bearer `OMNIROUTE_API_KEY` se estiver configurada.

## Autenticação

Consulte [Autenticação de gestão](../guides/MANAGEMENT-AUTH.md) para conhecer as quatro

- As rotas do painel (`/dashboard/*`) utilizam o cookie `auth_token`
- O início de sessão utiliza o hash da palavra-passe guardada; como alternativa, usa `INITIAL_PASSWORD`
- A opção `requireLogin` pode ser configurada através de `/api/settings/require-login`
- As rotas `/v1/*` podem exigir opcionalmente uma chave de API Bearer quando `REQUIRE_API_KEY=true`
- Nesta referência, "token de gestão" / "chave de API com âmbito de gestão" refere-se a uma das famílias apresentadas nesse guia — não a um tipo adicional de segredo indefinido

> **Alteração incompatível (v3.8.0)** — `/api/v1/agents/tasks/*` e os endpoints de gestão do período de espera exigem agora **autenticação de gestão** (cookie `auth_token` do painel ou uma chave de API com âmbito de gestão). Os clientes que anteriormente chamavam estas rotas sem autenticação receberão `401 Unauthorized`. Consulte o commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
