## Conclusões de chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Cabeçalhos personalizados

| Cabeçalho                | Direção  | Descrição                                                                                                                                                                                                                              |
| ------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Pedido   | Defina como `true` para ignorar a cache                                                                                                                                                                                                |
| `x-omniroute-no-memory`  | Pedido   | Defina como `true` para ignorar a injeção de memória e competências neste pedido (reflete a ausência de cache; evita a sobrecarga de tokens/custos por chamada)                                                                        |
| `X-OmniRoute-Progress`   | Pedido   | Defina como `true` para receber eventos de progresso                                                                                                                                                                                   |
| `X-Session-Id`           | Pedido   | Chave de sessão persistente para afinidade de sessão externa                                                                                                                                                                           |
| `x_session_id`           | Pedido   | A variante com caráter de sublinhado também é aceite (HTTP direto)                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Pedido   | Etiqueta de sessão/conversa fornecida pelo chamador (também alimenta a memória). Quando presente, é guardada literalmente em `call_logs.session_tag` para atribuição de custos por sessão (#8249) — nunca é sintetizada quando ausente |
| `Idempotency-Key`        | Pedido   | Chave de desduplicação (janela de 5 s)                                                                                                                                                                                                 |
| `X-Request-Id`           | Pedido   | Chave de desduplicação alternativa                                                                                                                                                                                                     |
| `x-omniroute-connection` | Pedido   | Fixa um pedido de modelo único a uma ligação de fornecedor (conta) através do respetivo ID — consulte [Fixação de conta por pedido](#account-pinning-per-request)                                                                      |
| `X-OmniRoute-Cache`      | Resposta | `HIT` ou `MISS` (sem streaming)                                                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | Resposta | `true` se tiver sido desduplicado                                                                                                                                                                                                      |
| `X-OmniRoute-Progress`   | Resposta | `enabled` se o acompanhamento do progresso estiver ativado                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | Resposta | ID de sessão efetivo utilizado pelo OmniRoute                                                                                                                                                                                          |
| `X-OmniRoute-Request-Id` | Resposta | ID de correlação do pedido (quando conhecido)                                                                                                                                                                                          |
| `X-OmniRoute-Version`    | Resposta | Versão da compilação do OmniRoute (sempre presente)                                                                                                                                                                                    |
| `X-OmniRoute-Cost-Saved` | Resposta | Montante em USD que a cache permitiu poupar num HIT (apenas acertos da cache)                                                                                                                                                          |
| `X-OmniRoute-Decision`   | Resposta | Rasto de encaminhamento: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` é a estratégia do combo ou `single` para um pedido que não seja de combo) — sempre presente nas respostas de conclusão                          |

> Nota sobre o Nginx: se depender de cabeçalhos com carateres de sublinhado (por exemplo, `x_session_id`), ative `underscores_in_headers on;`.

#### Fixação de conta por pedido

Quando um fornecedor tem várias ligações (contas ou chaves), o OmniRoute normalmente seleciona uma
através da respetiva estratégia de seleção de contas. Em alternativa, um pedido pode fixar uma ligação
específica através do cabeçalho `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Onde encontrar o ID.** Abra a página do fornecedor no painel
  (**Painel → Fornecedores → <fornecedor>**) e clique na etiqueta de ID `xxxxxxxx…` numa linha de ligação
  — isto copia o ID completo da ligação.
- **Que pedidos o respeitam.** Pedidos de modelo único (`provider/model`) em
  `/v1/chat/completions`, `/v1/messages` e `/v1/responses`. As combinações ignoram o cabeçalho: fixe
  uma conta por etapa da combinação através da ligação da própria etapa.
- **A fixação é estrita, não uma preferência.** A ligação fixada é utilizada exclusivamente. Uma
  falha durante o pedido regista o período de espera da conta, mas **não** muda para uma
  conta equivalente do mesmo fornecedor.
- **O período de espera e a quota libertam a fixação.** Enquanto a ligação fixada estiver num período de espera,
  tiver a quota esgotada ou estiver bloqueada por uma política de quotas, os pedidos posteriores recorrem às
  outras ligações do fornecedor, exatamente como o tráfego sem fixação.
- **IDs desconhecidos ou desativados causam uma falha.** Um ID que não esteja no conjunto ativo do fornecedor (por ter sido eliminado,
  desativado ou pertencer a outro fornecedor) não deixa nenhuma conta elegível, pelo que o pedido
  falha em vez de ser silenciosamente encaminhado para outro destino.

O Claude Code envia cabeçalhos personalizados através de `ANTHROPIC_CUSTOM_HEADERS`. Coloque-o no bloco `env`
de `~/.claude/settings.json` ou num ficheiro `.claude/settings.json` ao nível do projeto para fixar uma conta
diferente por projeto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fonte: `src/sse/handlers/chat.ts` (leitura do cabeçalho), `src/sse/services/auth.ts` e
`src/sse/services/sessionAffinityPin.ts` (libertação da fixação e verificação de ausência no conjunto).

> **Cabeçalhos de telemetria de custos:** as respostas bem-sucedidas sem transmissão também incluem o conjunto de telemetria de custos `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 casas decimais fixas; `0.0000000000` para pedidos gratuitos/sem preço definido), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` e `X-OmniRoute-Fallback-Attempts` (apenas quando > 0), além de `X-OmniRoute-Request-Id` e `X-OmniRoute-Version`. Estes são emitidos pelas conclusões de conversação, por `/v1/responses`, `/v1/messages` e **pelos endpoints de multimédia** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` e `/v1/moderations` (custo sempre `0`). O custo de multimédia é calculado por modalidade (por imagem, por segundo, por caráter, por unidade de pesquisa) quando os preços estão disponíveis; caso contrário, é `0` (prosseguimento em caso de falha).

> **Semântica de custos dos acertos de cache:** num ACERTO da cache semântica (`X-OmniRoute-Cache-Hit: true`), não é efetuada nenhuma chamada ao serviço a montante, pelo que `X-OmniRoute-Response-Cost` é `0.0000000000` (o custo **incremental** de servir o acerto). O custo original/que teria ocorrido é indicado separadamente em `X-OmniRoute-Cost-Saved`. Os consumidores de dados de faturação devem somar `X-OmniRoute-Response-Cost` (os acertos não têm custo); as análises da cache podem agregar `X-OmniRoute-Cost-Saved`.

## Concessões exclusivas de sessões geridas

A concessão exclusiva de sessões geridas é um contrato de encaminhamento opcional e independente do cliente: um proprietário ativo
detém uma ligação OmniRoute elegível. Não concede um modelo, não exige OAuth, não identifica um
cliente específico nem exige um fornecedor específico.

A chave de API usada para autenticação tem de possuir o âmbito `lease:exclusive` e uma lista
`allowedConnections` explícita e não vazia. O limite de mutação da base de dados impõe ambos os campos em conjunto durante a
criação da chave e as atualizações parciais.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

As respostas bem-sucedidas de aquisição, renovação e libertação expõem carimbos de data/hora, `state` e o valor positivo exato de
`generation`, mas nunca a ligação selecionada nem as credenciais. A renovação e a libertação fornecem a
geração no corpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

O proprietário de uma concessão ativa pode solicitar explicitamente metadados de apresentação seguros para a privacidade relativos à associação atual:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Esta ação de estado opcional é protegida pelo proprietário opaco, pela chave de API gerida autenticada e pela
geração ativa exata numa única transação de base de dados. `displayName` é apenas o nome configurado e sem espaços circundantes da
ligação; é `null` quando não existe um nome configurado seguro. O OmniRoute nunca o substitui por um
endereço de e-mail ou por uma identidade de conta gerada. O valor do fornecedor é uma etiqueta de apresentação não confidencial e nunca
um identificador gerado de fornecedor compatível. São excluídos credenciais, tokens, cookies, identificadores não processados de ligações ou de
chaves de API, hashes de proprietários, segredos de proteção e dados internos de encaminhamento.

As consultas com chave errada, proprietário errado, geração obsoleta, dados em falta, expirados, libertados ou invalidados
devolvem todas o mesmo erro `409 LEASE_FENCE_STALE`, sem metadados da ligação. Um cliente que tenha recebido a resposta de espera por capacidade não possui uma associação ativa para consultar. Quando o encaminhamento faz a transição de uma concessão ativa,
a mesma geração permanece válida e o estado devolve atomicamente a nova associação, nunca a antiga.
Os clientes existentes permanecem inalterados porque as respostas de aquisição, renovação, libertação e espera mantêm
os respetivos formatos anteriores.

Este contrato do servidor não altera o `/status` padrão do OpenAI Codex. Atualmente, o Codex padrão comunica o seu
fornecedor de modelos e o estado de autenticação/conta incorporado, mas não apresenta metadados arbitrários de contas de
fornecedores personalizados; uma integração futura do cliente terá de chamar esta ação e decidir como
apresentar `connection.displayName`.

Cada pedido de inferência gerida fornece depois ambos os cabeçalhos de controlo:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

O proprietário exato, a geração, a ligação ativa e a chave de API autenticada são validados imediatamente
antes de cada tentativa a montante suportada. A repetição do proprietário e da geração com outra chave falha mesmo
quando essa chave permite a mesma ligação. Os proprietários não processados não são guardados, registados, retidos no
instantâneo do pedido nem reencaminhados para o serviço a montante.

A contenção temporária devolve HTTP `429` com `Retry-After` e:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Esta resposta significa apenas que o conjunto elegível normal não estava vazio e que todos os candidatos livres estavam
detidos por uma concessão ativa externa. Modelos/fornecedores não suportados, incompatibilidade de políticas, período de arrefecimento, quota,
estado de funcionamento e outras falhas comuns de elegibilidade mantêm as respostas existentes do OmniRoute.

### `x-omniroute-compression`

Substituição por pedido do plano de compressão. Tem a precedência mais elevada — sobrepõe-se à substituição da combinação de encaminhamento,
ao perfil ativo, ao acionamento automático e à Predefinição do painel. Valores:

| Valor         | Efeito                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Sem compressão para este pedido.                                                                                                           |
| `default`     | O perfil Predefinição derivado do painel (ignora o perfil ativo). Os motores com perdas permanecem desativados.                            |
| `safe`        | Apenas desduplicação e normalização de espaços em branco.                                                                                  |
| `allow-lossy` | Mantém o plano do operador para este pedido, incluindo resumos e reescritas de estilo.                                                     |
| `engine:<id>` | Um único motor, quando ativado, por exemplo, `engine:rtk`. Adesão por pedido para esse motor.                                              |
| `<combo>`     | Uma combinação com nome, primeiro com correspondência pelo nome (sem distinção entre maiúsculas e minúsculas) e depois pelo identificador. |

Notas:

- Os valores desconhecidos são ignorados (o pedido nunca é rejeitado); a resolução prossegue para a precedência normal do operador.
- Se várias combinações partilharem um nome, indique o **id** da combinação para obter uma correspondência determinística.
- Uma combinação cujo nome seja `off` ou `default` não pode ser selecionada pelo nome (essas palavras-chave são interpretadas primeiro); referencie essa combinação pelo respetivo identificador.
- O interruptor principal de compressão é uma restrição absoluta: quando a compressão está globalmente desativada, este cabeçalho não pode ativá-la.

O plano aplicado é devolvido no cabeçalho da resposta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

em que `<source>` é um de `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ou `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Fornecedores disponíveis: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Os IDs de catálogo têm o formato `provider/model` (exemplo: `jina-ai/jina-embeddings-v5-omni-small`). Os IDs de modelos Jina sem fornecedor que apareçam no registo (por exemplo, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) também são resolvidos. As operações de embedding/rerank/classify/segment da Jina utilizam primeiro as credenciais `jina-ai` do painel; `JINA_AI_API_KEY` é utilizada como alternativa apenas quando não existe nenhuma chave no painel. O cartão `jina-reader` destina-se apenas ao Reader / `r.jina.ai` (`POST /v1/web/fetch`) e nunca fornece embeddings nem rerank.

Os modelos do registo que anunciam suporte multimodal também aceitam até 32 itens estruturados
independentes do fornecedor. Os tipos de itens multimédia são `text`, `image`, `audio`, `video` e `document`. O respetivo `source`
multimédia é `{"type":"url","url":"https://..."}` ou
`{"type":"base64","data":"...","media_type":"..."}`.

O Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
e o alias da família `jina-ai/jina-embeddings-v5-omni` → omni-small) também aceita documentos EmbeddingsV5Request nativos da Jina
e **reencaminha-os intactos** para `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Os valores nativos `{ image | audio | video | pdf }` podem ser um URL HTTPS público, um URI `data:` ou base64
em bruto. O OmniRoute não converte esses objetos em strings nem obtém os URLs das imagens nativas — a Jina obtém
os conteúdos multimédia públicos. Os campos adicionais da Jina (`task`, `normalized`, `truncate`, `embedding_type`) são
reencaminhados. Os SKUs Jina apenas de texto continuam a rejeitar documentos que não sejam de texto.

Limites de segurança e transporte:

- Os URLs de conteúdos multimédia remotos têm de ser HTTPS públicos. Os itens canónicos `{type,source:url}` são obtidos
  no servidor (revalidação de redirecionamentos, tempo limite, limites de tamanho, DNS público e fixação da ligação) e
  incorporados antes da chamada ao fornecedor. Os itens nativos da Jina `{image:"https://..."}` são reencaminhados sem alterações
  após a mesma verificação de HTTPS público; a Jina obtém o URL.
- Os conteúdos multimédia base64 inline estão limitados a 8 MiB descodificados por item e a 16 MiB descodificados em todo o pedido.

Tradução para o fornecedor (os itens canónicos nunca são reencaminhados sem alterações):

- Modelos multimodais da Jina: cada item de nível superior torna-se num objeto com uma chave de modalidade
  (`text` / `image` / `audio` / `video` / `pdf`), utilizando URIs de dados para conteúdos multimédia inline; um vetor por
  item de nível superior.
- Família Gemini Embedding 2: uma matriz de nível superior torna-se num único pedido nativo
  `models/{model}:embedContent` com `content.parts` (`text` ou `inline_data`).
- llama.cpp (`llama-cpp/<model>`, qualquer modelo carregado pelo servidor local): os itens canónicos `text`
  tornam-se strings simples, enquanto `image` / `audio` / `video` se tornam, cada um, num objeto
  `{"content": [part]}`, utilizando as partes de conteúdo de conversação do llama-server (`image_url`,
  `input_audio` com o formato `wav` / `mp3` / `flac`, `input_video`) com dados inline; um vetor
  por item de nível superior. O servidor tem de ser executado com `--embedding --mmproj …`; sem um projetor,
  rejeita os conteúdos multimédia. `document` não é suportado.
- Os modelos desconhecidos/dinâmicos sem metadados explícitos de modalidade rejeitam entradas estruturadas com HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

As combinações de modelo/modalidade não suportadas devolvem HTTP 400 em vez de converterem o item. Os campos de extensão
que não sejam de entrada em pedidos legados de strings/tokens continuam a ser transmitidos sem alterações.

```bash
# Listar todos os modelos de embeddings
GET /v1/embeddings
```

## Geração de imagens

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Os fornecedores disponíveis incluem OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local) e ComfyUI (local).

`n` devolve `n` imagens em `data[]`. Os fornecedores cuja API a montante devolve uma imagem por chamada
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) recebem `n` chamadas separadas a montante, com um máximo de 4 em simultâneo. Um
`seed` fixo é incrementado pelo índice da chamada (`seed`, `seed + 1`, …), para que as imagens sejam diferentes, mas permaneçam
reproduzíveis. `n` está limitado a 10. O pedido falha por completo se qualquer chamada falhar. A lista
de formatos com distribuição por várias chamadas é `SINGLE_IMAGE_FANOUT_FORMATS` em
`open-sse/handlers/imageGeneration/fanOut.ts`.

O ZenMux reutiliza a ligação existente com chave de API e aceita os prefixos `zenmux/` ou `zm/`:

- `zenmux/openai/gpt-image-2` utiliza a API OpenAI Images do ZenMux. As opções incluem `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` e `response_format`.
- Outros publicadores, como `zm/meta/muse-image-1.0`, utilizam o endpoint `:predict`
  do Vertex AI do ZenMux. `n` corresponde a `sampleCount`, `aspect_ratio` a `aspectRatio` e `image_size`
  (`1K`, `2K`, `4K`) a `sampleImageSize`. Um `size` em píxeis fornece apenas uma proporção,
  não dimensões garantidas em píxeis. As proporções, resoluções e contagens suportadas variam consoante o modelo.
- `zm/inclusionai/ming-image-0.1-design` escolhe as suas próprias dimensões. Omita `size`,
  `aspect_ratio` e `image_size`; valores explícitos devolvem HTTP 400. É possível solicitar PNG, JPEG e WebP
  com `output_format`.

Esta integração suporta a geração de imagens a partir de texto, não a edição de imagens de referência. A saída do Vertex
é normalizada para `data[].b64_json`; `response_format: "url"` devolve um URL HTTPS
a montante ou um URL de dados base64 quando apenas estão disponíveis os bytes da imagem. Saídas vazias/filtradas
devolvem um erro em vez de uma resposta de sucesso vazia. O acesso aos modelos depende da conta ZenMux.
Consulte a [API Vertex do ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) e a
[API OpenAI Images](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Listar todos os modelos de imagem
GET /v1/images/generations
```

## OCR de documentos

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` seleciona o fornecedor de OCR através de um prefixo `provider/model`; um ID de modelo sem prefixo (por exemplo,
`mistral-ocr-latest`) é associado ao respetivo fornecedor registado e, se `model` for omitido, é utilizado por predefinição o
Mistral (`mistral-ocr-latest`). Fornecedores registados (`open-sse/config/ocrRegistry.ts`):

| ID do fornecedor              | ID do modelo         | Valor de `model`                                              | Notas                                                                                                                                              |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (ou apenas `mistral-ocr-latest`) | Síncrono — a resposta é devolvida diretamente pela única chamada a montante.                                                                       |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | Operação assíncrona a montante (`analyze` + consulta repetida) — consulte abaixo.                                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | Síncrono, através do endpoint de parceiro `openapi/chat/completions` do Vertex AI — consulte abaixo para obter informações sobre autenticação/URL. |

Os três fornecedores respondem com o mesmo corpo no formato do Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxo de consulta repetida do Azure Document Intelligence

A API `analyze` do Azure Document Intelligence é assíncrona: o pedido inicial devolve um
cabeçalho `Operation-Location` em vez de um corpo, e é necessário consultar repetidamente o resultado. O processador
(`open-sse/handlers/ocr.ts`) consulta esse URL a cada segundo, até um máximo de 30 tentativas, falha imediatamente (não
continua a consultar) perante uma resposta de consulta que não seja `ok` ou um estado `"failed"`, e devolve `504` se a
operação ainda estiver em execução depois de se esgotar o limite de tentativas. A resposta final do Azure é
normalizada para o mesmo formato `pages`/`markdown` utilizado pelo Mistral antes de ser devolvida ao
chamador, para que o código do cliente não tenha de tratar o fornecedor como um caso especial.

### Autenticação e resolução do endpoint de OCR DeepSeek do Vertex AI

`vertex-deepseek-ocr` reutiliza a mesma autenticação do Vertex AI que o OmniRoute já suporta para
tráfego de conversação/imagem (`open-sse/executors/vertex.ts`): a chave de API da ligação é uma
credencial JSON de uma conta de serviço (trocada por um token de acesso OAuth de curta duração através do fluxo JWT bearer)
ou um token de acesso OAuth já emitido, utilizado tal como está. O URL do endpoint a montante é o
endpoint genérico de parceiro `openapi/chat/completions` do Vertex, criado a partir do projeto e da
região da ligação — um `providerSpecificData.project`/`providerSpecificData.region` explícito tem sempre prioridade;
caso contrário, o projeto é derivado do `project_id` do JSON da conta de serviço e a região
assume `us-central1` por predefinição. Ambas as resoluções ocorrem em `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) e são utilizadas por
`src/app/api/v1/ocr/route.ts` antes do encaminhamento para `handleOcr`.

## Listar modelos

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Devolve todos os modelos de conversação, incorporação e imagem + combinações no formato OpenAI
```

### Preços dos modelos (`pricing`)

Uma entrada contém um objeto `pricing` quando o OmniRoute conhece o preço do modelo. O preço provém
da tabela de preços utilizada pela contabilização de custos: predefinições incorporadas, preços sincronizados e
substituições definidas através de `/api/pricing`. Estes são preços de tabela, pelo que os fornecedores por subscrição também
apresentam um preço por token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Campos                                                          | Unidade                            | Notas                                                                                                                                                         |
| --------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD por token, cadeia decimal      | Compatível com o OpenRouter, nunca em notação exponencial. Os dois campos de cache só aparecem quando existe um preço de cache.                               |
| `input`, `output`, `cached`, `cache_creation`                   | USD por 1 milhão de tokens, número | Campos de versões anteriores do catálogo, mantidos para clientes existentes. `reasoning` e `long_context` também aparecem quando a linha de preços os contém. |

- As **combinações** apresentam o preço do primeiro destino visível. As combinações `auto/*` incorporadas escolhem um
  destino no momento do pedido, pelo que não têm `pricing`.
- Os **modelos gratuitos** apresentam `"0"` (e `0`) quando o respetivo preço é zero. Um modelo sem uma linha de preços
  também apresenta `"0"` quando o catálogo o assinala como gratuito (`free: true`) ou quando o catálogo incorporado de modelos gratuitos
  o inclui.
- **Preço desconhecido:** a entrada não tem uma chave `pricing`.
- Os **fornecedores com medição por créditos** (como o Kiro) faturam por pedido, em vez de por token. As respetivas
  entradas mantêm os campos numéricos por milhão que tinham anteriormente e não contêm campos de cadeia por token.
- As **variantes** (IDs de esforço de raciocínio, aliases sem raciocínio e espelhos de descoberta e gateway)
  copiam o preço do modelo para o qual encaminham.
- Os campos contêm apenas as tarifas base. Os escalões de contexto longo (o campo numérico `long_context`) e
  os multiplicadores do nível de serviço (por exemplo, Codex rápido ou flexível) não alteram `prompt` nem
  `completion`.
- O objeto é igual para todos os estilos de autenticação, incluindo um pedido ao estilo Anthropic
  com `x-api-key` e `anthropic-version` (a resposta mantém-se `{ "object": "list",
"data": [...] }`). Implementação: `src/app/api/v1/models/catalogPricing.ts`.

### Prefixos de ID dos modelos (`?prefix=`)

A maioria dos modelos é anunciada com um **prefixo de fornecedor**. O prefixo que obtém é controlado pelo
sinalizador de funcionalidade `MODELS_CATALOG_PREFIX_MODE` e pode ser substituído **por pedido** com um
parâmetro de consulta — útil para um cliente que pretenda uma lista limpa sem alterar a definição global do
servidor para todos os outros:

```bash
GET /v1/models?prefix=alias        # um ID por modelo — o prefixo de alias curto
GET /v1/models?prefix=dual         # ambas as formas (predefinição do servidor)
GET /v1/models?prefix=canonical    # apenas o prefixo completo do ID do fornecedor
```

| Modo        | Emite                                                   | Notas                                                                                                                                                                                                                                  |
| ----------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **e** `claude/claude-sonnet-4-6` | **Predefinição.** Ambos os IDs encaminham para o mesmo modelo; são mantidos para que as configurações de clientes que tenham codificado diretamente qualquer uma das formas continuem a funcionar. Duplica aproximadamente o catálogo. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Uma entrada por modelo. Os fornecedores sem um alias distinto continuam a emitir a respetiva entrada, pelo que nada se perde.                                                                                                          |
| `canonical` | `claude/claude-sonnet-4-6`                              | Uma entrada por modelo sob o prefixo completo do ID do fornecedor. Os fornecedores sem um alias distinto (por exemplo, `antigravity/…`, `agy/…`) também emitem aqui o respetivo ID único, pelo que nada se perde.                      |

Um espelho no modo `dual` também pode ser reconhecido sem o parâmetro de consulta: contém um campo `parent`
que aponta para o ID principal.

Os clientes que apresentem um seletor de modelos devem pedir `?prefix=alias` — é isto que a
[extensão OmniCopilot para o VS Code](../guides/VSCODE-COPILOT.md) faz.

### Filtros de descoberta (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` aceita filtros de descoberta opcionais. Sem qualquer um deles, a resposta permanece
inalterada. Estes restringem o catálogo que o autor da chamada já pode ver (as permissões da chave de API são aplicadas primeiro)
e são executados antes da paginação ao estilo OpenAI com `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # todas as capacidades indicadas têm de ser verdadeiras
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` do catálogo; as linhas sem um são `chat`
GET /v1/models?q=sonnet&limit=10                           # correspondência sem distinção entre maiúsculas e minúsculas no ID ou nome
```

| Parâmetro     | Valores                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | número inteiro não negativo, comparado com `context_length`                                         |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caracteres                                                                                    |

Um valor desconhecido, ou um `min_context` que não seja um número inteiro não negativo (por exemplo, `1.5`),
devolve HTTP `400` e a mensagem apresenta os valores válidos. Implementação:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista reduzida de modelos (`POST /v1/models/query`)

`POST /v1/models/query` devolve uma lista reduzida e determinística proveniente do mesmo catálogo, com a mesma
autenticação e visibilidade por chave que `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Todos os campos são opcionais. `capabilities` e `exclude` aceitam uma matriz ou uma cadeia de caracteres separada por vírgulas;
`max_output` é comparado com `max_output_tokens`. Os resultados são ordenados por `owned_by` e, em seguida, por `id`.
O valor predefinido de `limit` é `20`, e os valores superiores a `100` são limitados a `100`. JSON inválido, um campo
desconhecido ou um valor inválido devolve HTTP `400`.

### Modelos de chat ocultos individualmente

Um modelo marcado como **Oculto** na página do respetivo fornecedor é excluído do catálogo e rejeitado
com HTTP `404` / `model_not_found` quando solicitado explicitamente. A verificação utiliza o fornecedor
e o modelo resolvidos, incluindo aliases de fornecedores, prefixos de nós de fornecedores compatíveis e
predefinições de ligação. Uma combinação ignora destinos ocultos e pode utilizar um modelo semelhante visível;
quando não resta nenhum destino executável, devolve o mesmo código de erro. Tornar o modelo novamente visível
produz efeitos no pedido seguinte. As substituições de visibilidade exclusivas para imagens não ocultam o modelo
de chat com o mesmo ID.

Esta definição individual do modelo é distinta das
[listas de permissões/negações de exposição de modelos](../routing/MODEL_EXPOSURE_LIST.md), que filtram
a apresentação no catálogo e os candidatos ao encaminhamento automático, mantendo o envio explícito. As permissões
de modelos das chaves de API continuam a ser aplicadas de forma independente. O modo predefinido de prefixo do
catálogo continua a ser `dual`.

### Variantes de modelos sem raciocínio

Para modelos Claude com capacidade de raciocínio, `/v1/models` também apresenta uma variante **sem raciocínio** cujo ID tem o prefixo `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

A seleção deste ID (por exemplo, numa configuração do Claude Code que anexa sempre um bloco `thinking`) é resolvida para o verdadeiro `<provider>/<model>` com o raciocínio suprimido — `thinking:{type:"disabled"}` no caminho `/v1/messages`, ou os campos `reasoning`/`reasoning_effort` removidos no caminho `/v1/chat/completions`. A variante só é apresentada para modelos da família Claude que suportam raciocínio **e** respeitam `disabled` (assim, por exemplo, são excluídos modelos exclusivamente adaptativos que rejeitem `disabled`). Os operadores podem forçar a ativação ou desativação da variante por modelo através de `ModelSpec.noThinkingAlias`.

## Geração de áudio do ElevenLabs

Configure uma ligação ao fornecedor `elevenlabs` no OmniRoute com a sua chave de API do ElevenLabs.
Os clientes autenticam-se com a respetiva chave do **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
o gateway fornece a chave armazenada do fornecedor como `xi-api-key`. Nunca envie uma chave do ElevenLabs
como token bearer do gateway.

| Método | Caminho                     | Resposta                                     | Categoria de endpoint da chave de API |
| ------ | --------------------------- | -------------------------------------------- | ------------------------------------- |
| POST   | `/v1/sound-generation`      | Bytes de áudio nativos                       | `elevenlabs`                          |
| POST   | `/v1/music`                 | Bytes de áudio nativos                       | `music`                               |
| POST   | `/v1/music/stream`          | Bytes de áudio em streaming                  | `music`                               |
| POST   | `/v1/music/detailed`        | Áudio multipart nativo e plano de composição | `music`                               |
| POST   | `/v1/music/detailed/stream` | Metadados SSE nativos e segmentos de áudio   | `music`                               |
| POST   | `/v1/music/plan`            | Plano de composição em JSON                  | `music`                               |

Estes endpoints complementam as rotas existentes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` e `/v1/speech-to-text`. Os campos JSON nativos
e os parâmetros de consulta, como `output_format` e `enable_logging`, são preservados.
As respostas de `/v1/music/detailed` mantêm os respetivos limites multipart; processe-as como multipart.
`/v1/music/detailed/stream` devolve `text/event-stream` com metadados de composição e
segmentos de áudio em base64 nos eventos SSE. As seis rotas suportam pedidos de verificação prévia CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Um efeito sonoro curto. Duração: 0,5 a 30 segundos.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# A duração da música é expressa em milissegundos: 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilize `/v1/music/stream` com o mesmo corpo JSON para entrega incremental de áudio. A composição
aceita exatamente um de `prompt` ou `composition_plan`; `/v1/music/plan` requer `prompt`
e aceita opcionalmente `source_composition_plan`. Os esquemas nativos preservam campos adicionais
do fornecedor, para que as versões do plano de composição e as opções de ajuste fino cheguem ao ElevenLabs.

O endpoint unificado `/v1/music/generations` também aceita `elevenlabs/music_v1`,
`elevenlabs/music_v2` e `elevenlabs/music_v2_5`. Com uma ligação ativa ao ElevenLabs,
estes modelos são apresentados pelo catálogo de música. Este endpoint devolve
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. O respetivo campo `duration` é expresso em
segundos e é mapeado para `music_length_ms`; um `music_length_ms` explícito tem precedência.
`instrumental` é mapeado para `force_instrumental`, tendo o campo nativo precedência.
Utilize os endpoints nativos de streaming para streaming e o endpoint nativo de composição
para pedidos baseados apenas num plano de composição.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

As restrições de endpoint, modelo, orçamento e ligação são aplicadas antes de uma chamada a montante. As rotas
nativas devolvem os códigos de estado e os corpos de erro do serviço a montante sem alterações, incluindo `402` para uma
restrição do plano e `429` para um limite de quota. Os cabeçalhos `character-cost`, `song-id`, `request-id` e `retry-after`
são preservados quando estão presentes. Um saldo de créditos gratuitos não garante o acesso a todos os
modelos de música, formatos de saída ou funcionalidades da API: o ElevenLabs determina a elegibilidade de cada pedido.
O endpoint unificado preserva os códigos de estado de erro no envelope de erro normalizado do OmniRoute.

Contratos a montante: [efeitos sonoros](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composição musical](https://elevenlabs.io/docs/api-reference/music/compose) e
[detalhes de música em streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Nós de fornecedores de reranking:** `POST /v1/rerank` também encaminha pedidos para nós de fornecedores compatíveis com OpenAI
> (oMLX, vLLM, Infinity, TEI por detrás de um gateway, …) endereçados como `<node-prefix>/<model>`. Os nós de
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) são sempre elegíveis, tal como os nomes de anfitrião
> indicados pelo operador em `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (por exemplo, o nome de um serviço Docker/Compose,
> como `http://reranker:8080/v1`; estes são contactados diretamente, nunca através de `HTTP(S)_PROXY` nem do
> proxy fixado de uma ligação). Os nós em qualquer outro
> anfitrião — uma máquina na LAN ou um par Tailscale — só são elegíveis quando o operador ativa o sinalizador de funcionalidade
> `RERANK_REMOTE_PROVIDER_NODES` **e** o URL base do nó cumpre a política de URLs de saída do fornecedor
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> O passo de reranking do motor de memória chama esta rota através de
> loopback, pelo que a mesma regra se aplica a `rerankProviderModel` nas definições de Memória.
>
> **Formatos de servidores locais:** o nó é chamado em `<base>/v1/rerank` e, em caso de 404, em `<base>/rerank`
> (Infinity, TEI). O corpo enviado ao serviço a montante inclui tanto a nomenclatura Cohere/OpenAI (`documents`,
> `return_documents`) como a nomenclatura TEI (`texts`, `return_text`), e a resposta do serviço a montante é
> normalizada para o envelope Cohere: a resposta simples do TEI `[{index, score, text}]`, a resposta `{results: [{index, score}]}`
> de gateways leves e a resposta ao estilo Voyage `{data: [...]}` são todas devolvidas ao cliente como
> `{results: [{index, relevance_score, document?}]}`, ordenadas por pontuação e limitadas a `top_n`.

> **Descoberta de nós de fornecedores:** os modelos num nó de fornecedor compatível com OpenAI aparecem em `GET /v1/models`
> sob o prefixo do nó. As linhas sem metadados de endpoint (típicas das listagens locais de `/v1/models`)
> herdam o `apiType` do nó, pelo que os modelos de um nó `embeddings` têm `type: "embedding"` e os modelos de um
> nó `rerank` têm `type: "rerank"`, em vez de assumirem chat por predefinição; um
> `supportedEndpoints` explícito numa linha sincronizada ou adicionada manualmente continua a ter precedência.

### Exa e Tavily `provider_options`

Exa e Tavily lêem campos específicos do fornecedor de um pacote com namespace: `provider_options.exa` (ou `provider_options["exa-search"]`) e `provider_options.tavily` (ou `provider_options["tavily-search"]`). Apenas as chaves abaixo são encaminhadas. Cada um é verificado em relação ao seu próprio esquema Zod em `open-sse/handlers/search/providerOptionsPassthrough.ts` e uma chave com o tipo errado é descartada. Qualquer outra chave é ignorada, incluindo auth, base URL, `stream` e `outputSchema`. As chaves simples utilizadas por outros fornecedores (`cx`, `depth`, ...) funcionam como anteriormente.

| Provedor | Campos de nível superior                                                                                                                                                                                                                                                                                                                                                  | Aninhado                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Exa.     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitivas planas), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` fundido com o `{ text: true, highlights: true }` padrão |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                     |

Vencem sempre os campos genéricos: `query`, `max_results`, `filters` (domínios), `country` e o tópico derivado de `search_type`. No Exa, `search_type: "news"` mantém `category: "news"`. Tavily também aceita `search_type: "finance"` (`topic: "finance"`).

O custo da pesquisa Firecrawl é registado por bloco iniciado de 10 resultados devolvidos, em 0,002 dólares (2 créditos) por bloco e pelo menos um bloco por chamada ( [facturação Firecrawl](https://docs.firecrawl.dev/billing) ): 11 resultados custam 0,004 dólares.

O `time_range` genérico chega agora a ambos os fornecedores: Exa obtém `startPublishedDate` (ISO timestamp) e Tavily obtém `start_date` (`YYYY-MM-DD`). Uma data explícita em `provider_options` substitui a data mapeada.

Os resultados do Exa mantêm `id`, `highlight_scores`, `summary`, `subpages`, `entities` e `extras` em `provider_raw`. Os resultados Tavily mantêm `images` e `favicon`.

O custo da pesquisa de linkup está registado em 0,005 dólares para `depth` `fast` e `standard` e 0,05 dólares para `deep` ( [linkup price](https://docs.linkup.so/pages/documentation/development/pricing) ), independentemente de `depth` vir `provider_options` ou das definições da ligação.

O Exa `type: "lite"` (Exa 3.0) aceita um conjunto mais pequeno de campos e rejeita todo o pedido quando qualquer outro campo é definido. Para Lite, `additionalQueries`, `systemPrompt` e todas as teclas `contents` exceto `text` e `highlights` são descartadas antes da chamada. Os obsoletos `subpages`, `subpageTarget`, `highlights.numSentences` e `highlights.highlightsPerUrl` já não são encaminhados.

A contabilidade de custos é o registo simples `costPerQuery`, exceto para o Exa, que segue o próprio preço do Exa: 0,007 dólares por chamada para `auto` (e o legado `fast`) ou 0,004 dólares para `lite` (e o legado `instant`), cobrindo 10 resultados; 0,001 dólares por cada resultado adicional; e 0,001 dólares por resultado devolvido quando `contents.summary` estiver definido. Tavily está registado em 1 crédito (0,008 dólares) para `search_depth` `basic`, `fast` e `ultra-fast`, e 2 créditos (0,016 dólares) para `advanced` ( [créditos Tavily API](https://docs.tavily.com/documentation/api-credits) ). Uma chamada com `auto_parameters: true` que Tavily atualiza para avançado ainda está registada com 1 crédito.

## Web Fetch API

Extraia conteúdo de um URL através de um fornecedor de obtenção de conteúdo Web configurado (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

O Parallel Extract (`parallel-search`, a mesma chave de API que o Parallel Search) devolve apenas
Markdown — qualquer outro `format` resulta num `400` — e limita o conteúdo a 100 000 caracteres. Quando
não é possível extrair a própria página de destino, o serviço a montante comunica-o numa resposta HTTP 200;
o OmniRoute apresenta esse erro como um `422` com uma mensagem fixa.

| Método | Caminho         | Descrição                                                   |
| ------ | --------------- | ----------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Obtém/extrai um URL — corpo validado por `v1WebFetchSchema` |

**Autenticação:** chave de API Bearer (`extractApiKey` + `isValidApiKey`). Política aplicada através de `enforceApiKeyPolicy`.

**Fallback com reconhecimento de quota (#8297):** quando não é indicado explicitamente um `provider`, o conjunto
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) é
percorrido por uma ordem de
prioridade fixa (preenchimento prioritário) — um fornecedor configurado, mas com limitação de taxa, é ignorado
em vez de interromper imediatamente o pedido, e uma falha repetível/de quota no serviço a montante
(HTTP 429 sempre; 402/403 para escalões gratuitos ao estilo de quota do Firecrawl/Tavily/TinyFish —
não para o Jina Reader e nunca para um simples pedido inválido 400) faz avançar para o
próximo fornecedor ainda não tentado e com credenciais, no momento do pedido. Quando todos os fornecedores do
conjunto estão esgotados, o endpoint devolve um único `429` (com um cabeçalho `Retry-After`)
em vez do anterior `400` genérico. Quando é solicitado um `provider`
explícito, **não** existe fallback silencioso — um fornecedor explícito com limitação
de taxa ou com falha apresenta o seu próprio erro (`429` se estiver sujeito a limitação de taxa; caso contrário,
o estado do serviço a montante).

## Transmissão por WebSocket

```bash
GET /v1/ws?handshake=1
```

Valida um handshake de atualização para WebSocket e devolve as mensagens de exemplo do protocolo de comunicação (`request`, `cancel`). Os frames WS propriamente ditos são processados pelo servidor WS incluído, fora da tabela de rotas do Next.js.

## Utilização autónoma (`/api/usage/om-usage`)

Qualquer chave de API pode consultar a **sua própria** utilização e quotas — sem autenticação de gestão. Este é o endpoint que um
cliente (CLI, o painel OmniCopilot) utiliza para mostrar ao titular de uma chave os respetivos gastos.

```bash
# Formato de texto (o contrato histórico — texto simples para um terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato estruturado — o que uma IU consome
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

A chave tem de ter **`allowUsageCommand`** ativado (desativado por predefinição — o gestor de chaves de API do
painel ativa-o individualmente para cada chave). Sem esta opção, o endpoint responde com `403`.

`?format=json` devolve uma estrutura discriminada, para que um chamador nunca leia um campo de dados de uma
recusa. Em caso de sucesso:

```jsonc
{
  "allowed": true,
  // presente apenas quando a chave optou por limites de utilização por chave (USD diários/semanais):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // o instantâneo da quota do fornecedor selecionado, ou null quando ainda não existe nada em cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // o instantâneo de cada ligação, para que uma IU possa apresentar vários fornecedores lado a lado:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Em caso de recusa (`401` chave inválida / `403` não permitido), a mesma rota devolve
`{ "allowed": false, "error": { "message": "…" } }` — um `personal`/`provider` presente mas vazio
(chave permitida, ainda sem informação obtida) é um estado diferente de uma recusa, e apenas o formato JSON
permite distingui-los.

**Autenticação:** a própria chave de API Bearer do chamador, validada com `isValidApiKey` — esta _não_ é a
interface de gestão (`/api/keys/…`), que permanece protegida por `requireManagementAuth`.

### Percentagens de quota brutas vs. ajustadas ao limite de corte

Ao consumir `/api/usage/om-usage`, os chamadores devem ter em conta a diferença entre as
percentagens apresentadas pela **saída de texto simples** e pela **saída JSON** estruturada:

| Aspeto                   | Formato de texto simples (`/api/usage/om-usage` / `@@om-usage`)                                                | Formato JSON (`?format=json`)                                                         |
| :----------------------- | :------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------ |
| **Campo de saída**       | `NN% left` (por exemplo, `20% left`)                                                                           | `provider.quotas` / `providers[].quotas`                                              |
| **Medição**              | **Disponibilidade utilizável ajustada ao limite de corte**: capacidade restante acima do limite de corte       | **Quota bruta a montante**: medição não ajustada do fornecedor                        |
| **Ajuste ao corte**      | Ajustada através de `effectiveRemainingPercent()` para que a reserva protegida seja apresentada como `0% left` | Nenhum (valores brutos do instantâneo conforme comunicados pelo fornecedor)           |
| **Dados do limite**      | Incorporados na percentagem apresentada                                                                        | Armazenados em `quotaWindowThresholds` por ligação (ou predefinições do servidor)     |
| **Consumidor principal** | CLIs interativas, pedidos no terminal, operadores humanos                                                      | Integrações programáticas, painéis, análises, sistemas de acompanhamento de faturação |

#### A fórmula de ajuste ao limite de corte

O OmniRoute suporta limites de corte proativos de quota para impedir o esgotamento a montante (configurados através de
`quotaWindowThresholds` da ligação, das predefinições do fornecedor ou das definições globais de resiliência). Quando um limite de corte
(por exemplo, `cutoff = 25%`) está ativo numa janela de quota, o processador de texto calcula a disponibilidade restante da seguinte forma:

- Se `remaining <= cutoff`: devolve `0%`.
- Se `remaining > cutoff`: devolve `((remaining - cutoff) / (100 - cutoff)) * 100`.

A saída de texto formatada arredonda este valor para o número inteiro mais próximo (`Math.round(...)`).

#### Exemplo ilustrativo

Considere uma janela de fornecedor com **60% de utilização bruta** (logo, **40% de quota bruta restante**) e um
limite de corte configurado de **25% de quota restante**:

| Representação                     | Cálculo                                            | Restante |          Utilização implícita           |
| :-------------------------------- | :------------------------------------------------- | :------: | :-------------------------------------: |
| **JSON bruto (`?format=json`)**   | Instantâneo a montante (`quotas[window]`)          | **40%**  |                 **60%**                 |
| **Formato de texto (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (ao calcular `100 - remaining`) |

- **Por que motivo o texto mostra 20% restante:** Dos 40% de quota física restantes na conta, 25% estão reservados pela
  política de corte. O chamador dispõe apenas de 15% dos 75% de margem utilizável restante antes de o router deixar de
  encaminhar pedidos para esta ligação. O ajuste garante que a ligação assinala o esgotamento (`0% left`) exatamente quando
  o encaminhamento termina.
- **Por que motivo o JSON preserva os valores brutos:** O payload JSON devolve o instantâneo exato do fornecedor (`UsageSnapshot`)
  para que as ferramentas externas tenham acesso à utilização real a montante e aos
  `quotaWindowThresholds` ao nível da ligação, sem um ajuste com perda de informação efetuado pelo servidor.

#### Orientações para a migração dos consumidores

Se uma integração externa (como um plugin de editor ou uma extensão de agente) extraía anteriormente os dados do endpoint
de texto (`NN% left`) e calculava a percentagem utilizada como `100 - NN`, a migração para `?format=json` significa que:

- A leitura dos valores JSON em bruto refletirá o **consumo real a montante** (60% utilizado no exemplo acima).
- Se a integração pretender preservar a semântica da disponibilidade utilizável do endpoint de texto, poderá avaliar
  a fórmula efetiva do valor restante no lado do cliente, utilizando `quotaWindowThresholds` para substituições ao nível da ligação.

## Cache semântica

```bash
# Obter estatísticas da cache
GET /api/cache/stats

# Limpar todas as caches
DELETE /api/cache/stats
```

Exemplo de resposta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impacto na latência

Um ACERTO na cache semântica fornece a resposta a partir da cache **sem uma
chamada a montante**, pelo que o valor comunicado em `X-OmniRoute-Response-Latency` é próximo de zero
(independentemente da latência original a montante). Os clientes sensíveis à latência
(benchmarking, monitorização de p50/p99) devem verificar o cabeçalho de resposta
`X-OmniRoute-Cache-Latency`:

| Valor       | Significado                                                             |
| ----------- | ----------------------------------------------------------------------- |
| `synthetic` | Resposta fornecida pela cache; a latência não é o tempo real a montante |
| _(ausente)_ | Resposta de uma chamada real a montante                                 |

### Ignorar a cache por chave

As chaves de API podem optar por não efetuar leituras da cache semântica através de `cacheDefaultMode`:

| Valor    | Comportamento                                                                |
| -------- | ---------------------------------------------------------------------------- |
| `legacy` | Comportamento normal da cache (predefinição)                                 |
| `bypass` | Ignorar totalmente a consulta da cache; utilizar sempre o serviço a montante |

Defina na criação da chave (`POST /api/keys`) ou na atualização (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Ignorar a cache por pedido

Qualquer pedido pode ignorar a cache, independentemente das definições da chave:

```
X-OmniRoute-No-Cache: true
```

Para modelos sincronizados/importados, `PUT /api/provider-models` aceita `provider`, `modelId` e
`maxOutputTokenOverride`: um número inteiro positivo define o limite manual de tokens de saída, e `null`
limpa-o para restaurar a predefinição. `GET /api/provider-models?provider=<provider>` devolve estes
valores em `modelOutputOverrides`, incluindo modelos sem uma linha de modelo personalizado. A substituição
utiliza a capacidade de execução `max_output_tokens` e mantém-se após uma nova sincronização do modelo. A página
do fornecedor compatível com OpenAI disponibiliza os mesmos controlos de edição/limpeza e assinala os modelos
com suporte explícito para visão.

Os nós personalizados de Chat Completions adaptam as exclusões explícitas de raciocínio ao backend a montante. Um
teste de ligação bem-sucedido seleciona automaticamente os controlos de modelo de chat para cada ID de modelo exato
cuja entrada `/models` comprove um valor `owned_by` reconhecido: `vllm`, `sglang` ou `llamacpp`.
Os wrappers transparentes compatíveis com OpenAI podem preservar a entrada original do modelo dentro de um objeto
`openai` aninhado; a deteção segue até três desses invólucros. Os modelos com propriedade em falta, desconhecida ou
em conflito mantêm o comportamento normal do OpenAI. A deteção reutiliza o pedido de catálogo existente,
não gera tokens de conclusão e é invalidada quando o endpoint da ligação é alterado.

Para fixar o comportamento num backend que não exponha esses metadados, utilize a API existente de atualização
parcial do fornecedor:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envie esse corpo com `PUT /api/providers/<connection-id>`. Nessa ligação, um esforço de
raciocínio explícito de `none` é enviado como `chat_template_kwargs.thinking=false` e
`chat_template_kwargs.enable_thinking=false`. Os valores nativos explícitos do modelo continuam a prevalecer,
a menos que uma regra de raciocínio do lado do servidor imponha um esforço. A definição aplica-se apenas quando uma
ligação personalizada compatível com OpenAI envia um corpo de Chat Completions; os pedidos Responses e os fornecedores
normais mantêm o formato nativo dos respetivos pedidos. Defina `reasoningControl` como `openai` para forçar a passagem direta
normal de `reasoning_effort` do OpenAI, ou omita-o/defina-o como `null` para utilizar a deteção automática.

Os pedidos do classificador de modo automático do Claude Code desativam, por predefinição, o raciocínio nativo quando
não contêm controlos explícitos de raciocínio. A deteção utiliza o marcador de sistema do classificador em pedidos no formato
Claude, e não os nomes dos modelos nem os limites de conclusão. Os controlos explícitos do corpo, os cabeçalhos de esforço/raciocínio
suportados, as regras de encaminhamento e o esforço resolvido do modelo mantêm a respetiva prioridade existente. Ambas as fases do
classificador preservam os respetivos prompts, limites de conclusão, sequências de paragem e veredictos reais de permissão do serviço
a montante; a segunda fase ainda pode produzir o raciocínio visível solicitado como texto normal.

### Versão e Canal de Lançamento

```bash
GET /api/system/version
```

Rota de gestão acessível apenas através de loopback (autenticação de administrador). Devolve a versão em execução, a versão publicada mais recente e o estado da atualização automática. `releaseChannel` e `channels` são campos adicionais (linha 3.8.54); `channel` mantém o seu significado — o modo de implementação utilizado pelo atualizador do painel (`npm`, `source` ou `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal npm da compilação em execução: `nightly` para versões `-nightly.*`,
  `next` para outros pré-lançamentos (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para uma versão estável de uma
  versão principal anterior à de `channels.latest`; caso contrário, `latest`. As mesmas regras que
  `scripts/release/dist-tag.mjs`, que escolhe a dist-tag npm no momento da publicação.
- `channels` — versão mais recente publicada de cada dist-tag, obtida através de `npm view omniroute dist-tags` (com recurso
  alternativo a HTTP do registo), armazenada em cache com o mesmo TTL de 10 minutos que `latest`. `latest` está sempre presente
  (recorre ao campo `latest` e, em seguida, a `"unavailable"`); `next`, `nightly` e `lts` aparecem
  apenas quando essa dist-tag existe. Um pedido `Cache-Control: no-cache` atualiza ambas as consultas.

O modelo de canais (`latest` = v3 até à disponibilidade geral da versão 4.0, `next` = rc, `nightly` = compilações de `develop`,
`lts` = correções da v3 após a disponibilidade geral da versão 4.0) é descrito em `docs/ops/RELEASE_STRATEGY.md`.

## Transcrição de Áudio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transcreva ficheiros de áudio utilizando qualquer fornecedor STT configurado. O primeiro segmento
do caminho seleciona o fornecedor nativo (`openai/…`, `deepgram/…`). Os gateways que
reexportam o modelo de outro fornecedor utilizam um id qualificado
(`openrouter/deepgram/nova-3`).

**Pedido:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Resposta:**

```json
{
  "text": "Olá, este é o conteúdo de áudio transcrito.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Exemplos de ids de modelos:** `openai/whisper-1` (requer uma chave da OpenAI),
`openrouter/deepgram/nova-3` (requer uma chave da OpenRouter),
`deepgram/nova-3` (requer uma chave nativa da Deepgram). Um pedido simples
`deepgram/nova-3` **não** utiliza a OpenRouter.

**Formatos suportados:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Limites de tokens

Orçamentos de **tokens** por chave de API (distintos do Orçamento baseado em USD acima). Aplicados em linha no percurso do pedido: quando a utilização da janela atual de uma chave atinge o respetivo limite, os pedidos são rejeitados com `429 Too Many Requests`. Os limites podem ser aplicados a um `model` específico, a um `provider` ou `global`mente em toda a chave; quando vários limites correspondem a um pedido, prevalece o mais restritivo.

```bash
# Listar os limites de tokens de uma chave (inclui a utilização atual da janela)
GET /api/usage/token-limits?apiKeyId=key-123

# Criar ou atualizar um limite de tokens
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Eliminar um limite de tokens por id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Notas sobre o esquema** (`setTokenLimitSchema`): `apiKeyId` e `scopeType` (`model` | `provider` | `global`) são obrigatórios. `scopeValue` é obrigatório, exceto quando `scopeType` é `global` (por exemplo, um id de modelo para o âmbito `model` ou um id de fornecedor para o âmbito `provider`). `tokenLimit` tem de ser um número inteiro positivo (convertido a partir de uma string). Opcional: `id` (omitir para criar, fornecer para atualizar), `resetInterval` (`daily` | `weekly` | `monthly`, predefinição `monthly`), `resetTime` (`HH:MM`), `enabled` (predefinição `true`). As respostas `GET` enriquecem cada limite com `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` e `nextResetAt`. Este é um endpoint da classe de gestão (autenticação aplicada centralmente pelo pipeline de autorização).

## Processamento de pedidos

1. O cliente envia um pedido para `/v1/*`
2. O processador da rota chama `handleChat`, `handleEmbedding`, `handleAudioTranscription` ou `handleImageGeneration`
3. O modelo é resolvido (fornecedor/modelo direto ou alias/combo)
4. As credenciais são selecionadas a partir da base de dados local, com filtragem pela disponibilidade da conta
5. Para chat: `handleChatCore` verifica a cache semântica/de assinatura e resolve as definições de compressão do combo
6. A compressão proativa é executada antes da tradução do fornecedor quando está ativada (`lite`, Caveman, RTK ou empilhada)
7. O executor do fornecedor envia o pedido a montante
8. A resposta é novamente traduzida para o formato do cliente (chat) ou devolvida tal como está (embeddings/imagens/áudio)
9. A utilização, as análises de compressão e os registos de pedidos são guardados
10. Em caso de erros, é aplicada uma alternativa de acordo com as regras do combo

Referência completa da arquitetura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resiliência (alargada)

O OmniRoute disponibiliza três mecanismos independentes para falhas temporárias; os endpoints de gestão abaixo permitem aos operadores consultar e substituir as respetivas configurações:

| Âmbito                  | Armazenamento do estado                          | Consulta                                  | Reposição / limpeza                                        |
| ----------------------- | ------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------- |
| Disjuntor do fornecedor | `domain_circuit_breakers` + em memória           | `/api/monitoring/health`                  | `POST /api/resilience/reset`                               |
| Espera da ligação       | `rateLimitedUntil` nas ligações dos fornecedores | `/api/rate-limits`, `/api/providers/[id]` | (reativação diferida; limpar através do PUT do fornecedor) |
| Bloqueio do modelo      | Registo de disponibilidade de modelos em memória | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                   |

`PATCH /api/resilience` aceita substituições do disjuntor do fornecedor em `providerBreaker.oauth` e `providerBreaker.apikey`. Cada perfil suporta `degradationThreshold`, `failureThreshold` e `resetTimeoutMs`; os mesmos campos estão disponíveis em Painel → Definições → Resiliência.

```bash
# Limpar o bloqueio de um único modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Remover todos os bloqueios
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Para obter a referência conceptual completa e os valores predefinidos do disjuntor, consulte [`CLAUDE.md`](../../CLAUDE.md) → "Estado de Execução da Resiliência" e [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Fila de limitação de taxa e mecanismo de segurança de ativação automática

- **Caminho de escrita suportado**: `POST /api/rate-limits` com o corpo `{"connectionId": "<id>", "enabled": true|false}` é o endpoint de gestão suportado para ativar ou desativar a proteção contra limites de taxa numa ligação. `PUT /api/providers/[id]` não modifica nem inverte deliberadamente `rateLimitProtection` (#11278).
- **Semântica de `enabled: false`**: Definir `enabled: false` remove a proteção explícita da ligação, mas **não** exclui uma ligação ativa com chave de API do mecanismo de segurança global de ativação automática (`autoEnableApiKeyProviders = true`). Em `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` e `undefined` são equivalentes; as ligações ativas com chave de API sem proteção explícita permanecem protegidas pelo mecanismo de segurança de ativação automática.
- **Desativação global**: Para executar ligações com chave de API sem filas de limitação de taxa, desative globalmente o mecanismo de segurança através de `RATE_LIMIT_AUTO_ENABLE=false` (variável de ambiente) ou `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Definições → Resiliência / `PATCH /api/resilience`).

## Servidor A2A

O OmniRoute disponibiliza um endpoint A2A (agente para agente) JSON-RPC 2.0, além de um wrapper REST para utilização em inspeção/painéis.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opcional, exceto se OMNIROUTE_API_KEY estiver definida
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Métodos suportados (todos condicionados por `settings.a2aEnabled`):

| Método           | Descrição                                                                |
| ---------------- | ------------------------------------------------------------------------ |
| `message/send`   | Execução síncrona de competências; devolve `{task, artifacts, metadata}` |
| `message/stream` | Execução SSE em streaming do mesmo conjunto de competências              |
| `tasks/get`      | Obtém uma tarefa através de `taskId`                                     |
| `tasks/cancel`   | Cancela uma tarefa através de `taskId`                                   |

Competências incorporadas: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

```bash
GET /.well-known/agent.json
```

Devolve o cartão público do agente A2A (nome, descrição, capacidades, catálogo de competências e esquema de autenticação) — armazenado publicamente em cache durante 1 h. Não requer autenticação.

## Autenticação

Consulte [Autenticação de Gestão](../guides/MANAGEMENT-AUTH.md) para conhecer as quatro
famílias de credenciais (sessão do painel, token da CLI local, Token de Acesso
`oma_live_…`, chave de API com âmbito de gestão) e as diferenças relativamente às chaves de inferência.

- As rotas do painel (`/dashboard/*`) utilizam o cookie `auth_token`
- O início de sessão utiliza o hash da palavra-passe guardada; em alternativa, utiliza `INITIAL_PASSWORD`
- `requireLogin` pode ser ativado ou desativado através de `/api/settings/require-login`
- As rotas `/v1/*` exigem opcionalmente uma chave de API Bearer quando `REQUIRE_API_KEY=true`
- Nesta referência, «token de gestão» / «chave de API com âmbito de gestão» refere-se a uma das famílias descritas nesse guia — não a um tipo adicional de segredo não definido

> **Alteração incompatível (v3.8.0)** — `/api/v1/agents/tasks/*` e os endpoints de gestão do período de espera exigem agora **autenticação de gestão** (cookie `auth_token` do painel ou uma chave de API com âmbito de gestão). Os clientes que anteriormente chamavam estas rotas sem autenticação receberão `401 Unauthorized`. Consulte o commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
