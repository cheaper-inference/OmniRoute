> **TL;DR**: O OmniRoute monitoriza a utilização de tokens de cada pedido, calcula o custo, aplica a quota por chave de API e apresenta análises no painel. Este guia explica como tudo funciona.

**Fontes:**

- `open-sse/services/usage.ts` (~70KB) — monitorização principal da utilização
- `src/lib/usageAnalytics.ts` (~10KB) — agregação para o painel
- `src/lib/db/quotaSnapshots.ts` — dados históricos de quotas
- `src/lib/db/usage*.ts` — vários módulos de BD relacionados com a utilização

---

## Visão geral

Cada pedido que passa pelo OmniRoute gera um **registo de utilização** que inclui:

- **Identidade**: qual a chave de API, fornecedor, modelo e combinação
- **Tokens**: tokens de prompt, tokens de conclusão, tokens em cache e total
- **Custo**: montante em USD (calculado a partir dos dados de preços)
- **Temporização**: latência, carimbos de data/hora de início e fim
- **Estado**: sucesso, erro, limitação de taxa, etc.

Estes registos são agregados em **análises**, mantidos como **instantâneos de quota** e utilizados para aplicar **limites de orçamento por chave**.

```
Pedido ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                      análises  quota  faturação
                       (painel) (aplicar) (exportar)
```

## O que é registado

O serviço `usage.ts` captura um **evento de utilização** para cada pedido:

| Campo              | Tipo    | Origem                                                            |
| ------------------ | ------- | ----------------------------------------------------------------- |
| `id`               | string  | UUID gerado no momento do registo                                 |
| `apiKeyId`         | string  | A chave de API que iniciou o pedido                               |
| `provider`         | string  | ID do fornecedor (openai, anthropic, etc.)                        |
| `model`            | string  | ID do modelo (gpt-5, claude-opus-4-6, etc.)                       |
| `comboId`          | string? | ID da combinação, se encaminhado através de uma combinação        |
| `promptTokens`     | number  | Da resposta do fornecedor a montante                              |
| `completionTokens` | number  | Da resposta do fornecedor a montante                              |
| `cachedTokens`     | number  | Tokens encontrados na cache (cache de prompts da Anthropic, etc.) |
| `totalTokens`      | number  | prompt + conclusão                                                |
| `costUsd`          | number  | Calculado a partir dos dados de preços                            |
| `latencyMs`        | number  | Duração total do pedido                                           |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`        |
| `errorClass`       | string? | Classe de erro se o estado != sucesso                             |
| `timestamp`        | string  | ISO 8601 UTC                                                      |
| `metadata`         | object  | Dados personalizados injetados por plugins                        |

### De onde vêm os tokens

Os tokens são extraídos da resposta do fornecedor a montante no **processador de respostas**:

```ts
// De open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Para os fornecedores que não devolvem dados de utilização (alguns fornecedores baseados em cookies da Web), o OmniRoute **estima** os tokens utilizando uma heurística de `~4 chars per token` (consulte `open-sse/services/autoCombo/pipelineRouter.ts`).

### Tokens em cache

O OmniRoute monitoriza `cached_tokens` separadamente de `prompt_tokens` porque:

- A cache de prompts da Anthropic cobra uma tarifa reduzida pelos tokens em cache (10% da tarifa normal)
- Alguns fornecedores devolvem `cache_read_input_tokens`, aos quais deve ser aplicado um preço diferente
- A análise pode apresentar a **taxa de acertos da cache** = `cached_tokens / prompt_tokens`

### Diagnóstico dos escalões de escrita na cache

O painel de estado da cache de prompts no painel de análise distingue as escritas na cache
de 5 minutos e de 1 hora comunicadas pelo fornecedor. Os campos da Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` e
`usage.cache_creation.ephemeral_1h_input_tokens` são preservados durante a conversão dos dados de utilização com e
sem streaming e armazenados com os resumos dos registos de chamadas. O total combinado
de escritas na cache não é adicionado a esses escalões uma segunda vez.

As chamadas com apenas um contador combinado de escritas, incluindo registos antigos, têm um escalão
desconhecido. Uma discriminação parcial mantém o restante não atribuído como desconhecido; os contadores inválidos ou
contraditórios são assinalados em vez de lhes ser atribuído silenciosamente um TTL. Os indicadores de
TTL do lado do pedido não constituem prova de um escalão faturado.

A estimativa de escrita equivalente à API apresentada no painel abrange apenas os escalões comunicados com preço definido, não
a totalidade do pedido. Para os preços nativos dos modelos Claude/Anthropic, utiliza 1,25 vezes a
tarifa de entrada para escritas de 5 minutos e o dobro da tarifa de entrada para escritas de 1 hora. A ausência de
preços é apresentada como indisponível, não como zero. Os preços são capturados quando cada nova chamada é registada;
os preços dos registos históricos não são recalculados. Assim, as contas com subscrição podem ter uma
estimativa equivalente à API sem que esse montante seja efetivamente cobrado ou deduzido da quota
da subscrição. Os cálculos existentes de quota, orçamento e custos exatos do fornecedor permanecem inalterados.

Estes diagnósticos utilizam o resumo existente de estado da cache, com limites definidos, e a retenção dos registos
de chamadas. Não alteram os valores predefinidos de TTL dos pedidos, o encaminhamento nem a seleção de contas.
A captura do TTL solicitado pelo cliente e do TTL de saída efetivo no ponto de envio ao
fornecedor fica adiada; este painel apresenta os escalões dos comprovativos de utilização, não o TTL de saída efetivo.

Implementação: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` e `open-sse/utils/cacheWriteUsage.ts`.

## Cálculo de custos

Os custos são calculados a partir dos **dados de preços** sincronizados com o LiteLLM (`src/lib/pricingSync.ts`):

| Modelo            | Entrada $/1M | Saída $/1M | Em cache $/1M |
| ----------------- | ------------ | ---------- | ------------- |
| gpt-5             | $2.50        | $10.00     | —             |
| claude-opus-4-6   | $15.00       | $75.00     | $1.50         |
| claude-sonnet-4-5 | $3.00        | $15.00     | $0.30         |
| gemini-2.5-pro    | $1.25        | $10.00     | —             |

A fórmula de cálculo do custo (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Porquê subtrair os tokens em cache do prompt?** A parte em cache tem um preço separado; aplicar o preço de entrada ao prompt completo resultaria numa contagem excessiva.

### Sincronização de preços

Os dados de preços são sincronizados automaticamente com o LiteLLM através do endpoint `/api/pricing/sync` (acionado pela tarefa cron integrada, e não por uma variável de ambiente acessível ao utilizador):

```bash
# Acionamento manual
curl -X POST http://localhost:20128/api/pricing/sync
```

Para modelos sem dados de preços, o OmniRoute recorre à **estimativa do custo** utilizando tarifas médias internas (obtidas a partir dos dados de preços do LiteLLM).

## Agregação por Intervalo de Datas

O módulo `usageAnalytics.ts` calcula os widgets do painel a partir de dados de utilização em bruto. Suporta 7 intervalos de tempo:

| Intervalo | Janela                               | Caso de utilização                 |
| --------- | ------------------------------------ | ---------------------------------- |
| `1d`      | Últimas 24 horas                     | Deteção de picos de custo por hora |
| `7d`      | Últimos 7 dias                       | Revisão semanal                    |
| `30d`     | Últimos 30 dias                      | Faturação mensal                   |
| `90d`     | Últimos 90 dias                      | Análise trimestral                 |
| `ytd`     | Desde 1 de janeiro do ano atual      | Acompanhamento do orçamento anual  |
| `all`     | Todo o período                       | Estatísticas de todo o período     |
| `custom`  | Início/fim definidos pelo utilizador | Auditorias, consultas ad hoc       |

### Widgets do Painel Calculados

Para qualquer intervalo de datas, a camada de análise calcula:

| Widget                          | Descrição                                                       |
| ------------------------------- | --------------------------------------------------------------- |
| **Cartões de resumo**           | Total de pedidos, custo total, total de tokens, taxa de sucesso |
| **Gráfico de tendência diária** | Custo + tokens por dia, empilhados por modelo                   |
| **Mapa de calor de atividade**  | Grelha de hora do dia × dia da semana, cor = número de pedidos  |
| **Distribuição por modelo**     | Gráfico circular do custo por modelo                            |
| **Distribuição por fornecedor** | Gráfico de barras dos pedidos por fornecedor                    |
| **Principais chaves de API**    | Tabela das 10 chaves com maior custo                            |
| **Análise de erros**            | Taxa de erros ao longo do tempo, principais classes de erros    |

### Acesso Programático

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // registos do histórico de utilização
  "7d",                 // intervalo de tempo: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // mapa de ligações do fornecedor (connectionId → nome da conta)
  {
    startDate: "2025-01-01",  // opcional: para o intervalo "custom"
    endDate: "2025-06-01",   // opcional: para o intervalo "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (cêntimos)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Aplicação de Quotas

A quota por chave de API é aplicada em dois pontos:

1. **Limite flexível** (`quotaWarnAt`): aviso no painel quando a utilização ultrapassa o limiar
2. **Limite rígido** (`quotaLimit`): pedido rejeitado com HTTP 429 quando o limite é ultrapassado

### Configuração

```ts
// Por chave de API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — mostrar aviso
  quotaLimit: 10_00,    // $10.00 — bloqueio
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Fluxo de Aplicação

```
Pedido ──▶ quotaCheck()
              │
              ├── Dentro do limite?  ──▶ permitir
              │
              └── Acima do limite?  ──▶ 429 Too Many Requests
                                   com cabeçalho Retry-After
```

### Instantâneos de Quota

A tabela `quotaSnapshots` armazena o **estado histórico da quota** para análise de tendências:

| Campo | Descrição |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | A chave que está a ser acompanhada |
| `window` | "day" | "week" | "month" |
| `used` | Custo utilizado nesta janela (cêntimos) |
| `limit` | O limite (cêntimos) |
| `resetAt` | Quando a janela é reiniciada |
| `createdAt` | Quando o instantâneo foi criado |

Os instantâneos são criados **em cada pedido** com custo > 0 e utilizados para:

- Apresentar a barra de progresso da quota no painel
- Mostrar gráficos de tendências da quota de 30 dias
- Acionar alertas quando a utilização se aproxima do limite

## Retenção e limpeza

Os dados de utilização aumentam cerca de 1-10KB por pedido. Em grande escala, este volume pode ser significativo.

### Definições de retenção

A retenção do histórico de utilização é configurada nas Definições da base de dados na interface de utilizador ou através de `/api/settings/database`.

Por predefinição, o histórico de utilização é conservado durante **90 dias**.

### Limpeza

Os registos antigos são eliminados por `src/lib/db/cleanup.ts`:

- Acionado pelo processo cron em segundo plano
- Elimina de `usage_history` os registos mais antigos do que o período de retenção configurado em `usageHistory`

### Estimativa de armazenamento

| Taxa de pedidos     | Armazenamento de 30 dias | Armazenamento de 90 dias |
| ------------------- | ------------------------ | ------------------------ |
| 100 pedidos/dia     | ~3MB                     | ~9MB                     |
| 1,000 pedidos/dia   | ~30MB                    | ~90MB                    |
| 10,000 pedidos/dia  | ~300MB                   | ~900MB                   |
| 100,000 pedidos/dia | ~3GB                     | ~9GB                     |

Para volumes de tráfego muito elevados, considere:

- Reduzir o período de retenção nas Definições da base de dados
- Utilizar `aggregated_metrics` em vez dos registos em bruto (apenas para análises)

## Dicas de otimização de custos

### 1. Utilize o modelo adequado

```bash
# Resposta rápida — utilize uma opção económica + rápida
curl -d '{"model":"auto/fast","messages":[...]}'

# Tarefa complexa — privilegie a qualidade
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Ative a cache

A cache de prompts da Anthropic permite poupar **90% no contexto repetido**:

```ts
// A cache é automática — basta incluir o mesmo prompt de sistema extenso
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Será colocado em cache automaticamente
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Utilize a compressão

A compressão RTK + Caveman permite poupar **15-95% em sessões com utilização intensiva de ferramentas**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Defina quotas por chave

Defina sempre `quotaLimit` para evitar custos descontrolados:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Limite de $10/mês
```

### 5. Audite os maiores consumidores

Utilize o painel de controlo ou **`/api/usage/analytics`** para agrupar por chave de API e ordenar por custo:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Resolução de problemas

### "O custo é superior ao esperado"

1. Consulte **`/api/usage/analytics?groupBy=model`** — identifique o modelo dispendioso
2. Consulte **`/api/usage/analytics?groupBy=apiKey`** — identifique o consumidor com utilização intensiva
3. Verifique se os dados de preços estão atualizados: `POST /api/pricing/sync`

### "Faltam registos"

- Verifique as definições de retenção da base de dados em Painel de controlo → Base de dados → Limpeza — os registos antigos são eliminados pela tarefa de limpeza periódica (`src/lib/db/cleanup.ts`)
- Verifique se existem erros em `src/lib/db/usage*.ts` — as falhas de escrita na base de dados são registadas, mas não são apresentadas
- Verifique se o pedido chegou efetivamente a `chatCore` — verifique o encaminhamento combinado

### "A quota não está a ser aplicada"

- Verifique a definição `quotaLimit` da chave
- Verifique se `quotaWindow` está definido corretamente
- Procure registos `quotaSnapshots` — devem ser criados em cada pedido
