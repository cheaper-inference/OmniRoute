> **Resumindo**: `open-sse/` é o motor principal de streaming que processa todos os pedidos a LLM no OmniRoute. Contém ~1.400 ficheiros que implementam o pipeline de pedidos, executores, serviços, servidor MCP e camada de tradução. Este guia explica como as diferentes partes se integram.

**Fonte:** `open-sse/` (pacote do workspace, ~1.440 ficheiros `.ts` que não são de teste)

---

## Porquê um Pacote de Workspace Separado?

`open-sse/` é um **workspace autónomo** no monorepo do OmniRoute por vários motivos:

1. **Reutilização** — `open-sse` é publicado como `@omniroute/open-sse` no npm, pelo que outros projetos podem utilizá-lo de forma independente
2. **Limites bem definidos** — o motor de streaming está desacoplado da camada de UI/BD específica do OmniRoute
3. **Desempenho** — o motor não tem dependências do Next.js, permitindo arranques a frio mais rápidos em contextos de CLI/serverless
4. **Controlo de versões** — `open-sse` pode publicar versões segundo o seu próprio calendário

```json
// package.json
"workspaces": ["open-sse"]
```

## O Pipeline de Pedidos

Todos os pedidos a LLM passam por um **pipeline de 5 etapas**:

```
                              ┌──────────────┐
   Pedido HTTP                │  1. ENCAMINHAR│  resolução de combinações, seleção do modelo
   (rota do Next.js)          └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRADUZIR │   conversão de formatos (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXECUTAR │   executor do fornecedor, HTTP, repetição, disjuntor
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAMING│   transformação SSE, contrapressão
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REGISTAR │   acompanhamento da utilização, registo de chamadas, classificação de erros
                              └──────┬───────┘
                                     │
                                     ▼
                              Resposta HTTP (SSE ou JSON)
```

### Etapa 1: Encaminhar (services/combo.ts)

**Ponto de entrada**: `handleComboChat()` em `services/combo.ts`

Resolve o pedido para um tuplo concreto `(provider, model, account, credentials)`:

- Procura a combinação pelo ID (ou cria uma combinação virtual para modelos `auto/*`)
- Aplica a estratégia de encaminhamento (prioridade, ponderada, round-robin, etc.)
- Exclui fornecedores que não estejam operacionais (disjuntor)
- Escolhe o próximo destino viável

Para modelos `auto/*`, esta etapa também:

- Executa o algoritmo de **pontuação de 16 fatores** (`services/autoCombo/`)
- Seleciona um par `provider+model` com base no estado, custo, latência, etc.

### Etapa 2: Traduzir (translator/)

Se o formato de origem (por exemplo, OpenAI) for diferente do formato de destino (por exemplo, Claude), o pedido é **traduzido**:

- Prompt de sistema → mensagem de sistema
- Definições de ferramentas → formato de ferramentas específico do fornecedor
- Parâmetros de raciocínio/pensamento → equivalentes específicos do fornecedor
- Normalização das funções das mensagens (`developer` → `system` para sistemas que não sejam OpenAI)

O `translator/index.ts` expõe:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Etapa 3: Executar (executors/)

**Ponto de entrada**: `getExecutor(providerId).execute(request, options)`

Todos os fornecedores utilizam `DefaultExecutor` (`executors/default.ts`) através do recurso alternativo da fábrica `getExecutor()`. O executor:

- Constrói o URL a montante (`buildUrl()`)
- Adiciona cabeçalhos específicos do fornecedor (`buildHeaders()`)
- Transforma o corpo do pedido (`transformRequest()`)
- Envia o pedido HTTP com repetição + recuo exponencial
- Gere a atualização da autenticação, caso seja necessária (fornecedores OAuth)

Todos os executores estendem `BaseExecutor` (`executors/base.ts`, 1170 linhas de código), que disponibiliza:

- Lógica de repetição comum
- Integração com proxy
- Integração com disjuntor
- Hooks de registo da utilização

### Etapa 4: Streaming (utils/stream.ts)

Para respostas em streaming, o executor devolve um **ReadableStream**. O processador:

- Encaminha os dados através de uma transformação SSE (`createSSETransformStreamWithLogger`)
- Aplica pings periódicos para detetar ligações inativas
- Gere corretamente a desconexão do cliente (`pipeWithDisconnect`)
- Transforma SSE → JSON para clientes sem streaming

Para respostas sem streaming, o executor devolve um objeto JSON analisado, que é transmitido sem alterações.

### Etapa 5: Registar (services/usage.ts)

Após a resposta (com êxito ou falha), a utilização é registada:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` da resposta
- `cost_usd` calculado a partir dos dados de preços
- `latency_ms`, `status`, `error_class` em caso de falha
- Persistida na tabela `usage_history`

Os artefactos de registo de chamadas (se ativados) são escritos em `${DATA_DIR}/call_logs/`.

## Aprofundamento dos ficheiros principais

### chatCore.ts (5977 linhas)

O** manipulador de pedido principal** . Apesar do tamanho, tem uma estrutura clara:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

Apesar de ser uma função gigante, está organizada em** secções comentadas** este mapa para o pipeline de 5 estágios.

### combo.ts (4456 LOC)

O** mecanismo de encaminhamento** que resolve um combo para alvos ordenados.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Suporta** 22 estratégias de encaminhamento** (ver `src/shared/constants/routingStrategies.ts`):

| Estratégia          | Comportamento                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `priority`          | Lista ordenada do primeiro alvo                                                                         |
| `weighted`          | Probabilístico por peso por alvo                                                                        |
| `round-robin`       | Percorrer os alvos por ordem                                                                            |
| `context-relay`     | Distribua o contexto pelos alvos                                                                        |
| `fill-first`        | Preencha a quota antes de passar para a próxima                                                         |
| `p2c`               | Poder de duas escolhas                                                                                  |
| `random`            | Uniforme aleatório                                                                                      |
| `least-used`        | Escolha aquele com menos utilizações recentes                                                           |
| `cost-optimized`    | Alvo saudável mais barato primeiro                                                                      |
| `reset-aware`       | Ciente das janelas de reposição do fornecedor                                                           |
| `reset-window`      | Redefinir o encaminhamento baseado em janela                                                            |
| `expiry-first`      | Gastar a conta cuja quota expiraria sem ser utilizada primeiro                                          |
| `headroom`          | A maior margem de quota restante primeiro                                                               |
| `quota-weighted`    | Ignorar as contas esgotadas e, em seguida, levantar pela quota restante ÷ carga em trânsito             |
| `strict-random`     | Verdadeiramente uniforme (sem ponderação de qualidade)                                                  |
| `auto`              | Utilizar pontuação de 16 fatores (`autoCombo/`)                                                         |
| `lkgp`              | Primeiro o último bom fornecedor conhecido                                                              |
| `context-optimized` | Melhor para pedidos de contexto longo                                                                   |
| `cache-optimized`   | Fixe cada prefixo de prompt reutilizável na mesma conta (ocorrências de cache de prompt)                |
| `fusion`            | Distribua-se num painel em paralelo e depois sintetize através de um juiz (`fusion.ts`)                 |
| `pipeline`          | Passos da cadeia — a saída de cada alvo alimenta o próximo                                              |
| `jev`               | Aceitação: TypeSafe Jev admite quais as inscrições classificadas que são executadas; senão o seu pedido |

### base.ts (1170 LOC)

O** executor abstrato** que toda a classe executora se estende (directamente ou através `DefaultExecutor` e outras subclasses). Ele contém:

- `buildUrl()` — construção URL padrão (substituição de subclasses para personalização)
- Cabeçalhos padrão `buildHeaders()` — (autenticação, tipo de conteúdo)
- passagem `transformRequest()` — por defeito
- `execute()` — o loop HTTP principal com retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

O comportamento específico do fornecedor (cabeçalhos de autenticação, base URL, cabeçalhos de versão) é configurado através do registo do fornecedor, e não por classes de executores separadas.

## Executores (150 módulos)

Principalmente um ficheiro por fornecedor. Todas as classes executoras estendem `BaseExecutor` e substituem o que é diferente; os outros módulos são auxiliares por fornecedor (esquemas de ferramentas, adaptadores fetch/TTS, manipuladores de peculiaridades).

### Padrões Comuns

Os fornecedores são resolvidos através do `getExecutor(providerId)`, que retorna o executor configurado. Os fornecedores OpenAI/Anthropic-compatible usam `DefaultExecutor` (`executors/default.ts`). O comportamento específico do fornecedor (base URL, cabeçalhos de autenticação, versão API ) é configurado em `open-sse/config/providers/`, enquanto as transformações do corpo do pedido são tratadas em `open-sse/translator/`.

**URL personalizado** é definido através da configuração do fornecedor:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Autenticação personalizada** é tratado através da configuração de autenticação do registo do fornecedor (API key, OAuth, header profiles).

**Corpo de solicitação personalizado** transformações (por exemplo, Anthropic separando `system` de `messages`) são registadas por fornecedor em `open-sse/translator/`.

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

A resolução passa pelo `ExecutorRegistry` (`executors/registry.ts`): todo o executor especializado é declarado na tabela interna do `executors/index.ts` e registado via `registerExecutor(alias, instance)` no carregamento do módulo; `getExecutor()` consulta o registo e recorre a um `DefaultExecutor` memorizado para qualquer fornecedor sem uma entrada especializada. O mapeamento completo do executor do alias → é caracterizado pelo teste dourado `tests/unit/executor-map-golden.test.ts`.

## Tradutores

Traduza entre **3 formatos**: OpenAI, Anthropic, Gemini, além da nova Responses API.

### Quando é efetuada a tradução

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Traduções comuns:

- `OpenAI → Anthropic`: campo `system` separado, cabeçalho `x-api-key`
- `OpenAI → Gemini`: `contents` em vez de `messages`, `systemInstruction`
- `OpenAI → Responses API`: matriz `input`, estado `previous_response_id`

### Casos especiais tratados

- Papel `developer` → `system` para formatos que não sejam OpenAI
- Papel `system` → incorporado na primeira mensagem do utilizador para GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` do Gemini
- `tools` → formato de ferramentas específico do fornecedor
- Parâmetros de raciocínio (o1, Claude) → equivalentes específicos do fornecedor

## Servidor MCP

`open-sse/mcp-server/` implementa o servidor **Model Context Protocol**:

- **110 ferramentas** (gestão de fornecedores, combinações, memória, cache, compressão, proxy, competências, gamificação, plugins, Notion, Obsidian, corpus local)
- **3 transportes**: stdio, SSE, Streamable HTTP
- **33 âmbitos** para autorização granular

### Registo de ferramentas

As ferramentas são registadas como ficheiros autónomos em `open-sse/mcp-server/tools/`, cada um exportando um nome, esquema, processador e âmbito:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transportes

```ts
// stdio (utilização na CLI)
startMcpStdio(server);

// SSE (transmissão baseada em HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP moderno)
startMcpStreamable(server, port);
```

### Autorização

Todas as chamadas de ferramentas passam por verificações de âmbito (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformadores

`open-sse/transformer/` converte entre os formatos **Chat Completions** e **Responses API**.

### Porquê um transformador separado?

A Responses API é o novo formato da OpenAI com **conversas com estado** (`previous_response_id`). Quando um cliente envia um pedido Responses, o OmniRoute:

1. Converte internamente Responses → Chat Completions
2. Envia para o fornecedor (qualquer fornecedor que suporte Chat Completions)
3. Converte a resposta novamente para o formato Responses
4. Transmite a resposta convertida ao cliente

O transformador (`transformer/responsesTransformer.ts`) fornece:

```ts
createResponsesApiTransformStream(): TransformStream
```

Este processa:

- Eventos `response.output_item.added`
- Eventos `response.output_text.delta`
- Evento `response.completed`
- Mapeamento de chamadas de ferramentas (`function_call` ↔ `tool_calls`)

## Configuração

`open-sse/config/` contém a camada de configuração:

| Ficheiro                      | Finalidade                                                |
| ----------------------------- | --------------------------------------------------------- |
| `providerRegistry.ts`         | Registo de modelo de chat no catálogo de 394 fornecedores |
| `providerModels.ts`           | Aliases de modelo, mapeamento de formato                  |
| `constants.ts`                | Tempos limite, limites, códigos de estado                 |
| `defaultThinkingSignature.ts` | Assinatura de pensamento Claude padrão                    |
| `modelStrip.ts` (em serviços) | Remoção de campo por prestador                            |

### Esquema de registo de prestador

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

A validação Zod no carregamento do módulo garante que todas as configurações do fornecedor são válidas.

## Restrições de Desempenho

O motor de encaminhamento tem limites de desempenho rigorosos:

| Operação                                                    | Objetivo | Medição                         |
| ----------------------------------------------------------- | -------- | ------------------------------- |
| Resolução de combinações                                    | <10ms    | Para 50 destinos                |
| Verificação do limite de taxa                               | <1ms     | Token bucket em memória         |
| Fallback da família de modelos                              | <5ms     | Definições de famílias em cache |
| Despacho do encaminhamento de pedidos                       | <2ms     | Caminho crítico                 |
| **Sem I/O bloqueante no caminho crítico do encaminhamento** | —        | Tudo assíncrono                 |

---

## Antipadrões

❌ **Chamadas síncronas à BD em `combo.ts`** — pré-calcular e colocar em cache
❌ **Lógica de repetição nos handlers** — utilizar `retry()` do serviço de resiliência
❌ **Acesso direto à configuração do fornecedor** — utilizar os getters de `providerRegistry`
❌ **Cadeias de fallback codificadas diretamente** — definir em `modelFamilyFallback.ts`
❌ **Mutações de estado entre pedidos concorrentes** — utilizar apenas contexto ao nível do pedido

## Adicionar um Novo Componente

### Adicionar um Novo Serviço

1. Criar `open-sse/services/[serviceName].ts` com uma responsabilidade específica
2. Exportar a função principal do handler e quaisquer constantes
3. Adicionar testes unitários em `tests/unit/services/[serviceName].test.mjs`
4. Integrar no pipeline de pedidos em `handlers/chatCore.ts` (se estiver relacionado com o encaminhamento)
5. Atualizar a lógica de encaminhamento em `combo.ts` se o serviço afetar a seleção de destinos
6. Documentar neste ficheiro

### Adicionar um Novo Executor

1. Criar `open-sse/executors/[provider].ts` que estenda `BaseExecutor`
2. Registar em `config/providerRegistry.ts`
3. Adicionar à factory de `executors/index.ts`
4. Adicionar testes unitários para o executor
5. Documentar em `docs/architecture/ARCHITECTURE.md`

### Adicionar uma Nova Ferramenta MCP

1. Criar ou atualizar `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definir o esquema Zod para os dados de entrada
3. Registar a ferramenta em `mcp-server/index.ts`
4. Adicionar à matriz de âmbitos em `mcp-server/auth/`
5. Adicionar testes unitários
