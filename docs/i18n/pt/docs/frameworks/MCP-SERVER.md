> Servidor Model Context Protocol com 110 ferramentas para operações de encaminhamento, cache, compressão, memória, skills, proxy, pool, radar e origem de contexto.
>
> Fonte da verdade: `open-sse/mcp-server/server.ts` computa** 110 ferramentas exclusivas** com `countUniqueMcpTools()`: 45 definições canónicas (incluindo as seis ferramentas de ciclo de vida CCR, o trio de habilidades do agente, `omniroute_radar_catalog` e `omniroute_x_search`), além de memória (3), habilidades (4), habilidades GitHub (3), pool (6), gamificação (8), plug-ins (8), Notion (6), Obsidian (22), corpus local (3) e duas ferramentas de compressão apenas RTK.

## Instalação

OmniRoute MCP está integrado. Comece por:

```bash
omniroute --mcp
```

Ou através do transporte aberto:

```bash
# HTTP streamable transport (port 20130)
omniroute --dev  # MCP auto-starts on /mcp endpoint
```

Os transportes HTTP (`sse` / `streamable-http`, servidos em processo pelo servidor do painel) estão desativados por defeito e anteriormente só podiam ser alternados na página `/dashboard/mcp`. A partir da v3.8.51, o CLI tem paridade:

```bash
omniroute mcp status                                  # enabled/online, transport, tool count
omniroute mcp enable [--transport stdio|sse|streamable-http]
omniroute mcp disable
omniroute mcp restart                                 # resets active sse/streamable-http sessions
```

`mcp enable`/`mcp disable` PATCH o mesmo `mcpEnabled` (e opcionalmente `mcpTransport`) configurando o painel alterna através de `/api/settings`. `mcp restart` chama `POST /api/mcp/restart`: destrói sessões `sse`/`streamable-http` ativas para que o próximo pedido seja reinicializado corretamente, devolve `409` se MCP estiver desativado e `501` para o transporte `stdio` (os clientes stdio têm o seu próprio subprocesso — não existe nenhum identificador no processo para reiniciar).

## Transportes

O servidor MCP expõe três transportes, todos apoiados pela mesma fábrica `createMcpServer()` :

| Transporte        | Onde                                        | Quando usar                                                  |
| :---------------- | :------------------------------------------ | :----------------------------------------------------------- |
| `stdio`           | `open-sse/mcp-server/server.ts`             | integrações IDE (Claude Desktop, Cursor, etc.)               |
| `sse`             | `POST/GET /api/mcp/sse` via `httpTransport` | Clientes Browser/agent que necessitam de um fluxo de eventos |
| `streamable-http` | `POST/GET/DELETE /api/mcp/stream`           | Clientes HTTP multisessão (cabeçalho `mcp-session-id` )      |

O transporte HTTP activo (`sse` ou `streamable-http`) é seleccionado pela configuração `mcpTransport`. A troca de transporte fecha as sessões existentes no outro transporte.

### Acesso remoto (ignorar âmbito de gestão)

`/api/mcp/*` está na camada LOCAL_ONLY (`src/server/authz/routeGuard.ts`) — por defeito, apenas os hosts de loopback (`localhost`, `127.0.0.1`, `::1`) o conseguem alcançar. Desde a v3.8.2, os clientes sem loopback podem ligar-se se apresentarem um `Authorization: Bearer <api-key>` cuja chave carregue o scope `manage`. Esta é a única forma de aceder ao servidor MCP remoto através de um túnel, proxy reverso ou nome de host público.

```bash
# Grant manage scope: open the dashboard API Keys page and toggle
# "Management Access" on the key, or POST scopes:["manage"] when creating.

# Then connect from a remote MCP client:
curl -i \
  -H "Host: your-public-host.example" \
  -H "Authorization: Bearer sk-…" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"my-client","version":"0"}}}' \
  https://your-public-host.example/api/mcp/stream
```

Uma chave sem gestão (ou sem portador) devolve `403 LOCAL_ONLY`. O prefixo irmão `/api/cli-tools/runtime/*` é intencionalmente NOT ignorável — consulte [Route Guard Tiers — Manage-scope carve-out](../security/ROUTE_GUARD_TIERS.md#manage-scope-carve-out).

### Validação de origem

Após a autenticação, cada pedido para `/api/mcp/*` — os transportes e as rotas de gestão como `status`, `tools`, `audit` e `restart` — tem o seu cabeçalho `Origin` validado, seja qual for o chamador (chave API, token CLI, sessão de painel ou loopback anónimo com login desativado). Esta é a proteção de religação DNS exigida pela especificação MCP Streamable HTTP.

- **Sem cabeçalho `Origin`** → permitido. Os clientes OmniRoute CLI, SDK e IDE não enviam um.
- **Permitido `Origin`** → `localhost`, `127.0.0.1` ou `[::1]` em qualquer porta, ou a própria origem pública do OmniRoute: `OMNIROUTE_PUBLIC_BASE_URL` / `NEXT_PUBLIC_BASE_URL` / `NEXT_PUBLIC_APP_URL`, a origem encaminhada de um proxy reverso fiável (`OMNIROUTE_TRUST_PROXY`, apenas quando não está definida nenhuma base URL ) ou um host loopback/LAN IP. O cabeçalho `Host` por si só nunca torna uma origem fiável.
- **Qualquer outro `Origin`, incluindo `null`** → `403` com um corpo de erro JSON-RPC: `id: null`, `error.code: -32000`, `error.data.code: "INVALID_ORIGIN"`. Uma sessão de painel que apresente um token CSRF válido será ainda aceite, tal como para outras gravações de painel.

Um cliente MCP do browser servido por um proxy reverso necessita `OMNIROUTE_PUBLIC_BASE_URL`; não existe lista de permissões para outras origens. CORS preflight (`OPTIONS`) não é verificado na origem; a seguinte solicitação é.

As entradas CCR ficam apenas na memória e desaparecem no reinício. Cada bloco está limitado a 2 MiB, cada principal a 16 MiB e o armazenamento global a 64 MiB. As entradas estão padronizadas para um TTL de 24 horas (máximo de sete dias). A recuperação completa MCP está limitada a 256 KiB; os blocos maiores permanecem disponíveis nos modos ranged e grep. O armazenamento, recuperação, listagem, inspeção, eliminação e estatísticas são isolados pelo principal da chave API autenticado. Os registos de auditoria contêm hashes e metadados de tamanho, nunca conteúdo.

`omniroute_compression_status` reporta a compressão da descrição MCP separadamente em `analytics.mcpDescriptionCompression`. Estes valores são estimativas de tamanho de metadados para descrições listáveis MCP (`tools`, `prompts`, `resources` e `resourceTemplates`); não são recibos de utilização do fornecedor e estão marcados com `source: "mcp_metadata_estimate"`.

### Filtro de árvore de acessibilidade MCP (v3.8.0)

Separado das ferramentas de compressão acima referidas, OmniRoute inclui um filtro pós-execução que comprime o** resultados da ferramenta** de ferramentas MCP browser/accessibility antes de serem devolvidas ao agente. Este filtro em si não é uma ferramenta — é executado de forma transparente em qualquer resultado de ferramenta que contenha texto detalhado de árvore de acessibilidade ou de instantâneo do navegador (≥ 2000 caracteres).

Comportamentos principais:

- Recolhe ≥ 30 linhas irmãs repetidas consecutivas no resumo cabeça + cauda
- Preserva as âncoras `[ref=eXX]` exigidas pelo Playwright/computer-use
- Trunca o texto de grandes dimensões (> 50.000 caracteres) com uma dica de navegação
- Economia esperada:** 60–80%** em cargas úteis de instantâneo do navegador

Configuração: `compression.mcpAccessibility` nas definições globais (migração 056). Implementação: `open-sse/services/compression/engines/mcpAccessibility/`. Documentação completa: [Mecanismos de compressão — MCP Filtro de árvore de acessibilidade](../compression/COMPRESSION_ENGINES.md#mcp-accessibility-tree-filter).

Consulte [Mecanismos de compressão](../compression/COMPRESSION_ENGINES.md) e [compressão RTK](../compression/RTK_COMPRESSION.md) para obter o modelo de compressão em tempo de execução subjacente a estas ferramentas.

## Estruturas relacionadas (v3.8.0)

O inventário de ferramentas MCP acima (110 ferramentas únicas, computadas por `countUniqueMcpTools()`) tem um âmbito intencional para operações routing/cache/compression/memory/skills/proxy/context-source em tempo de execução. Duas estruturas adjacentes são fornecidas juntamente com o servidor MCP na v3.8.0 e são documentadas separadamente:

### Agentes de nuvem

Os agentes cloud são agentes de codificação AI fora de processo (codex-cloud, cursor-cloud, devin, jules) ligados ao OmniRoute através do mesmo modelo de ligação utilizado para os fornecedores LLM. São expostos através da sua própria superfície REST (`/api/v1/agents/*`) e são** não** parte do catálogo de ferramentas MCP — chamar um Agente de Nuvem não consome um âmbito MCP.

- Implementação: `src/lib/cloudAgent/` (`registry.ts`, `agents/codex.ts`, `agents/cursor.ts`, `agents/devin.ts`, `agents/jules.ts`).
- Ciclo de vida: `createTask`, `getStatus`, `approvePlan`, `sendMessage`, `listSources`.
- Documentação: [docs/frameworks/CLOUD_AGENT.md](./CLOUD_AGENT.md).

### Guarda-corpos

Os guardrails são filtros pre/post-execution (vision-bridge, pii-masker, prompt-injection) aplicados dentro do pipeline de chat. São executados antes de a camada MCP tool/route ser alcançada e emitem violações estruturadas para o pipeline de auditoria; não são invocados como ferramentas MCP.

- Implementação: `src/lib/guardrails/`.
- Documentação: [docs/security/GUARDRAILS.md](../security/GUARDRAILS.md).

Ao depurar uma chamada MCP que parece bloqueada, verifique o registo de auditoria MCP (entradas `scope_denied:*` ) e a trilha de auditoria do guardrails — uma solicitação pode ser rejeitada por um guardrail** antes** atinge sempre a camada de aplicação do âmbito MCP.

## Autenticação e escopos

A ferramenta MCP chama strings de âmbito de leitura do chamador. Esta verificação é um dos três namespaces independentes. Um passe de um verificador não é um passe dos outros. As regras são [três namespaces de âmbito](#three-scope-namespaces). O catálogo de ferramentas é [o MCP tool scopes](#mcp-tool-scopes).

### Três namespaces de âmbito

`manage` numa chave API, `read:compression` numa ferramenta MCP e `read` num token de acesso `oma_live_…` são três concessões diferentes. Os chamadores que enviam um token de acesso `read` para uma rota de gestão mutante obtêm HTTP 403 `Access token scope 'read' is insufficient; 'write' required.` Esta classificação é `scopeSatisfies`. Não consulta a tabela MCP e o correspondente MCP não a consulta.

| Espaço para nome          | Credencial                                                                   | Verificador               | Um passe permite                                                 |
| :------------------------ | :--------------------------------------------------------------------------- | :------------------------ | :--------------------------------------------------------------- |
| Gestão de chaves de API   | `api_keys.scopes`                                                            | `hasManageScope`          | Gestão REST para essa chave do portador                          |
| Aditivo de chave API      | mesma matriz, uma string exata                                               | o ajudante nomeado abaixo | Só aquela capacidade                                             |
| Escopos da ferramenta MCP | mesma matriz, senão MCP `_meta` (só HTTP/SSE ), senão `OMNIROUTE_MCP_SCOPES` | `scopeMatches`            | Esta ferramenta, uma vez ativada a fiscalização                  |
| Token de acesso           | `oma_live_…`                                                                 | `scopeSatisfies`          | A rota de gestão cujo método e caminho exigem esta classificação |

A cunhagem de cada credencial é abordada em [Management Authentication](../guides/MANAGEMENT-AUTH.md).

#### Escopos de chave API

Um array `api_keys.scopes` alimenta dois trabalhos. Utilizam funções diferentes.

**Gestão REST.** `manage` e `admin` são membros de `MANAGEMENT_API_KEY_SCOPES` (`src/shared/constants/managementScopes.ts`). `hasManageScope` é o que autoriza as rotas de gestão para essa chave. `admin` é capaz de gerir essas rotas. A palavra `admin` aqui não é a classificação do token de acesso e não se expande para os escopos da ferramenta MCP.

**Cordas aditivas.** Cada um é um teste de adesão exacto e fica fora de `MANAGEMENT_API_KEY_SCOPES`.

| Âmbito                         | Um passe permite                                                                                                                                                        |
| :----------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mcp:connect`                  | Apenas o não-loopback `/api/mcp/` LOCAL_ONLY carve-out (`hasMcpConnectOrManageScope`). Uma chave com `manage` ou `admin` ainda passa por esta eliminação.               |
| `self:usage`                   | `GET /api/v1/me/status` para esta chave (`src/app/api/v1/me/status/route.ts`). `POST /api/keys` adiciona este âmbito em create (`normalizeSelfServiceScopesForCreate`). |
| `self:account-quota`           | Quotas de conta upstream dentro desta carga útil de estado (`src/lib/usage/apiKeySelfService.ts`). A rota de estado ainda requer `self:usage`.                          |
| `policy:bypass-provider-quota` | As chamadas de inferência desta chave ignoram a política de quota de fornecedor (`hasProviderQuotaBypassScope` em `src/sse/handlers/chat.ts`).                          |

#### Correspondência

O catálogo é a tabela nos [escopos da ferramenta MCP](#mcp-tool-scopes). Não trate `MCP_SCOPE_LIST` em `src/shared/constants/mcpScopes.ts` como este catálogo: é o subconjunto original tipado. As ferramentas posteriores declaram escopos adicionais ao lado (`read:notion`, `read:skills`, `read:local-corpus` e o resto da tabela).

`evaluateToolScopes` em `open-sse/mcp-server/scopeEnforcement.ts` permite uma chamada quando cada âmbito necessário corresponde a algum âmbito concedido:

- `*` corresponde a todos os escopos necessários.
- Um âmbito concedido que termina em `*` corresponde a um âmbito obrigatório que começa com o prefixo antes do asterisco. `read:*` corresponde `read:compression`.
- Todos os outros escopos concedidos correspondem apenas à sequência idêntica exigida.

Uma chave cujos escopos são `["manage"]` falha `scopeMatches` para `read:compression`. A mesma chamada falha para `admin`, `mcp:connect`, `read` e `write` quando estas são as únicas strings concedidas. Não existe hierarquia entre os escopos da ferramenta MCP para além do `*` final.

A aplicação está desativada, a menos que `OMNIROUTE_MCP_ENFORCE_SCOPES=true` (padrão `false`). Enquanto estiver desligado, `evaluateToolScopes` permite a chamada e ignora o catálogo. Enquanto estiver activado, HTTP utiliza o `api_keys.scopes` da chave do portador como `authInfo` (consulte [Ligação do âmbito HTTP por chave](#per-key-http-scope-binding-7895) ). Quando nenhum âmbito de chave é resolvido, o conjunto concedido passa para MCP `_meta` (honrado apenas para os chamadores HTTP/SSE, dentro de um contexto de autenticação HTTP ; o `_meta` de um chamador stdio é ignorado porque o cliente o controla e não transporta qualquer identidade por chamador), pelo que `OMNIROUTE_MCP_SCOPES`.

#### Escopos de token de acesso

Os tokens `oma_live_…` (`src/lib/accessTokens/scopes.ts`) transportam `read`, `write` ou `admin`. `scopeSatisfies` é uma classificação: `admin` cobre `write` e `read` e `write` cobre `read`. Os escopos desconhecidos não cobrem nada.

`evaluateAccessTokenAuth` (`src/server/authz/accessTokenAuth.ts`) compara esta classificação com `inferRequiredScope` (`src/server/authz/accessScopes.ts`):

- `GET`, `HEAD` e `OPTIONS` requerem `read`.
- Todos os outros métodos requerem `write`.
- Os caminhos em `ADMIN_SCOPE_PREFIXES` requerem `admin` para cada método. `/api/mcp` está nessa lista, pelo que um token de acesso `write` ainda não pode chamar a superfície MCP HTTP.
- Os caminhos em `ADMIN_MUTATION_PREFIXES` requerem `admin` apenas para mutações.
- Os caminhos em `ADMIN_MUTATION_EXACT_PATHS` (`/api/settings`, `/api/settings/require-login`) requerem `admin` apenas para mutações, e apenas nesse caminho exacto — outras sub-rotas `/api/settings/*` mantêm `write`.

`PATCH /api/keys/{id}` é uma mutação e não está nestas listas de administração, pelo que um token `read` recebe 403 `Access token scope 'read' is insufficient; 'write' required.` Um token de acesso `write` ou `admin` satisfaz esta rota. Um painel JWT, o token de loopback CLI machine-id e uma chave API com `manage` ou `admin` ocupam outras ramificações e não são restringidos por esta classificação.

Um token de acesso que passa `scopeSatisfies` para `/api/mcp` apenas libertou o gate de gestão. As chamadas de ferramenta ainda executam `scopeMatches` em escopos de chave API. A classificação do token de acesso não é uma entrada para `scopeMatches`.

### capacidade de rota estreita `mcp:connect` — (#7895)

Alcançar o transporte HTTP/SSE MCP (`/api/mcp/*`) sem loopback requer a divisão `/api/mcp/` LOCAL_ONLY (consulte `docs/security/ROUTE_GUARD_TIERS.md`). Historicamente, esta divisão só aceitava uma chave `manage`/`admin` -scope API completa — demasiado ampla para um chamador que só precisa de falar MCP. `src/shared/constants/managementScopes.ts` exporta agora `MCP_CONNECT_SCOPE = "mcp:connect"`: um âmbito aditivo e estreito (mesmo precedente de `SELF_USAGE_SCOPE`) que autoriza ONLY o desvio `/api/mcp/` em `src/server/authz/policies/management.ts` — não concede qualquer outro acesso à rota de gestão e é deliberadamente mantido OUT de `MANAGEMENT_API_KEY_SCOPES`. Uma chave que contenha `manage`/`admin` ainda passa pela eliminação inalterada; `mcp:connect` é uma alternativa de baixo privilégio para os chamadores remotos apenas MCP, verificada através do `hasMcpConnectOrManageScope()`.

### Ligação de escopo HTTP por chave (#7895)

Sobre HTTP/SSE, `open-sse/mcp-server/httpTransport.ts` resolve agora o `api_keys.scopes` real do chamador através do `resolveMcpCallerAuthInfo()` (`open-sse/mcp-server/httpAuthContext.ts`) e passa-o para o MCP SDK do `transport.handleRequest(req, { authInfo })`, pelo que `extra.authInfo.scopes` atingindo cada chamada de ferramenta reflecte os próprios escopos da chave Bearer. `scopeEnforcement.ts`'s `resolveCallerScopeContext()` já priorizou `authInfo` sobre o `_meta` e `OMNIROUTE_MCP_SCOPES` env fallback — isto apenas preenche a primeira fonte de maior prioridade, que anteriormente não era alimentada HTTP. Quando nenhuma chave API é resolvida (sem cabeçalho, chave inválida), `authInfo` permanece `undefined` e a resolução passa para a cadeia `meta`/env existente inalterada. stdio não tem identidade por chamador (ver `mcpCallerIdentity.ts`) e não é afectado pela ligação por chave — salta o passo `_meta` (`_meta` é honrado apenas dentro de um contexto de autenticação HTTP, #15159) e resolve apenas a partir da chave `OMNIROUTE_MCP_SCOPES` env.

**A aplicação é forçada para chamadores HTTP/SSE de âmbito restrito, independentemente de `OMNIROUTE_MCP_ENFORCE_SCOPES`.** O padrão `OMNIROUTE_MCP_ENFORCE_SCOPES` para `false` é seguro apenas para o fluxo de operador único local/stdio, onde não existe identidade por chamador para o âmbito. `open-sse/mcp-server/server.ts::withScopeEnforcement()` activa incondicionalmente a aplicação do âmbito por ferramenta (`shouldForceScopeEnforcement()` in `scopeEnforcement.ts`) sempre que `resolveCallerScopeContext()` resolve `source === "authInfo"` (i.e., um cabeçalho de autorização HTTP real por chave, HTTP/SSE-only) AND esta chave não contém o âmbito `manage`/`admin` completo. Isto fecha a lacuna onde uma chave contendo ONLY o escopo de bypass `mcp:connect` estreito — documentado acima como não autorizando nada além do `/api/mcp/` LOCAL_ONLY carve-out — poderia invocar todas as ferramentas MCP assim que um operador habilitasse o acesso remote/non-loopback MCP, simplesmente porque `OMNIROUTE_MCP_ENFORCE_SCOPES` envia `false` por defeito. Uma chave `manage`/`admin` completa sobre HTTP e cada chamador stdio/local mantêm inalterado o comportamento -gated `OMNIROUTE_MCP_ENFORCE_SCOPES`.

## Descrição Compressão

A ferramenta MCP, o prompt e os registos de recursos podem comprimir as descrições no momento registration/list para reduzir a pegada de metadados exposta aos clientes (e, portanto, o custo do contexto de prompt). A implementação reside em `open-sse/mcp-server/descriptionCompressor.ts` e está ligada ao servidor MCP através de `compressMcpRegistryMetadata` dentro de `createMcpServer()`.

- A compressão é executada sobre o texto de descrição utilizando o conjunto de regras Caveman (`getRulesForContext("all", "full")`) com extração de blocos preservados (extensões de código, blocos protegidos, etc.) para que o conteúdo estrutural não seja alterado.
- Alternar por implantação através do valor `compression.mcpDescriptionCompressionEnabled` na tabela de definições `key_value` (padrão: ativado) — exposto no UI como** Compressão de descrição do Analytics → MCP** .
- Alterne todo o processo através de `OMNIROUTE_MCP_COMPRESS_DESCRIPTIONS=false` ou `OMNIROUTE_MCP_DESCRIPTION_COMPRESSION=false`.
- As estatísticas em tempo real são apresentadas através de `omniroute_compression_status` em `analytics.mcpDescriptionCompression` e marcadas como `source: "mcp_metadata_estimate"` para desambiguar dos recibos reais de utilização do fornecedor.

## Redução da cardinalidade da ferramenta (F4.3)

A compressão de descrição reduz os metadados de cada ferramenta;** redução da cardinalidade da ferramenta** vai um passo mais além ao reduzir _quantas_ ferramentas são publicitadas. Anunciar menos ferramentas no manifesto `tools/list` reduz o custo do token por pedido que o modelo do cliente paga pelo catálogo de ferramentas (compressão "camada 5"). A implementação é um filtro puro e sem estado em `open-sse/mcp-server/toolCardinality.ts` (`reduceToolManifest`), ligado ao ciclo de registo em `createMcpServer()` (`open-sse/mcp-server/server.ts`).

**Ativar, desativado por defeito.** O filtro só é executado quando pelo menos uma das duas variáveis de ambiente está definida; sem qualquer conjunto, todas as 110 ferramentas são anunciadas inalteradas.

| Variável         | Modo                                                                                                             |
| :--------------- | :--------------------------------------------------------------------------------------------------------------- |
| `MCP_TOOL_DENY`  | Lista negra de nomes de ferramentas — separados por vírgula que são sempre eliminados do `tools/list`            |
| `MCP_TOOL_ALLOW` | Lista de permissões — nomes de ferramentas separados por vírgula; só estes sobrevivem, tudo o resto é descartado |

`deny` tem prioridade sobre `allow`. Os nomes são separados por vírgula, cortados e as entradas vazias são ignoradas. Exemplos:

```bash
# Drop two tools from the catalog
MCP_TOOL_DENY="omniroute_get_health,omniroute_list_combos" omniroute --mcp

# Announce only the routing + quota tools (allow-list mode)
MCP_TOOL_ALLOW="omniroute_route_request,omniroute_check_quota" omniroute --mcp
```

**Como as ferramentas filtradas são removidas:** o registo é sempre bem-sucedido; uma ferramenta que o perfil rejeita é `.disable()` d no identificador MCP SDK, para que nunca apareça no `tools/list`, mas a cablagem permanece intacta (limpo enable/disable, sem novo registo). O analisador de perfis é `readMcpToolProfileFromEnv(process.env)`, que devolve `null` (sem filtragem) quando ambos os vars estão vazios.

A forma `ToolProfile` mais rica por detrás `reduceToolManifest` também suporta a filtragem de interseção de âmbito (`allowScopes`, com correspondência de wildcard `read:*` -style ) e um limite determinístico `maxTools`, mas estes dois botões necessitam do manifesto completo no momento do registo e são** não** exposto através das variáveis de ambiente hoje (um gancho `tools/list` -level é um acompanhamento rastreado). `estimateManifestTokens()` está disponível para comparar o custo do token manifesto antes e depois da redução.

## Pulsação em tempo de execução

O transporte stdio persiste em `${DATA_DIR}/runtime/mcp-heartbeat.json` a cada 5 segundos. O painel (`/api/mcp/status`) lê este ficheiro mais a atividade PID para derivar `online`. Em vez disso, HTTP transporta o estado do relatório do `getMcpHttpStatus()` em processo (sem escrita de ficheiros).

O instantâneo de pulsação contém:

```json
{
  "pid": 12345,
  "startedAt": "2026-05-13T12:34:56.000Z",
  "lastHeartbeatAt": "2026-05-13T12:35:01.000Z",
  "version": "1.8.1",
  "transport": "stdio",
  "scopesEnforced": false,
  "allowedScopes": [],
  "toolCount": 110
}
```

## Registo de auditoria

Cada chamada de ferramenta é registada na tabela SQLite `mcp_tool_audit` por `open-sse/mcp-server/audit.ts`:

- Nome da ferramenta, argumentos (hashed/truncated como `auditLevel` por ferramenta ), resultado
- Duração em ms, flag success/failure, mensagem de erro (quando aplicável)
- hash de chave API, carimbo de data/hora
- As negações de âmbito são registadas como `scope_denied:<reason>` com a lista de âmbito em falta

Utilize o painel ou os endpoints `/api/mcp/audit` e `/api/mcp/audit/stats` REST para inspecionar as chamadas recentes.
