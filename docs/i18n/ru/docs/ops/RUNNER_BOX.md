Пул самостоятельно размещённых раннеров работает на сервере **.113** (`tomni-proxmox-113`). С 2026-10-18 каждый
раннер OmniRoute имеет **одну роль**, одну метку и лимиты памяти/CPU, соответствующие измеренной
нагрузке. Слот Turbopack получает ресурсы, необходимые для сборки; остальные слоты рассчитаны с учётом
измеренных пиков. Перераспределение ресурсов на сервере возникает, только когда сборка Turbopack совпадает
со сборкой webpack Release-Green и заданием lint; подкачка хоста (16 GB) компенсирует это, а поскольку сборки
для pull request выполняются на размещённых раннерах, слот Turbopack большую часть времени простаивает:

| раннер               | метка            | роль                                                                                                                                               | `MemoryHigh` / `MemoryMax`    | `CPUQuota`   |
| -------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------ |
| `omniroute-113-5`    | `omni-build`     | сборки Turbopack: `ci.yml` `Build` (только push/dispatch), Docker amd64, `npm-publish`, `nightly-v4-build`, `preview-artifact`, ночная сборка a11y | 56 GB / 60 GB (подкачка 0)    | 1600 %       |
| `omniroute-113-6`    | `omni-release`   | Release-Green (`release-green` + `main-green`), сборка webpack                                                                                     | 20 GB / 24 GB (подкачка 4 GB) | 800 %        |
| `omniroute-113-2`    | `omni-light`     | ночные задания (Schemathesis, promptfoo, garak, k6) и `quality.yml` `lint-guard`                                                                   | 12 GB / 16 GB (подкачка 4 GB) | 600 %        |
| `omniroute-113`      | `omni-light`     | тот же пул, что и выше                                                                                                                             | 8 GB / 12 GB                  | 400 %        |
| OmniHeuris, OmniMind | (их репозитории) | только Dependabot (пиковое потребление каждого — 155 MB, 2026-10-18)                                                                               | 4 GB / 6 GB                   | 200 % каждый |

| --------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Лимиты находятся в файле `/etc/systemd/system/actions.runner.<…>.service.d/override.conf` каждого юнита
(предыдущие значения сохранены как `override.conf.bak-20261018`) и были применены без остановки командой
`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` — без перезапуска, поэтому ни одно
выполняющееся задание не было затронуто. Метки изменяются через API раннеров (`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`), также без перезапуска.

## Установка очистчика (однократно, на сервере)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): каждые 30 минут, журнал в /var/log/runner-janitor.log
*/30 * * * * MAX_ACTIVE_RUNNERS=8 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` обязателен: перед удалением очистчик проверяет одним снимком открытых
файлов, что путь не используется, а без этого инструмента ничего не удаляет и
сообщает об этом (код выхода 1). Любое изменение сначала проверяйте с `--dry-run` —
он точно показывает, что будет сделано, не изменяя ничего.

Что выполняется при каждом запуске: очистка наших собственных остаточных файлов
(`runner-*`, `omniroute-*`, `next-build*`, `e2e-build.tar.gz`) старше **3 ч на
tmpfs** и старше 24 ч на диске в `_work/_temp`; завершение процесса `next-build`
старше 75 мин (ни одна задача не выполняется так долго — 2026-08-27 один процесс
работал 70 мин после того, как GitHub объявил его задачу потерянной); удаление
рабочих копий старше 48 ч для раннеров, чьи юниты **остановлены**; предупреждение
при заполнении диска ≥ 85 %, PSI памяти `full/avg60` ≥ 10 % и количестве
слушателей, превышающем `MAX_ACTIVE_RUNNERS` (с разбивкой на omniroute/прочие).
Код выхода 1 = требуется внимание; проверьте журнал.

Правило 75 минут не обнаруживает сборку, от которой GitHub уже отказался. Когда
`Runner.Listener` не может продлить задачу, в `_diag/Runner_*.log` появляется
`POST request to …/renewjob timed out after 100 seconds`, API сообщает о состоянии задачи
`completed` (сбой) примерно через десять минут после последнего успешного продления, а
`next-build` продолжает работать без привязанной задачи (2026-10-18: сборка #17066 завершилась
с ошибкой в 19:43, но спустя пять минут её процесс сборки всё ещё занимал 40 ГБ). Проверьте ref
в новейшем `_diag/Worker_*.log`, затем отправьте SIGTERM только дереву процессов сборки по PID —
`next-build`, `npm run build`, `build-next-isolated.mjs` и рабочим процессам `_work`. Никогда не
трогайте `Runner.Listener`, `RunnerService.js` или `Runner.Worker`: рабочий процесс сообщит, что
задача отменена, а слушатель самостоятельно вернётся в онлайн.

## Юниты раннеров: KillMode

Стандартный для раннера параметр `KillMode=process` оставляет цепочку
`Runner.Worker → npm → next-build` работающей после остановки или перезапуска
юнита — осиротевшая сборка продолжает потреблять оперативную память и процессорные
ресурсы без привязанной задачи. Каждый юнит OmniRoute содержит drop-in-файл
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
с `KillMode=mixed`: сначала SIGTERM отправляется слушателю, а при наступлении
`TimeoutStop` всему cgroup отправляется SIGKILL. Изменение вступит в силу при
следующем перезапуске юнита — перезапускайте **по одному раннеру за раз и только
когда он простаивает**, выполняя проверку простоя и перезапуск одной командой.

## Правила эксплуатации

- **Одновременно выполняется только одна сборка Turbopack — ограничение обеспечивается меткой.** Каждая задача, запускающая полную сборку Turbopack
  `next build`, нацелена на `[self-hosted, omni-build]`, и только **`omniroute-113-5`** имеет эту
  метку: `ci.yml` `Build`, `npm-publish.yml` `publish`, `nightly-v4-build`, `preview-artifact`,
  ночная сборка a11y (#16853) и **amd64** в `docker-publish.yml` (webpack внутри BuildKit —
  Turbopack аварийно завершился там, запуск 33253576569). Этап Docker для arm64 остаётся на `ubuntu-24.04-arm`.
  Этап amd64 в `docker-publish` использует общую группу параллелизма `heavy-build-main` с `Build`
  из `ci.yml` (`cancel-in-progress: false`). Docker Engine должен находиться на `omniroute-113-5`. Второй слот
  Turbopack не помещается в 78 ГБ (2 × 33–37 ГБ плюс остальные процессы на машине); второй слот безопасен
  только для сборок webpack.
- **Сборки pull request выполняются на хостинговых раннерах (2026-10-18).** `Build` из `ci.yml` достигает `omni-build` только для
  `push` и `workflow_dispatch`; `Build` для каждого `pull_request` (из собственного репозитория или форка) и
  `merge_group` выполняется на `ubuntu-latest` с webpack. Когда каждый PR из собственного репозитория направлялся
  в этот слот, сборка Turbopack занимала его на 29–58 мин, 18 сборок ожидали в очереди до 18 ч, а
  собственная push-сборка ветки релиза получила слот один раз за 40 задач. На хостинговом раннере та же сборка
  PR занимает 8–12 мин параллельно с другими задачами PR. Turbopack — сборщик, поставляемый
  `npm-publish`, — продолжает проверяться в ветке релиза ночной сборкой a11y ветки по умолчанию
  (04:41 UTC), каждой push-сборкой или сборкой, запущенной вручную, которая достигает слота, а также самим
  `npm-publish`. `tests/unit/build/heavy-build-queue.test.ts`
  фиксирует условие из четырёх частей.
- **Никогда не задавайте слоту Turbopack меньше памяти, чем требуется по результатам измерений.** 2026-10-18 в 18:06 объём памяти слота был
  уменьшен с 56G/60G до 40G/44G, чтобы освободить место для `omni-release`. На протяжении всей фазы
  компиляции потребление держалось на уровне `MemoryHigh` (memory PSI `full` 30–43 %), а `Runner.Listener`,
  находящийся в той же cgroup, не мог продлить назначенную ему задачу. В тот же день были восстановлены
  заданные владельцем 56G/60G от 2026-10-17. При меньшем значении сборка не завершается ошибкой;
  она пробуксовывает из-за постоянного вытеснения памяти, и задача теряется.
- **У Release-Green есть собственный слот (2026-10-18).** До этого обе проверки Release-Green выполнялись
  на `omni-build`: при каждом push (~10/час, 97 из 100 запусков по push за один день были отменены
  в процессе выполнения) и три полных прогона продолжительностью ~2 ч в день (прогон в 05:29 ждал слот 6 ч) —
  единственный слот сборки был перегружен в несколько раз, а сборки PR из собственного репозитория ждали часами.
  `release-green` и `main-green` теперь нацелены на `omni-release` (только `omniroute-113-6`) с
  `OMNIROUTE_USE_TURBOPACK=0`, а начавшийся запуск больше не отменяется более новым push
  (при этом ожидающий слот по-прежнему схлопывает шквал запусков). `tests/unit/build/runner-capacity-routing.test.ts`
  фиксирует маршрутизацию, переключение на webpack и гарантирует, что на `omni-release` ничто не собирается с Turbopack.
- **Пул лёгких задач: `omni-light`.** `omniroute-113` и `omniroute-113-2` выполняют ночные задачи, которым
  нужна только серверная сборка `next build` (~5–6 ГБ; webpack), а также `lint-guard` из `quality.yml`. На
  `omniroute-113` до 2026-10-18 было задано `MemoryHigh=4G` — сборка promptfoo 54 минуты пыталась
  освободить там память; 8 ГБ устраняют троттлинг.
- **Меньше слушателей — намеренно.** Четыре юнита OmniRoute были отключены 2026-08-29 — каждый дополнительный
  слушатель становится ещё одним потребителем описанного выше бюджета памяти. Верхний предел для уборщика — 8 (`MAX_ACTIVE_RUNNERS=8` в cron): он учитывает
  каждый `Runner.Listener` на машине, а OmniHeuris и OmniMind добавляют ещё два к нашим пяти.
- **Задания Unit и Vitest остаются на размещённых раннерах.** `ci.yml` отправляет свои unit-шарды и задание Vitest на `[self-hosted, omni-ci]`, только когда переменная репозитория `vars.USE_VPS_TEST_RUNNER` равна `true`, и даже тогда только для запусков `pull_request` из того же репозитория; форки, `merge_group` и push остаются на `ubuntu-latest` (`tests/unit/vps-runner-variable-scope.test.ts`). Переменная равна `false`. 2026-10-28 трём 4-ядерным слушателям `omni-ci` потребовалось 250–270 с на `npm ci`, и каждый unit-шард упирался в 30-минутный лимит задания, тогда как размещённому шарду нужно ~634 с; нагрузка на машину составляла 17–24. Слушатели удалены. Не включайте переменную снова без слушателей, рассчитанных на unit-шард.
- **Никогда не очищайте `/tmp` или `_work` вручную, пока хотя бы один раннер занят.** Схема
  «проверить, затем удалить» с паузой между этими действиями привела к тому, что активная задача Build потеряла
  свой каталог `_work` 2026-08-27. Уборщик выполняет проверку и удаление за один шаг;
  предоставьте это ему.
- Остановка раннера во время выполнения задачи отменяет её (наблюдалось в рабочей среде): выполняйте `systemctl stop`, только
  когда у его слушателя нет дочернего процесса `Runner.Worker`, — и делайте это одной командой.
- Рабочие процессы не должны размещать артефакты в `/tmp` (это RAM). Скачивайте в
  `$RUNNER_TEMP` (на диске, отдельно для каждого раннера) — артефакт `next-build` размером 1,3 ГБ загружался
  в tmpfs 27–32 минуты, а его отправка с диска занимала 2 минуты.
- VPS `.15` предназначен только для приёмочного тестирования и никогда не запускает CI-раннеры.

## Линия размещённых раннеров (раннеры GitHub-hosted)

Репозиторий принадлежит организации `cheaper-inference` на тарифном плане **Team**: **60 одновременно выполняемых размещённых заданий**, общих для всех репозиториев организации, всех проверок PR, всех рабочих процессов, запускаемых при push, и конфигурации CodeQL по умолчанию. Приведённые ниже цифры измерены на тарифном плане **Pro** (40 одновременно выполняемых размещённых заданий). Согласно измерениям от 2026-10-18 во время
серии слияний (~10 слияний в час в `release/v3.8.52`): **за 24 ч было создано 2 500 запусков рабочих процессов**,
за 6 ч в ветку было выполнено 44 push, **106 размещённых заданий находились в очереди**, в то время как проверки PR ожидали
часами, а PR сливались без них. При каждом push в ветку запускалось девять рабочих процессов:

`tests/unit/build/push-storm-diet.test.ts` фиксирует триггер push только для `main` в `ci.yml` и
`quality.yml`. Побочный эффект: Codecov больше не получает базовую загрузку при каждом push в

в репозиторий порог покрытия и комментарий к PR не затронуты.

**Увеличение собственных вычислительных мощностей не устранит очередь размещённых заданий.** На машине разработчика
(`devbox-vm-06-dev002`, 24 vCPU / 54 ГБ) можно было бы разместить раннер, однако сеансы агентов уже
поддерживают нагрузку на уровне 20–26, в контейнере агента нет демона Docker, а перегружена именно
линия размещённых раннеров. На машине `.113` в тот же момент было свободно 71 ГБ, а нагрузка составляла 5–8; её ограничивает
указанный выше бюджет памяти на каждый процесс прослушивания (не более 6 процессов), а не ЦП. Оставшиеся меры
относятся к процессу разработки: сливать PR серии через очередь Mergify (`label=queue`; пакеты используют
один общий запуск CI для `merge_group` вместо отдельного запуска для каждого PR плюс отдельного запуска для каждого push),
сократить список языков в конфигурации CodeQL по умолчанию и отфильтровать `release-acceptance.yml` по файлам, которые он читает.
