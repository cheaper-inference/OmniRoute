Используйте это руководство, чтобы выбрать минимальный надёжный цикл разработки для pull request. Оно не
заменяет документы по архитектуре и безопасности для конкретных областей, ссылки на которые приведены ниже;
оно связывает каждый распространённый тип изменения с его контрактами, целевыми проверками и покрытием CI.

## Путь, по которому проходит каждое изменение

1. **Выберите базовую ветку до начала редактирования.** Найдите самую старшую активную ветку `release/v*` и
   создайте свою ветку от её вершины. Указывайте эту ветку как целевую, а не `main`. Если действует заморозка релиза,
   не выбирайте замороженную ветку в качестве целевой; используйте следующий активный цикл, описанный в
   [модели ветвления и релизов](BRANCHING_MODEL.md).
2. **Перечислите контракты.** Определите все каталоги, схемы, сгенерированные артефакты, публичные API и
   пользовательские интерфейсы, на которые влияет изменение. В таблице ниже приведён минимальный начальный набор.
3. **Напишите или обновите целевые тесты.** Изменения рабочего кода в `src/`, `open-sse/`, `electron/` или
   `bin/` требуют автоматизированного теста в том же PR. Запустите минимальный набор файлов тестов, подтверждающих
   поведение, а затем перечисленные целевые проверки.
4. **Позвольте CI запустить полную матрицу.** Полные сегменты модульных тестов, Vitest, порог покрытия и
   производственная сборка запускаются для PR. Запускайте широкий набор тестов локально только в том случае, если
   сбой целевой проверки указывает на более широкое влияние или изменение охватывает несколько подсистем.
5. **Синхронизируйтесь перед проверкой.** Получите активную базовую ветку, изучите её новые коммиты и отличия своей
   ветки от неё, затем выполните rebase или merge базовой ветки в соответствии с рабочим процессом для участников.
   Разрешайте конфликты сгенерированных файлов и каталогов на основе их исходников, повторно генерируйте их,
   перезапускайте целевой цикл и убедитесь, что PR по-прежнему нацелен на активную релизную ветку.
6. **Зафиксируйте подтверждения.** В шаблоне PR перечислите выполненные команды, все добавленные или изменённые
   файлы тестов, миграции или feature flags, а также все проверки, выполняемые только в CI, которые ещё ожидаются.

## Основные пути по типам изменений

Приведённые ниже команды являются минимальными целевыми проверками, а не разрешением пропустить тест,
непосредственно покрывающий изменённое вами поведение.

### Провайдер

**Контракты**

- Определение провайдера в `src/shared/constants/providers/` и его композиция в
  `src/shared/constants/providers.ts`.
- Модели и возможности в `open-sse/config/providerRegistry.ts` или в выделенных из него файлах реестра.
- Выбор исполнителя/транслятора, конфигурация OAuth или API-ключа, ресурсы панели управления и сгенерированный
  справочник провайдеров, когда применимо.
- Публичные учётные данные должны использовать `resolvePublicCred()`; ответы с ошибками должны использовать общие
  вспомогательные функции очистки ошибок. См. `docs/security/PUBLIC_CREDS.md` (git; не компилируется в `/docs`) и
  [очистку ошибок](../security/ERROR_SANITIZATION.md).

**Целевой цикл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # при изменении каталога; зафиксируйте сгенерированные отличия
npm run lint
```

Также протестируйте каждое затронутое семейство запросов: chat, Responses, images, embeddings, audio или video.
Рассматривайте отличия сгенерированного каталога и эталонных данных как изменения контрактов; не принимайте их
вслепую.

### Маршрутизация

**Контракты**

- Публичные значения стратегий и метаданные пользовательского интерфейса в `src/shared/constants/routingStrategies.ts`.
- Диспетчеризация и упорядочивание в `open-sse/services/combo.ts` и `open-sse/services/combo/`.
- Схемы combo, хранение данных, состояние отказоустойчивости, возможности моделей и элементы управления API/UI.
- [Механизм Auto-Combo](../routing/AUTO-COMBO.md) и документация по отказоустойчивости при изменении поведения.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # изменения стратегии или диспетчеризации
npm run check:known-symbols      # изменения регистрации стратегии
npm run lint
```

Локально используйте детерминированные тесты с имитацией вышестоящих сервисов. Проверочные тесты combo с реальными
сервисами требуют учётных данных и выполняются вручную, а не служат заменой CI.

### UI / UX

**Контракты**

- Границы маршрутов/страниц Next.js и общих компонентов в `src/app/` и
  `src/shared/components/`.
- Форматы ответов API, состояния загрузки/отсутствия данных/ошибки, поведение клавиатуры и программ экранного
  доступа, адаптивная компоновка, темы и расширение набора локалей.
- Исходные английские строки пользовательского интерфейса в `src/i18n/messages/en.json`; не добавляйте новые
  строки для пользователей напрямую в код.

**Целевой цикл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

При изменении взаимодействия или визуального оформления запустите приложение и проверьте как узкую, так и широкую
область просмотра. CI запускает производственную сборку и более широкие наборы тестов; для визуального поведения
по-прежнему необходимы целевой компонентный тест, Playwright-тест или документированная ручная проверка,
соответствующая изменению.

### i18n

**Контракты**

- `src/i18n/messages/en.json` является источником строк UI; `config/i18n.json` является источником локалей.
- Каталоги CLI хранятся отдельно в `bin/cli/locales/`.
- Сохраняйте заполнители и теги ICU без изменений. Не переводите названия продуктов/провайдеров/моделей,
  названия протоколов и заголовков, команды, идентификаторы кода/JSON, URL, переменные окружения и
  защищённые термины, такие как `OmniRoute`, `OAuth`, `MCP` и `A2A`. Текущий исходный список находится в
  `scripts/i18n/glossary/protected-terms.json`.

**Целевой цикл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # при изменении строк/каталогов CLI
npm run lint
```

Это руководство для существующей системы, а не предложение расширять её инструментарий или модель ключей.
Пока проектируется система на замену, вносите изменения i18n точечно. Не запускайте команды перевода,
обращающиеся к внешним сервисам, если только задача явно не требует сгенерированных переводов и вы не
проверили получившиеся отличия.

### CLI

**Контракты**

- Публичные команды и флаги в `bin/cli/`, сгенерированные команды API, коды завершения, stdout/stderr и
  структуры вывода JSON, поведение конфигурации/окружения и файлы, входящие в пакет.
- Пользовательские строки CLI должны использовать слой интернационализации CLI, а каталоги `en`/`pt-BR` должны оставаться синхронизированными.
- Сохраняйте Node в качестве поддерживаемой среды выполнения и соблюдайте контракт опубликованных исполняемых файлов.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # изменения сгенерированного/собранного CLI
npm run check:pack-policy     # изменения поверхности пакета
npm run lint
```

Используйте точную команду во временном каталоге данных, если поведение зависит от разбора, файлов или
статуса завершения. CI выполняет более широкие проверки артефактов пакета и экосистемы.

### База данных

**Контракты**

- Доменные модули находятся в `src/lib/db/`; импортируйте конкретные модули напрямую (старый слой реэкспорта `localDb.ts` удалён).
- Нумерованные идемпотентные SQL-миграции находятся в `src/lib/db/migrations/`; необходимо учитывать безопасность транзакций, поведение при обновлении,
  индексы и все участки вызывающего кода, затронутые схемой.
- Маршруты и обработчики никогда не выполняют необработанный SQL напрямую.

**Целевой цикл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

При добавлении миграции тестируйте как чистую базу данных, так и обновление с предыдущей схемы. Тесты базы данных
должны закрывать дескрипторы и вызывать `resetDbInstance()` во время очистки. Запускайте `npm run test:bun:db` только при
изменении экспериментального пути адаптера Bun; Node остаётся эталонной средой.

### Сборка / развёртывание

**Контракты**

- Корневые манифесты и манифесты рабочих пространств/lock-файл, `scripts/build/`, автономная сборка Next.js, содержимое пакета `dist/`,
  метаданные Electron для платформ, рабочие процессы CI и маркеры развёртывания.
- Поддерживаемые диапазоны версий Node и разрешённое использование Bun, описанное в `CLAUDE.md`, должны оставаться неизменными.
- Артефакты сборки не должны отслеживаться; применяются политики зависимостей, лицензий, рабочих процессов и пакетов.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # изменения зависимостей или lock-файла
npm run check:pack-policy      # изменения поверхности опубликованного пакета
npm run lint
```

Используйте `npm run build` локально, только если изменение затрагивает компиляцию, автономную сборку, ресурсы
или упаковку среды выполнения. Используйте `npm run build:release` только для проверки выпуска/развёртывания. Сборка в CI
является окончательным кроссплатформенным сигналом; изменения Electron для конкретной платформы требуют соответствующей целевой сборки
или подтверждения дымового тестирования.

## Скрипты разработчика для общей машины

Два вспомогательных скрипта в `scripts/dev/` реализуют локальный цикл работы на devbox, где активны другие сеансы:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # файлы из merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # только эти файлы
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # изолированное рабочее дерево, безопасное для параллельной работы
```

- `typecheck-touched.sh` проверяет типы только в затронутых файлах `.ts/.tsx` через временный
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) с лимитом кучи 6 ГБ, поэтому он заменяет общепроектный `tsc -p tsconfig.json`,
  который приводит к OOM на загруженной машине. Скрипт выводит ошибки в затронутых файлах и одну
  итоговую строку, а затем завершается с кодом `1` при наличии ошибок в затронутых файлах, `2`, если
  ошибки есть только в импортированных файлах или tsc завершился без диагностических сообщений
  (прочитайте указанный им журнал в `_artifacts/typecheck-touched/`), и `0`, если ошибок нет.
  Временный tsconfig всегда удаляется; никогда не добавляйте его в коммит.
- `new-worktree.sh` сериализует параллельные запуски с помощью
  `<git-common-dir>/omniroute-new-worktree.lock` (по умолчанию ожидает до 600 с, выводя заметное
  сообщение; способ переопределения описан в заголовке скрипта) и откатывает созданную им ветку,
  если `git worktree add` завершается с ошибкой до появления рабочего дерева, поэтому перед повторной
  попыткой не требуется вручную выполнять `git branch -D`. Жёсткие ссылки на `node_modules` и копия
  `.husky/_` остаются без изменений.

## Локальный цикл работы с кандидатом

Тесты исходного кода не могут доказать, что упакованный артефакт запускается: ошибки в списках
упаковки, сокращённых зависимостях и нативных бинарных файлах проявляются только после установки и
запуска tarball. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) — локальная часть процесса
однократной сборки, проверки и продвижения из RFC #8084: он собирает один кандидат, проверяет именно
этот артефакт, продвигает его путём переименования каталогов и откатывает, если продвинутый слот не
проходит проверку работоспособности.

```bash
npm run dev:candidate -- run --dry-run --json  # вывести план, ничего не изменять
npm run dev:candidate -- run                   # собрать + проверить + продвинуть, автоматически откатить
npm run dev:candidate -- build                 # npm pack + установка в _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # запуск на свободном порту, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # поменять местами current и previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # повторно использовать tarball, собранный в другом месте (CI)
```

- **Собирайте один раз.** `build` упаковывает текущее дерево (ему требуется `dist/server.js`,
  поэтому сначала выполните `npm run build:release`) или копирует `--from-tarball`, а затем
  устанавливает tarball в изолированный префикс npm, поскольку tarball не содержит `node_modules`.
  Идентификатором служит короткий sha `HEAD` (`-dirty`, если в дереве есть локальные изменения) либо
  `tgz-<sha256>` для tarball. Уже собранный чистый идентификатор используется повторно вместо новой
  сборки; передайте `--force`, чтобы пересобрать его.
- **Проверяйте пакет, а не исходный код.** `validate` запускает установленный CLI
  (`serve --port <free port>`) с новым `DATA_DIR=<candidate>/data`, фиктивными секретами и удалёнными
  из окружения операторскими `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` и `INITIAL_PASSWORD`,
  чтобы проверить режим loopback без ключей для новой установки. Он ожидает, пока
  `GET /api/health` начнёт возвращать 200, требует, чтобы `GET /v1/models` возвращал 200,
  останавливает группу процессов и записывает результат в `validation.json` вместе с хешем tarball.
- **Продвигайте тот же артефакт.** `promote` отклоняет кандидат без успешной проверки для текущего
  хеша его tarball. Активный слот по умолчанию — `_artifacts/candidate/current`; `--target <dir>`
  выбирает другой каталог в той же файловой системе, а его предыдущим слотом становится
  `<dir>.previous`. Каждое переименование атомарно, а при промежуточном сбое уже выполненные
  переименования отменяются.
- **Выполняйте откат.** `run` повторно проверяет продвинутый слот и меняет `current` и `previous`
  обратно, если проверка завершается неудачно. Кандидат, не прошедший первую проверку, никогда не
  продвигается.

Всё записывается в игнорируемый git каталог `_artifacts/candidate/`; существующая установка
OmniRoute и её каталог данных никогда не затрагиваются. Продвинутый CLI находится по пути
`_artifacts/candidate/current/prefix/bin/omniroute`; при его использовании запускайте его со своим
`DATA_DIR`. Коды завершения: `0` — успех, `1` — неудачная проверка или продвижение, `2` — ошибка
использования или отсутствующая сборка.

## Локальный цикл и CI

| Выполняется локально для каждого патча                                                                      | CI обеспечивает широкую проверку                                                     |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Прямые тесты поведения и указанные выше проверки категорий                                                  | Разделённый на сегменты полный набор модульных и последовательных тестов             |
| `npm run lint`                                                                                              | Наборы тестов Vitest и пороговые проверки покрытия/качества                          |
| Проверка типов или сборка — только если этого требует затронутый контракт                                   | Продукционная сборка, проверки безопасности, документации, зависимостей и политик PR |
| Ручные проверки взаимодействия/в реальном времени — только если поведение нельзя подтвердить автоматизацией | Межзадачные интеграционные и платформенные проверки, настроенные рабочим процессом   |

Успешный целевой цикл служит подтверждением корректности изменённого контракта, но не гарантирует,
что несвязанные проверки CI пройдут. В то же время не следует заставлять каждое локальное изменение
ожидать выполнения полной матрицы репозитория.

## Контрольный список сверки

Перед запросом на проверку:

- Убедитесь, что базовой веткой PR по-прежнему является самая новая активная ветка `release/v*`.
- Получите изменения из этой базовой ветки и просмотрите коммиты, добавленные с момента создания вашей ветки.
- Проверьте `git diff <active-base>...HEAD` на наличие случайных или автоматически сгенерированных изменений.
- Устраняйте конфликты в каталогах и сгенерированных документах, обновляя исходные данные и повторно генерируя результат.
- После сверки повторно запустите каждый целевой тест и каждую проверку, указанные в описании PR.
- Никогда не ослабляйте проверки и не удаляйте обязательные тесты лишь для соответствия изменившейся базовой ветке.

Правила заморозки выпуска и смены целевой ветки см. в документе
[Модель ветвления и выпуска](BRANCHING_MODEL.md). Полный перечень проверок CI см. в документе
[Справочник по проверкам качества](../architecture/QUALITY_GATES.md).
