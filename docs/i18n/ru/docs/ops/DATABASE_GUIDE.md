> **Кратко**: OmniRoute использует **SQLite с журналированием WAL** в качестве основного хранилища и шифрование **AES-256-GCM** для конфиденциальных полей при хранении. В этом руководстве рассматриваются схема, миграции, резервное копирование/восстановление и эксплуатационные инструкции.

**Источники:**

- `src/lib/db/core.ts` — синглтон + SCHEMA_SQL (17 базовых таблиц)
- `src/lib/db/migrationRunner.ts` — версионированные миграции
- `src/lib/db/migrations/` — 167 версионированных SQL-файлов
- `src/lib/db/encryption.ts` — вспомогательные функции шифрования
- `src/lib/db/backup.ts` — экспорт/импорт резервных копий
- `src/lib/db/healthCheck.ts` — диагностика состояния

## Почему SQLite?

OmniRoute выбрал SQLite вместо PostgreSQL/MySQL по нескольким причинам:

| Фактор                    | SQLite                                             | PostgreSQL                                             |
| ------------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| **Развертывание**         | Встраиваемая БД — отдельный сервер не нужен        | Требуется настройка сервера                            |
| **Шифрование**            | На уровне приложения (AES-256-GCM)                 | Встроенное TDE                                         |
| **Производительность**    | Быстрее для малых/средних нагрузок                 | Лучше для огромного числа параллельных операций записи |
| **Параллелизм**           | Режим WAL допускает параллельное чтение            | Полноценный MVCC                                       |
| **Резервное копирование** | Копирование одного файла                           | `pg_dump` или снимок файловой системы                  |
| **Вариант использования** | Установка для одного пользователя, встраиваемая БД | Многопользовательский SaaS                             |

Для развертываний с **одним пользователем и одним экземпляром** (основной вариант использования OmniRoute) SQLite проще и быстрее.

### Журналирование WAL

`core.ts` открывает базу данных в **режиме WAL (Write-Ahead Logging — журналирование с упреждающей записью)**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL допускает **параллельное чтение** во время записи — это важно для панели мониторинга, которая выполняет запросы одновременно с регистрацией запросов.

Размер кэша по умолчанию составляет **65 536 КиБ (64 МиБ)**. SQLite интерпретирует отрицательное значение
`cache_size` как приблизительную верхнюю границу в КиБ и выделяет страницы по мере необходимости.
В разделе **Настройки > Система и хранилище > Размер кэша** можно указывать целые значения от **1 до
1 000 000 КиБ**; при сохранении настройка применяется к активному подключению к базе данных,
а при запуске OmniRoute восстанавливает сохраненное значение.

## Расположение базы данных

Файл SQLite хранится по следующему пути:

| ОС      | Путь                                                        |
| ------- | ----------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                               |
| macOS   | `~/.omniroute/storage.sqlite`                               |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                   |
| Docker  | `/app/data/storage.sqlite` (настраивается через `DATA_DIR`) |

Сопутствующие файлы:

- `storage.sqlite-wal` — журнал упреждающей записи
- `storage.sqlite-shm` — файл общей памяти
- `call_logs/` — артефакты полезной нагрузки запросов (если включено)

**Изменение расположения:**

```bash
DATA_DIR=/custom/path omniroute
```

### Границы модулей

Основное архитектурное правило: **модули не обращаются напрямую к таблицам друг друга**. Для работы с данными другого модуля импортируйте функцию из этого модуля.

```ts
// ❌ НЕПРАВИЛЬНО: прямой SQL-запрос к таблице другого модуля
db.prepare("SELECT * FROM provider_connections").all();

// ✅ ПРАВИЛЬНО: используйте функцию модуля providers
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

Соблюдение этого правила контролируется при проверке кода — статическая проверка отсутствует, но нарушения отмечаются.

## Миграции

OmniRoute использует** версионные, идемпотентные миграции** в `src/lib/db/migrations/`. Каждая миграция представляет собой отдельный файл SQL. Сосуществуют два формата именования; версия, записанная в `_omniroute_migrations` представляет собой числовой префикс.

### Именование миграции

| Формат                                          | Пример                               | Используется для                                                                                                                                                                     |
| ----------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `NNN_description.sql` (ровно 3 цифры)           | `241_seen_models.sql`                | Старая серия `001`–`241`. Заморозка при получении формата метки времени (`240` и `241` были объединены непосредственно перед этим): ни один новый файл не получает порядковый номер. |
| `YYYYMMDDHHMMSS_description.sql` (14 цифр, UTC) | `20261113120000_add_usage_index.sql` | Каждая миграция, созданная с 13 ноября 2026 г.                                                                                                                                       |

Почему изменение: при последовательных номерах параллельная PRs выбирала один и тот же следующий номер, и всем, кроме одного, перед объединением приходилось перенумеровывать. Временная метка UTC дает каждому PR свою собственную версию.

Правила формата временной метки (обеспечиваются `npm run check:migration-numbering`, используются совместно с генератором в `scripts/check/lib/migrationNaming.mjs`):

- Временная метка — это реальная дата и время UTC, не ранее `20261113000000` и не позднее, чем через 10 минут.
- Описание представляет собой строчную букву `snake_case` начинающуюся с буквы (`a-z`, `0-9`, одинарный `_` между словами), не более 80 символов.
- Два файла с одинаковой меткой времени являются дубликатами.
- Правило отсутствия пробелов применяется только к старой серии: каждое число от `001` до `241` должно существовать, за исключением известных пробелов `026`, `055` и `121`. Удаление `241` (или любого старого файла) приводит к сбою шлюза. `001` и `241` никогда не могут быть добавлены в список разрешений `KNOWN_GAPS`. Файлы с отметкой времени никогда не создают пробелов.
- Каждая запись в `src/lib/db/migrations/` должна представлять собой обычный файл с допустимым именем `.sql` в нижнем регистре. Каталог, символическая ссылка, файл `.SQL` или `.sql.bak`, скрытый файл или имя с пробелом не проходят проверку, потому что бегун пропустит их автоматически или вылетит при загрузке.

**Применить заказ.** Бегун сортирует по числовому значению префикса, а не по тексту: сначала старые файлы `001`–`241`, затем файлы с метками времени в порядке меток времени, затем любые каталоги в пространстве имен, зарегистрированные с помощью `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (такие версии, как `ee-001`). Ожидаемая миграция — это любой файл, версия которого отсутствует в `_omniroute_migrations`, поэтому миграция из более старой ветки, которая объединяется с более новой, по-прежнему применяется к существующим базам данных.

**Временная метка — это порядок создания, а не порядок слияния.** Если ваша миграция зависит от таблицы или столбца, созданных в результате миграции с** новее** временная метка (например, одна из другой PR, которая объединилась первой), новая база данных запустится первой и выйдет из строя. Пока ваш PR все еще открыт, заново сгенерируйте имя файла с помощью `npm run db:new-migration`, чтобы он получил более новую временную метку, или сделайте его независимым. `npm run test:migrations:fresh` применяет каждую миграцию к пустой базе данных и фиксирует это.

### Объединенная миграция никогда не удаляется и не переименовывается

Как только файл миграции попадает в ветку выпуска или `main`, он уже запущен в базах данных гомологов и разработчиков, при установках VPS и в синхронизации Enterprise. С тех пор:

- **Никогда не удаляйте его.** Новые установки потеряют свою схему, в то время как обновленные базы данных сохранят ее.
- **Никогда не переименовывайте его.** Версия в `_omniroute_migrations` больше не будет соответствовать файлу, поэтому каждая база данных, которая уже применила ее, будет запускать ее снова. Неидемпотентный SQL затем дублирует данные или останавливает загрузку.
- **Нужна другая схема?** Создайте новую миграцию с помощью `npm run db:new-migration`.

Переименование безопасно только для файла, который еще не объединен, к чему относятся подсказки ворот. Тег выпуска здесь ничего не меняет: каждый запрос на ветку `release/v*` публикует образ Docker `:next` и запускается на гомологе, при установке VPS и синхронизации Enterprise, поэтому объединенная миграция выполняется в реальных базах данных до того, как появится какой-либо тег `vX.Y.Z`. Шлюз не выполняет каждое удаление базового файла, помеченного или нет.

- **Возврат объединенной миграции.** `git revert`, который удаляет файл, выходит из строя. Сохраните файл и отмените его схему при новой миграции: `npm run db:new-migration -- <description>`, с `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` и так далее. Обновленные и новые базы данных имеют одну и ту же схему.
- **Одно принятое переименование: запись совместимости и идентичное содержимое.** Если объединенный файл необходимо переместить (например, два объединенных файла имеют общую временную метку и бегун останавливается из-за конфликта версий), переименуйте более поздний файл, не трогая его SQL, и добавьте `{ fromVersion, fromName, toVersion, toName }` к `RENAMED_MIGRATION_COMPATIBILITY` в `src/lib/db/migrationRunner/constants.ts`. В базах данных, в которых применялась старая версия, строка `_omniroute_migrations` перемещается вместо повторного запуска файла. Шлюз предупреждает о таком переименовании и всегда запускает для него проверку коммутации, независимо от новой временной метки: при новых установках файл применяется в новой позиции, а в обновленных базах данных — нет, поэтому выберите новую временную метку рядом со старой. Шлюзу не удается переименовать, если содержимое изменилось (изменение схемы все еще происходит при новой миграции) или если целевой файл записи отсутствует на диске.
- **Никогда не переименовывайте в пределах одной и той же временной метки.** Переименование, при котором сохраняется временная метка и изменяется только описание, не проходит шлюз, с записью или без нее. Если у записи `toVersion` равен `fromVersion`, исполнитель удаляет старую строку `_omniroute_migrations` и снова применяет файл к каждой базе данных, которая уже запускала его. Без записи средство запуска отслеживает только версию: он пропускает файл в этих базах данных (новый контент там никогда не запускается) и регистрирует ошибку перенумерации при каждой загрузке. Используйте другую временную метку плюс запись совместимости или сохраните имя.
- **Шлюз проверяет, чтобы переименованный файл не запускался снова.** Для каждого скрытого переименования шлюз передает новое имя файла на проверку коммутации с помощью `--must-not-apply`. Проверка загружает обновленную базу данных с реальным исполнителем, и если исполнитель снова применяет этот файл (например, из-за того, что запись имеет неправильную версию или имя, или потому, что анализатор текста шлюза читает `constants.ts` иначе, чем TypeScript), шлюз завершается с ошибкой с `migration renomeada rodaria de novo` и просит вас проверить старые и новые версии и имена записи.

### Что ворота сверяют с базой

При запросе на извлечение и запуске очереди слияния `npm run check:migration-numbering` сравнивает `src/lib/db/migrations/` на диске с тем же каталогом в базовой ветке. База в следующем порядке: `--base-latest-tag`, `--base <ref>`, переменная `MIGRATION_BASE_REF` или, если `GITHUB_EVENT_NAME` равна `pull_request`, `pull_request_target` или `merge_group`, первый родительский элемент фиксации слияния, `merge_group.base_sha` полезных данных события или `git merge-base HEAD origin/$GITHUB_BASE_REF`. При запросе на включение или запуске очереди слияния без разрешимой базы шлюз выходит из строя. Вне CI без `--base` он печатает `comparação com a base: pulada (sem --base)` и пропускает эти правила.

`--base-latest-tag` сравнивается с тегом новейшего выпуска (`vX.Y.Z` в порядке семверов; теги с суффиксами, такие как Nightlies, не учитываются), который находится в истории `HEAD`, с теми же правилами, что и `--base`. Release-Green (`scripts/quality/validate-release-green.mjs`) запускает шлюз таким образом, потому что push-запуски и запланированные запуски не имеют базы запросов на включение, и слияние может произойти без нового запуска CI. Без тега выпуска в истории ворота выходят из строя; запустите `git fetch --tags` (в CI `actions/checkout` с `fetch-depth: 0` выводит теги).

За один запуск проверки коммутации охватываются неупорядоченные, отредактированные и переименованные файлы вместе.

Проверка коммутации (`scripts/check/migration-commutation.ts`) создает две временные базы данных с реальным путем установки:** обновленный** один (загрузка с базовой миграцией, затем повторная загрузка с тем же файлом с миграциями запроса на включение) и** свежий** один (одна загрузка с миграциями запроса на включение). Он сравнивает полученные схемы: таблицы и столбцы (игнорируя порядок столбцов), ограничения UNIQUE / PRIMARY KEY и FOREIGN KEY, нормализованный текст `CREATE TABLE` каждой таблицы (который охватывает ограничения CHECK, параметры сортировки, сгенерированные столбцы и параметры таблицы), индексы, триггеры и представления. Данные строк не сравниваются. Если они совпадают, шлюз печатает, что файл неисправен, но коммутирует и проходит. Если они различаются, шлюз терпит неудачу с разницей и подсказкой для случая: для файла с нарушением порядка повторно сгенерируйте его имя с помощью `npm run db:new-migration`, что безопасно, поскольку файл еще не объединен; для отредактированного базового файла восстановите базовое содержимое и поместите изменения в новую миграцию; для переименованного файла отмените переименование или выберите другую новую временную метку, в которой он перемещается, а не ту же самую временную метку с другим именем. Если сама проверка не может быть запущена, шлюз в CI дает сбой и предупреждает только локально. Для отредактированного базового файла обновленная база данных создается с использованием базового содержимого этого файла, и вторая загрузка пропускает ее, поскольку ее версия уже записана. Для переименованного файла обновленная база данных создается с использованием файла под его старым именем, а при второй загрузке строка `_omniroute_migrations` перемещается через запись совместимости вместо повторного запуска; шлюз передает новое имя с помощью `--must-not-apply`, поэтому проверка завершится неудачей, если вторая загрузка применит его. Если миграцию запроса на включение не удается применить на обновленном пути, то есть после каждой базовой миграции (независимо от того, завершается ли она сбоем при новой установке), шлюз сообщает `migration do PR não aplica` и просит вас исправить SQL в соответствии с текущей базовой схемой; если файл зависит от другого переноса запроса на включение с более поздней меткой времени, повторно создайте его имя с помощью `npm run db:new-migration`.

Чтобы выполнить то же сравнение локально, явно передайте базу, например `npm run check:migration-numbering -- --base origin/<base-branch>` или `npm run check:migration-numbering -- --base-latest-tag` для сравнения с последней версией.

### Преобразование миграции `NNN` Open PR

Запрос на включение, открытый до переключения, все еще может содержать последовательный файл, такой как `242_add_widgets.sql`. Старые числа выше `241` отклоняются, поэтому преобразуйте их перед объединением:

1. **Переименуйте файл с генератором, сохранив описание.** Запустите `npm run db:new-migration -- <same description>`, чтобы получить новое имя, переместите в него SQL и удалите старый файл `NNN_`. Описание должно оставаться идентичным: ему соответствует запись совместимости ниже.
2. **Добавьте запись о совместимости, если в постоянной базе данных использовался старый номер.** Если какая-либо сохраненная база данных (гомолог, VPS, собственная установка участника) выполнила сборку PR с файлом `NNN_`, добавьте `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` к `RENAMED_MIGRATION_COMPATIBILITY` в `src/lib/db/migrationRunner/constants.ts`. Это** требуется для `237` к `241`** : эти слоты теперь содержат канонические `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` и `241_seen_models.sql`, и без записи такая база данных навсегда пропускает каноническую миграцию и снова запускает преобразованную. Это также работает для слота, который остается пустым, например `242`, когда местом назначения является временная метка. Если сомневаетесь, добавьте запись. Где вы добавляете его в массив, не имеет значения: когда целевой слот записи все еще содержит строку, которую другая запись перемещает (например `237` удерживает строку PR, в то время как более старая строка `usage_history_calculated_cost` ожидает перемещения в `237`), бегун позволяет этой записи ждать, пока слот не освободится. Только реальный конфликт, например, слот, занимаемый строкой, в которой запись не перемещается, или две записи, которые меняют местами слоты, останавливает загрузку с помощью `Cannot reconcile ...`.
3. **Сохраняйте SQL идемпотентным** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), поскольку преобразованная миграция может соответствовать базе данных, в которой ее схема уже существует.
4. **Перемещение особых случаев с указанием версии.** Если PR добавила регистр для своего старого номера в `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) или в `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`), измените ключ на новую метку времени.

`tests/unit/db/codex-fence-migration-rename.test.ts` — рабочий пример теста переименованной миграции.

### Бэкпорты в ветки до перехода

Никогда не выбирайте и не переносите файл `YYYYMMDDHHMMSS_` в ветку, предшествующую коммутатору (например, в старую ветку `release/v*` ). Там бегун сортирует имена файлов как текст, поэтому файл с меткой времени будет работать между `201_` и `202_` в новой базе данных, а старый шлюз не понимает 14-значных префиксов. В такой ветке запишите изменение как следующий файл `NNN_` этой ветки, идемпотентный, чтобы он не работал, когда версия с отметкой времени появится позже.

### Как происходят миграции

При запуске `migrationRunner.ts`:

1. Создает таблицу `_omniroute_migrations`, если она не существует.
2. Запросы для уже примененных миграций
3. Применяет все новые миграции по порядку, каждую в транзакции.
4. Записывает каждую примененную миграцию с отметкой времени.

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### Идемпотентность

Миграции должны быть** идемпотент** — запускающий их дважды, должен быть пустым:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

Свободно используйте предложения `IF NOT EXISTS`, `IF EXISTS` и `OR IGNORE` / `OR REPLACE`.

### Добавление новой миграции

1. **Создать файл с помощью генератора** : `npm run db:new-migration -- <description>` (например `npm run db:new-migration -- add combo priority`). Он записывает `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` с текущим временем UTC и заголовком комментария, перемещается на одну секунду вперед, если используется эта временная метка, и никогда не перезаписывает файл. Не выбирайте номер вручную.
2. **Используйте безопасный DDL** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **Аккуратно заполняйте данные** : используйте `UPDATE ... WHERE ...` для обработки существующих строк
4. **Проверьте порядок и наименование** : `npm run test:migrations:fresh` (все миграции в пустой базе данных) и `npm run check:migration-numbering`
5. **Тест на копии** : никогда не запускайте непроверенные миграции в рабочей среде.

Пример:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **Обратная несовместимость изменений** (например, удаление столбцов) являются сложными. OmniRoute поддерживает ли NOT понижение версии — после применения миграции, изменение схемы является постоянным. Планируйте соответственно.

## Шифрование хранимых данных

Конфиденциальные поля (ключи API, токены OAuth, строки подключения) шифруются при хранении с использованием **AES-256-GCM**.

### Как это работает

```ts
// src/lib/db/encryption.ts (упрощённо)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### Где это используется

- `provider_connections.api_key` — шифруется на уровне приложения
- `provider_connections.access_token`, `refresh_token`, `id_token` — шифруются на уровне приложения
- Записи `key_value` с `namespace = "secrets"` — шифруются на уровне приложения
- `proxy_registry.auth` — шифруется на уровне приложения (если присутствует)

### Ключ шифрования

Ключ шифрования формируется на основе **секретной фразы** (задаётся через переменную окружения `STORAGE_ENCRYPTION_KEY`) и **соли** (хранится в БД). Для расшифровки данных необходимы оба значения.

```bash
# Сгенерировать безопасную секретную фразу
openssl rand -hex 32

# Задать в .env
STORAGE_ENCRYPTION_KEY=<ваш-ключ>
```

> **Критически важно**: потеря ключа шифрования означает потерю доступа ко всем зашифрованным данным. **Храните резервную копию ключа отдельно от базы данных**.

### Что НЕ шифруется

По соображениям производительности следующие данные хранятся в открытом виде:

- Отображаемые имена провайдеров
- Определения моделей (они и так общедоступны)
- Правила маршрутизации
- Записи об использовании (без персональных данных)

---

## Особенности шифрования (v3.8.16+)

OmniRoute использует **`migrateLegacyEncryptedString()`** для прозрачной поддержки двух схем шифрования:

- **Устаревшая** (до v3.5.0): «шифрование» на основе XOR (не является настоящей криптографией)
- **Текущая**: AES-256-GCM с корректным IV и тегом аутентификации

Вспомогательная функция миграции обнаруживает устаревший формат и при первом чтении повторно шифрует данные с использованием новой схемы. Это означает, что старую базу данных можно обновить без потери учётных данных.

## Кэш чтения

Для часто считываемых данных (моделей, провайдеров, настроек) `readCache.ts` предоставляет **кэш в памяти**:

```ts
// Кэшируется при запуске, сбрасывается при записи
const providers = await getCachedProviders(); // Быстро, из памяти
const fresh = await listProviders(); // Медленно, обращается к БД
```

| Кэшируемая сущность    | Ключ кэша      | TTL       |
| ---------------------- | -------------- | --------- |
| `models`               | `models:v1`    | До записи |
| `provider_connections` | `providers:v1` | До записи |
| `settings`             | `settings:v1`  | До записи |
| `combos`               | `combos:v1`    | До записи |

Кэш сбрасывается при каждой записи в соответствующую таблицу.

## Резервное копирование и восстановление

### Резервное копирование вручную

```bash
# Используйте CLI для создания локальной резервной копии
omniroute backup create --name pre-migration

# Или через API
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

Файл резервной копии содержит:

- Все таблицы БД (сериализованные в JSON)
- Артефакты журнала вызовов (закодированные в base64, необязательно)
- Настройки и секреты (в зашифрованном виде)
- Конфигурацию плагинов

### Восстановление

```bash
# Через CLI
omniroute restore pre-migration

# Через API
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **Предупреждение**: восстановление перезаписывает всю БД. Сначала остановите все клиенты.

### Автоматическое резервное копирование

```bash
# Включите автоматическое ежедневное резервное копирование через CLI
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

Расписание выполняется на стороне сервера фоновой задачей, которая запускается каждые 30 секунд
(по умолчанию) и сопоставляет cron-выражение с локальным временем сервера.

| Переменная                                  | Значение по умолчанию | Описание                                                                                                                       |
| ------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`               | Интервал запуска в мс (мин. `5000`). Должен быть короче 60 с, чтобы надёжно попадать в минуту, соответствующую cron-выражению. |

### Горячее резервное копирование SQLite

Для резервного копирования работающей БД без простоя:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

При этом используется API оперативного резервного копирования SQLite — команду можно безопасно выполнять во время работы OmniRoute.

## Настройка производительности

### Режим WAL

WAL включен по умолчанию. Для рабочих нагрузок с большим объемом записи рассмотрите следующее:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute не устанавливает `journal_size_limit`. Контрольная точка перемещает кадры WAL в основной файл, но файл WAL сохраняет свой наибольший выделенный размер. Защита `OMNIROUTE_WAL_GUARD_MAX_MB` только предупреждает и запускает `wal_checkpoint(RESTART)`; это не ограничение размера диска.

### Индексы

Ключевые индексы производительности (автоматически создаются при миграции):

- `idx_models_provider` поиск модели — по поставщику
- Расширение комбинированной цели `idx_combo_targets_combo_id` —
- `idx_usage_history_api_key_timestamp` аналитика использования —
- `idx_quota_snapshots_api_key_window` — отслеживание квот
- `idx_call_logs_timestamp` — запросы к журналу вызовов

Чтобы добавить новый индекс, создайте миграцию:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### I/O с отображением в памяти

Для очень больших баз данных (> 10 ГБ) отображение памяти можно настроить с помощью прагмы SQLite :

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### Уплотнение

Длительно работающие экземпляры OmniRoute выигрывают от периодического использования `VACUUM`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

Запускать ежемесячно в периоды с низким трафиком. (Режим WAL уменьшает необходимость, но не устраняет ее.)

## Проверка работоспособности

`src/lib/db/healthCheck.ts` предоставляет **диагностику работоспособности на уровне БД**:

Оба метода требуют аутентификации (в противном случае возвращается `401`). `GET` выполняет только диагностику; `POST` выполняет
ту же проверку с включённым параметром `autoRepair`.

```bash
GET  /api/db/health   # диагностика
POST /api/db/health   # диагностика + восстановление
```

Ответом является `DbHealthCheckResult`, сформированный функцией `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Бюджеты доменов ссылались на API-ключи, которых больше не существует.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| Поле              | Значение                                                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | Имеет значение `true`, если `issues` пуст. `driver` никогда не влияет на это значение.                                                                                        |
| `issues[].type`   | Одно из значений: `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`.                                                                            |
| `repairedCount`   | Количество строк, восстановленных во время этого запуска; всегда равно `0`, если `autoRepair` имеет значение false.                                                           |
| `backupCreated`   | Указывает, была ли создана резервная копия перед восстановлением.                                                                                                             |
| `checkedAt`       | Временная метка ISO, общая для запуска и любой созданной им записи о восстановлении.                                                                                          |
| `driver.name`     | Драйвер SQLite, обслуживающий проверяемую базу данных.                                                                                                                        |
| `driver.degraded` | Имеет значение `true`, если записи не сохраняются надёжно в файле базы данных — резервный WASM-драйвер `sql.js` (с сохранением всего файла целиком) или база данных в памяти. |

Те же данные возвращаются инструментом MCP `omniroute_db_health_check`.

Выполните `PRAGMA integrity_check`, чтобы обнаружить повреждения:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# Должно быть выведено: ok
```

Если команда возвращает что-либо, кроме `ok`, **немедленно прекратите использовать базу данных** и восстановите её из резервной копии.

## Аварийное восстановление

### Сценарий 1: потерян файл WAL

Файл `-wal` отсутствует, но `-shm` и основная база данных не повреждены:

```bash
# Автоматически восстанавливается при следующем открытии
omniroute
```

Если SQLite не может выполнить автоматическое восстановление:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### Сценарий 2: повреждён основной файл базы данных

Восстановите его из резервной копии:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` только загружает полный архив `.tar.gz` с работающего сервера
(`GET /api/db-backups/exportAll`, требуются учётные данные оператора); эта команда ничего не восстанавливает.

### Сценарий 3: потерян ключ шифрования

**Восстановление невозможно** без ключа. Зашифрованные поля невозможно прочитать. Повторно добавьте всех поставщиков вручную с новыми учётными данными.

> **Мера предосторожности**: всегда создавайте отдельную резервную копию ключа шифрования, желательно в менеджере паролей или KMS.

### Сценарий 4: диск заполнен

SQLite будет возвращать ошибки `SQLITE_FULL`. Освободите место на диске, затем выполните:

```bash
# Выполнить контрольную точку WAL, чтобы освободить место
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## Устранение неполадок

### «База данных заблокирована»

Другой процесс удерживает блокировку записи. Выполните одно из следующих действий:

- Дождитесь завершения другого процесса (проверьте с помощью `lsof | grep storage.sqlite`)
- Завершите другой процесс
- Если проблема сохраняется, перезапустите OmniRoute

### «Нарушено ограничение внешнего ключа»

Модуль домена нарушает ссылочную целостность. Проверьте:

- Потерянные строки в зависимых таблицах
- Каскадные удаления, которые не были распространены
- Недавнюю миграцию, изменившую внешний ключ

Выполните `PRAGMA foreign_key_check;`, чтобы найти нарушения.

### «Недостаточно памяти»

Ввод-вывод SQLite с отображением в память превышает ограничение ОС. Уменьшите объём с помощью директивы pragma SQLite:

```sql
PRAGMA mmap_size = 134217728;  -- 128 МБ вместо 256 МБ
```

Или отключите его:

```sql
PRAGMA mmap_size = 0;
```

### «Сбой миграции в процессе выполнения»

Миграция выполнялась в транзакции, поэтому изменения должны были откатиться. Если этого не произошло:

1. **Остановите OmniRoute** (чтобы предотвратить дальнейшие попытки)
2. **Проверьте состояние БД** с помощью `sqlite3`
3. **Исправьте вручную** частично выполненную миграцию
4. **Снова запустите** OmniRoute (будет выполнена повторная попытка миграции)

Чтобы предотвратить такую ситуацию, всегда сначала тестируйте миграции на копии.
