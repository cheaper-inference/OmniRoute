## Посадка на ветку релиза

Омни-очередь управляет посадками в `release/vX.Y.Z`. Прочтите `mode` верхнего уровня в `config/merge-queue/config.json` в ветке по умолчанию перед размещением PR. См. [Омни-очередь](OMNI_QUEUE.md).

- **`shadow`** запускает проверку и оставляет приземление для ручного слияния. Примените `omni-queue` к утвержденному PR в его последней главе. Проверьте право на участие с помощью `npm run queue -- why <PR>`. Подождите вердикта по этой голове в `npm run queue -- history --base <branch>`. Продолжайте `would-land`. На `culprit-found` или `would-dequeue` задержите слияние и устраните причину.
- **Теневые исключения.** Поезд с зеленым полным CI относительно текущего базового наконечника может продолжить движение без отдельного вердикта очереди. То же исключение применяется, когда заголовок PR уже содержит текущий базовый наконечник.
- **`live`** использует метку `omni-queue` для запуска целевой страницы. Только очередь получает PR. Оставьте команды слияния и прямые отправки в очередь.

Для каждой посадки требуется разрешение владельца и соответствующие необходимые проверки. Применяйте `omni-queue` только после того, как владелец разрешит посадку. Поставленные в очередь PRs касающиеся защищенных путей, также требуют решения `protected-approved` владельца для этого PR.

Набор правил «Требовать зеленые ворота при активном выпуске» требует наличия зеленых `Gate / CI` и `Gate / Quality` на головке. Никогда не используйте `--admin` для обхода красных ворот. Блоки заморозки выпуска сливаются с замороженной веткой. См. [жесткое правило 21](HARD_RULES_DETAIL.md). Никогда не отмечайте, не объединяйте и не отправляйте запрос на включение, что другой сеанс работает. См. [жесткое правило 22](HARD_RULES_DETAIL.md).

## Запрос на вытягивание поезда

1. Запустите ветку поезда с кончика базовой версии текущей версии. Интегрируйте точные утвержденные главы участников с помощью коммитов слияния. Сохраните историю коммитов, избегая сдавливания и перебазирования.
2. Откройте один запрос на ветку поезда. Подтвердите этот PR с собственным полным CI на текущей базовой подсказке. Перед приземлением еще раз проверьте кончик основания и утвержденные головки элементов. Обновите поезд и его CI когда проверенный кандидат изменится.
3. Поместите поезд PR с фиксацией слияния в соответствующем режиме очереди. В режиме реального времени метод посадки `merge-ff` очереди сохраняет коммиты слияния. Исходные главы участников становятся доступными из ветки выпуска. GitHub помечает член PRs как объединенный, а в коммитах сохраняются их авторы.

Общедоступный пример — [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071). Он объединил 18 участников PRs и получил коммит по слиянию 24 ноября 2026 года.

Обратная синхронизация от `main` со следующей веткой выпуска также осуществляется посредством коммита слияния. Сохранение происхождения `main` необходимо для последующих обратных синхронизаций. См. [Изоляция рабочего дерева](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash).

## Локальный валидатор поезда слияния

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

Валидатор извлекает базу и головы PR и объединяет их в одноразовое рабочее дерево. Он запускает пакет контроля четности один раз для полученного дерева. Неудачная выборка головы или конфликт слияния приводят к удалению этого PR, и сценарий продолжает работу с оставшимся PRs.

- **`--plan`** распечатывает шаги выбранного режима и завершает работу без создания рабочего дерева или обращения к пульту дистанционного управления. Объедините его с `--fast`, чтобы проверить быстрый план.
- **`--fast`** запускает общие статические вентили, выбранные измененные файлы `node:test` под `tests/unit/` и `npm run test:vitest`. Запускайте полную локальную проверку не реже одного раза в день по накопленным подсказкам при использовании быстрого режима.
- **Полный режим** добавляет статические вентили только для полной версии и запускает `npm run test:unit` и `npm run test:vitest`.

Неисправные статические ворота запускаются повторно на нетронутой базе, если базовый зонд доступен. Скрипт сообщает об унаследованных сбоях и продолжает работу, пока в базе также не появится каждая обнаруженная строка нарушения и общее количество не увеличится.

| Выход | Значение                                                                                                                                                      |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`   | Распечатал план или завершил комплект. В сводке пакета перечислены все унаследованные статические сбои и удаленные PRs.                                       |
| `1`   | Недопустимые аргументы, проверка Git не выполнена, предварительная проверка не удалась или PR не подключен.                                                   |
| `2`   | Проверка пакета не удалась и не квалифицировалась как унаследованная. Оператор может разделить пакет пополам, удалить проблемный PR и запустить его повторно. |

Местный пропуск предоставляет диагностические данные только для досье владельца. Для каждой целевой страницы по-прежнему требуется авторизация владельца, собственные необходимые проверки и вердикт теневой очереди, когда это применимо.

## Многоуровневое распределение

- **За PR.** CI и качество выбирают проверки на основе измененных путей. Код PRs выполняет быстрые контрольные проверки качества и тесты на воздействие с отдельными модульными заданиями и заданиями Vitest в CI.
- **Кандидат в очередь.** CI и Quality запускают полный профиль составленного кандидата в его очереди ref.
- **Совет по выпуску.** Release-Green запускает быстрые жесткие гейты при нажатиях, которые соответствуют его фильтрам пути. Три запланированных запуска в день используют полную очистку ветки выпуска.
- **За выпуск.** Полная матрица CI включает в себя сегменты E2E, проверку пакетов, загрузочный архив tar и проверки покрытия. См. [контрольный список выпуска](RELEASE_CHECKLIST.md).

## Предварительные условия для новой проверки для `merge-train.sh`

Предварительная проверка выполняется перед созданием рабочих деревьев. Установите зависимости с помощью `npm ci`. Убедитесь, что `node_modules/.bin/tsc` является исполняемым файлом и что `node_modules/node_modules` отсутствует. Убедитесь, что `node_modules/.bin/bun --version` выполнен успешно.

Если постустановка Bun была пропущена, запустите `(cd node_modules/bun && node install.js)`. Для проверки согласованности поставщика и проверки известных символов используется Bun. Валидатор запускает `npm run check:cycles:ratchet` в качестве блокирующего шлюза. Автономная команда `npm run check:cycles` носит рекомендательный характер.
