OmniRoute контролирует, какие **происхождение браузера** могут читать ответы из разных источников из единого централизованного списка разрешений. Модель **по умолчанию закрыто при отказе** : ни один источник не разрешен, пока вы его не включите. На этой странице описано, как разрешается список разрешенных, что на самом деле предоставляет `CORS_ALLOW_ALL=true` (и, что важно, что он делает).**нет** ), как безопасно настроить разработку и производство, а также предупреждение во время выполнения, которое отображается на панели мониторинга, когда подстановочный знак активен.

**Источник истины:** `src/server/cors/origins.ts` (`resolveAllowedOrigin`, `applyCorsHeaders`, `getCorsStatus`). Список разрешений применяется один раз, в промежуточном программном обеспечении (`src/server/authz/pipeline.ts`) обработчики — для каждого маршрута не устанавливают `Access-Control-Allow-Origin` самостоятельно.

## Как решается происхождение

Для каждого запроса промежуточное ПО вычисляет значение `Access-Control-Allow-Origin` в следующем порядке:

1. **`CORS_ALLOW_ALL=true`** (или устаревший `CORS_ORIGIN=*`) → возвращает `Origin` вызывающего абонента (или `*`, если нет заголовка `Origin` ), с `Vary: Origin`, поэтому кэши остаются правильными. Та же узкая точка `applyCorsHeaders()` также добавляет `Vary: Accept-Encoding` к каждому ответу 2xx с телом на поверхности `/v1*`/`/v1beta*` с аутентификацией по токену (`relaxForTokenAuth`, RFC 9110 §12.5.5, выпуск #6737), поэтому кэши downstream/shared могут правильно различать сжатые и несжатые варианты.
2. В противном случае запрос `Origin` нормализуется (строчные буквы, завершающая косая черта удаляется) и сопоставляется с **объединенный белый список** :
   - окружение **`CORS_ALLOWED_ORIGINS`** список —, разделенный запятыми, и
   - время выполнения **`corsOrigins`** параметр (Панель управления → Security → _CORS Allowed Origins_), внедренный через `setRuntimeAllowedOrigins()` из `src/lib/config/runtimeSettings.ts`.
3. Нет →**заголовок `Access-Control-Allow-Origin` не создается** . Браузер блокирует чтение из перекрестного источника. Это предполагаемое значение по умолчанию для закрытия при отказе.

| Конверт вар            | Значение                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| `CORS_ALLOWED_ORIGINS` | CSV точного происхождения (рекомендуется).                                                     |
| `CORS_ALLOW_ALL`       | `true`/`1` → отображает любое происхождение (подстановочный знак). Только Дев.                 |
| `CORS_ORIGIN`          | Наследие. `*` ведет себя как `CORS_ALLOW_ALL`; в список разрешенных добавляется одно значение. |

## Модель угроз — что на самом деле раскрывает `CORS_ALLOW_ALL=true`

К общему предупреждению OWASP («подстановочный знак CORS = любой сайт может позвонить вашему API») стоит отнестись серьезно, но опасность OmniRoute**уже, чем общий случай** , из-за одного конкретного факта реализации:

> **Центральный `applyCorsHeaders()` никогда не генерирует `Access-Control-Allow-Credentials`.** Браузер не будет предоставлять ответ между источниками _credentialed_ (содержащий файлы cookie), если сервер не отправит `Access-Control-Allow-Credentials: true`. Общий путь CORS OmniRoute никогда не работает.

Что это означает для каждой поверхности, даже с `CORS_ALLOW_ALL=true`:

| Поверхность                                           | Механизм аутентификации        | Эффект подстановочного знака CORS                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Панель управления / MANAGEMENT `/api/*`               | Сеанс cookie                   | Происхождение повторяется, но **без `Allow-Credentials`** браузер **блоки** сертифицированное чтение. Вредоносный сайт с перекрестным происхождением **не могу читать** ваши аутентифицированные ответы на информационной панели, а файл cookie сеанса не отображается.                                                                                                                                                                                                                                                                                                    |
| Клиент API `/v1/*`, `/v1beta/*`                       | Носитель/заголовок `x-api-key` | Уже вседозволительно **по дизайну** (`relaxForTokenAuth`): браузеры никогда не подключают `Authorization`/`x-api-key` автоматически, поэтому страница злоумышленника не сможет предоставить ваш ключ. Для расслабленного эха требуется аутентифицированный субъект (проверенный ключ API или сеанс информационной панели), а не только заголовок учетных данных, и он никогда не включает `Access-Control-Allow-Credentials`. Анонимные ответы (`REQUIRE_API_KEY=false`) используют настроенный список разрешений источника, включая явную подписку `CORS_ALLOW_ALL=true`. |
| Публичный доступ только для чтения (`/api/health`, …) | Никто                          | Нечувствительный; подстановочный знак безвреден.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

Итак,**остаток** Воздействие `CORS_ALLOW_ALL=true` ограничивается: (a) перекрестным происхождением без сертификации **читает** уже неаутентифицированных данных и (б) позволить CORS**предполетный пропуск** на маршрутах управления —, которые по-прежнему требуют аутентификации, которую не может обеспечить страница с перекрестным происхождением. Это **нет** вектор перехвата сеанса или кражи учетных данных на общем пути CORS.

### Одно настоящее исключение — `/api/v1/agents/`

Маршруты Cloud-Agent (`/api/v1/agents/{health,credentials,tasks,tasks/[id]}`) устанавливают свои **собственный** Заголовки CORS (`src/lib/cloudAgent/api.ts`, `getCloudAgentCorsHeaders`) и **делать** излучать `Access-Control-Allow-Origin: <origin>|*` вместе с `Access-Control-Allow-Credentials: true`. Это единственная поверхность, где сосуществуют исходное эхо и учетные данные, и это **независимый от `CORS_ALLOW_ALL`** . Эти маршруты аутентифицируются руководством (`requireManagementAuth`); Операторы, которые предоставляют панель мониторинга вне хоста, должны знать, что это единственное место, где в заголовках ответов разрешено чтение учетных данных из разных источников. Сведение его к явному списку разрешенных отслеживается отдельно от данного руководства CORS.

## Контрольный список производства

- **Никогда не устанавливайте `CORS_ALLOW_ALL=true` в производство.** Оставьте его не настроенным.
- Установить **явный** список происхождения — либо переменная окружения, либо поле вкладки «Безопасность»:

  ```bash
  CORS_ALLOWED_ORIGINS="https://app.example.com, https://admin.example.com"
  ```

- Если OmniRoute работает за обратным прокси/туннелем (nginx, Caddy, Cloudflare Tunnel, Tailscale), CORS**нет** ваш единственный контроль — защита маршрута обратной связи по-прежнему защищает маршруты, поддерживающие создание (см. [ROUTE_GUARD_TIERS](./ROUTE_GUARD_TIERS.md) ). Не подделывайте `X-Forwarded-For: 127.0.0.1`, чтобы «исправить» ошибку 403; при повторном открытии класса RCE защита маршрута закрывается.
- Подтвердите состояние выполнения: на панели мониторинга отображается **стойкое янтарное знамя** в информационной панели → Security → Authorization Inventory всякий раз, когда `CORS_ALLOW_ALL=true` активен, и `/api/settings/authz-inventory` возвращает конверт `cors: { allowAll, allowedOrigins }` который могут опрашивать инструменты мониторинга.

## Удобство разработки — позволяет использовать конкретное местное происхождение

Вам редко понадобится подстановочный знак даже в dev. Разрешите только те серверы разработки, которые вы используете:

```bash
# Vite (5173) + Next.js (3000) dev servers calling a local OmniRoute
CORS_ALLOWED_ORIGINS="http://localhost:5173, http://localhost:3000"
```

Исходные значения сопоставляются без учета регистра, а косая черта на конце игнорируется, поэтому `http://localhost:3000` и `http://localhost:3000/` эквивалентны. Тот же CSV может быть установлен во время выполнения в **Панель мониторинга → Security → CORS Разрешенные источники** без перезагрузки.

## Ключи API против сеансов cookie

- **Носитель / `x-api-key` (поверхность вывода `/v1/*` ):** браузеры никогда не прикрепляют их автоматически. CORS здесь не является значимым барьером — Ключ API является барьером —, поэтому эта поверхность намеренно является разрешающей, чтобы браузер и клиенты Electron могли читать ответы, на которые они уже имеют право. Для расслабленного эха требуется аутентифицированный субъект (подтвержденный ключ API или сеанс информационной панели), а не только заголовок учетных данных, и он никогда не включает `Access-Control-Allow-Credentials`. Анонимные ответы (`REQUIRE_API_KEY=false`) используют настроенный список разрешений источника, включая явное согласие на использование `CORS_ALLOW_ALL=true`. Отклонения аутентификации (401) остаются читаемыми, поэтому клиенты могут обнаружить отозванный или неправильно набранный ключ (#5242): собственный 401 конвейера сохраняет эхо, а маршрут, который отклоняет сам ключ после того, как конвейер обслужил его как анонимный (`/v1/models` и `/v1beta/models` с настроенной аутентификацией управления, маршруты `/v1/files`, `/v1/batches`, `/v1/media`, `/v1/session-leases` и автоматические комбинированные кандидатские маршруты на уровне владельца) добавляют эхо к этому 401 через `credentialRejectionHeaders()`. Эхо привязано к запросу, несущему заголовок учетных данных (`Authorization`, `x-api-key`, `x-goog-api-key` или файл cookie `auth_token` ), а не к тому, на каком из них проверен маршрут, и никогда не сопряжено с `Access-Control-Allow-Credentials`; тело представляет собой конверт с фиксированной ошибкой. Маршруты управления под `/api/v1/` охраняемые `requireManagementAuth()` (`/api/v1/management/*`, `/api/v1/registered-keys`, `/api/v1/providers/[provider]/limits`, `/api/v1/accounts/[id]/limits`, `/api/v1/issues/report`), не используют это исключение отклонения учетных данных: с `REQUIRE_API_KEY=false` их ответы 401/403 соответствуют настроенной политике происхождения CORS.
- **Сеанс cookie (панель управления):** защищено по умолчанию закрытием при отказе **и** из-за отсутствия `Access-Control-Allow-Credentials` на общем пути. Не допускайте использования источников management/dashboard в любой разрешительной конфигурации; они должны оставаться точно закрытыми при отказе.

## Рукопожатия WebSocket (`/v1/responses`, `/v1/ws`)

Браузеры не применяют CORS к WebSocket, поэтому транспорты WebSocket, которые возвращают выходные данные вывода, сами проверяют рукопожатие `Origin` (`src/server/origin/wsOrigin.ts`): ответы WebSocket (`/v1/responses`) и, когда OmniRoute проходит через `npm start` / `npm run dev`, мост `/v1/ws` и `/api/v1/ws`, который передает `/v1/chat/completions`, `/v1/messages` и `/v1/responses` в виде кадров. Мост запрашивает вердикт у `/api/v1/ws?handshake=1` и отказывается обновляться, если этот маршрут не прошел проверку. Требования аутентификации по-прежнему применяются отдельно. Проверка происхождения проходит, когда:

- у него нет заголовка `Origin` (Codex CLI, SDKs и другие небраузерные клиенты);
- `Origin` разрешен указанным выше списком разрешений (`CORS_ALLOWED_ORIGINS`, настройка `corsOrigins`, `CORS_ORIGIN`, `CORS_ALLOW_ALL`);
- `Origin` является одним из собственных общедоступных источников OmniRoute(настроенная общедоступная база URL, перенаправленный источник доверенного прокси-сервера или прямой хост loopback/LAN указанный в виде литерала IP, или `localhost` — те же кандидаты, которые используются при проверке мутации информационной панели); или
- он содержит действительный ключ API, как и на поверхности HTTP `/v1/*`.

Все остальное получает `403 ws_origin_forbidden`. Файл cookie сеанса информационной панели не исключает внешний `Origin`, поскольку браузер прикрепляет его к сокету любой страницы. `localhost` на другом порту не рассматривается как порт того же происхождения; добавьте такие источники разработки в `CORS_ALLOWED_ORIGINS`.

## Пример: обратный прокси перед OmniRoute

CORS обеспечивается самим OmniRoute, поэтому прокси-сервер обычно должен **нет** добавьте или перепишите заголовки `Access-Control-*` (двойные заголовки нарушают работу браузеров). Завершите TLS и перенаправьте —, пусть OmniRoute ответит перед полетом:

```nginx
# nginx — forward to OmniRoute; do NOT inject Access-Control-* here
location / {
    proxy_pass http://127.0.0.1:20128;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    # Keep the forwarding headers: a proxy on the same host connects from loopback, and they are
    # what tells OmniRoute the caller is not the local operator. A proxy that adds none of them
    # makes every remote caller look local. Never set X-Forwarded-For to 127.0.0.1 either.
}
```

Установите разрешенные источники браузера в OmniRoute (`CORS_ALLOWED_ORIGINS` или вкладка «Безопасность»), а не в прокси.
