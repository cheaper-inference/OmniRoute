## Обзор

Все маршруты API управления OmniRoute относятся к одному из трёх уровней
защиты. Классификация статична, определена в `src/server/authz/routeGuard.ts`
и проверяется до выполнения любой другой ветви аутентификации.

## Уровни

### Уровень 1 — LOCAL_ONLY

**Обеспечивается:** `isLocalOnlyPath(path)` → проверка loopback-хоста
**Обход:** по умолчанию отсутствует. Узкое исключение для путей из
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, когда запрос содержит действительный
API-ключ со скоупом `manage` (см. [Исключение для manage-скоупа](#manage-scope-carve-out)).

Эти маршруты порождают дочерние процессы или выполняют код во время выполнения. Их
открытие для трафика не с loopback-интерфейса позволило бы злоумышленнику,
получившему действительный JWT (например, через туннель Cloudflared/Ngrok),
инициировать порождение процессов — известный класс уязвимостей CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Что такое GHSA-fhh6-4qxv-rpqj (класс атаки):** управляющий/агентский сервер
предоставляет эндпоинт, который запускает подпроцесс (`npm install`, `node`, браузер,
прокси, `git`, `tar`, …). Если этот эндпоинт доступен извне хоста — потому что
оператор разместил OmniRoute за туннелем nginx/Cloudflare/Tailscale и JWT утёк,
или аутентификация была настроена неправильно, — злоумышленник превращает «вызвать API»
в «выполнить команду на хосте» (удалённое выполнение кода). OmniRoute закрывает эту
возможность, принудительно выполняя **проверку loopback-хоста безусловно, до любой
проверки аутентификации**, на каждом маршруте, способном порождать процессы:
утёкший токен, переданный через туннель, всё равно не сможет достичь порождения процессов.

**Полный набор LOCAL_ONLY.** Авторитетным источником являются
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` в
`src/server/authz/routeGuard.ts`; таблица ниже отражает текущее состояние. Проверка
`check-route-guard-membership` перечисляет каждый `route.ts` внутри префиксов,
способных порождать процессы, и завершает CI с ошибкой, если какой-либо из них
не классифицирован как local-only.

#### Исключение для manage-скоупа

Подмножество путей LOCAL_ONLY МОЖЕТ быть также доступно с не-loopback адресов
тогда и только тогда, когда запрос содержит заголовок `Authorization: Bearer <api-key>`,
в метаданных которого присутствует скоуп `manage` (или `admin`). Исключение
явно включается для каждого пути через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`,
так что по умолчанию для любого нового пути LOCAL_ONLY сохраняется строгий режим
только loopback. Неаутентифицированные запросы и запросы с ключами без manage
по-прежнему отклоняются с `403 LOCAL_ONLY`.

На сегодня единственный префикс, допускающий обход, — `/api/mcp/`. `/api/cli-tools/runtime/`
и `/api/services/` намеренно исключены, поскольку они могут запускать произвольные
подпроцессы (`npm install`, `node`), а это именно тот класс CVE, для предотвращения
которого существует уровень LOCAL_ONLY.

**#7895 — узкий скоуп `mcp:connect`:** исключение для `/api/mcp/` ТАКЖЕ принимает
Bearer-ключ с узким скоупом `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), проверяемым через
`hasMcpConnectOrManageScope()` в `src/server/authz/policies/management.ts`.
Это действует ТОЛЬКО для `/api/mcp/` — `mcp:connect` не даёт никаких прав ни на одном
другом маршруте управления (включая любой другой префикс обхода LOCAL_ONLY, если такой
когда-либо будет добавлен), и он намеренно исключён из
`MANAGEMENT_API_KEY_SCOPES`. Ключ со скоупом `manage`/`admin` по-прежнему проходит
исключение точно так же, как раньше; `mcp:connect` — это альтернатива с меньшими
привилегиями для удалённых вызовов, которым нужен только MCP и не требуется широкий
доступ к управлению.

| Запрос                                         | Путь                       | Результат                   |
| ---------------------------------------------- | -------------------------- | --------------------------- |
| Не-loopback, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY              |
| Не-loopback, Bearer со скоупом `manage`        | `/api/mcp/*`               | Разрешено                   |
| Не-loopback, Bearer со скоупом `mcp:connect`   | `/api/mcp/*`               | Разрешено                   |
| Не-loopback, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY              |
| Не-loopback, Bearer со скоупом `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY              |
| Не-loopback, Bearer со скоупом `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY              |
| Loopback, с любым Bearer или без него          | любой LOCAL_ONLY           | Разрешено (гейт пропускает) |

#### Рекомендации для операторов и аудит

Если вы запускаете OmniRoute за обратным прокси или туннелем (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), проверка loopback по-прежнему защищает перечисленные выше
маршруты, способные запускать процессы, — запрос, чей клиентский адрес не является
loopback, отклоняется с `403 LOCAL_ONLY` **до срабатывания аутентификации**, так что
утёкший JWT не сможет добраться до запуска процессов. Остаются две обязанности
оператора:

- **Не «чините» ошибку 403, подделывая IP клиента под loopback.** Установка
  `X-Forwarded-For: 127.0.0.1` или прокси, переписывающий адрес источника на
  loopback, заново открывает именно тот класс RCE-уязвимостей, который закрывает этот
  уровень. Публикуйте через прокси дашборд/API — но никогда маршруты, способные
  запускать процессы (spawn-capable).
- **Сохраняйте обход через manage-скоуп минимальным.** Обход возможен только для
  `/api/mcp/` и только с API-ключом со скоупом `manage`. Префиксы
  `SPAWN_CAPABLE_PREFIXES` никогда не могут быть добавлены в список обхода — схема
  zod их отклоняет, а `isLocalOnlyBypassableByManageScope` запрещает их во время
  выполнения (эшелонированная защита) — именно это дашборд подразумевает под
  формулировкой «cannot be made bypassable» («нельзя сделать обходимыми»). Тот же
  список запрета также содержит несколько маршрутов LOCAL_ONLY, которые не запускают
  процессы, но также никогда не должны быть доступны удалённо —
  `/api/oauth/kiro/auto-import` (читает локальные файлы учётных данных Kiro на хосте),
  `/api/discovery/` и `/api/issue-agent/`. Загрузчик снимков настроек во время
  выполнения также отбрасывает такие записи из сохранённой строки настроек, а
  устаревший импорт JSON (`/api/settings/import-json`) никогда не записывает ключи
  обхода. Каждая запись `LOCAL_ONLY_API_PREFIXES` должна либо находиться в списке
  запрета, либо быть проверена как допустимая для обхода
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршруты с
  динамическими сегментами и статическими путями, способные запускать процессы, под
  `/api/providers/` (например, `/login`, `/refresh-cursor`) покрываются
  сопутствующими регулярными выражениями `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` в
  `src/shared/constants/spawnCapablePrefixes.ts`, а не плоским массивом
  `SPAWN_CAPABLE_PREFIXES` — плоскому массиву пришлось бы покрывать весь префикс
  `/api/providers/`, чтобы их перехватить, чрезмерно расширяя дерево маршрутов,
  которое удалённые дашборды легитимно используют для CRUD-операций с провайдерами.

**Аудит доступа** — чтобы убедиться, что к этим маршрутам не обращается ничто извне хоста:

- Откройте **Authorization Inventory** на `/dashboard/settings/security`: там отображаются
  актуальный список префиксов LOCAL_ONLY, какие префиксы обходимы, а также определённый
  на этапе компиляции набор spawn-capable-маршрутов («cannot be made bypassable»).
- Ищите в логах обратного прокси / доступа указанные выше префиксы в сочетании с
  не-loopback адресом клиента. Любое такое совпадение, вернувшее `200` вместо
  `403 LOCAL_ONLY`, означает, что прокси маскирует реальный IP клиента — исправьте прокси.
- Запись `403 LOCAL_ONLY` в логах OmniRoute для одного из этих путей — это защита,
  работающая как задумано, а не ошибка, которую нужно подавлять.

#### Удалённо доступные маршруты с контролем проб в месте вызова

Некоторые маршруты должны оставаться доступными с удалённого дашборда, но выполняют
пробу на стороне хоста (`which <binary>`, `<binary> --version`, `tailscale status --json`)
для локальных вызовов. Они не являются LOCAL_ONLY для `GET`; вместо этого обработчик
считывает доверенное заключение о локальности пира через `getRequestPeerLocality()`
(`src/shared/utils/apiAuth.ts`) и выполняет пробу только для вызывающих с `loopback` /
`lan`. Удалённый (`remote`) вызывающий получает ответ той же формы, построенный из
источников, не запускающих процессы (сохранённое состояние, настройки, проверки файловой
системы), с флагом `probed: false`.

| Маршрут                                                          | Проба, пропускаемая для удалённых вызовов                            |
| ---------------------------------------------------------------- | -------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | Проба рантайма CLI (`allowLocalRuntimeProbe`) и резервный запуск CLI |
| `GET /api/headroom/status`                                       | `which headroom` и пробы python `--version`                          |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`    |
| `GET /api/tunnels/cloudflared` (исключён из LOCAL_ONLY для GET)  | Поиск `which cloudflared` в PATH                                     |

Новый маршрут чтения, который пробует хост, следует тому же шаблону либо сразу
классифицируется как LOCAL_ONLY.

### Уровень 2 — ALWAYS_PROTECTED

**Применяется через:** `isAlwaysProtectedPath(path)` → пропуск обхода `requireLogin=false`
**Обход:** невозможен при `requireLogin=false`; JWT требуется всегда

Эти маршруты разрушительны или необратимы. Разрешение их в установке «без пароля»
означало бы, что любой в той же LAN мог бы стереть базу данных или завершить
серверный процесс.

| Путь                                      | Причина                                                                 |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершает серверный процесс                                             |
| `/api/settings/database`                  | Экспорт, импорт и очистка базы данных                                   |
| `/api/db-backups`                         | Доступ к архиву полных резервных копий базы данных                      |
| `/api/settings/export-json`               | Экспортирует полный набор настроек (включая секреты)                    |
| `/api/settings/import-json`               | Заменяет полный набор настроек                                          |
| `/api/providers/health-autopilot/actions` | Выполняет корректирующие действия автопилота                            |
| `/api/settings/obsidian`                  | Выпускает многоразовые учётные данные WebDAV для любого корня хранилища |
| `/api/relay/tokens`                       | Выпускает, перечисляет, редактирует и отзывает токены ретрансляции      |
| `/api/cli-tools/apply`                    | Перезаписывает конфигурацию CLI на хосте оператора                      |
| `/api/cli-tools/guide-settings`           | Записывает файлы конфигурации CLI по указаниям руководства              |

| `/api/restart`                            | Перезапускает серверный процесс                                         |

**Ответ при нарушении:** `401 Authentication required`

`/api/settings/obsidian` покрывает свой дочерний маршрут `/webdav`: `POST` направляет файловый сервис WebDAV — обслуживаемый пользовательским слоем Node перед Next.js, вне этого конвейера — на выбранный вызывающей стороной корень и возвращает свежесозданные учётные данные Basic, `DELETE` ротирует их, а родительский `POST` сохраняет токен Obsidian REST API. GHSA-62vw лишь скрыл раскрытие пароля через `GET`; выпуск по-прежнему оставался на уровне fail-open (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` дополнительно отклоняет хранилище, которое является каталогом данных, находится внутри него или содержит его.

#### Экспорт и восстановление учётных данных — только для операторов

Уровень выше лишь решает, требуются ли _какие-либо_ учётные данные. Маршруты, выгружающие сохранённые учётные данные, добавляют вторую проверку в обработчике: `GET /api/settings/export-json` (расшифрованные подключения провайдеров и сырые ключи API), `GET /api/db-backups/export` (файл SQLite) и `GET /api/db-backups/exportAll` (полный архив) вызывают `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). Она принимает сессию панели управления, локальный субъект CLI или экземпляр с отключённым входом и отвечает `403` на ключи API любой области действия (включая `manage` и `admin`), а также на токены доступа `oma_`. Деструктивные аналоги удерживают ту же границу: `POST /api/db-backups/import` (загруженный `.sqlite`, включая `dryRun=true`), `POST /api/db-backups` (восстановление сохранённой резервной копии по id) и `POST /api/settings/import-json` (восстановление из устаревшего JSON) заменяют рабочую базу данных или весь набор настроек/подключений/ключей API, поэтому машинные учётные данные также не могут их инициировать. Удаление точек восстановления удерживает ту же границу: `DELETE /api/db-backups` (очистка — оставить последние N / удалить старше D дней) и `PATCH /api/db-backups` (настройки хранения), поскольку сохранённая политика хранения — это именно то, что `cleanupDbBackups()` применяет после каждого автоматического резервного копирования (`src/lib/db/backup.ts`), так что машинные учётные данные, способные сохранить `keepLatest: 1`, вычистили бы всё при следующем снимке. Просмотр списка и создание резервных копий (`GET`/`PUT /api/db-backups`) сохраняют обычную управленческую аутентификацию. Выпуск токенов синхронизации (`POST /api/sync/tokens`) использует тот же вспомогательный метод, плюс доверенный loopback-токен внутреннего сервиса.

### Начальная настройка при чистой установке — только с loopback, по реальному пиру, а не по `Host`

Если пароль управления не настроен (и нет `INITIAL_PASSWORD`), `isAuthRequired()` в `src/shared/utils/apiAuth.ts` оставляет анонимную начальную настройку открытой **только для loopback-пиров**. Принадлежность к loopback определяется по доверенным сигналам о пире, в порядке: реальный TCP-пир, помеченный токеном (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, то, что видит политика), собственное заключение конвейера `AUTHZ_HEADER_PEER_LOCALITY` (то, что видят обработчики маршрутов, доверенное только пока задан `OMNIROUTE_PEER_STAMP_TOKEN`) или реальный сокет-пир для прямых вызовов. `Host` / `nextUrl.hostname` никогда не учитываются, а запись первого пароля (`POST /api/settings/require-login`) подчиняется тому же ограничению, а не открыта для любого сетевого пира (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передаёт вниз собственное заключение `peerContext`, поэтому заголовки ИСХОДНОГО (до очистки) запроса никогда не определяют его.

### Уровень 3 — MANAGEMENT (по умолчанию)

Все остальные управленческие маршруты. Аутентификация требуется, если не задано `requireLogin=false`. Токены CLI могут аутентифицировать эти маршруты (loopback + действительный HMAC).

## Порядок проверки

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти к следующей проверке
     → не loopback, Bearer с областью manage
        И isLocalOnlyBypassableByManageScope     → разрешить (management_key)
     → иначе                                     → отклонить с 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → разрешить (system)
  3. hasValidCliToken(headers)?
     → разрешить (cli) [loopback + проверка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) или requireLogin=true?
     → isDashboardSessionAuthenticated?
        → разрешить (dashboard_session)
     → Bearer с областью manage для пути, не допускающего обход?
        → разрешить (management_key)
     → отклонить с 401/403
  5. requireLogin=false?
     → разрешить (anonymous)
```

Ветвь с областью manage на шаге 1 — единственный аутентифицированный способ получить доступ к маршруту
LOCAL_ONLY; при сбое бэкенда аутентификации возвращается 503 (а не 403), поэтому
истёкшая БД не приводит незаметно к режиму «запретить».

## Добавление нового маршрута, способного запускать процессы

1. Добавьте префикс пути в `LOCAL_ONLY_API_PREFIXES` в
   `src/server/authz/routeGuard.ts`
2. Добавьте тест в `tests/unit/authz/routeGuard.test.ts`, проверяющий, что
   `isLocalOnlyPath()` возвращает true для нового префикса
3. **Никогда не пропускайте этот шаг** — см. строгое правило №15 в `CLAUDE.md`
4. Решите: должен ли этот маршрут ТАКЖЕ входить в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Ответ по умолчанию — **нет**. Добавляйте его только тогда, когда маршрут безопасно предоставлять
   обладателю области manage (то есть он НЕ запускает произвольный код, управляемый пользователем).

## Добавление пути, допускающего обход с областью manage

1. Убедитесь, что маршрут не выполняет предоставленный пользователем код или команды. Если
   выполняет, остановитесь — это исключение здесь неприменимо.
2. Добавьте префикс в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` в
   `src/server/authz/routeGuard.ts`
3. Добавьте покрытие в `tests/unit/authz/management-policy.test.ts` для всех четырёх
   вариантов запроса: без Bearer (403), Bearer с областью manage (разрешить), Bearer без области manage
   (403), а также отдельный регрессионный тест для префикса, подтверждающий, что `/api/cli-tools/runtime/*` остаётся
   доступным строго через loopback даже при наличии Bearer с областью manage.

## Документирование уровней безопасности в OpenAPI

При добавлении нового маршрута в `docs/openapi.yaml` примените соответствующее
пользовательское расширение, если маршрут классифицирован в `routeGuard.ts`:

| Классификация routeGuard.ts                  | Аннотация YAML             | Применяемое ограничение                                   |
| -------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                    | `x-loopback-only: true`    | Безусловно блокируется для запросов не через loopback     |
| `ALWAYS_PROTECTED_API_PATHS`                 | `x-always-protected: true` | Аутентификация обязательна даже при `requireLogin=false`  |
| Внутренний маршрут администрирования/отладки | `x-internal: true`         | По умолчанию скрыт из /dashboard/api-endpoints            |
| Нет (публичный / стандартная аутентификация) | (аннотация не требуется)   | Стандартный доступ, управляемый параметром `requireLogin` |

### Проверка

Два скрипта обеспечивают согласованность аннотаций YAML с `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершается с ошибкой, если покрытие < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершается с ошибкой, если аннотации `x-loopback-only` или
  `x-always-protected` расходятся с константами времени компиляции

Оба скрипта запускаются в хуке перед коммитом и в CI.

### Правило ложноположительного срабатывания

Если маршрут аннотирован `x-always-protected` или `x-loopback-only`, но НЕ входит в
соответствующую константу `routeGuard.ts`, скрипт проверки покрытия завершается с ошибкой. Исправление всегда заключается в том, чтобы привести
YAML в соответствие с тем, что фактически контролирует `routeGuard.ts`, а не добавлять маршруты в `routeGuard.ts`
без одновременной реализации логики ограничения доступа.
