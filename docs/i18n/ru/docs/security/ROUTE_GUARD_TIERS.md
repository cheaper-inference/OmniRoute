## Обзор

Все маршруты API управления OmniRoute относятся к одному из трёх уровней
защиты. Классификация статична, определена в `src/server/authz/routeGuard.ts`
и проверяется до выполнения любой другой ветви аутентификации.

## Уровни

### Уровень 1 — LOCAL_ONLY

**Обеспечивается посредством:** `isLocalOnlyPath(path)` → проверка loopback-хоста  
**Обход:** По умолчанию отсутствует. Узкое исключение для путей из
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, если запрос содержит действительный
API-ключ с областью действия `manage` (см. [Исключение для области действия manage](#manage-scope-carve-out)).

Эти маршруты порождают дочерние процессы или выполняют код среды исполнения. Если
сделать их доступными для трафика не через loopback-интерфейс, злоумышленник,
получивший действительный JWT (например, через туннель Cloudflared/Ngrok), сможет
запускать создание процессов — это известный класс CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Что представляет собой GHSA-fhh6-4qxv-rpqj (класс атаки):** сервер управления/агент
предоставляет конечную точку, которая запускает подпроцесс (`npm install`, `node`, браузер,
прокси, `git`, `tar`, …). Если эта конечная точка доступна извне хоста — поскольку
оператор разместил OmniRoute за туннелем nginx/Cloudflare/Tailscale и произошла утечка JWT
либо аутентификация была настроена неправильно, — злоумышленник превращает «вызов API» в «выполнение
команды на хосте» (удалённое выполнение кода). OmniRoute устраняет эту угрозу, безусловно выполняя
**проверку loopback-хоста перед любой проверкой аутентификации** для каждого
маршрута, способного порождать процессы: украденный токен, используемый через туннель, всё равно не позволит
получить доступ к запуску процессов.

**Полный набор LOCAL_ONLY.** Авторитетным источником являются
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` в
`src/server/authz/routeGuard.ts`; приведённая ниже таблица отражает текущее состояние.
Проверка `check-route-guard-membership` перечисляет каждый файл `route.ts` в
префиксах, способных порождать процессы, и завершает CI с ошибкой, если какой-либо из них не классифицирован как доступный только локально.

#### Исключение для области управления

К подмножеству путей LOCAL_ONLY МОЖНО также обращаться не через loopback-интерфейс в том и
только том случае, если запрос содержит `Authorization: Bearer <api-key>`, метаданные
которого включают область `manage` (или `admin`). Исключение включается
явно для каждого пути с помощью `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, поэтому
по умолчанию любой новый путь LOCAL_ONLY остаётся доступным строго через loopback-интерфейс. Запросы
без аутентификации и запросы с ключами без области управления по-прежнему отклоняются с ответом
`403 LOCAL_ONLY`.

В настоящее время единственным префиксом, для которого разрешён обход, является `/api/mcp/`. `/api/cli-tools/runtime/` и
`/api/services/` намеренно исключены, поскольку они могут запускать произвольные
подпроцессы (`npm install`, `node`), что относится именно к тому классу CVE, от которого
предназначен защищать уровень LOCAL_ONLY.

**#7895 — узкая область `mcp:connect`:** исключение для `/api/mcp/` ТАКЖЕ допускает
Bearer-ключ с узкой областью `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), проверяемой с помощью
`hasMcpConnectOrManageScope()` в `src/server/authz/policies/management.ts`.
Она распространяется ТОЛЬКО на `/api/mcp/` — `mcp:connect` не предоставляет никаких прав ни для одного другого
маршрута управления (включая все прочие префиксы обхода LOCAL_ONLY, если таковые
когда-либо будут добавлены) и намеренно исключена из
`MANAGEMENT_API_KEY_SCOPES`. Ключ с `manage`/`admin` по-прежнему
позволяет воспользоваться исключением точно так же, как и раньше; `mcp:connect` — это альтернатива
с меньшими привилегиями для удалённых клиентов, использующих только MCP, которым не нужен широкий доступ к управлению.

| Запрос                                                         | Путь                       | Результат                     |
| -------------------------------------------------------------- | -------------------------- | ----------------------------- |
| Не через loopback-интерфейс, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Не через loopback-интерфейс, Bearer с областью `manage`        | `/api/mcp/*`               | Разрешить                     |
| Не через loopback-интерфейс, Bearer с областью `mcp:connect`   | `/api/mcp/*`               | Разрешить                     |
| Не через loopback-интерфейс, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Не через loopback-интерфейс, Bearer с областью `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Не через loopback-интерфейс, Bearer с областью `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Через loopback-интерфейс, с любым Bearer или без него          | любой LOCAL_ONLY           | Разрешить (проверка пройдена) |

#### Рекомендации для операторов и аудит

Если OmniRoute работает за обратным прокси-сервером или туннелем (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), проверка loopback-интерфейса по-прежнему защищает указанные выше
маршруты, способные запускать процессы: запрос, адрес клиента которого не относится к loopback-интерфейсу, отклоняется с
`403 LOCAL_ONLY` **до выполнения аутентификации**, поэтому утёкший JWT не позволит запустить процесс. У
операторов остаются две обязанности:

- **Не пытайтесь «исправить» ошибку 403, подделывая IP-адрес клиента как loopback.** Установка
  `X-Forwarded-For: 127.0.0.1` или использование прокси, который заменяет адрес источника на
  loopback, вновь открывает именно тот класс RCE-уязвимостей, от которого защищает этот уровень. Предоставляйте доступ к
  панели управления/API через прокси — но никогда к маршрутам, способным запускать процессы.
- **Сведите обход для области `manage` к минимуму.** Обход разрешён только для `/api/mcp/` и
  только с API-ключом, имеющим область `manage`. Значения `SPAWN_CAPABLE_PREFIXES` ни при каких
  условиях нельзя добавить в список обхода — схема zod отклоняет их, а
  `isLocalOnlyBypassableByManageScope` блокирует их во время выполнения (эшелонированная защита);
  именно это означает формулировка «нельзя сделать доступным для обхода» в панели управления. Тот же
  список запретов также содержит несколько маршрутов LOCAL_ONLY, которые не запускают процессы, но
  всё равно никогда не должны быть доступны удалённо: `/api/oauth/kiro/auto-import` (читает локальные
  для хоста файлы учётных данных Kiro), `/api/discovery/` и `/api/issue-agent/`. Загрузчик снимка
  состояния времени выполнения также удаляет такие записи из сохранённой строки настроек, а
  импорт устаревшего формата JSON (`/api/settings/import-json`) никогда не записывает ключи обхода.
  Каждая запись `LOCAL_ONLY_API_PREFIXES` должна либо находиться в списке запретов, либо быть
  проверена на допустимость обхода (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршруты
  с динамическими сегментами и статическими путями, способные запускать процессы, в `/api/providers/`
  (например, `/login`, `/refresh-cursor`) охватываются сопутствующими выражениями на основе регулярных
  выражений `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` в
  `src/shared/constants/spawnCapablePrefixes.ts`, а не плоским массивом
  `SPAWN_CAPABLE_PREFIXES` — иначе плоский массив должен был бы охватывать весь префикс
  `/api/providers/`, неоправданно расширяя ограничения на дерево маршрутов, которое удалённые панели
  управления правомерно используют для CRUD-операций с провайдерами.

**Аудит доступа** — чтобы убедиться, что ничто за пределами хоста не обращается к этим маршрутам:

- Откройте **Инвентаризацию авторизации** на `/dashboard/settings/security`: там отображаются
  актуальный список префиксов LOCAL_ONLY, префиксы, для которых разрешён обход, и определённый на
  этапе компиляции набор способных запускать процессы маршрутов («нельзя сделать доступным для обхода»).
- Выполните поиск в журналах обратного прокси / журналах доступа по указанным выше префиксам в
  сочетании с клиентским адресом, не являющимся loopback. Любой такой запрос, вернувший `200` вместо
  `403 LOCAL_ONLY`, означает, что прокси скрывает реальный IP-адрес клиента — исправьте конфигурацию прокси.
- Запись `403 LOCAL_ONLY` в журналах OmniRoute для одного из этих путей означает, что защита
  работает как задумано, а не ошибку, которую нужно подавить.

#### Удалённо доступные маршруты с проверкой в точке вызова

Некоторые маршруты должны оставаться доступными из удалённой панели управления, но для локальных
клиентов выполнять проверку на стороне хоста (`which <binary>`, `<binary> --version`,
`tailscale status --json`). Для запросов `GET` они не относятся к LOCAL_ONLY; вместо этого обработчик
считывает доверенный результат определения расположения однорангового узла с помощью
`getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) и запускает проверку только для клиентов
`loopback` / `lan`. Клиент `remote` получает ответ той же структуры, сформированный из источников,
не запускающих процессы (сохранённого состояния, настроек, проверок файловой системы), с флагом
`probed: false`.

| Маршрут                                                           | Проверка, пропускаемая для удалённых клиентов                                   |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`      | Проверка среды выполнения CLI (`allowLocalRuntimeProbe`) и резервный запуск CLI |
| `GET /api/headroom/status`                                        | `which headroom` и проверки python с `--version`                                |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check`  | `which tailscale`, `tailscale status/funnel --json`, `which brew`               |
| `GET /api/tunnels/cloudflared` (исключение из LOCAL_ONLY для GET) | Поиск `which cloudflared` в PATH                                                |

Новый маршрут чтения, выполняющий проверку хоста, должен следовать тому же шаблону либо быть
полностью классифицирован как LOCAL_ONLY.

### Уровень 2 — ALWAYS_PROTECTED

**Обеспечивается:** `isAlwaysProtectedPath(path)` → пропуск обхода `requireLogin=false`
**Обход:** отсутствует при `requireLogin=false`; JWT требуется всегда

Эти маршруты выполняют разрушительные или необратимые действия. Если разрешить их в установке
«без пароля», любой пользователь в той же локальной сети сможет стереть базу данных или завершить
процесс сервера.

| Путь                                      | Причина                                                                          |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершает процесс сервера                                                        |
| `/api/settings/database`                  | Экспорт, импорт и очистка базы данных                                            |
| `/api/db-backups`                         | Доступ к полному архиву резервной копии базы данных                              |
| `/api/settings/export-json`               | Экспортирует полный объект настроек (включая секреты)                            |
| `/api/settings/import-json`               | Заменяет полный объект настроек                                                  |
| `/api/providers/health-autopilot/actions` | Выполняет корректирующие действия автопилота                                     |
| `/api/settings/obsidian`                  | Выпускает повторно используемые учётные данные WebDAV для любого корня хранилища |
| `/api/relay/tokens`                       | Mints, lists, edits and revokes relay tokens                                     |

**Ответ при нарушении:** `401 Требуется аутентификация`

`/api/settings/obsidian` охватывает дочерний маршрут `/webdav`: `POST` направляет файловую службу WebDAV —
обслуживаемую пользовательским слоем Node перед Next.js, вне этого конвейера, — на выбранный вызывающей
стороной корневой каталог и возвращает только что созданные учётные данные Basic, `DELETE` обновляет их,
а родительский запрос `POST` сохраняет токен REST API Obsidian. GHSA-62vw скрывал только раскрытие пароля
через `GET`; выдача учётных данных по-прежнему относилась к уровню, по умолчанию разрешавшему доступ
(GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` дополнительно отклоняет хранилище, которое совпадает
с каталогом данных, находится внутри него или содержит его.

#### Экспорт учётных данных доступен только оператору

Уровень выше определяет только то, требуется ли _какая-либо_ учетная запись. Маршруты, которые загружают
сохраненные учетные данные, выполняют вторую проверку в обработчике: `GET /api/settings/export-json` (расшифрованные
подключения к провайдерам и необработанные ключи API), `GET /api/db-backups/export` (файл SQLite) и
`GET /api/db-backups/exportAll` (полный архив) вызывают `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). Эта функция принимает сессию панели управления, локальный субъект CLI или
экземпляр с отключенным входом в систему и отвечает `403` для ключей API с любой областью действия (включая `manage`
и `admin`), а также для токенов доступа `oma_`. Выдача токенов синхронизации (`POST /api/sync/tokens`) использует
ту же вспомогательную функцию, а также доверенный токен внутренней службы обратной петли.

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### Первоначальная настройка новой установки доступна только через обратную петлю — по фактическому узлу, а не по `Host`

Если пароль управления не настроен (и отсутствует `INITIAL_PASSWORD`), функция `isAuthRequired()` в
`src/shared/utils/apiAuth.ts` оставляет анонимную первоначальную настройку доступной **только для узлов обратной петли**.
Обратная петля определяется по доверенным признакам узла в следующем порядке: реальный TCP-узел, отмеченный токеном
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, то, что видит политика), собственный вердикт конвейера
`AUTHZ_HEADER_PEER_LOCALITY` (то, что видят обработчики маршрутов; считается доверенным только пока
задана переменная `OMNIROUTE_PEER_STAMP_TOKEN`) или реальный сокетный узел для прямых клиентов. `Host` /
`nextUrl.hostname` никогда не учитываются, а первоначальная запись пароля
(`POST /api/settings/require-login`) подчиняется тому же ограничению, а не открыта для любого
сетевого узла (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передает ниже собственный вердикт `peerContext`,
поэтому заголовки ИСХОДНОГО запроса (до удаления) никогда не влияют на это решение.

### Уровень 3 — УПРАВЛЕНИЕ (по умолчанию)

Все остальные маршруты управления. Аутентификация обязательна, если не задано
`requireLogin=false`. Токены CLI могут использоваться для аутентификации на этих маршрутах (обратная петля + действительная HMAC).

## Порядок проверки

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти к следующей проверке
     → не loopback, Bearer с областью manage
        И isLocalOnlyBypassableByManageScope     → разрешить (management_key)
     → иначе                                     → отклонить с 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → разрешить (system)
  3. hasValidCliToken(headers)?
     → разрешить (cli) [loopback + проверка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) или requireLogin=true?
     → isDashboardSessionAuthenticated?
        → разрешить (dashboard_session)
     → Bearer с областью manage для пути, не допускающего обход?
        → разрешить (management_key)
     → отклонить с 401/403
  5. requireLogin=false?
     → разрешить (anonymous)
```

Ветвь с областью manage на шаге 1 — единственный аутентифицированный способ получить доступ к маршруту
LOCAL_ONLY; при сбое бэкенда аутентификации возвращается 503 (а не 403), поэтому
истёкшая БД не приводит незаметно к режиму «запретить».

## Добавление нового маршрута, способного запускать процессы

1. Добавьте префикс пути в `LOCAL_ONLY_API_PREFIXES` в
   `src/server/authz/routeGuard.ts`
2. Добавьте тест в `tests/unit/authz/routeGuard.test.ts`, проверяющий, что
   `isLocalOnlyPath()` возвращает true для нового префикса
3. **Никогда не пропускайте этот шаг** — см. строгое правило №15 в `CLAUDE.md`
4. Решите: должен ли этот маршрут ТАКЖЕ входить в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Ответ по умолчанию — **нет**. Добавляйте его только тогда, когда маршрут безопасно предоставлять
   обладателю области manage (то есть он НЕ запускает произвольный код, управляемый пользователем).

## Добавление пути, допускающего обход с областью manage

1. Убедитесь, что маршрут не выполняет предоставленный пользователем код или команды. Если
   выполняет, остановитесь — это исключение здесь неприменимо.
2. Добавьте префикс в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` в
   `src/server/authz/routeGuard.ts`
3. Добавьте покрытие в `tests/unit/authz/management-policy.test.ts` для всех четырёх
   вариантов запроса: без Bearer (403), Bearer с областью manage (разрешить), Bearer без области manage
   (403), а также отдельный регрессионный тест для префикса, подтверждающий, что `/api/cli-tools/runtime/*` остаётся
   доступным строго через loopback даже при наличии Bearer с областью manage.

## Документирование уровней безопасности в OpenAPI

При добавлении нового маршрута в `docs/openapi.yaml` примените соответствующее
пользовательское расширение, если маршрут классифицирован в `routeGuard.ts`:

| Классификация routeGuard.ts                  | Аннотация YAML             | Применяемое ограничение                                   |
| -------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                    | `x-loopback-only: true`    | Безусловно блокируется для запросов не через loopback     |
| `ALWAYS_PROTECTED_API_PATHS`                 | `x-always-protected: true` | Аутентификация обязательна даже при `requireLogin=false`  |
| Внутренний маршрут администрирования/отладки | `x-internal: true`         | По умолчанию скрыт из /dashboard/api-endpoints            |
| Нет (публичный / стандартная аутентификация) | (аннотация не требуется)   | Стандартный доступ, управляемый параметром `requireLogin` |

### Проверка

Два скрипта обеспечивают согласованность аннотаций YAML с `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершается с ошибкой, если покрытие < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершается с ошибкой, если аннотации `x-loopback-only` или
  `x-always-protected` расходятся с константами времени компиляции

Оба скрипта запускаются в хуке перед коммитом и в CI.

### Правило ложноположительного срабатывания

Если маршрут аннотирован `x-always-protected` или `x-loopback-only`, но НЕ входит в
соответствующую константу `routeGuard.ts`, скрипт проверки покрытия завершается с ошибкой. Исправление всегда заключается в том, чтобы привести
YAML в соответствие с тем, что фактически контролирует `routeGuard.ts`, а не добавлять маршруты в `routeGuard.ts`
без одновременной реализации логики ограничения доступа.
