## Обзор

Все маршруты API управления OmniRoute относятся к одному из трёх уровней
защиты. Классификация статична, определена в `src/server/authz/routeGuard.ts`
и проверяется до выполнения любой другой ветви аутентификации.

## Уровни

### Уровень 1 — LOCAL_ONLY

**Принудительно:** `isLocalOnlyPath(path)` → проверка хоста с обратной связью** Обход:** По умолчанию нет. Узкое выделение путей в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, когда запрос содержит действительный ключ API с областью действия `manage` (см. [Выделение области управления](#manage-scope-carve-out) ).

Эти маршруты порождают дочерние процессы или выполняют код времени выполнения. Предоставление им трафика без обратной связи позволит злоумышленнику, получившему действительный JWT (например, через туннель Cloudflared/Ngrok ), запустить процесс, порождающий — известного класса CVE ( [GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj) ).

**Что такое GHSA-fhh6-4qxv-rpqj (класс атаки):** сервер management/agent предоставляет конечную точку, которая запускает подпроцесс (`npm install`, `node`, браузер, прокси, `git`, `tar`, …). Если эта конечная точка доступна из — вне хоста, потому что оператор поместил OmniRoute за туннель nginx/Cloudflare/Tailscale и произошла утечка JWT, или аутентификация была неправильно настроена — злоумышленник превращает «вызов API» в «запуск команды на хосте» (удаленное выполнение кода). OmniRoute закрывает это, применяя** проверка хоста с обратной связью безоговорочно, перед любой проверкой аутентификации** , на каждом маршруте, где возможно появление: утекший жетон через туннель все равно не может достичь места появления.

**Полный комплект LOCAL_ONLY.** Авторитетный источник — `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` в `src/server/authz/routeGuard.ts`; таблица ниже отражает текущее состояние. #### Выделение области управления

Доступ к подмножеству путей LOCAL_ONLY MAY также возможен без обратной связи тогда и только тогда, когда запрос содержит `Authorization: Bearer <api-key>`, метаданные которого включают область `manage` (или `admin`). Выделение ограничивается явно для каждого пути через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, поэтому по умолчанию для любого нового пути LOCAL_ONLY остается строгая петля. Неаутентифицированные запросы и запросы с неуправляемыми ключами по-прежнему отклоняются с помощью `403 LOCAL_ONLY`.

Сегодня единственным обходным префиксом является `/api/mcp/`. `/api/cli-tools/runtime/` и `/api/services/` намеренно исключены, поскольку они могут порождать произвольные подпроцессы (`npm install`, `node`), что является точным классом CVE для предотвращения которого существует уровень LOCAL_ONLY.

**#7895 — `mcp:connect` узкая область применения:** Выделение `/api/mcp/` ALSO принимает ключ носителя, содержащий узкую область действия `mcp:connect` (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), проверенную через `hasMcpConnectOrManageScope()` в `src/server/authz/policies/management.ts`. Это ограничено `/api/mcp/` ONLY — `mcp:connect` ничего не предоставляет ни на каком другом маршруте управления (включая любой другой префикс обхода LOCAL_ONLY, если он когда-либо будет добавлен), и он намеренно исключен из `MANAGEMENT_API_KEY_SCOPES`. Ключ, содержащий `manage`/`admin` по-прежнему проходит процедуру вырезания точно так же, как и раньше; `mcp:connect` — это альтернатива с более низким уровнем привилегий для удаленных абонентов, использующих только MCP, которым не требуется широкий доступ к управлению.

| Запрос                                                 | Путь                       | Результат                     |
| ------------------------------------------------------ | -------------------------- | ----------------------------- |
| Без шлейфа, без носителя                               | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Без шлейфа, носитель с областью действия `manage`      | `/api/mcp/*`               | Позволять                     |
| Без шлейфа, носитель с областью действия `mcp:connect` | `/api/mcp/*`               | Позволять                     |
| Без шлейфа, носитель без `manage`/`mcp:connect`        | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Без шлейфа, носитель с областью действия `mcp:connect` | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Без шлейфа, носитель с областью действия `manage`      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Шлейфовая проверка, носитель any/no                    | любая LOCAL_ONLY           | Разрешить (пропускает ворота) |

#### Руководство и аудит оператора

Если вы запускаете OmniRoute за обратным прокси-сервером или туннелем (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), проверка обратной связи по-прежнему защищает маршруты, поддерживающие создание, выше — Запрос, адрес клиента которого не имеет обратной связи, отклоняется с помощью `403 LOCAL_ONLY`** до запуска аутентификации** , поэтому просочившийся JWT не может достичь места появления. Остаются две обязанности оператора:

- **Не «исправляйте» ошибку 403, создавая клиентскую IP как петлю.** Установка `X-Forwarded-For: 127.0.0.1` или прокси-сервера, который перезаписывает исходный адрес на петлю, повторно открывает именно тот класс RCE который закрывает этот уровень. Предоставляйте dashboard/API через прокси-сервер — а не маршруты, поддерживающие создание.
- **Сохраняйте минимальный обход области управления.** Только `/api/mcp/` можно обойти, и только с помощью ключа `manage` -scoped API. `SPAWN_CAPABLE_PREFIXES` никогда не может быть добавлен в список обхода. — схема zod отклоняет их, а `isLocalOnlyBypassableByManageScope` запрещает их во время выполнения (глубокая защита), что на информационной панели означает «нельзя сделать обходными». Тот же список запретов также содержит несколько маршрутов LOCAL_ONLY, которые не создаются, но никогда не должны быть доступны удаленно: — `/api/oauth/kiro/auto-import` (читает локальные файлы учетных данных Kiro ), `/api/discovery/` и `/api/issue-agent/`. Загрузчик моментальных снимков во время выполнения также удаляет такие записи из строки сохраненных настроек, а устаревший импорт JSON (`/api/settings/import-json`) никогда не записывает ключи обхода. Каждая запись `LOCAL_ONLY_API_PREFIXES` должна находиться либо в списке запрещенных, либо рассматриваться как подходящая для обхода (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршруты с возможностью создания динамических сегментов и статических путей в `/api/providers/` (например `/login`, `/refresh-cursor`) покрываются компаньоном `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` на основе регулярных выражений в `src/shared/constants/spawnCapablePrefixes.ts`, а не плоским массивом `SPAWN_CAPABLE_PREFIXES` — плоский массив должен был бы покрывать весь префикс `/api/providers/`, чтобы перехватить их, чрезмерно расширяя дерево маршрутов, которые удаленные панели мониторинга законно используют для провайдера CRUD.

**Аудит доступа** —, чтобы убедиться, что эти маршруты не достигаются за пределами хоста:

- Откройте** Инвентаризация авторизации** на `/dashboard/settings/security`: он отображает живой список префиксов LOCAL_ONLY, префиксы которых можно обойти, и набор, поддерживающий создание во время компиляции («нельзя сделать обходным»).
- Найдите в журналах обратного прокси-сервера/доступа приведенные выше префиксы в сочетании с адресом клиента без обратной связи. Любое такое попадание, возвращающее `200` вместо `403 LOCAL_ONLY` означает, что прокси маскирует реального клиента. IP — исправит прокси.
- `403 LOCAL_ONLY` в журналах OmniRoute для одного из этих путей означает, что защита работает должным образом, а не ошибку, которую нужно подавить.

#### Удаленно доступные маршруты с контрольным шлюзом на месте вызова

Некоторые маршруты должны оставаться доступными с удаленной панели мониторинга, но при этом на стороне хоста должна выполняться проверка (`which <binary>`, `<binary> --version`, `tailscale status --json`) для локальных вызывающих абонентов. Они не являются LOCAL_ONLY для `GET`; вместо этого обработчик считывает вердикт доверенного узла с помощью `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) и запускает проверку только для вызывающих абонентов `loopback` / `lan`. Вызывающий `remote` получает ту же форму ответа, построенную из непорожденных источников (сохраняющееся состояние, настройки, проверки файловой системы), помеченных `probed: false`.

| Маршрут                                                          | Проверка пропущена для удаленных абонентов                                    |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | Проба времени выполнения CLI (`allowLocalRuntimeProbe`) и резервный вызов CLI |

Новый маршрут чтения, который проверяет хост, следует тому же шаблону или сразу классифицируется LOCAL_ONLY.

#### Экспорт и восстановление учетных данных доступны только оператору.

Уровень выше решает только, требуются ли какие-либо учетные данные. Маршруты, которые загружают сохраненные учетные данные, добавляют вторую проверку в обработчике: `GET /api/settings/export-json` (расшифрованные соединения провайдера и необработанные ключи API ), `GET /api/db-backups/export` (файл SQLite ) и `GET /api/db-backups/exportAll` (полный архив) вызывают `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). Он принимает сеанс информационной панели, локальный субъект CLI или экземпляр с отключенным входом в систему и отвечает `403` на ключи API любой области (включая `manage` и `admin`) и на токены доступа `oma_`. Деструктивные аналоги имеют те же границы: `POST /api/db-backups/import` (загруженный `.sqlite`, включая `dryRun=true` ), `POST /api/db-backups` (восстановление сохраненной резервной копии по идентификатору) и `POST /api/settings/import-json` (восстановление устаревшего JSON ) заменяют действующую базу данных или весь набор settings/connections/API-key, поэтому учетные данные компьютера также не могут их активировать. Уничтожение точек восстановления имеет те же границы: `DELETE /api/db-backups` (очистка — сохраняет последние N / отброшенные данные старше D дней) и `PATCH /api/db-backups` (настройки хранения), поскольку постоянное сохранение — это именно то, что `cleanupDbBackups()` применяет после каждого автоматического резервного копирования (`src/lib/db/backup.ts`), поэтому учетные данные машины, которые могли бы сохранить `keepLatest: 1` удалили бы все в следующем снимке. Листинг и создание резервных копий (`GET`/`PUT /api/db-backups`) сохраняют обычную аутентификацию управления. Выдача токена синхронизации (`POST /api/sync/tokens`) использует тот же вспомогательный метод, а также доверенный токен внутренней службы обратной связи.

### Начальная загрузка при новой установке — это — только для обратной связи от реального узла, а не `Host`

Без настроенного пароля управления (и без `INITIAL_PASSWORD`), `isAuthRequired()` в `src/shared/utils/apiAuth.ts` оставляет анонимную загрузочную загрузку открытой.** только для одноранговых узлов обратной связи** . Обратный шлейф определяется на основе сигналов доверенных одноранговых узлов в следующем порядке: реальный одноранговый узел TCP с отметкой токена (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, что видит политика), собственный вердикт `AUTHZ_HEADER_PEER_LOCALITY` конвейера (то, что видят обработчики маршрутов, доверяется только тогда, когда установлен `OMNIROUTE_PEER_STAMP_TOKEN` ) или реальный одноранговый узел сокета для прямых вызывающих абонентов. `Host` / `nextUrl.hostname` никогда не консультируются, а запись первого пароля (`POST /api/settings/require-login`) находится под тем же ограничением, а не открыта для каждого узла сети (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передает свой собственный вердикт `peerContext`, поэтому заголовки запроса ORIGINAL (pre-strip) никогда не решают его.

### Уровень 3 — MANAGEMENT (по умолчанию)

Все остальные маршруты управления. Требуется аутентификация, если не настроен `requireLogin=false`. Токены CLI могут аутентифицировать эти маршруты (обратная связь + valid HMAC).

## Порядок проверки

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти к следующей проверке
     → не loopback, Bearer с областью manage
        И isLocalOnlyBypassableByManageScope     → разрешить (management_key)
     → иначе                                     → отклонить с 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → разрешить (system)
  3. hasValidCliToken(headers)?
     → разрешить (cli) [loopback + проверка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) или requireLogin=true?
     → isDashboardSessionAuthenticated?
        → разрешить (dashboard_session)
     → Bearer с областью manage для пути, не допускающего обход?
        → разрешить (management_key)
     → отклонить с 401/403
  5. requireLogin=false?
     → разрешить (anonymous)
```

Ветвь с областью manage на шаге 1 — единственный аутентифицированный способ получить доступ к маршруту
LOCAL_ONLY; при сбое бэкенда аутентификации возвращается 503 (а не 403), поэтому
истёкшая БД не приводит незаметно к режиму «запретить».

## Добавление нового маршрута с возможностью появления

1. Добавьте префикс пути к `LOCAL_ONLY_API_PREFIXES` в `src/server/authz/routeGuard.ts`
2. Добавьте в `tests/unit/authz/routeGuard.test.ts` тест, подтверждающий, что `isLocalOnlyPath()` возвращает true для нового префикса.
3. **Никогда не пропускайте этот шаг** — см. жесткое правило #15 в `CLAUDE.md`
4. Решите: принадлежит ли этот маршрут ALSO `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`? Ответ по умолчанию** нет** . Соглашайтесь только в том случае, если маршрут безопасен для доступа к держателю области управления (т. е. если NOT порождает произвольный код, управляемый пользователем).

## Добавление пути, допускающего обход с областью manage

1. Убедитесь, что маршрут не выполняет предоставленный пользователем код или команды. Если
   выполняет, остановитесь — это исключение здесь неприменимо.
2. Добавьте префикс в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` в
   `src/server/authz/routeGuard.ts`
3. Добавьте покрытие в `tests/unit/authz/management-policy.test.ts` для всех четырёх
   вариантов запроса: без Bearer (403), Bearer с областью manage (разрешить), Bearer без области manage
   (403), а также отдельный регрессионный тест для префикса, подтверждающий, что `/api/cli-tools/runtime/*` остаётся
   доступным строго через loopback даже при наличии Bearer с областью manage.

## Документирование уровней безопасности в OpenAPI

При добавлении нового маршрута в `docs/openapi.yaml` примените соответствующее
пользовательское расширение, если маршрут классифицирован в `routeGuard.ts`:

| Классификация routeGuard.ts                  | Аннотация YAML             | Применяемое ограничение                                   |
| -------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                    | `x-loopback-only: true`    | Безусловно блокируется для запросов не через loopback     |
| `ALWAYS_PROTECTED_API_PATHS`                 | `x-always-protected: true` | Аутентификация обязательна даже при `requireLogin=false`  |
| Внутренний маршрут администрирования/отладки | `x-internal: true`         | По умолчанию скрыт из /dashboard/api-endpoints            |
| Нет (публичный / стандартная аутентификация) | (аннотация не требуется)   | Стандартный доступ, управляемый параметром `requireLogin` |

### Проверка

Два скрипта обеспечивают согласованность аннотаций YAML с `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершается с ошибкой, если покрытие < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершается с ошибкой, если аннотации `x-loopback-only` или
  `x-always-protected` расходятся с константами времени компиляции

Оба скрипта запускаются в хуке перед коммитом и в CI.

### Правило ложноположительного срабатывания

Если маршрут аннотирован `x-always-protected` или `x-loopback-only`, но НЕ входит в
соответствующую константу `routeGuard.ts`, скрипт проверки покрытия завершается с ошибкой. Исправление всегда заключается в том, чтобы привести
YAML в соответствие с тем, что фактически контролирует `routeGuard.ts`, а не добавлять маршруты в `routeGuard.ts`
без одновременной реализации логики ограничения доступа.
