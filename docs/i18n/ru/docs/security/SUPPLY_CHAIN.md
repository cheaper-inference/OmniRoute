OmniRoute публикует артефакты npm и Docker. Эти проверки обеспечивают происхождение,
инвентаризацию (SBOM) и сканирование CVE; все инструменты имеют открытый исходный код
и интегрированы в процессы выпуска.
Позиция **сначала рекомендации** — сейчас проверки только формируют отчёты, а после
первого успешного выпуска станут блокирующими.

| Проверка                 | Инструмент                                     | Где                           | Блокирует?                 | Результат                                      |
| ------------------------ | ---------------------------------------------- | ----------------------------- | -------------------------- | ---------------------------------------------- |
| Происхождение SLSA (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | только при сбое публикации | значок npmjs / `npm audit signatures`          |
| SBOM npm                 | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | только при сбое создания   | ресурс выпуска + артефакт                      |
| SBOM образа              | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | рекомендательная           | артефакт CycloneDX                             |
| CVE Trivy (SARIF)        | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | рекомендательная           | SARIF (HIGH+CRITICAL) → вкладка Security       |
| Проверка CRITICAL Trivy  | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **блокирующая**            | `exit-code: '1'` для исправимых CRITICAL       |
| vulnCount osv            | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **блокирующая**            | фиксирует `metrics.vulnCount` (direction:down) |
| OpenSSF Scorecard        | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | рекомендательная           | SARIF → Security + значок                      |

Пороговая проверка CVE образа использует **два шага** в `docker-publish.yml`: шаг SARIF
(`HIGH,CRITICAL`, `exit-code: 0`) сохраняет видимость HIGH+CRITICAL на вкладке Security,
не блокируя выпуск; шаг _проверки CRITICAL_ (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) завершает выпуск с ошибкой при наличии CVE уровня CRITICAL, **для которой
доступно исправление**. `ignore-unfixed` предотвращает блокировку выпуска из-за CVE
базового образа, для которой ещё нет исправления от вышестоящего поставщика.

## ⚠️ Вариативность CVE (блокирует проверки osv/Trivy)

osv и Trivy сверяют зависимости с базами данных CVE, которые **постоянно пополняются**. PR, **не изменяющий никаких зависимостей**, может внезапно получить красный статус из-за того, что для существующей зависимости была раскрыта новая CVE (osv: измеренный `vulnCount` > базового значения; Trivy: новая исправимая уязвимость уровня CRITICAL в образе). **Это ОЖИДАЕМОЕ рабочее поведение блокирующей проверки CVE, а не регрессия продукта.**

Когда osv или Trivy получают красный статус из-за недавно раскрытой CVE, следует:

1. **Обновить затронутую зависимость** (предпочтительно) — перейти на исправленную версию через `package.json` `overrides` (для транзитивных зависимостей) или пересобрать образ на основе исправленного базового образа.
2. **Если исправления от сопровождающих проекта ещё нет:**
   - **osv:** обновить базовое значение `metrics.vulnCount` в `config/quality/quality-baseline.json` (`npm run quality:ratchet -- --update` не распространяется на отдельные проверки — измените значение вручную, `direction:down`), добавив пояснение и ссылку на отслеживающую задачу.
   - **Trivy:** добавить запись в `.trivyignore` (по одному CVE-ID на строку) с комментарием, содержащим обоснование, и ссылкой на отслеживающую задачу. `ignore-unfixed: true` уже автоматически учитывает CVE, для которых нет исправлений.

Обязательные запуски OSV (`check:vuln-ratchet -- --ratchet`) завершаются с блокировкой, статусом `INCOMPLETE` и кодом выхода 2, если сканер, отчёт или базовое значение не могут быть проверены. При выявлении регрессии возвращается код выхода 1. Необязательный запуск по-прежнему может вернуть `SKIP` с кодом выхода 0, что не подтверждает успешное прохождение зависимостями сканирования. Блокирующий этап Trivy также требует успешного выполнения измерения: недоступные инструменты, завершившиеся сбоем задания и отсутствие данных об образе не позволяют подтвердить отсутствие уязвимостей в образе.

## Риск устаревшей зависимости

Корневой lock-файл больше не содержит `extract-zip` или ведущей к нему зависимости после
обновления закреплённой версии инструмента разработки promptfoo. Это устраняет ранее принятую
цепочку `promptfoo` → `@openai/codex-security` → `extract-zip`, отслеживаемую в #14482.
Регрессионные проверки в `tests/unit/extract-zip-14482-exposure.test.ts` предотвращают её
повторное появление и сохраняют запрет на импорты из производственного кода.

Текущее исправление зависимостей также ограничивает переопределения совместимости клиентом MSAL
для Azure identity, FTP-клиентом get-uri и зависимостью Zod для OpenCode v1 SDK. Получение токенов
Azure и извлечение данных по FTP тестируются с использованием контролируемых транспортов; оба пакета OpenCode
выполняют собственные наборы сборки и тестирования. Количество предупреждений реестра отражает состояние
на конкретный момент времени и может измениться после фиксации lock-файла.

## Бэклог: предупреждение Scorecard → блокировка

После первого успешного выпуска с отчётом Scorecard:

- Scorecard: порог оценки (фиксирует измеренную оценку; она не может снижаться).

Дополняет проверки этапа 7 (osv-scanner, gitleaks, actionlint+zizmor): zizmor
проверяет сами рабочие процессы; Scorecard измеряет совокупное состояние репозитория.
