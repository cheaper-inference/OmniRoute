Guardrails обеспечивают безопасность, соблюдение политик и преобразование
контента на границе между OmniRoute и вышестоящими провайдерами. Каждый
guardrail может проверять (и при необходимости отклонять, преобразовывать
или дополнять аннотациями) полезную нагрузку запросов (`preCall`) и ответы
вышестоящих провайдеров (`postCall`).

Система работает по принципу **fail-open**: если guardrail выбрасывает
исключение во время выполнения, реестр фиксирует ошибку и переходит к
следующему guardrail, не прерывая запрос. Блокировка — это всегда явное
решение (`block: true`), а не случайность. Единственное исключение —
прерванный запрос: когда `signal` вызывающей стороны прерывается,
выбросивший исключение guardrail отклоняет выполнение хука, а не
пропускается.

Хуки выполняются **не** на каждом маршруте и не для каждого ответа.
Прочитайте [Покрытие и ограничения](#coverage-and-limits), прежде чем
полагаться на guardrail как на средство защиты.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Базовая модель GLM 5.3 и `glm-5.3-{low,high,max}` имеют явные метаданные `supportsVision:false` registry/spec. Варианты GLM 5.3 Flash остаются моделями с собственным зрением. Маршрут `/v1/messages` кода Claude входит в общую цепочку ограждений предварительного вызова `handleChat`** до** перевод Claude-to-OpenAI; вложенные изображения результатов инструмента `Read` должны быть описаны или обработаны до того, как перевод превратит их в содержимое OpenAI `image_url` (#17069).

Перехватывает запросы с изображениями, направленные на** модели без зрения** и либо перенаправляет весь запрос на модель с поддержкой машинного зрения, либо заменяет части изображения текстовыми описаниями, созданными настраиваемой моделью машинного зрения перед восходящим вызовом. Это позволяет поставщикам текстовых услуг прозрачно обрабатывать мультимодальные полезные данные.

| `describe` |              | Всегда описывайте — блок перенаправления полностью пропускается; всегда отвечает выбранная пользователем модель.                                                                                                                                                                                                               |

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда ключ API вызывающего абонента ограничивает `allowedConnections`, пулы квот (`allowedQuotas`) или модели (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает только перенаправление и описание моделей, которые ключ может использовать, в соединениях, которые ключ может использовать. Затем вызов описания всегда проходит через самоцикл OmniRoute с заголовком `x-omniroute-self-loop-key-id`, поэтому принимающий запрос чата снова применяет политику соединения и модели этого ключа. `enforceApiKeyPolicy()` учитывает этот заголовок только вместе с носителем самоцикла, поэтому он может только сужать доступ, а идентификатор, который не разрешается, отклоняется.

Если для ключа не разрешена ни одна модель машинного зрения,** подтвержденная цель только для текста** локально отклоняет запрос изображения с помощью очистки HTTP 400 вместо пересылки байтов изображения в неспособный восходящий поток (#17069). Для целей с неизвестными или собственными возможностями видения путь описания сохраняет свое предыдущее поведение при открытии при сбое (meta `{ skipped: true, reason: "no_permitted_vision_model" }`). Запросы без ключа и ключи без этих ограничений ведут себя точно так же, как и раньше.

#### Подсказка описания с учетом задач (`modalityBridgeVisionTaskAware`)

По умолчанию** истинный** . `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет текст** последнее сообщение пользователя** (обрезано до 500 символов) в базовую подсказку описания, направляя описание в соответствии с тем, что на самом деле запрашивает пользователь (шаблон codex-vision-proxy), и запрашивая модель машинного зрения для расшифровки видимого текста. При выключенном флаге — или отсутствии пользовательского текста — базовое приглашение используется без изменений.

Собственный OpenAI-совместимый запрос самоцикла описания (`callVisionModelSingle()` в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` — безоговорочно для каждого caller/provider, не ограничиваясь каким-либо клиентским сигналом. Выборка с низкой детализацией снижает точность OCR именно для той задачи транскрипции текста, которую запрашивает это приглашение, поэтому сам вызов описания всегда запрашивает высокую детализацию независимо от того, какой уровень детализации использовался исходным входящим запросом. Это влияет только на тело внутреннего запроса описания; это не меняет того, как OmniRoute пересылает собственный `image_url.detail` вызывающего абонента по основному запросу. —, значение которого по умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode, в `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветвь формата Anthropic цикла описания не имеет поля `detail` и не затрагивается ни одним из вариантов по умолчанию.

#### Опишите ограничение вывода (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон           |
| ------------------------------ | ------------ | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50 000 |

`0` (по умолчанию) означает** без кепки** — описание, возвращаемое `callVisionModel()`, передается без изменений, сохраняя существующее поведение. Любое значение в диапазоне 100–50 000 усекает описание суффиксом `…` перед его объединением обратно в `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`). Увеличьте это значение для задач OCR с большим количеством деталей, где нижестоящая модель требует полной транскрипции; понизьте его до связанного использования токенов на моделях болтливого зрения. Поле информационной панели находится на панели «Дополнительно» вкладки «Видение» (`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и фиксирует любое значение от 1 до 99 до нижнего уровня 100, оставляя явное значение `0` нетронутым. — `0` является самостоятельным допустимым значением Zod (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто «неустановленным» значением по умолчанию.

#### Описать кеш (`modalityBridge/bridgeCache.ts`)

Кэш LRU + TTL в памяти для описания выходных данных, общий для всего процесса. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с кадрированием префикса длины (без коллизий границ поля). Компонент модели – это** настроен** Модель моста, а не модель, которая фактически ответила на запрос — `callVisionModel` может вернуться к внутреннему состоянию, а ввод ключа за попытку приведет к фрагментации кэша. Неудачные описания никогда не кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Удаленная нормализация изображения (автоматическая выборка describe/base64 )

Когда мост получает** удаленный** само изображение — Anthropic описывает самовызов и преобразование base64 формата claude-wire (`ensureBase64ImagesForClaudeWire`), оба через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — результирующие данные URI передаются через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед внедрением в запрос модели видения. Увеличенные изображения уменьшаются до** 2048 пикселей по длинному краю** (соответствует ограничению изменения размера OpenAI/Anthropic которое уже применяется на стороне сервера), что сокращает загрузку bytes/latency без изменения того, что видит модель видения. Для изменения размера используется `sharp`, загружаемый посредством динамического импорта: на платформе, где не удается загрузить собственный двоичный файл, `normalizeDataUri()`** никогда не бросает** — он возвращается к передаче исходных байтов, поэтому путь describe/base64-conversion всегда продолжает работать. Байты, не являющиеся изображением (выборка, которая не вернула декодируемое изображение), также передаются без изменений. Область действия этой нормализации ограничена изображениями, которые мост выбирает для собственного самовызова — Она никогда не применяется к необработанным сквозным полезным данным вызывающей стороны, что соответствует принципу мутации «только по согласию» (жесткое правило #20).

#### Схема настроек миграции +

Новые ключи `modalityBridge*` проверены Zod в `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, трио `modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая Audio Bridge. Миграция `141_modality_bridge_settings.sql` копирует существующие устаревшие значения `visionBridge*` в соответствующие новые ключи (идемпотентный, никогда не перезаписывает значение `modalityBridge*` установленное оператором); устаревшие ключи остаются принятыми в качестве резервного варианта чтения в течение одного цикла выпуска.

#### Статистика + заголовка прозрачности

Ответы с преобразованием описания содержат `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (построенный `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`, отмеченный `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`). Перенаправленные запросы получают** нет** заголовок — полезные данные остались нетронутыми, а замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (аутентификация управления, тот же уровень, что и `GET /api/settings`) возвращает счетчики модальности `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` в памяти для `vision`, `audio` и `video`. `averageLatencyMs` использует `latencySamples`, а не все попытки, в качестве знаменателя; операция без синхронизации не создает выборку с нулевой миллисекундой. `bridged` остается обратно совместимым псевдонимом для успешных преобразований; неудачные попытки не увеличивают его. Счетчики сбрасываются при перезапуске процесса по умолчанию (телеметрия, а не учет).

#### Конфигурация информационной панели

Специальная страница информационной панели — `/dashboard/settings/modality-bridge`. Его вкладки `Vision`, `Audio` и `Video` с URL-адресом сохраняют параметры запроса при переключении значения `tab`. На вкладке «Видение» представлены включение, режим, выбор модели (включая автоматический выбор по умолчанию), подсказки с учетом задач, расширенные ограничения timeout/image/description-length/cache, счетчики времени выполнения и запрос защищенного образца. Вкладка «Аудио» также доступна: она предоставляет возможность включения, средство выбора модели только для STT с автоматическим режимом, пределы timeout/max-clip, счетчики звука и образец теста `input_audio`. Вкладка «Видео» функциональна: она сообщает о состоянии выполнения FFmpeg/ffprobe — об одном из четырех явных состояний UI (`unknown`, когда зонд находится в работе или не может завершиться, `restricted` на узле информационной панели без обратной связи, где зонд пропускается на стороне клиента, `unavailable` после зондирования и подтверждения отсутствия, или `available` с версиями FFmpeg/ffprobe ). — сохраняет ограничения enable/model/frame/video/timeout, фильтрует средство выбора модели до моделей с поддержкой машинного зрения и отображает счетчики видео.

Бывшая карта Vision Bridge в настройках AI представляет собой ссылку совместимости на новую страницу; у него больше нет второй копии формы. Медиа-провайдеры также связывают рабочие процессы преобразования изображения в текст и речь в текст с соответствующими вкладками Modality Bridge, не удаляя существующую игровую площадку преобразования речи в текст.

**Обход входа в автоконтур:** когда вызов описания маршрутизируется через собственный цикл `/v1` OmniRoute(нестандартная модель поставщика), подзапрос отправляет `x-omniroute-admission-bypass: internal` и аутентифицируется с помощью разрешенных учетных данных самоцикла — локального дозорного `sk_omniroute` в локальном режиме или настроенного оператором ключа `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env (#1350), поэтому развертывания `REQUIRE_API_KEY=true` все еще могут выполнять вызов описания. Обход учитывается только для этих конкретных учетных данных, поэтому внешние клиенты не могут использовать заголовок для пропуска доступа.

Устаревшие настройки по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию mode/task-aware/cache и преобразователь настроек находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Guardrail предоставляет опцию конструктора `deps`, поэтому тесты могут внедрять поддельные реализации `getSettings` и `callVisionModel`.

### Аудио мост (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает запросы чата, несущие аудио, до того, как они достигнут цели, которая, как известно, не принимает аудиовход. Он никогда не перенаправляет запрос чата: аудиочасти расшифровываются через существующую многочастную конечную точку, совместимую с OpenAI, а выбранная модель чата продолжается текстовыми расшифровками.

Поток:

1. Разрешите `supportsAudio` через `getResolvedModelCapabilities()`. Выигрывают явные метаданные реестра поставщиков, затем метаданные статической модели, а затем синхронизированный `modalities_input`. Объявленный список ввода без `audio` — это `false`; никаких доказательств возможностей не осталось `null`. И `false` и `null` активируют консервативный мост, а `true` обходит его.
2. Разрешите настройки `modalityBridgeAudio*` и извлеките из каждого сообщения поддающиеся склейке аудиочасти верхнего уровня с помощью общего детектора `detectMediaParts()`. Поддерживаемые формы проводов: OpenAI `input_audio`, `audio_url` и `source.media_type: "audio/*"`. Вложенный звук обнаруживается для маршрутизации, но не удаляется путем сращивания. Работа ограничена `modalityBridgeAudioMaxClips`; более поздние части остаются нетронутыми.
3. Уважайте настроенный `provider/model` или позвольте `selectAudioBridgeModel()` пройти `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбрать первую модель с пригодными для использования активными учетными данными поставщика.
4. `callAudioTranscription()` преобразует звук base64/data-URI в составной `file` или загружает удаленный `audio_url` через общедоступную исходящую защиту с закреплением DNS и привязкой 25 MB. Затем он POSTs файл и выбранную модель в локальный автоцикл `/v1/audio/transcriptions`, аутентифицируя его с помощью `resolveSelfLoopBearer()`. Существующий маршрут транскрипции выполняет обычный поиск учетных данных, обработку cooldown/rate-limit и отправку поставщика.
5. Успешные вызовы заменяют свои части на `[Audio N]: <transcript>`. Вызовы выполняются с помощью `Promise.allSettled`: при отдельном сбое исходная аудиочасть сохраняется (контракт #4012 ). Если каждый вызов терпит неудачу и цель доказана `supportsAudio === false`, части становятся `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430 ). Для неизвестной цели (`null`) результат всех неудач остается нетронутым. Проверенная цель, предназначенная только для текста, без пригодных для использования учетных данных STT получает ту же явную заглушку без выполнения сетевого вызова.

Успешные расшифровки используют общепроцессный кеш LRU/TTL Modality Bridge. Ключ объединяет ссылку на звук, метку стабильной операции `audio-transcription` и выбранную модель STT ; сбои никогда не кэшируются. Попытки аудио обновляют общие счетчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`. Преобразованные ответы содержат `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; нетронутые запросы не получают сегмент Audio Bridge.

Настройки времени выполнения поддерживаются БД и проверяются Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Авто или STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кеш по-прежнему контролируется `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Видеомост (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает части видео верхнего уровня в Завершениях чата `messages` и Ответах API `input` перед вызовом цели без известной встроенной поддержки видео. Поддерживаемые формы: `input_video`, `video_url`, `video_source`, HTTPS URLs и `data:video/*;base64,...` data URIs. Простые имена файлов в тексте не рассматриваются как видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запросов, проверку capability/policy, агрегирование каждого запроса и полезную нагрузку ответа. Работа — для каждого видео, кэш всего результата, описывающий последовательность кадров (которая объединяет любую аудиозапись, объявленную вызывающим абонентом), и metrics/abort/cleanup — для каждой попытки скрыт за `processVideoPart` в `videoBridgePipeline.ts`, вызываемый один раз для каждой части видео внутри цикла `preCall`. Этот модуль также определяет явные границы портов `VideoMediaBrokerPort` (получение байтов и извлечение выборочных кадров), `VideoAudioTranscriptionPort` (объединение объявленной вызывающей стороной аудиорасшифровки с выборочными заголовками) и `VideoDrilldownPort` (устаревшая форма хранилища необработанных данных). Производство STT и удержание кадра формируются вокруг описывающего порта через `createVideoSttAdapter` и `createVideoDrilldownAdapter`; последний использует общий жизненный цикл непрозрачного дескриптора.

Публичный путь запроса `/v1` никогда не импортирует и не вызывает подпроцесс. Удаленные видео загружаются с ограничением в 50 MiB ; встроенные видео в формате Base64 имеют консервативное ограничение декодирования 36 MiB на одно видео, поэтому конверт model/messages/framing может оставаться в пределах лимита приема общедоступных запросов JSON равного 50 MiB. Перед распределением проверяются встроенные оценки длины и декодированного размера. HTTPS требуется на начальном удаленном URL и каждом перенаправлении, используя существующую общедоступную исходящую защиту с закреплением DNS. Затем байты пересекают точную внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут является одновременно `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только аутентифицированный для каждого процесса запрос доверенной обратной связи и никогда не принимает URL, путь к файловой системе, исполняемый файл или список аргументов. Конвейер API body-size и инкрементный читатель тела обработчика независимо обеспечивают ограничение ввода брокера в 50 MiB. Его ограниченная очередь выполняет одно извлечение за раз, допускает четыре ожидающих задания и ограничивает ожидающий ввод на уровне 100 MiB.

Внутри брокера `ffprobe` читает частный локальный файл; список разрешенных фиксированных форматов исключает форматы списков воспроизведения и манифестов. Для разрешенных контейнеров семейства MOV внешние ссылки на данные MOV остаются отключенными по умолчанию, и фиксированная команда не включает их. И `ffprobe` и `ffmpeg` используют белый список протокола `file` -only, один поток, фиксированные массивы аргументов, отсутствие оболочки и исполняемые файлы, разрешенные из `PATH`. Кавер-стримы с прикрепленными изображениями не являются воспроизводимыми кандидатами. Все воспроизводимые потоки должны удовлетворять ограничениям, и явный поток по умолчанию предпочтительнее детерминированного резервного варианта с наименьшим индексом. Видео ограничено 600 секундами, 8 192 пикселями на одно измерение и 33 554 432 исходными пикселями. FFmpeg выбирает 1–16 кадров JPEG средней точки, масштабирует длинный край максимум до 1024 пикселей без масштабирования меньших входных данных и никогда не получает URL. По умолчанию выборка равна `uniform`. Необязательные политики `scene_aware` и экспериментальные политики `segment_aware` выполняют один дополнительный фиксированный проход FFmpeg по уже проверенному локальному потоку, выбирают ограниченные временные метки сцены `showinfo` и детерминированно возвращаются к тем же унифицированным средним точкам в случае сбоя детектора, тайм-аута, неправильного вывода или пустого набора кандидатов. В режиме с учетом сегментов выборки средней точки распределяются пропорционально проверенным интервалам сцены; Ниже подробно описаны доказательства с учетом сегментов и резервное поведение. Жесткое ограничение в 16 кадров применяется после выбора в каждой политике. Когда запрос с учетом сцены имеет бюджет только в один кадр, он использует единую среднюю точку активного полного видео или окна фокуса и сообщает `policyEffective: uniform`: один выбранный кадр сцены не может сохранить оба временных конца. Вызывающая сторона может дополнительно предоставить конечное окно фокуса (`start`/`end` секунд); границы привязываются к продолжительности мультимедиа, обратные или неконечные окна отклоняются, а все политики выборки выполняются только внутри нормализованного интервала. Результирующее окно включается в метаданные выборки и в префикс недоверенного описания, чтобы последующие модели могли отличить конкретный отрывок от полной временной шкалы.

Фокус семантической подписи — это отдельная явная настройка. Режим анализа `full` по умолчанию сохраняет существующее приглашение фрейма и никогда не пересылает текст запроса в модель подписи. В режиме `focused` мост считывает только последние непустые созданные пользователем `text`/`input_text` из того же контейнера Chat или Responses, нормализует их до NFC, сжимает управляющие символы и пробелы и ограничивает их до 500 кодовых точек Юникода. Пустой результат возвращает точное приглашение `full`. Полезная подсказка сериализуется как JSON в выделенном блоке контекста недоверенного пользователя и может отдавать приоритет только наблюдаемым деталям; он не может отменить отдельное предупреждение о невыполнении инструкций, видимых или слышимых в средствах массовой информации. Текстовый фокус никогда не подразумевает `start`/`end` и не изменяет временной сэмплер.

#### данные структурного сегмента FU-07

`segment_aware` использует один ограниченный проход предварительного анализа для уже проверенного локального видеопотока. Цепочка фиксированных фильтров сначала масштабируется максимум до 320 пикселей в ширину, обнаруживает изменения сцены и замороженные интервалы, затем производит выборку с частотой 1 кадр в секунду для получения информации о размытии, средней яркости и spatial/temporal. Пропуск ограничен 600 структурными выборками, одним потоком FFmpeg/filter, одним и тем же протоколом `file` -only и списками разрешенных контейнеров, границей вывода процесса в 1 MiB и максимум 30 секундами внутри общего abort/deadline. брокера. Он никогда не принимает команду, фильтр, путь или URL из запроса.

Структурные значения представляют собой детерминированные доказательства выборки, а не семантическое понимание видео. Они не делают выводов о предметах, действиях, подписях, речи или намерениях пользователя. Границы сцены и стоп-кадра образуют сегменты; замораживание покрытия, размытие, экспозиция, пространственная детализация и временные изменения влияют только на то, как распределяется существующий бюджет 1–16 кадров. Полностью замороженный сегмент ограничен одним кадром, а незамороженные сегменты конкурируют за оставшийся бюджет. Когда количество границ превышает количество кадров, сохраняется равномерное покрытие временной шкалы, поэтому быстрые ранние сокращения не могут скрыть длинный конечный сегмент. Границы сцены в пределах 1-секундного разрешения анализа границы стоп-кадра объединяются.

Отсутствующие фильтры, доказательства malformed/empty, ошибка детектора или ограниченное время ожидания предварительного анализа не позволяют открыть точную единую политику средней точки. Прерывание вызывающего абонента или крайний срок брокера не открываются при сбое: он завершает текущий подпроцесс, предотвращает последующее извлечение кадра, а частное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерирует детерминированные реальные параметры FFmpeg для экономии вызовов субтитров после дедупликации, плотного распределения бюджета, доказательств blur/exposure/SI-TI, быстрых сокращений с длинным хвостом и постепенного затухания ложных срабатываний. Он записывает время стены предварительного анализа и, если доступен `/usr/bin/time`, дочерний CPU и пиковый RSS. Его проверки качества являются лишь структурными оракулами. Реальное качество модели подписей остается `HOLD` поскольку у этой системы нет авторизованной конечной точки или замороженного судьи. Денежная экономия также остается равной `HOLD` если только `--caption-cost-per-call-usd` не предоставит явную положительную оценку на каждый вызов; сценарий никогда не выдумывает ни одного результата.

Каждый кадр ограничен 4 MiB, все необработанные кадры вместе — 23 MiB, а сериализованный ответ брокера — 32 MiB. Частный временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg и не принимает собственный путь к исполняемому файлу. Перед созданием субтитров мост применяет консервативный проход визуальной дедупликации: каждый JPEG сокращается до буфера оттенков серого размером 16 × 16 и сравнивается только с последним сохраненным кадром. Для запрошенного бюджета титров, превышающего один кадр, извлечение предоставляет ограниченный пул кандидатов, в два раза превышающий бюджет, но не более 16 кадров. Запрошенное ограничение применяется только после дедупликации, при этом первый и последний выбранные кандидаты сохраняются во время окончательного сокращения, когда бюджет составляет не менее двух. Версионная политика `grayscale-16x16-mean-cells-v2` использует большее из значений средней дельты яркости и соотношения ячеек миниатюр, нормализованная дельта которых составляет не менее 0,05. Порог дублирования — это константа 0,04, выбранная для предсказуемости, а не представленная в качестве параметра времени выполнения. Этот вторичный высококонтрастный сигнал сохраняет небольшое движение и видимые изменения текста, которые могут скрыть сравнение только по средним значениям. Ошибки компаратора или декодера не позволяют открыть и сохранить покрытие. Выходные метаданные разделяют извлеченные кандидаты, успешно использованные кадры и удаленные визуальные дубликаты.

Явно отмеченная часть видео может запросить контактный лист с отметкой времени. Мост строит максимум 4-колонную сетку JPEG с 16 кадрами. Каждая 512-пиксельная ячейка записывает временную метку своего источника в высококонтрастную нижнюю полосу, в то время как те же временные метки остаются в текстовых метаданных для последующей ассоциации и аудита. Полный JPEG остается ограниченным на уровне 32 MiB. Если `sharp` не может декодировать или составить сетку, мост возвращается к отдельным кадрам JPEG ; прерывание клиента по-прежнему распространяется через операцию листа.

Доказательства продвижения намеренно отделены от микротеста синтетического состава. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет систему управления версиями схемы A/B для реальных моделей машинного зрения, совместимых с OpenAI. Он измеряет токены, сообщаемые поставщиком, сквозную задержку (включая состав листов), количество вызовов модели и сохранение фактов, определенных в манифесте. Необработанные ответы модели не записываются в отчет; сохраняются только дайджесты SHA-256 и сопоставленный факт IDs. Жгут не выполняет вызов сети или платной модели, если не передан `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без этого явного реального выполнения его машиночитаемый вердикт останется `HOLD`; Сами по себе синтетические измерения payload/call-count не являются доказательством продвижения по службе.

Отдельный `scripts/perf/video-bridge-promotion-eval.ts` использует наблюдения FU-07 или FU-09. Для допуска к повышению требуются все восемь типов синтетических сценариев, а также очищенный реальный клип, не менее трех измеренных повторений на роль и случай, все десять заявленных показателей, замороженные дайджесты media/prompt/expected-fact/settings, уникальное наблюдение IDs и проверенный заданный порядок A/B. Квитанция о выполнении связывает дайджест корпуса, точный кандидат SHA и версию модели. Отсутствующие или недействительные измерения остаются `HOLD`, включая CPU выше 30 с, пик RSS выше 512 MiB или предварительный анализ выше 30 с. Это ограничения на допуск доказательств, а не новая гарантия соблюдения RSS во время выполнения.

FU-07 требует сохранения качества не менее 98 % и задержки p95 не более чем в 1,2 раза от базового уровня, а также либо абсолютного улучшения запоминаемости с учетом регистра на 0,05 при эквивалентных средних вызовах субтитров, либо как минимум на 10 % меньше средних вызовов субтитров после дедупликации. FU-09 требует качества не менее 0,85, удержания 95 %, уменьшения средней задержки на 20 % и сокращения количества токенов на 10 %. Утрата важных фактов, соблюдение правил внедрения или отсутствие использования препятствуют продвижению по службе. Одно выполнение не может ничего способствовать: `--previous-report` подтверждает два различных, непересекающихся, последовательно подходящих выполнения одного и того же policy/model revision/candidate/corpus. Выборочный эксперимент не может подтвердить эксперимент с контрольным листом.

Коллекционерам следует оценивать ответы в памяти и сохранять `responseDigest`, а также метрики и привязки наблюдений, но никогда не сохранять текст ответа. Потребитель также читает устаревшие необработанные наблюдения, но никогда не копирует этот текст в свои отчеты. Для каждого наблюдения принимается ровно одно из значений `responseDigest` или `rawResponseText`. Версионный список разрешений остается пустым с неизменяемым значением `hold` по умолчанию. Для приемлемой записи требуется ссылка на доказательства, политика, пересмотр модели, точный кандидат SHA, дайджест манифеста и два отдельных запуска IDs; конфликтующие контексты отвергаются. Эти метаданные представляют собой контракт на аудит, а не доказательство того, что указанный файл содержит подлинные измерения. Прежде чем добавлять какие-либо записи, просмотрите фактические поступления. Конечная точка статистики управления и панель мониторинга видео демонстрируют консервативную готовность. Сконфигурированный псевдоним модели сам по себе не устанавливает ее версию или работающего кандидата SHA, поэтому текущая панель мониторинга сообщает `HOLD`, а не повторно использует право на участие из другого контекста выполнения. Явный экспериментальный отбор остается отдельным от продвижения; никакие значения по умолчанию не изменяются автоматически.

Вызывающие абоненты могут прикрепить дополнительный массив `transcript.cues` к поддерживаемой части видео, если у них уже есть выровненный текст. Каждый сигнал должен содержать `text`, конечный интервал `start`/`end` внутри исследуемой длительности и `source` из белого списка (`client`, `embedded` или `audio-bridge`); По умолчанию `confidence` имеет значение `1` и должно оставаться между `0` и `1`. Точные повторяющиеся реплики свернуты. OmniRoute никогда не запускает транскрипцию из этих метаданных: проверенные сигналы копируются в описанный результат с указанием источника, достоверности и интервала и отображаются как ненадежные наблюдения вместе с заголовками кадров. Недопустимый текст, текст, выходящий за пределы допустимого диапазона или не имеющий происхождения, скорее отклоняется, чем смешивается с потоком подписей. Оба канала транскрипта тела запроса нормализуют предоставленное происхождение `client`, включая самозаявленные метки `embedded` или `audio-bridge`. Только адаптер, принадлежащий серверу, может назначать эти доверенные метки с помощью аргумента `trustedSource`, предназначенного только для кода; поле запроса JSON не может достичь этого аргумента. Текст стенограммы остается ненадежным контентом, полученным из средств массовой информации, независимо от его происхождения, и никогда не должен определять авторизацию.

Опытный абонент может предоставить трек `audioTranscript` для того же видео; он рассматривается как текст, предоставленный клиентом, а не как доказательство транскрипции сервера. Слияние выполняет визуальные и звуковые наблюдения в рамках одного крайнего срока и сигнала об отмене, упорядочивает их по общей временной шкале, сворачивает точные дубликаты и сообщает о частичном результате, если только одна сторона добилась успеха. Недействительный `audioTranscript` деградирует до частичного результата — визуальное описание сохраняется, а звуковая ветвь записывает исправленный код ошибки — вместо сбоя всего видео. Доступность для каждой ветки, частичный флаг и очищенные коды ошибок сохраняются в описанном результате, в метаданных ограждения (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), в метаданных кэша результатов и в счетчиках объединения мостов. Путь Video Bridge по умолчанию не вызывает преобразование речи в текст или загрузку второй копии мультимедиа; без этой явной дорожки он остается только видео.

**Сохранение транскрипта (#12150 P1).** Это применяется автоматически всякий раз, когда Video Bridge (который сам по себе является добровольным) отображает сигнал расшифровки. — не имеет отдельного флага хранения. Когда запрос отображает какой-либо сигнал расшифровки (объявленный вызывающим абонентом `transcript` или объединенный `audioTranscript`), ограждение помечает его `videoBridgeObserved` и создает отредактированную тень описания видео — идентичную визуализацию, в которой свободное текстовое тело каждого сигнала заменяется на `[redacted-video-transcript]`, построенное путем замены поля структурированного сигнала перед сборкой строки (никогда не путем анализа сглаженного текста, поэтому содержимое сигнала не — состязательным или обычные, включая тела, содержащие `]` такие как `[inaudible]`/`[music]` — могут выжить). Тело запроса сохраненного журнала вызовов заменяет каждую текстовую часть, полученную из видео, на эту отредактированную тень, соответствующую равенству содержимого; привязка `fullText` пересчитывается из готовой полезной нагрузки ограждения перед вызовом, поэтому сопоставление по-прежнему завершается успешно после того, как более поздние ограждения цепочки (маскеры PII и учетных данных, приоритеты 10/95) перезаписывают текст описания на месте, а после внедрения system-prompt/handoff/memory изменяет форму массива сообщений. Тело, отправленное вверх по течению к модели, не изменяется. Наблюдаемый запрос также не заполняет долговременную память (извлечение на основе запроса и ответа пропускается), поэтому собственный ответ модели не может отображать текст расшифровки в памяти.

**Необработанные видеополя (#12430).** Когда мост включен, а встроенная поддержка видео неизвестна или отсутствует, определенные поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved` даже после сбоя описания или ограничения `maxVideos`. `null` и количество пустых строк; отсутствуют поля и метаданные, не относящиеся к видео. Сохраненные копии редактируют эти поля или пропускают запрос, а caches/Memory игнорируется.

В этих резервных путях действительные сигналы вызывающего абонента становятся поддерживаемыми частями `text`/`input_text`, а не нестандартными полями поставщика. Оба трека, предоставленные по запросу, остаются ненадежными наблюдениями `client` с явным предупреждением о том, что видео не было описано и временные метки не были проверены по данным СМИ. Существующие общие бюджеты 256-cue/64-KiB и бюджеты на вызов применяются одновременно к двум трекам; временные метки должны соответствовать 600-секундному потолку брокера и любому предоставленному окну фокусировки. Недействительные треки отбрасываются, а не пересылаются как произвольный текст; действительный родственный брат по-прежнему может использоваться, если их общий бюджет не превышен. Поля Null/empty не добавляют текст. Этот резервный вариант не добавляет выборку или транскрипцию мультимедиа. Поля расширения транскрипта удаляются из резервного видеоносителя и его объектов `video_url`/`source`. Список разрешений для проводов OpenAI остается строгим; неизвестные собственные видеоносители остаются доступными, а известные текстовые цели сохраняют безопасные маркеры. Структурированные тени редактирования защищают добавленный текст расшифровки, в то время как исходный запрос вызывающего абонента остается неизменным. Целевые объекты с встроенной поддержкой и отключенные мосты сохраняют существующее поведение обхода.

Дополнительные сохраненные копии используют тот же сигнал наблюдаемого запроса. Необработанный снимок клиентского запроса перед защитой, ожидающий запрос в памяти и журнал ранних отклоненных запросов структурно заменяют поля расшифровки в частях видео; Строковые подсказки, синтезированные на этапах конвейера, и передача контекста редактируются в приемнике тела постоянного запроса. Сохраняющийся маркер `video_content_removed` заставляет продолжение `previous_response_id` закрываться при сбое, а не восстанавливать текст, который был намеренно отброшен. Если наблюдаемый запрос теряет свою тень редактирования для каждой части перед записью в журнал или даже одна из нескольких теней видео не совпадает после последующих мутаций запроса, сохраненное тело запроса полностью опускается вместо сохранения частично отредактированной расшифровки.

Для наблюдаемого запроса ответ модели может цитировать любую часть расшифровки без структурированной границы сигнала. Поэтому сохраненный журнал вызовов `responseBody` заменяется маркером пропуска; подробный артефакт конвейера (который может включать в себя тела upstream/client и фрагменты потока) не сохраняется. Семантические, идемпотентные и кэши воспроизведения рассуждений обходят операции чтения и записи для этого запроса. Запрос провайдера и видимый клиенту ответ остаются неизменными. Ранние байты поддержки активности удаляются из временного буфера, если подробный артефакт опущен. Неверно сформированное предупреждение EventStream от Kiro сообщает только о количестве байтов полезной нагрузки, но не о его содержимом или необработанной ошибке парсера JSON. Это не означает, что каждая несвязанная диагностика provider/plugin была проверена; более широкая развертка с сохраненным стоком отслеживается в #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельную подложку кэша loopback/token-authenticated. Для каждой операции также требуется канонический непрозрачный принципал ID. Прежде чем рабочий вызывающий объект будет включен, он должен получить этот ID от аутентифицированного клиента и никогда не должен пересылать значение, выбранное клиентом. Ключи кэша привязывают этого принципала к каноническому сеансу и ссылке на видео IDs, сохраняют только их ключи SHA-256-derived и ограничивают операции чтения и удаления одним и тем же субъектом. Кэш хранит не более 16 производных кадров JPEG на запись, срок их действия истекает через десять минут и поддерживает ограниченное чтение `start`/`end` или явное удаление сеанса.

Каждый принципал ограничен 16 записями и 64 MiB канонических данных JPEG. Эти ограничения не зависят от глобального потолка 64-entry/256 MiB : давление основной квоты вытесняет только записи этого принципала, которые использовались реже всего, прежде чем рассматривать глобальное вытеснение LRU. Записи с истекшим сроком действия удаляются как из основного, так и из глобального учета активности кэша, а отмена и сбой проверки не приводят к частичной замене.

Кэш отклоняет неканонический формат Base64, избыточное заполнение, медиафайлы, отличные от JPEG, искаженные или усеченные JPEGs и JPEGs, которые выдают предупреждение во время ограниченного декодирования полного изображения `sharp`. Он перекодирует каждое принятое изображение как канонический JPEG, извлекает ширину и высоту из декодированных байтов вместо того, чтобы доверять полям вызывающего объекта, и отбрасывает все конечные полиглотные байты, а не сохраняет их. В обе квоты взимается только ограниченный канонический сжатый буфер. Ограничение по проводу JSON включает служебные данные Base64 для максимального количества декодированных входных данных 32 MiB. В каждом хранимом выводе записывается проверенный JPEG format/resolution, политика выборки, версия вывода, время создания, хеш содержимого, вычисленный сервером, и хешированная родительская ссылка, а также хэш родительского содержимого доверенного вызывающего объекта. Отмена проверяется между асинхронными фазами decode/hash перед фиксацией атомарного кэша.

Производитель продукции повторно использует уже полученные кадры брокера только после успешного визуального анализа, без второго видео download/extraction. Для этого требуется оператор `modalityBridgeVideoDrilldownEnabled=true`, строгий для каждой части `drilldown: true` и аутентифицированная запись ключа API ID. Значения principal/session, объявленные клиентом, никогда не устанавливают право собственности. Без выполнения всех трех условий он не хэширует, не изменяет размер и не сохраняет дополнительные кадры. Нарушение удержания сохраняет полезную зрительную реакцию. Согласованные запросы обходят кэш результатов всего видео, поэтому кэшированные результаты никогда не воспроизводят дескрипторы повторного воспроизведения.

Успешные ответы JSON и SSE предоставляют не более четырех непрозрачных дескрипторов в ограниченном заголовке `x-omniroute-video-drilldown`. Авторизованные источники браузера могут читать этот заголовок без расширения политики происхождения CORS. Новые дескрипторы используют `v1.<32-byte random base64url token>`, а в реестре сохраняются только их хэши SHA-256. Анализатор reader/header также принимает устаревшие 64-шестнадцатеричные токены. Аутентифицированным общедоступным потребителем является `GET /api/v1/video-bridge/drilldown?handle=...`, независимо контролируемый `modalityBridgeVideoDrilldownRemoteEnabled=true`. Явное постоянное ложное отзывает доступ, даже если включен устаревший резервный вариант `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env. Удержание производства имеет аналогичный устаревший резервный вариант `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`. Оба резервных варианта по умолчанию отключены.

Потребитель получает право собственности на основе аутентифицированного ключа и применяет политику ключей: как GET так и DELETE принадлежат к категории конечных точек `video`, включая псевдонимы `/v1` и `/api/v1`. Ключи с непустым списком разрешенных конечных точек должны включать `video`; неограниченные ключи остаются совместимыми. Потребитель возвращает одну и ту же ошибку 404 для неизвестных, просроченных и других дескрипторов ключа. Он принимает `variant=preview|standard|detail` (максимальное измерение JPEG 320/640/1280, никогда не масштабируется), `limit=1..8` (или устаревший псевдоним `frames`, никогда оба), `page` с отсчетом от нуля и необязательные секунды фокуса `start`/`end`. Дублирующиеся ключи запроса и окна с обратным фокусом отклоняются. Каждый возвращенный вариант имеет хэш фактического содержимого и метаданные фактического разрешения, связанные с сохраненным источником. Варианты создаются при чтении, а не сохраняются в виде дополнительных сохраненных копий. Ответ JSON, включая Base64/envelope, ограничен 32 MiB; страница слишком большого размера возвращает 413, и клиент должен запрашивать меньше кадров. Считывает отмену проверки при каждом изменении размера и перепроверяет достоверность дескриптора перед возвратом. `DELETE` по владельцу идемпотентен; удаление или истечение срока действия TTL освобождает сохраненный источник и учет использования.

Общее хранилище является локальным для процесса: срок действия дескрипторов истекает при перезапуске и не подлежит передаче между независимыми процессами OmniRoute. Статистика управления отображает эффективную политику хранения/удаления и объединяет только сохраненные entries/bytes, но не носители, ссылки, основные IDs или дескрипторы. На панели настроек видео отображаются эти значения, и на ней могут сохраняться оба переключателя согласия. Эта документация по реализации не является доказательством фактического развертывания или продвижения; Приемка реальной модели отслеживается отдельно.

Кадры сопровождаются субтитрами с использованием настроенной модели видео. Пустое переопределение видео наследует настройку Vision; если оба пусты, автотрассировщик Vision выбирает эффективную модель с поддержкой машинного зрения. Успешные подписи заменяют исходную часть стабильным префиксом `[Video description:`, который также помечает текст как ненадежное наблюдение, полученное из медиа, и сообщает последующим моделям не следовать инструкциям, найденным в медиа. Ключи кэша подписей кадров включают байты JPEG, приглашение, метку времени и эффективную модель; кэшируются только успешные подписи. Записи кэша сохраняют фактическую успешную модель производителя, включая резервную модель; мост сообщает `mixed` когда разными моделями были произведены разные кадры. Попадание в кэш повторно использует этот идентификатор производителя вместо того, чтобы перемаркировать его как запрошенный план маршрутизации. Кэш результатов всего видео вводится при каждом вводе, который изменяет выходное приглашение —, эффективную модель, политику выборки, количество кадров, режим семантического анализа, отпечаток SHA-256 нормализованной подсказки фокуса, окно фокуса, `transcript`, `audioTranscript` и флаг контактного листа —, поэтому изменение любого из этих измерений является промахом в кэше, а не устаревшим повторным использованием. Версия политики визуальной дедупликации, пороговое значение и ограниченное количество кадров-кандидатов также явно указаны в ключе кэша результатов и метаданных; поэтому изменение политики не может повторно использовать устаревшее описание всего видео. Метаданные Result-cache v4 сохраняют режим и отпечаток, а не необработанную пользовательскую задачу. Метаданные Guardrail сообщают как о запрошенных, так и об эффективных режимах анализа; о запрошенном режиме `focused` без полезного пользовательского текста сообщается как `full`.

Guardrail извлекает каждую поддерживаемую часть видео, но описывает не более чем `modalityBridgeVideoMaxVideos`. Для цели, в которой установлено наличие `supportsVideo === false`, неудачные видео и видео с превышением лимита становятся явными маркерами безопасного текста, поэтому необработанное видео не сохраняется. Когда возможности неизвестны, эти части сохраняют свой видеоноситель; любая резервная расшифровка следует за преобразованием ограниченного текста, описанным выше. Цели с `supportsVideo === true` обходят мост. Сигнал прерывания запроса клиента распространяется через загрузку, очередь брокера, подпроцессы и вызовы подписей; прерывает перерыв между видео и всегда открыт для необработанных медиафайлов.

Настройки времени выполнения поддерживаются БД и проверяются Zod:

| ----------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`      | Необязательная среда выполнения, подписка                                                                      |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` сохраняет общие подписи; `focused` использует ограниченный, ненадежный контекст последнего пользователя |
| `modalityBridgeVideoModel`          | `""`         | Наследовать модель Vision Bridge                                                                               |

Устаревшие значения сохраняются. Значения тайм-аута видео, превышающие 120 секунд, привязываются к крайнему сроку брокера; новые настройки, записываемые выше этого предела, отклоняются. `GET /api/modality-bridge/video/runtime` требует наличия доверенной локальной петли обратной связи перед аутентификацией или проверкой во время выполнения, а затем требует аутентификации управления. Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную причину, по которой среда выполнения недоступна. Конечная точка внутреннего извлечения не является общедоступной загрузкой API: насыщение очереди возвращает `503` плюс `Retry-After`, отключение вызывающего абонента возвращает `499`, а фиксированный крайний срок брокера возвращает `504`. Преобразованные ответы добавляют `video->text;model=<visionModel>;parts=<videos>` в центральный заголовок `x-omniroute-modality-bridge` без удаления сегментов Vision или Audio.

### PII Маскер (`piiMasker.ts`)

Работает** оба** этапы.

- **`preCall`** клонирует полезные данные, обходит `system`, `messages`, `input` и `prompt` (включая простые строковые элементы) и применяет `processPII()` (из `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда `PII_REDACTION_ENABLED=true` обнаруженный PII редактируется в исходящей полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который контролирует только политику быстрого внедрения). Если редактирование отключено, обнаружение записей вызовов учитывается без перезаписи содержимого.
- **`postCall`** глубоко клонирует ответ, запускает `sanitizePIIResponse()` плюс маскер формы Responses-API (`maskResponsesOutput` — охватывает `output_text` и `output[].content[].text`). Если происходит какое-либо редактирование, измененный ответ заменяет оригинал.

Ограждение никогда не блокируется; он только аннотирует (`meta.detections`, `meta.redacted`) или перезаписывает.

**Двустороннее хранилище (`PII_REVERSIBLE_VAULT_ENABLED`, по умолчанию `false`).** Когда оба `PII_REDACTION_ENABLED` и `PII_REVERSIBLE_VAULT_ENABLED` включены (DB переопределяет > env > по умолчанию, считывается один раз для каждого запроса), `handleChat` открывает одно хранилище для каждого запроса клиента (`src/lib/pii/requestTokenVaultScope.ts`) и передает его на проход предварительного вызова как `GuardrailContext.tokenVault`. Затем маскер записывает суррогатные токены, такие как `<<PII_EMAIL_QWERTYUI_1>>` вместо `[EMAIL_REDACTED]`, как для встроенных, проверенных (GDPR/POPIA), так и для пользовательских правил. Nonce — это 8 случайных букв верхнего регистра на запрос, и одно и то же значение получает один и тот же токен в запросе. Только маскер чеканит: защита быстрого внедрения и `/api/guardrails/test` запускаются без хранилища и сохраняют заполнители.

- Поставщик, каждый этап комбо, повторная попытка, член комиссии по слиянию и судья по слиянию видят только токены. Токены восстанавливаются один раз, в ответе 2xx, который оставляет `handleChat`: для каждого поля в проанализированном SSE (разделение токена по событиям все еще разрешается; аргументы вызова инструмента экранируются с помощью JSON) или для каждого поля в теле JSON с перевычислением `Content-Length`. Содержимое и текст рассуждений, а также аргументы вызова инструментов восстанавливаются. Тела ошибок (4xx/5xx) сохраняют токены.
- Сбои остаются конфиденциальными: если чеканка не удалась или хранилище отклонило значение (1000 записей, 256 символов на значение, всего 64 KB ), вместо него записывается заполнитель; токен, который хранилище не может разрешить, или неудачное восстановление остается буквальным, и в журнал записывается только счетчик. В хранилище нет таймеров и глобального состояния; он очищается, когда поток ответов заканчивается, отменяется или возникает ошибка.
- Когда запрос создает токены, извлечение памяти, сохранение идемпотентности и обе записи в семантический кэш пропускаются, поскольку ни один последующий запрос не может разрешить эти токены. В журналах вызовов запросы и ответы провайдера содержат токены; тело зарегистрированного клиентского запроса по-прежнему является необработанными входными данными клиента, как и при обычном редактировании.
- Токены используют случайный одноразовый номер для каждого запроса, поэтому префикс приглашения меняется на каждом ходу: кэширование приглашения на стороне поставщика не срабатывает для замаскированных ходов, а токен, который возвращается на более позднем ходу (например, через `previous_response_id`), принадлежит старому запросу и остается буквальным.

#### Выбор по типу, пользовательские шаблоны и счетчики обнаружения

**Панель мониторинга Настройки → → Безопасность → Маскирование PII** выбирает _что_ замаскировано. Он не включает маскирование: это по-прежнему `PII_REDACTION_ENABLED` (запрос) и `PII_RESPONSE_SANITIZATION` (ответ + SSE), оба по умолчанию отключены.

- **Выбор по типу** — встроенные идентификаторы перечислены в `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Не установлено означает каждый тип (поведение до существования этого параметра). Шаблон `ssn_us` механизма запросов сопоставляется с `ssn`. Шаблоны (Минимальный, Стандартный, Финансовый, Бразильский, USA, GDPR, POPIA, Полный) заполняют только флажки в UI.
- **идентификаторы GDPR и POPIA** — двенадцать встроенных идентификаторов, охватывающих EU и персональные идентификаторы Южной Африки (таблица ниже). Их регулярные выражения, валидаторы и теги юрисдикции находятся в одной таблице `src/shared/utils/piiPatterns.ts`, которую используют как дезинфицирующий агент ответов (`src/lib/piiSanitizer.ts`), так и маскировщик запросов (`src/shared/utils/inputSanitizer.ts`). Соответствие редактируется только тогда, когда его валидатор принимает его; простого набора цифр никогда не бывает достаточно. Оператор, который сохранил суженный выбор до того, как эти идентификаторы появились, сохраняет свое поведение до тех пор, пока не будут отмечены новые идентификаторы.
- **Пользовательские шаблоны** — до 20 шаблонов регулярных выражений или подстановочных знаков (`*` = до 64 символов без пробелов, `?` = один). Матчи становятся `[CUSTOM_REDACTED]`. Каждый шаблон проходит через `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): не более 500 символов, флаги ограничены `g i m s u`, должны компилироваться, должны проходить `safe-regex` (катастрофический возврат) и не должны соответствовать пустой строке или заполнителю редактирования. Шаблон, который потерпел неудачу, отклоняется при сохранении и тестировании, а сохраненная строка, которая терпит неудачу, пропускается во время выполнения вместо компиляции. Пользовательские шаблоны выполняются только при включенной маскировке.
- **Счетчики обнаружения** Подсчеты — для каждого типа (никогда не совпадающие значения), хранятся в памяти и сбрасываются при перезапуске (`src/lib/pii/piiDetectionStats.ts`). Они увеличиваются только при включенной маскировке.

Настройки хранятся в таблице `key_value` (пространство имен `pii_settings`, `src/lib/db/piiSettings.ts`) и считываются через 1-секундный кеш. API:

| Метод  | Путь                     | Цель                                                                          |
| ------ | ------------------------ | ----------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Состояние флага, `enabledTypes`, `customPatterns`, счетчики обнаружения       |
| `PUT`  | `/api/settings/pii`      | Заменить `enabledTypes` (`null` = все) and/or `customPatterns`                |
| `POST` | `/api/settings/pii/test` | Пробный прогон одного шаблона на выборке не более 8 KB; ничего не сохраняется |

Все три требуют аутентификации управления и проверки тела с помощью Zod (`src/shared/validation/schemas/piiSettings.ts`). При отключенном входе в систему (`requireLogin=false`) `GET` и тестовая конечная точка открыты, но `PUT` по-прежнему требуется сеанс информационной панели, ключ `manage` -scope API, токен доступа `oma_` с областью записи или выше или токен CLI или токен внутренней службы, отправленный из шлейфа.

### Оперативная инъекция (`promptInjection.ts`)

Обнаруживает состязательные структуры в пользовательском контенте и применяет настроенную политику. Поведение определяется переменными среды и опциями конструктора:

| Параметр         | Конверт вар                                                                                              | По умолчанию | Эффект                                                                                                                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                | `true`       | При `false` происходит короткое замыкание ограждения.                                                                                                                                                          |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`       | Политика внедрения: `block`, `warn` или `log`. (`redact` принимается для обратной совместимости, но не** нет** полоска инъекционного текста; запрос на перезапись PII контролируется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | опция `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная степень серьезности, необходимая для блокировки. По умолчанию Medium предназначен только для наблюдения.                                                                                           |

**Приоритет режима** (`getMode`): вызывающий абонент `options.mode` → `INJECTION_GUARD_MODE`** переопределение флага функции DB** (Панель управления → Настройки → Флаги функций) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env → `warn`. Таким образом, переопределение информационной панели побеждает переменные окружения, поэтому флаги функций UI управляют бегущей защитой в реальном времени (без перезапуска). Чтение DB является отказоустойчивым: в случае ошибки защита возвращается к поведению на основе env, а когда переопределение не установлено, поведение идентично разрешению только env.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов, используемый в другом месте конвейера).
2. Встроенный `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и `markdown_system_block`, оба уровня серьезности `high` ).
3. Необязательный `customPatterns` передаваемый через параметры конструктора (строки, регулярные выражения или записи `{ name, pattern, severity }` ).

Когда `mode === "block"`** и** хотя бы одно обнаружение соответствует порогу серьезности, `preCall` возвращает `{ block: true, message: "Request rejected: suspicious content detected" }`. В режимах `warn`/`log` ограждение регистрируется, но разрешает вызов. Общий вспомогательный элемент `evaluatePromptInjection()` также экспортируется для вызывающих абонентов, которым необходимо оценивать запросы без обращения к реестру.

**Привязка сканирования (v3.8.20):** детектор проверяет только** первые 16 KB** объединенного текста подсказки — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в `src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и `evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском цикла шаблонов. Директивы внедрения располагаются в верхней части входных данных, поэтому это ограничивает регулярное выражение CPU/GC для полезных данных размером в несколько сотен КБ без ослабления обнаружения (см. #3932, #4041).

### Маскировщик учетных данных (`credentialMasker.ts`)

Работает** оба** этапы, последние в цепочке по умолчанию (приоритет `95`). Удаляет известные шаблоны API-ключей/секретных токенов из исходящей полезной нагрузки (содержимое сообщения, аргументы вызова инструмента, результаты инструмента).** и** ответ поставщика, поэтому учетные данные, вставленные в приглашение (или возвращенные результатом инструмента), не передаются вышестоящему поставщику или обратно клиенту.

- **Только подписка** , то же соглашение, что и редактирование PII (жесткое правило #20-adjacent): отключено, если только `settings.credentialRedactionEnabled === true`** или** `CREDENTIAL_REDACTION_ENABLED=true`. Если его отключить, ограждение становится неактивным — оно никогда не блокируется и никогда не перезаписывается.
- `redactCredentials()` проходит по всему дереву payload/response (`walkValue()`, прототип-загрязнение, циклобезопасность через `WeakSet`) и заменяет совпадения заполнителем `[REDACTED:<type>]`, клонируя только те ветви, которые действительно изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдера LLM (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replication), токены VCS/SaaS (GitHub, Slack, Linear, Notion, npm, Postman, Discord), платежные ключи (Stripe, Square), облачные ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), приватные ключи / JWTs, строки подключения, несущие учетные данные (`mongodb://user:pass@...` и т. д.), а также общий шаблон значения заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключи в форме заголовков (`authorization`, `x-api-key`, `api-key`, `apikey`) редактируются структурно (только значение, сохраняется префикс схемы, такой как `Bearer `/`Basic ` ), а не с помощью общего текстового регулярного выражения.
- Ограждение никогда не блокируется; он только перезаписывает (`modifiedPayload` / `modifiedResponse`) и аннотирует (`meta.credentialsRedacted`, `meta.count`).

Страж регрессии: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true досрочно прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается из preCall для перезаписи запроса
  modifiedResponse?: TValue; // возвращается из postCall для перезаписи ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, проходящее по цепочке, для последующих guardrail.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны в guardrail.
Прерывание запроса — это намеренное исключение fail-open: медиамосты
прекращают работу и выполняют очистку, не восстанавливая исходные медиаданные
в целевую систему, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет guardrail (или заменяет по нормализованному
  имени) и пересортировывает по возрастанию `priority`.
- `clear()` / `list()` — административные вспомогательные методы.
- `runPreCallHooks(payload, context)` — перебирает активные guardrail,
  пропускает полезную нагрузку через `modifiedPayload` и останавливается на
  первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и при
  необходимости повторно регистрирует guardrail по умолчанию для чистой
  изоляции тестов.

Оба исполнителя возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — массив записей `GuardrailExecutionResult`, включающих поля
`blocked`, `skipped`, `modified`, `error` и `meta` для каждого guardrail, что
полезно для трассировки.

### Отключение guardrail для отдельных запросов

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` собирает
дедуплицированный список имён guardrail, которые следует пропустить для
текущего запроса. Существует пять каналов, читаемых в указанном порядке и
объединяемых в один список (при дедупликации побеждает первое вхождение):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` в теле запроса (верхний уровень)
3. `metadata.disabledGuardrails` в теле запроса (только если `metadata` является объектом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Устаревший заголовок `x-disabled-guardrails`

Все пять каналов объединяются, включая оба заголовка: отправка и
`x-omniroute-disabled-guardrails`, и `x-disabled-guardrails` приводит к пропуску
объединения их списков, а пустой современный заголовок больше не скрывает
устаревший
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), исправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значения могут быть массивами строк или строкой, разделённой запятыми; имена
обрезаются и нормализуются к нижнему регистру kebab-case (`pii_masker` →
`pii-masker`), а пустые элементы отбрасываются. Результат передаётся через
`context.disabledGuardrails` в реестр, который пропускает совпадающие guardrail
(`skipped: true` в `results`).

Список отключения влияет только на **реестр**. Режим `block` для
prompt-injection — обязательная граница: middleware защиты от инъекций
(`src/middleware/promptInjectionGuard.ts`) вызывает `evaluatePromptInjection()`
без какого-либо управляемого вызывающей стороной списка отключения (мёртвый
вызов `resolveDisabledGuardrails({ body })`, который оно раньше выполняло, был
удалён в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), поэтому запрос,
отключающий `prompt-injection`, всё равно отклоняется в режиме `block`. Это
сделано намеренно. Каналы отключения управляются вызывающей стороной (тело
запроса, метаданные, заголовки), и вызывающая сторона не должна иметь
возможности отключить средство защиты, установленное оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Объединение
заголовков из
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) меняет только
то, какие guardrail реестра пропускаются; оно не позволяет клиенту обойти
middleware. Обязательные политики guardrail для каждого ключа и каждой группы
отслеживаются в RFC v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
См. [Покрытие и ограничения](#coverage-and-limits).

## Порядок исполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и `open-sse/handlers/chatCore.ts` (маршруты семейства чатов, перечисленные в разделе [«Покрытие и ограничения](#coverage-and-limits) »):

1. `resolveDisabledGuardrails(...)` создает список пропуска на основе ключа, тела и заголовков API.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускает ограждения в порядке возрастания приоритета:
   - Неработающие ограждения записываются как `skipped`.
   - `preCall` каждого ограждения может перезаписать полезную нагрузку через `modifiedPayload`.
   - Первый `block: true` замыкает цепочку, и обработчик возвращает ответ об отклонении ограждения.
3. Полезная нагрузка (потенциально переписанная) передается в комбинированную маршрутизацию и восходящую диспетчеризацию.
4. **Только без потоковой передачи:** после того, как ответ собран, `guardrailRegistry.runPostCallHooks(...)` запускает ту же цепочку для ответа. Здесь `block: true` удаляет восходящий ответ и возвращает HTTP 400. Потоковые ответы полностью пропускают этот шаг.
5. **Только двусторонний свод:** когда запрос создает токены, `handleChat` восстанавливает их в ответе 2xx, который он возвращает, после перехватчиков пост-вызова и потокового преобразования PII, поэтому `PII_RESPONSE_SANITIZATION` видит токены и сгенерированный моделью PII, а не восстановленный оригинал.

Выбрасывающие ограждения записываются с помощью `error: <message>` и протоколируются через `logger.warn`, но цепочка продолжает работать при отказе — по замыслу.

Только немедленная инъекция.                                                                                                                                                                                                                                                                                               |

### Что не покрывается

- **Медиа, встраивания и маршруты данных** (`/v1/images/*`, `/v1/embeddings`, `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/rerank`, `/v1/search`, `/v1/moderations`) никогда не попадают в реестр. Здесь не работает маскирование PII, маскирование учетных данных или мост модальности. Их единственная проверка — это устаревшее промежуточное программное обеспечение для защиты от инъекций.
- **Потоковые ответы** никаких ограничений после вызова: нет пост-вызова `pii-masker` или `credential-masker`, а также нет блокировки после вызова. Применяется только потоковое преобразование PII (когда `PII_RESPONSE_SANITIZATION` включен). Учетные данные, отраженные в потоковом ответе, не редактируются.
- **Отключить каналы вместо промежуточного программного обеспечения (по дизайну):** промежуточное программное обеспечение оценивает внедрение подсказки с помощью собственного вызова `evaluatePromptInjection()` без передачи какого-либо списка отключения, управляемого вызывающим абонентом. Режим `block` — это обязательная граница, которую невозможно обойти отключением, управляемым вызывающим абонентом, в том числе на семейных маршрутах чата ( [#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413) ). Отключение `prompt-injection` пропускает только ограждение реестра.

### Что видит ответ перед постзвонком

На непотоковом пути порядок следующий: извлечение памяти → выполнение встроенного инструмента → ограждения пост-вызова → блок пост-вызова выход из хранилища семантического кэша →.

- **Извлечение памяти** и** исполнение инструмента** просмотрите ответ до того, как защитные ограждения после вызова смогут его переписать или заблокировать. Начиная с [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), извлечение памяти пропускает извлеченный текст через `sanitizePII` когда `PII_RESPONSE_SANITIZATION` включен (как потоковая, так и непотоковая передача), но ответ, который позже блокируется после вызова, по-прежнему предлагается памяти и инструментам.
- **Семантический кеш** сохраняет ответ после поствызова, поэтому он сохраняет переписанный ответ, а заблокированный ответ никогда не кэшируется. Записи кэша кодируются по ключу API.

## Конфигурация

Переменные среды, считываемые встроенными ограждениями:

| Переменная                            | Используется                    | Эффект                                                                                                         |
| ------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`              | Установите `false`, чтобы полностью отключить обнаружение.                                                     |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`              | Политика внедрения: `warn`, `block` или `log`. Устаревшее значение `redact` не перезаписывает текст внедрения. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`              | Режим защиты от впрыска; также флаг функции DB, который** переопределяет** переменные окружения (DB > ENV).    |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`              | Минимальная серьезность, которую `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.            |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`              | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                    | Когда `true` запрос PII редактируется (независимо от режима внедрения).                                        |
| `PII_REVERSIBLE_VAULT_ENABLED`        | `pii-masker`, `handleChat`      | С помощью `PII_REDACTION_ENABLED` создайте обратимые токены и восстановите их в ответах 2xx.                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нисходящий поток) | Управляет поведением маскера на стороне ответа.                                                                |

Ограждения Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек на базе БД (`getSettings()`), а не из переменных env. Первичные ключи Vision — это `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`. Устаревшие ключи `visionBridge*` принимаются только как документированный резервный вариант чтения за один цикл; При записи на приборную панель используются первичные ключи. Значения по умолчанию и резервный преобразователь находятся в `src/shared/constants/modalityBridgeDefaults.ts`, а устаревшие константы сохраняются в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие настройки `modalityBridgeCache*`. Аудио не имеет резервного варианта устаревших ключей, поскольку эти ключи были представлены в схеме Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` и `modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`. По умолчанию он отключен, поскольку FFmpeg/ffprobe являются необязательными эксплуатационными зависимостями, а субтитры кадров увеличивают задержку и стоимость модели.

## Пользовательские guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1. Создайте `src/lib/guardrails/myGuardrail.ts`, расширив `BaseGuardrail`.
2. Реализуйте `preCall` и/или `postCall`.
3. Либо зарегистрируйте guardrail во время импорта (добавьте вызов в `registerDefaultGuardrails`), либо вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет любой ранее зарегистрированный guardrail с тем же нормализованным именем.
4. Добавьте тесты в `tests/unit/` (существующие примеры:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,

## Покрытие маршрутов injection-guard и red-team (Фаза 8 · Блок D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) покрывает все маршруты,
принимающие пользовательские промпты. Он учитывает `INJECTION_GUARD_MODE` (по умолчанию
`warn` = только логирование; `block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                      | Маршруты                                                                                                                                             | Режим по умолчанию |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Текстовые (существующие) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративные             | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные                   | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут
блокирует корпус OWASP-LLM при `INJECTION_GUARD_MODE=block`; garak запускает пробы
(пропускается при отсутствии секрета). `moderations` включён для согласованности.
Режим block — это обязательная граница: `evaluatePromptInjection()` игнорирует
передаваемый middleware список отключений на уровне запроса, поэтому `disabledGuardrails`
**не** освобождает маршрут от этой проверки ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Ночной workflow (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) содержит два задания:

- **`promptfoo-guard` (блокирующее)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, «ignore all
  previous instructions…», джейлбрейки в стиле DAN) проверяет, что ответ содержит
  `error.code === "SECURITY_001"`, т.е. что guard действительно отклонил запрос.
- **`garak` (рекомендательное)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Зависит от
  секрета провайдера (`PROMPTFOO_PROVIDER_KEY`); при его отсутствии пропускается без
  ошибок и дополнен суффиксом `|| true`, поэтому отчитывается, не ломая CI.

Покрытие хелпера guard (`createInjectionGuard` / `withInjectionGuard`)
распространяется на каждый маршрут `/v1`, принимающий промпты; текст промпта
извлекается из `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
функцией `extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
