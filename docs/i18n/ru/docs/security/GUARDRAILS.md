> какие маршруты и пути ответов охватываются хуками, объединённые заголовки отключения (#16412),
> режим блокировки инъекций как обязательная граница (#16413) и кто видит ответ до post-call)

Guardrails обеспечивают безопасность, соблюдение политик и преобразование
контента на границе между OmniRoute и вышестоящими провайдерами. Каждый
guardrail может проверять (и при необходимости отклонять, преобразовывать
или дополнять аннотациями) полезную нагрузку запросов (`preCall`) и ответы
вышестоящих провайдеров (`postCall`).

Система работает по принципу **fail-open**: если guardrail выбрасывает
исключение во время выполнения, реестр фиксирует ошибку и переходит к
следующему guardrail, не прерывая запрос. Блокировка — это всегда явное
решение (`block: true`), а не случайность. Единственное исключение —
прерванный запрос: когда `signal` вызывающей стороны прерывается,
выбросивший исключение guardrail отклоняет выполнение хука, а не
пропускается.

Хуки выполняются **не** на каждом маршруте и не для каждого ответа.
Прочитайте [Покрытие и ограничения](#coverage-and-limits), прежде чем
полагаться на guardrail как на средство защиты.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Базовая модель GLM 5.3 и варианты `glm-5.3-{low,high,max}` имеют явные
метаданные `supportsVision:false` в реестре/спецификации. Варианты GLM 5.3
Flash остаются моделями с нативной поддержкой зрения. Маршрут
`/v1/messages` из Claude Code входит в общую цепочку pre-call guardrails
`handleChat` **до** преобразования Claude→OpenAI; вложенные изображения из
результатов инструмента `Read` должны быть описаны или обработаны до того,
как это преобразование перенесёт их в контент OpenAI `image_url` (#17069).

Перехватывает запросы, содержащие изображения и адресованные **моделям без
поддержки зрения**, и либо перенаправляет весь запрос на модель с
поддержкой зрения, либо заменяет части с изображениями текстовыми
описаниями, сгенерированными настраиваемой vision-моделью, до вызова
вышестоящего провайдера. Это позволяет текстовым провайдерам прозрачно
обрабатывать мультимодальную полезную нагрузку.

Алгоритм работы:

1. Пропустить, если целевая модель уже поддерживает зрение (если только
   она не входит в список принудительного моста
   `isVisionBridgeForcedModel`).
2. Извлечь части с изображениями через `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), который делегирует работу **унифицированному
   детектору медиа** `detectMediaParts()` в `open-sse/utils/mediaParts.ts` —
   единому источнику истины, совместно используемому с фильтром
   совместимости комбо. Извлечение ограничено списком разрешённых форм,
   которые `replaceImageParts` может вставить обратно (контракт
   «извлечение↔замена»): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"` и Responses
   API `input_image`. Совпадающие изображения, вложенные в
   `tool_result.content` Claude Code и в выводы инструментов Responses,
   также извлекаются и заменяются по своим исходным путям; формы, служащие
   только индикаторами, относятся к материалу фильтра комбо и не
   извлекаются. Пропустить, если ничего не найдено.
3. Получить рабочую конфигурацию через
   `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): приоритет отдаётся
   новым ключам настроек `modalityBridge*`; устаревшие ключи `visionBridge*`
   остаются **резервным вариантом на один цикл** (окно отката). Пропустить
   до любого обхода медиа, если мост отключён.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже)
   определяет: перенаправление или описание. Перенаправление возвращает
   `modifiedPayload` только с подменённым `model`, плюс метаданные
   `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений значением `maxImages`,
   составить промпт с учётом задачи, проверить кеш описаний, вызвать
   vision-модель **параллельно** (`Promise.allSettled`) и вставить на место
   изображений текстовые части `[Image N]: <description>`. Неудачное
   описание возвращает `null`: исходное изображение сохраняется для
   неизвестных целей и целей с поддержкой зрения (#4012), но
   **подтверждённая текстовая прямая цель** или комбо без vision-моделей
   получает явную текстовую заглушку
   `(unavailable — no vision-capable provider connected)` для каждого
   неописанного изображения, включая частичные сбои и изображения сверх
   лимита вызовов описания (#17069). Существующий запасной вариант для
   комбо на случай провала всех описаний остаётся в силе (#8430).
6. Вернуть `modifiedPayload` + метаданные (`imagesProcessed`,
   `descriptions`, `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                               |
| ---------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Устаревшая эвристика, без изменений (#6640/#7204): некомбо/`auto/` модели перенаправляются на лучшую vision-модель, если у исходной модели ещё нет пригодных учётных данных (тогда describe); комбо-цели всегда describe.                                                                                                               |
| `describe` |              | Всегда describe — блок перенаправления полностью пропускается; отвечает всегда выбранная пользователем модель.                                                                                                                                                                                                                          |
| `reroute`  |              | Принудительное перенаправление: защита «сохранить модель с учётными данными» обходится. Защита учётных данных **целевой** модели перенаправления по-прежнему действует — когда нет подходящей vision-цели, мост блокирует запрос с понятной ошибкой, а не выполняет describe и не отправляет необработанные изображения текстовой цели. |

Принудительные режимы срабатывают **до** запуска auto-эвристики; поведение `auto`
побайтово идентично защите до PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающей стороны ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает только
те модели перенаправления и describe, которые разрешено использовать ключу, и
только на подключениях, разрешённых для ключа. Вызов describe затем всегда
проходит через self-loop OmniRoute с заголовком `x-omniroute-self-loop-key-id`,
поэтому принимающий chat-запрос снова применяет политику подключений и моделей
этого ключа. `enforceApiKeyPolicy()` учитывает этот заголовок только вместе с
self-loop bearer, поэтому он может лишь сужать доступ, а id, который не удаётся
разрешить, отклоняется.

Если для ключа не разрешена ни одна vision-модель, **подтверждённая текстовая
цель** отклоняет запрос с изображением локально с понятным HTTP 400 вместо
пересылки байтов изображения несовместимому апстриму (#17069). Для целей с
неизвестной или встроенной поддержкой vision путь describe сохраняет прежнее
fail-open поведение (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений ведут себя точно так же, как раньше.

#### Учитывающий задачу промпт describe (`modalityBridgeVisionTaskAware`)

По умолчанию **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовому
промпту describe, направляя описание на то, что пользователь действительно спросил
(паттерн codex-vision-proxy), и просит vision-модель транскрибировать видимый
текст. При выключенном флаге — или при отсутствии пользовательского текста —
используется базовый промпт без изменений.

Собственный OpenAI-совместимый запрос describe self-loop (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` —
безусловно, для любого вызывающего/провайдера, независимо от каких-либо
клиентских сигналов. Низкодетализированная выборка снижает точность OCR именно
для задачи транскрибирования текста, которую этот промпт запрашивает, поэтому
сам вызов describe всегда запрашивает высокую детализацию независимо от того,
какой уровень детализации использовал исходный входящий запрос. Это влияет
только на тело внутреннего запроса describe; это не меняет то, как OmniRoute
пересылает собственный `image_url.detail` вызывающей стороны в основном запросе —
это значение по умолчанию применяется отдельно и только для обнаруженных
клиентов OpenCode, в `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`).
Ветвь describe self-loop в формате Anthropic не имеет поля `detail` и не
затрагивается ни одним из этих значений по умолчанию.

#### Ограничение вывода describe (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **без ограничения** — описание, возвращённое
`callVisionModel()`, передаётся без изменений, сохраняя существующее поведение.
Любое значение в диапазоне 100–50000 обрезает описание с суффиксом `…` перед
тем, как оно вставляется обратно как `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличьте это значение для задач OCR с высокой детализацией, где нижестоящей
модели нужна полная транскрипция; уменьшите его, чтобы ограничить потребление
токенов на многословных vision-моделях. Поле в дашборде находится на панели
Advanced вкладки Vision (`modality-bridge-max-chars` в
`ModalityBridgeVisionTab.tsx`) и подтягивает любое значение от 1 до 99 до
нижней границы 100, оставляя явный `0` без изменений — `0` является
самостоятельным допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию «не задано».

#### Кэш describe (`modalityBridge/bridgeCache.ts`)

Внутрипроцессный LRU + TTL кэш для выводов describe, общий для всего процесса.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
length-prefix framing (без коллизий на границах полей). Компонент модели — это
**настроенная** модель моста, а не модель, которая фактически ответила —
`callVisionModel` может выполнять внутренний fallback, а ключ по попыткам
фрагментировал бы кэш. Неудачные describe никогда не кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удалённых изображений (self-loop describe/загрузка base64)

Когда мост сам загружает **удалённое** изображение — self-вызов describe Anthropic и конвертация base64 в формате claude-wire (`ensureBase64ImagesForClaudeWire`), оба через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — результирующий data URI пропускается через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед встраиванием в запрос к vision-модели. Слишком большие изображения уменьшаются до **2048px по длинной стороне** (что совпадает с пределом ресайза, который OpenAI/Anthropic уже применяют на стороне сервера); это сокращает объём передаваемых байтов и задержку, не меняя того, что видит vision-модель. Ресайз выполняется через `sharp`, загружаемый динамическим import: на платформе, где его нативный бинарный файл не удаётся загрузить, `normalizeDataUri()` **никогда не выбрасывает исключение** — выполняется откат к сквозной передаче исходных байтов, поэтому путь describe/конвертации в base64 продолжает работать в любом случае. Байты, не являющиеся изображением (загрузка, не вернувшая декодируемое изображение), также пропускаются без изменений. Эта нормализация применяется только к изображениям, которые мост загружает для собственного self-вызова, — она никогда не применяется к «сырому» сквозному payload вызывающей стороны, в соответствии с принципом изменения только по явному согласию (жёсткое правило №20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` валидируются через Zod в `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, тройка `modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая Audio Bridge. Миграция `141_modality_bridge_settings.sql` копирует существующие устаревшие значения `visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не перезаписывает установленное оператором значение `modalityBridge*`); устаревшие ключи продолжают приниматься как фолбэк для чтения в течение одного релизного цикла.

#### Заголовок прозрачности + статистика

Ответы, преобразованные через describe, содержат заголовок `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (формируется `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`, проставляется `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`). Перенаправленные запросы **не** получают заголовка — payload оставался нетронутым, а замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (аутентификация уровня управления, тот же уровень, что у `GET /api/settings`) возвращает хранящиеся в памяти счётчики по модальностям `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и `video`. `averageLatencyMs` использует в качестве знаменателя `latencySamples`, а не все попытки; операция без замера времени не порождает фиктивный сэмпл с нулевой длительностью. `bridged` остаётся обратно-совместимым алиасом для успешных конвертаций; неудачные попытки его не увеличивают. Счётчики сбрасываются при перезапуске процесса — так задумано (это телеметрия, а не учёт).

#### Конфигурация дашборда

Отдельная страница дашборда — `/dashboard/settings/modality-bridge`. Её адресуемые через URL вкладки `Vision`, `Audio` и `Video` сохраняют query-параметры при переключении значения `tab`. Вкладка Vision предоставляет: включение, режим, выбор модели (включая автоматическое значение по умолчанию), промптинг с учётом задачи, расширенные лимиты таймаута/изображений/длины описания/кэша, счётчики времени выполнения и защищённый пример запроса. Вкладка Audio также доступна: она предоставляет включение, выбор модели (только STT) с вариантом Auto, лимиты таймаута/максимальной длительности клипа, счётчики аудио и тестовый пример `input_audio`. Вкладка Video функциональна: она отображает состояние рантайма FFmpeg/ffprobe — одно из четырёх явных состояний UI (`unknown`, пока проверка выполняется или не смогла завершиться; `restricted` на хосте дашборда не на loopback, где проверка пропускается на стороне клиента; `unavailable`, когда проверка выполнена и отсутствие подтверждено; или `available` с версиями FFmpeg/ffprobe) — сохраняет лимиты включения/модели/кадров/видео/таймаута, фильтрует список моделей до поддерживающих vision и отображает счётчики видео.

Прежняя карточка Vision Bridge в настройках ИИ теперь является ссылкой совместимости на новую страницу; она больше не содержит собственной второй копии формы. Раздел Media Providers также связывает рабочие процессы Image-to-Text и Speech-to-Text с соответствующими вкладками Modality Bridge, не удаляя существующую песочницу Speech-to-Text.

**Обход контроля допуска для self-loop:** когда вызов describe маршрутизируется через собственный self-loop `/v1` OmniRoute (нестандартная модель провайдера), подзапрос отправляет `x-omniroute-admission-bypass: internal` и аутентифицируется с разрешёнными учётными данными self-loop — локальным значением-маркером `sk_omniroute` в локальном режиме либо настроенным оператором ключом окружения `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), так что развёртывания с `REQUIRE_API_KEY=true` по-прежнему могут выполнять вызов describe. Обход признаётся только для этих конкретных учётных данных, поэтому внешние клиенты не могут использовать заголовок, чтобы обойти контроль допуска.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для режима/task-aware/кэша и резолвер настроек находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Guardrail предоставляет опцию конструктора `deps`, позволяющую тестам внедрять поддельные реализации `getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает chat-запросы, содержащие аудио, до того, как они достигнут цели, для которой не подтверждена поддержка аудиовхода. Он никогда не перенаправляет chat-запрос: аудиочасти транскрибируются через существующий OpenAI-совместимый multipart-эндпоинт, а выбранная chat-модель продолжает работу уже с текстовыми транскриптами.

Поток:

1. Определение `supportsAudio` выполняется через `getResolvedModelCapabilities()`. Приоритет имеют явные метаданные реестра провайдеров, затем статические метаданные модели, затем синхронизированные `modalities_input`. Объявленный список входных типов без `audio` даёт `false`; при отсутствии сведений о возможностях остаётся `null`. И `false`, и `null` активируют консервативный мост, тогда как `true` обходит его.
2. Определяются настройки `modalityBridgeAudio*` и из каждого сообщения извлекаются заменяемые аудиочасти верхнего уровня через общий детектор `detectMediaParts()`. Поддерживаемые сетевые форматы — OpenAI `input_audio`, `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио обнаруживается для маршрутизации, но не удаляется на пути замены. Объём работы ограничен `modalityBridgeAudioMaxClips`; последующие части остаются нетронутыми.
3. Используется настроенный `provider/model`, либо `selectAudioBridgeModel()` обходит `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбирает первую модель с пригодными активными учётными данными провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data-URI в multipart-`file` либо загружает удалённый `audio_url` через исходящий фильтр, разрешающий только публичные адреса, с фиксацией DNS и ограничением в 25 МБ. Затем файл и выбранная модель отправляются методом POST в локальный самовызов `/v1/audio/transcriptions` с аутентификацией через `resolveSelfLoopBearer()`. Существующий маршрут транскрипции выполняет обычный поиск учётных данных, обработку периодов охлаждения и ограничений частоты, а также диспетчеризацию провайдеров.
5. Успешные вызовы заменяют свои части на `[Audio N]: <transcript>`. Вызовы выполняются с `Promise.allSettled`: отдельный сбой сохраняет исходную аудиочасть (контракт #4012). Если все вызовы завершились неудачей и цель подтверждённо имеет `supportsAudio === false`, части заменяются на `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для неизвестной цели (`null`) результат полной неудачи остаётся нетронутым. Подтверждённая текстовая цель без пригодных учётных данных STT получает ту же явную заглушку без выполнения сетевого вызова.

Успешные транскрипты используют LRU/TTL-кеш Modality Bridge уровня процесса. Ключ объединяет ссылку на аудио, стабильную метку операции `audio-transcription` и выбранную STT-модель; сбои никогда не кешируются. Попытки обработки аудио обновляют общие счётчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`. Преобразованные ответы содержат `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; нетронутые запросы не получают сегмент Audio Bridge.

Настройки времени выполнения хранятся в базе данных и валидируются Zod:

| Ключ                          | По умолчанию | Диапазон                   |
| ----------------------------- | ------------ | -------------------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —                          |
| `modalityBridgeAudioModel`    | `""`         | Авто или идентификатор STT |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000                |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10                       |

Общий кеш по-прежнему управляется параметрами `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает видеочасти верхнего уровня в `messages` Chat Completions и `input` Responses API до вызова целевой модели без известной нативной поддержки видео. Поддерживаемые формы — `input_video`, `video_url`, `video_source`, HTTPS-URL и data-URI вида `data:video/*;base64,...`. Обычные имена файлов в тексте видео не считаются.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса, проверку возможностей и политики, агрегацию в рамках запроса и полезную нагрузку ответа. Работа над каждым видео — получение байтов, кеш полного результата, описание последовательности кадров (объединяющее любую объявленную вызывающей стороной аудиотранскрипцию), а также метрики, прерывание и очистка для каждой попытки — скрыта за `processVideoPart` в `videoBridgePipeline.ts`, вызываемой один раз для каждой видеочасти внутри цикла `preCall`. Этот модуль также определяет явные границы портов: `VideoMediaBrokerPort` (получение байтов и извлечение сэмплированных кадров), `VideoAudioTranscriptionPort` (объединение объявленной вызывающей стороной аудиотранскрипции с подписями к сэмплированным кадрам) и `VideoDrilldownPort` (граница персистентности детализации кадров; пока не подключена к `processVideoPart` — сегодня записи детализации создаёт только отдельный маршрут `/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не запускает подпроцесс. Удалённые видео загружаются с ограничением 50 МиБ; встроенные base64-видео имеют консервативный предел 36 МиБ в декодированном виде на одно видео, чтобы конверт из модели, сообщений и обрамления оставался в пределах публичного лимита приёма JSON-запросов 50 МиБ. Оценки встроенной длины и декодированного размера проверяются до выделения памяти. HTTPS обязателен для исходного удалённого URL и каждого перенаправления; используется существующий исходящий фильтр, разрешающий только публичные адреса, с фиксацией DNS. Затем байты пересекают строгую внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут одновременно `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только аутентифицированные запросы с доверенного loopback-интерфейса в рамках процесса и никогда не принимает URL, путь в файловой системе, исполняемый файл или список аргументов. Конвейер ограничения размера тела API и инкрементальный считыватель тела обработчика независимо друг от друга обеспечивают предел входных данных брокера в 50 МиБ. Его ограниченная очередь выполняет по одной распаковке за раз, допускает четыре ожидающих задания и ограничивает объём ожидающих входных данных 100 МиБ.

Внутри брокера `ffprobe` читает приватный локальный файл; фиксированный список разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых контейнеров семейства MOV внешние ссылки на данные MOV остаются отключёнными по умолчанию, и фиксированная команда не включает их. И `ffprobe`, и `ffmpeg` используют белый список протоколов, допускающий только `file`, один поток, фиксированные массивы аргументов, без оболочки, а исполняемые файлы разрешаются из `PATH`. Потоки обложек (attached picture) не являются кандидатами на воспроизведение. Все воспроизводимые потоки должны соответствовать ограничениям, а явно заданный поток по умолчанию предпочтительнее детерминированного отката к потоку с наименьшим индексом. Видео ограничены 600 секундами, 8 192 пикселями по каждому измерению и 33 554 432 исходными пикселями. FFmpeg извлекает 1–16 срединных кадров JPEG, уменьшает длинную сторону не более чем до 1 024 пикселей, не увеличивая меньшие исходники, и никогда не получает URL. По умолчанию используется выборка `uniform`. Необязательная политика `scene_aware` и экспериментальная `segment_aware` выполняют один дополнительный фиксированный проход FFmpeg по уже проверенному локальному потоку, выбирают ограниченные временные метки сцен из `showinfo` и детерминированно возвращаются к тем же равномерным срединным точкам при сбое детектора, тайм-ауте, некорректном выводе или пустом наборе кандидатов. Режим segment-aware распределяет срединные выборки пропорционально проверенным интервалам сцен; свидетельства segment-aware и поведение при откате подробно описаны ниже. Жёсткое ограничение в 16 кадров применяется после выбора в каждой политике. Когда у scene-aware-запроса бюджет всего в один кадр, используется равномерная срединная точка активного окна полного видео или фокусного окна и сообщается `policyEffective: uniform`: единственный выбранный кадр сцены не может сохранить оба временных края. Вызывающая сторона может дополнительно указать конечное фокусное окно (секунды `start`/`end`); границы обрезаются по длительности медиа, перевёрнутые или неконечные окна отклоняются, а все политики выборки выполняются только внутри нормализованного интервала. Результирующее окно включается в метаданные выборки и в префикс недоверенного описания, чтобы последующие модели могли отличить сфокусированный фрагмент от полной временной шкалы.

Семантический фокус описания — это отдельная, явная настройка. Режим анализа `full` по умолчанию сохраняет существующий промпт для кадров и никогда не передаёт текст запроса модели описания. В режиме `focused` мост читает только последнее непустое пользовательское `text`/`input_text` из того же контейнера Chat или Responses, нормализует его в NFC, схлопывает управляющие символы и пробелы и ограничивает результат 500 кодовыми точками Юникода. Пустой результат приводит к откату к точному промпту `full`. Пригодная подсказка сериализуется как JSON в выделенном блоке недоверенного пользовательского контекста и может лишь приоритизировать наблюдаемые детали; она не может отменить отдельное предупреждение о запрете следовать инструкциям, видимым или слышимым в медиа. Текстовый фокус никогда не выводит `start`/`end` и не изменяет временной сэмплер.

#### FU-07: структурные свидетельства сегментов

`segment_aware` использует один ограниченный проход предварительного анализа по уже проверенному локальному видеопотоку. Фиксированная цепочка фильтров сначала масштабирует до ширины не более 320 пикселей, обнаруживает смены сцен и замороженные интервалы, затем выполняет выборку с частотой 1 кадр в секунду для оценки размытости, средней яркости и пространственной/временной информации. Проход ограничен 600 структурными выборками, одним потоком FFmpeg/фильтров, теми же списками разрешённых протоколов (только `file`) и контейнеров, пределом вывода процесса в 1 МиБ и не более чем 30 секундами внутри общего механизма отмены/дедлайна брокера. Он никогда не принимает команду, фильтр, путь или URL из запроса.

Структурные значения — это детерминированные свидетельства для выборки, а не семантическое понимание видео. Они не выводят субъекты, действия, подписи, речь или намерения пользователя. Границы сцен и заморозок образуют сегменты; покрытие заморозками, размытость, экспозиция, пространственная детализация и временные изменения влияют только на то, как распределяется существующий бюджет в 1–16 кадров. Полностью замороженный сегмент ограничивается одним кадром, а незамороженные сегменты конкурируют за оставшийся бюджет. Когда границ больше, чем кадров, сохраняется равномерное покрытие временной шкалы, чтобы быстрые ранние склейки не могли скрыть длинный завершающий сегмент. Границы сцен, находящиеся в пределах 1-секундного разрешения анализа от границы заморозки, объединяются.

Отсутствующие фильтры, некорректные/пустые свидетельства, ошибка детектора или тайм-аут ограниченного предварительного анализа приводят к откату в режиме fail-open к точной политике равномерных срединных точек. Отмена вызывающей стороной или дедлайн брокера не приводит к fail-open: выполняющийся подпроцесс завершается, последующее извлечение кадров предотвращается, а приватное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерирует детерминированные реальные фикстуры FFmpeg для экономии вызовов модели описания после дедупликации, распределения бюджета при плотном движении, свидетельств размытости/экспозиции/SI-TI, быстрых склеек с длинным хвостом и ложноположительных срабатываний на плавных затуханиях. Он записывает астрономическое время предварительного анализа и, если доступен `/usr/bin/time`, время CPU дочернего процесса и пиковый RSS. Его проверки качества — это только структурные оракулы. Реальное качество модели описания остаётся в статусе `HOLD`, поскольку у этого стенда нет авторизованной конечной точки или замороженного судьи. Денежная экономия также остаётся в статусе `HOLD`, если только `--caption-cost-per-call-usd` не задаёт явную положительную оценку стоимости одного вызова; скрипт никогда не выдумывает ни один из этих результатов.

Размер каждого кадра ограничен 4 МиБ, всех необработанных кадров вместе — 23 МиБ, а сериализованного ответа брокера — 32 МиБ. Приватный временный каталог удаляется в `finally`. OmniRoute не поставляется в комплекте с FFmpeg и не принимает пользовательский путь к исполняемому файлу. Перед созданием подписей мост выполняет консервативный проход визуальной дедупликации: каждый JPEG уменьшается до буфера в градациях серого 16×16 и сравнивается только с последним сохранённым кадром. При запрошенном бюджете подписей больше одного кадра извлечение предоставляет ограниченный пул кандидатов объёмом до удвоенного бюджета, но никогда не более 16 кадров. Запрошенный предел применяется только после дедупликации, при этом первый и последний выбранные кандидаты сохраняются при финальном прореживании, если бюджет составляет не менее двух. Версионированная политика `grayscale-16x16-mean-cells-v2` использует большее из двух значений: среднюю дельту яркости и долю ячеек миниатюры, чья нормализованная дельта составляет не менее 0.05. Порог дубликата — константа 0.04, выбранная ради предсказуемости, а не вынесенная в настройку времени выполнения. Этот вторичный высококонтрастный сигнал сохраняет мелкие движения и изменения видимого текста, которые может скрыть сравнение только по среднему. Ошибки компаратора или декодера обрабатываются по принципу открытого отказа (fail open) и сохраняют покрытие. Выходные метаданные разделяют извлечённых кандидатов, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно помеченная видеочасть может запросить контактный лист с временными метками. Мост строит JPEG-сетку максимум из 4 столбцов и 16 кадров. В каждой 512-пиксельной ячейке исходная временная метка выжигается в высококонтрастную нижнюю полосу, при этом те же временные метки остаются в текстовых метаданных для последующей привязки и аудита. Полный JPEG по-прежнему ограничен 32 МиБ. Если `sharp` не может декодировать или составить сетку, мост возвращается к отдельным JPEG-кадрам; прерывание со стороны клиента по-прежнему распространяется через операцию создания листа.

Доказательства продвижения намеренно отделены от синтетического микробенчмарка композиции. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет A/B-стенд с версионированной схемой для реальных OpenAI-совместимых визуальных моделей. Он измеряет токены, сообщаемые провайдером, сквозную задержку по реальному времени (включая композицию листа), количество вызовов модели и удержание фактов, определённых манифестом. Сырые ответы модели не записываются в отчёт; сохраняются только SHA-256-дайджесты и идентификаторы совпавших фактов. Стенд не выполняет сетевых или платных вызовов модели, если не передан флаг `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без такого явного реального запуска его машиночитаемый вердикт остаётся `HOLD`; сами по себе синтетические измерения полезной нагрузки/количества вызовов не являются доказательствами продвижения.

Вызывающие стороны могут прикрепить необязательный массив `transcript.cues` к поддерживаемой видеочасти, если у них уже есть выровненный текст. Каждая реплика должна содержать `text`, конечный интервал `start`/`end` в пределах длительности, определённой при зондировании, и `source` из белого списка (`client`, `embedded` или `audio-bridge`); `confidence` по умолчанию равна `1` и должна оставаться между `0` и `1`. Точные дубликаты реплик сворачиваются. OmniRoute никогда не запускает транскрипцию на основе этих метаданных: проверенные реплики копируются в описанный результат вместе с источником, уверенностью и интервалом и отображаются как недоверенные наблюдения наряду с подписями кадров. Недействительный, выходящий за пределы диапазона или лишённый происхождения текст отклоняется, а не смешивается с потоком подписей. Оба канала транскриптов тела запроса нормализуют предоставленное происхождение к `client`, включая заявленные самим клиентом метки `embedded` или `audio-bridge`. Только принадлежащий серверу адаптер может присваивать эти доверенные метки через доступный только из кода аргумент `trustedSource`; поле JSON в запросе не может добраться до этого аргумента. Текст транскрипта остаётся недоверенным содержимым, полученным из медиа, независимо от его происхождения, и никогда не должен определять авторизацию.

Продвинутая вызывающая сторона может предоставить дорожку `audioTranscript` для того же видео; она рассматривается как предоставленный клиентом текст, а не как доказательство серверной транскрипции. Шов слияния выполняет визуальные и аудионаблюдения в рамках одного дедлайна и сигнала прерывания, упорядочивает их на общей временной шкале, сворачивает точные дубликаты и сообщает частичный результат, когда успешна только одна сторона. Недействительный `audioTranscript` деградирует до этого частичного результата — визуальное описание сохраняется, а аудиоветвь записывает очищенный код сбоя — вместо сбоя всего видео. Доступность по ветвям, флаг частичности и очищенные коды сбоев сохраняются в описанном результате, в метаданных ограждений (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), в метаданных кэша результатов и в счётчиках слияния моста. Путь Video Bridge по умолчанию не вызывает преобразование речи в текст и не загружает вторую копию медиа; без этой явной дорожки он работает только с видео.

**Хранение транскриптов (#12150 P1).** Это применяется автоматически всякий раз, когда
Video Bridge (который сам требует явного включения) отображает реплику транскрипта — отдельного
флага хранения нет. Когда запрос отображает любую реплику транскрипта (объявленный вызывающей стороной
`transcript` или объединённый `audioTranscript`), защитный механизм помечает его как
`videoBridgeObserved` и создаёт редактированную теневую копию описания видео —
идентичное представление, в котором текстовое содержимое каждой реплики заменяется на
`[redacted-video-transcript]`; копия создаётся путём подстановки в структурированное поле реплики
до сборки строки (а не путём анализа сведённого текста, поэтому никакое содержимое
реплики — ни вредоносное, ни обычное, включая текст с символом `]`, например
`[inaudible]`/`[music]`, — сохраниться не может). В сохраняемом теле запроса журнала вызовов
каждая текстовая часть, полученная из видео, заменяется этой редактированной теневой копией,
сопоставленной по равенству содержимого; опорное значение `fullText` повторно считывается из готовой
полезной нагрузки защитного механизма перед вызовом, поэтому сопоставление продолжает работать после того,
как последующие защитные механизмы цепочки (маскировщики персональных данных и
учётных данных с приоритетами 10/95) изменяют текст описания на месте, а также
после того, как внедрение системной инструкции, передачи контекста и памяти изменяет массив сообщений.
Тело, отправляемое модели, остаётся неизменным. Наблюдаемый запрос также не создаёт
долговременных данных в Memory (извлечение как из запроса, так и из ответа пропускается),
поэтому собственный ответ модели не может скопировать текст транскрипта в Memory.

**Необработанные поля видео (#12430).** Когда мост включён, а встроенная поддержка видео неизвестна или отсутствует, заданные поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved`, даже после сбоя создания описания или достижения ограничения `maxVideos`. Значения `null` и пустые строки учитываются; отсутствующие поля и метаданные, не относящиеся к видео, — нет. В сохраняемых копиях эти поля редактируются либо запрос полностью опускается, а кеши и Memory обходятся.

На этих резервных путях допустимые реплики, предоставленные вызывающей стороной, становятся поддерживаемыми частями `text`/`input_text`,
а не нестандартными полями провайдера. Обе предоставленные в запросе дорожки
остаются недоверенными наблюдениями `client` с явным предупреждением о том, что видео
не было описано, а временные метки не были сверены с медиаданными. Существующие
общие ограничения в 256 реплик/64 КиБ и ограничения на одну реплику применяются к обеим дорожкам вместе;
временные метки должны укладываться в установленный брокером предел в 600 секунд и в любое указанное
окно фокусировки. Недопустимые дорожки отбрасываются, а не пересылаются как произвольный текст; допустимая
соседняя дорожка всё ещё может использоваться, если их общий бюджет не превышен. Поля со значениями null или пустыми
строками не добавляют текста. Этот резервный механизм не добавляет получение медиаданных или транскрибирование.
Поля расширения транскрипта удаляются из резервного контейнера видео и его
объектов `video_url`/`source`. Список разрешённых полей сетевого формата OpenAI остаётся строгим; контейнеры видео
с неизвестной встроенной поддержкой остаются доступными, а известные цели, поддерживающие только текст, сохраняют безопасные маркеры.
Структурированные редактированные теневые копии защищают добавленный текст транскрипта, тогда как
исходный запрос, принадлежащий вызывающей стороне, остаётся неизменным. Цели со встроенной поддержкой и
отключённые мосты сохраняют существующее поведение обхода.

Дополнительные сохраняемые копии используют тот же сигнал наблюдаемого запроса. В необработанном
снимке клиентского запроса до применения защитных механизмов, ожидающем запросе в памяти и журнале
рано отклонённых запросов поля транскрипта в частях видео заменяются структурно;
строковые инструкции, сформированные этапами конвейера и при передаче контекста, редактируются
в точке сохранения тела запроса. Сохранённый маркер `video_content_removed`
заставляет продолжение через `previous_response_id` безопасно завершаться ошибкой, а не восстанавливать
текст, который был намеренно удалён. Если наблюдаемый запрос теряет свою
теневую копию для редактирования отдельных частей до журналирования или хотя бы одна из нескольких теневых копий видео
не совпадает после последующих изменений запроса, сохраняемое тело запроса
полностью опускается вместо сохранения частично отредактированного транскрипта.

Для наблюдаемого запроса ответ модели может цитировать любую часть
транскрипта без структурированной границы реплики. Поэтому сохраняемое в журнале вызовов
`responseBody` заменяется маркером пропуска; подробный
артефакт конвейера (который может включать тела запросов и ответов вышестоящего сервиса и клиента, а также фрагменты потока)
не сохраняется. Для этого запроса семантический кеш, кеш идемпотентности и кеш воспроизведения рассуждений
обходятся как при чтении, так и при записи. Запрос к провайдеру и видимый клиенту
ответ остаются неизменными. Ранние байты поддержания соединения удаляются из временного
буфера, когда подробный артефакт опускается. Предупреждение Kiro о некорректном EventStream
сообщает только размер полезной нагрузки в байтах, но никогда не включает её содержимое или необработанную ошибку
JSON-парсера.
Это не означает, что была проведена проверка всех несвязанных диагностических сообщений провайдеров и плагинов;
более широкий аудит мест сохранения отслеживается в #11658.

Жизненный цикл внутреннего `/api/modality-bridge/video/drilldown` представляет собой отдельную
кеширующую подсистему с доступом через loopback и аутентификацией по токену. Каждая операция также требует
канонического непрозрачного идентификатора принципала. Прежде чем включать рабочую вызывающую сторону, она должна
получать этот идентификатор из аутентифицированного арендатора и никогда не передавать
значение, выбранное клиентом. Ключи кеша связывают этого принципала с каноническими идентификаторами сеанса и
ссылки на видео, хранят только полученные из них ключи SHA-256 и ограничивают как чтение,
так и удаление одним и тем же принципалом. Кеш хранит не более 16 производных кадров JPEG
на запись, удаляет их через десять минут и поддерживает ограниченное чтение по
`start`/`end` либо явное удаление сеанса.

Для каждого принципала установлено ограничение в 16 записей и 64 МиБ канонических данных JPEG. Эти
ограничения не зависят от глобального предела в 64 записи/256 МиБ: при исчерпании квоты
принципала сначала вытесняются только наименее недавно использованные записи этого принципала, и лишь затем
рассматривается глобальное вытеснение по LRU. Истёкшие записи удаляются как из учёта принципала, так и из
глобального учёта при операциях с кешем, тогда как отмена и ошибка проверки не
фиксируют частичную замену.

Кэш отклоняет неканонический Base64, избыточный паддинг, не-JPEG-медиа, повреждённые или усечённые JPEG-файлы, а также JPEG-файлы, выдающие предупреждение при ограниченном декодировании полного изображения с помощью `sharp`. Он перекодирует каждое принятое изображение в канонический JPEG, выводит ширину и высоту из декодированных байтов вместо доверия полям вызывающей стороны и отбрасывает любые завершающие байты полиглот-формата, а не сохраняет их. В обе квоты засчитывается только ограниченный канонический сжатый буфер. Ограничение на размер JSON на транспорте учитывает накладные расходы Base64 для верхнего предела 32 МиБ декодированных входных данных. Каждый сохранённый производный объект фиксирует проверенный формат/разрешение JPEG, политику выборки, версию производного объекта, время создания, вычисленный сервером хеш содержимого и хешированную ссылку на родителя, а также хеш содержимого родителя от доверенной вызывающей стороны. Отмена проверяется между асинхронными фазами декодирования/хеширования перед атомарной фиксацией в кэше.

Этот транш ещё не подключает производственного производителя к маршруту и не предоставляет выбор вариантов с несколькими разрешениями. Поэтому прозрачный путь запросов Video Bridge не требует дополнительной работы, а вывод субъекта, привязанного к арендатору, и полный жизненный цикл мультиразрешения FU-08 остаются явной последующей работой, а не задокументированным завершённым поведением.

Кадры последовательно снабжаются описаниями с помощью настроенной модели Video. Пустое переопределение Video наследует настройку Vision; если оба значения пусты, автомаршрутизатор Vision выбирает фактическую модель с поддержкой зрения. Успешные описания заменяют исходную часть стабильным префиксом `[Video description:`, который также помечает текст как ненадёжное наблюдение, полученное из медиа, и указывает нижестоящим моделям не следовать инструкциям, найденным в медиа. Ключи кэша описаний кадров включают байты JPEG, промпт, метку времени и фактическую модель; кэшируются только успешные описания. Записи кэша сохраняют фактическую успешную производящую модель, включая резервную; мост сообщает `mixed`, когда разные кадры были созданы разными моделями. При попадании в кэш повторно используется эта идентичность производителя, а не перемаркировка в соответствии с запрошенным планом маршрутизации. Ключи кэша результатов для всего видео формируются по каждому входному параметру, влияющему на результат, — промпт, фактическая модель, политика выборки, количество кадров, режим семантического анализа, отпечаток SHA-256 нормализованной подсказки фокуса, окно фокуса, `transcript`, `audioTranscript` и флаг контакт-листа, — поэтому изменение любого из этих измерений является промахом кэша, а не повторным использованием устаревших данных. Версия политики визуальной дедупликации, порог и ограниченное количество кадров-кандидатов также явно указаны в ключе и метаданных кэша результатов; поэтому изменение политики не может привести к повторному использованию устаревшего описания всего видео. Метаданные кэша результатов v4 хранят режим и отпечаток, но никогда — исходный текст задачи пользователя. Метаданные гардрейла сообщают как запрошенный, так и фактический режимы анализа; запрошенный режим `focused` без пригодного пользовательского текста сообщается как фактически `full`.

Гардрейл извлекает все поддерживаемые видеочасти, но описывает не более `modalityBridgeVideoMaxVideos`. Для цели с доказанным `supportsVideo === false` неудачные и превышающие лимит видео становятся явными безопасными текстовыми маркерами, чтобы ни одно исходное видео не сохранялось. Когда возможность неизвестна, эти части сохраняют свой видеоноситель; любая резервная транскрипция следует описанному выше ограниченному преобразованию текста. Цели с `supportsVideo === true` обходят мост. Сигнал прерывания клиентского запроса распространяется через загрузку, очередь брокера, подпроцессы и вызовы описания; прерывания прекращают обработку между видео и никогда не приводят к открытому отказу с передачей исходных медиаданных.

| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                                      |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 мс                                                                                                           |

Устаревшие сохранённые значения таймаута Video свыше 120 секунд ограничиваются дедлайном брокера; новые записи настроек выше этого предела отклоняются. `GET /api/modality-bridge/video/runtime` требует доверенной маркированной локальности loopback до аутентификации или проверки runtime, а затем требует аутентификации управления. Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную причину, когда runtime недоступен. Внутренний эндпоинт извлечения не является публичным API загрузки: при насыщении очереди возвращается `503` с `Retry-After`, при отключении вызывающей стороны — `499`, а при истечении фиксированного дедлайна брокера — `504`. Преобразованные ответы добавляют `video->text;model=<visionModel>;parts=<videos>` в центральный заголовок `x-omniroute-modality-bridge`, не удаляя сегменты Vision и Audio.

### PII Masker (`piiMasker.ts`)

Выполняется на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input` и
  `prompt` (включая элементы в виде обычных строк) и применяет `processPII()` (из
  `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда
  `PII_REDACTION_ENABLED=true`, обнаруженные PII маскируются в исходящей
  полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет
  только политикой prompt-инъекций). Когда маскирование выключено, вызов
  фиксирует счётчики обнаружения, не перезаписывая содержимое.
- **`postCall`** глубоко клонирует ответ, запускает `sanitizePIIResponse()` вместе с
  маскировщиком формы Responses API (`maskResponsesOutput` — охватывает
  `output_text` и `output[].content[].text`). Если произошло хоть какое-то
  маскирование, изменённый ответ заменяет исходный.

Гардрейл никогда не блокирует; он только аннотирует (`meta.detections`,
`meta.redacted`) или перезаписывает.

#### Выбор по типам, пользовательские шаблоны и счётчики обнаружения

**Панель управления → Настройки → Безопасность → Маскирование PII** выбирает,
_что_ маскируется. Она не включает маскирование: это по-прежнему делают
`PII_REDACTION_ENABLED` (запрос) и `PII_RESPONSE_SANITIZATION` (ответ + SSE),
обе выключены по умолчанию.

- **Выбор по типам** — встроенные идентификаторы перечислены в
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Если не задано —
  применяются все типы (поведение, существовавшее до появления этой настройки).
  Шаблон `ssn_us` движка запросов соответствует `ssn`. Пресеты (Minimal,
  Standard, Financial, Brazilian, USA, Full) лишь проставляют галочки в UI.
- **Пользовательские шаблоны** — до 20 регулярных выражений или шаблонов с
  подстановочными знаками (`*` = до 64 непробельных символов, `?` = один).
  Совпадения заменяются на `[CUSTOM_REDACTED]`. Каждый шаблон проходит через
  `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): не более
  500 символов, флаги ограничены `g i m s u`, шаблон должен компилироваться,
  должен проходить проверку `safe-regex` (катастрофический бэктрекинг) и не
  должен совпадать с пустой строкой или с плейсхолдером маскирования. Шаблон,
  не прошедший проверку, отклоняется при сохранении и при тестировании, а
  сохранённая запись, не прошедшая проверку, пропускается во время выполнения
  вместо компиляции. Пользовательские шаблоны работают только при включённом
  маскировании.
- **Счётчики обнаружения** — количество по типам (никогда сами совпавшие
  значения), хранятся в памяти и сбрасываются при перезапуске
  (`src/lib/pii/piiDetectionStats.ts`). Они увеличиваются только при включённом
  маскировании.

Настройки хранятся в таблице `key_value` (пространство имён `pii_settings`,
`src/lib/db/piiSettings.ts`) и читаются через кэш с временем жизни 1 с. API:

| Метод  | Путь                     | Назначение                                                                    |
| ------ | ------------------------ | ----------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Состояние флага, `enabledTypes`, `customPatterns`, счётчики обнаружения       |
| `PUT`  | `/api/settings/pii`      | Заменяет `enabledTypes` (`null` = все) и/или `customPatterns`                 |
| `POST` | `/api/settings/pii/test` | Пробный прогон одного шаблона на образце не более 8 КБ; ничего не сохраняется |

Все три требуют аутентификации уровня управления и валидируют тело запроса с
помощью Zod (`src/shared/validation/schemas/piiSettings.ts`).

### Prompt-инъекции (`promptInjection.ts`)

Обнаруживает враждебные структуры в содержимом, предоставленном пользователем,
и применяет настроенную политику. Поведение определяется переменными окружения
и опциями конструктора:

| Настройка        | Переменная окружения                                                                                     | По умолчанию | Эффект                                                                                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                | `true`       | При `false` гардрейл досрочно завершает работу.                                                                                                                                                  |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`       | Политика инъекций: `block`, `warn` или `log`. (`redact` принимается для обратной совместимости, но **не** удаляет текст инъекции; перезапись PII в запросе управляется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | опция `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная серьёзность, необходимая для блокировки. При значении по умолчанию medium — только наблюдение.                                                                                       |

**Приоритет режимов** (`getMode`): `options.mode` вызывающей стороны →
**переопределение `INJECTION_GUARD_MODE` через флаг функции в БД** (Панель
управления → Настройки → Флаги функций) → env `INJECTION_GUARD_MODE` → env
`INPUT_SANITIZER_MODE` → `warn`. Таким образом, переопределение из панели
управления имеет приоритет над переменными окружения, поэтому UI флагов функций
управляет работающим гардом в реальном времени (без перезапуска). Чтение из БД
безопасно при сбоях: если оно завершается ошибкой, гард возвращается к поведению
на основе env, а когда переопределение не задано, поведение идентично
разрешению только по env.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор
   детекторов, используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline`
   и `markdown_system_block`, оба с серьёзностью `high`).
3. Опциональные `customPatterns`, передаваемые через опции конструктора
   (строки, регулярные выражения или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение достигает порога
серьёзности, `preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` guardrail логирует,
но пропускает вызов. Общий помощник `evaluatePromptInjection()` также
экспортируется для вызывающего кода, которому нужно оценивать промпты без
обращения к реестру.

**Граница сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384
байта) в `src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и
`evaluatePromptInjection()` выполняют `slice(0, MAX_INJECTION_SCAN_BYTES)` перед
запуском цикла по шаблонам. Инъекционные директивы располагаются в начале
входных данных, поэтому это ограничивает нагрузку регулярных выражений на
CPU/GC при полезных нагрузках в несколько сотен КБ, не ослабляя обнаружение
(см. #3932, #4041).

### Маскировщик учетных данных (`credentialMasker.ts`)

Работает на **обоих** этапах, последним в цепочке по умолчанию (приоритет
`95`). Затирает шаблоны известных API-ключей / секретных токенов в исходящей
полезной нагрузке (содержимое сообщений, аргументы вызовов инструментов,
результаты инструментов) **и** в ответе провайдера, так что учетные данные,
вставленные в промпт (или возвращённые результатом инструмента), не утекают
вышестоящему провайдеру или обратно клиенту.

- **Только по явному включению**, та же конвенция, что и для затирания PII
  (рядом с жёстким правилом №20): отключён, если только
  `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Когда он выключен, guardrail ничего не
  делает — никогда не блокирует и никогда не переписывает.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа
  (`walkValue()`, защищён от prototype pollution, безопасен при циклах
  благодаря `WeakSet`) и заменяет совпадения заглушкой `[REDACTED:<type>]`,
  клонируя только те ветви, которые действительно изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи LLM-провайдеров (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square),
  облачные ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), закрытые ключи
  / JWT, строки подключения с учетными данными (`mongodb://user:pass@...` и т.
  п.) и общий шаблон значения заголовка
  `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключи в форме заголовков
  (`authorization`, `x-api-key`, `api-key`, `apikey`) затираются структурно
  (только значение; префикс схемы вроде `Bearer `/`Basic ` сохраняется), а не
  через общее текстовое регулярное выражение.
- Guardrail никогда не блокирует; он только переписывает (`modifiedPayload` /
  `modifiedResponse`) и аннотирует (`meta.credentialsRedacted`, `meta.count`).

Регрессионная защита: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true досрочно прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается из preCall для перезаписи запроса
  modifiedResponse?: TValue; // возвращается из postCall для перезаписи ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, проходящее по цепочке, для последующих guardrail.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны в guardrail.
Прерывание запроса — это намеренное исключение fail-open: медиамосты
прекращают работу и выполняют очистку, не восстанавливая исходные медиаданные
в целевую систему, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет guardrail (или заменяет по нормализованному
  имени) и пересортировывает по возрастанию `priority`.
- `clear()` / `list()` — административные вспомогательные методы.
- `runPreCallHooks(payload, context)` — перебирает активные guardrail,
  пропускает полезную нагрузку через `modifiedPayload` и останавливается на
  первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и при
  необходимости повторно регистрирует guardrail по умолчанию для чистой
  изоляции тестов.

Оба исполнителя возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — массив записей `GuardrailExecutionResult`, включающих поля
`blocked`, `skipped`, `modified`, `error` и `meta` для каждого guardrail, что
полезно для трассировки.

### Отключение guardrail для отдельных запросов

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` собирает
дедуплицированный список имён guardrail, которые следует пропустить для
текущего запроса. Существует пять каналов, читаемых в указанном порядке и
объединяемых в один список (при дедупликации побеждает первое вхождение):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` в теле запроса (верхний уровень)
3. `metadata.disabledGuardrails` в теле запроса (только если `metadata` является объектом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Устаревший заголовок `x-disabled-guardrails`

Все пять каналов объединяются, включая оба заголовка: отправка и
`x-omniroute-disabled-guardrails`, и `x-disabled-guardrails` приводит к пропуску
объединения их списков, а пустой современный заголовок больше не скрывает
устаревший
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), исправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значения могут быть массивами строк или строкой, разделённой запятыми; имена
обрезаются и нормализуются к нижнему регистру kebab-case (`pii_masker` →
`pii-masker`), а пустые элементы отбрасываются. Результат передаётся через
`context.disabledGuardrails` в реестр, который пропускает совпадающие guardrail
(`skipped: true` в `results`).

Список отключения влияет только на **реестр**. Режим `block` для
prompt-injection — обязательная граница: middleware защиты от инъекций
(`src/middleware/promptInjectionGuard.ts`) вызывает `evaluatePromptInjection()`
без какого-либо управляемого вызывающей стороной списка отключения (мёртвый
вызов `resolveDisabledGuardrails({ body })`, который оно раньше выполняло, был
удалён в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), поэтому запрос,
отключающий `prompt-injection`, всё равно отклоняется в режиме `block`. Это
сделано намеренно. Каналы отключения управляются вызывающей стороной (тело
запроса, метаданные, заголовки), и вызывающая сторона не должна иметь
возможности отключить средство защиты, установленное оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Объединение
заголовков из
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) меняет только
то, какие guardrail реестра пропускаются; оно не позволяет клиенту обойти
middleware. Обязательные политики guardrail для каждого ключа и каждой группы
отслеживаются в RFC v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
См. [Покрытие и ограничения](#coverage-and-limits).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts` (маршруты семейства chat, перечисленные в разделе
[Покрытие и ограничения](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` формирует список пропусков на основе
   API-ключа, тела запроса и заголовков.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускает гардрейлы в порядке
   возрастания приоритета:
   - Отключённые гардрейлы фиксируются как `skipped`.
   - `preCall` каждого гардрейла может переписать полезную нагрузку через
     `modifiedPayload`.
   - Первый `block: true` досрочно прерывает цепочку, и обработчик возвращает
     ответ об отклонении гардрейлом.
3. (Потенциально переписанная) полезная нагрузка передаётся в
   комбо-маршрутизацию и диспетчеризацию к апстриму.
4. **Только для непотоковых запросов:** после сборки ответа
   `guardrailRegistry.runPostCallHooks(...)` запускает ту же цепочку для
   ответа. `block: true` здесь отбрасывает ответ апстрима и возвращает HTTP 400.
   Потоковые ответы полностью пропускают этот шаг.

Гардрейлы, выбрасывающие исключение, фиксируются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжает выполняться — fail-open по
замыслу.

- **Маршруты медиа, эмбеддингов и данных** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) никогда не достигают реестра.
  Никакой маскировки PII, маскировки учётных данных или моста модальностей там
  не выполняется. Их единственная проверка — устаревшее middleware
  injection-guard.
- **Потоковые ответы** не получают post-call гардрейлов: ни post-call
  `pii-masker` или `credential-masker`, ни post-call блокировки. Применяется
  только потоковое преобразование PII (когда включён
  `PII_RESPONSE_SANITIZATION`). Учётные данные, отражённые в потоковом ответе,
  не редактируются.
- **Каналы отключения и middleware (по замыслу):** middleware оценивает
  инъекции в промпты собственным вызовом `evaluatePromptInjection()`, не
  передавая никакого контролируемого вызывающей стороной списка отключений.
  Режим `block` — это обязательная граница, которую контролируемые вызывающей
  стороной отключения не могут обойти, в том числе на маршрутах семейства chat
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
  Отключение `prompt-injection` лишь пропускает гардрейл реестра.

### Что видит ответ до post-call

На непотоковом пути порядок таков: извлечение памяти → выполнение встроенных
инструментов → post-call гардрейлы → выход по post-call блокировке → запись в
семантический кэш.

- **Извлечение памяти** и **выполнение инструментов** видят ответ до того, как guardrails пост-вызова могут переписать или заблокировать его. Начиная с [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), извлечение памяти пропускает извлечённый текст через `sanitizePII`, когда включён `PII_RESPONSE_SANITIZATION` (как в потоковом, так и в непотоковом режиме), однако ответ, который пост-вызов позже заблокирует, всё равно уже был предложен памяти и инструментам.
- **Семантический кэш** сохраняет ответ после пост-вызова, поэтому он хранит переписанный ответ, а заблокированный ответ никогда не кэшируется. Записи кэша привязаны к ключу API.

## Конфигурация

Переменные окружения, которые считываются встроенными механизмами защиты (guardrails):

| Переменная                            | Используется              | Эффект                                                                                                                 |
| ------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | Политика обработки инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не перезаписывает текст инъекции. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | Режим защиты от инъекций; также флаг функции в БД, который **переопределяет** переменные окружения (БД > ENV).         |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | Минимальная серьёзность, при которой `MODE=block` отклоняет запрос: `high` (по умолчанию), `medium` или `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | Если `true`, PII-данные запроса маскируются (независимо от режима обработки инъекций).                                 |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | Управляет поведением маскирования на стороне ответа.                                                                   |

Механизмы защиты Modality Bridge считывают конфигурацию времени выполнения из
хранилища настроек на основе БД (`getSettings()`), а не из переменных окружения.
Основные ключи Vision: `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`. Устаревшие
ключи `visionBridge*` принимаются только как задокументированный резервный
вариант чтения на один цикл; записи из панели управления используют основные
ключи. Значения по умолчанию и резолвер резервного варианта находятся в
`src/shared/constants/modalityBridgeDefaults.ts`, а устаревшие константы
сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Audio использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. Для Audio нет резервного варианта с
устаревшими ключами, поскольку эти ключи были введены вместе со схемой Modality
Bridge.

Video использует `modalityBridgeVideoEnabled`,
`modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и `modalityBridgeVideoTimeout`, а также общие
настройки `modalityBridgeCache*`. По умолчанию отключено, поскольку
FFmpeg/ffprobe являются необязательными операционными зависимостями, а создание
описаний кадров увеличивает задержку и стоимость использования модели.

## Пользовательские guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1. Создайте `src/lib/guardrails/myGuardrail.ts`, расширив `BaseGuardrail`.
2. Реализуйте `preCall` и/или `postCall`.
3. Либо зарегистрируйте guardrail во время импорта (добавьте вызов в `registerDefaultGuardrails`), либо вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет любой ранее зарегистрированный guardrail с тем же нормализованным именем.
4. Добавьте тесты в `tests/unit/` (существующие примеры:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начинать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge поддерживает
внедрение зависимостей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge
предоставляет эквивалентные точки подмены для настроек, возможностей, выбора
STT-модели, проверки учётных данных и транскрипции. Благодаря этому тесты могут
проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов injection-guard и red-team (Фаза 8 · Блок D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) покрывает все маршруты,
принимающие пользовательские промпты. Он учитывает `INJECTION_GUARD_MODE` (по умолчанию
`warn` = только логирование; `block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                      | Маршруты                                                                                                                                             | Режим по умолчанию |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Текстовые (существующие) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративные             | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные                   | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут
блокирует корпус OWASP-LLM при `INJECTION_GUARD_MODE=block`; garak запускает пробы
(пропускается при отсутствии секрета). `moderations` включён для согласованности.
Режим block — это обязательная граница: `evaluatePromptInjection()` игнорирует
передаваемый middleware список отключений на уровне запроса, поэтому `disabledGuardrails`
**не** освобождает маршрут от этой проверки ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Ночной workflow (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) содержит два задания:

- **`promptfoo-guard` (блокирующее)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, «ignore all
  previous instructions…», джейлбрейки в стиле DAN) проверяет, что ответ содержит
  `error.code === "SECURITY_001"`, т.е. что guard действительно отклонил запрос.
- **`garak` (рекомендательное)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Зависит от
  секрета провайдера (`PROMPTFOO_PROVIDER_KEY`); при его отсутствии пропускается без
  ошибок и дополнен суффиксом `|| true`, поэтому отчитывается, не ломая CI.

Покрытие хелпера guard (`createInjectionGuard` / `withInjectionGuard`)
распространяется на каждый маршрут `/v1`, принимающий промпты; текст промпта
извлекается из `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
функцией `extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
