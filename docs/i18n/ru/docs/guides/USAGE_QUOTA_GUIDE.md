> **Кратко**: OmniRoute отслеживает использование токенов каждым запросом, рассчитывает стоимость, обеспечивает соблюдение квоты для каждого API-ключа и отображает аналитику на панели управления. В этом руководстве объясняется, как всё это работает.

**Исходные файлы:**

- `open-sse/services/usage.ts` (~70KB) — основная логика отслеживания использования
- `src/lib/usageAnalytics.ts` (~10KB) — агрегация данных для панели управления
- `src/lib/db/quotaSnapshots.ts` — исторические данные о квотах
- `src/lib/db/usage*.ts` — несколько модулей БД, связанных с использованием

## Обзор

Каждый запрос, проходящий через OmniRoute, создаёт **запись об использовании**, содержащую:

- **Идентификационные данные**: какой API-ключ, поставщик, модель и комбинация использовались
- **Токены**: токены промпта, токены завершения, кэшированные токены и общее количество
- **Стоимость**: сумма в USD, рассчитанная на основе данных о тарифах
- **Время**: задержка, временные метки начала и завершения
- **Статус**: успешно, ошибка, ограничение частоты запросов и т. д.

Эти записи агрегируются в **аналитику**, сохраняются в виде **снимков квот** и используются для обеспечения соблюдения **ограничений бюджета для каждого ключа**.

```
Запрос ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    аналитика  квота   биллинг
                    (панель)   (контроль) (экспорт)
```

## Что записывается

Сервис `usage.ts` фиксирует **событие использования** для каждого запроса:

| Поле               | Тип     | Источник                                                        |
| ------------------ | ------- | --------------------------------------------------------------- |
| `id`               | string  | UUID, генерируемый при записи                                   |
| `apiKeyId`         | string  | Ключ API, с которым был отправлен запрос                        |
| `provider`         | string  | Идентификатор провайдера (openai, anthropic и т. д.)            |
| `model`            | string  | Идентификатор модели (gpt-5, claude-opus-4-6 и т. д.)           |
| `comboId`          | string? | Идентификатор комбинации, если запрос направлен через неё       |
| `promptTokens`     | number  | Из ответа вышестоящего провайдера                               |
| `completionTokens` | number  | Из ответа вышестоящего провайдера                               |
| `cachedTokens`     | number  | Токены попадания в кэш (кэширование промптов Anthropic и т. д.) |
| `totalTokens`      | number  | Промпт + ответ                                                  |
| `costUsd`          | number  | Рассчитывается на основе данных о тарифах                       |
| `latencyMs`        | number  | Полная длительность обработки запроса                           |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`      |
| `errorClass`       | string? | Класс ошибки, если статус != success                            |
| `timestamp`        | string  | ISO 8601 UTC                                                    |
| `metadata`         | object  | Пользовательские данные, добавленные плагином                   |

### Откуда берутся токены

Токены извлекаются из ответа вышестоящего провайдера в **обработчике ответа**:

```ts
// Из open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Для провайдеров, которые не возвращают данные об использовании (некоторые провайдеры с доступом через веб-cookie), OmniRoute **оценивает** количество токенов с помощью эвристики `~4 chars per token` (см. `open-sse/services/autoCombo/pipelineRouter.ts`).

### Кэшированные токены

OmniRoute отслеживает `cached_tokens` отдельно от `prompt_tokens`, поскольку:

- При кэшировании промптов Anthropic для кэшированных токенов применяется сниженный тариф (10% от обычного)
- Некоторые провайдеры возвращают `cache_read_input_tokens`, для которых должен применяться другой тариф
- Аналитика может показывать **долю попаданий в кэш** = `cached_tokens / prompt_tokens`

### Диагностика тарифных категорий записи в кэш

Панель состояния кэша промптов в разделе аналитики различает записи в кэш
на 5 минут и на 1 час, о которых сообщает провайдер. Поля Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` и
`usage.cache_creation.ephemeral_1h_input_tokens` сохраняются при преобразовании данных об использовании как в потоковом, так и в
непотоковом режиме и записываются вместе со сводками журнала вызовов. Общее
количество записей в кэш не добавляется к этим категориям повторно.

У вызовов только с общим счётчиком записи, включая старые записи, тарифная категория
неизвестна. При частичной разбивке нераспределённый остаток остаётся в неизвестной категории; недопустимые или
противоречивые счётчики помечаются, а не получают TTL без предупреждения. Маркеры
TTL в запросе не подтверждают оплачиваемую тарифную категорию.

Оценка стоимости записи в эквиваленте API на этой панели охватывает только категории, для которых есть данные и тарифы, а не
весь запрос. Для стандартных тарифов моделей Claude/Anthropic используется коэффициент 1,25 к
тарифу на входные токены для записи на 5 минут и двойной тариф на входные токены для записи на 1 час. Отсутствующие
тарифы считаются недоступными, а не нулевыми. Тарифы фиксируются при регистрации каждого нового вызова;
стоимость исторических записей не пересчитывается. Поэтому для учётных записей с подпиской может отображаться
оценка в эквиваленте API, хотя эта сумма не списывается как денежные расходы и не расходует
квоту подписки. Существующие расчёты квот, бюджетов и точной стоимости по данным провайдера остаются без изменений.

Эта диагностика использует существующую сводку состояния кэша с ограниченным объёмом данных и действующие правила
хранения журнала вызовов. Она не меняет TTL запросов по умолчанию, маршрутизацию или выбор учётной записи.
Фиксация TTL, запрошенного клиентом, и фактического исходящего TTL в точке отправки
провайдеру отложена; эта панель показывает тарифные категории по данным о начислениях, а не фактический исходящий TTL.

Реализация: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` и `open-sse/utils/cacheWriteUsage.ts`.

## Расчёт стоимости

Стоимость рассчитывается на основе **данных о ценах**, синхронизированных с LiteLLM (`src/lib/pricingSync.ts`):

| Модель            | Вход, $/1M | Выход, $/1M | Кэш, $/1M |
| ----------------- | ---------- | ----------- | --------- |
| gpt-5             | $2.50      | $10.00      | —         |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50     |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30     |
| gemini-2.5-pro    | $1.25      | $10.00      | —         |

Формула расчёта стоимости (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Зачем вычитать кэшированные токены из токенов промпта?** Кэшированная часть тарифицируется отдельно; применение цены входных токенов ко всему промпту привело бы к завышенному расчёту.

### Синхронизация цен

Данные о ценах автоматически синхронизируются с LiteLLM через эндпоинт `/api/pricing/sync` (запускается встроенной задачей cron, а не пользовательской переменной окружения):

```bash
# Запуск вручную
curl -X POST http://localhost:20128/api/pricing/sync
```

Для моделей, по которым отсутствуют данные о ценах, OmniRoute выполняет **оценочный расчёт стоимости**, используя внутренние средние тарифы (полученные из данных о ценах LiteLLM).

## Агрегация по диапазонам дат

Модуль `usageAnalytics.ts` рассчитывает показатели для виджетов панели мониторинга на основе необработанных данных об использовании. Он поддерживает 7 временных диапазонов:

| Диапазон | Период                                 | Сценарий использования             |
| -------- | -------------------------------------- | ---------------------------------- |
| `1d`     | Последние 24 часа                      | Выявление почасовых скачков затрат |
| `7d`     | Последние 7 дней                       | Еженедельный обзор                 |
| `30d`    | Последние 30 дней                      | Ежемесячное выставление счетов     |
| `90d`    | Последние 90 дней                      | Ежеквартальный анализ              |
| `ytd`    | С 1 января текущего года               | Отслеживание годового бюджета      |
| `all`    | Всё время                              | Статистика за всё время            |
| `custom` | Начало и конец, заданные пользователем | Аудиты, разовые запросы            |

### Рассчитываемые виджеты панели мониторинга

Для любого диапазона дат аналитический слой рассчитывает:

| Виджет                        | Описание                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------- |
| **Сводные карточки**          | Общее число запросов, общие затраты, общее число токенов, доля успешных запросов |
| **График динамики по дням**   | Затраты и токены за день, с накоплением по моделям                               |
| **Тепловая карта активности** | Сетка «час суток × день недели», цвет = число запросов                           |
| **Разбивка по моделям**       | Круговая диаграмма затрат по моделям                                             |
| **Разбивка по провайдерам**   | Столбчатая диаграмма запросов по провайдерам                                     |
| **Ведущие API-ключи**         | Таблица 10 ключей с наибольшими затратами                                        |
| **Анализ ошибок**             | Доля ошибок во времени, наиболее частые классы ошибок                            |

### Программный доступ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // записи истории использования
  "7d",                 // временной диапазон: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // карта подключений провайдеров (connectionId → имя учётной записи)
  {
    startDate: "2025-01-01",  // необязательно: для диапазона "custom"
    endDate: "2025-06-01",   // необязательно: для диапазона "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (в центах)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Применение квот

Квота для каждого API-ключа применяется в двух местах:

1. **Мягкий лимит** (`quotaWarnAt`): предупреждение на панели мониторинга, когда использование превышает порог
2. **Жёсткий лимит** (`quotaLimit`): при превышении запрос отклоняется с кодом HTTP 429

### Настройка

```ts
// Для каждого API-ключа
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — показать предупреждение
  quotaLimit: 10_00,    // $10.00 — полная блокировка
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Схема применения квот

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### Снимки состояния квот

Таблица `quotaSnapshots` хранит **историю состояния квот** для анализа динамики:

| Поле | Описание |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Отслеживаемый ключ |
| `window` | "day" | "week" | "month" |
| `used` | Затраты за этот период (в центах) |
| `limit` | Лимит (в центах) |
| `resetAt` | Время сброса периода |
| `createdAt` | Время создания снимка |

Снимки создаются **при каждом запросе** со стоимостью > 0 и используются, чтобы:

- Отображать индикатор использования квоты на панели мониторинга
- Показывать графики динамики квот за 30 дней
- Отправлять оповещения, когда использование приближается к лимиту

### Запрос аналитики использования

Доступ к данным об использовании осуществляется через панель управления или инструменты MCP, а не напрямую через конечные точки экспорта REST. Доступная аналитика:

- **`/api/usage/analytics`** — агрегированные метрики использования (группировка по модели, провайдеру, ключу)
- **`/api/usage/quota`** — текущее состояние квоты для каждого ключа API
- **`/api/usage/history`** — журналы истории запросов

Два инструмента MCP предоставляют агентам доступ к данным об использовании (см. `open-sse/mcp-server/tools/`):

| Инструмент              | Описание                                                        |
| ----------------------- | --------------------------------------------------------------- |
| `omniroute_cost_report` | Формирует отчёт о расходах по каждому ключу за указанный период |
| `omniroute_check_quota` | Возвращает текущее состояние квоты для ключа API                |

Пример вызова агентом:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## Хранение и очистка

Объём данных об использовании увеличивается примерно на 1–10 КБ с каждым запросом. При больших масштабах это может составлять значительный объём.

### Настройки хранения

Срок хранения истории использования настраивается в разделе настроек базы данных в пользовательском интерфейсе или через `/api/settings/database`.

По умолчанию история использования хранится **90 дней**.

### Очистка

Старые записи удаляются с помощью `src/lib/db/cleanup.ts`:

- Запускается фоновым процессом cron
- Удаляет из `usage_history` записи старше срока хранения, заданного настройкой `usageHistory`

### Оценка объёма хранилища

| Частота запросов      | Хранение за 30 дней | Хранение за 90 дней |
| --------------------- | ------------------- | ------------------- |
| 100 запросов/день     | ~3 МБ               | ~9 МБ               |
| 1 000 запросов/день   | ~30 МБ              | ~90 МБ              |
| 10 000 запросов/день  | ~300 МБ             | ~900 МБ             |
| 100 000 запросов/день | ~3 ГБ               | ~9 ГБ               |

При очень высокой нагрузке рассмотрите следующие варианты:

- Сокращение срока хранения в настройках базы данных
- Использование `aggregated_metrics` вместо исходных записей (только для аналитики)

## Советы по оптимизации затрат

### 1. Используйте подходящую модель

```bash
# Быстрый ответ — используйте дешёвую и быструю модель
curl -d '{"model":"auto/fast","messages":[...]}'

# Сложная задача — выбирайте качество
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Включите кэширование

Кэширование промптов Anthropic позволяет сэкономить **90% на повторяющемся контексте**:

```ts
// Кэширование выполняется автоматически — просто передавайте один и тот же большой системный промпт
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Будет автоматически закэширован
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Используйте сжатие

Сжатие RTK + Caveman позволяет сэкономить **15-95% в сеансах с интенсивным использованием инструментов**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Установите квоты для каждого ключа

Всегда задавайте `quotaLimit`, чтобы предотвратить неконтролируемый рост затрат:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Лимит $10 в месяц
```

### 5. Анализируйте основных потребителей

Используйте панель управления или **`/api/usage/analytics`** для группировки по API-ключу и сортировки по стоимости:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Устранение неполадок

### "Затраты выше ожидаемых"

1. Проверьте **`/api/usage/analytics?groupBy=model`** — найдите дорогую модель
2. Проверьте **`/api/usage/analytics?groupBy=apiKey`** — найдите потребителя с большим расходом
3. Убедитесь, что данные о ценах актуальны: `POST /api/pricing/sync`

### "Записи отсутствуют"

- Проверьте настройки хранения данных БД в разделе Панель управления → База данных → Очистка — старые записи удаляются периодической задачей очистки (`src/lib/db/cleanup.ts`)
- Проверьте наличие ошибок в `src/lib/db/usage*.ts` — ошибки записи в БД регистрируются в журнале, но не отображаются пользователю
- Убедитесь, что запрос действительно достиг `chatCore` — проверьте маршрутизацию комбинаций

### "Квота не применяется"

- Проверьте настройку `quotaLimit` ключа
- Убедитесь, что `quotaWindow` задано правильно
- Проверьте наличие записей `quotaSnapshots` — они должны создаваться при каждом запросе
