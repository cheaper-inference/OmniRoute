OmniRoute имеет три различных, но связанных между собой механизма устойчивости. Каждый из них имеет разные масштабы и цели. Держите их отдельно при отладке поведения маршрутизации.

![3-layer resilience model](../diagrams/exported/resilience-3layers.svg)

> Источник: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd)

> **Приоритет Env-vs-dashboard для переключения устойчивости.** Включаемые переключатели устойчивости, полученные из среды — `QUOTA_PREFLIGHT_CUTOFF_ENABLED`, `PROVIDER_COOLDOWN_ENABLED`, `STREAM_RECOVERY_ENABLED`, `STREAM_RECOVERY_MIDSTREAM_ENABLED`, `STREAM_THROUGHPUT_WATCHDOG_ENABLED` — предоставляют только значение _default_ (`DEFAULT_RESILIENCE_SETTINGS`, `src/lib/resilience/settings.ts`). Логическое значение сохраняется в `resilienceSettings` (Dashboard →** Настройки устойчивости →** / `PATCH /api/resilience`, хранящийся в `key_value`), выигрывает у значения env: нормализация (`toBoolean`, `src/lib/resilience/settings/normalize.ts`) сохраняет сохраненное логическое значение, когда оно существует. Установка такой переменной env var в `true` в развертывании, где панель управления уже сохранила `false` поэтому ничего не меняется — переключите переключатель.** Настройки устойчивости →** (или вместо этого очистите сохраненное поле).

## 1. Circuit Breaker провайдера

**Область действия:** провайдер целиком (например, `glm`, `openai`, `anthropic`).

**Назначение:** прекратить отправку трафика провайдеру, который повторно даёт сбои на уровне upstream/сервиса.

**Реализация:**

- Основной класс: `src/shared/utils/circuitBreaker.ts`
- Подключение: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API статуса: `GET /api/monitoring/health`
- API сброса: `POST /api/resilience/reset`
- Обёртки: `open-sse/services/accountFallback.ts`
- Таблица БД: `domain_circuit_breakers`

**Состояния:**

- `CLOSED` — обычный трафик разрешён
- `DEGRADED` — трафик по-прежнему разрешён, но отслеживается повышенное число сбоев провайдера; возврат в `CLOSED` происходит после достаточного числа успешных запросов, после успешной проверки соединения либо по истечении самого длительного удержания в `OPEN` для последнего типа сбоя (его значение `cooldownByKind`, иначе `resetTimeout`, умноженное на `maxBackoffMultiplier`, но не менее одного периода cooldown) при отсутствии нового сбоя
- `OPEN` — провайдер временно заблокирован; комбо-маршрутизация пропускает его
- `HALF_OPEN` — таймаут сброса истёк; разрешён пробный запрос

**Настраиваемые значения по умолчанию (`open-sse/config/constants.ts`, доступны в разделе Dashboard → Settings → Resilience панели управления):**

| Класс     | Переход в DEGRADED | Открытие (OPEN) | Таймаут сброса |
| --------- | ------------------ | --------------- | -------------- |
| OAuth     | 5 сбоев            | 8 сбоев         | 60s            |
| API-ключ  | 7 сбоев            | 12 сбоев        | 30s            |
| Локальный | вычисляется        | 2 сбоя          | 15s            |

`degradationThreshold` определяет, когда провайдер переходит в `DEGRADED`; `failureThreshold` — когда он открывается и начинает пропускаться. Профили локальных провайдеров пока не отображаются на странице настроек Resilience.

**Коды срабатывания:** только статусы уровня провайдера `[408, 500, 502, 503, 504]`. НЕ срабатывает на ошибки уровня аккаунта (большинство 401/403/429 — они относятся к cooldown или блокировке).

**Ленивое восстановление:** когда срок `OPEN` истекает, `getStatus()`, `canExecute()`, `getRetryAfterMs()` обновляют состояние до `HALF_OPEN`. Те же операции чтения (и следующий сбой) постепенно возвращают устаревшее `DEGRADED` обратно в `CLOSED`. Фоновый таймер не требуется.

### Опциональный глобальный Provider Cooldown (оконный фильтр)

Четвёртый, **опциональный** уровень (`PROVIDER_COOLDOWN_ENABLED`, по умолчанию **выключен**) хранит межзапросную память о сбоящих провайдерах в `open-sse/services/providerCooldownTracker.ts`; её учитывает механизм выбора целей комбо-маршрутизации, чтобы последовательные комбо-запросы не обращались повторно к провайдеру, который только что дал сбой. Записи уровня провайдера подчиняются оконному фильтру `PROVIDER_PROFILES`:

| Профиль  | Срабатывает после (`providerFailureThreshold`) | В пределах (`providerFailureWindowMs`) | Cooldown (`providerCooldownMs`) |
| -------- | ---------------------------------------------: | -------------------------------------: | ------------------------------: |
| OAuth    |                                           `10` |                                `15min` |                          `5min` |
| API-ключ |                                           `15` |                                `30min` |                         `10min` |

Ниже порога провайдер **не** считается находящимся в cooldown; успешный запрос очищает окно. Записи уровня соединения (`provider:connectionId`) вместо этого используют экспоненциальный backoff `minRetryCooldownMs → maxRetryCooldownMs`. Переопределения: `OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`. Регрессионный тест: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Период ожидания подключения

**Область действия:** одно подключение/аккаунт/ключ провайдера.

**Назначение:** пропускать один неисправный ключ, пока другие подключения того же провайдера продолжают обслуживать запросы.

**Реализация:**

- Пометка как недоступного: `src/sse/services/auth.ts::markAccountUnavailable()`
- Выбор: `getProviderCredentials*` в том же файле
- Расчёт периода ожидания: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Настройки: `src/lib/resilience/settings.ts`

**Поля для каждого подключения:**

- `rateLimitedUntil` — временная метка окончания периода ожидания
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — счётчик экспоненциальной задержки

**Периоды ожидания по умолчанию:**

- Базовый для OAuth: 5 с
- Базовый для API-ключа: 3 с
- `429` для API-ключа: предпочтительно используются upstream-заголовки `Retry-After`/сброса или текст сброса, который можно разобрать
- Задержка: `baseCooldownMs * 2 ** failureIndex`

**Задержка повторной попытки для провайдера.** На странице сведений о провайдере есть список **Задержка повторной попытки** (Авто, от
15 с до 1 ч). Он сохраняет значение `resilienceSettings.providerQuotaOverrides[<providerId>].rateLimitCooldownSeconds`
(1–21600) через `PATCH /api/resilience`. Если ошибка ограничения частоты не содержит upstream-подсказку о повторной попытке,
это значение заменяет масштабированную задержку и сбрасывает `backoffLevel` в 0
(`open-sse/services/rotationConfig.ts::overrideFor`). Приоритеты для ошибки ограничения частоты, от наиболее высокого к наиболее низкому:
upstream-подсказка о повторной попытке, затем `providerSpecificData.rotationOverrides.rateLimitResetSeconds` для конкретного подключения,
затем задержка повторной попытки для провайдера, затем
`OMNIROUTE_ROTATION_RATE_LIMIT_RESET_SECONDS` из окружения, затем масштабированная задержка. Авто удаляет поле.
Это влияет только на причину ограничения частоты и никогда — на терминальные состояния.

**Защита от эффекта «стада»:** предотвращает чрезмерное продление периода ожидания или двойное увеличение `backoffLevel`
при одновременных сбоях.

**Ошибки `429` из-за ограничения параллелизма не повышают уровень задержки.** Ошибка `429`, тело которой сообщает
об ограничении параллелизма ("слишком много одновременных запросов", "ограничение параллелизма",
"ограничение параллельных запросов", `并发数过高` для GLM), означает, что аккаунт исправен, но занят.
`checkFallbackError()` возвращает причину `concurrency_limited`: немедленно переключается на следующее
подключение, переводит это подключение в фиксированный период ожидания `CONCURRENCY_LIMIT_COOLDOWN_MS` (1 с)
или использует upstream-подсказку о повторной попытке, оставляет `backoffLevel` без изменений и устанавливает
`skipProviderBreaker`.
Явное тело с информацией о квоте имеет приоритет, поэтому тело, которое также соответствует шаблону квоты,
остаётся вердиктом квоты. Обнаружение: `looksLikeConcurrencyLimit()` в `src/shared/utils/classify429.ts`;
вердикт: `open-sse/services/accountFallback/concurrencyLimit429.ts`. `classify429()` (`FailureKind` автоматического
размыкателя) не изменяется и по-прежнему считывает `rate_limit` для таких тел.

**Остановки потока контента не переводят аккаунт в период ожидания.** Когда сторожевой таймер остановки контента
(`open-sse/utils/streamHandler.ts`) прекращает ожидание потока, который вовремя не отправил вывод модели,
`markAccountUnavailable()` записывает ошибку для подключения, но не устанавливает период ожидания: остановка относится
к этому запросу и чаще всего вызвана длительным этапом рассуждения без вывода. Операторы могут включить это поведение
с помощью `resilienceSettings.streamStallCooldown.enabled` (по умолчанию `false`).

**Необязательный сигнал задержки для выбора аккаунта `p2c`.** Каждая отправленная попытка записывает время до первого
байта и результат для каждого подключения (а также для пары подключение + модель) в скользящем окне в памяти:
последние 20 образцов за 15 минут
(`open-sse/services/connectionLatencyTracker.ts`, запись выполняется из `safeLogEvents()` в
`src/sse/handlers/chatHelpers.ts`). Когда значение `resilienceSettings.p2cLatency.weight` больше
`0` (диапазон 0–20, по умолчанию `0` = выключено), `compareP2CConnections()` в `src/sse/services/auth.ts` добавляет
до `weight` баллов каждому кандидату пары. Половина этого значения рассчитывается по задержке как отношение к более
быстрому кандидату (задержка в два раза больше получает всю половину), а вторая половина — по скользящей доле ошибок.
Этот показатель применяется только когда у обоих кандидатов есть не менее 3 образцов, поэтому новые аккаунты
не получают штрафов, а его максимальное значение остаётся ниже штрафов за заблокированную и исчерпанную квоту.
Он не создаёт собственного автоматического размыкателя: сбойные аккаунты по-прежнему обрабатываются уровнями периода ожидания,
блокировки и автоматического размыкателя. Задайте его с помощью
`PATCH /api/resilience` `{ "p2cLatency": { "weight": 10 } }`.

**Кадры рассуждения перезапускают бюджет остановки контента.** Модель рассуждения может думать несколько минут
до появления первого видимого токена: Claude передаёт кадры `thinking_delta`, текст рассуждения в которых может быть пустым,
а Responses API передаёт один элемент рассуждения за другим. `isReasoningProgressFrame()` (`open-sse/utils/streamReadiness.ts`)
распознаёт эти кадры, и сторожевой таймер перезапускает свой бюджет после каждого из них вместо отмены этапа.
При этом они всё ещё не являются выводом модели, поэтому этап, завершившийся только рассуждением, по-прежнему
определяется как пустой, а этап, в котором рассуждение прекращается и отправляются только сигналы активности,
по-прежнему приводит к срабатыванию сторожевого таймера.

Двоичные кадры Kiro `reasoningContentEvent` с непустой подписью сохраняют эту активность рассуждения через исполнитель
как пустую дельту `reasoning_content`. Подпись не передаётся дальше. Метаданные, неполные кадры и пустые подписи
не перезапускают бюджет контента; независимый тайм-аут активного потока и отмена клиентом по-прежнему применяются
(`open-sse/executors/kiro/reasoning.ts`).

**Терминальные состояния (НЕ периоды ожидания):**

- `banned` — устанавливается при обнаружении запрещённого ключевого слова / блокировки аккаунта (см. [BAN_DETECTION](../security/BAN_DETECTION.md)). Отказы upstream для отдельных запросов (`request_rejected`, например OAuth 403 Anthropic "Request not allowed") никогда его не устанавливают: они подсчитываются для каждого подключения и модели и исключают эту модель из ротации с увеличивающимся периодом ожидания, ограниченным `REQUEST_REJECTED_MAX_COOLDOWN_MS` (1 ч), либо переводят подключение в период ожидания, если модель неизвестна — `open-sse/services/requestRejectedStreak.ts`
- `expired` (переходит в терминальное состояние после ограниченного числа повторных попыток — `EXPIRED_RETRY_MAX = 3` с экспоненциальной задержкой — чтобы временные ошибки OAuth могли быть устранены автоматически до окончательной деактивации аккаунта)
- `credits_exhausted`

Эти состояния сохраняются до изменения учётных данных или их сброса оператором. Не перезаписывайте терминальные состояния временным состоянием периода охлаждения.

**Ленивое восстановление:** когда время `rateLimitedUntil` истекло, соединение снова становится доступным. При успешном использовании `clearAccountError()` очищает все поля ошибок.

### Стена ограничения использования Claude OAuth: очередь с низким приоритетом + сброс ограничения сеанса

**Область применения:** одно соединение с подпиской Claude (OAuth). Обе функции **включаются отдельно для каждого
соединения** (Edit connection → раздел Claude → `lowPriorityMode` / `autoLimitReset` в
`providerSpecificData`; по умолчанию обе отключены) и повторяют команды Claude Code `/low-priority` и `/limit-reset` (контракт взаимодействия зафиксирован на основе Claude Code 2.1.263).

**Реализация:**

- Конечный автомат и классификация ответов: `open-sse/services/claudeLowPriority.ts`
- Клиент статуса/запроса сброса: `open-sse/services/claudeLimitReset.ts`
- Хук исполнителя (добавление заголовка + повторная попытка для того же аккаунта): `open-sse/executors/base.ts::execute()`
- Сохранение настроек включения: `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**Триггер:** 5-часовая стена использования — ответ `429`, заголовки которого содержат
`anthropic-ratelimit-unified-status: rejected` и, если аккаунт доступен,
`anthropic-ratelimit-unified-slow-offer: treatment`. До первого ответа
429 на стене ничего не отправляется; пакетный ответ 429 без унифицированных заголовков проходит обычный путь периода охлаждения.

**Очередь с низким приоритетом** (`lowPriorityMode`):

- При ответе 429 на стене исполнитель принимает предложение и немедленно повторяет запрос для **того же**
  аккаунта с `anthropic-usage-limit: slow`; очередь остаётся активной до объявленного
  `anthropic-ratelimit-unified-reset` (+ 60 секунд запаса), и каждый запрос в этом окне содержит заголовок. Перехваченный ответ 429 не достигает `handleChatCore`, поэтому соединение **не** переводится в период охлаждения и не переключается на другое.
- `anthropic-ratelimit-unified-slow-status` в последующих ответах: `active` / `not_needed`
  сохраняют очередь; при `slot_busy` (429) или `529` выполняется ожидание, указанное сервером в
  `anthropic-ratelimit-unified-slow-retry-after` (по умолчанию 20 с, ограничение 5–600 с, джиттер ±30%),
  и повторная попытка; ожидание ограничено значением `anthropic-ratelimit-unified-slow-max-wait` (по умолчанию 20 минут, ограничение 1 минута–6 часов) — после его истечения очередь завершается, а 10-минутный период охлаждения блокирует повторное принятие. Ожидание дополнительно ограничивается оставшимся временем собственного тайм-аута начала upstream-запроса (`resolveFetchStartTimeout`, по умолчанию 10 минут) за вычетом 5 секунд: без этого ограничения максимальное ожидание по умолчанию в 20 минут превышало бы срок действия запроса, и ожидание было бы прервано посередине, приводя к `TimeoutError` вместо корректного завершения с `max_wait` и периода охлаждения.
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, переход 5-часового окна или
  `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (что завершает очередь как
  `extra_usage` при любом статусе, поскольку платное превышение теперь покрывает стену) завершают очередь; после этого ответ проходит обычный путь периода охлаждения. `budget_exhausted` сохраняется до объявленного сброса бюджета (не более 8 дней).
- Проверка стены выполняется после собственных повторных попыток исполнителя внутри попытки, вызванных ответом 400 (редактирование контекста, ограничение параметров thinking/effort, автоматическое обучение параметров), поэтому ответ 429 на стене, появившийся только при одной из таких повторных попыток, всё равно перехватывается и не достигает пути периода охлаждения.
- Состояние хранится в памяти отдельно для каждого соединения (после перезапуска для повторного принятия потребуется ещё один ответ 429 на стене).

**Сброс ограничения сеанса** (`autoLimitReset`, выполняется перед очередью, если включены обе функции):

- `GET https://api.anthropic.com/api/oauth/usage?at_wall=1&skip_spend=1` → блок
  `juniper_tide`; если `arm: "reset"` и `available: true`,
  `POST https://api.anthropic.com/api/organizations/{orgUUID}/reset_rate_limits` с
  `{ "program": "juniper_tide" }` (UUID организации из `providerSpecificData.organizationUUID`, резервный вариант — bootstrap).
- `result: reset|not_limited` → запрос повторяется на полной скорости (без заголовка slow).
  `already_used` / `not_offered` кэшируют `next_available_at` (по умолчанию одна неделя); при любой ошибке выполняется отложенная повторная попытка на 15 минут. Сброс выполняется раз в неделю и всё равно учитывается в недельном ограничении.

### Автоматическое применение банковских сбросов

**Объем:** Соединения по подписке Codex и Claude (OAuth).**Подписаться** : настройка `bankedResetAutoApply` отключена и по умолчанию находится в режиме `dry-run` (Настройки → AI → — автоматическое применение группового сброса).

**Цель:** тратить накопленные сбросы самостоятельно, когда учетная запись достигает стены использования, вместо того, чтобы ждать, пока оператор нажмет «Погасить» на странице «Лимиты поставщика».

| --------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `codexCredits`              | Сброс кредитов Codex                             | фоновое задание, каждые 60 с                                                           |
| `claudeCredits`             | Банковские гранты Claude (кредиты `GRANT` )      | фоновое задание, каждые 60 с                                                           |
| `claudeSessionReset`        | Сброс еженедельного лимита сеансов Claude (выше) | путь запроса, используя ту же политику, что и переключатель для каждой учетной записи. |

**Выполнение:**

- Чистое решение (один набор правил для обоих путей): `src/lib/usage/bankedResetPolicy.ts::decideBankedReset()`
- Фоновое задание: `src/lib/services/bankedResetAutoApply.ts` (начато в `src/instrumentation-node.ts`)
- Шлюз пути запроса Claude : `src/lib/usage/claudeSessionResetPolicy.ts`, зарегистрированный через `setClaudeLimitResetPolicy()` в `open-sse/services/claudeLimitReset.ts`
- История, шапки и вебхук: `src/lib/usage/bankedResetAudit.ts`
- История API: `GET /api/settings/banked-reset-auto/history?limit=50` (аутентификация управления)

**Порядок решения** (первое невыполненное правило является записанной причиной):

1. Функция отключена, тип кредита отключен или учетная запись выходит за рамки (`accountScope` `all` / `selected` плюс карта `connections` для каждой учетной записи).
2. Вне дополнительного расписания UTC (`startHourUtc` > `endHourUtc` пересекает полночь).
3. Ограничения за последние 24 часа: `maxPerAccountPerDay` (1), `maxPerDay` (3) и `minSpacingMinutes` (30) между любыми двумя погашениями.
4. Триггер: изолированное окно `session` или `weekly` (читается из `getQuotaWindowStatus().reachedThreshold`, а не `isAccountQuotaExhausted()`, который сообщает только об учетной записи с каждым потраченным окном) или срок действия кредита, истекающий в `expiringCreditHours` (24) на учетной записи, которая использовала как минимум `expiringCreditMinUsedPercent` (50).
5. Защита естественного сброса: пропустить, когда закрытое 5-часовое окно сбрасывается в `sessionResetGuardMinutes` (90) или закрытое еженедельное окно в `weeklyResetGuardHours` (12).
6. Еженедельный уровень: пропустите 5-часовой сброс, если недельный остаток ниже `weeklyFloorPercent` (10).
7. Режим `last-resort` : пропустите, пока в обоих окнах другой учетной записи того же провайдера, находящейся в области действия, осталось не менее `poolHeadroomPercent` (10). Триггеры истечения кредита обходят это.
8. `dry-run` записывает строку и ничего не погашает; `last-resort` и `eager` выкупают.

Отсутствие данных о квоте никогда не разблокирует погашение: неизвестное время сброса или еженедельное использование пропускаются.

**Сброс сеанса Claude :** если эта функция отключена или `claudeSessionReset` отключен, переключатель `autoLimitReset` для каждой учетной записи действует точно так же, как и раньше. Если оба включены, эта функция заменяет переключатели для каждой учетной записи: учетная запись в области действия может запрашивать только тогда, когда это разрешено политикой, а в режиме `dry-run` заявки не подаются.

**Безопасность:** задание выкупает не более одного кредита за тик, принимает решение перед листингом кредитов (пропущенная учетная запись никогда не отображается в списке), использует ключи идемпотентности `auto-reset:<connectionId>:<yyyy-mm-dd>:<n>` и отключает учетную запись на 1 час после неудачного листинга или погашения. Каждое решение о погашении, сбое и пробном запуске записывается в `audit_log` (`action: "bankedReset.redeem"`, без токенов или кредитных идентификаторов); ограничения отсчитываются от этих строк, поэтому они сохраняются при перезапуске. При успешном погашении также активируется вебхук `provider.reset_redeemed`.

Стражи регрессии: `tests/unit/banked-reset-policy.test.ts`, `tests/unit/banked-reset-auto-apply.test.ts`, `tests/unit/claude-limit-reset-policy-gate.test.ts`, `tests/unit/banked-reset-history-route.test.ts`.

### Привязка сеанса (#7274)

**Область применения:** один клиентский сеанс (`X-Session-Id` / `x-codex-session-id` / `x-omniroute-session` заголовок) привязывается к одному соединению для **любого** провайдера.

**Назначение:** сохранять многошагового агента (Claude Code, aider, пользовательские агенты) в одном аккаунте между запросами, уменьшая потерю контекста при смене аккаунта и количество повторных холодных ответов 429 у провайдеров с состоянием сеанса на уровне аккаунта.

**Реализация:**

- Определение TTL: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Выбор/создание привязки: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Извлечение заголовка (обобщённо, для любого провайдера): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Таблица сохранённых привязок: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Настройка: `sessionAffinityTtlMs` (глобальный TTL в мс, значение `0` отключает функцию) — `src/lib/db/settings.ts`. Переименована из предназначенной только для Codex `codexSessionAffinityTtlMs` миграцией `124_generic_session_affinity_ttl.sql`, которая переносит ранее настроенный TTL Codex в новое значение по умолчанию.

До #7274 `resolveSessionAffinityTtlMs()` безусловно возвращала `0` для каждого провайдера, кроме `codex`, поэтому настройка TTL (и заголовки сеанса) нигде больше не действовали, хотя механизм привязки и извлечение заголовков уже не зависели от провайдера. Исправление удалило этот ранний возврат; теперь TTL единообразно применяется ко всем провайдерам после глобальной установки значения выше `0`.

Три заголовка привязки сеанса никогда не пересылаются upstream — исполнители создают собственные upstream-заголовки с нуля, а не передают клиентские заголовки напрямую, поэтому они остаются только внутренним идентификатором корреляции.

### Исключительные аренды управляемых соединений сеанса

**Область применения:** один активный управляемый HTTP-клиент/сеанс владеет одним подходящим соединением OmniRoute.

**Назначение:** обеспечить долговременное исключительное владение соединением для клиентов, которым требуется жёсткая граница маршрутизации между запросами. Это отличается от привязки к сеансу, которая является предпочтением мягкой непрерывности:
эксклюзивная аренда сохраняет состояние жизненного цикла в SQLite, обеспечивает глобальную уникальность активного владельца и активного соединения и отклоняет устаревшее поколение до отправки провайдеру.

Функция включается отдельно для каждого API-ключа. Управляемый ключ должен иметь область `lease:exclusive` и явно заданный непустой список `allowedConnections`. Любой HTTP-клиент может использовать конечную точку жизненного цикла; имя клиента, user-agent, провайдер, метод OAuth или модель не требуются. Аренда относится к соединению, а не к модели, поэтому смена модели сохраняет привязку, пока соединение остаётся обычно подходящим. Обычные правила модели, квоты, состояния здоровья, периода ожидания и списка разрешений сохраняют приоритет и могут перевести то же поколение на другое свободное подходящее соединение.

Жизненный цикл представлен запросом `POST /api/v1/session-leases` с действиями JSON `acquire`, `renew` и `release`.
Управляемые запросы инференса передают непрозрачное значение `X-OmniRoute-Lease-Owner` и точное значение `X-OmniRoute-Lease-Generation`. Владелец использует `vlo_`, за которым следуют 43 символа base64url; сохраняется только его хеш SHA-256. Каждая окончательная проверка перед отправкой также связывает идентификатор аутентифицированного API-ключа и идентификатор активного соединения. Управляющие заголовки аренды удаляются из журналов, сохраняемых снимков запросов и заголовков вышестоящего исполнителя.

Если при обычной маршрутизации имеются подходящие управляемые кандидаты, но каждый свободный кандидат занят чужой активной арендой, OmniRoute возвращает HTTP `429`, код lease-capacity-unavailable, состояние waiting-for-capacity и ограниченный `Retry-After`, рассчитанный на основе ближайшего релевантного истечения срока действия.
Обычное отсутствие подходящих кандидатов не является конфликтом аренд и сохраняет существующую семантику ошибок маршрутизации.

Связанные механизмы остаются отдельными:

- Занятость сеансов OAuth — это локальное для процесса мягкое распределение OAuth-аккаунтов.
- Семафоры аккаунтов предоставляют разрешения на параллельное выполнение запросов и завершаются после окончания запроса.
- Эксклюзивные аренды управляемых сеансов — это долговременное владение в рамках жизненного цикла с проверкой поколения.

## 3. Блокировка моделей

**Область действия:** тройка provider + connection + model.

**Область ключа по статусу:** статус ошибки определяет, в какую область блокировка записывается
(`resolveLockoutScope()` в `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — сигнал квоты или права доступа — блокируется **семейство квоты**:
  для codex — вся область `codex` / `spark` (каждая модель `gpt-5*` этого
  подключения), для других провайдеров — `getQuotaScopedModelForProvider()`.
- `404` блокирует базовую модель (`getModelLockKey()` сужает область `not_found`).
- Любой другой статус — ошибки транспорта/сервера `5xx` и собственный
  синтезированный OmniRoute статус `502`, возникающий при проверке качества, — блокирует только
  **точную** кортежную комбинацию provider/connection/model. Некорректный поток для одной модели
  не свидетельствует о квоте аккаунта; до введения этого правила один пустой ответ от
  `codex/gpt-5.6-luna` удалял из маршрутизации все модели `gpt-5*` этого подключения на 2–30 минут
  (с эскалацией), при этом его квота не затрагивалась.
- Явно указанная вызывающей стороной опция `scope` всегда имеет приоритет (Antigravity передаёт `"exact"`).

**Назначение:** не отключать целое подключение, если недоступна или ограничена квотой только одна модель.

**Примеры:**

- Провайдеры с квотой на уровне модели, возвращающие 429
- Локальные провайдеры, возвращающие 404 для одной отсутствующей модели
- Ошибки разрешений для определённых режимов/моделей провайдера (например, режимы Grok)

**Реализация:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

| `enabled`               | `false`                          | Главный переключатель — блокировка моделей **по умолчанию отключена**.            |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Статусы вышестоящей системы, считающиеся сбоем в области модели.                  |
| `baseCooldownMs`        | `120_000` (120 s)                | Начальная длительность блокировки при первом сбое.                                |
| `maxCooldownMs`         | `1_800_000` (30 min)             | Максимальная длительность увеличенного периода ожидания.                          |
| `maxBackoffSteps`       | `10`                             | Максимальное количество шагов экспоненциального увеличения задержки.              |
| `useExponentialBackoff` | `true`                           | Определяет, увеличивается ли период ожидания экспоненциально при повторных сбоях. |

Настройки сохраняются через обычное хранилище настроек и проверяются схемой настроек устойчивости;
карточка ограничивает значения `baseCooldownMs`/`maxCooldownMs`
(при этом `maxCooldownMs ≥ baseCooldownMs`) и `maxBackoffSteps`.

**Восстановление за счёт снижения после успеха:** восстановление происходит **не только** по
истечении таймера. Успешный ответ уменьшает счётчик сбоев модели, поэтому восстановившаяся
в середине периода модель прекращает наращивать задержку (и разблокируется) до истечения таймера.
При успешном целевом сочетании `open-sse/services/combo.ts` вызывает `decayModelFailureCount()`
(`open-sse/services/accountFallback.ts`), которая **уменьшает вдвое** сохранённый
`failureCount` (`Math.floor(failureCount / 2)`); когда он достигает `0`, запись о блокировке
удаляется полностью. Соответствующая функция `recordModelLockoutFailure()` увеличивает счётчик
(и увеличивает период ожидания) при сбоях в пределах окна эскалации. Это снижение после успеха
дополняет обычное истечение таймера — любой из этих путей может повторно включить модель.

**Состояние:** блокировки хранятся **в памяти** (в `Map` для каждого процесса, содержащих `ModelLockoutEntry`, с ключами `provider:connectionId:model`; блокировки с областью действия exact — с ключами `provider:connectionId:exact:model`), а не сохраняются в
БД — при перезапуске они теряются. _Настройки_ сохраняются; активное _состояние_ блокировки является эфемерным.

## 4. Управление параллелизмом через общую квоту (v3.8.36)

Учетные записи подписок (GLM, MiniMax и т. д.) часто принимают только ~1–3
параллельных запроса; превышение этого числа вызывает 429 и периоды
охлаждения. Особенно остро это проявляется в комбинациях с **общим
использованием квоты** (`qtSd/…`), где несколько API-ключей используют одну
учетную запись вышестоящего сервиса. Три уровня защиты не позволяют перегрузить
общую учетную запись.

### Ограничение параллелизма для подключения (`max_concurrent`)

Для каждого подключения провайдера можно указать верхний предел
`max_concurrent`
(`provider_connections.max_concurrent`, задается в модальном окне подключения,
через API или в БД). Оставьте поле пустым, чтобы не устанавливать ограничение.
Это единственный параметр, управляющий описанным ниже уровнем сериализации —
установите его равным фактическому параллелизму учетной записи (например, для
GLM ~1, для MiniMax ~2).

### Ограничения параллелизма для моделей (`modelConcurrency`)

Подключение также может задавать точные верхние пределы параллелизма для
отдельных моделей в своей карте `rateLimitOverrides`:

```json
{
  "rateLimitOverrides": {
    "maxConcurrent": 4,
    "modelConcurrency": { "glm-5": 1, "glm-4.7": 3 }
  }
}
```

Задайте это значение в модальном окне подключения (**Переопределения лимитов
скорости → Ограничения параллелизма для моделей**, по одной паре
`model=cap` в строке) или через
`PATCH /api/providers/[id]` с той же структурой JSON. Основные особенности:

- **Общее для подключения и для конкретной модели:** `maxConcurrent` остается
  общим для всего подключения ограничением. Если применимы оба ограничения,
  оба разрешения получаются атомарно в одном составном шлюзе
  (`global → provider → account → model`); фактическое поведение определяется
  более строгим применимым лимитом.
- **Точное совпадение ключа модели:** ключ — это строка модели, переданная
  исполнителю после разрешения маршрутизации, обычно идентификатор модели
  вышестоящего сервиса без префикса (`glm-5`), а не клиентский псевдоним
  `provider/model` (`zai/glm-5` не соответствует `glm-5`). Значения должны быть
  положительными целыми верхними пределами числа параллельных запросов.
- **Локальная постановка в очередь без обнаружения:** избыточные запросы
  помещаются в локальную очередь с существующей семантикой очереди и тайм-аутов
  (типизированные ошибки допуска `SEMAPHORE_TIMEOUT` /
  `SEMAPHORE_QUEUE_FULL`). OmniRoute не обнаруживает и не выводит политику
  вышестоящего сервиса — он применяет точные ограничения, настроенные
  оператором. Переполненный шлюз модели никогда не отключает провайдера и не
  создает постоянную блокировку модели; поведение при 429, охлаждении и
  резервном переключении на вышестоящем уровне остается резервным механизмом
  обработки ошибок.
- **Область действия для каждого подключения и процесса:** ограничения
  применяются отдельно к каждому подключению к БД и хранятся в памяти, поэтому
  два подключения, использующие один и тот же API-ключ вышестоящего сервиса, не
  координируют работу друг с другом.
- **Без настройки — без изменений:** отсутствие карты (или пустое поле в
  панели управления) не добавляет шлюз для модели. Пример конфигурации без
  утверждения какого-либо универсального ограничения для провайдера:

```text
glm-5=1
glm-4.7=3
```

### Сериализация запросов с общим использованием квоты

Когда диспетчеризация с общим использованием квоты направляет запрос в
подключение, для которого задан положительный `max_concurrent`, параллельные
запросы к этой **учетной записи** сериализуются через семафор для каждого
подключения (ключ `qsconn:<connectionId>`): избыточные запросы **ожидают в
очереди**, а не перегружают учетную запись. Механизм работает в режиме
**fail-open** — при заполненной очереди или истечении тайм-аута выполнение
продолжается без получения слота, вместо того чтобы отклонять запрос, который
можно диспетчеризировать. Переключатель находится в
**Настройки → Отказоустойчивость → Параллелизм для каждого подключения с
общим использованием квоты**
(`resilienceSettings.quotaShareConcurrencyLimit.enabled`, по умолчанию включен).
Без ограничения `max_concurrent` поведение не меняется.

> Шлюз маршрутизации общего использования квоты
> (`selectQuotaShareTarget`, DRR + P2C) также работает в режиме
> fail-open и лишь _снижает приоритет_ подключения, достигшего лимита. При
>
> > наличии пула из одного подключения он не может жестко ограничить нагрузку,
> > поэтому именно этот семафор фактически предотвращает перегрузку.

### Повторная попытка комбинации с учетом периода охлаждения

Для каждой стратегии комбинации (если она включена) запрос, который привел бы к
429 при коротком временном периоде охлаждения, ожидает его окончания и повторно
диспетчеризируется вместо возврата 429 — это охватывает окна TPM/RPM класса
Gemini (примерно 60 секунд в `retry-after`) в комбинациях из нескольких моделей,
например когда оба назначения комбинации из двух моделей достигают лимита
частоты для модели. Поведение ограничивается параметром `comboCooldownWait`
(`enabled`, `maxWaitMs`, `maxAttempts`, `budgetMs`) в разделе
**Настройки → Отказоустойчивость**. Ожидание никогда не выполняется для
`quota_exhausted` (блокировка до полуночи) или причин, связанных с
аутентификацией/отсутствием.

Комбинация может отключить это поведение с помощью
`config.comboCooldownWaitEnabled: false`. Только литеральное значение `false`
отключает общее ожидание комбинаций (ожидание периода охлаждения после
диспетчеризации и ожидание открытия схемы/снятия блокировки модели перед
диспетчеризацией), а также расширение минимального значения тайм-аута за счет
бюджета ожидания. Отсутствующее значение или `true` сохраняет глобальную
политику; `true` не может включить глобально отключенное ожидание. Явно
заданный `targetTimeoutMs` имеет приоритет. Это отключение не меняет отдельное
ожидание перед диспетчеризацией для встроенной фиксации хода native-Codex.

Тот же шлюз охватывает случай перед диспетчеризацией (#16319): когда все
назначения комбинации пропускаются до первой попытки, поскольку их модель
находится в кратковременной временной блокировке, путь с нулевым числом попыток
ожидает снятия блокировки в рамках тех же ограничений и повторно
диспетчеризирует запрос вместо ответа без подсказки
`503 ALL_TARGETS_SKIPPED`. Когда ожидание невозможно (достигнут предел,
исчерпано число попыток или бюджет либо функция отключена), итоговый ответ
повышается до `429 rate_limit_error` и содержит `retry_after` / `reset_at` из
самого раннего истечения временной блокировки; блокировки квоты,
аутентификации и отсутствующей модели по-прежнему возвращают ответ 503 без
подсказки.

```text
#16319 · comboCooldownWait · pre-dispatch (attempts = 0)
all targets skipped + transient model lockout:
  enabled ∧ 0 < waitMs ≤ maxWaitMs ∧ attempt < maxAttempts ∧ budgetLeftMs ≥ waitMs
    → wait → re-dispatch
  wait = false → HTTP 429 rate_limit_error
  retry_after / reset_at ← earliest transient lock expiry
quota_exhausted / auth_error / not_found / not_found_local:
  no transient hint → HTTP 503 ALL_TARGETS_SKIPPED
```

## 5. Контроль приёма очереди запросов (v3.8.49 · issue #6593)

**Область применения**: локальная очередь ограничения частоты запросов на уровне пары «провайдер+подключение» (`open-sse/services/rateLimitManager.ts`, на основе Bottleneck), на один уровень ниже трёх механизмов, описанных выше.

**`maxWaitMs` ограничивает ожидание в очереди; `executionMaxWaitMs` ограничивает выполнение.**
Эти два параметра намеренно разделены, и ни один не подпитывает другой.

`resilienceSettings.requestQueue.maxWaitMs` — это **бюджет ожидания в очереди**: он покрывает ожидание слота у провайдера и последующее пребывание в состоянии QUEUED, а его таймер сбрасывается в тот момент, когда задание покидает QUEUED и начинает выполняться (`rateLimitManager.ts`, `wrappedFn`). Запрос, превысивший этот бюджет, никогда не доходит до апстрима. Значение по умолчанию — 30000 мс, задаётся константой `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS` в `src/lib/resilience/settings.ts` и фиксируется тестом `tests/unit/ratelimit-admission-control-6593.test.ts`, так что изменение этого значения окрасит тест в красный, а не оставит этот абзац незаметно устаревшим.

`resilienceSettings.requestQueue.executionMaxWaitMs` — это то, что Bottleneck получает как `expiration` задания, таймер которого запускается только после диспетчеризации. Это страховка для исполнителей без собственного таймаута апстрима; если собственный таймаут начала fetch у исполнителя больше, значение повышается до него, поэтому оно не может оборвать корректный ответ, уже находящийся в процессе получения. Значение по умолчанию — 600000 мс (10 мин).

Передача бюджета очереди в `expiration` — именно то, что раньше убивало неинкрементальные шлюзы посреди выполнения: они законно работают минутами до получения первых байтов. Именно поэтому истечение expiration выдаётся как `code: "RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504), тогда как бюджет очереди несёт код таймаута очереди. Любой из них можно переопределить через `RATE_LIMIT_MAX_WAIT_MS` / `RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (переменные окружения) или панель управления (**Настройки → Resilience**). При нормализации оба значения ограничиваются диапазоном 1 мс – 24 ч.

**Приоритет для обоих параметров:** переменная окружения задаёт лишь значение _по умолчанию_. Значение, сохранённое в `resilienceSettings.requestQueue` (через панель управления / API-патч, хранится в `key_value`), имеет приоритет над ним, а заданные для конкретного подключения `rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` — над ним. Поэтому установка переменной окружения на развёртывании, где уже есть сохранённое значение, ничего не меняет — вместо этого очистите или обновите сохранённую настройку.

Время пребывания в очереди ограничено `maxWaitMs`; а `maxQueueDepth` (ниже) ограничивает, сколько вызывающих сторон может одновременно находиться в очереди.

**Повторы, указанные в теле ответа: пейсинг или блокировка.** Тело ответа 429 может само указывать время ожидания (Gemini `RetryInfo.retryDelay`, текст «retry after Ns»), которое считывает `updateFromResponseBody`. Ожидание, укладывающееся в `maxWaitMs` подключения, — это пейсинг: лимитер опустошает свой резервуар на это время, и вызовы из очереди диспетчеризуются, когда он пополняется. Ожидание дольше `maxWaitMs` — не то, что очередь может «отсидеть»: на исчерпанную дневную квоту Gemini отвечает `retryDelay: "86399s"`. Передаваемый дальше заголовок `Retry-After` на пересобранном ответе 429 (#16528) уже заставляет движок фолбэка блокировать модель на это окно, но пауза лимитера на то же время всё равно затормозила бы любой вызов, попавший к ключу раньше времени (например, после сброса устойчивости), на весь `maxWaitMs`. Когда такое ожидание приходит из типизированной детали Google `RetryInfo` (с происхождением `google_rpc_retry_info`), а лимитер ключа уже привязан к модели (см. `getLimiterKey`), ответ 429 вместо этого превращается в блокировку модели на этом подключении (`lockModelForLongBodyRetry` в `open-sse/services/rateLimitManager/bodyRetryPause.ts`, с потолком в 24 ч), а лимитер остаётся без паузы. Выбор аккаунта пропускает такую модель через `isModelLocked()`, как и преддиспетчерская проверка комбо для целей, закреплённых за этим подключением. В antigravity, где лимитер работает на семейство квот, блокировка ставится на конкретную модель — как и остальные его квотные блокировки. Имя, запрошенное клиентом, тоже блокируется, если алиас разрешил его в эту модель, поскольку эти проверки используют запрошенное имя; блокируется оно точечно (`lockExactModel`), так что алиас, пересекающий границу семейства квот antigravity или области codex, никогда не заблокирует своё собственное. Подсказка в свободной форме, нетипизированный `retryDelay` или лимитер, общий для всего подключения, сохраняют паузу. Когда лимитер, только что пересобранный на пути обработки 429, всё же уходит на паузу, вызывающая сторона, у которой оставшееся время в очереди истекает раньше, чем пауза, немедленно отклоняется с кодом таймаута очереди (`checkLimiterPause`), а не ждёт истечения этого времени; зафиксированный момент окончания привязан к точке до создания лимитера — там, где Bottleneck запускает свой таймер пополнения, — и любое последующее изменение резервуара о нём «забывает». Покрыто тестами `tests/unit/rate-limit-long-body-retry-lockout.test.ts` и `tests/unit/rate-limit-body-retry-pause.test.ts`.

**`maxQueueDepth` — опциональный лимит приёма (новое).** `resilienceSettings.requestQueue.maxQueueDepth` ограничивает, сколько запросов может одновременно находиться в очереди (ещё не диспетчеризованных) для одной пары «провайдер+подключение». Когда очередь уже содержит `maxQueueDepth` запросов, новый запрос быстро отклоняется с типизированной ошибкой `code: "RATE_LIMIT_QUEUE_FULL"` **до того**, как он достигнет `limiter.schedule()`, — поэтому отказ обходится дёшево и происходит раньше любой последующей работы по сжатию промпта / трансляции для этого запроса. По умолчанию `0` = отключено, что сохраняет прежнее поведение с неограниченной очередью; допустимый диапазон 0–100000. Переопределяется через `RATE_LIMIT_MAX_QUEUE_DEPTH` (переменная окружения) или `resilienceSettings.requestQueue.maxQueueDepth` (панель управления / API-патч).

Сама проверка приёма — чистая функция (`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), поэтому её можно покрыть модульными тестами без реального лимитера Bottleneck.

> RFC, из которого возникло #6593, также предлагал флаг
> `bypassCompressionOnRateLimit`. Конвейер `open-sse/services/compression/` в
> этом репозитории — это сжатие промпта/контекста исходящего запроса к LLM
> (`chatCore.ts`, в районе блока `resolveCompressionSettings`/`selectCompressionStrategy`),
> а не HTTP-сжатие ответов для синтезированных тел 429 — подходящего пути в коде
> для буквального флага обхода не существует. Этот шаг сжатия промпта к тому же
> сейчас выполняется _до_ `withRateLimit()` в конвейере запроса, поэтому
> переупорядочивание, чтобы пропускать его при отклонении из-за переполненной
> очереди, — отдельное, более масштабное изменение, выходящее за рамки данного
> issue; оно намеренно **не** реализовано здесь и оставлено на будущее — на
> случай, если выигрыш в экономии CPU оправдает риск переупорядочивания.

### Защитный механизм автоматического включения rate-limit и защита подключений (`rateLimitProtection`)

**Защитный механизм автоматического включения** (`resilienceSettings.requestQueue.autoEnableApiKeyProviders`, по умолчанию `true`):
По умолчанию OmniRoute автоматически включает защиту очередью от превышения лимита запросов для всех активных подключений провайдеров с API-ключом (`getProviderCategory(provider) === "apikey"`). Это гарантирует, что входящие запросы к чувствительным к лимитам upstream-ключам API ставятся в очередь и троттлятся через Bottleneck, а не приводят к всплеску upstream-ошибок 429. Защитный механизм можно переопределить через переменную окружения `RATE_LIMIT_AUTO_ENABLE` (`false`/`0`/`off` отключает, `true`/`1`/`on` принудительно включает), которая имеет приоритет над сохранённой настройкой дашборда (**Настройки → Отказоустойчивость** / `PATCH /api/resilience`).

**Семантика `rateLimitProtection` для отдельного подключения:**
Защита от rate-limit для отдельных подключений отслеживается через булево поле `rateLimitProtection` на подключениях провайдеров (сохраняется как `rate_limit_protection` в SQLite):

- **Явно включено (`rateLimitProtection === true`)**: Защита от rate-limit явно включена для этого подключения, независимо от категории провайдера и от того, активен ли защитный механизм автоматического включения.
- **Явно выключено (`rateLimitProtection === false`)**: Отключает явную защиту, но **не** выводит активное подключение с API-ключом из-под действия глобального защитного механизма автоматического включения. В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значения `false` и `undefined` эквивалентны: только `rateLimitProtection === true` трактуется как явное переопределение. Если `rateLimitProtection` равен `false` (или не задан), активное подключение с API-ключом всё равно соответствует условию автоматического включения и остаётся под защитой от rate-limit.
- **Отсутствие отказа для отдельного подключения**: Оператор в настоящее время не может задать «это конкретное активное подключение с API-ключом должно работать без защиты очередью от rate-limit», сохраняя автоматическое включение активным для остальных. Чтобы полностью работать с подключениями с API-ключами без очередей rate-limit, защитный механизм необходимо отключить глобально (`RATE_LIMIT_AUTO_ENABLE=false` или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`).

**Поддерживаемые пути записи:**

- **`POST /api/rate-limits`**: Поддерживаемый путь записи для управления — переключение `rateLimitProtection` для подключения (`{ connectionId: string, enabled: boolean }`). Вызов с `enabled: true` включает явную защиту; вызов с `enabled: false` снимает явную защиту (при этом активные подключения с API-ключами остаются под действием глобального защитного механизма, если автоматическое включение активно).
- **`PUT /api/providers/[id]`**: Намеренно **не** принимает и не переключает `rateLimitProtection` (#11278). Обновление метаданных подключения провайдера через `PUT /api/providers/[id]` никогда не изменит сохранённое состояние защиты от rate-limit.

## 6. Контроль пропускной способности медленного потока (#9709).

Дополнительная защита `resilienceSettings.streamRecovery.throughputWatchdog` обнаруживает восходящий поток, который все еще отправляет фрагменты, но выдает выходные данные помощника ниже настроенной скорости полезного вывода. Он намеренно отличается от тайм-аута простоя: сигналы пульса и метаданные не сбрасывают ни таймер, ни прогресс. Он также отличается от крайнего срока жесткой попытки (#9153), который остается абсолютным потолком безопасности независимо от качества продукции.

Сторожевому таймеру требуется период прогрева, за которым следует полное скользящее окно, прежде чем он сможет прервать работу. Он подсчитывает текстовые отклонения от выходных событий API «Завершения и ответы в чате» (консервативный байтовый прокси UTF-8 ), игнорирует события «только использование» и «пустые» события, а также приостанавливает обработку решений, пока активны события вызова инструмента или рассуждения. По умолчанию он отключен и может быть включен с помощью `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true` (это значение env задает только — по умолчанию, а сохраненное логическое значение `resilienceSettings.streamRecovery.throughputWatchdog.enabled` выигрывает; см. примечание о приоритете env-vs-dashboard в верхней части этого руководства); окно, прогрев, минимальная скорость и минимальный измеримый результат ограничены обычным слоем нормализации настроек устойчивости.

Если этот параметр включен, прерывание сторожевого таймера применяется только к активной попытке восходящего потока. Прежде чем появятся какие-либо видимые для клиента байты, существующий путь раннего восстановления той же учетной записи может повторно открыть попытку. После фиксации поток никогда не воспроизводится вслепую; только существующий контракт на продолжение безопасного промежуточного потока может добавить суффикс. Финализация остается однократной, поэтому учет использования и выпуск семафоров не дублируются.

## 7. Повторная фиксация статуса upstream (ошибки с неверно указанной квотой)

**Область применения:** один upstream-шлюз, который сообщает о временном исчерпании квоты с неверным HTTP-статусом.

**Назначение:** исправить вводящий в заблуждение статус **ДО** классификации, чтобы downstream-потребители (механизм fallback, агрегация combo, ответ клиенту) видели истинный характер сбоя, допускающий повторную попытку.

Некоторые шлюзы сигнализируют о ВРЕМЕННОМ исчерпании квоты HTTP-статусом, не допускающим повторную попытку. `agentrouter.org` возвращает `403` (иногда `400`) с телом на китайском языке (`用户额度不足` / `额度不足`) вместо стандартного `429`. Клиенты вроде Claude
Code считают `403` постоянной ошибкой и прерывают сессию, а без исправления механизм fallback классифицировал бы её как `AUTH_ERROR`, а не как событие, связанное с квотой.

**Реализация:**

- Реестр + matcher: `open-sse/config/upstreamStatusRestatement.ts` — список правил для каждого провайдера (`{id, fromStatuses, toStatus, textMarkers, excludeMarkers, defaultRetryAfterMs}`), сопоставляемых через `applyStatusRestatement()`.
- Место вызова: блок `providerFailure:` в `open-sse/handlers/chatCore.ts` (примерно строка 3654), сразу после того, как `parseUpstreamError()` разбирает upstream-ответ с HTTP-статусом ошибки (`!providerResponse.ok`), и до запуска любой классификации, поэтому все downstream-потребители видят исправленный статус. Ошибки, встроенные в поток SSE со статусом `200`, проходят по отдельному, более позднему пути разбора потока и сегодня **не** покрываются этим hook — это известное ограничение, которое пока не требуется для неверного статуса agentrouter (там ошибка проявляется как HTTP-статус ошибки).
- Возможность повторной попытки: `429` входит в `RETRY_AFTER_ELIGIBLE_STATUSES` (`open-sse/services/combo/unavailableRetryGate.ts`), поэтому для исправленной ошибки появляется настоящее окно повторной попытки вместо отображения неработоспособного `403`.
- Синтетический `60s` `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`) — это лишь значение, которое исправленный ответ сообщает **клиенту**; оно само по себе не является внутренней длительностью cooldown/блокировки соединения — она отдельно определяется механизмом, фактически обрабатывающим исправленную ошибку (эскалирующий backoff Connection Cooldown, §2, с базовым значением `3s` для провайдеров с API-ключами; или Model Lockout, §3, для провайдеров с квотой на модель, таких как agentrouter). Внутренне router может стать готовым к повторной попытке раньше, чем истечёт рекламируемое клиенту окно в 60s — это намеренно предусмотренный запас, а не ошибка.

Постоянные ошибки (у agentrouter — `无权访问模型`, то есть отсутствие доступа к этой модели) **НИКОГДА** не подвергаются повторной фиксации: `excludeMarkers` отменяет действие правила даже при совпадении `textMarkers`, поэтому ошибка сохраняет исходный статус и ничто не будет бесконечно повторять попытки. Соответствующее правило классификации провайдера (`agentrouter-model-access-denied` в `open-sse/config/providerErrorRules.ts`: `reason: "auth_error"`, `scope: "model"`, объявленный базовый cooldown `6h`) проверяется в `checkFallbackError` (`open-sse/services/accountFallback.ts`) _до_ общего раннего возврата для категории apikey `FORBIDDEN`, при условии `honorsRuleLockScope(provider)` (#10334 — в настоящее время эксклюзивно для agentrouter через allowlist `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в
`providerErrorRules.ts`). Объявленный правилом cooldown в 6h передаётся через `fallbackResult.baseCooldownMs`, но при этом продолжает использовать существующий путь блокировки на уровне модели (`lockModelIfPerModelQuota()` /
`recordModelLockoutFailure()`, не изменённый в #10334, за исключением источника cooldown): он ограничивается значением `mlSettings.maxCooldownMs` оператора (по умолчанию `1_800_000ms` / 30min), как и любая другая блокировка модели, а _сохраняемая причина блокировки_ остаётся прежней жёстко заданной `"forbidden"`, а не `"auth_error"` из правила — полностью учитывается только длительность cooldown, но не строка причины. Само соединение остаётся активным; соседние модели в том же соединении не затрагиваются.

Исправленные ошибки квоты (`额度不足`) в production достигают правила провайдера (`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`, `scope:
"connection"`, без собственного объявленного cooldown — применяется масштабированный backoff по умолчанию уровня persistence). Начиная с #10334, `scope` в `ProviderErrorRuleMatch` ИСПОЛЬЗУЕТСЯ сквозным образом, но **только** для провайдеров из allowlist `HONORS_RULE_LOCK_SCOPE_PROVIDERS` (`providerErrorRules.ts` — сегодня это только `"agentrouter"`, с проверкой через `honorsRuleLockScope()`). Для всех остальных провайдеров `scope` остаётся информационным, как и до #10334.
`checkFallbackError` передаёт scope совпавшего правила как
`fallbackResult.ruleScope`; `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) — это общий guard, подтверждающий, что
`ruleScope` действительно безопасно учитывать как сигнал, действующий на всё соединение и допускающий самостоятельное восстановление (scope `"connection"`, reason `quota_exhausted`, никогда не `permanent` и не `creditsExhausted` — защита от будущего сочетания в правиле scope `"connection"` с постоянным состоянием аккаунта). Его вызывают два потребителя:

- **Сохранение состояния** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  вместо перехода в ветку блокировки passthrough-провайдера **для каждой модели**
  (agentrouter использует `passthroughModels: true` → `hasPerModelQuota()`
  возвращает `true`), применяется **временная задержка для подключения** —
  `testStatus: "unavailable"` + `rateLimitedUntil`, но никогда не устанавливается
  терминальный статус (`credits_exhausted`/`banned`/`expired`) — поэтому подключение
  автоматически восстанавливается после истечения задержки, а не требует ручного
  сброса учётных данных.
  Пропускается для подключений с `disableCooling: true` (#2997): этот отказ
  от охлаждения приводит к переходу в блокировку для каждой модели
  (задокументированный компромисс — см. комментарий в коде над веткой).
- **Маршрутизация комбинации в рамках одного запроса** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): тот же защитный механизм
  добавляет подключение во внутриии́зменяемое множество `exhaustedConnections`,
  ключом которого служит `${provider}:${connectionId}`. При этом пропускается
  только оставшаяся цель SAME-REQUEST, которая _сама уже содержит этот точный
  `connectionId`_ в собственном объекте цели (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` перед поиском в `exhaustedConnections`) — обычная комбинация
  со списком моделей, в которой соседние цели не содержат собственного
  закреплённого `connectionId`, а он разрешается только для каждой отправки
  из заголовка ответа `X-OmniRoute-Selected-Connection-Id`, никогда не
  достигает такого совпадения ключей. В этом распространённом случае реальная
  защита от повторного использования только что исчерпавшегося аккаунта
  оставшейся частью маршрута — это НЕ данное множество, а описанный выше
  уровень сохранения состояния (`rateLimitedUntil` подключения теперь находится
  в будущем) в сочетании с тем, что этот же защитный механизм не добавляет
  провайдер в `transientRateLimitedProviders` для данной ошибки (см. раздел
  "Двухэтапная схема" и комментарий в коде для ветки
  `isAgentrouterConnectionQuotaScope` в `targetExhaustion.ts`): если оставить это
  множество без отметки, принудительное разрешение `allowRateLimitedConnection`
  в `combo.ts` (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) НЕ
  срабатывает для оставшихся целей провайдера, поэтому фильтр
  `rateLimitedUntil` при выборе учётных данных (`src/sse/services/auth.ts:1238`)
  работает в обычном режиме, и оставшаяся часть маршрута либо выбирает другое,
  всё ещё доступное подключение agentrouter, либо завершается ошибкой
  об отсутствии доступных учётных данных — она не принуждает повторно выбрать
  подключение, для которого эта ветка только что установила задержку.

### Двухэтапная схема: повторное формирование статуса, затем классификация

Повторное формирование статуса (`upstreamStatusRestatement.ts`) и правила
классификации провайдеров (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) — это отдельные реестры, которые оба используют
идентификатор провайдера и текстовые маркеры в качестве ключей, но выполняются
в разных местах и служат разным целям: повторное формирование статуса
заранее изменяет HTTP-статус в `chatCore.ts`; правила классификации выбирают
резервный `reason` и область блокировки `scope`
(`model` / `provider` / `connection`) внутри `checkFallbackError()`
(`open-sse/services/accountFallback.ts`).

Правила классификации видят полный **текст** ошибки (необходимый для поиска
маркеров в теле, например `额度不足`) только для провайдеров, перечисленных
в списке разрешённых `FULL_TEXT_RULE_PROVIDERS` в `providerErrorRules.ts`,
— в настоящее время это только `"agentrouter"`. Для каждого другого
**встроенного** провайдера из каталога `checkFallbackError` передаёт
`getProviderErrorRuleMatch` только структурированную ошибку (`{code, type}`),
чего достаточно для правил на основе заголовков/статуса/кода, но недостаточно
для поиска маркеров в тексте тела. Вспомогательная функция
`resolveRuleMatchBody()` выполняет этот выбор: полный текст ошибки для
провайдеров из списка разрешённых, структурированная ошибка в остальных
случаях. Добавление **встроенного** провайдера в `FULL_TEXT_RULE_PROVIDERS`
является явным разрешением для конкретного провайдера — этот механизм
существует для того, чтобы путь по умолчанию для каждого провайдера,
не входящего в список, оставался побайтно неизменным.

`scope` правила (`model` / `provider` / `connection`) — это отдельное
разрешение, не связанное с `FULL_TEXT_RULE_PROVIDERS`: `checkFallbackError`
только выставляет его в `fallbackResult.ruleScope`, а последующие компоненты
учитывают его не только как информационную метку лишь для провайдеров из
списка `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в том же файле (проверка выполняется
через `honorsRuleLockScope()` — сегодня это только `"agentrouter"`). См. выше
раздел "Ошибки квоты после повторного формирования статуса", где описано,
что именно делает совпадение `scope: "connection"`, если провайдер входит
в этот список разрешённых.

**#11104 — правила, объявленные оператором, обходят оба списка разрешённых.**
Оператор может объявить правило для конкретного провайдера во время выполнения
через `settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`),
не изменяя этот файл. Проверка операторского правила через
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — списки,
предназначенные для защиты поведения **правил по умолчанию** встроенных
провайдеров из каталога, — сделала бы механизм настроек неработающим для
всех провайдеров, кроме уже перечисленных в них, поскольку объявление
правила уже является явным разрешением со стороны оператора.
`resolveRuleMatchBody()` и `honorsRuleLockScope()` сначала проверяют
`hasOperatorRuleForProvider()`: провайдер с операторским правилом получает
необработанный текст ошибки, а объявленный для него `scope` учитывается
независимо от того, присутствует ли провайдер в каком-либо из этих списков.

**Правила, объявленные оператором** (`OperatorProviderErrorRule`): каждое
правило имеет необязательное поле `status` и необязательное поле `match`
(обычная подстрока текста ошибки без учёта регистра, но не RegExp, поэтому
она не может привести к ReDoS), и должно задавать хотя бы одно из двух.
Если заданы оба поля, они объединяются условием AND; пропущенное поле
соответствует любому значению, поэтому `{match: "insufficient_quota"}`
совпадает с любым статусом, содержащим этот код. Используется первое
совпавшее правило. `cooldownMs` допускает значение до 30 дней;
общее количество правил — не более 50.

**Общие значения по умолчанию** (`settings.providerErrorDefaults`, включаются явно, задаются через
`setOperatorProviderErrorDefaults`): `{[provider]: {cooldownMs, scope?, reason?}}`
с `cooldownMs` от 1 минуты до 30 дней. Значение по умолчанию применяется только
если ни одно правило оператора и ни одно встроенное правило каталога не подошло, и
только к ошибкам 402, 403, 408, 429 и 5xx. Ошибки формы запроса (400, 404, 409,
413, 422) и отдельные ошибки 401 сохраняют собственную обработку. Если
`reason` не задан явно, причина определяется по статусу так же, как это делает
`classifyError`. Объявление значения по умолчанию считается правилом оператора для
`hasOperatorRuleForProvider()`, поэтому учитывается его `scope` (по умолчанию
`"connection"`). Эффективная задержка значения по умолчанию — большее из
`cooldownMs` и собственной подсказки провайдера о повторной попытке (`Retry-After`,
`x-ratelimit-reset` или подсказка о сбросе в теле — та же подсказка, которую
движок учитывает, когда включена настройка задержки соединения "use upstream retry hints"),
поэтому значение по умолчанию может увеличить короткую подсказку upstream, но
никогда не сократит фактическое время сброса. Явное правило оператора сохраняет
свой точный `cooldownMs`. Ни правило, ни значение по умолчанию не обходят
защиты от задержки соединения в `markAccountUnavailable`: активная, более длинная
задержка никогда не сокращается, а терминальный статус никогда не перезаписывается.
Встроенные текстовые детекторы, которые запускаются раньше в `checkFallbackError`
(исчерпаны кредиты, дневная квота, деактивированный аккаунт), по-прежнему имеют
приоритет для соответствующих им фраз.

**Известный пробел — `providerRuleRegistry` никогда не проверяется для HTTP 400.**
Ветка `BAD_REQUEST` в `checkFallbackError` полностью классифицирует статус 400
с помощью собственных массивов шаблонов (`MODEL_ACCESS_DENIED_PATTERNS`,
`CONTEXT_OVERFLOW_PATTERNS` и т. д. в `accountFallback.ts`) и возвращает результат
до того, как будет достигнута расположенная выше ветка
`configuredRule`/`getProviderErrorRuleMatch`. Встроенное правило каталога (или
правило оператора) со `status: 400` синтаксически допустимо, но никогда не
сработает. Сегодня ни одно существующее правило не нацелено на 400, поэтому в
production ничего не затронуто — однако для будущего правила 400 сначала
потребуется изменить эту ветку. Это более крупное изменение, чем добавление
правила (оно повторно классифицирует 400 для каждого провайдера, уже полагающегося
на поведение массивов шаблонов), и оно выходит за рамки добавления правила для
одного провайдера.

### Добавление нового шлюза, неверно сообщающего о квоте

1. Зарегистрируйте один массив правил в `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Значения `textMarkers`
   должны быть специфичны для провайдера; никогда не используйте повторно
   общие английские фразы, пересекающиеся с

   для ошибок конкретной модели). Этот шаг действует в production только для
   провайдеров, чьим правилам нужен полный текст ошибки (маркеры в теле): добавьте
   идентификатор провайдера в `FULL_TEXT_RULE_PROVIDERS` в том же файле —
   иначе `checkFallbackError` передаст правилу только структурированную ошибку

   `markAccountUnavailable()` (`src/sse/services/auth.ts`) и
   `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`); без этого `scope`
   по-прежнему передаётся через `fallbackResult.ruleScope`, но ничего не делает.
3. Добавьте модульные тесты по образцу
   `tests/unit/upstream-status-restatement.test.ts` и
   `tests/unit/agentrouter-error-rules.test.ts` (включая проверки

   разрешённых провайдеров, тест, подтверждающий, что `resolveRuleMatchBody()`
   возвращает полный текст только для этого провайдера).

Изменения в `chatCore.ts`, `classifyError` или combo не требуются.

#### Блокировка по корзине исходящего трафика (#10880)

Провайдеры в `EGRESS_BUCKETED_LOCK_PROVIDERS` (семейство opencode) считаются
upstream с группировкой по IP (бесплатный уровень opencode группируется по IP, а
не по аккаунту — см. #9611): статус 429, классифицированный как
`quota_exhausted` **или** `rate_limit_exceeded`, устанавливает задержку для каждого
соединения семейства из списка разрешённых провайдеров, чей последний известный
исходящий IP совпадает с IP неудачного соединения, ещё до того, как ротация
попробует их
— это позволяет избежать N-1 гарантированно неудачных вызовов upstream (по той же
схеме, что и #10460/#10525). `rate_limit_exceeded` включён намеренно: на пути
`markAccountUnavailable` специфичные для opencode правила никогда не срабатывают
(в `checkFallbackError` не передаются заголовки/тело, а opencode не входит в
`FULL_TEXT_RULE_PROVIDERS`), поэтому ответ 429, тело которого содержит текст о
квоте подписки ("monthly usage limit reached"), классифицируется как
`quota_exhausted` резервным обработчиком текста квоты
(`buildSubscriptionQuotaFallback`, `accountFallback.ts`; задержка 1 ч.) до того,
как будет достигнуто правило `status_429`, — тогда как ответ 429 без текста о
квоте (обычное ограничение частоты) классифицируется через правило `status_429`
как `rate_limit_exceeded` и также устанавливает задержку для семейства IP. Честные
ограничения:

- **В режиме best-effort**: блокировка получает последний известный `egress_ip` соединения из `proxy_logs` (окно 24 ч, синхронно, без кэша). Холодный кэш (IP выхода ещё ни разу не проверялся) или отсутствие строки → завершающее ошибкой соединение всё равно переводится веткой в период охлаждения (записывается как и сейчас), просто ни одно соседнее соединение не блокируется.
- **Никогда не финальное состояние**: период охлаждения — это обновляемое окно квоты
  (`testStatus: "unavailable"`); постоянное состояние никогда не выводится из сигнала на уровне IP. Соединения с `disableCooling` полностью пропускают эту ветку.
- **Для семейства из списка разрешённых меняется гранулярность блокировки**: это изменение области действия, а не просто оптимизация для соседних соединений. opencode — это провайдер `passthroughModels`, поэтому до этой ветки ошибка 429 приводила к блокировке на уровне MODEL; теперь она приводит к периоду охлаждения соединения — в том числе для оператора, использующего единственное соединение без каких-либо соседних. Именно такую гранулярность уже объявляет корректной таблица правил opencode (`scope: "connection"`, `providerErrorRules.ts`), однако до сих пор она не применялась, поскольку opencode не входит в `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Ветка сама записывает период охлаждения и `backoffLevel` завершающегося ошибкой соединения, по аналогии с веткой agentrouter с областью действия соединения, и возвращает управление — блокировка на уровне модели и расположенный ниже общий путь никогда не достигаются.
- **Комбинации включены**: как и ветка agentrouter, эта область действия намеренно игнорирует понижение `persistUnavailableState`/`isCombo`, которое вызывающий комбинацию применяет к ошибке 429. Блокировка на уровне модели — не более слабая форма этой области действия, а неправильная единица: она ничего не говорит об исчерпанном IP, поэтому ротация комбинации продолжала бы тратить по одному гарантированно неудачному вызову на каждого соседа.
- **Безопасность соседних соединений**: соседнее соединение, уже находящееся в финальном состоянии (заблокировано/кредиты исчерпаны) или уже имеющее более длительный период охлаждения, никогда не перезаписывается.
- **Эксклюзивный список разрешённых**: расширение `EGRESS_BUCKETED_LOCK_PROVIDERS` — это явное решение владельца; никакой общей связки (паттерн #10334/#10419). Запрос соседних соединений использует тот же список разрешённых, а не дублирует его в виде SQL-литерала, поэтому его расширение остаётся изменением в одну строку.
- **Ротация IP выхода в обоих направлениях**: окно поиска (24 ч) значительно шире TTL кэша IP выхода (5 мин), поэтому «последний известный IP» — это история, а не текущее состояние. Если прокси соединения сменил IP в пределах окна, блокировка может **не обнаружить** действительно общий IP (зафиксирован новый, ещё не исчерпанный IP) — и симметрично может **перевести в период охлаждения соседнее соединение, которое с тех пор сменило IP** и больше не использует исчерпанный IP. Во втором случае это стоит соседнему соединению одного окна охлаждения; оба сценария являются допустимыми ограничениями best-effort-поиска на основе истории.
- **Стоимость**: два ограниченных сканирования `proxy_logs` (фильтрация по окну выполняется через `idx_pl_timestamp`), только с частотой ошибок 429. Новый индекс не нужен (миграция 134, YAGNI). Измерено на копии базы данных с реальным трафиком умеренного размера; экземпляр с высокой пропускной способностью хранит пропорционально больше строк в том же окне.

## Отладка

- Взвешенное комбо отвечает `503 all_targets_cooling_down` (заголовок `Retry-After` установлен, `diagnostics.excluded` перечисляет каждую цель с `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → пул настроен и подключён, просто каждая цель исключена таймером отказоустойчивости; предупреждение `[COMBO] Weighted selection: every target excluded before dispatch — …` указывает причины и оставшиеся секунды. Ответ `404 no_executable_targets` от того же комбо означает, что таймер отказоустойчивости не участвовал (нечего запускать, или каждый аккаунт не прошёл проверку доступности). Реализовано в `open-sse/services/combo/pinRecovery.ts` на основе исключений, собранных в `targetResolution.ts`.
- Все ключи провайдера пропущены → проверьте и состояние circuit breaker, И `rateLimitedUntil`/`testStatus` каждого подключения.
- Провайдер навсегда исключён после окна сброса → код читает сырой `state` вместо `getStatus()`/`canExecute()`.
- Один ключ отказал, остальные должны работать → предпочтите cooldown подключения вместо circuit breaker.
- Отказывает только одна модель → предпочтите блокировку модели (model lockout) вместо cooldown подключения.
- Состояние должно самовосстанавливаться, но не восстанавливается → проверьте метку времени в будущем и путь чтения, который обновляет истёкшее состояние. Постоянные статусы требуют ручного изменения.

## Состояние во время выполнения — краткая справка для агента

> Перенесено дословно из `AGENTS.md` → раздел "Resilience Runtime State" (PR #12743), чтобы
> руководство для агента оставалось в пределах бюджета контекста в 40 тыс. Это сжатое,
> ориентированное на агента представление разделов выше; пронумерованные разделы остаются
> полным справочником.

В OmniRoute есть три связанных, но различных механизма обработки временных сбоев. При
отладке поведения маршрутизации разделяйте их области действия. См.
[диаграмму 3-уровневой отказоустойчивости](../diagrams/exported/resilience-3layers.svg)
(источник: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd))
для наглядной карты.

### Circuit Breaker провайдера

**Область действия**: весь провайдер, например `glm`, `openai`, `anthropic`.

**Назначение**: прекратить отправку трафика провайдеру, который неоднократно даёт сбои на
уровне апстрима/сервиса, чтобы один нездоровый провайдер не замедлял каждый запрос.

**Реализация**:

- Основной класс: `src/shared/utils/circuitBreaker.ts`
- Связка гейта/выполнения чата: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API статуса во время выполнения: `src/app/api/monitoring/health/route.ts`
- Общие обёртки: `open-sse/services/accountFallback.ts`
- Таблица сохраняемого состояния: `domain_circuit_breakers`

**Состояния** (4 — `src/shared/utils/circuitBreaker.ts`):

- `CLOSED`: обычный трафик разрешён.
- `DEGRADED`: зона раннего предупреждения — сбои пересекли порог деградации, но ещё не
  порог размыкания; трафик по-прежнему идёт, дашборды показывают предупреждение.
  Успешный тест подключения или тихое окно без новых сбоев возвращает его в `CLOSED`
  (окно описано в `docs/architecture/RESILIENCE_GUIDE.md`).
- `OPEN`: провайдер временно заблокирован; вызывающие получают ответ provider-circuit-open,
  либо комбо-маршрутизация переходит к другой цели.
- `HALF_OPEN`: таймаут сброса истёк; разрешается пробный запрос. Успех замыкает
  breaker, сбой снова размыкает его.

**Значения по умолчанию** (`open-sse/config/constants.ts` → `PROVIDER_PROFILES`, используются через
`DEFAULT_RESILIENCE_SETTINGS.providerBreaker` в `src/lib/resilience/settings.ts` →
`getCircuitBreaker(provider, …)` в `src/sse/handlers/chatHelpers.ts`). Breaker всего
провайдера работает на `circuitBreakerThreshold` / `circuitBreakerReset`:

| Профиль   | деградирует при | размыкается при (`circuitBreakerThreshold`) | сброс (`circuitBreakerReset`) |
| --------- | --------------: | ------------------------------------------: | ----------------------------: |
| OAuth     |             `5` |                                         `8` |                         `60s` |
| API-ключ  |             `7` |                                        `12` |                         `30s` |
| Локальный |   (вычисляется) |                                         `2` |                         `15s` |

`PROVIDER_PROFILES` также определяет `providerFailureThreshold` (10/15/2),
`providerFailureWindowMs` (15/30/5 мин) и `providerCooldownMs` (5/10/1 мин): они питают
**оконный гейт опционального глобального Provider Cooldown** (`PROVIDER_COOLDOWN_ENABLED`, по умолчанию
выключен) — запись уровня провайдера в `open-sse/services/providerCooldownTracker.ts` считается
охлаждающейся только после `providerFailureThreshold` сбоев внутри `providerFailureWindowMs`, а затем
охлаждается в течение `providerCooldownMs`. Это НЕ пороги живого breaker — не настраивайте их,
ожидая поведения breaker. Каждое значение по умолчанию можно переопределить через
переменные окружения `OMNIROUTE_PROVIDER_BREAKER_*` и `OMNIROUTE_CIRCUIT_BREAKER_*`;
точная для времени выполнения справочная таблица находится в `docs/architecture/RESILIENCE_GUIDE.md`.

Только статусы сбоев уровня провайдера должны приводить к срабатыванию breaker провайдера:

```ts
(408, 500, 502, 503, 504);
```

Не размыкайте breaker всего провайдера из-за обычных ошибок аккаунта/ключа/модели, как
большинство случаев `401`, `403` или `429`. Обычно они относятся к cooldown подключения или
блокировке модели. Обычный `403` провайдера с API-ключом должен быть восстановимым, если
только он не классифицирован как терминальная ошибка провайдера/аккаунта.

Прерыватель использует ленивое восстановление, а не фоновый таймер. Когда срок состояния `OPEN` истекает, операции чтения, такие как `getStatus()`, `canExecute()` и `getRetryAfterMs()`, обновляют состояние до `HALF_OPEN`, поэтому дашборды и построители кандидатов для комбо не продолжают бесконечно исключать провайдера с истёкшим сроком.

### Кулдаун соединения

**Область действия**: одно соединение/аккаунт/ключ провайдера.

**Назначение**: временно пропускать один неисправный ключ/аккаунт, позволяя другим соединениям того же провайдера продолжать обслуживать запросы.

**Реализация**:

- Путь записи/обновления: `src/sse/services/auth.ts::markAccountUnavailable()`
- Выбор/фильтрация аккаунтов: `src/sse/services/auth.ts::getProviderCredentials...`
- Расчёт кулдауна: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Настройки: `src/lib/resilience/settings.ts`

Важные поля соединений провайдера:

```ts
rateLimitedUntil;
testStatus: "unavailable";
lastError;
lastErrorType;
errorCode;
backoffLevel;
```

Во время выбора аккаунта соединение пропускается, пока:

```ts
new Date(rateLimitedUntil).getTime() > Date.now();
```

Кулдауны тоже ленивые: когда `rateLimitedUntil` оказывается в прошлом, соединение снова становится доступным для выбора. При успешном использовании `clearAccountError()` очищает `testStatus`, `rateLimitedUntil`, поля ошибок и `backoffLevel`.

Поведение кулдауна соединения по умолчанию:

- Базовый кулдаун OAuth: `5s`.
- Базовый кулдаун API-ключа: `3s`.
- При ответе `429` для API-ключа следует отдавать предпочтение подсказкам о повторе от апстрима (`Retry-After`, заголовки сброса или парсируемый текст сброса), когда они доступны.
- Повторные устранимые сбои используют экспоненциальную задержку:

```ts
baseCooldownMs * 2 ** failureIndex;
```

Механизм защиты от эффекта лавинообразных запросов (thundering herd) не даёт параллельным сбоям на одном соединении многократно продлевать кулдаун или дважды увеличивать `backoffLevel`.

Терминальные состояния — это не кулдауны. Состояния `banned`, `expired` (которое становится терминальным только после N ограниченных повторных попыток через `EXPIRED_RETRY_MAX`) и `credits_exhausted` должны оставаться недоступными, пока не изменятся учётные данные/настройки или оператор не сбросит их вручную. Не перезаписывайте терминальные состояния временным состоянием кулдауна.

### Блокировка модели

**Область действия**: провайдер + соединение + модель.

**Назначение**: не отключать всё соединение, когда недоступна или ограничена квотой только одна модель для этого соединения.

Примеры:

- Провайдеры с квотами на отдельные модели, возвращающие `429`.
- Локальные провайдеры, возвращающие `404` для одной отсутствующей модели.
- Специфичные для провайдера ошибки прав доступа к режимам/моделям, например отдельные режимы Grok.

Блокировка модели реализована в `open-sse/services/accountFallback.ts` и позволяет тому же соединению продолжать обслуживать другие модели.

### Рекомендации по отладке

- Если все ключи провайдера пропускаются, проверьте как состояние прерывателя провайдера, так и `rateLimitedUntil`/`testStatus` каждого соединения.
- Если провайдер остаётся исключённым навсегда после окна сброса, проверьте, не читает ли код сырое значение `state` вместо использования `getStatus()`/`canExecute()`.
- Если один ключ провайдера не работает, но остальные должны работать, предпочитайте кулдаун соединения прерывателю провайдера.
- Если не работает только одна модель, предпочитайте блокировку модели кулдауну соединения.
- Если состояние должно восстанавливаться самостоятельно, у него должна быть временная метка в будущем/таймаут сброса и путь чтения, который обновляет истёкшее состояние. Постоянные статусы требуют ручного изменения учётных данных или конфигурации.

## Тестирование устойчивости (фаза 8 · блок C)

Помимо юнит-тестов логики устойчивости, три теста проверяют среду выполнения
в реальных условиях стресса/сбоев (все интеграционные/ночные — ни один не блокирует PR):

| Тест        | Что                                                                                                                                                                                                  | Запуск                                   |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Chaos       | Фейковый апстрим-узел вносит реальные задержки/сбросы/таймауты/503; проверяет, что circuit breaker открывается/восстанавливается и `checkFallbackError` классифицирует 503 как восстановимый фолбэк. | `RUN_CHAOS_INT=1 npm run test:chaos`     |
| Heap-growth | ~500 потоков на `createSSEStream` под `--expose-gc`; падает, если куча растёт сверх лимита (защита от OOM #3069).                                                                                    | `npm run test:heap`                      |
| k6 soak     | Длительная нагрузка на `/api/monitoring/health`; пороги p95/ошибок.                                                                                                                                  | `k6 run tests/load/k6-soak.js` (nightly) |

Оркестрируется `.github/workflows/nightly-resilience.yml` (cron + dispatch). В
стандартном `test:integration` chaos и heap самопропускаются (без `RUN_CHAOS_INT`/`--expose-gc`).
