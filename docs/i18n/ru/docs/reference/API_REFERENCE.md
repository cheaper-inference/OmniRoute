## Завершения чата

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Пользовательские заголовки

| Заголовок                | Направление | Описание                                                                                                                                                                                                                                              |
| ------------------------ | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Запрос      | Установите значение `true`, чтобы обойти кэш                                                                                                                                                                                                          |
| `x-omniroute-no-memory`  | Запрос      | Установите значение `true`, чтобы пропустить внедрение памяти и навыков для этого запроса (аналогично отключению кэша; позволяет избежать затрат токенов и средств на каждый вызов)                                                                   |
| `X-OmniRoute-Progress`   | Запрос      | Установите значение `true` для получения событий прогресса                                                                                                                                                                                            |
| `X-Session-Id`           | Запрос      | Ключ закреплённой сессии для внешней привязки сессии                                                                                                                                                                                                  |
| `x_session_id`           | Запрос      | Также принимается вариант с символами подчёркивания (прямой HTTP-запрос)                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | Запрос      | Предоставленный вызывающей стороной тег сессии/диалога (также передаётся в память). При наличии сохраняется без изменений в `call_logs.session_tag` для учёта затрат по отдельным сессиям (#8249) — при отсутствии никогда не создаётся автоматически |
| `Idempotency-Key`        | Запрос      | Ключ дедупликации (окно 5 с)                                                                                                                                                                                                                          |
| `X-Request-Id`           | Запрос      | Альтернативный ключ дедупликации                                                                                                                                                                                                                      |
| `x-omniroute-connection` | Запрос      | Закрепляет запрос к одной модели за одним подключением провайдера (учётной записью) по его идентификатору — см. [Закрепление учётной записи для каждого запроса](#account-pinning-per-request)                                                        |
| `X-OmniRoute-Cache`      | Ответ       | `HIT` или `MISS` (без потоковой передачи)                                                                                                                                                                                                             |
| `X-OmniRoute-Idempotent` | Ответ       | `true`, если выполнена дедупликация                                                                                                                                                                                                                   |
| `X-OmniRoute-Progress`   | Ответ       | `enabled`, если отслеживание прогресса включено                                                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | Ответ       | Фактический идентификатор сессии, используемый OmniRoute                                                                                                                                                                                              |
| `X-OmniRoute-Request-Id` | Ответ       | Идентификатор корреляции запроса (если известен)                                                                                                                                                                                                      |
| `X-OmniRoute-Version`    | Ответ       | Версия сборки OmniRoute (присутствует всегда)                                                                                                                                                                                                         |
| `X-OmniRoute-Cost-Saved` | Ответ       | Сумма в USD, сэкономленная благодаря кэшу при `HIT` (только для попаданий в кэш)                                                                                                                                                                      |
| `X-OmniRoute-Decision`   | Ответ       | Трассировка маршрутизации: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` — стратегия комбинации или `single` для запроса без комбинации) — всегда присутствует в ответах о завершении                                                 |

> Примечание по Nginx: если вы используете заголовки с символами подчёркивания (например, `x_session_id`), включите `underscores_in_headers on;`.

#### Закрепление учётной записи для отдельного запроса

Когда у провайдера есть несколько подключений (учётных записей или ключей), OmniRoute обычно выбирает одно из них
с помощью своей стратегии выбора учётной записи. Вместо этого запрос может закрепить конкретное подключение
с помощью заголовка `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Где найти идентификатор.** Откройте страницу провайдера на панели управления
  (**Панель управления → Провайдеры → <provider>**) и нажмите на плашку идентификатора `xxxxxxxx…` в строке подключения —
  полный идентификатор подключения будет скопирован.
- **Какие запросы его учитывают.** Запросы к одной модели (`provider/model`) на
  `/v1/chat/completions`, `/v1/messages` и `/v1/responses`. Комбинации игнорируют этот заголовок: вместо этого
  закрепляйте учётную запись для каждого шага комбинации через собственное подключение шага.
- **Закрепление строгое, а не предпочтительное.** Используется исключительно закреплённое подключение.
  Сбой в запросе запускает для учётной записи период охлаждения, но **не** приводит к переключению на
  другую учётную запись того же провайдера.
- **Период охлаждения и квота снимают закрепление.** Пока закреплённое подключение находится на охлаждении,
  исчерпало квоту или заблокировано политикой квот, последующие запросы переключаются на другие подключения
  провайдера — точно так же, как незакреплённый трафик.
- **Неизвестные или отключённые идентификаторы приводят к ошибке.** Если идентификатор отсутствует в активном пуле провайдера (удалён,
  деактивирован или относится к другому провайдеру), подходящих учётных записей не остаётся, поэтому запрос
  завершается ошибкой вместо незаметной маршрутизации в другое место.

Claude Code отправляет пользовательские заголовки через `ANTHROPIC_CUSTOM_HEADERS`. Добавьте эту переменную в блок `env`
файла `~/.claude/settings.json` или в файл `.claude/settings.json` на уровне проекта, чтобы закрепить отдельную
учётную запись для каждого проекта:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Источник: `src/sse/handlers/chat.ts` (чтение заголовка), `src/sse/services/auth.ts` и
`src/sse/services/sessionAffinityPin.ts` (снятие закрепления и проверка отсутствия в пуле).

> **Заголовки телеметрии стоимости:** успешные ответы без потоковой передачи также содержат набор телеметрии стоимости `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фиксированные 10 знаков после десятичной точки; `0.0000000000` для бесплатных запросов или запросов без указанной цены), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` и `X-OmniRoute-Fallback-Attempts` (только при значении > 0), а также `X-OmniRoute-Request-Id` и `X-OmniRoute-Version`. Они возвращаются для завершений чата, `/v1/responses`, `/v1/messages`, **а также для конечных точек мультимедиа** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` и `/v1/moderations` (стоимость всегда равна `0`). Стоимость мультимедиа рассчитывается с учётом соответствующей модальности (за изображение, секунду, символ или единицу поиска), если данные о ценах доступны; в противном случае используется `0` (fail-open).

> **Семантика стоимости при попадании в кэш:** при попадании в семантический кэш (`X-OmniRoute-Cache-Hit: true`) запрос к вышестоящему сервису не выполняется, поэтому значение `X-OmniRoute-Response-Cost` равно `0.0000000000` (**дополнительная** стоимость обслуживания попадания в кэш). Исходная/предполагаемая стоимость указывается отдельно в `X-OmniRoute-Cost-Saved`. Системам биллинга следует суммировать `X-OmniRoute-Response-Cost` (попадания в кэш ничего не стоят); системы аналитики кэша могут агрегировать `X-OmniRoute-Cost-Saved`.

## Эксклюзивные аренды управляемых сеансов

Эксклюзивная аренда управляемых сеансов — это необязательный, не зависящий от клиента контракт маршрутизации: один активный владелец
удерживает одно подходящее подключение OmniRoute. Она не арендует модель, не требует OAuth, не идентифицирует
конкретный клиент и не требует определённого провайдера.

API-ключ, используемый для аутентификации, должен иметь область действия `lease:exclusive` и явно заданный непустой
список `allowedConnections`. Граница мутации базы данных обеспечивает совместное соблюдение обоих требований при
создании ключа и частичных обновлениях.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успешные ответы на получение, продление и освобождение содержат временные метки, `state` и точное положительное
значение `generation`, но никогда не раскрывают выбранное подключение или учётные данные. При продлении и освобождении
поколение передаётся в теле JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Владелец активной аренды может явно запросить безопасные с точки зрения конфиденциальности отображаемые метаданные текущей привязки:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Это необязательное действие получения статуса защищено непрозрачным идентификатором владельца, аутентифицированным управляемым API-ключом и точным
активным поколением в рамках одной транзакции базы данных. `displayName` содержит только настроенное имя
подключения без начальных и конечных пробелов; если безопасного настроенного имени нет, значение равно `null`. OmniRoute никогда не подставляет
адрес электронной почты или сгенерированный идентификатор учётной записи. Значение провайдера является неконфиденциальной отображаемой меткой и никогда
не представляет собой сгенерированный идентификатор совместимого провайдера. Учётные данные, токены, файлы cookie, необработанные идентификаторы подключений или API-ключей,
хеши владельцев, секреты разграничения и внутренние данные маршрутизации исключены.

Запросы с неверным ключом, неверным владельцем, устаревшим поколением, отсутствующей, истёкшей, освобождённой или аннулированной арендой
возвращают одну и ту же ошибку `409 LEASE_FENCE_STALE` без метаданных подключения. Клиент, получивший ответ об ожидании доступной ёмкости, не имеет активной привязки, которую можно проверить. Когда маршрутизация переключает активную аренду,
то же поколение остаётся действительным, а статус атомарно возвращает новую привязку, но никогда не старую.
Существующие клиенты не затрагиваются, поскольку ответы на получение, продление, освобождение и ожидание сохраняют
прежнюю структуру.

Этот серверный контракт не изменяет стандартный `/status` OpenAI Codex. В настоящее время стандартный Codex сообщает о своём
провайдере модели и встроенном состоянии аутентификации/учётной записи, но не отображает произвольные пользовательские
метаданные учётной записи провайдера; будущая клиентская интеграция должна вызывать это действие и решать, как
отображать `connection.displayName`.

После этого каждый управляемый запрос на инференс передаёт оба управляющих заголовка:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точное соответствие владельца, поколения, активного подключения и аутентифицированного API-ключа проверяется непосредственно
перед каждой поддерживаемой попыткой обращения к вышестоящему сервису. Повторное использование владельца и поколения с другим ключом завершается ошибкой, даже
если этот ключ разрешает то же подключение. Необработанные идентификаторы владельцев не сохраняются, не записываются в журналы, не удерживаются в
снимке запроса и не пересылаются вышестоящему сервису.

При временной конкуренции возвращается HTTP `429` с `Retry-After` и следующим содержимым:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Этот ответ означает только то, что обычный набор подходящих подключений был непустым, а каждый свободный кандидат
удерживался чужой активной арендой. Для неподдерживаемых моделей/провайдеров, несоответствия политике, периода ожидания,
квоты, состояния работоспособности и других обычных сбоев проверки соответствия сохраняются существующие ответы OmniRoute.

### `x-omniroute-compression`

Переопределение плана сжатия для отдельного запроса. Имеет наивысший приоритет — превосходит переопределение комбинации маршрутизации,
активный профиль, автоматический триггер и значение Default на панели. Значения:

| Значение      | Эффект                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Не выполнять сжатие для этого запроса.                                                                                   |
| `default`     | Профиль Default, полученный из настроек панели (активный профиль игнорируется). Движки с потерями остаются отключёнными. |
| `safe`        | Только дедупликация и свёртывание пробельных символов.                                                                   |
| `allow-lossy` | Сохранить операторский план для этого запроса, включая сводки и переформулирование стиля.                                |
| `engine:<id>` | Один движок, если он включён, например `engine:rtk`. Включение этого движка для отдельного запроса.                      |
| `<combo>`     | Именованная комбинация: сначала выполняется поиск по имени без учёта регистра, затем по идентификатору.                  |

Примечания:

- Неизвестные значения игнорируются (запрос никогда не отклоняется); разрешение продолжается в соответствии с обычным порядком приоритетов оператора.
- Если несколько комбинаций имеют одинаковое имя, передайте **идентификатор** комбинации для детерминированного сопоставления.
- Комбинацию с именем `off` или `default` нельзя выбрать по имени (сначала интерпретируются эти ключевые слова); обращайтесь к такой комбинации по её идентификатору.
- Главный переключатель сжатия является жёстким ограничителем: если сжатие отключено глобально, этот заголовок не может его включить.

Применённый план возвращается в заголовке ответа:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

где `<source>` имеет одно из значений `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Эмбеддинги

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Доступные провайдеры: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Идентификаторы в каталоге имеют формат `provider/model` (пример: `jina-ai/jina-embeddings-v5-omni-small`). Также распознаются идентификаторы моделей Jina без указания провайдера, присутствующие в реестре (например, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`). Для операций Jina embed/rerank/classify/segment сначала используются учётные данные `jina-ai` из панели управления; `JINA_AI_API_KEY` используется только как резервный вариант, если ключ в панели управления отсутствует. Карточка `jina-reader` предназначена только для Reader / `r.jina.ai` (`POST /v1/web/fetch`) и никогда не используется для эмбеддингов или переранжирования.

Модели в реестре, для которых заявлена поддержка мультимодальности, также принимают до 32 структурированных
элементов в независимом от провайдера формате. Типы медиаэлементов: `text`, `image`, `audio`, `video` и `document`. Их поле `source`
имеет вид либо `{"type":"url","url":"https://..."}`, либо
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
и псевдоним семейства `jina-ai/jina-embeddings-v5-omni` → omni-small) также принимает нативные
документы EmbeddingsV5Request от Jina и **пересылает их без изменений** на `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Нативные значения `{ image | audio | video | pdf }` могут быть общедоступным HTTPS-URL, URI `data:` или необработанными
данными base64. OmniRoute не преобразует эти объекты в строки и не загружает изображения по нативным URL — Jina получает
общедоступные медиафайлы самостоятельно. Дополнительные поля Jina (`task`, `normalized`, `truncate`, `embedding_type`)
пересылаются. Текстовые SKU Jina по-прежнему отклоняют нетекстовые документы.

Ограничения безопасности и передачи данных:

- Удалённые URL медиафайлов должны быть общедоступными и использовать HTTPS. Канонические элементы `{type,source:url}` загружаются
  на стороне сервера (с повторной проверкой перенаправлений, тайм-аутом, ограничениями размера, проверкой публичного DNS и
  фиксацией соединения) и встраиваются перед вызовом провайдера. Нативные элементы Jina `{image:"https://..."}` пересылаются как есть
  после аналогичной проверки общедоступности HTTPS; URL загружает Jina.
- Встроенные медиафайлы в формате base64 ограничены 8 МиБ декодированных данных на элемент и 16 МиБ декодированных данных на весь запрос.

Преобразование для провайдеров (канонические элементы никогда не пересылаются без изменений):

- Мультимодальные модели Jina: каждый элемент верхнего уровня преобразуется в один объект с ключом модальности
  (`text` / `image` / `audio` / `video` / `pdf`), использующий URI данных для встроенных медиафайлов; один вектор на
  каждый элемент верхнего уровня.
- Семейство Gemini Embedding 2: один массив верхнего уровня преобразуется в один нативный запрос
  `models/{model}:embedContent` с `content.parts` (`text` или `inline_data`).
- llama.cpp (`llama-cpp/<model>`, любая модель, загруженная локальным сервером): канонические элементы `text`
  преобразуются в обычные строки, а `image` / `audio` / `video` — в отдельный объект
  `{"content": [part]}` с использованием частей содержимого чата llama-server (`image_url`,
  `input_audio` с форматом `wav` / `mp3` / `flac`, `input_video`) и встроенными данными; один вектор
  на каждый элемент верхнего уровня. Сервер должен быть запущен с `--embedding --mmproj …`; без проектора он
  самостоятельно отклоняет медиафайлы. `document` не поддерживается.
- Неизвестные/динамические модели без явно заданных метаданных модальности отклоняют структурированный ввод с HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Неподдерживаемые комбинации модели и модальности возвращают HTTP 400 вместо принудительного преобразования элемента. Поля расширения,
не относящиеся к вводу, в устаревших запросах со строками или токенами по-прежнему передаются без изменений.

```bash
# Получить список всех моделей эмбеддингов
GET /v1/embeddings
```

## Генерация изображений

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Доступные провайдеры: OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локальный), ComfyUI (локальный).

Параметр `n` возвращает `n` изображений в `data[]`. Для провайдеров, вышестоящий API которых возвращает одно изображение за вызов
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), выполняется `n` отдельных вышестоящих вызовов, при этом одновременно обрабатывается не более 4. Фиксированное
значение `seed` смещается на индекс вызова (`seed`, `seed + 1`, …), поэтому изображения различаются, но остаются
воспроизводимыми. Значение `n` ограничено 10. Если какой-либо вызов завершается с ошибкой, весь запрос считается неуспешным. Список
форматов с разветвлением запросов определён в `SINGLE_IMAGE_FANOUT_FORMATS` в
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux повторно использует существующее подключение с API-ключом и принимает префиксы `zenmux/` или `zm/`:

- `zenmux/openai/gpt-image-2` использует OpenAI Images API от ZenMux. Доступные параметры включают `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` и `response_format`.
- Другие издатели, например `zm/meta/muse-image-1.0`, используют эндпоинт ZenMux Vertex AI `:predict`.
  Параметр `n` сопоставляется с `sampleCount`, `aspect_ratio` — с `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — с `sampleImageSize`. Параметр `size` в пикселях задаёт только соотношение сторон,
  а не гарантированные размеры в пикселях. Поддерживаемые соотношения сторон, разрешения и количества зависят от модели.
- `zm/inclusionai/ming-image-0.1-design` самостоятельно выбирает размеры. Не указывайте `size`,
  `aspect_ratio` и `image_size`; явное указание значений приводит к возврату HTTP 400. Форматы PNG, JPEG и WebP
  можно запросить с помощью `output_format`.

Эта интеграция поддерживает генерацию изображений по тексту, но не редактирование по референсному изображению. Выходные данные Vertex
нормализуются в `data[].b64_json`; при `response_format: "url"` возвращается вышестоящий
HTTPS URL или URL с данными в base64, если доступны только байты изображения. При пустом или отфильтрованном результате
возвращается ошибка, а не успешный ответ без данных. Доступ к моделям зависит от учётной записи ZenMux.
См. [Vertex API от ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) и
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Список всех моделей изображений
GET /v1/images/generations
```

```bash
{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
```

Параметр `model` выбирает провайдера OCR с помощью префикса `provider/model`; идентификатор модели без префикса (например,

Mistral (`mistral-ocr-latest`). Зарегистрированные провайдеры (`open-sse/config/ocrRegistry.ts`):

| Идентификатор провайдера      | Идентификатор модели | Значение `model`                                                     | Примечания                                                                                                                    |
| ----------------------------- | -------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (или `mistral-ocr-latest` без префикса) | Синхронный режим — ответ возвращается непосредственно из единственного вышестоящего вызова.                                   |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                          | Асинхронный вышестоящий сервис (`analyze` + опрос) — см. ниже.                                                                |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                              | Синхронный режим через партнёрский эндпоинт Vertex AI `openapi/chat/completions` — сведения об аутентификации и URL см. ниже. |

Все три провайдера возвращают тело ответа в едином формате Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",

}
```

### Процесс опроса Azure Document Intelligence

API `analyze` в Azure Document Intelligence работает асинхронно: первоначальный запрос возвращает заголовок
`Operation-Location` вместо тела ответа, после чего необходимо опрашивать состояние результата. Обработчик
(`open-sse/handlers/ocr.ts`) опрашивает этот URL каждую секунду, выполняя не более 30 попыток; он немедленно завершает работу с ошибкой (не
продолжая опрос), если ответ опроса не имеет статус `ok` или возвращён статус `"failed"`, и возвращает `504`, если
операция всё ещё выполняется после исчерпания допустимого количества попыток. Итоговый ответ Azure
перед возвратом вызывающей стороне нормализуется в тот же формат `pages`/`markdown`, который используется Mistral,
поэтому клиентскому коду не требуется отдельно обрабатывать особенности провайдера.

### Аутентификация и определение эндпоинта Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` повторно использует тот же механизм аутентификации Vertex AI, который OmniRoute уже поддерживает для
трафика чатов и изображений (`open-sse/executors/vertex.ts`): API-ключ подключения представляет собой либо
учётные данные Service Account в формате JSON (которые обмениваются на краткосрочный OAuth-токен доступа посредством потока JWT-bearer),
либо уже выпущенный OAuth-токен доступа, используемый без изменений. URL вышестоящего эндпоинта — это универсальный
партнёрский эндпоинт Vertex `openapi/chat/completions`, сформированный на основе проекта и
региона подключения: явно заданные `providerSpecificData.project`/`providerSpecificData.region` всегда имеют приоритет;
в противном случае проект определяется из `project_id` в JSON Service Account, а регионом
по умолчанию является `us-central1`. Оба значения определяются в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) и используются в
`src/app/api/v1/ocr/route.ts` перед передачей запроса в `handleOcr`.

## Список моделей

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Возвращает все модели для чатов, эмбеддингов и изображений, а также комбинации в формате OpenAI
```

### Цены моделей (`pricing`)

Запись содержит объект `pricing`, когда OmniRoute известна цена модели. Цена берётся
из таблицы цен, используемой для учёта затрат: встроенные значения по умолчанию, синхронизированные цены и
переопределения, заданные через `/api/pricing`. Это цены по прейскуранту, поэтому у провайдеров с подпиской также
указывается цена за токен.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Поля                                                            | Единица измерения               | Примечания                                                                                                                                              |
| --------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD за токен, десятичная строка | Совместимы с OpenRouter, экспоненциальная запись никогда не используется. Два поля кеша присутствуют только при наличии цены кеширования.               |
| `input`, `output`, `cached`, `cache_creation`                   | USD за 1 млн токенов, число     | Поля из предыдущих версий каталога, сохранённые для существующих клиентов. `reasoning` и `long_context` также присутствуют, если они есть в строке цен. |

- **Комбинации** содержат цену своей первой видимой целевой модели. Встроенные комбинации `auto/*` выбирают
  целевую модель во время запроса, поэтому у них отсутствует `pricing`.
- **Бесплатные модели** содержат `"0"` (и `0`), когда их цена равна нулю. Модель без строки с ценой
  также содержит `"0"`, если каталог помечает её как бесплатную (`free: true`) или она указана
  во встроенном каталоге бесплатных моделей.
- **Неизвестная цена:** в записи отсутствует ключ `pricing`.
- **Провайдеры с тарификацией по кредитам** (например, Kiro) взимают плату за запрос, а не за токен. Их
  записи сохраняют прежние числовые поля цены за 1 млн токенов и не содержат строковых полей цены за токен.
- **Варианты** (идентификаторы уровня усилий рассуждения, псевдонимы без рассуждения, зеркала обнаружения и шлюза)
  копируют цену модели, на которую они направляют запросы.
- Поля содержат только базовые тарифы. Уровни длинного контекста (числовое поле `long_context`) и
  множители уровня обслуживания (например, Codex fast или flex) не изменяют `prompt` или
  `completion`.
- Объект одинаков для всех способов аутентификации, включая запрос в стиле Anthropic
  с `x-api-key` и `anthropic-version` (ответ остаётся `{ "object": "list",
"data": [...] }`). Реализация: `src/app/api/v1/models/catalogPricing.ts`.

### Префиксы идентификаторов моделей (`?prefix=`)

Большинство моделей публикуются с **префиксом провайдера**. Используемый префикс определяется
флагом функции `MODELS_CATALOG_PREFIX_MODE` и может быть переопределён **для каждого запроса** с помощью
параметра запроса — это полезно для клиента, которому нужен чистый список без изменения общесерверной
настройки для всех остальных:

```bash
GET /v1/models?prefix=alias        # один идентификатор на модель — короткий префикс-псевдоним
GET /v1/models?prefix=dual         # обе формы (значение сервера по умолчанию)
GET /v1/models?prefix=canonical    # только полный префикс идентификатора провайдера
```

| Режим       | Выводит                                                 | Примечания                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **и** `claude/claude-sonnet-4-6` | **По умолчанию.** Оба идентификатора направляют запросы к одной модели; это сохранено, чтобы конфигурации клиентов с жёстко заданной любой из форм продолжали работать. Размер каталога увеличивается примерно вдвое.          |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Одна запись на модель. Провайдеры без отдельного псевдонима всё равно выводят свою запись, поэтому ничего не теряется.                                                                                                         |
| `canonical` | `claude/claude-sonnet-4-6`                              | Одна запись на модель с полным префиксом идентификатора провайдера. Провайдеры без отдельного псевдонима (например, `antigravity/…`, `agy/…`) также выводят здесь свой единственный идентификатор, поэтому ничего не теряется. |

Зеркало в режиме `dual` можно распознать и без параметра запроса: оно содержит поле `parent`,
указывающее на основной идентификатор.

Клиентам, отображающим интерфейс выбора модели, следует запрашивать `?prefix=alias` — именно так поступает
[расширение OmniCopilot для VS Code](../guides/VSCODE-COPILOT.md).

### Фильтры обнаружения (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` поддерживает необязательные фильтры обнаружения. Если ни один из них не указан, ответ
не изменяется. Они сужают уже доступный вызывающей стороне каталог (сначала применяются разрешения ключа API)
и выполняются до постраничного вывода в стиле OpenAI с параметрами `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # все указанные возможности должны иметь значение true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # поле `type` каталога; строки без него считаются `chat`
GET /v1/models?q=sonnet&limit=10                           # регистронезависимое совпадение по идентификатору или имени
```

| Параметр      | Значения                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | неотрицательное целое число, сравнивается с `context_length`                                        |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 символов                                                                                      |

Неизвестное значение или значение `min_context`, не являющееся неотрицательным целым числом (например, `1.5`),
приводит к возврату HTTP `400`, а сообщение содержит список допустимых значений. Реализация:
`src/app/api/v1/models/catalogFilters.ts`.

### Краткий список моделей (`POST /v1/models/query`)

`POST /v1/models/query` возвращает краткий детерминированный список из того же каталога, с той же
аутентификацией и видимостью для каждого ключа, что и `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Каждое поле является необязательным. `capabilities` и `exclude` принимают массив или строку со значениями, разделёнными запятыми;
`max_output` сравнивается с `max_output_tokens`. Результаты сортируются сначала по `owned_by`, затем по `id`.
Значение `limit` по умолчанию равно `20`, а значения выше `100` ограничиваются до `100`. Некорректный JSON, неизвестное
поле или недопустимое значение приводят к возврату HTTP `400`.

### Отдельно скрытые модели чата

Модель, отмеченная как **Скрытая** на странице её провайдера, исключается из каталога и отклоняется
с HTTP `404` / `model_not_found` при явном запросе. Проверка использует определённые
провайдер и модель, включая псевдонимы провайдеров, префиксы узлов совместимых провайдеров и
значения подключения по умолчанию. Комбинация пропускает скрытые целевые модели и может использовать видимую альтернативу; если
не остаётся ни одной доступной для выполнения целевой модели, возвращается тот же код ошибки. Отмена скрытия вступает в силу при следующем
запросе. Переопределения видимости только для изображений не скрывают модель чата с тем же идентификатором.

Эта настройка отдельной модели не зависит от
[списков разрешения/запрета публикации моделей](../routing/MODEL_EXPOSURE_LIST.md), которые фильтруют модели, публикуемые в каталоге,
и кандидатов для автоматической маршрутизации, сохраняя при этом возможность явной диспетчеризации. Разрешения моделей для API-ключей
продолжают применяться независимо. Режим префиксов каталога по умолчанию остаётся `dual`.

### Варианты моделей без размышления

Для поддерживающих размышление моделей Claude `/v1/models` также публикует вариант **без размышления**, идентификатор которого имеет префикс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

При выборе этого идентификатора (например, в конфигурации Claude Code, которая всегда добавляет блок `thinking`) он преобразуется обратно в фактический `<provider>/<model>` с отключённым рассуждением — `thinking:{type:"disabled"}` для пути `/v1/messages` либо с удалёнными полями `reasoning`/`reasoning_effort` для пути `/v1/chat/completions`. Этот вариант присутствует в списке только для моделей семейства Claude, которые поддерживают размышление **и** учитывают значение `disabled` (поэтому, например, модели, поддерживающие только адаптивный режим и отклоняющие `disabled`, исключаются). Операторы могут принудительно включать или отключать этот вариант для каждой модели с помощью `ModelSpec.noThinkingAlias`.

## Генерация аудио ElevenLabs

Настройте подключение к провайдеру `elevenlabs` в OmniRoute с помощью вашего API-ключа ElevenLabs.
Клиенты проходят аутентификацию с помощью своего ключа **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюз передает сохраненный ключ провайдера в качестве `xi-api-key`. Никогда не передавайте ключ ElevenLabs
в качестве bearer-токена шлюза.

| Метод | Путь                        | Ответ                                            | Категория конечной точки API-ключа |
| ----- | --------------------------- | ------------------------------------------------ | ---------------------------------- |
| POST  | `/v1/sound-generation`      | Нативные аудиоданные                             | `elevenlabs`                       |
| POST  | `/v1/music`                 | Нативные аудиоданные                             | `music`                            |
| POST  | `/v1/music/stream`          | Потоковые аудиоданные                            | `music`                            |
| POST  | `/v1/music/detailed`        | Нативные multipart-аудиоданные и план композиции | `music`                            |
| POST  | `/v1/music/detailed/stream` | Нативные метаданные SSE и фрагменты аудиоданных  | `music`                            |
| POST  | `/v1/music/plan`            | План композиции в формате JSON                   | `music`                            |

Эти конечные точки дополняют существующие маршруты `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` и `/v1/speech-to-text`. Нативные поля JSON
и параметры запроса, такие как `output_format` и `enable_logging`, сохраняются.
В ответах `/v1/music/detailed` сохраняются их multipart-границы; обрабатывайте их как multipart.
`/v1/music/detailed/stream` возвращает `text/event-stream` с метаданными композиции и
фрагментами аудиоданных в кодировке base64 в событиях SSE. Все шесть маршрутов поддерживают предварительные запросы CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Короткий звуковой эффект. Продолжительность: от 0,5 до 30 секунд.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Продолжительность музыки указывается в миллисекундах: от 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Используйте `/v1/music/stream` с тем же телом JSON для поэтапной передачи аудиоданных. Для композиции
принимается строго одно из двух полей: `prompt` или `composition_plan`; `/v1/music/plan` требует `prompt`
и дополнительно может принимать `source_composition_plan`. Нативные схемы сохраняют дополнительные
поля провайдера, чтобы версии планов композиции и параметры тонкой настройки передавались в ElevenLabs.

Унифицированная конечная точка `/v1/music/generations` также принимает `elevenlabs/music_v1`,
`elevenlabs/music_v2` и `elevenlabs/music_v2_5`. При наличии активного подключения ElevenLabs
эти модели отображаются в каталоге музыки. Эта конечная точка возвращает
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Ее поле `duration` указывается в
секундах и сопоставляется с `music_length_ms`; явно заданное значение `music_length_ms` имеет приоритет.
`instrumental` сопоставляется с `force_instrumental`, при этом нативное поле имеет приоритет.
Используйте нативные потоковые конечные точки для потоковой передачи, а нативную конечную точку композиции —
для запросов, основанных только на плане композиции.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ограничения конечной точки, модели, бюджета и подключения применяются до обращения к вышестоящему сервису. Нативные
маршруты возвращают коды состояния и тела ошибок вышестоящего сервиса без изменений, включая `402` при ограничении
тарифного плана и `429` при превышении квоты. Заголовки `character-cost`, `song-id`, `request-id` и `retry-after`
сохраняются при их наличии. Бесплатный кредитный баланс не гарантирует доступ ко всем
музыкальным моделям, форматам вывода или функциям API: ElevenLabs определяет права доступа для каждого запроса.
Унифицированная конечная точка сохраняет коды состояния ошибок в нормализованной структуре ошибок OmniRoute.

Контракты вышестоящего сервиса: [звуковые эффекты](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[создание музыкальных композиций](https://elevenlabs.io/docs/api-reference/music/compose) и
[потоковая передача сведений о музыке](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

Все маршруты POST используют одинаковый формат: `Bearer your-api-key` + JSON-тело, проверяемое с помощью Zod (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` и т. д.; см. `src/shared/validation/schemas.ts`). При ошибке проверки схемы возвращается 4xx.

Для клиентов, которые не могут добавить `Authorization: Bearer ...`, OmniRoute также принимает ключи API в URL — либо через совместимые параметры строки запроса (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`), либо через описанные ниже специальные эндпоинты `/api/v1/vscode/{token}/...`.

```bash
# Переранжирование (провайдер облачного реестра или узел OpenAI-совместимого провайдера в формате "<prefix>/<model>")

# Классификация Jina (учётные данные Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Сегментатор Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Поиск Jina (s.jina.ai; алиасы провайдера: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Модерация
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — возвращает тело audio/mpeg (или в запрошенном формате)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Для TTS Soniox требуются язык и голос: значение `language` по умолчанию — "en"; при отсутствии
# голоса или использовании стандартного имени голоса OpenAI (alloy, nova, …) выбирается "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Редактирование изображения (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генерация видео / музыки (идентификатор модели с префиксом провайдера)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Узлы провайдеров для реранкинга:** `POST /v1/rerank` также направляет запросы к OpenAI-совместимым узлам провайдеров
> (oMLX, vLLM, Infinity, TEI за шлюзом, …), адресуемым как `<node-prefix>/<model>`. Узлы
> обратной петли (`localhost`, `127.0.0.1`, `172.16.0.0/12`) всегда доступны, как и имена хостов,
> указанные оператором в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (например, имя сервиса Docker/Compose,
> такое как `http://reranker:8080/v1`; обращения к ним выполняются напрямую, без использования
> `HTTP(S)_PROXY` или закреплённого за подключением прокси-сервера). Узлы на любых других
> хостах — компьютере в локальной сети или пире Tailscale — доступны только в том случае, если оператор включает
> флаг функции `RERANK_REMOTE_PROVIDER_NODES` **и** базовый URL узла соответствует политике
> исходящих URL провайдера (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Этап реранкинга подсистемы памяти вызывает этот маршрут через
> интерфейс обратной петли, поэтому то же правило применяется к `rerankProviderModel` в настройках памяти.
>
> **Форматы локальных серверов:** узел вызывается по адресу `<base>/v1/rerank`, а при ответе 404 — по адресу `<base>/rerank`
> (Infinity, TEI). Тело исходящего запроса содержит как написание Cohere/OpenAI (`documents`,
> `return_documents`), так и написание TEI (`texts`, `return_text`), а исходящий ответ
> нормализуется в оболочку Cohere: неперсонифицированный массив TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> от простых шлюзов и формат Voyage `{data: [...]}` — всё возвращается клиенту в виде
> `{results: [{index, relevance_score, document?}]}`, сортируется по оценке и ограничивается значением `top_n`.

> **Обнаружение узлов провайдеров:** модели на OpenAI-совместимом узле провайдера отображаются в `GET /v1/models`
> с префиксом узла. Строки без метаданных конечной точки (что типично для локальных списков `/v1/models`)
> наследуют `apiType` узла, поэтому модели узла `embeddings` имеют `type: "embedding"`, а модели
> узла `rerank` — `type: "rerank"` вместо типа чата по умолчанию; явно заданный
> `supportedEndpoints` в синхронизированной или добавленной вручную строке по-прежнему имеет приоритет.

### Экса и Тавили `provider_options`

Exa и Tavily считывают поля, специфичные для провайдера, из пакета пространства имен: `provider_options.exa` (или `provider_options["exa-search"]`) и `provider_options.tavily` (или `provider_options["tavily-search"]`). Пересылаются только указанные ниже ключи. Каждый из них проверяется на соответствие своей схеме Zod в `open-sse/handlers/search/providerOptionsPassthrough.ts`, и ключ неправильного типа удаляется. Любой другой ключ игнорируется, включая auth, base URL, `stream` и `outputSchema`. Плоские ключи, используемые другими провайдерами (`cx`, `depth`,...), работают как и прежде.

| Поставщик | Поля верхнего уровня                                                                                                                                                                                                                                                                                                                                                      | Вложенный                                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Экса      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоские примитивы), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` объединен с `{ text: true, highlights: true }` по умолчанию |
| Тавили    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                         |

Общие поля всегда выигрывают: `query`, `max_results`, `filters` (домены), `country` и тема, производная от `search_type`. На Exa `search_type: "news"` сохраняет `category: "news"`. Тавили также принимает `search_type: "finance"` (`topic: "finance"`).

Стоимость поиска Firecrawl фиксируется за запущенный блок из 10 возвращенных результатов по цене 0,002 доллара США (2 кредита) за блок и как минимум один блок за вызов ( [биллинг Firecrawl](https://docs.firecrawl.dev/billing) ): 11 результатов стоят 0,004 доллара США.

Общий `time_range` теперь достигает обоих поставщиков: Exa получает `startPublishedDate` (временная метка ISO ), а Tavily получает `start_date` (`YYYY-MM-DD`). Явная дата в `provider_options` переопределяет сопоставленную дату.

Результаты Exa сохраняют `id`, `highlight_scores`, `summary`, `subpages`, `entities` и `extras` в `provider_raw`. Результаты Tavily сохраняют `images` и `favicon`.

Стоимость поиска соединения записывается в размере 0,005 доллара США для `depth` `fast` и `standard` и 0,05 доллара США для `deep` ( [цена соединения](https://docs.linkup.so/pages/documentation/development/pricing) ), независимо от того, получен ли `depth` из `provider_options` или настроек соединения.

Exa `type: "lite"` (Exa 3.0) принимает меньший набор полей и отклоняет весь запрос, если установлено любое другое поле. В версии lite перед вызовом удаляются `additionalQueries`, `systemPrompt` и все ключи `contents` кроме `text` и `highlights`. Устаревшие `subpages`, `subpageTarget`, `highlights.numSentences` и `highlights.highlightsPerUrl` больше не пересылаются.

Учет затрат осуществляется в плоском реестре `costPerQuery`, за исключением Exa, который соответствует собственным ценам Exa: 0,007 доллара США за вызов для `auto` (и устаревшего `fast`) или 0,004 доллара США для `lite` (и устаревшего `instant`), охватывающего 10 результатов; 0,001$ за каждый последующий результат; и 0,001 доллара США за возвращаемый результат, если установлен `contents.summary`. Тавили записывается по 1 кредиту (0,008 доллара США) для `search_depth` `basic`, `fast` и `ultra-fast` и 2 кредитам (0,016 доллара США) для `advanced` ( [кредиты Tavily API](https://docs.tavily.com/documentation/api-credits) ). Звонок с помощью `auto_parameters: true`, который Тавили повышает до продвинутого уровня, по-прежнему учитывается за 1 кредит.

## API Web Fetch

Извлекает содержимое по URL через настроенного провайдера веб-загрузки (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, использует тот же API-ключ, что и Parallel Search) возвращает только
Markdown — любой другой `format` приводит к ответу `400` — и ограничивает размер содержимого 100 000 символами. Если
саму целевую страницу извлечь невозможно, вышестоящий сервис сообщает об этом внутри ответа HTTP 200;
OmniRoute преобразует такой ответ в `422` с фиксированным сообщением.

| Метод | Путь            | Описание                                                                          |
| ----- | --------------- | --------------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Загружает/извлекает данные по URL — тело проверяется с помощью `v1WebFetchSchema` |

**Аутентификация:** Bearer API-ключ (`extractApiKey` + `isValidApiKey`). Политика применяется через `enforceApiKeyPolicy`.

**Резервное переключение с учётом квоты (#8297):** если явный `provider` не указан, пул
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) обходится в фиксированном
порядке приоритета (сначала полностью используется первый провайдер) — настроенный провайдер с ограниченной частотой запросов пропускается
вместо немедленного завершения запроса, а повторяемая ошибка вышестоящего сервиса или ошибка квоты
(HTTP 429 всегда; 402/403 для бесплатных тарифов Firecrawl/Tavily/TinyFish с ограничениями квоты —
не для Jina Reader и никогда для обычного некорректного запроса 400) приводит к переходу
к следующему ещё не испробованному провайдеру с настроенными учётными данными во время выполнения запроса. Когда все провайдеры в
пуле исчерпаны, конечная точка возвращает единый ответ `429` (с заголовком `Retry-After`)
вместо прежнего обобщённого ответа `400`. Если явно запрошен `provider`,
**скрытое** резервное переключение не выполняется — явный провайдер с ограниченной частотой запросов или ошибкой
возвращает собственную ошибку (`429` при ограничении частоты запросов, в противном случае —
статус вышестоящего сервиса).

## Потоковая передача через WebSocket

```bash
GET /v1/ws?handshake=1
```

Проверяет рукопожатие обновления соединения до WebSocket и возвращает примеры сообщений проводного протокола (`request`, `cancel`). Фактические кадры WS обрабатываются встроенным WS-сервером вне таблицы маршрутов Next.js.

**Аутентификация:** Bearer API-ключ во время рукопожатия.

### Responses API через WebSocket (только codex)

```bash
# Тот же хост и порт, что и у HTTP API (по умолчанию 20128); обновите соединение:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (или: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Первым кадром ОБЯЗАТЕЛЬНО должен быть response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Прокси Responses API через WebSocket подключён **исключительно к `codex`** (бэкенду ChatGPT).
Он прослушивает тот же порт, что и API/панель управления, по путям `/v1/responses`,
`/responses` и `/api/v1/responses`. При получении первого кадра `response.create` он
выполняет аутентификацию и подготовку через внутренний мост `codex-responses-ws`, выбирает
OAuth-подключение codex и создаёт туннель к `wss://chatgpt.com/backend-api/codex/responses`
через транспорт `wreq-js`. **Модели, не относящиеся к codex, отклоняются** (`codex_ws_provider_required`).
Для маршрутизации с распределением квоты используйте `model: "qtSd/<group>/codex/<model>"`. Реализация находится в
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Аутентификация:** Bearer API-ключ во время рукопожатия. Встроенный HTTP-сервер (`server-ws.mjs`)
должен быть активной точкой входа (по умолчанию это так, если существует `app/server-ws.mjs`).

#### Идентификатор модели: используйте простой идентификатор ChatGPT (без префикса `codex/`)

**Codex CLI** от OpenAI проверяет имя модели на стороне клиента, когда
`supports_websockets = true`, и **отклоняет идентификаторы с префиксом провайдера**, такие как
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Передавайте **простой** идентификатор (например, `gpt-5.5`). Мост OmniRoute
работает только с codex, поэтому перед созданием туннеля к вышестоящему сервису он повторно разрешает простой идентификатор как модель codex
(`resolveCodexWsModelInfo`) — даже несмотря на то, что простой идентификатор
`gpt-5.5` при использовании HTTP в ином случае был бы направлен к другому провайдеру.

#### Настройка OpenAI Codex CLI

Направьте Codex CLI на OmniRoute, добавив пользовательского провайдера с поддержкой WebSocket
в `~/.codex/config.toml` (используйте отдельный `CODEX_HOME`, чтобы не изменять
существующую конфигурацию):

```toml
model = "gpt-5.5"                 # простой идентификатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без завершающей косой черты; URL для WS формируется автоматически (в рабочей среде используйте https/wss)
wire_api = "responses"                    # единственное поддерживаемое значение с февраля 2026 года
supports_websockets = true                # включает транспорт Responses через WS
env_key = "OMNIROUTE_API_KEY"             # содержит API-ключ OmniRoute (Bearer)
```

```bash
codex exec "Responda apenas: PONG"
```

CLI обновляет соединение по адресу `base_url + /responses` до WebSocket, а OmniRoute туннелирует его
к выбранному OAuth-подключению codex. Работа полностью проверена на локальном
сервере: ChatGPT возвращает `codex.rate_limits` + `response.created` и передаёт
результат потоково.

## Самостоятельный просмотр использования (`/api/usage/om-usage`)

Любой API-ключ может просматривать **собственные** данные об использовании и квотах — управленческая аутентификация не требуется. Это конечная точка, которую
клиент (CLI, панель OmniCopilot) использует, чтобы показать владельцу ключа его расходы.

```bash
# Текстовый формат (исторически сложившийся контракт — обычный текст для терминала)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Структурированный формат — используется пользовательским интерфейсом
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Для ключа должен быть включён параметр **`allowUsageCommand`** (по умолчанию отключён — менеджер API-ключей
на панели управления переключает его отдельно для каждого ключа). Без него конечная точка отвечает кодом `403`.

`?format=json` возвращает дискриминируемую структуру, поэтому вызывающая сторона никогда не считывает поле данных из
ответа с отказом. При успешном выполнении:

```jsonc
{
  "allowed": true,
  // присутствует только в том случае, если для ключа включены индивидуальные лимиты использования (дневные/недельные в USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // снимок квоты выбранного провайдера или null, если в кеше пока ничего нет:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // снимки всех подключений, чтобы пользовательский интерфейс мог отображать несколько провайдеров рядом:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При отказе (`401` — неверный ключ / `403` — доступ запрещён) тот же маршрут возвращает
`{ "allowed": false, "error": { "message": "…" } }` — присутствующее, но пустое значение `personal`/`provider`
(ключ разрешён, но данные пока не получены) представляет собой состояние, отличное от отказа, и различить их
можно только в JSON-формате.

**Аутентификация:** собственный API-ключ Bearer вызывающей стороны, проверяемый с помощью `isValidApiKey` — это _не_
интерфейс управления (`/api/keys/…`), который по-прежнему защищён с помощью `requireManagementAuth`.

### Исходные и скорректированные с учётом порога проценты квоты

При использовании `/api/usage/om-usage` вызывающим сторонам следует учитывать различие между
процентами, представленными в **текстовом выводе**, и структурированным **JSON-выводом**:

| Аспект                     | Текстовый формат (`/api/usage/om-usage` / `@@om-usage`)                                                   | JSON-формат (`?format=json`)                                                                                |
| :------------------------- | :-------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------- |
| **Поле вывода**            | `NN% left` (например, `20% left`)                                                                         | `provider.quotas` / `providers[].quotas`                                                                    |
| **Измерение**              | **Полезный лимит с поправкой на порог**: оставшаяся ёмкость сверх порогового значения                     | **Исходная квота вышестоящего провайдера**: нескорректированное измерение                                   |
| **Масштабирование порога** | Масштабируется с помощью `effectiveRemainingPercent()`, чтобы защищённый резерв отображался как `0% left` | Отсутствует (исходные значения снимка, сообщённые провайдером)                                              |
| **Данные порога**          | Учитываются в отображаемом проценте                                                                       | Хранятся в `quotaWindowThresholds` для каждого подключения (или используются значения сервера по умолчанию) |
| **Основной потребитель**   | Интерактивные CLI, терминальные подсказки, операторы                                                      | Программные интеграции, панели мониторинга, аналитика, средства учёта расходов                              |

#### Формула корректировки с учётом порога

OmniRoute поддерживает упреждающие пороги квот для предотвращения исчерпания ресурсов вышестоящего провайдера (настраиваются через
`quotaWindowThresholds` подключения, значения провайдера по умолчанию или глобальные параметры отказоустойчивости). Когда для окна квоты
активен порог отсечения (например, `cutoff = 25%`), средство текстового отображения рассчитывает оставшийся лимит следующим образом:

- Если `remaining <= cutoff`: возвращает `0%`.
- Если `remaining > cutoff`: возвращает `((remaining - cutoff) / (100 - cutoff)) * 100`.

В форматированном текстовом выводе результат округляется до ближайшего целого числа (`Math.round(...)`).

#### Наглядный пример

Рассмотрим окно провайдера с **60% исходного использования** (следовательно, остаётся **40% исходной квоты**) и настроенным
порогом отсечения в размере **25% оставшейся квоты**:

| Представление                      | Расчёт                                             | Остаток |           Подразумеваемое использование           |
| :--------------------------------- | :------------------------------------------------- | :-----: | :-----------------------------------------------: |
| **Исходный JSON (`?format=json`)** | Снимок вышестоящего провайдера (`quotas[window]`)  | **40%** |                      **60%**                      |
| **Текстовый формат (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (если рассчитывать как `100 - remaining`) |

- **Почему в тексте указано, что осталось 20%:** Из 40% физической квоты, оставшейся в учётной записи, 25% зарезервировано
  политикой отсечения. До того момента, когда маршрутизатор прекратит направлять запросы этому подключению, у вызывающей стороны
  остаётся только 15% из 75% доступного запаса. Масштабирование гарантирует, что подключение будет сигнализировать об исчерпании
  (`0% left`) именно тогда, когда маршрутизация прекратится.
- **Почему JSON сохраняет исходные значения:** Полезная нагрузка JSON возвращает точный снимок провайдера (`UsageSnapshot`),
  чтобы внешние инструменты имели доступ к достоверным данным об использовании ресурсов вышестоящего провайдера и параметру
  `quotaWindowThresholds` на уровне подключения без необратимого масштабирования на стороне сервера.

#### Рекомендации по миграции потребителей

Если внешняя интеграция (например, плагин редактора или расширение агента) ранее извлекала данные из текстовой
конечной точки (`NN% left`) и вычисляла процент использования как `100 - NN`, то переход на `?format=json` означает:

- Необработанные значения JSON будут отражать **фактическое потребление на вышестоящем уровне** (в приведённом выше примере использовано 60%).
- Если интеграции необходимо сохранить семантику доступного остатка текстовой конечной точки, она может вычислить
  эффективный остаток на стороне клиента, используя `quotaWindowThresholds` для переопределений на уровне подключения.

## Семантический кеш

```bash
# Получить статистику кеша
GET /api/cache/stats

# Очистить все кеши
DELETE /api/cache/stats
```

Пример ответа:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Влияние на задержку

При ПОПАДАНИИ в семантический кеш ответ возвращается из кеша **без вызова
вышестоящего сервиса**, поэтому указанная задержка `X-OmniRoute-Response-Latency`
близка к нулю (независимо от исходной задержки вышестоящего сервиса). Клиенты,
чувствительные к задержке (бенчмаркинг, мониторинг p50/p99), должны проверять
заголовок ответа `X-OmniRoute-Cache-Latency`:

| Значение        | Значение                                                                               |
| --------------- | -------------------------------------------------------------------------------------- |
| `synthetic`     | Ответ получен из кеша; задержка не отражает реальное время ответа вышестоящего сервиса |
| _(отсутствует)_ | Ответ получен в результате реального вызова вышестоящего сервиса                       |

### Обход кеша для отдельных ключей

Ключи API могут отключить чтение из семантического кеша с помощью `cacheDefaultMode`:

| Значение | Поведение                                                                   |
| -------- | --------------------------------------------------------------------------- |
| `legacy` | Обычное поведение кеша (по умолчанию)                                       |
| `bypass` | Полностью пропустить поиск в кеше; всегда обращаться к вышестоящему сервису |

Задайте при создании ключа (`POST /api/keys`) или обновлении (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Обход кеша для отдельного запроса

Любой запрос может обойти кеш независимо от настроек ключа:

```
X-OmniRoute-No-Cache: true
```

Для синхронизированных/импортированных моделей `PUT /api/provider-models` принимает `provider`, `modelId` и

сбрасывает его, восстанавливая значение по умолчанию. `GET /api/provider-models?provider=<provider>` возвращает эти
значения в `modelOutputOverrides`, включая модели без строки пользовательской модели. Переопределение
использует возможность среды выполнения `max_output_tokens` и сохраняется после повторной синхронизации модели. Страница
OpenAI-совместимого провайдера предлагает те же элементы управления для изменения/сброса и отмечает модели с явно заявленной поддержкой компьютерного зрения.

Пользовательские узлы Chat Completions адаптируют явный отказ от рассуждений к вышестоящему бэкенду.
Успешная проверка подключения автоматически выбирает элементы управления шаблоном чата для каждого точного идентификатора модели,
чья запись `/models` подтверждает распознанное значение `owned_by`: `vllm`, `sglang` или `llamacpp`.
Прозрачные OpenAI-совместимые обёртки могут сохранять исходную запись модели во вложенном
объекте `openai`; обнаружение охватывает до трёх таких уровней вложенности. Модели с отсутствующими, неизвестными или
противоречивыми данными о владельце сохраняют стандартное поведение OpenAI. При обнаружении повторно используется существующий запрос каталога,
токены завершения не генерируются, а результат обнаружения аннулируется при изменении эндпоинта подключения.

Чтобы зафиксировать поведение для бэкенда, который не предоставляет эти метаданные, используйте существующий API
частичного обновления провайдера:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Отправьте это тело с помощью `PUT /api/providers/<connection-id>`. Для этого подключения явно заданная
интенсивность рассуждений `none` передаётся как `chat_template_kwargs.thinking=false` и
`chat_template_kwargs.enable_thinking=false`. Явные нативные значения шаблона сохраняют приоритет,
если только серверное правило рассуждений не задаёт интенсивность принудительно. Настройка применяется только тогда, когда пользовательское
OpenAI-совместимое подключение отправляет тело Chat Completions; запросы Responses и стандартные
провайдеры сохраняют нативную структуру запросов. Установите для `reasoningControl` значение `openai`, чтобы принудительно включить стандартную
сквозную передачу OpenAI-параметра `reasoning_effort`, либо не указывайте его/задайте `null`, чтобы использовать автоматическое обнаружение.

Запросы классификатора автоматического режима Claude Code по умолчанию отключают нативное рассуждение, если
не содержат явных элементов управления рассуждением. Обнаружение использует системный маркер классификатора в запросах
формата Claude, а не имена моделей или ограничения завершения. Явные параметры тела, поддерживаемые заголовки интенсивности/рассуждения,
правила маршрутизации и вычисленная интенсивность рассуждений модели сохраняют существующий приоритет. Оба этапа классификатора
сохраняют свои промпты, ограничения завершения, стоп-последовательности и фактические решения вышестоящего сервиса
о разрешениях; второй этап по-прежнему может выводить запрошенное видимое рассуждение как обычный текст.

### Версия и канал выпуска

```bash
GET /api/system/version
```

Маршрут управления, доступный только через loopback-интерфейс (требуется аутентификация администратора). Возвращает запущенную версию, последнюю опубликованную версию и состояние автоматического обновления. `releaseChannel` и `channels` — дополнительные поля (ветка 3.8.54); `channel` сохраняет своё значение — режим развёртывания, используемый средством обновления панели управления (`npm`, `source` или `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-канал запущенной сборки: `nightly` для версий `-nightly.*`,
  `next` для других предварительных выпусков (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` для стабильной версии
  более старшей основной ветки, чем `channels.latest`, и `latest` во всех остальных случаях. Применяются те же правила, что и в
  `scripts/release/dist-tag.mjs`, который выбирает npm dist-tag во время публикации.
- `channels` — последняя опубликованная версия для каждого dist-tag, полученная из `npm view omniroute dist-tags` (с резервным
  запросом к реестру по HTTP) и кэшируемая с тем же TTL в 10 минут, что и `latest`. `latest` присутствует всегда
  (резервно используется поле `latest`, затем `"unavailable"`); `next`, `nightly` и `lts` отображаются
  только при наличии соответствующего dist-tag. Запрос с `Cache-Control: no-cache` обновляет результаты обоих запросов.

Модель каналов (`latest` = v3 до выхода общедоступной версии 4.0, `next` = rc, `nightly` = сборки `develop`,
`lts` = исправления v3 после выхода общедоступной версии 4.0) описана в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрибация аудио

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибируйте аудиофайлы с помощью любого настроенного провайдера STT. Первый сегмент пути
выбирает нативного провайдера (`openai/…`, `deepgram/…`). Шлюзы, которые
повторно предоставляют модель другого поставщика, используют квалифицированный идентификатор
(`openrouter/deepgram/nova-3`).

**Запрос:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Ответ:**

## Лимиты токенов

Бюджеты **токенов** для каждого API-ключа (отдельные от указанного выше бюджета в долларах США). Применяются непосредственно при обработке запроса: когда использование ключа в текущем окне достигает лимита, запросы отклоняются с ошибкой `429 Too Many Requests`. Лимиты могут распространяться на конкретную `model`, конкретного `provider` или применяться глобально (`global`) ко всему ключу; если запросу соответствуют несколько лимитов, применяется наиболее строгий из них.

```bash
# Вывести лимиты токенов ключа (включая использование в текущем окне)
GET /api/usage/token-limits?apiKeyId=key-123

# Создать или обновить лимит токенов
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Удалить лимит токенов по идентификатору
DELETE /api/usage/token-limits?id=tl-abc
```

> **Примечания к схеме** (`setTokenLimitSchema`): `apiKeyId` и `scopeType` (`model` | `provider` | `global`) обязательны. `scopeValue` обязателен, если только `scopeType` не равен `global` (например, идентификатор модели для области действия `model` или идентификатор провайдера для области действия `provider`). `tokenLimit` должен быть положительным целым числом (строка преобразуется в число). Необязательные поля: `id` (не указывайте для создания, укажите для обновления), `resetInterval` (`daily` | `weekly` | `monthly`, по умолчанию `monthly`), `resetTime` (`HH:MM`), `enabled` (по умолчанию `true`). Ответы `GET` дополняют каждый лимит полями `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` и `nextResetAt`. Это конечная точка класса управления (аутентификация централизованно обеспечивается конвейером авторизации).

## Обработка запросов

1. Клиент отправляет запрос в `/v1/*`
2. Обработчик маршрута вызывает `handleChat`, `handleEmbedding`, `handleAudioTranscription` или `handleImageGeneration`
3. Определяется модель (напрямую как провайдер/модель либо через псевдоним/комбинацию)
4. Учетные данные выбираются из локальной БД с фильтрацией по доступности учетной записи
5. Для чата: `handleChatCore` проверяет семантический кэш/кэш сигнатур и определяет настройки сжатия комбинации
6. Если включено проактивное сжатие, оно выполняется до преобразования для провайдера (`lite`, Caveman, RTK или их последовательное сочетание)
7. Исполнитель провайдера отправляет запрос вышестоящему сервису
8. Ответ преобразуется обратно в клиентский формат (для чата) или возвращается без изменений (для эмбеддингов, изображений и аудио)
9. Регистрируются использование, аналитика сжатия и журналы запросов
10. При ошибках применяется резервный вариант в соответствии с правилами комбинации

Полное описание архитектуры: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Отказоустойчивость (расширенная)

OmniRoute предоставляет три независимых механизма обработки временных сбоев; указанные ниже конечные точки управления позволяют операторам просматривать и переопределять их состояние:

| Область действия            | Хранилище состояния                          | Просмотр                                  | Сброс / очистка                                                           |
| --------------------------- | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------- |
| Прерыватель провайдера      | `domain_circuit_breakers` + в памяти         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                              |
| Период ожидания подключения | `rateLimitedUntil` в подключениях провайдера | `/api/rate-limits`, `/api/providers/[id]` | (повторное включение выполняется отложенно; очистка через PUT провайдера) |
| Блокировка модели           | Реестр доступности моделей в памяти          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                  |

`PATCH /api/resilience` принимает переопределения прерывателя провайдера в `providerBreaker.oauth` и `providerBreaker.apikey`. Каждый профиль поддерживает `degradationThreshold`, `failureThreshold` и `resetTimeoutMs`; те же поля доступны в Панель управления → Настройки → Отказоустойчивость.

```bash
# Очистить блокировку одной модели
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Удалить все блокировки
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Полное концептуальное описание и значения прерывателя по умолчанию: см. [`CLAUDE.md`](../../CLAUDE.md) → «Состояние среды выполнения отказоустойчивости» и [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Очередь ограничения частоты запросов и механизм автоматического включения

- **Поддерживаемый способ записи**: `POST /api/rate-limits` с телом `{"connectionId": "<id>", "enabled": true|false}` — поддерживаемая конечная точка управления для включения и отключения защиты подключения от превышения лимита запросов. `PUT /api/providers/[id]` намеренно не изменяет и не переключает `rateLimitProtection` (#11278).
- **Семантика `enabled: false`**: Установка `enabled: false` удаляет явно заданную защиту подключения, но **не** исключает активное подключение с API-ключом из глобального механизма автоматического включения (`autoEnableApiKeyProviders = true`). В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значения `false` и `undefined` эквивалентны; активные подключения с API-ключом без явно заданной защиты остаются защищёнными глобальным механизмом автоматического включения.
- **Глобальное отключение**: Чтобы использовать подключения с API-ключом без очередей ограничения частоты запросов, глобально отключите этот защитный механизм с помощью `RATE_LIMIT_AUTO_ENABLE=false` (переменная среды) или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Настройки → Отказоустойчивость / `PATCH /api/resilience`).

## Сервер MCP

OmniRoute поставляется со встроенным сервером Model Context Protocol с 3 транспортами (stdio, SSE, streamable-http) и инструментами с разграниченными областями доступа. Приведённые ниже эндпоинты панели управления получают данные о состоянии и аудите, а также проксируют HTTP-транспорты.

| Метод | Путь | Описание |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Проверка активности, транспорт, состояние подключения, последний вызов, наиболее используемые инструменты, процент успешных запросов за 24 часа |
| GET | `/api/mcp/tools` | Список инструментов MCP с полями `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Открытие потока SSE для транспорта SSE (возвращает `503`, если MCP отключён или транспорт не совпадает) |
| POST | `/api/mcp/sse` | Отправка фрейма JSON-RPC через транспорт SSE |
| GET | `/api/mcp/stream` | Открытие SSE-стороны транспорта Streamable HTTP (сообщения, инициируемые сервером) |
| POST | `/api/mcp/stream` | Отправка фрейма JSON-RPC через транспорт Streamable HTTP |
| DELETE | `/api/mcp/stream` | Завершение сессии Streamable HTTP |
| GET | `/api/mcp/audit` | Запрос журнала аудита — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Агрегированная статистика аудита (общее количество, процент успешных запросов, средняя длительность, наиболее используемые инструменты) |

**Аутентификация:** транспорты `sse`/`stream` используют отдельный механизм аутентификации MCP (Bearer-ключ API с областью доступа `mcp`); маршруты `status`/`tools`/`audit*` доступны для чтения из панели управления (дополнительная аутентификация, помимо доступа к хосту панели управления, не требуется).

> Оба HTTP-транспорта управляются параметрами `settings.mcpEnabled` и `settings.mcpTransport` — при несовпадении транспорта возвращается `400`, а если MCP отключён — `503`.

## Сервер A2A

OmniRoute предоставляет конечную точку A2A (Agent-to-Agent) JSON-RPC 2.0, а также REST-обёртку для проверки и использования в панели мониторинга.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # необязательно, если не задана переменная OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Поддерживаемые методы (все зависят от `settings.a2aEnabled`):

| Метод            | Описание                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Синхронное выполнение навыка; возвращает `{task, artifacts, metadata}` |
| `message/stream` | Потоковое выполнение того же набора навыков через SSE                  |
| `tasks/get`      | Получение задачи по `taskId`                                           |
| `tasks/cancel`   | Отмена задачи по `taskId`                                              |

Встроенные навыки: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Карточка агента

```bash
GET /.well-known/agent.json
```

Возвращает общедоступную карточку агента A2A (имя, описание, возможности, каталог навыков, схему аутентификации), которая публично кэшируется на 1 час. Аутентификация не требуется.

### Вспомогательные REST-маршруты

| Метод | Путь                         | Описание                                                                                                          |
| ----- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Состояние A2A + статистика задач + сводка кэшированной карточки агента                                            |
| GET   | `/api/a2a/tasks`             | Список задач — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не реализовано как вспомогательный REST-маршрут — создавайте через JSON-RPC `message/send`)                      |
| GET   | `/api/a2a/tasks/[id]`        | Получение одной задачи                                                                                            |
| POST  | `/api/a2a/tasks/[id]/cancel` | Отмена задачи                                                                                                     |

**Аутентификация:** вспомогательные REST-маршруты работают без административной аутентификации (доступны для чтения из панели мониторинга); маршрут JSON-RPC `/a2a` использует Bearer `OMNIROUTE_API_KEY`, если он настроен.

## Аутентификация

Описание четырёх семейств учётных данных (сессия панели управления, локальный токен CLI, токен доступа `oma_live_…`, API-ключ с областью действия управления) и их отличий от ключей инференса см. в разделе [Аутентификация управления](../guides/MANAGEMENT-AUTH.md).

- Маршруты панели управления (`/dashboard/*`) используют cookie `auth_token`
- При входе используется сохранённый хеш пароля; резервный вариант — `INITIAL_PASSWORD`
- Параметр `requireLogin` можно переключать через `/api/settings/require-login`
- Маршруты `/v1/*` могут требовать API-ключ Bearer, если `REQUIRE_API_KEY=true`
- Термины «токен управления» / «API-ключ с областью действия управления» в этом справочнике означают одно из семейств, описанных в указанном руководстве, а не дополнительный неопределённый тип секрета

> **Критическое изменение (v3.8.0)** — `/api/v1/agents/tasks/*` и эндпоинты управления периодом ожидания теперь требуют **аутентификацию управления** (cookie панели управления `auth_token` или API-ключ с областью действия управления). Клиенты, которые ранее обращались к этим маршрутам без аутентификации, получат ответ `401 Unauthorized`. См. коммит `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
