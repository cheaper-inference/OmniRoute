Основной справочник по API OmniRoute. В нём описывается общедоступный интерфейс `/v1` и наиболее часто используемые конечные точки управления; машиночитаемый [`docs/openapi.yaml`](../openapi.yaml) и дерево маршрутов в `src/app/api/` являются исчерпывающими источниками.

Сведения о специализированном протоколе, совместимом с OpenAI, и матрице возможностей провайдеров см. в
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md).

Каждое развёртывание предоставляет собственную копию спецификации по адресу `/openapi.yaml`, сгенерированную из `docs/openapi.yaml` во время сборки. Она содержит версию сборки и относительный URL сервера (`./`), поэтому запросы остаются на хосте, с которого был получен документ. Инструмент, импортирующий загруженный файл, не располагает информацией об этом хосте, поэтому базовый URL необходимо задать вручную.

## Завершение чата

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Пользовательские заголовки

| Header                   | Направление | Описание                                                                                                                                                                                                                                            |
| ------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Запрос      | Установите значение `true`, чтобы обойти кэш                                                                                                                                                                                                        |
| `x-omniroute-no-memory`  | Запрос      | Установите значение `true`, чтобы пропустить внедрение памяти и навыков для этого запроса (аналогично no-cache; устраняет накладные расходы на токены и стоимость каждого вызова)                                                                   |
| `X-OmniRoute-Progress`   | Запрос      | Установите значение `true` для событий прогресса                                                                                                                                                                                                    |
| `X-Session-Id`           | Запрос      | Ключ закрепления сеанса для привязки внешнего сеанса                                                                                                                                                                                                |
| `x_session_id`           | Запрос      | Также принимается вариант с подчёркиванием (прямой HTTP)                                                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | Запрос      | Предоставленный вызывающей стороной тег сеанса/диалога (также передаётся в память). Если указан, сохраняется без изменений в `call_logs.session_tag` для атрибуции стоимости по сеансам (#8249) — при отсутствии никогда не создаётся автоматически |
| `Idempotency-Key`        | Запрос      | Ключ дедупликации (окно 5 с)                                                                                                                                                                                                                        |
| `X-Request-Id`           | Запрос      | Альтернативный ключ дедупликации                                                                                                                                                                                                                    |
| `x-omniroute-connection` | Запрос      | Закрепляет запрос к одной модели за одним подключением провайдера (учётной записью) по его идентификатору — см. [Закрепление учётной записи для запроса](#account-pinning-per-request)                                                              |
| `X-OmniRoute-Cache`      | Ответ       | `HIT` или `MISS` (для непотоковой передачи)                                                                                                                                                                                                         |
| `X-OmniRoute-Idempotent` | Ответ       | `true`, если выполнена дедупликация                                                                                                                                                                                                                 |
| `X-OmniRoute-Progress`   | Ответ       | `enabled`, если отслеживание прогресса включено                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Ответ       | Фактически использованный OmniRoute идентификатор сеанса                                                                                                                                                                                            |
| `X-OmniRoute-Request-Id` | Ответ       | Идентификатор корреляции запроса (если известен)                                                                                                                                                                                                    |
| `X-OmniRoute-Version`    | Ответ       | Версия сборки OmniRoute (присутствует всегда)                                                                                                                                                                                                       |
| `X-OmniRoute-Cost-Saved` | Ответ       | Сумма в USD, сэкономленная благодаря кэшу при `HIT` (только для попаданий в кэш)                                                                                                                                                                    |
| `X-OmniRoute-Decision`   | Ответ       | Трассировка маршрутизации: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` — комбинированная стратегия или `single` для запроса без комбинации) — всегда присутствует в ответах о завершении                                          |

> Примечание для Nginx: если вы используете заголовки с подчёркиваниями (например, `x_session_id`), включите `underscores_in_headers on;`.

#### Закрепление учётной записи для запроса

Если у провайдера несколько подключений (учётных записей или ключей), OmniRoute обычно выбирает одно из них
с помощью стратегии выбора учётной записи. Вместо этого запрос может закрепить одно конкретное подключение
с помощью заголовка `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Где найти идентификатор.** Откройте страницу провайдера в дашборде
  (**Dashboard → Providers → <provider>**) и нажмите на чип с идентификатором `xxxxxxxx…` в строке
  подключения — это скопирует полный идентификатор подключения.
- **Какие запросы его учитывают.** Запросы к одной модели (`provider/model`) на
  `/v1/chat/completions`, `/v1/messages` и `/v1/responses`. Комбинации игнорируют этот заголовок:
  закрепляйте аккаунт для каждого шага комбинации через собственное подключение этого шага.
- **Закрепление является строгим, а не предпочтительным.** Используется исключительно закреплённое
  подключение. Сбой внутри запроса фиксирует период ожидания для аккаунта, но **не** переключает запрос
  на соседний аккаунт того же провайдера.
- **Период ожидания и исчерпание квоты снимают закрепление.** Пока для закреплённого подключения
  действует период ожидания, квота исчерпана или подключение заблокировано политикой квот, последующие
  запросы переключаются на другие подключения провайдера — точно так же, как незакреплённый трафик.
- **Неизвестные или отключённые идентификаторы приводят к ошибке.** Если идентификатор отсутствует
  в активном пуле провайдера (подключение удалено, деактивировано или принадлежит другому провайдеру),
  подходящий аккаунт не находится, поэтому запрос завершается ошибкой вместо незаметной маршрутизации
  в другое место.

Claude Code передаёт пользовательские заголовки через `ANTHROPIC_CUSTOM_HEADERS`. Добавьте его в блок
`env` файла `~/.claude/settings.json` или в файл `.claude/settings.json` на уровне проекта, чтобы
закрепить другой аккаунт для каждого проекта:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Источник: `src/sse/handlers/chat.ts` (чтение заголовка), `src/sse/services/auth.ts` и
`src/sse/services/sessionAffinityPin.ts` (снятие закрепления и проверка отсутствия в пуле).

> **Заголовки телеметрии стоимости:** ответы об успешном выполнении запросов без потоковой передачи также содержат набор заголовков телеметрии стоимости `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фиксированные 10 знаков после запятой; `0.0000000000` для бесплатных запросов или запросов без указанной стоимости), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` и `X-OmniRoute-Fallback-Attempts` (только если значение > 0), а также `X-OmniRoute-Request-Id` и `X-OmniRoute-Version`. Они добавляются для chat completions, `/v1/responses`, `/v1/messages`, **а также для конечных точек мультимедиа** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` и `/v1/moderations` (стоимость всегда `0`). Стоимость мультимедиа рассчитывается по каждой модальности (за изображение, за секунду, за символ, за единицу поиска), если данные о ценах доступны; в противном случае используется `0` (fail-open).

> **Семантика стоимости при попадании в кэш:** при попадании в семантический кэш (`X-OmniRoute-Cache-Hit: true`) вызов вышестоящего сервиса не выполняется, поэтому `X-OmniRoute-Response-Cost` равен `0.0000000000` (это **добавочная** стоимость обработки попадания в кэш). Исходная стоимость или стоимость, которая была бы начислена, указывается отдельно в `X-OmniRoute-Cost-Saved`. Системы, обрабатывающие данные для биллинга, должны суммировать `X-OmniRoute-Response-Cost` (попадания в кэш ничего не стоят); для аналитики кэша можно агрегировать `X-OmniRoute-Cost-Saved`.

## Эксклюзивные управляемые лизы сессий

Эксклюзивное управление лизингом сессий — это опциональный, нейтральный по отношению к клиенту контракт маршрутизации: один активный владелец удерживает одно подходящее соединение OmniRoute. Он не предоставляет модель в лизинг, не требует OAuth, не идентифицирует конкретного клиента и не требует конкретного провайдера.

Аутентифицирующий API-ключ должен иметь область действия `lease:exclusive` и явный непустой список `allowedConnections`. Граница изменения базы данных обеспечивает наличие обоих полей одновременно при создании ключа и выполнении частичных обновлений.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успешные ответы на операции acquire, renew и release содержат временные метки, `state` и точное положительное значение `generation`, но никогда не содержат выбранное соединение или учётные данные. Операции renew и release передают значение generation в теле JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Активный владелец лизы может явно запросить безопасные с точки зрения конфиденциальности отображаемые метаданные для своей текущей привязки:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Это опциональное действие status защищено непрозрачным идентификатором владельца, аутентифицированным управляемым API-ключом и точным активным поколением в рамках одной транзакции базы данных. `displayName` содержит только обрезанное настроенное имя соединения; если безопасное настроенное имя отсутствует, значение равно `null`. OmniRoute никогда не подставляет адрес электронной почты или сгенерированную идентичность аккаунта. Значение provider — это нечувствительная к данным отображаемая метка, а не сгенерированный идентификатор совместимого провайдера. Учётные данные, токены, cookie, необработанные идентификаторы соединений или API-ключей, хеши владельцев, секреты защиты от устаревших запросов и внутренние данные маршрутизации исключаются.

Запросы с неверным ключом, неверным владельцем, устаревшим поколением, отсутствующим, истёкшим, освобождённым или инвалидированным объектом во всех случаях возвращают одну и ту же ошибку `409 LEASE_FENCE_STALE` без метаданных соединения. Клиент, получивший ответ об ожидании доступной ёмкости, не имеет активной привязки, которую можно было бы проверить. Когда маршрутизация переключает активную лизу, то же поколение остаётся действительным, а status атомарно возвращает новую привязку, никогда не возвращая старую. Существующие клиенты не изменяются, поскольку ответы acquire, renew, release и ожидания сохраняют прежнюю структуру.

Этот серверный контракт не изменяет стандартный OpenAI Codex `/status`. Стандартный Codex в настоящее время сообщает своего провайдера модели и встроенное состояние аутентификации/аккаунта, но не отображает произвольные метаданные аккаунта пользовательского провайдера; последующая интеграция с клиентом должна вызывать это действие и самостоятельно решать, как отображать `connection.displayName`.

Каждый управляемый запрос инференса затем передаёт оба управляющих заголовка:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точные значения владельца и поколения, активное соединение и аутентифицированный API-ключ проверяются непосредственно перед каждой поддерживаемой попыткой обращения к вышестоящему сервису. Повторное использование владельца и поколения с другим ключом завершается ошибкой, даже если этот ключ разрешает использование того же соединения. Необработанные идентификаторы владельцев не сохраняются, не записываются в журналы, не хранятся в снимке запроса и не передаются вышестоящему сервису.

Временная конкуренция возвращает HTTP `429` с `Retry-After` и:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Этот ответ означает только то, что обычный подходящий набор соединений был непустым, а каждое свободное соединение-кандидат удерживалось чужой активной лизой. Неподдерживаемые модели/провайдеры, несоответствие политике, период охлаждения, квоты, состояние работоспособности и другие обычные причины отсутствия подходящих соединений сохраняют существующие ответы OmniRoute.

### `x-omniroute-compression`

Переопределение плана сжатия для отдельного запроса. Имеет наивысший приоритет — превосходит переопределение комбинации маршрутизации, активный профиль, автоматический триггер и Default на панели. Значения:

| Значение      | Эффект                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `off`         | Для этого запроса сжатие не выполняется.                                                            |
| `default`     | Профиль Default, определённый панелью (активный профиль игнорируется). Движки с потерями отключены. |
| `safe`        | Только дедупликация и свёртка пробелов.                                                             |
| `allow-lossy` | Сохранить план оператора для этого запроса, включая сводки и перезапись стиля.                      |
| `engine:<id>` | Один движок, если он включён, например `engine:rtk`. Явное включение этого движка для запроса.      |
| `<combo>`     | Именованная комбинация, сначала сопоставляемая по имени (без учёта регистра), затем по id.          |

Примечания:

- Неизвестные значения игнорируются (запрос никогда не отклоняется); разрешение продолжается по обычному порядку приоритетов оператора.
- Если несколько комбинаций имеют одно имя, передавайте combo **id** для детерминированного сопоставления.
- Комбинацию с именем `off` или `default` нельзя выбрать по имени (сначала интерпретируются эти ключевые слова); ссылайтесь на такую комбинацию по её id.
- Главный переключатель сжатия является жёстким ограничением: если сжатие глобально отключено, этот заголовок не может его включить.

Применённый план возвращается в заголовке ответа:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

где `<source>` — одно из значений `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Эмбеддинги

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Доступные провайдеры: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Идентификаторы каталога имеют формат `provider/model` (пример: `jina-ai/jina-embeddings-v5-omni-small`). Также разрешаются чистые идентификаторы моделей Jina, присутствующие в реестре (например, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`). Для Jina embed/rerank/classify/segment сначала используются учётные данные `jina-ai` из панели управления; `JINA_AI_API_KEY` используется только как резервный вариант, если ключ панели управления отсутствует. Карточка `jina-reader` предназначена только для Reader / `r.jina.ai` (`POST /v1/web/fetch`) и никогда не обслуживает эмбеддинги или rerank.

Модели реестра, заявляющие поддержку мультимодальности, также принимают до 32 структурированных элементов, независимых от провайдера. Типы медиаэлементов: `text`, `image`, `audio`, `video` и `document`. Их `source` представляет собой либо `{"type":"url","url":"https://..."}`, либо `{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` и псевдоним семейства `jina-ai/jina-embeddings-v5-omni` → omni-small) также принимает собственные документы Jina EmbeddingsV5Request и **передаёт их без изменений** на `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Собственные значения `{ image | audio | video | pdf }` могут быть общедоступным URL HTTPS, URI `data:` или необработанными данными base64. OmniRoute не преобразует эти объекты в строки и не загружает собственные URL изображений — Jina получает общедоступные медиафайлы самостоятельно. Дополнительные поля Jina (`task`, `normalized`, `truncate`, `embedding_type`) передаются дальше. Текстовые SKU Jina по-прежнему отклоняют документы, содержащие нетекстовые данные.

Ограничения безопасности и транспорта:

- Удалённые URL медиафайлов должны быть общедоступными и использовать HTTPS. Канонические элементы `{type,source:url}` загружаются на стороне сервера (повторная проверка перенаправлений, ограничение времени ожидания, ограничения размера, общедоступный DNS, фиксация подключения) и встраиваются перед вызовом провайдера. Элементы Jina native `{image:"https://..."}` передаются как есть после той же проверки общедоступного HTTPS; Jina загружает URL.
- Размер встроенных медиафайлов в формате base64 ограничен 8 МиБ в декодированном виде на элемент и 16 МиБ в декодированном виде на весь запрос.

Преобразование для провайдеров (канонические элементы никогда не передаются без изменений):

- Мультимодальные модели Jina: каждый элемент верхнего уровня преобразуется в один объект с ключом, соответствующим модальности (`text` / `image` / `audio` / `video` / `pdf`), с использованием URI `data:` для встроенных медиафайлов; один вектор на каждый элемент верхнего уровня.
- Семейство Gemini Embedding 2: один массив верхнего уровня преобразуется в один собственный запрос `models/{model}:embedContent` с `content.parts` (`text` или `inline_data`).
- llama.cpp (`llama-cpp/<model>`, любая модель, загруженная локальным сервером): канонические элементы `text` преобразуются в обычные строки, а `image` / `audio` / `video` — в отдельные объекты `{"content": [part]}`, использующие части содержимого чата llama-server (`image_url`, `input_audio` с форматом `wav` / `mp3` / `flac`, `input_video`) со встроенными данными; один вектор на каждый элемент верхнего уровня. Сервер должен быть запущен с параметрами `--embedding --mmproj …`; без проектора он сам отклоняет медиафайлы. `document` не поддерживается.
- Неизвестные/динамические модели без явно заданных метаданных модальностей отклоняют структурированный ввод с HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Неподдерживаемые сочетания моделей и модальностей возвращают HTTP 400, вместо того чтобы принудительно преобразовывать элемент. Поля расширений, не относящиеся к `input`, в устаревших запросах со строками/токенами по-прежнему передаются без изменений.

```bash
# Перечислить все модели эмбеддингов
GET /v1/embeddings
```

## Генерация изображений

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Доступны следующие провайдеры: OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локальный), ComfyUI (локальный).

`n` возвращает `n` изображений в `data[]`. Для провайдеров, API которых возвращает одно изображение за вызов
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), выполняется `n` отдельных вызовов upstream API — одновременно
не более 4. Фиксированное значение `seed` смещается на индекс вызова (`seed`, `seed + 1`, …),
поэтому изображения отличаются, но остаются воспроизводимыми. Максимальное значение `n` — 10.
Весь запрос завершается с ошибкой, если завершается ошибкой любой вызов. Список форматов с
fan-out — `SINGLE_IMAGE_FANOUT_FORMATS` в
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux использует существующее подключение с API-ключом и принимает префиксы `zenmux/` или `zm/`:

- `zenmux/openai/gpt-image-2` использует API изображений OpenAI от ZenMux. Доступны параметры `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` и `response_format`.
- Другие издатели, например `zm/meta/muse-image-1.0`, используют конечную точку Vertex AI `:predict`
  от ZenMux. Параметр `n` преобразуется в `sampleCount`, `aspect_ratio` — в `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — в `sampleImageSize`. Параметр `size` в пикселях задаёт только соотношение сторон,
  но не гарантированные размеры в пикселях. Поддерживаемые соотношения сторон, разрешения и количества
  изображений зависят от модели.
- `zm/inclusionai/ming-image-0.1-design` самостоятельно выбирает размеры. Не указывайте `size`,
  `aspect_ratio` и `image_size`; явное задание этих значений приводит к ошибке HTTP 400. Форматы PNG,
  JPEG и WebP можно запросить с помощью `output_format`.

Эта интеграция поддерживает генерацию изображений по текстовому описанию, но не редактирование
эталонных изображений. Вывод Vertex нормализуется в `data[].b64_json`; `response_format: "url"`
возвращает upstream URL с протоколом HTTPS или URL данных в формате base64, если доступны только
байты изображения. Пустой или отфильтрованный результат возвращается как ошибка, а не как успешный
ответ без данных. Доступ к моделям зависит от учётной записи ZenMux.
См. [Vertex API ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) и
[API изображений OpenAI](https://docs.zenmux.ai/api/openai/generate-an-image).

Подключение для входа в Microsoft 365 Copilot предоставляет `copilot-m365-web/m365-copilot-image`
через встроенный инструмент изображений Copilot: один раунд Copilot на изображение (`n` от 1 до 4),
параметр `size` влияет только на ориентацию, а изображения возвращаются непосредственно (`b64_json`
или URL данных для `response_format: "url"`). См. [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# Перечислить все модели изображений
GET /v1/images/generations
```

## OCR документов

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` выбирает провайдера OCR с помощью префикса `provider/model`; идентификатор модели без префикса (например,
`mistral-ocr-latest`) сопоставляется с зарегистрированным провайдером, а если `model` не указан, по умолчанию используется
Mistral (`mistral-ocr-latest`). Зарегистрированные провайдеры (`open-sse/config/ocrRegistry.ts`):

| Идентификатор провайдера      | Идентификатор модели | Значение `model`                                                     | Примечания                                                                                                               |
| ----------------------------- | -------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (или без префикса `mistral-ocr-latest`) | Синхронный — ответ возвращается непосредственно из единственного upstream-вызова.                                        |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                          | Асинхронный upstream (`analyze` + опрос) — см. ниже.                                                                     |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                              | Синхронный, через партнёрский endpoint Vertex AI `openapi/chat/completions` — сведения об аутентификации и URL см. ниже. |

Все три провайдера возвращают тело в одном формате Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процесс опроса Azure Document Intelligence

API `analyze` Azure Document Intelligence является асинхронным: исходный запрос возвращает
заголовок `Operation-Location` вместо тела, а результат необходимо получать опросом. Обработчик
(`open-sse/handlers/ocr.ts`) опрашивает этот URL каждую секунду, выполняя до 30 попыток, немедленно завершается с ошибкой (и
не продолжает опрос) при ответе опроса с не-`ok` или статусом `"failed"` и возвращает `504`, если операция всё ещё выполняется после исчерпания лимита попыток. Итоговый ответ Azure
нормализуется в ту же форму `pages`/`markdown`, которая используется Mistral, прежде чем возвращается вызывающей стороне, поэтому клиентскому коду не требуется отдельно обрабатывать провайдера.

### Аутентификация и разрешение endpoint Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` повторно использует ту же аутентификацию Vertex AI, которую OmniRoute уже поддерживает для
обработки чатов и изображений (`open-sse/executors/vertex.ts`): API-ключ подключения представляет собой либо учётные данные Service Account в формате JSON (обмениваемые на краткоживущий токен доступа OAuth через поток JWT bearer), либо уже выпущенный токен доступа OAuth, используемый как есть. URL upstream endpoint — это универсальный партнёрский endpoint Vertex `openapi/chat/completions`, сформированный на основе проекта и региона подключения: явно заданные `providerSpecificData.project`/`providerSpecificData.region` всегда имеют приоритет; в противном случае проект извлекается из `project_id` JSON Service Account, а регионом по умолчанию является `us-central1`. Оба разрешения выполняются в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), а затем используются в
`src/app/api/v1/ocr/route.ts` перед передачей управления в `handleOcr`.

### Цены моделей (`pricing`)

Запись содержит объект `pricing`, если OmniRoute знает цену модели. Цена берётся из таблицы
цен, которую использует учёт расходов: встроенных значений по умолчанию, синхронизированных
цен и переопределений, заданных через `/api/pricing`. Это цены из общего прайс-листа, поэтому
для провайдеров с подпиской также отображается цена за токен.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Поля                                                            | Единица измерения                        | Примечания                                                                                                                                                |
| --------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD за токен, строка с десятичным числом | Совместимо с OpenRouter, экспоненциальная нотация никогда не используется. Два поля кэша отображаются только при наличии цены кэширования.                |
| `input`, `output`, `cached`, `cache_creation`                   | USD за 1 млн токенов, число              | Поля из более ранних версий каталога, сохранённые для существующих клиентов. `reasoning` и `long_context` также отображаются, если они есть в строке цен. |

- **Комбинации** содержат цену своей первой видимой цели. Встроенные комбинации `auto/*`
  выбирают цель во время выполнения запроса, поэтому у них нет `pricing`.
- **Бесплатные модели** показывают `"0"` (и `0`), если их цена равна нулю. Модель без строки
  цен также показывает `"0"`, если каталог помечает её как бесплатную (`free: true`) или она
  указана во встроенном каталоге бесплатных моделей.
- **Неизвестная цена:** запись не содержит ключ `pricing`.
- **Провайдеры с оплатой по кредитам** (например, Kiro) тарифицируют запросы, а не токены. В
  их записях сохраняются имевшиеся ранее числовые поля за 1 млн токенов, но отсутствуют
  строковые поля цены за токен.
- **Варианты** (идентификаторы уровня усилий рассуждения, псевдонимы без размышления, зеркала
  обнаружения и шлюза) копируют цену модели, к которой они направляют запросы.
- Поля содержат только базовые тарифы. Уровни для длинного контекста (числовое поле
  `long_context`) и множители тарифных уровней обслуживания (например, быстрый или flex-режим
  Codex) не изменяют `prompt` или `completion`.
- Объект одинаков для всех способов аутентификации, включая запрос в стиле Anthropic с
  `x-api-key` и `anthropic-version` (ответ по-прежнему имеет вид `{ "object": "list",
"data": [...] }`). Реализация: `src/app/api/v1/models/catalogPricing.ts`.

### Префиксы идентификаторов моделей (`?prefix=`)

Большинство моделей публикуется с **префиксом провайдера**. Используемый префикс определяется
флагом функции `MODELS_CATALOG_PREFIX_MODE` и может быть переопределён **для отдельного
запроса** с помощью параметра запроса — это удобно для клиента, которому нужен
структурированный список без изменения общесерверной настройки для остальных пользователей:

```bash
GET /v1/models?prefix=alias        # один идентификатор на модель — префикс короткого псевдонима
GET /v1/models?prefix=dual         # обе формы (значение по умолчанию на сервере)
GET /v1/models?prefix=canonical    # только полный префикс идентификатора провайдера
```

| Режим       | Выводит                                                 | Примечания                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **и** `claude/claude-sonnet-4-6` | **По умолчанию.** Оба идентификатора направляют запросы к одной модели; это сохраняется для совместимости с конфигурациями клиентов, в которых жёстко задана любая из форм. Каталог становится примерно вдвое больше.          |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Одна запись на модель. Провайдеры без отдельного псевдонима всё равно выводят свою запись, поэтому ничего не теряется.                                                                                                         |
| `canonical` | `claude/claude-sonnet-4-6`                              | Одна запись на модель с полным префиксом идентификатора провайдера. Провайдеры без отдельного псевдонима (например, `antigravity/…`, `agy/…`) также выводят здесь свой единственный идентификатор, поэтому ничего не теряется. |

Зеркало в режиме `dual` также можно распознать без параметра запроса: оно содержит поле
`parent`, указывающее на основной идентификатор.

Клиентам, отображающим средство выбора модели, следует запрашивать `?prefix=alias` — именно
так работает
[расширение OmniCopilot для VS Code](../guides/VSCODE-COPILOT.md).

### Фильтры обнаружения (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` поддерживает дополнительные фильтры обнаружения. Без них ответ не меняется.
Они сужают каталог, который уже виден вызывающей стороне (сначала применяются разрешения
API-ключа), и выполняются до постраничной выборки в стиле OpenAI с помощью `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # все указанные возможности должны быть включены
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` каталога; строки без него считаются `chat`
GET /v1/models?q=sonnet&limit=10                           # регистронезависимое совпадение по идентификатору или имени
```

| Параметр      | Значения                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | неотрицательное целое число, сравнивается с `context_length`                                        |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | от 1 до 200 символов                                                                                |

Неизвестное значение или `min_context`, не являющийся неотрицательным целым числом (например, `1.5`),
возвращает HTTP `400`, а сообщение содержит список допустимых значений. Реализация:
`src/app/api/v1/models/catalogFilters.ts`.

### Краткий список моделей (`POST /v1/models/query`)

`POST /v1/models/query` возвращает короткий детерминированный список из того же каталога с той же
аутентификацией и видимостью для каждого ключа, что и `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Все поля необязательны. Для `capabilities` и `exclude` можно указать массив или строку, разделённую запятыми;
`max_output` сравнивается с `max_output_tokens`. Результаты сортируются по `owned_by`, затем по `id`.
Значение `limit` по умолчанию равно `20`, а значения больше `100` ограничиваются значением `100`. Недопустимый
JSON, неизвестное поле или недопустимое значение возвращает HTTP `400`.

### Индивидуально скрытые модели чата

Модель, помеченная как **Скрытая** на странице своего провайдера, исключается из каталога и при
явном запросе отклоняется с HTTP `404` / `model_not_found`. Проверка использует разрешённых провайдера
и модель, включая псевдонимы провайдеров, префиксы узлов совместимых провайдеров и значения подключений
по умолчанию. Комбинация пропускает скрытые цели и может использовать видимого родственника; если
исполняемых целей не остаётся, возвращается тот же код ошибки. Снятие скрытия вступает в силу при следующем
запросе. Переопределения видимости только для изображений не скрывают модель чата с тем же идентификатором.

Эта индивидуальная настройка модели отделена от
[списков разрешённых/запрещённых моделей](../routing/MODEL_EXPOSURE_LIST.md), которые фильтруют
представление в каталоге и кандидатов для автоматической маршрутизации, сохраняя явную диспетчеризацию.
Разрешения моделей для API-ключа продолжают применяться независимо. Режим префиксов каталога по умолчанию
остаётся `dual`.

### Варианты моделей без размышлений

Для поддерживающих размышления моделей Claude `/v1/models` также рекламирует вариант **без размышлений**,
идентификатор которого имеет префикс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Выбор этого идентификатора (например, в конфигурации Claude Code, которая всегда добавляет блок `thinking`)
разрешается обратно в реальный `<provider>/<model>` с отключённым рассуждением — `thinking:{type:"disabled"}`
на пути `/v1/messages` или с удалёнными полями `reasoning`/`reasoning_effort` на пути
`/v1/chat/completions`. Вариант отображается только для моделей семейства Claude, которые поддерживают
размышления **и** учитывают `disabled` (поэтому, например, модели, поддерживающие только адаптивный режим
и отклоняющие `disabled`, исключаются). Операторы могут принудительно включить или отключить вариант для
каждой модели через `ModelSpec.noThinkingAlias`.

## Генерация аудио ElevenLabs

Настройте подключение провайдера `elevenlabs` в OmniRoute с вашим API-ключом ElevenLabs.
Клиенты проходят аутентификацию с помощью своего ключа **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюз передает сохраненный ключ провайдера как `xi-api-key`. Никогда не отправляйте ключ ElevenLabs
в качестве токена bearer шлюза.

| Метод | Путь                        | Ответ                                         | Категория конечной точки API-ключа |
| ----- | --------------------------- | --------------------------------------------- | ---------------------------------- |
| POST  | `/v1/sound-generation`      | Собственные байты аудио                       | `elevenlabs`                       |
| POST  | `/v1/music`                 | Собственные байты аудио                       | `music`                            |
| POST  | `/v1/music/stream`          | Потоковые байты аудио                         | `music`                            |
| POST  | `/v1/music/detailed`        | Собственное multipart-аудио и план композиции | `music`                            |
| POST  | `/v1/music/detailed/stream` | Собственные метаданные SSE и фрагменты аудио  | `music`                            |
| POST  | `/v1/music/plan`            | JSON-план композиции                          | `music`                            |

Эти конечные точки дополняют существующие маршруты `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` и `/v1/speech-to-text`. Собственные поля JSON
и параметры запроса, такие как `output_format` и `enable_logging`, сохраняются.
Ответы `/v1/music/detailed` сохраняют свои multipart-границы; разбирайте их как multipart.
`/v1/music/detailed/stream` возвращает `text/event-stream` с метаданными композиции и
аудиофрагментами в формате base64 в событиях SSE. Все шесть маршрутов поддерживают предварительные
CORS-запросы.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Короткий звуковой эффект. Длительность: от 0,5 до 30 секунд.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Длительность музыки указывается в миллисекундах: от 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Используйте `/v1/music/stream` с тем же телом JSON для поэтапной передачи аудио. Композиция
принимает ровно одно из `prompt` или `composition_plan`; `/v1/music/plan` требует `prompt`
и опционально принимает `source_composition_plan`. Собственные схемы сохраняют дополнительные
поля провайдера, поэтому версии планов композиции и параметры тонкой настройки передаются в ElevenLabs.

Унифицированная конечная точка `/v1/music/generations` также принимает
`elevenlabs/music_v1`, `elevenlabs/music_v2` и `elevenlabs/music_v2_5`. При активном подключении
ElevenLabs эти модели доступны в каталоге музыки. Эта конечная точка возвращает
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Ее поле `duration` указывается в
секундах и преобразуется в `music_length_ms`; явное значение `music_length_ms` имеет приоритет.
`instrumental` преобразуется в `force_instrumental`, причем собственное поле имеет приоритет.
Для потоковой передачи используйте собственные потоковые конечные точки, а для запросов, основанных
только на плане композиции, — собственную конечную точку композиции.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ограничения конечной точки, модели, бюджета и подключения применяются до вызова вышестоящего сервиса. Собственные
маршруты возвращают коды состояния и тела ошибок вышестоящего сервиса без изменений, включая `402` для
ограничения плана и `429` для ограничения квоты. Заголовки `character-cost`, `song-id`, `request-id` и `retry-after`
сохраняются, если они присутствуют. Наличие бесплатного кредитного баланса не гарантирует доступ ко всем
моделям музыки, форматам вывода или функциям API: ElevenLabs определяет доступность для каждого запроса.
Унифицированная конечная точка сохраняет коды состояния ошибок в нормализованной оболочке ошибок OmniRoute.

Контракты вышестоящего сервиса: [звуковые эффекты](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[композиция музыки](https://elevenlabs.io/docs/api-reference/music/compose) и
[подробности потоковой передачи музыки](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

| GET    | `/api/v1/vscode/{token}/`                 | Псевдоним каталога OpenAI                |

Все маршруты POST используют одну и ту же структуру: `Bearer your-api-key` + тело JSON, проверяемое с помощью Zod (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` и т. д.; см. `src/shared/validation/schemas.ts`). При ошибке проверки схемы возвращается ответ 4xx.

```bash
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Классификация Jina (учётные данные Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Сегментатор Jina

# Поиск Jina (s.jina.ai; псевдонимы провайдера: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Модерация
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — возвращает тело audio/mpeg (или запрошенный формат)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Для Soniox TTS требуется язык и голос: `language` по умолчанию имеет значение "en"; отсутствующий
# голос или стандартное имя голоса OpenAI (alloy, nova, …) заменяется на "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Редактирование изображения (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генерация видео/музыки (идентификатор модели с префиксом провайдера)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Узлы провайдеров rerank:** `POST /v1/rerank` также направляется на совместимые с OpenAI узлы провайдеров
> (oMLX, vLLM, Infinity, TEI за шлюзом и т. д.), адресуемые как `<node-prefix>/<model>`. Узлы обратной связи
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) всегда подходят, как и имена хостов, перечисленные оператором в
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (например, имя сервиса Docker/Compose, такое как
> `http://reranker:8080/v1`; к ним обращаются напрямую, никогда через `HTTP(S)_PROXY` или закреплённый прокси
> соединения). Узлы на любых других
> хостах — в локальной сети или среди узлов Tailscale — подходят только если оператор включает
> функциональный флаг `RERANK_REMOTE_PROVIDER_NODES` **и** базовый URL узла проходит политику исходящих URL провайдера
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Шаг переранжирования движка памяти вызывает этот маршрут через
> обратную связь, поэтому это же правило применяется к `rerankProviderModel` в настройках памяти.
>
> **Форматы локального сервера:** к узлу обращаются по адресу `<base>/v1/rerank`, а при ответе 404 — по адресу `<base>/rerank`
> (Infinity, TEI). Тело запроса к вышестоящему сервису содержит оба варианта написания Cohere/OpenAI (`documents`,
> `return_documents`) и вариант написания TEI (`texts`, `return_text`), а ответ вышестоящего сервиса
> нормализуется в оболочку Cohere: необёрнутый массив TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> от тонких шлюзов и вариант Voyage `{data: [...]}` возвращаются клиенту как
> `{results: [{index, relevance_score, document?}]}`, отсортированные по оценке и ограниченные значением `top_n`.

> **Обнаружение узлов провайдеров:** модели на совместимом с OpenAI узле провайдера отображаются в `GET /v1/models`
> с префиксом узла. Строки без метаданных конечной точки (что обычно характерно для локальных списков `/v1/models`)
> наследуют `apiType` узла, поэтому модели узла `embeddings` имеют значение `type: "embedding"`, а
> модели узла `rerank` — значение `type: "rerank"`, вместо значения по умолчанию для чата;
> явное `supportedEndpoints` в синхронизированной или добавленной вручную строке всё же имеет приоритет.

### Именованные комбинации search/fetch

И `POST /v1/search` и `POST /v1/web/fetch` принимают `model` в качестве сохраненного комбинированного имени. Используйте либо `model`, либо явный `provider`; отправка обоих возвратов `400`. Без какого-либо поля существующий автоматический выбор поставщика остается неизменным.

И Combo Builder, и его каталог «Добавить модель» предоставляют собственные записи веб-операций для подключенных поставщиков, даже если у них нет списка моделей LLM. Серпер показывает** Веб-поиск** ; Тавили показывает** Веб-поиск/извлечение страниц** , а поставщики, предоставляющие только выборку, показывают** Извлечение страницы** . Выберите запись и учетную запись, как обычно. Одна запись Tavily обслуживает обе конечные точки веб-сайта; эти записи операций не добавляются в селекторы клиентов только для чата или зонды модели чата.

Например, создайте** приоритет** комбо с именем `shared-free` со следующими упорядоченными целями:

1. `openai/gpt-4o`
2. `tavily-search/web`
3. `serper-search/web`
4. `jina-reader/fetch`

Затем используйте одно и то же имя на каждой поверхности:

```json
{ "model": "shared-free", "query": "Open source speech recognition", "max_results": 5 }
```

```json
{ "model": "shared-free", "url": "https://example.com", "format": "markdown" }
```

Поиск считает Тавили, затем Серпера; «Принеси», — думает Тавили, затем Джина Ридер; Chat пропускает выделенных поставщиков search/fetch и учитывает OpenAI. Совместимость обеспечивается реестрами исполнителей search/fetch, а не словами в названии модели. Фильтрация предшествует выбору и отправке учетных данных и никогда не редактирует сохраненную комбинацию.

Маршруты без чата поддерживают `priority`, `fill-first`, `round-robin`, `weighted`, `random`, `strict-random`, `least-used` и `p2c`. Стратегии синтеза только для чата, такие как `fusion`, `pipeline` и `context-relay` отклоняются на маршрутах, не связанных с чатом, а не применяются молча к поиску или генерируемому медиа. Существующий комбинированный механизм обрабатывает упорядоченный резервный вариант, включая сбои восходящей квоты, и сохраняет IDs шагов, закрепления учетных записей, списки разрешенных учетных записей для каждого шага, вложенные ссылки, области connection/quota вызывающего абонента и политику комбинированного доступа. Результаты сохраняют свою собственную схему search/fetch, включая фактического поставщика; `X-OmniRoute-Combo-Trace` идентифицирует решение о маршрутизации. Неизвестные комбинации возвращают `404`; неактивные комбинации и комбинации без совместимых целей возвращают `400`.

Каждая попытка комбо использует одного явного поставщика. Он не может вызывать собственный автоматический пул поставщиков за спиной комбо. Запросы явного поставщика сохраняют свое существующее поведение с одним поставщиком. Запросы прямого чата, нацеленные на выделенных поставщиков search/fetch возвращают действенный JSON `400` вместо того, чтобы передаваться исполнителю в стиле OpenAI.

### Комбинированные маршруты с учетом возможностей

Сохраненные комбинации могут содержать объект `routes`, ключи которого являются возможностями API. Каждый маршрут имеет свой целевой список, стратегию и конфигурацию времени выполнения. `models`, `strategy` и `config` верхнего уровня остаются устаревшим планом Chat; старые комбинации без `routes` продолжают работать без изменений.

Поддерживаемые ключи маршрута: `chat`, `search`, `web-fetch`, `embeddings`, `rerank`, `images`, `image-edits`, `videos`, `music`, `ocr`, `audio-speech`, `audio-transcriptions`, `audio-translations` и `audio-generation`. Проекция конечной точки происходит до выбора, оценки или отправки учетных данных. Вложенные ссылки на комбо выбирают маршрут дочернего комбо для той же возможности.

`POST /v1/music/generations` и `POST /v1/ocr` принимают комбинированное имя в `model`. Собственный `POST /v1/music`, совместимый с ElevenLabs, также принимает комбинированное имя в `model_id`, но каждая используемая цель на этой собственной конечной точке должна быть музыкальной моделью ElevenLabs чтобы ее контракт двоичного ответа сохранялся. `POST /v1/sound-generation` принимает комбинацию `audio-generation` в `model_id` с тем же собственным двоичным ограничением. Используйте `/v1/music/generations` для гетерогенных поставщиков музыки.

**Автоматический выбор:** без `provider` первым запускается самый дешевый провайдер с настроенным соединением, а следующий подешевле — это аварийное переключение. Бесплатные поставщики последней инстанции (`duckduckgo-free`) используются только в том случае, если больше ничего не настроено. Самостоятельно размещенный SearXNG считается настроенным, как только в его соединении сохраняется реальный `baseUrl` (а не `http://localhost:8888/search` по умолчанию в каталоге): тогда он считается поставщиком с $0 перед поставщиками с ключом, при этом самый дешевый поставщик с ключом выполняет функцию аварийного переключения, в том числе когда SearXNG отвечает на 400, 401, 403 или 404. `baseUrl`, который не является действительным `http(s)` URL или указывает на адрес облачных метаданных, не учитывается. Соединение SearXNG, в котором хранится токен, ранжируется только по сравнению с `https://` или петлевым `http://`. В удаленном простом `http://` он никогда не обеспечивает аварийное переключение и остается последним средством, используемым только тогда, когда другой поставщик не настроен или когда запрашивается по имени, поэтому в этих двух случаях он отправляет токен в открытом виде.

### Экса и Тавили `provider_options`

Exa и Tavily считывают поля, специфичные для провайдера, из пакета пространства имен: `provider_options.exa` (или `provider_options["exa-search"]`) и `provider_options.tavily` (или `provider_options["tavily-search"]`). Пересылаются только указанные ниже ключи. Каждый из них проверяется на соответствие своей схеме Zod в `open-sse/handlers/search/providerOptionsPassthrough.ts`, и ключ неправильного типа удаляется. Любой другой ключ игнорируется, включая auth, base URL, `stream` и `outputSchema`. Плоские ключи, используемые другими провайдерами (`cx`, `depth`,...), работают как и прежде.

| Поставщик | Поля верхнего уровня                                                                                                                                                                                                                                                                                                                                                      | Вложенный                                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Экса      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоские примитивы), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` объединен с `{ text: true, highlights: true }` по умолчанию |
| Тавили    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                         |

Общие поля всегда выигрывают: `query`, `max_results`, `filters` (домены), `country` и тема, производная от `search_type`. На Exa `search_type: "news"` сохраняет `category: "news"`. Тавили также принимает `search_type: "finance"` (`topic: "finance"`).

Стоимость поиска Firecrawl записывается за каждый запущенный блок из 10 возвращенных результатов по цене 0,002 доллара США (2 кредита) за блок и как минимум один блок за вызов ( [биллинг Firecrawl](https://docs.firecrawl.dev/billing) ): 11 результатов стоят 0,004 доллара США.

Общий `time_range` теперь достигает обоих поставщиков: Exa получает `startPublishedDate` (временная метка ISO ), а Tavily получает `start_date` (`YYYY-MM-DD`). Явная дата в `provider_options` переопределяет сопоставленную дату.

Результаты Exa сохраняют `id`, `highlights` (каждое выделение, а не только первое, используемое в качестве `snippet`), `highlight_scores`, `summary`, `subpages`, `entities` и `extras` в `provider_raw`. Результаты Тавили сохраняют `images` и `favicon`.

Стоимость поиска соединения записывается в размере 0,005 доллара США для `depth` `fast` и `standard` и 0,05 доллара США для `deep` ( [цена соединения](https://docs.linkup.so/pages/documentation/development/pricing) ), независимо от того, получен ли `depth` из `provider_options` или настроек соединения.

Exa `type: "lite"` (Exa 3.0) принимает меньший набор полей и отклоняет весь запрос, если установлено любое другое поле. В версии lite перед вызовом удаляются `additionalQueries`, `systemPrompt` и все ключи `contents` кроме `text` и `highlights`. Устаревшие `subpages`, `subpageTarget`, `highlights.numSentences` и `highlights.highlightsPerUrl` больше не пересылаются.

Учет затрат осуществляется по плоскому реестру `costPerQuery`, за исключением Exa, который соответствует собственным ценам Exa: 0,007 доллара США за вызов для `auto` (и устаревшего `fast`) или 0,004 доллара США для `lite` (и устаревшего `instant`), охватывающего 10 результатов; 0,001$ за каждый последующий результат; и 0,001 доллара США за возвращаемый результат, если установлен `contents.summary`. Тавили записывается по 1 кредиту (0,008 доллара США) для `search_depth` `basic`, `fast` и `ultra-fast` и 2 кредитам (0,016 доллара США) для `advanced` ( [кредиты Tavily API](https://docs.tavily.com/documentation/api-credits) ). Звонок с помощью `auto_parameters: true`, который Тавили повышает до продвинутого уровня, по-прежнему учитывается за 1 кредит.

## Веб-выборка API

Извлекайте контент из URL с помощью настроенного поставщика веб-загрузок (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract, Keenable Fetch).

Параллельное извлечение (`parallel-search`, тот же ключ API, что и параллельный поиск) возвращает только Markdown — любой другой `format` представляет собой `400` — и ограничивает содержимое 100 000 символов. Когда саму целевую страницу невозможно извлечь, восходящий поток сообщает об этом внутри HTTP 200; OmniRoute отображает это как `422` с фиксированным сообщением.

Keenable Fetch (`keenable-search`) также возвращает только Markdown (любой другой `format` — это `400`) и ограничивает содержимое 100 000 символов. Он работает без ключа: явный запрос `provider: "keenable-search"` без соединения использует конечную точку Keenable без ключа (ограничения скорости для каждого IP). Настроенный ключ только снимает эти ограничения; автоматический выбор использует Keenable только тогда, когда ключ настроен.

| Метод | Путь            | Описание                                                  |
| ----- | --------------- | --------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Fetch/scrape — тело URL —, проверенное `v1WebFetchSchema` |

**Автор:** Носитель ключа API (`extractApiKey` + `isValidApiKey`). Политика применяется через `enforceApiKeyPolicy`.

Именованные комбинации используют описанный выше [контракт маршрутизации `model`](#named-searchfetch-combinations), сохраняя параметры и ответы, специфичные для выборки.

**Резервный вариант с учетом квот (#8297):** если не задано ни `provider` ни `model`, пул (`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search` → `keenable-search`) обрабатывается в фиксированном порядке приоритета (сначала заполнение). — поставщик с ограниченной скоростью, но настроенный пропускается вместо короткого замыкания запроса, и происходит сбой восходящего потока retryable/quota (HTTP 429 всегда; 402/403 для Уровни бесплатного использования Firecrawl/Tavily/TinyFish в стиле квоты — не для Jina Reader и никогда для простого 400 ошибочного запроса) передается следующему непроверенному поставщику с учетными данными во время запроса. Когда все поставщики в пуле исчерпаны, конечная точка возвращает один `429` (с заголовком `Retry-After` ) вместо предыдущего общего `400`. Когда запрашивается явный `provider`, происходит** нет** тихий резервный вариант — явный провайдер с ограничением скорости или сбой, выдает собственную ошибку (`429`, если скорость ограничена, в противном случае — статус восходящего потока).

## Потоковая передача через WebSocket

```bash
GET /v1/ws?handshake=1
```

Проверяет рукопожатие обновления WebSocket и возвращает примеры сообщений протокола
передачи (`request`, `cancel`). Фактические кадры WS обрабатываются встроенным WS-сервером
вне таблицы маршрутов Next.js.

**Аутентификация:** Bearer API-ключ во время рукопожатия.

### Responses API через WebSocket (только codex)

```bash
# Тот же host:port, что и у HTTP API (по умолчанию 20128); обновление соединения:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (или: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Первый кадр ДОЛЖЕН быть response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Прокси Responses-API-over-WebSocket подключён **исключительно к `codex`** (бэкенду
ChatGPT). Он прослушивает тот же порт, что и API/dashboard, по путям `/v1/responses`,
`/responses` и `/api/v1/responses`. При получении первого кадра `response.create` он
проходит аутентификацию и подготавливается через внутренний мост
`codex-responses-ws`, выбирает OAuth-подключение codex и туннелирует запрос к
`wss://chatgpt.com/backend-api/codex/responses` через транспорт `wreq-js`.
**Модели, отличные от codex, отклоняются** (`codex_ws_provider_required`).
Для маршрутизации с распределением квоты используйте
`model: "qtSd/<group>/codex/<model>"`. Реализовано в
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` +
`src/app/api/internal/codex-responses-ws/route.ts`.

**Аутентификация:** Bearer API-ключ во время рукопожатия. Встроенный HTTP-сервер
(`server-ws.mjs`) должен быть активной точкой входа (по умолчанию это так, когда существует
`app/server-ws.mjs`).

#### Идентификатор модели: используйте базовый идентификатор ChatGPT (без префикса `codex/`)

OpenAI **Codex CLI** проверяет имя модели на стороне клиента, когда
`supports_websockets = true`, и **отклоняет идентификаторы с префиксом провайдера**,
например `codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Передавайте **базовый** идентификатор (например, `gpt-5.5`).
Мост OmniRoute работает только с codex, поэтому перед туннелированием upstream он повторно
разрешает базовый идентификатор как модель codex
(`resolveCodexWsModelInfo`) — даже несмотря на то, что базовый `gpt-5.5` в противном
случае направлялся бы к другому провайдеру через HTTP.

#### Настройка OpenAI Codex CLI

Направьте Codex CLI в OmniRoute, добавив в `~/.codex/config.toml` пользовательского
провайдера с поддержкой WebSocket (используйте отдельный `CODEX_HOME`, чтобы не изменять
существующую конфигурацию):

```toml
model = "gpt-5.5"                 # базовый идентификатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без завершающей косой черты; URL WS выводится из него (в production используйте https/wss)
wire_api = "responses"                    # единственное поддерживаемое значение с февраля 2026 года
supports_websockets = true                # включает транспорт Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # содержит API-ключ OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API-ключ OmniRoute (любой ключ, если REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI преобразует `base_url + /responses` в WebSocket, а OmniRoute туннелирует его
к выбранному OAuth-подключению codex. Работа проверена от начала до конца на локальном
сервере: ChatGPT возвращает `codex.rate_limits` + `response.created` и передаёт
результат потоково.

## Отчеты о квотах и проблемах

| Метод | Путь                | Описание                                                                                             |
| ----- | ------------------- | ---------------------------------------------------------------------------------------------------- |
| GET   | `/v1/quotas/check`  | Предварительная проверка квоты для `provider` + `accountId` перед выдачей зарегистрированного ключа. |
| POST  | `/v1/issues/report` | Сообщите об ошибке выдачи quota/key в GitHub (требуется токен `GITHUB_ISSUES_REPO` + )               |

**Автор:** `/v1/quotas/check` принимает ключ API на предъявителя (`isAuthenticated`). `/v1/issues/report` предназначен только для управления (`requireManagementAuth`), как и `/api/v1/registered-keys`: сеанс информационной панели, локальный токен CLI или ключ API с областью действия `manage`/`admin` ; Ключи API только для вывода получают `403`.

### Восстановление сеанса квоты (согласие)

Непотоковый `POST /v1/chat/completions` или `POST /v1/responses`, который завершается сбоем из-за ошибки квоты терминала (`402`/`429`/`503`, тело которого сообщает, что квота или кредиты исчерпаны), можно припарковать и воспроизвести позже вместо возврата ошибки. Вызывающий абонент соглашается на запрос с тремя заголовками:

| Заголовок                    | Ценить                                                           |
| ---------------------------- | ---------------------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                                           |
| `x-omniroute-session`        | идентификатор сеанса, `[A-Za-z0-9._:-]{1,128}`                   |
| `x-omniroute-recovery-turn`  | сделать идентификатор уникальным в рамках сеанса (то же правило) |

Допускаются только повороты `stream: false` без инструментов, истории инструментов или `previous_response_id` и без PIN-кода `x-omniroute-connection`, и должен быть установлен `STORAGE_ENCRYPTION_KEY` (запрос хранится в зашифрованном виде до 24 часов). Тогда ответом будет `202` с `recovery.poll`; опрос `GET /v1/quota-recoveries/{id}` (`202` в ожидании, `200` с восстановленным телом после завершения) или отменить с помощью `DELETE`. Билеты видны только тому ключу API, который их создал. Повтор, результат которого неясен, заканчивается в `needs_confirmation` а не отправляется дважды. Источник: `src/lib/quota/quotaSessionRecovery.ts`.

## Использование самообслуживания (`/api/usage/om-usage`)

Любой ключ API может читать** свой собственный** использование и квоты — без аутентификации управления. Это конечная точка, которую клиент (CLI, панель OmniCopilot ) использует, чтобы показать держателю ключа свои расходы.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Ключ должен иметь**`allowUsageCommand`** включено (по умолчанию выключено. — менеджер API-ключей панели управления переключает его для каждого ключа). Без этого конечная точка отвечает `403`.

`?format=json` возвращает распознаваемую форму, поэтому вызывающая сторона никогда не считывает поле данных из отказа. Об успехе:

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При отказе (`401` плохой ключ / `403` не разрешен) тот же маршрут возвращает `{ "allowed": false, "error": { "message": "…" } }` — присутствующий, но пустой `personal`/`provider` (ключ разрешен, еще ничего не изучено) — это состояние, отличное от отказа, и только форма JSON отличает их.

**Автор:** собственный ключ API носителя вызывающего абонента, подтвержденный с помощью `isValidApiKey` — это _не_ поверхность управления (`/api/keys/…`), которая остается за `requireManagementAuth`.

### Необработанные проценты квот по сравнению с процентами квот, скорректированными по предельному значению

При потреблении `/api/usage/om-usage` вызывающие абоненты должны учитывать разницу между процентами, представленными** текстовый вывод** и структурированные** вывод JSON** :

| Аспект                      | Обычный текстовый формат (`/api/usage/om-usage` / `@@om-usage`)                                     | формат JSON (`?format=json`)                                                                   |
| :-------------------------- | :-------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| **Поле вывода**             | `NN% left` (например, `20% left`)                                                                   | `provider.quotas` / `providers[].quotas`                                                       |
| **Измерение**               | **Используемый надбавка с поправкой на сокращение** : оставшаяся емкость выше порога отсечки        | **Необработанная квота добычи** : нескорректированные показатели поставщика                    |
| **Масштабирование отсечки** | Масштабируется через `effectiveRemainingPercent()` поэтому защищенный резерв читается как `0% left` | Нет (необработанные значения моментального снимка, сообщенные поставщиком)                     |
| **Пороговые данные**        | Включено в отображаемый процент                                                                     | Хранится в `quotaWindowThresholds` для каждого соединения (или настроек сервера по умолчанию). |
| **Основной потребитель**    | Интерактивная CLIs, подсказки терминала, люди-операторы                                             | Программные интеграции, информационные панели, аналитика, трекеры биллинга                     |

#### Формула корректировки отсечки

OmniRoute поддерживает упреждающее сокращение квот для предотвращения исчерпания восходящего канала (настраивается через соединение `quotaWindowThresholds`, настройки поставщика по умолчанию или глобальные настройки устойчивости). Когда порог отсечки (например, `cutoff = 25%`) активен в окне квоты, средство визуализации текста вычисляет оставшееся разрешение как:

- Если `remaining <= cutoff`: возвращает `0%`.
- Если `remaining > cutoff`: возвращает `((remaining - cutoff) / (100 - cutoff)) * 100`.

Вывод форматированного текста округляет это значение до ближайшего целого числа (`Math.round(...)`).

#### Иллюстративный пример

Рассмотрим окно провайдера с** 60% сырое использование** (следовательно** 40 % необработанной оставшейся квоты** ) и настроенный** 25% ограничение оставшейся квоты** порог:

| Представительство                        | Расчет                                             | Оставшийся |      Подразумевается использование      |
| :--------------------------------------- | :------------------------------------------------- | :--------: | :-------------------------------------: |
| **Необработанный JSON (`?format=json`)** | Снимок восходящего потока (`quotas[window]`)       |  **40%**   |                 **60%**                 |
| **Текстовый формат (`NN% left`)**        | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**   | **80%** (при расчете `100 - remaining`) |

- **Почему в тексте указано, что осталось 20 %:** Из 40 % физической квоты, оставшейся на аккаунте, 25 % зарезервировано в соответствии с политикой отсечения. У вызывающего абонента остается только 15% из 75% полезного запаса, прежде чем маршрутизатор прекратит маршрутизацию к этому соединению. Масштабирование обеспечивает исчерпание сигналов соединения (`0% left`) именно тогда, когда маршрутизация прекратится.
- **Почему JSON сохраняет необработанные значения:** Полезная нагрузка JSON возвращает точный снимок поставщика (`UsageSnapshot`), поэтому внешние инструменты имеют доступ к достоверной информации об использовании восходящего потока и `quotaWindowThresholds` на уровне соединения без масштабирования с потерями на стороне сервера.

#### Руководство по миграции потребителей

Если внешняя интеграция (например, плагин редактора или расширение агента) ранее очистила конечную точку текста (`NN% left`) и вычислила процент использования как `100 - NN`, переход на `?format=json` означает:

- Чтение необработанных значений JSON отразит** фактическое потребление в разведке** (60% использовано в примере выше).
- Если интеграция желает сохранить семантику допустимого использования конечной точки текста, она может оценить эффективную оставшуюся формулу на стороне клиента, используя `quotaWindowThresholds` для переопределений на уровне соединения.

## Семантический кэш

```bash
# Получить статистику кэша
GET /api/cache/stats

# Очистить все кэши
DELETE /api/cache/stats
```

Пример ответа:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Влияние на задержку

При попадании в семантический кэш ответ возвращается из кэша **без
обращения к вышестоящему сервису**, поэтому сообщаемая
`X-OmniRoute-Response-Latency` близка к нулю
(независимо от исходной задержки вышестоящего сервиса). Клиентам, чувствительным к задержке
(бенчмаркинг, мониторинг p50/p99), следует проверять
заголовок ответа `X-OmniRoute-Cache-Latency`:

| Значение        | Описание                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `synthetic`     | Ответ возвращён из кэша; задержка не является реальным временем обращения к вышестоящему сервису |
| _(отсутствует)_ | Ответ получен в результате реального обращения к вышестоящему сервису                            |

### Отключение кэша для отдельных ключей

API-ключи могут отказаться от чтения семантического кэша с помощью `cacheDefaultMode`:

| Значение | Поведение                                                                   |
| -------- | --------------------------------------------------------------------------- |
| `legacy` | Обычное поведение кэша (по умолчанию)                                       |
| `bypass` | Полностью пропустить поиск в кэше; всегда обращаться к вышестоящему сервису |

Задаётся при создании ключа (`POST /api/keys`) или при его обновлении (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Отключение кэша для отдельного запроса

Любой запрос может обойти кэш независимо от настроек ключа:

```
X-OmniRoute-No-Cache: true
```

## Совместимость с управлением CLIProxyAPI

OmniRoute отвечает на три конечные точки управления [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI),
к которым обращаются панели мониторинга использования для получения данных об ограничениях подписок Claude и Codex
(например, источник лимитов использования `cliproxy` в T3 Code). Укажите в клиенте базовый URL
OmniRoute и используйте API-ключ с областью `manage` в качестве ключа управления. Маршруты
доступны по адресам `/v0/management/*` и `/api/v0/management/*`.

| Метод | Путь                         | Описание                                                                                                                                             |
| ----- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/v0/management/auth-files`  | OAuth-подключения Claude и Codex в виде `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Токены не передаются                 |
| POST  | `/v0/management/api-call`    | Тело `{ auth_index, method, url, header?, data? }`. Отправляет один разрешённый запрос с токеном учётной записи и возвращает `{ status_code, body }` |
| POST  | `/v0/management/reset-quota` | Тело `{ auth_index }`. Очищает период ожидания подключения, блокировки моделей и периоды ожидания Codex для отдельных областей одной учётной записи  |

- `auth_index` — это идентификатор подключения OmniRoute. `provider` — `claude` или `codex` (только
  OAuth-подключения; провайдер API-ключей `anthropic` не включается в список). Для Codex
  `id_token.chatgpt_account_id` — это сохранённый идентификатор рабочего пространства, а `plan_type` — сохранённый тариф.
- `api-call` не является универсальным прокси. Он принимает только Claude `GET
https://api.anthropic.com/api/oauth/usage` и Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` и
  `POST .../wham/rate-limit-reset-credits/consume`, причём каждый запрос должен выполняться только для учётной записи соответствующего
  провайдера. Все остальные запросы возвращают `403` без обращения к вышестоящему сервису. Заголовок
  `Authorization` вызывающего клиента (включая заполнитель `$TOKEN$`) игнорируется: OmniRoute внедряет
  токен доступа подключения, предварительно обновляя его, если срок действия скоро истекает, и пересылает только
  разрешённые заголовки (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`). Если `Chatgpt-Account-Id` отсутствует, по умолчанию используется сохранённый идентификатор рабочего пространства.
  Время ожидания запросов составляет 15 секунд; запросы выполняются через прокси подключения.
- `reset-quota` не изменяет конечные состояния (banned, expired, credits_exhausted). Неизвестный
  `auth_index` возвращает `404`.

**Аутентификация:** сеанс панели управления или API-ключ с областью `manage`; аутентификация обязательна
даже при отключённом входе в систему (пути входят в `ALWAYS_PROTECTED_API_PATHS`). Ключи только для выполнения запросов получают `403`. Источник:

Для моделей synced/imported `PUT /api/provider-models` принимает `provider`, `modelId` и `maxOutputTokenOverride`: положительное целое число устанавливает ограничение выходного токена вручную, а `null` очищает его, чтобы восстановить значение по умолчанию. `GET /api/provider-models?provider=<provider>` возвращает эти значения в `modelOutputOverrides`, включая модели без строки пользовательской модели. Переопределение использует возможности `max_output_tokens` среды выполнения и сохраняется при повторной синхронизации модели. Страница поставщика, совместимого с OpenAI, предлагает те же элементы управления edit/clear и модели маркировки с явной поддержкой машинного зрения.

На совместимом узле поставщика пути записи (`POST`, `PUT`, `PATCH`, `DELETE` и `/api/provider-models/validate-and-add`) сохраняют идентификатор модели как чистый восходящий идентификатор: идентификатор, вставленный из списка с префиксом, имеет свернутый любой ведущий стек собственного префикса узла, и ответы отражают сохраненный идентификатор. Скошенные идентификаторы канонических провайдеров (например, `nvidia/nemotron-…`) сохраняются дословно. `/v1/models` никогда не выдает составной идентификатор `<prefix>/<prefix>/<model>`.

Узлы пользовательских дополнений в чате адаптируют явный отказ от рассуждений к вышестоящему бэкэнду. Успешный тест соединения автоматически выбирает элементы управления шаблоном чата для каждой конкретной модели ID запись `/models` которой подтверждает распознанное значение `owned_by` : `vllm`, `sglang` или `llamacpp`. Прозрачные оболочки, совместимые с OpenAI, могут сохранять исходную запись модели внутри вложенного объекта `openai` ; обнаружение следует до трех таких конвертов. Модели с отсутствующим, неизвестным или конфликтующим владельцем сохраняют обычное поведение OpenAI. При обнаружении повторно используется существующий запрос каталога, не создаются токены завершения и становится недействительным при изменении конечной точки соединения.

Чтобы закрепить поведение серверной части, которая не предоставляет эти метаданные, используйте существующее частичное обновление поставщика API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Отправьте это тело с помощью `PUT /api/providers/<connection-id>`. В этом случае явное рассуждение `none` передается как `chat_template_kwargs.thinking=false` и `chat_template_kwargs.enable_thinking=false`. Явные значения собственного шаблона остаются авторитетными, если только правило обоснования на стороне сервера не принуждает к этому. Этот параметр применяется только в том случае, если пользовательское соединение, совместимое с OpenAI, отправляет тело завершения чата; Запросы ответов и обычные поставщики сохраняют свою собственную форму запроса. Установите для `reasoningControl` `openai`, чтобы принудительно использовать обычную сквозную передачу OpenAI `reasoning_effort`, или опустите it/set в `null` чтобы использовать автоматическое обнаружение.

Классификатор автоматического режима кода Claude требует отключить собственное мышление по умолчанию, если они не содержат явных элементов управления рассуждением. При обнаружении в запросах формата Claude используется системный маркер классификатора, а не имена моделей или пределы завершения. Явные элементы управления телом, поддерживаемые заголовки effort/thinking, правила маршрутизации и разрешенные усилия по модели сохраняют свой существующий приоритет. Обе стадии классификатора сохраняют свои подсказки, пределы завершения, последовательности остановки и реальные вердикты разрешения восходящего потока; второй этап все еще может воспроизводить запрошенное видимое рассуждение в виде обычного текста.

#### Предел происхождения модели

`GET /api/models?withLimits=1` (также `true`; `0`/`false` или его отсутствие сохраняет полезную нагрузку по умолчанию неизменной) добавляет `contextWindow`, `maxInputTokens`, `maxOutputTokens` и объект `capsSource` в каждую строку модели. `capsSource` называет правило, которое обеспечивает каждое ограничение, поэтому удивительное ограничение (например, 128 тыс. в модели 1M) можно проследить до его происхождения. Разрешенные значения совпадают с теми, которые используются в маршрутизации; флаг только добавляет поля и никогда не меняет значение. Любое другое значение `withLimits` отклоняется с помощью `400`.

| значение `capsSource`                        | Источник                                                                            |
| -------------------------------------------- | ----------------------------------------------------------------------------------- |
| `override:context`                           | Постоянное переопределение контекстного окна (`model_context_overrides`)            |
| `override:max_input` / `override:max_output` | Сохраняющееся переопределение возможностей `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Статическая авторитетная таблица контекстного окна                                  |
| `synced:<provider>/<model>`                  | строка синхронизированных возможностей models.dev                                   |
| `registry:<provider>/<model>`                | Запись в реестре провайдера                                                         |
| `spec:<model>`                               | Статическая спецификация модели                                                     |
| префикс `effort-base:`                       | Строка заимствована из базовой модели варианта с суффиксом усилия.                  |
| `none`                                       | Ни один источник не объявляет предел (значение — `null`)                            |

Реализация: `getResolvedModelCapabilitiesWithLimitSources()` в `src/lib/modelCapabilities.ts` и цепочки приоритета в `src/lib/modelCapabilityLimits.ts`.

### Детализация видеокадра

`GET /api/v1/video-bridge/drilldown` считывает непрозрачный дескриптор, привязанный к клиенту, возвращаемый в `x-omniroute-video-drilldown` после явного согласия запроса Video Bridge. И чтение, и `DELETE` всегда требуют действующего ключа API и независимого разрешения `modalityBridgeVideoDrilldownRemoteEnabled` оператора. Для хранения продукции дополнительно требуется `modalityBridgeVideoDrilldownEnabled` и строгий `drilldown: true` для каждой детали. Если ключ имеет непустой список разрешенных конечных точек, он должен включать `video` как для GET, так и для DELETE, независимо от того, использует ли вызывающая сторона `/v1` или `/api/v1`.

запрос GET : требуется `handle`; необязательные `variant` (`preview`, `standard`, `detail`), `limit` (1–8; устаревший `frames` принимается, но не может комбинироваться с `limit`), `page` с отсчетом от нуля и секунды `start`/`end`. Когда обе границы фокуса предоставлены, `end` должен быть больше, чем `start`. Ключи запроса Duplicate/unknown отклонены. Успешные ответы содержат `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` и необязательный `focusWindow`; no-store JSON ограничен 32 MiB, включая Base64. Выходные данные увеличенного размера возвращают 413; запросите меньше кадров.

`DELETE /api/v1/video-bridge/drilldown?handle=...` возвращает `{ "removed": 0|1 }`. Неизвестный, просроченный или перекрестный ключ GETs — это неразличимые ответы 404; перекрестный ключ DELETE не может удалить запись владельца. Отключенный доступ возвращает 403, аутентификация missing/invalid 401, недействительные запросы 400, отмена 499 и временные ошибки 503. Дескрипторы являются локальными для процесса, срок их действия истекает через десять минут и не сохраняются при перезапуске. Новые дескрипторы используют `v1.` плюс 32-байтовый случайный токен Base64URL ; сохраняются только хеши токенов. Устаревшие 64-шестнадцатеричные токены остаются синтаксически читаемыми для совместимости. См. раздел [«Защитные ограждения Video Bridge»](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) для получения информации о согласии, квотах и деталях получения вариантов.

### Версия и канал выпуска

```bash
GET /api/system/version
```

Маршрут управления только с обратной связью (авторизация администратора). Возвращает текущую версию, последнюю опубликованную версию и статус автоматического обновления. `releaseChannel` и `channels` – аддитивные поля (рельс 3.8.54); `channel` сохраняет свое значение. — режим развертывания, который использует программа обновления информационной панели (`npm`, `source` или `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm канал текущей сборки: `nightly` для версий `-nightly.*`, `next` для других предварительных выпусков (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` для стабильной версии более старой, чем `channels.latest`, в противном случае `latest`. Те же правила, что и у `scripts/release/dist-tag.mjs`, который выбирает dist-тег npm во время публикации.
- `channels` — опубликовал заголовок каждого dist-тега из `npm view omniroute dist-tags` (резервный HTTP реестра), кэшированный с тем же 10-минутным TTL что и `latest`. `latest` присутствует всегда (возврат к полю `latest`, затем `"unavailable"`); `next`, `nightly` и `lts` появляются только тогда, когда существует этот dist-тег. Запрос `Cache-Control: no-cache` обновляет оба поиска.

Модель канала (`latest` = v3 до GA 4.0, `next` = rc, `nightly` = `develop`, патчи `lts` = v3 после версии 4.0 GA) описана в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрибация аудио

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибируйте аудиофайлы с помощью любого настроенного провайдера STT. Первый сегмент пути
выбирает нативного провайдера (`openai/…`, `deepgram/…`). Шлюзы, которые
повторно экспортируют модель другого поставщика, используют квалифицированный идентификатор
(`openrouter/deepgram/nova-3`).

**Запрос:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Ответ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Примеры идентификаторов моделей:** `openai/whisper-1` (требуется ключ OpenAI),
`openrouter/deepgram/nova-3` (требуется ключ OpenRouter),
`deepgram/nova-3` (требуется нативный ключ Deepgram). Запрос с простым
`deepgram/nova-3` **не** использует OpenRouter.

**Поддерживаемые форматы:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** транскрибация в файловом режиме через
WebSocket Gemini Live (требуется API-ключ Gemini). Загружаемый файл преобразуется в монофонический PCM с частотой 16 кГц с помощью `ffmpeg`
(`ffmpeg` должен находиться в `PATH`, если только файл уже не является WAV-файлом с монофоническим PCM 16 кГц), передаётся
в сеанс, после чего возвращается финализированный текст в виде `{ "text": "..." }`. Необязательные поля формы `language` и `prompt`
передаются далее. Ограничения: для загрузок размером более 25 МиБ или декодированного аудио длительностью более 10 минут возвращается
`413`; преобразование, выполняющееся дольше 60 с, принудительно завершается, и возвращается `504`. API-ключ передаётся только
в заголовке `x-goog-api-key`, но никогда не включается в URL WebSocket.

Используйте эти псевдонимы, если интеграция не может добавить заголовок `Authorization` и требует встраивания API-ключа в базовый URL.

```bash
# Псевдоним каталога в стиле OpenAI

GET /api/v1/vscode/{token}/models

# Псевдонимы чата в стиле OpenAI

POST /api/v1/vscode/{token}/responses

# Псевдонимы в стиле Ollama

GET /api/v1/vscode/{token}/api/tags
```

Пример:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Примечания:

- Токенизированные псевдонимы используют те же обработчики, что и `/v1/*` и `/api/tags`; структуры ответов остаются идентичными.
- По возможности используйте `Authorization: Bearer ...`, если клиент поддерживает пользовательские заголовки.
- Токены в URL могут отображаться в журналах обратного прокси, истории браузера и телеметрии за пределами OmniRoute. Рассматривайте их как вариант совместимости, а не как основной режим аутентификации.

> **Примечания к схеме** (`setBudgetSchema`): `apiKeyId` является обязательным; как минимум одно из полей `dailyLimitUsd`, `weeklyLimitUsd` или `monthlyLimitUsd` должно быть больше нуля. Необязательные поля: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Устаревший формат `{keyId, limit, period}` возвращает `400 Bad Request`.

## Лимиты токенов

Лимиты **токенов** для каждого API-ключа (отдельно от указанного выше бюджета в USD). Применяются непосредственно в процессе обработки запроса: когда использование в текущем окне для ключа достигает установленного лимита, запросы отклоняются с ошибкой `429 Too Many Requests`. Лимиты могут быть ограничены конкретной `model`, `provider` или применяться `global` ко всему ключу; если запросу соответствуют несколько лимитов, применяется наиболее строгий.

```bash
# Получить лимиты токенов ключа (включая использование в текущем окне)
GET /api/usage/token-limits?apiKeyId=key-123

# Создать или обновить лимит токенов
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Удалить лимит токенов по идентификатору
DELETE /api/usage/token-limits?id=tl-abc
```

> **Примечания к схеме** (`setTokenLimitSchema`): обязательны `apiKeyId` и `scopeType` (`model` | `provider` | `global`). `scopeValue` обязателен, если `scopeType` не равен `global` (например, идентификатор модели для области `model` или идентификатор провайдера для области `provider`). `tokenLimit` должен быть положительным целым числом (преобразуется из строки). Необязательные поля: `id` (не указывать при создании, передать при обновлении), `resetInterval` (`daily` | `weekly` | `monthly`, по умолчанию `monthly`), `resetTime` (`HH:MM`), `enabled` (по умолчанию `true`). Ответы `GET` дополняют каждый лимит полями `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` и `nextResetAt`. Это конечная точка класса управления (аутентификация централизованно обеспечивается конвейером авторизации).

## Обработка запросов

1. Клиент отправляет запрос в `/v1/*`
2. Обработчик маршрута вызывает `handleChat`, `handleEmbedding`, `handleAudioTranscription` или `handleImageGeneration`
3. Определяется модель (непосредственно у провайдера/модели или через псевдоним/комбинацию)
4. Учетные данные выбираются из локальной БД с фильтрацией доступности учетной записи
5. Для чата: `handleChatCore` проверяет семантический кэш/кэш сигнатур и определяет настройки сжатия комбинации
6. Если включено, перед переводом для провайдера выполняется проактивное сжатие (`lite`, Caveman, RTK или их комбинация)
7. Исполнитель провайдера отправляет запрос вышестоящему сервису
8. Ответ переводится обратно в формат клиента (для чата) или возвращается как есть (для эмбеддингов/изображений/аудио)
9. Записываются данные об использовании, аналитика сжатия и журналы запросов
10. При возникновении ошибок применяется резервный вариант в соответствии с правилами комбинации

Полный справочник по архитектуре: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Отказоустойчивость (расширенная)

OmniRoute предоставляет три независимых механизма временных сбоев; приведённые ниже конечные точки управления позволяют операторам просматривать их состояние и переопределять его:

| Область                    | Хранилище состояния                            | Просмотр                                  | Сброс / очистка                                                 |
| -------------------------- | ---------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| Размыкатель провайдера     | `domain_circuit_breakers` + память             | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                    |
| Период ожидания соединения | `rateLimitedUntil` для подключений провайдеров | `/api/rate-limits`, `/api/providers/[id]` | (повторно включает при обращении; очистка через PUT провайдера) |
| Блокировка модели          | Реестр доступности моделей в памяти            | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                        |

`PATCH /api/resilience` принимает переопределения размыкателя провайдера в `providerBreaker.oauth` и `providerBreaker.apikey`. Каждый профиль поддерживает `degradationThreshold`, `failureThreshold` и `resetTimeoutMs`; те же поля доступны в разделе «Панель управления» → «Настройки» → «Отказоустойчивость».

```bash
# Очистить блокировку одной модели
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Удалить все блокировки
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Полный концептуальный справочник и значения по умолчанию для размыкателей см. в [`CLAUDE.md`](../../CLAUDE.md) → «Состояние среды выполнения отказоустойчивости» и [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Очередь ограничения частоты запросов и защитный механизм автоматического включения

- **Поддерживаемый путь записи**: `POST /api/rate-limits` с телом `{"connectionId": "<id>", "enabled": true|false}` — поддерживаемая конечная точка управления для включения или отключения защиты от ограничения частоты запросов для соединения. `PUT /api/providers/[id]` намеренно не изменяет и не переключает `rateLimitProtection` (#11278).
- **Семантика `enabled: false`**: установка `enabled: false` удаляет явную защиту для соединения, но **не исключает** активное соединение с API-ключом из глобального защитного механизма автоматического включения (`autoEnableApiKeyProviders = true`). В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значения `false` и `undefined` эквивалентны; активные соединения с API-ключом без явной защиты остаются защищёнными благодаря защитному механизму автоматического включения.
- **Глобальное отключение**: чтобы использовать соединения с API-ключом без очередей ограничения частоты запросов, отключите защитный механизм глобально через `RATE_LIMIT_AUTO_ENABLE=false` (переменная окружения) или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` («Настройки» → «Отказоустойчивость» / `PATCH /api/resilience`).

## Сервер A2A

OmniRoute предоставляет конечную точку A2A (Agent-to-Agent) JSON-RPC 2.0, а также REST-обёртку для инспекции и использования в панели мониторинга.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # необязательно, если не задана OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Поддерживаемые методы (для всех требуется `settings.a2aEnabled`):

| Метод            | Описание                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Синхронное выполнение навыка; возвращает `{task, artifacts, metadata}` |
| `message/stream` | Потоковое выполнение того же набора навыков через SSE                  |
| `tasks/get`      | Получить задачу по `taskId`                                            |
| `tasks/cancel`   | Отменить задачу по `taskId`                                            |

Встроенные навыки: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Карточка агента

```bash
GET /.well-known/agent.json
```

Возвращает общедоступную карточку агента A2A (имя, описание, возможности, каталог навыков, схему аутентификации), кэшируемую публично на 1 час. Аутентификация не требуется.

### Вспомогательные REST-методы

| Метод | Путь                         | Описание                                                                                                          |
| ----- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Статус A2A, статистика задач и сводка кэшированной карточки агента                                                |
| GET   | `/api/a2a/tasks`             | Список задач — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не реализовано как REST-метод — создавайте через JSON-RPC `message/send`)                                        |
| GET   | `/api/a2a/tasks/[id]`        | Получить одну задачу                                                                                              |
| POST  | `/api/a2a/tasks/[id]/cancel` | Отменить задачу                                                                                                   |

**Аутентификация:** вспомогательные REST-методы работают без управленческой аутентификации (доступны для чтения из панели мониторинга); маршрут JSON-RPC `/a2a` использует Bearer `OMNIROUTE_API_KEY`, если он настроен.

## Аутентификация

См. раздел [Аутентификация управления](../guides/MANAGEMENT-AUTH.md), посвящённый четырём семействам учётных данных (сеанс панели управления, локальный токен CLI, токен доступа `oma_live_…`, API-ключ с областью действия management) и различиям между ними и ключами инференса.

- Маршруты панели управления (`/dashboard/*`) используют cookie `auth_token`
- Для входа используется сохранённый хеш пароля; в качестве резервного варианта — `INITIAL_PASSWORD`
- Переключатель `requireLogin` можно изменять через `/api/settings/require-login`
- Маршруты `/v1/*` могут требовать Bearer API-ключ, если задано `REQUIRE_API_KEY=true`
- «Токен управления» / «API-ключ с областью действия management» в этом справочнике означает один из вариантов, описанных в том руководстве, — это не неопределённый дополнительный тип секрета
