OmniRoute интегрируется с тремя категориями CLI-инструментов, представленными на трёх отдельных страницах панели управления:

| Страница       | Маршрут                 | Концепция                                                                               | Количество |
| -------------- | ----------------------- | --------------------------------------------------------------------------------------- | ---------- |
| **CLI Code's** | `/dashboard/cli-code`   | Инструменты разработки, направляемые в OmniRoute (Клиент → CLI → OmniRoute → Провайдер) | 26         |
| **CLI Agents** | `/dashboard/cli-agents` | Автономные агенты, направляемые в OmniRoute (тот же поток, более широкая область задач) | 10         |
| **ACP Agents** | `/dashboard/acp-agents` | CLI, которые OmniRoute запускает как бэкенд через stdio/ACP (обратный поток)            | см. реестр |

Устаревшие маршруты перенаправляются с кодом 308: `/dashboard/cli-tools` → `/dashboard/cli-code`, `/dashboard/agents` → `/dashboard/acp-agents`.

## Как это работает

```
CLI Code's / CLI Agents (поток потребления):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (все направляются в OmniRoute)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute направляет запрос подходящему провайдеру)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (обратный поток запуска):
    Запрос клиента → OmniRoute → запускает CLI через stdio/ACP → ответ
```

**Преимущества:**

- Один ключ API для управления всеми инструментами
- Отслеживание затрат по всем CLI в панели управления
- Переключение моделей без повторной настройки каждого инструмента
- Работает локально и на удалённых серверах (VPS, Docker, Akamai, Cloudflare Tunnel)

## Автоматическая настройка с помощью `setup-*`

Вам не нужно вручную создавать конфигурацию каждого инструмента. OmniRoute предоставляет команду `setup-*` для каждого поддерживаемого CLI. Она считывает **актуальный** каталог моделей из запущенного экземпляра OmniRoute (локального или удалённого) и записывает собственную конфигурацию инструмента на вашем компьютере:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
```

Каждая команда принимает `--remote <url> --api-key <key>` (настройка локального инструмента для работы с удалённым OmniRoute), `--dry-run` (предварительный просмотр без записи) и `--port`. Для инструментов без автоматического обнаружения моделей (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive) используется `--model <id>` (а для неинтерактивного запуска — также `--yes`). `setup-5dive` — единственный сценарий, который не записывает данные в `$HOME`: он настраивает парк агентов 5dive, записывая на узле парка принадлежащий пользователю root профиль аутентификации, поэтому повторно запускается через `sudo` и не имеет собственного удалённого режима. Чтобы запустить CLI с подставленными нужными переменными окружения, вообще не записывая конфигурацию, используйте универсальный запускатель `omniroute run <target>` (claude, codex, aider, goose, opencode, qwen, gemini — цели и псевдонимы определяются в `bin/cli/cli-manifest.mjs`); устаревшие запускатели для отдельных инструментов `omniroute launch` (Claude Code) и `omniroute launch-codex` (Codex) по-прежнему доступны. Gemini CLI поддерживает только запуск: он является целью `omniroute run`, но для него нет сценария `setup-*`/`configure`.

> **Полная справочная информация:** основная таблица — что записывает каждая команда, все флаги, локальный и удалённый режимы, а также инструменты, которым требуется суффикс `/v1`, — находится в разделе
> **[Интеграции CLI](../guides/CLI-INTEGRATIONS.md)**.

### Запуск этих команд внутри контейнера

Команда `setup-*`, выполненная внутри контейнера OmniRoute, записывает данные в домашний каталог самого контейнера, который не используется ни одним CLI на хосте и исчезает вместе с контейнером. OmniRoute обнаруживает это и завершает работу с кодом `2`, выводя инструкции вместо записи данных. Поддерживаются два варианта дальнейших действий: установить CLI на хосте и выполнить `omniroute connect` для подключения к контейнеру либо подключить каталоги конфигурации через bind mount и задать `CLI_CONFIG_HOME` (профиль compose `host`). Каждая команда `setup-*`, а также `omniroute configure` и `omniroute config set`, принимает `--allow-container-write`, если вы действительно намерены настроить собственные CLI контейнера; переменная `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` выполняет ту же задачу для сервера. См.
[Руководство по Docker → Настройка инструментов CLI на хосте](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker).

**Эндпоинт применения** панели управления (`POST /api/cli-tools/apply`) обеспечивает ту же защиту: в контейнере попытка записи в целевой каталог, не подключённый с хоста через bind mount, получает ответ **`422`** с `containerEphemeralTarget: true`, безопасным текстом ошибки и — для инструментов, имеющих сценарий настройки на хосте (claude, codex, opencode, cline, kilo, continue), — командой `hostSetupCommand` (например, `omniroute setup-opencode`), которую следует выполнить на хосте; при этом ничего не записывается. `dryRun: true` продолжает работать в режиме контейнера и возвращает отредактированный предварительный просмотр и целевой путь, не обращаясь к диску. Содержимое предварительного просмотра не является конфигурацией с учётными данными, которую можно скопировать или импортировать. Выполните применение на хосте с исходными данными инструмента, базового URL, ключа API и модели либо используйте указанную команду настройки на стороне хоста. О заголовке предварительного просмотра и контракте запроса см. в разделе [Безопасность конфигурации CLI](../security/CLI-CONFIGURATION.md). Такое поведение является намеренным и защищено от регрессий тестом `tests/unit/api/cli-tools/apply-container-guard.test.ts` — никогда не «исправляйте» ошибку 422 удалением этой защиты.

## Источник истины

Унифицированный каталог находится в `src/shared/constants/cliTools.ts` и представлен как `CLI_TOOLS: Record<string, CliCatalogEntry>`.

Каждая запись содержит следующие поля (определённые в `src/shared/schemas/cliCatalog.ts`):

| Поле                                            | Тип                                                          | Описание                                                                         |
| ----------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| `category`                                      | `"code" \| "agent"`                                          | Страница, на которой отображается инструмент                                     |
| `vendor`                                        | `string`                                                     | Происхождение инструмента ("Anthropic", "OSS (P. Gauthier)")                     |
| `acpSpawnable`                                  | `boolean`                                                    | Также может использоваться как ACP Agent (отображается значок)                   |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | Уровень поддержки пользовательской конечной точки. `"none"` = очередь задач MITM |
| `configType`                                    | `"env" \| "custom" \| "guide" \| "custom-builder" \| "mitm"` | Механизм конфигурации                                                            |
| `id`, `name`, `color`, `description`, `docsUrl` | стандартные                                                  | Основные поля отображения                                                        |

Записи с `baseUrlSupport: "none"` **не отображаются** на страницах панели управления — они зарегистрированы в очереди задач MITM для плана 11 (см. `_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md`).

### Уровни возможностей (каталогизировано × обнаруживаемо × настраиваемо × запускаемо)

Не каждый каталогизированный инструмент можно обнаружить, настроить или запустить. Для каждого уровня существует один
декларирующий источник, а тест на расхождения обеспечивает их согласованность:

| Уровень              | Значение                                                                                            | Объявлен в                                                                 |
| -------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Каталогизировано** | Отображается в каталоге панели управления (имя, поставщик, документация, тип конфигурации)          | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                           |
| **Обнаруживаемо**    | Обнаружение бинарного файла/конфигурации, проверки работоспособности, пути конфигурации             | `src/shared/services/cliRuntime.ts` (каталог среды выполнения `CLI_TOOLS`) |
| **Настраиваемо**     | Поддерживается командой `omniroute configure <cli>` (существует сценарий настройки)                 | `bin/cli/cli-manifest.mjs` (`configure: true`)                             |
| **Запускаемо**       | Поддерживается командой `omniroute run <target>` (определено внедрение переменных среды/аргументов) | `bin/cli/cli-manifest.mjs` (`run: true`)                                   |

`bin/cli/cli-manifest.mjs` — это канонический исполняемый манифест для интерфейсов команд CLI:
`run`, `configure` и генераторы автодополнения оболочки получают из него
списки целей, разрешение псевдонимов (например, `kilocode`/`kilo-code`/`kilo_cli` → `kilo`)
и настройку флага `--model`. Проверка на расхождения
`tests/unit/cli/cli-manifest-drift.test.ts` гарантирует, что манифест, каталог среды выполнения,
каталог пользовательского интерфейса и все потребляющие интерфейсы остаются синхронизированными — если цель добавлена
в один интерфейс, но не в остальные, набор тестов завершается с ошибкой, не позволяя расхождениям остаться незамеченными.

## 5. API пакетного обнаружения

Обнаружение всех инструментов выполняется через единую конечную точку:

**`GET /api/cli-tools/all-statuses`**

- Аутентификация: `requireCliToolsAuth(request)` (та же, что и для других маршрутов `/api/cli-tools/`)
- Возвращает: `Record<toolId, ToolBatchStatus>` (тип: `src/shared/types/cliBatchStatus.ts`)
- Стратегия: `Promise.all` для всех инструментов, тайм-аут 5 с на каждый инструмент
- Кэш: LRU в памяти, индексируемый по `mtime` файла конфигурации. Кэш аннулируется при изменении mtime. Сбрасывается при перезапуске сервера.

Структура ответа для каждого инструмента:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // очищено, без трассировок стека
}
```

## 10. Внутренний CLI OmniRoute

Бинарный файл `omniroute` предоставляет команды для управления жизненным циклом сервера, настройки, диагностики и управления провайдерами. Точка входа: `bin/omniroute.mjs`.

```bash
omniroute                              # Запустить сервер (порт по умолчанию: 20128)
omniroute setup                        # Интерактивный мастер настройки
omniroute doctor                       # Проверить конфигурацию, БД, порты и среду выполнения
omniroute providers list               # Настроенные подключения к провайдерам
omniroute providers test-all           # Проверить каждое активное подключение
omniroute reset-password               # Сбросить пароль администратора
omniroute logs                         # Выводить журналы запросов в реальном времени
omniroute health                       # Подробное состояние (предохранители, кеш, память)
omniroute --version                    # Вывести версию
omniroute --help                       # Показать все команды
```

### Настройка и инициализация

```bash
omniroute setup                        # Интерактивный мастер настройки
omniroute setup --non-interactive      # Режим CI/автоматизации (читает переменные среды и флаги)
omniroute setup --password '<value>'   # Задать пароль администратора напрямую
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # Добавить и проверить провайдера за один раз
```

Распознаваемые переменные среды для неинтерактивной настройки:

| Переменная          | Назначение                                                            |
| ------------------- | --------------------------------------------------------------------- |
| `OMNIROUTE_API_KEY` | API-ключ провайдера (связан с `--api-key` через `.env()` в Commander) |
| `DATA_DIR`          | Переопределить каталог данных OmniRoute                               |

Все остальные входные данные для неинтерактивной настройки передаются как флаги, а не как переменные среды:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(см. параметры `omniroute setup` выше).

### Диагностика

```bash
omniroute doctor                       # Проверить конфигурацию, БД, порты, среду выполнения, память и доступность
omniroute doctor --json                # Машиночитаемый JSON
omniroute doctor --no-liveness         # Пропустить проверку работоспособности по HTTP
omniroute doctor --host 0.0.0.0        # Переопределить хост для проверки доступности
omniroute doctor --liveness-url <url>  # Полностью переопределить URL конечной точки проверки работоспособности
```

Команда doctor выполняет следующие проверки: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` и `Server liveness`. Она завершается с ненулевым кодом, если какая-либо проверка имеет результат `fail`.

### Управление провайдерами

```bash
omniroute providers available                       # Каталог провайдеров OmniRoute
omniroute providers available --search openai       # Фильтровать каталог по идентификатору/имени/псевдониму/категории
omniroute providers available --category api-key    # Фильтровать по категории (api-key, oauth, free, ...)
omniroute providers available --json                # Машиночитаемый JSON

omniroute providers list                            # Настроенные подключения к провайдерам
omniroute providers list --json

omniroute providers test <id|name>                  # Проверить одно настроенное подключение
omniroute providers test-all                        # Проверить каждое активное подключение
omniroute providers validate                        # Только локальная структурная проверка
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # Существующий поток OAuth
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

Команды `providers add/import/auth/edit/remove` в первую очередь используют API и поэтому работают с
активным локальным или удалённым контекстом. Учётные данные следует вводить с помощью
`--credential-stdin` или `--credential-env`; `--dry-run --json` сообщает только
редактированную информацию о наличии и структуре. `providers available` читает каталог OmniRoute;
`providers list/test/test-all/validate` сохраняют локальное поведение SQLite и
не требуют запущенного сервера.

Для пользовательского узла, совместимого с OpenAI или Anthropic, привяжите учётные данные к
идентификатору узла, возвращённому командой `omniroute nodes add`, используя `omniroute keys add "$NODE_ID" --stdin`.
Для этого требуется запущенный сервер и аутентификация управления в активном контексте.
CLI использует `POST /api/providers`, который проверяет узел и копирует параметры его конечной точки
в подключение. Если узел отсутствует, авторизация завершается ошибкой или сервер недоступен,
возвращается ошибка без создания резервных локальных учётных данных.

`nodes add --base-url` задаёт конечную точку узла; она отличается от адреса сервера
в `OMNIROUTE_BASE_URL`. Для файлов OpenAPI используйте
`omniroute openapi dump --format json --out ./openapi.json`; глобальный параметр `--output`
выбирает формат отображения CLI, а не имя файла назначения.

### Восстановление и сброс

```bash
omniroute reset-password                # Сбросить пароль администратора (также: omniroute-reset-password)
omniroute reset-encrypted-columns       # Показать предупреждение и выполнить пробный сброс зашифрованных учётных данных
omniroute reset-encrypted-columns --force  # Фактически заменить зашифрованные учётные данные в SQLite на null
```

### Экспорт учётных данных (⚠ обращайтесь с осторожностью)

```bash
omniroute auth export                                 # Показать предупреждение и запрос подтверждения — без доступа к БД
omniroute auth export --force                          # Экспортировать РАСШИФРОВАННЫЕ учётные данные ВСЕХ подключений в stdout в формате JSON
omniroute auth export --force --id <id>                 # Экспортировать только соответствующее подключение
omniroute auth export --force --format env               # Вывести строки OMNIROUTE_<PROVIDER>_<FIELD>=<value>
omniroute auth export --force --out creds.json           # Записать в файл (создаётся с правами доступа 0600)
```

`auth export` работает **только локально** (прямое чтение SQLite, без HTTP-маршрута) и намеренно выводит на экран или записывает
**незашифрованные** значения `apiKey`/`accessToken`/`refreshToken`/`idToken` — это функция, а не
ошибка. Без `--force` ничего не читается из базы данных и ничего не расшифровывается. Перед выводом любых незашифрованных данных
в stderr всегда выводится предупреждение. Требуется, чтобы переменная `STORAGE_ENCRYPTION_KEY`
была задана. Поле, которое не удалось расшифровать (устаревший ключ, повреждённый шифротекст), обозначается как
`<field>DecryptFailed: true` вместо прерывания всего экспорта или раскрытия исходной ошибки.

```bash
omniroute a2a status | card            # Состояние сервера A2A / карточка агента

omniroute tunnel list | create | stop  # Управление туннелями (cloudflare/tailscale/ngrok)
omniroute env show | get <k> | set <k> <v>  # Просмотреть / задать переменные окружения (временно)

omniroute test                         # Быстрая проверка подключения к провайдеру
omniroute update                       # Проверить наличие обновлений
omniroute completion                   # Сгенерировать автодополнение для командной оболочки
```

## Управление политикой ключа инференса с помощью OmniRoute CLI

Используйте аутентифицированный контекст управления (см. [Удалённый режим](../guides/REMOTE-MODE.md)),
чтобы просмотреть или обновить существующий ключ инференса по его ID:

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted` — это псевдоним для `--model-access-mode all`. Обновление очищает
список разрешённых моделей. При этом сохраняются области доступа, правила подключений, заблокированные модели, ограничения частоты запросов
и лимиты затрат, поэтому эти средства контроля всё ещё могут отклонить запрос. Явное указание
`--allowed-models ""` также выбирает `all`; объедините его с
`--model-access-mode restricted`, чтобы сохранить ограниченный ключ без разрешённых моделей.
Непустой список, разделённый запятыми, выбирает `restricted`, если явно не указано иное.
Противоречивое сочетание `all` с непустым списком разрешённых моделей отклоняется до отправки запроса.

`--rate-limit 30` задаёт количество запросов в минуту и сохраняет правила для других временных
окон. `--max-cost 5` включает дневной лимит в USD, не изменяя недельный лимит;
`--max-cost 0` удаляет дневной лимит и сохраняет существующий переключатель ограничения использования
и недельный лимит. Неуказанные поля политики остаются без изменений. При изменении частоты запросов
сначала считывается текущая политика; избегайте одновременного редактирования массива ограничений частоты запросов одного и того же ключа.

Команды политики используют аутентифицированные `GET`/`PATCH /api/keys/{id}` и учитывают активный
контекст и глобальный параметр `--api-key`. Вывод JSON содержит только поля политики,
без сохранённого ключа или его маскированного представления. Учётные данные, предназначенные только
для инференса, не могут авторизовать изменения параметров управления. Ошибка 401/403 требует проверки учётных
данных и контекста управления; она не свидетельствует об ошибке локального токена CLI или соли.
Отдельное соглашение о локальной аутентификации см. в разделе [Токен CLI](../security/CLI_TOKEN.md).
