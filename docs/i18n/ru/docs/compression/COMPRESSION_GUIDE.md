> Автоматически экономьте 15–95% токенов подходящего контекста. Краткий обзор см. в [разделе README о сжатии](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## Обзор

OmniRoute реализует модульный конвейер сжатия промптов, который запускается **заблаговременно**, до того как запросы поступают к вышестоящим провайдерам. Это означает, что экономия токенов происходит прозрачно — изменять рабочий процесс не требуется.

```
Запрос клиента
  → Выбор стратегии сжатия
    → Есть переопределение для комбинации? → Использовать настройку комбинации
    → Достигнут порог автозапуска? → Использовать автоматический режим
    → Режим по умолчанию? → Использовать глобальную настройку
    → Отключено? → Пропустить сжатие
  → Выбранный режим сжатия
    → Off: Без сжатия
    → Lite: Безопасная очистка пробелов и форматирования (~15%)
    → Standard: Удаление слов-паразитов в телеграфном стиле (~30%)
    → Aggressive: Устаревание истории + суммаризация (~50%)
    → Ultra: Эвристическое сокращение + прореживание блоков кода (~75%)
    → RTK: Фильтрация вывода терминала и инструментов с учётом команд (диапазон 60–90% для вышестоящего провайдера)
    → Stacked: Упорядоченный многоуровневый конвейер, обычно RTK, затем Caveman (диапазон 78–95% для подходящего содержимого)
  → Сжатый запрос → Провайдер
```

## Режимы сжатия

### Выключен

Сжатие не применяется. Все сообщения проходят без изменений.

### Облегчённый режим (~15% экономии, <1 мс задержки)

Самый безопасный режим — очистка форматирования. Усечение результатов инструментов приводит к потере данных, поэтому путь по умолчанию
(без `allow-lossy`, `engine:lite` или явного выбора именованной комбинации) запускает облегчённый режим с
`compressToolResults: false`: предыдущие результаты инструментов передаются провайдеру без изменений.

| Метод                    | Описание                                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | Объединение последовательных пустых строк и завершающих пробелов                                                        |
| `dedupSystemPrompt`      | Удаление дублирующихся системных сообщений                                                                              |
| `compressToolResults`    | Усечение предыдущих результатов инструментов до лимита облегчённого режима (с потерей данных: только при явном запросе) |
| `removeRedundantContent` | Удаление повторяющихся инструкций                                                                                       |
| `replaceImageUrls`       | Сокращение URI данных изображений в формате base64                                                                      |

**Лучше всего подходит для:** постоянного использования и критичных к безопасности рабочих процессов.

### Стандартный режим (~30% экономии)

Вдохновлён [Caveman](https://github.com/JuliusBrussee/caveman) — удаляет слова-паразиты и многословные формулировки, сохраняя смысл:

- Удаляет слова-паразиты ("please", "I think", "basically", "actually")
- Сокращает многословные фразы ("in order to" → "to", "as a result of" → "because")
- Убирает вежливые оговорки ("Would you mind...", "If you could possibly...")
- Более 30 регулярных выражений, настроенных для запросов по программированию

**Лучше всего подходит для:** повседневных рабочих процессов разработки и команд, учитывающих расходы.

### Агрессивный режим (~50% экономии)

Интеллектуальное управление историей для длительных сеансов:

- **Устаревание сообщений** — старые сообщения постепенно сжимаются
- **Сжатие результатов инструментов** — длинные результаты инструментов усекаются или исключаются (первые/последние строки,
  фильтрация по строкам совпадений, уплотнение ключей JSON)
- **Проверки структурной целостности** — гарантируют согласованность пар `tool_use` + `tool_result`
- **Учет контекстного окна** — соблюдаются ограничения на количество токенов для каждой модели

**Лучше всего подходит для:** длительных сеансов отладки и больших кодовых баз.

### Ультрарежим (~75% экономии)

Максимальное сжатие для сценариев с критичным количеством токенов:

- **Эвристическое прореживание** — прореживание токенов в прозе на основе оценок
- **Сохранение структуры** — блоки кода с ограждениями, встроенный код, URL и идентификаторы
  помечаются и восстанавливаются без изменений, никогда не удаляются
- **Необязательный уровень SLM** — небольшая локальная модель может уточнить результат прореживания при настройке
- Не зависит от агрессивного режима: не выполняет устаревание сообщений, сжатие результатов инструментов
  или резервное суммирование (только сбой уровня SLM может направить резервный проход через агрессивный режим)

**Лучше всего подходит для:** случаев, когда вы постоянно сталкиваетесь с ограничениями контекста.

### Режим RTK (60–90% в диапазоне upstream)

Режим RTK оптимизирован для многословных результатов инструментов, которые появляются в сеансах с агентами разработки:

- Распознаёт классы команд/вывода, такие как `git status`, `git diff`, `git log`, средства запуска тестов,
  сборки TypeScript/Vite/Webpack, ESLint/Biome/Prettier, `npm audit`/установки, журналы Docker, вывод инфраструктуры
  и общий вывод оболочки
- Применяет пакеты фильтров JSON из `open-sse/services/compression/engines/rtk/filters/`
- Импортирует фильтры схемы RTK TOML v1 из проектных или глобальных файлов `filters.toml`, с проверкой встроенных тестов
  и контролем доверия к файлам проекта
- Поставляется с 56 встроенными фильтрами с образцами встроенной проверки
- Удаляет управляющие последовательности ANSI, индикаторы выполнения, повторяющиеся строки и не требующий действий шум
- Сохраняет сбои, ошибки, предупреждения, изменённые файлы, сводки и конец длинного вывода
- Поддерживает фильтры проектов с контролем доверия, глобальные фильтры и необязательное восстановление редактированного необработанного вывода

**Лучше всего подходит для:** сеансов с агентами, использующими оболочку, сборку, тесты, git, grep и транскрипты вывода файлов.

### Комбинированный режим (78–95% в допустимом диапазоне)

Комбинированный режим запускает несколько механизмов сжатия в детерминированном порядке. Конвейер по умолчанию:

```txt
RTK -> Caveman
```

Такой порядок сначала делает вывод терминала/инструментов компактным, а затем применяет семантическое сокращение Caveman
к оставшемуся запросу на естественном языке. Комбинированные конвейеры можно настроить глобально или с помощью комбинаций сжатия,
назначенных комбинациям маршрутизации.

**Лучше всего подходит для:** смешанного контекста с большими журналами инструментов и инструкциями пользователя или сводками ассистента.

## Расчёт экономии при восходящей передаче

OmniRoute приводит данные об экономии за счёт сжатия из двух источников: бенчмарков вышестоящих проектов и
собственной комбинации движков OmniRoute.

| Источник | Число из README вышестоящего проекта, используемое здесь                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman  | на `~75%` меньше выходных токенов, средняя экономия выходных токенов в бенчмарках — `65%`, диапазон — `22-87%`, инструмент сжатия входных данных — `~46%` |
| RTK      | экономия вывода команд — `60-90%`; пример сеанса: `~118,000 -> ~23,900` токенов, или экономия `79.7%` (`~80%`)                                            |

Для пересекающихся полезных нагрузок инструментов/контекста стандартная комбинация OmniRoute последовательно применяет движки:

```txt
RTK -> Caveman
```

Совокупная экономия вычисляется мультипликативно, а не аддитивно:

```txt
совокупная = 1 - (1 - экономия RTK) * (1 - экономия входных данных Caveman)
средняя    = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
диапазон   = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Показатель `78-95%` применим, когда и RTK, и Caveman могут уменьшить одну и ту же полезную нагрузку входных данных/контекста.
Режим выходных ответов Caveman рассматривается отдельно: когда он включён, используйте собственные показатели экономии выходных данных Caveman (`65%`
в среднем, заявленные `~75%`, диапазон `22-87%`). Общая экономия на оплате зависит от соотношения промптов и выходных данных.

### Что на самом деле означает «подходящий для сжатия»

Заявленный диапазон 15-95% реален, но он применим только к **избыточному или многословному** содержимому — повторяющимся
строкам ошибок, журналу сборки, многократно выводящему одно и то же предупреждение, чрезмерно большому выводу `grep`/чтения файла. Это
**не** означает, что каждый запрос обеспечивает такую экономию.

Проверено эмпирически (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): запуск
`stacked` (RTK + Caveman) для блока `tool_result` в формате Anthropic, содержащего 300 одинаковых
строк ошибок, обеспечил **экономию токенов 95.93% / экономию символов 96.26%** — точно в пределах заявленного
диапазона. Однако запуск того же конвейера для обычного, неизбыточного вывода инструмента (чистого списка совпадений `grep`,
результата чтения короткого файла, обычного диалогового текста) ожидаемо даёт **почти нулевую экономию**, поскольку
удалять нечего, а `validateCompression()` (`validation.ts`) не допускает отправку
переписанного содержимого, если при этом удаляются или изменяются блоки кода, URL-адреса, заголовки, версии или идентификаторы констант в ВЕРХНЕМ РЕГИСТРЕ.

Это ожидаемое и безопасное поведение, а не ошибка: сеанс программирования, в котором в основном читаются или просматриваются через `grep` обычные файлы,
даст умеренную общую экономию даже при полностью включённом сжатии, тогда как сеанс, столкнувшийся с циклически повторяющейся ошибкой
или многословным линтером, обеспечит полный диапазон 78-95% экономии для такого трафика. Не используйте низкий
совокупный процент экономии одного сеанса как доказательство неправильной настройки сжатия — сначала проверьте, действительно ли
исходный вывод инструмента был избыточным.

## Визуализация экономии токенов

```
Без сжатия:          47K токенов отправлено в LLM
С Lite:              40K токенов отправлено          (экономия 15% — безопасный режим, включён всегда)
С Standard:          33K токенов отправлено          (экономия 30% — правила Caveman-speak)
С Aggressive:        24K токенов отправлено          (экономия 50% — устаревание + суммаризация)
С Ultra:             12K токенов отправлено          (экономия 75% — эвристическое отсечение)
С RTK:               19K-5K токенов отправлено       (экономия 60-90% на выводе команд/инструментов)
С Stacked:           10K-2.5K токенов отправлено     (диапазон экономии 78-95% для данных, подходящих для RTK+Caveman)
```

## Конфигурация

### Панель управления

Перейдите в `Dashboard → Context & Cache`:

- **Caveman** — выбор режима, языковые пакеты, предварительный просмотр и глобальные значения по умолчанию
- **RTK** — предварительный просмотр фильтра команд, параметры безопасности RTK и каталог фильтров
- **Compression Combos** — именованные конвейеры движков, назначенные комбинациям маршрутизации
- **Auto-Trigger Threshold** — автоматическое включение сжатия, когда количество токенов превышает порог

### Переопределение для комбинации

В разделе `Dashboard → Context & Cache → Compression Combos` назначьте комбинацию сжатия комбинации
маршрутизации:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Это позволяет использовать каскадное сжатие для бесплатных провайдеров и провайдеров для
написания кода, сохраняя облегчённый режим для платных подписок.

Это назначение «Переопределение для комбинации» представляет собой отдельный элемент управления,
отличный от переопределения **режима сжатия комбинации маршрутизации**
(Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — схема этого поля также принимает
`rtk`, `stacked` и `omniglyph`) — это переопределение не выбирает именованный конвейер
комбинации сжатия, а лишь задаёт поле `compressionMode`, используемое функцией
`resolveCompressionPlan`. Его можно задать либо на карточке комбинации (`Dashboard → Combos`), либо,
начиная с #6760, для каждой комбинации маршрутизации в списке «Assign to routing» в разделе
`Dashboard → Context & Cache → Compression Combos`, рядом с описанным выше флажком назначения
конвейера. Оба интерфейса сохраняют данные через одну и ту же конечную точку
`PUT /api/combos/{id}`.

### Переопределение для отдельного запроса

Передайте заголовок запроса `x-omniroute-compression`, чтобы переопределить план сжатия для одного
запроса. Он имеет наивысший приоритет — он имеет преимущество перед переопределением комбинации
маршрутизации, активным профилем, автоматическим включением и значением Default на панели.
Неизвестные значения игнорируются (запрос никогда не отклоняется), а глобальный главный
переключатель по-прежнему управляет всей функциональностью: если сжатие глобально отключено,
заголовок не может его включить. Значения:

| Значение      | Эффект                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `off`         | Для этого запроса сжатие не выполняется.                                                                      |
| `default`     | Профиль Default, определённый панелью (активный профиль игнорируется). Потеряющие данные движки отключены.    |
| `safe`        | То же, что и отсутствие заголовка.                                                                            |
| `allow-lossy` | Сохраняет план операторов этого запроса, включая сводки, фильтры релевантности и переписывание стиля.         |
| `engine:<id>` | Один движок, если он включён, например `engine:rtk`. Это явное включение этого движка для отдельного запроса. |
| `<combo>`     | Именованная комбинация, сначала сопоставляемая по имени (без учёта регистра), затем по идентификатору.        |

Без `allow-lossy`, `engine:<id>` или именованной комбинации движки с потерей данных не
применяются. Если Default, автоматическое включение или переопределение маршрутизации с потерей
данных понижается, OmniRoute сохраняет распознанные этапы без потери данных из настроенного
каскадного конвейера в заданном порядке. Резервный вариант
`session-dedup → lite` используется только в том случае, если не сохраняется ни одного
настроенного этапа без потери данных.

Предварительный просмотр **Effective pipeline** на панели настроек показывает обычный план в
состоянии покоя. Если может сработать автоматическое включение, тот же предварительный просмотр
также показывает его условный эффективный конвейер, благодаря чему разрешение без заголовка на
панели и во время выполнения остаётся согласованным.

Применённый план возвращается в заголовке ответа
`X-OmniRoute-Compression: <mode>; source=<source>`, где `<source>` принимает одно из значений:
`request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Передовые системы сжатия

Помимо семи режимов, описанных выше (исходный код также поддерживает режимы `codex-responses` и `omniglyph`, которые не рассматриваются в данном руководстве), в разделах ниже описаны функции, которые работают внутри или параллельно с этими режимами: сжатие результатов инструментов и прогрессивное старение — это шаги 1 и 2 агрессивного механизма (агрессивный режим и шаг `aggressive` многоуровневого конвейера), составной конвейер — то, как работает стековый режим, сжатие с учетом кэша понижает `aggressive` и `ultra` до `standard` для кэширования провайдеры, когда сжатие включено, а режим вывода Caveman и стили вывода — это дополнительные системные инструкции, отключенные по умолчанию, которые формируют выходные данные модели вместо сжатия запроса.

### Сжатие с учетом кэша

Некоторые провайдеры (например, Anthropic с быстрым кэшированием) поддерживают** быстрое кэширование** , что позволяет им кэшировать части приглашения для снижения затрат и задержки. Когда кэширование включено, агрессивное сжатие фактически может** повредить** производительность, поскольку он изменяет кэшированные токены, делая кеш недействительным.

Модуль `cachingAware.ts` решает эту проблему путем** определение контекста кэширования** и** настройка стратегии сжатия** соответственно.

#### Как это работает

1. **Определить контекст кэширования** — Сканирует тело запроса на наличие маркеров `cache_control`
2. **Определить поставщиков кэширования** — Проверяет, поддерживает ли целевой провайдер кэширование.
3. **Корректировка стратегии** — Понижает версию `aggressive`/`ultra` до `standard` для поставщиков кэширования
4. **Пропустить системное приглашение** — Системные подсказки обычно кэшируются, поэтому не сжимайте их.

Помощник по стратегии также возвращает флаг `deterministicOnly`, но построитель плана использует только стратегию — и ничто в дальнейшем не читает этот флаг сегодня.

#### Пример кода

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Когда использовать

Сжатие с учетом кэша** всегда включен** — настройка не требуется. Он срабатывает всякий раз, когда включено сжатие и целевой поставщик поддерживает оперативное кэширование (Anthropic, OpenAI и т. д.); явные маркеры `cache_control` не требуются — только поставщик кэширования инициирует переход на более раннюю версию, а сами по себе маркеры никогда этого не делают (обнаружение маркеров передает данные телеметрии кэша, а не стратегические решения).

OpenRouter считается поставщиком кэширования только для моделей `anthropic/*` : запросы кода Claude сохраняют точки останова `cache_control` (максимум 4), а защита защищает префикс, в то время как все остальные семейства OpenRouter (`openai/`, `google/`, `qwen/`, …) остаются удаленными и незащищенными.

### Прогрессивное старение

Длинные разговоры накапливают много сообщений, но более старые сообщения становятся менее актуальными. Модуль `progressiveAging.ts`** ухудшает качество сообщений в зависимости от расстояния поворота** (расстояние измеряется от конца разговора). С поставляемыми настройками по умолчанию (`verbatim: 2, light: 2, moderate: 3`):

- **Последние 2 хода (расстояние ≤ 2)** : Сохранено дословно
- **Расстояние 3** : Компрессия Caveman (удаление наполнителя).
- **Расстояние 4 +** : обобщение сообщений Ассистента; сообщения пользователя сокращены до первой строки, ограниченной 120 символами; другие роли нетронуты. Системные подсказки, уже устаревшие сообщения и последнее сообщение пользователя всегда сохраняются дословно независимо от расстояния. Ничего не удаляется сразу, и диапазон `light` недоступен с поставляемыми настройками по умолчанию (`light` равен `verbatim`).

#### Пример кода

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### Когда использовать

Прогрессивное старение – это** всегда включен** для режима `aggressive` — это шаг 2 `compressAggressive()`. Ультра режим не запускается. Это особенно эффективно для:

- Длительные сеансы кодирования
- Многодневные разговоры
- Агентские рабочие процессы с множеством вызовов инструментов

### Режим вывода «Пещерный человек»

Добавлен режим вывода «Пещерный человек»** подсказки системы** которые запрашивают у самой модели краткий вывод — уровень `lite` запрашивает краткие ответы, содержащие полные предложения, `full` просит ее «отвечать кратко, как умный пещерный человек», а `ultra` запрашивает телеграфный вывод; инструкции только просят, они не могут этого гарантировать. Запросы получают их через `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`): `open-sse/handlers/chatCore.ts` сначала разрешает выбор с помощью прокладки обратной совместимости (`resolveOutputStyleSelection()` в `open-sse/services/compression/outputStyles/backCompat.ts`), которая, пока `outputStyles` пуста, сопоставляет включенный `cavemanOutputMode` со стилем вывода `terse-prose` в `cavemanOutputMode.intensity` (см. Обратную совместимость ниже); непустой выбор `outputStyles` используется как есть, и тогда `cavemanOutputMode.enabled` и `intensity` не имеют никакого эффекта, в то время как его переключатель `autoClarity` все еще применяется. `outputMode.ts` содержит тексты инструкций (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), обход контента и помощник по размещению, который использует внедрение; собственный инжектор `applyCavemanOutputMode()` не имеет производственного вызывающего абонента.

#### Как это работает

Этот режим не сжимает входной сигнал. Он добавляет блок инструкций в системную подсказку (см. «Как работает внедрение» ниже), и любой режим сжатия входных данных, выбранный для запроса, по-прежнему запускается впоследствии в теле, которое теперь содержит блок. Перед пунктом об общих границах, которым заканчивается каждый уровень, английский уровень `full` гласит:

> «Отвечайте кратко, как умный пещерный человек. Оставляйте статьи (a/an/the), заполнители (just/really/basically/actually/simply), любезности, хеджирование. Фрагменты OK. Короткие синонимы (большие, не обширные, исправление не реализовано). Сохраняйте всю техническую суть, код, ошибки, URLs, идентификаторы точными».

Это особенно хорошо работает для:

- Генерация кода (более краткий вывод = меньше токенов)
- Быстрые вопросы и ответы (нет необходимости в подробных объяснениях)
- Пакетная обработка (максимальная пропускная способность)

#### Когда использовать

Режим вывода «Пещерный человек»** подписка** . Включив сжатие (`enabled: true`, главный переключатель на странице настроек сжатия), включите его с помощью `cavemanOutputMode.enabled`; `intensity` выбирает `lite`, `full` или `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Комбинация сжатия** Режим вывода** toggle (`outputMode`, level in `outputModeIntensity`) устанавливает тот же переключатель для запросов, к которым применяется комбо, и инструмент `omniroute_set_compression_engine` MCP записывает его через свой логический аргумент `outputMode`. Непустой выбор `outputStyles` имеет приоритет над этим переключателем. На панели управления, включив** Немногословная проза** стиль вывода вставляет тот же блок (см. Стили вывода ниже).

#### Как работает инъекция

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) разрешает выбор в каталоге (неизвестные идентификаторы и стили, не соответствующие локали, удаляются, никогда не возникает ошибка; выбор, который разрешается без стиля, оставляет тело неизменным, пропускается как `no_styles`), объединяет выбранные инструкции в порядке каталога, добавляет предложение границ** один раз** (плюс предложение безопасности `SAFETY_BOUNDARIES` или его перевод, если выбран `less-code` или `ponytail` ) и запускает блок с одного маркера идемпотентности (`[OmniRoute Output Styles]`), поэтому повторное применение не требуется. Если разрешенный язык (см. раздел «Выбор языка» ниже) имеет перевод, вместо английского языка вводится локализованная инструкция.

On a body with a non-empty `messages` array, the idempotency check runs before the content bypass: when the `[OmniRoute Output Styles]` marker is already in the top-level `system` field (a string or a content-block array) or in a system message with string content, the body is left unchanged as `already_applied` and no keyword check runs. Otherwise a content bypass (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) checks the text of the last three messages, whatever their role, and skips the styles for the whole turn when that text matches its security, irreversible-action or clarification keywords, or an order-sensitive sequence: `first`, `then`, `after that`, `before`, `rollback` or `backup` followed within 240 characters by `delete`, `drop`, `migrate`, `deploy` or `release`. The bypass runs while the **Auto-Clarity Bypass** toggle (`cavemanOutputMode.autoClarity`, on by default) is on; turning the toggle off skips the keyword check.

Когда обход позволяет пройти, `placeSystemInstruction()` (тот же файл), который никогда не создает новый `messages[0]`, помещает блок в первый из найденных:

1. Ведущее системное сообщение со строковым содержимым: блок добавляется после его текста.
2. Поле `system` верхнего уровня: блок добавляется после текста строки или добавляется как новый текстовый блок в массив блоков контента.
3. Первое позднее системное сообщение со строковым содержимым: блок добавляется после его текста.
4. Ничего из перечисленного: блок переходит в новое системное сообщение в конце `messages`.

В теле без массива `messages` (или с пустым) обход содержимого не выполняется и поле `system` верхнего уровня не обращается к нему. Блок добавляется после текста строкового поля `instructions`, если только это поле еще не содержит маркер `[OmniRoute Output Styles]`, и в этом случае тело остается неизменным как `already_applied`. Если тело не имеет строкового поля `instructions` но содержит `input` (строку или массив), блок становится `instructions`, заменяя любое нестроковое значение, содержащееся в поле. Тело, не содержащее ни строкового поля `instructions`, ни строки или массива `input` остается неизменным и пропускается как `no_messages`.

#### Как включить

В приборной панели:** Контекст сжатия Настройки сжатия →** (`/dashboard/context/settings`), раздел «Стили вывода»: одна строка на стиль с переключателем on/off и переключателем уровня. Стили внедряются, когда включено само сжатие (главный переключатель страницы, `enabled`).** Автоматический обход четкости** переключатель находится на** Пещерный человек** страница (`/dashboard/context/caveman`), в ее** Режим вывода** карта. Программно конфигурация сжатия сохраняет выбор как:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Обратная совместимость: пока `outputStyles` пуста, устаревшая настройка `cavemanOutputMode.enabled` сопоставляется с `terse-prose` по адресу `cavemanOutputMode.intensity`. Затем блок начинается с маркера `[OmniRoute Output Styles]`, где устаревший инжектор `applyCavemanOutputMode()` записывал `[OmniRoute Caveman Output Mode]`. Под маркером текст соответствует устаревшему внедрению в en, pt-BR, es, de, fr, it, ru, id и vi; в ja и zh перед предложением границ содержится один дополнительный пробел. `terse-prose` преобразуется в pt-BR, es, de, fr, it, ru, zh, ja, id и vi, поэтому запрос, разрешенным языком которого является `hu` получает английский текст, в котором устаревший инжектор использовал венгерский.

Выбор языка в стиле вывода (`resolveOutputStyleLanguage()` в `outputStyles/apply.ts`): при включенном `languageConfig.enabled` `autoDetect` выбирает последнее пользовательское сообщение в массиве `messages` запроса, содержащем текст (строковое содержимое или `text` его частей содержимого), и запускает на нем детектор механизма Caveman (`detectCompressionLanguage()`). Детектор возвращает `zh` для текста с символами хань и без кана; в противном случае он возвращает тот из `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` и `id` который имеет наибольшее количество совпадений подсказок, и `en` когда ни один из них не соответствует тексту —, который он не может классифицировать, получает английский, никогда не `defaultLanguage` и `vi` никогда не обнаруживается, хотя стили поставляют текст `vi`. Тело ответа API сохраняет свою очередь в `input`, который не подвергается выборке, поэтому он получает `defaultLanguage`, а затем английский язык. Если ни одно сообщение пользователя в `messages` не содержит текста или `autoDetect` отключен, применяется `defaultLanguage`, а затем английский язык. Если `languageConfig.enabled` отключен, языком будет английский — если только к запросу не применяется комбинация сжатия (комбинация, назначенная для комбинации маршрутизации запроса, или комбинация сжатия по умолчанию, к которой chatCore возвращается для встроенного многоуровневого конвейера): применение комбинации включает `languageConfig.enabled` для этого запроса и устанавливает `defaultLanguage` из языковых пакетов комбинации (сохраненное значение, если это один из пакетов комбинации, в противном случае первый пакет комбинации, который по умолчанию `en`), в то время как сохраненный `autoDetect` (включен по умолчанию) по-прежнему применяется. Механизм ввода Caveman выбирает язык пакета правил по-разному — для каждой текстовой части и, при отключенном автоматическом обнаружении, включает `enabledPacks`.

Матрица языка × стилей закрепляется с помощью `tests/unit/compression/output-styles-i18n-matrix.test.ts`: для каждого стиля каталога требуется запись в `BASELINE_LANGUAGES` теста; стиль, который не привязан к локали, должен поставлять перевод pt-BR ( `terse-cjk` с контролем локали исключен из этого правила), если он не указан в `KNOWN_ENGLISH_ONLY`, который может содержать только стили без каких-либо переводов. — перечисленный стиль, имеющий какой-либо перевод, не проходит тест; и стиль не проходит тест, если теряет язык, указанный в записи `BASELINE_LANGUAGES`. Чтобы добавить стиль, см. [EXTENDING_COMPRESSION](./EXTENDING_COMPRESSION.md#adding-an-output-style)

### Сжатие результатов инструмента

`compressToolResult()` в `open-sse/services/compression/toolResultCompressor.ts` сжимает текст результатов инструмента с помощью** 5 стратегий** . Он пробует их в этом порядке, и результат определяет первая включенная стратегия, проверка которой соответствует содержимому:

1. **`fileContent`** : содержимое 3 или более строк, в которых хотя бы одна строка, игнорируя начальные отступы, начинается с `import `, `export `, `function `, `class `, `const `, `let `, `var ` или `return ` (ключевое слово плюс пробел) или с `if`, `for` или `while`, за которыми следует `(` или ` (`, сохраняет свои первые 20 и последние 5 строк с отмеченной серединой.
2. **`grepSearch`** : контент, содержащий хотя бы одну строку в форме `<path>:<digits>:`, где текст перед первым двоеточием не имеет пробелов, сохраняет только те строки, не более 30, за которыми следует подсчет любых дальнейших совпадений и список совпадающих файлов; каждая вторая строка отбрасывается. Одной такой строки достаточно для запуска стратегии, поэтому строка журнала, начинающаяся с временной метки, например `12:30:45` также учитывается.
3. **`shellOutput`** : выходные данные, содержащие последовательность ANSI CSI (`ESC[`, затем цифры или точки с запятой, затем букву, как в цветовых кодах) или `$` за которым следуют пробелы в любом месте текста, теряют эти последовательности (другие escape-последовательности, такие как `ESC[?25l` или последовательность заголовков окон OSC, сохраняются) и сохраняют последние 50 строк с свернутыми последовательными повторяющимися строками. Поскольку эта проверка выполняется до `json` и `errorMessage`, JSON или вывод ошибок, содержащий такой `$` никогда не достигает их, пока `shellOutput` включен.
4. **`json`** : полезная нагрузка JSON длиной более 2000 символов, начинающаяся с `{` или `[` (после необязательного пробела), и анализ суммируется: массив из более чем 7 элементов сохраняет свои первые 5 и последние 2 элемента и общее количество, а объект сохраняет свои первые 20 ключей, при этом каждый вложенный объект или значение массива заменяется заполнителем `{…N keys}` (для массива N — его длина) и маркером `_remaining_<N>_keys`, подсчитывающим ключи, пропущенные после первых 20. Скалярные значения копируются целиком, поэтому объект с 20 или менее ключами без вложенных значений подвергается только повторному отступу — Минимизированный объект получает символы и остается неизменным.
5. **`errorMessage`** : вывод, который содержит где угодно и в любом регистре букв `error:`, `error ` (слово, за которым следует пробел, как в `no error found`), `[error]`, `exception:`, `exception `, `[exception]` или `traceback` сохраняет свою первую строку, следующие 10 строк и последние 3 с маркером `… [N frames elided] …` вместо строк между ними. Маркер появляется только тогда, когда за первой строкой следует более 13 строк, поэтому вывод ошибок в 14 строк или меньше не сокращается (при 12 или 13 строках последние 3 повторяющиеся строки уже сохраняются).

После совпадения стратегии, даже если она ничего не сохраняет, последующие стратегии не используются. Когда стратегия сопоставления не сохраняет предполагаемых токенов (длина ÷ 4, округленная вверх), — например, кодовый файл длиной 25 строк или меньше, или массив JSON более 2000 символов с 7 элементами или меньше — агрессивный механизм сохраняет исходный результат инструмента: оба вызывающих объекта (`compressAggressive()` и `compressAnthropicToolResultBlock()`) сохраняют оригинал, когда `saved` равен 0 или меньше, в то время как сам `compressToolResult()` по-прежнему возвращает выходные данные этой стратегии. Шаг результата инструмента — не последнее слово: резервный сумматор движка все равно может сократить сообщение `tool` или `function` длиной более 8192 символов (`maxTokensPerMessage`, 2048, умноженное на 4).

#### Когда использовать

Сжатие результатов инструмента — это шаг 1 агрессивного механизма (`compressAggressive()` в `open-sse/services/compression/aggressive.ts`), поэтому оно выполняется в агрессивном режиме и на шаге `aggressive` составного конвейера. Он сжимает сообщения `tool` и `function` в форме OpenAI, а также текст внутри блоков Anthropic `tool_result`. Каждая стратегия имеет свой собственный переключатель в `aggressive.toolStrategies`, все они включены по умолчанию. На приборной панели переключатели находятся на странице Caveman.** Передовой** просматривать при включенном сжатии и режиме по умолчанию «Агрессивный».

### Многоуровневый трубопровод

Стековый режим работает** несколько двигателей последовательно** — обычно сначала RTK (экономия 60-90% на выходных данных инструмента), затем Caveman на оставшемся тексте (экономия на входных данных ~ 46%). Составленный, то есть** 78–95 % приемлемый диапазон** (см. выше математические расчеты экономии в разведке и добыче): `1 - (1 - 0.60..0.90) × (1 - 0.46)` в среднем составляет ≈ 89%.

#### Как это работает

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### Когда использовать

Используйте составной режим для:

- Рабочие процессы с большим количеством инструментов (агентное кодирование, исследования)
- Экономичная пакетная обработка
- Когда вам нужна максимальная экономия токенов

Составные конвейеры настраиваются с помощью глобальной настройки сжатия `stackedPipeline` или с помощью именованной комбинации сжатия, назначенной комбинации маршрутизации (см. выше «Переопределение каждой комбинации») — а не с помощью автоматической комбинации `modePack` (это поле только повторно взвешивает выбор модели автоматического комбинирования, а `stacked` не является допустимым именем пакета).

## Переопределение комбинаций сжатия

Вы можете переопределить глобальный режим сжатия **для каждой комбинации**, чтобы точно настроить поведение
для различных сценариев использования:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Это полезно для:

- **Комбинаций для программирования**: используйте режим `aggressive` для длительных сессий
- **Комбинаций для быстрых вопросов и ответов**: используйте режим `lite` для быстрых ответов
- **Комбинаций с интенсивным использованием инструментов**: используйте режим `stacked` для максимальной экономии
- **Комбинаций для промышленной эксплуатации**: не включайте переопределение для провайдеров с кэшированием — постоянно активная
  корректировка с учётом кэша автоматически понижает `aggressive`/`ultra` до `standard`
  (режим `cache-aware` нельзя выбрать)
