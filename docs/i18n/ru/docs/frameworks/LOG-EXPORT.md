Непрерывный инкрементальный экспорт журналов вызовов OmniRoute во внешнее аналитическое хранилище.

Вкладка журналов на панели управления хранит историю запросов в SQLite (`call_logs`), объём которой ограничен
ротацией и сроком хранения. Экспорт журналов отправляет тот же набор записей по расписанию, чтобы он мог храниться
дольше локальной базы данных и объединяться с другими данными. Первое поддерживаемое назначение — BigQuery;
конвейер построен на реестре, поэтому новые назначения можно добавлять независимо.

## 1. Как это работает

```
сервер (расшифровка + проверка конфигурации, согласование курсора)
  → запуск через IPC → изолированный процесс ОС exportChild
    → storage.sqlite только для чтения → общие запросы/преобразование журналов вызовов
      → асинхронная загрузка артефактов → prepare()/send() назначения
        → пакет через IPC → сервер сохраняет курсор → подтверждение через IPC
          → следующий пакет; завершение через IPC → сервер фиксирует успех
```

- **Расписание** — одно cron-задание `JobRegistry`, `log_export`, по умолчанию `0 * * * *` (ежечасно,
  UTC). Регистрируется в `src/lib/initCloudSync.ts`; можно переопределить через `OMNIROUTE_LOG_EXPORT_CRON`.
  При каждом срабатывании последовательно обрабатываются все **включённые** назначения.
- **Курсор** — неявный `call_logs.rowid` SQLite, сохраняемый отдельно для каждого назначения в
  `log_export_destinations.cursor_row_id`. `timestamp` намеренно не используется как курсор: вызывающая сторона
  может задать собственное значение, поэтому медленный запрос может быть записан после более быстрого, начавшегося
  позже, и курсор на основе временной метки пропустил бы его.
- **Пакетная обработка** — `batch_size` строк на запрос (по умолчанию 500), `max_rows_per_run` строк на запуск
  (по умолчанию 10000), чтобы большой объём накопленных записей обрабатывался за несколько срабатываний, а не блокировал одно.
- **Доставка** — курсор продвигается только после успешного завершения `send()`. При сбое пакета
  курсор остаётся на прежнем месте, поэтому те же строки повторно отправляются при следующем запуске. Гарантия —
  доставка как минимум один раз с дедупликацией на стороне назначения, а не строго однократная доставка: BigQuery использует
  идентификатор записи журнала вызовов как ключ строки и учитывает его по мере возможности в пределах собственного окна дедупликации.
- **Защита от параллельных запусков** — cron и `POST .../run` могут сработать одновременно. Назначение,
  которое уже обрабатывается, пропускается, а не обрабатывается повторно (`skipped: true` в результате запуска),
  поэтому параллельный запуск не может повторно отправить пакет или переместить курсор назад.
- **Восстановление после очистки** — если `cursor_row_id` оказывается выше `MAX(rowid)` (вся таблица была
  очищена и нумерация rowid началась заново), исполнитель возвращает курсор к 0, чтобы не перестать видеть новые записи навсегда.

### Изолированный исполнитель и ограничения

Каждый запуск экспорта в назначение на Node создаёт отдельный краткоживущий дочерний процесс ОС (`child_process`
с IPC, а не `worker_threads`). Чтение тел, разбор и сериализация JSON полезной нагрузки,
`prepare()` назначения и сетевой ввод-вывод назначения выполняются в нём, а не в цикле событий сервера.
Через IPC передаются только конфигурация и небольшие сообщения о ходе выполнения; экспортируемые записи никогда не возвращаются
на сервер. Cron-задание и маршрут немедленного запуска сохраняют прежний публичный результат и защиту от параллельных запусков.

Дочерний процесс открывает определённый сервером `DATA_DIR/storage.sqlite` только для чтения через `node:sqlite`,
с `busy_timeout=5000` и `query_only=ON`. Он не импортирует синглтон базы данных и не выполняет
миграции, резервное копирование или обновления SQLite. Учёт отсутствующих и повреждённых артефактов (включая
UPDATE для повреждённого артефакта) остаётся исключительно в обработке подробных данных панели управления. Оба пути используют общий чистый
компонент получения подробных данных; экспорт использует асинхронное чтение файловой системы и тот же порядок поиска: артефакт → устаревшие
встроенные данные → устаревшие данные на диске → отсутствие данных. При открытии чтения дочерним процессом запуск фиксирует максимальный rowid вставки;
более поздние вставки ожидают следующего запуска. Это граница
вставки, а не длительная транзакция SQLite: запись в WAL и выполнение контрольных точек не блокируются во время
ожидания сети. Эта граница не замораживает обновления и удаления существующих строк.

После каждого принятого пакета дочерний процесс ожидает подтверждения. Сервер сначала сохраняет
курсор с помощью `advanceLogExportCursor`, затем отправляет `ack`; до этого следующий пакет не начинается.
Ошибка отправки, аварийное завершение или тайм-аут фиксируются как сбой без продвижения курсора для этого пакета. Ранее
подтверждённые пакеты остаются зафиксированными; повторно может быть отправлен не более чем один неподтверждённый пакет.
Успех фиксируется только после `done` и штатного завершения дочернего процесса. При сбоях дочерний процесс завершается
сигналом SIGTERM, а через 500 мс при необходимости отправляется SIGKILL; исполнитель ожидает полного завершения процесса.

| Переменная окружения                          | По умолчанию | Назначение                                                    |
| --------------------------------------------- | ------------ | ------------------------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | Ограничение полного времени выполнения для каждого назначения |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | Ограничение области old space V8 дочернего процесса в МБ      |

При недопустимых, неположительных или нецелочисленных значениях используются значения по умолчанию. Настройка кучи не ограничивает
общий RSS; очень большие пакеты по-прежнему могут исчерпать память дочернего процесса и привести к безопасному завершению запуска с ошибкой.
Значение по умолчанию 1024 МБ оставляет запас для стандартного пакета из 500 строк с артефактами по 512 КиБ при
включённых телах, в том числе для сериализации JSON в BigQuery с разбиением на части по размеру в байтах. Оно не делает
безопасным пакет из 10000 строк с телами. При исчерпании кучи V8 фиксируется ошибка с рекомендацией: уменьшить размер
пакета или увеличить `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; курсор остаётся на последнем
подтверждённом пакете. Современное ограничение размера артефактов не распространяется на исторические встроенные тела и тела на диске.
Операторы должны отдельно планировать RSS, особенно в контейнерах с ограниченной памятью.

Дочерний процесс наследует только вычисленное значение `DATA_DIR`, `NODE_ENV`, явно заданную `TZ` (для определения
локального времени в устаревших именах файлов), `ELECTRON_RUN_AS_NODE`, если она задана, и следующие параметры исходящих подключений:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (и их варианты в нижнем регистре),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
Глобальный диспетчер Undici использует те же правила определения прокси исключительно по переменным окружения и обхода прокси
для локальных хостов, что и сервер, включая `NO_PROXY`; он не импортирует `proxyFetch.ts` или связанные с ним флаги БД и функций.
Учётные данные прокси скрываются в пересылаемом выводе и записываемых ошибках. Учётные данные назначения
передаются только в одном стартовом IPC-сообщении, но никогда через argv или окружение; пересылаемые вывод и ошибки
снабжаются префиксом и очищаются от конфиденциальных данных. В аргументах запуска дочернего процесса отключается только `ExperimentalWarning`, чтобы
не повторять предупреждение Node о SQLite при каждом запуске cron; другие типы предупреждений остаются видимыми.

Модули назначений должны допускать импорт без зависимостей Next.js и зависимостей, предназначенных только для сервера. Существующая
реализация BigQuery уже соответствует этому требованию. Кеши токенов доступа сохраняются только на время работы дочернего
процесса, но не между запусками. Поддерживаемая среда выполнения — Node (engines в `package.json`), однако раздел README об установке Bun
и `Dockerfile.bun` также предлагают совместимый вариант для производственной среды с использованием
`bun:sqlite` (`src/lib/db/core.ts` / адаптеры). Поэтому под Bun экспорт сохраняет прежний
путь выполнения внутри процесса и однократно выдаёт предупреждение: изоляция кучи и тайм-аута в дочернем процессе недоступна. Используйте
Node для изоляции цикла событий и сбоев из-за нехватки памяти; здесь Bun не считается средой только для разработки.

Если включён `includeBodies`, предпочтительнее запускать экспорт с интервалом в несколько минут, например
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`, а не накапливать данные тел запросов и ответов за час.
Ограничения на размер пакета и число строк по-прежнему ограничивают каждый запуск. Процесс запускается отдельно для каждого назначения при каждом запуске;
небольшие затраты на запуск обеспечивают изоляцию цикла событий сервера, а не снижение общего потребления CPU.

### Данные тел (промпты и ответы)

По умолчанию экспорт содержит только сводные поля, отображаемые в **списке** журналов. Включение
**Экспорта промптов и ответов** (`includeBodies`) дополнительно передаёт данные, отображаемые на панели **подробностей**
журналов для каждого вызова:

| Поле                             | Содержимое                                                                  |
| -------------------------------- | --------------------------------------------------------------------------- |
| `request_body` / `response_body` | Тела вызова в том виде, в котором их отображает панель управления           |
| `pipeline_route_decision`        | Какое назначение и модель выбрал маршрутизатор                              |
| `pipeline_client_request`        | Исходный запрос точно в том виде, в котором его отправил клиент             |
| `pipeline_openai_request`        | После преобразования во внутренний формат OpenAI                            |
| `pipeline_provider_request`      | В том виде, в котором запрос фактически отправлен провайдеру, в его формате |
| `pipeline_provider_response`     | Исходный ответ провайдера                                                   |
| `pipeline_client_response`       | Данные, возвращённые вызывающей стороне                                     |
| `pipeline_error`                 | Подробности ошибки конвейера для неудачного вызова                          |
| `bodies_truncated`               | Истинно, если любое из полей выше достигло `maxBodyBytes`                   |

Эти данные содержат промпты, поэтому их экспорт **отключён по умолчанию** и намеренно настраивается отдельно для каждого назначения.
Экспортируются те же данные, которые отображаются на панели управления, поскольку экспорт и `getCallLogById` используют общий механизм
получения подробностей: при записи из тел
уже удаляются персональные данные и скрываются секреты, а для вызова с
API-ключом `noLog` тела вообще не сохраняются, поэтому экспортировать нечего.

Тела считываются для каждой строки из артефакта в файловой системе, поэтому загрузка этих данных выполняется только для назначений,
которые её запросили. Если артефакт отсутствует или повреждён, экспортируется сводная информация с телами, равными null,
вместо сбоя всего пакета и остановки продвижения курсора.

`maxBodyBytes` (по умолчанию 262144) ограничивает размер каждого поля. Более длинные тела **обрезаются, а не
отбрасываются** — даже обрезанный промпт позволяет понять, «что было запрошено», — а строка помечается флагом
`bodies_truncated`. Потоковые приращения по отдельным фрагментам не экспортируются; собранный ответ
уже содержится в `pipeline_provider_response` и `pipeline_client_response`.

## 3. REST API

Все маршруты требуют аутентификации для управления (`requireManagementAuth`). Секреты никогда не возвращаются:
сохранённый секрет возвращается в виде литерала `__stored__`, а передача этого значения обратно при обновлении
сохраняет существующие учётные данные.

Создание или обновление назначения, тип которого объявляет секрет, **требует наличия
`STORAGE_ENCRYPTION_KEY`**. Без него `encrypt()` молча возвращает данные без изменений, поэтому запись
отклоняется с кодом 400, чтобы не помещать учётные данные в SQLite в открытом виде (такую же проверку
применяет вебхук Telegram).

| Метод    | Путь                                     | Назначение                                                                            |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | Типы назначений и список полей их конфигурации                                        |
| `GET`    | `/api/log-export/destinations`           | Список назначений (секреты скрыты)                                                    |

## 4. Назначение экспорта BigQuery

Ключи конфигурации (`type: "bigquery"`):

| Ключ                 | Примечания                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `projectId`          | Проект GCP, содержащий набор данных                                                      |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                          |
| `tableId`            | `[A-Za-z0-9_]+`                                                                          |
| `location`           | Используется только при создании набора данных (по умолчанию `EU`)                       |
| `serviceAccountJson` | Ключ сервисного аккаунта. Секрет: хранится в зашифрованном виде, никогда не возвращается |
| `autoCreate`         | Создать набор данных и таблицу при первом экспорте (по умолчанию `true`)                 |

Сервисному аккаунту требуется разрешение `bigquery.tables.updateData` для целевой таблицы, а также
`bigquery.datasets.create` / `bigquery.tables.create`, если включён `autoCreate`.

Настроенный пакет — это единица продвижения **курсора**, а не HTTP-запроса: `send()` разбивает его на вызовы insertAll
не более чем по 500 строк, поэтому большой `batch_size` не приведёт к превышению ограничения BigQuery в 10 МБ на запрос.
При временных ошибках со статусами (408/429/500/502/503/504) выполняется до трёх повторных попыток с экспоненциальным
увеличением задержки и повторным использованием тех же insertIds; при ошибках аутентификации и схемы исключение выбрасывается с первой попытки,
чтобы не тратить время выполнения впустую.

Таблица, созданная только что, ещё не видна конечной точке потоковой вставки, которая в течение
нескольких секунд отвечает кодом 404. При таком ответе 404 запрос повторяется, но **только если таблица была создана в текущем запуске** —
если таблица действительно отсутствует, выполнение по-прежнему завершается ошибкой сразу. Обратите внимание: при повторном создании таблицы с именем,
которое недавно было удалено, BigQuery отклоняет потоковые вставки в течение нескольких минут; это
особенность последовательности «удаление — повторное создание», поэтому лучше использовать новое имя таблицы, а не удалять и создавать её заново.

**При частичном сбое возвращается HTTP 200 с непустым `insertErrors[]`.** Это считается
ошибкой и приводит к выбросу исключения, что не позволяет курсору продвинуться за строки, которые BigQuery так и не
принял; `tests/unit/log-export-bigquery.test.ts` фиксирует это поведение.

Для передачи используется обычный REST — самостоятельно подписанное утверждение RS256 обменивается на токен доступа по адресу
`https://oauth2.googleapis.com/token`, затем строки отправляются в `tabledata.insertAll`. Google SDK не
подключается. Токены доступа кешируются внутри процесса для каждой пары (сервисный аккаунт, область доступа).

Созданная таблица содержит по одному столбцу для каждого поля вкладки Logs, а также `exported_at`; её структура учитывает
реальные запросы к журналам вызовов:

- **Секционирование по дням на основе `timestamp`**, благодаря чему запрос с ограничением по дате сканирует только соответствующие дни.
- **Кластеризация по `api_key_name`, `provider`, `model`, `status`** (в указанном порядке), благодаря чему фильтрация по
  инициатору вызова, месту назначения или наличию ошибки исключает ненужные блоки внутри каждого раздела. BigQuery
  допускает не более четырёх столбцов кластеризации, и их порядок имеет значение: фильтр только по `api_key_name`
  исключает ненужные блоки, а фильтр только по `status` — нет.
- **Необязательное ограничение срока хранения разделов** через `partitionExpirationDays` (0 означает хранение всех данных), применяемое
  при создании таблицы.

Обе настройки применяются при создании. Существующая таблица сохраняет свою текущую структуру, поэтому
укажите в назначении экспорта новый идентификатор таблицы, если хотите применить эти настройки.

`tests/unit/log-export-bigquery.test.ts` проверяет, что преобразователь и схема таблицы остаются
согласованными, чтобы новый столбец журнала вызовов не мог незаметно потеряться при экспорте.

Пакеты разбиваются на части **одновременно** по числу строк и объёму сериализованных данных в байтах. Одного числа строк недостаточно,
если экспортируется содержимое запросов: 500 строк с промптами могут занимать десятки мегабайт, а insertAll
отклоняет запросы размером более 10 МБ. Формирование части завершается при достижении 500 строк или 9 МБ — в зависимости от того, что наступит раньше.

## 5. Назначение экспорта трассировок OTLP/HTTP

В конфигурации используется `type: "otlp-http"`. Это выполняемый по расписанию экспорт сохранённых
журналов вызовов с отслеживанием позиции курсором, а не приёмник событий маршрутизации в реальном
времени с доставкой по возможности из
`open-sse/services/routing/otel.ts`. Он не читает и не изменяет переменные окружения,
таймеры или буферы этого приёмника. При включении обоих механизмов могут создаваться два независимых вида спанов;
используйте область инструментирования `omniroute.log-export`, чтобы отличать эти спаны журналов вызовов.

| Ключ                     | Значение по умолчанию / назначение                                                                          |
| ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `endpoint`               | Обязательный полный HTTP(S) URL трассировок; суффикс `/v1/traces` не добавляется                            |
| `headers`                | Необязательные строки `Name: value` или JSON-объект со строковыми значениями; хранятся в зашифрованном виде |
| `requestHeaderAllowlist` | Пусто (выключено); имена/префиксы клиентских заголовков для записи в атрибуты спана                         |
| `serviceName`            | `omniroute`; атрибут ресурса `service.name`                                                                 |
| `langfuseMapping`        | `false`; добавляет атрибуты генерации/сессии/пользователя Langfuse                                          |
| `identity`               | `pseudonymous`, `keyName` или `none`                                                                        |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                                     |
| `timeoutMs`              | `30000` на каждую HTTP-попытку                                                                              |
| `environment`            | Не задано; необязательный атрибут `langfuse.environment`                                                    |

Эти поля отображаются в общей панели управления. `paths` принимает массив через API или содержимое текстового поля
с точными путями, разделёнными переводами строк/запятыми. Пути для эмбеддингов, переранжирования и других операций
пропускаются, если они не разрешены явно. Пропущенные строки всё равно продвигают курсор; существующие
счётчики исполнителя `exported`/`exportedTotal` учитывают обработанные исходные строки, включая отфильтрованные,
а не принятые спаны. Фильтрация выполняется в дочернем процессе без изменения его
контракта IPC/курсора.

Для проверки URL используется вспомогательная функция `parseAndValidateNonMetadataUrl` из
`src/shared/network/outboundUrlGuard.ts`, не требующая БД: политика `block-metadata`. Она выполняет те же
безусловные проверки адресов метаданных, протоколов и встроенных учётных данных, что и валидатор вебхуков
с разрешёнными частными URL, но намеренно разрешает адреса localhost/LAN без глобального
переопределения флагом функции. Это позволяет использовать самостоятельно размещённые конечные точки Langfuse, Phoenix, Tempo и Collector,
включая частные HTTP-конечные точки. Хосты облачных метаданных всегда блокируются.
Перенаправления не выполняются, поэтому коллектор не может перенаправить учётные данные на другой хост.
Как и существующий механизм лексической проверки URL, эта проверка не фиксирует результат разрешения DNS; настраивайте
только хосты, контролируемые оператором. Отдавайте предпочтение HTTPS, если конечная точка находится вне доверенной сети.

### Полезная нагрузка и доставка

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) содержит один
спан CLIENT на каждую разрешённую строку; имя спана точно совпадает с путём запроса. Именование по пути позволяет различать
Chat Completions, Responses и Messages, не включая сведения о модели или идентификации в
имя спана. Атрибуты ресурса включают `service.name` и `service.version` пакета.

Обычный механизм журналирования попыток чата (`open-sse/handlers/chatCore/attemptLogging.ts`) записывает
`duration = Date.now() - startTime` при завершении и не передаёт временную метку;
`saveCallLogOperation` в `src/lib/usage/callLogs.ts` по умолчанию задаёт временную метку как время записи
(завершения). Поэтому при экспорте конец задаётся временной меткой строки, а начало — как конец минус длительность
(миллисекунды, преобразованные в десятичные наносекунды). Переданные вызывающей стороной исторические временные метки
также сохраняются как время окончания; отдельного признака начала/завершения для каждой строки нет.
Длительность null преобразуется в ноль. Недопустимые или отсутствующие временные метки приводят к сбою пакета, а не к созданию
недетерминированных спанов. `ttftMs` допускает null и сопоставляется с `omniroute.ttft_ms`.

Атрибуты включают `gen_ai.operation.name="chat"`, провайдера, запрошенную модель и модель ответа,
входные/выходные токены, необязательные токены чтения кэша/создания кэша/рассуждений, HTTP-статус,
комбинацию, источник кэша, тег сессии и идентификатор корреляции. Целочисленные значения OTLP и временные метки
представляются десятичными строками; строки, логические значения и дробные числа используют соответствующие им варианты значений
OTLP. Спаны ошибок имеют статус ERROR и очищенное сообщение статуса. Каноническая
запись не содержит URL вышестоящего хоста, поэтому `server.address` опускается, чтобы не указывать
коллектор в качестве сервера модели. Стоимость не экспортируется.

Только `includeBodies=true` подгружает содержимое. При `langfuseMapping=false`
`gen_ai.input.messages` / `gen_ai.output.messages` содержат очищенный JSON тела запроса/ответа
в том виде, в котором он хранится в OmniRoute (канонизированный, если его можно разобрать), а не преобразованный массив
сообщений по семантическим соглашениям. Усечённые тела и тела не в формате JSON остаются обычным текстом. При `langfuseMapping=true`
тела передаются только в `langfuse.observation.input` / `langfuse.observation.output`;
атрибуты `gen_ai.*.messages` опускаются, поэтому каждое тело отправляется один раз. Оба режима
наследуют `maxBodyBytes` из существующего механизма подгрузки;
`omniroute.bodies_truncated=true` обозначает усечение.
Это назначение не добавляет дополнительных снимков конвейера или чтения неочищенных артефактов;
необязательный захват заголовков запросов использует существующий подгруженный снимок клиента, описанный ниже.
При экспорте тел используйте расписание с интервалом в несколько минут, например `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`,
вместо накопления часовой очереди.

### Необязательные заголовки клиентских запросов

Захват заголовков **по умолчанию выключен**. Задайте `requestHeaderAllowlist` в конфигурации назначения
и включите **Экспорт промптов и ответов** (`includeBodies: true` в назначении).
Список разрешений принимает массив через API или содержимое текстового поля с именами, разделёнными переводами строк/запятыми:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

Имена сопоставляются целиком без учёта регистра, если только единственный завершающий `*` не задаёт непустой
префикс имени заголовка. Отдельный `*`, встроенные подстановочные символы и недопустимые имена HTTP-заголовков отклоняются.
Допускается не более 64 селекторов, каждый с именем или префиксом длиной не более 256 байт ASCII.
Эта настройка не связана с `headers`, который используется для аутентификации экспортера в коллекторе.

При захвате читается только `pipeline_client_request`, заполняемый из
`clientRawRequest` (или устаревшего `clientRequest`) сохранённого подробного конвейера. Заголовки запроса к провайдеру никогда не используются как запасной источник.
Подробное журналирование конвейера должно быть включено на момент записи запроса. Если
`includeBodies` отключён либо JSON-снимок клиента отсутствует, повреждён или усечён, атрибуты
заголовков не формируются. Увеличение `maxBodyBytes` позволяет избежать усечения снимка при экспорте;
оно не может восстановить данные, которые не были сохранены. Снимок размером более 1 МиБ или содержащий более
256 записей заголовков игнорируется. Существующий экспорт запросов и ответов остаётся включённым наряду
с захватом заголовков; список разрешённых заголовков не предоставляет режима загрузки только заголовков.

Выбранные значения становятся массивами строк OTLP `http.request.header.<full lowercase header name>`,
даже если значение — одна строка. Например, `X-OmniRoute-Meta-Team: example-team` преобразуется в
`http.request.header.x-omniroute-meta-team` со значением
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
Полный префикс сохраняется: это обычные заголовки, без разбора бизнес-полей или
преобразования в метаданные `omniroute.metadata.*` / Langfuse. `langfuseMapping` не меняет семантику
заголовков. Выбранный заголовок `User-Agent` с одним значением также задаёт стандартный скалярный атрибут
`user_agent.original`. Запятые внутри одного значения не приводят к его разделению. Варианты с разным регистром объединяются в порядке
сохранённых записей; любой недопустимый вариант приводит к исключению всего заголовка. Атрибуты упорядочиваются по имени в нижнем регистре.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, заголовки API-ключей, имена, содержащие
маркеры auth/token/secret/password/credential, и внутренние учётные данные шлюза всегда
исключаются, даже если они выбраны или частично замаскированы в хранилище. Для известных шаблонов учётных данных используется
общий детектор учётных данных; маркеры скрытия исключаются, а не экспортируются как безопасные значения.
Принимаются только строки и непустые массивы строк; числа и объекты не преобразуются.
Недопустимые имена, ключи прототипа, управляющие символы (кроме горизонтальной табуляции) и некорректный Unicode
игнорируются без сбоя пакета и без включения их содержимого в сообщения об ошибках.

Каждый спан захватывает не более 32 заголовков, 16 значений на заголовок, 4096 байт UTF-8 на значение
и суммарно 16384 байт UTF-8 для имён и значений захваченных заголовков. Слишком большие или недопустимые заголовки
исключаются целиком, а не усекаются. Выбор заголовков — решение оператора в отношении конфиденциальности: даже безопасные на вид имена
могут содержать персональные данные, а эти ограничения и детекторы не являются универсальным средством очистки персональных данных.

### Ограничения доставки

Запросы ограничены 500 спанами и 4 МиБ JSON в UTF-8, включая оболочку.
Размер каждого разрешённого спана проверяется до первого запроса пакета курсора. Если отдельный
спан превышает лимит, ни одна часть этого пакета не отправляется, а операция завершается ошибкой с рекомендацией уменьшить
`maxBodyBytes`; спан не отбрасывается без уведомления. Предварительная проверка сохраняет только ссылки на записи и
количество байт, удаляя каждый временный спан и JSON; спаны заново создаются для порций ограниченного размера,
вместо хранения второй сериализованной копии пакета. При HTTP 408/429/5xx, сетевых сбоях и тайм-аутах выполняется не более
трёх попыток с экспоненциальной задержкой 250/500 мс. `Retry-After` в секундах или в формате HTTP-даты
может увеличить задержку до 5 секунд. Остальные статусы приводят к немедленному сбою. Частичное отклонение OTLP при статусе 2xx также вызывает исключение вместо
подтверждения потерянного спана; принимаются пустые подтверждения или подтверждения с корректным JSON,
при этом чтение ответа ограничено 64 КиБ.

Ошибки содержат только сведения, которыми располагает сам экспортер: HTTP-статус, категорию повторной попытки, число попыток и отправленных
спанов либо фиксированные формулировки о сбое подтверждения или сети. Тела ответов коллектора,
счётчики частичного успеха и заголовки ответов никогда не копируются в ошибки, журналы или на
панель мониторинга. Сбойный или частично принятый пакет не подтверждается: для назначения отображается
состояние сбоя с соответствующим статусом, курсор остаётся на последнем подтверждённом пакете, а следующий запуск
повторно отправляет те же строки. Постоянные статусы ошибки продолжают вызывать сбой, пока не будет исправлен коллектор или
конфигурация. Подробности ответа смотрите в собственных журналах коллектора. Для сводок ошибок журнала вызовов сохраняется
отдельный механизм скрытия конфиденциальных данных.
`prepare()` ничего не создаёт; проверка отправляет POST-запрос с содержимым ровно `{"resourceSpans":[]}` и сообщает
HTTP-статус, не записывая спаны журнала вызовов.

Идентификаторы трассировок и спанов — это первые 32/16 шестнадцатеричных цифр SHA-256 от
`"omniroute.trace\\0" + callLogId` и `"omniroute.span\\0" + callLogId`. Повторные отправки содержат
те же идентификаторы. Это не гарантирует дедупликацию: некоторые серверные системы, включая приём данных Langfuse
v4, не устраняют дубликаты спанов с одинаковыми идентификаторами. Аварийное завершение или сбой части пакета может
привести к повторной отправке не более одного неподтверждённого пакета курсора; дублироваться может весь этот пакет,
а не только его последняя HTTP-порция. Учитывайте этот компромисс при выборе размера пакета курсора.

### Пример для Langfuse

Настройте следующие поля для самостоятельно размещённого экземпляра Langfuse:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Сформируйте значение Authorization локально, закодировав в Base64 буквальную строку `public-key:secret-key`
(например, с помощью `Buffer.from(publicKey + ":" + secretKey).toString("base64")`).
Не вставляйте реальные учётные данные в журналы, снимки экрана или сообщения о проблемах. Сопоставление автоматически
задаёт `x-langfuse-ingestion-version: 4`; Authorization по-прежнему передаётся через `headers`.
И заголовки, и сгенерированная соль идентификации используют существующий механизм шифрования секретных
полей и значения-заполнители API; требуется `STORAGE_ENCRYPTION_KEY`.

Сопоставление добавляет тип/модель генерации, сведения об использовании в JSON (входные/выходные/общие значения и доступные
ключи кэша), снимки входных/выходных данных в JSON, уровень ERROR/DEFAULT, очищенное сообщение о статусе,
имя трассировки, идентификатор сессии, необязательное окружение и доступные для фильтрации
`langfuse.observation.metadata.<key>` для провайдера, запрошенной модели, пути, комбинации, источника
кэша и статуса. `langfuse.observation.completion_start_time` задаётся в формате ISO 8601 как
время начала + TTFT, только если TTFT известно и укладывается в длительность. Атрибуты стоимости не отправляются.

Режимы идентификации применяются к `langfuse.user.id`:

- `pseudonymous` (по умолчанию): HMAC-SHA256 от внутреннего идентификатора API-ключа со случайной
  32-байтовой солью для каждого назначения. Если соль отсутствует, она генерируется при создании, шифруется
  как `identitySalt`, никогда не возвращается и сохраняется при редактировании. Исходные идентификаторы ключей никогда не
  помещаются в атрибуты спанов. Повторное создание или ротация соли назначения изменяет идентификаторы пользователей.
- `keyName`: настроенное имя API-ключа, намеренно раскрывающее эту метку, заданную оператором.
- `none`: без идентификатора пользователя. Теги сессии по-прежнему экспортируются, если они есть; эти режимы не
  анонимизируют произвольное содержимое промптов или заданные оператором метки сессий/корреляции.

### Запуск без загрузки исторических данных

Только при создании включите **Начать с текущей позиции (пропустить существующие журналы)** или передайте
`startFromCurrentPosition: true` на верхнем уровне тела запроса API создания. Это инициализирует
`cursor_row_id` текущим максимальным rowid среди сохранённых строк журнала вызовов с помощью существующих вспомогательных функций
для курсора, без миграции. По умолчанию используется false (курсор 0 и загрузка сохранённой истории).
Это не настройка сброса курсора при обновлении.

Общее дополнение `ttftMs` также добавляет допускающий NULL столбец `ttft_ms` в средство сопоставления BigQuery
и схему новых таблиц: тест схемы требует, чтобы каждому полю канонической записи соответствовал
столбец. Экспорт в существующие таблицы продолжается без изменений: `prepare()` считывает схему таблицы и
исключает только `ttft_ms`, если этот столбец отсутствует. Добавьте допускающий NULL столбец INT64, чтобы получить TTFT
при следующем запуске, или используйте новую таблицу. PATCH, автоматическое изменение схемы и дополнительные
разрешения не требуются; для всех остальных полей строк сохраняется строгая проверка схемы.

## 6. Добавление назначения

1. Создайте `src/lib/logExport/destinations/<name>.ts`, экспортирующий `LogExportDestinationType`:
   схему Zod `configSchema`, массив дескрипторов `fields` для интерфейса, `secretFields` и
   `createClient(config)`, возвращающий `test()` / `prepare()` / `send(records)`.
2. Добавьте его в массив `DESTINATIONS` в `src/lib/logExport/registry.ts`.
3. Напишите тесты в `tests/unit/`.

Это все необходимые изменения: хранение данных, задание cron, слой REST, шифрование секретов и
форма панели управления — всё использует реестр.

Два правила для нового назначения:

- `send()` **должен выбрасывать исключение** при частичном сбое. Успешное завершение означает «эти строки уже есть в назначении»,
  и курсор безвозвратно перемещается за них.
- Назначение, принимающее URL от пользователя, должно проверять его через
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) перед выполнением запроса,
  так же, как это делают вебхуки. Для BigQuery это не требуется: его хосты заданы константами.

## 7. Эксплуатация

- **Панель управления**: Интеграции → Экспорт журналов. Добавьте назначение, нажмите **Тест**, чтобы проверить учётные данные
  без записи строк, затем включите его.
- **Очередь**: на карточке каждого назначения отображаются ожидающие отправки строки и курсор; `GET
/api/log-export/status` возвращает те же показатели, а также последние 20 запусков задания.
- **Сбой одного назначения не приводит к сбою остальных** — сводка запуска содержит статус каждого назначения
  в `last_status` / `last_error`, а история запусков задания хранит сводные данные.
- **При удалении назначения удаляется и его курсор.** После повторного добавления отправка начинается с самой старой сохранённой
  записи журнала вызовов, поэтому строки, которые уже могут быть в назначении, отправляются повторно. В BigQuery идентификатор строки
  `insertId` предотвращает такие дубликаты только в пределах собственного окна дедупликации BigQuery, поэтому лучше отключать
  назначение, а не удалять его.
