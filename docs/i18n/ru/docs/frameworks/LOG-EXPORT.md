Непрерывный инкрементальный экспорт журналов вызовов OmniRoute во внешнее аналитическое хранилище.

Вкладка журналов на панели управления хранит историю запросов в SQLite (`call_logs`), объём которой ограничен
ротацией и сроком хранения. Экспорт журналов отправляет тот же набор записей по расписанию, чтобы он мог храниться
дольше локальной базы данных и объединяться с другими данными. Первое поддерживаемое назначение — BigQuery;
конвейер построен на реестре, поэтому новые назначения можно добавлять независимо.

## 1. Как это работает

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **Расписание** — одно задание cron `JobRegistry`, `log_export`, по умолчанию — `0 * * * *` (почасово, UTC). Зарегистрирован в `src/lib/initCloudSync.ts`; переопределяется с помощью `OMNIROUTE_LOG_EXPORT_CRON`. Каждый тик истощает каждую** включено** пункт назначения последовательно.
- **Cursor** — Неявный `call_logs.rowid` SQLite сохраняемый для каждого пункта назначения в `log_export_destinations.cursor_row_id`. `timestamp` намеренно не является курсором: вызывающие могут указать свое собственное значение, поэтому медленный запрос может быть записан после более быстрого, который начался позже, и курсор метки времени пропустит его.
- **Пакетирование** — `batch_size` строк на запрос (по умолчанию 500), `max_rows_per_run` строк на запуск (по умолчанию 10 000), поэтому большое количество невыполненной работы истощается в течение нескольких тактов вместо того, чтобы блокировать один.
- **Доставка** — курсор перемещается только после разрешения `send()`. Неудачный пакет оставляет курсор там, где он был, поэтому при следующем запуске повторяются те же строки. Гарантия — это по крайней мере один раз плюс дедупликация на стороне назначения, но не ровно один раз: BigQuery ключает каждую строку по идентификатору журнала вызовов, который он учитывает по мере возможности в своем собственном окне дедупликации.
- **Защита перекрытия** — тик cron и `POST .../run` могут работать вместе. Пункт назначения, который уже опорожняется, пропускается, а не очищается дважды (`skipped: true` в результате выполнения), поэтому одновременный запуск не может повторно отправить пакет или записать курсор назад.
- **Очистить восстановление** — если `cursor_row_id` оказывается выше `MAX(rowid)` (вся таблица была очищена, а идентификаторы строк перезапущены), бегун перематывается на 0, а не становится навсегда слепым.

### Изолированный бегун и ограничения

Каждый целевой запуск на узле запускает отдельный недолговечный дочерний процесс OS (`child_process` с IPC, а не `worker_threads`). Чтение тела, полезная нагрузка JSON parsing/serialization, назначение `prepare()` и сеть назначения I/O выполняются там, а не в цикле событий сервера. Через IPC проходят только сообщения о конфигурации и небольшие сообщения о ходе выполнения; экспортированные записи никогда не возвращаются на сервер. Задание cron и маршрут «Выполнить сейчас» сохраняют один и тот же общедоступный результат и защиту от перекрытия.

Дочерний элемент открывает разрешенный сервером `DATA_DIR/storage.sqlite` только для чтения с помощью `node:sqlite` с помощью `busy_timeout=5000` и `query_only=ON`. Он не импортирует синглтон DB и не выполняет миграции, резервные копии или обновления SQLite. Учет артефактов Missing/corrupt (включая поврежденный артефакт UPDATE) остается только в пути к подробностям информационной панели. Оба пути используют чистый преобразователь деталей; При экспорте используется асинхронное чтение файловой системы и тот же порядок разрешения артефакта → устаревший встроенный → устаревший диск → нет. При запуске создается снимок максимального идентификатора строки вставки, когда дочерний элемент открывает свое средство чтения; более поздние вставки ждут следующего запуска. Это граница вставки, а не долгоживущая транзакция SQLite : модули записи и контрольные точки WAL остаются свободными во время ожидания в сети. Updates/deletions существующих строк не замораживаются этой границей.

После каждой принятой партии ребенок ждет подтверждения. Сервер сначала сохраняет курсор с помощью `advanceLogExportCursor`, затем отправляет `ack`; никакая следующая партия не начинается раньше нее. Сбой отправки, сбой или тайм-аут фиксируют сбой без продвижения этого пакета. Ранее подтвержденные пакеты остаются зафиксированными; повторно можно отправить максимум один неподтвержденный пакет. Успех фиксируется только после `done` и чистого дочернего выхода. При сбоях дочерний процесс завершается с помощью SIGTERM, переходя к SIGKILL через 500 мс, и исполнитель ожидает закрытия процесса.

| Переменная среды                              | По умолчанию | Цель                                                      |
| --------------------------------------------- | ------------ | --------------------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | Ограничение настенных часов для каждого пункта назначения |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | Ограничение старого пространства дочернего V8 в MB        |

Значения Invalid/non-positive/non-integer используют значения по умолчанию. Настройка кучи не является общим пределом RSS ; очень большие пакеты все равно могут исчерпать дочернюю память и безопасно завершить выполнение. Значение по умолчанию 1024 MB оставляет запас для стандартного пакета из 500 строк из 512 артефактов KiB с включенными телами, включая побайтовую сериализацию JSON в BigQuery. Это не делает партию тел из 10 000 рядов безопасной. Исчерпание кучи V8 фиксирует сбой, требующий принятия мер: уменьшить размер пакета или увеличить `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; курсор остается на последней подтвержденной партии. Исторические тела inline/disk не покрываются современной крышкой артефакта. Операторы должны составлять бюджет RSS отдельно, особенно внутри контейнеров с ограниченной памятью.

Дочерний элемент наследует только разрешенные значения `DATA_DIR`, `NODE_ENV`, явное значение `TZ` (устаревшее разрешение имени файла в локальном времени), `ELECTRON_RUN_AS_NODE` если оно присутствует, и следующие исходящие входные данные: `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (и их строчные формы), `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`. Глобальный диспетчер Undici разделяет чистое разрешение прокси-сервера среды и правила обхода локального хоста, включая `NO_PROXY`; он не импортирует `proxyFetch.ts` или его флаги DB/feature. Учетные данные прокси-сервера удаляются из пересылаемых выходных данных и регистрируются ошибки. Учетные данные назначения передаются только в одном начальном сообщении IPC, а не в argv или среде; Пересылка output/error имеет префикс и очищается. В аргументах дочернего exec отключен только `ExperimentalWarning`, чтобы избежать повторения предупреждения SQLite узла при каждом запуске cron; другие типы предупреждений остаются видимыми.

Целевые модули должны быть импортируемыми без зависимостей Next.js/server-only. Существующая реализация BigQuery уже соответствует этому контракту. Кэши токенов доступа сохраняются только для дочернего запуска, а не для всех запусков. Node — это поддерживаемая среда выполнения (движки `package.json` ). Существует наилучший неподдерживаемый путь совместимости Bun (`bun:sqlite` в `src/lib/db/core.ts` / адаптерах и `Dockerfile.bun`), поэтому экспорт не должен прерываться по нему. При Bun экспорт сохраняет предыдущий путь в процессе и выдает одноразовое предупреждение: изоляция дочернего heap/timeout недоступна. Используйте Node для изоляции цикла событий и OOM.

Когда `includeBodies` включен, предпочтительнее использовать поминутную частоту, например `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` а не накапливать ежечасный журнал невыполненной нагрузки. Ограничения на партии и строки по-прежнему ограничивают каждый прогон. Запуск процесса оплачивается за каждый пункт назначения за прогон; это компенсирует небольшие затраты на запуск для изоляции цикла событий сервера, а не снижает общее использование CPU.

### Полезные данные (подсказки и дополнения)

По умолчанию экспорт содержит только сводные поля журналов.** список** шоу. Включение** Экспорт подсказок и ответов** (`includeBodies`) дополнительно отправляет журналы** деталь** Панель показывает для каждого вызова:

| Поле                             | Что он содержит                                                    |
| -------------------------------- | ------------------------------------------------------------------ |
| `request_body` / `response_body` | Полезные данные вызова, отображаемые на информационной панели      |
| `pipeline_route_decision`        | Какую цель и модель выбрал маршрутизатор                           |
| `pipeline_client_request`        | Необработанный запрос в том виде, в каком его отправил клиент.     |
| `pipeline_openai_request`        | После перевода во внутреннюю форму OpenAI                          |
| `pipeline_provider_request`      | Как фактически отправлено вверх по течению, на диалекте провайдера |
| `pipeline_provider_response`     | Необработанный ответ восходящего потока                            |
| `pipeline_client_response`       | Что вернули звонившему                                             |
| `pipeline_error`                 | Подробности ошибки на уровне конвейера для неудачного вызова       |
| `bodies_truncated`               | Истинно, когда любое поле выше соответствует `maxBodyBytes`        |

Это быстрый контент, поэтому он** выключено по умолчанию** и сознательно выбор для каждого пункта назначения. Поставляется то, что показывает панель мониторинга, поскольку экспорт и `getCallLogById` имеют общее разрешение детализации: полезные данные уже очищаются с помощью PII и секретно редактируются при их записи, а вызов, сделанный с помощью ключа `noLog` API вообще не сохраняет никаких полезных данных, поэтому экспортировать нечего.

Полезные данные считываются по строкам из артефакта файловой системы, поэтому гидратация выполняется только для тех мест назначения, которые ее запросили. Отсутствующий или поврежденный артефакт экспортирует свою сводку с нулевыми полезными данными вместо того, чтобы сбой пакета и зависание курсора.

`maxBodyBytes` (по умолчанию 262144) ограничивает каждое поле. Более длинные полезные нагрузки** скорее усечено, чем удалено** — обрезанное приглашение по-прежнему отвечает на вопрос «то, что было задано» —, и строка помечается флагом `bodies_truncated`. Поточные изменения по частям не экспортируются; собранный ответ уже находится в `pipeline_provider_response` и `pipeline_client_response`.

## 3. REST API

Все маршруты требуют аутентификации для управления (`requireManagementAuth`). Секреты никогда не возвращаются:
сохранённый секрет возвращается в виде литерала `__stored__`, а передача этого значения обратно при обновлении
сохраняет существующие учётные данные.

Создание или обновление назначения, тип которого объявляет секрет, **требует наличия
`STORAGE_ENCRYPTION_KEY`**. Без него `encrypt()` молча возвращает данные без изменений, поэтому запись
отклоняется с кодом 400, чтобы не помещать учётные данные в SQLite в открытом виде (такую же проверку
применяет вебхук Telegram).

| Метод    | Путь                                     | Назначение                                                                            |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | Типы назначений и список полей их конфигурации                                        |
| `GET`    | `/api/log-export/destinations`           | Список назначений (секреты скрыты)                                                    |
| `POST`   | `/api/log-export/destinations`           | Создать назначение                                                                    |
| `GET`    | `/api/log-export/destinations/{id}`      | Получить одно назначение                                                              |
| `PUT`    | `/api/log-export/destinations/{id}`      | Обновить имя / состояние включения / конфигурацию / параметры пакетной обработки      |
| `DELETE` | `/api/log-export/destinations/{id}`      | Удалить                                                                               |
| `POST`   | `/api/log-export/destinations/{id}/test` | Проверить учётные данные без записи                                                   |
| `POST`   | `/api/log-export/destinations/{id}/run`  | Выгрузить накопленные данные сейчас, тем же способом, что и при запуске по расписанию |
| `GET`    | `/api/log-export/status`                 | Состояние cron, последние запуски, очередь для каждого назначения                     |

`GET /api/log-export/types` делает интерфейс универсальным: форма панели управления строится на основе
возвращаемых описаний полей, поэтому добавление нового назначения не требует изменений интерфейса.

## 4. Назначение BigQuery

Ключи конфигурации (`type: "bigquery"`):

| Ключ                 | Примечания                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projectId`          | Проект GCP, содержащий набор данных                                                                                                               |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                                                                   |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                                                                   |
| `location`           | Используется только при необходимости создать набор данных (по умолчанию `EU`)                                                                    |
| `serviceAccountJson` | Ключ сервисного аккаунта. Секрет: зашифрован при хранении и никогда не возвращается                                                               |
| `autoCreate`         | Создавать отсутствующие набор данных/таблицу; условно добавлять допускающие значения NULL столбцы сведений об использовании (по умолчанию `true`) |

Сервисному аккаунту требуется разрешение `bigquery.tables.updateData` для целевой таблицы, а также
`bigquery.datasets.create` / `bigquery.tables.create`, если включён `autoCreate`.
Для обновления существующей таблицы с целью добавления двух допускающих значения NULL полей
сведений об использовании также требуется `bigquery.tables.update`. Отсутствующее разрешение
приводит к сбою экспорта без продвижения его курсора.

Настроенная пакетная загрузка является единицей **курсора**, а не HTTP-запросом: `send()` разбивает
её на вызовы insertAll максимум по 500 строк, поэтому большой `batch_size` не может привести к
превышению ограничения BigQuery в 10 МБ на запрос. Временные статусы (408/429/500/502/503/504)
повторяются до трёх раз с экспоненциальной задержкой, при этом используются те же insertIds; ошибки
аутентификации и схемы приводят к исключению при первой попытке, не расходуя весь запуск.

Таблица, созданная несколько мгновений назад, ещё не видна конечной точке потоковой передачи, которая
в течение нескольких секунд отвечает с кодом 404. Этот 404 повторяется, но **только если таблица
была создана в рамках текущего запуска** — действительно отсутствующая таблица немедленно приводит
к сбою. Обратите внимание: повторное создание таблицы под именем, которое недавно было удалено,
заставляет BigQuery отказывать в потоковых вставках в течение нескольких минут; это свойство
операции удаления с последующим созданием, поэтому вместо удаления и повторного добавления
предпочтительно использовать новое имя таблицы.

**Частичный сбой возвращается как HTTP 200 с непустым `insertErrors[]`.** Это считается сбоем и
приводит к исключению, что останавливает продвижение курсора за строки, которые BigQuery не
принял; такое поведение зафиксировано в `tests/unit/log-export-bigquery.test.ts`.

Транспорт — обычный REST: самоподписанное утверждение RS256 обменивается на токен доступа по адресу
`https://oauth2.googleapis.com/token`, после чего строки передаются в `tabledata.insertAll`. SDK
Google не подключается. Токены доступа кэшируются в процессе отдельно для каждой пары (сервисный
аккаунт, область действия).

Созданная таблица содержит по одному столбцу для каждого поля вкладки Logs, а также `exported_at`,
и организована с учётом фактического способа запросов к журналам вызовов:

- **С секционированием по дням на основе `timestamp`**, поэтому запрос с ограничением только по
  дате сканирует лишь соответствующие дни.
- **С кластеризацией по `api_key_name`, `provider`, `model`, `status`** (в указанном порядке), поэтому
  фильтрация по тому, кто выполнил вызов, куда он был направлен или завершился ли он ошибкой,
  отсекает блоки внутри каждого раздела. BigQuery допускает не более четырёх столбцов кластеризации,
  и их порядок имеет значение: фильтр только по `api_key_name` отсекает блоки, а фильтр только по
  `status` — нет.
- **С необязательным сроком хранения разделов** через `partitionExpirationDays` (значение 0 сохраняет
  всё), применяемым при создании таблицы.

Оба параметра применяются во время создания. Существующая таблица сохраняет уже имеющуюся
структуру, поэтому, если вы хотите применить эти настройки, укажите для назначения новый
идентификатор таблицы.

`tests/unit/log-export-bigquery.test.ts` проверяет, что маппер и схема таблицы остаются согласованными,
поэтому новый столбец журнала вызовов не может быть незаметно отброшен при экспорте.

Пакеты разбиваются **одновременно по количеству строк и сериализованному размеру в байтах**.
Одного ограничения по количеству строк недостаточно после начала экспорта полезных нагрузок: 500
строк с промптами могут занимать десятки мегабайт, а insertAll отклоняет запрос размером более
10 МБ. Пакеты завершаются при достижении 500 строк или 9 МБ — в зависимости от того, что наступит раньше.

## 5. Назначение трасс OTLP/HTTP

Конфигурация использует `type: "otlp-http"`. Это запланированный экспорт сохранённых
журналов вызовов с поддержкой курсора, а не sink событий маршрутизации в реальном времени
с наилучшими усилиями из `open-sse/services/routing/otel.ts`. Он не читает и не изменяет
переменные окружения, таймеры или буферы этого sink. Одновременное включение обоих
механизмов может создавать два независимых типа спанов; используйте область
инструментирования `omniroute.log-export`, чтобы различать эти спаны журналов вызовов.

| Ключ                     | Значение по умолчанию / назначение                                                  |
| ------------------------ | ----------------------------------------------------------------------------------- |
| `endpoint`               | Полный URL трасс HTTP(S), обязателен; суффикс `/v1/traces` не добавляется           |
| `headers`                | Необязательные строки `Name: value` или JSON-объект строк; шифруются                |
| `requestHeaderAllowlist` | Пусто (выключено); имена/префиксы заголовков клиента для записи как атрибутов спана |
| `serviceName`            | `omniroute`; ресурс `service.name`                                                  |
| `langfuseMapping`        | `false`; добавляет атрибуты генерации/сессии/пользователя Langfuse                  |
| `identity`               | `pseudonymous`, `keyName` или `none`                                                |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                             |
| `timeoutMs`              | `30000` для каждой попытки HTTP                                                     |
| `environment`            | Не задано; необязательный `langfuse.environment`                                    |

Общая панель мониторинга отображает эти поля. `paths` принимает массив API или текстовую
область с точными путями, разделёнными переводами строк или запятыми. Вызовы embeddings,
rerank и другие пути пропускаются, если они явно не разрешены. Пропущенные строки всё
равно продвигают курсор; счётчики `exported`/`exportedTotal` существующего runner
учитывают обработанные исходные строки, включая отфильтрованные, а не только принятые
спаны. Фильтрация выполняется в дочернем процессе без изменения его контракта
IPC/курсора.

Проверка URL использует не зависящий от БД вспомогательный метод
`parseAndValidateNonMetadataUrl` из `src/shared/network/outboundUrlGuard.ts`: политику
`block-metadata`. Она выполняет те же безусловные проверки метаданных, протокола и
встроенных учётных данных, что и валидатор webhook, с разрешёнными приватными URL, но
намеренно допускает цели localhost/LAN без глобального переопределения feature flag.
Это позволяет использовать конечные точки self-hosted Langfuse, Phoenix, Tempo и
Collector, включая приватные HTTP-конечные точки. Хосты облачных метаданных всегда
блокируются. Перенаправления не выполняются, поэтому collector не может перенаправить
учётные данные на другой хост. Как и существующий лексический URL-фильтр, этот механизм
не фиксирует результат DNS-разрешения; настраивайте только хосты, контролируемые
оператором. Если конечная точка не находится в доверенной сети, предпочтительно
используйте HTTPS.

### Полезная нагрузка и доставка

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) содержит
один спан CLIENT для каждой разрешённой строки, названный её точным путём запроса.
Именование по пути различает Chat Completions, Responses и Messages, не включая данные
о модели или идентификации в имя спана. Атрибуты ресурса включают `service.name` и
`service.version` пакета.

Обычный регистратор попыток чата
(`open-sse/handlers/chatCore/attemptLogging.ts`) записывает
`duration = Date.now() - startTime` при завершении и не передаёт временную метку;
`saveCallLogOperation` в `src/lib/usage/callLogs.ts` по умолчанию задаёт временную метку
в момент записи (завершения). Поэтому экспорт устанавливает end равным временной метке
строки, а start — равным end − duration (в миллисекундах, преобразованных в десятичные
наносекунды). Переданные вызывающей стороной исторические временные метки также
сохраняются как время end; различение начала/завершения для отдельных строк отсутствует.
Значение duration `null` преобразуется в ноль. Недействительные или отсутствующие
временные метки приводят к ошибке пакета, а не к созданию недетерминированных спанов.
`ttftMs` допускает значение null и преобразуется в `omniroute.ttft_ms`.

Атрибуты включают `gen_ai.operation.name="chat"`, провайдера, запрошенную модель и
модель ответа, количество входных/выходных токенов, необязательные токены чтения
кэша/создания кэша/рассуждения, статус HTTP, комбинацию, источник кэша, тег сессии и
идентификатор корреляции. Целочисленные значения и временные метки OTLP являются
десятичными строками; строки, логические значения и дробные числа используют
соответствующие нативные варианты значений OTLP. Спаны с ошибками имеют статус ERROR и
санированное сообщение о статусе. Каноническая запись не содержит URL хоста upstream,
поэтому `server.address` не указывается, вместо того чтобы ошибочно идентифицировать
collector как сервер модели. Стоимость не экспортируется.

Только `includeBodies=true` загружает содержимое. При `langfuseMapping=false`
`gen_ai.input.messages` / `gen_ai.output.messages` содержат санированный JSON тела
запроса/ответа в том виде, в котором он сохранён OmniRoute (канонизированный, если его
удалось разобрать), а не преобразованный массив сообщений semconv. Обрезанные тела или
тела, не являющиеся JSON, остаются необработанным текстом. При
`langfuseMapping=true` тела передаются только как
`langfuse.observation.input` / `langfuse.observation.output`; атрибуты
`gen_ai.*.messages` не указываются, поэтому каждое тело отправляется один раз. Оба
режима наследуют `maxBodyBytes` из существующего пути загрузки; значение
`omniroute.bodies_truncated=true` указывает на обрезку.
Это назначение не добавляет дополнительные снимки конвейера или чтение несанированных
артефактов; необязательная запись заголовков запроса использует существующий снимок
клиента, загружаемый описанным ниже способом. При экспорте тел используйте интервал с
точностью до минуты, например `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`, вместо
накопления часового отставания.

### Необязательные заголовки запроса клиента

Запись заголовков **по умолчанию отключена**. Задайте `requestHeaderAllowlist` в
конфигурации назначения и включите **Export prompts and responses**
(`includeBodies: true` в назначении).
Список разрешённых значений принимает массив API или текстовую область с именами,
разделёнными переводами строк или запятыми:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

Имена сопоставляются без учёта регистра и полностью, если только одиночный завершающий `*` не выбирает непустой префикс имени заголовка. Одиночный `*`, встроенные подстановочные знаки и недопустимые имена HTTP-заголовков отклоняются.
Допускается не более 64 селекторов, каждый из которых содержит имя/префикс длиной не более 256 байт ASCII.
Этот параметр не связан с `headers`, который используется для аутентификации экспортёра перед сборщиком.

Захват читает только `pipeline_client_request`, заполняемый из сохранённого подробного конвейера
`clientRawRequest` (или устаревшего `clientRequest`). Заголовки запроса провайдера в качестве
резервного источника никогда не используются. Подробное журналирование конвейера должно быть
включено в момент записи запроса. Если `includeBodies` отключён либо JSON-снимок клиента
отсутствует, повреждён или обрезан, атрибуты заголовков не передаются. Увеличение
`maxBodyBytes` может предотвратить обрезание снимка во время экспорта, но не восстановит
сведения, которые изначально не были сохранены. Снимок размером более 1 МиБ или содержащий
более 256 записей заголовков игнорируется. Существующий экспорт prompt/response остаётся
включённым одновременно с захватом заголовков; список разрешённых заголовков не предоставляет
режим гидратации только заголовков.

Выбранные значения становятся массивами строк OTLP
`http.request.header.<full lowercase header name>`, даже если строка всего одна. Например,
`X-OmniRoute-Meta-Team: example-team` преобразуется в
`http.request.header.x-omniroute-meta-team` со значением
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
Полный префикс сохраняется: это обычные заголовки, без разбора бизнес-полей и преобразования в
`omniroute.metadata.*` / метаданные Langfuse. `langfuseMapping` не меняет семантику заголовков.
Выбранный однозначный `User-Agent` также устанавливает стандартный скаляр
`user_agent.original`. Запятые внутри одного значения не разделяются. Варианты регистра
объединяются в порядке записей сохранённого объекта; если любой вариант недопустим, весь этот
заголовок исключается. Атрибуты упорядочиваются по имени в нижнем регистре.

`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, заголовки с API-ключами, имена,
содержащие маркеры auth/token/secret/password/credential, а также внутренние учётные данные
шлюза всегда исключаются, даже если они выбраны или частично замаскированы в хранилище.
Для известных шаблонов учётных данных повторно используется общий детектор учётных данных;
маркеры редактирования исключаются, а не экспортируются как безопасные значения.
Принимаются только строки и непустые массивы строк; числа и объекты не преобразуются.
Недопустимые имена, ключи прототипа, управляющие символы (кроме горизонтальной табуляции) и
некорректный Unicode игнорируются без сбоя пакета и без отражения их содержимого в ошибках.

Каждый span захватывает не более 32 заголовков, 16 значений на заголовок, 4096 байт UTF-8 на
значение и 16384 общих байт UTF-8 для захваченных имён и значений заголовков. Заголовки,
превышающие ограничения или недопустимые, исключаются целиком, а не обрезаются. Выбор
заголовков — это решение оператора о конфиденциальности: даже безопасно выглядящие имена могут
содержать персональные данные, а эти ограничения и детекторы не являются универсальным
средством очистки PII.

### Ограничения доставки

Запросы ограничены 500 span и 4 МиБ JSON в кодировке UTF-8, включая конверт.
Каждый разрешённый span проверяется на размер до первого запроса пакета курсора. Если отдельный
span превышает лимит, никакая часть этого пакета не отправляется и возвращается ошибка с
рекомендацией уменьшить `maxBodyBytes`; он не отбрасывается молча. Предварительная проверка
сохраняет только ссылки на записи и размеры в байтах, удаляя каждый временный span/JSON;
span пересоздаются для ограниченных фрагментов вместо хранения второй сериализованной копии
пакета. Для HTTP 408/429/5xx, сетевых сбоев и тайм-аутов выполняется не более трёх попыток с
экспоненциальной задержкой 250/500 мс. Значения секунд в `Retry-After` или даты HTTP могут
увеличить задержку максимум до 5 секунд. При других статусах выполнение немедленно завершается
ошибкой. Частичный отказ OTLP 2xx также вызывает ошибку вместо подтверждения потерянного span;
пустые или корректные подтверждения JSON принимаются, при этом чтение ответа ограничено
64 КиБ.

Ошибки содержат только факты, принадлежащие экспортёру: HTTP-статус, класс повторной попытки,
число попыток и количество отправленных span либо фиксированный текст об ошибке подтверждения
или сети. Тела ответов сборщика, количество частично успешно обработанных элементов и
заголовки ответов никогда не копируются в ошибки, журналы или панель мониторинга. Неудачный
или частично принятый пакет не подтверждается: назначение отображается как Failing с этим
статусом, курсор остаётся на последнем подтверждённом пакете, а следующий запуск повторно
отправляет те же строки. Постоянные статусы продолжают вызывать ошибку, пока сборщик или
конфигурация не будут исправлены. Подробности ответа следует искать в собственных журналах
сборщика. Сводки ошибок журнала вызовов сохраняют отдельное редактирование.
`prepare()` ничего не создаёт; Test отправляет ровно `{"resourceSpans":[]}` и сообщает
HTTP-статус, не записывая span журнала вызовов.

Идентификаторы trace и span — это первые 32/16 шестнадцатеричных цифр SHA-256 от
`"omniroute.trace\\0" + callLogId` и `"omniroute.span\\0" + callLogId`. Повторные отправки
содержат те же идентификаторы. Это не является гарантией дедупликации: некоторые бэкенды,
включая приём данных Langfuse v4, не выполняют дедупликацию span с одинаковыми
идентификаторами. Сбой или частичный отказ фрагмента может повторно отправить не более одного
неподтверждённого пакета курсора; весь этот пакет может быть продублирован, а не только его
последний HTTP-фрагмент. При выборе размера пакета курсора учитывайте этот компромисс.

### Пример Langfuse

Настройте следующие поля для самостоятельно размещённого экземпляра Langfuse:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Сформируйте значение Authorization локально как Base64 от буквальной строки
`public-key:secret-key` (например, с помощью `Buffer.from(publicKey + ":" + secretKey).toString("base64")`).
Не вставляйте реальные учётные данные в журналы, снимки экрана или задачи. Сопоставление
автоматически устанавливает `x-langfuse-ingestion-version: 4`; Authorization по-прежнему
передаётся в `headers`. И заголовки, и сгенерированная соль идентификатора используют
существующий механизм зашифрованных секретных полей и заполнители API; требуется
`STORAGE_ENCRYPTION_KEY`.

Сопоставление добавляет тип/модель генерации, сведения об использовании JSON (входные/выходные данные/общее количество и доступные ключи
кэша), снимки входных/выходных данных JSON, уровень ERROR/DEFAULT, санитизированное сообщение о состоянии,
имя трассировки, идентификатор сессии, необязательное окружение и фильтруемое
`langfuse.observation.metadata.<key>` для провайдера, запрошенной модели, пути, комбинации, источника
кэша и состояния. `langfuse.observation.completion_start_time` имеет формат ISO 8601 и содержит
момент начала + TTFT только если TTFT известен и укладывается в длительность. Атрибуты стоимости не передаются.

Режимы идентификации применяются к `langfuse.user.id`:

- `pseudonymous` (по умолчанию): HMAC-SHA256 внутреннего идентификатора API-ключа со случайной
  32-байтовой солью для каждого назначения. Соль создаётся при создании, если отсутствует, шифруется
  как `identitySalt`, никогда не возвращается и сохраняется при редактировании.
  Исходные идентификаторы ключей никогда не помещаются в атрибуты span. Повторное создание или ротация соли
  назначения изменяет идентификаторы.
- `keyName`: настроенное имя API-ключа, намеренно раскрывающее метку, заданную оператором.
- `none`: идентификатор пользователя отсутствует. Теги сессии по-прежнему экспортируются, если они присутствуют;
  эти режимы не анонимизируют произвольное содержимое промптов или заданные оператором метки сессии/корреляции.

### Начало без обратного заполнения

Только при создании включите **Start from current position (skip existing logs)** или передайте
`startFromCurrentPosition: true` на верхнем уровне данных запроса create API. Это инициализирует
`cursor_row_id` текущим максимальным сохранённым rowid журнала вызовов с помощью существующих вспомогательных
функций курсора, без миграции. Значение по умолчанию — false (курсор 0 и обратное заполнение сохранённой истории).
Это не параметр сброса курсора во время обновления.

Общее добавление `ttftMs` также добавляет допускающий значение NULL столбец `ttft_ms` в сопоставитель BigQuery
и схему новой таблицы: тест схемы требует, чтобы для каждого канонического поля записи существовал столбец.
Существующие таблицы продолжают экспортироваться без изменений: `prepare()` читает схему таблицы
и исключает только `ttft_ms`, если этот столбец отсутствует. Добавьте допускающий значение NULL столбец INT64,
чтобы получить TTFT при следующем запуске, или используйте новую таблицу. Необязательный столбец TTFT
не инициирует обновление схемы. Столбцы подтверждения использования
следуют описанному ниже условному потоку совместимости с явным включением; для остальных полей строк
сохраняется строгая проверка схемы.

## 6. Добавление назначения

1. Создайте `src/lib/logExport/destinations/<name>.ts`, экспортирующий `LogExportDestinationType`:
   схему Zod `configSchema`, массив дескрипторов `fields` для интерфейса, `secretFields` и
   `createClient(config)`, возвращающий `test()` / `prepare()` / `send(records)`.
2. Добавьте его в массив `DESTINATIONS` в `src/lib/logExport/registry.ts`.
3. Напишите тесты в `tests/unit/`.

Это все необходимые изменения: хранение данных, задание cron, слой REST, шифрование секретов и
форма панели управления — всё использует реестр.

Два правила для нового назначения:

- `send()` **должен выбрасывать исключение** при частичном сбое. Успешное завершение означает «эти строки уже есть в назначении»,
  и курсор безвозвратно перемещается за них.
- Назначение, принимающее URL от пользователя, должно проверять его через
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) перед выполнением запроса,
  так же, как это делают вебхуки. Для BigQuery это не требуется: его хосты заданы константами.

## 7. Работа с ним

- **Панель управления**: Интеграции → Экспорт журналов. Добавьте назначение, запустите **Тест**, чтобы проверить учётные данные
  без записи строк, затем включите его.
- **Очередь**: на карточке каждого назначения отображаются ожидающие строки и курсор; `GET
/api/log-export/status` возвращает те же показатели, а также последние 20 запусков заданий.
- **Сбой назначения не приводит к сбою остальных** — сводка запуска записывает статус каждого назначения в
  `last_status` / `last_error`, а история запусков заданий сохраняет итоговый результат.
- **Удаление назначения удаляет его курсор.** При повторном добавлении обработка начинается с самого старого
  сохранённого журнала вызовов, из-за чего строки, которые уже могут находиться в назначении, отправляются повторно. В BigQuery
  идентификатор `insertId` устраняет дубликаты только в пределах собственного окна дедупликации BigQuery, поэтому вместо удаления
  назначения рекомендуется его отключать.

### Совместимость схемы с данными об использовании

Новые таблицы BigQuery включают допускающий значения NULL столбец `usage_evidence` (STRING, содержащий JSON) и
`usage_estimated` (BOOL). При включённом параметре `autoCreate` существующая таблица может получить только эти отсутствующие
столбцы, допускающие значения NULL. Экспортёр сохраняет полную существующую схему, включая метаданные полей, и отправляет
условный PATCH, используя возвращённый etag. Параллельное изменение схемы приводит к сбою экспорта, а не к её перезаписи;
при следующем запуске таблица считывается заново.

При отключённом параметре `autoCreate` добавьте эти столбцы самостоятельно перед экспортом записей с данными об использовании.
Отсутствующие метаданные схемы/etag или неудачное обновление также предотвращают вставку записей с такими данными. Курсор экспорта
не продвигается при этом сбое, а данные об использовании никогда не отбрасываются без уведомления. Локальное хранение журналов
по-прежнему применяется, пока экспорт заблокирован, поэтому устраните сбой до истечения срока хранения исходных строк.
