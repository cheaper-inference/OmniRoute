Непрерывный инкрементальный экспорт журналов вызовов OmniRoute во внешнее аналитическое хранилище.

Вкладка панели управления Logs хранит историю запросов в SQLite (`call_logs`), объём которой ограничен
ротацией и политикой хранения. Экспорт журналов по расписанию отправляет тот же набор записей во внешнее хранилище, чтобы они могли храниться
дольше локальной базы данных и объединяться с другими данными. Первым целевым хранилищем является BigQuery;
конвейер реализован как реестр, поэтому дополнительные назначения можно добавлять независимо.

## 1. Как это работает

```
сервер (расшифровка и проверка конфигурации, сверка курсора)
  → запуск IPC → изолированный процесс ОС exportChild
    → storage.sqlite только для чтения → общий запрос/преобразование журнала вызовов
      → асинхронная загрузка артефактов → prepare()/send() назначения
        → пакет через IPC → сервер сохраняет курсор → подтверждение через IPC
          → следующий пакет; done через IPC → сервер регистрирует успех
```

- **Расписание** — одно cron-задание `JobRegistry`, `log_export`, по умолчанию запускаемое по
  расписанию `0 * * * *` (ежечасно, UTC). Регистрируется в `src/lib/initCloudSync.ts`;
  расписание можно переопределить с помощью `OMNIROUTE_LOG_EXPORT_CRON`. При каждом срабатывании
  последовательно обрабатываются все **включённые** назначения.
- **Курсор** — неявный `call_logs.rowid` SQLite, сохраняемый отдельно для каждого назначения в
  `log_export_destinations.cursor_row_id`. `timestamp` намеренно не используется как курсор:
  вызывающие стороны могут передавать собственное значение, поэтому медленный запрос может быть
  записан после более быстрого, запущенного позже, и курсор на основе метки времени пропустил бы его.
- **Пакетная обработка** — `batch_size` строк на запрос (по умолчанию 500),
  `max_rows_per_run` строк за один запуск (по умолчанию 10000), чтобы большая очередь
  обрабатывалась за несколько срабатываний, а не блокировала одно из них.
- **Доставка** — курсор продвигается только после успешного завершения `send()`. При сбое пакета
  курсор остаётся на прежнем месте, поэтому те же строки повторно отправляются при следующем
  запуске. Гарантируется доставка хотя бы один раз в сочетании с устранением дубликатов на стороне
  назначения, а не истинная доставка строго один раз: BigQuery назначает каждой строке ключ на
  основе идентификатора журнала вызовов и учитывает его по мере возможности в пределах собственного
  окна дедупликации.
- **Защита от одновременного запуска** — срабатывание cron и `POST .../run` могут произойти
  одновременно. Уже обрабатываемое назначение пропускается, а не обрабатывается дважды
  (`skipped: true` в результате запуска), поэтому параллельный запуск не может повторно отправить
  пакет или сдвинуть курсор назад.
- **Восстановление после очистки** — если `cursor_row_id` оказывается выше `MAX(rowid)` (вся
  таблица была очищена, а нумерация rowid началась заново), обработчик сбрасывает курсор на 0,
  а не теряет данные навсегда.

### Изолированный обработчик и ограничения

Каждый запуск назначения в Node выполняется в отдельном недолговечном дочернем процессе ОС
(`child_process` с IPC, а не `worker_threads`). Чтение тел, разбор/сериализация JSON полезной
нагрузки, `prepare()` назначения и сетевой ввод-вывод назначения выполняются в нём, а не в цикле
событий сервера. Через IPC передаются только конфигурация и небольшие сообщения о ходе выполнения;
экспортируемые записи никогда не возвращаются на сервер. Cron-задание и маршрут «Запустить сейчас»
сохраняют прежний общедоступный результат и защиту от одновременного запуска.

Дочерний процесс открывает разрешённый сервером файл `DATA_DIR/storage.sqlite` только для чтения
с помощью `node:sqlite`, с `busy_timeout=5000` и `query_only=ON`. Он не импортирует общий экземпляр
БД и не выполняет миграции, резервное копирование или обновления SQLite. Учёт отсутствующих или
повреждённых артефактов (включая UPDATE для повреждённого артефакта) остаётся только в пути
просмотра подробностей на панели управления. Оба пути используют общий чистый обработчик
подробностей; при экспорте применяются асинхронное чтение файловой системы и тот же порядок
разрешения: артефакт → устаревшие встроенные данные → устаревшие данные на диске → отсутствие
данных. При открытии дочерним процессом средства чтения запуск фиксирует максимальный rowid
вставки; более поздние вставки ожидают следующего запуска. Это граница вставки, а не
долговременная транзакция SQLite: процессы записи WAL и контрольные точки могут свободно
выполняться во время ожидания сети. Обновления и удаления существующих строк этой границей
не фиксируются.

После каждого принятого пакета дочерний процесс ожидает подтверждения. Сервер сначала сохраняет
курсор с помощью `advanceLogExportCursor`, а затем отправляет `ack`; обработка следующего пакета
не начинается до его получения. Сбой отправки, аварийное завершение или истечение времени ожидания
регистрируется как ошибка без продвижения курсора для этого пакета. Ранее подтверждённые пакеты
остаются зафиксированными; повторно может быть отправлен не более чем один неподтверждённый пакет.
Успех регистрируется только после `done` и штатного завершения дочернего процесса. При сбоях
дочерний процесс завершается сигналом SIGTERM, а через 500 мс — сигналом SIGKILL, если это
необходимо; обработчик ожидает закрытия процесса.

| Переменная окружения                          | По умолчанию | Назначение                                        |
| --------------------------------------------- | ------------ | ------------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | Ограничение времени назначения по настенным часам |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | Лимит old-space V8 дочернего процесса в МБ        |

Для недопустимых, неположительных или нецелых значений используются значения по умолчанию.
Настройка кучи не является ограничением общего RSS; очень большие пакеты всё равно могут исчерпать
память дочернего процесса и привести к безопасному завершению запуска с ошибкой. Значение по
умолчанию 1024 МБ оставляет запас для стандартного пакета из 500 строк с артефактами размером
512 КиБ и включёнными телами, включая побайтовую пакетную сериализацию JSON в BigQuery. Оно не
делает безопасным пакет из 10000 строк с телами. Исчерпание кучи V8 регистрируется как ошибка
с рекомендацией по устранению: уменьшите размер пакета или увеличьте
`OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; курсор останется на последнем подтверждённом пакете.
Для исторических встроенных тел и тел на диске современное ограничение размера артефактов
не действует. Операторы должны отдельно планировать использование RSS, особенно в контейнерах
с ограниченной памятью.

Дочерний процесс наследует только разрешённый `DATA_DIR`, `NODE_ENV`, явно заданный `TZ`
(разрешение локального времени для устаревших имён файлов), `ELECTRON_RUN_AS_NODE`, если он
присутствует, и следующие входные параметры исходящих подключений: `HTTP_PROXY`, `HTTPS_PROXY`,
`ALL_PROXY`, `NO_PROXY` (и их варианты в нижнем регистре),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
Глобальный диспетчер Undici использует общие с сервером чистую обработку прокси из переменных
окружения и правила обхода прокси для локальных хостов, включая `NO_PROXY`; он не импортирует
`proxyFetch.ts` или связанные с ним БД и флаги функций. Учётные данные прокси скрываются в
перенаправляемом выводе и регистрируемых ошибках. Учётные данные назначения передаются только
в одном стартовом сообщении IPC и никогда — через argv или окружение; перенаправляемые вывод
и ошибки снабжаются префиксом и очищаются от конфиденциальных данных. В аргументах запуска
дочернего процесса отключено только предупреждение `ExperimentalWarning`, чтобы при каждом
запуске cron не повторялось предупреждение Node о SQLite; предупреждения других типов остаются
видимыми.

Модули назначения должны быть импортируемыми без зависимостей от Next.js или зависимостей, доступных только на сервере. Существующая реализация BigQuery уже соответствует этому требованию. Кеши токенов доступа существуют только в течение дочернего запуска, а не между запусками. Поддерживаемой средой выполнения является Node (`package.json` engines), однако раздел README об установке Bun и `Dockerfile.bun` также заявляют о совместимом с production-средой варианте с использованием `bun:sqlite` (`src/lib/db/core.ts` / адаптеры). Поэтому при использовании Bun экспорт сохраняет прежний внутрипроцессный путь и однократно выводит предупреждение: изоляция дочерней кучи и тайм-аутов недоступна. Используйте Node для изоляции цикла событий и OOM; Bun здесь не рассматривается как среда исключительно для разработки.

Когда включён параметр `includeBodies`, рекомендуется расписание с интервалом в несколько минут, например
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`, вместо накопления очереди полезной нагрузки за час.
Ограничения на пакеты и строки по-прежнему ограничивают каждый запуск. Затраты на запуск процесса возникают для каждого назначения при каждом запуске;
это обменивает небольшие затраты на запуск на изоляцию серверного цикла событий, а не на снижение общего использования CPU.

### Полезные нагрузки (промпты и ответы)

По умолчанию экспорт содержит только сводные поля, отображаемые в **списке** журналов. Включение
параметра **Экспортировать промпты и ответы** (`includeBodies`) дополнительно отправляет то, что отображается на панели **подробностей**
журналов для каждого вызова:

| Поле                             | Содержимое                                                                                    |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| `request_body` / `response_body` | Полезные нагрузки вызова в том виде, как их отображает панель управления                      |
| `pipeline_route_decision`        | Цель и модель, выбранные маршрутизатором                                                      |
| `pipeline_client_request`        | Исходный запрос в точности в том виде, как его отправил клиент                                |
| `pipeline_openai_request`        | Запрос после преобразования во внутренний формат OpenAI                                       |
| `pipeline_provider_request`      | Запрос в том виде, как он фактически отправлен вышестоящему провайдеру, в диалекте провайдера |
| `pipeline_provider_response`     | Необработанный ответ вышестоящего провайдера                                                  |
| `pipeline_client_response`       | Ответ, возвращённый вызывающей стороне                                                        |
| `pipeline_error`                 | Подробности ошибки на уровне конвейера для неудачного вызова                                  |
| `bodies_truncated`               | Истинно, если какое-либо из указанных выше полей достигло `maxBodyBytes`                      |

Это содержимое промптов, поэтому оно **по умолчанию отключено** и намеренно настраивается отдельно для каждого назначения.
Отправляется то, что отображается на панели управления, поскольку экспорт и `getCallLogById` используют общий механизм
получения подробностей: полезные нагрузки
уже очищены от PII и секретных данных при записи, а вызов, выполненный с API-ключом
`noLog`, вообще не сохраняет полезную нагрузку, поэтому экспортировать нечего.

Полезные нагрузки считываются для каждой строки из артефакта файловой системы, поэтому гидратация выполняется только для назначений,
которые её запросили. При отсутствии или повреждении артефакта экспортируется его сводка с нулевыми значениями полезной нагрузки,
а пакет не завершается с ошибкой и курсор не блокируется.

`maxBodyBytes` (по умолчанию 262144) ограничивает размер каждого поля. Более длинные полезные нагрузки **обрезаются, а не
отбрасываются** — обрезанный промпт всё равно позволяет понять, «что было запрошено», — и строка помечается полем
`bodies_truncated`. Потоковые дельты, поступающие по частям, не экспортируются; собранный ответ уже содержится
в `pipeline_provider_response` и `pipeline_client_response`.

## 3. REST API

Все маршруты требуют аутентификации управления (`requireManagementAuth`). Секреты никогда не возвращаются:
сохранённый секрет возвращается как литерал `__stored__`, а отправка этого значения обратно при обновлении
сохраняет существующие учётные данные.

Для создания или обновления назначения, тип которого объявляет секрет, **требуется
`STORAGE_ENCRYPTION_KEY`**. Без него `encrypt()` незаметно пропускает данные без изменений, поэтому операция записи
отклоняется с кодом 400, чтобы учётные данные не попали в SQLite в виде открытого текста (та же проверка
применяется вебхуком Telegram).

| Метод    | Путь                                     | Назначение                                                              |
| -------- | ---------------------------------------- | ----------------------------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | Типы назначений и списки их полей конфигурации                          |
| `GET`    | `/api/log-export/destinations`           | Список назначений (секреты скрыты)                                      |
| `POST`   | `/api/log-export/destinations`           | Создать назначение                                                      |
| `GET`    | `/api/log-export/destinations/{id}`      | Получить одно назначение                                                |
| `PUT`    | `/api/log-export/destinations/{id}`      | Обновить имя / состояние / конфигурацию / пакетирование                 |
| `DELETE` | `/api/log-export/destinations/{id}`      | Удалить                                                                 |
| `POST`   | `/api/log-export/destinations/{id}/test` | Проверить учётные данные без записи                                     |
| `POST`   | `/api/log-export/destinations/{id}/run`  | Выполнить выгрузку сейчас тем же способом, что и запланированный запуск |
| `GET`    | `/api/log-export/status`                 | Состояние cron, последние запуски, очередь для каждой цели              |

Именно `GET /api/log-export/types` делает пользовательский интерфейс универсальным: форма панели управления создаётся на основе
возвращённых описателей полей, поэтому добавление нового назначения не требует изменения пользовательского интерфейса.

## 4. Назначение BigQuery

Ключи конфигурации (`type: "bigquery"`):

| Ключ                 | Примечания                                                                          |
| -------------------- | ----------------------------------------------------------------------------------- |
| `projectId`          | Проект GCP, содержащий набор данных                                                 |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                     |
| `tableId`            | `[A-Za-z0-9_]+`                                                                     |
| `location`           | Используется только при необходимости создать набор данных (по умолчанию `EU`)      |
| `serviceAccountJson` | Ключ сервисного аккаунта. Секрет: зашифрован при хранении и никогда не возвращается |
| `autoCreate`         | Создать набор данных и таблицу при первом экспорте (по умолчанию `true`)            |

Сервисному аккаунту требуется разрешение `bigquery.tables.updateData` для целевой таблицы, а также
`bigquery.datasets.create` / `bigquery.tables.create`, если включён `autoCreate`.

Настроенный пакет является единицей **курсора**, а не HTTP: `send()` разбивает его на вызовы insertAll
не более чем по 500 строк, поэтому большой `batch_size` не может привести к превышению ограничения BigQuery в 10 МБ на запрос.
При временных статусах (408/429/500/502/503/504) выполняется до трёх повторных попыток с экспоненциальной
задержкой и повторным использованием тех же insertIds; ошибки аутентификации и схемы приводят к исключению при первой попытке,
а не расходуют время запуска.

Таблица, созданная несколько мгновений назад, ещё не видна потоковой конечной точке, которая отвечает
кодом 404 в течение нескольких секунд. Такой ответ 404 приводит к повторным попыткам, но **только если таблица была создана во время этого запуска** —
если таблица действительно отсутствует, операция сразу завершается ошибкой. Обратите внимание: повторное создание таблицы с именем недавно
удалённой таблицы приводит к тому, что BigQuery в течение нескольких минут отклоняет потоковые вставки; это
особенность удаления с последующим повторным созданием, поэтому вместо удаления и повторного добавления таблицы лучше использовать новое имя.

**Частичная ошибка возвращается как HTTP 200 с непустым массивом `insertErrors[]`.** Это рассматривается как
ошибка и приводит к исключению, благодаря чему курсор не продвигается дальше строк, которые BigQuery не
принял; такое поведение закреплено тестом `tests/unit/log-export-bigquery.test.ts`.

Для передачи используется обычный REST: самоподписанное утверждение RS256 обменивается на токен доступа по адресу
`https://oauth2.googleapis.com/token`, после чего строки отправляются в `tabledata.insertAll`. Google SDK
не подключается. Токены доступа кешируются внутри процесса для каждой пары (сервисный аккаунт, область доступа).

Созданная таблица содержит по одному столбцу для каждого поля вкладки Logs, а также `exported_at`, и организована
с учётом того, как фактически выполняются запросы к журналам вызовов:

- **Разбиение по дням на основе `timestamp`**, поэтому запрос с ограничением по дате сканирует только соответствующие дни.
- **Кластеризация по `api_key_name`, `provider`, `model`, `status`** (в указанном порядке), поэтому фильтрация по
  тому, кто выполнил вызов, куда он был направлен или завершился ли он ошибкой, исключает блоки внутри каждого раздела. BigQuery
  допускает не более четырёх столбцов кластеризации, и их порядок важен: фильтр только по `api_key_name`
  исключает блоки, а фильтр только по `status` — нет.
- **Необязательный срок хранения разделов** через `partitionExpirationDays` (0 сохраняет всё), применяемый
  при создании таблицы.

Обе настройки применяются при создании. Существующая таблица сохраняет уже имеющуюся структуру, поэтому,
если вы хотите применить их, укажите в качестве назначения новый идентификатор таблицы.

`tests/unit/log-export-bigquery.test.ts` проверяет, что маппер и схема таблицы остаются
синхронизированными, поэтому новый столбец журнала вызовов не может быть незаметно отброшен при экспорте.

Пакеты разбиваются на части с учётом **как** количества строк, **так и** объёма сериализованных данных в байтах. Одного количества строк недостаточно,
когда экспортируются полезные нагрузки: 500 строк с промптами могут занимать десятки мегабайт, а insertAll
отклоняет запросы размером более 10 МБ. Часть закрывается при достижении 500 строк или 9 МБ — в зависимости от того, что произойдёт раньше.

## 5. Назначение экспорта трассировок OTLP/HTTP

В конфигурации используется `type: "otlp-http"`. Это выполняемый по расписанию экспорт сохранённых
журналов вызовов с отслеживанием позиции курсором, а не приёмник событий маршрутизации в реальном
времени с доставкой по возможности из
`open-sse/services/routing/otel.ts`. Он не читает и не изменяет переменные окружения,
таймеры или буферы этого приёмника. При включении обоих механизмов могут создаваться два независимых вида спанов;
используйте область инструментирования `omniroute.log-export`, чтобы отличать эти спаны журналов вызовов.

| Ключ                     | Значение по умолчанию / назначение                                                                          |
| ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `endpoint`               | Обязательный полный HTTP(S) URL трассировок; суффикс `/v1/traces` не добавляется                            |
| `headers`                | Необязательные строки `Name: value` или JSON-объект со строковыми значениями; хранятся в зашифрованном виде |
| `requestHeaderAllowlist` | Пусто (выключено); имена/префиксы клиентских заголовков для записи в атрибуты спана                         |
| `serviceName`            | `omniroute`; атрибут ресурса `service.name`                                                                 |
| `langfuseMapping`        | `false`; добавляет атрибуты генерации/сессии/пользователя Langfuse                                          |
| `identity`               | `pseudonymous`, `keyName` или `none`                                                                        |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                                     |
| `timeoutMs`              | `30000` на каждую HTTP-попытку                                                                              |
| `environment`            | Не задано; необязательный атрибут `langfuse.environment`                                                    |

Эти поля отображаются в общей панели управления. `paths` принимает массив через API или содержимое текстового поля
с точными путями, разделёнными переводами строк/запятыми. Пути для эмбеддингов, переранжирования и других операций
пропускаются, если они не разрешены явно. Пропущенные строки всё равно продвигают курсор; существующие
счётчики исполнителя `exported`/`exportedTotal` учитывают обработанные исходные строки, включая отфильтрованные,
а не принятые спаны. Фильтрация выполняется в дочернем процессе без изменения его
контракта IPC/курсора.

Для проверки URL используется вспомогательная функция `parseAndValidateNonMetadataUrl` из
`src/shared/network/outboundUrlGuard.ts`, не требующая БД: политика `block-metadata`. Она выполняет те же
безусловные проверки адресов метаданных, протоколов и встроенных учётных данных, что и валидатор вебхуков
с разрешёнными частными URL, но намеренно разрешает адреса localhost/LAN без глобального
переопределения флагом функции. Это позволяет использовать самостоятельно размещённые конечные точки Langfuse, Phoenix, Tempo и Collector,
включая частные HTTP-конечные точки. Хосты облачных метаданных всегда блокируются.
Перенаправления не выполняются, поэтому коллектор не может перенаправить учётные данные на другой хост.
Как и существующий механизм лексической проверки URL, эта проверка не фиксирует результат разрешения DNS; настраивайте
только хосты, контролируемые оператором. Отдавайте предпочтение HTTPS, если конечная точка находится вне доверенной сети.

### Полезная нагрузка и доставка

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) содержит один
спан CLIENT на каждую разрешённую строку; имя спана точно совпадает с путём запроса. Именование по пути позволяет различать
Chat Completions, Responses и Messages, не включая сведения о модели или идентификации в
имя спана. Атрибуты ресурса включают `service.name` и `service.version` пакета.

Обычный механизм журналирования попыток чата (`open-sse/handlers/chatCore/attemptLogging.ts`) записывает
`duration = Date.now() - startTime` при завершении и не передаёт временную метку;
`saveCallLogOperation` в `src/lib/usage/callLogs.ts` по умолчанию задаёт временную метку как время записи
(завершения). Поэтому при экспорте конец задаётся временной меткой строки, а начало — как конец минус длительность
(миллисекунды, преобразованные в десятичные наносекунды). Переданные вызывающей стороной исторические временные метки
также сохраняются как время окончания; отдельного признака начала/завершения для каждой строки нет.
Длительность null преобразуется в ноль. Недопустимые или отсутствующие временные метки приводят к сбою пакета, а не к созданию
недетерминированных спанов. `ttftMs` допускает null и сопоставляется с `omniroute.ttft_ms`.

Атрибуты включают `gen_ai.operation.name="chat"`, провайдера, запрошенную модель и модель ответа,
входные/выходные токены, необязательные токены чтения кэша/создания кэша/рассуждений, HTTP-статус,
комбинацию, источник кэша, тег сессии и идентификатор корреляции. Целочисленные значения OTLP и временные метки
представляются десятичными строками; строки, логические значения и дробные числа используют соответствующие им варианты значений
OTLP. Спаны ошибок имеют статус ERROR и очищенное сообщение статуса. Каноническая
запись не содержит URL вышестоящего хоста, поэтому `server.address` опускается, чтобы не указывать
коллектор в качестве сервера модели. Стоимость не экспортируется.

Только `includeBodies=true` подгружает содержимое. При `langfuseMapping=false`
`gen_ai.input.messages` / `gen_ai.output.messages` содержат очищенный JSON тела запроса/ответа
в том виде, в котором он хранится в OmniRoute (канонизированный, если его можно разобрать), а не преобразованный массив
сообщений по семантическим соглашениям. Усечённые тела и тела не в формате JSON остаются обычным текстом. При `langfuseMapping=true`
тела передаются только в `langfuse.observation.input` / `langfuse.observation.output`;
атрибуты `gen_ai.*.messages` опускаются, поэтому каждое тело отправляется один раз. Оба режима
наследуют `maxBodyBytes` из существующего механизма подгрузки;
`omniroute.bodies_truncated=true` обозначает усечение.
Это назначение не добавляет дополнительных снимков конвейера или чтения неочищенных артефактов;
необязательный захват заголовков запросов использует существующий подгруженный снимок клиента, описанный ниже.
При экспорте тел используйте расписание с интервалом в несколько минут, например `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`,
вместо накопления часовой очереди.

### Необязательные заголовки клиентских запросов

Захват заголовков **по умолчанию выключен**. Задайте `requestHeaderAllowlist` в конфигурации назначения
и включите **Экспорт промптов и ответов** (`includeBodies: true` в назначении).
Список разрешений принимает массив через API или содержимое текстового поля с именами, разделёнными переводами строк/запятыми:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

Имена сопоставляются целиком без учёта регистра, если только единственный завершающий `*` не задаёт непустой
префикс имени заголовка. Отдельный `*`, встроенные подстановочные символы и недопустимые имена HTTP-заголовков отклоняются.
Допускается не более 64 селекторов, каждый с именем или префиксом длиной не более 256 байт ASCII.
Эта настройка не связана с `headers`, который используется для аутентификации экспортера в коллекторе.

При захвате читается только `pipeline_client_request`, заполняемый из
`clientRawRequest` (или устаревшего `clientRequest`) сохранённого подробного конвейера. Заголовки запроса к провайдеру никогда не используются как запасной источник.
Подробное журналирование конвейера должно быть включено на момент записи запроса. Если
`includeBodies` отключён либо JSON-снимок клиента отсутствует, повреждён или усечён, атрибуты
заголовков не формируются. Увеличение `maxBodyBytes` позволяет избежать усечения снимка при экспорте;
оно не может восстановить данные, которые не были сохранены. Снимок размером более 1 МиБ или содержащий более
256 записей заголовков игнорируется. Существующий экспорт запросов и ответов остаётся включённым наряду
с захватом заголовков; список разрешённых заголовков не предоставляет режима загрузки только заголовков.

Выбранные значения становятся массивами строк OTLP `http.request.header.<full lowercase header name>`,
даже если значение — одна строка. Например, `X-OmniRoute-Meta-Team: example-team` преобразуется в
`http.request.header.x-omniroute-meta-team` со значением
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
Полный префикс сохраняется: это обычные заголовки, без разбора бизнес-полей или
преобразования в метаданные `omniroute.metadata.*` / Langfuse. `langfuseMapping` не меняет семантику
заголовков. Выбранный заголовок `User-Agent` с одним значением также задаёт стандартный скалярный атрибут
`user_agent.original`. Запятые внутри одного значения не приводят к его разделению. Варианты с разным регистром объединяются в порядке
сохранённых записей; любой недопустимый вариант приводит к исключению всего заголовка. Атрибуты упорядочиваются по имени в нижнем регистре.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, заголовки API-ключей, имена, содержащие
маркеры auth/token/secret/password/credential, и внутренние учётные данные шлюза всегда
исключаются, даже если они выбраны или частично замаскированы в хранилище. Для известных шаблонов учётных данных используется
общий детектор учётных данных; маркеры скрытия исключаются, а не экспортируются как безопасные значения.
Принимаются только строки и непустые массивы строк; числа и объекты не преобразуются.
Недопустимые имена, ключи прототипа, управляющие символы (кроме горизонтальной табуляции) и некорректный Unicode
игнорируются без сбоя пакета и без включения их содержимого в сообщения об ошибках.

Каждый спан захватывает не более 32 заголовков, 16 значений на заголовок, 4096 байт UTF-8 на значение
и суммарно 16384 байт UTF-8 для имён и значений захваченных заголовков. Слишком большие или недопустимые заголовки
исключаются целиком, а не усекаются. Выбор заголовков — решение оператора в отношении конфиденциальности: даже безопасные на вид имена
могут содержать персональные данные, а эти ограничения и детекторы не являются универсальным средством очистки персональных данных.

### Ограничения доставки

Запросы ограничены 500 спанами и 4 МиБ JSON в UTF-8, включая оболочку.
Размер каждого разрешённого спана проверяется до первого запроса пакета курсора. Если отдельный
спан превышает лимит, ни одна часть этого пакета не отправляется, а операция завершается ошибкой с рекомендацией уменьшить
`maxBodyBytes`; спан не отбрасывается без уведомления. Предварительная проверка сохраняет только ссылки на записи и
количество байт, удаляя каждый временный спан и JSON; спаны заново создаются для порций ограниченного размера,
вместо хранения второй сериализованной копии пакета. При HTTP 408/429/5xx, сетевых сбоях и тайм-аутах выполняется не более
трёх попыток с экспоненциальной задержкой 250/500 мс. `Retry-After` в секундах или в формате HTTP-даты
может увеличить задержку до 5 секунд. Остальные статусы приводят к немедленному сбою. Частичное отклонение OTLP при статусе 2xx также вызывает исключение вместо
подтверждения потерянного спана; принимаются пустые подтверждения или подтверждения с корректным JSON,
при этом чтение ответа ограничено 64 КиБ.

Ошибки содержат только сведения, которыми располагает сам экспортер: HTTP-статус, категорию повторной попытки, число попыток и отправленных
спанов либо фиксированные формулировки о сбое подтверждения или сети. Тела ответов коллектора,
счётчики частичного успеха и заголовки ответов никогда не копируются в ошибки, журналы или на
панель мониторинга. Сбойный или частично принятый пакет не подтверждается: для назначения отображается
состояние сбоя с соответствующим статусом, курсор остаётся на последнем подтверждённом пакете, а следующий запуск
повторно отправляет те же строки. Постоянные статусы ошибки продолжают вызывать сбой, пока не будет исправлен коллектор или
конфигурация. Подробности ответа смотрите в собственных журналах коллектора. Для сводок ошибок журнала вызовов сохраняется
отдельный механизм скрытия конфиденциальных данных.
`prepare()` ничего не создаёт; проверка отправляет POST-запрос с содержимым ровно `{"resourceSpans":[]}` и сообщает
HTTP-статус, не записывая спаны журнала вызовов.

Идентификаторы трассировок и спанов — это первые 32/16 шестнадцатеричных цифр SHA-256 от
`"omniroute.trace\0" + callLogId` и `"omniroute.span\0" + callLogId`. Повторные отправки содержат
те же идентификаторы. Это не гарантирует дедупликацию: некоторые серверные системы, включая приём данных Langfuse
v4, не устраняют дубликаты спанов с одинаковыми идентификаторами. Аварийное завершение или сбой части пакета может
привести к повторной отправке не более одного неподтверждённого пакета курсора; дублироваться может весь этот пакет,
а не только его последняя HTTP-порция. Учитывайте этот компромисс при выборе размера пакета курсора.

### Пример для Langfuse

Настройте следующие поля для самостоятельно размещённого экземпляра Langfuse:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Сформируйте значение Authorization локально, закодировав в Base64 буквальную строку `public-key:secret-key`
(например, с помощью `Buffer.from(publicKey + ":" + secretKey).toString("base64")`).
Не вставляйте реальные учётные данные в журналы, снимки экрана или сообщения о проблемах. Сопоставление автоматически
задаёт `x-langfuse-ingestion-version: 4`; Authorization по-прежнему передаётся через `headers`.
И заголовки, и сгенерированная соль идентификации используют существующий механизм шифрования секретных
полей и значения-заполнители API; требуется `STORAGE_ENCRYPTION_KEY`.

Сопоставление добавляет тип/модель генерации, сведения об использовании в JSON (входные/выходные/общие значения и доступные
ключи кэша), снимки входных/выходных данных в JSON, уровень ERROR/DEFAULT, очищенное сообщение о статусе,
имя трассировки, идентификатор сессии, необязательное окружение и доступные для фильтрации
`langfuse.observation.metadata.<key>` для провайдера, запрошенной модели, пути, комбинации, источника
кэша и статуса. `langfuse.observation.completion_start_time` задаётся в формате ISO 8601 как
время начала + TTFT, только если TTFT известно и укладывается в длительность. Атрибуты стоимости не отправляются.

Режимы идентификации применяются к `langfuse.user.id`:

- `pseudonymous` (по умолчанию): HMAC-SHA256 от внутреннего идентификатора API-ключа со случайной
  32-байтовой солью для каждого назначения. Если соль отсутствует, она генерируется при создании, шифруется
  как `identitySalt`, никогда не возвращается и сохраняется при редактировании. Исходные идентификаторы ключей никогда не
  помещаются в атрибуты спанов. Повторное создание или ротация соли назначения изменяет идентификаторы пользователей.
- `keyName`: настроенное имя API-ключа, намеренно раскрывающее эту метку, заданную оператором.
- `none`: без идентификатора пользователя. Теги сессии по-прежнему экспортируются, если они есть; эти режимы не
  анонимизируют произвольное содержимое промптов или заданные оператором метки сессий/корреляции.

### Запуск без загрузки исторических данных

Только при создании включите **Начать с текущей позиции (пропустить существующие журналы)** или передайте
`startFromCurrentPosition: true` на верхнем уровне тела запроса API создания. Это инициализирует
`cursor_row_id` текущим максимальным rowid среди сохранённых строк журнала вызовов с помощью существующих вспомогательных функций
для курсора, без миграции. По умолчанию используется false (курсор 0 и загрузка сохранённой истории).
Это не настройка сброса курсора при обновлении.

Общее дополнение `ttftMs` также добавляет допускающий NULL столбец `ttft_ms` в средство сопоставления BigQuery
и схему новых таблиц: тест схемы требует, чтобы каждому полю канонической записи соответствовал
столбец. Экспорт в существующие таблицы продолжается без изменений: `prepare()` считывает схему таблицы и
исключает только `ttft_ms`, если этот столбец отсутствует. Добавьте допускающий NULL столбец INT64, чтобы получить TTFT
при следующем запуске, или используйте новую таблицу. PATCH, автоматическое изменение схемы и дополнительные
разрешения не требуются; для всех остальных полей строк сохраняется строгая проверка схемы.

## 6. Добавление места назначения

1. Создайте `src/lib/logExport/destinations/<name>.ts`, экспортирующий `LogExportDestinationType`:
   Zod-схему `configSchema`, массив дескрипторов `fields` для пользовательского интерфейса, `secretFields` и
   `createClient(config)`, возвращающий `test()` / `prepare()` / `send(records)`.
2. Добавьте его в массив `DESTINATIONS` в `src/lib/logExport/registry.ts`.
3. Напишите тесты в `tests/unit/`.

Это всё необходимое изменение: хранилище, задание cron, REST-слой, шифрование секретов и
форма панели управления используют реестр.

Два правила для нового места назначения:

- `send()` **обязан выбрасывать исключение** при частичном сбое. Успешное завершение означает: «в месте назначения есть эти строки»,
  после чего курсор навсегда перемещается за них.
- Место назначения, принимающее предоставленный пользователем URL, перед выполнением запроса должно проверить его с помощью
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`),
  как это делают вебхуки. Для BigQuery это не требуется: его хосты заданы константами.

## 7. Эксплуатация

- **Панель управления**: Интеграции → Экспорт журналов. Добавьте место назначения, запустите **Тест**, чтобы проверить учётные данные
  без записи строк, а затем включите его.
- **Очередь необработанных данных**: на каждой карточке места назначения отображаются количество ожидающих строк и курсор; `GET
/api/log-export/status` возвращает те же показатели, а также данные о последних 20 запусках задания.
- **Сбой одного места назначения не приводит к сбою остальных** — сводка запуска записывает статус каждого места назначения
  в `last_status` / `last_error`, а журнал запусков задания сохраняет сводные данные.
- **При удалении места назначения удаляется его курсор.** При повторном добавлении обработка начинается с самого старого сохранённого
  журнала вызовов, из-за чего строки, которые уже могут находиться в месте назначения, отправляются повторно. В BigQuery значение
  `insertId` каждой строки устраняет такие дубликаты только в пределах собственного окна дедупликации BigQuery, поэтому
  предпочтительнее отключить место назначения, а не удалять его.
