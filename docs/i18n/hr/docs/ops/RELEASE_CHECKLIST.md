## npm Trusted Publishing (zadano od v3.8.51) — pripremljeno na zahtjev, izravno kao pričuvna opcija

`npm-publish.yml` prema zadanim postavkama objavljuje putem **npm Trusted Publishing (OIDC)**: posao
`stage-npm` (koji se izvodi na GitHubovu hostiranom izvršitelju) razmjenjuje GitHubov id-token za kratkotrajnu npm
vjerodajnicu za to pokretanje — bez dugotrajnog npm tokena u tajnama repozitorija, bez upita za 2FA, uz priložen dokaz o podrijetlu.
To je zaobilazni mehanizam koji npm sada odobrava jer se tokeni koji preskaču 2FA povlače iz upotrebe;
njime se vraća potpuno automatski tijek koji je projekt imao do v3.8.48, uz zadržavanje
jamstva WS1.3 (procurjeli token ne može samostalno objavljivati — token ne postoji).

**Jednokratno postavljanje (vlasnik):** npmjs.com → paket `omniroute` → Settings → _Trusted
Publisher_ → GitHub: vlasnik `diegosouzapw`, repozitorij `OmniRoute`, tijek rada `npm-publish.yml`
(okruženje: nijedno). Dok to ne postoji, automatski korak ne uspijeva uz `ENEEDAUTH`:
ponovno ga pokrenite s `publish_mode=staged` (u nastavku) ili `direct`.

### Pripremljeno objavljivanje (na zahtjev — `publish_mode=staged`)

Tijek rada npm-publish više ne objavljuje izravno: pokreće zapakiranu tarball arhivu
(`check:pack-boot`), a zatim izvršava `npm stage publish` — točno ti bajtovi smještaju se u
registar, ali ih **nije moguće instalirati** dok ih vlasnik ne odobri. Ljudska 2FA provjera premještena je
NAKON dokaza, a ne prije njega.

**Tijek za vlasnika nakon što tijek rada postane zelen:**

1. `npm stage list omniroute` — pronađite ID pripremljenog izdanja (ispisuje se i u sažetku tijeka rada).
2. Provjerite pripremljene bajtove (preporučeno): `npm stage download <id>`, zatim instalirajte
   preuzetu tarball arhivu u privremeni prefiks i pokrenite je (`npm run check:pack-boot` automatizira
   istu provjeru paketiranja→instaliranja→pokretanja u CI-ju).
3. `npm stage approve <id>` — 2FA upit JEST objavljivanje. `npm stage reject <id>` odbacuje pripremljeno izdanje.
4. Zaštitna provjera nakon objavljivanja: provjeravatelj nakon objavljivanja (WS1.4 iz plana za v3.8.49) instalira
   objavljenu verziju iz javnog registra u čistom spremniku i pokreće je.

**Pričuvna opcija za hitne slučajeve:** `workflow_dispatch` s `publish_mode=direct` vraća
naslijeđeni neposredni `npm publish` (upotrijebite samo ako priprema ne funkcionira ispravno; zabilježite razlog).

**Jednokratno sigurnosno ojačavanje (vlasnik, npmjs.com):** konfigurirajte Trusted Publisher za
`omniroute` u načinu rada samo s pripremom kako procurjeli dugotrajni token ne bi mogao izvršiti `npm publish`
izravno niotkuda — CI može samo pripremiti izdanje; objaviti ga može samo vlasnik putem 2FA.

**Postupak za neispravne artefakte (nepromijenjen):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
kao zadana reakcija (traje nekoliko minuta, povratno je); `npm unpublish` samo unutar razdoblja od 72 sata i ako nema ovisnih paketa
te nikada kao prvi potez. Docker: nikada nemojte ponovno zapisivati oznaku verzije — vraćanje je
preusmjeravanje oznake `latest` na posljednji ispravan sažetak.

**Docker Hub `latest` (obavezno pri svakom stabilnom SemVer objavljivanju):** tijek rada
`docker-publish` mora označiti **i** `X.Y.Z` **i**, kada
`should-promote-latest.sh` potvrdi da je to najviši stabilni SemVer, `:latest`
s **istim sažetkom**. Nakon posla: sažetak oznake `latest` na Hubu mora biti jednak sažetku novog
SemVer izdanja, a `last_updated` mora biti ažuriran. Nemojte ostaviti `:latest` na starijoj
izgradnji dok bilješke o izdanju govore o ispravcima koji postoje samo u gitu. Compose
primjeri za brzi početak koriste `:latest`; GitOps bi trebao nastaviti prikvačivati `X.Y.Z`. Pogledajte
[Kanali Docker izdanja](../guides/DOCKER_GUIDE.md#release-channels) i #10317.

## Ubrzana staza za hitne ispravke (oznaka `hotfix`)

PR s oznakom `hotfix` preskače opsežnu CI matricu (E2E s 9 segmenata, prag
pokrivenosti, quality-gate, quality-extended) i zadržava brze provjere s jakim signalom: izgradnju,
segmente jediničnih testova, integracijske testove, vitest, lint/provjeru tipova, docs-sync, `check:pack-artifact`
i provjeru pokretanja iz tarballa (`check:pack-boot`). Cilj: zelen status za ≤15 min umjesto ~33 min.

**Pravila ulaska — sva četiri uvjeta su obvezna (po uzoru na hitne staze projekata Chromium/VS Code/Node):**

1. **Ozbiljnost**: produkcija ne radi — objavljeni artefakt ruši se pri pokretanju /
   sigurnosna ispravka / pogođen je svaki korisnik izdanja. „Važno” ne znači „ne radi”.
2. **Ovlaštenje**: samo vlasnik repozitorija primjenjuje oznaku `hotfix`. Oznaka JEST
   odobrenje — nikad je nemojte samostalno primijeniti na PR kampanje.
3. **Dokazi**: tijelo PR-a sadrži poveznicu na prethodno potpuno zeleno opsežno izvođenje (skup testova
   koji bi preskočeni poslovi ponovno provjerili) te test same ispravke koji prvo ne prolazi, a zatim prolazi.
4. **Opseg**: isključivo cherry-pick — minimalna ispravka, bez refaktoriranja i usputnih promjena.

Preskočena površina pokrivenosti/pragova ponovno se provjerava pri sljedećem potpunom izvođenju na
grani izdanja (kontinuirano zeleno izdanje) — staza preskače ČEKANJE, nikad provjeru valjanosti.
Promjene samo u testovima (sve datoteke pod `tests/`, nijedna pod `tests/e2e/`) automatski preskaču E2E
matricu, bez ikakve oznake.

### Build Layout

Repozitorij koristi tri različita izlazna direktorija — nikad ih nemojte miješati:

| Imenik    | Svrha                                                             | Pratili?        |
| --------- | ----------------------------------------------------------------- | --------------- |
| `src/`    | Izvor aplikacije (TypeScript / TSX)                               | Da              |
| `.build/` | Izgradi međuprodukte — `next build` izlaz (`distDir`)             | Ne (ignorirano) |
| `dist/`   | Npm paket koji se može isporučiti — sastavio `assembleStandalone` | Ne (ignorirano) |

> **Napomena operatera:** direktorij udaljene VPS slike ostaje `/usr/lib/node_modules/omniroute/app/`. Samo** in-repo** izlaz izlaza izgradnje premješten (`app/` → `dist/`). Sadržaj rsync `dist/` vještina implementacije u udaljeni `app/` dir — nisu potrebne promjene VPS putanje.

**Tijek jedne građevine:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Pokrenite NOT `npm run build` nakon čega slijedi zasebni `npm run build:cli` za implementaciju — koristite `npm run build:release` koji radi čistu ponovnu izgradnju + sentinel u jednoj naredbi.

### Provjera artefakta

## Izdvajanje izdanja 3.9.0 LTS (uvježbano u 3.8.58)

Nakon v3.8.59 sljedeća je verzija 3.9.0, a njezin vrh postaje osnova za dvije dugovječne grane:
`stable/v3` (linija v3 LTS, npm `latest`) i `develop` (v4, podignuta na 4.0.0, npm
`nightly`). Model grana/kanala, prijenos promjena unaprijed i oznake nalaze se u
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md); plan se nalazi u dokumentu [ROADMAP](../../ROADMAP.md) (3. faza). Izdvajanje se izvodi jednom;
u verziji 3.8.58 uvježbava se od početka do kraja na račvanju, a 3.8.59 završava uz
[kontrolni popis GO/NO-GO](./LTS_GO_NO_GO.md).

### Probno izvođenje (samo za čitanje, sigurno u svakom trenutku)

```bash
npm run release:dry-run-lts-cut                       # stvarno izdvajanje: 3.9.0 iz HEAD, prethodna oznaka v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # prikvači izvorni commit
```

`scripts/release/dry-run-lts-cut.mjs` ne izvršava ništa: čita git i `gh` te ispisuje
cijeli slijed — preduvjete (izvor se može razriješiti, izvorni repozitorij ima potpunu povijest —
plitki klon ne može poslati `stable/v3`, odredišna strana odbija paket kod prvog
umetnutog nadređenog commita, stoga izdvajanje prvo izvedite iz potpunog klona ili pokrenite
`git fetch --unshallow origin` — prethodna oznaka postoji, `package.json` ima ciljnu verziju,
otvoren je problem s oznakom `release-freeze`, nema otvorenog problema
`Release branch not green`
na postojećoj grani izdanja — grana koja ne postoji prijavljuje `?` kao nepoznato stanje, nikad
zeleno — konfiguriran je Mergifyjev red čekanja `release` (G11: `queue_rules`, `checks_timeout`,
oznaka `queue`), skup pravila `release/*` i dalje blokira brisanje i prisilno slanje, a
`stable/v3` i `develop` još ne postoje), dva koraka s granama, koji se okidači neaktivnih tijekova rada
i uvjeti `if:` aktiviraju (a koji ostaju blokirani varijablom repozitorija ili
prikvačeni za kanonski repozitorij), očekivane dist-oznake (`latest` → 3.9.0, `next` i
`nightly` prazne) te vraćanje. Izlazni kod `0` = `RESULT: READY`, `1` = neuspješan blokirajući
preduvjet (`✗`), `2` = pogreška pri uporabi. `--advisory <id,...>` spušta provjeru na upozorenje (`!`)
bez njezina skrivanja.

Pokrenite probno izvođenje stvarnog izdvajanja dok je zamrzavanje izdanja 3.9.0 još aktivno — grane se
stvaraju nakon oznake i prije nego što faza 12c ukine zamrzavanje.

### Proba verzije 3.8.58 (samo na račvanju)

```bash
# 1. Probno izvođenje na trenutačnom vrhu s parametrima za probu
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. Izvedite nad udaljenim RAČVANJEM (origin ili bilo koji udaljeni repozitorij čiji URL
#    pripada kanonskom repozitoriju bit će odbijen; za svaki se korak traži potvrda u terminalu)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. Pokrenite neaktivne tijekove rada u račvanju (workflow_dispatch tamo gdje probno izvođenje
#    prijavljuje prikvačenost za kanonski repozitorij), a zatim vratite promjene
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

Commit za podizanje verzije grane develop izrađuje se pomoću niskorazinskih git operacija (radno se stablo ne dira) i ažurira
istih pet datoteka kao commit za otvaranje ciklusa: `package.json`, `open-sse/package.json`,
`electron/package.json`, `package-lock.json` i `docs/openapi.yaml`. Odjeljak `[4.0.0]`
u dokumentu CHANGELOG i njegove i18n preslike potom se otvaraju na grani `develop`, prije njezina prvog
PR-a. Skripta nikad ne mijenja npm dist-oznake — uvježbajte ih na pomoćnom paketu.

### Artefakt za pretpregled PR-a (izgradite jednom, promovirajte iste bajtove)

`.github/workflows/preview-artifact.yml` izrađuje jednu produkcijsku tar-arhivu iz vrha PR-a i
provjerava upravo tu međuverziju (dio (a) stavke #8084). Samo PR-ovi iz istog repozitorija; ništa se ne objavljuje.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # ili dodajte oznaku `preview-artifact`
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # instalacija pretpregleda
```

Izvođenje pokreće `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, pakira
tar-arhivu, pokreće `npm run check:pack-boot` (lažne tajne, privremeni direktorij podataka), ponovno pakira i
ne uspijeva ako sažetak nije identičan, a zatim zapisuje `artifact-identity.json` (SHA vrha, SHA baze,
sažetak datoteke zaključavanja, platforma, arhitektura, node ABI, alat za pakiranje, pravilo izgradnje —
`scripts/release/artifact-identity.mjs`) te potvrđuje tar-arhivu u zasebnom zadatku. Promoviranje
pretpregleda znači instaliranje te tar-arhive: nikad je nemojte ponovno izgrađivati iz izvornog koda.

## Vraćanje na prethodnu verziju

Ako izdanje ima kritičan problem:

1. `gh release edit vX.Y.Z --prerelease` (označava ga kao izdanje koje nije najnovije)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (samo ako ga korisnici još nisu počeli upotrebljavati)
3. Ili: hitni ispravak na `release/vX.Y.0` → zakrpno izdanje `vX.Y.(Z+1)`
4. Odmah obavijestite korisnike putem GitHub Discussionsa i Discorda

## Stroga pravila

- Nikada nemojte izravno izvršavati commit na `main`
- Nikada nemojte upotrebljavati `git push --force` na granama `main` ili `release/*`
- Nikada nemojte preskakati Husky kuke (`--no-verify`)
- Nikada nemojte pohranjivati tajne, vjerodajnice ili `.env` datoteke u commit
- Pokrivenost mora ostati ≥60/60/60/60 (naredbe/retci/funkcije/grane)
- Pri izmjeni produkcijskog koda u `src/`, `open-sse/`, `electron/` ili `bin/` uvijek uključite ili ažurirajte testove
