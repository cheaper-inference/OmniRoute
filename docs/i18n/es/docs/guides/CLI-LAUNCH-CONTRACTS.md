El contrato `config/cli-tools-manifest.json` neutral declara IDs canónicos, alias, candidatos binarios, recetas de configuración, argumentos del modelo y capacidades. El adaptador de nodo simple en `bin/cli/cli-manifest.mjs` y el adaptador TypeScript en `src/shared/constants/cliIntegrationManifest.ts` leen el mismo archivo. `tests/unit/cli/cli-manifest-drift.test.ts` verifica juntos el tiempo de ejecución, el catálogo, la configuración, la finalización, los generadores y el registro del backend. Que una herramienta esté catalogada no significa que se pueda lanzar o configurar. En particular, 5dive sigue siendo solo de configuración.

## Entorno infantil y ciclo de vida.

`omniroute run`, `omniroute launch` y `omniroute launch-codex` heredan una lista permitida de compatibilidad OS/terminal e inyectan las credenciales del objetivo seleccionado. Los secretos de bases de datos y proveedores no relacionados no se heredan de forma predeterminada. `--inherit-env` restaura explícitamente la herencia completa del entorno principal; Úselo solo cuando el proceso de terceros seleccionado deba recibir esos valores. Este es un filtrado de entorno, no un entorno limitado OS : el proceso aún se ejecuta con los permisos del sistema de archivos de la persona que llama.

Las señales de interrupción y terminación se envían al niño. El iniciador espera el evento de cierre del niño antes de eliminar la configuración temporal. `OMNIROUTE_CHILD_SIGNAL_TIMEOUT_MS` controla el período de gracia antes de la terminación forzada (predeterminado 5000 milisegundos).

`omniroute launch <tool>` (ver [LAUNCH.md](./LAUNCH.md) ) sigue las mismas reglas de entorno y reenvío de señales, y agrega:

- **Inicio automático de la puerta de enlace.** Para un objetivo local, cuando ninguna puerta de enlace responde en el puerto, el iniciador inicia `omniroute serve --headless --no-open` vinculado a `127.0.0.1` bajo un proceso de reaper independiente. Cada lanzamiento en ejecución tiene una concesión en `DATA_DIR/launch/leases/` (latido cada 15 s, obsoleto después de 45 s o cuando su proceso finaliza). El reaper detiene la puerta de enlace que inició una vez que no ha habido ninguna concesión activa durante el período de gracia inactivo (`OMNIROUTE_LAUNCH_IDLE_GRACE_MS`, valor predeterminado de 10000 milisegundos). Se utiliza una puerta de enlace que el usuario inició pero nunca se detuvo. `--keep-gateway` o `omniroute gateway keep` convierten una puerta de enlace de inicio en una normal; `--no-start` restaura el antiguo comportamiento de fallo en caso de inactividad. Los objetivos remotos sólo se prueban.
- **Sesiones de lanzamiento.** Cada lanzamiento genera un token de sesión `olx_` de corta duración a partir de la credencial principal (`POST /api/launch/sessions`), lo activa mientras se ejecuta la herramienta, lee el resumen de uso y lo revoca después de que sale la herramienta. El token es un subconjunto estricto de su padre: los mismos permisos, el mismo catálogo o uno más limitado, una vida más corta y no es una credencial de panel. La herramienta recibe el token de sesión, nunca la credencial principal, y las solicitudes se etiquetan con `launch:<tool>:<sessionId>` a menos que se proporcione `--tag`. Una puerta de enlace sin la sesión API falla con `GatewayTooOld` en lugar de recurrir a un inicio sin alcance.
- **Configuración por lanzamiento.** Los archivos de configuración de la herramienta se escriben en un directorio temporal privado (modo 0700, prefijo `omnirouter-`) y se eliminan después de que el niño sale. Un `SIGKILL` del iniciador deja el directorio atrás; `omniroute launch --cleanup` elimina dichos directorios una vez que tienen más de un día.

## configuración persistente Gemini

```bash
omniroute setup-gemini --remote https://omni.example --model provider/model --yes
omniroute configure gemini --model provider/model --yes
omniroute run gemini --model provider/model --dry-run --json
```

Los dos primeros comandos configuran esta máquina para el servidor local o remoto seleccionado. La configuración conserva la configuración JSON no relacionada, selecciona la autenticación de clave API Gemini y escribe el punto final y la credencial en un archivo `.gemini/.env` privado. Rechaza JSON no válido en lugar de sobrescribirlo. El punto final URLs debe ser HTTP(S), sin credenciales integradas, parámetros de consulta ni fragmentos. La ejecución en seco imprime rutas, no valores de credenciales.

`GEMINI_CLI_HOME` o `--gemini-home` seleccionan la raíz principal persistente. Un `run gemini` real crea y luego elimina su propio hogar temporal. Ninguno de los modos pasa por alto las comprobaciones de confianza del espacio de trabajo de Gemini.

## perfiles Codex

`configure codex` escribe un `<name>.config.toml` privado con un modelo y su punto final de proveedor OmniRoute. Se hace referencia a las credenciales a través de `OMNIROUTE_API_KEY`, nunca incrustadas. El comando de inicio establece el modelo seleccionado en la clave `model` de nivel superior, no dentro de `model_providers`.

Los archivos de perfil separados son el contrato Codex documentado actual; se superponen a la configuración del usuario cuando se seleccionan con `codex --profile <name>`. Consulta [la referencia del perfil oficial](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) y [la guía OmniRoute Codex](./CODEX-CLI-CONFIGURATION.md).

## Ejecución de comandos herméticos.

Con un `DATA_DIR` explícito, configurar `OMNIROUTE_CLI_SKIP_DEFAULT_DATA_ENV=1` evita que el inicio caiga en el entorno de credenciales del directorio de datos de usuario predeterminado. Esto es útil para pruebas aisladas. No deshabilita otros archivos de entorno seleccionados explícitamente.

## Directorio de trabajo `.env`

El CLI lee los archivos `.env` en este orden, y el primer archivo que establece una clave gana: el `DATA_DIR` explícito, el directorio de datos predeterminado, el directorio de trabajo actual y luego el directorio del paquete. Las variables de Shell siempre ganan.

El directorio de trabajo puede pertenecer a otra persona (un repositorio clonado, un archivo descomprimido) y `omniroute serve` pasa el entorno CLI al servidor y a cada herramienta que ejecuta el servidor. Entonces, un `.env` puede configurar solo estas claves, enumeradas en `bin/cli/utils/untrustedCwdEnv.mjs`:

| Llave                           | Valores aceptados                                                                |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `REQUIRE_API_KEY`               | `true`, `1` o `yes` en cualquier caso, los valores que el servidor trata como en |
| `LANG`, `LC_ALL`, `LC_MESSAGES` | hasta 64 letras, dígitos, `_`, `.`, `@` o `-`                                    |
| `LANGUAGE`                      | lo mismo, más `:`                                                                |
| `TZ`                            | hasta 64 letras, dígitos, `_`, `+`, `-` o `/`, que no comiencen con `/`          |
| `NO_COLOR`, `FORCE_COLOR`       | hasta 16 letras y dígitos                                                        |

Cada valor que acepta `REQUIRE_API_KEY` activa la verificación, por lo que el archivo no puede desactivarla por sí solo. Sin embargo, no decide el resultado: el servidor lee una anulación de `REQUIRE_API_KEY` almacenada en la base de datos antes que el entorno, mientras que la advertencia de inicio sobre la escucha en todas las interfaces sin una clave API lee solo el entorno. Con una anulación almacenada de `false`, un directorio de trabajo `REQUIRE_API_KEY=true` deja el API abierto y oculta esa advertencia. La regla `TZ` es más estrecha que POSIX: rechaza `.`, `:`, `,` y `<>`, por lo que la forma `:Area/City` y reglas como `EST5EDT,M3.2.0,M11.1.0` deben configurarse en el shell o en `<DATA_DIR>/.env`.

Los nombres deben coincidir exactamente, en mayúsculas. Cualquier otra línea, un valor que no pase la verificación y un nombre que no contenga letras ASCII simples, dígitos y `_` (por ejemplo, uno con un byte NUL o una letra similar) se omitirán. El CLI imprime una advertencia que nombra las claves que no puede configurar y otra que nombra las claves permitidas que ignoró, cada una con qué cambiar (`TZ (expected a zone name such as Europe/Berlin)`, `lang (write the name as LANG)`). Ninguno imprime los valores. Las rutas de archivo en estos mensajes, y la ruta `.env` que informa `omniroute doctor`, tienen caracteres de escape cuando contienen caracteres de control o bidi. La restricción no se aplica cuando el directorio de trabajo es el directorio de datos o el directorio del paquete.

`PORT`, `API_PORT` y `DASHBOARD_PORT` no están en la lista. Sin un URL base de una fuente de mayor prioridad, el CLI habla con `localhost:<PORT>` y todo lo que escucha allí recibe la clave API del CLI, el token de contexto y el token de la máquina CLI (`x-omniroute-cli-token`, consulte [CLI_TOKEN.md](../security/CLI_TOKEN.md) ), que el servidor local acepta para llamadas de administración desde loopback. Un puerto del directorio de trabajo permitiría que ese archivo elija el oyente, así que configure los puertos en el shell, en `<DATA_DIR>/.env` o con la opción `--port` de los comandos que tienen uno (`serve`, `launch`, `run`).

El analizador no tiene sintaxis `export`. Una línea como `export LD_PRELOAD=...` nombra una variable `export LD_PRELOAD`; desde el directorio de trabajo se omite y en otros archivos `.env` establece ese nombre literal, que no se lee.

El CLI empareja el token almacenado de un contexto (token de acceso o clave API heredada) solo con el origen propio de ese contexto: esquema, host y puerto, en comparación con `URL.origin`. Esto se aplica a las solicitudes realizadas a través del cliente HTTP de CLI(`--base-url`, `OMNIROUTE_BASE_URL`, `omniroute connect <new-url>`) y a los comandos `launch`, `launch codex`, `configure` y `setup-*` que escriben un URL base y una clave en la configuración de otra herramienta. Apuntando a otro servidor con `--remote`, usan un `--api-key` o `OMNIROUTE_API_KEY` explícito si hay uno configurado, y ningún token de contexto. La comparación es exacta, por lo que `localhost` y `127.0.0.1`, o un host con y sin un punto final, cuentan como servidores diferentes y no obtienen ningún token de contexto. Un URL con información de usuario, una barra invertida o un espacio en blanco nunca coincide, porque otros analizadores URL ( `urllib` y `httpx` de Python, por ejemplo) pueden leer un host diferente. Para las solicitudes que CLI se envía a sí mismo, esa verificación cubre solo el esquema y la autoridad, por lo que una identificación con un espacio en la ruta o consulta conserva el token.
