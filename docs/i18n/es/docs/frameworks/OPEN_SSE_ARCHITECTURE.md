> **TL;DR**: `open-sse/` es el motor principal de streaming que procesa todas las solicitudes a LLM en OmniRoute. Contiene ~1,400 archivos que implementan el flujo de solicitudes, los ejecutores, los servicios, el servidor MCP y la capa de traducción. Esta guía explica cómo encajan todas las piezas.

**Fuente:** `open-sse/` (paquete del workspace, ~1,440 archivos `.ts` que no son de prueba)

---

## ¿Por qué un paquete de workspace independiente?

`open-sse/` es un **workspace independiente** dentro del monorepo de OmniRoute por varias razones:

1. **Reutilización** — `open-sse` se publica como `@omniroute/open-sse` en npm, por lo que otros proyectos pueden usarlo de forma independiente
2. **Límites claros** — el motor de streaming está desacoplado de la capa de interfaz de usuario/base de datos específica de OmniRoute
3. **Rendimiento** — el motor no tiene dependencias de Next.js, lo que permite arranques en frío más rápidos en contextos de CLI/serverless
4. **Versionado** — `open-sse` puede publicar versiones siguiendo su propio calendario

```json
// package.json
"workspaces": ["open-sse"]
```

## El flujo de solicitudes

Cada solicitud a un LLM atraviesa un **flujo de 5 etapas**:

```
                              ┌──────────────┐
   Solicitud HTTP              │  1. ENRUTAR  │   resolución de combos, selección de modelo
   (ruta de Next.js)           └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRADUCIR │   conversión de formato (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EJECUTAR │   ejecutor del proveedor, HTTP, reintentos, disyuntor
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAMING│   transformación SSE, contrapresión
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REGISTRAR│   seguimiento de uso, registro de llamadas, clasificación de errores
                              └──────┬───────┘
                                     │
                                     ▼
                              Respuesta HTTP (SSE o JSON)
```

### Etapa 1: Enrutamiento (services/combo.ts)

**Punto de entrada**: `handleComboChat()` en `services/combo.ts`

Resuelve la solicitud en una tupla concreta `(provider, model, account, credentials)`:

- Busca el combo por ID (o crea un combo virtual para los modelos `auto/*`)
- Aplica la estrategia de enrutamiento (prioridad, ponderada, round-robin, etc.)
- Excluye los proveedores con problemas (disyuntor)
- Selecciona el siguiente destino viable

Para los modelos `auto/*`, esta etapa también:

- Ejecuta el algoritmo de **puntuación de 16 factores** (`services/autoCombo/`)
- Selecciona un par `provider+model` según el estado, el coste, la latencia, etc.

### Etapa 2: Traducción (translator/)

Si el formato de origen (p. ej., OpenAI) difiere del formato de destino (p. ej., Claude), la solicitud se **traduce**:

- Prompt del sistema → mensaje del sistema
- Definiciones de herramientas → formato de herramientas específico del proveedor
- Parámetros de razonamiento/pensamiento → equivalentes específicos del proveedor
- Normalización del rol de los mensajes (`developer` → `system` para proveedores distintos de OpenAI)

`translator/index.ts` expone:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Etapa 3: Ejecución (executors/)

**Punto de entrada**: `getExecutor(providerId).execute(request, options)`

Todos los proveedores utilizan `DefaultExecutor` (`executors/default.ts`) mediante el mecanismo de reserva de la factoría `getExecutor()`. El ejecutor:

- Construye la URL ascendente (`buildUrl()`)
- Añade encabezados específicos del proveedor (`buildHeaders()`)
- Transforma el cuerpo de la solicitud (`transformRequest()`)
- Envía la solicitud HTTP con reintentos y retroceso exponencial
- Gestiona la renovación de la autenticación cuando es necesario (proveedores OAuth)

Todos los ejecutores extienden `BaseExecutor` (`executors/base.ts`, 1170 líneas de código), que proporciona:

- Lógica común de reintentos
- Integración con proxy
- Integración con disyuntor
- Hooks de registro de uso

### Etapa 4: Streaming (utils/stream.ts)

Para las respuestas en streaming, el ejecutor devuelve un **ReadableStream**. El controlador:

- Pasa el flujo por una transformación SSE (`createSSETransformStreamWithLogger`)
- Aplica señales periódicas de actividad para detectar conexiones inactivas
- Gestiona correctamente la desconexión del cliente (`pipeWithDisconnect`)
- Transforma SSE → JSON para clientes sin streaming

Para las respuestas sin streaming, el ejecutor devuelve un objeto JSON analizado que se transmite sin cambios.

### Etapa 5: Registro (services/usage.ts)

Después de la respuesta (correcta o fallida), se registra el uso:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` de la respuesta
- `cost_usd` calculado a partir de los datos de precios
- `latency_ms`, `status`, `error_class` si se produce un error
- Se conserva en la tabla `usage_history`

Los artefactos del registro de llamadas (si están habilitados) se escriben en `${DATA_DIR}/call_logs/`.

## Archivos clave en profundidad

### chatCore.ts (5977 líneas)

El** manejador de solicitudes principal** . A pesar de su tamaño, tiene una estructura clara:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

A pesar de ser una función gigante, está organizada en** secciones comentadas** ese mapa al oleoducto de 5 etapas.

### combo.ts (4456 LOC)

El** motor de enrutamiento** que resuelve un combo a objetivos ordenados.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Soportes** 22 estrategias de enrutamiento** (ver `src/shared/constants/routingStrategies.ts`):

| Estrategia          | Comportamiento                                                                            |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `priority`          | Lista ordenada del primer objetivo                                                        |
| `weighted`          | Probabilístico por peso por objetivo                                                      |
| `round-robin`       | Recorrer los objetivos en orden                                                           |
| `context-relay`     | Transmitir contexto entre objetivos                                                       |
| `fill-first`        | Llene la cuota antes de pasar al siguiente                                                |
| `p2c`               | El poder de dos opciones                                                                  |
| `random`            | Aleatorio uniforme                                                                        |
| `least-used`        | Elija el que tenga menos usos recientes                                                   |
| `cost-optimized`    | El objetivo saludable más barato primero                                                  |
| `reset-aware`       | Consciente de las ventanas de reinicio del proveedor                                      |
| `reset-window`      | Restablecer el enrutamiento basado en ventanas                                            |
| `expiry-first`      | Gaste primero la cuenta cuya cuota expiraría sin usarse                                   |
| `headroom`          | La mayor parte del margen de cuota restante primero                                       |
| `quota-weighted`    | Omita las cuentas agotadas y luego retire la cuota sobrante ÷ carga en vuelo              |
| `strict-random`     | Verdaderamente uniforme (sin ponderación de calidad)                                      |
| `auto`              | Utilice puntuación de 16 factores (`autoCombo/`)                                          |
| `lkgp`              | Primero el último buen proveedor conocido                                                 |
| `context-optimized` | Lo mejor para solicitudes de contexto largo                                               |
| `cache-optimized`   | Anclar cada prefijo de aviso reutilizable a la misma cuenta (accesos de caché de avisos)  |
| `fusion`            | Distribuyase en un panel en paralelo y luego sintetice a través de un juez (`fusion.ts`). |
| `pipeline`          | Pasos de cadena — la salida de cada objetivo alimenta al siguiente                        |
| `jev`               | Suscripción: TypeSafe Jev admite qué entradas clasificadas se publican; más tu pedido     |

### base.ts (1170 LOC)

El** ejecutor abstracto** que cada clase ejecutora extiende (directamente o mediante `DefaultExecutor` y otras subclases). Contiene:

- `buildUrl()` — construcción URL predeterminada (las subclases se anulan para personalizar)
- encabezados predeterminados `buildHeaders()` — (autenticación, tipo de contenido)
- Paso `transformRequest()` — de forma predeterminada
- `execute()` — el bucle principal HTTP con retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

El comportamiento específico del proveedor (encabezados de autenticación, base URL, encabezados de versión) se configura a través del registro del proveedor, no de clases de ejecutor separadas.

## Ejecutores (150 módulos)

Principalmente un archivo por proveedor. Todas las clases ejecutoras extienden `BaseExecutor` y anulan lo que difiere; los otros módulos son ayudantes por proveedor (esquemas de herramientas, adaptadores fetch/TTS, controladores de peculiaridades).

### Patrones comunes

Los proveedores se resuelven mediante `getExecutor(providerId)`, que devuelve el ejecutor configurado. Los proveedores OpenAI/Anthropic-compatible utilizan `DefaultExecutor` (`executors/default.ts`). El comportamiento específico del proveedor ( URL base, encabezados de autenticación, versión API ) se configura en `open-sse/config/providers/`, mientras que las transformaciones del cuerpo de la solicitud se manejan en `open-sse/translator/`.

**URL personalizado** se establece a través de la configuración del proveedor:

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**autenticación personalizada** se maneja a través de la configuración de autenticación del registro del proveedor (clave API, OAuth, perfiles de encabezado).

**Cuerpo de solicitud personalizado** Las transformaciones (por ejemplo, Anthropic que separa `system` de `messages`) se registran por proveedor en `open-sse/translator/`.

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

La resolución pasa por `ExecutorRegistry` (`executors/registry.ts`): cada ejecutor especializado se declara en la tabla integrada de `executors/index.ts` y se registra mediante `registerExecutor(alias, instance)` en la carga del módulo; `getExecutor()` consulta el registro y recurre a un `DefaultExecutor` memorizado para cualquier proveedor sin una entrada especializada. El mapeo completo del alias → ejecutor se caracteriza por la prueba dorada `tests/unit/executor-map-golden.test.ts`.

## Traductores

Traduce entre **3 formatos**: OpenAI, Anthropic y Gemini, además de la nueva Responses API.

### Cuándo se realiza la traducción

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Traducciones habituales:

- `OpenAI → Anthropic`: campo `system` independiente, encabezado `x-api-key`
- `OpenAI → Gemini`: `contents` en lugar de `messages`, `systemInstruction`
- `OpenAI → Responses API`: matriz `input`, estado `previous_response_id`

### Casos especiales contemplados

- Rol `developer` → `system` para proveedores distintos de OpenAI
- Rol `system` → combinado con el primer mensaje del usuario para GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` de Gemini
- `tools` → formato de herramientas específico del proveedor
- Parámetros de razonamiento (o1, Claude) → equivalentes específicos del proveedor

## Servidor MCP

`open-sse/mcp-server/` implementa el servidor del **Model Context Protocol**:

- **110 herramientas** (gestión de proveedores, combinaciones, memoria, caché, compresión, proxy, habilidades, gamificación, complementos, Notion, Obsidian y corpus local)
- **3 transportes**: stdio, SSE y Streamable HTTP
- **33 ámbitos** para una autorización detallada

### Registro de herramientas

Las herramientas se registran como archivos independientes en `open-sse/mcp-server/tools/`; cada uno exporta un nombre, un esquema, un controlador y un ámbito:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transportes

```ts
// stdio (uso de la CLI)
startMcpStdio(server);

// SSE (transmisión basada en HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP moderno)
startMcpStreamable(server, port);
```

### Autorización

Cada llamada a una herramienta pasa por comprobaciones de ámbito (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformadores

`open-sse/transformer/` convierte entre los formatos **Chat Completions** y **Responses API**.

### ¿Por qué un transformador independiente?

Responses API es el nuevo formato de OpenAI con **conversaciones con estado** (`previous_response_id`). Cuando un cliente envía una solicitud de Responses, OmniRoute:

1. Convierte internamente Responses → Chat Completions
2. La envía al proveedor (cualquier proveedor compatible con Chat Completions)
3. Vuelve a convertir la respuesta al formato de Responses
4. Transmite la respuesta convertida al cliente

El transformador (`transformer/responsesTransformer.ts`) proporciona:

```ts
createResponsesApiTransformStream(): TransformStream
```

Esto gestiona:

- Eventos `response.output_item.added`
- Eventos `response.output_text.delta`
- Evento `response.completed`
- Asignación de llamadas a herramientas (`function_call` ↔ `tool_calls`)

## Configuración

`open-sse/config/` contiene la capa de configuración:

| Archivo                        | Objetivo                                                        |
| ------------------------------ | --------------------------------------------------------------- |
| `providerRegistry.ts`          | Registro de modelo de chat sobre el catálogo de 394 proveedores |
| `providerModels.ts`            | Alias de modelo, mapeo de formato                               |
| `constants.ts`                 | Tiempos de espera, límites, códigos de estado                   |
| `defaultThinkingSignature.ts`  | Firma de pensamiento Claude predeterminada                      |
| `modelStrip.ts` (en servicios) | Eliminación de campos por proveedor                             |

### Esquema de registro de proveedores

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

La validación Zod en la carga del módulo garantiza que todas las configuraciones del proveedor sean válidas.

## Restricciones de rendimiento

El motor de enrutamiento tiene presupuestos de rendimiento estrictos:

| Operación                                                 | Objetivo | Medición                         |
| --------------------------------------------------------- | -------- | -------------------------------- |
| Resolución de combinaciones                               | <10ms    | Para 50 destinos                 |
| Comprobación del límite de solicitudes                    | <1ms     | Token bucket en memoria          |
| Fallback de familia de modelos                            | <5ms     | Definiciones de familia en caché |
| Despacho de enrutamiento de solicitudes                   | <2ms     | Ruta crítica                     |
| **Sin E/S bloqueante en la ruta crítica de enrutamiento** | —        | Todo asíncrono                   |

## Antipatrones

❌ **Llamadas síncronas a la BD en `combo.ts`** — precalcular y almacenar en caché
❌ **Lógica de reintentos en los manejadores** — usar `retry()` del servicio de resiliencia
❌ **Acceso directo a la configuración del proveedor** — usar los getters de `providerRegistry`
❌ **Cadenas de fallback codificadas de forma rígida** — definirlas en `modelFamilyFallback.ts`
❌ **Mutaciones de estado entre solicitudes simultáneas** — usar únicamente contexto con ámbito de solicitud

## Añadir un componente nuevo

### Añadir un servicio nuevo

1. Crear `open-sse/services/[serviceName].ts` con una responsabilidad específica
2. Exportar la función principal del manejador y cualquier constante
3. Añadir pruebas unitarias en `tests/unit/services/[serviceName].test.mjs`
4. Integrarlo en el flujo de procesamiento de solicitudes en `handlers/chatCore.ts` (si está relacionado con el enrutamiento)
5. Actualizar la lógica de enrutamiento en `combo.ts` si el servicio afecta a la selección de destinos
6. Documentarlo en este archivo

### Añadir un ejecutor nuevo

1. Crear `open-sse/executors/[provider].ts` que extienda `BaseExecutor`
2. Registrarlo en `config/providerRegistry.ts`
3. Añadirlo a la factoría de `executors/index.ts`
4. Añadir pruebas unitarias para el ejecutor
5. Documentarlo en `docs/architecture/ARCHITECTURE.md`

### Añadir una herramienta MCP nueva

1. Crear o actualizar `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definir el esquema Zod para las entradas
3. Registrar la herramienta en `mcp-server/index.ts`
4. Añadirla a la matriz de ámbitos en `mcp-server/auth/`
5. Añadir pruebas unitarias
