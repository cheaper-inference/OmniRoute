## Completado de chats

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

| ------------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

#### Fijación de cuenta por solicitud

Cuando un proveedor tiene varias conexiones (cuentas o claves), OmniRoute normalmente selecciona una
mediante su estrategia de selección de cuentas. En su lugar, una solicitud puede fijar una conexión específica
con el encabezado `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Dónde encontrar el id.** Abra la página del proveedor en el panel
  (**Dashboard → Providers → <provider>**) y haga clic en el chip de id `xxxxxxxx…` de una fila de conexión;
  esto copia el id completo de la conexión.
- **Qué solicitudes lo respetan.** Solicitudes de un solo modelo (`provider/model`) en
  `/v1/chat/completions`, `/v1/messages` y `/v1/responses`. Las combinaciones ignoran el encabezado: fije
  una cuenta para cada paso de la combinación mediante la conexión propia del paso.
- **La fijación es estricta, no una preferencia.** La conexión fijada se utiliza exclusivamente. Si se
  produce un error dentro de la solicitud, se registra el tiempo de espera de la cuenta, pero **no** se rota
  a una cuenta hermana del mismo proveedor.
- **El tiempo de espera y la cuota liberan la fijación.** Mientras la conexión fijada está en tiempo de espera,
  ha agotado la cuota o está bloqueada por una política de cuota, las solicitudes posteriores recurren a las
  demás conexiones del proveedor, exactamente igual que el tráfico no fijado.
- **Los ids desconocidos o deshabilitados fallan.** Un id que no está en el grupo activo del proveedor (eliminado,
  desactivado o perteneciente a otro proveedor) no deja ninguna cuenta elegible, por lo que la solicitud falla
  en lugar de enrutarse silenciosamente a otro lugar.

Claude Code envía encabezados personalizados mediante `ANTHROPIC_CUSTOM_HEADERS`. Colóquelo en el bloque `env`
de `~/.claude/settings.json`, o en un `.claude/settings.json` de nivel de proyecto para fijar una cuenta
diferente por proyecto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Fuente: `src/sse/handlers/chat.ts` (lectura del encabezado), `src/sse/services/auth.ts` y
`src/sse/services/sessionAffinityPin.ts` (liberación de la fijación y comprobación de ausencia en el grupo).

> **Encabezados de telemetría de costes:** las respuestas correctas sin streaming también incluyen el conjunto de telemetría de costes `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 decimales fijos; `0.0000000000` para solicitudes gratuitas o sin precio), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` y `X-OmniRoute-Fallback-Attempts` (solo cuando es > 0), además de `X-OmniRoute-Request-Id` y `X-OmniRoute-Version`. Estos se emiten mediante chat completions, `/v1/responses`, `/v1/messages` **y los endpoints multimedia** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` y `/v1/moderations` (siempre con coste `0`). El coste multimedia se calcula por modalidad (por imagen, por segundo, por carácter o por unidad de búsqueda) cuando hay precios disponibles; de lo contrario, es `0` (fail-open).

> **Semántica del coste de las coincidencias de caché:** en una coincidencia de caché semántica (`X-OmniRoute-Cache-Hit: true`) no se realiza ninguna llamada ascendente, por lo que `X-OmniRoute-Response-Cost` es `0.0000000000` (el coste **incremental** de servir la coincidencia). El coste original/que se habría generado se informa por separado en `X-OmniRoute-Cost-Saved`. Los consumidores de facturación deben sumar `X-OmniRoute-Response-Cost` (las coincidencias no tienen coste); los análisis de caché pueden agregar `X-OmniRoute-Cost-Saved`.

## Arrendamientos exclusivos de sesiones administradas

El arrendamiento exclusivo de sesiones administradas es un contrato de enrutamiento opcional y neutral respecto al cliente: un único propietario activo mantiene una conexión de OmniRoute elegible. No arrenda un modelo, no requiere OAuth, no identifica a un cliente concreto ni requiere un proveedor específico.

La clave de API de autenticación debe tener el alcance `lease:exclusive` y una lista `allowedConnections` explícita y no vacía. El límite de mutación de la base de datos exige ambos campos conjuntamente al crear claves y realizar actualizaciones parciales.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Las respuestas correctas de adquisición, renovación y liberación exponen marcas de tiempo, `state` y la `generation` positiva exacta, pero nunca la conexión seleccionada ni las credenciales. La renovación y la liberación proporcionan la generación en el cuerpo JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Un propietario de arrendamiento activo puede solicitar explícitamente metadatos de visualización seguros para la privacidad de su vinculación actual:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Esta acción de estado opcional está protegida por el propietario opaco, la clave de API administrada autenticada y la generación activa exacta en una única transacción de base de datos. `displayName` solo contiene el nombre configurado y recortado de la conexión; es `null` cuando no existe un nombre configurado seguro. OmniRoute nunca sustituye este valor por un correo electrónico ni por una identidad de cuenta generada. El valor de proveedor es una etiqueta de visualización no sensible y nunca un identificador de proveedor compatible generado. Se excluyen las credenciales, los tokens, las cookies, los identificadores sin procesar de conexiones o claves de API, los hashes de propietarios, los secretos de protección y los datos internos de enrutamiento.

Las búsquedas con una clave incorrecta, un propietario incorrecto, una generación obsoleta, o una vinculación ausente, expirada, liberada o invalidada devuelven el mismo error `409 LEASE_FENCE_STALE` sin metadatos de conexión. Un cliente que recibió la respuesta de espera por capacidad no tiene ninguna vinculación activa que inspeccionar. Cuando el enrutamiento cambia una sesión activa, la misma generación sigue siendo válida y el estado devuelve atómicamente la nueva vinculación, nunca la anterior. Los clientes existentes no cambian, porque las respuestas de adquisición, renovación, liberación y espera conservan sus formas anteriores.

Este contrato del servidor no cambia `/status` de OpenAI Codex estándar. Actualmente, Codex estándar informa sobre su proveedor de modelos y el estado integrado de autenticación o cuenta, pero no muestra metadatos arbitrarios de cuentas de proveedores personalizados; una integración posterior del cliente deberá llamar a esta acción y decidir cómo mostrar `connection.displayName`.

Cada solicitud de inferencia administrada proporciona entonces ambos encabezados de control:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

El propietario exacto, la generación, la conexión activa y la clave de API autenticada se protegen inmediatamente antes de cada intento ascendente compatible. Repetir el propietario y la generación con otra clave falla incluso cuando esa clave permite la misma conexión. Los propietarios sin procesar no se guardan, registran, conservan en la instantánea de la solicitud ni se reenvían al servicio ascendente.

La contención temporal devuelve HTTP `429` con `Retry-After` y:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Esta respuesta solo significa que el conjunto elegible ordinario no estaba vacío y que cada candidato libre estaba retenido por un arrendamiento activo de otro propietario. Los modelos o proveedores no compatibles, las discrepancias de políticas, el tiempo de enfriamiento, la cuota, el estado de salud y otros fallos ordinarios de elegibilidad conservan sus respuestas existentes de OmniRoute.

### `x-omniroute-compression`

Anulación por solicitud del plan de compresión. Tiene la precedencia más alta: prevalece sobre la anulación de la combinación de enrutamiento, el perfil activo, el activador automático y el valor predeterminado del panel. Valores:

| Valor         | Efecto                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | No aplicar compresión a esta solicitud.                                                                                           |
| `default`     | El perfil predeterminado derivado del panel (ignora el perfil activo). Los motores con pérdida se mantienen desactivados.         |
| `safe`        | Solo deduplicación y compactación de espacios en blanco.                                                                          |
| `allow-lossy` | Mantener el plan del operador para esta solicitud, incluidos los resúmenes y las reescrituras de estilo.                          |
| `engine:<id>` | Un único motor cuando está habilitado, por ejemplo, `engine:rtk`. Activación explícita de ese motor por solicitud.                |
| `<combo>`     | Una combinación con nombre, primero coincidente por nombre (sin distinguir mayúsculas de minúsculas) y después por identificador. |

Notas:

- Los valores desconocidos se ignoran (la solicitud nunca se rechaza); la resolución continúa con la precedencia normal del operador.
- Si varias combinaciones comparten un nombre, proporciona el **id** de la combinación para obtener una coincidencia determinista.
- Una combinación cuyo nombre sea `off` o `default` no se puede seleccionar por nombre (esas palabras clave se interpretan primero); haz referencia a dicha combinación mediante su identificador.
- El interruptor maestro de compresión es una barrera estricta: cuando la compresión está deshabilitada globalmente, este encabezado no puede habilitarla.

El plan aplicado se devuelve en el encabezado de respuesta:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

donde `<source>` es uno de `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` u `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Proveedores disponibles: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Los identificadores del catálogo tienen el formato `provider/model` (ejemplo: `jina-ai/jina-embeddings-v5-omni-small`). Los identificadores de modelos de Jina sin prefijo que aparecen en el registro (por ejemplo, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) también se resuelven. Las funciones de incorporación, reranking, clasificación y segmentación de Jina utilizan primero las credenciales de `jina-ai` del panel; `JINA_AI_API_KEY` solo se usa como alternativa cuando no existe ninguna clave del panel. La tarjeta `jina-reader` solo corresponde a Reader / `r.jina.ai` (`POST /v1/web/fetch`) y nunca proporciona incorporaciones ni reranking.

Los modelos del registro que anuncian compatibilidad multimodal también aceptan hasta 32
elementos estructurados independientes del proveedor. Los tipos de elementos multimedia son
`text`, `image`, `audio`, `video` y `document`. Su `source` multimedia es
`{"type":"url","url":"https://..."}` o
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
y el alias de familia `jina-ai/jina-embeddings-v5-omni` → omni-small) también acepta la
documentación nativa de EmbeddingsV5Request de Jina y la **reenvía intacta** a
`https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Los valores nativos `{ image | audio | video | pdf }` pueden ser una URL HTTPS pública, una URI
`data:` o base64 sin procesar. OmniRoute no convierte esos objetos en cadenas ni obtiene las URL
de imágenes nativas: Jina recupera el contenido multimedia público por sí misma. Los campos
adicionales de Jina (`task`, `normalized`, `truncate`, `embedding_type`) se reenvían. Las SKU
de Jina que solo admiten texto siguen rechazando documentos no textuales.

Límites de seguridad y transporte:

- Las URL multimedia remotas deben ser HTTPS públicas. Los elementos canónicos
  `{type,source:url}` se obtienen en el servidor (revalidación de redirecciones, tiempo de
  espera, límites de tamaño, DNS público y fijación de conexión) y se insertan antes de la
  llamada al proveedor. Los elementos nativos de Jina `{image:"https://..."}` se reenvían tal
  cual después de la misma comprobación de HTTPS público; Jina obtiene la URL.
- El contenido multimedia base64 insertado está limitado a 8 MiB decodificados por elemento y
  16 MiB decodificados en toda la solicitud.

Traducción al proveedor (los elementos canónicos nunca se reenvían sin cambios):

- Modelos multimodales de Jina: cada elemento de nivel superior se convierte en un objeto con
  una clave de modalidad (`text` / `image` / `audio` / `video` / `pdf`) usando URI de datos para
  el contenido multimedia insertado; un vector por cada elemento de nivel superior.
- Familia Gemini Embedding 2: un único arreglo de nivel superior se convierte en una sola
  solicitud nativa `models/{model}:embedContent` con `content.parts` (`text` o `inline_data`).
- llama.cpp (`llama-cpp/<model>`, cualquier modelo que el servidor local haya cargado): los
  elementos canónicos `text` se convierten en cadenas simples, y `image` / `audio` / `video` se
  convierten cada uno en un objeto `{"content": [part]}`, utilizando las partes de contenido de
  chat de llama-server (`image_url`, `input_audio` con formato `wav` / `mp3` / `flac`,
  `input_video`) con datos insertados; un vector por cada elemento de nivel superior. El servidor
  debe ejecutarse con `--embedding --mmproj …`; sin un proyector, rechaza el contenido multimedia
  por sí mismo. `document` no es compatible.
- Los modelos desconocidos o dinámicos sin metadatos explícitos de modalidad rechazan la entrada
  estructurada con HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Las combinaciones de modelo y modalidad no compatibles devuelven HTTP 400 en lugar de convertir el
elemento. Los campos de extensión que no sean de entrada en las solicitudes heredadas de cadenas
o tokens siguen pasando sin cambios.

```bash
# Lista todos los modelos de embeddings
GET /v1/embeddings
```

## Generación de imágenes

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Los proveedores disponibles incluyen OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local) y ComfyUI (local).

`n` devuelve `n` imágenes en `data[]`. Los proveedores cuya API ascendente devuelve una imagen por llamada
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) realizan `n` llamadas ascendentes independientes, con un máximo de 4 simultáneas. Una
`seed` fija se incrementa según el índice de la llamada (`seed`, `seed + 1`, …), por lo que las imágenes difieren, pero siguen siendo reproducibles. `n` está limitado a 10. La solicitud falla por completo si alguna llamada falla. La lista de formatos con expansión es `SINGLE_IMAGE_FANOUT_FORMATS` en
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux reutiliza la conexión existente basada en la clave de API y acepta los prefijos
`zenmux/` o `zm/`:

- `zenmux/openai/gpt-image-2` utiliza la API de imágenes de OpenAI de ZenMux. Las opciones incluyen `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` y `response_format`.
- Otros editores, como `zm/meta/muse-image-1.0`, utilizan el endpoint `:predict` de Vertex AI de ZenMux. `n` se asigna a `sampleCount`, `aspect_ratio` a `aspectRatio` y `image_size`
  (`1K`, `2K`, `4K`) a `sampleImageSize`. Un `size` expresado en píxeles solo proporciona una relación de aspecto,
  no dimensiones de píxeles garantizadas. Las relaciones, resoluciones y cantidades compatibles varían según el modelo.
- `zm/inclusionai/ming-image-0.1-design` elige sus propias dimensiones. Omite `size`,
  `aspect_ratio` e `image_size`; los valores explícitos devuelven HTTP 400. Se puede solicitar PNG, JPEG y WebP
  mediante `output_format`.

Esta integración admite la generación de texto a imagen, no la edición de imágenes de referencia. La salida de Vertex
se normaliza a `data[].b64_json`; `response_format: "url"` devuelve una URL HTTPS ascendente o una URL de datos en base64 cuando solo están disponibles los bytes de la imagen. Las salidas vacías o filtradas
devuelven un error en lugar de una respuesta correcta vacía. El acceso a los modelos depende de la cuenta de ZenMux.
Consulta [API de Vertex de ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) y
[API de imágenes de OpenAI](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Lista todos los modelos de imágenes
GET /v1/images/generations
```

## OCR de documentos

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` selecciona el proveedor de OCR mediante un prefijo `provider/model`; un identificador de modelo sin prefijo (por ejemplo,
`mistral-ocr-latest`) se resuelve en su proveedor registrado, y si se omite `model`, se utiliza Mistral de forma predeterminada (`mistral-ocr-latest`). Proveedores registrados (`open-sse/config/ocrRegistry.ts`):

| Id. del proveedor             | Id. del modelo       | Valor de `model`                                                  | Notas                                                                                                                                               |
| ----------------------------- | -------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (o `mistral-ocr-latest` sin prefijo) | Síncrono: la respuesta se devuelve directamente desde la única llamada ascendente.                                                                  |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                       | Ascendente asíncrono (`analyze` + sondeo): consulta la información siguiente.                                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                           | Síncrono, mediante el endpoint asociado `openapi/chat/completions` de Vertex AI: consulta la información siguiente sobre la autenticación y la URL. |

Los tres proveedores responden con el mismo cuerpo con formato de Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Flujo de sondeo de Azure Document Intelligence

La API `analyze` de Azure Document Intelligence es asíncrona: la solicitud inicial devuelve un encabezado
`Operation-Location` en lugar de un cuerpo, y es necesario sondear el resultado. El controlador
(`open-sse/handlers/ocr.ts`) sondea esa URL cada segundo durante un máximo de 30 intentos, falla rápidamente (no
sigue sondeando) ante una respuesta de sondeo que no sea `ok` o ante un estado `"failed"`, y devuelve `504` si la
operación aún se está ejecutando una vez agotado el presupuesto de intentos. La respuesta final de Azure se
normaliza con la misma estructura `pages`/`markdown` utilizada por Mistral antes de devolverse al
cliente, por lo que el código del cliente no necesita tratar el proveedor de forma especial.

### Autenticación y resolución del endpoint de Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` reutiliza la misma autenticación de Vertex AI que OmniRoute ya admite para el tráfico de
chat/imágenes (`open-sse/executors/vertex.ts`): la clave de API de la conexión es una credencial JSON de
Cuenta de servicio (intercambiada por un token de acceso OAuth de corta duración mediante el flujo de
portador JWT) o un token de acceso OAuth ya emitido, que se utiliza tal cual. La URL del endpoint ascendente es el
endpoint asociado genérico `openapi/chat/completions` de Vertex, construido a partir del proyecto y la
región de la conexión: un `providerSpecificData.project`/`providerSpecificData.region` explícito siempre tiene prioridad;
de lo contrario, el proyecto se obtiene de `project_id` del JSON de la Cuenta de servicio y la región toma
`us-central1` de forma predeterminada. Ambas resoluciones se realizan en `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), y `src/app/api/v1/ocr/route.ts` las utiliza antes de
enviar la solicitud a `handleOcr`.

## Listar modelos

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Devuelve todos los modelos de chat, embeddings e imágenes + combinaciones en formato OpenAI
```

### Precios de los modelos (`pricing`)

Una entrada incluye un objeto `pricing` cuando OmniRoute conoce el precio del modelo. El precio
proviene de la tabla de precios que utiliza la contabilidad de costes: valores predeterminados
integrados, precios sincronizados y sobrescrituras configuradas mediante `/api/pricing`. Estos
son precios de lista, por lo que los proveedores por suscripción también muestran un precio por
token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Campos                                                          | Unidad                        | Notas                                                                                                                                                                       |
| --------------------------------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD por token, cadena decimal | Compatibles con OpenRouter, nunca en notación exponencial. Los dos campos de caché aparecen solo cuando existe un precio de caché.                                          |
| `input`, `output`, `cached`, `cache_creation`                   | USD por 1M de tokens, número  | Campos de versiones anteriores del catálogo, conservados para los clientes existentes. `reasoning` y `long_context` también aparecen cuando la fila de precios los incluye. |

- Las **combinaciones** llevan el precio de su primer destino visible. Las combinaciones
  integradas `auto/*` seleccionan un destino en el momento de la solicitud, por lo que no tienen
  `pricing`.
- Los **modelos gratuitos** muestran `"0"` (y `0`) cuando su precio es cero. Un modelo sin fila
  de precios también muestra `"0"` cuando el catálogo lo marca como gratuito (`free: true`) o el
  catálogo integrado de modelos gratuitos lo incluye.
- **Precio desconocido:** la entrada no tiene la clave `pricing`.
- Los **proveedores con medición por créditos** (como Kiro) facturan por solicitud en lugar de
  por token. Sus entradas conservan los campos numéricos por 1M que tenían anteriormente y no
  incluyen campos de cadena por token.
- Las **variantes** (identificadores de nivel de razonamiento, alias sin pensamiento, espejos de
  descubrimiento y de gateway) copian el precio del modelo al que enrutan.
- Los campos contienen únicamente las tarifas base. Los niveles de contexto largo (el campo
  numérico `long_context`) y los multiplicadores del nivel de servicio (por ejemplo, Codex fast o
  flex) no modifican `prompt` ni `completion`.
- El objeto es el mismo para todos los estilos de autenticación, incluida una solicitud al estilo
  de Anthropic con `x-api-key` y `anthropic-version` (la respuesta sigue siendo `{ "object": "list",
"data": [...] }`). Implementación: `src/app/api/v1/models/catalogPricing.ts`.

### Prefijos de los identificadores de modelo (`?prefix=`)

La mayoría de los modelos se anuncian con un **prefijo del proveedor**. El prefijo que obtienes
está controlado por el indicador de funcionalidad `MODELS_CATALOG_PREFIX_MODE` y se puede
sobrescribir **por solicitud** con un parámetro de consulta — útil para un cliente que quiera
una lista limpia sin cambiar la configuración de todo el servidor para los demás:

```bash
GET /v1/models?prefix=alias        # un identificador por modelo — el prefijo de alias corto
GET /v1/models?prefix=dual         # ambas formas (predeterminado del servidor)
GET /v1/models?prefix=canonical    # solo el prefijo completo del identificador del proveedor
```

| Modo        | Emite                                                   | Notas                                                                                                                                                                                                                                   |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **y** `claude/claude-sonnet-4-6` | **Predeterminado.** Ambos identificadores enrutan al mismo modelo; se conservan para que las configuraciones de clientes que incluyeron cualquiera de las dos formas sigan funcionando. Duplica aproximadamente el tamaño del catálogo. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Una entrada por modelo. Los proveedores sin un alias distinto siguen emitiendo su entrada, por lo que no se pierde nada.                                                                                                                |
| `canonical` | `claude/claude-sonnet-4-6`                              | Una entrada por modelo con el prefijo completo del identificador del proveedor. Los proveedores sin un alias distinto (por ejemplo, `antigravity/…`, `agy/…`) también emiten aquí su único identificador, por lo que no se pierde nada. |

Un espejo en modo `dual` también se puede reconocer sin el parámetro de consulta: contiene un
campo `parent` que apunta al identificador principal.

Los clientes que muestran un selector de modelos deberían solicitar `?prefix=alias`; esto es lo
que hace la [extensión OmniCopilot para VS Code](../guides/VSCODE-COPILOT.md).

### Filtros de descubrimiento (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` acepta filtros de descubrimiento opcionales. Sin ninguno de ellos, la respuesta
no cambia. Estos filtros reducen el catálogo que el solicitante ya puede ver (los permisos de la
clave de API se aplican primero) y se ejecutan antes de la paginación de estilo OpenAI mediante
`limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # todas las capacidades indicadas deben ser verdaderas
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` del catálogo; las filas sin uno son `chat`
GET /v1/models?q=sonnet&limit=10                           # coincidencia sin distinguir mayúsculas de minúsculas en el identificador o el nombre
```

| Parámetro     | Valores                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | entero no negativo, comparado con `context_length`                                                  |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 caracteres                                                                                    |

Un valor desconocido, o un `min_context` que no sea un entero no negativo (por ejemplo, `1.5`),
devuelve HTTP `400` y el mensaje enumera los valores válidos. Implementación:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista breve de modelos (`POST /v1/models/query`)

`POST /v1/models/query` devuelve una lista breve y determinista del mismo catálogo, con la misma
autenticación y visibilidad por clave que `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Todos los campos son opcionales. `capabilities` y `exclude` aceptan un arreglo o una cadena
separada por comas; `max_output` se compara con `max_output_tokens`. Los resultados se ordenan por
`owned_by` y luego por `id`. `limit` tiene un valor predeterminado de `20` y los valores superiores
a `100` se limitan a `100`. El JSON no válido, un campo desconocido o un valor no válido devuelve
HTTP `400`.

### Modelos de chat ocultos individualmente

Un modelo marcado como **Oculto** en la página de su proveedor se excluye del catálogo y se rechaza
con HTTP `404` / `model_not_found` cuando se solicita explícitamente. La comprobación utiliza el
proveedor y el modelo resueltos, incluidos los alias de proveedor, los prefijos de nodo de
proveedores compatibles y los valores predeterminados de conexión. Un combo omite los destinos
ocultos y puede utilizar un modelo hermano visible; cuando no queda ningún destino ejecutable,
devuelve el mismo código de error. El cambio a visible se aplica en la siguiente solicitud. Las
anulaciones de visibilidad exclusivas para imágenes no ocultan el modelo de chat con el mismo ID.

Esta configuración de modelo individual es independiente de las
[listas de permitidos/denegados de exposición de modelos](../routing/MODEL_EXPOSURE_LIST.md), que
filtran la publicidad del catálogo y los candidatos del enrutamiento automático, al tiempo que
conservan el despacho explícito. Los permisos de modelos de las claves de API siguen aplicándose de
forma independiente. El modo de prefijo predeterminado del catálogo sigue siendo `dual`.

### Variantes de modelos sin razonamiento

Para los modelos Claude compatibles con el razonamiento, `/v1/models` también anuncia una variante
**sin razonamiento**, cuyo id lleva el prefijo `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Al seleccionar este id (por ejemplo, en una configuración de Claude Code que siempre incluye un
bloque `thinking`), se vuelve a resolver en el `<provider>/<model>` real con el razonamiento
suprimido: `thinking:{type:"disabled"}` en la ruta `/v1/messages`, o se eliminan los campos
`reasoning`/`reasoning_effort` en la ruta `/v1/chat/completions`. La variante solo se incluye para
los modelos de la familia Claude que admiten el razonamiento **y** respetan `disabled` (por lo que,
por ejemplo, se excluyen los modelos que solo admiten el modo adaptativo y rechazan `disabled`).
Los operadores pueden activar o desactivar la variante por modelo mediante
`ModelSpec.noThinkingAlias`.

## Generación de audio con ElevenLabs

Configura una conexión de proveedor `elevenlabs` en OmniRoute con tu clave de API de ElevenLabs.
Los clientes se autentican con su clave de **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
la puerta de enlace proporciona la clave de proveedor almacenada como `xi-api-key`. Nunca envíes una clave de ElevenLabs
como token bearer de la puerta de enlace.

| Método | Ruta                        | Respuesta                                    | Categoría del endpoint de clave de API |
| ------ | --------------------------- | -------------------------------------------- | -------------------------------------- |
| POST   | `/v1/sound-generation`      | Bytes de audio nativos                       | `elevenlabs`                           |
| POST   | `/v1/music`                 | Bytes de audio nativos                       | `music`                                |
| POST   | `/v1/music/stream`          | Bytes de audio en streaming                  | `music`                                |
| POST   | `/v1/music/detailed`        | Audio nativo multipart y plan de composición | `music`                                |
| POST   | `/v1/music/detailed/stream` | Metadatos SSE nativos y fragmentos de audio  | `music`                                |
| POST   | `/v1/music/plan`            | Plan de composición JSON                     | `music`                                |

Estos endpoints complementan las rutas existentes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` y `/v1/speech-to-text`. Los campos JSON nativos
y los parámetros de consulta como `output_format` y `enable_logging` se conservan.
Las respuestas de `/v1/music/detailed` conservan sus límites multipart; analízalas como multipart.
`/v1/music/detailed/stream` devuelve `text/event-stream` con metadatos de composición y
fragmentos de audio codificados en base64 en eventos SSE. Las seis rutas admiten la
solicitud previa de CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Un efecto de sonido corto. Duración: de 0,5 a 30 segundos.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# La duración de la música se expresa en milisegundos: de 3000 a 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Usa `/v1/music/stream` con el mismo cuerpo JSON para la entrega incremental de audio. La composición
acepta exactamente uno de `prompt` o `composition_plan`; `/v1/music/plan` requiere `prompt`
y acepta opcionalmente `source_composition_plan`. Los esquemas nativos conservan campos
adicionales del proveedor para que las versiones de los planes de composición y las opciones de
ajuste preciso lleguen a ElevenLabs.

El endpoint unificado `/v1/music/generations` también acepta
`elevenlabs/music_v1`, `elevenlabs/music_v2` y `elevenlabs/music_v2_5`. Con una conexión activa de
ElevenLabs, estos modelos se exponen en el catálogo de música. Este endpoint devuelve
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Su campo `duration` está expresado en
segundos y se asigna a `music_length_ms`; un `music_length_ms` explícito tiene precedencia.
`instrumental` se asigna a `force_instrumental`, y el campo nativo tiene precedencia.
Usa los endpoints de streaming nativos para el streaming y el endpoint de composición nativo
para las solicitudes impulsadas únicamente por un plan de composición.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Las restricciones de endpoint, modelo, presupuesto y conexión se aplican antes de una llamada ascendente. Las rutas nativas
devuelven los códigos de estado y los cuerpos de error ascendentes sin modificar, incluido `402` para una restricción
del plan y `429` para un límite de cuota. Los encabezados `character-cost`, `song-id`, `request-id` y `retry-after`
se conservan cuando están presentes. Un saldo de créditos gratuito no garantiza el acceso a todos los
modelos de música, formatos de salida o funciones de la API: ElevenLabs decide la autorización para cada solicitud.
El endpoint unificado conserva los códigos de estado de error en el sobre de error normalizado de OmniRoute.

Contratos ascendentes: [efectos de sonido](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composición musical](https://elevenlabs.io/docs/api-reference/music/compose) y
[detalles de música en streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Nodos de proveedores de reranking:** `POST /v1/rerank` también se enruta a nodos de proveedores compatibles con OpenAI
> (oMLX, vLLM, Infinity, TEI detrás de una puerta de enlace, …) identificados como `<node-prefix>/<model>`. Los nodos de bucle local
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) siempre son elegibles, al igual que los nombres de host que el operador
> incluye en `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (por ejemplo, un nombre de servicio de Docker/Compose como
> `http://reranker:8080/v1`; estos se contactan directamente, nunca a través de `HTTP(S)_PROXY` ni del proxy fijado de una
> conexión). Los nodos en cualquier otro host —un equipo de la LAN o un par de Tailscale— solo son elegibles cuando el operador habilita la
> marca de funcionalidad `RERANK_REMOTE_PROVIDER_NODES` **y** la URL base del nodo cumple la política de URL de salida del proveedor
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> El paso de reranking del motor de memoria llama a esta ruta a través del bucle local, por lo que la misma regla rige
> `rerankProviderModel` en la configuración de Memory.
>
> **Formatos de servidores locales:** se llama al nodo en `<base>/v1/rerank` y, en caso de 404, en `<base>/rerank`
> (Infinity, TEI). El cuerpo enviado al upstream incluye tanto la nomenclatura de Cohere/OpenAI (`documents`,
> `return_documents`) como la nomenclatura de TEI (`texts`, `return_text`), y la respuesta del upstream se
> normaliza al contenedor de Cohere: el `[{index, score, text}]` simple de TEI, `{results: [{index, score}]}`
> de las puertas de enlace ligeras y `{data: [...]}` al estilo de Voyage regresan al cliente como
> `{results: [{index, relevance_score, document?}]}`, ordenados por puntuación y limitados a `top_n`.

> **Detección de nodos de proveedores:** los modelos de un nodo de proveedor compatible con OpenAI aparecen en `GET /v1/models`
> bajo el prefijo del nodo. Las filas que no incluyen metadatos de endpoint (algo habitual en los listados locales de `/v1/models`)
> heredan el `apiType` del nodo, por lo que los modelos de un nodo de `embeddings` tienen `type: "embedding"` y los
> modelos de un nodo de `rerank` tienen `type: "rerank"` en lugar de asumir el tipo chat; un `supportedEndpoints` explícito
> en una fila sincronizada o añadida manualmente sigue teniendo prioridad.

## API de búsqueda

Abstracción de proveedores web/de búsqueda (Tavily, Brave, Exa, Serper, etc.).

| Método | Ruta                   | Descripción                                                                                                            |
| ------ | ---------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v1/search`           | Enumera los proveedores de búsqueda configurados y sus capacidades                                                     |
| POST   | `/v1/search`           | Ejecuta una consulta de búsqueda — cuerpo validado por `v1SearchSchema`, admite almacenamiento en caché y coalescencia |
| GET    | `/v1/search/analytics` | Estadísticas de aciertos/latencia/caché por proveedor                                                                  |

**Autenticación:** clave de API Bearer (`extractApiKey` + `isValidApiKey`). La política de búsqueda se aplica mediante `enforceApiKeyPolicy`.

### `provider_options` de Exa y Tavily

Exa y Tavily leen los campos específicos del proveedor desde un contenedor con espacio de nombres:
`provider_options.exa` (o `provider_options["exa-search"]`) y `provider_options.tavily`
(o `provider_options["tavily-search"]`). Solo se reenvían las claves indicadas a continuación. Cada una se
comprueba con su propio esquema de Zod en `open-sse/handlers/search/providerOptionsPassthrough.ts`,
y una clave con un tipo incorrecto se descarta. Cualquier otra clave se ignora, incluidas las de autenticación, la URL base,
`stream` y `outputSchema`. Las claves planas utilizadas por otros proveedores (`cx`, `depth`, ...) siguen funcionando como antes.

| Proveedor | Campos de nivel superior                                                                                                                                                                                                                                                                                                                                                  | Anidados                                                                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitivas planas), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` combinados sobre el valor predeterminado `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                         |

Los campos genéricos siempre prevalecen: `query`, `max_results`, `filters` (dominios), `country` y el
tema derivado de `search_type`. En Exa, `search_type: "news"` mantiene `category: "news"`.
Tavily también acepta `search_type: "finance"` (`topic: "finance"`).

El coste de búsqueda de Firecrawl se registra por cada bloque iniciado de 10 resultados devueltos, a $0.002 (2
créditos) por bloque y con al menos un bloque por llamada
([Facturación de Firecrawl](https://docs.firecrawl.dev/billing)): 11 resultados cuestan $0.004.

El `time_range` genérico ahora llega a ambos proveedores: Exa recibe `startPublishedDate` (marca de tiempo ISO)
y Tavily recibe `start_date` (`YYYY-MM-DD`). Una fecha explícita en `provider_options`
anula la asignada.

Los resultados de Exa conservan `id`, `highlights` (cada resaltado, no solo el primero utilizado como
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` y `extras` en
`provider_raw`. Los resultados de Tavily conservan `images` y `favicon`.

El coste de búsqueda de Linkup se registra en $0.005 para `depth` `fast` y `standard`, y en $0.05 para
`deep` ([Precios de Linkup](https://docs.linkup.so/pages/documentation/development/pricing)),
independientemente de si `depth` procede de `provider_options` o de la configuración de la conexión.

Exa `type: "lite"` (Exa 3.0) acepta un conjunto más reducido de campos y rechaza toda la solicitud
cuando se establece cualquier otro campo. Para lite, `additionalQueries`, `systemPrompt` y todas las claves de
`contents`, excepto `text` y `highlights`, se descartan antes de la llamada. Los elementos obsoletos
`subpages`, `subpageTarget`, `highlights.numSentences` y `highlights.highlightsPerUrl` ya no se
reenvían.

El cálculo de costes utiliza el registro plano `costPerQuery`, excepto en Exa, que sigue sus
propios precios: $0.007 por llamada para `auto` (y el heredado `fast`) o $0.004 para `lite` (y el heredado
`instant`), cubriendo 10 resultados; $0.001 por cada resultado adicional; y $0.001 por
cada resultado devuelto cuando se establece `contents.summary`. Tavily se registra con 1 crédito ($0.008) para
`search_depth` `basic`, `fast` y `ultra-fast`, y con 2 créditos ($0.016) para `advanced`
([Créditos de la API de Tavily](https://docs.tavily.com/documentation/api-credits)). Una llamada con
`auto_parameters: true` que Tavily actualiza a advanced se sigue registrando con 1 crédito.

## API de obtención web

Extrae contenido de una URL mediante un proveedor de obtención web configurado (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, misma clave de API que Parallel Search) devuelve solo Markdown
— cualquier otro `format` produce un `400` — y limita el contenido a 100.000 caracteres. Cuando la
propia página de destino no se puede extraer, el upstream lo informa dentro de un HTTP 200;
OmniRoute lo muestra como un `422` con un mensaje fijo.

| Método | Ruta            | Descripción                                                     |
| ------ | --------------- | --------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Obtiene/extrae una URL — cuerpo validado por `v1WebFetchSchema` |

**Autenticación:** clave de API Bearer (`extractApiKey` + `isValidApiKey`). La política se aplica mediante `enforceApiKeyPolicy`.

**Fallback consciente de la cuota (#8297):** cuando no se proporciona ningún `provider` explícito, el grupo
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) se recorre en orden de
prioridad fijo (fill-first): un proveedor limitado por tasa pero configurado se omite
en lugar de interrumpir la solicitud, y un fallo upstream reintentable o de cuota
(HTTP 429 siempre; 402/403 para los niveles gratuitos de tipo cuota de Firecrawl/Tavily/TinyFish —
no para Jina Reader, y nunca para un 400 simple de solicitud incorrecta) pasa al
siguiente proveedor con credenciales que aún no se haya probado en el momento de la solicitud. Cuando todos los proveedores del
grupo se han agotado, el endpoint devuelve un único `429` (con una cabecera `Retry-After`)
en lugar del `400` genérico anterior. Cuando se solicita un `provider` explícito, no
hay fallback silencioso: un proveedor explícito limitado por tasa o que falle muestra
su propio error (`429` si está limitado por tasa; en caso contrario, el estado del upstream).

## Streaming mediante WebSocket

```bash
GET /v1/ws?handshake=1
```

Valida un handshake de actualización a WebSocket y devuelve los mensajes de ejemplo del protocolo de conexión (`request`, `cancel`). Los frames WS reales los gestiona el servidor WS incluido, fuera de la tabla de rutas de Next.js.

**Autenticación:** clave de API Bearer durante el handshake.

### API de Responses mediante WebSocket (solo codex)

```bash
# Mismo host:puerto que la API HTTP (por defecto, 20128); actualiza la conexión:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (o: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# El primer frame DEBE ser response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Un proxy de Responses-API-over-WebSocket está conectado **exclusivamente a `codex`** (backend de ChatGPT). Escucha en el mismo puerto que la API/dashboard, en las rutas `/v1/responses`,
`/responses` y `/api/v1/responses`. En el primer frame `response.create`, se autentica y prepara la conexión mediante el puente interno `codex-responses-ws`, selecciona una conexión OAuth de codex y crea un túnel hacia
`wss://chatgpt.com/backend-api/codex/responses` mediante el transporte `wreq-js`. Los modelos que no sean codex se rechazan (`codex_ws_provider_required`).
Para el enrutamiento con cuota compartida, usa `model: "qtSd/<group>/codex/<model>"`. Implementado en
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autenticación:** clave de API Bearer durante el handshake. El servidor HTTP incluido (`server-ws.mjs`)
debe ser el punto de entrada activo (lo es de forma predeterminada cuando existe `app/server-ws.mjs`).

#### Id. de modelo: usa el id de ChatGPT sin prefijo (`codex/`)

El **Codex CLI** de OpenAI valida el nombre del modelo en el cliente cuando
`supports_websockets = true` y **rechaza los ids con prefijo de proveedor**, como
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Envía el id **sin prefijo** (por ejemplo, `gpt-5.5`). El puente de OmniRoute solo funciona con codex, por lo que vuelve a resolver un id sin prefijo como modelo de codex
(`resolveCodexWsModelInfo`) antes de crear el túnel upstream, aunque un `gpt-5.5` sin prefijo se enrutaría de otro modo a otro proveedor mediante HTTP.

#### Configuración del Codex CLI de OpenAI

Dirige el Codex CLI a OmniRoute añadiendo un proveedor personalizado con compatibilidad con WebSocket a `~/.codex/config.toml` (usa un `CODEX_HOME` independiente para evitar modificar una configuración existente):

```toml

model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # sin barra final; la URL WS se deriva (usa https/wss en producción)
wire_api = "responses"                    # único valor compatible desde febrero de 2026
supports_websockets = true                # habilita el transporte Responses mediante WS
env_key = "OMNIROUTE_API_KEY"             # contiene la clave de API de OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # una clave de API de OmniRoute (cualquier clave si REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

El CLI convierte `base_url + /responses` en un WebSocket y OmniRoute crea un túnel hacia la conexión OAuth de codex seleccionada. Validado de extremo a extremo contra el servidor local: ChatGPT devuelve `codex.rate_limits` + `response.created` y transmite la finalización.

### Recuperación de sesiones de cuota (optativa)

Una solicitud `POST /v1/chat/completions` o `POST /v1/responses` sin streaming que falle con un error de cuota
terminal (`402`/`429`/`503` cuyo cuerpo indique que la cuota o los créditos se han agotado)
puede aparcarse y reproducirse más tarde en lugar de devolver el error. El emisor opta por esta función por solicitud mediante tres encabezados:

| Encabezado                   | Valor                                               |
| ---------------------------- | --------------------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                              |
| `x-omniroute-session`        | id de sesión, `[A-Za-z0-9._:-]{1,128}`              |
| `x-omniroute-recovery-turn`  | id de turno único dentro de la sesión (misma regla) |

Solo son aptos los turnos con `stream: false`, sin herramientas, historial de herramientas ni `previous_response_id`, y sin
fijación de `x-omniroute-connection`; además, debe estar definida `STORAGE_ENCRYPTION_KEY` (la solicitud se almacena cifrada
durante un máximo de 24 h). La respuesta será entonces `202` con
`recovery.poll`; consulte mediante `GET /v1/quota-recoveries/{id}` (`202` mientras está pendiente, `200` con el
cuerpo recuperado cuando se completa) o cancele mediante `DELETE`. Los tickets solo son visibles para la clave de API que los creó. Una reproducción
cuyo resultado sea incierto termina en `needs_confirmation` en lugar de enviarse dos veces. Fuente: `src/lib/quota/quotaSessionRecovery.ts`.

## Uso de autoservicio (`/api/usage/om-usage`)

Cualquier clave de API puede leer **su propio** uso y sus cuotas; no requiere autenticación de gestión. Este es el endpoint que un
cliente (la CLI, el panel de OmniCopilot) utiliza para mostrar al titular de una clave su gasto.

```bash
# Formato de texto (el contrato histórico: texto sin formato para un terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Formato estructurado: lo que consume una interfaz de usuario
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

La clave debe tener **`allowUsageCommand`** habilitado (desactivado de forma predeterminada; el administrador de claves de API del panel
lo activa por clave). Sin esta opción, el endpoint responde con `403`.

`?format=json` devuelve una estructura discriminada para que el emisor nunca lea un campo de datos de una respuesta de rechazo. En caso de éxito:

```jsonc
{
  "allowed": true,
  // presente solo cuando la clave ha activado límites de uso por clave (USD diarios/semanales):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // instantánea de la cuota del proveedor seleccionado, o null cuando aún no hay nada almacenado en caché:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // instantánea de cada conexión, para que una interfaz de usuario pueda representar varios proveedores en paralelo:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

En caso de rechazo (clave `401` no válida / `403` no permitido), la misma ruta devuelve
`{ "allowed": false, "error": { "message": "…" } }`; un `personal`/`provider`
presente pero vacío (clave permitida, aún no se ha obtenido ningún dato) representa un estado diferente al de un rechazo, y solo el formato JSON
permite distinguirlos.

**Autenticación:** la propia clave de API Bearer del emisor, validada con `isValidApiKey`; esta no es la
superficie de gestión (`/api/keys/…`), que sigue protegida por `requireManagementAuth`.

### Porcentajes de cuota sin ajustar frente a ajustados por umbral

Al consumir `/api/usage/om-usage`, los emisores deben tener en cuenta la diferencia entre los
porcentajes presentados por la **salida de texto sin formato** y la salida estructurada **JSON**:

| Aspecto                          | Formato de texto sin formato (`/api/usage/om-usage` / `@@om-usage`)                                     | Formato JSON (`?format=json`)                                                                       |
| :------------------------------- | :------------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------------------- |
| **Campo de salida**              | `NN% left` (p. ej., `20% left`)                                                                         | `provider.quotas` / `providers[].quotas`                                                            |
| **Medición**                     | **Asignación utilizable ajustada por umbral**: capacidad restante por encima del umbral de corte        | **Cuota sin procesar del proveedor ascendente**: medición del proveedor sin ajustar                 |
| **Escalado del umbral de corte** | Escalado mediante `effectiveRemainingPercent()` para que la reserva protegida se muestre como `0% left` | Ninguno (valores de la instantánea sin procesar tal como los informa el proveedor)                  |
| **Datos del umbral**             | Incorporados al porcentaje mostrado                                                                     | Almacenados en `quotaWindowThresholds` por conexión (o en los valores predeterminados del servidor) |
| **Consumidor principal**         | CLIs interactivas, indicaciones de terminal, operadores humanos                                         | Integraciones programáticas, paneles, análisis, sistemas de seguimiento de facturación              |

#### Fórmula del ajuste por umbral de corte

OmniRoute admite umbrales de corte de cuota proactivos para evitar el agotamiento del proveedor ascendente (configurados mediante la conexión
`quotaWindowThresholds`, los valores predeterminados del proveedor o la configuración global de resiliencia). Cuando hay un umbral de corte
activo (por ejemplo, `cutoff = 25%`) en una ventana de cuota, el procesador de texto calcula la asignación restante de la siguiente manera:

- Si `remaining <= cutoff`: devuelve `0%`.
- Si `remaining > cutoff`: devuelve `((remaining - cutoff) / (100 - cutoff)) * 100`.

La salida de texto formateada redondea este valor al entero más cercano (`Math.round(...)`).

#### Ejemplo ilustrativo

Considera una ventana del proveedor con un **60% de uso sin procesar** (por lo tanto, un **40% de cuota restante sin procesar**) y un umbral configurado de **25% de cuota restante**:

| Representación                         | Cálculo                                            | Restante |               Uso implícito               |
| :------------------------------------- | :------------------------------------------------- | :------: | :---------------------------------------: |
| **JSON sin procesar (`?format=json`)** | Instantánea del proveedor (`quotas[window]`)       | **40%**  |                  **60%**                  |
| **Formato de texto (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (si se calcula `100 - remaining`) |

- **Por qué el texto muestra un 20% restante:** De la cuota física del 40% que queda en la cuenta, el 25% está reservado por la política de límite. El usuario solo dispone de un 15% de los 75% de margen utilizable antes de que el enrutador deje de enrutar hacia esta conexión. El escalado garantiza que la conexión indique agotamiento (`0% left`) exactamente cuando cese el enrutamiento.
- **Por qué JSON conserva los valores sin procesar:** La carga útil JSON devuelve la instantánea exacta del proveedor (`UsageSnapshot`), de modo que las herramientas externas tienen acceso a la utilización real del proveedor y a `quotaWindowThresholds` de nivel de conexión sin un escalado con pérdida en el servidor.

#### Guía de migración para consumidores

Si una integración externa (como un complemento de editor o una extensión de agente) analizaba anteriormente el endpoint de texto (`NN% left`) y calculaba el porcentaje utilizado como `100 - NN`, migrar a `?format=json` significa:

- Leer los valores JSON sin procesar reflejará el **consumo real del proveedor** (60% utilizado en el ejemplo anterior).
- Si la integración desea conservar la semántica de asignación utilizable del endpoint de texto, puede evaluar la fórmula de restante efectivo en el cliente utilizando `quotaWindowThresholds` para las anulaciones de nivel de conexión.

## Caché semántica

```bash
# Obtener estadísticas de la caché
GET /api/cache/stats

# Borrar todas las cachés
DELETE /api/cache/stats
```

Ejemplo de respuesta:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impacto en la latencia

Un HIT de la caché semántica proporciona la respuesta desde la caché **sin realizar una llamada upstream**, por lo que `X-OmniRoute-Response-Latency` se aproxima a cero (independientemente de la latencia upstream original). Los clientes sensibles a la latencia (pruebas comparativas, supervisión de p50/p99) deben comprobar la cabecera de respuesta `X-OmniRoute-Cache-Latency`:

| Value       | Meaning                                                                        |
| ----------- | ------------------------------------------------------------------------------ |
| `synthetic` | Respuesta proporcionada desde la caché; la latencia no es tiempo upstream real |
| _(absent)_  | Respuesta de una llamada upstream real                                         |

### Omisión de la caché por clave

Las claves de API pueden excluirse de las lecturas de la caché semántica mediante `cacheDefaultMode`:

| Value    | Behavior                                                                     |
| -------- | ---------------------------------------------------------------------------- |
| `legacy` | Comportamiento normal de la caché (predeterminado)                           |
| `bypass` | Omitir completamente la búsqueda en la caché; siempre contactar con upstream |

Se establece al crear la clave (`POST /api/keys`) o actualizarla (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Omisión de la caché por solicitud

Cualquier solicitud puede omitir la caché independientemente de la configuración de la clave:

```
X-OmniRoute-No-Cache: true
```

## Compatibilidad de gestión con CLIProxyAPI

OmniRoute responde a los tres endpoints de gestión de [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) que los paneles de uso consultan para leer los límites de suscripción de Claude y Codex (por ejemplo, el origen de límites de uso `cliproxy` de T3 Code). Apunta la URL base del cliente a OmniRoute y utiliza una clave de API con el ámbito `manage` como clave de gestión. Las rutas se sirven en `/v0/management/*` y en `/api/v0/management/*`.

| Method | Path                         | Description                                                                                                                                          |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Conexiones OAuth de Claude y Codex como `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Sin tokens                           |
| POST   | `/v0/management/api-call`    | Cuerpo `{ auth_index, method, url, header?, data? }`. Envía una solicitud permitida con el token de la cuenta y devuelve `{ status_code, body }`     |
| POST   | `/v0/management/reset-quota` | Cuerpo `{ auth_index }`. Borra el tiempo de espera de la conexión, los bloqueos del modelo y los tiempos de espera por ámbito de Codex de una cuenta |

- `auth_index` es el identificador de conexión de OmniRoute. `provider` es `claude` o `codex` (solo conexiones OAuth; el proveedor de clave de API `anthropic` no aparece en la lista). Para Codex, `id_token.chatgpt_account_id` es el identificador de espacio de trabajo almacenado y `plan_type` es el plan almacenado.
- `api-call` no es un proxy genérico. Solo acepta Claude `GET https://api.anthropic.com/api/oauth/usage` y Codex `GET https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` y `POST .../wham/rate-limit-reset-credits/consume`, cada uno únicamente para una cuenta del proveedor correspondiente. Cualquier otra solicitud devuelve `403` sin contactar con upstream. La cabecera `Authorization` del solicitante (incluido el marcador de posición `$TOKEN$`) se ignora: OmniRoute inyecta el token de acceso de la conexión, lo actualiza primero cuando está cerca de caducar y reenvía únicamente las cabeceras permitidas (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`). Si falta `Chatgpt-Account-Id`, se utiliza de forma predeterminada el identificador de espacio de trabajo almacenado. Las solicitudes agotan el tiempo de espera después de 15 segundos y utilizan el proxy de la conexión.
- `reset-quota` deja intactos los estados terminales (banned, expired, credits_exhausted). Un `auth_index` desconocido devuelve `404`.

**Autenticación:** se requiere una sesión del panel o una clave de API con el ámbito `manage`, incluso cuando el inicio de sesión está deshabilitado (las rutas están en `ALWAYS_PROTECTED_API_PATHS`). Las claves exclusivamente de inferencia reciben `403`. Fuente: `src/lib/cliproxyCompat/managementApi.ts`.

Para los modelos sincronizados/importados, `PUT /api/provider-models` acepta `provider`, `modelId` y
`maxOutputTokenOverride`: un entero positivo establece el límite manual de tokens de salida, y `null`
lo elimina para restaurar el valor predeterminado. `GET /api/provider-models?provider=<provider>` devuelve estos
valores en `modelOutputOverrides`, incluidos los modelos sin una fila de modelo personalizado. La anulación
utiliza la capacidad de tiempo de ejecución `max_output_tokens` y persiste después de una resincronización del modelo. La
página del proveedor compatible con OpenAI ofrece los mismos controles de edición/eliminación y marca los modelos con compatibilidad explícita con visión.

En un nodo de proveedor compatible, las rutas de escritura (`POST`, `PUT`, `PATCH`, `DELETE` y
`/api/provider-models/validate-and-add`) almacenan el identificador del modelo como el identificador ascendente sin prefijo: un identificador
pegado desde una lista con prefijo ve su cadena inicial de prefijos propios del nodo reducida a uno, y
las respuestas devuelven el identificador almacenado. Los identificadores con barras de los proveedores canónicos (por ejemplo, `nvidia/nemotron-…`) se
almacenan literalmente. `/v1/models` nunca emite un identificador apilado `<prefix>/<prefix>/<model>`.

Los nodos personalizados de Chat Completions adaptan las exclusiones explícitas del razonamiento al backend ascendente. Una
prueba de conexión correcta selecciona automáticamente los controles de plantilla de chat para cada ID de modelo exacto
cuya entrada de `/models` demuestre un valor reconocido de `owned_by`: `vllm`, `sglang` o `llamacpp`.
Los wrappers transparentes compatibles con OpenAI pueden conservar la entrada de modelo original dentro de un objeto
`openai` anidado; la detección sigue hasta tres de estos envoltorios. Los modelos con una propiedad de propietario
ausente, desconocida o en conflicto mantienen el comportamiento normal de OpenAI. La detección reutiliza la solicitud
de catálogo existente, no genera tokens de completado y se invalida cuando cambia el endpoint de conexión.

Para fijar el comportamiento de un backend que no expone esos metadatos, usa la API existente de actualización parcial
del proveedor:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envía ese cuerpo con `PUT /api/providers/<connection-id>`. En esa conexión, un esfuerzo de razonamiento explícito de
`none` se envía como `chat_template_kwargs.thinking=false` y
`chat_template_kwargs.enable_thinking=false`. Los valores explícitos de plantilla nativa siguen teniendo prioridad,
salvo que una regla de razonamiento del servidor fuerce un esfuerzo. La configuración solo se aplica cuando una
conexión personalizada compatible con OpenAI envía un cuerpo de Chat Completions; las solicitudes de Responses y los
proveedores normales conservan su formato de solicitud nativo. Establece `reasoningControl` en `openai` para forzar el
paso directo normal de `reasoning_effort` de OpenAI, u omítelo/establécelo en `null` para usar la detección automática.

Las solicitudes del clasificador de modo automático de Claude Code desactivan de forma predeterminada el pensamiento
nativo cuando no contienen controles de razonamiento explícitos. La detección usa el marcador de sistema del
clasificador en las solicitudes con formato de Claude, no los nombres de modelo ni los límites de completado. Los
controles explícitos del cuerpo, los encabezados de esfuerzo/pensamiento compatibles, las reglas de enrutamiento y el
esfuerzo de modelo resuelto mantienen su prioridad existente. Ambas etapas del clasificador conservan sus prompts,
límites de completado y secuencias de detención, así como los veredictos reales de permisos del backend ascendente;
la segunda etapa aún puede producir el razonamiento visible solicitado como texto normal.

#### Procedencia de los límites del modelo

`GET /api/models?withLimits=1` (también `true`; `0`/`false` u omitirlo mantiene sin cambios la carga útil
predeterminada) añade `contextWindow`, `maxInputTokens`, `maxOutputTokens` y un objeto `capsSource` a cada fila de
modelo. `capsSource` indica la regla que proporcionó cada límite, de modo que un límite inesperado (por ejemplo, 128k
en un modelo de 1M) pueda rastrearse hasta su origen. Los valores resueltos son los mismos que usa el enrutamiento;
la marca solo añade campos y nunca cambia un valor. Cualquier otro valor de `withLimits` se rechaza con `400`.

| Valor de `capsSource`                        | Origen                                                                        |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| `override:context`                           | Anulación persistida de la ventana de contexto (`model_context_overrides`)    |
| `override:max_input` / `override:max_output` | Anulación persistida de la capacidad `max_input_tokens` / `max_output_tokens` |
| `static-authoritative:<provider>/<model>`    | Tabla estática autorizada de ventanas de contexto                             |
| `synced:<provider>/<model>`                  | Fila de capacidades sincronizada de models.dev                                |
| `registry:<provider>/<model>`                | Entrada del registro del proveedor                                            |
| `spec:<model>`                               | Especificación estática del modelo                                            |
| Prefijo `effort-base:`                       | Fila tomada del modelo base de una variante con sufijo de esfuerzo            |
| `none`                                       | Ninguna fuente declara el límite (el valor es `null`)                         |

Implementación: `getResolvedModelCapabilitiesWithLimitSources()` en `src/lib/modelCapabilities.ts`
y las cadenas de precedencia en `src/lib/modelCapabilityLimits.ts`.

### Versión y canal de lanzamiento

```bash
GET /api/system/version
```

Ruta de administración exclusiva para loopback (autenticación de administrador). Devuelve la versión en ejecución, la versión publicada más reciente y el estado de actualización automática. `releaseChannel` y `channels` son campos aditivos (rail 3.8.54); `channel` conserva su significado: el modo de implementación que utiliza el actualizador del panel (`npm`, `source` o `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal de npm de la compilación en ejecución: `nightly` para versiones `-nightly.*`, `next` para otras versiones preliminares (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para una versión estable de una versión principal anterior a `channels.latest`; en cualquier otro caso, `latest`. Se aplican las mismas reglas que en `scripts/release/dist-tag.mjs`, que selecciona la etiqueta de distribución de npm en el momento de la publicación.
- `channels` — versión publicada más reciente de cada etiqueta de distribución, obtenida de `npm view omniroute dist-tags` (con fallback HTTP al registro), almacenada en caché con el mismo TTL de 10 minutos que `latest`. `latest` siempre está presente (recurre al campo `latest` y luego a `"unavailable"`); `next`, `nightly` y `lts` solo aparecen cuando existe esa etiqueta de distribución. Una solicitud con `Cache-Control: no-cache` actualiza ambas consultas.

El modelo de canales (`latest` = v3 hasta la disponibilidad general de 4.0, `next` = rc, `nightly` = compilaciones de `develop`, `lts` = parches de v3 después de la disponibilidad general de 4.0) se describe en `docs/ops/RELEASE_STRATEGY.md`.

## Transcripción de audio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transcribe archivos de audio utilizando cualquier proveedor STT configurado. El primer segmento de la ruta selecciona el proveedor nativo (`openai/…`, `deepgram/…`). Las pasarelas que vuelven a exportar el modelo de otro proveedor utilizan un id cualificado
(`openrouter/deepgram/nova-3`).

**Solicitud:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Respuesta:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Ids de modelo de ejemplo:** `openai/whisper-1` (requiere una clave de OpenAI),
`openrouter/deepgram/nova-3` (requiere una clave de OpenRouter),
`deepgram/nova-3` (requiere una clave nativa de Deepgram). Una solicitud básica a
`deepgram/nova-3` **no** utiliza OpenRouter.

**Formatos compatibles:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

Utiliza estos alias cuando una integración no pueda inyectar un encabezado `Authorization` y necesite incluir la clave de API en la URL base.

```bash
# Alias de catálogo con estilo OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Alias de chat con estilo OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Alias con estilo Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Ejemplo:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Notas:

- Los alias tokenizados reutilizan los mismos controladores que `/v1/*` y `/api/tags`; las estructuras de respuesta permanecen idénticas.
- Prefiere `Authorization: Bearer ...` siempre que el cliente admita encabezados personalizados.
- Los tokens basados en URL pueden aparecer en los registros del proxy inverso, el historial del navegador y la telemetría fuera de OmniRoute. Trátalos como una opción de compatibilidad, no como el modo de autenticación predeterminado.

## Límites de tokens

Presupuestos de **tokens** por clave de API (distintos del presupuesto basado en USD mencionado anteriormente). Se aplican en línea en la ruta de la solicitud: cuando el uso actual de la ventana de una clave alcanza su límite, las solicitudes se rechazan con `429 Too Many Requests`. Los límites pueden restringirse a un `model` específico, a un `provider` o aplicarse `global`mente a toda la clave; cuando varios límites coinciden con una solicitud, se aplica el más restrictivo.

```bash
# Listar los límites de tokens de una clave (incluye el uso actual de la ventana)
GET /api/usage/token-limits?apiKeyId=key-123

# Crear o actualizar un límite de tokens
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Eliminar un límite de tokens por id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Notas del esquema** (`setTokenLimitSchema`): `apiKeyId` y `scopeType` (`model` | `provider` | `global`) son obligatorios. `scopeValue` es obligatorio a menos que `scopeType` sea `global` (por ejemplo, un id de modelo para el ámbito `model` o un id de proveedor para el ámbito `provider`). `tokenLimit` debe ser un entero positivo (convertido desde una cadena). Opcionales: `id` (omitir para crear, proporcionar para actualizar), `resetInterval` (`daily` | `weekly` | `monthly`, valor predeterminado `monthly`), `resetTime` (`HH:MM`), `enabled` (valor predeterminado `true`). Las respuestas de `GET` enriquecen cada límite con `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` y `nextResetAt`. Este es un endpoint de clase de gestión (la autenticación se aplica de forma centralizada mediante el flujo de autorización).

## Procesamiento de solicitudes

1. El cliente envía la solicitud a `/v1/*`
2. El controlador de ruta llama a `handleChat`, `handleEmbedding`, `handleAudioTranscription` o `handleImageGeneration`
3. Se resuelve el modelo (proveedor/modelo directo o alias/combinación)
4. Las credenciales se seleccionan de la base de datos local aplicando el filtrado de disponibilidad de cuentas
5. Para el chat: `handleChatCore` comprueba la caché semántica/de firmas y resuelve la configuración de compresión de la combinación
6. La compresión proactiva se ejecuta antes de la traducción al proveedor cuando está habilitada (`lite`, Caveman, RTK o apilada)
7. El ejecutor del proveedor envía la solicitud ascendente
8. La respuesta se traduce de nuevo al formato del cliente (chat) o se devuelve tal cual (incrustaciones/imágenes/audio)
9. Se registran el uso, los análisis de compresión y los registros de solicitudes
10. Se aplica el mecanismo de respaldo en caso de errores según las reglas de la combinación

Referencia completa de la arquitectura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Resiliencia (ampliada)

OmniRoute expone tres mecanismos independientes para fallos temporales; los endpoints de administración siguientes permiten leerlos y sobrescribirlos:

| Ámbito                   | Almacenamiento del estado                          | Lectura                                   | Restablecer / borrar                                                         |
| ------------------------ | -------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- |
| Disyuntor del proveedor  | `domain_circuit_breakers` + en memoria             | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                                 |
| Enfriamiento de conexión | `rateLimitedUntil` en las conexiones del proveedor | `/api/rate-limits`, `/api/providers/[id]` | (se vuelve a habilitar de forma diferida; borrar mediante PUT del proveedor) |
| Bloqueo del modelo       | Registro de disponibilidad de modelos en memoria   | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                     |

`PATCH /api/resilience` acepta sobrescrituras del disyuntor del proveedor mediante `providerBreaker.oauth` y `providerBreaker.apikey`. Cada perfil admite `degradationThreshold`, `failureThreshold` y `resetTimeoutMs`; los mismos campos están disponibles en Dashboard → Settings → Resilience.

```bash
# Borrar el bloqueo de un solo modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Borrar todos los bloqueos
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Para consultar la referencia conceptual completa y los valores predeterminados del disyuntor, consulta [`CLAUDE.md`](../../CLAUDE.md) → "Estado de tiempo de ejecución de Resilience" y [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Cola de limitación de velocidad y red de seguridad de habilitación automática

- **Ruta de escritura compatible**: `POST /api/rate-limits` con el cuerpo `{"connectionId": "<id>", "enabled": true|false}` es el endpoint de administración compatible para alternar la protección contra la limitación de velocidad de una conexión. `PUT /api/providers/[id]` no modifica ni alterna deliberadamente `rateLimitProtection` (#11278).
- **Semántica de `enabled: false`**: establecer `enabled: false` elimina la protección explícita de la conexión, pero **no** excluye una conexión activa con clave API de la red de seguridad global de habilitación automática (`autoEnableApiKeyProviders = true`). En `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` y `undefined` son equivalentes; las conexiones activas con clave API sin protección explícita siguen protegidas por la red de seguridad de habilitación automática.
- **Deshabilitación global**: para ejecutar conexiones con clave API sin colas de limitación de velocidad, deshabilita globalmente la red de seguridad mediante `RATE_LIMIT_AUTO_ENABLE=false` (entorno) o `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`).

## Autenticación

Consulta [Autenticación de gestión](../guides/MANAGEMENT-AUTH.md) para conocer las cuatro
familias de credenciales (sesión del panel, token de CLI local, token de acceso
`oma_live_…`, clave de API con ámbito de gestión) y en qué se diferencian de las claves de inferencia.

- Las rutas del panel (`/dashboard/*`) usan la cookie `auth_token`
- El inicio de sesión usa el hash de contraseña guardado; como alternativa, `INITIAL_PASSWORD`
- `requireLogin` se puede alternar mediante `/api/settings/require-login`
- Las rutas `/v1/*` requieren opcionalmente una clave de API Bearer cuando `REQUIRE_API_KEY=true`
- En esta referencia, «token de gestión» / «clave de API con ámbito de gestión» significa una de las familias de esa guía, no un tipo de secreto adicional no definido

> **Cambio incompatible (v3.8.0)** — `/api/v1/agents/tasks/*` y los endpoints de gestión del tiempo de espera ahora requieren **autenticación de gestión** (cookie `auth_token` del panel o una clave de API con ámbito de gestión). Los clientes que anteriormente llamaban a estas rutas sin autenticación recibirán `401 Unauthorized`. Consulta el commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
