> **সংক্ষেপে**: OmniRoute প্রতিটি অনুরোধের টোকেন ব্যবহার ট্র্যাক করে, খরচ গণনা করে, প্রতি-API-কীর কোটা প্রয়োগ করে এবং ড্যাশবোর্ডে অ্যানালিটিক্স প্রদর্শন করে। এই নির্দেশিকায় এগুলো কীভাবে কাজ করে তা ব্যাখ্যা করা হয়েছে।

**উৎসসমূহ:**

- `open-sse/services/usage.ts` (~70KB) — প্রধান ব্যবহার ট্র্যাকিং
- `src/lib/usageAnalytics.ts` (~10KB) — ড্যাশবোর্ডের জন্য সমষ্টিকরণ
- `src/lib/db/quotaSnapshots.ts` — ঐতিহাসিক কোটা ডেটা
- `src/lib/db/usage*.ts` — ব্যবহার-সম্পর্কিত একাধিক DB মডিউল

## সংক্ষিপ্ত বিবরণ

OmniRoute-এর মধ্য দিয়ে প্রবাহিত প্রতিটি অনুরোধ একটি **ব্যবহার রেকর্ড** তৈরি করে, যা ধারণ করে:

- **পরিচয়**: কোন API কী, প্রোভাইডার, মডেল ও কম্বো
- **টোকেন**: প্রম্পট টোকেন, কমপ্লিশন টোকেন, ক্যাশ করা টোকেন ও মোট টোকেন
- **খরচ**: USD পরিমাণ (মূল্য নির্ধারণের ডেটা থেকে গণনা করা)
- **সময়**: ল্যাটেন্সি, শুরু/শেষের টাইমস্ট্যাম্প
- **স্থিতি**: সফল, ত্রুটি, রেট-লিমিটেড ইত্যাদি

এই রেকর্ডগুলোকে **অ্যানালিটিক্সে** সমষ্টিবদ্ধ করা হয়, **কোটা স্ন্যাপশট** হিসেবে সংরক্ষণ করা হয় এবং **প্রতি-কীর বাজেট সীমা** প্রয়োগ করতে ব্যবহার করা হয়।

```
অনুরোধ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    অ্যানালিটিক্স  কোটা   বিলিং
                    (ড্যাশবোর্ড) (প্রয়োগ) (এক্সপোর্ট)
```

## কী কী রেকর্ড করা হয়

`usage.ts` সার্ভিস প্রতিটি অনুরোধের জন্য একটি **ব্যবহার ইভেন্ট** সংগ্রহ করে:

| ক্ষেত্র            | ধরন     | উৎস                                                        |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | রেকর্ড করার সময় তৈরি করা UUID                             |
| `apiKeyId`         | string  | যে API কী দিয়ে অনুরোধটি শুরু করা হয়েছে                   |
| `provider`         | string  | প্রোভাইডার ID (openai, anthropic, ইত্যাদি)                 |
| `model`            | string  | মডেল ID (gpt-5, claude-opus-4-6, ইত্যাদি)                  |
| `comboId`          | string? | কোনো কম্বোর মাধ্যমে রাউট করা হলে সেই কম্বোর ID             |
| `promptTokens`     | number  | আপস্ট্রিম প্রতিক্রিয়া থেকে                                |
| `completionTokens` | number  | আপস্ট্রিম প্রতিক্রিয়া থেকে                                |
| `cachedTokens`     | number  | ক্যাশ হিট টোকেন (Anthropic প্রম্পট ক্যাশিং, ইত্যাদি)       |
| `totalTokens`      | number  | প্রম্পট + কমপ্লিশন                                         |
| `costUsd`          | number  | মূল্য নির্ধারণের ডেটা থেকে গণনা করা                        |
| `latencyMs`        | number  | অনুরোধের শুরু থেকে শেষ পর্যন্ত সময়কাল                     |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | স্ট্যাটাস != success হলে ত্রুটির শ্রেণি                    |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | প্লাগইন দ্বারা সংযোজিত কাস্টম ডেটা                         |

### টোকেন কোথা থেকে আসে

**রেসপন্স হ্যান্ডলার**-এ আপস্ট্রিম প্রোভাইডারের প্রতিক্রিয়া থেকে টোকেন সংগ্রহ করা হয়:

```ts
// open-sse/handlers/chatCore.ts থেকে
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

যেসব প্রোভাইডার ব্যবহারের তথ্য ফেরত দেয় না (কিছু ওয়েব-কুকি প্রোভাইডার), তাদের ক্ষেত্রে OmniRoute একটি `~4 chars per token` আনুমানিক নিয়ম ব্যবহার করে টোকেনের সংখ্যা **অনুমান করে** (দেখুন `open-sse/services/autoCombo/pipelineRouter.ts`)।

### ক্যাশ করা টোকেন

OmniRoute `prompt_tokens` থেকে আলাদাভাবে `cached_tokens` ট্র্যাক করে, কারণ:

- Anthropic প্রম্পট ক্যাশিংয়ে ক্যাশ করা টোকেনের জন্য কম হারে চার্জ করা হয় (স্বাভাবিকের 10%)
- কিছু প্রোভাইডার `cache_read_input_tokens` ফেরত দেয়, যার মূল্য আলাদাভাবে নির্ধারণ করা উচিত
- অ্যানালিটিক্সে **ক্যাশ হিটের হার** = `cached_tokens / prompt_tokens` দেখানো যায়

### ক্যাশ-রাইট স্তরের ডায়াগনস্টিকস

অ্যানালিটিক্স ড্যাশবোর্ডের প্রম্পট-ক্যাশ স্বাস্থ্য প্যানেল প্রোভাইডার-রিপোর্ট করা
5-মিনিট এবং 1-ঘণ্টার ক্যাশ রাইট আলাদা করে দেখায়। Anthropic-এর
`usage.cache_creation.ephemeral_5m_input_tokens` এবং
`usage.cache_creation.ephemeral_1h_input_tokens` স্ট্রিমিং ও
নন-স্ট্রিমিং ব্যবহারের তথ্য রূপান্তরের সময় অক্ষুণ্ণ রাখা হয় এবং কল-লগ সারসংক্ষেপের সঙ্গে সংরক্ষণ করা হয়। সম্মিলিত
ক্যাশ-রাইটের মোট সংখ্যা ওই বিভাগগুলোতে দ্বিতীয়বার যোগ করা হয় না।

পুরোনো রেকর্ডসহ যেসব কলে শুধু একটি সম্মিলিত রাইট কাউন্টার থাকে, সেগুলোর স্তর অজানা
থাকে। আংশিক বিভাজনের ক্ষেত্রে বরাদ্দ না হওয়া অবশিষ্ট অংশ অজানা রাখা হয়; অবৈধ বা
পরস্পরবিরোধী কাউন্টারগুলোকে নীরবে কোনো TTL নির্ধারণ না করে চিহ্নিত করা হয়। অনুরোধ-পক্ষের
TTL চিহ্নগুলো কোনো বিলকৃত স্তরের প্রমাণ নয়।

প্যানেলের API-সমতুল্য রাইটের আনুমানিক খরচ শুধু রিপোর্ট করা, মূল্য নির্ধারিত স্তরগুলোকে অন্তর্ভুক্ত করে,
পুরো অনুরোধকে নয়। নেটিভ Claude/Anthropic মডেলের মূল্য নির্ধারণের ক্ষেত্রে এটি 5-মিনিটের রাইটের জন্য
ইনপুট হারের 1.25 গুণ এবং 1-ঘণ্টার রাইটের জন্য ইনপুট হারের দ্বিগুণ ব্যবহার করে। অনুপস্থিত
মূল্যকে অনুপলব্ধ হিসেবে ধরা হয়, শূন্য হিসেবে নয়। প্রতিটি নতুন কল লগ করার সময় মূল্য সংরক্ষণ করা হয়;
পুরোনো রেকর্ডের মূল্য পুনর্নির্ধারণ করা হয় না। তাই সাবস্ক্রিপশন অ্যাকাউন্টে
সেই পরিমাণ নগদ ব্যয় বা সাবস্ক্রিপশন কোটা খরচ না হলেও একটি API-সমতুল্য আনুমানিক খরচ
থাকতে পারে। বিদ্যমান কোটা, বাজেট এবং প্রোভাইডারের সঠিক খরচের গণনা অপরিবর্তিত থাকে।

এই ডায়াগনস্টিকস বিদ্যমান সীমাবদ্ধ ক্যাশ-স্বাস্থ্য সারসংক্ষেপ এবং কল-লগ
সংরক্ষণ ব্যবস্থা ব্যবহার করে। এগুলো অনুরোধের ডিফল্ট TTL, রাউটিং বা অ্যাকাউন্ট নির্বাচন পরিবর্তন করে না।
প্রোভাইডারের কাছে পাঠানোর সীমানায় ক্লায়েন্টের অনুরোধ করা TTL এবং কার্যকর বহির্গামী TTL
সংগ্রহের কাজ স্থগিত রাখা হয়েছে; এই প্যানেল প্রাপ্তির রসিদে উল্লিখিত স্তর রিপোর্ট করে, কার্যকর বহির্গামী TTL নয়।

বাস্তবায়ন: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, এবং `open-sse/utils/cacheWriteUsage.ts`।

## খরচ গণনা

LiteLLM থেকে সিঙ্ক করা **মূল্য নির্ধারণের ডেটা** (`src/lib/pricingSync.ts`) ব্যবহার করে খরচ গণনা করা হয়:

| মডেল              | ইনপুট $/1M | আউটপুট $/1M | ক্যাশড $/1M |
| ----------------- | ---------- | ----------- | ----------- |
| gpt-5             | $2.50      | $10.00      | —           |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50       |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30       |
| gemini-2.5-pro    | $1.25      | $10.00      | —           |

খরচের সূত্র (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **প্রম্পট থেকে ক্যাশড অংশ বাদ দেওয়া হয় কেন?** ক্যাশড অংশের মূল্য আলাদাভাবে নির্ধারিত হয়; পুরো প্রম্পটের ওপর ইনপুট মূল্য প্রয়োগ করলে অতিরিক্ত গণনা হবে।

### মূল্য সিঙ্ক

`/api/pricing/sync` এন্ডপয়েন্টের মাধ্যমে LiteLLM থেকে মূল্য নির্ধারণের ডেটা স্বয়ংক্রিয়ভাবে সিঙ্ক করা হয় (এটি বিল্ট-ইন cron টাস্ক দ্বারা ট্রিগার হয়, ব্যবহারকারীর জন্য উন্মুক্ত কোনো env var দ্বারা নয়):

```bash
# ম্যানুয়াল ট্রিগার
curl -X POST http://localhost:20128/api/pricing/sync
```

যেসব মডেলের জন্য মূল্য নির্ধারণের ডেটা নেই, সেগুলোর ক্ষেত্রে OmniRoute অভ্যন্তরীণ গড় হার ব্যবহার করে **আনুমানিক খরচ নির্ধারণ** করে (LiteLLM-এর মূল্য নির্ধারণের ডেটা থেকে সংগৃহীত)।

## তারিখের পরিসরভিত্তিক সমষ্টিকরণ

`usageAnalytics.ts` মডিউলটি অপরিশোধিত ব্যবহার-সংক্রান্ত ডেটা থেকে ড্যাশবোর্ড উইজেট গণনা করে। এটি 7টি সময়ের পরিসর সমর্থন করে:

| পরিসর    | সময়সীমা                       | ব্যবহারের ক্ষেত্র                           |
| -------- | ------------------------------ | ------------------------------------------- |
| `1d`     | গত 24 ঘণ্টা                    | ঘণ্টাভিত্তিক খরচের আকস্মিক বৃদ্ধি শনাক্তকরণ |
| `7d`     | গত 7 দিন                       | সাপ্তাহিক পর্যালোচনা                        |
| `30d`    | গত 30 দিন                      | মাসিক বিলিং                                 |
| `90d`    | গত 90 দিন                      | ত্রৈমাসিক বিশ্লেষণ                          |
| `ytd`    | চলতি বছরের 1 জানুয়ারি থেকে    | বার্ষিক বাজেট পর্যবেক্ষণ                    |
| `all`    | সম্পূর্ণ সময়কাল               | সর্বকালীন পরিসংখ্যান                        |
| `custom` | ব্যবহারকারী-নির্ধারিত শুরু/শেষ | নিরীক্ষা, তাৎক্ষণিক প্রয়োজনভিত্তিক কোয়েরি |

যেকোনো তারিখের পরিসরের জন্য, অ্যানালিটিক্স স্তর গণনা করে:

| উইজেট                        | বিবরণ                                                    |
| ---------------------------- | -------------------------------------------------------- |
| **সারসংক্ষেপ কার্ড**         | মোট অনুরোধ, মোট খরচ, মোট টোকেন, সাফল্যের হার             |
| **দৈনিক প্রবণতার চার্ট**     | প্রতিদিনের খরচ + টোকেন, মডেল অনুযায়ী স্তূপীকৃত          |
| **কার্যকলাপের হিটম্যাপ**     | দিনের ঘণ্টা × সপ্তাহের দিনের গ্রিড, রং = অনুরোধের সংখ্যা |
| **মডেলভিত্তিক বিভাজন**       | মডেল অনুযায়ী খরচের পাই চার্ট                            |
| **প্রদানকারীভিত্তিক বিভাজন** | প্রদানকারী অনুযায়ী অনুরোধের বার চার্ট                   |
| **শীর্ষ API কী**             | খরচ অনুযায়ী শীর্ষ 10টি কী-এর সারণি                      |
| **ত্রুটি বিশ্লেষণ**          | সময়ের সঙ্গে ত্রুটির হার, প্রধান ত্রুটির শ্রেণি          |

### প্রোগ্রামভিত্তিক অ্যাক্সেস

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(

## কোটা প্রয়োগ

প্রতিটি API কী-এর কোটা দুটি স্থানে প্রয়োগ করা হয়:

1. **নমনীয় সীমা** (`quotaWarnAt`): ব্যবহার নির্ধারিত সীমা অতিক্রম করলে ড্যাশবোর্ডে সতর্কবার্তা
2. **কঠোর সীমা** (`quotaLimit`): সীমা অতিক্রম করলে HTTP 429 দিয়ে অনুরোধ প্রত্যাখ্যান

### কনফিগারেশন

```ts
// প্রতিটি API কী-এর জন্য
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — সতর্কবার্তা দেখান
  quotaLimit: 10_00,    // $10.00 — সম্পূর্ণ বন্ধ
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### প্রয়োগের প্রবাহ

```
অনুরোধ ──▶ quotaCheck()
              │
              ├── সীমার মধ্যে?  ──▶ অনুমতি দিন
              │
              └── সীমা অতিক্রম করেছে?  ──▶ 429 Too Many Requests
                                   Retry-After হেডারসহ
```

### কোটার স্ন্যাপশট

প্রবণতা বিশ্লেষণের জন্য `quotaSnapshots` সারণি **কোটার ঐতিহাসিক অবস্থা** সংরক্ষণ করে:

| ফিল্ড | বিবরণ |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | যে কী পর্যবেক্ষণ করা হচ্ছে |
| `window` | "day" | "week" | "month" |
| `used` | এই সময়সীমায় ব্যবহৃত খরচ (সেন্ট) |
| `limit` | সীমা (সেন্ট) |
| `resetAt` | কখন সময়সীমা পুনরায় শুরু হয় |
| `createdAt` | কখন স্ন্যাপশট নেওয়া হয়েছিল |

খরচ > 0 এমন **প্রতিটি অনুরোধে** স্ন্যাপশট নেওয়া হয় এবং এগুলো ব্যবহার করা হয়:

- ড্যাশবোর্ডে কোটার অগ্রগতি বার প্রদর্শন করতে
- 30 দিনের কোটার প্রবণতার চার্ট দেখাতে
- ব্যবহার সীমার কাছাকাছি পৌঁছালে সতর্কতা চালু করতে

## সংরক্ষণ ও পরিষ্কারকরণ

প্রতি অনুরোধে ব্যবহারের ডেটা প্রায় 1-10KB বৃদ্ধি পায়। বৃহৎ পরিসরে এটি উল্লেখযোগ্য হতে পারে।

### সংরক্ষণের সেটিংস

ব্যবহারের ইতিহাস সংরক্ষণের মেয়াদ UI-এর ডেটাবেস সেটিংস থেকে বা `/api/settings/database`-এর মাধ্যমে কনফিগার করা হয়।

ডিফল্টভাবে, ব্যবহারের ইতিহাস **90 দিন** সংরক্ষণ করা হয়।

### পরিষ্কারকরণ

পুরোনো রেকর্ড `src/lib/db/cleanup.ts` দ্বারা পরিষ্কার করা হয়:

- ব্যাকগ্রাউন্ড cron প্রক্রিয়ার মাধ্যমে চালু হয়
- কনফিগার করা `usageHistory` সংরক্ষণ সেটিংসের মেয়াদের চেয়ে পুরোনো রেকর্ড `usage_history` থেকে মুছে ফেলে

### স্টোরেজের আনুমানিক হিসাব

| অনুরোধের হার       | 30 দিনের স্টোরেজ | 90 দিনের স্টোরেজ |
| ------------------ | ---------------- | ---------------- |
| 100 অনুরোধ/দিন     | ~3MB             | ~9MB             |

| 10,000 অনুরোধ/দিন  | ~300MB           | ~900MB           |

অত্যধিক ট্রাফিকের ক্ষেত্রে বিবেচনা করুন:

- ডেটাবেস সেটিংসের মাধ্যমে সংরক্ষণের মেয়াদ কমানো

## সমস্যা সমাধান

### "খরচ প্রত্যাশার চেয়ে বেশি"

1. **`/api/usage/analytics?groupBy=model`** পরীক্ষা করুন — ব্যয়বহুল মডেলটি খুঁজে বের করুন
2. **`/api/usage/analytics?groupBy=apiKey`** পরীক্ষা করুন — অতিরিক্ত ব্যবহারকারীকে খুঁজে বের করুন
3. মূল্যসংক্রান্ত তথ্য হালনাগাদ আছে কি না যাচাই করুন: `POST /api/pricing/sync`

### "রেকর্ড পাওয়া যাচ্ছে না"

- ড্যাশবোর্ড → ডেটাবেস → ক্লিনআপ-এর অধীনে DB রিটেনশন সেটিংস পরীক্ষা করুন — নির্দিষ্ট সময় অন্তর চলা ক্লিনআপ টাস্ক পুরোনো রেকর্ড মুছে দেয় (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts`-এ ত্রুটি আছে কি না পরীক্ষা করুন — DB-তে লেখার ব্যর্থতা লগ করা হয়, কিন্তু সরাসরি দেখানো হয় না
- অনুরোধটি সত্যিই `chatCore`-এ পৌঁছেছে কি না যাচাই করুন — কম্বো রাউটিং পরীক্ষা করুন

### "কোটা কার্যকর হচ্ছে না"

- কী-এর `quotaLimit` সেটিং পরীক্ষা করুন
- `quotaWindow` সঠিকভাবে নির্ধারিত আছে কি না যাচাই করুন
- `quotaSnapshots` রেকর্ড খুঁজুন — প্রতিটি অনুরোধে এগুলো তৈরি হওয়ার কথা
