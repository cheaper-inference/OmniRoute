- `src/lib/db/migrationRunner.ts` — সংস্করণভিত্তিক মাইগ্রেশন
- `src/lib/db/migrations/` — ১৬৭টি সংস্করণভিত্তিক SQL ফাইল
- `src/lib/db/encryption.ts` — এনক্রিপশন সহায়ক
- `src/lib/db/backup.ts` — ব্যাকআপ এক্সপোর্ট/ইমপোর্ট
- `src/lib/db/healthCheck.ts` — স্বাস্থ্যসংক্রান্ত ডায়াগনস্টিকস

## SQLite কেন?

OmniRoute বিভিন্ন কারণে PostgreSQL/MySQL-এর পরিবর্তে SQLite বেছে নিয়েছে:

| বিবেচ্য বিষয়         | SQLite                                  | PostgreSQL                             |
| --------------------- | --------------------------------------- | -------------------------------------- |
| **ডিপ্লয়মেন্ট**      | এম্বেডেড — আলাদা সার্ভারের প্রয়োজন নেই | সার্ভার সেটআপের প্রয়োজন               |
| **এনক্রিপশন**         | অ্যাপ্লিকেশন স্তর (AES-256-GCM)         | বিল্ট-ইন TDE                           |
| **পারফরম্যান্স**      | ছোট/মাঝারি কাজের চাপের জন্য দ্রুততর     | বিপুলসংখ্যক সমবর্তী লেখার জন্য উন্নততর |
| **কনকারেন্সি**        | WAL মোড সমবর্তী রিডের অনুমতি দেয়       | পূর্ণাঙ্গ MVCC                         |
| **ব্যাকআপ**           | একক ফাইল কপি                            | `pg_dump` অথবা ফাইলসিস্টেম স্ন্যাপশট   |
| **ব্যবহারের ক্ষেত্র** | প্রতি-ব্যবহারকারী ইনস্টলেশন, এম্বেডেড   | মাল্টি-টেন্যান্ট SaaS                  |

**একক-ব্যবহারকারী, একক-ইনস্ট্যান্স** ডিপ্লয়মেন্টের ক্ষেত্রে (OmniRoute-এর প্রধান ব্যবহারের ক্ষেত্র), SQLite আরও সহজ ও দ্রুত।

### WAL জার্নালিং

`core.ts` ডেটাবেসটি **WAL (Write-Ahead Logging) মোডে** খোলে:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL লেখার সময় **সমবর্তী রিডের** অনুমতি দেয় — এটি ড্যাশবোর্ডের জন্য গুরুত্বপূর্ণ, কারণ অনুরোধগুলো রেকর্ড হওয়ার সময়ই এটি কোয়েরি চালায়।

ডিফল্ট ক্যাশের আকার **৬৫,৫৩৬ KiB (৬৪ MiB)**। SQLite একটি ঋণাত্মক
`cache_size`-কে KiB-এ একটি আনুমানিক সর্বোচ্চ সীমা হিসেবে ব্যাখ্যা করে এবং চাহিদা অনুযায়ী পেজ বরাদ্দ করে।
**Settings > System & Storage > Cache Size**-এ **১ থেকে
১,০০০,০০০ KiB** পর্যন্ত পূর্ণসংখ্যার মান গ্রহণ করা হয়; সেটিংটি সংরক্ষণ করলে তা সক্রিয় ডেটাবেস সংযোগে প্রয়োগ হয়,
এবং স্টার্টআপের সময় OmniRoute সংরক্ষিত মানটি পুনরুদ্ধার করে।

## ডেটাবেসের অবস্থান

SQLite ফাইলটি এখানে সংরক্ষিত থাকে:

| OS      | পাথ                                                             |
| ------- | --------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                   |
| macOS   | `~/.omniroute/storage.sqlite`                                   |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                       |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR`-এর মাধ্যমে কনফিগারযোগ্য) |

সহযোগী ফাইলসমূহ:

- `storage.sqlite-wal` — write-ahead লগ
- `storage.sqlite-shm` — শেয়ার্ড মেমরি ফাইল
- `call_logs/` — অনুরোধের পেলোড আর্টিফ্যাক্ট (সক্রিয় থাকলে)

**অবস্থান ওভাররাইড করুন:**

```bash
DATA_DIR=/custom/path omniroute
```

### মডিউলের সীমারেখা

একটি মূল আর্কিটেকচারাল নিয়ম হলো: **মডিউলগুলো সরাসরি একে অপরের টেবিল অ্যাক্সেস করে না**। অন্য কোনো মডিউলের ডেটা নিয়ে কাজ করতে হলে, সেই মডিউল থেকে সংশ্লিষ্ট ফাংশন ইমপোর্ট করুন।

```ts
// ❌ ভুল: অন্য মডিউল থেকে সরাসরি SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ সঠিক: providers মডিউলের ফাংশন ব্যবহার করুন
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

এই নিয়মটি কোড রিভিউয়ের মাধ্যমে প্রয়োগ করা হয়—কোনো স্ট্যাটিক যাচাই নেই, তবে লঙ্ঘন শনাক্ত হলে তা চিহ্নিত করা হয়।

## বেস স্কিমা (১৭টি টেবিল)

`core.ts`, `SCHEMA_SQL`-এ ১৭টি বেস টেবিল সংজ্ঞায়িত করে। এগুলো `001_initial_schema.sql` মাইগ্রেশনের মাধ্যমে তৈরি করা হয় এবং মূল স্কিমা গঠন করে।

### মূল টেবিলসমূহ (প্রাথমিক মাইগ্রেশনে তৈরি)

| টেবিল                      | উদ্দেশ্য                                | মূল কলামসমূহ                                                            |
| -------------------------- | --------------------------------------- | ----------------------------------------------------------------------- |

## মাইগ্রেশন

OmniRoute ব্যবহার করে** সংস্করণযুক্ত, অদম্য অভিবাসন** `src/lib/db/migrations/` তে। প্রতিটি মাইগ্রেশন একটি একক SQL ফাইল। দুটি নামকরণ বিন্যাস সহাবস্থান; `_omniroute_migrations` এ রেকর্ড করা সংস্করণ হল সংখ্যাসূচক উপসর্গ।

### মাইগ্রেশন নামকরণ

| বিন্যাস                                           | উদাহরণ                               | জন্য ব্যবহৃত                                                                                                                                                          |
| ------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (ঠিক 3 সংখ্যা)              | `241_seen_models.sql`                | পুরানো সিরিজ `001`–`241`। টাইমস্ট্যাম্প বিন্যাস অবতরণ করার সময় হিমায়িত (`240` এবং `241` এর ঠিক আগে একত্রিত করা হয়েছিল): কোনো নতুন ফাইল একটি ক্রমিক সংখ্যা পায় না। |
| `YYYYMMDDHHMMSS_description.sql` (14 সংখ্যা, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 থেকে তৈরি প্রতিটি স্থানান্তর।                                                                                                                              |

কেন পরিবর্তন: অনুক্রমিক সংখ্যার সাথে, সমান্তরাল PRs একই পরবর্তী সংখ্যা বাছাই করে এবং একত্রিত হওয়ার আগে একটি ব্যতীত সকলকে পুনরায় নম্বর দিতে হয়েছিল। একটি UTC টাইমস্ট্যাম্প প্রতিটি PR এর নিজস্ব সংস্করণ দেয়।

টাইমস্ট্যাম্প বিন্যাসের নিয়ম ( `npm run check:migration-numbering` দ্বারা প্রয়োগ করা হয়েছে, `scripts/check/lib/migrationNaming.mjs` এ জেনারেটরের সাথে ভাগ করা হয়েছে):

- টাইমস্ট্যাম্প হল একটি বাস্তব UTC তারিখ এবং সময়, `20261113000000` এর আগে নয় এবং ভবিষ্যতে 10 মিনিটের বেশি নয়।
- বর্ণনাটি হল ছোট হাতের `snake_case` একটি অক্ষর দিয়ে শুরু (`a-z`, `0-9`, শব্দের মধ্যে একক `_` ), সর্বাধিক 80টি অক্ষর।
- একই টাইমস্ট্যাম্প সহ দুটি ফাইল একটি সদৃশ।
- নো-গ্যাপ নিয়মটি শুধুমাত্র পুরানো সিরিজের ক্ষেত্রে প্রযোজ্য: `001` থেকে `241` পর্যন্ত প্রতিটি সংখ্যা অবশ্যই বিদ্যমান থাকতে হবে, পরিচিত ফাঁক `026`, `055` এবং `121` ছাড়া। `241` (বা কোন পুরানো ফাইল) মুছে ফেলা গেট ব্যর্থ হয়. `001` এবং `241` কখনই `KNOWN_GAPS` অনুমোদিত তালিকায় যোগ করা যাবে না। টাইমস্ট্যাম্পযুক্ত ফাইলগুলি কখনই ফাঁক তৈরি করে না।
- `src/lib/db/migrations/` তে প্রতিটি এন্ট্রি অবশ্যই একটি বৈধ ছোট হাতের `.sql` নামের একটি নিয়মিত ফাইল হতে হবে। একটি ডিরেক্টরি, একটি সিমলিংক, একটি `.SQL` বা `.sql.bak` ফাইল, একটি লুকানো ফাইল বা একটি স্পেস সহ একটি নাম গেটটি ব্যর্থ করে, কারণ রানার এটি নীরবে এড়িয়ে যাবে বা বুট করার সময় ক্র্যাশ করবে।

**অর্ডার প্রয়োগ করুন।** রানার উপসর্গের সাংখ্যিক মান অনুসারে সাজান, পাঠ্য দ্বারা নয়: পুরানো `001`–`241` ফাইলগুলি প্রথমে, তারপর টাইমস্ট্যাম্পের ক্রমানুসারে টাইমস্ট্যাম্প করা ফাইলগুলি, তারপরে `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` সাথে নিবন্ধিত যেকোন নেমস্পেসযুক্ত ডিরেক্টরি (সংস্করণ যেমন `ee-001`)। একটি মুলতুবি মাইগ্রেশন হল যেকোন ফাইল যার সংস্করণ `_omniroute_migrations` তে নেই, তাই একটি পুরানো শাখা থেকে একটি মাইগ্রেশন যা একটি নতুনের পরে একত্রিত হয় তা এখনও বিদ্যমান ডেটাবেসে প্রযোজ্য।

**টাইমস্ট্যাম্প হল ক্রিয়েশন অর্ডার, মার্জ অর্ডার নয়।** যদি আপনার মাইগ্রেশন একটি টেবিল বা কলামের উপর নির্ভর করে যা একটি মাইগ্রেশন দ্বারা তৈরি হয়** নতুন** টাইমস্ট্যাম্প (উদাহরণস্বরূপ, অন্য PR থেকে একটি যা প্রথমে একত্রিত হয়েছে), একটি নতুন ডাটাবেস প্রথমে আপনার চালাবে এবং ব্যর্থ হবে। আপনার PR এখনও খোলা থাকা অবস্থায়, `npm run db:new-migration` দিয়ে ফাইলের নামটি পুনরায় তৈরি করুন যাতে এটি একটি নতুন টাইমস্ট্যাম্প পায়, বা এটি স্বাধীন করে। `npm run test:migrations:fresh` একটি খালি ডাটাবেসে প্রতিটি মাইগ্রেশন প্রয়োগ করে এবং এটিকে ধরে।

### একটি মার্জড মাইগ্রেশন কখনও মুছে ফেলা বা পুনঃনামকরণ করা হয় না

একটি মাইগ্রেশন ফাইল একবার রিলিজ শাখায় বা `main` এ, এটি ইতিমধ্যেই হোমোলগ এবং ডেভেলপার ডাটাবেসে, VPS ইনস্টলে এবং এন্টারপ্রাইজ সিঙ্কে চলে। তারপর থেকে:

- **এটি কখনই মুছবেন না।** আপগ্রেড করা ডাটাবেস এটি রাখার সময় নতুন ইনস্টলগুলি তার স্কিমা হারাবে।
- **এটির নাম পরিবর্তন করবেন না।** `_omniroute_migrations` এর সংস্করণটি আর একটি ফাইলের সাথে মিলবে না, তাই প্রতিটি ডাটাবেস যা ইতিমধ্যে এটি প্রয়োগ করেছে তা আবার চালাবে। অ-আইডিমপোটেন্ট SQL তারপর ডেটা নকল করে বা বুট বন্ধ করে।
- **একটি ভিন্ন স্কিমা প্রয়োজন?** `npm run db:new-migration` দিয়ে একটি নতুন মাইগ্রেশন তৈরি করুন।

পুনঃনামকরণ শুধুমাত্র একটি ফাইলের জন্য নিরাপদ যা এখনও একত্রিত হয়নি, যে ক্ষেত্রে গেটের ইঙ্গিতগুলি উল্লেখ করে। একটি রিলিজ ট্যাগ এখানে কিছুই পরিবর্তন করে না: `release/v*` শাখায় প্রতিটি পুশ Docker `:next` ইমেজ প্রকাশ করে এবং homolog, VPS ইনস্টল এবং এন্টারপ্রাইজ সিঙ্কে চলে, তাই কোনো `vX.Y.Z` ট্যাগ বিদ্যমান থাকার আগে একটি মার্জড মাইগ্রেশন বাস্তব ডাটাবেসে চলে। গেট একটি বেস ফাইলের প্রতিটি অপসারণ ব্যর্থ, ট্যাগ বা না.

- **একটি মার্জড মাইগ্রেশন ফিরিয়ে আনা হচ্ছে।** ফাইল মুছে ফেলা একটি `git revert` গেট ব্যর্থ হয়. ফাইলটি রাখুন এবং একটি নতুন মাইগ্রেশনে এর স্কিমা পূর্বাবস্থায় ফেরান: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` ইত্যাদি সহ। আপগ্রেড করা এবং নতুন ডাটাবেসগুলি একই স্কিমা দিয়ে শেষ হয়।
- **একটি গৃহীত নাম পরিবর্তন: একটি সামঞ্জস্য এন্ট্রি এবং অভিন্ন বিষয়বস্তু৷** যদি একটি মার্জ করা ফাইল অবশ্যই সরানো হয় (উদাহরণস্বরূপ, দুটি মার্জ করা ফাইল একটি টাইমস্ট্যাম্প ভাগ করে এবং রানার একটি সংস্করণ সংঘর্ষে থেমে যায়), তার SQL স্পর্শ না করে পরবর্তীটির নাম পরিবর্তন করুন এবং `src/lib/db/migrationRunner/constants.ts` এ `RENAMED_MIGRATION_COMPATIBILITY` তে `{ fromVersion, fromName, toVersion, toName }` যোগ করুন। পুরানো সংস্করণ প্রয়োগ করা ডেটাবেসগুলি আবার ফাইল চালানোর পরিবর্তে তাদের `_omniroute_migrations` সারি সরানো হয়। গেটটি এমন একটি নাম পরিবর্তনের বিষয়ে সতর্ক করে এবং নতুন টাইমস্ট্যাম্প যাই হোক না কেন সর্বদা এটিতে কম্যুটেশন চেক চালায়: নতুন ইনস্টল ফাইলটি তার নতুন অবস্থানে প্রয়োগ করে, আপগ্রেড করা ডেটাবেসগুলি করে না, তাই পুরানোটির কাছাকাছি একটি নতুন টাইমস্ট্যাম্প বেছে নিন। যদি বিষয়বস্তু পরিবর্তিত হয় (একটি স্কিমা পরিবর্তন এখনও একটি নতুন মাইগ্রেশনে যায়), অথবা যদি এন্ট্রির টার্গেট ফাইলটি ডিস্কে না থাকে তাহলে গেটটি নাম পরিবর্তন করতে ব্যর্থ হয়।
- **একই টাইমস্ট্যাম্পের মধ্যে কখনও নাম পরিবর্তন করবেন না।** একটি পুনঃনাম যা টাইমস্ট্যাম্প রাখে এবং শুধুমাত্র বিবরণ পরিবর্তন করে তা প্রবেশের সাথে বা ছাড়াই গেটকে ব্যর্থ করে। একটি এন্ট্রির সাথে যার `toVersion` এর `fromVersion` এর সমান, রানার পুরানো `_omniroute_migrations` সারিটি মুছে ফেলে এবং ফাইলটি ইতিমধ্যেই চালানো প্রতিটি ডাটাবেসে আবার প্রয়োগ করে। একটি এন্ট্রি ছাড়াই, রানার শুধুমাত্র সংস্করণটি ট্র্যাক করে: এটি সেই ডাটাবেসের ফাইলটি এড়িয়ে যায় (নতুন সামগ্রী কখনই সেখানে চলে না) এবং প্রতিটি বুটে একটি পুনঃসংখ্যার ত্রুটি লগ করে। অন্য টাইমস্ট্যাম্প এবং একটি সামঞ্জস্যপূর্ণ এন্ট্রি ব্যবহার করুন, বা নাম রাখুন।
- **গেট চেক করে যে পুনঃনামকৃত ফাইলটি আবার চালানো হচ্ছে না।** প্রতিটি আচ্ছাদিত পুনঃনামকরণের জন্য, গেটটি নতুন ফাইলের নামটি `--must-not-apply` দিয়ে কমিউটেশন চেকে পাঠায়। চেকটি প্রকৃত রানারের সাথে আপগ্রেড করা ডাটাবেস বুট করে, এবং যদি রানার সেই ফাইলটি আবার প্রয়োগ করে (উদাহরণস্বরূপ, কারণ এন্ট্রিটির একটি ভুল সংস্করণ বা নাম রয়েছে, বা গেটের পাঠ্য পার্সার TypeScript থেকে `constants.ts` আলাদাভাবে পড়েছে), গেটটি `migration renomeada rodaria de novo` সাথে ব্যর্থ হয় এবং আপনাকে এন্ট্রির পুরানো এবং নতুন সংস্করণ এবং নামগুলি পরীক্ষা করতে বলে৷

### বেস বিরুদ্ধে গেট চেক কি

পুল অনুরোধ এবং মার্জ-কিউ রানে, `npm run check:migration-numbering` ডিস্কের `src/lib/db/migrations/` বেস শাখার একই ডিরেক্টরির সাথে তুলনা করে। ভিত্তি হল, এই ক্রমে: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` ভেরিয়েবল, বা, যখন `GITHUB_EVENT_NAME` হয় `pull_request`, `pull_request_target` বা `merge_group`, মার্জ কমিটের প্রথম প্যারেন্ট, ইভেন্ট পেলোডের `merge_group.base_sha`, বা `git merge-base HEAD origin/$GITHUB_BASE_REF`। কোনো মীমাংসাযোগ্য বেস ছাড়াই চালানোর অনুরোধে বা মার্জ-কিউতে গেটটি ব্যর্থ হয়। `--base` ছাড়া CI বাইরে এটি `comparação com a base: pulada (sem --base)` প্রিন্ট করে এবং এই নিয়মগুলি এড়িয়ে যায়।

`--base-latest-tag` নতুন রিলিজ ট্যাগের সাথে তুলনা করে ( semver ক্রমে`vX.Y.Z` ; প্রত্যয়যুক্ত ট্যাগ যেমন নাইটলি গণনা করা হয় না) যেটি `HEAD` এর ইতিহাসে রয়েছে, `--base` মতো একই নিয়মের সাথে। রিলিজ-গ্রিন (`scripts/quality/validate-release-green.mjs`) এইভাবে গেট চালায়, কারণ পুশ এবং নির্ধারিত রানের কোনো পুল অনুরোধের ভিত্তি নেই এবং একটি মার্জ নতুন CI রান ছাড়াই অবতরণ করতে পারে। ইতিহাসে কোন রিলিজ ট্যাগ ছাড়া গেট ব্যর্থ হয়; `git fetch --tags` চালান ( CI এ, `actions/checkout` `fetch-depth: 0` ট্যাগ নিয়ে আসে)।

কম্যুটেশন চেক (`scripts/check/migration-commutation.ts`) বাস্তব ইনস্টল পাথ সহ দুটি অস্থায়ী ডাটাবেস তৈরি করে: একটি** আপগ্রেড** একটি (বেস মাইগ্রেশনের সাথে বুট করুন, তারপর পুল অনুরোধের মাইগ্রেশন সহ একই ফাইলে আবার বুট করুন) এবং একটি** তাজা** একটি (পুল অনুরোধের মাইগ্রেশন সহ একটি বুট)। এটি ফলাফলের স্কিমাগুলির সাথে তুলনা করে: টেবিল এবং কলাম (কলামের ক্রম উপেক্ষা করে), UNIQUE / PRIMARY KEY এবং FOREIGN KEY সীমাবদ্ধতা, প্রতিটি টেবিলের স্বাভাবিক `CREATE TABLE` পাঠ্য (যা CHECK সীমাবদ্ধতা, কোলেশন, জেনারেট করা কলাম এবং সূচী বিকল্পগুলি কভার করে), টেবিল ভিউ, ট্রিগার বিকল্পগুলি। সারি তথ্য তুলনা করা হয় না. যদি সেগুলি মিলে যায়, গেটটি প্রিন্ট করে যে ফাইলটি অকার্যকর কিন্তু যাতায়াত করে এবং পাস করে। যদি তারা ভিন্ন হয়, তাহলে গেটটি পার্থক্যের সাথে ব্যর্থ হয় এবং কেসের জন্য একটি ইঙ্গিত দেয়: একটি বহিরাগত ফাইলের জন্য, এটির নাম `npm run db:new-migration` দিয়ে পুনরায় তৈরি করুন, যা নিরাপদ কারণ ফাইলটি এখনও মার্জ করা হয়নি; একটি সম্পাদিত বেস ফাইলের জন্য, বেস বিষয়বস্তু পুনরুদ্ধার করুন এবং একটি নতুন মাইগ্রেশনে পরিবর্তন করুন; একটি পুনঃনামকৃত ফাইলের জন্য, নাম পরিবর্তন করুন বা অন্য একটি নতুন টাইমস্ট্যাম্প চয়ন করুন যেখানে এটি যাতায়াত করে, অন্য নামের সাথে একই টাইমস্ট্যাম্প কখনই নয়। যদি চেক নিজেই চালাতে না পারে, তাহলে গেটটি CI এ ব্যর্থ হয় এবং শুধুমাত্র স্থানীয়ভাবে সতর্ক করে। একটি সম্পাদিত বেস ফাইলের জন্য, আপগ্রেড করা ডাটাবেসটি সেই ফাইলের বেসের বিষয়বস্তু দিয়ে তৈরি করা হয় এবং দ্বিতীয় বুটটি এটিকে এড়িয়ে যায় কারণ এর সংস্করণটি ইতিমধ্যেই রেকর্ড করা আছে। একটি পুনঃনামকৃত ফাইলের জন্য, আপগ্রেড করা ডাটাবেসটি তার পুরানো নামের অধীনে ফাইলের সাথে তৈরি করা হয় এবং দ্বিতীয় বুটটি এটিকে পুনরায় চালানোর পরিবর্তে সামঞ্জস্যপূর্ণ এন্ট্রির মাধ্যমে তার `_omniroute_migrations` সারিটি সরিয়ে দেয়; গেটটি `--must-not-apply` দিয়ে নতুন নাম পাস করে, তাই দ্বিতীয় বুটটি প্রয়োগ করলে চেক ব্যর্থ হয়। যদি একটি পুল অনুরোধ মাইগ্রেশন আপগ্রেড করা পথে প্রয়োগ করতে ব্যর্থ হয়, অর্থাৎ, প্রতিটি বেস মাইগ্রেশনের পরে (এটি নতুন ইনস্টলে ব্যর্থ হয় বা না হয়), গেটটি `migration do PR não aplica` রিপোর্ট করে এবং আপনাকে বেসের বর্তমান স্কিমার বিপরীতে SQL ঠিক করতে বলে; যদি ফাইলটি পরবর্তী টাইমস্ট্যাম্প সহ অন্য একটি পুল অনুরোধ স্থানান্তরের উপর নির্ভর করে, তাহলে `npm run db:new-migration` দিয়ে এর নাম পুনরায় তৈরি করুন।

স্থানীয়ভাবে একই তুলনা চালানোর জন্য, বেসটি স্পষ্টভাবে পাস করুন, উদাহরণস্বরূপ `npm run check:migration-numbering -- --base origin/<base-branch>`, বা `npm run check:migration-numbering -- --base-latest-tag` সর্বশেষ রিলিজের সাথে তুলনা করতে।

### একটি খোলা PR এর `NNN` মাইগ্রেশন রূপান্তর করা হচ্ছে

স্যুইচের আগে খোলা একটি টান অনুরোধ এখনও একটি অনুক্রমিক ফাইল যেমন `242_add_widgets.sql` বহন করতে পারে। `241` উপরের পুরানো সংখ্যাগুলি প্রত্যাখ্যান করা হয়েছে, তাই মার্জ করার আগে এটি রূপান্তর করুন:

1. **বর্ণনা রেখে জেনারেটরের সাথে ফাইলটির নাম পরিবর্তন করুন।** নতুন নাম পেতে `npm run db:new-migration -- <same description>` চালান, এটিতে SQL সরান এবং পুরানো `NNN_` ফাইলটি মুছুন। বর্ণনাটি অবশ্যই অভিন্ন থাকতে হবে: নীচের সামঞ্জস্যপূর্ণ এন্ট্রি এটিতে মেলে।
2. **একটি সামঞ্জস্যপূর্ণ এন্ট্রি যোগ করুন যদি একটি স্থায়ী ডাটাবেস পুরানো নম্বরটি চালায়।** যদি কোন ডাটাবেস রাখা হয় (homolog, a VPS, একজন অবদানকারীর নিজস্ব ইনস্টল) `NNN_` ফাইলের সাথে PR এর একটি বিল্ড রান করে, তাহলে `src/lib/db/migrationRunner/constants.ts` এ `RENAMED_MIGRATION_COMPATIBILITY` তে `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` যোগ করুন। এই** `237` থেকে `241` এর জন্য প্রয়োজনীয়** : এই স্লটগুলি এখন ক্যানোনিকাল `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` এবং `241_seen_models.sql` ধারণ করে এবং এন্ট্রি ছাড়াই এই ধরনের ডাটাবেস ক্যানোনিকাল মাইগ্রেশনকে চিরতরে এড়িয়ে যায় এবং রূপান্তরিতটিকে আবার চালায়৷ এটি এমন একটি স্লটের জন্যও কাজ করে যা খালি থাকে, যেমন `242`, যখন গন্তব্যটি একটি টাইমস্ট্যাম্প হয়। সন্দেহ হলে, এন্ট্রি যোগ করুন. যেখানে আপনি এটিকে অ্যারেতে যোগ করেন তা কোন ব্যাপার না: যখন একটি এন্ট্রির টার্গেট স্লটে এখনও একটি সারি থাকে যে অন্য এন্ট্রি চলে যায় (উদাহরণস্বরূপ `237` একটি PR সারি ধরে রাখে যখন একটি পুরানো `usage_history_calculated_cost` সারি `237` এ যাওয়ার জন্য অপেক্ষা করে), রানার সেই এন্ট্রিটিকে স্লটটি বিনামূল্যে না হওয়া পর্যন্ত অপেক্ষা করতে দেয়৷ শুধুমাত্র একটি বাস্তব দ্বন্দ্ব, যেমন একটি সারি দ্বারা ধারণকৃত একটি স্লট কোন এন্ট্রি মুভ নয়, অথবা দুটি এন্ট্রি যা স্লট অদলবদল করে, `Cannot reconcile ...` এর সাথে বুট বন্ধ করে দেয়।
3. **SQL বুদ্ধিমত্তাহীন রাখুন** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), কারণ রূপান্তরিত স্থানান্তর একটি ডাটাবেসের সাথে দেখা করতে পারে যেখানে এর স্কিমা ইতিমধ্যেই বিদ্যমান।
4. **সংস্করণ-কীড বিশেষ ক্ষেত্রে সরান।** যদি PR `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) বা `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) তে তার পুরানো নম্বরের জন্য একটি কেস যোগ করে, তাহলে নতুন টাইমস্ট্যাম্পে কী পরিবর্তন করুন।

`tests/unit/db/codex-fence-migration-rename.test.ts` একটি পরিবর্তিত স্থানান্তরের জন্য একটি পরীক্ষার একটি কার্যকর উদাহরণ।

### স্যুইচের আগে শাখাগুলিতে ব্যাকপোর্ট

চেরি-পিক বা `YYYYMMDDHHMMSS_` ফাইলকে এমন শাখায় ব্যাকপোর্ট করবেন না যেটি সুইচের পূর্ববর্তী (উদাহরণস্বরূপ একটি পুরানো `release/v*` শাখা)। সেখানে রানার ফাইলের নাম টেক্সট হিসাবে সাজায়, তাই একটি টাইমস্ট্যাম্প করা ফাইল একটি নতুন ডাটাবেসে `201_` এবং `202_` এর মধ্যে চলবে এবং সেখানে পুরানো গেট 14-সংখ্যার উপসর্গ বুঝতে পারে না। এই ধরনের একটি শাখায়, সেই শাখার নিজস্ব পরবর্তী `NNN_` ফাইল হিসাবে পরিবর্তনটি লিখুন, idempotent, তাই টাইমস্ট্যাম্পড সংস্করণটি পরে আসার সময় এটি একটি নো-অপ।

### কিভাবে মাইগ্রেশন চালানো হয়

শুরুতে, `migrationRunner.ts`:

1. বিদ্যমান না থাকলে `_omniroute_migrations` টেবিল তৈরি করে
2. ইতিমধ্যে-প্রযোজ্য মাইগ্রেশনের জন্য প্রশ্ন
3. ক্রমানুসারে যেকোনো নতুন স্থানান্তর প্রয়োগ করে, প্রতিটি একটি লেনদেনে
4. টাইমস্ট্যাম্প সহ প্রতিটি প্রয়োগকৃত স্থানান্তর রেকর্ড করে

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### অদম্যতা

মাইগ্রেশন হতে হবে** অক্ষমতা** — তাদের দুবার চালানো একটি নো-অপ হওয়া উচিত:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, এবং `OR IGNORE` / `OR REPLACE` ধারাগুলি উদারভাবে ব্যবহার করুন৷

### একটি নতুন মাইগ্রেশন যোগ করা হচ্ছে

1. **জেনারেটর দিয়ে ফাইল তৈরি করুন** : `npm run db:new-migration -- <description>` (উদাহরণস্বরূপ `npm run db:new-migration -- add combo priority`)। এটি বর্তমান UTC সময় এবং একটি মন্তব্য শিরোনাম সহ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` লিখে, যদি সেই টাইমস্ট্যাম্পটি নেওয়া হয় তবে এক সেকেন্ড এগিয়ে যায় এবং কখনই একটি ফাইল ওভাররাইট করে না। হাতে একটি সংখ্যা বাছাই করবেন না.
2. **নিরাপদ DDL ব্যবহার করুন** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **সাবধানে ডেটা ব্যাকফিল করুন** : বিদ্যমান সারি পরিচালনা করতে `UPDATE ... WHERE ...` ব্যবহার করুন
4. **অর্ডার এবং নামকরণ পরীক্ষা করুন** : `npm run test:migrations:fresh` (একটি খালি ডাটাবেসে সমস্ত স্থানান্তর) এবং `npm run check:migration-numbering`
5. **একটি অনুলিপি পরীক্ষা** : উৎপাদনে কখনই পরীক্ষিত মাইগ্রেশন চালাবেন না
6. **কোড থেকে তৈরি একটি টেবিল একটি মাইগ্রেশন প্রয়োজন** : যদি একটি মডিউল অলসভাবে টেবিলটি তৈরি করে (`CREATE TABLE IF NOT EXISTS`, একটি স্ব-নিরাময় পথ হিসাবে রাখা), একটি স্থানান্তর অবশ্যই একই DDL দিয়ে তৈরি করতে হবে। অন্যথায় একটি পরিষ্কার ইনস্টল এবং একটি আপগ্রেড করা ইনস্টল বিভিন্ন স্কিমা সহ শেষ হয়, সেই কোড পাথটি চলে কিনা তার উপর নির্ভর করে। `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` এবং `open-sse/` স্ক্যান করে এবং মাইগ্রেশন ছাড়াই একটি অলস `CREATE` এ ব্যর্থ হয় (#20557)। উদাহরণ: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`।

উদাহরণ:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **পিছনের-অসঙ্গত পরিবর্তন** (যেমন, ড্রপিং কলাম) কঠিন। OmniRoute একবার মাইগ্রেশন প্রয়োগ করা হলে NOT ডাউনগ্রেড — সমর্থন করে, স্কিমা পরিবর্তন স্থায়ী হয়। সেই অনুযায়ী পরিকল্পনা করুন।

## সংরক্ষিত অবস্থায় এনক্রিপশন

সংবেদনশীল ফিল্ডগুলো (API কী, OAuth টোকেন, কানেকশন স্ট্রিং) সংরক্ষিত অবস্থায় **AES-256-GCM** ব্যবহার করে এনক্রিপ্ট করা হয়।

### এটি যেভাবে কাজ করে

```ts
// src/lib/db/encryption.ts (সরলীকৃত)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### যেখানে এটি ব্যবহৃত হয়

- `provider_connections.api_key` — অ্যাপ্লিকেশন স্তরে এনক্রিপ্ট করা
- `provider_connections.access_token`, `refresh_token`, `id_token` — অ্যাপ্লিকেশন স্তরে এনক্রিপ্ট করা
- `namespace = "secrets"`-সহ `key_value` এন্ট্রি — অ্যাপ্লিকেশন স্তরে এনক্রিপ্ট করা
- `proxy_registry.auth` — উপস্থিত থাকলে অ্যাপ্লিকেশন স্তরে এনক্রিপ্ট করা

### এনক্রিপশন কী

এনক্রিপশন কীটি একটি **পাসফ্রেজ** (`STORAGE_ENCRYPTION_KEY` এনভায়রনমেন্ট ভ্যারিয়েবলের মাধ্যমে সেট করা) এবং একটি **সল্ট** (DB-তে সংরক্ষিত) থেকে উদ্ভূত হয়। ডেটা ডিক্রিপ্ট করতে উভয়ই প্রয়োজন।

```bash
# একটি নিরাপদ পাসফ্রেজ তৈরি করুন
openssl rand -hex 32

# .env-এ সেট করুন
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **গুরুত্বপূর্ণ**: এনক্রিপশন কী হারানোর অর্থ হলো সব এনক্রিপ্ট করা ডেটায় অ্যাক্সেস হারানো। **ডেটাবেস থেকে আলাদাভাবে কীটির ব্যাকআপ রাখুন**।

### যা এনক্রিপ্ট করা হয় না

পারফরম্যান্সের কারণে, নিম্নলিখিত তথ্যগুলো প্লেইনটেক্সটে সংরক্ষণ করা হয়:

- প্রোভাইডারের প্রদর্শিত নাম
- মডেলের সংজ্ঞা (ইতোমধ্যেই সর্বজনীন)
- রাউটিং নিয়ম
- ব্যবহারের রেকর্ড (কোনো PII নেই)

## এনক্রিপশন-সংক্রান্ত সতর্কতা (v3.8.16+)

OmniRoute দুটি এনক্রিপশন স্কিম স্বচ্ছভাবে পরিচালনা করতে **`migrateLegacyEncryptedString()`** ব্যবহার করে:

- **লিগ্যাসি** (v3.5.0-এর পূর্ববর্তী): XOR-ভিত্তিক "এনক্রিপশন" (প্রকৃত ক্রিপ্টোগ্রাফি নয়)
- **বর্তমান**: যথাযথ IV এবং auth tag-সহ AES-256-GCM

মাইগ্রেশন সহায়কটি লিগ্যাসি ফরম্যাট শনাক্ত করে এবং প্রথমবার পড়ার সময় নতুন স্কিম দিয়ে পুনরায় এনক্রিপ্ট করে। এর অর্থ হলো, ক্রেডেনশিয়াল না হারিয়েই আপনি একটি পুরোনো ডেটাবেস আপগ্রেড করতে পারবেন।

## ব্যাকআপ এবং পুনরুদ্ধার

### ম্যানুয়াল ব্যাকআপ

```bash
# একটি লোকাল ব্যাকআপ তৈরি করতে CLI ব্যবহার করুন
omniroute backup create --name pre-migration

# অথবা API-এর মাধ্যমে
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

ব্যাকআপ ফাইলে অন্তর্ভুক্ত থাকে:

- সব DB টেবিল (JSON-এ সিরিয়ালাইজ করা)
- কল লগ আর্টিফ্যাক্ট (base64-এনকোডেড, ঐচ্ছিক)
- সেটিংস + সিক্রেট (এনক্রিপ্ট করা)
- প্লাগইন কনফিগারেশন

### পুনরুদ্ধার

```bash
# CLI-এর মাধ্যমে
omniroute restore pre-migration

# API-এর মাধ্যমে
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **সতর্কতা**: পুনরুদ্ধার সম্পূর্ণ DB ওভাররাইট করে। প্রথমে সব ক্লায়েন্ট বন্ধ করুন।

### স্বয়ংক্রিয় ব্যাকআপ

```bash
# CLI-এর মাধ্যমে স্বয়ংক্রিয় দৈনিক ব্যাকআপ সক্রিয় করুন
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

সময়সূচিটি সার্ভার-সাইডে একটি ব্যাকগ্রাউন্ড জব দ্বারা কার্যকর করা হয়, যা প্রতি 30 সেকেন্ডে
(ডিফল্ট) টিক করে এবং লোকাল সার্ভারের সময় অনুযায়ী cron এক্সপ্রেশন মূল্যায়ন করে।

| ভেরিয়েবল                                   | ডিফল্ট  | বিবরণ                                                                                                                            |
| ------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000` | ms-এ টিকের ব্যবধান (সর্বনিম্ন `5000`)। মিলে যাওয়া cron মিনিটের মধ্যে নির্ভরযোগ্যভাবে পড়তে এটি অবশ্যই 60 s-এর চেয়ে কম হতে হবে। |

### SQLite হট ব্যাকআপ

সচল DB-এর শূন্য-ডাউনটাইম ব্যাকআপের জন্য:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

এটি SQLite-এর অনলাইন ব্যাকআপ API ব্যবহার করে—OmniRoute চলমান থাকা অবস্থায়ও এটি নিরাপদে চালানো যায়।

## পারফরম্যান্স টিউনিং

### WAL মোড

WAL ডিফল্টরূপে সক্রিয় করা হয়। উচ্চ-লেখা কাজের চাপের জন্য, বিবেচনা করুন:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` সেট করে না। একটি চেকপয়েন্ট WAL ফ্রেমগুলিকে প্রধান ফাইলে নিয়ে যায়, কিন্তু WAL ফাইলটি তার সবচেয়ে বড় বরাদ্দকৃত আকার রাখে। `OMNIROUTE_WAL_GUARD_MAX_MB` গার্ড শুধুমাত্র সতর্ক করে এবং `wal_checkpoint(RESTART)` চালায়; এটি একটি ডিস্ক-আকার ক্যাপ নয়।

### সূচক

পারফরম্যান্সের জন্য মূল সূচী (মাইগ্রেশন দ্বারা স্বয়ংক্রিয়ভাবে তৈরি):

- প্রদানকারী দ্বারা`idx_models_provider` — মডেল লুকআপ
- `idx_combo_targets_combo_id` — কম্বো লক্ষ্য সম্প্রসারণ
- `idx_usage_history_api_key_timestamp` — ব্যবহার বিশ্লেষণ
- `idx_quota_snapshots_api_key_window` — কোটা ট্র্যাকিং
- `idx_call_logs_timestamp` — কল লগ প্রশ্ন

একটি নতুন সূচক যোগ করতে, একটি মাইগ্রেশন তৈরি করুন:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### মেমরি-ম্যাপ করা I/O

খুব বড় ডাটাবেসের জন্য (> 10GB), মেমরি ম্যাপিং SQLite pragma এর মাধ্যমে সামঞ্জস্য করা যেতে পারে:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### কম্প্যাকশন

দীর্ঘ সময় ধরে চলমান OmniRoute দৃষ্টান্তগুলি মাঝে মাঝে `VACUUM` থেকে উপকৃত হয়:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

কম ট্রাফিক উইন্ডোর সময় মাসিক চালান. (WAL মোড প্রয়োজন কমায়, কিন্তু তা দূর করে না।)

## স্বাস্থ্য পরীক্ষা

`src/lib/db/healthCheck.ts` **DB-স্তরের স্বাস্থ্য ডায়াগনস্টিকস** প্রদান করে:

উভয় verb-এর জন্যই প্রমাণীকরণ প্রয়োজন (অন্যথায় `401`)। `GET` শুধু রোগনির্ণয় করে; `POST` একই পরীক্ষা `autoRepair` সক্রিয় রেখে চালায়।

```bash
GET  /api/db/health   # রোগনির্ণয়
POST /api/db/health   # রোগনির্ণয় + মেরামত
```

রেসপন্সটি হলো `runDbHealthCheck()` দ্বারা উৎপন্ন `DbHealthCheckResult`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "ডোমেইন বাজেটগুলো এমন API কী উল্লেখ করেছে, যেগুলো আর বিদ্যমান নেই।",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ফিল্ড             | অর্থ                                                                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `issues` খালি হলে `true`। `driver` কখনো এটিকে প্রভাবিত করে না।                                                                                    |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`-এর যেকোনো একটি।                                                   |
| `repairedCount`   | এই রানের সময় মেরামত করা সারির সংখ্যা; `autoRepair` false হলে সর্বদা `0`।                                                                         |
| `backupCreated`   | মেরামতের আগে ব্যাকআপ নেওয়া হয়েছিল কি না।                                                                                                        |
| `checkedAt`       | রান এবং এর লেখা যেকোনো মেরামত নোটে ব্যবহৃত অভিন্ন ISO টাইমস্ট্যাম্প।                                                                              |
| `driver.name`     | পরীক্ষিত ডেটাবেসটি পরিবেশনকারী SQLite ড্রাইভার।                                                                                                   |
| `driver.degraded` | ডেটাবেস ফাইল দ্বারা লেখাগুলো স্থায়ীভাবে সংরক্ষিত না হলে `true` — `sql.js` WASM ফলব্যাক (সম্পূর্ণ-ফাইল পার্সিস্টেন্স) অথবা একটি ইন-মেমরি ডেটাবেস। |

একই পেলোড `omniroute_db_health_check` MCP টুল দ্বারাও ফেরত দেওয়া হয়।

করাপশন শনাক্ত করতে `PRAGMA integrity_check` চালান:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# যা প্রিন্ট হওয়া উচিত: ok
```

এটি `ok` ছাড়া অন্য কিছু ফেরত দিলে, **অবিলম্বে ডেটাবেস ব্যবহার বন্ধ করুন** এবং ব্যাকআপ থেকে পুনরুদ্ধার করুন।

## দুর্যোগ পুনরুদ্ধার

### পরিস্থিতি 1: WAL ফাইল হারিয়ে গেছে

`-wal` ফাইলটি অনুপস্থিত, কিন্তু `-shm` এবং মূল DB অক্ষত রয়েছে:

```bash
# পরবর্তীবার খোলার সময় স্বয়ংক্রিয়ভাবে পুনরুদ্ধার হয়
omniroute
```

যদি SQLite স্বয়ংক্রিয়ভাবে পুনরুদ্ধার করতে না পারে:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### পরিস্থিতি 2: মূল DB ফাইল ক্ষতিগ্রস্ত হয়েছে

ব্যাকআপ থেকে পুনরুদ্ধার করুন:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` শুধু একটি চলমান সার্ভার থেকে সম্পূর্ণ `.tar.gz` আর্কাইভ ডাউনলোড করে
(`GET /api/db-backups/exportAll`, অপারেটর ক্রেডেনশিয়াল প্রয়োজন); এটি কিছুই পুনরুদ্ধার করে না।

### পরিস্থিতি 3: এনক্রিপশন কী হারিয়ে গেছে

কী ছাড়া **পুনরুদ্ধার সম্ভব নয়**। এনক্রিপ্ট করা ফিল্ডগুলো অপাঠ্য। নতুন ক্রেডেনশিয়াল দিয়ে সব প্রোভাইডার ম্যানুয়ালি পুনরায় যোগ করুন।

> **প্রশমন**: এনক্রিপশন কীটি সর্বদা আলাদাভাবে ব্যাকআপ রাখুন, আদর্শভাবে কোনো পাসওয়ার্ড ম্যানেজার বা KMS-এ।

### পরিস্থিতি 4: ডিস্ক পূর্ণ

SQLite `SQLITE_FULL` ত্রুটি ফেরত দেবে। ডিস্কে জায়গা খালি করুন, তারপর:

```bash
# জায়গা খালি করতে WAL-এর চেকপয়েন্ট তৈরি করুন
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## সাধারণ কার্যক্রম

### একটি টেবিল পরিদর্শন করুন

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### সব টেবিলের সারি গণনা করুন

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### সব ডেটা রিসেট (মুছে) করুন

```bash
# প্রথমে OmniRoute বন্ধ করুন
omniroute stop

# DB ফাইলটি মুছুন
rm ~/.omniroute/storage.sqlite*

# পুনরায় চালু করুন (খালি DB আবার তৈরি হবে)
omniroute
```

**নির্বাচিতভাবে** রিসেট করতে (প্রোভাইডারগুলো রেখে ব্যবহারের ডেটা মুছতে):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### একটি টেবিল এক্সপোর্ট করুন

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## সমস্যা সমাধান

### "ডেটাবেস লক করা আছে"

অন্য একটি প্রসেস রাইট লক ধরে রেখেছে। নিচের যেকোনো একটি করুন:

- অন্য প্রসেসটি শেষ হওয়ার জন্য অপেক্ষা করুন (`lsof | grep storage.sqlite` দিয়ে পরীক্ষা করুন)
- অন্য প্রসেসটি বন্ধ করে দিন
- সমস্যা স্থায়ী হলে OmniRoute পুনরায় চালু করুন

### "ফরেন কী কনস্ট্রেইন্ট ব্যর্থ হয়েছে"

কোনো ডোমেইন মডিউল রেফারেনশিয়াল ইন্টেগ্রিটি লঙ্ঘন করছে। পরীক্ষা করুন:

- নির্ভরশীল টেবিলে অনাথ সারি
- যেসব ক্যাসকেডিং ডিলিট ছড়িয়ে পড়েনি
- ফরেন কী পরিবর্তন করা সাম্প্রতিক মাইগ্রেশন

লঙ্ঘনগুলো খুঁজতে `PRAGMA foreign_key_check;` চালান।

### "মেমরি শেষ"

SQLite-এর মেমরি-ম্যাপড I/O অপারেটিং সিস্টেমের সীমা অতিক্রম করছে। SQLite pragma ব্যবহার করে কমান:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB-এর পরিবর্তে 128MB
```

অথবা নিষ্ক্রিয় করুন:

```sql
PRAGMA mmap_size = 0;
```

### "মাইগ্রেশন মাঝপথে ব্যর্থ হয়েছে"

মাইগ্রেশনটি একটি ট্রানজ্যাকশনে চলেছে, তাই এটি রোলব্যাক হয়ে যাওয়ার কথা। তা না হলে:

1. **OmniRoute বন্ধ করুন** (পরবর্তী প্রচেষ্টা প্রতিরোধ করতে)
2. `sqlite3` দিয়ে **DB-এর অবস্থা পরীক্ষা করুন**
3. আংশিক মাইগ্রেশনটি **ম্যানুয়ালি ঠিক করুন**
4. OmniRoute **পুনরায় চালু করুন** (মাইগ্রেশনটি আবার চেষ্টা করা হবে)

এটি প্রতিরোধ করতে, সবসময় প্রথমে একটি কপিতে মাইগ্রেশন পরীক্ষা করুন।
