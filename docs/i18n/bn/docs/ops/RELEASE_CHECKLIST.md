## npm Trusted Publishing (v3.8.51 থেকে default) — অনুরোধে staged, fallback হিসেবে direct

`npm-publish.yml` ডিফল্টভাবে **npm Trusted Publishing (OIDC)**-এর মাধ্যমে publish করে:
`stage-npm` job (github-hosted) সেই run-এর জন্য GitHub-এর id-token বিনিময় করে স্বল্পমেয়াদি npm
credential সংগ্রহ করে — repository secrets-এ কোনো দীর্ঘমেয়াদি npm token থাকে না, 2FA prompt আসে না, এবং provenance সংযুক্ত থাকে।
এটাই এখন npm sanctions-এর bypass, কারণ 2FA এড়িয়ে যায় এমন token অবসর নেওয়া হচ্ছে;
এটি v3.8.48 পর্যন্ত project-এ থাকা সম্পূর্ণ স্বয়ংক্রিয় flow ফিরিয়ে আনে এবং
WS1.3 guarantee বজায় রাখে (ফাঁস হওয়া token একা publish করতে পারে না — কোনো token-ই নেই)।

**একবারের setup (owner):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)। এটি তৈরি না হওয়া পর্যন্ত automatic step `ENEEDAUTH`-এ ব্যর্থ হবে:
`publish_mode=staged` (নিচে) অথবা `direct` দিয়ে পুনরায় dispatch করুন।

### Staged publishing (অনুরোধে — `publish_mode=staged`)

npm-publish workflow আর সরাসরি publish করে না: এটি packed tarball
(`check:pack-boot`) boot করে এবং এরপর `npm stage publish` চালায় — সঠিক bytes registry-তে
park করা হয়, **owner অনুমোদন না করা পর্যন্ত install করা যায় না**। Human 2FA gate
proof-এর আগে নয়, **পরে** সরানো হয়েছে।

**Workflow সবুজ হওয়ার পর Owner flow:**

1. `npm stage list omniroute` — stage id খুঁজে নিন (workflow summary-তেও এটি দেখানো হয়)।
2. Staged bytes যাচাই করুন (সুপারিশকৃত): `npm stage download <id>` চালান, এরপর
   ডাউনলোড করা tarball একটি temp prefix-এ install করে boot করুন
   (`npm run check:pack-boot` CI-তে একই pack→install→boot verdict স্বয়ংক্রিয়ভাবে চালায়)।
3. `npm stage approve <id>` — 2FA prompt-ই publish। `npm stage reject <id>` discard করে।
4. Post-publish net: post-publish verifier (v3.8.49 plan-এর WS1.4) একটি clean container-এ
   public registry থেকে published version install করে এবং boot করে।

**Emergency fallback:** `workflow_dispatch`-এর মাধ্যমে `publish_mode=direct` দিলে
পুরোনো immediate `npm publish` পুনরুদ্ধার হয় (শুধুমাত্র staging নিজেই সমস্যা করলে ব্যবহার করুন; কারণটি record করুন)।

**একবারের hardening (owner, npmjs.com):** `omniroute`-এর জন্য Trusted Publisher
stage-only mode-এ configure করুন, যাতে ফাঁস হওয়া দীর্ঘমেয়াদি token কোথাও থেকে সরাসরি
`npm publish` করতে না পারে — CI কেবল stage করতে পারে; শুধু owner-এর 2FA release করতে পারে।

**Broken-artifact playbook (অপরিবর্তিত):** default reflex হিসেবে
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ব্যবহার করুন
(কয়েক মিনিটে কার্যকর, reversible); `npm unpublish` কেবল 72h/no-dependents
window-এর মধ্যে এবং কখনোই প্রথম পদক্ষেপ হিসেবে নয়। Docker: version tag কখনো rewrite করবেন না —
rollback হলো `latest`-কে সর্বশেষ ভালো digest-এ repoint করা।

**Docker Hub `latest` (প্রতিটি stable SemVer publish-এ আবশ্যক):**
`docker-publish` workflow-কে **দুটিই** tag করতে হবে — `X.Y.Z` এবং,
যখন `should-promote-latest.sh` সম্মত হয় যে এটি সর্বোচ্চ stable SemVer, তখন `:latest` —
একই digest দিয়ে। Job-এর পরে: Hub `latest` digest নতুন SemVer digest-এর সমান হবে এবং
`last_updated` পরিবর্তিত হবে। Git-এ থাকা release notes-এ এমন fixes-এর কথা বলা অবস্থায়
`:latest`-কে পুরোনো build-এ রেখে দেবেন না, যা কেবল git-এ বিদ্যমান।
Compose quickstarts-এ `:latest` ব্যবহার হয়; GitOps-এ `X.Y.Z` pin করা চালিয়ে যাওয়া উচিত।
দেখুন [Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) এবং #10317।

**Docker Hub organization repository (`cheaperinference/omniroute`):** Docker Hub
repository-কে namespace-গুলোর মধ্যে সরাতে পারে না, তাই `diegosouzapw/omniroute` তার pull history
এবং প্রতিটি release ধরে রাখে, আর `docker-publish`-এর `mirror-org-dockerhub` job
প্রতিটি released version (এবং promote করা হলে `:latest`) `ghcr.io/cheaper-inference/omniroute`
থেকে organization repository-তে copy করে। এর জন্য `DOCKERHUB_ORG_USERNAME` /
`DOCKERHUB_ORG_TOKEN` secrets প্রয়োজন; এগুলো না থাকলেও job
"Docker Hub org mirror skipped" warning সহ green থাকে এবং অন্যান্য registry স্বাভাবিকভাবে publish করে।
পরে কোনো released version publish করতে **Actions → Mirror Docker image to the Docker Hub org → Run
workflow** চালান, যেখানে `version=X.Y.Z` (এবং সর্বোচ্চ stable version-এর জন্য
`promote_latest`) দিন: এটি existing images copy করে, rebuild করে না।

## হটফিক্স ফাস্ট-লেন (লেবেল `hotfix`)

`hotfix` লেবেলযুক্ত PR ভারী CI ম্যাট্রিক্স (9-শার্ড E2E, coverage ratchet,
quality-gate, quality-extended) এড়িয়ে দ্রুত, উচ্চ-সিগন্যাল গেটগুলো চালায়: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
এবং tarball boot-smoke (`check:pack-boot`)। লক্ষ্য: প্রায় 33 মিনিটের পরিবর্তে ≤15
মিনিটে সবুজ ফলাফল।

**প্রবেশ নীতি — চারটিই আবশ্যক (Chromium/VS Code/Node-এর জরুরি লেনের আদলে):**

1. **তীব্রতা**: প্রোডাকশন ভেঙে গেছে — প্রকাশিত artifact বুটের সময় ক্র্যাশ করে / একটি
   নিরাপত্তা সংশোধন / রিলিজের প্রতিটি ব্যবহারকারী প্রভাবিত। "গুরুত্বপূর্ণ" মানেই
   "ভেঙে গেছে" নয়।
2. **কর্তৃত্ব**: শুধুমাত্র repository owner `hotfix` লেবেল প্রয়োগ করেন। লেবেলটিই
   অনুমোদন — কোনো campaign PR-এ কখনো নিজে থেকে এটি ব্যবহার করা যাবে না।
3. **প্রমাণ**: PR body-তে আগের সম্পূর্ণ-সবুজ heavy run-এর লিংক থাকতে হবে (যে suite
   বাদ দেওয়া jobs পুনরায় যাচাই করত), পাশাপাশি সংশোধনটির নিজস্ব ব্যর্থ-তারপর-পাস
   হওয়া test-এর লিংক থাকতে হবে।
4. **পরিসর**: শুধু cherry-pick — ন্যূনতম সংশোধন, কোনো refactor নয়, কোনো
   ride-along নয়।

বাদ দেওয়া coverage/ratchet surface release branch-এর পরবর্তী full run-এ পুনরায়
যাচাই করা হয় (continuous release-green) — এই লেনটি `WAITING` এড়ায়, validation
নয়। শুধু tests-সংক্রান্ত diff ( `tests/`-এর অধীনে সব ফাইল, `tests/e2e/`-এর অধীনে
কোনো ফাইল নয়) কোনো লেবেল ছাড়াই স্বয়ংক্রিয়ভাবে E2E ম্যাট্রিক্স এড়ায়।

### Build Layout

Repository-টি তিনটি পৃথক output directory ব্যবহার করে — এগুলো কখনো গুলিয়ে ফেলবেন না:

| Directory | Purpose                                                      | Tracked?        |
| --------- | ------------------------------------------------------------ | --------------- |
| `src/`    | Application source (TypeScript / TSX)                        | Yes             |
| `.build/` | Build intermediates — `next build` output (`distDir`)        | No (gitignored) |
| `dist/`   | Shippable npm bundle — `assembleStandalone` দ্বারা assembled | No (gitignored) |

> **Operator note:** remote VPS image directory এখনও `/usr/lib/node_modules/omniroute/app/`।
> শুধুমাত্র **in-repo** build output সরানো হয়েছে (`app/` → `dist/`)। Deploy skills
> `dist/`-এর contents remote `app/` dir-এ rsync করে — কোনো VPS path পরিবর্তন প্রয়োজন নেই।

**Single-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy-এর জন্য `npm run build` চালিয়ে তার পরে আলাদা করে `npm run build:cli` চালাবেন না — `npm run build:release` ব্যবহার করুন, যা একটি command-এ clean rebuild + sentinel সম্পন্ন করে।

## 3.9.0 LTS কাট (3.8.58 এ রিহার্সাল করা হয়েছে)

v3.8.59-এর পরে পরবর্তী সংস্করণ হল 3.9.0, এবং এর টিপ দুটি দীর্ঘজীবী শাখায় পরিণত হয়: `stable/v3` (v3 LTS লাইন, npm `latest`) এবং `develop` (v4, 4.0.0-এ ধাক্কা দেওয়া, npm `nightly`)। branch/channel মডেল, ফরোয়ার্ড-পোর্ট এবং লেবেলগুলি [RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md) ; পরিকল্পনাটি [ROADMAP](../../ROADMAP.md) এ রয়েছে (পর্যায় 3)। কাটা একবার সঞ্চালিত হয়; 3.8.58 এটি একটি কাঁটাচামচের উপর শেষ থেকে শেষ পর্যন্ত রিহার্সাল করে এবং 3.8.59 [GO/NO-GO চেকলিস্টের](./LTS_GO_NO_GO.md) সাথে বন্ধ হয়।

### ড্রাই-রান (কেবল-পঠন, যেকোনো সময় নিরাপদ)

```bash
npm run release:dry-run-lts-cut                       # the real cut: 3.9.0 from HEAD, previous tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # pin the source commit
```

`scripts/release/dry-run-lts-cut.mjs` executes nothing: it reads git and `gh` and prints the whole sequence — preconditions (source resolves, the source repository has full history — a shallow clone cannot push `stable/v3`, the receiving side rejects the pack at the first grafted parent, so cut from a full clone or `git fetch --unshallow origin` first — previous tag exists, `package.json` is the target version, a `release-freeze` issue is open, no open `Release branch not green` issue on an existing release branch — a branch that does not exist reports `?` unknown, never green — omni-queue lands the release PRs (G11: `config/merge-queue/config.json` valid, its `bases` manage the release branch, `mode` `live`, its label exists), the `release/*` ruleset still blocks deletion and force-push, and `stable/v3` and `develop` do not exist yet), the two branch steps, which dormant-workflow triggers and `if:` conditions turn true (and which stay gated by a repository variable or pinned to the canonical repository), the expected dist-tags (`latest` → 3.9.0, `next` and `nightly` empty) and the rollback. Exit `0` = `RESULT: READY`, `1` = a blocking precondition failed (`✗`), `2` = usage error. `--advisory <id,...>` downgrades a check to a warning (`!`) without hiding it.

রিয়েল কাটের ড্রাই-রান চালান যখন 3.9.0 রিলিজ ফ্রিজ এখনও খোলা থাকে — ট্যাগের পরে এবং ফেজ 12c ফ্রিজ তুলে নেওয়ার আগে শাখাগুলি তৈরি হয়।

### 3.8.58 রিহার্সাল (শুধুমাত্র কাঁটা)

```bash
# 1. Dry-run on the current tip with rehearsal parameters
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. Execute against a FORK remote (origin, or any remote whose URL is the canonical
#    repository, is refused; every step asks for confirmation on the terminal)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. Exercise the dormant workflows in the fork (workflow_dispatch where the dry-run
#    reports a canonical-repository pin), then roll back
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

ডেভেলপ বাম্প কমিট গিট প্লাম্বিং দিয়ে তৈরি করা হয়েছে (কোনও কাজের গাছকে স্পর্শ করা হয়নি) এবং সাইকেল-ওপেন কমিট হিসাবে একই পাঁচটি ফাইল বাম্প করে: `package.json`, `open-sse/package.json`, `electron/package.json`, `package-lock.json` এবং `docs/openapi.yaml`। `[4.0.0]` CHANGELOG বিভাগ এবং এর i18n আয়না `develop` এর পরে, প্রথম PR এর আগে খোলা হয়। স্ক্র্যাচ প্যাকেজে থাকা npm dist-tags — রিহার্সেল স্ক্রিপ্ট কখনই পরিবর্তন করে না।

### PR প্রিভিউ আর্টিফ্যাক্ট (একবার তৈরি করুন, একই বাইট প্রচার করুন)

`.github/workflows/preview-artifact.yml` একটি PR হেড থেকে একটি প্রোডাকশন টারবল তৈরি করে এবং সঠিক বিল্ড (#8084 স্লাইস (a)) যাচাই করে। একই-রিপোজিটরি PRs শুধুমাত্র; কিছুই প্রকাশিত হয় না।

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # or add the `preview-artifact` label
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview install
```

রান `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, টারবল প্যাক করে, `npm run check:pack-boot` চালায় (জাল গোপনীয়তা, ক্ষণস্থায়ী ডেটা ডির), পুনরায় প্যাক করে এবং ব্যর্থ হয় যদি না ডাইজেস্ট অভিন্ন হয়, তারপর `artifact-identity.json` রেকর্ড করে (হেড SHA, বেস SHA, লকফাইল ABI, বিল্ড প্ল্যাটফর্ম, প্ল্যাটফর্ম নকল — `scripts/release/artifact-identity.mjs`) এবং একটি পৃথক কাজে টারবলকে সত্যায়িত করে। একটি পূর্বরূপ প্রচার করার অর্থ হল সেই টারবল ইনস্টল করা: উত্স থেকে কখনও পুনর্নির্মাণ করবেন না৷

### কাট (3.9.0, GO পরে)

1. GO [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) এ রেকর্ড করা হয়েছে।
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` `RESULT: READY` প্রিন্ট করে।
3. ড্রাই-রান প্রিন্ট — স্ক্রিপ্ট `origin` এ ঠেলে দিতে অস্বীকার করে কমান্ড দিয়ে `origin` তে শাখা তৈরি করুন। রিভিউ করা ডেভেলপ কমিট পুনরায় ব্যবহার করতে, প্রথমে আপনার ফর্কের বিপরীতে 3.9.0 টিপে `--execute` রিহার্সাল চালান; এটি উভয় SHAs প্রিন্ট করে, এবং একই কমিটগুলিকে ধাক্কা দেওয়া যেতে পারে:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. প্রথম PR ল্যান্ড করার আগে `stable/v3` এবং `develop` (রুলসেট + মার্জ কিউ) রক্ষা করুন।
5. সুপ্ত কর্মপ্রবাহগুলি শাখার অস্তিত্ব দ্বারা চালু হয়: `forward-port.yml` ( `stable/v3` এ ঠেলে), `validate-stable-pr.yml` (PRs থেকে `stable/v3`) এবং `nightly-v4-build.yml` ( `develop` তৈরি করে)। গো-লাইভ করার আগে, `secrets.FORWARD_PORT_TOKEN` রিপোজিটরি সিক্রেট সেট করুন (তাই CI ফরওয়ার্ড-পোর্ট PRs এ চলে); রাত্রিকালীন প্রকাশনা বন্ধ থাকে যতক্ষণ না মালিক রিপোজিটরি ভেরিয়েবল `vars.NIGHTLY_PUBLISH` `true` এ সেট না করে এবং npm বিশ্বস্ত প্রকাশনা `nightly-v4-build.yml` গ্রহণ করে। চ্যানেল রেজোলিউশন হল `scripts/release/dist-tag.mjs`, একই রেজোলিউর `npm-publish.yml` ব্যবহার করে।
6. চ্যানেলগুলি যাচাই করুন: `npm view omniroute dist-tags --json` `latest` = 3.9.0 দেখায় এবং v4 প্রকাশ না হওয়া পর্যন্ত `next` / `nightly` নয়৷
7. রোলব্যাক, যদি প্রয়োজন হয়: `git push origin --delete refs/heads/stable/v3 refs/heads/develop` এবং `npm dist-tag add omniroute@3.8.59 latest`।
