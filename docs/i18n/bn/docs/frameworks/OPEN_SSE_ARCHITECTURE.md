> **সংক্ষেপে**: `open-sse/` হলো মূল স্ট্রিমিং ইঞ্জিন, যা OmniRoute-এর প্রতিটি LLM অনুরোধ পরিচালনা করে। এতে অনুরোধ পাইপলাইন, এক্সিকিউটর, সার্ভিস, MCP সার্ভার এবং অনুবাদ স্তর বাস্তবায়নকারী প্রায় ১,৪০০টি ফাইল রয়েছে। এই নির্দেশিকায় অংশগুলো কীভাবে একসঙ্গে কাজ করে তা ব্যাখ্যা করা হয়েছে।

**উৎস:** `open-sse/` (ওয়ার্কস্পেস প্যাকেজ, প্রায় ১,৪৪০টি নন-টেস্ট `.ts` ফাইল)

## আলাদা ওয়ার্কস্পেস প্যাকেজ কেন?

OmniRoute মনোরেপোতে `open-sse/` একটি **স্বতন্ত্র ওয়ার্কস্পেস**, যার কয়েকটি কারণ রয়েছে:

1. **পুনর্ব্যবহারযোগ্যতা** — `open-sse`, npm-এ `@omniroute/open-sse` হিসেবে প্রকাশিত হয়, তাই অন্যান্য প্রজেক্ট এটি স্বাধীনভাবে ব্যবহার করতে পারে
2. **সুস্পষ্ট সীমারেখা** — স্ট্রিমিং ইঞ্জিনটি OmniRoute-নির্দিষ্ট UI/DB স্তর থেকে পৃথক
3. **কর্মক্ষমতা** — ইঞ্জিনটির কোনো Next.js নির্ভরতা নেই, ফলে CLI/serverless প্রেক্ষাপটে দ্রুততর কোল্ড স্টার্ট সম্ভব হয়
4. **সংস্করণ ব্যবস্থাপনা** — `open-sse` নিজস্ব সময়সূচি অনুযায়ী রিলিজ করতে পারে

```json
// package.json
"workspaces": ["open-sse"]
```

## অনুরোধ পাইপলাইন

প্রতিটি LLM অনুরোধ একটি **৫-ধাপের পাইপলাইনের** মধ্য দিয়ে প্রবাহিত হয়:

```
                              ┌──────────────┐
   HTTP অনুরোধ                │  ১. রাউট     │   কম্বো নির্ধারণ, মডেল নির্বাচন
   (Next.js রুট)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ২. অনুবাদ   │   ফরম্যাট রূপান্তর (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ৩. সম্পাদন  │   প্রোভাইডার এক্সিকিউটর, HTTP, পুনঃচেষ্টা, ব্রেকার
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ৪. স্ট্রিম   │   SSE রূপান্তর, ব্যাকপ্রেশার
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ৫. রেকর্ড   │   ব্যবহার ট্র্যাকিং, কল লগ, ত্রুটি শ্রেণিবিন্যাস
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP প্রতিক্রিয়া (SSE অথবা JSON)
```

### ধাপ ১: রাউট (services/combo.ts)

**এন্ট্রি পয়েন্ট**: `services/combo.ts`-এর `handleComboChat()`

অনুরোধটিকে একটি নির্দিষ্ট `(provider, model, account, credentials)` টাপলে রূপ দেয়:

- ID দিয়ে কম্বো খুঁজে বের করে (অথবা `auto/*` মডেলের জন্য একটি ভার্চুয়াল কম্বো তৈরি করে)
- রাউটিং কৌশল প্রয়োগ করে (অগ্রাধিকার, ওয়েটেড, রাউন্ড-রবিন ইত্যাদি)
- অস্বাস্থ্যকর প্রোভাইডারগুলো বাদ দেয় (সার্কিট ব্রেকার)
- পরবর্তী কার্যকর টার্গেট নির্বাচন করে

`auto/*` মডেলের জন্য এই ধাপটি আরও যা করে:

- **১৬-ফ্যাক্টর স্কোরিং** অ্যালগরিদম (`services/autoCombo/`) চালায়
- স্বাস্থ্য, খরচ, ল্যাটেন্সি ইত্যাদির ভিত্তিতে একটি `provider+model` জোড়া নির্বাচন করে

### ধাপ ২: অনুবাদ (translator/)

উৎস ফরম্যাট (যেমন OpenAI) এবং টার্গেট ফরম্যাট (যেমন Claude) ভিন্ন হলে, অনুরোধটি **অনুবাদ** করা হয়:

- সিস্টেম প্রম্পট → সিস্টেম মেসেজ
- টুলের সংজ্ঞা → প্রোভাইডার-নির্দিষ্ট টুল ফরম্যাট
- রিজনিং/থিংকিং প্যারামিটার → প্রোভাইডার-নির্দিষ্ট সমতুল্য রূপ
- মেসেজ ভূমিকা স্বাভাবিকীকরণ (OpenAI ছাড়া অন্যগুলোর জন্য `developer` → `system`)

`translator/index.ts` যা প্রকাশ করে:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### ধাপ ৩: সম্পাদন (executors/)

**এন্ট্রি পয়েন্ট**: `getExecutor(providerId).execute(request, options)`

সব প্রোভাইডার `getExecutor()` ফ্যাক্টরি ফলব্যাকের মাধ্যমে `DefaultExecutor` (`executors/default.ts`) ব্যবহার করে। এক্সিকিউটর যা করে:

- আপস্ট্রিম URL তৈরি করে (`buildUrl()`)
- প্রোভাইডার-নির্দিষ্ট হেডার যোগ করে (`buildHeaders()`)
- অনুরোধের বডি রূপান্তর করে (`transformRequest()`)
- পুনঃচেষ্টা ও এক্সপোনেনশিয়াল ব্যাকঅফসহ HTTP অনুরোধ পাঠায়
- প্রয়োজন হলে অথেন্টিকেশন রিফ্রেশ পরিচালনা করে (OAuth প্রোভাইডার)

সব এক্সিকিউটর `BaseExecutor` (`executors/base.ts`, 1170 LOC) সম্প্রসারণ করে, যা প্রদান করে:

- সাধারণ পুনঃচেষ্টা লজিক
- প্রক্সি ইন্টিগ্রেশন
- সার্কিট ব্রেকার ইন্টিগ্রেশন
- ব্যবহার রেকর্ডিং হুক

### ধাপ ৪: স্ট্রিম (utils/stream.ts)

স্ট্রিমিং প্রতিক্রিয়ার ক্ষেত্রে, এক্সিকিউটর একটি **ReadableStream** ফেরত দেয়। হ্যান্ডলার যা করে:

- একটি SSE ট্রান্সফর্মের (`createSSETransformStreamWithLogger`) মধ্য দিয়ে পাইপ করে
- বিচ্ছিন্ন সংযোগ শনাক্ত করতে হার্টবিট পিং প্রয়োগ করে
- ক্লায়েন্টের সংযোগ বিচ্ছিন্ন হওয়া সাবলীলভাবে পরিচালনা করে (`pipeWithDisconnect`)
- নন-স্ট্রিমিং ক্লায়েন্টের জন্য SSE → JSON রূপান্তর করে

নন-স্ট্রিমিং প্রতিক্রিয়ার ক্ষেত্রে, এক্সিকিউটর একটি পার্স করা JSON অবজেক্ট ফেরত দেয়, যা কোনো পরিবর্তন ছাড়াই পাঠিয়ে দেওয়া হয়।

### ধাপ ৫: রেকর্ড (services/usage.ts)

প্রতিক্রিয়ার পরে (সফল বা ব্যর্থ), ব্যবহারসংক্রান্ত তথ্য রেকর্ড করা হয়:

- প্রতিক্রিয়া থেকে `prompt_tokens`, `completion_tokens`, `cached_tokens`
- মূল্য নির্ধারণের ডেটা থেকে গণনা করা `cost_usd`
- ব্যর্থ হলে `latency_ms`, `status`, `error_class`
- `usage_history` টেবিলে সংরক্ষিত

কল লগের আর্টিফ্যাক্টগুলো (সক্রিয় থাকলে) `${DATA_DIR}/call_logs/`-এ লেখা হয়।

## কী ফাইল ডিপ-ডাইভ

### chatCore.ts (5977 লাইন)

দ** প্রধান অনুরোধ হ্যান্ডলার** . এর আকার সত্ত্বেও, এটির একটি পরিষ্কার কাঠামো রয়েছে:

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

### পৃথক ট্রান্সফর্মার কেন?

Responses API হলো **স্টেটফুল কথোপকথন** (`previous_response_id`) সমর্থিত OpenAI-এর নতুন ফরম্যাট। যখন কোনো ক্লায়েন্ট Responses অনুরোধ পাঠায়, OmniRoute:

1. অভ্যন্তরীণভাবে Responses → Chat Completions-এ রূপান্তর করে
2. প্রোভাইডারের কাছে পাঠায় (Chat Completions সমর্থন করে এমন যেকোনো প্রোভাইডার)
3. রেসপন্সটিকে আবার Responses ফরম্যাটে রূপান্তর করে
4. রূপান্তরিত রেসপন্সটি ক্লায়েন্টের কাছে স্ট্রিম করে

ট্রান্সফর্মারটি (`transformer/responsesTransformer.ts`) প্রদান করে:

```ts
createResponsesApiTransformStream(): TransformStream
```

এটি নিম্নলিখিত বিষয়গুলো পরিচালনা করে:

- `response.output_item.added` ইভেন্ট
- `response.output_text.delta` ইভেন্ট
- `response.completed` ইভেন্ট
- টুল কল ম্যাপিং (`function_call` ↔ `tool_calls`)

## কনফিগারেশন

`open-sse/config/` কনফিগারেশন স্তর ধারণ করে:

| ফাইল                            | উদ্দেশ্য                                             |
| ------------------------------- | ---------------------------------------------------- |
| `providerRegistry.ts`           | 394-প্রদানকারীর ক্যাটালগের উপর চ্যাট-মডেল রেজিস্ট্রি |
| `providerModels.ts`             | মডেল উপনাম, বিন্যাস ম্যাপিং                          |
| `constants.ts`                  | টাইমআউট, সীমা, স্থিতি কোড                            |
| `defaultThinkingSignature.ts`   | ডিফল্ট Claude চিন্তা স্বাক্ষর                        |
| `modelStrip.ts` (পরিষেবাগুলিতে) | প্রতি-প্রদানকারী ফিল্ড স্ট্রিপিং                     |

### প্রদানকারী রেজিস্ট্রি স্কিমা

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

মডিউল লোডেZod বৈধতা নিশ্চিত করে যে সমস্ত প্রদানকারী কনফিগার বৈধ।

❌ **`combo.ts`-এ সিঙ্ক্রোনাস DB কল** — আগে থেকে কম্পিউট করে ক্যাশ করুন

❌ **প্রোভাইডার কনফিগে সরাসরি অ্যাক্সেস** — `providerRegistry` গেটার ব্যবহার করুন
❌ **হার্ডকোড করা ফলব্যাক চেইন** — `modelFamilyFallback.ts`-এ সংজ্ঞায়িত করুন
❌ **সমসাময়িক রিকোয়েস্টজুড়ে স্টেট মিউটেশন** — শুধু রিকোয়েস্ট-স্কোপড কনটেক্সট ব্যবহার করুন

## নতুন কম্পোনেন্ট যোগ করা

### নতুন সার্ভিস যোগ করা

1. নির্দিষ্ট দায়িত্বসহ `open-sse/services/[serviceName].ts` তৈরি করুন
2. মূল হ্যান্ডলার ফাংশন এবং যেকোনো কনস্ট্যান্ট এক্সপোর্ট করুন
3. `tests/unit/services/[serviceName].test.mjs`-এ ইউনিট টেস্ট যোগ করুন
4. রাউটিং-সম্পর্কিত হলে `handlers/chatCore.ts`-এর রিকোয়েস্ট পাইপলাইনে ইন্টিগ্রেট করুন
5. সার্ভিসটি টার্গেট নির্বাচনকে প্রভাবিত করলে `combo.ts`-এর রাউটিং লজিক আপডেট করুন
6. এই ফাইলে ডকুমেন্ট করুন

### নতুন এক্সিকিউটর যোগ করা

1. `BaseExecutor` এক্সটেন্ড করে `open-sse/executors/[provider].ts` তৈরি করুন
2. `config/providerRegistry.ts`-এ রেজিস্টার করুন
3. `executors/index.ts` ফ্যাক্টরিতে যোগ করুন
4. এক্সিকিউটরের জন্য ইউনিট টেস্ট যোগ করুন
5. `docs/architecture/ARCHITECTURE.md`-এ ডকুমেন্ট করুন

### নতুন MCP টুল যোগ করা

1. `open-sse/mcp-server/tools/[category]Tools.ts` তৈরি বা আপডেট করুন
2. ইনপুটের জন্য Zod স্কিমা সংজ্ঞায়িত করুন
3. `mcp-server/index.ts`-এ টুলটি রেজিস্টার করুন
4. `mcp-server/auth/`-এর স্কোপ ম্যাট্রিক্সে যোগ করুন
5. ইউনিট টেস্ট যোগ করুন
