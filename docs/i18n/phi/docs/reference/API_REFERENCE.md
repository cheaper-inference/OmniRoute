## Mga Pagkumpleto ng Chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Mga Custom na Header

| Header                   | Direksyon | Paglalarawan                                                                                                                                                                                                                             |
| ------------------------ | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Request   | Itakda sa `true` upang lampasan ang cache                                                                                                                                                                                                |
| `x-omniroute-no-memory`  | Request   | Itakda sa `true` upang laktawan ang pag-inject ng memory + skills para sa request na ito (katulad ng no-cache; iniiwasan ang overhead sa token/gastos sa bawat tawag)                                                                    |
| `X-OmniRoute-Progress`   | Request   | Itakda sa `true` para sa mga event ng progreso                                                                                                                                                                                           |
| `X-Session-Id`           | Request   | Sticky session key para sa external session affinity                                                                                                                                                                                     |
| `x_session_id`           | Request   | Tinatanggap din ang variant na may underscore (direktang HTTP)                                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | Request   | Tag ng session/pag-uusap na ibinigay ng caller (ginagamit din ng memory). Kapag mayroon, pinapanatili nang eksakto sa `call_logs.session_tag` para sa pag-uugnay ng gastos sa bawat session (#8249) — hindi kailanman binubuo kapag wala |
| `Idempotency-Key`        | Request   | Key para sa deduplication (5s na palugit)                                                                                                                                                                                                |
| `X-Request-Id`           | Request   | Alternatibong key para sa deduplication                                                                                                                                                                                                  |
| `x-omniroute-connection` | Request   | I-pin ang isang single-model request sa isang koneksyon ng provider (account) gamit ang ID nito — tingnan ang [Pag-pin ng account sa bawat request](#account-pinning-per-request)                                                        |
| `X-OmniRoute-Cache`      | Response  | `HIT` o `MISS` (hindi streaming)                                                                                                                                                                                                         |
| `X-OmniRoute-Idempotent` | Response  | `true` kung na-deduplicate                                                                                                                                                                                                               |
| `X-OmniRoute-Progress`   | Response  | `enabled` kung naka-on ang pagsubaybay sa progreso                                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | Response  | Epektibong session ID na ginamit ng OmniRoute                                                                                                                                                                                            |
| `X-OmniRoute-Request-Id` | Response  | ID ng ugnayan ng request (kapag alam)                                                                                                                                                                                                    |
| `X-OmniRoute-Version`    | Response  | Bersyon ng build ng OmniRoute (laging naroroon)                                                                                                                                                                                          |
| `X-OmniRoute-Cost-Saved` | Response  | Halaga sa USD na naiwasan dahil sa cache sa isang HIT (para lamang sa mga cache hit)                                                                                                                                                     |
| `X-OmniRoute-Decision`   | Response  | Trace ng routing: `strategy=<name>; provider=<alias>; latency_ms=<n>` (ang `<name>` ay ang strategy ng combo, o `single` para sa request na hindi combo) — laging naroroon sa mga response sa pagkumpleto                                |

> Tala para sa Nginx: kung umaasa ka sa mga header na may underscore (halimbawa, `x_session_id`), i-enable ang `underscores_in_headers on;`.

#### Pag-pin ng account sa bawat request

Kapag maraming koneksyon (mga account o key) ang isang provider, karaniwang pumipili ang OmniRoute ng isa
gamit ang diskarte nito sa pagpili ng account. Sa halip, maaaring i-pin ng isang request ang isang partikular na koneksyon
gamit ang header na `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Kung saan makikita ang id.** Buksan ang pahina ng provider sa dashboard
  (**Dashboard → Mga Provider → <provider>**) at i-click ang `xxxxxxxx…` id chip sa isang row ng koneksyon
  — kokopyahin nito ang buong connection id.
- **Aling mga request ang sumusunod dito.** Mga single-model request (`provider/model`) sa
  `/v1/chat/completions`, `/v1/messages` at `/v1/responses`. Binabalewala ng mga combo ang header: mag-pin
  ng account para sa bawat hakbang ng combo sa pamamagitan ng sariling koneksyon ng hakbang.
- **Mahigpit ang pin, hindi lamang ito kagustuhan.** Eksklusibong ginagamit ang naka-pin na koneksyon. Ang
  pagkabigo sa loob ng request ay nagtatala ng cooldown ng account ngunit **hindi** lumilipat sa
  ibang account ng parehong provider.
- **Inaalis ng cooldown at quota ang pin.** Habang nasa cooldown ang naka-pin na koneksyon,
  ubos na ang quota, o bina-block ito ng isang patakaran sa quota, lilipat ang mga susunod na request sa iba pang
  koneksyon ng provider, katulad mismo ng trapikong hindi naka-pin.
- **Nabibigo ang mga hindi kilala o naka-disable na id.** Kapag wala ang isang id sa aktibong pool ng provider (na-delete,
  na-deactivate, o pagmamay-ari ng ibang provider), walang matitirang kwalipikadong account, kaya mabibigo ang request
  sa halip na tahimik itong i-route sa ibang lugar.

Nagpapadala ang Claude Code ng mga custom na header sa pamamagitan ng `ANTHROPIC_CUSTOM_HEADERS`. Ilagay ito sa `env` block
ng `~/.claude/settings.json`, o sa `.claude/settings.json` sa antas ng proyekto upang mag-pin ng ibang
account para sa bawat proyekto:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Pinagmulan: `src/sse/handlers/chat.ts` (pagbasa ng header), `src/sse/services/auth.ts` at
`src/sse/services/sessionAffinityPin.ts` (pag-aalis ng pin at pagsusuri kung wala ito sa pool).

> **Mga header ng telemetriya ng gastos:** kasama rin sa mga matagumpay na non-streaming response ang set ng telemetriya ng gastos na `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, nakapirming 10 decimal; `0.0000000000` para sa libre/walang presyo), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, at `X-OmniRoute-Fallback-Attempts` (kapag > 0 lamang), pati ang `X-OmniRoute-Request-Id` at `X-OmniRoute-Version`. Inilalabas ang mga ito ng mga chat completion, `/v1/responses`, `/v1/messages`, **at ng mga media endpoint** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, at `/v1/moderations` (palaging `0` ang gastos). Kinukuwenta ang gastos sa media ayon sa bawat modality (bawat larawan, bawat segundo, bawat character, bawat search-unit) kapag may available na presyo; kung wala, `0` (fail-open).

> **Semantika ng gastos sa cache hit:** sa isang HIT ng semantic cache (`X-OmniRoute-Cache-Hit: true`), walang ginagawang upstream call, kaya ang `X-OmniRoute-Response-Cost` ay `0.0000000000` (ang **incremental** na gastos sa pagsilbi ng hit). Hiwalay na iniuulat sa `X-OmniRoute-Cost-Saved` ang orihinal/dapat sana ay naging gastos. Dapat pagsamahin ng mga consumer ng billing ang `X-OmniRoute-Response-Cost` (walang gastos ang mga hit); maaaring pagsama-samahin ng analytics ng cache ang `X-OmniRoute-Cost-Saved`.

## Mga Eksklusibong Lease ng Pinamamahalaang Session

Ang eksklusibong pag-lease ng pinamamahalaang session ay isang opsyonal at client-neutral na kontrata sa pagruruta: isang aktibong may-ari
ang humahawak sa isang karapat-dapat na koneksyon ng OmniRoute. Hindi ito nagle-lease ng modelo, nangangailangan ng OAuth, kumikilala ng
partikular na client, o nangangailangan ng partikular na provider.

Ang API key na ginagamit sa pagpapatotoo ay dapat magkaroon ng scope na `lease:exclusive` at tahasang hindi bakanteng
listahan ng `allowedConnections`. Ipinapatupad ng hangganan ng mutation sa database ang dalawang field nang magkasama sa
paglikha ng key at sa mga bahagyang update.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Inilalantad ng matagumpay na mga tugon sa pagkuha, pag-renew, at pag-release ang mga timestamp, `state`, at ang eksaktong positibong
`generation`, ngunit hindi kailanman ang napiling koneksyon o mga kredensyal. Ibinibigay ng pag-renew at pag-release ang
generation sa JSON body:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Maaaring tahasang humiling ang aktibong may-ari ng lease ng display metadata na ligtas sa privacy para sa kasalukuyan nitong binding:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ang opsyonal na status action na ito ay nililimitahan ng opaque na may-ari, napatotohanang pinamamahalaang API key, at eksaktong
aktibong generation sa iisang transaksyon sa database. Ang `displayName` ay ang na-trim na naka-configure na
pangalan lamang ng koneksyon; ito ay `null` kapag walang ligtas na naka-configure na pangalan. Hindi kailanman nagpapalit ang OmniRoute ng
email o nabuong pagkakakilanlan ng account. Ang value ng provider ay isang hindi sensitibong display label at hindi kailanman
isang nabuong identifier ng compatible provider. Hindi isinasama ang mga kredensyal, token, cookie, raw na koneksyon o mga API
key id, owner hash, fencing secret, at panloob na data sa pagruruta.

Ang mga lookup na may maling key, maling may-ari, lipas na generation, nawawala, nag-expire, na-release, at na-invalidate ay
nagbabalik lahat ng parehong error na `409 LEASE_FENCE_STALE` nang walang metadata ng koneksyon. Ang client na nakatanggap ng tugon para sa paghihintay ng kapasidad ay walang aktibong binding na masusuri. Kapag inililipat ng pagruruta ang isang aktibong lease,
nananatiling valid ang parehong generation at atomikong ibinabalik ng status ang bagong binding, hindi kailanman ang luma.
Nananatiling hindi nagbabago ang mga kasalukuyang client dahil pinapanatili ng mga tugon sa pagkuha, pag-renew, pag-release, at paghihintay
ang dati nilang mga hugis.

Hindi binabago ng kontratang ito ng server ang stock na OpenAI Codex `/status`. Kasalukuyang iniuulat ng stock Codex ang
model provider nito at built-in na estado ng authentication/account ngunit hindi nito nire-render ang arbitraryong custom na
metadata ng provider account; dapat tawagin ng susunod na integrasyon ng client ang action na ito at magpasya kung paano
ipapakita ang `connection.displayName`.

Pagkatapos, ibinibigay ng bawat pinamamahalaang inference request ang parehong control header:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Ang eksaktong may-ari, generation, aktibong koneksyon, at napatotohanang API key ay agad na fine-fence
bago ang bawat sinusuportahang upstream attempt. Nabibigo ang pag-replay ng may-ari at generation gamit ang ibang key kahit
pinahihintulutan ng key na iyon ang parehong koneksyon. Hindi pine-persist, nila-log, pinananatili sa
request snapshot, o ipinapasa upstream ang mga raw na may-ari.

Ang pansamantalang kompetisyon ay nagbabalik ng HTTP `429` na may `Retry-After` at:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Ang ibig sabihin lamang ng tugon na ito ay hindi bakante ang karaniwang hanay ng mga karapat-dapat na koneksyon at bawat libreng kandidato ay
hawak ng aktibong lease ng ibang may-ari. Pinapanatili ng mga hindi sinusuportahang modelo/provider, hindi pagtugma sa policy, cooldown, quota,
health, at iba pang karaniwang pagkabigo sa eligibility ang kanilang mga kasalukuyang tugon ng OmniRoute.

### `x-omniroute-compression`

Override kada request ng compression plan. Pinakamataas ang precedence — nahihigitan nito ang override ng routing-combo,
ang aktibong profile, auto-trigger, at Default ng panel. Mga value:

| Value         | Epekto                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Walang compression para sa request na ito.                                                                               |
| `default`     | Ang Default profile na nagmula sa panel (binabalewala ang aktibong profile). Nananatiling naka-off ang mga lossy engine. |
| `safe`        | Dedup at whitespace folding lamang.                                                                                      |
| `allow-lossy` | Panatilihin ang operator plan para sa request na ito, kabilang ang mga summary at style rewrite.                         |
| `engine:<id>` | Isang engine kapag naka-enable, hal. `engine:rtk`. Opsyonal na pag-enable kada request para sa engine na iyon.           |
| `<combo>`     | Isang pinangalanang combo, unang itinutugma ayon sa pangalan (case-insensitive), at pagkatapos ayon sa id.               |

Mga tala:

- Binabalewala ang mga hindi kilalang value (hindi kailanman tinatanggihan ang request); nagpapatuloy ang resolution sa normal na precedence ng operator.
- Kung iisa ang pangalan ng maraming combo, ipasa ang **id** ng combo para sa isang deterministic na pagtutugma.
- Hindi maaaring piliin ayon sa pangalan ang combo na may pangalang `off` o `default` (inuunang bigyang-kahulugan ang mga keyword na iyon); tukuyin ang naturang combo gamit ang id nito.
- Ang master compression switch ay isang mahigpit na gate: kapag naka-disable sa pangkalahatan ang compression, hindi ito mae-enable ng header na ito.

Ibinabalik sa response header ang inilapat na plan:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

kung saan ang `<source>` ay isa sa `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, o `off`.

## Mga Embedding

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Mga available na provider: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Ang mga catalog id ay `provider/model` (halimbawa: `jina-ai/jina-embeddings-v5-omni-small`). Nareresolba rin ang mga bare Jina model id na nasa registry (halimbawa, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`). Para sa embed/rerank/classify/segment ng Jina, ginagamit muna ang mga credential ng dashboard na `jina-ai`; fallback lamang ang `JINA_AI_API_KEY` kapag walang dashboard key. Ang card na `jina-reader` ay para lamang sa Reader / `r.jina.ai` (`POST /v1/web/fetch`) at hindi kailanman naghahatid ng mga embedding o rerank.

Tumatanggap din ang mga registry model na nag-a-advertise ng multimodal support ng hanggang 32 provider-neutral na structured
item. Ang mga uri ng media item ay `text`, `image`, `audio`, `video`, at `document`. Ang kanilang media `source`
ay alinman sa `{"type":"url","url":"https://..."}` o
`{"type":"base64","data":"...","media_type":"..."}`.

Tumatanggap din ang Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
at ang family alias na `jina-ai/jina-embeddings-v5-omni` → omni-small) ng mga native
EmbeddingsV5Request doc ng Jina at **ipinapasa ang mga ito nang buo** sa `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Ang mga native na value na `{ image | audio | video | pdf }` ay maaaring pampublikong HTTPS URL, `data:` URI, o raw
base64. Hindi ginagawang string ng OmniRoute ang mga object na iyon o kinukuha ang mga native image URL — ang Jina mismo ang kumukuha
ng pampublikong media. Ipinapasa ang mga karagdagang field ng Jina (`task`, `normalized`, `truncate`, `embedding_type`).
Tinatanggihan pa rin ng mga text-only na Jina SKU ang mga doc na hindi text.

Mga limitasyon sa seguridad at transport:

- Dapat pampublikong HTTPS ang mga remote media URL. Kinukuha
  sa server-side ang mga canonical na `{type,source:url}` item (muling pag-validate ng redirect, timeout, mga limitasyon sa laki, pampublikong DNS, pag-pin ng koneksyon) at
  ini-inline bago ang provider call. Ipinapasa nang as-is ang mga Jina-native na `{image:"https://..."}` item
  pagkatapos ng parehong pagsusuri sa pampublikong HTTPS; kinukuha ng Jina ang URL.
- Limitado ang inline base64 media sa 8 MiB na na-decode bawat item at 16 MiB na na-decode sa kabuuan ng request.

Pagsasalin para sa provider (hindi kailanman ipinapasa nang hindi binabago ang mga canonical item):

- Mga Jina multimodal model: ang bawat top-level item ay nagiging isang object na may modality key
  (`text` / `image` / `audio` / `video` / `pdf`) gamit ang mga data URI para sa inline media; isang vector bawat
  top-level item.
- Pamilya ng Gemini Embedding 2: ang isang top-level array ay nagiging iisang native
  `models/{model}:embedContent` request na may `content.parts` (`text` o `inline_data`).
- llama.cpp (`llama-cpp/<model>`, anumang model na na-load ng lokal na server): ang mga canonical na `text` item
  ay nagiging mga plain string, at ang `image` / `audio` / `video` ay nagiging tig-isang
  `{"content": [part]}` object, gamit ang mga chat content part ng llama-server (`image_url`,
  `input_audio` na may format na `wav` / `mp3` / `flac`, `input_video`) na may inline data; isang vector
  bawat top-level item. Dapat tumakbo ang server gamit ang `--embedding --mmproj …`; kung walang projector,
  mismong server ang tatanggi sa media. Hindi sinusuportahan ang `document`.
- Tinatanggihan ng mga unknown/dynamic model na walang tahasang modality metadata ang structured input gamit ang HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Nagbabalik ng HTTP 400 ang mga hindi sinusuportahang kombinasyon ng model/modality sa halip na piliting i-convert ang item. Patuloy na
ipinapasa nang hindi binabago ang mga non-input extension field sa mga legacy string/token request.

```bash
# Ilista ang lahat ng embedding model
GET /v1/embeddings
```

## Pagbuo ng Larawan

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Kabilang sa mga available na provider ang OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokal), ComfyUI (lokal).

Nagbabalik ang `n` ng `n` larawan sa `data[]`. Ang mga provider na ang upstream API ay nagbabalik ng isang larawan sa bawat tawag
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) ay nakakakuha ng `n` magkakahiwalay na upstream na tawag, na may pinakamaraming 4 na sabay-sabay. Ang
nakapirming `seed` ay dinaragdagan batay sa index ng tawag (`seed`, `seed + 1`, …), kaya magkakaiba ang mga larawan ngunit nananatiling
nauulit ang mga resulta. Nililimitahan ang `n` sa 10. Nabibigo ang buong request kung mabigo ang alinmang tawag. Ang listahan
ng mga fan-out format ay `SINGLE_IMAGE_FANOUT_FORMATS` sa
`open-sse/handlers/imageGeneration/fanOut.ts`.

Muling ginagamit ng ZenMux ang kasalukuyang koneksyon ng API key at tinatanggap nito ang mga prefix na `zenmux/` o `zm/`:

- Ginagamit ng `zenmux/openai/gpt-image-2` ang OpenAI Images API ng ZenMux. Kabilang sa mga opsyon ang `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, at `response_format`.
- Ang iba pang publisher, gaya ng `zm/meta/muse-image-1.0`, ay gumagamit ng endpoint na `:predict`
  ng Vertex AI ng ZenMux. Ang `n` ay minamapa sa `sampleCount`, ang `aspect_ratio` sa `aspectRatio`, at ang `image_size`
  (`1K`, `2K`, `4K`) sa `sampleImageSize`. Ang isang pixel na `size` ay nagbibigay lamang ng aspect ratio,
  at hindi ng garantisadong mga dimensyon sa pixel. Nag-iiba ayon sa modelo ang mga sinusuportahang ratio, resolution, at bilang.
- Ang `zm/inclusionai/ming-image-0.1-design` ang pumipili ng sarili nitong mga dimensyon. Huwag isama ang `size`,
  `aspect_ratio`, at `image_size`; nagbabalik ng HTTP 400 ang mga tahasang value. Maaaring humiling ng PNG, JPEG, at WebP
  gamit ang `output_format`.

Sinusuportahan ng integrasyong ito ang pagbuo ng larawan mula sa teksto, hindi ang pag-edit gamit ang sangguniang larawan. Ang output ng Vertex
ay ginagawang pare-pareho sa `data[].b64_json`; nagbabalik ang `response_format: "url"` ng upstream na
HTTPS URL o base64 data URL kapag mga byte lamang ng larawan ang available. Ang mga walang laman/na-filter na output
ay nagbabalik ng error sa halip na walang-lamang tagumpay. Nakadepende sa ZenMux account ang access sa modelo.
Tingnan ang [Vertex API ng ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) at
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Ilista ang lahat ng modelo ng larawan
GET /v1/images/generations
```

Pinipili ng `model` ang OCR provider sa pamamagitan ng prefix na `provider/model`; ang model id na walang prefix (hal.

| ----------------------------- | -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (o `mistral-ocr-latest` lamang) | Synchronous — direktang ibinabalik ang response mula sa iisang upstream na tawag.                                               |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                  | Asynchronous na upstream (`analyze` + poll) — tingnan sa ibaba.                                                                 |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                      | Synchronous, sa pamamagitan ng partner endpoint na `openapi/chat/completions` ng Vertex AI — tingnan sa ibaba para sa auth/URL. |

Sumasagot ang lahat ng tatlong provider gamit ang parehong body na may anyong Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Daloy ng pag-poll ng Azure Document Intelligence

Asynchronous ang `analyze` API ng Azure Document Intelligence: nagbabalik ang paunang request ng
`Operation-Location` header sa halip na body, at kailangang paulit-ulit na i-poll ang resulta. Ang handler
(`open-sse/handlers/ocr.ts`) ay nagpo-poll sa URL na iyon bawat segundo nang hanggang 30 pagsubok, at agad na nabibigo (hindi
na nagpapatuloy sa pag-poll) kapag may hindi `ok` na poll response o status na `"failed"`, at nagbabalik ng `504` kung ang
operasyon ay tumatakbo pa rin matapos maubos ang nakalaang bilang ng mga pagsubok. Ang panghuling response ng Azure ay
ginagawang pare-pareho sa parehong anyong `pages`/`markdown` na ginagamit ng Mistral bago ito ibalik sa
tumatawag, kaya hindi kailangang gumawa ng client code ng espesyal na paghawak para sa provider.

### Auth at resolution ng endpoint para sa Vertex AI DeepSeek OCR

Muling ginagamit ng `vertex-deepseek-ocr` ang parehong authentication ng Vertex AI na sinusuportahan na ng OmniRoute para sa
trapiko ng chat/larawan (`open-sse/executors/vertex.ts`): ang API key ng koneksyon ay alinman sa
Service Account JSON credential (ipinagpapalit para sa panandaliang OAuth access token sa pamamagitan ng JWT-bearer
flow) o isa nang nagawang OAuth access token na ginagamit nang walang pagbabago. Ang upstream endpoint URL ay ang generic na
partner endpoint na `openapi/chat/completions` ng Vertex, na binubuo mula sa project at
region ng koneksyon — laging nangingibabaw ang tahasang `providerSpecificData.project`/`providerSpecificData.region`;
kung hindi, kinukuha ang project mula sa `project_id` ng Service Account JSON at nagde-default ang region
sa `us-central1`. Ang parehong resolution ay nangyayari sa `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), na ginagamit ng
`src/app/api/v1/ocr/route.ts` bago ipadala sa `handleOcr`.

### Mga presyo ng modelo (`pricing`)

Ang isang entry ay may `pricing` object kapag alam ng OmniRoute ang presyo ng modelo. Ang presyo ay
nagmumula sa talahanayan ng pagpepresyo na ginagamit ng cost accounting: mga built-in na default, naka-sync na presyo, at
mga override na itinakda sa pamamagitan ng `/api/pricing`. Mga list price ang mga ito, kaya nagpapakita rin ang mga subscription provider
ng presyo sa bawat token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Mga field                                                       | Yunit                           | Mga tala                                                                                                                                                                                   |
| --------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD bawat token, decimal string | Compatible sa OpenRouter, at hindi kailanman gumagamit ng exponent notation. Lumilitaw lang ang dalawang cache field kapag may presyo ang cache.                                           |
| `input`, `output`, `cached`, `cache_creation`                   | USD bawat 1M token, number      | Mga field mula sa mga naunang bersyon ng catalog, na pinanatili para sa mga kasalukuyang client. Lumilitaw din ang `reasoning` at `long_context` kapag mayroon ng mga ito ang pricing row. |

- Ang mga **combo** ay gumagamit ng presyo ng una nilang nakikitang target. Pumipili ng
  target sa oras ng request ang mga built-in na `auto/*` combo, kaya wala silang `pricing`.
- Nagpapakita ang mga **libreng modelo** ng `"0"` (at `0`) kapag zero ang presyo ng mga ito. Ang modelong walang pricing row
  ay nagpapakita rin ng `"0"` kapag minarkahan ito ng catalog bilang libre (`free: true`) o nakalista ito sa built-in na catalog
  ng mga libreng modelo.
- **Hindi alam na presyo:** walang `pricing` key ang entry.
- Ang mga **provider na sinusukat ayon sa credit** (gaya ng Kiro) ay naniningil bawat request sa halip na bawat token. Pinapanatili ng kanilang
  mga entry ang mga numeric na per-1M field na mayroon sila dati at walang mga per-token string field.
- Kinokopya ng mga **variant** (mga reasoning-effort ID, mga no-thinking alias, at mga discovery at gateway mirror)
  ang presyo ng modelong pinagruruta nila.
- Mga base rate lamang ang nasa mga field. Hindi binabago ng mga long-context tier (ang numeric na `long_context` field) at
  mga service-tier multiplier (halimbawa, Codex fast o flex) ang `prompt` o
  `completion`.
- Pareho ang object para sa bawat istilo ng authentication, kabilang ang isang Anthropic-style
  request na may `x-api-key` at `anthropic-version` (nanatiling `{ "object": "list",
"data": [...] }` ang response). Implementasyon: `src/app/api/v1/models/catalogPricing.ts`.

### Mga prefix ng model ID (`?prefix=`)

Karamihan sa mga modelo ay inilalathala sa ilalim ng isang **provider prefix**. Ang prefix na makukuha mo ay kinokontrol ng
`MODELS_CATALOG_PREFIX_MODE` feature flag, at maaaring i-override **sa bawat request** gamit ang isang
query parameter — kapaki-pakinabang para sa isang client na nais ng malinis na listahan nang hindi binabago ang server-wide
na setting para sa lahat ng iba pa:

```bash
GET /v1/models?prefix=alias        # isang ID bawat modelo — ang maikling alias prefix
GET /v1/models?prefix=dual         # parehong anyo (default ng server)
GET /v1/models?prefix=canonical    # ang buong provider-id prefix lamang
```

| Mode        | Inilalabas                                               | Mga tala                                                                                                                                                                                                          |
| ----------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **at** `claude/claude-sonnet-4-6` | **Default.** Parehong niruruta ng dalawang ID ang iisang modelo; pinanatili upang patuloy na gumana ang mga client config na nag-hardcode ng alinmang anyo. Halos dinodoble nito ang catalog.                     |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Isang entry bawat modelo. Inilalabas pa rin ng mga provider na walang natatanging alias ang kanilang entry, kaya walang nawawala.                                                                                 |
| `canonical` | `claude/claude-sonnet-4-6`                               | Isang entry bawat modelo sa ilalim ng buong provider-id prefix. Inilalabas din dito ng mga provider na walang natatanging alias (hal. `antigravity/…`, `agy/…`) ang kanilang nag-iisang ID, kaya walang nawawala. |

Maaari ring makilala ang isang `dual`-mode mirror nang wala ang query parameter: mayroon itong `parent`
field na tumuturo sa pangunahing ID.

Dapat humiling ang mga client na nagre-render ng model picker ng `?prefix=alias` — ito ang ginagawa ng
[OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md).

### Mga discovery filter (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

Tumatanggap ang `GET /v1/models` ng mga opsyonal na discovery filter. Kung wala ang alinman sa mga ito, hindi
nagbabago ang response. Nililimitahan ng mga ito ang catalog na nakikita na ng caller (unang inilalapat ang mga pahintulot ng API key),
at isinasagawa ang mga ito bago ang OpenAI-style na `limit` / `after` paging:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # dapat true ang bawat nakalistang capability
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` ng catalog; ang mga row na walang ganito ay `chat`
GET /v1/models?q=sonnet&limit=10                           # case-insensitive na pagtutugma sa ID o pangalan
```

| Parameter     | Mga Value                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | hindi negatibong integer, na inihahambing sa `context_length`                                       |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 character                                                                                     |

Ang hindi kilalang value, o isang `min_context` na hindi isang hindi negatibong integer (halimbawa, `1.5`),
ay nagbabalik ng HTTP `400`, at inililista ng mensahe ang mga wastong value. Implementasyon:
`src/app/api/v1/models/catalogFilters.ts`.

### Maikling listahan ng modelo (`POST /v1/models/query`)

Ang `POST /v1/models/query` ay nagbabalik ng isang maikli at deterministikong listahan mula sa parehong catalog, na may parehong
auth at visibility sa bawat key gaya ng `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Opsyonal ang bawat field. Tumatanggap ang `capabilities` at `exclude` ng array o string na pinaghihiwalay ng kuwit;
inihahambing ang `max_output` sa `max_output_tokens`. Inaayos ang mga resulta ayon sa `owned_by`, pagkatapos ay sa `id`.
Ang default ng `limit` ay `20`, at nililimitahan sa `100` ang mga value na higit sa `100`. Ang di-wastong JSON, hindi kilalang
field, o di-wastong value ay nagbabalik ng HTTP `400`.

### Mga indibidwal na nakatagong chat model

Ang modelong minarkahang **Nakatago** sa page ng provider nito ay hindi isinasama sa catalog at tinatanggihan
nang may HTTP `404` / `model_not_found` kapag tahasang hiniling. Ginagamit ng pagsusuri ang natukoy na
provider at modelo, kabilang ang mga alias ng provider, mga prefix ng node ng compatible na provider, at
mga default ng koneksyon. Nilalampasan ng combo ang mga nakatagong target at maaari itong gumamit ng nakikitang kaparehong modelo; kapag walang
natitirang executable na target, ibinabalik nito ang parehong error code. Magkakabisa ang pag-alis sa pagkakatago sa susunod na
request. Hindi itinatago ng mga visibility override na para lamang sa image ang chat model na may parehong ID.

Hiwalay ang setting na ito ng indibidwal na modelo sa
[mga allow/deny list para sa paglalantad ng modelo](../routing/MODEL_EXPOSURE_LIST.md), na nagfi-filter sa pag-anunsyo ng catalog
at mga kandidato para sa auto-routing habang pinananatili ang tahasang dispatch. Patuloy na nalalapat nang hiwalay ang mga pahintulot sa modelo
ng API key. Nananatiling `dual` ang default na prefix mode ng catalog.

### Mga variant ng modelong walang thinking

Para sa mga Claude model na may kakayahang mag-thinking, nag-aanunsyo rin ang `/v1/models` ng **walang-thinking** na variant na ang id ay may prefix na `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Kapag pinili ang id na ito (hal., sa isang Claude Code config na palaging naglalakip ng `thinking` block), muli itong tinutukoy sa tunay na `<provider>/<model>` habang pinipigilan ang reasoning — `thinking:{type:"disabled"}` sa `/v1/messages` path, o inaalis ang mga field na `reasoning`/`reasoning_effort` sa `/v1/chat/completions` path. Inililista lamang ang variant para sa mga Claude-family model na sumusuporta sa thinking **at** sumusunod sa `disabled` (kaya, hal., hindi isinasama ang mga adaptive-only model na tumatanggi sa `disabled`). Maaaring sapilitang i-on o i-off ng mga operator ang variant para sa bawat modelo sa pamamagitan ng `ModelSpec.noThinkingAlias`.

## Pagbuo ng audio gamit ang ElevenLabs

Mag-configure ng koneksyon sa provider na `elevenlabs` sa OmniRoute gamit ang iyong ElevenLabs API key.
Nagpapatotoo ang mga client gamit ang kanilang **OmniRoute** key (`Authorization: Bearer $OMNIROUTE_API_KEY`);
ibinibigay ng gateway ang nakaimbak na provider key bilang `xi-api-key`. Huwag kailanman magpadala ng ElevenLabs key
bilang gateway bearer token.

| Paraan | Path                        | Tugon                                      | Kategorya ng endpoint ng API key |
| ------ | --------------------------- | ------------------------------------------ | -------------------------------- |
| POST   | `/v1/sound-generation`      | Mga native audio byte                      | `elevenlabs`                     |
| POST   | `/v1/music`                 | Mga native audio byte                      | `music`                          |
| POST   | `/v1/music/stream`          | Mga streaming audio byte                   | `music`                          |
| POST   | `/v1/music/detailed`        | Native multipart audio at composition plan | `music`                          |
| POST   | `/v1/music/detailed/stream` | Native SSE metadata at mga audio chunk     | `music`                          |
| POST   | `/v1/music/plan`            | JSON composition plan                      | `music`                          |

Dinadagdagan ng mga endpoint na ito ang mga kasalukuyang route na `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` at `/v1/speech-to-text`. Pinapanatili ang mga native JSON field
at query parameter tulad ng `output_format` at `enable_logging`.
Pinananatili ng mga tugon ng `/v1/music/detailed` ang kanilang mga multipart boundary; i-parse ang mga ito bilang multipart.
Ibinabalik ng `/v1/music/detailed/stream` ang `text/event-stream` na may composition metadata at
mga base64 audio chunk sa mga SSE event. Sinusuportahan ng lahat ng anim na route ang CORS preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Isang maikling sound effect. Tagal: 0.5 hanggang 30 segundo.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Ang tagal ng musika ay ipinapahayag sa millisecond: 3000 hanggang 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Gamitin ang `/v1/music/stream` na may parehong JSON body para sa paunti-unting paghahatid ng audio. Ang composition
ay tumatanggap ng eksaktong isa sa `prompt` o `composition_plan`; kinakailangan ng `/v1/music/plan` ang `prompt`
at opsyonal na tumatanggap ng `source_composition_plan`. Pinapanatili ng mga native schema ang mga karagdagang
provider field upang makarating sa ElevenLabs ang mga bersyon ng composition plan at mga opsyon sa fine-tuning.

Tinatanggap din ng pinag-isang endpoint na `/v1/music/generations` ang `elevenlabs/music_v1`,
`elevenlabs/music_v2` at `elevenlabs/music_v2_5`. Kapag may aktibong koneksyon sa ElevenLabs,
inilalantad ng catalog ng musika ang mga model na ito. Ibinabalik ng endpoint na ito ang
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Nasa
segundo ang field nitong `duration` at minamapa ito sa `music_length_ms`; inuuna ang tahasang `music_length_ms`.
Minamapa ang `instrumental` sa `force_instrumental`, at inuuna ang native field.
Gamitin ang mga native streaming endpoint para sa streaming at ang native composition endpoint
para sa mga request na pinapatakbo lamang ng isang composition plan.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ipinapatupad ang mga paghihigpit sa endpoint, model, budget, at koneksyon bago ang isang upstream call. Ibinabalik ng mga native
route ang mga upstream status code at error body nang walang pagbabago, kabilang ang `402` para sa paghihigpit ng plan
at `429` para sa limitasyon ng quota. Pinapanatili ang mga header na `character-cost`, `song-id`, `request-id` at `retry-after`
kapag naroroon. Hindi ginagarantiya ng libreng balanse ng credit ang access sa bawat
music model, output format, o feature ng API: ang ElevenLabs ang nagpapasya sa karapatan sa access para sa bawat request.
Pinapanatili ng pinag-isang endpoint ang mga error status code sa normalized error envelope ng OmniRoute.

Mga upstream contract: [mga sound effect](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[komposisyon ng musika](https://elevenlabs.io/docs/api-reference/music/compose) at
[mga detalye ng streaming music](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Mga provider node para sa rerank:** Ang `POST /v1/rerank` ay nagru-route rin sa mga OpenAI-compatible na provider node
> (oMLX, vLLM, Infinity, TEI sa likod ng isang gateway, …) na tinutukoy bilang `<node-prefix>/<model>`. Ang mga loopback
> node (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ay palaging maaaring gamitin, gayundin ang mga hostname na
> inililista ng operator sa `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (hal. pangalan ng serbisyo ng Docker/Compose gaya
> ng `http://reranker:8080/v1`; direktang tinatawagan ang mga ito at hindi kailanman dumaraan sa `HTTP(S)_PROXY` o sa
> naka-pin na proxy ng isang koneksyon). Ang mga node sa anumang iba pang
> host — isang LAN box o Tailscale peer — ay maaari lamang gamitin kapag pinagana ng operator ang
> feature flag na `RERANK_REMOTE_PROVIDER_NODES` **at** pumasa ang base URL ng node sa patakaran sa
> outbound URL ng provider (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Tinatawag ng hakbang sa rerank ng memory engine ang route na ito sa pamamagitan ng
> loopback, kaya ang parehong panuntunan ang namamahala sa `rerankProviderModel` sa mga setting ng Memory.
>
> **Mga anyo ng lokal na server:** Tinatawag ang node sa `<base>/v1/rerank` at, kapag 404, sa `<base>/rerank`
> (Infinity, TEI). Taglay ng upstream body ang parehong baybay ng Cohere/OpenAI (`documents`,
> `return_documents`) at baybay ng TEI (`texts`, `return_text`), at ginagawang normal ang upstream response
> sa Cohere envelope: ang hubad na `[{index, score, text}]` ng TEI, ang `{results: [{index, score}]}`
> mula sa mga manipis na gateway, at ang istilong Voyage na `{data: [...]}` ay ibinabalik lahat sa client bilang
> `{results: [{index, relevance_score, document?}]}`, inayos ayon sa score at nilimitahan sa `top_n`.

> **Pagtuklas ng provider node:** Lumalabas sa `GET /v1/models`
> sa ilalim ng prefix ng node ang mga model sa isang OpenAI-compatible na provider node. Ang mga row na walang metadata ng endpoint (karaniwan sa mga lokal na listing ng `/v1/models`)
> ay nagmamana ng `apiType` ng node, kaya ang mga model ng isang `embeddings` node ay `type: "embedding"` at ang mga
> model ng isang `rerank` node ay `type: "rerank"` sa halip na gumamit ng chat bilang default; nananatiling
> mas prayoridad ang isang tahasang `supportedEndpoints` sa isang naka-sync o manual na idinagdag na row.

### Exa at Tavily `provider_options`

Binabasa ng Exa at Tavily ang mga field na partikular sa provider mula sa isang namespaced na bag: `provider_options.exa` (o `provider_options["exa-search"]`) at `provider_options.tavily` (o `provider_options["tavily-search"]`). Ang mga susi lamang sa ibaba ang ipinapasa. Ang bawat isa ay sinusuri laban sa sarili nitong Zod schema sa `open-sse/handlers/search/providerOptionsPassthrough.ts`, at ang isang susi na may maling uri ay nahuhulog. Anumang iba pang susi ay binabalewala, kabilang ang auth, base URL, `stream` at `outputSchema`. Ang mga flat key na ginagamit ng ibang mga provider (`cx`, `depth`, ...) ay gumagana tulad ng dati.

| Provider | Mga patlang sa pinakamataas na antas                                                                                                                                                                                                                                                                                                                                      | Nested                                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flat primitives), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                              | Pinagsama `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` sa default `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                     |

Palaging panalo ang mga generic na field: `query`, `max_results`, `filters` (mga domain), `country` at ang paksang hinango mula sa `search_type`. Sa Exa, pinapanatili ng `search_type: "news"` `category: "news"`. Tumatanggap din ang Tavily `search_type: "finance"` (`topic: "finance"`).

Ang gastos sa paghahanap ng Firecrawl ay naitala sa bawat panimulang bloke ng 10 ibinalik na resulta, sa $0.002 (2 credits) sa isang bloke at hindi bababa sa isang bloke bawat tawag ( [Firecrawl billing](https://docs.firecrawl.dev/billing) ): Ang 11 resulta ay nagkakahalaga ng $0.004.

Naabot na ngayon ng generic `time_range` ang parehong provider: Ang Exa ay nakakakuha ng `startPublishedDate` (ISO timestamp) at Tavily ay nakakakuha ng `start_date` (`YYYY-MM-DD`). Ino-override ng isang tahasang petsa sa `provider_options` ang naka-map.

Ang mga resulta ng Exa ay nagpapanatili `id`, `highlight_scores`, `summary`, `subpages`, `entities` at `extras` sa `provider_raw`. Ang mga resulta ng Tavily ay nagpapanatili `images` at `favicon`.

Ang gastos sa paghahanap ng linkup ay naitala sa $0.005 para sa `depth` `fast` at `standard` at $0.05 para sa `deep` ( [Pagpepresyo ng linkup](https://docs.linkup.so/pages/documentation/development/pricing) ), kung `depth` ay nagmula sa `provider_options` o sa mga setting ng koneksyon.

Ang Exa `type: "lite"` (Exa 3.0) ay tumatanggap ng mas maliit na hanay ng mga field at tinatanggihan ang buong kahilingan kapag nakatakda ang anumang ibang field. Para sa lite, `additionalQueries`, `systemPrompt` at bawat `contents` key maliban `text` at `highlights` ay ibinababa bago ang tawag. Ang hindi na ginagamit na `subpages`, `subpageTarget`, `highlights.numSentences` at `highlights.highlightsPerUrl` ay hindi na naipapasa.

Ang cost accounting ay ang flat registry `costPerQuery`, maliban sa Exa, na sumusunod sa sariling pagpepresyo ng Exa: $0.007 bawat tawag para sa `auto` (at ang legacy `fast`) o $0.004 para sa `lite` (at ang legacy `instant`), na sumasaklaw sa 10 resulta; $0.001 para sa bawat karagdagang resulta; at $0.001 bawat ibinalik na resulta kapag itinakda ang `contents.summary`. Ang Tavily ay naitala sa 1 credit ($0.008) para sa `search_depth` `basic`, `fast` at `ultra-fast`, at 2 credits ($0.016) para sa `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) ). Ang isang tawag na may `auto_parameters: true` na ina-upgrade ni Tavily sa advanced ay naitala pa rin sa 1 credit.

| Paraan | Path            | Paglalarawan                                                               |
| ------ | --------------- | -------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Kunin/i-scrape ang isang URL — body na bina-validate ng `v1WebFetchSchema` |

**Auth:** Bearer API key (`extractApiKey` + `isValidApiKey`). Ipinapatupad ang policy sa pamamagitan ng `enforceApiKeyPolicy`.

**Fallback na isinasaalang-alang ang quota (#8297):** kapag walang ibinigay na tahasang `provider`, ang pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ay
sinusuri sa nakapirming
pagkakasunod-sunod ng priyoridad (fill-first) — nilalaktawan ang isang provider na naka-configure ngunit nalimitahan ang rate
sa halip na agad ihinto ang request, at ang isang retryable/quota upstream failure
(palaging HTTP 429; 402/403 para sa mga quota-style free tier ng Firecrawl/Tavily/TinyFish —
hindi para sa Jina Reader, at hindi kailanman para sa karaniwang 400 bad request) ay lilipat sa
susunod na hindi pa nasusubukang provider na may credential habang pinoproseso ang request. Kapag naubos na ang lahat ng provider sa
pool, magbabalik ang endpoint ng iisang `429` (na may `Retry-After`
header) sa halip na ang dating generic na `400`. Kapag tahasang hiniling ang isang `provider`,
**walang** tahimik na fallback — ilalabas ng tahasang piniling provider na nalimitahan ang rate o nabigo
ang sarili nitong error (`429` kung nalimitahan ang rate, kung hindi ay ang upstream
status).

### Raw kumpara sa Mga Porsiyento ng Quota na Inayos Ayon sa Cutoff

Kapag ginagamit ang `/api/usage/om-usage`, dapat tandaan ng mga tumatawag ang pagkakaiba sa pagitan ng
mga porsiyentong ipinapakita ng **plain-text output** at ng nakaayos na **JSON output**:

| Aspeto                    | Plain-text na format (`/api/usage/om-usage` / `@@om-usage`)                                                      | JSON format (`?format=json`)                                                      |
| :------------------------ | :--------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| **Output field**          | `NN% left` (hal., `20% left`)                                                                                    | `provider.quotas` / `providers[].quotas`                                          |
| **Pagsukat**              | **Nagagamit na allowance na inayos ayon sa cutoff**: natitirang kapasidad na lampas sa cutoff threshold          | **Raw upstream quota**: hindi inayos na pagsukat ng provider                      |
| **Cutoff scaling**        | Ini-scale sa pamamagitan ng `effectiveRemainingPercent()` upang mabasa ang protektadong reserba bilang `0% left` | Wala (mga raw snapshot value ayon sa iniulat ng provider)                         |
| **Threshold data**        | Isinasama sa ipinapakitang porsiyento                                                                            | Naka-store sa `quotaWindowThresholds` kada koneksyon (o sa mga default ng server) |
| **Pangunahing gumagamit** | Mga interactive CLI, terminal prompt, at human operator                                                          | Mga programmatic integration, dashboard, analytics, at billing tracker            |

#### Ang Formula sa Pag-adjust ng Cutoff

Sinusuportahan ng OmniRoute ang mga proactive quota cutoff upang maiwasang maubos ang upstream (kino-configure sa pamamagitan ng
`quotaWindowThresholds` ng koneksyon, mga default ng provider, o mga global resilience setting). Kapag may aktibong cutoff threshold
(hal., `cutoff = 25%`) sa isang quota window, kinakalkula ng text renderer ang natitirang allowance bilang:

- Kung `remaining <= cutoff`: nagbabalik ng `0%`.
- Kung `remaining > cutoff`: nagbabalik ng `((remaining - cutoff) / (100 - cutoff)) * 100`.

Nire-round ng naka-format na text output ito sa pinakamalapit na integer (`Math.round(...)`).

#### Halimbawang Naglalarawan

Isaalang-alang ang isang provider window na may **60% raw usage** (kaya **40% raw remaining quota**) at may naka-configure na
**25% remaining-quota cutoff** threshold:

| Representasyon                | Pagkalkula                                         | Natitira |            Ipinahihiwatig na Nagamit             |
| :---------------------------- | :------------------------------------------------- | :------: | :----------------------------------------------: |
| **Raw JSON (`?format=json`)** | Upstream snapshot (`quotas[window]`)               | **40%**  |                     **60%**                      |
| **Text format (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (kung kinakalkula ang `100 - remaining`) |

- **Bakit 20% left ang ipinapakita ng text:** Sa 40% pisikal na quota na natitira sa account, 25% ang nakalaan dahil sa
  cutoff policy. May 15% lamang na natitira sa tumatawag mula sa 75% nagagamit na headroom bago huminto ang router sa
  pag-route sa koneksyong ito. Tinitiyak ng pag-scale na magsesenyas ang koneksyon na ubos na ito (`0% left`) sa mismong sandaling
  titigil ang pag-route.
- **Bakit pinananatili ng JSON ang mga raw value:** Ibinabalik ng JSON payload ang eksaktong provider snapshot (`UsageSnapshot`)
  upang magkaroon ang mga external tool ng access sa totoong upstream utilization at sa connection-level na
  `quotaWindowThresholds` nang walang lossy scaling sa server side.

#### Gabay sa Migration ng Consumer

Kung ang isang panlabas na integrasyon (gaya ng editor plugin o agent extension) ay dating nag-scrape ng text
endpoint (`NN% left`) at kinakalkula ang porsiyentong nagamit bilang `100 - NN`, ang paglipat sa `?format=json` ay nangangahulugang:

- Ipapakita ng pagbasa sa mga raw JSON value ang **aktuwal na paggamit sa upstream** (60% ang nagamit sa halimbawa sa itaas).
- Kung nais ng integrasyon na panatilihin ang semantika ng nagagamit na allowance ng text endpoint, maaari nitong suriin
  sa client side ang pormula ng epektibong natitira gamit ang `quotaWindowThresholds` para sa mga override sa antas ng koneksyon.

### Epekto sa latency

Kapag may HIT sa semantikong cache, inihahatid ang tugon mula sa cache **nang walang upstream
na tawag**, kaya halos zero ang iniulat na `X-OmniRoute-Response-Latency`
(anuman ang orihinal na upstream latency). Dapat suriin ng mga client na sensitibo sa latency
(benchmarking, pagsubaybay sa p50/p99) ang response header na
`X-OmniRoute-Cache-Latency`:

| Value       | Kahulugan                                                                     |
| ----------- | ----------------------------------------------------------------------------- |
| `synthetic` | Inihatid ang tugon mula sa cache; ang latency ay hindi tunay na upstream time |
| _(wala)_    | Tugon mula sa tunay na upstream na tawag                                      |

### Pag-bypass ng cache kada key

Maaaring hindi gumamit ng mga API key ng mga pagbasa sa semantikong cache sa pamamagitan ng `cacheDefaultMode`:

| Value    | Gawi                                                                    |
| -------- | ----------------------------------------------------------------------- |
| `legacy` | Normal na gawi ng cache (default)                                       |
| `bypass` | Ganap na laktawan ang paghahanap sa cache; palaging tumawag sa upstream |

Itakda sa paggawa ng key (`POST /api/keys`) o pag-update (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Pag-bypass kada request

Maaaring i-bypass ng anumang request ang cache anuman ang mga setting ng key:

```

```

Para sa mga naka-sync/na-import na modelo, tumatanggap ang `PUT /api/provider-models` ng `provider`, `modelId`, at
`maxOutputTokenOverride`: itinatakda ng isang positibong integer ang manu-manong limitasyon sa output token, at
inaalis ito ng `null` upang ibalik ang default. Ibinabalik ng `GET /api/provider-models?provider=<provider>` ang mga

ang runtime na kakayahang `max_output_tokens` at nananatili ito pagkatapos muling i-sync ang modelo. Nagbibigay ang page
ng OpenAI-compatible na provider ng parehong mga kontrol sa pag-edit/pag-clear at minamarkahan ang mga modelong may tahasang suporta sa vision.

Inaangkop ng mga custom na Chat Completions node ang tahasang pag-opt out sa reasoning para sa upstream backend. Awtomatikong
pinipili ng matagumpay na pagsubok sa koneksyon ang mga kontrol ng chat template para sa bawat eksaktong model ID
na ang entry sa `/models` ay nagpapatunay ng kinikilalang value ng `owned_by`: `vllm`, `sglang`, o `llamacpp`.
Maaaring panatilihin ng mga transparent na OpenAI-compatible wrapper ang orihinal na entry ng modelo sa loob ng isang nested na
`openai` object; sinusundan ng detection ang hanggang tatlong ganitong envelope. Pinananatili ng mga modelong may nawawala, hindi kilala, o
magkasalungat na ownership ang karaniwang gawi ng OpenAI. Muling ginagamit ng detection ang kasalukuyang request sa catalog,
hindi ito bumubuo ng mga completion token, at nai-invalidate ito kapag nagbago ang endpoint ng koneksyon.

Upang i-pin ang gawi para sa isang backend na hindi naglalantad ng metadata na iyon, gamitin ang kasalukuyang partial
provider update API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Ipadala ang body na iyon gamit ang `PUT /api/providers/<connection-id>`. Sa koneksyong iyon, ipinapadala ang tahasang
reasoning effort na `none` bilang `chat_template_kwargs.thinking=false` at
`chat_template_kwargs.enable_thinking=false`. Nananatiling may awtoridad ang mga tahasang native template value
maliban kung ipinipilit ng isang server-side reasoning rule ang isang effort. Nalalapat lamang ang setting kapag nagpapadala
ang isang custom na OpenAI-compatible na koneksyon ng Chat Completions body; pinananatili ng mga Responses request at karaniwang
provider ang kanilang native na anyo ng request. Itakda ang `reasoningControl` sa `openai` upang ipilit ang karaniwang OpenAI
`reasoning_effort` passthrough, o alisin ito/itakda ito sa `null` upang gumamit ng awtomatikong detection.

Bilang default, dini-disable ng mga Claude Code auto-mode classifier request ang native thinking kapag wala silang
tahasang reasoning control. Ginagamit ng detection ang system marker ng classifier sa mga Claude-format
request, hindi ang mga pangalan ng modelo o mga limitasyon sa completion. Pinananatili ng mga tahasang kontrol sa body, mga sinusuportahang effort/thinking
header, routing rule, at na-resolve na model effort ang kanilang kasalukuyang priyoridad. Pinananatili ng parehong classifier
stage ang kanilang mga prompt, limitasyon sa completion, stop sequence, at tunay na upstream permission
verdict; maaari pa ring gawin ng ikalawang stage ang hinihinging nakikitang reasoning nito bilang karaniwang text.

### Bersyon at Release Channel

```bash
GET /api/system/version
```

Ruta ng pamamahala na para lamang sa loopback (admin auth). Ibinabalik nito ang kasalukuyang bersyon, ang pinakabagong na-publish na bersyon, at ang status ng awtomatikong pag-update. Ang `releaseChannel` at `channels` ay mga karagdagang field (rail 3.8.54); nananatili ang kahulugan ng `channel` — ang deployment mode na ginagamit ng dashboard updater (`npm`, `source` o `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm channel ng kasalukuyang build: `nightly` para sa mga bersyong `-nightly.*`,
  `next` para sa iba pang pre-release (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` para sa isang stable na bersyon ng
  mas lumang major kaysa sa `channels.latest`, at `latest` sa lahat ng iba pang kaso. Parehong mga panuntunan ang ginagamit ng
  `scripts/release/dist-tag.mjs`, na pumipili ng npm dist-tag sa oras ng pag-publish.
- `channels` — na-publish na pinakabagong bersyon ng bawat dist-tag, mula sa `npm view omniroute dist-tags` (registry
  HTTP fallback), na naka-cache gamit ang parehong 10 minutong TTL gaya ng `latest`. Palaging naroroon ang `latest`
  (bumabalik sa `latest` field, pagkatapos ay sa `"unavailable"`); lumalabas lamang ang `next`, `nightly`, at `lts`
  kapag umiiral ang dist-tag na iyon. Nire-refresh ng isang kahilingang `Cache-Control: no-cache` ang parehong lookup.

Ang modelo ng channel (`latest` = v3 hanggang sa 4.0 GA, `next` = rc, `nightly` = mga build mula sa `develop`,
`lts` = mga patch ng v3 pagkatapos ng 4.0 GA) ay inilalarawan sa `docs/ops/RELEASE_STRATEGY.md`.

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
```

## Mga Limitasyon sa Token

Mga badyet sa **token** kada API key (naiiba sa badyet na nakabatay sa USD sa itaas). Ipinapatupad nang inline sa landas ng request: kapag naabot ng paggamit ng key sa kasalukuyang window ang limitasyon nito, tinatanggihan ang mga request gamit ang `429 Too Many Requests`. Maaaring saklawin ang mga limitasyon sa isang partikular na `model`, isang `provider`, o ilapat nang `global` sa buong key; kapag tumugma ang ilang limitasyon sa isang request, ang pinakamahigpit ang mananaig.

```bash
# Ilista ang mga limitasyon sa token ng isang key (kabilang ang aktuwal na paggamit sa kasalukuyang window)
GET /api/usage/token-limits?apiKeyId=key-123

# Gumawa o mag-update ng limitasyon sa token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Mag-delete ng limitasyon sa token ayon sa id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Mga tala sa schema** (`setTokenLimitSchema`): Kinakailangan ang `apiKeyId` at `scopeType` (`model` | `provider` | `global`). Kinakailangan ang `scopeValue` maliban kung ang `scopeType` ay `global` (hal., isang model id para sa saklaw na `model`, isang provider id para sa saklaw na `provider`). Ang `tokenLimit` ay dapat na isang positibong integer (kino-coerce mula sa string). Opsyonal: `id` (huwag isama upang gumawa, ibigay upang mag-update), `resetInterval` (`daily` | `weekly` | `monthly`, default na `monthly`), `resetTime` (`HH:MM`), `enabled` (default na `true`). Pinayayaman ng mga tugon sa `GET` ang bawat limitasyon gamit ang `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, at `nextResetAt`. Isa itong management-class endpoint (sentral na ipinapatupad ng authz pipeline ang auth).

## Pagproseso ng Request

1. Nagpapadala ang client ng request sa `/v1/*`
2. Tinatawag ng route handler ang `handleChat`, `handleEmbedding`, `handleAudioTranscription`, o `handleImageGeneration`
3. Nire-resolve ang model (direktang provider/model o alias/combo)
4. Pinipili ang mga credential mula sa lokal na DB na may pag-filter ayon sa availability ng account
5. Para sa chat: sinusuri ng `handleChatCore` ang semantic/signature cache at nire-resolve ang mga setting ng combo compression
6. Isinasagawa ang proactive compression bago ang provider translation kapag naka-enable (`lite`, Caveman, RTK, o stacked)
7. Ipinapadala ng provider executor ang upstream request
8. Isinasalin pabalik ang tugon sa format ng client (chat) o ibinabalik nang walang pagbabago (embeddings/images/audio)
9. Itinatala ang paggamit, compression analytics, at mga request log
10. Inilalapat ang fallback kapag may mga error ayon sa mga panuntunan ng combo

Kumpletong sanggunian sa arkitektura: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Katatagan (pinalawak)

Nagbibigay ang OmniRoute ng tatlong magkakahiwalay na mekanismo para sa pansamantalang pagkabigo; hinahayaan ng mga management endpoint sa ibaba ang mga operator na basahin at i-override ang mga ito:

| Saklaw                | Imbakan ng estado                                 | Pagbasa                                   | Pag-reset / pag-clear                                                 |
| --------------------- | ------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------- |
| Breaker ng provider   | `domain_circuit_breakers` + nasa memory           | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                          |
| Cooldown ng koneksyon | `rateLimitedUntil` sa mga koneksyon ng provider   | `/api/rate-limits`, `/api/providers/[id]` | (muling pinapagana nang lazy; i-clear sa pamamagitan ng provider PUT) |
| Lockout ng modelo     | Registry ng availability ng modelo na nasa memory | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                              |

Tumatanggap ang `PATCH /api/resilience` ng mga override sa breaker ng provider sa ilalim ng `providerBreaker.oauth` at `providerBreaker.apikey`. Sinusuportahan ng bawat profile ang `degradationThreshold`, `failureThreshold`, at `resetTimeoutMs`; makikita rin ang parehong mga field sa Dashboard → Mga Setting → Katatagan.

```bash
# I-clear ang lockout ng isang modelo
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Burahin ang lahat ng lockout
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Para sa kumpletong konseptuwal na sanggunian at mga default ng breaker: tingnan ang [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" at [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Queue ng Rate Limit at Safety Net para sa Awtomatikong Pag-enable

- **Sinusuportahang write path**: Ang `POST /api/rate-limits` na may body na `{"connectionId": "<id>", "enabled": true|false}` ang sinusuportahang management endpoint para i-toggle ang proteksyon laban sa rate limit para sa isang koneksyon. Sadyang hindi binabago o bina-baligtad ng `PUT /api/providers/[id]` ang `rateLimitProtection` (#11278).
- **Semantika ng `enabled: false`**: Inaalis ng pagtatakda ng `enabled: false` ang tahasang proteksyon para sa koneksyon, ngunit **hindi** nito inaalis ang isang aktibong koneksyon gamit ang API key mula sa pandaigdigang safety net para sa awtomatikong pag-enable (`autoEnableApiKeyProviders = true`). Sa `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), magkatumbas ang `false` at `undefined`; nananatiling protektado sa ilalim ng safety net para sa awtomatikong pag-enable ang mga aktibong koneksyon gamit ang API key na walang tahasang proteksyon.
- **Pandaigdigang pag-disable**: Upang patakbuhin ang mga koneksyon gamit ang API key nang walang mga queue ng rate limit, i-disable ang safety net sa buong system sa pamamagitan ng `RATE_LIMIT_AUTO_ENABLE=false` (env) o `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Mga Setting → Katatagan / `PATCH /api/resilience`).

## Pagpapatunay

Tingnan ang [Pagpapatunay sa Pamamahala](../guides/MANAGEMENT-AUTH.md) para sa apat na
pamilya ng kredensyal (session ng dashboard, lokal na CLI token, `oma_live_…` Access
Token, API key na may saklaw na manage) at kung paano naiiba ang mga ito sa mga inference key.

- Ginagamit ng mga ruta ng dashboard (`/dashboard/*`) ang cookie na `auth_token`
- Ginagamit sa pag-login ang naka-save na password hash; babalik sa `INITIAL_PASSWORD` kapag kinakailangan
- Maaaring i-toggle ang `requireLogin` sa pamamagitan ng `/api/settings/require-login`
- Opsyonal na nangangailangan ang mga rutang `/v1/*` ng Bearer API key kapag `REQUIRE_API_KEY=true`
- Ang "token sa pamamahala" / "API key na may saklaw sa pamamahala" sa sangguniang ito ay tumutukoy sa isa sa mga pamilya sa gabay na iyon — hindi sa isang hindi tinukoy na karagdagang uri ng lihim

> **Pagbabagong hindi backward-compatible (v3.8.0)** — Nangangailangan na ngayon ang `/api/v1/agents/tasks/*` at ang mga endpoint sa pamamahala ng cooldown ng **pagpapatunay sa pamamahala** (cookie na `auth_token` ng dashboard o API key na may saklaw sa pamamahala). Makakatanggap ang mga client na dating tumatawag sa mga rutang ito nang walang pagpapatunay ng `401 Unauthorized`. Tingnan ang commit na `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
