## 🎯 Mga Gamit

### Kaso 1: "Mayroon akong subscription sa Claude Pro"

**Problema:** Nag-e-expire ang quota nang hindi nagagamit, at naaabot ang mga limitasyon sa rate habang masinsinang nagko-code

```
Kombinasyon: "maximize-claude"
  1. cc/claude-opus-4-7        (lubusang gamitin ang subscription)
  2. glm/glm-4.7               (murang backup kapag ubos na ang quota)
  3. if/qwen3.8-max-preview       (libreng pang-emergency na fallback)

Buwanang gastos: $20 (subscription) + ~$5 (backup) = $25 lahat-lahat
kumpara sa $20 + pag-abot sa mga limitasyon = pagkabigo
```

### Kaso 2: "Gusto kong walang gastos"

**Problema:** Hindi kayang magbayad para sa mga subscription at kailangan ng maaasahang AI para sa pagko-code

```
Kombinasyon: "zero-cost"
  1. if/kimi-k2.7-code          (nakalistang libreng access; maaaring may mga limitasyon sa rate)
  2. kr/qwen3-coder-next        (libreng fallback ng Kiro)

Buwanang gastos: $0
Kalidad: beripikahin ang model, mga limitasyon, privacy, at SLA para sa iyong workload
```

### Kaso 3: "Kailangan kong mag-code 24/7, nang walang pagkaantala"

**Problema:** May mga deadline at hindi maaaring magkaroon ng downtime

```
Kombinasyon: "always-on"
  1. cc/claude-opus-4-7        (pinakamahusay na kalidad)
  2. cx/gpt-5.5                (ikalawang subscription)
  3. glm/glm-4.7               (mura, nagre-reset araw-araw)
  4. minimax/MiniMax-M2.1      (pinakamura, nagre-reset kada 5 oras)
  5. if/deepseek-v4-flash       (nakalistang libreng access; maaaring may mga limitasyon sa rate)

Resulta: Pinalalawak ng 5 fallback layer ang katatagan; hindi garantisado ang availability ng upstream
Buwanang gastos: $20-200 (mga subscription) + $10-20 (backup)
```

### Kaso 4: "Gusto ko ng LIBRENG AI sa OpenClaw"

**Problema:** Kailangan ng AI assistant sa mga messaging app, nang ganap na libre

```
Kombinasyon: "openclaw-free"
  1. if/qwen3.8-max-preview     (nakalistang libreng access; maaaring may mga limitasyon sa rate)
  2. if/deepseek-v4-flash       (nakalistang libreng access; maaaring may mga limitasyon sa rate)
  3. if/kimi-k2.7-code          (nakalistang libreng access; maaaring may mga limitasyon sa rate)

Buwanang gastos: $0
I-access sa pamamagitan ng: WhatsApp, Telegram, Slack, Discord, iMessage, Signal...
```

## 📖 Pag-set Up ng Provider

Upang maramihang magdagdag ng mga koneksiyong API-key mula sa isang CSV o JSON file, gamitin ang **Dashboard → Providers → Import from file**. Nakabatay sa posisyon ang mga column (`provider,name,apiKey,baseUrl,priority`); dapat umiiral na ang `provider` bilang isang pinamamahalaang provider o katugmang node. Tingnan ang [Pag-import ng mga provider mula sa isang CSV o JSON file](../providers/CSV-IMPORT.md).

### 🔐 Mga Subscription Provider

#### Claude Code (Pro/Max)

```bash
Dashboard → Providers → Ikonekta ang Claude Code
→ Pag-login gamit ang OAuth → Awtomatikong pag-refresh ng token
→ 5-oras + lingguhang pagsubaybay sa quota

Mga Model:
  cc/claude-opus-4-7
  cc/claude-sonnet-4-6
  cc/claude-haiku-4-5-20251001
```

**Tip para sa Pro:** Gamitin ang Opus para sa mga komplikadong gawain at Sonnet para sa bilis. Sinusubaybayan ng OmniRoute ang quota ng bawat model!

Walang browser sa OmniRoute host? Patakbuhin ang `claude setup-token` saanman naka-login ang Claude Code at i-paste ang isang-taong token sa tab na **Setup Token**. Tingnan ang [Claude Code gamit ang setup token](../providers/CLAUDE_CODE_SETUP_TOKEN.md).

Pinapanatili ng Claude at mga route na compatible sa Claude Code ang `max` na antas ng thinking effort para sa mga model na Opus at Sonnet. Hindi tinatanggap ng mga Haiku model ang antas ng effort na `max`, kaya ibinababa ng OmniRoute ang kahilingang iyon sa mataas na thinking budget bago ito ipadala upstream.

#### OpenAI Codex (Plus/Pro)

```bash
Dashboard → Providers → Ikonekta ang Codex
→ Pag-login gamit ang OAuth (port 1455)
→ 5-oras + lingguhang pag-reset

Mga Model:
  cx/gpt-5.5
  cx/gpt-5.4
```

#### GitHub Copilot

```bash
Dashboard → Providers → Ikonekta ang GitHub
→ OAuth sa pamamagitan ng GitHub
→ Buwanang pag-reset (ika-1 ng buwan)

Mga Model:
  gh/gpt-5.5
  gh/gpt-5.4
```

### 💰 Mga Murang Provider

1. Mag-sign up: [Zhipu AI](https://open.bigmodel.cn)

1. Mag-sign up: [Baidu AI Cloud Qianfan](https://cloud.baidu.com/product/wenxinworkshop)

**Gamitin:** `qianfan/ernie-5.1`, `qianfan/ernie-x1.1`, o ibang Qianfan model ID na compatible sa OpenAI.

## 🔧 Integrasyon sa CLI

### Cursor IDE

**Paggamit sa Cursor bilang OmniRoute client** (idaan ang chat ng Cursor sa OmniRoute):

```
Mga Setting → Mga Modelo → Advanced:
  OpenAI API Base URL: http://localhost:20128/v1
  OpenAI API Key: [mula sa dashboard ng omniroute]
  Modelo: cc/claude-opus-4-7
```

**Paggamit sa OmniRoute bilang Cursor provider** (tinatawag ng OmniRoute ang upstream ng Cursor): mas piliin ang
**Dashboard → Mga Provider → Cursor → Mag-login gamit ang Cursor**. Sa Docker, tingnan ang
[`docs/providers/CURSOR-DOCKER.md`](../providers/CURSOR-DOCKER.md).

### Claude Code

I-edit ang `~/.claude/settings.json`:

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:20128",
    "ANTHROPIC_AUTH_TOKEN": "your-omniroute-api-key"
  }
}
```

Gamitin dito ang Claude-compatible na root endpoint. Huwag idagdag ang `/v1` sa `ANTHROPIC_BASE_URL`.

### Codex CLI

```bash
export OPENAI_BASE_URL="http://localhost:20128"
export OPENAI_API_KEY="your-omniroute-api-key"
codex "your prompt"
```

### OpenClaw

I-edit ang `~/.openclaw/openclaw.json`:

```json
{
  "agents": {
    "defaults": {
      "model": { "primary": "omniroute/if/kimi-k2.7-code" }
    }
  },
  "models": {
    "providers": {
      "omniroute": {
        "baseUrl": "http://localhost:20128/v1",
```

### Tray mode

Simulan ang OmniRoute sa system tray:

```bash
omniroute serve --tray
```

Babalik ang command kapag handa na ang server at tray.

Magpapatuloy ang server nang wala ang terminal.

Sinusuportahan ng tray mode ang macOS, Windows, at mga graphical Linux session. Hindi awtomatikong binubuksan ng tray mode ang dashboard.

Gamitin ang tray menu para sa mga sumusunod na pagkilos:

- Buksan ang dashboard.
- Buksan ang `/dashboard/logs`.
- Baguhin ang awtomatikong pagsisimula.
- Ihinto ang OmniRoute.

Huwag pagsamahin ang `--tray` sa mga sumusunod na opsyon:

- `--daemon`
- `--log`
- `--no-recovery`

Nangangailangan ang mga mode na ito ng magkakaibang pagmamay-ari ng proseso.

Paganahin ang pagsisimula sa susunod na pag-login sa machine:

```bash
omniroute autostart enable
```

Ginagamit ng awtomatikong pagsisimula ang tray mode sa macOS, Windows, at mga graphical Linux session. Ginagamit ng headless Linux ang umiiral na systemd user service.

Huwag paganahin ang pagsisimula sa pag-login:

```bash
omniroute autostart disable
```

### Mga Custom na Model

Magdagdag ng anumang model ID sa anumang provider nang hindi hinihintay ang update ng app:

```bash
# Sa pamamagitan ng API
curl -X POST http://localhost:20128/api/provider-models \
  -H "Content-Type: application/json" \
  -d '{"provider": "openai", "modelId": "gpt-5.2", "modelName": "GPT-5.2"}'

# Ilista: curl http://localhost:20128/api/provider-models?provider=openai
# Alisin: curl -X DELETE "http://localhost:20128/api/provider-models?provider=openai&model=gpt-5.2"
```

O gamitin ang Dashboard: **Providers → [Provider] → Custom Models**.

Mga Tala:

- Ang mga provider na OpenRouter at OpenAI/Anthropic-compatible ay pinamamahalaan mula lamang sa **Available Models**. Ang manu-manong pagdagdag, import, at auto-sync ay lahat napupunta sa iisang listahan ng available-model, kaya walang hiwalay na seksyong Custom Models para sa mga provider na iyon.
- Ang seksyong **Custom Models** ay inilaan para sa mga provider na hindi nag-eexpose ng managed na pag-import ng mga available-model.

### Mga Custom na OpenAI-Compatible na Provider

Ang anumang gateway na gumagamit ng OpenAI API (isang self-hosted proxy, vLLM, isang third-party aggregator)
ay maaaring idagdag bilang sarili nitong provider node:

1. **Providers → Add OpenAI Compatible**.
2. **Name**: isang display label para sa node.
3. **Prefix**: ang pangalan sa routing. Tinatawag ng mga client ang mga model bilang `<prefix>/<model>`, kaya ang node na may
   prefix na `mygw` ay nagse-serve ng `mygw/gpt-4o-mini`. Kinakailangan; walang restriksyon sa mga character.
4. **API Type**: ang pamilya ng endpoint na sine-serve ng gateway (Chat Completions, Responses,
   Embeddings, audio, images).
5. **Base URL**: ang API root, hanggang sa at kasama ang `/v1` (halimbawa
   `https://gateway.example.com/v1`), hindi ang buong path na `/chat/completions`. Ang mga gateway na may
   mga non-standard na path ay nagse-set ng mga ito sa ilalim ng **Advanced Settings** (chat path, models path).
6. Ang field na **API Key (for Check)** ay sinusubukan lamang ang koneksyon. Pagkatapos gawin ang node,
   buksan ito at gamitin ang **Add Connection** para i-store ang key na gagamitin ng mga request.

Ang node ay nagkakaroon ng internal id na may anyong `openai-compatible-<apiType>-<uuid>`; hindi mo na
kailangang i-type ito, ang prefix ang pampublikong pangalan.

#### Mga naka-reservang prefix

Ang prefix ay hindi maaaring maging id o alias ng isang built-in na provider (halimbawa `openai`, `cf`), o
id ng isang retired na provider. Sinusuri ng model resolver ang mga built-in na id at alias bago ang mga
custom node, kaya ang isang node na gumagamit ng isa sa mga prefix na iyon ay hindi kailanman tatanggap ng
traffic: ang `<prefix>/model` ay pupunta sa built-in na provider, o magfa-fail closed kung retired na ang
provider na iyon. Ang paglikha o pag-edit ng node na may ganitong prefix ay tinatanggihan na may:

```text
prefix: "<prefix>" is a reserved provider prefix — choose a different prefix (reserved ids/aliases cannot be used for custom nodes because requests like <prefix>/model route to a built-in provider or fail closed when retired)
```

Pumili ng natatanging prefix (`mygw`, `acme-proxy`). Kung ang mga request sa isang custom node ay nagfa-fail
na may error na nagbabanggit ng built-in na provider o mga credentials nito, suriin kung naka-reserva ang
prefix ng node: ang mga node na na-save bago pa nagkaroon ng panuntunang ito ay naka-store pa rin, ngunit ang
kanilang prefix ay nagre-route sa built-in na provider. I-edit ang node at bigyan ito ng bagong prefix.

#### Mga opsyon ng gateway kada koneksyon

Ang mga key na ito ay nilalagay sa `providerSpecificData` ng isang koneksyon (halimbawa sa pamamagitan ng
`PUT /api/providers/{id}`):

- `toolNameMaxLength` (integer, 1–1024) — para sa mga OpenAI chat-format compatible na koneksyon na ang

### Pag-chain ng mga OmniRoute Peer

Ang isa pang OmniRoute gateway ay maaaring idagdag bilang isang **Custom OpenAI-compatible** na provider.
Gamitin ang `/v1` base URL ng peer at isang dedikadong, least-privilege na API key na inilabas ng peer na iyon.

Para sa mga reciprocal o multi-hop na chain, i-enable ang opt-in na loop guard sa bawat gateway:

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

Tanging ang mga request na ipinadala sa isang explicitly na naka-allowlist na peer URL ang tumatanggap ng
header na `X-OmniRoute-Peer-Trace`. Tinatanggihan ng gateway ang paulit na instance ID o naubos na hop
budget na may HTTP `508 Loop Detected`; ang mga ordinaryong upstream provider ay hindi tumatanggap ng anumang
peer metadata.

Ang peer chaining ay hindi database replication o host failover. Ang bawat gateway ay nagpapanatili ng
independyenteng SQLite state, cache, rate counter, at session. Gumamit ng health-checked na reverse proxy o
client failover para sa active/passive o active/active na availability, at huwag kailanman i-mount ang isang
SQLite database sa maraming tumatakbong OmniRoute instance.

### Mga Istratehiya sa Routing

I-configure sa **Dashboard → Settings → Routing**. Naglalantad ang dashboard ng anim na pinakaginagamit na estratehiya; ang mga combo at ang auto-router ay panloob na sumusuporta sa mas malawak na hanay.

**Mga estratehiyang nakikita sa Dashboard (routing sa antas ng account):**

| Estratehiya                    | Paglalarawan                                                                                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fill First**                 | Gumagamit ng mga account ayon sa pagkakasunud-sunod ng priyoridad — ang pangunahing account ang humahawak ng lahat ng request hanggang sa hindi na ito magagamit |
| **Round Robin**                | Umiikot sa lahat ng account na may nako-configure na sticky limit (default: 3 tawag bawat account)                                                               |
| **P2C (Power of Two Choices)** | Pumipili ng 2 random na account at nagre-route sa mas healthy — nagbabalanse ng load na may kamalayan sa health                                                  |
| **Random**                     | Random na pumipili ng account para sa bawat request gamit ang Fisher-Yates shuffle                                                                               |
| **Least Used**                 | Nagre-route sa account na may pinakalumang `lastUsedAt` timestamp, na pantay na namamahagi ng trapiko                                                            |
| **Cost Optimized**             | Nagre-route sa account na may pinakamababang priority value, na nag-o-optimize para sa mga provider na may pinakamababang gastos                                 |

**Mga advanced na estratehiya ng combo at auto** (nako-configure bawat combo o sa pamamagitan ng mga `auto/*` prefix — tingnan ang [AUTO-COMBO.md](../routing/AUTO-COMBO.md)):

- `priority` — mahigpit na pagkakasunud-sunod, hindi kailanman nagro-round-robin
- `weighted` — proporsyonal na paghahati ng trapiko ayon sa mga weight bawat modelo
- `fill-first` — patakbuhin ang unang modelo hanggang maabot ang mga limit
- `round-robin` / `strict-random` / `random`
- `p2c` (Power of Two Choices)
- `least-used` at `cost-optimized`
- `auto` — batay sa score sa lahat ng kandidato
- `lkgp` (Last Known Good Provider) — naka-pin sa huling matagumpay na provider, pagkatapos ay bumabalik sa mga panuntunan
- `context-optimized` — pumipili ng modelo na may pinakamalaking libreng context window
- `context-relay` — nagkakadena ng mga long-context na modelo para sa mga susunod na turn

### Resilience at mga Circuit Breaker

I-configure sa **Dashboard → Settings → Resilience**.

Nagpapatupad ang OmniRoute ng provider-level na resilience na may limang komponent:

1. **Request Queue & Pacing** — System-level na paghuhubog ng mga request:
   - **Requests Per Minute (RPM)** — Pinakamataas na bilang ng mga request kada minuto bawat account
   - **Min Time Between Requests** — Pinakamababang agwat sa milliseconds sa pagitan ng mga request
   - **Max Concurrent Requests** — Pinakamataas na sabay-sabay na mga request bawat account

2. **Connection Cooldown** — Konfigurasyon bawat uri ng auth para sa isang koneksyon matapos ang mga retryable na failure:
   - **Base Cooldown** — Default na cooldown window para sa mga retryable na upstream failure
   - **Use Upstream Retry Hints** — Sinusunod ang mga authoritative na `Retry-After` o reset hint kapag ibinigay
   - **Max Backoff Steps** — Pinakamataas na antas ng exponential backoff para sa mga paulit-ulit na failure

3. **Provider Circuit Breaker** — Sinusubaybayan ang end-to-end na mga provider failure, minamarkahan ang provider bilang degraded sa naka-configure na warning threshold, at binubuksan ang breaker kapag naabot ang naka-configure na failure threshold:
   - **Degradation Threshold** — Magkakasunod na provider failure bago pumasok sa `DEGRADED`
   - **Failure Threshold** — Magkakasunod na provider failure bago pumasok sa `OPEN`
   - **Reset Timeout** — Time window bago subukan muli ang provider
   - **CLOSED** (Healthy) — Normal na dumadaloy ang mga request
   - **DEGRADED** — Dumadaloy pa rin ang mga request habang sinusubaybayan ang mga tumaas na failure
   - **OPEN** — Pansamantalang naka-block ang provider matapos ang mga paulit-ulit na failure
   - **HALF_OPEN** — Sinusuri kung nakabawi na ang provider

   Ang mga connection-scoped na `429` rate limit ay nananatili sa **Connection Cooldown** at hindi ibinibilang patungo sa provider breaker.

   Ang runtime state ng provider breaker ay ipinapakita lamang sa **Dashboard → Health**.

4. **Wait For Cooldown** — Kung ang bawat candidate na koneksyon ay nagco-cooldown na, maaaring maghintay ang OmniRoute sa pinakamaagang cooldown at awtomatikong i-retry ang parehong client request.

5. **Rate Limit Auto-Detection** — Kapag nagbabalik ang mga upstream provider ng mga explicit na wait window, io-override ng mga hint na iyon ang lokal na connection cooldown kapag naka-enable ang setting.

**Pro Tip:** Gamitin ang pahinang **Health** para suriin at i-reset ang mga live na provider breaker matapos ang isang outage. Ang pahina ng Resilience ay nagbabago lamang ng konfigurasyon.

### Mga Istratehiya sa Pagbabalanse ng Combo

I-configure ang per-combo na pagbabalanse sa **Dashboard → Combos → Create/Edit → Strategy**.

| Istratehiya        | Paglalarawan                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------ |
| **Round-Robin**    | Paikot na dumadaan sa mga modelo nang sunud-sunod                                          |
| **Priority**       | Laging sinusubukan ang unang modelo; nagfa-fallback lang kapag may error                   |
| **Random**         | Pumipili ng random na modelo mula sa combo para sa bawat request                           |
| **Weighted**       | Nagruruta nang proporsyonal batay sa mga itinalagang timbang bawat modelo                  |
| **Least-Used**     | Nagruruta sa modelo na may pinakakaunting kamakailang request (gumagamit ng combo metrics) |
| **Cost-Optimized** | Nagruruta sa pinakamurang available na modelo (gumagamit ng pricing table)                 |

Ang mga global na default ng combo ay maaaring itakda sa **Dashboard → Settings → Routing → Combo Defaults**.
Ang mga combo target timeout ay nagmamana ng kasalukuyang request timeout bilang default. Gamitin ang
**Target timeout (seconds)** sa mga combo default o sa isang indibidwal na combo lamang kapag ang mas
maikling per-target na limitasyon ay dapat mag-trigger ng mas mabilis na fallback.

Ang mga zero-latency na combo optimization ay opt-in. Iwanang naka-disable ang **Zero-latency
optimizations** upang pigilan ang mga latency feature na ito na makipagsabayan sa mga fallback target,
lumaktaw ng mga target batay sa kasaysayan ng TTFT, o mag-compress ng mga fallback request; ang
pag-enable nito ay nagpapahintulot sa mga naka-configure na hedging, predictive TTFT skip, at
proactive fallback compression na ipagpalit ang routing/request fidelity para sa mas mababang tail
latency.

I-disable ang **Buffer ng reasoning token** kapag ang mga upstream provider ay nangangailangan ng mahigpit na mga limitasyon sa `max_tokens` / `maxOutputTokens`. Kapag pinagana, ang combo routing ay nagdaragdag lamang ng headroom ng reasoning-model para sa mga modelong may kilalang output cap at hinahayaang hindi nagbabago ang token limit ng kliyente kapag ang ligtas na halagang may buffer ay lalampas sa cap na iyon. Kung ang limit ng kliyente ay lampas na sa isang kilalang cap, ibinababa ito ng OmniRoute sa cap na iyon bago ipadala ang upstream request.

| **Signature Cache**       | Mga estadistika ng deduplication cache (mga aktibong key, hit rate)           |
| **Latency Telemetry**     | Agregasyon ng latency na p50/p95/p99 bawat provider                           |

**Kapaki-pakinabang na Tip:** Awtomatikong nire-refresh ang pahina ng Kalusugan tuwing 10 segundo. Gamitin ang card ng circuit breaker upang matukoy kung aling mga provider ang nakakaranas ng mga isyu.

## 🤖 Awtomatikong Pagruruta (Walang configuration)

Kasama sa OmniRoute ang isang **awtomatikong router na nakabatay sa score** na pumipili ng pinakamahusay na modelo para sa bawat kahilingan mula sa lahat ng nakakonektang provider — walang combo na kailangang imantini. Ipadala lang ang kahilingan gamit ang isa sa mga prefix na `auto/*`, at bubuo ang OmniRoute ng virtual na combo habang tumatakbo, na nagbibigay ng score sa mga kandidato batay sa latency, gastos, success rate, pagiging angkop sa context, pagiging angkop ng modelo sa gawain, mga kamakailang pagkabigo, quota, at estado ng circuit breaker.

| Prefix         | Ino-optimize para sa                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `auto`         | Balanseng default (latency × gastos × success rate)                                                                            |
| `auto/coding`  | Mga gawain sa coding: inuuna ang Claude, GPT-5, GLM, Kimi, Qwen Coder, at mga coder ng DeepSeek                                |
| `auto/cheap`   | Pinakamababang $/token, tumatanggap ng mas mataas na latency                                                                   |
| `auto/fast`    | Pinakamababang latency, hindi isinasaalang-alang ang gastos                                                                    |
| `auto/offline` | Mga local-only na provider (Ollama, vLLM, llama.cpp) — kapaki-pakinabang para sa mga air-gapped na setup                       |
| `auto/smart`   | Inuuna ang kalidad ng reasoning (Opus, GPT-5 xhigh, R1, GLM 5.1 reasoning)                                                     |
| `auto/lkgp`    | "Huling Kilalang Mahusay na Provider" — nananatili sa huling matagumpay na provider, pagkatapos ay bumabalik sa mga panuntunan |

Halimbawa:

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer $OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto/coding",
    "messages": [{ "role": "user", "content": "Refactor this Python function" }],
    "stream": true
  }'
```

Ganap na inilalarawan ang awtomatikong router sa [AUTO-COMBO.md](../routing/AUTO-COMBO.md) — kabilang ang kung paano isaayos ang mga scoring weight, i-blacklist ang mga provider, at siyasatin ang mga desisyon sa pagruruta sa **Dashboard → Auto Combo**.

## 🔌 Integrasyon ng MCP at A2A

Ang OmniRoute ay parehong **MCP server** (Model Context Protocol) at **A2A server** (Agent-to-Agent JSON-RPC 2.0). Maaaring direktang tawagin ng anumang MCP-compatible na IDE o agent host ang mga tool ng OmniRoute — walang kinakailangang karagdagang wrapper.

### Mga transport ng MCP

- **SSE**: `http://localhost:20128/api/mcp/sse`
- **Streamable HTTP**: `http://localhost:20128/api/mcp/stream`
- **stdio**: `omniroute --mcp` (para sa mga IDE plugin na mas gustong gumamit ng stdio)

### Ikonekta ang Claude Desktop

I-edit ang `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) o ang katumbas nito sa Windows/Linux:

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### Ikonekta ang Cursor / Continue / VS Code MCP

Gamitin ang SSE URL na `http://localhost:20128/api/mcp/sse` at isang Bearer API key na binuo sa **Dashboard → API Keys**.

### Mga scope

Kasalukuyang tumutukoy ang MCP ng 32 pinangalanang scope. Maaaring limitahan ang bawat Bearer key sa mga partikular na scope — tingnan ang [MCP-SERVER.md](../frameworks/MCP-SERVER.md) para sa opisyal na imbentaryo ng mga scope at tool, at ang [A2A-SERVER.md](../frameworks/A2A-SERVER.md) para sa JSON-RPC schema.

## 💾 Sistema ng Memory

Nagpapanatili ang OmniRoute ng **pangmatagalang memory ng pag-uusap** gamit ang hybrid retrieval:

- **SQLite FTS5** para sa paghahanap gamit ang keyword sa mga nakaraang turn
- **Qdrant vector store** (opsyonal) para sa semantic recall
- **Awtomatikong pagkuha ng mga fact** — binubuod ang mga entity, kagustuhan, at desisyon pagkatapos ng bawat session at iniimbak sa table na `memory_facts`
- Ang mga memory ay nakahiwalay ayon sa bawat API key at bawat session

Pamahalaan ang mga memory sa **Dashboard → Memory** (maghanap, mag-edit, mag-export, mag-purge). Hinahayaan ng HTTP interface (`/api/memory/*`) ang mga agent na magpadala at mag-query ng mga fact sa pamamagitan ng program — tingnan ang [MEMORY.md](../frameworks/MEMORY.md).

## 🔔 Mga Webhook

Mag-subscribe sa mga event ng OmniRoute para sa real-time na pagsubaybay at automation.

- Gumawa ng webhook sa **Dashboard → Webhooks** na may target URL at HMAC signing secret
- Mga available na event: `request.completed`, `request.failed`, `provider.unavailable`, `budget.exceeded`, `combo.switched`, `circuit_breaker.opened`, `circuit_breaker.closed`

```bash
# Ilista ang mga provider
curl http://localhost:20128/api/providers \

  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \

# Gumawa ng combo
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "premium", "strategy": "priority", "models": [{ "model": "cc/claude-opus-4-7" }, { "model": "glm/glm-5.1" }] }'
```

## 💻 Panloob na CLI

Ang OmniRoute ay may kasamang panloob na CLI (`omniroute …`) para sa pag-setup, mga diagnostic, at pagkontrol sa runtime. **Hiwalay ito sa pahina ng "Mga CLI Tool" sa dashboard**, na nagko-configure ng mga third-party na CLI (Claude Code, Cursor, Codex, Cline, …) upang makakonekta ang mga ito sa OmniRoute.

```bash
omniroute setup                    # Interaktibong wizard (password, mga provider, mga combo)
omniroute setup --non-interactive  # Angkop para sa CI
omniroute doctor                   # Mga diagnostic sa kalagayan (data dir, DB, mga provider, mga port)
omniroute providers available      # Ilista ang mga sinusuportahang provider
omniroute providers list           # Ilista ang mga naka-configure na koneksyon
omniroute providers test <id>      # Subukan nang live ang koneksyon sa provider
omniroute combos list              # Ilista ang mga combo
omniroute combos switch <name>     # Itakda ang default na combo
omniroute models                   # Ilista ang mga available na modelo (--json, --search)
omniroute keys add | list | remove # Pamahalaan ang mga API key mula sa terminal
omniroute backup                   # Gumawa ng snapshot ng config + DB
omniroute restore [<timestamp>]    # Mag-restore mula sa isang snapshot
omniroute health                   # Detalyadong kalagayan (mga breaker, cache, memory)
omniroute quota                    # Paggamit ng quota ng provider
omniroute mcp status               # Katayuan ng MCP server
omniroute a2a status               # Katayuan ng A2A server
omniroute tunnel list|create|stop  # Mga Cloudflare/Tailscale/ngrok tunnel
omniroute reset-password           # I-reset ang admin password
omniroute --mcp                    # Simulan ang MCP server sa pamamagitan ng stdio
omniroute --port 3000              # Simulan ang server sa isang custom na port
```

Tip: ipares ang `omniroute doctor --json` sa iyong monitoring tool upang makatanggap ng alerto kapag may hindi maayos na koneksyon sa provider.
