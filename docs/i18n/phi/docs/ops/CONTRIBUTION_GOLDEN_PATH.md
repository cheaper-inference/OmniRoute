Gamitin ang gabay na ito upang piliin ang pinakamaliit na maaasahang development loop para sa isang pull request. Hindi nito
pinapalitan ang mga dokumento sa arkitektura at seguridad na partikular sa bawat bahagi at naka-link sa ibaba; inuugnay nito ang bawat karaniwang
uri ng pagbabago sa mga contract, nakatuong pagsusuri, at saklaw ng CI nito.

## Ang landas na sinusunod ng bawat pagbabago

1. **Piliin ang base bago mag-edit.** Hanapin ang pinakamataas na aktibong `release/v*` branch at gumawa ng branch mula
   sa tip nito. I-target ang branch na iyon, hindi ang `main`. Kung may aktibong release freeze, huwag i-target ang naka-freeze na
   branch; gamitin ang susunod na aktibong cycle na inilalarawan sa
   [Modelo ng Branching at Release](BRANCHING_MODEL.md).
2. **Tukuyin ang mga contract.** Tukuyin ang bawat catalog, schema, generated artifact, public API, o user
   interface na naaapektuhan ng pagbabago. Ibinibigay ng talahanayan sa ibaba ang pinakamababang panimulang hanay.
3. **Sumulat o mag-update ng mga nakatuong test.** Ang mga pagbabago sa production sa `src/`, `open-sse/`, `electron/`, o
   `bin/` ay nangangailangan ng automated test sa parehong PR. Patakbuhin ang pinakamaliit na mga test file na nagpapatunay sa
   behavior, at pagkatapos ay ang mga nakalistang nakatuong gate.
4. **Hayaang patakbuhin ng CI ang malawak na matrix.** Tumatakbo sa PR ang kumpletong unit shards, Vitest, coverage ratchet, at
   production build. Magpatakbo lamang ng malawak na suite nang lokal kapag ang isang nakatuong failure ay nagpapahiwatig ng
   mas malawak na epekto o kapag sumasaklaw ang pagbabago sa ilang subsystem.
5. **I-reconcile bago ang review.** I-fetch ang aktibong base, suriin ang mga bagong commit nito at ang diff mo laban
   dito, at pagkatapos ay i-rebase o i-merge ang base ayon sa contributor workflow. Lutasin ang mga conflict sa generated file
   at catalog mula sa kanilang source, muling i-generate ang mga ito, patakbuhing muli ang nakatuong loop, at kumpirmahing
   naka-target pa rin ang PR sa aktibong release branch.
6. **Itala ang ebidensya.** Sa PR template, ilista ang mga command na pinatakbo, bawat test file na idinagdag o binago,
   mga migration o feature flag, at anumang CI-only validation na nakabinbin pa.

## Mga pangunahing landas ayon sa uri ng pagbabago

Ang mga command sa ibaba ay mga pinakamababang nakatuong pagsusuri, hindi pahintulot na laktawan ang isang test na direktang sumasaklaw sa
behavior na binago mo.

### Provider

**Mga contract**

- Depinisyon ng provider sa `src/shared/constants/providers/` at ang composition nito sa
  `src/shared/constants/providers.ts`.
- Mga model at capability sa `open-sse/config/providerRegistry.ts` o sa mga nakahiwalay nitong registry file.
- Pagpili ng executor/translator, configuration ng OAuth o API key, mga dashboard asset, at generated
  provider reference kapag naaangkop.
- Dapat gamitin ng mga public credential ang `resolvePublicCred()`; dapat gamitin ng mga error response ang mga shared sanitized
  error helper. Tingnan ang `docs/security/PUBLIC_CREDS.md` (git; hindi kino-compile sa `/docs`) at
  [Pag-sanitize ng Error](../security/ERROR_SANITIZATION.md).

**Nakatuong loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kapag nagbago ang catalog; i-commit ang generated diff
npm run lint
```

I-test din ang bawat apektadong request family: chat, Responses, images, embeddings, audio, o video.
Suriin ang mga generated catalog at golden diff bilang mga pagbabago sa contract; huwag tanggapin ang mga ito nang hindi sinusuri.

### Routing

**Mga contract**

- Mga public strategy value at UI metadata sa `src/shared/constants/routingStrategies.ts`.
- Dispatch at ordering sa ilalim ng `open-sse/services/combo.ts` at `open-sse/services/combo/`.
- Mga combo schema, persistence, resilience state, model capability, at API/UI control.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) at dokumentasyon ng resilience kapag nagbabago ang behavior.

**Nakatuong loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # mga pagbabago sa strategy o dispatch
npm run check:known-symbols      # mga pagbabago sa pagpaparehistro ng strategy
npm run lint
```

Gumamit ng mga deterministic mocked-upstream test nang lokal. Nangangailangan ng mga credential ang mga live combo smoke test at
manual ang mga ito, hindi mga pamalit sa CI.

### UI / UX

**Mga contract**

- Next.js route/page at mga shared component boundary sa ilalim ng `src/app/` at
  `src/shared/components/`.
- Mga hugis ng API response, loading/empty/error state, behavior ng keyboard at screen reader,
  responsive layout, theming, at pagpapalawak ng locale.
- Mga English UI source string sa `src/i18n/messages/en.json`; huwag mag-hard-code ng bagong text na nakikita ng user.

**Nakatuong loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Patakbuhin ang app para sa mga pagbabago sa interaction o visual at suriin ang parehong makitid at malapad na viewport. Pinapatakbo ng CI ang
production build at mas malalawak na suite; kailangan pa rin ng visual behavior ng nakatuong component test, Playwright test,
o dokumentadong manual na pagsusuring angkop sa pagbabago.

### i18n

**Mga contract**

- Ang `src/i18n/messages/en.json` ang UI source; ang `config/i18n.json` ang locale source.
- Hiwalay na matatagpuan ang mga CLI catalog sa ilalim ng `bin/cli/locales/`.
- Panatilihin nang eksakto ang mga ICU placeholder at tag. Huwag isalin ang mga pangalan ng product/provider/model,
  mga pangalan ng protocol at header, command, code/JSON identifier, URL, environment variable, o
  mga protektadong termino gaya ng `OmniRoute`, `OAuth`, `MCP`, at `A2A`. Ang kasalukuyang source list ay
  `scripts/i18n/glossary/protected-terms.json`.

**Nakatuong loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kapag nagbago ang mga CLI string/catalog
npm run lint
```

Gabay ito para sa kasalukuyang system, hindi isang paanyayang palawakin ang tooling o key model nito.
Panatilihing limitado at tiyak ang mga i18n patch habang idinidisenyo ang kapalit na system. Huwag magpatakbo ng mga translation
command na tumatawag sa mga external service maliban kung tahasang nangangailangan ang task ng mga generated translation at
nasuri mo na ang nagresultang diff.

### CLI

**Mga contract**

- Mga pampublikong command at flag sa `bin/cli/`, mga nabuong API command, exit code, stdout/stderr at
  mga hugis ng JSON output, gawi ng config/environment, at mga naka-package na file.
- Dapat gamitin ng mga string na nakikita ng user sa CLI ang CLI i18n layer at panatilihing magkakatugma ang mga catalog na `en`/`pt-BR`.
- Panatilihin ang Node bilang sinusuportahang runtime at ang kontrata ng nai-publish na binary.

**Nakatuong loop**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # mga pagbabago sa nabuo/naka-bundle na CLI
npm run check:pack-policy     # mga pagbabago sa package surface
npm run lint
```

Gamitin ang eksaktong command sa isang pansamantalang data directory kapag nakadepende ang gawi sa pag-parse, mga file, o exit
status. Isinasagawa ng CI ang mas malawak na pagsusuri sa package artifact at ecosystem.

### Database

**Mga kontrata**

- Mga domain module sa ilalim ng `src/lib/db/`; direktang mag-import ng mga partikular na module (inalis na ang lumang re-export layer na `localDb.ts`).
- Mga may numerong idempotent na SQL migration sa ilalim ng `src/lib/db/migrations/`, kaligtasan ng transaksyon, gawi ng pag-upgrade,
  mga index, at bawat caller na apektado ng schema.
- Hindi kailanman direktang nagpapatakbo ng raw SQL ang mga route at handler.

**Nakatuong loop**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Subukan ang parehong bagong database at pag-upgrade mula sa naunang schema kapag nagdaragdag ng migration. Dapat
isara ng mga database test ang mga handle at tawagin ang `resetDbInstance()` habang naglilinis. Patakbuhin lamang ang `npm run test:bun:db` kapag
nagbabago ang best-effort Bun adapter path; nananatiling awtoritatibo ang Node.

### Build / deploy

**Mga kontrata**

- Mga root at workspace manifest/lockfile, `scripts/build/`, standalone assembly ng Next.js, mga nilalaman ng package na `dist/`,
  metadata ng Electron platform, mga CI workflow, at mga deployment sentinel.
- Dapat manatiling buo ang mga sinusuportahang Node range at ang pinahihintulutang paggamit ng Bun sa `CLAUDE.md`.
- Mananatiling hindi sinusubaybayan ang mga build artifact; nalalapat ang mga patakaran sa dependency, lisensya, workflow, at package.

**Nakatuong loop**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # mga pagbabago sa dependency o lockfile
npm run check:pack-policy      # mga pagbabago sa surface ng nai-publish na package
npm run lint
```

Gamitin lamang ang `npm run build` nang lokal kapag nakaaapekto ang pagbabago sa compilation, standalone assembly, mga asset,
o runtime bundling. Gamitin lamang ang `npm run build:release` para sa release/deploy validation. Ang build ng CI ang
panghuling cross-platform na batayan; kailangan ng mga pagbabagong partikular sa platform ng Electron ang katugmang nakatuong build
o ebidensya mula sa smoke test.

## Mga developer script para sa isang shared machine

Dalawang helper sa `scripts/dev/` ang naglalarawan sa lokal na loop sa isang devbox kung saan may iba pang aktibong session:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # mga file mula sa merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ang mismong mga file na ito
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # nakahiwalay na worktree, ligtas patakbuhin nang sabay
```

- Tina-typecheck ng `typecheck-touched.sh` ang mga nabagong `.ts/.tsx` file lamang sa pamamagitan ng pansamantalang
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) sa ilalim ng 6 GB heap, kaya pinapalitan nito ang pangbuong-proyektong `tsc -p tsconfig.json`
  na nauubusan ng memory sa isang abalang machine. Ipinapakita nito ang mga error sa mga nabagong file kasama ang isang linya ng buod at nag-e-exit
  nang may `1` para sa mga error sa mga nabagong file, `2` kapag ang tanging mga error ay nasa mga na-import na file o namatay ang tsc
  nang walang diagnostic (basahin ang log na tinutukoy nito sa ilalim ng `_artifacts/typecheck-touched/`), at `0` kapag
  walang error. Palaging inaalis ang pansamantalang tsconfig; huwag kailanman mag-commit ng ganoon.
- Isinasagawa nang sunod-sunod ng `new-worktree.sh` ang magkakasabay na run gamit ang `<git-common-dir>/omniroute-new-worktree.lock`
  (naghihintay nang hanggang 600 s bilang default, na may nakikitang mensahe; nakadokumento sa header ng script ang
  override) at ibinabalik
  nito ang branch na ginawa nito kapag nabigo ang `git worktree add` bago umiral ang worktree, kaya hindi
  kailangan ng manu-manong `git branch -D` para muling subukan. Hindi binago ang hard-linked na `node_modules` at ang kopya ng `.husky/_`.

## Lokal na candidate loop

Hindi mapatutunayan ng mga source test na nagbo-boot ang naka-package na artifact: ang mga listahan sa packaging, mga na-prune na dependency,
at mga native binary ay nabibigo lamang kapag na-install at nasimulan na ang tarball. Ang `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ang lokal na bahagi ng build-once / validate / promote flow mula sa
RFC #8084: bumubuo ito ng isang candidate, vina-validate ang mismong artifact na iyon, pino-promote ito sa pamamagitan ng pagpapalit ng pangalan ng
mga directory, at ibinabalik ito kapag bumagsak sa health check ang na-promote na slot.

```bash
npm run dev:candidate -- run --dry-run --json  # ipakita ang plano, walang babaguhin
npm run dev:candidate -- run                   # bumuo + mag-validate + mag-promote, awtomatikong mag-rollback
npm run dev:candidate -- build                 # npm pack + i-install sa _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # i-boot sa isang libreng port, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # ipagpalit ang current at previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # muling gamitin ang tarball na binuo sa ibang lugar (CI)
```

- **Bumuo nang isang beses.** Pina-pack ng `build` ang kasalukuyang tree (kailangan nito ang `dist/server.js`, kaya patakbuhin muna ang
  `npm run build:release`) o kinokopya ang `--from-tarball`, pagkatapos ay ini-install ang tarball sa isang
  nakahiwalay na npm prefix, dahil walang kasamang `node_modules` ang tarball. Ang id ay ang maikling `HEAD`
  sha (`-dirty` kapag may mga lokal na pagbabago ang tree) o `tgz-<sha256>` para sa isang tarball. Ang clean id na
  nabuo na ay muling ginagamit sa halip na buuin muli; ipasa ang `--force` upang buuin itong muli.
- **I-validate ang package, hindi ang source.** Sinisimulan ng `validate` ang naka-install na CLI
  (`serve --port <free port>`) gamit ang bagong `DATA_DIR=<candidate>/data`, mga pekeng secret, at inalis sa
  environment ang `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY`, at `INITIAL_PASSWORD` ng operator, upang masuri nito
  ang keyless loopback posture ng isang bagong install. Hinihintay nitong magbalik ng 200 ang
  `GET /api/health`, inaatasang magbalik ng 200 ang `GET /v1/models`, pinatitigil ang process group,
  at itinatala ang resulta sa `validation.json` kasama ang hash ng tarball.
- **I-promote ang parehong artifact.** Tinatanggihan ng `promote` ang isang candidate na walang pumapasang validation para sa
  kasalukuyang hash ng tarball nito. Ang default na aktibong slot ay `_artifacts/candidate/current`; pumipili ang `--target <dir>`
  ng ibang directory sa parehong filesystem, at ang previous slot nito ay `<dir>.previous`.
  Atomic ang bawat pagpapalit ng pangalan, at kapag nagkaroon ng pagkabigo sa kalagitnaan, ibinabalik ang mga pagpapalit ng pangalang naisagawa na.
- **Mag-rollback.** Muling vina-validate ng `run` ang na-promote na slot at ibinabalik ang pagpapalitan ng `current` at `previous` kapag
  nabigo ang check na iyon. Hindi kailanman pino-promote ang candidate na nabigo sa unang validation.

Isinusulat ang lahat sa ilalim ng gitignored na `_artifacts/candidate/`; hindi kailanman ginagalaw ang umiiral na installation ng OmniRoute
at ang data directory nito. Ang na-promote na CLI ay
`_artifacts/candidate/current/prefix/bin/omniroute`; simulan ito gamit ang sarili mong `DATA_DIR` kapag ginagamit mo
ito. Mga exit code: `0` tagumpay, `1` nabigong validation o promotion, `2` error sa paggamit o nawawalang build.

## Lokal na loop kumpara sa CI

| Patakbuhin nang lokal para sa bawat patch                                                    | Nagbibigay ang CI ng malawakang signal                                        |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Mga direktang pagsubok sa gawi at mga gate ng kategorya sa itaas                             | Hinating buong unit suite at mga serial test                                  |
| `npm run lint`                                                                               | Mga Vitest suite at mga ratchet para sa coverage/kalidad                      |
| Typecheck o build lamang kapag kinakailangan ito ng apektadong contract                      | Production build, seguridad, docs, dependency, at mga gate ng patakaran sa PR |
| Mga manu-manong interaction/live check lamang kapag hindi mapatunayan ng automation ang gawi | Mga cross-job integration at platform check na na-configure ng workflow       |

Ang isang matagumpay na nakatuong loop ay ebidensya tungkol sa binagong contract, hindi patunay na papasa ang mga walang kaugnayang CI check. Sa kabilang banda, huwag paghintayin ang bawat lokal na pagbabago sa buong repository matrix.

## Checklist sa rekonsilyasyon

Bago humiling ng review:

- Kumpirmahing ang base ng PR ay ang pinakamataas na aktibong branch na `release/v*`.
- I-fetch ang base na iyon at suriin ang mga commit na na-merge mula nang gawin mo ang iyong branch.
- Suriin ang `git diff <active-base>...HEAD` para sa hindi sinasadya o awtomatikong nabuong churn.
- Lutasin ang mga conflict sa catalog at mga nabuong dokumento sa pamamagitan ng pag-update sa source at muling pagbuo ng output.
- Patakbuhing muli ang bawat nakatuong test/gate na nakalista sa paglalarawan ng PR pagkatapos ng rekonsilyasyon.
- Huwag kailanman pahinain ang mga assertion o alisin ang mga kinakailangang test para lamang tumugma sa nabagong base.

Para sa mga panuntunan sa release freeze at retargeting, gamitin ang
[Modelo ng Branching at Release](BRANCHING_MODEL.md). Para sa kumpletong imbentaryo ng CI, gamitin ang
[Reperensya ng mga Quality Gate](../architecture/QUALITY_GATES.md).
