ਇਹ ਹਰ ਗੇਟ ਦਾ ਵਰਣਨ ਕਰਦਾ ਹੈ, ਇਹ ਕੀ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਇਹ ਕਿਸ CI ਜੌਬ ਵਿੱਚ ਚੱਲਦਾ ਹੈ, ਕੀ ਇਹ
ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਇਨਵੈਂਟਰੀ ਅਤੇ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਪ੍ਰੋਫ਼ਾਈਲ

### ਉਮੀਦਵਾਰ ਦਾਖ਼ਲਾ

CI ਅਤੇ Quality Gates ਵਰਕਫ਼ਲੋ ਹਰ ਇੱਕ ਸਥਿਰ ਫ਼ੈਸਲਾ ਜਾਰੀ ਕਰਦੇ ਹਨ: `Gate / CI` ਅਤੇ
`Gate / Quality`। ਉਹਨਾਂ ਦੀ ਵਰਜਨ-ਨਿਯੰਤਰਿਤ ਦਾਖ਼ਲਾ ਨੀਤੀ ਹਰ ਅੱਪਸਟ੍ਰੀਮ ਜੌਬ ਨੂੰ
ਲਾਜ਼ਮੀ ਜਾਂ ਸਲਾਹਕਾਰ ਵਜੋਂ ਸੂਚੀਬੱਧ ਕਰਦੀ ਹੈ। ਲਾਗੂ ਹੋਣ ਵਾਲੀ ਲਾਜ਼ਮੀ ਜੌਬ ਦਾ ਸਫਲ ਹੋਣਾ
ਜ਼ਰੂਰੀ ਹੈ: ਗੁੰਮ, ਰੱਦ, ਛੱਡੇ ਗਏ, ਬਕਾਇਆ ਅਤੇ ਅਣਜਾਣ ਨਤੀਜੇ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦੇ।
ਇੱਕ ਵੈਧ ਕੇਵਲ-ਡੌਕਸ ਜਾਂ ਕੇਵਲ-ਕੈਟਾਲੌਗ ਵਰਗੀਕਰਨ ਕੋਡ ਲੇਨ ਨੂੰ ਗੈਰ-ਲਾਗੂ ਬਣਾ ਸਕਦਾ ਹੈ;
ਡਰਾਫ਼ਟ PR ਸਵੀਕਾਰਿਆ ਹੋਇਆ ਉਮੀਦਵਾਰ ਨਹੀਂ ਹੈ। `hotfix` ਲੇਬਲ ਸਬੂਤ ਦੀ ਲੋੜ ਨੂੰ ਮੁਆਫ਼ ਨਹੀਂ ਕਰਦਾ।

ਦੋਵੇਂ ਵਰਕਫ਼ਲੋ PRs ਅਤੇ main/release ਬ੍ਰਾਂਚਾਂ ਲਈ ਪੁਸ਼, ਮੈਨੁਅਲ ਡਿਸਪੈਚ ਅਤੇ
merge-group ਇਵੈਂਟਾਂ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। Push, dispatch ਅਤੇ merge-group ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦੇ ਹਨ। Forks
ਅਤੇ merge groups ਉਹਨਾਂ ਜੌਬਾਂ ਲਈ ਹੋਸਟ ਕੀਤੇ ਰਨਰ ਵਰਤਦੇ ਹਨ ਜੋ ਹੋਰਥਾਂ self-hosted
ਰਨਰ ਚੁਣਦੀਆਂ ਹਨ; ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਲੋੜੀਂਦੀ ਹੋਸਟ ਕੀਤੀ ਸਮਰੱਥਾ ਦੀ ਪੁਸ਼ਟੀ ਕੀਤੀ ਜਾਣੀ ਚਾਹੀਦੀ ਹੈ।

ਹਰੇਕ JSON ਰਸੀਦ ਚੈੱਕ-ਆਉਟ ਕੀਤੇ SHA, ਵਰਕਫ਼ਲੋ ਰਨ ਅਤੇ ਕੋਸ਼ਿਸ਼ ਦੀ ਪਛਾਣ ਕਰਦੀ ਹੈ।
CLI ਚੈੱਕਆਉਟ/ਇਵੈਂਟ SHA ਦੇ ਬੇਮੇਲ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਵਰਕਫ਼ਲੋ ਟੈਸਟ ਨੀਤੀ ਮੈਂਬਰਸ਼ਿਪ ਨੂੰ
ਫ਼ੈਸਲਾ ਜੌਬ ਦੀ `needs` ਸੂਚੀ ਨਾਲ ਬੰਨ੍ਹਦੇ ਹਨ, ਤਾਂ ਜੋ ਕੋਈ ਨਵੀਂ ਜਾਂ ਹਟਾਈ ਗਈ ਲੇਨ ਚੁੱਪਚਾਪ ਗਾਇਬ ਨਾ ਹੋ ਸਕੇ।
ਰਸੀਦਾਂ ਆਪਣੇ ਵਰਕਫ਼ਲੋ ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ, ਪ੍ਰਕਾਸ਼ਨ, ਡਿਪਲੌਇਮੈਂਟ, ਜਾਂ ਮੌਜੂਦਾ
ਸਲਾਹਕਾਰ ਸਕੈਨਰ ਦੀਆਂ ਅੰਦਰੂਨੀ ਕਾਰਵਾਈਆਂ ਨੂੰ ਨਹੀਂ। ਬ੍ਰਾਂਚ ਨਿਯਮਾਂ ਵਿੱਚ ਦੋਵੇਂ ਚੈੱਕ ਨਾਂ ਸਰਗਰਮ ਕਰਨਾ ਇੱਕ
ਵੱਖਰਾ ਪ੍ਰਸ਼ਾਸਕੀ ਬਦਲਾਅ ਹੈ; ਇਹ ਜੌਬਾਂ ਜੋੜਨਾ ਆਪਣੇ ਆਪ ਵਿੱਚ ਕਿਸੇ ਬ੍ਰਾਂਚ ਨੂੰ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਕਰਦਾ।

### ਸਟੈਟਿਕ ਸਕੈਨ ਇਨਵੈਂਟਰੀ

ਵਰਜਨ-ਨਿਯੰਤਰਿਤ npm-alias ਇਨਵੈਂਟਰੀ ਅਤੇ ਸਟੈਟਿਕ-ਸਕੈਨ ਮੈਂਬਰਸ਼ਿਪ
`config/quality/gate-manifest.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਸਕ੍ਰਿਪਟ ਨਾਂ ਅਤੇ ਸਟੀਕ ਕਮਾਂਡਾਂ ਨੂੰ
`package.json` ਨਾਲ ਪ੍ਰਮਾਣਿਤ ਕਰਨ ਲਈ `npm run check:gate-manifest` ਚਲਾਓ; ਜੋੜ, ਹਟਾਉਣ ਅਤੇ
ਕਮਾਂਡ ਡ੍ਰਿਫ਼ਟ ਸਥਾਨਕ ਹੁੱਕ ਅਤੇ CI ਵਿੱਚ ਬਦਲਾਅ-ਵਰਗੀਕਰਨ ਜੌਬਾਂ ਦੋਵਾਂ ਨੂੰ ਅਸਫਲ ਕਰਦੇ ਹਨ।
ਕੋਈ alias ਵਰਕਫ਼ਲੋ ਜੌਬ, ਮੈਟ੍ਰਿਕਸ ਇੰਸਟੈਂਸ ਜਾਂ ਟੈਸਟ ਕੇਸ ਨਹੀਂ ਹੁੰਦਾ: ਇਹਨਾਂ ਗਿਣਤੀਆਂ ਨੂੰ
ਪਰਸਪਰ ਬਦਲਣਯੋਗ ਵਜੋਂ ਪੇਸ਼ ਨਹੀਂ ਕੀਤਾ ਜਾਣਾ ਚਾਹੀਦਾ।

ਚੁਣੇ ਹੋਏ aliases ਨੂੰ ਚਲਾਏ ਬਿਨਾਂ ਜਾਂਚਣ ਲਈ `npm run quality:scan -- --list` ਜਾਂ `npm run quality:scan:fast -- --list`
ਵਰਤੋ। ਰਨਰ npm ਐਂਟਰੀਪੌਇੰਟ ਨੂੰ ਕਾਲ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਇਸਦਾ ਰਨਟਾਈਮ (ਜਿੱਥੇ ਕੌਂਫਿਗਰ ਕੀਤਾ ਹੋਵੇ ਉੱਥੇ Bun ਸਮੇਤ) ਬਰਕਰਾਰ ਰਹਿੰਦਾ ਹੈ।
ਮੈਨੀਫੈਸਟ ਉਹਨਾਂ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਤੋਂ ਬਾਹਰਲੇ aliases ਨੂੰ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਕਾਲ ਕੀਤੇ ਵਜੋਂ ਦਰਜ ਕਰਦਾ ਹੈ, ਅਤੇ
ਸਿਰਫ਼-ਪੜ੍ਹਨ ਸਕੈਨ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵਿੱਚ ਰੱਖ-ਰਖਾਅ ਕਮਾਂਡਾਂ ਮਨਾਹੀ ਹਨ।

ਇਹ ਪ੍ਰੋਫ਼ਾਈਲ ਸਿਰਫ਼ ਸਟੈਟਿਕ ਸਕੈਨ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। ਇਹ ਉਤਪਾਦ ਟੈਸਟਾਂ,
ਕਵਰੇਜ, ਪੈਕੇਜਿੰਗ, ਬਾਹਰੀ ਚੈੱਕਾਂ ਜਾਂ ਕਿਸੇ ਉਮੀਦਵਾਰ ਦੀ ਪੂਰੀ ਰਿਲੀਜ਼ ਸਵੀਕ੍ਰਿਤੀ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਨਹੀਂ ਕਰਦੇ।
ਵਰਕਫ਼ਲੋ ਦਾਖ਼ਲਾ ਲਿੰਕ ਕੀਤੇ `config/quality/admission-policy.json` ਅਤੇ
`scripts/quality/admission-verdict.mjs` ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। Release-observer ਪ੍ਰੋਫ਼ਾਈਲ ਵੱਖਰੇ ਰਹਿੰਦੇ ਹਨ;
ਉਹਨਾਂ ਦੇ ਲਾਗੂ ਚੈੱਕਾਂ ਅਤੇ ਰਸੀਦਾਂ ਦੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਜਾਂਚ ਕਰੋ। ਹੇਠਾਂ ਦਿੱਤੀ ਗੱਦ
ਇਨਵੈਂਟਰੀ ਇੱਕ ਹਵਾਲਾ ਹੈ, ਇਹ ਇਸ ਗੱਲ ਦਾ ਸਬੂਤ ਨਹੀਂ ਕਿ ਕੋਈ ਗੇਟ ਅਸਲ ਵਿੱਚ ਚੱਲਿਆ ਸੀ।

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (ਨੀਤੀ ਗੇਟ) ਅਤੇ `scripts/quality/` (ਰੈਚਟ ਇੰਜਣ) ਦੇ ਅਧੀਨ ਮੌਜੂਦ ਹਨ।
CI ਲਈ ਪ੍ਰਮਾਣਿਕ ਸਰੋਤ `.github/workflows/ci.yml` ਹੈ।

### ਰਿਲੀਜ਼ PR ਫਾਸਟ-ਪਾਥ (`quality.yml`)

`.github/workflows/quality.yml` main/release PRs, ਸੁਰੱਖਿਅਤ-ਬ੍ਰਾਂਚ
ਪੁਸ਼ਾਂ, dispatch ਅਤੇ merge groups ਉੱਤੇ CI ਨੂੰ ਪੂਰਾ ਕਰਦਾ ਹੈ। PRs ਪਾਥ-ਫਿਲਟਰ ਕੀਤੇ ਤੇਜ਼ ਚੈੱਕ ਵਰਤਦੇ ਹਨ। ਸਥਾਈ ਤੌਰ 'ਤੇ
ਅਸਮਰੱਥ ਕੀਤਾ ਡੁਪਲੀਕੇਟ ਬਿਲਡ ਹਟਾ ਦਿੱਤਾ ਗਿਆ ਸੀ; ਅਸਲ build/package/boot ਚੈੱਕ CI ਵਿੱਚ ਬਰਕਰਾਰ ਹਨ।

| ਜੌਬ                                              | ਦਾਇਰਾ                                                                                                                                                                                               | ਬਲੌਕਿੰਗ         |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API ਡੌਕਸ ਹਵਾਲੇ ਅਤੇ docs-all                                                                                                                                                          | ਹਾਂ             |
| `Fast Quality Gates`                             | Code PRs; ਸਟੈਟਿਕ ਚੈੱਕ, typecheck, dashboard typecheck, ਪ੍ਰਭਾਵਿਤ unit tests                                                                                                                          | ਹਾਂ             |
| `Forgotten sibling tests`                        | Code PRs; ਬਦਲੇ ਹੋਏ ਮੌਡੀਊਲਾਂ ਤੋਂ ਸਟੈਟਿਕ ਉਪਭੋਗਤਾਵਾਂ ਅਤੇ ਸੰਭਾਵੀ sibling tests ਤੱਕ ਟਰੇਸ; barrel ਅਤੇ dynamic-import ਪਾਥ ਸਲਾਹਕਾਰ ਡਾਇਗਨੌਸਟਿਕ ਵਜੋਂ ਰਿਪੋਰਟ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਹਵਾਲਾ ਦਿੱਤੇ allowlist ਅਪਵਾਦਾਂ ਸਮੇਤ | **ਸਲਾਹਕਾਰ**     |
| `Vitest (fast-path)`                             | Code PRs; ਤੇਜ਼ vitest ਸੂਟ                                                                                                                                                                           | ਹਾਂ             |
| `Unit Tests fast-path`                           | Code PRs; 4-shard unit ਸੂਟ                                                                                                                                                                          | ਹਾਂ             |

#### ਭੁੱਲੇ ਹੋਏ sibling tests ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests` ਟੈਸਟ-ਪ੍ਰਭਾਵ ਮੈਪ ਦੇ ਪਿੱਛੇ ਵਾਲੇ import resolver ਨੂੰ ਮੁੜ ਵਰਤਦਾ ਹੈ।
ਹਰੇਕ ਬਦਲੇ ਹੋਏ production ਮੌਡੀਊਲ ਲਈ, ਜਦੋਂ ਸੰਭਾਵੀ
ਟੈਸਟ pull-request diff ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਇਹ ਨਿਰਧਾਰਿਤ `changed module/symbol -> static consumer -> candidate sibling test` ਲੜੀਆਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ।
ਕਿਸੇ ਵੀ ਬਲੌਕਿੰਗ ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਲਈ Markdown ਸੰਖੇਪ ਅਤੇ JSON ਨਤੀਜੇ ਨੂੰ
`forgotten-sibling-tests` ਵਰਕਫ਼ਲੋ ਆਰਟੀਫੈਕਟ ਵਜੋਂ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ।

Barrel ਮੁੜ-ਨਿਰਯਾਤ ਅਤੇ ਡਾਇਨਾਮਿਕ ਆਯਾਤ ਸਿਰਫ਼ resolution ਡਾਇਗਨੋਸਟਿਕ ਹਨ; ਇਹ ਕਦੇ ਵੀ
ਬਲਾਕ ਕਰਨ ਵਾਲੀ ਖੋਜ ਨਹੀਂ ਬਣਾਉਂਦੇ। ਸਮੀਖਿਆ ਕੀਤੇ ਅਪਵਾਦ
`config/quality/forgotten-sibling-allowlist.json` ਵਿੱਚ ਰਹਿੰਦੇ ਹਨ। ਹਰ ਐਂਟਰੀ ਵਿੱਚ consumer ਅਤੇ candidate
ਟੈਸਟ ਦਾ ਨਾਮ, ਇੱਕ ਵਿਸ਼ੇਸ਼ ਤਰਕ, ਅਤੇ GitHub issue ਜਾਂ pull request ਦਾ ਲਿੰਕ ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਗਲਤ ਬਣਤਰ ਵਾਲੀਆਂ ਐਂਟਰੀਆਂ
fail-closed ਹੁੰਦੀਆਂ ਹਨ। ਅਪਵਾਦ ਮਿਟਾਏ ਗਏ candidate ਟੈਸਟ ਜਾਂ `.skip`/`.todo` ਜੋੜਨ ਵਾਲੇ diff ਨੂੰ ਦਬਾ ਨਹੀਂ ਸਕਦੇ;
assertion ਨੂੰ ਕਮਜ਼ੋਰ ਕਰਨਾ ਅਤੇ ਹੋਰ masking ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਬਲਾਕ ਕਰਨ ਵਾਲੇ
`check:test-masking` gate ਦੀ ਜ਼ਿੰਮੇਵਾਰੀ ਰਹਿੰਦੇ ਹਨ।

| `check-new-key-coverage` (inline) | ਇੱਕ **ਨਵੀਂ** ਅੰਗਰੇਜ਼ੀ key ਦਾ ਹਰੇਕ locale ਵਿੱਚ ਅਨੁਵਾਦ ਕੀਤਾ ਗਿਆ ਹੈ — `__MISSING__:` ਮਾਰਕਰ ਅਸਵੀਕਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ                                                                           | ਹਾਂ          |
| `check-translation-ratio`         | ਹਰੇਕ locale ਲਈ ਅਸਲ-ਅਨੁਵਾਦ ਅਨੁਪਾਤ (allowlist ਤੋਂ ਬਾਹਰ ਅੰਗਰੇਜ਼ੀ ਨਾਲ ਇੱਕੋ ਜਿਹੇ / placeholder / ਗੁੰਮ leaves) `config/quality/i18n-translation-baseline.json` + ਛੋਟ ਤੋਂ ਵੱਧ ਨਹੀਂ ਹੋਣਾ ਚਾਹੀਦਾ | **ਸਲਾਹਕਾਰੀ** |

`fetch-depth: 0` ਦੀ ਲੋੜ ਹੈ — value-drift ਗੇਟ merge base ਦੇ ਮੁਕਾਬਲੇ `en.json` ਦਾ diff ਕਰਦਾ ਹੈ।

#### `check-ui-value-drift` — ਪੁਰਾਣੇ-ਅਨੁਵਾਦ ਦਾ ਗੇਟ

ਇਹ ਉਸ ਇੱਕ i18n regression ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ ਹੋਰ ਗੇਟ ਸੰਰਚਨਾਤਮਕ ਤੌਰ 'ਤੇ ਨਹੀਂ ਦੇਖ ਸਕਦੇ: ਇੱਕ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ
ਮੁੜ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ _ਪਿਛਲੇ_ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਤੋਂ ਬਣੇ ਅਨੁਵਾਦ ਉੱਥੇ ਹੀ ਰਹਿ ਜਾਂਦੇ ਹਨ, ਜਿਸ ਕਰਕੇ
ਗ਼ੈਰ-ਅੰਗਰੇਜ਼ੀ ਵਰਤੋਂਕਾਰ ਭਰੋਸੇ ਨਾਲ ਲਿਖੀ ਹੋਈ, ਪਰ ਹੁਣ ਗ਼ਲਤ, ਲਿਖਤ ਪੜ੍ਹਦੇ ਰਹਿੰਦੇ ਹਨ।

ਇਹ ਅਸਲ ਵਿੱਚ ਰਿਲੀਜ਼ ਹੋਇਆ ਸੀ। ਜਦੋਂ Antigravity
login helper ਸ਼ਾਮਲ ਕੀਤਾ ਗਿਆ (#5203), ਤਾਂ `oauthModal.googleOAuthWarning` ਮੁੜ ਲਿਖਿਆ ਗਿਆ; **43 ਵਿੱਚੋਂ 39 locales** ਵਿੱਚ ਉਹ ਲਿਖਤ ਹੀ ਰਹੀ ਜੋ operators ਨੂੰ "ਪੂਰਾ
URL ਕਾਪੀ ਕਰਕੇ ਹੇਠਾਂ ਪੇਸਟ ਕਰਨ" ਲਈ ਕਹਿੰਦੀ ਸੀ — ਇੱਕ ਅਜਿਹਾ flow ਜੋ ਉਸ provider ਲਈ ਪੂਰਾ ਹੀ ਨਹੀਂ ਹੋ ਸਕਦਾ। ਇਹ
#8463 ਤੱਕ ਕਿਸੇ ਦੀ ਨਜ਼ਰ ਵਿੱਚ ਨਹੀਂ ਆਇਆ, ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹ keys backfill ਕਰਦਾ ਹੈ ਜੋ **ਗੈਰ-ਮੌਜੂਦ** ਹਨ, ਉਹਨਾਂ ਨੂੰ ਕਦੇ ਨਹੀਂ ਜੋ **ਪੁਰਾਣੀਆਂ** ਹਨ;
- `check-ui-keys-coverage` key ਦੀ _ਮੌਜੂਦਗੀ_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣੇ ਅਨੁਵਾਦ ਨੂੰ ਵੀ ਕਵਰ ਕੀਤਾ ਹੋਇਆ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ਦਸਤਾਵੇਜ਼ੀ mirrors ਨੂੰ ਟ੍ਰੈਕ ਕਰਦਾ ਹੈ —
  ਇਹ ਕਦੇ ਵੀ `src/i18n/messages/*.json` ਨੂੰ ਨਹੀਂ ਪੜ੍ਹਦਾ। 2026-09 ਦੇ ਮੁੜ-sync ਤੋਂ ਬਾਅਦ ਜੌਬ `docs-sync-strict` ਵਿੱਚ ਰੋਕਣ ਵਾਲਾ: ਕੋਈ ਮੁੱਖ ਦਸਤਾਵੇਜ਼ ਸੋਧੋ → `npm run i18n:run -- --files=<doc>` (ਸੈਕਸ਼ਨ-ਪੱਧਰ, ਘੱਟ ਖ਼ਰਚ ਵਾਲਾ)।

**Diff-ਸਚੇਤ, baseline-ਸਮਰਥਿਤ ਨਹੀਂ।** ਇਹ merge base ਉੱਤੇ ਮੌਜੂਦ `en.json` ਦੀ ਤੁਲਨਾ
working tree ਨਾਲ ਕਰਦਾ ਹੈ; ਹਰ ਉਸ key ਲਈ ਜਿਸਦਾ English ਮੁੱਲ ਬਦਲਿਆ ਹੈ, ਕੋਈ ਵੀ locale ਜਿਸ ਵਿੱਚ
ਹਾਲੇ ਵੀ ਨਾ-ਬਦਲਿਆ ਅਨੁਵਾਦ ਮੌਜੂਦ ਹੈ, ਪੁਰਾਣਾ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ। ਇਹ ਜਾਣ-ਬੁੱਝ ਕੇ **ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਕਰਜ਼ੇ ਨੂੰ ਸਥਿਰ ਰੱਖਦਾ ਹੈ** — ਕੋਈ diff
ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਲੰਬੇ ਸਮੇਂ ਤੋਂ ਮੌਜੂਦ ਅਨੁਵਾਦ ਕਿਸ ਪੁਰਾਣੇ English ਪਾਠ ਤੋਂ ਆਇਆ ਸੀ, ਇਸ ਲਈ gate
ਸਿਰਫ਼ ਉਸੇ ਨੂੰ ਜਾਂਚਦਾ ਹੈ ਜਿਸਨੂੰ ਮੌਜੂਦਾ ਤਬਦੀਲੀ ਛੂੰਹਦੀ ਹੈ। ਵਿਕਲਪ (ਹਰ key ਲਈ hash baseline) ਦੀ ਲਾਗਤ
ਲਗਭਗ 600 KB ਦੀ generated file ਹੋਵੇਗੀ, ਜੋ ਸਭ ਤੋਂ ਵੱਡੇ ਮੌਜੂਦਾ baseline ਤੋਂ 3× ਵੱਡੀ ਹੈ ਅਤੇ ਹਰ i18n PR ਉੱਤੇ ਬਦਲੇਗੀ।

ਇਸਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ ਅਨੁਵਾਦਾਂ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ, ਜਾਂ
2. ਉਨ੍ਹਾਂ ਨੂੰ `__MISSING__:<new english>` ਉੱਤੇ ਸੈੱਟ ਕਰੋ — ਫਿਰ runtime ਸਹੀ ਕੀਤਾ ਹੋਇਆ English ਪਾਠ ਦਿੰਦਾ ਹੈ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਅਤੇ key ਨੂੰ ਅਨੁਵਾਦ ਲਈ ਕਤਾਰ ਵਿੱਚ ਜੋੜ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।

ਜੇ string ਦਾ **ਅਰਥ** ਬਦਲਿਆ ਹੈ, ਤਾਂ **key ਦਾ ਨਾਮ ਬਦਲਣ** ਨੂੰ ਤਰਜੀਹ ਦਿਓ: ਨਵੀਂ key
ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵਿਰਾਸਤ ਵਿੱਚ ਨਹੀਂ ਲੈ ਸਕਦੀ। #8463 ਵਿੱਚ ਇਹੀ pattern ਵਰਤਿਆ ਗਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # ਸਖ਼ਤ (ਜੋ CI ਚਲਾਉਂਦਾ ਹੈ)
npm run i18n:check-value-drift:warn     # ਸਿਰਫ਼ ਰਿਪੋਰਟ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ਜਦੋਂ base catalog ਨੂੰ ਪੜ੍ਹਿਆ ਨਹੀਂ ਜਾ ਸਕਦਾ (base ref ਤੋਂ ਬਿਨਾਂ shallow
clone), ਤਾਂ `SKIP reason=base-unresolved` ਨਾਲ 0 exit ਕਰਦਾ ਹੈ, ਜੋ `check-openapi-breaking` ਦੇ ਵਿਹਾਰ ਨੂੰ ਦਰਸਾਉਂਦਾ ਹੈ।

**ਨਵਾਂ-ਕੋਡ ਮੋਡ (Clean-as-You-Code) — 2026-08-30 ਤੋਂ, ਸਿਰਫ਼ PR ਫਾਸਟ-ਪਾਥ**

`pull_request` ਇਵੈਂਟਾਂ ਉੱਤੇ `quality.yml`, `--base-ref <PR base SHA>` ਨੂੰ `check:file-size`,

ਨੇ ਬਦਲਿਆ ਹੈ** (`scripts/check/newCodeMode.mjs`: ਮਰਜ-ਬੇਸ ਨੂੰ ਇੱਕ ਅਸਥਾਈ
`git worktree` ਵਿੱਚ ਸਾਕਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ESLint/knip ਉੱਥੇ ਅਤੇ HEAD ਉੱਤੇ ਚਲਾਏ ਜਾਂਦੇ ਹਨ, ਅਤੇ ਪ੍ਰਤੀ-ਫ਼ਾਈਲ ਗਿਣਤੀਆਂ ਦਾ ਡਿਫ਼ ਕੱਢਿਆ ਜਾਂਦਾ ਹੈ):

- **ਬਲੌਕਿੰਗ** — PR ਨੇ ਆਪਣੀਆਂ ਬਦਲੀਆਂ ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਸਾਈਕਲੋਮੈਟਿਕ/ਕਾਗਨਿਟਿਵ ਉਲੰਘਣਾਵਾਂ ਜਾਂ ਡੈੱਡ ਐਕਸਪੋਰਟ ਜੋੜੇ ਹਨ
  (ਲੌਗ ਵਿੱਚ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ਸਲਾਹਕਾਰੀ** — ਗਲੋਬਲ ਕੁੱਲ ਬਨਾਮ ਫ੍ਰੀਜ਼ ਕੀਤੀ ਬੇਸਲਾਈਨ। ਵਿਰਾਸਤ ਵਿੱਚ ਮਿਲੀ ਡ੍ਰਿਫ਼ਟ ਕਦੇ ਵੀ
  ਕਿਸੇ ਬੇਕਸੂਰ PR ਨੂੰ ਲਾਲ ਨਹੀਂ ਕਰਦੀ; ਰਿਲੀਜ਼ ਮਿਲਾਣ ਵੇਲੇ ਡ੍ਰਿਫ਼ਟ ਨੂੰ ਮੁੜ ਫ੍ਰੀਜ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਹੈੱਡਰੂਮ ਜੌਬ ਦੁਆਰਾ ਨਿਗਰਾਨੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

`check:file-size` ਆਪਣੇ ਨਿਯਮਾਂ ਅਨੁਸਾਰ ਬੇਸ ਰੈਫ਼ ਵਰਤਦਾ ਹੈ (`scripts/check/check-file-size.mjs`, #8522):
ਇਹ ਟ੍ਰੀ ਵਿੱਚ ਹਰ ਸਰੋਤ ਅਤੇ ਟੈਸਟ ਫ਼ਾਈਲ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ, `git show` ਨਾਲ PR ਬੇਸ ਉੱਤੇ ਹਰੇਕ ਦੀ ਲਾਈਨ ਗਿਣਤੀ
ਪੜ੍ਹਦਾ ਹੈ, ਅਤੇ ਕਿਸੇ ਫ਼ਾਈਲ ਨੂੰ ਸਿਰਫ਼ ਉਦੋਂ ਫੇਲ ਕਰਦਾ ਹੈ ਜਦੋਂ ਉਹ ਆਪਣੀ ਬੇਸਲਾਈਨ ਸੀਮਾ
(`frozen` / `testFrozen`, ਜਾਂ ਬੇਸਲਾਈਨ ਤੋਂ ਬਾਹਰਲੀ ਫ਼ਾਈਲ ਲਈ `cap` / `testCap`) ਅਤੇ ਆਪਣੇ ਬੇਸ
ਆਕਾਰ ਵਿੱਚੋਂ ਵੱਡੇ ਮੁੱਲ ਤੋਂ ਅੱਗੇ ਵਧਦੀ ਹੈ। ਇਸ ਲਈ, ਬੇਸ ਉੱਤੇ ਪਹਿਲਾਂ ਹੀ ਡ੍ਰਿਫ਼ਟ ਹੋਈ ਫ਼ਾਈਲ ਕਦੇ ਵੀ ਕਿਸੇ ਬੇਕਸੂਰ PR ਨੂੰ ਲਾਲ ਨਹੀਂ ਕਰਦੀ।

`check:boundary:ratchet` ਆਪਣੇ ਇਕੱਲੇ ਅੰਕ ਉੱਤੇ ਵੀ ਇਹੀ ਨਿਯਮ ਲਾਗੂ ਕਰਦਾ ਹੈ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ਇਵੈਂਟਾਂ ਉੱਤੇ
`quality.yml` ਦੇ fast-gates ਅਤੇ `ci.yml` ਦੀ lint job ਦੋਵੇਂ PR ਦਾ base SHA ਪਾਸ ਕਰਦੇ ਹਨ, base commit ਨੂੰ
`git archive` export ਤੋਂ ਮਾਪਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ PR ਕੇਵਲ ਉਦੋਂ ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਇਸਦੀ `open-sse → src` edge
ਗਿਣਤੀ `metrics.boundaryOpenSseToSrc` ਅਤੇ base ਉੱਤੇ ਮੌਜੂਦ ਗਿਣਤੀ ਵਿੱਚੋਂ ਵੱਡੀ ਗਿਣਤੀ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ। ਸੀਮਾ
ਤੋਂ ਉੱਪਰ base drift ਦੀ ਰਿਪੋਰਟ ਕੀਤੀ ਜਾਂਦੀ ਹੈ (`base drift herdado`), ਪਰ ਇਹ ਕਦੇ ਵੀ ਕਿਸੇ ਬੇਕਸੂਰ PR ਨੂੰ ਅਸਫਲ
ਨਹੀਂ ਕਰਦੀ; push → main ਪੂਰਨ ਸੀਮਾ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ, ਅਤੇ resolve ਨਾ ਹੋ ਸਕਣ ਵਾਲਾ base SHA ਚੇਤਾਵਨੀ
ਦੇ ਨਾਲ ਉਸੇ ਉੱਤੇ fallback ਕਰਦਾ ਹੈ।

`workflow_dispatch` runs, release-green sweep ਅਤੇ nightly headroom job ਕੋਲ ਕੋਈ PR base ਨਹੀਂ ਹੁੰਦਾ
ਅਤੇ ਉਹ ਪੂਰਨ (global) ਤੁਲਨਾ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ। Coverage, duplication ਅਤੇ type-coverage ਫਿਲਹਾਲ global
ਹੀ ਰਹਿੰਦੇ ਹਨ (ਉਨ੍ਹਾਂ ਦੇ tools ਘੱਟ ਲਾਗਤ ਨਾਲ per-file diff ਨਹੀਂ ਬਣਾਉਂਦੇ) — ਇਹ ਵੀ ਇਸੇ ਵਿਵਹਾਰ ਲਈ ਉਮੀਦਵਾਰ ਹਨ।

**v4.0 ਉੱਤੇ ਪੜਾਅ ਸਮਾਪਤ ਕਰਨਾ (LTS = ਪਹਿਲਾਂ ਨਾਲੋਂ ਵਧੇਰੇ ਸਖ਼ਤ, "ਵਾਪਸ ਆਮ ਵਾਂਗ" ਨਹੀਂ)**

2. `quality-baseline.json` ਵਿੱਚੋਂ `_policy` ਮਿਟਾਓ (`--require-tighten` ਅਤੇ nightly

### CodeQL ਰੈਚਟ: ਰਿਫ੍ਰੈਸ਼ ਦੀ ਆਵਿਰਤੀ ਅਤੇ ਮੈਨੁਅਲ ਟ੍ਰਿਗਰ

`state: configured`, `schedule: weekly`: ਇਹ GitHub ਦਾ ਡਿਫਾਲਟ-ਸੈੱਟਅੱਪ ਸਕੈਨ ਹੈ, ਨਾ ਕਿ ਹਰ ਪੁਸ਼
ਲਈ ਕੀਤਾ ਜਾਣ ਵਾਲਾ ਵਿਸ਼ਲੇਸ਼ਣ। ਨਤੀਜਾ: ਅਲਰਟ ਠੀਕ ਕਰਨ ਵਾਲੀ PR ਦੇ ਮਰਜ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਰੈਚਟ
ਅਗਲਾ ਨਿਰਧਾਰਤ ਸਕੈਨ ਚੱਲਣ ਤੱਕ ਪੁਰਾਣੀ, ਵੱਧ ਗਿਣਤੀ ਹੀ ਪੜ੍ਹਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਸਕੈਨ ਦੇ
ਅੱਪਡੇਟ ਹੋਣ ਤੱਕ ਇਹ ਹਰ ਖੁੱਲ੍ਹੀ PR, ਫਿਕਸ ਕਰਨ ਵਾਲੀ PR ਦੀਆਂ ਆਪਣੀਆਂ ਅਗਲੀਆਂ ਤਬਦੀਲੀਆਂ ਸਮੇਤ,
'ਤੇ ਰਿਗ੍ਰੈਸ਼ਨ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ।

**ਮੈਨੁਅਲ ਰਿਫ੍ਰੈਸ਼**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ਵਿਸ਼ਲੇਸ਼ਣ ਨੂੰ ਮੁੜ
ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਕੁਝ ਮਿੰਟਾਂ ਵਿੱਚ ਅਲਰਟ ਦੁਬਾਰਾ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਪਹਿਲਾਂ `.github/workflows/codeql.yml`
ਪੜ੍ਹੋ — ਇਸਦਾ ਸਿਰਲੇਖ ਸਮਝਾਉਂਦਾ ਹੈ ਕਿ ਇਹ ਸਿਰਫ਼ `workflow_dispatch` ਲਈ ਹੈ, **ਕਿਉਂਕਿ ਇਸਦਾ
GitHub ਦੇ "default setup" ਨਾਲ ਟਕਰਾਅ ਹੁੰਦਾ ਹੈ** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`)। `push`/`pull_request`/

## ਨਵਾਂ ਗੇਟ ਸ਼ਾਮਲ ਕਰਨਾ

1. `scripts/check/check-<name>.mjs` (ਜਾਂ `.ts`) ਬਣਾਓ। ਨੀਤੀ ਗੇਟ 0/1 ਨਾਲ ਬੰਦ ਹੁੰਦੇ ਹਨ।

3. ਇਸਨੂੰ `.github/workflows/ci.yml` ਵਿੱਚ ਢੁਕਵੀਂ ਜੌਬ ਹੇਠ ਜੋੜੋ
   (ਨੀਤੀ → `lint` ਜਾਂ `docs-sync-strict`; ਰੈਚਿਟ → `quality-gate`)।
4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

### ਮਰਜ / ਡੀਡੁਪ (ਮਕੈਨੀਕਲ, ਘੱਟ ਜੋਖਮ)

ਹਰ ਉਮੀਦਵਾਰ ਨੂੰ 2026-06-17 ਨੂੰ ਲਾਈਵ ਗੇਟ ਸਥਿਤੀ ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਗਿਆ ਸੀ (ਭਰੋਸਾ ਕਰੋ, ਪਰ ਤਸਦੀਕ ਵੀ ਕਰੋ);
ਕਈ "ਸਪਸ਼ਟ" ਮਰਜਾਂ ਦੇ ਪਿੱਛੇ ਕਰਜ਼ਾ ਲੁਕਿਆ ਹੋਇਆ ਨਿਕਲਿਆ ਅਤੇ ਉਹ **ਸਿੱਧੇ ਤੌਰ 'ਤੇ ਵਰਤਣਯੋਗ ਬਦਲ ਨਹੀਂ** ਹਨ।

- **`check:docs-sync` ਦੋ ਵਾਰ ਚੱਲਦਾ ਹੈ** — `lint` ਜੌਬ ਵਿੱਚ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਅਤੇ ਮੁੜ `check:docs-all` (`docs-sync-strict`) ਅਤੇ husky pre-commit ਹੁੱਕ ਦੇ ਅੰਦਰ। ✅ **ਪੂਰਾ ਹੋਇਆ** — ਵੱਖਰਾ `lint` ਇਨਵੋਕੇਸ਼ਨ ਹਟਾਇਆ ਗਿਆ।
- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼-ਸੁਥਰਾ ਮਰਜ ਨਹੀਂ ਹੈ।** `audit:deps` ਕਿਸੇ ਵੀ high/critical CVE 'ਤੇ ਹਾਰਡ-ਫੇਲ ਹੁੰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਬੇਸਲਾਈਨ (ਇਸ ਵੇਲੇ 1 MODERATE) ਦੇ ਮੁਕਾਬਲੇ ਕਿਸੇ _ਰਿਗ੍ਰੈਸ਼ਨ_ 'ਤੇ ਫੇਲ ਹੁੰਦਾ ਹੈ। ਅਰਥ-ਵਿਹਾਰ ਵੱਖਰੇ ਹਨ — `audit:deps` ਨੂੰ ਹਟਾਉਣ ਨਾਲ ਪੂਰਨ high/critical ਗੇਟ ਖਤਮ ਹੋ ਜਾਵੇਗਾ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਚੱਕਰ ਖੋਜ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (#15159 G-01/G-02)। ਇੱਥੇ ਪੁਰਾਣੇ ਟੈਕਸਟ ਨੇ `check:cycles` ਨੂੰ "ਹਰਾ, ਸੰਭਾਲ ਕੇ ਚੁਣਿਆ" ਗੇਟ ਕਿਹਾ ਸੀ ਅਤੇ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖਣ ਨੂੰ ਇਸ ਆਧਾਰ 'ਤੇ ਜਾਇਜ਼ ਠਹਿਰਾਇਆ ਸੀ ਕਿ `check:circular-deps` (dpdm) ਨੇ 91 ਚੱਕਰ ਰਿਪੋਰਟ ਕੀਤੇ ਸਨ। ਉਹ ਹਰਾ ਦਰਜਾ ਇੱਕ **ਗਲਤ ਹਰਾ ਸੰਕੇਤ** ਸੀ: `check:cycles` ਨੇ 5 ਸਬਡਾਇਰੈਕਟਰੀਆਂ (450 ਫ਼ਾਈਲਾਂ) ਸਕੈਨ ਕੀਤੀਆਂ, ਸਿਰਫ਼ ਸਥਿਰ `import|export … from` ਨਾਲ ਮੇਲ ਕੀਤਾ, ਅਤੇ ਹਰੇਕ `@/` ਅਤੇ `@omniroute/open-sse/` ਸਪੈਸੀਫਾਇਰ ਨੂੰ ਛੱਡ ਦਿੱਤਾ, ਇਸ ਲਈ ਇਹ ਉਹ dynamic-import + alias ਚੱਕਰ ਨਹੀਂ ਦੇਖ ਸਕਿਆ ਜੋ ਰਿਪੋ ਵਿੱਚ ਹਾਵੀ ਸਨ। ਠੀਕ ਕੀਤਾ ਗਿਆ: ਗੇਟ ਹੁਣ `src` + `open-sse` (5023 ਫ਼ਾਈਲਾਂ) ਵਿੱਚੋਂ ਲੰਘਦਾ ਹੈ, TypeScript AST ਤੋਂ ਸਪੈਸੀਫਾਇਰ ਇਕੱਠੇ ਕਰਦਾ ਹੈ (ਇਸ ਲਈ `import("…")` ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ type-position `typeof import("…")` ਨਹੀਂ), ਅਤੇ tsconfig `paths` ਨੂੰ ਰਿਜ਼ੌਲਵ ਕਰਦਾ ਹੈ। ਇਹ 0 ਨਹੀਂ, ਸਗੋਂ **14** ਚੱਕਰ ਲੱਭਦਾ ਹੈ। ਕਿਉਂਕਿ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ 14 ਚੱਕਰਾਂ ਨੂੰ ਗੇਟ PR ਵਿੱਚ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, `check:cycles` ਹੁਣ ਇੱਕ **ਰੈਚਿਟ** ਹੈ (`--ratchet`, `quality-baseline.json` ਵਿੱਚ ਸੀਮਾ `metrics.cycles.value = 14`, `direction: down`) — ਇਹ ਕਿਸੇ ਵੀ _ਰਿਗ੍ਰੈਸ਼ਨ_ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ ਅਤੇ ਗਿਣਤੀ ਸਿਰਫ਼ ਘਟ ਸਕਦੀ ਹੈ। CI `npm run check:cycles:ratchet` ਚਲਾਉਂਦਾ ਹੈ। ਘਟਾਓ ਦਾ ਕੰਮ **A-01** ਦੇ ਨਾਲ ਚੱਲੇਗਾ। `check:circular-deps` (dpdm) ਵਿਆਪਕ ਦੂਜੀ ਰਾਏ ਵਜੋਂ ਸਲਾਹਕਾਰੀ ਰਹਿੰਦਾ ਹੈ।
- **ਜਟਿਲਤਾ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, `ruleId` ਮੁਤਾਬਕ ਗਿਣਤੀ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive ਬੇਸਲਾਈਨਾਂ ਸੁਤੰਤਰ ਰਹਿਣ; ਵੱਖਰੇ `check:complexity` / `check:cognitive-complexity` ਲੋਕਲ `--update` ਲਈ ਬਰਕਰਾਰ ਹਨ।
