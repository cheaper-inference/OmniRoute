ਇਹ ਦਸਤਾਵੇਜ਼ OmniRoute ਵਿੱਚ ਸਾਰੇ CI ਗੁਣਵੱਤਾ ਗੇਟਾਂ ਲਈ ਪ੍ਰਮਾਣਿਕ ਹਵਾਲਾ ਹੈ।
ਇਹ ਹਰ ਗੇਟ ਦਾ ਵਰਣਨ ਕਰਦਾ ਹੈ, ਇਹ ਕੀ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਇਹ ਕਿਸ CI ਜੌਬ ਵਿੱਚ ਚੱਲਦਾ ਹੈ, ਕੀ ਇਹ
ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਸੂਚੀ ਅਤੇ ਐਗਜ਼ਿਕਿਊਸ਼ਨ ਪ੍ਰੋਫ਼ਾਈਲ

### ਉਮੀਦਵਾਰ ਦੀ ਪ੍ਰਵਾਨਗੀ

CI ਅਤੇ Quality Gates ਵਰਕਫ਼ਲੋ ਹਰੇਕ ਇੱਕ ਸਥਿਰ ਫ਼ੈਸਲਾ ਜਾਰੀ ਕਰਦੇ ਹਨ: `Gate / CI` ਅਤੇ
`Gate / Quality`। ਉਨ੍ਹਾਂ ਦੀ ਵਰਜਨਬੱਧ ਪ੍ਰਵਾਨਗੀ ਨੀਤੀ ਹਰ ਅੱਪਸਟ੍ਰੀਮ ਜੌਬ ਨੂੰ
ਲੋੜੀਂਦੀ ਜਾਂ ਸਲਾਹਕਾਰੀ ਵਜੋਂ ਸੂਚੀਬੱਧ ਕਰਦੀ ਹੈ। ਕੋਈ ਲਾਗੂ ਲੋੜੀਂਦੀ ਜੌਬ ਸਫਲ ਹੋਣੀ ਚਾਹੀਦੀ ਹੈ:
ਗੁੰਮ, ਰੱਦ, ਛੱਡੇ ਗਏ, ਬਕਾਇਆ ਅਤੇ ਅਣਜਾਣ ਨਤੀਜੇ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦੇ। ਇੱਕ ਵੈਧ
ਸਿਰਫ਼-ਡੌਕਸ ਜਾਂ ਸਿਰਫ਼-ਕੈਟਾਲੌਗ ਵਰਗੀਕਰਨ ਕੋਡ ਲੇਨ ਨੂੰ ਗੈਰ-ਲਾਗੂ ਬਣਾ ਸਕਦਾ ਹੈ;
ਇੱਕ ਡਰਾਫਟ PR ਸਵੀਕਾਰਿਆ ਹੋਇਆ ਉਮੀਦਵਾਰ ਨਹੀਂ ਹੈ। ਇੱਕ `hotfix` ਲੇਬਲ ਸਬੂਤ ਦੀ ਲੋੜ ਖਤਮ ਨਹੀਂ ਕਰਦਾ।

ਦੋਵੇਂ ਵਰਕਫ਼ਲੋ main/release ਬ੍ਰਾਂਚਾਂ ਵਿੱਚ ਆਉਣ ਵਾਲੇ PRs, `main` ਵੱਲ ਪੁਸ਼ਾਂ, ਮੈਨੂਅਲ ਡਿਸਪੈਚ
ਅਤੇ merge-group ਇਵੈਂਟਾਂ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। Push, dispatch ਅਤੇ merge-group ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦੇ ਹਨ। Pushes to
`release/**` ਇਨ੍ਹਾਂ ਨੂੰ ਸ਼ੁਰੂ ਨਹੀਂ ਕਰਦੇ (2026-10-18): ਹਰ ਤਬਦੀਲੀ ਪਹਿਲਾਂ ਹੀ ਆਪਣੇ PR ਉੱਤੇ ਮੈਟ੍ਰਿਕਸ ਚਲਾ ਚੁੱਕੀ ਹੁੰਦੀ ਹੈ
ਅਤੇ ਮਿਲਾਇਆ ਗਿਆ ਸੰਯੋਜਨ Release-Green ਦੀ ਜੌਬ ਹੈ (`docs/ops/RUNNER_BOX.md` → ਹੋਸਟ ਕੀਤੀ ਲੇਨ)। Forks
ਅਤੇ merge groups ਉਹਨਾਂ ਜੌਬਾਂ ਲਈ ਹੋਸਟ ਕੀਤੇ runners ਵਰਤਦੇ ਹਨ ਜੋ ਨਹੀਂ ਤਾਂ self-hosted
runners ਚੁਣਦੀਆਂ; ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਯਥੇਸ਼ਟ ਹੋਸਟ ਕੀਤੀ ਸਮਰੱਥਾ ਦੀ ਪੁਸ਼ਟੀ ਲਾਜ਼ਮੀ ਹੈ।

ਹਰੇਕ JSON ਰਸੀਦ ਚੈੱਕ-ਆਉਟ ਕੀਤੇ SHA, ਵਰਕਫ਼ਲੋ ਰਨ ਅਤੇ ਕੋਸ਼ਿਸ਼ ਦੀ ਪਛਾਣ ਕਰਦੀ ਹੈ।
CLI, checkout/event SHA ਦੇ ਬੇਮੇਲ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਵਰਕਫ਼ਲੋ ਟੈਸਟ ਨੀਤੀ ਮੈਂਬਰਸ਼ਿਪ ਨੂੰ
ਫ਼ੈਸਲਾ ਜੌਬ ਦੀ `needs` ਸੂਚੀ ਨਾਲ ਬੰਨ੍ਹਦੇ ਹਨ, ਤਾਂ ਜੋ ਕੋਈ ਨਵੀਂ ਜਾਂ ਹਟਾਈ ਗਈ ਲੇਨ ਚੁੱਪਚਾਪ ਗਾਇਬ ਨਾ ਹੋ ਸਕੇ।
ਰਸੀਦਾਂ ਆਪਣੇ ਵਰਕਫ਼ਲੋ ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ, ਪ੍ਰਕਾਸ਼ਨ, ਡਿਪਲੌਇਮੈਂਟ ਜਾਂ ਕਿਸੇ ਮੌਜੂਦਾ
ਸਲਾਹਕਾਰੀ ਸਕੈਨਰ ਦੇ ਅੰਦਰੂਨੀ ਹਿੱਸਿਆਂ ਨੂੰ ਨਹੀਂ। ਬ੍ਰਾਂਚ ਨਿਯਮਾਂ ਵਿੱਚ ਦੋਵੇਂ ਚੈੱਕ ਨਾਂ ਸਰਗਰਮ ਕਰਨਾ
ਇੱਕ ਵੱਖਰੀ ਪ੍ਰਸ਼ਾਸਕੀ ਤਬਦੀਲੀ ਹੈ; ਇਹ ਜੌਬਾਂ ਜੋੜਨਾ ਆਪਣੇ ਆਪ ਕਿਸੇ ਬ੍ਰਾਂਚ ਨੂੰ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਕਰਦਾ।

### ਸਟੈਟਿਕ ਸਕੈਨ ਸੂਚੀ

ਵਰਜਨਬੱਧ npm-alias ਸੂਚੀ ਅਤੇ ਸਟੈਟਿਕ-ਸਕੈਨ ਮੈਂਬਰਸ਼ਿਪ
`config/quality/gate-manifest.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਸਕ੍ਰਿਪਟ ਨਾਂ ਅਤੇ ਸਟੀਕ ਕਮਾਂਡਾਂ ਨੂੰ
`package.json` ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕਰਨ ਲਈ `npm run check:gate-manifest` ਚਲਾਓ; ਜੋੜ, ਹਟਾਉਣ ਅਤੇ
ਕਮਾਂਡ ਡ੍ਰਿਫਟ ਲੋਕਲ ਹੁੱਕ ਅਤੇ CI ਵਿੱਚ ਤਬਦੀਲੀ-ਵਰਗੀਕਰਨ ਜੌਬਾਂ ਦੋਵਾਂ ਨੂੰ ਅਸਫਲ ਕਰ ਦਿੰਦੇ ਹਨ।
ਕੋਈ alias ਇੱਕ ਵਰਕਫ਼ਲੋ ਜੌਬ, ਮੈਟ੍ਰਿਕਸ ਇੰਸਟੈਂਸ ਜਾਂ ਟੈਸਟ ਕੇਸ ਨਹੀਂ ਹੁੰਦਾ: ਇਨ੍ਹਾਂ ਗਿਣਤੀਆਂ ਨੂੰ
ਆਪਸ ਵਿੱਚ ਬਦਲਣਯੋਗ ਵਜੋਂ ਪੇਸ਼ ਨਹੀਂ ਕੀਤਾ ਜਾਣਾ ਚਾਹੀਦਾ।

ਚੁਣੇ ਹੋਏ aliases ਨੂੰ ਚਲਾਏ ਬਿਨਾਂ ਵੇਖਣ ਲਈ `npm run quality:scan -- --list` ਜਾਂ
`npm run quality:scan:fast -- --list` ਵਰਤੋ। Runner npm ਐਂਟਰੀਪੌਇੰਟ ਨੂੰ ਇਨਵੋਕ ਕਰਦਾ ਹੈ,
ਇਸ ਲਈ ਇਸ ਦਾ ਰਨਟਾਈਮ (ਜਿੱਥੇ ਸੰਰਚਿਤ ਹੋਵੇ, Bun ਸਮੇਤ) ਬਰਕਰਾਰ ਰਹਿੰਦਾ ਹੈ।
ਮੈਨੀਫੈਸਟ ਉਹਨਾਂ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਤੋਂ ਬਾਹਰਲੇ aliases ਨੂੰ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਇਨਵੋਕ ਕੀਤੇ ਵਜੋਂ ਦਰਜ ਕਰਦਾ ਹੈ, ਅਤੇ
ਰੀਡ-ਓਨਲੀ ਸਕੈਨ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵਿੱਚ ਰੱਖ-ਰਖਾਅ ਕਮਾਂਡਾਂ ਦੀ ਮਨਾਹੀ ਹੈ।

ਇਹ ਪ੍ਰੋਫ਼ਾਈਲ ਸਿਰਫ਼ ਸਟੈਟਿਕ ਸਕੈਨ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। ਇਹ ਪ੍ਰੋਡਕਟ ਟੈਸਟਾਂ,
ਕਵਰੇਜ, ਪੈਕੇਜਿੰਗ, ਬਾਹਰੀ ਚੈੱਕਾਂ ਜਾਂ ਕਿਸੇ ਉਮੀਦਵਾਰ ਦੀ ਪੂਰੀ ਰਿਲੀਜ਼ ਸਵੀਕ੍ਰਿਤੀ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਨਹੀਂ ਕਰਦੇ।
ਵਰਕਫ਼ਲੋ ਪ੍ਰਵਾਨਗੀ ਲਿੰਕ ਕੀਤੇ `config/quality/admission-policy.json` ਅਤੇ
`scripts/quality/admission-verdict.mjs` ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ। Release-observer ਪ੍ਰੋਫ਼ਾਈਲ ਵੱਖਰੇ ਰਹਿੰਦੇ ਹਨ;
ਉਨ੍ਹਾਂ ਦੇ ਲਾਗੂ ਚੈੱਕਾਂ ਅਤੇ ਰਸੀਦਾਂ ਦੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਜਾਂਚ ਕਰੋ। ਹੇਠਾਂ ਦਿੱਤੀ ਗੱਥਾਤਮਕ
ਸੂਚੀ ਇੱਕ ਹਵਾਲਾ ਹੈ, ਇਸ ਗੱਲ ਦਾ ਸਬੂਤ ਨਹੀਂ ਕਿ ਕੋਈ ਗੇਟ ਅਸਲ ਵਿੱਚ ਚੱਲਿਆ ਸੀ।

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (ਨੀਤੀ ਗੇਟ) ਅਤੇ `scripts/quality/` (ਰੈਚਿਟ ਇੰਜਣ) ਅਧੀਨ ਮੌਜੂਦ ਹਨ।
CI ਲਈ ਸੱਚਾਈ ਦਾ ਸਰੋਤ `.github/workflows/ci.yml` ਹੈ।

### Release PR ਤੇਜ਼-ਮਾਰਗ (`quality.yml`)

`.github/workflows/quality.yml`, main/release PRs, `main` ਵੱਲ ਪੁਸ਼ਾਂ,
dispatch ਅਤੇ merge groups ਉੱਤੇ CI ਦੀ ਪੂਰਤੀ ਕਰਦਾ ਹੈ। PRs ਪਾਥ-ਫ਼ਿਲਟਰ ਕੀਤੇ ਤੇਜ਼ ਚੈੱਕ ਵਰਤਦੇ ਹਨ। ਸਥਾਈ ਤੌਰ 'ਤੇ
ਅਯੋਗ ਕੀਤੀ ਡੁਪਲੀਕੇਟ build ਹਟਾ ਦਿੱਤੀ ਗਈ ਸੀ; ਅਸਲੀ build/package/boot ਚੈੱਕ CI ਵਿੱਚ ਹੀ ਰਹਿੰਦੇ ਹਨ।

#### ਭੁੱਲੇ ਹੋਏ sibling tests ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests` ਟੈਸਟ-ਪ੍ਰਭਾਵ ਮੈਪ ਦੇ ਪਿੱਛੇ ਵਰਤੇ ਜਾਣ ਵਾਲੇ ਇੰਪੋਰਟ ਰਿਜ਼ਾਲਵਰ ਨੂੰ ਮੁੜ ਵਰਤਦਾ ਹੈ।
ਹਰੇਕ ਬਦਲੇ ਹੋਏ ਪ੍ਰੋਡਕਸ਼ਨ ਮੋਡੀਊਲ ਲਈ, ਜਦੋਂ ਉਮੀਦਵਾਰ ਟੈਸਟ
ਪੁੱਲ ਰਿਕਵੇਸਟ ਦੇ ਡਿਫ਼ ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਤਾਂ ਇਹ ਨਿਰਧਾਰਤ
`changed module/symbol -> static consumer -> candidate sibling test` ਲੜੀਆਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ। ਕਿਸੇ ਵੀ ਬਲਾਕਿੰਗ ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਲਈ Markdown ਸਾਰਾਂਸ਼ ਅਤੇ JSON ਨਤੀਜੇ ਨੂੰ
`forgotten-sibling-tests` ਵਰਕਫ਼ਲੋ ਆਰਟੀਫੈਕਟ ਵਜੋਂ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ।

ਬੈਰਲ ਰੀ-ਐਕਸਪੋਰਟ ਅਤੇ ਡਾਇਨਾਮਿਕ ਇੰਪੋਰਟ ਸਿਰਫ਼ ਰਿਜ਼ੋਲਿਊਸ਼ਨ ਡਾਇਗਨੋਸਟਿਕ ਹਨ; ਇਹ ਕਦੇ ਵੀ
ਬਲਾਕਿੰਗ ਖੋਜ ਨਹੀਂ ਬਣਾਉਂਦੇ। ਸਮੀਖਿਆ ਕੀਤੇ ਅਪਵਾਦ
`config/quality/forgotten-sibling-allowlist.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਹਰੇਕ ਐਂਟਰੀ ਵਿੱਚ ਕੰਜ਼ਿਊਮਰ ਅਤੇ ਉਮੀਦਵਾਰ
ਟੈਸਟ ਦਾ ਨਾਮ ਹੋਣਾ, ਇੱਕ ਖਾਸ ਤਰਕ ਦੇਣਾ, ਅਤੇ GitHub ਇਸ਼ੂ ਜਾਂ ਪੁੱਲ ਰਿਕਵੇਸਟ ਨਾਲ ਲਿੰਕ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ। ਗਲਤ ਢੰਗ ਨਾਲ ਬਣਾਈਆਂ ਐਂਟਰੀਆਂ
ਫੇਲ-ਕਲੋਜ਼ਡ ਹੁੰਦੀਆਂ ਹਨ। ਅਪਵਾਦ ਕਿਸੇ ਮਿਟਾਏ ਗਏ ਉਮੀਦਵਾਰ ਟੈਸਟ ਜਾਂ `.skip`/`.todo` ਜੋੜਨ ਵਾਲੇ ਡਿਫ਼ ਨੂੰ ਦਬਾ ਨਹੀਂ ਸਕਦੇ;
ਅਸਰਸ਼ਨ ਨੂੰ ਕਮਜ਼ੋਰ ਕਰਨਾ ਅਤੇ ਹੋਰ ਮਾਸਕਿੰਗ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਬਲਾਕ ਕਰਨ ਵਾਲੇ
`check:test-masking` ਗੇਟ ਦੇ ਅਧੀਨ ਰਹਿੰਦੇ ਹਨ।

#### `check-ui-value-drift` — ਪੁਰਾਣੇ-ਅਨੁਵਾਦ ਦਾ ਗੇਟ

ਇਹ ਉਸ ਇੱਕ i18n ਰਿਗ੍ਰੈਸ਼ਨ ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ ਹੋਰ ਗੇਟ ਸੰਰਚਨਾਤਮਕ ਤੌਰ 'ਤੇ ਨਹੀਂ ਦੇਖ ਸਕਦੇ: ਜਦੋਂ ਕਿਸੇ ਅੰਗਰੇਜ਼ੀ value
ਨੂੰ ਮੁੜ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ _ਪਿਛਲੀ_ ਅੰਗਰੇਜ਼ੀ ਤੋਂ ਬਣਾਏ ਗਏ ਅਨੁਵਾਦ ਪਿੱਛੇ ਹੀ ਰਹਿ ਜਾਂਦੇ ਹਨ, ਇਸ ਲਈ
ਗੈਰ-ਅੰਗਰੇਜ਼ੀ ਵਰਤੋਂਕਾਰ ਭਰੋਸੇ ਨਾਲ ਲਿਖੀ ਹੋਈ, ਪਰ ਹੁਣ ਗਲਤ, ਸਮੱਗਰੀ ਪੜ੍ਹਦੇ ਰਹਿੰਦੇ ਹਨ।

ਇਹ ਸਮੱਸਿਆ ਅਸਲ ਰਿਲੀਜ਼ ਵਿੱਚ ਆਈ ਸੀ। ਜਦੋਂ Antigravity
login helper ਸ਼ਾਮਲ ਕੀਤਾ ਗਿਆ (#5203), ਤਾਂ `oauthModal.googleOAuthWarning` ਨੂੰ ਮੁੜ ਲਿਖਿਆ ਗਿਆ; **43 ਵਿੱਚੋਂ 39 locales** ਵਿੱਚ ਅਜੇ ਵੀ ਆਪਰੇਟਰਾਂ ਨੂੰ "ਪੂਰਾ URL ਕਾਪੀ ਕਰਕੇ ਹੇਠਾਂ ਪੇਸਟ ਕਰਨ" ਲਈ ਕਹਿਣ ਵਾਲਾ ਟੈਕਸਟ ਮੌਜੂਦ ਰਿਹਾ — ਇੱਕ ਅਜਿਹਾ ਪ੍ਰਵਾਹ ਜੋ ਉਸ ਪ੍ਰਦਾਤਾ ਲਈ ਪੂਰਾ ਨਹੀਂ ਹੋ ਸਕਦਾ। ਇਹ
#8463 ਤੱਕ ਧਿਆਨ ਵਿੱਚ ਨਹੀਂ ਆਇਆ ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹ keys ਵਾਪਸ ਭਰਦਾ ਹੈ ਜੋ **ਗੈਰਹਾਜ਼ਰ** ਹਨ, ਉਹਨਾਂ ਨੂੰ ਕਦੇ ਨਹੀਂ ਜੋ **ਪੁਰਾਣੀਆਂ** ਹਨ;
- `check-ui-keys-coverage` key ਦੀ _ਮੌਜੂਦਗੀ_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵੀ ਕਵਰ ਕੀਤਾ ਹੋਇਆ ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ਦਸਤਾਵੇਜ਼ੀ ਪ੍ਰਤੀਆਂ ਨੂੰ ਟਰੈਕ ਕਰਦਾ ਹੈ —
  ਇਹ `src/i18n/messages/*.json` ਨੂੰ ਕਦੇ ਨਹੀਂ ਪੜ੍ਹਦਾ। 2026-09 ਮੁੜ-ਸਿੰਕ ਤੋਂ ਬਾਅਦ ਜੌਬ `docs-sync-strict` ਵਿੱਚ ਬਲਾਕਿੰਗ: ਕਿਸੇ ਮੁੱਖ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਸੰਪਾਦਿਤ ਕਰੋ → `npm run i18n:run -- --files=<doc>` (ਸੈਕਸ਼ਨ-ਪੱਧਰੀ, ਘੱਟ ਖਰਚ ਵਾਲਾ)।

**ਡਿਫ਼-ਸਚੇਤ, ਬੇਸਲਾਈਨ-ਅਧਾਰਿਤ ਨਹੀਂ।** ਇਹ ਮਰਜ ਬੇਸ ਉੱਤੇ ਮੌਜੂਦ `en.json` ਦੀ ਵਰਕਿੰਗ ਟ੍ਰੀ ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ; ਹਰ ਉਸ ਕੁੰਜੀ ਲਈ ਜਿਸਦਾ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਬਦਲਿਆ ਹੈ, ਜੇ ਕਿਸੇ ਲੋਕੇਲ ਵਿੱਚ ਅਜੇ ਵੀ ਨਾ-ਬਦਲਿਆ ਅਨੁਵਾਦ ਮੌਜੂਦ ਹੈ, ਤਾਂ ਉਹ ਪੁਰਾਣਾ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ। ਇਹ ਜਾਣ-ਬੁੱਝ ਕੇ **ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਕਰਜ਼ੇ ਨੂੰ ਜਮਾਂ ਰੱਖਦਾ ਹੈ** — ਕੋਈ ਡਿਫ਼ ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਲੰਮੇ ਸਮੇਂ ਤੋਂ ਮੌਜੂਦ ਅਨੁਵਾਦ ਕਿਸ ਪੁਰਾਣੇ ਅੰਗਰੇਜ਼ੀ ਪਾਠ ਤੋਂ ਆਇਆ ਸੀ, ਇਸ ਲਈ ਗੇਟ ਸਿਰਫ਼ ਮੌਜੂਦਾ ਤਬਦੀਲੀ ਦੁਆਰਾ ਛੂਹੀਆਂ ਚੀਜ਼ਾਂ ਦਾ ਮੁਲਾਂਕਣ ਕਰਦਾ ਹੈ। ਵਿਕਲਪ (ਹਰ ਕੁੰਜੀ ਲਈ ਹੈਸ਼ ਬੇਸਲਾਈਨ) ਲਈ ਲਗਭਗ 600 KB ਦੀ ਜਨਰੇਟ ਕੀਤੀ ਫ਼ਾਈਲ ਦੀ ਲੋੜ ਪਵੇਗੀ, ਜੋ ਸਭ ਤੋਂ ਵੱਡੀ ਮੌਜੂਦਾ ਬੇਸਲਾਈਨ ਤੋਂ 3× ਵੱਡੀ ਹੋਵੇਗੀ ਅਤੇ ਹਰ i18n PR ਉੱਤੇ ਬੇਲੋੜੀਆਂ ਤਬਦੀਲੀਆਂ ਪੈਦਾ ਕਰੇਗੀ।

ਇਸਨੂੰ ਪੂਰਾ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ ਅਨੁਵਾਦਾਂ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ, ਜਾਂ
2. ਉਨ੍ਹਾਂ ਨੂੰ `__MISSING__:<new english>` ਉੱਤੇ ਸੈੱਟ ਕਰੋ — ਫਿਰ ਰਨਟਾਈਮ ਸਹੀ ਕੀਤਾ ਅੰਗਰੇਜ਼ੀ ਪਾਠ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਅਤੇ ਕੁੰਜੀ ਅਨੁਵਾਦ ਲਈ ਕਤਾਰ ਵਿੱਚ ਲੱਗ ਜਾਂਦੀ ਹੈ।

ਜੇ ਸਤਰ ਦਾ **ਅਰਥ** ਬਦਲਿਆ ਹੈ, ਤਾਂ **ਕੁੰਜੀ ਦਾ ਨਾਮ ਬਦਲਣ** ਨੂੰ ਤਰਜੀਹ ਦਿਓ: ਕੋਈ ਨਵੀਂ ਕੁੰਜੀ ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵਿਰਾਸਤ ਵਿੱਚ ਨਹੀਂ ਲੈ ਸਕਦੀ। #8463 ਵਿੱਚ ਇਹੀ ਪੈਟਰਨ ਵਰਤਿਆ ਗਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ਜਦੋਂ ਬੇਸ ਕੈਟਾਲੌਗ ਪੜ੍ਹਿਆ ਨਹੀਂ ਜਾ ਸਕਦਾ (ਬੇਸ ਰੈਫ਼ ਤੋਂ ਬਿਨਾਂ ਸ਼ੈਲੋ ਕਲੋਨ), ਤਾਂ `SKIP reason=base-unresolved` ਦੇ ਨਾਲ 0 ਐਗਜ਼ਿਟ ਕਰਦਾ ਹੈ, ਜੋ `check-openapi-breaking` ਦੇ ਵਿਹਾਰ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੈ।

  ਕਿਸੇ ਬੇਕਸੂਰ PR ਨੂੰ ਲਾਲ ਨਹੀਂ ਕਰਦੀ; ਰਿਲੀਜ਼ ਮਿਲਾਣ ਵੇਲੇ ਡ੍ਰਿਫ਼ਟ ਨੂੰ ਮੁੜ ਫ੍ਰੀਜ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਹੈੱਡਰੂਮ ਜੌਬ ਦੁਆਰਾ ਨਿਗਰਾਨੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

ਪੜ੍ਹਦਾ ਹੈ, ਅਤੇ ਕਿਸੇ ਫ਼ਾਈਲ ਨੂੰ ਸਿਰਫ਼ ਉਦੋਂ ਫੇਲ ਕਰਦਾ ਹੈ ਜਦੋਂ ਉਹ ਆਪਣੀ ਬੇਸਲਾਈਨ ਸੀਮਾ

`workflow_dispatch` runs, release-green sweep ਅਤੇ nightly headroom job ਕੋਲ ਕੋਈ PR base ਨਹੀਂ ਹੁੰਦਾ

ਇਸ ਫ਼ਾਈਲ ਨੂੰ ਉਸ ਤਬਦੀਲੀ ਦੇ ਨਾਲ ਹੀ ਕਮਿਟ ਕਰੋ ਜਿਸ ਨੇ ਮੈਟ੍ਰਿਕ ਵਿੱਚ ਸੁਧਾਰ ਕੀਤਾ ਹੈ। ਬੇਸਲਾਈਨ
ਅੱਪਡੇਟ ਕੀਤੇ ਬਿਨਾਂ ਕਿਸੇ ਮੈਟ੍ਰਿਕ ਨੂੰ ਸੁਧਾਰਨ ਵਾਲੀ PR ਨੂੰ `--require-tighten` ਪਕੜ ਲਵੇਗਾ
(ਪੜਾਅ 6A.5, ਲਾਗੂਕਰਨ ਬਕਾਇਆ ਹੈ)।

### CodeQL ਰੈਚਟ: ਰਿਫ੍ਰੈਸ਼ ਦੀ ਆਵਿਰਤੀ ਅਤੇ ਮੈਨੁਅਲ ਟ੍ਰਿਗਰ

`check:codeql-ratchet` **ਰਿਪੋਜ਼ਟਰੀ ਦੀ ਸਥਿਤੀ ਪੜ੍ਹਦਾ ਹੈ, ਜੋ ਇੱਕ ਸਮਾਂ-ਸੂਚੀ ਅਨੁਸਾਰ ਰਿਫ੍ਰੈਸ਼ ਹੁੰਦੀ ਹੈ — ਹਰ PR ਲਈ ਨਹੀਂ।**

ਲਈ ਕੀਤਾ ਜਾਣ ਵਾਲਾ ਵਿਸ਼ਲੇਸ਼ਣ। ਨਤੀਜਾ: ਅਲਰਟ ਠੀਕ ਕਰਨ ਵਾਲੀ PR ਦੇ ਮਰਜ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਰੈਚਟ
ਅਗਲਾ ਨਿਰਧਾਰਤ ਸਕੈਨ ਚੱਲਣ ਤੱਕ ਪੁਰਾਣੀ, ਵੱਧ ਗਿਣਤੀ ਹੀ ਪੜ੍ਹਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਸਕੈਨ ਦੇ
ਅੱਪਡੇਟ ਹੋਣ ਤੱਕ ਇਹ ਹਰ ਖੁੱਲ੍ਹੀ PR, ਫਿਕਸ ਕਰਨ ਵਾਲੀ PR ਦੀਆਂ ਆਪਣੀਆਂ ਅਗਲੀਆਂ ਤਬਦੀਲੀਆਂ ਸਮੇਤ,
'ਤੇ ਰਿਗ੍ਰੈਸ਼ਨ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ।

**ਮੈਨੁਅਲ ਰਿਫ੍ਰੈਸ਼**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ਵਿਸ਼ਲੇਸ਼ਣ ਨੂੰ ਮੁੜ

ਦੇ ਅੰਦਰ ਬੈਂਕ ਕੀਤੀ ਘਟਾਵ ਠੀਕ ਹੈ), ਜਦਕਿ ਪ੍ਰਤੀ-ਮਰਜ ਰਨ, ਮਰਜ ਮੁਹਿੰਮਾਂ ਦੌਰਾਨ PR ਸ਼ਾਖਾ ਨੂੰ ਵਾਰ-ਵਾਰ
ਮੁੜ ਬਣਾਉਂਦਾ ਅਤੇ ਹਰ ਵਾਰ ਪੂਰੇ ESLint ਵਾਕ ਦੀ ਲਾਗਤ ਭਰਦਾ। ਪਛਾਣ `push` (`release-green`) 'ਤੇ ਹੀ ਰਹਿੰਦੀ ਹੈ;

### ਸੁਰੱਖਿਆ ਤਸਦੀਕਕਾਰ

ਜੌਬ ਬਿਨਾਂ ਨਿਗਰਾਨੀ ਦੇ ਬੇਸਲਾਈਨਾਂ ਵਿੱਚ ਲਿਖਦੀ ਹੈ, ਇਸ ਲਈ `verify-ratchet-bank.mjs` ਹੀ ਇਸਨੂੰ
ਸਵੀਕਾਰਯੋਗ ਬਣਾਉਂਦਾ ਹੈ। ਇਹ `--update` ਤੋਂ ਬਾਅਦ ਵਾਲੇ ਟ੍ਰੀ ਦੀ `HEAD` ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ ਅਤੇ **ਕੋਈ ਵੀ ਕਮਿਟ
ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਜੌਬ ਨੂੰ ਰੋਕ ਦਿੰਦਾ ਹੈ** — ਕੋਈ PR ਨਹੀਂ ਖੋਲ੍ਹਦਾ — ਜਦੋਂ ਤੱਕ ਹਰ ਤਬਦੀਲੀ ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਇੱਕ ਨਾ ਹੋਵੇ:

- ਇੱਕ `frozen` / `testFrozen` ਅੰਕੀ ਐਂਟਰੀ **ਘਟਾਈ** ਜਾਂ **ਹਟਾਈ** ਗਈ ਹੋਵੇ
- `complexity-baseline.json` → `count` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ

ਹੋਰ ਕੁਝ ਵੀ ਅਸਫਲ ਹੁੰਦਾ ਹੈ: ਕੋਈ ਸੰਖਿਆ ਵਧਾਉਣਾ, ਐਂਟਰੀ ਜੋੜਨਾ, `cap`/`testCap` ਬਦਲਣਾ, ਜਾਂ
ਕਿਸੇ `_rebaseline_*` ਨੋਟ ਨੂੰ ਮਿਟਾਉਣਾ/ਮੁੜ ਲਿਖਣਾ (ਉਹ ਨੋਟ ਇਸ ਗੱਲ ਦਾ ਆਡਿਟ ਟ੍ਰੇਲ ਹਨ ਕਿ ਹਰੇਕ
ਉੱਪਰੀ ਸੀਮਾ ਕਿਉਂ ਮੌਜੂਦ ਹੈ ਅਤੇ ਉਹ ਫ਼ਾਈਲ ਐਂਟਰੀਆਂ ਵਾਲੇ ਉਸੇ `frozen` ਆਬਜੈਕਟ ਦੇ ਅੰਦਰ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ)।
ਜੋ ਬੌਟ ਸੀਮਾ ਵਧਾ ਸਕੇ, ਉਹ ਮੌਜੂਦਾ ਸਥਿਤੀ ਨਾਲੋਂ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਹੋਰ ਮਾੜਾ ਹੋਵੇਗਾ। ਰਿਗ੍ਰੈਸ਼ਨ
ਗਾਰਡ: `tests/unit/verify-ratchet-bank.test.ts`.

ਜੌਬ ਕਦੇ ਵੀ `release/*` ਵੱਲ push ਨਹੀਂ ਕਰਦੀ — ਇੱਕ ਮਨੁੱਖ PR ਨੂੰ ਮਰਜ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਕੋਈ ਖਰਾਬ ਮਾਪ
ਬਿਨਾਂ ਸਮੀਖਿਆ ਦੇ ਲਾਗੂ ਨਹੀਂ ਹੋ ਸਕਦਾ।

## ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਨੀਤੀ

ਹਰ ਉਹ ਗੇਟ ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਉਲੰਘਣਾਵਾਂ ਕਾਰਨ ਅਸਫਲ ਨਹੀਂ ਹੋ ਸਕਦਾ, ਇੱਕ ਸਥਿਰ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਰਤਦਾ ਹੈ
(ਉਦਾਹਰਨ ਲਈ, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ਨੀਤੀ ਇਹ ਹੈ:

**ਮੂਲ ਕਾਰਨ ਠੀਕ ਕਰੋ; ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੋ ਜਦੋਂ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੋਵੇ ਅਤੇ
ਉਸੇ PR ਵਿੱਚ ਠੀਕ ਨਾ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੋਵੇ।**

ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਿੱਚ ਕੋਈ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰਦੇ ਸਮੇਂ:

1. ਕਾਰਨ ਦੱਸਦੀ ਇੱਕ ਟਿੱਪਣੀ ਸ਼ਾਮਲ ਕਰੋ।
2. ਟ੍ਰੈਕਿੰਗ ਮੁੱਦੇ ਦਾ ਹਵਾਲਾ ਦਿਓ (ਉਦਾਹਰਨ ਲਈ, `// #3498 — ਪੜਾਅ 2 ਦੀ ਵਿਸ਼ੇਸ਼ਤਾ, ਹਾਲੇ ਲਾਗੂ ਨਹੀਂ ਕੀਤੀ ਗਈ`)।
3. ਉਲੰਘਣਾ ਠੀਕ ਕਰਨ ਵਾਲੇ ਉਸੇ PR ਵਿੱਚ ਐਂਟਰੀ ਹਟਾਓ — ਇੱਕ ਪੁਰਾਣੀ ਐਂਟਰੀ ਜੋ ਹੁਣ
   ਕਿਸੇ ਸਰਗਰਮ ਉਲੰਘਣਾ ਨੂੰ ਦਬਾਉਂਦੀ ਨਹੀਂ ਹੈ, ਆਪਣੇ ਆਪ ਵਿੱਚ ਇੱਕ ਖ਼ਰਾਬੀ ਹੈ (6A.3 ਪੁਰਾਣੀ-ਲਾਗੂਕਰਨ ਜਾਂਚ,

## ਨਵਾਂ ਗੇਟ ਸ਼ਾਮਲ ਕਰਨਾ

1. `scripts/check/check-<name>.mjs` (ਜਾਂ `.ts`) ਬਣਾਓ। ਨੀਤੀ ਗੇਟ 0/1 ਨਾਲ ਬੰਦ ਹੁੰਦੇ ਹਨ।

3. ਇਸਨੂੰ `.github/workflows/ci.yml` ਵਿੱਚ ਢੁਕਵੀਂ ਜੌਬ ਹੇਠ ਜੋੜੋ
   (ਨੀਤੀ → `lint` ਜਾਂ `docs-sync-strict`; ਰੈਚਿਟ → `quality-gate`)।
4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

ਹਰ ਉਮੀਦਵਾਰ ਨੂੰ 2026-06-17 ਨੂੰ ਲਾਈਵ ਗੇਟ ਸਥਿਤੀ ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਗਿਆ ਸੀ (ਭਰੋਸਾ ਕਰੋ, ਪਰ ਤਸਦੀਕ ਵੀ ਕਰੋ);

- **`check:docs-sync` ਦੋ ਵਾਰ ਚੱਲਦਾ ਹੈ** — `lint` ਜੌਬ ਵਿੱਚ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਅਤੇ ਮੁੜ `check:docs-all` (`docs-sync-strict`) ਅਤੇ husky pre-commit ਹੁੱਕ ਦੇ ਅੰਦਰ। ✅ **ਪੂਰਾ ਹੋਇਆ** — ਵੱਖਰਾ `lint` ਇਨਵੋਕੇਸ਼ਨ ਹਟਾਇਆ ਗਿਆ।
- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼-ਸੁਥਰਾ ਮਰਜ ਨਹੀਂ ਹੈ।** `audit:deps` ਕਿਸੇ ਵੀ high/critical CVE 'ਤੇ ਹਾਰਡ-ਫੇਲ ਹੁੰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਬੇਸਲਾਈਨ (ਇਸ ਵੇਲੇ 1 MODERATE) ਦੇ ਮੁਕਾਬਲੇ ਕਿਸੇ _ਰਿਗ੍ਰੈਸ਼ਨ_ 'ਤੇ ਫੇਲ ਹੁੰਦਾ ਹੈ। ਅਰਥ-ਵਿਹਾਰ ਵੱਖਰੇ ਹਨ — `audit:deps` ਨੂੰ ਹਟਾਉਣ ਨਾਲ ਪੂਰਨ high/critical ਗੇਟ ਖਤਮ ਹੋ ਜਾਵੇਗਾ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਚੱਕਰ ਖੋਜ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (#15159 G-01/G-02)। ਇੱਥੇ ਪੁਰਾਣੇ ਟੈਕਸਟ ਨੇ `check:cycles` ਨੂੰ "ਹਰਾ, ਸੰਭਾਲ ਕੇ ਚੁਣਿਆ" ਗੇਟ ਕਿਹਾ ਸੀ ਅਤੇ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖਣ ਨੂੰ ਇਸ ਆਧਾਰ 'ਤੇ ਜਾਇਜ਼ ਠਹਿਰਾਇਆ ਸੀ ਕਿ `check:circular-deps` (dpdm) ਨੇ 91 ਚੱਕਰ ਰਿਪੋਰਟ ਕੀਤੇ ਸਨ। ਉਹ ਹਰਾ ਦਰਜਾ ਇੱਕ **ਗਲਤ ਹਰਾ ਸੰਕੇਤ** ਸੀ: `check:cycles` ਨੇ 5 ਸਬਡਾਇਰੈਕਟਰੀਆਂ (450 ਫ਼ਾਈਲਾਂ) ਸਕੈਨ ਕੀਤੀਆਂ, ਸਿਰਫ਼ ਸਥਿਰ `import|export … from` ਨਾਲ ਮੇਲ ਕੀਤਾ, ਅਤੇ ਹਰੇਕ `@/` ਅਤੇ `@omniroute/open-sse/` ਸਪੈਸੀਫਾਇਰ ਨੂੰ ਛੱਡ ਦਿੱਤਾ, ਇਸ ਲਈ ਇਹ ਉਹ dynamic-import + alias ਚੱਕਰ ਨਹੀਂ ਦੇਖ ਸਕਿਆ ਜੋ ਰਿਪੋ ਵਿੱਚ ਹਾਵੀ ਸਨ। ਠੀਕ ਕੀਤਾ ਗਿਆ: ਗੇਟ ਹੁਣ `src` + `open-sse` (5023 ਫ਼ਾਈਲਾਂ) ਵਿੱਚੋਂ ਲੰਘਦਾ ਹੈ, TypeScript AST ਤੋਂ ਸਪੈਸੀਫਾਇਰ ਇਕੱਠੇ ਕਰਦਾ ਹੈ (ਇਸ ਲਈ `import("…")` ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ type-position `typeof import("…")` ਨਹੀਂ), ਅਤੇ tsconfig `paths` ਨੂੰ ਰਿਜ਼ੌਲਵ ਕਰਦਾ ਹੈ। ਇਹ 0 ਨਹੀਂ, ਸਗੋਂ **14** ਚੱਕਰ ਲੱਭਦਾ ਹੈ। ਕਿਉਂਕਿ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ 14 ਚੱਕਰਾਂ ਨੂੰ ਗੇਟ PR ਵਿੱਚ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, `check:cycles` ਹੁਣ ਇੱਕ **ਰੈਚਿਟ** ਹੈ (`--ratchet`, `quality-baseline.json` ਵਿੱਚ ਸੀਮਾ `metrics.cycles.value = 14`, `direction: down`) — ਇਹ ਕਿਸੇ ਵੀ _ਰਿਗ੍ਰੈਸ਼ਨ_ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ ਅਤੇ ਗਿਣਤੀ ਸਿਰਫ਼ ਘਟ ਸਕਦੀ ਹੈ। CI `npm run check:cycles:ratchet` ਚਲਾਉਂਦਾ ਹੈ। ਘਟਾਓ ਦਾ ਕੰਮ **A-01** ਦੇ ਨਾਲ ਚੱਲੇਗਾ। `check:circular-deps` (dpdm) ਵਿਆਪਕ ਦੂਜੀ ਰਾਏ ਵਜੋਂ ਸਲਾਹਕਾਰੀ ਰਹਿੰਦਾ ਹੈ।
- **ਜਟਿਲਤਾ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, `ruleId` ਮੁਤਾਬਕ ਗਿਣਤੀ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive ਬੇਸਲਾਈਨਾਂ ਸੁਤੰਤਰ ਰਹਿਣ; ਵੱਖਰੇ `check:complexity` / `check:cognitive-complexity` ਲੋਕਲ `--update` ਲਈ ਬਰਕਰਾਰ ਹਨ।

ਰੱਖਦੀਆਂ ਹਨ। ਹਰ ਭਾਸ਼ਾ ਲਈ ਇੱਕ ਪ੍ਰਤੀਸ਼ਤ ਇਹ ਗੱਲ ਪ੍ਰਗਟ ਨਹੀਂ ਕਰ ਸਕਦਾ ਕਿ "ਇਹ ਫੀਚਰ ਬਿਨਾਂ ਅਨੁਵਾਦ ਦੇ
ਜਾਰੀ ਕੀਤਾ ਗਿਆ" — ਇੱਕ ਪੂਰਾ ਫੀਚਰ ਕਿਸੇ ਨਵੇਂ locale ਵਿੱਚ ਬਿਨਾਂ ਕਿਸੇ ਟੈਕਸਟ ਦੇ ਸ਼ਾਮਲ ਹੋ ਸਕਦਾ ਹੈ ਅਤੇ
ਅੰਕੜੇ ਨੂੰ ਕਦੇ ਬਦਲਦਾ ਵੀ ਨਹੀਂ।

ਇਸ ਵਿੱਚ ਦਰਜ ਘਟਨਾ ਇਹ ਹੈ: Orchestration Canvas ਦੇ Phase 3 ਨੇ ਆਪਣੀਆਂ ਗਿਆਰਾਂ ਕੁੰਜੀਆਂ ਦਾ ਉਸ ਵੇਲੇ
ਮੌਜੂਦ 42 locales ਵਿੱਚ ਅਨੁਵਾਦ ਕੀਤਾ। ਕੁਝ ਘੰਟਿਆਂ ਬਾਅਦ EU-language ਬੈਚ (#13044) ਨੇ repo ਨੂੰ 51
locales ਤੱਕ ਪਹੁੰਚਾ ਦਿੱਤਾ, ਅਤੇ ਨੌਂ ਨਵੇਂ ਆਏ locales (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`,
`sr`) ਨੂੰ ਉਹ ਕੁੰਜੀਆਂ ਕਦੇ ਨਹੀਂ ਮਿਲੀਆਂ। `deepMergeFallback` ਕਿਸੇ ਗੈਰਹਾਜ਼ਰ ਕੁੰਜੀ ਦੀ ਥਾਂ ਅੰਗਰੇਜ਼ੀ
