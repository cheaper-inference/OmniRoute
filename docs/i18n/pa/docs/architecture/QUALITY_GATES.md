ਇਹ ਦਸਤਾਵੇਜ਼ OmniRoute ਵਿੱਚ ਸਾਰੇ CI ਗੁਣਵੱਤਾ ਗੇਟਾਂ ਲਈ ਪ੍ਰਮਾਣਿਕ ਹਵਾਲਾ ਹੈ।
ਇਹ ਹਰ ਗੇਟ ਦਾ ਵਰਣਨ ਕਰਦਾ ਹੈ, ਇਹ ਕੀ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਇਹ ਕਿਸ CI ਜੌਬ ਵਿੱਚ ਚੱਲਦਾ ਹੈ, ਕੀ ਇਹ
ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਇਨਵੈਂਟਰੀ ਅਤੇ ਐਗਜ਼ਿਕਿਊਸ਼ਨ ਪ੍ਰੋਫ਼ਾਈਲ

### ਉਮੀਦਵਾਰ ਦਾਖਲਾ

CI ਅਤੇ Quality Gates ਵਰਕਫ਼ਲੋ ਹਰ ਇੱਕ ਇੱਕ ਸਥਿਰ ਫ਼ੈਸਲਾ ਜਾਰੀ ਕਰਦੇ ਹਨ: `Gate / CI` ਅਤੇ
`Gate / Quality`। ਉਨ੍ਹਾਂ ਦੀ ਵਰਜਨਬੱਧ ਦਾਖਲਾ ਨੀਤੀ ਹਰ ਅੱਪਸਟ੍ਰੀਮ ਜੌਬ ਨੂੰ ਲਾਜ਼ਮੀ ਜਾਂ
ਸਲਾਹਕਾਰ ਵਜੋਂ ਦਰਜ ਕਰਦੀ ਹੈ। ਲਾਗੂ ਹੋਣ ਵਾਲੀ ਲਾਜ਼ਮੀ ਜੌਬ ਸਫ਼ਲ ਹੋਣੀ ਚਾਹੀਦੀ ਹੈ: ਗੁੰਮ,
ਰੱਦ, ਛੱਡੇ ਹੋਏ, ਬਕਾਇਆ ਅਤੇ ਅਣਜਾਣ ਨਤੀਜੇ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦੇ। ਵੈਧ
docs-only ਜਾਂ catalog-only ਵਰਗੀਕਰਨ ਕੋਡ ਲੇਨ ਨੂੰ ਅਣਲਾਗੂ ਬਣਾ ਸਕਦਾ ਹੈ;
ਡ੍ਰਾਫ਼ਟ PR ਸਵੀਕਾਰਿਆ ਉਮੀਦਵਾਰ ਨਹੀਂ ਹੁੰਦਾ। `hotfix` ਲੇਬਲ ਸਬੂਤ ਤੋਂ ਛੋਟ ਨਹੀਂ ਦਿੰਦਾ।

ਦੋਵੇਂ ਵਰਕਫ਼ਲੋ main/release ਬ੍ਰਾਂਚਾਂ ਵਿੱਚ PRs, `main` ਉੱਤੇ ਪੁਸ਼, ਮੈਨੁਅਲ ਡਿਸਪੈਚ
ਅਤੇ merge-group ਇਵੈਂਟ ਕਵਰ ਕਰਦੇ ਹਨ। ਪੁਸ਼, ਡਿਸਪੈਚ ਅਤੇ merge-group ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦੇ ਹਨ।
`release/**` ਉੱਤੇ ਪੁਸ਼ ਇਨ੍ਹਾਂ ਨੂੰ ਸ਼ੁਰੂ ਨਹੀਂ ਕਰਦੇ (2026-10-18): ਹਰ ਤਬਦੀਲੀ ਪਹਿਲਾਂ ਹੀ ਆਪਣੇ PR
ਉੱਤੇ ਮੈਟ੍ਰਿਕਸ ਚਲਾ ਚੁੱਕੀ ਹੁੰਦੀ ਹੈ ਅਤੇ ਮਰਜ ਕੀਤਾ ਸੰਯੋਗ Release-Green ਦਾ ਕੰਮ ਹੁੰਦਾ ਹੈ
(`docs/ops/RUNNER_BOX.md` → Hosted lane)। ਫ਼ੋਰਕ ਅਤੇ merge groups ਉਨ੍ਹਾਂ ਜੌਬਾਂ ਲਈ hosted
ਰੰਨਰ ਵਰਤਦੇ ਹਨ ਜੋ ਨਹੀਂ ਤਾਂ self-hosted ਰੰਨਰ ਚੁਣਦੀਆਂ; ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਕਾਫ਼ੀ hosted ਸਮਰੱਥਾ
ਦੀ ਪੁਸ਼ਟੀ ਕਰਨੀ ਲਾਜ਼ਮੀ ਹੈ।

ਇੱਕ ਆਮ PR ਤੇਜ਼ ਚੋਣ ਚਲਾਉਂਦਾ ਹੈ। ਦਾਖਲਾ ਨੀਤੀ ਦੀਆਂ `full-code` ਅਤੇ `full-code-e2e` ਲੇਨਾਂ
(E2E, ਇੰਟੀਗ੍ਰੇਸ਼ਨ, ਪੈਕੇਜ ਆਰਟੀਫੈਕਟ, Electron smoke, Bun SQLite, ecosystem
ਅਤੇ protocol clients) ਸਿਰਫ਼ Mergify queue ਡ੍ਰਾਫ਼ਟ ਜਾਂ ਪੂਰੇ ਰਨ ਉੱਤੇ ਚਲਦੀਆਂ ਹਨ:
`gh workflow run ci.yml --ref <branch>`।

ਹਰ JSON ਰਸੀਦ ਚੈਕ-ਆਊਟ ਕੀਤੇ SHA, ਵਰਕਫ਼ਲੋ ਰਨ ਅਤੇ ਕੋਸ਼ਿਸ਼ ਦੀ ਪਛਾਣ ਕਰਦੀ ਹੈ।
CLI ਚੈਕ-ਆਊਟ/ਇਵੈਂਟ SHA ਦੇ ਅਸੰਗਤ ਹੋਣ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਵਰਕਫ਼ਲੋ ਟੈਸਟ ਨੀਤੀ ਮੈਂਬਰਸ਼ਿਪ ਨੂੰ
ਵਰਡਿਕਟ ਜੌਬ ਦੀ `needs` ਸੂਚੀ ਨਾਲ ਬੰਨ੍ਹਦੇ ਹਨ ਤਾਂ ਜੋ ਨਵੀਂ ਜਾਂ ਹਟਾਈ ਗਈ ਲੇਨ ਚੁੱਪਚਾਪ
ਗਾਇਬ ਨਾ ਹੋ ਸਕੇ। ਰਸੀਦਾਂ ਆਪਣੇ ਵਰਕਫ਼ਲੋ ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ, ਪ੍ਰਕਾਸ਼ਨ, ਡਿਪਲੌਇਮੈਂਟ ਜਾਂ
ਮੌਜੂਦਾ ਸਲਾਹਕਾਰ ਸਕੈਨਰ ਦੇ ਅੰਦਰੂਨੀ ਹਿੱਸਿਆਂ ਨੂੰ ਨਹੀਂ। ਬ੍ਰਾਂਚ ਨਿਯਮਾਂ ਵਿੱਚ ਦੋਵੇਂ ਚੈਕ ਨਾਮ
ਸਰਗਰਮ ਕਰਨਾ ਇੱਕ ਵੱਖਰੀ ਪ੍ਰਸ਼ਾਸਕੀ ਤਬਦੀਲੀ ਹੈ; ਇਨ੍ਹਾਂ ਜੌਬਾਂ ਨੂੰ ਜੋੜਨਾ ਆਪਣੇ ਆਪ ਕਿਸੇ
ਬ੍ਰਾਂਚ ਦੀ ਸੁਰੱਖਿਆ ਨਹੀਂ ਕਰਦਾ।

### ਮਰਜ ਕਤਾਰ

`queue` ਲੇਬਲ PR ਨੂੰ Mergify ਕਤਾਰ (`.mergify.yml`) ਵਿੱਚ ਭੇਜਦਾ ਹੈ। Mergify
`mergify/merge-queue/` ਬ੍ਰਾਂਚ ਉੱਤੇ ਇੱਕ ਡ੍ਰਾਫ਼ਟ PR ਖੋਲ੍ਹਦਾ ਹੈ, CI ਉੱਥੇ ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦਾ ਹੈ,
ਅਤੇ ਅਸਲ PR ਤਦ ਮਰਜ ਹੁੰਦਾ ਹੈ ਜਦੋਂ `Gate / CI`, `Gate / Quality` ਅਤੇ
`Merge integrity (changelog + generated skills)` ਪਾਸ ਹੋ ਜਾਣ।

Mergify ਆਪਣਾ ਕਤਾਰ ਸਾਰ ਡ੍ਰਾਫ਼ਟ ਦੇ ਵੇਰਵੇ ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਅਤੇ ਹੋਰ ਐਪਸ ਵੀ ਇਸਨੂੰ ਸੰਪਾਦਿਤ ਕਰ ਸਕਦੀਆਂ ਹਨ।
ਅਜਿਹੇ ਡ੍ਰਾਫ਼ਟ ਉੱਤੇ `pull_request` `edited` ਇਵੈਂਟ ਆਪਣਾ concurrency group
(`-queue-edit-<run_id>`) ਲੈਂਦਾ ਹੈ ਤਾਂ ਜੋ ਇਹ ਡ੍ਰਾਫ਼ਟ ਦੇ ਅਸਲ ਰਨ ਨੂੰ ਰੱਦ ਨਾ ਕਰ ਸਕੇ, ਅਤੇ ਇਹ ਗੇਟ ਅਤੇ
ਮੈਟ੍ਰਿਕਸ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ। ਸਿਰਫ਼ `Merge integrity` ਫਿਰ ਵੀ ਚਲਦਾ ਹੈ। ਛੱਡੀ ਗਈ ਗੇਟ ਜੌਬ
ਇੱਕ ਵੱਖਰਾ ਚੈਕ ਨਾਮ ਰੱਖਦੀ ਹੈ, ਕਿਉਂਕਿ Mergify ਛੱਡੇ ਹੋਏ `Gate / CI` ਨੂੰ ਅਸਫ਼ਲ ਚੈਕ ਵਜੋਂ ਪੜ੍ਹਦਾ ਹੈ
ਅਤੇ PR ਨੂੰ ਕਤਾਰ ਵਿੱਚੋਂ ਕੱਢ ਦਿੰਦਾ ਹੈ।

ਕਤਾਰ ਵਿੱਚੋਂ ਕੱਢੇ ਜਾਣ ਤੋਂ ਬਾਅਦ, ਪੁਸ਼ ਹਮੇਸ਼ਾ PR ਨੂੰ ਮੁੜ ਕਤਾਰ ਵਿੱਚ ਨਹੀਂ ਪਾਉਂਦਾ। ਇਸ ਉੱਤੇ
`@mergifyio queue` ਟਿੱਪਣੀ ਕਰੋ।

### ਸਵੀਕ੍ਰਿਤੀ ਰਿਡਿਊਸਰ ਵਿੱਚ ਸੰਭਾਲਿਆ ਸਬੂਤ

`scripts/quality/validate-release-acceptance.mjs` ਦਿੱਤੀ ਗਈ ਯੋਜਨਾ ਅਤੇ ਇਸ ਦੇ
ਮੈਨੀਫੈਸਟਾਂ ਨੂੰ ਘਟਾਉਂਦਾ ਹੈ; ਇਹ ਸਥਾਪਤ ਨਹੀਂ ਕਰਦਾ ਕਿ ਯੋਜਨਾ ਪੂਰੀ ਰਿਲੀਜ਼ ਪਾਈਪਲਾਈਨ ਨੂੰ
ਕਵਰ ਕਰਦੀ ਹੈ। ਇਸ ਦੀਆਂ ਰਿਪੋਰਟਾਂ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ `releaseAcceptance: false` ਸੈੱਟ ਕਰਦੀਆਂ ਹਨ,
ਭਾਵੇਂ ਉਹ ਯੋਜਨਾ `VERIFIED` ਹੋਵੇ। `release-acceptance.yml` ਵਰਕਫ਼ਲੋ ਅਜੇ ਵੀ ਅਸਲ
ਬਿਲਡ, ਪੈਕੇਜ, ਬੂਟ ਜਾਂ ਪ੍ਰਮੋਸ਼ਨ ਰਸੀਦਾਂ ਦੀ ਥਾਂ shadow fixtures ਵਰਤਦਾ ਹੈ।

CLI ਨੂੰ ਸੰਭਾਲੇ ਹੋਏ ਸਬੂਤ ਦੀ ਪੁਸ਼ਟੀ ਕਰਨ ਲਈ `--evidence-root` ਲਾਜ਼ਮੀ ਚਾਹੀਦਾ ਹੈ।
ਫ਼ਾਈਲਾਂ ਨੂੰ `<evidence-root>/<artifact_id>/<member>` ਵਜੋਂ ਹੱਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ
SHA-256 ਨਾਲ ਹੈਸ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਸਬੂਤ ਤੋਂ ਬਿਨਾਂ PASS ਰਿਕਾਰਡ, ਗੁੰਮ ਜਾਂ ਬਦਲੀ ਹੋਈ ਫ਼ਾਈਲ,
ਅਸੁਰੱਖਿਅਤ ਪਾਥ ਜਾਂ ਸਿਮਲਿੰਕ ਪੁਸ਼ਟੀ ਨੂੰ ਰੋਕਦਾ ਹੈ। ਗੁੰਮ ਫ਼ਾਈਲਾਂ ਖਾਲੀ ਸਫ਼ਲ ਲੌਗਾਂ ਦੇ ਬਰਾਬਰ
ਨਹੀਂ ਹੁੰਦੀਆਂ। ਮੌਜੂਦਾ SHA/run/attempt ਜਾਂਚਾਂ ਸੁਤੰਤਰ ਰਹਿੰਦੀਆਂ ਹਨ: ਮਿਲਦੇ ਬਾਈਟ ਪੁਰਾਣੀ
ਰਸੀਦ ਨੂੰ ਠੀਕ ਨਹੀਂ ਕਰ ਸਕਦੇ। ਫ਼ਾਈਲ ਦੀ ਅਖੰਡਤਾ ਐਗਜ਼ਿਕਿਊਸ਼ਨ ਦੀ ਪ੍ਰਮਾਣਿਕਤਾ ਜਾਂ ਆਰਟੀਫੈਕਟ
ਪ੍ਰਮੋਸ਼ਨ ਦਾ ਸਬੂਤ ਨਹੀਂ ਹੈ।

### ਸਥਿਰ ਸਕੈਨ ਇਨਵੈਂਟਰੀ

ਵਰਜਨਬੱਧ npm-alias ਇਨਵੈਂਟਰੀ ਅਤੇ static-scan ਮੈਂਬਰਸ਼ਿਪ
`config/quality/gate-manifest.json` ਵਿੱਚ ਰਹਿੰਦੀ ਹੈ। `package.json` ਦੇ ਮੁਕਾਬਲੇ
ਸਕ੍ਰਿਪਟ ਨਾਮਾਂ ਅਤੇ ਸਹੀ ਕਮਾਂਡਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰਨ ਲਈ `npm run check:gate-manifest` ਚਲਾਓ;
ਜੋੜ, ਹਟਾਉਣ ਅਤੇ ਕਮਾਂਡ ਵਿੱਚ ਤਬਦੀਲੀ ਦੋਵੇਂ ਸਥਾਨਕ ਹੁੱਕ ਅਤੇ CI ਵਿੱਚ change-classification
ਜੌਬਾਂ ਨੂੰ ਅਸਫ਼ਲ ਕਰ ਦਿੰਦੇ ਹਨ। ਇੱਕ alias ਕੋਈ ਵਰਕਫ਼ਲੋ ਜੌਬ, ਮੈਟ੍ਰਿਕਸ ਇੰਸਟੈਂਸ ਜਾਂ ਟੈਸਟ ਕੇਸ
ਨਹੀਂ ਹੈ: ਇਨ੍ਹਾਂ ਗਿਣਤੀਆਂ ਨੂੰ ਪਰਸਪਰ ਬਦਲਣਯੋਗ ਵਜੋਂ ਪੇਸ਼ ਨਹੀਂ ਕੀਤਾ ਜਾਣਾ ਚਾਹੀਦਾ।

ਚੁਣੇ ਹੋਏ aliases ਨੂੰ ਚਲਾਏ ਬਿਨਾਂ ਜਾਂਚਣ ਲਈ `npm run quality:scan -- --list` ਜਾਂ
`npm run quality:scan:fast -- --list` ਵਰਤੋ। ਰੰਨਰ npm ਐਂਟਰੀਪੌਇੰਟ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ,
ਇਸ ਲਈ ਇਸ ਦਾ ਰਨਟਾਈਮ (ਜਿੱਥੇ ਕੌਂਫ਼ਿਗਰ ਕੀਤਾ ਹੋਵੇ ਉੱਥੇ Bun ਸਮੇਤ) ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ।
ਮੈਨੀਫੈਸਟ ਉਨ੍ਹਾਂ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਤੋਂ ਬਾਹਰਲੇ aliases ਨੂੰ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ ਚਲਾਏ ਜਾਣ ਵਾਲੇ ਵਜੋਂ
ਦਰਜ ਕਰਦਾ ਹੈ, ਅਤੇ read-only ਸਕੈਨ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵਿੱਚ ਮੇਨਟੇਨੈਂਸ ਕਮਾਂਡਾਂ ਮਨਾਹੀ ਹਨ।

ਇਹ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਸਿਰਫ਼ ਸਥਿਰ ਸਕੈਨ ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ। ਇਹ ਉਤਪਾਦ ਟੈਸਟਾਂ, ਕਵਰੇਜ,
ਪੈਕੇਜਿੰਗ, ਬਾਹਰੀ ਜਾਂਚਾਂ ਜਾਂ ਉਮੀਦਵਾਰ ਦੀ ਪੂਰੀ ਰਿਲੀਜ਼ ਸਵੀਕ੍ਰਿਤੀ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਨਹੀਂ ਕਰਦੀਆਂ।
ਵਰਕਫ਼ਲੋ ਦਾਖਲਾ ਸੰਬੰਧਿਤ `config/quality/admission-policy.json` ਅਤੇ
`scripts/quality/admission-verdict.mjs` ਵਰਤਦਾ ਹੈ। Release-observer ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵੱਖਰੀਆਂ
ਰਹਿੰਦੀਆਂ ਹਨ; ਉਨ੍ਹਾਂ ਦੀਆਂ ਲਾਗੂ ਜਾਂਚਾਂ ਅਤੇ ਰਸੀਦਾਂ ਦੀ ਸੁਤੰਤਰ ਤੌਰ ਉੱਤੇ ਜਾਂਚ ਕਰੋ। ਪੂਰੇ
observer ਦੀਆਂ ਸਥਿਰ ਕਮਾਂਡਾਂ `config/quality/release-green-static-profile.json` ਵਿੱਚ
ਘੋਸ਼ਿਤ ਹਨ, ਜਿਨ੍ਹਾਂ ਵਿੱਚ `audit:deps`, mutation-test ਚੋਣ ਅਤੇ translation checks ਸ਼ਾਮਲ ਹਨ।
ਲੋਡਰ npm ਕਮਾਂਡਾਂ ਦੀ `package.json` ਅਤੇ ਮਾਡਲ ਕੀਤੀਆਂ CI/Quality ਘੋਸ਼ਣਾਵਾਂ ਦੇ ਮੁਕਾਬਲੇ
ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ; ਇਹ shell tokens ਨੂੰ arguments ਵਜੋਂ ਚਲਾਉਣ ਦੀ ਥਾਂ drift ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ।
ਲਾਜ਼ਮੀ scanner SKIP/INCOMPLETE ਆਉਟਪੁੱਟ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦੀ। ਪ੍ਰੋਫ਼ਾਈਲ ਆਪਣੀਆਂ
ਬਾਹਰੀ exclusions ਦਰਜ ਕਰਦਾ ਹੈ ਅਤੇ hosted coverage, test matrices, package ਜਾਂ deployment
evidence ਦੀ ਥਾਂ ਨਹੀਂ ਲੈਂਦਾ। ਹੇਠਾਂ ਦਿੱਤੀ ਗਈ ਗੱਥਾਤਮਕ ਇਨਵੈਂਟਰੀ ਇੱਕ ਸੰਦਰਭ ਹੈ, ਇਹ ਸਬੂਤ ਨਹੀਂ
ਕਿ ਕੋਈ ਗੇਟ ਅਸਲ ਵਿੱਚ ਚੱਲਿਆ ਸੀ।

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (policy gates) ਅਤੇ `scripts/quality/` (ratchet engine) ਦੇ
ਅਧੀਨ ਰਹਿੰਦੀਆਂ ਹਨ। CI ਦਾ ਸੱਚਾ ਸਰੋਤ `.github/workflows/ci.yml` ਹੈ।

### ਰਿਲੀਜ਼ PR ਤੇਜ਼-ਮਾਰਗ (`quality.yml`)

`.github/workflows/quality.yml` main/release PRs, `main` ਉੱਤੇ ਪੁਸ਼,
dispatch ਅਤੇ merge groups ਉੱਤੇ CI ਨੂੰ ਪੂਰਾ ਕਰਦਾ ਹੈ। PRs path-filtered ਤੇਜ਼ ਜਾਂਚਾਂ ਵਰਤਦੇ ਹਨ।
ਸਥਾਈ ਤੌਰ ਉੱਤੇ ਅਸਮਰੱਥ duplicate build ਹਟਾ ਦਿੱਤਾ ਗਿਆ ਹੈ; ਅਸਲ build/package/boot ਜਾਂਚਾਂ
CI ਵਿੱਚ ਮੌਜੂਦ ਰਹਿੰਦੀਆਂ ਹਨ। unit suite ਅਤੇ vitest ਸਿਰਫ਼ CI ਵਿੱਚ ਚਲਦੇ ਹਨ
(`Unit Tests (N/8)` ਅਤੇ `Vitest`)।

| ਕੰਮ                                              | ਦਾਇਰਾ                                                                                                           | ਬਲੌਕਿੰਗ         |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | --------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API docs refs ਅਤੇ docs-all                                                                       | ਹਾਂ             |
| `Fast Quality Gates`                             | Code PRs; static checks, typecheck, dashboard typecheck, ਪ੍ਰਭਾਵਿਤ unit tests, ਭੁੱਲੇ ਹੋਏ sibling tests (ਸਲਾਹਕਾਰ) |
| `No new ESLint warnings`                         | Code PRs; suppressions-aware lint guard                                                                         | ਹਾਂ, forks ਸਮੇਤ |
| `Merge integrity (changelog + generated skills)` | Non-draft PRs; changelog ਅਤੇ generated skill sync                                                               | ਹਾਂ, forks ਸਮੇਤ |

#### ਭੁੱਲੇ ਹੋਏ sibling tests ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ਦੇ ਇੱਕ ਸਲਾਹਕਾਰ ਪੜਾਅ ਵਜੋਂ ਚੱਲਦਾ ਹੈ ਅਤੇ
test-impact map ਦੇ ਪਿੱਛੇ ਵਾਲੇ import resolver ਨੂੰ ਦੁਬਾਰਾ ਵਰਤਦਾ ਹੈ।
ਹਰ ਬਦਲੇ ਹੋਏ production module ਲਈ, ਇਹ ਨਿਰਧਾਰਤ
`changed module/symbol -> static consumer -> candidate sibling test` ਚੇਨਾਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ, ਜਦੋਂ candidate
test pull-request diff ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ। Markdown summary ਅਤੇ JSON result ਨੂੰ
calibration ਲਈ `forgotten-sibling-tests` workflow artifact ਵਜੋਂ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ, blocking rollout ਤੋਂ ਪਹਿਲਾਂ।

Barrel re-exports ਅਤੇ dynamic imports ਸਿਰਫ਼ resolution diagnostics ਹਨ; ਇਹ ਕਦੇ ਵੀ
blocking finding ਨਹੀਂ ਬਣਾਉਂਦੇ। Reviewed exceptions ਇੱਥੇ ਰਹਿੰਦੇ ਹਨ:
`config/quality/forgotten-sibling-allowlist.json`। ਹਰ entry ਵਿੱਚ consumer ਅਤੇ candidate
test ਦਾ ਨਾਮ, ਇੱਕ ਵਿਸ਼ੇਸ਼ rationale, ਅਤੇ GitHub issue ਜਾਂ pull request ਦਾ link ਦੇਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਗਲਤ ਬਣੀਆਂ
entries fail closed ਹੁੰਦੀਆਂ ਹਨ। Exceptions deleted candidate test ਜਾਂ `.skip`/`.todo` ਜੋੜਨ ਵਾਲੇ diff ਨੂੰ
suppress ਨਹੀਂ ਕਰ ਸਕਦੀਆਂ; assertion weakening ਅਤੇ ਹੋਰ masking ਦੀ ਜ਼ਿੰਮੇਵਾਰੀ ਸੁਤੰਤਰ ਤੌਰ ’ਤੇ blocking
`check:test-masking` gate ਦੀ ਹੈ।

ਐਂਟਰੀ ਦੇ ਇੰਪੋਰਟ ਗ੍ਰਾਫ਼ ਦੀ ਪਾਲਣਾ ਕਰਦੀ ਹੈ, ਇਸ ਲਈ ਬਿਲਡ ਪ੍ਰੋਗਰਾਮ ਵਿੱਚ ਕਦੇ ਵੀ ਨਾ ਆਉਣ ਵਾਲੀਆਂ ਫ਼ਾਈਲਾਂ ਦੀ ਵੀ
ਉੱਥੇ ਜਾਂਚ ਹੁੰਦੀ ਹੈ।

ਇਹ ਨਤੀਜਾ ਮਹੱਤਵਪੂਰਨ ਹੈ ਜਦੋਂ ਇਹ ਨਿਰਧਾਰਤ ਕੀਤਾ ਜਾਵੇ ਕਿ ਕੋਈ ਫ਼ਾਈਲ ਟਾਈਪ ਕੀਤੀ ਹੋਈ ਹੈ ਜਾਂ ਨਹੀਂ: **`check:build-typecheck`
ਅਧੀਨ ਸਿਫ਼ਰ ਡਾਇਗਨੋਸਟਿਕਾਂ ਦਾ ਮਤਲਬ ਸਿਫ਼ਰ ਨਹੀਂ ਹੈ**। 26 ਫ਼ਾਈਲਾਂ ਤੋਂ `@ts-nocheck` ਹਟਾਉਣ
'ਤੇ ਉਨ੍ਹਾਂ ਵਿੱਚੋਂ 23 ਬਿਲਡ ਪ੍ਰੋਗਰਾਮ ਵਿੱਚ ਗਲਤੀ-ਰਹਿਤ ਦਿਖਾਈਆਂ ਦਿੱਤੀਆਂ; ਉਨ੍ਹਾਂ ਵਿੱਚੋਂ ਸੋਲ੍ਹਾਂ ਨੇ ਸਖ਼ਤ ਪ੍ਰੋਗਰਾਮ ਵਿੱਚ ਲਗਭਗ

### Derived values: the `pr` and `release` gate modes

Feature PR ਕਦੇ ਵੀ ਅਜਿਹਾ ਮੁੱਲ ਨਹੀਂ ਲਿਖਦੀ ਜੋ ਆਪਣੇ base ਦੀ state ’ਤੇ ਨਿਰਭਰ ਹੋਵੇ: provider, migration,
MCP-tool ਅਤੇ strategy counts, README SVG numbers, facts snapshot। ਇੱਕ ਕਦਮ ਇਹਨਾਂ ਸਭ ਨੂੰ ਮੁੜ recompute ਕਰਦਾ ਹੈ,
`npm run release:refresh-derived` ਰਾਹੀਂ, ਜਿਸਨੂੰ release ਅਤੇ nightly derived-refresh PR ਚਲਾਉਂਦੇ ਹਨ।
ਇਸ ਲਈ **releases ਦੇ ਵਿਚਕਾਰ base ਡਿਜ਼ਾਇਨ ਅਨੁਸਾਰ live code ਤੋਂ ਪਿੱਛੇ ਹੁੰਦਾ ਹੈ**, ਅਤੇ ਜੇ ਕੋਈ gate ਜਾਂ test
tree ਦੀ live code ਨਾਲ ਤੁਲਨਾ ਕਰੇ, ਤਾਂ sibling ਵੱਲੋਂ provider ਜੋੜਨ ਤੋਂ ਬਾਅਦ ਹਰ PR ’ਤੇ red ਹੋਵੇਗਾ। ਇਸ ਲਈ
derived values ਦਾ ਮੁਲਾਂਕਣ ਕਰਨ ਵਾਲੇ gates ਦੋ ਮੋਡਾਂ ਵਿੱਚੋਂ ਇੱਕ ਵਿੱਚ ਚਲਦੇ ਹਨ, ਜਿਨ੍ਹਾਂ ਦਾ ਨਿਰਧਾਰਨ
`scripts/check/lib/gateMode.mjs` ਕਰਦਾ ਹੈ (ਪਹਿਲਾ match ਲਾਗੂ ਹੁੰਦਾ ਹੈ):

1. ਕਮਾਂਡ ਲਾਈਨ ’ਤੇ `--mode=pr|release`;
2. `OMNIROUTE_GATE_MODE` environment variable (`pr` ਜਾਂ `release`);
3. GitHub Actions event ਤੋਂ automatic: ਅਜਿਹਾ `pull_request` ਜਿਸਦਾ head `release/v*` ਨਹੀਂ ਹੈ,
   `merge_group`, ਜਾਂ `omni-queue/**` ਨੂੰ push → `pr`; ਬਾਕੀ ਸਭ (push, schedule,
   dispatch, release PR `release/v* → main`, ਕੋਈ ਵੀ local run) → `release`।

ਹਰ ਮੋਡ ਵਿੱਚ `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) ਕਿਹੜੀ ਚੀਜ਼ ’ਤੇ ਅਸਫਲ ਹੁੰਦਾ ਹੈ:

| Mode      | ਅਸਫਲਤਾਵਾਂ                                                                                                                                                                                                                                                                                                                                                                                                                              | ਲਾਈਵ ਤੱਥਾਂ ਦੀ ਲੋੜ |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `release` | ਹਰ ਜਾਂਚ ਵਿੱਚ ਟ੍ਰੀ ਤੋਂ ਇਕੱਠੇ ਕੀਤੇ ਤੱਥਾਂ ਦੇ ਮੁਕਾਬਲੇ ਸਖ਼ਤ ਸਮਾਨਤਾ (ਗੇਟ ਦਾ ਹਮੇਸ਼ਾਂ ਤੋਂ ਵਰਤਾਅ): ਪੁਰਾਣੀ ਗਿਣਤੀ, ਵਰਜਨ, ਕਵਰੇਜ ਫ਼ਲੋਰ ਜਾਂ SVG ਨੰਬਰ ਇੱਕ STRICT drift ਹੈ                                                                                                                                                                                                                                                                             | ਹਾਂ               |
| `pr`      | ਸਿਰਫ਼ ਉਹੀ ਜੋ ਬਦਲਾਅ ਨੇ ਕੀਤਾ, PR ਬੇਸ ਦੇ ਮੁਕਾਬਲੇ ਉਸੇ claim extractors ਨਾਲ diff ਕੀਤਾ ਹੋਇਆ: (1) ਉਸ ਜਾਂਚ ਅਤੇ ਫ਼ਾਈਲ ਲਈ ਬੇਸ ਵਿੱਚ ਮੌਜੂਦ ਨਾ ਰਹੀ managed value ("PR ਨੇ ਇੱਕ managed number ਸੰਪਾਦਿਤ ਕੀਤਾ — ਲਾਈਨ ਨੂੰ ਬੇਸ ਟੈਕਸਟ 'ਤੇ ਮੁੜ ਬਹਾਲ ਕਰੋ"); (2) ਬੇਸ ਵਿੱਚ ਮੌਜੂਦ ਲੋੜੀਂਦਾ claim ਜੋ head ਵਿੱਚ ਗੁੰਮ ਹੋ ਗਿਆ। ਜਿਨ੍ਹਾਂ content invariants ਲਈ ਤੱਥਾਂ ਦੀ ਲੋੜ ਨਹੀਂ, ਉਹ release mode ਵਾਂਗ ਚਲਦੇ ਹਨ; release-only ਜਾਂਚਾਂ ਸੂਚੀਬੱਧ ਕਰਕੇ ਛੱਡ ਦਿੱਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ | ਨਹੀਂ              |

Agent-instruction ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਕੋਈ ਵੀ derived count ਨਹੀਂ ਹੁੰਦੀ: `AGENTS.md`, `llm.txt` (ਅਤੇ ਇਸ ਦੀਆਂ
`docs/i18n/*/llm.txt` ਕਾਪੀਆਂ), bs `AGENTS.md` fork, `open-sse/services/AGENTS.md`,
`src/shared/constants/agentSkills.ts`, `skills/README.md` ਅਤੇ ਹਰ `skills/*/SKILL.md` ਸਰੋਤ ਵੱਲ
(ਉਦਾਹਰਨ ਲਈ `ROUTING_STRATEGY_VALUES` in `src/shared/constants/routingStrategies.ts`) ਅਤੇ
`npm run facts` ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦੀਆਂ ਹਨ। ਦੋਵੇਂ modes ਵਿੱਚ invariant "No derived counts (agent-instruction file …)"
ਉੱਥੇ ਕਿਸੇ count (providers, migrations, MCP tools ਅਤੇ scopes, routing strategies, scoring factors, mode packs) ਨੂੰ
ਅਸਫਲ ਮੰਨਦਾ ਹੈ, ਇਸ ਲਈ release refresh ਨੂੰ ਕਦੇ ਵੀ ਕਿਸੇ instruction file ਨੂੰ ਮੁੜ ਲਿਖਣ ਦੀ ਲੋੜ ਨਹੀਂ ਪੈਂਦੀ।

`pr` mode ਵਿੱਚ writer branches managed values ਨੂੰ ਸੰਪਾਦਿਤ ਕਰ ਸਕਦੀਆਂ ਹਨ: `chore/derived-*` (nightly refresh
PR), `release/v*`, ਅਤੇ translation waves `docs/i18n-*` ਅਤੇ `chore/i18n-*`
(`scripts/check/lib/derivedClaimsDiff.mjs`)। Queue batches (`merge_group`, Mergify drafts,
`omni-queue/**`) ਨੂੰ ਦੁਬਾਰਾ ਨਹੀਂ ਪਰਖਿਆ ਜਾਂਦਾ: ਉਹਨਾਂ ਵਿੱਚ ਉਹ PRs ਜੋੜੇ ਜਾਂਦੇ ਹਨ ਜਿਨ੍ਹਾਂ ਨੂੰ ਗੇਟ ਪਹਿਲਾਂ ਹੀ
ਇੱਕ-ਇੱਕ ਕਰਕੇ ਪਰਖ ਚੁੱਕਾ ਹੈ।

Exit codes: `0` ਸਾਫ਼ · `1` STRICT drift (ਜਾਂ `--strict` ਨਾਲ soft drift) ਜਾਂ managed-value
ਉਲੰਘਣਾ · `2` infrastructure — code facts ਇਕੱਠੇ ਨਹੀਂ ਕੀਤੇ ਜਾ ਸਕੇ (tsx probe ਅਸਫਲ ਹੋਈ ਜਾਂ ਸਮਾਂ ਸਮਾਪਤ ਹੋ ਗਿਆ;
timeout `OMNIROUTE_FACTS_TIMEOUT_MS`, default 600000 ms ਹੈ) ਜਾਂ, CI ਵਿੱਚ, PR diff
base resolve ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਿਆ। Exit 2 ਕਦੇ ਵੀ documentation divergence ਨਹੀਂ ਹੁੰਦਾ: job ਨੂੰ
ਦੁਬਾਰਾ ਚਲਾਓ ਜਾਂ environment ਠੀਕ ਕਰੋ।

ਹਰ mode ਕਿੱਥੇ ਚਲਦਾ ਹੈ:

| ਕਿੱਥੇ                                                                                                      | Mode                                                                                                                                                                                                         |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Feature PR — `ci.yml` job `docs-sync-strict`, `quality.yml` step "Docs accuracy"                           | `pr` (automatic); job ਬੇਸ ਨੂੰ `BASE_SHA` ਵਜੋਂ ਪਾਸ ਕਰਦਾ ਹੈ ਅਤੇ `fetch-depth: 2` ਨਾਲ checkout ਕਰਦਾ ਹੈ                                                                                                          |
| `merge_group`, `omni-queue/**` candidates, merge train ਦੀ ਪੂਰੀ gate list                                   | `pr`                                                                                                                                                                                                         |
| Release PR (`release/v* → main`), pushes, scheduled ਅਤੇ manual runs                                        | `release`                                                                                                                                                                                                    |
| Release-Green (`scripts/quality/validate-release-green.mjs`)                                               | HARD items `OMNIROUTE_GATE_MODE=pr` ਨਾਲ ਚਲਦੇ ਹਨ ("ਕੀ base ਨੇ break ਕੀਤਾ?"); DRIFT item `derived-refresh` `npm run release:refresh-derived -- --check` ਚਲਾਉਂਦਾ ਹੈ (strict view, ਕਦੇ ਵੀ base-red ਨਹੀਂ ਖੋਲ੍ਹਦਾ) |
| Release (`/generate-release` phases 0a ਅਤੇ 1; skill wiring ਇੱਕ ਵੱਖਰਾ owner-approved change ਹੈ)             | `npm run release:refresh-derived` derived files ਲਿਖਦਾ ਹੈ; release PR ਦੀਆਂ ਆਪਣੀਆਂ checks ਫਿਰ `release` mode ਵਿੱਚ ਚਲਦੀਆਂ ਹਨ                                                                                    |
| `nightly-derived-refresh.yml` (ਰੋਜ਼ਾਨਾ, ਸਭ ਤੋਂ ਉੱਚੇ `release/vX.Y.Z`, release-freeze ਦੌਰਾਨ ਛੱਡਿਆ ਜਾਂਦਾ ਹੈ) | `npm run release:refresh-derived -- --profile=nightly`; diff ਹੋਣ 'ਤੇ ਇਹ `chore/derived-refresh` ਤੋਂ ONE PR ਖੁੱਲ੍ਹੀ ਰੱਖਦਾ ਹੈ; ਕਦੇ merge ਨਹੀਂ ਕਰਦਾ                                                             |

ਇਸ ਦੇ ਪਿੱਛੇ ਵਾਲੀਆਂ commands:

- `npm run facts` ਹਰ derived number ਨੂੰ JSON ਵਜੋਂ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ (`scripts/release/facts.mjs`)।
  `--key=code.mcpTools` ਇੱਕ ਮੁੱਲ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ, ਜਦਕਿ `--snapshot` live tree ਦੀ ਬਜਾਏ
  commit ਕੀਤੇ snapshot ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ। ਜਦੋਂ facts ਇਕੱਠੇ ਨਹੀਂ ਕੀਤੇ ਜਾ ਸਕਦੇ, ਤਾਂ Exit 2 ਹੁੰਦਾ ਹੈ।

  `provider-reference` (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (snapshot), `numbers`
  (counts gate ਦੀ rewrite plan ਨੂੰ docs ਉੱਤੇ ਲਾਗੂ ਕਰਦਾ ਹੈ, ਫਿਰ ਉਹਨਾਂ ਨੂੰ
  `docs/i18n/` mirrors ਤੱਕ ਲੈ ਜਾਂਦਾ ਹੈ), `readme-diagrams`, `skills` (generated `SKILL.md`),
  `e2e-timings` (tree ਵਿੱਚ `syncE2eTimings` ਆਉਣ ਤੱਕ ਛੱਡਿਆ ਜਾਂਦਾ ਹੈ), `ui-keys` (`en.json`
  ਵੱਲੋਂ ਹਟਾਈਆਂ keys ਨੂੰ prune ਕਰਦਾ ਹੈ ਅਤੇ, `--rewritten-since=<ref>` ਨਾਲ — ਡਿਫਾਲਟ
  `origin/main` — ਆਖਰੀ release ਤੋਂ ਬਾਅਦ ਦੁਬਾਰਾ ਲਿਖੀਆਂ English values ਨੂੰ ਮੁੜ queue ਕਰਦਾ ਹੈ),
  `llm-mirrors` ਅਤੇ `verify-generated` (write ਤੋਂ ਬਾਅਦ release mode ਵਿੱਚ
  `check:generated-artifacts` ਅਤੇ `check:agent-skills-sync` ਪਾਸ ਹੋਣੇ ਲਾਜ਼ਮੀ ਹਨ; `--check` ਵਿੱਚ
  ਅਤੇ ਜਦੋਂ `--only` ਇਸਨੂੰ ਬਾਹਰ ਰੱਖਦਾ ਹੈ, ਛੱਡੇ ਜਾਂਦੇ ਹਨ; failure ਹੋਣ ਤੇ exit 2 ਹੁੰਦਾ ਹੈ)।
  `changelog` step opt-in ਹੈ (`--with-changelog`, ਸਿਰਫ਼ release profile ਵਿੱਚ)। `--profile=nightly`
  ਕਦੇ ਵੀ version claim ਨੂੰ ਨਹੀਂ ਛੁਹਿੰਦਾ। `-- --check` ਨਾਲ ਇਹ ਕੁਝ ਵੀ ਨਹੀਂ ਲਿਖਦਾ ਅਤੇ ਜਦੋਂ ਕੋਈ
  ਫਾਈਲ ਬਦਲਣੀ ਹੋਵੇ ਜਾਂ ਕਿਸੇ managed value ਨੂੰ manual edit ਦੀ ਲੋੜ ਹੋਵੇ ਤਾਂ exit 1 ਕਰਦਾ ਹੈ
  (ਦੋਵੇਂ ਸੂਚੀਬੱਧ ਕੀਤੇ ਜਾਂਦੇ ਹਨ); infrastructure failure ਹੋਣ ਤੇ exit 2 ਹੁੰਦਾ ਹੈ। `--json`
  ਨਤੀਜੇ ਨੂੰ JSON ਵਜੋਂ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ।
- `docs/reference/derived-facts.json` ਉਹ facts ਦਾ snapshot ਹੈ ਜੋ ਆਖਰੀ refresh ਨੇ ਵਰਤੇ ਸਨ।
  ਇਸਨੂੰ ਸਿਰਫ਼ refresh ਹੀ ਲਿਖਦਾ ਹੈ। README SVG generators ਇਸਨੂੰ ਪੜ੍ਹਦੇ ਹਨ, ਅਤੇ PR ਸਮੇਂ ਦੇ
  unit tests committed docs ਅਤੇ generated files ਦੀ ਇਸ ਨਾਲ ਤੁਲਨਾ ਕਰਦੇ ਹਨ — live code ਨਾਲ
  ਕਦੇ ਨਹੀਂ। suite ਦੀ ਇਕੱਲੀ live comparison
  `tests/unit/check-docs-counts-sync.test.ts` ਵਿੱਚ "the release refresh closes the cycle" ਹੈ:
  live facts ਨਾਲ refresh ਦੀ rewrite plan ਨੂੰ memory ਵਿੱਚ ਲਾਗੂ ਕਰਨ ਤੋਂ ਬਾਅਦ ਕੋਈ ਵੀ STRICT drift
  ਬਾਕੀ ਨਹੀਂ ਰਹਿੰਦਾ ਜਿਸਦੀ ਇਹ report ਨਾ ਕਰੇ, ਅਤੇ ਦੁਬਾਰਾ planning ਕਰਨ ਨਾਲ ਕੁਝ ਨਹੀਂ ਬਦਲਦਾ।

ਸਥਾਨਕ ਤੌਰ ਤੇ ਦੁਹਰਾਉਣ ਲਈ (ਸਥਾਨਕ run ਡਿਫਾਲਟ ਰੂਪ ਵਿੱਚ `release` ਹੁੰਦਾ ਹੈ):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # feature PR ਦਾ ਮੁਲਾਂਕਣ ਕਿਸ ਆਧਾਰ ਤੇ ਹੁੰਦਾ ਹੈ
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # release ਕੀ rewrite ਕਰੇਗਾ
```

Resolvable base ਤੋਂ ਬਿਨਾਂ (ਨਾ `BASE_SHA`/`BASE_REF`, ਨਾ ਹੀ ਸਥਾਨਕ
`origin/release/v<version>`) ਸਥਾਨਕ `pr` run warning ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ ਅਤੇ fail ਹੋਣ ਦੀ ਬਜਾਏ
diff ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ।

**ਦੋ modes (2026-11-13 ਤੋਂ)।** ਇੱਕ feature PR `en.json` (ਅਤੇ
`bin/cli/locales/en.json`) ਵਿੱਚ keys ਜੋੜਦਾ ਜਾਂ ਦੁਬਾਰਾ ਲਿਖਦਾ ਹੈ ਅਤੇ ਕਿਸੇ ਹੋਰ locale ਨੂੰ

`config/quality/derived-paths/translation.json` family) ਅਜਿਹੇ feature PR ਨੂੰ fail ਕਰਦਾ ਹੈ।
ਹੋਰ locales ਹਰ release ਵਿੱਚ ਇੱਕ ਵਾਰ `release:refresh-derived` ਰਾਹੀਂ ਪੂਰੇ ਕੀਤੇ ਜਾਂਦੇ ਹਨ,
ਜੋ `scripts/i18n/sync-ui-keys.mjs` ਵਿੱਚ `syncUiKeys()` ਨੂੰ call ਕਰਦਾ ਹੈ (missing keys ਜੋੜੋ,
ਹਟਾਈਆਂ ਗਈਆਂ keys prune ਕਰੋ, ਦੁਬਾਰਾ ਲਿਖੀ English ਦੇ translations ਨੂੰ `rewrittenSinceRef` ਨਾਲ
mark ਕਰੋ, translate ਕਰੋ), ਜਾਂ translation wave ਰਾਹੀਂ। Gates mode ਨੂੰ
`scripts/check/lib/gateMode.mjs` ਤੋਂ ਪੜ੍ਹਦੇ ਹਨ: `pr` mode ਵਿੱਚ (feature PRs,
`merge_group`, `omni-queue/**`) ਉੱਪਰਲੇ release-mode gates `SKIP reason=pr-mode` ਪ੍ਰਿੰਟ ਕਰਦੇ
ਹਨ ਅਤੇ 0 exit ਕਰਦੇ ਹਨ; `release` mode ਵਿੱਚ (release PR, `main` ਉੱਤੇ pushes,
`workflow_dispatch`, ਸਥਾਨਕ runs) ਉਹ ਪਹਿਲਾਂ ਵਾਂਗ strict ਰਹਿੰਦੇ ਹਨ, ਅਤੇ release PR ਉੱਤੇ
diff-aware gates ਨੂੰ `BASE_REF=origin/main` ਮਿਲਦਾ ਹੈ, ਇਸ ਲਈ ਉਹ cycle ਵੱਲੋਂ ਜੋੜੀ ਜਾਂ ਦੁਬਾਰਾ
ਲਿਖੀ ਹਰ key ਦਾ ਮੁਲਾਂਕਣ ਕਰਦੇ ਹਨ। Feature-PR verdict ਦਾ ਸਥਾਨਕ preview
`--mode=pr` ਨਾਲ ਕਰੋ।

ਇੱਕ PR ਜੋ ਹਾਲੇ ਵੀ `pr` ਮੋਡ ਵਿੱਚ locale catalogs ਬਦਲਦਾ ਹੈ (translation wave, release refresh, translation-only fix), ਛੱਡਿਆ ਨਹੀਂ ਜਾਂਦਾ: `check-key-completeness` ਇਸ ਵੱਲੋਂ ਬਦਲੇ ਗਏ ਹਰ catalog ਨੂੰ merge base ਦੇ ਉਸੇ catalog (`scripts/i18n/lib/touched-catalogs.mjs`) ਨਾਲ ਜਾਂਚਦਾ ਹੈ ਅਤੇ ਉਦੋਂ ਫੇਲ ਹੁੰਦਾ ਹੈ ਜਦੋਂ catalog ਵਿੱਚੋਂ ਕੋਈ key ਗੁੰਮ ਹੋ ਜਾਵੇ, `en.json` ਵਿੱਚ ਨਾ ਮੌਜੂਦ key ਆ ਜਾਵੇ, ਅਸਲ translation `__MISSING__:` marker ਜਾਂ English text ਵਿੱਚ ਬਦਲ ਜਾਵੇ, ਜਾਂ ਕੋਈ value ਉਸ English string ਦੇ placeholders/tags ਨੂੰ ਹੁਣ interpolate ਨਾ ਕਰੇ ਜਿਸਨੂੰ PR ਨੇ ਨਹੀਂ ਛੋਹਿਆ। PR ਵਿੱਚ ਨਵਾਂ catalog ਪੂਰਾ `en.json` key set ਲੈ ਕੇ ਆਉਣਾ ਚਾਹੀਦਾ ਹੈ। PR ਵੱਲੋਂ ਛੋਹੇ ਗਏ catalogs ਲਈ ਇਹ ਉਹੀ ਕੁਝ ਕਵਰ ਕਰਦਾ ਹੈ ਜੋ ratio ਅਤੇ CLI-parity gates ਵੇਖਣਗੇ।

Locale-parity unit tests (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`,
`i18n-placeholder-parity`) `tests/_helpers/localeParityMode.ts` ਰਾਹੀਂ ਉਹੀ modes follow ਕਰਦੇ ਹਨ: `pr` mode ਵਿੱਚ ਇਹ key-parity assertions ਨੂੰ skip ਕਰਦੇ ਹਨ ਅਤੇ merge base ਤੋਂ ਬਾਅਦ ਬਦਲੇ ਗਏ English ਵਾਲੀਆਂ keys ਦੀ placeholder parity release refresh ਲਈ ਛੱਡ ਦਿੰਦੇ ਹਨ (unit-test job ਦਾ shallow checkout ਇਸਨੂੰ ਪੜ੍ਹ ਨਾ ਸਕੇ ਤਾਂ ਹਰ key)। ਉਹ helper ਇਸਦਾ **ਇਕੱਲਾ ਮਨਜ਼ੂਰਸ਼ੁਦਾ mode-conditional skip** ਹੈ:
`check:test-masking` `.skip(` ਅਤੇ `{ skip: true }` ਨੂੰ ਗਿਣਦਾ ਹੈ, ਪਰ ਇਸ ਵੱਲੋਂ ਵਾਪਸ ਕੀਤੇ computed
`{ skip: "<reason>" }` ਨੂੰ ਨਹੀਂ ਗਿਣਦਾ, ਇਸ ਲਈ `tests/unit/locale-parity-mode.test.ts` ਉਨ੍ਹਾਂ tests ਦੀ ਸੂਚੀ ਨੂੰ pin ਕਰਦਾ ਹੈ ਜਿਨ੍ਹਾਂ ਨੂੰ ਇਸਦੀ ਵਰਤੋਂ ਦੀ ਇਜਾਜ਼ਤ ਹੈ — ਇੱਕ ਹੋਰ ਜੋੜਨਾ ਉਸ ਸੂਚੀ ਵਿੱਚ reviewed edit ਹੈ।

#### `check-ui-value-drift` — ਪੁਰਾਣੀ translation gate

ਉਹ ਇੱਕ i18n regression ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ ਹੋਰ gates structural ਤੌਰ ‘ਤੇ ਨਹੀਂ ਦੇਖ ਸਕਦੇ: English value ਨੂੰ ਦੁਬਾਰਾ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ ਪਿਛਲੇ English ਤੋਂ ਬਣੀਆਂ translations ਪਿੱਛੇ ਰਹਿ ਜਾਂਦੀਆਂ ਹਨ, ਇਸ ਲਈ non-English users ਵਿਸ਼ਵਾਸ ਨਾਲ ਲਿਖਿਆ ਹੋਇਆ, ਪਰ ਹੁਣ ਗਲਤ copy ਪੜ੍ਹਦੇ ਰਹਿੰਦੇ ਹਨ।

ਇਹ ਅਸਲ ਵਿੱਚ ship ਹੋਇਆ ਸੀ। Antigravity login helper ਆਉਣ ਵੇਲੇ `oauthModal.googleOAuthWarning` ਨੂੰ ਦੁਬਾਰਾ ਲਿਖਿਆ ਗਿਆ (#5203); **43 ਵਿੱਚੋਂ 39 locales** ਵਿੱਚ operators ਨੂੰ "ਪੂਰਾ URL copy ਕਰਕੇ ਹੇਠਾਂ paste ਕਰੋ" ਦੱਸਣ ਵਾਲਾ text ਰਹਿ ਗਿਆ — ਅਜਿਹਾ flow ਜੋ ਉਸ provider ਲਈ ਪੂਰਾ ਨਹੀਂ ਹੋ ਸਕਦਾ। #8463 ਤੱਕ ਇਹ ਪਤਾ ਨਹੀਂ ਲੱਗਿਆ, ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹਨਾਂ keys ਨੂੰ backfill ਕਰਦਾ ਹੈ ਜੋ **ਮੌਜੂਦ ਨਹੀਂ**, stale keys ਨੂੰ ਕਦੇ ਨਹੀਂ;
- `check-ui-keys-coverage` key _presence_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ stale translation covered ਵਜੋਂ score ਹੁੰਦੀ ਹੈ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` documentation mirrors ਨੂੰ track ਕਰਦਾ ਹੈ —
  ਇਹ ਕਦੇ `src/i18n/messages/*.json` ਨਹੀਂ ਪੜ੍ਹਦਾ। ਇਹ `docs-sync-strict` job ਵਿੱਚ ਚੱਲਦਾ ਹੈ: PRs ‘ਤੇ advisory,
  push ਅਤੇ nightly ‘ਤੇ strict; translation wave mirrors ਨੂੰ refresh ਕਰਦੀ ਹੈ, feature PR ਨੂੰ ਨਹੀਂ।

**Diff-aware, baseline-backed ਨਹੀਂ।** ਇਹ merge base ‘ਤੇ `en.json` ਦੀ ਤੁਲਨਾ working tree ਨਾਲ ਕਰਦਾ ਹੈ; ਹਰ ਉਸ key ਲਈ ਜਿਸਦੀ English value ਬਦਲੀ ਹੈ, ਜੇ ਕੋਈ locale ਹਾਲੇ ਵੀ untouched translation ਰੱਖਦਾ ਹੈ ਤਾਂ ਉਹ stale ਹੈ। ਇਹ ਜਾਣ-ਬੁੱਝ ਕੇ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ debt ਨੂੰ **freeze** ਕਰਦਾ ਹੈ — diff ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਲੰਬੇ ਸਮੇਂ ਤੋਂ ਮੌਜੂਦ translation ਕਿਸ ਪੁਰਾਣੀ English ਤੋਂ ਆਈ ਸੀ, ਇਸ ਲਈ gate ਸਿਰਫ਼ ਮੌਜੂਦਾ change ਨੂੰ judge ਕਰਦਾ ਹੈ। ਵਿਕਲਪ (ਹਰ key ਲਈ hash baseline) ਲਈ ਲਗਭਗ 600 KB ਦੀ generated file ਚਾਹੀਦੀ ਹੁੰਦੀ, ਜੋ ਸਭ ਤੋਂ ਵੱਡੇ ਮੌਜੂਦਾ baseline ਤੋਂ 3× ਵੱਡੀ ਹੈ ਅਤੇ ਹਰ i18n PR ‘ਤੇ churn ਕਰਦੀ।

ਇਸਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ translations ਨੂੰ update ਕਰੋ, ਜਾਂ
2. ਉਹਨਾਂ ਨੂੰ `__MISSING__:<new english>` ‘ਤੇ set ਕਰੋ — runtime ਫਿਰ corrected English serve ਕਰਦਾ ਹੈ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਅਤੇ key translation ਲਈ queue ਹੋ ਜਾਂਦੀ ਹੈ।

ਜੇ string ਦਾ **ਅਰਥ** ਬਦਲਿਆ ਹੈ, ਤਾਂ key ਦਾ ਨਾਮ ਬਦਲਣਾ ਤਰਜੀਹ ਦਿਓ: ਨਵੀਂ key stale translation inherit ਨਹੀਂ ਕਰ ਸਕਦੀ। ਇਹੀ pattern #8463 ਵਿੱਚ ਵਰਤਿਆ ਗਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

**New-code mode (Clean-as-You-Code) — 2026-08-30 ਤੋਂ, ਸਿਰਫ਼ PR fast-path ਲਈ**

`pull_request` events ਉੱਤੇ `quality.yml`, `check:file-size`,
`check:complexity-ratchets` ਅਤੇ `check:dead-code` ਨੂੰ `--base-ref <PR base SHA>` ਪਾਸ ਕਰਦੀ ਹੈ।
`check:complexity-ratchets` ਅਤੇ `check:dead-code` ਲਈ gate, merge-base ਦੀ ਤੁਲਨਾ
**ਸਿਰਫ਼ PR ਵੱਲੋਂ ਛੁਹੀਆਂ ਫਾਈਲਾਂ ਤੱਕ ਸੀਮਿਤ** ਕਰਕੇ ਕਰਦਾ ਹੈ
(`scripts/check/newCodeMode.mjs`: merge-base ਨੂੰ throwaway
`git worktree` ਵਿੱਚ materialize ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਉੱਥੇ ਅਤੇ HEAD ਉੱਤੇ ESLint/knip ਚਲਾਏ ਜਾਂਦੇ ਹਨ,
ਅਤੇ per-file counts ਦਾ diff ਕੀਤਾ ਜਾਂਦਾ ਹੈ):

- **blocking** — PR ਨੇ ਜਿਹੜੀਆਂ ਫਾਈਲਾਂ ਬਦਲੀਆਂ ਹਨ, ਉਨ੍ਹਾਂ ਵਿੱਚ cyclomatic/cognitive violations ਜਾਂ dead exports ਸ਼ਾਮਲ ਕੀਤੇ ਹਨ
  (log ਵਿੱਚ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` ਹੁੰਦੇ ਹਨ);
- **advisory** — frozen baseline ਦੇ ਮੁਕਾਬਲੇ global total। Inherited drift ਕਿਸੇ ਨਿਰਦੋਸ਼ PR ਨੂੰ ਕਦੇ red ਨਹੀਂ ਕਰਦਾ;
  release reconciliation ਉੱਤੇ drift ਨੂੰ ਮੁੜ freeze ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ headroom job ਵੱਲੋਂ ਨਿਗਰਾਨੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

`check:file-size` base ref ਨੂੰ ਆਪਣੇ ਨਿਯਮਾਂ ਅਨੁਸਾਰ ਵਰਤਦਾ ਹੈ (`scripts/check/check-file-size.mjs`, #8522):
ਇਹ tree ਵਿੱਚ ਹਰ source ਅਤੇ test file ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ, `git show` ਨਾਲ PR base ਉੱਤੇ ਹਰ ਫਾਈਲ ਦੀ
line count ਪੜ੍ਹਦਾ ਹੈ, ਅਤੇ ਕਿਸੇ ਫਾਈਲ ਨੂੰ ਸਿਰਫ਼ ਉਦੋਂ fail ਕਰਦਾ ਹੈ ਜਦੋਂ ਉਹ ਆਪਣੀ baseline ceiling
(`frozen` / `testFrozen`, ਜਾਂ baseline ਤੋਂ ਬਾਹਰਲੀ ਫਾਈਲ ਲਈ `cap` / `testCap`) ਅਤੇ ਆਪਣੇ base
size ਵਿੱਚੋਂ ਵੱਡੀ ਸੀਮਾ ਤੋਂ ਵੱਧ ਵਧਦੀ ਹੈ। ਇਸ ਲਈ base ਉੱਤੇ ਪਹਿਲਾਂ ਹੀ drift ਕਰ ਚੁੱਕੀ ਫਾਈਲ ਕਿਸੇ ਨਿਰਦੋਸ਼ PR ਨੂੰ
ਕਦੇ red ਨਹੀਂ ਕਰਦੀ।

`check:boundary:ratchet` ਆਪਣੇ ਇਕੱਲੇ ਨੰਬਰ ਉੱਤੇ ਵੀ ਇਹੀ ਨਿਯਮ ਲਾਗੂ ਕਰਦਾ ਹੈ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ਇਵੈਂਟਾਂ ਦੌਰਾਨ
`quality.yml` ਦੇ fast-gates ਅਤੇ `ci.yml` ਦਾ lint job ਦੋਵੇਂ PR ਦਾ base SHA ਪਾਸ ਕਰਦੇ ਹਨ, base commit ਨੂੰ
`git archive` ਐਕਸਪੋਰਟ ਤੋਂ ਮਾਪਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ PR ਕੇਵਲ ਉਦੋਂ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਇਸਦੀ
`open-sse → src` edge ਗਿਣਤੀ `metrics.boundaryOpenSseToSrc` ਅਤੇ base ਉੱਤੇ ਮੌਜੂਦ ਗਿਣਤੀ ਵਿੱਚੋਂ ਵੱਡੀ
ਗਿਣਤੀ ਤੋਂ ਵੱਧ ਹੋਵੇ। ceiling ਤੋਂ ਉੱਪਰਲਾ base drift ਰਿਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`base drift herdado`),
ਪਰ ਕਿਸੇ ਬੇਦੋਸ਼ PR ਨੂੰ ਕਦੇ red ਨਹੀਂ ਕਰਦਾ; push → main absolute ceiling ਕਾਇਮ ਰੱਖਦਾ ਹੈ, ਅਤੇ ਹੱਲ ਨਾ ਹੋ ਸਕਣ ਵਾਲਾ
base SHA warning ਦੇ ਨਾਲ ਇਸ ceiling ਉੱਤੇ ਵਾਪਸ ਆ ਜਾਂਦਾ ਹੈ।

ਇੱਕ omni-queue candidate ( `omni-queue/**` ਵੱਲ push, [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ਵੇਖੋ)
ਨੂੰ pull request ਵਾਂਗ ਹੀ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ: ਦੋਵੇਂ workflows candidate base
(`needs.changes.outputs.candidateBase`) ਨੂੰ `--base-ref` ਵਜੋਂ ਪਾਸ ਕਰਦੇ ਹਨ, ਅਤੇ
`check:ts7-diagnostics-ratchet` ਵੀ ਇਸਦੇ ਵਿਰੁੱਧ ਚਲਦਾ ਹੈ। ਨਵੇਂ ਕੋਡ ਵਾਲੇ ਦੋ gates ਲਈ comparison base
ਉਹ SHA ਖੁਦ ਹੈ, top merge commit ਦਾ ਪਹਿਲਾ parent ਨਹੀਂ, ਇਸ ਲਈ batch ਦੀ ਹਰ pull request ਦਾ ਮੁਲਾਂਕਣ ਹੁੰਦਾ ਹੈ।

`workflow_dispatch` runs, release-green sweep ਅਤੇ nightly headroom job ਕੋਲ ਕੋਈ PR base ਨਹੀਂ ਹੁੰਦਾ
ਅਤੇ ਇਹ absolute (global) comparison ਜਾਰੀ ਰੱਖਦੇ ਹਨ। Coverage, duplication ਅਤੇ type-coverage ਫਿਲਹਾਲ
global ਰਹਿੰਦੇ ਹਨ (ਉਨ੍ਹਾਂ ਦੇ tools ਸਸਤੇ ਢੰਗ ਨਾਲ per-file diff ਨਹੀਂ ਬਣਾਉਂਦੇ) — ਇਸੇ ਤਰ੍ਹਾਂ ਸੰਭਾਲੇ ਜਾਣ ਲਈ ਉਮੀਦਵਾਰ।

   `--update` — ਹਰ baseline ਮਾਪੀ ਗਈ value ਉੱਤੇ ਆ ਜਾਂਦਾ ਹੈ।
2. `quality-baseline.json` ਵਿੱਚੋਂ `_policy` ਮਿਟਾਓ (`--require-tighten` ਅਤੇ nightly
   banking ਨੂੰ ਮੁੜ ਸਰਗਰਮ ਕਰਦਾ ਹੈ), `check-openapi-coverage.mjs` ਵਿੱਚ
   `THRESHOLD = 36` (ਜਾਂ ਇਸ ਤੋਂ ਵੱਧ) ਮੁੜ-ਸਥਾਪਿਤ ਕਰੋ।
3. ਜਿੱਥੇ modularization ਨਾਲ ਲਾਭ ਹੋਇਆ ਹੈ, ਉੱਥੇ ਮਾਪੀ ਗਈ value ਤੋਂ ਵੀ ਵੱਧ ਸਖ਼ਤੀ ਲਿਆਓ: file-size `cap`
   ਮੁੜ 1000 (ਜਾਂ 800), coverage floors +5, modularized packages ਲਈ dead exports 0।

## ਰੈਚੇਟ ਬੇਸਲਾਈਨ (`quality-baseline.json`)

ਰੈਚੇਟ ਇੰਜਣ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ

| ਮੈਟ੍ਰਿਕ               | ਦਿਸ਼ਾ  | ਅਰਥ                                        |


`--update` ਫਲੈਗ ਮੌਜੂਦਾ ਮਾਪੀਆਂ ਗਈਆਂ ਕਦਰਾਂ ਨੂੰ `quality-baseline.json` ਵਿੱਚ ਲਿਖਦਾ ਹੈ।
ਸੁਧਾਰ ਨੂੰ ਬੇਸਲਾਈਨ ਵਿੱਚ ਦਰਜ ਕਰਨਾ ਰਿਲੀਜ਼/ਨਾਈਟਲੀ ਕੰਮ ਹੈ, ਫੀਚਰ PR ਦਾ ਨਹੀਂ:
`--require-tighten` (Fase 6A.5) ਸਿਰਫ਼ ਰਿਲੀਜ਼ ਮੋਡ (push, schedule, ਰਿਲੀਜ਼ PR,
ਲੋਕਲ ਰਨ) ਵਿੱਚ ਦਰਜ ਨਾ ਕੀਤੇ ਸੁਧਾਰ ਨੂੰ ਅਸਫਲ ਕਰਦਾ ਹੈ। ਫੀਚਰ PR ਵਿੱਚ (`pr` ਗੇਟ ਮੋਡ)
ਇਹ ਸੁਧਾਰ ਨੂੰ ਜਾਣਕਾਰੀ ਵਜੋਂ ਦਿਖਾਉਂਦਾ ਹੈ ਅਤੇ ਪਾਸ ਹੋ ਜਾਂਦਾ ਹੈ; ਰਿਗ੍ਰੈਸ਼ਨ ਦੋਵਾਂ ਮੋਡਾਂ ਵਿੱਚ
ਅਸਫਲ ਹੁੰਦਾ ਹੈ। velocity ਪੜਾਅ ਦੌਰਾਨ ਇਹ ਹਰ ਥਾਂ ਸਲਾਹਕਾਰ ਹੁੰਦਾ ਹੈ
(`_policy.requireTighten: false`)। ਵੇਖੋ
[ਤਿਆਰ ਕੀਤੀਆਂ ਫਾਈਲਾਂ ਅਤੇ ਰਿਲੀਜ਼ ਸਮੇਂ ਲਿਖੀਆਂ ਜਾਣ ਵਾਲੀਆਂ ਡੈਰੀਵਡ ਬੇਸਲਾਈਨਾਂ](#generated-files-and-derived-baselines-written-at-release)।

### CodeQL ਰੈਚੇਟ: ਰਿਫ੍ਰੈਸ਼ ਅੰਤਰਾਲ ਅਤੇ ਮੈਨੁਅਲ ਟ੍ਰਿਗਰ

`check:codeql-ratchet` **ਰਿਪੋਜ਼ਟਰੀ ਦੀ ਸਥਿਤੀ ਪੜ੍ਹਦਾ ਹੈ, ਜੋ ਸ਼ਡਿਊਲ ਅਨੁਸਾਰ ਰਿਫ੍ਰੈਸ਼ ਹੁੰਦੀ ਹੈ — ਹਰ PR ਲਈ ਨਹੀਂ।**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ਇਹ ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ
`state: configured`, `schedule: weekly`: ਇਹ GitHub ਦਾ ਡਿਫਾਲਟ-ਸੈਟਅੱਪ ਸਕੈਨ ਹੈ, ਹਰ push ਲਈ
ਵਿਸ਼ਲੇਸ਼ਣ ਨਹੀਂ। ਨਤੀਜਾ: ਅਲਰਟ ਠੀਕ ਕਰਨ ਵਾਲਾ PR ਮਰਜ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਅਗਲਾ ਸ਼ਡਿਊਲ ਕੀਤਾ ਸਕੈਨ
ਚੱਲਣ ਤੱਕ ਰੈਚੇਟ ਪੁਰਾਣੀ, ਵੱਧ ਗਿਣਤੀ ਪੜ੍ਹਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਇਹ ਹਰ ਖੁੱਲ੍ਹੇ PR ਵਿੱਚ
ਰਿਗ੍ਰੈਸ਼ਨ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ, ਠੀਕ ਕਰਨ ਵਾਲੇ PR ਦੇ ਆਪਣੇ ਅਗਲੇ PR ਵਿੱਚ ਵੀ, ਜਦ ਤੱਕ ਸਕੈਨ ਨਵੀਂ
ਸਥਿਤੀ ਨਹੀਂ ਲੈ ਲੈਂਦਾ।

**ਮੈਨੁਅਲ ਰਿਫ੍ਰੈਸ਼**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ਵਿਸ਼ਲੇਸ਼ਣ ਨੂੰ
ਦੁਬਾਰਾ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਕੁਝ ਮਿੰਟਾਂ ਵਿੱਚ ਅਲਰਟ ਮੁੜ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਪਹਿਲਾਂ
`.github/workflows/codeql.yml` ਪੜ੍ਹੋ — ਇਸਦਾ ਹੈਡਰ ਦੱਸਦਾ ਹੈ ਕਿ ਇਹ ਸਿਰਫ਼
`workflow_dispatch` ਹੈ **ਕਿਉਂਕਿ ਇਹ GitHub ਦੇ "default setup" ਨਾਲ ਟਕਰਾਉਂਦਾ ਹੈ**
(`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`)।
`push`/`pull_request`/`schedule` ਟ੍ਰਿਗਰ ਮੁੜ ਸਰਗਰਮ ਕਰਨ ਲਈ ਪਹਿਲਾਂ **ਮਾਲਕ ਦੀ ਕਾਰਵਾਈ ਲਾਜ਼ਮੀ ਹੈ**:
Settings → Code security → CodeQL: Default → Advanced। ਉਸ ਸਵਿੱਚ ਤੋਂ ਬਿਨਾਂ
` schedule:` ਟ੍ਰਿਗਰ ਨਾ ਜੋੜੋ — ਇਸ ਨਾਲ ਸਿਰਫ਼ ਅਸਫਲ ਰਨ ਬਣਣਗੇ।

**ਗਿਣਤੀ ਘਟਣ ਤੋਂ ਬਾਅਦ ਬੇਸਲਾਈਨ ਨੂੰ ਕੱਸੋ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ਨਵੀਂ ਮਾਪੀ ਗਈ ਗਿਣਤੀ ਨੂੰ `quality-baseline.json` →
`metrics.codeqlAlerts.value` ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਤਾਂ ਜੋ ਰੈਚੇਟ ਪੁਰਾਣੀ ਉੱਚੀ ਸੀਮਾ ਤੱਕ ਮੁੜ
ਵਧਣ ਵਾਲੇ ਰਿਗ੍ਰੈਸ਼ਨ ਨੂੰ ਚੁੱਪਚਾਪ ਮਨਜ਼ੂਰ ਨਾ ਕਰੇ। ਕੰਮ ਕੀਤਾ ਉਦਾਹਰਨ (2026-09-02/03):
PR #12502 ਨੇ 7 ਅਸਲ ਅਲਰਟ ਠੀਕ ਕੀਤੇ (13 → 6 ਮਾਪੇ ਗਏ ਖੁੱਲ੍ਹੇ ਅਲਰਟ); PR #12530 ਨੇ
ਫ੍ਰੀਜ਼ ਕੀਤੀ ਬੇਸਲਾਈਨ ਨੂੰ ਮਿਲਾਉਣ ਲਈ 11 → 6 ਤੱਕ ਕੱਸਿਆ; ਬਾਕੀ 6 ਨੂੰ ਫਿਰ ਹਰੇਕ ਅਲਰਟ ਲਈ
ਕਾਰਨ ਦਰਜ ਕਰਕੇ dismiss ਕੀਤਾ ਗਿਆ ਅਤੇ ਖੁੱਲ੍ਹੇ ਅਲਰਟ 0 ਰਹਿ ਗਏ।

**Dismissal ਓਪਰੇਟਰ ਦਾ ਫੈਸਲਾ ਹੈ (Hard Rule #14)** — ਕਿਸੇ ਵੀ CodeQL ਅਲਰਟ ਨੂੰ

ਉਸ sanitizer ਲਈ `false positive` ਜਿਸਨੂੰ CodeQL ਨਹੀਂ ਦੇਖ ਸਕਦਾ (ਮਿਸਾਲ:

ਜੌਬ ਬਿਨਾਂ ਨਿਗਰਾਨੀ ਦੇ ਬੇਸਲਾਈਨਾਂ ਵਿੱਚ ਲਿਖਦੀ ਹੈ, ਇਸ ਲਈ `verify-ratchet-bank.mjs` ਹੀ ਇਸਨੂੰ

ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਜੌਬ ਨੂੰ ਰੋਕ ਦਿੰਦਾ ਹੈ** — ਕੋਈ PR ਨਹੀਂ ਖੋਲ੍ਹਦਾ — ਜਦੋਂ ਤੱਕ ਹਰ ਤਬਦੀਲੀ ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਇੱਕ ਨਾ ਹੋਵੇ:

## ਮਨਜ਼ੂਰ-ਸੂਚੀ ਨੀਤੀ

ਹਰੇਕ ਗੇਟ ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਉਲੰਘਣਾਵਾਂ ਕਾਰਨ ਫੇਲ੍ਹ ਨਹੀਂ ਹੋ ਸਕਦਾ, ਇੱਕ ਜਮੀ ਹੋਈ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਵਰਤਦਾ ਹੈ
(ਜਿਵੇਂ, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ਨੀਤੀ ਇਹ ਹੈ:

**ਮੂਲ ਕਾਰਨ ਠੀਕ ਕਰੋ; ਮਨਜ਼ੂਰ-ਸੂਚੀ ਦੀ ਵਰਤੋਂ ਸਿਰਫ਼ ਉਦੋਂ ਕਰੋ ਜਦੋਂ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੋਵੇ ਅਤੇ
ਉਸੇ PR ਵਿੱਚ ਠੀਕ ਨਾ ਕੀਤੀ ਜਾ ਸਕੇ।**

ਮਨਜ਼ੂਰ-ਸੂਚੀ ਵਿੱਚ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰਦੇ ਸਮੇਂ:

1. ਜਾਇਜ਼ ਠਹਿਰਾਉਣ ਵਾਲੀ ਟਿੱਪਣੀ ਸ਼ਾਮਲ ਕਰੋ।
2. ਟ੍ਰੈਕਿੰਗ ਇਸ਼ੂ ਦਾ ਹਵਾਲਾ ਦਿਓ (ਜਿਵੇਂ, `// #3498 — Phase 2 feature, not yet implemented`)।
3. ਉਲੰਘਣਾ ਠੀਕ ਕਰਨ ਵਾਲੇ ਉਸੇ PR ਵਿੱਚ ਐਂਟਰੀ ਹਟਾਓ — ਇੱਕ ਪੁਰਾਣੀ ਐਂਟਰੀ ਜੋ ਹੁਣ ਸਰਗਰਮ ਉਲੰਘਣਾ ਨੂੰ
   ਦਬਾਉਂਦੀ ਨਹੀਂ, ਆਪਣੇ ਆਪ ਵਿੱਚ ਇੱਕ ਖਾਮੀ ਹੈ (ਲਾਗੂ ਹੋਣ ਤੋਂ ਬਾਅਦ 6A.3 stale-enforcement
   ਇੱਕ ਅਨਾਥ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਐਂਟਰੀ ਉੱਤੇ ਗੇਟ ਫੇਲ੍ਹ ਕਰੇਗਾ)।

ਟੈਸਟ ਤੇਜ਼ੀ ਨਾਲ ਪਾਸ ਕਰਵਾਉਣ ਲਈ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਐਂਟਰੀਆਂ ਨਾ ਸ਼ਾਮਲ ਕਰੋ। ਵਧਦੀ ਹੋਈ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਦੇ ਨਾਲ ਹਰਾ ਗੇਟ
ਗੁਣਵੱਤਾ ਦਾ ਇੱਕ ਝੂਠਾ ਭਰੋਸਾ ਹੁੰਦਾ ਹੈ।

### ਜਦੋਂ ਤੁਹਾਡੇ PR ਵਿੱਚ ਕੋਈ ਗੇਟ ਫੇਲ੍ਹ ਹੋਵੇ

1. **ਗੇਟ ਦਾ ਆਉਟਪੁੱਟ ਧਿਆਨ ਨਾਲ ਪੜ੍ਹੋ** — ਇਹ ਤੁਹਾਨੂੰ ਬਿਲਕੁਲ ਦੱਸਦਾ ਹੈ ਕਿ ਕਿਹੜੀ ਫ਼ਾਈਲ ਜਾਂ ਸਿੰਬਲ ਨੇ
   ਨਿਯਮ ਦੀ ਉਲੰਘਣਾ ਕੀਤੀ ਹੈ।
2. **ਉਲੰਘਣਾ ਠੀਕ ਕਰੋ** — ਜ਼ਿਆਦਾਤਰ ਗੇਟ ਨਿਰਧਾਰਿਤ ਫ਼ਾਈਲ-ਸਿਸਟਮ ਜਾਂਚਾਂ ਹੁੰਦੀਆਂ ਹਨ ਜੋ ਕੋਡ ਸਹੀ ਹੁੰਦੇ ਹੀ
   ਪਾਸ ਹੋ ਜਾਂਦੀਆਂ ਹਨ।
3. **ਜੇ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੈ** (ਅਰਥਾਤ, ਤੁਸੀਂ ਇਸਨੂੰ ਸ਼ਾਮਲ ਨਹੀਂ ਕੀਤਾ ਪਰ ਗੇਟ ਹੁਣ ਇਸਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ):
   ਜਾਇਜ਼ ਠਹਿਰਾਉਣ ਵਾਲੀ ਟਿੱਪਣੀ ਅਤੇ ਟ੍ਰੈਕਿੰਗ ਇਸ਼ੂ ਦੇ ਨਾਲ ਇੱਕ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰੋ।
4. **ਜੇ ਗੇਟ ਇੱਕ ਰੈਚੇਟ ਹੈ** (ਕਵਰੇਜ, ESLint ਚੇਤਾਵਨੀਆਂ, ਡੁਪਲੀਕੇਸ਼ਨ, ਜਟਿਲਤਾ):
   ਤੁਹਾਡੀ ਤਬਦੀਲੀ ਨੇ ਮੈਟਰਿਕ ਨੂੰ ਖ਼ਰਾਬ ਕੀਤਾ ਹੈ। ਅੰਦਰੂਨੀ ਸਮੱਸਿਆ ਠੀਕ ਕਰੋ, ਜਾਂ (ਬਹੁਤ ਘੱਟ ਮਾਮਲਿਆਂ ਵਿੱਚ)
   `npm run quality:ratchet -- --update` ਚਲਾਓ, ਜੇ ਤਬਦੀਲੀ ਜਾਣ-ਬੁੱਝ ਕੇ ਕੀਤੀ ਗਈ ਹੈ ਅਤੇ ਮੈਟਰਿਕ ਦਾ ਘਟਣਾ ਸਵੀਕਾਰਯੋਗ ਹੈ —
   ਪਰ PR ਦੇ ਵੇਰਵੇ ਵਿੱਚ ਇਸਦਾ ਕਾਰਨ ਦਰਜ ਕਰੋ।
5. **ਸਲਾਹਕਾਰੀ ਗੇਟ** (`continue-on-error: true`) ਜਾਣਕਾਰੀ ਲਈ ਹੁੰਦੇ ਹਨ — ਇਹ
   ਮਰਜ ਨੂੰ ਰੋਕਦੇ ਨਹੀਂ, ਪਰ CI ਸਾਰ ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦੇ ਹਨ। ਫਿਰ ਵੀ ਇਨ੍ਹਾਂ ਨੂੰ ਠੀਕ ਕਰੋ।

## ਨਵਾਂ ਗੇਟ ਸ਼ਾਮਲ ਕਰਨਾ

1. `scripts/check/check-<name>.mjs` (ਜਾਂ `.ts`) ਬਣਾਓ। ਨੀਤੀ ਗੇਟ 0/1 ਨਾਲ ਬੰਦ ਹੁੰਦੇ ਹਨ।
   ਰੈਚਿਟ-ਸ਼ੈਲੀ ਗੇਟ `collect-metrics.mjs` ਰਾਹੀਂ `quality-metrics.json` ਵਿੱਚ ਇੱਕ ਮਾਪਦੰਡ ਲਿਖਦੇ ਹਨ।
2. `package.json` ਵਿੱਚ `"check:<name>": "node scripts/check/check-<name>.mjs"` ਸ਼ਾਮਲ ਕਰੋ।
3. ਇਸਨੂੰ `.github/workflows/ci.yml` ਵਿੱਚ ਢੁਕਵੀਂ ਜੌਬ ਹੇਠ ਜੋੜੋ
   (ਨੀਤੀ → `lint` ਜਾਂ `docs-sync-strict`; ਰੈਚਿਟ → `quality-gate`)।
4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

### ਮਰਜ / ਡੀਡੁਪ (ਮਕੈਨਿਕਲ, ਘੱਟ ਜੋਖ਼ਮ)

- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼ ਮਰਜ ਨਹੀਂ।** `audit:deps` ਸਾਰੀਆਂ ਪੰਜ ਲੌਕਫ਼ਾਈਲਾਂ ਵਿੱਚ critical advisories ਅਤੇ ਅਧੂਰੇ audits ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ, ਜਦਕਿ ਮੌਜੂਦਾ ਨੀਤੀ ਅਧੀਨ high advisories ਨੂੰ ਚੇਤਾਵਨੀਆਂ ਵਜੋਂ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਚੈੱਕ-ਇਨ ਕੀਤੇ baseline ਦੇ ਮੁਕਾਬਲੇ _regression_ ਹੋਣ ’ਤੇ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ ਅਤੇ ਲੋੜ ਪੈਣ ’ਤੇ ਗੁੰਮ ਮਾਪਾਂ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਅਰਥ-ਵਿਗਿਆਨ ਵੱਖਰੇ ਹਨ — `audit:deps` ਹਟਾਉਣ ਨਾਲ absolute critical gate ਅਤੇ ਸੁਤੰਤਰ package audit receipts ਖਤਮ ਹੋ ਜਾਣਗੇ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਸਾਈਕਲ ਡਿਟੈਕਸ਼ਨ** — ✅ **ਪੂਰਾ** (#15159 G-01/G-02)। ਇੱਥੇ ਪੁਰਾਣੇ ਟੈਕਸਟ ਵਿੱਚ `check:cycles` ਨੂੰ “green, curated” ਗੇਟ ਕਿਹਾ ਗਿਆ ਸੀ ਅਤੇ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖਣ ਦਾ ਕਾਰਨ ਦਿੱਤਾ ਗਿਆ ਸੀ ਕਿਉਂਕਿ `check:circular-deps` (dpdm) ਨੇ 91 cycles ਰਿਪੋਰਟ ਕੀਤੇ ਸਨ। ਉਹ ਹਰਾ ਨਤੀਜਾ **ਝੂਠਾ ਹਰਾ** ਸੀ: `check:cycles` ਨੇ 5 subdirectories (450 files) ਸਕੈਨ ਕੀਤੀਆਂ, ਸਿਰਫ਼ static `import|export … from` ਨਾਲ ਮੇਲ ਖਾਧਾ ਅਤੇ ਹਰ `@/` ਅਤੇ `@omniroute/open-sse/` specifier ਨੂੰ ਛੱਡ ਦਿੱਤਾ, ਇਸ ਲਈ ਇਹ ਰਿਪੋ ’ਤੇ ਹਾਵੀ dynamic-import + alias cycles ਨੂੰ ਦੇਖ ਹੀ ਨਹੀਂ ਸਕਿਆ। ਠੀਕ ਕੀਤਾ ਗਿਆ: ਹੁਣ ਗੇਟ `src` + `open-sse` (5023 files) ਵਿੱਚ ਜਾਂਦਾ ਹੈ, TypeScript AST ਤੋਂ specifiers ਇਕੱਠੇ ਕਰਦਾ ਹੈ (ਇਸ ਲਈ `import("…")` ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ type-position `typeof import("…")` ਨਹੀਂ) ਅਤੇ tsconfig `paths` ਨੂੰ resolve ਕਰਦਾ ਹੈ। ਇਸਨੂੰ 0 ਨਹੀਂ, **14** cycles ਮਿਲਦੇ ਹਨ। ਕਿਉਂਕਿ 14 ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ cycles ਨੂੰ gate PR ਵਿੱਚ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, `check:cycles` ਹੁਣ ਇੱਕ **ਰੈਸ਼ਟ** ਹੈ (`--ratchet`, `quality-baseline.json` ਵਿੱਚ ceiling `metrics.cycles.value = 14`, `direction: down`) — ਇਹ ਕਿਸੇ ਵੀ _regression_ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ ਅਤੇ ਗਿਣਤੀ ਸਿਰਫ਼ ਘਟ ਸਕਦੀ ਹੈ। CI `npm run check:cycles:ratchet` ਚਲਾਉਂਦਾ ਹੈ। ਬਰਨ-ਡਾਊਨ **A-01** ਦੇ ਨਾਲ ਹੋਵੇਗਾ। `check:circular-deps` (dpdm) ਵਿਆਪਕ ਦੂਜੀ ਰਾਏ ਵਜੋਂ ਸਲਾਹਕਾਰੀ ਰਹਿੰਦਾ ਹੈ।
- **ਕੰਪਲੈਕਸਿਟੀ** — ✅ **ਪੂਰਾ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, ruleId ਅਨੁਸਾਰ ਗਿਣਤੀ ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive baselines ਸੁਤੰਤਰ ਰਹਿਣ; ਵਿਅਕਤੀਗਤ `check:complexity` / `check:cognitive-complexity` ਸਥਾਨਕ `--update` ਲਈ ਬਣੇ ਰਹਿੰਦੇ ਹਨ।
