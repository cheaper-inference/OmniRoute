ਇਹ ਦਸਤਾਵੇਜ਼ OmniRoute ਵਿੱਚ ਸਾਰੇ CI ਗੁਣਵੱਤਾ ਗੇਟਾਂ ਲਈ ਪ੍ਰਮਾਣਿਕ ਹਵਾਲਾ ਹੈ।
ਇਹ ਹਰ ਗੇਟ ਦਾ ਵਰਣਨ ਕਰਦਾ ਹੈ, ਇਹ ਕੀ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਇਹ ਕਿਸ CI ਜੌਬ ਵਿੱਚ ਚੱਲਦਾ ਹੈ, ਕੀ ਇਹ
ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਇਨਵੈਂਟਰੀ ਅਤੇ ਐਗਜ਼ਿਕਿਊਸ਼ਨ ਪ੍ਰੋਫ਼ਾਈਲ

### ਉਮੀਦਵਾਰ ਦਾਖਲਾ

CI ਅਤੇ Quality Gates ਵਰਕਫ਼ਲੋ ਹਰ ਇੱਕ ਇੱਕ ਸਥਿਰ ਫ਼ੈਸਲਾ ਜਾਰੀ ਕਰਦੇ ਹਨ: `Gate / CI` ਅਤੇ
`Gate / Quality`। ਉਹਨਾਂ ਦੀ ਵਰਜਨਬੱਧ ਦਾਖਲਾ ਨੀਤੀ ਹਰ ਅੱਪਸਟ੍ਰੀਮ ਜੌਬ ਨੂੰ ਲਾਜ਼ਮੀ ਜਾਂ
ਸਲਾਹਕਾਰ ਵਜੋਂ ਦਰਜ ਕਰਦੀ ਹੈ। ਲਾਗੂ ਹੋਣ ਵਾਲੀ ਲਾਜ਼ਮੀ ਜੌਬ ਦਾ ਸਫ਼ਲ ਹੋਣਾ ਜ਼ਰੂਰੀ ਹੈ: ਗੁੰਮ,
ਰੱਦ ਕੀਤੇ, ਛੱਡੇ ਗਏ, ਬਕਾਇਆ ਅਤੇ ਅਣਜਾਣ ਨਤੀਜੇ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦੇ। ਵੈਧ
docs-only ਜਾਂ catalog-only ਵਰਗੀਕਰਨ ਕੋਡ ਲੇਨ ਨੂੰ ਗੈਰ-ਲਾਗੂ ਬਣਾ ਸਕਦੀ ਹੈ;
ਡਰਾਫ਼ਟ PR ਸਵੀਕਾਰਿਆ ਉਮੀਦਵਾਰ ਨਹੀਂ ਹੈ। `hotfix` ਲੇਬਲ ਸਬੂਤ ਤੋਂ ਛੋਟ ਨਹੀਂ ਦਿੰਦਾ।

ਦੋਵੇਂ ਵਰਕਫ਼ਲੋ main/release ਬ੍ਰਾਂਚਾਂ ਵਿੱਚ ਜਾਣ ਵਾਲੇ PRs, `main` ਵੱਲ ਪੁਸ਼,
ਮੈਨੂਅਲ ਡਿਸਪੈਚ ਅਤੇ merge-group ਇਵੈਂਟਾਂ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। ਪੁਸ਼, ਡਿਸਪੈਚ ਅਤੇ merge-group
ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦੇ ਹਨ। `release/**` ਵੱਲ ਪੁਸ਼ ਉਹਨਾਂ ਨੂੰ ਸ਼ੁਰੂ ਨਹੀਂ ਕਰਦੇ (2026-10-18):
ਹਰ ਤਬਦੀਲੀ ਆਪਣੇ PR ਉੱਤੇ ਪਹਿਲਾਂ ਹੀ ਮੈਟ੍ਰਿਕਸ ਚਲਾ ਚੁੱਕੀ ਹੁੰਦੀ ਹੈ ਅਤੇ ਮਿਲਿਆ ਹੋਇਆ ਸੰਯੋਗ
Release-Green ਦੀ ਜ਼ਿੰਮੇਵਾਰੀ ਹੈ (`docs/ops/RUNNER_BOX.md` → Hosted lane)। ਫੋਰਕ
ਅਤੇ merge groups ਉਹਨਾਂ ਜੌਬਾਂ ਲਈ hosted runners ਵਰਤਦੇ ਹਨ ਜੋ ਨਹੀਂ ਤਾਂ self-hosted
runners ਚੁਣਦੇ; ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਯਥੇਸ਼ਟ hosted ਸਮਰੱਥਾ ਦੀ ਪੁਸ਼ਟੀ ਹੋਣੀ ਚਾਹੀਦੀ ਹੈ।

ਇੱਕ ਆਮ PR ਤੇਜ਼ ਚੋਣ ਚਲਾਉਂਦਾ ਹੈ। ਦਾਖਲਾ ਨੀਤੀ ਦੀਆਂ `full-code` ਅਤੇ `full-code-e2e` ਲੇਨਾਂ
(E2E, ਇੰਟੀਗ੍ਰੇਸ਼ਨ, ਪੈਕੇਜ ਆਰਟੀਫੈਕਟ, Electron smoke, Bun SQLite, ecosystem
ਅਤੇ protocol clients) ਸਿਰਫ਼ Mergify queue ਡਰਾਫ਼ਟ ਉੱਤੇ ਜਾਂ ਪੂਰੇ ਰਨ ਵਿੱਚ ਚਲਦੀਆਂ ਹਨ:
`gh workflow run ci.yml --ref <branch>`।

ਹਰ JSON ਰਸੀਦ ਚੈੱਕ-ਆਉਟ ਕੀਤੇ SHA, ਵਰਕਫ਼ਲੋ ਰਨ ਅਤੇ ਕੋਸ਼ਿਸ਼ ਦੀ ਪਛਾਣ ਕਰਦੀ ਹੈ।
CLI ਚੈੱਕਆਉਟ/ਇਵੈਂਟ SHA ਦੇ ਅਣਮੈਚ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਵਰਕਫ਼ਲੋ ਟੈਸਟ ਨੀਤੀ ਮੈਂਬਰਸ਼ਿਪ ਨੂੰ
ਵਰਡਿਕਟ ਜੌਬ ਦੀ `needs` ਸੂਚੀ ਨਾਲ ਬੰਨ੍ਹਦੇ ਹਨ, ਤਾਂ ਜੋ ਨਵੀਂ ਜਾਂ ਹਟਾਈ ਗਈ ਲੇਨ ਚੁੱਪਚਾਪ
ਗਾਇਬ ਨਾ ਹੋ ਸਕੇ। ਰਸੀਦਾਂ ਸਿਰਫ਼ ਆਪਣੇ ਵਰਕਫ਼ਲੋ ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ, ਪ੍ਰਕਾਸ਼ਨ,
ਡਿਪਲੌਇਮੈਂਟ ਜਾਂ ਮੌਜੂਦਾ ਸਲਾਹਕਾਰ ਸਕੈਨਰ ਦੇ ਅੰਦਰੂਨੀ ਹਿੱਸਿਆਂ ਨੂੰ ਨਹੀਂ। ਬ੍ਰਾਂਚ ਨਿਯਮਾਂ ਵਿੱਚ
ਦੋਵੇਂ ਚੈੱਕ ਨਾਮ ਸਰਗਰਮ ਕਰਨਾ ਇੱਕ ਵੱਖਰੀ ਪ੍ਰਸ਼ਾਸਕੀ ਤਬਦੀਲੀ ਹੈ; ਇਹ ਜੌਬਾਂ ਜੋੜਨ ਨਾਲ ਆਪਣੇ ਆਪ
ਕੋਈ ਬ੍ਰਾਂਚ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਹੁੰਦੀ।

### Merge queue

`queue` ਲੇਬਲ ਇੱਕ PR ਨੂੰ Mergify queue (`.mergify.yml`) ਵਿੱਚ ਭੇਜਦਾ ਹੈ। Mergify
`mergify/merge-queue/` ਬ੍ਰਾਂਚ ਉੱਤੇ ਇੱਕ ਡਰਾਫ਼ਟ PR ਖੋਲ੍ਹਦਾ ਹੈ, CI ਉੱਥੇ ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦੀ ਹੈ,
ਅਤੇ ਮੂਲ PR ਤਦੋਂ ਮਿਲਦਾ ਹੈ ਜਦੋਂ `Gate / CI`, `Gate / Quality` ਅਤੇ
`Merge integrity (changelog + generated skills)` ਪਾਸ ਹੋ ਜਾਣ।

Mergify ਆਪਣਾ queue ਸਾਰ ਡਰਾਫ਼ਟ ਦੇ ਵੇਰਵੇ ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਅਤੇ ਹੋਰ ਐਪਾਂ ਵੀ ਇਸਨੂੰ ਸੋਧ ਸਕਦੀਆਂ ਹਨ।
ਅਜਿਹੇ ਡਰਾਫ਼ਟ ਉੱਤੇ `pull_request` `edited` ਇਵੈਂਟ ਆਪਣਾ concurrency group
(`-queue-edit-<run_id>`) ਲੈਂਦਾ ਹੈ, ਇਸ ਲਈ ਇਹ ਡਰਾਫ਼ਟ ਦੇ ਅਸਲ ਰਨ ਨੂੰ ਰੱਦ ਨਹੀਂ ਕਰ ਸਕਦਾ,
ਅਤੇ ਗੇਟ ਅਤੇ ਮੈਟ੍ਰਿਕਸ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ। ਸਿਰਫ਼ `Merge integrity` ਫਿਰ ਵੀ ਚਲਦਾ ਹੈ।
ਛੱਡੀ ਗਈ ਗੇਟ ਜੌਬ ਇੱਕ ਵੱਖਰਾ ਚੈੱਕ ਨਾਮ ਰੱਖਦੀ ਹੈ, ਕਿਉਂਕਿ Mergify ਛੱਡੇ ਗਏ
`Gate / CI` ਨੂੰ ਅਸਫ਼ਲ ਚੈੱਕ ਵਜੋਂ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ PR ਨੂੰ queue ਵਿੱਚੋਂ ਕੱਢ ਦਿੰਦਾ ਹੈ।

Dequeue ਤੋਂ ਬਾਅਦ, ਪੁਸ਼ ਹਮੇਸ਼ਾ PR ਨੂੰ ਮੁੜ queue ਵਿੱਚ ਨਹੀਂ ਪਾਉਂਦਾ। ਇਸ ਉੱਤੇ
`@mergifyio queue` ਟਿੱਪਣੀ ਕਰੋ।

### ਸਵੀਕ੍ਰਿਤੀ ਰਿਡਿਊਸਰ ਵਿੱਚ ਸੰਭਾਲਿਆ ਸਬੂਤ

`scripts/quality/validate-release-acceptance.mjs` ਦਿੱਤੀ ਗਈ ਯੋਜਨਾ ਅਤੇ ਉਸਦੇ
ਮੈਨੀਫੈਸਟਾਂ ਨੂੰ ਘਟਾਉਂਦਾ ਹੈ; ਇਹ ਸਥਾਪਤ ਨਹੀਂ ਕਰਦਾ ਕਿ ਯੋਜਨਾ ਪੂਰੀ ਰਿਲੀਜ਼ ਪਾਈਪਲਾਈਨ ਨੂੰ
ਕਵਰ ਕਰਦੀ ਹੈ। ਇਸ ਦੀਆਂ ਰਿਪੋਰਟਾਂ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ `releaseAcceptance: false` ਸੈੱਟ
ਕਰਦੀਆਂ ਹਨ, ਭਾਵੇਂ ਉਹ ਯੋਜਨਾ `VERIFIED` ਹੋਵੇ। `release-acceptance.yml` ਵਰਕਫ਼ਲੋ ਹਾਲੇ ਵੀ
ਅਸਲ build, package, boot ਜਾਂ promotion ਰਸੀਦਾਂ ਦੀ ਥਾਂ shadow fixtures ਵਰਤਦਾ ਹੈ।

CLI ਨੂੰ ਸੰਭਾਲੇ ਹੋਏ ਸਬੂਤ ਦੀ ਪੁਸ਼ਟੀ ਕਰਨ ਲਈ `--evidence-root` ਲਾਜ਼ਮੀ ਚਾਹੀਦਾ ਹੈ।
ਫ਼ਾਈਲਾਂ ਨੂੰ `<evidence-root>/<artifact_id>/<member>` ਵਜੋਂ ਰਿਜ਼ਾਲਵ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ
SHA-256 ਵਜੋਂ ਹੈਸ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਸਬੂਤ ਤੋਂ ਬਿਨਾਂ PASS ਰਿਕਾਰਡ, ਗੁੰਮ ਜਾਂ ਬਦਲੀ ਹੋਈ
ਫ਼ਾਈਲ, ਅਸੁਰੱਖਿਅਤ ਪਾਥ ਜਾਂ ਸਿਮਲਿੰਕ ਤਸਦੀਕ ਨੂੰ ਰੋਕਦਾ ਹੈ। ਗੁੰਮ ਫ਼ਾਈਲਾਂ ਖਾਲੀ ਸਫ਼ਲ ਲੌਗਾਂ
ਦੇ ਸਮਾਨ ਨਹੀਂ ਹਨ। ਮੌਜੂਦਾ SHA/run/attempt ਜਾਂਚਾਂ ਸੁਤੰਤਰ ਰਹਿੰਦੀਆਂ ਹਨ: ਮਿਲਦੇ ਬਾਈਟ
ਪੁਰਾਣੀ ਰਸੀਦ ਨੂੰ ਠੀਕ ਨਹੀਂ ਕਰ ਸਕਦੇ। ਫ਼ਾਈਲ ਦੀ ਅਖੰਡਤਾ ਐਗਜ਼ਿਕਿਊਸ਼ਨ ਦੀ ਪ੍ਰਮਾਣਿਕਤਾ ਜਾਂ
ਆਰਟੀਫੈਕਟ ਪ੍ਰਮੋਸ਼ਨ ਦਾ ਸਬੂਤ ਨਹੀਂ ਹੈ।

### ਸਥਿਰ ਸਕੈਨ ਇਨਵੈਂਟਰੀ

ਵਰਜਨਬੱਧ npm-alias ਇਨਵੈਂਟਰੀ ਅਤੇ static-scan ਮੈਂਬਰਸ਼ਿਪ
`config/quality/gate-manifest.json` ਵਿੱਚ ਰਹਿੰਦੇ ਹਨ। `package.json` ਦੇ ਮੁਕਾਬਲੇ
ਸਕ੍ਰਿਪਟ ਨਾਮਾਂ ਅਤੇ ਸਹੀ ਕਮਾਂਡਾਂ ਦੀ ਜਾਂਚ ਕਰਨ ਲਈ `npm run check:gate-manifest` ਚਲਾਓ;
ਜੋੜ, ਹਟਾਉਣ ਅਤੇ ਕਮਾਂਡ ਵਿੱਚ ਤਬਦੀਲੀ ਸਥਾਨਕ ਹੁੱਕ ਅਤੇ CI ਦੇ change-classification ਜੌਬਾਂ
ਦੋਵਾਂ ਨੂੰ ਅਸਫ਼ਲ ਕਰਦੇ ਹਨ। ਇੱਕ alias ਕੋਈ ਵਰਕਫ਼ਲੋ ਜੌਬ, ਮੈਟ੍ਰਿਕਸ ਇੰਸਟੈਂਸ ਜਾਂ ਟੈਸਟ ਕੇਸ
ਨਹੀਂ ਹੈ: ਇਹ ਗਿਣਤੀਆਂ ਪਰਸਪਰ ਬਦਲਵਾਂ ਵਜੋਂ ਪੇਸ਼ ਨਹੀਂ ਕੀਤੀਆਂ ਜਾਣੀਆਂ ਚਾਹੀਦੀਆਂ।

ਚੁਣੇ ਹੋਏ aliases ਨੂੰ ਚਲਾਏ ਬਿਨਾਂ ਜਾਂਚਣ ਲਈ `npm run quality:scan -- --list` ਜਾਂ
`npm run quality:scan:fast -- --list` ਵਰਤੋ। ਰਨਰ npm ਐਂਟਰੀਪੌਇੰਟ ਨੂੰ ਬੁਲਾਉਂਦਾ ਹੈ,
ਇਸ ਲਈ ਇਸਦਾ ਰਨਟਾਈਮ (ਜਿੱਥੇ ਕਨਫ਼ਿਗਰ ਕੀਤਾ ਹੋਵੇ ਉੱਥੇ Bun ਸਮੇਤ) ਸੁਰੱਖਿਅਤ ਰਹਿੰਦਾ ਹੈ।
ਮੈਨੀਫੈਸਟ ਉਹਨਾਂ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਤੋਂ ਬਾਹਰਲੇ aliases ਨੂੰ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ ਬੁਲਾਏ ਜਾਣ ਵਾਲੇ ਵਜੋਂ
ਦਰਜ ਕਰਦਾ ਹੈ, ਅਤੇ read-only scan ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵਿੱਚ maintenance commands ਮਨਾਹੀ ਹਨ।

ਇਹ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਸਿਰਫ਼ static scan ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ। ਇਹ ਉਤਪਾਦ ਟੈਸਟਾਂ, ਕਵਰੇਜ,
ਪੈਕੇਜਿੰਗ, ਬਾਹਰੀ ਜਾਂਚਾਂ ਜਾਂ ਕਿਸੇ ਉਮੀਦਵਾਰ ਦੀ ਪੂਰੀ ਰਿਲੀਜ਼ ਸਵੀਕ੍ਰਿਤੀ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਨਹੀਂ
ਕਰਦੀਆਂ। ਵਰਕਫ਼ਲੋ ਦਾਖਲਾ ਸੰਬੰਧਿਤ `config/quality/admission-policy.json` ਅਤੇ
`scripts/quality/admission-verdict.mjs` ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। Release-observer
ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵੱਖਰੀਆਂ ਰਹਿੰਦੀਆਂ ਹਨ; ਉਹਨਾਂ ਦੀਆਂ ਲਾਗੂ ਜਾਂਚਾਂ ਅਤੇ ਰਸੀਦਾਂ ਦੀ ਸੁਤੰਤਰ ਤੌਰ ਉੱਤੇ
ਜਾਂਚ ਕਰੋ। ਪੂਰੇ observer ਦੀਆਂ static commands
`config/quality/release-green-static-profile.json` ਵਿੱਚ ਘੋਸ਼ਿਤ ਹਨ, ਜਿਨ੍ਹਾਂ ਵਿੱਚ
`audit:deps`, mutation-test selection ਅਤੇ translation checks ਸ਼ਾਮਲ ਹਨ। ਲੋਡਰ
package.json ਦੇ ਮੁਕਾਬਲੇ npm ਕਮਾਂਡਾਂ ਅਤੇ ਮਾਡਲ ਕੀਤੀਆਂ CI/Quality ਘੋਸ਼ਣਾਵਾਂ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ;
ਇਹ drift ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ ਅਤੇ shell tokens ਨੂੰ arguments ਵਜੋਂ ਚਲਾਉਂਦਾ ਨਹੀਂ। ਲਾਜ਼ਮੀ
scanner ਦਾ SKIP/INCOMPLETE ਆਉਟਪੁੱਟ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦਾ। ਪ੍ਰੋਫ਼ਾਈਲ ਆਪਣੇ ਬਾਹਰੀ
ਬਾਹਰਕਰਨ ਦਰਜ ਕਰਦਾ ਹੈ ਅਤੇ hosted coverage, test matrices, package ਜਾਂ deployment
ਸਬੂਤ ਦੀ ਥਾਂ ਨਹੀਂ ਲੈਂਦਾ। ਹੇਠਾਂ ਦਿੱਤੀ ਗੱਥਾਤਮਕ ਇਨਵੈਂਟਰੀ ਇੱਕ ਹਵਾਲਾ ਹੈ, ਇਸ ਗੱਲ ਦਾ ਸਬੂਤ
ਨਹੀਂ ਕਿ ਕੋਈ ਗੇਟ ਅਸਲ ਵਿੱਚ ਚੱਲਿਆ ਸੀ।

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (policy gates) ਅਤੇ `scripts/quality/` (ratchet engine)
ਦੇ ਅਧੀਨ ਰਹਿੰਦੀਆਂ ਹਨ। CI ਦਾ ਸਰੋਤ-ਸੱਚ `.github/workflows/ci.yml` ਹੈ।

### ਰਿਲੀਜ਼ PR fast-path (`quality.yml`)

`.github/workflows/quality.yml` main/release PRs, `main` ਵੱਲ ਪੁਸ਼,
ਡਿਸਪੈਚ ਅਤੇ merge groups ਉੱਤੇ CI ਨੂੰ ਪੂਰਾ ਕਰਦਾ ਹੈ। PRs ਪਾਥ-ਫ਼ਿਲਟਰ ਕੀਤੀਆਂ ਤੇਜ਼
ਜਾਂਚਾਂ ਵਰਤਦੇ ਹਨ। ਸਥਾਈ ਤੌਰ ਉੱਤੇ ਅਸਮਰੱਥ duplicate build ਹਟਾ ਦਿੱਤਾ ਗਿਆ ਹੈ; ਅਸਲ
build/package/boot ਜਾਂਚਾਂ CI ਵਿੱਚ ਹੀ ਰਹਿੰਦੀਆਂ ਹਨ। unit suite ਅਤੇ vitest ਸਿਰਫ਼ CI ਵਿੱਚ
ਚਲਦੇ ਹਨ (`Unit Tests (N/8)` ਅਤੇ `Vitest`)।

| ਕੰਮ                                              | ਦਾਇਰਾ                                                                                                           | ਬਲਾਕਿੰਗ         |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | --------------- |
| `Docs Gates (fast-path)`                         | Docs/code PRs; API docs refs ਅਤੇ docs-all                                                                       | ਹਾਂ             |
| `Fast Quality Gates`                             | Code PRs; static checks, typecheck, dashboard typecheck, ਪ੍ਰਭਾਵਿਤ unit tests, ਭੁੱਲੇ ਹੋਏ sibling tests (ਸਲਾਹਕਾਰ) |
| `No new ESLint warnings`                         | Code PRs; suppressions-aware lint guard                                                                         | ਹਾਂ, forks ਸਮੇਤ |
| `Merge integrity (changelog + generated skills)` | Non-draft PRs; changelog ਅਤੇ generated skill sync                                                               | ਹਾਂ, forks ਸਮੇਤ |

#### ਭੁੱਲੇ ਹੋਏ sibling tests ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` ਦੇ ਸਲਾਹਕਾਰ ਪੜਾਅ ਵਜੋਂ ਚੱਲਦਾ ਹੈ ਅਤੇ
test-impact map ਦੇ ਪਿੱਛੇ ਵਾਲੇ import resolver ਨੂੰ ਦੁਬਾਰਾ ਵਰਤਦਾ ਹੈ।
ਹਰੇਕ ਬਦਲੇ ਹੋਏ production module ਲਈ, ਇਹ ਨਿਰਧਾਰਤ
`changed module/symbol -> static consumer -> candidate sibling test` ਚੇਨਾਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ, ਜਦੋਂ candidate
test pull-request diff ਵਿੱਚ ਮੌਜੂਦ ਨਾ ਹੋਵੇ। Markdown summary ਅਤੇ JSON result ਨੂੰ
calibration ਲਈ `forgotten-sibling-tests` workflow artifact ਵਜੋਂ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ,
ਕਿਸੇ ਵੀ blocking rollout ਤੋਂ ਪਹਿਲਾਂ।

Barrel re-exports ਅਤੇ dynamic imports ਸਿਰਫ਼ resolution diagnostics ਹਨ; ਇਹ ਕਦੇ ਵੀ
blocking finding ਨਹੀਂ ਬਣਾਉਂਦੇ। Reviewed exceptions
`config/quality/forgotten-sibling-allowlist.json` ਵਿੱਚ ਰਹਿੰਦੀਆਂ ਹਨ। ਹਰੇਕ entry ਵਿੱਚ consumer ਅਤੇ candidate
test ਦਾ ਨਾਮ, ਵਿਸ਼ੇਸ਼ rationale, ਅਤੇ GitHub issue ਜਾਂ pull request ਦਾ ਲਿੰਕ ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਗਲਤ ਫਾਰਮੈਟ ਵਾਲੀਆਂ entries
ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ। Exceptions ਕਿਸੇ deleted candidate test ਜਾਂ ਅਜਿਹੇ diff ਨੂੰ suppress ਨਹੀਂ ਕਰ ਸਕਦੀਆਂ ਜੋ `.skip`/`.todo`
ਜੋੜਦਾ ਹੋਵੇ; assertion weakening ਅਤੇ ਹੋਰ masking ਦੀ ਜ਼ਿੰਮੇਵਾਰੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ blocking
`check:test-masking` gate ਦੀ ਹੈ।

#### ਅਨੁਵਾਦ ਮਿਰਰ ਡੈਰੀਵਡ ਫ਼ਾਈਲਾਂ ਹਨ (PR ਮੋਡ ਬਨਾਮ ਰਿਲੀਜ਼ ਮੋਡ)

ਇੱਕ ਫੀਚਰ PR ਸਿਰਫ਼ ਅੰਗਰੇਜ਼ੀ ਸਰੋਤਾਂ ਵਿੱਚ ਸੋਧ ਕਰਦਾ ਹੈ। `docs/i18n/<locale>/**` ਮਿਰਰ (ਜਿਨ੍ਹਾਂ ਵਿੱਚ 66
`llm.txt` ਕਾਪੀਆਂ ਅਤੇ ਅਨੁਵਾਦ ਕੀਤੀਆਂ `CHANGELOG.md` ਫ਼ਾਈਲਾਂ ਵੀ ਸ਼ਾਮਲ ਹਨ) ਅਤੇ `.i18n-state.json` ਨੂੰ
ਅਨੁਵਾਦ ਵੇਵ (`docs/i18n-*` / `chore/i18n-*` ਬ੍ਰਾਂਚਾਂ, ਸ਼ਡਿਊਲ ਕੀਤਾ ਗਿਆ
`i18n-mirror-refresh.yml`) ਅਤੇ ਰਿਲੀਜ਼ (`npm run release:sync-changelog-i18n`) ਰਾਹੀਂ ਇੱਕ ਕਦਮ ਵਿੱਚ ਦੁਬਾਰਾ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ। ਇਸ ਲਈ ਮਿਰਰ
ਗੇਟ ਦੋ ਮੋਡਾਂ ਵਿੱਚ ਚਲਦੇ ਹਨ, ਜਿਨ੍ਹਾਂ ਦਾ ਨਿਰਧਾਰਨ `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`,
ਫਿਰ `OMNIROUTE_GATE_MODE`, ਅਤੇ ਉਸ ਤੋਂ ਬਾਅਦ Actions ਇਵੈਂਟ; ਸਥਾਨਕ ਰਨ `release` ਹੁੰਦਾ ਹੈ) ਰਾਹੀਂ ਹੁੰਦਾ ਹੈ:

- `check:docs-sync` — ਰਿਲੀਜ਼ ਮੋਡ ਹਰ ਜਾਂਚ ਚਲਾਉਂਦਾ ਹੈ। PR ਮੋਡ package.json/OpenAPI ਵਰਜਨ,
  ਰੂਟ CHANGELOG headings ਅਤੇ superseded-docs guard ਨੂੰ ਰੱਖਦਾ ਹੈ, ਅਤੇ
  `SKIP reason=pr-mode` ਨੂੰ `llm.txt` mirror ਕਾਪੀਆਂ ਅਤੇ ਅਨੁਵਾਦ ਕੀਤੇ CHANGELOG ਭਾਗਾਂ ਲਈ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ —
  ਜਦੋਂ ਤੱਕ PR mirrors ਨਹੀਂ ਲਿਖਦਾ: `config/quality/derived-paths/*.json` ਵਿੱਚ `docs/i18n/**` family ਦੇ writer ਵਜੋਂ
  ਘੋਸ਼ਿਤ head branch ਦੋਵੇਂ ਜਾਂਚਾਂ ਸਖ਼ਤੀ ਨਾਲ ਚਲਾਉਂਦੀ ਹੈ, ਅਤੇ, ਜਦੋਂ diff base resolve ਹੋ ਜਾਵੇ, ਆਪਣੇ diff ਵਿੱਚ
  `docs/i18n/<locale>/llm.txt` ਜਾਂ `CHANGELOG.md` ਨੂੰ ਸੋਧਣ ਵਾਲੀ ਤਬਦੀਲੀ ਉਹ ਜਾਂਚ ਸਖ਼ਤੀ ਨਾਲ ਚਲਾਉਂਦੀ ਹੈ। depth-1 checkout
  (`docs-sync-strict` job) ਵਿੱਚ diff base resolve ਨਹੀਂ ਹੁੰਦਾ, ਇਸ ਲਈ PR ਮੋਡ ਇੱਕ ਐਸੀ ਜਾਂਚ ਵੀ ਚਲਾਉਂਦਾ ਹੈ ਜਿਸ ਨੂੰ base ਦੀ ਲੋੜ ਨਹੀਂ:
  ਹਰ `llm.txt` mirror ਮੌਜੂਦ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ, ਆਪਣਾ `---` separator ਕਾਇਮ ਰੱਖਣਾ ਚਾਹੀਦਾ ਹੈ ਅਤੇ ਜਾਂ ਤਾਂ root body ਜਾਂ ਉਹ body ਰੱਖਣਾ ਚਾਹੀਦਾ ਹੈ
  ਜਿਸਨੂੰ ਜ਼ਿਆਦਾਤਰ mirrors ਸਾਂਝਾ ਕਰਦੇ ਹਨ। ਜੇ base ਬਦਲ ਗਿਆ ਹੋਵੇ ਤਾਂ ਸਾਰੇ mirrors ਇੱਕੋ ਜਿਹੇ stale ਰਹਿੰਦੇ ਹਨ ਅਤੇ ਜਾਂਚ ਪਾਸ ਹੁੰਦੀ ਹੈ;
  ਕਿਸੇ ਇੱਕ mirror ਵਿੱਚ ਹੱਥੋਂ ਕੀਤੀ ਸੋਧ ਅਸਫਲ ਹੁੰਦੀ ਹੈ। depth-1 PR checkout ਵਿੱਚ ਅਨੁਵਾਦ ਕੀਤੀਆਂ `CHANGELOG.md` ਫਾਈਲਾਂ ਲਈ
  ਐਸੀ ਕੋਈ ਜਾਂਚ ਨਹੀਂ ਹੈ।
- pre-commit hook `check-docs-sync.mjs --mode=pr` ਚਲਾਉਂਦਾ ਹੈ: commit ਦਾ ਮੁਲਾਂਕਣ ਇਸ ਆਧਾਰ ’ਤੇ ਹੁੰਦਾ ਹੈ ਕਿ ਉਹ ਕੀ ਕਰਦਾ ਹੈ।
  flag ਤੋਂ ਬਿਨਾਂ local run release mode ਹੁੰਦਾ ਹੈ, ਅਤੇ root `llm.txt` ਨੂੰ ਸੋਧਣ ਵਾਲਾ ਇੱਕ merged PR ਉਸ base ’ਤੇ ਅਗਲੇ ਹਰ commit ਨੂੰ
  ਉਦੋਂ ਤੱਕ ਰੋਕ ਦਿੰਦਾ ਜਦੋਂ ਤੱਕ wave ਨਾ ਚੱਲੇ। ਇਹੀ ਨਿਯਮ ਕਿਸੇ ਵੀ mode-aware gate ਲਈ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜੋ Husky hook ਚਲਾਉਂਦਾ ਹੈ:
  hook `--mode=pr` ਪਾਸ ਕਰਦਾ ਹੈ, ਅਤੇ strict verdict release-mode runs (release PR, `main` ਵੱਲ pushes, plain local run) ਕੋਲ ਰਹਿੰਦਾ ਹੈ।
- Mirror-content unit tests (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`,
  `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`,
  `docs/*-locales`) — release mode ਹਰ locale ਦੀ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ। PR mode ਸਿਰਫ਼ ਉਹਨਾਂ mirrors ਦੀ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ ਜੋ
  `.i18n-state.json` ਦੇ ਅਨੁਸਾਰ English source ਨਾਲ current ਹਨ (ਪੂਰੀ file hash, ਜਾਂ test ਵੱਲੋਂ pin ਕੀਤੇ section ਦੀ recorded
  section hash) ਅਤੇ stale ਵਾਲਿਆਂ ਨੂੰ ਕਾਰਨ ਸਮੇਤ skip ਕਰਦਾ ਹੈ। `target_hash` provenance checks ਦੋਵੇਂ modes ਵਿੱਚ ਹਰ locale ਲਈ ਚੱਲਦੀਆਂ ਹਨ।
  Freshness ਹਰ `## ` section ਲਈ ਵੱਖਰੀ ਹੈ, unit `run-translation.mjs` hash ਕਰਦੀ ਹੈ; ਲੰਮਾ section (ਇਸ file ਦੀ gate inventory
  ਲਗਭਗ ਇਸਦਾ ਅੱਧਾ ਹੈ) ਦਾ ਮਤਲਬ ਹੈ ਕਿ ਇਸ ਵਿੱਚ ਕੀਤੀ ਕੋਈ ਵੀ edit ਉਹਨਾਂ mirrors ਨੂੰ stale ਕਰ ਦਿੰਦੀ ਹੈ, ਅਤੇ ਉਹਨਾਂ ਦੀਆਂ PR-mode
  assertions ਅਗਲੀ wave ਤੱਕ skip ਹੁੰਦੀਆਂ ਰਹਿੰਦੀਆਂ ਹਨ। ਜੇ English source ਵਿੱਚ ਕੋਈ anchor ਹੁਣ ਮੌਜੂਦ ਨਾ ਹੋਵੇ ਤਾਂ ਪੂਰੀ file
  comparison ’ਤੇ fallback ਕੀਤਾ ਜਾਂਦਾ ਹੈ।
- `i18n translation drift` — PRs ’ਤੇ advisory, push, nightly ਅਤੇ release cut ’ਤੇ strict ਹੁੰਦਾ ਹੈ, ਤਾਂ ਜੋ stale mirror

### Derived values: `pr` ਅਤੇ `release` gate modes

Feature PR ਕਦੇ ਵੀ ਉਹ value ਨਹੀਂ ਲਿਖਦਾ ਜੋ ਆਪਣੇ base ਦੀ state ’ਤੇ ਨਿਰਭਰ ਹੋਵੇ: provider, migration,
MCP-tool ਅਤੇ strategy counts, README SVG numbers, facts snapshot। ਇੱਕ step ਇਹਨਾਂ ਸਾਰਿਆਂ ਨੂੰ ਦੁਬਾਰਾ compute ਕਰਦਾ ਹੈ,
`npm run release:refresh-derived`, ਜਿਸਨੂੰ release ਅਤੇ nightly derived-refresh PR ਚਲਾਉਂਦੇ ਹਨ। ਇਸ ਲਈ **releases ਦੇ ਵਿਚਕਾਰ
base live code ਤੋਂ ਪਿੱਛੇ ਹੁੰਦਾ ਹੈ — ਇਹ design ਅਨੁਸਾਰ ਹੈ**, ਅਤੇ ਜੇ ਕੋਈ gate ਜਾਂ test tree ਦੀ live code ਨਾਲ ਤੁਲਨਾ ਕਰੇ ਤਾਂ
ਕਿਸੇ sibling ਵੱਲੋਂ provider ਜੋੜਨ ਤੋਂ ਬਾਅਦ ਹਰ PR ’ਤੇ red ਹੋਵੇਗਾ। Derived values ਦਾ ਮੁਲਾਂਕਣ ਕਰਨ ਵਾਲੇ gates ਇਸ ਲਈ
ਦੋ modes ਵਿੱਚੋਂ ਇੱਕ ਵਿੱਚ ਚੱਲਦੇ ਹਨ, ਜਿਨ੍ਹਾਂ ਦਾ ਨਿਰਧਾਰਨ `scripts/check/lib/gateMode.mjs` ਕਰਦਾ ਹੈ (ਪਹਿਲਾ match ਲਾਗੂ ਹੁੰਦਾ ਹੈ):

1. command line ’ਤੇ `--mode=pr|release`;
2. `OMNIROUTE_GATE_MODE` environment variable (`pr` ਜਾਂ `release`);
3. GitHub Actions event ਤੋਂ automatic: `pull_request` ਜਿਸਦਾ head `release/v*` ਨਾ ਹੋਵੇ,
   `merge_group`, ਜਾਂ `omni-queue/**` ਵੱਲ push → `pr`; ਬਾਕੀ ਸਭ (push, schedule,
   dispatch, release PR `release/v* → main`, ਕੋਈ ਵੀ local run) → `release`।

ਹਰ mode ਵਿੱਚ `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) ਕਿਹੜੀਆਂ ਚੀਜ਼ਾਂ ’ਤੇ ਅਸਫਲ ਹੁੰਦਾ ਹੈ:

| ਮੋਡ       | ਅਸਫਲਤਾਵਾਂ                                                                                                                                                                                                                                                                                                                                                                                                                             | ਲਾਈਵ ਤੱਥਾਂ ਦੀ ਲੋੜ |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `release` | ਹਰ ਜਾਂਚ, ਟ੍ਰੀ ਤੋਂ ਇਕੱਠੇ ਕੀਤੇ ਤੱਥਾਂ ਨਾਲ ਸਖ਼ਤ ਸਮਾਨਤਾ (ਉਹ ਵਰਤਾਅ ਜੋ ਗੇਟ ਵਿੱਚ ਹਮੇਸ਼ਾਂ ਰਿਹਾ ਹੈ): ਪੁਰਾਣੀ ਗਿਣਤੀ, ਵਰਜਨ, ਕਵਰੇਜ ਫ਼ਲੋਰ ਜਾਂ SVG ਨੰਬਰ ਸਖ਼ਤ ਤੌਰ 'ਤੇ ਬਦਲਾਅ ਹੈ                                                                                                                                                                                                                                                                         | ਹਾਂ               |
| `pr`      | ਸਿਰਫ਼ ਉਹੀ ਜੋ ਬਦਲਾਅ ਨੇ ਕੀਤਾ, PR ਬੇਸ ਦੇ ਮੁਕਾਬਲੇ ਉਹੀ ਕਲੇਮ ਐਕਸਟ੍ਰੈਕਟਰ ਵਰਤ ਕੇ: (1) ਕੋਈ ਪ੍ਰਬੰਧਿਤ ਮੁੱਲ ਜੋ ਉਸ ਜਾਂਚ ਅਤੇ ਫ਼ਾਈਲ ਲਈ ਬੇਸ ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਸੀ ("PR ਨੇ ਪ੍ਰਬੰਧਿਤ ਨੰਬਰ ਵਿੱਚ ਸੋਧ ਕੀਤੀ — ਲਾਈਨ ਨੂੰ ਬੇਸ ਟੈਕਸਟ 'ਤੇ ਵਾਪਸ ਲਿਆਓ"); (2) ਕੋਈ ਲੋੜੀਂਦਾ ਕਲੇਮ ਜੋ ਬੇਸ ਵਿੱਚ ਸੀ ਅਤੇ ਹੈਡ ਵਿੱਚੋਂ ਗੁੰਮ ਹੋ ਗਿਆ। ਜਿਨ੍ਹਾਂ ਕੰਟੈਂਟ ਇਨਵੇਰੀਅੰਟਸ ਨੂੰ ਤੱਥਾਂ ਦੀ ਲੋੜ ਨਹੀਂ, ਉਹ ਰਿਲੀਜ਼ ਮੋਡ ਵਾਂਗ ਚੱਲਦੇ ਹਨ; ਸਿਰਫ਼ ਰਿਲੀਜ਼ ਵਾਲੀਆਂ ਜਾਂਚਾਂ ਸੂਚੀਬੱਧ ਕਰਕੇ ਛੱਡ ਦਿੱਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ | ਨਹੀਂ              |

ਏਜੰਟ-ਨਿਰਦੇਸ਼ ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਕੋਈ ਵੀ ਡੈਰੀਵਡ ਗਿਣਤੀ ਨਹੀਂ ਹੈ: `AGENTS.md`, `llm.txt` (ਅਤੇ ਇਸ ਦੀਆਂ
`docs/i18n/*/llm.txt` ਕਾਪੀਆਂ), bs `AGENTS.md` ਫ਼ੋਰਕ, `open-sse/services/AGENTS.md`,
`src/shared/constants/agentSkills.ts`, `skills/README.md` ਅਤੇ ਹਰ `skills/*/SKILL.md`
ਸਰੋਤ (ਉਦਾਹਰਨ ਲਈ `ROUTING_STRATEGY_VALUES` in `src/shared/constants/routingStrategies.ts`) ਅਤੇ ਇਸ ਦੀ ਥਾਂ
`npm run facts` ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦੇ ਹਨ। ਇਨਵੇਰੀਅੰਟ "No derived counts (agent-instruction file …)" ਦੋਵੇਂ ਮੋਡਾਂ ਵਿੱਚ ਉੱਥੇ ਕੋਈ ਗਿਣਤੀ (ਪ੍ਰੋਵਾਈਡਰ, ਮਾਈਗ੍ਰੇਸ਼ਨ, MCP ਟੂਲ ਅਤੇ ਸਕੋਪ, ਰਾਊਟਿੰਗ ਰਣਨੀਤੀਆਂ, ਸਕੋਰਿੰਗ ਫੈਕਟਰ, ਮੋਡ ਪੈਕ) ਮਿਲਣ 'ਤੇ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ ਰਿਲੀਜ਼ ਰਿਫ੍ਰੈਸ਼ ਨੂੰ ਕਦੇ ਵੀ ਕਿਸੇ ਨਿਰਦੇਸ਼ ਫ਼ਾਈਲ ਨੂੰ ਦੁਬਾਰਾ ਲਿਖਣ ਦੀ ਲੋੜ ਨਹੀਂ ਪੈਂਦੀ।

`pr` ਮੋਡ ਵਿੱਚ ਲੇਖਕ ਬ੍ਰਾਂਚਾਂ ਪ੍ਰਬੰਧਿਤ ਮੁੱਲਾਂ ਵਿੱਚ ਸੋਧ ਕਰ ਸਕਦੀਆਂ ਹਨ: `chore/derived-*` (ਰਾਤਰੀ ਰਿਫ੍ਰੈਸ਼
PR), `release/v*`, ਅਤੇ ਅਨੁਵਾਦ ਵੇਵਜ਼ `docs/i18n-*` ਅਤੇ `chore/i18n-*`
(`scripts/check/lib/derivedClaimsDiff.mjs`)। ਕਤਾਰ ਬੈਚ (`merge_group`, Mergify ਡਰਾਫਟ,
`omni-queue/**`) ਦੀ ਦੁਬਾਰਾ ਜਾਂਚ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ: ਇਹ ਉਹਨਾਂ PRs ਦਾ ਜੋੜ ਹੁੰਦੇ ਹਨ ਜਿਨ੍ਹਾਂ ਦੀ ਗੇਟ ਨੇ ਪਹਿਲਾਂ ਹੀ ਇੱਕ-ਇੱਕ ਕਰਕੇ ਜਾਂਚ ਕਰ ਲਈ ਹੈ।

ਐਗਜ਼ਿਟ ਕੋਡ: `0` ਸਾਫ਼ · `1` ਸਖ਼ਤ ਬਦਲਾਅ (ਜਾਂ `--strict` ਨਾਲ ਸਾਫ਼ਟ ਬਦਲਾਅ) ਜਾਂ ਪ੍ਰਬੰਧਿਤ-ਮੁੱਲ
ਉਲੰਘਣਾ · `2` ਇਨਫ਼ਰਾਸਟ੍ਰਕਚਰ — ਕੋਡ ਤੱਥ ਇਕੱਠੇ ਨਹੀਂ ਕੀਤੇ ਜਾ ਸਕੇ (tsx ਪ੍ਰੋਬ ਅਸਫਲ ਹੋਈ ਜਾਂ
ਟਾਈਮਆਊਟ ਹੋ ਗਿਆ; ਟਾਈਮਆਊਟ `OMNIROUTE_FACTS_TIMEOUT_MS` ਹੈ, ਡਿਫ਼ਾਲਟ 600000 ms) ਜਾਂ, CI ਵਿੱਚ, PR ਡਿਫ਼ ਬੇਸ
ਹੱਲ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਿਆ। ਐਗਜ਼ਿਟ 2 ਕਦੇ ਵੀ ਦਸਤਾਵੇਜ਼ੀ ਵਿਸੰਗਤੀ ਨਹੀਂ ਹੁੰਦਾ: ਜੌਬ ਦੁਬਾਰਾ ਚਲਾਓ ਜਾਂ
ਵਾਤਾਵਰਣ ਠੀਕ ਕਰੋ।

ਇਸ ਦੇ ਪਿੱਛੇ ਵਾਲੀਆਂ ਕਮਾਂਡਾਂ:

- `npm run facts` ਹਰ ਵਿਉਤਪੰਨ ਨੰਬਰ ਨੂੰ JSON ਵਜੋਂ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ (`scripts/release/facts.mjs`)।

- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) ਵਿਉਤਪੰਨ ਫ਼ਾਈਲਾਂ ਨੂੰ ਇੱਕ ਹੀ ਪਾਸ ਵਿੱਚ, ਇਸ ਕ੍ਰਮ ਅਨੁਸਾਰ, ਮੁੜ ਗਣਨਾ ਕਰਦਾ ਹੈ (`--only=` ਲਈ ਕਦਮ IDs): `provider-reference`
  (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (ਸਨੈਪਸ਼ਾਟ), `numbers` (counts gate ਦੀ rewrite ਯੋਜਨਾ docs ਉੱਤੇ ਲਾਗੂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਫਿਰ `docs/i18n/` ਮਿਰਰਾਂ ਤੱਕ ਪਹੁੰਚਾਈ ਜਾਂਦੀ ਹੈ),
  `readme-diagrams`, `skills` (ਤਿਆਰ ਕੀਤੀ `SKILL.md`), `e2e-timings` (ਜਦੋਂ ਤੱਕ ਟ੍ਰੀ ਵਿੱਚ `syncE2eTimings` ਨਹੀਂ ਆਉਂਦਾ, ਛੱਡਿਆ ਜਾਂਦਾ ਹੈ), `ui-keys` (`en.json` ਵੱਲੋਂ ਹਟਾਈਆਂ ਗਈਆਂ keys ਨੂੰ ਕੱਢਦਾ ਹੈ ਅਤੇ, `--rewritten-since=<ref>` — ਮੂਲ ਰੂਪ ਵਿੱਚ `origin/main` — ਨਾਲ, ਆਖਰੀ ਰਿਲੀਜ਼ ਤੋਂ ਬਾਅਦ ਮੁੜ ਲਿਖੀਆਂ ਗਈਆਂ ਅੰਗਰੇਜ਼ੀ values ਨੂੰ ਦੁਬਾਰਾ ਕਤਾਰ ਵਿੱਚ ਰੱਖਦਾ ਹੈ), `llm-mirrors` ਅਤੇ `verify-generated` (ਲਿਖਣ ਤੋਂ ਬਾਅਦ, release mode ਵਿੱਚ `check:generated-artifacts` ਅਤੇ `check:agent-skills-sync` ਪਾਸ ਹੋਣੇ ਲਾਜ਼ਮੀ ਹਨ; `--check` ਵਿੱਚ ਅਤੇ ਜਦੋਂ `--only` ਇਸਨੂੰ ਬਾਹਰ ਰੱਖਦਾ ਹੈ, ਛੱਡੇ ਜਾਂਦੇ ਹਨ; ਅਸਫਲਤਾ ਦਾ ਐਗਜ਼ਿਟ ਕੋਡ 2 ਹੁੰਦਾ ਹੈ)। `changelog` ਕਦਮ opt-in ਹੈ (`--with-changelog`, ਕੇਵਲ release profile ਵਿੱਚ)। `--profile=nightly` ਕਦੇ ਵੀ version claim ਨੂੰ ਨਹੀਂ ਛੁਹਿੰਦਾ। `-- --check` ਨਾਲ ਇਹ ਕੁਝ ਨਹੀਂ ਲਿਖਦਾ ਅਤੇ ਜਦੋਂ ਕੋਈ ਫ਼ਾਈਲ ਬਦਲਣੀ ਹੋਵੇ ਜਾਂ ਕਿਸੇ managed value ਨੂੰ ਹੱਥੋਂ ਸੋਧਣ ਦੀ ਲੋੜ ਹੋਵੇ ਤਾਂ ਐਗਜ਼ਿਟ ਕੋਡ 1 ਦਿੰਦਾ ਹੈ (ਦੋਵੇਂ ਦਰਸਾਏ ਜਾਂਦੇ ਹਨ); infrastructure failure ਉੱਤੇ ਐਗਜ਼ਿਟ ਕੋਡ 2 ਹੁੰਦਾ ਹੈ। `--json` ਨਤੀਜੇ ਨੂੰ JSON ਵਜੋਂ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ।
- `docs/reference/derived-facts.json` ਉਹਨਾਂ facts ਦਾ ਸਨੈਪਸ਼ਾਟ ਹੈ ਜਿਨ੍ਹਾਂ ਨੂੰ ਆਖਰੀ refresh ਨੇ ਵਰਤਿਆ ਸੀ। ਇਸਨੂੰ ਸਿਰਫ਼ refresh ਹੀ ਲਿਖਦਾ ਹੈ। README SVG generators ਇਸਨੂੰ ਪੜ੍ਹਦੇ ਹਨ, ਅਤੇ PR-ਸਮੇਂ ਦੇ unit tests ਕਮਿਟ ਕੀਤੇ docs ਅਤੇ generated files ਦੀ ਇਸ ਨਾਲ ਤੁਲਨਾ ਕਰਦੇ ਹਨ — ਲਾਈਵ code ਨਾਲ ਕਦੇ ਨਹੀਂ। suite ਦੀ ਇਕੱਲੀ live comparison `tests/unit/check-docs-counts-sync.test.ts` ਵਿੱਚ "the release refresh closes the cycle" ਹੈ: live facts ਨਾਲ, refresh ਦੀ rewrite ਯੋਜਨਾ ਨੂੰ memory ਵਿੱਚ ਲਾਗੂ ਕਰਨ ਉੱਤੇ ਕੋਈ ਵੀ STRICT drift ਬਾਕੀ ਨਹੀਂ ਰਹਿੰਦੀ ਜਿਸਦੀ ਇਹ ਰਿਪੋਰਟ ਨਾ ਕਰੇ, ਅਤੇ ਮੁੜ ਯੋਜਨਾ ਬਣਾਉਣ ਨਾਲ ਕੁਝ ਨਹੀਂ ਬਦਲਦਾ।

ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ ਦੁਬਾਰਾ ਬਣਾਉਣ ਲਈ (ਇੱਕ local run ਮੂਲ ਰੂਪ ਵਿੱਚ `release` ਉੱਤੇ ਚੱਲਦਾ ਹੈ):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

ਕਿਸੇ resolvable base ਤੋਂ ਬਿਨਾਂ (ਨਾ `BASE_SHA`/`BASE_REF`, ਨਾ ਹੀ local `origin/release/v<version>`) local
`pr` run ਇੱਕ warning ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ ਅਤੇ ਅਸਫਲ ਹੋਣ ਦੀ ਬਜਾਏ diff ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ।

Gates mode ਨੂੰ `scripts/check/lib/gateMode.mjs` ਤੋਂ ਪੜ੍ਹਦੇ ਹਨ: `pr` mode (feature PRs,

0 ਨਾਲ exit ਕਰਦੇ ਹਨ; `release` mode (release PR, `main` ਵੱਲ pushes, `workflow_dispatch`, local runs) ਵਿੱਚ ਉਹ ਪਹਿਲਾਂ ਵਾਂਗ strict ਰਹਿੰਦੇ ਹਨ, ਅਤੇ release PR ਉੱਤੇ diff-aware gates ਨੂੰ `BASE_REF=origin/main` ਮਿਲਦਾ ਹੈ, ਇਸ ਲਈ ਉਹ ਹਰ ਉਸ key ਨੂੰ judge ਕਰਦੇ ਹਨ ਜਿਸਨੂੰ cycle ਨੇ ਜੋੜਿਆ ਜਾਂ ਮੁੜ ਲਿਖਿਆ ਹੈ। Feature-PR ਦਾ verdict ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ `--mode=pr` ਨਾਲ preview ਕਰੋ।

ਇੱਕ PR ਜੋ `pr` ਮੋਡ ਵਿੱਚ locale catalogs ਨੂੰ ਬਦਲਦਾ ਰਹਿੰਦਾ ਹੈ (translation wave, release refresh, translation-only fix), ਉਸਨੂੰ ਛੱਡਿਆ ਨਹੀਂ ਜਾਂਦਾ: `check-key-completeness` merge base (`scripts/i18n/lib/touched-catalogs.mjs`) ਵਿੱਚ ਉਸੇ catalog ਦੇ ਮੁਕਾਬਲੇ ਬਦਲੇ ਗਏ ਹਰ catalog ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ ਅਤੇ ਹੇਠ ਲਿਖੀਆਂ ਸਥਿਤੀਆਂ ਵਿੱਚ ਅਸਫਲ ਹੁੰਦਾ ਹੈ: catalog ਵਿੱਚੋਂ ਗੁੰਮ ਹੋਈ key, `en.json` ਵਿੱਚ ਨਾ ਹੋਣ ਵਾਲੀ key, ਅਸਲ translation ਦਾ `__MISSING__:` marker ਜਾਂ English text ਵਿੱਚ ਬਦਲ ਜਾਣਾ, ਜਾਂ ਉਹ value ਜੋ ਕਿਸੇ English string ਦੇ placeholders/tags ਨੂੰ ਹੁਣ interpolate ਨਹੀਂ ਕਰਦੀ ਅਤੇ ਜਿਸਨੂੰ PR ਨੇ ਨਹੀਂ ਛੇੜਿਆ। PR ਵਿੱਚ ਨਵਾਂ catalog ਪੂਰਾ `en.json` key set ਲੈ ਕੇ ਆਉਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਇਸ ਨਾਲ PR ਵੱਲੋਂ ਛੇੜੇ ਗਏ catalogs ਲਈ ਇਹ ਪਤਾ ਲੱਗ ਜਾਂਦਾ ਹੈ ਕਿ ratio ਅਤੇ CLI-parity gates ਕੀ ਦੇਖਣਗੇ।

Locale-parity unit tests (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) `tests/_helpers/localeParityMode.ts` ਰਾਹੀਂ ਇਹੀ modes follow ਕਰਦੇ ਹਨ: `pr` ਮੋਡ ਵਿੱਚ ਉਹ key-parity assertions ਛੱਡ ਦਿੰਦੇ ਹਨ ਅਤੇ merge base ਤੋਂ ਬਾਅਦ ਬਦਲੀਆਂ English keys ਦੀ placeholder parity release refresh ਲਈ ਛੱਡ ਦਿੰਦੇ ਹਨ (unit-test job ਦਾ shallow checkout ਉਹ base ਪੜ੍ਹ ਨਾ ਸਕੇ ਤਾਂ ਹਰ key)। ਉਹ helper ਇਸ mode-conditional skip ਲਈ **ਇਕੱਲਾ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਤਰੀਕਾ** ਹੈ:
`check:test-masking` `.skip(` ਅਤੇ `{ skip: true }` ਦੀ ਗਿਣਤੀ ਕਰਦਾ ਹੈ, ਪਰ ਇਸ ਵੱਲੋਂ ਵਾਪਸ ਕੀਤੇ computed
`{ skip: "<reason>" }` ਦੀ ਨਹੀਂ। ਇਸ ਲਈ `tests/unit/locale-parity-mode.test.ts` ਉਹਨਾਂ tests ਦੀ ਸੂਚੀ ਨੂੰ pin ਕਰਦਾ ਹੈ ਜੋ ਇਸਦੀ ਵਰਤੋਂ ਕਰ ਸਕਦੇ ਹਨ — ਇੱਕ ਹੋਰ test ਜੋੜਨਾ ਉਸ ਸੂਚੀ ਵਿੱਚ reviewed edit ਹੁੰਦਾ ਹੈ।

#### `check-ui-value-drift` — ਪੁਰਾਣੀ translation ਲਈ gate

ਇਹ ਉਹ ਇੱਕ i18n regression ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ ਹੋਰ gates ਸੰਰਚਨਾਤਮਕ ਤੌਰ ‘ਤੇ ਨਹੀਂ ਦੇਖ ਸਕਦੇ: English value ਨੂੰ ਦੁਬਾਰਾ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ _ਪਿਛਲੀ_ English ਤੋਂ ਬਣੀਆਂ translations ਪਿੱਛੇ ਰਹਿ ਜਾਂਦੀਆਂ ਹਨ, ਇਸ ਲਈ non-English users ਭਰੋਸੇਯੋਗ ਲੱਗਣ ਵਾਲਾ ਪਰ ਹੁਣ-ਗਲਤ copy ਪੜ੍ਹਦੇ ਰਹਿੰਦੇ ਹਨ।

ਇਹ ਅਸਲ ਵਿੱਚ production ਵਿੱਚ ਚਲਾ ਗਿਆ ਸੀ। `oauthModal.googleOAuthWarning` ਨੂੰ Antigravity login helper ਦੇ ਆਉਣ ‘ਤੇ ਦੁਬਾਰਾ ਲਿਖਿਆ ਗਿਆ (#5203); **43 ਵਿੱਚੋਂ 39 locales** ਵਿੱਚ operators ਨੂੰ “ਪੂਰਾ URL copy ਕਰਕੇ ਹੇਠਾਂ paste ਕਰੋ” ਦੱਸਣ ਵਾਲਾ text ਰਹਿ ਗਿਆ — ਇੱਕ ਅਜਿਹਾ flow ਜੋ ਉਸ provider ਲਈ ਪੂਰਾ ਨਹੀਂ ਹੋ ਸਕਦਾ। ਇਹ #8463 ਤੱਕ ਨਜ਼ਰਅੰਦਾਜ਼ ਰਿਹਾ ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹਨਾਂ keys ਨੂੰ backfill ਕਰਦਾ ਹੈ ਜੋ **ਗੈਰ-ਮੌਜੂਦ** ਹਨ, ਪੁਰਾਣੀਆਂ ਨਹੀਂ;
- `check-ui-keys-coverage` key _presence_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ stale translation covered ਮੰਨੀ ਜਾਂਦੀ ਹੈ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` documentation mirrors ਨੂੰ track ਕਰਦਾ ਹੈ —
  ਇਹ `src/i18n/messages/*.json` ਨੂੰ ਕਦੇ ਨਹੀਂ ਪੜ੍ਹਦਾ। ਇਹ `docs-sync-strict` job ਵਿੱਚ ਚੱਲਦਾ ਹੈ: PRs ‘ਤੇ advisory,
  push ਅਤੇ nightly ‘ਤੇ strict; translation wave mirrors ਨੂੰ refresh ਕਰਦੀ ਹੈ, feature PR ਨੂੰ ਨਹੀਂ।

**Diff-aware, baseline-backed ਨਹੀਂ।** ਇਹ merge base ‘ਤੇ `en.json` ਦੀ ਤੁਲਨਾ working tree ਨਾਲ ਕਰਦਾ ਹੈ; ਹਰ ਉਸ key ਲਈ ਜਿਸਦੀ English value ਬਦਲੀ ਹੈ, ਜੇ ਕੋਈ locale ਹਾਲੇ ਵੀ untouched translation ਰੱਖਦਾ ਹੈ ਤਾਂ ਉਹ stale ਹੈ। ਇਹ ਜਾਣਬੁੱਝ ਕੇ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ debt ਨੂੰ **freeze** ਕਰਦਾ ਹੈ — diff ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਕੋਈ ਪੁਰਾਣੀ translation ਕਿਹੜੀ English ਤੋਂ ਆਈ ਸੀ, ਇਸ ਲਈ gate ਸਿਰਫ਼ ਮੌਜੂਦਾ change ਨੂੰ judge ਕਰਦਾ ਹੈ। ਵਿਕਲਪ (ਹਰ key ਲਈ hash baseline) ਲਗਭਗ 600 KB ਦੀ generated file ਦੀ ਲਾਗਤ ਲਿਆਉਂਦਾ, ਜੋ ਮੌਜੂਦਾ ਸਭ ਤੋਂ ਵੱਡੇ baseline ਤੋਂ 3× ਹੈ ਅਤੇ ਹਰ i18n PR ‘ਤੇ churn ਕਰਦਾ।

ਇਸਨੂੰ ਪੂਰਾ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ translations ਨੂੰ update ਕਰੋ, ਜਾਂ
2. ਉਹਨਾਂ ਨੂੰ `__MISSING__:<new english>` ‘ਤੇ ਸੈੱਟ ਕਰੋ — runtime ਫਿਰ corrected English serve ਕਰਦਾ ਹੈ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਅਤੇ key translation ਲਈ queue ਵਿੱਚ ਚਲੀ ਜਾਂਦੀ ਹੈ।

ਜੇ string ਦਾ **ਅਰਥ** ਬਦਲ ਗਿਆ ਹੈ, ਤਾਂ **key ਦਾ ਨਾਮ ਬਦਲਣਾ** ਤਰਜੀਹ ਦਿਓ: ਨਵੀਂ key stale translation inherit ਨਹੀਂ ਕਰ ਸਕਦੀ। #8463 ਨੇ ਇਹੀ pattern ਵਰਤਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # strict (CI ਵਿੱਚ ਚੱਲਣ ਵਾਲਾ)
npm run i18n:check-value-drift:warn     # ਸਿਰਫ਼ report
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

**New-code mode (Clean-as-You-Code) — 2026-08-30 ਤੋਂ, ਸਿਰਫ਼ PR fast-path ਲਈ**

`pull_request` events ਉੱਤੇ `quality.yml`, `check:file-size`,
`check:complexity-ratchets` ਅਤੇ `check:dead-code` ਨੂੰ `--base-ref <PR base SHA>` ਪਾਸ ਕਰਦੀ ਹੈ।
`check:complexity-ratchets` ਅਤੇ `check:dead-code` ਲਈ gate, merge-base ਦੀ ਤੁਲਨਾ
**ਸਿਰਫ਼ PR ਵੱਲੋਂ ਛੁਹੀਆਂ ਫਾਈਲਾਂ ਤੱਕ ਸੀਮਿਤ** ਕਰਕੇ ਕਰਦਾ ਹੈ
(`scripts/check/newCodeMode.mjs`: merge-base ਨੂੰ throwaway
`git worktree` ਵਿੱਚ materialize ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਉੱਥੇ ਅਤੇ HEAD ਉੱਤੇ ESLint/knip ਚਲਾਏ ਜਾਂਦੇ ਹਨ,
ਅਤੇ per-file counts ਦਾ diff ਕੀਤਾ ਜਾਂਦਾ ਹੈ):

- **blocking** — PR ਨੇ ਜਿਹੜੀਆਂ ਫਾਈਲਾਂ ਬਦਲੀਆਂ ਹਨ, ਉਨ੍ਹਾਂ ਵਿੱਚ cyclomatic/cognitive violations ਜਾਂ dead exports ਸ਼ਾਮਲ ਕੀਤੇ ਹਨ
  (log ਵਿੱਚ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` ਹੁੰਦੇ ਹਨ);
- **advisory** — frozen baseline ਦੇ ਮੁਕਾਬਲੇ global total। Inherited drift ਕਿਸੇ ਨਿਰਦੋਸ਼ PR ਨੂੰ ਕਦੇ red ਨਹੀਂ ਕਰਦਾ;
  release reconciliation ਉੱਤੇ drift ਨੂੰ ਮੁੜ freeze ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ headroom job ਵੱਲੋਂ ਨਿਗਰਾਨੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

`check:file-size` base ref ਨੂੰ ਆਪਣੇ ਨਿਯਮਾਂ ਅਨੁਸਾਰ ਵਰਤਦਾ ਹੈ (`scripts/check/check-file-size.mjs`, #8522):
ਇਹ tree ਵਿੱਚ ਹਰ source ਅਤੇ test file ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ, `git show` ਨਾਲ PR base ਉੱਤੇ ਹਰ ਫਾਈਲ ਦੀ
line count ਪੜ੍ਹਦਾ ਹੈ, ਅਤੇ ਕਿਸੇ ਫਾਈਲ ਨੂੰ ਸਿਰਫ਼ ਉਦੋਂ fail ਕਰਦਾ ਹੈ ਜਦੋਂ ਉਹ ਆਪਣੀ baseline ceiling
(`frozen` / `testFrozen`, ਜਾਂ baseline ਤੋਂ ਬਾਹਰਲੀ ਫਾਈਲ ਲਈ `cap` / `testCap`) ਅਤੇ ਆਪਣੇ base
size ਵਿੱਚੋਂ ਵੱਡੀ ਸੀਮਾ ਤੋਂ ਵੱਧ ਵਧਦੀ ਹੈ। ਇਸ ਲਈ base ਉੱਤੇ ਪਹਿਲਾਂ ਹੀ drift ਕਰ ਚੁੱਕੀ ਫਾਈਲ ਕਿਸੇ ਨਿਰਦੋਸ਼ PR ਨੂੰ
ਕਦੇ red ਨਹੀਂ ਕਰਦੀ।

`check:boundary:ratchet` ਆਪਣੇ ਇਕੱਲੇ ਨੰਬਰ ਉੱਤੇ ਵੀ ਇਹੀ ਨਿਯਮ ਲਾਗੂ ਕਰਦਾ ਹੈ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ਇਵੈਂਟਾਂ ਦੌਰਾਨ
`quality.yml` ਦੇ fast-gates ਅਤੇ `ci.yml` ਦਾ lint job ਦੋਵੇਂ PR ਦਾ base SHA ਪਾਸ ਕਰਦੇ ਹਨ, base commit ਨੂੰ
`git archive` ਐਕਸਪੋਰਟ ਤੋਂ ਮਾਪਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ PR ਕੇਵਲ ਉਦੋਂ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਇਸਦੀ
`open-sse → src` edge ਗਿਣਤੀ `metrics.boundaryOpenSseToSrc` ਅਤੇ base ਉੱਤੇ ਮੌਜੂਦ ਗਿਣਤੀ ਵਿੱਚੋਂ ਵੱਡੀ
ਗਿਣਤੀ ਤੋਂ ਵੱਧ ਹੋਵੇ। ceiling ਤੋਂ ਉੱਪਰਲਾ base drift ਰਿਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`base drift herdado`),
ਪਰ ਕਿਸੇ ਬੇਦੋਸ਼ PR ਨੂੰ ਕਦੇ red ਨਹੀਂ ਕਰਦਾ; push → main absolute ceiling ਕਾਇਮ ਰੱਖਦਾ ਹੈ, ਅਤੇ ਹੱਲ ਨਾ ਹੋ ਸਕਣ ਵਾਲਾ
base SHA warning ਦੇ ਨਾਲ ਇਸ ceiling ਉੱਤੇ ਵਾਪਸ ਆ ਜਾਂਦਾ ਹੈ।

ਇੱਕ omni-queue candidate ( `omni-queue/**` ਵੱਲ push, [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ਵੇਖੋ)
ਨੂੰ pull request ਵਾਂਗ ਹੀ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ: ਦੋਵੇਂ workflows candidate base
(`needs.changes.outputs.candidateBase`) ਨੂੰ `--base-ref` ਵਜੋਂ ਪਾਸ ਕਰਦੇ ਹਨ, ਅਤੇ
`check:ts7-diagnostics-ratchet` ਵੀ ਇਸਦੇ ਵਿਰੁੱਧ ਚਲਦਾ ਹੈ। ਨਵੇਂ ਕੋਡ ਵਾਲੇ ਦੋ gates ਲਈ comparison base
ਉਹ SHA ਖੁਦ ਹੈ, top merge commit ਦਾ ਪਹਿਲਾ parent ਨਹੀਂ, ਇਸ ਲਈ batch ਦੀ ਹਰ pull request ਦਾ ਮੁਲਾਂਕਣ ਹੁੰਦਾ ਹੈ।

`workflow_dispatch` runs, release-green sweep ਅਤੇ nightly headroom job ਕੋਲ ਕੋਈ PR base ਨਹੀਂ ਹੁੰਦਾ
ਅਤੇ ਇਹ absolute (global) comparison ਜਾਰੀ ਰੱਖਦੇ ਹਨ। Coverage, duplication ਅਤੇ type-coverage ਫਿਲਹਾਲ
global ਰਹਿੰਦੇ ਹਨ (ਉਨ੍ਹਾਂ ਦੇ tools ਸਸਤੇ ਢੰਗ ਨਾਲ per-file diff ਨਹੀਂ ਬਣਾਉਂਦੇ) — ਇਸੇ ਤਰ੍ਹਾਂ ਸੰਭਾਲੇ ਜਾਣ ਲਈ ਉਮੀਦਵਾਰ।

   banking ਨੂੰ ਮੁੜ ਸਰਗਰਮ ਕਰਦਾ ਹੈ), `check-openapi-coverage.mjs` ਵਿੱਚ
   `THRESHOLD = 36` (ਜਾਂ ਇਸ ਤੋਂ ਵੱਧ) ਮੁੜ-ਸਥਾਪਿਤ ਕਰੋ।
3. ਜਿੱਥੇ modularization ਨਾਲ ਲਾਭ ਹੋਇਆ ਹੈ, ਉੱਥੇ ਮਾਪੀ ਗਈ value ਤੋਂ ਵੀ ਵੱਧ ਸਖ਼ਤੀ ਲਿਆਓ: file-size `cap`
   ਮੁੜ 1000 (ਜਾਂ 800), coverage floors +5, modularized packages ਲਈ dead exports 0।

## ਰੈਚੇਟ ਬੇਸਲਾਈਨ (`quality-baseline.json`)

ਰੈਚੇਟ ਇੰਜਣ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ


ਸੁਧਾਰ ਨੂੰ ਬੇਸਲਾਈਨ ਵਿੱਚ ਦਰਜ ਕਰਨਾ ਰਿਲੀਜ਼/ਨਾਈਟਲੀ ਕੰਮ ਹੈ, ਫੀਚਰ PR ਦਾ ਨਹੀਂ:

ਲੋਕਲ ਰਨ) ਵਿੱਚ ਦਰਜ ਨਾ ਕੀਤੇ ਸੁਧਾਰ ਨੂੰ ਅਸਫਲ ਕਰਦਾ ਹੈ। ਫੀਚਰ PR ਵਿੱਚ (`pr` ਗੇਟ ਮੋਡ)
ਇਹ ਸੁਧਾਰ ਨੂੰ ਜਾਣਕਾਰੀ ਵਜੋਂ ਦਿਖਾਉਂਦਾ ਹੈ ਅਤੇ ਪਾਸ ਹੋ ਜਾਂਦਾ ਹੈ; ਰਿਗ੍ਰੈਸ਼ਨ ਦੋਵਾਂ ਮੋਡਾਂ ਵਿੱਚ

[ਤਿਆਰ ਕੀਤੀਆਂ ਫਾਈਲਾਂ ਅਤੇ ਰਿਲੀਜ਼ ਸਮੇਂ ਲਿਖੀਆਂ ਜਾਣ ਵਾਲੀਆਂ ਡੈਰੀਵਡ ਬੇਸਲਾਈਨਾਂ](#generated-files-and-derived-baselines-written-at-release)।

### CodeQL ਰੈਚੇਟ: ਰਿਫ੍ਰੈਸ਼ ਅੰਤਰਾਲ ਅਤੇ ਮੈਨੁਅਲ ਟ੍ਰਿਗਰ

`check:codeql-ratchet` **ਰਿਪੋਜ਼ਟਰੀ ਦੀ ਸਥਿਤੀ ਪੜ੍ਹਦਾ ਹੈ, ਜੋ ਸ਼ਡਿਊਲ ਅਨੁਸਾਰ ਰਿਫ੍ਰੈਸ਼ ਹੁੰਦੀ ਹੈ — ਹਰ PR ਲਈ ਨਹੀਂ।**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ਇਹ ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ
`state: configured`, `schedule: weekly`: ਇਹ GitHub ਦਾ ਡਿਫਾਲਟ-ਸੈਟਅੱਪ ਸਕੈਨ ਹੈ, ਹਰ push ਲਈ
ਵਿਸ਼ਲੇਸ਼ਣ ਨਹੀਂ। ਨਤੀਜਾ: ਅਲਰਟ ਠੀਕ ਕਰਨ ਵਾਲਾ PR ਮਰਜ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਅਗਲਾ ਸ਼ਡਿਊਲ ਕੀਤਾ ਸਕੈਨ
ਚੱਲਣ ਤੱਕ ਰੈਚੇਟ ਪੁਰਾਣੀ, ਵੱਧ ਗਿਣਤੀ ਪੜ੍ਹਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਇਹ ਹਰ ਖੁੱਲ੍ਹੇ PR ਵਿੱਚ
ਰਿਗ੍ਰੈਸ਼ਨ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ, ਠੀਕ ਕਰਨ ਵਾਲੇ PR ਦੇ ਆਪਣੇ ਅਗਲੇ PR ਵਿੱਚ ਵੀ, ਜਦ ਤੱਕ ਸਕੈਨ ਨਵੀਂ
ਸਥਿਤੀ ਨਹੀਂ ਲੈ ਲੈਂਦਾ।

**ਮੈਨੁਅਲ ਰਿਫ੍ਰੈਸ਼**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ਵਿਸ਼ਲੇਸ਼ਣ ਨੂੰ
ਦੁਬਾਰਾ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਕੁਝ ਮਿੰਟਾਂ ਵਿੱਚ ਅਲਰਟ ਮੁੜ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਪਹਿਲਾਂ
`.github/workflows/codeql.yml` ਪੜ੍ਹੋ — ਇਸਦਾ ਹੈਡਰ ਦੱਸਦਾ ਹੈ ਕਿ ਇਹ ਸਿਰਫ਼
`workflow_dispatch` ਹੈ **ਕਿਉਂਕਿ ਇਹ GitHub ਦੇ "default setup" ਨਾਲ ਟਕਰਾਉਂਦਾ ਹੈ**
(`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`)।
`push`/`pull_request`/`schedule` ਟ੍ਰਿਗਰ ਮੁੜ ਸਰਗਰਮ ਕਰਨ ਲਈ ਪਹਿਲਾਂ **ਮਾਲਕ ਦੀ ਕਾਰਵਾਈ ਲਾਜ਼ਮੀ ਹੈ**:
Settings → Code security → CodeQL: Default → Advanced। ਉਸ ਸਵਿੱਚ ਤੋਂ ਬਿਨਾਂ
` schedule:` ਟ੍ਰਿਗਰ ਨਾ ਜੋੜੋ — ਇਸ ਨਾਲ ਸਿਰਫ਼ ਅਸਫਲ ਰਨ ਬਣਣਗੇ।

**ਗਿਣਤੀ ਘਟਣ ਤੋਂ ਬਾਅਦ ਬੇਸਲਾਈਨ ਨੂੰ ਕੱਸੋ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ਨਵੀਂ ਮਾਪੀ ਗਈ ਗਿਣਤੀ ਨੂੰ `quality-baseline.json` →
`metrics.codeqlAlerts.value` ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਤਾਂ ਜੋ ਰੈਚੇਟ ਪੁਰਾਣੀ ਉੱਚੀ ਸੀਮਾ ਤੱਕ ਮੁੜ
ਵਧਣ ਵਾਲੇ ਰਿਗ੍ਰੈਸ਼ਨ ਨੂੰ ਚੁੱਪਚਾਪ ਮਨਜ਼ੂਰ ਨਾ ਕਰੇ। ਕੰਮ ਕੀਤਾ ਉਦਾਹਰਨ (2026-09-02/03):
PR #12502 ਨੇ 7 ਅਸਲ ਅਲਰਟ ਠੀਕ ਕੀਤੇ (13 → 6 ਮਾਪੇ ਗਏ ਖੁੱਲ੍ਹੇ ਅਲਰਟ); PR #12530 ਨੇ
ਫ੍ਰੀਜ਼ ਕੀਤੀ ਬੇਸਲਾਈਨ ਨੂੰ ਮਿਲਾਉਣ ਲਈ 11 → 6 ਤੱਕ ਕੱਸਿਆ; ਬਾਕੀ 6 ਨੂੰ ਫਿਰ ਹਰੇਕ ਅਲਰਟ ਲਈ

**Dismissal ਓਪਰੇਟਰ ਦਾ ਫੈਸਲਾ ਹੈ (Hard Rule #14)** — ਕਿਸੇ ਵੀ CodeQL ਅਲਰਟ ਨੂੰ

ਸਵੀਕਾਰਯੋਗ ਬਣਾਉਂਦਾ ਹੈ। ਇਹ `--update` ਤੋਂ ਬਾਅਦ ਵਾਲੇ ਟ੍ਰੀ ਦੀ `HEAD` ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ ਅਤੇ **ਕੋਈ ਵੀ ਕਮਿਟ
ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਜੌਬ ਨੂੰ ਰੋਕ ਦਿੰਦਾ ਹੈ** — ਕੋਈ PR ਨਹੀਂ ਖੋਲ੍ਹਦਾ — ਜਦੋਂ ਤੱਕ ਹਰ ਤਬਦੀਲੀ ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਇੱਕ ਨਾ ਹੋਵੇ:

- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ

ਹੋਰ ਕੁਝ ਵੀ ਅਸਫਲ ਹੁੰਦਾ ਹੈ: ਕੋਈ ਸੰਖਿਆ ਵਧਾਉਣਾ, ਐਂਟਰੀ ਜੋੜਨਾ, `cap`/`testCap` ਬਦਲਣਾ, ਜਾਂ

## ਮਨਜ਼ੂਰ-ਸੂਚੀ ਨੀਤੀ

ਹਰੇਕ ਗੇਟ ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਉਲੰਘਣਾਵਾਂ ਕਾਰਨ ਫੇਲ੍ਹ ਨਹੀਂ ਹੋ ਸਕਦਾ, ਇੱਕ ਜਮੀ ਹੋਈ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਵਰਤਦਾ ਹੈ
(ਜਿਵੇਂ, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ਨੀਤੀ ਇਹ ਹੈ:

**ਮੂਲ ਕਾਰਨ ਠੀਕ ਕਰੋ; ਮਨਜ਼ੂਰ-ਸੂਚੀ ਦੀ ਵਰਤੋਂ ਸਿਰਫ਼ ਉਦੋਂ ਕਰੋ ਜਦੋਂ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੋਵੇ ਅਤੇ
ਉਸੇ PR ਵਿੱਚ ਠੀਕ ਨਾ ਕੀਤੀ ਜਾ ਸਕੇ।**

ਮਨਜ਼ੂਰ-ਸੂਚੀ ਵਿੱਚ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰਦੇ ਸਮੇਂ:

1. ਜਾਇਜ਼ ਠਹਿਰਾਉਣ ਵਾਲੀ ਟਿੱਪਣੀ ਸ਼ਾਮਲ ਕਰੋ।
2. ਟ੍ਰੈਕਿੰਗ ਇਸ਼ੂ ਦਾ ਹਵਾਲਾ ਦਿਓ (ਜਿਵੇਂ, `// #3498 — Phase 2 feature, not yet implemented`)।
3. ਉਲੰਘਣਾ ਠੀਕ ਕਰਨ ਵਾਲੇ ਉਸੇ PR ਵਿੱਚ ਐਂਟਰੀ ਹਟਾਓ — ਇੱਕ ਪੁਰਾਣੀ ਐਂਟਰੀ ਜੋ ਹੁਣ ਸਰਗਰਮ ਉਲੰਘਣਾ ਨੂੰ
   ਦਬਾਉਂਦੀ ਨਹੀਂ, ਆਪਣੇ ਆਪ ਵਿੱਚ ਇੱਕ ਖਾਮੀ ਹੈ (ਲਾਗੂ ਹੋਣ ਤੋਂ ਬਾਅਦ 6A.3 stale-enforcement
   ਇੱਕ ਅਨਾਥ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਐਂਟਰੀ ਉੱਤੇ ਗੇਟ ਫੇਲ੍ਹ ਕਰੇਗਾ)।

ਟੈਸਟ ਤੇਜ਼ੀ ਨਾਲ ਪਾਸ ਕਰਵਾਉਣ ਲਈ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਐਂਟਰੀਆਂ ਨਾ ਸ਼ਾਮਲ ਕਰੋ। ਵਧਦੀ ਹੋਈ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਦੇ ਨਾਲ ਹਰਾ ਗੇਟ
ਗੁਣਵੱਤਾ ਦਾ ਇੱਕ ਝੂਠਾ ਭਰੋਸਾ ਹੁੰਦਾ ਹੈ।

### ਜਦੋਂ ਤੁਹਾਡੇ PR ਵਿੱਚ ਕੋਈ ਗੇਟ ਫੇਲ੍ਹ ਹੋਵੇ

1. **ਗੇਟ ਦਾ ਆਉਟਪੁੱਟ ਧਿਆਨ ਨਾਲ ਪੜ੍ਹੋ** — ਇਹ ਤੁਹਾਨੂੰ ਬਿਲਕੁਲ ਦੱਸਦਾ ਹੈ ਕਿ ਕਿਹੜੀ ਫ਼ਾਈਲ ਜਾਂ ਸਿੰਬਲ ਨੇ
   ਨਿਯਮ ਦੀ ਉਲੰਘਣਾ ਕੀਤੀ ਹੈ।
2. **ਉਲੰਘਣਾ ਠੀਕ ਕਰੋ** — ਜ਼ਿਆਦਾਤਰ ਗੇਟ ਨਿਰਧਾਰਿਤ ਫ਼ਾਈਲ-ਸਿਸਟਮ ਜਾਂਚਾਂ ਹੁੰਦੀਆਂ ਹਨ ਜੋ ਕੋਡ ਸਹੀ ਹੁੰਦੇ ਹੀ
   ਪਾਸ ਹੋ ਜਾਂਦੀਆਂ ਹਨ।
3. **ਜੇ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੈ** (ਅਰਥਾਤ, ਤੁਸੀਂ ਇਸਨੂੰ ਸ਼ਾਮਲ ਨਹੀਂ ਕੀਤਾ ਪਰ ਗੇਟ ਹੁਣ ਇਸਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ):
   ਜਾਇਜ਼ ਠਹਿਰਾਉਣ ਵਾਲੀ ਟਿੱਪਣੀ ਅਤੇ ਟ੍ਰੈਕਿੰਗ ਇਸ਼ੂ ਦੇ ਨਾਲ ਇੱਕ ਮਨਜ਼ੂਰ-ਸੂਚੀ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰੋ।
4. **ਜੇ ਗੇਟ ਇੱਕ ਰੈਚੇਟ ਹੈ** (ਕਵਰੇਜ, ESLint ਚੇਤਾਵਨੀਆਂ, ਡੁਪਲੀਕੇਸ਼ਨ, ਜਟਿਲਤਾ):
   ਤੁਹਾਡੀ ਤਬਦੀਲੀ ਨੇ ਮੈਟਰਿਕ ਨੂੰ ਖ਼ਰਾਬ ਕੀਤਾ ਹੈ। ਅੰਦਰੂਨੀ ਸਮੱਸਿਆ ਠੀਕ ਕਰੋ, ਜਾਂ (ਬਹੁਤ ਘੱਟ ਮਾਮਲਿਆਂ ਵਿੱਚ)
   `npm run quality:ratchet -- --update` ਚਲਾਓ, ਜੇ ਤਬਦੀਲੀ ਜਾਣ-ਬੁੱਝ ਕੇ ਕੀਤੀ ਗਈ ਹੈ ਅਤੇ ਮੈਟਰਿਕ ਦਾ ਘਟਣਾ ਸਵੀਕਾਰਯੋਗ ਹੈ —
   ਪਰ PR ਦੇ ਵੇਰਵੇ ਵਿੱਚ ਇਸਦਾ ਕਾਰਨ ਦਰਜ ਕਰੋ।
5. **ਸਲਾਹਕਾਰੀ ਗੇਟ** (`continue-on-error: true`) ਜਾਣਕਾਰੀ ਲਈ ਹੁੰਦੇ ਹਨ — ਇਹ
   ਮਰਜ ਨੂੰ ਰੋਕਦੇ ਨਹੀਂ, ਪਰ CI ਸਾਰ ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦੇ ਹਨ। ਫਿਰ ਵੀ ਇਨ੍ਹਾਂ ਨੂੰ ਠੀਕ ਕਰੋ।

## ਨਵਾਂ ਗੇਟ ਸ਼ਾਮਲ ਕਰਨਾ

1. `scripts/check/check-<name>.mjs` (ਜਾਂ `.ts`) ਬਣਾਓ। ਨੀਤੀ ਗੇਟ 0/1 ਨਾਲ ਬੰਦ ਹੁੰਦੇ ਹਨ।
   ਰੈਚਿਟ-ਸ਼ੈਲੀ ਗੇਟ `collect-metrics.mjs` ਰਾਹੀਂ `quality-metrics.json` ਵਿੱਚ ਇੱਕ ਮਾਪਦੰਡ ਲਿਖਦੇ ਹਨ।
2. `package.json` ਵਿੱਚ `"check:<name>": "node scripts/check/check-<name>.mjs"` ਸ਼ਾਮਲ ਕਰੋ।
3. ਇਸਨੂੰ `.github/workflows/ci.yml` ਵਿੱਚ ਢੁਕਵੀਂ ਜੌਬ ਹੇਠ ਜੋੜੋ
   (ਨੀਤੀ → `lint` ਜਾਂ `docs-sync-strict`; ਰੈਚਿਟ → `quality-gate`)।
4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

ਡਾਇਗਨੋਸਟਿਕਸ ਦਾ ਨਿਰਾਕਰਨ ਕਰਨ — `typecheck:core` ਦਾ ਇੱਕ ਕੰਪਾਇਲ-ਕਰਨ-ਤੋਂ-ਪਹਿਲਾਂ-ਦਾਅਵਾ ਸਾਥੀ,
ਜੋ "ਘੜੇ ਹੋਏ ਚਿੰਨ੍ਹ" ਵਾਲੀਆਂ ਗਲਤੀਆਂ ਨੂੰ ਸਰੋਤ ਉੱਤੇ ਹੀ ਘਟਾਉਂਦਾ ਹੈ। ਇਸਨੂੰ ਜਾਣਬੁੱਝ ਕੇ
ਆਪਣੇ ਆਪ ਲੋਡ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ (ਤੁਸੀਂ MCP↔LSP ਬ੍ਰਿਜ ਚੁਣਦੇ ਅਤੇ ਤਸਦੀਕ ਕਰਦੇ ਹੋ); ਇੱਕ ਖ਼ਰਾਬ ਐਂਟਰੀ ਸਿਰਫ਼
ਕਨੈਕਸ਼ਨ ਗਲਤੀ ਲੌਗ ਕਰਦੀ ਹੈ ਅਤੇ ਕਦੇ ਵੀ ਸੈਸ਼ਨਾਂ ਨੂੰ ਭੰਗ ਨਹੀਂ ਕਰਦੀ।

### ਮਰਜ / ਡੀਡੁਪ (ਮਕੈਨਿਕਲ, ਘੱਟ ਜੋਖ਼ਮ)

ਹਰੇਕ ਉਮੀਦਵਾਰ ਨੂੰ 2026-06-17 ਨੂੰ ਲਾਈਵ ਗੇਟ ਸਥਿਤੀ ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਗਿਆ
(ਭਰੋਸਾ ਕਰੋ—ਪਰ ਪੁਸ਼ਟੀ ਵੀ ਕਰੋ); ਕਈ “ਸਪਸ਼ਟ” ਮਰਜਾਂ ਵਿੱਚ ਲੁਕਿਆ ਕਰਜ਼ਾ ਮਿਲਿਆ ਅਤੇ ਉਹ
**ਸਿੱਧੇ ਡ੍ਰੌਪ-ਇਨ ਨਹੀਂ ਹਨ।**

- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼ ਮਰਜ ਨਹੀਂ।** `audit:deps` ਸਾਰੀਆਂ ਪੰਜ ਲੌਕਫ਼ਾਈਲਾਂ ਵਿੱਚ critical advisories ਅਤੇ ਅਧੂਰੇ audits ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ, ਜਦਕਿ ਮੌਜੂਦਾ ਨੀਤੀ ਅਧੀਨ high advisories ਨੂੰ ਚੇਤਾਵਨੀਆਂ ਵਜੋਂ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਚੈੱਕ-ਇਨ ਕੀਤੇ baseline ਦੇ ਮੁਕਾਬਲੇ _regression_ ਹੋਣ ’ਤੇ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ ਅਤੇ ਲੋੜ ਪੈਣ ’ਤੇ ਗੁੰਮ ਮਾਪਾਂ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਅਰਥ-ਵਿਗਿਆਨ ਵੱਖਰੇ ਹਨ — `audit:deps` ਹਟਾਉਣ ਨਾਲ absolute critical gate ਅਤੇ ਸੁਤੰਤਰ package audit receipts ਖਤਮ ਹੋ ਜਾਣਗੇ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਸਾਈਕਲ ਡਿਟੈਕਸ਼ਨ** — ✅ **ਪੂਰਾ** (#15159 G-01/G-02)। ਇੱਥੇ ਪੁਰਾਣੇ ਟੈਕਸਟ ਵਿੱਚ `check:cycles` ਨੂੰ “green, curated” ਗੇਟ ਕਿਹਾ ਗਿਆ ਸੀ ਅਤੇ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖਣ ਦਾ ਕਾਰਨ ਦਿੱਤਾ ਗਿਆ ਸੀ ਕਿਉਂਕਿ `check:circular-deps` (dpdm) ਨੇ 91 cycles ਰਿਪੋਰਟ ਕੀਤੇ ਸਨ। ਉਹ ਹਰਾ ਨਤੀਜਾ **ਝੂਠਾ ਹਰਾ** ਸੀ: `check:cycles` ਨੇ 5 subdirectories (450 files) ਸਕੈਨ ਕੀਤੀਆਂ, ਸਿਰਫ਼ static `import|export … from` ਨਾਲ ਮੇਲ ਖਾਧਾ ਅਤੇ ਹਰ `@/` ਅਤੇ `@omniroute/open-sse/` specifier ਨੂੰ ਛੱਡ ਦਿੱਤਾ, ਇਸ ਲਈ ਇਹ ਰਿਪੋ ’ਤੇ ਹਾਵੀ dynamic-import + alias cycles ਨੂੰ ਦੇਖ ਹੀ ਨਹੀਂ ਸਕਿਆ। ਠੀਕ ਕੀਤਾ ਗਿਆ: ਹੁਣ ਗੇਟ `src` + `open-sse` (5023 files) ਵਿੱਚ ਜਾਂਦਾ ਹੈ, TypeScript AST ਤੋਂ specifiers ਇਕੱਠੇ ਕਰਦਾ ਹੈ (ਇਸ ਲਈ `import("…")` ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ type-position `typeof import("…")` ਨਹੀਂ) ਅਤੇ tsconfig `paths` ਨੂੰ resolve ਕਰਦਾ ਹੈ। ਇਸਨੂੰ 0 ਨਹੀਂ, **14** cycles ਮਿਲਦੇ ਹਨ। ਕਿਉਂਕਿ 14 ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ cycles ਨੂੰ gate PR ਵਿੱਚ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, `check:cycles` ਹੁਣ ਇੱਕ **ਰੈਸ਼ਟ** ਹੈ (`--ratchet`, `quality-baseline.json` ਵਿੱਚ ceiling `metrics.cycles.value = 14`, `direction: down`) — ਇਹ ਕਿਸੇ ਵੀ _regression_ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ ਅਤੇ ਗਿਣਤੀ ਸਿਰਫ਼ ਘਟ ਸਕਦੀ ਹੈ। CI `npm run check:cycles:ratchet` ਚਲਾਉਂਦਾ ਹੈ। ਬਰਨ-ਡਾਊਨ **A-01** ਦੇ ਨਾਲ ਹੋਵੇਗਾ। `check:circular-deps` (dpdm) ਵਿਆਪਕ ਦੂਜੀ ਰਾਏ ਵਜੋਂ ਸਲਾਹਕਾਰੀ ਰਹਿੰਦਾ ਹੈ।
- **ਕੰਪਲੈਕਸਿਟੀ** — ✅ **ਪੂਰਾ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, ruleId ਅਨੁਸਾਰ ਗਿਣਤੀ ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive baselines ਸੁਤੰਤਰ ਰਹਿਣ; ਵਿਅਕਤੀਗਤ `check:complexity` / `check:cognitive-complexity` ਸਥਾਨਕ `--update` ਲਈ ਬਣੇ ਰਹਿੰਦੇ ਹਨ।
