## ਇੱਕ ਰੀਲਿਜ਼ ਸ਼ਾਖਾ 'ਤੇ ਲੈਂਡਿੰਗ

ਓਮਨੀ-ਕਤਾਰ `release/vX.Y.Z` ਵਿੱਚ ਲੈਂਡਿੰਗ ਨੂੰ ਨਿਯੰਤ੍ਰਿਤ ਕਰਦੀ ਹੈ। PR ਤੇ ਉਤਰਨ ਤੋਂ ਪਹਿਲਾਂ ਡਿਫੌਲਟ ਬ੍ਰਾਂਚ 'ਤੇ `config/merge-queue/config.json` ਵਿਚ ਉੱਚ-ਪੱਧਰੀ `mode` ਪੜ੍ਹੋ। [ਓਮਨੀ-ਕਤਾਰ](OMNI_QUEUE.md) ਦੇਖੋ।

- **`shadow`** ਪ੍ਰਮਾਣਿਕਤਾ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਲੈਂਡਿੰਗ ਨੂੰ ਮੈਨੂਅਲ ਅਭੇਦ 'ਤੇ ਛੱਡਦਾ ਹੈ। ਇਸ ਦੇ ਅੰਤਮ ਸਿਰਲੇਖ 'ਤੇ ਪ੍ਰਵਾਨਿਤ PR 'ਤੇ `omni-queue` ਲਾਗੂ ਕਰੋ। `npm run queue -- why <PR>` ਨਾਲ ਯੋਗਤਾ ਦੀ ਜਾਂਚ ਕਰੋ। `npm run queue -- history --base <branch>` ਵਿੱਚ ਉਸ ਸਿਰ ਦੇ ਫੈਸਲੇ ਦੀ ਉਡੀਕ ਕਰੋ। `would-land` ਤੇ ਅੱਗੇ ਵਧੋ। `culprit-found` ਜਾਂ `would-dequeue` ਤੇ, ਅਭੇਦ ਨੂੰ ਫੜੋ ਅਤੇ ਕਾਰਨ ਨੂੰ ਠੀਕ ਕਰੋ।
- **ਸ਼ੈਡੋ ਅਪਵਾਦ।** ਮੌਜੂਦਾ ਬੇਸ ਟਿਪ ਦੇ ਵਿਰੁੱਧ ਹਰੇ ਰੰਗ ਦੀ ਪੂਰੀ CI ਵਾਲੀ ਰੇਲਗੱਡੀ ਇੱਕ ਵੱਖਰੀ ਕਤਾਰ ਦੇ ਫੈਸਲੇ ਤੋਂ ਬਿਨਾਂ ਅੱਗੇ ਵਧ ਸਕਦੀ ਹੈ। ਇਹੀ ਅਪਵਾਦ ਉਦੋਂ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ PR ਹੈੱਡ ਵਿੱਚ ਪਹਿਲਾਂ ਹੀ ਮੌਜੂਦਾ ਅਧਾਰ ਟਿਪ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ।
- **`live`** ਲੈਂਡਿੰਗ ਨੂੰ ਟਰਿੱਗਰ ਕਰਨ ਲਈ `omni-queue` ਲੇਬਲ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। ਇਕੱਲੀ ਕਤਾਰ PR ਤੇ ਉਤਰਦੀ ਹੈ। ਮਰਜ ਕਮਾਂਡਾਂ ਨੂੰ ਛੱਡੋ ਅਤੇ ਕਤਾਰ 'ਤੇ ਸਿੱਧੀ ਪੁਸ਼ ਕਰੋ।

ਹਰ ਲੈਂਡਿੰਗ ਲਈ ਮਾਲਕ ਦੇ ਅਧਿਕਾਰ ਅਤੇ ਲਾਗੂ ਲੋੜੀਂਦੇ ਜਾਂਚਾਂ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ। ਮਾਲਕ ਦੁਆਰਾ ਲੈਂਡਿੰਗ ਦਾ ਅਧਿਕਾਰ ਦਿੱਤੇ ਜਾਣ ਤੋਂ ਬਾਅਦ ਹੀ `omni-queue` ਲਾਗੂ ਕਰੋ। ਕਤਾਰਬੱਧ PRs ਨੂੰ ਛੂਹਣ ਵਾਲੇ ਸੁਰੱਖਿਅਤ ਮਾਰਗਾਂ ਲਈ ਵੀ ਉਸ PR ਲਈ ਮਾਲਕ ਦੇ `protected-approved` ਫੈਸਲੇ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

"ਸਰਗਰਮ ਰੀਲੀਜ਼ 'ਤੇ ਹਰੇ ਦਰਵਾਜ਼ੇ ਦੀ ਲੋੜ ਹੈ" ਨਿਯਮ ਦੇ ਸਿਰ 'ਤੇ ਹਰੇ `Gate / CI` ਅਤੇ `Gate / Quality` ਲੋੜ ਹੁੰਦੀ ਹੈ। ਲਾਲ ਗੇਟ ਨੂੰ ਬਾਈਪਾਸ ਕਰਨ ਲਈ ਕਦੇ ਵੀ `--admin` ਦੀ ਵਰਤੋਂ ਨਾ ਕਰੋ। ਇੱਕ ਰੀਲਿਜ਼ ਫ੍ਰੀਜ਼ ਬਲਾਕ ਜੰਮੇ ਹੋਏ ਸ਼ਾਖਾ ਵਿੱਚ ਮਿਲ ਜਾਂਦੇ ਹਨ। [ਸਖ਼ਤ ਨਿਯਮ 21](HARD_RULES_DETAIL.md) ਦੇਖੋ। ਕਦੇ ਵੀ ਕਿਸੇ ਪੁੱਲ ਬੇਨਤੀ ਨੂੰ ਲੇਬਲ, ਵਿਲੀਨ ਜਾਂ ਪੁਸ਼ ਨਾ ਕਰੋ ਕਿ ਕੋਈ ਹੋਰ ਸੈਸ਼ਨ ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ। [ਸਖ਼ਤ ਨਿਯਮ 22](HARD_RULES_DETAIL.md) ਦੇਖੋ।

## ਰੇਲਗੱਡੀ ਖਿੱਚਣ ਦੀ ਬੇਨਤੀ

1. ਮੌਜੂਦਾ ਰੀਲੀਜ਼ ਬੇਸ ਟਿਪ 'ਤੇ ਰੇਲਗੱਡੀ ਸ਼ਾਖਾ ਸ਼ੁਰੂ ਕਰੋ। ਮਰਜ ਕਮਿਟਾਂ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਸਹੀ ਪ੍ਰਵਾਨਿਤ ਮੈਂਬਰ ਸਿਰਾਂ ਨੂੰ ਏਕੀਕ੍ਰਿਤ ਕਰੋ। ਸਕੁਐਸ਼ ਅਤੇ ਰੀਬੇਸ ਤੋਂ ਬਚ ਕੇ ਆਪਣੇ ਵਚਨਬੱਧ ਇਤਿਹਾਸ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖੋ।
2. ਰੇਲਗੱਡੀ ਸ਼ਾਖਾ ਲਈ ਇੱਕ ਪੁੱਲ ਬੇਨਤੀ ਖੋਲ੍ਹੋ। ਮੌਜੂਦਾ ਅਧਾਰ ਟਿਪ 'ਤੇ ਉਸ PR ਇਸਦੇ ਆਪਣੇ ਪੂਰੇ CI ਨਾਲ ਪ੍ਰਮਾਣਿਤ ਕਰੋ। ਲੈਂਡਿੰਗ ਤੋਂ ਪਹਿਲਾਂ ਅਧਾਰ ਟਿਪ ਅਤੇ ਪ੍ਰਵਾਨਿਤ ਮੈਂਬਰ ਸਿਰਾਂ ਦੀ ਮੁੜ ਜਾਂਚ ਕਰੋ। ਜਦੋਂ ਪ੍ਰਮਾਣਿਤ ਉਮੀਦਵਾਰ ਬਦਲਦਾ ਹੈ ਤਾਂ ਟ੍ਰੇਨ ਅਤੇ ਇਸਦੇ CI ਤਾਜ਼ਾ ਕਰੋ।
3. ਲਾਗੂ ਕਤਾਰ ਮੋਡ ਦੇ ਤਹਿਤ ਇੱਕ ਮਰਜ ਕਮਿਟ ਦੇ ਨਾਲ ਟ੍ਰੇਨ PR ਲੈਂਡ ਕਰੋ। ਲਾਈਵ ਮੋਡ ਵਿੱਚ, ਕਤਾਰ ਦੀ `merge-ff` ਲੈਂਡਿੰਗ ਵਿਧੀ ਮਰਜ ਕਮਿਟਾਂ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖਦੀ ਹੈ। ਰੀਲੀਜ਼ ਬ੍ਰਾਂਚ ਤੋਂ ਅਸਲੀ ਮੈਂਬਰ ਮੁਖੀ ਪਹੁੰਚਯੋਗ ਬਣ ਜਾਂਦੇ ਹਨ। GitHub ਮੈਂਬਰ PRs ਅਭੇਦ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕਰਦਾ ਹੈ ਅਤੇ ਕਮਿਟ ਆਪਣੇ ਲੇਖਕਾਂ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ।

ਇੱਕ ਜਨਤਕ ਉਦਾਹਰਨ [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071) ਹੈ। ਇਸਨੇ 18 ਮੈਂਬਰ PRs ਜੋੜਿਆ ਅਤੇ 2026-11-24 ਨੂੰ ਇੱਕ ਮਰਜ ਕਮਿਟ ਦੇ ਨਾਲ ਉਤਰਿਆ।

`main` ਤੋਂ ਅਗਲੀ ਰੀਲੀਜ਼ ਸ਼ਾਖਾ ਵਿੱਚ ਇੱਕ ਸਿੰਕ-ਬੈਕ ਵੀ ਇੱਕ ਮਰਜ ਕਮਿਟ ਦੁਆਰਾ ਉਤਰਦਾ ਹੈ। ਬਾਅਦ ਵਿੱਚ ਸਿੰਕ-ਬੈਕ ਲਈ `main` ਵੰਸ਼ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖਣਾ ਜ਼ਰੂਰੀ ਹੈ। [ਵਰਕਟਰੀ ਆਈਸੋਲੇਸ਼ਨ](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash) ਦੇਖੋ।

## ਸਥਾਨਕ ਅਭੇਦ-ਰੇਲ ਵੈਲੀਡੇਟਰ

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

ਵੈਲੀਡੇਟਰ ਬੇਸ ਅਤੇ PR ਹੈੱਡਾਂ ਨੂੰ ਲਿਆਉਂਦਾ ਹੈ ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਡਿਸਪੋਸੇਬਲ ਵਰਕਟਰੀ ਵਿੱਚ ਜੋੜਦਾ ਹੈ। ਇਹ ਨਤੀਜੇ ਵਾਲੇ ਰੁੱਖ 'ਤੇ ਇਕ ਵਾਰ ਆਪਣਾ ਸਮਾਨਤਾ ਸੂਟ ਚਲਾਉਂਦਾ ਹੈ। ਇੱਕ ਅਸਫਲ ਸਿਰ ਪ੍ਰਾਪਤੀ ਜਾਂ ਅਭੇਦ ਵਿਵਾਦ ਉਸ PR ਨੂੰ ਬਾਹਰ ਕੱਢਦਾ ਹੈ ਅਤੇ ਸਕ੍ਰਿਪਟ ਬਾਕੀ PRs ਨਾਲ ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ।

- **`--plan`** ਚੁਣੇ ਹੋਏ ਮੋਡ ਦੇ ਕਦਮਾਂ ਨੂੰ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ ਅਤੇ ਵਰਕਟਰੀ ਬਣਾਉਣ ਜਾਂ ਰਿਮੋਟ ਨਾਲ ਸੰਪਰਕ ਕੀਤੇ ਬਿਨਾਂ ਬਾਹਰ ਨਿਕਲਦਾ ਹੈ। ਤੇਜ਼ ਯੋਜਨਾ ਦਾ ਮੁਆਇਨਾ ਕਰਨ ਲਈ ਇਸਨੂੰ `--fast` ਨਾਲ ਜੋੜੋ।
- **`--fast`** ਆਮ ਸਥਿਰ ਗੇਟਾਂ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ, `tests/unit/` ਅਤੇ `npm run test:vitest` ਦੇ ਅਧੀਨ ਚੁਣੀਆਂ ਗਈਆਂ `node:test` ਫਾਈਲਾਂ ਨੂੰ ਬਦਲਿਆ ਗਿਆ ਹੈ। ਫਾਸਟ ਮੋਡ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਸਮੇਂ ਇਕੱਠੇ ਕੀਤੇ ਟਿਪ 'ਤੇ ਦਿਨ ਵਿੱਚ ਘੱਟੋ-ਘੱਟ ਇੱਕ ਵਾਰ ਪੂਰਾ ਸਥਾਨਕ ਪ੍ਰਮਾਣਿਕਤਾ ਚਲਾਓ।
- **ਪੂਰਾ ਮੋਡ** ਪੂਰੇ-ਸਿਰਫ਼ ਸਥਿਰ ਗੇਟਾਂ ਨੂੰ ਜੋੜਦਾ ਹੈ ਅਤੇ `npm run test:unit` ਅਤੇ `npm run test:vitest` ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ।

ਇੱਕ ਅਸਫ਼ਲ ਸਥਿਰ ਗੇਟ ਨੂੰ ਅਛੂਤ ਅਧਾਰ 'ਤੇ ਦੁਬਾਰਾ ਚਲਾਇਆ ਜਾਂਦਾ ਹੈ ਜੇਕਰ ਅਧਾਰ ਪੜਤਾਲ ਉਪਲਬਧ ਹੈ। ਸਕ੍ਰਿਪਟ ਵਿਰਾਸਤ ਵਿੱਚ ਪ੍ਰਾਪਤ ਅਸਫਲਤਾਵਾਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ ਅਤੇ ਉਦੋਂ ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ ਜਦੋਂ ਹਰ ਮਾਨਤਾ ਪ੍ਰਾਪਤ ਉਲੰਘਣਾ ਲਾਈਨ ਵੀ ਅਧਾਰ 'ਤੇ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ ਅਤੇ ਕੁੱਲ ਗਿਣਤੀ ਵਿੱਚ ਵਾਧਾ ਨਹੀਂ ਹੁੰਦਾ ਹੈ।

## ਟਾਇਰਿੰਗ

- **ਪ੍ਰਤੀ PR** CI ਅਤੇ ਬਦਲੇ ਗਏ ਮਾਰਗਾਂ ਦੇ ਆਧਾਰ 'ਤੇ ਕੁਆਲਿਟੀ ਦੀ ਚੋਣ ਕਰੋ। ਕੋਡ PRs CI ਵਿੱਚ ਵੱਖਰੀ ਇਕਾਈ ਅਤੇ Vitest ਨੌਕਰੀਆਂ ਦੇ ਨਾਲ, ਤੇਜ਼ ਗੁਣਵੱਤਾ ਵਾਲੇ ਗੇਟ ਅਤੇ ਪ੍ਰਭਾਵਤ ਟੈਸਟਾਂ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ।
- **ਪ੍ਰਤੀ ਕਤਾਰ ਉਮੀਦਵਾਰ।** CI ਅਤੇ ਕੁਆਲਿਟੀ ਇਸ ਦੇ ਕਤਾਰ ਰੈਫ 'ਤੇ ਬਣੇ ਉਮੀਦਵਾਰ ਲਈ ਪੂਰਾ ਪ੍ਰੋਫਾਈਲ ਚਲਾਉਂਦੇ ਹਨ।
- **ਪ੍ਰਤੀ ਰੀਲੀਜ਼ ਟਿਪ।** ਰੀਲੀਜ਼-ਗ੍ਰੀਨ ਪੁਸ਼ਾਂ 'ਤੇ ਤੇਜ਼ ਹਾਰਡ ਗੇਟਾਂ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ ਜੋ ਇਸਦੇ ਪਾਥ ਫਿਲਟਰਾਂ ਨਾਲ ਮੇਲ ਖਾਂਦੇ ਹਨ। ਪ੍ਰਤੀ ਦਿਨ ਤਿੰਨ ਅਨੁਸੂਚਿਤ ਰਨ ਰੀਲੀਜ਼ ਬ੍ਰਾਂਚ ਲਈ ਪੂਰੀ ਸਵੀਪ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹਨ।
- **ਪ੍ਰਤੀ ਰੀਲੀਜ਼.** ਪੂਰੇ CI ਮੈਟ੍ਰਿਕਸ ਵਿੱਚ E2E ਸ਼ਾਰਡਸ, ਪੈਕੇਜ ਪ੍ਰਮਾਣਿਕਤਾ, ਟਾਰਬਾਲ ਬੂਟ ਸਮੋਕ, ਅਤੇ ਕਵਰੇਜ ਜਾਂਚ ਸ਼ਾਮਲ ਹਨ। [ਰੀਲੀਜ਼ ਚੈੱਕਲਿਸਟ](RELEASE_CHECKLIST.md) ਦੇਖੋ।

## `merge-train.sh` ਲਈ ਤਾਜ਼ਾ-ਚੈੱਕਆਉਟ ਪੂਰਵ-ਸ਼ਰਤਾਂ

ਵਰਕਟਰੀਜ਼ ਬਣਾਉਣ ਤੋਂ ਪਹਿਲਾਂ ਪ੍ਰੀਫਲਾਈਟ ਚੱਲਦੀ ਹੈ। `npm ci` ਨਾਲ ਨਿਰਭਰਤਾ ਸਥਾਪਤ ਕਰੋ। ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `node_modules/.bin/tsc` ਚੱਲਣਯੋਗ ਹੈ ਅਤੇ `node_modules/node_modules` ਗੈਰਹਾਜ਼ਰ ਹੈ। ਜਾਂਚ ਕਰੋ ਕਿ `node_modules/.bin/bun --version` ਸਫਲ ਹੁੰਦਾ ਹੈ।

ਜੇਕਰ Bun ਪੋਸਟਇੰਸਟਾਲ ਛੱਡਿਆ ਗਿਆ ਸੀ, `(cd node_modules/bun && node install.js)` ਚਲਾਓ। ਪ੍ਰਦਾਤਾ ਦੀ ਇਕਸਾਰਤਾ ਅਤੇ ਜਾਣੇ-ਪਛਾਣੇ ਚਿੰਨ੍ਹ ਦੀ ਜਾਂਚ Bun ਵਰਤੋਂ ਕਰਦੀ ਹੈ। ਵੈਲੀਡੇਟਰ `npm run check:cycles:ratchet` ਬਲਾਕਿੰਗ ਗੇਟ ਵਜੋਂ ਚਲਾਉਂਦਾ ਹੈ। ਸਟੈਂਡਅਲੋਨ `npm run check:cycles` ਕਮਾਂਡ ਸਲਾਹਕਾਰੀ ਹੈ।
