ਇੱਕ pull request ਲਈ ਸਭ ਤੋਂ ਛੋਟਾ ਭਰੋਸੇਯੋਗ ਵਿਕਾਸ ਲੂਪ ਚੁਣਨ ਵਾਸਤੇ ਇਸ ਗਾਈਡ ਦੀ ਵਰਤੋਂ ਕਰੋ। ਇਹ ਹੇਠਾਂ ਲਿੰਕ ਕੀਤੇ ਖੇਤਰ-ਵਿਸ਼ੇਸ਼ ਆਰਕੀਟੈਕਚਰ ਅਤੇ ਸੁਰੱਖਿਆ ਦਸਤਾਵੇਜ਼ਾਂ ਦੀ ਥਾਂ ਨਹੀਂ ਲੈਂਦੀ; ਇਹ ਹਰ ਆਮ ਤਬਦੀਲੀ ਦੀ ਕਿਸਮ ਨੂੰ ਉਸਦੇ ਇਕਰਾਰਨਾਮਿਆਂ, ਕੇਂਦਰਿਤ ਜਾਂਚਾਂ ਅਤੇ CI ਕਵਰੇਜ ਨਾਲ ਜੋੜਦੀ ਹੈ।

## ਹਰ ਤਬਦੀਲੀ ਵੱਲੋਂ ਅਪਣਾਇਆ ਜਾਣ ਵਾਲਾ ਮਾਰਗ

1. **ਸੰਪਾਦਨ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਬੇਸ ਚੁਣੋ।** ਸਭ ਤੋਂ ਉੱਚੀ ਸਰਗਰਮ `release/v*` ਬ੍ਰਾਂਚ ਲੱਭੋ ਅਤੇ
   ਉਸਦੇ ਸਿਰੇ ਤੋਂ ਬ੍ਰਾਂਚ ਬਣਾਓ। ਉਸ ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਕਰੋ, `main` ਨੂੰ ਨਹੀਂ। ਜੇ ਰਿਲੀਜ਼ ਫ੍ਰੀਜ਼ ਸਰਗਰਮ ਹੈ, ਤਾਂ ਫ੍ਰੀਜ਼ ਕੀਤੀ
   ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਨਾ ਕਰੋ; ਇਸ ਦੀ ਬਜਾਏ
   [ਬ੍ਰਾਂਚਿੰਗ ਅਤੇ ਰਿਲੀਜ਼ ਮਾਡਲ](BRANCHING_MODEL.md) ਵਿੱਚ ਵਰਣਿਤ ਅਗਲੇ ਸਰਗਰਮ ਚੱਕਰ ਦੀ ਵਰਤੋਂ ਕਰੋ।
2. **ਇਕਰਾਰਨਾਮਿਆਂ ਦੇ ਨਾਮ ਦਿਓ।** ਹਰ ਉਸ ਕੈਟਾਲਾਗ, ਸਕੀਮਾ, ਜਨਰੇਟ ਕੀਤੀ ਆਰਟੀਫੈਕਟ, ਜਨਤਕ API, ਜਾਂ ਵਰਤੋਂਕਾਰ
   ਇੰਟਰਫੇਸ ਦੀ ਪਛਾਣ ਕਰੋ ਜਿਸ ਨੂੰ ਤਬਦੀਲੀ ਪ੍ਰਭਾਵਿਤ ਕਰਦੀ ਹੈ। ਹੇਠਾਂ ਦਿੱਤੀ ਸਾਰਣੀ ਘੱਟੋ-ਘੱਟ ਸ਼ੁਰੂਆਤੀ ਸੈੱਟ ਦਿੰਦੀ ਹੈ।
3. **ਕੇਂਦਰਿਤ ਟੈਸਟ ਲਿਖੋ ਜਾਂ ਅੱਪਡੇਟ ਕਰੋ।** `src/`, `open-sse/`, `electron/`, ਜਾਂ
   `bin/` ਵਿੱਚ ਪ੍ਰੋਡਕਸ਼ਨ ਤਬਦੀਲੀਆਂ ਲਈ ਉਸੇ PR ਵਿੱਚ ਇੱਕ ਆਟੋਮੇਟਡ ਟੈਸਟ ਲੋੜੀਂਦਾ ਹੈ। ਸਭ ਤੋਂ ਛੋਟੀਆਂ ਟੈਸਟ ਫਾਈਲਾਂ ਚਲਾਓ ਜੋ
   ਵਿਹਾਰ ਨੂੰ ਸਾਬਤ ਕਰਦੀਆਂ ਹਨ, ਫਿਰ ਸੂਚੀਬੱਧ ਕੇਂਦਰਿਤ ਗੇਟ ਚਲਾਓ।
4. **CI ਨੂੰ ਵਿਆਪਕ ਮੈਟ੍ਰਿਕਸ ਚਲਾਉਣ ਦਿਓ।** ਪੂਰੇ ਯੂਨਿਟ ਸ਼ਾਰਡ, Vitest, ਕਵਰੇਜ ਰੈਚਟ, ਅਤੇ
   ਪ੍ਰੋਡਕਸ਼ਨ ਬਿਲਡ PR ਉੱਤੇ ਚੱਲਦੇ ਹਨ। ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਵਿਆਪਕ ਸੂਟ ਸਿਰਫ਼ ਉਦੋਂ ਚਲਾਓ ਜਦੋਂ ਕੋਈ ਕੇਂਦਰਿਤ ਅਸਫਲਤਾ
   ਵਿਆਪਕ ਪ੍ਰਭਾਵ ਵੱਲ ਸੰਕੇਤ ਕਰਦੀ ਹੋਵੇ ਜਾਂ ਜਦੋਂ ਤਬਦੀਲੀ ਕਈ ਸਬਸਿਸਟਮਾਂ ਤੱਕ ਫੈਲੀ ਹੋਵੇ।
5. **ਸਮੀਖਿਆ ਤੋਂ ਪਹਿਲਾਂ ਤਾਲਮੇਲ ਕਰੋ।** ਸਰਗਰਮ ਬੇਸ ਨੂੰ ਫੈਚ ਕਰੋ, ਉਸਦੇ ਨਵੇਂ ਕਮਿਟਾਂ ਅਤੇ ਉਸਦੇ ਮੁਕਾਬਲੇ ਆਪਣੇ ਡਿਫ਼ ਦੀ
   ਜਾਂਚ ਕਰੋ, ਫਿਰ ਯੋਗਦਾਨਕਰਤਾ ਵਰਕਫਲੋ ਅਨੁਸਾਰ ਬੇਸ ਨੂੰ ਰੀਬੇਸ ਜਾਂ ਮਰਜ ਕਰੋ। ਜਨਰੇਟ ਕੀਤੀ ਫਾਈਲ ਅਤੇ ਕੈਟਾਲਾਗ
   ਟਕਰਾਵਾਂ ਨੂੰ ਉਨ੍ਹਾਂ ਦੇ ਸਰੋਤ ਤੋਂ ਹੱਲ ਕਰੋ, ਉਨ੍ਹਾਂ ਨੂੰ ਮੁੜ ਜਨਰੇਟ ਕਰੋ, ਕੇਂਦਰਿਤ ਲੂਪ ਦੁਬਾਰਾ ਚਲਾਓ, ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ
   PR ਹਾਲੇ ਵੀ ਸਰਗਰਮ ਰਿਲੀਜ਼ ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਕਰਦਾ ਹੈ।
6. **ਸਬੂਤ ਦਰਜ ਕਰੋ।** PR ਟੈਂਪਲੇਟ ਵਿੱਚ ਚਲਾਈਆਂ ਗਈਆਂ ਕਮਾਂਡਾਂ, ਜੋੜੀ ਜਾਂ ਬਦਲੀ ਗਈ ਹਰ ਟੈਸਟ ਫਾਈਲ,
   ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਜਾਂ ਫੀਚਰ ਫਲੈਗਾਂ, ਅਤੇ ਹਾਲੇ ਬਾਕੀ ਕਿਸੇ ਵੀ ਸਿਰਫ਼-CI ਪ੍ਰਮਾਣਿਕਤਾ ਨੂੰ ਸੂਚੀਬੱਧ ਕਰੋ।

## ਤਬਦੀਲੀ ਦੀ ਕਿਸਮ ਅਨੁਸਾਰ ਸੁਨਹਿਰੀ ਮਾਰਗ

ਹੇਠਾਂ ਦਿੱਤੀਆਂ ਕਮਾਂਡਾਂ ਘੱਟੋ-ਘੱਟ ਕੇਂਦਰਿਤ ਜਾਂਚਾਂ ਹਨ, ਤੁਹਾਡੇ ਵੱਲੋਂ ਬਦਲੇ ਗਏ ਵਿਹਾਰ ਨੂੰ ਸਿੱਧੇ ਤੌਰ 'ਤੇ ਕਵਰ ਕਰਨ ਵਾਲਾ
ਟੈਸਟ ਛੱਡਣ ਦੀ ਇਜਾਜ਼ਤ ਨਹੀਂ।

### ਪ੍ਰਦਾਤਾ

**ਇਕਰਾਰਨਾਮੇ**

- `src/shared/constants/providers/` ਵਿੱਚ ਪ੍ਰਦਾਤਾ ਦੀ ਪਰਿਭਾਸ਼ਾ ਅਤੇ
  `src/shared/constants/providers.ts` ਵਿੱਚ ਉਸਦੀ ਰਚਨਾ।
- `open-sse/config/providerRegistry.ts` ਜਾਂ ਇਸ ਦੀਆਂ ਵੱਖ ਕੀਤੀਆਂ ਰਜਿਸਟਰੀ ਫਾਈਲਾਂ ਵਿੱਚ ਮਾਡਲ ਅਤੇ ਸਮਰੱਥਾਵਾਂ।
- ਲਾਗੂ ਹੋਣ 'ਤੇ ਐਗਜ਼ੀਕਿਊਟਰ/ਟ੍ਰਾਂਸਲੇਟਰ ਚੋਣ, OAuth ਜਾਂ API-key ਸੰਰਚਨਾ, ਡੈਸ਼ਬੋਰਡ ਐਸੈੱਟ, ਅਤੇ ਜਨਰੇਟ ਕੀਤਾ
  ਪ੍ਰਦਾਤਾ ਹਵਾਲਾ।
- ਜਨਤਕ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ ਲਈ `resolvePublicCred()` ਦੀ ਵਰਤੋਂ ਲਾਜ਼ਮੀ ਹੈ; ਗਲਤੀ ਜਵਾਬਾਂ ਲਈ ਸਾਂਝੇ ਸੈਨਿਟਾਈਜ਼ ਕੀਤੇ
  ਗਲਤੀ ਹੈਲਪਰ ਵਰਤਣੇ ਲਾਜ਼ਮੀ ਹਨ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ) ਅਤੇ
  [ਗਲਤੀ ਸੈਨਿਟਾਈਜ਼ੇਸ਼ਨ](../security/ERROR_SANITIZATION.md) ਵੇਖੋ।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # ਜਦੋਂ ਕੈਟਾਲਾਗ ਬਦਲਦਾ ਹੈ; ਜਨਰੇਟ ਕੀਤਾ ਡਿਫ਼ ਕਮਿਟ ਕਰੋ
npm run lint
```

ਹਰ ਪ੍ਰਭਾਵਿਤ ਬੇਨਤੀ ਪਰਿਵਾਰ ਦਾ ਵੀ ਟੈਸਟ ਕਰੋ: ਚੈਟ, Responses, ਚਿੱਤਰ, ਐਂਬੈਡਿੰਗ, ਆਡੀਓ, ਜਾਂ ਵੀਡੀਓ।
ਜਨਰੇਟ ਕੀਤੇ ਕੈਟਾਲਾਗ ਅਤੇ ਗੋਲਡਨ ਡਿਫ਼ਾਂ ਦੀ ਇਕਰਾਰਨਾਮਾ ਤਬਦੀਲੀਆਂ ਵਜੋਂ ਸਮੀਖਿਆ ਕਰੋ; ਉਨ੍ਹਾਂ ਨੂੰ ਅੱਖਾਂ ਮੀਟ ਕੇ ਸਵੀਕਾਰ ਨਾ ਕਰੋ।

### ਰਾਊਟਿੰਗ

**ਇਕਰਾਰਨਾਮੇ**

- `src/shared/constants/routingStrategies.ts` ਵਿੱਚ ਜਨਤਕ ਰਣਨੀਤੀ ਮੁੱਲ ਅਤੇ UI ਮੈਟਾਡੇਟਾ।
- `open-sse/services/combo.ts` ਅਤੇ `open-sse/services/combo/` ਅਧੀਨ ਡਿਸਪੈਚ ਅਤੇ ਕ੍ਰਮਬੱਧਤਾ।
- Combo ਸਕੀਮਾ, ਸਥਾਇਤਾ, ਲਚੀਲਾਪਣ ਸਥਿਤੀ, ਮਾਡਲ ਸਮਰੱਥਾਵਾਂ, ਅਤੇ API/UI ਕੰਟਰੋਲ।
- ਵਿਹਾਰ ਬਦਲਣ 'ਤੇ [Auto-Combo ਇੰਜਣ](../routing/AUTO-COMBO.md) ਅਤੇ ਲਚੀਲਾਪਣ ਦਸਤਾਵੇਜ਼।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ਰਣਨੀਤੀ ਜਾਂ ਡਿਸਪੈਚ ਤਬਦੀਲੀਆਂ
npm run check:known-symbols      # ਰਣਨੀਤੀ ਰਜਿਸਟ੍ਰੇਸ਼ਨ ਤਬਦੀਲੀਆਂ
npm run lint
```

ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਨਿਰਧਾਰਤ ਮੌਕਡ-ਅਪਸਟ੍ਰੀਮ ਟੈਸਟ ਵਰਤੋ। ਲਾਈਵ combo ਸਮੋਕ ਟੈਸਟਾਂ ਲਈ ਕ੍ਰੈਡੈਂਸ਼ਲ ਲੋੜੀਂਦੇ ਹਨ ਅਤੇ ਇਹ
ਮੈਨੁਅਲ ਹਨ, CI ਦੇ ਬਦਲ ਨਹੀਂ।

### UI / UX

**ਇਕਰਾਰਨਾਮੇ**

- `src/app/` ਅਤੇ `src/shared/components/` ਅਧੀਨ Next.js ਰੂਟ/ਪੇਜ ਅਤੇ ਸਾਂਝੇ ਕੰਪੋਨੈਂਟ ਦੀਆਂ ਹੱਦਾਂ।
- API ਜਵਾਬ ਆਕਾਰ, ਲੋਡਿੰਗ/ਖਾਲੀ/ਗਲਤੀ ਸਥਿਤੀਆਂ, ਕੀਬੋਰਡ ਅਤੇ ਸਕ੍ਰੀਨ-ਰੀਡਰ ਵਿਹਾਰ,
  ਰਿਸਪਾਂਸਿਵ ਲੇਆਉਟ, ਥੀਮਿੰਗ, ਅਤੇ ਲੋਕੇਲ ਵਿਸਤਾਰ।

## ਸਾਂਝੀ ਮਸ਼ੀਨ ਲਈ ਡਿਵੈਲਪਰ ਸਕ੍ਰਿਪਟਾਂ

ਦੋ `scripts/dev/` ਸਹਾਇਕ ਉਸ devbox ਉੱਤੇ ਸਥਾਨਕ ਲੂਪ ਨੂੰ ਕੋਡਬੱਧ ਕਰਦੇ ਹਨ ਜਿੱਥੇ ਹੋਰ ਸੈਸ਼ਨ ਸਰਗਰਮ ਹਨ:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD ਤੋਂ ਫ਼ਾਈਲਾਂ
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ਬਿਲਕੁਲ ਇਹੀ ਫ਼ਾਈਲਾਂ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # ਅਲੱਗ worktree, ਸਮਾਂਤਰ ਤੌਰ 'ਤੇ ਸੁਰੱਖਿਅਤ
```

- `typecheck-touched.sh` ਕੇਵਲ ਬਦਲੀਆਂ ਗਈਆਂ `.ts/.tsx` ਫ਼ਾਈਲਾਂ ਦੀ ਇੱਕ ਅਸਥਾਈ
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ਰਾਹੀਂ 6 GB heap ਹੇਠ typecheck ਕਰਦੀ ਹੈ, ਇਸ ਲਈ ਇਹ ਪ੍ਰੋਜੈਕਟ-ਵਿਆਪੀ `tsc -p tsconfig.json`
  ਦੀ ਥਾਂ ਲੈਂਦੀ ਹੈ, ਜੋ ਲੋਡ ਵਾਲੀ ਮਸ਼ੀਨ ਉੱਤੇ OOM ਹੋ ਜਾਂਦੀ ਹੈ। ਇਹ ਬਦਲੀਆਂ ਫ਼ਾਈਲਾਂ ਵਿਚਲੀਆਂ ਗਲਤੀਆਂ ਦੇ ਨਾਲ ਇੱਕ ਸੰਖੇਪ ਲਾਈਨ ਪ੍ਰਿੰਟ ਕਰਦੀ ਹੈ ਅਤੇ
  ਬਦਲੀਆਂ ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਗਲਤੀਆਂ ਲਈ `1`, ਜਦੋਂ ਸਿਰਫ਼ imported ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਗਲਤੀਆਂ ਹੋਣ ਜਾਂ tsc
  ਬਿਨਾਂ diagnostics ਦੇ ਬੰਦ ਹੋ ਜਾਵੇ ਤਾਂ `2` (ਉਸ ਵੱਲੋਂ `_artifacts/typecheck-touched/` ਹੇਠ ਦੱਸੀ log ਪੜ੍ਹੋ), ਅਤੇ
  ਸਭ ਕੁਝ ਠੀਕ ਹੋਣ 'ਤੇ `0` ਨਾਲ ਬੰਦ ਹੁੰਦੀ ਹੈ। ਅਸਥਾਈ tsconfig ਹਮੇਸ਼ਾ ਹਟਾ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ; ਇਸਨੂੰ ਕਦੇ commit ਨਾ ਕਰੋ।
- `new-worktree.sh` `<git-common-dir>/omniroute-new-worktree.lock` ਉੱਤੇ ਸਮਕਾਲੀ runs ਨੂੰ ਲੜੀਵਾਰ ਚਲਾਉਂਦੀ ਹੈ
  (ਮੂਲ ਰੂਪ ਵਿੱਚ 600 s ਤੱਕ ਉਡੀਕ ਕਰਦੀ ਹੈ ਅਤੇ ਦਿਖਾਈ ਦੇਣ ਵਾਲਾ ਸੁਨੇਹਾ ਦਿੰਦੀ ਹੈ; script header ਵਿੱਚ
  override ਦਾ ਦਸਤਾਵੇਜ਼ ਹੈ) ਅਤੇ ਜਦੋਂ worktree ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ `git worktree add` ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਤਾਂ
  ਆਪਣੇ ਵੱਲੋਂ ਬਣਾਈ branch ਨੂੰ ਵਾਪਸ ਹਟਾ ਦਿੰਦੀ ਹੈ, ਇਸ ਲਈ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਵਾਸਤੇ ਹੱਥੀਂ `git branch -D` ਚਲਾਉਣ ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ।
  hard-linked `node_modules` ਅਤੇ `.husky/_` ਦੀ copy ਵਿੱਚ ਕੋਈ ਬਦਲਾਅ ਨਹੀਂ ਹੁੰਦਾ।

## ਸਥਾਨਕ candidate ਲੂਪ

Source tests ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰ ਸਕਦੇ ਕਿ packaged artifact boot ਹੁੰਦਾ ਹੈ: packaging ਸੂਚੀਆਂ, pruned dependencies,
ਅਤੇ native binaries ਸਿਰਫ਼ tarball install ਅਤੇ start ਹੋਣ ਤੋਂ ਬਾਅਦ ਹੀ ਅਸਫਲ ਹੁੰਦੇ ਹਨ। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 ਦੇ build-once / validate / promote flow ਦਾ ਸਥਾਨਕ ਪੱਖ ਹੈ:
ਇਹ ਇੱਕ candidate ਬਣਾਉਂਦੀ ਹੈ, ਬਿਲਕੁਲ ਉਸੇ artifact ਨੂੰ validate ਕਰਦੀ ਹੈ, directory renames ਰਾਹੀਂ ਉਸਨੂੰ
promote ਕਰਦੀ ਹੈ, ਅਤੇ ਜਦੋਂ promoted slot ਆਪਣੀ health check ਵਿੱਚ ਅਸਫਲ ਹੁੰਦੀ ਹੈ ਤਾਂ ਉਸਨੂੰ roll back ਕਰਦੀ ਹੈ।

```bash
npm run dev:candidate -- run --dry-run --json  # ਯੋਜਨਾ ਪ੍ਰਿੰਟ ਕਰੋ, ਕੁਝ ਨਾ ਬਦਲੋ
npm run dev:candidate -- run                   # build + validate + promote, ਸਵੈਚਾਲਿਤ rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ਵਿੱਚ install
npm run dev:candidate -- validate --id <id>    # ਖਾਲੀ port ਉੱਤੇ boot, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current ਅਤੇ previous ਨੂੰ ਆਪਸ ਵਿੱਚ ਬਦਲੋ
npm run dev:candidate -- run --from-tarball <file.tgz>  # ਕਿਤੇ ਹੋਰ (CI) ਬਣੇ tarball ਨੂੰ ਮੁੜ ਵਰਤੋ
```

- **ਇੱਕ ਵਾਰ build ਕਰੋ।** `build` ਮੌਜੂਦਾ tree ਨੂੰ pack ਕਰਦੀ ਹੈ (ਇਸਨੂੰ `dist/server.js` ਦੀ ਲੋੜ ਹੈ, ਇਸ ਲਈ ਪਹਿਲਾਂ
  `npm run build:release` ਚਲਾਓ) ਜਾਂ `--from-tarball` ਨੂੰ copy ਕਰਦੀ ਹੈ, ਫਿਰ tarball ਨੂੰ ਇੱਕ
  ਅਲੱਗ npm prefix ਵਿੱਚ install ਕਰਦੀ ਹੈ, ਕਿਉਂਕਿ tarball ਵਿੱਚ `node_modules` ਨਹੀਂ ਹੁੰਦਾ। id ਛੋਟਾ `HEAD`
  sha ਹੁੰਦਾ ਹੈ (ਜਦੋਂ tree ਵਿੱਚ ਸਥਾਨਕ ਬਦਲਾਅ ਹੋਣ ਤਾਂ `-dirty`) ਜਾਂ tarball ਲਈ `tgz-<sha256>`। ਪਹਿਲਾਂ ਹੀ
  build ਹੋਈ clean id ਨੂੰ ਦੁਬਾਰਾ build ਕਰਨ ਦੀ ਬਜਾਏ ਮੁੜ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ; ਇਸਨੂੰ ਦੁਬਾਰਾ build ਕਰਨ ਲਈ `--force` ਦਿਓ।
- **Source ਨੂੰ ਨਹੀਂ, package ਨੂੰ validate ਕਰੋ।** `validate` install ਕੀਤੀ CLI ਨੂੰ
  (`serve --port <free port>`) ਇੱਕ ਨਵੇਂ `DATA_DIR=<candidate>/data`, ਨਕਲੀ secrets ਨਾਲ start ਕਰਦੀ ਹੈ, ਅਤੇ
  operator ਦੇ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ਅਤੇ `INITIAL_PASSWORD` ਨੂੰ environment ਵਿੱਚੋਂ ਹਟਾ ਦਿੰਦੀ ਹੈ,
  ਤਾਂ ਜੋ ਇਹ ਨਵੀਂ installation ਦੀ keyless loopback posture ਦੀ ਜਾਂਚ ਕਰੇ। ਇਹ
  `GET /api/health` ਵੱਲੋਂ 200 ਵਾਪਸ ਕਰਨ ਦੀ ਉਡੀਕ ਕਰਦੀ ਹੈ, `GET /v1/models` ਵੱਲੋਂ 200 ਵਾਪਸ ਕਰਨ ਦੀ ਲੋੜ ਰੱਖਦੀ ਹੈ, process group ਨੂੰ ਰੋਕਦੀ ਹੈ,
  ਅਤੇ tarball hash ਦੇ ਨਾਲ verdict ਨੂੰ `validation.json` ਵਿੱਚ ਦਰਜ ਕਰਦੀ ਹੈ।
- **ਉਸੇ artifact ਨੂੰ promote ਕਰੋ।** `promote` ਉਸ candidate ਨੂੰ ਅਸਵੀਕਾਰ ਕਰਦੀ ਹੈ ਜਿਸਦੇ
  ਮੌਜੂਦਾ tarball hash ਲਈ ਸਫਲ validation ਨਾ ਹੋਵੇ। ਮੂਲ active slot `_artifacts/candidate/current` ਹੈ; `--target <dir>`
  ਉਸੇ filesystem ਉੱਤੇ ਕੋਈ ਹੋਰ directory ਚੁਣਦਾ ਹੈ, ਅਤੇ ਉਸਦੀ previous slot `<dir>.previous` ਹੁੰਦੀ ਹੈ।
  ਹਰ rename atomic ਹੁੰਦਾ ਹੈ, ਅਤੇ ਵਿਚਕਾਰ ਅਸਫਲਤਾ ਆਉਣ 'ਤੇ ਪਹਿਲਾਂ ਹੀ ਹੋ ਚੁੱਕੇ renames ਨੂੰ ਵਾਪਸ ਉਲਟ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।
- **Roll back ਕਰੋ।** `run` promoted slot ਨੂੰ ਦੁਬਾਰਾ validate ਕਰਦੀ ਹੈ ਅਤੇ ਜਦੋਂ
  ਉਹ check ਅਸਫਲ ਹੋਵੇ ਤਾਂ `current` ਅਤੇ `previous` ਨੂੰ ਮੁੜ ਆਪਸ ਵਿੱਚ ਬਦਲ ਦਿੰਦੀ ਹੈ। ਪਹਿਲੀ validation ਵਿੱਚ ਅਸਫਲ candidate ਨੂੰ ਕਦੇ promote ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ।

ਹਰ ਚੀਜ਼ gitignored `_artifacts/candidate/` ਹੇਠ ਲਿਖੀ ਜਾਂਦੀ ਹੈ; ਮੌਜੂਦਾ OmniRoute
installation ਅਤੇ ਇਸਦੀ data directory ਨੂੰ ਕਦੇ ਨਹੀਂ ਛੂਹਿਆ ਜਾਂਦਾ। promoted CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ਹੈ; ਇਸਨੂੰ ਵਰਤਦੇ ਸਮੇਂ ਆਪਣੇ `DATA_DIR` ਨਾਲ start ਕਰੋ।
Exit codes: ਸਫਲਤਾ ਲਈ `0`, ਅਸਫਲ validation ਜਾਂ promotion ਲਈ `1`, usage error ਜਾਂ build ਨਾ ਮਿਲਣ ਲਈ `2`।

## ਸਥਾਨਕ ਲੂਪ ਬਨਾਮ CI

| ਹਰ ਪੈਚ ਲਈ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਚਲਾਓ                                                    | CI ਵਿਆਪਕ ਸੰਕੇਤ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ                                  |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| ਉੱਪਰ ਦਿੱਤੇ ਸਿੱਧੇ ਵਿਹਾਰ ਟੈਸਟ ਅਤੇ ਸ਼੍ਰੇਣੀ ਗੇਟ                                     | ਸ਼ਾਰਡ ਕੀਤਾ ਪੂਰਾ ਯੂਨਿਟ ਸੂਟ ਅਤੇ ਕ੍ਰਮਵਾਰ ਟੈਸਟ                     |
| `npm run lint`                                                                  | Vitest ਸੂਟ ਅਤੇ ਕਵਰੇਜ/ਗੁਣਵੱਤਾ ਰੈਚਿਟ                             |
| ਟਾਈਪ-ਚੈਕ ਜਾਂ ਬਿਲਡ ਸਿਰਫ਼ ਉਦੋਂ, ਜਦੋਂ ਪ੍ਰਭਾਵਿਤ ਕੰਟਰੈਕਟ ਲਈ ਇਸਦੀ ਲੋੜ ਹੋਵੇ            | ਪ੍ਰੋਡਕਸ਼ਨ ਬਿਲਡ, ਸੁਰੱਖਿਆ, ਦਸਤਾਵੇਜ਼, ਡਿਪੈਂਡੈਂਸੀ ਅਤੇ PR-ਨੀਤੀ ਗੇਟ  |
| ਮੈਨੁਅਲ ਇੰਟਰੈਕਸ਼ਨ/ਲਾਈਵ ਜਾਂਚਾਂ ਸਿਰਫ਼ ਉਦੋਂ, ਜਦੋਂ ਆਟੋਮੇਸ਼ਨ ਵਿਹਾਰ ਨੂੰ ਸਾਬਤ ਨਾ ਕਰ ਸਕੇ | ਵਰਕਫ਼ਲੋ ਦੁਆਰਾ ਸੰਰਚਿਤ ਕ੍ਰਾਸ-ਜੌਬ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਅਤੇ ਪਲੇਟਫਾਰਮ ਜਾਂਚਾਂ |

ਇੱਕ ਸਫਲ ਕੇਂਦ੍ਰਿਤ ਲੂਪ ਬਦਲੇ ਹੋਏ ਕੰਟਰੈਕਟ ਬਾਰੇ ਸਬੂਤ ਹੈ, ਇਹ ਇਸ ਗੱਲ ਦਾ ਪ੍ਰਮਾਣ ਨਹੀਂ ਕਿ ਗੈਰ-ਸੰਬੰਧਿਤ CI ਜਾਂਚਾਂ
ਪਾਸ ਹੋਣਗੀਆਂ। ਇਸਦੇ ਉਲਟ, ਹਰ ਸਥਾਨਕ ਸੋਧ ਨੂੰ ਪੂਰੇ ਰਿਪੋਜ਼ਟਰੀ ਮੈਟ੍ਰਿਕਸ ਦੀ ਉਡੀਕ ਨਾ ਕਰਵਾਓ।

## ਸਮਕਾਲੀਕਰਨ ਜਾਂਚ-ਸੂਚੀ

ਸਮੀਖਿਆ ਦੀ ਬੇਨਤੀ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ:

- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ PR ਦਾ ਬੇਸ ਅਜੇ ਵੀ ਸਭ ਤੋਂ ਉੱਚੀ ਸਰਗਰਮ `release/v*` ਬ੍ਰਾਂਚ ਹੈ।
- ਉਸ ਬੇਸ ਨੂੰ ਫੈਚ ਕਰੋ ਅਤੇ ਤੁਹਾਡੇ ਵੱਲੋਂ ਬ੍ਰਾਂਚ ਬਣਾਏ ਜਾਣ ਤੋਂ ਬਾਅਦ ਸ਼ਾਮਲ ਹੋਏ ਕਮਿਟਾਂ ਦੀ ਸਮੀਖਿਆ ਕਰੋ।
- ਅਣਜਾਣੇ ਜਾਂ ਜਨਰੇਟ ਹੋਏ ਬੇਲੋੜੇ ਬਦਲਾਵਾਂ ਲਈ `git diff <active-base>...HEAD` ਦੀ ਸਮੀਖਿਆ ਕਰੋ।
- ਸਰੋਤ ਨੂੰ ਅੱਪਡੇਟ ਕਰਕੇ ਅਤੇ ਆਉਟਪੁੱਟ ਨੂੰ ਮੁੜ ਜਨਰੇਟ ਕਰਕੇ ਕੈਟਾਲੌਗ ਅਤੇ ਜਨਰੇਟ ਕੀਤੇ ਦਸਤਾਵੇਜ਼ਾਂ ਦੇ ਟਕਰਾਅ ਹੱਲ ਕਰੋ।
- ਸਮਕਾਲੀਕਰਨ ਤੋਂ ਬਾਅਦ PR ਵਰਣਨ ਵਿੱਚ ਸੂਚੀਬੱਧ ਹਰ ਕੇਂਦ੍ਰਿਤ ਟੈਸਟ/ਗੇਟ ਨੂੰ ਮੁੜ ਚਲਾਓ।
- ਬਦਲੇ ਹੋਏ ਬੇਸ ਨਾਲ ਮੇਲ ਕਰਨ ਲਈ ਕਦੇ ਵੀ ਅਸਰਸ਼ਨਾਂ ਨੂੰ ਕਮਜ਼ੋਰ ਨਾ ਕਰੋ ਜਾਂ ਲੋੜੀਂਦੇ ਟੈਸਟ ਨਾ ਹਟਾਓ।

ਰਿਲੀਜ਼-ਫ੍ਰੀਜ਼ ਅਤੇ ਰੀਟਾਰਗੇਟਿੰਗ ਨਿਯਮਾਂ ਲਈ,
[ਬ੍ਰਾਂਚਿੰਗ ਅਤੇ ਰਿਲੀਜ਼ ਮਾਡਲ](BRANCHING_MODEL.md) ਦੀ ਵਰਤੋਂ ਕਰੋ। ਪੂਰੀ CI ਸੂਚੀ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਸੰਦਰਭ](../architecture/QUALITY_GATES.md) ਦੀ ਵਰਤੋਂ ਕਰੋ।
