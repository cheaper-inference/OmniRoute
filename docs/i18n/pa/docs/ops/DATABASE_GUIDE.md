## SQLite ਕਿਉਂ?

OmniRoute ਨੇ ਕਈ ਕਾਰਨਾਂ ਕਰਕੇ PostgreSQL/MySQL ਦੀ ਥਾਂ SQLite ਨੂੰ ਚੁਣਿਆ:

| ਕਾਰਕ               | SQLite                                | PostgreSQL                         |
| ------------------ | ------------------------------------- | ---------------------------------- |
| **ਡਿਪਲੌਇਮੈਂਟ**     | ਏਮਬੈੱਡਡ — ਵੱਖਰੇ ਸਰਵਰ ਦੀ ਲੋੜ ਨਹੀਂ      | ਸਰਵਰ ਸੈੱਟਅੱਪ ਦੀ ਲੋੜ                |
| **ਇਨਕ੍ਰਿਪਸ਼ਨ**     | ਐਪਲੀਕੇਸ਼ਨ-ਲੇਅਰ (AES-256-GCM)          | ਬਿਲਟ-ਇਨ TDE                        |
| **ਕਾਰਗੁਜ਼ਾਰੀ**     | ਛੋਟੇ/ਦਰਮਿਆਨੇ ਵਰਕਲੋਡਾਂ ਲਈ ਵਧੇਰੇ ਤੇਜ਼   | ਬਹੁਤ ਵੱਡੀਆਂ ਸਮਕਾਲੀ ਰਾਈਟਾਂ ਲਈ ਬਿਹਤਰ |
| **ਸਮਕਾਲੀਤਾ**       | WAL ਮੋਡ ਸਮਕਾਲੀ ਰੀਡਾਂ ਦੀ ਆਗਿਆ ਦਿੰਦਾ ਹੈ | ਪੂਰਾ MVCC                          |
| **ਬੈਕਅੱਪ**         | ਇੱਕੋ ਫ਼ਾਈਲ ਦੀ ਕਾਪੀ                    | `pg_dump` ਜਾਂ ਫ਼ਾਈਲਸਿਸਟਮ ਸਨੈਪਸ਼ਾਟ  |
| **ਵਰਤੋਂ ਦਾ ਮਾਮਲਾ** | ਪ੍ਰਤੀ-ਉਪਭੋਗਤਾ ਇੰਸਟਾਲ, ਏਮਬੈੱਡਡ         | ਮਲਟੀ-ਟੈਨੈਂਟ SaaS                   |

**ਇੱਕ-ਉਪਭੋਗਤਾ, ਇੱਕ-ਇੰਸਟੈਂਸ** ਡਿਪਲੌਇਮੈਂਟਾਂ (OmniRoute ਦੀ ਮੁੱਖ ਵਰਤੋਂ) ਲਈ SQLite ਵਧੇਰੇ ਸਰਲ ਅਤੇ ਤੇਜ਼ ਹੈ।

### WAL ਜਰਨਲਿੰਗ

`core.ts` ਡਾਟਾਬੇਸ ਨੂੰ **WAL (Write-Ahead Logging) ਮੋਡ** ਵਿੱਚ ਖੋਲ੍ਹਦਾ ਹੈ:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL ਰਾਈਟਾਂ ਦੌਰਾਨ **ਸਮਕਾਲੀ ਰੀਡਾਂ** ਦੀ ਆਗਿਆ ਦਿੰਦਾ ਹੈ — ਇਹ ਡੈਸ਼ਬੋਰਡ ਲਈ ਮਹੱਤਵਪੂਰਨ ਹੈ, ਜੋ ਬੇਨਤੀਆਂ ਰਿਕਾਰਡ ਕੀਤੇ ਜਾਣ ਦੌਰਾਨ ਕਵੇਰੀਆਂ ਚਲਾਉਂਦਾ ਹੈ।

ਡਿਫੌਲਟ ਕੈਸ਼ ਆਕਾਰ **65,536 KiB (64 MiB)** ਹੈ। SQLite ਰਿਣਾਤਮਕ
`cache_size` ਨੂੰ KiB ਵਿੱਚ ਇੱਕ ਅਨੁਮਾਨਿਤ ਉੱਪਰੀ ਸੀਮਾ ਵਜੋਂ ਸਮਝਦਾ ਹੈ ਅਤੇ ਲੋੜ ਅਨੁਸਾਰ ਪੇਜ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ।
**ਸੈਟਿੰਗਾਂ > ਸਿਸਟਮ ਅਤੇ ਸਟੋਰੇਜ > ਕੈਸ਼ ਆਕਾਰ** **1 ਤੋਂ
1,000,000 KiB** ਤੱਕ ਦੇ ਪੂਰਨ ਅੰਕ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ; ਸੈਟਿੰਗ ਨੂੰ ਸੇਵ ਕਰਨ ਨਾਲ ਇਹ ਚਾਲੂ ਡਾਟਾਬੇਸ ਕਨੈਕਸ਼ਨ ਉੱਤੇ ਲਾਗੂ ਹੋ ਜਾਂਦੀ ਹੈ,
ਅਤੇ OmniRoute ਸਟਾਰਟਅੱਪ ਵੇਲੇ ਸੰਭਾਲੇ ਹੋਏ ਮੁੱਲ ਨੂੰ ਮੁੜ ਬਹਾਲ ਕਰਦਾ ਹੈ।

## ਡਾਟਾਬੇਸ ਦਾ ਟਿਕਾਣਾ

SQLite ਫ਼ਾਈਲ ਇੱਥੇ ਸਟੋਰ ਕੀਤੀ ਜਾਂਦੀ ਹੈ:

| OS      | ਪਾਥ                                                           |
| ------- | ------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                 |
| macOS   | `~/.omniroute/storage.sqlite`                                 |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                     |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` ਰਾਹੀਂ ਕਨਫ਼ਿਗਰ ਕਰਨ ਯੋਗ) |

ਸਹਾਇਕ ਫ਼ਾਈਲਾਂ:

- `storage.sqlite-wal` — ਰਾਈਟ-ਅਹੈੱਡ ਲੌਗ
- `storage.sqlite-shm` — ਸਾਂਝੀ ਮੈਮੋਰੀ ਫ਼ਾਈਲ
- `call_logs/` — ਬੇਨਤੀ ਪੇਲੋਡ ਆਰਟੀਫੈਕਟ (ਜੇ ਸਮਰੱਥ ਕੀਤਾ ਹੋਵੇ)

**ਟਿਕਾਣਾ ਓਵਰਰਾਈਡ ਕਰੋ:**

```bash
DATA_DIR=/custom/path omniroute
```

## ਡੋਮੇਨ ਮੋਡੀਊਲ ਆਰਕੀਟੈਕਚਰ

OmniRoute ਦੇ ਡੇਟਾਬੇਸ ਵਿੱਚ `src/lib/db/` ਅੰਦਰ **110 ਸਿਖਰ-ਪੱਧਰੀ TypeScript ਮੋਡੀਊਲ** ਹਨ। ਹਰ ਡੋਮੇਨ ਮੋਡੀਊਲ:

- ਇੱਕ ਜਾਂ ਵੱਧ ਖ਼ਾਸ ਟੇਬਲਾਂ ਦਾ ਮਾਲਕ ਹੁੰਦਾ ਹੈ
- ਟਾਈਪ ਕੀਤੇ CRUD ਫੰਕਸ਼ਨ ਐਕਸਪੋਰਟ ਕਰਦਾ ਹੈ
- ਕਦੇ ਵੀ ਕਿਸੇ ਹੋਰ ਮੋਡੀਊਲ ਦੀਆਂ ਟੇਬਲਾਂ ਨੂੰ ਨਹੀਂ ਛੂੰਹਦਾ
- DB ਤੱਕ ਪਹੁੰਚ ਕਰਨ ਲਈ `core.ts` ਤੋਂ `getDbInstance()` ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ

ਇੱਕ ਮੁੱਖ ਆਰਕੀਟੈਕਚਰ ਨਿਯਮ: **ਮੋਡੀਊਲ ਇੱਕ-ਦੂਜੇ ਦੀਆਂ ਟੇਬਲਾਂ ਤੱਕ ਸਿੱਧੀ ਪਹੁੰਚ ਨਹੀਂ ਕਰਦੇ**। ਕਿਸੇ ਹੋਰ ਮੋਡੀਊਲ ਦੇ ਡੇਟਾ ਨਾਲ ਕੰਮ ਕਰਨ ਲਈ, ਉਸ ਮੋਡੀਊਲ ਤੋਂ ਫੰਕਸ਼ਨ ਇੰਪੋਰਟ ਕਰੋ।

```ts

db.prepare("SELECT * FROM provider_connections").all();

// ✅ ਸਹੀ: providers ਮੋਡੀਊਲ ਦੇ ਫੰਕਸ਼ਨ ਦੀ ਵਰਤੋਂ ਕਰੋ
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

ਇਹ ਨਿਯਮ ਕੋਡ ਸਮੀਖਿਆ ਰਾਹੀਂ ਲਾਗੂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ—ਕੋਈ ਸਥਿਰ ਜਾਂਚ ਨਹੀਂ ਹੈ, ਪਰ ਉਲੰਘਣਾਵਾਂ ਨੂੰ ਚਿੰਨ੍ਹਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

## ਪਰਵਾਸ

OmniRoute ਵਰਤਦਾ ਹੈ** ਸੰਸਕਰਣ, ਅਯੋਗ ਮਾਈਗ੍ਰੇਸ਼ਨ** `src/lib/db/migrations/` ਵਿੱਚ ਹਰੇਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਇੱਕ ਸਿੰਗਲ SQL ਫਾਈਲ ਹੈ। ਦੋ ਨਾਮਕਰਨ ਫਾਰਮੈਟ ਇਕੱਠੇ ਮੌਜੂਦ ਹਨ; `_omniroute_migrations` ਵਿੱਚ ਦਰਜ ਕੀਤਾ ਗਿਆ ਸੰਸਕਰਣ ਸੰਖਿਆਤਮਕ ਅਗੇਤਰ ਹੈ।

### ਮਾਈਗ੍ਰੇਸ਼ਨ ਨਾਮਕਰਨ

| ਫਾਰਮੈਟ                                         | ਉਦਾਹਰਨ                               | ਲਈ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ                                                                                                                                                       |
| ---------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (ਬਿਲਕੁਲ 3 ਅੰਕ)           | `241_seen_models.sql`                | ਪੁਰਾਣੀ ਲੜੀ `001`-`241`. ਫ੍ਰੀਜ਼ ਕੀਤਾ ਗਿਆ ਜਦੋਂ ਟਾਈਮਸਟੈਂਪ ਫਾਰਮੈਟ ਲੈਂਡ ਹੋਇਆ (`240` ਅਤੇ `241` ਇਸ ਤੋਂ ਠੀਕ ਪਹਿਲਾਂ ਮਿਲਾਏ ਗਏ ਸਨ): ਕਿਸੇ ਵੀ ਨਵੀਂ ਫਾਈਲ ਨੂੰ ਕ੍ਰਮਵਾਰ ਨੰਬਰ ਨਹੀਂ ਮਿਲਦਾ। |
| `YYYYMMDDHHMMSS_description.sql` (14 ਅੰਕ, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 ਤੋਂ ਹਰ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਬਣਾਇਆ ਗਿਆ।                                                                                                                             |

ਤਬਦੀਲੀ ਕਿਉਂ: ਕ੍ਰਮਵਾਰ ਸੰਖਿਆਵਾਂ ਦੇ ਨਾਲ, ਸਮਾਨਾਂਤਰ PRs ਉਹੀ ਅਗਲੀ ਸੰਖਿਆ ਨੂੰ ਚੁਣਿਆ ਅਤੇ ਇੱਕ ਨੂੰ ਛੱਡ ਕੇ ਬਾਕੀ ਸਾਰੇ ਨੂੰ ਮਿਲਾਨ ਤੋਂ ਪਹਿਲਾਂ ਦੁਬਾਰਾ ਨੰਬਰ ਕਰਨਾ ਪਿਆ। ਇੱਕ UTC ਟਾਈਮਸਟੈਂਪ ਹਰੇਕ PR ਨੂੰ ਇਸਦਾ ਆਪਣਾ ਸੰਸਕਰਣ ਦਿੰਦਾ ਹੈ।

ਟਾਈਮਸਟੈਂਪ ਫਾਰਮੈਟ ਲਈ ਨਿਯਮ ( `npm run check:migration-numbering` ਦੁਆਰਾ ਲਾਗੂ ਕੀਤਾ ਗਿਆ, `scripts/check/lib/migrationNaming.mjs` ਵਿੱਚ ਜਨਰੇਟਰ ਨਾਲ ਸਾਂਝਾ ਕੀਤਾ ਗਿਆ):

- ਟਾਈਮਸਟੈਂਪ ਇੱਕ ਅਸਲੀ UTC ਮਿਤੀ ਅਤੇ ਸਮਾਂ ਹੈ, ਜੋ ਕਿ `20261113000000` ਤੋਂ ਪਹਿਲਾਂ ਨਹੀਂ ਹੈ ਅਤੇ ਭਵਿੱਖ ਵਿੱਚ 10 ਮਿੰਟਾਂ ਤੋਂ ਵੱਧ ਨਹੀਂ ਹੈ।
- ਵਰਣਨ ਇੱਕ ਅੱਖਰ (`a-z`, `0-9`, ਸ਼ਬਦਾਂ ਦੇ ਵਿਚਕਾਰ ਸਿੰਗਲ `_` ) ਨਾਲ ਸ਼ੁਰੂ ਹੋਣ ਵਾਲੇ ਛੋਟੇ ਅੱਖਰਾਂ ਦਾ `snake_case` ਹੈ, ਵੱਧ ਤੋਂ ਵੱਧ 80 ਅੱਖਰ।
- ਇੱਕੋ ਟਾਈਮਸਟੈਂਪ ਵਾਲੀਆਂ ਦੋ ਫਾਈਲਾਂ ਇੱਕ ਡੁਪਲੀਕੇਟ ਹਨ।
- ਨੋ-ਗੈਪ ਨਿਯਮ ਸਿਰਫ਼ ਪੁਰਾਣੀ ਲੜੀ 'ਤੇ ਲਾਗੂ ਹੁੰਦਾ ਹੈ: `001` ਤੋਂ `241` ਤੱਕ ਹਰੇਕ ਨੰਬਰ ਮੌਜੂਦ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ, `026`, `055` ਅਤੇ `121` ਨੂੰ ਛੱਡ ਕੇ। `241` (ਜਾਂ ਕੋਈ ਪੁਰਾਣੀ ਫਾਈਲ) ਨੂੰ ਮਿਟਾਉਣਾ ਗੇਟ ਨੂੰ ਅਸਫਲ ਕਰਦਾ ਹੈ। `001` ਅਤੇ `241` ਕਦੇ ਵੀ `KNOWN_GAPS` ਅਨੁਮਤੀ ਸੂਚੀ ਵਿੱਚ ਸ਼ਾਮਲ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ। ਟਾਈਮਸਟੈਂਪਡ ਫਾਈਲਾਂ ਕਦੇ ਵੀ ਅੰਤਰ ਨਹੀਂ ਬਣਾਉਂਦੀਆਂ.
- `src/lib/db/migrations/` ਵਿੱਚ ਹਰੇਕ ਐਂਟਰੀ ਇੱਕ ਵੈਧ ਲੋਅਰਕੇਸ `.sql` ਨਾਮ ਵਾਲੀ ਇੱਕ ਨਿਯਮਤ ਫਾਈਲ ਹੋਣੀ ਚਾਹੀਦੀ ਹੈ। ਇੱਕ ਡਾਇਰੈਕਟਰੀ, ਇੱਕ ਸਿਮਲਿੰਕ, ਇੱਕ `.SQL` ਜਾਂ `.sql.bak` ਫਾਈਲ, ਇੱਕ ਲੁਕਵੀਂ ਫਾਈਲ ਜਾਂ ਇੱਕ ਸਪੇਸ ਵਾਲਾ ਨਾਮ ਗੇਟ ਨੂੰ ਫੇਲ ਕਰਦਾ ਹੈ, ਕਿਉਂਕਿ ਦੌੜਾਕ ਇਸਨੂੰ ਚੁੱਪਚਾਪ ਛੱਡ ਦੇਵੇਗਾ ਜਾਂ ਬੂਟ ਹੋਣ ਤੇ ਕਰੈਸ਼ ਹੋ ਜਾਵੇਗਾ।

**ਆਰਡਰ ਲਾਗੂ ਕਰੋ।** ਦੌੜਾਕ ਅਗੇਤਰ ਦੇ ਸੰਖਿਆਤਮਕ ਮੁੱਲ ਦੁਆਰਾ ਛਾਂਟਦਾ ਹੈ, ਟੈਕਸਟ ਦੁਆਰਾ ਨਹੀਂ: ਪੁਰਾਣੀ `001`–`241` ਫਾਈਲਾਂ ਪਹਿਲਾਂ, ਫਿਰ ਟਾਈਮਸਟੈਂਪ ਕ੍ਰਮ ਵਿੱਚ ਟਾਈਮਸਟੈਂਪ ਕੀਤੀਆਂ ਫਾਈਲਾਂ, ਫਿਰ `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ਨਾਲ ਰਜਿਸਟਰਡ ਕੋਈ ਵੀ ਨੇਮਸਪੇਸਡ ਡਾਇਰੈਕਟਰੀਆਂ (ਵਰਜਨ ਜਿਵੇਂ ਕਿ `ee-001`)। ਇੱਕ ਲੰਬਿਤ ਮਾਈਗ੍ਰੇਸ਼ਨ ਕੋਈ ਵੀ ਫਾਈਲ ਹੁੰਦੀ ਹੈ ਜਿਸਦਾ ਸੰਸਕਰਣ `_omniroute_migrations` ਵਿੱਚ ਨਹੀਂ ਹੈ, ਇਸਲਈ ਇੱਕ ਪੁਰਾਣੀ ਬ੍ਰਾਂਚ ਤੋਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਜੋ ਇੱਕ ਨਵੀਂ ਬ੍ਰਾਂਚ ਤੋਂ ਬਾਅਦ ਅਭੇਦ ਹੋ ਜਾਂਦੀ ਹੈ ਅਜੇ ਵੀ ਮੌਜੂਦਾ ਡੇਟਾਬੇਸ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ।

**ਟਾਈਮਸਟੈਂਪ ਰਚਨਾ ਕ੍ਰਮ ਹੈ, ਵਿਲੀਨ ਕ੍ਰਮ ਨਹੀਂ।** ਜੇਕਰ ਤੁਹਾਡਾ ਮਾਈਗ੍ਰੇਸ਼ਨ ਇੱਕ ਟੇਬਲ ਜਾਂ ਕਾਲਮ 'ਤੇ ਨਿਰਭਰ ਕਰਦਾ ਹੈ ਜੋ ਇੱਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨਾਲ a** ਨਵਾਂ** ਟਾਈਮਸਟੈਂਪ (ਉਦਾਹਰਨ ਲਈ, ਇੱਕ ਹੋਰ PR ਤੋਂ ਇੱਕ ਜੋ ਪਹਿਲਾਂ ਅਭੇਦ ਹੋਇਆ), ਇੱਕ ਤਾਜ਼ਾ ਡੇਟਾਬੇਸ ਪਹਿਲਾਂ ਤੁਹਾਡਾ ਚੱਲੇਗਾ ਅਤੇ ਅਸਫਲ ਹੋਵੇਗਾ। ਜਦੋਂ ਕਿ ਤੁਹਾਡਾ PR ਅਜੇ ਵੀ ਖੁੱਲ੍ਹਾ ਹੈ, `npm run db:new-migration` ਨਾਲ ਫਾਈਲ ਨਾਮ ਨੂੰ ਦੁਬਾਰਾ ਬਣਾਓ ਤਾਂ ਕਿ ਇਹ ਇੱਕ ਨਵਾਂ ਟਾਈਮਸਟੈਂਪ ਪ੍ਰਾਪਤ ਕਰੇ, ਜਾਂ ਇਸਨੂੰ ਸੁਤੰਤਰ ਬਣਾਉ। `npm run test:migrations:fresh` ਹਰ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਖਾਲੀ ਡੇਟਾਬੇਸ ਤੇ ਲਾਗੂ ਕਰਦਾ ਹੈ ਅਤੇ ਇਸਨੂੰ ਫੜਦਾ ਹੈ।

### ਇੱਕ ਵਿਲੀਨ ਮਾਈਗਰੇਸ਼ਨ ਨੂੰ ਕਦੇ ਵੀ ਮਿਟਾਇਆ ਜਾਂ ਬਦਲਿਆ ਨਹੀਂ ਜਾਂਦਾ ਹੈ

ਇੱਕ ਵਾਰ ਇੱਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਫਾਈਲ ਇੱਕ ਰੀਲੀਜ਼ ਸ਼ਾਖਾ ਜਾਂ `main` ਤੇ ਹੈ, ਇਹ ਪਹਿਲਾਂ ਹੀ homolog ਅਤੇ ਡਿਵੈਲਪਰ ਡੇਟਾਬੇਸ, VPS ਸਥਾਪਨਾਵਾਂ ਅਤੇ ਐਂਟਰਪ੍ਰਾਈਜ਼ ਸਿੰਕ ਵਿੱਚ ਚੱਲ ਚੁੱਕੀ ਹੈ। ਉਦੋਂ ਤੋਂ:

- **ਇਸਨੂੰ ਕਦੇ ਨਾ ਮਿਟਾਓ।** ਅੱਪਗ੍ਰੇਡ ਕੀਤੇ ਡੇਟਾਬੇਸ ਇਸ ਨੂੰ ਰੱਖਣ ਦੇ ਦੌਰਾਨ ਤਾਜ਼ਾ ਸਥਾਪਨਾਵਾਂ ਇਸਦੀ ਸਕੀਮਾ ਨੂੰ ਗੁਆ ਦਿੰਦੀਆਂ ਹਨ।
- **ਇਸਦਾ ਨਾਮ ਕਦੇ ਨਾ ਬਦਲੋ।** `_omniroute_migrations` ਵਿੱਚ ਸੰਸਕਰਣ ਹੁਣ ਇੱਕ ਫਾਈਲ ਨਾਲ ਮੇਲ ਨਹੀਂ ਖਾਂਦਾ, ਇਸਲਈ ਹਰੇਕ ਡੇਟਾਬੇਸ ਜੋ ਪਹਿਲਾਂ ਹੀ ਇਸਨੂੰ ਲਾਗੂ ਕਰ ਚੁੱਕਾ ਹੈ ਇਸਨੂੰ ਦੁਬਾਰਾ ਚਲਾਏਗਾ। ਗੈਰ-ਇਡੀਮਪੋਟੈਂਟ SQL ਫਿਰ ਡੇਟਾ ਨੂੰ ਡੁਪਲੀਕੇਟ ਕਰਦਾ ਹੈ ਜਾਂ ਬੂਟ ਨੂੰ ਰੋਕਦਾ ਹੈ।
- **ਇੱਕ ਵੱਖਰੀ ਸਕੀਮਾ ਦੀ ਲੋੜ ਹੈ?** `npm run db:new-migration` ਨਾਲ ਇੱਕ ਨਵਾਂ ਮਾਈਗਰੇਸ਼ਨ ਬਣਾਓ।

ਨਾਮ ਬਦਲਣਾ ਸਿਰਫ਼ ਉਸ ਫਾਈਲ ਲਈ ਸੁਰੱਖਿਅਤ ਹੈ ਜੋ ਅਜੇ ਤੱਕ ਵਿਲੀਨ ਨਹੀਂ ਕੀਤੀ ਗਈ ਹੈ, ਜੋ ਕਿ ਗੇਟ ਦੇ ਸੰਕੇਤਾਂ ਦਾ ਹਵਾਲਾ ਦਿੰਦਾ ਹੈ। ਇੱਕ ਰੀਲੀਜ਼ ਟੈਗ ਇੱਥੇ ਕੁਝ ਨਹੀਂ ਬਦਲਦਾ: ਇੱਕ `release/v*` ਬ੍ਰਾਂਚ ਵਿੱਚ ਹਰ ਪੁਸ਼ Docker `:next` ਚਿੱਤਰ ਨੂੰ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ ਅਤੇ homolog, VPS ਸਥਾਪਨਾਵਾਂ ਅਤੇ ਐਂਟਰਪ੍ਰਾਈਜ਼ ਸਿੰਕ 'ਤੇ ਚੱਲਦਾ ਹੈ, ਇਸਲਈ ਕਿਸੇ ਵੀ `vX.Y.Z` ਟੈਗ ਦੇ ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਇੱਕ ਵਿਲੀਨ ਮਾਈਗਰੇਸ਼ਨ ਅਸਲ ਡੇਟਾਬੇਸ 'ਤੇ ਚੱਲਦਾ ਹੈ। ਗੇਟ ਬੇਸ ਫਾਈਲ ਦੇ ਹਰ ਹਟਾਉਣ ਵਿੱਚ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਟੈਗ ਕੀਤਾ ਜਾਂ ਨਹੀਂ।

- **ਵਿਲੀਨ ਕੀਤੇ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਵਾਪਸ ਕੀਤਾ ਜਾ ਰਿਹਾ ਹੈ।** ਇੱਕ `git revert` ਜੋ ਫਾਈਲ ਨੂੰ ਮਿਟਾਉਂਦਾ ਹੈ ਗੇਟ ਨੂੰ ਫੇਲ ਕਰਦਾ ਹੈ। ਫਾਈਲ ਨੂੰ ਰੱਖੋ ਅਤੇ ਇਸਦੀ ਸਕੀਮਾ ਨੂੰ ਇੱਕ ਨਵੇਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਵਿੱਚ ਅਨਡੂ ਕਰੋ: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` ਅਤੇ ਇਸ ਤਰ੍ਹਾਂ ਦੇ ਨਾਲ। ਅੱਪਗਰੇਡ ਅਤੇ ਤਾਜ਼ਾ ਡਾਟਾਬੇਸ ਫਿਰ ਉਸੇ ਸਕੀਮਾ ਨਾਲ ਖਤਮ ਹੁੰਦਾ ਹੈ.
- **ਇੱਕ ਸਵੀਕਾਰ ਕੀਤਾ ਗਿਆ ਨਾਮ: ਇੱਕ ਅਨੁਕੂਲਤਾ ਇੰਦਰਾਜ਼ ਅਤੇ ਸਮਾਨ ਸਮੱਗਰੀ।** ਜੇਕਰ ਇੱਕ ਵਿਲੀਨ ਕੀਤੀ ਫਾਈਲ ਨੂੰ ਮੂਵ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, ਦੋ ਵਿਲੀਨ ਕੀਤੀਆਂ ਫਾਈਲਾਂ ਇੱਕ ਟਾਈਮਸਟੈਂਪ ਨੂੰ ਸਾਂਝਾ ਕਰਦੀਆਂ ਹਨ ਅਤੇ ਰਨਰ ਇੱਕ ਸੰਸਕਰਣ ਟਕਰਾਅ ਨਾਲ ਰੁਕ ਜਾਂਦਾ ਹੈ), ਤਾਂ ਇਸਦੇ SQL ਛੂਹਣ ਤੋਂ ਬਿਨਾਂ ਬਾਅਦ ਵਾਲੇ ਦਾ ਨਾਮ ਬਦਲੋ ਅਤੇ `src/lib/db/migrationRunner/constants.ts` ਵਿੱਚ `{ fromVersion, fromName, toVersion, toName }` ਨੂੰ `RENAMED_MIGRATION_COMPATIBILITY` ਵਿੱਚ ਜੋੜੋ। ਪੁਰਾਣੇ ਸੰਸਕਰਣ ਨੂੰ ਲਾਗੂ ਕਰਨ ਵਾਲੇ ਡੇਟਾਬੇਸ ਫਾਈਲ ਨੂੰ ਦੁਬਾਰਾ ਚਲਾਉਣ ਦੀ ਬਜਾਏ ਆਪਣੀ `_omniroute_migrations` ਕਤਾਰ ਨੂੰ ਹਿਲਾ ਦਿੰਦੇ ਹਨ। ਗੇਟ ਅਜਿਹੇ ਨਾਮ ਬਦਲਣ ਬਾਰੇ ਚੇਤਾਵਨੀ ਦਿੰਦਾ ਹੈ ਅਤੇ ਹਮੇਸ਼ਾ ਇਸ 'ਤੇ ਕਮਿਊਟੇਸ਼ਨ ਜਾਂਚ ਚਲਾਉਂਦਾ ਹੈ, ਜੋ ਵੀ ਨਵਾਂ ਟਾਈਮਸਟੈਂਪ: ਤਾਜ਼ਾ ਸਥਾਪਨਾਵਾਂ ਫਾਈਲ ਨੂੰ ਇਸਦੀ ਨਵੀਂ ਸਥਿਤੀ 'ਤੇ ਲਾਗੂ ਕਰਦੀਆਂ ਹਨ, ਅੱਪਗਰੇਡ ਕੀਤੇ ਡੇਟਾਬੇਸ ਨਹੀਂ ਕਰਦੇ, ਇਸ ਲਈ ਪੁਰਾਣੇ ਦੇ ਨੇੜੇ ਇੱਕ ਨਵਾਂ ਟਾਈਮਸਟੈਂਪ ਚੁਣੋ। ਗੇਟ ਨਾਮ ਬਦਲਣ ਵਿੱਚ ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਜੇਕਰ ਸਮੱਗਰੀ ਬਦਲੀ ਗਈ ਹੈ (ਇੱਕ ਸਕੀਮਾ ਤਬਦੀਲੀ ਅਜੇ ਵੀ ਇੱਕ ਨਵੇਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਵਿੱਚ ਜਾਂਦੀ ਹੈ), ਜਾਂ ਜੇਕਰ ਐਂਟਰੀ ਦੀ ਟੀਚਾ ਫਾਈਲ ਡਿਸਕ 'ਤੇ ਨਹੀਂ ਹੈ।
- **ਉਸੇ ਟਾਈਮਸਟੈਂਪ ਦੇ ਅੰਦਰ ਕਦੇ ਵੀ ਨਾਮ ਨਾ ਬਦਲੋ।** ਇੱਕ ਨਾਮ ਬਦਲਣਾ ਜੋ ਟਾਈਮਸਟੈਂਪ ਰੱਖਦਾ ਹੈ ਅਤੇ ਸਿਰਫ਼ ਵਰਣਨ ਨੂੰ ਬਦਲਦਾ ਹੈ, ਗੇਟ ਨੂੰ ਅਸਫਲ ਕਰਦਾ ਹੈ, ਐਂਟਰੀ ਦੇ ਨਾਲ ਜਾਂ ਬਿਨਾਂ। ਇੱਕ ਐਂਟਰੀ ਦੇ ਨਾਲ ਜਿਸਦਾ `toVersion` ਇਸਦੇ `fromVersion` ਦੇ ਬਰਾਬਰ ਹੈ, ਦੌੜਾਕ ਪੁਰਾਣੀ `_omniroute_migrations` ਕਤਾਰ ਨੂੰ ਮਿਟਾ ਦਿੰਦਾ ਹੈ ਅਤੇ ਫਾਈਲ ਨੂੰ ਹਰੇਕ ਡੇਟਾਬੇਸ ਉੱਤੇ ਦੁਬਾਰਾ ਲਾਗੂ ਕਰਦਾ ਹੈ ਜੋ ਪਹਿਲਾਂ ਹੀ ਇਸਨੂੰ ਚਲਾ ਚੁੱਕਾ ਹੈ। ਐਂਟਰੀ ਤੋਂ ਬਿਨਾਂ, ਦੌੜਾਕ ਸਿਰਫ਼ ਸੰਸਕਰਣ ਨੂੰ ਟ੍ਰੈਕ ਕਰਦਾ ਹੈ: ਇਹ ਉਹਨਾਂ ਡੇਟਾਬੇਸ 'ਤੇ ਫਾਈਲ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ (ਨਵੀਂ ਸਮੱਗਰੀ ਉੱਥੇ ਕਦੇ ਨਹੀਂ ਚੱਲਦੀ) ਅਤੇ ਹਰ ਬੂਟ 'ਤੇ ਇੱਕ ਮੁੜ-ਨੰਬਰ ਗਲਤੀ ਨੂੰ ਲੌਗ ਕਰਦਾ ਹੈ। ਕਿਸੇ ਹੋਰ ਟਾਈਮਸਟੈਂਪ ਅਤੇ ਅਨੁਕੂਲਤਾ ਇੰਦਰਾਜ਼ ਦੀ ਵਰਤੋਂ ਕਰੋ, ਜਾਂ ਨਾਮ ਰੱਖੋ।
- **ਗੇਟ ਜਾਂਚ ਕਰਦਾ ਹੈ ਕਿ ਨਾਮ ਬਦਲੀ ਗਈ ਫਾਈਲ ਦੁਬਾਰਾ ਨਹੀਂ ਚੱਲਦੀ.** ਹਰੇਕ ਕਵਰ ਕੀਤੇ ਨਾਮ ਬਦਲੇ ਲਈ, ਗੇਟ ਨਵੇਂ ਫਾਈਲ ਨਾਮ ਨੂੰ `--must-not-apply` ਨਾਲ ਕਮਿਊਟੇਸ਼ਨ ਜਾਂਚ ਲਈ ਪਾਸ ਕਰਦਾ ਹੈ। ਚੈੱਕ ਅਸਲ ਦੌੜਾਕ ਨਾਲ ਅੱਪਗਰੇਡ ਕੀਤੇ ਡੇਟਾਬੇਸ ਨੂੰ ਬੂਟ ਕਰਦਾ ਹੈ, ਅਤੇ ਜੇਕਰ ਦੌੜਾਕ ਉਸ ਫਾਈਲ ਨੂੰ ਦੁਬਾਰਾ ਲਾਗੂ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਣ ਵਜੋਂ, ਕਿਉਂਕਿ ਐਂਟਰੀ ਦਾ ਇੱਕ ਗਲਤ ਸੰਸਕਰਣ ਜਾਂ ਨਾਮ ਹੈ, ਜਾਂ ਕਿਉਂਕਿ ਗੇਟ ਦਾ ਟੈਕਸਟ ਪਾਰਸਰ `constants.ts` TypeScript ਤੋਂ ਵੱਖਰਾ ਪੜ੍ਹਦਾ ਹੈ), ਗੇਟ `migration renomeada rodaria de novo` ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ ਅਤੇ ਤੁਹਾਨੂੰ ਐਂਟਰੀ ਦੇ ਪੁਰਾਣੇ ਅਤੇ ਨਵੇਂ ਸੰਸਕਰਣਾਂ ਅਤੇ ਨਾਮਾਂ ਦੀ ਜਾਂਚ ਕਰਨ ਲਈ ਕਹਿੰਦਾ ਹੈ।

### ਗੇਟ ਬੇਸ ਦੇ ਵਿਰੁੱਧ ਕੀ ਜਾਂਚ ਕਰਦਾ ਹੈ

ਪੁੱਲ ਬੇਨਤੀ ਅਤੇ ਮਰਜ-ਕਿਊ ਰਨ 'ਤੇ, `npm run check:migration-numbering` ਬੇਸ ਬ੍ਰਾਂਚ 'ਤੇ ਉਸੇ ਡਾਇਰੈਕਟਰੀ ਨਾਲ ਡਿਸਕ 'ਤੇ `src/lib/db/migrations/` ਤੁਲਨਾ ਕਰਦਾ ਹੈ। ਅਧਾਰ ਹੈ, ਇਸ ਕ੍ਰਮ ਵਿੱਚ: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` ਵੇਰੀਏਬਲ, ਜਾਂ, ਜਦੋਂ `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` ਜਾਂ `merge_group` ਹੁੰਦਾ ਹੈ, ਮਰਜ ਕਮਿਟ ਦਾ ਪਹਿਲਾ ਪੈਰੇਂਟ, ਇਵੈਂਟ ਪੇਲੋਡ ਦਾ `merge_group.base_sha`, ਜਾਂ `git merge-base HEAD origin/$GITHUB_BASE_REF`। ਇੱਕ ਪੁੱਲ ਬੇਨਤੀ ਜਾਂ ਅਭੇਦ-ਕਤਾਰ ਵਿੱਚ ਬਿਨਾਂ ਹੱਲ ਹੋਣ ਯੋਗ ਅਧਾਰ ਦੇ ਨਾਲ ਗੇਟ ਫੇਲ ਹੋ ਜਾਂਦਾ ਹੈ। `--base` ਤੋਂ ਬਿਨਾਂ CI ਤੋਂ ਬਾਹਰ ਇਹ `comparação com a base: pulada (sem --base)` ਛਾਪਦਾ ਹੈ ਅਤੇ ਇਹਨਾਂ ਨਿਯਮਾਂ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ।

`--base-latest-tag` ਸਭ ਤੋਂ ਨਵੇਂ ਰੀਲੀਜ਼ ਟੈਗ ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ ( semver ਕ੍ਰਮ ਵਿੱਚ `vX.Y.Z` ; ਪਿਛੇਤਰ ਟੈਗ ਜਿਵੇਂ ਕਿ ਨਾਈਟਲੀਜ਼ ਦੀ ਗਿਣਤੀ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ) ਜੋ ਕਿ `--base` ਦੇ ਸਮਾਨ ਨਿਯਮਾਂ ਦੇ ਨਾਲ, `HEAD` ਦੇ ਇਤਿਹਾਸ ਵਿੱਚ ਹੈ। ਰੀਲੀਜ਼-ਗ੍ਰੀਨ (`scripts/quality/validate-release-green.mjs`) ਗੇਟ ਨੂੰ ਇਸ ਤਰੀਕੇ ਨਾਲ ਚਲਾਉਂਦਾ ਹੈ, ਕਿਉਂਕਿ ਪੁਸ਼ ਅਤੇ ਅਨੁਸੂਚਿਤ ਰਨ ਦਾ ਕੋਈ ਪੁੱਲ ਬੇਨਤੀ ਅਧਾਰ ਨਹੀਂ ਹੁੰਦਾ ਹੈ ਅਤੇ ਇੱਕ ਅਭੇਦ ਇੱਕ ਤਾਜ਼ਾ CI ਰਨ ਤੋਂ ਬਿਨਾਂ ਉਤਰ ਸਕਦਾ ਹੈ। ਇਤਿਹਾਸ ਵਿੱਚ ਕੋਈ ਰੀਲਿਜ਼ ਟੈਗ ਦੇ ਨਾਲ ਗੇਟ ਫੇਲ ਹੋ ਜਾਂਦਾ ਹੈ; `git fetch --tags` ਚਲਾਓ ( CI ਵਿੱਚ, `fetch-depth: 0` ਨਾਲ `actions/checkout` ਟੈਗ ਲਿਆਉਂਦਾ ਹੈ)।

ਕਮਿਊਟੇਸ਼ਨ ਚੈੱਕ (`scripts/check/migration-commutation.ts`) ਅਸਲ ਇੰਸਟਾਲ ਮਾਰਗ ਦੇ ਨਾਲ ਦੋ ਅਸਥਾਈ ਡੇਟਾਬੇਸ ਬਣਾਉਂਦਾ ਹੈ: ਇੱਕ** ਅੱਪਗਰੇਡ ਕੀਤਾ** ਇੱਕ (ਬੇਸ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨਾਲ ਬੂਟ ਕਰੋ, ਫਿਰ ਪੁੱਲ ਬੇਨਤੀ ਦੇ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨਾਲ ਉਸੇ ਫਾਈਲ 'ਤੇ ਦੁਬਾਰਾ ਬੂਟ ਕਰੋ) ਅਤੇ ਇੱਕ** ਤਾਜ਼ਾ** ਇੱਕ (ਪੁੱਲ ਬੇਨਤੀ ਦੇ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨਾਲ ਇੱਕ ਬੂਟ)। ਇਹ ਨਤੀਜੇ ਵਾਲੇ ਸਕੀਮਾਂ ਦੀ ਤੁਲਨਾ ਕਰਦਾ ਹੈ: ਟੇਬਲ ਅਤੇ ਕਾਲਮ (ਕਾਲਮ ਆਰਡਰ ਨੂੰ ਨਜ਼ਰਅੰਦਾਜ਼ ਕਰਨਾ), UNIQUE / PRIMARY KEY ਅਤੇ FOREIGN KEY ਸੀਮਾਵਾਂ, ਹਰੇਕ ਸਾਰਣੀ ਦਾ ਸਧਾਰਣ `CREATE TABLE` ਟੈਕਸਟ (ਜੋ ਕਿ CHECK ਰੁਕਾਵਟਾਂ, ਕੋਲੇਸ਼ਨਾਂ, ਉਤਪੰਨ ਕਾਲਮ ਅਤੇ ਸੂਚਕਾਂਕ ਵਿਕਲਪਾਂ, ਟੇਬਲ ਵਿਊਜ਼ ਟ੍ਰਿਗਰ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ)। ਕਤਾਰ ਡੇਟਾ ਦੀ ਤੁਲਨਾ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ। ਜੇਕਰ ਉਹ ਮੇਲ ਖਾਂਦੇ ਹਨ, ਤਾਂ ਗੇਟ ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ ਕਿ ਫਾਈਲ ਆਰਡਰ ਤੋਂ ਬਾਹਰ ਹੈ ਪਰ ਆਉਣ-ਜਾਣ ਅਤੇ ਲੰਘ ਜਾਂਦੀ ਹੈ। ਜੇਕਰ ਉਹ ਭਿੰਨ ਹੁੰਦੇ ਹਨ, ਤਾਂ ਗੇਟ ਫਰਕ ਅਤੇ ਕੇਸ ਲਈ ਇੱਕ ਸੰਕੇਤ ਦੇ ਨਾਲ ਫੇਲ ਹੋ ਜਾਂਦਾ ਹੈ: ਇੱਕ ਆਊਟ-ਆਫ-ਆਰਡਰ ਫਾਈਲ ਲਈ, ਇਸਦਾ ਨਾਮ `npm run db:new-migration` ਨਾਲ ਦੁਬਾਰਾ ਤਿਆਰ ਕਰੋ, ਜੋ ਕਿ ਸੁਰੱਖਿਅਤ ਹੈ ਕਿਉਂਕਿ ਫਾਈਲ ਨੂੰ ਅਜੇ ਮਰਜ ਨਹੀਂ ਕੀਤਾ ਗਿਆ ਹੈ; ਇੱਕ ਸੰਪਾਦਿਤ ਅਧਾਰ ਫਾਈਲ ਲਈ, ਅਧਾਰ ਸਮੱਗਰੀ ਨੂੰ ਬਹਾਲ ਕਰੋ ਅਤੇ ਇੱਕ ਨਵੀਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਵਿੱਚ ਤਬਦੀਲੀ ਕਰੋ; ਇੱਕ ਨਾਮ ਬਦਲੀ ਗਈ ਫਾਈਲ ਲਈ, ਨਾਮ ਬਦਲੋ ਜਾਂ ਕੋਈ ਹੋਰ ਨਵਾਂ ਟਾਈਮਸਟੈਂਪ ਚੁਣੋ ਜਿੱਥੇ ਇਹ ਕਮਿਊਟ ਕਰਦਾ ਹੈ, ਕਦੇ ਵੀ ਕਿਸੇ ਹੋਰ ਨਾਮ ਨਾਲ ਇੱਕੋ ਟਾਈਮਸਟੈਂਪ ਨਹੀਂ। ਜੇ ਚੈਕ ਆਪਣੇ ਆਪ ਨਹੀਂ ਚੱਲ ਸਕਦਾ, ਤਾਂ ਗੇਟ CI ਵਿੱਚ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ ਅਤੇ ਸਿਰਫ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਚੇਤਾਵਨੀ ਦਿੰਦਾ ਹੈ। ਇੱਕ ਸੰਪਾਦਿਤ ਬੇਸ ਫਾਈਲ ਲਈ, ਅੱਪਗਰੇਡ ਕੀਤਾ ਡੇਟਾਬੇਸ ਉਸ ਫਾਈਲ ਦੇ ਅਧਾਰ ਦੀ ਸਮੱਗਰੀ ਨਾਲ ਬਣਾਇਆ ਗਿਆ ਹੈ, ਅਤੇ ਦੂਜਾ ਬੂਟ ਇਸਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ ਕਿਉਂਕਿ ਇਸਦਾ ਸੰਸਕਰਣ ਪਹਿਲਾਂ ਹੀ ਰਿਕਾਰਡ ਕੀਤਾ ਗਿਆ ਹੈ। ਇੱਕ ਨਾਮ ਬਦਲੀ ਗਈ ਫਾਈਲ ਲਈ, ਅੱਪਗਰੇਡ ਡੇਟਾਬੇਸ ਨੂੰ ਇਸਦੇ ਪੁਰਾਣੇ ਨਾਮ ਹੇਠ ਫਾਈਲ ਨਾਲ ਬਣਾਇਆ ਗਿਆ ਹੈ, ਅਤੇ ਦੂਜਾ ਬੂਟ ਇਸਨੂੰ ਦੁਬਾਰਾ ਚਲਾਉਣ ਦੀ ਬਜਾਏ ਅਨੁਕੂਲਤਾ ਐਂਟਰੀ ਦੁਆਰਾ ਆਪਣੀ `_omniroute_migrations` ਕਤਾਰ ਨੂੰ ਮੂਵ ਕਰਦਾ ਹੈ; ਗੇਟ ਨਵੇਂ ਨਾਂ ਨੂੰ `--must-not-apply` ਨਾਲ ਪਾਸ ਕਰਦਾ ਹੈ, ਇਸਲਈ ਜਾਂਚ ਅਸਫਲ ਹੋ ਜਾਂਦੀ ਹੈ ਜੇਕਰ ਦੂਜਾ ਬੂਟ ਇਸਨੂੰ ਲਾਗੂ ਕਰਦਾ ਹੈ। ਜੇਕਰ ਪੁੱਲ ਬੇਨਤੀ ਮਾਈਗ੍ਰੇਸ਼ਨ ਅੱਪਗਰੇਡ ਕੀਤੇ ਮਾਰਗ 'ਤੇ ਲਾਗੂ ਕਰਨ ਵਿੱਚ ਅਸਫਲ ਹੋ ਜਾਂਦੀ ਹੈ, ਭਾਵ, ਹਰੇਕ ਬੇਸ ਮਾਈਗ੍ਰੇਸ਼ਨ ਤੋਂ ਬਾਅਦ (ਭਾਵੇਂ ਇਹ ਇੱਕ ਤਾਜ਼ਾ ਇੰਸਟਾਲੇਸ਼ਨ 'ਤੇ ਵੀ ਫੇਲ ਹੁੰਦਾ ਹੈ ਜਾਂ ਨਹੀਂ), ਗੇਟ `migration do PR não aplica` ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ ਅਤੇ ਤੁਹਾਨੂੰ ਅਧਾਰ ਦੀ ਮੌਜੂਦਾ ਸਕੀਮਾ ਦੇ ਵਿਰੁੱਧ SQL ਨੂੰ ਠੀਕ ਕਰਨ ਲਈ ਕਹਿੰਦਾ ਹੈ; ਜੇਕਰ ਫਾਈਲ ਬਾਅਦ ਦੇ ਟਾਈਮਸਟੈਂਪ ਦੇ ਨਾਲ ਕਿਸੇ ਹੋਰ ਪੁੱਲ ਬੇਨਤੀ ਮਾਈਗਰੇਸ਼ਨ 'ਤੇ ਨਿਰਭਰ ਕਰਦੀ ਹੈ, ਤਾਂ ਇਸਦਾ ਨਾਮ `npm run db:new-migration` ਨਾਲ ਦੁਬਾਰਾ ਬਣਾਓ।

ਉਹੀ ਤੁਲਨਾ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਚਲਾਉਣ ਲਈ, ਬੇਸ ਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਪਾਸ ਕਰੋ, ਉਦਾਹਰਨ ਲਈ `npm run check:migration-numbering -- --base origin/<base-branch>`, ਜਾਂ `npm run check:migration-numbering -- --base-latest-tag` ਨਵੀਨਤਮ ਰੀਲੀਜ਼ ਨਾਲ ਤੁਲਨਾ ਕਰਨ ਲਈ।

### ਇੱਕ ਓਪਨ PR ਦੇ `NNN` ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਬਦਲਣਾ

ਸਵਿੱਚ ਤੋਂ ਪਹਿਲਾਂ ਖੋਲ੍ਹੀ ਗਈ ਇੱਕ ਪੁੱਲ ਬੇਨਤੀ ਅਜੇ ਵੀ ਇੱਕ ਕ੍ਰਮਵਾਰ ਫਾਈਲ ਰੱਖ ਸਕਦੀ ਹੈ ਜਿਵੇਂ ਕਿ `242_add_widgets.sql`। `241` ਤੋਂ ਉੱਪਰਲੇ ਪੁਰਾਣੇ ਨੰਬਰਾਂ ਨੂੰ ਰੱਦ ਕਰ ਦਿੱਤਾ ਗਿਆ ਹੈ, ਇਸਲਈ ਮਿਲਾਨ ਤੋਂ ਪਹਿਲਾਂ ਇਸਨੂੰ ਬਦਲੋ:

1. **ਵਰਣਨ ਨੂੰ ਰੱਖਦੇ ਹੋਏ, ਜਨਰੇਟਰ ਨਾਲ ਫਾਈਲ ਦਾ ਨਾਮ ਬਦਲੋ।** ਨਵਾਂ ਨਾਮ ਪ੍ਰਾਪਤ ਕਰਨ ਲਈ `npm run db:new-migration -- <same description>` ਚਲਾਓ, SQL ਨੂੰ ਇਸ ਵਿੱਚ ਲੈ ਜਾਓ, ਅਤੇ ਪੁਰਾਣੀ `NNN_` ਫਾਈਲ ਨੂੰ ਮਿਟਾਓ। ਵਰਣਨ ਇੱਕੋ ਜਿਹਾ ਰਹਿਣਾ ਚਾਹੀਦਾ ਹੈ: ਹੇਠਾਂ ਦਿੱਤੀ ਅਨੁਕੂਲਤਾ ਐਂਟਰੀ ਇਸ 'ਤੇ ਮੇਲ ਖਾਂਦੀ ਹੈ।
2. **ਇੱਕ ਅਨੁਕੂਲਤਾ ਇੰਦਰਾਜ਼ ਸ਼ਾਮਲ ਕਰੋ ਜੇਕਰ ਇੱਕ ਨਿਰੰਤਰ ਡੇਟਾਬੇਸ ਪੁਰਾਣੇ ਨੰਬਰ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ।** ਜੇਕਰ ਕੋਈ ਡਾਟਾਬੇਸ ਰੱਖਿਆ ਗਿਆ ਹੈ (homolog, a VPS, ਇੱਕ ਯੋਗਦਾਨਕਰਤਾ ਦਾ ਆਪਣਾ ਇੰਸਟਾਲ) `NNN_` ਫਾਈਲ ਨਾਲ PR ਦਾ ਇੱਕ ਬਿਲਡ ਚਲਾਇਆ ਗਿਆ ਹੈ, `src/lib/db/migrationRunner/constants.ts` ਵਿੱਚ `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` ਨੂੰ `RENAMED_MIGRATION_COMPATIBILITY` ਵਿੱਚ ਜੋੜੋ। ਇਹ ਹੈ** `237` ਤੋਂ `241` ਲਈ ਲੋੜੀਂਦਾ ਹੈ** : ਉਹ ਸਲਾਟ ਹੁਣ ਕੈਨੋਨੀਕਲ `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` ਅਤੇ `241_seen_models.sql` ਰੱਖਦੇ ਹਨ, ਅਤੇ ਬਿਨਾਂ ਐਂਟਰੀ ਦੇ ਅਜਿਹਾ ਡੇਟਾਬੇਸ ਕੈਨੋਨੀਕਲ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਹਮੇਸ਼ਾ ਲਈ ਛੱਡ ਦਿੰਦਾ ਹੈ ਅਤੇ ਪਰਿਵਰਤਿਤ ਨੂੰ ਦੁਬਾਰਾ ਚਲਾਉਂਦਾ ਹੈ। ਇਹ ਇੱਕ ਸਲਾਟ ਲਈ ਵੀ ਕੰਮ ਕਰਦਾ ਹੈ ਜੋ ਖਾਲੀ ਰਹਿੰਦਾ ਹੈ, ਜਿਵੇਂ ਕਿ `242`, ਜਦੋਂ ਮੰਜ਼ਿਲ ਇੱਕ ਟਾਈਮਸਟੈਂਪ ਹੁੰਦੀ ਹੈ। ਜਦੋਂ ਸ਼ੱਕ ਹੋਵੇ, ਤਾਂ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰੋ। ਤੁਸੀਂ ਇਸ ਨੂੰ ਐਰੇ ਵਿੱਚ ਕਿੱਥੇ ਜੋੜਦੇ ਹੋ ਇਸ ਨਾਲ ਕੋਈ ਫ਼ਰਕ ਨਹੀਂ ਪੈਂਦਾ: ਜਦੋਂ ਇੱਕ ਐਂਟਰੀ ਦਾ ਟੀਚਾ ਸਲਾਟ ਅਜੇ ਵੀ ਇੱਕ ਕਤਾਰ ਰੱਖਦਾ ਹੈ ਜੋ ਇੱਕ ਹੋਰ ਇੰਦਰਾਜ਼ ਦੂਰ ਚਲੀ ਜਾਂਦੀ ਹੈ (ਉਦਾਹਰਨ ਲਈ `237` ਇੱਕ PR ਕਤਾਰ ਨੂੰ ਰੱਖਦਾ ਹੈ ਜਦੋਂ ਕਿ ਇੱਕ ਪੁਰਾਣੀ `usage_history_calculated_cost` ਕਤਾਰ `237` ਵਿੱਚ ਜਾਣ ਦੀ ਉਡੀਕ ਕਰਦੀ ਹੈ), ਦੌੜਾਕ ਉਸ ਐਂਟਰੀ ਨੂੰ ਸਲਾਟ ਖਾਲੀ ਹੋਣ ਤੱਕ ਉਡੀਕ ਕਰਨ ਦਿੰਦਾ ਹੈ। ਸਿਰਫ਼ ਇੱਕ ਅਸਲੀ ਟਕਰਾਅ, ਜਿਵੇਂ ਕਿ ਇੱਕ ਕਤਾਰ ਵਿੱਚ ਕੋਈ ਐਂਟਰੀ ਮੂਵ ਨਹੀਂ, ਜਾਂ ਦੋ ਐਂਟਰੀਆਂ ਜੋ ਸਲਾਟਾਂ ਨੂੰ ਸਵੈਪ ਕਰਦੀਆਂ ਹਨ, `Cannot reconcile ...` ਨਾਲ ਬੂਟ ਨੂੰ ਰੋਕਦਾ ਹੈ।
3. **SQL ਨੂੰ ਨਿਰਬਲ ਰੱਖੋ** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), ਕਿਉਂਕਿ ਪਰਿਵਰਤਿਤ ਮਾਈਗ੍ਰੇਸ਼ਨ ਇੱਕ ਡੇਟਾਬੇਸ ਨੂੰ ਪੂਰਾ ਕਰ ਸਕਦਾ ਹੈ ਜਿੱਥੇ ਇਸਦਾ ਸਕੀਮਾ ਪਹਿਲਾਂ ਹੀ ਮੌਜੂਦ ਹੈ।
4. **ਸੰਸਕਰਣ-ਕੁੰਜੀ ਵਾਲੇ ਵਿਸ਼ੇਸ਼ ਕੇਸਾਂ ਨੂੰ ਮੂਵ ਕਰੋ।** ਜੇਕਰ PR ਆਪਣੇ ਪੁਰਾਣੇ ਨੰਬਰ ਲਈ `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) ਜਾਂ `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) ਵਿੱਚ ਕੇਸ ਜੋੜਿਆ ਹੈ, ਤਾਂ ਕੁੰਜੀ ਨੂੰ ਨਵੇਂ ਟਾਈਮਸਟੈਂਪ ਵਿੱਚ ਬਦਲੋ।

`tests/unit/db/codex-fence-migration-rename.test.ts` ਮੁੜ-ਨਾਮ ਕੀਤੇ ਮਾਈਗ੍ਰੇਸ਼ਨ ਲਈ ਇੱਕ ਟੈਸਟ ਦੀ ਇੱਕ ਕਾਰਜਸ਼ੀਲ ਉਦਾਹਰਨ ਹੈ।

### ਸਵਿੱਚ ਤੋਂ ਪਹਿਲਾਂ ਸ਼ਾਖਾਵਾਂ ਲਈ ਬੈਕਪੋਰਟ

`YYYYMMDDHHMMSS_` ਫਾਈਲ ਨੂੰ ਕਦੇ ਵੀ ਚੈਰੀ-ਪਿਕ ਜਾਂ ਬੈਕਪੋਰਟ ਨਾ ਕਰੋ ਉਸ ਸ਼ਾਖਾ ਵਿੱਚ ਜੋ ਸਵਿੱਚ ਤੋਂ ਪਹਿਲਾਂ ਹੈ (ਉਦਾਹਰਨ ਲਈ ਇੱਕ ਪੁਰਾਣੀ `release/v*` ਸ਼ਾਖਾ)। ਉੱਥੇ ਦਾ ਦੌੜਾਕ ਫਾਈਲ ਦੇ ਨਾਮਾਂ ਨੂੰ ਟੈਕਸਟ ਦੇ ਰੂਪ ਵਿੱਚ ਕ੍ਰਮਬੱਧ ਕਰਦਾ ਹੈ, ਇਸਲਈ ਇੱਕ ਟਾਈਮਸਟੈਂਪਡ ਫਾਈਲ ਇੱਕ ਤਾਜ਼ਾ ਡੇਟਾਬੇਸ ਵਿੱਚ `201_` ਅਤੇ `202_` ਦੇ ਵਿਚਕਾਰ ਚੱਲੇਗੀ, ਅਤੇ ਉੱਥੇ ਪੁਰਾਣਾ ਗੇਟ 14-ਅੰਕ ਅਗੇਤਰਾਂ ਨੂੰ ਨਹੀਂ ਸਮਝਦਾ ਹੈ। ਅਜਿਹੀ ਬ੍ਰਾਂਚ 'ਤੇ, ਉਸ ਬ੍ਰਾਂਚ ਦੀ ਆਪਣੀ ਅਗਲੀ `NNN_` ਫਾਈਲ, idempotent ਦੇ ਤੌਰ 'ਤੇ ਬਦਲਾਅ ਲਿਖੋ, ਇਸ ਲਈ ਜਦੋਂ ਟਾਈਮਸਟੈਂਪ ਵਾਲਾ ਸੰਸਕਰਣ ਬਾਅਦ ਵਿੱਚ ਆਉਂਦਾ ਹੈ ਤਾਂ ਇਹ ਇੱਕ ਨੋ-ਓਪ ਹੈ।

### ਮਾਈਗ੍ਰੇਸ਼ਨ ਕਿਵੇਂ ਚੱਲਦੇ ਹਨ

ਸ਼ੁਰੂਆਤ 'ਤੇ, `migrationRunner.ts`:

1. ਜੇ ਮੌਜੂਦ ਨਹੀਂ ਹੈ ਤਾਂ `_omniroute_migrations` ਸਾਰਣੀ ਬਣਾਉਂਦਾ ਹੈ
2. ਪਹਿਲਾਂ ਤੋਂ ਲਾਗੂ ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਲਈ ਸਵਾਲ
3. ਕਿਸੇ ਵੀ ਨਵੇਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਕ੍ਰਮ ਵਿੱਚ ਲਾਗੂ ਕਰਦਾ ਹੈ, ਹਰੇਕ ਇੱਕ ਲੈਣ-ਦੇਣ ਵਿੱਚ
4. ਟਾਈਮਸਟੈਂਪ ਨਾਲ ਹਰੇਕ ਲਾਗੂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਰਿਕਾਰਡ ਕਰਦਾ ਹੈ

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### ਨਿਪੁੰਸਕਤਾ

ਪਰਵਾਸ ਜ਼ਰੂਰ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ** ਨਿਰਬਲ** — ਉਹਨਾਂ ਨੂੰ ਦੋ ਵਾਰ ਚਲਾਉਣਾ ਇੱਕ ਨੋ-ਓਪ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, ਅਤੇ `OR IGNORE` / `OR REPLACE` ਧਾਰਾਵਾਂ ਦੀ ਖੁੱਲ੍ਹ ਕੇ ਵਰਤੋਂ ਕਰੋ।

### ਇੱਕ ਨਵਾਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਸ਼ਾਮਲ ਕਰਨਾ

1. **ਜਨਰੇਟਰ ਨਾਲ ਫਾਈਲ ਬਣਾਓ** : `npm run db:new-migration -- <description>` (ਉਦਾਹਰਨ ਲਈ `npm run db:new-migration -- add combo priority`)। ਇਹ ਮੌਜੂਦਾ UTC ਸਮੇਂ ਅਤੇ ਇੱਕ ਟਿੱਪਣੀ ਸਿਰਲੇਖ ਨਾਲ `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` ਲਿਖਦਾ ਹੈ, ਇੱਕ ਸਕਿੰਟ ਅੱਗੇ ਵਧਦਾ ਹੈ ਜੇਕਰ ਉਹ ਟਾਈਮਸਟੈਂਪ ਲਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ ਕਦੇ ਵੀ ਇੱਕ ਫਾਈਲ ਨੂੰ ਓਵਰਰਾਈਟ ਨਹੀਂ ਕਰਦਾ ਹੈ। ਹੱਥ ਨਾਲ ਨੰਬਰ ਨਾ ਚੁਣੋ.
2. **ਸੁਰੱਖਿਅਤ DDL ਵਰਤੋਂ ਕਰੋ** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **ਧਿਆਨ ਨਾਲ ਡਾਟਾ ਬੈਕਫਿਲ ਕਰੋ** : ਮੌਜੂਦਾ ਕਤਾਰਾਂ ਨੂੰ ਸੰਭਾਲਣ ਲਈ `UPDATE ... WHERE ...` ਵਰਤੋਂ ਕਰੋ
4. **ਆਰਡਰ ਅਤੇ ਨਾਮਕਰਨ ਦੀ ਜਾਂਚ ਕਰੋ** : `npm run test:migrations:fresh` (ਖਾਲੀ ਡੇਟਾਬੇਸ ਤੇ ਸਾਰੇ ਮਾਈਗ੍ਰੇਸ਼ਨ) ਅਤੇ `npm run check:migration-numbering`
5. **ਇੱਕ ਕਾਪੀ 'ਤੇ ਟੈਸਟ ਕਰੋ** : ਉਤਪਾਦਨ 'ਤੇ ਕਦੇ ਵੀ ਬਿਨਾਂ ਜਾਂਚ ਕੀਤੇ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨਾ ਚਲਾਓ

ਉਦਾਹਰਨ:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **ਪਿੱਛੇ ਵੱਲ - ਅਸੰਗਤ ਤਬਦੀਲੀਆਂ** (ਉਦਾਹਰਨ ਲਈ, ਕਾਲਮ ਛੱਡਣਾ) ਮੁਸ਼ਕਲ ਹਨ। ਇੱਕ ਵਾਰ ਮਾਈਗ੍ਰੇਸ਼ਨ ਲਾਗੂ ਹੋਣ ਤੋਂ ਬਾਅਦ, OmniRoute NOT ਡਾਊਨਗ੍ਰੇਡ — ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ, ਸਕੀਮਾ ਤਬਦੀਲੀ ਸਥਾਈ ਹੁੰਦੀ ਹੈ। ਉਸ ਅਨੁਸਾਰ ਯੋਜਨਾ ਬਣਾਓ।

## ਸਟੋਰੇਜ ਵਿੱਚ ਇਨਕ੍ਰਿਪਸ਼ਨ

ਸੰਵੇਦਨਸ਼ੀਲ ਫ਼ੀਲਡਾਂ (API ਕੁੰਜੀਆਂ, OAuth ਟੋਕਨ, ਕਨੈਕਸ਼ਨ ਸਟ੍ਰਿੰਗਾਂ) ਨੂੰ ਸਟੋਰੇਜ ਵਿੱਚ **AES-256-GCM** ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਇਨਕ੍ਰਿਪਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

```ts
// src/lib/db/encryption.ts (ਸਰਲ ਰੂਪ)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### ਇਹ ਕਿੱਥੇ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ

- `provider_connections.api_key` — ਐਪਲੀਕੇਸ਼ਨ ਪੱਧਰ ਉੱਤੇ ਇਨਕ੍ਰਿਪਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ
- `provider_connections.access_token`, `refresh_token`, `id_token` — ਐਪਲੀਕੇਸ਼ਨ ਪੱਧਰ ਉੱਤੇ ਇਨਕ੍ਰਿਪਟ ਕੀਤੇ ਜਾਂਦੇ ਹਨ
- `namespace = "secrets"` ਵਾਲੀਆਂ `key_value` ਐਂਟਰੀਆਂ — ਐਪਲੀਕੇਸ਼ਨ ਪੱਧਰ ਉੱਤੇ ਇਨਕ੍ਰਿਪਟ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ
- `proxy_registry.auth` — ਐਪਲੀਕੇਸ਼ਨ ਪੱਧਰ ਉੱਤੇ ਇਨਕ੍ਰਿਪਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਜੇ ਮੌਜੂਦ ਹੋਵੇ)

### ਇਨਕ੍ਰਿਪਸ਼ਨ ਕੁੰਜੀ

ਇਨਕ੍ਰਿਪਸ਼ਨ ਕੁੰਜੀ ਇੱਕ **ਪਾਸਫਰੇਜ਼** (`STORAGE_ENCRYPTION_KEY` env var ਰਾਹੀਂ ਸੈੱਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ) ਅਤੇ ਇੱਕ **ਸਾਲਟ** (DB ਵਿੱਚ ਸਟੋਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ) ਤੋਂ ਬਣਾਈ ਜਾਂਦੀ ਹੈ। ਡਾਟਾ ਡਿਕ੍ਰਿਪਟ ਕਰਨ ਲਈ ਦੋਵੇਂ ਲੋੜੀਂਦੇ ਹਨ।

```bash
# ਇੱਕ ਸੁਰੱਖਿਅਤ ਪਾਸਫਰੇਜ਼ ਬਣਾਓ
openssl rand -hex 32

# .env ਵਿੱਚ ਸੈੱਟ ਕਰੋ
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **ਬਹੁਤ ਮਹੱਤਵਪੂਰਨ**: ਇਨਕ੍ਰਿਪਸ਼ਨ ਕੁੰਜੀ ਗੁਆਉਣ ਦਾ ਮਤਲਬ ਹੈ ਸਾਰੇ ਇਨਕ੍ਰਿਪਟ ਕੀਤੇ ਡਾਟੇ ਤੱਕ ਪਹੁੰਚ ਗੁਆਉਣਾ। **ਕੁੰਜੀ ਦਾ ਬੈਕਅੱਪ ਡਾਟਾਬੇਸ ਤੋਂ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ ਲਓ**।

### ਕੀ ਇਨਕ੍ਰਿਪਟ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ

ਕਾਰਗੁਜ਼ਾਰੀ ਦੇ ਕਾਰਨਾਂ ਕਰਕੇ, ਹੇਠ ਲਿਖੀਆਂ ਚੀਜ਼ਾਂ ਨੂੰ ਪਲੇਨਟੈਕਸਟ ਵਿੱਚ ਸਟੋਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:

- ਪ੍ਰੋਵਾਈਡਰ ਦੇ ਡਿਸਪਲੇ ਨਾਮ
- ਮਾਡਲ ਪਰਿਭਾਸ਼ਾਵਾਂ (ਪਹਿਲਾਂ ਹੀ ਜਨਤਕ)
- ਰਾਊਟਿੰਗ ਨਿਯਮ
- ਵਰਤੋਂ ਦੇ ਰਿਕਾਰਡ (ਕੋਈ PII ਨਹੀਂ)

## ਇਨਕ੍ਰਿਪਸ਼ਨ ਸੰਬੰਧੀ ਸਾਵਧਾਨੀਆਂ (v3.8.16+)

OmniRoute ਦੋ ਇਨਕ੍ਰਿਪਸ਼ਨ ਸਕੀਮਾਂ ਨੂੰ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਸੰਭਾਲਣ ਲਈ **`migrateLegacyEncryptedString()`** ਵਰਤਦਾ ਹੈ:

- **ਪੁਰਾਣੀ** (v3.5.0 ਤੋਂ ਪਹਿਲਾਂ): XOR-ਅਧਾਰਿਤ "ਇਨਕ੍ਰਿਪਸ਼ਨ" (ਅਸਲ ਕ੍ਰਿਪਟੋਗ੍ਰਾਫੀ ਨਹੀਂ)
- **ਮੌਜੂਦਾ**: ਉਚਿਤ IV ਅਤੇ ਪ੍ਰਮਾਣਿਕਤਾ ਟੈਗ ਨਾਲ AES-256-GCM

ਮਾਈਗ੍ਰੇਸ਼ਨ ਸਹਾਇਕ ਪੁਰਾਣੇ ਫਾਰਮੈਟ ਦੀ ਪਛਾਣ ਕਰਦਾ ਹੈ ਅਤੇ ਪਹਿਲੀ ਵਾਰ ਪੜ੍ਹੇ ਜਾਣ 'ਤੇ ਨਵੀਂ ਸਕੀਮ ਨਾਲ ਮੁੜ ਇਨਕ੍ਰਿਪਟ ਕਰਦਾ ਹੈ। ਇਸਦਾ ਅਰਥ ਹੈ ਕਿ ਤੁਸੀਂ ਕ੍ਰਿਡੈਂਸ਼ਲ ਗੁਆਏ ਬਿਨਾਂ ਪੁਰਾਣੇ ਡਾਟਾਬੇਸ ਨੂੰ ਅੱਪਗ੍ਰੇਡ ਕਰ ਸਕਦੇ ਹੋ।

## ਰੀਡ ਕੈਸ਼

ਅਕਸਰ ਪੜ੍ਹੇ ਜਾਣ ਵਾਲੇ ਡਾਟੇ (ਮਾਡਲਾਂ, ਪ੍ਰਦਾਤਾਵਾਂ, ਸੈਟਿੰਗਾਂ) ਲਈ, `readCache.ts` ਇੱਕ **ਇਨ-ਮੈਮੋਰੀ ਕੈਸ਼** ਪ੍ਰਦਾਨ ਕਰਦੀ ਹੈ:

```ts
// ਸਟਾਰਟਅੱਪ ਵੇਲੇ ਕੈਸ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਲਿਖਣ 'ਤੇ ਅਵੈਧ ਕੀਤਾ ਜਾਂਦਾ ਹੈ
const providers = await getCachedProviders(); // ਤੇਜ਼, ਇਨ-ਮੈਮੋਰੀ
const fresh = await listProviders(); // ਹੌਲੀ, DB ਤੱਕ ਪਹੁੰਚ ਕਰਦਾ ਹੈ
```

| ਕੈਸ਼ ਕੀਤੀ ਇਕਾਈ         | ਕੈਸ਼ ਕੁੰਜੀ     | TTL      |
| ---------------------- | -------------- | -------- |
| `models`               | `models:v1`    | ਲਿਖਣ ਤੱਕ |
| `provider_connections` | `providers:v1` | ਲਿਖਣ ਤੱਕ |
| `settings`             | `settings:v1`  | ਲਿਖਣ ਤੱਕ |
| `combos`               | `combos:v1`    | ਲਿਖਣ ਤੱਕ |

ਸੰਬੰਧਿਤ ਟੇਬਲ ਵਿੱਚ ਹਰ ਵਾਰ ਲਿਖਣ 'ਤੇ ਕੈਸ਼ ਅਵੈਧ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।

## ਬੈਕਅੱਪ ਅਤੇ ਰਿਕਵਰੀ

### ਮੈਨੂਅਲ ਬੈਕਅੱਪ

```bash
# ਸਥਾਨਕ ਬੈਕਅੱਪ ਬਣਾਉਣ ਲਈ CLI ਦੀ ਵਰਤੋਂ ਕਰੋ
omniroute backup create --name pre-migration

# ਜਾਂ API ਰਾਹੀਂ
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

ਬੈਕਅੱਪ ਫਾਈਲ ਵਿੱਚ ਇਹ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ:

- ਸਾਰੀਆਂ DB ਟੇਬਲਾਂ (JSON ਵਿੱਚ ਸੀਰੀਅਲਾਈਜ਼ ਕੀਤੀਆਂ)
- ਕਾਲ ਲੌਗ ਆਰਟੀਫੈਕਟ (base64-ਇਨਕੋਡ ਕੀਤੇ, ਵਿਕਲਪਿਕ)
- ਸੈਟਿੰਗਾਂ + ਸੀਕ੍ਰੇਟ (ਇਨਕ੍ਰਿਪਟ ਕੀਤੇ)
- ਪਲੱਗਇਨ ਕੌਂਫਿਗਰੇਸ਼ਨ

### ਰੀਸਟੋਰ

```bash
# CLI ਰਾਹੀਂ
omniroute restore pre-migration

# API ਰਾਹੀਂ
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **ਚੇਤਾਵਨੀ**: ਰੀਸਟੋਰ ਪੂਰੇ DB ਨੂੰ ਓਵਰਰਾਈਟ ਕਰ ਦਿੰਦਾ ਹੈ। ਪਹਿਲਾਂ ਸਾਰੇ ਕਲਾਇੰਟ ਬੰਦ ਕਰੋ।

### ਸਵੈਚਾਲਿਤ ਬੈਕਅੱਪ

```bash
# CLI ਰਾਹੀਂ ਸਵੈਚਾਲਿਤ ਰੋਜ਼ਾਨਾ ਬੈਕਅੱਪ ਸਮਰੱਥ ਕਰੋ
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

ਸ਼ੈਡਿਊਲ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ 'ਤੇ ਇੱਕ ਬੈਕਗ੍ਰਾਊਂਡ ਜੌਬ ਦੁਆਰਾ ਚਲਾਇਆ ਜਾਂਦਾ ਹੈ, ਜੋ ਹਰ 30 ਸਕਿੰਟ
(ਡਿਫਾਲਟ) ਬਾਅਦ ਟਿਕ ਕਰਦੀ ਹੈ ਅਤੇ ਸਥਾਨਕ ਸਰਵਰ ਸਮੇਂ ਦੇ ਮੁਕਾਬਲੇ cron ਐਕਸਪ੍ਰੈਸ਼ਨ ਦਾ ਮੁਲਾਂਕਣ ਕਰਦੀ ਹੈ।

| ਵੇਰੀਏਬਲ                                     | ਡਿਫਾਲਟ  | ਵਰਣਨ                                                                                                                       |
| ------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000` | ms ਵਿੱਚ ਟਿਕ ਅੰਤਰਾਲ (ਘੱਟੋ-ਘੱਟ `5000`)। ਮੇਲ ਖਾਂਦੇ cron ਮਿੰਟ ਦੇ ਅੰਦਰ ਭਰੋਸੇਯੋਗ ਢੰਗ ਨਾਲ ਆਉਣ ਲਈ ਇਹ 60 s ਤੋਂ ਛੋਟਾ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ। |

### SQLite ਹੌਟ ਬੈਕਅੱਪ

ਚੱਲ ਰਹੇ DB ਦਾ ਬਿਨਾਂ ਡਾਊਨਟਾਈਮ ਬੈਕਅੱਪ ਲੈਣ ਲਈ:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

ਇਹ SQLite ਦੀ ਔਨਲਾਈਨ ਬੈਕਅੱਪ API ਵਰਤਦਾ ਹੈ — OmniRoute ਦੇ ਚੱਲਦੇ ਸਮੇਂ ਇਸਨੂੰ ਚਲਾਉਣਾ ਸੁਰੱਖਿਅਤ ਹੈ।

## ਪ੍ਰਦਰਸ਼ਨ ਟਿਊਨਿੰਗ

### WAL ਮੋਡ

WAL ਮੂਲ ਰੂਪ ਵਿੱਚ ਯੋਗ ਹੈ। ਉੱਚ-ਲਿਖਤ ਵਰਕਲੋਡ ਲਈ, ਵਿਚਾਰ ਕਰੋ:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` ਸੈੱਟ ਨਹੀਂ ਕਰਦਾ ਹੈ। ਇੱਕ ਚੈਕਪੁਆਇੰਟ WAL ਫਰੇਮਾਂ ਨੂੰ ਮੁੱਖ ਫਾਈਲ ਵਿੱਚ ਭੇਜਦਾ ਹੈ, ਪਰ WAL ਫਾਈਲ ਆਪਣਾ ਸਭ ਤੋਂ ਵੱਡਾ ਨਿਰਧਾਰਤ ਆਕਾਰ ਰੱਖਦੀ ਹੈ। `OMNIROUTE_WAL_GUARD_MAX_MB` ਗਾਰਡ ਸਿਰਫ ਚੇਤਾਵਨੀ ਦਿੰਦਾ ਹੈ ਅਤੇ `wal_checkpoint(RESTART)` ਚਲਾਉਂਦਾ ਹੈ; ਇਹ ਇੱਕ ਡਿਸਕ-ਆਕਾਰ ਕੈਪ ਨਹੀਂ ਹੈ।

### ਸੂਚਕਾਂਕ

ਪ੍ਰਦਰਸ਼ਨ ਲਈ ਮੁੱਖ ਸੂਚਕਾਂਕ (ਪ੍ਰਵਾਸ ਦੁਆਰਾ ਸਵੈ-ਬਣਾਇਆ ਗਿਆ):

- ਪ੍ਰਦਾਤਾ ਦੁਆਰਾ`idx_models_provider` — ਮਾਡਲ ਲੁੱਕਅੱਪ
- `idx_combo_targets_combo_id` — ਕੰਬੋ ਟੀਚਾ ਵਿਸਥਾਰ
- `idx_usage_history_api_key_timestamp` — ਵਰਤੋਂ ਵਿਸ਼ਲੇਸ਼ਣ
- `idx_quota_snapshots_api_key_window` — ਕੋਟਾ ਟਰੈਕਿੰਗ
- `idx_call_logs_timestamp` — ਕਾਲ ਲੌਗ ਸਵਾਲ

ਇੱਕ ਨਵਾਂ ਸੂਚਕਾਂਕ ਜੋੜਨ ਲਈ, ਇੱਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਬਣਾਓ:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### ਮੈਮੋਰੀ-ਮੈਪਡ I/O

ਬਹੁਤ ਵੱਡੇ ਡੇਟਾਬੇਸ (> 10GB) ਲਈ, ਮੈਮੋਰੀ ਮੈਪਿੰਗ ਨੂੰ SQLite ਪ੍ਰਗਮਾ ਦੁਆਰਾ ਐਡਜਸਟ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### ਸੰਕੁਚਿਤ

ਲੰਬੇ ਸਮੇਂ ਤੋਂ ਚੱਲ ਰਹੇ OmniRoute ਉਦਾਹਰਨਾਂ ਨੂੰ ਕਦੇ-ਕਦਾਈਂ `VACUUM` ਤੋਂ ਲਾਭ ਹੁੰਦਾ ਹੈ:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

ਘੱਟ-ਟ੍ਰੈਫਿਕ ਵਿੰਡੋਜ਼ ਦੌਰਾਨ ਮਹੀਨਾਵਾਰ ਚਲਾਓ। (WAL ਮੋਡ ਲੋੜ ਨੂੰ ਘਟਾਉਂਦਾ ਹੈ, ਪਰ ਇਸਨੂੰ ਖਤਮ ਨਹੀਂ ਕਰਦਾ।)

## ਸਿਹਤ ਜਾਂਚ

`src/lib/db/healthCheck.ts` **DB-ਪੱਧਰੀ ਸਿਹਤ ਨਿਦਾਨ** ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ:

ਦੋਵਾਂ ਕਿਰਿਆਵਾਂ ਲਈ ਪ੍ਰਮਾਣੀਕਰਨ ਲੋੜੀਂਦਾ ਹੈ (ਨਹੀਂ ਤਾਂ `401`)। `GET` ਸਿਰਫ਼ ਨਿਦਾਨ ਕਰਦਾ ਹੈ; `POST`
ਉਹੀ ਜਾਂਚ `autoRepair` ਸਮਰੱਥ ਕਰਕੇ ਚਲਾਉਂਦਾ ਹੈ।

```bash
GET  /api/db/health   # ਨਿਦਾਨ ਕਰੋ
POST /api/db/health   # ਨਿਦਾਨ + ਮੁਰੰਮਤ
```

ਜਵਾਬ `runDbHealthCheck()` ਦੁਆਰਾ ਤਿਆਰ ਕੀਤਾ `DbHealthCheckResult` ਹੈ
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "ਡੋਮੇਨ ਬਜਟਾਂ ਨੇ ਉਹਨਾਂ API ਕੁੰਜੀਆਂ ਦਾ ਹਵਾਲਾ ਦਿੱਤਾ ਜੋ ਹੁਣ ਮੌਜੂਦ ਨਹੀਂ ਹਨ।",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ਫ਼ੀਲਡ             | ਅਰਥ                                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | ਜਦੋਂ `issues` ਖਾਲੀ ਹੋਵੇ ਤਾਂ `true`। `driver` ਇਸਨੂੰ ਕਦੇ ਪ੍ਰਭਾਵਿਤ ਨਹੀਂ ਕਰਦਾ।                                                                          |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` ਵਿੱਚੋਂ ਇੱਕ।                                                         |
| `repairedCount`   | ਇਸ ਰਨ ਦੌਰਾਨ ਮੁਰੰਮਤ ਕੀਤੀਆਂ ਕਤਾਰਾਂ; ਜਦੋਂ `autoRepair` false ਹੋਵੇ ਤਾਂ ਹਮੇਸ਼ਾ `0`।                                                                      |
| `backupCreated`   | ਕੀ ਮੁਰੰਮਤ ਤੋਂ ਪਹਿਲਾਂ ਬੈਕਅੱਪ ਲਿਆ ਗਿਆ ਸੀ।                                                                                                             |
| `checkedAt`       | ਰਨ ਅਤੇ ਇਸ ਦੁਆਰਾ ਲਿਖੇ ਗਏ ਕਿਸੇ ਵੀ ਮੁਰੰਮਤ ਨੋਟ ਵੱਲੋਂ ਸਾਂਝਾ ਕੀਤਾ ISO ਟਾਈਮਸਟੈਂਪ।                                                                          |
| `driver.name`     | ਜਾਂਚੇ ਗਏ ਡਾਟਾਬੇਸ ਨੂੰ ਸੇਵਾ ਦੇਣ ਵਾਲਾ SQLite ਡਰਾਈਵਰ।                                                                                                   |
| `driver.degraded` | ਜਦੋਂ ਲਿਖਤਾਂ ਨੂੰ ਡਾਟਾਬੇਸ ਫ਼ਾਈਲ ਦੁਆਰਾ ਟਿਕਾਊ ਢੰਗ ਨਾਲ ਬੈਕ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ ਤਾਂ `true` — `sql.js` WASM ਫ਼ਾਲਬੈਕ (ਪੂਰੀ-ਫ਼ਾਈਲ ਸਥਾਇਤਾ) ਜਾਂ ਇਨ-ਮੈਮੋਰੀ ਡਾਟਾਬੇਸ। |

ਇਹੀ ਪੇਲੋਡ `omniroute_db_health_check` MCP ਟੂਲ ਦੁਆਰਾ ਵਾਪਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

ਖਰਾਬੀ ਦਾ ਪਤਾ ਲਗਾਉਣ ਲਈ `PRAGMA integrity_check` ਚਲਾਓ:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ਇਹ ਪ੍ਰਿੰਟ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ: ok
```

ਜੇ ਇਹ `ok` ਤੋਂ ਇਲਾਵਾ ਕੁਝ ਵੀ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਤਾਂ **ਡਾਟਾਬੇਸ ਦੀ ਵਰਤੋਂ ਤੁਰੰਤ ਬੰਦ ਕਰੋ** ਅਤੇ ਬੈਕਅੱਪ ਤੋਂ ਰੀਸਟੋਰ ਕਰੋ।

## ਆਫ਼ਤ ਤੋਂ ਮੁੜ-ਬਹਾਲੀ

### ਸਥਿਤੀ 1: WAL ਫ਼ਾਈਲ ਗੁੰਮ ਹੋ ਗਈ

`-wal` ਫ਼ਾਈਲ ਗੁੰਮ ਹੈ, ਪਰ `-shm` ਅਤੇ ਮੁੱਖ DB ਸਹੀ-ਸਲਾਮਤ ਹਨ:

```bash
# ਅਗਲੀ ਵਾਰ ਖੋਲ੍ਹਣ 'ਤੇ ਆਪਣੇ ਆਪ ਮੁੜ-ਬਹਾਲ ਹੁੰਦਾ ਹੈ
omniroute
```

ਜੇ SQLite ਆਪਣੇ ਆਪ ਮੁੜ-ਬਹਾਲ ਨਹੀਂ ਕਰ ਸਕਦਾ:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### ਸਥਿਤੀ 2: ਮੁੱਖ DB ਫ਼ਾਈਲ ਖ਼ਰਾਬ ਹੋ ਗਈ

ਬੈਕਅੱਪ ਤੋਂ ਮੁੜ-ਬਹਾਲ ਕਰੋ:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` ਸਿਰਫ਼ ਚੱਲ ਰਹੇ ਸਰਵਰ ਤੋਂ ਇੱਕ ਪੂਰਾ `.tar.gz` ਆਰਕਾਈਵ ਡਾਊਨਲੋਡ ਕਰਦਾ ਹੈ
(`GET /api/db-backups/exportAll`, ਓਪਰੇਟਰ ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਲੋੜੀਂਦਾ ਹੈ); ਇਹ ਕਿਸੇ ਵੀ ਚੀਜ਼ ਨੂੰ ਮੁੜ-ਬਹਾਲ ਨਹੀਂ ਕਰਦਾ।

### ਸਥਿਤੀ 3: ਇਨਕ੍ਰਿਪਸ਼ਨ ਕੁੰਜੀ ਗੁੰਮ ਹੋ ਗਈ

ਕੁੰਜੀ ਤੋਂ ਬਿਨਾਂ **ਮੁੜ-ਬਹਾਲੀ ਸੰਭਵ ਨਹੀਂ ਹੈ**। ਇਨਕ੍ਰਿਪਟ ਕੀਤੇ ਫ਼ੀਲਡ ਪੜ੍ਹੇ ਨਹੀਂ ਜਾ ਸਕਦੇ। ਨਵੇਂ ਕ੍ਰੈਡੈਂਸ਼ੀਅਲਾਂ ਨਾਲ ਸਾਰੇ ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ ਹੱਥੀਂ ਦੁਬਾਰਾ ਸ਼ਾਮਲ ਕਰੋ।

> **ਜੋਖਮ ਘਟਾਉਣ ਦਾ ਉਪਾਅ**: ਇਨਕ੍ਰਿਪਸ਼ਨ ਕੁੰਜੀ ਦਾ ਹਮੇਸ਼ਾ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਬੈਕਅੱਪ ਲਓ, ਆਦਰਸ਼ ਤੌਰ 'ਤੇ ਕਿਸੇ ਪਾਸਵਰਡ ਮੈਨੇਜਰ ਜਾਂ KMS ਵਿੱਚ।

### ਸਥਿਤੀ 4: ਡਿਸਕ ਭਰ ਗਈ

SQLite `SQLITE_FULL` ਗਲਤੀਆਂ ਵਾਪਸ ਕਰੇਗਾ। ਡਿਸਕ ਦੀ ਜਗ੍ਹਾ ਖਾਲੀ ਕਰੋ, ਫਿਰ:

```bash
# ਜਗ੍ਹਾ ਖਾਲੀ ਕਰਨ ਲਈ WAL ਦਾ ਚੈੱਕਪੁਆਇੰਟ ਬਣਾਓ
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## ਆਮ ਕਾਰਵਾਈਆਂ

### ਕਿਸੇ ਟੇਬਲ ਦੀ ਜਾਂਚ ਕਰੋ

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### ਸਾਰੇ ਟੇਬਲਾਂ ਵਿੱਚ ਕਤਾਰਾਂ ਦੀ ਗਿਣਤੀ ਕਰੋ

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### ਸਾਰਾ ਡੇਟਾ ਰੀਸੈੱਟ (ਮਿਟਾਓ) ਕਰੋ

```bash
# ਪਹਿਲਾਂ OmniRoute ਨੂੰ ਰੋਕੋ
omniroute stop

# DB ਫ਼ਾਈਲ ਮਿਟਾਓ
rm ~/.omniroute/storage.sqlite*

# ਮੁੜ ਚਾਲੂ ਕਰੋ (ਖਾਲੀ DB ਦੁਬਾਰਾ ਬਣਾਇਆ ਜਾਵੇਗਾ)
omniroute
```

**ਚੋਣਵੀਂ** ਰੀਸੈੱਟ ਲਈ (ਪ੍ਰਦਾਤਿਆਂ ਨੂੰ ਰੱਖੋ, ਵਰਤੋਂ ਦਾ ਡੇਟਾ ਮਿਟਾਓ):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### ਇੱਕ ਟੇਬਲ ਐਕਸਪੋਰਟ ਕਰੋ

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## ਸਮੱਸਿਆ-ਨਿਵਾਰਣ

### "ਡੇਟਾਬੇਸ ਲੌਕ ਹੈ"

ਕਿਸੇ ਹੋਰ ਪ੍ਰਕਿਰਿਆ ਨੇ ਲਿਖਣ ਵਾਲਾ ਲੌਕ ਫੜਿਆ ਹੋਇਆ ਹੈ। ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ ਇੱਕ ਕਾਰਵਾਈ ਕਰੋ:

- ਦੂਜੀ ਪ੍ਰਕਿਰਿਆ ਦੇ ਪੂਰਾ ਹੋਣ ਦੀ ਉਡੀਕ ਕਰੋ (`lsof | grep storage.sqlite` ਨਾਲ ਜਾਂਚੋ)
- ਦੂਜੀ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਸਮਾਪਤ ਕਰੋ
- ਜੇ ਸਮੱਸਿਆ ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ, ਤਾਂ OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ

### "ਫ਼ੌਰਨ ਕੁੰਜੀ ਪਾਬੰਦੀ ਅਸਫਲ ਰਹੀ"

ਕੋਈ ਡੋਮੇਨ ਮੋਡੀਊਲ ਸੰਦਰਭਕ ਅਖੰਡਤਾ ਦੀ ਉਲੰਘਣਾ ਕਰ ਰਿਹਾ ਹੈ। ਜਾਂਚ ਕਰੋ:

- ਨਿਰਭਰ ਟੇਬਲਾਂ ਵਿੱਚ ਬਿਨਾਂ ਸੰਬੰਧ ਵਾਲੀਆਂ ਕਤਾਰਾਂ
- ਕੈਸਕੇਡਿੰਗ ਮਿਟਾਉਣ ਦੀਆਂ ਕਾਰਵਾਈਆਂ ਜੋ ਅੱਗੇ ਲਾਗੂ ਨਹੀਂ ਹੋਈਆਂ
- ਹਾਲੀਆ ਮਾਈਗ੍ਰੇਸ਼ਨ ਜਿਸ ਨੇ ਕਿਸੇ ਫ਼ੌਰਨ ਕੁੰਜੀ ਨੂੰ ਬਦਲਿਆ ਹੈ

ਉਲੰਘਣਾਵਾਂ ਲੱਭਣ ਲਈ `PRAGMA foreign_key_check;` ਚਲਾਓ।

### "ਮੈਮੋਰੀ ਖ਼ਤਮ ਹੋ ਗਈ"

SQLite ਦਾ ਮੈਮੋਰੀ-ਮੈਪਡ I/O, OS ਦੀ ਸੀਮਾ ਤੋਂ ਵੱਧ ਰਿਹਾ ਹੈ। SQLite pragma ਰਾਹੀਂ ਇਸਨੂੰ ਘਟਾਓ:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB ਦੀ ਬਜਾਏ 128MB
```

ਜਾਂ ਇਸਨੂੰ ਅਸਮਰੱਥ ਕਰੋ:

```sql
PRAGMA mmap_size = 0;
```

### "ਮਾਈਗ੍ਰੇਸ਼ਨ ਅੱਧ ਵਿਚਕਾਰ ਅਸਫਲ ਹੋ ਗਈ"

ਮਾਈਗ੍ਰੇਸ਼ਨ ਇੱਕ ਟ੍ਰਾਂਜ਼ੈਕਸ਼ਨ ਵਿੱਚ ਚੱਲੀ ਸੀ, ਇਸ ਲਈ ਇਸਨੂੰ ਰੋਲ ਬੈਕ ਹੋ ਜਾਣਾ ਚਾਹੀਦਾ ਸੀ। ਜੇ ਅਜਿਹਾ ਨਹੀਂ ਹੋਇਆ:

1. **OmniRoute ਨੂੰ ਰੋਕੋ** (ਹੋਰ ਕੋਸ਼ਿਸ਼ਾਂ ਨੂੰ ਰੋਕਣ ਲਈ)
2. `sqlite3` ਨਾਲ **DB ਦੀ ਸਥਿਤੀ ਜਾਂਚੋ**
3. ਅਧੂਰੀ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ **ਹੱਥੀਂ ਠੀਕ ਕਰੋ**
4. OmniRoute ਨੂੰ **ਦੁਬਾਰਾ ਚਲਾਓ** (ਮਾਈਗ੍ਰੇਸ਼ਨ ਦੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾਵੇਗੀ)

ਇਸਨੂੰ ਰੋਕਣ ਲਈ, ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਦੀ ਜਾਂਚ ਹਮੇਸ਼ਾ ਪਹਿਲਾਂ ਇੱਕ ਕਾਪੀ 'ਤੇ ਕਰੋ।
