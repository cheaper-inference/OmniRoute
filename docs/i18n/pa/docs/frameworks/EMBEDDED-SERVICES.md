- OmniRoute ਉਹਨਾਂ ਨੂੰ ਬਾਲ ਪ੍ਰਕਿਰਿਆਵਾਂ ਵਜੋਂ ਪੈਦਾ ਕਰਦਾ ਹੈ ਅਤੇ ਨਿਗਰਾਨੀ ਕਰਦਾ ਹੈ
- OmniRoute ਬੱਚੇ ਦੇ ਵਾਤਾਵਰਣ ਵਿੱਚ ਇੱਕ ਅਕਾਦਮੀ API ਕੁੰਜੀ ਨੂੰ ਇੰਜੈਕਟ ਕਰਦਾ ਹੈ ਅਤੇ ਇਸਨੂੰ ਡਾਊਨਟਾਈਮ ਤੋਂ ਬਿਨਾਂ ਘੁੰਮਾਉਂਦਾ ਹੈ (ਜਿੱਥੇ ਲਾਗੂ ਹੁੰਦਾ ਹੈ)
- ਸਾਰੇ ਪ੍ਰਬੰਧਨ ਰਸਤੇ (`/api/services/*`) ਹਨ**LOCAL_ONLY** — ਸਿਰਫ਼ ਲੂਪਬੈਕ ਤੋਂ ਪਹੁੰਚਯੋਗ (ਸਖਤ ਨਿਯਮ #17)

### ਪ੍ਰਬੰਧਿਤ ਪ੍ਰੌਕਸੀ ਕੋਰ

ਕਸਟਮ ਪ੍ਰੌਕਸੀ ਹੋਸਟ ਖੇਤਰ ਇੱਕ V2Ray ਸਰੋਤ ਲਿੰਕ ਨੂੰ ਵੀ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ। ਚੁਣੋ** sing-box** ਜਾਂ** ਐਕਸਰੇ** ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ, ਫਿਰ ਸੇਵ 'ਤੇ ਕਲਿੱਕ ਕਰੋ। ਟਾਈਪਿੰਗ ਕਦੇ ਵੀ ਡਾਊਨਲੋਡ ਜਾਂ ਕੋਰ ਸ਼ੁਰੂ ਨਹੀਂ ਹੁੰਦੀ ਹੈ। ਸੇਵ ਅਧਿਕਾਰਤ ਰੀਲੀਜ਼ ਆਰਕਾਈਵ ਦੀ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ, ਨੇਟਿਵ ਕੌਂਫਿਗਰੇਸ਼ਨ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਇੱਕ ਵੱਖਰਾ ਲੋਕਲਹੋਸਟ SOCKS ਲਿਸਨਰ ਸ਼ੁਰੂ ਕਰਦਾ ਹੈ, ਅਤੇ ਕੇਵਲ ਤਦ ਹੀ ਪ੍ਰੌਕਸੀ ਰਜਿਸਟਰੀ ਅਸਾਈਨਮੈਂਟ ਲਿਖਦਾ ਹੈ। ਅਸਫਲ ਸਰਗਰਮੀ ਪਿਛਲੀ ਵਿਵਸਥਿਤ ਸੰਰਚਨਾ ਅਤੇ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਬਹਾਲ ਕਰਦੀ ਹੈ। `STORAGE_ENCRYPTION_KEY` ਦੀ ਲੋੜ ਹੈ; ਸਰੋਤ ਲਿੰਕ ਐਨਕ੍ਰਿਪਟ ਕੀਤੇ ਗਏ ਹਨ।

ਪ੍ਰਬੰਧਿਤ ਫਾਈਲਾਂ `DATA_DIR/services/managed-proxy/` ਦੇ ਅਧੀਨ ਰਹਿੰਦੀਆਂ ਹਨ, TPROXY ਤੋਂ ਵੱਖਰੀਆਂ। ਪ੍ਰਤੀ ਚੁਣੇ ਹੋਏ ਕੋਰ, 100 ਸਰੋਤਿਆਂ ਤੱਕ ਇੱਕ ਮਲਕੀਅਤ ਵਾਲੀ ਪ੍ਰਕਿਰਿਆ ਹੈ। ਕੋਈ ਆਟੋਸਟਾਰਟ ਜਾਂ ਗਲੋਬਲ ਰਾਊਟਿੰਗ ਡਿਫੌਲਟ ਨਹੀਂ ਬਦਲਿਆ ਗਿਆ ਹੈ। ਸਫਲ ਸੇਵ ਸਿਰਫ ਇਸ ਪ੍ਰਬੰਧਿਤ ਕੋਰ ਲਈ ਕਿਰਿਆਸ਼ੀਲਤਾ ਨੂੰ ਯਾਦ ਰੱਖਦਾ ਹੈ; ਐਪਲੀਕੇਸ਼ਨ ਸਟਾਰਟਅਪ ਪਹਿਲਾਂ ਤੋਂ ਪ੍ਰਮਾਣਿਤ ਬਾਈਨਰੀ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹੋਏ ਸੁਰੱਖਿਅਤ ਕੀਤੇ ਕੋਰਾਂ ਨੂੰ ਰੀਸਟੋਰ ਕਰਦਾ ਹੈ, ਕਦੇ ਵੀ ਬੂਟ-ਟਾਈਮ ਡਾਉਨਲੋਡ ਨਹੀਂ। ਸਪਸ਼ਟ ਸਟਾਪ ਉਸ ਸਰਗਰਮੀ ਫਲੈਗ ਨੂੰ ਸਾਫ਼ ਕਰਦਾ ਹੈ। ਇੱਕ ਗੁੰਮ ਜਾਂ ਖਰਾਬ ਬਾਈਨਰੀ ਲਈ ਇੱਕ ਸਰੋਤ ਨੂੰ ਮੁੜ-ਸੁਰੱਖਿਅਤ ਕਰਨ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ। ਰਜਿਸਟਰੀ ਨੂੰ ਮਿਟਾਉਣਾ ਸਰੋਤ ਅਤੇ ਸਰੋਤਿਆਂ ਨੂੰ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਹਟਾਉਂਦਾ ਹੈ; ਪ੍ਰਬੰਧਿਤ ਕਤਾਰਾਂ ਲਈ ਸਧਾਰਣ ਅੰਤਮ ਬਿੰਦੂ ਸੰਪਾਦਨਾਂ ਨੂੰ ਅਸਵੀਕਾਰ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ ਤਾਂ ਜੋ ਸੁਰੱਖਿਅਤ ਕੀਤਾ ਸਰੋਤ ਚੁੱਪਚਾਪ ਇਸਦੇ ਰੂਟ ਕੀਤੇ ਸਰੋਤਿਆਂ ਤੋਂ ਦੂਰ ਨਹੀਂ ਜਾ ਸਕਦਾ।

ਅਣਜਾਣ ਤਾਰ ਵਿਕਲਪ, ਅਸੁਰੱਖਿਅਤ TLS ਫਲੈਗ, ਬਾਹਰੀ ਪਲੱਗਇਨ, ਸਥਾਨਕ ਫਾਈਲ-ਪਾਥ ਵਿਕਲਪ ਅਤੇ ਅਸਮਰਥਿਤ ਸੰਜੋਗਾਂ ਨੂੰ ਚੁੱਪਚਾਪ ਰੱਦ ਕਰਨ ਦੀ ਬਜਾਏ ਰੱਦ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਮੂਲ ਵਸਤੂਆਂ ਆਊਟਬਾਉਂਡ ਪਰਿਭਾਸ਼ਾਵਾਂ ਹਨ, ਨਾ ਕਿ ਪੂਰੀ-ਕੋਰ ਸੰਰਚਨਾਵਾਂ; control/direct/bypass ਆਊਟਬਾਉਂਡ ਸਵੀਕਾਰ ਨਹੀਂ ਕੀਤੇ ਜਾਂਦੇ ਹਨ। sing-box 1.14 'ਤੇ WireGuard ਅੰਤਮ ਬਿੰਦੂਆਂ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਇਸਲਈ ਇਸਨੂੰ ਮੂਲ ਆਊਟਬਾਉਂਡ ਵਜੋਂ ਸਵੀਕਾਰ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਇਹ ਇੱਕ ਆਲ-ਫਾਰਮੈਟ ਕਨਵਰਟਰ ਨਹੀਂ ਹੈ; SSR, ਲੀਗੇਸੀ whole-base64 ਸ਼ੈਡੋਸੌਕਸ ਲਿੰਕਸ, ਆਰਬਿਟਰਰੀ ਕਲੈਸ਼ ਆਬਜੈਕਟ ਅਤੇ ਟੇਬਲ ਤੋਂ ਗੈਰਹਾਜ਼ਰ ਟ੍ਰਾਂਸਪੋਰਟ ਵੇਰੀਐਂਟਸ ਨੂੰ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਸਮਰਥਿਤ ਸਰੋਤ ਫਾਰਮੈਟ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

`/api/services/managed-proxy` ਪ੍ਰਮਾਣਿਤ ਅਤੇ ਲੂਪਬੈਕ-ਸਿਰਫ਼ ਹੈ: GET ਰੀਡੈਕਟ ਕੀਤੇ ਮੈਟਾਡੇਟਾ ਨੂੰ ਸੂਚੀਬੱਧ ਕਰਦਾ ਹੈ, POST `{core,name,sourceLink,id?,assignment?}` ਸੁਰੱਖਿਅਤ ਕਰਦਾ ਹੈ, PATCH `{core,action:"start"|"stop"}` ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ। ਹੋਸਟ ਦੀ ਭਰੋਸੇਯੋਗ ਪੀਅਰ-ਸਟੈਂਪ ਪਾਈਪਲਾਈਨ ਮੌਜੂਦ ਹੋਣੀ ਚਾਹੀਦੀ ਹੈ। ਨੇਟਿਵ ਕੋਰ ਡਾਇਗਨੌਸਟਿਕਸ ਨੂੰ ਦਬਾਇਆ ਜਾਂਦਾ ਹੈ ਕਿਉਂਕਿ ਉਹਨਾਂ ਵਿੱਚ ਪ੍ਰਮਾਣ ਪੱਤਰ ਸ਼ਾਮਲ ਹੋ ਸਕਦੇ ਹਨ; ਲਾਈਫਸਾਈਕਲ ਇਵੈਂਟਸ ਮੌਜੂਦਾ ਸਟ੍ਰਕਚਰਡ ਐਪਲੀਕੇਸ਼ਨ ਫਾਈਲ ਲੌਗਰ ਦੀ ਵਰਤੋਂ ਬਿਨਾਂ ਸਰੋਤ ਲਿੰਕ ਜਾਂ ਅੱਪਸਟ੍ਰੀਮ ਪੇਲੋਡ ਦੇ ਕਰਦੇ ਹਨ। ਸਹਾਇਤਾ ਲਈ ਸਿਰਫ ਰੋਗਾਣੂ-ਮੁਕਤ ਐਪਲੀਕੇਸ਼ਨ ਲੌਗ ਨੱਥੀ ਕਰੋ। ਅਧਿਕਾਰਤ ਸੰਸਕਰਣਾਂ ਨੂੰ ਰਿਲੀਜ਼-ਸੰਪੱਤੀ SHA-256 ਮੈਨੀਫੈਸਟ ਦੇ ਨਾਲ ਸਿੰਗ-ਬਾਕਸ 1.14.3 ਅਤੇ Xray 26.3.27 ਵਿੱਚ ਪਿੰਨ ਕੀਤਾ ਗਿਆ ਹੈ; ਭਵਿੱਖ ਦੇ ਅੱਪਡੇਟਾਂ ਲਈ ਵਰਜਨ ਅਤੇ ਸਾਰੇ ਪ੍ਰਮਾਣਿਤ ਡਾਇਜੈਸਟਾਂ ਨੂੰ ਇਕੱਠੇ ਬਦਲਣ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

```
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
              ਹੈਲਥ ਪ੍ਰੋਬ ਸਫਲ   │         ਕ੍ਰੈਸ਼ / SIGTERM       │
                               ┌────▼─────┐  (5s ਵਿੱਚ ਐਗਜ਼ਿਟ)   │
                               │ running  │──── ਕ੍ਰੈਸ਼ ─────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

ਸਟੇਟਾਂ `version_manager` DB ਟੇਬਲ (`status` ਕਾਲਮ) ਵਿੱਚ ਸਟੋਰ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ ਅਤੇ
`ServiceSupervisor` ਦੀ ਇਨ-ਮੈਮੋਰੀ ਸਟੇਟ ਵਿੱਚ ਪ੍ਰਤੀਬਿੰਬਿਤ ਹੁੰਦੀਆਂ ਹਨ। ਚੱਲ ਰਹੀ ਪ੍ਰਕਿਰਿਆ ਲਈ
ਇਨ-ਮੈਮੋਰੀ ਸਟੇਟ ਅਧਿਕਾਰਤ ਹੁੰਦੀ ਹੈ; ਬੂਟ ਸਮੇਂ DB ਸਟੇਟ ਟਿਕਾਊ ਫਾਲਬੈਕ ਹੁੰਦੀ ਹੈ।

### ਸਟੇਟ ਤਬਦੀਲੀਆਂ

| ਇਸ ਤੋਂ          | ਇਵੈਂਟ                                           | ਇਸ ਵਿੱਚ                |
| --------------- | ----------------------------------------------- | ---------------------- |
| `not_installed` | `install()` ਸਫਲ ਹੁੰਦਾ ਹੈ                        | `stopped`              |
| `stopped`       | `start()` ਕਾਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ                     | `starting`             |
| `starting`      | ਹੈਲਥ ਪ੍ਰੋਬ 200 ਵਾਪਸ ਕਰਦਾ ਹੈ                     | `running`              |
| `starting`      | ਸਿਹਤਮੰਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਪ੍ਰਕਿਰਿਆ ਬੰਦ ਹੋ ਜਾਂਦੀ ਹੈ | `error`                |
| `running`       | `stop()` ਕਾਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ                      | `stopping` → `stopped` |
| `running`       | ਪ੍ਰਕਿਰਿਆ ਅਚਾਨਕ ਬੰਦ ਹੁੰਦੀ ਹੈ (< 5 s)             | `error` (ਤੇਜ਼ ਕ੍ਰੈਸ਼)  |
| `running`       | ਪ੍ਰਕਿਰਿਆ ਅਚਾਨਕ ਬੰਦ ਹੁੰਦੀ ਹੈ (> 5 s)             | `error`                |
| `error`         | `start()` ਕਾਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ                     | `starting`             |
| ਕੋਈ ਵੀ          | `stopping` ਦੌਰਾਨ `stop()`                       | ਕੋਈ ਕਾਰਵਾਈ ਨਹੀਂ        |

### ਓਪਰੇਸ਼ਨ ਲਾਕ

`ServiceSupervisor` ਇੱਕ async ਓਪਰੇਸ਼ਨ ਲਾਕ (`withLock()`) ਰਾਹੀਂ ਲਾਈਫਸਾਈਕਲ ਓਪਰੇਸ਼ਨਾਂ ਨੂੰ
ਲੜੀਵਾਰ ਕਰਦਾ ਹੈ। ਇੱਕੋ ਸੁਪਰਵਾਈਜ਼ਰ ਉੱਤੇ ਇਕੱਠੀਆਂ `start()` ਕਾਲਾਂ ਦੇ ਨਤੀਜੇ ਵਜੋਂ ਸਿਰਫ਼
ਇੱਕ spawn ਹੁੰਦਾ ਹੈ; ਦੂਜਾ ਕਾਲਰ ਉਡੀਕ ਕਰਦਾ ਹੈ ਅਤੇ ਮੌਜੂਦਾ ਸਟੇਟਸ ਵਾਪਸ ਕਰਦਾ ਹੈ। ਇਹ
ਰੇਸ ਕੰਡੀਸ਼ਨਾਂ ਨੂੰ ਰੋਕਦਾ ਹੈ, ਜਿਵੇਂ ਕਿ ਜਦੋਂ ਆਟੋ-ਸਟਾਰਟ ਅਤੇ UI ਬਟਨ ਇੱਕੋ ਸਮੇਂ ਟ੍ਰਿਗਰ ਹੋਣ।

## 4. API ਹਵਾਲਾ

`/api/services/` ਅਧੀਨ ਸਾਰੇ ਰਸਤੇ ਹਨ**LOCAL_ONLY** (ਸਿਰਫ਼ ਲੂਪਬੈਕ, ਸਖ਼ਤ ਨਿਯਮ #17)। ਗੈਰ-ਲੂਪਬੈਕ ਬੇਨਤੀਆਂ ਪ੍ਰਮਾਣਿਤ ਟੋਕਨ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ `403 LOCAL_ONLY` ਪ੍ਰਾਪਤ ਕਰਦੀਆਂ ਹਨ।

### 4.1 9 ਰੂਟਰ ਐਂਡਪੁਆਇੰਟ (11 ਰੂਟ)

#### `POST /api/services/9router/install`

npm ਤੋਂ 9 ਰਾਊਟਰ ਇੰਸਟਾਲ ਕਰੋ। ਆਪਣੇ ਖੁਦ ਦੇ `package.json` ਅਤੇ `node_modules/` ਨਾਲ `DATA_DIR/services/9router/` ਬਣਾਉਂਦਾ ਹੈ। OmniRoute ਦੇ ਆਪਣੇ ਡੈਪਸ ਨਾਲ ਟਕਰਾਅ ਨਹੀਂ ਕਰਦਾ।

**ਸਰੀਰ ਨੂੰ ਬੇਨਤੀ ਕਰੋ** (ਸਾਰੇ ਵਿਕਲਪਿਕ):

```json
{ "version": "latest" }
```

| ਖੇਤਰ      | ਟਾਈਪ ਕਰੋ | ਡਿਫਾਲਟ     | ਵਰਣਨ                                 |
| --------- | -------- | ---------- | ------------------------------------ |
| `version` | `string` | `"latest"` | ਇੰਸਟਾਲ ਕਰਨ ਲਈ npm ਵਰਜਨ ਟੈਗ ਜਾਂ ਸੇਮਵਰ |

**ਜਵਾਬ:**

| ਸਥਿਤੀ | ਵਰਣਨ                                                   |
| ----- | ------------------------------------------------------ |
| `200` | `{ ok: true, installedVersion: "x.y.z", path: "..." }` |
| `400` | ਅਵੈਧ ਬੇਨਤੀ ਬਾਡੀ (Zod ਪ੍ਰਮਾਣਿਕਤਾ ਅਸਫਲਤਾ)                |
| `409` | ਪਹਿਲਾਂ ਹੀ ਸਥਾਪਿਤ ਕੀਤਾ ਜਾ ਰਿਹਾ ਹੈ (ਲਾਕ ਹੋਲਡ)            |
| `500` | npm ਇੰਸਟਾਲ ਅਸਫਲ — ਦੋਸਤਾਨਾ ਗਲਤੀ ਲਈ `message` ਵੇਖੋ       |

**ਨੋਟ:** `execFile('npm', [...])` — ਕੋਈ ਸ਼ੈੱਲ ਨਹੀਂ, ਕੋਈ ਇੰਟਰਪੋਲੇਸ਼ਨ ਨਹੀਂ (ਸਖਤ ਨਿਯਮ #13) ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। EACCES ਗਲਤੀਆਂ ਦੋਸਤਾਨਾ ਸੰਦੇਸ਼ਾਂ ਵਜੋਂ ਸਾਹਮਣੇ ਆਈਆਂ ਹਨ।

### 4.2 CLIProxyAPI ਅੰਤਮ ਬਿੰਦੂ (10 ਰਸਤੇ)

CLIProxyAPI ਕੋਲ 9Router ਮਾਇਨਸ `rotate-key`, ਪਲੱਸ `accounts`, `provider-expose` ਅਤੇ `auto-restart-adopted` ਵਰਗੀ ਅੰਤਮ ਬਿੰਦੂ ਦੀ ਸ਼ਕਲ ਹੈ। ਇਹ ਹੁਣ ਸਪੌਨ (`needsApiKey: true` API ਮਾਡਲ ਸਿੰਕ ਲਈ ਵਰਤਿਆ ਜਾਂਦਾ `bootstrap.ts`); `status` ਵਿੱਚ ਘੱਟ ਖੇਤਰ ਸ਼ਾਮਲ ਹਨ।

| ਵਿਧੀ   | ਮਾਰਗ                                | ਵਰਣਨ                                      |
| ------ | ----------------------------------- | ----------------------------------------- |
| `POST` | `/api/services/cliproxy/install`    | npm ਤੋਂ CLIProxyAPI ਇੰਸਟਾਲ ਕਰੋ            |
| `POST` | `/api/services/cliproxy/start`      | CLIProxyAPI ਸ਼ੁਰੂ ਕਰੋ                     |
| `POST` | `/api/services/cliproxy/stop`       | CLIProxyAPI ਬੰਦ ਕਰੋ                       |
| `POST` | `/api/services/cliproxy/restart`    | CLIProxyAPI ਰੀਸਟਾਰਟ ਕਰੋ                   |
| `POST` | `/api/services/cliproxy/update`     | ਨਵੇਂ ਸੰਸਕਰਣ ਲਈ ਅੱਪਡੇਟ ਕਰੋ                 |

**ਪੇਅਰਿੰਗ:** open-wa ਗੈਰ-ਅਧਿਕਾਰਤ ਹੈ ਅਤੇ WhatsApp — ਨਾਲ ਗੈਰ-ਸੰਬੰਧਿਤ ਹੈ, ਕਨੈਕਟ ਕੀਤਾ ਨੰਬਰ WhatsApp ਦੇ ਆਪਣੇ ਆਟੋਮੇਸ਼ਨ ਖੋਜ ਤੋਂ ਪਾਬੰਦੀ ਦਾ ਜੋਖਮ ਰੱਖਦਾ ਹੈ। ਪਹਿਲੀ ਸ਼ੁਰੂਆਤ 'ਤੇ, ਪੇਅਰਿੰਗ QR ਕੋਡ ਨੂੰ stdout 'ਤੇ ਪ੍ਰਿੰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਮੌਜੂਦਾ ਲੌਗਜ਼ panel/SSE ਸਟ੍ਰੀਮ — ਰਾਹੀਂ ਸਾਹਮਣੇ ਆਉਂਦਾ ਹੈ, ਇਸ ਏਕੀਕਰਣ ਵਿੱਚ ਅਜੇ ਤੱਕ ਕੋਈ ਸਮਰਪਿਤ QR- ਚਿੱਤਰ ਅੰਤਮ ਬਿੰਦੂ ਨਹੀਂ ਹੈ।

| `POST` | `/api/services/singbox/install`              | + ਡਾਊਨਲੋਡ ਕਰੋ ਪਿੰਨ ਕੀਤੇ ਸਿੰਗ-ਬਾਕਸ ਰੀਲੀਜ਼ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ           |

| `POST` | `/api/services/singbox/stop`                 | ਗਾਇਨ-ਬਾਕਸ ਬੰਦ ਕਰੋ                                                |
| `POST` | `/api/services/singbox/restart`              | ਸਿੰਗ-ਬਾਕਸ ਨੂੰ ਮੁੜ-ਚਾਲੂ ਕਰੋ                                       |
| `POST` | `/api/services/singbox/update`               | Re-verify/reinstall ਪਿੰਨਡ ਰੀਲੀਜ਼                                 |
| `GET`  | `/api/services/singbox/status`               | ਲਾਈਵ + DB ਸਥਿਤੀ                                                  |
| `POST` | `/api/services/singbox/auto-start`           | ਆਟੋ-ਸਟਾਰਟ ਨੂੰ ਟੌਗਲ ਕਰੋ                                           |
| `POST` | `/api/services/singbox/auto-restart-adopted` | ਅਪਣਾਈ ਗਈ (ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ) ਪ੍ਰਕਿਰਿਆ ਲਈ ਆਟੋ-ਰੀਸਟਾਰਟ ਨੂੰ ਟੌਗਲ ਕਰੋ |
| `GET`  | `/api/services/singbox/logs`                 | SSE ਲੌਗ ਟੇਲ (ਸਾਂਝੇ `[name]/logs` ਡਾਇਨਾਮਿਕ ਰੂਟ ਰਾਹੀਂ)             |

**TPROXY ਵਾਇਰਿੰਗ:** `ensureSingboxTproxy()` (`src/mitm/tproxy/setup.ts`) `config.json` ਲਿਖਦਾ ਹੈ ਅਤੇ `applyTproxy()` TPROXY ਫਾਇਰਵਾਲ ਨਿਯਮਾਂ ਨੂੰ ਸਥਾਪਤ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਸੁਪਰਵਾਈਜ਼ਰ ਨੂੰ ਸ਼ੁਰੂ ਕਰਦਾ ਹੈ। ਜੇਕਰ ਸੁਪਰਵਾਈਜ਼ਰ ਗੁੰਮ ਹੈ ਜਾਂ `running` ਤੱਕ ਪਹੁੰਚਣ ਵਿੱਚ ਅਸਫਲ ਰਹਿੰਦਾ ਹੈ, ਤਾਂ ਇਹ ਹੁਣ ਗਲਤੀ ਦੇ ਪੱਧਰ 'ਤੇ ਲੌਗ ਕਰਦਾ ਹੈ (ਅਸਫ਼ਲਤਾ ਨੂੰ ਚੁੱਪਚਾਪ ਨਿਗਲਣ ਦੀ ਬਜਾਏ) ਤਾਂ ਇੱਕ ਓਪਰੇਟਰ ਦੱਸ ਸਕਦਾ ਹੈ ਕਿ TPROXY ਨਿਯਮਾਂ ਨੂੰ ਉਹਨਾਂ ਦੇ ਪਿੱਛੇ ਕੰਮ ਕਰਨ ਵਾਲੇ ਸੁਣਨ ਵਾਲੇ ਤੋਂ ਬਿਨਾਂ ਲਾਗੂ ਕੀਤਾ ਗਿਆ ਸੀ।

### 4.9 ਰਿਵਰਸ ਪ੍ਰੌਕਸੀ (9 ਰਾਊਟਰ ਡੈਸ਼ਬੋਰਡ ਏਮਬੇਡ)

ਡੈਸ਼ਬੋਰਡ ਇੱਕ ਅੰਦਰੂਨੀ ਰਿਵਰਸ ਪ੍ਰੌਕਸੀ ਦੁਆਰਾ ਇੱਕ iframe ਦੇ ਅੰਦਰ 9Router ਵੈੱਬ UI ਏਮਬੇਡ ਕਰਦਾ ਹੈ:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

ਇਹ ਪ੍ਰੌਕਸੀ:

- ਬੇਨਤੀ ਨੂੰ `http://127.0.0.1:{port}/{path}` ਨੂੰ ਅੱਗੇ ਭੇਜਦਾ ਹੈ (ਸਿਰਫ਼ ਲੂਪਬੈਕ)
- ਸਟ੍ਰਿਪ ਇਨਕਮਿੰਗ `cookie` ਅਤੇ `authorization` ਹੈਡਰ ( OmniRoute ਸੈਸ਼ਨ ਦਾ ਕੋਈ ਲੀਕ ਨਹੀਂ)
- 9Router ਪ੍ਰਮਾਣਿਕਤਾ ਲਈ `Authorization: Bearer {apiKey}` ਇੰਜੈਕਟ ਕਰਦਾ ਹੈ
- ਜਵਾਬ ਤੋਂ `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` ਦੀਆਂ ਪੱਟੀਆਂ
- `<base href>` ਨੂੰ ਇੰਜੈਕਟ ਕਰਨ ਅਤੇ ਪੂਰਨ ਮਾਰਗਾਂ ਨੂੰ ਆਮ ਬਣਾਉਣ ਲਈ HTML ਜਵਾਬਾਂ ਨੂੰ ਦੁਬਾਰਾ ਲਿਖਦਾ ਹੈ (`/foo` → `/dashboard/.../embed/foo`)

ਏਮਬੈਡਡ ਡੈਸ਼ਬੋਰਡ ਲਈ WebSocket ਅੱਪਗਰੇਡਾਂ ਨੂੰ ਇੱਕ ਸਮਰਪਿਤ ਪੋਰਟ ਉੱਤੇ ਇੱਕ ਸਾਥੀ ਸਰਵਰ ਦੁਆਰਾ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ (ਵੇਖੋ `src/lib/services/embedWsProxy.ts`)।

**ਸੁਰੱਖਿਆ:** ਏਮਬੇਡ ਪ੍ਰੌਕਸੀ ਰੂਟਾਂ ਨੂੰ `LOCAL_ONLY_API_PREFIXES` ਦੇ ਅਧੀਨ ਸ਼੍ਰੇਣੀਬੱਧ ਕੀਤਾ ਗਿਆ ਹੈ ਅਤੇ ਸਿਰਫ ਲੂਪਬੈਕ ਤੋਂ ਪਹੁੰਚਿਆ ਜਾ ਸਕਦਾ ਹੈ। ਇੱਕ ਹਮਲਾਵਰ ਜੋ ਇੱਕ Cloudflare/Ngrok ਸੁਰੰਗ ਦੁਆਰਾ ਇੱਕ JWT ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ, ਏਮਬੈਡਡ ਸੇਵਾਵਾਂ ਵਿੱਚ ਪ੍ਰੌਕਸੀ ਨਹੀਂ ਕਰ ਸਕਦਾ ਹੈ।

## 5. ਸੁਰੱਖਿਆ

### LOCAL_ONLY ਲਾਗੂਕਰਨ (ਸਖ਼ਤ ਨਿਯਮ #17)

`/api/services/` ਅਤੇ `/dashboard/providers/services/*/embed/` ਦੇ ਅਧੀਨ ਸਾਰੇ ਰੂਟਾਂ ਨੂੰ
`src/server/authz/routeGuard.ts` ਵਿੱਚ LOCAL_ONLY ਵਜੋਂ ਵਰਗੀਕ੍ਰਿਤ ਕੀਤਾ ਗਿਆ ਹੈ। ਲੂਪਬੈਕ ਜਾਂਚ
ਕਿਸੇ ਵੀ ਪ੍ਰਮਾਣੀਕਰਨ ਸ਼ਾਖਾ ਤੋਂ ਪਹਿਲਾਂ ਬਿਨਾਂ ਕਿਸੇ ਸ਼ਰਤ ਦੇ ਚੱਲਦੀ ਹੈ:

```
ਬੇਨਤੀ ਆਉਂਦੀ ਹੈ
  → isLocalOnlyPath(path)?
      → ਗੈਰ-ਲੂਪਬੈਕ → 403 LOCAL_ONLY (ਹਮੇਸ਼ਾ, ਪ੍ਰਮਾਣੀਕਰਨ ਜਾਂਚ ਤੋਂ ਪਹਿਲਾਂ)
      → ਲੂਪਬੈਕ     → ਆਮ ਪ੍ਰਮਾਣੀਕਰਨ ਵੱਲ ਅੱਗੇ ਵਧੋ
```

ਇਹ ਲੀਕ ਹੋਏ JWT (ਉਦਾਹਰਨ ਲਈ, ਕਿਸੇ ਟਨਲ ਰਾਹੀਂ) ਨੂੰ `npm install` ਜਾਂ
ਪ੍ਰੋਸੈੱਸ ਸਪੌਨਿੰਗ ਸ਼ੁਰੂ ਕਰਨ ਤੋਂ ਰੋਕਦਾ ਹੈ। ਪੂਰੇ ਟੀਅਰ ਮੈਟ੍ਰਿਕਸ ਲਈ
`docs/security/ROUTE_GUARD_TIERS.md` ਵੇਖੋ।

### API ਕੁੰਜੀ ਇੰਜੈਕਸ਼ਨ

9Router ਅਤੇ Mux ਨੂੰ ਆਪਣੇ HTTP ਐਂਡਪੌਇੰਟਾਂ ਲਈ ਇੱਕ API ਕੁੰਜੀ/ਬੇਅਰਰ ਟੋਕਨ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।
OmniRoute:

1. `crypto.randomBytes(32).toString("base64url")` ਰਾਹੀਂ ਸੇਵਾ-ਵਿਸ਼ੇਸ਼
   ਪ੍ਰੀਫਿਕਸ (`nr_` 9Router ਲਈ, `mx_` Mux ਲਈ) ਵਾਲੀ ਕੁੰਜੀ ਬਣਾਉਂਦਾ ਹੈ।
2. AES-256-GCM ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਇਸਨੂੰ ਸਟੋਰ ਕੀਤੀ ਹਾਲਤ ਵਿੱਚ ਇਨਕ੍ਰਿਪਟ ਕਰਦਾ ਹੈ (ਉਹੀ ਸਾਈਫਰ ਜੋ ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣ-ਪੱਤਰਾਂ ਲਈ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ)।
3. ਸਪੌਨ ਸਮੇਂ ਇਸਨੂੰ ਡੀਕ੍ਰਿਪਟ ਕਰਕੇ ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ ਵਜੋਂ ਇੰਜੈਕਟ ਕਰਦਾ ਹੈ —
   9Router ਲਈ `NINEROUTER_API_KEY`, Mux ਲਈ `MUX_SERVER_AUTH_TOKEN` (ਕਦੇ ਵੀ CLI
   ਫਲੈਗ ਨਹੀਂ, ਇਸ ਲਈ ਟੋਕਨ ਕਦੇ ਵੀ `ps`/ਪ੍ਰੋਸੈੱਸ ਸੂਚੀਆਂ ਵਿੱਚ ਦਿਖਾਈ ਨਹੀਂ ਦਿੰਦਾ)।
4. ਕਿਸੇ ਵੀ HTTP ਜਵਾਬ ਵਿੱਚ ਪਲੇਨਟੈਕਸਟ ਕੁੰਜੀ ਕਦੇ ਵਾਪਸ ਨਹੀਂ ਕਰਦਾ।

CLIProxyAPI ਨੂੰ ਸਪੌਨ ਸਮੇਂ ਇੰਜੈਕਟ ਕੀਤੀ ਇੱਕ ਸਮਰਪਿਤ ਡਾਟਾ-ਪਲੇਨ ਕੁੰਜੀ ਮਿਲਦੀ ਹੈ
(`needsApiKey: true` — ਅਡੈਪਟਰ ਦੇ ਵਿਰੁੱਧ ਮਾਡਲ ਸਿੰਕ ਲਈ ਵਰਤੀ ਜਾਂਦੀ ਹੈ)।

### SSRF ਸੁਰੱਖਿਆ

ਰਿਵਰਸ HTTP ਪ੍ਰੌਕਸੀ (`/dashboard/.../embed/[...path]`) ਨੂੰ ਸਿਰਫ਼
`http://127.0.0.1:{port}` ਵੱਲ ਫਾਰਵਰਡ ਕਰਨ ਲਈ ਹਾਰਡਕੋਡ ਕੀਤਾ ਗਿਆ ਹੈ। ਇਹ ਕਦੇ ਵੀ ਗੈਰ-ਲੂਪਬੈਕ
ਮੰਜ਼ਿਲਾਂ ਵੱਲ ਰੀਡਾਇਰੈਕਟਾਂ ਦੀ ਪਾਲਣਾ ਨਹੀਂ ਕਰਦਾ। `ssrf-req-filter` ਲਾਇਬ੍ਰੇਰੀ ਦੀ ਵਰਤੋਂ ਕਿਸੇ ਵੀ ਅਜਿਹੇ ਅੱਪਸਟ੍ਰੀਮ URL ਨੂੰ ਰੱਦ ਕਰਨ ਲਈ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਜੋ
ਲੂਪਬੈਕ ਰੇਂਜ ਤੋਂ ਬਾਹਰ ਰਿਜ਼ੌਲਵ ਹੁੰਦਾ ਹੈ।

### ਸ਼ੈੱਲ ਸੁਰੱਖਿਆ (ਸਖ਼ਤ ਨਿਯਮ #13)

`npm install` ਨੂੰ `execFile('npm', ['install', pkg, '--prefix', dir])` ਰਾਹੀਂ ਚਲਾਇਆ ਜਾਂਦਾ ਹੈ —
ਕੋਈ ਟੈਂਪਲੇਟ ਲਿਟਰਲ ਨਹੀਂ, ਕੋਈ ਸ਼ੈੱਲ ਨਹੀਂ ਅਤੇ ਕਮਾਂਡ
ਸਤਰ ਵਿੱਚ ਬਾਹਰੀ ਪਾਥਾਂ ਦੀ ਕੋਈ ਇੰਟਰਪੋਲੇਸ਼ਨ ਨਹੀਂ। ਰਨਟਾਈਮ ਮੁੱਲ (ਪੋਰਟ, API ਕੁੰਜੀਆਂ) ਚਾਈਲਡ ਦੇ `env` ਆਬਜੈਕਟ ਰਾਹੀਂ ਪਾਸ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।

### ਗਲਤੀ ਸੈਨਿਟਾਈਜ਼ੇਸ਼ਨ (ਸਖ਼ਤ ਨਿਯਮ #12)

`/api/services/*` ਤੋਂ ਆਉਣ ਵਾਲੇ ਸਾਰੇ ਗਲਤੀ ਜਵਾਬ `buildErrorBody()` ਜਾਂ
`sanitizeErrorMessage()` ਰਾਹੀਂ ਲੰਘਦੇ ਹਨ। ਕੱਚੇ `err.stack` ਅਤੇ `err.message` ਕਾਲਰ ਨੂੰ
ਕਦੇ ਵੀ ਜਿਉਂ ਦੇ ਤਿਉਂ ਵਾਪਸ ਨਹੀਂ ਕੀਤੇ ਜਾਂਦੇ।

## 6. ਨਵੀਂ ਐਮਬੈਡਿਡ ਸੇਵਾ ਜੋੜਨਾ

ਇਨ੍ਹਾਂ 8 ਕਦਮਾਂ ਦੀ ਪਾਲਣਾ ਕਰੋ। ਪ੍ਰਮਾਣਿਕ ਹਵਾਲੇ ਵਜੋਂ `src/lib/services/installers/`
ਅਤੇ `src/app/api/services/` ਵਿੱਚ ਮੌਜੂਦਾ ਇੰਪਲੀਮੈਂਟੇਸ਼ਨਾਂ ਨੂੰ ਪੜ੍ਹੋ।

### ਕਦਮ 1 — ਇੰਸਟਾਲਰ ਬਣਾਓ

`ninerouter.ts` ਦੇ ਮਾਡਲ ਅਨੁਸਾਰ `src/lib/services/installers/{name}.ts` ਬਣਾਓ:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // ਕੋਈ ਖਾਲੀ ਪੋਰਟ ਚੁਣੋ

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

`installers/utils.ts` ਤੋਂ `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` ਵਰਤੋ
— `execSync` ਜਾਂ ਸ਼ੈੱਲ ਇੰਟਰਪੋਲੇਸ਼ਨ ਕਦੇ ਨਾ ਵਰਤੋ।

### ਕਦਮ 2 — ਬੂਟਸਟਰੈਪ ਵਿੱਚ ਰਜਿਸਟਰ ਕਰੋ

`src/lib/services/bootstrap.ts` ਵਿੱਚ `SERVICES` ਐਰੇ ਵਿੱਚ ਇੱਕ `ServiceEntry` ਜੋੜੋ:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // ਜੇ API ਕੁੰਜੀ ਦੀ ਲੋੜ ਨਹੀਂ ਤਾਂ false
}
```

`cfg.tool === "myservice"` ਨੂੰ ਸੰਭਾਲਣ ਲਈ `buildSpawnArgsFactory()` ਨੂੰ ਵਿਸਤਾਰ ਦਿਓ।

#### ਪਲੱਗੇਬਲ ਪ੍ਰਦਾਤਾ-ਪਲੱਗਇਨ ਕਾਂਟ੍ਰੈਕਟ (ਪੜਾਅ 1, #7333)

`src/lib/services/providerPlugins/` ਇੱਕ `ServiceProviderPlugin` ਕਾਂਟ੍ਰੈਕਟ ਪੇਸ਼ ਕਰਦਾ ਹੈ ਜੋ
ਇੱਕ ਬੈਕਐਂਡ ਦੇ `bootstrap.ts` `ServiceEntry` ਫੀਲਡਾਂ ਅਤੇ `serviceBackends.ts`
ਮੈਨੀਫੈਸਟ-ਟੈਂਪਲੇਟ ਫੀਲਡਾਂ ਨੂੰ ਇੱਕ ਆਬਜੈਕਟ ਵਿੱਚ ਪੈਕੇਜ ਕਰਦਾ ਹੈ, ਨਾ ਕਿ ਇੱਕੋ ਬੈਕਐਂਡ ਦੇ ਸਰੂਪ ਨੂੰ
ਦੋ ਗੈਰ-ਸੰਬੰਧਿਤ ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਦਰਸਾਉਂਦਾ ਹੈ। ਇਸ ਲਿਖਤ ਦੇ ਸਮੇਂ **ਸਿਰਫ਼ `9router` ਨੂੰ
ਮਾਈਗਰੇਟ ਕੀਤਾ ਗਿਆ ਹੈ** — `bootstrap.ts` ਆਪਣੀ `SERVICES[]` ਐਂਟਰੀ
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`) ਤੋਂ ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ,
ਅਤੇ ਜੇ ਪਲੱਗਇਨ ਕਦੇ ਮੌਜੂਦ ਨਾ ਹੋਵੇ ਤਾਂ ਸਟਾਰਟਅੱਪ ਗਲਤੀ ਸੁੱਟਦਾ ਹੈ। `cliproxy`, `mux`, ਅਤੇ `bifrost`
ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਇਨਲਾਈਨ `SERVICES[]` ਲਿਟਰਲਾਂ 'ਤੇ ਬਿਨਾਂ ਬਦਲਾਅ ਦੇ ਰਹਿੰਦੇ ਹਨ।

`open-sse/config/providerPluginManifest.ts` ਵਿੱਚ ਇੱਕ ਐਡਿਟਿਵ
`createServiceBackendManifestEntry(pluginId, template)` ਹੈਲਪਰ ਵੀ ਜੋੜਿਆ ਗਿਆ ਹੈ ਜੋ ਇੱਕ `SERVICE_BACKEND_MANIFEST_TEMPLATE` ਐਂਟਰੀ ਤੋਂ ਸੁਚੱਜੀ ਤਰ੍ਹਾਂ ਬਣੀ
`ProviderPluginManifestEntry` ਤਿਆਰ ਕਰਦਾ ਹੈ — ਇਹ
ਹਾਲੇ ਕਿਸੇ ਵੀ ਲਾਈਵ ਬੇਨਤੀ ਪਾਥ ਨਾਲ **ਜੋੜਿਆ ਨਹੀਂ ਗਿਆ** (ਨਾ `generateProviderPluginManifestFromRegistry()`
ਅਤੇ ਨਾ ਹੀ `/v1/providers/[provider]/models` ਨਾਲ); ਕਾਂਟ੍ਰੈਕਟ ਦੇ ਦੂਜੇ ਬੈਕਐਂਡ ਲਈ ਸਾਬਤ ਹੋਣ ਤੋਂ ਬਾਅਦ ਇਹ ਕੰਮ ਅਗਲੀ ਕਾਰਵਾਈ ਲਈ ਬਾਕੀ ਹੈ।

ਅਗਲੀਆਂ PRs ਲਈ ਮੁਲਤਵੀ, ਮਸਲਾ #7333 ਅਧੀਨ ਟ੍ਰੈਕ ਕੀਤਾ ਗਿਆ: `cliproxyapi` ਨੂੰ ਉਸੇ
ਰਜਿਸਟਰੀ ਰਾਹੀਂ ਮਾਈਗਰੇਟ ਕਰਨਾ, `mux`/`bifrost` ਨੂੰ `ServiceBackendPluginId` ਯੂਨੀਅਨ ਵਿੱਚ ਸਧਾਰਨੀਕਰਨ ਕਰਨਾ,
ਐਗਜ਼ੀਕਿਊਟਰ-ਰੂਟਿੰਗ ਦੀ ਵਿਸ਼ੇਸ਼-ਸੰਭਾਲ (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) ਨੂੰ ਪਲੱਗਇਨ ਕਾਂਟ੍ਰੈਕਟ ਵਿੱਚ ਸ਼ਾਮਲ ਕਰਨਾ, ਅਤੇ
`createServiceBackendManifestEntry()` ਨੂੰ ਕਿਸੇ ਲਾਈਵ ਮੈਨੀਫੈਸਟ/ਮਾਡਲ ਕੋਡ ਪਾਥ ਨਾਲ ਜੋੜਨਾ।

### ਕਦਮ 4 — 7 API ਐਂਡਪੌਇੰਟ ਬਣਾਓ

`src/app/api/services/{name}/` ਦੇ ਅਧੀਨ:

```
_lib.ts            getOrInitSupervisor() ਹੈਲਪਰ
```

## 7. ਸਮੱਸਿਆ ਨਿਵਾਰਣ

### ਸੇਵਾ ਸ਼ੁਰੂ ਨਹੀਂ ਹੁੰਦੀ

**ਲੱਛਣ:** Start ਬਟਨ 503 ਵਾਪਸ ਕਰਦਾ ਹੈ, ਸਥਿਤੀ `"error"` ਜਾਂ `"starting"` ਉੱਤੇ ਹੀ ਰਹਿੰਦੀ ਹੈ।

**ਜਾਂਚ-ਸੂਚੀ:**

1. `GET /api/services/{name}/logs` ਦੀ ਜਾਂਚ ਕਰੋ (ਜਾਂ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ Logs ਪੈਨਲ ਦੀ)। `Error: ENOENT`, `address already in use`, ਜਾਂ `Cannot find module` ਵਰਗੀਆਂ ਲਾਈਨਾਂ ਲੱਭੋ।
2. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `npm` PATH ਵਿੱਚ ਹੈ: ਉਸੇ ਵਰਤੋਂਕਾਰ ਖਾਤੇ ਤੋਂ `which npm` ਚਲਾਓ ਜੋ OmniRoute ਚਲਾਉਂਦਾ ਹੈ।
3. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਸੇਵਾ ਇੰਸਟਾਲ ਹੈ: `installedVersion` ਲਈ `GET /api/services/{name}/status` ਦੀ ਜਾਂਚ ਕਰੋ। ਜੇ ਇਹ `null` ਹੈ, ਤਾਂ ਪਹਿਲਾਂ ਇੰਸਟਾਲੇਸ਼ਨ ਚਲਾਓ।
4. ਜਾਂਚ ਕਰੋ ਕਿ `DATA_DIR/services/{name}/node_modules/` ਮੌਜੂਦ ਹੈ ਅਤੇ ਖਾਲੀ ਨਹੀਂ ਹੈ।
5. ਸਾਫ਼ ਕੀਤੇ ਐਗਜ਼ਿਟ ਕਾਰਨ ਲਈ ਸਥਿਤੀ ਜਵਾਬ ਵਿੱਚ `lastError` ਫ਼ੀਲਡ ਦੀ ਜਾਂਚ ਕਰੋ।

### ਕੋਲਡ ਸਟਾਰਟ ਹੌਲੀ ਹੈ (`running` ਤੱਕ ਪਹੁੰਚਣ ਲਈ > 10 s)

**ਲੱਛਣ:** ਸਥਿਤੀ `"running"` ਜਾਂ `"error"` ਵਿੱਚ ਜਾਣ ਤੋਂ ਪਹਿਲਾਂ ਲੰਮੇ ਸਮੇਂ ਤੱਕ `"starting"` ਉੱਤੇ ਰਹਿੰਦੀ ਹੈ।

**ਵਿਆਖਿਆ:** 9Router ਦੇ ਕੋਲਡ ਸਟਾਰਟ ਵਿੱਚ ਵੱਡੇ ਡਿਪੈਂਡੈਂਸੀ ਟ੍ਰੀ (DNS, ਟਨਲ, MITM ਮੋਡੀਊਲ) ਇੰਪੋਰਟ ਕਰਨਾ ਸ਼ਾਮਲ ਹੈ। ਡਿਫਾਲਟ ਹੈਲਥ ਇੰਟਰਵਲ 2 s ਹੈ ਅਤੇ ਸੁਪਰਵਾਈਜ਼ਰ ਵੱਲੋਂ ਟਾਈਮਆਉਟ ਘੋਸ਼ਿਤ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ 3 ਕੋਸ਼ਿਸ਼ਾਂ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ (ਪਰ ਪੋਲਿੰਗ ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ)।

**ਹੱਲ:** `healthIntervalMs` ਅਤੇ `waitForHealthy` ਟਾਈਮਆਉਟ (`healthIntervalMs * 3`) ਨੂੰ `bootstrap.ts` ਵਿੱਚ ਕੌਂਫਿਗਰ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ। ਵੱਧ ਸਟਾਰਟਅੱਪ ਸਮੇਂ ਵਾਲੀਆਂ ਸੇਵਾਵਾਂ ਲਈ, `healthIntervalMs` ਨੂੰ 5000 ਅਤੇ `stopTimeoutMs` ਨੂੰ 30 000 ਤੱਕ ਵਧਾਓ।

---

### ਪੋਰਟ ਟਕਰਾਅ (`EADDRINUSE`)

**ਲੱਛਣ:** ਲੌਗਾਂ ਵਿੱਚ `address already in use :::20130` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ।

**ਕਾਰਨ:**

- ਕੋਈ ਹੋਰ ਪ੍ਰਕਿਰਿਆ ਪਹਿਲਾਂ ਹੀ ਪੋਰਟ 20130 ਵਰਤ ਰਹੀ ਹੈ।
- ਪਿਛਲੀ 9Router ਪ੍ਰਕਿਰਿਆ ਪੂਰੀ ਤਰ੍ਹਾਂ ਬੰਦ ਨਹੀਂ ਹੋਈ ਸੀ (ਜ਼ੌਂਬੀ PID)।

**ਹੱਲ:**

1. `.env` ਵਿੱਚ `NINEROUTER_PORT` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਰਾਹੀਂ ਡਿਫਾਲਟ ਪੋਰਟ ਬਦਲੋ।
2. ਟਕਰਾਅ ਪੈਦਾ ਕਰਨ ਵਾਲੀ ਪ੍ਰਕਿਰਿਆ ਲੱਭੋ ਅਤੇ ਬੰਦ ਕਰੋ: `lsof -ti :20130 | xargs kill -9`।
3. ਹਰ ਸੇਵਾ ਲਈ ਪੋਰਟ ਨੂੰ `bootstrap.ts` ਵਿੱਚ `port` ਫ਼ੀਲਡ ਰਾਹੀਂ ਕੌਂਫਿਗਰ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ।

**ਨੋਟ:** OmniRoute ਦੇ ਡਿਫਾਲਟ ਪੋਰਟ 20128 ਨਾਲ ਟਕਰਾਅ ਤੋਂ ਬਚਣ ਲਈ 9Router ਖ਼ਾਸ ਤੌਰ ਉੱਤੇ ਪੋਰਟ 20130 ਨੂੰ ਡਿਫਾਲਟ ਵਜੋਂ ਵਰਤਦਾ ਹੈ।

### ਇੰਸਟਾਲੇਸ਼ਨ ਦੌਰਾਨ ਇਜਾਜ਼ਤ ਅਸਵੀਕਾਰ (EACCES)

**ਲੱਛਣ:** ਇੰਸਟਾਲੇਸ਼ਨ 500 ਵਾਪਸ ਕਰਦੀ ਹੈ, ਲੌਗਾਂ ਵਿੱਚ `EACCES` ਜਾਂ `permission denied` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ।

**ਕਾਰਨ:**

- `DATA_DIR` ਜਾਂ ਇਸ ਦੀ ਪੈਰੈਂਟ ਡਾਇਰੈਕਟਰੀ OmniRoute ਪ੍ਰਕਿਰਿਆ ਵੱਲੋਂ ਲਿਖਣਯੋਗ ਨਹੀਂ ਹੈ।
- ਮੈਪ ਕੀਤੇ ਵਾਲਿਊਮ ਲਈ ਲਿਖਣ ਦੀ ਪਹੁੰਚ ਤੋਂ ਬਿਨਾਂ Docker rootless ਦੇ ਅੰਦਰ ਚੱਲ ਰਿਹਾ ਹੈ।

**ਹੱਲ:**

1. `DATA_DIR` (ਡਿਫਾਲਟ: `~/.omniroute/`) ਦੀ ਜਾਂਚ ਕਰੋ: `ls -la ~/.omniroute/`
2. ਯਕੀਨੀ ਬਣਾਓ ਕਿ OmniRoute ਪ੍ਰਕਿਰਿਆ ਵਾਲਾ ਵਰਤੋਂਕਾਰ ਡਾਇਰੈਕਟਰੀ ਦਾ ਮਾਲਕ ਹੈ: `chown -R $USER ~/.omniroute/`
3. Docker ਵਿੱਚ, ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਵਾਲਿਊਮ ਮਾਊਂਟ ਕੋਲ ਕੰਟੇਨਰ ਵਰਤੋਂਕਾਰ ਲਈ ਸਹੀ ਇਜਾਜ਼ਤਾਂ ਹਨ।

### ਅੱਪਡੇਟ ਅਸਫਲ ਹੁੰਦੀ ਹੈ (`npm install` ਟਾਈਮਆਉਟ ਜਾਂ ਨੈੱਟਵਰਕ ਗਲਤੀ)

**ਲੱਛਣ:** ਅੱਪਡੇਟ `InstallError` ਨਾਲ 500 ਵਾਪਸ ਕਰਦੀ ਹੈ, ਲੌਗਾਂ ਵਿੱਚ ਨੈੱਟਵਰਕ ਟਾਈਮਆਉਟ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ।

**ਜਾਂਚ-ਸੂਚੀ:**

1. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ npm ਰਜਿਸਟਰੀ ਤੱਕ ਪਹੁੰਚ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੈ: `npm ping`।
2. ਕਾਰਪੋਰੇਟ ਪ੍ਰੌਕਸੀ ਦੀ ਜਾਂਚ ਕਰੋ: `npm config get proxy`, `npm config get https-proxy`।
3. ਇੰਸਟਾਲੇਸ਼ਨ ਨੂੰ ਹੱਥੀਂ ਅਜ਼ਮਾਓ: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`।
4. ਜੇ air-gap ਦੇ ਪਿੱਛੇ ਹੋ, ਤਾਂ tarball ਨੂੰ ਪਹਿਲਾਂ ਤੋਂ ਡਾਊਨਲੋਡ ਕਰੋ ਅਤੇ `npm install /path/to/tarball.tgz` ਵਰਤੋ।

### ਸੇਵਾ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਤੁਰੰਤ ਬਾਅਦ `"error"` ਸਥਿਤੀ ਦਿਖਾਉਂਦੀ ਹੈ (ਤੇਜ਼ ਕਰੈਸ਼)

**ਲੱਛਣ:** ਸਥਿਤੀ 5 ਸਕਿੰਟਾਂ ਤੋਂ ਘੱਟ ਸਮੇਂ ਵਿੱਚ `"starting"` ਤੋਂ `"error"` ਵਿੱਚ ਬਦਲ ਜਾਂਦੀ ਹੈ। `lastError` ਵਿੱਚ `"Fast crash (exited with code 1)"` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ।

**ਜਾਂਚ-ਸੂਚੀ:**

1. ਪੂਰਾ ਲੌਗ ਟੇਲ ਪੜ੍ਹੋ: `GET /api/services/{name}/logs?tail=500`।
2. ਆਮ ਕਾਰਨ: ਸੇਵਾ ਵੱਲੋਂ ਉਮੀਦ ਕੀਤੇ ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਮੌਜੂਦ ਨਹੀਂ ਹਨ।
3. 9Router ਲਈ: ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `NINEROUTER_DISABLE_MITM=true` ਅਤੇ `NINEROUTER_DISABLE_TUNNEL=true` ਸਪੌਨ ਸਮੇਂ ਪਾਸ ਕੀਤੇ env ਵਿੱਚ ਹਨ (`installers/ninerouter.ts` ਵਿੱਚ `resolveSpawnArgs` ਵੇਖੋ)।

## 8. ਅਕਸਰ ਪੁੱਛੇ ਜਾਂਦੇ ਸਵਾਲ

**ਸਵਾਲ: ਕੀ ਮੈਂ ਐਂਬੈਡ ਕੀਤੀਆਂ ਸੇਵਾਵਾਂ ਦੇ ਐਂਡਪੌਇੰਟ non-loopback ਕਲਾਇੰਟਾਂ ਲਈ ਉਪਲਬਧ ਕਰ ਸਕਦਾ ਹਾਂ?**

ਨਹੀਂ। LOCAL_ONLY ਟੀਅਰ ਜਾਣਬੁੱਝ ਕੇ ਬਣਾਇਆ ਗਿਆ ਹੈ (ਸਖ਼ਤ ਨਿਯਮ #17)। ਉਹ ਰੂਟ ਜੋ
`npm install` ਚਲਾ ਸਕਦੇ ਹਨ ਜਾਂ `node` ਪ੍ਰਕਿਰਿਆਵਾਂ ਸਪੌਨ ਕਰ ਸਕਦੇ ਹਨ, non-loopback
ਟ੍ਰੈਫ਼ਿਕ ਤੋਂ ਪਹੁੰਚਯੋਗ ਨਹੀਂ ਹੋਣੇ ਚਾਹੀਦੇ, ਕਿਉਂਕਿ ਕਿਸੇ ਟਨਲ (Cloudflare, Ngrok, Tailscale) ਰਾਹੀਂ ਲੀਕ ਹੋਇਆ JWT
ਨਹੀਂ ਤਾਂ ਮਨਮਾਨੀਆਂ ਪ੍ਰਕਿਰਿਆਵਾਂ ਸਪੌਨ ਕਰਨ ਦੀ ਆਗਿਆ ਦੇ ਦੇਵੇਗਾ। `/api/services/` ਲਈ ਇਸ ਤੋਂ ਬਾਹਰ ਰਹਿਣ ਦਾ ਕੋਈ ਵਿਕਲਪ
ਨਹੀਂ ਹੈ — `/api/mcp/` ਦੇ ਉਲਟ, ਇਸਨੂੰ manage-scope bypass
ਸੂਚੀ ਤੋਂ ਬਾਹਰ ਰੱਖਿਆ ਗਿਆ ਹੈ। `docs/security/ROUTE_GUARD_TIERS.md` ਵੇਖੋ।

---

**ਸਵਾਲ: ਕੀ 9Router ਅਤੇ CLIProxyAPI ਪ੍ਰੋਡਕਸ਼ਨ/ਕਲਾਉਡ ਡਿਪਲੌਇਮੈਂਟਾਂ ਵਿੱਚ ਉਪਲਬਧ ਹੋਣਗੇ?**

ਹਾਂ। ਦੋਵੇਂ ਸੇਵਾਵਾਂ OmniRoute ਵਾਂਗ ਹੀ local-first ਮਾਡਲ ਦੀ ਪਾਲਣਾ ਕਰਦੀਆਂ ਹਨ। ਇਹ ਇੱਕੋ
ਮਸ਼ੀਨ ਉੱਤੇ ਚੱਲਦੀਆਂ ਹਨ ਅਤੇ loopback ਰਾਹੀਂ ਸੰਚਾਰ ਕਰਦੀਆਂ ਹਨ। ਇੱਥੇ "ਪ੍ਰੋਡਕਸ਼ਨ" ਦਾ ਮਤਲਬ ਉਹ VPS
ਜਾਂ ਲੋਕਲ ਸਰਵਰ ਹੈ ਜਿੱਥੇ OmniRoute ਡਿਪਲੌਇ ਕੀਤਾ ਗਿਆ ਹੈ, ਨਾ ਕਿ ਕੋਈ ਰਿਮੋਟ ਕਲਾਉਡ ਪ੍ਰਦਾਤਾ।

---

**ਸਵਾਲ: ਮੈਂ supervisor ਨੂੰ ਡੀਬੱਗ ਕਿਵੇਂ ਕਰਾਂ?**

1. SSE ਲੌਗ ਸਟ੍ਰੀਮ ਨੂੰ ਲਾਈਵ ਵੇਖੋ: `curl -N http://localhost:20128/api/services/9router/logs`।
2. OmniRoute ਦੇ pino ਆਉਟਪੁੱਟ ਵਿੱਚ `service:supervisor` namespace ਅਨੁਸਾਰ ਫਿਲਟਰ ਕੀਤੇ
   ਸਟ੍ਰਕਚਰਡ ਲੌਗ ਜਾਂਚੋ।
3. DB ਕਤਾਰ ਦੀ ਜਾਂਚ ਕਰੋ: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`।
4. ਮੌਜੂਦਾ ਲਾਈਵ ਸਥਿਤੀ, PID, health ਅਤੇ `lastError` ਨੂੰ ਇੱਕੋ ਕਾਲ ਵਿੱਚ ਵੇਖਣ ਲਈ
   `GET /api/services/9router/status` ਵਰਤੋ।

---

**ਸਵਾਲ: supervisor `health: "degraded"` ਜਾਂ `health: "unknown"` ਦਿਖਾਉਂਦਾ ਹੈ, ਪਰ state `"running"` ਹੈ। ਕੀ ਇਹ ਕੋਈ ਸਮੱਸਿਆ ਹੈ?**

`"degraded"` ਦਾ ਮਤਲਬ ਹੈ ਕਿ health probe ਨੇ non-200 ਜਵਾਬ ਵਾਪਸ ਕੀਤਾ। `"unknown"` ਦਾ ਮਤਲਬ ਹੈ ਕਿ ਹਾਲੇ ਤੱਕ ਕੋਈ
probe ਪੂਰਾ ਨਹੀਂ ਹੋਇਆ (ਪਹਿਲੀ poll ਨਾਲ race)। ਸਟਾਰਟਅੱਪ ਦੌਰਾਨ ਦੋਵੇਂ ਅਸਥਾਈ ਹੁੰਦੇ ਹਨ।
ਜੇ `"running"` ਤੋਂ ਬਾਅਦ `healthIntervalMs * 3` ms ਤੋਂ ਵੱਧ ਸਮੇਂ ਲਈ health
`"degraded"` ਰਹਿੰਦੀ ਹੈ, ਤਾਂ ਐਂਬੈਡ ਕੀਤੀ ਸੇਵਾ ਚੱਲ ਰਹੀ ਹੈ ਪਰ ਇਸਦੀ HTTP API ਜਵਾਬ ਨਹੀਂ ਦੇ ਰਹੀ। ਜਾਂਚੋ
ਕਿ status response ਵਿੱਚ ਪੋਰਟ ਸਹੀ ਹੈ ਅਤੇ ਕੀ ਸੇਵਾ ਵਾਸਤਵ ਵਿੱਚ
ਉਸ ਪੋਰਟ ਉੱਤੇ ਸੁਣ ਰਹੀ ਹੈ।

---

**ਸਵਾਲ: ਕੀ ਮੈਂ ਪੂਰੀ ਤਰ੍ਹਾਂ ਰੀਸਟਾਰਟ ਕੀਤੇ ਬਿਨਾਂ 9Router API key ਬਦਲ ਸਕਦਾ ਹਾਂ?**

ਨਹੀਂ। API key ਨੂੰ ਸਪੌਨ ਸਮੇਂ environment variable ਰਾਹੀਂ 9Router ਨੂੰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।
ਚੱਲ ਰਹੀ ਪ੍ਰਕਿਰਿਆ ਵਿੱਚ environment variables ਬਦਲੇ ਨਹੀਂ ਜਾ ਸਕਦੇ। `POST .../rotate-key`
ਨਵੀਂ key ਲਾਗੂ ਕਰਨ ਲਈ ਸੇਵਾ ਨੂੰ ਆਪਣੇ ਆਪ ਰੋਕ ਕੇ ਮੁੜ ਚਾਲੂ ਕਰਦਾ ਹੈ। key rotation
ਸੇਵਾ ਦੇ `stopTimeoutMs` (ਡਿਫੌਲਟ 15 s) ਅਤੇ ਇਸਦੇ ਸਟਾਰਟਅੱਪ
ਸਮੇਂ ਦੇ ਜੋੜ ਦੇ ਅੰਦਰ ਲਾਗੂ ਹੋ ਜਾਂਦੀ ਹੈ।

---

**ਸਵਾਲ: ring buffer ਦੀ ਸੀਮਾ ਕੀ ਹੈ ਅਤੇ ਜਦੋਂ ਇਹ ਭਰ ਜਾਂਦਾ ਹੈ ਤਾਂ ਕੀ ਹੁੰਦਾ ਹੈ?**

ਹਰੇਕ ਸੇਵਾ ਕੋਲ ਇੱਕ ਸਮਰਪਿਤ 5 MB ring buffer ਹੁੰਦਾ ਹੈ। ਜਦੋਂ buffer ਭਰ ਜਾਂਦਾ ਹੈ, ਤਾਂ ਨਵੀਆਂ ਲਾਈਨਾਂ ਲਈ ਥਾਂ ਬਣਾਉਣ ਵਾਸਤੇ ਸਭ ਤੋਂ ਪੁਰਾਣੀਆਂ
ਲੌਗ ਲਾਈਨਾਂ ਹਟਾ ਦਿੱਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ। SSE `snapshot` event
`tail` ਸੀਮਾ ਦੇ ਅੰਦਰ ਸਭ ਤੋਂ ਹਾਲੀਆ ਲਾਈਨਾਂ ਵਾਪਸ ਕਰਦਾ ਹੈ। ਜਦੋਂ ਤੱਕ DB ਕਤਾਰ ਵਿੱਚ
`logsBufferPath` ਸੈੱਟ ਨਾ ਹੋਵੇ, ਲੌਗ ਡਿਸਕ ਉੱਤੇ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਕੀਤੇ ਜਾਂਦੇ।
