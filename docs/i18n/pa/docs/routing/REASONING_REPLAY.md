> **ਆਖਰੀ ਵਾਰ ਅੱਪਡੇਟ ਕੀਤਾ:** 2026-06-28 — v3.8.40

OmniRoute ਸੋਚਣ-ਮੋਡ ਵਾਲੇ ਮਾਡਲਾਂ ਦੁਆਰਾ ਤਿਆਰ ਕੀਤੀ ਸਹਾਇਕ `reasoning_content` ਨੂੰ ਕੈਪਚਰ ਕਰਦਾ ਹੈ ਅਤੇ ਜਦੋਂ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾ ਨੂੰ ਇਸਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਬਹੁ-ਵਾਰੀ ਬੇਨਤੀਆਂ ਵਿੱਚ ਇਸਨੂੰ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਮੁੜ ਚਲਾਉਂਦਾ ਹੈ। ਇਹ ਉਹਨਾਂ HTTP 400 ਗਲਤੀਆਂ ਨੂੰ ਖਤਮ ਕਰਦਾ ਹੈ ਜੋ ਸਖ਼ਤ ਪ੍ਰਦਾਤਾ ਉਦੋਂ ਦਿੰਦੇ ਹਨ ਜਦੋਂ ਕਿਸੇ ਕਲਾਇੰਟ ਦੇ ਗੱਲਬਾਤ ਇਤਿਹਾਸ ਵਿੱਚ ਪਿਛਲੀ ਵਾਰੀ ਦੀ ਤਰਕ-ਪ੍ਰਕਿਰਿਆ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦੀ।

## ਇਹ ਕਿਉਂ ਮੌਜੂਦ ਹੈ

ਕਈ ਸੋਚਣ-ਮੋਡ ਪ੍ਰਦਾਤਾ ਅਗਲੀ ਵਾਰੀ ਨੂੰ ਰੱਦ ਕਰ ਦਿੰਦੇ ਹਨ ਜਦੋਂ ਤੱਕ **ਪਿਛਲੇ ਸਹਾਇਕ ਸੁਨੇਹੇ ਵਿੱਚ ਮੂਲ `reasoning_content` ਸ਼ਾਮਲ ਨਾ ਹੋਵੇ**। ਅੱਪਸਟ੍ਰੀਮ ਇਸ ਤਰ੍ਹਾਂ ਦੇ ਸੁਨੇਹਿਆਂ ਨਾਲ 400 ਵਾਪਸ ਕਰਦਾ ਹੈ:

```
ਪੈਰਾਮੀਟਰ ਗਲਤ ਹੈ: ਸੋਚਣ ਮੋਡ ਵਿੱਚ reasoning_content ਨੂੰ API ਨੂੰ ਵਾਪਸ ਭੇਜਣਾ ਲਾਜ਼ਮੀ ਹੈ।
```

ਪਰ ਆਮ ਕਲਾਇੰਟ (Cursor, Cline, Roo Code, OpenAI SDK) ਆਪਣੇ ਵੱਲੋਂ ਮੁੜ ਚਲਾਏ ਜਾਣ ਵਾਲੇ ਇਤਿਹਾਸ ਵਿੱਚੋਂ `reasoning_content` ਨੂੰ ਹਟਾ ਦਿੰਦੇ ਹਨ। OmniRoute ਇਸਨੂੰ ਸਰਵਰ-ਪਾਸੇ ਕੈਸ਼ ਤੋਂ ਬਹਾਲ ਕਰਦਾ ਹੈ, ਤਾਂ ਜੋ ਅੱਪਸਟ੍ਰੀਮ ਨੂੰ ਦਿਖਾਈ ਦੇਣ ਵਾਲੀ ਬੇਨਤੀ ਇਕਸਾਰ ਰਹੇ। ਮੁੱਦਾ #1628 ਨੇ ਹਾਈਬ੍ਰਿਡ ਮੈਮੋਰੀ/SQLite ਸਥਾਇਤਾ ਪੇਸ਼ ਕੀਤੀ, ਤਾਂ ਜੋ ਕੈਸ਼ ਪ੍ਰਕਿਰਿਆ ਦੇ ਮੁੜ ਚਾਲੂ ਹੋਣ ਤੋਂ ਬਾਅਦ ਵੀ ਕਾਇਮ ਰਹੇ।

## ਆਰਕੀਟੈਕਚਰ

```
ਵਾਰੀ N (ਸਹਾਇਕ ਜਨਰੇਟ ਕਰਦਾ ਹੈ):
  → ਜਵਾਬ ਵਿੱਚ reasoning_content + tool_calls ਸ਼ਾਮਲ ਹੁੰਦੇ ਹਨ
  → ਜੇ requiresReasoningReplay(provider, model): cacheReasoningFromAssistantMessage()
      ਲਿਖਦਾ ਹੈ (ਮੈਮੋਰੀ + DB), ਹਰ tool_call.id ਦੁਆਰਾ ਕੁੰਜੀਬੱਧ
  → ਜਵਾਬ ਕਲਾਇੰਟ ਨੂੰ ਅੱਗੇ ਭੇਜਦਾ ਹੈ (ਜੋ reasoning ਨੂੰ ਸੰਭਾਲ ਕੇ ਰੱਖ ਵੀ ਸਕਦਾ ਹੈ ਜਾਂ ਨਹੀਂ ਵੀ)

ਵਾਰੀ N+1 (ਕਲਾਇੰਟ ਫ਼ਾਲੋ-ਅੱਪ ਭੇਜਦਾ ਹੈ):
  → ਅਨੁਵਾਦਕ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ: requiresReasoningReplay(provider, model) === true
  → tool_calls ਵਾਲੇ ਅਤੇ reasoning_content ਤੋਂ ਬਿਨਾਂ ਹਰ ਸਹਾਇਕ ਸੁਨੇਹੇ ਲਈ:
      lookupReasoning(toolCalls[0].id) → ਮੈਮੋਰੀ → DB
      ਮਿਲਿਆ  → msg.reasoning_content = cached; recordReplay()
      ਨਾ ਮਿਲਿਆ → msg.reasoning_content = "" (ਪੁਰਾਣੇ DeepSeek ਲਈ ਲੈਗੇਸੀ ਫ਼ਾਲਬੈਕ)
  → ਅੱਪਸਟ੍ਰੀਮ ਨੂੰ ਇਕਸਾਰ ਇਤਿਹਾਸ ਦਿਸਦਾ ਹੈ → ਕੋਈ 400 ਨਹੀਂ
```

ਕੈਪਚਰ `open-sse/handlers/chatCore.ts` ਵਿੱਚ ਹੁੰਦਾ ਹੈ (ਦੋ ਥਾਵਾਂ ਉੱਤੇ, ਦੋ `cacheReasoningFromAssistantMessage` ਕਾਲ ਸਾਈਟਾਂ ਉੱਤੇ)। ਰੀਪਲੇਅ ਸਕੀਮਾ ਕੋਅਰਸ਼ਨ ਤੋਂ ਬਾਅਦ ਪਰ ਡਿਸਪੈਚ ਤੋਂ ਪਹਿਲਾਂ `open-sse/translator/index.ts` ਵਿੱਚ ਹੁੰਦਾ ਹੈ।

ਸਧਾਰਨ (ਬਿਨਾਂ ਟੂਲ-ਕਾਲ ਵਾਲੀਆਂ) ਸਹਾਇਕ ਵਾਰੀਆਂ ਨੂੰ ਵੱਖਰੇ ਢੰਗ ਨਾਲ ਕੁੰਜੀਬੱਧ ਕੀਤਾ ਜਾਂਦਾ ਹੈ: `buildAssistantMessageCacheKey()` ਸੈਸ਼ਨ ਸਕੋਪ ਅਤੇ ਉਸ ਵਾਰੀ ਤੱਕ ਦੀ ਨਾਰਮਲਾਈਜ਼ ਕੀਤੀ OpenAI-ਫਾਰਮੈਟ ਟ੍ਰਾਂਸਕ੍ਰਿਪਟ ਦਾ ਡਾਈਜੈਸਟ ਬਣਾਉਂਦਾ ਹੈ, ਕਿਉਂਕਿ `tools` ਮੌਜੂਦ ਹੋਣ ਉੱਤੇ DeepSeek ਨੂੰ _ਹਰ_ ਪਿਛਲੀ ਵਾਰੀ ਦੀ ਰੀਜ਼ਨਿੰਗ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ। Responses-API ਟਾਰਗੇਟਾਂ ਲਈ (ਉਦਾਹਰਨ ਵਜੋਂ `opencode-go/deepseek-v4-flash`, ਜੋ `/responses` ਵੱਲ ਰੂਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ) ਅੱਪਸਟ੍ਰੀਮ ਬਾਡੀ ਵਿੱਚ `messages` ਦੀ ਬਜਾਏ `input` ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ `translateRequest()` (`open-sse/translator/index.ts`) ਇੱਕ ਕਾਲਬੈਕ ਵਿਕਲਪ ਰਾਹੀਂ ਉਸ ਪਿਵਟ ਟ੍ਰਾਂਸਕ੍ਰਿਪਟ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ ਜਿਸਦਾ ਇਸ ਨੇ ਡਾਈਜੈਸਟ ਬਣਾਇਆ ਸੀ, ਅਤੇ ਕੈਪਚਰ ਸਾਈਟਾਂ ਉਸੇ ਟ੍ਰਾਂਸਕ੍ਰਿਪਟ ਦਾ ਡਾਈਜੈਸਟ ਬਣਾਉਂਦੀਆਂ ਹਨ। Responses ਰੀਪਲੇਅ ਪਾਸ ਹਰ ਸਰੋਤ ਫਾਰਮੈਟ ਲਈ OpenAI ਪਿਵਟ ਉੱਤੇ ਚੱਲਦਾ ਹੈ, ਇਸ ਲਈ Anthropic Messages ਕਲਾਇੰਟਾਂ (Claude → OpenAI → Responses) ਨੂੰ ਵੀ ਰੀਪਲੇਅ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

## ਸਟੋਰੇਜ — ਹਾਈਬ੍ਰਿਡ ਮੈਮੋਰੀ + SQLite

ਹੌਟ ਪਾਥ ਇੱਕ ਇਨ-ਮੈਮੋਰੀ `Map` (ਰਚਨਾ-ਅਧਾਰਿਤ LRU) ਵਰਤਦਾ ਹੈ, ਜਿਸਨੂੰ ਕਰੈਸ਼ ਰਿਕਵਰੀ ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਦਿੱਖ ਲਈ ਇੱਕ SQLite ਟੇਬਲ ਦਾ ਸਮਰਥਨ ਪ੍ਰਾਪਤ ਹੈ।

| ਪਰਤ    | ਲਾਗੂਕਰਨ                                          | ਉਦੇਸ਼                                                           |
| ------ | ------------------------------------------------ | --------------------------------------------------------------- |
| ਮੈਮੋਰੀ | `open-sse/services/reasoningCache.ts` ਵਿੱਚ `Map` | ਤੇਜ਼ ਖੋਜਾਂ, 200 'ਤੇ ਸਭ ਤੋਂ ਪੁਰਾਣੀ ਐਂਟਰੀ ਹਟਾਉਂਦਾ ਹੈ              |
| DB     | `reasoning_cache` ਟੇਬਲ (`src/lib/db/`)           | ਮੁੜ ਚਾਲੂ ਹੋਣ ਤੋਂ ਬਾਅਦ ਵੀ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ, ਅੰਕੜਿਆਂ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ |

ਲਿਖਤਾਂ ਦੋਵਾਂ ਵਿੱਚ ਜਾਂਦੀਆਂ ਹਨ। ਪੜ੍ਹਤਾਂ ਪਹਿਲਾਂ ਮੈਮੋਰੀ ਦੀ ਜਾਂਚ ਕਰਦੀਆਂ ਹਨ, ਫਿਰ DB 'ਤੇ ਫਾਲਬੈਕ ਕਰਦੀਆਂ ਹਨ (DB ਵਿੱਚ ਮਿਲੀਆਂ ਐਂਟਰੀਆਂ ਨੂੰ ਵਾਪਸ ਮੈਮੋਰੀ ਵਿੱਚ ਪ੍ਰਮੋਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ)। DB ਅਸਫਲਤਾਵਾਂ ਘਾਤਕ ਨਹੀਂ ਹੁੰਦੀਆਂ — ਇਨ-ਮੈਮੋਰੀ ਕੈਸ਼ ਹੌਟ ਪਾਥ ਦੀ ਸੇਵਾ ਜਾਰੀ ਰੱਖਦਾ ਹੈ।

**ਡਿਫਾਲਟ:**

- TTL: `2h` (`TTL_MS = 2 * 60 * 60 * 1000`)
- ਵੱਧ ਤੋਂ ਵੱਧ ਮੈਮੋਰੀ ਐਂਟਰੀਆਂ: `200` (`MAX_MEMORY_ENTRIES`)
- ਐਵਿਕਸ਼ਨ: ਸਭ ਤੋਂ ਪੁਰਾਣਾ `createdAt` ਪਹਿਲਾਂ

## ਡਾਟਾਬੇਸ ਸਕੀਮਾ

ਮਾਈਗ੍ਰੇਸ਼ਨ: `src/lib/db/migrations/033_create_reasoning_cache.sql`

```sql
CREATE TABLE IF NOT EXISTS reasoning_cache (
  tool_call_id   TEXT PRIMARY KEY,
  provider       TEXT NOT NULL,
  model          TEXT NOT NULL,
  reasoning      TEXT NOT NULL,
  char_count     INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL DEFAULT (datetime('now')),
  expires_at     INTEGER NOT NULL
);
```

ਇੰਡੈਕਸ: `expires_at`, `provider`, `model`, `created_at`। `expires_at` ਨੂੰ Unix epoch ਸਕਿੰਟਾਂ ਵਜੋਂ ਸਟੋਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ; SELECT ਪਰਤ ਪੁਰਾਣੀਆਂ ਟੈਕਸਟ ਵੈਲਿਊਆਂ ਨੂੰ `EXPIRES_AT_EPOCH_SQL` ਰਾਹੀਂ ਨਾਰਮਲਾਈਜ਼ ਕਰਦੀ ਹੈ।

ਨਵਾਂ ਸਖ਼ਤ ਪ੍ਰਦਾਤਾ/ਮਾਡਲ ਜੋੜਨ ਦਾ ਅਰਥ ਹੈ ਇਨ੍ਹਾਂ ਸੂਚੀਆਂ ਵਿੱਚੋਂ ਕਿਸੇ ਇੱਕ ਵਿੱਚ ਇਸਨੂੰ ਸ਼ਾਮਲ ਕਰਨਾ ਅਤੇ ਰੀਪਲੇ ਇੰਜੈਕਸ਼ਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰਨ ਵਾਲਾ ਯੂਨਿਟ ਟੈਸਟ ਲਿਖਣਾ। PR ਵੇਰਵੇ ਵਿੱਚ ਉਸ ਬਿਲਕੁਲ ਸਹੀ ਅੱਪਸਟ੍ਰੀਮ 400 ਸਤਰ ਦਾ ਹਵਾਲਾ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ ਜਿਸ ਨੇ ਤਬਦੀਲੀ ਲਈ ਪ੍ਰੇਰਿਤ ਕੀਤਾ।

## ਕਾਰਜਕਾਰੀ ਟਿੱਪਣੀਆਂ

- **ਸਫ਼ਾਈ:** `cleanupReasoningCache()` ਦੀ ਮਿਆਦ ਪੁੱਗ ਚੁੱਕੀਆਂ ਮੈਮੋਰੀ ਐਂਟਰੀਆਂ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ ਅਤੇ `DELETE FROM reasoning_cache WHERE expires_at <= unixepoch('now')` ਚਲਾਉਂਦਾ ਹੈ। ਸਿਹਤ-ਜਾਂਚ ਵਰਕਰ ਇਸਨੂੰ ਸਮੇਂ-ਸਮੇਂ 'ਤੇ ਕਾਲ ਕਰਦੇ ਹਨ।
- **ਕ੍ਰੈਸ਼ ਤੋਂ ਮੁੜ-ਪ੍ਰਾਪਤੀ:** ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ ਮੈਮੋਰੀ ਖਾਲੀ ਹੁੰਦੀ ਹੈ, ਪਰ DB ਵਿੱਚ ਅਜੇ ਵੀ ਮਿਆਦ ਨਾ ਪੁੱਗੀਆਂ ਐਂਟਰੀਆਂ ਮੌਜੂਦ ਰਹਿੰਦੀਆਂ ਹਨ। ਕਿਸੇ ਦਿੱਤੇ `tool_call_id` ਲਈ ਪਹਿਲੀ ਖੋਜ DB ਹਿੱਟ ਹੁੰਦੀ ਹੈ; ਇਸ ਤੋਂ ਬਾਅਦ ਦੀਆਂ ਖੋਜਾਂ ਮੈਮੋਰੀ ਹਿੱਟ ਹੁੰਦੀਆਂ ਹਨ।
- **ਕੋਈ ਰੀਜ਼ਨਿੰਗ ਨਹੀਂ, ਕੋਈ ਕੈਸ਼ ਨਹੀਂ:** ਜਦੋਂ ਸਹਾਇਕ ਸੁਨੇਹੇ ਵਿੱਚ ਕੋਈ `reasoning_content` / `reasoning` ਫੀਲਡ ਨਹੀਂ ਹੁੰਦੀ, ਤਾਂ `cacheReasoningFromAssistantMessage` `0` ਵਾਪਸ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਗੈਰ-ਥਿੰਕਿੰਗ ਜਵਾਬਾਂ ਦੀ ਕੋਈ ਲਾਗਤ ਨਹੀਂ ਹੁੰਦੀ।
- **ਲਿਖਣਾ ਵੀ ਸ਼ਰਤਬੱਧ ਹੈ:** `chatCore.ts` ਵਿੱਚ ਦੋਵੇਂ ਕਾਲ ਸਥਾਨ (ਗੈਰ-ਸਟ੍ਰੀਮਿੰਗ ਅਤੇ ਸਟ੍ਰੀਮਿੰਗ) ਸਿਰਫ਼ ਉਦੋਂ ਹੀ `cacheReasoningFromAssistantMessage()` ਨੂੰ ਕਾਲ ਕਰਦੇ ਹਨ ਜਦੋਂ `requiresReasoningReplay(provider, model)` `true` ਹੁੰਦਾ ਹੈ — ਇਹ ਉਹੀ ਪ੍ਰੈਡੀਕੇਟ ਹੈ ਜਿਸਦੀ ਰੀਡ ਸਾਈਡ ਜਾਂਚ ਕਰਦੀ ਹੈ। ਉਹ ਇੰਸਟਾਲੇਸ਼ਨ ਜੋ ਕਦੇ ਵੀ ਕਿਸੇ ਰੀਪਲੇ ਪ੍ਰਦਾਤਾ ਨੂੰ ਨਹੀਂ ਵਰਤਦੀਆਂ, ਹਰ ਰੀਜ਼ਨਿੰਗ-ਧਾਰਕ ਜਵਾਬ ਉੱਤੇ ਲਿਖਣ, ਇੰਡੈਕਸ ਅੱਪਡੇਟ ਅਤੇ try/catch ਦੀ ਲਾਗਤ ਦੇਣੀ ਬੰਦ ਕਰ ਦਿੰਦੀਆਂ ਹਨ।
- **ਗੈਰ-ਸਖ਼ਤ ਪ੍ਰਦਾਤਾ:** ਜਦੋਂ `requiresReasoningReplay` `false` ਹੁੰਦਾ ਹੈ ਅਤੇ ਟਾਰਗੇਟ ਫਾਰਮੈਟ OpenAI ਹੁੰਦਾ ਹੈ, ਤਾਂ ਟ੍ਰਾਂਸਲੇਟਰ ਬਾਹਰ ਜਾਣ ਵਾਲੇ ਸੁਨੇਹਿਆਂ ਵਿੱਚੋਂ ਕਿਸੇ ਵੀ `reasoning_content` ਫੀਲਡ ਨੂੰ **ਹਟਾ ਦਿੰਦਾ ਹੈ** — OpenAI Chat Completions ਇਸਨੂੰ ਸਵੀਕਾਰ ਨਹੀਂ ਕਰਦਾ।

## Muse ਅਪਾਰਦਰਸ਼ੀ ਤਰਕ ਦੀ ਮਾਲਕੀ

Muse (`muse-code`) ਕਾਲਰ ਨਾਲ ਬੱਝਿਆ ਅਪਾਰਦਰਸ਼ੀ ਤਰਕ (`encrypted_content`) ਵਾਪਸ ਕਰਦਾ ਹੈ। ਇਸ ਨੂੰ ਵੱਖਰੇ ਖਾਤੇ ਜਾਂ ਮੁੜ ਜਾਰੀ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਨਾਲ ਰੀਪਲੇ ਕਰਨਾ ਅੱਪਸਟ੍ਰੀਮ 'ਤੇ ਨਾਕਾਮ ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ ਨੇਟਿਵ OAuth ਬੇਨਤੀਆਂ ਪ੍ਰਤੀ-ਬੇਨਤੀ ਬਦਲਾਅ ਦੀ ਥਾਂ ਸੈਸ਼ਨ-ਪੱਧਰੀ ਮਾਲਕੀ ਵਰਤਦੀਆਂ ਹਨ (`src/sse/services/museSessionOwnership.ts`, ਲਾਗੂਕਰਨ `src/sse/handlers/chat.ts` ਵਿੱਚ)। ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਚੁਣੇ API-ਕੁੰਜੀ ਕਨੈਕਸ਼ਨ ਅਤੇ ਸਿਰਫ਼ API-ਕੁੰਜੀ ਸੰਰਚਨਾਵਾਂ ਇਸ ਮਾਲਕੀ ਮੋਡ ਤੋਂ ਬਿਨਾਂ ਆਪਣੀ ਮੌਜੂਦਾ ਰਾਊਟਿੰਗ ਰੱਖਦੀਆਂ ਹਨ।

- ਹਰ ਟਰਨ ਵਿੱਚ ਸਥਿਰ ਸੈਸ਼ਨ ID ਦਿਓ: `x-omniroute-session-id`, `x-omniroute-session`, `x-session-id` ਜਾਂ `x-codex-session-id`; ਜਾਂ ਬਾਡੀ ਵਿੱਚ `prompt_cache_key`, `session_id`, `conversation_id` ਜਾਂ `metadata.session_id` ਵਰਤੋ (ਇਸੇ ਪਹਿਲ ਦੇ ਕ੍ਰਮ ਵਿੱਚ)। ਦੋ ਜਾਂ ਵੱਧ ਨੇਟਿਵ OAuth ਖਾਤੇ ਸਰਗਰਮ ਹੋਣ 'ਤੇ ਗੁੰਮ ਜਾਂ ਖਾਲੀ ID 400 ਵਾਪਸ ਕਰਦੇ ਹਨ; ਇੱਕ OAuth ਖਾਤੇ ਨਾਲ ਬਦਲਣ ਲਈ ਹੋਰ ਖਾਤਾ ਨਹੀਂ ਹੁੰਦਾ, ਇਸ ਲਈ ਅਜਿਹੀ ਬੇਨਤੀ ਬਿਨਾਂ ਪਿੰਨ ਵਾਲੀ ਰਾਊਟਿੰਗ ਰੱਖਦੀ ਹੈ। ਸਕੋਪ ਵਿੱਚ ਕਾਲਰ ਦੀ OmniRoute API-ਕੁੰਜੀ ਦਾ ID ਸ਼ਾਮਲ ਹੈ।
- ਨਵੇਂ ਸੁਤੰਤਰ ਸੈਸ਼ਨ API-ਕੁੰਜੀ ਦੀ ਕਨੈਕਸ਼ਨ ਨੀਤੀ ਵੱਲੋਂ ਮਨਜ਼ੂਰ ਸਰਗਰਮ ਨੇਟਿਵ OAuth ਖਾਤਿਆਂ ਵਿੱਚ ਕਨੈਕਸ਼ਨ ID ਅਨੁਸਾਰ ਵਾਰੀ-ਵਾਰੀ ਵੰਡੇ ਜਾਂਦੇ ਹਨ। ਇਹ ਵੰਡ ਕਨੈਕਸ਼ਨ ਕੂਲਡਾਊਨ, ਅੰਤਿਮ ਸਥਿਤੀ (`banned`, `expired`, `credits_exhausted`) ਜਾਂ ਮੰਗੇ ਮਾਡਲ ਲਈ ਲੌਕ ਵਾਲੇ ਖਾਤੇ ਛੱਡਦੀ ਹੈ; Muse ਅੱਪਸਟ੍ਰੀਮ ਨਾਕਾਮੀਆਂ ਹੋਰ ਪ੍ਰਦਾਤਿਆਂ ਵਾਂਗ ਕੂਲਡਾਊਨ ਅਤੇ ਬ੍ਰੇਕਰ ਸਥਿਤੀ ਦਰਜ ਕਰਦੀਆਂ ਹਨ। ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਲਾਜ਼ਮੀ ਕੀਤਾ ਕਨੈਕਸ਼ਨ ਨਵੇਂ ਸੈਸ਼ਨ ਲਈ ਵਾਰੀ-ਵਾਰੀ ਵੰਡ ਛੱਡਦਾ ਹੈ, ਪਰ ਸਫਲ ਜਵਾਬ ਦੇ ਚੁੱਕੇ ਮਾਲਕ ਨੂੰ ਨਹੀਂ ਬਦਲ ਸਕਦਾ।
- ਮਾਲਕ ਵੱਲੋਂ ਸਫਲ ਜਵਾਬ ਦੇਣ ਤੱਕ, ਜਿਸ ਸੈਸ਼ਨ ਦਾ ਮਾਲਕ ਅਣਉਪਲਬਧ ਹੋ ਗਿਆ ਹੋਵੇ ਉਹ ਸਿਹਤਮੰਦ ਖਾਤੇ ਨੂੰ ਮੁੜ ਸੌਂਪਿਆ ਜਾਂਦਾ ਹੈ। ਪਹਿਲੇ ਸਫਲ ਜਵਾਬ ਤੋਂ ਬਾਅਦ ਸੈਸ਼ਨ ਉਸ ਮਾਲਕ ਨਾਲ ਪਿੰਨ ਰਹਿੰਦਾ ਹੈ ਜਦੋਂ ਤੱਕ ਉਹ 30 ਦਿਨ ਨਿਸ਼ਕ੍ਰਿਆ ਨਹੀਂ ਰਹਿੰਦਾ (`MUSE_SESSION_IDLE_TTL_MS`)।
- ਹਰ ਜਾਰੀ ਬੇਨਤੀ ਅਤੇ ਟੂਲ-ਨਤੀਜਾ ਟਰਨ ਸੈਸ਼ਨ ਮਾਲਕ ਨਾਲ ਪਿੰਨ ਰਹਿੰਦਾ ਹੈ: ਕਨੈਕਸ਼ਨ, ਖਾਤਾ ਪਛਾਣ ਅਤੇ ਇਨਫਰੈਂਸ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਦੀ ਪੀੜ੍ਹੀ; ਇਹ ਅੱਪਸਟ੍ਰੀਮ ਕੋਸ਼ਿਸ਼ਾਂ ਤੋਂ ਪਹਿਲਾਂ ਮੁੜ ਜਾਂਚੇ ਜਾਂਦੇ ਹਨ, ਪ੍ਰਮਾਣ-ਪੱਤਰ ਰੀਫ੍ਰੈਸ਼ ਤੋਂ ਬਾਅਦ ਦੀਆਂ ਕੋਸ਼ਿਸ਼ਾਂ ਸਮੇਤ। Responses ਕਾਲ ID/ਆਈਟਮ ਹਵਾਲੇ ਅਤੇ Chat Completions ਟੂਲ-ਕਾਲ ID ਉਸ ਸੈਸ਼ਨ ਅਤੇ ਪੀੜ੍ਹੀ ਲਈ ਦਰਜ ਹੋਣੇ ਲਾਜ਼ਮੀ ਹਨ।
- `muse_session_ownership` ਨੇਮਸਪੇਸ ਵਿੱਚ SQLite `key_value` ਰਿਕਾਰਡ (`src/lib/db/museSessionOwnership.ts`) ਮਾਲਕੀ ਅਤੇ ਰੋਟੇਸ਼ਨ ਕਰਸਰ ਰੀਸਟਾਰਟਾਂ ਵਿਚਕਾਰ ਸੰਭਾਲਦੇ ਹਨ। ਹਰ ਦਾਅਵਾ ਅਤੇ ਦਿੱਤਾ ਜਵਾਬ ਸੈਸ਼ਨ ਦੀ ਸਰਗਰਮੀ ਦਾ ਸਮਾਂ ਅੱਪਡੇਟ ਕਰਦਾ ਹੈ; `MUSE_SESSION_IDLE_TTL_MS` ਤੋਂ ਵੱਧ ਨਿਸ਼ਕ੍ਰਿਆ ਸੈਸ਼ਨ ਸਾਫ਼ ਹੁੰਦਾ ਹੈ (ਮਾਲਕ ਪਿੰਨ, ਜਵਾਬ ਦਿੱਤੇ ਜਾਣ ਦਾ ਫਲੈਗ ਅਤੇ ਦਰਜ ਅਪਾਰਦਰਸ਼ੀ/ਹਵਾਲਾ ਹੈਸ਼), ਵੱਧ ਤੋਂ ਵੱਧ ਹਰ 10 ਮਿੰਟਾਂ ਵਿੱਚ ਇੱਕ ਵਾਰ ਅਤੇ ਸੀਮਿਤ ਬੈਚਾਂ ਵਿੱਚ, ਇਸ ਲਈ ਬਾਅਦ ਦਾ ਇਤਿਹਾਸ ਰੀਪਲੇ ਅਣਜਾਣ ਮਾਲਕ ਵਜੋਂ ਸੁਰੱਖਿਅਤ ਤੌਰ 'ਤੇ ਰੱਦ ਹੁੰਦਾ ਹੈ। ਰਿਕਾਰਡਾਂ ਵਿੱਚ ਕਨੈਕਸ਼ਨ ID ਅਤੇ ਖਾਤਾ ਪਛਾਣ, ਪ੍ਰਮਾਣ-ਪੱਤਰਾਂ, ਅਪਾਰਦਰਸ਼ੀ ਸਮੱਗਰੀ ਅਤੇ ਜਾਰੀ ਹਵਾਲਿਆਂ ਦੇ ਹੈਸ਼ ਹੁੰਦੇ ਹਨ, ਭੇਤ ਜਾਂ ਗੱਲਬਾਤ ਇਤਿਹਾਸ ਨਹੀਂ। ਕਲਾਇੰਟਾਂ ਨੂੰ ਪੂਰਾ ਇਤਿਹਾਸ ਅਤੇ ਅਪਾਰਦਰਸ਼ੀ ਤਰਕ ਸੰਭਾਲ ਕੇ ਭੇਜਣਾ ਲਾਜ਼ਮੀ ਹੈ।
- ਅਣਜਾਣ ਜਾਂ ਪਰਾਇਆ ਅਪਾਰਦਰਸ਼ੀ ਤਰਕ, ਗੁੰਮ ਮਾਲਕ, ਅਣਉਪਲਬਧ ਮਾਲਕ-ਖਾਤਾ ਜਾਂ ਦਰਜ ਇਤਿਹਾਸ ਨਾਲ ਪੀੜ੍ਹੀ ਦੀ ਤਬਦੀਲੀ ਸਪਸ਼ਟ 4xx/503 ਨਾਲ ਸੁਰੱਖਿਅਤ ਤੌਰ 'ਤੇ ਰੱਦ ਹੁੰਦੀ ਹੈ — ਕਦੇ ਚੁੱਪਚਾਪ ਹੋਰ ਖਾਤੇ 'ਤੇ ਫੇਲਓਵਰ ਨਹੀਂ ਹੁੰਦਾ ਅਤੇ ਤਰਕ ਕਦੇ ਨਹੀਂ ਸੁੱਟਿਆ ਜਾਂਦਾ।
- ਉਸੇ ਖਾਤੇ ਦੀ ਮੁੜ ਜਾਰੀ ਕੁੰਜੀ ਸਿਰਫ਼ ਉਦੋਂ ਅਪਣਾਈ ਜਾਂਦੀ ਹੈ ਜਦੋਂ ਸੈਸ਼ਨ ਨੇ ਰੀਪਲੇਯੋਗ ਇਤਿਹਾਸ ਦਰਜ ਨਹੀਂ ਕੀਤਾ; ਦਰਜ ਇਤਿਹਾਸ ਵਾਲੇ ਸੈਸ਼ਨ ਨਵੇਂ ਸਿਰੇ ਤੋਂ ਸ਼ੁਰੂ ਹੋਣ ਤੱਕ ਸੁਰੱਖਿਅਤ ਨਕਾਰ ਕਰਦੇ ਰਹਿੰਦੇ ਹਨ।
- ਖਾਲੀ ਅੱਪਸਟ੍ਰੀਮ ਜਵਾਬ (`upstream_empty_response` / `empty_response`, ਕਾਲਰ ਨੂੰ ਕੁਝ ਨਹੀਂ ਭੇਜਿਆ ਗਿਆ) ਉਸੇ ਮਾਲਕ 'ਤੇ ਵੱਧ ਤੋਂ ਵੱਧ ਦੋ ਵਾਰ, ਪਹਿਲਾਂ 0.5 s ਅਤੇ ਫਿਰ 1.5 s ਬਾਅਦ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`MUSE_EMPTY_RESPONSE_RETRY_DELAYS_MS`)। ਸਾਰੀਆਂ ਕੋਸ਼ਿਸ਼ਾਂ ਖਾਲੀ ਹੋਣ 'ਤੇ ਮੂਲ 502 ਬਿਨਾਂ ਕੂਲਡਾਊਨ ਜਾਂ ਬ੍ਰੇਕਰ ਚਿੰਨ੍ਹ ਦੇ ਵਾਪਸ ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ ਅਸਥਿਰ ਜਵਾਬ ਕਦੇ ਮਾਲਕ ਨੂੰ ਲੌਕਆਉਟ ਨਹੀਂ ਕਰਦਾ।
- ਸਾਰੀਆਂ `muse-code` ਬੇਨਤੀਆਂ ਸਟ੍ਰੀਮਿੰਗ ਲਿਖਤਾਂ ਸਮੇਤ ਸੈਮੈਂਟਿਕ-ਕੈਸ਼ ਪੜ੍ਹਤਾਂ ਅਤੇ ਲਿਖਤਾਂ ਛੱਡਦੀਆਂ ਹਨ, ਤਾਂ ਜੋ ਕੈਸ਼ ਕੀਤਾ ਅਪਾਰਦਰਸ਼ੀ ਆਉਟਪੁੱਟ ਹੋਰ ਸੈਸ਼ਨ ਮਾਲਕ ਨਾ ਲੈ ਸਕੇ।
